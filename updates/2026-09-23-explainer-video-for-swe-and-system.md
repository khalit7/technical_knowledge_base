The first is the direction of dependency: the fundamentals bound what a design may promise, the design shapes the code, the craft decides whether it survives. The second is where a model bends the ordinary answer, and the page names four places. Requests are seconds of GPU time streamed a token at a time rather than a few milliseconds of a processor. Capacity arrives in whole GPUs rather than fluid virtual CPUs, and there is no tenth of one. Correctness is statistical rather than binary, so what you can promise is a distribution rather than an assertion. And cost per call is not a later optimisation: it picks the design, because caching, routing and quotas are the architecture rather than tuning laid on top of it. That is the one comparison in the episode, drawn as a grid of the same four questions asked of a CRUD service and of a model service.

One layer down, the fundamentals get the beat the page says they deserve: they are not background reading you get to eventually, they are how you defend a design choice by naming the bottleneck rather than by pattern matching. fsync latency at roughly a millisecond, which caps what one transaction can write; TCP slow start, which is why short-lived connections underuse the link; the page cache, which is why a disk read is often free and why memory pressure looks like unexplained IO; and GPU memory bandwidth, which caps decode throughput because generating one token reads the whole weight set once. Then the payoff this page makes and few pages do: OSTEP's three-way split lands on GPU serving almost directly, paging becoming KV cache block management and scheduling becoming continuous batching. The craft pillar is the three separate things an ML system makes you test, code and data and model behaviour, where the third has no assertion that a generated answer is correct, only that it still behaves. The ten-thousand-tenant walk is where the three pillars visibly compose, and the page notes it is also, almost verbatim, the ML system design interview. The take is that the board is not a reading list, whatever the forty-four hours of resources hanging off it suggest: it is an order of dependency that runs both ways, justify up and debug down, and the only part of it that is in none of those books is the part where the model bends four answers. It closes on the gap the page names against Andrew Ng's list of software fundamentals: front end proper and conventional application security are not here, and if that is the job this is not your map.
