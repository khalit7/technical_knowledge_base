# Interactive HTML ideas

Every visualisation considered so far for the Technical knowledge base's interactive pages: what was built, what was proposed, and what was rejected, followed by the method used to decide. Per-page research notes with full formulas and every URL are kept in `technical_knowledge_base/<section>/<topic>/<page>/src/viz_ideas*.md`.

## 2. Methodology: how a good visualisation is chosen, and where ideas come from

The method grew out of Khalid's direction on each round. It starts from the content, not from a catalogue of chart types. Before anything is drawn, the builder reads the page and everything it leans on until it could teach the subject, then writes down in one sentence the question the subject keeps returning to: for Topic: llms it was where the test-time budget goes and what a model costs to serve; for DeepSeek, what it costs to train and serve; for Google, what a request costs counted in tokens. A visualisation is worth building when it makes that question measurable. The page's existing visuals and outbound links are listed first, so new ideas do not repeat what exists and the page's own sources become the first places to look.

Two kinds of visual have proved most valuable, and Khalid singled out both. The first recomputes a published figure from a formula, with one parameter the reader can move: the DeepSeek Cache tab rebuilds the KV memory of every attention design from its configuration, and the Compute tab does the same for FLOPs per token, each landing on the number the lab itself reported. The second lays the whole subject on one axis, usually time, as the Lineage and release-timeline tabs do. Both teach something prose cannot: a crossover where one cost overtakes another, a dominant term that changes as a parameter moves, a shape such as a funnel or a pipeline bubble, or a trajectory over years.

Candidates are scored from 0 to 2 on a fixed set of questions. Is there a quantity that changes with a parameter the reader controls? Do the defaults reproduce a figure a source states? Can every input be computed from public data (papers, configuration files, code, pricing pages) rather than read off an image or guessed? Does it show something a sentence cannot? Does it correct a known misconception, such as reading the $5.6M training figure as the whole cost of DeepSeek-V3, or "one million tokens means an hour of anything"? Does it measure the page's central question? Is it absent from the page and from the main existing explainers? Reproducing a claim and being computable count double, build cost is subtracted, and ties go to the visual that links to more of the page's other tabs. A visual is rejected when it shows a single number with nothing to move, when its data exists only in images, when it repeats something already shown, or when its subject belongs to another page.

Placement follows from scope. Every page has the same frame: a Reading tab first, holding the explanation interleaved with the visuals needed to follow it; one tab for each visual that deserves room of its own; and Further reading last, with every page and resource linked and timed. A visual gets its own tab when it answers a question of the form "across all of X, how does Y change": across every generation, every model, every release. It sits inside Reading when it explains one mechanism at the moment the text introduces it, and inside an existing tab when it shares that tab's axis, as the DeepSeek config diff shares the Lineage tab's set of models. On a root topic page the Reading tab is kept as short as it can be while still self-sufficient, because the depth lives on the child pages; on a deep dive nothing is cut, because that page owns its details.

Numbers are treated with care because the HTML is now the only content of the page. Each figure is traced to the source that first states it, and the link is recorded at the moment it is read. Every proposed visual is recomputed in a short script before it is proposed; that is how the V4-Flash compute figure was found to come out at 12% against DeepSeek's 10%, which the tab now shows as an exposed assumption instead of hiding. Each number is labelled as published, derived with its formula, illustrative, or unconfirmed. The Google round added four rules: say whether a default reproduces a figure independently or only by construction (the cost-per-task split matches Artificial Analysis because one input was back-solved from it); when two primary figures disagree, as Gemma 4's report does with its own memory table, show both with the arithmetic behind each rather than picking silently; record the index version beside every benchmark index score, since launch-day and current figures are on different scales; and when two current documentation pages disagree, ask which models each figure applies to.

The sources searched fall into a consistent order, from the most authoritative to the most interpretive. Primary papers and technical reports come first, in their HTML versions on arXiv where the figures and tables can be read, because the authors' own figures show which quantity they think matters and their tables hold the numbers every calculation needs: the DeepSeek V2 to V4 reports, the R1 paper, the Gemini 1.5 and 2.5 reports, the Gemma 2, 3 and 4 reports. Model cards and configuration files on Hugging Face come next for exact architecture values, and a model card's headline chart is often the figure worth reproducing (the V4.1-Flash card's 437x cache reduction). Official code repositories give diagrams of systems behaviour, formula tables and small algorithms that can be ported exactly, as DualPipe and EPLB were. Changelogs and pricing pages turn into time series of releases and prices. Visual explainers show what the field has already drawn, so the page does not copy it and so it is clear which ideas readers find hard: Jay Alammar's illustrated R1, Sebastian Raschka's architecture comparison and gallery, Maarten Grootendorst's visual guides to MoE and reasoning, Hugging Face blogs on MLA, GRPO and Gemma. Interactive explainers and playbooks show interaction patterns that work: the Ultra-Scale Playbook's calculators, siboehm's pipeline-parallel tables, Polo Club's Transformer Explainer, Brendan Bycroft's LLM Visualization, and the many VRAM calculators. Analysts and data trackers provide independent estimates and series to cross-check against: Epoch AI (training compute, inference price trends, open against closed and US against China gaps, the Capabilities Index, DeepSeek's training cost), Artificial Analysis (the Intelligence Index and cost per task), METR (task time horizons), LMArena and its history, OpenRouter's usage study, SemiAnalysis, the Stanford AI Index, Our World in Data, LifeArchitect's models table and timeline, Information is Beautiful, and Pareto-frontier trackers. Videos come last, useful for metaphors but rarely for data.

How the search was run changed with the tools available. The Topic: llms round used web search, with queries built from patterns such as "<author> visual guide <topic>", "<technique> interactive visualization" or "explorable", "<model> technical report figure <quantity>", "<model> API price history", "<model> training cost estimate", and, always, a search for critiques of the topic's best-known claims, because a widespread misconception makes a good visual. By the DeepSeek and Google rounds the session's search budget was spent, so research ran by fetching pages directly: the page's own links, canonical addresses (arXiv HTML pages, GitHub organisations, Hugging Face model and config pages, API documentation paths, named authors' newsletters) and links found inside fetched pages. Some tactics proved reliable: preferring arXiv's /html/ pages to /abs/, asking for exact tables rather than summaries, following redirects by hand, using raw README files when the rendered page is thin. Paywalled or bot-blocked hosts, prices that appear only in images, and summarised READMEs that drop the table you need are the usual failures; a number that cannot be confirmed is marked unconfirmed rather than filled in from memory.

The second Google round added ten more rules, most of them about numbers that look like facts and are not. Check a source's rounding before calling a mismatch a contradiction. Run every published limit through the window arithmetic, because session limits, file-size caps and output caps often fall out of window divided by rate; if one matches, label it as a reconstruction rather than as the cause. Never join two metrics a company reports one after the other (Google moved from monthly tokens across surfaces to API tokens per minute); plot them as separate series and say when each stops being reported. For an "effective" or "active" parameter claim, sum the parameter table every way and show which sum reproduces the headline, or show the candidates if none does. A memory table's KV column may not credit the architecture's own savings, so recompute it both ways. Speeds and latencies are measurements with a date, like index scores, and third parties quoting them go stale. Compare compute only at matched precision, stating dense or sparse on both sides. When an official model repository is gated, use a named mirror, say so, and cross-check one value against the report. Extract saved PDFs with pdftotext in layout mode, which keeps tables intact. And treat regulatory filings as a search engine: full-text search over SEC filings returns the exact exhibit for any phrase a company has used about itself, which beats guessing blog addresses.

The thirteen other child pages of Topic: llms added rules of their own, most of them about where a published figure can mislead. A headline ratio whose accounting is unstated (MiniMax's "1/20 of the per-token compute", Zhipu's per-layer, per-head "fair comparison") is shown under each accounting, with the one that reproduces it named, since a per-layer and a whole-model ratio can differ by nearly two times. Parameter-counting conventions differ even within one vendor (Mistral's Devstral 2 leaves out the input embedding, Medium 3.5 of the same shape includes it), so each row states its convention and a toggle switches between them. A paper's own tables are checked for internal arithmetic before use (one percentage in Llama 3's Table 5 is a misprint), and when a paper compares against "the predecessor", the table header, not the prose, says which model that is. When a config and its paper disagree, the config describes the checkpoint. A model card superseded by a later technical report is treated as the older source and the page says what changed; a leaderboard re-run in place is two dated readings, side by side. A vendor's table that quotes a rival's score is checked against the rival's own figure (xAI's 57.9% for Fable 5.1 is Anthropic's figure for GPT-6 Astra). Values printed as labels on a figure may be transcribed, with a label, because transcription is exact where reading a curve is not. Corporate events have several dates: the regulatory filing fixes the legal one, the company's own usage fixes the name. When a live page differs from its archived copies, the archived raw HTML is used and the live reading marked unconfirmed. And when a page leans on a curated third-party table, every row is recomputed, the match count published and each mismatch shown with both arithmetics, as the Architecture Gallery did for 84 of 86 KV figures.

Some pages are not about mechanisms, and the scoring fits them poorly. Categorical facts that vary per item, such as licences checkpoint by checkpoint, become a checker or a matrix read verbatim, never paraphrased into thresholds the text does not state; whether a model is still served by the API and whether its weights can still be downloaded are tracked separately. On a data page the table is the main visual and keeps every field of every row, tags the compiler assigned are labelled as the compiler's rather than the labs', every chart that derives a "first" carries the table's window caveat, and every aggregate is checked to sum back to the table. A breadth page with many small subjects puts them on the same axes, with an evidence column (vendor, independent or mixed) and a labelled fallback where a value such as active parameters is missing. A security design has no number to reproduce, so its before/after animation is labelled an illustrative scenario built from the lab's components and implies no behaviour the source does not state. In sampling maths, a per-problem formula is not the benchmark curve, and a distribution fitted to two published points matches them by construction, so anything it implies beyond them is labelled derived. Three new kinds of source proved useful: a lab's public training logs (Ai2's Weights & Biases projects return sampled history anonymously, with the caveats that sampling hides single-step spikes and gaps between runs are unlabelled); the Hugging Face refs API, whose count of public checkpoint branches is a dated measurement; and the Wayback Machine's CDX API with raw captures, which gets past bot-blocked lab sites.

Animation is one of the strongest tools available and should be used often. Khalid singled out the DeepSeek MLA explainer: one token animated step by step through multi-head latent attention, with a toggle that runs the same animation for standard multi-head attention, so the old method and the new one can be watched side by side. That is the pattern to repeat wherever a page explains a mechanism that replaced an earlier one, or a process that unfolds in steps: show the previous method and the new one as two animations of the same input, drawn to the same scale, so the difference is seen rather than described. What made it work, and should be copied: everything drawn to scale (one square per 64 numbers, so 576 against 32,768 is visible); a caption for every step saying what happens and why it matters; running counters that tie the picture to the numbers the text quotes; play, pause, step forward and back, a scrubber and a speed control, so a reader can stop on the step they are thinking about; and good manners, meaning it only animates while on screen and in the visible tab, and starts paused, one step at a time, when the reader's system asks for reduced motion. An animation earns its place under the same test as any visual (it must teach something a static view or a sentence cannot), but motion through steps and a before-and-after comparison usually pass that test, so when scoring candidates, give an explicit point to "can be shown as a step-by-step animation, ideally against the method it replaced". The earlier rejection of an animated MLA explainer as duplicating the static mode switch was wrong: the static switch shows the two end states, the animation shows how one becomes the other.

The aim is a skill that makes all of these decisions on its own for any topic: what the page needs understood, which visuals would make that measurable, where to find ideas for them, and where to find and check their data. What remains to settle before it is written down as such is a tested set of search queries for when web search is available, and the requirement, already practised here, that every proposed visual comes with a recompute script whose defaults land on a published figure.
