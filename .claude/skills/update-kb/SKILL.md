# update-kb

The repository is the source of truth; the site shows it and Notion links to it. This skill is the periodic pass that keeps the knowledge base current. It replaces the old Notion skills (update-KB, the knowledge-base half of "Run the weekly Monday update", create-interactive-html, create-explainer-video and the Notion-to-GitHub mirror), which were deleted on 2026-10-19. Everything they knew that still applies is in this folder.

Every page is still built with the `explainer-page` skill and published with `sync-kb-github`; this skill decides **what** changes, and in what order. **Every page this run creates or edits follows the teaching contract** ([../explainer-page/teaching/teaching-contract.md](../explainer-page/teaching/teaching-contract.md)): core idea, hero figure, "You need" and new terms at the top; core first, depth in closed `<details>`; the header "Reading: N min, plus M in closed details."; nothing moves before the reader acts; one owner per concept ([../../../technical_knowledge_base/OWNERS.md](../../../technical_knowledge_base/OWNERS.md)); a knowledge ledger (`src/ledger.json`) kept true. The editorial rules that decide **how** an update reads are in [editorial-rules.md](editorial-rules.md). Read both before writing anything; where they disagree, the contract wins.

## The window always comes from Notion
1. Query the Notion data source `collection://99887928-0063-4df2-a9e8-7260a099e423` (database "Source freshness" on Me / _AI / Last updated) for the row whose `Source` is `Technical KB` (row id `3e15c17b-0d0d-8127-97b5-e5229f7d5682`). Its **Through date** is the last day already covered.
2. The window runs from that Through date (inclusive, so nothing on the boundary day is missed; drop items the previous issue already carries) to today. Never infer the start from a schedule, from git history or from memory: only from that row.
3. Cross-check: the newest folder in `technical_knowledge_base/reference/tech_news/` should be dated the Through date. If they disagree, say so in the report and use the Notion row anyway.
4. If the window is longer than about two weeks, still do one pass and one issue covering the whole window (name the issue by the window's end date, and say in its At a glance that it covers several weeks).

## Steps
1. **Set up.** `git pull`; the tree must be clean. In a cloud sandbox (the weekly routine), first run `. html_utils/cloud_setup.sh` from the repo root, once, in the lead's shell, before any agent starts (agents never re-source it; [../explainer-page/lessons.md](../explainer-page/lessons.md), 2026-10-26): it installs the Python env and check tools and points every page check at the sandbox's Chromium with `--no-sandbox` (the sandbox runs as root; without it every check script crashes). `python3 html_utils/sync_status.py --no-build` should say Notion is up to date; if not, publish what is pending first (`sync-kb-github`), so this run's diff is only this run's work. Save `python3 html_utils/check_times.py` to the scratchpad as the baseline of stale quotes that predate the run.
2. **Research the window** (read only, nothing written yet):
   - **Releases and results** relevant to the existing topic map: models and tools, papers, benchmark results, chips and compute, developer tooling and agents. Search per topic root (titles in `pages.json`), and separately for important releases that topic searches miss.
   - **The currency sweep** that release tracking is blind to: who owns it, what it costs, what licence it is under, can you buy it (acquisitions, price and licence changes, commercial availability). See [editorial-rules.md](editorial-rules.md).
   - **Newsletters**: with the Gmail connector, read-only, open every technical newsletter issue received in the window (rules in "Newsletters" below).
   - **Scope**: AI/ML and major big-tech developments, and significant technical community discussion (Hacker News points and comments recorded as dated readings). Skip general startups, consumer gadgets and crypto unless genuinely major.
   - Every item gets a primary source link, its date and who reported it; vendor claims are labelled as such.
3. **Triage into a plan**, written to the scratchpad, before any page changes. Each item gets exactly one route:
   - **News issue only** (industry news, a release with no durable lesson).
   - **News issue and a page edit**: name the page that owns the subject (look it up in `technical_knowledge_base/OWNERS.md` first, then `pages.json` and the topic roots), what passage changes, its ledger label (`core`; `depth`, for a closed block; or `volatile`: a version, price, availability, leaderboard reading or incident, which goes only to the provider page's dated table, a dated closed block or the issue), and which sentences elsewhere it makes untrue (the root's map, tables, summary claims, comparisons, sibling pages). Other pages get one sentence and a link to the owner, never a second copy.
   - **Paper page**: a paper central to a topic gets a row in the Papers database and its own page; a less central one is only linked in the issue. The paper page owns the paper's method, numbers and evidence (OWNERS.md, Reference); a concept page states the result in a sentence or two, with its scope, and links the paper for the numbers.
   - **New topic or child page**: only when no existing page fits and the body of durable knowledge justifies it, never because one or two items lack a home. Propose it to Khalid in the report rather than building it in this run.
   - **Dropped**, with the reason.

   Common items and the pages they always touch (find each page's folder and id in `pages.json`; this is a floor, not a limit):

   | Item | Owner (gets the depth) | Also check and fix |
   |---|---|---|
   | A new or updated model from a lab with its own page (OpenAI, Anthropic, Google DeepMind, Meta, DeepSeek, Qwen, Mistral, Moonshot, MiniMax, xAI, Zhipu, Ai2) | that lab's child page under Topic: llm-landscape (current family, sizes, context, pricing, licence, scores with harness) | Topic: llm-landscape root: its map, comparison tables and "state of play" claims; Other notable providers if it names the lab |
   | A model from a lab without its own page | Other notable providers (under llm-landscape) | the llm-landscape root; propose a new provider page in the report if the lab now matters enough |
   | A model that introduces an architectural change (attention, MoE, positional scheme, hybrid, objective) | the matching Topic: llm-architecture child (attention variants, mixture of experts, long context, beyond attention, families and objectives, ...) and the LLM Architecture Gallery | the llm-architecture root; the lab's llm-landscape page names the change and links to it |
   | New benchmark scores or a new benchmark version | the matching Topic: benchmarks child (knowledge and reasoning, math, coding, agentic, long context and multimodal, arenas, safety) | the benchmarks root; any llm-landscape page quoting the old figure |
   | Serving, training, hardware, agents, retrieval, tooling news | the child page that owns the mechanism in that topic | that topic's root, and any page with a superlative or comparison the news changes |
4. **Papers first**, so the issue can quote their scoped claims. For each paper routed to a page: create its row in the Papers database (`collection://d440058d-ec1c-4b72-b141-046d5d969389`, properties `Paper`, `Year` with venue where relevant, `Topics` from the existing options, `Takeaway` in one sentence that agrees with the page) with the link line from the `sync-kb-github` skill as its body, add its `pages.json` entry (`path` under `reference/papers/`, exact `title`, `id`, `parent` "Papers", `section` "Reference", `status` `html_only`, `"notion": "link"`) and its line in `reference/papers/README.md`, then build it with page kind [paper](../explainer-page/page-kinds/paper.md), whose "Teaching contract on a paper page" section lists what the page must have (core sentence, hero, You need, new terms, closed depth, measured header, the template `99_js_tabs.js`, no autoplay, a ledger once final). **Scope the takeaway to the paper's own evidence**: the model and size, single runs or seeds, the metric, matched comparisons rather than each side's best, no "first", "proves", "beats" or "consistently" without support; the same text goes in `paper.json`, the card, `live.md` if the page has one, `mk_coverage.py` and the row's `Takeaway` property.
5. **Write the tech-news issue** as a new page: folder `technical_knowledge_base/reference/tech_news/YYYY_MM_DD_tech_news/` (the window's end date), built with the `explainer-page` skill, page kind [tech-news](../explainer-page/page-kinds/tech-news.md). The issue text is written fresh into `src/issue.md` (it plays the role `live.md` plays for an older issue: the issue's own words, which later re-checks never overwrite). Copy the machinery from the newest issue. Shape: the 3 to 5 most important stories first, then sections as warranted; concise, factual, linked, no hype. Each item names the knowledge-base page it feeds. **The issue's words are frozen once published, so scope them before writing**: an item about a paper is written from the paper, or from its page when it has one, never from the blog or abstract: which model and size, single runs or seeds, which metric, matched comparisons, the conditions a theorem needs, no "first", "proves", "beats" or "consistently" without support (2026-10-26: the issue printed a blog's "about 30%" and an unconditional theorem, corrected only in boxes; [tech-news](../explainer-page/page-kinds/tech-news.md)).
6. **Integrate the durable knowledge** into the owning pages' `src/parts`, following the teaching contract and [editorial-rules.md](editorial-rules.md): rewrite the passage so the page reads as if it had always been true, then walk up and fix what the change invalidates (root map and tables, summary claims, comparisons, Further reading). Place each unit by its label: a durable mechanism or result in core, beside its visual; detail, provenance and per-item lists (incident catalogues, version rows) in closed `<details>`; volatile facts in the provider page's dated table or a closed block whose summary carries its read date ("as of 26 October 2026"; on a paper page "Since the paper (checked <date>)"), never as present-tense core prose ("now", "the latest") and never as a promise ("weights promised by <date>"). For every edited page, in this order (the checks of [../explainer-page/orchestration/briefs/rebuild-page.md](../explainer-page/orchestration/briefs/rebuild-page.md), steps 5 and 6):
   - add or relabel its units in `src/ledger.json`, each key a string the built page shows (a page without a ledger gets one only when it is rewritten, `ledger.py init`);
   - rebuild (in a cloud sandbox the C locale can reorder globbed parts: diff the rebuilt `index.html` against HEAD);
   - recompute the header "Reading: N min, plus M in closed details." from `node html_utils/audit_pages.mjs <scratch>/a.jsonl <folder>` and `python3 html_utils/audit_pages.py <scratch>/a.jsonl` (Reading tab, 230 words a minute, both numbers), then rebuild;
   - `sh html_utils/checkpage.sh <folder>` ends `fail=0, emdash 0, errbox 1, clipped 0` (read its exit status; never `checkpage.sh ... | tail -1 && commit`, the pipe hides a failure); `python3 html_utils/ledger.py check <folder>` prints problems 0; the page's own checks in `src/` pass.

   When every page is final, `python3 html_utils/check_times.py --fix` rewrites the reading times other pages quote for the changed headers; rebuild and recheck every page it lists under "fixed pages", and copy each AMBIGUOUS line it prints into the report (fix by hand those that quote a page this run changed). If the page has a video, the video now lags the page: add one line beside the header line that names the video, saying what the video does not cover and the date the page moved past it; remove it when the video is remade. Never remake videos in this run.
7. **Register the issue page.** Create the Notion child page under Tech news (`3c65c17b-0d0d-8172-97b0-f28491701516`) titled `YYYY-MM-DD: tech news` with the link line as its body, add its `pages.json` entry (`parent` "Tech news", `section` "Reference", `status` `html_only`, `"notion": "link"`) and its line in `reference/tech_news/README.md`. Link the previous issue's Further reading to the new one (a page edit like any other).
8. **Publish** every changed and new page with the `sync-kb-github` skill (check, commit, push; the site deploys from main) until `sync_status.py --no-build` says "Published". Every page must pass its checks (`checkpage.sh` `fail=0`, `ledger.py check` problems 0 where a ledger exists, its own `src/` checks) before it is committed; in a cloud sandbox run the privacy checks with a neutral `USER`/`HOME` (the sandbox login is `root`). A new page that owns a concept gets its `OWNERS.md` row in the same commit (a paper page is covered by the Reference row); a page that fails is fixed or left uncommitted and named in the report. When a page goes live, update the status line in its `README.md` to say it is published: never leave "not yet published" or "being built" on a live page (`grep -rn "not yet published" technical_knowledge_base --include=README.md` must print nothing at the end).
9. **Move the date forward, last**, so it only ever reflects completed work: update the `Technical KB` row: `Through date` = the window's end, `Last processed` = today, `Status` `Current` only when everything planned shipped, every changed page passed its checks and `check_times.py` lists no stale quote (fixable or ambiguous) beyond the set-up baseline; otherwise `Partial`, naming the pages and the reason (2026-10-26: 22 pages were left with stale quotes and the row said Current), and `Notes`: the window, the issue page (its full `https://app.notion.com/p/<id>` link written out as text, since a Markdown link in a property is dropped), the pages changed, the papers added, open provenance questions. Notes replace the previous notes; history is in git and in the issues.
10. **Report** to Khalid (see the end).

## Newsletters
Read with the Gmail connector only; never send, label, archive or draft anything. Search the window for recurring editorial publications about software, AI/ML, data or the tech industry (TLDR, Medium digests, Towards Data Science and similar are examples, not a closed list): a dated issue, a masthead, a run of linked stories with short blurbs, sent by a publication rather than a person.
- **Keep**: anything matching a topic; significant releases, results and papers with the **primary** source link (never the newsletter's tracking redirect); big-tech moves worth a line in the issue; an article only when it has real technical substance (a method, a benchmark, a postmortem, a non-obvious result).
- **Drop**: sponsored items, job ads, course promotions, listicles, career advice, shallow rehashes, anything you cannot pin down beyond the blurb, marketing mail wrapped as a newsletter.
- Collapse each story to one candidate across issues and publications, keeping the best link. Then route it with everything else in step 3. List the newsletters opened in the report so Khalid can prune the set.
- Nothing from mail ever enters the repository except the public story and its primary link: no addresses, names of senders who are people, or account mail.

## Short videos and other source media
A short video, post or thread is a source type, not a knowledge silo: route its durable content to the owning page. Record source, creator, URL, duration and capture date; keep the creator's claim separate from verified fact; never promote an unsupported claim into a page. A video that is mainly a good explanation goes to the page's Further reading instead.

## Orchestration
Research can be split across subagents (for example one per section of topics, plus one for newsletters), and the issue, page edits and papers can be built by agents with the `explainer-page` briefs. Follow Khalid's current rule on how many agents run at once and the lead rules in [../explainer-page/orchestration/topic-pipeline.md](../explainer-page/orchestration/topic-pipeline.md): agents never commit, publish, write to Notion or edit `pages.json`; the lead merges the plan, so two items that touch the same page become one coherent edit. No Workflow tool without Khalid's opt-in. In a cloud sandbox, follow the 2026-10-26 lesson in [../explainer-page/lessons.md](../explainer-page/lessons.md): the lead sources `cloud_setup.sh` once, rebuilt pages are compared against HEAD, privacy checks run with a neutral `USER`/`HOME`, and no check is piped into a commit.

## Hard rules
- Never write to Notion except: the new Tech news child page and new Papers rows (each a link page), the link-page steps of `sync-kb-github`, and the freshness row at the end.
- Never put knowledge in Notion: its pages are only links to the site. If a Notion page holds text that is not in the repository, stop and show Khalid.
- There is no Updates changelog, Tracker or Visuals database any more (retired 2026-10-19): do not recreate them. The record of a run is its tech-news issue, its git commits and the freshness row's notes.
- No em-dashes anywhere. Privacy grep before every commit (the pattern list is in `engineering_foundations/topic_protocols/src/.private_patterns`).
- Never delete a Notion page; retitle "TO DELETE: ..." and tell Khalid.

## Report
One tight summary, leading with anything that failed: the window and where it came from; sources and newsletters read; the issue page (link); every page changed and why; papers added; items dropped and why; proposed new topics or children; pages left unpublished or with failing checks, and why; the AMBIGUOUS lines `check_times.py` left; open provenance questions; the freshness row as written.
