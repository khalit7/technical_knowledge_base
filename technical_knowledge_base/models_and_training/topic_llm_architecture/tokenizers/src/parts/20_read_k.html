Training your own

Use the Hugging Face {{tokenizers|https://github.com/huggingface/tokenizers}} library or {{SentencePiece|https://github.com/google/sentencepiece}} on a corpus that matches your target distribution: the vocabulary is frozen with the model, so the languages, scripts, code and number formats you care about must be in the tokenizer's training data. Decide the pre-tokenization rules (digits, whitespace runs, code) before training, reserve special tokens for your chat template, and measure fertility on held-out text in every language you will serve. Where the training corpus comes from and how it is filtered is the subject of {{Topic: data-curation-and-datasets|n:3c65c17b0d0d811fa5ecda8d365ab00f}}. Changing the tokenizer of a trained model means new embedding rows that start untrained, so extending a vocabulary (Llama 3 added 28K entries to tiktoken's 100K before training, not after) is far easier than swapping one.

The running example's tokenizer is a complete, minimal recipe: the code below is the training part of the root's src/data/prepare_data.py, as rerun by src/bpe/bpe_sweep.py, with that run's printed result.

Settings worth knowing: initial_alphabet=ByteLevel.alphabet() puts all 256 bytes in the vocabulary even if the corpus lacks some (without it, a byte never seen in training could not be encoded); min_frequency stops training early on a small corpus (43,702 entries instead of 65,536 here); special tokens are listed up front so they get the first ids and are never split.

Common mistakes

Comparing token counts or prices across models as if a token were a fixed amount of text
The same English text costs about the same with every current tokenizer (4.8 to 5.0 characters per token on FLORES English), but other languages differ by up to 5 times between tokenizers. Compare per character or per word of your own text.
Reading config vocab_size as the number of tokens
Configs pad the embedding matrix: Qwen3's says 151,936 for 151,669 real entries, DeepSeek-V3's 129,280 for 128,815. Count the tokenizer's entries, not the config.
Assuming every modern tokenizer splits digits the same way
GPT-4, GPT-4o, Llama 3 and 4 and DeepSeek group digits in threes from the left; LLaMA 2, Gemma and Qwen split every digit. Number formatting in prompts changes what the model sees.
Ending a prompt with a space
The space usually belongs to the next token (" Paris" is one token), so a prompt ending in a bare space forces an unusual boundary. See {{Failure modes|#rd-fail}}.
Calling WordPiece "BPE with a different score" in the Hugging Face library
The library's WordPieceTrainer runs plain frequency BPE with ## prefixes; the likelihood score is the course's reconstruction of Google's unpublished trainer. A WordPiece vocabulary trained with the library and BERT's original are built by different rules.
Distilling logits between models with different tokenizers
Token-level distributions only line up when the vocabularies match; otherwise distil on sampled text, or use a method built for mismatched vocabularies.
Trusting a trailing space, or stripping one, without checking
On SmolLM2-135M, "The capital of France is" and the same prompt plus one space give different next-token distributions and different continuations (measured above). Keep prompts in the form the model was trained on; never end a completion prompt with a space.
Training a model on text its tokenizer was not trained on
The running example's TinyStories BPE needs 64 tokens for a 91-character Python function and 3 tokens per Chinese character (one per byte); Llama 3's needs 28 and about 1. A model fine-tuned on a new domain or language with an old tokenizer pays that on every token, and rarely used entries may be glitch tokens.
Letting special-token strings through from user text
Qwen3's tokenizer turns the typed string "<|im_end|>" into the real end-of-turn id 151645 by default (measured above). Use split_special_tokens=True for untrusted text or escape it before templating.
Tokenizing a rendered chat template a second time
Rendering with tokenize=False and then calling the tokenizer adds a second beginning-of-sequence token on Gemma 3 (ids start [2, 2, 105], measured above). Tokenize with the template, or pass add_special_tokens=False.

Interview questions

Why do LLMs use subword tokens rather than words or bytes?
Words leave out-of-vocabulary holes and need huge vocabularies; bytes have no holes but make sequences 3 to 4 times longer, and attention and per-token compute scale with length. Subwords keep frequent words whole and fall back to bytes for the rest: no holes, short sequences. Measured here: the running story is 874 bytes, 255 tokens with a 4,096-entry BPE.
Walk through one step of BPE training. What breaks ties?
Count every adjacent symbol pair inside pre-tokenized words, weighted by word frequency; merge the most frequent pair into a new symbol everywhere; record the merge. Hugging Face's trainer orders a priority queue by count, then by the pair with smaller ids (trainer.rs, quoted above), and stops at the target size or when the best count falls below min_frequency.
How is BPE encoding different from WordPiece encoding?
BPE replays learned merges by rank inside each word (lowest rank first). WordPiece stores no merges and takes the longest vocabulary match from the left, with ## for continuations, mapping a whole word to [UNK] if any part fails. The same vocabulary can give different pieces ("hugs": hug ##s against hu ##gs).
A 1B-parameter model has a 256K vocabulary and width 2,048, tied. What share of its weights is the embedding, and what does the output layer cost per token?
256K × 2,048 = 537M, about half of 1B. The output layer is 2 × 256K × 2,048 = 1.07 GFLOPs per token, about half of the forward pass of a 1B model (2 GFLOPs). Gemma 3 1B is close to this (262,144 × 1,152 = 302M, 30% of 1.0B, from the root's Config calculator).
Why does gpt-oss-20b's vocabulary matter more than Llama 3.1 8B's, although its table is a smaller share of total parameters?
Total parameters do not run per token; active ones do. gpt-oss-20b activates 4 of 32 experts, so its 201,088 × 2,880 untied tables are 28% of the active parameters and its output layer 16% of the decode FLOPs per token, against 13% and 7% for dense Llama 3.1 8B (root Config calculator numbers).
Why might a model fail to add 12345 + 6789, and what cheap change helps?
A tokenizer that cuts digit runs in threes from the left gives 123|45 and 678|9: units digits sit in different token positions, so place value is not aligned. Commas force right-to-left groups. Measured here on OLMo 2 1B: 3% exact plain against 19% with commas, digit accuracy 39% against 71%; Singh and Strouse 2024 show the same on GPT-3.5 and GPT-4. Single-digit tokenizers (Qwen, Gemma) avoid it at the price of longer numbers.
What is a glitch token and how would you find them in a model you are given?
A vocabulary entry the model almost never saw in training, so its embedding is untrained. Find candidates from the weights: rows that cluster together or have unusual norms (here 132 unseen entries had cosine similarity 0.996 with each other and norms 2.5 times the median), check frequency in a training sample, then confirm by prompting the model to repeat the token.
Config says vocab_size 151,936 but the tokenizer has 151,669 entries. Bug?
No: the embedding is padded to a round multiple so the matmul tiles well on tensor cores (pad_to_multiple_of in transformers). The extra rows are never emitted by the tokenizer; they still cost parameters and output FLOPs. Count len(tokenizer), not the config.
Design: you are pretraining a 3B model that must serve English, Hindi, Japanese and Python. How do you choose the tokenizer?
Train byte-level BPE (no holes) on a sample matching the target mix, oversampling the smaller languages so they get merges; pick digit handling (single digits, or groups of three from the right) and whitespace-run tokens for code before training; reserve chat and tool special tokens up front. Size: measure characters per token on held-out text per language at, say, 64K, 128K and 256K, and weigh tokens saved against the table's cost (at width 3,072 a 256K untied vocabulary is 1.6B parameters, half the model, so tie the embeddings or stay near 128K: SmolLM3 3B ties a 128,256-entry table, root map config). Check the result: fertility per language within about 1.5 times English, no unseen entries in a training sample, round-trip decode exact on every test string.
Why do almost all new 2026 models reuse their predecessor's tokenizer?
A tokenizer change invalidates every embedding and output row and every cached dataset tokenization, so it only happens with a new pretraining run and a measured gain. Measured here: DeepSeek-V4 keeps V3's 128,000 ordinary tokens, Gemma 4 shares 262,125 entries with Gemma 3, GLM-5.3, MiniMax-M3 and Olmo 3 equal their predecessors. Qwen3.5 and Llama 4 changed theirs, for multilingual coverage.
