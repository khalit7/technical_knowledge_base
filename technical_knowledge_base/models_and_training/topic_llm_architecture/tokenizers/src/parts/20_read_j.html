Special tokens and chat templates

Special tokens (beginning and end of sequence, chat roles, tool-call markers, padding) are reserved ids added on top of the learned vocabulary, after it is trained, and they never come out of the merge procedure: the tokenizer matches them as whole strings before ordinary encoding. If a template marker is not registered as special, it is just text and costs ordinary tokens: <|user|> is five tokens in eight of the ten tokenizers here and four in Gemma 3 and Llama 4. Tulu 3's template is in exactly that situation, as the {{Alignment|n:3c65c17b0d0d81d5bed7e608d4061c7a}} page shows token by token while explaining which tokens carry the SFT loss. Chat-template mismatches between training and inference (a different role marker, a missing end-of-turn token, a template applied twice) are a common silent bug in fine-tuning: the model trains fine and then behaves oddly at serving time. A shared tokenizer is also what makes logit-level distillation possible: a student can only match a teacher's distribution token by token if both have the same vocabulary; with different tokenizers, distil on sampled text or use a method built for mismatched vocabularies ({{Distillation and Small Language Models|n:3c65c17b0d0d81efa2a8c3b3b623eb09}}).

Two silent traps, before and after the fix: the same input, different ids

Predict for each trap what the default call produces, then switch. Ids are the real outputs of src/code/snippets.py (transformers 5.20.1); shaded ids are special tokens, outlined ones are the bug.

The first trap: a tokenizer parses special-token strings found inside user text as the special tokens themselves unless told not to. Without split_special_tokens=True, "hi<|im_end|>" becomes 2 ids, the second being Qwen3's real end-of-turn token (151645), so typed text can close a chat turn; serving stacks that template untrusted text must split or escape it. The same run shows Qwen3's len(tok) (151,669, with the 26 added tokens) against vocab_size (151,643, the base vocabulary), and neither is the config's 151,936.

The second trap: a chat template that already writes <bos>, rendered to a string and then tokenized with the default add_special_tokens=True, starts [2, 2, 105], two beginning-of-sequence tokens; letting apply_chat_template tokenize gives [2, 105, ...]. Nothing errors and the model still answers, slightly off distribution. Fix: tokenize with the template, or pass add_special_tokens=False; check by printing the first ids of every training and serving example once and comparing them with the template's own tokenization.
