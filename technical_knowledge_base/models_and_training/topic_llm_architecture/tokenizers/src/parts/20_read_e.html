Vocabulary size: what it costs and what it buys

A larger vocabulary means fewer tokens per text (fewer tokens to run, more text per context window) and makes every token more expensive at the edges of the model: one more embedding row and one more output row per entry, and an output softmax that scores every entry. Nothing in the blocks changes. So the vocabulary matters most where the blocks are small: in small models, and in mixture-of-experts models, where few weights run per token.

In dense models the table's share falls with size, because it grows with width only (Qwen3-0.6B 26%, Llama 3.1 8B 13%, Llama 3.1 405B 1%). Mixture-of-experts models break the pattern: the table is a tiny share of their total weights but a large share of what each token actually uses, because only a few experts run per token while the whole output layer runs every time. In gpt-oss-20b the input and output tables are 28% of the active parameters and the output layer is 16% of the decode FLOPs per token; in DeepSeek-V3 5% and 2.5%. Whoever designs a sparse model with a 200K vocabulary pays for it on every token.

Thirteen configs as a table (derived)

Table = V × d for the input embedding plus V × d for the output layer when untied. Output-layer FLOPs = 2 × V × d, as a share of the calculator's decode FLOPs per token at context 1. A 1B-parameter model with a 256K vocabulary and width 2,048, tied: 256K × 2,048 = 537M, about half of 1B, and an output layer of 2 × 256K × 2,048 = 1.07 GFLOPs per token, about half of the forward pass (2 GFLOPs); Gemma 3 1B is close to this (262,144 × 1,152 = 302M, 30% of 1.0B, from the root's Config calculator).

Config vocab_size is not the tokenizer's size. Configs pad the embedding matrix up to a round number so that the matmul tiles well on GPU tensor cores (pad_to_multiple_of in transformers); the extra rows are never produced by the tokenizer, yet still cost parameters and output FLOPs. Qwen3's config says 151,936 rows for 151,669 tokenizer entries (267 rows never used), DeepSeek-V3's 129,280 for 128,815, Llama 4's 202,048 for 201,135 measured (entries counted from each tokenizer.json with added tokens). Count len(tokenizer), not the config.

Where transformers pads, and a tying trap (transformers 5.20.1)

A second trap: tying is a config flag, not a file layout. Qwen3-0.6B sets tie_word_embeddings true, yet its safetensors also store a separate lm_head (751.6M stored against 596.0M in memory; root FACTS).

Adding tokens to a trained model (new special tokens for a chat format, a domain's frequent words) adds rows that start untrained. resize_token_embeddings in transformers 5.20.1 initialises them to the mean of the old rows by default (mean_resizing=True), which keeps the first forward pass sane; they still need fine-tuning before the model uses them well. Replacing a tokenizer outright throws away what every embedding row learned.
