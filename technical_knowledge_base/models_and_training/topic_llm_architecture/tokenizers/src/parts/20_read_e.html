Vocabulary size: what it costs and what it buys

The trade, in one line. A larger vocabulary means fewer tokens per text (fewer tokens to run, more text per context window, a cheaper effective context) and makes every token more expensive at the edges of the model: one more embedding row and one more output row per entry, and an output softmax that scores every entry. Nothing in the blocks changes. So the vocabulary matters most where the blocks are small: in small models the table is a real fraction of a small model's parameters, and in mixture-of-experts models a real fraction of the active ones.

Predict: the tiny GPT has 4,721,920 parameters outside its embedding. If it used GPT-2's tokenizer (50,257 entries, tied, width 256) instead of the 4,096-entry one, what share of its parameters would be the embedding table?
derived 50,257 × 256 = 12.87M against 4.72M: 73% of the model would be a lookup table, and the output layer would cost 25.7M FLOPs per token against 9.4M for all six blocks. With 4,096 entries the table is 1.05M (18%). That is why the setup trained its own small vocabulary (root src/data/README.md), and the same arithmetic is why Gemma 3 270M is "170 million embedding parameters ... and 100 million for our transformer blocks" ({{Google|https://developers.googleblog.com/en/introducing-gemma-3-270m/}}, 262,144 × 640 = 167.8M embedding parameters of 268.1M, leaving 100.3M, reproduced from its config).

Share of total and of active parameters (the calculator's "all" accounting, embedding included; routed experts scaled by k/E). Output-layer FLOPs = 2 × V × d, as a share of the calculator's decode FLOPs per token at context 1 (the embedding lookup costs no FLOPs). The {{Vocabulary size|#t-voc}} tab charts all 45 configs.

Read down the columns. In dense models the table's share falls with size, because it grows with width only (Qwen3-0.6B 26%, Llama 3.1 8B 13%, Llama 3.1 405B 1%). Mixture-of-experts models break the pattern: the table is a tiny share of their total weights but a large share of what each token actually uses, because only a few experts run per token while the whole output layer runs every time. In gpt-oss-20b the input and output tables are 28% of the active parameters and the output layer is 16% of the decode FLOPs per token; in DeepSeek-V3 5% and 2.5%. Whoever designs a sparse model with a 200K vocabulary pays for it on every token.

Config vocab_size is not the tokenizer's size. Configs pad the embedding matrix up to a round number so that the matmul tiles well on GPU tensor cores; the extra rows are never produced by the tokenizer. Transformers exposes this when you resize:

Qwen3's config says 151,936 rows for 151,669 tokenizer entries (267 rows never used), DeepSeek-V3's 129,280 for 128,815, Llama 4's 202,048 for 201,135 measured (entries counted from each tokenizer.json with added tokens). The padded rows still cost parameters and output FLOPs. A second trap: tying is a config flag, not a file layout. Qwen3-0.6B sets tie_word_embeddings true, yet its safetensors also store a separate lm_head (751.6M stored against 596.0M in memory; root FACTS).

Adding tokens to a trained model (new special tokens for a chat format, a domain's frequent words) adds rows that start untrained. resize_token_embeddings in transformers 5.20.1 initialises them to the mean of the old rows by default (mean_resizing=True), which keeps the first forward pass sane; they still need fine-tuning before the model uses them well. Replacing a tokenizer outright throws away what every embedding row learned.
