In one screen

A tokenizer cuts text into tokens, pieces drawn from a fixed list called the vocabulary, and replaces each piece by its position in that list, an integer id. The model only ever sees those ids: id i selects row i of the embedding matrix, and at the output the model scores every one of the V vocabulary entries. Every current LLM uses subword tokens: frequent words stay whole, rare words break into pieces, and nothing is ever unknown because the pieces bottom out in single bytes. The vocabulary is learned from a corpus before pretraining and frozen with the model. Three algorithms learn it: BPE merges the most frequent pair, WordPiece merges the pair whose parts are most surprising together, Unigram starts big and prunes. Production LLMs almost all run byte-level BPE; what differs between them is the vocabulary size (32K to 262K), the pre-tokenization rules (how digits, spaces and code are cut before merging) and the data the vocabulary was trained on, which decides who pays more tokens for the same text.

The running example. Every number on this page that can be measured on the running example of {{Topic: llm-architecture|n:3fd5c17b0d0d8172b490dc9f9ac281df}} is: the tiny GPT (6 layers, width 256, 5.84M parameters) reads TinyStories through a byte-level BPE of 4,096 tokens trained on TinyStories itself, and the running sequence is the 256-token opening of a held-out story about Roxy the rhinoceros (root src/data/README.md). This page retrains that tokenizer, takes it apart merge by merge, and puts it beside the tokenizers of real models.

Problem
A model needs a finite set of input symbols. Words are too many and leave holes; bytes are too long. Subwords keep sequences short without holes.
How
Learn a vocabulary from a corpus (BPE, WordPiece or Unigram), cut text into its pieces, map pieces to ids, and map ids back to text exactly.
Cost
One embedding row per entry (plus an output row unless tied), an output softmax over V entries per token, and every token the text needs, which is compute, context and money.
When it matters
Small models (the table can be a quarter of the weights), MoE models (it is a large share of the active weights), other languages and code (2 to 15 times more tokens), numbers, spelling, chat templates.
How to check
Count tokens per character on your own text, print the pieces of the strings you care about, compare len(tokenizer) with vocab_size, and diff the template's token ids against what training used.

What a tokenizer does, on the running example

Intuition first: a tokenizer is a lossless compressor with a fixed dictionary. Text goes in, a shorter list of dictionary positions comes out, and decoding the list gives back exactly the same text. A modern tokenizer runs four stages, each a separate object in the Hugging Face tokenizers library: a normalizer (optional cleanup such as Unicode NFC; the running example has none), a pre-tokenizer (cuts text into word-like chunks that no token may cross, and for byte-level BPE turns each chunk into bytes), the model (BPE: applies learned merges inside each chunk), and a post-processor (adds special tokens such as a beginning-of-sequence marker). The decoder runs it backwards.

Where the ids go. Inside the model, id i selects row i of the embedding matrix E (V × d = 4,096 × 256 in the tiny GPT), and the output layer multiplies the final hidden state by a V × d matrix to give one score (logit) per vocabulary entry.
