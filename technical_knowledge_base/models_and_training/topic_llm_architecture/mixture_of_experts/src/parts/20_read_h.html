Fine-tuning an MoE with transformers and assuming it is still balanced

Qwen3-MoE, Mixtral, gpt-oss and Llama 4 compute their auxiliary loss only when output_router_logits=True, and their configs ship with it off: a tiny Qwen3-MoE returns aux_loss = [[f:hfc_aux_none|s]] by default and [[f:hfc_aux_on|f2]] with the flag (about k = 2, the value of perfect balance under transformers' formula, section 3). DeepSeek-V3 has no auxiliary loss and never updates its bias: three AdamW steps on a tiny DeepSeek-V3 left a non-zero e_score_correction_bias bit for bit unchanged (it is a buffer, not a parameter). Check: log per-expert counts during the fine-tune; set the flag, or implement the bias update.

Building a Qwen3-MoE from the default config

Qwen3MoeConfig() gives norm_topk_prob = [[f:hfc_norm|s]] while every released Qwen3-MoE config says true: a from-scratch model or a converted checkpoint without its config weights experts by raw softmax probabilities (summing to less than 1). Check: diff your config against the released one, field by field.

Reading transformers' balancing loss as the Switch loss

Balanced routing gives [[f:hf_bal|f2]], not 1, and two layers collapsed onto different experts score [[f:hf_two_diff|f2]] against [[f:hf_one|f2]] for one: it pools counts over layers (section 3). A dashboard alarm set at "aux loss above 1" fires on a perfectly balanced model with k = 2.

"Experts specialise by topic"

Mixtral's own analysis: "Surprisingly, we do not observe obvious patterns in the assignment of experts based on the topic" ({{Mixtral|n:3c65c17b0d0d81eba72af0ac91ddc6b3}}, section 5); assignments track syntax and token identity more than subject, and domain specialisation appears mostly with global-batch balancing (section 3). [[mis_special]]

Pricing an MoE on its total, or "8x7B is 56B"

Mixtral 8x7B is 46.7B because only the FFNs are copied; it computes like 12.9B. Memory is priced on the total, compute on the active (sections 1 and 8).

"Sigmoid routing picks different experts from softmax"

From the same logits both pick the same top k (both are increasing); they differ in gate weights, and once a selection bias or a group limit is added, softmax-plus-bias and sigmoid-plus-bias can pick differently because the bias is added on different scales.

Treating dropped tokens as an error that would show up

Nothing fails: a dropped assignment silently leaves that token with less (or no) FFN output in that layer, and the loss just gets worse (section 4). The only signal is the dropped fraction, if you log it.

Asking for more experts per token than exist

The tiny GPT with 4 experts and top_k = 6: [[f:hfc_topk_err|s]], from torch.topk inside the router. The same message appears when a converted checkpoint's num_experts_per_tok does not match its expert count.

Interview questions

Why does an MoE with 8 experts and top-2 have the FLOPs of a dense model, and what does it pay instead?
When each expert is half the dense FFN width, two of them cost one dense FFN; the router adds 2dE FLOPs per token (0.4% here). It pays in memory (all experts resident: 2.6 times the tiny GPT's parameters), communication once experts are sharded, balancing machinery, and skinny per-expert matrix multiplies.
Where does the router's gradient come from, and why does that cause collapse?
Only through the gate weights of the chosen experts (top-k has no gradient); unchosen experts get no signal (measured here: at most [[f:grad_lm_ratio|e]] of the chosen ones' gradient, floating-point rounding). A slightly favoured expert gets more updates, improves, and wins more: a rich-get-richer loop that balancing breaks.
Write the Switch balancing loss and say what it is at perfect balance and at collapse.
α E ∑ fiPi; f counts dispatch (no gradient), P is the mean router probability. Uniform: α. All tokens to expert 1 with P1 = 0.7 among 4 experts: 2.8α. In transformers' pooled version, uniform top-2 gives 2.
Auxiliary-loss-free balancing: what is updated, by what rule, and why does it not hurt quality?
A per-expert bias added to the scores for selection only; bi += γ sign(mean load − loadi) after each step (γ = 0.001 in V3). It never enters the output or the gradient, so it moves the decision boundary without a competing objective. DeepSeek still keeps a tiny sequence-wise loss (α = 0.0001).
What is a capacity factor, and why do modern training stacks not use one?
C = CF · n · k / E slots per expert; overflow is dropped and skips the FFN. Dropless grouped-GEMM kernels (MegaBlocks) compute ragged per-expert groups, so nothing is dropped or padded; static buffers survive where shapes must be static.
DeepSeek-V3: 671B total, 37B active. Rebuild both from the config in your head.
Expert 3 × 7,168 × 2,048 = 44M; 58 MoE layers × 257 experts = 656.6B; dense rest about 14.4B; total 671B. Active: 58 × 9 × 44M = 23B + 14.4B = 37.6B with the input embedding, 36.6B without (which rounds to the report's 37B).
Per token per MoE layer, how many bytes cross the network under expert parallelism?
k · d · bytes each way (less what lands locally): DeepSeek-V3 in BF16 8 × 7,168 × 2 = 112 KiB out and 112 KiB back per token per layer, forward; the backward repeats it. Group-limited routing caps how much of it crosses nodes.
At what batch size does a 256-expert, top-8 model stop decoding like its active size?
Expected distinct experts touched is E(1 − (1 − k/E)B): 8 at B = 1, about 163 at B = 32, nearly all 256 by B = 256. Past a few tens of sequences it reads almost all its weights per step, like a dense model of its total size, while each expert still sees only B · k / E tokens.
Design: you have 64 H100s (8 nodes of 8, NVLink inside, 400 Gb/s InfiniBand between) and a compute budget for a 7B-active model. Design the FFN and its parallelism.
Fine-grained MoE: for example 128 routed experts of width about d/4 with top 8 plus 1 shared, first 1 to 3 layers dense, sigmoid scores with bias balancing and a tiny sequence-wise loss, dropless kernels, router in float32 (and a z-loss if logits grow). Expert parallel 8-way inside each node (NVLink), data parallel (FSDP/ZeRO) across nodes for attention and dense parts, so the all-to-all stays on NVLink; if experts must span nodes, group-limit each token to 2 to 4 nodes. Measure per-expert load and dropped fraction from step 1, and check memory: total parameters, not active, set the shard sizes.
Design: serve a 1T-total, 32B-active MoE at low latency for batch 1 and cheaply at batch 512. What changes between the two?
Batch 1: few experts touched, decode reads about the active weights, latency is set by memory bandwidth and the all-to-all latency; use fewer, larger nodes and quantised experts (4 to 8 bits) so the model fits in as few GPUs as possible. Batch 512: nearly all experts touched every step; spread experts wide (EP over many GPUs) so each GPU's few experts get a useful slice of tokens, replicate hot experts (EPLB), disaggregate prefill from decode, and use grouped GEMM. The KV cache, not the experts, then limits the batch: that is an attention-design question.
