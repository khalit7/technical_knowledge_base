8. What an MoE costs to serve

Memory is priced on the total, compute on the active. Every expert must be resident, because the next token may pick any of them: DeepSeek-V3's 671B parameters are 1,342 GB in BF16, 671 GB in FP8 and about 336 GB at 4 bits (derived), while each token computes like a 37B dense model. Experts are where the bytes are, so experts are what gets quantised: gpt-oss was "post-trained with MXFP4 quantization of the MoE weights, making gpt-oss-120b run on a single 80GB GPU" (model card, vendor), and DeepSeek-V4-Pro's config sets expert_dtype to fp4.

Decode reads the experts that were hit. Decoding is limited by how many weight bytes are read per step, not by FLOPs. A dense model reads all its weights once per step whatever the batch. An MoE reads only the experts its batch touched: with B running sequences each picking k of E experts at random, about E · (1 − (1 − k/E)B) distinct experts per layer (derived, assuming uniform independent routing; real routing is skewed, which touches fewer). For DeepSeek-V3 (E = 256, k = 8) that is 8 experts at B = 1, about 163 at B = 32 and about 256 at B = 256: at batch 1 an MoE decodes like its active size, at large batch it reads its whole total. Meanwhile each touched expert serves only about B · k / E tokens (8 at B = 256), so its matrix multiplies are skinny and bandwidth-bound unless the batch is very large. The {{Dense vs MoE calculator|#t-calc}} draws both curves for any config; the {{Mixtral paper page|n:3c65c17b0d0d81eba72af0ac91ddc6b3}} animates one decode step of Mixtral against Llama 2 70B and 13B on a roofline.

Imbalance comes back at request time. Real traffic is skewed (one language, one code base, one prompt template), so some experts run hot and their GPUs set the tail latency. DeepSeek-V3's deployment answers with redundant copies of hot experts, chosen from live statistics "periodically (e.g., every 10 minutes)": 32 redundant experts in a prefill unit of 4 nodes and 32 GPUs; in decoding, a unit of 40 nodes and 320 GPUs where "each GPU hosts only one expert, and 64 GPUs are responsible for hosting redundant experts and shared experts" ({{V3 report|n:3c65c17b0d0d815fb8dac9ba1e35ab81}}, section 3.4, vendor). The placement algorithm is open as {{EPLB|https://github.com/deepseek-ai/EPLB}}. Serving MoE at that width is the subject of {{Distributed and disaggregated serving|n:3c65c17b0d0d8170bd7cdf47af0ec07b}}.

Attention is untouched. MoE shrinks FFN compute only; the KV cache and attention FLOPs are those of the attention design, which is why the models that pushed sparsity furthest also changed attention (MLA in DeepSeek, Kimi and Mistral Large 3; sparse or linear attention in DeepSeek-V3.2 and V4, GLM-5, MiniMax M3, Qwen3-Next and Kimi K3). See {{Attention variants|n:3fd5c17b0d0d8120859ecc2d0236e846}} and {{Long context|n:3fd5c17b0d0d81059ee1ce20c0326dc5}}.

How to check it. In a serving engine, log the router's top-k indices per layer over a window of real traffic and compare the busiest expert's count with the mean; measure decode step time against batch size: an MoE's curve rises faster than a dense model's of the same active size until every expert is hit, then flattens.

9. What real configs choose

Read verbatim from the config.json files the root's Architecture map saved (fetched 2026-10-18; release dates and published totals from its curated sources). "−" means the config has no such field; the router function for models whose config does not name it is read from the transformers code that runs them.

23 MoE models, December 2023 to July 2026

E: routed experts per MoE layer; k: routed experts per token; shared: always-on experts; width: one routed expert's hidden size (d: model width); MoE layers: of all layers; balancing: the config's topk_method (noaux_tc = DeepSeek's bias) or use_routing_bias; groups: n_group/topk_group; scale: routed_scaling_factor; C(E, k) = number of possible expert sets per token. Config fields can disagree with what training used: router_aux_loss_coef (0.001 in Qwen3, 0.02 in Mixtral, 0.9 in gpt-oss-120b) is the value transformers would use to fine-tune, not a stated pretraining value.
