Cache ladder: what one token stores, and what one decoded token reads

Eleven attention designs, each read from a real config.json, on one axis: bytes. For a context length you choose, each rung shows the cache one sequence holds, the bytes one new token must read from it, and the arithmetic done on what is read. The ratio of the last two decides whether a decode step waits on memory or on compute.

The same decode step on two rungs, at H100 speeds

One decoded token's attention, all layers, one sequence, on one H100 SXM (989 TFLOPS dense BF16, 3.35 TB/s HBM3; calculation, a roofline: the step takes the longer of bytes / bandwidth and FLOPs / peak). Weights, the feed-forward network and kernel overheads are left out: this isolates attention's share. Batching does not help attention here, because every sequence has its own cache.

What this tab does not count

Real deployments store some caches in FP8 or FP4 (DeepSeek-V4 keeps entries in FP8 with the 64 RoPE dimensions in BF16, per its report as summarised on the {{DeepSeek page|n:3c65c17b0d0d81a2ae7ec6796947a235}}); the bf16 convention here keeps every rung comparable. The DSA indexer keys are counted as bf16 numbers too (DeepSeek runs the indexer in FP8 or FP4). FLOPs for the Gated DeltaNet layers of Qwen3-Next are left at zero: their state update is a fixed cost per token, independent of context, owned by {{Beyond attention|n:3fd5c17b0d0d8142bc9ecac1fc366966}}. Paged allocation, fragmentation and batch sizing belong to {{Batching, KV cache and scheduling|n:3c65c17b0d0d819db53bd2c48909e5b2}}.
