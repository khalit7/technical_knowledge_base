10. Common mistakes, with the real numbers

Converting MHA to GQA by averaging heads, and shipping it
No error, and the model is broken: averaging the tiny MHA's 8 KV heads into 2 took held-out loss from 2.137 to 4.276 (section 2). Averaging is a starting point for uptraining (the GQA paper's 5%), not a conversion. measured
Folding WUK into the query when RoPE rotates the whole key
The algebra looks the same and nothing errors, but the score depends on the distance through the rotation: on the trained at_mla, folding with one matrix moves attention weights by up to 0.40 (section 3). MLA works only because its content path carries no position; the position goes through the separate RoPE key. measured
Reading num_key_value_heads to size an MLA cache
DeepSeek-V3's config says num_key_value_heads: 128; the cache is kv_lora_rank + qk_rope_head_dim = 576 numbers per layer, 68.6 KiB per token, not the 3.81 MiB that 128 heads of 128 keys and values would give (the root's Config calculator handles this; a hand calculation from the head count is 57x too big).
Expecting DSA to save memory
It adds memory: every token keeps its MLA entry and a 128-number indexer key (V3.2: 83.9 KiB per token against V3's 68.6, bf16). It saves reads and arithmetic past 2,048 tokens, and its indexer still reads a key for every token (section 5). calculation
Serving a full-attention model with a plain sliding cache
Evicting the first token removes the sink the model relies on: SmolLM2-135M with a 64-token window, loss 3.36 against 1.62 with the full cache, and 1.81 if position 0 is kept (the root's Inside lab). The tiny GPT has no sink, so it barely notices (the root's Attention lab); a real pretrained model does. measured
Off-by-one windows and which layers are global
In transformers 5.20.1 a window W keeps keys with kv_idx > q_idx - sliding_window: W keys including the query, not W previous tokens plus the query. Gemma 3's sliding_window_pattern: 6 makes layers 6, 12, ... global ((i + 1) % 6), not layers 1, 7, ...; gpt-oss starts with a local layer. Checking the mask with a probe sequence (one token per position, read the attention weights with eager attention) catches both.
The DSA indexer's RoPE layout
DeepSeek's V3.2-Exp model card added a note on 2025-11-17: the indexer's RoPE needs the non-interleaved layout while MLA's RoPE is interleaved, and the earlier demo code had them wrong (the root's Attention lab notes). Two RoPE conventions in one layer is a real trap when porting; the Positional Encodings child measured interleaved instead of split-half RoPE on the tiny GPT: held-out 1.961 to 3.606, no error.
Using SDPA and asking for attention weights to look for sinks
transformers 5.20.1 warns that sdpa "does not support output_attentions=True" and returns an empty tuple (the root's Inside lab); load the model with attn_implementation="eager", as this page's SmolLM2 probe does.

11. Interview questions, with short answers

Why does GQA lose so little quality relative to MHA?
Each head keeps its own query map, so heads still attend differently; what they share is the subspace keys and values live in, and trained MHA keys and values occupy far fewer directions than H · dh (the tiny MHA: 128 of 512 directions hold over 99% of the variance). The loss grows when the model has the data to use more directions: 7B on 1.33T tokens, MMLU 45.2 MHA against 41.2 GQA-8 (DeepSeek-V2 Table 8).
Derive MLA's absorbed form and say why RoPE needs a separate key.
q · WUK c = (WUKT q) · c, and WO WUV folds offline, so attention runs over the cached latent directly. With RoPE on the key the score is q · Rj−t WUK c, and the middle matrix depends on the distance, so it cannot be folded; MLA keeps the content path position-free and caches a small shared RoPE key (64 numbers in V3) beside the 512-number latent.
Is decode attention memory-bound or compute-bound, for GQA and for MLA?
GQA does 2 FLOPs per cached number per query head in its group, about H / Hkv FLOPs per byte in bf16 (4 for Llama 3.1 8B): far below an H100's ~295, so memory-bound at any batch, because each sequence has its own cache. Absorbed MLA with 128 heads on one 576-number entry does about 242 FLOPs per byte (the Cache ladder): near the balance point, so MLA can afford many heads.
A sliding window of 4,096 over 32 layers: what context can the model use?
The reach is 32 x 4,095, about 131K tokens (Mistral's "theoretical attention span"), but information must survive 32 hops of mixing; effective recall is far shorter, which is why later models keep some global layers (Gemma 3 5 : 1, gpt-oss 1 : 1) and Mistral's later models dropped the window. Memory is W per layer whatever the context.
What is an attention sink and how do gpt-oss and Qwen3-Next avoid needing one?
Softmax forces weights to sum to 1, so heads with nothing to read park weight on the first token, which grows a massive activation; evicting it breaks windowed serving. gpt-oss adds a learned logit per head (a column with no value) so real weights can sum to less than 1; Qwen3-Next multiplies each head's output by a sigmoid gate, so a head can output nearly nothing (Qiu et al.: first-token attention 46.7% to 4.8%).
DSA versus NSA in one sentence each.
DSA: a separate cheap indexer (ReLU scores, FP8) scores every token and MLA attends to the top 2,048; it stores more and reads less. NSA: three branches (compressed blocks, top-16 selected blocks chosen from the compressed scores, a 512 window) mixed by learned gates; selection by block for contiguous memory reads.
Design: a 70B-class dense model must serve 128K-token requests at batch 16 on one 8 x 80 GB node. Choose the attention.
Weights in bf16 take about 141 GB of 640. At Llama 3.1 70B's shape (80 layers, 128-dim heads), MHA with 64 KV heads needs 2.5 MiB per token, 5 TiB for the batch: impossible. GQA-8 needs 320 KiB per token, 40 GiB per request, 640 GiB for 16: still does not fit beside the weights. GQA-8 with an FP8 cache (320 GiB) fits; so does an MLA-style latent of 576 numbers (90 KiB per token over 80 layers, 180 GiB). For a new model, MLA or GQA with a 5 : 1 local : global interleave (most layers then hold only their window); for an existing GQA model, FP8 KV first, then sparse reads if decode speed at 128K matters. The {{Design drill|#t-drill}} tab does this arithmetic for seven such questions.
Design: you have a trained MHA model and need a 4x smaller cache next month. What do you do?
Average the KV heads into groups (GQA-2 for 4x) and uptrain on about 5% of the original tokens, as the GQA paper did, then check quality: section 2's tiny model went from 2.137 to 4.276 when averaged, back to 2.481 after 5% uptraining and 2.317 after 10%, while a GQA-2 trained from the start reached 2.160 (20 windows). Alternatives: FP8 or INT4 KV quantisation (no retraining, 2x to 4x), or an SVD-based conversion to an MLA-like latent, which keeps more of the model before uptraining (section 2's projection: +0.009 at 128 numbers) but needs MLA kernels to pay off.
