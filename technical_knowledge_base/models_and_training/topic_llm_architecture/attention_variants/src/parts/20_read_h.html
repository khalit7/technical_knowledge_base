Differential attention: subtract the noise (a variant that has not spread)

The problem it targets. A softmax over thousands of keys gives every irrelevant key a small positive weight, and together they can outweigh the few relevant ones: the DIFF Transformer paper calls this attention noise. How it works (Ye et al., Microsoft Research and Tsinghua, {{arXiv 2410.05258|https://arxiv.org/html/2410.05258}}): split each head's query and key into two halves, compute two attention maps, and subtract one from the other:

DiffAttn(X) = ( softmax(Q1K1T/√d) − λ · softmax(Q2K2T/√d) ) V
λ
learned per layer: exp(λq1 · λk1) − exp(λq2 · λk2) + λinit, with λinit = 0.8 − 0.6 exp(−0.3 (l − 1))
after
a per-head RMSNorm ("GroupNorm applies normalization to each head independently") times (1 − λinit)

Noise common to both maps cancels, like a differential amplifier; the weights can now be negative. authors' results: "Diff Transformer requires only about 65% of model size or training tokens" to match a Transformer (a 6.8B DIFF matches an 11B Transformer; 160B tokens match 251B); 3B models on 350B tokens average 56.2 against 55.4 zero-shot and 58.0 against 56.4 five-shot (Table 8); multi-needle retrieval at 4K with 6 needles 0.85 against 0.55 (Table 2); attention on the answer span 0.27 against 0.03, on noise 0.01 against 0.51 (Table 3); largest attention logit 38.8 against 318.0 (Table 5). The cost: two softmaxes per head over half-size queries and keys, the same cache per token as the MHA it replaces (keys of both halves are stored), and a kernel that FlashAttention does not provide in one call. Adoption: transformers 5.20.1 ships a DiffLlama implementation (models/diffllama), but none of the 2026 open-weight configs this topic reads uses it; the variant that spread is the much cheaper gate of section 6. Not run here: the paper's gains appear at billions of parameters and hundreds of billions of tokens, and the tiny GPT has no long-range noise to cancel (its attention is mostly local: the closed table in section 5).

Common mistakes, with the real numbers
Converting MHA to GQA by averaging heads, and shipping it
No error, and the model is broken: averaging the tiny MHA's 8 KV heads into 2 took held-out loss from 2.137 to 4.276 (section 2). Averaging is a starting point for uptraining (the GQA paper's 5%), not a conversion. measured
Folding WUK into the query when RoPE rotates the whole key
The algebra looks the same and nothing errors, but the score depends on the distance through the rotation: on the trained at_mla, folding with one matrix moves attention weights by up to 0.40 (section 3). MLA works only because its content path carries no position; the position goes through the separate RoPE key. measured
Mapping query heads to KV heads with repeat instead of repeat_interleave
GQA's query head h reads KV head h // (H / Hkv): heads 0 to 3 share KV head 0. Expanding the KV heads with repeat (0, 1, 0, 1, ...) instead of repeat_interleave (0, 0, 0, 0, 1, ...) runs without error and wires every head to the wrong keys: the trained GQA-2 went from 2.1025 to 2.9907 held-out (the root's Attention lab). Without the expansion, or enable_gqa=True, SDPA fails loudly instead: "The size of tensor a (8) must match the size of tensor b (2)". measured
Reading a field name as a cache design (Motif 3)
Motif 3 has kv_lora_rank 512 like DeepSeek, but its released modeling_motif.py caches the expanded keys (16 heads × 192) and values (16 × 128): 530 KiB per token, not the 59.6 KiB a latent cache would hold (found by the LLM Architecture Gallery child). Whether a model caches the latent is a property of its code, not its config.
"MLA is a kind of GQA"
GQA shares identical keys and values between heads. MLA shares a latent from which every head reads its own keys and values through its own projections; only in decode, after absorption, does it take the multi-query shape, and then over a 576-number entry with per-head projections either side.
"HCA is sparse attention"
HCA attends densely to all of its compressed entries; CSA is the one that also selects.
Reading num_key_value_heads to size an MLA cache
DeepSeek-V3's config says num_key_value_heads: 128; the cache is kv_lora_rank + qk_rope_head_dim = 576 numbers per layer, 68.6 KiB per token, not the 3.81 MiB that 128 heads of 128 keys and values would give (the root's Config calculator handles this; a hand calculation from the head count is 57x too big).
Expecting DSA to save memory
It adds memory: every token keeps its MLA entry and a 128-number indexer key (V3.2: 83.9 KiB per token against V3's 68.6, bf16). It saves reads and arithmetic past 2,048 tokens, and its indexer still reads a key for every token (section 5). calculation
Serving a full-attention model with a plain sliding cache
Evicting the first token removes the sink the model relies on: SmolLM2-135M with a 64-token window, loss 3.36 against 1.62 with the full cache, and 1.81 if position 0 is kept (the root's Inside lab; section 6). The tiny GPT has no sink, so it barely notices (the root's Attention lab); a real pretrained model does. measured
Off-by-one windows and which layers are global
In transformers 5.20.1 a window W keeps keys with kv_idx > q_idx - sliding_window: W keys including the query, not W previous tokens plus the query. Gemma 3's sliding_window_pattern: 6 makes layers 6, 12, ... global ((i + 1) % 6), not layers 1, 7, ...; gpt-oss starts with a local layer. Checking the mask with a probe sequence (one token per position, read the attention weights with eager attention) catches both.
The DSA indexer's RoPE layout
DeepSeek's V3.2-Exp model card added a note on 2025-11-17: the indexer's RoPE needs the non-interleaved layout while MLA's RoPE is interleaved, and the earlier demo code had them wrong (the root's Attention lab notes). Two RoPE conventions in one layer is a real trap when porting; the Positional Encodings child measured interleaved instead of split-half RoPE on the tiny GPT: held-out 1.961 to 3.606, no error.
Using SDPA and asking for attention weights to look for sinks
transformers 5.20.1 warns that sdpa "does not support output_attentions=True" and returns an empty tuple (the root's Inside lab); load the model with attn_implementation="eager", as this page's SmolLM2 probe does.

Seven questions of the kind asked in model design reviews and interviews. Each reveal does the arithmetic with this page's code (the same formulas as the root's Config calculator) or shows the measured or published result.

Sliding window or sparse attention for long context? A window caps memory and reads but forgets: anything older than the window must be relayed through layers, which models often fail to learn, so designs keep some global layers (Gemma 3 1 in 6, gpt-oss 1 in 2). Sparse attention keeps everything and reads a learned subset, so it can still retrieve one old token, but the cache is as large as before and the selector costs something at every step. Windows when memory is the limit, sparse attention when reads and long-range recall both matter, and often both together with GQA or MLA underneath.
