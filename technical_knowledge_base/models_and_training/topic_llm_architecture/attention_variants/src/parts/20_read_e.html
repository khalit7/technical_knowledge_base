5. Sparse attention: keep everything, read a few

The problem. Windows and interleaves bound what is kept by distance, and the long-range layers still read everything. Sparse attention bounds what is read by relevance instead: every entry stays in memory, and each query attends to the k entries most likely to matter. It only works if attention really is concentrated on a few keys, and if those keys can be found without computing full attention.

The premise, measured. In SmolLM2-135M on 1,024 tokens, a query's own top 16 keys (of at least 257) hold 75% to 94% of its attention in layers 13 to 30, while the last 64 keys plus position 0 hold only 46% to 76%: concentrated, and not on the most recent tokens. These are oracle top-k (chosen with the real weights); the {{Which keys are read|#t-keys}} tab shows the per-layer table and lets you select keys on the running sequence under each scheme. measured on Apple M1 Pro (CPU)

NSA: three branches and a learned mix

Native Sparse Attention (Yuan et al., DeepSeek, {{arXiv 2502.11089|https://arxiv.org/html/2502.11089}}) computes three attentions per query and adds them with gates (each in [0, 1], from an MLP and a sigmoid on the query token): a compressed branch that attends to one summary per block of l = 32 tokens (stride d = 16), a selected branch that attends in full to the n = 16 blocks of l′ = 64 tokens with the highest compressed-branch scores ("including the 1 initial block and 2 local blocks"), and a sliding window of w = 512. Blocks, not tokens, are selected, so the kernel reads contiguous memory; and the selection reuses the compressed branch's scores, so finding the blocks costs little. It is trained with the sparsity in place ("native"), not applied after training.

authors' results (section 4.1 and Tables 1, 2, 4): a 27B-total, 3B-active MoE (30 layers, 64 heads in GQA groups of 4) pretrained on 270B tokens at 8K (section 1 says 260B; the paper disagrees with itself), then extended to 32K. General benchmarks average 0.456 against full attention's 0.443; LongBench average 0.469 against 0.437; at 64K, up to 9.0x forward and 6.0x backward speedup in training, and 11.6x fewer memory accesses per decoded token (Table 4: 5,632 against 65,536 equivalent tokens, an expected speedup, a calculation). Not run here: it needs Triton kernels on CUDA and contexts long enough to have blocks to skip.

DSA: an indexer picks the top 2,048 tokens

DeepSeek Sparse Attention (V3.2-Exp, September 2025; V3.2 technical report) is simpler: a lightning indexer with a few small heads scores every cached token for the current query, It,s = Σj wt,j ReLU(qt,j · ks), and MLA's attention then runs over the top k = 2,048 tokens only (V3.2 config: index_n_heads 64, index_head_dim 128, index_topk 2048). ReLU instead of softmax and FP8 make the indexer cheap, but it still scores every token, so the whole layer stays O(L2) in its indexer while core attention becomes O(Lk). The indexer is trained first to imitate dense attention (a KL loss, about 2.1B tokens with the model frozen), then the whole model adapts to top-2,048 selection over about 944B tokens. Memory goes up, not down: every token keeps its MLA entry plus a 128-number indexer key (V3.2: 83.9 KiB per token against V3's 68.6, bf16). The full mechanism, training and prices are on the {{DeepSeek page|n:3c65c17b0d0d81a2ae7ec6796947a235}}; DeepSeek reported V3.2-Exp at parity with V3.1-Terminus DeepSeek. DSA has spread beyond DeepSeek: GLM-5's config (February 2026) has the same three fields (32 indexer heads of 128, top 2,048) on an MLA backbone.

DeepSeek-V4: compress what is stored as well

V4 (April 2026) changes what is stored: CSA layers merge every 4 tokens into one 512-number entry and apply DSA-style top-k to the merged entries (1,024 in V4-Pro), HCA layers merge every 128 tokens and read all of them, and both keep a 128-token uncompressed window and a learned sink logit per head. In V4-Pro's config 30 layers are CSA and 31 HCA (compress_ratios). In the bf16 convention that is 7.7 KiB per token of compressed entries plus 1.9 KiB of indexer keys: the {{Cache ladder|#t-ladder}} puts it beside V3 and V3.2. The DeepSeek page derives the reported "about 2% of a GQA-8 cache at 1M tokens"; this page does not repeat it.

When it matters: only past the point where k is a small share of the context: below 2,048 tokens DSA reads everything, as dense attention does. And the indexer's own reads grow with the context: at 131,072 tokens each layer's indexer reads a 128-number key for every token, 14x more numbers than the 2,048 entries of 576 that attention reads, so a decoded token reads about 24% of what V3 reads, not 2,048 / 131,072 = 1.6% (bf16 convention, calculation in the {{Cache ladder|#t-ladder}}; DeepSeek's FP8 indexer keys halve that part). How to check: index_topk and index_head_dim in the config; in transformers 5.20.1 the indexer's score is F.relu(scores) and selection is index_scores.topk(topk, dim=-1) (section 9).
