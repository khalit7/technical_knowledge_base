5. Sparse attention: keep everything, read a few

The problem. Windows bound what is kept by distance, and the global layers still read everything. Sparse attention bounds what is read by relevance: every entry stays in memory, and each query attends to the k entries most likely to matter. That works only if attention really is concentrated on a few keys, and if those keys can be found without computing full attention.

The premise, measured. In SmolLM2-135M on 1,024 tokens, a query's own top 16 keys (of at least 257) hold 75% to 94% of its attention in layers 13 to 30, while the last 64 keys plus position 0 hold only 46% to 76%: concentrated, and not on the most recent tokens, so NSA and DSA select by score, not distance. These are oracle top-k, an upper bound for any selector; {{Which keys are read|#t-keys}} shows any query and layer. measured on Apple M1 Pro (CPU)

NSA: three branches and a learned mix

Concrete. Native Sparse Attention (Yuan et al., DeepSeek-AI and Peking University, {{arXiv 2502.11089|https://arxiv.org/html/2502.11089}}) computes three attentions per query, "compressed coarse-grained tokens, selectively retained fine-grained tokens, and sliding windows for local contextual information", and adds them with gates (each in [0, 1], from an MLP and a sigmoid on the query token). Its settings (section 4.1): a summary per block of l = 32 tokens with stride d = 16; the n = 16 selected blocks of l′ = 64 tokens "including the 1 initial block and 2 local blocks"; a window of w = 512.

NSA reads a summary of everything, a few whole blocks, and the recent window, then mixes them

One query over 64 earlier tokens, blocks of 8 and 4 selected blocks illustrative. Selection reuses the compressed scores, so finding blocks is cheap, and whole blocks keep the kernel's reads contiguous.

It is trained with the sparsity in place ("native"), not applied after training, and the paper reports it above full attention on its own benchmarks and up to 11.6x fewer memory accesses per decoded token at 64K.

NSA's reported results (authors' runs; not run here)

authors' results (section 4.1, Tables 1, 2, 4): a 27B-total, 3B-active MoE (30 layers, hidden 2,560, 64 heads in GQA groups of 4) pretrained on 270B tokens at 8K (section 1 says 260B; the paper disagrees with itself), then extended to 32K with YaRN. General benchmarks average 0.456 against full attention's 0.443; LongBench 0.469 against 0.437; at 64K up to 9.0x forward and 6.0x backward speedup in training. Table 4 counts what one decode step must load: 2,048 equivalent tokens against 8,192 at 8K (4x), 2,560 at 16K (6.4x), 3,584 at 32K (9.1x), 5,632 against 65,536 at 64K (11.6x), an expected speedup, a calculation. Not run here: it needs Triton kernels on CUDA and contexts long enough to have blocks to skip.

DSA: a lightning indexer picks the top 2,048 tokens

Concrete. DeepSeek Sparse Attention (V3.2-Exp, shipped 29 September 2025; V3.2 technical report, {{arXiv 2512.02556|https://arxiv.org/abs/2512.02556}}) is simpler. A lightning indexer with a few small heads scores every cached token for the current query, and MLA's attention then runs over the top k only. V3.2's config: index_n_heads 64, index_head_dim 128, index_topk 2048. GLM-5 (February 2026) has the same three fields (32 indexer heads of 128, top 2,048) on an MLA backbone.

One decode step under DSA: score every entry cheaply, read only the top k

One square per cached token of the running sequence (226 tokens), k = 16 (V3.2: 2,048). Scores: SmolLM2-135M's real attention from the last token, layer 18, mean of 9 heads, standing in for the indexer: an oracle, the best any indexer could do. measured on Apple M1 Pro (CPU)

ReLU instead of a softmax, and FP8 (the indexer "can be implemented in FP8"), make each score cheap, but every token is scored: DSA "reduces the core attention complexity of the main model from O(L2) to O(Lk)", while "the lightning indexer still has a complexity of O(L2)" (DeepSeek). DSA sits on MLA's MQA mode because a selected entry must be shared by all heads for the kernel to be efficient. Memory goes up: 68.6 + 15.25 = 83.9 KiB per token in bf16 with the indexer keys. Unlike MLA, exact up to its low-rank bottleneck, DSA is an approximation, trained in: DeepSeek "deliberately aligned the training configurations of DeepSeek-V3.2-Exp with V3.1-Terminus" and reports "performance on par with V3.1-Terminus" ({{model card|https://huggingface.co/deepseek-ai/DeepSeek-V3.2-Exp}}, vendor).

How it was trained. V3.2 continued from V3.1-Terminus in two stages: a dense warm-up with the model frozen, the indexer alone fitted for 1,000 steps (2.1B tokens) to the main attention distribution (summed over heads, normalised) with a KL-divergence loss; then 943.7B tokens of sparse training in which the whole model adapts to top-2,048 selection while the indexer, detached from the main graph, keeps fitting attention over the selected set.

When it matters, how to check. Only past k: below 2,048 tokens DSA reads everything. And the indexer's read grows with the context: at 131,072 tokens it reads 14x more numbers than attention does, so a decoded token reads about 24% of what V3 reads, not 2,048 / 131,072 = 1.6% (bf16, calculation; FP8 indexer keys halve that part). Check index_topk and index_head_dim (transformers 5.20.1: F.relu(scores), then index_scores.topk(topk, dim=-1)), and judge quality with long-context retrieval rather than perplexity: a selector that misses the one needed token barely moves average loss ({{Long-context and multimodal benchmarks|n:3ef5c17b0d0d810bb4dfc98919c9be8a}}).

DeepSeek-V4: compress what is stored, then select

Concrete. V4 (April 2026, {{DeepSeek-V4 report|https://arxiv.org/pdf/2606.19348}}) changes what is stored, with two layer types interleaved. CSA (Compressed Sparse Attention) merges every m = 4 tokens into one 512-number entry, with overlapping blocks (each entry built from 2m = 8 tokens through two weight series), then applies DSA to the merged entries: an indexer of 64 heads of 128, in FP4, picks the top 1,024 (V4-Pro) or 512 (V4-Flash). HCA (Heavily Compressed Attention) merges every 128 tokens, without overlap, and reads all of them. In V4-Pro's config 30 layers are CSA and 31 HCA (compress_ratios, read 2026-10-18).

Both layer types keep a window of 128 uncompressed recent tokens (a query may attend only to completed blocks, so without it its own unfinished block, usually the most relevant, would be invisible) and use each entry as key and value for every query head, MLA's decode shape.

The rest of V4's attention layer: queries, output groups, partial RoPE, sink, layout, storage (report)

Shared-KV multi-query attention: each entry is key and value for every query head, 64 in Flash and 128 in Pro. Low-rank queries and a grouped output projection: queries come from a latent (1,024 in Flash, 1,536 in Pro), MLA's query trick; head outputs are projected in 8 or 16 groups to 1,024 each before the final projection, because c · nh is large. Partial RoPE and a sink: RoPE on the last 64 dimensions; because an entry is also a value, the output is rotated back by the query's position so it carries relative position; a learned sink logit per head (section 6). Layout: V4-Flash has 43 layers, the first two pure sliding window, the rest alternating CSA and HCA; V4-Pro 61, the first two HCA, the rest alternating. Storage: entries in FP8 except the 64 RoPE dimensions, which stay BF16, nearly halving the cache against pure BF16.

DeepSeek's figures: against BF16 GQA-8 with head dimension 128, the V4 cache is about 2% at 1M tokens; against V3.2 at 1M, V4-Pro needs 27% of the single-token FLOPs and 10% of the cache, V4-Flash 10% and 7%. The GQA-8 baseline is already 16 times smaller than MHA with 128 heads of the same size, so "2% of a vanilla transformer" overstates it. It is built for million-token contexts and long agent loops, at the price of lossy summaries and a more complex stack. In the bf16 convention of section 7, V4-Pro holds 7.7 KiB per token of entries plus 1.9 KiB of indexer keys.

Reproducing the reported 2% from the config (derived, two stated inputs)

The inputs: V4-Pro's split of its 59 alternating layers (30 CSA and 29 HCA, so 31 HCA with the first two, confirmed by compress_ratios) and the precision of the indexer keys (FP4, half a byte per dimension, an assumption).

  1. One stored entry: 448 FP8 dimensions at 1 byte plus 64 BF16 RoPE dimensions at 2 bytes = 576 bytes.
  2. A CSA layer stores one entry per 4 tokens, 576 / 4 = 144 bytes per token, plus one 128-dimension indexer key per 4 tokens, 128 × 0.5 / 4 = 16 bytes: 160 bytes per token.
  3. An HCA layer stores 576 / 128 = 4.5 bytes per token.
  4. V4-Pro: 30 × 160 + 31 × 4.5 = 4,939.5 bytes per token.
  5. GQA-8 in BF16 over the same 61 layers: 2 × 8 × 128 × 2 = 4,096 bytes per layer, 249,856 bytes per token. Ratio: 1.98%.

FP8 indexer keys give 2.17% and none 1.78%, so the reported "about 2%" is robust to that assumption. The 128-token windows add a fixed 128 × 576 × 61 = 4.5 MB per sequence. derived
