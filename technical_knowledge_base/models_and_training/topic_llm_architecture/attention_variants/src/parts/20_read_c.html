3. MLA: cache a latent, rebuild the heads

Concrete. DeepSeek-V3 has 128 heads of 128. MHA would cache 2 × 128 × 128 = 32,768 numbers per token per layer; multi-head latent attention (DeepSeek-V2, {{arXiv 2405.04434|https://arxiv.org/html/2405.04434}}) caches a 512-number latent plus a 64-number RoPE key, 576: about 57 times fewer, the size of GQA with 2.25 groups (576 = 2 × 2.25 × 128), yet every head keeps its own keys. Over 61 layers in bf16: 70,272 bytes (68.6 KiB) per token against 3,997,696 (3.81 MiB) for MHA and 249,856 (244 KiB) for GQA-8, which MLA beats by 3.6x.

  1. A token arrives. Token t enters one of V3's 61 attention layers as its hidden state ht: 7,168 numbers, 112 cells. Nothing of it is cached yet.
  2. Compress into the latent. The down-projection WDKV (green glass) maps ht to the latent cKVt of dc = 512 numbers. This one vector stands in for the keys and values of all 128 heads, which is where the saving comes from: 512 instead of 2 × 128 × 128.
  3. Add the decoupled RoPE key. Rotary position embeddings cannot pass through the absorbed product (it would differ for every pair of positions), so a separate key kRt = RoPE(WKRht) carries position: dRh = 64 numbers, one copy shared by all 128 heads.
  4. Write 576 numbers to the cache. Only [cKVt ; kRt], 512 + 64 = 576 numbers, is written to this layer's cache. That is the whole per-token cost of MLA: (dc + dRh) × l = 576 × 61 = 35,136 numbers, 70,272 bytes in BF16.
  5. Prefill: rebuild the heads (MHA mode). In training and prefill attention is compute-bound and many queries run at once, so each head's own slice of WUK and WUV (purple glass) rebuilds its 128-number key and value from the latent, and every key is extended by the shared kR. These 2 × 128 × 128 = 32,768 numbers per token (dashed) are computed, used and discarded: never cached.
  6. Decode: absorb, every head reads one entry (MQA mode). In decode WUKi moves onto the query side, (WUKi)⊤qt,i scored straight against cKVj, and WUVi folds into WO. All 128 query heads (orange) read the same 576-number entry of every earlier token, its first 512 serving as the value: nothing is expanded, so a decoded token reads 576 numbers per earlier token per layer, not 32,768.
  7. Compare with standard MHA. Per token per layer MLA caches 576 numbers where standard MHA with V3's 128 heads of 128 would cache 2 × 128 × 128 = 32,768 (dashed, to the same scale): about 57 times fewer, the size of GQA with only 2.25 groups (V2 paper). Over 61 layers that is 68.6 KiB per token against 3.81 MiB.
  1. A token arrives. Token t enters one attention layer as its hidden state ht: 7,168 numbers, 112 cells. Nothing of it is cached yet.
  2. Project the keys. WK projects ht into one 128-number key per head: 128 × 128 = 16,384 numbers, 256 cells.
  3. Project the values. WV does the same for the values: another 16,384 numbers. Every head's key and value are its own; nothing is shared between heads.
  4. Write 32,768 numbers to the cache. All of it is cached, because every later token attends to every earlier key and value: 2nhdh = 32,768 numbers in this layer, 1,998,848 over 61 layers, 3,997,696 bytes (3.81 MiB) per token in BF16.
  5. Decode: each head reads its own keys and values. Each decoded token's 128 query heads read their own keys and values for every earlier token: 32,768 numbers per earlier token per layer, all moved from memory for every decoded token. That read sets serving throughput, and it is the number MLA attacks.
  6. Compare with MLA. Standard MHA caches 32,768 numbers per token per layer; MLA at the same 128 heads of 128 caches 576 (the green row on top), about 57 times fewer. Over 61 layers: 3.81 MiB against 68.6 KiB per token.

the latent, dc numbers per token per layer (normalised by an RMSNorm): the only content that is cached (DeepSeek-V3 dc = 512; tiny GPT 64)
WDKV

As a factorisation. MHA's stacked [WK; WV] becomes WU WDKV, rank at most dc: the trained version of section 2's projection (64 directions cost the tiny MHA 0.093, 128 cost 0.009). GQA forces heads to share the same key; MLA gives every head its own key, built from a shared, smaller summary.

Absorption: why decode never rebuilds the keys. Matrix products associate, so the key up-projection moves onto the query side and the value up-projection into the output projection:

qh · khj = qh · (WUKh cj) = ((WUKh)T qh) · cj = q̃h · cj
output = Σh WOh WUVh ( Σj ahj cj )
q̃h
the query moved into latent space: dc numbers, once per step per head
WOh WUVh
folded once, offline (the V2 paper: absorb WUK into WQ and WUV into WO)

So the same layer runs in two modes. In training and prefill, where many queries run at once and attention is compute-bound, it rebuilds per-head keys and values and runs as ordinary MHA ("MHA mode"); the rebuilt keys are used and discarded, never cached. In decode it runs absorbed ("MQA mode"): all 128 heads read the same 576-number entry of every earlier token, whose first 512 numbers also serve as the value (V3.2 paper, appendix A). In decode MLA is multi-query attention over one wide entry, with per-head projections on either side that GQA does not have; that is why its quality holds where MQA's does not. DeepSeek's inference code uses this form (attn_impl "absorb" in inference/model.py).

Why RoPE needs a separate key. With RoPE on the whole key the score is qh · Rj−t WUKh cj: the matrix between query and latent depends on the distance, so no single matrix can be folded into the query, and every prefix key would have to be rebuilt at every step. MLA keeps the content path free of position and adds a decoupled RoPE key kRj = RoPEj(WKR xj) of dr = 64 numbers, shared by all heads and cached beside the latent, with a per-head RoPE query: score = q̃h · cj + qh,R · kRj, scaled by 1/√(dh + dr). MLA also compresses the queries through a second latent (d′c = 1,536 in V2 and V3), which saves activation memory in training and does not change the cache.

Evidence. DeepSeek-V2's Table 9 (DeepSeek): MLA beats MHA at two MoE scales, MMLU 50.0 against 48.7 with a 15.6K against 110.6K element cache, and 59.0 against 57.5 at about 250B parameters. Against its earlier dense DeepSeek 67B, V2 reported a 93.3% smaller cache and 5.76 times the maximum generation throughput, over 50K tokens per second on one 8-GPU H800 node, with the cache quantised to about 6 bits per element (vendor; the model changed too, so not MLA alone). On the tiny GPT MLA trails MHA by about 0.09 (closed block below).

Cost, when, how to check. MLA trades bytes for FLOPs: at DeepSeek-V3's shape and 32,768 tokens, absorbed decode reads 57x fewer bytes than an expanded cache but does about 3.7x the arithmetic (every head dots its query with the whole 576-number entry, not a 192-number key), landing near an H100's balance point (section 7). It pays for large models at long context and large batch. It needs its own kernels (FlashMLA; support in serving stacks lags GQA's), and the latent, shared by all heads, cannot be split by head under tensor parallelism. Check kv_lora_rank (dc) and qk_rope_head_dim (dr): the cache per token per layer is dc + dr, whatever num_key_value_heads says (DeepSeek-V3's says 128).

MLA beyond DeepSeek: Kimi K2, GLM-5, NoPE and gated MLA, QK-Clip (variants in released models)

Kimi K2 copies V3's MLA with 64 heads; GLM-5 moved from GQA to MLA (64 heads, 512 + 64). Kimi Linear and Kimi K3 run their MLA layers with no positional encoding (mla_use_nope): with no rotation there is nothing to decouple, the layers run as plain multi-query attention at inference, and K3 extrapolates to 1M tokens "without any positional-encoding modification" (K3 report, §3.4; the {{Kimi page|n:3c65c17b0d0d81f5abf5dbdbac821a12}}); K3 also gates their output ("Gated MLA", section 6). Kimi K2's QK-Clip shows the shared RoPE key's other consequence: it rescales each head's own query and key parts and must leave the shared rotary key alone.

Why MLA trails MHA on the tiny GPT: three runs (measured investigation)

The root's Attention lab measured MLA (dc 64, dr 16) at 2.255 held-out (seed 1: 2.248) against MHA's 2.160: about 0.09 worse, and 10% slower to train, while DeepSeek reports MLA beating MHA. Three hypotheses, each testable cheaply: the latent is too small; the shared RoPE key is too narrow (positions matter a lot to this model: NoPE costs 0.23, per the Positional Encodings child); or MLA simply trains slower at this budget.
