1. Why the cache is the cost

Concrete. Llama 3.1 8B keeps, for every past token, a key and a value for each of its 8 KV heads of 128 numbers in each of its 32 layers: 2 × 8 × 128 × 32 = 65,536 numbers, 128 KiB per token in bf16. A past token's keys and values never change in a causal decoder, so they are computed once and kept; generating one token reads all of it once. Each number read is used by the query heads that share it, one multiply-add for the score and one for the weighted value, so decode attention does about (query heads / KV heads) FLOPs per byte: 1 for MHA, 4 for Llama 3.1 8B. An H100 can do about 295 (989 TFLOPS dense bf16 over 3.35 TB/s), so the step waits on memory, and batching does not help because every sequence reads its own cache. Cache bytes are decode time.

Measured. One attention layer at Llama 3.1 8B's shape, batch 4, 32,768 cached tokens, fp16 on the M1 Pro's GPU (run for the root's former Attention lab, now carried by this page): MHA 17.49 ms, GQA-8 5.97 ms, absorbed MLA 3.43 ms, MQA 1.54 ms. The order is the order of bytes cached (8,192, 2,048, 576 and 256 numbers per token per layer), not of heads or FLOPs. measured on Apple M1 Pro (MPS)

Notation and the running example (the symbols used below; the tiny GPT and SmolLM2)

Notation. One layer, input xt, H query heads of size dh: qht = WQh xt, khj = WKh xj, vhj = WVh xj, weights ahtj = softmaxj(qht · khj / √dh) over j ≤ t, output Σj ahtj vhj per head, concatenated and multiplied by WO. RoPE rotates q and k by their positions so the score depends on j − t.

The running example. The topic's tiny GPT (6 layers, dmodel 256, 8 heads of 32, context 256, RoPE), trained on TinyStories for 1,500 steps of 8,192 tokens with the same seed and batches for every variant, so two runs differ only in their attention. The root's Attention lab trained MHA, GQA-4, GQA-2, MQA, MLA, a 64-token window and a 2 local : 1 global interleave; this page adds eight runs. Held-out loss differences under about 0.016 are inside the spread between two seeds (MHA 2.160 and 2.175 on 100 windows). Real-model behaviour comes from SmolLM2-135M (30 layers, 9 query heads and 3 KV heads of 64), inference only.

2. MQA and GQA: share keys and values across heads

Concrete. Llama 3.1 8B has 32 query heads but 8 KV heads: each key and value head is read by a group of 4 query heads, so a layer stores 2 × 8 × 128 = 2,048 numbers per token instead of MHA's 8,192. MQA (Shazeer 2019, {{arXiv 1911.02150|https://arxiv.org/abs/1911.02150}}) is the limit, one KV head for all; GQA (Ainslie et al. 2023, {{arXiv 2305.13245|https://arxiv.org/abs/2305.13245}}) is anything in between. The cache shrinks by H / Hkv; the queries keep full resolution.

Why sharing costs little. Head h's score is a bilinear form, qht · khj = xtT (WQh)T WKh xj. Under MQA every head uses the same WK: the heads still ask different questions (their query maps differ), but must find the answers in the same dh numbers per token; values likewise. So sharing is cheap exactly when the keys and values the heads need live in a subspace much smaller than H · dh. That is measurable:

A trained MHA cache uses far fewer directions than it stores

Keys and values together span 512 numbers per token per layer, yet the top 64 directions hold 94.2% to 99.6% of their variance and the top 128 hold 99.3% to 99.98%; keys alone, 32 directions (what MQA keeps) hold 84% to 94%. Variance is not loss: the closed block below tests it.

Trained from scratch, sharing is free here: GQA-4, GQA-2 and MQA land at 2.185, 2.182 and 2.177 (seed 1: 2.185) against MHA's 2.160 (seed 1: 2.175) on 100 windows, inside the seed spread.

At scale the gap appears: published, not run here

DeepSeek-V2's Appendix D.1 (Table 8, {{arXiv 2405.04434|https://arxiv.org/html/2405.04434}}; DeepSeek's own runs) trained 7B dense models on 1.33T tokens with parameters aligned by layer count: MMLU MHA 45.2, GQA-8 41.2, MQA 37.9; BBH 37.0 / 35.6 / 33.2. The GQA paper (Table 1, T5-XXL uptrained, Google): MHA 47.2 average at 1.51 s per sample, GQA-8 47.1 at 0.28 s, MQA 46.6 at 0.24 s; its authors converted MHA checkpoints with "5% of original pre-training compute" and report that "uptrained GQA achieves quality close to multi-head attention with comparable speed to MQA". Sharing also removes parameters from WK and WV, which comparisons at equal size give back to the FFN or depth. Both results fit the derivation: a model with enough data to use more key directions than the shared heads provide pays for sharing; the tiny GPT (12.3M tokens) is limited by data, not by key directions.

Cost, when, how to check. 4x fewer bytes made the decode step 2.9x faster above (17.49 to 5.97 ms). Under tensor parallelism MQA's single KV head is replicated on every GPU, so the per-GPU saving shrinks; GQA needs no new kernels and, with 4 to 16 KV heads, is the default of almost every 2024 to 2026 open model without MLA (Llama 3, Qwen3, Gemma 3, gpt-oss; MQA in PaLM and Gemma 3 270M). Check num_key_value_heads: per layer the cache is 2 · num_key_value_heads · head_dim numbers per token. The trap is in the kernel: an eager path that copies K and V up to all 32 heads first (transformers' repeat_kv) took 38.13 ms in the same measurement, slower than MHA. measured

Converting a trained MHA model: averaging, projection, uptraining (measured; the design angle when you own an MHA checkpoint)

The GQA paper converts a trained MHA checkpoint by mean-pooling the key and value projections of the heads in each group ("works better than selecting a single key and value head or randomly initializing"), then uptrains for 5% of the original steps (α = 0.05). Averaging keeps only the subspace the heads have in common; projecting onto the directions they actually use is the alternative. Predict: the tiny MHA's 8 key heads and 8 value heads are averaged into 2 groups (GQA-2), no training. Its held-out loss was 2.137. What is it now?

Measured: averaging the tiny MHA's 8 KV heads into 2 took held-out loss from 2.137 to 4.276; 5% uptraining brought it back to 2.481 and 10% to 2.317, while a GQA-2 trained from the start reached 2.160 (20 windows). Projecting jointly onto 64 directions cost 0.093 and onto 128 directions 0.009, with no training: an SVD-style conversion to an MLA-like latent keeps far more of the model, but needs MLA kernels to pay off. The no-retraining alternative for a 2x to 4x smaller cache is FP8 or INT4 KV quantisation ({{Long context|n:3fd5c17b0d0d81059ee1ce20c0326dc5}}). The GQA paper reports that GQA "already achieves reasonable performance after conversion while MQA requires uptraining to be useful" at T5-XXL scale; here it does not, so this small model's heads are more specialised. measured on Apple M1 Pro (CPU)
