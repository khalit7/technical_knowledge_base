Attention variants: MHA, MQA, GQA, MLA, sliding window, sparse attention and sinks

1. The problem, the notation, the running example

The problem. When a decoder generates token t, every layer computes a query qt and compares it with the keys of all earlier tokens; the earlier keys and values do not change, so they are stored: the KV cache. Decoding one token reads the whole cache once and does about two multiply-adds per number read. That ratio, about 1 FLOP per byte in bf16 for MHA, is far below what a GPU can do per byte of memory (an H100 does about 295), so decode attention waits on memory: cache bytes are decode time, and at long context or large batch they are also the memory that limits how many requests fit. The root's Attention lab (on Topic: llm-architecture) draws the cache and measures it (one MPS layer at Llama 3.1 8B's shape, 32K tokens, batch 4: MHA 17.49 ms, GQA-8 5.97 ms, MQA 1.54 ms); this page asks why each smaller cache works, and what each one gives up.

Notation. One layer, input xt (dmodel numbers, already normalised), H query heads of size dh. Head h computes qht = WQh xt, khj = WKh xj, vhj = WVh xj, weights ahtj = softmaxj(qht · khj / √dh) over j ≤ t, output oht = Σj ahtj vhj, then the heads are concatenated and multiplied by WO. With RoPE, q and k are rotated by their positions before the dot product, so the score depends on j − t.

The running example. The topic's tiny GPT (6 layers, dmodel 256, 8 heads of 32, context 256, RoPE) trained on TinyStories for 1,500 steps of 8,192 tokens, with the same seed and batches for every variant, so two runs differ only in their attention. The root's Attention lab trained MHA, GQA-4, GQA-2, MQA, MLA, a 64-token window and a 2 local : 1 global interleave; this page reuses those checkpoints and adds eight runs (MLA with a bigger latent and a wider RoPE key, a learned sink, an output gate, windows of 16, 32 and 128, and a 16-token interleave). Held-out loss is the mean next-token cross-entropy on fixed validation windows; differences under about 0.016 are inside the spread between two seeds of the same model (MHA 2.160 and 2.175 on 100 windows). Real-model behaviour comes from SmolLM2-135M (30 layers, 9 query heads and 3 KV heads of 64), inference only.

2. Sharing keys and values: why MQA and GQA cost so little

The idea. MQA (Shazeer 2019, arXiv 1911.02150) keeps H query heads but only one key head and one value head; GQA (Ainslie et al. 2023, arXiv 2305.13245) keeps Hkv of each, every one shared by a group of H / Hkv query heads. The cache shrinks by H / Hkv. The question is why the model barely notices.

The derivation. Write head h's score as a bilinear form of the two tokens: qht · khj = xtT (WQh)T WKh xj. In MHA each head owns both factors. In MQA every head uses the same WK, so head h's form is (WQh)T WK: the heads still ask different questions (their query maps differ, so their attention patterns differ), but they must find the answers in the same dh numbers per token. Values work the same way: head h contributes WOh WV Σj ahtj xj, so every head mixes the same value vectors with its own weights and its own output map. Sharing therefore costs little exactly when the keys and values the heads need live in a subspace much smaller than H · dh. That is measurable.

Projection is not pooling. The GQA paper converts a trained MHA checkpoint by averaging the key and value projections of the heads in each group, then trains for 5% of the original steps ("uptraining"). Averaging is a crude projection: it keeps only the subspace the heads have in common. Both conversions, with no training at all, on the same checkpoint and the same 20 held-out windows:

Trained from scratch, sharing is free here. Trained with the same budget, the lab's GQA-4, GQA-2 and MQA land at 2.185, 2.182 and 2.177 (seed 1: 2.185) against MHA's 2.160 (seed 1: 2.175) on 100 windows: inside the seed spread (root Attention lab). A model that is trained with shared heads from the start learns query maps that ask their questions of one shared key space; the rank measurement above says 64 to 128 directions are enough for this model, and MQA gives it 32 for keys and 32 for values in every layer.

At scale the gap appears: published, not run here

DeepSeek-V2's Appendix D.1 (Table 8, arXiv 2405.04434; DeepSeek's own runs) trained 7B dense models on 1.33T tokens with parameters aligned by layer count: MMLU MHA 45.2, GQA-8 41.2, MQA 37.9; BBH 37.0 / 35.6 / 33.2. The GQA paper (Table 1, T5-XXL uptrained, Google): MHA 47.2 average at 1.51 s per sample, GQA-8 47.1 at 0.28 s, MQA 46.6 at 0.24 s. Both are consistent with the derivation: a model with enough data to use more key directions than the shared heads provide pays for sharing; the tiny GPT, which saw 12.3M tokens, is limited by data, not by key directions, so it does not. Not run here: a 7B model on 1.33T tokens.

The cost. GQA-8 on Llama 3.1 8B's shape stores 4x less than MHA and decodes about 2.9x faster in the lab's one-layer MPS benchmark (17.49 to 5.97 ms at 32K tokens, batch 4): close to the 4x in bytes, because decode is memory-bound. It also has fewer parameters (WK and WV shrink by 4x), which papers usually give back to the FFN or the depth when they compare at equal size. When it matters: always at serving; GQA with 4 to 16 KV heads is the default of almost every 2024 to 2026 open model without MLA (the root's Architecture map). How to check: num_key_value_heads in the config; cache per token = 2 · layers · num_key_value_heads · head_dim · bytes.

3. MLA: a low-rank cache, the absorbed form, and the decoupled RoPE key

The idea. Section 2 found that a trained MHA's keys and values live in far fewer directions than H · dh. Multi-head latent attention (DeepSeek-V2, arXiv 2405.04434) builds that into the layer: each token stores one short latent vector, and every head's key and value are linear functions of it. The step-by-step animation of one token through MLA (compress, add the RoPE key, cache 576 numbers, rebuild heads in prefill, absorb in decode) is on the DeepSeek page; this section derives it and checks it numerically.

As a factorisation. MHA's stacked key and value projection [WK; WV] is a (2 H dh) by dmodel matrix. MLA writes it as WU WDKV with an inner dimension dc, so its rank is at most dc: the trained version of the projection in section 2, where projecting the tiny MHA's keys and values jointly onto 64 directions cost 0.093 in loss and 128 directions 0.009. The difference from GQA: GQA forces heads to share the same key; MLA lets every head have its own key, built from a shared, smaller summary.

The absorbed form. Rebuilding every head's key from every cached latent at each decode step would undo the saving (it is a matrix multiply over the whole cache). It is unnecessary, because matrix products associate. For head h:

qh · khj = qh · (WUKh cj) = ((WUKh)T qh) · cj = q̃h · cj
output = Σh WOh WUVh ( Σj ahj cj )
q̃h
the query moved into latent space: dc numbers, computed once per step per head
WOh WUVh
folded once, offline: dmodel by dc per head

So every head attends directly over the cached latents, like MQA with one dc-dimensional key that is also the value: all H heads read the same entry. DeepSeek's own inference code uses this form for decode (attn_impl "absorb", inference/model.py, per the root's Config calculator notes).

Why RoPE breaks it, and the decoupled key. With RoPE the key is Rj WUKh cj and the query Rt qh, so the score is qh · Rj−t WUKh cj: the matrix between query and latent depends on the distance, and no single matrix can be folded into the query. MLA therefore keeps the content path free of position and adds a small separate decoupled RoPE key kRj = RoPEj(WKR xj) of dr numbers, shared by all heads and cached beside the latent, with a matching per-head RoPE query: score = q̃h · cj + qh,R · kRj. DeepSeek-V3: dc 512, dr 64, so 576 numbers per token per layer, 68.6 KiB per token over 61 layers in bf16.

Why MLA loses here: an investigation

The root's Attention lab measured MLA (dc 64, dr 16) at 2.255 held-out (seed 1: 2.248) against MHA's 2.160: about 0.09 worse, and 10% slower to train, while DeepSeek-V2's Table 9 (DeepSeek) reports MLA beating MHA at two MoE scales (MMLU 50.0 against 48.7 with a 15.6K against 110.6K element cache; 59.0 against 57.5 at about 250B parameters). Three hypotheses, each testable cheaply: the latent is too small; the shared RoPE key is too narrow (positions matter a lot to this model: NoPE costs 0.23, per the Positional Encodings child); or MLA simply trains slower at this budget. The cost. MLA trades bytes for FLOPs: its decode reads 57x fewer bytes than the expanded cache at DeepSeek-V3's shape but does about 3.7x the arithmetic, which lands near an H100's balance point instead of far below it. Prefill (many queries at once) usually uses the naive form, because there the up-projection is amortised over all queries. MLA also needs its own kernels (FlashMLA) and complicates tensor parallelism, since the latent is shared by all heads and cannot be split by head. When it matters: large models at long context and large batch, where the cache dominates memory. How to check: kv_lora_rank (dc) and qk_rope_head_dim (dr) in the config; cache per token per layer = dc + dr numbers, whatever num_key_value_heads says (DeepSeek-V3's config says 128).

4. Sliding windows and local : global interleaves

The idea. A sliding window of W lets each query attend only to the last W tokens (itself included). The cache becomes a ring buffer of W entries per layer: token t overwrites slot t mod W (Mistral 7B's "rolling buffer cache", which its paper says "reduces the cache memory usage by 8x" at 32K with W = 4,096, arXiv 2310.06825). Memory per sequence stops growing at W, and so does the decode read. This page treats the window as a cache design; what it does to long-context quality, and how local and global layers trade memory against recall at 128K, is on Long context.

Reach grows with depth. Layer 2 reads layer 1's outputs, which each mixed W tokens, so after L local layers the last token can be influenced by the previous L · (W − 1) tokens: Mistral's 32 layers and W 4,096 give the "theoretical attention span of approximately 131K tokens" its paper states. Theoretical, because the information has to survive many hops of mixing; the Which keys are read tab animates the reach layer by layer for an all-local stack and a 2 : 1 interleave.

Interleaves. Most models that use windows now keep some full-attention (global) layers so that any token can reach any other in one hop: Gemma 2 alternates 1 : 1 with W 4,096 (context 8,192), Gemma 3 uses "5 local layers for every global layer" with W 1,024, Gemma 4 keeps 5 : 1 with W 1,024 (50 and 10 layers in the 31B config), gpt-oss alternates 1 : 1 with a "bandwidth" of only 128 tokens. Gemma 3's report measured the trade (Google, section 5.2): ratio and window changes have "minimal impact on perplexity", and the cache overhead at 32K falls from 60% of model memory with global-only attention to under 15% with 1 : 3 and W 1,024 (figures and the ratio wording as the Long context child quotes them).

Measured: how small can the window be?

measured on Apple M1 Pro (MPS training, CPU evaluation): the tiny GPT with RoPE, trained with every layer local at W = 16, 32, 64 (the lab's run) and 128, against full attention (W = 256, the training length), plus two interleaves (layers 3 and 6 global); and the full-attention model served with a window it was never trained with. Held-out loss on the lab's 192 fixed validation windows, CPU, by position.

Predict: the tiny GPT trained with every layer limited to a 16-token window, then the same with layers 3 and 6 made global (2 local : 1 global). How much of the gap to full attention does the interleave close?

The cost. A local layer forgets everything older than W unless another layer carried it forward; with all layers local, recall of a fact from far back depends on many hops. Interleaving brings back one full cache per global layer, so the memory saving is set by the share of global layers (5 : 1 keeps about a sixth of the full cache at long context). Kernels must handle the window (FlashAttention has a window_size argument) and the cache must be a ring buffer or a paged cache that frees old blocks. When it matters: at contexts several times W, where the full layers' cache dominates. How to check: sliding_window and layer_types (or Gemma 3's sliding_window_pattern, where every 6th layer is global) in the config; in transformers 5.20.1 a window keeps the keys with kv_idx > q_idx - sliding_window, W keys including the query itself (section 9).

5. Sparse attention: keep everything, read a few

The problem. Windows and interleaves bound what is kept by distance, and the long-range layers still read everything. Sparse attention bounds what is read by relevance instead: every entry stays in memory, and each query attends to the k entries most likely to matter. It only works if attention really is concentrated on a few keys, and if those keys can be found without computing full attention.

The premise, measured. In SmolLM2-135M on 1,024 tokens, a query's own top 16 keys (of at least 257) hold 75% to 94% of its attention in layers 13 to 30, while the last 64 keys plus position 0 hold only 46% to 76%: concentrated, and not on the most recent tokens. These are oracle top-k (chosen with the real weights); the Which keys are read tab shows the per-layer table and lets you select keys on the running sequence under each scheme. measured on Apple M1 Pro (CPU)

NSA: three branches and a learned mix

Native Sparse Attention (Yuan et al., DeepSeek, arXiv 2502.11089) computes three attentions per query and adds them with gates (each in [0, 1], from an MLP and a sigmoid on the query token): a compressed branch that attends to one summary per block of l = 32 tokens (stride d = 16), a selected branch that attends in full to the n = 16 blocks of l′ = 64 tokens with the highest compressed-branch scores ("including the 1 initial block and 2 local blocks"), and a sliding window of w = 512. Blocks, not tokens, are selected, so the kernel reads contiguous memory; and the selection reuses the compressed branch's scores, so finding the blocks costs little. It is trained with the sparsity in place ("native"), not applied after training.

authors' results (section 4.1 and Tables 1, 2, 4): a 27B-total, 3B-active MoE (30 layers, 64 heads in GQA groups of 4) pretrained on 270B tokens at 8K (section 1 says 260B; the paper disagrees with itself), then extended to 32K. General benchmarks average 0.456 against full attention's 0.443; LongBench average 0.469 against 0.437; at 64K, up to 9.0x forward and 6.0x backward speedup in training, and 11.6x fewer memory accesses per decoded token (Table 4: 5,632 against 65,536 equivalent tokens, an expected speedup, a calculation). Not run here: it needs Triton kernels on CUDA and contexts long enough to have blocks to skip.

DSA: an indexer picks the top 2,048 tokens

DeepSeek Sparse Attention (V3.2-Exp, September 2025; V3.2 technical report) is simpler: a lightning indexer with a few small heads scores every cached token for the current query, It,s = Σj wt,j ReLU(qt,j · ks), and MLA's attention then runs over the top k = 2,048 tokens only (V3.2 config: index_n_heads 64, index_head_dim 128, index_topk 2048). ReLU instead of softmax and FP8 make the indexer cheap, but it still scores every token, so the whole layer stays O(L2) in its indexer while core attention becomes O(Lk). The indexer is trained first to imitate dense attention (a KL loss, about 2.1B tokens with the model frozen), then the whole model adapts to top-2,048 selection over about 944B tokens. Memory goes up, not down: every token keeps its MLA entry plus a 128-number indexer key (V3.2: 83.9 KiB per token against V3's 68.6, bf16). The full mechanism, training and prices are on the DeepSeek page; DeepSeek reported V3.2-Exp at parity with V3.1-Terminus DeepSeek. DSA has spread beyond DeepSeek: GLM-5's config (February 2026) has the same three fields (32 indexer heads of 128, top 2,048) on an MLA backbone.

DeepSeek-V4: compress what is stored as well

V4 (April 2026) changes what is stored: CSA layers merge every 4 tokens into one 512-number entry and apply DSA-style top-k to the merged entries (1,024 in V4-Pro), HCA layers merge every 128 tokens and read all of them, and both keep a 128-token uncompressed window and a learned sink logit per head. In V4-Pro's config 30 layers are CSA and 31 HCA (compress_ratios). In the bf16 convention that is 7.7 KiB per token of compressed entries plus 1.9 KiB of indexer keys: the Cache ladder puts it beside V3 and V3.2. The DeepSeek page derives the reported "about 2% of a GQA-8 cache at 1M tokens"; this page does not repeat it.

6. Attention sinks, learned sinks and output gates

The problem. Softmax weights must sum to 1. A head that has nothing useful to read for this token (a "previous-name" head on a token with no name nearby) still has to put its weight somewhere. Trained LLMs learn to park it on a token whose value contributes little, nearly always the first one: an attention sink (Xiao et al. 2023, StreamingLLM, arXiv 2309.17453). The root's Inside lab found SmolLM2-135M's sink switching on at layer 12 (weight on token 0 at most 0.085 before, 0.31 to 0.74 after), together with a massive activation (dimension 507 of token 0's residual reaching 20,155 against a median 1.56). The sink matters to the cache: a sliding window that evicts token 0 breaks the model (SmolLM2, window 64: loss 3.36 against 1.62 full; keeping token 0 as well: 1.81), which is why StreamingLLM keeps the first few tokens beside the window.

Three fixes that remove the need for a real token.

  • A learned sink logit per head: an extra score column with no value, so a head can send weight "nowhere" and the real weights sum to less than 1. gpt-oss: "Each attention head has a learned bias in the denominator of the softmax" (model card, arXiv 2508.10925); DeepSeek-V4 uses one too. StreamingLLM's own pretraining test added a learned sink token to a 160M model: perplexity with a window of 1,023 plus one kept token 18.01, against 18.49 for the vanilla model, and the vanilla model with no kept token at all 27.87 (Table 10).
  • An output gate: multiply each head's attention output by a sigmoid of the token's own input, elementwise, before the output projection. A head with nothing to say closes its gate instead of finding a sink. Qiu et al. (Qwen team, arXiv 2505.06708) compared gate positions and forms on a 15B MoE and a 1.7B dense model with up to 3.5T tokens; the gate after attention, elementwise, was best (Table 1, 15B MoE: average perplexity 6.026 to 5.761, MMLU 58.79 to 60.82); the share of attention on the first token fell from 46.7% to 4.8% and the largest hidden activation from 1,053 to 94 (Table 4); the mean gate value was 0.116 (mostly closed); and a 48-layer dense model that diverged at a learning rate of 8e-3 trained with the gate (authors' runs). Qwen3-Next and Qwen3.5 ship it (attn_output_gate: true).
  • Softmax with an extra 1 in the denominator: Evan Miller's "Attention Is Off By One" (2023-07-24), exp(xi) / (1 + Σj exp(xj)), is a sink logit fixed at 0; a learned logit generalises it.

Measured: a sink ablation on the tiny GPT

measured on Apple M1 Pro (MPS training, CPU evaluation): three tiny GPTs with RoPE, same seed and batches: plain MHA (the lab's at_mha), MHA with a learned sink logit per head (the topic's sink preset, gpt-oss style), and MHA with an elementwise sigmoid output gate (added by this page's src/runs/av_model.py without editing the shared model, Qwen3-Next style). One head, before and after its sink: where the weight goes

The cost. A sink logit is H parameters per layer and one more column in the softmax; FlashAttention-style kernels need it passed in (transformers 5.20.1 concatenates it in the eager path, section 9). The gate is a dmodel by H · dh matrix per layer (Qwen3-Next fuses it into the query projection, doubling its width), about 7% more parameters for the tiny GPT. When it matters: serving with windows or evicted caches (a model with a learned sink or a gate does not depend on keeping token 0), quantisation (massive activations are what break low-bit formats), and training stability at high learning rates. How to check: sinks in gpt-oss's weights, attn_output_gate in Qwen's configs; in a model without either, measure the weight on token 0 by layer with eager attention (SDPA returns no weights), as the root's Inside lab does.

7. Differential attention: subtract the noise

The problem it targets. A softmax over thousands of keys gives every irrelevant key a small positive weight, and together they can outweigh the few relevant ones: the DIFF Transformer paper calls this attention noise. How it works (Ye et al., Microsoft Research and Tsinghua, arXiv 2410.05258): split each head's query and key into two halves, compute two attention maps, and subtract one from the other:

DiffAttn(X) = ( softmax(Q1K1T/√d) − λ · softmax(Q2K2T/√d) ) V
λ
learned per layer: exp(λq1 · λk1) − exp(λq2 · λk2) + λinit, with λinit = 0.8 − 0.6 exp(−0.3 (l − 1))
after
a per-head RMSNorm ("GroupNorm applies normalization to each head independently") times (1 − λinit)

Noise common to both maps cancels, like a differential amplifier; the weights can now be negative. authors' results: "Diff Transformer requires only about 65% of model size or training tokens" to match a Transformer (a 6.8B DIFF matches an 11B Transformer; 160B tokens match 251B); 3B models on 350B tokens average 56.2 against 55.4 zero-shot and 58.0 against 56.4 five-shot (Table 8); multi-needle retrieval at 4K with 6 needles 0.85 against 0.55 (Table 2); attention on the answer span 0.27 against 0.03, on noise 0.01 against 0.51 (Table 3); largest attention logit 38.8 against 318.0 (Table 5). The cost: two softmaxes per head over half-size queries and keys, the same cache per token as the MHA it replaces (keys of both halves are stored), and a kernel that FlashAttention does not provide in one call. Adoption: transformers 5.20.1 ships a DiffLlama implementation (models/diffllama), but none of the 2026 open-weight configs this topic reads uses it; the variant that spread is the much cheaper gate of section 6. Not run here: the paper's gains appear at billions of parameters and hundreds of billions of tokens, and the tiny GPT has no long-range noise to cancel (its attention is mostly local, section 5).

10. Common mistakes, with the real numbers

Converting MHA to GQA by averaging heads, and shipping it
No error, and the model is broken: averaging the tiny MHA's 8 KV heads into 2 took held-out loss from 2.137 to 4.276 (section 2). Averaging is a starting point for uptraining (the GQA paper's 5%), not a conversion. measured
Folding WUK into the query when RoPE rotates the whole key
The algebra looks the same and nothing errors, but the score depends on the distance through the rotation: on the trained at_mla, folding with one matrix moves attention weights by up to 0.40 (section 3). MLA works only because its content path carries no position; the position goes through the separate RoPE key. measured
Reading num_key_value_heads to size an MLA cache
DeepSeek-V3's config says num_key_value_heads: 128; the cache is kv_lora_rank + qk_rope_head_dim = 576 numbers per layer, 68.6 KiB per token, not the 3.81 MiB that 128 heads of 128 keys and values would give (the root's Config calculator handles this; a hand calculation from the head count is 57x too big).
Expecting DSA to save memory
It adds memory: every token keeps its MLA entry and a 128-number indexer key (V3.2: 83.9 KiB per token against V3's 68.6, bf16). It saves reads and arithmetic past 2,048 tokens, and its indexer still reads a key for every token (section 5). calculation
Serving a full-attention model with a plain sliding cache
Evicting the first token removes the sink the model relies on: SmolLM2-135M with a 64-token window, loss 3.36 against 1.62 with the full cache, and 1.81 if position 0 is kept (the root's Inside lab). The tiny GPT has no sink, so it barely notices (the root's Attention lab); a real pretrained model does. measured
Off-by-one windows and which layers are global
In transformers 5.20.1 a window W keeps keys with kv_idx > q_idx - sliding_window: W keys including the query, not W previous tokens plus the query. Gemma 3's sliding_window_pattern: 6 makes layers 6, 12, ... global ((i + 1) % 6), not layers 1, 7, ...; gpt-oss starts with a local layer. Checking the mask with a probe sequence (one token per position, read the attention weights with eager attention) catches both.
The DSA indexer's RoPE layout
DeepSeek's V3.2-Exp model card added a note on 2025-11-17: the indexer's RoPE needs the non-interleaved layout while MLA's RoPE is interleaved, and the earlier demo code had them wrong (the root's Attention lab notes). Two RoPE conventions in one layer is a real trap when porting; the Positional Encodings child measured interleaved instead of split-half RoPE on the tiny GPT: held-out 1.961 to 3.606, no error.
Using SDPA and asking for attention weights to look for sinks
transformers 5.20.1 warns that sdpa "does not support output_attentions=True" and returns an empty tuple (the root's Inside lab); load the model with attn_implementation="eager", as this page's SmolLM2 probe does.

11. Interview questions, with short answers

Why does GQA lose so little quality relative to MHA?
Each head keeps its own query map, so heads still attend differently; what they share is the subspace keys and values live in, and trained MHA keys and values occupy far fewer directions than H · dh (the tiny MHA: 128 of 512 directions hold over 99% of the variance). The loss grows when the model has the data to use more directions: 7B on 1.33T tokens, MMLU 45.2 MHA against 41.2 GQA-8 (DeepSeek-V2 Table 8).
Derive MLA's absorbed form and say why RoPE needs a separate key.
q · WUK c = (WUKT q) · c, and WO WUV folds offline, so attention runs over the cached latent directly. With RoPE on the key the score is q · Rj−t WUK c, and the middle matrix depends on the distance, so it cannot be folded; MLA keeps the content path position-free and caches a small shared RoPE key (64 numbers in V3) beside the 512-number latent.
Is decode attention memory-bound or compute-bound, for GQA and for MLA?
GQA does 2 FLOPs per cached number per query head in its group, about H / Hkv FLOPs per byte in bf16 (4 for Llama 3.1 8B): far below an H100's ~295, so memory-bound at any batch, because each sequence has its own cache. Absorbed MLA with 128 heads on one 576-number entry does about 242 FLOPs per byte (the Cache ladder): near the balance point, so MLA can afford many heads.
A sliding window of 4,096 over 32 layers: what context can the model use?
The reach is 32 x 4,095, about 131K tokens (Mistral's "theoretical attention span"), but information must survive 32 hops of mixing; effective recall is far shorter, which is why later models keep some global layers (Gemma 3 5 : 1, gpt-oss 1 : 1) and Mistral's later models dropped the window. Memory is W per layer whatever the context.
What is an attention sink and how do gpt-oss and Qwen3-Next avoid needing one?
Softmax forces weights to sum to 1, so heads with nothing to read park weight on the first token, which grows a massive activation; evicting it breaks windowed serving. gpt-oss adds a learned logit per head (a column with no value) so real weights can sum to less than 1; Qwen3-Next multiplies each head's output by a sigmoid gate, so a head can output nearly nothing (Qiu et al.: first-token attention 46.7% to 4.8%).
DSA versus NSA in one sentence each.
DSA: a separate cheap indexer (ReLU scores, FP8) scores every token and MLA attends to the top 2,048; it stores more and reads less. NSA: three branches (compressed blocks, top-16 selected blocks chosen from the compressed scores, a 512 window) mixed by learned gates; selection by block for contiguous memory reads.
Design: a 70B-class dense model must serve 128K-token requests at batch 16 on one 8 x 80 GB node. Choose the attention.
Weights in bf16 take about 141 GB of 640. At Llama 3.1 70B's shape (80 layers, 128-dim heads), MHA with 64 KV heads needs 2.5 MiB per token, 5 TiB for the batch: impossible. GQA-8 needs 320 KiB per token, 40 GiB per request, 640 GiB for 16: still does not fit beside the weights. GQA-8 with an FP8 cache (320 GiB) fits; so does an MLA-style latent of 576 numbers (90 KiB per token over 80 layers, 180 GiB). For a new model, MLA or GQA with a 5 : 1 local : global interleave (most layers then hold only their window); for an existing GQA model, FP8 KV first, then sparse reads if decode speed at 128K matters. The Design drill tab does this arithmetic for seven such questions.
Design: you have a trained MHA model and need a 4x smaller cache next month. What do you do?
Average the KV heads into groups (GQA-2 for 4x) and uptrain on about 5% of the original tokens, as the GQA paper did, then check quality: section 2's tiny model went from 2.137 to 4.276 when averaged, back to 2.481 after 5% uptraining and 2.317 after 10%, while a GQA-2 trained from the start reached 2.160 (20 windows). Alternatives: FP8 or INT4 KV quantisation (no retraining, 2x to 4x), or an SVD-based conversion to an MLA-like latent, which keeps more of the model before uptraining (section 2's projection: +0.009 at 128 numbers) but needs MLA kernels to pay off.
