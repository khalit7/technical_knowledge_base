In one screen

Almost every open model released in 2025 and 2026 is still the machine of Topic: llm-architecture: a stack of decoder blocks, each mixing information across tokens (attention or a recurrence) and then transforming each token on its own (a feed-forward network, FFN), with a normalisation and a residual connection around each. What differs between two model cards is a short list of choices inside that block. This page teaches you to read those choices off a card and a config.json in thirty seconds, and shows, for the 105 of the 109 models in Sebastian Raschka's LLM Architecture Gallery whose config this page could read, which choices they made, layer by layer.

Two terms first. The KV cache is the keys and values of every earlier token that an attention layer keeps during generation so it does not recompute them; its size per token is the number this page keeps returning to, because it, not the parameter count, decides whether long context and many concurrent users fit in memory. A per-layer strip is this page's picture of a model: one thin bar per layer, coloured by what that layer does (legend in section 4), three bars per model for the mixer, the FFN and the position scheme.

The one-line takeaway
Read a card for two different things: how many parameters run per token (dense or experts: compute and latency) and what each token leaves behind (attention variant, windows, linear layers: cache and concurrency). In 2026 almost every model is sparse in both, in different proportions, and the per-layer strips are the quickest way to see the proportions.

1. The gallery, and how this page rebuilt it

What it is. The LLM Architecture Gallery is Sebastian Raschka's side-by-side reference of open-weight model architectures: a drawn diagram per model and a fact sheet with total and active parameters, decoder type, attention and layer mix, context length, licence, links to the config and the technical report, and one headline number, the KV cache per token in bf16. Its metadata is a single models.yml under Apache 2.0; this page uses it at commit 589d213 (4 October 2026, read 18 October 2026): 109 entries from GPT-2 XL to models released in October 2026. It is a third-party summary: useful because it is consistent, not because it is a primary source.

Its convention for the headline number, from its KV-cache notes: "the logical cache added by one token for one sequence", batch 1, 2 bytes per element, summed over every layer that appends to a growing cache. A sliding-window layer is counted at full cost ("It changes how long a token remains in the cache"), linear and state-space layers count 0 B and their fixed state is kept outside the number, and MLA counts its compressed latent, not expanded keys and values. The root page's Architecture map (on Topic: llm-architecture) and this page use the same convention, so the three agree, and both add a second number with the windows credited.

How this page rebuilt it. For each entry the script downloads nothing at build time: it reads the saved config.json (public mirrors for gated Meta and Google repos), decodes one code per layer for the mixer, the FFN and the position scheme, and sums the cache layer by layer. Then it compares its own number with the gallery's.

Not rebuilt: four entries whose config is not public (three gated repos, one LoRA adapter with no config of its own), and the three DeepSeek V4 entries, whose compressed caches the per-layer formula does not express; for those the gallery's figure is shown, with the reconstruction in section 12.

2. Reading a model card in thirty seconds

A model card answers five questions, and each answer predicts something different. Ask them in this order:

  1. Total and active parameters. The total is the memory you must provision for the weights; the active count is what runs per token, so it sets latency and price. They are routinely conflated. Their ratio is the MoE sparsity.
  2. Attention type and layer mix. Full attention, windows, linear layers or trained sparse attention, and in what proportion: how cost grows with context, which matters more than the advertised context length.
  3. KV cache per token, times context, times concurrent requests, with the windows credited: whether long context fits, in GiB.
  4. Experts: routed, active, shared. How much expert parallelism serving needs, and how much skewed traffic will hurt (the Mixture of experts page owns why).
  5. Licence, and whether base weights shipped. Base weights decide whether you can post-train at all.

gpt-oss-120b (August 2025)

  1. 117B total, 5.1B active (OpenAI's model card, vendor): 4.4% runs per token, so it decodes like a 5B model and needs memory for 117B.
  2. 36 layers alternating a 128-token sliding window and full attention, one to one: cost grows with context through 18 of 36 layers.
  3. 8 KV heads of 64: 72 KiB per token on the card, 36 KiB per token effective at 131,072 tokens; one full-context request holds 4.5 GiB, so 16 such requests need 72 GiB of cache.
  4. 128 routed experts, 4 active, no shared expert in the config.
  5. Apache 2.0; the card does not say whether a base checkpoint shipped.

Kimi K3 (July 2026)

  1. 2.8T total, 104B active (gallery line from Moonshot's card, vendor): 3.7% runs per token.
  2. 93 layers: 69 Kimi Delta Attention layers (linear, fixed state) and 24 MLA layers that carry no positional encoding (mla_use_nope).
  3. Only the 24 MLA layers grow a cache: 24 × (512 + 64) × 2 = 27 KiB per token, 3.4 GiB at 131,072 tokens; the 69 linear layers add a fixed state of 1,572,864 numbers each, 414 MiB per sequence in FP32 (matrix state only).
  4. 896 routed experts, 16 active, 2 shared; the first layer dense.
  5. "Kimi K3 License" (gallery); read it before planning to serve or post-train.

4. The per-layer strips

A card's "layer mix" line ("52 sliding-window + 10 global") hides where those layers sit, and position matters: Gemma 3 puts a global layer after every five windowed ones so that information never travels more than five layers before it can reach the whole context, while a model that put all its global layers at the end would not. The strips draw each layer in order, left (layer 0, next to the embedding) to right (the last layer, next to the output head), each model stretched to the same width.

Three bars per model: mixer, FFN, position. The number on the right is the KV cache per token in bf16 (every layer at full cost). Click a name to open that model in Decode a config. The tiny GPT is this topic's running example (6 layers of multi-head attention with learned positions, 6,144 bytes per token), drawn on the same scale of colours.

How to read one. Count the blue, green and purple cells in the top bar: full attention, MLA and trained sparse layers, the ones whose cache grows with every token. Yellow cells (linear) and teal cells (windowed) stop growing. Orange cells in the middle bar are expert layers, so a grey first cell is the dense prefix DeepSeek-style models keep. A black cell (white in dark mode) in the bottom bar is a layer with no positional encoding: Llama 4 Maverick's every fourth layer, SmolLM3's every fourth, Kimi K3's attention layers. The Compare architectures tab has the strips for every model, sortable and filterable.

5. The attention ladder: one token, seven designs, the same shape

The mixer bar has seven colours because there are, in practice, seven answers to one question: what must this token leave behind in this layer so that later tokens can attend to it? The animation runs one token through one layer of the same shape for every design: 32 query heads of 128 (Llama 3.1 8B's shape), 16 earlier tokens already cached, and five steps (arrive, project, store, read at decode, scale to 128K tokens). MHA's footprint stays drawn dashed behind every other design, so each is seen against what it replaced.

One cell is 256 numbers: one KV head's key and value (128 + 128). Cells are drawn to scale in every design.

Shapes: 32 query heads of 128 as Llama 3.1 8B (config); MLA at DeepSeek-V3's latent of 512 plus a 64-number RoPE key (config); the recurrent state 32 heads of 128 × 128, the shape of Qwen3-Next's Gated DeltaNet layers and Kimi Linear's KDA layers (their configs). The 16-token context and the 8-token window are illustrative; the 128K figures use the formulas of this page. The animation runs only on screen, and starts paused, one step at a time, under reduced motion.

Step 5 is the argument in numbers, per layer at 128K tokens in bf16: MHA 2 GiB, GQA 512 MiB, MLA 144 MiB, MQA 64 MiB; a 4,096-token window caps at 16 MiB and a recurrent state stays at 1 MiB. Why each design costs little quality, MLA's absorbed form and its decoupled RoPE key, are derived on Attention variants and animated on DeepSeek (the MLA explainer); the Attention lab (on Topic: llm-architecture) trains the tiny GPT with each. This page's question is narrower: which rung each released model chose, and in what mixture. The next sections take the deltas one at a time.

6. Delta one: what each token stores

The problem. During decoding every new token must read the keys and values of every earlier token, in every attention layer. Multi-head attention (MHA) stores a key and a value for each of its heads; at Llama 3.1 70B's shape with all 64 heads that would be 2,560 KiB per token, 320 GiB for one 128K request.

How models shrink it. Grouped-query attention (GQA) shares one key and value head among a group of query heads (Llama 3.1 70B: 64 query heads, 8 KV heads, 320 KiB per token). Multi-head latent attention (MLA) stores a 512-number compressed latent plus a 64-number positional key per layer whatever the head count (DeepSeek-V3: 61 × 576 × 2 = 68.6 KiB per token). The table puts the real per-layer cost of each design side by side, read from the configs.

What it costs. Fewer KV heads cost a little quality (the GQA and DeepSeek-V2 ablations are on Attention variants); MLA costs extra projections and its own kernels. When it matters: decode is bound by memory traffic, so a smaller cache is faster decode, not only more room. How to check: num_key_value_heads × head_dim × 4 bytes per attention layer, or (kv_lora_rank + qk_rope_head_dim) × 2 for MLA, then count the layers that grow a cache.

In the gallery's 2026 models no model uses plain MHA, 16 use MLA latents (alone, under a sparse indexer, or between linear layers), and the median cache is 68.6 KiB per token against 144 KiB for the 2025 models. The spread is still a hundredfold: Nemotron 3.5 Lightning keeps 6 KiB per token, Gemma 4 31B 840 KiB.

7. Delta two: how long it is kept (sliding windows)

The problem. Most of what a token needs is nearby. How: most layers attend only to the last W tokens (a sliding window), and every few layers a global layer attends to everything, so far information still reaches every token, a few layers later. A windowed layer stores the same row per token as its base design but drops rows older than W, so the memory one request holds at context T is the sum over layers of bytes per token × min(T, W).

Every windowed model in the gallery with a computable cache: KV per token on the card (every layer at full cost, light bar) against the average per token actually held at 131,072 tokens with windows credited (dark bar). Derived from configs, bf16.

What it costs. Information more than W tokens back reaches a token only through the global layers, so exact retrieval far back depends on how many there are. When it matters: only past the window; below W the two numbers coincide. How to check: count sliding_attention entries in layer_types and read sliding_window; then credit them. In this set the local-to-global ratio runs from 1:1 (gpt-oss) through 3:1 (11 models, the most common) to 5:1 (Gemma 3 and 4), and windows from 128 tokens (11 models, gpt-oss and MiMo among them) to 8,192 (Llama 4's chunks). Crediting the windows cuts the long-context cache 2 times for gpt-oss and 18 times for Gemma 4 31B: 840 KiB per token on the card, about 46 KiB per token held at 131,072 tokens.

8. Delta three: whether it is stored at all (linear and state-space layers)

The problem. Even windows keep a cache that grows with context in the global layers. How: replace most attention layers with a recurrence that folds each token into a fixed-size state: Gated DeltaNet in Qwen3-Next and Qwen3.5 to 3.8, Kimi Delta Attention in Kimi Linear and Kimi K3, Mamba-2 in Nemotron 3 and Granite 4.0-H, lightning attention in Ling, short convolutions in LFM2.5. Keep one attention layer in three to eight for exact recall. The mechanisms are on Beyond attention; here, what the released mixtures are.

What it costs. The state is a lossy summary; what is not written into it is gone, which is why every released hybrid keeps some attention. Moonshot's Kimi Linear ablation (vendor, arXiv 2510.26692, Table 1) picked 3 KDA layers per MLA layer: validation perplexity 5.65 at 3:1 against 5.66 at 1:1, 5.70 at 7:1, 5.82 at 15:1 and 5.77 for the pure full-attention baseline (0:1). When it matters: the fixed state is a cost too; the last column is the context at which the state equals the growing cache, below which the hybrid holds more per request than its attention layers alone suggest. How to check: count linear_attention, mamba or M entries; the state per layer is heads × key dim × value dim (or heads × head dim × state size for Mamba-2).

Predict: Qwen3.5 397B keeps 15 attention layers of 60, 30 KiB per token in all; its 45 Gated DeltaNet layers hold 180 MiB of FP32 state per sequence. Past what context does the growing cache outweigh the fixed state?

About 6,000: 180 MiB / 30 KiB = 6,144 tokens. Below that a short chat holds more state than cache; at 262,144 tokens the cache is 7.5 GiB and the state a rounding error. For serving many short requests the state, not the cache, sets concurrency.

9. Delta four: how many FFN weights run (experts)

The problem. Quality grows with parameters, latency with the parameters each token uses. How: a mixture-of-experts (MoE) layer holds many expert FFNs and a router sends each token to k of them, often plus one always-on shared expert; many models keep their first layers dense. Of the gallery's 2026 models with a config, 52 of 66 are MoE; 39 of those add a shared expert and 31 keep a dense prefix; 8 experts per token is the most common choice (31 models). The routing, balancing and parallelism are owned by Mixture of experts.

What it costs. All experts must be in memory, so the total, not the active count, sets the hardware. When it matters: at small batch, decode reads every expert some token picks. How to check: n_routed_experts, num_experts_per_tok, n_shared_experts, and the dense prefix from first_k_dense_replace or a per-layer list. The active share runs down to about 3% (DeepSeek V4-Pro 3.1%, Kimi K2.5 to K2.7 3.2%, Kimi K3 3.7%, gallery lines). The MoE choice and the attention choice are independent: Kimi K3 is extreme on both.

10. Delta five: how position enters

The problem. Attention by itself does not know the order of tokens. Almost every model rotates queries and keys by their position (RoPE, 61 of the 66 models of 2026), and the deltas are in the details, each readable from the config: partial RoPE (rotate only some dimensions: 25 models, the Qwen3.5 to 3.8 line and Gemma 4's global layers among them); no position in some layers (5 models in 2026: Kimi K3 and Ember-1 in all 24 attention layers, Solar Open 2, Muse Glimmer, GLM-5.3-Flash; earlier Llama 4 Maverick in 12 of 48 and SmolLM3 in 9 of 36); different bases per layer type (10,000 on local layers against 500,000 to 10,000,000 on global ones in Gemma 4, MiMo, Laguna and Naive); and scaling past the trained length (YaRN factors in 9 of the 2026 configs). Why each works, and RoPE scaling in full, are on Positional Encodings. How to check: the bottom strip; then rope_parameters per layer type.

11. Norms and gates: on the card, rarely in the config

Pre-norm RMSNorm is close to universal; the 2025 to 2026 deltas are QK-norm (an RMSNorm on queries and keys before the dot product, which bounds attention logits), extra norms after each sublayer (OLMo 2's post-sublayer norm, Gemma's sandwich), and output gates on attention (Qwen3-Next, Trinity, Laguna, Kimi K3's "Gated MLA"). Configs rarely state these as fields (the modeling code does them), so this page does not decode them; the gallery's attention line names QK-norm for 19 of the 2026 models, an undercount because it is named only when the card mentions it. The root Architecture map (on Topic: llm-architecture) records norm placement and QK-norm, sourced, for its 46 lineage models, and Normalisation, residuals and stability owns why they work.

12. Delta six: stack shape

The sections above assume one causal stack, each layer run once, each with its own cache. Four 2025 to 2026 configs break that, and each changes the cache arithmetic:

  • Looped layers. Ouro-Thinking 2.6B runs its 48 layers 4 times per token (total_ut_steps 4) and each pass keeps its own cache: 384 KiB per pass, 1.5 MiB per token, the largest per-token cache in the gallery from a 2.6B model. Nanbeige 4.2 runs 22 layers twice (num_loops 2).
  • Cross-layer KV sharing. Gemma 4 E2B and E4B let their last 20 and 18 layers reuse the cache of an earlier layer of the same type (num_kv_shared_layers; transformers 5.20.1, modeling_gemma4.py, is_kv_shared_layer): 18 KiB and 56 KiB per token, not the gallery's 35 and 84.
  • Two attention sublayers per layer. LongCat-Flash layers each hold two MLA sublayers and a shortcut MoE beside two dense MLPs (modeling_longcat_flash.py): 14 layers in the config, 28 caches.
  • Compressed and shared caches. DeepSeek V4 compresses most layers' entries 4 times (CSA) or 128 times (HCA) along the sequence. From compress_ratios, in the gallery's bf16 convention (512 numbers per entry, indexer keys and the 128-token windows left out): V4-Pro 30 CSA + 31 HCA layers, 7,928 bytes per token, which reproduces the gallery's 7.7 KiB; V4-Flash 21 CSA + 20 HCA layers plus 2 window-only layers, 5,536 bytes, the gallery's 5.4 KiB. DeepSeek V4.1-Flash goes further, an encoder whose final state feeds the decoder's keys and values (gallery; detailed, with its 890 bytes per token at FP4, on DeepSeek). The DeepSeek page's own V4-Pro estimate, 4,939.5 bytes per token, uses FP8 main entries and FP4 indexer keys: a different precision convention, not a contradiction.

Multi-token prediction (MTP) layers, extra heads that predict tokens further ahead and double as a draft model (Families and objectives), are a fifth: when used at inference they keep caches too, which is the whole difference between this page's 180 KiB and the gallery's 192 KiB for Step 3.5 Flash.

13. How the numbers were checked

A curated table is only as good as its recomputation (lesson of this page's first build). Every cache figure here was checked four ways, all on an Apple M1 Pro (CPU), configs only:

  1. Against the gallery. 95 of the 101 figures both sides compute agree within rounding; the six that do not are in section 1, each with both arithmetics.
  2. Against transformers' own parsing. src/checks/hf_layer_types.py builds each config with its transformers 5.20.1 configuration class (no weights, no network) and compares the per-layer list transformers itself derives with this page's mixer strip. Result: 59 models agree layer for layer, 0 differ; the other 49 cannot be checked this way: 19 need custom code (no class in transformers), 2 configs are rejected by their class (a non-finite number inside a list, a field type), and 28 classes keep no per-layer list, 26 of them for stacks this page also draws as uniform; the other two are Inkling (windows from local_layer_ids) and MiniMax M3 (three dense layers, from its model card).
  3. Against the root's Config calculator. src/checks/cc_agree.mjs runs the root page's Config calculator (on Topic: llm-architecture) code on every gallery config it models and compares the KV cache at 1; 1,000; 4,096; 32,768 and 131,072 tokens with windows credited: 44 models, 220 numbers, all equal (the calculator includes DeepSeek V3.2's indexer keys, as this page's "with indexer" figure does). Two Nemotron configs that spell their pattern as layers_block_type make the calculator throw (TypeError: c.hybrid_override_pattern is not iterable), reported to the root.
  4. Against the root's Architecture map. The 27 models both pages draw have identical strips, cache, windows and expert counts, field for field.

Common mistakes

Sizing the cache by query heads
The cache is set by KV heads. Llama 3.1 70B has 64 query heads and 8 KV heads; using 64 overstates its cache 8 times (2,560 KiB per token instead of 320).
Taking the card's per-token figure as the long-context cost of a windowed model
The headline counts windowed layers at full cost. Gemma 4 31B reads 840 KiB per token but holds about 46 KiB per token at 131,072 tokens: 105 GiB against 5.8 GiB for one request.
Calling a hybrid "cache-free"
Its attention layers still grow a cache (Kimi K3: 27 KiB per token) and the state is a fixed cost per request (414 MiB in FP32 for Kimi K3), larger than the cache up to about 15,700 tokens.
Assuming sparse attention shrinks the cache
Selecting the top k keys cuts arithmetic, not storage: every key must stay available to be selected, and the indexer adds keys of its own. DeepSeek V3.2 keeps V3's 68.6 KiB per token plus 15.25 KiB of indexer keys (61 × 128 × 2 bytes). Storage falls only when entries are also compressed, as in V4.
Treating total parameters as compute, or active as memory
Total sets the memory floor, active sets latency and price, and an encoder-decoder can have two active counts (DeepSeek V4.1-Flash: 8B during prefill, 16B during decode, gallery).
Reading a field name as a cache design
Motif 3 has kv_lora_rank 512 like DeepSeek, but its released modeling_motif.py caches the expanded keys (16 heads × 192) and values (16 × 128): 530 KiB per token, not the 59.6 KiB a latent cache would hold. What is cached is decided by the code.
Saving an error page as a config
A gated repo answers an anonymous download with a short error body. This page's first build saved nine of them as .json files (one reads, in full, Invalid username or password.) and silently skipped those models. Parse every downloaded config and fail loudly.
Trusting a curated table without recomputing it
Six of the gallery's 101 recomputable figures do not follow from the configs; two of them (Gemma 4 E2B and E4B) overstate the cache by about 1.5 to 2 times because they ignore cross-layer sharing. Recompute every row you rely on and publish the match count.

Two more mistakes, deriving head_dim from hidden_size and reading max_position_embeddings as trained context, are worked on the root page's section 12 (Topic: llm-architecture).

Interview questions

A config has 60 layers, 50 of them sliding (window 1,024, 16 KV heads of 256) and 10 global with one shared K = V tensor of 4 heads × 512. KV per token in bf16, and at 131,072 tokens?
Sliding: 2 × 16 × 256 × 2 = 16 KiB per layer; global: 4 × 512 × 2 = 4 KiB. Per token on the card: 50 × 16 + 10 × 4 = 840 KiB. At 131,072 tokens the sliding layers hold 1,024 tokens each (800 MiB) and the global ones all of them (5 GiB): about 5.8 GiB, 46 KiB per token. That is Gemma 4 31B.
Why does gpt-oss-120b's cache halve at long context, while Gemma 3 27B's falls six times?
gpt-oss alternates windows and global layers 1:1 with a 128-token window, so half its layers stop growing; Gemma 3 has 5 windowed layers per global one, so five sixths stop growing.
"2.8T total, 104B active". What does each number tell you about serving it?
2.8T is the weight memory (5.1 TiB in bf16, so a multi-node deployment or aggressive quantisation); 104B is the compute per token, so latency and price are those of a 100B dense model. Neither says anything about the cache: that is the attention design (27 KiB per token for Kimi K3).
A hybrid keeps 1 attention layer in 4. At what context does its fixed state stop mattering?
Where the state equals the growing cache: state bytes divided by cache bytes per token. Qwen3-Next: 72 MiB of FP32 state against 24 KiB per token, about 3,000 tokens; beyond a few tens of thousands of tokens the state is a rounding error.
Why do so many MoE models keep their first layers dense?
Early representations are barely differentiated by token type, so routing on them is close to random and unstable; dense layers there cost little and steady training. 31 of the 52 MoE models of 2026 in the gallery do it, most with one to three dense layers.
Two 30B models differ tenfold in KV cache per token. Name three causes you would look for in the config.
KV heads (MHA against GQA or MQA), head dimension, MLA latent against full keys and values, how many layers grow a cache (windows, linear layers, shared layers), looped passes.
Design: serve 16 concurrent 1M-token conversations on one node of 8 × 80 GB GPUs, weights and cache in bf16. Which gallery design would you start from, and why?
First filter on published context: Gemma 4 31B (256K), Qwen3.5 and Qwen3-Next (262K) are out. Then budget: 640 GB is 596 GiB. Nemotron 3 Super 120B-A12B: weights about 224 GiB; its 8 attention layers hold 8 GiB per 1M-token request plus 160 MiB of Mamba-2 state, about 130 GiB for 16 requests: about 355 GiB, it fits with room for activations. Kimi K3 has a small cache (27 GiB per request) but 2.8T of weights (5.1 TiB). A GQA model of the same size would hold hundreds of GiB per request. So: a Mamba-2 or linear-attention hybrid with few attention layers, MoE for quality at 12B active, then FP8 for both weights and cache if headroom is needed. Illustrative arithmetic: activations, framework overheads and expert placement are left out.

Cache at context: what one request actually holds

The card's number is per token; what a server must hold is, for every layer, its bytes per token times the tokens that layer keeps, plus any fixed recurrent state, times the requests resident at once:

memory per request = Σlayers bytesℓ × min(T, Wℓ) + Σlinear layers stateℓ
T
the tokens in the request (prompt plus generated so far)
Wℓ
layer ℓ's window; infinite for a full-attention layer, so it keeps all T
bytesℓ
what layer ℓ stores per token (section 6 of the Reading tab), bf16 or FP8
stateℓ
a linear layer's fixed state, heads × key dim × value dim (Gated DeltaNet, KDA) or heads × head dim × state size (Mamba-2), kept in FP32 as the root Config calculator does
