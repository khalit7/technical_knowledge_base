13. How the numbers were checked

A curated table is only as good as its recomputation (lesson of this page's first build). Every cache figure here was checked four ways, all on an Apple M1 Pro (CPU), configs only:

  1. Against the gallery. 95 of the 101 figures both sides compute agree within rounding; the six that do not are in section 1, each with both arithmetics.
  2. Against transformers' own parsing. src/checks/hf_layer_types.py builds each config with its transformers 5.20.1 configuration class (no weights, no network) and compares the per-layer list transformers itself derives with this page's mixer strip. Result: 59 models agree layer for layer, 0 differ; the other 49 cannot be checked this way: 19 need custom code (no class in transformers), 2 configs are rejected by their class (a non-finite number inside a list, a field type), and 28 classes keep no per-layer list, 26 of them for stacks this page also draws as uniform; the other two are Inkling (windows from local_layer_ids) and MiniMax M3 (three dense layers, from its model card).
  3. Against the root's Config calculator. src/checks/cc_agree.mjs runs the root page's {{Config calculator (on Topic: llm-architecture)|n:3fd5c17b0d0d8172b490dc9f9ac281df}} code on every gallery config it models and compares the KV cache at 1; 1,000; 4,096; 32,768 and 131,072 tokens with windows credited: 44 models, 220 numbers, all equal (the calculator includes DeepSeek V3.2's indexer keys, as this page's "with indexer" figure does). Two Nemotron configs that spell their pattern as layers_block_type make the calculator throw (TypeError: c.hybrid_override_pattern is not iterable), reported to the root.
  4. Against the root's Architecture map. The 27 models both pages draw have identical strips, cache, windows and expert counts, field for field.

Common mistakes

Sizing the cache by query heads
The cache is set by KV heads. Llama 3.1 70B has 64 query heads and 8 KV heads; using 64 overstates its cache 8 times (2,560 KiB per token instead of 320).
Taking the card's per-token figure as the long-context cost of a windowed model
The headline counts windowed layers at full cost. Gemma 4 31B reads 840 KiB per token but holds about 46 KiB per token at 131,072 tokens: 105 GiB against 5.8 GiB for one request.
Calling a hybrid "cache-free"
Its attention layers still grow a cache (Kimi K3: 27 KiB per token) and the state is a fixed cost per request (414 MiB in FP32 for Kimi K3), larger than the cache up to about 15,700 tokens.
Assuming sparse attention shrinks the cache
Selecting the top k keys cuts arithmetic, not storage: every key must stay available to be selected, and the indexer adds keys of its own. DeepSeek V3.2 keeps V3's 68.6 KiB per token plus 15.25 KiB of indexer keys (61 × 128 × 2 bytes). Storage falls only when entries are also compressed, as in V4.
Treating total parameters as compute, or active as memory
Total sets the memory floor, active sets latency and price, and an encoder-decoder can have two active counts (DeepSeek V4.1-Flash: 8B during prefill, 16B during decode, gallery).
Reading a field name as a cache design
Motif 3 has kv_lora_rank 512 like DeepSeek, but its released modeling_motif.py caches the expanded keys (16 heads × 192) and values (16 × 128): 530 KiB per token, not the 59.6 KiB a latent cache would hold. What is cached is decided by the code.
Saving an error page as a config
A gated repo answers an anonymous download with a short error body. This page's first build saved nine of them as .json files (one reads, in full, Invalid username or password.) and silently skipped those models. Parse every downloaded config and fail loudly.
Trusting a curated table without recomputing it
Six of the gallery's 101 recomputable figures do not follow from the configs; two of them (Gemma 4 E2B and E4B) overstate the cache by about 1.5 to 2 times because they ignore cross-layer sharing. Recompute every row you rely on and publish the match count.

Two more mistakes, deriving head_dim from hidden_size and reading max_position_embeddings as trained context, are worked on the root page's section 12 ({{Topic: llm-architecture|n:3fd5c17b0d0d8172b490dc9f9ac281df}}).

Interview questions

A config has 60 layers, 50 of them sliding (window 1,024, 16 KV heads of 256) and 10 global with one shared K = V tensor of 4 heads × 512. KV per token in bf16, and at 131,072 tokens?
Sliding: 2 × 16 × 256 × 2 = 16 KiB per layer; global: 4 × 512 × 2 = 4 KiB. Per token on the card: 50 × 16 + 10 × 4 = 840 KiB. At 131,072 tokens the sliding layers hold 1,024 tokens each (800 MiB) and the global ones all of them (5 GiB): about 5.8 GiB, 46 KiB per token. That is Gemma 4 31B.
Why does gpt-oss-120b's cache halve at long context, while Gemma 3 27B's falls six times?
gpt-oss alternates windows and global layers 1:1 with a 128-token window, so half its layers stop growing; Gemma 3 has 5 windowed layers per global one, so five sixths stop growing.
"2.8T total, 104B active". What does each number tell you about serving it?
2.8T is the weight memory (5.1 TiB in bf16, so a multi-node deployment or aggressive quantisation); 104B is the compute per token, so latency and price are those of a 100B dense model. Neither says anything about the cache: that is the attention design (27 KiB per token for Kimi K3).
A hybrid keeps 1 attention layer in 4. At what context does its fixed state stop mattering?
Where the state equals the growing cache: state bytes divided by cache bytes per token. Qwen3-Next: 72 MiB of FP32 state against 24 KiB per token, about 3,000 tokens; beyond a few tens of thousands of tokens the state is a rounding error.
Why do so many MoE models keep their first layers dense?
Early representations are barely differentiated by token type, so routing on them is close to random and unstable; dense layers there cost little and steady training. 31 of the 52 MoE models of 2026 in the gallery do it, most with one to three dense layers.
Two 30B models differ tenfold in KV cache per token. Name three causes you would look for in the config.
KV heads (MHA against GQA or MQA), head dimension, MLA latent against full keys and values, how many layers grow a cache (windows, linear layers, shared layers), looped passes.
Design: serve 16 concurrent 1M-token conversations on one node of 8 × 80 GB GPUs, weights and cache in bf16. Which gallery design would you start from, and why?
First filter on published context: Gemma 4 31B (256K), Qwen3.5 and Qwen3-Next (262K) are out. Then budget: 640 GB is 596 GiB. Nemotron 3 Super 120B-A12B: weights about 224 GiB; its 8 attention layers hold 8 GiB per 1M-token request plus 160 MiB of Mamba-2 state, about 130 GiB for 16 requests: about 355 GiB, it fits with room for activations. Kimi K3 has a small cache (27 GiB per request) but 2.8T of weights (5.1 TiB). A GQA model of the same size would hold hundreds of GiB per request. So: a Mamba-2 or linear-attention hybrid with few attention layers, MoE for quality at 12B active, then FP8 for both weights and cache if headroom is needed. Illustrative arithmetic: activations, framework overheads and expert placement are left out.
