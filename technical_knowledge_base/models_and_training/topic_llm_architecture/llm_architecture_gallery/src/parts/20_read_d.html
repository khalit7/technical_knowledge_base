6. Delta one: what each token stores

The problem. During decoding every new token must read the keys and values of every earlier token, in every attention layer. Multi-head attention (MHA) stores a key and a value for each of its heads; at Llama 3.1 70B's shape with all 64 heads that would be 2,560 KiB per token, 320 GiB for one 128K request.

How models shrink it. Grouped-query attention (GQA) shares one key and value head among a group of query heads (Llama 3.1 70B: 64 query heads, 8 KV heads, 320 KiB per token). Multi-head latent attention (MLA) stores a 512-number compressed latent plus a 64-number positional key per layer whatever the head count (DeepSeek-V3: 61 × 576 × 2 = 68.6 KiB per token). The table puts the real per-layer cost of each design side by side, read from the configs.

What it costs. Fewer KV heads cost a little quality (the GQA and DeepSeek-V2 ablations are on {{Attention variants|n:3fd5c17b0d0d8120859ecc2d0236e846}}); MLA costs extra projections and its own kernels. When it matters: decode is bound by memory traffic, so a smaller cache is faster decode, not only more room. How to check: num_key_value_heads × head_dim × 4 bytes per attention layer, or (kv_lora_rank + qk_rope_head_dim) × 2 for MLA, then count the layers that grow a cache.

In the gallery's 2026 models no model uses plain MHA, 16 use MLA latents (alone, under a sparse indexer, or between linear layers), and the median cache is 68.6 KiB per token against 144 KiB for the 2025 models. The spread is still a hundredfold: Nemotron 3.5 Lightning keeps 6 KiB per token, Gemma 4 31B 840 KiB.

7. Delta two: how long it is kept (sliding windows)

The problem. Most of what a token needs is nearby. How: most layers attend only to the last W tokens (a sliding window), and every few layers a global layer attends to everything, so far information still reaches every token, a few layers later. A windowed layer stores the same row per token as its base design but drops rows older than W, so the memory one request holds at context T is the sum over layers of bytes per token × min(T, W).

Every windowed model in the gallery with a computable cache: KV per token on the card (every layer at full cost, light bar) against the average per token actually held at 131,072 tokens with windows credited (dark bar). Derived from configs, bf16.

What it costs. Information more than W tokens back reaches a token only through the global layers, so exact retrieval far back depends on how many there are. When it matters: only past the window; below W the two numbers coincide. How to check: count sliding_attention entries in layer_types and read sliding_window; then credit them. In this set the local-to-global ratio runs from 1:1 (gpt-oss) through 3:1 (11 models, the most common) to 5:1 (Gemma 3 and 4), and windows from 128 tokens (11 models, gpt-oss and MiMo among them) to 8,192 (Llama 4's chunks). Crediting the windows cuts the long-context cache 2 times for gpt-oss and 18 times for Gemma 4 31B: 840 KiB per token on the card, about 46 KiB per token held at 131,072 tokens.

Predict: Llama 4 Maverick has 48 layers; 36 attend within 8,192-token chunks and 12 are global, each layer 4 KiB per token. The card says 192 KiB per token. What does a 131,072-token request hold per token?

Skip: show the answer

57 KiB. The 12 global layers hold every token: 12 × 4 = 48 KiB per token. The 36 chunked layers hold at most 8,192 tokens each, which spread over 131,072 tokens is 36 × 4 KiB × 8,192 / 131,072 = 9 KiB per token. Close to "only the globals count", but not equal: windows that are a large fraction of the context still cost. (This page, like the root Config calculator, treats Llama 4's chunks as an 8,192-token window, an upper bound for chunked attention.)

8. Delta three: whether it is stored at all (linear and state-space layers)

The problem. Even windows keep a cache that grows with context in the global layers. How: replace most attention layers with a recurrence that folds each token into a fixed-size state: Gated DeltaNet in Qwen3-Next and Qwen3.5 to 3.8, Kimi Delta Attention in Kimi Linear and Kimi K3, Mamba-2 in Nemotron 3 and Granite 4.0-H, lightning attention in Ling, short convolutions in LFM2.5. Keep one attention layer in three to eight for exact recall. The mechanisms are on {{Beyond attention|n:3fd5c17b0d0d8142bc9ecac1fc366966}}; here, what the released mixtures are.

What it costs. The state is a lossy summary; what is not written into it is gone, which is why every released hybrid keeps some attention. Moonshot's Kimi Linear ablation (vendor, {{arXiv 2510.26692|https://arxiv.org/abs/2510.26692}}, Table 1) picked 3 KDA layers per MLA layer: validation perplexity 5.65 at 3:1 against 5.66 at 1:1, 5.70 at 7:1, 5.82 at 15:1 and 5.77 for the pure full-attention baseline (0:1). When it matters: the fixed state is a cost too; the last column is the context at which the state equals the growing cache, below which the hybrid holds more per request than its attention layers alone suggest. How to check: count linear_attention, mamba or M entries; the state per layer is heads × key dim × value dim (or heads × head dim × state size for Mamba-2).

Predict: Qwen3.5 397B keeps 15 attention layers of 60, 30 KiB per token in all; its 45 Gated DeltaNet layers hold 180 MiB of FP32 state per sequence. Past what context does the growing cache outweigh the fixed state?

Skip: show the answer

About 6,000: 180 MiB / 30 KiB = 6,144 tokens. Below that a short chat holds more state than cache; at 262,144 tokens the cache is 7.5 GiB and the state a rounding error. For serving many short requests the state, not the cache, sets concurrency.

9. Delta four: how many FFN weights run (experts)

The problem. Quality grows with parameters, latency with the parameters each token uses. How: a mixture-of-experts (MoE) layer holds many expert FFNs and a router sends each token to k of them, often plus one always-on shared expert; many models keep their first layers dense. Of the gallery's 2026 models with a config, 52 of 66 are MoE; 39 of those add a shared expert and 31 keep a dense prefix; 8 experts per token is the most common choice (31 models). The routing, balancing and parallelism are owned by {{Mixture of experts|n:3fd5c17b0d0d81fda06bf955af7c2b58}}.

What it costs. All experts must be in memory, so the total, not the active count, sets the hardware. When it matters: at small batch, decode reads every expert some token picks. How to check: n_routed_experts, num_experts_per_tok, n_shared_experts, and the dense prefix from first_k_dense_replace or a per-layer list. The active share runs down to about 3% (DeepSeek V4-Pro 3.1%, Kimi K2.5 to K2.7 3.2%, Kimi K3 3.7%, gallery lines). The MoE choice and the attention choice are independent: Kimi K3 is extreme on both.

10. Delta five: how position enters

The problem. Attention by itself does not know the order of tokens. Almost every model rotates queries and keys by their position (RoPE, 61 of the 66 models of 2026), and the deltas are in the details, each readable from the config: partial RoPE (rotate only some dimensions: 25 models, the Qwen3.5 to 3.8 line and Gemma 4's global layers among them); no position in some layers (5 models in 2026: Kimi K3 and Ember-1 in all 24 attention layers, Solar Open 2, Muse Glimmer, GLM-5.3-Flash; earlier Llama 4 Maverick in 12 of 48 and SmolLM3 in 9 of 36); different bases per layer type (10,000 on local layers against 500,000 to 10,000,000 on global ones in Gemma 4, MiMo, Laguna and Naive); and scaling past the trained length (YaRN factors in 9 of the 2026 configs). Why each works, and RoPE scaling in full, are on {{Positional Encodings|n:3c65c17b0d0d81a5b7c9e578fcdfac00}}. How to check: the bottom strip; then rope_parameters per layer type.

11. Norms and gates: on the card, rarely in the config

Pre-norm RMSNorm is close to universal; the 2025 to 2026 deltas are QK-norm (an RMSNorm on queries and keys before the dot product, which bounds attention logits), extra norms after each sublayer (OLMo 2's post-sublayer norm, Gemma's sandwich), and output gates on attention (Qwen3-Next, Trinity, Laguna, Kimi K3's "Gated MLA"). Configs rarely state these as fields (the modeling code does them), so this page does not decode them; the gallery's attention line names QK-norm for 19 of the 2026 models, an undercount because it is named only when the card mentions it. The root {{Architecture map (on Topic: llm-architecture)|n:3fd5c17b0d0d8172b490dc9f9ac281df}} records norm placement and QK-norm, sourced, for its 46 lineage models, and {{Normalisation, residuals and stability|n:3fd5c17b0d0d8163b50dc5e9d9240e89}} owns why they work.

12. Delta six: stack shape

The sections above assume one causal stack, each layer run once, each with its own cache. Four 2025 to 2026 configs break that, and each changes the cache arithmetic:

  • Looped layers. Ouro-Thinking 2.6B runs its 48 layers 4 times per token (total_ut_steps 4) and each pass keeps its own cache: 384 KiB per pass, 1.5 MiB per token, the largest per-token cache in the gallery from a 2.6B model. Nanbeige 4.2 runs 22 layers twice (num_loops 2).
  • Cross-layer KV sharing. Gemma 4 E2B and E4B let their last 20 and 18 layers reuse the cache of an earlier layer of the same type (num_kv_shared_layers; transformers 5.20.1, modeling_gemma4.py, is_kv_shared_layer): 18 KiB and 56 KiB per token, not the gallery's 35 and 84.
  • Two attention sublayers per layer. LongCat-Flash layers each hold two MLA sublayers and a shortcut MoE beside two dense MLPs (modeling_longcat_flash.py): 14 layers in the config, 28 caches.
  • Compressed and shared caches. DeepSeek V4 compresses most layers' entries 4 times (CSA) or 128 times (HCA) along the sequence. From compress_ratios, in the gallery's bf16 convention (512 numbers per entry, indexer keys and the 128-token windows left out): V4-Pro 30 CSA + 31 HCA layers, 7,928 bytes per token, which reproduces the gallery's 7.7 KiB; V4-Flash 21 CSA + 20 HCA layers plus 2 window-only layers, 5,536 bytes, the gallery's 5.4 KiB. DeepSeek V4.1-Flash goes further, an encoder whose final state feeds the decoder's keys and values (gallery; detailed, with its 890 bytes per token at FP4, on {{DeepSeek|n:3c65c17b0d0d81a2ae7ec6796947a235}}). The DeepSeek page's own V4-Pro estimate, 4,939.5 bytes per token, uses FP8 main entries and FP4 indexer keys: a different precision convention, not a contradiction.

Multi-token prediction (MTP) layers, extra heads that predict tokens further ahead and double as a draft model ({{Families and objectives|n:3fd5c17b0d0d8105b616c17c1439f766}}), are a fifth: when used at inference they keep caches too, which is the whole difference between this page's 180 KiB and the gallery's 192 KiB for Step 3.5 Flash.
