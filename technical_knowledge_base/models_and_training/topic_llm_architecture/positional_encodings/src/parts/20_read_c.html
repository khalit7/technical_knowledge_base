4. The base and the variants, read from the configs

A larger base slows every pair except pair 0, so more pairs stay informative across a long window. Xiong et al. found Llama 2's base of 10,000 decayed attention too strongly beyond 4,000 to 6,000 tokens and proposed "increasing the 'base frequency b' of RoPE from 10,000 to 500,000", called adjusted base frequency, ABF ({{Xiong et al. §4.1|https://arxiv.org/abs/2309.16039}}); Llama 3 pretrains with 500,000 ({{Llama 3 page|n:3c65c17b0d0d81aca58ccb9d720b474e}}), and Qwen3 raises 10,000 to 1,000,000 for its long-context stage ({{Qwen3 page|n:3c65c17b0d0d81a19006e6b096a6e14b}}). This is a pretraining choice, not the NTK-aware scaling of section 7, although both change the base.

Bases have climbed from 10,000 to 106 and beyond as context grew

Read a config's position line in 30 seconds. (1) Is there RoPE at all: rope_theta or rope_parameters, but check the modeling code of hybrids, where the field can be present and unused. (2) How many dimensions rotate: head_dim × partial_rotary_factor, or qk_rope_head_dim for MLA, or rotary_dim. (3) Which layers: layer_types, no_rope_layers, no_rope_layer_interval, per-layer-type rope_parameters. (4) Scaling: rope_scaling or rope_parameters.rope_type with its factor and original_max_position_embeddings, the length the model was actually pretrained at; max_position_embeddings is a ceiling, not the trained length (Qwen3's configs say 40,960 for a 32,768-token native window; MiniMax-M1's says 10,240,000).

transformers 5 renamed the field
From transformers 5, configs are standardised to rope_parameters, a dict holding rope_type, rope_theta, factor and the rest (nested per layer type for Gemma 4); old rope_theta and rope_scaling fields are still read and moved into it (RotaryEmbeddingConfigMixin.standardize_rope_params in transformers modeling_rope_utils.py). Code that reads config.rope_scaling directly gets the old field or nothing.

Five variants matter in practice. Partial RoPE rotates a fraction of each head and leaves the rest to match on content alone (GPT-NeoX 25%, Phi-2 40%, GLM-4.5 half, Qwen3-Next a quarter). Decoupled RoPE (DeepSeek's MLA) keeps position out of the compressed keys and carries it in a separate 64-dimension key shared by all heads, because a rotated key would block absorbing the key up-projection into the query (the mechanism is on {{Attention variants|n:3fd5c17b0d0d8120859ecc2d0236e846}}). Multimodal RoPE gives images and video several indices: Qwen2-VL splits the rotation into "temporal, height, and width" components, and for text "these components utilize identical position IDs, making M-RoPE functionally equivalent to 1D-RoPE" ({{Qwen2-VL §2.1|https://arxiv.org/abs/2409.12191}}). What this does inside a vision-language model (an image advances the position counter by its larger side, not by its token count) is on {{Vision-language models|n:3fc5c17b0d0d81adbb7be5bc41c4d9d0}}, section 2a. Mixed layers interleave RoPE layers with NoPE layers or a different base. No RoPE anywhere in hybrids, where recurrent layers carry order. The strips show the layer patterns, read from each config:

Partial RoPE comes in two kinds. The default kind spreads the whole spectrum over the rotated dimensions (exponents 2i/drot), so its slowest pair is as slow as a full head's. Gemma 4's "proportional" kind keeps the full head's exponents (2i/dhead) for the first pairs and sets the rest to zero frequency, so it keeps only the fast clocks.

Same idea, opposite spectra: Qwen3-Next keeps the slow clocks, Gemma 4's global layers keep only fast ones

Why keep only fast pairs: Barbero et al. found Gemma uses RoPE's highest frequencies for positional attention patterns and "greatly prefers to use the lowest frequencies", which they suspect carry semantic information ({{Round and Round We Go|https://arxiv.org/abs/2410.06205}}).
