Every attention variant answers one question differently: what must each token leave behind so that later tokens can read it? That leftover, the KV cache, decides how much memory a long conversation takes and how many bytes each generated token has to read, and those two numbers usually decide the serving bill. 1. Why attention keeps a cache

The problem. A decoder generates one token at a time. At step t the new token's query must be compared with the key of every earlier token, and the resulting weights average the earlier tokens' values. Keys and values are projections of each token's residual stream at that layer (k = WKx, v = WVx), and a token's x at a layer never changes once it is computed, because causal attention never lets a token see later ones. So recomputing them at every step is pure waste: step t would redo t projections per layer, and generating n tokens would cost about n2/2 projections instead of n.

How it works. Each layer stores every token's keys and values the first time it computes them and appends one entry per new token. Decoding then costs one new key and value per layer plus a read of everything stored. That read is the catch: the cache is read in full for every generated token, and at batch sizes that fit in memory the decode step is limited by memory bandwidth, not arithmetic (the case is made with numbers on {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}).

KV bytes per token = 2 (K and V) x layers x KV heads x head_dim x bytes per number tiny GPT, MHA: 2 x 6 x 8 x 32 x 2 (bf16) = 6,144 bytes per token -> 1.5 MiB at its 256-token context Llama 3.1 8B: 2 x 32 x 8 x 128 x 2 = 131,072 bytes (128 KiB) -> 16 GiB at 131,072 tokens, per sequence

What it costs, when it matters. The cache grows linearly with context and with batch, and for every token decoded the whole thing streams through the chip. At short context and small batch the weights dominate memory traffic; at long context or large batch the cache does (the {{Config calculator|#t-calc}} finds Llama 3.1 8B's attention reads equal its weight reads at about 28,600 cached tokens). Every variant below shrinks one factor of the formula: GQA and MQA shrink "KV heads", MLA replaces "2 x KV heads x head_dim" by one small latent, sliding windows cap the number of tokens a layer keeps, sparse attention keeps everything but reads only part of it, and state-space layers keep a fixed-size state instead (the {{Reading tab|#t-read}}'s section 10).

How to check it. Count it from the config (the formula above, or section 8), then confirm in the serving engine's startup log, which reports the KV cache memory and the number of tokens it can hold (vLLM prints both); the two disagree when the engine pads blocks or the config has windows you did not credit.
