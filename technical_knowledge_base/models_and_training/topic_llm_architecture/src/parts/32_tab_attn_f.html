Common mistakes

Interview questions

Why does decoding need a KV cache, and why is a decode step memory-bound?
A token's keys and values at a layer never change in a causal decoder, so they are computed once and stored; without the cache, step t recomputes t projections per layer. With it, each step does a little arithmetic per byte read: each cached number (2 bytes in bf16) is multiplied and added once by each query head that shares it, so attention does about (query heads / KV heads) FLOPs per byte read: 1 for MHA, 4 for Llama 3's GQA, and batching does not raise it because every sequence has its own cache. A datacenter GPU needs hundreds of FLOPs per byte to be compute-bound ({{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}), so the step waits on memory. Section 5 measures it.
Compute the KV cache of Llama 3.1 70B for one 128K-token request.
GQA, MQA or MLA: what does each give up?
GQA shares keys and values inside groups of query heads: a small quality cost, no new parts, every kernel supports it (DeepSeek's 7B ablation still shows GQA-8 below MHA on hard benchmarks, section 4). MQA is the extreme: the largest saving and the largest quality cost, and with tensor parallelism the single KV head is replicated on every GPU, so the per-GPU saving shrinks. MLA stores a compressed latent: the cache of a few KV heads with quality at or above MHA in DeepSeek's runs, paid for with extra projections, a decoupled RoPE key, custom kernels and, because the latent is shared by all heads, no way to split the cache across tensor-parallel ranks by head (derived from the design). GQA is the default when you want boring; MLA when the cache dominates the bill.
Why does MLA need a separate RoPE key?
At decode, MLA folds the key up-projection into the query (absorption), so attention runs directly against the cached latent. RoPE rotates keys by a position-dependent matrix that would sit between the up-projection and the query, and a matrix that changes with position cannot be folded into a fixed one. So the position information gets its own small key (64 numbers in DeepSeek-V3), shared by all heads and cached beside the latent, while the latent part carries no rotation. The step-by-step version is on {{DeepSeek|n:3c65c17b0d0d81a2ae7ec6796947a235}}.

Sliding window or sparse attention for long context?
A window caps memory and reads but forgets: anything older than the window must be relayed through layers, which models often fail to learn, so designs keep some global layers (Gemma 3 1 in 6, gpt-oss 1 in 2). Sparse attention (NSA, DSA) keeps everything and reads a learned subset, so it can still retrieve one old token, but the cache is as large as before and the selector costs something at every step. Windows when memory is the limit, sparse attention when reads and long-range recall both matter, and often both together with GQA or MLA underneath.

10. The code

Every number in this tab came from the scripts in src/attn/ and the shared tiny GPT in src/data/. The cache is a few lines; the quotes from transformers are at the pinned v5.20.1, located by pattern (src/attn/extract_code.py).

How the runs were made, and how to rerun them

Training (MPS, under the shared bench lock, one run at a time): train.py --preset <p> --set pos=rope --steps 1500 then eval.py, for rope (MHA), gqa4, gqa2, mqa, mla, swa64, swa64_g3, with seed 1 repeats of MHA, MQA and MLA. Queue script: src/attn/run_train.sh; results summarised into src/attn/out/runs_summary.json by make_page_data.py.

Decode timing: src/attn/decode_bench.py (MPS, about two minutes) writes out/decode_bench.json. Serving with a sliding cache, sinks, the GQA expansion bug: src/attn/cpu_evals.py (CPU, a few minutes) writes out/cpu_evals.json. Error messages: src/attn/sdpa_errors.py. Page data: make_page_data.py writes parts/32_js_at_0data.js; check_data.py checks the page against the recorded files.
