3. Attention, and why it needs a cache

The problem. A token's meaning depends on earlier tokens ("it" needs its referent). Attention lets each position build its output as a weighted average of earlier positions' information, with weights the model computes from the content. Each position makes three vectors from its normalised residual stream: a query (what it is looking for), a key (what it offers to be found by) and a value (what it passes on if chosen). For one head:

Attention(Q, K, V) = softmax( Q K⊤ / √dh + M ) V
Q, K, V
T × dh matrices: one query, key and value row per position; dh is the head dimension (64 to 256 in current models)
Q K⊤
T × T scores: every query dotted with every key
√dh
a dot product of dh random terms has spread about √dh; dividing keeps the softmax from saturating into a one-hot as dh grows ({{Vaswani et al. 2017, section 3.2.1|https://arxiv.org/abs/1706.03762}})
M
the causal mask: 0 where a query may look (itself and earlier), minus infinity for later positions

A layer runs H heads in parallel, each with its own projections, so different heads can track different relations (the previous token, a matching earlier token, the subject of the sentence; the {{Inside a real model|#t-inside}} lab finds such heads in a trained model). Their outputs are concatenated and projected back to d.

Why a cache. In generation, the new token's query must be scored against the keys of every earlier token, and those keys and values do not change when a token is appended (the mask stops earlier positions from seeing later ones). So they are computed once and stored: the KV cache. Generation then splits into two phases. Prefill runs the whole prompt at once, a large matrix multiply, limited by arithmetic. Decode produces one token per step, and each step must read every weight and the whole cache from memory to do little arithmetic, so it is limited by memory bandwidth. The cache costs:

KV bytes per token = 2 × L × Hkv × dh × b
2
keys and values
L
layers that keep a cache
Hkv
key-value heads per layer (the attention variant decides this, section 4)
b
bytes per number: 2 in BF16, 1 in FP8
Predict: Llama 3.1 70B (80 layers, 8 KV heads of 128) serving one request at its full 128K context (131,072 tokens), cache in BF16. How big is that request's KV cache?
derived 2 × 80 × 8 × 128 × 2 = 327,680 bytes (320 KiB) per token, × 131,072 = 40 GiB, for one request. The weights are about 141 GB in BF16 (70.6 billion parameters × 2 bytes), so 4 such requests hold more cache than weights, and 32 would need 1.25 TiB. With full multi-head attention (64 KV heads) every number would be 8 times larger. At long context the attention design, not the parameter count, decides what a GPU can serve. ({{config|https://huggingface.co/unsloth/Meta-Llama-3.1-70B/raw/main/config.json}})

When it matters and how to check. Short prompts and small batches: the weights dominate memory and the cache barely matters. Long contexts, many concurrent requests or agents with long histories: the cache dominates. To check a running server, look at its reported KV-cache capacity in tokens (vLLM prints it at start-up); to check a design, compute the formula above. FlashAttention changes how attention is computed (tiled, never storing the T × T matrix), not how much is cached ({{FlashAttention|n:3c65c17b0d0d81e4a3e8e7a2c4771381}}).
