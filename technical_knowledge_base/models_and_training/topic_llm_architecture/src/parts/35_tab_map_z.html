Common mistakes when reading a config

Applying the GQA formula to an MLA model
DeepSeek-V3's config.json says num_key_value_heads: 128. Plugging that into 2 x layers x kv_heads x head_dim x 2 bytes gives 3,904 KiB per token (with 128-dimension values), about 3.8 MiB. MLA caches one latent of kv_lora_rank (512) plus one RoPE key of qk_rope_head_dim (64) per layer: 576 x 61 x 2 bytes = 68.6 KiB. The field is there for the code path that rebuilds heads; check for kv_lora_rank before using it.
Counting sliding-window layers at full cost
Gemma 3 27B stores 496 KiB per token if every layer is counted, which is 62 GiB for one 131,072-token sequence. 52 of its 62 layers keep only the last 1,024 tokens, so the real figure is 10.4 GiB. The per-token number is still right for the first 1,024 tokens; past the window the windowed layers stop growing.
Reading max_position_embeddings as the trained context
MiniMax-M1's config says 10,240,000 while its model card says it natively supports 1 million tokens. Qwen3 32B's config says 40,960 while the card says 32,768 natively and 131,072 with YaRN. The config field is the size the code allows; the trained and evaluated length is in the card or paper, and going past it needs the scaling the card names.
Reading a per-head key count off the wrong layers
Gemma 4 31B lists num_key_value_heads: 16 with head_dim: 256, but those apply to the 50 sliding layers. Its 10 global layers use num_global_key_value_heads: 4 of global_head_dim: 512 and store one tensor for both K and V (attention_k_eq_v). Counting all 60 layers the sliding way gives 960 KiB per token; the config's own layer types give 840 KiB.
Treating active parameters as the memory you need
gpt-oss-120b runs 5.1B parameters per token, but all 117B must sit in memory (the model card's point is that it fits one 80 GB GPU in its MXFP4 format). "17B" in Llama 4 Maverick's name is the active count; the total is 400B. Mixtral 8x7B is 46.7B in total, not 56B, because only the FFN is replicated eight times.

Notes on the data

  • Sources. Shapes come from each model's config.json on Hugging Face (copies in src/map/inputs/configs/, fetched 2026-10-18; gated Meta and Google repos read from public mirrors with the same shapes). GPT-3 and PaLM have no public config: their rows use the papers' tables. Dates, licences and parameter counts link to the model card, paper or announcement in each row's card; where a 2025 or 2026 date comes only from Sebastian Raschka's LLM Architecture Gallery (a third-party list, Apache 2.0) the row says "gallery".
  • Calculations. Every KV figure is derived: bf16, 2 bytes per number; full cost counts every cache-growing layer; "at 128K" credits windows. The figures agree with the gallery page's independent recalculation for every model the two share. DeepSeek-V4-Pro's compressed caches are not computed here.
  • Labels from configs. Attention, window and mixer labels are read from config fields; norm placement, QK-norm and activation come from the paper or card cited in the row (the configs rarely state them).
