Compute it in your head

Interview arithmetic. Each answer is computed live from the real config with the same code as the calculator, and shows the working. Rough mental numbers to carry: a 4096-wide layer's attention projections with 8 KV heads are about 42M parameters; a SwiGLU feed-forward block is 3df; BF16 is 2 bytes.

Checked against the checkpoints

The target is not the number in a model's name but the exact count of stored tensors that Hugging Face reports for each repository's safetensors files (read 2026-10-18 at the commit listed in src/calc/inputs/hf_param_counts.json). Those counts include things that are not the main model's parameters, so the check is: calculated main model + MTP layers + vision tower + anything else stored = Hub count, with every addition explained. The second check is the published headline: which way of counting rounds (or truncates) to the figure the vendor printed.

Common mistakes

Using the query head count for the KV cache
The cache holds nkv heads, not nh. For Llama 3.1 8B that is 8, not 32: 128 KiB per token in BF16, not 512 KiB. The {{KV-cache calculator|n:3fd5c17b0d0d81059ee1ce20c0326dc5#t-kv}} on Long context switches the same model to MHA to show the 4× difference.
Assuming head_dim = hidden_size / num_heads
Many configs set head_dim explicitly. Gemma 7B has 16 heads of 256 on a 3072-wide stream (16 × 256 = 4096 ≠ 3072); Qwen3 32B has 64 heads of 128 on a 5120-wide stream. hidden_size // num_attention_heads gives the wrong attention parameters and the wrong cache for both. Read head_dim when it is there.
Counting the embedding twice when it is tied
tie_word_embeddings: true means the output head reuses the input embedding matrix: count Vd once. It still costs 2Vd FLOPs per token as the head. And a tied checkpoint can still store both: Qwen3 0.6B's file saves lm_head.weight as its own tensor, which is why the Hub says 0.75B for a 0.6B model.
Calling all MoE parameters "active", or the active count "the model size"
A token uses k of E routed experts; all E must still be in memory. Mixtral 8x7B is not 56B (only the feed-forward blocks are replicated: attention, norms and embeddings are shared) and not 14B active (2 of 8 experts plus the shared parts is 12.9B). Vendors also differ on whether the active count includes the embedding and the head: the check table shows which convention reproduces each headline.
Reading a quantised checkpoint's size as its parameter count
The Hub's count of DeepSeek-V3 is 684.5B: 671.0B main model, 13.5B MTP layer, and 41.5M FP32 block-scale tensors that FP8 weights carry (one scale per 128 × 128 block). The same repository family is not consistent: the Hub counts the scale tensors for DeepSeek-V3 and V3.2-Exp but not for V3.2 or Kimi K2, although the files of all four contain them (checked in the shard headers).
Forgetting that GQA does not cut attention FLOPs
Sharing key/value heads shrinks the cache and the bytes read per step; every query head still scores every cached position. Long-context prefill is compute-bound on those scores whatever nkv is.
Treating a sliding-window or chunked layer as global
Gemma 3 27B keeps 5 of every 6 layers at a 1024-token window (512 on Gemma 3 1B); gpt-oss alternates 128-token windows with full attention; Mistral 7B v0.1 used a 4096 window everywhere. Their cache stops growing on those layers once the context passes the window, so a whole-model "KV per token × context" overstates them several times at long context.

Interview questions

Parameter count of a Llama-style model from its config?
Vd (embedding) + Vd if untied (head) + L × [d(nh + 2nkv)dh + nhdhd (attention) + 3df (SwiGLU) + 2d (norms)] + d. For Llama 3.1 8B this is exactly 8,030,261,248, the stored count.
FLOPs to train a 7B dense model on 2T tokens?
About 6ND = 6 × 7e9 × 2e12 = 8.4e22, plus the attention term (small at 4k context for a 7B model, a few percent). Use the active N for an MoE.
Why does decode at batch 1 run far below a GPU's peak FLOPs?
Each step reads every active weight once (2 bytes per parameter in BF16) for 2 FLOPs per parameter: about 1 FLOP per byte. An H100 SXM needs about 295 FLOPs per byte (989.5 TFLOP/s dense BF16 over 3.35 TB/s, NVIDIA's figures) to be compute-bound, so batch-1 decode is memory-bound by two orders of magnitude. Batching reuses each weight read across sequences; the cache does not batch, since each sequence reads its own. See {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}.
Design: serve 128k-token contexts at batch 32 on one 80 GB GPU. What attention?
Budget first: 32 × 131,072 = 4.2M cached tokens. After an 8B model's BF16 weights (16 GB), 64 GB is left: about 15 KB per cached token across all layers. Llama 3.1 8B's GQA cache is 128 KiB per token, 8.6× too much (550 GB for the batch); an FP8 cache halves that and still misses. DeepSeek-V3's MLA is 576 numbers per layer, but over 61 layers that is 69 KiB per token: it misses too. A hybrid with only a few attention layers fits: Nemotron-H 8B (4 attention layers out of 52) needs 16 KiB per token plus 99 MiB of recurrent state per sequence, 72 GB for the batch in BF16 (over) and 38 GB with an FP8 cache (fits beside the weights). So: few attention layers or windows on most of them, few KV heads, an FP8 cache, and then check quality on long-context evaluations, since that is what these savings cost. Every number here is from the calculator above.
Why did DeepSeek choose MLA, and what does it cost?
It caches one 512-wide latent plus a 64-wide shared RoPE key per layer (576 numbers) instead of 2 × 128 heads × 128: a cache per token about 57× smaller than MHA at the same head count. The cost is compute: decode scores every position against the 576-wide latent in every head, so attention FLOPs per position are larger than MHA's, and RoPE has to be split off into a decoupled key. See the {{MLA explainer|n:3c65c17b0d0d81a2ae7ec6796947a235}}.
Dense 8B or MoE 30B-A3B for the same serving budget?
The MoE costs fewer FLOPs per token (3.3B active) but needs memory for 30.5B parameters, and at large batches its decode steps read most experts, so its bytes per step approach the full model's. It wins when memory is plentiful and compute or latency at small batch is the limit; the dense model wins on a memory-limited device.
