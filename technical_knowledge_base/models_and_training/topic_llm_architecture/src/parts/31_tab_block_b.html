Where the FLOPs go: 2N, 6N and the attention term

The problem. “How much compute does a model need per token?” decides training budgets and serving cost, and it has a two-line answer once the block is clear. How it works. A weight matrix of shape (out, in) applied to one token is out x in multiply-adds, 2 x out x in FLOPs. Every matrix weight a token passes through is used exactly once, so the weights cost 2N FLOPs, N being the matrix weights a token touches (the input embedding is a row copy and costs nothing; a tied LM head is a matrix product and counts; in a mixture of experts only the active experts count). Attention adds work no weight accounts for: per layer, the query meets t keys (2 x d_attn x t) and the weights meet t values (the same again), so 4 x n_layer x d_attn x t for a token that sees t positions. The backward pass needs two products of the same size per weight (the gradient for the input and the gradient for the weight), so a training step is about 3x the forward: 6N per token when attention is small.

forward per token = 2N + 4 x n_layer x d_attn x t (t = positions attended) training per token = 3 x forward ~ 6N when 4 x n_layer x d_attn x t is small next to 2N

measured PyTorch’s FLOP counter (torch.utils.flop_counter.FlopCounterMode, torch 2.14.1, CPU) on one forward pass of the tiny GPT over the 256-token running sequence: 3,355,443,200 FLOPs, equal to the formula (2N x 256 = 2,952,790,016 for the weights plus 402,653,184 for attention), and the same exact match for the SwiGLU and GQA presets. Forward plus backward on 255 tokens: 10,022,307,840 against 3,340,769,280 forward, a ratio of 3.0. The counter sees the full 256 x 256 score matrix (the mask is added, nothing is skipped), so its attention term is t = 256 for every token; a causal kernel such as FlashAttention skips the masked half, which is the per-token average of t(t+1)/2 / t that the calculator uses for prefill. published Kaplan et al. 2020, Table 1 ({{arXiv 2001.08361|https://arxiv.org/abs/2001.08361}}, read 2026-10-18), writes C_forward = 2N + 2 n_layer n_ctx d_attn with N the non-embedding parameters, and drops the context term because it is “a relatively small fraction” when d_model > n_ctx / 12; with the backward pass “approximately twice the compute”, C ≈ 6N. Their single context term equals the two products here averaged over a causal context (each sees n_ctx/2 positions on average). Their N also leaves out the de-embedding (LM head), which they count apart (2 d_model n_vocab); the calculator below keeps it in 2N, which matters for small models with large vocabularies.

When it matters. For the tiny GPT (d_model 256) attention reaches 2N at 1,878 positions when decoding (3,754 averaged over a prefill); for Llama 3.1 8B (d_attn 4,096) at 28,628 (57,255); for a model whose attention layers all use a window (or for an SSM) the line never comes. A decoder-only layer of width d with a 4x FFN has 12 d² matrix weights (4 d² attention, 8 d² FFN), 24 d² FLOPs, against 4 d t for attention, so for the blocks alone the crossover is t = 6 d for one decoded token and t = 12 d averaged over a causal prefill, Kaplan’s n_ctx / 12 rule; the LM head and a wider FFN push it later. GQA does not move it: it shrinks K and V, not the queries that do the dot products. How to check. Wrap one forward in FlopCounterMode (it counts matrix products only) on the eager path, or compare a profiler’s matmul time to its attention-kernel time at two context lengths. What transfers. FLOP counts are properties of the architecture and transfer exactly; time does not, because decoding is limited by memory traffic (weights and KV cache read per token), not by FLOPs ({{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}).
