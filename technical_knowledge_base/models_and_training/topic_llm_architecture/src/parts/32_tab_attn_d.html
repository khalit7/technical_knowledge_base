6. Sliding windows, local and global layers, and attention sinks

The problem a window solves. GQA and MLA make each entry smaller; the cache still grows with every token. A sliding window of W tokens caps it: a layer keeps only the last W entries, in a ring buffer ("the keys and values for the timestep i are stored in position i mod W of the cache", {{Mistral 7B, section 2|https://arxiv.org/html/2310.06825}}). Information older than W can still travel, one window per layer: "hi can access tokens from the input layer at a distance of up to W x k tokens", about 131K for W = 4,096 over 32 layers (same source, vendor). That is a theoretical span: the information has to be relayed through intermediate tokens, and nothing guarantees a model learns to do it.

Local and global layers. Every recent design that uses windows keeps some full layers, so that long-range retrieval has a direct path. Gemma 3 uses "a pattern of 5 local layers for every global layer" with a span of "only 1024 tokens" for the local layers, introduced because of "the memory explosion of the KV cache" at 128K ({{Gemma 3 report|https://arxiv.org/html/2503.19786}}, vendor). gpt-oss alternates "banded window and fully dense patterns, where the bandwidth is 128 tokens" ({{gpt-oss model card|https://arxiv.org/html/2508.10925}}, vendor). Calculated from their configs with windows credited, at 131,072 tokens in bf16 derived: Gemma 3 27B stores 496 KiB per token by the formula but holds 10.41 GiB per sequence, against 62.00 GiB if all 62 layers were global; gpt-oss-120b holds 4.50 GiB against 9.00 GiB; Mistral 7B v0.1, whose 32 layers all use a 4,096-token window, holds 0.50 GiB against 16.00 GiB (the same arithmetic as the {{Architecture map|#t-map}}).

Attention sinks. Softmax weights must sum to one, so a head with nothing relevant to read still has to put its attention somewhere; trained models learn to park it on the first token, whatever that token is (StreamingLLM, {{Xiao et al. 2023|https://arxiv.org/abs/2309.17453}}). A sliding cache that evicts the first token removes the parking place, and the model breaks. The fix is to keep a few initial tokens forever, or to train with an explicit sink: gpt-oss gives "each attention head ... a learned bias in the denominator of the softmax ... which enables the attention mechanism to pay no attention to any tokens" (model card, vendor; the tiny GPT has the same switch as attn_sink). The {{Inside a real model|#t-inside}} tab measures sinks in SmolLM2-135M; here the question is what they mean for a cache.

Before and after: one trained model, served with a sliding cache

The full-attention MHA model of section 3 (trained on 256-token windows) is served as if its cache were a sliding window of W tokens: first evicting everything older than W, then keeping the first token (or the first four) as StreamingLLM does. The SWA-64 model, trained with its window, is the control. Loss is counted only at positions at or beyond W, where something has been evicted.

7. Sparse attention: keep everything, read a little

The problem. Windows forget; GQA and MLA still read every cached token at every step. Sparse attention keeps the whole cache but lets each query read only a chosen subset, which cuts decode reads and long-context FLOPs while leaving storage as it was. The hard part is choosing the subset cheaply and learning to choose it during training ("natively trainable"), rather than pruning a dense model afterwards.

  • NSA (Native Sparse Attention, {{Yuan et al. 2025|https://arxiv.org/abs/2502.11089}}, DeepSeek-AI and Peking University): three branches per query, "compressed coarse-grained tokens, selectively retained fine-grained tokens, and sliding windows for local contextual information", combined by learned gates, with kernels that load blocks of keys.   • DSA (DeepSeek Sparse Attention, DeepSeek-V3.2-Exp, then V3.2): a "lightning indexer" with a few heads scores every cached token for each query (ReLU scores, "can be implemented in FP8"), and the MLA attention then reads only the top-k entries. DeepSeek: DSA "reduces the core attention complexity of the main model from O(L2) to O(Lk)", while "the lightning indexer still has a complexity of O(L2)" but needs much less compute ({{DeepSeek-V3.2 technical report, section 2|https://huggingface.co/deepseek-ai/DeepSeek-V3.2/blob/main/assets/paper.pdf}}, vendor). The V3.2 config sets index_topk 2,048, index_n_heads 64 and index_head_dim 128 (read 2026-10-18). At 131,072 cached tokens a query reads 2,048 full entries, 1.6% of them, but the indexer still scores all 131,072 with its 128-number keys, so the read per step is smaller, not constant (derived). DeepSeek says it "deliberately aligned the training configurations of DeepSeek-V3.2-Exp with V3.1-Terminus" and reports "performance on par with V3.1-Terminus" ({{model card|https://huggingface.co/deepseek-ai/DeepSeek-V3.2-Exp}}, vendor; how long-context quality is measured independently is on {{Long-context and multimodal benchmarks|n:3ef5c17b0d0d810bb4dfc98919c9be8a}}).

When it matters, how to check. Sparse attention pays at long context (tens of thousands of tokens and up), where the read of the cache dominates the step; at 4K it mostly adds an indexer. Check by measuring decode time per token against context in the serving engine with the sparse kernels enabled, and by a long-context retrieval benchmark rather than perplexity, since a selector that misses the one needed token barely moves average loss. Not run here: both need CUDA kernels (FlashMLA, DeepGEMM) and models far beyond this Mac.
