The idea in one screen

Every model on this page is the same stack of transformer blocks with two dials set differently: the attention mask (which positions each position may read) and the objective (which tokens it is asked to predict, from what input). The mask decides what can be cached and whether the model can generate; the objective decides how much training signal each sequence gives. Multi-token prediction and diffusion attack the decoder's one-token-per-forward loop from opposite sides.

1. One block, four masks

Attention scores form a T by T matrix: row i is the query (the position asking), column j the key (the position read). The mask adds minus infinity to forbidden cells before the softmax, so their weight is exactly zero. Left unmasked, a model asked to predict token i+1 while it can see token i+1 learns to copy; the mask is how one architecture serves both understanding and writing. The first 12 tokens of the running sequence under each pattern:

Which keys each query may read, and what that lets you cache

The mask is free and decides the cache. Same FLOPs, same parameters. A causal model's past keys and values never change when a token arrives, so they are computed once and kept: the KV cache. Under a bidirectional mask every new token changes every earlier position's output, so an encoder or a diffusion LM recomputes the whole sequence every pass. An encoder-decoder's decoder caches its own causal KV plus the cross-attention keys and values of the encoder output, computed once per input; T5Gemma 2 fuses the decoder's self- and cross-attention into one attention with one mask.

A mask is a training-time contract. We took the reference tiny GPT, trained causally, and changed only the mask at inference (src/lab/masks.py, the topic's 20 fixed held-out batches of 32 windows, 640 windows of 256 tokens; correction: the 2026-10-18 page said "20 windows", checked against the script). Predict first: with a bidirectional mask the model can see the very token it must predict. Does its loss go down?

The code that ran. The topic's tiny GPT builds an additive mask in attn_bias (root src/data/tiny_gpt.py); this page swaps in a version with a mode switch without editing the shared file (src/lab/fo_common.py):

MASK = {"mode": "causal", "prefix": 0}

def attn_bias(cfg, layer_idx, q_pos, k_pos, device, slopes=None):
    diff = q_pos[:, None] - k_pos[None, :]
    if MASK["mode"] == "causal":
        keep = diff >= 0
    elif MASK["mode"] == "bidir":
        keep = torch.ones_like(diff, dtype=torch.bool)
    elif MASK["mode"] == "prefix":
        keep = (diff >= 0) | (k_pos[None, :] < MASK["prefix"])
    return torch.zeros(keep.shape, device=device).masked_fill(~keep, float("-inf"))[None]

def enable_masks():
    tiny_gpt.attn_bias = attn_bias
    tiny_gpt.is_local = lambda cfg, li: True   # forces the explicit softmax path (SDPA would apply is_causal)


Output of masks.py (scrubbed of timings), Apple M1 Pro, CPU, torch 2.14.1. The is_local override matters: the tiny GPT's fast path calls F.scaled_dot_product_attention(..., is_causal=True) and would ignore any custom mask.

Which positions are masked or corrupted is one seeded draw (illustrative positions); the rules are the real ones.




    

  • Causal LM (CLM). Target: the text shifted left by one; a 256-token window gives 255 loss terms (the topic's trainer reads 257 tokens and scores all 256). It won because every token of every document is a training example, any task can be written as a prompt, and the model generates with the same forward it was trained with; Pretraining runs it at scale. The costs: a strict left-to-right loop at inference and no right-hand context for the token being predicted.
    • 

  • Masked LM (MLM). BERT (BERT paper page) picks 15% of positions; of those, 80% become [MASK], 10% a random token, 10% stay unchanged, because [MASK] never appears at fine-tuning and a model that only sees [MASK] at scored positions learns nothing useful about real tokens there. transformers 5.20.1 keeps these defaults in DataCollatorForLanguageModeling: mlm_probability = 0.15, mask_replace_prob = 0.8, random_replace_prob = 0.1 (data/data_collator.py lines ). The cost is signal: about 38 loss terms per 256-token window against CLM's 255. ELECTRA (Clark et al. 2020, ICLR 2020) answered with replaced-token detection, where "the task is defined over all input tokens rather than just the small subset that was masked out"; ModernBERT raised the masking rate to 30%.
    • 

  • Span corruption (T5). Contiguous spans are replaced by one sentinel each (<extra_id_0>, ...); the target is each sentinel followed by the tokens it replaced. T5's default corrupts 15% in spans of mean length 3 (T5 paper page, whose Corrupt a sentence tab runs T5's own preprocessing). Per 512 input tokens the target is  tokens ( corrupted,  sentinels, one end token), so the decoder, the expensive autoregressive half, works on about a fifth of the text.
    • 

  • Prefix LM, MTP and masked diffusion have their own sections (6, 7, 8). Masked diffusion is MLM with the rate drawn at random between 0 and 1 per sequence and each term weighted by one over it: at rate 0.15 it is exactly BERT's objective, and the random rate is what makes it a generator.

How this happens in real code
Writing your own attention with F.scaled_dot_product_attention(q, k, v) and forgetting is_causal=True (the default is False); passing a padding mask and assuming it also makes attention causal; or loading a decoder checkpoint into an encoder class. The symptom is always the same: a training loss far below anything plausible for the data (here  nats per token on stories whose honest loss is about 2.3), then nonsense at generation. A loss that is too good is a bug until proven otherwise.







4. Encoders: both sides of every token


Many jobs never generate text: embed a query and a million documents and find the nearest, label a ticket, score whether a passage answers a question. For those the best representation of each token uses the words on both sides, in one forward pass. An encoder is the same stack with a bidirectional mask, trained with MLM; a task head reads its per-token vectors: a pooled vector for classification and embedding models, a relevance score over a concatenated query and document for a cross-encoder reranker, per-token labels for tagging.


Measured: both sides win, once the model has learned to use them. The masked diffusion model of section 8 is, at a fixed rate, an MLM encoder adapted from the reference tiny GPT. We hid a fixed random 15%, 50% or 90% of 16 held-out windows and asked it to recover them in one bidirectional pass; the causal reference predicted the same positions from the true left context (every real token before the blank, which the encoder is not given). Predict: at 90% hidden, which wins?


Both sides beat the left side only when most of both sides is visible


Top-1 accuracy on the hidden positions, measured on Apple M1 Pro (CPU), src/lab/diff_eval.py, after  adaptation steps.


At 15% hidden the encoder beats the causal model clearly; at 90% the order reverses, because the encoder sees almost nothing while the causal model still sees the true past. That is why MLM masks a small share, and why a diffusion LM's first steps, with almost everything masked, are its least certain. Turning right-hand context into accuracy has to be learned: after the first  adaptation steps the encoder did not yet win at 15% ( against the causal ). At full pretraining the gap is the same sign: BERT Table 5 gives 87.9 against 77.8 F1 on SQuAD dev for the same model trained left to right.


What changed since BERT. RoBERTa dropped next-sentence prediction (which the BERT paper page treats as unproven: one run, reversed by RoBERTa) and trained longer on more data with dynamic masking. ModernBERT (December 2024) brought the decoder era's parts into an encoder: RoPE, GeGLU, alternating global and 128-token sliding-window layers, MLM at 30%, 2 trillion tokens at native context 8,192; base about 149M parameters, large about 395M. Ettin (Seq vs Seq paper page, July 2025) trained encoders and decoders in pairs on the same data and recipe from 17M to 1B: encoders win classification and retrieval, decoders win generation, at every size, and 50B tokens of continued training on the other objective closes neither gap (the 400M encoder reaches 91.3 on MNLI against the 1B decoder's 89.9).


Cost and how to check. An encoder forward costs about 2N FLOPs per token (N parameters), like a decoder's prefill, with no KV cache afterwards; at 149M parameters it embeds a chunk in one pass on a CPU. Size buys a decoder-as-embedder its lead back only at large ratios (the Ettin paper page puts the largest ratio a native model wins at 2.7x, against the abstract's "10x"). An encoder's config names a ...ForMaskedLM or ...Model class rather than ...ForCausalLM, its attention sets is_causal = False, and its tokenizer has a [MASK] (or <mask>) token; model.generate either fails or produces filler.

5. Encoder-decoder: T5 to T5Gemma 2


A bidirectional encoder reads the input once; a causal decoder writes the output, and in every block a cross-attention layer lets each output position read every encoder vector (the encoder-decoder view of the mask figure in section 1). The input can be long and fully bidirectional while generation stays causal.


Twice the parameters, the same FLOPs. T5 compared architectures at equal compute (Table 2 of T5): a 12 + 12 layer encoder-decoder has twice the parameters (2P) of a 12-layer decoder yet the same FLOPs (M) over an input plus target of the same total length, because each token passes through only one 12-layer stack:

Published, T5 Table 2 (arXiv 1910.10683; values as printed in the T5 page's tables.json), 220M-class models, one run each; the T5 page puts the paper's run-to-run noise at a fraction of these gaps. With fine-tuning on understanding-heavy benchmarks, bidirectional reading of the input was worth about 7 to 8 GLUE points over a causal decoder in 2019.


Why decoders won anyway. Wang et al. 2022 (arXiv 2204.05832, models over 5B parameters on 170B tokens) found that after purely unsupervised pretraining causal decoders have the strongest zero-shot generalisation, while non-causal MLM models win only after multitask fine-tuning. A general assistant answers anything zero-shot and writes long outputs from short prompts, and one stack makes caching, batching and serving simpler.


Where encoder-decoders still win: long input, short output tied to it: translation, summarisation, speech recognition (Whisper: "We chose an encoder-decoder Transformer", Radford et al. 2022, section 2.2). T5Gemma and T5Gemma 2 (paper page) build encoder-decoders by copying a pretrained decoder's weights into both stacks and continuing with UL2 or PrefixLM: after instruction tuning the 2B-2B beats Gemma 2 2B by 7.1 points (46.1 against 39.0); the unbalanced 9B-2B decodes at about 1.05x Gemma 2 2B's latency with much higher accuracy on GSM8K; T5Gemma 2's 4B-4B scores 81.7 on RULER 32K against Gemma 3 4B's 66.8 although pretrained at 16K (57.6 against 51.7 at 128K). The paper page's verdict: the direction is believable, the sizes are single runs from models with about twice the parameters.







6. Prefix LM and mixtures of objectives (UL2)


A prefix LM is a decoder with the prefix mask of section 1: prompt read bidirectionally, continuation causally, only the continuation scored. It buys most of the encoder-decoder's gain with one stack (T5 Table 2: 81.82 against 83.28 GLUE; the causal LM 74.70). The price is at inference: the prompt's keys and values depend on the whole prompt, so a prompt cannot be extended without recomputing its cache, which breaks the multi-turn and prefix-caching tricks serving relies on (Batching, KV cache and scheduling). And it has to be trained as one: our causal checkpoint run with a 128-token prefix got worse even on the scored suffix (section 1).


UL2 (Tay et al., arXiv 2205.05131) mixes three denoisers in one run, each announced by a mode token: R (regular span corruption, mean spans 3 and 8 at 15%), S (sequential: one span covering the last quarter of the input, which is prefix LM), X (extreme: spans of 64 tokens or corruption at 50%). Its 20B model reported beating 175B GPT-3 on zero-shot SuperGLUE (vendor, 2022). UL2 survives as the adaptation objective of T5Gemma.






7. Multi-token prediction (MTP)


Next-token prediction asks each position about one token, so a model can do well on local patterns without planning; and at inference the decoder makes one forward per token, each limited at small batch by reading the weights from memory, not by arithmetic (Performance math). Multi-token prediction adds loss terms for tokens two or more places ahead: a denser training signal, and a ready-made guess for the next forward to check.


Two ways to predict the token after next: the sequential module is told the next token








    

  • Parallel heads (Gloeckle et al., arXiv 2404.19737, April 2024): n independent one-layer heads on a shared trunk and unembedding; head k predicts t+k from the trunk's state at t alone. Heads run forward and backward one at a time, so peak memory stays O(V + d) instead of O(nV + d). vendor (Meta): at 13B, 12% more HumanEval and 17% more MBPP problems solved; "worse than the baseline for small model sizes, but outperform the baseline at scale"; n = 4 best for token-level code; as drafts, 3.0x faster decoding on code and 2.7x on text.
    • 

  • Sequential module (DeepSeek-V3, arXiv 2412.19437 section 2.2): depth k takes the previous depth's state and the embedding of the known token ti+k, so the chain stays causal (the paper compares it to EAGLE). DeepSeek-V3 uses D = 1 and weights the loss by λ = 0.3 for the first 10T tokens and 0.1 for the remaining 4.8T.

8. Diffusion language models


A decoder writes 48 tokens in 48 forwards, each waiting for the last. An image diffusion model starts from noise and refines the whole picture at once over a fixed number of steps (Diffusion from zero teaches it for pixels). A diffusion language model does the same for text with masking as the noise: start from a row of [MASK] tokens and fill in several per forward, in any order. Here is ours (the reference tiny GPT adapted into one, below) writing the same 48-token continuation of the running sequence's opening that the causal model writes token by token. How it works: masked diffusion from zero


    

  1. Forward process (the noise). Pick a time t between 0 and 1 and hide each token independently with probability t: clean at t = 0, all [MASK] at t = 1.
    2. 

  2. The model is a bidirectional transformer (an encoder) that reads the partly masked sequence and predicts the original token at every masked position.
    3. 

  3. The loss (LLaDA, Nie et al., arXiv 2502.09992): cross-entropy on the masked positions only, each weighted by 1/t, averaged over the sequence length. The weight makes the sum an upper bound on the negative log-likelihood; MDLM (Sahoo et al., NeurIPS 2024) calls it "a mixture of classical masked language modeling losses". Fix t = 0.15 and you have BERT; draw t at random and the model learns every stage from nearly clean to fully masked.
    4. 

  4. Sampling (the reverse process), what the figure steps through: start with the prompt followed by L masks; each step, predict every masked position, commit some and leave the rest masked. LLaDA commits the most confident ones (low-confidence remasking). With L tokens and K steps it commits L/K tokens per forward.
    5.

Why 1/t: at rate t the expected number of masked tokens is tL; dividing by t makes every rate contribute a comparable per-sequence term, and the result bounds the likelihood, so training it is maximum-likelihood training of a generative model rather than a fixed-rate MLM. The bound is not a perplexity: our adapted model's  and the causal model's 2.28 are not the same kind of number.

Committing more tokens per forward from the same, partly masked context lowers quality. Random remasking instead of confidence order is clearly worse at 48 steps ( against ), as in LLaDA's own ablation, but at 12 steps it is better here ( against ): committing the 4 most confident slots at once tends to pick the same easy pieces in neighbouring places, which random order avoids. LLaDA's table is at one step per token; this toy does not test it at few steps. The tiny model is small and briefly adapted: read the ordering, not the gap to AR.


Real bad output: parallel commits do not coordinate
The causal model continues prompt 7 with "". The diffusion model at 12 steps writes "". Our tokenizer splits the name Roxy into pieces (R, o, x, y), and each step predicts every masked slot independently given the current context, so slots filled in the same step cannot agree: the name comes out as fragments ("R", "Ro", "Roy") and confident common pieces land side by side ("named named"). This conditional-independence cost grows with tokens per step, which is why fewer steps lose quality and why production systems commit in small blocks with confidence thresholds.


What it costs


Every diffusion step is a full bidirectional forward over prompt plus answer, and nothing can be cached between steps because every position's keys change as tokens are committed ("LLaDA is incompatible with KV caching"). So diffusion trades more FLOPs for fewer sequential forwards: worth it when decoding is memory-bound (one user, small batch), not when a server is already compute-bound at large batch. For the 48-token continuation of an -token prompt, 12 diffusion steps process  token positions against the AR decoder's  (derived; the counter in the figure). Block diffusion (Arriola et al., ICLR 2025) fixes the caching problem: generate blocks left to right, diffuse inside each block, cache the finished ones. DiffusionGemma uses the same block-AR idea; its paper page runs that sampler on its own toy.

9. Choosing


    

  • Generate open-ended text, follow instructions or reason: a decoder-only model. If it ships MTP weights, use them as the draft; if you pretrain at billions of parameters, a depth-1 sequential MTP loss is a cheap addition (one block, λ around 0.1 to 0.3) that you can drop at inference, judged at equal compute.
    • 

  • Vectors or labels for a lot of text, cheaply: an encoder (ModernBERT-class, 150M to 400M), fine-tuned for the task. At equal size and data it beats a decoder used as an embedder (Ettin).
    • 

  • Long input, short output tied to it (translation, summarisation, speech): consider an encoder-decoder, ideally adapted from a decoder you trust (T5Gemma 2); an unbalanced large encoder with a small decoder buys quality at small-decoder latency.
    • 

  • One user, latency first, quality tax acceptable: a block-diffusion LM. At high concurrency a batched AR server with speculative decoding is the better use of the GPU.
    •

Interview rehearsal: six questions and three design questions (optional)


Why did decoder-only models win over encoder-decoders?
One objective that makes every token a training example and every task a prompt; the strongest zero-shot generalisation after unsupervised pretraining (Wang et al. 2022); one stack, one cache, simple batching and prefix caching. Encoder-decoders still win input-heavy tasks at equal compute (T5 Table 2).


Why can't you generate well with BERT?
It was trained to fill a few blanks given almost all of the context; generation starts with no right context at all and needs many tokens committed in a sensible order. A masked diffusion model is the same architecture trained at every masking rate, which is exactly what fixes this.


An encoder-decoder has twice the parameters of a decoder. Does it cost twice as much to run?
No: each token passes through one stack, so at equal total length the FLOPs are about the same (T5 Table 2: 2P parameters, M FLOPs for both). Memory for weights doubles; the decoder caches its own KV plus cross-attention KV computed once from the encoder.


What does DeepSeek-V3's MTP module see, and why does that matter for drafting?
The main model's last hidden state at i and the embedding of the true token i+1; one block and the shared head predict i+2. Knowing i+1 makes its guess much better than a parallel head's (measured here: top-1  against ), so as a draft it is accepted often (85 to 90% in DeepSeek's report) and gives up to 2 tokens per forward.


With a depth-1 draft accepted with probability a, how many tokens per forward?
1 + a for one draft token per forward (each forward always yields the verified token, plus the draft when accepted); DeepSeek's 0.85 to 0.9 gives 1.85 to 1.9, close to their reported 1.8x TPS. With chained depth-k drafts accepted independently, 1 + a + a² + ... + ak.


Design: classify 50 million support tickets a day and draft a reply for the 1% that need a human.
A fine-tuned encoder (ModernBERT-base class, about 150M parameters) for the classification: one forward per ticket, batched on CPUs or one small GPU, no generation. A decoder-only model only for the 500k drafts, with MTP or a draft model for latency, prompted with the classifier's label and retrieved replies (an encoder again, as the embedder). Using the decoder for both would cost hundreds of times more per ticket for worse classification at equal size (Ettin).


Design: code completion in an editor, one user, under 100 ms for 30 tokens on one GPU.
Decode is memory-bound at batch 1, so cut sequential forwards. Options: an AR model with its MTP heads or an EAGLE-style draft (1.5 to 3x, exact distribution, easy to serve); a block-diffusion model (DiffusionGemma reports about 20 tokens per forward at one request, with a quality tax); or a smaller model. Measure acceptance on real completions first: code is repetitive, so drafts are accepted often. Revisit at high concurrency, where batching beats both.


Design: you are pretraining a 30B decoder. Would you add MTP, and how would you know it helped?
Yes, depth 1, sequential, λ about 0.3 then 0.1, shared embedding and head: about one extra block of compute per step and no inference cost. Know it helped by an equal-compute ablation (not equal tokens: the module adds FLOPs) at two scales on code, maths and knowledge benchmarks, several seeds or at least the noise of reruns, and the draft acceptance rate as a bonus. Our tiny run shows why equal compute matters: the module added  FLOPs per step.
