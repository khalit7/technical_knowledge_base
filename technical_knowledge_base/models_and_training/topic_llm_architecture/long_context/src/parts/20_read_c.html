1. Why every token of context costs memory and compute

The problem. A decoder generates one token at a time, and each new token's attention needs the keys and values (the K and V vectors every earlier token produced in every layer). Recomputing them for the whole prefix at every step would cost a full forward pass over the context per token, so engines keep them: the KV cache. It is the only part of a running transformer that grows with the context. The root explains why the cache exists ({{Topic: llm-architecture|n:3fd5c17b0d0d8172b490dc9f9ac281df}}, section 3, and its Attention lab); this page is about what happens when the context gets long.

KV bytes per token = 2 × layers × KV heads × head dim × bytes per number
2
one key and one value
KV heads
the number of distinct key/value heads (8 in Llama 3.1, against 32 or 64 query heads)
bytes
2 in bf16, 1 in fp8

How big it gets. Llama 3.1 8B (32 layers, 8 KV heads of 128) stores 2 × 32 × 8 × 128 × 2 = 131,072 bytes, 128 KiB, per token. At its advertised 131,072 tokens that is 16 GiB for one sequence, as much as its 16.06 GB of bf16 weights; Llama 3.1 70B needs 320 KiB per token, 40 GiB per 128K sequence derived (the root's {{Config calculator|n:3fd5c17b0d0d8172b490dc9f9ac281df}}, which reconciles these configs with their Hub parameter counts exactly). Concurrency multiplies it: on one 80 GB GPU, after the 8B model's weights, three 128K sequences fit, and thirteen at 32K derived, the {{Memory wall|#t-wall}} tab's defaults.

Why it is slow, not only big. Decoding reads the whole cache once per generated token: each cached number is used for two multiply-adds (one score, one weighted sum), far too little arithmetic per byte to keep a GPU's compute units busy, so decode speed is set by memory bandwidth ({{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}} has the roofline). At 128K tokens the 8B model reads 16 GiB of cache per sequence per step on top of its 16 GB of weights; batching shares the weight read across sequences, never the cache read.

Compute grows faster than memory. Reading a prompt (prefill) costs every token's attention over all earlier tokens, so the attention FLOPs of a prompt grow with the square of its length, while the weight FLOPs grow linearly. For Llama 3.1 8B a decode step's attention FLOPs equal its weight FLOPs at about 28,600 cached tokens, and at 131,072 tokens attention is 70% of the prefill's FLOPs derived (root Block lab and Config calculator; the Memory wall's compute panel shows any model).

The four walls (the root's section 9, in one line each)

Memory: the cache grows linearly with context and concurrency. Compute: prefill attention grows with the square of the prompt. Position: positions past the trained length were never seen. Use: a model that fits and runs a long prompt may still not use it. Sections 2 to 5 take the first two, section 6 the third, section 7 the fourth.

Predict. Llama 3.1 70B goes from 8 KV heads to MQA (one KV head). At 128K tokens on eight 80 GB GPUs, how many more sequences fit, and how much faster does a 128K prefill get?
The cache shrinks by the number of KV heads removed (8 to 1), so about eight times the sequences fit once the weights are paid for (10 at 128K as configured; the Memory wall gives the exact count). Prefill FLOPs barely move: attention FLOPs are set by the 64 query heads and the positions each reads, not by how many distinct keys are stored. Fewer KV heads cut memory and decode bandwidth; only windows, sparsity or a different mixer cut prefill compute.

How to check it. Compute 2 × num_hidden_layers × num_key_value_heads × head_dim × bytes from config.json (watch for sliding_window, layer_types and MLA's kv_lora_rank, which change the sum), multiply by context and concurrency, and compare with the GPU's memory after weights. In a running vLLM server the metric vllm:kv_cache_usage_perc shows how full the cache is ({{Batching, KV cache and scheduling|n:3c65c17b0d0d819db53bd2c48909e5b2}}).
