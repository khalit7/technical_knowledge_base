2. Slow, not only big: decode reads it, prefill squares it

Decode is bandwidth, prefill is compute. Every generated token reads the whole cache once: each cached number feeds two multiply-adds (one score, one weighted sum), far too little arithmetic per byte to keep a GPU busy, so decode speed is set by memory bandwidth (about 1 FLOP per byte for MHA in bf16 against an H100's balance of about 295; {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}} has the roofline). Cache bytes are decode time. Reading a prompt is the other wall: every token's attention over all earlier ones, so a prompt's attention FLOPs grow with the square of its length while its weight FLOPs grow linearly. Memory and compute are different walls, moved by different levers.

Fig. 2: rows are queries, columns are keys, so one cell is one query-key pair of one head in one layer; 12 tokens are drawn (illustrative), and the shares quoted are Llama 3.1 8B's at real lengths derived with the root's calc.py.

  1. Prefill: a triangle of pairs. Reading a prompt, each token's query meets the key of itself and every earlier token: the causal triangle holds T(T+1)/2 pairs, about 8.6 billion per head per layer at 131,072 tokens. All rows are computed in one parallel pass, so prefill is limited by arithmetic, not memory.
  2. A line against a square. Each token also passes once through the weights (the bar beside its row, the same for every token). Weight FLOPs grow with T, attention FLOPs with T²: attention is 7% of a 4,096-token prefill of Llama 3.1 8B and 70% of a 131,072-token one.
  3. Decode: one new row, the whole cache read. A generated token adds one row: its query reads every cached key and value once (the stream from every column) and the weights once more (the plate). At 128K tokens Llama 3.1 8B reads 16 GiB of cache per sequence per step on top of its 16 GB of weights.
  4. Each row is one longer. The context grows by one with every decoded token, so every step reads one more entry while the weight read stays flat: attention's share of decode FLOPs passes half at about 28,600 tokens and is 82% at 131,072.
  5. Batching shares the weights, never the cache. Four sequences decode together: one read of the weights serves all four, but each reads its own cache, so at long context the cache read sets the step time and batching stops helping.

The two walls cross at different lengths: the chart beside gives attention's share of the FLOPs per token for both phases. In decode the cache read already costs more bytes than the weights before 128K; in prefill the square wins later, because the average prompt token reads only about half the prompt.

Predict. Llama 3.1 70B goes from 8 KV heads to MQA (one KV head). At 128K tokens on eight 80 GB GPUs, how many more sequences fit, and how much faster does a 128K prefill get?
The cache shrinks by the KV heads removed (8 to 1), so about eight times the sequences fit once the weights are paid (10 at 128K as configured). Prefill FLOPs barely move: attention FLOPs are set by the 64 query heads and the positions each reads, not by how many distinct keys are stored. Fewer KV heads, fewer bits and eviction cut memory and decode reads; only windows, sparsity or a different mixer cut prefill compute.

3. Smaller entries: fewer KV heads, a latent, fewer bits

Three levers shrink each token's entry and keep every token.

Fewer KV heads (GQA, MQA): query heads share keys and values. Llama 3.1's 8 KV heads for 32 (8B) or 64 (70B) query heads already cut the cache 4 or 8 times against MHA; MQA goes to one. Small quality cost when done in training or uptraining (GQA paper).

A compressed latent (MLA): DeepSeek-V3 caches 576 numbers per layer whatever its 128 heads, 68.6 KiB per token over 61 layers in bf16, against 3.81 MiB for MHA at the same shape: about 57 times fewer, the size of GQA with only 2.25 groups. Both mechanisms are drawn in 3D on {{Attention variants|n:3fd5c17b0d0d8120859ecc2d0236e846}} (Figs. 3 and 4; the MLA before and after was first built for the {{DeepSeek|n:3c65c17b0d0d81a2ae7ec6796947a235}} page): it animates the mechanism, this page sizes it.

Fewer bits per number (KV quantisation): keys and values in 8, 4 or 2 bits with a scale per group of numbers. It needs no retraining, which is why engines ship it (FP8 in vLLM and SGLang; q8_0 and q4_0 in llama.cpp, measured on Qwen3-1.7B on {{Batching, KV cache and scheduling|n:3c65c17b0d0d819db53bd2c48909e5b2}} section 8). It halves (fp8) or quarters (4-bit) memory and decode reads at once, and composes with every other lever.

The chart beside is KIVI's finding: "the key cache should be quantized per-channel" and "the value cache should be quantized per-token" ({{Liu et al. 2024|https://arxiv.org/abs/2402.02750}}). Measured here on SmolLM2-135M (section 4's pass-key test): 8 bits are free (97% against 97% full), 4 bits nearly free (KIVI layout 93%), and 2 bits need keys per channel (50% against 7% per token) and still lose half. measured Check retrieval at your length, not perplexity, and the key statistics beside on your model.

All the quantisation numbers, KIVI's claims, and the MLA headline reconciled

KIVI makes 2-bit caches workable ({{Liu et al. 2024|https://arxiv.org/abs/2402.02750}}; the authors report "2.6× less peak memory (including model weight)", up to 4 times larger batches and 2.35 to 3.47 times the throughput; authors' claims, not run here). Measured here on SmolLM2-135M at 4,096 tokens, 30 pass-key prompts (section 4 has the test): full cache 97%; int8 per token 97%, int4 87% (KIVI layout 93%), int2 7% per token against 50% with keys per channel (and the new-story loss rises to 2.45 per token against 2.22). 8 bits are free, 4 bits nearly free, 2 bits need the per-channel layout and still lose half. measured How to check: retrieval at your length, not perplexity, plus the key statistics above on your model.

MLA at DeepSeek-V3's shape against 8-group GQA: 244 KiB per token. Per sequence at 131,072 tokens: 8.58 GiB, where MHA would need 488 GiB.
