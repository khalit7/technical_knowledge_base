Long context: KV cache growth and compression, local and global attention, effective context

What every token of context costs in memory and compute, how to size the KV cache of any model, the levers that shrink it (smaller entries, fewer entries, local layers) and what each costs in quality, and why the context a model accepts is not the context it uses. Reading: 22 min, plus 13 in closed details. Data as of October 2026.
The idea in one sentenceEvery token a transformer has read leaves a key and a value in every attention layer, so the KV cache grows in a straight line with the context at a rate the architecture fixes; long context is the craft of lowering that rate (or the number of tokens kept), and then proving the model still uses what it kept.

KV cache: the keys and values of every earlier token, per layer, kept so decoding does not recompute them.
Prefill / decode: reading the prompt in one pass / generating one token at a time against the cache.
Local (sliding-window) layer: attends to the last W tokens only, so its cache stops at W entries; a global layer keeps all.
Eviction: dropping cached entries by a score; attention sink: the first tokens, which soak up attention and must be kept.
Position wall: the loss rising past the trained length, where RoPE angles were never seen.
Effective context: the longest input at which the model still does a given task well; measured, never read from a config.

1. What one token costs

The numbers first. Llama 3.1 8B has 32 layers, each with 8 KV heads of 128 numbers (its 32 query heads share them). One token therefore stores 2 (K and V) × 32 × 8 × 128 = 65,536 numbers, 2 × 32 × 8 × 128 × 2 = 131,072 bytes in bf16: 128 KiB per token. At its advertised 131,072 tokens that is 16 GiB (17.18 GB) for one sequence, as much as its 16.06 GB of bf16 weights; one 80 GB GPU holds three such sequences after the weights, thirteen at 32K. Llama 3.1 70B (80 layers, same heads) needs 320 KiB per token, 40 GiB per 128K sequence. derived

What one token leaves in one layer, by attention design, to scale

One square is 64 numbers. MHA, GQA-8 and MQA at Llama 3.1 8B's shape (32 query heads of 128); MLA at DeepSeek-V3's (a 512-number latent plus a 64-number RoPE key, whatever the 128 heads); DSA adds a 128-number indexer key (DeepSeek-V3.2, GLM-5). A sliding-window layer stores the same entry as its full twin but only for the last W tokens; a recurrent layer stores nothing per token and keeps a fixed state instead. The mistake worth one line: sizing with query heads

With num_attention_heads Llama 3.1 70B comes out at 2,560 KiB per token instead of 320 KiB, eight times too much (1 sequence at 128K on eight 80 GB GPUs instead of 10). For MLA, the same slip gives 3.81 MiB per token for DeepSeek-V3 instead of 68.6 KiB.

How to check. Read num_hidden_layers, num_key_value_heads, head_dim from config.json, then the fields that change the sum: sliding_window with layer_types or sliding_window_pattern, MLA's kv_lora_rank, an indexer's head dim, linear-attention layers. vLLM prints the cache it allocated at start-up, and its metric vllm:kv_cache_usage_perc shows how full it is (Batching, KV cache and scheduling).

Why two pages can give two cache sizes for the same model (accounting conventions)
  • Windows credited or not. The "card" convention (Raschka's gallery: "the logical cache added by one token for one sequence") counts every layer at full cost, so Gemma 3 27B is 496 KiB per token; what one 128K request actually holds, windows credited, is 10.41 GiB, not 62 GiB.
  • DSA indexer keys counted or not. DeepSeek-V3.2 is 68.6 KiB per token for its MLA latents alone and 83.9 KiB with its 128-number indexer keys in bf16; in its released FP8 decode layout the DeepSeek page reports 48,068 bytes per token (FlashMLA). GLM-5 likewise: 87.75 KiB of latents, 107.3 KiB with indexer keys.
  • Published mixed layouts. DeepSeek-V4 stores FP8 entries with bf16 RoPE dimensions and an FP4 indexer: 4,939.5 bytes per token for V4-Pro on the DeepSeek page, against about 9.7 KiB if everything were bf16 (the attention-variants convention).
  • Recurrent state dtype. FP32 here and in the root calculator (Qwen3.5 and 3.8 configs say mamba_ssm_dtype: float32); 16-bit on the Qwen, GLM and Memory technology pages, which halves every state figure. How serving engines store it varies.
  • "1M". 1,048,576 tokens here and on Attention variants; 1,000,000 on the DeepSeek page. Ratios do not change; absolute figures differ by 4.9%.
  • Units. KiB and GiB are powers of 2; GB is 109 bytes: 16 GiB is 17.18 GB.

2. Slow, not only big: decode reads it, prefill squares it

Decode is bandwidth. Every generated token reads the whole cache once: each cached number feeds two multiply-adds (one score, one weighted sum), far too little arithmetic per byte to keep a GPU busy, so decode speed is set by memory bandwidth (about 1 FLOP per byte for MHA in bf16 against an H100's balance of about 295; Performance math has the roofline). Cache bytes are decode time. At 128K tokens Llama 3.1 8B reads 16 GiB of cache per sequence per step on top of its 16 GB of weights; batching shares the weight read across sequences, never the cache read.

Attention overtakes the weights at about 28,600 tokens in decode, and takes 70% of a 128K prefill

Llama 3.1 8B: share of FLOPs per token spent in attention, against context. Decode: one new token over a cache of T. Prefill: the average token of a T-token prompt, which reads about half the prompt, so prefill crosses later. Weight FLOPs are flat; attention FLOPs grow with every position read. derived with the root's calc.py.

Prefill is compute. Reading a prompt costs every token's attention over all earlier ones, so a prompt's attention FLOPs grow with the square of its length while its weight FLOPs grow linearly. Memory and compute are different walls, moved by different levers:

Predict. Llama 3.1 70B goes from 8 KV heads to MQA (one KV head). At 128K tokens on eight 80 GB GPUs, how many more sequences fit, and how much faster does a 128K prefill get?
The cache shrinks by the KV heads removed (8 to 1), so about eight times the sequences fit once the weights are paid (10 at 128K as configured). Prefill FLOPs barely move: attention FLOPs are set by the 64 query heads and the positions each reads, not by how many distinct keys are stored. Fewer KV heads, fewer bits and eviction cut memory and decode reads; only windows, sparsity or a different mixer cut prefill compute.

3. Smaller entries: fewer KV heads, a latent, fewer bits

Three levers shrink each token's entry and keep every token.

Fewer KV heads (GQA, MQA): query heads share keys and values. Llama 3.1's 8 KV heads for 32 (8B) or 64 (70B) query heads already cut the cache 4 or 8 times against MHA; MQA goes to one. Small quality cost when done in training or uptraining (GQA paper).

A compressed latent (MLA): DeepSeek-V3 caches 576 numbers per layer whatever its 128 heads, 68.6 KiB per token over 61 layers in bf16, against 3.81 MiB for MHA at the same shape: about 57 times fewer, the size of GQA with only 2.25 groups. The DeepSeek MLA explainer animates the mechanism.

Fewer bits per number (KV quantisation): keys and values in 8, 4 or 2 bits with a scale per group of numbers. It needs no retraining, which is why engines ship it (FP8 in vLLM and SGLang; q8_0 and q4_0 in llama.cpp, measured on Qwen3-1.7B on Batching, KV cache and scheduling section 8). It halves (fp8) or quarters (4-bit) memory and decode reads at once, and composes with every other lever.

Keys have outlier channels, values do not: why 2-bit keys must be grouped per channel

SmolLM2-135M, all 90 caches (30 layers x 3 KV heads), one 4,096-token prompt: the largest channel's mean magnitude over the median channel's. Keys: median 9.4 times; values 2.7 times. A per-token group of keys spends its range on the few large channels and rounds the rest to almost nothing. measured on Apple M1 Pro (CPU) (src/kv/key_channels.py)

That is KIVI's finding: "the key cache should be quantized per-channel" and "the value cache should be quantized per-token" (Liu et al. 2024). Measured here on SmolLM2-135M (section 4's pass-key test): 8 bits are free (97% against 97% full), 4 bits nearly free (KIVI layout 93%), and 2 bits need keys per channel (50% against 7% per token) and still lose half. measured Check retrieval at your length, not perplexity, and the key statistics above on your model.

KIVI makes 2-bit caches workable (Liu et al. 2024; the authors report "2.6× less peak memory (including model weight)", up to 4 times larger batches and 2.35 to 3.47 times the throughput; authors' claims, not run here). MLA at DeepSeek-V3's shape against 8-group GQA: 244 KiB per token. Per sequence at 131,072 tokens: 8.58 GiB, where MHA would need 488 GiB. DeepSeek-V2's headline, that MLA "reduces the KV cache by 93.3%" against its 67B dense predecessor (vendor), reproduces only with V2's cache quantised to about 6 bits: in bf16 the arithmetic gives 82.2% (69,120 against 389,120 bytes per token).

4. Fewer entries: eviction

Most cached tokens get little attention most of the time; eviction scores each entry and keeps the best within a budget. StreamingLLM keeps the first few tokens (the attention sinks) plus a recent window: fluent forever, but nothing that left the window is remembered (Xiao et al. 2023). H2O keeps the "heavy hitters", tokens that "contribute most of the value when computing attention scores", plus recent ones (Zhang et al. 2023). SnapKV keeps what the last prompt tokens, usually the question, attend to (Li et al. 2024).

The test here: SmolLM2-135M, one 4,096-token prompt of TinyStories with a planted sentence ("The secret number is 66226. Remember it.") and a question at the end; prefill with the full cache, compress, then score the continuation against what survived (prefill-then-compress, SnapKV's setting). Each policy keeps the same share in every one of the 90 caches. measured on Apple M1 Pro (CPU), fp32, 4 threads, deterministic.

Fewer bits beat fewer entries at equal memory; perplexity hides the difference

What the runs show. Only a question-aware policy survives: SnapKV keeps 97% at a quarter of the cache, but 0% when it scored the cache before the question arrived. Every eviction policy loses copying already at half the cache, while int4 at 31% of the bytes keeps it. Perplexity sees none of this: H2O at 12.5% moves the new-story loss from 2.07 to 2.10 while answering 0% of pass-key questions. And keep the first tokens: a recent window without sinks sends the new-story loss to 4.02; with 4 sinks, 2.08.

Two lessons a paper's headline will not give you

An eviction method is only as good as the test: perplexity or summarisation can stay flat while retrieval of a single fact goes to zero. And question-aware methods need the question at compression time; in a multi-turn chat, an agent loop or a shared prefix cache the document is compressed before anyone asks, and the method becomes another heuristic.

Cost, and how to check. Scoring needs attention weights that fused kernels never materialise; the prefill peak is untouched; per-head selections free no paged blocks (the Batching page measured 0% of 16-token blocks freed). Test retrieval and copying at the budget, with the question where your application puts it, and measure memory the engine actually frees. (The root's Inside a real model tab finds SmolLM2's sink switching on at layer 12.)

Every result. 5. Local and global layers: a smaller cache designed in, not cut out

Eviction decides after training which entries to drop, and the model was never trained to cope. A local layer makes the decision part of the architecture: in training and inference each query sees only the last W tokens, so the layer's cache never holds more than W entries. Interleaving local layers with a few global ones keeps a direct path to any old token while most layers stay cheap (the ring-buffer mechanism: section 4 of Attention variants).

Mistral's paper says the window "reduces the cache memory usage by 8x" at its 32,768-token sequences (32,768 / 4,096, reproduced independently), and stacking 32 windowed layers reaches 32 × 4,096 = 131,072 tokens in theory. Gemma 3 keeps RoPE base 10,000 on local layers and 1,000,000 on global ones (rope_local_base_freq, rope_theta), because only global layers see long distances. On one 80 GB GPU in bf16, Gemma 3 27B as released fits one 128K request (11.17 GB of cache after 54 GB of weights) and, with every layer global, none (66.57 GB for one): the local layers are what make 128K servable at all on one GPU.

Published quality cost: small, when trained in. Google reports for Gemma 3 that changing the local:global ratio has "minimal impact on perplexity", "even with 7-to-1 local to global" (vendor). Two cautions: that is perplexity, which section 4 measured to be the wrong test, and on models trained with their layout.

Measured here: imposing a layout does not work. SmolLM2-135M was trained with full attention in all 30 layers. Making 25 of them local after training (sinks plus a window, every sixth layer global, at the same memory as the other policies; the local_global policy of section 4): result pending. The model never learned to route old information through its global layers; converting a trained model needs continued training with the layout in place.

Other ways to cut the per-token rate, each a training-time design: share keys and values across adjacent layers; replace most layers with a fixed recurrent state (hybrids); or compress and sparsify what is stored and read (DSA saves reading, not storing; DeepSeek-V4 stores about 2% of a GQA-8 cache at 1M tokens). The KV-cache calculator sizes each.

The published evidence in full, and the other per-token levers

Gemma 3 report: the ratio changes have "minimal impact on perplexity", "even with 7-to-1 local to global", and the window "can be reduced significantly without impacting perplexity"; on memory, "global only" gives "a memory overhead of 60%" at 32K, "reduced to less than 15%" with sliding windows of 1,024 (Gemma 3 report, sections 5.1 and 5.2, vendor; the report writes the ratio as "1:3" there and 5:1 elsewhere). Our arithmetic for 27B in bf16 gives 31% and 5.8%: the same fivefold cut, not the same numbers; we did not find which model size and precision the report's figure uses. Gemma 2's Table 10 shrinks the trained 4,096 window at inference to 2,048 and 1,024: validation perplexity 1.63, 1.63, 1.64 (vendor). Databricks' MixAttention study, testing on RULER, found long-context ability needs "at least one standard attention KV cache that is computed in the deeper layers" (Rajput et al. 2024, third-party, building on Character.AI's 2024 blog).

Cross-layer sharing attacks the layer count: adjacent layers reuse one set of keys and values; Cross-Layer Attention reports it can "reduce the size of the KV cache by another 2x" beyond MQA "while maintaining nearly the same accuracy as unmodified MQA", trained from scratch at 1B and 3B (Brandon et al. 2024, third-party). Hybrids keep a fixed recurrent state in most layers: Nemotron-H 8B keeps 4 attention layers of 52 (16 KiB per token plus about 99 MiB of state per sequence), Qwen3-Next one in four (24 KiB per token; its DeltaNet state equals the cache of 512 tokens of the layers it replaces), GLM-5.3-Flash 11 sparse layers of 45 (owned by Beyond attention). Sparse and compressed attention changes what is read or stored: DSA (DeepSeek-V3.2, GLM-5) stores every latent plus an indexer key and reads only the top 2,048, so it saves reading, not storing; MiniMax M3.1 Flash runs sparse attention in every layer, having replaced the three full-attention layers M3 kept, so in production the always-on global path can be a sparse one (model card, vendor); DeepSeek-V4 compresses entries 4 or 128 to one, about 2% of a GQA-8 cache at 1M tokens (mechanisms on Attention variants; sizes in the KV-cache calculator).

When it matters, how to check. Local layers pay off once the context is several times the window; below that they cost and save nothing. Check the layout in config.json (sliding_window with layer_types or sliding_window_pattern, attention_chunk_size), check that your engine frees windowed entries (a cache that allocates every layer at full length gives the quality cost of windows without their memory), then test the long-range path with retrieval at the target length.

6. Long prompts: the compute side

A 128K-token prompt is a 128K-row attention matrix per head per layer, and it costs in four separate ways, each fixed exactly (no quality cost) by a neighbouring page's method: FlashAttention keeps the score matrix out of memory, chunked prefill stops one long prompt stalling everyone else's stream, context parallelism splits one sequence across GPUs, and only windows, trained sparse attention or recurrent layers cut the quadratic FLOPs themselves.

To check a serving setup, time a prefill at your target length (time to first token) against section 2's crossover: below about 28,600 tokens for an 8B Llama, weights dominate and attention tricks change little.

7. Past the trained length: the position wall

A model is trained on windows of some length; nothing stops a longer prompt at inference. With RoPE (each query and key rotated by an angle proportional to its position, so their dot product depends on distance), a longer prompt produces angles, in the slowly rotating dimensions, that training never showed; with learned absolute positions there is no row in the table at all (the topic's tiny GPT raises IndexError: learned positions stop at 256; got position 299, on purpose; no scaling rule exists for a learned table: retrain or switch scheme). The schemes and extension methods (position interpolation, NTK-aware scaling, YaRN, Llama 3's rule) belong to Positional Encodings; here is what the wall costs and why training at length is still needed.

The tiny GPT past its 256-token training length: scaling trades the short range, training fixes both

At this scale the training, not the scaling rule, did the work. The window-64 model has no wall at all (2.1 in range, 2.09 at 1,024 to 2,047): no query ever looks further than 64 tokens, which is also why it cannot retrieve from further.

Why: a distance is learned only as often as it is seen

In one training window of length L, the distance d between a query and a key occurs L − d times: distance 1 at 255 query positions, distance 250 at 6. A model trained on 256-token windows has seen distances past 200 in about 5% of its query-key pairs and past 255 never. Drag to see the share of training pairs at or beyond a distance.

An et al. trace short effective contexts in open models to exactly this "left-skewed frequency distribution of relative positions", and find effective lengths "typically not exceeding half of their training lengths" (An et al. 2024, third-party). So production recipes pair a scaling rule with training at the new length: Gemma 3 pre-trains with 32K sequences and rescales RoPE by 8 to reach 128K (Gemma 3 report, section 5.3, vendor); Llama 3 grew from 8K to 128K over six stages (section 6). How to check: read rope_scaling and original_max_position_embeddings, then plot loss by position on long held-out documents; a curve that turns up at the trained length is the wall.

8. Effective context: accepting a token is not using it

A model can fit a 128K prompt in memory, read it without a position error, and still ignore most of it. The effective context is the longest input at which it still does a given task well: it depends on the task and the threshold and is measured, never read from the config. max_position_embeddings is an allocation, not a training fact: Qwen3 32B's config says 40,960 for a model trained to 32,768 natively, MiniMax-M1's 10,240,000 (root's Architecture map). Published measurements at scale (RULER found that of models claiming 32K or more "only half" hold up at 32K; NoLiMa removes the shared words between question and needle and finds most models effective to 2K or less) are owned by Long-context and multimodal benchmarks.

SmolLM2-135M retrieves one number up to its configured 8,192 tokens, then nothing

The pass-key prompt of section 4, full cache, seven lengths, five needle depths, four seeds per cell (140 prompts); cells give correct answers out of 4. Config: max_position_embeddings 8,192, RoPE base 100,000, no rope_scaling; the model card names the base model "SmolLM2-135M-8k" (read 2026-10-18); the SmolLM2 paper describes a 2K to 8K extension for the 1.7B model only (Allal et al. 2025, vendor). measured on Apple M1 Pro (CPU)

Read it as a wall, not a slope. Inside 8,192 tokens the misses are near-misses (at 1K and 2K always the first digit, 1 for 6 or 7; at 8,192 only with the number 8K tokens back); past it every answer is broken text such as "a1...." for 66226. Short prompts are not easier for this 135M model, a reminder that 20 prompts per length is coarse.

Four causes, each with a section above: positions trained rarely (7); attention spread thinner over more keys, so one relevant token gets a smaller share (a length-dependent temperature, such as YaRN's, counters it); windows that cannot see far (5); caches compressed by policies the model never trained with (4). The shape of the heads matters too: at a fixed parameter budget, wider heads (a larger head dimension) barely changed pretraining loss or short-task scores but improved long-context retrieval, with more retrieval heads (heads that copy a token from far back) forming, and the gain held even with the attention projections frozen during long-context continued pretraining (Head Dimension Matters for Long-Context Retrieval (arXiv 2610.32213)). How to check, at the length and prompt format you ship: loss by position, a retrieval grid over length and depth, then a task string matching cannot solve (NoLiMa-style). Report the length at which your threshold still holds.

Reading it. No single lever reaches 32. fp8 is free but only doubles capacity; MQA and a local/global layout cut the cache 8 and 6 times but are training-time choices (section 5); only the windowed layout also cuts prefill compute (attention from 70% to 28% of the FLOPs). Other budgets. Many short chats favour MLA or few KV heads plus prefix caching. Long single sequences (agents, codebases) make one sequence's cache and its prefill dominate: hybrids with a constant-state mixer in most layers or trained sparse attention change the curve rather than shift it. Mixture-of-experts models move the weight bar, not the cache: DeepSeek-V3 needs 671 GB of fp8 weights on eight 141 GB GPUs but only 9.21 GB of MLA cache per 128K sequence, so 39 fit. Try any of them in the KV-cache calculator.

Design question: a coding agent that reads 1M tokens of repository per task

Concurrency is low, so one sequence's cache and the prefill dominate. At 1,048,576 tokens Llama 3.1 8B's cache alone is 128 GiB; DeepSeek-V3's MLA 68.6 GiB; Qwen3-Next's hybrid 24 GiB; DeepSeek-V4-Pro's compressed attention under 5 GiB (calculator). So: a hybrid with constant-state layers in most of the stack plus a few global attention layers (Qwen3-Next's 1 in 4, Nemotron-H's 4 of 52), or trained sparse or compressed attention; context parallelism for the prefill across GPUs; an fp8 cache for the global layers; no question-aware eviction (the question changes every turn); evaluation of retrieval and multi-hop use at 1M, and retrieval into a shorter context when the effective length falls short (Agentic retrieval, long context and memory).

Design question: eviction or quantisation at the same memory?

Quantisation first: it keeps every entry, needs no attention scores, works with fused kernels and paged blocks, and 8 or 4 bits cost little (here int4 kept retrieval and copying; eviction at 25% kept neither copying nor, unless question-aware, retrieval). SnapKV beats H2O on a planted fact (87% against 0% at 12.5%) because it scores by the question's own attention, while H2O keeps tokens many queries attended, which a fact read once is not. Evict when the context itself must be bounded (streaming), with sinks kept.

Design question: why not make a trained full-attention model local/global after the fact?

Its retrieval heads are spread over many layers; making most of them local removes the paths it learned (SmolLM2 with 25 of 30 layers made local: 37% at half the cache, 3% at a quarter, copy loss 1.56). Models with a layout are trained with it (Gemma 2 and 3, gpt-oss); conversion needs continued training.
