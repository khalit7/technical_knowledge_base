MSA (MiniMax Sparse Attention, M3): keep exact lookup, read a few blocks

M3 takes the third route. Trained sparse attention keeps the softmax and the full KV cache but lets each query attend only to a selected subset of keys; if the right keys are selected the lookup is exact, because nothing was compressed. The difficulty moves into selection (cheap, trainable end to end) and into kernels (a selected set is irregular, and irregular memory access is what GPUs do worst). Sparse attention in general, and DeepSeek's DSA, are taught on {{Attention variants|n:3fd5c17b0d0d8120859ecc2d0236e846}}; MSA is MiniMax's version, from the {{MSA paper, arXiv 2606.13392|@pmsa}} and M3's {{config|@cm3}}:

  1. A token arrives. At position 131,072 it enters one of M3's 57 MSA layers and forms 64 query heads of 128 (4 GQA groups of 16), its key and value for each of the 4 KV heads, and for the index branch 4 index queries (one per group) and one shared index key, all of dimension 128. Each grey plate is one KV head's cache over the whole context, in blocks of 128 earlier tokens (to scale: a lit block is one block); the gold plate holds the index keys.
  2. Write to the cache: nothing is dropped. Its keys and values (2 × 4 × 128 × 2 = 2,048 bytes) go to every KV head and its index key (256 bytes, BF16 assumed) to the gold plate. All 1,024 blocks stay resident: MSA never shrinks what is stored, it only chooses what to read.
  3. Index branch: score every earlier token. One small index query head per KV group and one index key head shared by all groups score every earlier token, Si,j = qidxi,r · kidxj / √didx: 4 × 128 × 131,072 multiply-adds, reading all the index keys (32.0 MiB). The one part of MSA that still grows with the context, which is why it is kept light.
  4. Block scores: max-pool. Keys are cut into blocks of Bk = 128 tokens; a block scores the maximum of its tokens' scores, so one strongly relevant token lifts its whole block (the gold shade: group 1's block scores).
  5. Selection per GQA group: 16 blocks each. Each group ranks the blocks by raw score (an "exp-free" top-k, since softmax preserves order) and keeps its own top k = 16, the query's own block always included. The four colours are the four groups: they share the local block and the sink at the start but retrieve different long-range blocks; 64 of 1,024 blocks are lit.
  6. Exact attention on the selection. Each group's 16 query heads run ordinary softmax over the kBk = 2,048 selected keys of their own KV head, reading 4 × 2,048 × 2 × 128 × 2 bytes = 4 MiB. Nothing was compressed, so if the right blocks were chosen the lookup is exact. This layer read 36.0 MiB for the token, against 512 MiB in one of M2's layers.
  1. A token arrives. At position 131,072 it enters one of M2's 62 layers and forms 48 query heads of 128 (8 GQA groups of 6) and its key and value for each of the 8 KV heads, one orange plate each.
  2. Write to the cache. Its keys and values, 2 × 8 × 128 × 2 = 4,096 bytes, are appended to the 8 heads; the cache already holds every earlier token, 1,024 blocks of 128.
  3. Every query head scores every key. No selection: each head's query is dotted with all 131,072 keys of its group's KV head, so the token reads every key (256 MiB) and does 48 × 128 × 131,072 multiply-adds for the scores.
  4. Softmax over everything, then the values. The weighted sum reads every value (256 MiB more, purple), another 48 × 128 × 131,072 multiply-adds: 512 MiB read in this one layer for one token. Exact, the reference the other two routes are measured against, and its cost grows with every token in every layer: why M2 stopped at a 196,608-token window and M3 needed MSA to reach 1M.
  1. A token arrives. It enters one of MiniMax-01's 70 lightning layers and forms 64 heads of query, key and value, each of dimension 128.
  2. No cache: update the state. Nothing is appended per token: this layer keeps no cache at all. Each head adds k⊤v to its fixed 128 × 128 state (green glass): 64 × 128 × 128 multiply-adds.
  3. Read the state, not the history. The output is q times the state: another 64 × 128 × 128 multiply-adds, reading 64 × 128 × 128 × 2 bytes = 2 MiB at any context. The cheapest route by far, and the one that lost exact recall: a fixed state cannot hand back one earlier token verbatim.
  4. The 8th layer is still softmax. One layer in every eight is softmax GQA with 8 KV heads: it caches 4,096 bytes per token and reads all of them, as M2 does (512 MiB here). That is MiniMax-01's 40 KiB per token: only 10 of its 80 layers grow with context. MiniMax gave this up in M2 for quality on multi-hop reasoning and retrieval, not for speed.

Block scores and selections are illustrative (a fixed seed with a sink block and a few hot regions, the pattern of the MSA paper's Figure 5); every count and byte figure is computed from the configs. One GQA group is 16 query heads in M3 and 6 in M2. Training: a KL loss pulls the index scores towards the main branch's attention; its inputs are detached, so it updates only the index projections (details in a closed block below).

The cost per query at position n, counting multiply-adds for scores and the weighted sum in the main branch and for scores alone in the index branch:

Cfull=2Hdhn,CMSA=2HdhkBk+Hidxdidxn

With M3's H = 64, dh = 128, kBk = 2,048, Hidx = 4, didx = 128 at n = 1,048,576: Cfull ≈ 1.72 × 1010, CMSA = 33,554,432 + 536,870,912 ≈ 5.70 × 108, a ratio of about 30. Each query reads 2,048 of 1,048,576 keys, 1 in 512, and the index branch is 94% of what remains, which is why it has to be light.

Selection does not shrink storage. Every key must stay resident for the indexer to choose from. M3's main cache is 60 × 2 × 4 × 128 × 2 bytes = 120 KiB per token, about 120 GiB for one 1M-token sequence, plus one 128-dimension index key per token in each of the 57 MSA layers: 14.25 KiB more per token if stored in BF16 (the precision is not stated; assumption). The saving over M2 comes from halving the KV heads (8 to 4), not from MSA; the model card's "reduces the attention compute and memory footprint" ({{M3 card|@km3}}) is true of what each query reads, not of what is stored.

The kernel: "KV outer, gather Q". A natural sparse kernel loops over queries and fetches the blocks each one selected; every fetched tile then serves only the G query heads of one group, about G FLOPs per byte (16 in M3: 64 query heads over 4 groups). MSA's kernel inverts the loops: for each KV block it gathers every query that selected it into one 128 × 128 matrix multiply, so the tile is loaded once and reused. The paper puts the intensity at about ⅔ Bk, roughly 85 for Bk = 128; hot blocks (an early "sink" block nearly every query selects) are split across thread blocks by a scheduler. MiniMax report it as more than 4 times faster than the open-source Flash-Sparse-Attention and flash-moba kernels ({{M3 announcement|@m3b}}, repeated by launch partner {{Fireworks|@fw}}; code on {{GitHub|@msagh}}).

Where MSA sits, and what it scored. Block-level selection with a separate top-k per GQA group keeps reads contiguous while letting groups retrieve different blocks (the paper's attention maps show each group tracing its own long-range stripes beside a shared local diagonal and sink column). In granularity MSA is finer than Kimi's MoBA but coarser than DSA, which selects individual tokens; the M3 announcement's wording that MSA partitions the KV "more precisely" than DSA and MoBA ({{MiniMax|@m3b}}) is about effective coverage, not selection unit. On the paper's 109B test model (41 layers, 6B active, 3T training tokens), MSA converted from a full-attention checkpoint and extended to long context scored 72.12 on RULER at 128K against 72.00 for full attention, and 45.93 on HELMET at 128K against 46.53; trained sparse from scratch, it matched or beat full attention on most of the paper's pretraining suite.

What each route stores, reads and computes

The three generations on one set of axes. Fig. 6 sets them side by side at 128K and at 1M: one group per quantity, one column per route (green MiniMax-01, orange M2, blue M3), each group on its own scale because the units differ. Compressing history into a fixed state (linear) buys the most and costs recall; selecting which history to read (sparse) buys less and keeps lookups exact, at the price of a trained selector that runs over every token and can miss a block; full attention is the reference both are measured against.

  1. Stored per sequence, at 128K. The left group, glass: M2 keeps 31.0 GiB of keys and values for one 131,072-token sequence, MiniMax-01 5.14 GiB (its 10 softmax layers plus the fixed 140 MiB of lightning state), M3 16.8 GiB, of which 1.78 GiB (gold) are index keys (BF16 assumed). Storage is where MSA saves nothing: M3 sits below M2 only because it has 4 KV heads instead of 8.
  2. Read per decoded token. The middle group, streaming to the token: M2 reads everything it stored, 31.0 GiB; the hybrid reads its 5.14 GiB; M3 reads 2.75 GiB, 11.3 times less than M2, and 65% of that is the index keys (gold): the selector has become the main read. Decode is memory-bound, so this group is the closest of the three to decode speed.
  3. Multiply-adds per decoded token. The right group: M2 9.99 × 10¹⁰, the hybrid 2.16 × 10¹⁰ (its lightning layers cost the same at any context), M3 1.22 × 10¹⁰, 8.2 times less than M2, of which the index branch (gold) is 31%.
  4. At 1M tokens. M2 cannot run here (its window is 196,608 tokens; dashed and cut). M3 stores 134 GiB against the hybrid's 40.1 GiB, but reads 20.5 GiB per token against 40.1 GiB and does 8.41 × 10¹⁰ multiply-adds against 1.72 × 10¹¹: half the hybrid's on both, with every lookup still exact.
  5. The "1/20" accounting. M2's formula at 1M (7.99 × 10¹¹ multiply-adds, had it a window that long) against M3's gives a ratio of 9.5; only with all 60 layers sparse (hypothetical, 3.42 × 10¹⁰; M3 keeps 3 full-attention layers) does it reach 23.3, past MiniMax's 1/20.
