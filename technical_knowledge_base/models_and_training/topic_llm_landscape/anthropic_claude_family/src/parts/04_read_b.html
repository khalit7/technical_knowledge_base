Where Claude ranks

The Artificial Analysis Intelligence Index is a composite of ten evaluations (agents 30%, coding 20%, general knowledge 30%, scientific reasoning 20%) on one 0 to 100 scale, a coarse cross-lab ranking since the mixture is theirs rather than yours ({{methodology|@aameth}}). Its version matters more than its rank. Version 4.2 (4 September 2026) dropped GPQA Diamond as saturated; version 4.3 (7 September) moved Terminal-Bench to 4.0, replaced tau3-Banking with AutomationBench-AA and raised the weight of private held-out tests from 40% to 45%; methodology 4.3.2 (19 September) re-anchored the GDPval-AA Elo scale. The result is still a 0 to 100 score.

On v4.3, Opus 5.5 at max effort leads every model at 57.6; Fable 5.1 (max) scores 53.4, Opus 5 (max) 50.8 ({{Artificial Analysis|@aalb}}, read 1 October 2026). Opus 5.5 at its default medium effort scores 51.2 at $1.34 per index task against GPT-6 Astra at max effort on 52.7 at $3.26: a point and a half lower for 41% of the cost (1.336 / 3.2575; {{Artificial Analysis|@aaop}}). Before v4.2 the composite was on a different 0 to 100 scale, on which Opus 5 led through August 2026 at roughly 63 and Fable 5 at roughly 62; those figures cannot be set beside v4.3 scores, and no v4.3 model inherits them. The Effort and cost per task tab plots every Claude run.

What is measured directly is narrower and firmer. Real-SWE, published in September 2026 by Specific Labs on tasks licensed from private production codebases, put Fable 5.1 in Claude Code first at 38.8% (GPT-6 Astra in Codex 33.8%, Gemini 3.8 Flash 31.2%, with overlapping confidence intervals); it did not include Opus 5.5 or Sonnet 5.5 ({{DEV Community|@rswe}}). The documentation now recommends starting with Opus 5.5 for most workloads and moving to Fable 5.1 for demanding reasoning and long-horizon agentic work, "or when your evals on Claude Opus 5.5 at higher effort still fall short" ({{models overview|@models}}). The release's other case for Fable 5.1 is its writing: Glean's judges preferred its answers "roughly 2-to-1" over Fable 5 on everyday knowledge questions, and Canva called the writing "the standout" ({{Anthropic|@fab51}}).

How thinking is controlled

The family's signature API surface is how the caller steers deliberation, and it changed shape in 2026. The first design (Claude 3.7 Sonnet to Opus 4.5) was a caller-set cap; the current one is a model-decided amount steered by a coarse caller-set level.

Adaptive thinking. The model decides, per request and per step, whether to think and for how long. On Opus 5.5, Fable 5.1 and Mythos 5.1 it is always on and cannot be disabled; on Sonnet 5.5 it is on by default. On Opus 4.6 to 4.8 and Sonnet 4.6 it is off until you ask for it. Only Haiku 4.5 among current models still uses the older manual mode, thinking: {type: "enabled", budget_tokens: N} ({{thinking docs|@think}}).

Effort. The caller steers adaptive thinking with output_config.effort: low, medium, high, xhigh or max. Effort is a behavioural signal, not a token budget: it scales every output token (thinking, text and tool calls, so lower effort also means fewer and terser tool calls), and at low effort the model still thinks on a hard enough problem, just less. The hard ceiling is max_tokens, which bounds thinking plus response together. The default is high on most models and medium on Opus 5.5, so a request that omits effort runs one level lower on Opus 5.5 than it did on Opus 5 ({{effort docs|@effort}}).

Changing effort mid-conversation. On Fable 5.1, Mythos 5.1, Opus 5.5, Opus 5 and Sonnet 5.5, a per-message setting (beta: an empty system message carrying the new output_config.effort) changes it from the next user turn and keeps the prompt cache. Changing the top-level value between requests restarts the cache, because effort is rendered into the prompt itself ({{effort docs|@effort}}).

Try: enabled with a budget, the 3.7-era request: every model from Opus 4.7 on returns a 400 error. Then disabled at max: only models that let thinking be switched off at all, and only below xhigh on Opus 5, accept it.

Interleaved thinking. Thinking between tool calls, so the model reasons about each tool result before acting on it. Under adaptive thinking it is automatic; Haiku 4.5 does not support it. The newest models (Fable 5.1, Mythos 5.1, Opus 5.5, Sonnet 5.5, Fable 5) also write short progress updates between tool calls, notes for the person watching the agent rather than reasoning, and they write fewer of them at higher effort ({{thinking docs|@think}}).

What you see, and what you pay for. You never receive the raw chain of thought. With display: "summarized" a thinking block holds a summary written by a different model; with "omitted", the default on the 5.x models, the block's text is empty (a beta "updates" shows only the progress updates). Either way you are billed for the full thinking tokens as output tokens, so the billed output count does not match the text you can see. On Fable 5.1, Opus 5.5, Sonnet 5.5 and Fable 5 a prompt that tries to pull the reasoning into the visible answer can be refused as reasoning_extraction.

Passing thinking back, and preserved thinking

Each thinking block carries a signature, an encrypted copy of the full reasoning. Within a tool-use turn, every thinking block must be passed back complete and unmodified alongside its tool_use block, or the model loses the reasoning that led to the call; a modified block is rejected with a 400 error. On current Opus and Sonnet models and the Mythos class, earlier turns' thinking blocks stay in context (and in the cache) and are billed as input like the rest of the history; on Haiku 4.5 and older models they are stripped once a new user message arrives ({{thinking docs|@think}}).

Preserved thinking, introduced with Fable 5.1 and extended to Opus 5.5 and Sonnet 5.5, adds two checks to the signature ({{preserved thinking docs|@pres}}):

  • Which model produced the block. Fable 5.1 and Mythos 5.1 read every earlier model's blocks and no earlier model reads theirs; Opus 5.5 reads Opus 5 and earlier Opus, Sonnet and Haiku blocks; Sonnet 5.5 reads Sonnet 5, Opus 4.8, Haiku 4.5 and earlier. A block the current model cannot read is dropped silently and not billed.
  • Whether everything before it is unchanged: the system prompt, the tools and every earlier message. If the prefix changed, that block and every later one are invalid, and the API either rejects the request with a 400 error or drops the invalid blocks (unbilled, though the model may then think more to rebuild the reasoning), whichever the caller chooses.

The prefix check is enforced by default for API accounts created on or after 31 August 2026 and is opt-in on older ones; Sonnet 5.5 also ties its blocks to the account that produced them. Anthropic states the purpose as anti-distillation: without it, someone could take a thinking block from an expensive model, edit the conversation before it, and reuse the reasoning to train or steer a cheaper model. It sits beside Anthropic's September threat report (10 September, twelve days before Opus 5.5), which lists illicit distillation among the seven kinds of misuse it disrupted ({{Anthropic|@threat}}), and it narrows what a neutral harness can replay or reconstruct from a transcript: the same direction as GPT-6 Astra's recurrent depth, for a different reason (detail on {{OpenAI: GPT family|n:3c65c17b0d0d814abf90d5b9e567d72f}}).

Append-only, or what an edit costs

An agent conversation as the API sees it. Apply one change before the next request and watch which thinking blocks survive and where the prompt cache stops matching. Block sizes are illustrative; the rules are from the {{preserved thinking|@pres}} and {{prompt caching|@cache}} docs.

Try: "Edit the system prompt in place", then "Add a mid-conversation system message instead". The same instruction reaches the model either way; only the second keeps the reasoning and the cache.

Two consequences for a harness builder. Cost per task is now steered rather than set: effort is the dial and max_tokens the fuse, and neither fixes the number of thinking tokens in advance. And the conversation has to be append-only: a harness that rewrites earlier turns, edits the system prompt mid-session or swaps tools in place invalidates the model's reasoning, so instructions, tool changes and effort changes go in as new messages at the end (mid-conversation system messages, tool_addition and tool_removal blocks, per-message effort, server-side compaction and context editing). This is also why Claude-based harnesses such as {{Claude Code|@cc}} do well on long-horizon coding evaluations like SWE-bench and Terminal-Bench: the model is built to think again after every observation.
