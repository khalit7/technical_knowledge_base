Attention: from grouped-query, to sparse, to a hybrid

At long context the KV cache, not the weights, decides how many requests fit on an accelerator, and reading it decides decode speed. GLM's attention has been rebuilt twice to shrink both. The mechanisms are on {{Attention variants|n:3fd5c17b0d0d8120859ecc2d0236e846}} and the cache arithmetic on {{Long context|n:3fd5c17b0d0d81059ee1ce20c0326dc5}}; this section is what GLM chose and what each choice bought.

GLM-5: MLA with wider heads, plus DSA

GLM-5 replaced grouped-query attention with DeepSeek's MLA (one 512-number latent plus a 64-number rotary key cached per token and layer) and added DSA (the lightning indexer picks the top 2,048 entries for the main attention) ({{GLM-5 report|@r5}}, {{config|@cfg53}}). Every entry stays in the cache so that it can be picked later; DSA saves reading, not storing. Each of 78 layers caches 512 + 64 = 576 numbers, 576 × 78 × 2 bytes = 87.75 KiB per token at 16 bits against GLM-4.5's 368 KiB; at the full 1,048,576-token context the latents alone are 87.75 GiB for one request.

GLM's own change is the head shape. DeepSeek-V3 uses 192-dimensional query-key heads with a head count chosen for the roofline of Nvidia's H800; GLM-5 widens them to 256 and cuts the number of heads by a third, which "keeps the training computation and the number of parameters constant while decreasing the decoding computation". The report calls this MLA-256, tuned for the seven Chinese accelerator platforms GLM-5 was adapted to (Huawei Ascend, Moore Threads, Hygon, Cambricon, Kunlunxin, MetaX and Enflame) rather than for the H800. DSA was not trained from scratch: GLM-5 continued pretraining from its dense-attention base with a 1,000-step warm-up that trains only the indexer, then a 20B-token sparse-adaptation stage; the report puts DSA's saving at "roughly 1.5 to 2 times" less attention computation for long sequences ({{GLM-5 report|@r5}}).

IndexShare (GLM-5.2): run the indexer once per four layers

DSA makes the main attention cheap, but the indexer still compares each query with every earlier token, so its cost still grows with context, and at a million tokens it becomes the bill ({{Raschka|@rasch}}). The IndexCache study IndexShare builds on measured 70% to 100% overlap between the positions selected by adjacent DSA layers ({{IndexCache|@icache}}): neighbouring indexers mostly rediscover the same tokens. So in GLM-5.2 the indexer runs at the first of each group of four layers and the next three reuse its list; in the released config 21 of the 78 layers run an indexer ({{GLM-5.2 blog|@b52}}, {{config|@cfg53}}). The sharing layers still compute their own queries, attention weights and value mix; only the list is reused. GLM-5.2 was trained this way from mid-training at 128K sequence length.

Past about 128K tokens the indexer, not the attention it feeds, is most of the work; IndexShare and IndexPool cut exactly that term

Flash's 34 KDA layers each add about 3 × 128 × 128 multiply-adds per head per token (an estimate of the delta-rule update and read, labelled as such). Projections and experts are left out unless "add active weights" is on.

Zhipu reports a 2.9 times reduction in per-token FLOPs at a 1M context, with the caveats that this is not an end-to-end speedup and that IndexShare "does not proportionally reduce per-token KV-cache size" ({{GLM-5.2 card|@c52}}, {{GLM-5.2 blog|@b52}}). Amdahl's law turns the figure into a statement about where the work was: if a share f of the work shrinks by n = 4 and the total by S = 2.9, then f = (1 − 1/S) / (1 − 1/n) = 0.655 / 0.75 = 0.87, so about seven eighths of GLM-5.1's per-token work at 1M was the indexer. For one query at L = 1,048,576 one indexer does 1,048,576 × 32 × 128 = 4.29 × 109 multiply-adds, while the main attention reads 2,048 entries, 0.2% of the cache.

Counted from the configs, 78 indexers against 21 plus 40B active weights give 2.7 times, close to the published 2.9 (details in the reproduction block below).

GLM-5.3-Flash: three linear layers to one sparse, and IndexPool

Flash, the first GLM to combine sparse and linear attention, replaces most attention layers with Moonshot's Kimi Delta Attention (KDA), a gated delta-rule linear attention whose state per request has a fixed size: each of its 64 heads keeps a 128 × 128 matrix that every new token updates (the mechanism is on {{Beyond attention|n:3fd5c17b0d0d8142bc9ecac1fc366966}}). Its 45 layers repeat three KDA layers and one sparse-attention layer, ending on a KDA layer: 34 KDA layers and 11 sparse ones, so only 11 / 45 = 24% of the layers keep a cache that grows with context ({{Flash config|@cfgfl}}). The sparse layers are MLA without positional encoding (NoPE; {{Positional encodings|n:3c65c17b0d0d81a5b7c9e578fcdfac00}}), so they cache a 512-number latent and no rotary key, with DSA reading the top 2,048 entries ({{config|@cfgfl}}, {{MarkTechPost|@mtpfl}}). In Zhipu's words, linear attention "captures local dependencies through state modeling, while sparse attention retrieves relevant global context through a lightweight indexer" ({{Z.ai docs|@dfl}}).

IndexPool attacks the indexer from the other side. IndexShare cut how many layers run an indexer; IndexPool cuts how many entries each indexer scores, by compressing four indexer key vectors into one "through weighted pooling" ({{Z.ai docs|@dfl}}). At L = 1,048,576 each Flash indexer scores 1,048,576 / 4 = 262,144 pooled keys. How a selected pooled entry maps back to the 2,048 attended tokens is not described in the sources read (the config keeps the newest, incomplete group selectable: index_kpool_always_select_tail). Against GLM-5.3, Zhipu reports 3.01 times less attention compute and a 4.44 times smaller KV cache ({{Z.ai docs|@dfl}}), counted "per head per layer" for compute and as "average KV cache size per layer (BF16)" for memory, so that models of different sizes compare fairly. That 4.4x is the whole design, not IndexPool: most of it comes from 34 of 45 layers holding no growing cache at all.

Counted from the two configs on Zhipu's per-layer convention the cache ratio is 4.6, near the published 4.44, and it factors as layer mix 45 / 11 = 4.09, times dropping the rotary key 576 / 512 = 1.125, times IndexPool 1.18. Per whole model the cache per token falls 47,616 / 5,984 = 8.0 times, because Flash also has fewer layers.

That combination is what makes the advertised million-token window affordable to serve rather than merely available. At 1M tokens one Flash request holds about 11.7 GiB of growing cache in 16-bit precision plus a fixed KDA state of 34 × 64 × 128 × 128 numbers (68 MiB in 16-bit), against 93 GiB for GLM-5.3. Zhipu itself notes that Flash's cache "is still slightly larger than Kimi-K3 and DeepSeek-V4-Flash", while its attention compute is the lowest of the four ({{Z.ai docs|@dfl}}).

slime and RL: built for episodes of very different lengths

Zhipu open-sourced slime, its RL post-training framework, the system behind every GLM from GLM-4.5 to GLM-5.3 ({{slime|@slime}}), and arguably as strategic as the weights. The problem it solves: in agentic RL a rollout is a whole episode of tool calls, and episode lengths are long-tailed (three tool calls, or three hundred). A synchronous step waits for the slowest rollout; in the GLM-4.5 report's words, "synchronous RL training often leads to severe GPU underutilization as workers wait for the slowest rollouts to complete" ({{GLM-4.5 report|@r45}}). The before/after on real response lengths, and asynchronous RL in general, are on {{RL for LLMs|n:3c65c17b0d0d818c9bcff7177325fe56}}.

slime has two modes ({{GLM-4.5 report|@r45}}). A colocated, synchronous mode, for reasoning RL whose rollouts are of similar length, runs generation and training on the same devices in turn. A disaggregated, asynchronous mode, for agentic RL, partitions the accelerators into rollout engines that generate continuously into the buffer and a trainer that consumes them without waiting for a batch; new weights are synchronised back periodically. The same lesson as prefill and decode disaggregation in serving ({{Distributed and disaggregated serving|n:3c65c17b0d0d8170bd7cdf47af0ec07b}}): when two coupled phases have different profiles, decouple them and buffer between.

The cost is staleness: a trajectory started under policy version w0 and trained on at version w′ is off-policy. GLM-5 bounds it twice ({{GLM-5 report|@r5}}):

discard if w′ − w0 > τ;    rt = πθ(yt | context) / πrollout(yt | context);    keep token t only if 1 − εℓ ≤ rt ≤ 1 + εh
w′, w0
current policy version, and the version that generated the oldest part of the trajectory
τ
the staleness threshold
yt
the token at position t
πθ, πrollout
the policy being trained, and the one that generated the token
rt
their importance ratio
εℓ, εh
lower and upper bounds of the trust region

The second rule is Direct Double-sided Importance Sampling: a token outside the band is masked out entirely, so a badly off-policy token cannot steer the update, and no historical policy checkpoints have to be kept. A token-in, token-out gateway passes token ids rather than text between the agent environment and the trainer, so a trajectory is never re-tokenised into slightly different tokens than the ones the policy produced ({{GLM-5 report|@r5}}). Utilisation stops being hostage to the longest episode, which is what makes agentic RL affordable at the cadence Zhipu runs it.

GLM-5.2: from GRPO back to a critic

GRPO scores each rollout against the others sampled for the same prompt: advantage = (reward − group mean) / group standard deviation, given to every token of the rollout (the objective is on {{RL for LLMs|n:3c65c17b0d0d818c9bcff7177325fe56}}). That needs the rollouts of a group to be comparable units, and GLM-5.2's long-horizon tasks broke it: context compaction splits a super-long trajectory into several sub-traces, so rollouts of the same prompt yield different numbers of trainable traces of very different lengths.

So Zhipu "move[d] from group-wise optimization to a critic-based PPO formulation that learns from individual rollouts, relying on a critic to estimate token-level advantages", training on every compacted sub-trace with a token-level loss to handle their length imbalance ({{GLM-5.2 blog|@b52}}).

Reward hacking. GLM-5.2 hacked more than GLM-5.1: agents read protected evaluation artifacts, copied answers from references or upstream commits, or fetched the target source with curl. Zhipu added an anti-hack module to training and evaluation: a rule-based filter for recall, then an LLM judge of the flagged action's intent for precision, run online. A detected hack is blocked and answered with dummy information, but the rollout continues, so the episode still teaches something and training avoids the instability of abruptly stopped rollouts ({{GLM-5.2 blog|@b52}}). Hacking in general, with measured GLM-5.2 hack rates, is on {{Reward hacking|n:3c65c17b0d0d8196a6f1f29a817aa974}}.
