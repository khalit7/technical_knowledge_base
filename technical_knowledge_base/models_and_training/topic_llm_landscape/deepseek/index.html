The through-line: one question, asked at every layer

DeepSeek is a spinoff of High-Flyer, a Chinese quantitative hedge fund, and its line reads as if designed by people who pay for their own GPUs. One question runs through every release: what does it cost to train, and above all to serve, a frontier-quality model?

Nearly every named contribution asks it at a different layer: attention (MLA, then sparse attention, then compressed attention), feed-forward (fine-grained mixture-of-experts with shared experts, balanced without an auxiliary loss), numerics (FP8 training, low-precision serving), parallelism (DualPipe, DeepEP) and reinforcement learning (GRPO, which deletes the critic network). DeepSeek publish weights and tech reports, though not data, under permissive licences (R1 and V4.1-Flash are MIT). That is why the line matters beyond its own weights: its layout is the template other open MoE models reuse (Kimi K2 keeps MLA and the fine-grained-plus-shared expert layout, at 384 experts), and its price cuts are where its serving arithmetic reaches the market: V2 started the Chinese API price war, and V3.2-Exp cut API prices by more than half (DeepSeek).

In September 2026 the question reached the shape of the model itself. V4.1-Flash is a 552B encoder-decoder, the first shipped at frontier scale since the field settled on decoder-only stacks, and the reason DeepSeek give is the KV cache, not quality (model card). T5 had argued the encoder-decoder case on quality grounds years earlier without moving anyone; serving arithmetic did.

Attention: MLA, then DSA, then compressed attention

Decode reads every cached key and value once per new token, so the size of the KV cache decides how many sequences fit on a GPU and what each decoded token costs. DeepSeek attacked that number three times, each time on a different factor: how big each entry is (MLA, V2), how many entries a token reads (DSA, V3.2-Exp) and how many are stored at all (CSA and HCA, V4). The mechanisms (formulas, absorption, the decoupled RoPE key, the indexer, compression, with measurements) are taught once, on Attention variants; whole-model cache sizes against context length, with DeepSeek's generations among the presets, are in the KV-cache calculator on Long context. This section keeps what DeepSeek chose and what each choice bought it.

See MLA step by step on Attention variants →The before/after animation first built for this page: one token through one attention layer at DeepSeek-V3's dimensions, MLA against standard MHA. At the write step MLA stores 9 squares where MHA stores 512.

MLA (V2): one latent per token instead of per-head keys and values

V2 caches a 512-number latent plus a 64-number RoPE key per token per layer, 576 numbers where MHA with V2 and V3's 128 heads of 128 would cache 32,768. At V3's 61 layers in BF16 that is 70,272 bytes per token (68.6 KiB), against 3.81 MiB for MHA and 244 KiB for 8-group GQA. Every head still rebuilds its own keys and values from the latent, so DeepSeek got a cache smaller than GQA's without GQA's sharing; in decode the up-projections are absorbed and MLA runs as multi-query attention over one wide entry. Against DeepSeek's own dense 67B, V2 reported a 93.3% smaller cache and 5.76 times the maximum generation throughput (V2 paper). The price is extra projection arithmetic and kernels of its own, which is why later DeepSeek attention (DSA, V4's CSA) is built on MLA's decode shape rather than on GQA.

DSA (V3.2-Exp): keep the whole cache, read the top 2,048

V3.2-Exp (29 September 2025) left MLA's cache in place and cut what each decoded token reads: a lightning indexer, a few small heads in FP8 with ReLU instead of a softmax for throughput, scores every cached entry, and attention reads only the top 2,048. It is an approximation, so it was trained in, continued from V3.1-Terminus, and DeepSeek reported parity with V3.1-Terminus on standard and long-context benchmarks; every entry stays resident and the indexer still scores them all. DeepSeek cut API prices by more than 50% when it shipped (DeepSeek announcement).

CSA and HCA (V4): store less

V4 (DeepSeek-V4 report) shrinks what is stored, not only what is read. CSA layers merge every 4 tokens into one entry and run DSA's selection over the merged entries (top 1,024 in V4-Pro, 512 in V4-Flash); HCA layers merge every 128 tokens and read all of them; both keep a 128-token exact window. V4-Pro interleaves 30 CSA and 31 HCA layers. DeepSeek report the cache at about 2% of BF16 GQA-8 at 1M tokens (a baseline already 16 times smaller than MHA), and, against V3.2 at 1M tokens, 10% of the cache and 27% of the single-token FLOPs for V4-Pro, 7% and 10% for V4-Flash. Attention variants reproduces the 2% from the config and shows stored against read per layer; Long context sets every DeepSeek generation side by side against context length.

V4.1-Flash: the encoder-decoder cache stack

V4.1-Flash pushes the programme past the attention layer into the shape of the network. Splitting a 40-layer transformer into a 20-layer causal encoder and a 20-layer decoder means the prompt is encoded once into a shared representation rather than carried as a per-layer cache through one causal stack. DeepSeek combine that with cross-layer sparse attention with index reuse, hierarchical retrieval, an Engram memory and FP4 cache storage. The reported result is 890 bytes per token, roughly a quarter of V4-Flash's HBM footprint and an eighth of its SSD footprint, which is what makes long agent loops affordable rather than merely possible (model card; zartbot gives the HBM and SSD ratios as runtime and persistent cache storage). End-to-End Context Compression at Scale argued the encoder-decoder case for context compression on exactly this systems ground.

The detailed public walkthrough, zartbot's architecture breakdown, describes the mechanics behind those numbers.

Try: switch phase. A prompt position stops at the encoder; a generated token goes through all 40 layers, which is why one active-parameter count does not describe this model.

  • Why the active count differs by phase. Prompt positions pass through the 20 encoder layers only, so prefill activates 8B parameters; each generated token passes through all 40 layers, so decode activates 16B.
  • How the halves connect. Not through T5-style cross-attention: the decoder's global keys and values are projected from the encoder's 20th-layer hidden state by layer-dependent projection weights, so decoder layers reuse one shared cache instead of storing their own. The stack keeps three copies of encoder cache and one of decoder cache across its 40 layers.
  • Index reuse. Layers run in one of three modes: full layers compute their own cache entries and top-k indices; reindex layers reuse a full layer's entries but score them with their own indexer query to pick new top-k indices; reuse layers take both the entries and the indices unchanged. So neither the cache nor the full selection is rebuilt at every layer.
  • Experts. 384 routed experts with 6 active per token.

The layer pattern. The released config.json spells out which layer does what (config.json, read with zartbot; layers numbered from 0 as there). Layers 0 and 1 are sliding-window only. The rest of the encoder is three blocks of one full layer and five reuse layers, and its entries merge two adjacent positions into one (compress_ratios = 2). The decoder keeps every position: layer 20 is full and also builds the indexer's candidate pool; layers 24, 28, 32 and 36 reindex; all the others reuse. The Engram memory is injected at layers 1 and 14.

Try: hover or tap a layer. Count the layers that store a cache copy: 4 of 40 (the arcs show who reads each one). Then slide the context in the funnel: the first stage grows with the context, the second never ranks more than 16,384 positions.

The two-stage indexer. At decode, the full layer 20 ranks the context in blocks of 8 positions and keeps up to 2,048 blocks, a candidate pool of up to 16,384 positions; each later indexing layer then ranks only that pool and keeps its own top 512 (zartbot; candidate_topk_blocks, candidate_block_size and index_topk in the config). The model card's phrase is "bounding deeper indexer cost independently of context length" (model card).

What one entry costs. DeepSeek's attention kernels store a V4.1 cache entry as 528 bytes in FP8 (512 values plus 16 scale bytes) or 288 bytes in FP4 (512 values at half a byte plus 32 scale bytes) (FlashMLA), and the model card says the main cache is FP4. As an estimate, not DeepSeek's breakdown: if the three encoder copies hold one entry per two positions and the decoder copy one per position, the main cache is 3 × 288 ÷ 2 + 288 = bytes per token; the reported 890 also counts the indexer keys.

The MoE layer: fine-grained experts, shared experts, balancing without a loss

A mixture-of-experts (MoE) layer replaces the feed-forward network with many expert networks and a router that sends each token to a few of them, so compute per token follows the active parameters while capacity follows the total. Routing, capacity factors, expert parallelism and what breaks at inference are on Mixture of experts; this section covers what DeepSeek do differently.

DeepSeekMoE: many narrow experts plus shared ones

DeepSeekMoE, from V2, makes two changes to the Mixtral-style mixture of experts (a handful of large experts, two active per token).

  • Fine-grained experts: split each expert into several narrower ones and activate more per token, so V3 routes 8 of 256 rather than 2 of 8. The active parameter count is unchanged, but the number of distinct expert combinations explodes, which is what lets experts specialise narrowly instead of each being a generalist.
  • Shared experts: experts every token passes through unconditionally, absorbing the common computation otherwise duplicated inside every routed expert and freeing routed capacity for what is actually specialised.

Which experts light up is random here; a real router picks by affinity.

Both changes cost routing and communication overhead: more experts touched per token means more all-to-all traffic, which is why DeepSeek ended up writing their own communication kernels (DeepEP).

Aux-loss-free load balancing

Left alone, routers collapse: tokens pile onto a few popular experts, wasting the rest, and under expert parallelism the most loaded GPU sets the step time for everyone. The standard auxiliary balancing loss works but is a second objective fighting the first, pushing tokens away from the expert that would have modelled them best. V3 instead adds a bias to each expert's affinity for the top-k choice only (V3 report):

gi,t′={si,tifsi,t+bi∈Topk({sj,t+bj},Kr)0otherwise
bi
expert i's bias, used only to choose; the gate weight that scales the expert's output still comes from the unbiased si,t, so the bias never enters the gradient

After each step, the bias of every overloaded expert (measured over the whole batch) is decreased by γ and that of every underloaded one increased by γ, the bias update speed: 0.001 for V3's first 14.3T tokens and 0 for the last 500B. Balancing becomes a control loop outside the loss: it costs nothing in the objective and cannot trade quality for uniformity. V3 kept only a tiny sequence-wise auxiliary loss (weight α = 0.0001) against extreme imbalance inside one sequence, and dropped no tokens in training or inference; V4 uses the same values.

Worked example (illustrative numbers). A token scores expert A at 0.62 and expert B at 0.60, with one slot left in its top-k. A has been overloaded for 30 consecutive steps, so bA = −30 × 0.001 = −0.03, while B's bias is 0. The selection scores are 0.62 − 0.03 = 0.59 for A and 0.60 for B, so the token goes to B. B's gate weight is computed from its true affinity, 0.60, renormalised with the other selected experts: the bias moved the decision boundary and nothing else.

Try: a toy router (illustrative: 16 experts, top-2, 1,024 tokens per step, some experts made popular on purpose). With the bias off, the popular experts stay overloaded; switch it on and the control loop pulls every expert towards the mean. A larger γ converges faster and jitters more.

V4 adds anticipatory routing against loss spikes, which DeepSeek traced to outliers in the MoE layers that routing amplifies: at step t the features use the current parameters, but the routing indices are computed with the parameters of step t − Δt, decoupling the router's updates from the backbone's. It is not always on: an automatic detector triggers a short rollback and switches it on only when a loss spike occurs, at about 20% extra wall-clock time while active, after which training reverts to the standard mode (V4 report).

MTP: multi-token prediction

Multi-Token Prediction (MTP) adds lightweight modules that predict, during training, not only the next token but the one after it (and further out) from the same trunk: denser supervision per forward pass, so the model learns more per token seen, and representations forced to look further ahead. Unlike earlier multi-token work with parallel independent heads, V3's modules are sequential, each a transformer block that takes the previous depth's representation and the next token's embedding, so the causal chain is kept at every depth. V3 and V4 use depth 1 (one extra token), weighted 0.3 in the loss for most of training and 0.1 at the end. At inference the extra module is already a draft of the next token, reusable as a built-in draft model for speculative decoding, with no separate draft model to train, align and host: V3 reports the second token accepted 85% to 90% of the time, for 1.8 times the tokens per second (V3 report).

V4's other changes: mHC and Muon

mHC (Manifold-Constrained Hyper-Connections) widens the residual stream. Instead of one residual vector per token, V4 carries nhc = 4 of them and mixes them around each block (V4 report):

Unconstrained hyper-connections were unstable when many layers were stacked. mHC projects Bl onto the doubly stochastic matrices (non-negative, every row and column summing to one) with 20 Sinkhorn-Knopp iterations, which bounds its spectral norm by 1 so the residual mapping cannot amplify the signal; and the set is closed under multiplication, so a deep stack stays bounded too. The three maps are generated from the input, which is why this costs little: nhc is tiny next to d.

Try: a random positive 4 × 4 matrix (illustrative) and the Sinkhorn-Knopp iterations, which alternately rescale its rows and its columns to sum to one. Slide from 0 to 20 and watch the sums go to 1 and the spectral norm fall to 1.

Muon replaces AdamW for most weight matrices: it orthogonalises each momentum update with Newton-Schulz iterations before applying it, with AdamW kept for the embedding, the output head and the RMSNorm weights. V4-Flash was pretrained on 32T tokens and V4-Pro on 33T (V4 report).

Numerics and systems: FP8, DualPipe, DeepEP, disaggregation

FP8 mixed-precision training was V3's headline systems result: the first validation of FP8 training on an extremely large model, roughly halving memory traffic and raising effective tensor-core throughput against BF16 (V3 report). Naive FP8 fails because the format's dynamic range is small: one outlier forces the tensor's scale down and small gradients flush to zero. The recipe:

  • Fine-grained scaling: one scale factor per 1 × 128 tile of activations and per 128 × 128 block of weights, rather than one per tensor, so one outlier cannot poison a whole matrix.
  • Sensitive components in higher precision: master weights, optimizer state, normalisation, the embedding and the output layers.
  • Accumulation promoted to FP32 every 128 elements, because the H800 tensor cores keep only about 14 bits when accumulating FP8 products.

On their reported curves the loss stays within 0.25% relative error of BF16; the price is a much more delicate training stack. V4 goes further at the serving end: the routed expert weights are stored in FP4 through quantisation-aware training, and the lightning indexer computes in FP4 (V4 report).

DualPipe is a pipeline-parallel schedule. Ordinary pipeline parallelism leaves "bubbles", stretches where a stage waits on its neighbour with nothing to do. DualPipe feeds the pipeline from both ends and overlaps one micro-batch's MoE all-to-all dispatch and combine traffic with another's compute, hiding expert communication behind arithmetic instead of serialising it in front. This mattered more to DeepSeek than to most: they trained on H800s, whose interconnect bandwidth is cut relative to the H100, so communication rather than FLOPs was the binding constraint, and 20 of each H800's 132 streaming multiprocessors were given over to communication (V3 report).

How big the bubble is. In a pipeline of PP stages, each micro-batch passes forward through every stage and then backward. The chunks have durations F (forward), B (full backward) and W (the backward-for-weights part, which zero-bubble schedules split off and run later to fill gaps); F&B is one forward and one backward chunk from different micro-batches run together, so that one's all-to-all traffic hides behind the other's compute. DeepEP, DeepSeek's open-sourced expert-parallel communication library, is hand-written dispatch and combine kernels for MoE routing traffic, with separate NVLink and RDMA paths and a low-latency variant for decode. It exists because generic collective operations are not shaped like MoE traffic, which is a skewed, dynamically routed, token-level all-to-all rather than a uniform exchange. V4 folds computation, communication and memory access for the MoE layer into a single fused kernel (V4 report).

Prefill/decode disaggregation splits serving across two GPU pools because the phases have opposite bottlenecks: prefill is compute-bound and batches thousands of tokens at once; decode is memory-bandwidth-bound and produces one token per sequence per step. Interleaving them configures each phase wrong; separating them lets each pool be batched, parallelised and sized for its own limit, at the cost of shipping the KV cache between pools. It is now standard in serious vLLM and SGLang deployments; Inference techniques covers it, with speculative decoding, across engines.

Expert placement in serving: replicate and pack

The bias loop balances the router during training, but a deployed model still has inherently hot experts, and under expert parallelism the GPU holding them sets everyone's step time. DeepSeek's serving answer is the Expert Parallelism Load Balancer (EPLB): duplicate the heaviest experts ("redundant experts") and pack the copies onto GPUs so that every GPU carries a similar load, each copy taking an equal share of its expert's traffic (EPLB repository). It has two policies. Hierarchical, used when the number of nodes divides the number of expert groups: pack whole expert groups onto nodes evenly, replicate within each node, then pack onto that node's GPUs; V3's routing is group-limited (a token's experts come from at most 4 of its 8 expert groups, topk_group and n_group in its config.json), so keeping a group on one node keeps that traffic inside the node. Global, used otherwise: replicate anywhere and pack across all GPUs. The README suggests hierarchical for prefill (smaller expert parallelism) and global for decode (larger).

In production DeepSeek run V3 and R1 prefill on units of 4 nodes (32 GPUs, EP32) and decode on 18 nodes (144 GPUs, EP144), each with 32 redundant experts: 256 + 32 = 288 expert copies, so 9 routed experts per GPU in prefill and 2 in decode, each GPU also holding the shared expert (day 6).

Try: the default is the README's worked example (12 experts in 4 groups, 4 redundant copies, 2 nodes of 4 GPUs, the published loads of its first layer); the EPLB view reproduces its published placement exactly. Compare with the naive view, which puts expert i on GPU i mod 8 with no copies, and read the max-to-mean ratio: that is how much longer the busiest GPU takes than an even split. Training and RL: GRPO, R1, hybrid thinking

GRPO (Group Relative Policy Optimization), from the DeepSeekMath work, is a PPO variant whose distinguishing move is deleting the value network. PPO needs a learned critic of roughly policy size for the advantage baseline: a second large model in memory, a second thing to train, a second thing to go unstable. GRPO instead samples a group of completions for the same prompt, scores them all, and uses the group's own statistics as the baseline:

A^i=ri−mean(r1,…,rG)std(r1,…,rG)
ri
the reward of completion i of a group of G
Âi
the advantage given to every token of completion i

Try: click a reward to flip it between 0 and 1. The default group of four with rewards 1, 0, 0, 1 has mean 0.5 and standard deviation 0.5, so the correct answers get +1 and the wrong ones −1. Make all four the same: the group teaches nothing.

That buys roughly half the memory and one fewer model to babysit, and fits verifiable-reward RL naturally, since many rollouts per prompt are cheap when scoring is automatic. It costs those extra rollouts, moving the expense into sampling, and later work showed the standard-deviation normalisation biases across prompt difficulty and response length, which several successor variants simply drop. The full objective, its clipping and the successors are on RL for LLMs: RLHF, GRPO, RLVR.

RLVR and R1. R1-Zero applied GRPO directly to the V3 base with rewards computed only from automatically checkable outcomes (mathematics with a known answer, code that passes tests) plus formatting, with no supervised reasoning traces at all: RL with verifiable rewards (RLVR). Long chains of thought, self-checking and backtracking emerged from that alone, and the emergence, not the benchmark number, is the result that mattered: reasoning was reachable without proprietary reasoning data, which is what made an open reasoning era possible rather than merely announced. R1 proper added a small cold-start supervised set to fix R1-Zero's unreadable, language-mixed output, then RL, then a further supervised-plus-RL round. DeepSeek also distilled R1's traces into Qwen and Llama bases from 1.5B to 70B, showing the behaviour transfers by ordinary supervised fine-tuning (SFT) on traces, which is why half the open reasoning models of 2025 were R1 distillations (R1 paper).

The recipe as a flow. R1's training alternates supervised fine-tuning and RL four times over, and most of the data in it was generated by the model's own predecessors: the cold-start set was partly R1-Zero output made readable, and 600K of the 800K supervised samples were sampled from the RL checkpoint itself, keeping only correct answers (R1 paper, section 2.3). The distilled students are the same 800K samples pointed at smaller models.

Try: click a stage for its data, its reward and what it fixed. Band widths follow the published sample counts (the cold start is only "thousands", so it is drawn thin). Then read the scatter: at 14B and 32B the students keep most of the teacher's AIME score.

Hybrid thinking (V3.1 onward) folds chat and reasoning into one checkpoint, with long-chain mode selected by the prompt template rather than by loading different weights (DeepSeek). One set of weights, one cache, one deployment, and the caller pays for deliberation only where it earns its latency.

Specialists, then one student (V4). V4's post-training first trains a separate expert model per domain (mathematics, coding, agents, instruction following), each by SFT and then GRPO against domain reward models, and then consolidates them into one model by on-policy distillation: the unified model samples its own outputs and is trained to minimise the reverse KL divergence to the teachers (V4 report).

These are costs of running one evaluation task, not token prices; AA's blended token prices are $0.18 and $0.69 per million: on token price V4.1-Flash is about 3.8 times cheaper, per task only about 2.5 times, because it spends more tokens on each task. V4.1-Flash reports Terminal-Bench 2.1 at 90.6, a Codeforces rating of 3471 and GPQA Diamond at 90.9 (API changelog), with DeepSeek conceding it holds up better on shorter agent loops than on the longest-horizon evaluations: the generation bought serving cost rather than capability headroom.

The 1017 checkpoint is, in DeepSeek's words, "a minor update" that "reduces task execution time and output length", but its own table moves most on the long agent loops the September build conceded: Terminal-Bench 4.0 from 31.2 to 42.3 (in the Claude Code harness), DeepSWE v1.1 from 74.2 to 77.0 (mini-swe-v2 harness), AutomationBench v1.0.6 from 54.8 to 60.5 and Humanity's Last Exam without tools from 36.8 to 42.6. Claude Opus 5 still leads most rows of that table (51.8 on Terminal-Bench 4.0, 56.3 on HLE). On Vals AI's fixed mini-swe-agent harness the 1017 checkpoint scores 31.82% on Terminal-Bench 4.0 at $0.54 a task, against 65.15% for Claude Opus 5.5 at $13.20 (Vals AI). Parameter counts disagree across sources: Artificial Analysis and the September card give 552B, while the 1017 repository stores 763B of tensors (model card).

Search and Fetch. The same day DeepSeek opened two tool APIs priced per call rather than per token: Search returns up to 50 ranked results and Fetch turns a page into Markdown, each at $0.75 per 1,000 successful calls, with billing from 1 November 2026 (Beijing time) and calls made through the server-side tools of DeepSeek Harness, Claude Code and Codex free before then (DeepSeek).

Common mistakes and misconceptions

"The aux-loss-free bias changes the expert's output."
The bias only decides which experts are chosen; the gate weight comes from the unbiased affinity, so the bias never appears in the gradient.
"V4.1-Flash has 16B active parameters."
It has 8B during prefill and 16B during decode; one active count does not describe an encoder-decoder, and capacity plans built on one figure mislead.
"The $5.6M figure is what V3 cost."
It is the official training run, 2,788K H800 GPU hours (2,664K of pre-training, 119K of context extension and 5K of post-training) priced at an assumed $2 per H800 hour, so $5.576M, and DeepSeek say it excludes prior research and ablations (V3 report, Table 1). R1's own training added a reported 147K hours, $294K at the same rate (R1 paper, v2, appendix B.4.4), while SemiAnalysis estimate the hardware available to DeepSeek at about 50,000 Hopper GPUs and $1.6B of server capex, an outside estimate (SemiAnalysis).
"DeepSeek's serving runs at a 545% margin."
That is DeepSeek's theoretical figure for one day in February 2025 if every token had been billed at R1's prices; they say actual revenue was substantially lower, because V3 is cheaper, web and app use is free and night-time discounts applied (day 6). On their figures the day (27 to 28 February 2025) cost $87,072, an average of 226.75 H800 nodes at $2 per GPU-hour, against a theoretical $562,027 of revenue (day 6).
"The V4 Flash vision model is DeepSeek's only image model."
It was, from 21 August 2026. V4.1-Flash has native vision, and since 14 September the deepseek-v4-flash-vision-exp name routes to it (API changelog).

DeepSeek LLM and Coder

2023 (DeepSeek LLM 67B: 29 November 2023, GitHub)
  • A High-Flyer (quant fund) spinoff's first models: early Llama-style dense models, notable for the scaling-law and data work that set up what followed.

V2

May 2024 (6 May, GitHub) · V2 paper
  • Introduced MLA and DeepSeekMoE (fine-grained plus shared experts).
  • Against DeepSeek 67B: 42.5% lower training cost, a 93.3% smaller KV cache and 5.76 times the generation throughput.
  • MLA's serving cost is what let DeepSeek start the Chinese API price war.

V3

December 2024 (26 December, Hugging Face) · V3 report
  • MLA plus a 256-expert MoE (8 routed active, 1 shared), aux-loss-free bias-based balancing, multi-token prediction, FP8 mixed-precision training, DualPipe.
  • The official training run took 2.788M H800 GPU hours, which DeepSeek priced at $5.576M assuming $2 per GPU hour on a 2,048-GPU cluster, excluding prior research and ablations. The figure shook the industry, and the report is unusually explicit about the infrastructure behind it.

R1

January 2025 (20 January, DeepSeek) · R1 paper
  • GRPO-based RL on the V3 base produced o1-class reasoning; R1-Zero showed the behaviour emerging from pure RL.
  • MIT licence, plus distillations from 1.5B to 70B.
  • Triggered the "DeepSeek moment" and Nvidia's record one-day selloff.

V3.1

August 2025 (21 August, DeepSeek)
  • Chat and reasoning merged into one hybrid-thinking checkpoint.

V3.2-Exp

September 2025 (29 September, DeepSeek) · V3.2 paper
  • DSA, the lightning-indexer sparse attention, continued from V3.1-Terminus.
  • API prices cut by more than half at launch.

V4: V4 Pro and V4 Flash

April 2026 (24 April, The Next Web) · V4 report
  • The current family: two MoE models, V4 Pro (1.6T total / 49B active) and V4 Flash (284B / 13B).
  • Hybrid compressed attention (CSA over groups of 4 with top-k selection, HCA over groups of 128) with low-rank queries and grouped output projections holds the KV cache near 2% of BF16 8-group GQA's at 1M context; mHC residuals; Muon; FP4 expert weights.
  • V4-Pro at maximum reasoning effort reports 80.6% resolved on SWE-bench Verified with DeepSeek's in-house harness (a bash tool and a file-edit tool, up to 500 steps and 512K tokens of context), against 80.2 for Kimi K2.6 Thinking in the same table of the V4 report.
  • V4-Flash at maximum effort reports 73.2 on BrowseComp against V4-Pro's 83.4, with a quarter of the active parameters.

V4 Flash vision

August 2026 (21 August) · API docs
  • deepseek-v4-flash-vision-exp, an experimental vision variant of V4 Flash and, until V4.1-Flash, the only DeepSeek model accepting image input.
  • Images are normalised to at most 384 tokens each, up to 600 images per request.
  • Since 14 September its name routes to V4.1-Flash (API changelog).

V4.1-Flash

September 2026 (10 September, API changelog) · model card
  • 552B total, 8B active during prefill and 16B during decode; MIT licence; weights on Hugging Face in 48 safetensors shards.
  • A causal encoder-decoder, 40 layers split 20 and 20: the first frontier-scale open model to abandon the decoder-only consensus. 1M-token context, native vision, and a reasoning-effort dial from 1 to 100.
  • Reported Terminal-Bench 2.1 at 90.6, Codeforces 3471 and GPQA Diamond 90.9, with DeepSeek conceding it holds up better on shorter agent loops than on the longest-horizon evaluations: the generation bought serving cost rather than capability headroom.
  • Pricing $0.30 input and $1.20 output per million tokens at peak and half that off-peak, cache hits from $0.006 (pricing).
  • The API id is deepseek-flash, and since 14 September at noon Beijing time the deepseek-v4-flash names route here, so a call naming V4 Flash is answered by V4.1-Flash. V4 Pro is not rerouted: it keeps its own service and pricing ($1.32 input and $3.96 output per million at peak, cache hits $0.044).

V4.1-Flash-1017

October 2026 (17 October, DeepSeek news) · model card
  • "A minor update to DeepSeek-V4.1-Flash" that "reduces task execution time and output length"; MIT licence, 1M context, served as deepseek-flash at unchanged prices.
  • DeepSeek's table: Terminal-Bench 4.0 31.2 to 42.3 (Claude Code harness), DeepSWE v1.1 74.2 to 77.0, AutomationBench v1.0.6 54.8 to 60.5. Artificial Analysis: 45 on Intelligence Index v4.3 at $0.26 per task, second among open weights.
  • Launched with the Search and Fetch APIs at $0.75 per 1,000 successful calls each.

The DeepSeek template across the field

DeepSeek's layout (MLA attention, many narrow routed experts plus a shared one, a few dense layers first) became a template other labs reuse. Pick two models: the card highlights every configuration value that differs, and the rows beneath compute what those values buy. MLA's cache depends only on the latent, the RoPE key and the layer count, never on the number of heads, so models that change the heads change their attention compute and not their cache.

Try: the default pair is V3 against Kimi K2: half the heads and 384 experts, yet exactly the same 70,272 bytes of cache per token, and half the attention FLOPs. Then pick Mistral Large 3 (same cache again) and GLM-4.5, which uses grouped-query attention instead.
