Quantization and Precision

How numbers are stored for training and serving: the formats, how a scale is shared, post-training quantisation and the outlier problem, quantisation-aware training, and mixed-precision, FP8 and 4-bit training. The idea in one sentenceA low-precision number is a small code times a scale shared with its neighbours, so how much a model loses depends less on the bit count than on how many numbers share each scale and whether an outlier sets it; every method on this page (block formats, GPTQ, AWQ, SmoothQuant, rotations, quantisation-aware training, FP8 and 4-bit training) is a way to choose that scale, or to move the outlier, so the model's outputs barely change.

1. Number formats: range against precision

A gradient of 10−8 stored in fp16 becomes 0; in bf16 it survives. The value 500 in fp8 E4M3 saturates at 448, while E5M2 stores 512. And 1 + 2−8 is exact in fp16 but rounds to 1 in bf16. All three follow from two fields of the bit layout: the exponent bits set the range (how many powers of two, or binades, the format spans), the mantissa bits set the precision (the relative step between neighbouring values, 2−m). How the bits encode a value, subnormals and rounding are built bit by bit in Numerical computing for ML (sections 2 to 4); this page starts from the consequence.

Fewer exponent bits leave fewer binades: E4M3 spans under 18, E2M1 under 4, bf16 the same 2−126 to 2128 as fp32

Range of seven floating formats on one log2 axis; pale is the subnormal tail, solid the normal range. Computed from each layout derived: largest = 2emax × (2 − 2−m), smallest subnormal = 21−bias−m. fp16 covers 40 binades.

Any number through every format: its bits, what comes back, the error and the step at that size

Rounding is round-to-nearest-even with subnormals, as in hardware conversion. Formats with infinities (fp32, tf32, bf16, fp16, E5M2) overflow to infinity once past the largest value by half a step; E4M3 and E2M1 have none, and conversion kernels saturate. "Step here" is the gap between neighbouring values at this magnitude (one unit in the last place).

So bf16 is less precise than fp16 (7 mantissa bits against 10, a relative step of 0.0078 against 0.00098); it won training because of range: its exponent is fp32's, so small gradients do not underflow and no loss scaling is needed (section 6). 2. Sharing a scale: per tensor, per channel, per block

Integer and 4-bit formats store a code and a scale: q = round(x / scale) + zero_point, and the value read back is (q − zero_point) × scale. The scale is set by the largest magnitude in the group it covers (absmax; asymmetric schemes also fit a zero point to the minimum), so one large value sets the step for everything that shares its scale. That is why the choice of scope matters more than the bit count. The animation runs one block of 32 real weights through five scopes; the weights are the exact bf16 values of the layer in the hero, chosen because its largest weight, −1.664 in input column 5, is 64 times the layer's standard deviation (0.026) measured here.

The quantisers are ported exactly from src/qformats.py and follow the specs: INT4 symmetric absmax; MXFP4 with the OCP shared exponent floor(log2(amax)) − 2 (Rouhani et al. 2023, Algorithm 1); NVFP4 with an E4M3 block scale and a per-tensor FP32 scale of amax / (448 × 6).

The scale costs bits. Bits per weight = element bits + scale bits / block size derived: INT4 with an fp16 scale and zero per 128 is 4 + 32/128 = 4.25; MXFP4 4 + 8/32 = 4.25 (MXFP8 8.25); NVFP4 4 + 8/16 = 4.5, plus one FP32 per tensor; NF4 with double quantisation 4 + 8/64 + 32/(64 × 256) = 4.127; llama.cpp's Q4_K block 4.5 and a whole Q4_K_M file about 4.9. Budget memory on these effective bits, never on the nominal 4.

MXFP4 against NVFP4. An E8M0 scale is a power of two, so a block's largest value lands anywhere between 4 and 8 times the scale, and above 6 it clips; NVFP4's E4M3 scale puts the largest on 6 almost exactly, over blocks half as long. Pick MXFP4 and row 223, block 0, in the animation to see the clipping. MXFP4's advantage is portability: it is an open standard that also runs on AMD (the MI355X, per Spheron's guide, a vendor blog that calls its own accuracy table directional).

3. Post-training quantisation: GPTQ and AWQ

PTQ quantises a trained model with no retraining. fp32 to fp16 or bf16 is essentially free; integer and 4-bit formats need the scales of section 2, and activations need a choice of when to set them: dynamic PTQ computes them on the fly per batch or token (a little latency, no calibration data), static PTQ freezes them from a calibration set (lower latency; inputs beyond the frozen range clip). Weight-only methods are the LLM mainstream because generating one token at a time is memory-bound: the time goes into streaming weights, so shrinking them speeds decoding up even if the multiply still runs in 16-bit. When the matmul itself is the bottleneck, FP8 W8A8 is the default (section 7).

Round-to-nearest treats each weight alone. GPTQ (Frantar et al. 2022) quantises a layer one column at a time and, after each column, adjusts the columns not yet quantised to cancel the error in the layer's output, using approximate second-order (Hessian) information from calibration activations (H = 2XTX, with one row of X per calibration token). When two input channels carry similar signals, an error rounded into one can be paid back by the other:

GPTQ pushes each column's rounding error into the columns still to come, so a later weight rounds the other way

illustrative One row w = (0.60, −0.88, −0.76, 0.20), a grid with step 0.25 and six calibration inputs, so every number fits on screen; the update is the paper's Algorithm 1: H = 2XTX plus 1% of its mean diagonal (dampening), U the upper Cholesky factor of H−1, and after quantising column j, wk ← wk − (wj − qj) / Ujj × Ujk for every later k. Round-to-nearest stores 0.50, −1.00, −0.75, 0.25 (output error 32.9%); GPTQ stores 0.50, −0.75, −0.75, 0.25 (8.5%), with a slightly higher weight error (13.0% against 12.4%) derived by src/visuals_ref.py.

GPTQ is built on Optimal Brain Quantization with lazy batch updates and a Cholesky reformulation; it quantised 175B models "in approximately four GPU hours" to 3 or 4 bits. Act-order (quantising columns in decreasing order of activation size) is not in the paper; it came from the GPTQ repository, where it lowered LLaMA-7B's WikiText-2 perplexity from 7.15 to 6.09 (IST-DASLab/gptq).

AWQ (Lin et al. 2023, MLSys 2024 best paper) starts from "protecting only 1% salient weights can greatly reduce quantization error", and picks the salient channels from the activation distribution, not the weights. Rather than keep them in high precision, it multiplies those input channels by a scale s = sXα before 4-bit quantisation (α by grid search over [0, 1]) and folds 1/s into the previous operation; group size 128. It is the weight-side half of section 4's migration, animated there.

Lower weight error is not the goal: GPTQ and AWQ raise it and lower the output error

The 4.25-bit schemes on the whole layer measured here: round-to-nearest with groups of 128 gives 7.80% output error, AWQ 6.20% and GPTQ with act-order 6.12%, while both methods raise the plain weight error (from 10.8% to 12.8% and 18.1%): they spend error where the activations are small. Weight error is not output error, which is why both need calibration data.

Below 4 bits the data matters as much as the method. At 2 bits scalar PTQ (one value per weight, as above) collapses to chance on QA tasks; vector codebooks, which quantise groups of weights to entries of a learned codebook, plus jointly chosen calibration and recovery-training data reached about 2.3 effective bits at 89 to 97% of full-precision QA accuracy on 3.8B to 32B dense and MoE models, with 1.4 to 30 times less compute than the best quantisation-aware baseline (Beyond 4 bits (arXiv 2610.28537)).

4. Outliers, and moving them out of the way

A few channels with huge magnitudes destroy naive scaling. In activations they are a property of the channel, recurring on every token: LLM.int8() found features "up to 20x larger than in other dimensions" in about 25% of layers of small models, and "at around 6.7B parameters, a phase shift occurs" where all layers and 75% of sequence positions are affected, though outliers remain "about 0.1% of all features" (Dettmers et al. 2022; its fix keeps those features in fp16, decomposing the matmul at a threshold of 6.0). In the Qwen layer used on this page, the largest input channel peaks at 31.9 against a median channel peak of 2.0, a 16-fold gap measured here. The fixes are finer scales (section 2), compensating for the error (GPTQ, section 3), moving the difficulty somewhere easier (SmoothQuant, AWQ), or rotating it away (QuIP#, QuaRot, SpinQuant).

Migration. Divide each activation channel by a factor s and multiply the matching weight column by s: the product XWT is unchanged exactly, but the outlier channels shrink. SmoothQuant (W8A8; Xiao et al. 2022) chooses s so both sides quantise well; AWQ chooses it so salient weights span more levels. The animation runs both on the same real input, each against the plain method it improves: 16 tokens of A Tale of Two Cities entering the same Qwen layer, on 64 of its 896 input channels (the 8 with the largest activations on the calibration text plus 56 at random) and 8 of its output rows (at random). Scales come from a separate calibration text (the opening of Pride and Prejudice), as they would in practice.

Try: run W8A8 plain, then SmoothQuant at α = 0.5 (the paper's default for OPT and BLOOM). Then drag α: near 0 the weights' own outliers are pushed into the activations and the error grows; near 1 the weights take all of it. Then compare INT4 plain against AWQ.

Rotation. Multiply the activations by an orthogonal matrix and the weights by the same matrix; the product is unchanged, because the rotation cancels (XR)(WR)T = XWT, but each rotated channel is a mix of all the original ones, so no channel stands out and one 4-bit scale fits every value.

Rotations are what make 2 to 3 bit weights and 4-bit activations work (QuIP#, QuaRot, SpinQuant), and NVFP4 pretraining uses the same trick on its gradients (section 6).

Published results for rotations

QuIP# (randomised Hadamard plus E8 lattice codebooks plus fine-tuning) has "QuIP# 3 bit" beating "a theoretical lossless 4 bit model" on Llama 2 (Tseng et al. 2024); QuaRot's W4A4 Llama 2-70B with a 4-bit KV cache loses "at most 0.47 WikiText-2 perplexity" and keeps 99% of zero-shot performance (Ashkboos et al. 2024); SpinQuant learns the rotation, narrowing W4A4KV4 LLaMA-2 7B's zero-shot gap to 2.9 points (Liu et al. 2024).

5. Quantisation-aware training, and models built ternary

PTQ asks a trained model to survive rounding it never saw. QAT inserts fake quantisation during training: quantise then dequantise in the forward pass, so the loss sees the rounding, and pass the gradient straight through the rounding in the backward pass (the straight-through estimator, Bengio et al. 2013), so the model learns weights that survive the eventual precision.

The forward pass uses the rounded weight; the backward pass pretends the rounding is not there

Rounding has zero gradient almost everywhere, so without the straight-through estimator no gradient would reach w. The master weight stays in high precision and keeps accumulating small updates; only its rounded copy is used in the forward pass and shipped.

It costs extra training compute and recovers most of PTQ's loss at 4 bits and below: Google's QAT for Gemma 3 (to Q4_0, about 5,000 steps) reports "We reduce the perplexity drop by 54%" against PTQ (Google), and torchao's QAT of Llama 3 8B recovers "up to 96% of the accuracy degradation on hellaswag and 68% of the perplexity degradation on wikitext" (PyTorch torchao). QLoRA-style training (frozen NF4 base plus bf16 adapters) is the budget alternative: it trains adapters on a quantised base rather than teaching the base to be quantised (PEFT, QLoRA).

Ternary weights take only −1, 0 and +1 (times a scale), and that is where the compression floor currently sits: trained that way from the start, the quality cost is smaller than the bit count suggests. BitNet b1.58 is the model family that made ternary training work (Ma et al. 2024); Ternary Bonsai 2 27B (PrismML, 17 September 2026), "based on Qwen3.8 27B", stores "1.76 effective bits per weight" and keeps 98.2% of its base model's aggregate benchmark score (PrismML). These models were built ternary rather than converted, so their bits per weight are a packing result, not a reason to quantise an ordinary checkpoint this far: an ordinary dense model rounded to under 3 bits falls off a cliff (section 7).

Current QAT practice, and what each approach has been shown to cost, as published

Ternary in detail: Bonsai 2's numbers, and why the floor is not 1.585 bits

Ternary Bonsai 2 27B "uses ternary {−1, 0, +1} weights with FP16 group-wise scaling, for 1.76 effective bits per weight and a total model footprint of 5.9GB", "more than 9x smaller while retaining 98.2% of aggregate benchmark performance": it scores 83.9 against Qwen3.8 27B's 85.4, with a 262K-token context, text and image input, agentic tool use in its benchmark suite, Apache 2.0, and up to 143 tokens per second on an RTX 5090 (PrismML, model card). The headline numbers check out derived: 27 × 109 × 1.76 / 8 = 5.94 GB; 16 / 1.76 = 9.1 times; 83.9 / 85.4 = 98.2%.

The nominal floor is not 1.585 bits either. Three values carry log2 3 = 1.585 bits; packing five trits in a byte (35 = 243 fits in 256) gives 1.6, and with power-of-two group sizes it "rounds up to 1.625", because it treats the three values as equally likely. They are not: across 29 ternary models, zeros are "up to 51.5% of all weights". BITCOS stores "a dense presence bitmap plus a compacted sign vector" and "costs 2 − z bits per weight element given a zero density z": it beats five-trit packing in 26 of the 29 models, reaches 1.485 bits on the sparsest, and decodes up to 1.18× faster on CPUs and 1.27× on GPUs (Georganas et al. 2026). 2 − z beats 1.625 once zeros pass 37.5%, and beats log2 3 once they pass 41.5% derived. For comparison, llama.cpp's own ternary types cost 1.6875 (TQ1_0: 54 bytes per 256 weights, scale included) and 2.0625 bits (TQ2_0) from the block structs.

6. Training in low precision: mixed precision, FP8 and NVFP4

Every linear layer runs three matmuls per training step: the forward pass (Y = XWT), the gradient for the layer below (dX = dY·W) and the gradient for the weights (dW = dYTX). A training recipe is a choice of format and scale for the inputs of each, plus what stays in high precision for the update. The rule since Micikevicius et al. 2017: compute-heavy operations run in low precision; numerically sensitive state stays high. Float32 master weights and optimiser state, because otherwise small updates round away; matmuls in fp16 or bf16 on tensor cores, with products summed in fp32 and reductions, softmax and norms often in fp32; and, in fp16 only, loss scaling (multiply the loss by S before the backward pass, divide the gradients by S in fp32), because fp16 gradients underflow. bf16 has fp32's exponent range and skips loss scaling entirely: this is why bf16 became the default.

Each recipe picks a format for the six matmul inputs; the update stays in high precision in all of them

fp16 mixed precision (Micikevicius et al. 2017): fp16 copies of the weights, activations and gradients; the loss is multiplied by S so small gradients land inside fp16's range (smallest subnormal 2−24), and divided out in fp32 before the update. Master weights and Adam's moments in fp32.

bf16 mixed precision: the same, with bf16, and no loss scaling. Master weights, first and second moments in fp32. This is where the 16 bytes per parameter of Adam training come from: 2 (bf16 weights) + 2 (gradients) + 4 + 4 + 4 (fp32 master, first and second moments) derived, as in ZeRO.

FP8 with NVIDIA's Transformer Engine (Hopper and Blackwell): "E4M3 for weight and activation tensors, and E5M2 for gradient tensors" (FP8 formats, Micikevicius et al. 2022), which TE's HYBRID recipe does exactly, with one scale per tensor. Its original "delayed scaling" uses the scale from the previous iteration and an amax history (default 1,024 steps) (TE docs). Weights and gradients accumulate in higher precision.

DeepSeek-V3's fine-grained FP8 at 671B: 1 × 128 tiles for activations, 128 × 128 blocks for weights, E4M3 on all tensors (gradients too), partial sums promoted to FP32 every 128 elements, and "the relative loss error of our FP8-training model remains consistently below 0.25%" against BF16 (§3.3). The DeepSeek-V3 paper page animates the tile and block scaling and the accumulation.

NVFP4 pretraining (NVIDIA 2025) needed four things: random Hadamard transforms (16 × 16, on the weight-gradient inputs) to smooth outliers; 2D 16 × 16 block scaling for weights so the forward and backward passes see the same quantised weights; stochastic rounding on gradients; and keeping some layers in BF16 (the first two and the last eight blocks, 16% of the linear layers).

Each failure of the fp16 recipe without its fixes (updates rounding away, gradients underflowing) is measured on a real model's 134.5 million gradients, with a loss-scale slider and PyTorch's GradScaler rules, in Numerical computing for ML (section 11). The same scaler in the frameworks: PyTorch's GradScaler on one real step (1,636 gradients below 2−24, 58 after ×65,536) on Making training fast, section 6; JAX's jmp loss scale, with a measured float16 table, on The JAX training stack, section 7.

Why FP8 needs fine scales and FP32 promotion, measured on other pages: one outlier of 900 fixes a per-tensor E4M3 scale so that 12,118 non-zero values flush to zero, against 11 with one scale per row (Profiling, benchmarking and correctness, section 5); and Hopper's FP8 tensor-core accumulation keeps only around 14 bits, which is why DeepSeek-V3 copies partial sums to FP32 every 128 elements (Libraries and tensor cores, section 8).

What FP8 buys. In PyTorch's torchtitan, Float8 is a configuration flag: on Llama 3.1 8B with FSDP on 8 H100s, torch.compile plus Float8 reached 9,409 tokens per second, +50.35% over plain FSDP; +65.08% on 128 GPUs (torchtitan, Tables 1 and 2). Adding Float8 on top of compile (6,674 tokens per second) is 9,409 / 6,674 = +41% derived.

Correction
The old page said torchtitan and Transformer Engine give "about 30 to 40% throughput gains" from FP8. torchtitan's own tables give +41% for adding Float8 to a compiled run and +50% for compile plus Float8 over eager, on 8 GPUs, rising to +65% on 128 (link above).

Four bits. Blackwell tensor cores natively support MXFP8, MXFP4 and NVFP4, moving 4-bit from a storage trick to a compute format: "Tensor Cores deliver FP4 computations at 2× (on GB200 chips) and 3× (on GB300 chips) higher math throughput rates compared to FP8" (NVIDIA 2025, §2). With the recipe above, a 12B hybrid Mamba-Transformer trained on 10T tokens in NVFP4 matched its FP8 baseline closely (MMLU-Pro 62.58 against 62.62; MMLU 76.57 against 77.36; HumanEval+ 57.43 against 59.93). In the same paper's 8B experiment, MXFP4 matched NVFP4's loss only with 36% more tokens (1.36T against 1T), and its loss gap to BF16 was about 2.5% against NVFP4's 1.5%: section 2's power-of-two scale, at training scale. The MXFP4 gap can be mostly closed with the same kind of fixes: AMD trained GPT-OSS-20B on MLPerf's Small MoE task with random Hadamard transforms, stochastic rounding and a simplified weight de-oscillation (stopping weights from flipping back and forth between two adjacent 4-bit values), reaching a validation loss of 3.3350 against BF16's 3.3283 and cutting the extra steps needed to reach the MLPerf target from +20.0% to +5.0%; differential gradient estimation, outlier clipping and macro-block scaling did not help. The MXFP4 was simulated on MI300 GPUs, so no wall-clock gain is reported (Training an MoE LLM in MXFP4 (arXiv 2610.32229)).

Corrections
The old page described NVFP4 pretraining as "matching-quality training with 2-3x matmul speedups": the 2 to 3 times is the hardware's peak FP4 rate against FP8 on GB200 and GB300, not a speedup measured in the paper. It put the MXFP4 "36% more tokens" result without its setting: it is the 8B experiment, 1.36T against 1T tokens. And it said low-precision RL reduces "the rollout/trainer precision mismatch that destabilises RL": the LMSYS post reports that both low-precision formats show higher train-inference mismatch than BF16, with reward curves that still track BF16, and that NVFP4 there is used for MoE experts in rollout and forward only, not for "rollouts with bf16 training" across the model.
Low-precision RL, and quantising recurrent states

Low-precision RL is live (LMSYS, 29 July 2026): in the Miles framework (SGLang rollouts, Megatron and Transformer Engine training), MXFP8 runs end to end, "rollout, forward propagation, weight-gradient GEMMs, and data-gradient GEMMs"; NVFP4 covers only the MoE experts in rollout and forward, with the backward pass in high precision and the rest of the model (shared experts, the last 15% of layers) in BF16. On Qwen3-30B-A3B with GRPO, "all five low-precision reward curves closely track the BF16 reward curve", although "both low-precision formats show higher train-inference mismatch than BF16". Both cut rollout time; MXFP8 training is faster than BF16, the NVFP4 backward variants slower in that implementation. The methods that go further (TRACE, TRIAGE, and KV4-RL for the KV cache of asynchronous rollouts) all target that mismatch rather than the quantisation error on each side; they, why the mismatch matters, and the importance-sampling corrections are on RL for LLMs.

Recurrent states: linear-attention layers replace the growing KV cache with a fixed-size state, which becomes the memory bottleneck under concurrent serving, and quantising it naively fails because errors propagate through every later state update. STEPQuant allocates precision by error magnitude and memory lifetime and fits key-row and value-column scales jointly; on Qwen3.8-27B and Kimi-Linear-48B-A3B-Instruct it closely matched FP32-state accuracy at a nominal 6 bits, and in SGLang gave over 5x state compression and up to 68.7% less total serving memory (STEPQuant (arXiv 2609.38169)).

7. Serving: the default stack, and reading a quantisation name

Inference default stack, 2026: bf16, then FP8 W8A8 (near-lossless), then NVFP4 or INT4 weight-only for memory-bound serving; MoE models quantise their experts aggressively. FP8 W8A8 is the low-effort default on Hopper and Blackwell: vLLM's FP8-dynamic uses static per-channel weight scales and dynamic per-token activation scales, needs no calibration data, and gives "a 2x reduction in model memory requirements and up to a 1.6x improvement in throughput" (vLLM). NVFP4 is about 3.5 times smaller than FP16 and 1.8 times smaller than FP8 (NVIDIA; 16 / 4.5 = 3.56, 8 / 4.5 = 1.78 derived). llama.cpp's ggml has begun adding an NVFP4 block type too (ggml-common.h). The kernel decides whether a format pays: vLLM's Humming kernels (Ant Group and vLLM, in vLLM since 0.29.0) run W4A16 at about twice Marlin's speed at large batch on H200, and gave DeepSeek-V4.1-Flash on 8 H20s 14 to 43% more throughput than Marlin (vendor figures, vLLM blog, 21 October 2026). Memory tables quantise too: DeepSeek-V4.1-Flash spends 196B parameters on its Engram n-gram memory, and 4-bit tables saved 47 to 55% of that memory there and on Qwen3.8-Flash-Next for under 1.2% more perplexity (Low-Bit N-Gram Embeddings (arXiv 2610.31646)). Serving kernels live in Topic: inference-and-serving, KV-cache quantisation and sizing in Long context, and which formats each GPU runs natively in Topic: hardware.

A GGUF name is the letter Q, a nominal bit count and a variant tag: _0 and _1 are the legacy flat formats (32 weights, one fp16 scale, plus a minimum for _1); K marks the K-quants (a 256-weight super-block whose sub-block scales are themselves quantised, like QLoRA's double quantisation); IQ marks codebook types steered by an importance matrix (imatrix), the activation-weighted idea of AWQ and GPTQ; _S, _M, _L name a per-tensor mixing recipe, not a block format. So the bits per weight are never the nominal number (section 2). The short version: Q4_K_M with an imatrix is the default, I-quants buy size rather than quality per byte, and dense models fall off a cliff below about 3 bits. Every type's block layout (decoded from real files), the mixing recipes, importance matrices and a quality ladder measured as KL divergence against F16 on two Qwen3 models are owned by Local and on-device inference (sections 4 and 5), with llama.cpp's own perplexity lists; the file container is section 4 of Model formats: GGUF, safetensors, ONNX, and the rest.

A parameter count on the Hub can be a storage count. The Hub reads the tensors' shapes, and packed 4-bit weights are stored two per byte as U8, so each counts as half. MiniMax M3.1 Flash shows 220.5B parameters on its Hub page; 206.6B of those are packed 4-bit storage, and the model card gives about 428B (MiniMax-M3.1-Flash on Hugging Face). Read the card, not the widget.

gptq-4bit-128g-actorder_TrueGPTQ, 4-bit weight-only. Group size 128: one scale and zero point per 128 consecutive weights along the input dimension. Smaller g is finer and more accurate but adds scale overhead (4 + 32/128 = 4.25 bits at g128 with fp16 scale and zero derived); 32g is the quality end, 128g the usual compromise, no g means per channel. act-order (desc_act in the config) quantises columns in decreasing order of activation size so accumulated error lands on the columns that matter least. Better accuracy, historically incompatible with some fused kernels: "Some GPTQ clients have had issues with models that use Act Order plus Group Size, but this is generally resolved now" (TheBloke's card)
awq-4bit-128g, AWQ-INT4AWQ, 4-bit weight-only, group size 128. Instead of reordering, it rescales the roughly 1% of salient channels (chosen by activation magnitude) before quantising. No reordering means simpler, faster kernels, which is why AWQ often wins on throughput at similar accuracy unconfirmed as a general rule. Qwen ships official AWQ checkpoints (for example Qwen3-8B-AWQ)
nf4, fp4, load_in_4bit, bnb-4bitbitsandbytes. A runtime flag, not a checkpoint format: the fp16 weights are quantised on load. NF4 is a 16-level codebook fitted to a normal distribution over 64-weight blocks; "double quant" additionally quantises the block scales (4.127 bits per weight 4 + 8/64 + 32/(64 × 256)). This is the QLoRA base. Convenient, not competitive on serving throughput
W4A16compressed-tensors and llm-compressor (the vLLM naming): "Quantizes weights to 4 or 8-bit integer precision, retaining activations in 16-bit", per group, "optimally compressed using non-RTN algorithms (GPTQ, AWQ) which require a dataset" (llm-compressor). Memory-bound win: right for low concurrency where you are streaming weights
W8A8 (-INT8)Weights and activations both int8, so the matmul itself runs in int8. Needs calibration for static activation scales (or GPTQ/AWQ for the weights). The high-throughput, compute-bound choice on pre-Hopper hardware
FP8-dynamicFP8 W8A8 with per-channel weight scales and per-token activation scales computed at runtime. No calibration set required. The low-effort near-lossless default on Hopper and Blackwell (vLLM). vLLM can also do it online from a bf16 checkpoint with a per-tensor scale
FP8-staticSame, but the activation scales are frozen from a calibration pass. Marginally faster (no per-token reduction), and marginally more brittle: a distribution shift away from the calibration data shows up as clipping. llm-compressor lists it as an option of its FP8 scheme rather than a separate name. FP8_BLOCK uses 128 × 128 weight tiles and per-128 activation groups, DeepSeek-V3's recipe
NVFP4, MXFP4 checkpointsBlackwell-native 4-bit. NVFP4: a global scale per tensor and FP8 E4M3 scales per 16, and it "requires a calibration dataset to calibrate activation global scales"; MXFP4: E8M0 scales per 32, "no calibration data required if using RTN", "though RTN accuracy may be lower" (llm-compressor)

On the dual 5090s: GGUF or a native checkpoint

Which model and which GGUF type fit two 32 GB cards, and the rule that a bigger model at Q4_K_M beats a smaller one at Q8_0 (checked by measurement), are in Local and on-device inference (sections 5 and 9). The precision side: MoE experts tolerate much harder quantisation than the attention and shared layers; gpt-oss ships only its MoE weights, "90+% of the total parameter count", in MXFP4 (gpt-oss card), and llama.cpp's MXFP4_MOE type keeps "other tensors" at Q8_0. And the two 5090s are Blackwell SM120 with native FP8 and NVFP4 tensor cores, while GGUF's K-quants are a CPU-friendly design that dequantises to fp16 before the matmul. For single-stream interactive work the difference is small and llama.cpp's flexibility wins; once concurrency matters, an FP8 or NVFP4 checkpoint under vLLM uses hardware the GGUF path never touches, and the gap becomes large.

Common mistakes

"An uploader's perplexity proves the quant is fine"
Perplexity on the calibration distribution hides losses off it, and schemes with similar perplexity diverge on instruction-following and reasoning (Kurt 2026). Evaluate on your own tasks.
"Quantise from whatever file you have"
Always quantise from the full-precision original: errors from an already-quantised file compound and cannot be recovered (Model formats).
