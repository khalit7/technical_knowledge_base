Vocabulary size

A bigger vocabulary packs more text into each token, so every request is shorter; it costs one row of the embedding matrix per entry (and a second row in the output layer unless the two are tied). This tab puts both sides of that trade on data: vocabularies over time, what they cost in parameters, and what they save in tokens.

Vocabulary size over time

33 models, 2018 to 2026, vocabulary size on a log axis. Click a point or a table row for its configuration. Try the Qwen family: 152K from Qwen-7B (2023) to Qwen3 (2025), then 248K with Qwen3.5 (2026).

All rows, with sources

Vocabulary = vocab_size in each model's config.json on Hugging Face (fetched 3 October 2026; padded, see the Reading tab), or the tiktoken encoding size for OpenAI's closed models. Date = the paper or announcement for the 2018 to 2020 models, LLaMA and the closed models; for the others, the day the Hugging Face repository was created, a proxy for the public release of the weights (the official repository where it is not gated, otherwise the named mirror).

What the vocabulary costs in parameters

Share of all weights spent on the embedding table (and the output layer when it is untied), smallest models first. Try reading down: the share falls as models grow, because the table grows with width only, not with depth or experts.

Embedding parameters = vocabulary × hidden width, doubled when tie_word_embeddings is false; all parameters = the safetensors total reported by Hugging Face, which includes any vision encoder or multi-token-prediction layers in the repository. Gemma 4 E2B is left out: its per-layer embeddings make the share incomparable.

Calculator. Defaults reproduce Gemma 3 270M's published split, independently: "170 million embedding parameters ... and 100 million for our transformer blocks" ({{Google|https://developers.googleblog.com/en/introducing-gemma-3-270m/}}). Try a 32K vocabulary at the same width.
