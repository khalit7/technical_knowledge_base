3. Data parallelism (DP, DDP)

Replicate the model on every GPU and give each replica a different micro-batch. After backward, an all-reduce averages the gradients, so every replica takes the identical optimiser step. Step through one step of Llama 3 8B on four GPUs, four sequences of 8,192 tokens (or one of 32,768: data parallelism cannot cut a single sequence):

DDP sends the gradients in buckets (25 MiB by default in PyTorch's DistributedDataParallel) as soon as each is ready, so the all-reduce overlaps the rest of backward. PyTorch's old DataParallel was a single process driving the GPUs of one machine by threads; DDP runs one process per GPU, works across machines, and is the baseline everything else builds on (Li et al. 2020). It scales nearly linearly while the all-reduce hides behind backward, and that has a size condition: a replica sends about 2 × 2Ψ bytes and computes 6Ψ FLOPs per token, so the transfer hides when each replica processes T ≥ 2I/3 tokens per step, where I is the GPU's sustained FLOP/s over the link's bytes per second. For an H100 at 40% of its BF16 peak over a 400 Gb/s card that is about 5,300 tokens per replica ({{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}} section 9 derived); Llama 3 405B's 16M-token batches over 128 replicas give 131,072 tokens each, far above it.

Its cost is memory: the full 16 bytes per parameter on every GPU, the ceiling ZeRO and FSDP remove. The global batch is micro-batch × gradient-accumulation steps × data-parallel degree (Playbook), so DP is also how a layout reaches its target batch once the model fits, and a fixed token budget per step caps it: Llama 3's 16K-GPU run had fewer sequences per DP rank than its 8K-GPU run and a lower MFU (41% against 43%, §3.3.2).

4. ZeRO and FSDP: sharded data parallelism

Data parallelism stores the same 16 bytes per parameter n times. ZeRO ({{paper page|n:3c65c17b0d0d81879a7ed90bca007699}}, Rajbhandari et al. 2019) shards them across the data-parallel group instead, in three stages.

Predict: the ZeRO paper's 7.5B model needs 120 GB per GPU under plain data parallelism. Shard only the optimiser state over 64 GPUs (ZeRO-1). About how much is left per GPU?
31.4 GB. The 12 bytes of fp32 master weights and Adam moments become 12/64, but the 4 bytes of bf16 weights and gradients stay whole on every GPU: 4 + 12/64 = 4.19 bytes per parameter. Sharding the 4 is what stages 2 and 3 do.

ZeRO-1 shards the optimiser state: each GPU updates its 1/n of the fp32 master weights, then an all-gather shares the updated bf16 weights. ZeRO-2 also shards the gradients, reduce-scattered as backward produces them; stages 1 and 2 send what DDP sends. ZeRO-3 also shards the parameters: each layer's weights are all-gathered just in time for forward and again for backward, then freed. Communication is 3Ψ against DP's 2Ψ, 1.5 times (§7), and model-state memory falls as 1/N.

Try: step ZeRO-3 against the DP counters: the bars fall to a quarter while the bytes counter grows by half. Then HSDP, where only 8.0 GB per GPU crosses InfiniBand.

The extra gathers are not free: with gradient accumulation ZeRO-3 gathers the weights again for every micro-batch, forward and backward, and across servers that traffic lands on the slow link; HSDP or ZeRO-2 are the usual fixes. Re-gathering for backward is itself a choice: keeping each layer's gathered weights from forward to backward saves the second all-gather (2Ψ again instead of 3Ψ) for activation-like memory. FSDP2's reshard_after_forward controls it (by default every module reshards except the root); XLA kept the weights on the {{Sharding and scale (JAX)|n:3c65c17b0d0d8125b084e6720cc66b3d}} page's measured run; Llama 3's FSDP shards optimiser state and gradients but keeps weights gathered after forward (§3.3.2).

FSDP is PyTorch's native version, "motivated by" ZeRO with a design aligned with the rest of PyTorch (Zhao et al. 2023); its default full sharding is ZeRO-3, and it has a ZeRO-2-like mode as well. FSDP2 (fully_shard) shards each parameter on its own dimension 0 as a DTensor, so it composes with TP, PP and EP on a device mesh. The 2026 default: on PyTorch, without a need for NVMe offload, use FSDP2 rather than DeepSpeed; the arithmetic is the same, the composition cleaner.

Hybrid sharding (HSDP) builds "a 2-D DeviceMesh that contains replica groups on one dimension and shard groups on the other" (torchtitan paper): FSDP-shard within a server (or a small group), DDP-replicate across groups. The heavy per-layer all-gathers stay on NVLink and only the gradient all-reduce crosses servers (8.0 GB per GPU on InfiniBand against 36.1 GB for ZeRO-3 across both servers). It also bounds the blast radius of a failure: a lost server leaves complete replicas, which is how {{torchft|https://github.com/pytorch/torchft}} does "fault tolerance across the replicated dimension". Use it when the model fits in one server's (or group's) aggregate memory.

Offload, and what FSDP2's per-parameter sharding buys (depth)
  • ZeRO-Offload moves optimiser state and its update to CPU memory (Ren et al. 2021); ZeRO-Infinity adds NVMe, enough to "fine-tune trillion parameter models on a single NVIDIA DGX-2 node" (Rajbhandari et al. 2021).
  • FSDP2 "replac[ed] the original FSDP1 FlatParameter sharding. Specifically, parameters are now represented as DTensors sharded on the tensor dimension 0" (torchtitan paper). A 2026 {{framework survey|https://megacpp.com/blog/framework-survey-fsdp-vs-megatron-vs-deepspeed/}} reaches the same split as the default above: DeepSpeed remains the pragmatic choice mainly for memory-bound runs that need ZeRO-Infinity offload.
  • Because every FSDP2 parameter keeps its own identity, state_dict handling is sane through Distributed Checkpoint (DCP), and partial freezing works, so LoRA-style fine-tuning is straightforward.
  • FSDP2 "records an average of 7% lower GPU memory versus FSDP1" and "an average gain of 1.5% faster throughput" reported (torchtitan paper).
