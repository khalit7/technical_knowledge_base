5. Tensor parallelism and sequence parallelism

Tensor parallelism splits individual weight matrices across GPUs ({{Megatron-LM|n:3c65c17b0d0d8133ae92fbe90a1f308e}}): a column-parallel matrix followed by a row-parallel one, in the feed-forward block and in attention (heads are divided among GPUs). Fig. 7 runs one feed-forward block on two GPUs, in Megatron-LM's notation (Y = GeLU(X·A), Z = Y·B), first as plain TP, then with sequence parallelism:

  1. The input, whole on both GPUs. Both GPUs hold every token of X. Megatron's f operator is the identity going forward (its backward is an all-reduce).
  2. Column split of A. GPU 0 holds the first half of A's columns, GPU 1 the second (the outline is the half it does not hold). X·A₀ and X·A₁ are independent, so GeLU runs locally with no communication.
  3. Row split of B. Each GPU holds the matching half of B's rows, so Zᵢ = Yᵢ·Bᵢ is only a partial sum of the output.
  4. One all-reduce. Z₀ + Z₁ = Z needs a sum, one all-reduce of the block's output (b × s × h values; Megatron's g). Then LayerNorm and dropout run on all tokens on both GPUs: duplicated work and duplicated activation memory.
  1. Own tokens only. Outside the matmuls each GPU keeps only its own half of the tokens, so LayerNorm and dropout are no longer duplicated.
  2. All-gather. An all-gather rebuilds the full X on both GPUs before the column-parallel matmul.
  3. Column split of A. As in TP: GeLU(X·Aᵢ) on each GPU, no communication.
  4. Row split of B. As in TP: each GPU ends with a partial sum.
  5. Reduce-scatter. A reduce-scatter replaces the all-reduce, leaving each GPU the summed output for its own tokens. Same bytes, because an all-reduce is a reduce-scatter plus an all-gather.

Sequence parallelism (Megatron-style) extends TP to the regions TP leaves replicated, LayerNorm and dropout, by splitting their activations along the sequence. The all-reduce becomes a reduce-scatter plus an all-gather of the same total size, so communication is unchanged and the duplicated activation memory disappears: activations per layer fall from sbh(34 + 5as/h) to sbh/t(34 + 5as/h), and with selective recomputation to 34sbh/t (Korthikanti et al. 2022). One small collective appears: each GPU ran the LayerNorm on its own tokens, so the LayerNorm weights' gradients are partial sums and need an all-reduce over the TP group (recorded on {{Distributed PyTorch|n:3c65c17b0d0d815e85aff8decd8f35ab}} section 6). It is not context parallelism (section 8): it lives inside the TP group and leaves attention whole.

That is two all-reduces per layer forward and two backward, inside every layer, in small latency-bound messages on the critical path: the next matmul needs the result, so overlap cannot hide them. Fig. 8: four GPUs, the same step as before:

  1. Setup: every matrix cut in four. Each GPU holds a quarter of every weight matrix: query, key and value heads and the first feed-forward matrices by columns, the attention output and second feed-forward matrix by rows. 4 bytes per parameter, 32.1 GB. The four GPUs act as one model replica, so the whole batch, four 8,192-token sequences, goes through all four.
  2. Layer 1, attention. Column-parallel QKV gives each GPU 8 of the 32 heads, so attention runs locally. The row-parallel output projection leaves a partial sum on each GPU: one all-reduce of the batch's hidden states, 0.40 GB per GPU. With sequence parallelism this is a reduce-scatter plus an all-gather of the same size, and LayerNorm activations are split by tokens.
  3. Layer 1, feed-forward. Column-parallel W1 and W3, the SwiGLU applied locally (the reason for the column-then-row pairing: no sync in between), row-parallel W2, then the second all-reduce.
  4. Layers 2 to 32. Two all-reduces per layer: 64 in the forward pass, 25.8 GB per GPU.
  5. Backward. The mirror image: two all-reduces of input gradients per layer, 64 more, 25.8 GB. Each GPU computes the weight gradients for its own slices only.
  6. Optimiser step, no gradient sync. There is one replica, so nothing to average. Total 51.5 GB per GPU, more than any other split, in 128 small, latency-bound pieces inside every layer: tensor parallelism only works on NVLink.

TP sends 51.5 GB per GPU for this step, more than any other split, and its bytes per FLOP do not depend on the batch at all, only on the degree, the hidden size and the link, so a slow link cannot be bought back with bigger batches: for Llama 3.1 70B at TP 8 over a 400 Gb/s card the communication is 141% of the compute ({{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}} section 9 derived). Hence Megatron's guidance, TP "up to degree g when using g-GPU servers", then pipeline parallelism across servers (Narayanan et al. 2021); the Playbook measured "around 43% performance degradation" when TP crosses nodes, against 14% for PP. Keep the degree a divisor of the number of heads (of KV heads, with grouped-query attention): otherwise the attention has to be reshuffled, and the JAX page measured 1.33 times the predicted bytes for 4 heads over 8 devices.

6. Pipeline parallelism

Pipeline parallelism splits the model into stages of consecutive layers, one per GPU or group. Only activations (forward) and their gradients (backward) cross a stage boundary, 2sbh bytes per micro-batch each way, so PP is cheap on bandwidth and is the preferred way to split a model across servers. Run naively, one batch at a time, only one stage works while the others wait: the bubble. Cutting the batch into m micro-batches lets stages work on different micro-batches at once. Fig. 9: four stages, four micro-batches, the 1F1B schedule, with the timeline on the floor:

  1. Setup: eight layers per GPU. GPU 0 holds layers 1 to 8 with the embedding, GPU 3 layers 25 to 32 with the output head: 4 bytes per parameter of the whole model each, 32.1 GB (the end stages a little more). The batch is cut into four micro-batches, one sequence each; the timeline on the floor fills as the step runs.
  2. Warm-up. Micro-batch 1 enters stage 1, then its activations are sent to stage 2, and so on. The later stages wait: the start of the bubble.
  3. Steady state: one forward, one backward. 1F1B: once the last stage starts backward, each stage alternates a forward and a backward, so it never holds more than p micro-batches of activations (GPipe holds all m). Gradients flow back by send and receive.
  4. Cool-down. The pipeline drains; the first stage waits for the last gradients. Idle share of the timeline: (p − 1)/(m + p − 1) = 43%; in Megatron's terms the bubble is (p − 1)/m = 75% of the ideal time.
  5. Optimiser step. Each stage updates its own layers; nothing to average. The traffic was tiny, 0.54 GB per GPU at most, one activation per micro-batch per boundary: pipeline parallelism is the split to put on slow links.

The idle share of the timeline is (p − 1)/(m + p − 1), 43% here; Megatron writes the same bubble as (p − 1)/m of the ideal time, 75%.

A schedule decides the order of forwards and backwards:

  • GPipe (Huang et al. 2019): all forwards, then all backwards. Bubble time fraction (p − 1)/m of the ideal time, and every stage holds the activations of all m micro-batches.
  • 1F1B (from PipeDream, Harlap et al. 2018; Megatron uses its flushing variant, PipeDream-Flush): after a warm-up, each stage alternates one forward and one backward. The bubble is the same as GPipe's; what changes is memory, at most p micro-batches in flight instead of m (Narayanan et al. 2021).
  • Interleaved 1F1B: each GPU holds v non-adjacent chunks of layers, cutting the bubble to (p − 1)/(v·m) for v times more point-to-point traffic. Llama 3 used it, with a tunable number of consecutive micro-batches per stage, and states the same ratio, (PP − 1)/(V × M) ({{Llama 3|n:3c65c17b0d0d81aca58ccb9d720b474e}} §3.3.2).
  • Zero bubble, ZB-H1 (Qi et al. 2023): backward is split into the gradient for the input (B), which the previous stage is waiting for, and for the weights (W), which nobody is, so W fills the gaps. "The bubble size is reduced to a third of 1F1B's size" at the same peak memory; ZB-H2 removes it for about twice the activations.
  • DualPipe (DeepSeek-V3, {{paper page|n:3c65c17b0d0d815fb8dac9ba1e35ab81}}): micro-batches enter from both ends, each forward chunk is overlapped with a backward chunk, and the all-to-all and pipeline communication hide inside the computation. Bubble (PP/2 − 1)(F&B + B − 3W), for two copies of the parameters and PP + 1 micro-batches of activations (Table 2). The V-shaped variants (DualPipeV, ZBV) give rank 0 both the first and the last stage, so the pipeline turns round on one GPU (both run on {{Distributed PyTorch|n:3c65c17b0d0d815e85aff8decd8f35ab}} section 8).
Predict: 8 stages, 20 micro-batches. Switching from GPipe to 1F1B does what to the bubble?
Nothing: both idle (p − 1)/m = 35% of the ideal time. 1F1B caps the activations in flight at p micro-batches instead of m. Interleaving (÷ v), zero-bubble schedules and DualPipe are what shrink the bubble: move the sliders.

Fig. 10 · The bubble falls with more micro-batches and with interleaving; 1F1B alone changes only memory

The default is DeepSeek's DualPipe README example, 8 stages and 20 micro-batches; at m = 8 the GPipe and 1F1B rows rise to 88% of the ideal time. Rows use illustrative chunk times (forward 1, full backward 2, weight-gradient part 1), which is what makes ZB-H1 exactly a third of 1F1B.

The price of PP is the bubble, a batch-size constraint (enough micro-batches per step), uneven memory (the first stage holds the most activations, and the embedding) and invasive code changes.
