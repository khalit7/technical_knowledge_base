LoRA against full fine-tuning

Two careful studies, a year apart, agree more than their titles suggest: LoRA matches full fine-tuning when the data fits in its capacity and it is set up right, and falls behind when the data is pretraining-sized.

"LoRA learns less and forgets less" (Biderman et al., 2024)

{{Biderman et al.|https://arxiv.org/abs/2405.09673}} trained Llama-2-7B on code and on math, two ways each: continued pretraining (CPT: StarCoder-Python up to 20B tokens; OpenWebMath, 14.7B tokens) and instruction fine-tuning (IFT: Magicoder-Evol-Instruct-110K, 73M tokens; MetaMathQA, 103M tokens). They scored the target skill (HumanEval for code, GSM8K for math) and, to measure forgetting, the average of HellaSwag, WinoGrande and ARC-Challenge, which the base model already knew.

Predict, then step: on code CPT, which run ends highest, and which forgets most? Step through it; then switch to code IFT, where LoRA at rank 256 matches or beats full fine-tuning at epoch 4 while forgetting far less.

Full fine-tuning climbs higher but slides left (forgets); LoRA stays right, and on instruction data catches up

published values from {{Tables S1 to S8|https://arxiv.org/html/2405.09673v2#A4}}, one run per point; the paper's figures plot the same data. Further right is less forgetting; higher is more learning.

  • Continued pretraining: LoRA learns less. After 20B tokens of code, full fine-tuning reaches 0.263 on HumanEval and LoRA at rank 256 0.224; on math after 20B tokens, 0.293 against 0.202 on GSM8K. Rank 16 barely moves at all (0.162, 0.158).
  • Instruction fine-tuning: the gap mostly closes. Code IFT at epoch 4: LoRA r = 256 0.498 against full fine-tuning 0.470 (full fine-tuning's best, 0.497, comes at epoch 8). Math IFT at epoch 4: 0.625 against 0.642.
  • LoRA forgets less. After code IFT at epoch 4 the forgetting average is 0.632 for LoRA r = 64 and 0.512 for full fine-tuning; after one epoch the LoRA runs still sat at about 0.65. LoRA "mitigates forgetting more aggressively than classic regularization techniques" (dropout, weight decay).
  • Their recommendations: LoRA for instruction fine-tuning, not continued pretraining; all modules; rank 256 when memory allows; α = 2r; sweep the learning rate from 1e-5 to 5e-4.

"LoRA without regret" (Thinking Machines, 2025)

{{John Schulman and Thinking Machines Lab|https://thinkingmachines.ai/blog/lora/}} (29 September 2025) swept learning rates for LoRA and full fine-tuning on Llama 3 and Qwen3 models (including a mixture-of-experts one), with SFT on Tulu3 and OpenThoughts3 and RL on MATH and GSM. When "a few key details" are right, LoRA learns with the same sample efficiency as full fine-tuning:

  • All layers, especially the MLP and MoE layers ({{Which matrices|#s-where}}).
  • Not capacity-constrained: the adapter must have more parameters than the information to be learned. LLM datasets carry "around 1 bit (0.69 nats) per token"; for typical instruction and reasoning sets LoRA has room. "For datasets that exceed LoRA capacity, LoRA underperforms FullFT", not by hitting a floor but by learning less efficiently.
  • Learning rate about 10 times full fine-tuning's: "the optimal LR for LoRA is consistently 10x the one used for FullFT in the same application, for both supervised learning and reinforcement learning". A LoRA run that "doesn't learn" at full fine-tuning's rate is often just under-stepped.
  • Modest batch sizes: LoRA "pays a larger penalty in loss as batch size increases beyond some point", and a higher rank does not fix it, "a property of the product-of-matrices parametrization". Hugging Face's {{TRL guide|https://huggingface.co/docs/trl/main/lora_without_regret}} turns this into "an effective batch size < 32".
  • RL needs almost no capacity. LoRA "fully matches" full fine-tuning for policy-gradient RL "even with ranks as low as 1". Supervised learning gives O(tokens) bits per episode, a policy gradient only O(1) bits through the advantage. Their MATH run used about 10,000 problems × 32 samples, so at one bit each about 320,000 bits, against "3M parameters" in a rank-1 LoRA on Llama-3.1-8B (derived: 2,621,440 on all seven matrices, which rounds to their figure; check it in the {{Trainable parameters|#t-count}} tab). The TRL guide's ranks: 256 for post-training-scale SFT, 1 to 32 for RL.
  • Cheaper per step: "slightly more than ⅔ of the FLOPs that full fine-tuning does per pass", from 2N² + 6NR multiply-adds against 3N² for an N × N matrix at rank R (no weight gradient for the frozen matrix). derived 67.4% at N = 4,096, R = 16; 79.2% at R = 256.
The two studies, reconciled
Biderman et al.'s continued pretraining runs (14.7 to 20B tokens) are exactly the "datasets that exceed LoRA capacity" regime; their instruction runs, where LoRA caught up, are the "low-regret" regime. Thinking Machines cites them for this: LoRA underperforms "in settings that resemble pre-training". Use full fine-tuning or {{continued pretraining|n:3c65c17b0d0d8119b8f0e801caa09474}} for billions of tokens of new domain text; LoRA for post-training.
A worked instance at the small end, and a correction (optional)

A Qwen 3.8 4B model was taught to write PostgreSQL query plans: SFT on 400 GPT-6 Astra trajectories (440 generated in two rounds of 120 and 320, each keeping 20 for validation) through a LoRA of 21.2 million parameters (42.5 MB), then a custom "anchored" GRPO against measured execution time. Best of three rollouts, it reached a 1.81 times geometric-mean speed-up over Postgres's own planner on 113 join-heavy queries, for $1,200 in total (about $800 of rented 2 × H100 time and $400 of API fees; development on two RTX 3090s) ({{write-up, 16 September 2026|https://rohanbansal.com/qorl}}).

The old text said this cost "a few hundred dollars", ran "on consumer GPUs" and beat "a hand-tuned production planner". The write-up gives $1,200, training on a rented H100 node (consumer cards for development), and compares against PostgreSQL's built-in planner.

DoRA: magnitude and direction

{{DoRA|https://arxiv.org/abs/2402.09353}} (Liu et al., ICML 2024) starts from a measurement: across training checkpoints, full fine-tuning's changes in each weight column's length and in its direction were negatively correlated (a large turn with a small stretch, or the reverse), while LoRA's were positively correlated, because one low-rank update moves both together. DoRA separates them: it trains each column's length directly and its direction with LoRA.

The same 60° turn: LoRA's length dips and recovers on the way; DoRA turns at constant length, with the length as its own number

illustrative one 2-D column moved toward a target turned 60° at the same length, along the straight path each parametrisation takes in its own parameters; not a trained model. Both reach the target: it shows how each moves, not which is more accurate.

W′ = m · (W0 + BA) / ‖W0 + BA‖c
m
a trainable magnitude vector, one number per column (per output unit in PyTorch's layout), initialised to ‖W0‖c
‖·‖c
"the vector-wise norm of a matrix across each column vector"

The results ({{Table 1|https://arxiv.org/html/2402.09353v6}}): on eight commonsense-reasoning tasks, LLaMA-7B averaged 74.7 with LoRA (0.83% of parameters trained), 78.4 with DoRA (0.84%) and 77.5 with DoRA at half the rank (0.43%); LLaMA3-8B 80.8 against 85.2. Two cautions: the LoRA numbers for LLaMA 7B and 13B are taken from an earlier paper (LLM-Adapters) rather than re-tuned, while DoRA kept LoRA's configuration "adjusting only the learning rate"; and the extra 0.01% is the magnitude vector (the {{Trainable parameters|#t-count}} tab's LLaMA-7B preset reproduces 0.83%, 0.84% and 0.43%). To save memory DoRA treats the norm as a constant in the backward pass, which cut training memory by about 24.4% on LLaMA with a 0.2-point difference in accuracy. Once trained, DoRA merges like LoRA, so serving is free; PEFT enables it with use_dora=True.

Serving many adapters

One adapter is best merged: the model is the base's shape and speed. Many adapters on one base are a different problem. Merging each means a full copy of the model per adapter; keeping them unmerged means one copy of the base, shared by every request, and a small extra product x · Ai · Bi per request for whichever adapter it asked for. That is multi-LoRA serving, the consequence of LoRA's parallel form; routing, adapter limits and engine settings are on {{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}.

{{S-LoRA|https://arxiv.org/abs/2311.03285}} keeps every adapter in host memory, fetches the ones the running requests need, and pages adapter weights and the KV cache from one memory pool ("Unified Paging"), with kernels that batch requests for adapters of different ranks. It served 2,000 adapters on one GPU at 7.61 requests per second, against 8.05 with five. The baseline that merges each adapter into its own copy ran out of memory beyond a handful, and was 4 times slower even then: derived 8.05 / 2.04 = 3.9 times, and 7.99 / 0.25 = 32 times faster than PEFT, which swaps adapters between batches. {{Punica|https://arxiv.org/abs/2310.18547}} introduced the batching kernel for many LoRA models against one copy of the base; {{vLLM|https://docs.vllm.ai/en/latest/features/lora.html}} (--enable-lora, with limits such as max_loras, max_lora_rank and max_cpu_loras) and {{SGLang|https://docs.sglang.ai/advanced_features/lora.html}} ("techniques from S-LoRA and Punica") ship it. The memory side of serving (KV cache, paging) is {{PagedAttention|n:3c65c17b0d0d81bf8b90ca93fee19f5f}}.

LoRA in products (optional)

Apple's on-device foundation model swaps rank-16 adapters, "10s of megabytes" each, per feature ({{Apple, June 2024|https://machinelearning.apple.com/research/introducing-apple-foundation-models}}), and Thinking Machines' {{Tinker|https://thinkingmachines.ai/tinker/}} fine-tuning service is built on LoRA.
