2. Resolution: tiles against native resolution

An encoder trained on 224 or 384-pixel squares sees a phone screenshot or an A4 page squashed into that square: thin text vanishes and the aspect ratio is wrong. One token per patch at full size fixes it at a cost that grows with the pixel count. Four answers have been used, in this order; here is what each does to a 1,920 × 1,080 screenshot:

How native resolution works: three changes. (1) The image is resized only until both sides are multiples of the merged patch (32 pixels for Qwen3.5: 16-pixel patches, 2 × 2 merge), with its pixel count kept between a minimum and a maximum (Qwen3.5’s processor: 65,536 to 16,777,216 pixels, that is 64 to 16,384 tokens); the rule is smart_resize (transformers v5.20.1, models/qwen2_vl/image_processing_qwen2_vl.py line 63), ported in the {{Token budget|#t-vmbud}} tab and checked against the processor on 24 sizes. (2) The encoder’s fixed position table is replaced or supplemented by 2-D RoPE (rotation by row and by column), so any grid is legal: Qwen2-VL “modified ViT by removing the original absolute position embeddings and introducing 2D-RoPE” paper. (3) The language model is told where each token sat, through 3-D positions (2a below).

Tokens grow with pixels only under native resolution. Square images of every size through the real processors measured: SmolVLM (default N = 4) rescales every image to 2,048 first, so its count does not move; Qwen3.5 (default limits) grows with the pixel count up to its 16,384-token cap; InternVL3-1B (256 tokens per 448 tile plus a thumbnail) steps with the tile grid; LLaVA-1.5 is 576 always.

What the budgets do to answers measured. On the root’s 30 questions SmolVLM gets 24 at 64, 26 at 320, 26 at 1,088 image tokens. Qwen3.5 gets 23 at 64, 24 at 256, 27 at 1,024 when a sentence such as “There are 3 red circles” counts as the number, but only 21, 21, 22 under the root lab’s strict rule, because it often ignores “Answer with a number” and writes a sentence: one score measures seeing, the other following the format. More tokens helped Qwen3.5 most on counting shapes; at 64 tokens it also fell for the typographic attack (“dog” for the cat with a DOG sticker); the clock, the sum of the bars and the astronaut’s missing horse fail at every budget (SmolVLM fails the clock and the sum too). Every answer is in out/qa_scored.json.

2a. Positions: an image uses its side length, not its token count

A language model with RoPE gives each token one integer position. SmolVLM’s does exactly that for image tokens (positions k, k+1, ...), so the token below a given one is 8 positions away inside a tile, and rows and columns survive only through the <row_r_col_c> text tags the processor inserts. M-RoPE (the rotary mechanism is on {{Positional Encodings|n:3c65c17b0d0d81a5b7c9e578fcdfac00}}) splits the rotary dimensions into time, row and column groups: text tokens get the same value in all three (ordinary RoPE), image tokens keep the time fixed and get their row and column, and the next text starts at the largest image position plus one.

The same 256 image tokens, two position schemes. Qwen3.5 reads the 512 × 512 cat as 16 × 16 tokens starting at position 4, measured with the model’s own get_rope_index measured: (t, h, w) runs from (4, 4, 4) to (4, 19, 19) and the next text token gets (20, 20, 20); the whole 277-token prompt ends at position 36, where 1-D positions would end at 276.

Predict, then reveal. With 3-D positions, an image of 4,096 tokens (64 × 64) advances the position counter by about how much?
About 64 derived: the counter moves by the larger side of the token grid, as the 16 × 16 cat moved it by 16. The paper gives this as a reason for M-RoPE: it “reduces the value of position IDs for images and videos, enabling the model to extrapolate to longer sequences during inference” ({{Wang et al., section 2.1|https://arxiv.org/html/2409.12191}}) paper. The context in tokens (memory, compute) is unchanged: every image token is still attended to.
The M-RoPE quotes, Qwen3-VL’s interleaving, and how to check positions yourself (provenance)

Qwen2-VL: “For text inputs, these components utilize identical position IDs, making M-RoPE functionally equivalent to 1D-RoPE”; for an image “the temporal IDs of each visual token remain constant, while distinct IDs are assigned to the height and width components”; the next modality starts at “the maximum position ID of the preceding modality” plus one ({{section 2.1|https://arxiv.org/html/2409.12191}}) paper. Qwen3-VL keeps the three groups but interleaves them across the frequency bands, because “chunking the embedding dimensions into temporal (t), horizontal (h), and vertical (w) groups induces an imbalanced frequency spectrum” ({{Qwen3-VL Technical Report, section 1|https://arxiv.org/html/2511.21631}}) paper; Qwen3.5-0.8B’s config says "mrope_interleaved": true, "mrope_section": [11, 11, 10].

To check: open the {{What the model saw|#t-vmsaw}} tab and click any token of any image to read its position, 1-D for SmolVLM and (t, h, w) for Qwen3.5, as the models’ own code computes them (get_rope_index in models/qwen3_5/modeling_qwen3_5.py, line 1364).
