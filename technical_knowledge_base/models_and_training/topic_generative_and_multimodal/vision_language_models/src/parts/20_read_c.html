2. Resolution and positions: tiles against native resolution

The problem. An encoder trained on 224 or 384-pixel squares sees a phone screenshot or an A4 page squashed into that square: thin text vanishes and the aspect ratio is wrong. Feeding the full image at one token per patch would fix it at a cost that grows with the pixel count. Four answers have been used, in this order:

How native resolution works. Three changes make an encoder accept any size. (1) The image is resized only enough that both sides are multiples of the merged patch (32 pixels for Qwen3.5: 16-pixel patches, 2 × 2 merge), and its pixel count is kept inside a minimum and a maximum (Qwen3.5’s processor: 65,536 to 16,777,216 pixels, that is 64 to 16,384 tokens). The rule is smart_resize (transformers v5.20.1, models/qwen2_vl/image_processing_qwen2_vl.py line 63; ported in the {{Token and cache budget|#t-vmbud}} tab and checked against the processor on 24 sizes). (2) The encoder’s fixed position table is replaced or supplemented by 2-D RoPE (rotary position embeddings that rotate by row and by column), so any grid is legal: Qwen2-VL “modified ViT by removing the original absolute position embeddings and introducing 2D-RoPE” paper. (3) The language model is told where each token sat in the image, through 3-D positions (below).

2a. Positions in 1-D and 3-D

A language model with rotary position embeddings (RoPE, see {{Positional Encodings|n:3c65c17b0d0d81a5b7c9e578fcdfac00}}) gives each token one integer position. SmolVLM’s language model does exactly that for image tokens: they are positions k, k+1, ..., so the token below a given one is 8 positions away inside a tile and the global view sits far from the tiles; the row and column survive only through the <row_r_col_c> text tags the processor inserts. M-RoPE (multimodal RoPE) splits the rotary dimensions into three groups for time, height and width: “For text inputs, these components utilize identical position IDs, making M-RoPE functionally equivalent to 1D-RoPE”, while for an image “the temporal IDs of each visual token remain constant, while distinct IDs are assigned to the height and width components”, and the next modality starts at “the maximum position ID of the preceding modality” plus one ({{Wang et al., section 2.1|https://arxiv.org/html/2409.12191}}) paper. Qwen3-VL keeps the three groups but interleaves them across the frequency bands, because “chunking the embedding dimensions into temporal (t), horizontal (h), and vertical (w) groups induces an imbalanced frequency spectrum” ({{Qwen3-VL Technical Report, section 1|https://arxiv.org/html/2511.21631}}) paper; Qwen3.5-0.8B’s config says "mrope_interleaved": true, "mrope_section": [11, 11, 10].

Predict, then reveal. Qwen3.5 reads a 512 × 512 photo as 256 image tokens (16 × 16) starting at position 4. Which position does the first text token after the image get?

Why it matters. Positions are a budget too. With 1-D positions a 4,096-token image consumes 4,096 positions of the trained context; with 3-D positions it consumes about 64. The paper gives this as a reason: M-RoPE “reduces the value of position IDs for images and videos, enabling the model to extrapolate to longer sequences during inference”. The context window in tokens (memory, compute) is unchanged: every image token is still attended to.

How to check it. Open the {{What the model saw|#t-vmsaw}} tab: pick any token of any image and read its position, 1-D for SmolVLM and (t, h, w) for Qwen3.5, as the models’ own code computes them (get_rope_index in models/qwen3_5/modeling_qwen3_5.py, line 1364).
