1. The vision transformer in detail

Every encoder on this page is a vision transformer (ViT): cut the image into square patches, turn each patch into a vector with one shared matrix (the patch embedding), add a vector that says where the patch was (the position embedding), run a stack of transformer blocks, and read one vector (or all of them) out at the end. The root's {{Vision lab|n:3c65c17b0d0d817ab6ade318917bff55}} animates that pipeline on CLIP and SigLIP 2 and checks that the patch embedding is exactly "cut, flatten, multiply"; the {{ViT paper page|n:3c65c17b0d0d811fa231cfcde6c1954d}} trains one from scratch. This section is the detail those two leave out: what the choices cost, and what breaks when you change them.

The five encoders run on this page

All five are base-size (about 86 million parameters in the image tower), so differences come from how they were trained, not from size. Each image goes through the model's own preprocessor, as anyone using the model would do.

What a token costs

The problem. Fine detail (small text, thin lines, many small objects) needs many pixels per object, and every extra patch is another token every layer must process. How it works. An R × R image in P × P patches gives N = (R / P)² tokens. Each transformer block then does four D × D projections per token (queries, keys, values, output), two N × N products for attention (scores, then the weighted sum), and two MLP matrices of D × F per token:

MACs per image ≈ 3P²·D·N + L · ( 4ND² + 2N²D + 2NDF )
N
tokens: (R/P)² patches plus any [CLS] or register tokens
D, F, L
width, MLP hidden width, number of blocks (768, 3,072, 12 for every base model here)
MACs
multiply-accumulates; FLOPs are about twice as many

Only the 2N²D term grows with the square of the token count, and at 224 pixels it is small: 4% of a ViT-B/16 and 23% of DINOv2 B/14 at its 518-pixel training size derived. Most of the cost is linear in tokens, so token count is the number to watch.

Predict: a ViT-B/16 goes from 224 × 224 to 448 × 448 pixels. How much more compute per image?
About 4.5×: 197 tokens become 785, four times as many, so the projections and MLP cost four times as much; the attention scores cost sixteen times as much, but they were only 4% of the total. The formula gives 17.56 to 78.49 GMACs, a factor of 4.47 derived. Quadratic attention starts to dominate only at much higher token counts, which is why VLMs that feed thousands of image tokens use windowed attention in the encoder (section 3).

How to check it. The formula agrees exactly with PyTorch's FLOP counter (torch.utils.flop_counter.FlopCounterMode) on transformers models built from the configs, but only when attention runs as plain matrix multiplies: with PyTorch's fused attention kernel (scaled_dot_product_attention, the default) the counter silently skips the 2N²D term measured. Published counts disagree for the same reason. The timm model card for ViT-B/16 at 224 says 16.9 GMACs, which matches the count without attention scores (16.85; with them, 17.56); the card for DINOv2 B/14 at 518 says 151.7, which matches the count with them (151.57; without, 116.98) derived. Two cards from one library, two accountings. The {{Tokens and cost|#t-vecalc}} tab shows the split for any configuration.
