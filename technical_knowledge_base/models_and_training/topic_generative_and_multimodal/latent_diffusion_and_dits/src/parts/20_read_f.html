5. MMDiT: text and image in one attention

The problem. In cross-attention the text is read but never changes: the 77 vectors are the same in every layer, so the text cannot adapt to what the image has become. DiT's class conditioning through adaLN carries only one vector, too little for a sentence. Stable Diffusion 3 wanted the text to be processed alongside the image ({{Esser et al., Mar 2024|https://arxiv.org/abs/2403.03206}}).

How it works. Concatenate the text tokens and the image tokens into one sequence and run one attention over all of it, but give each modality its own weights: "two separate sets of weights for the two modalities ... equivalent to having two independent transformers for each modality, but joining the sequences of the two modalities for the attention operation" (section 4). Each block has, for image and for text separately, the Q, K, V and output projections, the MLP and the adaLN modulation (driven by the timestep and the pooled text vector); only the softmax is shared. In diffusers the join is one line ({{attention_processor.py line 1480|https://github.com/huggingface/diffusers/blob/v0.41.0/src/diffusers/models/attention_processor.py#L1480}}): query = torch.cat([query, encoder_hidden_states_query_proj], dim=2), the same for keys and values, then split again after attention.

Who attends to whom: four ways to mix text and image

What it bought, by the paper's own comparison. On CC12M at matched settings, "Our MM-DiT variant significantly outperforms the cross-attention and vanilla variants" (DiT with concatenated text, CrossDiT with cross-attention, and UViT), on validation loss, CLIP score and FID (section 5.2.3, Figure 4; vendor, the authors' runs). Two engineering details came with it. QK-normalisation: at scale, attention logits grew until the attention entropy collapsed in the last blocks; RMSNorm on Q and K in both streams prevented it and "enables efficient training at bf16-mixed precision" (section 5.3.2, "QK-Normalization"). Modulation is a third of the model: each stream has its own d × 6d modulation per block, so counted here SD3.5 Large's modulation layers hold 2,686.3M of 8,056.6M parameters (33.3%) and Qwen-Image's (60 MMDiT blocks) 6,815.9M of 20,430.4M (33.4%).

A finding from counting: the position table the Hub counts and diffusers does not

SD3 Medium's config instantiated here has 2,028,328,000 parameters; the Hub's public total for the repo is 2,084,951,104. The difference, 56,623,104, is exactly 192 × 192 × 1,536: the 2-D position table for a 192 × 192 patch grid. Diffusers registers it as a buffer that is saved with the weights ({{embeddings.py line 331|https://github.com/huggingface/diffusers/blob/v0.41.0/src/diffusers/models/embeddings.py#L331}}: persistent = True if pos_embed_max_size else False), not as a parameter. SD3.5 Large: 8,146,280,768 on the Hub against 8,056,627,520 here, a gap of 89,653,248 = 192 × 192 × 2,432. With the table, both configs reproduce the Hub totals exactly. derived Parameter counts in model cards can include such tables; check before comparing.

The cost. Joint attention costs (N + T)2 per layer and the text stream's weights run on every text token, so text length is no longer nearly free: SD3.5 Large at 1024 pixels costs 28.95 TFLOP per pass with 77 text tokens and 31.12 with diffusers' 333 (a 7.5% difference, counted).

6. FLUX-style double and single stream blocks

The problem. Two full weight sets per block double the parameters per unit of depth. Once text and image have been mixed for a while, do they still need separate weights?

How it works. FLUX.1 (Black Forest Labs, August 2024; no paper, but the FLUX.1 Kontext report describes it) "is built from a mix of double stream and single stream blocks. Double stream blocks employ separate weights for image and text tokens ... After passing the sequences through the double stream blocks, we concatenate them and apply 38 single stream blocks to the image and text tokens. Finally, we discard the text tokens and decode the image tokens" ({{Labs et al. 2025|https://arxiv.org/abs/2506.15742}}, section 2). The released code has 19 double blocks and 38 single blocks ({{BFL flux util.py|https://github.com/black-forest-labs/flux/blob/802fb4713906133fcbd0d8dc5351620ca4773036/src/flux/util.py#L299}}: depth 19, depth_single_blocks 38, hidden size 3,072, 24 heads). A single-stream block is a parallel transformer block (as in ViT-22B): one LayerNorm and one modulation, then attention and the MLP computed side by side from the same input, their outputs concatenated and projected once ({{transformer_flux.py line 404|https://github.com/huggingface/diffusers/blob/v0.41.0/src/diffusers/models/transformers/transformer_flux.py#L404}}), which halves the modulation parameters and makes larger matrix multiplications.

Where the parameters go in ten denoisers

Shares of each model's parameters by kind of layer, counted on the meta device from the configs (attention and MLP split by stream; modulation = every adaLN, adaLN-single, time-injection or shared modulation layer). derived The {{Architecture explorer|#t-ldarch}} shows the numbers and the block structure.

Three things the counts show. (1) Guidance distillation is visible in the weights. FLUX.1 [dev] counted here is 11,901,408,320 and [schnell] 11,891,178,560, both equal to the Hub's public totals; the difference, 10,229,760, is the guidance embedder: [dev] was distilled to take the guidance scale as an input (embedded like the timestep), so it runs one denoiser pass per step where classifier-free guidance runs two. (2) Single blocks are half-size: FLUX.1's 38 single blocks hold 5,380.5M parameters, its 19 double blocks 6,456.8M. (3) Modulation keeps shrinking: 27.3% of FLUX.1, then FLUX.2 [klein] 4B shares one modulation per stream across all its blocks (5 double, 20 single): 160.4M, 4.1% of 3,875,544,576 (equal to the Hub total). Z-Image runs a single stream from the start (two refiner layers each for noise and caption, then 30 joint layers) with a low-rank modulation: 2.1% of 6,154,908,736.

Predict: FLUX.1 [dev] at 28 steps against SD3.5 Large at 28 steps with guidance 7.0, both at 1024 pixels. FLUX.1 has 1.5 times the parameters. Which costs more per image?

7. Positions for image tokens: tables, crops and 2-D RoPE

The problem. Attention is blind to order: shuffle the tokens and the outputs shuffle with them. An image transformer must be told where each patch sits, in two dimensions, and ideally in a way that still works at a resolution or aspect ratio it was not trained at.

Three answers in use.

  • A fixed 2-D sine-cosine table (DiT, PixArt): half the channels encode the row, half the column, at geometric frequencies. It is computed for one grid; the DiT code builds it at construction for one input size, which is why this page's FLOP counter had to rebuild DiT-XL/2 for every resolution.
  • A large table, center-cropped (SD3): one table for a 192 × 192 patch grid, cropped to the image's grid at run time ({{embeddings.py line 336|https://github.com/huggingface/diffusers/blob/v0.41.0/src/diffusers/models/embeddings.py#L336}}), so any size up to 192 × 2 × 8 = 3,072 pixels per side has positions. For mixed aspect ratios the paper builds "a combination of extended and interpolated position grids" and center-crops them (section 5.3.2).
  • Rotary embeddings in 2-D or 3-D (FLUX, Qwen-Image, Z-Image, FLUX.2): rotate each query and key by angles proportional to the token's position, so their dot product depends only on the offset between two tokens. FLUX splits each 128-wide head into 16 channels for a third axis (time or reference image), 56 for the row and 56 for the column (axes_dim [16, 56, 56]); image token ids are (0, row, column) ({{pipeline_flux.py line 508|https://github.com/huggingface/diffusers/blob/v0.41.0/src/diffusers/pipelines/flux/pipeline_flux.py#L508}}) and the text tokens' ids are all zero, so text sits at "no position" and is told apart by its own weights. Qwen-Image's MSRoPE instead places the text "along the diagonal of the image" grid ({{Qwen-Image report|https://arxiv.org/abs/2508.02324}}, section 2.4). Z-Image uses 32/48/48 channels; FLUX.2 four axes of 32. There is no table to outgrow, which helps with new sizes but does not by itself make the model good at them (section 8).
