10. Native or pipeline: the design decision

A product that chats, looks at images, draws and talks can be one network or specialised models wired together. Both exist in production; the choice is an engineering trade.

The pipeline loses whatever is not written down; the native model pays in pretraining and stability

QuestionPipeline (separate models)Native (one network)
What crosses between partsText or a small vector: anything not written down is lost (tone, layout, the exact look of an input image)Everything stays in one sequence; the model can copy, edit and refer to any earlier pixel or sound
Image quality todayThe best open image generators are diffusion and flow models (parent page, Model map)Discrete-token generators are capped by their tokenizer (section 5); hybrids (Transfusion, BAGEL) close the gap by keeping a diffusion objective
LatencyStages add up (2.8 to 5.4 s for OpenAI's old voice cascade)One model, one stream (232 to 320 ms claimed for GPT-4o, 160 to 200 ms for Moshi); vendor numbers, not comparable setups
Cost to buildReuse trained parts; train a few projectionsPretrain on interleaved data from the start; stability work (Chameleon's QK-norm, section 6)
Upgrading one partSwap the generator or the speech modelRetrain or fine-tune the whole model
Control and auditText between stages can be logged, filtered, editedFilters must work on images and audio directly (GPT-4o's streaming voice classifier)
Editing an input imageHard: the generator sees only a prompt (unless it takes the image too)Natural: the input image is in context (the GPT-4o addendum's "Image-to-Image Transformation")

A rule that survives the details. If the output must depend on fine detail of an input in another modality (edit this photo, answer in the same voice, keep this character consistent across images), information must not pass through a narrow text channel, so native or at least deeply coupled designs win. If each modality is a separate job with a clean text interface (caption, then illustrate), a pipeline of the best specialists is cheaper, faster to improve and easier to control.

The pipeline at its most explicit: NExT-GPT (example)

The pipeline at its most explicit. NExT-GPT uses ImageBind (1.2B) to read, a Vicuna 7B to think, and Stable Diffusion 1.5, AudioLDM and Zeroscope to write images, sound and video; the language model emits special "modality signal" tokens that tell a projection which decoder to drive, and only the projections and a LoRA are trained: "155M(=28+33+31+31+32) / [155M + 12.275B ...], or only 1% of parameters" ({{Wu et al., arXiv 2309.05519v3, section 3|https://arxiv.org/html/2309.05519v3}}) authors. By its own arithmetic that is 1.25%, not 1% derived.

How to check which you have. Ask the model to edit a detail of an input image that a caption would not mention (the pattern on a sleeve, a number in the corner), or to answer a question about a speaker's tone. A pipeline fails in characteristic ways: it redraws the image from scratch, or answers about the words only.

Six mistakes, with what they look like (real errors from the runs)
Image codes put into a text vocabulary without an offset
In a shared vocabulary, image code c must become id Vtext + c. Forget the offset and nothing fails: code 472 silently looks up text token 472. Add the offset but leave the embedding sized for text only and PyTorch stops you: (run here with a 32,000-entry text table and ids 32,472 to 32,999). Check: assert that every image id is at least Vtext and below the embedding's row count, and that the output softmax is restricted to image ids inside an image span. measured
Decoding tokens with a different tokenizer than the one that made them
Codes are only meaningful to the tokenizer that produced them. FSQ-1000 codes fed to the 128-code VQ decoder raise ; the reverse is worse because it runs: VQ-128 codes decoded by the FSQ decoder give images the classifier recognises of the time (chance is 10%), FD against with the right decoder. Ship the tokenizer's hash with the generator. measured
Judging an autoregressive image model below its tokenizer's ceiling
If the tokenizer's own reconstructions score FD on real images, no generator over its codes will score much better without guidance, whatever its size. Measure the tokenizer's reconstruction FD (or rFID) first, at the same N, and report it beside the generator's number. measured
Counting sequential calls and calling it compute (or the reverse)
An autoregressive image costs one call per token but each call processes one new token; a diffusion step processes every latent token at once. The tiny models here differ by times in sampling FLOPs and the other way round in sequential calls (section 5). State both, and the batch size, whenever comparing speed.
A masked-token loss written with boolean indexing, on Apple's GPU
The natural MaskGIT loss, F.cross_entropy(logits[masked], t[masked]), gives a tensor whose length changes every step (the number of masked codes is random). On MPS under this topic's memory cap, memory use grew until, about 200 steps in, training stopped with RuntimeError: MPS backend out of memory (MPS allocated: 1.09 GiB, other allocations: 4.21 GiB, max allowed: 5.33 GiB). Tried to allocate 31.50 MiB on shared pool., for a 3M-parameter model whose autoregressive twin peaked at 2.5 GiB. The fix keeps shapes fixed: cross-entropy at every position, multiplied by the mask, divided by its sum (src/ar/tinyar.py, mask_loss). Same mathematics; the rerun peaked at 2,498 MiB. (Why varying shapes cost so much memory on MPS was not investigated further.) measured
Porting a resize rule with the wrong rounding
The Qwen image processor rounds with Python's round(), which sends halves to the even neighbour. A JavaScript port using Math.round for this page's {{Token economics|#t-nmtok}} tab first got 5 of 24 recorded sizes wrong (336 × 336 gave 121 tokens instead of 100, because 336 / 32 = 10.5 rounds to 10, not 11); with half-to-even it matches all 24. measured
Two design questions (interview rehearsal)
Design: add image generation to an existing 8B chat model. What do you build?
Cheapest first: a pipeline, where the LLM writes a prompt for a strong diffusion model, gives the best image quality today and needs no pretraining; it fails at edits of input images. If edits and consistency matter, add a generation pathway the LLM conditions directly: either discrete codes from a good tokenizer (f = 16, 16k-ish codes, LlamaGen-style) predicted by the LLM with CFG, or, better per FLOP, a diffusion or flow head over VAE latents with a separate set of expert weights (BAGEL-style) so text quality is not damaged. Keep the understanding encoder separate from the generation tokenizer (Janus's lesson). Measure: tokenizer reconstruction FD first, then GenEval or a preference eval, text benchmarks before and after, latency per image (sequential calls times per-call time).
Design: a voice assistant with a 300 ms response target.
A cascade's three stages add up to seconds (OpenAI's own 2.8 to 5.4 s). Use a low-frame-rate causal codec (12.5 Hz, about 8 codebooks) so the big model runs once per 80 ms frame, a small depth model for the codebooks within a frame, text predicted alongside audio, and streaming decode; full duplex if interruptions matter. Budget: frame time plus acoustic delay (Moshi: 80 + 80 = 160 ms theoretical). Add a voice-identity classifier on the output stream.
What transfers from this laptop, and what does not (provenance)
  • Transfers: the shape of the trade-offs. A discrete tokenizer sets a ceiling the generator cannot pass without guidance; autoregressive sampling costs one call per token and little compute per call; masked decoding trades calls for passes over all tokens; guidance on logits behaves like guidance on noise predictions (better fidelity, less diversity); greedy decoding collapses an image distribution.
  • Does not transfer: the ranking. At 64 tokens and 3M parameters, trained for minutes on 28 × 28 grey clothing, small differences in FD are noise from one training run and one tokenizer; published results at scale (LlamaGen 2.18 with guidance against DiT 2.27 on ImageNet 256, VAR 1.92, MAR 1.55; sections 4 and 5) differ from each other more because of tokenizers, sizes and recipes than because of the family. Timings were measured on an Apple M1 Pro (MPS) at batch 1 and batch 1,000 and say nothing about an H100 serving stack (vLLM made LlamaGen 3.3 to 4.1 times faster in its own Table 7).
  • Not run here: any real native multimodal model (Chameleon is gated and image generation was not released; Janus-Pro-7B, BAGEL and Emu3 exceed the memory budget in fp16 for little extra lesson beyond published numbers); any speech model (the sibling page {{Video and audio generation|n:3c65c17b0d0d8198bd7be111a3dc4c3a}} ran the codecs).
