The idea in one screen

A native multimodal model makes every modality positions in one token sequence of one transformer; the designs differ in what an image becomes on the way in (encoder vectors, latent patches, discrete codes or raw patches) and how an image is written out (not at all, one code per call, a few parallel rounds, or diffusion inside the same network), and each choice is paid for in quality, sequential calls and training stability.

1. Early against late fusion: where the modalities meet

A modality is a kind of signal (text, images, audio, video). The question that separates multimodal designs is where and when the modalities meet, called fusion. Late fusion approaches "encode images and text separately before combining them at a later stage": a VLM such as LLaVA is late fusion, a pretrained image encoder plus a small projector into a pretrained language model. Early fusion means "all modalities are projected into a shared representational space from the start" (both from Chameleon, arXiv 2405.09818v2, sections 6 and 1). Any-to-any is the far end; GPT-4o's system card is the best-known claim: it "accepts as input any combination of text, audio, image, and video and generates any combination of text, audio, and image outputs" (arXiv 2410.21276v1) vendor. Native is a training claim, not an architecture: section 6 shows four models that use the word and mean different things.

Predict before you step: the request "here is a photo of a pullover, draw it in red" runs through both designs. Which needs more sequential network calls, and which generator ever sees your photo?

In the pipeline every detail the sentence leaves out (the exact cut, the cuffs, the pose) is gone and the generator draws a new pullover; in the early-fusion model every output code can attend to every input code. 2. Two kinds of image token: one to read, one to write

A transformer works on a sequence of vectors; text gets there by looking each token id up in an embedding table. An image has no ids, and what it becomes decides whether the model can ever write images.

Soft tokens (continuous). A vision encoder (ViT, SigLIP) outputs one vector per patch; a projector maps them to the model's width. Rich and semantic, but the model cannot output them: its output layer is a softmax over the vocabulary, and soft tokens are not in it. Every VLM and the encoder-free models read images this way: 1,088 positions for one image in SmolVLM-500M, 280 by default in Gemma 4 12B Unified.

Discrete tokens (codes). An image tokenizer (VQ-VAE, VQGAN or FSQ) maps each cell of a small latent grid to the index of its nearest codebook entry: an integer, exactly like a text token id, and a decoder maps codes back to pixels. Now the model can predict an image with the same softmax and cross-entropy it uses for words. The price: the tokenizer's reconstruction is lossy, and the model must write every code.

How the tokenizer is trained is the sibling page Autoencoders and VAEs's; here it is a fixed part. The running example uses that page's best tiny tokenizer, an FSQ autoencoder with levels [8, 5, 5, 5] (8 × 5 × 5 × 5 = 1,000 codes): each 28 × 28 Fashion-MNIST image, padded to 32 × 32, becomes an 8 × 8 grid, so 64 tokens from 1,000 codes. The topic's 128-code VQ-VAE (root Latent lab recordings; VQ training is taught on Autoencoders and VAEs) gives a second tokenizer of the same shape.

How many bits is an image? Writing one of 1,000 codes blindly costs log2 1,000 = 9.97 bits, so 64 codes cost 637.8 bits; the codes' frequencies over the training set give 8.11 bits per code, 519.2 per image. An autoregressive model that predicts each code from the class and the codes before it needs, on held-out validation images, 233.7 bits per image: its exact negative log-likelihood, a number diffusion models cannot give cheaply.

Why not one kind for both jobs? Janus tried it: with one VQ tokenizer for reading and writing, its understanding score (POPE) was 60.1; with SigLIP features to read and VQ codes to write, 87.0 (Janus Table 5, arXiv 2410.13848v1) vendor. Codes trained to reconstruct pixels keep what pixels need (exact edges, colours), not what a question needs (what the object is). That is why Janus, BAGEL and most unified models keep two encodings (section 6).

3. Writing an image one token at a time

Put the image's codes in raster order (left to right, top to bottom) and model them like words. The chain rule turns the probability of a whole image into a product of next-token probabilities:

p(x1, …, x64 | c) = ∏i p(xi | c, x1, …, xi−1)
xi
the code at position i (one of 1,000 here)
c
the condition: a class here, a text prompt in a real model, both as tokens before the image

Training is next-token cross-entropy with teacher forcing, all 64 positions in one pass under a causal mask; generating is a loop of one call, one sampled code, append. The running example's model is a 6-layer transformer of width 192 (3,069,160 parameters, 3.07M), the class embedding as the first position (LlamaGen's layout), trained with the topic's exact DDPM recipe (the one Diffusion from zero uses) (batch 128, AdamW 5 × 10-4, EMA 0.999, 10% of labels dropped for guidance) for 4,207 steps, 490 s on the M1 Pro's GPU.

Three knobs, the same as for text. Temperature T divides the logits before the softmax (0 means always take the top code, greedy); top-k keeps the k likeliest codes; classifier-free guidance on logits runs the conditional and the null-class input together and uses lu + s(lc − lu), s = 1 being the plain conditional model. LlamaGen states this form; its best ImageNet result uses s = 1.65 (arXiv 2406.06525v1). Guidance doubles the batch, not the number of sequential steps. The same knobs for text, with real logits, are on Sampling and Decoding; for images the verdicts differ.

Temperature and top-k trade diversity for typicality and FD punishes it; guidance is the knob that buys fidelity

One knob per view, 1,000 samples per point (100 per class), the same random draws at every setting; FD in the shared classifier's feature space against the 10,000 test images (lower is better; 1,000 real validation images score 18.93). measured on Apple M1 Pro (MPS)

What the measurements say. Without guidance the best FD is at temperature 1, the temperature the model was trained for: cooling to 0.7 makes every class look tidier (classifier accuracy rises) but samples cluster around the most typical shapes, diversity drops and FD gets worse; heating to 1.3 adds noise faster than variety. Top-k behaves like cooling: keeping the 10 likeliest codes gives FD 75.9 against 54.6 with all 1,000. Guidance helps most: the best scale, s = 1.5, brings FD to 44.2 with 92.1% of samples recognised as the asked-for class; s = 0 (the unconditional model) gives FD 218.0 and the right class only 11.7% of the time, chance level. measured Guidance on logits behaves as guidance on noise predictions does for diffusion (the topic's DDPM runs scored best at s = 2, root Diffusion lab recordings).

The sampling loop that produced every number, guidance in library code, and two checks (code)

Copied from src/ar/tinyar.py (sample_ar, without its recording lines):

for i in range(m.n_tok):
    inp_tokens = out if (not use_cache or i == 0) else out[:, -1:]
    if cfg not in (0, 1):
        inp_tokens = torch.cat([inp_tokens, inp_tokens])
    if use_cache:
        lg = m(inp_tokens if i > 0 else inp_tokens[:, :0], yy, caches=caches, start=0 if i == 0 else i)[:, -1]
    else:
        lg = m(inp_tokens, yy)[:, -1]
    if cfg not in (0, 1):
        lc, lu = lg.chunk(2); lg = lu + cfg * (lc - lu)
    f = _filter(lg.float(), temperature, top_k)
    if f is None:
        nxt = lg.argmax(-1)
        p = lg.float().softmax(-1)
    else:
        p = f.softmax(-1)
        if u is not None:
            nxt = _draw(p, u[:, i].to(dev))
        else:
            nxt = torch.multinomial(p.cpu(), 1, generator=gen).squeeze(1).to(dev)
    out = torch.cat([out, nxt[:, None]], 1)

Guidance in library code: transformers implements the same line for Janus as scores_processed = uncond_logits + (cond_logits - uncond_logits) * self.guidance_scale (logits_process.py line 2205, v5.20.1), and Janus's generate falls back to 5 when no scale is given (modeling_janus.py line 1194).

Checks that ran: the cached and uncached loops give logits within 1.4 × 10-6 and identical samples (CPU); one image at batch 1 takes 0.18 s with the cache and 0.15 s without (MPS, median of 3): at 64 tokens recomputing the short prefix is cheaper than the cache's bookkeeping on this GPU; the cache pays off for the thousands of tokens of a real image or conversation, where recomputation grows with the square of the length. measured

5. Autoregressive against diffusion and flow, at equal training compute

The setup. The topic's diffusion run trained a 1.04M-parameter TinyUNet as a DDPM for 4,000 steps at batch 128, and its flow run trained the same network with flow matching (root Diffusion and Flow lab recordings). One TinyUNet forward pass on one image costs 403.0 MFLOP (counted with PyTorch's FlopCounterMode); one pass of the token transformer over 64 tokens costs 383.2 MFLOP (linear layers counted, attention added by formula because the counter skips the fused attention kernel). So the transformer trains for 4,000 × 403.0 / 383.2 = 4,207 steps: the same training FLOPs, the same images in the same minibatch order.

At equal training FLOPs diffusion and flow win on quality; the token model wins on sampling cost by three orders of magnitude

FD in the shared classifier's feature space, N = 1,000 (100 per class), lower is better; the real-image floor is the same score for 1,000 real validation images; the tokenizer ceiling is the FSQ autoencoder's reconstructions of those images. Training FLOPs = 3 × forward FLOPs × 128 × steps (the usual forward plus backward estimate). Sampling FLOPs per image include guidance's second pass and, for the token models, the tokenizer's decoder. The FSQ tokenizer's own training (5,000 steps at batch 128) adds about 48 TFLOP, outside the matched budget of 619 TFLOP. DDPM and flow rows are the root's recorded numbers (src/diff/out, src/flow/out), not re-run. measured on Apple M1 Pro (MPS)

The tokenizer is a ceiling, and guidance can look through it. Without guidance the token model's FD (54.6) sits above the tokenizer's own reconstruction FD (47.7), as it must. Guidance (s = 1.5) brings it to 44.2, below that ceiling, because guidance does not model the data distribution: it pushes samples toward what is typical of each class in the classifier's feature space, which is exactly what FD measures here. Quality: DDPM 34.9 without guidance, flow 23.8 with it; their pixel-space denoiser loses nothing to a tokenizer. Cost: 64 small calls and about 373.9 MFLOP per image against 1,000 full-image calls and about 403 GFLOP for the DDPM (1,028 times fewer FLOPs; 51 times fewer than 50 flow steps). A worse tokenizer makes everything worse: over the topic's 128-code VQ the same transformer reaches FD 108.5 (81.2 with guidance), although its likelihood looks better (179.0 bits per image against 233.7): fewer bits to predict because the tokenizer kept less. Bits per image are comparable only for the same tokenizer. measured

At scale. On ImageNet 256 the families have traded places for years: LlamaGen-3B FID 2.18 with guidance s = 1.65 (9.38 without), VAR 1.92, MAR 1.55, DiT-XL/2 2.27, each reported by its own authors with its own tokenizer or VAE (LlamaGen, VAR, MAR) vendor. For text-to-image inside a unified model, Transfusion's controlled comparison (section 6) found continuous latents with a diffusion loss far more compute-efficient than discrete tokens, for the reason seen here: a discrete tokenizer throws information away before the generator starts.

Chameleon: everything is a token, and the training fights back

Chameleon (Meta, May 2024) is the reference early-fusion model: the shared space "allows for seamless reasoning and generation across modalities. However, it also presents significant technical challenges, particularly in terms of optimization stability and scaling" (arXiv 2405.09818v2, section 1). A VQ tokenizer turns "a 512 x 512 image into 1024 discrete tokens from a codebook of size 8192", and those 8,192 codes sit inside one BPE vocabulary of 65,536; the 7B and 34B transformers predict text and image tokens with the same softmax.

Why it was hard: the modalities compete. With all weights shared, "each modality will try to "compete" with the other by increasing its norms slightly", harmless early but divergent "once we get outside the effective representation range of bf16"; with image generation disabled training showed no instability (Figure 10). The fixes: QK-Norm (layer norm on queries and keys before the attention softmax) for both sizes, "essential in both cases"; dropout 0.1 for the 7B, a Swin-style reordering of the norms for the 34B; and z-loss, 10-5 log2 Z on the output softmax's normaliser Z, because QK-Norm "does not solve the problem of logit shift in the final softmax". The operational lesson: "monitoring uncontrolled growth of output norms is strongly correlated with predicting future loss divergence", even when divergence arrives "after as much as even 20-30% of training progress" (all section 2.3) vendor. How QK-norm and z-loss work in any transformer is on Normalisation, residuals and stability.

Emu3 (BAAI, September 2024) pushed the same bet to an 8B model writing 4,096 codes per 512 × 512 image, and Emu3.5 (October 2025) fills those codes in parallel rounds for "about 20x" faster images.

Chameleon's evidence, what Meta released, and Emu3's numbers (provenance)

What it showed, and what it released. No FID or GenEval of its own: its evidence is human preference on mixed text-and-image answers, 60.4% and 51.6% win rates (a tie counts half) against Gemini and GPT-4V answers augmented with DALL·E 3 images ("Gemini+" and "GPT-4V+" in the body; the introduction calls them "Gemini-Pro and GPT-4V") vendor. The released weights take images in but write only text: "At this time, we are not releasing the Chameleon image generation model" (Meta blog, 18 June 2024); licence Chameleon Research License (research only, gated). The transformers port enforces it in code: after the output layer, logits[:, :, image_tokens] = torch.finfo(logits.dtype).min under the comment "Disallow image tokens" (modeling_chameleon.py lines 1066 to 1068, v5.20.1); its QK-Norm is self.q_norm = ChameleonLayerNorm(...) at line 280. Its own named weakness is the tokenizer: "reconstructing images with a large amount of text" (section 2.1).

Emu3 (BAAI, September 2024) keeps the bet and pushes it: an 8B model with a 131,072-token context, 4,096 tokens from 32,768 SBER-MoVQGAN codes for a 512 × 512 image, sampled with top-k 16,384 and guidance 5.0 to 5.5 (arXiv 2409.18869v1) vendor. Its GenEval win over SDXL (0.66 against 0.55) uses a GPT-4V prompt rewriter; without it Emu3 scores 0.54 (its Table 7). Emu3.5 (October 2025) fills tokens in parallel for "about 20x" faster images; its Table 16 (512 s to 22 s, or 120 s to 10 s with FlagScale, for a 4,096-token 1024 × 1024 image) gives ratios of about 23 and 12 derived (arXiv 2510.26583v1).

Janus: one transformer, two image encodings

DeepSeek's Janus starts from the section 2 measurement: "due to the differing levels of information granularity required by multimodal understanding and generation, this approach can lead to suboptimal performance ... we decouple visual encoding into separate pathways" (arXiv 2410.13848v1): SigLIP-Large-Patch16-384 features to read, LlamaGen's VQ tokenizer (16,384 codes, downsampling 16, 384 × 384 images, so 576 tokens: derived) to write.

Transfusion: next token for text, diffusion for images, one set of weights

Transfusion (Meta, August 2024) keeps images continuous: it "combines the language modeling loss function (next token prediction) with diffusion to train a single transformer over mixed-modality sequences" (arXiv 2408.11039v1). An 86M-parameter VAE turns a 256 × 256 image into a 32 × 32 × 8 latent; U-Net down blocks make 2 × 2 latent patches, 256 positions per image. The loss is L = LLM + λ LDDPM with λ = 5 (section 7). The mask is "causal attention to every element in the sequence, and bidirectional attention within the elements of each individual image"; turning on the bidirectional part alone moved FID from 61.3 to 20.3 in their ablation (Table 5, 0.76B models).

Predict: the authors retrained a Chameleon-style discrete-token model and Transfusion at 7B on the same 0.5T tokens. How much of Chameleon's compute did Transfusion need to match its image FID?
vendor A parity FLOP ratio of 0.029 (Table 3): "34x less compute". To match the CLIP score it needs 0.319, which is where the introduction's "less than a third of the compute" comes from: two headlines from one table, one per metric. The chart below shows all six.

Show-o and BAGEL: the other hybrids

  • Show-o (NUS and ByteDance, 2024): 1.3B (Phi-1.5), images as MAGVIT-v2 lookup-free codes (8,192, 16 × 16 at 256 px), written by masked prediction as in section 4, with "omni-attention": "Show-o model text tokens v within the sequence via causal attention.   • BAGEL (ByteDance Seed, 2025): a "Mixture-of-Transformer-Experts (MoT) architecture that employs selective activation of modality-specific parameters" with "shared self-attention operations": separate weights for understanding and generation tokens, one attention over both; SigLIP 2 to read, the FLUX VAE latent and rectified flow to write; 7B active, 14B total (arXiv 2505.14683v3). Why separate weights pay is section 7.

Encoder-free: patches straight into the language model

Every design above still has an image encoder or tokenizer trained separately. Fuyu-8B (Adept, October 2023) removed it: "there is no image encoder. Image patches are instead linearly projected into the first layer of the transformer, bypassing the embedding lookup" (model card; 30-pixel patches, CC-BY-NC). Gemma 4 12B Unified (Google; Hugging Face repository created 23 May 2026; Apache 2.0) does the same at scale for images and audio: it "takes in 48 x 48 x 3 RGB patches, but replaces the 550M vision encoder by a single large matmul (35M parameters)", with 2-D coordinate position embeddings, and is "trained from scratch" (Gemma 4 report, arXiv 2607.02770v2, section 2.3). It reads images and audio; it does not write them.

7. Interleaved data and the balance between modalities

A model that shares weights across modalities has to be told, three ways, how much each modality matters: by the data mix (what share of tokens is text, image-caption pairs, or interleaved documents, where images sit at their place in running text), by the loss weights, and by which weights each modality may use. Only interleaved documents show the model several images with the text between them, the shape of the mixed answers these models are asked to write; a caption pair is one image and one sentence.

Loss weights. Transfusion trains on "50% text and 50% image data" with L = LLM + λ LDDPM, λ = 5 "following preliminary experiments". The weight is needed because the two losses count differently: the "LM loss is computed per token, while diffusion loss is computed per image", one term spread over 256 patches. In a Chameleon-style model there is one cross-entropy over one vocabulary, so the balance is set by the data mix alone, and the modalities fight inside the shared softmax and norms (section 6).

Modality-specific weights. The cure for competition that does not touch the data is to stop sharing everything: Mixture-of-Transformers "decouples non-embedding parameters of the model by modality" (the feed-forward networks, attention projection matrices and layer norms), keeping "global self-attention over the full input sequence" (arXiv 2411.04996v2). BAGEL is this design with two experts, one for understanding (text and ViT tokens) and one for generation (VAE tokens): about twice the parameters, "identical FLOPs during both training and inference" as its dense baseline.

9. Speech in and out: from a three-model cascade to one model per audio frame

A voice assistant built as a cascade runs speech recognition, a language model and text-to-speech in a row. OpenAI's description of its own pre-GPT-4o Voice Mode is exactly this: "a pipeline of three separate models", with average latencies "of 2.8 seconds (GPT-3.5) and 5.4 seconds (GPT-4)", and the language model "loses a lot of information": "it can't directly observe tone, multiple speakers, or background noises, and it can't output laughter, singing, or express emotion" (Hello GPT-4o, 13 May 2024, archived) vendor.

The cascade hands text between three models; a native model writes one column of 17 tokens every 80 ms

Moshi's layout, drawn for 6 frames (480 ms): one model takes the user's audio tokens in and writes its own text and audio tokens in the same 80 ms step, so nothing passes through a text hand-off and tone survives in both directions. How the 17 streams are laid out (inner-monologue text, the temporal and depth transformers, the one-frame acoustic delay) is taught on Video and audio generation, section 8, which owns the codec and the streams. lab

How native speech works. A neural audio codec cuts the waveform into frames and quantizes each frame with several codebooks in a chain (residual vector quantization); the codecs themselves are Video and audio generation's, and here only the rates matter. Two open designs:

  • Moshi (Kyutai, 2024): one full-duplex model on the Mimi codec at 12.5 frames a second (8 codebooks, 1.1 kbps), one big-model step per 80 ms frame; "a theoretical latency of 160ms, 200ms in practice" (arXiv 2410.00037v2) lab. Its streams, inner monologue and latency budget: Video and audio generation, section 8.
  • Qwen2.5-Omni and Qwen3-Omni (Alibaba, open weights): a Thinker (the language model) and a Talker that turns the Thinker's output into speech codes, "end-to-end jointly trained" (Qwen2.5-Omni, arXiv 2503.20215v1). In Qwen3-Omni both are mixtures of experts (Thinker 30B with 3B active, Talker 3B with 0.3B active), input and output audio run at 12.5 Hz, the Talker predicts the first codebook and a small multi-token module the residual ones, a causal ConvNet replaces diffusion for code-to-waveform, and the "theoretical end-to-end first-packet latency" is 234 ms for audio, 547 ms for video, 1,172 ms at 6 concurrent requests (arXiv 2509.17765v1, Tables 1 and 2) vendor.
AnyGPT, cascade latency sources, and the Qwen omni licences (depth)
  • AnyGPT (Fudan, 2024): the purest "everything is a token" design. Speech through SpeechTokenizer (8 codebooks of 1,024 at 50 Hz; the language model predicts only the first, semantic one), images through SEED (32 tokens from 8,192 codes, decoded by an unCLIP Stable Diffusion), music through Encodec (4 codebooks of 2,048 at 50 Hz, 200 tokens a second), all on an unchanged LLaMA-2 7B: "without any alterations to the current large language model (LLM) architecture" (arXiv 2402.12226v3). Its Table 1 gives the music vocabulary as 4,096 while its text says 8,192: the paper disagrees with itself.
  • Cascade latency, other sources: Kyutai's Moshi paper puts it at "several seconds", against "a few hundred milliseconds" in human conversation (Défossez et al. 2024, section 1) lab; no primary source checked here gives a component-by-component breakdown of a cascade (unconfirmed).
  • Qwen licences: Apache 2.0 for the Qwen3-Omni 30B-A3B models; Qwen2.5-Omni-3B is under a research licence while the 7B is Apache 2.0 (model cards, 2026-10-17).
Predict: a native speech model must produce 10 seconds of audio with Mimi tokens. If every codebook token were generated by the big model one at a time, how many big-model steps is that, and what time budget does each step get for real time?
derived 10 s × 12.5 frames × 8 codebooks = 1,000 tokens, so 1,000 sequential steps with 10 ms each, a hard budget for a 7B model. Moshi's layout runs the big model once per frame (125 steps, 80 ms each) and leaves the 8 codebooks of a frame to a small depth transformer: the same tokens, an eighth of the big steps. Try both layouts in Token economics, part 3.

When it matters. Native speech wins when the turn-taking delay or the voice itself is the product (tone, interruptions, laughter). A cascade wins when you must swap parts (a better recogniser, a new voice), audit the text that was said, or reuse a strong text model without retraining it on audio. Safety has to be rebuilt for the audio channel: OpenAI allows "only the preset voices we created in collaboration with voice actors" and runs "a standalone output classifier" in streaming fashion that blocks output whose speaker does not match the preset, after observing "rare instances where the model would unintentionally generate an output emulating the user's voice" (GPT-4o system card, section 3.3.1) vendor.

10. Native or pipeline: the design decision

A product that chats, looks at images, draws and talks can be one network or specialised models wired together. Both exist in production; the choice is an engineering trade.

The pipeline loses whatever is not written down; the native model pays in pretraining and stability

A rule that survives the details. If the output must depend on fine detail of an input in another modality (edit this photo, answer in the same voice, keep this character consistent across images), information must not pass through a narrow text channel, so native or at least deeply coupled designs win. If each modality is a separate job with a clean text interface (caption, then illustrate), a pipeline of the best specialists is cheaper, faster to improve and easier to control.

The pipeline at its most explicit: NExT-GPT (example)

The pipeline at its most explicit. NExT-GPT uses ImageBind (1.2B) to read, a Vicuna 7B to think, and Stable Diffusion 1.5, AudioLDM and Zeroscope to write images, sound and video; the language model emits special "modality signal" tokens that tell a projection which decoder to drive, and only the projections and a LoRA are trained: "155M(=28+33+31+31+32) / [155M + 12.275B ...], or only 1% of parameters" (Wu et al., arXiv 2309.05519v3, section 3) authors. By its own arithmetic that is 1.25%, not 1% derived.

How to check which you have. Ask the model to edit a detail of an input image that a caption would not mention (the pattern on a sleeve, a number in the corner), or to answer a question about a speaker's tone. A pipeline fails in characteristic ways: it redraws the image from scratch, or answers about the words only.

Depth: mistakes, design questions, and what transfers

Optional. Each block is closed; none is needed to follow the sections above.

Six mistakes, with what they look like (real errors from the runs)
Image codes put into a text vocabulary without an offset
In a shared vocabulary, image code c must become id Vtext + c. Forget the offset and nothing fails: code 472 silently looks up text token 472. Add the offset but leave the embedding sized for text only and PyTorch stops you: IndexError: index out of range in self (run here with a 32,000-entry text table and ids 32,472 to 32,999). Check: assert that every image id is at least Vtext and below the embedding's row count, and that the output softmax is restricted to image ids inside an image span. measured
Decoding tokens with a different tokenizer than the one that made them
Codes are only meaningful to the tokenizer that produced them. FSQ-1000 codes fed to the 128-code VQ decoder raise IndexError: index 472 is out of bounds for dimension 0 with size 128; the reverse is worse because it runs: VQ-128 codes decoded by the FSQ decoder give images the classifier recognises 7.6% of the time (chance is 10%), FD 1656.12 against 87.05 with the right decoder. Ship the tokenizer's hash with the generator. measured
Judging an autoregressive image model below its tokenizer's ceiling
If the tokenizer's own reconstructions score FD 47.66 on real images, no generator over its codes will score much better without guidance, whatever its size. Measure the tokenizer's reconstruction FD (or rFID) first, at the same N, and report it beside the generator's number. measured
Counting sequential calls and calling it compute (or the reverse)
An autoregressive image costs one call per token but each call processes one new token; a diffusion step processes every latent token at once. The tiny models here differ by 1,028 times in sampling FLOPs and the other way round in sequential calls (section 5). State both, and the batch size, whenever comparing speed.
A masked-token loss written with boolean indexing, on Apple's GPU
The natural MaskGIT loss, F.cross_entropy(logits[masked], t[masked]), gives a tensor whose length changes every step (the number of masked codes is random). On MPS under this topic's memory cap, memory use grew until, about 200 steps in, training stopped with RuntimeError: MPS backend out of memory (MPS allocated: 1.09 GiB, other allocations: 4.21 GiB, max allowed: 5.33 GiB). Tried to allocate 31.50 MiB on shared pool., for a 3M-parameter model whose autoregressive twin peaked at 2.5 GiB. The fix keeps shapes fixed: cross-entropy at every position, multiplied by the mask, divided by its sum (src/ar/tinyar.py, mask_loss). Same mathematics; the rerun peaked at 2,498 MiB. (Why varying shapes cost so much memory on MPS was not investigated further.) measured
Porting a resize rule with the wrong rounding
The Qwen image processor rounds with Python's round(), which sends halves to the even neighbour. A JavaScript port using Math.round for this page's Token economics tab first got 5 of 24 recorded sizes wrong (336 × 336 gave 121 tokens instead of 100, because 336 / 32 = 10.5 rounds to 10, not 11); with half-to-even it matches all 24. measured
Two design questions (interview rehearsal)
Design: add image generation to an existing 8B chat model. What do you build?
Cheapest first: a pipeline, where the LLM writes a prompt for a strong diffusion model, gives the best image quality today and needs no pretraining; it fails at edits of input images. If edits and consistency matter, add a generation pathway the LLM conditions directly: either discrete codes from a good tokenizer (f = 16, 16k-ish codes, LlamaGen-style) predicted by the LLM with CFG, or, better per FLOP, a diffusion or flow head over VAE latents with a separate set of expert weights (BAGEL-style) so text quality is not damaged. Keep the understanding encoder separate from the generation tokenizer (Janus's lesson). Measure: tokenizer reconstruction FD first, then GenEval or a preference eval, text benchmarks before and after, latency per image (sequential calls times per-call time).
Design: a voice assistant with a 300 ms response target.
A cascade's three stages add up to seconds (OpenAI's own 2.8 to 5.4 s). Use a low-frame-rate causal codec (12.5 Hz, about 8 codebooks) so the big model runs once per 80 ms frame, a small depth model for the codebooks within a frame, text predicted alongside audio, and streaming decode; full duplex if interruptions matter. Budget: frame time plus acoustic delay (Moshi: 80 + 80 = 160 ms theoretical). Add a voice-identity classifier on the output stream.
What transfers from this laptop, and what does not (provenance)
  • Transfers: the shape of the trade-offs. A discrete tokenizer sets a ceiling the generator cannot pass without guidance; autoregressive sampling costs one call per token and little compute per call; masked decoding trades calls for passes over all tokens; guidance on logits behaves like guidance on noise predictions (better fidelity, less diversity); greedy decoding collapses an image distribution.
  • Does not transfer: the ranking. At 64 tokens and 3M parameters, trained for minutes on 28 × 28 grey clothing, small differences in FD are noise from one training run and one tokenizer; published results at scale (LlamaGen 2.18 with guidance against DiT 2.27 on ImageNet 256, VAR 1.92, MAR 1.55; sections 4 and 5) differ from each other more because of tokenizers, sizes and recipes than because of the family. Timings were measured on an Apple M1 Pro (MPS) at batch 1 and batch 1,000 and say nothing about an H100 serving stack (vLLM made LlamaGen 3.3 to 4.1 times faster in its own Table 7).
  • Not run here: any real native multimodal model (Chameleon is gated and image generation was not released; Janus-Pro-7B, BAGEL and Emu3 exceed the memory budget in fp16 for little extra lesson beyond published numbers); any speech model (the sibling page Video and audio generation ran the codecs).
