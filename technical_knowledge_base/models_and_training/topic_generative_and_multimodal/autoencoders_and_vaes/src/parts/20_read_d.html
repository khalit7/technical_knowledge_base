4. Why reconstructions blur, and what actually fixes it

The problem. Autoencoders trained with a pixel loss give soft, smeared reconstructions, and VAEs more so. The Latent lab shows the effect; here are its four causes, because each has a different fix.

  1. The pixel loss rewards the average. When the code does not pin down a detail (the exact position of an edge, the pattern of a texture), the squared error is minimised by the mean of all the images consistent with the code, and the mean of slightly different sharp edges is a soft edge. Absolute error (L1) gives the median, a little sharper, but the same in kind. Fix: a loss that does not reward averaging, a perceptual or adversarial one.
  2. Too little rate. A small latent, a high β or a Gaussian σ that is too large (section 2) means the code pins down less, so there is more to average over. Fix: more channels or tokens, a smaller KL weight. Generator autoencoders use a KL weight of about 10−6.
  3. The VAE's sampling noise. Training decodes z = μ + σε, not μ, so the decoder learns to expect a jittered code and hedges. Decoding the mean at test time helps only a little.
  4. The downsampling factor. Detail finer than one latent cell has to be redrawn by the decoder from nothing. At 8 × downsampling a 512 × 512 image's 1-pixel strokes share a cell with 63 other pixels.

The trade-off you cannot escape. Blau and Michaeli proved that, at a given rate, the lowest possible distortion (pixel error) and the most realistic-looking output are different targets, and pushing one costs the other ({{The perception-distortion trade-off, 2018|https://arxiv.org/abs/1711.06077}}). A decoder that draws plausible fur where the code was unsure will score a worse PSNR than one that draws the average blur. So "sharper" and "lower pixel error" are not the same goal, and a tokenizer trained for generation should be judged on how realistic its reconstructions look, not on PSNR alone.

The fix, measured on the tiny tokenizer

The same 128-code VQ tokenizer (with dead-code restarts, as the Latent lab's vq_restart) trained three ways: the pixel loss only; plus a perceptual loss (LPIPS, the distance between the two images' features in a pretrained AlexNet, {{Zhang et al. 2018|https://arxiv.org/abs/1801.03924}}); plus a patch adversarial loss from step 2,500 (a small discriminator that labels every 8 × 8 region of the 32 × 32 image as real or reconstructed, hinge loss, weighted adaptively as in the LDM code). This is the VQGAN recipe at toy scale (section 7).

5. VQ-VAE training: the straight-through gradient and keeping the codebook alive

How it works, in brief (the Latent lab builds it step by step). The encoder outputs a vector ze at each latent position; the quantizer replaces it by the nearest of K codebook vectors e; the decoder sees e. Nearest-neighbour lookup has no gradient, so the decoder's gradient with respect to e is copied to ze unchanged, the straight-through estimator; a codebook loss ‖sg[ze] − e‖2 moves the chosen codes towards the encoder's outputs and a commitment loss β‖ze − sg[e]‖2 (β = 0.25) keeps the encoder near its codes ({{van den Oord et al. 2017|https://arxiv.org/abs/1711.00937}}, eq. 3).

The problem: dead codes. A code that is never the nearest to any encoder output receives no gradient from either loss, so it never moves and is never chosen: codebook collapse. With the usual initialisation (uniform in ±1/K, far smaller than the encoder's outputs) most codes die in the first few hundred steps. The fixes in use, each run here on the same tokenizer:

  • Dead-code restarts: re-seed unused codes from random encoder outputs of the current batch (Jukebox, {{Dhariwal et al. 2020, section 3.1|https://arxiv.org/abs/2005.00341}}). The Latent lab's vq_restart.
  • EMA codebook: no codebook loss; each code is set to a moving average of the encoder outputs assigned to it (decay 0.99), with Laplace smoothing of the counts (VQ-VAE appendix A.1). Faster and more stable updates, but a code that wins nothing still does not move.
  • Normalised codes: L2-normalise both ze and the codebook before the lookup, so distances become angles and every code lives on the same sphere as the data (ViT-VQGAN, {{Yu et al. 2021, section 3.2|https://arxiv.org/abs/2110.04627}}); usually combined with low-dimensional codes (8 to 32 numbers), the "factorized codes" of the same paper.
  • Data-dependent initialisation (k-means on the first training batch's encoder outputs, as in SoundStream, which also uses EMA codebooks and restarts: {{Zeghidour et al. 2021, section III-C|https://arxiv.org/abs/2107.03312}}) and the rotation trick for a better-than-copied gradient ({{Fifty et al. 2024|https://arxiv.org/abs/2410.06424}}): not run here.

Log codes used and perplexity every few hundred steps; a perplexity far below K means you are paying for a codebook you do not have. Read the library's loss too: diffusers' VectorQuantizer applies β to the wrong term unless legacy=False (the Latent lab, section 7).

6. FSQ and LFQ: quantizers with nothing to collapse

The idea. Codebook collapse happens because the codebook is learned. Remove it: make the code grid fixed and let the encoder learn to use it.

FSQ: finite scalar quantization

Project the encoder output to a few channels d (3 to 10), squash each into a bounded range with tanh, and round it to one of Li levels. The codebook is implicit, the product of the levels: [8, 5, 5, 5] gives 1,000 codes from 4 channels. No codebook loss, no commitment loss, gradients by straight-through rounding ({{Mentzer et al. 2023|https://arxiv.org/abs/2309.15505}}). The paper reports codebook usage "≈100% for most models, without relying on any auxiliary losses" and recommends Li ≥ 5 for every channel published.

LFQ: lookup-free quantization

The extreme case: log2 K channels, each quantized to its sign, ±1. The token is the binary number the signs spell, so 18 channels give 218 = 262,144 codes with no lookup at all. An entropy penalty, E[H(q(z))] − H[E(q(z))], makes each token confident and all tokens used (MAGVIT-v2, {{Yu et al. 2023, eq. 3 to 5|https://arxiv.org/abs/2310.05737}}; weight 0.1, commitment 0.25 in its appendix) published.

The FSQ bounding function, ported from the paper's appendix A.1 to PyTorch and used for every FSQ run here (src/quant/quantizers.py):

def bound(self, z):                     # paper appendix A.1, def bound
    eps = 1e-3
    half_l = (self.L - 1) * (1 - eps) / 2
    offset = torch.where(self.L % 2 == 1, 0.0, 0.5)   # even L needs an asymmetric range
    shift = torch.tan(offset / half_l)
    return torch.tanh(z + shift) * half_l - offset

q = round_ste(self.bound(z))            # integers; round_ste(x) = x + (round(x) - x).detach()
zq = q / (self.L // 2)                  # what the decoder sees, about [-1, 1]

The cost. FSQ and LFQ put fewer numbers into each token (3 to 18 channels against VQ's 8 to 256), so one token carries less, and the levels are fixed rather than fitted to the data. In return large vocabularies become usable: MAGVIT-v2 reports reconstruction and generation both improving as LFQ's vocabulary grows, "a property not observed in current VQ-VAE methods" published, and FSQ reports VQ "is actually worse for large codebooks" published.

When it matters, how to check. Choose FSQ or LFQ when you need a vocabulary of thousands to hundreds of thousands of codes, or when VQ's collapse keeps coming back. Check codes used and perplexity exactly as for VQ; a large vocabulary is also harder for the generator to model (section 8), so check generation, not only reconstruction.
