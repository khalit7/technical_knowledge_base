3. How many tokens is an image?

The problem. More image tokens let a model see finer detail (small text, a chart’s labels), but each one is a token the language model must attend over, in context and in time. A fixed low resolution (LLaVA-1.5’s one 336-pixel view) misses detail; full resolution at one token per 16-pixel patch would make a 2,048-pixel square 16,384 tokens derived: (2,048 / 16)². Every VLM picks a point between the two.

How SmolVLM does it. Its image processor (transformers v5.20.1, models/idefics3/image_processing_idefics3.py) does three things: it scales the image so its long side equals size.longest_edge (2,048 by default, written N × 512 below with N = 4), keeping the aspect ratio (lines 58–92); it rounds both sides up to whole 512-pixel tiles by resizing, not padding (resize_for_vision_encoder, lines 319–348); and it cuts the tiles and appends the whole image shrunk to 512 as a global view (split_images, lines 286–317). Each view becomes 64 tokens. The processor then writes one placeholder per token into the prompt, with a tag naming each tile’s row and column (processing_idefics3.py lines 216–243).

Three things the counting showed measured
  • Input resolution does not change the count. A 64 × 64 icon and a 3,000 × 3,000 photo both become 17 views and 1,088 image tokens: small images are upscaled to 2,048 first. Only the aspect ratio and the N setting matter.
  • Shapes are stretched to whole tiles. A 1920 × 1080 photo becomes 2,048 × 1,152 and then 2,048 × 1,536 (3 × 4 tiles): height stretched by a third.
  • N above 6 breaks the tile tags. The vocabulary has <row_1_col_1> to <row_6_col_6> as single learned tokens; <row_7_col_1> is split into 9 ordinary text pieces (<, row, _, 7, ...). At N = 8 a square image takes 4,538 prompt tokens, of which 4,160 are image tokens and 378 are markers.

    Where the vectors go. Inside the model the prompt is embedded token by token, and then every <image> position is overwritten, in order, by the projected image vectors:
    

    # transformers v5.20.1, models/idefics3/modeling_idefics3.py lines 557-559 (inputs_merger)
special_image_mask = special_image_mask.unsqueeze(-1).to(inputs_embeds.device)
image_hidden_states = image_hidden_states.to(inputs_embeds.device, inputs_embeds.dtype)
inputs_embeds = inputs_embeds.masked_scatter(special_image_mask, image_hidden_states)
    

    So the language model never sees the placeholder’s own embedding: only its position. If the number of placeholders and the number of image vectors disagree (a hand-written prompt, a processor and model from different versions), the scatter misplaces vectors or fails; always build the prompt with the model’s own processor.
    

    Image tokens are not words. measured The projected image vectors have a median length (L2 norm) of 101 (10th to 90th percentile 83 to 158); the language model’s own word embeddings have a median length of 3.5. The nearest vocabulary embedding to each of the 64 global-view image tokens has a median cosine similarity of 0.27, and the nearest “words” are meaningless: <|im_start|> for 32 of the 64, <|im_end|> for 12, then fragments such as amine. The language model has learned to read these vectors as a different kind of input; they are not disguised words.
    

    The tile tags (<row_1_col_1> and so on) are single learned tokens. The SmolVLM paper found that plain-text position markers “caused early training plateaus” and that “learned positional tokens outperform raw text tokens for compact VLMs” (section 3.1, Finding 5) published; the 9-piece <row_7_col_1> above is exactly the raw-text case.
