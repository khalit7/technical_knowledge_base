Long-context cost: every GLM attention design, from its config

Each GLM generation rebuilt attention to change one of two numbers: how much cache a request holds, and how much attention work each decoded token does. This tab computes both from the config.json files ({{GLM-4.5|@cfg45}}, {{GLM-5|@cfg5}}, {{GLM-5.3|@cfg53}}, {{GLM-5.3-Flash|@cfgfl}}) at any context length. Try: drag the context to 1M and watch the indexer term take over GLM-5's compute; switch IndexPool off to see how little of Flash's cache saving it supplies; add the active weights to see IndexShare's 2.9x appear.

Cache held by one request

Attention work per decoded token

cache per token = Σlayers (latent + indexer key / pool) × bytes
work per token = Σlayers [HIdI · L / pool + H · min(k, L) · (dscore + dvalue)]
latent
576 numbers (512 + 64 rotary) for GLM-5 to 5.3, 512 for Flash's NoPE layers; GLM-4.5 caches 2 × 8 × 128 = 2,048 per layer instead
indexer key
128 numbers in each layer that runs an indexer: all 78 in GLM-5 and 5.1, 21 in GLM-5.2 and 5.3, 11 in Flash, where IndexPool divides by 4
HIdI
32 indexer heads × 128 dimensions
H
attention heads (64; 96 in GLM-4.5)
k
2,048 entries read by sparse attention; full attention reads all L
dscore + dvalue
576 + 512 in MLA's decode form, 512 + 512 for Flash, 128 + 128 per head for GQA

Flash's 34 KDA layers add no growing cache; they hold 64 × 128 × 128 numbers each regardless of context and do about 3 × 128 × 128 multiply-adds per head per token (an estimate of the delta-rule update and read, labelled). Projections and experts are outside the attention terms unless "add active weights" is on.
