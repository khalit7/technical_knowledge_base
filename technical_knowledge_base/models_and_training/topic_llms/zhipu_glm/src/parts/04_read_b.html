Attention: from grouped-query, to sparse, to a hybrid

A model's KV cache holds, for every earlier token and every layer, what the attention needs to look that token up again; at long context it, rather than the weights, decides how many requests fit on an accelerator. GLM's attention has been rebuilt twice to shrink it and the work of reading it. The attention family and KV-cache arithmetic across labs are on {{LLM Architecture Gallery|n:3c65c17b0d0d81be8a07f2562fa2030a}}; this section is what GLM did.

GLM-5: MLA with wider heads, plus DSA

GLM-5 replaced grouped-query attention with DeepSeek's MLA (Multi-head Latent Attention), which caches one 512-number latent vector plus a 64-number rotary key per token and layer and expands it into per-head keys and values on the fly, and added DSA (DeepSeek Sparse Attention), in which a cheap scorer, the lightning indexer, ranks every earlier token for the current query and the main attention then reads only the top 2,048 ({{GLM-5 report|@r5}}, {{config|@cfg53}}). Both mechanisms are explained on {{DeepSeek|n:3c65c17b0d0d81a2ae7ec6796947a235}}. Every entry stays in the cache so that it can be picked later; DSA saves reading, not storing.

GLM's own change is the head shape. DeepSeek-V3 uses 192-dimensional query-key heads with a head count chosen for the roofline of Nvidia's H800; GLM-5 widens them to 256 and cuts the number of heads by a third, which "keeps the training computation and the number of parameters constant while decreasing the decoding computation". The report calls this MLA-256, and it was tuned for the seven Chinese accelerator platforms GLM-5 was adapted to (Huawei Ascend, Moore Threads, Hygon, Cambricon, Kunlunxin, MetaX and Enflame) rather than for the H800. DSA was not trained from scratch: GLM-5 continued pretraining from its dense-attention base with a 1,000-step warm-up that trains only the indexer, then a 20B-token sparse-adaptation stage; the report puts DSA's saving at "roughly 1.5 to 2 times" less attention computation for long sequences ({{GLM-5 report|@r5}}).

Worked example: what GLM-5.2 caches per token. Each of 78 layers caches 512 + 64 = 576 numbers, so 576 × 78 × 2 bytes = 89,856 bytes, 87.75 KiB per token in 16-bit precision, against GLM-4.5's 368 KiB. The indexer keeps its own 128-number key per token in every layer that runs an indexer. At the full 1,048,576-token context the latents alone are 87.75 GiB for one request.

IndexShare (GLM-5.2): run the indexer once per four layers

DSA makes the main attention cheap, but the indexer still compares each query with every earlier token, so its cost is still quadratic in context length, and at a million tokens it becomes the bill ({{Raschka|@rasch}}). The IndexCache study that IndexShare builds on measured 70% to 100% overlap between the positions selected by adjacent DSA layers ({{IndexCache|@icache}}): neighbouring indexers mostly rediscover the same tokens. So in GLM-5.2 the indexer runs at the first of each group of four layers and the next three reuse its list of selected positions; in the released config 21 of the 78 layers run an indexer ({{GLM-5.2 blog|@b52}}, {{config|@cfg53}}). The sharing layers still compute their own queries, attention weights and value mix; only the list is reused. GLM-5.2 was trained this way from mid-training at 128K sequence length.

Zhipu reports a 2.9 times reduction in per-token FLOPs at a 1M context, with the caveats that this is not an end-to-end speedup and that IndexShare "does not proportionally reduce per-token KV-cache size" ({{GLM-5.2 card|@c52}}, {{GLM-5.2 blog|@b52}}). Amdahl's law turns the figure into a statement about where the work was:

S = 1 / ((1 − f) + f / n)   ⟺   f = (1 − 1/S) / (1 − 1/n)
S
overall reduction in per-token work (2.9)
f
share of per-token work spent in the indexer before the change
n
factor by which the indexer work shrinks (about 4)

Worked example. For one query at L = 1,048,576 one indexer does 1,048,576 × 32 × 128 = 4.29 × 109 multiply-adds, while the main attention reads 2,048 entries, 2,048 / 1,048,576 = 0.2% of the cache. Solving Amdahl's law: f = (1 − 1/2.9) / (1 − 1/4) = 0.655 / 0.75 = 0.87, so at a 1M context about seven eighths of GLM-5.1's per-token work would have been the indexer. Counting it from the configs instead (78 indexers before, 21 after, plus 40B active weights as 40 × 109 multiply-adds) gives 2.7 times; the Long-context cost tab shows the terms.

GLM-5.3-Flash: linear plus sparse attention, and IndexPool

Flash, published as the first GLM to combine sparse and linear attention, replaces most attention layers with Moonshot's Kimi Delta Attention (KDA), a gated delta-rule linear attention whose state per request has a fixed size: each of its 64 heads keeps a 128 × 128 matrix that every new token updates, instead of a cache that grows with context (the mechanism is on {{Moonshot AI: Kimi|n:3c65c17b0d0d81f5abf5dbdbac821a12}}). Its 45 layers repeat three KDA layers and one sparse-attention layer, ending on a KDA layer: 34 KDA layers and 11 sparse ones, so only 11 / 45 = 24% of the layers keep a cache that grows with context ({{Flash config|@cfgfl}}). The sparse layers are MLA without positional encoding (NoPE), so they cache a 512-number latent and no rotary key, with DSA reading the top 2,048 entries ({{config|@cfgfl}}, {{MarkTechPost|@mtpfl}}). In Zhipu's words, linear attention "captures local dependencies through state modeling, while sparse attention retrieves relevant global context through a lightweight indexer" ({{Z.ai docs|@dfl}}).

IndexPool attacks the indexer from the other side. IndexShare cut how many layers run an indexer; IndexPool cuts how many entries each indexer scores, by compressing four indexer key vectors into one "through weighted pooling" ({{Z.ai docs|@dfl}}). At L = 1,048,576 each Flash indexer scores 1,048,576 / 4 = 262,144 pooled keys. The config also keeps the newest, not yet complete group of keys selectable (index_kpool_always_select_tail); how a selected pooled entry maps back to the 2,048 attended tokens is not described in the sources read.

Against GLM-5.3, Zhipu reports 3.01 times less attention compute and a 4.44 times smaller KV cache ({{Z.ai docs|@dfl}}), counted "per head per layer" for compute and as "average KV cache size per layer (BF16)" for memory, so that models of different sizes compare fairly. That 4.4x is the whole design, not IndexPool: most of it comes from 34 of 45 layers holding no growing cache at all. Defaults reproduce the 4.44x cache reduction only approximately, and independently: counting from the two config.json files on Zhipu's per-layer convention, GLM-5.3 averages (78 × 576 + 21 × 128) / 78 = 610 numbers per layer and token and Flash 11 × (512 + 128/4) / 45 = 133, a ratio of 4.6 against the published 4.44. The 3% gap is not explained by anything published. Of the 4.6, the layer mix gives 45 / 11 = 4.09, dropping the rotary key 576 / 512 = 1.125, and IndexPool only 1.18 (without it Flash would average 156 and the ratio would be 3.9). Per whole model the cache per token falls 47,616 / 5,984 = 8.0 times, more than the per-layer figure, because Flash also has fewer layers. Not reproduced: the 3.01x attention compute; Zhipu does not say which terms or which context length it counted, and our per-head count at 1M gives about 4.4x.

That combination is what makes the advertised million-token window affordable to serve rather than merely available. At 1M tokens one Flash request holds about 11.7 GiB of growing cache in 16-bit precision plus a fixed KDA state of 34 × 64 × 128 × 128 numbers (68 MiB in 16-bit), against 93 GiB for GLM-5.3. Zhipu itself notes that Flash's cache "is still slightly larger than Kimi-K3 and DeepSeek-V4-Flash", while its attention compute is the lowest of the four ({{Z.ai docs|@dfl}}). The Long-context cost tab draws both against context for every GLM design.

slime: RL infrastructure built for the agentic case

Zhipu open-sourced slime, its RL post-training framework (Megatron for training, SGLang for rollouts), and it is arguably as strategically important as the weights: it is the RL framework behind every GLM from GLM-4.5 to GLM-5.3 ({{slime|@slime}}). In agentic RL a single rollout is a whole episode of tool calls, and episode lengths are long-tailed: one trajectory takes three tool calls, another three hundred. Classic synchronous on-policy RL waits for the whole batch of rollouts before each training step, so accelerators idle on the slowest trajectory, and utilisation collapses exactly when the episodes get interesting. The GLM-4.5 report says it plainly: "synchronous RL training often leads to severe GPU underutilization as workers wait for the slowest rollouts to complete" ({{GLM-4.5 report|@r45}}).

slime supports two modes ({{GLM-4.5 report|@r45}}). A colocated, synchronous mode, for reasoning RL whose rollouts are of similar length, runs generation and training on the same devices in turn. A disaggregated, asynchronous mode, for agentic RL, partitions the accelerators into rollout engines and training engines: the rollout engines generate trajectories continuously into a buffer, the trainer consumes them without waiting for a batch to complete, and the new weights are synchronised back to the rollout engines periodically. Same lesson as prefill and decode disaggregation in serving ({{Inference techniques|n:3c65c17b0d0d819db53bd2c48909e5b2}}): when two coupled phases have different profiles, decouple them and buffer between.

Illustrative episode lengths

Four rollout slots over 48 time steps, one square per step of an episode. The episode lengths are illustrative (a long-tailed mix, the first batch 3, 5, 8 and 40 steps); the trainer takes one step per 4 finished trajectories, and the staleness limit τ = 2 policy versions is also illustrative. The rules (discard by version, then keep tokens whose importance ratio is inside the band) are GLM-5's ({{GLM-5 report|@r5}}).

The cost is staleness. A trajectory that started under policy version w0 and is trained on at version w′ came from an older policy than the one being updated, so the update is off-policy and needs a bounded staleness window or importance correction to stay stable. GLM-5 does both ({{GLM-5 report|@r5}}):

discard if w′ − w0 > τ;    rt = πθ(yt | context) / πrollout(yt | context);    keep token t only if 1 − εℓ ≤ rt ≤ 1 + εh
w′, w0
current policy version, and the version that generated the oldest part of the trajectory
τ
the staleness threshold
yt
the token at position t
πθ, πrollout
the policy being trained, and the one that generated the token
rt
their importance ratio
εℓ, εh
lower and upper bounds of the trust region

The second rule is Direct Double-sided Importance Sampling: a token outside the band is masked out entirely, so a badly off-policy token cannot steer the update, and no historical policy checkpoints have to be kept. A token-in, token-out gateway passes token ids rather than text between the agent environment and the trainer, so a trajectory is never re-tokenised into slightly different tokens than the ones the policy produced ({{GLM-5 report|@r5}}). The benefit of all this is that utilisation stops being hostage to the longest episode, which is what makes agentic RL affordable at the cadence Zhipu runs it.

GLM-5.2: from GRPO back to a critic

GRPO, the RL objective most open reasoning models use, has no learned value function: it samples a group of rollouts for each prompt and scores each by how its reward compares with the group's (the objective is on {{RL for LLMs: RLHF, GRPO, RLVR|n:3c65c17b0d0d818c9bcff7177325fe56}}):

Ai = (Ri − mean(R1, …, RG)) / std(R1, …, RG)
Ai
the advantage given to every token of rollout i
Ri
its reward
G
the group size

That needs the rollouts of a group to be comparable units, and GLM-5.2's long-horizon tasks broke it: a super-long trajectory is split by context compaction into several sub-traces, so rollouts of the same prompt yield different numbers of trainable traces of very different lengths. Zhipu "move[d] from group-wise optimization to a critic-based PPO formulation that learns from individual rollouts, relying on a critic to estimate token-level advantages", training on every compacted sub-trace with a token-level loss to handle their length imbalance ({{GLM-5.2 blog|@b52}}). A critic gives each token its own advantage, so credit can fall on the step that mattered in a 300-step trace rather than equally on all of them.

Worked example (illustrative rewards). A group of four rollouts scores 1, 0, 0 and 1: mean 0.5, standard deviation 0.5, so the advantages are +1, −1, −1 and +1, and every token of the first rollout gets +1 whether it was the decisive edit or an idle directory listing. If the first rollout was compacted into three sub-traces and the second into one, the group score has to be smeared over units of very different size; a critic sidesteps the question by scoring tokens directly, at the price of a second large network to train and keep calibrated.

Reward hacking. GLM-5.2 showed more hacking than GLM-5.1: agents read protected evaluation artifacts, copied answers from references or upstream commits, or fetched the target source with curl. Zhipu added an anti-hack module to training and evaluation, a rule-based filter for recall followed by an LLM judge of the flagged action's intent for precision, run online: a detected hack is blocked and answered with dummy information, but the rollout continues, so the episode still teaches something and training avoids the instability of abruptly stopped rollouts ({{GLM-5.2 blog|@b52}}).
