What it is and why it matters

Almost every open model released since 2023 is the same machine as GPT-2: a stack of identical decoder blocks, each doing attention (every token looks back at earlier tokens) and then a feed-forward network (FFN, a per-token multilayer perceptron), with normalisation and a residual connection around each, and a positional scheme telling attention where each token sits. What differs between models is a small number of choices inside that block, and nearly all of them are about memory and compute efficiency rather than modelling power.

This page owns those generic mechanisms for the llms topic: the attention variants (MHA, MQA, GQA, MLA, sliding window, trained sparse, linear and hybrid), the MoE feed-forward in brief, normalisation placement, positional encoding and stack shape, each with what it buys and what it costs. The lab pages keep only what their own variant does differently, and carry their own animations of it: DeepSeek (MLA, DSA, V4.1-Flash), Qwen and Zhipu (hybrids), Moonshot AI: Kimi (KDA) and Mistral AI (sliding window).

The single number that ties the choices together is the KV cache per token: the bytes a model must keep in accelerator memory for every token of context it holds. It is set by the attention design, not by the parameter count, so two models of the same size can differ on it by an order of magnitude, and it decides whether long context and high concurrency are affordable. Learn to compute it and read it off a card, and most of what changed in a new model follows.

Terms

Decoder block
Attention, then an FFN, each wrapped as x ← x + F(Norm(x)) in the pre-norm layout most models use. A model is L of these stacked.
Residual stream
The vector x each token carries through the stack; every sublayer reads it and adds its output back.
Query, key, value
Per-token vectors made by learned projections of the residual stream. A token's query is compared with earlier tokens' keys to decide how much of each of their values to take.
Head
One independent attention computation of dimension dh (the head dimension, typically 64 to 256). A layer runs H query heads in parallel.
KV heads
The number of distinct key and value projections a layer computes, Hkv: equal to H in classic multi-head attention, smaller in the variants below.
KV cache
During generation, the keys and values of every earlier token, stored so they are not recomputed at each step. It grows by one entry per layer for every token of context.
Prefill and decode
Prefill processes the whole prompt in parallel and is compute-bound; decode produces one token at a time and must read all the weights and the whole KV cache for each token, so it is memory-bandwidth-bound. A smaller cache means faster decode, not only more room.
Dense and MoE
A dense model runs every FFN parameter for every token; a mixture-of-experts (MoE) model has many expert FFNs and a router that activates a few per token, so total parameters (memory) and active parameters (compute per token) differ.

Attention and the KV cache

One attention head computes, for a sequence of T tokens:

Attention(Q, K, V) = softmax( Q K⊤ / √dh + M ) V
Q, K, V
∈ ℝT × dh: the query, key and value vector of every token, one per row, for this head
Q K⊤
the T × T matrix of dot products between every query and every key (the attention logits)
√dh
keeps the logits' spread roughly constant as the head dimension grows
M
the mask: 0 where a query may look, −∞ where it may not (for a causal decoder, every later position)
softmax
runs along each row, turning that query's logits into weights that sum to 1, which then average the rows of V

A layer runs H such heads and concatenates their outputs. At decode time only the newest token's query is new, but it needs the keys and values of all earlier tokens, which is why they are cached. The cache for one token, and the memory a deployment must hold, are:

KV bytes per token = 2 × L × Hkv × dh × b
KV memory = KV bytes per token × Tctx × Nconcurrent
2
counts keys and values
L
the number of layers that keep a cache (all of them in a plain transformer)
Hkv
KV heads per layer, which is where the attention variant enters
dh
the head dimension
b
bytes per stored element: 2 for BF16, 1 for FP8, 0.5 for FP4
Tctx, Nconcurrent
the context held per request, and the number of requests resident at once

Worked example: Llama 3.1 70B. Its configuration has L = 80 layers, 64 query heads, Hkv = 8 KV heads and a hidden size of 8,192, so dh = 8,192 / 64 = 128. In BF16: per token 2 × 80 × 8 × 128 × 2 = 327,680 bytes = 320 KiB; one request holding a 131,072-token (128K) context 327,680 × 131,072 = 42,949,672,960 bytes = 40 GiB; eight such requests, 320 GiB of KV cache, more than twice the roughly 140 GB the 70 billion BF16 weights occupy (70 × 109 × 2 bytes). Had the same model used full multi-head attention (Hkv = 64), every figure would be 8 times larger: 2,560 KiB per token and 320 GiB for a single 128K request. That factor is why the attention variant, not the parameter count, decides whether long context is affordable.

Try: the defaults are Llama 3.1 70B and reproduce 320 KiB, 40 GiB and 320 GiB. Set KV heads to 64 to see the MHA counterfactual, or FP8 to halve everything.

The gallery's headline does not credit sliding windows

The gallery quotes this per-token figure in BF16 for every model, using the same formula (with the MLA and linear-layer variants below), per its KV-cache calculation notes: "the logical cache added by one token for one sequence", batch 1, 2 bytes per element, a logical estimate separate from measured serving memory (allocator padding, buffers and kernel layouts usually add more). A windowed layer is counted at full per-token cost: the window only limits how long entries are kept. So for a model with many windowed layers the long-context memory is much lower than the headline suggests (worked through under sliding windows). The same notes count only layers that append to a growing cache: DeltaNet, Lightning Attention, Mamba-2 and xLSTM layers add 0 B per token and keep a fixed-size state instead.

MHA, MQA and GQA: how many query heads share a KV head

Classic multi-head attention (MHA) gives every query head its own key and value head, Hkv = H. Multi-query attention (MQA, Shazeer, 2019) goes to the other extreme, one shared KV head for all queries, Hkv = 1. Grouped-query attention (GQA, Ainslie et al., 2023) sits between: query heads are divided into Hkv groups, and every head in a group reads the same keys and values. Query head i (counting from 0) uses KV head

g(i) = ⌊ i / (H / Hkv) ⌋
H / Hkv
the group size (query heads per KV head)
⌊ · ⌋
rounds down

Each layer stores 2 Hkv dh elements per token instead of 2 H dh.

  • What it buys. The cache is sized by KV heads, so a group size of 8 cuts the cache and the per-token memory traffic by 8, and because decode is memory-bandwidth-bound that is close to a linear speedup at long context.
  • What it costs. Expressivity: query heads in a group can no longer attend along independent key subspaces. The loss is small, and it can be recovered without pretraining from scratch: the GQA paper converts existing MHA checkpoints by continuing training ("uptraining") for about 5% of the original pre-training compute, and reports quality close to MHA at a speed comparable to MQA. MQA saves more and degrades more.
  • Worked example. Llama 3.1 8B has 32 layers, 32 query heads, 8 KV heads and dh = 128, so groups of 4 query heads share a KV head and query heads 0 to 3 read KV head 0 (step 4 of the animation, GQA). Per token: 2 × 32 × 8 × 128 × 2 = 131,072 bytes = 128 KiB. OLMo 2 7B, which keeps full MHA over 32 layers, needs 512 KiB per token (the gallery's figure, reproduced from its config), four times as much for a model of similar size.

GQA was the 2023 to 2024 default and remains the baseline in Llama 3 and 4, Qwen3, Gemma and gpt-oss: of the 89 models rebuilt on the Compare tab, 46 use GQA in all their attention layers, 19 use MLA (some with a sparse indexer on top), 24 contain linear or recurrent layers (xLSTM 7B is recurrent throughout), and only 4 keep full MHA (GPT-2 XL, OLMo 2 7B, OLMo 3 7B and Ouro-Thinking); Gemma 3 270M is the lone MQA model, with one KV head.

MLA (multi-head latent attention): cache a compressed latent instead of keys and values

Introduced in DeepSeek-V2 (arXiv 2405.04434) and now used well beyond DeepSeek (V2, V3, R1, V3.2, Kimi K2 to K2.6, Mistral Large 3 and Small 4, GLM-5, Sarvam 105B, per their configs). Instead of caching keys and values per head, project them jointly into a single low-rank latent vector, cache only that, and up-project back to per-head keys and values inside the attention call:

ct = WDKV ht,   kCt,i = WUKi ct,   vt,i = WUVi ct
kRt = RoPE(WKR ht),   kt,i = [ kCt,i ; kRt ]
ht
token t's input to the attention layer (the normalised residual stream)
WDKV
down-projects it to the latent ct of dimension dc, much smaller than 2H dh
WUKi, WUVi
up-project the latent to head i's content key and value
kRt
a small decoupled RoPE key of dimension dR, shared by all heads, carrying the position
[ · ; · ]
concatenation, so head i's key is its content key plus the shared positional key

Only ct and kRt are cached: dc + dR elements per layer per token, regardless of the number of heads. At inference the up-projections need not be materialised: WUKi can be multiplied into the query projection and WUVi into the output projection, so attention runs directly against the cached latent, and every query head reads the same entry (the MLA step 4 of the animation; the DeepSeek page animates the absorption itself).

  • Why the separate RoPE key. RoPE multiplies each key by a position-dependent rotation. Applied to the latent, the rotation would sit between WUKi and the query and could no longer be folded into the query projection, since it changes with position; rotating before compression does not survive the up-projection either. So position travels in the small extra key, and the latent stays position-free.
  • Worked example: DeepSeek V3. 61 layers, 128 heads of dh = 128, latent dc = 512, decoupled key dR = 64 (config; DeepSeek-V3 Technical Report). Per token in BF16: 61 × (512 + 64) × 2 = 70,272 bytes = 68.6 KiB. Full MHA at the same shape would store 2 × 128 × 128 = 32,768 elements per layer, 61 × 32,768 × 2 = 3,997,696 bytes = 3,904 KiB per token: MLA is 57 times smaller. Against GQA it still wins: 576 elements per layer is what GQA would store with only 2.25 KV heads of dimension 128.
  • What it buys. A cache smaller than aggressive GQA, and DeepSeek's ablations report quality at or slightly above MHA, the unusual part: most cache reductions cost quality.
  • What it costs. Compute and complexity. Every attention call pays extra projections, trading arithmetic (cheap and parallel) for memory traffic (scarce during decode), the right trade on current hardware. The decoupled RoPE path makes the kernels fussier than GQA's, which is why MLA support lagged in serving stacks.

Local/global mixing (sliding-window layers)

Most layers attend only within a fixed window of the W most recent tokens, with a full-attention ("global") layer inserted periodically. Gemma 3 uses 5 local layers per global layer with a 1,024-token window (Gemma 3 report); gpt-oss alternates sliding and full layers one to one with a 128-token window (config); 3:1 appears in OLMo 3 (window 4,096), Arcee Trinity Large and, as chunked attention of 8,192 tokens, Llama 4 Maverick (configs on the Compare tab). A windowed layer needs cache only for the window, so the memory one request holds at context length T is:

KV memory per request = ( Lglobal × T + Llocal × min(T, W) ) × bytes per layer per token
Lglobal, Llocal
count the full and windowed layers
bytes per layer per token
2 Hkv dh b

Past T = W the windowed term stops growing, so total cache grows only through the global layers.

  • What it buys and costs. Quality loss is negligible on most workloads because the global layers still route information across the whole sequence. The cost is that information must travel through those global layers, so the ratio is a real hyperparameter: retrieval-style long-context tasks, where an exact token far back must be recovered, are the workload most sensitive to it.

Trained sparse attention

A lightweight learned indexer scores candidate keys, or blocks of keys, per query, and full attention is computed only over the selected top k, so the logits cost O(k dh) per query instead of O(T dh), plus the indexer's own cheaper pass over all T. Because full attention's scores grow with T2 over a sequence, going from a 128K to a 1M window multiplies that part of the work by 82 = 64, and trained sparse attention is what made 1M-token contexts economical in 2026: DeepSeek V3.2's DSA, V4's compressed CSA and HCA (which drop the KV cache to about 2% of vanilla), MiniMax M3's MSA, and Qwen's QSA, which selects at micro-block rather than individual-token granularity because block-level gathers are far friendlier to memory hardware than scattered token-level ones (each lab page carries its variant and sources: DeepSeek, MiniMax, Qwen).

Selection by itself cuts arithmetic, not storage: every key must stay available for the indexer to choose from, so the cache shrinks only when it is also compressed, as in V4. The gallery's notes make the same point for a GQA-based design: top-2,048 selection "limits attention work without capping the stored history", and the indexer keys are an extra cache of their own (KV-cache notes). It costs: the indexer is itself trained and runs on every query, selection is a hard decision that can miss the one token that mattered, and it has to be trained in rather than bolted on.

Linear and hybrid attention: Gated DeltaNet, KDA and Mamba-2

Replace softmax attention in most layers with a recurrent update to a fixed-size state, so per-token cost is constant and no KV cache grows with context. In its simplest form (linear attention) each head keeps a matrix state and updates it per token:

St = St−1 + vt kt⊤,   ot = St qt
St
∈ ℝdv × dk, the state after token t: dv × dk entries whatever the context length
kt, vt, qt
that token's key, value and query
ot
the head's output

Plain accumulation never forgets, so modern variants add a decay and an error-correcting write. Gated DeltaNet (Yang et al., 2024) uses

St = αt St−1 ( I − βt ktkt⊤ ) + βt vtkt⊤
αt
∈ (0, 1), a learned per-token decay (the gate), one scalar per head
βt
∈ (0, 1), a learned write strength
I
the identity; the bracket first erases what the state stores under key kt, then vt is written there (the delta rule)

Kimi Delta Attention (KDA), the layer of Kimi Linear (arXiv 2510.26692), "extends Gated DeltaNet with a finer-grained gating mechanism": the scalar head-wise decay αt becomes a diagonal matrix Diag(αt), one forgetting rate per key channel ("akin to Gated Linear Attention"). Written in this page's orientation,

St = St−1 Diag(αt) ( I − βt ktkt⊤ ) + βt vtkt⊤
αt
∈ (0, 1)dk, a vector of decays, so each column of the state fades at its own rate (the KDA step 3 of the animation shows the columns fading unevenly)

The paper writes the transpose, St = (I − βtktkt⊤) Diag(αt) St−1 + βtktvt⊤ with S ∈ ℝdk × dv; the two are the same update.

Hybrids interleave periodic full-attention layers to restore exact recall: roughly 1 in 4, the 3:1 ratio of Kimi Linear and Qwen3-Next. Kimi Linear's ablation picked 3:1 over 0:1, 1:1, 7:1 and 15:1 (validation perplexity 5.65 against 5.77, 5.66, 5.70 and 5.82), and the paper reports the hybrid beating full MLA under an identical recipe while "reducing KV cache usage by up to 75%" (3 of every 4 layers keep none, so the 75% follows by construction) "and achieving up to 6× decoding throughput for a 1M context"; its MLA layers also drop RoPE altogether (NoPE). Qwen3-Next's Gated DeltaNet, Moonshot's KDA, and Mamba-2 hybrids such as NVIDIA's Nemotron 3 and IBM Granite 4 all take this shape, pushing KV cache per token from hundreds of KiB down to tens of KiB or less. Mamba is the state-space formulation underneath: a selective recurrence whose input-dependent parameters play the role of αt and βt here.

  • Worked example: Qwen3-Next 80B-A3B. 48 layers, of which 36 are Gated DeltaNet and 12 are full (gated) attention with 2 KV heads of dh = 256 (config). Only the 12 full layers grow a cache: 12 × 2 × 2 × 256 × 2 = 24,576 bytes = 24 KiB per token (the gallery's figure), 3 GiB at 128K. The fixed state is 32 value heads × 128 × 128 = 524,288 numbers per DeltaNet layer, 36 MiB over 36 layers at 2 bytes (72 MiB in the float32 many kernels keep it in): the same as the growing cache at 1,536 tokens, so beyond a few thousand tokens the state is noise. All 48 layers as full attention would need 96 KiB per token.
  • Worked example: Kimi Linear 48B-A3B. 27 layers: 20 KDA and 7 MLA (config). Cache: 7 × (512 + 64) × 2 = 8,064 bytes = 7.9 KiB per token; state 20 layers × 32 heads × 128 × 128 = 20 MiB at 2 bytes.
  • What it costs. The cost is inherent to the fixed-size state: it is a lossy summary, so anything not written into it is unrecoverable, and pure linear models are measurably worse at exact retrieval. The hybrid exists because the full-attention layers buy that capability back, and the mixing ratio is the dial between memory footprint and recall fidelity.

2. MoE configuration, in brief

Each block's feed-forward network becomes many expert FFNs plus a router that activates a few per token, decoupling capacity from per-token compute. The trend runs from few big experts (Mixtral 8x7B with top-2 of 8, Grok 2 with 8) to many small ones at high sparsity, usually with a shared always-on expert: DeepSeek V3 runs 256 routed experts with 8 active plus 1 shared, Kimi K2 384, K3 896 with 16 active (and 2 shared, per its config), while Qwen3 uses 128 with no shared expert (Qwen reinstated one from Qwen3-Next on: 512 experts, 10 routed plus 1 shared). Several models keep the first blocks dense (V3, GLM-4.5), because early-layer representations are barely differentiated and routing on them is near-random and destabilising. The expert counts of every model are in the FFN strip on the Compare tab, read from config.json.

The MoE choice and the attention choice are independent: MoE sets the weight memory and the compute per token, attention sets the KV cache, and a card has to be read for both. Topic: llms (Deeper: inside an MoE) owns the mechanism: why fine-grained sparsity wins and what it costs, top-k routing and its gating formula, load balancing (auxiliary losses against DeepSeek's bias-based aux-loss-free scheme), capacity factors and dropped tokens, expert parallelism, and what breaks at inference.

Multi-token prediction (MTP) heads are increasingly standard alongside this: extra output heads trained to predict the token after next, and the one after that. In training they densify the learning signal per position; at inference they act as a built-in draft model for speculative decoding, so the speedup arrives without a separate small model to maintain. The cost is a modest number of extra parameters and a more involved loss.

3. Normalisation

RMSNorm is universal. It rescales by the root mean square of the activations and drops LayerNorm's mean subtraction and bias, which removes one reduction and a set of parameters at no measured quality cost:

RMSNorm(x) = x / √( (1/d) Σj xj2 + ε ) ⊙ g
LayerNorm(x) = (x − μ) / √(σ2 + ε) ⊙ g + b
x
∈ ℝd, one token's activation vector with components xj
μ, σ2
the mean and variance of its components
ε
a small constant for numerical safety (Llama 3.1 uses 10−5, config)
g, b, ⊙
a learned per-dimension gain, LayerNorm's learned bias, and elementwise multiplication

Try: the default vector (1, 2, 3, 4) reproduces the worked example. Add a constant to every entry: LayerNorm's output does not move, RMSNorm's does, because RMSNorm keeps the mean the model put there.

Input x (gain 1, ε ignored)
Where the norm sits around a sublayer F

Worked example (gain 1, ε ignored). For x = (1, 2, 3, 4): the mean square is (1 + 4 + 9 + 16)/4 = 7.5, the RMS is √7.5 = 2.739, and RMSNorm gives (0.365, 0.730, 1.095, 1.461), the same direction rescaled. LayerNorm first subtracts the mean 2.5, divides by the standard deviation √1.25 = 1.118, and gives (−1.342, −0.447, 0.447, 1.342), centred on zero. RMSNorm costs one reduction instead of two.

The interesting differences are placement and extras. Writing F for a sublayer (attention or FFN):

  • Pre-norm, x + F(Norm(x)), is the default. It keeps a clean unnormalised identity path down the residual stream, which is what makes deep models trainable without learning-rate warmup tricks. Its known cost is that residual-stream magnitudes grow with depth. The original Transformer's post-norm, Norm(x + F(x)) (Attention Is All You Need), normalises the stream itself and is harder to train deep.
  • Post-norm variants. OLMo 2 (2 OLMo 2 Furious) normalises each sublayer's output before it is added back, x + Norm(F(x)), which damps what each block injects and is reported to improve loss stability. Gemma 3 normalises both before and after each block, x + Norm(F(Norm(x))), taking the stability of both placements for an extra norm per sublayer, negligible next to the matmuls.
  • QK-norm. RMSNorm on the query and key vectors before the attention dot product (in most implementations before RoPE). This bounds attention-logit magnitude, which otherwise grows steadily during training and produces the classic bf16 attention overflow and loss spike. With unit gain an RMS-normalised vector of dimension dh has length √dh, so the scaled logit q · k / √dh is at most √dh, about 11.3 for dh = 128; only the learned gains can raise it. It spread from OLMo 2 and Gemma to most 2025-and-later models and is close to free insurance. MiniMax M2 applies it per layer rather than per head: its config sets qk_norm_type: per_layer and the gallery lists "per-layer QK-Norm", one RMSNorm over all heads' queries (and keys) together. Cost: two extra normalisations per attention layer.

4. Positional encoding

Attention on its own is order-blind: permute the keys and values and each query's output is unchanged. RoPE (rotary position embedding, from RoFormer) is near-universal. It splits each query and key into dh/2 pairs of dimensions and rotates pair i of a token at position m by the angle m θi:

( q′2i, q′2i+1 ) = ( q2i cos mθi − q2i+1 sin mθi,  q2i sin mθi + q2i+1 cos mθi )
θi = base−2i/dh,   ⟨ Rmq, Rnk ⟩ = ⟨ q, Rn−mk ⟩
q2i, q2i+1
the two components of pair i (for i = 0, …, dh/2 − 1) and q′ the rotated ones; keys are rotated the same way by their own position n
θi
pair i's frequency in radians per token, with base classically 10,000 and 500,000 in Llama 3
Rm
the whole block-diagonal rotation for position m; the identity says the query-key dot product depends only on the offset n − m, because rotations compose and a rotation's transpose is its inverse

So RoPE injects absolute position in form but gives attention scores that depend on relative distance, with no parameters. Low-index pairs rotate fast and resolve short-range order; high-index pairs rotate slowly and encode long-range position. With dh = 128 and base 500,000, pair 0 turns 1 radian per token (a full turn every 6.3 tokens) while pair 63 turns 2.46 × 10−6 radians per token (a full turn every 2.56 million tokens).

Worked example (one pair, an illustrative θ = 0.5 radians per token). Take q = k = (1, 0). At m = 3 and n = 5 the query is rotated by 1.5 radians to (0.0707, 0.9975) and the key by 2.5 radians to (−0.8011, 0.5985); their dot product is 0.0707 × (−0.8011) + 0.9975 × 0.5985 = 0.5403 = cos(1.0). Move both tokens to m = 10, n = 12: the angles become 5 and 6 radians, the gap is still 1 radian, and the dot product is again 0.5403.

Everything below is about a model trained at one context length having to work at another. Positional Encodings owns the context-extension methods in detail (position interpolation, NTK-aware base scaling, YaRN, LongRoPE) and the older absolute and relative schemes; the summary here is what a model card's positional line means.

  • Base and interpolation scaling (YaRN and relatives). Raising RoPE's frequency base, or interpolating position indices, stretches the rotations so a longer context falls inside the range of angles the model saw in training. YaRN (Peng et al., 2023) does this per frequency band: for pair i it counts how many full turns r = Lorig / λi fit in the original context (λi = 2π / θi), leaves pairs with r > β alone, divides the frequency of pairs with r < α by the scale factor s, and ramps linearly between (the paper suggests α = 1, β = 32 for Llama), plus an attention temperature √(1/t) = 0.1 ln s + 1. It buys context extension with a short continued-training phase; blunt uniform interpolation costs short-range precision, the failure mode YaRN was designed around. gpt-oss ships YaRN with a scaling factor of 32 on a base of 150,000 for its 131,072-token context (config: original 4,096, beta_fast 32, beta_slow 1).

Try: each bar is one RoPE pair; its height is how many full turns it makes inside the original training context (log scale). The default is gpt-oss (64-dimensional heads, base 150,000, 4,096 original, factor 32) and gives 9 pairs kept, 9 on the ramp and 14 fully interpolated, with a temperature factor of 1.347. Switch to Llama 3's base to see more pairs fall below one turn.

  • Partial RoPE. Rotate only a fraction of each head's dimensions and leave the rest position-free, so those dimensions match on content alone. This empirically extrapolates better beyond the trained length, at the cost of some positional resolution. In the configs: Qwen3-Next and its successors rotate 25% (partial_rotary_factor 0.25), MiniMax M2 64 of 128 dimensions, GLM-4.5 half. MLA's decoupled key is a structural relative: position lives in 64 dimensions, content in the rest.
  • NoPE on a subset of layers. No positional encoding at all in some layers. A causal decoder can still infer ordering from the attention mask, and layers with no positional bias extrapolate past the training length far more gracefully, since no rotation runs off the end of its trained range. Pure NoPE is weaker on short-range ordering, so it is mixed: SmolLM3 makes every fourth layer NoPE (9 of 36), Kimi Linear and Kimi K3 drop RoPE from their full-attention layers, and several 2026 models interleave RoPE and NoPE layers (Muse Glimmer, Solar Open 2).
  • iRoPE (Llama 4). Interleaves local RoPE layers (chunked attention, 8,192 tokens) with global layers that carry no positional encoding, 36 and 12 in Maverick, plus inference-time attention temperature scaling, aimed squarely at length generalisation rather than at cache size.
  • Different bases per layer type. Gemma 3 keeps base 10,000 on its local layers and raises it to 1,000,000 on its global layers, since only the global layers ever see long distances; Gemma 4, MiMo and Laguna do the same.

The position strip on the Compare tab shows, layer by layer, which of these each model uses.

5. Stack shape: depth reuse, and the encoder-decoder return

Two September 2026 releases changed something the four sections above quietly assume, that a model is one causal decoder stack executed once per token.

  • Recurrent depth (looped transformers). Rather than adding layers, reuse them: activations are looped back through the same blocks, so serial depth per token decouples from parameter count. GPT-6 Astra is assumed to work this way (unconfirmed: OpenAI has not published its architecture), and the Recurrent Looped Transformer specification is the first published account of the family, pairing a causal encoder that builds a global KV memory with a decoder carrying its full state, final output and layerwise sliding-window cache included, across the prompt and response boundary with no reset, for unbounded temporal depth at fixed per-token compute. It buys compute without parameter memory, which makes the model cheaper to host. It costs recurrent state that the serving stack must carry between requests, and shorter visible reasoning traces, a real loss to chain-of-thought monitorability. The specification ships with no trained weights, no efficiency measurements and no quality results, so this is a shape to recognise on a card rather than a recipe to copy (Topic: llms (Deeper: test-time compute) places it among the ways of spending test-time compute). Looping already shows up in open configs: Ouro-Thinking 2.6B runs 4 passes over 48 layers, each keeping its own cache, so its 384 KiB per pass becomes 1.5 MiB per token (KV-cache notes).
  • Encoder-decoder at frontier scale. In an encoder-decoder, an encoder reads the input once with its own layers and the decoder generates while attending to the encoder's output through cross-attention, instead of one causal stack doing both. DeepSeek V4.1-Flash is 552B split into a 20-layer causal encoder and a 20-layer decoder, activating 8B during prefill and 16B during decode. It departs from the classic design in one respect: it has no cross-attention; the decoder's keys and values are projected from the encoder's layer-20 state instead (zartbot), detailed on DeepSeek. The argument is not T5's quality one (T5 measured encoder-decoders ahead at matched compute, and the field went decoder-only regardless): encoding the prompt once into a shared representation, combined with cross-layer sparse attention with index reuse, hierarchical retrieval and FP4 cache storage, gets the KV cache to 890 bytes per token, a quarter of V4-Flash's HBM footprint and an eighth of its SSD footprint. At that rate a 131,072-token context holds about 111 MiB, against 40 GiB for Llama 3.1 70B above. The gallery's own BF16 count for the growing global cache is (3/2 + 1) × (512 + 128) × 2 = 3,200 bytes = 3.125 KiB per token; the 890 bytes uses FP4 main KV and indexer keys with quantisation scales (KV-cache notes). T5Gemma is the other current encoder-decoder line, at small scale and built by adapting decoder checkpoints rather than pretraining (Encoder-Decoder Gemma and T5Gemma 2). Note what this does to rule 1 below.

How to read a new model card in 30 seconds

  1. Total versus active parameters. The ratio is the sparsity; the total is the memory floor you must provision, the active count sets latency and price per token. They predict different things and are routinely conflated, and the active count is no longer guaranteed to be a single number: an encoder-decoder can activate one figure during prefill and another during decode.
  2. Attention type and layer mix. Quadratic, hybrid or trained-sparse, and in what proportion. This is how cost scales with context, which matters more than the headline context number.
  3. KV cache per token, multiplied by target context and concurrency. "Does long context actually fit", answered in gigabytes. Credit the sliding windows yourself: the headline figure counts windowed layers at full cost (the Cache at context tab does it for you).
  4. Experts: routed, active, shared. Determines routing style, how much expert parallelism you need to make per-expert batches efficient, and how much skewed traffic will hurt.
  5. Licence, and whether base weights shipped, not just instruct. Base weights decide whether you can do your own post-training at all.

Worked example: gpt-oss-120b, from its gallery card and configuration:

  1. 117B total, 5.1B active: 4.4% of the parameters run per token, so it decodes like a 5B model but needs memory for all 117B.
  2. 36 GQA layers alternating a 128-token sliding window with full attention, one to one: cost grows with context through only 18 of the 36 layers.
  3. 8 KV heads of dh = 64: 72 KiB per token headline, about 36 KiB per token effective at long context. At 131,072 tokens that is 4.5 GiB per request, so 16 concurrent full-context requests need about 72 GiB of cache.
  4. 128 routed experts, 4 active per token, no shared expert listed in the configuration.
  5. Released under Apache 2.0 (model card); whether a base checkpoint shipped is not stated there, so check before planning post-training on it.

The rule of thumb that falls out: if the workload is short-context and throughput-bound, GQA is the safe default; if long context at high concurrency dominates the bill, the choice is between shrinking what each token stores (MLA, FP8 or FP4 cache), storing it for fewer tokens (sliding windows), or not storing it at all in most layers (linear hybrids), and each gives up something different: kernel simplicity, far-back recall through fewer layers, or exact recall through a lossy state.

Common mistakes and misconceptions

Sizing the cache by query heads
The cache is set by KV heads. Llama 3.1 70B has 64 query heads and only 8 KV heads; using 64 overstates its cache 8 times.
Forgetting the factor 2 or the element size
Keys and values are both stored, and an FP8 cache is half a BF16 one. Quote the precision with the number.
Taking the gallery's per-token figure as the long-context cost of a windowed model
The headline counts windowed layers at full cost. Gemma 3 27B reads 496 KiB per token but holds about 83 KiB per token at 128K context.
Treating total parameters as compute or active parameters as memory
Total sets the memory floor, active sets latency and price, and in an encoder-decoder the active count differs between prefill and decode.
Assuming sparse attention shrinks the cache
Selecting the top k keys cuts arithmetic; storage falls only when the cache is also compressed.
Calling a linear hybrid "cache-free"
Its full-attention layers still keep a growing cache (24 KiB per token in Qwen3-Next), and the recurrent state is a fixed cost per request (36 MiB there at 2 bytes per element).
Thinking MLA just stores fewer heads
It stores a learned compression of all heads jointly, plus a separate positional key, and it needs its own kernels; porting a GQA kernel does not work.
Confusing pre-norm with post-norm variants
OLMo 2's layout still keeps the residual stream unnormalised; it normalises the sublayer's output, which is not the original Transformer's post-norm.
Reading RoPE as absolute position
The rotation is absolute in form, but attention scores depend only on the offset between two tokens.
Trusting any curated table without recomputing it
Rebuilding the gallery from config.json matches 84 of its 86 recomputable figures; for MiMo-V2-Flash and V2.5 the config gives 217.5 KiB per token against the gallery's 144 KiB (both arithmetics on the Compare tab).

Cache at context: what a request actually holds

The gallery's figure is per token; what a deployment must hold is that figure, layer by layer, times the tokens each layer actually keeps, plus any fixed recurrent state, times the number of requests. This tab sums it for any set of models:

memory per request = Σlayers bytes per tokenℓ × min(T, Wℓ) + Σlinear layers stateℓ × b
Wℓ
layer ℓ's window (∞ for a full-attention layer)
stateℓ
a linear layer's fixed state in elements: heads × dk × dv (Gated DeltaNet, KDA) or heads × head dim × state size (Mamba-2), from the config; convolution caches are small and left out
b
bytes per element, the same for cache and state here (configs such as Nemotron 3 and Qwen3.5 keep the state in float32, which doubles that term)

Try: the defaults reproduce the Reading tab: Llama 3.1 70B at 40 GiB per 128K request, Gemma 3 27B at 10.4 GiB (62 GiB with windows not credited), gpt-oss-120b at 4.5 GiB, Qwen3-Next at 3 GiB plus 36 MiB of state. Turn off "credit windows" to see the gallery convention; slide the context down to find where a hybrid's fixed state stops mattering.
