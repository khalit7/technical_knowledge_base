Cache at context: what a request actually holds

The gallery's figure is per token; what a deployment must hold is that figure, layer by layer, times the tokens each layer actually keeps, plus any fixed recurrent state, times the number of requests. This tab sums it for any set of models:

memory per request = Σlayers bytes per tokenℓ × min(T, Wℓ) + Σlinear layers stateℓ × b
Wℓ
layer ℓ's window (∞ for a full-attention layer)
stateℓ
a linear layer's fixed state in elements: heads × dk × dv (Gated DeltaNet, KDA) or heads × head dim × state size (Mamba-2), from the config; convolution caches are small and left out
b
bytes per element, the same for cache and state here (configs such as Nemotron 3 and Qwen3.5 keep the state in float32, which doubles that term)

Try: the defaults reproduce the Reading tab: Llama 3.1 70B at 40 GiB per 128K request, Gemma 3 27B at 10.4 GiB (62 GiB with windows not credited), gpt-oss-120b at 4.5 GiB, Qwen3-Next at 3 GiB plus 36 MiB of state. Turn off "credit windows" to see the gallery convention; slide the context down to find where a hybrid's fixed state stops mattering.

Logical BF16 estimate for one sequence per request, as in the gallery's {{KV-cache notes|@kvc}}; paged allocation, padding and runtime buffers move measured memory up or down. Weights are not included. A dot marks each model's configured maximum context (max_position_embeddings); lines continue past it for comparison only.
