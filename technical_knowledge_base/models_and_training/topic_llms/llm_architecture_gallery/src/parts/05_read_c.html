2. MoE configuration, in brief

Each block's feed-forward network becomes many expert FFNs plus a router that activates a few per token, decoupling capacity from per-token compute. The trend runs from few big experts (Mixtral 8x7B with top-2 of 8, Grok 2 with 8) to many small ones at high sparsity, usually with a shared always-on expert: DeepSeek V3 runs 256 routed experts with 8 active plus 1 shared, Kimi K2 384, K3 896 with 16 active (and 2 shared, per its config), while Qwen3 uses 128 with no shared expert (Qwen reinstated one from Qwen3-Next on: 512 experts, 10 routed plus 1 shared). Several models keep the first blocks dense (V3, GLM-4.5), because early-layer representations are barely differentiated and routing on them is near-random and destabilising. The expert counts of every model are in the FFN strip on the Compare tab, read from config.json.

The MoE choice and the attention choice are independent: MoE sets the weight memory and the compute per token, attention sets the KV cache, and a card has to be read for both. {{Mixture-of-Experts (MoE) models|n:3c65c17b0d0d810080cce6648ac8f2f2}} owns the mechanism: why fine-grained sparsity wins and what it costs, top-k routing and its gating formula, load balancing (auxiliary losses against DeepSeek's bias-based aux-loss-free scheme), capacity factors and dropped tokens, expert parallelism, and what breaks at inference.

Multi-token prediction (MTP) heads are increasingly standard alongside this: extra output heads trained to predict the token after next, and the one after that. In training they densify the learning signal per position; at inference they act as a built-in draft model for speculative decoding, so the speedup arrives without a separate small model to maintain. The cost is a modest number of extra parameters and a more involved loss.

3. Normalisation

RMSNorm is universal. It rescales by the root mean square of the activations and drops LayerNorm's mean subtraction and bias, which removes one reduction and a set of parameters at no measured quality cost:

RMSNorm(x) = x / √( (1/d) Σj xj2 + ε ) ⊙ g
LayerNorm(x) = (x − μ) / √(σ2 + ε) ⊙ g + b
x
∈ ℝd, one token's activation vector with components xj
μ, σ2
the mean and variance of its components
ε
a small constant for numerical safety (Llama 3.1 uses 10−5, {{config|@l70}})
g, b, ⊙
a learned per-dimension gain, LayerNorm's learned bias, and elementwise multiplication

Worked example (gain 1, ε ignored). For x = (1, 2, 3, 4): the mean square is (1 + 4 + 9 + 16)/4 = 7.5, the RMS is √7.5 = 2.739, and RMSNorm gives (0.365, 0.730, 1.095, 1.461), the same direction rescaled. LayerNorm first subtracts the mean 2.5, divides by the standard deviation √1.25 = 1.118, and gives (−1.342, −0.447, 0.447, 1.342), centred on zero. RMSNorm costs one reduction instead of two.

The interesting differences are placement and extras. Writing F for a sublayer (attention or FFN):

  • Pre-norm, x + F(Norm(x)), is the default. It keeps a clean unnormalised identity path down the residual stream, which is what makes deep models trainable without learning-rate warmup tricks. Its known cost is that residual-stream magnitudes grow with depth. The original Transformer's post-norm, Norm(x + F(x)) ({{Attention Is All You Need|n:3c65c17b0d0d81999af7f16f8ed8ee9e}}), normalises the stream itself and is harder to train deep.
  • Post-norm variants. OLMo 2 ({{2 OLMo 2 Furious|n:3c65c17b0d0d81fb9857fb956165ae1c}}) normalises each sublayer's output before it is added back, x + Norm(F(x)), which damps what each block injects and is reported to improve loss stability. Gemma 3 normalises both before and after each block, x + Norm(F(Norm(x))), taking the stability of both placements for an extra norm per sublayer, negligible next to the matmuls.
  • QK-norm. RMSNorm on the query and key vectors before the attention dot product (in most implementations before RoPE). This bounds attention-logit magnitude, which otherwise grows steadily during training and produces the classic bf16 attention overflow and loss spike. With unit gain an RMS-normalised vector of dimension dh has length √dh, so the scaled logit q · k / √dh is at most √dh, about 11.3 for dh = 128; only the learned gains can raise it. It spread from OLMo 2 and Gemma to most 2025-and-later models and is close to free insurance. MiniMax M2 applies it per layer rather than per head: its {{config|@mm2cfg}} sets qk_norm_type: per_layer and the gallery lists "per-layer QK-Norm", one RMSNorm over all heads' queries (and keys) together. Cost: two extra normalisations per attention layer.

4. Positional encoding

Attention on its own is order-blind: permute the keys and values and each query's output is unchanged. RoPE (rotary position embedding, from {{RoFormer|n:3c65c17b0d0d81cfa5e9f54459720098}}) is near-universal. It splits each query and key into dh/2 pairs of dimensions and rotates pair i of a token at position m by the angle m θi:

( q′2i, q′2i+1 ) = ( q2i cos mθi − q2i+1 sin mθi,  q2i sin mθi + q2i+1 cos mθi )
θi = base−2i/dh,   ⟨ Rmq, Rnk ⟩ = ⟨ q, Rn−mk ⟩
q2i, q2i+1
the two components of pair i (for i = 0, …, dh/2 − 1) and q′ the rotated ones; keys are rotated the same way by their own position n
θi
pair i's frequency in radians per token, with base classically 10,000 and 500,000 in Llama 3
Rm
the whole block-diagonal rotation for position m; the identity says the query-key dot product depends only on the offset n − m, because rotations compose and a rotation's transpose is its inverse

So RoPE injects absolute position in form but gives attention scores that depend on relative distance, with no parameters. Low-index pairs rotate fast and resolve short-range order; high-index pairs rotate slowly and encode long-range position. With dh = 128 and base 500,000, pair 0 turns 1 radian per token (a full turn every 6.3 tokens) while pair 63 turns 2.46 × 10−6 radians per token (a full turn every 2.56 million tokens).

Worked example (one pair, an illustrative θ = 0.5 radians per token). Take q = k = (1, 0). At m = 3 and n = 5 the query is rotated by 1.5 radians to (0.0707, 0.9975) and the key by 2.5 radians to (−0.8011, 0.5985); their dot product is 0.0707 × (−0.8011) + 0.9975 × 0.5985 = 0.5403 = cos(1.0). Move both tokens to m = 10, n = 12: the angles become 5 and 6 radians, the gap is still 1 radian, and the dot product is again 0.5403.

Everything below is about a model trained at one context length having to work at another. {{Positional Encodings|n:3c65c17b0d0d81a5b7c9e578fcdfac00}} owns the context-extension methods in detail (position interpolation, NTK-aware base scaling, YaRN, LongRoPE) and the older absolute and relative schemes; the summary here is what a model card's positional line means.

  • Base and interpolation scaling (YaRN and relatives). Raising RoPE's frequency base, or interpolating position indices, stretches the rotations so a longer context falls inside the range of angles the model saw in training. YaRN ({{Peng et al., 2023|@yarn}}) does this per frequency band: for pair i it counts how many full turns r = Lorig / λi fit in the original context (λi = 2π / θi), leaves pairs with r > β alone, divides the frequency of pairs with r < α by the scale factor s, and ramps linearly between (the paper suggests α = 1, β = 32 for Llama), plus an attention temperature √(1/t) = 0.1 ln s + 1. It buys context extension with a short continued-training phase; blunt uniform interpolation costs short-range precision, the failure mode YaRN was designed around. gpt-oss ships YaRN with a scaling factor of 32 on a base of 150,000 for its 131,072-token context ({{config|@gptoss}}: original 4,096, beta_fast 32, beta_slow 1).

Try: each bar is one RoPE pair; its height is how many full turns it makes inside the original training context (log scale). The default is gpt-oss (64-dimensional heads, base 150,000, 4,096 original, factor 32) and gives 9 pairs kept, 9 on the ramp and 14 fully interpolated, with a temperature factor of 1.347. Switch to Llama 3's base to see more pairs fall below one turn.

  • Partial RoPE. Rotate only a fraction of each head's dimensions and leave the rest position-free, so those dimensions match on content alone. This empirically extrapolates better beyond the trained length, at the cost of some positional resolution. In the configs: Qwen3-Next and its successors rotate 25% (partial_rotary_factor 0.25), MiniMax M2 64 of 128 dimensions, GLM-4.5 half. MLA's decoupled key is a structural relative: position lives in 64 dimensions, content in the rest.
  • NoPE on a subset of layers. No positional encoding at all in some layers. A causal decoder can still infer ordering from the attention mask, and layers with no positional bias extrapolate past the training length far more gracefully, since no rotation runs off the end of its trained range. Pure NoPE is weaker on short-range ordering, so it is mixed: SmolLM3 makes every fourth layer NoPE (9 of 36), Kimi Linear and Kimi K3 drop RoPE from their full-attention layers, and several 2026 models interleave RoPE and NoPE layers (Muse Glimmer, Solar Open 2).
  • iRoPE (Llama 4). Interleaves local RoPE layers (chunked attention, 8,192 tokens) with global layers that carry no positional encoding, 36 and 12 in Maverick, plus inference-time attention temperature scaling, aimed squarely at length generalisation rather than at cache size.
  • Different bases per layer type. Gemma 3 keeps base 10,000 on its local layers and raises it to 1,000,000 on its global layers, since only the global layers ever see long distances; Gemma 4, MiMo and Laguna do the same.

The position strip on the Compare tab shows, layer by layer, which of these each model uses.

5. Stack shape: depth reuse, and the encoder-decoder return

Two September 2026 releases changed something the four sections above quietly assume, that a model is one causal decoder stack executed once per token.

  • Recurrent depth (looped transformers). Rather than adding layers, reuse them: activations are looped back through the same blocks, so serial depth per token decouples from parameter count. GPT-6 Astra is assumed to work this way (unconfirmed: OpenAI has not published its architecture), and the Recurrent Looped Transformer specification is the first published account of the family, pairing a causal encoder that builds a global KV memory with a decoder carrying its full state, final output and layerwise sliding-window cache included, across the prompt and response boundary with no reset, for unbounded temporal depth at fixed per-token compute. It buys compute without parameter memory, which makes the model cheaper to host. It costs recurrent state that the serving stack must carry between requests, and shorter visible reasoning traces, a real loss to chain-of-thought monitorability. The specification ships with no trained weights, no efficiency measurements and no quality results, so this is a shape to recognise on a card rather than a recipe to copy ({{Reasoning models and test-time compute|n:3c65c17b0d0d8190b9b4cd0acbcb66df}} places it among the ways of spending test-time compute). Looping already shows up in open configs: Ouro-Thinking 2.6B runs 4 passes over 48 layers, each keeping its own cache, so its 384 KiB per pass becomes 1.5 MiB per token ({{KV-cache notes|@kvc}}).
  • Encoder-decoder at frontier scale. In an encoder-decoder, an encoder reads the input once with its own layers and the decoder generates while attending to the encoder's output through cross-attention, instead of one causal stack doing both. DeepSeek V4.1-Flash is 552B split into a 20-layer causal encoder and a 20-layer decoder, activating 8B during prefill and 16B during decode. It departs from the classic design in one respect: it has no cross-attention; the decoder's keys and values are projected from the encoder's layer-20 state instead ({{zartbot|@zart}}), detailed on {{DeepSeek|n:3c65c17b0d0d81a2ae7ec6796947a235}}. The argument is not T5's quality one ({{T5|n:3d45c17b0d0d81ec8ebfec02e953a7fd}} measured encoder-decoders ahead at matched compute, and the field went decoder-only regardless): encoding the prompt once into a shared representation, combined with cross-layer sparse attention with index reuse, hierarchical retrieval and FP4 cache storage, gets the KV cache to 890 bytes per token, a quarter of V4-Flash's HBM footprint and an eighth of its SSD footprint. At that rate a 131,072-token context holds about 111 MiB, against 40 GiB for Llama 3.1 70B above. The gallery's own BF16 count for the growing global cache is (3/2 + 1) × (512 + 128) × 2 = 3,200 bytes = 3.125 KiB per token; the 890 bytes uses FP4 main KV and indexer keys with quantisation scales ({{KV-cache notes|@kvc}}). T5Gemma is the other current encoder-decoder line, at small scale and built by adapting decoder checkpoints rather than pretraining ({{Encoder-Decoder Gemma and T5Gemma 2|n:3d45c17b0d0d81a9a22ffaada508db5c}}). Note what this does to rule 1 below.

How to read a new model card in 30 seconds

  1. Total versus active parameters. The ratio is the sparsity; the total is the memory floor you must provision, the active count sets latency and price per token. They predict different things and are routinely conflated, and the active count is no longer guaranteed to be a single number: an encoder-decoder can activate one figure during prefill and another during decode.
  2. Attention type and layer mix. Quadratic, hybrid or trained-sparse, and in what proportion. This is how cost scales with context, which matters more than the headline context number.
  3. KV cache per token, multiplied by target context and concurrency. "Does long context actually fit", answered in gigabytes. Credit the sliding windows yourself: the headline figure counts windowed layers at full cost (the Cache at context tab does it for you).
  4. Experts: routed, active, shared. Determines routing style, how much expert parallelism you need to make per-expert batches efficient, and how much skewed traffic will hurt.
  5. Licence, and whether base weights shipped, not just instruct. Base weights decide whether you can do your own post-training at all.

Worked example: gpt-oss-120b, from its gallery card and {{configuration|@gptoss}}:

  1. 117B total, 5.1B active: 4.4% of the parameters run per token, so it decodes like a 5B model but needs memory for all 117B.
  2. 36 GQA layers alternating a 128-token sliding window with full attention, one to one: cost grows with context through only 18 of the 36 layers.
  3. 8 KV heads of dh = 64: 72 KiB per token headline, about 36 KiB per token effective at long context. At 131,072 tokens that is 4.5 GiB per request, so 16 concurrent full-context requests need about 72 GiB of cache.
  4. 128 routed experts, 4 active per token, no shared expert listed in the configuration.
  5. Released under Apache 2.0 ({{model card|@gptosscard}}); whether a base checkpoint shipped is not stated there, so check before planning post-training on it.

The rule of thumb that falls out: if the workload is short-context and throughput-bound, GQA is the safe default; if long context at high concurrency dominates the bill, the choice is between shrinking what each token stores (MLA, FP8 or FP4 cache), storing it for fewer tokens (sliding windows), or not storing it at all in most layers (linear hybrids), and each gives up something different: kernel simplicity, far-back recall through fewer layers, or exact recall through a lossy state.

Common mistakes and misconceptions

Sizing the cache by query heads
The cache is set by KV heads. Llama 3.1 70B has 64 query heads and only 8 KV heads; using 64 overstates its cache 8 times.
Forgetting the factor 2 or the element size
Keys and values are both stored, and an FP8 cache is half a BF16 one. Quote the precision with the number.
Taking the gallery's per-token figure as the long-context cost of a windowed model
The headline counts windowed layers at full cost. Gemma 3 27B reads 496 KiB per token but holds about 83 KiB per token at 128K context.
Treating total parameters as compute or active parameters as memory
Total sets the memory floor, active sets latency and price, and in an encoder-decoder the active count differs between prefill and decode.
Assuming sparse attention shrinks the cache
Selecting the top k keys cuts arithmetic; storage falls only when the cache is also compressed.
Calling a linear hybrid "cache-free"
Its full-attention layers still keep a growing cache (24 KiB per token in Qwen3-Next), and the recurrent state is a fixed cost per request (36 MiB there at 2 bytes per element).
Thinking MLA just stores fewer heads
It stores a learned compression of all heads jointly, plus a separate positional key, and it needs its own kernels; porting a GQA kernel does not work.
Confusing pre-norm with post-norm variants
OLMo 2's layout still keeps the residual stream unnormalised; it normalises the sublayer's output, which is not the original Transformer's post-norm.
Reading RoPE as absolute position
The rotation is absolute in form, but attention scores depend only on the offset between two tokens.
Trusting any curated table without recomputing it
Rebuilding the gallery from config.json matches 84 of its 86 recomputable figures; for MiMo-V2-Flash and V2.5 the config gives 217.5 KiB per token against the gallery's 144 KiB (both arithmetics on the Compare tab).
