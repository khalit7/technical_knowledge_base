MHA, MQA and GQA: how many query heads share a KV head

Classic multi-head attention (MHA) gives every query head its own key and value head, Hkv = H. Multi-query attention (MQA, {{Shazeer, 2019|@mqa}}) goes to the other extreme, one shared KV head for all queries, Hkv = 1. Grouped-query attention (GQA, {{Ainslie et al., 2023|@gqa}}) sits between: query heads are divided into Hkv groups, and every head in a group reads the same keys and values. Query head i (counting from 0) uses KV head

g(i) = ⌊ i / (H / Hkv) ⌋
H / Hkv
the group size (query heads per KV head)
⌊ · ⌋
rounds down

Each layer stores 2 Hkv dh elements per token instead of 2 H dh.

  • What it buys. The cache is sized by KV heads, so a group size of 8 cuts the cache and the per-token memory traffic by 8, and because decode is memory-bandwidth-bound that is close to a linear speedup at long context.
  • What it costs. Expressivity: query heads in a group can no longer attend along independent key subspaces. The loss is small, and it can be recovered without pretraining from scratch: the GQA paper converts existing MHA checkpoints by continuing training ("uptraining") for about 5% of the original pre-training compute, and reports quality close to MHA at a speed comparable to MQA. MQA saves more and degrades more.
  • Worked example. {{Llama 3.1 8B|@l8}} has 32 layers, 32 query heads, 8 KV heads and dh = 128, so groups of 4 query heads share a KV head and query heads 0 to 3 read KV head 0 (step 4 of the animation, GQA). Per token: 2 × 32 × 8 × 128 × 2 = 131,072 bytes = 128 KiB. OLMo 2 7B, which keeps full MHA over 32 layers, needs 512 KiB per token (the gallery's figure, reproduced from its config), four times as much for a model of similar size.

GQA was the 2023 to 2024 default and remains the baseline in Llama 3 and 4, Qwen3, Gemma and gpt-oss: of the 89 models rebuilt on the Compare tab, 46 use GQA in all their attention layers, 19 use MLA (some with a sparse indexer on top), 24 contain linear or recurrent layers (xLSTM 7B is recurrent throughout), and only 4 keep full MHA (GPT-2 XL, OLMo 2 7B, OLMo 3 7B and Ouro-Thinking); Gemma 3 270M is the lone MQA model, with one KV head.

MLA (multi-head latent attention): cache a compressed latent instead of keys and values

Introduced in DeepSeek-V2 ({{arXiv 2405.04434|@dsv2}}) and now used well beyond DeepSeek (V2, V3, R1, V3.2, Kimi K2 to K2.6, Mistral Large 3 and Small 4, GLM-5, Sarvam 105B, per their configs). Instead of caching keys and values per head, project them jointly into a single low-rank latent vector, cache only that, and up-project back to per-head keys and values inside the attention call:

ct = WDKV ht,   kCt,i = WUKi ct,   vt,i = WUVi ct
kRt = RoPE(WKR ht),   kt,i = [ kCt,i ; kRt ]
ht
token t's input to the attention layer (the normalised residual stream)
WDKV
down-projects it to the latent ct of dimension dc, much smaller than 2H dh
WUKi, WUVi
up-project the latent to head i's content key and value
kRt
a small decoupled RoPE key of dimension dR, shared by all heads, carrying the position
[ · ; · ]
concatenation, so head i's key is its content key plus the shared positional key

Only ct and kRt are cached: dc + dR elements per layer per token, regardless of the number of heads. At inference the up-projections need not be materialised: WUKi can be multiplied into the query projection and WUVi into the output projection, so attention runs directly against the cached latent, and every query head reads the same entry (the MLA step 4 of the animation; the {{DeepSeek page|n:3c65c17b0d0d81a2ae7ec6796947a235}} animates the absorption itself).

  • Why the separate RoPE key. RoPE multiplies each key by a position-dependent rotation. Applied to the latent, the rotation would sit between WUKi and the query and could no longer be folded into the query projection, since it changes with position; rotating before compression does not survive the up-projection either. So position travels in the small extra key, and the latent stays position-free.
  • Worked example: DeepSeek V3. 61 layers, 128 heads of dh = 128, latent dc = 512, decoupled key dR = 64 ({{config|@dsv3cfg}}; {{DeepSeek-V3 Technical Report|n:3c65c17b0d0d815fb8dac9ba1e35ab81}}). Per token in BF16: 61 × (512 + 64) × 2 = 70,272 bytes = 68.6 KiB. Full MHA at the same shape would store 2 × 128 × 128 = 32,768 elements per layer, 61 × 32,768 × 2 = 3,997,696 bytes = 3,904 KiB per token: MLA is 57 times smaller. Against GQA it still wins: 576 elements per layer is what GQA would store with only 2.25 KV heads of dimension 128.
  • What it buys. A cache smaller than aggressive GQA, and DeepSeek's ablations report quality at or slightly above MHA, the unusual part: most cache reductions cost quality.
  • What it costs. Compute and complexity. Every attention call pays extra projections, trading arithmetic (cheap and parallel) for memory traffic (scarce during decode), the right trade on current hardware. The decoupled RoPE path makes the kernels fussier than GQA's, which is why MLA support lagged in serving stacks.

Local/global mixing (sliding-window layers)

Most layers attend only within a fixed window of the W most recent tokens, with a full-attention ("global") layer inserted periodically. Gemma 3 uses 5 local layers per global layer with a 1,024-token window ({{Gemma 3 report|@g3}}); gpt-oss alternates sliding and full layers one to one with a 128-token window ({{config|@gptoss}}); 3:1 appears in OLMo 3 (window 4,096), Arcee Trinity Large and, as chunked attention of 8,192 tokens, Llama 4 Maverick (configs on the Compare tab). A windowed layer needs cache only for the window, so the memory one request holds at context length T is:

KV memory per request = ( Lglobal × T + Llocal × min(T, W) ) × bytes per layer per token

Past T = W the windowed term stops growing, so total cache grows only through the global layers.

  • Worked example: Gemma 3 27B. 62 layers (52 windowed, 10 global), 16 KV heads of 128, so 8 KiB per layer per token, the gallery's 496 KiB spread over 62 layers. At T = 131,072: global layers hold 10 × 8,192 × 131,072 bytes = 10 GiB; windowed layers hold 52 × 8,192 × 1,024 bytes = 416 MiB, fixed. Total about 10.4 GiB, against 62 GiB at the headline 496 KiB per token: about 6 times less (5.96). Effective long-context cost is about 83 KiB per token, not 496.
  • Worked example: gpt-oss-120b. 36 layers, 8 KV heads of dh = 64: 2 KiB per layer per token, 72 KiB per token headline. At 131,072 tokens the 18 global layers hold 4.5 GiB and the 18 windowed layers 4.5 MiB, so the effective cost halves to 36 KiB per token.
  • What it buys and costs. Quality loss is negligible on most workloads because the global layers still route information across the whole sequence. The cost is that information must travel through those global layers, so the ratio is a real hyperparameter: retrieval-style long-context tasks, where an exact token far back must be recovered, are the workload most sensitive to it.

Trained sparse attention

A lightweight learned indexer scores candidate keys, or blocks of keys, per query, and full attention is computed only over the selected top k, so the logits cost O(k dh) per query instead of O(T dh), plus the indexer's own cheaper pass over all T. Because full attention's scores grow with T2 over a sequence, going from a 128K to a 1M window multiplies that part of the work by 82 = 64, and trained sparse attention is what made 1M-token contexts economical in 2026: DeepSeek V3.2's DSA, V4's compressed CSA and HCA (which drop the KV cache to about 2% of vanilla), MiniMax M3's MSA, and Qwen's QSA, which selects at micro-block rather than individual-token granularity because block-level gathers are far friendlier to memory hardware than scattered token-level ones (each lab page carries its variant and sources: {{DeepSeek|n:3c65c17b0d0d81a2ae7ec6796947a235}}, {{MiniMax|n:3c65c17b0d0d813ba1c0cb4ba00659b8}}, {{Qwen|n:3c65c17b0d0d81fd8c36ce06672bb235}}).

Selection by itself cuts arithmetic, not storage: every key must stay available for the indexer to choose from, so the cache shrinks only when it is also compressed, as in V4. The gallery's notes make the same point for a GQA-based design: top-2,048 selection "limits attention work without capping the stored history", and the indexer keys are an extra cache of their own ({{KV-cache notes|@kvc}}). It costs: the indexer is itself trained and runs on every query, selection is a hard decision that can miss the one token that mattered, and it has to be trained in rather than bolted on.

Linear and hybrid attention: Gated DeltaNet, KDA and Mamba-2

Replace softmax attention in most layers with a recurrent update to a fixed-size state, so per-token cost is constant and no KV cache grows with context. In its simplest form (linear attention) each head keeps a matrix state and updates it per token:

St = St−1 + vt kt⊤,   ot = St qt
St
∈ ℝdv × dk, the state after token t: dv × dk entries whatever the context length
kt, vt, qt
that token's key, value and query
ot
the head's output

Plain accumulation never forgets, so modern variants add a decay and an error-correcting write. Gated DeltaNet ({{Yang et al., 2024|@gdn}}) uses

St = αt St−1 ( I − βt ktkt⊤ ) + βt vtkt⊤
αt
∈ (0, 1), a learned per-token decay (the gate), one scalar per head
βt
∈ (0, 1), a learned write strength
I
the identity; the bracket first erases what the state stores under key kt, then vt is written there (the delta rule)

Kimi Delta Attention (KDA), the layer of {{Kimi Linear (arXiv 2510.26692)|@kl}}, "extends Gated DeltaNet with a finer-grained gating mechanism": the scalar head-wise decay αt becomes a diagonal matrix Diag(αt), one forgetting rate per key channel ("akin to Gated Linear Attention"). Written in this page's orientation,

St = St−1 Diag(αt) ( I − βt ktkt⊤ ) + βt vtkt⊤
αt
∈ (0, 1)dk, a vector of decays, so each column of the state fades at its own rate (the KDA step 3 of the animation shows the columns fading unevenly)

The paper writes the transpose, St = (I − βtktkt⊤) Diag(αt) St−1 + βtktvt⊤ with S ∈ ℝdk × dv; the two are the same update.

Hybrids interleave periodic full-attention layers to restore exact recall: roughly 1 in 4, the 3:1 ratio of Kimi Linear and Qwen3-Next. Kimi Linear's ablation picked 3:1 over 0:1, 1:1, 7:1 and 15:1 (validation perplexity 5.65 against 5.77, 5.66, 5.70 and 5.82), and the paper reports the hybrid beating full MLA under an identical recipe while "reducing KV cache usage by up to 75%" (3 of every 4 layers keep none, so the 75% follows by construction) "and achieving up to 6× decoding throughput for a 1M context"; its MLA layers also drop RoPE altogether (NoPE). Qwen3-Next's Gated DeltaNet, Moonshot's KDA, and Mamba-2 hybrids such as NVIDIA's Nemotron 3 and IBM Granite 4 all take this shape, pushing KV cache per token from hundreds of KiB down to tens of KiB or less. {{Mamba|n:3c65c17b0d0d8179984fc3a1fee4c36a}} is the state-space formulation underneath: a selective recurrence whose input-dependent parameters play the role of αt and βt here.

  • Worked example: Qwen3-Next 80B-A3B. 48 layers, of which 36 are Gated DeltaNet and 12 are full (gated) attention with 2 KV heads of dh = 256 ({{config|@qncfg}}). Only the 12 full layers grow a cache: 12 × 2 × 2 × 256 × 2 = 24,576 bytes = 24 KiB per token (the gallery's figure), 3 GiB at 128K. The fixed state is 32 value heads × 128 × 128 = 524,288 numbers per DeltaNet layer, 36 MiB over 36 layers at 2 bytes (72 MiB in the float32 many kernels keep it in): the same as the growing cache at 1,536 tokens, so beyond a few thousand tokens the state is noise. All 48 layers as full attention would need 96 KiB per token.
  • Worked example: Kimi Linear 48B-A3B. 27 layers: 20 KDA and 7 MLA ({{config|@klcfg}}). Cache: 7 × (512 + 64) × 2 = 8,064 bytes = 7.9 KiB per token; state 20 layers × 32 heads × 128 × 128 = 20 MiB at 2 bytes.
  • What it costs. The cost is inherent to the fixed-size state: it is a lossy summary, so anything not written into it is unrecoverable, and pure linear models are measurably worse at exact retrieval. The hybrid exists because the full-attention layers buy that capability back, and the mixing ratio is the dial between memory footprint and recall fidelity.
