Where Muse Spark scores, and on which scale

Artificial Analysis has changed its Intelligence Index twice since Muse Spark 1.3 shipped: v4.2 on 4 September 2026 (GPQA Diamond removed) and v4.3 on 7 September (Terminal-Bench moved from 2.1 to 4.0, τ³-Banking replaced by AutomationBench-AA, private tests weighted 45% instead of 40%), with a methodology update to v4.3.2 on 19 September ({{Artificial Analysis|@aalb}}, read 1 October 2026). The release-time 61 and 62 are on the scale before v4.2. On the current v4.3 the same model scores 45.1 at xhigh and 48.1 at max, at $1.37 per index task at xhigh and $1.60 at max ({{Artificial Analysis|@aam}}). A number from one version never compares with another, so the chart keeps them in separate panels.

Read on v4.3, Meta's best run (48.1) is fourth among labs by each lab's best model, behind Anthropic (57.6), OpenAI (52.7) and Google DeepMind (52.6), derived from the same leaderboard; the earlier description of a "reranked v4.2" on which Meta came third was wrong, since v4.2 was a change of benchmarks, not a reranking of labs. The release-time point, "cheapest at its level", does not survive the rescaling: on v4.3 GPT-6.1 Sol (max) scores 51.8 at $0.72 a task and GPT-6 Sol (max) 47.6 at $1.04, both above Muse Spark 1.3 (xhigh) and cheaper per task. Muse Glimmer, at 17.5 for $0.06 a task, sits in the open-weights cluster well below the open frontier, where Xiaomi's MiMo-V2.6-Pro leads at 46.3.

The Muse agent's security architecture

The Muse agent holds standing access to a user's mail, payments and accounts while reading attacker-controllable web pages and messages, which is the worst case for prompt injection (instructions hidden in content the agent reads). Meta's design assumes the model will sometimes be fooled and makes being fooled grant nothing that matters. From Meta's own description of 8 September 2026 ({{Meta|@sec}}):

  1. The runtime cell. The agent harness runs in a systemd-nspawn container inside the user's VM, with "root inside the runtime cell ... mapped to an unprivileged host user", its own filesystem and virtual network interface, filtered system calls (no io_uring) and limited kernel capabilities (no CAP_SYS_PTRACE, no CAP_NET_ADMIN).
  2. Security services outside the cell. Separate services hold what the agent must not: hatch-authd stores credentials (including OAuth tokens for third-party services), privsep workers run the built-in connector code with tightly scoped credential access, hatch-safety runs independent classifier models over requests and responses so that an attacker inside the cell cannot switch them off, and Sentinel is "the sole permission authority" for connector actions and network egress. The cell talks to them only over Unix domain sockets with kernel-authenticated peer checks.
  3. Surrogate credentials. The agent never sees a real password, token or card. "Code in the runtime cell or a worker only ever sees a 'surrogate' token, minted by authd. After the concrete network request is authorized, Sentinel will replace any surrogate tokens with the real credential ... at the network boundary", so an injected "send me the token" can only exfiltrate a placeholder.
  4. Egress policy. Sentinel resolves each request to allow, deny or ask, inspecting it at layers 4 and 7: "the hostname, the resolved and final destination IP address, the port, protocol, HTTP method, path, and the actual decoded request". It tracks tainted egress through the kernel: each tool process starts clean and becomes tainted if it reads user data (eBPF programs on cgroups and on Linux Security Module hooks Meta added), so a request carrying data from an untrusted source does not ride an auto-allow rule.
  5. Approvals outside the conversation. When Sentinel's answer is "ask", execution halts and the approval goes "directly to the Muse client", appearing in the app's own interface, not as a message in the chat with Muse, so text in the context window cannot manufacture consent. Grants are "strict capabilities, not conversational suggestions", bound to the connector or destination: one-time, session, task, time-bounded or permanent. Checkouts always need approval with the exact purchase details and use single-use card numbers through Stripe Link, bound to one merchant, one amount and a short validity.
  6. A browser that cannot be scripted. The browser sub-agent sees "an accessibility tree snapshot of the page, not the raw DOM", and has no way to run JavaScript in the page; a separate family of classifiers looks for prompt injection in pages, images and files, for high-risk forms and for egress of unrelated personal data.

The animation runs one injected page through two agents: a naive one that holds real credentials and sends whatever it composes, and Muse's design. The injection succeeds against the model in both; what differs is what it buys.

The task, the injected page and the attacker's address are illustrative; the components and rules are Meta's. Meta publishes no example attack.

Meta offers "up to $300,000 for valid reports ... including up to $130,000 for successful prompt injection attempts that affect one user", and has published no accuracy figures for its classifiers, so the parts that still rest on detection are unmeasured ({{Meta|@sec}}). The boundary also covers only the cloud VM: on 22 September 2026 the researcher Patrick Wardle disclosed that malware already running under the user's account could change an undocumented macOS setting and redirect the Muse Mac client's dictation traffic, with its prompts and authentication data, to a server of its choosing ({{Cybersecurity News|@csn}}); that report gives no patch, and the fix "four days later" recorded earlier is unconfirmed in the sources read here. The general principle, that enforcement and credentials belong outside the component that can be persuaded, is developed on {{Topic: agentic-harnesses|n:3c65c17b0d0d81d881a8fe98b4cff7bb}}, and the comparison with self-hosted personal agents on {{Personal agents: OpenClaw, Hermes Agent, and how they differ from coding harnesses|n:3c75c17b0d0d81bf9462fbeb09593e1c}}.

Strategic read. Llama's retreat handed open-weights leadership to the Chinese labs and to Mistral, and it is a retreat from the open frontier only: Muse Spark 1.3 put Meta back in the frontier band in September 2026, and Muse Glimmer put it back in open weights at 30B, the size people run locally, not at the frontier. Which open model leads now depends on the benchmark, and the contenders (DeepSeek, Qwen, Moonshot's Kimi, Zhipu's GLM, Xiaomi's MiMo) are mapped on {{Topic: llms|n:3c65c17b0d0d812d9e00f6ec89965286}}. Whether Meta returns to the open frontier turns on one checkable event: the publication of Muse Spark weights. Llama 3.1 and 3.3 remain default bases in many fine-tuning stacks purely through incumbency: tooling, LoRA adapters, quantised builds and tribal knowledge accumulated around them, and that inertia outlives the quality argument.

Which Meta model when

  • You need frontier capability from Meta and can use a hosted API: Muse Spark 1.3. It buys frontier-band scores at a low cost per task, and costs closed weights, a single vendor's API and no technical report.
  • You need weights you can run locally or modify, with no licence conditions: Muse Glimmer. Apache 2.0 removes the 700-million-user clause, and a 24 GB GPU is enough for the 17 GB build; it is a 30B model (17.5 on the v4.3 index), so do not expect frontier reasoning.
  • You have an existing Llama fine-tuning pipeline: stay on Llama 3.1 or 3.3 while its adapters and quantised builds earn their keep, and plan a move, since nothing newer will ship under the Llama name.
  • You need a large open MoE from Meta: Llama 4 Maverick fits one 8-GPU H100 host in FP8 (400 GB of weights against 8 × 80 GB = 640 GB), but test it on your own tasks first; its public numbers did not hold up in practice, and the open models on the provider pages ({{DeepSeek|n:3c65c17b0d0d81a2ae7ec6796947a235}}, {{Alibaba: Qwen|n:3c65c17b0d0d81fd8c36ce06672bb235}}, {{Mistral AI|n:3c65c17b0d0d814a9882e6ebc326fa56}}) have overtaken it.
  • You are building a personal agent with account access: study the Muse agent's design (surrogate credentials, egress control outside the model, approvals outside the conversation) whatever model you use.

Whether a model fits your GPU, with its context, is on Run it yourself.

Common mistakes and misconceptions

"Llama 4 has a usable 10M-token context."
That is Scout's claimed limit, resting on iRoPE and attention temperature scaling; a claimed window is not demonstrated quality at that length, and Maverick's limit is 1M. It is also not a single-GPU figure: even with only the 12 global layers growing, Scout's cache at 10M tokens is about 481 GiB in BF16 (derived from the configuration on Run it yourself), six H100s' worth before any weights.
"17B active means 17B of memory."
Active parameters set the compute per token; all 109B or 400B parameters must still be stored. Scout fits one H100 only with Int4 weights (109B at half a byte is about 54.5 GB).
"Llama is open source."
The Llama licences restrict very large users and are Meta's own terms. Muse Glimmer's Apache 2.0 is the first Meta licence that is open source in the usual sense.
"Meta overtrained its flagship."
The 405B sat close to compute-optimal at about 38.5 tokens per parameter; the heavy overtraining was in the 8B and 70B (about 1,875 and 214 tokens per parameter), which are the ones served at volume.
"The 1417 LMArena score was Maverick's."
It belonged to an unreleased experimental checkpoint tuned for chat preference.
"Muse Spark 1.3's 61 compares with today's index numbers."
The 61 and 62 are on the scale the index used at release, before v4.2; a number from one version does not compare with another. On the current v4.3 the same model is 45.1 at xhigh and 48.1 at max, the figures to set beside other v4.3 scores.
"The Muse agent cannot be prompt-injected."
It can; the design limits what a successful injection achieves. The classifiers that still catch some attacks are unmeasured in public, and the Mac client sat outside the VM boundary.
"Chinchilla says train 20 tokens per parameter, full stop."
The 20 is the training-only optimum, and even that depends on whose fit you use: Hoffmann et al.'s own fitted law implies about 70 tokens per parameter, Epoch's replication about 20 ({{Besiroglu et al.|@epoch}}). Once serving is counted the optimum moves far higher; see the Overtraining explorer.
