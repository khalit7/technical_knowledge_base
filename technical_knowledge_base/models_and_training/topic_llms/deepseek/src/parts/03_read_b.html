Compressed attention in V4: CSA and HCA

V4 (DeepSeek-V4 report) changes what is stored, not only what is read, with two attention types interleaved through the stack.

Compression. Each layer computes per-token KV entries Cj of dimension c = 512 and a compression weight for each, then merges every block of tokens into one entry:

The compressed entry is a learned weighted average of the block, channel by channel.

  • CSA (Compressed Sparse Attention) compresses every m = 4 tokens into one entry, with overlapping blocks (each entry is built from 2m = 8 tokens through two weight series), then applies DSA to the compressed entries: the lightning indexer scores them and each query attends to the top-k only, 512 in V4-Flash and 1,024 in V4-Pro. The indexer has 64 heads of dimension 128 and runs in FP4.
  • HCA (Heavily Compressed Attention) compresses every m′ = 128 tokens into one entry, without overlap, and attends densely to all of them.

Both add the same four pieces around the compressed entries:

  • A sliding window of nwin = 128 uncompressed recent tokens. A query may only attend to completed blocks, so without the window it could not see the tokens in its own unfinished block, which are usually the most relevant ones.
  • Shared-KV multi-query attention. Each entry serves as both key and value for every query head (64 heads in Flash, 128 in Pro), the MQA shape MLA already used in decode.
  • Low-rank queries and a grouped output projection. Queries come from a compressed latent (dimension 1,024 in Flash, 1,536 in Pro), MLA's query trick; the heads' outputs are projected in 8 (Flash) or 16 (Pro) groups to 1,024 dimensions each before the final projection, because c · nh is large.
  • Partial RoPE and an attention sink. RoPE is applied to the last 64 dimensions of queries and entries, and, because an entry is also a value, the output is rotated back by the query's position so that it carries relative rather than absolute position. A learned sink logit per head lets the attention weights sum to less than one.

Layout and storage. V4-Flash has 43 layers, the first two pure sliding-window, the rest alternating CSA and HCA; V4-Pro has 61, the first two HCA, the rest alternating. Entries are stored in FP8 except the 64 RoPE dimensions, which stay BF16, nearly halving the cache against pure BF16.

Reported efficiency. Against BF16 GQA with 8 groups and head dimension 128, DeepSeek report the V4 cache at about 2% at a 1M-token context. Against V3.2 at 1M tokens, V4-Pro needs 27% of the single-token FLOPs and 10% of the KV cache, and V4-Flash 10% and 7% (V4 report).

    Sparse selection still needs the whole cache resident so that something can be selected from it, whereas compression shrinks what is resident. HCA reads every one of its entries, yet reads fewer than DSA stores by two orders of magnitude, because there are so few of them. Running both gives a cache that is precise nearby (the window, and CSA's fine blocks chosen by the indexer) and cheap far away (HCA's coarse summaries of everything).

    V4.1-Flash: the encoder-decoder cache stack

    V4.1-Flash pushes the programme past the attention layer into the shape of the network. Splitting a 40-layer transformer into a 20-layer causal encoder and a 20-layer decoder means the prompt is encoded once into a shared representation rather than carried as a per-layer cache through one causal stack. DeepSeek combine that with cross-layer sparse attention with index reuse, hierarchical retrieval, an Engram memory and FP4 cache storage. The reported result is 890 bytes per token, roughly a quarter of V4-Flash's HBM footprint and an eighth of its SSD footprint, which is what makes long agent loops affordable rather than merely possible (model card; zartbot gives the HBM and SSD ratios as runtime and persistent cache storage). End-to-End Context Compression at Scale argued the encoder-decoder case for context compression on exactly this systems ground.

    The detailed public walkthrough, zartbot's architecture breakdown, describes the mechanics behind those numbers.

    Try: switch phase. A prompt position stops at the encoder; a generated token goes through all 40 layers, which is why one active-parameter count does not describe this model.

    • Why the active count differs by phase. Prompt positions pass through the 20 encoder layers only, so prefill activates 8B parameters; each generated token passes through all 40 layers, so decode activates 16B.
    • How the halves connect. Not through T5-style cross-attention: the decoder's global keys and values are projected from the encoder's 20th-layer hidden state by layer-dependent projection weights, so decoder layers reuse one shared cache instead of storing their own. The stack keeps three copies of encoder cache and one of decoder cache across its 40 layers.
    • Index reuse. Layers run in one of three modes: full layers compute their own cache entries and top-k indices; reindex layers reuse a full layer's entries but score them with their own indexer query to pick new top-k indices; reuse layers take both the entries and the indices unchanged. So neither the cache nor the full selection is rebuilt at every layer.
    • Experts. 384 routed experts with 6 active per token.

    The layer pattern. The released config.json spells out which layer does what (config.json, read with zartbot; layers numbered from 0 as there). Layers 0 and 1 are sliding-window only. The rest of the encoder is three blocks of one full layer and five reuse layers, and its entries merge two adjacent positions into one (compress_ratios = 2). The decoder keeps every position: layer 20 is full and also builds the indexer's candidate pool; layers 24, 28, 32 and 36 reindex; all the others reuse. The Engram memory is injected at layers 1 and 14.

    Try: hover or tap a layer. Count the layers that store a cache copy: 4 of 40 (the arcs show who reads each one). Then slide the context in the funnel: the first stage grows with the context, the second never ranks more than 16,384 positions.

    The two-stage indexer. At decode, the full layer 20 ranks the context in blocks of 8 positions and keeps up to 2,048 blocks, a candidate pool of up to 16,384 positions; each later indexing layer then ranks only that pool and keeps its own top 512 (zartbot; candidate_topk_blocks, candidate_block_size and index_topk in the config). The model card's phrase is "bounding deeper indexer cost independently of context length" (model card).

    What one entry costs. DeepSeek's attention kernels store a V4.1 cache entry as 528 bytes in FP8 (512 values plus 16 scale bytes) or 288 bytes in FP4 (512 values at half a byte plus 32 scale bytes) (FlashMLA), and the model card says the main cache is FP4. As an estimate, not DeepSeek's breakdown: if the three encoder copies hold one entry per two positions and the decoder copy one per position, the main cache is 3 × 288 ÷ 2 + 288 = bytes per token; the reported 890 also counts the indexer keys.

    The MoE layer: fine-grained experts, shared experts, balancing without a loss

    A mixture-of-experts (MoE) layer replaces the feed-forward network with many expert networks and a router that sends each token to a few of them, so compute per token follows the active parameters while capacity follows the total. Routing, capacity factors, expert parallelism and what breaks at inference are on Mixture-of-Experts (MoE) models; this section covers what DeepSeek do differently.

    DeepSeekMoE: many narrow experts plus shared ones

    DeepSeekMoE, from V2, makes two changes to the Mixtral-style mixture of experts (a handful of large experts, two active per token).

    • Fine-grained experts: split each expert into several narrower ones and activate more per token, so V3 routes 8 of 256 rather than 2 of 8. The active parameter count is unchanged, but the number of distinct expert combinations explodes, which is what lets experts specialise narrowly instead of each being a generalist.
    • Shared experts: experts every token passes through unconditionally, absorbing the common computation otherwise duplicated inside every routed expert and freeing routed capacity for what is actually specialised.

    Both changes cost routing and communication overhead: more experts touched per token means more all-to-all traffic, which is why DeepSeek ended up writing their own communication kernels (DeepEP).

    Aux-loss-free load balancing

    Left alone, routers collapse: tokens pile onto a few popular experts, wasting the rest, and under expert parallelism the most loaded GPU sets the step time for everyone. The standard auxiliary balancing loss works but is a second objective fighting the first, pushing tokens away from the expert that would have modelled them best. V3 instead adds a bias to each expert's affinity for the top-k choice only (V3 report):

    gi,t′={si,tifsi,t+bi∈Topk({sj,t+bj},Kr)0otherwise
    bi
    expert i's bias, used only to choose; the gate weight that scales the expert's output still comes from the unbiased si,t, so the bias never enters the gradient

    After each step, the bias of every overloaded expert (measured over the whole batch) is decreased by γ and that of every underloaded one increased by γ, the bias update speed: 0.001 for V3's first 14.3T tokens and 0 for the last 500B. Balancing becomes a control loop outside the loss: it costs nothing in the objective and cannot trade quality for uniformity. V3 kept only a tiny sequence-wise auxiliary loss (weight α = 0.0001) against extreme imbalance inside one sequence, and dropped no tokens in training or inference; V4 uses the same values.

    Worked example (illustrative numbers). A token scores expert A at 0.62 and expert B at 0.60, with one slot left in its top-k. A has been overloaded for 30 consecutive steps, so bA = −30 × 0.001 = −0.03, while B's bias is 0. The selection scores are 0.62 − 0.03 = 0.59 for A and 0.60 for B, so the token goes to B. B's gate weight is computed from its true affinity, 0.60, renormalised with the other selected experts: the bias moved the decision boundary and nothing else.

    Try: a toy router (illustrative: 16 experts, top-2, 1,024 tokens per step, some experts made popular on purpose). With the bias off, the popular experts stay overloaded; switch it on and the control loop pulls every expert towards the mean. A larger γ converges faster and jitters more.

    V4 adds anticipatory routing against loss spikes, which DeepSeek traced to outliers in the MoE layers that routing amplifies: at step t the features use the current parameters, but the routing indices are computed with the parameters of step t − Δt, decoupling the router's updates from the backbone's. It is not always on: an automatic detector triggers a short rollback and switches it on only when a loss spike occurs, at about 20% extra wall-clock time while active, after which training reverts to the standard mode (V4 report).

    MTP: multi-token prediction

    Multi-Token Prediction (MTP) adds lightweight modules that predict, during training, not only the next token but the one after it (and further out) from the same trunk: denser supervision per forward pass, so the model learns more per token seen, and representations forced to look further ahead. Unlike earlier multi-token work with parallel independent heads, V3's modules are sequential, each a transformer block that takes the previous depth's representation and the next token's embedding, so the causal chain is kept at every depth. V3 and V4 use depth 1 (one extra token), weighted 0.3 in the loss for most of training and 0.1 at the end. At inference the extra module is already a draft of the next token, reusable as a built-in draft model for speculative decoding, with no separate draft model to train, align and host: V3 reports the second token accepted 85% to 90% of the time, for 1.8 times the tokens per second (V3 report).
