The through-line: one question, asked at every layer

DeepSeek is a spinoff of High-Flyer, a Chinese quantitative hedge fund, and its line reads as if designed by people who pay for their own GPUs. One question runs through every release: what does it cost to train, and above all to serve, a frontier-quality model?

Nearly every named contribution asks it at a different layer: attention (MLA, then sparse attention, then compressed attention), feed-forward (fine-grained mixture-of-experts with shared experts, balanced without an auxiliary loss), numerics (FP8 training, low-precision serving), parallelism (DualPipe, DeepEP) and reinforcement learning (GRPO, which deletes the critic network). DeepSeek publish weights and tech reports, though not data, under permissive licences (R1 and V4.1-Flash are MIT). That is why the line matters beyond its own weights: its layout is the template other open MoE models reuse (Kimi K2 keeps MLA and the fine-grained-plus-shared expert layout, at 384 experts), and its price cuts are where its serving arithmetic reaches the market: V2 started the Chinese API price war, and V3.2-Exp cut API prices by more than half (DeepSeek).

In September 2026 the question reached the shape of the model itself. V4.1-Flash is a 552B encoder-decoder, the first shipped at frontier scale since the field settled on decoder-only stacks, and the reason DeepSeek give is the KV cache, not quality (model card). T5 had argued the encoder-decoder case on quality grounds years earlier without moving anyone; serving arithmetic did.

Attention: MLA, then DSA, then compressed attention

The problem. Multi-head attention caches one key and one value vector per head per token. Decode reads the whole cache one token at a time, so the size of this KV cache sets serving throughput: how many sequences fit on a GPU, and what each decoded token costs in memory bandwidth. Every DeepSeek attention variant attacks that number. For head i of a query token t, standard attention computes

𝐨t,i=∑j=1tsoftmaxj(𝐪t,i⊤𝐤j,idh)𝐯j,i

Multiply by the bytes per element (2 for BF16) and by the context length to get the memory one sequence needs.

The prior answer. Multi-Query Attention (MQA) shares one K/V head across all query heads; Grouped-Query Attention (GQA) keeps one per group of query heads. Both shrink the cache linearly in the sharing factor and both pay in representational capacity: the keys and values are genuinely shared, so heads lose independent memory and quality degrades as the ratio is pushed. These, and sliding-window and linear attention across the field, are on LLM Architecture Gallery.

MLA: cache one latent per token, rebuild the heads from it

Multi-head Latent Attention (MLA), from V2 (DeepSeek-V2 paper), refuses the GQA trade. It projects the token's hidden state into one low-rank latent vector, caches only that, and reconstructs each head's keys and values through learned up-projections:

Nothing is shared between heads: each head has its own slice of WUK and WUV, reading its own directions out of the latent. The per-head structure still exists, stored compressed.

Why decompression costs no extra pass. Matrix multiplication is associative, so the key up-projection can move onto the query side:

𝐪t,i⊤𝐤j,iC=𝐪t,i⊤WiUK𝐜jKV=(WiUK⊤𝐪t,i)⊤𝐜jKV

The query is projected once into latent space and scored directly against the cached latents, so the full keys are never materialised. Values work the same way: head i's output is WUVi ∑j at,j,i cKVj, with at,j,i the attention weights, so WUVi folds into the output projection WO. The V2 paper calls this absorbing WUK into WQ and WUV into WO.

Why RoPE needs a separate key. Rotary position embeddings (RoPE) rotate queries and keys by an angle proportional to position. Applied to kCj, a position-dependent rotation would sit between qt,i and WUKi in the product above, and because matrix products do not commute the absorbed matrix would differ for every pair of positions: the keys of the whole prefix would have to be recomputed at every step. elements. MLA also compresses the queries through a second latent of dimension d′c; that saves activation memory in training and does not change the cache.

Two modes of the same layer. In training and prefill, where attention is compute-bound and many queries are processed at once, MLA materialises the per-head keys and values and runs as ordinary multi-head attention ("MHA mode"). In decode it runs absorbed ("MQA mode"): every one of the nh query heads, after projection into latent space, attends to the same cached entry of dc + dRh dimensions, which serves as the shared key, and its first dc dimensions as the shared value (DeepSeek-V3.2 paper, appendix A).

So in decode MLA is multi-query attention, over one wide entry instead of one narrow head, with per-head projections on either side that GQA does not have. That is why its quality holds where MQA's does not: the V2 paper reports MLA's cache equal to GQA with only 2.25 groups while its performance is stronger than MHA (V2 paper).

Worked example: the cache per token with V3's dimensions. V2 and V3 both use nh = 128 heads of dh = 128, a KV latent of dc = 512, a query latent of d′c = 1536 and a decoupled RoPE dimension dRh = 64; V3 has l = 61 layers (DeepSeek-V3 report).

Try: the bars are the per-layer formulas above at V3's dimensions. Slide the GQA group count to 2, then 3. MLA's 576 elements fall between them: 576 = 2 × 2.25 × 128, the V2 paper's "GQA with 2.25 groups". MQA is one group.

Across 61 layers in BF16 (2 bytes per element): MHA needs 32,768 × 61 × 2 = 3,997,696 bytes per token (3.81 MiB), GQA-8 needs 249,856 bytes (244 KiB), and MLA needs 576 × 61 × 2 = 70,272 bytes (68.6 KiB). MLA is about 57 times smaller than MHA with these dimensions and about 3.6 times smaller than 8-group GQA. At a 128K-token context (131,072 tokens), one sequence's MLA cache is 70,272 × 131,072 ≈ 9.21 × 109 bytes, 8.58 GiB, where MHA would need 488 GiB. The Cache across generations tab plots these against context length beside V4 and V4.1-Flash.

Against DeepSeek's own previous dense model, DeepSeek 67B, V2 reported a 93.3% smaller KV cache and 5.76 times the maximum generation throughput: over 50K tokens per second on one 8-GPU H800 node, with the cache further quantised to about 6 bits per element (V2 paper).

MLA costs extra projection FLOPs per attention call and a fussier kernel (the absorbed and unabsorbed paths, plus the decoupled RoPE key), and buys long contexts that are affordable to serve without GQA's quality tax.

DSA: keep the whole cache, read only the top-k

DeepSeek Sparse Attention (DSA), shipped in V3.2-Exp on 29 September 2025, attacks the other half of the bill: even a small cache is read in full by every decoded token, so cost grows linearly with context length. A cheap scoring function, the lightning indexer, ranks every cached entry against the current query (DeepSeek-V3.2 paper):

It,s=∑j=1HIwt,jIReLU(𝐪t,jI·𝐤sI)𝐮t=Attn(𝐡t,{𝐜s:It,s∈Top-k(It,:)})

ReLU is used instead of a softmax for throughput, and the indexer runs in FP8. Core attention then runs only over the top-k entries; V3.2 selects k = 2,048.

DSA is built on MLA's MQA mode, because a selected entry must be shared by all query heads for the kernel to be efficient. Two things make or break it. The indexer must be genuinely cheap (few heads, low precision), because it still scores every entry and so remains quadratic in context length overall; DSA turns core attention from O(L2) into O(Lk), with L the sequence length. And the model must be trained with the sparsity in place, so it does not depend on entries the indexer will drop. V3.2 was continued from V3.1-Terminus in two stages:

  1. Dense warm-up: freeze the model and train only the indexer, for 1,000 steps (2.1B tokens), to match the main attention distribution (the attention scores summed over heads and normalised, fitted with a KL-divergence loss).
  2. Sparse stage: 943.7B tokens in which the whole model adapts to top-2,048 selection, while the indexer, detached from the main graph, keeps fitting the attention distribution over the selected set.

Worked example. At a 128K context, core attention for one decoded token reads 2,048 of 131,072 cached entries, 1.56%; the indexer still scores all 131,072, but with a handful of FP8 heads rather than 128 full ones. Nothing is removed from memory: every entry stays resident so that it can be selected later.

Unlike MLA, which is exact up to the low-rank bottleneck, DSA is an approximation. DeepSeek reported V3.2-Exp at parity with V3.1-Terminus on standard and long-context benchmarks, and cut API prices by more than 50% when it shipped (DeepSeek announcement).
