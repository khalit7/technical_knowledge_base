Expert parallelism and the systems view

Expert parallelism (EP) shards the experts across devices: each GPU holds a subset of a layer's experts, and every token must travel to wherever its chosen experts live. The layer therefore costs two collectives. A dispatch all-to-all sends each token's hidden state to the ranks holding its k experts, the experts compute locally, and a combine all-to-all returns the outputs to be weighted and summed on the token's home rank.

𝔼[tokens per expert]=B·kNall-to-all per token per layer≈k·ddispatch elements each way

B is the number of tokens in the step (at decode, one per running sequence) and ddispatch the width of what is sent: the hidden size dmodel in most models. The first sets how skinny each expert's matmul is; the second what EP costs. Volume grows with k, not with total parameters.

Decode arithmetic for one MoE layer

Defaults are DeepSeek-V3 at 256 running sequences and reproduce the figures below by formula. Kimi K3's released code projects each token from 7,168 down to a 3,584-wide latent before the routed experts and back up after them ({{config|@k3cfg}}, {{model files|@k3files}}), so it dispatches half as many numbers per expert; that reading is ours, since the {{model card|@k3}} does not describe the mechanism.

Worked example. At decode with 256 running sequences, a dense FFN multiplies each weight by 256 tokens. With N = 256 and k = 8, each expert sees on average 256 × 8 / 256 = 8 tokens, so every weight byte read from memory serves 8 tokens instead of 256. And each token sends 8 × 7,168 = 57,344 values per MoE layer each way; at 2 bytes each that is 112 KiB out and 112 KiB back, per token, per layer.

DeepSeek-V3 bounds the expensive part with node-limited routing: each token's experts are chosen from at most 4 nodes, so cross-node (InfiniBand) traffic per token is capped however the scores fall. Because NVLink inside a node is about 3.2 times faster than InfiniBand (160 against 50 GB/s), the report notes V3 could raise k to 13 (4 nodes × 3.2 experts per node) at the same communication cost ({{V3 report|@v3h}}).

How EP composes with the rest of the parallelism stack, the part that decides whether a training run fits:

  • Data parallel, ZeRO, FSDP shard optimiser state and parameters across the data-parallel group as usual; expert weights are simply the largest thing being sharded (98% of DeepSeek-V3's total).
  • Tensor parallel splits the matrices inside each expert; EP splits which experts live where. They are orthogonal and often combined: TP inside a node on NVLink bandwidth, EP across nodes or a whole pool.
  • Pipeline parallel splits layers across stages. Its bubble and the MoE all-to-all are both latency, and overlapping them is what DeepSeek-V3's {{DualPipe|@dualpipe}} schedule exists for.

The all-to-all is a synchronising collective, so its cost is set by the slowest rank (the systems half of load balancing), and at small batch sizes it is latency-bound rather than bandwidth-bound, so it does not amortise. DeepSeek's {{DeepEP|@deepep}} is the reference open implementation: dispatch and combine kernels on NVLink and RDMA paths, overlapping communication with compute, plus a low-latency mode for decoding. With prefill/decode disaggregation (compute-bound prefill and memory-bound decode on separate pools, each batched and parallelised on its own terms), this is the reference stack for cheap high-sparsity serving. V3's decode deployment is "wide EP" at its limit: 320-way EP in which each GPU hosts one expert, 64 of the GPUs holding redundant and shared experts ({{V3 report, 3.4|@v3h}}).

What breaks at inference

Serving an MoE is a different problem from serving a dense model of the same active size, and every difference is a downside except the FLOP count.

  • Memory is priced on total parameters. A 671B/37B model needs all 671B resident across the serving pool: 1,342 GB at BF16, 671 GB at FP8, about 336 GB at 4 bits. Quantisation and MoE arrived together for this reason: expert weights are the overwhelming majority of the parameters, so per-expert INT4 or MXFP4 storage is what makes trillion-parameter checkpoints fit.
  • Each expert sees only a slice of the batch, about B · k / N: at 256 experts and k = 8, one thirty-second of it. Decode already gives small GEMMs and sparsity divides them further, so per-expert matmuls are memory-bandwidth-bound unless the aggregate batch is very large. Hence the modern serving pattern: huge batches, wide EP so each GPU's few experts get a decent share, grouped GEMM kernels fusing many small per-expert matmuls into one launch, and disaggregation so decode batches independently of prefill.
  • Load imbalance returns at request time, and it is not the training distribution. Real traffic is skewed (one language, one code style, one prompt template repeated), so a few experts run hot and their GPUs set everyone's tail latency. The standard mitigation is redundancy: replicate hot experts onto extra devices and re-place them from observed traffic. V3 re-plans its redundant experts periodically, for example every 10 minutes, and hosts 32 redundant experts in prefill ({{V3 report|@v3h}}); the placement algorithm is open as {{EPLB|@eplb}}.
  • Attention was never sparsified. MoE reduces FFN compute and leaves attention cost and the KV cache where they were. At long context these dominate, which is why the models that pushed sparsity hardest also shipped MLA, sparse attention or linear attention: two independent efficiency axes that have to be attacked separately.
  • Routing is input-dependent, so performance is input-dependent. Latency and throughput vary with what the batch contains, making capacity planning statistical and benchmark speeds sensitive to prompt mix in a way dense models are not.

Why sparsity ratios rose, and what caps them

The ratio climbed fast and then settled into a band: Mixtral at 3.6x (about 28% of parameters active) in 2023, DeepSeek-V3 at 18x at the end of 2024, Kimi K2 at about 32x in 2025 (1.04T over 32B). Frontier-band models released in 2026 span about 16x (Tencent Hy4 preview) to 33x (DeepSeek V4 Pro), 3% to 6.5% active, so 2026 moved the band's centre rather than its ceiling. The {{landscape tab|#t-land}} plots all of them.

The pull is scaling behaviour. Holding active parameters fixed and adding total parameters keeps lowering loss, because that is capacity without per-token compute. Moonshot fitted a sparsity scaling law for Kimi K2: at constant active parameters, raising the total expert count kept lowering training and validation loss, and to reach a validation loss of 1.5, sparsity 48 (8 of 384 experts) needed 1.69x, 1.39x and 1.15x fewer FLOPs than sparsity 8, 16 and 32. K2 stopped at 48 because "this gain comes with increased infrastructure complexity" ({{K2 report|@k2r}}). Note that Moonshot's "sparsity" counts experts (384 / 8), not parameters (about 32x).

Three things push back and set the ceiling. Memory: total parameters must be stored and paid for at serving time, the hard constraint and the reason native low-precision checkpoints matter. Communication: fan-out per token grows with k, and all-to-all volume with it. Expert under-training: each expert sees about k/N of the token stream, so at very high N experts risk seeing too few tokens to specialise within a fixed budget, which motivates shared experts and work on routing stability at large N. Kimi K3's Stable LatentMoE (896 experts, 16 active, 2 shared) is aimed at exactly this; Moonshot's card claims "an approximate 2.5× improvement in overall scaling efficiency over Kimi K2" ({{K3 card|@k3}}).

Read a "sparsest model" claim carefully, because three different quantities get that label. The ratio decides how much memory you buy per unit of decode speed: among models with one active count, V4 Pro leads at about 33x. The absolute active count decides what a token costs: StepFun's Step 5 Preview activates 27B of 600B, the smallest in the frontier band here although its 22x ratio is unremarkable, and Qwen3.8-Flash-Next's 6B of 125B is the smallest among the flash tier, at about 21x. A phase-dependent model breaks both rankings: DeepSeek V4.1-Flash is an encoder-decoder activating 8B of 552B in prefill (69x) and 16B in decode (35x) ({{DeepSeek changelog|@v41}}). A vendor claiming to be sparsest is usually quoting whichever of these it wins.

Trends worth knowing
  • Shared experts are a design choice, not settled practice. Qwen3 dropped them and did fine ({{Qwen3 report|@q3r}}), yet Qwen brought one back from Qwen3-Next onwards (10 routed plus 1 shared out of 512, {{Qwen3-Next card|@qnext}}), and most other lines kept them.
  • Dense warm-up layers. V3 (its first 3 of 61 layers), Kimi K2 (first 1) and GLM (first 3) keep the first blocks dense ({{V3 config|@v3cfg}}, {{K2 config|@k2cfg}}, {{GLM-5.3-Flash config|@glmfcfg}}). The usual explanation: early-layer representations are close to raw embeddings and poorly differentiated, so routing there is near-random and destabilising, and running those blocks dense costs only a little compute.
  • MoE reached small models. Gemma 4 26B-A4B ({{Gemma 4|@gem4}}), Cohere North Mini Code 30B-A3B ({{Cohere|@north}}) and gpt-oss-20b ({{model card|@oss}}) make laptop-class MoE normal: memory for the whole model, compute for a fraction, which suits a machine with plenty of unified memory and little compute.
  • Low-precision native checkpoints. K2 Thinking ships INT4 ({{card|@k2t}}), K3 MXFP4 weights with MXFP8 activations from quantisation-aware training ({{card|@k3}}), and gpt-oss MXFP4 experts ({{model card|@oss}}): the released weights are already 4-bit. Sparse plus quantised is how trillion-parameter weights stay servable.
  • Sigmoid routing plus bias balancing (the V3 lineage) has largely replaced softmax routing with heavy auxiliary losses: V3, Kimi K2 and K3, GLM-5.2 and GLM-5.3-Flash all ship scoring_func: sigmoid or its equivalent with topk_method: noaux_tc in their configs.

Common mistakes and misconceptions

"8x7B is a 56B model."
The experts share attention and embeddings, so it is 46.7B total, and only 12.9B are active per token (rebuilt in the {{Total and active|#t-par}} tab).
"Active parameters set the memory bill."
They set compute. Every parameter must be resident; a 37B-active model needs 671B of weights loaded.
"Experts specialise by topic."
Assignment is decided per token per layer by a learned router; there is no guarantee an expert maps to a human-readable domain, which is why "one expert per broad domain" is what fine-grained designs moved past. Domain-level specialisation is measurable, and is stronger with global-batch balancing, but it is a statistical lean, not a topic label.
"The z-loss balances experts."
It only bounds router logit size for numerical stability.
"The balancing loss moves tokens directly."
The dispatch fraction fi has no gradient; the loss moves only the router probabilities Pi.
"Sigmoid routing selects different experts from softmax."
From the same logits both pick the same top k; they differ in the gate weights and in what gradients and biases then do to them.
"Dropped tokens are an error."
They are silent: the token skips the FFN through the residual path, and the output just gets worse for it.
"A benchmark speed describes the model."
For MoE it describes the model under that prompt mix, batch size and expert placement, because routing and therefore throughput are input-dependent.
"Sparsest" without a quantity.
Ratio, absolute active count and per-phase active count each have different leaders; and Moonshot's "sparsity 48" counts experts, not parameters.
