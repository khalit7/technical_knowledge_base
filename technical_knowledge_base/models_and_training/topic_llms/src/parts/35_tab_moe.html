Inside one MoE layer

Only the feed-forward network (FFN) of a transformer block becomes sparse: it is replaced by N independent FFNs, the experts, plus a small trainable router. Attention, normalisation and the residual stream stay dense and shared. For every token the router scores every expert, keeps the top k, and the layer outputs the sum of those experts' outputs weighted by the router's own scores.

Expert
In modern models a SwiGLU block with three weight matrices (gate, up and down projections), so it holds 3 · dmodel · dff parameters: dmodel is the hidden size, dff the expert's inner width, the same as a dense model's FFN or narrower.
Top-k routing
Each token is processed by the k experts with the highest scores; the other N − k are skipped for that token.
Gate weight
The normalised router score gi that multiplies expert i's output. It is the router's only path to a gradient.
Shared expert
An expert that bypasses the router and runs for every token (drawn in green above).
Load balance
How evenly tokens spread across experts. An expert receiving far more than its share is hot; one receiving almost nothing has collapsed.
Capacity factor (CF)
A multiplier on an expert's average load that fixes the size of its token buffer; tokens beyond the buffer are dropped. A dropless implementation has no such buffer.
Expert parallelism (EP)
Sharding a layer's experts across devices, so tokens travel to their experts and back through all-to-all collectives.

What sparsity costs, and what the rest of this tab is about: memory is priced on total parameters while throughput is priced on active ones, since every parameter must be resident at serving time; routing adds two all-to-all collectives per layer; per-expert matrix multiplications (GEMMs) are small and skinny, so utilisation is worse than the FLOP count suggests; and a discrete decision inside an otherwise differentiable model is a permanent source of instability.

The mechanism, step by step

Per token with hidden state h, an MoE layer does four things:

  1. Score. Router logits s = Wrh, one per expert. Wr is a single dmodel × N matrix, typically well under 0.1% of the layer: in DeepSeek-V3 it is 7,168 × 256 = 1.8M parameters against 11.32B for the whole MoE layer, 0.016% (rebuilt below). The router is free in every sense except the trouble it causes.
  2. Normalise. Softmax over all N classically, or an independent sigmoid per expert in the DeepSeek-V3 lineage. Both are monotonic in the logit, so from the same logits they select the same experts; they differ in the gate values they hand to step 4.
  3. Select. Keep the top k, and renormalise those k weights so they sum to one.
  4. Combine. Output y = Σi ∈ top-k gi Ei(h), added back into the residual stream.
Why routing collapses unless something stops it
The gate weight gi is the only path by which the router learns anything. Selection is a discrete, argmax-like operation with no gradient, so the router receives gradient only through the size of gi on the experts actually chosen. An expert that stops being selected stops producing any evidence that it would have been good. That is the structural reason routing collapses, and the reason every balancing technique below exists.

Softmax and sigmoid routers

With softmax scoring and top-k renormalisation, where 𝒯 is the set of the k experts with the largest logits:

pi=esi∑j=1Nesjgi=pi∑j∈𝒯pj(i∈𝒯)y=h+∑i∈𝒯giEi(h)

si is expert i's router logit, pi its softmax probability over all N experts, gi the renormalised gate weight, Ei(h) expert i's output, and the leading h is the residual connection. Renormalised this way, gi is exactly a softmax over the k selected logits, which is how Mixtral writes it: Softmax(TopK(x · Wg)), every logit outside the top k set to minus infinity ({{Mixtral paper|https://arxiv.org/abs/2401.04088}}).

With sigmoid scoring, as in DeepSeek-V3 ({{report, section 2.1.2|https://arxiv.org/html/2412.19437v1}}):

σi=11+e−sigi=σi∑j∈𝒯σj(i∈𝒯)

σi is expert i's independent affinity in (0, 1). A softmax probability is a share of one distribution over all N experts, so it averages 1/N and shrinks as experts are added; a sigmoid affinity depends on its own logit only, whatever N is. After renormalisation softmax gates are exponentially peaked (a logit gap of 1 is a weight ratio of e ≈ 2.72), sigmoid gates much flatter. The usual reading of why high-k fine-grained designs moved to sigmoid plus renormalisation as k climbed into double digits is the first property: scores that do not compete or dilute as N grows. DeepSeek-V3's report states the choice without arguing it.

How many experts per token

The router has three jobs that pull against each other: score experts per token, decide how many to activate, and keep the resulting traffic spread across hardware. Which lab ships which style is compared on the {{Reading tab|#t-read}}; here is what each style buys mechanically.

Noisy top-k (2017)

Gaussian noise added to the scores before selection, so nearly tied experts share the traffic instead of the marginally better one winning every time: balancing in the selection rule rather than in the loss, at a little routing precision ({{Shazeer et al., 2017|https://arxiv.org/abs/1701.06538}}).

Top-2 (GShard, Mixtral)

The default for years ({{GShard|https://arxiv.org/abs/2006.16668}}). Twice top-1's expert FLOPs; buys a smoother layer function (the output can interpolate between two experts) and a better-conditioned router, because two gate weights give it a comparison rather than a single scalar.

Top-1 (Switch)

Minimum FLOPs, minimum dispatch, one expert's weights touched. No second opinion within a token, and the single gate weight is the only learning signal, so it depends most on aggressive balancing. Switch's real contribution was showing that k = 1 works at all, against the prior assumption that k ≥ 2 was needed for a usable router signal ({{Switch Transformer|https://arxiv.org/abs/2101.03961}}).

Fine-grained top-k plus shared experts

Split the same expert budget into many narrower experts and raise k to match ({{DeepSeekMoE|https://arxiv.org/abs/2401.06066}}). Active parameters stay about constant while the combinations the router can express grow: C(256, 8) ≈ 4.1 × 1014 against C(8, 2) = 28. Always-on shared experts absorb what every token needs (general syntax, frequent patterns), so routed experts spend capacity on specialising. The cost is hardware: smaller per-expert GEMMs and wider all-to-all fan-out per token. The granularity slider in Rebuilt from configs shows the trade on a real configuration.

Load balancing

Left alone, routing collapses. An expert chosen slightly more often receives more gradient, improves, and is chosen more often still, while the rest starve and never generate evidence that they were worth reviving. That is a quality problem, because effective capacity shrinks to the experts that survived, and at the same time a systems problem: with experts sharded across GPUs, an overloaded expert stalls its whole layer, since the all-to-all waits on the slowest shard, and hot experts overrun whatever per-expert memory was allocated.

The fixes, in the order they were invented, with what each costs:

  1. Noisy gating. Randomness in the selection rule redistributes tokens near a decision boundary. Cheap and unbiased, but it touches only marginal cases and cannot rescue an expert that has fallen far behind.
  2. Auxiliary load-balancing loss ({{Switch Transformer|https://arxiv.org/abs/2101.03961}}):
    ℒaux=α·N·∑i=1NfiPifi=1T∑x∈ℬ𝟙{arg maxp(x)=i}Pi=1T∑x∈ℬpi(x)

    ℬ is the batch of T tokens, fi the fraction of tokens dispatched to expert i (a count, with no gradient), Pi the mean router probability expert i received (differentiable), and α the coefficient: Switch used 10−2, the value it found "balanced load quickly without interfering with training loss". The factor N makes the loss equal α under perfectly uniform routing whatever the expert count; top-k variants count all T · k assignments in fi and rescale so the uniform case stays constant. Worked example: with N = 4 and uniform routing, fi = Pi = 0.25, so ℒ = α × 4 × (4 × 0.0625) = α. Collapsed onto expert 1 with f = (1, 0, 0, 0) and P = (0.7, 0.1, 0.1, 0.1): α × 4 × 0.7 = 2.8α. The gradient flows only through P1, pushing the router's probability for expert 1 down.

    The product is smallest when both are uniform, so the term pushes the router toward even traffic, but it nudges the router's beliefs rather than editing the assignment. Its cost is a second objective beside language modelling, and the two conflict wherever a token genuinely belongs to one expert: the quality tax the aux-loss-free method later removed.
  3. Device-level balancing loss. {{DeepSeekMoE|https://arxiv.org/abs/2401.06066}} groups experts by the device they live on and balances traffic across groups rather than individual experts, conceding that per-expert uniformity was never the goal: what matters is that no GPU is the straggler in the all-to-all. It buys real throughput and leaves the router freer within a device.
  4. Capacity factor. A hard cap on how many tokens any one expert accepts; see Capacity below.
  5. Aux-loss-free balancing (DeepSeek-V3, now on nearly every open MoE model card from 2025 on). Keep a per-expert bias bi added to the routing score only for top-k selection: selection uses σi + bi, the gate weight uses σi alone, and after each step
    bi←bi−γ·sign(ci−c‾)

    ci is the number of tokens expert i received in the step, c̄ the mean over experts, γ the bias update speed. V3 set γ = 0.001 for the first 14.3T training tokens and 0 for the last 500B, kept a sequence-wise balance loss of the same α Σ fi Pi form with α = 0.0001 "just to avoid extreme imbalance", and drops no tokens in training or inference ({{V3 report|https://arxiv.org/html/2412.19437v1}}).

    Because the bias never enters the gate weight, it never appears in the gradient: balancing moves the decision boundary instead of adding a competing objective, so the quality tax of point 2 disappears.
Often confused with load balancing: the router z-loss
{{ST-MoE|https://arxiv.org/abs/2202.08906}} adds ℒz = (1/B) Σi (log Σj exj(i))2 with coefficient cz = 0.001, where B is the number of tokens and xj(i) token i's logit for expert j. It balances nothing: it keeps the logits small, because large router logits with bf16 exponentials give roundoff blowups and loss spikes. In ST-MoE's stability study it made all three runs stable, as tight update clipping also did, but without clipping's significant quality cost. It costs nearly nothing, so add it whichever balancing method is used.

Balancing scope: per sequence, per micro-batch or global batch

Which tokens the balance is measured over matters as much as the method. A load-balancing loss is usually computed per micro-batch, and a micro-batch for a billion-scale model holds only a few sequences, often packed from one domain, so it is nearly a sequence-level constraint: even a pure code sequence is pushed to spread over every expert. Qwen's {{global-batch paper|https://arxiv.org/abs/2501.11873}} synchronises the counts fi across data-parallel ranks (and, with a buffer, across gradient-accumulation steps) so balance is demanded only over the diverse global batch. It reports about 0.1 lower pre-training perplexity and about 2 points on benchmarks, and expert specialisation by domain that micro-batch balancing suppresses; Qwen3 adopted it ({{Qwen3 report|https://arxiv.org/abs/2505.09388}}). DeepSeek reached the same conclusion from the other side: its aux-loss-free method balances per batch, and a batch-wise auxiliary loss matched it, with validation losses of 2.258 (sequence-wise loss), 2.253 (aux-loss-free) and 2.253 (batch-wise loss) on 1B MoE models, and 2.085 against 2.080 and 2.080 at 3B ({{V3 report, 4.5.3|https://arxiv.org/html/2412.19437v1}}).

The same routing, judged at two scopes

Four micro-batches, each from one domain, routed over four experts (illustrative). Slide specialisation up: each domain sends more of its tokens to "its" expert. The loss is computed with Pi = fi for simplicity and shown as a multiple of α (1.0 is perfectly balanced).

The price of a wider scope: a cross-rank reduction of routing counts every step, and a router balanced over the corpus while individual sequences, and so individual devices at serving time, are not. DeepSeek names the same two risks for batch-wise methods: imbalance within certain sequences or small batches, and domain shift at inference.

Capacity factors and dropped tokens

Training an MoE efficiently with static shapes means allocating a fixed buffer per expert before knowing how many tokens will choose it:

C=CF·k·TN

C is the number of token slots in each expert's buffer, CF the capacity factor, T the tokens in the batch, k the experts per token, N the experts. Switch, being top-1, writes it as tokens per batch divided by number of experts, times capacity factor. 1.0 provisions exactly the average; ST-MoE trained at 1.25 and evaluated at 2.0 ({{ST-MoE|https://arxiv.org/abs/2202.08906}}).

Worked example. A batch of T = 4,096 tokens, N = 64 experts, k = 2, CF = 1.25: average load 2 × 4,096 / 64 = 128 tokens, capacity C = 1.25 × 128 = 160 slots. A hot expert that attracts 200 tokens drops 40 of them (20% of its traffic); one that attracts 60 leaves 100 padded slots computed for nothing. CF = 2.0 gives 256 slots, no drops here, and 60% more buffer on every expert.

Raising CF costs memory and padding compute in proportion, because buffers are allocated and processed whether or not they fill. Lowering it drops tokens arriving at a full expert: in GShard and Switch they skip the layer, passing through on the residual connection with no FFN applied. Switch also tried rerouting overflow to the next-best expert ("No-Token-Left-Behind") and found no empirical benefit. A dropped token is not a crash but a silently weaker forward pass, and drops concentrate on exactly the tokens that wanted the popular experts.

Two consequences. Drop behaviour differs between training and inference, since inference batches have different composition and often no capacity limit at all, so a model trained with heavy dropping is evaluated in a regime it was not trained in. And the problem is an artefact of static buffers: dropless MoE ({{MegaBlocks|https://arxiv.org/abs/2211.15841}}) computes the experts as block-sparse matrix multiplication over ragged per-expert token groups, so nothing is padded and nothing is dropped. Modern training stacks therefore discuss grouped GEMM kernels rather than capacity factors, which survive mostly in older recipes and in inference-time admission control.

Expert parallelism and the systems view

Expert parallelism (EP) shards the experts across devices: each GPU holds a subset of a layer's experts, and every token must travel to wherever its chosen experts live. The layer therefore costs two collectives. A dispatch all-to-all sends each token's hidden state to the ranks holding its k experts, the experts compute locally, and a combine all-to-all returns the outputs to be weighted and summed on the token's home rank.

𝔼[tokens per expert]=B·kNall-to-all per token per layer≈k·ddispatch elements each way

B is the number of tokens in the step (at decode, one per running sequence) and ddispatch the width of what is sent: the hidden size dmodel in most models. The first sets how skinny each expert's matmul is; the second what EP costs. Volume grows with k, not with total parameters.

Decode arithmetic for one MoE layer

Defaults are DeepSeek-V3 at 256 running sequences and reproduce the worked example below by formula. Kimi K3's released code projects each token from 7,168 down to a 3,584-wide latent before the routed experts and back up after them ({{config|https://huggingface.co/moonshotai/Kimi-K3/blob/main/config.json}}, {{model files|https://huggingface.co/moonshotai/Kimi-K3/tree/main}}), so it dispatches half as many numbers per expert; that reading is ours, since the {{model card|https://huggingface.co/moonshotai/Kimi-K3}} does not describe the mechanism.

Worked example. At decode with 256 running sequences, a dense FFN multiplies each weight by 256 tokens. With N = 256 and k = 8, each expert sees on average 256 × 8 / 256 = 8 tokens, so every weight byte read from memory serves 8 tokens instead of 256. And each token sends 8 × 7,168 = 57,344 values per MoE layer each way; at 2 bytes each that is 112 KiB out and 112 KiB back, per token, per layer.

DeepSeek-V3 bounds the expensive part with node-limited routing: each token's experts are chosen from at most 4 nodes, so cross-node (InfiniBand) traffic per token is capped however the scores fall. Because NVLink inside a node is about 3.2 times faster than InfiniBand (160 against 50 GB/s), the report notes V3 could raise k to 13 (4 nodes × 3.2 experts per node) at the same communication cost ({{V3 report|https://arxiv.org/html/2412.19437v1}}).

How EP composes with the rest of the parallelism stack, the part that decides whether a training run fits:

  • Data parallel, ZeRO, FSDP shard optimiser state and parameters across the data-parallel group as usual; expert weights are simply the largest thing being sharded (98% of DeepSeek-V3's total).
  • Tensor parallel splits the matrices inside each expert; EP splits which experts live where. They are orthogonal and often combined: TP inside a node on NVLink bandwidth, EP across nodes or a whole pool.
  • Pipeline parallel splits layers across stages. Its bubble and the MoE all-to-all are both latency, and overlapping them is what DeepSeek-V3's {{DualPipe|https://github.com/deepseek-ai/DualPipe}} schedule exists for.

The all-to-all is a synchronising collective, so its cost is set by the slowest rank (the systems half of load balancing), and at small batch sizes it is latency-bound rather than bandwidth-bound, so it does not amortise. DeepSeek's {{DeepEP|https://github.com/deepseek-ai/DeepEP}} is the reference open implementation: dispatch and combine kernels on NVLink and RDMA paths, overlapping communication with compute, plus a low-latency mode for decoding. With prefill/decode disaggregation (compute-bound prefill and memory-bound decode on separate pools, each batched and parallelised on its own terms), this is the reference stack for cheap high-sparsity serving. V3's decode deployment is "wide EP" at its limit: 320-way EP in which each GPU hosts one expert, 64 of the GPUs holding redundant and shared experts ({{V3 report, 3.4|https://arxiv.org/html/2412.19437v1}}).

What breaks at inference

Serving an MoE is a different problem from serving a dense model of the same active size, and every difference is a downside except the FLOP count. The weight-memory bill itself is on the Reading tab's {{Cost to serve|#t-read}} calculator; these are the rest.

  • Expert weights are what gets quantised. Experts are the overwhelming majority of the parameters (98% of DeepSeek-V3's total, rebuilt below), so per-expert INT4 or MXFP4 storage is what makes trillion-parameter checkpoints fit; quantisation and MoE arrived together for this reason. A 671B/37B model is 1,342 GB at BF16, 671 GB at FP8, about 336 GB at 4 bits.
  • Each expert sees only a slice of the batch, about B · k / N: at 256 experts and k = 8, one thirty-second of it. Decode already gives small GEMMs and sparsity divides them further, so per-expert matmuls are memory-bandwidth-bound unless the aggregate batch is very large. Hence the modern serving pattern: huge batches, wide EP so each GPU's few experts get a decent share, grouped GEMM kernels fusing many small per-expert matmuls into one launch, and disaggregation so decode batches independently of prefill.
  • Load imbalance returns at request time, and it is not the training distribution. Real traffic is skewed (one language, one code style, one prompt template repeated), so a few experts run hot and their GPUs set everyone's tail latency. The standard mitigation is redundancy: replicate hot experts onto extra devices and re-place them from observed traffic. V3 re-plans its redundant experts periodically, for example every 10 minutes, and hosts 32 redundant experts in prefill ({{V3 report|https://arxiv.org/html/2412.19437v1}}); the placement algorithm is open as {{EPLB|https://github.com/deepseek-ai/EPLB}}.
  • Attention was never sparsified. MoE reduces FFN compute and leaves attention cost and the KV cache where they were, which is why the models that pushed sparsity hardest also shipped the cache-shrinking attention compared on the Reading tab: two independent efficiency axes that have to be attacked separately.
  • Routing is input-dependent, so performance is input-dependent. Latency and throughput vary with what the batch contains, making capacity planning statistical and benchmark speeds sensitive to prompt mix in a way dense models are not.

Total and active parameters, rebuilt from configuration files

A model card's two numbers follow from its configuration file. Pick a model: every bar below is computed from that model's released config.json with the formula, then compared with the figure the lab publishes. The labs' published counts on the Reading tab's scatter are the same quantities.

Ptotal=Lmoe((N+Ns)PE+dmodelN)+PrestPactive=Lmoe((k+Ns)PE+dmodelN)+Prest

Lmoe is the number of MoE layers, Ns the shared experts, PE = 3 dmodel dff one SwiGLU expert, dmodelN the router, and Prest everything dense: attention in every layer, embeddings and output head, and any dense FFN layers. Sparsity ratio = Ptotal / Pactive. Small terms the formula leaves out (norms, biases, gpt-oss's attention sinks) are included in the computation.

Every preset against its published figures

Worked example: DeepSeek-V3's 671B and 37B, step by step

The released config ({{config.json|https://huggingface.co/deepseek-ai/DeepSeek-V3/raw/main/config.json}}) gives dmodel = 7,168, 61 layers of which the first 3 are dense (FFN width 18,432), expert width dff = 2,048, 256 routed experts with 8 active plus 1 shared, a 129,280-token vocabulary with an untied output head, and Multi-head Latent Attention (MLA) with 128 heads, query compression 1,536, key-value compression 512, and head dimensions 128 plus 64 for the rotary part.

  1. One expert: 3 × 7,168 × 2,048 = 44,040,192, about 44.0M parameters.
  2. One MoE layer: 257 × 44.04M + 7,168 × 256 (router) = 11,318.4M + 1.8M, about 11.32B. The router is 0.016% of it.
  3. All 58 MoE layers: about 656.6B.
  4. The dense parts: MLA at about 187.1M per layer times 61 is 11.41B; three dense FFNs at 3 × 7,168 × 18,432 each is 1.19B; input embedding plus output head at 2 × 129,280 × 7,168 is 1.85B. Together 14.46B.
  5. Total: 656.6 + 14.46 ≈ 671.0B. The 685B on the Hugging Face model card is this 671B plus the 14B multi-token-prediction module, which is not part of the main model ({{DeepSeek-V3 README|https://github.com/deepseek-ai/DeepSeek-V3}}).
  6. Active: each MoE layer runs 9 experts (8 routed plus 1 shared), 58 × (9 × 44.04M + 1.8M) = 23.09B, plus the same 14.46B dense, ≈ 37.6B.
  7. Sparsity ratio 671.0 / 37.6 ≈ 17.9. Weights: 1,342 GB at BF16, 671 GB at FP8, about 336 GB at 4 bits. Compute per token: that of a 37.6B dense model.

Two things fall out. Experts (routed plus shared) are 98% of the total but 61% of the active count, so attention and embeddings, invisible in the total, are a large share of what a token costs. And the V3 report's 671B total and 37B activated are reproduced from the architecture alone.

Worked example: why Mixtral 8x7B is 46.7B, not 56B
From the paper's Table 1 ({{Mixtral paper|https://arxiv.org/abs/2401.04088}}): dmodel = 4,096, 32 layers, dff = 14,336, 8 experts, top-2, grouped-query attention with 32 query and 8 key-value heads of dimension 128, vocabulary 32,000. One expert is 3 × 4,096 × 14,336 = 176.2M; experts total 32 × 8 × 176.2M = 45.1B; attention 32 × 41.9M = 1.34B; embeddings 0.26B. Total 46.7B, active 32 × 2 × 176.2M + 1.34 + 0.26 = 12.9B, ratio 3.6x.
Dense warm-up layers
V3 (its first 3 of 61 layers), Kimi K2 (first 1) and GLM (first 3) keep the first blocks dense ({{V3 config|https://huggingface.co/deepseek-ai/DeepSeek-V3/raw/main/config.json}}, {{K2 config|https://huggingface.co/moonshotai/Kimi-K2-Instruct/blob/main/config.json}}, {{GLM-5.3-Flash config|https://huggingface.co/zai-org/GLM-5.3-Flash/blob/main/config.json}}); Llama 4 Maverick alternates, MoE in every second layer ({{config|https://huggingface.co/unsloth/Llama-4-Maverick-17B-128E-Instruct/blob/main/config.json}}). The usual explanation for warm-up layers: early-layer representations are close to raw embeddings and poorly differentiated, so routing there is near-random and destabilising, and running those blocks dense costs only a little compute.

Mechanism mistakes

The comparison-level mistakes (total parameters as cost, 8x7B as 56B) are on the Reading tab.

"Experts specialise by topic."
Assignment is decided per token per layer by a learned router; there is no guarantee an expert maps to a human-readable domain, which is why "one expert per broad domain" is what fine-grained designs moved past. Domain-level specialisation is measurable, and is stronger with global-batch balancing, but it is a statistical lean, not a topic label.
"The z-loss balances experts."
It only bounds router logit size for numerical stability.
"The balancing loss moves tokens directly."
The dispatch fraction fi has no gradient; the loss moves only the router probabilities Pi.
"Sigmoid routing selects different experts from softmax."
From the same logits both pick the same top k; they differ in the gate weights and in what gradients and biases then do to them.
"Dropped tokens are an error."
They are silent: the token skips the FFN through the residual path, and the output just gets worse for it.
