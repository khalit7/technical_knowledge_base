7. PII scrubbing: what two regular expressions catch and miss

The problem. Web text contains personal data: email addresses, phone numbers, home addresses, names. A model can memorise and repeat it. How it works in FineWeb. datatrove's PIIFormatter (pipeline/formatters/pii.py:42-94) runs two regular expressions: one for email addresses (replaced in turn by email@example.com and firstname.lastname@example.org) and one for IPv4 addresses, replaced only when Python's ipaddress says they are global (pii.py:34-39), so 192.168.x.x and other private addresses stay. Nothing else is touched. Cost: two regex passes per document; nothing is removed, text is edited.

When it matters and how to check it

Regex scrubbing is cheap and predictable, which is why FineWeb uses it; its limits are in the counts above. Phone numbers, street addresses and social handles remain, and almost half of what the email regex replaces (66 of 140) are role addresses of organisations (info@, sales@), not people. Stronger options cost more: NER-based tools such as Microsoft Presidio find names and addresses, with false positives of their own, and one way to afford them is to run them only on the higher-risk slices (forums, comments). To check a scrubber, count matches of independent detectors after it, as here, and read a sample.

8. Read the source: how datatrove runs a pipeline

Everything above is a handful of Python classes. Reading them is the fastest way to know what a pipeline really does (all paths under src/datatrove/, tag v0.10.1, commit 1977fbb0).

  • A pipeline is a list of steps, and documents stream through it. Each step is a PipelineStep whose run(data, rank, world_size) (pipeline/base.py:99) takes a generator of Document objects and yields documents; the executor chains them, so nothing is held in memory between steps. A reader is the first step and ignores its input.
  • Filters subclass BaseFilter: filter(doc) returns True or (False, reason); the base class counts the reason in its stats and, if given an exclusion_writer, writes the dropped document with metadata.filter_reason (pipeline/filters/base_filter.py:62-82). That is how every removed document in this tab could be read back.
  • Extractors run each page in a sandboxed subprocess with a wall-clock timeout (pipeline/extractors/base.py:40-65, the sandbox class at line 85; trafilatura's options at extractors/trafilatura.py:22-55). On macOS the sandbox needs the fork start method, one of the workarounds in this lab's scripts.
  • The executor splits input files into tasks (FineWeb used 8,000 per crawl on a Slurm cluster, examples/fineweb.py:65); each task writes its own output shard and a stats JSON, which is where the per-stage counts in section 1 come from. The same pipeline runs locally (LocalPipelineExecutor), on Slurm or on Ray, which is why a laptop run reproduces the cluster run per document.
  • MinHash is four pipeline stages (signatures, buckets, clustering, filtering) because each needs all the output of the previous one: see the {{Dedup lab|#t-dedup}}.

Each rule's file and line range is shown under the rule explorer chart; language ID at filters/language_filter.py:43-65 and utils/lid.py:53-59; URL filter at filters/url_filter.py:80-132.

9. Common mistakes, and interview questions

Trusting a library default or an example script
The datatrove FineWeb example became multilingual when a default changed (section 4); its quality filter uses 0.01 where the paper says 0.1, and C4's sentence minimum is 5 where the T5 paper says 3 (section 5). Pin versions, pass every argument that matters, and diff your output against a known reference (here, FineWeb's own documents from the same file: 2,403 of 2,425 reproduced).
Using WET text because it is already extracted
Measured here: 877 English documents survive the filters from WET text against 2,692 from trafilatura on the same pages. WET's menus and widgets make the repetition and line rules fire, and what survives carries boilerplate. FineWeb (trafilatura) and DCLM (resiliparse) both re-extract from WARC.
Letting machine load change the dataset
A per-page timeout depends on wall-clock time, so a busy node drops more pages: 199 timeouts in run0, 12 of which FineWeb kept. Size timeouts generously, log them as a stage, and rerun them.
Reading a drop count as a quality measure
A rule that removes 173 documents can be wrong on most of them (the 0.01 duplicated-line rule: 6 wrong of 8 labelled). Label a sample on each side of every threshold before trusting it.
Tuning thresholds on one file and calling it done
One WARC cannot show cross-file duplication, and rare rules (lorem ipsum, curly brackets) fire a handful of times. Check a decision on several files and, for dedup, on the whole crawl.
Calling regex scrubbing "PII removal"
Two regexes catch emails and public IPs only; phone numbers, addresses and names remain (section 7). Say exactly what was scrubbed.

Interview questions, with short answers

Why does the URL filter run before extraction, and language ID before the quality rules?
Cheapest first: each stage should remove as much as it can before a more expensive one runs. A URL lookup costs microseconds and reads no content; extraction costs milliseconds per page; language ID is cheap and removes about 64% of extracted documents in a crawl like this; spaCy-tokenised rules and neural classifiers are the most expensive, so they see the least.
FineWeb's WET ablation lost to trafilatura on WARC. Why, mechanically?
WET keeps every visible string, so documents carry navigation, cookie banners and widget text. That both adds low-value tokens and changes the statistics the filters see (duplicate lines, short lines, lines without punctuation), so some good pages are dropped and many bad ones survive. On our file the same filters keep 877 documents from WET against 2,692 from trafilatura.
How would you choose a threshold for a new heuristic rule?
FineWeb's method: compare the rule's distribution on a high-quality and a low-quality reference (they used their dedup ablations), pick a cut where they separate, then train small models on data with and without the rule and compare benchmark scores. Before that, label a sample of what it drops near the threshold, and report the share of tokens it removes.
Your pipeline's output differs from a published dataset built with the same code. Where do you look?
Versions and defaults (library and model versions, changed defaults), arguments the example omits, extraction timeouts and failures, dedup scope (per file, per crawl, global), and order of stages. Join on a stable id (here WARC-Record-ID) and inspect the documents in one set and not the other, stage by stage.
Design: you have one week of CPU to turn one Common Crawl crawl into an English pretraining set. What runs where?
Read WARCs from object storage in many parallel tasks (one shard of files per task); per document, in order: URL blocklist, extraction (resiliparse if CPU is the constraint, about 8 times faster per DCLM; trafilatura if precision matters more), lid.176, repetition and quality rules, PII regexes, writing the survivors with their stats; then MinHash per crawl as a separate multi-stage job; then a model-based quality classifier on the survivors (GPU if available). Keep every removed document with its reason, a stats file per task, and a labelled sample per rule.
