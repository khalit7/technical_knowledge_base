10. Storage, loading and the tools that run it

How the data is stored. The pipeline and the training run want different formats.

  • While curating: one document per record with its metadata (URL, crawl, language score, quality score, duplicate-cluster id), in compressed JSONL (one JSON object per line, gzip or zstd) or Parquet (a columnar format: a reader can load only the columns it needs, and per-column compression is good). FineWeb and FineWeb-Edu ship as Parquet and DCLM-baseline as zstd-compressed JSONL; datatrove and the Dolma toolkit read and write both.
  • For training: documents are tokenized once and stored as flat arrays of token ids (2 bytes per token when the vocabulary has fewer than 65,536 entries, 4 bytes otherwise: Qwen3's vocabulary is larger, and storing its ids as 16-bit integers would corrupt 97% of FineWeb documents, as measured by {{Storage and loading at scale|n:3f95c17b0d0d81398782efcb29d950d4}}), memory-mapped so a data-loader worker reads any slice without loading the file, or packed into streaming shards (MosaicML Streaming's MDS, WebDataset's tar files) that workers fetch from object storage and can resume deterministically after a crash.
  • The loader samples from per-domain shards with the mixture weights of section 7, concatenates documents separated by an end-of-text token, and cuts the stream into fixed-length sequences (packing). Shuffling is approximate at this scale: shuffle the order of shards, then shuffle inside a buffer.

Two consequences matter in practice. When the mixing weights are applied at load time rather than baked into the files (both are common), changing the mix needs no reprocessing. And the token count you plan with depends on the tokenizer: the same text is a different number of tokens for GPT-2, Llama or Qwen tokenizers, which is why every corpus size in this page says whose count it is (tokenizers: {{Tokenizers|n:3c65c17b0d0d817187bcd94a1b0f15ea}}).

The tools. Three open frameworks run whole pipelines; teams with existing big-data infrastructure also write their own stages on Spark or Ray.

ToolWhat it isReach for it when
datatrove (Hugging Face)Python pipeline blocks (readers, extractors, filters, MinHash and exact dedup, tokenizers, writers) with local, Slurm and Ray executors; FineWeb's pipeline is its example script. v0.10.1 read for this pageyou want a FineWeb-style pipeline you can read and change; CPU clusters
Dolma toolkit (AI2)Rust-backed: taggers attach scores to every document (Gopher, C4 and quality-model taggers), then a mixer filters and samples by those scores; a Rust Bloom filter for dedup and decontaminationyou want "tag once, filter many ways" and very fast tagging
NeMo Curator (NVIDIA)GPU-accelerated curation for text, image, video and audio; since release 26.02 every pipeline runs on Ray; fuzzy and semantic dedup, classifiers, PII and synthetic-data stagesyou have GPUs to spare and the dedup or classifier stage dominates your cost
Spark or Ray, customYour own stages on a general distributed engineyou already run that infrastructure or need logic no framework has
