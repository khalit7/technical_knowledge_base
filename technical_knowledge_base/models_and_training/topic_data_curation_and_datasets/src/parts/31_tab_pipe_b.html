1. The funnel: 20,991 pages in, 2,617 documents out

The problem. A crawl is mostly not training text: menus, shop listings, error pages, other languages, spam, near copies. A curation pipeline removes it in stages, and the order matters because the stages cost very different amounts: a URL lookup costs microseconds, HTML extraction milliseconds, a neural quality classifier far more. So the cheap, high-recall stages go first and the expensive ones see only what survives. How it works here: the stages of datatrove's FineWeb example (examples/fineweb.py:33-73), run on one WARC file with languages=['en'] (see section 4 for why that argument matters), then MinHash deduplication inside this file and PII scrubbing. Every removed document was written to disk with the rule that removed it, so each bar below can be opened in the later sections.

What one file cannot show

One WARC is 1/90,000 of the crawl. Within-file MinHash finds only copies inside this file (75 documents); FineWeb ran MinHash over each whole crawl, and Dolma 3 reports exact dedup removing 67% of what its heuristics kept, then MinHash another 23% (published, Dolma 3 pool README). That is why our final set holds 214 documents that FineWeb does not: the main expected cause is copies of them in other files of the crawl. Of the 2,425 documents FineWeb kept from this file, 2,403 (99.1%) are in our output, so the per-document filtering reproduces closely.
