Bloom filters: exact dedup in fixed memory

The problem. Exact dedup needs a set of every hash seen so far: billions of entries. The tool. A Bloom filter is an array of m bits and k hash functions. Adding an item sets the k bits its hashes point to; testing an item checks whether all k are set. A new item can find all its bits already set by others (a false positive: "seen" when it was not), but a seen item is never missed. The Dolma toolkit streams documents through one: for each paragraph, if the filter says "seen", mark it a duplicate, otherwise add it.

A 32-bit filter, one paragraph at a time

measured paragraphs: lines from the running example that recur on many sites (the table in the Exact section), fed in a fixed order with repeats. The hash functions here are FNV-1a with different seeds, computed live; Dolma uses k seeded ahash hashers (bloom_filter.rs:181-212). With 32 bits the filter fills fast and starts saying "seen" for new paragraphs: watch for red.

The formula and the real tool. After n distinct items, a fresh item collides with probability about (1 − e−kn/m)k, smallest at k = (m/n) ln 2. We ran the real Dolma toolkit (dolma 1.2.1, paragraph mode) on the 743,644 non-blank lines of the 19,241 extracted documents, whose exact count of repeats is 256,024 (487,620 distinct), with filters from 64 KiB to 64 MiB. Because a Bloom filter never misses a repeat, every mark beyond 256,024 is a false positive.

measured three runs per size (Dolma draws new random hash seeds for every filter, bloom_filter.rs:76-98, so false positives differ run to run); expected = the sum over the 487,620 new paragraphs of the formula at the filter's fill when each arrives (the filter fills as it streams), with Dolma's own choice of k = ⌈(m/n) ln 2⌉ (bloom_filter.rs:27-32). Measured and expected agree within about 1%. At 1 MiB (17 bits per distinct paragraph) 11 to 14 paragraphs of 487,620 are wrongly dropped; at 64 KiB a third of all new paragraphs would be.

Found in the source: --dedupe.min_words switches paragraph dedup off
In deduper.rs (lines 338-380) the word-count check is the first branch of an if / else if / else, and the deduplication sits in the final else, so whenever min_words is above 0 no paragraph ever reaches it. Measured: the same 64 MiB run with --dedupe.min_words 1 marks 0 paragraphs instead of 256,024. Document mode has the same branch structure (lines 261-277; read, not run). Two smaller notes: when no size is given, Dolma sizes the filter by doubling from 1 MiB until the formula meets the target rate (bloom_filter.rs:45-61), so small runs get at least 1 MiB; and datatrove's own Bloom filter caps its size with MAX_HASH = 1 << 32 - 1 (bloom_filter.py:20), which Python parses as 1 << 31.

Two other uses of the same structure: Dolma seeds a filter with benchmark test items and flags any training paragraph that hits it (decontamination); DCLM used a Bloom-filter variant for near duplicates, marking a document when most of its n-grams have been seen before, because it "scales more easily to datasets surpassing 10TB" than MinHash (published DCLM Section 4.3). datatrove ships a similar step, SingleBloomFilter: 13-word shingles, a document is a duplicate when more than 80% of them were seen (bloom_filter.py:39-42, 185).

Semantic dedup: neighbours in embedding space

The problem. Two pages can say the same thing in different words: no shared 5-word phrase, Jaccard near 0. The tool. Embed every document with a text encoder (a model that maps text to a vector so that similar meanings land close together), cluster the vectors with k-means, and inside each cluster drop a document whose cosine similarity to an earlier-ranked one is at least 1 − ε. That is SemDeDup (Abbas et al. 2023) as NeMo Curator 1.4.0 runs it on GPUs: rank each cluster with the documents farthest from the centroid first ("hard", its default), keep the first, and remove any later document too close to one before it (stages/deduplication/semantic/pairwise.py, docstring at lines 95-131; defaults embeddinggemma-300m, 100 clusters, ε = 0.01 in stages/text/deduplication/semantic.py:80-92).

measured on CPU: the 2,692 filtered documents embedded with the encoder inside the FineWeb-Edu classifier on disk (Snowflake arctic-embed-m, first 512 tokens, the [CLS] vector, normalised); about s on 4 threads. Dots: the 856 MinHash pairs (true Jaccard across, cosine up), plus the 30 most similar pairs that share almost no shingles (Jaccard below 0.3, drawn in the second colour). The dashed line is the cosine cut 1 − ε. k-means with 20 clusters removes almost the same documents as comparing all pairs (the counts below), because near-identical documents land in the same cluster.
