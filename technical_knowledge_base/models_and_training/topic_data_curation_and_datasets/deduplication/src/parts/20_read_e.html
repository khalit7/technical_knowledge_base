4. From pairs to clusters: union-find, chaining, and which copy to keep

The problem. LSH outputs pairs, and "remove one document of every pair" is ill-defined when pairs overlap (A~B and B~C). Pipelines treat candidates as edges of a graph and keep one document per connected component (documents linked by any chain of edges).

Union-find (disjoint-set) keeps a forest: every document points to a parent, and a tree's root represents its set. find(x) follows parents to the root; union(x, y) points one root at the other. Path compression (after a find, point every node on the path straight at the root) and union by size (the smaller tree joins the larger) make each operation nearly constant time. datatrove's MinhashDedupCluster does exactly this in a Python dict (minhash.py:537-556), then removes every node that is not a root (579-583). Per band it sorts the signatures and emits only neighbouring equal pairs (minhash.py:471-480), so m identical band values give m−1 edges, not m(m−1)/2: on the running example the 14 bands wrote 810 pair records for only 94 distinct pairs; union-find gives 31 clusters and removes 75 documents. Chaining. A component can join two documents that are not similar at all, through intermediates. In the largest cluster (25 pages from 25 sites whose extracted text is one cookie-consent notice), a page with two sentences about a stove before the same banner has Jaccard 0.49 with the kept page; it joined through other banner pages and was removed. The fix: Dolma 3 computes the true Jaccard inside each cluster and removes only documents at 0.8 or more (allenai/dolma3 pool README). On the running example that check removes 65 instead of 75: the 10 that come back joined through chains. Lee et al. confirmed candidates with Jaccard and edit similarity > 0.8; RefinedWeb skipped verification to favour recall ("our main concern is improving recall", Appendix G.3.1).

Which copy survives is a choice. datatrove keeps the union-find root, whichever set won the size comparisons: on the running example the kept page is the longest member in 23 of 31 clusters and the lowest document index in 30. FineWeb describes it as "one randomly chosen document" per cluster. Llama 3 keeps the most recent version of each URL; Dolma 3 keeps the most recent copy; Zyda-2 kept the copy from the source it ranked highest (FineWeb-Edu-2, then DCLM, then Zyda-1, then Dolma-CC). A good default for web text: the most recent crawl (fresher content, working links), then the longest extraction. Keep the count: FineWeb-2 stores each kept document's cluster size, so a later step can repeat documents the web repeated (rehydration, section 10).

Connected components at scale (depth)
  • One machine. datatrove's clustering step must run as a single task (assert world_size == 1, minhash.py:533); its example gives that task 2 CPUs with 70 GB each, 140 GB in total, and 90 hours (examples/minhash_deduplication.py:66-84). measured the same dict structure costs about 140 bytes per document that appears in any pair (tracemalloc, 106 nodes in clusters of 4), so 140 GB holds about 109 duplicated documents. A numpy parent array costs 4 to 8 bytes per document instead: scipy's connected_components labelled 107 nodes with 5×106 random edges in about 2.5 s (rough: one core, shared machine).
  • Many machines. Union-find is sequential; distributed systems use label propagation instead. The text-dedup Spark script implements Kiveris et al.'s "large-star / small-star" alternation (each round, every node links to the smallest label in its neighbourhood; about O(log2 n) rounds; minhash_spark.py:38-134 at tag 2023.09.20). NeMo Curator 1.4.0 runs cuGraph's multi-GPU weakly connected components (fuzzy/connected_components.py:20-21, 146).
  • Giant components. A boilerplate cluster can reach a million documents (Zyphra reports a DCLM cluster "close to 1 million documents"); a chain through templates can merge unrelated sets. Inspect the largest components before removing anything.
