Numbers like "FineWeb keeps about a tenth of the crawl" are easier to believe when you can see the tenth. The topic's running example is one raw WARC file from the crawl of July 2024 ({{Topic: data-curation-and-datasets|n:3c65c17b0d0d811fa5ecda8d365ab00f}}, CC-MAIN-2024-30, segment 1720763514387.30, file 00000): @@kp_responses@@ HTTP responses, of which @@kp_html@@ are HTML pages with status 200. FineWeb and FineWeb-Edu record, for every document, the WARC file it came from, so their documents from this one file can be matched to the raw pages by URL. Three things to take from it. First, the bulk of the loss happens before any learned filter: FineWeb's rules, language ID and deduplication already drop about nine pages in ten of this file (the topic's {{Pipeline lab|n:3c65c17b0d0d811fa5ecda8d365ab00f}} tab measures where, stage by stage, on the same file). Second, an educational filter at threshold 3 keeps @@kp_edu_of_fw_pct@@ of what FineWeb kept, so a corpus built this way is small by design: that is the 1.3T against 18.5T of section 3. Third, moving the cut from 3 to 2 multiplies what survives several times, which is the trade Nemotron-CC made explicit: for a long run, more medium-quality tokens can beat repeating a small high-quality set.

Not run here: Nemotron-CC and DCLM on the same file. DCLM-Baseline only covers crawls up to 2022, so it has no documents from this 2024 file. Nemotron-CC v1 does cover CC-MAIN-2024-30, but its files on Common Crawl's bucket are split by quality bucket and not by source WARC file, so finding this file's pages means reading all 722 of its 2024-30 files (about 260 GB at the bucket's average of 0.37 GB per file: 10.4 TiB over 31,279 files): a network job, not a GPU one, left out for the topic's 15 GB disk budget.
