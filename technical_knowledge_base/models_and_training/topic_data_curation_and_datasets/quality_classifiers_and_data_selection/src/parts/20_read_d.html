2. Reference-set classifiers from zero: how fastText scores a page

The problem. You have billions of documents and a few hundred thousand examples of text you like (the reference set, or positives). You want a scorer cheap enough to run on every document of a crawl. The answer since GPT-3 has been a linear classifier on word features, trained to separate the reference set from random crawl documents (the negatives). DCLM's classifier, the one behind DCLM-baseline and OLMo 2's pretraining mix, is a fastText model: Facebook's library for linear text classifiers with hashed word n-grams (Joulin et al. 2016).

How it works, read from fastText v0.9.2's source (the version every pipeline here uses) and checked number for number below:

  1. One line of text. fastText reads one line at a time, so the document's lines are first joined with a space: " ".join(text.strip().splitlines()) (DCLM's enricher, baselines/mappers/enrichers/quality_prediction_enrichers_calc_fasttext.py:49 at commit 361714b; Dolma's tagger does the same). The Python binding appends a newline, which becomes the end-of-sentence token </s>.
  2. Tokens are what lies between ASCII spaces, tabs and newlines (dictionary.cc:208-232). No lowercasing and no punctuation splitting: Why, why and why? are three different words.
  3. Features. Every token found in the vocabulary contributes its own row (DCLM's model has @@dclm_nwords@@ words). Every pair of neighbouring tokens contributes a hashed bigram: the two tokens' 32-bit FNV-1a hashes are combined as h = h1 * 116049371 + h2 and reduced modulo 2,000,000 buckets (dictionary.cc:312-322). Unknown words still take part in bigrams, and unrelated bigrams that land in the same bucket share a row.
  4. Average. The document vector is the plain mean of all feature rows, 100 numbers each (model.cc:42-50). A 50-word page and a 5,000-word page both end up as one averaged vector.
  5. Score. Two output vectors, one per label (__label__hq, __label__cc); a softmax over the two dot products gives P(hq). With two labels this is a logistic regression: logit = (whq - wcc) · mean of rows.
  6. Cut. DCLM keeps a document when P(hq) ≥ 0.018112 (baselines/baselines_configs/fasttext_filter.yaml:8), the value that keeps the top 10% of its pool.

Because step 5 is linear, every feature's push, its row dotted with (whq - wcc), adds up exactly to the document's logit after dividing by the number of features. This page rebuilds DCLM's prediction from the weights this way for all @@n_run0@@ documents; the largest difference from fastText's own output is @@ft_rebuild_maxdiff@@, which is fastText adding 10-5 inside its log (loss.cc std_log). That decomposition drives the animation below and the {{Classifier replay|#t-qctr}} tab.

A trap found while rebuilding it
The first rebuild was wrong on some documents by up to 0.84 in probability. Two details of the C++ matter: tokens are split on ASCII whitespace only (Python's str.split() also splits on non-breaking spaces), and the 32-bit word hashes are stored in a std::vector<int32_t> (dictionary.cc:382), so a hash above 231 becomes negative and is sign-extended when widened to 64 bits for the bigram formula. Any reimplementation of fastText features (in Rust, Spark or a GPU kernel) has to copy both, or its bigram buckets silently differ.

The cost

Training is minutes on a laptop: DCLM's recipe at full size (200,000 positives and 200,000 negatives, with the smaller bucket table of section 3) took @@train_full_secs@@ s here on 4 threads measured, rough. Scoring is a hash lookup and a 100-dimensional average, about @@cost_ft_ms@@ ms per document per core, so a whole crawl is a CPU job, not a GPU job. The memory is the catch: the 2,000,000 bigram buckets plus a vocabulary of millions of words make DCLM's file 2.39 GB, loaded once per worker process (DCLM's README asks for --ray_num_cpus 2 per task for this reason).

GPT-3's version: logistic regression and a random keep

GPT-3 (Brown et al. 2020, Appendix A) trained a logistic regression on Spark's standard tokenizer and HashingTF features, with WebText, Wikipedia and a web books corpus as positives and unfiltered Common Crawl as negatives. It did not keep a top slice. It kept a document when np.random.pareto(α) > 1 - score with α = 9, "to take mostly documents the classifier scored highly, but still include some documents that were out of distribution". NumPy's pareto draws from a Lomax distribution with P(X > x) = (1 + x)-α, so the chance of keeping a document with score s is

P(keep | s) = (2 - s)-9

1.5-9 = 2.6%
