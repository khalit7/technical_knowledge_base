The idea in one screen

Keep the corpus twice: documents, compressed, for people and pipelines, and tokens, as flat fixed-width arrays the GPU can slice; then make the training order a pure function of (seed, samples consumed), so every rank gets packed, well-mixed windows and a restart continues at exactly the next sample.

From curated documents to a GPU batch: what each stage stores, per token

Bars are bytes per Qwen3 token to scale, measured on 2,000 FineWeb documents (the uint16 bar is per GPT-2 token) measured. Documents shrink to about 1.9 bytes per token compressed; token files are exactly 2 or 4. Everything below the token file is computed, not stored: the order comes from the seed, and the checkpoint only needs the number of samples consumed.

You need: what token ids are (Tokenizers) and what a data-parallel rank is (Distributed Training). Memory mapping and the page cache are on Storage and file systems; object stores and parallel file systems on Storage and data movement. This page owns the formats and the loaders.

1. The two lives of a corpus

As documents: one web page's text plus its metadata (URL, crawl, language score, quality score, duplicate-cluster id), one record per document. People and later pipeline runs read these to inspect what a filter dropped, to filter again at a new threshold, to decontaminate against a new benchmark, to publish. FineWeb ships Parquet; DCLM-baseline and Nemotron-CC ship zstd-compressed JSON Lines. Token files cannot be re-filtered or re-tokenized, so the documents are kept beside them.

As tokens: a model sees only token ids. Tokenizing is done once, offline, and stored as flat integer arrays with a small index of where each document ends (section 5); the training job reads raw numbers and parses nothing. On the running example:

First 2,000 rows of the setup's random FineWeb sample (1,422,641 Qwen3 tokens; 1,464,937 GPT-2 tokens) measured; "per trillion tokens" is bytes per token × 1012 derived. Cross-checks, derived: Nemotron-CC states 6.3T tokens in 10.4 TiB of zstd JSONL (its data page), 1.82 bytes per token in its own tokenizer, against our 1.93; FineWeb's card lists its June 2025 crawl as 419.6 GB of snappy Parquet for 152.4B GPT-2 tokens, 2.75 bytes per token, against our 2.92.

Rule of thumb
English web text is about 4.8 bytes of UTF-8 per token with a modern 150k vocabulary, about 1.9 bytes per token compressed, and exactly 2 or 4 bytes per token as a training array. A trillion training tokens is about 2 TB (vocabulary under 65,536) or 4 TB of token files, and roughly the same again for the compressed documents kept beside them.

2. Documents on disk: JSON Lines and compression

JSON Lines (JSONL) is one JSON object per line, {"text": "...", "url": "...", "language_score": 0.93, ...}: any language reads it, a broken line breaks one record, files concatenate with cat. The 2,000 documents take 7.70 MB, 6.80 MB of it the text and the rest keys and metadata repeated on every line. A compressor replaces repeated byte sequences with references to earlier ones: gzip (DEFLATE, RFC 1951 and 1952, levels 1 to 9) or zstd (Zstandard, open-sourced by Facebook in 2016, RFC 8878, levels 1 to 22), which compresses better at the same speed and decompresses several times faster (the zstd README benchmark published, vendor). The level trades write time for size; read speed barely depends on it, so data written once and read many times can afford a high level.

zstd keeps shrinking with level; gzip stops at level 6

Bytes on disk for the same 2,000 documents measured, src/scripts/formats.py; gzip from Python's gzip module, zstd from zstandard 0.25.0. Read speeds of every format are in the Format comparer.

The catch: no random access. A gzip or zstd stream is one chain: to reach document 1,500 you decompress documents 1 to 1,499. Reading 200 random documents from the 2,000-document .jsonl.zst took about 1.8 s; the same 200 from the token file of section 5 about 5 ms rough. Fine for pipeline stages, which read files start to end; wrong for a training loader that wants sample 8,213,511 now. Corpora live with it by keeping files small (thousands per crawl) and converting to an indexed format before training.

3. Parquet and Arrow: columns instead of rows

"How many documents have language_score above 0.9?" should not read 7 MB of text, but JSONL keeps each record's fields side by side. Parquet is columnar: the file is cut into row groups; inside each, every column's values form one column chunk (pages, each compressed on its own); a footer at the end records where every chunk starts, its size, and its minimum and maximum. A reader fetches the footer, then only the chunks it needs. Like values compress better together, and low-cardinality columns get dictionary encoding (each distinct value once, then small integers) and run-length encoding. The byte layout is on Analytics: columnar engines, DuckDB and the lakehouse; here is what matters for training data, on FineWeb's first CC-MAIN-2024-30 file, read by its footer alone (data/CC-MAIN-2024-30/000_00000.parquet, revision 9bb295dd, HTTP range requests) measured:

The text column is almost the whole file; row groups of about 2 MB are what a reader fetches

Small row groups (998 to 1,000 rows, 1.9 to 2.7 MB compressed) let a streaming reader start after a few megabytes rather than the whole 2.15 GB file, and let datatrove or Spark split one file across many tasks. They cost footer bytes: 3.8 MB here, describing 972 × 9 column chunks. "Columnar" saves little when you want the text and a lot when you want anything else.

Correction to the root page: Parquet is not larger than zstd JSONL
The root's Tool map measured 3.02 MB for Parquet with zstd against 2.74 MB for JSONL with zstd and first left it "not investigated further" (it now gives this cause). When no level is given, pyarrow 26 writes zstd at level 1 (our file with no level is byte-identical to the one written with compression_level=1), while the JSONL used level 3. At level 3 Parquet is 2.69 MB, 2% smaller than the JSONL; at level 19, 2.22 MB. Always pass compression_level when comparing or publishing.

Arrow is Parquet's in-memory sibling: the same columnar layout, uncompressed and laid out exactly as a program uses it, so an Arrow IPC file (also called Feather) can be memory-mapped. Hugging Face datasets converts every dataset it loads into Arrow files in its cache and memory-maps them, which is why "loading" a 100 GB dataset is instant and costs no RAM until rows are read. The price is disk: uncompressed Arrow is as large as the raw data (7.46 MB here); its optional LZ4 or zstd buffer compression (4.42 and 3.01 MB) gives up zero-copy mapping.

Row-group size against file size, on our own file (depth)

One row group of 2,000 rows: 2.69 MB at zstd level 3; row groups of 500 rows: 2.71 MB; of 100 rows: 2.94 MB, 9% larger measured. Each row group restarts every column's dictionary and compression window and adds footer metadata. Turning dictionary encoding off changed almost nothing here (2.68 MB), because the text column dominates and has no repeated values.

4. Shard formats built for streaming: WebDataset, MDS, Lance

A job reading from object storage (section 9) needs three things: a reader can start on any shard, shards are big enough that per-request latency is amortised, and an index finds a sample by number. Three formats are designed around them:

A tar member pays 1,536 bytes of headers for a 1,910-byte text sample; MDS pays a few bytes of offsets

Top: one WebDataset tar member at the mean payload of our 4,000 members (1,910 bytes), to scale; webdataset 1.0.2 writes a PAX extended header (512-byte header plus 512 bytes of data) before every member's own 512-byte header, and pads the payload to a multiple of 512 derived from the tar format. Middle: the whole measured file, 14.50 MB of which 7.64 MB is payload. Bottom: an MDS shard, samples back to back after an offset table, with one index.json for the dataset.

  • WebDataset stores samples in plain POSIX tar files: a sample is all files sharing a key (000017.txt, 000017.json). Any tool reads them, strictly sequentially, which object stores serve well. Our 2,000 samples (4,000 members) make a 14.50 MB tar: 47% of the file is headers and padding; compressing the tar (3.14 MB) recovers it. It suits images and audio (large samples) better than short text.
  • MDS (MosaicML Streaming): shard files of at most size_limit bytes (64 MiB by default, streaming/base/format/base/writer.py line 79, version 0.13.0) holding samples back to back with an offset table, plus one index.json listing every shard's sample count, size and compression, so a loader knows where sample 8,213,511 lives without opening anything. Our 2,000 documents: 7.46 MB raw, 2.74 MB with zstd per shard.
  • Lance: a newer columnar format built for fast random access by row (and vector search), for jobs that need arbitrary rows rather than a stream: 3.38 MB here with default settings.

The Format comparer puts all the variants side by side with what each can do (random access, column projection, append, streaming) and rough read speeds.

5. Token files: what a pretraining run actually reads

Tokenize once, offline. Each document is independent, so pipelines run tokenizing as many CPU tasks, one per input file, each writing its own token shard (datatrove's DocumentTokenizer, Megatron's tools/preprocess_data.py). On this machine the Hugging Face tokenizers library encoded 50,000 FineWeb documents (37.6M Qwen3 tokens) at about 1.4M tokens per second on 4 threads and 0.49M tokens per second on one rough. 15 trillion tokens at 0.49M per core-second is about 8,500 core-hours derived (3.1 × 107 core-seconds): an afternoon on a 2,000-core cluster, once, instead of every training node's CPUs for the whole run, tied to one tokenizer version.

The layout. Every document's ids go one after another into one binary file, each id a fixed-width integer, usually with an end-of-document token (EOD, for example <|endoftext|>) after each document; an index beside it records where each document ends. The file is memory-mapped, so tokens[i : i + 2049] costs one page-cache lookup, no parsing and no copy of the rest. Megatron's pair on our 2,000 documents: 5,730,606 bytes with Qwen3 ids (int32), 2,969,916 bytes with GPT-2 ids (uint16); the index is 40,042 bytes, 20 bytes per document measured, written byte for byte to Megatron's layout by src/scripts/formats.py. zstd saves less than you might hope on ids (uint32 Qwen3: 5.69 MB to 2.38 MB; uint16 GPT-2: 2.93 MB to 2.10 MB) and kills random access, so token files are stored raw.

The 16-bit trap, measured
Qwen3's vocabulary has 151,669 entries, so its ids need 18 bits. In our 2,000 documents, 34,587 of 1,422,641 tokens (2.4%) have ids of 65,536 or more, and 1,942 documents (97%) contain at least one. Written as uint16, each such id silently becomes id mod 65,536, another real token. Nothing crashes; the model trains on corrupted text. datatrove's default token_size=2 and nanoGPT's hard-coded uint16 both do this if you change the tokenizer and forget the width. Check: after writing, compare max(ids) with the vocabulary size and decode one document.

What the wrapped ids become

From one token file to training samples: Megatron's three indices

Something must decide which slices become samples, in which order, for how many epochs. nanoGPT draws random start positions every step (torch.randint(len(data) - block_size, ...), train.py lines 116-131): no epochs, and draws with replacement both repeat and miss text; after as many windows as would cover the file once, about e−1 ≈ 36.8% of tokens has never been seen (simulated on a 50-million-token array: 36.8% derived): fine for a toy, not for a run whose data budget is planned in epochs. Megatron-LM's GPTDataset instead builds three small arrays once, saves them as .npy files, and memory-maps them in every rank (gpt_dataset.py lines 475-660):

  1. document_index: every document id once per epoch, all epochs shuffled together with numpy.random.RandomState(seed) (_build_document_index, lines 734-765).
  2. sample_index: walks that order as one stream and records where every sample starts (document position, token offset); each sample is sequence_length + 1 tokens, the extra one the last target (helpers.cpp build_sample_idx, lines 144-249).
  3. shuffle_index: a permutation of the sample numbers, from the same random state (_build_shuffle_index).

Sample k of the run is shuffle_index[k] → two rows of sample_index → a few slices of the token file. Everything is a function of the seed, so a restart needs only the samples consumed. Step through it on twelve real documents, then switch to nanoGPT and watch the coverage strip:

6. Packing documents into windows, and their boundaries

A GPU trains on rectangles: a batch of sequences of one context length L. Documents are not that shape: in our sample the median is 466 Qwen3 tokens and the 90th percentile 1,386. Four ways to fill the windows, measured on the same 2,000 documents at L = 2,048 measured:

  • Pad: one document per window, the rest padding masked out of the loss: 2,143 windows, 67.6% of positions wasted (padding to the batch's longest sequence, as fine-tuning code does, helps a little).
  • Truncate: one window per document, long tails thrown away: 12.4% of all tokens lost, padding as before.
  • Concatenate and chunk ("packing" in most code: GPT-3, nanoGPT, Megatron's default): join with EOD tokens, cut every L. 696 windows, 99.95% real tokens; but 605 of the 2,000 documents are cut, and tokens attend to the previous, unrelated document.
  • Best-fit packing (Ding et al. 2024): split only documents longer than L, then place pieces longest first into the window with the least room that fits (Best-Fit Decreasing). 697 windows; only the 93 documents longer than 2,048 tokens are cut.

Document boundaries in attention. With several documents in a window, either every token attends to everything before it (cheap, the standard GPT-3 setup), or a document mask lets a token attend only to earlier tokens of its own document, usually with position ids restarting at each document. On our windows, 53% of the (query, key) pairs a causal model computes cross a document boundary at L = 2,048, and 81% at 8,192 measured. A document mask removes them, and a variable-length attention kernel (FlashAttention's varlen interface, PyTorch's FlexAttention with a document mask) also skips their compute. Megatron exposes this as reset_attention_mask and reset_position_ids (gpt_dataset.py lines 800-860); datatrove's dataset returns per-document positions from the .index file (utils/dataset.py lines 70-127).

"Cross-document pairs": the share of causal (query, key) pairs whose query and key belong to different documents. Masked, they are excluded; with a variable-length kernel the same share is the attention-score work saved (the rest of the model's FLOPs are unchanged). Truncation and padding have none, at the cost in the table below.

What the evidence says published. Llama 3: "We use an attention mask that prevents self-attention between different documents within the same sequence. We find that this change had limited impact during in standard pre-training, but find it to be important in continued pre-training on very long sequences" (Llama 3 paper, section 3.2). Ding et al. (LLaMA-architecture 7B and 13B models) report gains from best-fit packing of +4.7% on reading comprehension, +16.8% on context following and +9.2% on program synthesis, and up to 58.3% less closed-domain hallucination. The gains are small to moderate for short web documents at 2k to 8k windows and grow with long contexts and data where whole documents matter (code files, long articles, instruction data); the waste of padding always matters. Sequence-length schedules and long-context stages are on Pretraining.

The evidence in detail, and the strategies at 50,000 documents (depth)
  • Ding et al. 2024, Table 10, separates the mask from the packing at 2k context: concatenation 46.71% reading comprehension, concatenation with a document mask 47.92%, best-fit packing with the mask 48.92%; summarisation got worse with the mask alone (12.16 to 11.79 ROUGE-2) and better with packing (13.14). Perplexity moved only with the mask (9.64 to 9.53). Their Table 1: the optimised algorithm packs 1 billion documents in 10,816 s on one CPU thread.
  • Zhao et al. 2024 (arXiv 2402.13991) find intra-document causal masking improves language modelling and downstream results, and that packing related documents together (retrieved by BM25) helps further.
  • For fine-tuning-style data the waste of padding is the headline: Krell et al. (arXiv 2107.02027, Graphcore) found up to 50% padding in common NLP datasets and a 2× speedup for BERT phase-2 pretraining from packing.

7. Sharding: splitting the data across files, ranks and workers

Nothing at this scale is one file: writers run in parallel (one output shard per pipeline task), each data-parallel rank reads different data with several loader worker processes, a failed task redoes one shard, and object stores serve many medium-sized objects better than one huge one. Data reaches the ranks in one of two ways:

Index-based loaders ignore shard boundaries; shard-based loaders need at least ranks × workers shards

Index-based (Megatron, MosaicML Streaming, map-style PyTorch datasets with a DistributedSampler): every rank computes the same global sample order from the seed and takes its own slice of each global batch. Shard-based (WebDataset, Hugging Face streaming IterableDataset): shards are dealt to ranks, then to each rank's workers; dealt round robin, 11 shards over 2 ranks × 4 workers leave 3 workers reading a second shard while the other 5 sit idle illustrative. Keep the shard count a multiple of ranks × workers. Hugging Face's split_dataset_by_node assigns whole shards only when num_shards is a multiple of the world size; otherwise "each node keeps 1 example out of world_size, skipping the other examples", so every node reads every shard (distributed.py lines 21-23, datasets 5.0.1).

A version-specific trap, measured
With datasets 5.0.1, our 11-file streaming dataset reports num_shards = 11, but after .shuffle(seed, buffer_size) it reports 1: the new shuffle reads up to max_buffer_input_shards = 10 shard groups round robin into the buffer (iterable_dataset.py lines 3738-3830), and the wrapper exposes the minimum shard count of its sources. A DataLoader with 4 workers then warns "Too many dataloader workers: 4 (max is dataset.num_shards=1). Stopping 3 dataloader workers." and runs on one. Passing max_buffer_input_shards=1 restores 11 shards (and the older shuffle). Print num_shards after every transformation.

How big. Large enough that per-request latency and per-file overhead vanish, small enough that a worker starts quickly and a shuffle has many units to permute: tens of megabytes to a few gigabytes. MosaicML Streaming's default size_limit is 64 MiB; FineWeb's Parquet files are about 2 GB, with 2 MB row groups as the real reading unit.

8. Shuffling

SGD assumes each batch is a fair sample of the data; pipeline output is written per crawl, language, quality bucket and source. Read in order, a model sees one bucket for thousands of steps; its gradients lean toward it, and the loss jumps at every switch. Three ways to shuffle at scale:

  1. Global permutation. Number every sample and permute the numbers with a seed (Megatron's shuffle_index, any map-style dataset with a shuffling sampler). Perfect, deterministic, and possible only because token files can read sample k directly.
  2. Shard order plus a buffer. For sequential formats (tar, Parquet, JSONL streamed): shuffle the shard order, read shards sequentially, and keep a shuffle buffer of B examples, emitting a random one and putting the next read in its slot. It mixes only about B examples back, so B must be large next to a shard (WebDataset; Hugging Face IterableDataset.shuffle, default B = 1,000). MosaicML Streaming sits between 1 and 2: samples are permuted inside blocks of shuffle_block_size samples (default at least 262,144), so memory and downloads stay bounded while mixing stays wide.
  3. Shuffle offline. Write the token shards already shuffled (datatrove's tokenizer and merger, section 5) and read them sequentially. Cheap at train time, fixed: a new order means rewriting the data.

Measured on a corpus written the bad way: 11 shards of 200 documents, one per Nemotron-CC quality bucket and kind (CC-MAIN-2024-30, the first 200 documents of each head sample), read back under each scheme with the real libraries; a batch is 32 samples measured:

Read in order, a batch holds 1.1 buckets; shard order plus a 1,000-example buffer gives 9.0; a global permutation 10.5. A buffer is only as good as its ratio to a shard: 100 examples over 200-example shards gives 2.7 buckets. And each DataLoader batch is built inside one worker from its shards, so 4 workers drop the 1,000-example buffer to 3.6 buckets. Predict where the colours clump before you pick a scheme:

9. Streaming from object storage

Object storage (S3, Google Cloud Storage, Azure Blob and the S3-compatible stores most clusters run) serves whole objects by key over HTTP, with byte-range reads, and scales throughput by parallel requests rather than one fast stream; every request pays a fixed latency, which is why shards and row groups are megabytes, not kilobytes. Its request rates, latencies and the parallel file systems beside it (including Llama 3's 240 PB Tectonic) are taught on Storage and data movement. A loader reads from it in one of three ways:

  • Copy first: sync the token files to local NVMe or a parallel file system before training.
  • Stream with a local cache: MosaicML Streaming and LitData download shards ahead of use into a local cache (predownload, cache_limit) and evict old ones, and make the sample order independent of the number of nodes (num_canonical_nodes), so a job can resume on a different cluster size.
  • Stream without a cache: Hugging Face load_dataset(..., streaming=True) reads Parquet row groups over HTTP as it goes; WebDataset reads tar shards from any URL or pipe. Simple, but every epoch downloads everything again.

Not run here: object-store throughput depends on the network and the store, and a laptop on home broadband would teach nothing that transfers. Section 12 shows how little bandwidth text needs, which is why streaming text works at all.

10. Data loaders: keeping the next batch ready

The data loader is the code in each training process that produces the next batch while the GPU computes on the current one. In PyTorch it is torch.utils.data.DataLoader: a dataset says how to get samples, by index (map-style, __getitem__(i), with a sampler deciding the order) or as a stream (iterable-style, __iter__); num_workers separate processes fetch in parallel; each keeps prefetch_factor batches ready (2 by default); pin_memory puts them in page-locked memory so the copy to the GPU overlaps compute. The same idea one level up: a loader that fetches the next shard only when it needs it adds the fetch to every step; one that keeps the next shards in flight hides it, as long as fetching is faster than computing.

Prefetching hides the fetch, until a fetch takes longer than a step

One 4 MiB token shard per step, 100 ms of compute per step (a sleep standing in for the GPU), 16 steps, median of 3 runs; measured in the ML infra topic's Storage lab, from one container to an S3-compatible store and to a Docker volume, and shown first on Storage and data movement measured. The model mode assumes one fetch at a time in the background: a step takes fetch + compute without prefetch, and max(fetch, compute) with it illustrative; at 9 ms it lands within 1.3% of both measured S3 totals.

The iterable-dataset worker trap. With an iterable dataset every worker process runs __iter__ from the start; unless the dataset asks which worker it is and takes its share, each sample comes out once per worker. Run here, with real output:

class Naive(IterableDataset):
    def __iter__(self): return iter(range(1000))
class Sharded(IterableDataset):
    def __iter__(self):
        w = get_worker_info(); k, n = (w.id, w.num_workers) if w else (0, 1)
        return iter(range(k, 1000, n))           # worker k takes every n-th sample
for D in (Naive, Sharded):
    got = [int(x) for b in DataLoader(D(), batch_size=50, num_workers=4) for x in b]
    print(D.__name__, len(got), len(set(got)))


src/scripts/resume.py, torch 2.14.1, CPU measured: Naive yields 4,000 samples, 1,000 distinct. Libraries that stream shards (Hugging Face datasets, WebDataset, MosaicML Streaming) split by shard for you; your own iterable dataset must, by worker and by rank.


How fast does a loader need to be? Much less than people expect for text. Reading 8 × 2,048-token windows from a memory-mapped token file, the nanoGPT way, ran at about 48M tokens per second in one process; a map-style dataset through a DataLoader at about 5M tokens per second with no workers and about 49M with 4 rough, file in the page cache. One H100 training a 1B-parameter model at 40% utilisation consumes about 66,000 tokens per second (section 12). The loader becomes the bottleneck when it does real work per sample (tokenizing online, decoding images or video, heavy augmentation), when the file is remote and nothing prefetches it, or at start-up, when every rank opens files and builds indices before the first step. Seeing a data-bound step in a profiler trace, and the worker settings that fix it, is on Making training fast (section 4).


Mixing at load time. With several token files mixed by weight (web, code, maths) the loader also picks the source of each sample. Megatron's BlendedDataset precomputes which dataset and which sample with a deterministic error-driven rule and caches them like the other indices, so resuming still needs only the samples consumed; Hugging Face's interleave_datasets samples at random, and its stopping_strategy ("first_exhausted" or "all_exhausted") silently changes how often small sources repeat. Both are taught, with the blending rule animated, on Data mixing.







11. Checkpointing the data state and resuming mid-epoch


Large runs stop all the time: Llama 3 405B's pretraining saw 466 job interruptions in a 54-day snapshot, 419 of them unexpected, about 78% from confirmed or suspected hardware (Llama 3, section 3.3.4 published), more than 8 a day. Each restart reloads the model and optimiser; if the loader cannot also return to the exact next sample, the run silently trains on some data twice and some not at all, and two runs from the same checkpoint differ.


What the data state is. For an index-based loader, one integer: the samples consumed (plus the seed and the configuration that built the indices, which do not change). Megatron's sampler literally starts at it: for idx in range(self.consumed_samples, self.total_samples) (data_samplers.py lines 190-198 at 80781ab). For a streaming loader with a shuffle buffer the state includes the buffer's contents, which are rarely saved. For a mixture with adaptive weights, also the weights and the sampler's random state. Each loader below read one epoch of the same 2,200 samples straight through, then again stopping after 20 batches (640 samples), saving the state the library offers, and resuming in a fresh loader measured:




src/scripts/resume.py; torch 2.14.1, torchdata 0.11.0, datasets 5.0.1, mosaicml-streaming 0.13.0. Restarting the epoch with the same seed reads the first 640 twice; with a new seed, 463 are read twice and 463 never. The Hugging Face documentation states the loss: "examples from shuffle buffers are lost when resuming and the buffers are refilled with new data" (iterable_dataset.py line 2566). Losing 1,000 of 2,200 is dramatic because the epoch is tiny; on a real run it is one buffer per worker per restart, small but not zero, and the order after the restart differs from an uninterrupted run: accept and log it, or use an index-based loader for pretraining.

12. The cost model: bytes per token, terabytes per trillion, megabytes per second


Three formulas cover the storage and bandwidth side of planning a run derived:


tokens/s per GPU ≈ MFU × peak FLOP/s ÷ (6 × N)
N
model parameters (6N FLOPs per token for forward and backward, ignoring attention)
MFU
model FLOPs utilisation, the share of peak the run achieves (Llama 3 405B: 38-43%, Table 4)


loader bytes/s = tokens/s × bytes per token
bytes per token
2 (uint16) or 4 (uint32) for token files; about 1.9 for zstd JSONL plus tokenizer CPU


storage = training tokens × bytes per token
e.g.
15T tokens of uint32 ids = 60 TB; the same as uint16 = 30 TB


Llama 3 405B as a check: 16,384 GPUs at 400 TFLOP/s each (Table 4, 41% BF16 MFU) and N = 405B give 16,384 × 400 × 1012 ÷ (6 × 405 × 109) ≈ 2.7 million tokens per second for the whole job, about 165 per GPU. With 16M tokens per batch (Table 4) that is a step every 6.2 s, and about 11 MB/s of uint32 ids for 16,384 GPUs, against a storage fabric sustaining 2 TB/s. 13. Depth: design questions


Design the data storage and loading for a 2,048-GPU pretraining run of a 70B model on 15T tokens, data in S3 (rehearsal)
Clarify: vocabulary size (uint16 or uint32), context length, number of domains and whether weights change during the run, how often the job restarts. Storage: keep curated documents as zstd Parquet with metadata (re-filtering, decontamination, audits); tokenize once on a CPU cluster into token shards with document-end indices, one set per domain, tokenizer revision recorded; 15T × 4 bytes = 60 TB of ids, about the same again for documents. Getting it to the GPUs: 2,048 H100s at 40% MFU on 70B is about 2,048 × 0.4 × 989.5 × 1012 ÷ (6 × 70 × 109) ≈ 1.9M tokens/s, under 8 MB/s of ids for the whole job: copy to a parallel file system or local NVMe before training, or stream with a local cache (MosaicML Streaming) with prefetch. Order: index-based (Megatron-style document, sample and shuffle indices, plus blending indices for the domain weights), built once and cached, so each rank reads its slice by sample number. Packing: concatenation or best-fit packing, with a document mask if long-context quality matters. Resumption: save consumed samples and the data-config hash with every checkpoint; test exact resume in CI. Failure modes to name: wrong id width, too few shards, buffer-only shuffles, a changed tokenizer between shards. The calculator's "70B on 2,048 H100s" preset is this design.


Your loss curve has a sawtooth with a period of a few thousand steps. What do you check first? (rehearsal)
Data order. A period suggests shards or sources read one after another: check shard-order shuffling, the buffer size against the shard size, whether each DataLoader worker reads a single source, and whether the mixture sampler resets each epoch.


Parquet or JSONL for a published corpus? (rehearsal)
Parquet if people will query metadata or read a subset of columns, and if readers will stream it (row groups give natural units); JSONL with zstd if simplicity and line-level robustness matter more. At the same zstd level the sizes are within a few percent (section 3). Either way, publish the compression levels and the tokenizer you counted tokens with. On-the-fly tokenizing, the other half of the question people ask, makes sense only for small fine-tuning sets or while the tokenizer is still changing.
