10. Data loaders: keeping the next batch ready

The data loader is the code in each training process that produces the next batch while the GPU computes on the current one. In PyTorch it is torch.utils.data.DataLoader: a dataset says how to get samples, by index (map-style, __getitem__(i), with a sampler deciding the order) or as a stream (iterable-style, __iter__); num_workers separate processes fetch in parallel; each keeps prefetch_factor batches ready (2 by default); pin_memory puts them in page-locked memory so the copy to the GPU overlaps compute. The same idea one level up: a loader that fetches the next shard only when it needs it adds the fetch to every step; one that keeps the next shards in flight hides it, as long as fetching is faster than computing. How often it is not, measured on production training servers (Mohan et al.'s data stalls, VLDB 2021), and the page cache, readahead and memory mapping underneath, are {{Storage and file systems|n:3f05c17b0d0d8141be7acc1313570cbf#rd-s11}}, section 11.

Prefetching hides the fetch, until a fetch takes longer than a step

One 4 MiB token shard per step, 100 ms of compute per step (a sleep standing in for the GPU), 16 steps, median of 3 runs; measured in the ML infra topic's Storage lab, from one container to an S3-compatible store and to a Docker volume, and shown first on {{Storage and data movement|n:3fc5c17b0d0d818a94ced3fc7c3331fe}} measured. The model mode assumes one fetch at a time in the background: a step takes fetch + compute without prefetch, and max(fetch, compute) with it illustrative; at 9 ms it lands within 1.3% of both measured S3 totals.

The iterable-dataset worker trap. With an iterable dataset every worker process runs __iter__ from the start; unless the dataset asks which worker it is and takes its share, each sample comes out once per worker. Run here, with real output:

class Naive(IterableDataset):
    def __iter__(self): return iter(range(1000))
class Sharded(IterableDataset):
    def __iter__(self):
        w = get_worker_info(); k, n = (w.id, w.num_workers) if w else (0, 1)
        return iter(range(k, 1000, n))           # worker k takes every n-th sample
for D in (Naive, Sharded):
    got = [int(x) for b in DataLoader(D(), batch_size=50, num_workers=4) for x in b]
    print(D.__name__, len(got), len(set(got)))


src/scripts/resume.py, torch 2.14.1, CPU measured: Naive yields 4,000 samples, 1,000 distinct. Libraries that stream shards (Hugging Face datasets, WebDataset, MosaicML Streaming) split by shard for you; your own iterable dataset must, by worker and by rank.


How fast does a loader need to be? Much less than people expect for text. Reading 8 × 2,048-token windows from a memory-mapped token file, the nanoGPT way, ran at about 48M tokens per second in one process; a map-style dataset through a DataLoader at about 5M tokens per second with no workers and about 49M with 4 rough, file in the page cache. One H100 training a 1B-parameter model at 40% utilisation consumes about 66,000 tokens per second (section 12). The loader becomes the bottleneck when it does real work per sample (tokenizing online, decoding images or video, heavy augmentation), when the file is remote and nothing prefetches it, or at start-up, when every rank opens files and builds indices before the first step. Seeing a data-bound step in a profiler trace, and the worker settings that fix it, is on {{Making training fast|n:3c65c17b0d0d810d9e1fdf9ec942c20d}} (section 4).


Mixing at load time. With several token files mixed by weight (web, code, maths) the loader also picks the source of each sample. Megatron's BlendedDataset precomputes which dataset and which sample with a deterministic error-driven rule and caches them like the other indices, so resuming still needs only the samples consumed; Hugging Face's interleave_datasets samples at random, and its stopping_strategy ("first_exhausted" or "all_exhausted") silently changes how often small sources repeat. Both are taught, with the blending rule animated, on {{Data mixing|n:3c65c17b0d0d819ea5d6c59471e66875}}.







11. Checkpointing the data state and resuming mid-epoch


Large runs stop all the time: Llama 3 405B's pretraining saw 466 job interruptions in a 54-day snapshot, 419 of them unexpected, about 78% from confirmed or suspected hardware ({{Llama 3, section 3.3.4|https://arxiv.org/abs/2407.21783}} published), more than 8 a day. Each restart reloads the model and optimiser; if the loader cannot also return to the exact next sample, the run silently trains on some data twice and some not at all, and two runs from the same checkpoint differ.


What the data state is. For an index-based loader, one integer: the samples consumed (plus the seed and the configuration that built the indices, which do not change). Megatron's sampler literally starts at it: for idx in range(self.consumed_samples, self.total_samples) (data_samplers.py lines 190-198 at 80781ab). For a streaming loader with a shuffle buffer the state includes the buffer's contents, which are rarely saved. For a mixture with adaptive weights, also the weights and the sampler's random state. Each loader below read one epoch of the same 2,200 samples straight through, then again stopping after 20 batches (640 samples), saving the state the library offers, and resuming in a fresh loader measured:




src/scripts/resume.py; torch 2.14.1, torchdata 0.11.0, datasets 5.0.1, mosaicml-streaming 0.13.0. Restarting the epoch with the same seed reads the first 640 twice; with a new seed, 463 are read twice and 463 never. The Hugging Face documentation states the loss: "examples from shuffle buffers are lost when resuming and the buffers are refilled with new data" (iterable_dataset.py line 2566). Losing 1,000 of 2,200 is dramatic because the epoch is tiny; on a real run it is one buffer per worker per restart, small but not zero, and the order after the restart differs from an uninterrupted run: accept and log it, or use an index-based loader for pretraining.

12. The cost model: bytes per token, terabytes per trillion, megabytes per second


Three formulas cover the storage and bandwidth side of planning a run derived:


tokens/s per GPU ≈ MFU × peak FLOP/s ÷ (6 × N)
N
model parameters (6N FLOPs per token for forward and backward, ignoring attention)
MFU
model FLOPs utilisation, the share of peak the run achieves (Llama 3 405B: 38-43%, Table 4)


loader bytes/s = tokens/s × bytes per token
bytes per token
2 (uint16) or 4 (uint32) for token files; about 1.9 for zstd JSONL plus tokenizer CPU


storage = training tokens × bytes per token
e.g.
15T tokens of uint32 ids = 60 TB; the same as uint16 = 30 TB


Llama 3 405B as a check: 16,384 GPUs at 400 TFLOP/s each (Table 4, 41% BF16 MFU) and N = 405B give 16,384 × 400 × 1012 ÷ (6 × 405 × 109) ≈ 2.7 million tokens per second for the whole job, about 165 per GPU. With 16M tokens per batch (Table 4) that is a step every 6.2 s, and about 11 MB/s of uint32 ids for 16,384 GPUs, against a storage fabric sustaining 2 TB/s.
