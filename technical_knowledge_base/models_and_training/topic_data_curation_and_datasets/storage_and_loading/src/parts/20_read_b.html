2. Documents on disk: JSON Lines and compression

The problem. The pipeline writes billions of documents and every later stage, and every person debugging it, must read them back. The simplest format that works is JSON Lines (JSONL): one JSON object per line, {"text": "...", "url": "...", "language_score": 0.93, ...}. Any language can read it, a broken line breaks only one record, and files can be concatenated with cat. Its cost is size: the 2,000 documents take 7.70 MB, of which 6.80 MB is the text itself and the rest is keys, quotes and metadata repeated on every line.

How compression helps. A compressor finds repeated byte sequences and replaces them with short references to earlier occurrences, then encodes the result with fewer bits for common symbols. Two are used for corpora. gzip (DEFLATE, standardised in {{RFC 1951 and 1952|https://www.rfc-editor.org/rfc/rfc1952}} in 1996, levels 1 to 9) is everywhere. zstd (Zstandard, open-sourced by Facebook in 2016, {{RFC 8878|https://www.rfc-editor.org/rfc/rfc8878}}, levels 1 to 22) compresses better at the same speed and decompresses several times faster (the {{zstd README benchmark|https://github.com/facebook/zstd#benchmarks}} published, vendor), which is why DCLM-baseline and Nemotron-CC ship zstd-compressed JSONL. The level trades compression time for size; decompression speed barely depends on it, so data written once and read many times can afford a high level.

Bytes on disk for the same 2,000 documents measured, src/scripts/formats.py; gzip from Python's gzip module, zstd from zstandard 0.25.0. Read speeds for every format are in the {{Format comparer|#t-fmt}}.

The catch: no random access. A gzip or zstd stream is one long chain: to reach document 1,500 you must decompress documents 1 to 1,499 first. Reading 200 randomly chosen documents from the 2,000-document .jsonl.zst file took about 1.8 s; reading the same 200 from the token file of section 5 took about 5 ms rough. That is fine for pipeline stages, which read files start to end, and wrong for a training loader, which wants "give me sample 8,213,511" at once. Corpora live with it by keeping files small (thousands of files per crawl) so a reader can start anywhere at a file boundary, and by converting to a format with an index before training.

3. Parquet and Arrow: columns instead of rows

The problem. Most later questions touch one or two fields. "How many documents have language_score above 0.9?" should not read 7 MB of text. JSONL stores each record's fields side by side, so it must read everything.

How Parquet works. Parquet is a columnar file format: it stores all values of one column together. The file is cut into row groups (a block of rows, say 1,000 documents); inside each row group, each column's values form a column chunk, made of pages, each compressed on its own; at the end, a footer records where every chunk starts, its size and its minimum and maximum. A reader fetches the footer first, then only the chunks it needs. Values of one column look alike (all dates, all language codes), so they compress far better together, and Parquet also applies dictionary encoding (store each distinct value once, then small integers) and run-length encoding to columns with few distinct values. The byte-by-byte layout is taught on {{Analytics: columnar engines, DuckDB and the lakehouse|n:3ef5c17b0d0d8157814ec5dd8a0d4fb5}}; here we only need what matters for training data.

Three things to notice. The text column is almost the whole file, so "columnar" saves little when you want the text, and a lot when you want anything else. The row groups are small (998 to 1,000 rows, 1.9 to 2.7 MB compressed each): that is what lets a streaming reader start after fetching a few megabytes rather than a 2.15 GB file, and what lets datatrove or Spark split one file across many tasks. And the footer is 3.8 MB, because it describes 972 × 9 column chunks: small row groups cost footer bytes and compression, which our own file shows (one row group of 2,000 rows: 2.69 MB at zstd level 3; row groups of 100 rows: 2.94 MB, 9% larger) measured.

Why the root page found Parquet larger than zstd JSONL
The root's Tool map measured 3.02 MB for Parquet with zstd against 2.74 MB for JSONL with zstd, and left it "not investigated further". The reason: when no level is given, pyarrow 26 writes zstd at level 1 (our file with no level is byte-identical to the one written with compression_level=1), while the JSONL used level 3. At level 3 Parquet is 2.69 MB, 2% smaller than the JSONL; at level 19 it is 2.22 MB. Always pass compression_level when comparing or publishing.

Arrow is the in-memory sibling of Parquet: the same columnar layout, but uncompressed and laid out exactly as a program uses it, so a file in Arrow's IPC format (also called Feather) can be memory-mapped, meaning the operating system maps the file into the program's address space and reads pages from disk only when they are touched (the {{Storage and file systems|n:3f05c17b0d0d8141be7acc1313570cbf}} page explains the page cache behind this). Hugging Face datasets converts every dataset it loads into Arrow files in its cache and memory-maps them; that is why "loading" a 100 GB dataset is instant and costs no RAM until rows are read. The cost is disk: uncompressed Arrow is as large as the raw data (7.46 MB here); Arrow's optional LZ4 or zstd buffer compression (4.42 and 3.01 MB) gives up zero-copy mapping.

4. Shard formats built for streaming: WebDataset, MDS, Lance

When the training job reads from object storage (section 10) instead of a local disk, three properties matter: a reader can start on any shard (one file of a dataset split into many), shards are big enough that per-request latency is amortised, and there is an index so a sample can be found by number. Three formats are designed around that.

  • WebDataset stores samples in plain POSIX tar files: a sample is all files sharing a key (000017.txt, 000017.json). Any tool can make or read them, and reading is strictly sequential, which object stores serve well. The cost for small text samples is the tar format itself: every member has a 512-byte header and is padded to a multiple of 512 bytes, and webdataset 1.0.2 writes PAX headers that add another 1,024 bytes per member. Our 2,000 samples (4,000 members, 7.64 MB of payload) make a 14.50 MB tar: 47% of the file is headers and padding. Compressing the tar (3.14 MB) recovers it. WebDataset suits images and audio (large samples) better than short text.
  • MDS is MosaicML Streaming's format: shard files of at most size_limit bytes (64 MiB by default, streaming/base/format/base/writer.py line 79, version 0.13.0) holding samples back to back with an offset table, plus one index.json listing every shard's sample count, byte size and compression. With the index a loader knows where sample 8,213,511 lives without opening anything. Our 2,000 documents: 7.46 MB raw, 2.74 MB with zstd per shard.
  • Lance is a newer columnar format designed for fast random access by row (and vector search), useful when a training or evaluation job needs arbitrary rows rather than a stream: 3.38 MB here with default settings.

The {{Format comparer|#t-fmt}} puts all fifteen variants side by side with what each can do (random access, column projection, append, streaming) and rough read speeds.
