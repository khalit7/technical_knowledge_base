In one screen

The earlier stages of the pipeline decide which text a model trains on. This page is about the plumbing after that: how the chosen text is stored on disk, and how it is loaded, a batch at a time, into a training job running on hundreds or thousands of GPUs, so that every GPU gets the right tokens, in a well-mixed order, without waiting, and so that a crash at step 300,000 resumes at exactly step 300,001.

1. DocumentsText plus metadata (URL, crawl, scores) in JSONL or Parquet. What the pipeline writes and what gets published.
2. Tokenize onceEvery document turned into token ids, offline, on CPUs, with an end-of-document token after each.
3. Token shardsFlat arrays of ids (2 or 4 bytes each) plus an index of where documents end. What a pretraining run reads.
4. Index and shuffleCut the stream into fixed-length windows (packing) and fix their order with a seed.
5. LoaderEach data-parallel rank reads its own windows, a few batches ahead, in worker processes.
6. GPUGets a batch of shape (batch, sequence length) every step. Saves "samples consumed" with each checkpoint.

1. The two lives of a corpus

A curated corpus lives twice, in two different shapes, because two different readers want it.

As documents. The curation pipeline (extraction, filters, dedup, quality scoring) works on documents: one web page's text plus its metadata, the facts about it (URL, crawl, language score, quality score, duplicate-cluster id). People and later pipeline runs want to read these: to inspect what a filter dropped, to filter again at a new threshold, to publish the corpus. So documents are stored as records, one per document, in a general-purpose format: JSON Lines or Parquet (sections 2 and 3). FineWeb ships Parquet; DCLM-baseline and Nemotron-CC ship zstd-compressed JSON Lines.

As tokens. A language model never sees text. It sees token ids, integers that index its vocabulary (the {{Tokenizers|n:3c65c17b0d0d817187bcd94a1b0f15ea}} page explains how text becomes ids). Tokenizing is expensive enough, and a training run reads the data often enough, that it is done once, offline, and the result is stored as flat arrays of integers with a small index of where each document ends (section 5). The training job then reads raw numbers, without parsing anything.

How big is each life? On the running example, measured:

Bytes per Qwen3 token on the first 2,000 rows of the setup's random FineWeb sample (1,422,641 Qwen3 tokens; 1,464,937 GPT-2 tokens). "Per trillion tokens" is the same ratio scaled, derived: bytes per token × 1012. Cross-checks against published corpora, also derived: Nemotron-CC states 6.3T tokens in 10.4 TiB of zstd JSONL (its {{data page|https://data.commoncrawl.org/contrib/Nemotron/Nemotron-CC/index.html}}), 1.82 bytes per token in its own tokenizer, against our 1.93; FineWeb's card lists its June 2025 crawl as 419.6 GB of snappy Parquet for 152.4B GPT-2 tokens, 2.75 bytes per token, against our 2.92.

The rule of thumb this gives you
English web text is about 4.8 bytes of UTF-8 per token with a modern 150k vocabulary, about 1.9 bytes per token once compressed, and exactly 2 or 4 bytes per token as a training array. So a trillion training tokens is about 2 TB (vocabulary under 65,536) or 4 TB (larger vocabularies) of token files, and roughly the same again for the compressed documents you keep beside them.
