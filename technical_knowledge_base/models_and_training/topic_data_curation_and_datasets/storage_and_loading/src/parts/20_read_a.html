The idea in one screen

Keep the corpus twice: documents, compressed, for people and pipelines, and tokens, as flat fixed-width arrays the GPU can slice; then make the training order a pure function of (seed, samples consumed), so every rank gets packed, well-mixed windows and a restart continues at exactly the next sample.

From curated documents to a GPU batch: what each stage stores, per token

Bars are bytes per Qwen3 token to scale, measured on 2,000 FineWeb documents (the uint16 bar is per GPT-2 token) measured. Documents shrink to about 1.9 bytes per token compressed; token files are exactly 2 or 4. Everything below the token file is computed, not stored: the order comes from the seed, and the checkpoint only needs the number of samples consumed.

1. The two lives of a corpus

As documents: one web page's text plus its metadata (URL, crawl, language score, quality score, duplicate-cluster id), one record per document. People and later pipeline runs read these to inspect what a filter dropped, to filter again at a new threshold, to decontaminate against a new benchmark, to publish. FineWeb ships Parquet; DCLM-baseline and Nemotron-CC ship zstd-compressed JSON Lines. Token files cannot be re-filtered or re-tokenized, so the documents are kept beside them.

As tokens: a model sees only token ids. Tokenizing is done once, offline, and stored as flat integer arrays with a small index of where each document ends (section 5); the training job reads raw numbers and parses nothing. On the running example:

First 2,000 rows of the setup's random FineWeb sample (1,422,641 Qwen3 tokens; 1,464,937 GPT-2 tokens) measured; "per trillion tokens" is bytes per token × 1012 derived. Cross-checks, derived: Nemotron-CC states 6.3T tokens in 10.4 TiB of zstd JSONL (its {{data page|https://data.commoncrawl.org/contrib/Nemotron/Nemotron-CC/index.html}}), 1.82 bytes per token in its own tokenizer, against our 1.93; FineWeb's card lists its June 2025 crawl as 419.6 GB of snappy Parquet for 152.4B GPT-2 tokens, 2.75 bytes per token, against our 2.92.

Rule of thumb
English web text is about 4.8 bytes of UTF-8 per token with a modern 150k vocabulary, about 1.9 bytes per token compressed, and exactly 2 or 4 bytes per token as a training array. A trillion training tokens is about 2 TB (vocabulary under 65,536) or 4 TB of token files, and roughly the same again for the compressed documents kept beside them.

2. Documents on disk: JSON Lines and compression

JSON Lines (JSONL) is one JSON object per line, {"text": "...", "url": "...", "language_score": 0.93, ...}: any language reads it, a broken line breaks one record, files concatenate with cat. The 2,000 documents take 7.70 MB, 6.80 MB of it the text and the rest keys and metadata repeated on every line. A compressor replaces repeated byte sequences with references to earlier ones: gzip (DEFLATE, {{RFC 1951 and 1952|https://www.rfc-editor.org/rfc/rfc1952}}, levels 1 to 9) or zstd (Zstandard, open-sourced by Facebook in 2016, {{RFC 8878|https://www.rfc-editor.org/rfc/rfc8878}}, levels 1 to 22), which compresses better at the same speed and decompresses several times faster (the {{zstd README benchmark|https://github.com/facebook/zstd#benchmarks}} published, vendor). The level trades write time for size; read speed barely depends on it, so data written once and read many times can afford a high level.

zstd keeps shrinking with level; gzip stops at level 6

Bytes on disk for the same 2,000 documents measured, src/scripts/formats.py; gzip from Python's gzip module, zstd from zstandard 0.25.0. Read speeds of every format are in the {{Format comparer|#t-fmt}}.

The catch: no random access. A gzip or zstd stream is one chain: to reach document 1,500 you decompress documents 1 to 1,499. Reading 200 random documents from the 2,000-document .jsonl.zst took about 1.8 s; the same 200 from the token file of section 5 about 5 ms rough. Fine for pipeline stages, which read files start to end; wrong for a training loader that wants sample 8,213,511 now. Corpora live with it by keeping files small (thousands per crawl) and converting to an indexed format before training.
