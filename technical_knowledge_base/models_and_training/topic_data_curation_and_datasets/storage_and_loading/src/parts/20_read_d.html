7. Packing documents into windows, and their boundaries

The problem. A GPU trains on rectangles: a batch of sequences all of the same context length L (2,048, 4,096, 8,192 tokens). Documents are not that shape. In our sample the median document is 466 Qwen3 tokens and the 90th percentile 1,386, so most documents are far shorter than any window, and a few are longer.

Four ways to fill the windows, all measured on the same 2,000 documents at L = 2,048 measured:

  • Pad: one document per window, the rest filled with a padding token that is masked out of the loss. 2,143 windows, 67.6% of positions are padding: two thirds of the compute does nothing. (Padding to the longest sequence in the batch instead of to L helps a little, and is what fine-tuning code does; for pretraining the waste stays large.)
  • Truncate: one window per document, the tail of long documents thrown away: 12.4% of all tokens lost, and padding as before.
  • Concatenate and chunk ("packing" in most code, GPT-3, nanoGPT, Megatron's default): join all documents with EOD tokens in between and cut every L tokens. 696 windows, 99.95% real tokens. The price: 605 of the 2,000 documents are cut by a window boundary, so their second part is trained without its beginning; and in a causal model every token can attend to the end of the previous, unrelated document, unless something stops it.
  • Best-fit packing ({{Ding et al. 2024|https://arxiv.org/abs/2404.10830}}): first split only documents longer than L, then place the pieces longest first, each into the window with the least room that still fits it, a classic bin-packing heuristic called Best-Fit Decreasing. 697 windows (one more than concatenation), and only the 93 documents longer than 2,048 tokens are ever cut.

The {{Packing lab|#t-pack}} animates all four on the same documents, with an attention picture per window and a slider for L.

Document boundaries in attention. When several documents share a window, there are two choices. Let every token attend to everything before it in the window (cheap, the standard GPT-3 setup), or apply a document mask, an attention mask that lets a token attend only to earlier tokens of its own document, usually with position ids restarting at each document. On our windows at L = 2,048, 53% of the (query, key) pairs a causal model computes cross a document boundary; at 8,192 it is 81% measured. A document mask removes them, and a variable-length attention kernel (FlashAttention's varlen interface, PyTorch's FlexAttention with a document mask) also skips their compute. Megatron exposes this as reset_attention_mask and reset_position_ids (gpt_dataset.py lines 800-860); datatrove's dataset can return per-document positions read from the .index file (utils/dataset.py lines 70-127).

What the evidence says published:

  • Llama 3: "We use an attention mask that prevents self-attention between different documents within the same sequence. We find that this change had limited impact during in standard pre-training, but find it to be important in continued pre-training on very long sequences" ({{Llama 3 paper, section 3.2|https://arxiv.org/abs/2407.21783}}).
  • Ding et al. 2024 (LLaMA-architecture 7B and 13B models, AWS) report relative gains from best-fit packing of +4.7% on reading comprehension, +16.8% on context following and +9.2% on program synthesis, and up to 58.3% less closed-domain hallucination (abstract). Their Table 10 separates the mask from the packing at 2k context: concatenation 46.71% reading comprehension, concatenation with a document mask 47.92%, best-fit packing with the mask 48.92%; summarisation got worse with the mask alone (12.16 to 11.79 ROUGE-2) and better with packing (13.14). Perplexity moved only with the mask (9.64 to 9.53). Their Table 1: the optimised algorithm packs 1 billion documents in 10,816 s on one CPU thread.
  • Zhao et al. 2024 ({{arXiv 2402.13991|https://arxiv.org/abs/2402.13991}}) find intra-document causal masking improves language modelling and downstream results, and that packing related documents together (retrieved by BM25) helps further.
  • For fine-tuning-style data the waste of padding is the headline: Krell et al. ({{arXiv 2107.02027|https://arxiv.org/abs/2107.02027}}, Graphcore) found up to 50% padding in common NLP datasets and a 2× speedup for BERT phase-2 pretraining from packing.

When it matters. For short web documents and 2k to 8k windows the gains reported are small to moderate; they grow with long contexts and with data where whole documents matter (code files, long articles, instruction data). The waste of padding always matters. The Topic: llm-training-and-post-training page's {{Pretraining|n:3c65c17b0d0d814f82cffd0d5c0dd5ba}} child covers sequence length schedules and long-context stages.

8. Sharding: splitting the data across files, ranks and workers

A shard is one file (or one directory of files) holding a slice of the dataset. Sharding exists because nothing at this scale can be one file: writers run in parallel (one output shard per pipeline task), readers run in parallel (each data-parallel rank, that is each model replica in data-parallel training, reads different data, and each rank's loader runs several worker processes), a failed task redoes one shard, and object stores serve many medium-sized objects better than one huge one.

How data reaches each rank. Two designs. Index-based (Megatron, MosaicML Streaming, map-style PyTorch datasets with a DistributedSampler): every rank computes the same global sample order from the seed and takes its own slice of each global batch; shard boundaries do not matter. Shard-based (WebDataset, Hugging Face streaming IterableDataset): shards are dealt out, first across ranks (split_dataset_by_node), then across each rank's workers. Then the number of shards must be at least ranks × workers and preferably a multiple, or some workers idle and ranks finish at different times.

A version-specific trap, measured
With datasets 5.0.1, our 11-file streaming dataset reports num_shards = 11, but after .shuffle(seed, buffer_size) it reports 1: the new shuffle reads up to max_buffer_input_shards = 10 shard groups round robin into the buffer (iterable_dataset.py lines 3738-3830), and the wrapper exposes the minimum shard count of its sources. A DataLoader with 4 workers then warns "Too many dataloader workers: 4 (max is dataset.num_shards=1). Stopping 3 dataloader workers." and runs on one. Passing max_buffer_input_shards=1 restores 11 shards (and the older shuffle). Check num_shards after every transformation.

How big. Large enough that per-request latency and per-file overhead vanish, small enough that a worker starts quickly and a shuffle has many units to permute: tens of megabytes to a few gigabytes. MosaicML Streaming's default size_limit is 64 MiB; FineWeb's Parquet files are about 2 GB with 2 MB row groups inside, which act as the real reading unit.

9. Shuffling

The problem. Stochastic gradient descent assumes each batch is a fair sample of the data. Pipeline output is the opposite: files are written per crawl, per language, per quality bucket, per source. Read in order, a model sees one bucket for thousands of steps, then the next; its gradients are biased toward whatever it is reading, and the loss curve jumps at every switch.

Three ways to shuffle at scale.

  1. Global permutation. Number every sample and permute the numbers with a seed (Megatron's shuffle_index, any map-style dataset with a shuffling sampler). Perfect mixing, deterministic, and only possible because token files allow reading sample k directly.
  2. Shard order plus a buffer. For sequential formats (tar, Parquet, JSONL streamed): shuffle the order of shards, read them sequentially, and keep a shuffle buffer of B examples, emitting a random one and replacing it with the next read. Memory is B examples, mixing reaches only about B examples back, so B must be large compared with a shard (WebDataset, Hugging Face IterableDataset.shuffle, default B = 1,000).
  3. Shuffle offline. Write the token shards already shuffled (datatrove's tokenizer and merger, section 6), then read them sequentially at train time. Cheap at train time, but fixed: a new order means rewriting the data.

MosaicML Streaming mixes 1 and 2: shards are grouped into blocks of shuffle_block_size samples (default at least 262,144) and samples are permuted within blocks, so memory and downloads stay bounded while mixing stays wide.

And with several DataLoader workers each batch is built inside one worker from its shards, so 4 workers drop the average to 3.6 buckets per batch even with a 1,000-example buffer.

10. Streaming from object storage

Object storage (Amazon S3, Google Cloud Storage, Azure Blob, and the S3-compatible stores most clusters run) keeps files as whole objects addressed by key and served over HTTP, with byte-range reads. It scales throughput by parallelism rather than by a fast single stream: Amazon's guidance is "at least 3,500 PUT/COPY/POST/DELETE or 5,500 GET/HEAD requests per second per partitioned Amazon S3 prefix", with no limit on prefixes ({{AWS S3 performance guidelines|https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html}} published, vendor). Every request also pays a fixed latency, which is why shards and row groups are megabytes, not kilobytes.

Three ways to read from it.

  • Copy first: sync the token files to local NVMe or a parallel file system before training (Meta trained Llama 3 from Tectonic, a distributed file system of 240 PB on 7,500 servers sustaining 2 TB/s, peak 7 TB/s, and names highly bursty checkpoint writes as its main challenge, {{Llama 3, section 3.3.1|https://arxiv.org/abs/2407.21783}}).
  • Stream with a local cache: MosaicML Streaming and LitData download shards ahead of use into a local cache (predownload, cache_limit) and evict old ones, and make the sample order independent of the number of nodes (num_canonical_nodes), so a job can resume on a different cluster size.
  • Stream without a cache: Hugging Face load_dataset(..., streaming=True) reads Parquet row groups over HTTP as it goes; WebDataset reads tar shards from any URL or pipe. Simple, but every epoch downloads everything again.

Not run here: throughput from object storage depends on the network and the store, and a laptop on home broadband would teach nothing that transfers. The {{Throughput calculator|#t-calc}} shows how little bandwidth text needs, which is why streaming text works at all.
