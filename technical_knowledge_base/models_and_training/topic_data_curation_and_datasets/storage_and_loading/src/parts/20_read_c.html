5. Token files: what a pretraining run actually reads

The problem. A training step needs, for each sequence in the batch, a run of token ids of exactly the context length. Parsing JSON and running a tokenizer for every step would burn CPU on every node and make every run depend on tokenizer code. So the corpus is tokenized once and stored as the thing the GPU wants: integers.

How it works. Every document's ids are written one after another into one binary file, each id as a fixed-width integer, usually with an end-of-document token (EOD, for example <|endoftext|>) after each document so the model learns where texts stop. Beside it, an index records where each document ends. The file is then memory-mapped (section 3): tokens[i : i + 2049] costs one page-cache lookup, no parsing and no copy of the rest of the file. Compressing a token file with zstd saves less than you might hope (uint32 Qwen3 ids: 5.69 MB to 2.38 MB; uint16 GPT-2 ids: 2.93 MB to 2.10 MB) and kills random access, so token files are normally stored raw.

The 16-bit trap, measured
Qwen3's vocabulary has 151,669 entries, so its ids need 18 bits. In our 2,000 documents, 34,587 of 1,422,641 tokens (2.4%) have ids of 65,536 or more, and 1,942 documents (97%) contain at least one. Written as uint16, each such id silently becomes id mod 65,536, another real token. Nothing crashes; the model trains on corrupted text. datatrove's default token_size=2 and nanoGPT's hard-coded uint16 both do this if you change the tokenizer and forget the width. Check: after writing, read back a shard and compare max(ids) with the vocabulary size, and decode one document.

From one token file to training samples: Megatron's three indices

A token file is one long stream. Something must decide which slices become samples, in which order, for how many epochs, and how to resume. nanoGPT's answer is the simplest possible one: at every step, draw random start positions (torch.randint(len(data) - block_size, ...), train.py lines 116-131). There is no notion of an epoch, and random draws with replacement both repeat and miss text: after as many windows as would cover the file once, a share of about e−1 ≈ 36.8% of tokens has never been seen (simulated on a 50-million-token array: 36.8% derived) while others were seen twice or more.

Megatron-LM's GPTDataset instead builds three small arrays once, saves them as .npy files beside the data, and memory-maps them in every rank (gpt_dataset.py lines 475-660):

  1. document_index: every document id once per epoch, all epochs shuffled together with numpy.random.RandomState(seed) (_build_document_index, lines 734-765).
  2. sample_index: walks that shuffled document order as one concatenated stream and records, for every sample, the document position and token offset where it starts; each sample is sequence_length + 1 tokens, the extra one being the last target (helpers.cpp build_sample_idx, lines 144-249).
  3. shuffle_index: a permutation of the sample numbers, from the same random state (_build_shuffle_index).

Sample k of the run is then shuffle_index[k] → two rows of sample_index → a few slices of the token file. Everything is a pure function of the seed, so a restart only needs the number of samples consumed so far (section 12). Step through it on twelve real documents:

6. Tokenizing at scale

How it is done. Tokenizing is embarrassingly parallel: each document is independent. Pipelines run it as many CPU tasks, one per input file, each writing its own token shard: datatrove's DocumentTokenizer (which also shuffles documents inside each output file, and whose DocumentTokenizerMerger shuffles across files, so the training reader can then read sequentially: "heavily optimized for sequential reads, and we actually pre-shuffled the data", utils/dataset.py line 39), or Megatron's tools/preprocess_data.py with many worker processes.

The cost. On this machine the Hugging Face tokenizers library (Rust) encoded 50,000 FineWeb documents (37.6M Qwen3 tokens) at about 1.4M tokens per second with 4 threads and about 0.49M tokens per second on one thread rough. At 0.49M tokens per core-second, 15 trillion tokens need about 3.1 × 107 core-seconds, about 8,500 core-hours derived: an afternoon on a 2,000-core cluster, and a once-only cost. Doing it inside the training loop instead would cost every training node's CPUs for the whole run, and couple the run to the tokenizer version.

What to record. The tokenizer's name and revision (the same text is a different number of tokens per tokenizer: 4.77 characters per Qwen3 token on these 50,000 documents; the {{Pretraining corpora|n:3c65c17b0d0d81f382b6e75707d00663}} page measures GPT-2 against Qwen3), the id width, whether an EOD token was appended, and the document count, so a later reader can verify a shard before training on it.
