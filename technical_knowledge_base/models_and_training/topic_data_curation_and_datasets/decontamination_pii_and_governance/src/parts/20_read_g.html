Common mistakes

Trusting a dataset-level threshold
Tulu 3's rule calls a training set contaminated above 2% of an evaluation's items. Measured here, Tulu 3's own RLVR prompts contain @@mmlu_hsm_copies@@ MMLU high-school-mathematics test questions with their answers: @@mmlu_hsm_share@@ of that subject, but only @@mmlu_all_share@@ of MMLU, under the threshold. Check per subject (or per benchmark slice) as well as per benchmark.
Decontaminating only against the benchmarks you report today
Next quarter's evaluation suite will include sets your data was never checked against. Keep the n-gram index code and the per-document provenance so the check can be re-run, and record which evaluations each data version was cleaned against (Tulu 3 separated "development" and "unseen" suites for this reason).
Treating every flag as contamination
On the web samples here no flagged page contained a test question: they quoted famous passages the items quote, or shared a stock question stem. Removing them costs text and buys nothing. Label a sample of what your rule removes before deciding what to remove.
Normalising numbers or punctuation without thinking about maths
Stripping punctuation merges z^4 + z^2 with z^4 - z^2; replacing numbers with 0 makes any twelve-number run match any table. Both happened here (section 3). For maths and code benchmarks, match on a normalisation that keeps operators and digits, or confirm matches by comparing answers.
Checking prompts against the test question only
Few-shot prompts carry exemplars. Every Tulu 3 RLVR maths row starts with the same worked examples, so a check that scans the whole prompt flags the exemplars, and one that skips them may skip the real question at the end. Know where the question sits in each format.
Assuming n-grams catch paraphrases
They do not: Yang et al.'s rephrased MMLU had an n-gram F1 of 0. Use embedding similarity to propose candidates and a judge (a person or an LLM) to decide, for synthetic and distilled data especially.
Reading a membership-inference AUC from WikiMIA as evidence about a benchmark
Most of that signal is the date shift between old and new Wikipedia articles (Duan et al.). Evidence about one item from loss alone is weak; use set-level tests.
Scrubbing PII after deduplication is skipped, or before extraction
Repeated PII is what gets memorised, so dedup is part of PII handling; and scrubbing raw HTML misses addresses that extraction later assembles from separate elements, while Cloudflare-obfuscated emails survive as "[email protected]" placeholders. Scrub the extracted text, after dedup.
Honouring robots.txt only at crawl time
A site that blocks an AI crawler today is still in every old crawl. Decide whether you apply current signals retroactively (Apertus did, at about 8% of English tokens) and record the decision with the data version.
Dropping provenance fields to save space
Without the source id and URL a removal request or a licence question cannot be answered from the data. The fields are a few dozen bytes per document against kilobytes of text.

Interview questions

Your model scores 15 points above expectations on one benchmark. How do you check for contamination?
Search the training data for the benchmark: 8-gram coverage per item (Llama 3 / ConTAM style, longest match), list the items with high coverage, read them, and split the benchmark into clean and contaminated parts. If the clean part scores the same, contamination is not the explanation (GPT-3, DCLM). If you cannot search the data, use set-level model probes (exchangeability, dataset inference) and a fresh parallel test set (GSM1k), not single-item loss.
Why 13-grams in GPT-3 and 8-grams in Llama 3 and Tulu 3?
Longer n means fewer false positives from common phrases but more misses when the copy is slightly edited. Singh et al. found n above 8 causes false negatives in estimating the score inflation; GPT-3 compensated for 13 by ignoring n-grams frequent in training data. Measured here, 13-grams flagged @@iq_13_docs@@ web documents across the samples and 8-grams with Tulu's coverage rule flagged @@iq_8_docs@@; none contained a test question.
Document, paragraph or span: what do you remove?
Depends on the data. Post-training: drop the example. Pretraining: remove the matched span with a margin (GPT-3) or the paragraph, keep the rest, and do not remove pages that only share a famous passage. Always log removals so a later audit can retrain or re-score.
Which PII detector would you use for a 10-trillion-token web corpus, and for a chat-log fine-tuning set?
Web: regexes for emails and IPs (cheap, high precision; FineWeb, Dolma), maybe phones with a strict pattern, after dedup; NER over that volume costs GPU-hours and mangles place names and public figures. Chat logs: a model-based detector (Presidio-style NER plus regexes, or a fine-tuned NER like StarPII for code), masking with typed placeholders, and a review of a sample of what it missed.
A site owner asks you to remove their site from your training data. What has to exist for that to take an hour, not a month?
Per-document provenance (URL, host, source id, data version), an index from host to document ids in every derived dataset (filtered, deduped, tokenised shards), and a pipeline that can rebuild or mask shards. Then a removal is a join and a rebuild of the affected shards; record it so future versions keep it out.
System design: design the decontamination, PII and governance stage for a 15T-token pretraining corpus and a 1M-example post-training mixture.
Clarify: which evaluations (development and held-out), which jurisdictions (EU AI Act summary?), retroactive opt-out policy. Index: 8-gram and 13-gram hashes of every evaluation item (questions and answers separately, normalisation that keeps digits and operators for maths and code), stored with item ids; the test side is a few million n-grams, a hash set in memory on every worker. Pretraining pass: one streaming pass, sharded by WARC file (stateless tasks on Slurm or Ray, datatrove-style), emitting per-document matches (item, coverage, longest run) as an attributes file rather than deleting; drop n-grams that hit more than about 10 documents as boilerplate; remove spans for "copy" matches, keep "passage" matches; canary-string filter. PII: after dedup, regexes for emails and IPs (plus IBAN and cards with checksums) replaced by typed placeholders; dropping documents with many hits. Post-training: prompts only, Tulu 3's rule per evaluation and per subject, embedding top-k plus an LLM judge for paraphrases in synthetic and distilled sets, drop matched examples, NER-based PII scrubbing. Governance: per-document provenance (source id, URL, crawl, licence field, signals present: robots.txt for AI tokens at crawl time and current, TDMRep, noai), a host-to-shard index for removals, a datasheet and Croissant metadata per release, the AI Act summary computed from provenance. Validation: read stratified samples of what each rule removed; report clean-subset scores for every benchmark; re-run the index when the evaluation suite changes. Cost: one extra pass at tokenising speed; the expensive parts are the LLM judge on post-training candidates and NER where used.
