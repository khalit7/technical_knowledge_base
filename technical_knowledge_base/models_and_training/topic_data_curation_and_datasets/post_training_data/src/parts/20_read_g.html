7. Verifiable-reward data: a prompt, a label and a checker

The problem. Reinforcement learning needs a reward for every sampled answer, millions of times. A judge model is slow and can be gamed; a program is fast and cannot be argued with, so where an answer can be checked mechanically (a number, a passing test, a formatting rule) RLVR uses a checker. A row is then: a prompt, a label (the reference answer, the tests, the constraint's parameters) and the name of the checker. The model learns whatever the checker rewards, so every checker error becomes a training signal: a false negative (a right answer scored 0) pushes the model away from correct behaviour, a false positive pays it for a wrong one.

Math: extracting the answer is the hard part

A checker first extracts an answer from free text (the last number; the content of the last \boxed{}; the sentence "The final answer is ...") and then compares it with the label (as strings, after normalising LaTeX, or symbolically). Six extractors from the root's lab (Tulu 3's own GSM8K and MATH verifiers, the strict Minerva sentence, exact \boxed{}, "The answer is", Hugging Face's Math-Verify 0.8.0), run here on DeepSeek-R1's real answers, the case RL actually sees; the root's {{Post-training data lab|n:3c65c17b0d0d811fa5ecda8d365ab00f}} ran them on reference solutions.

Offline difficulty filtering

A prompt the model always solves gives every rollout the same reward, so with group-relative methods (GRPO and relatives) its advantage is zero and it teaches nothing; a prompt it never solves does the same. OLMo 3 generated eight rollouts per prompt from the initial checkpoint and removed "all samples that the model easily solves (that is, those with a pass rate greater than 62.5%)" (Sec. 4.4.2). The cut is visible in the released data measured: over all @@rl_pr_rows@@ math, code and IF rows with a recorded pass rate, the highest is @@rl_pr_max@@ (5 of 8), and @@rl_pr_zero@@ rows (@@rl_pr_zero_pct@@) have a pass rate under 1/16 (in effect none of eight right), kept although they give no signal at the start of training (the 7B run filtered only from above).

Code: tests are labels, and labels can be weak

A code row is a problem statement, hidden tests (input and expected output), and a checker that runs the program in a sandbox. Published pipelines lose many problems to the tests themselves: open-r1's Python set went from @@code_all@@ problems (copied from PrimeIntellect's SYNTHETIC-1 pool) to @@code_decon@@ after 8-gram decontamination, to @@code_tested@@ in its "decontaminated-tested" version, in which every gold solution passes its own tests (test_reward = 1 on every row measured; the card does not say how the others failed). A test that the gold solution passes can still be too weak to fail a wrong one. Published: on hard problems TACO's tests accept wrong solutions often enough that "false positive rate" exceeds 90% ({{HardTests, arXiv 2505.24098|https://arxiv.org/abs/2505.24098}}).

Mutation testing, measured. For @@mut_n@@ seeded problems of that set, the gold solution and up to four mutants (one small change each: flip a comparison, add 1 to a constant, swap + and −, swap min and max), all run against the problem's tests (up to @@mut_max_tests@@) in a sandbox with no network and no file writes. A mutant that passes every test is indistinguishable from the gold solution to the reward.

@@mut_read@@ The fix is in the data: generated inputs checked against the gold solution (HardTests, CodeContests+), or tests chosen because they kill mutants.

Instruction-following constraints

IFEval defined 25 constraint types a program can check ("answer in all lowercase", "at least 300 words", "end with this exact phrase") over 541 prompts, with a strict and a loose mode (the loose one also tries the answer without its first line, last line or markdown asterisks) ({{arXiv 2311.07911|https://arxiv.org/abs/2311.07911}}). RLVR sets attach such constraints to ordinary prompts: Tulu 3's 14,973 IF rows add one constraint each (24 types, about 620 rows each measured, root lab); Ai2's IF_multi_constraints_upto5 (@@if_multi_n@@ rows, used for OLMo 3's RL) adds up to five per prompt, in the style of IFBench's training data, which pairs Tulu 3 SFT prompts with "at least one and up to n constraints" and adds 29 new constraint types ({{arXiv 2507.02833|https://arxiv.org/abs/2507.02833}}). Two data facts worth knowing:

  • The reward is partial credit. open-instruct's IFEvalVerifier returns the share of constraints met (ground_truth_utils.py lines 310 to 355 at 72f46040), not IFEval's all-or-nothing prompt-level score. On OLMo 3's IF rollouts measured: @@rl_if_roll@@ rollouts meet all their constraints @@rl_if_all@@ times, partial credit sums to @@rl_if_partial@@; Ai2 recorded @@rl_if_rec@@ correct.
  • The base prompts come from the SFT mixture. Every IF_multi row keeps the id of the Tulu 3 SFT row its prompt came from; @@if_safety_pct@@ of them are prompts from the two adversarial safety subsets (WildJailbreak, WildGuardMix) with formatting constraints attached (section 9).
