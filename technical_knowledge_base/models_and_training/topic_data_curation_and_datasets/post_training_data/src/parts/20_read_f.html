6. Verifiable-reward data: a prompt, a label and a checker

RL needs a reward for every sampled answer, millions of times. Where an answer can be checked mechanically (a number, a passing test, a formatting rule), RLVR uses a program, so a row is a prompt, a label (reference answer, tests, constraint parameters) and the name of a checker. The model learns whatever the checker rewards: a false negative (a right answer scored 0) pushes it away from correct behaviour, a false positive pays it for a wrong one. How the reward drives the update, and what verifier errors do during RL, is on {{RL for LLMs|n:3c65c17b0d0d818c9bcff7177325fe56}} (section 5); here the question is whether the data's labels and checkers are right.

Difficulty: keep the prompts the model sometimes solves

A prompt the model always solves gives every rollout the same reward, so under group-relative methods (GRPO and relatives) its advantage is zero and it teaches nothing; a prompt it never solves does the same. OLMo 3 generated eight rollouts per prompt from the initial checkpoint and removed "all samples that the model easily solves (that is, those with a pass rate greater than 62.5%)" (Sec. 4.4.2).

Code: tests are labels, and labels can be weak

A code row is a problem, hidden tests (input, expected output) and a sandbox that runs the program. Passing the gold solution does not make a suite strong: on hard problems TACO's tests accept wrong solutions often enough that "false positive rate" exceeds 90% ({{HardTests, arXiv 2505.24098|https://arxiv.org/abs/2505.24098}}). Mutation testing measures it: for @@mut_n@@ seeded problems, the gold solution and up to four mutants (one small change each: flip a comparison, add 1 to a constant, swap + and −, swap min and max) run against the problem's tests (up to @@mut_max_tests@@) in a sandbox with no network and no file writes. A mutant that passes every test is, to the reward, the gold solution.

About one mutant in five survives every test; single-test problems are the weakest

@@mut_read@@ The fix is in the data: generated inputs checked against the gold solution (HardTests, CodeContests+), or tests chosen because they kill mutants.

Instruction-following constraints

IFEval defined 25 constraint types a program can check ("answer in all lowercase", "at least 300 words", "end with this exact phrase") over 541 prompts ({{arXiv 2311.07911|https://arxiv.org/abs/2311.07911}}); RLVR sets attach such constraints to ordinary prompts (Tulu 3's 14,973 IF rows, one each; Ai2's IF_multi_constraints_upto5, @@if_multi_n@@ rows with up to five, used for OLMo 3's RL). The reward is partial credit: open-instruct's IFEvalVerifier returns the share of constraints met (ground_truth_utils.py lines 310 to 355 at 72f46040), not IFEval's all-or-nothing score. On OLMo 3's IF rollouts measured, @@rl_if_roll@@ rollouts meet all their constraints @@rl_if_all@@ times, partial credit sums to @@rl_if_partial@@, and Ai2 recorded @@rl_if_rec@@ correct: a rollout meeting three of five constraints earns 0.6.
