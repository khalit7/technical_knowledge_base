1. Extraction: from a WARC record to the main text

The problem. A WARC response record is the bytes a server returned: HTTP headers, then HTML. Common Crawl's WET file has the same pages as text, but its converter keeps every visible string in page order, so training on it is training on menus. Every serious pipeline since 2021 re-extracts from the WARC: FineWeb with trafilatura, DCLM and Dolma 3 with resiliparse, Nemotron-CC with jusText published.

How a page looks to an extractor. A parser (lxml, or resiliparse's Lexbor) turns the HTML into the DOM, a tree of elements with attributes and text. The extractor walks it, decides block by block what is main content and what is boilerplate, then linearises what it kept: writes it out as text, choosing line breaks and what to do with lists, tables, code and maths. It has three kinds of evidence, each wrong on some pages:

<!-- illustrative: the shape of a typical page --> <body> <nav class="menu"> Home | Shop | Blog </nav> boilerplate: a tag name says so <div id="content"> main content: class/id hints <h1>Herbivory</h1> <p>Herbivory is the consumption of plant material ...</p> long, few links, many stop words <pre>def f(x): return x</pre> whitespace matters here </div> <div class="widget"><table id="wp-calendar">...</table></div> a sidebar calendar <footer> (c) 2024 ... Privacy policy </footer> </body>

Names (tag names, class and id attributes, ARIA roles), text statistics (length, link density, stop-word density) and position (what surrounds a block). The four libraries below weigh them differently.

2. Four extractors, four kinds of evidence

resiliparse: one pass of rules over names (DCLM, Dolma 3). It walks the DOM once in compiled code and asks one question of every element; a "no" skips the whole subtree. The checks: tag names (nav, aside always out), hidden attributes, about twenty class and id patterns (navigation, sidebar, footer, cookie, share, ads, comments, "related posts"), ARIA roles, and a link-density test on deep divs. No scoring and no second chance, so it is fast (DCLM: 4.55 MB/s per core against trafilatura's 0.56, Table 16 published; about 28 times faster here rough) and it fails when a site's class names do not say what a block is.

resiliparse in its source, and the settings used here (file:line, v1.0.9)

extract_plain_text(html, main_content=True) walks the DOM once, in C++ over the Lexbor parser, and asks _is_main_content_node about every element (resiliparse-py/resiliparse/extract/html2text.pyx:530-726). The checks, in order: tag names (nav, aside, audio, video, time are always out; a footer or ul near the top of the body or with a link ratio above 0.2 is out), the hidden and aria-hidden attributes, then about twenty regular expressions over class and id (lines 469-489: navigation, sidebars, footers and cookie banners, social buttons, ads, logos, modals, galleries, comments, sign-in links, "related posts"), ARIA roles such as banner and navigation, and finally a link-density test on deep divs (more than 60% of text in links, under 1,500 characters: out). An article whitelist regex (article|entry|post|content|body|text|page) rescues blocks before the blacklists are tried.

Settings matter: Dolma's toolkit calls it with main_content=True, alt_texts=False, links=False, comments=True, list_bullets=True, preserve_formatting=True (dolma/warc/linearizers.py:34-47, v1.2.1), which is what this page uses.

trafilatura: XPath rules, then three fallbacks (RefinedWeb, FineWeb). It cleans the tree, looks for the body with a list of XPath expressions (class names such as "entry-content", then <article>, then "main"), compares its result with readability's, rescues short results with jusText, and finally grabs whatever text the page has. The trafilatura cascade in its source (file:line, v1.11.0)

bare_extraction (trafilatura/core.py, v1.11.0) runs a cascade:

  1. Clean the tree (htmlprocessing.py:41-75): delete every element in MANUALLY_CLEANED (settings.py:211-219: aside, footer, form, nav, script, figure, iframe, and also math, which matters in section 5) and strip the tags in MANUALLY_STRIPPED.
  2. Find the body (main_extractor.py:535-591): try the expressions of BODY_XPATH (xpaths.py:13-54) in order: elements whose class contains "post-content", "entry-content", "article-body" and many others; the first <article>; more class patterns; anything whose class or id starts with "main". Inside the match, prune by more XPath lists (footers, "related", "share", "cookie", "sidebar", "nav", and even any class containing "bar": xpaths.py:105-130) and by link density (htmlprocessing.py:129-161: with favor_precision, a paragraph under 200 characters whose links hold more than 80% of its text goes).
  3. Compare with readability (external.py:45-109, core.py:202): run its bundled copy of readability-lxml; take readability's text instead when trafilatura found nothing, or when readability found more than twice as much and the result does not start with "{", or in two borderline cases.
  4. Rescue with jusText (external.py:132-169): when the result is under 250 characters or still contains unwanted elements, run jusText with loosened thresholds (length 50, stop-word bounds 0.1 and 0.2, every language's stop-word list merged) and keep its text if it is not four times shorter.
  5. Baseline (core.py:205-206): if the text is still under 250 characters (MIN_EXTRACTED_SIZE, settings.cfg:19), grab the page's <article>, its paragraphs, or its whole body text.

jusText: classify blocks, then let neighbours decide (Pile-CC, Nemotron-CC). It splits the page into blocks at block-level tags and classifies each on its own: bad if more than 20% of its characters are in links (or it has a copyright sign), short if under 70 characters, otherwise good or near-good by stop-word density (0.32 and 0.30). Then four passes revise the uncertain blocks from their neighbours. Stop words make it language-specific: with the English list, a German page is all "bad". jusText in its source, and a pass that never runs (file:line, v3.0.2; issue #45)

jusText (Pomikálek, 2011) splits the cleaned page into blocks at block-level tags (paragraphs, headings, list items, table cells) and gives each one a context-free class (justext/core.py:243-275): bad if more than 20% of its characters are in links, if it contains a copyright sign, or if it sits inside a select; short if under 70 characters; then by stop-word density, good if at least 0.32 and over 200 characters, near-good if at least 0.30, else bad. Then four passes revise the uncertain ones from their neighbours (core.py:307-371): headings close before a good block; short blocks between two good ones become good, between two bad ones bad; near-good blocks become bad only when surrounded by bad; headings again.

A pass that never runs. The first pass ("good headings", core.py:313-326) is meant to promote a short heading when a good block follows within 200 characters. But it copies each block's class while it iterates, so the blocks after the heading still have the empty class they were created with (paragraph.py:22) and the test never succeeds. The animation's third step shows it changing nothing. Reported upstream as issue #45 (open since 2022-11-09). Fixing it changes jusText's output on [[JT_FIX_CHANGED]], always by keeping more text measured; the fourth pass partly makes up for it, which is why heading 12 in the animation is rescued at the last step.

readability: score containers by the paragraphs inside them. readability-lxml (a port of Arc90's Readability, the ancestor of Firefox's reader view) deletes elements whose class or id looks unlikely ("comment", "sidebar"), scores every paragraph (one point, plus one per comma, plus one per 100 characters up to 3), passes the score to its parent and half to its grandparent, scales each container by one minus its link density, and keeps the best container with its good siblings. It fails on pages with no single dominant container (forums, listings, data tables), where it returns one fragment.

readability in its source (file:line, v0.9)

readability-lxml first deletes elements whose class or id looks unlikely ("comment", "footer", "sidebar", "menu" and others, unless they also look like "article", "content" or "main": readability.py:28-46, 775-790). It then scores every p, pre, td and blockquote of 25 characters or more: 1 point, plus one per comma, plus one per 100 characters up to 3 (score_paragraphs, lines 675-725); the paragraph's parent gets the score and its grandparent half of it. Containers start from a class weight (plus or minus 25 for "article"-like or "comment"-like names) and a tag bonus (+5 for div, -5 for headings and nav), and every score is multiplied by one minus the container's link density. The best-scoring container wins, with its good siblings (select_best_candidate, lines 629-664).
