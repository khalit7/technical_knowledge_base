In one screen

A web crawl stores pages as the server sent them: HTML, with menus, cookie banners, scripts and footers wrapped around whatever the page is about. Before a model can learn from it, two jobs must happen. Extraction turns each HTML page into plain text and tries to keep only the page's main content. Filtering then throws away whole documents (wrong language, spam, lists of links, adult sites) or individual lines (a "Read more" here, a "3 likes" there) using cheap rules and small classifiers. Together they decide most of what a web-trained model ever sees: on our one file of Common Crawl, 20,991 fetched pages become 2,692 English documents that pass every rule.

The whole page follows one file, the topic's running example: one WARC file (a Web ARChive file: Common Crawl's container of raw HTTP responses) from Common Crawl's July 2024 crawl, CC-MAIN-2024-30, with 20,991 responses. The root's {{Pipeline lab|n:3c65c17b0d0d811fa5ecda8d365ab00f}} tab pushes it through a FineWeb-style pipeline and draws the funnel; this page opens each box of that funnel and measures what is inside. 1. From a WARC record to a tree of elements

The problem. A WARC response record is the bytes a server returned: HTTP headers, then an HTML document. Common Crawl also publishes a WET file per WARC file: the same pages already turned into text, but by a converter that keeps every visible string, in page order. Training on that is training on menus. So every serious pipeline since 2021 re-extracts from the WARC (FineWeb with trafilatura, DCLM and Dolma 3 with resiliparse, Nemotron-CC with jusText) published.

How a page looks to an extractor. A browser, or a parser such as lxml or resiliparse's Lexbor, turns the HTML into the DOM (Document Object Model): a tree whose nodes are elements (<div>, <p>, <nav>, <table>) with attributes (class="sidebar", id="content") and text. An extractor walks this tree and decides, node by node or block by block, what is the page's main content and what is boilerplate (navigation, headers, footers, cookie notices, share buttons, "related articles", ads). It then linearises what it kept: writes it out as text, choosing where line breaks go and what to do with lists, tables, code and maths.

Three kinds of evidence are available, and the four extractors below use them in different proportions: names (tag names, class and id attributes, ARIA roles), text statistics (length, link density: the share of a block's characters inside links, stop-word density: the share of its words that are function words such as "the" and "of"), and position (what surrounds a block).
