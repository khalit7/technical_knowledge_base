In one screen

A web crawl stores pages as the server sent them: HTML, with menus, cookie banners, scripts and footers wrapped around whatever the page is about. Before a model can learn from it, two jobs must happen. Extraction turns each HTML page into plain text and tries to keep only the page's main content. Filtering then throws away whole documents (wrong language, spam, lists of links, adult sites) or individual lines (a "Read more" here, a "3 likes" there) using cheap rules and small classifiers. Together they decide most of what a web-trained model ever sees: on our one file of Common Crawl, 20,991 fetched pages become 2,692 English documents that pass every rule.

The whole page follows one file, the topic's running example: one WARC file (a Web ARChive file: Common Crawl's container of raw HTTP responses) from Common Crawl's July 2024 crawl, CC-MAIN-2024-30, with 20,991 responses. 1. From a WARC record to a tree of elements

The problem. A WARC response record is the bytes a server returned: HTTP headers, then an HTML document. Common Crawl also publishes a WET file per WARC file: the same pages already turned into text, but by a converter that keeps every visible string, in page order. Training on that is training on menus. So every serious pipeline since 2021 re-extracts from the WARC (FineWeb with trafilatura, DCLM and Dolma 3 with resiliparse, Nemotron-CC with jusText) published.

How a page looks to an extractor. A browser, or a parser such as lxml or resiliparse's Lexbor, turns the HTML into the DOM (Document Object Model): a tree whose nodes are elements (<div>, <p>, <nav>, <table>) with attributes (class="sidebar", id="content") and text. An extractor walks this tree and decides, node by node or block by block, what is the page's main content and what is boilerplate (navigation, headers, footers, cookie notices, share buttons, "related articles", ads). It then linearises what it kept: writes it out as text, choosing where line breaks go and what to do with lists, tables, code and maths.

<!-- illustrative: the shape of a typical page --> <body> <nav class="menu"> Home | Shop | Blog </nav> boilerplate: a tag name says so <div id="content"> main content: class/id hints <h1>Herbivory</h1> <p>Herbivory is the consumption of plant material ...</p> long, few links, many stop words <pre>def f(x): return x</pre> whitespace matters here </div> <div class="widget"><table id="wp-calendar">...</table></div> a sidebar calendar <footer> (c) 2024 ... Privacy policy </footer> </body>

Three kinds of evidence are available, and the four extractors below use them in different proportions: names (tag names, class and id attributes, ARIA roles), text statistics (length, link density: the share of a block's characters inside links, stop-word density: the share of its words that are function words such as "the" and "of"), and position (what surrounds a block). None of them is right on every page, which is why the next section reads their source.

2. Four ways to find the main text, read from the source

All four libraries answer the same question with different evidence. Read them in order of increasing cleverness; the files and lines are at the pinned versions above.

resiliparse: one pass of rules over names (DCLM, Dolma 3)

How it works. extract_plain_text(html, main_content=True) walks the DOM once, in C++ over the Lexbor parser, and asks _is_main_content_node about every element (resiliparse-py/resiliparse/extract/html2text.pyx:530-726). A "no" skips the whole subtree. The checks, in order: tag names (nav, aside, audio, video, time are always out; a footer or ul near the top of the body or with a link ratio above 0.2 is out), the hidden and aria-hidden attributes, then about twenty regular expressions over class and id (lines 469-489: navigation, sidebars, footers and cookie banners, social buttons, ads, logos, modals, galleries, comments, sign-in links, "related posts"), ARIA roles such as banner and navigation, and finally a link-density test on deep divs (more than 60% of text in links, under 1,500 characters: out). An article whitelist regex (article|entry|post|content|body|text|page) rescues blocks before the blacklists are tried.

Cost. One linear pass in compiled code, no scoring, no second chance: DCLM measured 4.55 MB/s per core against trafilatura's 0.56 (Table 16, published), and on this machine it ran about 28 times faster than trafilatura (root's Pipeline lab, rough). When it fails: when a site's class names do not say what a block is, or say the wrong thing. Settings matter: Dolma's toolkit calls it with main_content=True, alt_texts=False, links=False, comments=True, list_bullets=True, preserve_formatting=True (dolma/warc/linearizers.py:34-47, v1.2.1), which is what this page uses.

trafilatura: XPath rules, then three fallbacks (RefinedWeb, FineWeb)

How it works. bare_extraction (trafilatura/core.py, v1.11.0) runs a cascade:

  1. Clean the tree (htmlprocessing.py:41-75): delete every element in MANUALLY_CLEANED (settings.py:211-219: aside, footer, form, nav, script, figure, iframe, and also math, which matters in section 5) and strip the tags in MANUALLY_STRIPPED.
  2. Find the body (main_extractor.py:535-591): try the expressions of BODY_XPATH (xpaths.py:13-54) in order: elements whose class contains "post-content", "entry-content", "article-body" and many others; the first <article>; more class patterns; anything whose class or id starts with "main". Inside the match, prune by more XPath lists (footers, "related", "share", "cookie", "sidebar", "nav", and even any class containing "bar": xpaths.py:105-130) and by link density (htmlprocessing.py:129-161: with favor_precision, a paragraph under 200 characters whose links hold more than 80% of its text goes).
  3. Compare with readability (external.py:45-109, core.py:202): run its bundled copy of readability-lxml; take readability's text instead when trafilatura found nothing, or when readability found more than twice as much and the result does not start with "{", or in two borderline cases.
  4. Rescue with jusText (external.py:132-169): when the result is under 250 characters or still contains unwanted elements, run jusText with loosened thresholds (length 50, stop-word bounds 0.1 and 0.2, every language's stop-word list merged) and keep its text if it is not four times shorter.
  5. Baseline (core.py:205-206): if the text is still under 250 characters (MIN_EXTRACTED_SIZE, settings.cfg:19), grab the page's <article>, its paragraphs, or its whole body text.

Measured: which branch produced the text. Instrumenting those calls on all 20,280 pages that passed the URL filter (trafilatura 1.11.0, datatrove's settings, no timeout) shows how often the clever part is the part that decides:

So trafilatura is less one algorithm than a vote among four, with a crude fallback for a quarter of the crawl. Pages that end in "baseline" are mostly short: product pages, error pages, listings; the heuristic filters later remove most of them.

jusText: classify blocks, then let neighbours decide (Pile-CC, Nemotron-CC)

How it works. jusText (Pomikálek, 2011) splits the cleaned page into blocks at block-level tags (paragraphs, headings, list items, table cells) and gives each one a context-free class (justext/core.py:243-275): bad if more than 20% of its characters are in links, if it contains a copyright sign, or if it sits inside a select; short if under 70 characters; then by stop-word density, good if at least 0.32 and over 200 characters, near-good if at least 0.30, else bad. Then four passes revise the uncertain ones from their neighbours (core.py:307-371): headings close before a good block; short blocks between two good ones become good, between two bad ones bad; near-good blocks become bad only when surrounded by bad; headings again. Stop words make it language-specific: with the English list, a German page is all "bad".

A pass that never runs
The first pass ("good headings", core.py:313-326) is meant to promote a short heading when a good block follows within 200 characters. But it copies each block's class while it iterates, so the blocks after the heading still have the empty class they were created with (paragraph.py:22) and the test never succeeds. The animation's second step shows it changing nothing. Reported upstream as issue #45 (open since 2022-11-09). Fixing it changes jusText's output on 843 of the 20,265 pages it parsed (4.2%), always by keeping more text measured; the fourth pass partly makes up for it, which is why heading 12 in the animation is rescued at the last step.

readability: score containers by the paragraphs inside them

How it works. readability-lxml (a port of Arc90's Readability, the ancestor of Firefox's reader view) first deletes elements whose class or id looks unlikely ("comment", "footer", "sidebar", "menu" and others, unless they also look like "article", "content" or "main": readability.py:28-46, 775-790). It then scores every p, pre, td and blockquote of 25 characters or more: 1 point, plus one per comma, plus one per 100 characters up to 3 (score_paragraphs, lines 675-725); the paragraph's parent gets the score and its grandparent half of it. Containers start from a class weight (plus or minus 25 for "article"-like or "comment"-like names) and a tag bonus (+5 for div, -5 for headings and nav), and every score is multiplied by one minus the container's link density. The best-scoring container wins, with its good siblings (select_best_candidate, lines 629-664). When it fails: pages with no single dominant container (forums, listings, tables of data), where it returns one fragment.

3. Measured: the same pages through six extractors

The experiment. Take the 20,280 pages of our WARC file that pass the URL filter. Extract each with six methods, then run exactly the same filters on every result: run0's datatrove chain (lid.176 English above 0.65, Gopher repetition and quality rules, C4's rules without terminal punctuation, FineWeb's three rules). Count what comes out, and how much of it FineWeb itself kept from this file (2,425 documents; FineWeb used trafilatura with these settings). The chain run on trafilatura's text reproduces run0 exactly: 2,692 kept, 2,404 of them in FineWeb measured.

What it shows. Common Crawl's WET text has three times trafilatura's characters but survives the filters worst: its menus and widgets make the repetition and line rules fire. jusText with an English stop-word list returns nothing for most non-English pages (it acts as a second language filter) yet keeps the most English documents, because its block classification keeps short paragraphs that trafilatura's precision mode discards; only 1,946 of its 3,231 are documents FineWeb kept. Nemotron-CC made the same observation at scale: on 13 Common Crawl snapshots, jusText plus their filters gave 1,380 billion tokens and 104 billion "high-quality" tokens (FineWeb-Edu classifier score 3 or more) against trafilatura's 994 and 80 billion, and jusText without their filters 1,804 and 127 billion (Table 1, arXiv 2412.02595, published; the table's "+28.6%" and "+57.4%" are consistent with its rounded 80, 104 and 127 within rounding).

Is the text right, not just long? Counting kept documents says nothing about whether the extractor chose the right lines. For that you need pages where people marked the main content by hand. The Web Content Extraction Benchmark (Bevendorff et al., SIGIR 2023; 3,985 pages from eight older datasets, Apache-2.0) has them. The ablations that matter, as published. FineWeb trained 1.71-billion-parameter models on 28 billion tokens of trafilatura-on-WARC text and of WET text, both with only fastText English filtering, and the WARC model was ahead throughout (FineWeb paper section 3.2 and its Figure 1, arXiv 2406.17557v2; the curves are plotted, no table, so no number is read from them here; note the section's text says "Fig. 2" for a result whose caption is Figure 1). DCLM (Table 3, 1B parameters, 1x compute) scored 24.1 Core with resiliparse, 24.5 with trafilatura and 20.7 with WET, and chose resiliparse for its speed published. So the big step is WARC instead of WET; among main-content extractors the downstream difference is small, and the choice is about cost, recall (Nemotron-CC) and what happens to code, tables and maths (section 5).

4. Why extractors fail, page by page

The root's Pipeline lab found three telling pages. Reading the HTML and the code explains each one; open them side by side in the Extraction comparer.

The calendar widget. An advocacy site's sidebar holds a WordPress calendar (<table id="wp-calendar">, one cell per day). WET keeps every cell: "M", "T", "W", "1", "2" ... as lines of text. trafilatura and resiliparse both drop it, for the same reason: an ancestor's class or id contains "sidebar" (trafilatura's OVERALL_DISCARD_XPATH, xpaths.py:105-130; resiliparse's sidebar_cls_regex, html2text.pyx:476, matches the list's class "sidebar_widgets").
Menu lines ending in "|". A university weather page is laid out as one HTML <table>: a menu cell and a content cell. trafilatura keeps tables and writes each cell followed by " | " and each row on its own line (xml.py:320-343), so the whole menu ("Animate: ON | OFF Switch Channel: Visible True Color ...") becomes one long line ending in "|". resiliparse writes the same cells as separate lines. Layout tables are a 1990s habit, still common on university and government sites.
The "dropped" data table. A railway reference page's mileage list is not a table at all: it is a <pre> block. Both trafilatura and resiliparse keep its two data lines; what differs is that resiliparse also keeps the heading and the "Last update" line, and only resiliparse keeps the tab between mileage and place name. Correction to the Pipeline lab's caption ("resiliparse drops the data"): neither drops it; its own line masks show both keeping lines 20 and 21 measured.

The cache that makes extraction depend on page order

datatrove's Trafilatura step calls extract(..., deduplicate=True) by default (pipeline/extractors/trafilatura.py:27,49-54). In trafilatura that switches on a process-wide least-recently-used cache of 4,096 text segments (deduplication.py:231, settings.py:191): every paragraph over 100 characters is counted, and from its fourth sighting on it is dropped (duplicate_test, lines 242-253; MAX_REPETITIONS = 2, settings.cfg:29); the same test on the whole extracted body drops entire documents (core.py:228). It is a cheap within-site boilerplate remover: a disclaimer repeated on every page of a site disappears after three pages.

But a cache in a worker process makes the output depend on which pages that process saw before, in what order. Running all 20,280 pages through one process three ways:

Why it matters on a cluster. FineWeb split each crawl into 8,000 tasks (examples/fineweb.py:65); each task's sandbox process has its own cache, and datatrove restarts the sandbox after a timeout, which empties it. So the same page can come out differently depending on the task it lands in and on how loaded the node was. The effect is small in aggregate (1.25% of characters here) but it breaks reproducibility, and it is a near-duplicate filter nobody configured. Pass deduplicate=False and deduplicate later, on purpose (Deduplication).

5. Tables, code and maths

The problem. A main-content extractor is tuned on news articles and blog posts. Three structures carry meaning in their layout, and each extractor linearises them differently: a table (rows and columns), a code block (line breaks and indentation, which in Python are syntax), and maths (written as TeX for MathJax to render in the browser, or as MathML, an XML language for formulas, with TeX attached as an annotation and an image as fallback).

Measured on more pages. Our random WARC file holds 3 pages with MathML among 20,280, too few to say anything. So this page fetched 131 distinct pages from the same crawl, chosen from sites known for each structure, by looking their URLs up in Common Crawl's index and range-requesting the single WARC record of each: Stack Exchange questions (MathJax TeX in the text), arXiv abstracts, Wikipedia maths articles (MathML), Python and JavaScript documentation and Stack Overflow (code in <pre>), Wikipedia "List of" articles and statistics sites (tables). What happens, mechanically.

  • Code. trafilatura 1.11 turns the Python documentation's example class, a <pre> block full of syntax-highlighting <span>s, into one line ("class Foo: def __getitem__(self, index): ... def __len__(self): ..."). Traced on that page: its own XPath path produced the text, no fallback was involved, and its clean-up function trim is ' '.join(string.split()) (utils.py:333-339), which turns every run of whitespace, newlines included, into one space; only a few code paths ask to preserve spaces (main_extractor.py:246, 277, 390). trafilatura 2.3.1 keeps indentation on about two thirds of such lines. resiliparse's serialiser keeps <pre> text verbatim (preserve_formatting=True). jusText rejects code blocks: code has almost no English stop words.
  • Maths. On Wikipedia every extractor but jusText removes all 804 formulas: trafilatura deletes <math> elements outright (MANUALLY_CLEANED, settings.py:211-219), resiliparse with Dolma's settings drops the fallback image's alt text, which is where Wikipedia also puts the TeX (alt_texts=False). What is left reads "Suppose that for every where is the indicator function": sentences with holes. On Stack Exchange the TeX is plain text between dollar signs, so it survives whenever the post survives. OpenWebMath had to write its own extractor on top of resiliparse for exactly this reason: most LaTeX on Common Crawl is MathJax source that only the browser's JavaScript turns into maths, so the delimiters must be found in the raw HTML (OpenWebMath, arXiv 2310.06786, sections 3 and B, published).
  • Tables. trafilatura writes Markdown-like rows ("Acquisition date | Company | Business |" then "---|---|"), resiliparse writes cells separated by tabs with one row per line, readability-lxml flattens a whole table into a single paragraph.
The fingerprint in FineWeb itself
The filters after extraction remove what the extractor left. In 50,000 random FineWeb documents from CC-MAIN-2024-30, not one contains the character "{", the string "javascript" or "lorem ipsum" (C4's rules drop such documents or lines), not one has a line starting with four spaces or a tab (datatrove's C4 step strips every line, c4_filters.py:95, so indentation cannot survive even if an extractor kept it), and none contains "\frac" measured. A general web corpus built this way has no code with braces and no LaTeX at all; code and maths need their own pipelines (The Stack, OpenWebMath, FineMath, MegaMath; see Pretraining corpora).
Predict: FineWeb's ablation of C4's rules says the curly-bracket rule removes 2.8% of tokens. What does a rule that drops any document containing "{" do to a dataset meant to teach code?

6. Language identification

The problem. Common Crawl is multilingual and its pages do not reliably say what language they are in. An English corpus must drop everything else; a multilingual corpus must route each document to its language. Language ID runs right after extraction because it is cheap and removes most of the crawl: here 12,270 of 19,241 extracted documents (64%) are not English above the threshold (root's Pipeline lab).

How a fastText language identifier works. The text (newlines replaced by spaces: datatrove utils/lid.py:54) is split into words, and each word into its character n-grams with boundary markers: "<the>" gives "<t", "th", "he", "e>", "<th", "the", "he>" and so on. Every word and n-gram is hashed into one of a fixed number of buckets and looked up in a table of small vectors; the document's vector is their average; one linear layer and a softmax turn it into a probability for each label (Joulin et al., "Bag of Tricks", arXiv 1607.01759). It ignores word order entirely, which is why it is fast (about a millisecond for a whole web document here, a hundredth of trafilatura's time, rough) and why it is fooled by text that is not prose. A label for noise matters: a model without one must call a page of numbers some language.

The threshold, and where 0.65 comes from

A document is kept as English when the model's English probability passes a threshold. RefinedWeb introduced 0.65 for lid.176's top-language score and said why: below it "usually corresponds to pages without any natural text" (section 3.1, arXiv 2306.01116); FineWeb kept it. Others chose differently published: CCNet and Dolma 0.5 (Dolma section 5.1: it removed 61.7% of the data by bytes), mC4 0.7, Nemotron-CC 0.3 (with pycld2 as a second opinion), C4 0.99 with langdetect (TFDS c4_utils.py:116), and FineWeb2 a threshold per language: max(0.3, min(0.9, median - one standard deviation)) of that language's score distribution (FineWeb2 section 4.2, arXiv 2506.20920). On our documents that rule gives 0.71 for lid.176's English scores and 0.79 for GlotLID's derived.

Measured: two models on the same 19,241 documents. lid.176 and GlotLID agree on the top language for 93.6% of documents. Above 0.65, lid.176 keeps 6,971 as English and GlotLID 6,962; 6,534 are English for both. Common Crawl's own CLD2 label in the WET header says English for 6,879 of them. Where the models disagree, the documents are mostly not prose: navigation-only pages, product grids, pages mixing two languages. The Language ID lab has the full confusion table, a threshold slider for both models and the disagreeing documents.

Code-switching and mixed pages

A document-level label hides pages that are partly in another language: a Spanish article with an English menu, an Indonesian shop with English product names, a bilingual government page. Classifying every line of at least four words with GlotLID, 362 of 7,885 (4.6%) of the documents labelled English have at least 20% of their line characters confidently (score 0.5 or more) in another language, and 1,749 of all 19,241 do measured. A document-level filter keeps or drops those lines with the rest; line-level language ID (what GlotLID's authors recommend for low-resource corpora, and what CCNet does for paragraphs) can keep the right part.

Low-resource languages

lid.176 has 176 labels, so a page in a language it does not know is forced onto the closest one it does. GlotLID gave 531 of our documents a language that lid.176 has no label for (counting by ISO 639-3 code, macrolanguages joined) measured. But read them before celebrating coverage: the top four are Dagbani, Angika, Kirmanjki and Nigerian Pidgin, and lid.176 calls most of them English. A spot check of 24 (hand-checked) found none actually in those languages: they are navigation menus, server directory listings, calendars, timetables, product tables and code in English, Japanese, French, German and others. Text that is not prose lands on whichever small language's training data looked most like lists. This is the "noise" problem GlotLID's authors describe, and the reason FineWeb2 sets thresholds per language and runs further filters for low-resource ones. For a multilingual corpus a large label set decides whether a language exists in the data at all, which is why FineWeb2 switched to GlotLID after training models on documents chosen by each identifier: GlotLID was better on higher-resource languages and slightly behind on lower-resource ones in their runs (FineWeb2 section 4.2 and its Figure 5; plotted, not tabulated) published.

Common mistake: reading the threshold as a quality knob
Documents near 0.65 are mostly English pages that are not prose (the root's Pipeline lab read them: menus, tables, a PHP error log). Raising the threshold removes them, and the cost falls on the edges of English: Dolma audited its identifier on the International Corpus of English (spoken and written English from nine countries) and found every document kept at its threshold of 0.5 but some lost as the threshold rises, "a majority" still kept at 0.9 (Dolma Appendix G and Figure 7, arXiv 2402.00159; the per-region shares are only plotted) published. Measure what a threshold removes before using it as a quality filter; quality has its own classifiers (Quality classifiers and data selection).

7. The heuristic rules, one by one

The problem. After language ID most English pages are still not text worth training on: shop listings, link lists, login pages, spam, truncated teasers. Model-based classifiers can judge this (see Quality classifiers and data selection), but they cost more and encode someone's taste. So pipelines first apply heuristic rules: one statistic computed from the text, one threshold, drop the document past it. Three families are in every modern English pipeline, applied in this order by FineWeb and by our run0:

  • Gopher repetition (DeepMind's MassiveText, Rae et al. 2021, Appendix A, Table A1): the share of duplicated lines and paragraphs, of characters in them, of characters in the most frequent 2-, 3- and 4-gram, and in all repeated 5- to 10-grams. Purpose, in the paper's words: repetition "is often linked with uninformative content", and repetitive training data may make a model repeat itself.
  • Gopher quality (same appendix): 50 to 100,000 words, mean word length 3 to 10 characters, hash and ellipsis symbols at most 0.1 per word, at most 90% of lines starting with a bullet and at most 30% ending with an ellipsis, at least 80% of words containing a letter, and at least two of eight English stop words ("the", "be", "to", "of", "and", "that", "have", "with"). Gopher chose simple rules "to remove low-quality data while minimising potential for bias".
  • C4 (Raffel et al. 2020, section 2.2): keep only lines ending in terminal punctuation and with at least 5 words, drop pages with fewer than 3 sentences, any bad word, "lorem ipsum" or a curly bracket, drop lines mentioning JavaScript. FineWeb found the terminal-punctuation rule the strongest single C4 rule but too costly (it removed about 30% of tokens) and left it off.
  • FineWeb's own (Penedo et al. 2024, section 3.6): drop a document when at most 12% of its lines end in punctuation, when at least 10% of its characters are in duplicated lines, or when at least 67% of its lines are 30 characters or shorter. They found them by comparing histograms of many statistics on two versions of the 2013-48 crawl, the better-scoring per-crawl deduplicated one and the worse globally deduplicated one, putting thresholds where the worse version was denser (16 candidates), then ablating each with 28-billion-token runs on the 2019-18 crawl and keeping the three that helped most: together about 22% of tokens removed and about 1% better aggregate score (section 3.6 and Figure 8) published. The paper's 0.1 for duplicated-line characters replaced MassiveText's 0.2.

How to check a rule: read what it drops. A drop count says nothing about whether the dropped documents were bad. For every rule this page drew up to 20 more of run0's drops (seed 1) on top of the Pipeline lab's 8 (seed 0), plus 40 more kept documents, and labelled each from its opening lines: R right drop, W wrong drop (coherent, informative text worth training on), U unclear hand-labelled, 495 new labels in all. The bar is the wrong-drop share with its 95% Wilson interval; the label counts are small, so read the intervals, not the bars.

What the labels say.

  • Safe rules: too few words, too few stop words, top 2-, 3- and 4-gram, lines ending in an ellipsis. Their drops are near-empty pages (login forms, "JavaScript required", empty carts), navigation menus, and lists of truncated teasers. Zero or one wrong drop in 28 each.
  • Rules that misfire on formats, not on quality: the bullet-line rule counts any line starting with "-" (gopher_quality_filter.py:101-105), and trafilatura writes every list item as "- item", so an article written as a list goes (8 of 27 wrong). The curly-bracket rule removes any page with a code sample (6 of 13). The FineWeb duplicated-line rule at datatrove's 0.01 removes articles whose only repetition is a heading or a date line printed twice (10 of 28).
  • Reading the first lines can mislead the labeller too. Most line-punctuation drops look like articles in their first 200 characters but are one or two teaser lines cut mid-sentence by the site; the one real false drop found was an essay whose author hard-wrapped every line, so no line ended in punctuation.
  • Kept is not clean: of 64 kept documents labelled across both samples, 17 are junk the rules missed (product pages, a sales page, spun SEO text, an Italian page that passed English language ID): the rules remove the worst, a classifier is still needed.

The Rule workbench lets you move every threshold at once and see how many documents survive, how many of them FineWeb kept, and how many labelled good documents you lose; the Label browser shows every labelled document with its excerpt.

9. Line-level edits against document-level decisions

The problem. Many pages are a good paragraph surrounded by debris the extractor let through: "Share", "3 likes", "Read more", a date, an address block. A document-level rule keeps or drops the whole page; a line-level rule deletes the debris and keeps the rest. Line edits rescue text but can leave fragments, and they change the statistics every later rule sees (in datatrove the FineWeb rules run on the text C4 already edited, c4_filters.py:135).

Three line-level schemes, all measured on the 6,971 English documents:

  • C4 as FineWeb runs it (no terminal-punctuation rule): delete lines of fewer than 3 words, lines mentioning JavaScript, lines with cookie or terms-of-use phrases. It deleted 71,012 of 193,197 lines (37%) but only 5.1% of characters, and edited 1,414 of the 2,692 documents that survive every rule measured; a re-implementation that records each line's reason matches datatrove's output on 6,971 of 6,971 documents.
  • C4 as C4 ran it: also delete every line that does not end in ".", "!", "?" or a quote. That deletes 34.6% of all characters, close to the 30% of tokens FineWeb reports for this rule measured.
  • RefinedWeb's line-wise corrections (App. G.2): delete lines that are mostly upper case, only digits, a counter ("3 likes"), one word, or a short call to action ("sign in", "read more", "items in cart"), and drop the document if those lines hold more than 5% of its words. RefinedWeb did not release this code; this page's version is a reconstruction from the paper's description with guessed pattern lists, so its counts show the mechanism, not RefinedWeb's numbers: it would drop 1,526 of the 6,971 documents and 152 of the 2,692 our chain keeps reconstruction.

The same document, from the running example and in FineWeb, under each scheme:

An environmental organisation's volunteer event page (the place names are a public reserve). Line decisions computed by this page's re-implementations, checked against datatrove for C4 measured.

The lesson. FineWeb's C4 step keeps this page but turns "LOCATION / 176 Bells Pocket Road / Strathpine / QLD 4500" into a lone "176 Bells Pocket Road"; C4's terminal-punctuation rule cuts it to three sentences, which datatrove's default minimum of five rejects (C4's own minimum of three would keep it); the RefinedWeb-style rule throws it away for having too many flagged lines. None of the three is wrong in general; each makes a different trade between keeping text and keeping text coherent. Check line-level rules by reading edited documents, not only dropped ones.

10. URL and domain filters

The problem. Some sites should never be fetched into a corpus (adult content, malware, spam farms, file hosts), and the cheapest place to stop them is before extraction, from the URL alone. RefinedWeb chose to filter adult content only by URL, arguing that classifiers and word lists over content "overfilter" minority and medical text (App. G.1, citing Welbl et al. 2021 and Dodge et al. 2021) published.

How it works. RefinedWeb aggregated about 4.6 million domains from the UT1 blacklists of the Université Toulouse 1 Capitole (a list maintained for school and university proxies), choosing ten categories (adult 4,516,478 entries, phishing 42,445, dating, gambling, file hosting, ddos, "agressif", chat, mixed adult, French regulated gambling: Table 13), then removed fewer than 100 benign but prolific domains found by inspecting every URL matched more than 4,000 times in 832 million pages (6.04 million, 0.73%, matched). Beside the list, three word lists score the URL itself: "strict" subwords banned anywhere (even split across dots and dashes), "hard" whole words, and "soft" words needing two hits (App. G.1.2). datatrove ships this design: URLFilter (pipeline/filters/url_filter.py:33-132) checks the registered domain, the full host, the exact URL, then the three word lists, with the lists inside the package published.

  • Where datatrove's list comes from. Of its 4,558,940 domains, 4,536,294 (99.5%) are in today's UT1 adult category and 21,839 in phishing (the categories overlap); only 390 are in no current UT1 category measured. It is RefinedWeb's list, frozen.
  • It ages. UT1's adult category, downloaded on 2026-10-15, has 62,986 domains datatrove's copy lacks. On our 19,424 pages a fresh list with RefinedWeb's categories would remove 42 more (7 adult, 13 gambling, 8 dating, 6 file hosting, 4 phishing, 4 mixed adult) measured.
  • Words in URLs are evidence, not proof. The root's Pipeline lab read the 77 word-based drops on this file: 10 were ordinary pages whose URL shared a word with the lists. One quirk in the code: for the hard and soft lists the URL is split into words without lower-casing (url_filter.py:120) while the lists are stored lower case (line 21), so an upper-case banned word in a URL path escapes them; only the subword check lower-cases the URL (line 128).

11. Toxicity and adult content

The problem. A URL list misses adult or hateful text on ordinary domains (forums, comment sections, fan fiction), and some builders want that text out of a pretraining set. Three approaches are in use, each with a known cost:

  • A word list over the content. C4 dropped any page containing a word from the "List of Dirty, Naughty, Obscene, and Otherwise Bad Words" (LDNOOBW; 403 English entries today), matched as whole words on lower-cased text (TFDS c4_utils.py:508-560). Dodge et al. (2021) showed the cost: documents classified as African-American English and Hispanic-aligned English were removed at 42% and 32%, against 6.2% for White-aligned English, and documents mentioning LGBTQ+ identities were removed far more often than the average (sections 5.2 and 5.3, arXiv 2104.08758) published.
  • A classifier over sentences. Dolma trained two fastText classifiers (word unigrams and bigrams, 100-dimensional, read from the model files) on the Jigsaw Toxic Comments data, one for "hate" and one for "NSFW", and removed every sentence scoring above a threshold. Its ablation compared τ = 0.4 (removing 5.5 to 7.3% of content) with τ = 0.0004 (29.1 to 34.9%): the stricter one scored better downstream, Dolma kept 0.4 to preserve scale (section 5.3 and Appendix H, arXiv 2402.00159) published.
  • External signals. Gopher removed pages failing Google's SafeSearch, explicitly instead of word lists because of Dodge et al.'s finding; FineWeb filters adult content by URL only published.

Measured on what our pipeline kept. The 2,617 documents that survive run0 (URL list, language ID, every heuristic rule, MinHash and PII scrubbing) still contain material a content filter would act on:

The bad-word rule would remove 147 of the 2,617 kept documents (5.6%). Reading 30 of them: 21 are ordinary text whose only "bad word" is a medical, anatomical or everyday term, 6 are adult or hateful pages the URL list missed hand-labelled. Dolma's sentence classifiers at 0.4 would delete text from 257 of the kept documents (0.4% of their characters); at 0.0004, 11.4% of characters measured. Which to use depends on what the model is for: a filter that removes the vocabulary of sexual health also removes the model's ability to discuss it.

12. Putting it in order: cost and design

Cheapest first, and keep every drop. The order of a pipeline is set by cost per document and by what each stage needs: the URL check reads only the URL; extraction must run before anything can read text; language ID costs about a millisecond and removes most of a multilingual crawl; rules that tokenise (Gopher with spaCy, C4 with NLTK's sentence splitter) cost more; model-based classifiers and MinHash come last, on what survives. Measured costs on this machine, all rough:

What transfers to a cluster. Every count and every kept-or-dropped decision on this page is deterministic given the same versions and inputs, and reproduces per document on a cluster (run0 does reproduce FineWeb's per-document decisions for 2,403 of the 2,425 documents FineWeb kept from this file, root's Pipeline lab). Timings do not transfer: they were taken at a load average of 20 to 90 on a laptop CPU. The per-page timeout does not transfer either: it is wall-clock time, so it drops more pages on a busier node, and the trafilatura cache depends on the order pages reach each worker.

A design that stays debuggable, the shape datatrove and the Dolma toolkit both encourage:

  1. Read WARC files in many parallel tasks; extract with resiliparse if CPU is the constraint, trafilatura with deduplicate=False if precision on articles matters more, and a separate extractor for code and maths pages.
  2. Write every document's statistics (language scores, every rule value) once, as a column, instead of filtering on the fly; thresholds then become queries you can change without re-extracting (the Dolma toolkit's "taggers then mixer" design, and how this page's rule workbench works).
  3. Keep every dropped document with its reason (datatrove's exclusion_writer), label a sample per rule, and diff your output against a published dataset built from the same crawl.
  4. Pin versions and write down every argument, including the ones you did not change.

13. Common mistakes

Training on WET text because it is already extracted
On our file the same filters keep 877 documents from WET against 2,692 from trafilatura and 2,150 from resiliparse; FineWeb and DCLM both measured WET as worse downstream. Re-extract from WARC.
Leaving trafilatura's deduplicate=True on in a distributed job
It is a hidden, order-dependent near-duplicate filter: 310 of our pages lost all their text to it and the output changed with page order. Turn it off and deduplicate as a separate, reproducible stage.
Expecting a general web pipeline to give you code and maths
trafilatura 1.11 flattens code blocks, every main-content extractor tested but jusText deletes Wikipedia's maths, and C4's curly-bracket rule removes any page with a brace: FineWeb's 50,000-document sample contains no "{" at all. Route code and maths pages to their own extraction (OpenWebMath's approach) and their own filters.
Copying an example script and assuming it reproduces the paper
datatrove's FineWeb example became multilingual when LanguageFilter's default changed in v0.3.0 (2024-08-28); its C4 defaults swap the paper's numbers; its FineWeb duplicated-line default is 0.01, not the paper's 0.1. Pass every argument explicitly and diff against the published dataset.
Judging a rule by how much it removes
The FineWeb duplicated-line rule removed 173 documents here, and 10 of 28 labelled ones were worth keeping. Label a sample of each rule's drops, near the threshold and at random, and report the wrong-drop share with its interval.
Labelling a document from its first lines
Truncated teasers and hard-wrapped essays look alike in the first 200 characters. Look at the structure (line count, line lengths, where lines end) before deciding.
Using the language-ID threshold as a quality filter
Near 0.65 sit English pages that are not prose, and raising it also removes English varieties and mixed-language pages. Use a quality classifier for quality.
Using a frozen blocklist
datatrove's domain list is RefinedWeb's from 2023; today's UT1 adult list has 62,986 more domains. Refresh lists, and re-check the prolific domains a list blocks (RefinedWeb removed fewer than 100 benign ones by hand).
Calling a word list "toxicity filtering"
A bad-word match is mostly anatomy, medicine and everyday slang; Dodge et al. showed it removes dialects and identity mentions disproportionately. Say what was filtered and measure what was lost.

14. Interview questions, with short answers

Why re-extract text from WARC when Common Crawl gives you WET?
WET keeps every visible string, so documents carry menus and widgets. That adds low-value tokens and distorts the statistics the filters use (duplicated lines, short lines, punctuation), so good pages are dropped and bad ones kept. FineWeb's and DCLM's ablations both show WARC extraction ahead; on our file the same filters keep 877 WET documents against 2,692 from trafilatura.
trafilatura or resiliparse for a 100-TB crawl?
DCLM found them equal downstream (24.5 against 24.1 Core at 1B scale) and resiliparse about 8 times faster per core, so resiliparse when CPU is the cost. trafilatura has a slightly higher precision on news-like pages and keeps tables as rows; resiliparse keeps code and the tab structure of preformatted text. Either way, turn off trafilatura's cache and handle code and maths separately.
How does jusText decide what is boilerplate?
It splits the page into blocks, classifies each from length, link density and stop-word density (good, near-good, short, bad), then revises short and near-good blocks from their nearest good or bad neighbours. It is language-specific through the stop-word list.
Why 0.65 for English language ID, and would you change it?
RefinedWeb chose it for lid.176 because lower scores are mostly pages without natural text; FineWeb kept it. For one language it is reasonable; for many, a per-language threshold such as FineWeb2's (median minus one standard deviation, clipped to 0.3 to 0.9) is better, since closely related languages have lower confidence. Check what sits near the threshold before moving it.
A rule removes 10% of your documents. How do you decide whether to keep it?
Read a sample of its drops near the threshold and at random and estimate the wrong-drop share with an interval; check what share of tokens it removes; then train small models with and without it (FineWeb's 28-billion-token ablations) and compare benchmark scores. A rule that removes formats (lists, code) rather than quality should be fixed, not tuned.
Line-level or document-level filtering?
Line-level edits rescue good paragraphs from debris but can leave incoherent fragments and change the statistics later rules see; document-level rules are safer for coherence and lose more text. C4 did both; FineWeb kept only C4's cheap line edits; RefinedWeb dropped a document when its edits exceeded 5% of words.
Design: build the extraction and filtering stage for a 2-trillion-token English pretraining run from 20 Common Crawl snapshots.
About 1.8 million WARC files (90,000 per crawl), so thousands of CPU tasks, one shard of files each, reading from object storage. Per document, in order: URL blocklist (refreshed) and word lists; extraction (resiliparse for throughput, deduplicate off), with code and maths pages routed to dedicated extractors; lid.176 or GlotLID with a checked threshold; Gopher repetition and quality rules, then C4 line edits and FineWeb's rules with explicitly set parameters; PII scrubbing. Write every statistic as columns plus the text, keep dropped documents with reasons, and log per-task stats. Then MinHash per crawl as a separate job, a quality classifier on survivors (GPU), and decontamination. Budget by measured throughput per core and by yield measured on a sample: here 13% of HTML pages and 19% of extracted characters survive the rules, before dedup and the classifier remove more, so size the number of snapshots from that, not from raw crawl size. Validate with a labelled sample per rule and small-model ablations before the full run.
