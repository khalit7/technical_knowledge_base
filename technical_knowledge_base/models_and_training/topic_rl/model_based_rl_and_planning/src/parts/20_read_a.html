The idea in one screen

Planning and learning are the same operation, a backup of values, applied to different experience: real, or simulated by a model. Every method on this page differs only in where the model comes from (given, as the rules of Go are, or learned), when the planning happens (in the background, or at decision time from the state the agent is in), and how far a learned model is trusted before its errors pile up.

1What a model is, and what planning means

"Given a state and an action, a model produces a prediction of the resultant next state and next reward" ({{Sutton and Barto §8.1|http://incompleteideas.net/book/RLbook2020.pdf#page=181}}). Dynamic programming needs a distribution model, p(s′, r | s, a), because its expected updates sum over every successor. Almost everything else uses a sample model: the book's example is the sum of a dozen dice, where a program that rolls twelve dice is easy and the table of all sums is "harder and more error-prone". Simulators, game engines and most learned models are sample models. Either part, transitions and rewards, can be given (the rules of Go, exactly; a physics simulator, approximately) or learned (Dyna's table; MuZero learns only what its search needs, §8).

Planning is "any computational process that takes a model as input and produces or improves a policy". The chapter's unifying claim: all state-space planning computes value functions, by backups applied to simulated experience. Learning is the same backups applied to real experience. The smallest case, random-sample one-step tabular Q-planning, picks a state and action at random, asks a sample model for a reward and next state, and applies the Q-learning update; it converges to the optimal policy for the model under the same conditions as Q-learning ({{§8.1|http://incompleteideas.net/book/RLbook2020.pdf#page=183}}).

Two times to plan. Background planning (DP, Dyna) gradually improves a value table or network, and actions are later read off it cheaply. Decision-time planning (heuristic search, rollouts, MCTS) starts when a state is reached and outputs one action; most of what it computes is discarded ({{§8.8|http://incompleteideas.net/book/RLbook2020.pdf#page=202}}). It suits problems with time to think per move, such as chess. AlphaZero does both: search at every move, and a network that learns from the search. "Model-based" does not mean "learned model": DP and AlphaZero use a given one. And the reward model of RLHF does not make RLHF model-based: nothing plans with it ({{RL for LLMs|n:3c65c17b0d0d818c9bcff7177325fe56}}).

Terms from control and planning (under 1 min)

Learning a model from data is what control engineers call system identification; Sutton and Barto borrow direct RL (values from real experience) and indirect RL (values through a model) from the adaptive control literature (chapter 8 notes, {{p. 192|http://incompleteideas.net/book/RLbook2020.pdf#page=214}}). This page is about state-space planning, search through states; plan-space planning, which edits whole plans, is "difficult to apply efficiently to the stochastic sequential decision problems" of RL.

2Dyna: learning, planning and acting together

Dyna (Sutton 1990, cited in {{Sutton and Barto's chapter 8 notes|http://incompleteideas.net/book/RLbook2020.pdf#page=214}}) is the hero figure as an algorithm. Each real transition updates Q directly and is stored in a table model; then n planning steps replay remembered transitions through the same update, "just as if they had really happened". Which simulated transitions to generate is called search control. The book's trade-off: indirect methods "often make fuller use of a limited amount of experience"; direct methods "are much simpler and are not affected by biases in the design of the model" ({{§8.2|http://incompleteideas.net/book/RLbook2020.pdf#page=185}}).

Tabular Dyna-Q (Sutton and Barto, p. 164) Loop forever: (a) S ← current state; (b) A ← ε-greedy(S, Q) (c) take A; observe R, S′ (d) direct RL: Q(S, A) ← Q(S, A) + α [R + γ max_a Q(S′, a) − Q(S, A)] (e) model learning: Model(S, A) ← R, S′ (deterministic environment assumed) (f) planning, repeat n times: S ← a random previously observed state; A ← a random action previously taken in S R, S′ ← Model(S, A); apply the update of (d)

Without (e) and (f) this is one-step Q-learning. Planning only replays pairs actually experienced, so the model is never asked about something it has not seen.

Example 8.1, the Dyna maze: a 6 × 9 grid with 47 open cells, reward +1 only for entering the goal, γ = 0.95, α = 0.1, ε = 0.1, 30 repetitions. With no planning (n = 0) the agent needed "about 25 episodes" to reach ε-optimal performance, n = 5 about five, and n = 50 "only three episodes" ({{Example 8.1|http://incompleteideas.net/book/RLbook2020.pdf#page=186}}). Without planning, a value moves back one cell each time the agent walks through. With n = 50, the goal's value spreads along everything already walked. The planning steps are not free: n = 50 does 50 table updates for every real one. Dyna pays when real steps are expensive (a robot, a user) and computation is cheap.

3When the model is wrong

Models are wrong because the environment is stochastic and few samples were seen, because function approximation generalised badly, or because the environment changed ({{§8.3|http://incompleteideas.net/book/RLbook2020.pdf#page=188}}). The two cases behave differently. An optimistic model corrects itself: in the blocking maze (Example 8.2) the short path is closed after 1,000 steps; the planned policy walks into the new wall, finds out, and both agents recover. A pessimistic model may never be corrected: in the shortcut maze (Example 8.3) a shortcut opens after 3,000 steps, and plain Dyna-Q "never switched to the shortcut. In fact, it never realized that it existed. Its model said that there was no shortcut, so the more it planned, the less likely it was to step to the right and discover it."

Dyna-Q+ treats this as exploration of the model: for each pair it counts the steps τ since it was last tried for real, and plans as if that transition paid a bonus.

planned reward = r + κ √τ
r
the reward the model predicts
τ
real time steps since the pair was last tried
κ
a small constant (the book gives no value; this page uses 10−3)

The bonus is used only in planning updates, so values become optimistic about long-untested actions and the agent goes to test them, even through long detours. The book's footnote adds that untried actions may be planned with, their initial model leading back to the same state with reward 0.

Optimism taken to its extreme: E3 and R-max (under 1 min)

Exploration bonuses taken "to its logical extreme" become provably efficient model-based algorithms: E3 (Kearns and Singh 2002) and R-max (Brafman and Tennenholtz 2003) assume every incompletely explored choice is maximally rewarding and plan to test it, and find a near-optimal policy in time polynomial in the number of states and actions; "usually too slow for practical algorithms but ... probably the best that can be done in the worst case" (chapter 8 notes). Exploration in general is on {{Bandits and exploration|n:3ee5c17b0d0d81acba54d70ac51c601c}}.

4Where to spend planning

Dyna replays transitions uniformly, which is wasteful: at the start of episode 2 only the pair leading into the goal has a non-zero value, so almost every replay moves zero into zero. Prioritised sweeping ({{§8.4|http://incompleteideas.net/book/RLbook2020.pdf#page=190}}; Moore and Atkeson 1993, Peng and Williams 1993) keeps a queue ordered by how much each pair's value would change and, after each update, pushes the predecessors of the changed state; on mazes of this shape it reached the optimum with fewer updates, "often by a factor of 5 to 10". Decision-time planning (§5) is the extreme of this focusing: all computation goes to the state the agent is in. The sweeps themselves are owned by {{Dynamic programming|n:3c65c17b0d0d81baada7e1c05ce69d01}} (section 12 and its Sweep lab, which races them on this same maze).

Sample against expected updates, trajectory sampling and RTDP (1 min)
  • Prioritised sweeping works backwards from wherever values changed, so the model must also predict predecessors; Example 8.4 allowed at most n = 5 updates per real step. The priority is |R + γ maxa Q(S′, a) − Q(S, A)|.
  • Sample against expected updates ({{§8.5|http://incompleteideas.net/book/RLbook2020.pdf#page=194}}). An expected update of one pair costs about b times a sample update, where b is the number of possible next states. With equally likely successors and correct successor values, t sample updates leave an error of √((b − 1)/(b t)) of the initial error, so a small fraction of b samples removes most of it. Sample updates are likely better "on problems with large stochastic branching factors and too many states to be solved exactly"; learned models in deep RL are sample models for this reason.
  • Trajectory sampling and RTDP ({{§8.6 to 8.7|http://incompleteideas.net/book/RLbook2020.pdf#page=196}}). Simulating whole trajectories under the current policy puts updates where the policy goes. In the book's random tasks this helped early and hurt late, and helped more with more states and fewer branches; real-time DP solved a racetrack with about half the updates of sweeping value iteration.
