2. Golden sets

A golden set is the instrument the gate reads, so it is built and maintained like code: sources in, tagged items, two suites with different jobs, a version number.

The tags make per-slice gating possible; the split keeps the pass rate readable. A regression item guards something that already works and should pass almost always (Anthropic: regression suites "should have a nearly 100% pass rate"); a capability item measures something the system cannot yet do and is expected to fail often. One pass rate over both moves for reasons nobody can read. Notion's team, in a {{Braintrust case study|https://www.braintrust.dev/blog/notion}} (vendor page, undated), notes that a new model "might pass a regression eval at 100%", which is why they also keep frontier evals: a set everyone passes has stopped measuring.

  • Sources: a representative slice of real traffic, deduplicated and scrubbed of personally identifiable information (PII); regression cases (every production incident becomes a test); adversarial and edge cases; and safety canaries, items that must always be refused or always be answered.
  • Each item carries an input, the expected behaviour (a reference answer, a rubric, or programmatic checks) and metadata tags: intent, difficulty, source incident. Section 3's animation could split its 160 turns only because MT-Bench tags every question with a category.
  • Size: the practical range is 100 to 500 items per product surface; smaller sets can gate only large effects, larger ones rot because nobody maintains them. Anthropic: "20-50 simple tasks drawn from real failures is a great start"; Hamel Husain and Shreya Shankar: regression sets "grow to 100 or more examples"; GitHub Copilot runs "more than 4,000 offline tests". Write each gate's minimum detectable effect next to its threshold, so nobody believes a 20-item slice can see a half-point drop (how many items a threshold needs: {{Eval statistics|n:3ef5c17b0d0d8187a7b4e5b4ec4a546d}}).

The FAQ's other working numbers: "Start with 100 diverse traces and annotate at least the first 30 yourself"; in CI, "Favor assertions or other deterministic checks over LLM-as-judge" ({{evals FAQ|https://hamel.dev/blog/posts/evals-faq/}}, September 2026 revision). Anthropic's own documentation leans the other way on volume: "More questions with slightly lower signal automated grading is better than fewer questions with high-quality human hand-graded evals" ({{Develop tests|https://platform.claude.com/docs/en/test-and-evaluate/develop-tests}}).

Lifecycle: a golden set decays

  • Decay. It drifts away from reality three ways: the product changes, traffic changes, and the set leaks into prompts and fine-tunes. Refresh it on a schedule from recent traffic and error analysis; the FAQ adds that if "everything keeps passing", an eval should be run less often or retired.
  • Criteria drift. Shankar et al. found that "users need criteria to grade outputs, but grading outputs helps users define criteria" ({{Who Validates the Validators?|https://arxiv.org/abs/2404.12272}}, Apr 2024): the expected behaviour changes as people read outputs, so rubrics are versioned with the items.
  • Versioning. Any edit to the set is a reviewed change, and the champion is re-scored on every new version: a v2 score is a reading on a different instrument and never shares a chart line with v1.
  • A held-out split that is never published or sent to a vendor that might train on your traffic.
  • Gold labels are fallible. Before a gate failure is believed, audit the failing items: the eval system has three fallible parts (model, judge, gold). Keep "ambiguous, exclude from gating" as a valid label state and gate on the verified subset (auditing method and error rates: {{Human evaluation and annotation|n:3ef5c17b0d0d819485bcc54a45d49420}}; the root page's {{attribution stepper|n:3c65c17b0d0d8181b351e1b8fc6a1546#rd-fail}} shows the split on six physics benchmarks).
