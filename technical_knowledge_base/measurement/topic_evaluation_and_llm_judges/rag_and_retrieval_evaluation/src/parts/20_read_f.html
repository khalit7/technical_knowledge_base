Building a RAG eval set: real questions, two labels each

A few hundred well-made items beat ten thousand synthetic ones.

  1. Mine real questions from logs, support tickets and subject-matter experts. Synthetic questions come out longer and more literal: one September 2026 comparison on a production corpus found real queries averaged 6.8 words against 15.7 for generated ones, and that tuning on the synthetic set picked a retriever with up to 8 times the latency of the fastest (Kucia and Gawlik, arXiv 2609.14579, preprint).
  2. Label each question twice: the relevant passage ids with grades (for the retrieval half) and a reference answer, or a list of nuggets (for the generation half). Expert time is the bottleneck; spend it here. Labelling only the top results of one system biases the labels toward that system; pool the top 10 of several systems, as TREC does.
  3. Bootstrap coverage with generation, then filter by hand. RAGAS's generator builds a knowledge graph over your chunks (entities, keyphrases, similarity links) and by default draws a third each of single-hop specific, multi-hop abstract and multi-hop specific questions (docs). Unfiltered, generated questions quote the chunk's own phrasing and are easy for lexical retrieval by construction.
  4. Include the hard cases on purpose: unanswerable questions (score abstention, not recall), multi-hop questions, ambiguous ones, near-duplicate documents, and questions whose answer changed over time.
  5. Version it. Re-chunking the index invalidates passage-id labels; re-label or map them. Never tune on the held-out slice.

Label quality and agreement are on {{Human evaluation and annotation|n:3ef5c17b0d0d819485bcc54a45d49420}}; turning the set into a release gate on {{Production eval engineering|n:3c65c17b0d0d81b39ad9e96193d21adc}}; watching retrieval quality on live traffic, and golden-set size in CI, on {{RAG in production|n:3f85c17b0d0d81aa9ba9c0ceac9e28c1}}.

Comparing two RAG systems fairly

Predict: on SciFact, BM25's nDCG@10 is 0.676 and the dense model's 0.645. On how many of the 300 claims does BM25 do better? Pick "BM25 against dense".

A 0.03 gap in the means is 68 wins against 70 losses: not a result on 300 queries

One bar per query, sorted: nDCG@10 of the second system minus the first. measured; the 95% interval is a paired bootstrap over queries (10,000 resamples, seed 0, src/paired.py), derived. SciFact, BM25 against dense: interval −0.067 to +0.005, so "BM25 beats dense on SciFact" is not established; against the hybrid +0.043 (+0.020 to +0.065), 74 wins and 20 losses. Even the two BM25 implementations differ beyond noise on SciFact (−0.024, −0.046 to −0.002).

The rules that keep a comparison fair:

  • Paired, with an interval. Report the per-query difference and its interval, not two means; which test and how many questions you need is on {{Eval statistics|n:3ef5c17b0d0d8187a7b4e5b4ec4a546d}}.
  • Labels pooled from both systems. Unjudged passages count as irrelevant, so a new system that finds good passages nobody labelled is under-scored; judge the pooled top results of both before comparing.
  • The same prompt budget. The same k and the same token budget: a system given more passages wins recall by construction and may lose precision and faithfulness.
  • The same pinned judge, prompt and version for every generation metric, ideally from a third model family (judges rate their own family up).
  • Both halves, plus cost and latency. A change can move the bug between halves with accuracy unchanged, as the hybrid did for SciFact claim 54 in the animation.

Long context against RAG is the same comparison

When a corpus fits in a million-token window, "do we need retrieval at all?" is answered on your own questions: both arms on the same golden set, with the same correctness check, at your corpus size, with cost and latency beside accuracy. Retrieval metrics apply only to the RAG arm; the long-context arm is scored end to end plus faithfulness against the whole window. Position inside the window matters (Lost in the Middle; {{Long-context and multimodal benchmarks|n:3ef5c17b0d0d810bb4dfc98919c9be8a}} owns it and the effective-length benchmarks), and the measured trade-off, including Self-Route's routing between the two, is on {{Agentic retrieval, long context and memory|n:3c65c17b0d0d8105a68cfb504ed4b0e8}}.

Two more findings for the long-context arm
  • More retrieved passages is not monotone (Jin et al.), and LaRA found no single winner between RAG and long context; both are owned by {{Agentic retrieval|n:3c65c17b0d0d8105a68cfb504ed4b0e8}}, section 8. So evaluate recall@k and end-to-end accuracy together across k, not recall alone.
  • Neither wins everywhere: Self-Route (EMNLP 2024 Industry) found long context ahead on average when budget allowed, and routing each query to RAG or long context by the model's own judgement kept quality at 65% lower cost on Gemini-1.5-Pro (the paper's prose; its Table 1, used by the owner page, gives 38.4% of long context's tokens).

Agentic RAG

When the model calls retrieval as a tool in a loop, the per-call metrics still apply to each search, and the trajectory needs its own checks: did it search when it should (and not when it should not), how good were its reformulated queries, how many calls until it had enough, and are the final citations verified against what it actually read. {{Agent and trajectory evaluation|n:3ef5c17b0d0d81fdbabaf3582bff37f2}} owns grading trajectories; public agentic benchmarks are on {{Agentic benchmarks|n:3c65c17b0d0d811fb926d7b91ef8234e}}.
