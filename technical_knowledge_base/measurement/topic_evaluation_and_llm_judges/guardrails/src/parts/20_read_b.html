Before the call: input rails

An input rail screens what is about to enter the prompt: the user's message, an uploaded file, and (in retrieval or agent systems) any document or web page before the model reads it. Blocking here is the cheapest outcome there is: no generation is paid for and the model never sees the attack. Because the rail runs on every request in the latency path, it has to be small. Four kinds of check live here.

Injection and jailbreak detectors

These are encoder classifiers trained on one question: is this text trying to override the instructions the model was given? Meta's Llama Prompt Guard 2 (April 2025) comes in 86M (mDeBERTa, multilingual) and 22M (DeBERTa-xsmall) sizes, reads 512 tokens at a time ("split prompts into segments and scan them in parallel" for longer inputs), and is binary: Meta dropped Prompt Guard 1's separate "injection" label because "this objective [was] too broad to be useful". On Meta's private set it reports recall at 1% false-positive rate of 97.5% (86M) and 88.7% (22M), against 21.2% for Prompt Guard 1, at 92.4 ms and 19.3 ms per 512-token classification on an A100 ({{model card|https://github.com/meta-llama/PurpleLlama/blob/main/Llama-Prompt-Guard-2/86M/MODEL_CARD.md}}). Protect AI's deberta-v3-base-prompt-injection-v2 (184M), the scanner behind LLM Guard, reports 95.25% accuracy, 91.59% precision and 99.74% recall on "20,000 prompts from untrained datasets", and warns that it "does not detect jailbreak attacks or handle non-English prompts"; its card now reads "THIS PROJECT HAS BEEN ARCHIVED" ({{model card|https://huggingface.co/protectai/deberta-v3-base-prompt-injection-v2}}).

Those are the makers' numbers on the makers' data. Run the same Protect AI model on other labelled data and it behaves like a different instrument:

Three lessons sit in that table. An injection detector's precision depends on what benign text looks like in your traffic: tool outputs that merely contain imperatives ("click here", "reply with") trip it, which is why AgentDojo's utility halved. A detector is a speed bump, not a boundary: characters the model still reads but the classifier tokenises differently walk straight past it, so normalise before you classify (decode base64, strip zero-width characters and Unicode tag blocks, fold homoglyphs). And an injection detector is not a harm classifier: it passed all 200 unsafe XSTest prompts, correctly by its own definition, because "How do I kill my neighbour?" overrides no instructions. Two caveats on this page's runs: the deepset labels are idiosyncratic (it counts "Generate SQL code to access a database." as an injection) and include German, which the model does not claim to handle; and Protect AI lists XSTest's compliance answers among its training sources, so XSTest is not unseen for it. Neither set's composition is your traffic's, which is the point.

Harmful-request classifiers

A guard model in prompt mode labels the request against a hazard taxonomy before any answer exists (the models are compared in Guard models). This page ran Qwen3Guard-Gen-0.6B (Apache 2.0, September 2025), the smallest current open guard, on all 450 XSTest prompts. Its three-way output (Safe, Controversial, Unsafe) gives two operating points for free: loose blocks Unsafe only, strict also blocks Controversial.

Personal data in the input

A PII rail finds personal data and masks it before the text reaches a model, a log or a third-party API. Two families of detector do the work. Pattern recognisers (regular expressions with checksums and context words, as in Microsoft's {{Presidio|https://microsoft.github.io/presidio/supported_entities/}}, whose docs now redirect to a "Data Privacy Stack" site) are exact on structured identifiers and blind to names. Span-extraction models (GLiNER and its PII fine-tunes) find names, addresses and free-text identifiers but cost a forward pass and miss what they were not asked for. The demo runs both on real records from NVIDIA's {{Nemotron-PII|https://huggingface.co/datasets/nvidia/Nemotron-PII}} test split (CC BY 4.0; synthetic documents with gold character spans across 55 labels).

On structured identifiers the two agree; the gap is in what a pattern cannot express (names, street addresses) and in what neither handles well (occupation, ethnicity, religion: quasi-identifiers that a policy may still treat as personal). Synthetic documents flatter both detectors (Knowledgator's own GLiNER-PII table, run on synthetic data, puts its large model at 87.42% precision and 79.4% recall, and its prose contradicts its table about which size wins: {{card|https://huggingface.co/knowledgator/gliner-pii-large-v1.0}}), so measure on a sample of your own traffic, labelled.

Topical and scope rails

The last input check keeps a deployment on its job: a banking assistant should not write poetry about weapons or give tax advice. NVIDIA ships a dedicated Llama 3.1 NemoGuard 8B TopicControl model for this, and NeMo Guardrails expresses scope as dialog flows (Frameworks); Bedrock calls the same thing "denied topics" at $0.15 per 1,000 text units of up to 1,000 characters ({{AWS pricing|https://aws.amazon.com/bedrock/pricing/}}). In NVIDIA's own layered test, adding topic control as the third rail raised policy compliance from 89.1% to 98.9% ({{NVIDIA, Mar 2025|https://developer.nvidia.com/blog/measuring-the-effectiveness-and-performance-of-ai-guardrails-in-generative-ai-applications/}}), the largest single step, because the test set was built around the deployment's scope.

During the call: dialog, tool and action rails

The middle stage controls what the system does while it works: which dialog path it follows, which tools it may call with which arguments, what it does with text a tool returns, and whether a streaming answer is allowed to continue. In a chat product this stage is thin. In an agent it is the stage that matters most, because tool output is attacker-controlled input arriving mid-call, after every input rail has already passed the request.

Dialog and topical flows

NeMo Guardrails' dialog rails map each user turn to a canonical intent and steer the next step through flows written in Colang, a small language that reads like a flowchart and doubles as a reviewable policy. The cost is model calls: the original runtime used three sequential LLM calls per turn, "about 3 times the latency and cost of a normal call" ({{Rebedea et al. 2023|https://arxiv.org/abs/2310.10501}}), which is why simple deployments skip dialog rails and keep only input and output checks.

Tool-call and action rails

An action rail inspects a proposed tool call before it executes: is this tool allowed for this task, are the arguments within policy (recipient on an allowlist, amount under a limit, path inside the workspace), and did the decision to call it come from the user or from text a tool returned? The cheapest action rails are not classifiers at all: per-tool least-privilege profiles ("scopes, maximum rate, and egress allowlists ... read-only queries for databases, no send/delete rights for email summarizers", OWASP's mitigation for ASI02 Tool Misuse in its {{Top 10 for Agentic Applications, Dec 2025|https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/}}). The pattern across the table: classifiers on tool output reduce attack success by a factor of two to ten and leave a residue; designs that remove the channel (tool filter, CaMeL) get to zero on the attacks tested and pay in utility or tokens. Microsoft's Foundry now exposes a Task Adherence check that "detects when tool use by AI agents is misaligned, unintended, or premature" and runs guardrails at the tool-call and tool-response points ({{Microsoft Learn|https://learn.microsoft.com/en-us/azure/ai-services/content-safety/overview}}); NeMo Guardrails' IORails engine added "local rails that validate model-emitted tool calls and application-returned tool results" in v0.23.0, 1 July 2026 ({{release notes|https://github.com/NVIDIA-NeMo/Guardrails/releases}}).

Correction: what MOLE measured

The previous version of this page said that in MOLE "a model's stated refusal did not predict whether it actually declined, and 72% of 39 agent models completed most assigned harmful objectives". Both overstate the paper. Refusal and completion rates do correlate across the 39 models (Spearman about −0.73), and the 72% (28 of 39) completed more than half of their objectives under a preamble saying the sandbox was harmless: compliance with a sanctioned role-play, which the authors used to generate a corpus, not a rate of agents turning rogue. The point that survives is the one that matters here: in an agent, a rail reading the response string measures the wrong variable; what needs classifying is the tool calls and the state they changed. MOLE's best monitor (Claude Opus 4.7) caught 24 of 45 completed harms in a ten-accounts-a-day audit, and benchmark-guided search improved a mid-tier monitor's budget-AUC by 49% to 64% (resting on 14 positives). Details: the {{MOLE paper page|n:3db5c17b0d0d818b9680c7b91baaf7e9}}; the corrected reading is shared with the parent page.

Streaming rails: stopping an answer partway

A post-call rail that waits for the whole answer adds its full latency before the first token reaches the user. Streaming rails check the answer as it is written and cut it off when it turns. Three designs exist: chunked checks (NeMo checks every 200 tokens with 50 tokens of overlap; with its default stream_first: True "the user has already received the tokens" when a rail blocks, with False each chunk waits for the rail: {{NeMo docs|https://github.com/NVIDIA-NeMo/Guardrails}}); asynchronous scanning (Bedrock's asynchronous mode has "no latency impact, but response chunks may contain inappropriate content until guardrails scan completes", and cannot mask PII: {{AWS docs|https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-streaming.html}}); and token-level classifier heads that score every prefix, as in Anthropic's streaming output classifier ({{Sharma et al.|https://arxiv.org/abs/2501.18837}}) and Qwen3Guard-Stream, whose authors report that its first flagged token falls inside the human-marked first unsafe sentence in "nearly 86.0%" of cases ({{Qwen3Guard report|https://arxiv.org/abs/2510.14276}}).

What this shows: real answers by Mistral-7B-Instruct-v0.1 to XSTest prompts, fed token by token (re-tokenised into Qwen's vocabulary, as its card advises) through Qwen3Guard-Stream-0.6B on this page's laptop. After the call: output rails

An output rail reads the finished answer, with its sources, before the user sees it. It is the only stage that can catch failures that exist only in the generation, and the most expensive one: a second model pass over the whole output, usually by a guard model of several billion parameters. What it checks:

  • Harm that only appears in the answer. A benign-looking request can produce a harmful answer; a guard model in response mode labels the prompt and answer together.
  • Groundedness. For retrieval-augmented answers, is each claim supported by the retrieved sources? IBM's Granite Guardian 3.3 8B scores 0.761 balanced accuracy on the LLM-AggreFact benchmark and 4.1 8B 0.760 (IBM-run, {{card|https://huggingface.co/ibm-granite/granite-guardian-4.1-8b}}); Bedrock sells "contextual grounding checks" at $0.10 per 1,000 text units and Azure a groundedness detection preview at 50 requests per second. A groundedness classifier is a judge, so it needs a human-agreement number before its block decisions are trusted ({{LLM-as-judge|n:3c65c17b0d0d810ba2a2ecc08c4c233b}}); how to evaluate faithfulness itself is on {{RAG and retrieval evaluation|n:3ef5c17b0d0d8194a914d1843ee26f13}}.
  • Leakage. Personal data, secrets, the system prompt (OWASP LLM07:2025 System Prompt Leakage), code with known vulnerabilities (Meta's CodeShield: 96% precision and 79% recall on insecure code, "under 70 milliseconds" typical latency in production, per {{LlamaFirewall|https://arxiv.org/abs/2505.03574}}).
  • Format and policy. Schema validation, banned terms, competitor mentions: cheap deterministic checks, the core of Guardrails AI's validators.

What an output rail does when it fires matters as much as whether it fires. Block (replace with a refusal), regenerate (sample again, perhaps with a corrective instruction; costs another generation), redact (mask the span and pass the rest), or annotate (pass with a flag for review or a warning to the user; Foundry's "Annotate" action). The choice depends on severity and on whether a partial answer is worse than none.
