Compiled 2026-10-04. Every number is followed by its source URL and the fetch date. "unconfirmed" means I could not confirm it from a primary source in this session. Note: the web search budget was exhausted in this session, so all sources are direct fetches of known primary URLs (GitHub API, PyPI JSON, arXiv, vendor docs); items I could not reach by direct URL are marked unconfirmed.

## 1. NVIDIA NeMo Guardrails

- What: open-source toolkit for "programmable guardrails" between application code and the LLM; Python, async-first; also an OpenAI-compatible guardrails server. Source: https://raw.githubusercontent.com/NVIDIA-NeMo/Guardrails/develop/README.md (fetched 2026-10-04).
- Maintainer: NVIDIA. Repo moved from `NVIDIA/NeMo-Guardrails` to `NVIDIA-NeMo/Guardrails` (GitHub API redirect, fetched 2026-10-04). README now titles it "NVIDIA NeMo Guardrails Library".
- Licence: Apache-2.0 (README badge; GitHub API reports NOASSERTION because of extra files). PyPI package `nemoguardrails`.
- Latest release: **v0.24.1, 2026-09-16** (patch); v0.24.0 2026-08-26; v0.23.0 2026-07-01; v0.22.0 2026-05-22; v0.21.0 2026-03-12; v0.20.0 2026-01-22. Source: https://api.github.com/repos/NVIDIA-NeMo/Guardrails/releases?per_page=8 and https://pypi.org/pypi/nemoguardrails/json (fetched 2026-10-04). Stars about 7.2k.
- Five rail types (README, verbatim): "1. Input rails: applied to the input from the user; an input rail can reject the input, stopping any additional processing, or alter the input (e.g., to mask potentially sensitive data, to rephrase). 2. Dialog rails: influence how the LLM is prompted; dialog rails operate on canonical form messages ... 3. Retrieval rails: applied to the retrieved chunks in the case of a RAG ... scenario; a retrieval rail can reject a chunk ... or alter the relevant chunks ... 4. Execution rails: applied to input/output of the custom actions (a.k.a. tools), that need to be called by the LLM. 5. Output rails: applied to the output generated by the LLM; an output rail can reject the output ... or alter it (e.g., removing sensitive data)." Source: README above (2026-10-04).
- Colang: "Two versions of Colang, 1.0 and 2.0, are supported and Colang 1.0 is the default." (README, 2026-10-04). Colang 2.0 introduced in v0.9.0, 2024-05-10: "Colang 2.0 brings a more solid foundation for building complex guardrail configurations (with better parallelism support), advanced RAG orchestration ..., agents ..., and multi-modal LLM-driven interaction ... Colang 2.0 is a complete overhaul of the Colang language". Source: https://api.github.com/repos/NVIDIA-NeMo/Guardrails/releases/tags/v0.9.0 (2026-10-04). v0.8.0 (2024-02-28) added jailbreak heuristics input rail.
- Engines in 2026: `LLMRails` (the original Colang runtime) and **`IORails`**, new in v0.21.0 (2026-03-12): "a new optimized Input/Output rail engine that supports parallel execution of NemoGuard rails (content-safety, topic-safety, and jailbreak detection)". v0.22.0 (2026-05-22) "IORails milestone 2" added streaming output rails, OpenTelemetry, reasoning models and "_speculative generation_ in non-streaming mode, which runs input rails in parallel with the main application LLM response generation. This hides the latency of input rails while still guaranteeing response safety." v0.23.0 (2026-07-01): IORails tool calling streaming and non-streaming "including local rails that validate model-emitted tool calls and application-returned tool results"; lightweight Hugging Face classifier rails for input, output and retrieval. v0.24.0 (2026-08-26): "IORails can now execute 59 of the library's 67 action-backed input and output surfaces"; `RailOutcome` allow/block/transform contract; "(streaming) Fail closed when rail actions fail". v0.24.1 adds "IORails admission shedding" overload response and parsing "Nemotron 3.5" content-safety responses. Source: GitHub releases API (2026-10-04). No published IORails latency numbers: the release notes page "contain[s] no statements about IORails performance" (https://docs.nvidia.com/nemo/guardrails/latest/about/release-notes.html, 2026-10-04).
- Other integrations named in release notes: Cisco AI Defense (v0.18.0, 2025-11-06), CrowdStrike AIDR, PolicyAI, Trend Micro Vision One AI Guard, Fiddler (v0.21.0), F5 Guardrails (v0.24.0), GLiNER PII and Nemotron-Content-Safety-Reasoning-4B with "/think" mode (v0.20.0, 2026-01-22), BotThinking events to rail reasoning traces (v0.18.0).
- Parallel rails: config `rails.input.parallel` / `rails.output.parallel`, both default `false` ("Execute input rails in parallel"). Source: https://docs.nvidia.com/nemo/guardrails/latest/configure-guardrails/configuration-reference.html (2026-10-04).
- Streaming output rails (verbatim from docs): `chunk_size` default 200 "Number of tokens per chunk that output rails process"; `context_size` default 50 "Tokens carried over between chunks for continuity"; `stream_first` default True. "True (default): The client receives each chunk of tokens before output rails process that chunk. This provides faster time-to-first-token, but if a rail blocks the content, the user has already received the tokens. The stream terminates with a JSON error on violation." "False: Output rails process each chunk before the client receives tokens. The user never sees blocked content, but time-to-first-token increases by the rail execution time per chunk." chunk_size: "Larger values: Fewer rail executions, but higher latency to first output; Smaller values: More rail executions, but faster time-to-first-token". Source: https://raw.githubusercontent.com/NVIDIA-NeMo/Guardrails/develop/docs/configure-rails/yaml-schema/streaming/output-rail-streaming.mdx (2026-10-04).
- Paper: Rebedea, Dinu, Sreedhar, Parisien, Cohen (NVIDIA), "NeMo Guardrails: A Toolkit for Controllable and Safe LLM Applications with Programmable Rails", arXiv 2310.10501, 2023-10-16 (EMNLP 2023 demo track: venue unconfirmed in this fetch). Dialog rails use three sequential LLM calls (user canonical form, next step, bot message). Cost quote: "The three-step CoT prompting approach used by the Guardrails runtime incurs extra costs and extra latency ... the latency and costs required are about 3 times the latency and cost of a normal call". Moderation rails on a 200-sample balanced set: gpt-3.5-turbo with both rails blocks about 99% harmful, 2% helpful; text-davinci-003 97% / 5%. Fact-checking rail (MSMARCO) about 80% accuracy; hallucination rail (20 unanswerable questions) 95% with gpt-3.5-turbo, 70% with text-davinci-003. Source: https://arxiv.org/html/2310.10501 (2026-10-04; figures summarised by fetch tool, re-check exact table before quoting).
- NVIDIA measured latency (developer blog, Aditi Bodhankar, 2025-03-03, "Measuring the Effectiveness and Performance of AI Guardrails in Generative AI Applications"): main LLM Llama 3.1 70B Instruct; in-house dataset "of 215 interactions, with approximately 10% being multi-turn". Table 2: no guardrails 0.91 s average latency, 112.9 tokens/s/interaction, 75.01% policy compliance; + content safety 1.29 s, 101.2 tok/s, 83.0%; + jailbreak detection 1.36 s, 99.0 tok/s, 89.1%; all three (content safety, topic control, jailbreak) 1.44 s, 98.70 tok/s, 98.9%. Verbatim: "adding the first guardrail layer increases average latency by about half a second while raising policy violation detection from 75% to 83%." GPU not stated. Source: https://developer.nvidia.com/blog/measuring-the-effectiveness-and-performance-of-ai-guardrails-in-generative-ai-applications/ (2026-10-04). So full stack: +0.53 s (+58%) latency, about -12.6% throughput, for +23.9 points compliance (my arithmetic).
- NemoGuard NIMs (announced 2025-01-16, https://blogs.nvidia.com/blog/nemo-guardrails-nim-microservices/, fetched 2026-10-04): Content Safety NIM (Llama 3.1 NemoGuard 8B ContentSafety, trained on the Aegis Content Safety Dataset, "over 35,000 human-annotated data samples flagged for AI safety and jailbreak attempts"), Topic Control NIM (Llama 3.1 NemoGuard 8B TopicControl), Jailbreak Detection NIM (NemoGuard JailbreakDetect). The blog calls them small language models for "lower latency"; it gives no latency figure itself (the "half a second" number is from the 2025-03-03 developer blog above). 2026 additions: Nemotron-Content-Safety-Reasoning-4B (supported from v0.20.0, 2026-01-22); "Nemotron 3.5" content-safety parsing (v0.24.1). Model sizes of JailbreakDetect: unconfirmed.
- Benchmark harness: repo `benchmark/` uses AIPerf and Locust with mock LLMs; README: "Adding guardrails to an LLM-based application improves safety and security, while adding some latency. These benchmarks allow users to quantify the tradeoff". No published results in repo. Source: https://raw.githubusercontent.com/NVIDIA-NeMo/Guardrails/develop/benchmark/README.md (2026-10-04).

## 2. Guardrails AI (guardrails-ai/guardrails)

- What: Python framework that runs "Input/Output Guards in your application that detect, quantify and mitigate the presence of specific types of risks"; Guards are composed of validators; also structured-output generation; optional Guardrails Server (Flask/Gunicorn, OpenAI-compatible). Source: https://raw.githubusercontent.com/guardrails-ai/guardrails/main/README.md (2026-10-04).
- Maintainer: Guardrails AI Inc. (Shreya Rajpal et al.). **Acquired by Harvey**: blog "Guardrails AI Joins Harvey", 2026-09-08: Guardrails AI is "joining their product and engineering organization"; the framework "is downloaded more than 250,000 times a month". Future of the OSS library after acquisition: not stated (unconfirmed). Source: https://guardrailsai.com/blog/guardrails-ai-joins-harvey (2026-10-04).
- Licence: Apache-2.0 (GitHub API and PyPI, 2026-10-04). About 7.5k stars.
- Latest release: **v0.11.0, 2026-08-14** (includes "[GR-1710] Deprecate hub CLI + private registry"); v0.10.2 2026-06-04; v0.10.0 2026-04-03. Source: https://api.github.com/repos/guardrails-ai/guardrails/releases?per_page=3 and https://pypi.org/pypi/guardrails-ai/json (2026-10-04).
- Architecture: input guards and output guards around the LLM call; validators can run on streamed output chunks (streaming validation; chunking strategy per validator); on-fail actions (exception, reask, fix, filter, refrain, noop). No dialog/retrieval/tool stage as a first-class concept (my reading of README; the stage list is not stated in one sentence in the README).
- Validators hub: README: "Guardrails Hub is a collection of pre-built measures of specific types of risks (called 'validators')." **Hub sunset**: README news item "[July 6, 2026] Guardrails validators are moving to standard PyPI packages you install directly with `pip`, and Guardrails is discontinuing its hosted remote inferencing ... Planned cutoff: August 25, 2026." Migration issue: "guardrails hub install and the private validator registry (pypi.guardrailsai.com)" and "The hosted remote-inference servers (hub.api.guardrailsai.com)" stop on 2026-08-25; "50 of the 64 validators are available on PyPI today"; new install form `pip install guardrails-ai-detect-pii`; remote inference replaced by `use_local=True` or a self-hosted `validation_endpoint=`. Source: https://github.com/guardrails-ai/guardrails/issues/1560 (2026-10-04).
- Guard models called: depends on validator; e.g. Detect Jailbreak, Guardrails PII (GLiNER-based), Toxic Language, Restrict to Topic, Competitor Check, Provenance LLM; validators can call any LLM via litellm.
- **Guardrails Index** (benchmark): README: "[Feb 12, 2025] We just launched Guardrails Index -- the first of its kind benchmark comparing the performance and latency of 24 guardrails across 6 most common categories". Page now at https://guardrailsai.com/index (old index.guardrailsai.com 308-redirects). Stated: "24 Guardrails tested", "6 Number of Datasets", "32 Days spent on GPU". Best score per category (y-axis labelled "F1 Score"): Jailbreaking: Detect Jailbreak 0.81 (runner-up 0.81); PII: Guardrails PII 0.65 (runner-up 0.62); Content moderation: Toxic Language 0.72 (runner-up 0.60); Topic restriction: Restrict to Topic (Hybrid) 0.93 (runner-up 0.91); Competitor check: Competitor Check 0.67 (0.64); Hallucination: Provenance LLM 0.77 (0.75). Only the PII tab's latency values render in static HTML: GLiNER for PII latency CPU 0.5031 s, GPU 0.0460 s; Guardrails PII CPU 0.5002 s, GPU 0.0678 s, F1 0.6520; Presidio CPU 0.0161 s, GPU 0.0150 s, F1 0.3698 (note: the static text repeats F1 0.6520 for GLiNER too, possibly a render artefact; treat GLiNER F1 as unconfirmed). Chart latency axis spans 0 to 0.072 s, i.e. these validators are tens of milliseconds on GPU. Latency for other categories is in the PDF (not fetched; unconfirmed). Source: https://guardrailsai.com/index (fetched 2026-10-04; the page metadata gives 2026-09-09 as a modified date, the benchmark itself is from 2025-02-12).

## 3. Meta LlamaFirewall (PurpleLlama)

- What: "a framework designed to detect and mitigate AI centric security risks, supporting multiple layers of inputs and outputs, such as typical LLM chat and more advanced multi-step agentic operations. It consists of a set of scanners for different security risks." A policy engine whose scanners attach per role (user, assistant, tool) at any stage of an agent's trace. Source: https://raw.githubusercontent.com/meta-llama/PurpleLlama/main/LlamaFirewall/README.md (2026-10-04).
- Maintainer: Meta (PurpleLlama repo). Licence: LlamaFirewall subfolder MIT (https://raw.githubusercontent.com/meta-llama/PurpleLlama/main/LlamaFirewall/LICENSE); PurpleLlama root is Llama 3.2 Community License; Prompt Guard 2 weights under the Llama 4 Community License (unconfirmed in this fetch).
- Latest release: PyPI `llamafirewall` **1.0.3, 2025-05-29** (1.0.0 on 2025-04-29); no newer PyPI release as of 2026-10-04 although the folder still receives maintenance commits (latest 2026-08-18). Sources: https://pypi.org/pypi/llamafirewall/json; https://api.github.com/repos/meta-llama/PurpleLlama/commits?path=LlamaFirewall (2026-10-04).
- Paper: Chennabasappa, Nikolaidis, Song, Molnar, Ding, et al., "LlamaFirewall: An open source guardrail system for building secure AI agents", arXiv 2505.03574, 2025-05-06. Source: https://arxiv.org/html/2505.03574 (2026-10-04).
- Components (README): "PromptGuardScanner, AlignmentCheckScanner, CodeShieldScanner, and customizable regex filters". PromptGuard 2: "A fast, lightweight BERT-style classifier that detects direct prompt injection attempts. It operates on user inputs and untrusted content such as web data". AlignmentCheck: chain-of-thought auditor that reads the agent's reasoning/actions trace for goal hijacking (uses an LLM via the Together API by default: "If you plan to use the alignment check scanner, you will need to set up the Together API key"). CodeShield: "A static analysis engine that examines LLM-generated code for security issues in real time. Supports both Semgrep and regex-based rules across 8 programming languages." Also an "OpenAI Guardrail Integration" example.
- Stages: input (user prompt), tool output / untrusted content (PromptGuard), agent reasoning and actions (AlignmentCheck, runs on assistant role), output code (CodeShield), arbitrary text (regex). Streaming: not described.
- **AgentDojo results** (paper, verbatim summary from fetch): "The baseline configuration showed an attack success rate of 17.6% with 47.7% utility. Using PromptGuard V2 86M alone reduced ASR to 7.5% while maintaining 47.0% utility. AlignmentCheck with Llama 4 Maverick achieved 2.89% ASR at 43.1% utility." "PromptGuard + AlignmentCheck delivered the best defensive performance, reducing ASR to 1.75%" with 42.7% utility. Table values: no guardrail ASR 17.63%, utility 47.73%; PG2 86M ASR 7.53%, utility 47.01%; AlignmentCheck (Llama 4 Maverick) 2.89% / 43.09%; combined 1.75% / 42.68%. The paper also claims AlignmentCheck gives an "83% reduction in attack success rate" on AgentDojo (17.63 to 2.89 is 83.6%; my arithmetic). So combined: ASR -90% relative, utility -5.05 points. Source: https://arxiv.org/html/2505.03574 (2026-10-04).
- AlignmentCheck accuracy: with "Llama 4 Maverick and Llama 3.3 70B as AlignmentCheck scanners", "over 80% recall with a false positive rate below 4%" (internal benchmark). Cost caveat verbatim: "Effective alignment checks require large, capable models. Smaller models lack the general reasoning ability needed for accurate semantic evaluation, limiting effectiveness in resource-constrained environments." No ms figure for AlignmentCheck (unconfirmed / not published).
- **Prompt Guard 2 latency** (model card table, verbatim columns "Latency per classification (A100 GPU, 512 tokens)"): Llama Prompt Guard 1 (86M, mdeberta-v3): AUC English .987, recall at 1% FPR 21.2%, AUC multilingual .983, 92.4 ms. **Prompt Guard 2 86M** (mdeberta-v3): .998, 97.5%, .995, **92.4 ms**. **Prompt Guard 2 22M** (deberta-v3-xsmall): .995, 88.7%, .942, **19.3 ms**. Card: the 22M "reduces latency and compute costs by 75%, with minimal performance trade-offs"; "Both Llama Prompt Guard 2 models support a 512-token context window. For longer inputs, split prompts into segments and scan them in parallel". AgentDojo "APR @ 3% utility reduction": PG1 67.6%, PG2 86M 81.2%, PG2 22M 78.4%, ProtectAI 22.2%, Deepset 13.5%, LLM Warden 12.9%. Source: https://raw.githubusercontent.com/meta-llama/PurpleLlama/main/Llama-Prompt-Guard-2/86M/MODEL_CARD.md (2026-10-04). Contradiction: the arXiv HTML fetch rendered PG2 86M English AUC as ".98"; the model card says ".998" (trust the card).
- **CodeShield**: "Achieved a precision of 96% and a recall of 79% in identifying insecure code"; two tiers, roughly 60 ms first layer and roughly 300 ms second layer; in production "typical end-to-end latency of under 70 milliseconds". Source: https://arxiv.org/html/2505.03574 (2026-10-04; tier figures summarised by fetch tool, verify wording before quoting).
- CyberSecEval: benchmark suite lives in https://github.com/meta-llama/PurpleLlama/tree/main/CybersecurityBenchmarks (CyberSecEval 1 to 4; CyberSecEval 4 released with LlamaFirewall in April 2025 per Meta's LlamaCon announcement: unconfirmed in this session). Llama Guard 4 (12B, multimodal, pruned from Llama 4 Scout) card: https://raw.githubusercontent.com/meta-llama/PurpleLlama/main/Llama-Guard4/12B/MODEL_CARD.md (no latency figure in card).

## 4. LLM Guard (Protect AI, now Palo Alto Networks)

- What: open-source "security toolkit for LLM interactions": a library of prompt (input) scanners and output scanners run in sequence around the LLM call; also an API server. Source: https://raw.githubusercontent.com/protectai/llm-guard/main/README.md (2026-10-04).
- Maintainer: Protect AI; Palo Alto Networks "today announced it has completed its acquisition of Protect AI" on 2025-07-22, folding it into Prisma AIRS; the press release does not mention LLM Guard. Source: https://www.paloaltonetworks.com/company/press/2025/palo-alto-networks-completes-acquisition-of-protect-ai (2026-10-04).
- Licence: MIT. About 3.2k stars.
- Latest release: **0.3.16, 2025-05-19** (PyPI and changelog; changelog has an empty "[Unreleased] - 0.3.17"; last push 2026-07-08). No GitHub "releases" objects, only tags. Effectively in maintenance mode since the acquisition (my reading). Sources: https://pypi.org/pypi/llm-guard/json, https://raw.githubusercontent.com/protectai/llm-guard/main/docs/changelog.md (2026-10-04).
- Stages: input and output only (no dialog, retrieval or tool stage as such; scanners can be applied to retrieved text by the caller). Streaming: not built in (unconfirmed).
- Scanners (README, 2026-10-04). Prompt: Anonymize, BanCode, BanCompetitors, BanSubstrings, BanTopics, Code, Gibberish, InvisibleText, Language, PromptInjection, Regex, Secrets, Sentiment, TokenLimit, Toxicity (15). Output: BanCode, BanCompetitors, BanSubstrings, BanTopics, Bias, Code, Deanonymize, JSON, Language, LanguageSame, MaliciousURLs, NoRefusal, ReadingTime, FactualConsistency, Gibberish, Regex, Relevance, Sensitive, Sentiment, Toxicity, URLReachability (21).
- Guard models: mostly small Hugging Face classifiers (PromptInjection uses Protect AI's deberta-v3-base-prompt-injection-v2; Anonymize uses Presidio plus NER models). Model names: see doc pages; partially unconfirmed.

Source: https://raw.githubusercontent.com/protectai/llm-guard/main/docs/input_scanners/prompt_injection.md (2026-10-04). ## 5. Other frameworks and managed services (2026)

### 5a. AWS Amazon Bedrock Guardrails (managed)

- What: configurable safeguards applied to user inputs and model responses "(excluding reasoning content blocks)", either inline with Bedrock inference (guardrail ID and version) or standalone via the `ApplyGuardrail` API for any model. Safeguards (verbatim names): Content filters (Hate, Insults, Sexual, Violence, Misconduct and Prompt Attack; text and image), Denied topics, Word filters, Sensitive information filters (probabilistic PII plus custom regex; block or mask), Contextual grounding checks ("detect hallucinations in model responses if they are not grounded ... in the source or are irrelevant to the user's query"), Automated Reasoning checks ("validate the accuracy of foundation model responses against a set of logical rules"). Input tagging lets you evaluate only part of a prompt (e.g. skip retrieved docs). Cross-account enforcements exist. Source: https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html (2026-10-04).
- Tiers: Standard vs Classic. Standard "Provides more robust performance compared to Classic tier", uses cross-Region inference, supports prompt leakage detection, code-element coverage, denied-topic definitions up to 1,000 characters (Classic 200), extensive languages (Classic: English, French, Spanish). Source: https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-tiers.html (2026-10-04).
- Streaming (verbatim): synchronous (default) mode "will buffer and apply the configured policies to one or more response chunks before the response is sent back to the user. The synchronous processing mode introduces some latency"; asynchronous mode "sends the response chunks to the user as soon as they become available, while asynchronously applying the configured policies in the background. The advantage is that response chunks are provided immediately with no latency impact, but response chunks may contain inappropriate content until guardrails scan completes. As soon as inappropriate content is identified, subsequent chunks will be blocked". "Amazon Bedrock Guardrails doesn't support the masking of sensitive information with asynchronous mode." Enabled with `"streamProcessingMode": "ASYNCHRONOUS"`. Source: https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-streaming.html (2026-10-04).
- **Pricing** (verbatim, https://aws.amazon.com/bedrock/pricing/, fetched 2026-10-04): content filters (text, Standard and Classic) "$0.15 per 1,000 text units"; content filters (image) "$0.00075 per image processed"; denied topics "$0.15 per 1,000 text units"; sensitive information filters "$0.10 per 1,000 text units"; sensitive information filters (regular expression) "Free"; word filters "Free"; contextual grounding checks "$0.10 per 1,000 text units"; Automated Reasoning checks "$0.17 per 1,000 text units per Automated Reasoning policy". Separate **InvokeGuardrailChecks API** table: content filters (text only) "$0.07 per 1,000 text units"; prompt attack (text only) "$0.08 per 1,000 text units" ("With the InvokeGuardrailChecks API, you can use the prompt attack filter separately outside of content filters"); sensitive information filters "$0.10 per 1,000 text units". "A text unit can contain up to 1000 characters." InvokeGuardrailChecks launch date: unconfirmed. Worked example (my arithmetic): a 4,000-character prompt plus 2,000-character answer = 6 text units; content filter + denied topics + PII = $0.40 per 1,000 units, so $0.0024 per turn.
- Published effectiveness claims (marketing, verbatim): "blocks up to 88% of harmful content"; Automated Reasoning checks "validate correct model responses with up to 99% accuracy". Source: https://aws.amazon.com/bedrock/guardrails/ (2026-10-04). No published latency figure found (unconfirmed). Automated Reasoning checks GA date: August 2025 (unconfirmed in this session; the 2025 AWS news blog URL I tried returned 404).

### 5b. Microsoft: Azure AI Content Safety and Foundry guardrails (managed)

- What: Azure AI Content Safety APIs (now billed as "Content Safety in Foundry Control Plane"). Features table (verbatim purposes): **Prompt Shields** "Scans text for the risk of a User input attack on a Large Language Model"; **Groundedness detection (preview)** "Detects whether the text responses of large language models (LLMs) are grounded in the source materials provided by the users"; **Protected material text detection** "Scans AI-generated text for known text content (for example, song lyrics, articles, recipes, selected web content)"; **Task adherence API** "Detects when tool use by AI agents is misaligned, unintended, or premature in the context of a user interaction"; Analyze text / Analyze image (sexual, violence, hate, self-harm, multi-severity); Custom categories standard and rapid (preview). Protected material, groundedness and custom categories (standard) are English only. Source: https://learn.microsoft.com/en-us/azure/ai-services/content-safety/overview (page updated 2026-10-01, fetched 2026-10-04).
- Rate limits S0 (verbatim table): moderation APIs, Prompt Shields, protected material "1000 RP10S"; groundedness detection (preview) "50 RPS"; custom categories (standard) "5 RPS"; multimodal "10 RPS". F0: 5 RPS each. Same source.
- Prompt Shields: two shields. User prompt attacks (previously "Jailbreak risk detection"; subtypes: attempt to change system rules, embedding a conversation mockup, role-play, encoding attacks) scanned at the "user input" intervention point; document attacks ("hidden instructions in third-party content") scanned at "user input" and "tool response". Standalone API "analyzes a `userPrompt` and up to five `documents`" returning `attackDetected`. **Spotlighting (preview)**: "The service transforms the document content by using base64 encoding, and the model treats it as less trustworthy"; "Spotlighting has no direct cost. However, base64 encoding increases the number of document tokens". Source: https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/jailbreak-detection (ms.date 2026-08-28, fetched 2026-10-04).
- Task adherence: concept page dated 2025-08-13; detects "tool actions that are misaligned with user goals or input intent, or improper tool input/output relative to user intent"; output `{"taskRiskDetected": true, "details": "..."}`; English-tested; data may be processed in US/EU regions. Source: https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/task-adherence (2026-10-04).

## 6. Frontier-lab deployment-side classifiers and monitors

### 6a. Anthropic Constitutional Classifiers (2025)

- Paper: Mrinank Sharma et al., "Constitutional Classifiers: Defending against Universal Jailbreaks across Thousands of Hours of Red Teaming", arXiv 2501.18837, 2025-01-31. Source: https://arxiv.org/html/2501.18837 (2026-10-04).
- Design: input classifier framed as "a next-token-prediction problem" (fine-tuned LMs with a constitution-derived template); **streaming output classifier** with "a linear value head that predicts the harmfulness of a full sequence" from each token prefix; at deployment uses the "cumulative-maximum value-head probability": if "the classifier's predicted score for a given token exceeds a given threshold, we block the output" (so generation can be halted mid-stream). Classifiers trained on synthetic data generated from a natural-language constitution of permitted/restricted content (CBRN focus). Production-like system: Claude 3.5 Haiku classifiers guarding Claude 3.5 Sonnet (New); the bug-bounty prototype used Claude 3.5 Sonnet classifiers (per fetch summary).
- Red teaming (paper): 405 invited participants (from about 800 applicants), 183 estimated active; "mean estimate is 4,720 hours, with 90% confidence intervals of [3,242, 7,417]"; up to $15,000 per universal jailbreak; $95K paid in total (per fetch summary; verify). Blog: "183 active participants spent an estimated >3,000 hours over a two-month experimental period". Public demo: "339 jailbreakers ... across more than 300,000 chat interactions, representing approximately 3,700 collective hours".
- Numbers (blog, verbatim): automated jailbreak success "86%" unguarded vs "4.4%" with classifiers; "a slightly increased refusal rate (by 0.38%), but this was not statistically significant"; "The compute cost was moderately higher (by 23.7%) than that of the unguarded model." Paper: "0.38% absolute increase in production-traffic refusals", "23.7% inference overhead". Source: https://www.anthropic.com/research/constitutional-classifiers (2026-10-04; blog dated 2025-02-03, unconfirmed).
- Contradiction note: red-teaming hours: blog ">3,000 hours" (the conservative lower bound) vs paper mean estimate 4,720 hours (90% CI 3,242 to 7,417). Not contradictory, just different statistics; cite which one.

### 6b. Constitutional Classifiers++ (2026)

- Paper: Hoagy Cunningham, Jerry Wei, Zihan Wang, et al., "Constitutional Classifiers++: Efficient Production-Grade Defenses against Universal Jailbreaks", arXiv 2601.04603, 2026-01-08. Source: https://arxiv.org/html/2601.04603 (2026-10-04). Found via arXiv API (https://export.arxiv.org/api/query?search_query=ti:constitutional+AND+ti:classifiers).
- Abstract (verbatim extracts): "exchange classifiers that evaluate model responses in their full conversational context, which addresses vulnerabilities in last-generation systems that examine outputs in isolation"; "a two-stage classifier cascade where lightweight classifiers screen all traffic and escalate only suspicious exchanges to more expensive classifiers"; "efficient linear probe classifiers and ensemble them with external classifiers"; "a production-grade system achieving a 40x computational cost reduction compared to our baseline exchange classifier, while maintaining a 0.05% refusal rate on production traffic"; "over 1,700 hours" of red teaming; "no attack on this system successfully elicited responses to all eight target queries comparable in detail to an undefended model".
- Body (verbatim): "roughly an 8x reduction compared to the two-stage system described in Section 4, and approximately a 40x reduction compared to the single exchange classifier in Section 3." "The flag rate, the proportion of queries refused, was 0.05%, substantially lower than the 0.38% reported by Sharma et al. (2025)." Probes stream: "During inference, we use an exponentially weighted moving average (EMA) instead of a sliding window mean for computational convenience ... the probe monitors all exchanges during generation." Probes read the guarded model's own activations (so stage one is nearly free). Guarded model in the deployment study: Claude Sonnet 4.5 (per fetch summary).
- Anthropic blog "Next-generation Constitutional Classifiers", 2026-01-09 (verbatim): "roughly 1% compute overhead if applied to Claude Opus 4.0 traffic"; "refusal rate of 0.05% on harmless queries, an 87% drop from the original classifiers system"; "over 1,700 cumulative hours of red-teaming across 198,000 attempts". Source: https://www.anthropic.com/research/next-generation-constitutional-classifiers (2026-10-04). (0.38% to 0.05% is an 87% drop: consistent.) Overhead trajectory for the page: 23.7% (2025) to about 1% (2026).
- Contradiction note: one fetch summary of the paper reported "3.5% relative overhead"; I could not find that sentence verbatim on re-query, and the paper states the comparison only as ratios (40x, 8x). Treat "3.5%" as unconfirmed; use the blog's "roughly 1%".
- Related 2026 arXiv items (titles only, not read): "Trojan-Speak: Bypassing Constitutional Classifiers with No Jailbreak Tax via Adversarial Finetuning" (2603.29038, 2026-03-30); "HaloGuard 1.0: An Open Weights Constitutional Classifier for Multilingual AI Safety" (2607.02079, 2026-07-02).

### 7b. Design patterns for hiding guard latency (with sources)

1. **Run the input guard in parallel with generation ("optimistic" / speculative)**. OpenAI cookbook: "send your guardrails asynchronously along with your main LLM call" with two `asyncio.create_task` calls (https://developers.openai.com/cookbook/examples/how_to_use_guardrails). OpenAI Agents SDK default `run_in_parallel=True`: "best latency ... However, if the guardrail's tripwire is triggered, the agent may have already consumed tokens and executed tools before being cancelled"; blocking mode avoids "side effects from tool calls" (https://api.github.com/repos/openai/openai-agents-python/contents/docs/guardrails.md). NeMo IORails speculative generation (v0.22.0, 2026-05-22): "runs input rails in parallel with the main application LLM response generation. This hides the latency of input rails while still guaranteeing response safety" (non-streaming mode only). Cost: wasted tokens when the guard fires; unsafe for agents with side-effecting tools.
2. **Run several guards in parallel with each other**: NeMo `rails.input.parallel` / `rails.output.parallel` (default false); IORails "parallel execution of NemoGuard rails (content-safety, topic-safety, and jailbreak detection)" (v0.21.0). Latency becomes max(guards) instead of sum(guards).
3. **Streaming output rails, chunked**: NeMo `chunk_size` 200 tokens, `context_size` 50, `stream_first` True (user sees the chunk before the rail checks it; violation ends the stream with a JSON error) or False (each chunk waits for the rail; "time-to-first-token increases by the rail execution time per chunk"). OGX: validate in "batches of approximately 200 characters". Bedrock: synchronous (buffer then scan) vs asynchronous ("no latency impact, but response chunks may contain inappropriate content until guardrails scan completes"; no PII masking in async). OpenAI Guardrails library `stream=True`: "Output guardrails run in parallel with streaming; Risk: Violative content may briefly appear". OpenAI Moderation parameter: scores "arrive after the full generated output is available".
4. **Token-level streaming classifier that halts generation**: Constitutional Classifiers' value head with cumulative-maximum score per token (arXiv 2501.18837); CC++ linear probes on the guarded model's own activations with an EMA, monitoring "all exchanges during generation" (arXiv 2601.04603).
5. **Cascade (cheap high-recall first stage, expensive second stage)**: CC++ two-stage cascade ("lightweight classifiers screen all traffic and escalate only suspicious exchanges"; 40x cheaper than a single exchange classifier; about 1% compute overhead on Opus 4.0 traffic). GPT-5 "fast, topical classifier" then "reasoning model" monitor (topical classifier recall 0.960). gpt-oss-safeguard guide: "small, high-recall classifiers" before the reasoning model. Model Armor/Bedrock are single-stage managed calls.
6. **Pick the smallest guard that holds accuracy**: PG2 22M is 4.8x faster than 86M (19.3 vs 92.4 ms) for recall 88.7% vs 97.5% at 1% FPR; ONNX on GPU cut LLM Guard PromptInjection from 81 ms to 7.65 ms.

## Contradictions and caveats found

- Prompt Guard 2 86M English AUC: arXiv HTML render gave ".98", model card ".998". Use the model card.
- Constitutional Classifiers red-team hours: blog ">3,000 hours" vs paper mean estimate 4,720 hours (CI 3,242 to 7,417): different statistics, both valid.
- CC++ overhead: a first fetch summary claimed "3.5% relative overhead"; not found verbatim; Anthropic blog says "roughly 1% compute overhead if applied to Claude Opus 4.0 traffic". Use 1%.
- NVIDIA "half a second": the sentence is "adding the first guardrail layer increases average latency by about half a second", but Table 2 shows 0.91 to 1.29 s (+0.38 s) for the first layer; the full three-rail stack is +0.53 s. The prose rounds up.
