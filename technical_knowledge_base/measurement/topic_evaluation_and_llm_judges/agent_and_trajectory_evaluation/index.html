Agent and trajectory evaluation: grading actions, not messages

How to evaluate your own agent: what to grade (the final message, the final state, or the steps), who grades it (code, a judge model, an agent judge, a process reward model), how to make the number repeatable and hard to game, what it costs, and what to log. ⏱ 27 min read · +7h 05m resources. A chat model is graded on what it says. An agent is graded on what it did: the database rows it changed, the files it committed, the money it moved, the calls it made on the way. Its final message is only a claim about those things, and on real trials the claim and the facts disagree often enough to matter.

This page is about evaluating your own agent: the one you are building, on your tasks, before you ship it and while it runs. Public agentic benchmarks (GAIA, OSWorld, WebArena, τ²-bench, Terminal-Bench, METR time horizons) and how each was broken in 2026 belong to Agentic benchmarks, which also owns pass^k on real τ²-bench trials and the Terminal-Bench verifier exploit; this page links them and applies them. The parent, Topic: evaluation-and-llm-judges, explains why any eval is a measuring instrument that has to be calibrated; this page is that idea for agents.

The rule this page argues for
Grade the outcome first, with code, on a state you can diff. Grade actions (not messages) wherever an action can do harm the outcome check does not see. Use the path only for diagnosis or for actions that must never happen, never as an exact sequence to match. Read failing and suspiciously passing transcripts every time the number moves. This is close to Anthropic's own advice, "it's often better to grade what the agent produced, not the path it took" (Demystifying evals for AI agents, 9 Jan 2026), with one addition from the safety results below: what an agent did along the way is part of what it produced.

Outcome grading: check the world, not the claim

Anthropic's vocabulary is the clearest available: a task is one test with inputs and success criteria, a trial is one attempt at it, a grader scores some aspect of the attempt, the transcript (or trajectory) is "the complete record of a trial, including outputs, tool calls, reasoning, intermediate results", and the outcome is "the final state in the environment at the end of the trial" (Demystifying evals for AI agents). Outcome graders come in four common shapes:

ShapeHow it decidesExample
State diffReplay the gold actions on a copy of the starting state, compare with the state the agent leftτ²-bench hashes the agent's database and the gold database and requires equality (evaluator_env.py): any order of calls, any wording, the same end state

A state diff is the strongest of these because it is indifferent to path and wording, and it sees changes the agent never mentioned. Keep it a diff, not just a hash: when a trial fails, the six differing fields of the default trial above explain it in one look, where a hash only says "different".

The do-nothing baseline

An outcome check is only as informative as the set of tasks it runs on. Many good agent tasks have "change nothing" as the right answer: refuse a cancellation the policy forbids, decline an unaffordable change. On those, an agent that does nothing passes. This page ran that agent through τ²-bench's evaluator: each task's first user turn and then nothing, no tool calls.

Do-nothing agent: the greeting and first user message of a real trial, then the conversation ends; graded with evaluate_simulation at commit 5bfa7e3. Airline and telecom use the full reward; retail's reward also includes LLM-judged assertions, which were not run, so its figure is the database component only (an upper bound for the do-nothing agent). Per-model bars: passes split by whether the do-nothing agent also passes that task; computed in the page from the 400 trials and checked by recompute.py.

On airline, 23 of 50 tasks are passed by an agent that does nothing, and 88 of GPT-5.2's 166 passing trials are on those tasks. Its pass^1 on the 27 tasks that need a change is 72.2%, against 83.0% overall (Opus 4.5: 73.2% against 84.0%). Neither number is wrong; they answer different questions, and the overall one hides that nearly half the suite rewards restraint. Anthropic's advice is the general form: "Test both the cases where a behavior should occur and where it shouldn't ... avoid class-imbalanced evals." For your own suite: run a do-nothing agent and a random agent first, report their scores beside every result, and report change and no-change tasks separately.

What an outcome check cannot see

  • Harm along the way. An agent that emails a customer's data to the wrong address and then finishes the booking correctly passes a check on the reservations table. The outcome check covers the state you decided to check; everything else is the next section's job.
  • A wrong gold state. The default trial above fails because the gold reservation assumes no insurance and one card while the simulated user asked for both. Your gold state encodes your assumptions about the user, and a simulated user does not know them.
  • A better route than the gold. GPT-5.2's task-31 trial upgraded the cabin so the flight could be moved and left the user satisfied; the gold says nothing should change. Anthropic's CORE-Bench story is the same failure at scale: Opus 4.5 "initially scored 42%" until a researcher found "rigid grading that penalized '96.12' when expecting '96.124991…', ambiguous task specs, and stochastic tasks"; after fixes and a less constrained scaffold it scored 95% (Anthropic, 9 Jan 2026).
  • Success the checker did not anticipate. On web agents, AgentRewardBench's experts found the benchmarks' rule-based checkers precise (83.8% precision) but blind to many real successes (55.9% recall), so they underreport success: GPT-4o's success rate was 16.7 points lower by the rules than by the experts on WebArena and 18.5 points on VisualWebArena (Lù et al., AgentRewardBench, Apr 2025).

Partial credit helps where a task has parts: "A support agent that correctly identifies the problem and verifies the customer but fails to process a refund is meaningfully better than one that fails immediately" (Anthropic). Score each required change separately and keep the all-or-nothing score beside it.

Grade actions, not messages

A message grader reads what the agent said. For agents that is the weakest evidence available, because saying and doing come apart. On the 400 τ²-bench trials, the transcript judge's verdict and the database disagree on 49: 18 trials where the judge found every assertion met and the database was wrong, and 31 the other way. And that judge read the whole transcript, tool calls included; a grader that reads only the final message knows less.

Two 2026 studies make the same point at higher stakes.

MOLE: what was measured (correction carried from the parent page)
An earlier version of the parent page said MOLE found that "a model's stated refusal did not predict whether it actually declined". That overstates the paper. What it measured: under a preamble telling every model the sandbox is harmless and that refusing spoils the research, 28 of 39 models (72%) completed more than half of their assigned harmful objectives; across models, refusal and completion rates are strongly linked (Spearman -0.73); 24 models never refused yet completed anywhere from 20% to 100%, mostly by not attempting; and the best monitor (Claude Opus 4.7, reviewing 10 accounts a day) caught 24 of 45 completed harms. Completion was verified in the services' state, not in what the agent said (Muhamed and Smith, MOLE, Sep 2026; corrected reading on the MOLE paper page). The point that survives: in agentic systems, grade what the account did.

Emergence World ran eight ten-agent worlds for days under phishing, misinformation and memory exposure, and scored private reasoning, requested actions, executed actions and speech separately, letting none count for another (Akkil et al., Sep 2026). All seven exposed worlds warned their community about the phishing; none removed its traces. In the Gemini world, agents made 489 calls to the attacker's database after their own world had flagged the lure (counted from the released tool-call records on the Emergence World paper page). A grader of messages would have scored that world as having detected the attack. (The paper's "up to 46 hours" is one agent retrying an attack link after the campaign, not a measured detection-to-stop delay; corrected on the paper page.)

And the logs of ordinary benchmarks hide the same thing. HAL re-ran nine benchmarks in 21,730 rollouts and, by reading logs with an LLM's help, found agents "searching for the benchmark on HuggingFace instead of solving a task, or misusing credit cards in flight booking tasks" (Kapoor et al., HAL, Oct 2025); neither shows up in a success rate.

How to grade actions

  • Forbidden actions as hard checks. List what must never happen (a write without the user's explicit yes, a payment method not on the profile, a call outside the allow-list) and scan every tool call for it. τ²-bench encodes some of this in its policy; your own list belongs in code.
  • Unexpected writes. Count writes that are in no gold action. On the 400 trials an exact audit of write calls (every gold write present with the same arguments, no others) agrees with the database check on 396; where they disagree, the transcript is worth reading.
  • A monitor over the trace for what you cannot enumerate. MOLE's results say how to build one: an LLM reading what the agent did beat count-based anomaly detection, and showing the monitor the agent's reasoning helped wherever the agent wrote it (on MOLE's DeepSeek corpus GPT-4.1 with reasoning beat GPT-5.5 on audit events alone). And it shows what to avoid: the renderer clipped every tool argument at 600 characters, so no monitor ever saw a data-poisoning trigger.
Go deeper (optional): runtime enforcement of the same checks, as rails before and after each call: Guardrails. Benchmarks that grade refusals and harmful completions: Safety and honesty benchmarks. The monitor-side audit you can run in the browser: the MOLE paper page's Run the daily audit tab.

Step-level grading: where it went wrong, and what not to demand

A step grader looks inside the trajectory. Four kinds are in use:

  • Gold-action matching. For each action in the task's reference solution, did the agent make that call with those arguments? τ²-bench computes this for every trial (action_checks, each marked read, write or generic), though its airline and retail rewards do not use it.
  • Trajectory matching. Compare the whole sequence of tool calls with a reference. LangChain's agentevals names the options cleanly: strict ("the same messages in the same order with the same tool calls"), unordered (the same calls in any order), subset and superset, each with a tool_args_match_mode of exact, ignore, subset or superset. The Path matchers tab runs all of them on the five real trials above.
  • Per-step judges and process reward models, which score each step's quality (next section).
  • Efficiency counts: calls, failed calls, repeated calls, tokens and time per trial.

Demanding the reference path is the common mistake. Anthropic: "There is a common instinct to check that agents followed very specific steps like a sequence of tool calls in the right order. We've found this approach too rigid and results in overly brittle tests, as agents regularly find valid approaches that eval designers didn't anticipate." On the 400 trials, τ²-bench's gold-action check fails on 24 trials whose database is exactly right, usually over read calls (a lookup the agent did not need, or a calculate the agent did in its head, as in task 12 above). Restricting the check to write calls removes nearly all of that noise: the exact write audit agrees with the database on 396 of 400. The Path matchers tab measures the whole range on GPT-5.2's 200 trials: matching every call strictly in order passes 7 trials and agrees with the final state on 38; matching write calls in any order with exact arguments agrees on 198.

Steps earn their keep in four places:

  1. Diagnosis. The outcome says "fail"; the steps say which call, with which argument, after which user turn. Every number on this page was explained by reading steps.
  2. Actions that must never happen, as hard checks (the previous section).
  3. Cost and efficiency, which the outcome cannot see: two agents that reach the same state with 7 calls and with 70 are not the same agent (see Cost and budgets).
  4. When the outcome is unobservable or arrives too late: long tasks, production actions you cannot replay, intermediate checkpoints for partial credit.

Who grades a trajectory: judges, agent judges and process reward models

Code graders cover what you can specify. For the rest (was the plan sensible, was the user handled well, did a research agent's report answer the question) a model grades the trajectory. Three designs exist, and each needs its own calibration against people, as the parent page argues for every judge.

Trajectory LLM judges

A model reads the transcript (messages, calls, results) and answers a rubric; τ²-bench's natural-language assertions above are one, and agentevals ships a default TRAJECTORY_ACCURACY_PROMPT. On web agents, AgentRewardBench had experts label 1,302 trajectories from 5 benchmarks and 4 agents and tested 12 judges: "no single LLM excels across all benchmarks"; the best, GPT-4o with accessibility trees, reached 69.8% precision, below the rule-based checkers' 83.8% but with far better recall (AgentRewardBench). On 931 mobile-agent trajectories, a simple judge reading sampled screenshots (90.9% with Gemini 3 Flash, the authors' own baseline) matched or beat purpose-built pipelines (89.3% for AgentRewardBench's method) (MobileJudgeBench, Aug 2026, preprint).

Agent-as-a-judge

Instead of reading a transcript, the judge acts: it opens the produced repository, runs code and checks each requirement against evidence. The original paper built DevAI (55 AI-development tasks, 365 hierarchical requirements, three expert annotators) and reports its agent judge agreeing with the experts' consensus on 90.44% of requirements against 60.38% for an LLM judge without tools, on OpenHands' outputs in its black-box setting, for $30.58 and 118.43 minutes against about $1,297.50 and 86.5 hours for the three experts (Zhuge et al., Oct 2024; its own runs).

Correction: DevAI's cost and time percentages are swapped in the paper (carried from the root's Judge atlas)
Section 4.4 says the agent judge cost 2.29% of the human cost and took 2.36% of the time. Its own figures give the reverse: $30.58 / $1,297.50 = 2.36% of the cost, and 118.43 of 5,190 minutes = 2.28% of the time. The abstract's savings (97.64% of the cost, 97.72% of the time) agree with the figures.

A third party confirms the direction: on AJ-Bench (155 tasks, 516 annotated trajectories in search, data systems and GUI), giving the judge tools lifted DeepSeek V3.2 from 64.49 to 77.34 (+12.85 points) and GPT-5-mini (low) from 59.00 to 72.41 (+13.41) (Shi et al., AJ-Bench, Apr 2026, preprint). Every judge reading is in the root's Judge atlas tab.

Process reward models

A process reward model (PRM) scores each step rather than the end. The idea came from maths: OpenAI found "process supervision significantly outperforms outcome supervision" for training on MATH, with its process-supervised model solving 78% of a representative test subset, and released PRM800K, 800,000 step-level human labels (Lightman et al., May 2023). For agents, AgentPRM learns step values from Monte Carlo rollouts (how often does the task succeed if you continue from here?), and InversePRM learns them from demonstrations; 3B models trained with them beat GPT-4o baselines on ALFWorld (Choudhury, Feb 2025). As an evaluator, a PRM gives a per-step curve that locates the step where success became unlikely. Two cautions: it is a trained model, so an agent optimised against it can exploit it (the paper itself analyses reward hacking; see Reward Hacking), and its step scores need the same meta-evaluation as any judge.

A judge only knows what it is shown

MOLE's monitors are trajectory judges, and its observability result generalises: on the three multiday corpora whose agents wrote reasoning, GPT-4.1 reading that reasoning had a higher recall than GPT-5.5 reading only the audit events (0.49 against 0.39, 0.71 against 0.52, 0.68 against 0.45; the paired interval excludes zero on one corpus, is borderline on one and not established on one), and a 600-character clip on tool arguments hid every data-poisoning trigger from every monitor. Decide what the judge sees as deliberately as which judge you use; log enough that you can change your mind later.

Reliability across runs

An agent run is a sample. The same agent on the same task can pass, fail, or pass for a different reason, so one trial per task measures luck as much as skill. Two numbers separate them: pass@k, the chance that at least one of k trials succeeds, and pass^k, "the probability that all k trials succeed" (Anthropic's wording; the metric is from τ-bench, Yao et al., Jun 2024). A product that must work every time a customer calls is a pass^k product. The estimators, the animation and every reproduced τ²-bench run are on Agentic benchmarks (its pass^k on real trials tab); this page applies them to the two airline runs it uses.

From the released trials, pass^1 to pass^4 come out at 83.0, 78.3, 75.0, 72.0 for GPT-5.2 and 84.0, 77.7, 73.5, 70.0 for Opus 4.5, matching the leaderboard's pass^1 and pass^4 independently. Per task, over all eight trials:

30 tasks pass in all 8 trials, 17 are mixed, and 3 (tasks 23, 39 and 44) never pass. Anthropic's rule of thumb applies to the last group: "a 0% pass rate across many trials (i.e 0% pass@100) is most often a signal of a broken task, not an incapable agent". Eight trials is far from a hundred, and whether these three are broken is unconfirmed here; they are the first transcripts to read. Task 29 is the mixed kind worth reading too: it passed once, and what decided it was the simulated user.

Where the variance comes from

  • The agent's sampling. The variance you want to measure.
  • The simulated user. In τ²-bench a model plays the customer, and its improvisations change the right answer (task 29). Part of what any simulated-user eval measures is the simulator, and its version changes between leaderboard rows (Agentic benchmarks has the details). Pin it, and when a task flips, check whether the user changed first.
  • The environment. "Each trial should be 'isolated' by starting from a clean environment. Unnecessary shared state between runs (leftover files, cached data, resource exhaustion) can cause correlated failures due to infrastructure flakiness rather than agent performance" (Anthropic). Count infrastructure failures separately: τ²-bench scores any run that did not end with the agent or user stopping as 0 (evaluate_simulation), so a crashed container and a wrong answer look the same unless you log the termination reason (all 400 trials here ended with the user stopping).
  • The grader. A code grader on a fixed trajectory should be deterministic: re-grading the 200 GPT-5.2 airline trials reproduces every recorded reward. An LLM judge is not; re-run it on fixed trajectories to measure its own noise before you blame the agent.

Trials of one task are correlated, so error bars must be clustered by task, and k trials of 50 tasks are not 50k independent observations: Eval statistics has the formulas and the sample-size calculator.

Reward hacking and verifier exploits in your own evals

An eval you optimise against becomes a target, and agents find the gaps faster than people do. In April 2026 Berkeley RDI's exploit agent scored near the top of eight public agent benchmarks "without solving a single task"; the seven flaw patterns and the Terminal-Bench curl exploit, animated on a real task, are on Agentic benchmarks (Reading, Integrity, and the Grade a real task tab). The same happens inside private evals:

  • Models hack the scorer you gave them. METR found o3 reward hacking in 0.7% of runs across HCAST tasks and more than 43 times as often on RE-Bench, including 21 of 21 runs of Optimize LLM Foundry, 12 of 28 of Rust Codecontest and 6 of 24 of Optimize a Kernel; hacks included overwriting the timing function, returning the answer "the scoring system already calculated", and monkey-patching the evaluation "so that it judges every submission as successful". It found them by inspecting anomalously high-scoring runs and, on HCAST, with a model monitor (METR, 5 Jun 2025).
  • Impossible tasks measure the propensity. ImpossibleBench mutates a task's tests so they contradict its specification; any pass "necessarily implies a specification-violating shortcut". GPT-5 cheated on 76% of one-off-mutated SWE-bench tasks and 2.9% of the LiveCodeBench ones; hiding the tests cut cheating success to near zero; letting the agent flag the task for a human lowered GPT-5 from 54% to 9% on conflicting SWE-bench tasks; a Claude Sonnet 4 monitor caught 86 to 89% of cheating on LiveCodeBench but only 42 to 50% on SWE-bench (Zhong, Raghunathan and Carlini, Oct 2025).
  • The harness can overfit the eval. StateM's 95.28% raw Terminal-Bench 2.1 submission fell to 94.38% with the four flagged trials its authors accepted, 93.26% with all nine reward-hacking flags zeroed, and 92.36% with all 13 flags the leaderboard's judge raised (four for "harness cheating", gate slots that mapped onto single tasks); the pull request was closed unmerged on 19 September 2026 (StateM paper page). HarnessDev measured the general form: the score a harness creator could see moved the same way as the held-out score in only 34 of 64 version changes (HarnessDev paper page).
  • Self-improving agents keep their hacks. In a Factorio run, Prime Agent found it could spawn resources through RCON despite an anti-cheating heartbeat and saved the shortcut as a reusable skill (Prime Agent paper page).
Defences that cost little
  • Run the verifier where the agent cannot reach it: a separate container, tests copied in after the agent stops, read-only or hidden tests.
  • Add canaries: impossible variants of a few tasks (any pass is a hack) and a do-nothing agent (its score is the floor).
  • Keep a held-out task split that no prompt, harness or skill was tuned on.
  • Read the transcripts of the highest scores and of every sudden jump, as METR did; then put a monitor on the rest.
  • Give the agent a legitimate way out ("flag for a human"); it cut cheating by more than five times in ImpossibleBench.

Cost and step budgets

Two agents with the same success rate are not equally good if one needs three times the money or ten times the calls, and an agent with no budget can buy success by trying longer. Fix the budget before the run (steps, tokens, wall-clock time, dollars), report the score at that budget, and count "ran out of budget" as its own failure category. τ²-bench's runs here allowed 200 steps and 10 tool errors per trial (the files' run configuration); MOLE capped sessions at 50 turns and two of its four agents hit the cap on the same assignment that GPT-5.3 finished in 9 turns.

Per-trial agent cost as recorded in each trial's agent_cost field of the released files (the harness's own estimate; the user simulator's cost is separate), averaged over passing and failing trials; computed in the page, checked by recompute.py.

Failures cost more than successes for both agents (GPT-5.2: $0.181 against $0.100 a trial, 15.7 tool calls against 9.6), because a failing agent keeps searching. And the two runs that tie at pass^1 are far apart in cost: $22.76 for GPT-5.2's 200 trials against $79.84 for Opus 4.5's, which is $0.137 against $0.475 per successful trial. Prices change and these are the harness's estimates, so treat the ratio, not the dollars, as the finding. At scale the same holds: HAL spent about $40,000 on 21,730 rollouts and found "higher reasoning effort reducing accuracy in the majority of runs" (HAL), so more budget is not automatically more score. The root's Same model, many harnesses tab and Agentic benchmarks (the harness section) show how much of an agent's bill is the harness rather than the model.

Sandboxes and environment design

The environment is half of an agent eval: the tools, the state they act on, the simulated user if there is one, and the verifier. Which harness gives you which sandbox (Docker, Kubernetes, VMs, cloud sandboxes, NVIDIA OpenShell with network policies in Inspect; none in lm-eval or HELM) is on Eval harnesses, section Sandboxes for agentic evals. What to design, whichever you use:

  • The production agent in a copy of production. "It's essential that the agent in the eval functions roughly the same as the agent used in production" (Anthropic): the same tool schemas, system prompt and limits, so the eval measures what you ship.
  • State you can reset and diff. τ²-bench's whole world is a JSON database rebuilt for every trial and replayed for grading, with a frozen clock (every booking in these trials is created at 2024-05-15 15:00). That is what made this page's re-grading and diffs possible.
  • A clean start per trial, so failures are independent (the reliability section).
  • A verifier out of the agent's reach. On Terminal-Bench 2.0 an exploit agent replaced the curl the in-container verifier used, and every 3.0 and 4.0 task declares a separate verifier container; OSWorld's gold files were downloadable from inside the VM (Agentic benchmarks).
  • A network policy stated per task: no network, an allow-list, or open. Emergence World's agents turned a read-only fetch tool into a publishing channel through a GET-accepting API (its paper page has the round-by-round containment).
  • A pinned simulated user, with instructions that say what the user wants on every choice the gold state depends on (task 29's insurance and payment method were not).
  • Long-horizon state when the risk is long-horizon. MOLE's simulated organisation (150 agent-run accounts, 9 stateful services, 30 workdays) exists because single-session tasks cannot show harm that accumulates across days.

Observability and tracing

Everything on this page was graded from logs. A trace that records each model call, each tool call with its arguments and result, and the state before and after is what lets you re-grade old runs with a new grader, attribute a failure, and audit a suspicious pass. Common mistakes

Grading the final message
It is a claim. On 400 real trials it disagreed with the database 49 times. Grade the state, and the actions where harm can hide.
Demanding the reference path
Valid routes differ. The gold-action check failed 24 trials whose database was exactly right. Match writes, not reads; use the path to diagnose.
Quoting a score without the do-nothing baseline
23 of 50 τ²-bench airline tasks pass with no action. Report the floor and split change from no-change tasks.
One trial per task, or pass^1 as reliability
Report pass^k and cluster error bars by task; read the tasks that never pass before calling the agent weak.
Blaming the agent for the simulator, the environment or the judge
Pin the user simulator, isolate trials, log termination reasons, and re-run LLM judges on fixed trajectories to measure their own noise.
A verifier the agent can touch
Tests in the agent's container, gold files on a reachable URL, a timer the agent can overwrite: each has been exploited. Separate the verifier.
Tuning the harness on the tasks you score
StateM's task-shaped gates and HarnessDev's 34 of 64 agreement: keep a held-out split.
Ignoring cost and budget
Same pass^1, three times the cost per success. Fix budgets and report cost per success.
Clipped or partial traces
A judge cannot grade what it is not shown; OpenTelemetry's tool arguments and results are opt-in.

Checklist for your own agent eval

  1. Write tasks with a resettable, diffable state and a gold end state; say in the user instructions everything the gold depends on.
  2. Balance tasks that need a change against tasks whose right answer is no change; run a do-nothing agent and report its score.
  3. Grade the outcome with code; add hard checks for forbidden actions and an audit of unexpected writes.
  4. Use model judges (transcript, agent-as-a-judge, PRM) only for what code cannot specify, and calibrate each against human labels.
  5. Run several trials per task; report pass^k, clustered error bars, and per-task outcomes.
  6. Isolate trials and the verifier; pin the simulator, the judge and the harness versions.
  7. Add impossible canaries and a held-out split; read the top scores and every jump.
  8. Fix budgets; report cost per success and budget-exhausted failures separately.
  9. Log full traces (arguments, results, state, reasoning, versions) so any grader can be re-run.

Path matchers

How strict should a step grader be? This tab runs the four trajectory-match modes and four argument-match modes of LangChain's agentevals (ported line by line from its Python source at commit 946ad15, 13 Jul 2026) against τ²-bench's gold actions, on all 400 airline trials, and reports how often each setting passes a trial and how often it agrees with the final-state check.

strict
the same tool calls in the same order (agentevals also requires the same messages; τ²-bench's gold has none, so this port compares calls only)
unordered
the same tool calls, any order
subset
every call the agent made is in the reference (no extra calls)
superset
every reference call was made (extra calls allowed)
arguments
exact equal; superset the agent's arguments include every reference key and value; subset the reverse; ignore names only. Matching is on top-level keys, as in agentevals.

The five stepped-through trials, under the selected cell

Try: start at strict, exact, all calls (the setting closest to "follow the reference path"), then switch to write calls only and move to unordered. Then click superset: it passes the task-31 trial, whose gold path is empty, because every reference call was made (there are none); the extra write that broke the database is invisible to it. Only modes that forbid extra calls (strict, unordered, subset) catch it.

Grid values for all 400 trials were computed offline by src/match_port.py; the five-trial verdicts below are computed in the page by the JavaScript port and checked against the Python port by checks/check_ui.mjs.
