Outcome grading: check the world, not the claim

Anthropic's vocabulary is the clearest available: a task is one test with inputs and success criteria, a trial is one attempt at it, a grader scores some aspect of the attempt, the transcript (or trajectory) is "the complete record of a trial, including outputs, tool calls, reasoning, intermediate results", and the outcome is "the final state in the environment at the end of the trial" ({{Demystifying evals for AI agents|https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents}}). Outcome graders come in four common shapes:

ShapeHow it decidesExample
State diffReplay the gold actions on a copy of the starting state, compare with the state the agent leftτ²-bench hashes the agent's database and the gold database and requires equality ({{evaluator_env.py|https://github.com/sierra-research/tau2-bench/blob/main/src/tau2/evaluator/evaluator_env.py}}): any order of calls, any wording, the same end state
TestsRun tests the agent's change must make pass, and tests it must not breakSWE-bench's FAIL_TO_PASS and PASS_TO_PASS test lists ({{SWE-bench harness|https://github.com/SWE-bench/SWE-bench}}); Terminal-Bench's tests/test.sh writing 1 or 0 (its isolation problem is on {{Agentic benchmarks|n:3c65c17b0d0d811fb926d7b91ef8234e}})
AssertionsProgrammatic checks on named parts of the stateτ²-bench telecom's environment assertions on the simulated phone; OSWorld's per-task checker scripts
Required informationString checks that the agent told the user specific factsτ²-bench's communicate_info: a substring that must appear in an agent message

A state diff is the strongest of these because it is indifferent to path and wording, and it sees changes the agent never mentioned. Keep it a diff, not just a hash: when a trial fails, the six differing fields of the default trial above explain it in one look, where a hash only says "different".

The do-nothing baseline

An outcome check is only as informative as the set of tasks it runs on. Many good agent tasks have "change nothing" as the right answer: refuse a cancellation the policy forbids, decline an unaffordable change. On those, an agent that does nothing passes. This page ran that agent through τ²-bench's evaluator: each task's first user turn and then nothing, no tool calls.

Do-nothing agent: the greeting and first user message of a real trial, then the conversation ends; graded with evaluate_simulation at commit 5bfa7e3. Airline and telecom use the full reward; retail's reward also includes LLM-judged assertions, which were not run, so its figure is the database component only (an upper bound for the do-nothing agent). Per-model bars: passes split by whether the do-nothing agent also passes that task; computed in the page from the 400 trials and checked by recompute.py.

On airline, 23 of 50 tasks are passed by an agent that does nothing, and 88 of GPT-5.2's 166 passing trials are on those tasks. Its pass^1 on the 27 tasks that need a change is 72.2%, against 83.0% overall (Opus 4.5: 73.2% against 84.0%). Neither number is wrong; they answer different questions, and the overall one hides that nearly half the suite rewards restraint. Anthropic's advice is the general form: "Test both the cases where a behavior should occur and where it shouldn't ... avoid class-imbalanced evals." For your own suite: run a do-nothing agent and a random agent first, report their scores beside every result, and report change and no-change tasks separately.

What an outcome check cannot see

  • Harm along the way. An agent that emails a customer's data to the wrong address and then finishes the booking correctly passes a check on the reservations table. The outcome check covers the state you decided to check; everything else is the next section's job.
  • A wrong gold state. The default trial above fails because the gold reservation assumes no insurance and one card while the simulated user asked for both. Your gold state encodes your assumptions about the user, and a simulated user does not know them.
  • A better route than the gold. GPT-5.2's task-31 trial upgraded the cabin so the flight could be moved and left the user satisfied; the gold says nothing should change. Anthropic's CORE-Bench story is the same failure at scale: Opus 4.5 "initially scored 42%" until a researcher found "rigid grading that penalized '96.12' when expecting '96.124991…', ambiguous task specs, and stochastic tasks"; after fixes and a less constrained scaffold it scored 95% ({{Anthropic, 9 Jan 2026|https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents}}).
  • Success the checker did not anticipate. On web agents, AgentRewardBench's experts found the benchmarks' rule-based checkers precise (83.8% precision) but blind to many real successes (55.9% recall), so they underreport success: GPT-4o's success rate was 16.7 points lower by the rules than by the experts on WebArena and 18.5 points on VisualWebArena ({{Lù et al., AgentRewardBench, Apr 2025|https://arxiv.org/abs/2504.08942}}).

Partial credit helps where a task has parts: "A support agent that correctly identifies the problem and verifies the customer but fails to process a refund is meaningfully better than one that fails immediately" (Anthropic). Score each required change separately and keep the all-or-nothing score beside it.

Grade actions, not messages

A message grader reads what the agent said. For agents that is the weakest evidence available, because saying and doing come apart. On the 400 τ²-bench trials, the transcript judge's verdict and the database disagree on 49: 18 trials where the judge found every assertion met and the database was wrong, and 31 the other way. And that judge read the whole transcript, tool calls included; a grader that reads only the final message knows less.

Two 2026 studies make the same point at higher stakes.

MOLE: what was measured (correction carried from the parent page)
An earlier version of the parent page said MOLE found that "a model's stated refusal did not predict whether it actually declined". That overstates the paper. What it measured: under a preamble telling every model the sandbox is harmless and that refusing spoils the research, 28 of 39 models (72%) completed more than half of their assigned harmful objectives; across models, refusal and completion rates are strongly linked (Spearman -0.73); 24 models never refused yet completed anywhere from 20% to 100%, mostly by not attempting; and the best monitor (Claude Opus 4.7, reviewing 10 accounts a day) caught 24 of 45 completed harms. Completion was verified in the services' state, not in what the agent said ({{Muhamed and Smith, MOLE, Sep 2026|https://arxiv.org/abs/2609.06966}}; corrected reading on the {{MOLE paper page|n:3db5c17b0d0d818b9680c7b91baaf7e9}}). The point that survives: in agentic systems, grade what the account did.

Emergence World ran eight ten-agent worlds for days under phishing, misinformation and memory exposure, and scored private reasoning, requested actions, executed actions and speech separately, letting none count for another ({{Akkil et al., Sep 2026|https://arxiv.org/abs/2609.17320}}). All seven exposed worlds warned their community about the phishing; none removed its traces. In the Gemini world, agents made 489 calls to the attacker's database after their own world had flagged the lure (counted from the released tool-call records on the {{Emergence World paper page|n:3e25c17b0d0d818fbffbc9e2ceab824b}}). A grader of messages would have scored that world as having detected the attack. (The paper's "up to 46 hours" is one agent retrying an attack link after the campaign, not a measured detection-to-stop delay; corrected on the paper page.)

And the logs of ordinary benchmarks hide the same thing. HAL re-ran nine benchmarks in 21,730 rollouts and, by reading logs with an LLM's help, found agents "searching for the benchmark on HuggingFace instead of solving a task, or misusing credit cards in flight booking tasks" ({{Kapoor et al., HAL, Oct 2025|https://arxiv.org/abs/2510.11977}}); neither shows up in a success rate.

How to grade actions

  • Forbidden actions as hard checks. List what must never happen (a write without the user's explicit yes, a payment method not on the profile, a call outside the allow-list) and scan every tool call for it. τ²-bench encodes some of this in its policy; your own list belongs in code.
  • Unexpected writes. Count writes that are in no gold action. On the 400 trials an exact audit of write calls (every gold write present with the same arguments, no others) agrees with the database check on 396; where they disagree, the transcript is worth reading.
  • A monitor over the trace for what you cannot enumerate. MOLE's results say how to build one: an LLM reading what the agent did beat count-based anomaly detection, and showing the monitor the agent's reasoning helped wherever the agent wrote it (on MOLE's DeepSeek corpus GPT-4.1 with reasoning beat GPT-5.5 on audit events alone). And it shows what to avoid: the renderer clipped every tool argument at 600 characters, so no monitor ever saw a data-poisoning trigger.
