Step-level grading: where it went wrong, and what not to demand

A step grader looks inside the trajectory. Four kinds are in use:

  • Gold-action matching. For each action in the task's reference solution, did the agent make that call with those arguments? τ²-bench computes this for every trial (action_checks, each marked read, write or generic), though its airline and retail rewards do not use it.
  • Trajectory matching. Compare the whole sequence of tool calls with a reference. LangChain's {{agentevals|https://github.com/langchain-ai/agentevals}} names the options cleanly: strict ("the same messages in the same order with the same tool calls"), unordered (the same calls in any order), subset and superset, each with a tool_args_match_mode of exact, ignore, subset or superset. The {{Path matchers|#t-match}} tab runs all of them on the five real trials above.
  • Per-step judges and process reward models, which score each step's quality (next section).
  • Efficiency counts: calls, failed calls, repeated calls, tokens and time per trial.

Demanding the reference path is the common mistake. Anthropic: "There is a common instinct to check that agents followed very specific steps like a sequence of tool calls in the right order. We've found this approach too rigid and results in overly brittle tests, as agents regularly find valid approaches that eval designers didn't anticipate." On the 400 trials, τ²-bench's gold-action check fails on 24 trials whose database is exactly right, usually over read calls (a lookup the agent did not need, or a calculate the agent did in its head, as in task 12 above). Restricting the check to write calls removes nearly all of that noise: the exact write audit agrees with the database on 396 of 400. The {{Path matchers|#t-match}} tab measures the whole range on GPT-5.2's 200 trials: matching every call strictly in order passes 7 trials and agrees with the final state on 38; matching write calls in any order with exact arguments agrees on 198.

Steps earn their keep in four places:

  1. Diagnosis. The outcome says "fail"; the steps say which call, with which argument, after which user turn. Every number on this page was explained by reading steps.
  2. Actions that must never happen, as hard checks (the previous section).
  3. Cost and efficiency, which the outcome cannot see: two agents that reach the same state with 7 calls and with 70 are not the same agent (see {{Cost and budgets|#rd-cost}}).
  4. When the outcome is unobservable or arrives too late: long tasks, production actions you cannot replay, intermediate checkpoints for partial credit.

Who grades a trajectory: judges, agent judges and process reward models

Code graders cover what you can specify. For the rest (was the plan sensible, was the user handled well, did a research agent's report answer the question) a model grades the trajectory. Three designs exist, and each needs its own calibration against people, as the parent page argues for every judge.

Trajectory LLM judges

A model reads the transcript (messages, calls, results) and answers a rubric; τ²-bench's natural-language assertions above are one, and agentevals ships a default TRAJECTORY_ACCURACY_PROMPT. On web agents, AgentRewardBench had experts label 1,302 trajectories from 5 benchmarks and 4 agents and tested 12 judges: "no single LLM excels across all benchmarks"; the best, GPT-4o with accessibility trees, reached 69.8% precision, below the rule-based checkers' 83.8% but with far better recall ({{AgentRewardBench|https://arxiv.org/abs/2504.08942}}). On 931 mobile-agent trajectories, a simple judge reading sampled screenshots (90.9% with Gemini 3 Flash, the authors' own baseline) matched or beat purpose-built pipelines (89.3% for AgentRewardBench's method) ({{MobileJudgeBench, Aug 2026, preprint|https://arxiv.org/abs/2608.11434}}).

Agent-as-a-judge

Instead of reading a transcript, the judge acts: it opens the produced repository, runs code and checks each requirement against evidence. The original paper built DevAI (55 AI-development tasks, 365 hierarchical requirements, three expert annotators) and reports its agent judge agreeing with the experts' consensus on 90.44% of requirements against 60.38% for an LLM judge without tools, on OpenHands' outputs in its black-box setting, for $30.58 and 118.43 minutes against about $1,297.50 and 86.5 hours for the three experts ({{Zhuge et al., Oct 2024|https://arxiv.org/abs/2410.10934}}; its own runs).

Correction: DevAI's cost and time percentages are swapped in the paper (carried from the root's Judge atlas)
Section 4.4 says the agent judge cost 2.29% of the human cost and took 2.36% of the time. Its own figures give the reverse: $30.58 / $1,297.50 = 2.36% of the cost, and 118.43 of 5,190 minutes = 2.28% of the time. The abstract's savings (97.64% of the cost, 97.72% of the time) agree with the figures.

A third party confirms the direction: on AJ-Bench (155 tasks, 516 annotated trajectories in search, data systems and GUI), giving the judge tools lifted DeepSeek V3.2 from 64.49 to 77.34 (+12.85 points) and GPT-5-mini (low) from 59.00 to 72.41 (+13.41) ({{Shi et al., AJ-Bench, Apr 2026, preprint|https://arxiv.org/abs/2604.18240}}). Process reward models

A process reward model (PRM) scores each step rather than the end. The idea came from maths: OpenAI found "process supervision significantly outperforms outcome supervision" for training on MATH, with its process-supervised model solving 78% of a representative test subset, and released PRM800K, 800,000 step-level human labels ({{Lightman et al., May 2023|https://arxiv.org/abs/2305.20050}}). For agents, AgentPRM learns step values from Monte Carlo rollouts (how often does the task succeed if you continue from here?), and InversePRM learns them from demonstrations; 3B models trained with them beat GPT-4o baselines on ALFWorld ({{Choudhury, Feb 2025|https://arxiv.org/abs/2502.10325}}). As an evaluator, a PRM gives a per-step curve that locates the step where success became unlikely. Two cautions: it is a trained model, so an agent optimised against it can exploit it (the paper itself analyses reward hacking; see {{Reward Hacking|n:3c65c17b0d0d8196a6f1f29a817aa974}}), and its step scores need the same meta-evaluation as any judge.

A judge only knows what it is shown

MOLE's monitors are trajectory judges, and its observability result generalises: on the three multiday corpora whose agents wrote reasoning, GPT-4.1 reading that reasoning had a higher recall than GPT-5.5 reading only the audit events (0.49 against 0.39, 0.71 against 0.52, 0.68 against 0.45; the paired interval excludes zero on one corpus, is borderline on one and not established on one), and a 600-character clip on tool arguments hid every data-poisoning trigger from every monitor. Decide what the judge sees as deliberately as which judge you use; log enough that you can change your mind later.
