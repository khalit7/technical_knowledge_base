Reliability across runs: pass^k

An agent run is a sample. The same agent on the same task can pass, fail, or pass for a different reason, so one trial per task measures luck as much as skill. Two numbers separate them: pass@k, the chance that at least one of k trials succeeds (the right number when a person picks the best attempt), and pass^k, "the probability that all k trials succeed" (Anthropic's wording; the metric is from {{τ-bench, Yao et al., Jun 2024|https://arxiv.org/abs/2406.12045}}). A product that must work every time a customer calls is a pass^k product.

A concrete task first: with 4 trials of which 3 passed, the chance that 2 trials drawn from them both pass is C(3,2)/C(4,2) = 3/6 = 0.5. Averaged over tasks:

pass^k = mean over tasks of C(c, k) / C(n, k)     pass@k = mean over tasks of [ 1 − C(n−c, k) / C(n, k) ],   n trials per task, c of them passed

pass@k counts the draws of k trials that include at least one pass (all draws minus those taken only from the n − c failures); it has been the metric of code benchmarks since Codex. Both estimators are unbiased for k ≤ n, and at k = 1 both equal the mean success rate; beyond n they cannot be estimated without a model of each task's success probability.

The two agents tie at k = 1 and part as k grows: reliability is a curve, not a number

pass^k from the released trials with the formula above: GPT-5.2 83.0, 78.3, 75.0, 72.0; Opus 4.5 84.0, 77.7, 73.5, 70.0 for k = 1 to 4, matching the leaderboard's pass^1 and pass^4 independently. derived here

Anthropic's rule of thumb applies to the last group: "a 0% pass rate across many trials (i.e 0% pass@100) is most often a signal of a broken task, not an incapable agent". Eight trials is far from a hundred, and whether these three are broken is unconfirmed here; they are the first transcripts to read. Task 29 is the mixed kind worth reading too: it passed once, and what decided it was the simulated user.

Where the variance comes from

  • The agent's sampling. The variance you want to measure.
  • The simulated user. Its improvisations change the right answer (task 29), so part of what any simulated-user eval measures is the simulator, and its version changes between leaderboard rows. Pin it, and when a task flips, check whether the user changed first.
  • The environment. "Each trial should be 'isolated' by starting from a clean environment. Unnecessary shared state between runs (leftover files, cached data, resource exhaustion) can cause correlated failures due to infrastructure flakiness rather than agent performance" (Anthropic).
  • The grader. A code grader on a fixed trajectory is deterministic: re-grading the 200 GPT-5.2 airline trials reproduces every recorded reward. An LLM judge is not; re-run it on fixed trajectories to measure its own noise before you blame the agent.

Trials of one task are correlated, so k trials of 50 tasks are not 50k independent observations: cluster error bars by task ({{Eval statistics|n:3ef5c17b0d0d8187a7b4e5b4ec4a546d}} has the formulas and the sample-size calculator). A failure taxonomy for agent runs

A pass rate says how often; a taxonomy says why, and which fix to try. Use two levels. The symptom can be read by code from the trace and the state diff, for every trial. The cause needs a person (or a judge) reading the transcript, for a sample.

Most failed trials either never wrote, or wrote the wrong thing

The 66 failed trials of the 400 (GPT-5.2 34, Opus 4.5 32), each placed in one symptom by comparing its write calls with the gold writes: wrote on a no-change task; made no write when one was needed; a gold write missing and another made instead; some gold writes missing; every gold write plus extra ones; writes exactly right but the required information not given. measured here, checked by recompute.py.

Symptoms are not causes. "No write when one was needed" includes task 0's transfer to a human and an agent wrongly refusing; "wrong write" includes task 29, where the cause was the gold state and the simulated user, not the agent. τ-bench's authors read 36 failed gpt-4o retail trajectories and found about 55% "wrong argument or information provided", 25% "incorrect decision-making" (rules and domain) and 19% "partial resolution of compound requests"; 4 further failures were the user instructions' fault (τ-bench, Figure 5).
