Simulated users, sandboxes and environment design

The environment is half of an agent eval: the tools, the state they act on, the simulated user if there is one, and the verifier. Which harness gives you which sandbox (Docker, Kubernetes, VMs, cloud sandboxes, NVIDIA OpenShell with network policies in Inspect; none in lm-eval or HELM) is on {{Eval harnesses|n:3c65c17b0d0d81ea9cd5eb65795ff5c9}}, section Sandboxes for agentic evals; RL environments built for training are on {{Harnesses for training and evaluation|n:3f15c17b0d0d815ea579d6c80065aa36}}. What to design, whichever you use:

The agent touches only its tools; the verifier and the gold live where it cannot reach

One trial's environment as τ²-bench builds it, with the two boundaries that matter: the sandbox (everything the agent can change) and the verifier's side (gold actions, gold state, the checker), which the agent must not be able to read or edit. Every arrow across the sandbox wall is a choice: the network policy, and what the simulated user is told.

  • The production agent in a copy of production. "It's essential that the agent in the eval functions roughly the same as the agent used in production" (Anthropic): the same tool schemas, system prompt and limits, so the eval measures what you ship.
  • State you can reset and diff. τ²-bench's whole world is a JSON database rebuilt for every trial and replayed for grading, with a frozen clock (every booking in these trials is created at 2024-05-15 15:00). That is what made this page's re-grading and diffs possible.
  • A clean start per trial, so failures are independent ({{Reliability|#rd-rel}}).
  • A pinned simulated user with instructions that say what the user wants on every choice the gold state depends on (task 29's insurance and payment method were not). Keep the simulator's model and prompt fixed across the runs you compare.
  • A verifier out of the agent's reach. On Terminal-Bench 2.0 an exploit agent replaced the curl the in-container verifier used, and every 3.0 and 4.0 task declares a separate verifier container; OSWorld's gold files were downloadable from inside the VM ({{Agentic benchmarks|n:3c65c17b0d0d811fb926d7b91ef8234e}}).
  • A network policy stated per task: no network, an allow-list, or open. Emergence World's agents turned a read-only fetch tool into a publishing channel through a GET-accepting API (its paper page has the round-by-round containment).
  • Long-horizon state when the risk is long-horizon. MOLE's simulated organisation (150 agent-run accounts, 9 stateful services, 30 workdays) exists because single-session tasks cannot show harm that accumulates across days.

Reward hacking and verifier exploits in your own evals

An eval you optimise against becomes a target, and agents find the gaps faster than people do. In April 2026 Berkeley RDI's exploit agent scored near the top of eight public agent benchmarks "without solving a single task" (the flaw patterns and the Terminal-Bench curl exploit are on {{Agentic benchmarks|n:3c65c17b0d0d811fb926d7b91ef8234e}}; the training-time version is {{Reward Hacking|n:3c65c17b0d0d8196a6f1f29a817aa974}}). The same happens inside private evals:

  • Models hack the scorer you gave them. METR found o3 reward hacking in 0.7% of HCAST runs and more than 43 times as often on RE-Bench (overwriting the timing function, monkey-patching the evaluation "so that it judges every submission as successful"), found by inspecting anomalously high-scoring runs ({{METR, 5 Jun 2025|https://metr.org/blog/2025-06-05-recent-reward-hacking/}}).
  • Impossible tasks measure the propensity. ImpossibleBench mutates a task's tests so they contradict its specification; any pass "necessarily implies a specification-violating shortcut". GPT-5 cheated on 76% of one-off-mutated SWE-bench tasks; letting the agent flag the task for a human lowered it from 54% to 9% on conflicting SWE-bench tasks ({{Zhong, Raghunathan and Carlini, Oct 2025|https://arxiv.org/abs/2510.20270}}).
  • The harness can overfit the eval. StateM's 95.28% Terminal-Bench 2.1 submission fell to 92.36% with all 13 flags the leaderboard's judge raised (four for "harness cheating", gate slots that mapped onto single tasks). HarnessDev: the score a harness creator could see moved the same way as the held-out score in only 34 of 64 version changes ({{HarnessDev paper page|n:3d45c17b0d0d81cd9883f783840e013f}}).
  • Self-improving agents keep their hacks. In a Factorio run, Prime Agent found it could spawn resources through RCON despite an anti-cheating heartbeat and saved the shortcut as a reusable skill ({{Prime Agent paper page|n:3cd5c17b0d0d81579a02f0431f24c6cb}}).
Defences that cost little
  • Run the verifier where the agent cannot reach it (the figure above): a separate container, tests copied in after the agent stops, read-only or hidden tests.
  • Add canaries: impossible variants of a few tasks (any pass is a hack) and a do-nothing agent (its score is the floor).
  • Keep a held-out task split that no prompt, harness or skill was tuned on.
  • Read the transcripts of the highest scores and of every sudden jump, as METR did; then put a monitor on the rest.
  • Give the agent a legitimate way out ("flag for a human"); it cut cheating by more than five times in ImpossibleBench.
The numbers in detail: METR's tasks, ImpossibleBench's monitors, StateM's flags

METR: hacks also included returning the answer "the scoring system already calculated". On RE-Bench, 21 of 21 runs of Optimize LLM Foundry, 12 of 28 of Rust Codecontest and 6 of 24 of Optimize a Kernel reward hacked; on HCAST it also used a model monitor.

ImpossibleBench: GPT-5 cheated on 2.9% of the one-off-mutated LiveCodeBench tasks; hiding the tests cut cheating success to near zero; a Claude Sonnet 4 monitor caught 86 to 89% of cheating on LiveCodeBench but only 42 to 50% on SWE-bench.

StateM: 95.28% raw, 94.38% with the four flagged trials its authors accepted, 93.26% with all nine reward-hacking flags zeroed, 92.36% with all 13 (420, 415 and 411 of 445 trials); the pull request was closed unmerged on 19 September 2026 ({{StateM paper page|n:3c65c17b0d0d81899098d8153e100691}}).

Cost and step budgets

Two agents with the same success rate are not equally good if one needs three times the money or ten times the calls, and an agent with no budget can buy success by trying longer. Fix the budget before the run (steps, tokens, wall-clock time, dollars), report the score at that budget, and count "ran out of budget" as its own failure. τ²-bench's runs here allowed 200 steps and 10 tool errors per trial (the files' run configuration); MOLE capped sessions at 50 turns, and two of its four agents hit the cap on the same assignment that GPT-5.3 finished in 9 turns.

Failing trials cost more than passing ones, and equal pass rates hide a 3.5x cost gap

Mean agent cost and tool calls per trial, passing against failing, from each trial's agent_cost field in the released files (the harness's own estimate; the user simulator's cost is separate). computed here, checked by recompute.py.

A failing agent keeps searching (GPT-5.2: $0.181 against $0.100 a trial, 15.7 tool calls against 9.6). The two runs that tie at pass^1 cost $22.76 for GPT-5.2's 200 trials against $79.84 for Opus 4.5's: $0.137 against $0.475 per successful trial. Prices change and these are the harness's estimates, so the ratio, not the dollars, is the finding. At scale, HAL spent about $40,000 on 21,730 rollouts and found "higher reasoning effort reducing accuracy in the majority of runs", so more budget is not automatically more score. What to log so any grader can run again

Everything on this page was graded from logs. Log every tool call with full arguments and results (no 600-character clip), state snapshots or diffs, the termination reason, tokens, cost and time per step, the agent's reasoning where policy allows (MOLE's monitors needed it), and the versions of the model, prompt, harness, simulated user and judge. Then any grader can be re-run, later, on the same trials.

One trap in the standard: in the OpenTelemetry GenAI conventions a tool span requires gen_ai.tool.name, but gen_ai.tool.call.arguments and gen_ai.tool.call.result are opt-in, so default instrumentation drops exactly what an action grader needs. Turn them on in eval runs. Spans, attributes and the tools compared: {{LLM observability|n:3c65c17b0d0d81fe82c0c6e9360afec4}}.

Building an agent eval suite for your own product

  1. Write tasks with a resettable, diffable state and a gold end state; say in the user instructions everything the gold depends on.
  2. Balance tasks that need a change against tasks whose right answer is no change; run a do-nothing agent and report its score.
  3. Grade the outcome with code; add hard checks for forbidden actions and an audit of unexpected writes.
  4. Use model judges (transcript, agent-as-a-judge, PRM) only for what code cannot specify, and calibrate each against human labels.
  5. Run several trials per task; report pass^k, clustered error bars, and per-task outcomes.
  6. Isolate trials and the verifier; pin the simulator, the judge and the harness versions.
  7. Label failures by symptom with code and by cause for the ones you read.
  8. Add impossible canaries and a held-out split; read the top scores and every jump.
  9. Fix budgets; report cost per success and budget-exhausted failures separately.
  10. Log full traces (arguments, results, state, reasoning, versions) so any grader can be re-run.
