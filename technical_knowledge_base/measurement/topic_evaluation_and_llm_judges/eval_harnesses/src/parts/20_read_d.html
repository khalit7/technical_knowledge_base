Each harness, one by one

lm-evaluation-harness (EleutherAI)

The reproducibility standard for base-model benchmarking and the default behind "numbers in a model card". It was the backend of Hugging Face's Open LLM Leaderboard v1 and v2; the leaderboard Space was archived on 13 March 2025 (parent page, tab Same model, many harnesses), although the harness README still calls it "the backend for 🤗 Hugging Face's popular Open LLM Leaderboard" ({{README|https://github.com/EleutherAI/lm-evaluation-harness/blob/d6de81643928d653435c431bae19945d41d32520/README.md}}).

  • Architecture. A TaskManager discovers task YAML files and builds ConfigurableTask objects; a registry maps model names to LM subclasses. The registry holds 37 model names, aliases included (hf, vllm, sglang, openai-completions, anthropic, litellm, mamba, gguf, nemo, neuron, IPEX, ONNX, TensorRT-LLM, watsonx and more; {{lm_eval/models|https://github.com/EleutherAI/lm-evaluation-harness/tree/d6de81643928d653435c431bae19945d41d32520/lm_eval/models}}). Implement the three request methods and any backend runs every task; requests are batched, cached (--use_cache, --cache_requests) and distributed.
  • Task YAML. Declares the dataset (a Hugging Face Hub path), doc_to_text and doc_to_target (Jinja templates, or Python through !function), output_type, metrics, generation settings and filter chains (regex extraction, take-first, majority voting for self-consistency). Variants (shot counts, chain-of-thought versions, translations) are YAML overrides through include:; groups and tags aggregate tasks (mmlu is a group of 57 subtasks). The tasks folder has 221 benchmark directories and about 14,000 YAML files at commit d6de816; the README says "over 60 standard academic benchmarks, with hundreds of subtasks and variants".
  • Gotchas. Few-shot formatting and --apply_chat_template change scores materially; trust_remote_code runs dataset code; results depend on filter chains as much as on the model; YAML quoting bites (until: ['\n'] in single quotes is a backslash and an n, not a newline: the project's {{footguns.md|https://github.com/EleutherAI/lm-evaluation-harness/blob/d6de81643928d653435c431bae19945d41d32520/docs/footguns.md}}). Always log the task's version from its metadata: GSM8K is at version 3.0.

Inspect (UK AI Security Institute)

The frontier-safety and agentic standard: used by AI security institutes, METR, Apollo Research and labs for pre-deployment testing. Where lm-eval models "prompt in, string out", Inspect models an eval as a program.

  • Abstractions. A Task is a dataset, a solver and a scorer. A solver transforms a TaskState (messages, output, a per-sample store); solvers compose into chains: system_message(), prompt_template(), generate(), chain_of_thought(), self_critique(), multiple_choice(), use_tools(), or a whole agent such as react() (the older basic_agent() still ships). A scorer grades the final state: exact(), match(), includes(), pattern(), choice(), answer(), math(), model_graded_qa(), model_graded_fact(), the perplexity scorers, or custom Python, including batteries of judges. Metrics aggregate scores (accuracy, stderr, bootstrap_stderr, ci_wilson, even krippendorff_alpha); Epochs reruns each sample and reduces with mean, median, mode, max, at_least_k or pass_at_k ({{scorer exports|https://github.com/UKGovernmentBEIS/inspect_ai/blob/9f6accda8dce5ccd754e6be1a22fbcee96042e82/src/inspect_ai/scorer/__init__.py}}).
  • Sandboxing: below, in {{Sandboxes for agentic evals|#rd-sandbox}}. It is the feature that made Inspect the agentic default.
  • Tooling. inspect view and the VS Code extension render every model call, tool call, state change and score from the log: the best debugging experience of any harness, and the .eval format is stable enough for other tools to consume. The tab {{Inside a run log|#t-logs}} walks a real one.
  • Models. All major APIs and local engines (vLLM, SGLang, Hugging Face transformers, Ollama, llama-cpp-python, and even TransformerLens and nnterp for interpretability work; {{providers|https://inspect.aisi.org.uk/providers.html}}); --model switches provider without touching the task.
  • inspect_evals is the community collection: "120+ evaluation implementations and 200+ Inspect AI tasks" by its own count ({{EVAL_REGISTER.md|https://github.com/UKGovernmentBEIS/inspect_evals/blob/0dacad3c3bacfb50308de94eb8b8f9e368cfe30c/EVAL_REGISTER.md}}). Since 8 May 2026 it takes no new eval code: new evals live in their authors' repositories and are listed in a Register at a pinned commit (see {{Contributing|#rd-contrib}}).

lighteval (Hugging Face)

Harness-inspired and Hugging Face-native: 1000+ tasks by its README, backends for transformers and accelerate, vLLM, SGLang, TGI, Inference Endpoints, Inference Providers, LiteLLM and nanotron (evaluation during pretraining), tight Hub integration (results and per-sample details pushed to the Hub), quick custom tasks in Python, wide multilingual coverage; it powers Hugging Face's leaderboards.

What changed: lighteval now runs on Inspect
Its README lists lighteval eval, "using inspect-ai as a backend", as the preferred entry point ({{README|https://github.com/huggingface/lighteval/blob/c2af9e5f2fde494539f84c8ea9d09f18ac9e9c14/README.md}}); its GSM8K task carries an Inspect sample converter, a solver chain and a scorer next to the classic prompt function, with the same prompt text as inspect_evals' GSM8K ({{gsm8k.py|https://github.com/huggingface/lighteval/blob/c2af9e5f2fde494539f84c8ea9d09f18ac9e9c14/src/lighteval/tasks/tasks/gsm8k.py}}). Its docs warn that "not all tasks are compatible with inspect-ai's API as of yet". The last PyPI release is 0.13.0 (24 November 2025) while main kept moving (30 September 2026): install from source for current behaviour, and pin the commit.

Choose it when you live in the Hugging Face stack or need evaluation inside a nanotron or FSDP training loop. It is weaker than lm-eval on community-verified task parity and, outside its Inspect path, weaker than Inspect on agents.

HELM (Stanford CRFM)

The multi-metric methodology reference: each scenario scored on accuracy, calibration, robustness, fairness, bias, toxicity and efficiency ({{Liang et al. 2022|https://arxiv.org/abs/2211.09110}}), with every prompt and response dumped per instance and browsable in a web UI. It spawned domain leaderboards: VHELM, HEIM, MedHELM, audio, enterprise and more ({{README|https://github.com/stanford-crfm/helm/blob/63754d05db6f874e41a395880fb573890a13e791/README.md}}).

A run is a RunSpec: a scenario (how to load instances), an adapter spec (instructions, input and output nouns, shots, max tokens, stop sequences) and metric specs. HELM's GSM8K is "Q: ... A:" with 5 training examples whose answers have "####" replaced by "The answer is", 400 tokens, stop at a blank line ({{run spec|https://github.com/stanford-crfm/helm/blob/63754d05db6f874e41a395880fb573890a13e791/src/helm/benchmark/run_specs/lite_run_specs.py#L137-L158}}).

Maintenance mode since 1 June 2026 (verified)
The README says "HELM entered maintenance mode on June 1, 2026", and the {{Maintenance Mode Policy|https://crfm-helm.readthedocs.io/en/latest/maintenance_mode/}} says volunteers maintain it on a best-effort basis, "no new features will be added to HELM, and no new evaluations will be added to the HELM leaderboards", and scenarios may break as provider APIs change. The last commit on main is 5 June 2026. Read it for methodology (its "coverage beats a headline score" stance predated the field by two years); do not build new pipelines on it. The policy names Evalchemy, Inspect Evals, lighteval, lm-eval-harness and Unitxt as alternatives.

OpenAI's two: evals and simple-evals

  • {{openai/evals|https://github.com/openai/evals}} (2023) is a registry: a YAML names an eval template (Match, Includes, FuzzyMatch, model-graded) and points at JSONL samples kept in Git LFS. Match passes when the output starts with the ideal answer ({{evals/api.py|https://github.com/openai/evals/blob/8eac7a7de5215c907fbddc30efdaf316913eccdd/evals/api.py#L79-L104}}), which a chain-of-thought answer never does. The README now points to Evals in the OpenAI dashboard, says "we are currently not accepting evals with custom code", and the last PyPI release is 3.0.1.post1 (1 May 2024).
  • {{openai/simple-evals|https://github.com/openai/simple-evals}} (2024) published how OpenAI produced its launch numbers: zero-shot chain-of-thought with simple instructions, because few-shot and role-play prompts are "carryovers from evaluating base models". Its July 2025 notice says it "will no longer be updated for new models or benchmark results"; it continues to host the reference implementations of HealthBench, BrowseComp and SimpleQA ({{README|https://github.com/openai/simple-evals/blob/652c89d0ca9df547706735883097e9537d40dc47/README.md}}).

Evalchemy and Unitxt

  • Evalchemy (DataComp and Bespoke Labs) "builds on the LM-Eval-Harness" for post-trained models: one install for reasoning, code and chat benchmarks (AIME, MATH500, LiveCodeBench, GPQA Diamond, MT-Bench, AlpacaEval, WildBench and others), API models through Curator. A benchmark is a Python class with generate_responses and evaluate_responses on lm-eval's LM and Instance. Its MATH500 sets "do_sample": False and "temperature": 0.7 in the same request ({{eval_instruct.py|https://github.com/mlfoundations/evalchemy/blob/6ed674159b37f740f2353a86f596f49f6ac13c19/eval/chat_benchmarks/MATH500/eval_instruct.py#L78-L92}}): which one wins depends on the backend, so log what was actually sent. Last commit 23 December 2025.
  • Unitxt (IBM) treats prompt variation as first-class: a card (loader, preprocessing steps, task) is combined at run time with a template, a format (for example chat API) and a number of demos, and a card can list many templates ({{MMLU card|https://github.com/IBM/unitxt/blob/74b8bb6330fed5e1a78ae0c35c1e2c1c126db7f6/src/unitxt/catalog/cards/mmlu/abstract_algebra.json}}). Its catalog badge counts 68 tasks, 3,254 datasets, 357 prompts and 584 metrics. It plugs into others: lm-eval ships tasks/unitxt and HELM a unitxt_scenario.
