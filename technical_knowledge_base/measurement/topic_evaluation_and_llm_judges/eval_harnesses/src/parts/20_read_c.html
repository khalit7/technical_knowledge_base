How each scores: three decisions inside every number

Whatever the harness, a score is the product of three decisions: how the answer is read (probabilities or generated text), how a generated answer is extracted, and how the prompt is wrapped (raw text or the model's chat template). The parent page's tab Same model, many harnesses measures how much each one moves a score; here is where each harness makes them.

1. Probabilities or text

lm-eval-harness has four request types ({{lm_eval/api/instance.py|https://github.com/EleutherAI/lm-evaluation-harness/blob/d6de81643928d653435c431bae19945d41d32520/lm_eval/api/instance.py#L5-L7}}), and a backend only has to implement three methods to run all of them ({{model guide|https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/model_guide.md}}):

  • loglikelihood(context, continuation): the log-probability of a given continuation and whether it is the greedy one. A multiple_choice task asks it once per option and picks the largest. No sampling, deterministic, cheap, works on base models; it measures how the model ranks given options, never whether it can produce an answer, and it needs log-probabilities of the prompt, which most chat APIs do not return.
  • loglikelihood_rolling(text): the log-probability of a whole text, for perplexity and bits-per-byte.
  • generate_until(context, until=[...]): generate until a stop string, then post-process with filters. This is what chat and reasoning models need, and every extraction rule becomes part of the score.
Length normalisation, exactly
For multiple_choice tasks lm-eval reports acc (argmax of the summed log-probabilities), acc_norm (argmax of the sum divided by the option's length in characters), and, when asked, acc_bytes (divided by its UTF-8 byte length) and acc_mutual_info ({{task.py lines 1494 to 1560|https://github.com/EleutherAI/lm-evaluation-harness/blob/d6de81643928d653435c431bae19945d41d32520/lm_eval/api/task.py#L1494-L1560}}). The old version of this page called acc_norm byte-length normalised; it is character-length, which is the same for ASCII options and different for most other scripts.

The other harnesses lean generative. HELM has both generation and multiple-choice adapters; Inspect, simple-evals, promptfoo and Braintrust score generated text. Inspect added perplexity() and target_perplexity() scorers in 0.3.212 (24 April 2026; {{changelog|https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/CHANGELOG.md}}); the docs describe target_perplexity() as the counterpart of lm-eval's loglikelihood pattern, and it needs prompt log-probabilities, which only its vLLM and SageMaker providers supply ({{Inspect: Perplexity|https://inspect.aisi.org.uk/perplexity.html}}).

The field has been moving multiple-choice benchmarks from loglikelihood to generated chain-of-thought formats; Hugging Face's Open LLM Leaderboard v2, run on lm-eval, mixed both: four of its six tasks (BBH, GPQA, MMLU-Pro, MuSR) are multiple_choice and two (IFEval, MATH Level 5) are generate_until ({{tasks/leaderboard|https://github.com/EleutherAI/lm-evaluation-harness/tree/d6de81643928d653435c431bae19945d41d32520/lm_eval/tasks/leaderboard}}). Scores under the two formats are different measurements even when the benchmark has the same name: never compare across them.

2. Extraction

A generative task is only as good as the code that finds the answer in the text. On GSM8K, the same benchmark in each harness uses a different rule (the tab {{One task, every harness|#t-same}} runs all of them on real outputs):

HarnessRule for the GSM8K answer
lm-eval gsm8kTwo filters reported side by side: strict-match needs #### <number> (the training-set format the 5 shots teach); flexible-extract takes the last number-like string. Then exact_match after removing commas, $ and a trailing period
inspect_evals gsm8kThe prompt asks for ANSWER: $ANSWER, but the scorer match(numeric=True) ignores that line: it takes the last number in the whole output and compares numerically, formatted to 5 significant digits (.5g): for the 18 of 1,319 test answers above 99,999, a prediction of 114,201 matches a gold of 114,200
lighteval gsm8kParses expressions and LaTeX (a boxed answer first) from the output and the gold, then compares the parsed values
HELM gsmfinal_number_exact_match: the last match of -?[\d,]+(?:.\d+)? in output and gold. The dot is unescaped, so it matches any character: "3 4" is read as one number
simple-evals MGSM (English)Text after the last "Answer", then the last number in it (the code comment says "the first number"; the code returns the last). The match on "Answer" is case-sensitive, so an "ANSWER:" line, the format inspect_evals asks for, is never found
OpenAI evals MatchThe output must start with the ideal answer string

Extraction failures score as wrong answers, silently. They are the usual cause of "model X dropped 20 points": a new model writes **72** or \boxed{72} or "The answer is: 72 dollars" and the old regex misses it. When a score moves, read ten failures before believing it.

3. Chat template

Instruction-tuned models were trained on their own chat format; sending them raw text is a different test. Each harness has a default:

  • lm-eval sends raw text unless asked. --apply_chat_template wraps prompts in the tokenizer's template, --fewshot_as_multiturn (on by default with it) turns the shots into alternating turns, and --system_instruction adds a system prompt ({{interface.md|https://github.com/EleutherAI/lm-evaluation-harness/blob/d6de81643928d653435c431bae19945d41d32520/docs/interface.md#L75-L120}}). The results file records a hash of the chat template and of the system instruction.
  • Inspect sends messages; its Hugging Face provider applies the tokenizer's chat template unless use_chat_template=False. inspect_evals' GSM8K puts its ten shots in one system message.
  • simple-evals and the app-level tools always send chat messages; HELM builds a text prompt and the model client decides how to send it.
A default worth knowing: Inspect's local Hugging Face provider samples
Inspect's hf provider sets do_sample=True unless the model argument do_sample=False is passed ({{hf.py line 118|https://github.com/UKGovernmentBEIS/inspect_ai/blob/9f6accda8dce5ccd754e6be1a22fbcee96042e82/src/inspect_ai/model/_providers/hf.py#L117-L118}}), so a local run uses the model's own sampling settings (Qwen2.5-0.5B-Instruct's {{generation config|https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct/blob/main/generation_config.json}} samples at temperature 0.7, top-p 0.8, top-k 20, repetition penalty 1.1). Passing --temperature 0 instead raises an error in transformers 5.18, which this page hit. lm-eval's GSM8K task sets do_sample: false, temperature: 0.0 in the YAML. Greedy against sampled is a knob in its own right.
