Contributing: where the entry points are now

  • lm-evaluation-harness: still genuinely open. Port or add a task in YAML ({{new task guide|https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/new_task_guide.md}}; its checklist asks whether you checked against the paper's reference implementation and documented how), fix answer-extraction filters for reasoning models, or add a backend ({{model guide|https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/model_guide.md}}). Maintainers keep a list of "good first issue" and "help wanted" items ({{CONTRIBUTING|https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/CONTRIBUTING.md}}).
  • Inspect: two repositories with very different bars. inspect_ai is the framework (a high bar). inspect_evals changed its model in 2026:
    Correction: inspect_evals no longer takes new eval code
    The old version of this page called inspect_evals "the designed on-ramp": pick a published benchmark, propose it in an issue, ship it with an end-to-end test and a parity check, start with question-answering before agentic tasks. Since 8 May 2026 "new evaluations must be hosted in an upstream repo and registered to Inspect Evals via a simple .yaml file" ({{EVAL_REGISTER.md|https://github.com/UKGovernmentBEIS/inspect_evals/blob/0dacad3c3bacfb50308de94eb8b8f9e368cfe30c/EVAL_REGISTER.md}}); the Register lists each eval at a pinned commit of its author's repository, which must be installable, depend on inspect_ai and define tasks with @task ({{register guide|https://github.com/UKGovernmentBEIS/inspect_evals/blob/0dacad3c3bacfb50308de94eb8b8f9e368cfe30c/register/README.md}}). Pull requests to the collection now come only from pre-approved contributors; anyone else raises an issue and uploads .eval logs that show the problem (the rule was tightened on 2 October 2026). And the priority flipped: the guide now prefers "agentic or task-based over simple Q&A", credibly sourced, with a frontier-model baseline to validate against ({{CONTRIBUTING|https://github.com/UKGovernmentBEIS/inspect_evals/blob/0dacad3c3bacfb50308de94eb8b8f9e368cfe30c/CONTRIBUTING.md}}).
    The practical path today: implement the eval in your own repository from the {{Generality Labs template|https://github.com/Generality-Labs/inspect-evals-template}}, test it against a published baseline to the bar in its {{docs/methodology.md|https://github.com/UKGovernmentBEIS/inspect_evals/blob/0dacad3c3bacfb50308de94eb8b8f9e368cfe30c/docs/methodology.md}} and {{BEST_PRACTICES.md|https://github.com/UKGovernmentBEIS/inspect_evals/blob/0dacad3c3bacfb50308de94eb8b8f9e368cfe30c/BEST_PRACTICES.md}}, register it, and report bugs in existing evals with logs. Given Khalid's judge-battery background, model-graded scorers and judge-reliability tooling are a natural niche, now as a registered upstream eval or a scorer contribution rather than a pull request to the collection.
  • lighteval: custom tasks and metrics in Python ({{adding a custom task|https://huggingface.co/docs/lighteval/adding-a-custom-task}}), multilingual task contributions, and converting tasks to its Inspect path.
  • HELM: notable models, notable scenarios, API-client fixes and significant bug fixes only; open an issue first and wait for triage, because pull requests without one are closed ({{Maintenance Mode Policy|https://crfm-helm.readthedocs.io/en/latest/maintenance_mode/}}).
  • OpenAI: simple-evals accepts only bug fixes, model adapters and new result rows; openai/evals accepts no custom-code evals, only template-based or model-graded YAML ones.
  • promptfoo: an ordinary open-source project (providers, assertions, red-team plugins), now with OpenAI as owner.

Common mistakes

Comparing scores from two harnesses because the benchmark has the same name
Prompt, shots, scoring method, extraction and chat template all differ by default; on GSM8K alone the six rules above disagree on what counts as an answer. Compare within one harness, one version, one config.
Reporting a number without the harness version, task version and settings
Give harness and commit, task version, shots, chat template on or off, decoding (greedy or sampled, with seed), max tokens, and the extraction filter. lm-eval writes most of this into its results file; Inspect into its log header; copy it into the report.
Trusting the default decoding
Inspect's local Hugging Face provider samples unless told not to; Evalchemy's MATH500 sends both do_sample: False and temperature: 0.7. Set decoding explicitly and check what reached the model in the log.
Believing a sudden drop before reading the failures
A new output format (**72**, \boxed{72}, "ANSWER: 72") or a truncated completion scores as a wrong answer. In this page's own lm-eval run, strict-match scored 0 of 10 and flexible-extract 1 of 10 on identical outputs; Inspect's scorer reads yet another way (tab {{Inside a run log|#t-logs}}).
Running a model-written-code task without a sandbox
lm-eval's --confirm_run_unsafe_code and Inspect's local sandbox both run model code as you on your machine. Use Docker or a VM-backed sandbox for anything agentic.
Building a new pipeline on HELM or simple-evals
Both are frozen for new work (HELM since 1 June 2026, simple-evals since July 2025). Read them for method; run current evals elsewhere.
Using a model-level harness to decide whether to ship an application change
A checkpoint's GSM8K score says little about your prompt, retrieval and tools. Run the harness for general capability and app-level golden sets for the product ({{Production eval engineering|n:3c65c17b0d0d81b39ad9e96193d21adc}}).
