8. Each harness, in depth

Optional: architecture, gotchas and contribution paths, one block per harness.

lm-evaluation-harness (EleutherAI): task YAML, model registry, gotchas

The reproducibility standard for base-model benchmarking and the default behind "numbers in a model card". It was the backend of Hugging Face's Open LLM Leaderboard v1 and v2, and its README still describes it as the leaderboard's backend; the leaderboard Space was archived on 13 March 2025 ({{README|https://github.com/EleutherAI/lm-evaluation-harness/blob/d6de81643928d653435c431bae19945d41d32520/README.md}}).

  • Architecture. A TaskManager discovers task YAML files and builds ConfigurableTask objects; a registry maps model names to LM subclasses. The registry holds 37 model names, aliases included (hf, vllm, sglang, openai-completions, anthropic, litellm, mamba, gguf, nemo, neuron, IPEX, ONNX, TensorRT-LLM, watsonx and more; {{lm_eval/models|https://github.com/EleutherAI/lm-evaluation-harness/tree/d6de81643928d653435c431bae19945d41d32520/lm_eval/models}}). Implement the three request methods and any backend runs every task.
  • Task YAML. Declares the dataset (a Hub path), doc_to_text and doc_to_target (Jinja templates, or Python through !function), output_type, metrics, generation settings and filter chains (regex extraction, take-first, majority voting for self-consistency). Variants (shot counts, chain-of-thought versions, translations) are YAML overrides through include:; groups and tags aggregate tasks (mmlu is a group of 57 subtasks). The tasks folder has 221 benchmark directories and about 14,000 YAML files at commit d6de816; the README says "over 60 standard academic benchmarks, with hundreds of subtasks and variants".
  • Gotchas. trust_remote_code runs dataset code; YAML quoting bites (until: ['\n'] in single quotes is a backslash and an n, not a newline: the project's {{footguns.md|https://github.com/EleutherAI/lm-evaluation-harness/blob/d6de81643928d653435c431bae19945d41d32520/docs/footguns.md}}). Always log the task's version: GSM8K is at version 3.0.
  • Contributing: still genuinely open. Port or add a task in YAML ({{new task guide|https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/new_task_guide.md}}; its checklist asks whether you checked against the paper's reference implementation and documented how), fix answer-extraction filters for reasoning models, or add a backend. Maintainers keep "good first issue" and "help wanted" items ({{CONTRIBUTING|https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/CONTRIBUTING.md}}).
Inspect (UK AI Security Institute): solvers, scorers, models, and the 2026 change to inspect_evals

The frontier-safety and agentic standard: used by AI security institutes, METR, Apollo Research and labs for pre-deployment testing.

  • Abstractions. Solvers compose into chains: system_message(), prompt_template(), generate(), chain_of_thought(), self_critique(), multiple_choice(), use_tools(), or a whole agent such as react() (the older basic_agent() still ships). Scorers: exact(), match(), includes(), pattern(), choice(), answer(), math(), model_graded_qa(), model_graded_fact(), the perplexity scorers, or custom Python, including batteries of judges. Metrics: accuracy, stderr, bootstrap_stderr, ci_wilson, even krippendorff_alpha ({{scorer exports|https://github.com/UKGovernmentBEIS/inspect_ai/blob/9f6accda8dce5ccd754e6be1a22fbcee96042e82/src/inspect_ai/scorer/__init__.py}}).
  • Tooling. inspect view and the VS Code extension render every model call, tool call, state change and score from the log: the best debugging experience of any harness, and the .eval format is stable enough for other tools to consume.
  • Models. All major APIs and local engines (vLLM, SGLang, Hugging Face transformers, Ollama, llama-cpp-python, even TransformerLens and nnterp for interpretability work; {{providers|https://inspect.aisi.org.uk/providers.html}}); --model switches provider without touching the task.
  • inspect_evals is the community collection: "120+ evaluation implementations and 200+ Inspect AI tasks" by its own count.
Correction: inspect_evals no longer takes new eval code
The old version of this page called inspect_evals "the designed on-ramp": pick a published benchmark, propose it in an issue, ship it with an end-to-end test and a parity check, start with question-answering before agentic tasks. Since 8 May 2026 "new evaluations must be hosted in an upstream repo and registered to Inspect Evals via a simple .yaml file" ({{EVAL_REGISTER.md|https://github.com/UKGovernmentBEIS/inspect_evals/blob/0dacad3c3bacfb50308de94eb8b8f9e368cfe30c/EVAL_REGISTER.md}}); the Register lists each eval at a pinned commit of its author's repository, which must be installable, depend on inspect_ai and define tasks with @task ({{register guide|https://github.com/UKGovernmentBEIS/inspect_evals/blob/0dacad3c3bacfb50308de94eb8b8f9e368cfe30c/register/README.md}}). Pull requests to the collection now come only from pre-approved contributors; anyone else raises an issue and uploads .eval logs that show the problem (tightened on 2 October 2026). The priority flipped too: the guide now prefers "agentic or task-based over simple Q&A", credibly sourced, with a frontier-model baseline to validate against ({{CONTRIBUTING|https://github.com/UKGovernmentBEIS/inspect_evals/blob/0dacad3c3bacfb50308de94eb8b8f9e368cfe30c/CONTRIBUTING.md}}).

The practical path today: implement the eval in your own repository from the {{Generality Labs template|https://github.com/Generality-Labs/inspect-evals-template}}, test it against a published baseline to the bar in its {{docs/methodology.md|https://github.com/UKGovernmentBEIS/inspect_evals/blob/0dacad3c3bacfb50308de94eb8b8f9e368cfe30c/docs/methodology.md}} and {{BEST_PRACTICES.md|https://github.com/UKGovernmentBEIS/inspect_evals/blob/0dacad3c3bacfb50308de94eb8b8f9e368cfe30c/BEST_PRACTICES.md}}, register it, and report bugs in existing evals with logs. Model-graded scorers and judge-reliability tooling fit Khalid's judge-battery background, now as a registered upstream eval or a scorer contribution. inspect_ai itself, the framework, has a high bar.

lighteval (Hugging Face): now on Inspect

Harness-inspired and Hugging Face-native: 1000+ tasks by its README, backends for transformers and accelerate, vLLM, SGLang, TGI, Inference Endpoints, Inference Providers, LiteLLM and nanotron (evaluation during pretraining), results and per-sample details pushed to the Hub, quick custom tasks in Python, wide multilingual coverage; it powers Hugging Face's leaderboards. Its README lists lighteval eval, "using inspect-ai as a backend", as the preferred entry point ({{README|https://github.com/huggingface/lighteval/blob/c2af9e5f2fde494539f84c8ea9d09f18ac9e9c14/README.md}}); its GSM8K task carries an Inspect sample converter, solver chain and scorer next to the classic prompt function, with the same prompt text as inspect_evals' GSM8K ({{gsm8k.py|https://github.com/huggingface/lighteval/blob/c2af9e5f2fde494539f84c8ea9d09f18ac9e9c14/src/lighteval/tasks/tasks/gsm8k.py}}). Its docs warn that "not all tasks are compatible with inspect-ai's API as of yet". The last PyPI release (0.13.0, 24 November 2025) lags main: install from source and pin the commit.

Choose it when you live in the Hugging Face stack or need evaluation inside a nanotron or FSDP training loop; it is weaker than lm-eval on community-verified task parity and, outside its Inspect path, weaker than Inspect on agents. Contributing: custom tasks and metrics in Python ({{adding a custom task|https://huggingface.co/docs/lighteval/adding-a-custom-task}}), multilingual tasks, converting tasks to its Inspect path.

HELM (Stanford CRFM): the multi-metric reference, in maintenance mode

Each scenario scored on accuracy, calibration, robustness, fairness, bias, toxicity and efficiency ({{Liang et al. 2022|https://arxiv.org/abs/2211.09110}}), with every prompt and response dumped per instance and browsable in a web UI. It spawned domain leaderboards: VHELM, HEIM, MedHELM, audio, enterprise and more ({{README|https://github.com/stanford-crfm/helm/blob/63754d05db6f874e41a395880fb573890a13e791/README.md}}). A run is a RunSpec: a scenario, an adapter spec (instructions, input and output nouns, shots, max tokens, stop sequences) and metric specs. HELM's GSM8K is "Q: ... A:" with 5 training examples, 400 tokens, stop at a blank line ({{run spec|https://github.com/stanford-crfm/helm/blob/63754d05db6f874e41a395880fb573890a13e791/src/helm/benchmark/run_specs/lite_run_specs.py#L137-L158}}).

Maintenance mode since 1 June 2026 (verified). The README says "HELM entered maintenance mode on June 1, 2026", and the {{Maintenance Mode Policy|https://crfm-helm.readthedocs.io/en/latest/maintenance_mode/}} says volunteers maintain it on a best-effort basis, "no new features will be added to HELM, and no new evaluations will be added to the HELM leaderboards", and scenarios may break as provider APIs change. Read it for methodology (its "coverage beats a headline score" stance predated the field by two years); do not build new pipelines on it. The policy names Evalchemy, Inspect Evals, lighteval, lm-eval-harness and Unitxt as alternatives. Contributions: notable models, notable scenarios, API-client fixes and significant bug fixes only; open an issue first, because pull requests without one are closed.

OpenAI's evals and simple-evals; Evalchemy; Unitxt
  • {{openai/evals|https://github.com/openai/evals}} (2023) is a registry: a YAML names an eval template (Match, Includes, FuzzyMatch, model-graded) and points at JSONL samples kept in Git LFS. Match passes when the output starts with the ideal answer ({{evals/api.py|https://github.com/openai/evals/blob/8eac7a7de5215c907fbddc30efdaf316913eccdd/evals/api.py#L79-L104}}). The README now points to Evals in the OpenAI dashboard and says "we are currently not accepting evals with custom code"; it accepts only template-based or model-graded YAML evals.
  • {{openai/simple-evals|https://github.com/openai/simple-evals}} (2024) published how OpenAI produced its launch numbers: zero-shot chain-of-thought with simple instructions. Its July 2025 notice says it "will no longer be updated for new models or benchmark results" ({{README|https://github.com/openai/simple-evals/blob/652c89d0ca9df547706735883097e9537d40dc47/README.md}}); it accepts only bug fixes, model adapters and new result rows.
  • Evalchemy (DataComp and Bespoke Labs) "builds on the LM-Eval-Harness" for post-trained models: one install for reasoning, code and chat benchmarks (AIME, MATH500, LiveCodeBench, GPQA Diamond, MT-Bench, AlpacaEval, WildBench and others), API models through Curator. A benchmark is a Python class with generate_responses and evaluate_responses. Its MATH500 sets "do_sample": False and "temperature": 0.7 in the same request ({{eval_instruct.py|https://github.com/mlfoundations/evalchemy/blob/6ed674159b37f740f2353a86f596f49f6ac13c19/eval/chat_benchmarks/MATH500/eval_instruct.py#L78-L92}}): which wins depends on the backend, so log what was actually sent.
  • Unitxt (IBM) treats prompt variation as first-class: a card (loader, preprocessing steps, task) is combined at run time with a template, a format (for example chat API) and a number of demos, and a card can list many templates ({{MMLU card|https://github.com/IBM/unitxt/blob/74b8bb6330fed5e1a78ae0c35c1e2c1c126db7f6/src/unitxt/catalog/cards/mmlu/abstract_algebra.json}}). Its catalog badge counts 68 tasks, 3,254 datasets, 357 prompts and 584 metrics. It plugs into others: lm-eval ships tasks/unitxt and HELM a unitxt_scenario.
App-level tools: promptfoo and Braintrust
  • {{promptfoo|https://github.com/promptfoo/promptfoo}}: open source (MIT), command line and YAML first, local first. A promptfooconfig.yaml declares a matrix: prompts x providers x test cases, each with assertions ({{getting-started example|https://github.com/promptfoo/promptfoo/blob/5fde786d0c296339be3fd189d1542157e1d4217a/examples/getting-started/promptfooconfig.yaml}}). At commit 5fde786 its docs list 44 deterministic assertion types (from equals, contains and regex to is-json, latency, cost, tool-call F1 and trajectory checks such as trajectory:tool-sequence) and 17 model-assisted ones (llm-rubric, g-eval, factuality, context-faithfulness, trajectory:goal-success and others) ({{assertions|https://github.com/promptfoo/promptfoo/blob/5fde786d0c296339be3fd189d1542157e1d4217a/site/docs/configuration/expected-outputs/index.md}}). A diff view, CI integration and a red-teaming and vulnerability-scanning mode. On 9 March 2026 Promptfoo announced it "has agreed to be acquired by OpenAI" and "will remain open source" ({{announcement|https://www.promptfoo.dev/blog/promptfoo-joining-openai/}}). Choose it for repository-local prompt regression tests and multi-model comparisons with the fastest setup. Contributing: an ordinary open-source project (providers, assertions, red-team plugins), now with OpenAI as owner.
  • {{Braintrust|https://www.braintrust.dev/docs/evaluate}}: a commercial platform. Every evaluation has three parts, data, task and scorers: Eval("My project", data=init_dataset(...), task=..., scores=[Factuality]), run with bt eval ({{run in code|https://braintrust.dev/docs/evaluate/run-in-code}}). Playground runs overwrite themselves; experiments are immutable snapshots for comparison and CI gates; datasets are versioned so experiments can pin a version; scorers come from its open-source {{autoevals|https://github.com/braintrustdata/autoevals}} library, code or LLM judges; online scoring rules grade production traces asynchronously, which, with no ground truth on live traffic, means judge scorers ({{online scoring|https://braintrust.dev/docs/evaluate/score-online}}). Human review is built in. Choose it when you want the loop from offline evaluation to production observability in one place and are willing to pay for it.
  • Same niche, named without a review: {{Langfuse|https://github.com/langfuse/langfuse}}, {{Arize Phoenix|https://github.com/Arize-ai/phoenix}} and {{W&B Weave|https://github.com/wandb/weave}}. Tracing itself is {{LLM observability|n:3c65c17b0d0d81fe82c0c6e9360afec4}}; judges used as scorers are {{LLM-as-judge|n:3c65c17b0d0d810ba2a2ecc08c4c233b}}.
Mistakes that cost real numbers
  • Comparing two harnesses' scores because the benchmark has the same name. On GSM8K alone the six rules above disagree on what counts as an answer; compare within one harness, one version, one config.
  • Trusting the default decoding. Inspect's local provider samples unless told not to; Evalchemy's MATH500 sends both do_sample: False and temperature: 0.7. Set decoding explicitly and check what reached the model in the log.
  • Believing a sudden drop before reading the failures. In this page's own lm-eval run, strict-match scored 0 of 10 and flexible-extract 1 of 10 on identical outputs.
  • Running model-written code without a sandbox. Use Docker or a VM-backed sandbox for anything agentic.
  • Building a new pipeline on HELM or simple-evals. Both are frozen for new work; read them for method.
  • Using a model-level harness to decide whether to ship an application change. A checkpoint's GSM8K score says little about your prompt, retrieval and tools.
