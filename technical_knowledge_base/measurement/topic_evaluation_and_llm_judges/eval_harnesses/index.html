Every harness does the same three things: load items, get the model to respond, turn the response into a number. They differ in what they treat as the unit of work, and that one choice decides what they can score, what they log, whether they can run an agent safely, and how easy it is to reproduce someone else's number.

The parent page, Topic: evaluation-and-llm-judges, explains why an eval is a measuring instrument and shows, in its tab Same model, many harnesses, how far one model's score moves when only the harness changes (a 200-item reproduction on Qwen2.5-0.5B and published cases such as LLaMA-65B on MMLU). This page does not repeat that; it explains the harnesses themselves.

Two units of work: a request, or a program

lm-eval-harness turns a task into a list of requests. A YAML file says how to render each document into text, the harness builds every request up front (context plus what to compute: a log-probability or a generation with stop strings), sends them in batches to a backend that only knows three methods, and then runs filters and metrics over the responses. Nothing happens per sample that the YAML did not declare. That is why it is reproducible and why it scales to hundreds of fixed tasks.

Inspect turns a task into a program run once per sample. A Sample becomes a TaskState; a chain of solvers transforms it (add a system message, fill a template, call the model, call a tool, critique, loop as an agent); a scorer grades the final state; every step is recorded as an event. That is why it can express agents, sandboxes and judge batteries, and why its logs are complete.

The same GSM8K problem through both

Real runs by this page: Qwen2.5-0.5B-Instruct (fp32, CPU, 2 threads) on the first ten GSM8K test problems, under lm-eval 0.4.13's gsm8k task as shipped and under inspect_evals 0.23.0's gsm8k on inspect-ai 0.3.276, with greedy decoding in both (Inspect needed do_sample=False, see below) and Inspect capped at 512 new tokens instead of its 2048 default to bound CPU time. How each scores: three decisions inside every number

Whatever the harness, a score is the product of three decisions: how the answer is read (probabilities or generated text), how a generated answer is extracted, and how the prompt is wrapped (raw text or the model's chat template). The parent page's tab Same model, many harnesses measures how much each one moves a score; here is where each harness makes them.

1. Probabilities or text

lm-eval-harness has four request types (lm_eval/api/instance.py), and a backend only has to implement three methods to run all of them (model guide):

  • loglikelihood(context, continuation): the log-probability of a given continuation and whether it is the greedy one. A multiple_choice task asks it once per option and picks the largest. No sampling, deterministic, cheap, works on base models; it measures how the model ranks given options, never whether it can produce an answer, and it needs log-probabilities of the prompt, which most chat APIs do not return.
  • loglikelihood_rolling(text): the log-probability of a whole text, for perplexity and bits-per-byte.
  • generate_until(context, until=[...]): generate until a stop string, then post-process with filters. This is what chat and reasoning models need, and every extraction rule becomes part of the score.
Length normalisation, exactly
For multiple_choice tasks lm-eval reports acc (argmax of the summed log-probabilities), acc_norm (argmax of the sum divided by the option's length in characters), and, when asked, acc_bytes (divided by its UTF-8 byte length) and acc_mutual_info (task.py lines 1494 to 1560). The old version of this page called acc_norm byte-length normalised; it is character-length, which is the same for ASCII options and different for most other scripts.

The other harnesses lean generative. HELM has both generation and multiple-choice adapters; Inspect, simple-evals, promptfoo and Braintrust score generated text. Inspect added perplexity() and target_perplexity() scorers in 0.3.212 (24 April 2026; changelog); the docs describe target_perplexity() as the counterpart of lm-eval's loglikelihood pattern, and it needs prompt log-probabilities, which only its vLLM and SageMaker providers supply (Inspect: Perplexity).

The field has been moving multiple-choice benchmarks from loglikelihood to generated chain-of-thought formats; Hugging Face's Open LLM Leaderboard v2, run on lm-eval, mixed both: four of its six tasks (BBH, GPQA, MMLU-Pro, MuSR) are multiple_choice and two (IFEval, MATH Level 5) are generate_until (tasks/leaderboard). Scores under the two formats are different measurements even when the benchmark has the same name: never compare across them.

2. Extraction

A generative task is only as good as the code that finds the answer in the text. On GSM8K, the same benchmark in each harness uses a different rule (the tab One task, every harness runs all of them on real outputs):

HarnessRule for the GSM8K answer
lm-eval gsm8kTwo filters reported side by side: strict-match needs #### <number> (the training-set format the 5 shots teach); flexible-extract takes the last number-like string. Then exact_match after removing commas, $ and a trailing period
inspect_evals gsm8kThe prompt asks for ANSWER: $ANSWER, but the scorer match(numeric=True) ignores that line: it takes the last number in the whole output and compares numerically, formatted to 5 significant digits (.5g): for the 18 of 1,319 test answers above 99,999, a prediction of 114,201 matches a gold of 114,200
lighteval gsm8kParses expressions and LaTeX (a boxed answer first) from the output and the gold, then compares the parsed values
HELM gsmfinal_number_exact_match: the last match of -?[\d,]+(?:.\d+)? in output and gold. The dot is unescaped, so it matches any character: "3 4" is read as one number
simple-evals MGSM (English)Text after the last "Answer", then the last number in it (the code comment says "the first number"; the code returns the last). The match on "Answer" is case-sensitive, so an "ANSWER:" line, the format inspect_evals asks for, is never found
OpenAI evals MatchThe output must start with the ideal answer string

Extraction failures score as wrong answers, silently. They are the usual cause of "model X dropped 20 points": a new model writes **72** or \boxed{72} or "The answer is: 72 dollars" and the old regex misses it. When a score moves, read ten failures before believing it.

3. Chat template

Instruction-tuned models were trained on their own chat format; sending them raw text is a different test. Each harness has a default:

  • lm-eval sends raw text unless asked. --apply_chat_template wraps prompts in the tokenizer's template, --fewshot_as_multiturn (on by default with it) turns the shots into alternating turns, and --system_instruction adds a system prompt (interface.md). The results file records a hash of the chat template and of the system instruction.
  • Inspect sends messages; its Hugging Face provider applies the tokenizer's chat template unless use_chat_template=False. inspect_evals' GSM8K puts its ten shots in one system message.
  • simple-evals and the app-level tools always send chat messages; HELM builds a text prompt and the model client decides how to send it.
A default worth knowing: Inspect's local Hugging Face provider samples
Inspect's hf provider sets do_sample=True unless the model argument do_sample=False is passed (hf.py line 118), so a local run uses the model's own sampling settings (Qwen2.5-0.5B-Instruct's generation config samples at temperature 0.7, top-p 0.8, top-k 20, repetition penalty 1.1). Passing --temperature 0 instead raises an error in transformers 5.18, which this page hit. lm-eval's GSM8K task sets do_sample: false, temperature: 0.0 in the YAML. Greedy against sampled is a knob in its own right.

Each harness, one by one

lm-evaluation-harness (EleutherAI)

The reproducibility standard for base-model benchmarking and the default behind "numbers in a model card". It was the backend of Hugging Face's Open LLM Leaderboard v1 and v2; the leaderboard Space was archived on 13 March 2025 (parent page, tab Same model, many harnesses), although the harness README still calls it "the backend for 🤗 Hugging Face's popular Open LLM Leaderboard" (README).

  • Architecture. A TaskManager discovers task YAML files and builds ConfigurableTask objects; a registry maps model names to LM subclasses. The registry holds 37 model names, aliases included (hf, vllm, sglang, openai-completions, anthropic, litellm, mamba, gguf, nemo, neuron, IPEX, ONNX, TensorRT-LLM, watsonx and more; lm_eval/models). Implement the three request methods and any backend runs every task; requests are batched, cached (--use_cache, --cache_requests) and distributed.
  • Task YAML. Declares the dataset (a Hugging Face Hub path), doc_to_text and doc_to_target (Jinja templates, or Python through !function), output_type, metrics, generation settings and filter chains (regex extraction, take-first, majority voting for self-consistency). Variants (shot counts, chain-of-thought versions, translations) are YAML overrides through include:; groups and tags aggregate tasks (mmlu is a group of 57 subtasks). The tasks folder has 221 benchmark directories and about 14,000 YAML files at commit d6de816; the README says "over 60 standard academic benchmarks, with hundreds of subtasks and variants".
  • Gotchas. Few-shot formatting and --apply_chat_template change scores materially; trust_remote_code runs dataset code; results depend on filter chains as much as on the model; YAML quoting bites (until: ['\n'] in single quotes is a backslash and an n, not a newline: the project's footguns.md). Always log the task's version from its metadata: GSM8K is at version 3.0.

Inspect (UK AI Security Institute)

The frontier-safety and agentic standard: used by AI security institutes, METR, Apollo Research and labs for pre-deployment testing. Where lm-eval models "prompt in, string out", Inspect models an eval as a program.

  • Abstractions. A Task is a dataset, a solver and a scorer. A solver transforms a TaskState (messages, output, a per-sample store); solvers compose into chains: system_message(), prompt_template(), generate(), chain_of_thought(), self_critique(), multiple_choice(), use_tools(), or a whole agent such as react() (the older basic_agent() still ships). A scorer grades the final state: exact(), match(), includes(), pattern(), choice(), answer(), math(), model_graded_qa(), model_graded_fact(), the perplexity scorers, or custom Python, including batteries of judges. Metrics aggregate scores (accuracy, stderr, bootstrap_stderr, ci_wilson, even krippendorff_alpha); Epochs reruns each sample and reduces with mean, median, mode, max, at_least_k or pass_at_k (scorer exports).
  • Sandboxing: below, in Sandboxes for agentic evals. It is the feature that made Inspect the agentic default.
  • Tooling. inspect view and the VS Code extension render every model call, tool call, state change and score from the log: the best debugging experience of any harness, and the .eval format is stable enough for other tools to consume. The tab Inside a run log walks a real one.
  • Models. All major APIs and local engines (vLLM, SGLang, Hugging Face transformers, Ollama, llama-cpp-python, and even TransformerLens and nnterp for interpretability work; providers); --model switches provider without touching the task.
  • inspect_evals is the community collection: "120+ evaluation implementations and 200+ Inspect AI tasks" by its own count (EVAL_REGISTER.md). Since 8 May 2026 it takes no new eval code: new evals live in their authors' repositories and are listed in a Register at a pinned commit (see Contributing).

lighteval (Hugging Face)

Harness-inspired and Hugging Face-native: 1000+ tasks by its README, backends for transformers and accelerate, vLLM, SGLang, TGI, Inference Endpoints, Inference Providers, LiteLLM and nanotron (evaluation during pretraining), tight Hub integration (results and per-sample details pushed to the Hub), quick custom tasks in Python, wide multilingual coverage; it powers Hugging Face's leaderboards.

What changed: lighteval now runs on Inspect
Its README lists lighteval eval, "using inspect-ai as a backend", as the preferred entry point (README); its GSM8K task carries an Inspect sample converter, a solver chain and a scorer next to the classic prompt function, with the same prompt text as inspect_evals' GSM8K (gsm8k.py). Its docs warn that "not all tasks are compatible with inspect-ai's API as of yet". The last PyPI release is 0.13.0 (24 November 2025) while main kept moving (30 September 2026): install from source for current behaviour, and pin the commit.

Choose it when you live in the Hugging Face stack or need evaluation inside a nanotron or FSDP training loop. It is weaker than lm-eval on community-verified task parity and, outside its Inspect path, weaker than Inspect on agents.

HELM (Stanford CRFM)

The multi-metric methodology reference: each scenario scored on accuracy, calibration, robustness, fairness, bias, toxicity and efficiency (Liang et al. 2022), with every prompt and response dumped per instance and browsable in a web UI. It spawned domain leaderboards: VHELM, HEIM, MedHELM, audio, enterprise and more (README).

A run is a RunSpec: a scenario (how to load instances), an adapter spec (instructions, input and output nouns, shots, max tokens, stop sequences) and metric specs. HELM's GSM8K is "Q: ... A:" with 5 training examples whose answers have "####" replaced by "The answer is", 400 tokens, stop at a blank line (run spec).

Maintenance mode since 1 June 2026 (verified)
The README says "HELM entered maintenance mode on June 1, 2026", and the Maintenance Mode Policy says volunteers maintain it on a best-effort basis, "no new features will be added to HELM, and no new evaluations will be added to the HELM leaderboards", and scenarios may break as provider APIs change. The last commit on main is 5 June 2026. Read it for methodology (its "coverage beats a headline score" stance predated the field by two years); do not build new pipelines on it. The policy names Evalchemy, Inspect Evals, lighteval, lm-eval-harness and Unitxt as alternatives.

OpenAI's two: evals and simple-evals

  • openai/evals (2023) is a registry: a YAML names an eval template (Match, Includes, FuzzyMatch, model-graded) and points at JSONL samples kept in Git LFS. Match passes when the output starts with the ideal answer (evals/api.py), which a chain-of-thought answer never does. The README now points to Evals in the OpenAI dashboard, says "we are currently not accepting evals with custom code", and the last PyPI release is 3.0.1.post1 (1 May 2024).
  • openai/simple-evals (2024) published how OpenAI produced its launch numbers: zero-shot chain-of-thought with simple instructions, because few-shot and role-play prompts are "carryovers from evaluating base models". Its July 2025 notice says it "will no longer be updated for new models or benchmark results"; it continues to host the reference implementations of HealthBench, BrowseComp and SimpleQA (README).

Evalchemy and Unitxt

  • Evalchemy (DataComp and Bespoke Labs) "builds on the LM-Eval-Harness" for post-trained models: one install for reasoning, code and chat benchmarks (AIME, MATH500, LiveCodeBench, GPQA Diamond, MT-Bench, AlpacaEval, WildBench and others), API models through Curator. A benchmark is a Python class with generate_responses and evaluate_responses on lm-eval's LM and Instance. Its MATH500 sets "do_sample": False and "temperature": 0.7 in the same request (eval_instruct.py): which one wins depends on the backend, so log what was actually sent. Last commit 23 December 2025.
  • Unitxt (IBM) treats prompt variation as first-class: a card (loader, preprocessing steps, task) is combined at run time with a template, a format (for example chat API) and a number of demos, and a card can list many templates (MMLU card). Its catalog badge counts 68 tasks, 3,254 datasets, 357 prompts and 584 metrics. It plugs into others: lm-eval ships tasks/unitxt and HELM a unitxt_scenario.

App-level tools: promptfoo and Braintrust

A different job: evaluating your application (prompt, model, retrieval, tools and code together) on your own cases, not a model on public tasks.

  • promptfoo: open source (MIT), command line and YAML first, local first. A promptfooconfig.yaml declares a matrix: prompts x providers x test cases, each test with assertions (getting-started example). At commit 5fde786 its docs list 44 deterministic assertion types (from equals, contains and regex to is-json, latency, cost, tool-call F1 and trajectory checks such as trajectory:tool-sequence) and 17 model-assisted ones (llm-rubric, g-eval, factuality, context-faithfulness, trajectory:goal-success and others) (assertions). It has a diff view, CI integration and a serious red-teaming and vulnerability-scanning mode. On 9 March 2026 Promptfoo announced it "has agreed to be acquired by OpenAI" and "will remain open source"; the README now says it "is now part of OpenAI" and remains MIT licensed (announcement). Choose it for repository-local prompt regression tests and multi-model comparisons with the fastest setup.
  • Braintrust: a commercial platform. Every evaluation has three parts, data, task and scorers: Eval("My project", data=init_dataset(...), task=..., scores=[Factuality]), run with bt eval (run in code). Playground runs overwrite themselves; experiments are immutable snapshots meant for comparison and CI gates; datasets are versioned so experiments can pin a version; scorers come from its open-source autoevals library, code or LLM judges; online scoring rules grade production traces asynchronously, which, with no ground truth on live traffic, means judge scorers (online scoring). Human review is built in. Choose it when you want the loop from offline evaluation to production observability in one place and are willing to pay for it.

Alternatives in the same niche, named here without a review: Langfuse, Arize Phoenix and W&B Weave. Observability of agent systems belongs to Topic: agentic-frameworks; how to build gates, golden sets and promotion paths with any of these tools belongs to Production eval engineering.

The boundary rule
Model-level harnesses answer "is this checkpoint good?"; app-level tools answer "is this system change safe to ship?". Khalid's regression-gate work is the second kind even when the trigger is a model swap. The pattern that works: a harness for the swap candidate's general capabilities, app-level golden sets for the product surface.

Reproducibility and logging

A score is reproducible only if every input to it is pinned and every output is kept. The harnesses differ most in the second.

What the logs are for: when a number moves, the first three suspects are a genuine capability change, a broken extraction filter, and a truncated completion. Only per-sample logs separate them. The tab Inside a run log shows both formats from real runs.

  • Seeds and sampling. Greedy decoding is not the default everywhere (Inspect's local Hugging Face provider samples, above). With sampling, run several epochs and report the spread; see Eval statistics for how many items and repeats a difference needs.
  • Token counts can be the batch's. Inspect's local Hugging Face provider records each sample's usage as the padded batch shape: in this page's run every one of the ten samples logged 2,269 input and 494 output tokens, while the real prompts were 2,184 to 2,269 tokens and the outputs 146 to 493 (hf.py lines 651 to 652; counts in src/data/runs.json). Its stop reason was logged as "unknown". API providers report real usage; for a local model, count tokens yourself before using the log to spot truncation.
  • Serving. The same weights behind different providers or precisions are different instruments; lighteval's own example compares one model across three Inference Providers for this reason.
  • Caching makes reruns cheap and can also replay a stale answer: lm-eval's --use_cache is keyed by model and task, and Inspect's generate(cache=True) by the model, its settings and the messages.

Sandboxes for agentic evals

An agent eval lets model-written code and commands run. Inspect makes that a first-class part of the task: tools such as bash(), python() and text_editor() require a sandbox, each sample can get its own, and the environment is declared next to the task as a Dockerfile or compose.yaml (Sandboxing). Nothing else here compares. lm-eval runs code tasks such as HumanEval on the host, gated by unsafe_code: true in the task and --confirm_run_unsafe_code on the command line; HELM, simple-evals and openai/evals have no sandbox layer; Braintrust connects agent code to its playground through "remote evals or sandboxes" (docs); promptfoo grades agent trajectories but does not isolate them. How to grade what an agent did, rather than its last message, is Agent and trajectory evaluation; public agentic benchmarks (pass^k, METR horizons, Terminal-Bench exploits) are on Topic: benchmarks' Agentic page.

The opposite trade: a harness inside an enclave
Google DeepMind's August 2026 double-blind pilot ran a proprietary model and private items inside a confidential-computing enclave so neither side saw the other's secret; its cost is the thing Inspect's log viewer exists for: no one can read the transcripts, so a bad score cannot be attributed to capability, a broken extraction filter or a truncated completion. Details and caveats: Topic: benchmarks (Reading, "What a number leaves out").

Contributing: where the entry points are now

  • lm-evaluation-harness: still genuinely open. Port or add a task in YAML (new task guide; its checklist asks whether you checked against the paper's reference implementation and documented how), fix answer-extraction filters for reasoning models, or add a backend (model guide). Maintainers keep a list of "good first issue" and "help wanted" items (CONTRIBUTING).
  • Inspect: two repositories with very different bars. inspect_ai is the framework (a high bar). inspect_evals changed its model in 2026:
    Correction: inspect_evals no longer takes new eval code
    The old version of this page called inspect_evals "the designed on-ramp": pick a published benchmark, propose it in an issue, ship it with an end-to-end test and a parity check, start with question-answering before agentic tasks. Since 8 May 2026 "new evaluations must be hosted in an upstream repo and registered to Inspect Evals via a simple .yaml file" (EVAL_REGISTER.md); the Register lists each eval at a pinned commit of its author's repository, which must be installable, depend on inspect_ai and define tasks with @task (register guide). Pull requests to the collection now come only from pre-approved contributors; anyone else raises an issue and uploads .eval logs that show the problem (the rule was tightened on 2 October 2026). And the priority flipped: the guide now prefers "agentic or task-based over simple Q&A", credibly sourced, with a frontier-model baseline to validate against (CONTRIBUTING).
    The practical path today: implement the eval in your own repository from the Generality Labs template, test it against a published baseline to the bar in its docs/methodology.md and BEST_PRACTICES.md, register it, and report bugs in existing evals with logs. Given Khalid's judge-battery background, model-graded scorers and judge-reliability tooling are a natural niche, now as a registered upstream eval or a scorer contribution rather than a pull request to the collection.
  • lighteval: custom tasks and metrics in Python (adding a custom task), multilingual task contributions, and converting tasks to its Inspect path.
  • HELM: notable models, notable scenarios, API-client fixes and significant bug fixes only; open an issue first and wait for triage, because pull requests without one are closed (Maintenance Mode Policy).
  • OpenAI: simple-evals accepts only bug fixes, model adapters and new result rows; openai/evals accepts no custom-code evals, only template-based or model-graded YAML ones.
  • promptfoo: an ordinary open-source project (providers, assertions, red-team plugins), now with OpenAI as owner.

Common mistakes

Comparing scores from two harnesses because the benchmark has the same name
Prompt, shots, scoring method, extraction and chat template all differ by default; on GSM8K alone the six rules above disagree on what counts as an answer. Compare within one harness, one version, one config.
Reporting a number without the harness version, task version and settings
Give harness and commit, task version, shots, chat template on or off, decoding (greedy or sampled, with seed), max tokens, and the extraction filter. lm-eval writes most of this into its results file; Inspect into its log header; copy it into the report.
Trusting the default decoding
Inspect's local Hugging Face provider samples unless told not to; Evalchemy's MATH500 sends both do_sample: False and temperature: 0.7. Set decoding explicitly and check what reached the model in the log.
Believing a sudden drop before reading the failures
A new output format (**72**, \boxed{72}, "ANSWER: 72") or a truncated completion scores as a wrong answer. In this page's own lm-eval run, strict-match scored 0 of 10 and flexible-extract 1 of 10 on identical outputs; Inspect's scorer reads yet another way (tab Inside a run log).
Running a model-written-code task without a sandbox
lm-eval's --confirm_run_unsafe_code and Inspect's local sandbox both run model code as you on your machine. Use Docker or a VM-backed sandbox for anything agentic.
Building a new pipeline on HELM or simple-evals
Both are frozen for new work (HELM since 1 June 2026, simple-evals since July 2025). Read them for method; run current evals elsewhere.
Using a model-level harness to decide whether to ship an application change
A checkpoint's GSM8K score says little about your prompt, retrieval and tools. Run the harness for general capability and app-level golden sets for the product (Production eval engineering).

Extraction bench: seven rules, the same real outputs

Twenty real outputs: Qwen2.5-0.5B-Instruct on the first ten GSM8K test problems, once through lm-eval's gsm8k (raw 5-shot prompt) and once through inspect_evals' gsm8k (chat template, 10 shots in a system message), both run by this page on 4 October 2026 (tab Inside a run log). Each output is then scored by every harness's extraction rule, using the harness's own code where it installs (lm-eval, Inspect, lighteval) and a verbatim copy of the function where it does not (HELM, simple-evals, openai/evals), in src/compute_extract.py.

What this is not
A score. Ten items from a 0.5-billion-parameter model cannot rank harnesses or models (the exact Clopper-Pearson 95% interval for 1 correct out of 10 runs from 0.3% to 44.5%); the point is that the same text gets different verdicts. Sample sizes are on Eval statistics.
