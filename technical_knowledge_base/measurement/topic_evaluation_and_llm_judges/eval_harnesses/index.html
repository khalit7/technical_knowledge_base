The idea in one sentence. A benchmark score is the output of a chain of harness decisions (prompt template, few-shot examples, chat template, reading the answer by log-likelihood or by generation, answer extraction, normalisation), every harness makes them differently by default, and changing one link moves the same weights on the same questions by tens of points.

Every number on this chain was measured on one model with one link changed. Qwen2.5-0.5B-Instruct on 200 MMLU test items, ten harness settings (section 3, Why scores differ); the GSM8K line is this page's own lm-eval run, two filters on identical outputs. The one figure not from that model: LLaMA-65B, 63.6 under the original MMLU code against 48.8 under lm-eval-harness as of January 2023 (Hugging Face, 23 June 2023).

New terms

  • Harness: the program that turns a benchmark into a number (not the agent "harness" that runs a model in a loop, which is Topic: agentic-harnesses).
  • Shots: solved examples placed in the prompt before the question.
  • Log-likelihood scoring: compare the model's probabilities of given answers; generative scoring: let it write, then parse.
  • Extraction (lm-eval: filter): the code that finds the answer in generated text.
  • Solver and scorer (Inspect): a step that changes the sample's state; the function that grades the final state.
  • acc_norm: log-likelihood divided by the answer's length in characters.

The boundary rule
Model-level harnesses answer "is this checkpoint good?"; app-level tools answer "is this system change safe to ship?". A regression gate on a model swap is the second kind even when the trigger is a model: run a harness for the candidate's general capability, and app-level golden sets for the product surface (Production eval engineering owns gates and golden sets).

1. Two designs: a list of requests, or a program per sample

Every harness loads items, gets the model to respond and turns the response into a number. What it treats as the unit of work decides what it can score, what it logs and whether it can run an agent safely.

  • lm-evaluation-harness builds requests. A YAML file says how to render each document into text; the harness builds every request up front (context plus a log-probability to compute or a generation with stop strings), sends them in batches to a backend that implements only three methods, then runs filters and metrics over the responses. Nothing happens per sample that the YAML did not declare: reproducible, and it scales to hundreds of fixed tasks.
  • Inspect runs a program per sample. A Sample becomes a TaskState; a chain of solvers transforms it (add a system message, fill a template, call the model, call a tool, critique, loop as an agent); a scorer grades the final state; every step is recorded as an event. It can express agents, sandboxes and judge batteries, and its logs are complete.

Chat template

Instruction-tuned models were trained on their own chat format; sending them raw text is a different test, and each harness has a different default:

  • lm-eval sends raw text unless asked. --apply_chat_template wraps prompts in the tokenizer's template, --fewshot_as_multiturn (on by default with it) turns the shots into alternating turns, and --system_instruction adds a system prompt (interface.md). The results file records a hash of the chat template and of the system instruction.
  • Inspect sends messages; its Hugging Face provider applies the tokenizer's chat template unless use_chat_template=False.
  • simple-evals and the app-level tools always send chat messages; HELM builds a text prompt and the model client decides how to send it.

Size of the effect: the largest on this page. The same 0-shot MMLU prompt, raw then wrapped in Qwen2.5's chat template and parsed strictly: 41.5% to 8.0% (-33.5 points); 168 of 200 answers had no letter where the parser looked, because the model explains instead of answering. Adding "Answer with only the letter." brought it back to 38.5%. Qwen2.5's template also inserts a default system line ("You are Qwen ... a helpful assistant") when none is given: a knob nobody set.

A default worth knowing: Inspect's local Hugging Face provider samples
Inspect's hf provider sets do_sample=True unless the model argument do_sample=False is passed (hf.py line 118), so a local run uses the model's own sampling settings (Qwen2.5-0.5B-Instruct's generation config: temperature 0.7, top-p 0.8, top-k 20, repetition penalty 1.1). Passing --temperature 0 instead raises an error in transformers 5.18, which this page hit. lm-eval's GSM8K task sets do_sample: false, temperature: 0.0 in the YAML. Greedy against sampled is a knob in its own right.

Read the answer: log-likelihood or generation

lm-eval-harness has four request types (lm_eval/api/instance.py) and a backend implements three methods to run them all (model guide):

  • loglikelihood(context, continuation): the log-probability of a given continuation and whether it is the greedy one. A multiple_choice task asks it once per option and picks the largest. Deterministic, cheap, works on base models, can never produce an invalid answer; it measures how the model ranks given options, never whether it can produce one, and it needs prompt log-probabilities, which most chat APIs do not return.
  • loglikelihood_rolling(text): the log-probability of a whole text, for perplexity and bits-per-byte.
  • generate_until(context, until=[...]): generate until a stop string, then filter. What chat and reasoning models need; every extraction rule becomes part of the score.

The other harnesses lean generative: HELM has both adapters; Inspect, simple-evals, promptfoo and Braintrust score generated text. Inspect added perplexity() and target_perplexity() in 0.3.212 (24 April 2026; changelog), described by its docs as the counterpart of lm-eval's loglikelihood pattern; it needs prompt log-probabilities, which only its vLLM and SageMaker providers supply (Inspect: Perplexity).

Length normalisation, exactly
For multiple_choice tasks lm-eval reports acc (argmax of the summed log-probabilities), acc_norm (argmax of the sum divided by the option's length in characters) and, when asked, acc_bytes (divided by its UTF-8 byte length) and acc_mutual_info (task.py lines 1494 to 1560). Correction: the old version of this page called acc_norm byte-length normalised; it is character-length, the same for ASCII options and different for most other scripts. On the 200 items, acc to acc_norm moved +0.5 points; scoring the answer text instead of the letter moved this model +0.5 and LLaMA-65B -14.8.

Extraction: the code that finds the answer

A generative score is only as good as the code that finds the answer in the text. On GSM8K each harness uses a different rule (the files themselves: tab GSM8K in every harness):

When a number moves, the first three suspects are a real capability change, a broken extraction filter and a truncated completion; only per-sample logs separate them (tab Inside a run log walks both formats from the real runs).

Logs can misreport: token counts from Inspect's local provider
Inspect's local Hugging Face provider records each sample's usage as the padded batch shape: in this page's run every one of the ten samples logged 2,269 input and 494 output tokens, while the real prompts were 2,184 to 2,269 tokens and the outputs 146 to 493 (hf.py lines 651 to 652; counts in src/data/runs.json), and the stop reason was "unknown". API providers report real usage; for a local model, count tokens yourself before using the log to spot truncation.
  • Seeds and sampling. Greedy is not the default everywhere (Inspect's local provider samples, section 2). With sampling, run several epochs and report the spread; Inspect's Epochs reruns each sample and reduces with mean, median, mode, max, at_least_k or pass_at_k.
  • Serving. The same weights behind different providers or precisions are different instruments: Llama 3.1 8B Instruct through Together's FP8 endpoint scored 56.06 on HELM's MMLU against Meta's 69.4 (confounded with the prompt and token budget); lighteval's own example compares one model across three Inference Providers for this reason.

5. Running evals at scale: tokens, batching, caching

Cost and time are driven by tokens, and the harness decides most of them before the model runs. The page's own two runs, per GSM8K problem:

Inspect's prompt is 2.3 times lm-eval's, and 87% to 92% of it is the same system message every time. Real token counts with the model's tokenizer (src/data/runs.json); share of prompt characters in the identical 10-shot system message, measured on all ten prompts. lm-eval draws a different five shots per problem, so no two of its prompts share a prefix.

Derived for the full test set (1,319 problems, mean per problem times 1,319): lm-eval's prompt about 1.27 million input and 0.15 million output tokens; inspect_evals' about 2.93 million input and 0.42 million output, per epoch. Cost is items x (input tokens x input price + output tokens x output price) x epochs; prices are volatile and belong to the provider pages. Measured wall time for the ten problems on 2 CPU threads: 132 s (lm-eval, 256-token cap) against 763 s (Inspect, 512-token cap), confounded by prompt length, output length and batching, so not a speed comparison of the harnesses.

  • Shots dominate input cost. Ten shots made 87% to 92% of every Inspect prompt here. Fewer shots, or shots the model does not need, are the cheapest saving; check the effect on the score first (section 2).
  • A fixed prefix is cacheable. Inspect's identical system message is exactly what provider prompt caching and a serving engine's prefix cache reuse; lm-eval's per-problem shots defeat it. Whether a cache hit is billed less is the provider's rule.
  • Batching, lm-eval. --batch_size takes an integer, auto or auto:N (default 1), with --max_batch_size as the ceiling (interface.md). The Hugging Face backend sorts requests longest first, so "any OOMs will happen right away rather than near the end" and the first batch sets the padded length; on out-of-memory it halves the batch and retries. For multiple choice it groups requests that share a context and reuses one forward pass for one-token continuations, which "speeds up some multiple-choice tasks proportionally to the number of choices" (huggingface.py). Serving engines (vLLM, SGLang backends) batch for you.
  • Concurrency, Inspect. Inspect is built around API calls in flight rather than local batches: adaptive concurrency by default "with a maximum of 100 concurrent connections per model", starting at 20, cutting the limit by a factor of 0.8 on a rate-limit error, and retrying recoverable errors indefinitely with exponential backoff unless --max-retries or --timeout caps it (model concurrency). max_samples follows the connection limit; one task runs at a time unless --max-tasks is raised (parallelism).
  • Caching responses. lm-eval's --use_cache keeps model responses in SQLite under a path prefix and --cache_requests caches the built prompts. Inspect's --cache (or cache=True) keys on the model and base URL, the message history, the epoch, the generate config and the active tools, and "will expire in 1 week" unless a CachePolicy says otherwise (caching). A cache makes reruns cheap and can replay a stale answer after a provider silently updates a model: a cached run measures the old one.
  • Subsets. --limit (both harnesses) runs the first n items for a smoke test; a number from it is not the benchmark's number, and how many items a difference needs is Eval statistics's question.

6. Sandboxes for agentic evals

An agent eval lets model-written code and commands run. Inspect makes the environment part of the task: tools such as bash(), python() and text_editor() require a sandbox, each sample can get its own, and the environment is declared next to the task as a Dockerfile or compose.yaml (Sandboxing). Nothing else here compares: lm-eval runs code tasks such as HumanEval on the host, gated by unsafe_code: true in the task and --confirm_run_unsafe_code; HELM, simple-evals and openai/evals have no sandbox layer; Braintrust connects agent code through "remote evals or sandboxes" (docs); promptfoo grades agent trajectories but does not isolate them. Inspect's local sandbox and lm-eval's flag both run model code as you on your machine.

The opposite trade: a harness inside an enclave
Google DeepMind's August 2026 double-blind pilot ran a proprietary model and private items inside a confidential-computing enclave so neither side saw the other's secret; its cost is the thing Inspect's log viewer exists for: no one can read the transcripts, so a bad score cannot be attributed to capability, a broken extraction filter or a truncated completion. 8. Each harness, in depth

Optional: architecture, gotchas and contribution paths, one block per harness.

lm-evaluation-harness (EleutherAI): task YAML, model registry, gotchas

The reproducibility standard for base-model benchmarking and the default behind "numbers in a model card". It was the backend of Hugging Face's Open LLM Leaderboard v1 and v2, and its README still describes it as the leaderboard's backend; the leaderboard Space was archived on 13 March 2025 (README).

  • Architecture. A TaskManager discovers task YAML files and builds ConfigurableTask objects; a registry maps model names to LM subclasses. The registry holds 37 model names, aliases included (hf, vllm, sglang, openai-completions, anthropic, litellm, mamba, gguf, nemo, neuron, IPEX, ONNX, TensorRT-LLM, watsonx and more; lm_eval/models). Implement the three request methods and any backend runs every task.
  • Task YAML. Declares the dataset (a Hub path), doc_to_text and doc_to_target (Jinja templates, or Python through !function), output_type, metrics, generation settings and filter chains (regex extraction, take-first, majority voting for self-consistency). Variants (shot counts, chain-of-thought versions, translations) are YAML overrides through include:; groups and tags aggregate tasks (mmlu is a group of 57 subtasks). The tasks folder has 221 benchmark directories and about 14,000 YAML files at commit d6de816; the README says "over 60 standard academic benchmarks, with hundreds of subtasks and variants".
  • Gotchas. trust_remote_code runs dataset code; YAML quoting bites (until: ['\n'] in single quotes is a backslash and an n, not a newline: the project's footguns.md). Always log the task's version: GSM8K is at version 3.0.
  • Contributing: still genuinely open. Port or add a task in YAML (new task guide; its checklist asks whether you checked against the paper's reference implementation and documented how), fix answer-extraction filters for reasoning models, or add a backend. Maintainers keep "good first issue" and "help wanted" items (CONTRIBUTING).
Inspect (UK AI Security Institute): solvers, scorers, models, and the 2026 change to inspect_evals

The frontier-safety and agentic standard: used by AI security institutes, METR, Apollo Research and labs for pre-deployment testing.

  • Abstractions. Solvers compose into chains: system_message(), prompt_template(), generate(), chain_of_thought(), self_critique(), multiple_choice(), use_tools(), or a whole agent such as react() (the older basic_agent() still ships). Scorers: exact(), match(), includes(), pattern(), choice(), answer(), math(), model_graded_qa(), model_graded_fact(), the perplexity scorers, or custom Python, including batteries of judges. Metrics: accuracy, stderr, bootstrap_stderr, ci_wilson, even krippendorff_alpha (scorer exports).
  • Tooling. inspect view and the VS Code extension render every model call, tool call, state change and score from the log: the best debugging experience of any harness, and the .eval format is stable enough for other tools to consume.
  • Models. All major APIs and local engines (vLLM, SGLang, Hugging Face transformers, Ollama, llama-cpp-python, even TransformerLens and nnterp for interpretability work; providers); --model switches provider without touching the task.
  • inspect_evals is the community collection: "120+ evaluation implementations and 200+ Inspect AI tasks" by its own count.
Correction: inspect_evals no longer takes new eval code
The old version of this page called inspect_evals "the designed on-ramp": pick a published benchmark, propose it in an issue, ship it with an end-to-end test and a parity check, start with question-answering before agentic tasks. Since 8 May 2026 "new evaluations must be hosted in an upstream repo and registered to Inspect Evals via a simple .yaml file" (EVAL_REGISTER.md); the Register lists each eval at a pinned commit of its author's repository, which must be installable, depend on inspect_ai and define tasks with @task (register guide). Pull requests to the collection now come only from pre-approved contributors; anyone else raises an issue and uploads .eval logs that show the problem (tightened on 2 October 2026). The priority flipped too: the guide now prefers "agentic or task-based over simple Q&A", credibly sourced, with a frontier-model baseline to validate against (CONTRIBUTING).

The practical path today: implement the eval in your own repository from the Generality Labs template, test it against a published baseline to the bar in its docs/methodology.md and BEST_PRACTICES.md, register it, and report bugs in existing evals with logs. Model-graded scorers and judge-reliability tooling fit Khalid's judge-battery background, now as a registered upstream eval or a scorer contribution. inspect_ai itself, the framework, has a high bar.

lighteval (Hugging Face): now on Inspect

Harness-inspired and Hugging Face-native: 1000+ tasks by its README, backends for transformers and accelerate, vLLM, SGLang, TGI, Inference Endpoints, Inference Providers, LiteLLM and nanotron (evaluation during pretraining), results and per-sample details pushed to the Hub, quick custom tasks in Python, wide multilingual coverage; it powers Hugging Face's leaderboards. Its README lists lighteval eval, "using inspect-ai as a backend", as the preferred entry point (README); its GSM8K task carries an Inspect sample converter, solver chain and scorer next to the classic prompt function, with the same prompt text as inspect_evals' GSM8K (gsm8k.py). Its docs warn that "not all tasks are compatible with inspect-ai's API as of yet". The last PyPI release (0.13.0, 24 November 2025) lags main: install from source and pin the commit.

Choose it when you live in the Hugging Face stack or need evaluation inside a nanotron or FSDP training loop; it is weaker than lm-eval on community-verified task parity and, outside its Inspect path, weaker than Inspect on agents. Contributing: custom tasks and metrics in Python (adding a custom task), multilingual tasks, converting tasks to its Inspect path.

HELM (Stanford CRFM): the multi-metric reference, in maintenance mode

Each scenario scored on accuracy, calibration, robustness, fairness, bias, toxicity and efficiency (Liang et al. 2022), with every prompt and response dumped per instance and browsable in a web UI. It spawned domain leaderboards: VHELM, HEIM, MedHELM, audio, enterprise and more (README). A run is a RunSpec: a scenario, an adapter spec (instructions, input and output nouns, shots, max tokens, stop sequences) and metric specs. HELM's GSM8K is "Q: ... A:" with 5 training examples, 400 tokens, stop at a blank line (run spec).

Maintenance mode since 1 June 2026 (verified). The README says "HELM entered maintenance mode on June 1, 2026", and the Maintenance Mode Policy says volunteers maintain it on a best-effort basis, "no new features will be added to HELM, and no new evaluations will be added to the HELM leaderboards", and scenarios may break as provider APIs change. Read it for methodology (its "coverage beats a headline score" stance predated the field by two years); do not build new pipelines on it. The policy names Evalchemy, Inspect Evals, lighteval, lm-eval-harness and Unitxt as alternatives. Contributions: notable models, notable scenarios, API-client fixes and significant bug fixes only; open an issue first, because pull requests without one are closed.

OpenAI's evals and simple-evals; Evalchemy; Unitxt
  • openai/evals (2023) is a registry: a YAML names an eval template (Match, Includes, FuzzyMatch, model-graded) and points at JSONL samples kept in Git LFS. Match passes when the output starts with the ideal answer (evals/api.py). The README now points to Evals in the OpenAI dashboard and says "we are currently not accepting evals with custom code"; it accepts only template-based or model-graded YAML evals.
  • openai/simple-evals (2024) published how OpenAI produced its launch numbers: zero-shot chain-of-thought with simple instructions. Its July 2025 notice says it "will no longer be updated for new models or benchmark results" (README); it accepts only bug fixes, model adapters and new result rows.
  • Evalchemy (DataComp and Bespoke Labs) "builds on the LM-Eval-Harness" for post-trained models: one install for reasoning, code and chat benchmarks (AIME, MATH500, LiveCodeBench, GPQA Diamond, MT-Bench, AlpacaEval, WildBench and others), API models through Curator. A benchmark is a Python class with generate_responses and evaluate_responses. Its MATH500 sets "do_sample": False and "temperature": 0.7 in the same request (eval_instruct.py): which wins depends on the backend, so log what was actually sent.
  • Unitxt (IBM) treats prompt variation as first-class: a card (loader, preprocessing steps, task) is combined at run time with a template, a format (for example chat API) and a number of demos, and a card can list many templates (MMLU card). Its catalog badge counts 68 tasks, 3,254 datasets, 357 prompts and 584 metrics. It plugs into others: lm-eval ships tasks/unitxt and HELM a unitxt_scenario.
App-level tools: promptfoo and Braintrust
  • promptfoo: open source (MIT), command line and YAML first, local first. A promptfooconfig.yaml declares a matrix: prompts x providers x test cases, each with assertions (getting-started example). At commit 5fde786 its docs list 44 deterministic assertion types (from equals, contains and regex to is-json, latency, cost, tool-call F1 and trajectory checks such as trajectory:tool-sequence) and 17 model-assisted ones (llm-rubric, g-eval, factuality, context-faithfulness, trajectory:goal-success and others) (assertions). A diff view, CI integration and a red-teaming and vulnerability-scanning mode. On 9 March 2026 Promptfoo announced it "has agreed to be acquired by OpenAI" and "will remain open source" (announcement). Choose it for repository-local prompt regression tests and multi-model comparisons with the fastest setup. Contributing: an ordinary open-source project (providers, assertions, red-team plugins), now with OpenAI as owner.
  • Braintrust: a commercial platform. Every evaluation has three parts, data, task and scorers: Eval("My project", data=init_dataset(...), task=..., scores=[Factuality]), run with bt eval (run in code). Playground runs overwrite themselves; experiments are immutable snapshots for comparison and CI gates; datasets are versioned so experiments can pin a version; scorers come from its open-source autoevals library, code or LLM judges; online scoring rules grade production traces asynchronously, which, with no ground truth on live traffic, means judge scorers (online scoring). Human review is built in. Choose it when you want the loop from offline evaluation to production observability in one place and are willing to pay for it.
  • Same niche, named without a review: Langfuse, Arize Phoenix and W&B Weave. Tracing itself is LLM observability; judges used as scorers are LLM-as-judge.
Mistakes that cost real numbers
  • Comparing two harnesses' scores because the benchmark has the same name. On GSM8K alone the six rules above disagree on what counts as an answer; compare within one harness, one version, one config.
  • Trusting the default decoding. Inspect's local provider samples unless told not to; Evalchemy's MATH500 sends both do_sample: False and temperature: 0.7. Set decoding explicitly and check what reached the model in the log.
  • Believing a sudden drop before reading the failures. In this page's own lm-eval run, strict-match scored 0 of 10 and flexible-extract 1 of 10 on identical outputs.
  • Running model-written code without a sandbox. Use Docker or a VM-backed sandbox for anything agentic.
  • Building a new pipeline on HELM or simple-evals. Both are frozen for new work; read them for method.
  • Using a model-level harness to decide whether to ship an application change. A checkpoint's GSM8K score says little about your prompt, retrieval and tools.
