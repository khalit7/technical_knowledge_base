One function against unit tests: HumanEval, MBPP and pass@k

HumanEval came with OpenAI's Codex paper in July 2021: 164 hand-written Python problems, each a function signature and docstring, with "an average of 7.7 tests per problem" ({{Chen et al. 2021, section 2.2|https://arxiv.org/abs/2107.03374}}). The model writes the body, the tests run in a sandbox, and a problem counts as solved if every test passes. At launch Codex-12B solved 28.8%, GPT-3 0% and GPT-J 11.4%; sampling 100 completions per problem and counting a problem solved if any one passed, Codex reached 70.2% ({{abstract|https://arxiv.org/abs/2107.03374}}). MBPP (Google, August 2021) is the entry-level counterpart: 974 crowd-sourced tasks "designed to be solvable by entry-level programmers", each a one-sentence description with three assert statements; the paper's largest model, 137B parameters, solved 59.6% few-shot ({{Austin et al. 2021|https://arxiv.org/abs/2108.07732}}).

Why hand-written (provenance)

Codex was trained on 159 GB of GitHub Python, which already held solutions to most public puzzle sets, so the problems had to be new. Codex sampled pass@1 at temperature 0.2 and pass@100 at 0.8.

pass@k as reported: 28.8% and 70.2% are different metrics

pass@k is the probability that at least one of k sampled programs passes. On real per-problem results the gap between pass@1 and pass@10 is wide enough to reorder models:

Drawing exactly k samples per problem and checking gives a noisy answer, so the Codex paper draws n ≥ k samples (it used n = 200, k ≤ 100), counts the c that pass, and estimates

pass@k = Eproblems [ 1 − C(n−c, k) / C(n, k) ]
n
samples drawn per problem; c of them pass every test
C(a, b)
binomial coefficient: the number of ways to choose b of a
C(n−c, k)/C(n, k)
the chance that k samples drawn without replacement from the n are all failures

Reading rules. A pass@k figure needs its k, its n and its temperature, and a pass@10 is never comparable with a pass@1. pass@1 is the number for a user who runs the model once; pass@k with large k measures what a system that can run tests and pick a passing answer could reach, which is how AlphaCode and later contest systems used it (selection is on {{Test-time compute and reasoning|n:4035c17b0d0d813f9fb2d62cff1f09ef}}). The estimator itself, and pass^k beside it, belong to {{Agent and trajectory evaluation|n:3ef5c17b0d0d81fdbabaf3582bff37f2}}; {{Agentic benchmarks, Fig. 3|n:3c65c17b0d0d811fb926d7b91ef8234e#stg-pk}} draws it trial by trial on real released runs, so this page keeps only what a coding score needs.

Why the obvious estimator is wrong (the estimator's bias, animated; a calculator; the bias for any pass rate)

The tempting shortcut is to estimate pass@1 as p̂ = c/n and plug it into 1 − (1 − p̂)k. The paper shows in its Appendix A that this "results in a consistent underestimate", and that "the gap doesn't fully close even when n > 5k" ({{Codex paper, section 2.1 and Appendix A|https://arxiv.org/abs/2107.03374}}). The reason is curvature: (1 − p̂)k is convex in p̂, so averaging it over the luck of the draw overstates the chance that all k fail. The paper also gives a numerically stable product form, 1 − ∏i=n−c+1..n(1 − k/i), which this page uses.

The 20 outcomes are one fixed draw at p = 0.15 illustrative; the true pass@5 is 1 − 0.855 = 55.6%. The last step's averages are exact sums over the binomial distribution of c, computed in the page and checked against src/recompute.py (for n = 10, p = 0.1, k = 5: 40.95% for the Codex estimator, the true value, against 34.85% for the plug-in).

Fig. 4 draws 20 samples for one problem whose true pass rate is 15% illustrative and tracks both estimates of pass@5 as the samples arrive, four at a time; the last step replaces this one draw by the exact average over every possible draw. The true pass@5 is 1 − 0.855 = 55.6%.

  1. One problem, true pass rate 15%. We want pass@5: the chance that at least one of 5 samples passes. Both estimators will see the same samples.
  2. Samples 1 to 4: c = 1 of n = 4. The Codex estimator needs n ≥ k = 5 samples, so only the plug-in has a value: 1 − (1 − 1/4)5 = 76.3%.
  3. Samples 5 to 8: c = 1 of 8. Codex: 1 − C(7,5)/C(8,5) = 62.5%. Plug-in: 1 − (7/8)5 = 48.7%.
  4. Samples 9 to 12: c = 2 of 12. Codex 68.2%, plug-in 59.8%.
  5. Samples 13 to 16: c = 2 of 16. Codex 54.2%, plug-in 48.7%: the two move together, the plug-in always lower.
  6. Samples 17 to 20: c = 3 of 20. Here c/n equals the true rate, so the plug-in lands on the truth (55.6%) and the Codex estimate is above it (60.1%): one draw cannot show bias.
  7. Averaged over every possible draw of 20. For every c the plug-in curve sits below the Codex curve. Weighted by how likely each c is, the Codex estimator averages exactly 55.6%, the truth; the plug-in averages 51.8%, 3.8 points low. That is the Codex paper's "consistent underestimate".

One problem: n, c and k

Try: n = 10, c = 1, k = 10: the Codex estimator is 100% (one of the ten passed, and k = n takes all ten), the plug-in 65.1%. Then raise n with c/n fixed and watch the two converge slowly.

Bias, exactly: the average of each estimator over every possible draw

Fix a true pass rate p and a sample count n. c is then Binomial(n, p), and each estimator's average over c can be computed exactly. The true pass@k is 1 − (1 − p)k.

Weak tests overstate correctness: EvalPlus and BigCodeBench

HumanEval's 7.7 tests per problem catch obvious mistakes, not edge cases. EvalPlus (Liu et al., 2023) generated new test inputs with "LLM- and mutation-based strategies", checked against the reference solution, and extended HumanEval's tests "by 80x" into HumanEval+; a 2024 release did the same for MBPP ("35x more tests" in MBPP+, 378 tasks after broken ones were removed; {{EvalPlus README|https://github.com/evalplus/evalplus}}). On 26 models it reduced pass@k "by up-to 19.3-28.9%" and reordered models: WizardCoder-CodeLlama and Phind-CodeLlama overtook ChatGPT on HumanEval+, which neither did on HumanEval ({{Liu et al. 2023|https://arxiv.org/abs/2305.01210}}).

  2. HumanEval's 13 inputs. Sample 1 fails one, is_prime(1), which it calls prime. Samples 6 and 4 pass all 13, so HumanEval grades two of the three programs CORRECT, as the paper did.
  3. EvalPlus adds 154 inputs. Generated by an LLM and by mutating seed inputs; the reference solution supplies each expected answer, and its contract admits any integer, including 0 and negatives.
  4. Sample 6 meets them. 45 wrong answers, every one on 0 or a negative number, which it calls prime because it returns False only for 1; 11 large inputs run over 1 second, because it tries every divisor up to n. It passes 98 of 154: under HumanEval+ it is wrong.
  5. Samples 4 and 1 meet them. Sample 4, the textbook square-root check, passes all 167. Sample 1, already caught by HumanEval, adds 46 wrong answers and one run over 1 second.

Sample 6 is the lesson. HumanEval's tests never ask about 0 or a negative number, so a program that calls them prime was graded CORRECT. A weak suite does not just add noise; it rewards a specific kind of wrong program, which is why EvalPlus's reorderings happened.

BigCodeBench (BigCode, June 2024) moved from puzzles to practical code: 1,140 tasks that call functions "from 139 libraries and 7 domains", with "5.6 test cases with an average branch coverage of 99%" ({{README|https://github.com/bigcode-project/bigcodebench}}). At launch the best of 60 models scored "up to 60%" against human performance of 97% ({{Zhuo et al. 2024|https://arxiv.org/abs/2406.15877}}). It is not saturated but unmaintained: no models were added after April 2025. GPT-4's technical report already estimated about 25% of HumanEval overlapping its training data ({{OpenAI 2023, Appendix C|https://arxiv.org/abs/2303.08774}}), and no 2026 model card reports HumanEval or MBPP; HumanEval+ and MBPP+ stay useful as cheap regression tests for small models.

More detail (input counts, BigCodeBench variants)

In the released v0.1.10 data, HumanEval's 164 problems carry 1,570 base inputs and 122,683 HumanEval+ inputs derived (counted from {{the release|https://github.com/evalplus/humanevalplus_release/releases/tag/v0.1.10}}). BigCodeBench comes in a Complete variant (docstring) and an Instruct variant (short instruction), plus a 148-task Hard subset added in July 2024.

Corrections to the old page

"HumanEval: saturated (>99%) and retired" mixed a lab figure with an independent one. The >99% is one OpenAI simple-evals row (o4-mini high, 99.3%); the independent tops are 96.3% on base tests and 89.0% on HumanEval+. Saturated stands; the 7-point gap between the two suites is the more useful number.

"BigCodeBench: saturating" is wrong: its tops are 62.4% (Full) and 40.5% (Hard). It is not saturated but unmaintained since April 2025, so it says nothing about 2026 models.
