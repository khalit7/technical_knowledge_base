Coding benchmarks: HumanEval to SWE-bench Pro

How code benchmarks are built and graded, from one Python function against a handful of unit tests to whole repositories, contest ratings and licensed private code; what each score means, how it fails, and what to use now. Coding benchmarks in one screen

A coding benchmark gives a model a programming task and runs what it writes against tests. That makes code the most objectively graded skill there is, and also the easiest to overstate: a score is only as good as the tests, the tasks may already sit in the training data, and once the model is an agent in a repository the harness around it is part of the score.

The field moved in three steps. One function against a few unit tests (HumanEval, MBPP, 2021), measured by pass@k. Contest problems pinned to dates (LiveCodeBench, Codeforces ratings), so a model can be scored on problems published after it was trained. Real issues in whole repositories (the SWE-bench family, 2023 onward), where an agent edits a codebase and the repository's own tests decide. Each step was forced by the previous one saturating, and each brought its own failure: weak tests, frozen leaderboards, leaked solutions, memorised repositories. By 2026 the answers to contamination have split three ways: new tasks by the calendar, private code by licence, and familiar code transformed beyond recognition.

One function against unit tests: HumanEval, MBPP and pass@k

HumanEval came with OpenAI's Codex paper in July 2021: 164 hand-written Python problems, each a function signature and docstring, with "an average of 7.7 tests per problem" (Chen et al. 2021, section 2.2). Hand-written mattered because Codex was trained on 159 GB of GitHub Python, which already held solutions to most public puzzle sets. The model writes the function body; the tests run in a sandbox; a problem counts as solved if every test passes. At launch Codex-12B solved 28.8%, GPT-3 0% and GPT-J 11.4%; sampling 100 completions per problem and counting a problem solved if any one passed, Codex reached 70.2% (abstract).

MBPP (Google, August 2021) is the entry-level counterpart: 974 crowd-sourced tasks "designed to be solvable by entry-level programmers", each a one-sentence description with three assert statements; the largest model of the paper, 137B parameters, solved 59.6% few-shot (Austin et al. 2021).

pass@k, and why the obvious estimator is wrong

That 70.2% is a different metric from 28.8%. pass@k is the probability that at least one of k sampled programs passes. Drawing exactly k samples per problem and checking gives a noisy answer, so the Codex paper draws n ≥ k samples (it used n = 200, k ≤ 100), counts the c that pass, and estimates

pass@k = Eproblems [ 1 − C(n−c, k) / C(n, k) ]
n
samples drawn per problem; c of them pass every test
C(a, b)
binomial coefficient: the number of ways to choose b of a
C(n−c, k)/C(n, k)
the chance that k samples drawn without replacement from the n are all failures

The tempting shortcut is to estimate pass@1 as p̂ = c/n and plug it into 1 − (1 − p̂)k. The paper shows in its Appendix A that this "results in a consistent underestimate", and that "the gap doesn't fully close even when n > 5k" (Codex paper, section 2.1 and Appendix A). The reason is curvature: (1 − p̂)k is convex in p̂, so averaging it over the luck of the draw overstates the chance that all k fail. The paper also gives a numerically stable product form, 1 − ∏i=n−c+1..n(1 − k/i), which this page uses.

The animation draws 20 samples for one problem whose true pass rate is 15% illustrative and tracks both estimates of pass@5 as samples arrive. The final step replaces one lucky or unlucky draw by the exact average over every possible draw.

The 20 outcomes are one fixed draw at p = 0.15 illustrative; the true pass@5 is 1 − 0.855 = 55.6%. The last step's averages are exact sums over the binomial distribution of c, computed in the page and checked against src/recompute.py (for n = 10, p = 0.1, k = 5: 40.95% for the Codex estimator, the true value, against 34.85% for the plug-in). On real per-problem results from LiveCodeBench, the pass@k lab tab shows the gap for ten models.

Two reading rules follow. A pass@k figure needs its k, its n and its temperature (Codex sampled pass@1 at temperature 0.2 and pass@100 at 0.8), and a pass@10 is never comparable with a pass@1. And pass@1 is the number that matters for a user who runs the model once; pass@k with large k measures what a system that can run tests and pick a passing answer could reach, which is how AlphaCode and later contest systems used it.

Weak tests overstate correctness: EvalPlus and BigCodeBench

HumanEval's 7.7 tests per problem catch obvious mistakes, not edge cases. EvalPlus (Liu et al., 2023) generated new test inputs with "LLM- and mutation-based strategies", checked against the reference solution, and extended HumanEval's tests "by 80x" into HumanEval+; a 2024 release did the same for MBPP ("35x more tests" in MBPP+, 378 tasks after broken ones were removed; EvalPlus README). On 26 models it reduced pass@k "by up-to 19.3-28.9%" and reordered models: WizardCoder-CodeLlama and Phind-CodeLlama overtook ChatGPT on HumanEval+, which neither did on HumanEval (Liu et al. 2023). In the released v0.1.10 data, HumanEval's 164 problems carry 1,570 base inputs and 122,683 HumanEval+ inputs derived (counted from the release).

Where the two sets stand. OpenAI's simple-evals lists 99.3% for o4-mini (high) on HumanEval, a lab figure; the independent EvalPlus board tops out at 96.3% on base tests and 89.0% on HumanEval+ (o1-preview and o1-mini), and at 80.2% on MBPP+ against 95.5% on base MBPP (o1-preview) (EvalPlus leaderboard; simple-evals). GPT-4's technical report already estimated about 25% of HumanEval overlapping its training data (OpenAI 2023, Appendix C). No 2026 model card reports either set.

BigCodeBench (BigCode, June 2024) moved from puzzles to practical code: 1,140 tasks that call functions "from 139 libraries and 7 domains", with "5.6 test cases with an average branch coverage of 99%", in a Complete variant (docstring) and an Instruct variant (short instruction), plus a 148-task Hard subset added in July 2024 (README). At launch the best of 60 models scored "up to 60%" against human performance of 97% (Zhuo et al. 2024). The board's tops are 62.4% on Full (Gemini-Exp-1206, Complete, calibrated pass@1) and 40.5% on Hard, with no models added after April 2025 (BigCodeBench results).

Contest problems pinned to dates: LiveCodeBench, LiveCodeBench Pro, Codeforces


LiveCodeBench (Jain et al., March 2024) answers contamination with the calendar. It "continuously collects new problems over time from contests across three competition platforms, namely LeetCode, AtCoder, and CodeForces", stores each problem's release date, and lets a reader score any model only on problems released after that model's training data ended (Jain et al. 2024). It also has three scenarios besides code generation: self-repair, code execution and test-output prediction. The last release, release_v6, holds 1,055 problems dated May 2023 to April 2025; the board grades pass@1 from 10 samples for most non-reasoning models and from one for reasoning models derived (from the granularity of the per-problem scores in the board's data).


The design works only while new problems keep arriving, and they stopped. On the board's own data, o4-mini (high) scores 80.2% on the 454 problems from 1 August 2024 to 7 April 2025 derived, and no later problems or models exist. The calendar split itself still teaches: on the 328 medium problems up to December 2024, DeepSeek-V3 solves 71.2% of those released before July 2024 and 35.9% of those after, a 35-point drop; GPT-4-Turbo falls 8.4 points over the same months and GPT-4o 8.5 derived. Part of every drop is newer problems being harder; the excess is the contamination signal. The LiveCodeBench by date tab rebuilds the board's date slider on all 28 models.

LiveCodeBench Pro (Zheng et al., June 2025) raised the difficulty: problems "from Codeforces, ICPC, and IOI that are continuously updated", each annotated by olympiad medalists, with failed submissions analysed line by line. Its launch finding was that "without external tools, the best model achieves only 53% pass@1 on medium-difficulty problems and 0% on hard problems", and that models do well on implementation-heavy problems and badly on "nuanced algorithmic reasoning and complex case analysis" (Zheng et al. 2025). It reports a Codeforces-scale rating per model. The site is now offline and its ratings stop at November 2025 contests, topped by Gemini 3 Deep Think at 3,298 (leaderboard backend, read 4 October 2026).

Codeforces ratings express contest results on the human scale. DeepMind's AlphaCode ranked "on average ... top 54.3% in competitions with more than 5,000 participants" in simulated contests (Li et al. 2022). OpenAI's ladder: GPT-4o 808, o1 1,673 (89th percentile), o1-ioi 2,214 with its full test-time strategy (98th), and o3 2,724 (99.8th); o3 also reached gold on IOI 2024 problems without hand-made strategies, while o1-ioi competing live placed in the 49th percentile (OpenAI 2025). In September 2025 an OpenAI system solved all 12 problems of the ICPC World Finals, and Gemini 2.5 Deep Think 10, both at gold-medal level (Google DeepMind; The Decoder). In 2026 vendors print ratings above 3,000: DeepSeek gives 3,471 for V4.1 Flash, method not stated (DeepSeek release notes).


These numbers are hard to compare. Each lab simulates contests its own way (which contests, how many submissions, whether failed public tests can be retried, how penalties are charged). CodeElo (January 2025) standardised the harness by submitting to Codeforces itself and computing ratings the platform's way; there o1-mini rated 1,578 and QwQ-32B-Preview 1,261, while most other models sat "in the lowest 25 percent among all human participants" (Quan et al. 2025). A live contest (IOI, ICPC) is the one setting where contamination is impossible by construction; the price is that it happens once a year and cannot be re-run.







Real issues in whole repositories: the SWE-bench family


SWE-bench (Jimenez et al., Princeton, October 2023) changed the unit of work from a function to a repository. Its builders collected about 90,000 pull requests from 12 popular Python repositories, kept those that resolve a GitHub issue and change test files, and kept only those where at least one test fails before the pull request and passes after it (a fail-to-pass test), leaving 2,294 tasks (Jimenez et al. 2023, section 2). A task gives the model the issue text and the repository at the commit before the fix; the model returns a patch; the harness applies it, adds the pull request's test changes, and runs the fail-to-pass tests (which must now pass) and the pass-to-pass tests (which passed before and must still pass). "% resolved" is the share of tasks where all of them do.


At launch the best model, Claude 2, resolved 1.96% with retrieved files and 4.8% when handed the files the real fix edited (paper, section 5). The gap between those two figures was the first sign that, in repository-level work, finding the right place matters as much as writing the fix; by 2024 the score belonged to agents that browse, edit and run tests, which is why SWE-bench is also an agent benchmark (the Agentic benchmarks page covers the agent side). SWE-bench Lite is a 300-task subset "sampled to be more self-contained, with a focus on evaluating functional bug fixes", from 11 of the 12 repositories, made "to encourage adoption" by making runs cheaper; its last leaderboard entry dates from September 2025, and the full set's top is 52.62% (Sonar Foundation Agent with Claude Opus 4.5, December 2025) (swebench.com data).


SWE-bench Verified (OpenAI with the SWE-bench authors, 13 August 2024) is the subset that became the standard number of 2024 and 2025. 93 experienced Python developers screened 1,699 random tasks for issues too vague to solve and tests that reject valid fixes; more than two thirds were filtered out, and 500 that passed were kept (OpenAI; the post refused automated reading on 4 October 2026, so the share filtered is quoted from secondary summaries, not re-read). GPT-4o with the Agentless scaffold resolved 33.2% at launch. Counted from the released dataset derived, the 500 tasks are narrower than the name suggests:




So Verified is mostly short, single-file Django and SymPy fixes from issues filed between 2013 and August 2023, every one of them years older than any 2026 model's training data. The One SWE-bench task tab opens one of them completely: the issue, the gold patch, the test patch, the 3 fail-to-pass and 19 pass-to-pass tests, and the harness run for four candidate patches.


Where Verified stands. Vals AI's bash-only run (mini-SWE-agent, one tool) puts Claude Opus 5 at 97.0%, and eight models between 93.4% and 97.0%, last updated 1 September 2026 (Vals AI). On 500 tasks one task is 0.2 points and the standard error at 95% is about 1.0 point derived: √(0.95 × 0.05 / 500), so the top of the board is a tie. Epoch AI's own scaffold measured 83.5% for Claude Opus 4.7 in April 2026, and the swebench.com board's last entry is 26 February 2026 at 79.2%; it dropped its bash-only board on 1 September 2026 (parent atlas). SWE-bench Multimodal (October 2024) moved to 617 visual bugs in 17 JavaScript libraries, every task with at least one image (Yang et al. 2024); its top is 35.98% (GUIRepair with o3, July 2025) and no 2026 model has entered.

What is wrong with SWE-bench: leaked solutions, weak tests, memorised repositories


Solution leakage. SWE-Bench+ (October 2024) read every task that SWE-Agent with GPT-4 resolved and compared its patch with the real one: in 32.67% "the solutions were directly provided in the issue report or the comments", and 31.08% passed "due to weak test cases"; removing both cut that system's resolution rate from 12.47% to 3.97% (Aleithan et al. 2024). A cruder check on Verified itself derived: in 49 of the 500 tasks at least one line the gold patch adds (12 characters or more, not a comment) appears verbatim in the issue text, and in 14 every such line does (rule and list in src/inputs/verified_stats.json). That rule misses paraphrase: the task in the One SWE-bench task tab is not counted, yet its issue spells out the fixing regular expression.


Weak tests. A task's fail-to-pass tests are those of the original pull request, written to check that one fix, not every correct fix or every wrong one. Verified's median task has a single fail-to-pass test derived. A patch that makes that test pass while breaking behaviour nobody tested counts as resolved; Verified's screening removed tests that reject correct fixes, not tests that accept wrong ones.


Memorised repositories. The SWE-Bench Illusion paper (June 2025) asked models to name the file to edit from the issue text alone, without the repository: they reached "up to 76% accuracy" on SWE-bench Verified against "up to 53%" on repositories outside SWE-bench, and reproduced gold functions with "up to 35% consecutive 5-gram accuracy" on SWE-bench against up to 18% elsewhere (Liang et al. 2025). SWE-Bench+ also found "over 94% of the issues were created before LLM's knowledge cutoff dates". The three answers below each attack this problem differently.







SWE-bench Pro: harder tasks, private splits, and a second version


Version 1 (Scale AI, 21 September 2025) kept SWE-bench's task shape and changed what goes in it. 1,865 problems from 41 repositories in three sets: a public set from 11 repositories and a held-out set from 12, all under GPL or other strong copyleft licences (so that training on them carries legal weight), and a commercial set from 18 proprietary codebases of partner startups, whose problems are never published although its results are. Trivial edits were excluded: "the reference solutions span 107.4 lines of code across 4.1 files" on average, and every problem changes at least 10 lines, against Verified's median of 7 lines in one file derived. Each issue was rewritten by people into a problem statement, a list of requirements and the interface the tests expect, so that a correct fix is not failed for guessing a different function name (Deng et al. 2025, sections 1 and 3).

Three answers to contamination: the calendar, the licence, the transformation


Every public coding set leaks: the tasks are on GitHub, the fixes are on GitHub, and the models are trained on GitHub. Three designs answer this in 2026, and each pays for its defence differently.




By the calendar
SWE-rebench (Nebius), SWE-bench-Live (Microsoft)
Mine fresh issues every month and score models only on tasks newer than they are.
Pays with: no stable test set, so no time series; few tasks per window.
Now: 111 problems from 65 repositories (15 May to 1 July 2026); top Claude Fable 5 64.5%.


By licensing
Real-SWE (Specific Labs), SWE-bench Pro's private sets
License private codebases that have never been public, so no crawl can contain them.
Pays with: nobody outside can inspect or re-run the tasks; very few tasks.
Now: 10 tasks, 8 runs each; top GPT-6 Astra 46.25%.


By transformation
SchrodingerRepo
Keep the familiar tasks but rewrite each repository at run time with its behaviour unchanged, and compare.
Pays with: it measures how much of a score depends on familiar surface, not ability directly.
Now: SWE-bench Verified drops 6.0 to 14.4 points when transformed.





By the calendar: SWE-rebench


SWE-rebench (Nebius, May 2025) built an automated pipeline that has mined over 21,000 interactive Python tasks from GitHub, and uses its continuous supply of fresh ones as a leaderboard; its paper compares models with their SWE-bench Verified scores and concludes "performance of some language models might be inflated due to contamination issues" (Badertdinov et al. 2025). The current window holds 111 problems from 65 repositories dated 15 May to 1 July 2026, each model run 5 times; the top five (Claude Fable 5 64.5%, Grok 4.5 63.8%, Claude Opus 5 63.4%, GLM-5.2 62.9%, GPT-5.6 Sol 62.3%) sit within about 2 points, with run-to-run SEMs of 0.6 to 1.8 (SWE-rebench, read 4 October 2026). SWE-bench-Live (Microsoft, May 2025) does the same at a different scale: 1,319 tasks from 93 repositories created since 2024 at its first release, and "a substantial performance gap compared to static benchmarks like SWE-bench" (Zhang et al. 2025).


The board flags "potential contamination" when a model was released after a window began, and its data allow a direct test: for every model whose task range straddles its release date, compare its score on tasks from before the release with tasks from after.




Each row is one model or agent on SWE-rebench. The dot is its resolved rate on tasks dated after its release minus its rate on tasks dated before (in points; hover for both rates and task counts), both sides at least 20 tasks, rates as published for each date range; the line spans ±2 standard errors from task sampling alone, √(p(1−p)/n) per side derived (the board's own SEMs measure run-to-run variation, not task sampling). Task difficulty also drifts from month to month for every model alike.


The result is a null. Of the 50 models, 24 score higher on the older tasks and 26 on the newer; the median difference is 1.0 point in favour of the newer tasks, and only 4 differences exceed two task-sampling standard errors derived. That is the expected answer, and the instructive one: a task published a few weeks before a model's release is almost never in that model's training data, because training data end months before release. The calendar protects through the training cutoff, not the release date, and the gap that matters is between fresh issues and the years-old ones in Verified.



By licensing: Real-SWE


Real-SWE (Specific Labs, September 2026) licenses "a private production codebase ... from a real-world company" for each task: billing, tax, migrations, in TypeScript, Go and Python services with databases and business tools around them. A typical instruction is 1,742 characters and the reference solution edits a median of 11 files (6 in DeepSWE). Each model runs in its own native harness at high reasoning, 8 times per task, and verifiers are injected at grading time (Real-SWE, read 4 October 2026). Licensing is the one defence that does not depend on the tasks being new. Its weakness is size: with ten tasks, every square below matters. Click a task to drop it and watch the ranking.




Passes out of 8 per task and model, as published; the per-model rates reproduce the leaderboard exactly derived (GPT-6 Astra 37 of 80 = 46.25%). Harnesses: Codex CLI (GPT-6 Astra, GPT-5.6 Sol), Claude Code (Fable 5.1, GLM 5.3), Gemini CLI, Muse Code, Grok Build, Kimi Code.


Four of the ten tasks are resolved under 15% of the time, one (Analytics stream reducer) in none of 64 runs; no model solves every task, and the leader, GPT-6 Astra, fails four tasks in all 8 of its runs. The commonest failure is a missed requirement (33% to 55% of each model's failed runs), then integration errors and unverified assumptions. Rollouts under 10 minutes fail less often than longer ones (57.4% of 108 against 66.2% of 532), and estimated cost per rollout runs from $2.50 (Gemini 3.8 Flash, 38.75%) to $6.96 (Fable 5.1, 45.0%) with no clear relation to score.

By transformation: SchrodingerRepo


SchrodingerRepo (August 2026) keeps SWE-bench Verified's 500 tasks and rebuilds each repository at evaluation time with its behaviour unchanged, at four levels: the issue reworded, identifiers remapped, definitions reordered within files, code rewritten. GPT-5.4-mini in mini-swe-agent falls from 46.8% to 35.6% with all four, and its average actions per task rise from 11.3 to 19.8; across the paper's models the full transformation costs 6.0 to 11.2 points on all 500 tasks and 14.4 points for Gemini 3.1 Flash Lite on the 300 most-leaked tasks (Table I).




The knowledge base's SchrodingerRepo paper page runs the released transformation code live on the paper's Django case and argues the reading: the drop shows that unfamiliar names cost exploration, which is not the same as proving the familiar ones were memorised. Either way, a share of a static Verified score is knowing where to look.







Other coding benchmarks worth knowing


Aider Polyglot (Aider, December 2024) replaced Aider's Python-only editing benchmark after it saturated (Claude 3.5 Sonnet 84.2%, "Models as old as GPT 3.5 Turbo were able to solve half of the 133 problems"). From Exercism's 697 exercises in C++, Go, Java, JavaScript, Python and Rust it kept the 225 "solved by 3 or fewer" of seven strong models; the model edits code through Aider's edit formats and gets a second attempt after seeing failing tests. o1 (high) launched it at 62% (Aider). It is cheap to run and tests the editing loop practitioners use, which made it popular with them; its top is 88.0% (GPT-5 high, diff format, August 2025) and the board has added few frontier entries since (leaderboard, via Epoch AI). Saturating.


DeepSWE (Datacurve, 2026) runs every model in one fixed minimal harness (mini-swe-agent) on 113 repository tasks (v1.1) and reports pass@1 averaged over 4 runs with a 95% interval; the top is Gemini 3.8 Flash (high) at 73.8% ± 1.4 at a mean $2.36 per task, board updated 22 September 2026 (DeepSWE, as read for the Topic: llms, Benchmarks tab). A fixed harness is what makes its readings comparable across models; it trades away the vendor agents that Real-SWE keeps on purpose.


Phi-Bench (USTC, StepFun and others, September 2026) asks whether a model can engineer the infrastructure AI runs on: 85 open-ended tasks in nine categories (training systems, inference and serving, compression, kernels, I/O, hardware and edge, data infrastructure, system optimisation, system assurance) in three formats of rising scope: 55 single-file kernel completions, 20 multi-file repository implementations and 10 end-to-end optimisations where the model must first find the bottleneck. Tasks were reconstructed from pull requests and issues, mined with agent help and generated tests, or curated by experts where no history exists, grounded in 2,260 papers and 1,852 engineering artifacts. Claude Opus 5 leads at 36.53, then Kimi K3 28.12 and Qwen3.8 Max 27.73 (Ding et al. 2026). The knowledge base's Phi-Bench paper page replays its MoE training task and simulates its scoring.


Corrections to the old page (from the Phi-Bench paper page)
36.53 is a mean reward in which matching the expert reference earns zero, not a percentage of tasks passed. "Hardware and edge tasks collapse to 5.4%" is Qwen3.7 Max, seventh overall, on a category of 3 tasks; Claude Opus 5 scores 3.9 there. "Longer reasoning budgets do not reliably help" is too strong: the effort figure covers 30 tasks, all three models tested are best at maximum effort, and Kimi K3 loses 45% at low effort.


Terminal-Bench (agents completing tasks in a terminal; version 4.0 current since September 2026, not comparable with 2.x) is often quoted beside SWE-bench Pro as a coding number. It belongs to the Agentic benchmarks page, which owns its versions and harnesses.

Common mistakes


Comparing pass@1 with pass@k, or the plug-in estimate with the Codex one
pass@100 (70.2% for Codex-12B) and pass@1 (28.8%) are different metrics. pass@k computed as 1 − (1 − p̂)k underestimates; use 1 − C(n−c,k)/C(n,k) with n ≥ k samples, and report n and the temperature. pass@k lab.


Treating "passes the tests" as "correct"
HumanEval graded a sample that calls every negative number prime as CORRECT; HumanEval+ caught it. Verified's median task has one fail-to-pass test. Ask how many tests, and whether anyone tried to break them.


Quoting a frozen leaderboard as current
LiveCodeBench (April 2025 problems), LiveCodeBench Pro (November 2025 ratings), BigCodeBench (April 2025 models), SWE-bench Multimodal (no 2026 entry) and swebench.com's Verified board (February 2026) are all frozen. "Unmaintained" and "saturated" are different reasons to stop using a benchmark; check the date of the last entry.


Calling "SWE-bench Pro" one benchmark
V1 public, V1 commercial, V2 public, V2 Hard and V2 private give 79.2% to 99.4% for one model. Name the version and split, and prefer the private one.


Comparing scores across harness columns
% resolved belongs to model plus scaffold, turn limit and cost cap. Bash-only, open-scaffold and vendor-agent figures are not comparable; on SWE-bench Pro V1 the same GPT-5 scored 23.3% (200 turns) and 41.8% (250 turns, uncapped cost) on the same split.


Reading a release date as a training cutoff
A rolling benchmark protects a model only on tasks newer than its training data. Tasks published weeks before a release are almost never in it, which is why SWE-rebench's before-and-after-release split shows nothing, while LiveCodeBench's split around DeepSeek-V3's marker shows a 35-point drop.


Ranking models on ten tasks
On Real-SWE one task is 10 points of a model's score; dropping a single task can change the leader. Read small private benchmarks as evidence of a gap, not as a ranking.


Ignoring answer leakage inside the task
Some SWE-bench issues contain the fix (32.67% of one agent's resolved tasks in SWE-Bench+). A resolved task can mean the model copied the issue's suggestion; transformed or private tasks remove that route.









pass@k lab


pass@k is the chance that at least one of k sampled programs passes the tests. The Codex paper's estimator draws n ≥ k samples per problem, counts the c that pass, and computes 1 − C(n−c, k)/C(n, k), the chance that k samples drawn without replacement from those n all fail. The plug-in 1 − (1 − c/n)k looks equivalent and is biased low (Chen et al. 2021, Appendix A). Background and the step-by-step animation are in the Reading tab.



One problem: n, c and k


Try: n = 10, c = 1, k = 10: the Codex estimator is 100% (one of the ten passed, and k = n takes all ten), the plug-in 65.1%. Then raise n with c/n fixed and watch the two converge slowly.












Bias, exactly: the average of each estimator over every possible draw


Fix a true pass rate p and a sample count n. c is then Binomial(n, p), and each estimator's average over c can be computed exactly. The true pass@k is 1 − (1 − p)k.

LiveCodeBench by date
