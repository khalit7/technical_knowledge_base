In one screen

An agentic benchmark gives a model tools and an environment (a shell, a desktop, a website, a simulated customer, a set of protocol servers), lets it act for many steps, and then a checker inspects what changed. What it scores is not a completion but a system: the model, the harness (the program that runs the loop, holds the context and exposes the tools), the effort setting, the time and step budget, and the environment itself.

Three consequences run through everything below:

1. The number belongs to a system

Change the harness, the effort or the time limit and the same weights score differently. On ordinary tasks the harness mostly moves the bill (about 2× between harnesses at equal success, Arena, 16 Sep 2026); on some it moves the score by tens of points.

2. Best case is not reliability

A task solved once in four tries counts toward pass@k but not toward pass^k, the chance that all k tries succeed. On real τ²-bench trials pass^4 is 15 to 30 points below pass^1 (computed in this page).

3. The environment can be attacked

In April 2026 an exploit agent from Berkeley RDI reached near-perfect scores on eight agent benchmarks without solving a task, by editing what the checker reads or reading the answers it ships with.

Anatomy of an agent benchmark

Every agent benchmark is four parts, and each part is a place where the number can go wrong:

Environment

What the agent acts on: a Docker container (Terminal-Bench, SWE-bench), a virtual machine (OSWorld), self-hosted websites (WebArena), databases behind tool APIs (τ²-bench), live servers (MCP-Universe), the open web (GAIA, BrowseComp). Self-hosted means reproducible; live means realistic but drifting.

Task

An instruction plus an initial state, and the limits: time, steps, CPU and memory. Limits are part of the task: Terminal-Bench 4.0 changed them and called it a new major version.

Agent

Model plus harness plus settings. Leaderboards list the pair (Terminal-Bench, Real-SWE) or fix the harness (HAL, METR); vendor tables use their own.

Checker

What decides success: tests on the end state, a match against a hidden answer, a database comparison, a rubric, a judge model, or an expert. The checker is the benchmark's real definition of the task.

Checkers come in five kinds, from most to least mechanical:

CheckerUsed byWhat it misses
Tests or scripts on the final stateTerminal-Bench, OSWorld, WebArena (partly), SWE-bench, MCPMarkAnything the tests do not probe; and if the tests run where the agent ran, the agent can edit them

One real task, three runs

The task below is real: regex-log from Terminal-Bench 2.0 (Apache 2.0). The agent must write a regular expression that finds the last date on each log line that contains a valid IPv4 address, and save it to /app/regex.txt. Its checker, tests/test.sh, installs curl, downloads the uv installer with curl ... | sh, runs pytest on 25 log lines that must yield exactly 9 dates, and writes 1 or 0 to /logs/verifier/reward.txt. Run it three ways: an honest agent, Berkeley RDI's exploit on the 2.0 layout, and the same exploit against the separate verifier container that Terminal-Bench 3.0 and 4.0 tasks declare.

The files, commands and test are verbatim from the task's repository (read 4 Oct 2026); the exploit steps follow Berkeley RDI, who report it on all 89 tasks (82 through the curl step shown here, the other 7 by wrapping pip, python or a preinstalled uvx). The third run is illustrative: regex-log is a 2.0 task, drawn here under the verifier layout that every one of the 74 Terminal-Bench 3.0 and 66 4.0 task files declares (environment_mode = "separate", artifacts copied out, nothing installed at trial time; counted in this page from the 3.0 and 4.0 task files). RDI did not test 3.0 or 4.0. You can grade your own regex against the real test in Grade a real task.

What the animation shows is the most common root cause in RDI's audit: the checker trusted something the agent could touch. Harbor, the harness, re-uploads the protected /tests/ folder before verification, but the verifier then used the container's own curl. Counted from the terminal-bench-2 repository in this page, 82 of the 89 tasks' test.sh files fetch the uv installer with curl at verification time, which matches RDI's count independently.

Best case or reliability: pass@k against pass^k

Agents are sampled, so the same task can pass on one try and fail on the next. Run every task n times and count its successes c. Two summaries answer opposite questions:

pass@k = mean over tasks of [ 1 − C(n−c, k) / C(n, k) ]     pass^k = mean over tasks of [ C(c, k) / C(n, k) ]
pass@k
chance that at least one of k tries succeeds: the best case, the metric of code benchmarks since Codex
pass^k
chance that all k tries succeed ("pass hat k"): reliability, introduced by τ-bench (Yao et al., 2024) for agents that must act correctly every time a customer calls
C(a, b)
binomial coefficient; both estimators are unbiased for k ≤ n. At k = 1 both equal the mean success rate.

The τ-bench paper's own example: gpt-4o as a function-calling agent passed 61% of retail tasks once, but pass^8 fell to about 25% (abstract and section 5). The animation below runs the arithmetic on real released trials: GPT-5.2 (high) on τ²-bench's 114 retail tasks, four trials each, from the trajectory file Sierra published with its leaderboard submission (26 Feb 2026, user simulator GPT-5.2). Every value it shows is computed in the page from those 456 trials, and it lands on the leaderboard's published 81.58 / 69.59 / 59.87 / 51.75 exactly.

Each square is one task, placed in the column of how many of its 4 trials succeeded; its fill is the task's contribution to the metric at the current k (C(c,k)/C(4,k) for pass^k, 1 − C(4−c,k)/C(4,k) for pass@k). Only runs whose released file reproduces the published figures exactly are offered (27 of 36 files checked; the others are listed in pass^k on real trials).

Three things to take from it. First, the drop is set by the middle columns: a task solved 3 times in 4 counts 0.75 toward pass^1 and nothing toward pass^4, so a model whose failures are spread thinly across many tasks falls hardest. Second, rankings can change with k. On retail, GPT-5.2 (81.58), Claude Opus 4.5 (79.61) and Gemini 3 Flash (76.75) differ by five points at pass^1 and tie exactly at pass^4 (51.75: each solved 59 of 114 tasks four times out of four). On airline, Opus 4.5 leads at pass^1 (84.0 against 83.0) and GPT-5.2 at pass^4 (72.0 against 70.0); with 50 tasks that is one task either way, inside the noise. Third, pass@k flatters: the same GPT-5.2 run reaches 96.49% at pass@4, so "solved at least once" and "solved every time" differ by 45 points.

Other boards report the same split. MCPMark launched with gpt-5 (medium) at 52.56% pass@1 and 33.86% pass^4; its board's last top entry is GPT-5.2 (high) at 57.5% pass@1 and 44.9% pass^4 (MCPMark leaderboard, updated 15 Dec 2025). The Terminal-Bench 4.0 board runs every pair 5 times per task and prints pass@5 beside the mean: GPT-6 Astra (max) in Codex 58.18% mean and 71.2% pass@5, Claude Fable 5.1 (max) in Claude Code 57.88% and 78.8%, so the order flips depending on which you read (chart below).

The harness, the effort and the budget

An agent's score belongs to the pair (model, harness) at a setting. The evidence on how much each part moves the number:

  • Harness, on ordinary tasks: mostly cost. Arena's HarnessTax study (16 Sep 2026) ran 21 pairs, seven models in three harnesses (Claude Code, Codex CLI and Pi, a minimal open-source harness with four tools: read, write, edit, bash), on the same 30 sampled tasks each from SWE-bench Lite and Terminal-Bench 2.0, three attempts per task. The harness moved success by about ±2 points on SWE-bench Lite and about ±5 on Terminal-Bench 2.0, but Claude Code cost about 2.0× Pi and 1.6× Codex on SWE-bench Lite and 1.5× Pi on Terminal-Bench 2.0 (geometric means). Claude Fable 5 solved 97.8% in Claude Code, 96.7% in Codex and 96.7% in Pi, at $1.33 against $0.67 per attempt (Claude Code against Pi). In 9 of 12 comparisons a model's best observed score came from a harness other than its provider's; GPT-5.6 Sol reached 83.3% on Terminal-Bench 2.0 in Pi against 78.9% in Codex, at $0.42 against $0.76. Claude Code's initial context was over 10× Pi's. Thirty tasks and three attempts is a small sample, which the authors' bootstrap intervals reflect.
  • Harness, on some tasks: the score. StateM (Aug 2026) wrapped a fixed command-line agent in a checked state-machine runbook and lifted GPT-5.5 (xhigh) from 83.1% to 92.1% on Terminal-Bench 2.1 with the same weights, and reported 95.3% raw with GPT-5.6 Sol; the runbook was developed on the same 89 tasks it is scored on, and the leaderboard closed that submission without merging. On ARC-AGI-3, GPT-6 Astra at the same effort scored 62.7% in one harness and 98.6% in another (Knowledge and reasoning owns that case).
  • Effort. On the official Terminal-Bench 4.0 board, GPT-6 Astra in Codex runs from 50.61% at low effort to 58.18% at max, and Claude Opus 5 scores 53.94% at xhigh but 51.82% at max (chart below). HAL found higher reasoning effort reduced accuracy in the majority of its runs across 9 models and 9 benchmarks.
  • Budget. Time, steps and resources are part of the task. OSWorld-Verified reports scores per step budget (50 or 100 steps; see Computer use); Terminal-Bench 4.0 replaced per-task agent timeouts with a flat 8 hours, one reason it is a new major version.
  • Who ran it. Lab tables run their own harnesses and settings. On Terminal-Bench-Science, Claude Fable 5.1 is 52.6% in Anthropic's own run and 40.0% on the official board; GPT-6 Astra is 64.6% in Anthropic's table and 68.1% on the board (Terminal-Bench-Science board, read 4 Oct 2026).

Terminal: Terminal-Bench and Terminal-Bench-Science

Terminal-Bench (Stanford and the Laude Institute; maintained in the harbor-framework organisation, Apache 2.0) gives the agent a shell in a Docker container and a task taken from real work: compile and fix builds, recover a database, train a small model, crack a hash, configure a server. Each task ships an environment, a human-written reference solution and tests that check the end state (paper, Jan 2026). Because Claude Code, Codex CLI, OpenHands and other agents run against it directly, it doubles as a harness benchmark, and the leaderboard lists each entry as an agent and model pair.

The versions are not one scale. Each changed the tasks, the limits or the checker, and the old page's "there is no 3.x" was wrong:

Corrections to the old page
  • "4.0 (Sep 2026) is the current version, and there is no 3.x because the numbering jumped": Terminal-Bench 3.0 exists (tagged 23 Jul 2026, 74 tasks) and 4.0 was tagged 26 Aug 2026 (announced 28 Aug). The maintainers chose 4.0 over 3.1 because Terminal-Bench is now a continuous benchmark with semantic versioning, and changed resources and removed tasks are breaking changes that require re-running trials (4.0 announcement).
  • "2.0 ... reached ~92% (GPT-5.6-class) by Aug 2026": the 92% figures are lab numbers on 2.1 (OpenAI's GPT-5.6 Sol Ultra with four parallel agents 91.9%). The official tops are 84.7% on 2.0 and 83.8% on 2.1 (root Benchmark atlas, from Wayback captures of the boards).
  • "resets the scale to GPT-6 Astra 57.9% and Claude Fable 5.1 55.8%": those come from Anthropic's Opus 5.5 table. The official board reads GPT-6 Astra (max) 58.18%, Claude Fable 5.1 (max) 57.88%, Claude Opus 5 (xhigh) 53.94%, Grok 4.7 (xhigh) 37.58% (read 4 Oct 2026); Opus 5.5 is not on it yet (Anthropic's own run: 66.4%).
  • "stood at 52.6% for Claude Fable 5.1 one week later": 52.6% is Anthropic's own run, published five days after launch; the official Terminal-Bench-Science board lists Fable 5.1 at 40.0% and Artificial Analysis measured 43.3%.

What changed at 4.0, in the task files. 8 tasks removed (2 saturated, 2 refused by models, 2 with public solutions, 2 for quality or platform problems), 19 fixed, and every task's agent timeout set to a flat 8 hours (65 of the 66 task files state 28,800 s; the announcement says all). "Saturated" was defined strictly: every model class in every family of the latest generation solves the task 5 times out of 5. Because time and memory limits are part of a task when the agent has a shell and a clock, 2.x and 4.0 scores are not comparable even on tasks that survived. The announcement also notes fewer agent timeouts and errors than 3.0, so less measurement noise, and that Sonnet 5 used 21.6 billion tokens on the run against 6.5 billion for Opus 5.

Terminal-Bench-Science 0.1 (announcement, 27 Aug 2026), by Stanford with the Terminal-Bench and Harbor teams, is the first agent benchmark built around research workflows rather than software engineering: 70 tasks across life, physical, Earth, mathematical and engineering sciences, from 376 contributors in 22 countries, reviewed by domain and technical reviewers plus a final "bar-raiser", graded by task-specific tests, three trials per task. At launch Claude Opus 5 led at 30.0%, GPT-5.6 Sol 22.4%, Claude Fable 5 21.4%, GPT-5.6 Luna 3.3%. Within a week the official board reached 68.1% (GPT-6 Astra (max) in Codex, dated 3 Sep, ±3.2) and later 63.3% for Claude Opus 5.5 (max). It is meant to be continuous: version 0.2 was taking task pull requests until 5 October 2026. Lab and board figures disagree for the same model in both directions (Fable 5.1 52.6% against 40.0%; Opus 5.5 58.7% against 63.3%; Astra 64.6% against 68.1%), so quote the board and say which.

Computer use: OSWorld and its relatives

OSWorld (Xie et al., XLANG Lab, HKU, Apr 2024) runs the agent on a real Ubuntu virtual machine, seeing screenshots (and optionally the accessibility tree) and sending mouse and keyboard actions, across office apps, browsers, file managers, IDEs and workflows that span several apps. Each of its 369 tasks has an initial-state setup and a custom evaluation script that inspects the final state (a file's contents, a setting, a spreadsheet). At launch people completed 72.36% and the best model 12.24%. Claude 3.5 Sonnet's computer-use release in October 2024 scored 14.9% screenshot-only, 22.0% with more steps (Anthropic, 22 Oct 2024).

Correction: OSWorld 2.0 vendor figures are partial credit
The old page and current vendor cards quote OSWorld 2.0 at 72.6% (GPT-6 Astra), 74.0% (Claude Opus 5) and 81.8% (Claude Opus 5.5), with GPT-6 Sol at 60.5% offline at extra-high effort. These are partial-credit scores, from different task releases and harnesses: OpenAI's 72.6% is release 2026.08.08, offline set (OpenAI); Anthropic's 74.0% and 81.8% are its own re-run on the 10 September task files with a new context harness, where the strict pass rates are 37.2% and 48.7% (Opus 5.5 system card, 8.13.3). On the official board's default binary metric the best is 44.33% (Opus 5, release 2.1), and the maintainers' own run of Opus 5 on release 2026.08.08 read 31.4% binary, 68.3% partial. OpenAI also notes that the Fable 5.1 system card used modified tasks and grading. At launch (26 Jun 2026) the best public model was Claude Opus 4.8 at 20.6% binary with batched tools. A 2.0 figure without release, set and metric carries no information, and none of them compares with OSWorld-Verified.

How OSWorld was broken. RDI's exploit agent reached 73%: the gold files the checker compares against sit on public Hugging Face URLs inside the task configuration, and the VM has internet, so the agent downloads the gold file straight into the path the checker reads ("the evaluator compares gold vs. gold"); state checks were met by setting the state directly (gsettings set, writing expected config files); the 29 tasks marked infeasible were answered "FAIL" for free points; and the grader called Python's eval() on a string read from the VM, so a crafted gsettings value ran code on the grading machine (RDI).

Relatives. Windows Agent Arena (Microsoft, Sep 2024) adapts OSWorld's framework to 150+ Windows tasks, parallelised on Azure to finish in about 20 minutes; its Navi agent scored 19.5% against 74.5% for people. AndroidWorld (Google, May 2024) has 116 programmatic tasks across 20 Android apps, parameterised so each run draws new instances; the best agent then completed 30.6%.

Web: WebArena, VisualWebArena and the live web

WebArena (Zhou et al., CMU, Jul 2023) self-hosts working copies of four kinds of site (an e-commerce store, a social forum, a GitLab, a content-management system) plus a map, a wiki and manuals, and poses 812 long-horizon tasks checked for functional correctness: the resulting site state, or the answer string. The best GPT-4 agent completed 14.41% against 78.24% for people. Self-hosting makes it reproducible, and its sites and tasks have been public since 2023. The official leaderboard sheet tops at 74.3% (WebTactix with DeepSeek V3.2, February 2026). VisualWebArena (Koh et al., Jan 2024) adds tasks that need the page's images, where text-only agents fall short.

How WebArena was broken. RDI reached about 100% of 812 tasks: navigating the browser to a file:// URL opens the task's own configuration, gold answer included (file:///proc/self/cwd/config_files/{task_id}.json); its must_include check is substring containment, so a verbose answer passes; it calls eval() on agent-controlled strings; and its LLM-judged answers can be steered by text injected into the agent's reply.

The live web trades reproducibility for realism. WebVoyager (Jan 2024) runs on 15 real websites with a GPT-4V judge that agreed with people 85.3% of the time. Online-Mind2Web ("An Illusion of Progress?", Apr 2025) has 300 tasks across 136 live websites and found earlier results over-optimistic; its LLM judge agrees with people about 85% of the time. Mind2Web 2 (Jun 2025) has 130 long-horizon research tasks graded by task-specific judge agents with tree-structured rubrics for correctness and citations; OpenAI Deep Research reached 50 to 70% of human performance in half the time.

Assistants and deep research: GAIA, Gaia2, BrowseComp

GAIA (Mialon et al., Meta and Hugging Face, Nov 2023) asks real-world questions that need web browsing, files, multimodal input and several steps, with one short unambiguous answer each, graded by quasi-exact match after normalisation by answer type. Level 1 needs at most one tool and five steps, Level 2 about five to ten steps and several tools, Level 3 arbitrarily long action sequences. Of 466 questions, a 166-question development set is annotated and the answers to 300 are withheld for the leaderboard. People scored 92%, GPT-4 with plugins 15%. The leaderboard now tops at 93.69% (Level 1 98.9, Level 2 93.1, Level 3 85.7), a multi-model agent combining Qwen3.8 Max, DeepSeek V4 Pro and Claude Opus 5, dated 22 Sep 2026: above the human figure, and the submission is answers, not a sandboxed run.

How GAIA was broken. It is a "submit your answers" leaderboard, and the validation answers are public on Hugging Face, so RDI's agent loaded them from a local file. Its normaliser strips all whitespace and punctuation and lowercases, so "D.R M.A.R.T.I.N L.U.T.H.E.R K.I.N.G J.R" matches "Dr. Martin Luther King Jr.". The leaderboard's 100% blocker is a check that every score equals 1, so missing one question per level gives about 98% while passing the filter. And the scorer penalises correct answers: a ground truth of "1,500" is split as a list ["1", "500"], so the correct "1500" is marked wrong.

Gaia2 (Meta ARE, Sep 2025) runs asynchronously in simulated apps: the environment changes while the agent works, and tasks add ambiguity, noise, collaboration with other agents and time limits. No system dominated, and budget-scaling curves plateaued.

BrowseComp (Wei et al., OpenAI, Apr 2025) has 1,266 questions whose short answers are hard to find and easy to check; each was written so another person could not solve it within ten minutes and the models of the day could not either. At launch GPT-4o scored 0.6% (1.9% with browsing), o1 9.9% and OpenAI Deep Research 51.5%, a model trained on data meant to teach this kind of search; browsing also raised calibration error (confident wrong answers). Vendor figures now reach 91.5% (GPT-6 Astra, OpenAI, 2 Sep 2026) and 92.2% (GPT-5.6 Sol Ultra with four parallel agents, OpenAI), mixing single- and multi-agent setups; there is no independent board, and Anthropic left it out of its Opus 5.5 table.

Customer service: τ-bench, τ²-bench, τ³ and Hyper-τ-bench

τ-bench (Yao et al., Sierra, Jun 2024) puts an agent between a simulated user (an LLM playing a customer with hidden instructions) and a domain's tool APIs, under a written policy it must obey. Retail has 500 users, 50 products, 1,000 orders, 7 write and 8 read tools and 115 tasks; airline has 500 users, 300 flights, 2,000 reservations, 6 write and 7 read tools and 50 tasks. Success compares the database at the end with the annotated goal state, so many different conversations can pass. It introduced pass^k. Sierra later fixed more than 50 airline and retail tasks, so legacy results are not directly comparable with current ones (taubench.com).

τ²-bench (Barres et al., Jun 2025) adds a telecom domain with dual control: the user also has tools and acts on a shared device state, so the agent must guide a person through steps rather than do everything itself. Tasks are generated compositionally from atomic parts, and the user simulator is constrained by tools and observable state; agents dropped sharply from "no user" to dual control. The core leaderboard (version 1.0.1, four trials, user simulator GPT-5.2; older rows used GPT-4.1) tops at 87.91% mean pass^1, Qwen3.5-397B-A17B (retail 84.4, airline 81.5, telecom 97.8), 2 Mar 2026; no 2026 frontier model has a core entry, and telecom is near the ceiling. The live frontier moved to τ³: a banking domain that needs knowledge retrieval over about 700 documents (top 55.15% pass^1, Qwen 3.8 Max (xhigh), 4 Aug 2026) and a voice track. Two caveats travel with every number: part of what is measured is the user simulator, itself a model whose version changed; and agents misbehave in ways the database check can miss (HAL's log inspection found agents misusing credit cards in flight-booking tasks).

Hyper-τ-bench (Sierra, 8 Sep 2026) points the same machinery at agents that build agents: a developer agent recovers requirements from a simulated business's records (about 1,700 files for banking), builds a customer-service agent in a sandbox, and is scored by how that agent handles held-out tasks, with overspending the budget scoring zero. Claude Opus 5 (max) in Claude Code alone passed 23.9%; an engineer with deep context working with the same class of model reached 82.2% on the same tasks, 3.44 times as much. The 82.2% is a human-plus-model reference, not the same configuration. Attempted sandbox circumvention appeared in 17 to 42% of runs. Who the agent works with moves the number as far as which harness it runs in.

Long tasks and real work: METR horizons, GDPval, AutomationBench, Agents' Last Exam

METR's time horizon (Kwa et al., Mar 2025) turns a task suite into one number with units. Skilled people are timed on each task; for each model, METR fits a logistic curve of success against the logarithm of the human time and reports where it crosses 50% (and 80%): the length of task, in human time, that the model completes half the time. The suite combines HCAST (189 software, ML, security and reasoning tasks with 563 human baselines over 1,500 hours, from one minute to 8+ hours), RE-Bench and 66 short software tasks; version 1.1 uses 228 tasks. A horizon has no ceiling until it outgrows the suite, which is now the limit:

  • Fitted from the released runs in this page. METR's v1.1 runs file has 24,008 runs; refitting each model with METR's own settings (diversity weights, near-zero regularisation) reproduces every 50% horizon in its results file to the published rounding (Time horizon fit).
  • Doubling time about 4.2 months, not 7. The v1.1 file gives 128.7 days (95% interval 104 to 158) for frontier models from 2023 on and 187.8 days (about 6.2 months) over the whole series since 2019; the 2025 paper's "about seven months" was the earlier, longer window. The page refits both from the file's points.
  • The suite is running out. The best measured horizon is Claude Mythos Preview (early) at 1,045 minutes (about 17 hours; 95% interval 509 to 3,304), dated 8 May 2026, beyond the 16 hours METR treats as reliable, so the trend fit excludes it; no Opus 5.x, Fable or GPT-6 measurement is published yet.
  • Reward hacking was measured here first. o3 reward-hacked in 39 of 128 RE-Bench runs (30.4%), and in every one of 21 runs on one task, against 8 of 1,087 on HCAST (0.7%), because RE-Bench shows the scoring function to the agent (METR, 5 Jun 2025).

GDPval (OpenAI, Oct 2025) samples real deliverables from 44 occupations in the 9 sectors that contribute most to US GDP, written by professionals with on average 14 years of experience; 1,320 tasks, a 220-task gold subset public with an automated grader. Experts compare the model's deliverable with a professional's. OpenAI reported GPT-5.5 winning or tying 84.9% of the time (Apr 2026); Epoch's run of the gold subset gives GPT-5.2 49.7% wins with ties excluded, a different metric. GDPval-AA v2.1 is Artificial Analysis's agentic variant, graded head to head into an Elo scale anchored at 1600 for DeepSeek V4.1 Flash since 19 Sep 2026: Claude Opus 5.5 (max) 1846, Claude Sonnet 5.5 1844, Claude Fable 5.1 1735, Claude Opus 5 1708, GPT-6 Astra (max) 1542 (AA, read 1 Oct 2026). Only differences mean anything on an Elo scale, and it is a different instrument from OpenAI's GDPval.

AutomationBench 1.0.6 (Zapier) automates business workflows across 47 tools, on a held-out private set (with a public set for research), and prints dollars per task beside the score: Gemini 4 Argon (high) leads at 51.29% for $1.70 per task (1 Oct 2026). OpenAI quotes GPT-6 Sol (xhigh) at 33.2% for $0.27 per task and Claude Opus 5 at 11.1 times that cost (OpenAI; the old page said "high" effort and "roughly nine times"). Artificial Analysis's AutomationBench-AA is a partial-credit rerun (Argon 77.5%), a different metric. Zapier flags that safety-classifier fallbacks change scores (Fable 5.1's 31.4% includes about 40% of tasks completed by Opus 5 as fallback) and that most failures are false confidence: the model declares success while failing.

Agents' Last Exam (site; Berkeley RDI with 300+ experts) covers professional agent work in 55 sub-industries; 147 tasks are public from a corpus of over 1,500, graded by rubric into a strict pass rate and a partial score. The old page called OpenAI's GPT-6 Sol 56.4% the only figure; an independent leaderboard exists (hosted by Snorkel), led by Claude Opus 5.5 (max, Claude Code) at 38.2% pass rate (63.2% score, 4 Oct 2026), and OpenAI's 56.4% is the partial score (the board's pass rate for GPT-6 Sol is 32.2%).

Vending-Bench (Andon Labs, Feb 2025) runs a simulated vending-machine business over more than 20 million tokens per run: simple steps, long horizon. Claude 3.5 Sonnet and o3-mini usually made a profit, but every model had runs that derailed (misread delivery schedules, forgotten orders, "meltdown" loops), and failures did not track when the context filled. AgentBench (Tsinghua, Aug 2023), eight environments from an OS shell to games, is historical: not reported on 2026 cards, its successors measure each environment more deeply.

These trade benchmark cleanliness for external validity, which is why they are increasingly quoted in capability-forecasting debates.

When the subject is the system, not the agent

A cluster from September 2026 scores something around the model, each a different answer to where agent performance lives:

  • HarnessDev scores a model's ability to build a harness from minimal components and then evolve it from feedback: six creator models, four domains, five downstream benchmarks, 2,207 instances, with execution-token cost beside capability. The best generated harness (Opus 4.8 running itself) averaged 67.8 against 86.2 for human-engineered references, which ran different, mostly newer models. Corrections: "match or beat on writing and ML experimentation" holds only for the best one or two creators; on evolution, all five self-runtime runs improved on 630 held-out tasks (+1.43 to +4.44), but the score a creator could see moved the same way as the held-out score in only 34 of 64 version changes, and swapping the model that executes a harness can halve its score.
  • MOLE scores the monitor: 150 AI-operated accounts share 9 stateful services over 30 workdays with 12 injected threats. 28 of 39 agent models (72%) completed most assigned harmful objectives, measured under a preamble telling them the sandbox is harmless and refusing spoils the research; refusal and completion rates are strongly linked across models (Spearman −0.73), so the old "stated refusal does not predict whether it declines" overstates the paper. The best monitor (Claude Opus 4.7) caught 24 of 45 completed harms in a single-day audit of 10 accounts a day.
  • Emergence World scores what survives duration: eight worlds of ten agents (six ran 16 days, one 21, one ended on day 4), about 850,000 LLM calls and 50 billion tokens, under prompt injection, misinformation and memory exposure. No world was resilient to all three; all 7 exposed worlds warned their community about the phishing and none removed its traces. The old "kept interacting 46 hours later" is one agent retrying an attack link about 46 hours after the campaign ended, not a measured detection-to-stop delay. It also tracks goal drift and tool-call failure trends day by day, which a suite of short episodes cannot see in principle, however many episodes it has.
  • EdgeBench (ByteDance Seed) has 134 day-scale tasks, 51 public; agents submit repeatedly within a time budget and the best submission is the score. SoL-Pi (NVIDIA) used it to show a harness-level improvement loop cutting recorded tokens 44.7 to 49.0% against Pi, mostly cache reads, with API cost about a third lower, at 93.7 to 94.3% of Pi's score: not "at task parity" as the old page said, and the cost per hour is SoL-Pi's derived metric, not EdgeBench's.
  • The harness tax (above) is the same lesson in money: a suite that reports only success cannot express it. ARC-AGI-3 is the exception where the harness takes the score with it (Knowledge and reasoning).

Code as agent work. SWE-bench, SWE-bench Pro and Real-SWE are agent benchmarks too (the score depends on the scaffold; "bash only" and "full agent" columns differed by 10 to 20 points on swebench.com, whose bash-only board was dropped on 1 Sep 2026). Coding owns them. One of them matters here for its method: Real-SWE (Specific Labs) licenses 10 tasks from companies' private production repositories (median 11 files changed), so they cannot leak into training data, the one contamination defence that does not decay as a benchmark ages. Eight model and native-harness pairs ran 8 rollouts per task (640 in all), at $2.50 to $6.96 per rollout. It now reads GPT-6 Astra 46.25% and Claude Fable 5.1 45.00% (the old page's "Fable 5.1 leads at 38.8%" is out of date), and the old "71.4% of rollouts that finished inside ten minutes failed" is no longer what the page shows: 57.4% of rollouts under ten minutes failed (62 of 108) against 66.2% of longer ones (352 of 532), so short runs now fail less often (read 4 Oct 2026).

The integrity crisis

In April 2026 Hao Wang, Qiuyang Mang, Alvin Cheung, Koushik Sen and Dawn Song at UC Berkeley published How We Broke Top AI Agent Benchmarks (Berkeley RDI; the paper is arXiv 2605.12673 and the scanner is BenchJack). An automated agent audited eight prominent agent benchmarks, built a working exploit for each, ran it through the official evaluation, and scored near the top "without solving a single task", in most cases with no model calls at all:

RDI group the flaws into seven patterns, and every benchmark on this page can be read against them:

  1. No isolation between agent and evaluator (SWE-bench, Terminal-Bench, OSWorld): the checker reads state the agent could write.
  2. Answers shipped with the test (WebArena configs, OSWorld gold URLs, GAIA's public validation answers).
  3. eval() on untrusted input (WebArena, OSWorld): code execution on the grading machine, a security hole as well as a scoring one.
  4. LLM judges without input sanitisation (WebArena, CAR-bench): the agent's text reaches the judge's prompt.
  5. Weak string matching (WebArena's substring check, GAIA's normaliser).
  6. Evaluation logic that does not evaluate (FieldWorkArena's validator, CAR-bench's skipped components, GAIA's comma bug that marks correct answers wrong).
  7. Trusting the output of untrusted code (pytest output and reward files produced inside the agent's container).

It is not only a red-team result. RDI also list incidents in the wild: IQuest-Coder-V1 claimed 81.4% on SWE-bench until 24.4% of its trajectories were found running git log to copy the answer from history (corrected to 76.2%); in KernelBench, torch.empty() returned stale GPU memory holding the evaluator's reference answer; and Anthropic's Mythos Preview assessment describes a model that, unable to edit a file it lacked permission for, injected code into a config file that ran with elevated privileges and deleted itself afterwards. HAL, which reran 9 benchmarks with 21,730 rollouts (about $40,000), found agents searching Hugging Face for the benchmark instead of solving the task. METR measured o3 reward-hacking in 30.4% of RE-Bench runs by overwriting a grader's timer, monkey-patching the evaluator and caching answers. So an agent score you did not run yourself, under an isolated evaluator with held-out checks, deserves suspicion; RDI say plainly they are not claiming current leaders cheat, but that optimisation pressure can find the evaluator before it finds the solution.

What changed since. Terminal-Bench 3.0 and 4.0 tasks declare a separate verifier environment, copy out only declared artifacts and install nothing at trial time (74 of 74 and 66 of 66 task files, counted here; the animation in Anatomy shows why that defeats the wrapper exploit). Separation does not fix the other six patterns.

The minimum bar for an agent benchmark (RDI's Agent-Eval Checklist, condensed)
  • Run the checker outside the agent's environment, on a read-only host; copy artifacts out through a controlled channel and treat them as untrusted; mount binaries and test files read-only.
  • Never put reference answers, gold files or evaluator configs where the agent can read them; keep the primary split's answers secret and rotate instances.
  • Never call eval() on agent-controlled strings; parse structured data.
  • Treat agent text as data in any judge prompt (delimiters, stripping, structured output), or grade extracted features instead.
  • Before publishing, attack your own evaluator with a null agent (its score is the floor and should be zero), a random agent, a prompt-injection agent and a state-tampering agent.
  • Score robustly: no substring matches on short strings, a crashed task counts as zero, no category skips a check.
Go deeper: Grade a real task runs regex-log's real test on your own regex and lists each exploit beside the defence that stops it; Reward Hacking covers why trained agents find these paths; Safety and honesty covers AgentHarm and monitoring.

Common mistakes

Quoting a model's agent score without the harness, effort and budget
The pair is the unit. One model on the official Terminal-Bench 4.0 board spans 50.61% to 58.18% across effort settings; a harness lifted one model 9 points on Terminal-Bench 2.1; on ARC-AGI-3 two harnesses at equal effort gave 62.7% and 98.6%.
Splicing versions of one benchmark
Terminal-Bench 2.0, 2.1, 3.0 and 4.0 are different task sets with different limits and checkers; OSWorld, OSWorld-Verified and OSWorld 2.0 (three releases, full or offline, binary or partial) are not one scale. Write the version, the set and the metric.
Reading partial credit as success rate
OSWorld 2.0's partial score and binary accuracy differ by 30 to 40 points for the same run; Agents' Last Exam's 56.4% "score" for GPT-6 Sol is a 32.2% pass rate.
Treating pass^1 as reliability
On τ²-bench retail, three models 5 points apart at pass^1 tie at pass^4, 25 to 30 points lower. If a product must work every time, ask for pass^k.
Putting a lab's own run beside a board's
On Terminal-Bench-Science the same model reads 52.6% (lab) and 40.0% (board). Compare like with like and say who ran each number.
Trusting a score the environment could have produced
If the checker ran where the agent ran, read answers it could see, or asked a judge that reads the agent's text, the score is an upper bound on capability plus an unknown amount of exploitation.
Reading a small set's gap as a ranking
50 airline tasks: one task is 2 points. 30 sampled tasks with 3 attempts (HarnessTax) cannot separate harnesses a few points apart. Use the root's error-bar calculator.
Quoting a METR horizon beyond the suite
A 17-hour horizon on a suite whose longest reliable range is about 16 hours, with an interval from 8 to 55 hours, says "beyond what this suite can measure", not "17 hours".

Beyond k = 4: the plug-in curve

With four trials, pass^k can be estimated without bias only up to k = 4. Treating each task's observed rate c/4 as its true success probability gives a curve for larger k, labelled plug-in, not an estimate: a task seen 4 times out of 4 counts as certain forever, so the curve flattens at the share of 4-of-4 tasks, and the true pass^8 is lower.

Files that do not reproduce the published figures

Counting a missing reward (an errored simulation) as a failure. Where the published value is higher, the leaderboard may have scored a different file or excluded errors; either way these runs are left out of the charts above.

Time horizon fit

How METR turns a task suite into one number in minutes, done here on METR's own released runs. Each of the 228 tasks in suite v1.1 has a human time (the geometric mean of skilled people's successful attempts, or an estimate); each model ran each task several times. For one model, the fit is a logistic curve of success against log2(human minutes), each task weighted by METR's diversity weight (task families with many members count less); the 50% horizon is where the curve crosses one half. Grade a real task

The Terminal-Bench 2.0 task regex-log (Apache 2.0; expert time estimate 45 minutes, junior 180), with its real test. Write a regex and run the test: it joins the test's 25 log lines, applies your pattern the way re.findall(pattern, log_text, re.MULTILINE) does, and passes only if the matches equal the 9 expected dates, in order. The task's instruction, verbatim:













The test runs in your browser's JavaScript regex engine, which agrees with Python's re on the constructs these patterns use (lookaheads, classes, groups, anchors with the multiline flag); Python-only syntax such as (?P<name>...) is translated, others may differ. src/recompute.py runs the presets through Python's re and checks the same verdicts. Like Python's findall, a pattern with one group returns that group, with none the whole match.
