5. The integrity crisis

In April 2026 Hao Wang, Qiuyang Mang, Alvin Cheung, Koushik Sen and Dawn Song at UC Berkeley published {{How We Broke Top AI Agent Benchmarks|https://rdi.berkeley.edu/blog/trustworthy-benchmarks-cont/}} (Berkeley RDI; the paper is {{arXiv 2605.12673|https://arxiv.org/abs/2605.12673}} and the scanner is {{BenchJack|https://github.com/benchjack/benchjack}}). An automated agent audited eight prominent agent benchmarks, built a working exploit for each, ran it through the official evaluation, and scored near the top "without solving a single task", in most cases with no model calls at all. RDI group the flaws into seven patterns (numbered in the table), and every benchmark on this page can be read against them: 1 no isolation between agent and evaluator (the checker reads state the agent could write); 2 answers shipped with the test; 3 eval() on untrusted input (code execution on the grading machine, a security hole as well as a scoring one); 4 LLM judges without input sanitisation (the agent's text reaches the judge's prompt); 5 weak string matching; 6 evaluation logic that does not evaluate; 7 trusting the output of untrusted code (pytest output and reward files produced inside the agent's container).

It is not only a red-team result: the same paths turn up in real runs, and optimisation pressure can find the evaluator before it finds the solution. RDI say plainly they are not claiming current leaders cheat; but an agent score you did not run yourself, under an isolated evaluator with held-out checks, deserves suspicion. Why trained agents find these paths is {{Reward Hacking|n:3c65c17b0d0d8196a6f1f29a817aa974}}'s subject.

Incidents in the wild: IQuest-Coder-V1, KernelBench, Mythos Preview, HAL, METR

RDI list incidents outside their audit: IQuest-Coder-V1 claimed 81.4% on SWE-bench until 24.4% of its trajectories were found running git log to copy the answer from history (corrected to 76.2%); in KernelBench, torch.empty() returned stale GPU memory holding the evaluator's reference answer; and Anthropic's Mythos Preview assessment describes a model that, unable to edit a file it lacked permission for, injected code into a config file that ran with elevated privileges and deleted itself afterwards. HAL found agents searching Hugging Face for the benchmark instead of solving the task. {{METR|https://metr.org/blog/2025-06-05-recent-reward-hacking/}} measured o3 reward-hacking in 30.4% of RE-Bench runs by overwriting a grader's timer, monkey-patching the evaluator and caching answers.

What changed since. Terminal-Bench 3.0 and 4.0 tasks declare a separate verifier environment, copy out only declared artifacts and install nothing at trial time (74 of 74 and 66 of 66 task files, counted here). Separation does not fix the other six patterns.

The minimum bar for an agent benchmark (RDI's Agent-Eval Checklist, condensed)
  • Run the checker outside the agent's environment, on a read-only host; copy artifacts out through a controlled channel and treat them as untrusted; mount binaries and test files read-only.
  • Never put reference answers, gold files or evaluator configs where the agent can read them; keep the primary split's answers secret and rotate instances.
  • Never call eval() on agent-controlled strings; parse structured data.
  • Treat agent text as data in any judge prompt (delimiters, stripping, structured output), or grade extracted features instead.
  • Before publishing, attack your own evaluator with a null agent (its score is the floor and should be zero), a random agent, a prompt-injection agent and a state-tampering agent.
  • Score robustly: no substring matches on short strings, a crashed task counts as zero, no category skips a check.

6. Reading a reported agentic score

Eight questions, each with the case on this page that shows why it matters:

  1. Which version, task set and metric? (binary, partial, pass^1, pass^k, Elo; full, offline, public, held-out)Terminal-Bench 2.0, 2.1, 3.0 and 4.0 are different task sets with different limits and checkers; OSWorld, OSWorld-Verified and OSWorld 2.0 (three releases, full or offline, binary or partial) are not one scale. Partial and binary differ by 30 to 40 points for the same OSWorld 2.0 run; Agents' Last Exam's 56.4% "score" for GPT-6 Sol is a 32.2% pass rate.
  2. Who ran it: the official board, an independent rerun, or the lab?On Terminal-Bench-Science the same model reads 52.6% (lab) and 40.0% (board). Compare like with like and say who ran each number.
  3. Which harness, effort, and time and step budget?The pair is the unit: nine agents moved one model 18 points on Terminal-Bench 2.0; effort moves GPT-6 Astra from 50.61% to 58.18% on the 4.0 board; on ARC-AGI-3 two harnesses at equal effort gave 62.7% and 98.6%.
  4. How many trials per task, and how many tasks?50 airline tasks: one task is 2 points. On τ²-bench retail, three models 5 points apart at pass^1 tie at pass^4, 25 to 30 points lower. Error bars for a given task count are {{Eval statistics|n:3ef5c17b0d0d8187a7b4e5b4ec4a546d}}' subject.
  5. Is the checker isolated from the agent, and are the answers hidden?If the checker ran where the agent ran, read answers it could see, or asked a judge that reads the agent's text, the score is an upper bound on capability plus an unknown amount of exploitation.
  6. Is there a simulated user or a judge model in the loop, and which version?τ²-bench changed its user simulator from GPT-4.1 to GPT-5.2; MCP Atlas, Mind2Web 2 and GDPval-AA grade with models.
  7. Is the board still maintained, and does the comparison use the same date's entries?MCP-Universe and MCPMark stopped in 2025; τ²-bench's core board has no 2026 frontier model; METR's page is no longer actively updated.
  8. Is there a cost beside the score?The same answer can cost twice as much in one harness as another (HarnessTax); AutomationBench and the Terminal-Bench 4.0 board print dollars per task or per run.
