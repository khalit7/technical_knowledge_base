In one screen

An agentic benchmark gives a model tools and an environment (a shell, a desktop, a website, a simulated customer, a set of protocol servers), lets it act for many steps, and then a checker inspects what changed. What it scores is not a completion but a system: the model, the harness (the program that runs the loop, holds the context and exposes the tools), the effort setting, the time and step budget, and the environment itself.

Three consequences run through everything below:

1. The number belongs to a system

Change the harness, the effort or the time limit and the same weights score differently. On ordinary tasks the harness mostly moves the bill (about 2× between harnesses at equal success, {{Arena, 16 Sep 2026|https://arena.ai/blog/coding-agents-harness-tax}}); on some it moves the score by tens of points.

2. Best case is not reliability

A task solved once in four tries counts toward pass@k but not toward pass^k, the chance that all k tries succeed. On real τ²-bench trials pass^4 is 15 to 30 points below pass^1 (computed in this page).

3. The environment can be attacked

In April 2026 an exploit agent from {{Berkeley RDI|https://rdi.berkeley.edu/blog/trustworthy-benchmarks-cont/}} reached near-perfect scores on eight agent benchmarks without solving a task, by editing what the checker reads or reading the answers it ships with.

Anatomy of an agent benchmark

Every agent benchmark is four parts, and each part is a place where the number can go wrong:

Environment

What the agent acts on: a Docker container (Terminal-Bench, SWE-bench), a virtual machine (OSWorld), self-hosted websites (WebArena), databases behind tool APIs (τ²-bench), live servers (MCP-Universe), the open web (GAIA, BrowseComp). Self-hosted means reproducible; live means realistic but drifting.

Task

An instruction plus an initial state, and the limits: time, steps, CPU and memory. Limits are part of the task: Terminal-Bench 4.0 changed them and called it a new major version.

Agent

Model plus harness plus settings. Leaderboards list the pair (Terminal-Bench, Real-SWE) or fix the harness (HAL, METR); vendor tables use their own.

Checker

What decides success: tests on the end state, a match against a hidden answer, a database comparison, a rubric, a judge model, or an expert. The checker is the benchmark's real definition of the task.

Checkers come in five kinds, from most to least mechanical:

CheckerUsed byWhat it misses
Tests or scripts on the final stateTerminal-Bench, OSWorld, WebArena (partly), SWE-bench, MCPMarkAnything the tests do not probe; and if the tests run where the agent ran, the agent can edit them

One real task, three runs

The task below is real: {{regex-log|https://github.com/harbor-framework/terminal-bench-2/tree/main/regex-log}} from Terminal-Bench 2.0 (Apache 2.0). The agent must write a regular expression that finds the last date on each log line that contains a valid IPv4 address, and save it to /app/regex.txt. Its checker, tests/test.sh, installs curl, downloads the uv installer with curl ... | sh, runs pytest on 25 log lines that must yield exactly 9 dates, and writes 1 or 0 to /logs/verifier/reward.txt. Run it three ways: an honest agent, Berkeley RDI's exploit on the 2.0 layout, and the same exploit against the separate verifier container that Terminal-Bench 3.0 and 4.0 tasks declare.

The files, commands and test are verbatim from the task's repository (read 4 Oct 2026); the exploit steps follow {{Berkeley RDI|https://rdi.berkeley.edu/blog/trustworthy-benchmarks-cont/}}, who report it on all 89 tasks (82 through the curl step shown here, the other 7 by wrapping pip, python or a preinstalled uvx). The third run is illustrative: regex-log is a 2.0 task, drawn here under the verifier layout that every one of the 74 Terminal-Bench 3.0 and 66 4.0 task files declares (environment_mode = "separate", artifacts copied out, nothing installed at trial time; counted in this page from the {{3.0 and 4.0 task files|https://github.com/harbor-framework/terminal-bench/tree/v4.0.0/tasks}}). RDI did not test 3.0 or 4.0. You can grade your own regex against the real test in Grade a real task.

What the animation shows is the most common root cause in RDI's audit: the checker trusted something the agent could touch. Harbor, the harness, re-uploads the protected /tests/ folder before verification, but the verifier then used the container's own curl. Counted from the {{terminal-bench-2 repository|https://github.com/harbor-framework/terminal-bench-2}} in this page, 82 of the 89 tasks' test.sh files fetch the uv installer with curl at verification time, which matches RDI's count independently.
