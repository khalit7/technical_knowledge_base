1. How an agent benchmark is built and checked

Take one real task, {{regex-log|https://github.com/harbor-framework/terminal-bench-2/tree/main/regex-log}} from Terminal-Bench 2.0 (Apache 2.0). The task is an instruction plus an initial state plus limits: write a regular expression that finds the last date on each log line containing a valid IPv4 address, save it to /app/regex.txt, within 900 seconds, 1 CPU and 2 GB. The environment is a Docker container with a shell. The checker, tests/test.sh, installs curl, downloads the uv installer with curl ... | sh, runs pytest on 25 log lines that must yield exactly 9 dates, and writes 1 or 0 to /logs/verifier/reward.txt. The score is the share of tasks whose reward file says 1. Step through three runs: an honest agent, Berkeley RDI's exploit on the 2.0 layout, and the same exploit against the separate verifier that Terminal-Bench 3.0 and 4.0 tasks declare.

A reward of 1 is evidence of a solution only if the agent could not touch what the checker runs

Files, commands and test verbatim from the task's repository (read 4 Oct 2026); exploit steps follow {{Berkeley RDI|https://rdi.berkeley.edu/blog/trustworthy-benchmarks-cont/}}, who report it on all 89 tasks (82 through the curl step shown, the other 7 by wrapping pip, python or a preinstalled uvx). The third run is illustrative: regex-log is a 2.0 task, drawn under the layout that every one of the 74 Terminal-Bench 3.0 and 66 4.0 task files declares (environment_mode = "separate", artifacts copied out, nothing installed at trial time; counted in this page from the {{3.0 and 4.0 task files|https://github.com/harbor-framework/terminal-bench/tree/v4.0.0/tasks}}). RDI did not test 3.0 or 4.0.

The root cause is the commonest in RDI's audit: the checker trusted something the agent could touch. Harbor, the harness, re-uploads the protected /tests/ folder before verification, but the verifier then used the container's own curl. Counted from the {{terminal-bench-2 repository|https://github.com/harbor-framework/terminal-bench-2}} in this page, 82 of the 89 tasks' test.sh files fetch the uv installer with curl at verification time, which matches RDI's count independently.

Grade your own regex against regex-log's real test (the task's instruction, presets, a per-line verdict)

Expert time estimate 45 minutes, junior 180. The test joins the 25 log lines, applies your pattern the way re.findall(pattern, log_text, re.MULTILINE) does, and passes only if the matches equal the 9 expected dates, in order. The instruction, verbatim:













The test runs in your browser's JavaScript regex engine, which agrees with Python's re on the constructs these patterns use (lookaheads, classes, groups, anchors with the multiline flag); Python-only syntax such as (?P<name>...) is translated, others may differ. src/recompute.py runs the presets through Python's re and checks the same verdicts. Like Python's findall, a pattern with one group returns that group, with none the whole match.




Every agent benchmark has the same four parts as this task, and each can move the number. Environments range from a Docker container (Terminal-Bench, SWE-bench), a virtual machine (OSWorld), self-hosted websites (WebArena) and databases behind tool APIs (τ²-bench) to live servers (MCP-Universe) and the open web (GAIA, BrowseComp): self-hosted means reproducible, live means realistic but drifting. Limits are part of the task: Terminal-Bench 4.0 changed them and called it a new major version. The agent is model plus harness plus settings: leaderboards list the pair (Terminal-Bench, Real-SWE) or fix the harness (HAL, METR); vendor tables use their own. 2. Best case or reliability: pass@k against pass^k


Agents are sampled, so the same task can pass on one try and fail on the next. The {{τ-bench paper (Yao et al., 2024)|https://arxiv.org/abs/2406.12045}} showed what that does to a customer-service agent: gpt-4o as a function-calling agent passed 61% of retail tasks once, but the chance of passing the same task eight times out of eight, pass^8, fell to about 25% (abstract and section 5). Below are real released trials: GPT-5.2 (high) on τ²-bench's 114 retail tasks, four trials each, from the trajectory file Sierra published with its leaderboard submission (26 Feb 2026, user simulator GPT-5.2). Every value is computed in the page from those 456 trials and lands on the leaderboard's published 81.58 / 69.59 / 59.87 / 51.75 exactly.




The drop from pass^1 to pass^4 is set by the middle columns: tasks solved sometimes













Each square is one task, placed in the column of how many of its 4 trials succeeded; its fill is the task's contribution to the metric at the current k. Only runs whose released file reproduces the published figures exactly are offered (27 of 36 files checked; the others are listed in the closed block below).




Run every task n times and count its successes c. The two summaries answer opposite questions:


pass@k = mean over tasks of [ 1 − C(n−c, k) / C(n, k) ]     pass^k = mean over tasks of [ C(c, k) / C(n, k) ]


pass@k
chance that at least one of k tries succeeds: the best case, the metric of code benchmarks since Codex
pass^k
chance that all k tries succeed: reliability, introduced by τ-bench for agents that must act correctly every time a customer calls
C(a, b)
binomial coefficient; both estimators are unbiased for k ≤ n. At k = 1 both equal the mean success rate.


On real τ²-bench trials pass^4 is 15 to 30 points below pass^1. A task solved 3 times in 4 counts 0.75 toward pass^1 and nothing toward pass^4, so a model whose failures are spread thinly across many tasks falls hardest. And pass@k flatters: the same GPT-5.2 run reaches 96.49% at pass@4, so "solved at least once" and "solved every time" differ by 45 points. Because the drop depends on how failures are spread, rankings change with k. Predict before you move the slider: on retail, GPT-5.2 (81.58), Claude Opus 4.5 (79.61) and Gemini 3 Flash (76.75) differ by five points at pass^1. What happens at pass^4?




Rankings at pass^1 are not rankings at pass^4






Every reproduced τ²-bench run in the chosen domain, recomputed from its trajectory file (submissions in {{sierra-research/tau2-bench|https://github.com/sierra-research/tau2-bench/tree/main/web/leaderboard/public/submissions}}, MIT, read 4 Oct 2026). On retail at k = 4 the three runs tie exactly at 51.75: each solved 59 of 114 tasks four times out of four. On airline, Opus 4.5 leads at pass^1 (84.0 against 83.0) and GPT-5.2 at pass^4 (72.0 against 70.0); with 50 tasks that is one task either way, inside the noise.




Other boards report the same split. {{MCPMark|https://arxiv.org/abs/2509.24002}} launched with gpt-5 (medium) at 52.56% pass@1 and 33.86% pass^4; its board's last top entry is GPT-5.2 (high) at 57.5% pass@1 and 44.9% pass^4 ({{MCPMark leaderboard|https://mcpmark.ai/leaderboard}}, updated 15 Dec 2025). The {{Terminal-Bench 4.0 board|https://www.tbench.ai/leaderboard}} runs every pair 5 times per task and prints pass@5 beside the mean: GPT-6 Astra (max) in Codex 58.18% mean and 71.2% pass@5, Claude Fable 5.1 (max) in Claude Code 57.88% and 78.8%, so the order flips depending on which you read. If a product must work every time, ask for pass^k.

Beyond k = 4: the plug-in curve


With four trials, pass^k can be estimated without bias only up to k = 4. Treating each task's observed rate c/4 as its true success probability gives a curve for larger k, labelled plug-in, not an estimate: a task seen 4 times out of 4 counts as certain forever, so the curve flattens at the share of 4-of-4 tasks, and the true pass^8 is lower.
