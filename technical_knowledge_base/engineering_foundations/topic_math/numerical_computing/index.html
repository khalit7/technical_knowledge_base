A computer stores a real number as a sign, a power of two and a fixed number of binary digits. So it can only hold numbers from a finite grid: the grid is dense near zero and sparse far away, every result is snapped to the nearest grid point, and the grid ends (past it lies infinity). The one idea to keep
Every floating-point result is the true result times (1+δ)(1 + \delta) with |δ||\delta| at most half the format's epsilon, as long as nothing overflows or underflows. Trouble comes from three places only: leaving the range (overflow to infinity, underflow to zero), subtracting nearly equal numbers (cancellation), and piling up many small errors (long sums). Stable algorithms are rearrangements that avoid all three.

1. How a computer stores a number

The question. A memory cell holds only 0s and 1s. How do you get from a row of bits to −13-13, to 0.10.1, to 3×10383 \times 10^{38}?

Binary: place values are powers of two

In decimal, 413413 means 4×100+1×10+3×14 \times 100 + 1 \times 10 + 3 \times 1: each place is worth ten times the place to its right. In binary each place is worth twice the place to its right, and each digit (a bit) is 0 or 1. So

11012=1×8+1×4+0×2+1×1=13.1101_2 = 1 \times 8 + 1 \times 4 + 0 \times 2 + 1 \times 1 = 13.

The subscript 2 says "read in base 2". Places to the right of the binary point are worth 12,14,18,…\tfrac12, \tfrac14, \tfrac18, \dots, so 0.1012=12+18=0.6250.101_2 = \tfrac12 + \tfrac18 = 0.625. A fraction has a finite binary expansion only if its denominator is a power of two. 110\tfrac{1}{10} is not, so in binary it repeats forever, 0.1=0.0001120.1 = 0.0\overline{0011}_2, exactly as 13=0.333…\tfrac13 = 0.333\ldots repeats in decimal. Any computer that stores a fixed number of bits must cut 0.10.1 off somewhere; that cut is the first rounding error you meet, and it is why 0.1+0.20.1 + 0.2 prints as 0.30000000000000004 in Python (measured).

Integers and two's complement

An unsigned 8-bit integer holds 00 to 28−1=2552^8 - 1 = 255. For negative numbers, every modern machine uses two's complement: the top bit is worth −27=−128-2^{7} = -128 instead of +128+128. So an 8-bit signed integer (int8) holds −128-128 to 127127, and

−13=111100112=−128+64+32+16+2+1.-13 = 11110011_2 = -128 + 64 + 32 + 16 + 2 + 1.

The trick that makes it popular: adding works with the same circuit as unsigned addition, and negating is "flip every bit, add 1" (13=00001101213 = 00001101_2, flipped 11110010211110010_2, plus one 11110011211110011_2). The price is that integers wrap around: in int8, 127+1=−128127 + 1 = -128 (derived; NumPy does the same and warns). Integers are exact inside their range and evenly spaced, which is why quantised weights are stored as int8 or int4 codes with a separate scale (the Quantization and precision page).

Why integers are not enough: the floating point idea

ML needs both 3×10−83 \times 10^{-8} (a typical small gradient) and 5×1045 \times 10^{4} (a large activation) in the same tensor. An evenly spaced grid fine enough for the first needs about 101210^{12} steps to reach the second, about 41 bits, and it would waste nearly all of them on precision nobody needs at large values. The fix is scientific notation in base 2: store a number as

x=(−1)s×m×2E,1≤m<2.x = (-1)^{s} \times m \times 2^{E}, \qquad 1 \le m \lt 2 .

Read it as: a sign ss (0 for plus, 1 for minus), a significand mm (also called the mantissa: the digits, always between 1 and 2), and an exponent EE (an integer: which power of two). Example: 13=1.625×2313 = 1.625 \times 2^{3} because 1.625×8=131.625 \times 8 = 13, and in binary 11012=1.1012×231101_2 = 1.101_2 \times 2^{3}: moving the binary point three places is multiplying by 232^3. The point "floats" to just after the first 1, hence floating point. With a fixed number of bits for mm, every number carries the same number of significant binary digits whatever its size: the gaps between neighbours grow in proportion to the number. That proportional grid is the whole design.

What it is used for in ML
Every weight, activation and gradient is a floating-point number; token ids, counts and quantised codes are integers. Integer wraparound appears in practice when an int32 index overflows past 231−1≈2.1×1092^{31} - 1 \approx 2.1 \times 10^{9} elements, the size of a single large embedding or attention tensor.

2. IEEE 754, bit by bit

The question. The root page's loss is 2.4076…2.4076\ldots. Which 32 bits does PyTorch store for it, and how do you read them back?

The standard that fixes the answer is IEEE 754, first published in 1985 and revised in 2008 and 2019 (IEEE 754-2019; William Kahan, its main architect, received the 1989 Turing Award for it). Before it, every computer maker rounded differently and the same program gave different answers on different machines. It defines the formats, what every operation must return, and the special values. A 32-bit float (float32, fp32, "single precision") is three fields:

sign: 1 bitexponent field: 8 bitsfraction (mantissa) field: 23 bits
x=(−1)s×(1+f223)×2e−127(1≤e≤254)x = (-1)^{s} \times \Bigl(1 + \frac{f}{2^{23}}\Bigr) \times 2^{\,e - 127} \qquad (1 \le e \le 254)
ss
the sign bit: 0 for positive, 1 for negative.
ee
the 8-bit biased exponent field, read as an unsigned integer 0 to 255. The true exponent is E=e−127E = e - 127; 127 is the bias (28−1−12^{8-1} - 1). Storing E+127E + 127 instead of a signed EE makes the fields of positive floats sort in the same order as the numbers, so hardware can compare floats with integer comparisons.
ff
the 23-bit fraction field, read as an integer 0 to 223−12^{23} - 1. The leading 1 of the significand is not stored (every normal number has one, so it is free: the hidden bit). A float32 therefore carries p=24p = 24 significant bits, the format's precision.

Worked by hand, the loss in fp32. The exact loss is ln⁡(e2+e1+e0)=2.40760596444438…\ln(e^2 + e^1 + e^0) = 2.40760596444438\ldots (the root's tiny model, target sat). It lies between 21=22^1 = 2 and 22=42^2 = 4, so E=1E = 1 and the stored exponent is e=1+127=128=100000002e = 1 + 127 = 128 = 10000000_2. The significand is 2.4076…/2=1.2038…2.4076\ldots / 2 = 1.2038\ldots; its fractional part times 2232^{23} is 1,709,622.6…1{,}709{,}622.6\ldots, which rounds to f=1,709,623f = 1{,}709{,}623. Reading back: x=(1+1,709,623/8,388,608)×2x = (1 + 1{,}709{,}623 / 8{,}388{,}608) \times 2, which is 1.2038029432296753×21.2038029432296753 \times 2, which is 2.40760588645935062.4076058864593506. The stored value is off by 7.8×10−87.8 \times 10^{-8}, a relative error of 3.2×10−83.2 \times 10^{-8}. Python's standard library agrees: struct.pack('>f', loss).hex() gives 401a1637, which is the same 32 bits in hexadecimal (measured).

Why subnormals exist. Without them the gap between 0 and the smallest normal number, 2−1262^{-126}, would be 2232^{23} times wider than the gap just above it, so two different tiny numbers could subtract to exactly 0. With them, numbers fade to zero in equal steps of 2−1492^{-149} (gradual underflow), and x−y=0x - y = 0 only when x=yx = y (Goldberg 1991, its "Denormalized Numbers" subsection). The price is that a subnormal keeps fewer significant bits: 10−4010^{-40} in float32 has only 17 of them. Some hardware drops subnormals for speed (flush to zero): Google's TPU blog says "bfloat16 handles denormals differently from FP32: it flushes them to zero" (Wang and Kanwar 2019), and PyTorch's notes say AMD MI200's FP16 and BF16 matrix instructions "flush input and output denormal values to zero" (numerical accuracy notes, v2.14.1).

The NaN rules that matter in practice. NaN spreads: one NaN in a matrix multiply's input makes every output that touches it NaN, and one NaN in the loss makes every gradient NaN. x != x is true only for NaN, which is how torch.isnan works conceptually. And NaN compares false with everything, so loss > 10 is false for a NaN loss: a divergence check written that way never fires (use not torch.isfinite(loss)).

What it is used for in ML
Reading a dtype: torch.finfo(torch.float32) prints exactly these constants (eps, max, smallest_normal, tiny). Debugging: a NaN is a bit pattern with an all-ones exponent, so a tensor dump that shows 7fc00000 is a NaN and 7f800000 is +∞+\infty.

3. Gaps between floats, machine epsilon and rounding

The question. How close together are neighbouring floats, how wrong can one rounding make a number, and which way does a tie go?

The grid doubles its spacing every power of two

Between two consecutive powers of two, 2E2^E and 2E+12^{E+1} (one binade), a format with pp significant bits has exactly 2p−12^{p-1} evenly spaced values. The spacing there is one ulp ("unit in the last place"):

ulp⁡(x)=2E−(p−1)for 2E≤|x|<2E+1.\operatorname{ulp}(x) = 2^{\,E - (p - 1)} \quad \text{for } 2^E \le |x| \lt 2^{E+1} .

In words: the gap is the value of the last stored bit. For float32 (p=24p = 24) the gap is 2−232^{-23} between 1 and 2, 2−222^{-22} between 2 and 4, and 2−13≈1.2×10−42^{-13} \approx 1.2 \times 10^{-4} between 1024 and 2048. So float32 can tell 1000.0 from 1000.0001 but not from 1000.00001. Below the smallest normal number the spacing stops shrinking: subnormals are evenly spaced. Machine epsilon and unit roundoff

Machine epsilon ε\varepsilon is the gap between 1 and the next float: ε=2−(p−1)\varepsilon = 2^{-(p-1)}. The unit roundoff u=ε/2=2−pu = \varepsilon / 2 = 2^{-p} is the largest relative error of one rounding. Libraries report ε\varepsilon (torch.finfo(...).eps, numpy.finfo(...).eps, C's FLT_EPSILON); numerical analysis texts usually write uu (Higham 2002, chapter 2). Mixing them up is a factor of two.

Why one rounding costs at most uu relative error. Take xx with 2E≤|x|<2E+12^E \le |x| \lt 2^{E+1}. Neighbouring floats there are 2E−p+12^{E-p+1} apart, so the nearest one is at most half that away: |fl⁡(x)−x|≤2E−p|\operatorname{fl}(x) - x| \le 2^{E-p}. Divide by |x|≥2E|x| \ge 2^E:
|fl⁡(x)−x||x|≤2E−p2E=2−p=u.\frac{|\operatorname{fl}(x) - x|}{|x|} \le \frac{2^{E-p}}{2^{E}} = 2^{-p} = u .
Here fl⁡(x)\operatorname{fl}(x) means "xx rounded to the format". This holds for every xx in the normal range. Check on the loss: float32 3.2×10−8≤u=5.96×10−83.2 \times 10^{-8} \le u = 5.96 \times 10^{-8}; float16 2.4082031252.408203125, error 2.5×10−4≤2−11=4.9×10−42.5 \times 10^{-4} \le 2^{-11} = 4.9 \times 10^{-4}; bfloat16 2.406252.40625, error 5.6×10−4≤2−8=3.9×10−35.6 \times 10^{-4} \le 2^{-8} = 3.9 \times 10^{-3} (all derived from the bits above). In the subnormal range the bound fails: there the absolute error is at most half of the smallest subnormal, and the relative error can reach 100%.

A handy reading: pp bits are about plog10⁡2≈0.301pp \log_{10} 2 \approx 0.301\,p decimal digits. float64 carries about 16 digits, float32 about 7.2, float16 about 3.3 and bfloat16 about 2.4 (derived). bfloat16 cannot tell 256 from 257: both round to 256.

Round to nearest, ties to even

IEEE 754 requires every basic operation (+,−,×,÷, +, -, \times, \div, \sqrt{\ }, and the fused multiply-add) to return the exactly rounded result: compute as if with infinite precision, then round once. The default rounding mode is round to nearest, ties to even: pick the nearest float, and if the exact result sits exactly halfway between two, pick the one whose last bit is 0. Ties to even, rather than ties away from zero, avoids a systematic upward drift when many ties occur. Three measured examples in float16 and bfloat16:

Stochastic rounding

Nearest rounding is deterministic and, for a tiny repeated update, always wrong in the same direction. Stochastic rounding rounds up with probability equal to how far the exact value lies toward the upper neighbour: if xx sits a fraction tt of the way from aa to the next float bb, it returns bb with probability tt and aa otherwise, so on average it returns xx exactly (𝔼[SR⁡(x)]=(1−t)a+tb=x\mathbb{E}[\operatorname{SR}(x)] = (1 - t)a + tb = x). Example (derived): a bfloat16 weight 0.1070.107 sits where the gap is 2−11≈0.0004882^{-11} \approx 0.000488; an update of 10−410^{-4} is 0.2050.205 of a gap, so nearest rounding never moves the weight, while stochastic rounding moves it one gap up about one step in five and after 1,000 such updates the weight has moved about 0.10.1 in expectation, as it should. Gupta et al. trained networks with 16-bit fixed point "when using stochastic rounding" (Gupta et al. 2015); Zamirai et al. used it, and Kahan summation (section 7), to train in bf16 alone (Zamirai et al. 2020); NVIDIA's 4-bit pretraining recipe uses it on gradients "for unbiased gradient estimation" (NVIDIA 2025).

What it is used for in ML
Choosing a dtype is choosing ε\varepsilon: an update, a residual or a loss difference smaller than ε\varepsilon times the value it is added to is invisible. Tolerances in tests (torch.testing.assert_close) are set from ε\varepsilon of the dtype for the same reason.

4. The formats ML uses

The question. float64, float32, TF32, float16, bfloat16, FP8, 4-bit: what does each give up, and why did ML move from the first to the last in fifteen years?

Every format is the same recipe with different field widths. The exponent bits decide the range (how large and how small a number can be before overflow or underflow); the mantissa bits decide the precision (ε\varepsilon, the relative gap). Fewer bits per number means less memory, less memory traffic and more arithmetic per second on the same chip, which is why each new GPU generation added a narrower format. What each one is for

  • float64 is NumPy's default and the reference this page checks everything against. GPUs built for ML run it slowly or not at all on tensor cores, so training never uses it.
  • float32 is PyTorch's default dtype and the format of master weights, optimiser state and accumulators in mixed-precision training (section 11). About 7 decimal digits.
  • TF32 keeps float32's range and float16's precision for matrix multiplies on NVIDIA Ampere and later: "TF32 includes an 8-bit exponent (same as FP32), 10-bit mantissa (same precision as FP16), and 1 sign-bit" (NVIDIA, May 2020). In PyTorch 2.14.1 it is off by default for matrix multiplies and on for convolutions; the notes recommend torch.backends.cuda.matmul.fp32_precision = "tf32" "if your network does not need full float32 precision" (notes).
  • float16 has 3 more mantissa bits than bfloat16 but only 5 exponent bits: it overflows at 65,504 and turns anything below 6×10−86 \times 10^{-8} into 0. That is why it needs loss scaling (section 11).
  • bfloat16 is float32 with the last 16 bits cut off: same 8 exponent bits, 7 mantissa bits. Google's reasoning: "neural networks are far more sensitive to the size of the exponent than that of the mantissa", and the multipliers are "about half the size in silicon of a typical FP16 multiplier" (Wang and Kanwar 2019). Conversion to and from float32 is a shift (Kalamkar et al. 2019). It is the default training dtype in 2026.
  • FP8 comes in two flavours because forward and backward passes need different things: "E4M3 for weight and activation tensors, and E5M2 for gradient tensors" (Micikevicius et al. 2022). With only 8 values per binade (E4M3) every tensor needs its own scale factor; how that is chosen per tensor, per row or per tile is the Quantization and precision page's subject. PyTorch also has float8_e4m3fnuz and float8_e5m2fnuz variants with no negative zero.
  • 4-bit block formats. The OCP Microscaling (MX) spec v1.0 (Sep 2023) defines MXFP8, MXFP6, MXFP4 and MXINT8: blocks of 32 elements sharing one power-of-two scale stored as E8M0 (spec, table 1). MXFP4's elements are E2M1, which can only be 0,±0.5,±1,±1.5,±2,±3,±4,±60, \pm0.5, \pm1, \pm1.5, \pm2, \pm3, \pm4, \pm6. NVIDIA's NVFP4 (Blackwell) uses blocks of 16 with an E4M3 scale "to each 16-value micro-block" plus "a second-level FP32 scalar applied per tensor" (NVIDIA, 24 Jun 2025). Depth, outliers and measured errors: Quantization and precision, its Bit explorer and One real layer tabs.
Two libraries, two answers for the same FP8 cast (measured)
Converting 10001000 to E4M3 (largest 448): PyTorch 2.14.1's tensor.to(torch.float8_e4m3fn) returns 448 (it saturates), while ml_dtypes 0.6.0 returns NaN. Both are allowed: the OFP8 spec "requires implementation of saturating and non-saturating modes", and in non-saturating mode an overflowing E4M3 result is NaN (spec, section 5.2 and table 3). E5M2 has infinities, so 10001000 rounds to 1024 in both. Know which one your kernel does before you trust an FP8 tensor's max.
What it is used for in ML
Reading a training recipe: "bf16 mixed precision" means bf16 matrix multiplies with float32 master weights and accumulators; "FP8 training" means FP8 matrix-multiply inputs with per-tensor or per-block scales and higher-precision accumulation; an inference card's "NVFP4" or "MXFP4" means 4-bit weights with block scales.

5. The error of one operation, and how errors travel

The question. If each operation is rounded, how wrong can a whole computation get, and how do you tell a hard problem from a bad algorithm?

Because IEEE 754 rounds each basic operation once, correctly, every operation obeys the standard model (Higham 2002, chapter 2):

fl⁡(x∘y)=(x∘y)(1+δ),|δ|≤u,∘∈{+,−,×,÷}\operatorname{fl}(x \circ y) = (x \circ y)(1 + \delta), \qquad |\delta| \le u, \qquad \circ \in \{+, -, \times, \div\}

In words: the computed result is the exact result of the exact inputs, nudged by a relative error of at most uu (5.96×10−85.96 \times 10^{-8} in float32), as long as the result neither overflows nor underflows. One operation is therefore almost perfect. Problems come from what happens to errors already present in the inputs, and from many operations in a row. The fused multiply-add (FMA, required since IEEE 754-2008) computes a×b+ca \times b + c with a single rounding instead of two; matrix-multiply units are built from it.

Two ways to measure how wrong an answer is. The forward error is the distance from the true answer. The backward error asks a different question: is the computed answer the exact answer for a slightly different input, and how different? An algorithm whose answers are always exact answers to inputs perturbed by a few uu is backward stable. The two are linked by the condition number of the problem:

forward error≲κ×backward error.\text{forward error} \lesssim \kappa \times \text{backward error} .

So there are two separate ways to get a bad answer: a badly conditioned problem (large κ\kappa: any algorithm loses digits) or an unstable algorithm (large backward error on a well-conditioned problem: a better algorithm fixes it). The naive softmax of section 9 is the second kind.

6. Cancellation and the condition number of a computation

The question. Why does (1+10−8)−1(1 + 10^{-8}) - 1 come out as exactly 0 in float32, and why does a textbook variance formula return a negative variance?

Catastrophic cancellation

Subtracting two nearly equal numbers is exact (the Sterbenz lemma: if y/2≤x≤2yy/2 \le x \le 2y, then x−yx - y is a float), but it exposes the rounding errors the two numbers already carried, now measured against a tiny result. Measured, x=10−8x = 10^{-8}:

  • float32: 1+10−81 + 10^{-8} rounds to 1 (the gap above 1 is 1.2×10−71.2 \times 10^{-7}), so (1+x)−1=0(1 + x) - 1 = 0: 100% error.
  • float64: (1+x)−1=9.99999993922529×10−9(1 + x) - 1 = 9.99999993922529 \times 10^{-9}, a relative error of 6.1×10−96.1 \times 10^{-9}, which is 5×1075 \times 10^{7} times the format's u=1.1×10−16u = 1.1 \times 10^{-16}. Eight of sixteen digits are gone, not because the subtraction was inexact but because 1+x1 + x was rounded first.

The general rule: when a≈ba \approx b, the relative error of a−ba - b is the relative error of the inputs multiplied by |a|/|a−b||a| / |a - b|. The fix is always the same: rewrite the formula so the subtraction of nearly equal quantities never happens.

7. Summation: order matters, and long sums drift

The question. A loss is a mean over a batch; a matrix multiply is millions of sums; a gradient is a sum over tokens. What happens to a sum of a million numbers in 16 bits?

Floating-point addition is not associative

In exact arithmetic (a+b)+c=a+(b+c)(a + b) + c = a + (b + c). In floating point each ++ rounds, and the rounding depends on the sizes of the operands, so the grouping changes the answer. Measured in float64:

  • (0.1+0.2)+0.3=0.6000000000000001(0.1 + 0.2) + 0.3 = 0.6000000000000001, but 0.1+(0.2+0.3)=0.60.1 + (0.2 + 0.3) = 0.6.
  • (1016+1)−1016=0(10^{16} + 1) - 10^{16} = 0, but (1016−1016)+1=1(10^{16} - 10^{16}) + 1 = 1. Near 101610^{16} float64's gap is 2, so 1016+110^{16} + 1 is a tie and rounds back to 101610^{16}: the 1 is absorbed.

Addition is still commutative (a+b=b+aa + b = b + a exactly), and a single addition is still within uu. It is chains of additions in different orders that differ.

How large is the error of a long sum?

Add x1,…,xnx_1, \dots, x_n left to right (recursive summation). Each partial sum is rounded: sˆk=(sˆk−1+xk)(1+δk)\hat s_k = (\hat s_{k-1} + x_k)(1 + \delta_k) with |δk|≤u|\delta_k| \le u. Unrolling, x1x_1 and x2x_2 pass through n−1n - 1 roundings, x3x_3 through n−2n - 2, and so on, so to first order in uu

|sˆn−sn|≤(n−1)u∑i=1n|xi|.|\hat s_n - s_n| \le (n - 1)\, u \sum_{i=1}^{n} |x_i| .
Where that bound comes from, in three lines

sˆ2=(x1+x2)(1+δ2)\hat s_2 = (x_1 + x_2)(1 + \delta_2), sˆ3=((x1+x2)(1+δ2)+x3)(1+δ3)\hat s_3 = \bigl((x_1 + x_2)(1 + \delta_2) + x_3\bigr)(1 + \delta_3), and so on. Multiplying out, sˆn=∑ixi∏k=max⁡(i,2)n(1+δk)\hat s_n = \sum_i x_i \prod_{k = \max(i, 2)}^{n} (1 + \delta_k). Each product of at most n−1n - 1 factors (1+δk)(1 + \delta_k) lies within (1±u)n−1=1±(n−1)u+O(u2)(1 \pm u)^{n-1} = 1 \pm (n-1)u + O(u^2). Subtract the exact sum and bound each term by |xi|(n−1)u|x_i|\,(n-1)u. The full statement with the O(u2)O(u^2) term is in Higham 2002, chapter 4.

The bound grows with nn, and it is relative to ∑|xi|\sum|x_i|, not to the answer: with mixed signs the answer can be tiny and the relative error huge. Worse than the bound suggests is stagnation: once the running sum is large, each new small term is below half a gap and is lost entirely. Adding 1 over and over (measured): float16 stops at 2,048, bfloat16 at 256, float32 at 16,777,216. These are 2p2^{p}: at 2p2^p the gap becomes 2, and adding 1 is a tie that rounds back (to even).

Three better algorithms

  • Pairwise summation: add neighbours in pairs, then pairs of pairs, as a binary tree. Each term passes through only ⌈log2⁡n⌉\lceil \log_2 n \rceil roundings, so the bound becomes ⌈log2⁡n⌉u∑|xi|\lceil \log_2 n \rceil\, u \sum|x_i|: 20 instead of a million for n=106n = 10^6. It is what GPUs do naturally (a tree reduction), and NumPy uses "partial pairwise summation" (its sum docstring).
  • Kahan (compensated) summation (Kahan 1965) carries a second number cc that holds what the last addition lost, and feeds it back into the next one. Its error bound is (2u+O(nu2))∑|xi|\bigl(2u + O(n u^2)\bigr)\sum|x_i|: independent of nn while nu≪1n u \ll 1. Python's built-in sum of floats switched to a compensated algorithm in 3.12: measured, Python 3.13 gives sum([1e16, 1.0, -1e16]) = 1.0 where Python 3.9 gives 0.0; math.fsum is exactly rounded.
  • Accumulate in higher precision: keep 16-bit inputs but add them in a float32 accumulator. This is what tensor cores do for fp16 and bf16 matrix multiplies (PyTorch notes: "intermediate accumulations (reduction) in single-precision"), and what FP8 recipes do every so many elements: DeepSeek-V3 promotes partial sums to FP32 every 128 elements (see Quantization and precision).
y=xk−c,t=s+y,c=(t−s)−y,s=ty = x_k - c, \qquad t = s + y, \qquad c = (t - s) - y, \qquad s = t

Read Kahan's four lines as: yy is the new term corrected by last step's loss; tt is the rounded new sum; (t−s)(t - s) is what actually got added, so (t−s)−y(t - s) - y is minus what was lost; keep it in cc. In exact arithmetic cc would always be 0, which is why an optimising compiler that assumes associativity can silently delete it.

8. Determinism: why the same code gives different numbers

From the order of additions. A parallel reduction splits a sum into chunks, adds each chunk, then adds the chunk totals; the chunking depends on the number of threads, the block sizes a kernel picks for this tensor shape, and whether a matrix multiply splits its inner dimension (split-K). What it is used for in ML
Debugging (bit-identical reruns let you bisect a divergence), on-policy RL (the sampler and the trainer must compute the same log-probabilities, Thinking Machines' motivation), regression tests on model outputs (compare with a tolerance, not with ==), and evaluation at temperature 0 (expect small differences between runs and providers).

9. The stable softmax, log-sum-exp and log-softmax

The question. The root's tiny model gives logits (2,1,0)(2, 1, 0) and a loss of 2.408. Push the logits to (1000,999,0)(1000, 999, 0): the true probabilities barely change in shape, yet a naive softmax returns NaN. Why, and what one-line change fixes it?

The fix: subtract the largest logit

Multiply the top and bottom of the softmax by the same number e−me^{-m}:

ezi∑jezj=e−mezie−m∑jezj=ezi−m∑jezj−m.\frac{e^{z_i}}{\sum_j e^{z_j}} = \frac{e^{-m}\, e^{z_i}}{e^{-m} \sum_j e^{z_j}} = \frac{e^{z_i - m}}{\sum_j e^{z_j - m}} .

The value is unchanged for any mm. Choose m=maxj⁡zjm = \max_j z_j. Terms that underflow to 0 are smaller than the format's tiniest number, far below uu relative to the 1 in the denominator, so dropping them changes nothing visible.

On (1000,999,0)(1000, 999, 0): m=1000,d=1m = 1000, d = 1; then m=1000,d=1+e−1=1.368m = 1000, d = 1 + e^{-1} = 1.368; then d=1.368+e−1000=1.368d = 1.368 + e^{-1000} = 1.368, the same denominator as before. This rescaling is the heart of FlashAttention (Dao et al. 2022; the FlashAttention paper page runs the kernel in its Run the kernel tab), which computes attention's softmax tile by tile without ever holding a full row of scores. The error analysis of the shifted formulas is in Blanchard, Higham and Higham 2021.

What it is used for in ML
Every cross-entropy loss, every attention layer (with the mask's −∞-\infty entries), log-likelihoods of sequences, mixture models and the ELBO (sums of probabilities done in log space), beam-search scores. Rule: work with logits and log-probabilities, call the fused function (cross_entropy, log_softmax, logsumexp), and never write torch.log(torch.softmax(z, -1)).

10. The stable toolbox: logsigmoid, BCE with logits, softplus, epsilons

The question. Softmax is one function. Which other everyday formulas in ML overflow, underflow or cancel, and what is the stable rewrite of each?

One pattern covers almost all of them: split on the sign, so the exponential only ever sees a non-positive number, and use log1p for the log of one plus something small. The identity behind it is e−|x|≤1e^{-|x|} \le 1 for every xx.

logsigmoid

The sigmoid σ(x)=1/(1+e−x)\sigma(x) = 1/(1 + e^{-x}) gives a probability from one logit. Its log appears in every binary loss. Naively, ln⁡σ(−100)\ln\sigma(-100) in float32: e100e^{100} overflows (past e88.72e^{88.72}), σ=1/∞=0\sigma = 1/\infty = 0, ln⁡0=−∞\ln 0 = -\infty (measured); the true value is −100-100. The stable form comes from two cases. For x≥0x \ge 0, ln⁡σ(x)=−ln⁡(1+e−x)\ln\sigma(x) = -\ln(1 + e^{-x}). For x<0x \lt 0, multiply top and bottom by exe^{x}: σ(x)=ex/(1+ex)\sigma(x) = e^{x}/(1 + e^{x}), so ln⁡σ(x)=x−ln⁡(1+ex)\ln\sigma(x) = x - \ln(1 + e^{x}). Both are one formula:

ln⁡σ(x)=min⁡(x,0)−log1p⁡(e−|x|).\ln \sigma(x) = \min(x, 0) - \operatorname{log1p}\bigl(e^{-|x|}\bigr) .

PyTorch's CPU kernel is that line, computed in float32 even for 16-bit inputs: min_vec - buffer_vec0.log1p() with buffer_vec0 = data_vec0.abs().neg().exp() (Activation.cpp, lines 33 to 48).

Binary cross-entropy with logits

For a logit xx and a label y∈{0,1}y \in \{0, 1\} (or a soft label in [0,1][0, 1]), binary cross-entropy is ℓ=−[yln⁡σ(x)+(1−y)ln⁡(1−σ(x))]\ell = -[\,y \ln\sigma(x) + (1 - y)\ln(1 - \sigma(x))\,]. Two facts make it stable: 1−σ(x)=σ(−x)1 - \sigma(x) = \sigma(-x), and ln⁡σ(−x)=ln⁡σ(x)−x\ln\sigma(-x) = \ln\sigma(x) - x (from σ(−x)=e−xσ(x)\sigma(-x) = e^{-x}\sigma(x)). Substitute:

ℓ=−yln⁡σ(x)−(1−y)(ln⁡σ(x)−x)=(1−y)x−ln⁡σ(x)=max⁡(x,0)−xy+log1p⁡(e−|x|).\ell = -y \ln\sigma(x) - (1 - y)\bigl(\ln\sigma(x) - x\bigr) = (1 - y)\,x - \ln\sigma(x) = \max(x, 0) - x y + \operatorname{log1p}\bigl(e^{-|x|}\bigr) .

The last form uses the logsigmoid line above. Worked: x=2x = 2, y=1y = 1 gives 0−2+2+log1p⁡(e−2)=0.12690 - 2 + 2 + \operatorname{log1p}(e^{-2}) = 0.1269; y=0y = 0 gives 2+0.1269=2.12692 + 0.1269 = 2.1269 (derived). Naively in float32 with x=30x = 30, y=0y = 0: σ(30)=1−9.4×10−14\sigma(30) = 1 - 9.4 \times 10^{-14} rounds to exactly 1, ln⁡(1−1)=−∞\ln(1 - 1) = -\infty, loss ∞\infty (measured); the stable form gives 30+log1p⁡(e−30)=30.030 + \operatorname{log1p}(e^{-30}) = 30.0. PyTorch v2.14.1 computes (1 - target).mul_(input).sub_(log_sigmoid_input), the middle form above (Loss.cpp, lines 349 to 364).

Why not Sigmoid then BCELoss?
Because the probability has already rounded to 0 or 1 before the loss sees it. PyTorch patches the symptom: "BCELoss clamps its log function outputs to be greater than or equal to -100", so the x=30x = 30 example returns 100 instead of 30, a finite but wrong loss with a wrong gradient. Under autocast it refuses outright: "binary_cross_entropy and BCELoss raise an error in autocast-enabled regions", and the docs say to combine the sigmoid and the loss with binary_cross_entropy_with_logits (loss.py, amp docs, v2.14.1).

softplus

softplus⁡(x)=ln⁡(1+ex)\operatorname{softplus}(x) = \ln(1 + e^{x}), a smooth ReLU and the negative of ln⁡σ(−x)\ln\sigma(-x). Naively, float32 softplus⁡(100)=ln⁡(1+∞)=∞\operatorname{softplus}(100) = \ln(1 + \infty) = \infty (measured). Stable: max⁡(x,0)+log1p⁡(e−|x|)\max(x, 0) + \operatorname{log1p}(e^{-|x|}). PyTorch's nn.Softplus(beta=1.0, threshold=20.0) takes a shortcut instead: when βx>20\beta x \gt 20 it returns xx unchanged. What it drops, log1p⁡(e−20)=2.1×10−9\operatorname{log1p}(e^{-20}) = 2.1 \times 10^{-9}, is a thousand times smaller than float32's gap at 20 (1.9×10−61.9 \times 10^{-6}), so the shortcut is exact in float32 (derived).

Epsilons: the small numbers added on purpose

Many formulas divide by something that can be 0: a standard deviation, a norm, a square root of a second moment. Libraries add a small ϵ\epsilon (not machine epsilon, just a small constant):

  • LayerNorm: y=x−mean⁡(x)var⁡(x)+ϵγ+βy = \dfrac{x - \operatorname{mean}(x)}{\sqrt{\operatorname{var}(x) + \epsilon}}\,\gamma + \beta, default ϵ=10−5\epsilon = 10^{-5} (nn.LayerNorm, v2.14.1). For a constant row, var⁡=0\operatorname{var} = 0: without ϵ\epsilon the result is 0/0=0/0 = NaN; with it, 0×1/10−5=0×316.2=00 \times 1/\sqrt{10^{-5}} = 0 \times 316.2 = 0. It also caps the gain for nearly constant rows at 316.
  • RMSNorm: y=x/ϵ+1n∑ixi2y = x / \sqrt{\epsilon + \tfrac1n\sum_i x_i^2}. PyTorch's default ϵ\epsilon is now the machine epsilon of the compute type, 1.19×10−71.19 \times 10^{-7} for float16, bfloat16 and float32 inputs (docstring, v2.14.1); model configs set their own (SmolLM2-135M: rms_norm_eps 10−510^{-5}).
  • Adam: the update divides by vˆ+ϵ\sqrt{\hat v} + \epsilon with default ϵ=10−8\epsilon = 10^{-8} (torch.optim.Adam, v2.14.1). In float16, 10−810^{-8} is below the smallest subnormal (6×10−86 \times 10^{-8}) and becomes 0: one reason optimiser state stays in float32.
  • Even 10−510^{-5} is not a normal float16 number: it is a subnormal (stored as 1.0014×10−51.0014 \times 10^{-5}; smallest normal 6.1×10−56.1 \times 10^{-5}). Autocast runs layer_norm, group_norm and norm in float32 for this kind of reason (amp docs).

11. Mixed-precision training: master weights, loss scaling, and why bf16 skips it

The question. Training in 16 bits halves memory and doubles speed. What exactly breaks if you just call model.half(), and what do the standard fixes repair?

The recipe that made 16-bit training work comes from Micikevicius et al. 2017: "maintaining a master copy of weights in FP32, loss-scaling that minimizes gradient values becoming zeros, and FP16 arithmetic with accumulation in FP32". Each of the three fixes one failure. To see the failures on a real model rather than in principle, this page ran one training step of SmolLM2-135M (134,515,008 parameters, 30 layers) on 4 sequences of 128 tokens of Tiny Shakespeare: once in float32 on the CPU as the reference (loss 3.5607), then in pure float16 and pure bfloat16 on the laptop's GPU (MPS), keeping every one of the 134.5 million gradients (measured; src/inputs/measure_b.py).

Failure 1: small updates vanish (fix: float32 master weights)

A weight update is the learning rate times something of order one (Adam's normalised step). Added to a 16-bit weight, it disappears whenever it is below half the weight's gap (section 3). On SmolLM2's real weights (median |w|=0.107|w| = 0.107), the fraction of weights an update of size η\eta would not change at all:

Measured: (w.to(dtype) - eta * sign(g).to(dtype)) == w.to(dtype) over all 134.5M weights. The two 83.8% cells are the same weights: both conditions reduce to |w|≥2−5|w| \ge 2^{-5}. Typical LLM learning rates are 10−410^{-4} to 10−310^{-3}, decayed lower at the end of training.

At a median weight of 0.107, bfloat16's gap is 2−11=0.000492^{-11} = 0.00049, so any step below 0.000240.00024 is lost: most of a run at learning rate 10−410^{-4} would not train. The fix is a float32 master copy of the weights: the optimiser adds the update in float32, and a 16-bit copy is made for the next forward pass. The paper's version of the argument: an update becomes zero "when the magnitude of a normalized weight value is at least 2048 times larger that of the weight update" (float16 has 10 mantissa bits, 211=20482^{11} = 2048). The bytes this costs (2 + 2 + 4 + 4 + 4 = 16 per parameter with Adam) are counted on the Quantization and precision page.

Failure 2: small gradients underflow (fix: loss scaling, float16 only)

Gradients are small. In the float32 reference step, the median |g||g| is 3.2×10−53.2 \times 10^{-5}, below float16's smallest normal number (2−14=6.1×10−52^{-14} = 6.1 \times 10^{-5}): 68% of SmolLM2's gradients live in float16's subnormal range, where precision drains away, 7.2% are below its smallest subnormal 2−242^{-24}, and 5.0% are below 2−252^{-25} and round to exactly 0 when cast (measured). The 2017 paper found the same order on a speech model: "approximately 5% of weight gradient values have exponents smaller than −24-24".

Loss scaling multiplies the loss by a constant SS before the backward pass. By the chain rule every gradient is multiplied by SS too, shifting the whole histogram right by log2⁡S\log_2 S binades into float16's range; the gradients are divided by SS in float32 before the update, so the step is unchanged. Too small an SS leaves gradients in the underflow zone; too large pushes the largest past 65,504 into infinity.

Why bfloat16 mostly does not need loss scaling

bfloat16 has float32's 8 exponent bits, so its smallest normal number is 1.2×10−381.2 \times 10^{-38} like float32's; SmolLM2's smallest gradient is 2−51≈4×10−162^{-51} \approx 4 \times 10^{-16}, 22 orders of magnitude inside the range. In the pure bfloat16 run only 0.00005% of gradients became 0, with no scaling. bfloat16's problem is the other axis: with 8 significant bits its gradients had a median relative error of 4.8%, against 0.55% for float16 at a good scale (measured). Range is fixed by the format; precision is fixed by float32 master weights and float32 accumulation. Google's summary: "Unlike FP16, which typically requires special handling via techniques such as loss scaling, BF16 comes close to being a drop-in replacement for FP32" (Wang and Kanwar 2019). "Mostly": hardware that flushes bfloat16 subnormals to zero (section 2) has a smaller range at the bottom, and FP8 and 4-bit training are back to needing scales, per tensor or per block.

Failure 3: large activations overflow (fix: bf16, or keep the risky ops in float32)

float16's largest number, 65,504, is reachable inside a network: attention scores before the softmax, the sum of squares inside a norm, a residual stream with outlier features, the logits of a large vocabulary. One overflow gives ∞\infty, the next softmax gives NaN. This is why autocast keeps exactly those operations in float32 (softmax, layer_norm, norm, sum, exp, the losses; section 9) and runs matrix multiplies in 16 bits with float32 accumulation.

What it is used for in ML
The standard PyTorch loop: with torch.autocast("cuda", dtype=torch.bfloat16) around the forward pass, float32 parameters and optimiser; with float16, add scaler = torch.amp.GradScaler(), scaler.scale(loss).backward(), scaler.step(opt), scaler.update(), and unscale before gradient clipping (scaler.unscale_(opt)) so the clip threshold applies to the true gradients.

A real hunt, on the running example

The naive softmax cross-entropy on logits (1000,999,0)(1000, 999, 0), target sat, in PyTorch 2.14.1 (measured, src/inputs/nan_demo.py): the forward pass returns loss = inf, not NaN (psat=1/∞=0p_{\text{sat}} = 1/\infty = 0, −ln⁡0=∞-\ln 0 = \infty), and the backward pass returns gradients [nan, nan, nan]. Wrapping the same code in torch.autograd.detect_anomaly() stops at the culprit: Function 'DivBackward0' returned nan values in its 0th output, the division by the overflowed sum. The fused F.cross_entropy on the same logits returns 1000.3132 with gradient [0.7311, 0.2689, -1.0].

A procedure

  1. Check where it first appears. Log the loss and the global gradient norm every step; a gradient norm that jumps by orders of magnitude a few steps before the NaN points to an instability (learning rate, a layer's logits growing), not a single bad operation. With GradScaler, a few skipped steps are normal; skipped steps every iteration are not.
  2. Find the first non-finite activation. Register a forward hook on every module that checks torch.isfinite(output).all() and records the module name; the first one to fail is the culprit, everything after it is collateral.
  3. Find the first non-finite gradient. torch.autograd.detect_anomaly() (or set_detect_anomaly(True)) does "two things": it records forward tracebacks so the backward error can name "the forward operation that created the failing backward function", and with check_nan=True "any backward computation that generates 'nan' value will raise an error". Its own warning: "This mode should be enabled only for debugging" (anomaly_mode.py, v2.14.1).
  4. Replay the batch. Save the batch and the weights at the failing step; rerun in float32, then in float64. If float64 is finite, it is a precision or range problem (section 4); if not, it is the data or the maths (a log of 0, a division by a zero norm).
  5. Fix the cause, not the symptom. Replace the naive formula with its stable form (sections 9 and 10), keep the risky operation in float32, lower the learning rate or clip gradients for an instability. torch.nan_to_num on a loss hides the evidence; skipping a step on a non-finite loss is acceptable only as a guard while you look.
What it is used for in ML
Every divergence post-mortem. Two published instabilities had exactly this shape: PaLM added an auxiliary "z loss =10−4⋅log2⁡Z= 10^{-4} \cdot \log^2 Z to encourage the softmax normalizer log⁡(Z)\log(Z) to be close to 0, which we found increases the stability of training" (Chowdhery et al. 2022, section 5); ViT-22B saw attention logits "grow to over 50000 in magnitude" without normalisation, near float16's 65,504, and fixed it by applying LayerNorm to queries and keys (Dehghani et al. 2023, appendix B).

13. Where research is now

The question. Which numerical questions are still open in 2026, and which papers are worth reading next?
  • Fewer bits for training. FP8 training at 671B parameters with fine-grained scaling (DeepSeek-V3, December 2024; the DeepSeek-V3 paper page animates it in its Quantise and accumulate tab) and NVFP4 pretraining of a 12B model on 10 trillion tokens, "the longest publicly documented training run in 4-bit precision to date", using random Hadamard transforms, two-dimensional block scaling, stochastic rounding of gradients and a few layers kept in higher precision (NVIDIA, Sep 2025). Every ingredient is this page's: range (scales), precision (rounding), and accumulation. Depth and measurements: Quantization and precision.
  • 16-bit-only training. Can the float32 master copy go? Zamirai et al. show nearest rounding "cancels small updates" in bf16 and that stochastic rounding and Kahan summation on the weight update recover "0.1% lower to 0.2% higher validation accuracy compared to 32-bit training" across seven applications (2020).
  • Determinism as a feature. Batch-invariant kernels make inference reproducible at a speed cost (Thinking Machines 2025); on-policy reinforcement learning needs the sampler's and the trainer's log-probabilities to match bit for bit.
  • Accurate kernels, one pass. Online softmax (Milakov and Gimelshein 2018) inside FlashAttention, with error analysis of shifted log-sum-exp and softmax (Blanchard, Higham and Higham 2021).
  • Stability by architecture. QK normalisation, z-loss and softmax capping keep logits in range so that low precision survives (section 12).

14. Common mistakes

Comparing floats with ==
0.1+0.2≠0.30.1 + 0.2 \ne 0.3 in every binary format. Compare with a tolerance scaled to the dtype: torch.testing.assert_close or math.isclose(a, b, rel_tol=...), with the relative tolerance a few times ε\varepsilon of the dtype.
Writing torch.log(torch.softmax(z)) or Sigmoid then BCELoss
Probabilities round to 0 or 1 before the log sees them. Use log_softmax, cross_entropy on logits, and binary_cross_entropy_with_logits (sections 9 and 10).
Keeping a running sum, a metric or an optimiser state in bf16
A bf16 running sum of ones stops at 256; a bf16 sum of a thousand numbers in [0,1)[0, 1) is 50% low (measured, section 7). Accumulate in float32; keep master weights and Adam's moments in float32.
Believing machine epsilon is the smallest positive number
ε\varepsilon is the gap above 1 (float32 1.19×10−71.19 \times 10^{-7}); the smallest positive float32 is 1.4×10−451.4 \times 10^{-45} and the smallest normal one 1.18×10−381.18 \times 10^{-38}. And libraries' eps is 2u2u, twice the unit roundoff in textbooks.
Using fp16 without a loss scaler, or bf16 with one "to be safe"
fp16 without scaling silently zeroes gradients (8.2% on SmolLM2, measured). bf16 does not need scaling; a scaler is harmless but adds skipped steps if misconfigured.
Clipping gradients before unscaling them
With GradScaler the gradients are SS times too large until unscaled; clip after scaler.unscale_(optimizer).
Expecting bit-identical results across GPUs, batch sizes or thread counts
The order of additions changes (section 8). torch.sum of the same tensor gives different results at 4 and 8 CPU threads (measured). Compare with tolerances; for exact reproducibility fix hardware, versions, batch shapes and use deterministic algorithms.
Computing a variance as x2−x‾2\overline{x^2} - \bar x^2
It can be negative (−8-8 on three float32 numbers near 10,000, measured). Use two passes or Welford.
Storing logits or targets in bf16 and expecting their small differences to survive
999 and 1000 are the same bfloat16 number; so are 256 and 257. Keep logits, losses and anything compared by small differences in float32.
Trusting an FP8 cast's overflow behaviour without checking
PyTorch saturates 1000→4481000 \to 448 in E4M3; ml_dtypes returns NaN (measured, section 4).
Letting the compiler reassociate
Fast-math flags (-ffast-math, some JIT settings) let the compiler assume associativity and delete Kahan's correction term as algebraically zero (section 7).

Summation lab

Add NN numbers in float16, bfloat16 or float32 with four algorithms and compare each with the exact sum (computed with Shewchuk's exact algorithm, as Python's math.fsum). Every addition is rounded to the chosen format exactly as the hardware would round it. The chart repeats the sum for every NN up to your choice, so you can see each method's error grow (or not). It extends Reading section 7, which shows the same experiment measured in NumPy and PyTorch on a million numbers.

Try: float16, uniform, N=10,000N = 10{,}000: the naive sum stalls at 2,048 (59% low) while pairwise and Kahan are within one rounding; then big first value: one 10,000 followed by small numbers, where naive loses almost all of them; then mixed signs: the exact sum is small compared with ∑|xi|\sum|x_i|, and every method's error bound is relative to ∑|xi|\sum|x_i|, not to the answer, so relative errors grow; then press Shuffle 20 orders.
A relative error of exactly 0 is drawn at the bottom edge, an infinite one (overflow) at the top.

The four algorithms
Naive: one running sum, s←fl⁡(s+xi)s \leftarrow \operatorname{fl}(s + x_i); error bound (N−1)u∑|xi|(N-1)u\sum|x_i|. Pairwise: add neighbours, then pairs of pairs (a binary tree); bound ⌈log2⁡N⌉u∑|xi|\lceil\log_2 N\rceil u \sum|x_i|. Kahan: a running sum plus a correction cc holding what the last addition lost; bound (2u+O(Nu2))∑|xi|(2u + O(Nu^2))\sum|x_i|, so it degrades once Nu2Nu^2 is not small (bfloat16 at N≈105N \approx 10^5). fp32 accumulator: the 16-bit inputs added into a float32 running sum, what tensor cores do. "Best possible" is the exact sum rounded once to the format: no algorithm that returns a value in this format can do better. Data are generated by a seeded generator (mulberry32) and rounded to the format first, so only the summation rounds; recompute.py reproduces the uniform cases at N=100N = 100, 1,000 and 10,000 in NumPy.
