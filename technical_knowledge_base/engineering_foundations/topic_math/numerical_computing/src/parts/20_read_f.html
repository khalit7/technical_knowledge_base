5. Summation: order matters, and long sums drift

A loss is a mean over a batch, a matrix multiply is millions of sums, a gradient is a sum over tokens. Each \(+\) rounds, and the rounding depends on the operands' sizes, so floating-point addition is not associative. Measured in float64: \((0.1 + 0.2) + 0.3 = 0.6000000000000001\) but \(0.1 + (0.2 + 0.3) = 0.6\); \((10^{16} + 1) - 10^{16} = 0\) but \((10^{16} - 10^{16}) + 1 = 1\), because near \(10^{16}\) the gap is 2, so \(10^{16} + 1\) is a tie that rounds back and the 1 is absorbed. Addition is still commutative (\(a + b = b + a\) exactly); it is chains of additions in different orders that differ.

Adding \(x_1, \dots, x_n\) left to right (recursive summation), \(x_1\) and \(x_2\) pass through \(n - 1\) roundings, \(x_3\) through \(n - 2\), and so on, so to first order in \(u\)

\[ |\hat s_n - s_n| \le (n - 1)\, u \sum_{i=1}^{n} |x_i| . \]
Where that bound comes from, in three lines

\(\hat s_2 = (x_1 + x_2)(1 + \delta_2)\), \(\hat s_3 = \bigl((x_1 + x_2)(1 + \delta_2) + x_3\bigr)(1 + \delta_3)\), and so on. Multiplying out, \(\hat s_n = \sum_i x_i \prod_{k = \max(i, 2)}^{n} (1 + \delta_k)\). Each product of at most \(n - 1\) factors \((1 + \delta_k)\) lies within \((1 \pm u)^{n-1} = 1 \pm (n-1)u + O(u^2)\). Subtract the exact sum and bound each term by \(|x_i|\,(n-1)u\). The full statement with the \(O(u^2)\) term is in {{Higham 2002|https://doi.org/10.1137/1.9780898718027}}, chapter 4.

The bound grows with \(n\) and is relative to \(\sum|x_i|\), not to the answer: with mixed signs the answer can be tiny and the relative error huge. Worse is stagnation: once the running sum is large, each small term is below half a gap and lost entirely. Adding 1 over and over (measured), float16 stops at 2,048, bfloat16 at 256, float32 at 16,777,216: these are \(2^{p}\), where the gap becomes 2 and adding 1 is a tie that rounds back (to even). Three fixes:

  • Pairwise summation: add neighbours in pairs, then pairs of pairs. Each term passes through \(\lceil \log_2 n \rceil\) roundings, so the bound becomes \(\lceil \log_2 n \rceil\, u \sum|x_i|\): 20 instead of a million for \(n = 10^6\). GPUs do this naturally (a tree reduction); NumPy uses "partial pairwise summation" (its sum docstring).
  • Kahan (compensated) summation ({{Kahan 1965|https://doi.org/10.1145/363707.363723}}) carries a second number \(c\) holding what the last addition lost and feeds it into the next one. Its bound is \(\bigl(2u + O(n u^2)\bigr)\sum|x_i|\): independent of \(n\) while \(n u \ll 1\).
  • Accumulate in higher precision: 16-bit inputs added in a float32 accumulator. Tensor cores do this for fp16 and bf16 matrix multiplies (PyTorch notes: "intermediate accumulations (reduction) in single-precision"); FP8 recipes promote partial sums periodically: DeepSeek-V3 every 128 elements ({{Quantization and precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}).
\[ y = x_k - c, \qquad t = s + y, \qquad c = (t - s) - y, \qquad s = t \]

Read Kahan's four lines as: \(y\) is the new term corrected by last step's loss; \(t\) is the rounded new sum; \((t - s)\) is what actually got added, so \((t - s) - y\) is minus what was lost. In exact arithmetic \(c\) would always be 0, which is why a compiler allowed to reassociate (-ffast-math, some JIT settings) can silently delete it. Step through both on the same input:

Measured on a million numbers (NumPy and PyTorch on this laptop, uniform on \([0, 1)\)): the naive 16-bit running sum is useless past a few thousand terms (float16 59% low at \(N = 10^4\), bfloat16 50% low at \(N = 10^3\)); pairwise and Kahan stay within one rounding; Kahan in bfloat16 fails at \(N = 10^6\) (87% error) exactly as its bound warns, since \(n u^2 = 10^6 \times 2^{-16} \approx 15\) is no longer small; the float32 accumulator is the best by orders of magnitude. At \(N = 10^6\) the true sum, about 500,000, is beyond float16's 65,504, so pairwise, NumPy and torch.sum overflow to infinity and Kahan to NaN (its correction becomes \(\infty - \infty\)); only the naive sum stays finite, because it stalled at 2,048 long before. Rules: accumulate in float32 (float64 for metrics), prefer the library's reduction to a Python loop, never keep a running total in bf16.
