1. A float, bit by bit

In binary each place is worth twice the place to its right, and places after the point are worth \(\tfrac12, \tfrac14, \tfrac18, \dots\). A fraction has a finite binary expansion only if its denominator is a power of two, so \(0.1 = 0.0\overline{0011}_2\) repeats forever and any fixed number of bits must cut it off: that is why \(0.1 + 0.2\) prints as 0.30000000000000004 in Python (measured). ML needs \(3 \times 10^{-8}\) (a small gradient) and \(5 \times 10^{4}\) (a large activation) in the same tensor; an evenly spaced grid fine enough for the first needs about \(10^{12}\) steps, about 41 bits, to reach the second. So numbers are stored in base-2 scientific notation, \(x = (-1)^{s} \times m \times 2^{E}\) with \(1 \le m \lt 2\): \(13 = 1101_2 = 1.101_2 \times 2^{3} = 1.625 \times 8\). The point "floats" to just after the first 1, and every number carries the same number of significant bits whatever its size: the gaps between neighbours grow in proportion to the number.

Integers and two's complement (for quantised codes and index overflow)

An unsigned 8-bit integer holds \(0\) to \(2^8 - 1 = 255\). For negative numbers every modern machine uses two's complement: the top bit is worth \(-2^{7} = -128\) instead of \(+128\), so int8 holds \(-128\) to \(127\) and \(-13 = 11110011_2 = -128 + 64 + 32 + 16 + 2 + 1\). Adding uses the same circuit as unsigned addition, and negating is "flip every bit, add 1" (\(13 = 00001101_2\), flipped \(11110010_2\), plus one \(11110011_2\)). The price is that integers wrap around: in int8, \(127 + 1 = -128\) (derived; NumPy does the same and warns). Integers are exact inside their range and evenly spaced, which is why quantised weights are stored as int8 or int4 codes with a separate scale ({{Quantization and precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}). Token ids, counts and quantised codes are integers; wraparound appears in practice when an int32 index overflows past \(2^{31} - 1 \approx 2.1 \times 10^{9}\) elements, the size of a single large embedding or attention tensor.

IEEE 754 float32: three fields

The standard that fixes every bit is IEEE 754 (1985, revised 2008 and 2019: {{IEEE 754-2019|https://doi.org/10.1109/IEEESTD.2019.8766229}}; William Kahan, its main architect, received the 1989 {{Turing Award|https://amturing.acm.org/award_winners/kahan_1023746.cfm}}). Before it, every computer maker rounded differently. A 32-bit float (float32, fp32) is:

sign: 1 bitexponent field: 8 bitsfraction (mantissa) field: 23 bits
\[ x = (-1)^{s} \times \Bigl(1 + \frac{f}{2^{23}}\Bigr) \times 2^{\,e - 127} \qquad (1 \le e \le 254) \]
\(s\)
the sign bit: 0 for positive, 1 for negative.
\(e\)
the 8-bit biased exponent, read as an unsigned integer 0 to 255; the true exponent is \(E = e - 127\), and 127 is the bias (\(2^{8-1} - 1\)). Storing \(E + 127\) makes positive floats sort like their bit patterns, so hardware compares floats with integer comparisons.
\(f\)
the 23-bit fraction, an integer 0 to \(2^{23} - 1\). The leading 1 is not stored (the hidden bit), so float32 carries \(p = 24\) significant bits, its precision.

The loss, by hand. The exact loss \(\ln(e^2 + e^1 + e^0) = 2.40760596444438\ldots\) lies between 2 and 4, so \(E = 1\) and \(e = 128 = 10000000_2\). The significand is \(1.2038\ldots\); its fractional part times \(2^{23}\) is \(1{,}709{,}622.6\ldots\), which rounds to \(f = 1{,}709{,}623\). Read back, \(1.2038029432296753 \times 2 = 2.4076058864593506\): off by \(7.8 \times 10^{-8}\), a relative error of \(3.2 \times 10^{-8}\). struct.pack('>f', loss).hex() gives 401a1637, the same 32 bits (measured). Four kinds of bit pattern

The two extreme exponent fields are reserved. Every ML bug involving NaN starts in this table:

Subnormals make numbers fade to zero in equal steps of \(2^{-149}\) (gradual underflow), so \(x - y = 0\) only when \(x = y\) ({{Goldberg 1991|https://doi.org/10.1145/103162.103163}}, "Denormalized Numbers"); without them the gap between 0 and \(2^{-126}\) would be \(2^{23}\) times wider than the gap just above it. The price: \(10^{-40}\) in float32 keeps only 17 significant bits. NaN spreads (one NaN in a matrix multiply's input makes every output that touches it NaN) and compares false with everything, so loss > 10 is false for a NaN loss and a divergence check written that way never fires: use not torch.isfinite(loss). In a tensor dump, 7fc00000 is a NaN and 7f800000 is \(+\infty\); torch.finfo(torch.float32) prints the constants (eps, max, smallest_normal, tiny).

Hardware that flushes subnormals to zero

Some hardware drops subnormals for speed (flush to zero): Google's TPU blog says "bfloat16 handles denormals differently from FP32: it flushes them to zero" ({{Wang and Kanwar 2019|https://cloud.google.com/blog/products/ai-machine-learning/bfloat16-the-secret-to-high-performance-on-cloud-tpus}}), and PyTorch's notes say AMD MI200's FP16 and BF16 matrix instructions "flush input and output denormal values to zero" ({{numerical accuracy notes, v2.14.1|https://github.com/pytorch/pytorch/blob/v2.14.1/docs/source/notes/numerical_accuracy.md}}). On such hardware the bottom of the range is \(2^{-126}\), not \(2^{-133}\) (bfloat16's smallest subnormal).
