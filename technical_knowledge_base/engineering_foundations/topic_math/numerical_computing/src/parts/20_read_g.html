7. Summation: order matters, and long sums drift

The question. A loss is a mean over a batch; a matrix multiply is millions of sums; a gradient is a sum over tokens. What happens to a sum of a million numbers in 16 bits?

Floating-point addition is not associative

In exact arithmetic \((a + b) + c = a + (b + c)\). In floating point each \(+\) rounds, and the rounding depends on the sizes of the operands, so the grouping changes the answer. Measured in float64:

  • \((0.1 + 0.2) + 0.3 = 0.6000000000000001\), but \(0.1 + (0.2 + 0.3) = 0.6\).
  • \((10^{16} + 1) - 10^{16} = 0\), but \((10^{16} - 10^{16}) + 1 = 1\). Near \(10^{16}\) float64's gap is 2, so \(10^{16} + 1\) is a tie and rounds back to \(10^{16}\): the 1 is absorbed.

Addition is still commutative (\(a + b = b + a\) exactly), and a single addition is still within \(u\). It is chains of additions in different orders that differ.

How large is the error of a long sum?

Add \(x_1, \dots, x_n\) left to right (recursive summation). Each partial sum is rounded: \(\hat s_k = (\hat s_{k-1} + x_k)(1 + \delta_k)\) with \(|\delta_k| \le u\). Unrolling, \(x_1\) and \(x_2\) pass through \(n - 1\) roundings, \(x_3\) through \(n - 2\), and so on, so to first order in \(u\)

\[ |\hat s_n - s_n| \le (n - 1)\, u \sum_{i=1}^{n} |x_i| . \]
Where that bound comes from, in three lines

\(\hat s_2 = (x_1 + x_2)(1 + \delta_2)\), \(\hat s_3 = \bigl((x_1 + x_2)(1 + \delta_2) + x_3\bigr)(1 + \delta_3)\), and so on. Multiplying out, \(\hat s_n = \sum_i x_i \prod_{k = \max(i, 2)}^{n} (1 + \delta_k)\). Each product of at most \(n - 1\) factors \((1 + \delta_k)\) lies within \((1 \pm u)^{n-1} = 1 \pm (n-1)u + O(u^2)\). Subtract the exact sum and bound each term by \(|x_i|\,(n-1)u\). The full statement with the \(O(u^2)\) term is in {{Higham 2002|https://doi.org/10.1137/1.9780898718027}}, chapter 4.

The bound grows with \(n\), and it is relative to \(\sum|x_i|\), not to the answer: with mixed signs the answer can be tiny and the relative error huge. Worse than the bound suggests is stagnation: once the running sum is large, each new small term is below half a gap and is lost entirely. Adding 1 over and over (measured): float16 stops at 2,048, bfloat16 at 256, float32 at 16,777,216. These are \(2^{p}\): at \(2^p\) the gap becomes 2, and adding 1 is a tie that rounds back (to even).

Three better algorithms

  • Pairwise summation: add neighbours in pairs, then pairs of pairs, as a binary tree. Each term passes through only \(\lceil \log_2 n \rceil\) roundings, so the bound becomes \(\lceil \log_2 n \rceil\, u \sum|x_i|\): 20 instead of a million for \(n = 10^6\). It is what GPUs do naturally (a tree reduction), and NumPy uses "partial pairwise summation" (its sum docstring).
  • Kahan (compensated) summation ({{Kahan 1965|https://doi.org/10.1145/363707.363723}}) carries a second number \(c\) that holds what the last addition lost, and feeds it back into the next one. Its error bound is \(\bigl(2u + O(n u^2)\bigr)\sum|x_i|\): independent of \(n\) while \(n u \ll 1\). Python's built-in sum of floats switched to a compensated algorithm in 3.12: measured, Python 3.13 gives sum([1e16, 1.0, -1e16]) = 1.0 where Python 3.9 gives 0.0; math.fsum is exactly rounded.
  • Accumulate in higher precision: keep 16-bit inputs but add them in a float32 accumulator. This is what tensor cores do for fp16 and bf16 matrix multiplies (PyTorch notes: "intermediate accumulations (reduction) in single-precision"), and what FP8 recipes do every so many elements: DeepSeek-V3 promotes partial sums to FP32 every 128 elements (see {{Quantization and precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}).
\[ y = x_k - c, \qquad t = s + y, \qquad c = (t - s) - y, \qquad s = t \]

Read Kahan's four lines as: \(y\) is the new term corrected by last step's loss; \(t\) is the rounded new sum; \((t - s)\) is what actually got added, so \((t - s) - y\) is minus what was lost; keep it in \(c\). In exact arithmetic \(c\) would always be 0, which is why an optimising compiler that assumes associativity can silently delete it.

Before and after: the same eleven float16 numbers, \(2048\) then ten copies of \(0.4\) (stored as \(0.39990234\)). Exact sum \(2051.999\); the nearest float16 is 2052.

Measured: a long sum in three formats and five ways

Sum the first \(N\) of a million numbers drawn uniformly from \([0, 1)\), each first rounded to the format so that only the summation rounds. Relative error against the exact sum (math.fsum), measured on this laptop; "fp32 accumulator" adds the 16-bit inputs in a float32 running sum; torch.sum is PyTorch 2.14.1 on the CPU.

What the table shows: the naive 16-bit running sum is useless past a few thousand terms (stagnation: float16 is 59% low at \(N = 10^4\), bfloat16 is 50% low at \(N = 10^3\)). Pairwise and Kahan stay within one rounding of the final result. Kahan in bfloat16 fails at \(N = 10^6\) (87% error) exactly as its bound warns: \(n u^2 = 10^6 \times 2^{-16} \approx 15\), no longer small. The float32 accumulator is the best by orders of magnitude, which is why hardware does it. At \(N = 10^6\) the true sum, about 500,000, is beyond float16's 65,504, so pairwise, NumPy and torch.sum overflow to infinity and Kahan to NaN (its correction becomes \(\infty - \infty\)); only the naive sum stays finite, because it stalled at 2,048 long before. The {{Summation lab|#t-sum}} reruns this live, with other data and shuffled orders.

What it is used for in ML
Loss means over long sequences, gradient accumulation over micro-batches, metric averages over a test set, the dot products inside every matrix multiply. Rules: accumulate in float32 (or float64 for metrics), prefer the library's reduction to a Python loop, and never keep a running total in bf16.

8. Determinism: why the same code gives different numbers

The question. You fix every seed and run the same training step twice. The losses differ in the sixth digit. Where does the randomness come from?

From the order of additions. A parallel reduction splits a sum into chunks, adds each chunk, then adds the chunk totals; the chunking depends on the number of threads, the block sizes a kernel picks for this tensor shape, and whether a matrix multiply splits its inner dimension (split-K). A GPU kernel that lets many threads add into one location uses atomic adds, and then the order is whichever thread finishes first. Measured on this laptop:

So "nondeterminism" has two different meanings. Run-to-run: the same call on the same input differs between runs (atomics, as in the MPS index_add_ row). Configuration-dependent: the same call is repeatable, but changes with thread count, batch size or hardware (the torch.sum row). Thinking Machines showed that LLM inference is mostly the second kind: the forward pass "involves no operations that require atomic adds" and is run-to-run deterministic, but kernels are not batch invariant, so a request's numbers depend on how many other requests share its batch. Sampling Qwen3-235B-A22B-Instruct-2507 1,000 times at temperature 0, they got 80 unique completions, all identical for the first 102 tokens; with batch-invariant kernels all 1,000 matched (same post; the serving side is on the {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}} page). In training, the backward pass is where atomics live: gradients of embeddings, gathers and scatters add many contributions into the same row.

What PyTorch lets you control (v2.14.1)

  • torch.manual_seed(0) seeds "the RNG for all devices"; DataLoader workers need their own seeding function and generator (the notes give a seed_worker recipe).
  • torch.use_deterministic_algorithms(True) picks deterministic implementations where they exist and raises a RuntimeError for operations that have none. The docstring lists both: made deterministic, for example index_add, scatter_add_ and the backward of nn.Embedding on CUDA; raising, for example NLLLoss and histc on CUDA. Deterministic kernels "tend to have worse performance".
  • torch.backends.cudnn.benchmark = False stops cuDNN choosing among algorithms by timing (which "may select different algorithms on subsequent runs"); torch.backends.cudnn.deterministic = True controls only cuDNN's convolution choice.
  • Up to v2.9.1 the docstring also required CUBLAS_WORKSPACE_CONFIG=:4096:8 (or :16:8) for some CUDA operations; that paragraph is absent from v2.10.0 onward (checked in both sources).
  • Even then: "Completely reproducible results are not guaranteed across PyTorch releases, individual commits, or different platforms" ({{reproducibility notes|https://github.com/pytorch/pytorch/blob/v2.14.1/docs/source/notes/randomness.md}}), and A.sum(-1)[0] "is not guaranteed to be bitwise equal" to the sum of the slice ({{numerical accuracy notes|https://github.com/pytorch/pytorch/blob/v2.14.1/docs/source/notes/numerical_accuracy.md}}).
What it is used for in ML
Debugging (bit-identical reruns let you bisect a divergence), on-policy RL (the sampler and the trainer must compute the same log-probabilities, Thinking Machines' motivation), regression tests on model outputs (compare with a tolerance, not with ==), and evaluation at temperature 0 (expect small differences between runs and providers).
