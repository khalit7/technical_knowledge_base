6. Determinism: why the same code gives different numbers

Fix every seed, run the same step twice, and the losses can still differ in the sixth digit. The cause is the order of additions. A parallel reduction splits a sum into chunks, adds each chunk, then adds the chunk totals; the chunking depends on the thread count, the block sizes a kernel picks for this shape, and whether a matrix multiply splits its inner dimension (split-K). A kernel that lets many threads add into one location uses atomic adds, and then the order is whichever thread finishes first.

So "nondeterminism" has two meanings. Run-to-run: the same call on the same input differs between runs (atomics, the MPS index_add_ row). Configuration-dependent: repeatable, but changes with thread count, batch size or hardware (the torch.sum row). Thinking Machines showed that LLM inference is mostly the second kind: the forward pass "involves no operations that require atomic adds" and is run-to-run deterministic, but kernels are not batch invariant, so a request's numbers depend on how many other requests share its batch. Sampling Qwen3-235B-A22B-Instruct-2507 1,000 times at temperature 0, they got 80 unique completions, all identical for the first 102 tokens; with batch-invariant kernels all 1,000 matched (same post; the serving side is on {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}}). In training, the backward pass is where atomics live: gradients of embeddings, gathers and scatters add many contributions into the same row. Bit-identical reruns matter for bisecting a divergence, for on-policy RL (sampler and trainer must compute the same log-probabilities, Thinking Machines' motivation) and for regression tests, which should compare with a tolerance, not ==; expect small differences between runs and providers at temperature 0.

What PyTorch lets you control (v2.14.1)
  • torch.manual_seed(0) seeds "the RNG for all devices"; DataLoader workers need their own seeding function and generator (the notes give a seed_worker recipe).
  • torch.use_deterministic_algorithms(True) picks deterministic implementations where they exist and raises a RuntimeError for operations that have none. The docstring lists both: made deterministic, for example index_add, scatter_add_ and the backward of nn.Embedding on CUDA; raising, for example NLLLoss and histc on CUDA. Deterministic kernels "tend to have worse performance".
  • torch.backends.cudnn.benchmark = False stops cuDNN choosing among algorithms by timing (which "may select different algorithms on subsequent runs"); torch.backends.cudnn.deterministic = True controls only cuDNN's convolution choice.
  • Up to v2.9.1 the docstring also required CUBLAS_WORKSPACE_CONFIG=:4096:8 (or :16:8) for some CUDA operations; that paragraph is absent from v2.10.0 onward (checked in both sources).
  • Even then: "Completely reproducible results are not guaranteed across PyTorch releases, individual commits, or different platforms" ({{reproducibility notes|https://github.com/pytorch/pytorch/blob/v2.14.1/docs/source/notes/randomness.md}}), and A.sum(-1)[0] "is not guaranteed to be bitwise equal" to the sum of the slice ({{numerical accuracy notes|https://github.com/pytorch/pytorch/blob/v2.14.1/docs/source/notes/numerical_accuracy.md}}).
