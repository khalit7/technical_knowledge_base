4. The formats ML uses

The question. float64, float32, TF32, float16, bfloat16, FP8, 4-bit: what does each give up, and why did ML move from the first to the last in fifteen years?

Every format is the same recipe with different field widths. The exponent bits decide the range (how large and how small a number can be before overflow or underflow); the mantissa bits decide the precision (\(\varepsilon\), the relative gap). Fewer bits per number means less memory, less memory traffic and more arithmetic per second on the same chip, which is why each new GPU generation added a narrower format. \(\varepsilon = 2^{-m}\) for \(m\) mantissa bits. "Largest" is \((2 - 2^{-m}) \times 2^{E_{\max}}\) for the IEEE-style formats and \((2 - 2^{-(m-1)}) \times 2^{8} = 448\) for E4M3, whose top exponent holds numbers (only S.1111.111 is NaN, and there is no infinity: OFP8 spec, table 2). "\(e^z\) overflows at" is \(\ln\) of the largest value: the logit above which a naive softmax returns infinity, as in the root's {{Gradient lab|n:3c65c17b0d0d81cdb851c0835b25a538}} (709.78, 88.72, 11.09). TF32 is a compute mode, not a storage type: tensors stay float32 in memory, and the tensor core reads "the first 10 bits of the input mantissa" (PyTorch notes, v2.14.1).

Spacing of each format against the size of the number, both on log scales (first view: the range where weights, activations and gradients live). Each line climbs one step per binade (relative precision constant), is flat at the left in the subnormal range (absolute precision constant) and stops at the format's largest value. bfloat16 and float32 cover the same range; bfloat16 sits \(2^{16}\) higher, its gaps 65,536 times wider. float16 is as precise as TF32 but stops at 65,504. What each one is for

  • float64 is NumPy's default and the reference this page checks everything against. GPUs built for ML run it slowly or not at all on tensor cores, so training never uses it.
  • float32 is PyTorch's default dtype and the format of master weights, optimiser state and accumulators in mixed-precision training (section 11). About 7 decimal digits.
  • TF32 keeps float32's range and float16's precision for matrix multiplies on NVIDIA Ampere and later: "TF32 includes an 8-bit exponent (same as FP32), 10-bit mantissa (same precision as FP16), and 1 sign-bit" ({{NVIDIA, May 2020|https://developer.nvidia.com/blog/nvidia-ampere-architecture-in-depth/}}). In PyTorch 2.14.1 it is off by default for matrix multiplies and on for convolutions; the notes recommend torch.backends.cuda.matmul.fp32_precision = "tf32" "if your network does not need full float32 precision" ({{notes|https://github.com/pytorch/pytorch/blob/v2.14.1/docs/source/notes/numerical_accuracy.md}}).
  • float16 has 3 more mantissa bits than bfloat16 but only 5 exponent bits: it overflows at 65,504 and turns anything below \(6 \times 10^{-8}\) into 0. That is why it needs loss scaling (section 11).
  • bfloat16 is float32 with the last 16 bits cut off: same 8 exponent bits, 7 mantissa bits. Google's reasoning: "neural networks are far more sensitive to the size of the exponent than that of the mantissa", and the multipliers are "about half the size in silicon of a typical FP16 multiplier" ({{Wang and Kanwar 2019|https://cloud.google.com/blog/products/ai-machine-learning/bfloat16-the-secret-to-high-performance-on-cloud-tpus}}). Conversion to and from float32 is a shift ({{Kalamkar et al. 2019|https://arxiv.org/abs/1905.12322}}). It is the default training dtype in 2026.
  • FP8 comes in two flavours because forward and backward passes need different things: "E4M3 for weight and activation tensors, and E5M2 for gradient tensors" ({{Micikevicius et al. 2022|https://arxiv.org/abs/2209.05433}}). With only 8 values per binade (E4M3) every tensor needs its own scale factor; how that is chosen per tensor, per row or per tile is the {{Quantization and precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}} page's subject. PyTorch also has float8_e4m3fnuz and float8_e5m2fnuz variants with no negative zero.
  • 4-bit block formats. The OCP Microscaling (MX) spec v1.0 (Sep 2023) defines MXFP8, MXFP6, MXFP4 and MXINT8: blocks of 32 elements sharing one power-of-two scale stored as E8M0 (spec, table 1). MXFP4's elements are E2M1, which can only be \(0, \pm0.5, \pm1, \pm1.5, \pm2, \pm3, \pm4, \pm6\). NVIDIA's NVFP4 (Blackwell) uses blocks of 16 with an E4M3 scale "to each 16-value micro-block" plus "a second-level FP32 scalar applied per tensor" ({{NVIDIA, 24 Jun 2025|https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low-precision-inference/}}). Depth, outliers and measured errors: {{Quantization and precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}, its Bit explorer and One real layer tabs.
Two libraries, two answers for the same FP8 cast (measured)
Converting \(1000\) to E4M3 (largest 448): PyTorch 2.14.1's tensor.to(torch.float8_e4m3fn) returns 448 (it saturates), while ml_dtypes 0.6.0 returns NaN. Both are allowed: the OFP8 spec "requires implementation of saturating and non-saturating modes", and in non-saturating mode an overflowing E4M3 result is NaN (spec, section 5.2 and table 3). E5M2 has infinities, so \(1000\) rounds to 1024 in both. Know which one your kernel does before you trust an FP8 tensor's max.
What it is used for in ML
Reading a training recipe: "bf16 mixed precision" means bf16 matrix multiplies with float32 master weights and accumulators; "FP8 training" means FP8 matrix-multiply inputs with per-tensor or per-block scales and higher-precision accumulation; an inference card's "NVFP4" or "MXFP4" means 4-bit weights with block scales.
