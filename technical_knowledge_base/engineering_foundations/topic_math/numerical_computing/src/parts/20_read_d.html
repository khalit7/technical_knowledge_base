3. The formats ML uses

Every format is the same recipe with different field widths (the hero draws them). Fewer bits per number means less memory, less traffic and more arithmetic per second on the same chip, which is why each GPU generation added a narrower format. All limits below are computed from the bit layouts by recompute.py and agree with NumPy, ml_dtypes and the specifications cited.

\(\varepsilon = 2^{-m}\) for \(m\) mantissa bits. "Largest" is \((2 - 2^{-m}) \times 2^{E_{\max}}\) for the IEEE-style formats and \((2 - 2^{-(m-1)}) \times 2^{8} = 448\) for E4M3, whose top exponent holds numbers (only S.1111.111 is NaN, and there is no infinity: OFP8 spec, table 2). "\(e^z\) overflows at" is \(\ln\) of the largest value: the logit above which a naive softmax returns infinity (709.78, 88.72, 11.09). TF32 is a compute mode, not a storage type: tensors stay float32 in memory, and the tensor core reads "the first 10 bits of the input mantissa" (PyTorch notes, v2.14.1).

Each format's gap grows one step per binade, then the line stops at its largest value

Gap against the size of the number, both on log scales. Each line is flat at the left in the subnormal range (absolute precision constant), then climbs one step per binade (relative precision constant). bfloat16 and float32 cover the same range; bfloat16 sits \(2^{16}\) higher, its gaps 65,536 times wider. float16 is as precise as TF32 but stops at 65,504. Derived from the bit layouts.
  • float64 is NumPy's default and this page's reference; GPUs built for ML run it slowly or not at all on tensor cores, so training never uses it.
  • float32 is PyTorch's default dtype and the format of master weights, optimiser state and accumulators in mixed-precision training (section 9).
  • TF32: "an 8-bit exponent (same as FP32), 10-bit mantissa (same precision as FP16), and 1 sign-bit" for matrix multiplies on NVIDIA Ampere and later ({{NVIDIA, May 2020|https://developer.nvidia.com/blog/nvidia-ampere-architecture-in-depth/}}). In PyTorch 2.14.1 it is off by default for matrix multiplies (details below).
  • float16 has 3 more mantissa bits than bfloat16 but only 5 exponent bits: it overflows at 65,504 and turns anything below \(6 \times 10^{-8}\) into 0, hence loss scaling (section 9).
  • bfloat16 is float32 with the last 16 bits cut off, so conversion is a shift ({{Kalamkar et al. 2019|https://arxiv.org/abs/1905.12322}}). Google's reasoning: "neural networks are far more sensitive to the size of the exponent than that of the mantissa", and the multipliers are "about half the size in silicon of a typical FP16 multiplier" ({{Wang and Kanwar 2019|https://cloud.google.com/blog/products/ai-machine-learning/bfloat16-the-secret-to-high-performance-on-cloud-tpus}}). It is the default training dtype in 2026.
  • FP8 comes in two flavours because the passes need different things: "E4M3 for weight and activation tensors, and E5M2 for gradient tensors" ({{Micikevicius et al. 2022|https://arxiv.org/abs/2209.05433}}). With 8 values per binade every tensor needs its own scale;
  • 4-bit block formats (MXFP4 with an E8M0 scale per 32 elements, NVFP4 with an E4M3 scale per 16 plus a per-tensor FP32 scale), how scales are chosen per tensor, row or tile, and FP8 training as DeepSeek-V3 ran it are {{Quantization and precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}'s subject (its Bit explorer and One real layer tabs). Reading a recipe: "bf16 mixed precision" means bf16 matrix multiplies with float32 master weights and accumulators; "FP8 training" means FP8 matrix-multiply inputs with per-tensor or per-block scales and higher-precision accumulation.
TF32 in PyTorch, and the fnuz FP8 variants

In PyTorch 2.14.1 TF32 is off by default for matrix multiplies and on for convolutions; torch.backends.cuda.matmul.fp32_precision = "tf32" turns it on "if your network does not need full float32 precision" ({{notes|https://github.com/pytorch/pytorch/blob/v2.14.1/docs/source/notes/numerical_accuracy.md}}). PyTorch also has float8_e4m3fnuz and float8_e5m2fnuz variants with no negative zero.

Two libraries, two answers for the same FP8 cast (measured)
Converting \(1000\) to E4M3 (largest 448): PyTorch 2.14.1's tensor.to(torch.float8_e4m3fn) returns 448 (it saturates), while ml_dtypes 0.6.0 returns NaN. Both are allowed: the OFP8 spec "requires implementation of saturating and non-saturating modes", and in non-saturating mode an overflowing E4M3 result is NaN (spec, section 5.2 and table 3). E5M2 has infinities, so \(1000\) rounds to 1024 in both. Know which one your kernel does before you trust an FP8 tensor's max.
