11. Checking any gradient numerically

Compare the analytic gradient with a finite difference. A Taylor expansion, \(f(x \pm h) = f(x) \pm h f'(x) + \tfrac{h^2}{2} f''(x) \pm \tfrac{h^3}{6} f'''(x) + \cdots\), shows how differently the two common differences behave:

\[ \frac{f(x + h) - f(x)}{h} = f'(x) + \frac{h}{2} f''(x) + \cdots, \qquad \frac{f(x + h) - f(x - h)}{2h} = f'(x) + \frac{h^2}{6} f'''(x) + \cdots \]

The central difference's error falls a hundredfold per tenfold smaller step

0.14.2e-31.1e-4
0.014.1e-41.1e-6
0.0014.1e-51.1e-8

On the tiny model's \(\partial L/\partial z_{\text{sat}} = -0.90997\), float64 (src/recompute.py): the one-sided error is proportional to \(h\), the central one to \(h^2\), as the expansion predicts. Too small an \(h\) loses again to rounding, because \(f(x + h) - f(x - h)\) subtracts two nearly equal numbers; the root's {{Gradient lab|n:3c65c17b0d0d81cdb851c0835b25a538}} plots the full V shape, where rounding takes over below about \(h = 10^{-6}\).

  • Use float64. In float32 the rounding floor is about \(10^{-7}\) relative, and a correct gradient can fail: the correct fused softmax cross-entropy below fails gradcheck in float32 with "Jacobian mismatch". The documentation warns: "The default values are designed for input of double precision" ({{torch.autograd.gradcheck|https://docs.pytorch.org/docs/stable/generated/torch.autograd.gradcheck.gradcheck.html}}; defaults eps \(10^{-6}\), atol \(10^{-5}\), rtol \(10^{-3}\)). Machine epsilon and catastrophic cancellation are sections 3 and 6 of {{Numerical computing for ML|n:3f05c17b0d0d81d6af0be4a9a2edba8d}}.
  • Compare relatively: \(|a - n| / \max(1, |a|, |n|)\), so that large and small gradients are judged alike.
  • Check a VJP with one random probe. To check a layer's backward without building its Jacobian, pick a random \(\bar y\) and differentiate the scalar \(\bar y \cdot f(x)\) numerically: its gradient is exactly \(J^\top \bar y\). The workbench in section 6 checks every layer this way.
  • Avoid kinks: ReLU at exactly 0, max-pooling ties and absolute values make finite differences straddle a corner. Check at points away from them.

What a check catches. The most common bug in a hand-written backward rule is forgetting that a VJP must multiply by the incoming gradient. It goes unnoticed when the function is the last thing before .sum().backward() (the incoming gradient is then 1) and breaks as soon as anything is downstream; gradcheck reports it at once.

A custom backward for softmax cross-entropy, its gradcheck, and the buggy version, run for real (2 min)

Write your own backward when the composed rule is numerically poor (it divides by a tiny probability, as in 6d), when it saves more than needed (keep \(p\) instead of every intermediate), when a fused kernel hides its inside from the framework, or when you deliberately want a different "gradient" (a straight-through estimator for rounding in quantisation-aware training). PyTorch's recipe: "Subclass Function and implement the forward(), (optional) setup_context() and backward() methods"; "backward() (or vjp()) defines the gradient formula. It will be given as many Tensor arguments as there were outputs, with each of them representing gradient w.r.t. that output ... It should return as many tensors as there were inputs"; and "save_for_backward() should be used to save any tensors needed for the backward pass" ({{Extending PyTorch|https://docs.pytorch.org/docs/stable/notes/extending.html}}). The mechanics of autograd.Function are on {{Tensors, the dispatcher and autograd|n:3f85c17b0d0d81138595c1c6cd52f795}}.

class SoftmaxCE(torch.autograd.Function):
    @staticmethod
    def forward(z, y):
        logp = z - torch.logsumexp(z, dim=-1, keepdim=True)
        return -logp.gather(-1, y[..., None]).squeeze(-1)

    @staticmethod
    def setup_context(ctx, inputs, output):
        z, y = inputs
        ctx.save_for_backward(torch.softmax(z, dim=-1), y)   # keep p, not the logits

    @staticmethod
    def backward(ctx, gL):
        p, y = ctx.saved_tensors
        gz = p.clone()
        gz.scatter_add_(-1, y[..., None], -torch.ones_like(y, dtype=p.dtype)[..., None])  # p - onehot
        return gL[..., None] * gz, None                      # times the incoming gradient; y gets none

12. What autograd records

PyTorch's autograd is reverse-mode AD run on a graph recorded afresh on every forward pass (which is what lets ordinary Python control flow decide the graph): each operation adds a backward node, which is that operation's VJP rule from section 6, and saves the tensors the rule needs (section 9). loss.backward() starts at the root with gradient 1 and runs each node once all its incoming gradients have arrived; a parameter's node adds the result into .grad. Here is the tiny model, run for real (PyTorch 2.14.1, src/inputs/measure/tiny_autograd.py):

x = torch.tensor([2., 1.], requires_grad=True)
W = torch.tensor([[1., 0.], [0., 1.], [1., -2.]], requires_grad=True)
L = F.cross_entropy((W @ x)[None], torch.tensor([2]))
# walking L.grad_fn and each node's next_functions prints:
NllLossBackward0     -> LogSoftmaxBackward0   saved: self (1, 3), target (1,), total_weight ()
LogSoftmaxBackward0  -> UnsqueezeBackward0    saved: result (1, 3)
UnsqueezeBackward0   -> MvBackward0           saved: nothing
MvBackward0          -> AccumulateGrad (W), AccumulateGrad (x)   saved: self (3, 2), vec (2,)
# the saved tensors are the very objects W and x, not copies:
z.grad_fn._saved_self is W, z.grad_fn._saved_vec is x   ->  True True

MvBackward0 is rule 6a; LogSoftmaxBackward0 and NllLossBackward0 are the two halves of 6d. Saved tensors are references, so a saved weight costs nothing extra; a saved activation is the memory of section 9. How the engine schedules nodes, version counters for in-place safety, retain_graph, hooks and no_grad are {{Tensors, the dispatcher and autograd|n:3f85c17b0d0d81138595c1c6cd52f795}}'s subject. JAX traces the function into a jaxpr, applies forward mode with jax.jvp, extracts the linear map with jax.linearize and gets reverse mode by transposing it (jax.vjp; jax.grad is vjp with the cotangent 1); run on the tiny model in float64 it gives the same \(\bar W\) and \(\bar x\) as PyTorch to the last digit, and its backward dot_general contracts \(W\)'s rows where the forward one contracted its columns: the transpose of rule 6a, produced mechanically ({{JAX core|n:3c65c17b0d0d81b7a0d1faba6cef5561}}). torch.func offers the same function transforms on PyTorch's engine: grad, vjp, jvp, jacrev, jacfwd, hessian and vmap, which gives per-example gradients in one call.
