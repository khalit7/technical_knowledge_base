10. How PyTorch autograd and JAX actually do it

The question. You call loss.backward() and every .grad fills in. What happened?

PyTorch: a graph recorded while the forward pass runs

The documentation describes it in three sentences: "Autograd is a reverse automatic differentiation system. Conceptually, autograd records a graph recording all of the operations that created the data as you execute operations, giving you a directed acyclic graph whose leaves are the input tensors and roots are the output tensors." Each operation adds a node (a Function), and "the .grad_fn attribute of each torch.Tensor is an entry point into this graph". And "the graph is recreated from scratch at every iteration, and this is exactly what allows for using arbitrary Python control flow statements" ({{Autograd mechanics|https://docs.pytorch.org/docs/stable/notes/autograd.html}}).

Here is the tiny model, run for real (PyTorch 2.14.1; the script is src/inputs/measure/tiny_autograd.py):

x = torch.tensor([2., 1.], requires_grad=True)
W = torch.tensor([[1., 0.], [0., 1.], [1., -2.]], requires_grad=True)
L = F.cross_entropy((W @ x)[None], torch.tensor([2]))
# walking L.grad_fn and each node's next_functions prints:
NllLossBackward0     -> LogSoftmaxBackward0   saved: self (1, 3), target (1,), total_weight ()
LogSoftmaxBackward0  -> UnsqueezeBackward0    saved: result (1, 3)
UnsqueezeBackward0   -> MvBackward0           saved: nothing
MvBackward0          -> AccumulateGrad (W), AccumulateGrad (x)   saved: self (3, 2), vec (2,)
# the saved tensors are the very objects W and x, not copies:
z.grad_fn._saved_self is W, z.grad_fn._saved_vec is x   ->  True True
  • Nodes and edges. Each node is the backward rule of one operation: MvBackward0 is the matrix-vector product's VJP from section 5a, LogSoftmaxBackward0 and NllLossBackward0 the two halves of 5d. Its next_functions point to the nodes that produced its inputs. A leaf tensor that requires a gradient ends in an AccumulateGrad node, which adds the arriving gradient into .grad.
  • Saved tensors. "Some operations need intermediary results to be saved during the forward pass in order to execute the backward pass", and you can see them "by looking for its attributes starting with the prefix _saved" (same page). They are references, so a saved weight costs nothing extra; a saved activation is the memory of section 9.
  • The backward pass starts at the root with gradient 1, calls each node's backward rule once all its incoming gradients have arrived, and frees the saved tensors as it goes. Calling L.backward() a second time therefore fails: "Trying to backward through the graph a second time (or directly access saved tensors after they have already been freed)" (the real error; pass retain_graph=True to keep them).
  • Gradients accumulate. AccumulateGrad adds, it does not overwrite. That is what lets a weight used twice receive both contributions (section 4), and why training loops call optimizer.zero_grad() (or set .grad to None) before each step; forgetting it is one of the root page's eight gradient bugs.
  • In-place safety. "Every tensor keeps a version counter, that is incremented every time it is marked dirty in any operation. When a Function saves any tensors for backward, a version counter of their containing Tensor is saved as well." If a saved tensor was modified in place, backward raises "one of the variables needed for gradient computation has been modified by an inplace operation" (real output for b = a.exp(); b.add_(1), since exp saves its result).
  • No graph at all under torch.no_grad() or torch.inference_mode(): nothing is recorded or saved, which is why inference held 0 bytes of activations in section 9.

The {{Real autograd graph|#t-graph}} tab does the same walk for one tiny transformer block and the loss: 71 nodes, 13 of them AccumulateGrad, every saved tensor with its shape, and the order the engine actually ran them.

torch.func: derivatives as function transforms

torch.func (formerly functorch) offers the JAX-style interface on the same engine: grad(f) returns a function that computes the gradient; vjp(f, x) returns \(f(x)\) and a function \(v \mapsto J^\top v\); jvp(f, (x,), (u,)) returns \(f(x)\) and \(Ju\); jacrev, jacfwd and hessian build whole Jacobians; and vmap vectorises any of them, which gives per-example gradients in one call. The measurements in sections 7 and 12 use these.

JAX: trace, then transform the trace

JAX traces a Python function into a small typed program, a jaxpr, and differentiates that program: jax.jvp applies forward mode, jax.linearize extracts the linear map, and reverse mode is obtained by transposing the linear map, which is jax.vjp; jax.grad is vjp with the cotangent 1. Run on the tiny model (JAX 0.11.2, float64), jax.grad gives the same \(\bar W\) and \(\bar x\) as PyTorch to the last digit, and its jaxpr for \(\bar x\) ends with the backward pass written out (excerpt; the full program is in src/inputs/measure/jax.json):

    ba:f64[3] = pad[padding_config=((2, np.int64(0), 0),)] z 0.0:f64[]   # -1 at the sat position: the gradient of -z[y]
    bb:f64[] = div 1.0:f64[] s                                         # 1 / sum(exp)
    ...
    bh:f64[3] = mul bg q                                               # exp(z - max) / sum: the softmax p
    bi:f64[3] = add_any ba bh                                          # p - onehot
    bj:f64[2] = dot_general[
      dimension_numbers=(([0], [0]), ([], []))                         # contract over the 3 words: W^T (p - y)
      preferred_element_type=float64
    ] bi a
  in (bj,) }

Comments added; lines between bb and bh omitted. The forward program's dot_general contracted \(W\)'s columns with \(x\) (dimension numbers ([1], [0])); the backward one contracts \(W\)'s rows with the cotangent (([0], [0])): the transpose of section 5a, produced mechanically.

On cost, JAX's documentation gives the same picture as section 7: for a VJP "the FLOP cost ... is only about three times the cost of evaluating f", and "though the FLOPs are friendly, memory scales with the depth of the computation"; for a JVP "the memory cost is independent of the depth of the computation" ({{JAX, The Autodiff Cookbook|https://docs.jax.dev/en/latest/notebooks/autodiff_cookbook.html}}). Its rule for whole Jacobians: "jacfwd ... is more efficient for "tall" Jacobian matrices (more outputs than inputs), while jacrev ... is more efficient for "wide" Jacobian matrices".
