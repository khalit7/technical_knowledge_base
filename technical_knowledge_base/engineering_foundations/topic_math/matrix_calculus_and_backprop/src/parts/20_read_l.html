11. Writing your own backward, and checking any gradient

The question. When should you write a backward rule by hand, and how do you know it is right?

Custom backward functions

Autograd's own rules are usually right and fast. Write your own when the composed rule is numerically poor (it divides by a tiny probability, as in 5d), when it saves more memory than needed (keep \(p\) instead of every intermediate), when you have a fused kernel the framework cannot see inside, or when you deliberately want a different "gradient" (a straight-through estimator for rounding in quantisation-aware training). PyTorch's recipe: "Subclass Function and implement the forward(), (optional) setup_context() and backward() methods"; "backward() (or vjp()) defines the gradient formula. It will be given as many Tensor arguments as there were outputs, with each of them representing gradient w.r.t. that output ... It should return as many tensors as there were inputs"; and "save_for_backward() should be used to save any tensors needed for the backward pass" ({{Extending PyTorch|https://docs.pytorch.org/docs/stable/notes/extending.html}}). Here is the fused softmax cross-entropy of 5d, run for real:

class SoftmaxCE(torch.autograd.Function):
    @staticmethod
    def forward(z, y):
        logp = z - torch.logsumexp(z, dim=-1, keepdim=True)
        return -logp.gather(-1, y[..., None]).squeeze(-1)

    @staticmethod
    def setup_context(ctx, inputs, output):
        z, y = inputs
        ctx.save_for_backward(torch.softmax(z, dim=-1), y)   # keep p, not the logits

    @staticmethod
    def backward(ctx, gL):
        p, y = ctx.saved_tensors
        gz = p.clone()
        gz.scatter_add_(-1, y[..., None], -torch.ones_like(y, dtype=p.dtype)[..., None])  # p - onehot
        return gL[..., None] * gz, None                      # times the incoming gradient; y gets none

Script and output: src/inputs/measure/custom_fn.py, custom_fn.out. The first row is the tiny model: loss 2.408, gradient \(p - y\).

The bug in the second version is the most common one in hand-written backward functions: forgetting that a VJP must multiply by the incoming gradient. It goes unnoticed when the function is the last thing before .sum().backward() (the incoming gradient is then 1) and breaks as soon as anything is downstream. JAX's equivalent is jax.custom_vjp (forward returns the output and the residuals to save; backward maps residuals and cotangent to input cotangents).

Gradient checking

Compare the analytic gradient with a finite difference. The two common differences have very different accuracy, which a Taylor expansion shows: \(f(x \pm h) = f(x) \pm h f'(x) + \tfrac{h^2}{2} f''(x) \pm \tfrac{h^3}{6} f'''(x) + \cdots\), so

\[ \frac{f(x + h) - f(x)}{h} = f'(x) + \frac{h}{2} f''(x) + \cdots, \qquad \frac{f(x + h) - f(x - h)}{2h} = f'(x) + \frac{h^2}{6} f'''(x) + \cdots \]

The one-sided difference has an error proportional to \(h\); the central difference cancels the \(h^2\) terms and its error is proportional to \(h^2\). Too small an \(h\) loses again to rounding, because \(f(x + h) - f(x - h)\) subtracts two nearly equal numbers.

Practical rules:

  • Use float64. In float32 the rounding floor is about \(10^{-7}\) relative, and a correct gradient can fail: the correct SoftmaxCE above fails gradcheck in float32 with the same "Jacobian mismatch" error. The documentation warns: "The default values are designed for input of double precision" ({{torch.autograd.gradcheck|https://docs.pytorch.org/docs/stable/generated/torch.autograd.gradcheck.gradcheck.html}}; defaults eps \(10^{-6}\), atol \(10^{-5}\), rtol \(10^{-3}\)). Why: a finite difference subtracts two nearly equal losses, so it keeps only the digits the format has left after cancellation; machine epsilon and catastrophic cancellation are sections 3 and 6 of {{Numerical computing for ML: floating point, precision formats, stable softmax|n:3f05c17b0d0d81d6af0be4a9a2edba8d}}.
  • Compare relatively: \(|a - n| / \max(1, |a|, |n|)\), so that large and small gradients are judged alike.
  • Check a VJP with one random probe. To check a layer's backward without building its Jacobian, pick a random \(\bar y\) and differentiate the scalar \(\bar y \cdot f(x)\) numerically: its gradient is exactly \(J^\top \bar y\), the VJP. The {{Derivative workbench|#t-bench}} checks every layer this way.
  • Avoid kinks: ReLU at exactly 0, max-pooling ties and absolute values make finite differences straddle a corner. Check at points away from them.
