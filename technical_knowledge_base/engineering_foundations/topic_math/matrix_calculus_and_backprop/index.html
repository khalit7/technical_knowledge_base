1. Functions of a vector: the gradient

The question. A loss depends on many numbers at once. How do you describe how it changes when all of them can move?

The picture first

Think of a function of two numbers, f(x1,x2)f(x_1, x_2), as the height of a landscape above the point (x1,x2)(x_1, x_2). Standing at one point, you can ask how steeply the ground rises if you walk due east (only x1x_1 changes) and how steeply if you walk due north (only x2x_2 changes). Those two slopes are the partial derivatives. Every other direction's slope is a mix of them, so those two numbers describe the whole tilt of the ground at that point.

The words, then the formula

For a function that takes a vector xx with nn entries and returns one number (a scalar), the partial derivative ∂f/∂xi\partial f / \partial x_i is the slope along entry ii with every other entry held fixed. Stacking all nn of them gives the gradient:

∇xf=(∂f∂x1,∂f∂x2,…,∂f∂xn)\nabla_x f = \left( \frac{\partial f}{\partial x_1}, \frac{\partial f}{\partial x_2}, \ldots, \frac{\partial f}{\partial x_n} \right)
∇xf\nabla_x f
"grad of ff with respect to xx": a vector with one slope per entry of xx, so it has the same shape as xx.
∂\partial
the curly d of a partial derivative: "only this input moves".

What the gradient is for: it gives the best straight-line (linear) prediction of how ff changes for any small step δ\delta,

f(x+δ)≈f(x)+∇xf⋅δ=f(x)+∑i∂f∂xiδif(x + \delta) \approx f(x) + \nabla_x f \cdot \delta = f(x) + \sum_i \frac{\partial f}{\partial x_i}\,\delta_i

In plain words: the change in output is each input's change times that input's slope, added up. The slope along a unit direction uu (the directional derivative) is ∇xf⋅u\nabla_x f \cdot u. It is largest when uu points along the gradient, which is why the gradient is the direction of steepest increase and why training steps the other way.

Worked example
f(x1,x2)=x12+3x1x2f(x_1, x_2) = x_1^2 + 3x_1x_2 at x=(2,1)x = (2, 1), where f=4+6=10f = 4 + 6 = 10. Holding x2x_2 fixed, ∂f/∂x1=2x1+3x2=7\partial f/\partial x_1 = 2x_1 + 3x_2 = 7; holding x1x_1 fixed, ∂f/∂x2=3x1=6\partial f/\partial x_2 = 3x_1 = 6. So ∇f=(7,6)\nabla f = (7, 6). Prediction for the step δ=(0.01,0)\delta = (0.01, 0): 10+7×0.01=10.0710 + 7 \times 0.01 = 10.07; the exact value is 2.012+3×2.01=10.07012.01^2 + 3 \times 2.01 = 10.0701. Along the unit direction u=(0.6,0.8)u = (0.6, 0.8) the slope is 7×0.6+6×0.8=9.07 \times 0.6 + 6 \times 0.8 = 9.0, a little under the steepest possible slope ‖∇f‖=85=9.22\lVert \nabla f \rVert = \sqrt{85} = 9.22.

A scalar of a matrix: the gradient is a matrix

Nothing changes when the input is a matrix: one partial derivative per entry, arranged in the same rows and columns. For the tiny model's loss as a function of the 3×23 \times 2 weight matrix, ∇WL\nabla_W L is also 3×23 \times 2. Rule: the gradient of a scalar has the shape of the thing you differentiate with respect to. It is the most useful sanity check in this whole subject, and it is exactly what PyTorch stores in W.grad.

2. Functions that return a vector: the Jacobian, and the shape of every derivative

The question. A layer does not return one number; it returns a vector. Each output can respond to each input. How do you hold all those slopes?

A function ff that takes nn numbers and returns mm numbers (written f:ℝn→ℝmf: \mathbb{R}^n \to \mathbb{R}^m, where ℝn\mathbb{R}^n means "lists of nn real numbers") has one slope for every (output, input) pair. Arranged as a table with one row per output and one column per input, they form the Jacobian (after Carl Jacobi):

J=∂f∂x=(∂f1∂x1⋯∂f1∂xn⋮⋱⋮∂fm∂x1⋯∂fm∂xn),Jij=∂fi∂xj,J is m×nJ = \frac{\partial f}{\partial x} = \begin{pmatrix} \frac{\partial f_1}{\partial x_1} & \cdots & \frac{\partial f_1}{\partial x_n} \\ \vdots & \ddots & \vdots \\ \frac{\partial f_m}{\partial x_1} & \cdots & \frac{\partial f_m}{\partial x_n} \end{pmatrix}, \qquad J_{ij} = \frac{\partial f_i}{\partial x_j}, \quad J \text{ is } m \times n

Row ii is the gradient of output ii, laid flat. Column jj says how every output responds when only input jj moves. The linear prediction now reads f(x+δ)≈f(x)+Jδf(x + \delta) \approx f(x) + J\delta: a matrix times the step.

Three Jacobians to know

A linear map. For z=Wxz = Wx, each output is zi=∑jWijxjz_i = \sum_j W_{ij} x_j, so nudging xjx_j moves ziz_i by WijW_{ij} per unit: ∂zi/∂xj=Wij\partial z_i / \partial x_j = W_{ij}. The Jacobian of a matrix-vector product with respect to the vector is the matrix itself, J=WJ = W, here 3×23 \times 2.

An elementwise function. For h=ϕ(a)h = \phi(a) applied entry by entry (a ReLU, a tanh), output ii depends only on input ii, so the Jacobian is diagonal: J=diag⁡(ϕ′(a))J = \operatorname{diag}(\phi'(a)), the matrix with the slopes ϕ′(ai)\phi'(a_i) on the diagonal and zeros elsewhere.

Softmax, derived without skipping a step. Write pi=ezi/Sp_i = e^{z_i} / S with S=∑kezkS = \sum_k e^{z_k}. Two cases.

  1. The same index, j=ij = i. The quotient rule (slope of top over bottom = (top' times bottom minus top times bottom') over bottom squared), with ∂ezi/∂zi=ezi\partial e^{z_i}/\partial z_i = e^{z_i} and ∂S/∂zi=ezi\partial S/\partial z_i = e^{z_i}:
    ∂pi∂zi=eziS−ezieziS2=pi−pi2=pi(1−pi)\frac{\partial p_i}{\partial z_i} = \frac{e^{z_i} S - e^{z_i} e^{z_i}}{S^2} = p_i - p_i^2 = p_i(1 - p_i)
  2. A different index, j≠ij \ne i. The top does not move, the bottom does:
    ∂pi∂zj=0⋅S−eziezjS2=−pipj\frac{\partial p_i}{\partial z_j} = \frac{0 \cdot S - e^{z_i} e^{z_j}}{S^2} = -p_i p_j

    ∂pi∂zj=pi(δij−pj),Jsoftmax=diag⁡(p)−pp⊤\frac{\partial p_i}{\partial z_j} = p_i(\delta_{ij} - p_j), \qquad J_{\text{softmax}} = \operatorname{diag}(p) - p\,p^\top
    where pp⊤p\,p^\top is the outer product: column times row, a square table whose entry (i,j)(i, j) is pipjp_i p_j.

The shape of every derivative

The derivative of an output with aa entries with respect to an input with bb entries holds a×ba \times b numbers. That gives a small table, where WW is a p×qp \times q matrix:

The bottom-right corner is where matrix calculus gets its reputation. The good news for ML: you never need it. The loss is a scalar, so the only derivatives that must be stored are in the top row, and each has the shape of its parameter. The big arrays appear only in the middle of the chain rule, and section 5 shows that they can always be skipped.

Why the big arrays are wasteful
The derivative of z=Wxz = Wx (3 numbers) with respect to WW (6 numbers) is a 3×3×23 \times 3 \times 2 array of 18 numbers: ∂zi/∂Wkl=δikxl\partial z_i / \partial W_{kl} = \delta_{ik}\, x_l (score ii depends only on row ii of WW). Twelve of the 18 are zero. For one real layer with a 4096×40964096 \times 4096 weight, the same array would have 40963≈6.9×10104096^3 \approx 6.9 \times 10^{10} entries, almost all zero.

3. Numerator and denominator layout: why papers disagree

The question. A paper writes ∂L/∂W\partial L/\partial W and its shape is the transpose of W.grad. Is one of them wrong?

Neither. The slopes are the same numbers; the disagreement is only about which way round to write the table. There are two conventions for ∂y/∂x\partial y/\partial x when yy has mm entries and xx has nn:

Numerator layout (the Jacobian convention)

Rows follow the thing on top (the numerator, yy): ∂y/∂x\partial y/\partial x is m×nm \times n, the Jacobian of section 2. The derivative of a scalar with respect to a vector is then a row (1×n1 \times n). The chain rule reads left to right in the same order as the composition.

Denominator layout (the gradient convention)

Rows follow the thing underneath (the denominator, xx): ∂y/∂x\partial y/\partial x is n×mn \times m, the transpose. The derivative of a scalar with respect to a vector is then a column shaped like xx, which is what an update x←x−η∇xLx \leftarrow x - \eta \nabla_x L needs.

Why papers disagree. There is no field-wide standard, and many authors mix the two. Wikipedia's survey of the conventions puts it plainly: "even within a given field different authors can be found using competing conventions. Authors of both groups often write as though their specific conventions were standard", and "some choose denominator layout for gradients (laying them out as column vectors), but numerator layout for the vector-by-vector derivative" (Wikipedia, Matrix calculus, Layout conventions). Two of the best-known ML texts use numerator layout and say so: Deisenroth, Faisal and Ong, "In this book, we use the numerator layout of the derivative" (Mathematics for Machine Learning, section 5.3, p. 150; they also write the gradient as a row vector, Eq. 5.40), and Parr and Howard, "We are using the so-called numerator layout but many papers and software will use the denominator layout" (The Matrix Calculus You Need For Deep Learning, section 4). Their reason is the chain rule: in numerator layout it reads left to right with no transposes.

4. The chain rule in matrix form

The question. A network is a chain of layers. Each layer's Jacobian is easy on its own. How do they combine, and in which order should you multiply them?

Derived from the linear prediction

Let y=g(x)y = g(x) and z=f(y)z = f(y). A small step δx\delta x moves yy by about JgδxJ_g\,\delta x (section 2), and that moves zz by about JfJ_f times it:

δz≈Jfδy≈JfJgδx⟹Jf∘g(x)=Jf(g(x))Jg(x)\delta z \approx J_f\,\delta y \approx J_f\,J_g\,\delta x \qquad\Longrightarrow\qquad J_{f \circ g}(x) = J_f\big(g(x)\big)\; J_g(x)
f∘gf \circ g
"ff after gg": apply gg, then ff.
Jf(g(x))J_f(g(x))
the Jacobian of ff evaluated at the value yy that gg actually produced, which is why the backward pass needs the forward pass's values.

In plain words: the Jacobian of a chain is the product of the Jacobians, in the order of the chain. Entry by entry, ∂zi∂xk=∑j∂zi∂yj∂yj∂xk\frac{\partial z_i}{\partial x_k} = \sum_j \frac{\partial z_i}{\partial y_j}\frac{\partial y_j}{\partial x_k}: add up the effect of xkx_k on ziz_i through every intermediate yjy_j. The shapes line up by themselves: (m×p)(m \times p) times (p×n)(p \times n) gives m×nm \times n.

For a scalar loss: the vector-Jacobian product

When the last function is the loss, its Jacobian is a single row, ∂L/∂y\partial L/\partial y. Written as gradients (columns shaped like the variables), the chain rule becomes

∇xL=Jg⊤∇yL(row form: ∂L∂x=∂L∂yJg)\nabla_x L = J_g^\top\, \nabla_y L \qquad\text{(row form: } \tfrac{\partial L}{\partial x} = \tfrac{\partial L}{\partial y}\,J_g \text{)}

This is the vector-Jacobian product (VJP): the gradient arriving at a layer's output, y‾=∇yL\bar y = \nabla_y L, multiplied by the layer's Jacobian, gives the gradient at the layer's input, x‾=J⊤y‾\bar x = J^\top \bar y. The bar notation, v‾\bar v for "the gradient of the loss with respect to vv, shaped like vv", is the one used in the autodiff literature and in the rest of this page.

The famous "prediction minus target" is just two VJPs multiplied out.

Order matters: multiply from the loss end

For a chain of kk layers, ∂L∂x=∂L∂hkJkJk−1⋯J1\frac{\partial L}{\partial x} = \frac{\partial L}{\partial h_k} J_k J_{k-1} \cdots J_1. Matrix multiplication is associative, so any bracketing gives the same answer, but not the same cost. Starting at the loss, every product is a row times a matrix: for layers of width dd, d2d^2 multiply-adds each, kd2k d^2 in all. Starting at the input, every product is a matrix times a matrix: d3d^3 each. At d=4096d = 4096 that is a factor of 4096. Section 7 turns this into the two modes of automatic differentiation.

Several paths: gradients add

When one value feeds two places, the sum over intermediates in the chain rule becomes a sum over paths. Two cases matter in every transformer:

  • A residual connection y=x+F(x)y = x + F(x) has Jacobian I+JFI + J_F, so x‾=y‾+JF⊤y‾\bar x = \bar y + J_F^\top \bar y: the gradient arrives once through the identity path, untouched, and once through the block. That untouched copy is why very deep residual networks still train.
  • A weight used twice, such as an embedding matrix tied to the output layer: its gradient is the sum of the gradients from both uses. In the Real autograd graph, the embedding's accumulator is the very last node the engine runs, because it waits for both contributions.

5. The layer gradients worth knowing cold, each derived

The question. Autograd computes these for you. Why derive them? Because reading a paper, writing a fused kernel, debugging a NaN or answering an interview question all start from them, and because each one teaches the same three moves: write one output entry with indices, differentiate, and recognise the result as a matrix product.

Every derivation below gives the backward rule of one layer: given y‾\bar y (the gradient arriving at the output, same shape as yy), return the gradient for each input. The Derivative workbench runs each one on numbers you can change and checks it against finite differences.

5a. Linear layer: y=Wx+by = Wx + b

Shapes: xx has nn entries, WW is m×nm \times n, bb and yy have mm.

  1. One output entry: yk=∑jWkjxj+bky_k = \sum_j W_{kj}\,x_j + b_k.
  2. The weight WijW_{ij} appears only in output k=ik = i, multiplied by xjx_j, so ∂yk/∂Wij=δkixj\partial y_k/\partial W_{ij} = \delta_{ki}\,x_j. The chain rule sums over outputs: W‾ij=∑ky‾kδkixj=y‾ixj\bar W_{ij} = \sum_k \bar y_k\,\delta_{ki}\,x_j = \bar y_i\,x_j.
  3. The input xjx_j appears in every output, multiplied by WkjW_{kj}: x‾j=∑ky‾kWkj\bar x_j = \sum_k \bar y_k\,W_{kj}.
  4. The bias bkb_k appears once with slope 1: b‾k=y‾k\bar b_k = \bar y_k.
  5. Recognise the matrix forms:
    W‾=y‾x⊤(m×n),x‾=W⊤y‾(n),b‾=y‾(m)\bar W = \bar y\,x^\top \;(m \times n), \qquad \bar x = W^\top \bar y \;(n), \qquad \bar b = \bar y \;(m)

A batch. PyTorch's nn.Linear stores WW as (out, in) and computes Y=XW⊤+bY = XW^\top + b for a batch XX of shape B×nB \times n, one example per row. The same three moves give

W‾=Y‾⊤X(m×n),X‾=Y‾W(B×n),b‾=∑rowsY‾(m)\bar W = \bar Y^\top X \;(m \times n), \qquad \bar X = \bar Y\,W \;(B \times n), \qquad \bar b = \textstyle\sum_{\text{rows}} \bar Y \;(m)

In plain words: a weight's gradient is (gradient coming in) times (input that went in), summed over the batch; an input's gradient is the gradient coming in sent back through the transposed weights; a bias that was added to every row collects the sum of every row's gradient. Y‾⊤X\bar Y^\top X is the sum over examples of one outer product each, so one example's weight gradient has rank 1 and a batch's has rank at most BB.

5c. Softmax: the VJP without the Jacobian

Multiply the Jacobian of section 2 by an incoming gradient p‾\bar p and simplify; it is symmetric, so J⊤=JJ^\top = J:

z‾=(diag⁡(p)−pp⊤)p‾=p⊙p‾−p(p⋅p‾)=p⊙(p‾−(p⋅p‾)𝟏)\bar z = \big(\operatorname{diag}(p) - p\,p^\top\big)\,\bar p = p \odot \bar p - p\,(p \cdot \bar p) = p \odot \big(\bar p - (p \cdot \bar p)\,\mathbf{1}\big)

In plain words: subtract from each incoming gradient the probability-weighted average of all of them, then scale by the probability. Cost: one dot product and one pass over the KK entries, O(K)O(K), against O(K2)O(K^2) to build the Jacobian. For a 128,000-word vocabulary that is the difference between a vector and a table of 16 billion numbers per token. PyTorch's softmax node saves only its output pp (_softmax_backward_data(grad, result, dim, ...), derivatives.yaml line 2237).

5d. Softmax cross-entropy: two VJPs that collapse

The root page derives ∇zL=p−y\nabla_z L = p - y by writing L=−zy+ln⁡∑jezjL = -z_y + \ln \sum_j e^{z_j} (Topic: math, Reading section 4). Here is the same result as a composition, which shows why frameworks fuse the two layers.

  1. The loss L=−ln⁡pyL = -\ln p_y has p‾k=−1/py\bar p_k = -1/p_y for the right word and 0 for the others: p‾=−𝟏y/py\bar p = -\mathbf{1}_y / p_y, where 𝟏y\mathbf{1}_y is the one-hot vector of the right word. It divides by pyp_y, which can be tiny.
  2. Its dot product with pp is p⋅p‾=−py/py=−1p \cdot \bar p = -p_y/p_y = -1.
  3. Softmax's VJP (5c): z‾=p⊙(p‾+𝟏)=p⊙𝟏−p⊙𝟏y/py=p−𝟏y\bar z = p \odot (\bar p + \mathbf{1}) = p \odot \mathbf{1} - p \odot \mathbf{1}_y / p_y = p - \mathbf{1}_y.

The division by pyp_y cancels exactly. Computed separately, a probability that underflows to 0 would give p‾=−∞\bar p = -\infty and a NaN; fused, the gradient is just the probabilities minus the target. That is why F.cross_entropy takes logits, and why PyTorch's graph shows LogSoftmaxBackward0 feeding NllLossBackward0 (see the Real autograd graph): log-softmax is computed stably once and saved. For a batch averaged over BB examples (reduction="mean"), each row's gradient is (p−𝟏y)/B(p - \mathbf{1}_y)/B; with label smoothing or distillation targets qq, it is p−qp - q.

5e. Layer norm, derived completely

Layer norm (Ba, Kiros and Hinton 2016) rescales each token's vector xx (with NN entries) to mean 0 and variance 1, then applies a learned scale γ\gamma and shift β\beta:

μ=1N∑ixi,σ2=1N∑i(xi−μ)2,r=1σ2+ϵ,xˆi=(xi−μ)r,yi=γixˆi+βi\mu = \frac{1}{N}\sum_i x_i, \quad \sigma^2 = \frac{1}{N}\sum_i (x_i - \mu)^2, \quad r = \frac{1}{\sqrt{\sigma^2 + \epsilon}}, \quad \hat x_i = (x_i - \mu)\,r, \quad y_i = \gamma_i \hat x_i + \beta_i
rr
the reciprocal standard deviation (PyTorch calls it rstd); ϵ\epsilon (default 10−510^{-5}) keeps it finite.
xˆ\hat x
the normalised vector.
  1. The easy ones: yi=γixˆi+βiy_i = \gamma_i \hat x_i + \beta_i gives γ‾=y‾⊙xˆ\bar\gamma = \bar y \odot \hat x and β‾=y‾\bar\beta = \bar y (summed over the tokens of a batch), and passes gˆ:=xˆ‾=y‾⊙γ\hat g := \bar{\hat x} = \bar y \odot \gamma to the normalisation.
  2. xˆi\hat x_i depends on xjx_j through three routes: directly, through μ\mu and through rr. The first two give r(δij−1N)r\,(\delta_{ij} - \tfrac{1}{N}), because ∂μ/∂xj=1/N\partial \mu/\partial x_j = 1/N.
  3. The variance: ∂σ2/∂xj=2N(xj−μ)\partial \sigma^2/\partial x_j = \tfrac{2}{N}(x_j - \mu). (Its route through μ\mu contributes −2N2∑i(xi−μ)=0-\tfrac{2}{N^2}\sum_i (x_i - \mu) = 0, because deviations from the mean add up to 0.)
  4. So ∂r/∂xj=−12(σ2+ϵ)−3/2⋅2N(xj−μ)\partial r/\partial x_j = -\tfrac{1}{2}(\sigma^2 + \epsilon)^{-3/2} \cdot \tfrac{2}{N}(x_j - \mu) =−r3N(xj−μ)=−r2Nxˆj= -\tfrac{r^3}{N}(x_j - \mu) = -\tfrac{r^2}{N}\hat x_j.

6. Differentials and the trace trick: derive any matrix gradient without indices

The question. Index-by-index derivations work, but get long for expressions like tr⁡(X⊤AXB)\operatorname{tr}(X^\top A X B) or log⁡det⁡Σ\log\det\Sigma. Is there a way to stay with whole matrices?

7. Automatic differentiation: forward mode against reverse mode

The question. A model has billions of parameters and one loss. How does a computer get all the slopes, exactly, for the price of a few forward passes?

Three ways to get a derivative

  • Symbolic: manipulate the formula, as in a computer algebra system. Exact, but the expression for a deep network's derivative grows explosively, and code with loops and branches has no single formula.
  • Numerical: finite differences, (f(x+h)−f(x−h))/2h(f(x + h) - f(x - h))/2h. Easy, but approximate (section 11), and it needs two evaluations per input: 2n2n forward passes for nn parameters.
  • Automatic differentiation (AD, or autodiff): run the program, and apply the chain rule to each primitive operation as it runs, using that operation's known local derivative. Exact up to floating-point rounding, works through loops and branches, and costs a small multiple of one evaluation. The standard survey states the bound: computing the m×nm \times n Jacobian costs "ncops(f)n\,c\,\text{ops}(f)" in forward mode and "mcops(f)m\,c\,\text{ops}(f)" in reverse mode, "where c is a constant guaranteed to be c < 6 and typically c ∼ [2, 3]" (Baydin et al. 2018, section 3.2, p. 13, citing Griewank and Walther 2008). Griewank calls the reverse-mode case, a gradient at a small constant multiple of the function's cost whatever nn, the "Cheap Gradient Principle", and adds that "there is no corresponding Cheap Jacobian Principle" (Griewank 2012, p. 391).

AD sees a program as a computational graph: nodes are values, edges are primitive operations (a matrix product, an exponential, a sum), each with a known local derivative. The tiny model's graph is a chain: W,x→z=Wx→p=softmax⁡(z)→L=−ln⁡psatW, x \to z = Wx \to p = \operatorname{softmax}(z) \to L = -\ln p_{\text{sat}}. The chain rule of section 4 says the derivative is a product of the local Jacobians; the two modes of AD are the two orders of multiplying it out.

Forward mode: Jacobian-vector products

Pick one input direction uu and carry a tangent v˙\dot v (how fast each value changes along uu) alongside every value, in the same order as the computation: z˙=J1u\dot z = J_1 u, p˙=J2z˙\dot p = J_2 \dot z, ... One pass gives JuJu: how every output changes along one input direction. A full gradient over nn inputs needs nn passes.

Reverse mode: vector-Jacobian products

Run forward once, keeping what each local derivative will need. Then carry an adjoint v‾\bar v (the gradient of one output with respect to vv) backwards from that output: p‾\bar p, then z‾=J2⊤p‾\bar z = J_2^\top \bar p, then W‾\bar W and x‾\bar x. One backward pass gives the slope of one output with respect to every input. Backpropagation is reverse mode applied to a loss.

Forward mode has a neat algebraic form: dual numbers a+bεa + b\varepsilon with the rule ε2=0\varepsilon^2 = 0. Then f(a+bε)=f(a)+f′(a)bεf(a + b\varepsilon) = f(a) + f'(a)\,b\,\varepsilon for any smooth ff (the Taylor series stops after the linear term), so evaluating with dual numbers carries the derivative along for free. PyTorch exposes it as torch.func.jvp and dual tensors in torch.autograd.forward_ad; JAX as jax.jvp.

Why reverse mode wins for training, and when it does not

For f:ℝn→ℝmf: \mathbb{R}^n \to \mathbb{R}^m, the whole Jacobian costs nn forward-mode passes or mm reverse-mode passes, so the cheaper mode is the one whose count is smaller. Training has m=1m = 1 (one loss) and nn in the billions: reverse mode, by a factor of nn. Forward mode wins when inputs are few and outputs many, for example the sensitivity of every output of a simulation to one hyperparameter. Measured with torch.func.jacfwd and jacrev on f(x)=Btanh⁡(Ax)f(x) = B\tanh(Ax) (hidden width 256, float64, two CPU threads):

The price of reverse mode is memory. The backward sweep runs in the opposite order to the computation, so every value a local derivative needs must still exist when the sweep reaches it: it has to be stored during the forward pass, or recomputed. Forward mode carries its tangent along and can forget each value at once. Sections 8 and 9 measure both costs.

A little history
"Forward mode AD as a general method for evaluating partial derivatives was essentially discovered by Wengert (1964)"; the work of "Linnainmaa (1970, 1976) is often cited as the first published description of the reverse mode"; in machine learning it "has been reinvented several times ... until it was eventually brought to fame by Rumelhart et al. (1986)" (Baydin et al. 2018, section 3.3). Griewank's history adds that Ostrowski used the reverse idea some five years before Linnainmaa, in chemical engineering (Griewank 2012, p. 389). As Baydin et al. put it, "the backpropagation algorithm is only a special case of AD" (section 4.2).

8. Why the backward pass costs about twice the forward pass

The question. "Training costs about three forward passes" and "6N FLOPs per token" are quoted everywhere. Where do they come from, and how exact are they?

Count one linear layer. The forward pass computes Y=XW⊤Y = XW^\top: one matrix product, B×n×mB \times n \times m multiply-adds. The backward pass (5a) computes two: X‾=Y‾W\bar X = \bar Y W and W‾=Y‾⊤X\bar W = \bar Y^\top X, each the same size. So every matrix product costs twice as much backward as forward, and almost all of a transformer's arithmetic is matrix products. A multiply-add is 2 floating-point operations (FLOPs), so a model with NN weights spends about 2N2N FLOPs per token forward and 4N4N backward:

Kaplan et al.: "Accounting for the backwards pass (approximately twice the compute as the forwards pass), we then define the estimated non-embedding compute as C≈6NC \approx 6N floating point operators per training token" (Scaling Laws for Neural Language Models, section 2.1; paper page). Their forward count is 2N+2nlayernctxdmodel2N + 2\,n_{\text{layer}}\,n_{\text{ctx}}\,d_{\text{model}} (Eq. 2.2); the second term, attention over the context, is left out of the 6N.

Measured: a small GPT-style stack

  • FLOPs: exactly 2.00. Forward 68.7 GFLOP, backward 137.4 GFLOP, for both kinds of product (mm 60.1 against 120.3, the attention bmm 8.6 against 17.2). Kaplan's 6N with NN = 25.2 million gives 154.9 GFLOP for the step; the counter's total is 206.2. The gap is the two things 6N leaves out on purpose: the tied output layer (25.8 GFLOP, because it reuses the embedding) and attention over the context (another 25.8 at 512 tokens); 0.2 GFLOP goes the other way, because 6N counts the biases and norm weights as if they were matrix weights.
  • Time: less than 2. On a quiet machine the backward pass took 0.182 s against 0.126 s forward, a ratio of 1.44. The profiler shows why: the matrix products alone take 2.1 times as long backward (0.122 s against 0.057 s), but the forward pass also spends 0.026 s on softmax exponentials whose backward costs 0.006 s, and the elementwise and memory-bound operations do not double. Two earlier runs on the same machine under load gave ratios of 1.95 and 1.57: wall-clock ratios depend on the hardware and on how much of the work is matrix products.
So: "about twice" is a FLOP statement
It is exact for the matrix products, which is why FLOP budgets use 6N (and add the attention term at long context). Wall-clock time also depends on memory traffic and on the non-matmul operations, so measure it rather than assume it.

9. Memory: what the backward pass must keep, and activation checkpointing

The question. Inference on a model fits in memory; training the same model on the same batch does not. What is all that extra memory?

Every rule in section 5 needs something from the forward pass: a linear layer's weight gradient needs its input xx; GELU needs its input; softmax and tanh need their outputs; layer norm needs its input and its statistics. These activations must be kept from the moment the forward pass computes them until the backward pass uses them, so at the turn from forward to backward almost all of them are alive at once. Inference keeps nothing: each value can be freed as soon as the next layer has read it.

Activation checkpointing (also called gradient checkpointing or rematerialisation) trades compute for memory: keep only some activations, the checkpoints, and during the backward pass recompute the missing ones from the nearest checkpoint. Chen et al. showed the trade can be made very cheap: "we design an algorithm that costs O(n)O(\sqrt{n}) memory to train a n layer network, with only the computational cost of an extra forward pass per mini-batch" (Chen et al. 2016, abstract). The argument (their section 4.3, Eq. 1): split the nn layers into kk segments; keep the kk segment boundaries, and during the backward pass hold one segment's n/kn/k activations at a time. Memory is about n/k+kn/k + k, smallest at k=nk = \sqrt n, where it is 2n2\sqrt n instead of nn; each segment is recomputed once, so the extra work is at most one forward pass.

10. How PyTorch autograd and JAX actually do it

The question. You call loss.backward() and every .grad fills in. What happened?

PyTorch: a graph recorded while the forward pass runs

The documentation describes it in three sentences: "Autograd is a reverse automatic differentiation system. Conceptually, autograd records a graph recording all of the operations that created the data as you execute operations, giving you a directed acyclic graph whose leaves are the input tensors and roots are the output tensors." Each operation adds a node (a Function), and "the .grad_fn attribute of each torch.Tensor is an entry point into this graph". And "the graph is recreated from scratch at every iteration, and this is exactly what allows for using arbitrary Python control flow statements" (Autograd mechanics).

Here is the tiny model, run for real (PyTorch 2.14.1; the script is src/inputs/measure/tiny_autograd.py):

  • Nodes and edges. Each node is the backward rule of one operation: MvBackward0 is the matrix-vector product's VJP from section 5a, LogSoftmaxBackward0 and NllLossBackward0 the two halves of 5d. Its next_functions point to the nodes that produced its inputs. A leaf tensor that requires a gradient ends in an AccumulateGrad node, which adds the arriving gradient into .grad.
  • Saved tensors. "Some operations need intermediary results to be saved during the forward pass in order to execute the backward pass", and you can see them "by looking for its attributes starting with the prefix _saved" (same page). They are references, so a saved weight costs nothing extra; a saved activation is the memory of section 9.
  • The backward pass starts at the root with gradient 1, calls each node's backward rule once all its incoming gradients have arrived, and frees the saved tensors as it goes. Calling L.backward() a second time therefore fails: "Trying to backward through the graph a second time (or directly access saved tensors after they have already been freed)" (the real error; pass retain_graph=True to keep them).
  • Gradients accumulate. AccumulateGrad adds, it does not overwrite. That is what lets a weight used twice receive both contributions (section 4), and why training loops call optimizer.zero_grad() (or set .grad to None) before each step; forgetting it is one of the root page's eight gradient bugs.
  • In-place safety. "Every tensor keeps a version counter, that is incremented every time it is marked dirty in any operation. When a Function saves any tensors for backward, a version counter of their containing Tensor is saved as well." If a saved tensor was modified in place, backward raises "one of the variables needed for gradient computation has been modified by an inplace operation" (real output for b = a.exp(); b.add_(1), since exp saves its result).
  • No graph at all under torch.no_grad() or torch.inference_mode(): nothing is recorded or saved, which is why inference held 0 bytes of activations in section 9.

torch.func: derivatives as function transforms

torch.func (formerly functorch) offers the JAX-style interface on the same engine: grad(f) returns a function that computes the gradient; vjp(f, x) returns f(x)f(x) and a function v↦J⊤vv \mapsto J^\top v; jvp(f, (x,), (u,)) returns f(x)f(x) and JuJu; jacrev, jacfwd and hessian build whole Jacobians; and vmap vectorises any of them, which gives per-example gradients in one call. 11. Writing your own backward, and checking any gradient

The question. When should you write a backward rule by hand, and how do you know it is right?

Custom backward functions

Autograd's own rules are usually right and fast. Write your own when the composed rule is numerically poor (it divides by a tiny probability, as in 5d), when it saves more memory than needed (keep pp instead of every intermediate), when you have a fused kernel the framework cannot see inside, or when you deliberately want a different "gradient" (a straight-through estimator for rounding in quantisation-aware training). PyTorch's recipe: "Subclass Function and implement the forward(), (optional) setup_context() and backward() methods"; "backward() (or vjp()) defines the gradient formula. It will be given as many Tensor arguments as there were outputs, with each of them representing gradient w.r.t. that output ... It should return as many tensors as there were inputs"; and "save_for_backward() should be used to save any tensors needed for the backward pass" (Extending PyTorch). Here is the fused softmax cross-entropy of 5d, run for real:

class SoftmaxCE(torch.autograd.Function):
    @staticmethod
    def forward(z, y):
        logp = z - torch.logsumexp(z, dim=-1, keepdim=True)
        return -logp.gather(-1, y[..., None]).squeeze(-1)

    @staticmethod
    def setup_context(ctx, inputs, output):
        z, y = inputs
        ctx.save_for_backward(torch.softmax(z, dim=-1), y)   # keep p, not the logits

    @staticmethod
    def backward(ctx, gL):
        p, y = ctx.saved_tensors
        gz = p.clone()
        gz.scatter_add_(-1, y[..., None], -torch.ones_like(y, dtype=p.dtype)[..., None])  # p - onehot
        return gL[..., None] * gz, None                      # times the incoming gradient; y gets none

Gradient checking

Compare the analytic gradient with a finite difference. The two common differences have very different accuracy, which a Taylor expansion shows: f(x±h)=f(x)±hf′(x)+h22f′′(x)±h36f′′′(x)+⋯f(x \pm h) = f(x) \pm h f'(x) + \tfrac{h^2}{2} f''(x) \pm \tfrac{h^3}{6} f'''(x) + \cdots, so

f(x+h)−f(x)h=f′(x)+h2f′′(x)+⋯,f(x+h)−f(x−h)2h=f′(x)+h26f′′′(x)+⋯\frac{f(x + h) - f(x)}{h} = f'(x) + \frac{h}{2} f''(x) + \cdots, \qquad \frac{f(x + h) - f(x - h)}{2h} = f'(x) + \frac{h^2}{6} f'''(x) + \cdots

12. Second derivatives: Hessian-vector products without the Hessian

The question. Curvature (how the slope itself changes) sets learning-rate limits and powers Newton-type methods. The Hessian of a model with nn parameters has n2n^2 entries. How can you use it at all?

The Hessian HH of a scalar LL is the Jacobian of its gradient: Hij=∂2L/∂θi∂θjH_{ij} = \partial^2 L / \partial \theta_i \partial \theta_j, an n×nn \times n symmetric matrix (the order of differentiation does not matter for smooth functions). Its meaning, its eigenvalues and Newton's method are the calculus sibling's subject (Calculus and optimisation for ML). This page's concern is how to compute with it. Almost every use needs only products HvHv with chosen vectors, and those can be had without ever forming HH:

Hv=∇θ(∇θL⋅v)=ddε∇θL(θ+εv)|ε=0Hv = \nabla_\theta\big(\nabla_\theta L \cdot v\big) = \frac{d}{d\varepsilon}\, \nabla_\theta L(\theta + \varepsilon v)\Big|_{\varepsilon = 0}

Left: take the gradient, dot it with the fixed vector vv (a scalar), and take the gradient of that: two reverse passes, "double backward". Right: the directional derivative of the gradient along vv: one forward-mode pass through the gradient computation, "forward-over-reverse". Pearlmutter's 1994 paper gives "an exact and numerically stable procedure for computing [HvHv], which takes about as much computation, and is about as local, as a gradient evaluation", in "O(n) time and space" against the O(n2)O(n^2) of forming HH (Pearlmutter 1994, abstract and section 1). JAX's cookbook recommends the second nesting: "forward-over-reverse is typically the most efficient", because forward mode suits the outer, square Jacobian of ∇L:ℝn→ℝn\nabla L: \mathbb{R}^n \to \mathbb{R}^n (The Autodiff Cookbook). Baydin et al. note that the nestings perform "the same arithmetic operation sequence" and differ in overheads (footnote 16).

# PyTorch, double backward
g, = torch.autograd.grad(loss_fn(theta), theta, create_graph=True)   # keep the graph of the gradient
Hv, = torch.autograd.grad(g @ v, theta)
# PyTorch or JAX, forward-over-reverse
Hv = torch.func.jvp(torch.func.grad(loss_fn), (theta,), (v,))[1]
Hv = jax.jvp(jax.grad(loss_fn), (theta,), (v,))[1]

13. Einsum: one notation for every contraction, and its FLOP count

The question. Attention, batched matrix products, outer products and traces all look different on paper. Is there one way to write, cost and differentiate them all?

Einsum (Einstein summation) labels every axis with a letter. Two rules: a letter that appears in the inputs but not in the output is summed over; the output's letters, in the order written, give its shape (so a transpose is just a relabelling). Carried from the old Linear algebra page (checked):

The cost falls out of the letters. A contraction does one multiply-add for every combination of all its distinct letters, so it costs the product of all the letter sizes in multiply-adds, twice that in FLOPs. For attention scores with batch b=2b = 2, heads h=8h = 8, q=k=128q = k = 128 positions and head width d=64d = 64: 2⋅8⋅128⋅128⋅64=16,777,2162 \cdot 8 \cdot 128 \cdot 128 \cdot 64 = 16{,}777{,}216 multiply-adds (33.6 million FLOPs, which is NumPy's einsum_path count, 3.355e+07). Doubling the sequence length doubles both qq and kk, so the cost quadruples: attention's quadratic cost, read off the string.

Order matters for three or more operands. ABvABv with 1000×10001000 \times 1000 matrices can be computed as (AB)v(AB)v or A(Bv)A(Bv). NumPy's np.einsum_path('ij,jk,k->i', A, B, v, optimize='optimal') reports (real output, NumPy 2.5.3): "Naive FLOP count: 3.000e+09", "Optimized FLOP count: 4.000e+06", "Theoretical speedup: 750.000", by contracting k,jk->j first. (NumPy's count is the multiply-adds times the number of operands, 3 here, so its naive count is 3 times 10910^9.) Its "optimal" strategy "combinatorially explores all possible ways of contracting the listed tensors"; the default "greedy" one is "Equivalent to the 'optimal' path for most contractions" (numpy.einsum_path). This is the same lesson as section 4: multiply by the vector first.

The backward pass of an einsum is an einsum. For CC = einsum('ij,jk->ik', A, B), the gradient for one operand is the einsum of the output's gradient with the other operands, written into that operand's letters: A‾\bar A = einsum('ik,jk->ij', C̄, B) =C‾B⊤= \bar C B^\top and B‾\bar B = einsum('ij,ik->jk', A, C̄) =A⊤C‾= A^\top \bar C, the rules of 5a with no transposes to remember. Each backward einsum has the same set of letters as the forward one, so the same cost: a two-operand contraction costs twice as much backward, which is section 8 again.

Common mistakes

Mixing layouts inside one derivation.
Writing the chain rule in numerator layout and plugging in a gradient shaped like the parameter puts transposes in the wrong places. Pick one layout, and check every result's shape against the parameter (section 3).
A custom backward that ignores the incoming gradient.
A VJP must multiply by y‾\bar y. The bug is invisible when the function is the last step before .sum().backward() and wrong everywhere else; gradcheck catches it (section 11).
"Backward costs the same as forward."
Twice the FLOPs for every matrix product (section 8), plus the memory of every stored activation, which is usually what runs out first (section 9).
"Checkpointing costs one whole extra forward pass."
At most one. Non-reentrant checkpointing stops recomputing early (20.8% extra FLOPs measured, against 33% for a full forward of the step), and selective recomputation of only the attention core costs 2 to 3% (Distributed Training).
Building a Jacobian you only need to multiply by.
Softmax's Jacobian is K×KK \times K; its VJP is O(K)O(K) (section 5c). The same holds for every layer: frameworks never form Jacobians during training, and hand-written code should not either.
Using forward mode, or finite differences, to get a training gradient.
Both need one pass per parameter. Reverse mode needs one pass in total (section 7).
Modifying a saved tensor in place.
PyTorch's version counter raises an error, but only when the backward pass reaches that node, far from the line that caused it. torch.autograd.set_detect_anomaly(True) reports the forward operation responsible.
Forgetting that gradients accumulate.
Without zero_grad() each step adds to the last step's gradient. Deliberate accumulation over micro-batches is the same mechanism, used on purpose (divide the loss by the number of micro-batches).
Gradient-checking in float32.
A correct function fails. Check in float64 with central differences, away from kinks (section 11).
Breaking the graph without noticing.
.detach(), .item(), .numpy(), in-place writes to .data, and integer operations such as argmax and rounding all stop gradients: the parameters before them silently get zero or no gradient. A straight-through estimator (a custom backward that passes y‾\bar y through unchanged) is the deliberate version.
Mean against sum in the loss.
With reduction="mean" each example's gradient carries a factor 1/B1/B (5d). Switching to a sum multiplies every gradient by the batch size, which acts like multiplying the learning rate by it.

Where research is going

Most current work attacks the two costs of reverse mode, memory and the strict backward ordering.

  • Not storing activations at all. Reversible networks reconstruct each layer's input from its output during the backward pass: RevNet is "a variant of ResNets where each layer's activations can be reconstructed exactly from the next layer's", so "the activation storage requirements are independent of depth" (Gomez et al. 2017).
  • Differentiating a solution instead of the steps that found it. Implicit differentiation applies the implicit function theorem at a fixed point or an optimum. Deep equilibrium models "analytically backpropagate through the equilibrium point using implicit differentiation", so training needs "only constant memory, regardless of the effective "depth" of the network" (Bai, Kolter and Koltun 2019); JAXopt made the technique modular (Blondel et al. 2022).
  • Gradients from forward mode alone. The "forward gradient" multiplies a random direction vv by the JVP along it: "an unbiased estimate of the gradient that can be evaluated in a single forward run of the function, entirely eliminating the need for backpropagation" (Baydin et al. 2022). The variance grows with the number of parameters, which is why it has not replaced backpropagation for large models.
  • Splitting the backward pass. Section 5a's two products, X‾\bar X (needed immediately by the previous layer) and W‾\bar W (needed only by the optimiser), can be scheduled separately. Zero Bubble pipeline parallelism does exactly this, "to split the backward computation into two parts, one that computes gradient for the input and another that computes for the parameters", to fill pipeline bubbles (Qi et al. 2023; see Distributed Training).
  • Letting the compiler choose what to save. torch.compile traces forward and backward together (AOTAutograd) and decides which activations to save and which to recompute by a min-cut computation over the joint graph: "a min-cut based recomputation pass with AOTAutograd + NVFuser that consistently improves both memory and runtime" (He 2022, PyTorch developer forum). Cheap elementwise operations are recomputed, matrix products and random operations are saved.
The five things to take away
1. A gradient has the shape of its parameter. 2. Every layer's backward is a vector-Jacobian product, derived by writing one entry with indices or by the trace trick. 3. Reverse mode gets every slope of one loss in one pass, for about twice the forward FLOPs. 4. The price is stored activations; checkpointing buys memory back with recomputation. 5. Curvature is available as Hessian-vector products, at the cost of a gradient or two.
