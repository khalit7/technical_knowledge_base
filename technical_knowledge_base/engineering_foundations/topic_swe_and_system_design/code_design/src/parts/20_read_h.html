Types: hints, checkers, overloads, and an unannotated trap

Python does not check types when it runs: def f(x: int) happily accepts a string. A type hint ({{PEP 484|https://peps.python.org/pep-0484/}}, written 2014, Python 3.5) is an annotation for tools; a type checker reads the hints without running the code and reports calls that cannot work (passing None where a str is required, forgetting that a lookup can fail, misspelling an attribute): a whole class of bugs found in seconds at your desk, plus documentation that cannot go stale because CI checks it.

def summarize_chat(chat_id: str, *, store: ChatStore, model: ChatModel) -> Summary:def claim_key(owner: str, key: str, fingerprint: str) -> JSONResponse | None:role: Literal["user", "assistant", "system"]

Read them as sentences: JSONResponse | None ("a response, or nothing"; the | spelling is {{PEP 604|https://peps.python.org/pep-0604/}}, Python 3.10) forces every caller to handle the nothing; Literal[...] limits a string to known values, so a typo like "asistant" is caught; the bare * makes everything after it keyword-only.

Four checkers exist: mypy (2.4.0, the reference), pyright (Microsoft, inside VS Code's Pylance), ty (Astral, a 0.0.x beta) and pyrefly (Meta); their versions, strict settings and how they disagree on the same code are in {{Python: typing, uv, packaging and the toolchain, section 2|n:4055c17b0d0d8192878fce7505cc612f#s2}}.

What pros do: pick one checker, run it in CI and in the editor, and make new code pass its strict mode while old code is brought in module by module. Two checkers disagreeing on edge cases is normal; running two is rarely worth it.

A trap, measured: an unannotated function is nearly invisible to the checker
Run on the tangled LLM call (before.py), mypy --strict reports error: "". Not one of its real problems. Without annotations every parameter is Any, and Any is compatible with everything, so there is almost nothing to contradict. Type checking pays only once the signatures carry types. after.py, fully annotated: errors under the same flags, and now a wrong call would be caught.

Overloads, when the return type depends on an argument. The official OpenAI SDK (v3.24.0, 2026-10-02) types chat.completions.create with @overload: with stream: Literal[True] it returns Stream[ChatCompletionChunk], otherwise a ChatCompletion ({{source at the tag|https://github.com/openai/openai-python/blob/v3.24.0/src/openai/resources/chat/completions/completions.py}}), so iterating over a non-streamed reply is an error at your desk. Also: NewType("ModelId", str) so a model id cannot be passed where a chat id is expected, and generic functions with {{PEP 695|https://peps.python.org/pep-0695/}}'s def first[T](xs: Sequence[T]) -> T (Python 3.12).

Cost. Annotations take time to write, and the checker has opinions about dynamic code (decorators, **kwargs plumbing, ORMs) that can take an hour to satisfy. # type: ignore[code] with the specific code is the honest escape. Do not chase strict mode in a throwaway notebook.

Cost. Every rule you enable is a rule someone must satisfy or silence. Turning on everything (select = ["ALL"]) on an old codebase produces thousands of findings and teaches people to ignore the linter. Start with the defaults plus a few rules that catch bugs (bugbear B, blind except BLE), add more one at a time, and fix or baseline existing violations when you do.
