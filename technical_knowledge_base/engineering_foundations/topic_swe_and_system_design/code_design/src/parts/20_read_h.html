10. Refactoring safely: tests first, then small steps

{{Martin Fowler's definition|https://refactoring.com/}}: a refactoring is "a change made to the internal structure of software to make it easier to understand and cheaper to modify without changing its observable behavior". The last clause is the whole discipline. If behaviour changes, it is not a refactoring, and it belongs in a separate, reviewed change. Fowler's book Refactoring (1999; 2nd edition 2018, with examples in JavaScript) is a catalogue of such small, named, safe moves: Extract Function, Inline Function, Rename Variable, and dozens more.

How do you know behaviour did not change? You need tests that pin it down before you start. For code that has none, Michael Feathers (Working Effectively with Legacy Code, 2004) named the tool: a characterization test, whose purpose "is to document your system's actual behavior, not check for the behavior you wish your system had" ({{Feathers, 2016|https://michaelfeathers.silvrback.com/characterization-testing}}). You call the code, record what it does today, even if it looks wrong, and assert exactly that. His blunt definition from {{2002|http://web.archive.org/web/2006id_/http://www.objectmentor.com/resources/articles/WorkingEffectivelyWithLegacyCode.pdf}}: "The main thing that distinguishes legacy code from non-legacy code is tests, or rather a lack of tests."

Then the loop: make one small change, run the tests, commit; repeat. Each step is small enough that when a test goes red you know exactly which change did it, and undoing it costs seconds. Kent Beck's version of when to do this: "for each desired change, make the change easy (warning: this may be hard), then make the easy change" (2012, quoted by {{Fowler|https://martinfowler.com/articles/preparatory-refactoring-example.html}}).

What the run shows, in order:

  • Steps 1 to 7 change structure only, and the tests prove it: 14 of 14 green every time. Complexity falls from 9 to 6 and the handler from 52 to 28 lines. Ruff's PLR0911 (too many return statements, default limit 6) fires on the original and stops firing at step 2, once errors are raised instead of returned.
  • Step 8 turns a test red. Moving authentication into a FastAPI dependency changed which error wins when a request has no API key and an invalid body: 401 now, 422 before, because dependencies run before body validation. No reader of the diff would have spotted it; the characterization test did. That is a behaviour change, so it gets a decision, not a shrug: checking identity first is the better behaviour (an unknown caller should not learn how its body is wrong), so step 9 updates the test in its own commit, which a reviewer approves on its own.

In one jump to a MessageService class, the handler shrinks to 10 lines with complexity 2, and 4 of 14 tests fail: the fingerprint forgot the chat id, the key is no longer released after a 404, and replays lost their Idempotent-Replayed header. About the numbers
McCabe's cyclomatic complexity counts independent paths through a function (roughly, 1 plus the number of decision points). His 1976 paper proposed 10 as "a reasonable, but not magical, upper limit" ({{McCabe, IEEE TSE, 1976|http://www.literateprogramming.com/mccabe.pdf}}, scanned copy); ruff's C901 uses 10 by default and radon grades 1 to 5 as A and 6 to 10 as B ({{radon docs|https://radon.readthedocs.io/en/latest/commandline.html#the-cc-command}}). The original handler scored 9, under every threshold, and was still the hardest function in the service to change. Metrics find candidates; they do not judge design. The rewrite's score of 2 is the proof: the lowest number on the chart belongs to the broken version.
What it costs, and when not to
Writing characterization tests first is real work (here, 14 tests for one handler). Refactoring takes review time that ships no feature. Do not refactor code that is about to be deleted, code nobody needs to change, or during an incident. Never mix a refactoring and a behaviour change in one pull request: the reviewer cannot tell which line is which.
