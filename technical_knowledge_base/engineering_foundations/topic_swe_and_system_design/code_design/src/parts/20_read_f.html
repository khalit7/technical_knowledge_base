9. Refactoring safely: pin behaviour with tests, then small steps

{{Martin Fowler's definition|https://refactoring.com/}}: a refactoring is "a change made to the internal structure of software to make it easier to understand and cheaper to modify without changing its observable behavior". If behaviour changes, it is not a refactoring and belongs in a separate, reviewed change. His book Refactoring (1999; 2nd edition 2018, examples in JavaScript) is a catalogue of small, named, safe moves: Extract Function, Inline Function, Rename Variable, and dozens more. For code with no tests, Michael Feathers (Working Effectively with Legacy Code, 2004) named the first tool: a characterization test, whose purpose "is to document your system's actual behavior, not check for the behavior you wish your system had" ({{Feathers, 2016|https://michaelfeathers.silvrback.com/characterization-testing}}): call the code, record what it does today, even if it looks wrong, and assert exactly that. His blunt definition from {{2002|http://web.archive.org/web/2006id_/http://www.objectmentor.com/resources/articles/WorkingEffectivelyWithLegacyCode.pdf}}: "The main thing that distinguishes legacy code from non-legacy code is tests, or rather a lack of tests." Then the loop: one small change, run the tests, commit; when a test goes red you know exactly which change did it, and undoing it costs seconds. Kent Beck: "for each desired change, make the change easy (warning: this may be hard), then make the easy change" (2012, quoted by {{Fowler|https://martinfowler.com/articles/preparatory-refactoring-example.html}}).

Cost. Characterization tests first are real work (here, 14 tests for one handler), and refactoring takes review time that ships no feature. Do not refactor code that is about to be deleted, code nobody needs to change, or during an incident. Never mix a refactoring and a behaviour change in one pull request: the reviewer cannot tell which line is which.

About the complexity numbers (McCabe, radon, ruff thresholds)

McCabe's cyclomatic complexity counts independent paths through a function (roughly, 1 plus the number of decision points). His 1976 paper proposed 10 as "a reasonable, but not magical, upper limit" ({{McCabe, IEEE TSE, 1976|http://www.literateprogramming.com/mccabe.pdf}}, scanned copy); ruff's C901 uses 10 by default and radon grades 1 to 5 as A and 6 to 10 as B ({{radon docs|https://radon.readthedocs.io/en/latest/commandline.html#the-cc-command}}). The original handler scored 9, under every threshold, and was still the hardest function in the service to change. Metrics find candidates; they do not judge design. The rewrite's score of 2 is the proof: the lowest number on the chart belongs to the broken version.

10. Code an LLM agent can change safely

A coding agent edits, runs something, reads the result and edits again. It stops when the work looks done, so the design question is what it can check and how much it must read. Anthropic's Claude Code guidance puts both constraints plainly: "Give Claude a check it can run: tests, a build, a screenshot to compare", and "Claude's context window fills up fast, and performance degrades as it fills" ({{Best practices for Claude Code|https://code.claude.com/docs/en/best-practices}}, page updated 2026-10-20, read 2026-10-24). Everything in sections 1 to 9 serves an agent for the same reasons it serves a human, with less slack:

Static diagram. Evidence from this page's own runs: the characterization tests caught step 8's 401 against 422 (section 9); mypy --strict found 1 error in the unannotated tangled call and so would not guard it (depth block "Types"); ruff's BLE001 flags the blind except Exception of section 7. Where no check exists, "looks done" is the only signal, and the reviewer becomes the loop.

  • A check it can run: characterization tests before a change (section 9), types on signatures, a linter with bug-finding rules. The narrower the check, the sooner the loop closes.
  • Seams: ports and injected collaborators (section 5) let the agent run the core with fakes, in milliseconds, without network or credentials.
  • Small, cohesive files with names that say what things are for: the agent reads only what the change needs, which keeps its context small (section 2). A 17-line handler that calls idempotency_claim is cheaper to load than 52 interleaved lines.
  • Invariants written down: state what must always hold ("a claimed key is released unless a response was saved") in a docstring or test name, and check the change against that sentence.
  • Never let it edit the tests and the code in the same step to make a failure go away; that is how a characterization test gets "fixed" instead of the bug. Keep diffs small, one change at a time, as for humans.
  • Check every new dependency exists and is the package you think it is: across 16 models and 576,000 code samples, "the average percentage of hallucinated packages is at least 5.2% for commercial models and 21.7% for open-source models", with 205,474 unique invented names ({{Spracklen et al., USENIX Security 2025|https://arxiv.org/abs/2406.10279}}). Attackers register such names ("slopsquatting"), so pip install of an unknown suggested package can install malware.

Plausible is the risk: the failure mode is code that looks right, passes the tests it wrote for itself, and is subtly wrong at the edges. Reviewing what comes back is the same review as for a human, with a higher bar ("LLM-authored code raises the review bar, not lowers it", from the old page): read the tests first (do they test behaviour, or mocks?), then the edges assistants handle worst (error paths, retries, empty inputs, concurrency, time zones). The "retry everything" and "blocking call in async code" diffs in the {{Review lab|#t-review}} are both typical. Where tests are silent on very large or AI-written changes is {{Testing and quality|n:3c65c17b0d0d81548848e2ebdd2f63ee}}'s section 13; the harnesses that run agents are {{Topic: agentic-harnesses|n:3c65c17b0d0d81d881a8fe98b4cff7bb}}; how coding agents are benchmarked, and why scores can mislead, is {{Agentic benchmarks|n:3c65c17b0d0d811fb926d7b91ef8234e}} and the paper page {{Schrödinger's Code Repository|n:3e95c17b0d0d81e8b0e0e99acbeb9713}} (has an LLM learned SWE-bench or memorised it?).

What the evidence says about AI and speed (dated, as of 2026-10-04)
  • Speed is not settled. METR's randomised trial (16 experienced open-source developers, 246 real issues in their own repositories, early-2025 tools) found "when developers use AI tools, they take 19% longer than without", while the developers expected a 24% speedup and still believed afterwards that AI had sped them up by 20% ({{METR, 2025-07-10|https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/}}). A February 2026 follow-up with newer tools says its new data "gives us an unreliable signal of the current productivity effect of AI tools", because of who chose to take part ({{METR, 2026-02-24|https://metr.org/blog/2026-02-24-uplift-update/}}). Honest summary: no reliable measurement yet, and your own feeling of speed is not evidence.
  • Delivery can suffer. Google's DORA 2024 report associated a 25% increase in AI adoption with 7.5% better documentation quality and 3.4% better code quality, but also "an estimated decrease in delivery throughput by 1.5%, and an estimated reduction in delivery stability by 7.2%" ({{Google Cloud blog, 2024-10-23|https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report}}).

11. Technical debt is a decision

Ward Cunningham coined the metaphor in his OOPSLA 1992 experience report: "Shipping first time code is like going into debt. A little debt speeds development so long as it is paid back promptly with a rewrite", and "Every minute spent on not-quite-right code counts as interest on that debt" ({{The WyCash Portfolio Management System|https://c2.com/doc/oopsla92.html}}). The useful part is the decision it frames: debt is fine when it buys something and its interest is small; it is a problem when nobody chose it or nobody pays it down.

Two questions sort any shortcut: did we know, and was it sensible?

Martin Fowler's {{Technical Debt Quadrant|https://martinfowler.com/bliki/TechnicalDebtQuadrant.html}} (14 October 2009): "the useful distinction isn't between debt or non-debt, but between prudent and reckless debt", and "there's also a difference between deliberate and inadvertent debt". The cell texts paraphrase his examples. Prudent and inadvertent debt is, in his words, "not just common but inevitable for teams that are excellent designers": you learn what the design should have been by building it.

  • Interest is paid only where you change code. Fowler: "The prudent debt to reach a release may not be worth paying down if the interest payments are sufficiently small - such as if it were in a rarely touched part of the code-base." So pay down where change is frequent: the busiest handler, not the yearly report script.
  • Write the decision down: a ticket or a comment that says what was skipped, why, and what would trigger paying it (a second provider, a second caller). The tangled LLM call is fine as a one-off script; the trigger to restructure it is "runs unattended or gains a second caller" (section 7).
  • Pay in small refactorings, not a rewrite (section 9): each step ships, keeps the tests green and can stop at any point when the interest is low enough.
  • "Quick and dirty" is usually reckless: Fowler agrees with Robert Martin that choosing it "because they think they can't afford the time required to write clean code" underestimates where the design payoff comes, since "The whole point of good design and clean code is to make you go faster".
