7. Error handling design

The tangled LLM call returned None for four different failures (section 4). That is the most common error-handling mistake in Python services: the caller gets "something went wrong" with the reason thrown away, and the logs say summarize failed: 'choices' from inside a retry loop. {{PEP 20|https://peps.python.org/pep-0020/}}, the Zen of Python, says it in two lines: "Errors should never pass silently. Unless explicitly silenced."

Python's idiom is to raise an exception: an object that travels up the call stack until some caller that can do something about it catches it. Python's glossary even names the style: EAFP, "Easier to ask for forgiveness than permission" ({{glossary|https://docs.python.org/3/glossary.html#term-EAFP}}): try the operation and catch the failure, instead of checking every precondition first.

Design the errors like an interface

The exceptions a module raises are part of its interface. Four rules cover most of the design:

  1. One base class per package, so a caller can catch everything from you in one line: SummarizeError.
  2. One subclass per thing a caller would handle differently, not per place it can happen: ChatNotFound (show a 404), ModelOutputError (log, maybe try another prompt), ModelUnavailable (retry later).
  3. Say whether retrying helps. Put it in the type or an attribute (retryable = True), so retry code does not parse messages.
  4. Keep the cause: raise ModelOutputError(str(e)) from e chains the original exception, so the traceback shows both.

Real libraries do exactly this. The OpenAI Python SDK at v3.24.0 ({{_exceptions.py|https://github.com/openai/openai-python/blob/v3.24.0/src/openai/_exceptions.py}}):

OpenAIError└ APIError ├ APIConnectionError # could not reach the server: retried │ └ APITimeoutError # retried └ APIStatusError # the server answered with an error status ├ BadRequestError (400), AuthenticationError (401), PermissionDeniedError (403), │ NotFoundError (404), UnprocessableEntityError (422) # our fault: not retried ├ ConflictError (409), RateLimitError (429) # retried └ InternalServerError (5xx) # retried

Its {{README|https://github.com/openai/openai-python/blob/v3.24.0/README.md#retries}} states the policy: "Connection errors (for example, due to a network connectivity problem), 408 Request Timeout, 409 Conflict, 429 Rate Limit, and >=500 Internal errors are all retried by default", 2 times with a short exponential backoff, and "Requests are retried only when their body can be safely resent". The HTTP library underneath has the same shape (httpx: HTTPError splits into RequestError, with TransportError and its timeouts below it, and HTTPStatusError; {{docs|https://www.python-httpx.org/exceptions/}}). after.py copies the policy at small scale: only TransportError, 429 and 5xx are retried.

Note on the old page and on the SDK
The old page described the retry pattern correctly. Two things changed since: the SDK is now at major version 3, and its README says its clients are "powered by HTTPX2" (pydantic's fork of httpx), whose exception tree mirrors httpx's. Code that caught httpx.TimeoutException around SDK calls should catch the SDK's own APITimeoutError instead: depend on the interface the library publishes, not on what it happens to use inside.

Where to catch

Catch where you can do something: retry, fall back, or turn the error into a response. In the refactored service that is one place: a single exception handler turns every ProblemError into an RFC 9457 problem response (step 2 of the refactor; the HTTP side is taught in "Errors" on {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}). Everywhere else, let exceptions travel. Catching just to log and re-raise doubles every log line; catching Exception to "be safe" is the bug measured in section 4 (ruff flags it as BLE001, blind except).

Define errors out of existence

Ousterhout's advice ({{exceptions notes|https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=exceptions}}): "Whenever possible, define errors out of existence." Choose semantics where the awkward case is not an error at all. Python's standard library has small examples: set.discard(x) does nothing if x is absent (set.remove raises), os.makedirs(path, exist_ok=True), dict.get(key, default). In the refactor, idempotency_claim releasing the key on every exit removes a whole category of "forgot to release" errors instead of handling them.

What it costs, and when not to
A hierarchy is interface: every class you publish is a promise (section 9). Do not create one exception class per function. Exceptions are slow-ish in tight loops and wrong for expected outcomes ("no more pages" is a return value, not an error).

8. Dependency injection without a framework

Dependency injection sounds like enterprise Java. In Python it is one habit: a function or class receives the things it uses instead of creating them. The tangled LLM call created its own database connection (sqlite3.connect(os.environ["CHAT_DB"])) and called a module-level httpx.post; to test it you must patch globals. The refactored one takes them as arguments:

def summarize_chat(chat_id: str, *, store: ChatStore, model: ChatModel) -> Summary: ...class HttpChatModel: def __init__(self, url, key, model="small", *, attempts=3, sleep=time.sleep, client=None): ... # real defaults; tests pass fakes

The payoff is concrete. The unit test for the retry policy passes sleep=slept.append and an httpx client with a scripted transport; it checks that a 429 then a 503 are retried with waits of exactly 1 and 2 seconds, and it runs in milliseconds without sleeping or touching a network (test_http_model_retries_only_transient_errors in src/llmcall/test_after.py).

  • The composition root. Somewhere, real objects must be built: one place, usually main.py, creates the database pool, the HTTP client and the settings once at start-up and passes them down. Nothing else calls os.environ or opens connections.
  • FastAPI already has it. Depends(current_owner) in step 8 of the refactor is dependency injection; tests swap a dependency with {{app.dependency_overrides|https://fastapi.tiangolo.com/advanced/testing-dependencies/}}.
  • Fakes over mocks. A fake is a small working implementation (an in-memory store); a mock records calls and returns canned values. Mocks let a test check that a call happened rather than that the result is right; the {{Review lab|#t-review}} has a real test that still passes when the function it claims to test is broken.
What it costs, and when not to
Parameters multiply; give the common case a default (sleep=time.sleep). Do not inject what never varies (the json module, pure helpers). A DI container library is rarely worth it in Python: explicit arguments plus one composition root are easier to read than a registry.
