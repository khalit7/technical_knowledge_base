5. Interfaces and dependency direction: ports, adapters, injection, validated edges

The demo service is one 200-line file, and at that size one file is right. Picture it at 5,000 lines with a second way in (a nightly batch job that summarises chats) and a second database (Postgres in production, SQLite in tests). Now "where does this code go?" decides how much has to change when one of those outside things changes. The organising idea is ports and adapters (hexagonal architecture), from Alistair Cockburn's {{2005 article|https://alistair.cockburn.us/hexagonal-architecture/}}: "Allow an application to equally be driven by users, programs, automated test or batch scripts, and to be developed and tested in isolation from its eventual run-time devices and databases." The product's rules sit in the middle and know nothing about HTTP, SQL or a vendor's SDK; a port is an interface the middle defines ("something that can give me a chat's messages"), an adapter implements it for one technology (Postgres, SQLite, an HTTP client, a fake for tests).

Imports point down, toward the rules; only main.py knows the adapters

The chat service laid out by layer. Solid arrows are imports: each layer may import only the layers below it. Adapters implement ports (dashed) and are built and wired in by main.py, the composition root. Swapping SQLite for Postgres touches one adapter file; a test runs a use case with fakes and no network.

chat_service/ main.py # composition root: builds the adapters, hands them to the app config.py # settings read from the environment, validated once at start-up api/ # FastAPI routers: parse HTTP in, call a use case, render HTTP out. Thin. services/ # use cases: send_message, summarize_chat. Orchestrate; no SQL, no HTTP. domain/ # pure rules: fingerprints, prices, reply parsing. Imports nothing above. ports.py # Protocols the services need: ChatStore, ChatModel, RateLimiter adapters/ # postgres_store.py, sqlite_store.py, http_model.py, redis_limiter.py

Dependency direction is the rule that matters. domain imports nothing from the project; services import domain and ports; api imports services; nothing imports api or adapters except main.py. The rule can be enforced in CI with {{import-linter|https://import-linter.readthedocs.io/}} (2.15, September 2026), whose "layers" contract fails the build when a lower layer imports a higher one. Where I/O lives: I/O is anything that leaves the process (network, disk, database, clock, randomness, environment variables). It is slow, can fail, and makes tests need setup, so push it to the edges: read what you need, decide in plain functions, then write the results (section 7 measures why).

A port in Python is a Protocol

A Protocol ({{PEP 544|https://peps.python.org/pep-0544/}}, Python 3.8, "static duck typing") declares the methods something must have; any class with matching methods satisfies it, with no base class and no import of the protocol. Prefer it to an abstract base class when the implementations live in other packages or in tests. (How the type checker treats it is the {{Python page|n:3cd5c17b0d0d81b28acdea39e7a4d998}}'s, Part 1 section 6.)

class ChatModel(Protocol): def complete(self, system: str, user: str) -> str: ...# HttpChatModel (real HTTP) and FakeModel (tests) both satisfy it; neither mentions it.

Dependency injection without a framework

Dependency injection in Python is one habit: a function or class receives the things it uses instead of creating them. The tangled LLM call created its own database connection (sqlite3.connect(os.environ["CHAT_DB"])) and called a module-level httpx.post, so testing it means patching globals. The refactored one takes them as arguments:

def summarize_chat(chat_id: str, *, store: ChatStore, model: ChatModel) -> Summary: ...class HttpChatModel: def __init__(self, url, key, model="small", *, attempts=3, sleep=time.sleep, client=None): ... # real defaults; tests pass fakes

The unit test for the retry policy passes sleep=slept.append and an httpx client with a scripted transport; it checks that a 429 then a 503 are retried with waits of exactly 1 and 2 seconds, in milliseconds, without sleeping or touching a network (test_http_model_retries_only_transient_errors in src/llmcall/test_after.py). One place, the composition root (usually main.py), builds the database pool, the HTTP client and the settings once at start-up and passes them down; nothing else calls os.environ or opens connections. FastAPI already has injection: Depends(current_owner) in step 8 of the refactor is it, and tests swap a dependency with {{app.dependency_overrides|https://fastapi.tiangolo.com/advanced/testing-dependencies/}}. Pass fakes (small working implementations, such as an in-memory store) rather than mocks (objects that record calls and return canned values): the {{Review lab|#t-review}} has a real test that still passes when the function it claims to test is broken ({{Testing and quality|n:3c65c17b0d0d81548848e2ebdd2f63ee}} section 4 owns test doubles). Cost: parameters multiply, so give the common case a default (sleep=time.sleep); do not inject what never varies (the json module, pure helpers); a DI container library is rarely worth it in Python.

Validate at the boundary, trust inside

A dataclass (standard library) generates __init__, __eq__ and __repr__ and checks nothing at run time; {{attrs|https://www.attrs.org/}} does the same with more options. A {{pydantic|https://docs.pydantic.dev/latest/}} BaseModel validates and converts every value when the object is built, raising an error that says which field and why. Validation is the point at an input boundary and wasted work everywhere else:

A validated pydantic object costs about times a dataclass

real best of 7 runs of 100,000 constructions, nanoseconds per object, on an , Python , pydantic (pydantic-core ), attrs ; script src/bench/bench_models.py. Absolute numbers depend on the machine; the ratios are the point.

Nothing for one request, real money in a loop over ten million log rows. So: pydantic at the boundaries (HTTP bodies, LLM outputs, config read from the environment with {{pydantic-settings|https://docs.pydantic.dev/latest/concepts/pydantic_settings/}} 2.15.0, files from outside), dataclasses or attrs inside.

Two surprises in the bars, and two signature habits

Two surprises: model_construct, the documented "skip validation" escape hatch, is slower here than validating (pydantic's {{performance notes|https://docs.pydantic.dev/latest/concepts/performance/}} and {{model docs|https://docs.pydantic.dev/latest/concepts/models/#creating-models-without-validation}} warn that in V2 "for simple models, going with validation may even be faster"), and parsing JSON straight into a model (model_validate_json) beats json.loads plus a dataclass, which is why pydantic's docs say to prefer it. Two signature habits from the old page: accept abstract types, return concrete ones (take Sequence[Message] or Iterable; return list[Message]), and avoid "stringly typed" values (a str that is really one of five model names should be a Literal or an Enum).

Cost. Every layer is a file to open and a name to learn. For a CRUD service whose "rules" are "store what the client sent", a service layer that only forwards calls to a repository is a shallow module: pure cost. Start with one module per feature (chats.py, billing.py); introduce a port when a second adapter actually appears (a test fake counts) or the rules grow beyond a screen.
