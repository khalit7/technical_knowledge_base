3. Structuring a service: layers, dependency direction, where I/O lives

The demo service is one 200-line file, and at that size one file is right. Picture it at 5,000 lines with a second way in (a nightly batch job that summarises chats) and a second database (Postgres in production, SQLite in tests). Now the question "where does this code go?" matters, because the answer decides how much has to change when one of those outside things changes.

The idea that organises almost every well-structured service has an old name: ports and adapters, also called hexagonal architecture, from Alistair Cockburn's {{2005 article|https://alistair.cockburn.us/hexagonal-architecture/}}. Its stated intent: "Allow an application to equally be driven by users, programs, automated test or batch scripts, and to be developed and tested in isolation from its eventual run-time devices and databases." In plain words: the rules of your product sit in the middle and know nothing about HTTP, SQL or a vendor's SDK. A port is an interface the middle defines ("something that can give me a chat's messages"); an adapter is the code that implements it for one technology (Postgres, SQLite, an HTTP client, a fake for tests).

The chat service laid out by layer. Arrows are imports: each layer may import only the layers below it in the middle column; adapters implement ports and are wired in at the top.
chat_service/ main.py # composition root: builds the adapters, hands them to the app (section 8) config.py # settings read from the environment, validated once at start-up api/ # FastAPI routers: parse HTTP in, call a use case, render HTTP out. Thin. services/ # use cases: send_message, summarize_chat. Orchestrate; no SQL, no HTTP. domain/ # pure rules: fingerprints, prices, reply parsing. Imports nothing above. ports.py # Protocols the services need: ChatStore, ChatModel, RateLimiter adapters/ # postgres_store.py, sqlite_store.py, http_model.py, redis_limiter.py

Dependency direction is the rule that matters. domain imports nothing from the project; services import domain and ports; api imports services; nothing imports api or adapters except main.py. Then swapping SQLite for Postgres touches one adapter file, and a test can run a use case with fakes and no network. The rule can be enforced in CI with {{import-linter|https://import-linter.readthedocs.io/}} (2.15, September 2026), whose "layers" contract fails the build when a lower layer imports a higher one.

Where I/O lives. I/O (input/output) is anything that leaves the process: network, disk, database, clock, randomness, environment variables. It is slow, can fail, and makes tests need setup. Push it to the edges: read everything you need, make the decisions in plain functions, then write the results. The next section shows why on real code.

What it costs, and when not to
Every layer is a file to open and a name to learn. For a CRUD service whose "rules" are "store what the client sent", a service layer that only forwards calls to a repository is a shallow module (section 5): pure cost. Start with one module per feature (chats.py, billing.py); introduce a port when a second adapter actually appears (a test fake counts) or the rules grow beyond a screen.

4. Functional core, imperative shell: a tangled LLM call, measured

A pure function returns a value computed only from its arguments and changes nothing outside itself: no I/O, no globals. Pure functions are trivial to test (call, compare) and safe to reuse. Functional core, imperative shell is Gary Bernhardt's name for structuring code so that the decisions live in pure functions (the core) and a thin outer layer does the I/O (the shell) .

The example: a function that gives a chat a title and a summary by calling an LLM. The "before" version is the shape such code reaches after a few months of fixes: one function reads the database, builds the prompt, calls an OpenAI-style HTTP endpoint with retries, digs JSON out of the reply and writes the result. It was written for this page; the "after" version does the same job split into a core, two ports, two adapters and a ten-line shell. Both were then run through the same seven situations with a scripted fake server (no network), counting HTTP calls and seconds spent sleeping between retries.

What the table shows: in four of the seven situations the "before" code returns None, and in two of those only after three calls and seven seconds of sleeping. A caller cannot tell "the model refused" from "our request is malformed" from "this chat is empty". The cause is one line: except Exception around everything, which turns every bug, including a KeyError in our own parsing and a 400 that says our request is wrong, into "retry and hope". The "after" version retries only what retrying can fix (429 and 5xx responses, dropped connections) and says what went wrong with a typed exception (section 7).

What it costs, and when not to
The "after" file is longer ( source lines against ) and has eleven functions instead of one. For a one-off script you run by hand, that is overhead; keep it tangled and short. It pays as soon as the code runs unattended, has more than one caller, or needs tests. One honest behaviour change: "before" silently cut titles to 200 characters, "after" rejects them as a model output error. That was a decision, and it should be called out in the pull request, not hidden in a refactor (section 10).
