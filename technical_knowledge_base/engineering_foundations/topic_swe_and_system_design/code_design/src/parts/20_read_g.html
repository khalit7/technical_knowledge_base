9. Designing a Python library

A library is code whose callers you do not control: another team, the open-source world, or you in a different repository. Every rule above gets stricter because you cannot fix the callers when you change something. The bar the old page set is a good one: a colleague can use the package correctly from the type signatures alone. To make it concrete, the refactored LLM call was packaged as a real library, chatsummary 0.3.0 (in src/libdemo/), and built.

A small, explicit public surface

{{PEP 8|https://peps.python.org/pep-0008/#public-and-internal-interfaces}}: "Any backwards compatibility guarantees apply only to public interfaces", and modules "should explicitly declare the names in their public API using the __all__ attribute". In practice:

# chatsummary/__init__.py: the public API is exactly this list__all__ = ["summarize_chat", "render_transcript", "Summary", "Message", "ChatModel", "ChatStore", "HttpChatModel", "SqliteChatStore", "SummarizeError", "ChatNotFound", ...]# everything else lives in chatsummary/_core.py: the underscore says "internal, may change"
  • One obvious entry point (summarize_chat); everything else is there to support it.
  • Keyword-only options. A bare * in the signature ({{PEP 3102|https://peps.python.org/pep-3102/}}) forces summarize_chat("c1", store=s, model=m). Callers' code then says what each argument is, and you can add or reorder options later without breaking anyone.
  • No boolean positional flags. summarize(chat, True) means nothing at the call site; summarize(chat, force=True) does, and two behaviours behind one flag are often two functions.
  • Typed, and say so. Ship a py.typed marker file: {{PEP 561|https://peps.python.org/pep-0561/}} says packages that support type checking "MUST add a marker file named py.typed". Run mypy --strict in CI. The built wheel holds exactly: ; mypy --strict on it: "".
  • Exceptions are interface (section 7): one base class, exported.

Why so strict about the surface? Hyrum's law (quoted on {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}): with enough users, every observable behaviour will be depended on by somebody, documented or not. The smaller the surface, the less you are stuck with.

Versions: semantic versioning

{{Semantic Versioning 2.0.0|https://semver.org/}}: given MAJOR.MINOR.PATCH, increment MAJOR "when you make incompatible API changes", MINOR "when you add functionality in a backward compatible manner", PATCH "when you make backward compatible bug fixes". And: "Major version zero (0.y.z) is for initial development. Anything MAY change at any time. The public API SHOULD NOT be considered stable." That is why serious users pin 0.x libraries tightly (pydantic>=2.7,<3 pins a major; for a 0.x dependency pin the minor). The {{Breaking or not?|n:3c65c17b0d0d8190ade6c34e8f653e79}} quiz on the backend API page trains the same judgement for HTTP APIs.

Deprecation: change a public name without breaking anyone

To rename max_chars to limit in a released library: accept both for a while, warn when the old one is used, remove it in a later version that the warning names.

def render_transcript(messages, *, limit: int = 8000, max_chars: int | None = None) -> str: if max_chars is not None: warnings.warn("render_transcript(max_chars=...) is deprecated since 0.3.0 and will be removed in 0.5.0; " "use limit=...", DeprecationWarning, stacklevel=2) limit = max_chars return _render_transcript(messages, limit)

real called with the old name it still works and emits "", pointing at the caller's line () thanks to stacklevel=2. Without the shim, the same call fails outright: (from the Review lab).

Correction to the old page: how long to warn
The old page said "deprecate with DeprecationWarning one minor version before removal". Python's own policy, {{PEP 387|https://peps.python.org/pep-0387/#making-incompatible-changes}}, asks for more: "Wait for the warning to appear in at least two minor Python versions of the same major version", and "It is preferred, though, to wait 5 years before removal". That is CPython's rule, not a law for every library, but "at least two releases" is the safer default. Two more facts the old page missed: {{PEP 565|https://peps.python.org/pep-0565/}} makes DeprecationWarning visible by default only for code running directly in __main__, so your users' applications usually do not show it; their test runs do, since pytest displays it by default ({{pytest docs|https://docs.pytest.org/en/stable/how-to/capture-warnings.html}}). For warnings meant for end users of an application, the {{warnings docs|https://docs.python.org/3/library/warnings.html#warning-categories}} point to FutureWarning.

What it costs, and when not to
A published library turns every refactor into a compatibility question. Inside one company's monorepo, an internal module that every caller can be changed with in one commit does not need semver or deprecation shims: change the callers. Promote code to a library only when callers live in places you cannot edit.
