3. Deep modules and information hiding

An abstraction is "a simplified view of something that omits unimportant details" (Ousterhout's {{modular design notes|https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=modularDesign}}). A module is worth its interface when it hides much more than it exposes: "Deep class: small interface, lots of functionality"; a shallow one has a complex interface or little behind it, so "invoking a method isn't much easier than just typing in the code of the method". His canonical deep module is Unix file I/O: a handful of calls (open, read, write, close and a seek) hide disks, caches, permissions and whole file systems. The idea is David Parnas's information hiding ("On the Criteria To Be Used in Decomposing Systems into Modules", Communications of the ACM, 1972), which Ousterhout calls "the single most important idea in software design".

Most helpers of the refactored handler are deep; the two one-liners earn their place by their names

Every helper in the refactored service (step 10), drawn the way Ousterhout draws modules: the red top edge is the interface (parameters a caller must supply), the height is what it hides (source lines of its body), counted from the file by gen_data.py. A proxy: real interfaces also include errors, side effects and ordering rules, which no line count captures. claim_key hides 15 lines behind 3 parameters; chat_exists and request_fingerprint hide one line each and still earn their place, because their names say what a query or a hash is for. A shallow helper is fine when its name carries meaning; a shallow layer of them is classitis.

Three warnings from the same notes, each visible in the running example:

  • Classitis: "small classes taken to the extreme", each adding the least possible functionality, so the reader pays many interfaces for little. An LLMClientWrapper whose methods each call one SDK method is the everyday case: either hide something real (retries, typed errors, a smaller interface) or call the SDK directly.
  • Information leakage: one design decision known by several modules, so changing it means changing all of them. Its commonest cause is temporal decomposition: code split by the order things happen ("claim", then "release", then "save") instead of by what each piece knows. After step 9, claim_key was fairly deep, but the handler still had to remember to call release_key on two separate paths: the knowledge "a claimed key must be given back unless a response was saved" leaked into the caller.
  • Pull complexity downwards: "Let a few module developers suffer, rather than thousands of users." Step 10 pulled the leaked rule down into one context manager, idempotency_claim, which releases the key on every exit without a saved response. The caller's interface got smaller, and a latent bug disappeared as a side effect: in steps 0 to 9, a crash after claiming a key left it "started" forever, so every retry got (measured; section 9).

4. When to abstract: wait for the third copy, and back out of the wrong one

Every abstraction is a loan: it saves principal (duplicated code, places a change must touch) and charges interest (one more name to learn, one more jump when reading, one more shape every future change must fit). Two rules decide whether to take it.

The rule of three. "The first time you do something, you just do it. The second time you do something similar, you wince at the duplication, but you do the duplicate thing anyway. The third time you do something similar, you refactor." Popularised by Martin Fowler's Refactoring (1999) and attributed there to Don Roberts (1st edition, p. 58, quoted on the {{c2 wiki|https://wiki.c2.com/?ThreeStrikesAndYouRefactor}}; also {{Wikipedia|https://en.wikipedia.org/wiki/Rule_of_three_(computer_programming)}}; the book is not online, so this is a secondary quotation). With two copies you cannot yet see which parts really vary; with three, the axis of variation is visible, so the abstraction is shaped by facts rather than guesses. The demo service's auth check appeared four times (one per endpoint), which is why step 8 of the refactor turns it into one dependency.

The wrong abstraction costs more than duplication. Sandi Metz: "duplication is far cheaper than the wrong abstraction" ({{The Wrong Abstraction|https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction}}, 2016; she notes the phrase circulated earlier). Step through how it happens and her remedy:

Her remedy, in her words: "Re-introduce duplication by inlining the abstracted code back into every caller", keep in each copy only the branch that caller uses, delete the rest, then look again for the real shared part. "When dealing with the wrong abstraction, the fastest way forward is back."

The ML version: premature platformisation
Building "the framework for all our training jobs" or "the generic LLM provider layer" before the second job or provider exists. The abstraction is shaped by imagination, the second real case does not fit, and it grows flags. Build the concrete thing twice; extract the platform from the working examples. (Carried from the old page; it is the rule of three applied to systems.)

Cheap reversibility beats prediction: prefer abstractions you can inline away (a function, a Protocol) over ones you cannot (a service boundary, a published API, a database schema), and decide those last, when you know most. When not to abstract: two copies that may diverge; a "generic" layer with one implementation and no test fake; a base class whose subclasses override most of it; a wrapper whose methods each call one method of the thing it wraps (shallow: it adds a name and hides nothing).

Config, plugins and entry points (when variation is data, or others extend you)
  • Declarative config over code when the variation is data-shaped: eval suites, model routing tables, pipeline definitions as YAML or JSON validated by pydantic. The DAG engine split is the model: the DAG definition is declarative, the operators are code. The trap: config that grows conditionals until it is a worse programming language. When config needs if/else, go back to code (or a real DSL with review and tests).
  • Plugin architectures when others must extend you without forking: a small stable interface (a Protocol), and discovery through entry points, a standard packaging mechanism "for an installed distribution to advertise components it provides" ({{spec|https://packaging.python.org/en/latest/specifications/entry-points/}}). pytest finds plugins through the pytest11 entry point and its {{pluggy|https://pluggy.readthedocs.io/en/latest/}} core "enables 1400+ plugins"; Airflow providers declare an {{apache_airflow_provider entry point|https://airflow.apache.org/docs/apache-airflow-providers/howto/create-custom-providers.html}}; vLLM loads general plugins from the {{vllm.general_plugins group|https://docs.vllm.ai/en/stable/design/plugin_system/}}. Cost: a plugin interface is forever (Hyrum's law, quoted on {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}), so start private and promote to a plugin API only under demonstrated demand.
