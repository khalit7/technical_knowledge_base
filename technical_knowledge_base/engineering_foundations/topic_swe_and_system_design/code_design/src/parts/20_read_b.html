2. Readable code: names, function size, comments

Three habits do most of the work. None needs a framework; all three are about the reader.

Names

Python's style guide, {{PEP 8|https://peps.python.org/pep-0008/#naming-conventions}}, fixes the spelling: functions and variables in lower_case_with_underscores, classes in CapWords, constants in ALL_CAPS, and a leading underscore (_helper) as the "weak internal use indicator". The spelling is the easy part; a formatter and linter enforce it (section 12). The hard part is choosing what a name says:

  • Say what it is, not how it is made. The handler has req_hash = hashlib.sha256(...). The refactor renames the idea to request_fingerprint(chat_id, body): a reader learns what it is for (deciding whether two requests are "the same") without reading the hashing.
  • Put the unit in the name when there is one: timeout_s, max_chars, refill_per_s (all in the demo service). A bare timeout=30 leaves every reader guessing: seconds or milliseconds?
  • Booleans read as questions: is_retryable, has_more. Functions read as verbs: claim_key, release_key, save_reply.
  • Name length follows scope. r is fine for a response used on the next two lines; a module-level name needs to stand alone. Words like data, info, manager, handle and process say almost nothing; they usually mean the thing has no single job yet.

Function size and one level of abstraction

A function should read at one level of detail: either it says what happens in a few named steps, or it does one of those steps in detail. Mixing the two forces the reader to switch between "the plan" and "the SQL" every few lines. How short should a function be? Two experts disagree, usefully
Robert C. Martin's Clean Code (2008) pushes for very small functions. Ousterhout argues the opposite risk: "The advice in Clean Code on method length is so extreme that it encourages programmers to create teeny-tiny methods that suffer from both shallow interfaces and entanglement", and "Depth is more important than length: first make functions deep, then try to make them short enough to be easily read" ({{their written debate, September 2024 to February 2025|https://github.com/johnousterhout/aposd-vs-clean-code#method-length}}; the second quote is from the {{2nd edition extract|https://web.stanford.edu/~ouster/cgi-bin/aposd2ndEdExtract.pdf}}). The practical rule: split a function when the pieces have names that explain them and can be understood alone; do not split when the reader would have to jump between five tiny functions to follow one idea.

Comments that say why

Code says what it does; a comment earns its place by saying what the code cannot: why it is this way, what it protects against, what was tried and rejected. PEP 8: "Comments that contradict the code are worse than no comments", and inline comments "are unnecessary and in fact distracting if they state the obvious" (its example: x = x + 1 # Increment x). Google's review guide asks for comments that "mostly explain why instead of what" ({{What to look for|https://google.github.io/eng-practices/review/reviewer/looking-for.html#comments}}). From the demo service:

earns its place

API_KEYS = {sha256(b"sk_test_alice"): "alice"} # store a hash of the key, never the key# 1. claim the key atomically: the primary key makes a second insert fail

Says why (a leaked database must not leak keys) and what the code relies on (the primary key constraint), which no name can say.

noise

owner = who(authorization) # get the ownertokens -= 1 # subtract one token

Repeats the code. When the code changes, these are the comments that go stale and start to lie.

What it costs, and when not to
Renaming in shared code touches every caller and every open pull request; in a library it is a breaking change (section 9). Splitting functions adds jumps for the reader; it pays only when the new names carry meaning. Do not add docstrings to every private three-line helper "for completeness": a good name is shorter and cannot go stale.
