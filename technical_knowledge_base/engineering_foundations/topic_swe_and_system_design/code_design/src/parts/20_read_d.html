6. Composition over inheritance, and when patterns help

The Gang of Four's Design Patterns (Gamma, Helm, Johnson and Vlissides, 1994) states the principle in five words: "Favor object composition over class inheritance" (chapter 1; the book is not online). Inheritance reuses code by making a class a kind of another class, so the subclass depends on its parent's insides (tight coupling, and the coupling cannot be changed at run time). Composition reuses code by holding another object behind its interface, so each piece can be swapped or stacked. The difference shows the moment features combine:

Predict: two model providers, and you want retries, caching and logging in any combination. How many classes does each design need?

Derived, illustrative names: with m providers and k optional features, a subclass per combination needs m × 2k classes (2 × 8 = 16 at three features, counting the plain one); wrappers that each satisfy the same ChatModel Protocol need m + k = 5 and are stacked at the composition root: Logged(Cached(Retrying(HttpChatModel(...)))). Each wrapper is testable alone with a fake inside it.

Inheritance is still right for a true "is a" with a stable parent you control: an exception hierarchy (section 8), a framework's base class that is designed for it. Python's mechanics (the MRO, mixins, super()) are {{Python: the data model and protocols, section 5|n:4055c17b0d0d816a8705e4d3f20b3da7#s5}}'s.

Patterns: a name for a variation you already have

A design pattern is a named, reusable shape for a recurring problem. It helps when the variation it handles already exists in your code (the third copy of section 4) and when the name speeds review ("this is a Strategy"). It hurts when applied before the variation exists, which adds the interest of an abstraction without the principal. Many classic patterns shrink in a language with first-class functions and modules: Peter Norvig found "16 of 23 patterns have qualitatively simpler implementation in Lisp or Dylan than in C++ for at least some uses of each pattern", for example Strategy, Command, Template Method and Visitor through first-class functions and Facade through modules ({{Design Patterns in Dynamic Languages|https://norvig.com/design-patterns/}}, first presented 5 May 1996).
