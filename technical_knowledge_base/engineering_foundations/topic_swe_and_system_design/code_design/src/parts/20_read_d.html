5. Abstraction economics: when an abstraction pays

An abstraction is "a simplified view of something that omits unimportant details" (Ousterhout's {{modular design notes|https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=modularDesign}}): a function, a class, a Protocol, a config schema, a whole service. Every one of them is a loan. It saves principal (duplicated code, the number of places a change must touch) and charges interest (one more name to learn, one more jump when reading, one more thing every future change must fit). The questions below decide whether a loan is worth taking.

Wait for the third copy: the rule of three

"The first time you do something, you just do it. The second time you do something similar, you wince at the duplication, but you do the duplicate thing anyway. The third time you do something similar, you refactor." That is the rule of three, popularised by Martin Fowler's Refactoring (1999) and attributed there to Don Roberts (quoted from the 1st edition, p. 58, on the {{c2 wiki|https://wiki.c2.com/?ThreeStrikesAndYouRefactor}}; also {{Wikipedia|https://en.wikipedia.org/wiki/Rule_of_three_(computer_programming)}}; the book itself is not online, so this is a secondary quotation). The reason to wait: with two copies you cannot yet see which parts really vary. With three, the axis of variation is visible, so the abstraction is shaped by facts rather than guesses. The demo service's auth check appeared four times (one per endpoint), which is why step 8 of the refactor turns it into one dependency.

The wrong abstraction costs more than duplication

Sandi Metz: "duplication is far cheaper than the wrong abstraction" ({{The Wrong Abstraction|https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction}}, 2016; she notes the phrase circulated earlier). The pattern she describes: someone extracts a shared function; a new case is almost like it, so they add a parameter and an if; repeat a few times, and the shared function is a knot of flags that every caller depends on and nobody dares to change. Her remedy is to go backwards: "Re-introduce duplication by inlining the abstracted code back into every caller", keep in each copy only the branch that caller uses, delete the rest, then look again for the real shared part. "When dealing with the wrong abstraction, the fastest way forward is back."

The ML version: premature platformisation
Building "the framework for all our training jobs" or "the generic LLM provider layer" before the second job or provider exists. The abstraction is shaped by imagination, the second real case does not fit, and it grows flags. Build the concrete thing twice; extract the platform from the working examples. (This advice is carried from the old page; it is the rule of three applied to systems.)

Deep modules, not shallow ones

Ousterhout's central idea: a module is worth its interface when it hides much more than it exposes. "Deep class: small interface, lots of functionality"; a shallow one has a complex interface or little behind it, so "invoking a method isn't much easier than just typing in the code of the method". His canonical deep module is Unix file I/O: a handful of calls (open, read, write, close and a seek) hide disks, caches, permissions and whole file systems. Three related warnings from the same notes:

  • Classitis: "small classes taken to the extreme", each adding the least possible functionality, so the reader pays many interfaces for little.
  • Information leakage: a design decision known by several modules, so changing it means changing all of them. Its commonest cause is temporal decomposition: code split by the order things happen ("claim", then "release", then "save") instead of by what each piece knows.
  • Pull complexity downwards: "Let a few module developers suffer, rather than thousands of users." A module should handle the awkward cases itself instead of handing them to every caller.

The idea is older than the book: information hiding comes from David Parnas, "On the Criteria To Be Used in Decomposing Systems into Modules" (Communications of the ACM, 1972), which Ousterhout calls "the single most important idea in software design".

Read honestly, the chart says something uncomfortable about the refactor. After step 9, claim_key was fairly deep, but the handler still had to remember to call release_key on two separate paths: the knowledge "a claimed key must be given back unless a response was saved" leaked into the caller. That is exactly where a latent bug hid: if the handler crashed after claiming a key, the key stayed "started" forever and every retry got 409 (measured in every step from 0 to 9, on retry; see section 10). Step 10 pulls that complexity down into one context manager, idempotency_claim, which releases the key on every exit without a saved response. The caller's interface got smaller; the bug disappeared as a side effect.

Config, plugins and reversibility

  • Declarative config over code when the variation is data-shaped: eval suites, model routing tables, pipeline definitions as YAML or JSON validated by pydantic. The DAG engine split is the model: the DAG definition is declarative, the operators are code. The trap: config that grows conditionals until it is a worse programming language. When config needs if/else, go back to code (or a real DSL with review and tests).
  • Plugin architectures when others must extend you without forking: a small stable interface (a Protocol), and discovery through entry points, a standard packaging mechanism "for an installed distribution to advertise components it provides" ({{spec|https://packaging.python.org/en/latest/specifications/entry-points/}}). pytest finds plugins through the pytest11 entry point and its {{pluggy|https://pluggy.readthedocs.io/en/latest/}} core "enables 1400+ plugins"; Airflow providers declare an {{apache_airflow_provider entry point|https://airflow.apache.org/docs/apache-airflow-providers/howto/create-custom-providers.html}}; vLLM loads general plugins from the {{vllm.general_plugins group|https://docs.vllm.ai/en/stable/design/plugin_system/}}. Cost: a plugin interface is forever (Hyrum's law, quoted on {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}), so start private and promote to a plugin API only under demonstrated demand.
  • Cheap reversibility beats prediction: prefer abstractions you can inline away (a function, a Protocol) over ones you cannot (a service boundary, a published API, a database schema). Decide those last, when you know most.
When not to abstract
Two copies that may diverge; a "generic" layer with one implementation and no test fake; a base class whose subclasses override most of it; a wrapper whose methods each call one method of the thing it wraps (shallow: it adds a name and hides nothing).
