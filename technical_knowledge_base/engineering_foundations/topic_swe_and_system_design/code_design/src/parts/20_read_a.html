The idea in one screen

Good code design keeps the next change cheap and safe: put what changes together behind a small interface that hides a lot (high cohesion, low coupling, deep modules), let dependencies point toward the stable rules and keep I/O at the edges, and change structure only in small steps that tests pin down.

The same handler before and after: five concerns tangled in one function, then each behind one named helper

Real code: the busiest endpoint of the chat API built on {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}, before (52 lines, McCabe complexity 9) and after the ten-step refactor of section 9 (17 lines, complexity 4). Each stripe is one line of the handler, coloured by the concern it serves (by keyword rules, so a line or two is approximate). Before, the idempotency logic alone is split into 5 separate runs of lines; after, every concern is a call to a helper whose box is drawn as wide as its parameters and as tall as the lines it hides.

Why this is the whole subject. Code is read far more often than it is written ({{PEP 8|https://peps.python.org/pep-0008/#a-foolish-consistency-is-the-hobgoblin-of-little-minds}} credits the insight to Guido van Rossum), so the test of a design is the next change: code that works today but makes every change risky is bad code; code that is a little longer but where each change touches one place is good code. Every section below is one technique for that, with what it costs and when not to use it.

You need: Python and a little FastAPI; nothing else. Elsewhere: tests themselves are {{Testing and quality|n:3c65c17b0d0d81548848e2ebdd2f63ee}}'s (doubles, CI, mutation testing); language idioms, typing mechanics and the toolchain (ruff, uv, type checkers, packaging) are the {{Python page|n:3cd5c17b0d0d81b28acdea39e7a4d998}}'s; whole-system design is {{System design case studies|n:3ef5c17b0d0d81c3b211d75127ef5ded}}'; HTTP API design is {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}'s.

Module, interface
any unit with an inside and an outside (function, class, file, package, service); everything a caller must know to use it: names, parameters, results, errors, side effects
Cohesion, coupling
how strongly the parts inside one module belong together; how much one module depends on the inside of another
Deep module
small interface, lots hidden behind it (Ousterhout); a shallow one hides little more than it exposes
Port, adapter
an interface the core defines for something it needs (a store, a model); the code that implements it for one technology
Functional core, imperative shell
decisions in pure functions; a thin outer layer does the I/O
Refactoring, characterization test
a change of structure that keeps behaviour; a test that records what code does today
Technical debt
design shortcuts whose cost is paid later as "interest" on every change that touches them

1. The enemy is complexity; cohesion and coupling are how you see it

John Ousterhout, who teaches software design at Stanford, defines complexity as "Anything related to the structure of a system that makes it hard to work on the development of that system" ({{his course notes|https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=complexity}}; the book is {{A Philosophy of Software Design|https://web.stanford.edu/~ouster/cgi-bin/book.php}}, 2nd edition July 2021). Its three symptoms: change amplification (a simple change needs many edits), cognitive load (you must hold a lot in your head to make a change) and unknown unknowns (something you needed to know was not obvious, or not even findable). Its two causes: dependencies (if one piece changes, another must too) and obscurity (it is not clear how or why the code works). It is "judged by readers of code, not the writer", and it is incremental: "an accumulation of thousands of small dependencies and obscurities".

The older vocabulary for the same thing is cohesion and coupling, from Stevens, Myers and Constantine, "Structured design" ({{IBM Systems Journal 13(2), 1974|https://doi.org/10.1147/sj.132.0115}}; Constantine had used the terms since the late 1960s). Paraphrased: a module is cohesive when everything in it serves one purpose, so a change of that purpose touches one place; two modules are coupled when one depends on the other's insides, so changing one forces a change in the other. Aim for high cohesion and low coupling. In the hero figure the "before" handler has low cohesion: auth, rate limiting, idempotency, storage and the model call interleave, so changing the idempotency rule means finding its lines in five places. Coupling is the cause Ousterhout calls dependencies; low cohesion produces his change amplification and cognitive load.

Kent Beck's four rules of simple design, in priority order, compress the goal ({{Fowler's summary, 2015|https://martinfowler.com/bliki/BeckDesignRules.html}}): passes the tests, reveals intention, no duplication, fewest elements.

The running example
The chat product from the parent topic. Its API is a 200-line FastAPI service; its busiest endpoint, POST /v1/chats/{id}/messages, is one 52-line function that checks the API key, applies a rate limit, handles idempotency keys, stores the message, charges credits and "calls the model". It works, and it is exactly the kind of function that becomes hard to change. A second example, an LLM call that titles and summarises a chat, was written for this page in the tangled shape such code usually grows into.

2. Readable code: names, one level of detail, comments that say why

Names

{{PEP 8|https://peps.python.org/pep-0008/#naming-conventions}} fixes the spelling (lower_case_with_underscores functions, CapWords classes, ALL_CAPS constants, a leading underscore as the "weak internal use indicator"), and a formatter enforces it. The hard part is what a name says:

  • What it is, not how it is made. The handler has req_hash = hashlib.sha256(...); the refactor names the idea request_fingerprint(chat_id, body), so a reader learns what it is for (deciding whether two requests are "the same") without reading the hashing.
  • The unit in the name: timeout_s, max_chars, refill_per_s. A bare timeout=30 leaves every reader guessing: seconds or milliseconds?
  • Booleans read as questions (is_retryable, has_more), functions as verbs (claim_key, release_key, save_reply).
  • Length follows scope. r is fine for a response used on the next two lines; a module-level name must stand alone. data, info, manager, handle and process say almost nothing; they usually mean the thing has no single job yet.

One level of detail per function

A function should either say what happens in a few named steps, or do one of those steps in detail. Mixing the two forces the reader to switch between "the plan" and "the SQL" every few lines. Toggle the real handler: before, the rate-limit lines sit between the auth lines and the idempotency lines; after, each concern is one named line and the details live in functions you open only when you need them.

How short should a function be? Two experts disagree, usefully
Robert C. Martin's Clean Code (2008) pushes for very small functions. Ousterhout: "The advice in Clean Code on method length is so extreme that it encourages programmers to create teeny-tiny methods that suffer from both shallow interfaces and entanglement", and "Depth is more important than length: first make functions deep, then try to make them short enough to be easily read" ({{their written debate, September 2024 to February 2025|https://github.com/johnousterhout/aposd-vs-clean-code#method-length}}; the second quote is from the {{2nd edition extract|https://web.stanford.edu/~ouster/cgi-bin/aposd2ndEdExtract.pdf}}). The practical rule: split when the pieces have names that explain them and can be understood alone; do not split when the reader would jump between five tiny functions to follow one idea.

Comments that say why

Code says what; a comment earns its place by saying what the code cannot: why, what it protects against, what was tried and rejected. PEP 8: "Comments that contradict the code are worse than no comments", and inline comments "are unnecessary and in fact distracting if they state the obvious" (its example: x = x + 1 # Increment x). Google's review guide asks for comments that "mostly explain why instead of what" ({{What to look for|https://google.github.io/eng-practices/review/reviewer/looking-for.html#comments}}).

earns its place

API_KEYS = {sha256(b"sk_test_alice"): "alice"} # store a hash of the key, never the key# 1. claim the key atomically: the primary key makes a second insert fail

Says why (a leaked database must not leak keys) and what the code relies on (the primary key constraint), which no name can say.

noise

owner = who(authorization) # get the ownertokens -= 1 # subtract one token

Repeats the code. When the code changes, these are the comments that go stale and start to lie.

Cost. Renaming in shared code touches every caller and every open pull request; in a library it is a breaking change (section 12). Splitting adds jumps for the reader and pays only when the new names carry meaning. Do not docstring every private three-line helper "for completeness": a good name is shorter and cannot go stale.
