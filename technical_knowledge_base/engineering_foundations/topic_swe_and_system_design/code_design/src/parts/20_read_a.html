The page in one screen

Code is read far more often than it is written ({{PEP 8|https://peps.python.org/pep-0008/#a-foolish-consistency-is-the-hobgoblin-of-little-minds}} credits this insight to Guido van Rossum, Python's creator). So "good code" mostly means code that is cheap to read and safe to change. Everything below is a technique for that, each with the problem it solves, what it costs, and when not to use it.

Readable code: names that say what a thing is, functions that stay at one level of detail, comments that say why. Section
Structure: split a service into layers whose imports point one way, and keep I/O (network, disk, clock) at the edges. Section
Functional core, imperative shell: decisions in pure functions you can test in microseconds; a thin shell does the I/O. Shown on a real tangled LLM call: same seven situations, measured before and after. Section
Abstraction is a loan: it saves duplication but charges indirection. Wait for the third copy; prefer deep modules (small interface, lots hidden); a wrong abstraction costs more than duplication. Section
Types: type hints plus a checker (mypy, pyright) catch whole classes of bugs before running; dataclasses inside, pydantic at the boundaries (measured: about 5 times the cost of a dataclass per object). Section
Errors: raise typed exceptions instead of returning None; one base class per package; say in the type whether retrying helps. Section
Dependency injection: pass collaborators in as arguments; no framework needed; tests pass fakes. Section
Library design: a small public surface, keyword-only options, semantic versions, deprecations that warn for at least two releases. Section
Refactoring safely: pin behaviour with tests, then change structure in small steps that keep them green. Watch it on a real 52-line handler: ten steps, complexity 9 to 4, one test that caught a real behaviour change, and a latent bug found on the way. Section
Code review: approve when the change improves the code, not when it is perfect; small changes; label nits. Practise on real diffs in the {{Review lab|#t-review}}. Section
Tooling: ruff (lint and format), a type checker, pre-commit, uv, with versions as of today. Section
AI coding assistants: treat their output as a pull request from a fast, confident stranger; the evidence on speed is mixed. Section

1. What "good code" means

When you start, "good code" sounds like taste. It is more concrete than that. John Ousterhout, who teaches software design at Stanford, defines the enemy as complexity: "Anything related to the structure of a system that makes it hard to work on the development of that system" ({{his course notes|https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=complexity}}; the book is {{A Philosophy of Software Design|https://web.stanford.edu/~ouster/cgi-bin/book.php}}, 2nd edition July 2021). He names three symptoms: change amplification (a simple change needs many edits), cognitive load (you must hold a lot in your head to make a change) and unknown unknowns (something you needed to know was not obvious, or not even findable). And two causes: dependencies (if one piece changes, another must too) and obscurity (it is not clear how or why the code works). It is "judged by readers of code, not the writer", and it is incremental: "an accumulation of thousands of small dependencies and obscurities".

So the test of a design is the next change. Code that works today but makes every change risky is bad code; code that is a little longer but where each change touches one place is good code. Kent Beck's four rules of simple design, in priority order, say the same thing in one line each ({{Fowler's summary, 2015|https://martinfowler.com/bliki/BeckDesignRules.html}}): passes the tests, reveals intention, no duplication, fewest elements.

The running example
The chat product from the parent topic. Its API was built on {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}: a 200-line FastAPI service. Its busiest endpoint, POST /v1/chats/{id}/messages, is one 52-line function that checks the API key, applies a rate limit, handles idempotency keys, stores the message, charges credits and "calls the model". It works, and every exchange on that page was captured from it. It is also exactly the kind of function that becomes hard to change. This page refactors it. A second example, an LLM call that titles and summarises a chat, was written for this page in the tangled shape such code usually grows into.

Two words you will meet everywhere below. A module in design talk means any unit with an inside and an outside: a function, a class, a Python file, a package, a service. Its interface is everything a caller must know to use it (the names, parameters, return values, errors and side effects); its implementation is the rest. Most of code design is deciding what goes on which side.
