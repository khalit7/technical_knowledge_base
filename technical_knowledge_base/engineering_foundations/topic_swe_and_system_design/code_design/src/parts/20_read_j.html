What it costs, and when not to
Every rule you enable is a rule someone must satisfy or silence. Turning on everything (select = ["ALL"]) on an old codebase produces thousands of findings and teaches people to ignore the linter. Start with the defaults plus a few rules that catch bugs (bugbear B, blind except BLE), add more one at a time, and fix or baseline existing violations when you do.

13. Working with AI coding assistants: you are the reviewer

An AI coding assistant writes plausible code fast. Plausible is the risk: the failure mode is code that looks right, passes the tests it wrote for itself, and is subtly wrong at the edges. The old page put it well: "LLM-authored code raises the review bar, not lowers it". What the evidence says, as of today:

  • Speed is not settled. METR's randomised trial (16 experienced open-source developers, 246 real issues in their own repositories, early-2025 tools) found "when developers use AI tools, they take 19% longer than without", while the developers expected a 24% speedup and still believed afterwards that AI had sped them up by 20% ({{METR, 2025-07-10|https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/}}). A February 2026 follow-up with newer tools says its new data "gives us an unreliable signal of the current productivity effect of AI tools", because of who chose to take part ({{METR, 2026-02-24|https://metr.org/blog/2026-02-24-uplift-update/}}). Honest summary: no reliable measurement yet, and your own feeling of speed is not evidence.
  • Delivery can suffer. Google's DORA 2024 report associated a 25% increase in AI adoption with 7.5% better documentation quality and 3.4% better code quality, but also "an estimated decrease in delivery throughput by 1.5%, and an estimated reduction in delivery stability by 7.2%" ({{Google Cloud blog, 2024-10-23|https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report}}).
  • Models invent packages. Across 16 models and 576,000 code samples, "the average percentage of hallucinated packages is at least 5.2% for commercial models and 21.7% for open-source models", with 205,474 unique invented names ({{Spracklen et al., USENIX Security 2025|https://arxiv.org/abs/2406.10279}}). Attackers register such names ("slopsquatting"), so pip install of a suggested package you have never heard of can install malware.

A reviewer's checklist for AI output

  1. Read the tests first. Do they test behaviour, or do they test mocks? Would they fail if the code were wrong? (Review lab, "a test that tests the mock".)
  2. Ask for the invariants. Make the assistant (or yourself) state what must always hold ("a claimed key is released unless a response was saved") and check the code against that sentence.
  3. Check every new dependency exists, is the package you think it is, and is maintained.
  4. Watch the edges: error paths, retries, empty inputs, concurrency, time zones. Assistants write the happy path well. The "retry everything" and "blocking call in async code" diffs in the Review lab are both typical.
  5. Keep diffs small, the same rule as for humans; ask for one change at a time.
  6. Never let it edit the tests and the code in the same step to make a failure go away; that is how a characterization test gets "fixed" instead of the bug.
Go deeper: agent harnesses that run coding assistants are covered in {{Topic: agentic-harnesses|n:3c65c17b0d0d81d881a8fe98b4cff7bb}}; how coding agents are benchmarked, and why scores can mislead, in {{Agentic benchmarks|n:3c65c17b0d0d811fb926d7b91ef8234e}} and the paper page {{Schrödinger's Code Repository|n:3e95c17b0d0d81e8b0e0e99acbeb9713}} (has an LLM learned SWE-bench or memorised it?).

14. Common mistakes

Returning None (or False) for failures
The caller cannot tell why, and usually does not check. Raise a typed exception (section 7). Measured in section 4: four different failures, one None.
except Exception: around a block "to be safe"
It catches your own bugs (KeyError, TypeError) and the errors that say your request is wrong, then retries or hides them. Catch the narrowest exception that you can actually handle.
Abstracting on the second copy
The shared function gets shaped by a guess, then grows flags. Wait for the third (section 5); if the abstraction is already wrong, inline it back.
Shallow wrappers and classitis
A LLMClientWrapper whose methods each call one SDK method adds a name and hides nothing. Either hide something real (retries, typed errors, a smaller interface) or call the SDK directly.
Mixing a refactoring and a behaviour change in one PR
The reviewer cannot tell which line changes what callers see. Step 8 of the refactor shows a behaviour change hiding inside a "pure cleanup".
Rewriting instead of refactoring
The rewrite in section 10 is shorter, scores lower complexity, and fails 4 of 14 tests plus one untested behaviour. Rewrites lose the details that lived in the old structure.
Untyped signatures with a type checker in CI
The checker cannot check what is not annotated; mypy --strict reported 1 error on the tangled function, none of them its real problems. Annotate signatures first.
pydantic everywhere
Validation at every internal hop costs about five times a dataclass per object (measured, section 6) and buries the real boundary. Validate where data enters; trust it inside.
Humans reviewing formatting
Wastes the reviewer's attention and starts arguments. ruff format plus pre-commit ends the topic.
Removing a public name without a deprecation period
Callers break on upgrade with TypeError: ... unexpected keyword argument (measured in the Review lab). Warn for at least two releases first (section 9).
