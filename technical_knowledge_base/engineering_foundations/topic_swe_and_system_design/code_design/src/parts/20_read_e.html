7. Functional core, imperative shell: a tangled LLM call, measured

A pure function returns a value computed only from its arguments and changes nothing outside itself; it is trivial to test (call, compare) and safe to reuse. Functional core, imperative shell is Gary Bernhardt's name for putting the decisions in pure functions (the core) and the I/O in a thin outer layer (the shell) .

The example: a function that gives a chat a title and a summary by calling an LLM. "Before" is the shape such code reaches after a few months of fixes: one function reads the database, builds the prompt, calls an OpenAI-style HTTP endpoint with retries, digs JSON out of the reply and writes the result. "After" does the same job as a core, two ports, two adapters and a ten-line shell. Both were written for this page and run through the same seven situations with a scripted fake server (no network), counting HTTP calls and seconds spent sleeping between retries. Pick a situation:

real both files run on with httpx and pydantic ; script src/llmcall/measure.py. Retry sleeps are recorded, not slept.

In four of the seven situations "before" returns None, and in two of those only after three calls and seven seconds of sleeping, so a caller cannot tell "the model refused" from "our request is malformed" from "this chat is empty". The cause is one line: except Exception around everything, which turns every bug, including a KeyError in our own parsing and a 400 that says our request is wrong, into "retry and hope". "After" retries only what retrying can fix (429 and 5xx responses, dropped connections) and says what went wrong with a typed exception.

8. Error handling design: errors are part of the interface

Returning None for four different failures is the commonest error-handling mistake in Python services: the reason is thrown away, and the logs say summarize failed: 'choices' from inside a retry loop. {{PEP 20|https://peps.python.org/pep-0020/}}: "Errors should never pass silently. Unless explicitly silenced." Python's idiom is to raise an exception that travels up until a caller that can act catches it, in the style the glossary calls EAFP, "Easier to ask for forgiveness than permission" ({{glossary|https://docs.python.org/3/glossary.html#term-EAFP}}). The mechanics (chaining, groups, finally) are the {{Python page|n:3cd5c17b0d0d81b28acdea39e7a4d998}}'s, Part 1 section 7; the design is four rules:

  1. One base class per package, so a caller can catch everything from you in one line: SummarizeError.
  2. One subclass per thing a caller would handle differently, not per place it can happen: ChatNotFound (show a 404), ModelOutputError (log, maybe try another prompt), ModelUnavailable (retry later).
  3. Say whether retrying helps in the type or an attribute (retryable = True), so retry code does not parse messages.
  4. Keep the cause: raise ModelOutputError(str(e)) from e chains the original, so the traceback shows both.
A real hierarchy: the type says whether the SDK retries
OpenAIError└ APIError ├ APIConnectionError # could not reach the server: retried │ └ APITimeoutError # retried └ APIStatusError # the server answered with an error status ├ BadRequestError (400), AuthenticationError (401), PermissionDeniedError (403), │ NotFoundError (404), UnprocessableEntityError (422) # our fault: not retried ├ ConflictError (409), RateLimitError (429) # retried └ InternalServerError (5xx) # retried

The OpenAI Python SDK at v3.24.0 ({{_exceptions.py|https://github.com/openai/openai-python/blob/v3.24.0/src/openai/_exceptions.py}}). Its {{README|https://github.com/openai/openai-python/blob/v3.24.0/README.md#retries}}: "Connection errors (for example, due to a network connectivity problem), 408 Request Timeout, 409 Conflict, 429 Rate Limit, and >=500 Internal errors are all retried by default", 2 times with a short exponential backoff, and "Requests are retried only when their body can be safely resent". after.py copies the policy at small scale: only TransportError, 429 and 5xx are retried. Retry policy as a whole (backoff, jitter, budgets) is {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}'s.

Where to catch: where you can do something (retry, fall back, or turn the error into a response). In the refactored service that is one place: a single exception handler turns every ProblemError into an RFC 9457 problem response (step 2 of the refactor; the HTTP side is section 2 of {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}}). Everywhere else, let exceptions travel. Catching just to log and re-raise doubles every log line; catching Exception "to be safe" is the bug measured in section 7 (ruff flags it as BLE001, blind except).

Define errors out of existence (Ousterhout, {{exceptions notes|https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=exceptions}}: "Whenever possible, define errors out of existence"): choose semantics where the awkward case is not an error. set.discard(x) does nothing if x is absent (set.remove raises), os.makedirs(path, exist_ok=True), dict.get(key, default); in the refactor, idempotency_claim releasing the key on every exit removes a whole category of "forgot to release" errors.

Cost. A hierarchy is interface: every class you publish is a promise (section 12). Do not create one exception class per function. Exceptions are slow-ish in tight loops and wrong for expected outcomes ("no more pages" is a return value, not an error).

Note on the old page and on the SDK's HTTP library (checked 2026-10-04)

The old page described the retry pattern correctly. Two things changed since: the SDK is now at major version 3, and its README says its clients are "powered by HTTPX2" (pydantic's fork of httpx), whose exception tree mirrors httpx's (httpx: HTTPError splits into RequestError, with TransportError and its timeouts below it, and HTTPStatusError; {{docs|https://www.python-httpx.org/exceptions/}}). Code that caught httpx.TimeoutException around SDK calls should catch the SDK's own APITimeoutError instead: depend on the interface the library publishes, not on what it happens to use inside.
