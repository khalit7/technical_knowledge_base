6. Types in Python: hints, checkers, dataclasses, pydantic, protocols

Python does not check types when it runs: def f(x: int) happily accepts a string. A type hint ({{PEP 484|https://peps.python.org/pep-0484/}}, written 2014, Python 3.5) is an annotation for tools. A type checker reads the hints without running the code and reports calls that cannot work: passing None where a str is required, forgetting that a lookup can fail, misspelling an attribute. The problem it solves: a whole class of bugs found in seconds at your desk instead of in production, plus documentation that cannot go stale because CI checks it.

def summarize_chat(chat_id: str, *, store: ChatStore, model: ChatModel) -> Summary:def claim_key(owner: str, key: str, fingerprint: str) -> JSONResponse | None:role: Literal["user", "assistant", "system"]

Read them as sentences: JSONResponse | None ("a response, or nothing"; the | spelling is {{PEP 604|https://peps.python.org/pep-0604/}}, Python 3.10) forces every caller to handle the nothing. Literal[...] limits a string to known values, so a typo like "asistant" is caught. The bare * makes everything after it keyword-only (section 9).

A trap, measured: an unannotated function is nearly invisible to the checker
Run on the tangled LLM call (before.py), mypy --strict reports error: "". Not one of its real problems. Without annotations every parameter is Any, and Any is compatible with everything, so there is almost nothing to contradict. Type checking pays only once the signatures carry types. after.py, fully annotated: errors under the same flags, and now a wrong call would be caught.

Protocols: interfaces without inheritance

A Protocol ({{PEP 544|https://peps.python.org/pep-0544/}}, Python 3.8, "static duck typing") declares the methods something must have. Any class with matching methods satisfies it, with no base class and no import of the protocol:

class ChatModel(Protocol): def complete(self, system: str, user: str) -> str: ...# HttpChatModel (real HTTP) and FakeModel (tests) both satisfy it; neither mentions it.

This is how the "port" of section 3 is written in Python. Prefer it to an abstract base class when the implementations live in other packages or in tests.

Overloads: when the return type depends on an argument

The official OpenAI SDK (v3.24.0, 2026-10-02) types chat.completions.create with @overload: with stream: Literal[True] it returns Stream[ChatCompletionChunk], otherwise a ChatCompletion ({{source at the tag|https://github.com/openai/openai-python/blob/v3.24.0/src/openai/resources/chat/completions/completions.py}}). The checker then knows which one you hold, and iterating over a non-streamed reply is an error at your desk. Other tools in the same box: NewType("ModelId", str) so a model id cannot be passed where a chat id is expected, and generic functions with {{PEP 695|https://peps.python.org/pep-0695/}}'s def first[T](xs: Sequence[T]) -> T (Python 3.12).

dataclasses, attrs, pydantic: which one where

All three turn "a bag of named fields" into a class. A dataclass (standard library) generates __init__, __eq__ and __repr__ and checks nothing at run time. {{attrs|https://www.attrs.org/}} does the same with more options. A {{pydantic|https://docs.pydantic.dev/latest/}} BaseModel validates and converts every value when the object is built: wrong types, missing fields and constraint violations raise an error that says which field and why. Validation is the point at an input boundary and wasted work everywhere else. Measured cost per object:

real best of 7 runs of 100,000 constructions, nanoseconds per object, on an , Python , pydantic (pydantic-core ), attrs ; script src/bench/bench_models.py. Absolute numbers depend on the machine; the ratios are the point.

Three readings. A validated pydantic object costs about times a dataclass: nothing for one request, real money in a loop over ten million log rows. model_construct, the documented "skip validation" escape hatch, is slower here than validating; pydantic's own {{performance notes|https://docs.pydantic.dev/latest/concepts/performance/}} and {{model docs|https://docs.pydantic.dev/latest/concepts/models/#creating-models-without-validation}} warn that in V2 "for simple models, going with validation may even be faster". And parsing JSON straight into a model (model_validate_json) beats json.loads plus a dataclass, which is why pydantic's docs say to prefer it. The rule that follows: pydantic at the boundaries (HTTP bodies, LLM outputs, config read from the environment with {{pydantic-settings|https://docs.pydantic.dev/latest/concepts/pydantic_settings/}} 2.15.0, files from outside), dataclasses or attrs inside once the data is known to be valid.

Two more habits from the old page, both about signatures: accept abstract types, return concrete ones (take Sequence[Message] or Iterable, so callers can pass a list, a tuple or a generator; return list[Message], so callers know exactly what they got), and avoid "stringly typed" values (a str that is really one of five model names should be a Literal or an Enum).

What it costs, and when not to
Annotations take time to write and the checker has opinions about dynamic code (decorators, **kwargs plumbing, ORMs) that can take an hour to satisfy. # type: ignore[code] with the specific code is the honest escape. Do not chase strict mode in a throwaway notebook. Do not use pydantic models as your internal domain objects in hot paths.
