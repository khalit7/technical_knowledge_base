8. Snapshot and golden tests

Some outputs are too big to write by hand in a test: the full message list sent to the model, a rendered email, a transformed data frame. A snapshot test (also golden test) records the output once into a file, you review that file like code, and every later run compares against it. Any difference fails the test and shows a diff. Here it pins the exact prompt the chat product sends.

real experiments/snap/ with {{syrupy|https://github.com/syrupy-project/syrupy}} 
SYSTEM = "You are a helpful assistant for Acme. Answer briefly."

def build_messages(history, user_msg, max_turns=2):
    """The exact message list sent to the model: system prompt, the last few turns, the new message."""
    return [{"role": "system", "content": SYSTEM}] + history[-2 * max_turns:] + [{"role": "user", "content": user_msg}]

def test_prompt_is_stable(snapshot):      # syrupy's fixture
    assert build_messages(HISTORY, "refund?") == snapshot
$ pytest --snapshot-update # first run: writes __snapshots__/test_prompt_snapshot.ambr 1 snapshot generated. # someone changes max_turns=2 to max_turns=1 $ pytest E AssertionError: assert [+ received] == [- snapshot] E - dict({ E - 'content': 'price?', E - 'role': 'user',... 1 snapshot failed.

The change dropped a whole turn of conversation from every prompt; a snapshot makes that visible in review, where an assertion on "the last message is the user's" would not. {{inline-snapshot|https://15r10nk.github.io/inline-snapshot/}} does the same with the value written into the test file itself, which keeps small snapshots next to the code that checks them.

The danger is the update flag. When a snapshot fails, the easy move is --snapshot-update and commit, and the test now blesses the bug. Treat a snapshot diff as a code change: read it in review. Scrub values that change on every run (timestamps, generated ids) before comparing, or the test is flaky. Do not snapshot huge outputs nobody will read; snapshot a small, meaningful view of them.

When to use: prompt assembly, rendered templates, API response shapes, data transforms checked against a reviewed output file (a golden file). When not: anything nondeterministic, such as live model output; that needs an eval with a tolerance, not equality (section 12).

9. Testing async code

A chat backend is mostly async code: functions declared async def that pause at await while waiting on the network, so one process can serve many requests at once. pytest itself cannot run an async def test; a plugin such as {{pytest-asyncio|https://pytest-asyncio.readthedocs.io/}} (or AnyIO's pytest plugin) runs it in an event loop. In pytest-asyncio's default strict mode each async test needs @pytest.mark.asyncio.

real experiments/asy/test_async.py with pytest , pytest-asyncio 
async def first_token(stream, timeout):
    """Wait for the first token of a streamed reply, give up after `timeout` seconds."""
    return await asyncio.wait_for(anext(stream), timeout)

async def slow_stream(delay):
    await asyncio.sleep(delay)
    yield "Hello"

@pytest.mark.asyncio
async def test_first_token_arrives():
    assert await first_token(slow_stream(0.01), timeout=1) == "Hello"

@pytest.mark.asyncio
async def test_slow_model_times_out():
    with pytest.raises(TimeoutError):
        await first_token(slow_stream(10), timeout=0.05)

async def test_no_marker():                    # forgot the marker
    assert await first_token(slow_stream(0), 1) == "WRONG"

A trap that used to pass silently
The unmarked test asserts something false, and it fails here only because pytest refuses to run it. In older pytest versions an async test with no plugin was skipped with a warning, so a suite could show green while its async tests never ran; current pytest fails it instead ({{pytest 8.4.0 changelog|https://docs.pytest.org/en/stable/changelog.html}}, 2025-06-02: "Async tests will now fail, instead of warning+skipping, if you don't have any suitable plugin installed."). If your project pins an old pytest, check the warnings summary.
  • Timeouts belong in async tests: a hung await hangs CI forever. Give every network wait a timeout in the code, and test it with a delay far beyond the timeout (10 s against 0.05 s above) so the test is not flaky.
  • Do not sleep to wait for something. await asyncio.sleep(0.1) "so the background task finishes" is the classic flaky test (section 13). Await the task, or wait on an event the code sets.
  • Time-dependent logic (rate limiters, cache expiry, retries with backoff): pass the clock in as a function, and give the test a fake clock it can advance instantly, instead of sleeping for real.
  • Test web endpoints in-process: FastAPI's TestClient or httpx.AsyncClient with an ASGI transport calls your app without a network; {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}} has the service.
