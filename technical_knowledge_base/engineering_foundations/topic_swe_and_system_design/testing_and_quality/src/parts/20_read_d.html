6. Property-based testing: let the computer pick the inputs

An example-based test checks the inputs you thought of; bugs live in the ones you did not (the empty string, the one-character document, the emoji, the negative number). A property is a statement that must hold for every valid input, such as "cutting a document into chunks and gluing them back gives the document". A property-based test states the property, and a library generates hundreds of inputs trying to break it. The idea comes from Haskell's QuickCheck (Claessen and Hughes, 2000); in Python the library is {{Hypothesis|https://hypothesis.readthedocs.io/}}.

real experiments/hyp/test_chunking_property.py
from hypothesis import given, strategies as st
from chunking import chunk, unchunk

@st.composite
def chunk_args(draw):                       # a custom strategy: valid (size, overlap) pairs
    size = draw(st.integers(min_value=1, max_value=50))
    overlap = draw(st.integers(min_value=0, max_value=size - 1))
    return size, overlap

@given(text=st.text(), args=chunk_args())
def test_round_trip_loses_nothing(text, args):
    size, overlap = args
    assert unchunk(chunk(text, size, overlap), overlap) == text

A strategy describes how to generate one kind of value (st.text(), st.integers(1, 50), your own with @st.composite). Shrinking is what happens after a failure: Hypothesis keeps trying simpler versions of the failing input (shorter strings, smaller numbers, simpler characters) and keeps any that still fail, so the report is text='0', size=2, overlap=0 instead of a random 30-character unicode string. A one-character document with a two-character window: the bug, in one line.

  2. First failure (call 3). 2 characters, size 16, overlap 7: the text is shorter than one window, so chunk() returns no windows at all and the round trip gives back ''. The red floor shows why it came so soon: with overlap 0 an input fails unless its windows fit exactly, so most random documents trip it.
  3. Shrinking starts (calls 4 to 10). Hypothesis now tries simpler variants and keeps any that still fail. Overlap 7 becomes 0: still fails. It also tries two other failing texts (10 and 3 characters); size 1 always passes (one-character windows always fit), so the shrinker throws those away.
  4. Smaller windows (calls 11 to 15). Back on the 2-character text, size 16 halves to 8 and then 4: still failing. The empty text and size 2 (two characters fit one window exactly) pass.
  5. Size 3, plainer characters (calls 16 to 20). Size 3 still fails; the two exotic code points become '00', which still fails at size 3; sizes 1 and 2 pass.
  6. Shorter text (calls 21 to 24). '0' with size 3 fails, size 1 passes, size 2 fails: the smallest failure so far (glowing). The empty text passes again.
  7. The report (call 25). Nothing simpler fails, so Hypothesis runs the smallest failure once more to print its error report: text='0', args=(2, 0), a one-character document with a two-character window. Of the calls, 14 failed.
  1. The same property on the fixed chunk(). A window now starts wherever there is text the previous window did not cover. The floor is recomputed with the fixed code: no input in this space fails.
  2. Calls 1 to 50. The first half of a 100-call run of the same property: every generated input lands green, whatever its length, size and overlap.
  3. Calls 51 to 100. All 100 pass, the last character of every text covered by a window; the longer run below passed 5,000.

Across runs. Hypothesis is random, so the search differs from run to run. Over fixed seeds it found the bug in every run, always within the first generated inputs, because most random documents trip it. Shrinking ended at the true minimum ('0', size 2, overlap 0) in of runs; the others stopped at slightly larger inputs such as '0000' with size 3, which are just as readable. Shrinking is a local search: it guarantees that no simpler variant it tried still fails, not that no smaller failing input exists.

The fix starts a window wherever there is text the previous window did not cover: range(0, max(len(text) - overlap, 1), step), plus an early return for empty text. The same property then passed 5,000 generated cases (experiments/hyp/test_fixed_property.py, 2.3 s). It also cures a second symptom the examples never hit: the tail of any document whose length does not line up with the step, such as the last character of "abcde" with size 4 and overlap 1.

Determinism in CI. Hypothesis saves each failing input in a local example database (.hypothesis/examples) and replays it first next time. A CI machine starts with that folder empty, so Hypothesis {{now defaults|https://hypothesis.readthedocs.io/en/latest/reference/api.html#hypothesis.settings}} to derandomize=True on CI ("If running on CI, the default is True"): every CI run tries the same inputs, so a red build reproduces, and new inputs are explored on developers' machines (or keep randomness in CI and cache the database between runs). Pin a found bug as a permanent regression case with @example(text="0", args=(2, 0)) above @given.

Stateful testing: random sequences of operations

Some bugs need a particular sequence of calls. A stateful test lists the operations (rules), and Hypothesis runs random sequences of them against your code and a simple trusted model, comparing after each step. Here it tests the least-recently-used cache that holds embeddings by text hash: it should keep the two most recently used keys, but get forgets to mark a key as used. Hypothesis shrank random sequences to this five-step recipe:

Writing that sequence by hand requires already knowing the bug.

The stateful test's code (a RuleBasedStateMachine against an OrderedDict model)
real experiments/hyp/test_lru_stateful.py
class LRUMatchesModel(RuleBasedStateMachine):
    def __init__(self):
        super().__init__()
        self.cache = LRUCache(capacity=2)
        self.model = OrderedDict()            # the obviously-correct reference

    @rule(k=keys, v=st.integers())
    def put(self, k, v):
        self.cache.put(k, v)
        self.model[k] = v
        self.model.move_to_end(k)
        if len(self.model) > 2:
            self.model.popitem(last=False)

    @rule(k=keys)
    def get(self, k):
        expected = self.model.get(k)
        if k in self.model:
            self.model.move_to_end(k)
        assert self.cache.get(k) == expected

TestLRU = LRUMatchesModel.TestCase

Properties that pay off, especially in ML code

  • Round trip: decode(encode(x)) == x; config to YAML and back; a tokenizer where it promises it.
  • Invariants: shape and dtype preserved; row count preserved (or changed by exactly the filtered rows); no NaN introduced; output vocabulary within the expected set; probabilities sum to 1.
  • Idempotence: normalising twice equals normalising once, f(f(x)) == f(x).
  • Equivalence to a slow reference: the vectorised implementation equals a plain loop on every input (a test oracle).
  • Monotonicity: a higher score never ranks lower.
  • Never crashes: a parser for model output returns a value or raises your own error type, for any string.

What it costs, and when not to use it. Each property runs 100 examples by default, so it is slower than one example (seconds, not milliseconds). Thinking of a true property is the hard part; a property that restates the implementation proves nothing, and a strategy narrower than real inputs gives false confidence. Keep a few readable example tests as documentation, and add properties where the input space is large: parsers, serialisers, numeric transforms, data structures, anything with an inverse.

Checked: the old page's NumPy example, run as written (it fails, twice)

The old page's example property, @given(hnp.arrays(dtype=np.float32, shape=st.integers(1, 1000))) asserting that min-max normalisation produces no NaN, fails at once. Two reasons. First, by default the float strategy also generates NaN and infinity, so the test partly checks its own inputs; restrict them with elements=st.floats(-1e6, 1e6, width=32). Second, with finite inputs it still fails, and Hypothesis shrinks to x = array([0.]): a constant column makes max - min zero, and 0/0 is NaN. A real bug in every naive min-max scaler, found in under a second (experiments/mlt/test_normalize.py).

hypothesis.extra.numpy and hypothesis.extra.pandas generate arrays and data frames directly. Build domain objects with st.builds or @st.composite and reuse them across tests as a library of typed inputs.

Above sampling: fuzzing, then proof

A fuzz test is the "never crashes" property run for hours instead of 100 examples, with inputs mutated towards new code paths by coverage feedback; Google's OSS-Fuzz runs such entry points continuously for open-source libraries. However long it runs, it still samples. The rung above proves the property for every input: in October 2026 Anthropic's Frontier Red Team and Theorem had Claude write machine-checked Rocq proofs that 239 OSS-Fuzz entry points across 123 libraries never crash, fail an assertion or hit a memory-safety error for any input under 64 MB ({{Anthropic, Formal verification at scale|https://www.anthropic.com/research/formal-verification}}). The existing fuzz test became the specification ("this test always passes"), the library and the test were compiled to a RISC-V binary, and the proof is about those instructions, not the source; about 180 million lines of Rocq in all, and the effort found and patched hundreds of bugs, among them a counter underflow that needed a roughly 20 MB input, the kind sampling rarely reaches.

What the proof does not cover is as important. It assumes a single-threaded static binary linked against musl, a fixed memory budget and a modelled Linux process, while most deployments run x86 or ARM with glibc and threads; it trusts the RISC-V and OS models, the theorem statements and the proof checker; and it says nothing a fuzz test does not ask, such as wrong output. The authors put it plainly: "'Formally verified' does not mean 'bug-free.'" One failure mode is specific to a model doing the proving: Claude "could make any theorem provable by rewriting the program into one that trivially never crashes", so patches were penalised, logged and audited (the same patch-to-pass shortcut as on {{Reward Hacking|n:3c65c17b0d0d8196a6f1f29a817aa974}}). For your own code the order stays: examples, then properties, then fuzzing for parsers and decoders that take untrusted bytes; proof is now within reach where a crash is a security bug.
