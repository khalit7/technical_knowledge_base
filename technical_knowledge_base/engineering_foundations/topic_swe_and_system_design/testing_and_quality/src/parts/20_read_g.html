9. Flaky tests

A flaky test passes and fails on the same code. It is worse than no test: every red build might be noise, so people learn to press "rerun" until it is green, and then a real failure gets rerun away too. At Google's scale, "about 1.5% of all test runs" reported a flaky result and "almost 16% of our tests have some level of flakiness" ({{Micco, Google Testing Blog, 2016|https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html}}).

Almost half of fixed flaky tests waited on something asynchronously

Luo, Hariri, Eloussi and Marinov studied 201 fixes of flaky tests in 51 open-source projects and classified 161 ({{FSE 2014|https://mir.cs.illinois.edu/marinov/publications/LuoETAL14FlakyTestsAnalysis.pdf}}). Async wait: the test sleeps or polls instead of waiting for the thing it needs. Test order dependency: one test relies on state another leaves behind. "Other" is derived (161 - 74 - 32 - 19 = 36, several smaller categories). In ML code add unseeded randomness, real network calls and exact asserts on floats.

Two of these, built and measured:

1. Unseeded randomness

flaky

def full_jitter(attempt, rng=None):
    rng = rng or random
    return rng.uniform(0, backoff_delay(attempt))

def test_jitter_waits_a_bit():
    # attempt 3: uniform in [0, 2.0] seconds
    assert full_jitter(3) >= 0.1    # false 5% of the time

fixed

def test_jitter_stays_within_bounds():
    rng = random.Random(1234)        # same draws every run
    for attempt in range(1, 8):
        for _ in range(1000):
            d = full_jitter(attempt, rng)
            assert 0 <= d <= backoff_delay(attempt)

Each square is one run of the flaky test (pytest --count=2000, run by run from a JUnit XML report); red ones failed.

The fix does two things. It seeds the generator, so a failure always reproduces. And it asserts the real contract (the wait lies between 0 and the cap), which is true on every draw; "waits at least 0.1 s" was never part of the contract, and no seed makes an untrue assertion correct.

2. Test order dependency

flaky

def test_default_model():
    assert build_request("hi")["model"] == "small"

def test_large_model_override():
    settings_mod.CONFIG["model"] = "large"   # never restored
    assert build_request("hi")["model"] == "large"

fixed

def test_large_model_override(monkeypatch):
    monkeypatch.setitem(settings_mod.CONFIG, "model", "large")
    assert build_request("hi")["model"] == "large"
    # monkeypatch undoes the change after the test

The top cause: waiting on async code

A chat backend is mostly async code: functions declared async def that pause at await while waiting on the network, so one process can serve many requests at once. pytest itself cannot run an async def test; a plugin such as {{pytest-asyncio|https://pytest-asyncio.readthedocs.io/}} (or AnyIO's pytest plugin) runs it in an event loop. The rules that keep async tests deterministic:

  • Do not sleep to wait for something. await asyncio.sleep(0.1) "so the background task finishes" is the classic flaky test. Await the task, or wait on an event the code sets.
  • Timeouts belong in async tests: a hung await hangs CI forever. Give every network wait a timeout in the code, and test it with a delay far beyond the timeout (10 s against 0.05 s below) so the test is not flaky.
  • Time-dependent logic (rate limiters, cache expiry, retries with backoff): pass the clock in as a function, and give the test a fake clock it can advance instantly, instead of sleeping for real.
  • Test web endpoints in-process: FastAPI's TestClient or httpx.AsyncClient with an ASGI transport calls your app without a network; {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}} has the service.
Async tests in code, and a trap that used to pass silently (pytest-asyncio, pytest 8.4)

In pytest-asyncio's default strict mode each async test needs @pytest.mark.asyncio.

real experiments/asy/test_async.py with pytest , pytest-asyncio 
async def first_token(stream, timeout):
    """Wait for the first token of a streamed reply, give up after `timeout` seconds."""
    return await asyncio.wait_for(anext(stream), timeout)

async def slow_stream(delay):
    await asyncio.sleep(delay)
    yield "Hello"

@pytest.mark.asyncio
async def test_first_token_arrives():
    assert await first_token(slow_stream(0.01), timeout=1) == "Hello"

@pytest.mark.asyncio
async def test_slow_model_times_out():
    with pytest.raises(TimeoutError):
        await first_token(slow_stream(10), timeout=0.05)

async def test_no_marker():                    # forgot the marker
    assert await first_token(slow_stream(0), 1) == "WRONG"
PASSED test_async.py::test_first_token_arrives PASSED test_async.py::test_slow_model_times_out FAILED test_async.py::test_no_marker - Failed: async def functions are not natively supported.

The unmarked test asserts something false, and it fails here only because pytest refuses to run it. In older pytest versions an async test with no plugin was skipped with a warning, so a suite could show green while its async tests never ran; current pytest fails it instead ({{pytest 8.4.0 changelog|https://docs.pytest.org/en/stable/changelog.html}}, 2025-06-02: "Async tests will now fail, instead of warning+skipping, if you don't have any suitable plugin installed."). If your project pins an old pytest, check the warnings summary.

Find, measure, quarantine

Find them on purpose. {{pytest-randomly|https://pypi.org/project/pytest-randomly/}} shuffles test order on every run and resets random.seed, printing the seed so a failing order can be replayed with -p randomly --randomly-seed=N; run it in CI and order dependencies surface in days instead of months. {{pytest-xdist|https://pypi.org/project/pytest-xdist/}} (-n auto) runs tests in parallel processes, which finds shared files and ports. pytest-repeat's --count reruns a suspect test hundreds of times, as above.

Measure them. A test's flakiness is the share of runs on the same commit where it failed and then passed on retry. CI systems that keep test history (Buildkite Test Engine, Datadog, Trunk, or a script over JUnit XML reports) can compute it per test and rank the worst.

Quarantine, then fix or delete. Google built "a tool that monitors the flakiness of tests and if the flakiness is too high, it automatically quarantines the test. Quarantining removes the test from the critical path and files a bug for developers to reduce the flakiness" (same post). By hand: move it out of the blocking job, give the bug an owner and a deadline, then fix it or delete it. Automatic retry ({{pytest-rerunfailures|https://pypi.org/project/pytest-rerunfailures/}}, --reruns 2) keeps the build green but hides real intermittent bugs (a race in your code looks exactly like a flaky test) and slows the suite; if you use it, record every rerun and review the list. Never let "rerun until green" become the culture.
