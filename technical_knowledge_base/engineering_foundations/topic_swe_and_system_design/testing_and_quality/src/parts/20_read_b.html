2. Layers: what each catches, what it costs

Tests are grouped by how much of the system one test runs: a unit test runs one function or class in one process, no network or disk (milliseconds); an integration test runs your code with a real dependency such as a database, queue or another module (milliseconds to seconds); an end-to-end test drives the whole deployed system like a user (HTTP requests to the real API, a browser clicking the UI: seconds to minutes, and the flakiest); static checks (mypy, pyright, ruff) read the code without running it. Because "unit" and "integration" mean different things to different teams, Google sorts tests by the resources they use instead: "small tests run in a single process, medium tests run on a single machine, and large tests run wherever they want" ({{Software Engineering at Google, ch. 11|https://abseil.io/resources/swe-book/html/ch11.html}}). The PostgreSQL tests on this page are medium: one machine, a local server.

Pyramid and trophy agree on the top; they differ on how wide the middle is

Band widths are the shapes' proportions, not measurements. Click a band for what that layer catches, misses and costs on this page.

The test pyramid (Mike Cohn, Succeeding with Agile, 2009; {{Fowler's summary|https://martinfowler.com/bliki/TestPyramid.html}}, 2012): many fast unit tests at the base, fewer integration tests, very few end-to-end tests. Google's testing blog suggested "a 70/20/10 split: 70% unit tests, 20% integration tests, and 10% end-to-end tests" as a first guess ({{Wacker, 2015|https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html}}). The testing trophy (Kent C. Dodds, 2018; {{his 2021 write-up|https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications}}) puts static checks at the base and makes integration the widest layer, after Guillermo Rauch's line "Write tests. Not too many. Mostly integration." (2016).

Which shape? Both want most of the checking done by fast, reliable tests and few slow end-to-end ones. The pyramid fits code with a lot of logic of its own (a retry policy, a tokenizer, a pricing engine); the trophy fits code that is mostly wiring between other systems (a web front end, a thin API over a database), where a unit test with everything mocked checks little. ML systems add a band on top, evals, which score a model or prompt on a set of cases against a threshold; they are statistical, slow and costly, so they run on merge or nightly ({{Production eval engineering|n:3c65c17b0d0d81b39ad9e96193d21adc}} owns them).

3. Unit tests that survive refactoring

The first piece of the chat product under test is the chunker: before a document can be searched by meaning (retrieval, the R in RAG), it is cut into overlapping windows of text, each embedded separately. The function and three ordinary pytest tests:

real experiments/hyp/chunking.py
def chunk(text: str, size: int, overlap: int) -> list[str]:
    """Split text into windows of `size` characters; neighbours share `overlap` characters."""
    if not 0 <= overlap < size:
        raise ValueError("need 0 <= overlap < size")
    step = size - overlap
    return [text[i:i + size] for i in range(0, len(text) - size + 1, step)]

def unchunk(chunks: list[str], overlap: int) -> str:
    """Inverse of chunk: glue the windows back, dropping each repeated overlap."""
    if not chunks:
        return ""
    return chunks[0] + "".join(c[overlap:] for c in chunks[1:])
real experiments/hyp/test_chunking_examples.py
from chunking import chunk, unchunk

def test_splits_into_overlapping_windows():
    assert chunk("abcdefghij", size=4, overlap=1) == ["abcd", "defg", "ghij"]

def test_no_overlap():
    assert chunk("abcdef", size=2, overlap=0) == ["ab", "cd", "ef"]

def test_round_trip():
    text = "the quick brown fox jumps over the lazy dog!!"   # 45 characters
    assert unchunk(chunk(text, size=10, overlap=5), overlap=5) == text
$ pytest -q test_chunking_examples.py ... [100%] 3 passed in 0.53s

All green, and the function has a bug: look at len(text) - size + 1. Any document shorter than one window produces no chunks at all, so it silently vanishes from the search index. The three examples happen to use lengths where the windows fit exactly. Section 6 finds it without being told where to look.

Test behaviour, not implementation

The most useful idea in test design: a test checks what the code promises (its outputs, its errors, its effects others can see), not how it does it. Google's testing book puts the goal as tests that are "unchanging": they only need to change when the requirements change ({{Software Engineering at Google, ch. 12|https://abseil.io/resources/swe-book/html/ch12.html}}). The figure is why: the two kinds of test answer two kinds of change in opposite ways.

The retry policy's backoff_delay(attempt) returns 0.5 s doubled per attempt, capped at 8. The real bug is mutant backoff_delay #2 from section 10 (cap 8 changed to 9), which survived the weak suite. The brittle test is illustrative (mocker comes from pytest-mock).

How a good test reads:

  • Arrange, act, assert: build the inputs, call the code once, check the result. If a test needs three acts, it is three tests.
  • One reason to fail, and a name that says the behaviour: test_retry_preserves_idempotency_key, not test_retry_2. When it goes red in CI, the name is the bug report.
  • Tiny literal inputs written in the test itself, so the expected output can be checked by eye.
  • Write the failing test before fixing a bug. It proves you reproduced the bug and stops it coming back (a regression test). Every production incident should leave one behind; for model behaviour the equivalent is a new case in the golden set ({{Production eval engineering|n:3c65c17b0d0d81b39ad9e96193d21adc}}).
  • Design for testing: a function that takes its inputs as arguments and returns a value (a pure function) needs no setup at all. Anything that touches S3, a database or the clock goes behind an interface a test can replace. {{Code design|n:3ef5c17b0d0d817b99a0ff9701ff30cd}} (sections 4 and 8: functional core, dependency injection) shows the refactoring on a real handler.
pytest in one screen (runner, fixtures, parametrisation, errors, floats, markers, a starting config)

{{pytest|https://docs.pytest.org/en/stable/}} is the standard test runner for Python. A test runner finds your tests, runs each one in isolation, and reports which passed. pytest's rules are short: files named test_*.py, functions named test_*, and a plain assert statement as the check. When an assert fails, pytest rewrites it to show both sides ({{assertion introspection|https://docs.pytest.org/en/stable/how-to/assert.html}}), so you never need special assertEqual methods.

Fixtures. A fixture is a function that builds something a test needs (a database connection, a temporary folder, a fake server) and cleans it up afterwards. A test asks for it by naming it as an argument; pytest calls the fixture, passes in the value, and after the test runs the code after yield ({{fixtures docs|https://docs.pytest.org/en/stable/how-to/fixtures.html}}). The scope says how often it is rebuilt: function (default, once per test), module, or session (once per run, for expensive things). Fixtures shared by many files live in a conftest.py, which pytest loads automatically. These are the real fixtures behind the PostgreSQL tests in section 5:

real experiments/integ/conftest.py (timing code removed)
import sqlite3, tempfile
import pytest, psycopg, pgserver

@pytest.fixture
def sqlite_conn():
    conn = sqlite3.connect(":memory:")
    yield conn                      # the test runs here
    conn.close()                    # teardown, even if the test failed

@pytest.fixture(scope="session")    # start PostgreSQL once for the whole run
def pg_server():
    yield pgserver.get_server(tempfile.mkdtemp(prefix="pgtest"), cleanup_mode="stop")

@pytest.fixture
def pg_conn(pg_server):             # fixtures can use other fixtures
    with psycopg.connect(pg_server.get_uri(), autocommit=False) as conn:
        yield conn
        conn.rollback()             # every test's writes vanish: tests stay independent

pytest ships useful fixtures too: tmp_path (a fresh folder per test), monkeypatch (change an attribute, dict item or environment variable and undo it after the test; it fixes the order-dependent flake in section 9), capsys (capture printed output) and caplog (capture log records).

Parametrisation. @pytest.mark.parametrize runs the same test body once per row, each reported as its own test (test_parse_retry_after[-3-0.0]), so one bad row does not hide the others ({{parametrize docs|https://docs.pytest.org/en/stable/how-to/parametrize.html}}).   • assert total == pytest.approx(0.3) compares floats with a tolerance (default relative 1e-6); 0.1 + 0.2 == 0.3 is false in binary floating point. Section 8 shows why this matters for ML code.
