15. CI pipelines: running it all on every change

Continuous integration (CI) runs the checks automatically on every push and pull request, on a clean machine, and blocks the merge if any fail. It turns "the tests pass on my laptop" into "the tests pass, from scratch, for everyone". The design problem is time: developers wait for CI, so the order and split of the checks matter as much as the checks.

  • Cheapest first, fail fast. Lint and type checks take seconds and catch a large share of mistakes; run them first and stop there if they fail. Then unit tests (aim for a few minutes), then integration tests, then the slow tiers.
  • Tiers by cost. Unit on every push; integration with real services and fakes on every pull request; GPU, full-model and eval tiers on the merge queue or nightly. Mark tests (@pytest.mark.slow, gpu, integration) so laptops and CI select with -m.
  • Cache dependencies. Resolving and downloading packages can take longer than the tests; uv with its cache restores an environment in seconds.
  • Cancel stale runs. A new push to the same branch makes the previous run worthless; concurrency with cancel-in-progress: true cancels it ({{workflow syntax|https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax}}).
  • Parallelise with pytest -n auto (pytest-xdist) inside a job, and a matrix across Python versions; set fail-fast: false on a matrix when you want every version to report rather than stop at the first failure.
  • Same checks locally. pre-commit hooks run ruff (and optionally the fast tests) before each commit, so CI is rarely the first to find a lint error.
A complete GitHub Actions workflow for the chat product, dated 2026-10-04 (written for this page and parsed as valid YAML, not run on GitHub): experiments/ci/ci.yml
# .github/workflows/ci.yml  (written 2026-10-04; action versions checked on GitHub that day)
name: ci
on:
  pull_request:
  push:
    branches: [main]
  schedule:
    - cron: "0 3 * * *"              # nightly: slow and GPU tiers

concurrency:                          # a new push cancels the older run of the same branch
  group: ci-${{{ github.ref }}
  cancel-in-progress: true

jobs:
  static:                             # seconds: fail fast on the cheapest checks
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.2.0   # no floating @v10 tag since v8: pin a release or a SHA
        with: { enable-cache: true }
      - run: uv sync --locked
      - run: uv run ruff check . && uv run ruff format --check .
      - run: uv run mypy src

  unit:                               # minutes at most: every push
    needs: static
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false                # let every Python version report
      matrix: { python: ["3.12", "3.13"] }
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.2.0
        with: { enable-cache: true, python-version: "${{{ matrix.python }}" }
      - run: uv sync --locked
      - run: uv run pytest -m "not slow and not gpu" -n auto -p randomly --junitxml=unit.xml

  integration:                        # real PostgreSQL as a service container
    needs: unit
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17
        env: { POSTGRES_PASSWORD: test }
        ports: ["5432:5432"]
        options: >-
          --health-cmd pg_isready --health-interval 2s --health-timeout 5s --health-retries 20
    env:
      DATABASE_URL: postgresql://postgres:test@localhost:5432/postgres
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.2.0
        with: { enable-cache: true }
      - run: uv sync --locked
      - run: uv run pytest -m "integration" --junitxml=integration.xml

  gpu-nightly:                        # smoke training run and evals on a GPU runner
    if: github.event_name == 'schedule'
    runs-on: gpu-t4                   # the name you gave your GPU larger runner
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.2.0
        with: { enable-cache: true }
      - run: uv sync --locked
      - run: uv run pytest -m "gpu or slow"
Version pins, checked 2026-10-04
actions/checkout is at v7 (v7.0.1, 2026-07-20); many examples online still show v4. astral-sh/setup-uv stopped publishing floating major tags at v8.0.0 ("You won't be able to use @v8 or @v8.0 any longer", {{release notes|https://github.com/astral-sh/setup-uv/releases/tag/v8.0.0}}), so @v10 does not resolve: pin a full release such as v10.2.0, or a commit SHA, which is the safer habit for every third-party action.

GPU tests in CI

Some code paths (CUDA kernels, mixed precision, a serving engine) only run on a GPU. The options, cheapest to most flexible:

OptionWhat you getCost and catch
Avoid needing oneCPU runs of the smallest model that exercises the path, or a fake engine.Free; misses GPU-only bugs.
GitHub-hosted GPU runner4 vCPU, one NVIDIA T4 (16 GB), 28 GB RAM.$0.052 per minute on Linux, GitHub Team or Enterprise Cloud only ({{runner pricing|https://docs.github.com/en/billing/reference/actions-runner-pricing}}, 2026-10-04). A T4 is old and small: fine for smoke tests, not for a 70B model.
Self-hosted runner on your own GPU machineAny GPU, weights cached on local disk.You run and secure it; never attach one to a public repository, where anyone's pull request could run code on it.
Ephemeral cloud GPU from a CPU job (Modal, SkyPilot, a cloud batch API)A large GPU for the minutes the test needs.Pay per second; needs credentials in CI; cold starts add minutes.

Whatever runs on GPUs: cache model weights on the runner, use the smallest model that exercises the code, assert numeric results with tolerances (section 11), and keep full-size evals in the nightly tier.
