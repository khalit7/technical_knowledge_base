10. Coverage and mutation testing: is the suite any good?

Code coverage measures which code ran during the tests: line coverage counts executed lines; branch coverage also checks that every if went both ways. {{coverage.py|https://coverage.readthedocs.io/}} measures both (coverage run --branch -m pytest, then coverage report -m lists the lines that never ran). That list is valuable: code no test executes is certainly untested. The reverse does not hold: coverage records that a line ran, not that any test checked what it did.

Mutation testing asks the better question: if the code had a bug, would a test fail? A tool makes many small changes to the code, one at a time (each change is a mutant: >= becomes >, 2 becomes 3, - 1 becomes + 1), and runs the tests against each. A mutant is killed if some test fails and survives if every test still passes: a bug your suite would not notice. The mutation score is the share killed.

A gap measured here: what mutmut 3 does not mutate
mutmut 3 only mutates code inside functions; its README says to use mutmut 2 "if you want to mutate code outside of functions". The module-level RETRYABLE = frozenset({408, 429, 500, 502, 503, 504}) produced no mutants at all, so mutmut could not tell you that the weak suite never checks which statuses are retryable. The improved suite covers it by naming every status explicitly. Keep important constants inside functions or test them directly.

What the research and practice say

  • Inozemtseva and Holmes measured 31,000 test suites over five Java systems and found "a low to moderate correlation between coverage and effectiveness when the number of test cases in the suite is controlled for", effectiveness being mutants killed ({{ICSE 2014|https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf}}). Coverage is a floor detector, not a goal.
  • Google's guidance treats "60% as 'acceptable', 75% as 'commendable' and 90% as 'exemplary'", while adding "There is no 'ideal code coverage number' that universally applies to all products" and "We should not be obsessing on how to get from 90% code coverage to 95%" ({{Google Testing Blog, 2020|https://testing.googleblog.com/2020/08/code-coverage-best-practices.html}}).
  • Google runs mutation testing incrementally, "mutating only changed code during code review", showing at most one mutant per line as a review comment; "82% of all surfaced mutants with feedback were labeled as productive by developers" ({{Petrović et al., 2021|https://arxiv.org/abs/2102.11378}}). Developers exposed to it "write more tests, and actively improve their test suites" ({{Petrović et al., ICSE 2021|https://arxiv.org/abs/2103.07189}}).

What it costs. One run of the suite per mutant: here mutants at mutants per second, under a second, but a large service has tens of thousands of mutants and a suite that takes minutes. So run it on changed code only (as Google does), nightly, or on the modules that matter most (pricing, permissions, retries). Some mutants are equivalent: they change the code but not its behaviour, cannot be killed, and need a human to dismiss them. Skip it for glue code and prototypes; use it where a silent wrong value is expensive.
