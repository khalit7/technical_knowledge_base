4. Test doubles: prefer real, then fake, then mock

Real dependencies (the model provider, a payment API, a database) can be slow, cost money, need network access or fail at random. A test double stands in for one during a test, the way a stunt double stands in for an actor. Gerard Meszaros named the kinds in xUnit Test Patterns (2007); Martin Fowler's {{Mocks Aren't Stubs|https://martinfowler.com/articles/mocksArentStubs.html}} (2004, revised 2007) is the classic explanation. A dummy fills a parameter and is never used (a logger=None); a stub returns canned answers (a model client whose complete() always returns "Hello"); a spy is a stub that also records how it was called; a mock is pre-programmed with expected calls and fails the test if they differ (unittest.mock, pytest-mock: client.complete.assert_called_once_with(...)); a fake is a small working implementation with shortcuts (an in-memory chat store, an HTTP handler that answers like a chat-completions API).

What a test proves depends on what stands behind the seam

The same chat-search handler tested three ways. Only the real engine catches the case-sensitivity bug in section 5; the fake catches it only if whoever wrote the fake knew PostgreSQL's rule; the mock catches nothing about results, because it checks that a call was made.

Prefer real, then fake, then mock. Google's testing book: "A real implementation should be preferred over a test double. A fake is often the ideal solution if a real implementation can't be used" ({{Software Engineering at Google, ch. 13|https://abseil.io/resources/swe-book/html/ch13.html}}), and mocks sparingly. A test made of mocks restates the implementation, so it passes when the code is wrong and fails when the code is refactored correctly. {{Code design|n:3ef5c17b0d0d817b99a0ff9701ff30cd}}'s Review lab has a real example: a mock-only test that still passes with the function it claims to test broken.

Where a mock is the right tool

The interaction is the behaviour: "a payment is charged exactly once", "the alert is sent", "we never call the provider when the cache hits". Mock at the boundary you own (your PaymentGateway wrapper), not deep inside third-party libraries.

Where a mock lies

Mocking the database, then asserting the SQL string was passed. Mocking requests.post to return a dict that the real API never returns. Mocking a function in the same module you are testing. Each passes forever while production breaks.

Contract tests: keeping fakes honest

A fake drifts: the real service changes a field name and your fake does not. A contract test checks the agreement between two sides directly. In consumer-driven contract testing ({{Pact|https://docs.pact.io/}}, "a code-first consumer-driven contract testing tool"; pact-python 3.4.1, 2026-09-17), each side tests alone, yet a breaking change is caught before deploy:

Consumer-driven contracts: the consumer writes the expectations, the provider's CI replays them

Cost and when not to: it needs a place to share pacts (the Pact Broker or PactFlow) and buy-in from both teams. For a third-party API you do not control (a model provider), the provider will never run your pacts; use recorded responses and schema checks instead (section 7), and an OpenAPI document as the contract when one exists ({{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}}, section 3).

5. Integration tests against the engine you ship

An integration test runs your code with a real dependency (the actual database engine, a real Redis, a real HTTP stack) and catches the bugs that live between components: SQL a different engine reads differently, a transaction that does not roll back, a type the driver converts. A common shortcut is SQLite in memory in tests while production runs PostgreSQL. What that shortcut cost, measured:

real experiments/integ/: the same test against SQLite and PostgreSQL 
def search_chats(conn, owner, text):
    """Chats of this owner whose title contains `text`, ignoring case (the product spec)."""
    rows = conn.execute(q(conn, "SELECT id FROM chats WHERE owner = ? AND title LIKE ? ORDER BY id"),
                        (owner, f"%{text}%")).fetchall()
    return [r[0] for r in rows]

@pytest.mark.parametrize("db", ["sqlite_conn", "pg_conn"])
def test_search_ignores_case(db, request):
    conn = request.getfixturevalue(db)
    seed(conn)   # "Trip planning for Lisbon", "trip budget spreadsheet" (ada); "Trip ideas" (bob)
    assert search_chats(conn, "ada", "trip") == [1, 2]
Same query, same rows, two engines: PostgreSQL misses the capitalised title

Measured on 2026-10-04 (median of 50 runs each, experiments/integ/test_timing.py): per test, create a table, 3 inserts, 1 search. pytest's verdict: FAILED test_search.py::test_search_ignores_case[pg_conn] - assert [2] == [1, 2].

SQLite's LIKE ignores case for ASCII letters by default ({{SQLite docs|https://www.sqlite.org/lang_expr.html#like}}); PostgreSQL's LIKE is case-sensitive and offers ILIKE for the other behaviour ({{PostgreSQL docs|https://www.postgresql.org/docs/16/functions-matching.html#FUNCTIONS-LIKE}}). So the SQLite suite was green while production users searching "trip" never saw "Trip planning for Lisbon". The fix, lower(title) LIKE lower(?), passes on both; at scale you would add a trigram index ({{Topic: databases|n:3cd5c17b0d0d815d8841ec845f5f3324}} owns that depth).

The usual objection is speed: here a real PostgreSQL costs well under a second of startup per test run and a couple of milliseconds per test, so a suite of 500 such tests adds about a second. A little time for tests that use the engine you ship.

Keeping tests independent. Tests sharing a database leak state into each other. The cheapest isolation is a transaction rolled back after each test (the pg_conn fixture in section 3's pytest block). When the code under test commits on its own, truncate the tables after each test, or clone a prepared database per test with CREATE DATABASE t1 TEMPLATE base. With parallel workers (pytest-xdist), give each worker its own database. When not to: logic that does not touch the dependency (pricing rules, parsing, retry decisions) belongs in fast unit tests; integration tests are for the seams: queries, transactions, migrations, serialisation, configuration.
