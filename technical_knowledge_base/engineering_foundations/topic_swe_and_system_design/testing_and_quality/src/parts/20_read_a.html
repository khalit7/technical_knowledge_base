The idea in one screen

A test is worth the bug it would catch: for each behaviour, pick the cheapest deterministic check that fails when that behaviour breaks (a unit test, a generated property, a real database, a contract, a schema), run the cheap checks on every change, and judge the suite by what it notices (mutation score, flakiness), not by what it runs (coverage).

Every bug on this page, at the lowest layer that caught it

All of these were run for this page on 2026-10-04 against small pieces of the LLM chat product from the parent topic (a document chunker, a retry policy, chat search, a model-output parser, a data schema, a training loop). Higher layers run more of the system per test, cost more and fail for more reasons; the right-hand notes are the measured findings, each taught in its section below. Model quality, the top band, is measured by evals on another page.

The rule under every section: test each behaviour at the lowest layer that can catch its bugs. The chunker bug needs nothing above a unit test, but only a generated input finds it; the case-sensitive search cannot be caught below a real PostgreSQL; and the suite itself needs testing, because 100% coverage still let 7 of 23 planted bugs through.

1. What a test buys, and what it cannot

An automated test writes down the check you would do by hand (run the code, try an input, look at the output) so a machine repeats it in milliseconds whenever anything changes. It buys three things. Confidence to change: the day you refactor, upgrade a library or swap a model provider, the suite tells you within a minute whether anything a caller relies on broke; without it every change is a gamble, so people stop changing things and the code rots. Documentation that cannot go stale: test_client_errors_are_not_retried[404] says what the retry policy promises and fails the moment it stops being true. Design pressure: code that is hard to test (it opens its own database connection, reads the clock, calls the model directly) is usually hard to change for the same reasons.

It cannot prove the code correct. Edsger Dijkstra, 1970: "Program testing can be used to show the presence of bugs, but never to show their absence!" ({{EWD249|https://www.cs.utexas.edu/~EWD/ewd02xx/EWD249.PDF}}). Each kind of test is a different net; the craft is choosing nets that catch the bugs you are likely to have, at a cost you can afford to run on every change.

Checked: "a bug costs 100 times more in production" (the number is weaker than it sounds)

Its usual source is Boehm and Basili's 2001 "Software Defect Reduction Top 10 List" ({{IEEE Computer|https://www.cs.umd.edu/projects/SoftEng/ESEG/papers/82.78.pdf}}): "Finding and fixing a software problem after delivery is often 100 times more expensive than finding and fixing it during the requirements and design phase", which the same article qualifies: for small, noncritical systems the factor is "more like 5:1 than 100:1". It traces back to 1970s and 1980s data from large waterfall projects. Menzies, Nichols, Shull and Layman tested it on 171 modern projects and "found no evidence for the delayed issue effect" ({{arXiv 1609.04886|https://arxiv.org/abs/1609.04886}}, Empirical Software Engineering 2017); Laurent Bossavit traces how the figure spread in {{The Leprechauns of Software Engineering|https://leanpub.com/leprechauns}} (chapter 10).

What does hold, without a multiplier: a bug caught by a test on your laptop costs you seconds and nobody else anything; the same bug in production costs an incident, a rollback, a postmortem and some users' trust ({{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}). Argue for tests from that, not from the 100x.
