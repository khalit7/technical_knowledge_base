The page in one screen

A test is a small program that runs a piece of your code on an input you chose and checks the result. Its job is not to prove the code correct; it is to let you change the code tomorrow and find out in seconds whether you broke something. Everything below is a way to make that check cheaper, faster, or better at noticing bugs.

The habits that matter most
  • Test behaviour through the public interface, not how the code does it; then tests survive refactoring (section).
  • Prefer real things, then fakes, then mocks; a mock can pass while the code is broken (section).
  • Run the fast tests first and on every change; slow tests on merge or nightly (section).
  • Coverage tells you what never ran, not what is tested; mutation testing tells you whether a bug would be noticed (section).
  • A flaky test is a bug: measure it, quarantine it, fix it or delete it (section).
  • For ML and LLM code, test the code exactly, the data with schemas, and the model statistically; model quality belongs to evals, not unit tests (ML, LLM).

1. Why test at all

You already test: you run the code, try an input, look at the output. An automated test writes that check down so a machine can repeat it in milliseconds, every time anything changes. Three things follow.

  • Confidence to change. The real value of a test suite shows up the day you refactor, upgrade a library or swap a model provider: you change the code, run the suite, and know within a minute whether anything a caller relies on broke. Without tests, every change is a gamble, so people stop changing things and the code rots.
  • Documentation that cannot go stale. test_client_errors_are_not_retried[404] tells the next reader exactly what the retry policy promises, and it fails the moment it stops being true.
  • Design pressure. Code that is hard to test (it opens its own database connection, reads the clock, calls the model directly) is usually hard to change for the same reasons.

What tests cannot do is prove the code correct. Edsger Dijkstra, 1970: "Program testing can be used to show the presence of bugs, but never to show their absence!" (EWD249). Each kind of test below is a different net; the craft is choosing nets that catch the bugs you are likely to have, at a cost you can afford to run on every change.

Checked: "a bug costs 100 times more in production"

The number is everywhere and weaker than it sounds. Its usual source is Boehm and Basili's 2001 "Software Defect Reduction Top 10 List" (IEEE Computer): "Finding and fixing a software problem after delivery is often 100 times more expensive than finding and fixing it during the requirements and design phase", which the same article qualifies: for small, noncritical systems the factor is "more like 5:1 than 100:1". It traces back to 1970s and 1980s data from large waterfall projects. Menzies, Nichols, Shull and Layman tested it on 171 modern projects and "found no evidence for the delayed issue effect" (arXiv 1609.04886, Empirical Software Engineering 2017); Laurent Bossavit traces how the figure spread in The Leprechauns of Software Engineering (chapter 10).

What does hold, without a multiplier: a bug caught by a test on your laptop costs you seconds and nobody else anything; the same bug in production costs an incident, a rollback, a postmortem and some users' trust (Reliability engineering). Argue for tests from that, not from the 100x.

2. The test pyramid, the trophy, and what each layer catches

Tests are grouped by how much of the system they run at once:

  • Unit test: one function or class, in one process, no network or disk. Milliseconds.
  • Integration test: your code together with a real dependency (database, queue, another module). Milliseconds to seconds.
  • End-to-end test: the whole deployed system driven like a user would (HTTP requests to the real API, a browser clicking the UI). Seconds to minutes, and the most likely to be flaky.
  • Static checks: type checkers and linters (mypy, pyright, ruff) that read the code without running it.

Because "unit" and "integration" mean different things to different teams, Google sorts tests by the resources they use instead: "small tests run in a single process, medium tests run on a single machine, and large tests run wherever they want" (Software Engineering at Google, ch. 11). The PostgreSQL tests on this page are medium: one machine, a local server.

The test pyramid (Mike Cohn, Succeeding with Agile, 2009; Fowler's summary, 2012) says: many fast unit tests at the base, fewer integration tests, very few end-to-end tests at the top. Google's testing blog suggested "a 70/20/10 split: 70% unit tests, 20% integration tests, and 10% end-to-end tests" as a first guess (Wacker, 2015). The testing trophy (Kent C. Dodds, 2018; his 2021 write-up) puts static checks at the base and makes integration the widest layer, after Guillermo Rauch's line "Write tests. Not too many. Mostly integration." (2016). Which shape? They agree more than the arguments suggest: both want most of the checking done by fast, reliable tests, and few slow end-to-end ones. The pyramid fits code with a lot of logic of its own (a retry policy, a tokenizer, a pricing engine); the trophy fits code that is mostly wiring between other systems (a web front end, a thin API over a database), where a unit test with everything mocked checks little. A practical rule: test each behaviour at the lowest layer that can catch its bugs. The case-sensitivity bug in section 6 cannot be caught below the integration layer; the chunker bug in section 7 needs nothing above a unit test.

ML systems add a layer on top: evals, which score a model or prompt on a set of cases and compare against a threshold. They are statistical, slow and costly, so they run on merge or nightly; Production eval engineering owns them.

3. pytest from zero

pytest is the standard test runner for Python. A test runner finds your tests, runs each one in isolation, and reports which passed. pytest's rules are short: files named test_*.py, functions named test_*, and a plain assert statement as the check. When an assert fails, pytest rewrites it to show both sides (assertion introspection), so you never need special assertEqual methods.

The first piece of the chat product under test is the chunker: before a document can be searched by meaning (retrieval, the R in RAG), it is cut into overlapping windows of text, each embedded separately. Here are the function and three ordinary tests.

real experiments/hyp/chunking.py
def chunk(text: str, size: int, overlap: int) -> list[str]:
    """Split text into windows of `size` characters; neighbours share `overlap` characters."""
    if not 0 <= overlap < size:
        raise ValueError("need 0 <= overlap < size")
    step = size - overlap
    return [text[i:i + size] for i in range(0, len(text) - size + 1, step)]

def unchunk(chunks: list[str], overlap: int) -> str:
    """Inverse of chunk: glue the windows back, dropping each repeated overlap."""
    if not chunks:
        return ""
    return chunks[0] + "".join(c[overlap:] for c in chunks[1:])
real experiments/hyp/test_chunking_examples.py
from chunking import chunk, unchunk

def test_splits_into_overlapping_windows():
    assert chunk("abcdefghij", size=4, overlap=1) == ["abcd", "defg", "ghij"]

def test_no_overlap():
    assert chunk("abcdef", size=2, overlap=0) == ["ab", "cd", "ef"]

def test_round_trip():
    text = "the quick brown fox jumps over the lazy dog!!"   # 45 characters
    assert unchunk(chunk(text, size=10, overlap=5), overlap=5) == text
$ pytest -q test_chunking_examples.py ... [100%] 3 passed in 0.53s

All green, and the function has a bug: look at len(text) - size + 1. Any document shorter than one window produces no chunks at all, so it silently vanishes from the search index. The three examples happen to use lengths where the windows fit exactly. Hold that thought; section 7 finds it without being told where to look.

Fixtures: setup that tests ask for by name

A fixture is a function that builds something a test needs (a database connection, a temporary folder, a fake server) and cleans it up afterwards. A test asks for it by naming it as an argument; pytest calls the fixture, passes in the value, and after the test runs the code after yield (fixtures docs). The scope says how often it is rebuilt: function (default, once per test), module, or session (once per run, for expensive things). Fixtures shared by many files live in a conftest.py, which pytest loads automatically. These are the real fixtures behind the PostgreSQL tests in section 6:

real experiments/integ/conftest.py (timing code removed)
import sqlite3, tempfile
import pytest, psycopg, pgserver

@pytest.fixture
def sqlite_conn():
    conn = sqlite3.connect(":memory:")
    yield conn                      # the test runs here
    conn.close()                    # teardown, even if the test failed

@pytest.fixture(scope="session")    # start PostgreSQL once for the whole run
def pg_server():
    yield pgserver.get_server(tempfile.mkdtemp(prefix="pgtest"), cleanup_mode="stop")

@pytest.fixture
def pg_conn(pg_server):             # fixtures can use other fixtures
    with psycopg.connect(pg_server.get_uri(), autocommit=False) as conn:
        yield conn
        conn.rollback()             # every test's writes vanish: tests stay independent

pytest ships useful fixtures too: tmp_path (a fresh folder per test), monkeypatch (change an attribute, dict item or environment variable and undo it after the test; it fixes the order-dependent flake in section 13), capsys (capture printed output) and caplog (capture log records).

Parametrisation: one test, many cases

@pytest.mark.parametrize runs the same test body once per row, each reported as its own test (test_parse_retry_after[-3-0.0]), so one bad row does not hide the others (parametrize docs). From the retry policy that the chat product uses when the model provider fails:

real experiments/mut/tests/test_strong.py (excerpt)

    ("2", 2.0), ("1.5", 1.5), ("0", 0.0), ("-3", 0.0), (None, None), ("soon", None),

Checking errors, floats and slow tests

  • with pytest.raises(ValueError, match="overlap"): passes only if the block raises that exception type with a matching message. Assert the type and the condition, not merely that "something failed".
  • assert total == pytest.approx(0.3) compares floats with a tolerance (default relative 1e-6); 0.1 + 0.2 == 0.3 is false in binary floating point. Section 11 shows why this matters for ML code.
  • Markers label tests: @pytest.mark.slow, @pytest.mark.gpu. Declare them under markers in your config and add --strict-markers so a typo is an error, not a silently unselected test (markers docs).

4. Test behaviour, not implementation

The single most useful idea in test design: a test should check what the code promises (its outputs, its errors, its effects that others can see), not how it does it. A test tied to the how breaks every time you improve the code without changing what it does, which teaches people to stop refactoring. Google's testing book puts the goal as tests that are "unchanging": they only need to change when the requirements change (Software Engineering at Google, ch. 12).

brittle tests the implementation

def test_backoff_uses_min(mocker):
    spy = mocker.spy(builtins, "min")
    backoff_delay(3)
    spy.assert_called_once()

def test_retryable_set():
    assert 503 in retrypolicy.RETRYABLE

Illustrative (mocker comes from pytest-mock). Breaks if you rewrite the cap as an if; passes if the delay is wrong; reaches into a private detail.

robust tests the behaviour

def test_backoff_doubles_from_base_then_caps():
    assert [backoff_delay(a) for a in range(1, 7)] \
        == [0.5, 1, 2, 4, 8, 8]

def test_stops_at_max_attempts():
    assert not should_retry(503, attempt=3)

Survives any rewrite that keeps the promise; fails on any change a caller could notice.

How a good test reads

  • Arrange, act, assert: build the inputs, call the code once, check the result. If a test needs three acts, it is three tests.
  • One reason to fail, and a name that says the behaviour: test_retry_preserves_idempotency_key, not test_retry_2. When it goes red in CI, the name is the bug report.
  • Tiny literal inputs written in the test itself, so the expected output can be checked by eye.
  • Write the failing test before fixing a bug. It proves you reproduced the bug, and it stops the bug coming back (a regression test). Every production incident should leave one behind; for model behaviour, the equivalent is a new case in the golden set (Production eval engineering).
  • Design for testing: a function that takes its inputs as arguments and returns a value (a pure function) needs no setup at all. Anything that touches S3, a database or the clock goes behind an interface that a test can replace. Code design (sections 4 and 8: functional core, dependency injection) shows the refactoring on a real handler.

5. Test doubles: fakes, stubs, mocks, and why over-mocking lies

Real dependencies (the model provider, a payment API, a database) can be slow, cost money, need network access or fail at random. A test double stands in for one during a test, the way a stunt double stands in for an actor. Gerard Meszaros named the kinds in xUnit Test Patterns (2007); Martin Fowler's Mocks Aren't Stubs (2004, revised 2007) is the classic explanation.

DoubleWhat it isExample in the chat product
DummyPassed in to fill a parameter, never used.A logger=None argument in a test that never logs.
StubReturns canned answers.A model client whose complete() always returns "Hello".
SpyA stub that also records how it was called.The fake LLM server below keeps every request so the test can check temperature == 0.
MockPre-programmed with expected calls; the test fails if the calls differ (Python's unittest.mock, pytest-mock).client.complete.assert_called_once_with(...)
FakeA small working implementation with shortcuts.An in-memory chat store; an HTTP handler that answers like a chat-completions API.

Prefer real, then fake, then mock. Google's testing book recommends using the real implementation whenever it is fast and deterministic, a fake when it is not, and mocks sparingly (Software Engineering at Google, ch. 13: "A real implementation should be preferred over a test double. A fake is often the ideal solution if a real implementation can't be used"). The reason is what a mock checks: that your code called something in a particular way, not that the result is right. A test made of mocks restates the implementation, so it passes when the code is wrong and fails when the code is refactored correctly. Code design's Review lab has a real example: a mock-only test that still passes with the function it claims to test broken.

Where a mock is the right tool

The interaction is the behaviour: "a payment is charged exactly once", "the alert is sent", "we never call the provider when the cache hits". Mock at the boundary you own (your PaymentGateway wrapper), not deep inside third-party libraries.

Where a mock lies

Mocking the database, then asserting the SQL string was passed. Mocking requests.post to return a dict that the real API never returns. Mocking a function in the same module you are testing. Each passes forever while production breaks.

Contract tests: keeping fakes honest

A fake drifts: the real service changes a field name and your fake does not. A contract test checks the agreement between two sides directly. In consumer-driven contract testing (Pact, "a code-first consumer-driven contract testing tool"; pact-python 3.4.1, 2026-09-17), the consumer's tests run against a Pact mock server and write down every request they make and the response they rely on (the pact file); the provider's CI then replays those requests against the real provider and fails if any expectation breaks. Each side tests alone, yet a breaking change is caught before deploy.

Cost and when not to: it needs a place to share pacts (the Pact Broker or PactFlow) and buy-in from both teams. For a third-party API you do not control (a model provider), the provider will never run your pacts; use recorded responses and schema checks instead (section 12), and an OpenAPI document as the contract when one exists (Building a backend API, section 16).

6. Integration tests with real dependencies

An integration test runs your code together with a real dependency: the actual database engine, a real Redis, a real HTTP stack. It catches the bugs that live between components: SQL a different engine reads differently, a transaction that does not roll back, a type the driver converts. A common shortcut is to test against SQLite in memory while production runs PostgreSQL. Here is what that shortcut cost, measured.

real experiments/integ/: the same test against SQLite and PostgreSQL 
def search_chats(conn, owner, text):
    """Chats of this owner whose title contains `text`, ignoring case (the product spec)."""
    rows = conn.execute(q(conn, "SELECT id FROM chats WHERE owner = ? AND title LIKE ? ORDER BY id"),
                        (owner, f"%{text}%")).fetchall()
    return [r[0] for r in rows]

@pytest.mark.parametrize("db", ["sqlite_conn", "pg_conn"])
def test_search_ignores_case(db, request):
    conn = request.getfixturevalue(db)
    seed(conn)   # "Trip planning for Lisbon", "trip budget spreadsheet" (ada); "Trip ideas" (bob)
    assert search_chats(conn, "ada", "trip") == [1, 2]
test_search.py .F FAILED test_search.py::test_search_ignores_case[pg_conn] - assert [2] == [1, 2] 1 failed, 1 passed

SQLite's LIKE ignores case for ASCII letters by default (SQLite docs); PostgreSQL's LIKE is case-sensitive and offers ILIKE for the other behaviour (PostgreSQL docs). So the SQLite suite was green while production users searching "trip" never saw "Trip planning for Lisbon". The fix, lower(title) LIKE lower(?), passes on both; at scale you would add a trigram index (Topic: databases owns that depth).

The usual objection is speed. Measured on this laptop, a real PostgreSQL costs about a second of startup per test run and a couple of milliseconds per test. A suite of 500 such tests would add roughly a second. That is the trade: a little time for tests that use the engine you ship.

Keeping tests independent. Tests sharing a database leak state into each other. The cheapest isolation is the one above: each test runs inside a transaction that is rolled back at the end. When not to: logic that does not touch the dependency (pricing rules, parsing, retry decisions) belongs in fast unit tests. Integration tests are for the seams: queries, transactions, migrations, serialisation, configuration.

7. Property-based testing: let the computer pick the inputs

An example-based test checks the inputs you thought of. Bugs live in the inputs you did not think of: the empty string, the one-character document, the emoji, the negative number. A property is a statement that must hold for every valid input, such as "cutting a document into chunks and gluing them back gives the document". A property-based test states the property, and a library generates hundreds of inputs trying to break it. The idea comes from Haskell's QuickCheck (Claessen and Hughes, 2000); in Python the library is Hypothesis.

real experiments/hyp/test_chunking_property.py
from hypothesis import given, strategies as st
from chunking import chunk, unchunk

@st.composite
def chunk_args(draw):                       # a custom strategy: valid (size, overlap) pairs
    size = draw(st.integers(min_value=1, max_value=50))
    overlap = draw(st.integers(min_value=0, max_value=size - 1))
    return size, overlap

@given(text=st.text(), args=chunk_args())
def test_round_trip_loses_nothing(text, args):
    size, overlap = args
    assert unchunk(chunk(text, size, overlap), overlap) == text
$ pytest -q test_chunking_property.py E AssertionError: assert '' == '0' E Failing test case: test_round_trip_loses_nothing( E text='0', E args=(2, 0), E ) 1 failed in 1.81s

Two words to learn. A strategy describes how to generate one kind of value (st.text(), st.integers(1, 50), your own with @st.composite). Shrinking is what happens after a failure: Hypothesis keeps trying simpler versions of the failing input (shorter strings, smaller numbers, simpler characters) and keeps any that still fail, so the report is text='0', size=2, overlap=0 instead of a random 30-character unicode string. A one-character document with a two-character window: the bug, in one line.

Across runs. Hypothesis is random, so the search differs from run to run. Over fixed seeds it found the bug in every run, always within the first generated inputs, because most random documents trip it. Shrinking ended at the true minimum ('0', size 2, overlap 0) in of runs; the others stopped at slightly larger inputs such as '0000' with size 3, which are just as readable. Shrinking is a local search: it guarantees that no simpler variant it tried still fails, not that no smaller failing input exists.

The fix starts a window wherever there is text the previous window did not cover: range(0, max(len(text) - overlap, 1), step), plus an early return for empty text. The same property then passed 5,000 generated cases (experiments/hyp/test_fixed_property.py, 2.3 s). The fix also cures a second symptom the examples never hit: the tail of any document whose length does not line up with the step, such as the last character of "abcde" with size 4 and overlap 1.

The example database, and determinism in CI

When a test fails, Hypothesis saves the failing input in a local example database (.hypothesis/examples) and replays it first on the next run, so a bug found once is not lost to randomness. On a CI machine that folder starts empty, so Hypothesis now defaults to derandomize=True when it detects CI ("If running on CI, the default is True"): every CI run tries the same inputs, so a red build reproduces, and new inputs are explored on developers' machines. The alternative is to keep randomness in CI and cache the database between runs. Add @example(text="0", args=(2, 0)) above @given to pin a found bug as a permanent regression case.

Stateful testing: random sequences of operations

Some bugs need a particular sequence of calls. A stateful test lists the operations (rules), and Hypothesis runs random sequences of them against your code and a simple trusted model, comparing after each step. Here it tests the least-recently-used cache that holds embeddings by text hash: it should keep the two most recently used keys, but get forgets to mark a key as used.

real experiments/hyp/test_lru_stateful.py
class LRUMatchesModel(RuleBasedStateMachine):
    def __init__(self):
        super().__init__()
        self.cache = LRUCache(capacity=2)
        self.model = OrderedDict()            # the obviously-correct reference

    @rule(k=keys, v=st.integers())
    def put(self, k, v):
        self.cache.put(k, v)
        self.model[k] = v
        self.model.move_to_end(k)
        if len(self.model) > 2:
            self.model.popitem(last=False)

    @rule(k=keys)
    def get(self, k):
        expected = self.model.get(k)
        if k in self.model:
            self.model.move_to_end(k)
        assert self.cache.get(k) == expected

TestLRU = LRUMatchesModel.TestCase

Five steps, shrunk from random sequences: the exact recipe for the bug. Writing that sequence by hand requires already knowing the bug.

Properties that pay off, especially in ML code

  • Round trip: decode(encode(x)) == x; config to YAML and back; a tokenizer where it promises it.
  • Invariants: shape and dtype preserved; row count preserved (or changed by exactly the filtered rows); no NaN introduced; output vocabulary within the expected set; probabilities sum to 1.
  • Idempotence: normalising twice equals normalising once, f(f(x)) == f(x).
  • Equivalence to a slow reference: the vectorised implementation equals a plain loop on every input (a test oracle).
  • Monotonicity: a higher score never ranks lower.
  • Never crashes: a parser for model output returns a value or raises your own error type, for any string.

hypothesis.extra.numpy and hypothesis.extra.pandas generate arrays and data frames directly. Build domain objects with st.builds or @st.composite and reuse them across tests as a library of typed inputs.

Checked: the old page's NumPy example, run as written
The old page's example property, @given(hnp.arrays(dtype=np.float32, shape=st.integers(1, 1000))) asserting that min-max normalisation produces no NaN, fails at once. Two reasons. First, by default the float strategy also generates NaN and infinity, so the test partly checks its own inputs; restrict them with elements=st.floats(-1e6, 1e6, width=32). Second, with finite inputs it still fails, and Hypothesis shrinks to x = array([0.]): a constant column makes max - min zero, and 0/0 is NaN. A real bug in every naive min-max scaler, found in under a second (experiments/mlt/test_normalize.py).

What it costs, and when not to use it. Each property runs 100 examples by default, so it is slower than one example (seconds, not milliseconds). Thinking of a true property is the hard part; a property that restates the implementation proves nothing. A strategy narrower than real inputs gives false confidence. Keep a few readable example tests as documentation, and add properties where the input space is large: parsers, serialisers, numeric transforms, data structures, anything with an inverse.

8. Snapshot and golden tests

Some outputs are too big to write by hand in a test: the full message list sent to the model, a rendered email, a transformed data frame. A snapshot test (also golden test) records the output once into a file, you review that file like code, and every later run compares against it. Any difference fails the test and shows a diff. Here it pins the exact prompt the chat product sends.

real experiments/snap/ with syrupy 
SYSTEM = "You are a helpful assistant for Acme. Answer briefly."

def build_messages(history, user_msg, max_turns=2):
    """The exact message list sent to the model: system prompt, the last few turns, the new message."""
    return [{"role": "system", "content": SYSTEM}] + history[-2 * max_turns:] + [{"role": "user", "content": user_msg}]

def test_prompt_is_stable(snapshot):      # syrupy's fixture
    assert build_messages(HISTORY, "refund?") == snapshot
$ pytest --snapshot-update # first run: writes __snapshots__/test_prompt_snapshot.ambr 1 snapshot generated. # someone changes max_turns=2 to max_turns=1 $ pytest E AssertionError: assert [+ received] == [- snapshot] E - dict({ E - 'content': 'price?', E - 'role': 'user',... 1 snapshot failed.

The change dropped a whole turn of conversation from every prompt; a snapshot makes that visible in review, where an assertion on "the last message is the user's" would not. inline-snapshot does the same with the value written into the test file itself, which keeps small snapshots next to the code that checks them.

The danger is the update flag. When a snapshot fails, the easy move is --snapshot-update and commit, and the test now blesses the bug. Treat a snapshot diff as a code change: read it in review. Scrub values that change on every run (timestamps, generated ids) before comparing, or the test is flaky. Do not snapshot huge outputs nobody will read; snapshot a small, meaningful view of them.

When to use: prompt assembly, rendered templates, API response shapes, data transforms checked against a reviewed output file (a golden file). When not: anything nondeterministic, such as live model output; that needs an eval with a tolerance, not equality (section 12).

9. Testing async code

A chat backend is mostly async code: functions declared async def that pause at await while waiting on the network, so one process can serve many requests at once. pytest itself cannot run an async def test; a plugin such as pytest-asyncio (or AnyIO's pytest plugin) runs it in an event loop. In pytest-asyncio's default strict mode each async test needs @pytest.mark.asyncio.

real experiments/asy/test_async.py with pytest , pytest-asyncio 
async def first_token(stream, timeout):
    """Wait for the first token of a streamed reply, give up after `timeout` seconds."""
    return await asyncio.wait_for(anext(stream), timeout)

async def slow_stream(delay):
    await asyncio.sleep(delay)
    yield "Hello"

@pytest.mark.asyncio
async def test_first_token_arrives():
    assert await first_token(slow_stream(0.01), timeout=1) == "Hello"

@pytest.mark.asyncio
async def test_slow_model_times_out():
    with pytest.raises(TimeoutError):
        await first_token(slow_stream(10), timeout=0.05)

async def test_no_marker():                    # forgot the marker
    assert await first_token(slow_stream(0), 1) == "WRONG"
PASSED test_async.py::test_first_token_arrives PASSED test_async.py::test_slow_model_times_out FAILED test_async.py::test_no_marker - Failed: async def functions are not natively supported.
A trap that used to pass silently
The unmarked test asserts something false, and it fails here only because pytest refuses to run it. In older pytest versions an async test with no plugin was skipped with a warning, so a suite could show green while its async tests never ran; current pytest fails it instead (pytest 8.4.0 changelog, 2025-06-02: "Async tests will now fail, instead of warning+skipping, if you don't have any suitable plugin installed."). If your project pins an old pytest, check the warnings summary.
  • Timeouts belong in async tests: a hung await hangs CI forever. Give every network wait a timeout in the code, and test it with a delay far beyond the timeout (10 s against 0.05 s above) so the test is not flaky.
  • Do not sleep to wait for something. await asyncio.sleep(0.1) "so the background task finishes" is the classic flaky test (section 13). Await the task, or wait on an event the code sets.
  • Time-dependent logic (rate limiters, cache expiry, retries with backoff): pass the clock in as a function, and give the test a fake clock it can advance instantly, instead of sleeping for real.
  • Test web endpoints in-process: FastAPI's TestClient or httpx.AsyncClient with an ASGI transport calls your app without a network; Building a backend API has the service.

10. Test data: where test inputs come from

Every test needs inputs, and bad test data is a quiet source of bad tests: fixtures nobody understands, copies of production that leak personal data, shared files one test edits and another depends on. The options, from smallest to largest:

SourceUse it forWatch out for

11. Testing data and ML code

An ML system has three things to test, and they behave differently:

ObjectBehaviourHow you test it
Code (transforms, feature code, training loop, serving)Deterministic, given fixed seeds.pytest unit tests, property tests, types; exact or tolerance-based asserts.
Data (inputs, features, labels)Changes every day; can be checked against a schema and a distribution.Schema checks (pandera, Great Expectations) at pipeline boundaries; drift monitors in production.
Model (weights, prompts, the provider behind them)Statistical: right on most inputs, never all.Evals with thresholds and behavioural test sets (Production eval engineering).

Most "ML testing" failures come from testing only the first row. Eugene Yan's How to Test Machine Learning Code and Systems (2020) splits model tests into pre-train tests (shapes, the loss goes down, no label leakage) and post-train tests ("Post-train tests check if the learned logic is expected"); Google's ML Test Score (Breck et al., 2017) lists "28 specific tests and monitoring needs" across data, model development, infrastructure and monitoring, still the best checklist for production readiness.

Transforms are ordinary code: test them like it

The code between raw data and model input (cleaning, joining, feature computation, tokenisation, prompt assembly) is where most ML bugs live, and it is plain deterministic code. The habits:

  • Tiny literal fixtures: a few rows built inline, so the expected output can be checked by eye; golden files for bigger cases.
  • Invariants, not only examples: row count preserved (or changed by exactly the filtered rows), no NaN introduced, dtypes stable, keys unique, output values in the expected set.
  • Edge inputs production will send: an empty frame, one row, an all-null column, unicode, maximum-length strings, duplicate keys.
  • Tokenisation and prompt assembly are transforms too: assert round trips where the tokenizer promises them, render templates with empty, huge and injection-shaped fields, and assert exact token counts on cost-critical paths.
  • Pure functions over explicit inputs; anything that reads S3 or a database sits behind an interface a test can replace.
real experiments/mlt/test_transform.py (3 passed in 0.48 s)
def clean_chats(df):
    """Drop duplicate chat ids (keep the latest), strip whitespace, drop empty messages."""
    out = (df.sort_values("ts").drop_duplicates("chat_id", keep="last")
             .assign(text=lambda d: d["text"].str.strip()))
    return out[out["text"] != ""].sort_values("chat_id").reset_index(drop=True)

def test_keeps_latest_duplicate_and_drops_blank():
    df = pd.DataFrame({"chat_id": ["a", "a", "b", "c"], "ts": [1, 2, 1, 1],
                       "text": ["old", " new ", "hi", "   "]})
    want = pd.DataFrame({"chat_id": ["a", "b"], "ts": [2, 1], "text": ["new", "hi"]})
    pdt.assert_frame_equal(clean_chats(df), want)

def test_empty_frame_stays_empty_with_same_columns():
    df = pd.DataFrame({"chat_id": pd.Series(dtype=str), "ts": pd.Series(dtype=int),
                       "text": pd.Series(dtype=str)})

Tests check code on inputs you chose; production data arrives without asking. A data schema states what valid data looks like (columns, types, ranges, allowed values, uniqueness), and a validation step rejects or quarantines a batch that breaks it before it reaches training or a dashboard.

Seeds and tolerances: deterministic enough to test

A test that fails once in fifty runs is worse than none (section 13). ML code is full of randomness: shuffles, initialisation, dropout, sampling. Pass a seeded generator in (rng = np.random.default_rng(0)) rather than using global state, and set seeds for random, NumPy and PyTorch in a fixture. Even then, exact equality on floats is the wrong check:

The same million float32 numbers, summed forwards and backwards, give different answers, because floating-point addition is not associative. Parallel hardware sums in whatever order its threads finish, so GPU results can change between runs and versions: PyTorch states that "completely reproducible results are not guaranteed across PyTorch releases, individual commits, or different platforms", and offers torch.use_deterministic_algorithms(True) at some speed cost (PyTorch reproducibility notes). So numeric tests assert with a tolerance chosen for the precision: np.testing.assert_allclose(got, want, rtol=1e-5) for float32, looser for bf16, and never ==.

The training smoke test

Unit tests cannot see wiring bugs in a training loop: labels shuffled separately from inputs, the wrong tensor detached, a loss that is computed but never back-propagated. The cheapest catch is a smoke test: train on ten examples for a few hundred steps and assert the model memorises them.

real experiments/mlt/test_smoke.py (a tiny NumPy logistic regression stands in for a real model)
def test_overfits_ten_examples():
    losses = train(*ten_examples())
    assert losses[-1] < 0.1 * losses[0]       # a correct loop memorises 10 examples

def test_smoke_catches_shuffled_labels():
    losses = train(*ten_examples(), bug=True)  # labels shuffled apart from their inputs
    assert not losses[-1] < 0.1 * losses[0]   # the broken loop cannot

With a real model, use the smallest configuration that exercises the code path (two layers, a tiny vocabulary, or a 0.5B-parameter checkpoint), on CPU if possible, in seconds. It runs on every pull request; the full training run never does.

Model behaviour: where tests end and evals begin

Behavioural test sets borrow unit-test ideas for models. CheckList (Ribeiro et al., ACL 2020) names three kinds: minimum functionality tests (simple cases the model must get right), invariance tests ("label-preserving perturbations": a paraphrase or a swapped name must not change the answer) and directional tests (adding "answer in French" must change the language). Because a model passes them statistically, they are scored with a threshold and per-slice results, versioned with the prompt, and wired in as a merge gate; that machinery is on Production eval engineering.

12. Testing LLM features

An LLM feature is ordinary code wrapped around a call whose answer varies. Split it accordingly: the code around the call (building the prompt, parsing the answer, retrying, falling back) is tested like any code, fast and exactly, with the model replaced; the model's quality is measured by evals. Mixing the two gives slow, flaky, expensive unit tests that still do not tell you whether the model is good.

Contract tests on structured output

When model output feeds other code, the boundary needs a contract: a schema the output must satisfy, checked on every response. In Python that is a pydantic model. Structured-output modes (JSON mode, JSON schema, tool calling) and constrained decoding make valid output much more likely; validate anyway. Put semantic rules in the schema too: enum fields really in the enum, numbers within bounds, ids that resolve, citation indices in range.

real experiments/llm/extract.py with pydantic , httpx 
class Ticket(BaseModel):
    category: Literal["billing", "bug", "account", "other"]
    priority: int = Field(ge=1, le=4)
    summary: str = Field(min_length=1, max_length=200)

def extract_ticket(client: httpx.Client, message: str, retries: int = 1) -> Ticket:
    prompt = f"Return JSON with category, priority (1-4) and summary for: {message}"
    for attempt in range(retries + 1):
        r = client.post("/v1/chat/completions", json={
            "model": "small", "temperature": 0,
            "response_format": {"type": "json_object"},
            "messages": [{"role": "user", "content": prompt}]})
        r.raise_for_status()
        text = r.json()["choices"][0]["message"]["content"]
        try:
            return Ticket.model_validate_json(text)
        except ValidationError as e:              # repair: one retry with the error appended
            prompt += f"\nYour last answer was invalid: {e.errors()[0]['msg']}. Return valid JSON only."
    raise ValueError("model output failed validation after retries")

The repair loop retries once with the validation error in the prompt, then gives up and lets the caller fall back. Count how often it fires: a rising repair rate is an early signal that a model or prompt change has regressed.

A fake model server

To test that code without a real model, replace the HTTP layer. httpx.MockTransport routes requests to a Python function in the same process: a fake chat-completions server that returns scripted replies and records what it was sent (a fake and a spy at once, section 5).

real experiments/llm/test_extract.py (3 passed in 0.18 s)
def fake_llm(*replies):
    """A fake chat-completions server: returns the given replies in order and records requests."""
    seen = []
    def handler(request: httpx.Request) -> httpx.Response:
        seen.append(json.loads(request.content))
        content = replies[min(len(seen) - 1, len(replies) - 1)]
        return httpx.Response(200, json={"choices": [{"message": {"content": content}}]})
    return httpx.Client(base_url="http://fake-llm", transport=httpx.MockTransport(handler)), seen

def test_out_of_range_priority_is_repaired_once():
    client, seen = fake_llm('{"category": "bug", "priority": 7, "summary": "App crashes"}',
                            '{"category": "bug", "priority": 4, "summary": "App crashes"}')
    assert extract_ticket(client, "the app crashes on login").priority == 4
    assert len(seen) == 2 and "invalid" in seen[1]["messages"][0]["content"]

def test_gives_up_after_one_repair():
    client, seen = fake_llm('not json at all')
    with pytest.raises(ValueError):
        extract_ticket(client, "hello")
    assert len(seen) == 2

These tests pin the behaviour that matters to the rest of the system (valid output passes through, one repair, then a clean failure, temperature=0 and JSON mode are actually sent) and run in milliseconds with no API key. The same fake can be a small local HTTP server (FastAPI or http.server) when the code under test builds its own client.

Recorded responses (VCR)

A fake returns what you think the provider returns. A recorded response test captures what it really returned once: vcrpy intercepts HTTP, saves request and response to a YAML cassette, and replays it on later runs without a network. pytest-recording wraps it as a marker. Here the "provider" is a local server so the run is self-contained; with a real provider the steps are the same.

Record modes decide what happens on a miss: once (vcrpy's default) records if the cassette does not exist and replays otherwise; none never touches the network, which pytest-recording uses by default "to prevent unintentional network requests"; new_episodes and all record more. Costs: cassettes go stale when the provider changes its API, so re-record on a schedule and when upgrading the SDK; they can capture secrets and user data, so filter headers and use synthetic inputs; and a cassette replays one sample of a nondeterministic model, so assert on structure, not on exact wording.

When an eval replaces a test

A unit test asks "is this exactly right?" and expects the answer yes every time. For model quality ("are tickets categorised correctly?") the honest answer is a rate ("on 94% of cases", say), so the check is an eval: a versioned set of cases, scored, compared with the current production configuration, with a threshold and per-slice results. Use the split:

Test (exact, every push, fake model)

Prompt assembly, output parsing, schema validation, repair and fallback logic, retries, streaming, token counting, cost accounting, the gateway's routing rules.

Eval (statistical, on merge or nightly, real model)

Answer quality, categorisation accuracy, refusal behaviour, tone, groundedness. Every model, prompt, temperature or provider change runs it. See Production eval engineering and Eval harnesses.

A few deterministic assertions sit in between and can run on real model output in the eval job: the output parses, the tool call is valid, no forbidden string appears. Treat prompts as code: versioned, reviewed, and every edit runs the eval. Runtime checks on live traffic are Guardrails.

13. Flaky tests

A flaky test passes and fails on the same code. It is worse than no test: every red build might be noise, so people learn to press "rerun" until it is green, and then a real failure gets rerun away too. At Google's scale, "about 1.5% of all test runs" reported a flaky result and "almost 16% of our tests have some level of flakiness" (Micco, Google Testing Blog, 2016).

Causes. Luo, Hariri, Eloussi and Marinov studied 201 fixes of flaky tests in 51 open-source projects; of the 161 they could classify, the top causes were async wait (74, 45%: the test sleeps or polls instead of waiting for the thing it needs), concurrency (32, 20%) and test order dependency (19, 12%: one test relies on state another leaves behind) (FSE 2014). In ML code add unseeded randomness, real network calls, and exact asserts on floats. Two of these, built and measured:

1. Unseeded randomness

flaky

def full_jitter(attempt, rng=None):
    rng = rng or random
    return rng.uniform(0, backoff_delay(attempt))

def test_jitter_waits_a_bit():
    # attempt 3: uniform in [0, 2.0] seconds
    assert full_jitter(3) >= 0.1    # false 5% of the time

fixed

def test_jitter_stays_within_bounds():
    rng = random.Random(1234)        # same draws every run
    for attempt in range(1, 8):
        for _ in range(1000):
            d = full_jitter(attempt, rng)
            assert 0 <= d <= backoff_delay(attempt)

Each square is one run of the flaky test (pytest --count=2000, run by run from a JUnit XML report); red ones failed.

The fix does two things. It seeds the generator, so a failure always reproduces. And it asserts the real contract (the wait lies between 0 and the cap), which is true on every draw; "waits at least 0.1 s" was never part of the contract, and no seed makes an untrue assertion correct.

2. Test order dependency

flaky

def test_default_model():
    assert build_request("hi")["model"] == "small"

def test_large_model_override():
    settings_mod.CONFIG["model"] = "large"   # never restored
    assert build_request("hi")["model"] == "large"

fixed

def test_large_model_override(monkeypatch):
    monkeypatch.setitem(settings_mod.CONFIG, "model", "large")
    assert build_request("hi")["model"] == "large"
    # monkeypatch undoes the change after the test

Find them on purpose. pytest-randomly shuffles test order on every run and resets random.seed, printing the seed so a failing order can be replayed with -p randomly --randomly-seed=N; run it in CI and order dependencies surface in days instead of months. pytest-xdist (-n auto) runs tests in parallel processes, which finds shared files and ports. pytest-repeat's --count reruns a suspect test hundreds of times, as above.

Measure them. A test's flakiness is the share of runs on the same commit where it failed and then passed on retry. CI systems that keep test history (Buildkite Test Engine, Datadog, Trunk, or a script over JUnit XML reports) can compute it per test and rank the worst.

What to do with one. Google built "a tool that monitors the flakiness of tests and if the flakiness is too high, it automatically quarantines the test. Quarantining removes the test from the critical path and files a bug for developers to reduce the flakiness" (same post). Do the same by hand if you must: move it out of the blocking job, give the bug an owner and a deadline, then fix it or delete it. Automatic retry (pytest-rerunfailures, --reruns 2) keeps the build green, but it hides real intermittent bugs (a race in your code looks exactly like a flaky test) and slows the suite; if you use it, record every rerun and review the list. Never let "rerun until green" become the culture.

14. Coverage and mutation testing: is the suite any good?

Code coverage measures which code ran during the tests. Line coverage counts executed lines; branch coverage also checks that every if went both ways. coverage.py measures both: coverage run --branch -m pytest, then coverage report -m lists the lines that never ran. That list is valuable: code no test executes is certainly untested. The reverse does not hold. Coverage records that a line ran, not that any test checked what it did.

Here is a weak suite for the retry policy. It calls every function, so every line and branch runs:

real experiments/mut/tests/test_weak.py
def test_should_retry():
    assert should_retry(503, attempt=1)
    assert not should_retry(503, attempt=3)

def test_backoff_delay():
    assert backoff_delay(1) > 0

def test_parse_retry_after():
    assert parse_retry_after("2") == 2.0
    assert parse_retry_after(None) is None
    assert parse_retry_after("soon") is None

Mutation testing asks the better question: if the code had a bug, would a test fail? A tool makes many small changes to the code, one at a time (each change is a mutant: >= becomes >, 2 becomes 3, - 1 becomes + 1), and runs the tests against each. A mutant is killed if some test fails, and survives if every test still passes: a bug your suite would not notice. The mutation score is the share killed.

real mutmut , configured in pyproject.toml
[tool.mutmut]
source_paths = ["src/"]
pytest_add_cli_args_test_selection = ["tests/test_weak.py"]

$ mutmut run            # generate mutants, run the suite against each
$ mutmut results        # list survivors
$ mutmut show retrypolicy.x_backoff_delay__mutmut_9    # the diff of one mutant

The weak suite has 100% line and branch coverage and lets planted bugs through, every one of them a wrong value: the base delay 0.5 changed to 1.5, the cap 8 to 9, doubling changed to tripling, an off-by-one in the exponent, a negative Retry-After floored at 1 instead of 0. And of its kills were mutants that crash (min(None, ...)), which any test that merely calls the line would kill. The improved suite (exact delays for attempts 1 to 6, a custom cap, every retryable and non-retryable status, the boundary at the last allowed attempt, negative and zero headers) kills all . Toggle tests on and off and watch both numbers in the Mutation lab.

A gap measured here: what mutmut 3 does not mutate
mutmut 3 only mutates code inside functions; its README says to use mutmut 2 "if you want to mutate code outside of functions". The module-level RETRYABLE = frozenset({408, 429, 500, 502, 503, 504}) produced no mutants at all, so mutmut could not tell you that the weak suite never checks which statuses are retryable. The improved suite covers it by naming every status explicitly. Keep important constants inside functions or test them directly.

What the research and practice say

  • Inozemtseva and Holmes measured 31,000 test suites over five Java systems and found "a low to moderate correlation between coverage and effectiveness when the number of test cases in the suite is controlled for", effectiveness being mutants killed (ICSE 2014). Coverage is a floor detector, not a goal.
  • Google's guidance treats "60% as 'acceptable', 75% as 'commendable' and 90% as 'exemplary'", while adding "There is no 'ideal code coverage number' that universally applies to all products" and "We should not be obsessing on how to get from 90% code coverage to 95%" (Google Testing Blog, 2020).
  • Google runs mutation testing incrementally, "mutating only changed code during code review", showing at most one mutant per line as a review comment; "82% of all surfaced mutants with feedback were labeled as productive by developers" (Petrović et al., 2021). Developers exposed to it "write more tests, and actively improve their test suites" (Petrović et al., ICSE 2021).

What it costs. One run of the suite per mutant: here mutants at mutants per second, under a second, but a large service has tens of thousands of mutants and a suite that takes minutes. So run it on changed code only (as Google does), nightly, or on the modules that matter most (pricing, permissions, retries). Some mutants are equivalent: they change the code but not its behaviour, cannot be killed, and need a human to dismiss them. Skip it for glue code and prototypes; use it where a silent wrong value is expensive.

15. CI pipelines: running it all on every change

Continuous integration (CI) runs the checks automatically on every push and pull request, on a clean machine, and blocks the merge if any fail. It turns "the tests pass on my laptop" into "the tests pass, from scratch, for everyone". The design problem is time: developers wait for CI, so the order and split of the checks matter as much as the checks.

  • Cheapest first, fail fast. Lint and type checks take seconds and catch a large share of mistakes; run them first and stop there if they fail. Then unit tests (aim for a few minutes), then integration tests, then the slow tiers.
  • Tiers by cost. Unit on every push; integration with real services and fakes on every pull request; GPU, full-model and eval tiers on the merge queue or nightly. Mark tests (@pytest.mark.slow, gpu, integration) so laptops and CI select with -m.
  • Cache dependencies. Resolving and downloading packages can take longer than the tests; uv with its cache restores an environment in seconds.
  • Cancel stale runs. A new push to the same branch makes the previous run worthless; concurrency with cancel-in-progress: true cancels it (workflow syntax).
  • Parallelise with pytest -n auto (pytest-xdist) inside a job, and a matrix across Python versions; set fail-fast: false on a matrix when you want every version to report rather than stop at the first failure.
  • Same checks locally. pre-commit hooks run ruff (and optionally the fast tests) before each commit, so CI is rarely the first to find a lint error.
A complete GitHub Actions workflow for the chat product, dated 2026-10-04 (written for this page and parsed as valid YAML, not run on GitHub): experiments/ci/ci.yml
# .github/workflows/ci.yml  (written 2026-10-04; action versions checked on GitHub that day)
name: ci
on:
  pull_request:
  push:
    branches: [main]
  schedule:
    - cron: "0 3 * * *"              # nightly: slow and GPU tiers

concurrency:                          # a new push cancels the older run of the same branch
  group: ci-${{{ github.ref }}
  cancel-in-progress: true

jobs:
  static:                             # seconds: fail fast on the cheapest checks
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.2.0   # no floating @v10 tag since v8: pin a release or a SHA
        with: { enable-cache: true }
      - run: uv sync --locked
      - run: uv run ruff check . && uv run ruff format --check .
      - run: uv run mypy src

  unit:                               # minutes at most: every push
    needs: static
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false                # let every Python version report
      matrix: { python: ["3.12", "3.13"] }
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.2.0
        with: { enable-cache: true, python-version: "${{{ matrix.python }}" }
      - run: uv sync --locked
      - run: uv run pytest -m "not slow and not gpu" -n auto -p randomly --junitxml=unit.xml

  integration:                        # real PostgreSQL as a service container
    needs: unit
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17
        env: { POSTGRES_PASSWORD: test }
        ports: ["5432:5432"]
        options: >-
          --health-cmd pg_isready --health-interval 2s --health-timeout 5s --health-retries 20
    env:
      DATABASE_URL: postgresql://postgres:test@localhost:5432/postgres
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.2.0
        with: { enable-cache: true }
      - run: uv sync --locked
      - run: uv run pytest -m "integration" --junitxml=integration.xml

  gpu-nightly:                        # smoke training run and evals on a GPU runner
    if: github.event_name == 'schedule'
    runs-on: gpu-t4                   # the name you gave your GPU larger runner
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.2.0
        with: { enable-cache: true }
      - run: uv sync --locked
      - run: uv run pytest -m "gpu or slow"
Version pins, checked 2026-10-04
actions/checkout is at v7 (v7.0.1, 2026-07-20); many examples online still show v4. astral-sh/setup-uv stopped publishing floating major tags at v8.0.0 ("You won't be able to use @v8 or @v8.0 any longer", release notes), so @v10 does not resolve: pin a full release such as v10.2.0, or a commit SHA, which is the safer habit for every third-party action.

16. Very large changes and AI-written code: where tests are silent

A green suite says the behaviours someone thought to test still hold. It says nothing about the rest, and a big change travels straight through the rest. Nous Research's refactor of its Hermes agent codebase is a measured example: about nineteen active hours, 1,393 subagents (up to 218 at once) working on a repository of 1,063,826 non-test Python lines, cutting non-test source by 34.4% for about $19,300 in model costs for the main run (roughly $25k with follow-ups). Per-agent worktrees and a frozen baseline made the parallel edits integrable. Community review then caught public names that had been removed and a suppress() rewrite that changed exception handling at about 65 sites: "These were real regressions the existing tests had missed" (Nous Research, 2026).

What closes that gap:

  • Public-API diffing as a merge gate. List the exported surface (__all__, public classes, function signatures) before and after, and fail on any removal or signature change the change does not declare. Tests cover what someone called; the public surface is the promise.
  • Exception-contract tests. Assert the exception type and the condition that raises it (pytest.raises(RateLimited) on the 429 path), not only that an error happens. Broadened or swallowed exceptions are exactly the change a happy-path suite cannot see.
  • Frozen baselines. Compare behaviour against the pinned pre-change commit, not a moving main branch; run the old and new code on the same recorded inputs and diff the outputs.
  • Review by surface, not by file. Nobody reads a million-line diff. Spend human attention on the public interface, the error paths and the deleted code; mutation testing on the changed lines shows where the tests are silent.

The same rules apply to one AI-written pull request: read the tests first, and check they would fail if the code were wrong. Code design (section 13 and its Review lab) covers reviewing AI-written code.

Common mistakes

Testing the implementation instead of the behaviour
Asserting which internal functions were called, or the exact SQL string. Every refactor breaks the tests, so people stop refactoring. Assert outputs and visible effects (section 4).
Mocking everything
A suite of mocks restates the code and passes while production breaks. Use real objects, then fakes, and mocks only where the interaction is the behaviour (section 5).
SQLite in tests, PostgreSQL in production
Different engines read the same SQL differently: here a search was case-insensitive in tests and case-sensitive in production. A real PostgreSQL costs about a second per run (section 6).
Treating coverage as the goal
100% line and branch coverage killed only of mutants. Coverage finds untested code; it does not prove tested code is checked (section 14).
Rerunning until green
A flaky test hides real races in your code. Measure, quarantine with an owner, fix or delete (section 13).
Sleeping in tests
time.sleep(1) to "let the worker finish" is slow and flaky. Wait on the event, await the task, or inject a fake clock (section 9).
Exact float equality in ML tests
The same numbers summed in a different order give a different float32 result. Use assert_allclose with a tolerance chosen for the dtype (section 11).
Calling the real model in unit tests
Slow, costly, nondeterministic and needs a key in CI. Test the code with a fake server or a cassette; measure the model with evals (section 12).
Blindly updating snapshots
--snapshot-update turns a failing test into one that blesses the bug. Read the snapshot diff like code (section 8).
One slow CI job for everything
A 40-minute single job means people stop waiting for it. Split by cost, run the cheapest first, cache dependencies, cancel stale runs (section 15).
Fixing a bug without a test
Write the failing test first: it proves you reproduced the bug and stops it coming back.
