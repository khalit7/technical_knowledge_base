The idea in one screen

A test is worth the bug it would catch: for each behaviour, pick the cheapest deterministic check that fails when that behaviour breaks (a unit test, a generated property, a real database, a contract, a schema), run the cheap checks on every change, and judge the suite by what it notices (mutation score, flakiness), not by what it runs (coverage).

1. What a test buys, and what it cannot

An automated test writes down the check you would do by hand (run the code, try an input, look at the output) so a machine repeats it in milliseconds whenever anything changes. It buys three things. Confidence to change: the day you refactor, upgrade a library or swap a model provider, the suite tells you within a minute whether anything a caller relies on broke; without it every change is a gamble, so people stop changing things and the code rots. Documentation that cannot go stale: test_client_errors_are_not_retried[404] says what the retry policy promises and fails the moment it stops being true. Design pressure: code that is hard to test (it opens its own database connection, reads the clock, calls the model directly) is usually hard to change for the same reasons.

It cannot prove the code correct. Edsger Dijkstra, 1970: "Program testing can be used to show the presence of bugs, but never to show their absence!" (EWD249). (A machine-checked proof can show absence, for one stated property under stated assumptions: section 6.) Each kind of test is a different net; the craft is choosing nets that catch the bugs you are likely to have, at a cost you can afford to run on every change.

Checked: "a bug costs 100 times more in production" (the number is weaker than it sounds)

Its usual source is Boehm and Basili's 2001 "Software Defect Reduction Top 10 List" (IEEE Computer): "Finding and fixing a software problem after delivery is often 100 times more expensive than finding and fixing it during the requirements and design phase", which the same article qualifies: for small, noncritical systems the factor is "more like 5:1 than 100:1". It traces back to 1970s and 1980s data from large waterfall projects. Menzies, Nichols, Shull and Layman tested it on 171 modern projects and "found no evidence for the delayed issue effect" (arXiv 1609.04886, Empirical Software Engineering 2017); Laurent Bossavit traces how the figure spread in The Leprechauns of Software Engineering (chapter 10).

What does hold, without a multiplier: a bug caught by a test on your laptop costs you seconds and nobody else anything; the same bug in production costs an incident, a rollback, a postmortem and some users' trust (Reliability engineering). Argue for tests from that, not from the 100x.

2. Layers: what each catches, what it costs

Tests are grouped by how much of the system one test runs: a unit test runs one function or class in one process, no network or disk (milliseconds); an integration test runs your code with a real dependency such as a database, queue or another module (milliseconds to seconds); an end-to-end test drives the whole deployed system like a user (HTTP requests to the real API, a browser clicking the UI: seconds to minutes, and the flakiest); static checks (mypy, pyright, ruff) read the code without running it. Because "unit" and "integration" mean different things to different teams, Google sorts tests by the resources they use instead: "small tests run in a single process, medium tests run on a single machine, and large tests run wherever they want" (Software Engineering at Google, ch. 11). The PostgreSQL tests on this page are medium: one machine, a local server.

Pyramid and trophy agree on the top; they differ on how wide the middle is

Band widths are the shapes' proportions, not measurements. Click a band for what that layer catches, misses and costs on this page.

The test pyramid (Mike Cohn, Succeeding with Agile, 2009; Fowler's summary, 2012): many fast unit tests at the base, fewer integration tests, very few end-to-end tests. Google's testing blog suggested "a 70/20/10 split: 70% unit tests, 20% integration tests, and 10% end-to-end tests" as a first guess (Wacker, 2015). The testing trophy (Kent C. Dodds, 2018; his 2021 write-up) puts static checks at the base and makes integration the widest layer, after Guillermo Rauch's line "Write tests. Not too many. Mostly integration." (2016).

Which shape? Both want most of the checking done by fast, reliable tests and few slow end-to-end ones. The pyramid fits code with a lot of logic of its own (a retry policy, a tokenizer, a pricing engine); the trophy fits code that is mostly wiring between other systems (a web front end, a thin API over a database), where a unit test with everything mocked checks little. ML systems add a band on top, evals, which score a model or prompt on a set of cases against a threshold; they are statistical, slow and costly, so they run on merge or nightly (Production eval engineering owns them).

3. Unit tests that survive refactoring

The first piece of the chat product under test is the chunker: before a document can be searched by meaning (retrieval, the R in RAG), it is cut into overlapping windows of text, each embedded separately. The function and three ordinary pytest tests:

real experiments/hyp/chunking.py
def chunk(text: str, size: int, overlap: int) -> list[str]:
    """Split text into windows of `size` characters; neighbours share `overlap` characters."""
    if not 0 <= overlap < size:
        raise ValueError("need 0 <= overlap < size")
    step = size - overlap
    return [text[i:i + size] for i in range(0, len(text) - size + 1, step)]

def unchunk(chunks: list[str], overlap: int) -> str:
    """Inverse of chunk: glue the windows back, dropping each repeated overlap."""
    if not chunks:
        return ""
    return chunks[0] + "".join(c[overlap:] for c in chunks[1:])
real experiments/hyp/test_chunking_examples.py
from chunking import chunk, unchunk

def test_splits_into_overlapping_windows():
    assert chunk("abcdefghij", size=4, overlap=1) == ["abcd", "defg", "ghij"]

def test_no_overlap():
    assert chunk("abcdef", size=2, overlap=0) == ["ab", "cd", "ef"]

def test_round_trip():
    text = "the quick brown fox jumps over the lazy dog!!"   # 45 characters
    assert unchunk(chunk(text, size=10, overlap=5), overlap=5) == text
$ pytest -q test_chunking_examples.py ... [100%] 3 passed in 0.53s

All green, and the function has a bug: look at len(text) - size + 1. Any document shorter than one window produces no chunks at all, so it silently vanishes from the search index. The three examples happen to use lengths where the windows fit exactly. Section 6 finds it without being told where to look.

Test behaviour, not implementation

The most useful idea in test design: a test checks what the code promises (its outputs, its errors, its effects others can see), not how it does it. Google's testing book puts the goal as tests that are "unchanging": they only need to change when the requirements change (Software Engineering at Google, ch. 12). The figure is why: the two kinds of test answer two kinds of change in opposite ways.

How a good test reads:

  • Arrange, act, assert: build the inputs, call the code once, check the result. If a test needs three acts, it is three tests.
  • One reason to fail, and a name that says the behaviour: test_retry_preserves_idempotency_key, not test_retry_2. When it goes red in CI, the name is the bug report.
  • Tiny literal inputs written in the test itself, so the expected output can be checked by eye.
  • Write the failing test before fixing a bug. It proves you reproduced the bug and stops it coming back (a regression test). Every production incident should leave one behind; for model behaviour the equivalent is a new case in the golden set (Production eval engineering).
  • Design for testing: a function that takes its inputs as arguments and returns a value (a pure function) needs no setup at all. Anything that touches S3, a database or the clock goes behind an interface a test can replace. Code design (sections 7 and 5: functional core, dependency injection) shows the refactoring on a real handler.
pytest in one screen (runner, fixtures, parametrisation, errors, floats, markers, a starting config)

pytest is the standard test runner for Python. A test runner finds your tests, runs each one in isolation, and reports which passed. pytest's rules are short: files named test_*.py, functions named test_*, and a plain assert statement as the check. When an assert fails, pytest rewrites it to show both sides (assertion introspection), so you never need special assertEqual methods.

Fixtures. A fixture is a function that builds something a test needs (a database connection, a temporary folder, a fake server) and cleans it up afterwards. A test asks for it by naming it as an argument; pytest calls the fixture, passes in the value, and after the test runs the code after yield (fixtures docs). The scope says how often it is rebuilt: function (default, once per test), module, or session (once per run, for expensive things). Fixtures shared by many files live in a conftest.py, which pytest loads automatically. These are the real fixtures behind the PostgreSQL tests in section 5:

4. Test doubles: prefer real, then fake, then mock

Real dependencies (the model provider, a payment API, a database) can be slow, cost money, need network access or fail at random. A test double stands in for one during a test, the way a stunt double stands in for an actor. Gerard Meszaros named the kinds in xUnit Test Patterns (2007); Martin Fowler's Mocks Aren't Stubs (2004, revised 2007) is the classic explanation. A dummy fills a parameter and is never used (a logger=None); a stub returns canned answers (a model client whose complete() always returns "Hello"); a spy is a stub that also records how it was called; a mock is pre-programmed with expected calls and fails the test if they differ (unittest.mock, pytest-mock: client.complete.assert_called_once_with(...)); a fake is a small working implementation with shortcuts (an in-memory chat store, an HTTP handler that answers like a chat-completions API).

What a test proves depends on what stands behind the seam

The same chat-search handler tested three ways. Only the real engine catches the case-sensitivity bug in section 5; the fake catches it only if whoever wrote the fake knew PostgreSQL's rule; the mock catches nothing about results, because it checks that a call was made.

Prefer real, then fake, then mock. Google's testing book: "A real implementation should be preferred over a test double. A fake is often the ideal solution if a real implementation can't be used" (Software Engineering at Google, ch. 13), and mocks sparingly. A test made of mocks restates the implementation, so it passes when the code is wrong and fails when the code is refactored correctly. Code design's Review lab has a real example: a mock-only test that still passes with the function it claims to test broken.

Where a mock is the right tool

The interaction is the behaviour: "a payment is charged exactly once", "the alert is sent", "we never call the provider when the cache hits". Mock at the boundary you own (your PaymentGateway wrapper), not deep inside third-party libraries.

Where a mock lies

Mocking the database, then asserting the SQL string was passed. Mocking requests.post to return a dict that the real API never returns. Mocking a function in the same module you are testing. Each passes forever while production breaks.

Contract tests: keeping fakes honest

A fake drifts: the real service changes a field name and your fake does not. A contract test checks the agreement between two sides directly. In consumer-driven contract testing (Pact, "a code-first consumer-driven contract testing tool"; pact-python 3.4.1, 2026-09-17), each side tests alone, yet a breaking change is caught before deploy:

Cost and when not to: it needs a place to share pacts (the Pact Broker or PactFlow) and buy-in from both teams. For a third-party API you do not control (a model provider), the provider will never run your pacts; use recorded responses and schema checks instead (section 7), and an OpenAPI document as the contract when one exists (Service APIs, section 3).

5. Integration tests against the engine you ship

An integration test runs your code with a real dependency (the actual database engine, a real Redis, a real HTTP stack) and catches the bugs that live between components: SQL a different engine reads differently, a transaction that does not roll back, a type the driver converts. A common shortcut is SQLite in memory in tests while production runs PostgreSQL. What that shortcut cost, measured:

real experiments/integ/: the same test against SQLite and PostgreSQL 
def search_chats(conn, owner, text):
    """Chats of this owner whose title contains `text`, ignoring case (the product spec)."""
    rows = conn.execute(q(conn, "SELECT id FROM chats WHERE owner = ? AND title LIKE ? ORDER BY id"),
                        (owner, f"%{text}%")).fetchall()
    return [r[0] for r in rows]

@pytest.mark.parametrize("db", ["sqlite_conn", "pg_conn"])
def test_search_ignores_case(db, request):
    conn = request.getfixturevalue(db)
    seed(conn)   # "Trip planning for Lisbon", "trip budget spreadsheet" (ada); "Trip ideas" (bob)
    assert search_chats(conn, "ada", "trip") == [1, 2]
Same query, same rows, two engines: PostgreSQL misses the capitalised title

Measured on 2026-10-04 (median of 50 runs each, experiments/integ/test_timing.py): per test, create a table, 3 inserts, 1 search. pytest's verdict: FAILED test_search.py::test_search_ignores_case[pg_conn] - assert [2] == [1, 2].

SQLite's LIKE ignores case for ASCII letters by default (SQLite docs); PostgreSQL's LIKE is case-sensitive and offers ILIKE for the other behaviour (PostgreSQL docs). So the SQLite suite was green while production users searching "trip" never saw "Trip planning for Lisbon". The fix, lower(title) LIKE lower(?), passes on both; at scale you would add a trigram index (Topic: databases owns that depth).

The usual objection is speed: here a real PostgreSQL costs well under a second of startup per test run and a couple of milliseconds per test, so a suite of 500 such tests adds about a second. A little time for tests that use the engine you ship.

Keeping tests independent. Tests sharing a database leak state into each other. The cheapest isolation is a transaction rolled back after each test (the pg_conn fixture in section 3's pytest block). When the code under test commits on its own, truncate the tables after each test, or clone a prepared database per test with CREATE DATABASE t1 TEMPLATE base. With parallel workers (pytest-xdist), give each worker its own database. When not to: logic that does not touch the dependency (pricing rules, parsing, retry decisions) belongs in fast unit tests; integration tests are for the seams: queries, transactions, migrations, serialisation, configuration.

6. Property-based testing: let the computer pick the inputs

An example-based test checks the inputs you thought of; bugs live in the ones you did not (the empty string, the one-character document, the emoji, the negative number). A property is a statement that must hold for every valid input, such as "cutting a document into chunks and gluing them back gives the document". A property-based test states the property, and a library generates hundreds of inputs trying to break it. The idea comes from Haskell's QuickCheck (Claessen and Hughes, 2000); in Python the library is Hypothesis.

real experiments/hyp/test_chunking_property.py
from hypothesis import given, strategies as st
from chunking import chunk, unchunk

@st.composite
def chunk_args(draw):                       # a custom strategy: valid (size, overlap) pairs
    size = draw(st.integers(min_value=1, max_value=50))
    overlap = draw(st.integers(min_value=0, max_value=size - 1))
    return size, overlap

@given(text=st.text(), args=chunk_args())
def test_round_trip_loses_nothing(text, args):
    size, overlap = args
    assert unchunk(chunk(text, size, overlap), overlap) == text

A strategy describes how to generate one kind of value (st.text(), st.integers(1, 50), your own with @st.composite). Shrinking is what happens after a failure: Hypothesis keeps trying simpler versions of the failing input (shorter strings, smaller numbers, simpler characters) and keeps any that still fail, so the report is text='0', size=2, overlap=0 instead of a random 30-character unicode string. Across runs. Hypothesis is random, so the search differs from run to run. Over fixed seeds it found the bug in every run, always within the first generated inputs, because most random documents trip it. Shrinking ended at the true minimum ('0', size 2, overlap 0) in of runs; the others stopped at slightly larger inputs such as '0000' with size 3, which are just as readable. Shrinking is a local search: it guarantees that no simpler variant it tried still fails, not that no smaller failing input exists.

The fix starts a window wherever there is text the previous window did not cover: range(0, max(len(text) - overlap, 1), step), plus an early return for empty text. The same property then passed 5,000 generated cases (experiments/hyp/test_fixed_property.py, 2.3 s). It also cures a second symptom the examples never hit: the tail of any document whose length does not line up with the step, such as the last character of "abcde" with size 4 and overlap 1.

Determinism in CI. Hypothesis saves each failing input in a local example database (.hypothesis/examples) and replays it first next time. A CI machine starts with that folder empty, so Hypothesis now defaults to derandomize=True on CI ("If running on CI, the default is True"): every CI run tries the same inputs, so a red build reproduces, and new inputs are explored on developers' machines (or keep randomness in CI and cache the database between runs). Pin a found bug as a permanent regression case with @example(text="0", args=(2, 0)) above @given.

Stateful testing: random sequences of operations

Some bugs need a particular sequence of calls. A stateful test lists the operations (rules), and Hypothesis runs random sequences of them against your code and a simple trusted model, comparing after each step. Here it tests the least-recently-used cache that holds embeddings by text hash: it should keep the two most recently used keys, but get forgets to mark a key as used. Hypothesis shrank random sequences to this five-step recipe:

The stateful test's code (a RuleBasedStateMachine against an OrderedDict model)
real experiments/hyp/test_lru_stateful.py
class LRUMatchesModel(RuleBasedStateMachine):
    def __init__(self):
        super().__init__()
        self.cache = LRUCache(capacity=2)
        self.model = OrderedDict()            # the obviously-correct reference

    @rule(k=keys, v=st.integers())
    def put(self, k, v):
        self.cache.put(k, v)
        self.model[k] = v
        self.model.move_to_end(k)
        if len(self.model) > 2:
            self.model.popitem(last=False)

    @rule(k=keys)
    def get(self, k):
        expected = self.model.get(k)
        if k in self.model:
            self.model.move_to_end(k)
        assert self.cache.get(k) == expected

Properties that pay off, especially in ML code

  • Round trip: decode(encode(x)) == x; config to YAML and back; a tokenizer where it promises it.
  • Invariants: shape and dtype preserved; row count preserved (or changed by exactly the filtered rows); no NaN introduced; output vocabulary within the expected set; probabilities sum to 1.
  • Idempotence: normalising twice equals normalising once, f(f(x)) == f(x).
  • Equivalence to a slow reference: the vectorised implementation equals a plain loop on every input (a test oracle).
  • Monotonicity: a higher score never ranks lower.
  • Never crashes: a parser for model output returns a value or raises your own error type, for any string.

What it costs, and when not to use it. Each property runs 100 examples by default, so it is slower than one example (seconds, not milliseconds). Thinking of a true property is the hard part; a property that restates the implementation proves nothing, and a strategy narrower than real inputs gives false confidence. Keep a few readable example tests as documentation, and add properties where the input space is large: parsers, serialisers, numeric transforms, data structures, anything with an inverse.

Checked: the old page's NumPy example, run as written (it fails, twice)

The old page's example property, @given(hnp.arrays(dtype=np.float32, shape=st.integers(1, 1000))) asserting that min-max normalisation produces no NaN, fails at once. Two reasons. First, by default the float strategy also generates NaN and infinity, so the test partly checks its own inputs; restrict them with elements=st.floats(-1e6, 1e6, width=32). Second, with finite inputs it still fails, and Hypothesis shrinks to x = array([0.]): a constant column makes max - min zero, and 0/0 is NaN. A real bug in every naive min-max scaler, found in under a second (experiments/mlt/test_normalize.py).

hypothesis.extra.numpy and hypothesis.extra.pandas generate arrays and data frames directly. Build domain objects with st.builds or @st.composite and reuse them across tests as a library of typed inputs.

Above sampling: fuzzing, then proof

A fuzz test is the "never crashes" property run for hours instead of 100 examples, with inputs mutated towards new code paths by coverage feedback; Google's OSS-Fuzz runs such entry points continuously for open-source libraries. However long it runs, it still samples. The rung above proves the property for every input: in October 2026 Anthropic's Frontier Red Team and Theorem had Claude write machine-checked Rocq proofs that 239 OSS-Fuzz entry points across 123 libraries never crash, fail an assertion or hit a memory-safety error for any input under 64 MB (Anthropic, Formal verification at scale). The existing fuzz test became the specification ("this test always passes"), the library and the test were compiled to a RISC-V binary, and the proof is about those instructions, not the source; about 180 million lines of Rocq in all, and the effort found and patched hundreds of bugs, among them a counter underflow that needed a roughly 20 MB input, the kind sampling rarely reaches.

What the proof does not cover is as important. It assumes a single-threaded static binary linked against musl, a fixed memory budget and a modelled Linux process, while most deployments run x86 or ARM with glibc and threads; it trusts the RISC-V and OS models, the theorem statements and the proof checker; and it says nothing a fuzz test does not ask, such as wrong output. The authors put it plainly: "'Formally verified' does not mean 'bug-free.'" One failure mode is specific to a model doing the proving: Claude "could make any theorem provable by rewriting the program into one that trivially never crashes", so patches were penalised, logged and audited (the same patch-to-pass shortcut as on Reward Hacking). For your own code the order stays: examples, then properties, then fuzzing for parsers and decoders that take untrusted bytes; proof is now within reach where a crash is a security bug.

7. Testing code that calls an LLM

An LLM feature is ordinary code wrapped around a call whose answer varies. Split it accordingly: the code around the call (building the prompt, parsing the answer, retrying, falling back) is tested like any code, fast and exactly, with the model replaced; the model's quality is measured by evals. Mixing the two gives slow, flaky, expensive unit tests that still do not tell you whether the model is good.

One LLM feature, four checks: three exact tests on our code, one eval on the model

The highlighted box is the seam: the HTTP client is passed in, so a test can put a fake server or a recorded cassette behind it without editing the code. Everything left and right of it is our code and gets exact tests on every push; only the model's quality needs a statistical eval.

Deterministic seams. Make every source of variation something the caller passes in: the HTTP or SDK client (so a test supplies a fake), the clock as a function (so a test advances it instantly instead of sleeping), the random generator seeded (section 9's jitter fix). With all three injected, a test of the code around the model is as deterministic as a test of a pure function.

Contract tests on structured output

When model output feeds other code, the boundary needs a contract: a schema the output must satisfy, checked on every response. In Python that is a pydantic model. Structured-output modes (JSON mode, JSON schema, tool calling) and constrained decoding make valid output much more likely; validate anyway. Put semantic rules in the schema too: enum fields really in the enum, numbers within bounds, ids that resolve, citation indices in range.

real experiments/llm/extract.py with pydantic , httpx 
class Ticket(BaseModel):
    category: Literal["billing", "bug", "account", "other"]
    priority: int = Field(ge=1, le=4)
    summary: str = Field(min_length=1, max_length=200)

def extract_ticket(client: httpx.Client, message: str, retries: int = 1) -> Ticket:
    prompt = f"Return JSON with category, priority (1-4) and summary for: {message}"
    for attempt in range(retries + 1):
        r = client.post("/v1/chat/completions", json={
            "model": "small", "temperature": 0,
            "response_format": {"type": "json_object"},
            "messages": [{"role": "user", "content": prompt}]})
        r.raise_for_status()
        text = r.json()["choices"][0]["message"]["content"]
        try:
            return Ticket.model_validate_json(text)
        except ValidationError as e:              # repair: one retry with the error appended
            prompt += f"\nYour last answer was invalid: {e.errors()[0]['msg']}. Return valid JSON only."
    raise ValueError("model output failed validation after retries")

The repair loop retries once with the validation error in the prompt, then gives up and lets the caller fall back. Count how often it fires: a rising repair rate is an early signal that a model or prompt change has regressed.

Record and replay (VCR)

A fake returns what you think the provider returns. A recorded response test captures what it really returned once: vcrpy intercepts HTTP, saves request and response to a YAML cassette, and replays it on later runs without a network; pytest-recording wraps it as a marker. Here the "provider" is a local server so the run is self-contained; with a real provider the steps are the same.

Costs: cassettes go stale when the provider changes its API, so re-record on a schedule and when upgrading the SDK; they can capture secrets and user data, so filter headers and use synthetic inputs; and a cassette replays one sample of a nondeterministic model, so assert on structure, not on exact wording. Record modes decide what happens on a miss: once (vcrpy's default) records if the cassette does not exist and replays otherwise; none never touches the network, which pytest-recording uses by default "to prevent unintentional network requests"; new_episodes and all record more.

Snapshot hygiene (scrubbing, size, inline snapshots)

Treat a snapshot diff as a code change and read it in review. Scrub values that change on every run (timestamps, generated ids) or the test is flaky. Snapshot a small, meaningful view, not huge outputs nobody will read. inline-snapshot writes the value into the test file itself, which keeps small snapshots next to the code that checks them.

When an eval replaces a test

A unit test asks "is this exactly right?" and expects yes every time. For model quality ("are tickets categorised correctly?") the honest answer is a rate ("on 94% of cases", say), so the check is an eval: a versioned set of cases, scored, compared with the current production configuration, with a threshold and per-slice results (Production eval engineering, Eval harnesses). The split: tests (exact, every push, fake model) for prompt assembly, output parsing, schema validation, repair and fallback logic, retries, streaming, token counting, cost accounting and the gateway's routing rules; evals (statistical, on merge or nightly, real model) for answer quality, categorisation accuracy, refusal behaviour, tone and groundedness, run on every model, prompt, temperature or provider change. A few deterministic assertions sit in between and can run on real model output in the eval job: the output parses, the tool call is valid, no forbidden string appears. Treat prompts as code: versioned, reviewed, and every edit runs the eval. Runtime checks on live traffic are Guardrails.

8. Testing data and ML code

An ML system has three things to test, and they behave differently:

Code is checked exactly, data against a schema, the model statistically

Most "ML testing" failures come from testing only the code. Eugene Yan's How to Test Machine Learning Code and Systems (2020) splits model tests into pre-train tests (shapes, the loss goes down, no label leakage) and post-train tests ("Post-train tests check if the learned logic is expected"); Google's ML Test Score (Breck et al., 2017) lists "28 specific tests and monitoring needs" across data, model development, infrastructure and monitoring, still the best checklist for production readiness.

Transforms are ordinary code: test them like it

The code between raw data and model input (cleaning, joining, feature computation, tokenisation, prompt assembly) is where most ML bugs live, and it is plain deterministic code. Use tiny literal fixtures (a few rows built inline, golden files for bigger cases); invariants, not only examples (row count preserved or changed by exactly the filtered rows, no NaN introduced, dtypes stable, keys unique, output values in the expected set); and the edge inputs production will send (an empty frame, one row, an all-null column, unicode, maximum-length strings, duplicate keys). Tokenisation and prompt assembly are transforms too: assert round trips where the tokenizer promises them, render templates with empty, huge and injection-shaped fields, and assert exact token counts on cost-critical paths.

Seeds and tolerances: deterministic enough to test

ML code is full of randomness (shuffles, initialisation, dropout, sampling). Pass a seeded generator in (rng = np.random.default_rng(0)) rather than using global state, and set seeds for random, NumPy and PyTorch in a fixture. Even then, exact equality on floats is the wrong check:

The same million float32 numbers, summed forwards and backwards, give different answers, because floating-point addition is not associative. Parallel hardware sums in whatever order its threads finish, so GPU results can change between runs and versions: PyTorch states that "completely reproducible results are not guaranteed across PyTorch releases, individual commits, or different platforms", and offers torch.use_deterministic_algorithms(True) at some speed cost (PyTorch reproducibility notes). So numeric tests assert with a tolerance chosen for the precision: np.testing.assert_allclose(got, want, rtol=1e-5) for float32, looser for bf16, and never ==.

Model behaviour: where tests end and evals begin

9. Flaky tests

A flaky test passes and fails on the same code. It is worse than no test: every red build might be noise, so people learn to press "rerun" until it is green, and then a real failure gets rerun away too. At Google's scale, "about 1.5% of all test runs" reported a flaky result and "almost 16% of our tests have some level of flakiness" (Micco, Google Testing Blog, 2016).

Almost half of fixed flaky tests waited on something asynchronously

Luo, Hariri, Eloussi and Marinov studied 201 fixes of flaky tests in 51 open-source projects and classified 161 (FSE 2014). Async wait: the test sleeps or polls instead of waiting for the thing it needs. Test order dependency: one test relies on state another leaves behind. "Other" is derived (161 - 74 - 32 - 19 = 36, several smaller categories). In ML code add unseeded randomness, real network calls and exact asserts on floats.

Two of these, built and measured:

The top cause: waiting on async code

A chat backend is mostly async code: functions declared async def that pause at await while waiting on the network, so one process can serve many requests at once. pytest itself cannot run an async def test; a plugin such as pytest-asyncio (or AnyIO's pytest plugin) runs it in an event loop. The rules that keep async tests deterministic:

  • Do not sleep to wait for something. await asyncio.sleep(0.1) "so the background task finishes" is the classic flaky test. Await the task, or wait on an event the code sets.
  • Timeouts belong in async tests: a hung await hangs CI forever. Give every network wait a timeout in the code, and test it with a delay far beyond the timeout (10 s against 0.05 s below) so the test is not flaky.
  • Time-dependent logic (rate limiters, cache expiry, retries with backoff): pass the clock in as a function, and give the test a fake clock it can advance instantly, instead of sleeping for real.
  • Test web endpoints in-process: FastAPI's TestClient or httpx.AsyncClient with an ASGI transport calls your app without a network; Building a backend API has the service.

Find, measure, quarantine

Find them on purpose. pytest-randomly shuffles test order on every run and resets random.seed, printing the seed so a failing order can be replayed with -p randomly --randomly-seed=N; run it in CI and order dependencies surface in days instead of months. pytest-xdist (-n auto) runs tests in parallel processes, which finds shared files and ports. pytest-repeat's --count reruns a suspect test hundreds of times, as above.

Measure them. A test's flakiness is the share of runs on the same commit where it failed and then passed on retry. CI systems that keep test history (Buildkite Test Engine, Datadog, Trunk, or a script over JUnit XML reports) can compute it per test and rank the worst.

Quarantine, then fix or delete. Google built "a tool that monitors the flakiness of tests and if the flakiness is too high, it automatically quarantines the test. Quarantining removes the test from the critical path and files a bug for developers to reduce the flakiness" (same post). By hand: move it out of the blocking job, give the bug an owner and a deadline, then fix it or delete it. Automatic retry (pytest-rerunfailures, --reruns 2) keeps the build green but hides real intermittent bugs (a race in your code looks exactly like a flaky test) and slows the suite; if you use it, record every rerun and review the list. Never let "rerun until green" become the culture.

10. Coverage and mutation testing: is the suite any good?

Code coverage measures which code ran during the tests: line coverage counts executed lines; branch coverage also checks that every if went both ways. coverage.py measures both (coverage run --branch -m pytest, then coverage report -m lists the lines that never ran). That list is valuable: code no test executes is certainly untested. The reverse does not hold: coverage records that a line ran, not that any test checked what it did.

Mutation testing asks the better question: if the code had a bug, would a test fail? A tool makes many small changes to the code, one at a time (each change is a mutant: >= becomes >, 2 becomes 3, - 1 becomes + 1), and runs the tests against each. A mutant is killed if some test fails and survives if every test still passes: a bug your suite would not notice. The mutation score is the share killed.

A gap measured here: what mutmut 3 does not mutate
mutmut 3 only mutates code inside functions; its README says to use mutmut 2 "if you want to mutate code outside of functions". The module-level RETRYABLE = frozenset({408, 429, 500, 502, 503, 504}) produced no mutants at all, so mutmut could not tell you that the weak suite never checks which statuses are retryable. The improved suite covers it by naming every status explicitly. Keep important constants inside functions or test them directly.

What the research and practice say

  • Inozemtseva and Holmes measured 31,000 test suites over five Java systems and found "a low to moderate correlation between coverage and effectiveness when the number of test cases in the suite is controlled for", effectiveness being mutants killed (ICSE 2014). Coverage is a floor detector, not a goal.
  • Google's guidance treats "60% as 'acceptable', 75% as 'commendable' and 90% as 'exemplary'", while adding "There is no 'ideal code coverage number' that universally applies to all products" and "We should not be obsessing on how to get from 90% code coverage to 95%" (Google Testing Blog, 2020).
  • Google runs mutation testing incrementally, "mutating only changed code during code review", showing at most one mutant per line as a review comment; "82% of all surfaced mutants with feedback were labeled as productive by developers" (Petrović et al., 2021). Developers exposed to it "write more tests, and actively improve their test suites" (Petrović et al., ICSE 2021).

What it costs. One run of the suite per mutant: here mutants at mutants per second, under a second, but a large service has tens of thousands of mutants and a suite that takes minutes. So run it on changed code only (as Google does), nightly, or on the modules that matter most (pricing, permissions, retries). Some mutants are equivalent: they change the code but not its behaviour, cannot be killed, and need a human to dismiss them. Skip it for glue code and prototypes; use it where a silent wrong value is expensive.

11. CI: fast feedback, cheapest checks first

Continuous integration (CI) runs the checks automatically on every push and pull request, on a clean machine, and blocks the merge if any fail. It turns "the tests pass on my laptop" into "the tests pass, from scratch, for everyone". The design problem is time: developers wait for CI, so the order and split of the checks matter as much as the checks.

A change meets the cheapest checks first; the slow tiers run on merge or at night

The job graph of the workflow below (written for this page on 2026-10-04 and parsed as valid YAML, not run on GitHub). Each job runs only if the one before it passed (needs:); a new push to the same branch cancels the older run. The durations are the order of magnitude each tier should aim for, not measurements.

  • Cheapest first, fail fast. Lint and type checks take seconds and catch a large share of mistakes; run them first and stop there if they fail. Then unit tests (aim for a few minutes), then integration tests, then the slow tiers.
  • Tiers by cost. Unit on every push; integration with real services and fakes on every pull request; GPU, full-model and eval tiers on the merge queue or nightly. Mark tests (@pytest.mark.slow, gpu, integration) so laptops and CI select with -m.
  • Cache dependencies. Resolving and downloading packages can take longer than the tests; uv with its cache restores an environment in seconds.
  • Cancel stale runs. A new push to the same branch makes the previous run worthless; concurrency with cancel-in-progress: true cancels it (workflow syntax).
  • Parallelise with pytest -n auto (pytest-xdist) inside a job, and a matrix across Python versions; set fail-fast: false on a matrix when you want every version to report rather than stop at the first failure.
  • Same checks locally. pre-commit hooks run ruff (and optionally the fast tests) before each commit, so CI is rarely the first to find a lint error.

GPU tests in CI

Some code paths (CUDA kernels, mixed precision, a serving engine) only run on a GPU. Whatever runs on GPUs: cache model weights on the runner, use the smallest model that exercises the code, assert numeric results with tolerances (section 8), and keep full-size evals in the nightly tier.

12. Static analysis, types and review: the checks that are not tests

Static analysis (ruff for lint, mypy or pyright for types) reads the code and catches whole classes of bugs before anything runs: type errors (passing a str where an int is expected), misspelled names, unused imports, unreachable code, a missing await. It misses anything about values at run time: a wrong formula type-checks fine. It costs seconds for a whole repository, which is why it is the first CI job and a pre-commit hook in the figure above.

Code review is the human check: a second engineer reads the change before it merges. As a quality practice it covers what no automated check can: whether the tests would fail if the code were wrong (read the tests first), whether the public surface and the error paths changed on purpose, and whether the change was needed at all. Google's mutants as review comments (section 10) make the first question visible to the reviewer.

How to write types (hints, checkers, dataclasses against pydantic, protocols) and how to give and take a review are Code design's (types and checkers in its closed "Depth: types and tooling" block, review as a craft in section 13), with its measured checker runs; this page places them in the pipeline.

13. Very large and AI-written changes: where tests are silent

A green suite says the behaviours someone thought to test still hold. It says nothing about the rest, and a big change travels straight through the rest. Nous Research's refactor of its Hermes agent codebase is a measured example: about nineteen active hours, 1,393 subagents (up to 218 at once) working on a repository of 1,063,826 non-test Python lines, cutting non-test source by 34.4% for about $19,300 in model costs for the main run (roughly $25k with follow-ups). Per-agent worktrees and a frozen baseline made the parallel edits integrable. Community review then caught public names that had been removed and a suppress() rewrite that changed exception handling at about 65 sites: "These were real regressions the existing tests had missed" (Nous Research, 2026). What closes that gap:

  • Public-API diffing as a merge gate. List the exported surface (__all__, public classes, function signatures) before and after, and fail on any removal or signature change the change does not declare. Tests cover what someone called; the public surface is the promise.
  • Exception-contract tests. Assert the exception type and the condition that raises it (pytest.raises(RateLimited) on the 429 path), not only that an error happens. Broadened or swallowed exceptions are exactly the change a happy-path suite cannot see.
  • Frozen baselines. Compare behaviour against the pinned pre-change commit, not a moving main branch; run the old and new code on the same recorded inputs and diff the outputs.
  • Review by surface, not by file. Nobody reads a million-line diff. Spend human attention on the public interface, the error paths and the deleted code; mutation testing on the changed lines shows where the tests are silent.

The same rules apply to one AI-written pull request: read the tests first, and check they would fail if the code were wrong. Code design (section 13 and its Review lab) covers reviewing AI-written code.
