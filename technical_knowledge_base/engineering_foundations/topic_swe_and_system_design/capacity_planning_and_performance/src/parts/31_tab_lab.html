Load-test lab

A simulated load test you can run a hundred times a minute. Requests arrive at random (an open workload, as real users do) at the utilisation you choose; a balancer sends each one to one of several servers, each serving one request at a time, first come first served. For every policy the lab sweeps the load from 10% to 98% and draws the p50 or p99 latency, so you see where each one's knee is. Every policy gets identical arrivals and identical work per request; only the choice of server differs. The code is the same as the Reading's animation (src/model.py and parts/21_js_model.js, checked against each other).

Try: start with "Measured setup" and compare the dots (Experiment 3, eight real server processes) with the curves. Then "One slow server": random and round robin go vertical early, two choices barely moves. Then "Heavy-tailed requests": every curve rises (Kingman's variability term), and the gap between policies widens. Then 32 servers: one shared queue and least outstanding can run far hotter.

How the lab works, and how it was checked

  • Model. Poisson arrivals at rate ρ × total capacity; each server serves one request at a time in arrival order; a request's latency is its wait plus its own service time. Policies: random; round robin; power of two choices (two distinct servers at random, the one with fewer requests in it, ties to the first drawn); least outstanding (fewest in it, ties to the lowest number); one shared queue (each request goes to whichever server frees up first: exactly M/M/c when service is exponential). The first 10% of each run is dropped as warm-up.
  • Checked against theory. With exponential service, random assignment makes every server an M/M/1 queue, so its p99 should be ln(100) / (1 − ρ) service times; one shared queue should match M/M/c's exact distribution (Erlang C). Tick "Theory lines" to see both. At 90% with 8 servers, the default run gives a random p99 of 40.4 against 46.1 in theory, and shared 7.6 against 7.1 (src/recompute_out.json); the gap is sampling noise of 18,000 requests, which the 60,000 option narrows.
  • Checked against measurement. The dots are Experiment 3 on the Reading tab: eight real server processes and a client-side balancer, at the real utilisations of 75% and 96%, latencies divided by the measured service time (21.6 ms) and multiplied by the one you set. They show when the settings match the experiment (8 servers, exponential, no slow server; or the slow-server run at 75%).
  • Same code in two languages. src/model.py and parts/21_js_model.js are line-for-line twins; src/check_model.mjs runs both on 110 cases (1,525 numbers) and finds no difference above 1.2 × 10−15.
  • Not modelled: network time, servers with several worker slots, retries and timeouts (the {{Resilience lab|n:3ef5c17b0d0d8152b8dececf34196174}} on Reliability engineering has those), stale load information at the balancer.
