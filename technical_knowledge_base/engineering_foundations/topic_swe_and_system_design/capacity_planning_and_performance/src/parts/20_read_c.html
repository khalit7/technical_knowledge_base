Load balancing

A load balancer (the root's Step 1) sits in front of a pool of identical servers and picks one for each piece of work. Queueing just showed why the choice matters: random assignment turns 8 servers into 8 separate queues, while a policy that sends work to an idle server approaches one shared queue, with a p99 several times lower at the same cost.

Layer 4 and layer 7

A layer 4 (L4) balancer sees TCP connections and copies bytes without reading the HTTP inside (AWS Network Load Balancer, Linux IPVS, Google's Maglev); a layer 7 (L7) balancer terminates HTTP, so it can balance per request, route by path, retry and count requests in flight per server (nginx, Envoy, HAProxy, AWS Application Load Balancer). The difference bites with HTTP/2 and gRPC, which send many requests over one long-lived connection: an L4 balancer that spread connections evenly can still leave one server with the busiest client. So: an L4 or cloud balancer at the edge, L7 or client-side balancing (the client, or a sidecar such as Envoy, picks per call) inside ({{gRPC blog, 2017|https://grpc.io/blog/grpc-load-balancing/}}: "The application data (HTTP/2 and gRPC frames) are simply copied between the client connection to the backend connection").

Power of two choices: Mitzenmacher's "supermarket model", where "each customer chooses some constant d servers independently and uniformly at random ... and waits for service at the one with the fewest customers", found that "having d = 2 choices leads to exponential improvements in the expected time a customer spends in the system over d = 1, whereas having d = 3 choices is only a constant factor better than d = 2" ({{IEEE TPDS 12(10), 2001|https://www.eecs.harvard.edu/~michaelm/postscripts/tpds2001.pdf}}). His many-server limit gives the mean time in the system, in service times, as the sum over i ≥ 1 of λ(di − d)/(d − 1): at 90% load, random 10, two choices 2.61, three choices 2.03; at 99%, 100 against 5.4. The second sample removes most of the damage, which is why Envoy ({{"Defaults to 2 so that we perform two-choice selection"|https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/cluster/v3/cluster.proto}}) and HAProxy ({{"The default value is 2"|https://docs.haproxy.org/3.2/configuration.html#4.2-balance}}) both sample two.

Mitzenmacher's limit as n grows (exponential service), computed in src/recompute.py; his paper reports simulations within a few percent of it for 100 queues up to 95% load. The animation and lab use 8 servers, where two choices helps a little less.

How Experiment 3 was run (provenance)
Experiment 3: eight server processes, one client-side balancer

Eight copies of Experiment 1's server (one request at a time each, exponential service with a nominal mean of 20 ms), each a separate process; one open-loop client sends Poisson traffic and picks a server per request with each policy, counting its own requests in flight per server (exactly what a client-side balancer or a sidecar does). 40 seconds per run at 70% and 90% of nominal capacity, then 30 seconds at 70% with server 0 three times slower. Same arrival seed for every policy.

The runs meant for 70% and 90% ran at 75% and 96% (real service time 21.5 ms, not 20). With server 0 three times slower, random and round robin kept sending it 1/8 of the traffic, more than it could serve; two choices and least outstanding sent it 5.9% and 6.0%.

Affinity: consistent hashing

Sometimes the same key must keep reaching the same server: a per-server cache, a chat whose KV cache is warm on one GPU replica, or Discord's channels, where one instance per channel is what makes coalescing work (root {{Case files|n:3c65c17b0d0d81048ae0dd14ac399b4d}}: "Trillions of messages: hot partitions, request coalescing, a new database"). Server = hash(key) mod N moves almost every key when N changes (nginx: "adding or removing a server from the group may result in remapping most of the keys to different servers", {{upstream module|https://nginx.org/en/docs/http/ngx_http_upstream_module.html#hash}}). Consistent hashing places servers and keys on a circle and sends each key to the next server clockwise, so adding a server moves only about 1/N of the keys. Its cost is hot keys: bounded loads refuses a server already above a set multiple of the average and moves on round the ring. Do not use affinity for stateless requests: it throws away the balancing you just paid for.

Ring hash and Maglev, bounded loads, health checks, draining, slow start, and real configs (depth)

nginx's hash ... consistent (ketama): "only a few keys will be remapped". Envoy offers a ring hash and Maglev, which "uses the algorithm described in section 3.4 of [the Maglev paper] with a fixed table size of 65537" and looks up faster ({{Envoy load balancers|https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/load_balancing/load_balancers}}). HAProxy's hash-balance-factor: "if <factor> is 150, then no server will be allowed to have a load more than 1.5 times the average ... Reasonable values are from 125 to 200" ({{HAProxy 3.2 manual|https://docs.haproxy.org/3.2/configuration.html#4.2-hash-balance-factor}}).

  • Active health checks: the balancer probes each server (an HTTP GET every few seconds) and removes it after several failures. Open-source nginx lacks them ("periodic health checks is available as part of our commercial subscription"); it only counts real failures (max_fails, default 1, within fail_timeout, default 10 seconds). What a health endpoint should check is on {{Reliability engineering, Health checks done right|n:3ef5c17b0d0d8152b8dececf34196174}}.
  • Outlier detection (passive): Envoy's defaults eject after 5 consecutive 5xx responses, checked every 10 s, for a base 30 s, never more than 10% of the pool at once ({{Envoy outlier detection|https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/cluster/v3/outlier_detection.proto}}). The 10% cap matters: a balancer that ejects every server has built an outage.
  • Connection draining: stop sending new requests to a server being removed, let the ones in flight finish. AWS ALB waits 300 seconds by default ("deregistration delay"): "If a deregistering target terminates the connection before the deregistration delay elapses, the client receives a 500-level error response" ({{AWS ALB target group attributes|https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-target-group-attributes.html}}). Kubernetes gives a deleted pod a 30-second grace period by default ({{pod lifecycle|https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/}}); keep serving after SIGTERM until the balancer has stopped sending.
  • Slow start: a new server with a cold cache gets a ramp. HAProxy's slowstart grows its weight "linearly from 0 to 100%"; ALB's slow start does the same, but "You can't enable slow start mode when using the least outstanding requests or weighted random routing algorithms".

When not to bother: two servers behind a managed balancer with similar, fast requests are fine on round robin. The policy matters once requests vary in cost (an LLM call against a cache hit), servers vary (one is garbage-collecting), or you run hot. For LLM servers the right signal is tokens or KV-cache memory in use, not requests in flight: {{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}} measures that on real replicas.
