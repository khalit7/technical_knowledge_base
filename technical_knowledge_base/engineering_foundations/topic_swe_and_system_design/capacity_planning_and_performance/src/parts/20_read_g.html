Common mistakes

Reporting the average latency
It hides the tail that users feel and cannot be combined across servers. Report p50, p99 and p99.9 from merged histograms.
Planning to run at 90% to "use what we pay for"
At 90% a single queue's wait is 9 service times and the p99 is 46; one failure or a 10% burst pushes it past 100%. Experiment 1's runs aimed at 90% actually ran at 101% because the real service time was 12% longer than assumed.
Load testing closed-loop and quoting the p99
The tool stops sending when the server stalls, so the stall is missing from the data: Experiment 2's closed-loop p99 was 89 ms against 1,400 ms for the same server measured open-loop. Use arrival-rate executors and measure from the scheduled time.
Load testing one URL with one key
100% cache hits measures the cache. Use production's key spread and endpoint mix.
Random or round-robin balancing in front of uneven work
Both keep sending a slow server its full share. In Experiment 3, with one server three times slower, random and round robin had p99s of 28 seconds (the slow server's queue grew all run); two choices kept the p99 at 280 ms.
Treating the cache as optional when the database is sized for the misses
A cold cache sends ten times the reads to a database sized for 10% of them. Warm caches before traffic, keep spare cache capacity (Facebook's Gutter), and protect hot keys from stampedes.
Updating the cache on write instead of deleting it
Concurrent writers can leave the older value cached for the full TTL. Delete after the database commit; keep a TTL as the backstop.
Every process opening its own big pool
Pools multiply across processes and servers; the database's 100 connections run out. Size from the database's side; add PgBouncer.
Holding a database connection across a model call
The hold time becomes seconds and Little's law asks for thousands of connections. Release before calling out.
Adding threads to speed up CPU-bound Python
Under the GIL four threads took as long as running the jobs one after another (Experiment 4). Use processes, native code, or the free-threaded build with its dependencies checked.
Profiling only the CPU
A request waiting 400 ms on the network shows nothing in a CPU flame graph. Use wall-clock profiling or tracing for waits.
Sizing for the daily average, or for a per-hour peak when per-second bursts matter
Size for the busy hour with headroom for bursts; plan known events separately. Real peak factors range from 1.2 (global Wikipedia, hourly) to 25 (Twitter, per second).

Glossary

Cache: a faster copy of an answer; hit rate is the share of reads it serves.
Capacity planning: forecast, peak factor, headroom and spares turned into hardware and dates.
CDN: a cache run in many cities near users.
Closed workload: a fixed set of users, each waiting for an answer before sending again.
Coordinated omission: a load tester missing the requests it failed to send during a stall.
Coalescing: many identical requests in flight served by one backend call.
Consistent hashing: key-to-server mapping that moves about 1/N of keys when a server changes.
Connection and pool: an open, logged-in channel to a database; a set kept open and lent out.
Coefficient of variation: standard deviation divided by mean; 0 constant, 1 exponential.
Flame graph: sampled call stacks; width is time share, not a timeline.
GIL: CPython's lock letting one thread run Python code at a time.
Hedged request: a backup copy sent after a delay; the first answer wins.
Hit rate: share of reads answered by the cache; backend load is (1 − h) × reads.
Knee: where latency starts to rise steeply with load.
L4 / L7 balancer: picks per connection without reading HTTP / reads each HTTP request.
Latency: time for one request, sent to answered.
Load balancer: picks a server for each piece of work.
Load test: synthetic traffic to learn behaviour under load.
M/M/1, M/M/c: random arrivals, random (exponential) service, 1 or c servers sharing one queue.
Open workload: requests arrive at a rate regardless of answers.
Power of two choices: sample two servers, use the less loaded.
Peak factor: busiest period's rate over the average.
Percentile: the value a given share of requests beat (p50, p99).
Poisson process: independent random arrivals at a steady average rate.
Profiler: measures where a program spends its time; sampling or tracing.
Queue: work waiting for a busy resource.
Saturation: work queued because a resource is fully busy.
Stampede: many requests rebuilding the same expired cache entry at once.
Tail: the slow end of the latency distribution.
Throughput: requests finished per second.
Utilisation (ρ): share of time a resource is busy.
