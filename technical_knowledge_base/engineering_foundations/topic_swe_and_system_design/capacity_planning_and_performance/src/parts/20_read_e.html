Connection pooling and database load

Every query travels over a database connection: a TCP connection, often TLS, plus a login, plus memory on the database server. In Postgres it is a whole operating-system process: "PostgreSQL implements a "process per user" client/server model. In this model, every client process connects to exactly one backend process" ({{Postgres docs, How Connections Are Established|https://www.postgresql.org/docs/current/connect-estab.html}}). Opening one costs several network round trips (the root's Numbers to know: a new TCP plus TLS 1.3 connection costs 16 ms nearby and 156 ms across the world), and the server allows few: max_connections "is typically 100" by default ({{Postgres 18 docs|https://www.postgresql.org/docs/current/runtime-config-connection.html}}). So production code never opens a connection per request. A connection pool keeps a few open and lends them out: a request borrows one, runs its queries, gives it back.

How big: Little's law again

Connections in use on average = queries per second × time each query holds a connection. The chat API at the busy hour sends about 3,472 database reads a second (1,157 requests, 3 reads each, the Scale simulator's defaults); at 1 ms each that is 3.5 connections busy on average. Pools need headroom for bursts, and the M/M/c maths says how much (the share of queries that find every connection busy, Erlang C, for 3.47 connections' worth of load):

Six to eight connections per database is enough for this whole product's reads, which surprises everyone the first time. The HikariCP authors (Java's most used pool) make the same point with the Oracle Real-World Performance group's demonstration, where cutting a pool from 2,048 connections to 96 took response times from about 100 ms to about 2 ms, and a starting formula, "connections = ((core_count * 2) + effective_spindle_count)", summed up as "You want a small pool, saturated with threads waiting for connections" ({{HikariCP, About Pool Sizing|https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing}}). A database with 8 cores cannot run more than 8 queries at once anyway; extra connections only add contention.

The two traps that take databases down

1. Pools multiply. SQLAlchemy 2.1's default pool is pool_size=5 plus max_overflow=10 per process ({{create_engine docs|https://docs.sqlalchemy.org/en/21/core/engines.html}}). 20 app servers × 4 worker processes × 15 = 1,200 possible connections against a database allowing 100. Size pools from the database's side: total across every process ≤ what the database can run.

2. Hold time is what counts. Holding a connection (or worse, an open transaction) while calling the model turns 1 ms into 10 seconds: 1,157 requests a second × 10 s = 11,570 connections. Read what you need, release the connection, call the model, then borrow one again to save the reply.

PgBouncer: a pool in front of the database

When many processes each hold their own pool, put one pooler in front of Postgres. PgBouncer (1.26.0, 23 September 2026) accepts thousands of client connections and maps them onto a few real ones. Its pool_mode decides when a real connection goes back ({{PgBouncer config|https://www.pgbouncer.org/config.html}}):

  • session (the default): "Server is released back to pool after client disconnects." Safe, saves little.
  • transaction: "Server is released back to pool after transaction finishes." The mode that gives the big win, at a price: "clients must not use any session-based features, since each transaction ends up in a different connection and thus gets a different session state" (session variables, advisory locks, LISTEN; prepared statements are tracked, up to max_prepared_statements = 200 per connection by default).
  • statement: released after every query; multi-statement transactions are refused.

Defaults to know: default_pool_size = 20 real connections per user and database pair, max_client_conn = 100 client connections. Managed poolers exist too (Amazon RDS Proxy is one). For the chat API: each app process keeps a small pool (psycopg_pool 3.3 defaults to min_size=4, fixed size unless you set max_size), PgBouncer in transaction mode in front, and the database's max_connections sized for PgBouncer's real connections plus admin headroom.

When not to: a single small app with one process does not need PgBouncer; its own pool is enough. And a pool does not create database capacity: if the database is at 90% CPU, a bigger pool only makes more queries wait inside it.

Profiling: find where the time goes

When something is slow, the most expensive mistake is guessing. A profiler measures where a running program spends its time. Two kinds: tracing (deterministic) profilers record every function call (Python's cProfile), exact but slow enough to distort the program; sampling profilers look at the call stack many times a second and count what they see, which is cheap enough to run on a production server.

Reading a flame graph

Brendan Gregg's flame graph (December 2011) draws the sampled stacks: "The x-axis shows the stack profile population, sorted alphabetically (it is not the passage of time), and the y-axis shows stack depth, counting from zero at the bottom ... The wider a frame is, the more often it was present in the stacks" ({{Gregg, Flame Graphs|https://www.brendangregg.com/flamegraphs.html}}; the {{CACM 2016 article|https://doi.org/10.1145/2909476}}). So you look for wide plateaus at the top: functions that are themselves on the CPU in many samples. A wide frame lower down only says that a lot happens beneath it.

Illustrative, not a measured profile: the shape to look for. Here re-tokenising the whole conversation on every message is the plateau; caching the token count per message would remove most of it.

The trap: a CPU profile shows only time on the CPU. A request that spends 400 ms waiting for the database or the model is invisible in it, because waiting uses no CPU. For waits you need off-CPU or wall-clock profiling (py-spy's --idle includes idle threads), or better, distributed tracing, which shows each call's duration across services ({{Observability|n:3ef5c17b0d0d811e8490c54dd42c2b9b}}).

py-spy, and Python's new built-in sampler

py-spy (0.4.2, April 2026) is the usual tool: a sampling profiler written in Rust that "doesn't run in the same process as the profiled Python program", so it attaches to a live server without a restart, with "extremely low overhead"; it supports CPython 2.3 to 2.7 and 3.3 to 3.14 ({{py-spy|https://github.com/benfred/py-spy}}).

py-spy top --pid 12345 # live view: which functions are on the CPU now py-spy record -o profile.svg --pid 12345 # flame graph of a running server (Ctrl-C to stop) py-spy dump --pid 12345 # every thread's stack, once: "where is it stuck?" py-spy record --gil --idle -o p.svg --pid 12345 # only threads holding the GIL; include idle ones

Python 3.15 (final release due 9 October 2026, {{PEP 790|https://peps.python.org/pep-0790/}}) ships a sampling profiler in the standard library, profiling.sampling (the "tachyon" profiler), with cProfile moved to profiling.tracing ({{PEP 799, Final|https://peps.python.org/pep-0799/}}).

Async I/O, threads and processes in Python, and the GIL

Standard CPython has a global interpreter lock (GIL): only one thread runs Python code at a time in a process. A thread waiting on the network or a disk releases it. So the right tool depends on what the work waits for:

  • Waiting on I/O (database, Redis, the model API: almost everything our chat API does): asyncio (one thread, thousands of waits interleaved; FastAPI's async def endpoints) or threads. FastAPI runs plain def endpoints in AnyIO worker threads, and "The default AnyIO worker thread limiter has a value of 40" ({{AnyIO docs|https://anyio.readthedocs.io/en/stable/threads.html}}), a hidden concurrency cap worth knowing.
  • CPU work in Python (tokenising, JSON on large payloads, image resizing): threads do not help under the GIL; use processes (several Uvicorn or Gunicorn workers, roughly one per core, or a ProcessPoolExecutor), or native code that releases the GIL (NumPy, most tokenizers written in Rust or C).

Free-threaded Python, status on 2026-10-04. Python 3.13 (October 2024) shipped an experimental build without the GIL ({{PEP 703|https://peps.python.org/pep-0703/}}). Python 3.14 (October 2025) made it "officially supported but still optional" (phase II of {{PEP 779|https://peps.python.org/pep-0779/}}), whose acceptance criteria capped the single-thread slowdown at 15%; the 3.14 docs measure about 1% on macOS on Apple silicon and 8% on x86-64 Linux ({{Python 3.14 free-threading howto|https://docs.python.org/3/howto/free-threading-python.html}}). Making it the default (phase III) is "left for a future PEP". In practice: the default python3 still has a GIL, C extensions must be rebuilt and declare support, so for a web service in 2026 processes for CPU work and asyncio for I/O remain the safe default; try the free-threaded build for CPU-heavy, thread-friendly code with its dependencies checked.
