Connection pools and concurrency limits

Every query travels over a database connection: TCP, often TLS, a login, and memory on the server. In Postgres it is a whole process ("PostgreSQL implements a "process per user" client/server model", {{Postgres docs|https://www.postgresql.org/docs/current/connect-estab.html}}); opening one costs several round trips (root's Numbers to know: a new TCP plus TLS 1.3 connection costs 16 ms nearby and 156 ms across the world), and max_connections "is typically 100" ({{Postgres 18 docs|https://www.postgresql.org/docs/current/runtime-config-connection.html}}). So a connection pool keeps a few open and lends them out.

How big: Little's law again

Connections busy = queries a second × time each holds one. The chat API at the busy hour sends about 3,472 reads a second (1,157 requests, 3 reads each, the Scale simulator's defaults); at 1 ms each, 3.5 connections busy on average. Erlang C says how much headroom bursts need (the share of queries that find every connection busy):

Erlang C for 3.47 connections' worth of load: 6 connections leave 17.2% of queries waiting, 8 leave 2.9%, 10 leave 0.3%.

Six to eight connections per database carry this whole product's reads, which surprises everyone the first time. HikariCP's authors make the same point with the Oracle Real-World Performance group's demonstration, where cutting a pool from 2,048 connections to 96 took response times from about 100 ms to about 2 ms, and a starting formula, "connections = ((core_count * 2) + effective_spindle_count)": "You want a small pool, saturated with threads waiting for connections" ({{HikariCP, About Pool Sizing|https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing}}). A database with 8 cores cannot run more than 8 queries at once; extra connections only add contention. The same reasoning sizes every concurrency limit in the service: worker processes, thread pools (FastAPI's hidden AnyIO limit of 40 threads, below), HTTP client pools, model streams (LLM-backed services).

The two traps that take databases down

1. Pools multiply. SQLAlchemy 2.1's default pool is pool_size=5 plus max_overflow=10 per process ({{create_engine docs|https://docs.sqlalchemy.org/en/21/core/engines.html}}). 20 app servers × 4 worker processes × 15 = 1,200 possible connections against a database allowing 100. Size pools from the database's side: total across every process ≤ what the database can run.

2. Hold time is what counts. Holding a connection (or worse, an open transaction) while calling the model turns 1 ms into 10 seconds: 1,157 requests a second × 10 s = 11,570 connections. Read what you need, release the connection, call the model, then borrow one again to save the reply.

Correction (2026-10-24)
The 11,570 above counts all five requests per message as model calls. Only the message request calls the model, about 231 a second at the busy hour, so holding a connection across the call needs 231 × 10 s = 2,315 connections, the root's figure for streams open at once. Either is far beyond Postgres's default of 100; the lesson stands.
PgBouncer: a pool in front of the database (depth)

When many processes each hold their own pool, put one pooler in front of Postgres. PgBouncer (1.26.0, 23 September 2026) accepts thousands of client connections and maps them onto a few real ones. Its pool_mode decides when a real connection goes back ({{PgBouncer config|https://www.pgbouncer.org/config.html}}):

  • session (the default): "Server is released back to pool after client disconnects." Safe, saves little.
  • transaction: "Server is released back to pool after transaction finishes." The big win, at a price: "clients must not use any session-based features, since each transaction ends up in a different connection and thus gets a different session state" (session variables, advisory locks, LISTEN; prepared statements are tracked, up to max_prepared_statements = 200 per connection by default).
  • statement: released after every query; multi-statement transactions are refused.

Defaults to know: default_pool_size = 20 real connections per user and database pair, max_client_conn = 100. Managed poolers exist too (Amazon RDS Proxy). For the chat API: each app process keeps a small pool (psycopg_pool 3.3 defaults to min_size=4, fixed size unless you set max_size), PgBouncer in transaction mode in front, and max_connections sized for PgBouncer's real connections plus admin headroom. Running it in production is on {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}}.

When not to: a single small app with one process does not need PgBouncer. And a pool does not create database capacity: if the database is at 90% CPU, a bigger pool only makes more queries wait inside it.

Profiling: find where the time goes

When something is slow, the most expensive mistake is guessing. A profiler measures where a running program spends its time. Tracing profilers record every call (Python's cProfile): exact, but slow enough to distort the program. Sampling profilers look at the call stack many times a second and count what they see: cheap enough for a production server.

Reading a flame graph

Brendan Gregg's flame graph (December 2011) draws the sampled stacks: "The x-axis shows the stack profile population, sorted alphabetically (it is not the passage of time), and the y-axis shows stack depth, counting from zero at the bottom ... The wider a frame is, the more often it was present in the stacks" ({{Gregg, Flame Graphs|https://www.brendangregg.com/flamegraphs.html}}; {{CACM 2016|https://doi.org/10.1145/2909476}}). So look for wide plateaus at the top: functions that are themselves on the CPU in many samples. A wide frame lower down only says a lot happens beneath it.

The trap: a CPU profile shows only time on the CPU. A request that spends 400 ms waiting for the database or the model is invisible in it, because waiting uses no CPU. For waits use off-CPU or wall-clock profiling (py-spy's --idle includes idle threads), or distributed tracing ({{Observability|n:3ef5c17b0d0d811e8490c54dd42c2b9b}}). Async I/O, threads and processes in Python, and the GIL

Standard CPython has a global interpreter lock (GIL): only one thread runs Python code at a time in a process; a thread waiting on the network or a disk releases it. So the GIL is a capacity question: how many cores can one process use? (How one FastAPI service waits, with 50 requests measured in four handler styles, is {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}, section 6.)

  • Waiting on I/O (database, Redis, the model API: almost everything our chat API does): asyncio (one thread, thousands of waits interleaved; FastAPI's async def endpoints) or threads. FastAPI runs plain def endpoints in AnyIO worker threads, and "The default AnyIO worker thread limiter has a value of 40" ({{AnyIO docs|https://anyio.readthedocs.io/en/stable/threads.html}}): a hidden concurrency cap, so by Little's law a sync endpoint holding a thread for a 10-second model call serves at most 4 requests a second per process.
  • CPU work in Python (tokenising, large JSON, image resizing): threads do not help under the GIL; use processes (several Uvicorn or Gunicorn workers, roughly one per core, or a ProcessPoolExecutor), or native code that releases the GIL (NumPy, tokenizers written in Rust or C).

Free-threaded Python, status on 2026-10-04. Python 3.13 (October 2024) shipped an experimental build without the GIL ({{PEP 703|https://peps.python.org/pep-0703/}}). Python 3.14 (October 2025) made it "officially supported but still optional" (phase II of {{PEP 779|https://peps.python.org/pep-0779/}}), whose acceptance criteria capped the single-thread slowdown at 15%; the 3.14 docs measure about 1% on macOS on Apple silicon and 8% on x86-64 Linux ({{Python 3.14 free-threading howto|https://docs.python.org/3/howto/free-threading-python.html}}). Making it the default (phase III) is "left for a future PEP". In practice the default python3 still has a GIL and C extensions must be rebuilt and declare support, so for a web service in 2026 processes for CPU work and asyncio for I/O remain the safe default; try the free-threaded build for CPU-heavy, thread-friendly code with its dependencies checked.
