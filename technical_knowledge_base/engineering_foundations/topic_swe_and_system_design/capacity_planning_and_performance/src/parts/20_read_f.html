Load testing without fooling yourself

A load test sends synthetic traffic at a system to learn what it does under load before real users find out. Its kinds differ by the question: a load test (can it carry the expected peak?), a stress or breakpoint test (where and how does it break?), a soak test (hours at normal load: leaks, slow growth), a spike test (a sudden jump: does autoscaling keep up?). All of them share two traps that make a test report numbers far better than reality.

Trap 1: the workload model

A closed workload has a fixed number of virtual users; each sends a request, waits for the answer, maybe "thinks", and only then sends the next. An open workload has requests arriving at a rate, whatever the system is doing. Bianca Schroeder, Adam Wierman and Mor Harchol-Balter showed how different the answers are ({{"Open Versus Closed: A Cautionary Tale", NSDI 2006|https://www.usenix.org/legacy/event/nsdi06/tech/full_papers/schroeder/schroeder.pdf}}): "for a fixed load, the mean response time for an open system model can exceed that for a closed system model by an order of magnitude or more", and variability in request sizes "has a huge impact on response times in open systems" but "much less of an effect in closed models". A closed test is self-limiting: when the server slows down, the users slow down with it, so the queue never builds the way it would in production. Users on the internet do not wait for each other, so a public API is close to open (strictly, "partly open": sessions arrive independently, and inside a session a user waits for each reply).

Trap 2: coordinated omission

Gil Tene named the measurement version of the same problem ({{"How NOT to Measure Latency", Strange Loop 2015|https://www.youtube.com/watch?v=lJ8ydIuPFeU}}). A closed-loop tool measures each request from when it was actually sent. During a stall it sends nothing, so the requests that real users would have sent during the stall, and that would have waited, are never measured: the tool has coordinated with the server to omit the bad moments. That is coordinated omission. wrk2's README: wrk "exhibits a strong Coordinated Omission effect, through which most of the high latency artifacts exhibited by the measured server will be ignored"; wrk2 instead "measures response latency from the time the transmission should have occurred according to the constant throughput configured for the run" ({{wrk2|https://github.com/giltene/wrk2}}). Its example with a 1.4 second server pause: corrected p99 1.27 s, uncorrected p99 6.04 ms.

Experiment 2: the same stalling server, measured closed-loop and open-loop

Experiment 1's server (one request at a time, exponential service, mean 10 ms nominal), set to freeze for 1.5 s every 15 s, as a stop-the-world garbage-collection pause or a slow disk flush would. 30 requests a second for 60 s, twice: a closed-loop generator (3 users, each sending at most 10 a second, waiting for each answer, catching up immediately when late: what wrk, Locust users and k6's constant-vus do), and an open-loop one (evenly spaced sends at the same rate, never waiting). The closed run also logged when each request should have been sent, which gives the corrected reading.

Designing a realistic test

  1. Model the traffic from production: the mix of endpoints (for every message, our app also loads history, lists chats, refreshes auth: 1 + 4 requests), the request sizes, the spread of keys. A test that reads one chat a million times measures the cache, not the system.
  2. Model the slow dependencies honestly. If the model provider is stubbed out, stub it with its real latency distribution, streaming for about 10 seconds, or the test will never find the connection pool and worker limits that a 10-second call exposes.
  3. Ramp in steps and hold each step long enough for queues to settle and for the p99 to rest on enough samples (thousands of requests per step).
  4. Record offered against achieved throughput, errors and every resource's utilisation (USE). If achieved stops following offered, you are past the knee; if errors rise, the latency numbers are flattered by the failures.
  5. Check the load generator. If its own CPU is saturated, its latency numbers are its own queueing. Our Experiment 1 logged how late each send was against its schedule for this reason (its p99 lateness was 3 to 7 ms, small next to latencies of 50 ms and more, and counted in the measurement because latency runs from the scheduled time).
  6. Test in an environment shaped like production (same instance types, same database size, same cache warmth) and say what differs.

Finding the knee

Plot the p99 (y) against achieved throughput (x) across the steps: flat, then bending up, then vertical. The knee is where it bends; the usable capacity is the highest throughput whose p99 still meets your target with headroom left. From Experiment 1 (one server, about 11 ms of work): p99 54 ms at 11% busy, 114 ms at 57%, 190 ms at 79%, 321 ms at 89%, 556 ms at 95%, then seconds. With a p99 target of 200 ms this server's usable capacity is about 80% of its maximum; with 100 ms, about 50%. The target, not the hardware, sets the usable fraction. Little's law checks the result: achieved throughput × mean latency must equal the concurrency the generator held in flight.

Capacity planning

Capacity planning decides how much hardware to have, and when, so that the peak is served with the required reliability at the lowest cost. Google's SRE book lists what it needs: "An accurate organic demand forecast, which extends beyond the lead time required for acquiring capacity", "An accurate incorporation of inorganic demand sources into the demand forecast", and "Regular load testing of the system to correlate raw capacity (servers, disks, and so on) to service capacity" ({{SRE book, ch. 1|https://sre.google/sre-book/introduction/}}). Organic demand is steady growth; inorganic is a launch, a marketing push, a viral post. The load test supplies the per-server capacity; the rest of this section turns the forecast into a number of servers.

Peak factors: the root's 2× explained

Capacity is sized for the peak, not the average: the peak factor is the busiest period's rate divided by the average. The root assumed 2× (busy hour over daily average) and labelled it illustrative. Real hourly traffic says it is a sensible number for one region and too high for a global product. Wikipedia's hourly page views by human users for September 2026 (Wikimedia's public API):

The window matters as much as the product. Per second, peaks are far sharper: Twitter's busiest second in August 2013 was 143,199 Tweets against an average of about 5,700, a factor of 25 (root Case files: "A peak 25 times the average"). Servers absorb second-scale bursts with queues and headroom; hours-scale peaks need capacity; known events (a launch, a match final) need a separate inorganic forecast.

Headroom, N+1 and N+2

Let N be the number of servers needed to carry the peak at the target utilisation. N+1 adds one spare so that losing any single server still leaves the peak served. N+2 adds two, so that one server can be down for maintenance or a deploy while another fails. Google's capacity planning tool expresses requirements this way: "I want to meet service Foo's demand in each geographic region, and have N + 2 redundancy" ({{SRE book, ch. 18|https://sre.google/sre-book/software-engineering-in-sre/}}). The same logic applies to bigger failure units. Spread across Z availability zones (separate data centres in one region), losing a zone loses 1/Z of capacity, so the fleet must be Z/(Z − 1) times the peak need: 1.5× with 3 zones, 2× with 2.

Autoscaling adds and removes servers as load moves (AWS target tracking on CPU or requests per target, Kubernetes' Horizontal Pod Autoscaler). It does not remove the need to plan: it needs a floor that survives a failure, a ceiling that the database behind it can take, a signal that tracks real load (Slack's autoscaler removed servers that looked idle because they were waiting on a saturated network: root Case files, "The first Monday of the year: autoscaling made it worse"), and it is too slow for the first minutes of a spike. GPU replicas take minutes to start, which changes the whole approach: {{ML system design, section 8|n:3c65c17b0d0d8117b057dc2586836ec8}}.

The plan for the chat API

One server: an m7i.xlarge (4 vCPU, $0.2016 an hour on demand in us-east-1, 730 hours a month, the root's price) carrying 769 requests a second at 100% (4 cores / 5.2 ms of CPU per request, the Scale simulator's figure with background jobs on a queue). Defaults: the root's chat assistant, 1 million daily users × 10 messages × 5 requests per message / 86,400 s = 579 requests a second on average. Servers = ceil(peak / (769 × target)) + spares. Checked in src/recompute.py.

With the defaults the arithmetic is: peak 1,157 requests a second, 769 × 0.6 = 462 per server, so 3 servers carry the peak at 50% each, and N+1 makes 4 ($589 a month). With all 4 up, the peak runs at 38%; with one down, 50%, the same as the root's Scale simulator after its suggested fixes (3 app servers at 50%). Growing 10% a month for 6 months nearly doubles the load (1.77×), which needs 6 servers. The app tier is the cheap part: the root's Step 6 shows the GPU fleet dominating the bill, and the same method sizes it with a per-GPU throughput instead of a per-server one.

When not to over-plan: stateless app servers in a cloud autoscale in minutes, so plan their floor and limits rather than a year of growth; spend the forecasting effort where lead times are long (GPUs, database instances, reserved capacity contracts).
