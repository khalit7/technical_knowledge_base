Load testing without fooling yourself

A load test sends synthetic traffic at a system to learn what it does under load before real users find out: a load test (can it carry the expected peak?), a stress or breakpoint test (where and how does it break?), a soak test (hours at normal load: leaks, slow growth), a spike test (does autoscaling keep up?). All share two traps that make a test report numbers far better than reality.

Trap 1: the workload model

A closed workload has a fixed number of virtual users; each sends a request, waits for the answer, and only then sends the next. An open workload has requests arriving at a rate, whatever the system is doing. Schroeder, Wierman and Harchol-Balter ({{"Open Versus Closed: A Cautionary Tale", NSDI 2006|https://www.usenix.org/legacy/event/nsdi06/tech/full_papers/schroeder/schroeder.pdf}}): "for a fixed load, the mean response time for an open system model can exceed that for a closed system model by an order of magnitude or more", and request-size variability "has a huge impact on response times in open systems" but "much less of an effect in closed models". A closed test is self-limiting: when the server slows, the users slow with it, so the queue never builds as it would in production. Users on the internet do not wait for each other, so a public API is close to open (strictly "partly open": sessions arrive independently, and inside a session a user waits for each reply).

Trap 2: coordinated omission

Gil Tene named the measurement version ({{"How NOT to Measure Latency", Strange Loop 2015|https://www.youtube.com/watch?v=lJ8ydIuPFeU}}). A closed-loop tool measures each request from when it was actually sent. During a stall it sends nothing, so the requests real users would have sent during the stall, and that would have waited, are never measured: the tool has coordinated with the server to omit the bad moments. That is coordinated omission. wrk2's README: wrk "exhibits a strong Coordinated Omission effect, through which most of the high latency artifacts exhibited by the measured server will be ignored"; wrk2 instead "measures response latency from the time the transmission should have occurred according to the constant throughput configured for the run" ({{wrk2|https://github.com/giltene/wrk2}}). Its example with a 1.4 second pause: corrected p99 1.27 s, uncorrected 6.04 ms.

Experiment 2 reproduces it: the same server, set to freeze for 1.5 s every 15 s, measured closed-loop and open-loop at the same rate. Predict how far apart the two p99s will be, then switch between the three readings.

How Experiment 2 was run (provenance)
Experiment 2: the same stalling server, measured closed-loop and open-loop

Experiment 1's server (one request at a time, exponential service, mean 10 ms nominal), set to freeze for 1.5 s every 15 s, as a stop-the-world garbage-collection pause or a slow disk flush would. 30 requests a second for 60 s, twice: a closed-loop generator (3 users, each sending at most 10 a second, waiting for each answer, catching up immediately when late: what wrk, Locust users and k6's constant-vus do), and an open-loop one (evenly spaced sends at the same rate, never waiting). The closed run also logged when each request should have been sent, which gives the corrected reading.

During each stall the 3 closed-loop users sent 3 requests and stopped, so only 3 slow requests per stall were recorded; real users would have sent 45. The corrected reading (from the schedule) recovers a p99 of 1.43 s.

Designing a realistic test

  1. Model the traffic from production: the endpoint mix (for every message, our app also loads history, lists chats, refreshes auth: 1 + 4 requests), request sizes, the spread of keys. A test that reads one chat a million times measures the cache, not the system.
  2. Model the slow dependencies honestly. Stub the model provider with its real latency distribution, streaming for about 10 seconds, or the test will never find the pool and worker limits a 10-second call exposes.
  3. Use an open model, ramp in steps and hold each step long enough for queues to settle and for the p99 to rest on thousands of requests.
  4. Record offered against achieved throughput, errors and every resource's utilisation (USE). If achieved stops following offered, you are past the knee; if errors rise, the latencies are flattered by the failures.
  5. Check the load generator. If its CPU is saturated, its latencies are its own queueing. Experiment 1 logged how late each send was (p99 lateness 3 to 7 ms, small next to latencies of 50 ms and more, and counted, because latency runs from the scheduled time).
  6. Test in an environment shaped like production (instance types, database size, cache warmth) and say what differs.

Finding the knee

Plot the p99 against achieved throughput across the steps: flat, then bending, then vertical. The usable capacity is the highest throughput whose p99 still meets your target with headroom. From Experiment 1's curve (one server, about 11 ms of work): with a p99 target of 200 ms this server's usable capacity is about 80% of its maximum; with 100 ms, about 50%. The target, not the hardware, sets the usable fraction. Little's law checks the result: achieved throughput × mean latency must equal the concurrency the generator held in flight. The {{Load-test lab|#t-lab}} draws these curves for any pool size, service-time distribution and balancing policy, with Experiment 3's measured points.
