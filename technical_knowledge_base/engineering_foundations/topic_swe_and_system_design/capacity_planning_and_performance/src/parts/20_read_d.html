Caching strategy

A cache keeps a copy of an answer somewhere faster than where it came from (the root's Step 2). It is the cheapest capacity you will ever buy: a Redis read takes about 0.14 ms (root's Numbers to know) while the query it replaces takes milliseconds and, more importantly, uses up the database, the component hardest to scale. It also brings stale answers, a dependency that can empty itself, and stampedes. Invalidation races, Redis's eviction measured on real traffic, and the LLM caches are on {{Caching|n:3cd5c17b0d0d817ebd6ccadd4750c23a}}; this section is the capacity view.

Further left is faster and takes more load off everything behind it, but is harder to invalidate: you can delete a Redis key, you cannot reach into a million phones. So cache immutable things far out (the app's code and images on a CDN, long Cache-Control: max-age, a new file name per version) and changing data close in. An in-process cache (functools.lru_cache, or cachetools 7.2 with a TTL) costs nothing per read but is per server: 8 servers mean 8 copies, 8 times the misses, 8 places to invalidate. A shared cache is one hop away and holds one copy for everyone.

The patterns: who reads and writes the cache

PatternOn a readOn a writeTrade-off
Cache-aside (lazy loading)App checks the cache; on a miss it reads the database and fills the cacheApp writes the database, then deletes the cache entryThe default. Simple, caches only what is read; the first read after a change is slow
Read-throughThe cache library loads missing entries from a function you give itAs cache-asideSame behaviour, less app code; the loader is one place to add coalescing
Write-throughAs cache-asideApp writes cache and database together, synchronouslyReads after writes are fresh; every write pays twice, and you cache data nobody may read
Write-back (write-behind)From the cacheWrite the cache now, flush to the database later in batchesFast writes, absorbs bursts; a cache crash loses acknowledged writes. Rarely right for user data
Write-aroundAs cache-asideWrite the database only; let the entry expireFor data written often and read rarely

Two details carry most of the correctness: on a write, delete, do not update, the cached copy (two concurrent updaters can leave the older value cached), and keep the TTL even with invalidation, because some code path will forget to delete and the TTL bounds how long that bug lasts. The remaining race (a reader putting back a value a writer just invalidated) and Facebook's lease fix are on {{Caching, section 3|n:3cd5c17b0d0d817ebd6ccadd4750c23a}}.

Cache-aside in code, with redis-py (depth)

Cache-aside for our chat API's "load a conversation", with redis-py 8.1 (current on 2026-10-04):

import json, redis r = redis.Redis(host="cache", port=6379) def get_chat(chat_id): key = f"chat:{chat_id}:v1" # version the key so a format change cannot read old entries hit = r.get(key) if hit is not None: return json.loads(hit) chat = db_load_chat(chat_id) # the slow path: a Postgres query r.set(key, json.dumps(chat), ex=300) # TTL 300 s bounds how stale it can ever be return chat def rename_chat(chat_id, title): db_rename_chat(chat_id, title) # 1. write the source of truth (commit) r.delete(f"chat:{chat_id}:v1") # 2. then delete, never update, the cached copy

Hit-rate maths: what the cache does to the database

The hit rate h is the share of reads the cache answers. With λ reads a second, the database sees (1 − h) × λ. Going from 90% to 99% hits looks like a 9-point gain but divides the database's read load by ten (1,000 reads a second become 100, then 10). Mean latency is h × tcache + (1 − h) × (tcache + tdb). Predict: at the defaults, what happens to the database if the cache restarts empty?

Cache read 0.143 ms (Redis GET, root's Numbers to know); a miss adds 5 ms for the database query (illustrative: an indexed primary-key lookup measured 0.067 ms there, a chat history with joins and sorting is slower). Default database capacity 600 reads a second and 1,000 reads a second of demand are the root's Step 2 example; empty, the cache sends the database 167% of its capacity. Formulas checked in src/recompute.py.

Three consequences. The tail is the miss path: at a 95% hit rate the p99 is a database read however fast the cache is; a cache improves the median far more than the p99. The database is now sized for the misses, so the cache has become part of your capacity: when it empties (a restart, a failover, a deploy that changes every key) the full load lands on a database sized for a tenth of it (the root's Scale simulator calls this "cold cache"; Facebook keeps spare "Gutter" servers, about 1% of the memcached fleet, to take a failed server's keys rather than let its misses reach the databases). Warm up before taking traffic: fill a new cache from the old one, or ramp traffic with slow start.

The good side of the dependency, root Case files: "DNS failed in one data center; caches kept most of GitHub up". The hit rate itself is set by how often a key is read again within its TTL (a conversation is re-read on every message; a unique search never is), how skewed popularity is, and whether the hot set fits in memory (measured on real traffic on {{Caching, section 1|n:3cd5c17b0d0d817ebd6ccadd4750c23a}}).

Eviction: LRU, LFU, TinyLFU, and Redis's default (depth)
  • LRU (least recently used): evict what was read longest ago. Cheap, good for most workloads. Redis approximates it by sampling: it "samples a small number of keys at random and then evicts the ones with the longest time since last access" (maxmemory-samples 5 by default).
  • LFU (least frequently used): evict what is read least often, with counts that decay. Better when a few keys are steadily popular and a scan of one-off keys would flush them out of an LRU. Redis has it since 4.0, with a "Morris counter" of a few bits per key.
  • TinyLFU: an admission policy: a new entry only gets in if it is estimated to be read more often than the entry it would evict, using a compact frequency sketch ({{Einziger, Friedman and Manes, ACM ToS 2017|https://arxiv.org/abs/1512.00727}}). Caffeine, the standard Java cache, uses W-TinyLFU: "a small admission LRU that evicts to a large Segmented LRU if accepted by the TinyLfu admission policy" ({{Caffeine wiki|https://github.com/ben-manes/caffeine/wiki/Efficiency}}).

Redis does not evict by default: the shipped redis.conf sets maxmemory-policy noeviction, so a full Redis fails writes. For a cache set maxmemory and a policy explicitly; the Redis docs call allkeys-lru "a good default option if you have no reason to prefer any others" ({{Redis key eviction|https://redis.io/docs/latest/develop/reference/eviction/}}). Redis 8.6 added LRM (least recently modified) policies. Every policy measured on real traffic is on {{Caching, section 5|n:3cd5c17b0d0d817ebd6ccadd4750c23a}}.

Thundering herds and cache stampedes

A cache stampede (dog-piling, a thundering herd): a popular entry expires, and every request that arrives before someone has rebuilt it misses and rebuilds it too. If the rebuild takes 300 ms and the key is read 200 times a second, 60 requests run the same expensive query at once, which makes the query slower, which widens the window. Facebook measured it: "Without leases, all of the cache misses resulted in a peak database query rate of 17K/s. With leases, the peak database query rate was 1.3K/s" ({{Nishtala et al., NSDI 2013|https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf}}; root Case files: "Leases cut a cache stampede from 17,000 to 1,300 queries a second"). Step through the three modes on the same expiry:

The page's model (src/model.py, stampede): one key read 200 times a second, expiring at t = 1 s, rebuilt by a 300 ms database query; XFetch with β = 1 and Δ = 300 ms, seeded random draws. Illustrative rates; the counts (60, 1, 1 database queries) are checked in src/recompute.py.

  1. Request coalescing (single-flight): the first miss rebuilds; the others wait for its answer (Go's singleflight, nginx's proxy_cache_lock on, Facebook's leases across servers). Cost: the waiters still wait for the rebuild.
  2. Serve stale while revalidating: keep the old value a little past its TTL and refresh in the background (Cache-Control: stale-while-revalidate=30, {{RFC 5861|https://datatracker.ietf.org/doc/html/rfc5861}}). Cost: a few seconds of staleness.
  3. Probabilistic early expiry (XFetch): each reader recomputes early with a probability that rises as expiry approaches and as the rebuild gets more expensive: recompute if now − Δ · β · ln(rand()) ≥ expiry, Δ the last rebuild's duration ({{Vattani, Chierichetti and Lowenstein, VLDB 2015|https://cseweb.ucsd.edu/~avattani/papers/cache_stampede.pdf}}, proved optimal). Cost: one early rebuild per expiry, no waiting, no locks.
  4. TTL jitter: entries written together with the same TTL expire together; add a random 0 to 10% to each TTL. (Advice, not from a single source.)
The defences in their sources' words, a minimal single-flight for asyncio, and CDNs (depth)

Go's singleflight: "making sure that only one execution is in-flight for a given key at a time. If a duplicate comes in, the duplicate caller waits for the original to complete and receives the same results" ({{golang.org/x/sync v0.23.0|https://pkg.go.dev/golang.org/x/sync/singleflight}}). nginx's proxy_cache_lock on: "only one request at a time will be allowed to populate a new cache element" ({{nginx proxy module|https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_cache_lock}}); its stale-while-revalidate is proxy_cache_use_stale updating plus proxy_cache_background_update on. Facebook's leases hand out one token per key every 10 seconds; other clients are told to "wait a short amount of time". XFetch's authors: β = 1 "already provides effective prevention against cache stampedes".

A minimal single-flight: the first caller for a key creates a future and does the work; others await the same future.

import asyncio _inflight: dict[str, asyncio.Future] = {} async def get_coalesced(key, load): if (fut := _inflight.get(key)) is not None: return await fut # someone is already loading this key: share their answer fut = asyncio.get_running_loop().create_future() _inflight[key] = fut try: value = await load(key) # the one real database call fut.set_result(value) return value except Exception as e: fut.set_exception(e) # waiters get the error too, not a hang raise finally: del _inflight[key]

Per process only: 8 servers can still send 8 queries. Route each key to one server (consistent hashing, as Discord did) or coalesce in the shared cache (a short lock key with SET key NX PX 3000) to go further.

CDNs. A CDN is a cache run for you in hundreds of cities. It serves static files and any public response you mark cacheable with Cache-Control: public, max-age=... (s-maxage for shared caches only). Its hit ratio is what you pay for: every miss crosses the world to your servers. CDNs collapse concurrent misses for the same URL into one request to you (the same coalescing idea), and support stale-while-revalidate and stale-if-error. For our chat assistant the CDN carries the app and static assets; conversations are personal and uncacheable at the edge. LLM-specific caches (prompt caching, KV prefix reuse, semantic caches) are on {{Caching, sections 10 to 12|n:3cd5c17b0d0d817ebd6ccadd4750c23a}}.

When not to cache: data that must be exactly current (a credit balance, a permission just revoked), data read once (a unique search), or anything you cannot invalidate and would be harmed by serving late. And do not add a cache to hide a missing index: fix the query first (root Step 2).
