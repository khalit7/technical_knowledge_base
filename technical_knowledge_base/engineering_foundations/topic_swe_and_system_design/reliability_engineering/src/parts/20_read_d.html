Rate limiting: per-client fairness

Load shedding protects the service from the total; a rate limit protects it from one client, and other clients from that client. It caps each client (an API key, a user, an IP address, a tenant) at a rate such as 10 requests a second, and rejects the rest with HTTP 429 Too Many Requests, ideally with a Retry-After header saying when to come back (RFC 6585 §4). LLM APIs limit tokens per minute as well as requests, because one request can cost 100 times another. Stripe runs four limiters: a request rate limiter ("by far the most important one", N requests per second per user), a concurrent-requests limiter ("You can only have 20 API requests in progress at the same time"), and two load shedders, and warns: "Make sure you have kill switches to disable the rate limiters should they kick in erroneously" ({{Tarjan, Stripe, 2017|https://stripe.com/blog/rate-limiters}}).

Five algorithms on one burst

  • Fixed window: count requests per calendar second; reset at each boundary. One counter, but a client can send the limit at the end of one second and again at the start of the next: twice the limit within one real second.
  • Sliding log: remember the time of every accepted request and count those in the last second. Exact, but memory grows with the limit.
  • Sliding window counter: keep only this window's and the previous window's counts and assume the previous one was spread evenly. Cloudflare's example: 42 requests last minute, 18 so far in a minute that started 15 s ago gives 42 × (45/60) + 18 = 49.5. Over 400 million requests, "0.003% of requests have been wrongly allowed or rate limited", with "an average difference of 6% between real rate and the approximate rate" ({{Cloudflare, 2017|https://blog.cloudflare.com/counting-things-a-lot-of-different-things/}}).
  • Token bucket: a bucket holds up to B tokens and refills at R per second; each request takes one or is rejected. Allows bursts up to B, average R. Stripe: "We use the token bucket algorithm to do rate limiting", implemented in Redis. Standardised in networking as early as RFC 2697 (1999), whose meter uses token buckets that are refilled "CIR times per second" ({{RFC 2697|https://www.rfc-editor.org/rfc/rfc2697.txt}}).
  • Leaky bucket (as a queue): requests wait in a bounded queue that drains at a fixed rate; when it is full, new ones are rejected. It smooths bursts into a steady stream at the cost of delay, like Linux's token bucket filter which "is a pure shaper" and queues packets "up to a configured limit" ({{tc-tbf(8)|https://man7.org/linux/man-pages/man8/tc-tbf.8.html}}). (Confusingly, "leaky bucket as a meter" is equivalent to a token bucket; GCRA, used by some Redis rate limiters, is that form.)

In production: limits live at the edge (API gateway, Envoy, Cloudflare) or in a shared store (Redis, with the check-and-decrement done atomically in one Lua script so two servers cannot both take the last token). Limit per tenant and per expensive resource (tokens per minute per model), tell clients their remaining allowance in headers, and make your own clients obey 429 with jitter: the root's Case files include Cloudflare's September 2025 dashboard outage, where the company's own dashboard overwhelmed its API. The capacity side (how many requests a server can take at all) is in {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}}.

Health checks done right

A health check is a request a load balancer or orchestrator sends to each server to decide whether to send it traffic or restart it. AWS's Builders' Library separates three depths ({{Implementing health checks|https://builder.aws.com/content/3Ev53O39izHCtWLzp4XU6t8PC1O/implementing-health-checks}}): liveness checks "test the basic connectivity to a service and the presence of a server process"; local checks "verify that the application is likely to be able to function" (disk not full, config loaded); dependency checks are "a thorough inspection of the ability of an application to interact with its adjacent systems".

Kubernetes has three probes: liveness (fail it and the container is restarted), readiness (fail it and the pod is taken out of the load balancer, not restarted) and startup (holds the other two off while a slow app starts, useful for a model server loading weights). Defaults: probe every 10 s, 1 s timeout, 3 failures in a row to fail, 1 success to pass ({{Kubernetes docs|https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/}}). The docs' own warning: "Incorrect implementation of liveness probes can lead to cascading failures. This results in restarting of container under high load", and their pattern is that "the liveness probe passes when the app itself is healthy, but the readiness probe additionally checks that each required back-end service is available."

Health-check mistakes that cause outages
Liveness checks a dependency. The database has a slow minute, every pod fails liveness, Kubernetes restarts all of them, and the restart stampede (cold caches, new connections) keeps the database down. Keep liveness to "the process can answer".
Every server fails at once and the balancer obeys. If all hosts look unhealthy, the problem is probably shared (the check, or a dependency), and removing every host guarantees an outage. AWS load balancers do the opposite: "when all servers fail health checks at the same time, the load balancer fails open, allowing traffic to all servers" (Builders' Library). Envoy's 10% ejection cap is the same idea. The root's Case files hold Meta's October 2021 outage, where a health rule correct for one site withdrew every data center at once.
The check is cheaper than real work. A /health that returns 200 while real requests fail is gray failure by design; pair health checks with user-side SLIs.

Deployment safety: most outages are changes

"SRE has found that roughly 70% of outages are due to changes in a live system", and the book's remedies are to automate "progressive rollouts", "quickly and accurately detecting problems" and "rolling back changes safely when problems arise" ({{SRE book, ch. 1|https://sre.google/sre-book/introduction/}}). A change includes code, config, feature flags, model versions, prompts, dependency upgrades and infrastructure.

  • Canary: release to a small slice first and compare it with the rest. The SRE workbook's arithmetic: if a bad build fails 20% of requests, a 5% canary gives "a 1% overall error rate" instead of 20% ({{Canarying releases|https://sre.google/workbook/canarying-releases/}}). It should be "sizeable and last long enough to be representative", and "We strongly advise running only one canary deployment at a time."
  • Progressive rollout in waves: AWS deploys first to a "one-box" stage ("a single virtual machine or single container"), then in "waves" of increasing size; "A typical pipeline waits at least one hour after each one-box stage, at least 12 hours after the first regional wave" ({{Liguori, Automating safe, hands-off deployments|https://builder.aws.com/content/3ErTKQOTKc5NIw031UePBPxTQ6I/automating-safe-hands-off-deployments}}). The wait is called bake time.
  • Automatic rollback: alarms watch the canary and each wave; a high-severity alarm is used "to page the oncall engineer and to automatically roll back the service if a deployment is in progress" (same essay). Make rollback the default reaction, debug later.
  • Feature flags: ship code switched off and turn it on separately, per user group or percentage. Fowler and Hodgson's four kinds: release toggles (latent code "which may never be turned on"), experiment toggles (A/B tests), ops toggles ("disable or degrade that feature quickly in production"), permissioning toggles ({{Feature Toggles|https://martinfowler.com/articles/feature-toggles.html}}). A flag flip is itself a change: roll it out in stages too.

Config is code. The root's Case files hold four outages that were config or content pushed everywhere at once: Cloudflare's November 2025 proxy crash from a doubled feature file, Cloudflare's 2026 follow-up that now rolls config out like code, CrowdStrike's July 2024 content update that crashed 8.5 million PCs, and Knight Capital's 2012 deploy that reached seven of eight servers.
