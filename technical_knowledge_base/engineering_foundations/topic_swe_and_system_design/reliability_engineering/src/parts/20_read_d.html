9. Rate-limit algorithms: per-client fairness

Shedding protects the service from the total; a rate limit protects it from one client, and other clients from that client: each API key, user or tenant gets a rate such as 10 requests a second, and the rest get 429 Too Many Requests, ideally with Retry-After (RFC 6585 §4). LLM APIs limit tokens per minute as well, because one request can cost 100 times another. This page owns the algorithms; how an API exposes limits (headers, quotas, tiers) is {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}}', and budgets at an LLM gateway are {{Gateways and routing|n:3f15c17b0d0d81e4a964c129a3e520ae}}'.

  • Fixed window: count per calendar second, reset at each boundary. One counter, but a client can send the limit just before and again just after the boundary: twice the limit within one real second.
  • Sliding log: remember every accepted request's time and count the last second. Exact; memory grows with the limit.
  • Sliding window counter: this window's and the previous window's counts, assuming the previous was spread evenly. Cloudflare: 42 requests last minute, 18 so far in a minute that started 15 s ago gives 42 × (45/60) + 18 = 49.5; over 400 million requests "0.003% of requests have been wrongly allowed or rate limited", with "an average difference of 6% between real rate and the approximate rate" ({{Cloudflare, 2017|https://blog.cloudflare.com/counting-things-a-lot-of-different-things/}}).
  • Token bucket: up to B tokens, refilled at R per second, one per request. Bursts up to B, average R. Stripe: "We use the token bucket algorithm to do rate limiting", in Redis; standardised in networking as early as RFC 2697 (1999), refilled "CIR times per second" ({{RFC 2697|https://www.rfc-editor.org/rfc/rfc2697.txt}}).
  • Leaky bucket (as a queue): requests wait in a bounded queue drained at a fixed rate; smooth output at the cost of delay, like Linux's token bucket filter, which "is a pure shaper" ({{tc-tbf(8)|https://man7.org/linux/man-pages/man8/tc-tbf.8.html}}). "Leaky bucket as a meter" is equivalent to a token bucket; GCRA, used by some Redis limiters, is that form.

Make your own clients obey 429 with jitter: the root's Case files include Cloudflare's September 2025 dashboard outage, where its own dashboard overwhelmed its API.

Stripe's four limiters (2017)

Stripe runs four limiters: a request rate limiter ("by far the most important one"), a concurrent-requests limiter ("You can only have 20 API requests in progress at the same time") and two load shedders, and warns: "Make sure you have kill switches to disable the rate limiters should they kick in erroneously" ({{Tarjan, Stripe, 2017|https://stripe.com/blog/rate-limiters}}).

10. Health checks done right

A health check is a request a load balancer or orchestrator sends to decide whether a server gets traffic or a restart. AWS separates liveness ("basic connectivity to a service and the presence of a server process"), local (disk, config) and dependency checks ("a thorough inspection of the ability of an application to interact with its adjacent systems"; {{Implementing health checks|https://builder.aws.com/content/3Ev53O39izHCtWLzp4XU6t8PC1O/implementing-health-checks}}). Kubernetes has liveness, readiness and startup probes (startup holds the others off while a model server loads weights); defaults: every 10 s, 1 s timeout, 3 failures to fail, 1 success to pass ({{Kubernetes docs|https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/}}).

What each failure does decides what each probe may check

Kubernetes: "Incorrect implementation of liveness probes can lead to cascading failures"; "the liveness probe passes when the app itself is healthy, but the readiness probe additionally checks that each required back-end service is available." AWS: "when all servers fail health checks at the same time, the load balancer fails open, allowing traffic to all servers"; Envoy's 10% ejection cap is the same idea.

Three outage patterns. Liveness that checks the database: a slow minute fails every pod, all restart, and the stampede (cold caches, new connections) keeps the database down. Every host unhealthy at once: the problem is shared, so removing every host guarantees an outage (Meta's October 2021 outage in the root's Case files: a health rule correct for one site withdrew every data center). A /health cheaper than real work: 200 while real requests fail is gray failure by design; pair it with user-side SLIs.

11. Deployment safety: most outages are changes

"SRE has found that roughly 70% of outages are due to changes in a live system"; the remedies are "progressive rollouts", "quickly and accurately detecting problems" and "rolling back changes safely when problems arise" ({{SRE book, ch. 1|https://sre.google/sre-book/introduction/}}). A change is code, config, flags, model versions, prompts, dependency upgrades and infrastructure. The lever is blast radius: a canary releases to a small slice first, and if a bad build fails 20% of requests, a 5% canary gives "a 1% overall error rate" ({{SRE workbook, Canarying releases|https://sre.google/workbook/canarying-releases/}}); it should be "sizeable and last long enough to be representative", and "We strongly advise running only one canary deployment at a time."

Waves, each baked before the next

AWS deploys first to a "one-box" stage ("a single virtual machine or single container"), then in waves of increasing size: "A typical pipeline waits at least one hour after each one-box stage, at least 12 hours after the first regional wave" ({{Liguori, Automating safe, hands-off deployments|https://builder.aws.com/content/3ErTKQOTKc5NIw031UePBPxTQ6I/automating-safe-hands-off-deployments}}). The wait is bake time; a high-severity alarm is used "to page the oncall engineer and to automatically roll back the service if a deployment is in progress" (automatic rollback: roll back first, debug later).

Feature flags ship code switched off and turn it on separately. Fowler and Hodgson's four kinds: release toggles (latent code "which may never be turned on"), experiment toggles (A/B tests), ops toggles ("disable or degrade that feature quickly in production"), permissioning toggles ({{Feature Toggles|https://martinfowler.com/articles/feature-toggles.html}}). A flag flip is itself a change. Config is code: the root's Case files hold four outages from config or content pushed everywhere at once: Cloudflare's November 2025 proxy crash from a doubled feature file, Cloudflare's 2026 follow-up that now rolls config out like code, CrowdStrike's July 2024 content update that crashed 8.5 million PCs, and Knight Capital's 2012 deploy that reached seven of eight servers. Model and prompt changes (shadow traffic, canaries judged by evals, A/B tests) are {{Production eval engineering|n:3c65c17b0d0d81b39ad9e96193d21adc}}'s.
