Idempotency: making a retry safe

An operation is idempotent if doing it twice has the same effect as doing it once: "set the title to X" is, "append a message" and "charge $20" are not. HTTP defines GET, PUT and DELETE as idempotent and POST as not (RFC 9110 §9.2.2). The problem a retry creates: when a call times out, the client cannot tell whether the server never got it or did the work and the reply was lost. The fix is an idempotency key: the client makes up a unique ID for one intended action and sends it with every attempt; the server stores the key with the result and, on a repeat, returns the stored result instead of acting again ({{Brandur Leach, Stripe, 2017|https://stripe.com/blog/idempotency}}). The parent root's Step 4 animates the double charge it prevents. How to build it in an API (where to store keys, the race between two attempts with the same key, expiry, what to return when a key is reused with a different body) belongs to {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}; how queues and consumers deduplicate belongs to {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}.

Retries hidden inside a client library are the easy ones to miss. Jepsen found in 2024 that the etcd Java client "jetcd incorrectly retries non-idempotent requests which may have actually succeeded", which "allows transactions to execute multiple times, or to appear to fail but actually succeed"; the fix offered was to disable its retries ({{Kingsbury, Jepsen, jetcd 0.8.2, 2024-08-08|https://jepsen.io/analyses/jetcd-0.8.2}}; carried from the {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}} page). Read what your client libraries retry.

Reliability rule: no automatic retry of a non-idempotent call without a key. For an LLM call, a retry is idempotent in effect (you pay twice, nothing else changes) unless the call has side effects such as tool calls that send email; those need keys at the tool.

Circuit breakers: stop calling what is broken

Timeouts bound how long each call to a sick dependency wastes; a circuit breaker stops making the calls. It wraps a dependency and watches outcomes: "Once the failures reach a certain threshold, the circuit breaker trips, and all further calls to the circuit breaker return with an error, without the protected call being made at all" ({{Fowler, 2014|https://martinfowler.com/bliki/CircuitBreaker.html}}). Michael Nygard popularised it in the book Release It! (Fowler credits him). Three states:

ClosedNormal. Calls go through; outcomes are counted in a sliding window.
→
OpenFailure rate crossed the threshold. Calls fail at once (or go to a fallback) for a wait period.
→
Half-openAfter the wait, a few trial calls go through. If they succeed, close; if not, open again.

What it buys: callers stop waiting a full timeout per call, workers are freed at once, the dependency gets breathing room to recover, and the fallback (a smaller model, a cached answer) runs immediately instead of after the timeout.

History in one paragraph. Netflix's Hystrix made breakers mainstream in Java; its README now says "Hystrix is no longer in active development, and is currently in maintenance mode", that Netflix would use "open and active projects like resilience4j for new internal projects", and that its "focus has shifted towards more adaptive implementations that react to an application's real time performance rather than pre-configured settings" ({{Hystrix README, 2018-11-19|https://raw.githubusercontent.com/Netflix/Hystrix/master/README.md}}). Today the same protection often lives outside the application, in a proxy such as Envoy, configured once for every service.

Envoy's "circuit breakers" are not Fowler's
Envoy calls its limits circuit breakers, but they are "fully distributed (not coordinated)" caps on concurrency per upstream cluster: by default at most 1,024 connections, 1,024 pending requests, 1,024 parallel requests and 3 parallel retries ({{Envoy docs|https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/circuit_breaking}}). That is a bulkhead. The closest thing to a breaker in Envoy is outlier detection, which ejects one bad host from the pool: after 5 consecutive 5xx, checked every 10 s, ejected for 30 s times the number of ejections, never more than 10% of the cluster at once ({{outlier detection API|https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/cluster/v3/outlier_detection.proto}}). The 10% cap is the important part: it stops a bad health signal from ejecting everything.
What breakers cost, and when not to use one
A breaker rejects calls that might have worked, and adds a mode that only appears during failures. Brooker argues breakers "introduce modal behavior into systems that can be difficult to test" and prefers the retry token bucket for that reason (Builders' Library). Do not put one breaker in front of a dependency made of many independent hosts or tenants (one bad shard would open the breaker for all; use outlier detection or a breaker per host); do not use one on low-traffic calls where 5 failures are noise; and decide what the open state returns, or an open breaker is just a faster outage.

Bulkheads: one leak does not sink the ship

A bulkhead splits capacity into separate pools so that one consumer cannot take it all: "Isolate the elements of an application into pools so that if one element fails, the others continue to function", named after the watertight compartments of a ship's hull ({{Azure Architecture Center|https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead}}). For our chat API: give model-provider calls at most 30 of the 50 workers and a separate connection pool, so that a provider stall leaves 20 workers for login, history and billing. The same idea at larger scale is cell or shard isolation: the root's Case files include Shopify's "pods", many small isolated copies of the platform so one shop's bad day stays theirs. The cost is idle capacity, since a pool cannot borrow from its neighbour; the mistake is pools so small they fail under normal peaks.

Load shedding and admission control: say no early

When more work arrives than a service can finish, something must give. A queue that grows without limit turns overload into latency, then into timeouts, then (with retries) into a metastable failure. Load shedding rejects the excess on purpose, cheaply and early, so the work you accept still succeeds. The quantity to protect is goodput: "the subset of the throughput that is handled without errors and with low enough latency for the client to make use of the response"; "If load shedding is working, goodput will remain steady even as offered throughput increases well beyond the scaled capabilities of the service" ({{Yanacek, Builders' Library|https://builder.aws.com/content/3Eun1EEyX6p2e3VYNyRLSJzLuMV/using-load-shedding-to-avoid-overload}}).

  • Bound every queue. The SRE book: "it is usually better to have small queue lengths relative to the thread pool size (e.g., 50% or less), which results in the server rejecting requests early when it can't sustain the rate of incoming requests" (ch. 22). In the measured experiment, a queue of 8 was the fix.
  • Reject cheaply. A rejection that costs as much as the work saves nothing; reject before parsing the body or calling anything (Yanacek notes that even iptables connection limits "can reject excess connections far more cheaply than any server process").
  • Drop work nobody waits for. If the deadline has passed, skip it ("it can skip doing the rest of the work", same essay).
  • Shed by priority. Google tags each request with a criticality, from CRITICAL_PLUS ("the most critical requests") to SHEDDABLE ("frequent partial unavailability and occasional full unavailability is expected"), provisions capacity for the critical classes, and sheds from the bottom ({{SRE book, ch. 21|https://sre.google/sre-book/handling-overload/}}). Stripe reserves "a fraction of our infrastructure for critical requests. If our reservation number is 20%, then any non-critical request over their 80% allocation would be rejected with status code 503" ({{Tarjan, Stripe, 2017|https://stripe.com/blog/rate-limiters}}). For our chat product: paid users before free, interactive chat before batch summarisation.
  • Adapt the limit. Instead of a fixed concurrency limit, measure it. Netflix's concurrency-limits library treats the limit like a TCP congestion window and uses Little's law, "Limit = Average RPS * Average Latency" ({{README|https://raw.githubusercontent.com/Netflix/concurrency-limits/master/README.md}}); its gradient algorithm shrinks the limit as latency rises above the no-load latency ({{Netflix, 2018, archived|https://web.archive.org/web/2019id_/https://medium.com/@NetflixTechBlog/performance-under-load-3e6fa9a60581}}). Google's clients throttle themselves too, rejecting locally with probability max(0, (requests − K × accepts) / (requests + 1)), K = 2 (SRE book, ch. 21).

Graceful degradation and brownouts

Graceful degradation "takes the concept of load shedding one step further by reducing the amount of work that needs to be performed" (SRE book, ch. 22): instead of refusing, serve a cheaper answer, "responses that are not as accurate as or that contain less data than normal responses, but that are easier to compute" (ch. 21). A brownout is the deliberate version under load: switch off optional features (Amazon's load-shedding essay uses the word for the overload state itself). Decide the ladder in advance; for our chat assistant:

FullLarge model, retrieval, tools
→
LighterSmaller or other provider's model
→
LeanerNo retrieval, shorter context
→
CachedA cached answer for common questions
→
Honest error"Busy, try in a minute", fast

Each rung needs a switch an operator can flip in seconds (an ops toggle or kill switch, {{Fowler and Hodgson, Feature Toggles|https://martinfowler.com/articles/feature-toggles.html}}) and a test. The SRE book's advice for code that only runs in emergencies: run "a small subset of servers near overload in order to exercise this code path". Do not degrade where a wrong answer is worse than none (a payment, a medical dosage).
