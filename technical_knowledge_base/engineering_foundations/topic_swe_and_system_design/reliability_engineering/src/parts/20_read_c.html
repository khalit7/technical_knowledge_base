6. Idempotency: making a retry safe

An operation is idempotent if doing it twice equals doing it once ("set the title" is; "append a message" and "charge $20" are not; HTTP defines GET, PUT and DELETE as idempotent and POST as not, RFC 9110 §9.2.2). After a timeout the client cannot tell "never arrived" from "done, reply lost", so a retry of a non-idempotent call needs an idempotency key: a client-made ID sent with every attempt, stored by the server with the result, so a repeat returns the stored result instead of a second charge ({{Brandur Leach, Stripe, 2017|https://stripe.com/blog/idempotency}}). AWS does the same with "client request tokens", and returns an error if the same token arrives with different parameters ({{Featonby, Builders' Library|https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/}}). Building it (storage, the race between two attempts, expiry, a reused key with a different body) is {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}}' (section 4); why exactly-once is an end-to-end property is {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}} section 9; consumers deduplicating is {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}'s.

The reliability rule: no automatic retry of a non-idempotent call without a key, and read what your client libraries retry: Jepsen found the etcd Java client "jetcd incorrectly retries non-idempotent requests which may have actually succeeded" ({{Kingsbury, Jepsen, 2024-08-08|https://jepsen.io/analyses/jetcd-0.8.2}}). An LLM call is idempotent in effect (you pay twice) unless it has side effects such as tool calls that send email; those need keys at the tool.

7. Circuit breakers: stop calling what is broken

Timeouts bound how long each call to a sick dependency wastes; a circuit breaker stops making the calls: "Once the failures reach a certain threshold, the circuit breaker trips, and all further calls to the circuit breaker return with an error, without the protected call being made at all" ({{Fowler, 2014|https://martinfowler.com/bliki/CircuitBreaker.html}}, crediting Michael Nygard's Release It!).

Fig. 5 runs the after design of section 8's before and after (a 100 ms timeout, a breaker that opens at 50% failures over the last 20 calls, waits 2 s and tries 5 calls, a smaller fallback model) through the same 3 s provider slowdown, in the page's simulation engine.

  1. Closed: calls go through. The breaker counts outcomes in a sliding window: here the last 20 calls (resilience4j's default: at least 50% of the last 100 calls). Before the slowdown every call succeeds in 25 ms.
  2. Failures fill the window. At second 10 the provider takes 3 s per call, so each call fails at its 100 ms timeout. Once at least half of the last 20 calls failed, the breaker trips.
  3. Open: fail fast. For a wait period (2 s here; 60 s by default in resilience4j) every call returns at once, answered by the fallback, without calling the provider. What it buys: no full timeout per call, workers freed at once, breathing room for the dependency, and the fallback runs immediately. In this run the breaker refused 315 calls, and 336 requests in all were answered by the fallback.
  4. Half-open: a few trial calls. After the wait, 5 trial calls go through (resilience4j: 10). While the provider is still slow they fail and the breaker opens again; a trial that fails sends it back to Open. It was open for 6.0 s in all, flickering through half-open every 2 s.
  5. Closed again. Once the provider recovers at second 15, the trials pass and the breaker closes; full answers return. Not one request failed in the whole run, against 403 without the defences (Fig. 1).
Envoy's "circuit breakers" are not Fowler's
Envoy's are "fully distributed (not coordinated)" concurrency caps per upstream cluster: by default 1,024 connections, 1,024 pending requests, 1,024 parallel requests and 3 parallel retries ({{Envoy docs|https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/circuit_breaking}}). That is a bulkhead. Envoy's closest thing to a breaker is outlier detection, which ejects one bad host: after 5 consecutive 5xx, checked every 10 s, ejected for 30 s times the number of ejections, never more than 10% of the cluster at once ({{outlier detection API|https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/cluster/v3/outlier_detection.proto}}). The 10% cap stops a bad health signal from ejecting everything.

Costs and when not to. A breaker rejects calls that might have worked and adds a mode that appears only during failures; Brooker argues breakers "introduce modal behavior into systems that can be difficult to test" and prefers the retry token bucket. Do not put one breaker in front of many independent hosts or tenants (one bad shard opens it for all; use outlier detection or a breaker per host), nor on low-traffic calls where 5 failures are noise; and decide what Open returns, or an open breaker is just a faster outage.

8. Overload: bulkheads, load shedding, degradation

A bulkhead splits capacity into pools so one consumer cannot take it all: "Isolate the elements of an application into pools so that if one element fails, the others continue to function" ({{Azure Architecture Center|https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead}}). For our chat API: model-provider calls get at most 30 of the 50 workers and their own connection pool, so a provider stall leaves 20 for login, history and billing. At larger scale it is cell isolation (the root's Case files: Shopify's "pods", so one shop's bad day stays theirs), one way to shrink blast radius. The cost is idle capacity; the mistake is pools too small for normal peaks.

  1. One shared pool. The 20 workers of the before design (end of this section) serve both kinds of request: 50 a second send a message and call the provider, 50 load history (5 ms of our own work).
  2. The provider slows; everything fails. At 3 s per call, message requests take all 20 of 20 workers; history loads queue behind them, and 175 of them fail although they never touch the provider.
  3. Two pools. Split the same 20 workers: 10 only for requests that call the provider, 10 for everything else (the engine run once per pool, 50 requests a second each).
  4. The same slowdown, contained. The provider pool fills (10 of 10) and 242 message requests fail; the other pool never notices: 0 of 2,053 history loads fail.
  5. What it costs, and what it does not fix. History needs about a quarter of one worker (50 a second × 5 ms), so its pool sits mostly idle; that idle capacity is the price. The provider pool still fails its own requests: bounding the wait (timeout, breaker, fallback; Fig. 5) is what saves those.

Load shedding and goodput

When more work arrives than a service can finish, a queue that grows without limit turns overload into latency, then timeouts, then (with retries) a metastable failure. Load shedding rejects the excess early and cheaply so accepted work still succeeds. The quantity to protect is goodput: "the subset of the throughput that is handled without errors and with low enough latency for the client to make use of the response" ({{Yanacek, Builders' Library|https://builder.aws.com/content/3Eun1EEyX6p2e3VYNyRLSJzLuMV/using-load-shedding-to-avoid-overload}}).

  • Bound every queue: "it is usually better to have small queue lengths relative to the thread pool size (e.g., 50% or less)" (SRE book, ch. 22). In the measured storm a queue of 8 was the fix.
  • Reject cheaply and drop expired work: reject before parsing the body or calling anything (even iptables limits "can reject excess connections far more cheaply than any server process"); if the deadline has passed, "it can skip doing the rest of the work" (Yanacek).
  • Shed by priority: Google tags requests from CRITICAL_PLUS to SHEDDABLE and sheds from the bottom ({{SRE book, ch. 21|https://sre.google/sre-book/handling-overload/}}); Stripe reserves "a fraction of our infrastructure for critical requests" (20%: non-critical traffic over its 80% gets 503, {{Tarjan, 2017|https://stripe.com/blog/rate-limiters}}). For us: paid before free, interactive chat before batch summaries.
  • Adapt the limit to measured latency instead of fixing it (details below).
Adaptive concurrency limits and client-side throttling (Netflix, Google)

Netflix's concurrency-limits treats it like a TCP congestion window with Little's law, "Limit = Average RPS * Average Latency" ({{README|https://raw.githubusercontent.com/Netflix/concurrency-limits/master/README.md}}), shrinking it as latency rises above the no-load latency ({{Netflix, 2018, archived|https://web.archive.org/web/2019id_/https://medium.com/@NetflixTechBlog/performance-under-load-3e6fa9a60581}}). Google's clients throttle themselves, rejecting locally with probability max(0, (requests − K × accepts) / (requests + 1)), K = 2 (ch. 21).

Past capacity, an unbounded queue's goodput collapses; a bounded one holds

The measured experiment's service (4 slots of 28 ms, so 143 calls a second; 100 ms client timeout; no retries, no slowdown), run by the Resilience lab engine at each load. At 200 a second: 0.7 against 143.1 good answers a second. Yanacek: "If load shedding is working, goodput will remain steady even as offered throughput increases well beyond the scaled capabilities of the service".

Graceful degradation

Graceful degradation goes further: serve "responses that are not as accurate as or that contain less data than normal responses, but that are easier to compute" (ch. 21). A brownout switches optional features off under load (Amazon's load-shedding essay uses the word for the overload state itself). Decide the ladder in advance:

FullLarge model, retrieval, tools
→
LighterSmaller or other provider's model
→

Each rung needs a switch an operator can flip in seconds (an ops toggle or kill switch, {{Fowler and Hodgson, Feature Toggles|https://martinfowler.com/articles/feature-toggles.html}}) and a test: code that only runs in emergencies is the least tested you own, so run "a small subset of servers near overload in order to exercise this code path" (SRE book). Do not degrade where a wrong answer is worse than none (a payment, a dosage).

Before and after: one slowdown, two designs

Same event through two versions of our chat API: half the requests need the provider (send a message), half do not (load history); 20 worker slots; users give up after 2 s; at second 10 the provider takes 3 s per call instead of 25 ms, for 5 seconds. Before: no timeout on the provider call, no breaker, unbounded queue. After: 100 ms timeout, a breaker (opens at 50% failures over the last 20 calls, waits 2 s, tries 5 calls), a fallback answer (a smaller model) and a queue bounded at 40. Watch the worker strip: in Before, history loads fail although they never touch the provider. Each step plays a stretch of seconds.

  1. Seconds 7 to 9: normal traffic. 100 requests a second: half send a message (need the provider, 25 ms), half load history (5 ms of our own work). 20 workers are plenty; nothing waits.
  2. Second 10: the provider slows to 3 s per call. With no timeout, each message request holds a worker for 3 s. At 50 such requests a second, all 20 workers are stuck within half a second.
  3. Seconds 11 to 14: the cascade. Every worker waits on the provider, so history loads, which never needed it, queue behind them too. The queue grows by about 100 a second and everyone waits past 2 s.
  4. Second 15: the provider recovers. Calls started before second 15 still take 3 s, and the queue holds hundreds of requests whose users already gave up; we still process them.
  5. Seconds 16 to 21: draining. The backlog is worked off, mostly for users who left; then service is normal again.
  6. Totals. Before: 89.8% of all requests answered in time; 403 failed, 175 of them history loads that never needed the provider. Switch to After to run the same slowdown with the defences on.
  1. Seconds 7 to 9: normal traffic. The same 100 requests a second; nothing waits.
  2. Second 10: timeouts, then the breaker. Calls now hit the 100 ms timeout. After 20 calls with at least half failing, the breaker opens and message requests get the fallback model at once.
  3. Seconds 11 to 14: contained. Workers are free: history loads are untouched, message requests get the fallback model. Every 2 s the breaker lets 5 trial calls through; they time out, so it opens again. The queue never forms.
  4. Second 15: the provider recovers. The next half-open trial succeeds and the breaker closes; full answers return.
  5. Seconds 16 to 21: normal. Nothing to drain: nothing piled up.
  6. Totals. After: 100% of all requests answered in time (91.5% with the full model); 0 failed. Compare with Before: the same slowdown, no user saw an error.
