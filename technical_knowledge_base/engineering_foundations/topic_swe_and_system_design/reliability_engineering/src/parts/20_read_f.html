14. LLM calls: what is different

Every mechanism above applies to a model provider, with four differences that change the numbers.

  • The provider is the weakest link and you do not control it. At two to three nines (section 1), it sets the chat API's ceiling unless the call is optional: a fallback rung (another provider, a smaller model, a cached answer) is what lifts availability above the provider's. Routing, cooldowns and fallback chains across providers are {{Gateways and routing|n:3f15c17b0d0d81e4a964c129a3e520ae}}'s; this page's job is the breaker that decides when to use them and the test that proves they work.
  • Overload has its own codes. Anthropic's API returns 529 overloaded_error, which "can occur when the API experiences high traffic across all users", separate from 429 for your own rate limit ({{Anthropic API errors|https://docs.claude.com/en/api/errors}}); OpenAI returns 503 with code server_is_overloaded: "Follow the Retry-After header when it's present" ({{OpenAI error codes|https://platform.openai.com/docs/guides/error-codes}}). A 529 or 503 means the dependency is not healthy, which is exactly when a retry budget and a breaker should stop retrying.
  • SDKs retry for you. Anthropic's SDK "automatically retries transient failures (such as connection errors, rate limits, and 5xx server errors) with exponential backoff, twice by default" (same page). Wrap it in your own 3 attempts and one call becomes up to 9; set max_retries so only one layer retries.
  • Latency is long and streamed. A reply can take tens of seconds, and when "receiving a streaming response over server-sent events (SSE), an error can occur after the API returns a 200 response" (Anthropic). Anthropic advises streaming or batches for requests "especially those over 10 minutes", since "Some networks might drop idle connections". So a total timeout is the wrong tool:
One long reply under three timeout designs

Illustrative times: first token at 1.5 s, a healthy reply streaming to 48 s. A time-to-first-token timeout catches a provider that never starts; an idle timeout between tokens catches a stall; neither kills a long healthy answer. Long-tail latency is also why hedging is rare here: a second copy doubles GPU cost.

Retries cost money and quota. A retried completion is billed again and spends tokens-per-minute quota, so a retry storm against a provider can turn into a 429 storm on your own account. Budget retries (section 4), cap concurrency per provider (a bulkhead), and alert on the share of replies served by fallback rungs (the quality SLI of section 12).

15. Chaos testing: when it pays

Fallbacks, breakers and failovers run only during failures, so they rot unless failure is made on purpose. "Chaos Engineering is the discipline of experimenting on a system in order to build confidence in the system's capability to withstand turbulent conditions in production" ({{Principles of Chaos Engineering, March 2019|https://principlesofchaos.org/}}). Its principles: build a hypothesis around steady-state behaviour, vary real-world events, run experiments in production ("Chaos strongly prefers to experiment directly on production traffic"), automate them to run continuously, and minimise blast radius ("Experimenting in production has the potential to cause unnecessary customer pain"). Netflix's Chaos Monkey "randomly terminates virtual machine instances and containers that run inside of your production environment" ({{README|https://github.com/Netflix/chaosmonkey}}), by default only on weekdays between 9 and 15 local time ({{configuration|https://github.com/Netflix/chaosmonkey/blob/master/docs/Configuration-file-format.md}}), when engineers are there to watch.

When it pays: once the defences exist and the SLIs can see the effect (an experiment with no steady-state metric proves nothing), when there is redundancy to test (replicas, a second provider), and when the error budget can absorb the experiment. Start with a game day in office hours on staging or a canary slice: kill the provider connection and watch whether the breaker opens and the fallback rung serves. When it does not: a single-instance service with no fallback (the answer is known: it goes down), a team without on-call or rollback, or a budget already spent. Fault injection in tests (a mock dependency that hangs or returns 529) catches most of the same bugs earlier and cheaper; testing practice is {{Testing and quality|n:3c65c17b0d0d81548848e2ebdd2f63ee}}'s.

The habits behind the table, as the old Distributed Systems Basics page put them: make every mutation idempotent, bound every queue, jitter every retry (and budget it), and name the failure you are defending against when you add a component. Where these live: in the client library (tenacity, resilience4j, Polly, the AWS SDKs, gRPC service config), in a sidecar or gateway (Envoy, Istio, an LLM gateway), or in the platform (Kubernetes probes, deployment controllers). A proxy gives one consistent policy; code knows what is idempotent. Many teams do both, and must then make sure only one layer retries.

Glossary (every term defined on this page)
Availability: share of time or requests the service works.
Durability: saved data stays saved.
Correctness: the answer is right, not just returned.
Open system: new work arrives whatever the system does.
Trigger / sustaining effect: what pushes a system into a bad state / what keeps it there.
Percentile: p99.9 is the latency 99.9% of calls beat.
Timeout, deadline, deadline propagation: longest wait; absolute end time; passing the remaining time down.
Retry, exponential backoff, jitter: send again; wait longer each time; randomise the wait.
Retry budget, token bucket: retries capped at a share of traffic; a refilling allowance.
Hedged request: a second copy sent when the first is slow.
Idempotent, idempotency key: twice equals once; a client-made ID that marks a repeat.
Circuit breaker, outlier detection: stop calling a failing dependency; eject one bad host.
Bulkhead, load shedding, goodput: separate pools; reject excess early; useful timely answers per second.
Graceful degradation, brownout, kill switch: a cheaper answer; optional features off; a flag that turns a feature off in seconds.
Rate limit: a cap per client, answered with 429; fixed window, sliding log, sliding window counter, token bucket, leaky bucket are its algorithms.
Health check, liveness / readiness: a probe; restart it / stop sending it traffic.
Canary, waves, bake time, rollback, feature flag: a small first slice; growing stages; the wait between them; back to the last good version; a switch that turns code on without a deploy.
SLI / SLO / SLA, error budget, burn rate: measure / target / contract; 100% minus the SLO; how fast it is spent (1 = exactly on time).
Incident, postmortem (blameless): an unplanned event needing coordinated response; the written account, aimed at systems not people.
