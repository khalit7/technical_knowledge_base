What pros run in production today

A starting configuration for a service like our chat API, with where each choice comes from. Tune from measurements; these are defaults to beat, not laws.

The habits behind the table, as the old Distributed Systems Basics page put them: make every mutation idempotent, bound every queue, jitter every retry (and budget it), and name the failure you are defending against when you add a component.

Where these live today: in the client library (tenacity, resilience4j, Polly, the AWS SDKs, gRPC service config), in a sidecar or gateway (Envoy, Istio, an LLM gateway), or in the platform (Kubernetes probes, deployment controllers). Putting retries, timeouts and breakers in a proxy gives one consistent policy; putting them in code gives knowledge of what is idempotent. Many teams do both, and must then make sure only one layer retries.

Common mistakes

Calling a dependency with no timeout
Library defaults (requests, gRPC) wait forever. One slow dependency then holds every worker. Set a timeout on every call, and a deadline on every request.
Retrying at every layer
Attempts multiply: 3 tries at 5 layers is 243 calls to the database. Retry at one layer and make the others fail fast.
Believing backoff and jitter prevent retry storms
They prevent synchronised waves. In an open system every failed request still makes all its attempts, so the load is the same, only later; the measured experiment did not recover with them. Cap the total with a retry budget.
Retrying non-idempotent writes
A retried "charge" or "send email" happens twice. Use idempotency keys, or do not retry.
Unbounded queues
They turn overload into latency and then into timeouts for everyone, and keep the server busy with work whose clients have gone. Bound them and reject early.
Liveness probes that check the database
A database slowdown becomes a restart of every pod. Liveness checks the process; readiness checks dependencies.
A circuit breaker with no fallback, or one breaker for a whole fleet
An open breaker without a defined answer is a faster outage; one breaker over many independent hosts lets one bad host block all of them.
Measuring availability only from inside the server
Gray failure: the server is fine, users are not (DNS, load balancer, client bugs). Measure SLIs as close to the user as possible.
Shipping config to everyone at once
Config, flags, prompts and model versions are changes. Roll them out in waves with automatic rollback, like code.
Debugging before mitigating
During an incident, undo the most recent change first and understand it later.
Postmortems that name a person
People then hide what happened and the same failure returns. Fix the system that let a normal mistake become an outage.
Untested fallbacks
Code that only runs in emergencies is the least tested you own. Exercise it on purpose, regularly.

Glossary

Availability: share of time or requests the service works.
Durability: saved data stays saved.
Correctness: the answer is right, not just returned.
Nines: 99.9% is three nines; each nine is 10x less downtime.
Open system: new work arrives whatever the system does.
Trigger: what pushes a system into a bad state.
Sustaining effect: what keeps it there after the trigger ends (often retries).
Percentile: p99.9 is the latency 99.9% of calls beat.
Timeout: the longest a caller waits before giving up.
Deadline: an absolute time after which the answer is useless.
Deadline propagation: passing the remaining time to every downstream call.
Retry: sending the same request again after a failure.
Exponential backoff: doubling the wait before each retry, up to a cap.
Jitter: randomising waits so clients do not retry together.
Retry budget: retries capped at a share of normal traffic.
Token bucket: a refilling allowance that permits bursts but caps the average.
Hedged request: a second copy sent when the first is slow.
Idempotent: doing it twice equals doing it once.
Idempotency key: a client-made ID that lets the server recognise a repeat.
Circuit breaker: stops calling a failing dependency for a while.
Outlier detection: removing one misbehaving host from a pool.
Bulkhead: separate pools so one failure cannot use all capacity.
Load shedding: rejecting excess work early and cheaply.
Goodput: useful, timely answers per second.
Graceful degradation: a cheaper answer instead of none.
Brownout: switching off optional features under load.
Kill switch: a flag that turns a feature off in seconds.
Rate limit: a cap per client, answered with 429.
Fixed window, sliding log, sliding window counter, leaky bucket: rate limiting algorithms.
Health check: a probe deciding whether a server gets traffic.
Liveness / readiness: restart it / stop sending it traffic.
Canary: a small first slice of a release.
Waves and bake time: growing rollout stages and the wait between them.
Rollback: returning to the last good version.
Feature flag: a switch that turns code on without a deploy.
SLI / SLO / SLA: the measure / the target / the contract.
Error budget: 100% minus the SLO, spent on change.
Burn rate: how fast the budget is being spent (1 = exactly on time).
Incident: an unplanned event needing coordinated response.
Postmortem (blameless): the written account, aimed at systems not people.
