3. Timeouts and deadlines: never wait forever

A timeout is the longest a caller waits before giving up and freeing what it holds (a worker, a connection, memory). Without one, a single hung dependency can hold every worker in our chat API, and requests that never needed it (loading the conversation list) fail too. Many libraries do not set one: Python requests does "not time out unless a timeout value is set explicitly" ({{docs|https://requests.readthedocs.io/en/latest/user/quickstart/}}); "By default, gRPC does not set a deadline" ({{gRPC deadlines guide|https://grpc.io/docs/guides/deadlines/}}).

Choosing the number. Too long and workers pile up behind a slow dependency; too short and you abandon calls about to succeed (and retrying them doubles the load). Marc Brooker's method at AWS: "we choose an acceptable rate of false timeouts (such as 0.1%). Then, we look at the corresponding latency percentile on the downstream service (p99.9 in this example)" ({{Builders' Library, archived|https://web.archive.org/web/2024/https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/}}). A percentile such as p99.9 is the latency 99.9% of calls beat. When p99.9 sits close to p50, "adding some padding helps us avoid small latency increases that cause high numbers of timeouts."

Measured: the tail, not the 25 ms of work, sets the timeout

The tiny service of the experiment below (4 worker slots, 25 ms per call, 100 requests a second at random) answered 2,972 requests in 30 s: p50 27.5 ms, p90 42.5 ms, p99 62.3 ms, p99.9 72.3 ms, max 77.6 ms (Apple M1 Pro, 2026-10-04, src/lab/; histogram by src/gen_lat_js.py). Brooker's rule gives about 72 ms; padded to 100 ms. Queueing makes the tail.

A deadline is absolute ("worthless after 12:00:03.200"). Passing it down every hop is deadline propagation: "The tree of RPCs emanating from an initial request will all have the same absolute deadline" ({{SRE book, ch. 22|https://sre.google/sre-book/addressing-cascading-failures/}}).

Each hop gets only the time that remains

A 10 s request budget with 7 s already spent leaves the provider call 3 s, not a fresh 10. gRPC converts "the deadline to a timeout from which the already elapsed time is already deducted", automatically in some languages and opt-in in others such as C++. Over HTTP there is no standard header (our experiment's service reads X-Deadline). A server that sees an expired deadline skips the work, because nobody is waiting (Yanacek, {{Using load shedding to avoid overload|https://builder.aws.com/content/3Eun1EEyX6p2e3VYNyRLSJzLuMV/using-load-shedding-to-avoid-overload}}).

Mistakes that matter: one timeout for the whole stack, so an inner call outlives the caller who already gave up; an outer timeout shorter than inner timeout plus retries (Envoy counts retries inside the route timeout "to avoid an exponential retry/timeout explosion", {{Envoy router docs|https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/router_filter}}); a total timeout on a streamed LLM reply ({{section 14|#s-llm}}).

Library defaults and code (httpx, the requests and gRPC advice)

httpx is the exception among Python clients: it raises after "5 seconds of network inactivity" by default and splits the timeout into connect, read, write and pool parts ({{httpx docs|https://www.python-httpx.org/advanced/timeouts/}}). The requests docs: "Nearly all production code should use this parameter in nearly all requests". gRPC without a deadline means "a client to end up waiting for a response effectively forever".

# Python, httpx 0.28: separate connect and read limits, and a per-call budget client = httpx.Client(timeout=httpx.Timeout(2.0, connect=0.5)) # 2 s read/write/pool, 0.5 s to connect remaining = deadline - time.monotonic() r = client.post(url, json=body, timeout=max(0.05, remaining)) # never more than the time left

4. Retries: when they help, and how they hurt

A retry turns a momentary failure (a reset, a restarting server, a 503 from an instance being replaced) into a success. Retry only when all three hold: the error is transient (connection errors, timeouts, 503, 429 after its Retry-After; not 400, 422, 401 or 403); the operation is safe to repeat (reads are; "charge $20" needs an {{idempotency key|#s-idem}}; gRPC retries only before reply headers: "Once the response header is received, the RPC is committed", {{gRPC retry guide|https://grpc.io/docs/guides/retry/}}); and the dependency is healthy overall: "We avoid this amplification by retrying only when we observe that the dependency is healthy" (Brooker).

Retries at every layer multiply

Brooker's five-deep stack with three tries per layer: "the load on the database will increase 243x" (35 = 243). The SRE book: attempts can reach "the product of the number of attempts at each layer" (ch. 22). In our product, 3 tries each at the app, the API and the provider's gateway turn one tap into up to 27 model calls. Hence "retry at a single point in the stack", usually the layer that knows the operation is idempotent; the others fail fast.

Backoff and jitter

Exponential backoff waits longer before each retry; jitter randomises each wait, because clients that failed together and back off by the same amounts come back together, in waves. Predict before you toggle: does jitter reduce the number of retries?

The same 20 clients, failing at the same moment, retrying 4 times (base 100 ms)

Retries per 25 ms. Illustrative, seeded; checked by src/recompute.py. Jitter flattens the waves; the count stays 80. Brooker: "none of these approaches fundamentally change the N2 nature of the work". That is why the storm below did not end with jitter alone.

Brooker's 2015 simulation ({{AWS Architecture Blog|https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/}}), with attempt counting from 0: no jitter, min(cap, base * 2 ** attempt), is "the clear loser. It not only takes more work, but also takes more time"; full jitter, random_between(0, min(cap, base * 2 ** attempt)), "uses less work, but slightly more time" and is the usual default; "Of the jittered approaches, 'Equal Jitter' is the loser" (half fixed, half random); decorrelated jitter, min(cap, random_between(base, sleep * 3)), is close to full. With 100 contending clients jitter "reduced our call count by more than half"; the 2023 update says the scheme "continues to serve as a pillar for how Amazon builds remote client libraries".

Retry budgets: capping the total

A retry budget limits retries to a share of normal traffic, so they switch themselves off when most calls fail. It is usually a token bucket: a counter that refills slowly and is spent by each retry. Google allows at most 3 attempts per request and retries only while they are under 10% of a client's requests: three attempts alone let load grow to "somewhere just below 3X"; the budget "reduces the growth to just 1.1x in the general case" ({{SRE book, ch. 21|https://sre.google/sre-book/handling-overload/}}). gRPC's throttle: each failure takes 1 token, each success adds tokenRatio, no retries while tokens ≤ maxTokens/2.

gRPC's own jitter is narrower than full jitter: each wait is the exponential value times random(0.8, 1.2) (gRFC A6). tenacity's wait_random_exponential is documented as corresponding "to the 'Full Jitter' algorithm" ({{source, 9.1.4|https://raw.githubusercontent.com/jd/tenacity/9.1.4/tenacity/wait.py}}).

Hedging is the retry for slowness rather than failure: a hedged request sends a second copy when the first is merely slow and takes whichever answers first. It fights the fan-out tail: if one call in 100 is slow and a page makes 100 calls in parallel, "63% of user requests will take more than one second" (1 − 0.99100 = 63.4%; Dean and Barroso, {{The Tail at Scale, 2013|https://www.barroso.org/publications/TheTailAtScale.pdf}}). Hedge only idempotent reads, never toward an overloaded dependency; for LLM calls it doubles GPU cost, so it is rare.

Hedging's numbers (Dean and Barroso)

Defer the second request "until the first request has been outstanding for more than the 95th-percentile expected latency", which limits extra load to about 5%. In a Google BigTable benchmark, hedging after 10 ms cut the 99.9th-percentile latency of reading 1,000 values "from 1,800ms to 74ms while sending just 2% more requests". Reducing variability itself is {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}}'s subject.

5. A retry storm, measured

Setup (code in src/lab/, Python standard library, run 2026-10-04 on an Apple M1 Pro): a real HTTP service on a local socket with 4 worker slots, each request holding a slot for 25 ms (a call through a pool of 4 connections), so about 160 requests a second. A load generator sends 100 new requests a second at random moments (open system) for 40 s, with the 100 ms client timeout chosen above and at most 3 attempts. Trigger: from second 10 to 15 each call takes 100 ms, so capacity drops to 40 a second. Like most servers, ours keeps working on a request after its client has given up. Six policies, 3 random seeds each.

Predict: which of these ends the storm once the 5-second slowdown is over?
Only the budget (and, below, a bounded queue). Backoff with jitter recovered in no seed: each request still makes its 3 attempts, only later. Skipping expired work raised useful work but every retry still had to be queued and rejected. Pick a policy above the chart to check.
Measured: the same 5-second slowdown under six retry policies

Success: share of the 4,000 logical requests answered on some attempt. Attempts per request: HTTP requests per logical request. Useful work: share of the server's completed work whose client was still waiting. Recovery: seconds after the slowdown until every later second answered at least 90% of its arrivals ("never" means not within the 25 s left). Mean of 3 seeds, with the range. Model: the {{Resilience lab|#t-lab}} engine on the same configuration and seeds.

What it shows. With timeouts and no retries the service falls behind, drains its queue and recovers. With immediate retries it never recovers: each timed-out request comes back up to twice more, about 300 attempts a second arrive at a service that can do 160, the queue grows without end, and the server answers clients who already left. The trigger lasted 5 seconds; the outage lasted until the experiment ended. Backoff with full jitter did not help at all: in an open system each request still makes its 3 attempts, so the average load is the same. What fixed it was removing work: a retry budget cut retries to almost nothing once failures dominated, and a bounded queue (shed at 8 waiting) answered the excess with an immediate 503, keeping the wait short enough for accepted requests to succeed.

Honest limits of this experiment, and how the model was checked

One laptop, Python's asyncio, a socket on the same machine, an artificial dependency (a sleep), a small scale. A sleep overshoots: {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}} measured about 1 ms per sleep on the same kind of laptop, so real utilisation may sit a few percent above the nominal figures (the measured 28 ms per call already includes it; the runs were not repeated). Real networks add delays and real services more layers. The direction of every result matches the sources and the Resilience lab's model: with the per-call time set to the measured 28 ms (25 ms of work plus about 3 ms of overhead, read from the baseline p50) and 103 ms in the slowdown, its "Measured" presets land within 2.5 points of the measured success and on the same recovery verdict for all six configurations (last column of the table). That agreement is by construction for the per-call time and independent for everything else.
