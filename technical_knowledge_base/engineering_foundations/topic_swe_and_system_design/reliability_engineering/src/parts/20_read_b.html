Timeouts and deadlines: never wait forever

A timeout is the longest a caller will wait for an answer before giving up and freeing whatever it was holding (a worker thread, a connection, memory). Without one, a single hung dependency can hold every worker in our chat API, and then requests that never needed that dependency (loading a conversation list) fail too. Many libraries do not set one for you:

  • Python requests: "By default, requests do not time out unless a timeout value is set explicitly"; the docs add "Nearly all production code should use this parameter in nearly all requests" ({{requests docs|https://requests.readthedocs.io/en/latest/user/quickstart/}}).
  • gRPC: "By default, gRPC does not set a deadline which means it is possible for a client to end up waiting for a response effectively forever" ({{gRPC deadlines guide|https://grpc.io/docs/guides/deadlines/}}).
  • httpx is the exception: it raises after "5 seconds of network inactivity" by default, and splits the timeout into connect, read, write and pool parts ({{httpx docs|https://www.python-httpx.org/advanced/timeouts/}}).

Choosing the number

Too long and workers pile up behind a slow dependency; too short and you abandon calls that were about to succeed (and, if you retry them, you double the load). Marc Brooker's method at AWS: "we choose an acceptable rate of false timeouts (such as 0.1%). Then, we look at the corresponding latency percentile on the downstream service (p99.9 in this example)" ({{Builders' Library, archived copy|https://web.archive.org/web/2024/https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/}}). A percentile such as p99.9 is the latency that 99.9% of calls beat. He adds a caveat: when p99.9 is close to p50 (the median), "adding some padding helps us avoid small latency increases that cause high numbers of timeouts."

Measured for this page
The tiny service used in the experiment below (4 worker slots, each call taking 25 ms, 100 requests a second arriving at random) answered 2,972 requests in 30 s with p50 27.5 ms, p90 42.5 ms, p99 62.3 ms, p99.9 72.3 ms, max 77.6 ms (Apple M1 Pro, 2026-10-04, src/lab/). By Brooker's rule the timeout is about 72 ms; we padded it to 100 ms. Note how far p99.9 sits from p50: waiting in the queue, not the 25 ms of work, makes the tail.

Deadlines, and passing them down

A timeout is relative ("wait 2 s"); a deadline is absolute ("this request is worthless after 12:00:03.200"). When our chat API has a 10 s budget for the whole user request and has already spent 7 s, its call to the model provider should get the remaining 3 s, not a fresh 10. Passing the deadline along every hop is deadline propagation: "a deadline is set high in the stack (e.g., in the frontend). The tree of RPCs emanating from an initial request will all have the same absolute deadline" ({{SRE book, ch. 22|https://sre.google/sre-book/addressing-cascading-failures/}}). gRPC does it by converting "the deadline to a timeout from which the already elapsed time is already deducted", automatically in some languages and opt-in in others such as C++ (gRPC deadlines guide). Over HTTP there is no standard header; teams send their own (our experiment's service reads an X-Deadline header). The payoff is on the server side: a server that sees an expired deadline can skip the work, because nobody is waiting for the answer (Yanacek, {{Using load shedding to avoid overload|https://builder.aws.com/content/3Eun1EEyX6p2e3VYNyRLSJzLuMV/using-load-shedding-to-avoid-overload}}).

# Python, httpx 0.28: separate connect and read limits, and a per-call budget client = httpx.Client(timeout=httpx.Timeout(2.0, connect=0.5)) # 2 s read/write/pool, 0.5 s to connect remaining = deadline - time.monotonic() r = client.post(url, json=body, timeout=max(0.05, remaining)) # never more than the time left
Common timeout mistakes
No timeout at all (the library default). One timeout for the whole stack, so an inner call outlives the outer caller who already gave up. An outer timeout shorter than inner timeout plus retries (the outer gives up while the inner is still retrying; Envoy counts retries inside the route timeout "to avoid an exponential retry/timeout explosion", {{Envoy router docs|https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/router_filter}}). Streaming LLM replies with a total timeout of 10 s that kills long but healthy answers: use a time-to-first-token timeout plus an idle timeout between tokens instead.

Retries: when they help, and how they hurt

Many failures are momentary: a connection reset, a server restarting, a 503 from an instance that was being replaced. A retry (sending the same request again) turns those into successes. Retry only when all three hold:

  1. The error is transient. Connection errors, timeouts, 503 (unavailable), 429 (too many requests, after the server's Retry-After time). Not 400 or 422 (the request itself is wrong and will fail again), not 401 or 403.
  2. The operation is safe to repeat. Reads are; "charge $20" is not unless it carries an idempotency key. gRPC only retries before the reply headers arrive: "Once the response header is received, the RPC is committed. No further retries will be attempted" ({{gRPC retry guide|https://grpc.io/docs/guides/retry/}}).
  3. The dependency is healthy overall. Retrying into an overloaded service adds load to the thing that is already drowning. Brooker: "We avoid this amplification by retrying only when we observe that the dependency is healthy" (Builders' Library).

Amplification across layers

If each layer retries on its own, attempts multiply. Brooker's example is a five-deep stack with three tries at each layer: "the load on the database will increase 243x" (35 = 243), "making it unlikely to ever recover". The SRE book says the same: one request "may produce a number of attempts as large as the product of the number of attempts at each layer" (ch. 22). Hence the rule "retry at a single point in the stack" (Brooker), usually the layer closest to the user or the one that knows the operation is idempotent. In our chat product, if the phone app retries 3 times, our API retries the provider 3 times and the provider's gateway retries its GPU servers 3 times, one tap becomes up to 27 model calls.

Backoff and jitter

Exponential backoff waits longer before each retry, so a struggling service sees retries thin out. Jitter randomises each wait, because clients that failed at the same moment and back off by the same amounts come back at the same moment, in waves. The formulas from Brooker's 2015 post ({{AWS Architecture Blog|https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/}}), where attempt counts retries from 0, base is the first wait and cap the longest:

VariantWait before the next tryBrooker's finding
Capped exponential, no jittermin(cap, base * 2 ** attempt)"the clear loser. It not only takes more work, but also takes more time"
Full jitterrandom_between(0, min(cap, base * 2 ** attempt))"uses less work, but slightly more time"; the usual default today
Equal jitterhalf the backoff fixed, half random"Of the jittered approaches, 'Equal Jitter' is the loser"
Decorrelated jittermin(cap, random_between(base, sleep * 3))close to full jitter

With 100 clients contending, jitter "reduced our call count by more than half". The post's 2023 update says the scheme "continues to serve as a pillar for how Amazon builds remote client libraries", and most AWS SDKs use it. One limit the post states plainly: "none of these approaches fundamentally change the N2 nature of the work" when N clients contend. Backoff spreads retries out in time; it does not reduce how many there are. That matters in the experiment below.

Retry budgets: capping the total

Hedging: a retry before the failure

A hedged request sends a second copy when the first is merely slow, and uses whichever answers first. Dean and Barroso: defer the second request "until the first request has been outstanding for more than the 95th-percentile expected latency", which limits the extra load to about 5%; in a Google BigTable benchmark, hedging after 10 ms cut the 99.9th-percentile latency of reading 1,000 values "from 1,800ms to 74ms while sending just 2% more requests" ({{The Tail at Scale, CACM 2013|https://www.barroso.org/publications/TheTailAtScale.pdf}}). Their reason it matters: if one call in 100 is slow and a page needs 100 calls in parallel, "63% of user requests will take more than one second" (1 − 0.99100 = 63.4%). Hedge only idempotent reads, and never toward a dependency that is overloaded rather than unlucky; for LLM calls hedging doubles GPU cost, so it is rare.

A retry storm, measured

To see a metastable failure rather than read about one, this page ran one. The setup (code in src/lab/, Python standard library only, run 2026-10-04 on an Apple M1 Pro): a real HTTP service on a local socket with 4 worker slots; each request holds a slot for 25 ms (think: a call to a dependency through a pool of 4 connections), so it can serve about 160 requests a second. A load generator sends 100 new requests a second at random moments (an open system: arrivals do not wait for answers) for 40 s, with the 100 ms client timeout chosen above and at most 3 attempts. The trigger: from second 10 to second 15 the dependency slows to 100 ms per call, so capacity drops to 40 a second. Like most real servers, ours keeps working on a request even after its client has given up. Each configuration ran with 3 random seeds.

Measured: the same 5-second slowdown under six retry policies

Success: share of the 4,000 logical requests that got an answer on some attempt. Attempts per request: how many HTTP requests each logical request caused. Useful work: share of the server's completed work whose client was still waiting. Recovery: seconds after the slowdown ended until every later second answered at least 90% of its arrivals ("never" means not within the 25 s left). Mean of 3 seeds, with the range. Model: the Resilience lab engine on the same configuration and seeds.

What it shows. With timeouts and no retries the service falls behind during the slowdown and then drains its queue and recovers. With immediate retries it never recovers: every request that times out comes back up to twice more, so about 300 attempts a second arrive at a service that can do 160; the queue grows without end, the wait in it is far beyond the 100 ms timeout, and the server spends its time answering clients who already left. That is a metastable failure: the trigger lasted 5 seconds, the outage lasted until the experiment ended. Exponential backoff with full jitter did not help at all here, which surprises most people. Jitter fixes synchronised waves and contention among a fixed set of clients; in an open system each request still makes its 3 attempts, only later, so the average load is the same. What fixed it was removing work: a retry budget cut retries to almost nothing once failures dominated, and a bounded queue (shed at 8 waiting) answered the excess with an immediate 503, keeping the wait short enough that accepted requests succeeded. Passing the deadline to the server (skip expired work) raised the share of useful work but did not end the storm, because every retry still had to be queued and rejected.

Honest limits of this experiment
One laptop, Python's asyncio, a socket on the same machine, an artificial dependency (a sleep), and a small scale. The work is an asyncio.sleep, and a sleep overshoots: {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}} measured about 1 ms per sleep on the same kind of laptop, so real utilisation may sit a few percent above the nominal figures here (the measured 28 ms per call below already includes it; the runs were not repeated). Real networks add their own delays and real services have more layers. The direction of every result matches the sources above and the model in the Resilience lab, which was checked against these runs: with the per-call time set to the measured 28 ms (25 ms of work plus about 3 ms of overhead, read from the baseline p50) and 103 ms in the slowdown, its "Measured" presets land within 2.5 points of the measured success and on the same recovery verdict for all six configurations (last column of the table). That agreement is by construction for the per-call time and independent for everything else.
