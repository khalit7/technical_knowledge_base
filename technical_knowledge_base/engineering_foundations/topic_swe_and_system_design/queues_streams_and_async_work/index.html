The idea in one screen

Handing work to a queue or a log means it will be delivered at least once, never exactly once, so you make its effect happen once (an idempotent consumer, an outbox for the hand-off itself) and you watch the age of the oldest message, because a queue hides overload instead of removing it.

Three places where handed-off work goes wrong, and the fix for each

1The hand-off. Saving a row and publishing its event are two writes with no shared transaction; a crash between them loses the event. Fix: the transactional outbox.
2The acknowledgement. A worker that dies after the work but before the ack gets the message back, and the work runs twice. Fix: an idempotent consumer keyed on a producer-assigned id.
3The rate. If arrivals exceed what workers can finish (λ > C/S), nothing errors: the backlog just grows. Fix: backpressure, workers sized by Little's law, an alarm on message age.

Measured on a real Postgres later on this page: 1,000 jobs with a 5% crash chance were done 1,046 to 1,053 times, and exactly 1,000 with a unique key on the job id; a naive dual write lost 19 to 28 events per 500 orders, the outbox none.

You need: nothing beyond a web service and a database transaction. The parent root's Step 3 ("Slow work leaves the request path", Topic: swe-and-system-design) is the five-minute version. Why "exactly once" is an end-to-end property of any distributed system, and how Kafka's partitions are replicated, are on Distributed systems fundamentals; this page is the queue and stream machinery.

Why async: accept now, do later

The request path is everything between a request arriving and its response. Work done on it makes every user wait and holds one of the server's limited request slots: on the parent root, 5 PDF uploads among 30 chat messages made chat messages wait up to 3 seconds that should have waited none (the root's Step 3, Topic: swe-and-system-design). The fix separates accepting work from doing it: the handler writes a message (a small record such as {"type": "embed_document", "doc_id": 981}) somewhere durable and answers at once. The producer writes messages, the consumer or worker handles them, the broker stores them in between, and to acknowledge (ack) is to tell the broker "done".

Over HTTP the hand-off is 202 Accepted, "the request has been accepted for processing, but the processing has not been completed" (RFC 9110 §15.3.3), with a job id to poll or a later webhook. Designing those endpoints, and handing work to a background task inside one service (and what that loses when the process dies), is Building a backend API's; this page starts where the work crosses into a broker.

Goes async on the chat assistant

  • Embedding an uploaded document (tens of seconds)
  • Generating a conversation title after the first reply
  • Usage metering and billing events
  • Receipts, e-mails, outgoing webhooks to customers
  • Nightly evaluation runs, re-embedding the corpus (the worked example)
  • Long agent tasks that run for minutes

Stays on the request path

  • The reply the user is reading (stream it instead)
  • Anything the next screen needs to show correctly
  • Checks that must reject the request (auth, rate limits, validation)
  • Writes the user must see confirmed (saving the message itself)

What async costs: the result is late, so the product must show progress and handle "not ready yet"; failures happen where no user sees them, so they need their own alerts; jobs can run twice; and the broker is one more system to run. A rule of thumb (opinion, not a sourced rule): make work async when it is slow, can fail and be retried independently, or fans out to several consumers; keep it synchronous when the caller needs the result to continue.

Two shapes: queues and logs

Most confusion about "queues versus Kafka" is confusion between two shapes of broker. Decide by who reads a message: one worker (a job: "embed document 981") or several systems (a fact: "order 42 was placed", read by e-mail, warehouse and analytics, each at its own pace).

A queue forgets what was done; a log remembers, and each reader keeps its own place

Queue: workers that share it are competing consumers; each message goes to one of them and is deleted on ack, so progress is tracked per message (SQS, RabbitMQ queues, a Postgres jobs table, Redis lists behind Celery or RQ). Log: a log (a stream) keeps every message for a retention period whether read or not; each reader remembers its position, the offset, so many readers see every message and a new one can replay from the start (Kafka, Kinesis Data Streams, Redpanda, Pulsar, Redis Streams, RabbitMQ Streams). A message queue is the first shape.

Kafka states it: "events are not deleted after consumption. Instead, you define for how long Kafka should retain your events through a per-topic configuration setting" (Kafka 4.3 introduction); the default retention is 7 days (retention.ms, topic configs). RabbitMQ added the log shape for the same reason: "Streams model an append-only log of messages that can be repeatedly read until they expire" (RabbitMQ Streams). Choose a queue for jobs (per-message acks, retries and dead-lettering, never wanted again once done); choose a log for facts several systems care about, or when you may need to replay history (rebuild a search index, backfill a new service), and pay with partitions to plan, offsets to manage and usually a cluster to run.

Kafka: partitions, keys, offsets and consumer groups

A topic is a named log (orders, chat_messages), split into partitions: independent logs on different brokers, read in parallel, each message numbered by its offset. A message's key is hashed to pick its partition, so "if the key chosen was a user id then all data for a given user would be sent to the same partition" (Kafka design). Two rules follow, and the widget shows both:

  • Ordering is per partition only. Kafka "guarantees that any consumer of a given topic-partition will always read that partition's events in exactly the same order as they were written" (Kafka introduction); across partitions there is no order. Key by what must stay in order: a user's messages, an order's state changes.
  • A consumer group gets one consumer per partition. Each partition "is consumed by exactly one consumer within each subscribing consumer group at any given time" (Kafka design). So a group never uses more consumers than partitions, and a different group (analytics) receives every message again.

More consumers than partitions sit idle; a new partition count moves keys

Twelve chat messages from four users, keyed by user id, placed with Kafka's real default partitioner for keyed records, murmur2(key bytes) mod partitions (a port of Kafka's Utils.murmur2 that reproduces the six test vectors in Kafka's UtilsTest). Partitions are dealt to consumers round-robin for the picture; the real assignor may pair them differently. Message order illustrative

Adding partitions to a keyed topic re-hashes keys onto new partitions, so per-key ordering breaks across the change for messages already written.

Offsets, commits and the two timers. A consumer saves its position by committing offsets. By default the client does it in the background: enable.auto.commit is true, every 5 seconds (consumer configs), which is why "when do I commit relative to the work?" (the next section) is decided for you unless you take it over. A consumer is declared dead, and its partitions handed on in a rebalance, after session.timeout.ms (45 s without heartbeats) or max.poll.interval.ms (5 minutes between calls to poll(), after which "the consumer is considered failed and the group will rebalance"). That second timer is Kafka's visibility timeout: a job slower than it loses its partition mid-work.

Lag is the partition's latest offset minus the group's committed offset: the log's queue depth. Divide by the consume rate to get it in seconds, the number users feel (kafka-consumer-groups.sh --describe shows "how far behind the end of the log they are", Kafka operations).

Kafka as a queue, now. One partition per consumer made Kafka a poor job queue (one slow message holds up its partition; parallelism stops at the partition count). Kafka 4.2 (February 2026) made share groups (KIP-932) production-ready (Kafka 4.2 release): more consumers than partitions, records "acknowledged individually", delivery attempts counted, each record locked for 30 seconds by default: the SQS model, inside Kafka.

More Kafka detail: where offsets live, rebalance protocols, share-group history (depth)

Committed offsets are stored in an internal topic, __consumer_offsets (Kafka implementation). Kafka 4.0 made a new consumer rebalance protocol (KIP-848) generally available that "says goodbye to 'stop-the-world' rebalances" (Kafka 4.0 release), but clients still default to the classic one (group.protocol "The default value is classic", consumer configs, 4.3). Share groups ("Queues for Kafka") in the design document's words: "partitions may be assigned to multiple consumers", "The number of consumers in a share group can exceed the number of partitions", "Records are acknowledged individually", and "Delivery attempts to consumers in a share group are counted" (Kafka design, The Share Consumer); a locked record can be acknowledged, released, rejected or renewed. They were early access in 4.0 and a preview in 4.1. How each partition is replicated, with a leader, followers and a Raft-based controller since Kafka 4.0, is on Distributed systems fundamentals. Kafka's design document is unusually readable: Kafka 4.3 design (about 1 h).

Delivery semantics: which comes first, the work or the ack

A consumer does two things with each message: the work (send the receipt) and the ack (delete it, or commit the offset). A crash can land between them, and the order you chose decides what that crash costs. Kafka's documentation names the outcomes: "At most once: Messages may be lost but are never redelivered. At least once: Messages are never lost but may be redelivered. Exactly once: Each message is processed once and only once" (Kafka design, Message Delivery Semantics).

At-most-once: ack, then work

msg = queue.receive() queue.delete(msg) # ack first send_receipt(msg.order) # crash here: receipt never sent

Kafka: the consumer "crashes after saving its position but before saving the output ... This corresponds to 'at-most-once' semantics". Fine for metrics samples or a "typing..." indicator; wrong for anything a user paid for.

At-least-once: work, then ack

msg = queue.receive() send_receipt(msg.order) # crash after this line... queue.delete(msg) # ...and msg comes back: sent twice

Kafka: "the first few messages it receives will already have been processed. This corresponds to the 'at-least-once' semantics". The default almost everywhere, because a duplicate can be detected and a loss cannot.

Measured: one lost or one duplicated receipt per crash, and none with a unique key

A jobs table used the way SQS works, four worker processes, 1,000 jobs, a 5% chance of crashing per job, three runs per mode. At-most-once lost 52, 44 and 53 receipts, one per crash, with no error anywhere. At-least-once sent every receipt, and 52, 46 and 53 customers got two. With an idempotent receiver (a primary key on the job id, ON CONFLICT DO NOTHING): exactly 1,000 receipts in all three runs, the 52, 46 and 53 repeats caught and counted. And with no crashes at all but a visibility timeout of 0.3 s against job times averaging 0.1 s: 20, 24 and 23 duplicates per 600 jobs, because a slow job looks like a dead worker (visibility timeouts).

The expected count. If each delivery crashes after the side effect with probability p, a job is delivered on average 1/(1 − p) times, so 1,000 jobs at p = 0.05 give 1,000 × 0.05 / 0.95 = 52.6 duplicates; the three runs gave 50.3 on average. The Queue lab simulates the same queue: its model of these two runs, averaged over 20 seeds, gives 53.0 duplicates (range 38 to 76) for the crash run and 21.5 (range 15 to 28) for the 0.3 s timeout run, against 50.3 and 22.3 measured. The defaults of its two "Lab run" presets reproduce the measurement independently: the model shares the settings and was not fitted to the results (checked in src/recompute.py).

Why there is no exactly-once delivery. The sender cannot know what the receiver did: "If a producer attempts to publish a message and experiences a network error, it cannot be sure if this error happened before or after the message was committed" (Kafka design). Jim Gray proved the general case in 1978 (the "two generals" problem, quoted below). What systems offer instead is an effect that happens once: at-least-once delivery plus deduplication, called effectively-once or exactly-once processing. In an interview, say "at-least-once delivery, with idempotent consumers, so the effect happens once", and name the deduplication key (advice kept from the old page).

Read the fine print on "exactly-once"
Kafka's own docs: "Many systems claim to provide 'exactly-once' delivery semantics, but it is important to read the fine print, because sometimes these claims are misleading". SQS FIFO's "exactly-once processing" means the queue drops a re-sent message with the same deduplication id "within the 5-minute deduplication interval" (SQS FIFO); a consumer that crashes before deleting still gets the message again.
How the experiment was run, the two generals, and an ack is only as good as the disk (depth)

Apple M1 Pro, PostgreSQL 16 from the pgserver wheel, 2026-10-04; script src/lab/pg_lab.py, about 3 minutes in all. Everything is real: separate OS processes, real transactions, real row locks, real redelivery by timeout. The only artificial part is the crash, injected with os._exit() at a chosen line, which kills the process with no clean-up, as a kill signal or a power cut would. A worker claims the oldest visible job and hides it for a visibility timeout (2 s here), all in one statement:

UPDATE jobs SET visible_at = now() + interval '2 seconds', receives = receives + 1 WHERE id = (SELECT id FROM jobs WHERE visible_at <= now() ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING id, order_id, receives;

It then "sends a receipt" by inserting a row into a second database (standing in for an e-mail provider: outside the queue's transaction, as a real one would be) and finally deletes the job. A supervisor restarts crashed workers, as systemd or Kubernetes would. In the timeout run, job times are exponential with mean 0.1 s, so about 5% of jobs take longer than 0.3 s.

Gray's proof that two parties talking through messengers that may be lost cannot be certain they agree: "Let P be the shortest such protocol. Suppose the last messenger in P gets lost. Then either this messenger is useless or one of the generals doesn't get a needed message" (Gray, Notes on Data Base Operating Systems, §5.8.3.3.1). So no protocol makes the delivery happen exactly once over a network that can lose messages.

The rest of the Kafka quote names the cases where claims fail: "they don't translate to the case where consumers or producers can fail, cases where there are multiple consumer processes, or cases where data written to disk can be lost". The last one is real: Jepsen found that NATS JetStream "calls fsync to flush data to disk only once every two minutes, but acknowledges messages immediately", and simulated power failures lost "roughly thirty seconds of writes" (Jepsen, NATS 2.12.1, 2025-12-08).

What Kafka's "exactly-once" covers

Kafka is the system that most often advertises exactly-once semantics (EOS), through two mechanisms added in Kafka 0.11 (2017) by KIP-98. The picture says what each covers, and what neither can:

The transaction covers Kafka topics and the consumer's offsets; an e-mail is outside it

Idempotent producer: "The broker assigns each producer an ID and deduplicates messages using a sequence number that is sent by the producer along with every message" (Kafka design), so a retried send is not appended twice; on by default since Kafka 3.0, with acks=all. Transactions: a read-process-write step writes its output records and its new input offsets ("we can write the offset to Kafka in the same transaction as the output topics") and commits them together; readers with isolation.level=read_committed see only committed records. The default is read_uncommitted. Anything the step does outside Kafka is not in the box.

The scope is Kafka to Kafka. The docs: this gives "exactly-once delivery when reading, processing and writing data on Kafka topics. Exactly-once delivery for other destination systems generally requires cooperation with such systems ... Otherwise, Kafka guarantees at-least-once delivery by default." If the work is "send an e-mail" or "write to Postgres", you are back to at-least-once plus deduplication, or to "letting the consumer store its offset in the same place as its output" (one Postgres transaction for both).

Correction to the old page
The old "Distributed Systems Basics" page listed "Kafka transactional producer + idempotent consumer offsets" as a way to get exactly-once processing. "Idempotent consumer offsets" is loose: what Kafka does is commit the consumer's offsets inside the producer's transaction, and that gives exactly-once only when input and output are both Kafka topics. Any external effect still needs its own deduplication.

When not to use Kafka transactions: when the output is not a Kafka topic (they cannot cover it), and when a duplicate is cheap to absorb downstream (an idempotent consumer is simpler and faster).

The transaction protocol step by step, what it costs, and the bugs Jepsen found (depth)
  1. The producer is configured with a transactional.id, a stable name that survives restarts. A broker acting as transaction coordinator keeps the state of its transactions in an internal, replicated transaction log.
  2. On start, the producer registers its transactional.id; the coordinator bumps an epoch number, so "any previous zombie instance of the producer is fenced off" (KIP-98). A zombie is an old instance that was presumed dead but is still running; fencing means its writes are rejected.
  3. Within a transaction the producer writes output records to any partitions, and also the consumer's new offsets (sendOffsetsToTransaction). "The consumer's position is stored as a message in an internal topic".
  4. On commit, the coordinator writes COMMIT markers into every partition involved; read_committed consumers then see the records.

The idempotent producer covers one producer session writing to one partition and says nothing about consumers. "In 3.0.0 and 3.1.0, a bug prevented the idempotence default from being applied" until 3.0.1, 3.1.1 and 3.2.0 (Kafka 3.0 upgrade notes).

Cost. Confluent's 2017 measurement: with 1 KB messages and 100 ms transactions, producer throughput fell 3% against an at-least-once, in-order producer, and 20% against the then-default acks=1 (Narkhede, Confluent, 2017); with Kafka Streams and a 100 ms commit interval the loss was 15 to 30%. The docs add that "using a replication factor lower than 3 effectively voids EOS" (recommend 3 with min.insync.replicas=2, Kafka Streams docs).

How solid it is. In 2024 Jepsen found that "There is no concept of a transaction number. When a server receives a commit (or abort) message, it has no way to know what transaction the client intended to commit", reproduced aborted reads and torn transactions in Kafka itself (KAFKA-17754), and Kafka's engineers expected KIP-890 to fix it (Jepsen, Bufstream 0.1.0, 2024-11-12). KIP-890 bumps the epoch "after every commit/abort marker" so each transaction is identified by (producer id, epoch) (KIP-890); its second phase shipped in Kafka 4.0, where it "reduces the chances of 'zombie transactions'" (Kafka 4.0 release). Whether KAFKA-17754 is fully closed was not checked for this page.

Idempotent consumers: making the second delivery harmless

An operation is idempotent when doing it twice has the same effect as once. The measured chart above is the whole argument: the same crashes, the same redeliveries, and the unique key turned 52 duplicates into 52 "caught". Four ways to get there, cheapest first:

  1. Write absolute values, not increments. "Set document 981's embeddings to X", SET status = 'paid' instead of balance = balance + 10, overwrite a file at a path derived from the input. Kafka: "In many cases messages have a primary key and so the updates are idempotent (receiving the same message twice just overwrites a record with another copy of itself)". Free, but an e-mail cannot be "set".
  2. Record the message id in the same transaction as the effect, the idempotent consumer: "the message handler inserts the message's ID into the PROCESSED_MESSAGE table. Since the (subscriberId, messageID) is the PROCESSED_MESSAGE table's primary key the INSERT will fail if the message has been already processed successfully" (microservices.io, Idempotent Consumer). Works whenever the effect lives in your own database.
  3. Pass an idempotency key to the system that does the effect (a payment, an e-mail provider, a model provider): Idempotency-Key: order-42-receipt, derived from the message, and they deduplicate. How a server implements such keys is on Building a backend API; when a client should retry is on Reliability engineering.
  4. Version checks for updates that can arrive out of order: UPDATE orders SET ..., version = 7 WHERE id = 42 AND version < 7 ignores anything not newer, deduplicating and reordering at once.
def handle(msg): # called for every delivery, including redeliveries with conn.transaction(): cur = conn.execute( "INSERT INTO processed_events (event_id) VALUES (%s) ON CONFLICT DO NOTHING", (msg["event_id"],)) if cur.rowcount == 0: return # seen before: do nothing, but still ack conn.execute("INSERT INTO receipts (order_id, ...) VALUES (%s, ...)", (msg["order_id"],)) queue.ack(msg) # a crash before this line is now harmless

The key must come from the producer (an event id, an order id plus event type), never be generated on receipt: a random id made by the consumer is new on every redelivery, so nothing is ever deduplicated. Choose it by what must happen once, not by what the transport calls a message: Stripe warns that sometimes "two separate Event objects are generated and sent" for one change and says to deduplicate by "the ID of the object in data.object along with the event.type" (Stripe webhooks).

What it costs: a row per processed message, so the table needs an expiry longer than the longest possible redelivery window (the broker's retention or maximum retry period). A dedup window shorter than the redelivery window lets duplicates through: SQS FIFO's 5-minute window means a re-send after 6 minutes is a new message.

Visibility timeouts, leases and heartbeats

A queue cannot see a worker die; it only sees that no ack came. So it lends each message out for a fixed time, the visibility timeout: "If you don't delete it before the timeout expires, the message becomes visible again" (SQS visibility timeout); default 30 s, maximum 12 h. The general name for a time-limited claim is a lease, and every broker has one: Kafka's max.poll.interval.ms (5 minutes), share groups' record lock (30 s), Celery on Redis's visibility_timeout (1 hour), RabbitMQ's redelivery when a consumer's channel closes.

The timeout trades duplicates against delay; a heartbeat removes the trade

Predict: a job takes 45 s on a queue with SQS's default 30 s timeout. How many workers run it? Then compare the three settings.

Times illustrative; the measured version of "too short" is above (0.3 s timeout, 0.1 s mean job: 20 to 24 duplicates per 600 jobs). At SQS's 12-hour maximum, a crashed job is 12 hours late.

The production answer is a timeout comfortably above the normal job time plus a heartbeat: a long job keeps extending its own lease. SQS: "use the ChangeMessageVisibility action to extend the visibility timeout while processing the message", within the 12-hour limit from first receipt; Kafka share groups added a RENEW acknowledgement in 4.2 "for extended processing times". To hand a message back early, set its timeout to 0. Even a correct setting is not a hard guarantee: SQS says "there's no absolute guarantee that a message won't be delivered more than once during the visibility timeout period", which is why the consumer is idempotent anyway.

A real trap: Celery acknowledges before it runs
"the default behavior is to acknowledge the message in advance, just before it's executed, so that a task invocation that already started is never executed again" (Celery 5.6.3 tasks guide): at-most-once, so a worker killed mid-task loses the task. task_acks_late = True makes it at-least-once, but "Even if task_acks_late is enabled, the worker will acknowledge tasks when the worker process executing them abruptly exits or is signaled" unless task_reject_on_worker_lost = True, which the docs warn "can cause message loops" (Celery configuration). On Redis, a task not acknowledged within the 1-hour visibility timeout "will be redelivered to another worker and executed", which breaks ETA and countdown tasks scheduled further out: "it will be executed again, and again in a loop" (Celery Redis broker).

Dead-letter queues and poison messages

A poison message fails every time (malformed data, a bug one input triggers, a document too large to embed). Under at-least-once delivery it comes back forever, burning a worker each time, and in an ordered stream it blocks everything behind it. A dead-letter queue (DLQ) moves it aside after N attempts. SQS: "The maxReceiveCount is the number of times a consumer can receive a message from a source queue before it is moved to a dead-letter queue" (SQS DLQs). Load the "Poison, no DLQ" preset in the Queue lab and watch one bad message hold a worker until you set max receives.

  • Alert on DLQ depth. An unwatched DLQ is a slower way of losing data: every message in it is a customer's job that did not happen.
  • Build the replay path first. SQS has a "dead-letter queue redrive" back to the source queue once the bug is fixed; elsewhere you write a script. Replayed messages run again, so the consumer must be idempotent. AWS: "a best practice to always set the retention period of a dead-letter queue to be longer than the retention period of the original queue."
  • Mind ordering. Moving a message aside lets later ones overtake it: "Don't use a dead-letter queue with a FIFO queue if you don't want to break the exact order of messages or operations" (AWS). For ordered streams, stop and page someone, or park every later message for the same key too.

How many retries and with what backoff and jitter is retry policy, owned by Reliability engineering, whose measured retry storm shows why retries without a budget make outages worse.

DLQ defaults in RabbitMQ, Dramatiq and Kafka (reference)

RabbitMQ quorum queues count deliveries and default to a limit of 20 since 4.0; without a dead-letter exchange configured, a message over the limit is dropped (quorum queues). Dramatiq moves a message to its dead letter queue after its retries (20 by default) "where it's kept for up to 7 days and then automatically dropped" (Dramatiq 2.2.1 guide). Kafka consumer groups have no built-in DLQ: the application (or Kafka Connect's error handling) writes failures to a separate topic; share groups count delivery attempts and let a consumer reject a record.

Backpressure, Little's law and draining a backlog

A queue absorbs bursts, and it absorbs overload that never ends just as quietly. David Yanacek of Amazon: "if a failure or unexpected load pattern causes the arrival rate to exceed the processing rate, it quickly flips into a more sinister operating mode. In this mode, the end-to-end latency grows higher and higher" (Yanacek, Avoiding insurmountable queue backlogs, Amazon Builders' Library; quotes checked against the 2024 archived copy).

The arithmetic. Arrivals λ per second, S seconds of work per message, C workers: they finish at most C/S per second, so utilisation is ρ = λS / C. Below 1 the queue stays short on average, though waiting climbs steeply as ρ nears 1 (the curve is on Capacity planning and performance). Above 1 the backlog grows by λ − C/S every second, forever; more queue space does not help, only more workers, less work per message or fewer messages. And once a backlog exists, only the spare capacity drains it: B messages take B / (C/S − λ).

Only spare capacity drains a backlog: at twice the arrival rate, a one-hour outage takes another hour

Predict: consumers are down for an hour while messages keep arriving. With 50% spare capacity (1.5× the arrival rate), how long until the queue is empty again? Then drag.

Drain time = outage × λ / (C/S − λ) = 60 min / (k − 1) for capacity k×λ derived. The default lands on Yanacek's "recovering from the outage requires double the system's capacity for another hour after the recovery"; he also reports a backlog "10x the capacity that the consumer side was scaled to" taking "300 minutes" to work through. For a first-in, first-out queue the line is also the age of the oldest message, in minutes, because the backlog divided by λ is exactly how long the head has waited.

Little's law ties the averages together: "the average number of items in a queuing system, denoted L, equals the average arrival rate of items to the system, λ, multiplied by the average waiting time of an item in the system, W. Thus, L = λW" (Little, Operations Research 59(3), 2011), for the long-run averages of a stable system, whatever the distributions (a backlog that keeps growing has no stable average). Two uses: size workers (embedding 5 documents a second at 20 s each keeps 5 × 20 = 100 jobs in progress, so at least 100 worker slots: the parent root's example), and turn a backlog into a wait (500 messages at 50 a second is about 10 s). Yanacek's version: 100 messages a second at 100 ms is 10 busy threads; at 10 s it is 1,000. The Queue lab checks L against λW on every run.

Backpressure carries "we cannot keep up" back to whoever produces the work, so the system degrades at the edge instead of everywhere:

  • Bound the queue and reject at admission: over the limit, answer 429 Too Many Requests (which "MAY include a Retry-After header", RFC 6585 §4) or 503. Fail fast at the door rather than time out deep inside.
  • Block the producer: Kafka's producer buffers up to buffer.memory, then blocks send() for up to max.block.ms (producer configs); a bounded asyncio.Queue(maxsize=...) makes await q.put() wait.
  • Limit what each consumer holds: RabbitMQ's prefetch "defines the max number of unacknowledged deliveries that are permitted on a channel" (RabbitMQ confirms); Celery prefetches 4 messages per process by default (worker_prefetch_multiplier), which is why long tasks run with 1.
  • Shed or sideline old work: in a backlog the newest work is often the most valuable; real-time systems "often are implemented with FIFO-ish queues, but prefer LIFO-ish behavior" (Yanacek).

What to watch: the age of the oldest message, not the length. "we focus more on measuring the age of messages that are in the queue. This quickly catches cases where the systems are behind, or are frequently erroring out and causing retries" (Yanacek). A queue of 10,000 may be healthy (fast consumers) and a queue of 50 stuck (one poison message retried forever); age tells which. In SQS that is ApproximateAgeOfOldestMessage; in Kafka, lag converted to time.

Metastable failures, Amazon's backlog tactics, credit-based flow control (depth)

A backlog can keep itself alive after its cause is gone: old messages time out at their callers, who retry and add more. Bronson et al. call this a metastable failure, "a bad state that persists even when the trigger is removed" (Metastable Failures in Distributed Systems, HotOS 2021). Hence the old page's rule: bound the queue, and prefer rejecting at admission over timing out deep in the stack.

Yanacek's other mode: "When there is no backlog in the queue, the system's latency is low, and the system is in fast mode." Amazon moves messages older than a threshold "into a backlog queue that we work through only after we're caught up on the live queue", drops messages a periodic full sync will redo anyway, and isolates noisy customers by hashing each to a few of many queues (shuffle sharding). Load shedding by priority is on Reliability engineering. The parent root's Case files tab holds a real backlog that never drained ("EC2 could not hand out servers: a queue that never drained").

Protocols push back too: HTTP/2 and gRPC use per-stream credit windows (WINDOW_UPDATE, RFC 9113 §5.2); depth on Topic: protocols.

The dual-write problem and the transactional outbox

Placing an order means saving it in the database and publishing "order placed" for e-mail, warehouse and analytics: a dual write, two writes to two systems that share no transaction. Gunnar Morling, then Debezium's lead: "we cannot have one shared transaction that would span the service's database as well as Apache Kafka, as the latter doesn't support to be enlisted in distributed (XA) transactions" (Debezium blog, 2019-02-19). Whichever write goes first, a crash between them leaves the systems disagreeing. Step through the same order under three designs:

Swapping the two writes swaps the failure; the outbox turns them into one

Crash points are the ones the measured lab injects; counts in the captions are from that lab (500 orders, 5% crash chance, three runs).

The transactional outbox (Chris Richardson's name): "the service that sends the message to first store the message in the database as part of the transaction that updates the business entities. A separate process then sends the messages to the message broker" (microservices.io, Transactional outbox). The relay "might, for example, crash after publishing a message but before recording the fact that it has done so. When it restarts, it will then publish the message again. As a result, a message consumer must be idempotent". So the outbox converts "sometimes lost" into "sometimes duplicated", and the idempotent consumer converts that into "once".

Measured on the same laptop Postgres (the "broker" is a second database, so there is genuinely no shared transaction; 500 orders, 5% crash chance at the dangerous line, three runs):

With a batch of 10 events per relay transaction, a crash mid-batch rolls back every "sent" mark in the batch, so all of them are published again: about 4 to 5 duplicates per crash. With one event per transaction, duplicates equal crashes. Batching is faster; it multiplies duplicates.

Two ways to run the relay. A polling publisher loops over SELECT ... WHERE sent_at IS NULL ORDER BY seq LIMIT 100 FOR UPDATE SKIP LOCKED, publishes and marks sent (microservices.io): simple, any database, a little polling load and latency; several relays can run thanks to SKIP LOCKED, but then strict ordering across them is lost. Change data capture (CDC) instead tails the database's log: in Postgres, logical decoding of the write-ahead log, "the process of extracting all persistent changes to a database's tables into a coherent, easy to understand format" (PostgreSQL docs). Debezium is the standard tool: no polling, ordered by commit, at the cost of a Kafka Connect deployment and a replication slot to monitor (an abandoned slot makes Postgres keep WAL forever). It is still at-least-once: "while it is recovering from the fault, it's possible that the connector might emit some duplicate change events" (Debezium Postgres connector).

When you do not need an outbox: when the queue lives in the same database. River "encourages the use of the same database for application data and job queue. By enqueueing jobs transactionally along with other database changes, whole classes of distributed systems problems are avoided" (River docs). The outbox is such a queue, with a relay that forwards to Kafka for consumers that live elsewhere. And the receiving side's mirror is the inbox: the consumer stores each incoming message id with its effects, which is the idempotent consumer by another name.

Webhooks are the same problem facing outwards: calling a customer's endpoint after a database change is a dual write to their server, so the sender delivers from an outbox with retries and the receiver answers 2xx at once and queues the work (details below). Webhooks as an API are owned by Service APIs, section 6.

What the outbox costs: a table that grows (delete or partition sent rows), a relay or CDC pipeline to run and monitor, events a little later than the commit, and duplicates every consumer must absorb. When not to use it: when the event is not critical (a lost analytics ping is fine), or when the consumers can read your database's job queue directly.

The measured counts, Debezium's outbox table, inbox libraries, and webhooks in full (reference)

Debezium's Outbox Event Router expects an outbox table with columns id, aggregatetype, aggregateid, type and payload, routing each row by default to a topic named outbox.event.<aggregatetype> with aggregateid as the message key (Debezium outbox event router). Pattern pages: "Publish messages by polling the database's outbox table"; "Tail the database transaction log and publish each message/event inserted into the outbox to the message broker" (microservices.io, transaction log tailing).

Inbox in libraries: MassTransit: "The inbox is used to keep track of received messages to guarantee exactly-once consumer behavior" (MassTransit); NServiceBus "uses the message identity (MessageId) to deduplicate messages" (NServiceBus outbox). Oban lists "Transactional Control: Enqueue a job along with other database changes, ensuring that everything is committed or rolled back atomically" (Oban).

In numbers: commit-then-publish lost 19, 28 and 27 events; publish-then-commit produced 19, 28 and 27 phantom events; the outbox lost none, with 147 to 185 duplicate events in batches of 10 and 24 to 32 one at a time, and after deduplication exactly 500 orders and 500 events in every run.

Webhooks in full: the sender writes "deliver event X to customer Y" in the transaction and delivers from a worker with retries (Stripe retries "for up to three days"); the receiver answers 2xx at once and queues the work. GitHub "does not automatically redeliver failed deliveries" (GitHub, failed deliveries), so a receiver that is down simply misses them. Stripe: "Your endpoint must quickly return a successful status code (2xx) before any complex logic that could cause a timeout", and it retries "for up to three days with an exponential back off in live mode" (Stripe webhooks). GitHub expects a 2XX "within 10 seconds" (GitHub best practices).

Sagas, not two-phase commit

The outbox makes one service's write and event atomic. "Upgrade to Pro" spans three: charge the card (payments), raise the token quota (quota), send a receipt (e-mail). If the quota update fails after the charge, the user has paid for nothing.

A saga commits each step and undoes with compensations; 2PC holds locks and waits

Two-phase commit (2PC) asks every participant to prepare (do the work, hold the locks, promise to commit), then tells all to commit or all to abort. "The classic Two-Phase Commit protocol blocks if the coordinator fails" (Gray and Lamport, Consensus on Transaction Commit), and the systems a service talks to (Kafka, SaaS APIs, a payment provider) cannot take part at all. Postgres supports the prepare step but warns "Unless you're writing a transaction manager, you probably shouldn't be using PREPARE TRANSACTION" (PostgreSQL docs). 2PC run over consensus inside distributed databases is on Distributed systems fundamentals.

A saga gives up atomicity and adds undo: "A saga is a sequence of local transactions. Each local transaction updates the database and publishes a message or event to trigger the next local transaction in the saga. If a local transaction fails because it violates a business rule then the saga executes a series of compensating transactions" (microservices.io, Saga; the idea is Garcia-Molina and Salem's, SIGMOD 1987). What that means in practice:

  • Compensations are business actions, not rollbacks. A refund is not "the charge never happened"; some steps cannot be compensated at all (an e-mail sent), so they go last.
  • No isolation. Others see the half-done state between steps; microservices.io lists "Lack of isolation" as the main drawback. Defences: a PENDING status other code respects, re-reading before acting, the riskiest step first.
  • Every step and compensation runs at least once, because messages drive them, so each is idempotent.
  • Choreography or orchestration. In choreography "each local transaction publishes domain events that trigger local transactions in other services"; in orchestration "an orchestrator (object) tells the participants what local transactions to execute". Orchestration keeps the flow in one place, which is what durable workflow engines (below) are for.

When not to use either: if all the data can live in one database, use one transaction. Splitting data across services is what creates the need for sagas; do it for a reason.

2PC's details, the 1987 definition, and event-driven architecture, event sourcing and CQRS (depth)

In 2PC, prepared participants hold their locks and cannot decide alone while the coordinator is gone. Postgres's warning in full: "PREPARE TRANSACTION is not intended for use in applications ... Unless you're writing a transaction manager, you probably shouldn't be using PREPARE TRANSACTION". 2PC lives on inside distributed databases (Spanner, CockroachDB), run over consensus so the coordinator cannot simply vanish. The 1987 paper: a long transaction "is a saga if it can be written as a sequence of transactions that can be interleaved with other transactions", and the system "guarantees that either all the transactions in a saga are successfully completed or compensating transactions are run to amend a partial execution"; "other transactions might see the effects of a partial saga execution". Choreography has no central piece, but the flow is spread across services and hard to see.

Event-driven architecture. In an event-driven architecture, services announce facts ("order 42 placed") on a log instead of calling each other ("e-mail service, send a receipt"). The old page's trade holds: temporal decoupling (the e-mail service can be down and catch up), fan-out (consumers added without touching the producer), an audit trail and replay; against eventual consistency between views, harder tracing (propagate trace ids in message headers: Observability) and schema discipline. An event is a fact in the past tense with any number of readers; a command ("send receipt") is a request to one recipient that may refuse, and putting commands on a shared log hides who is responsible. A thin event carries ids and the consumer fetches current data; a fat event carries the data, so consumers work while the producer is down. Schema changes must be backward compatible (add optional fields, never rename or remove), usually enforced by a schema registry (old page, kept as practice).

Event sourcing and CQRS. In event sourcing the events are the source of truth: "every change to the state of an application is captured in an event object, and that these event objects are themselves stored in the sequence they were applied for the same lifetime as the application state itself" (Fowler, Event Sourcing, 2005); state is computed by replaying them. CQRS uses "a different model to update information than the model you use to read information" (Fowler, CQRS, 2011); a Kafka-to-ClickHouse analytics pipeline is a mild form. Fowler: "beware that for most systems CQRS adds risky complexity." Microsoft (2026): "It's costly to migrate to or from an event sourcing solution ... For most systems and most parts of a system, traditional data management is sufficient", not suitable when systems "have straightforward CRUD operations that don't require auditability, replay, or historical reconstruction of state", and "Message brokers such as Apache Kafka typically lack per-entity stream queries and optimistic concurrency. They work well as a distribution layer ... but they aren't a substitute for an event store" (Azure Architecture Center, Event Sourcing). The old page's verdict, "rarely worth it outside ledgers", is an opinion that matches both sources. For an ML platform the useful part is the log: usage events, feedback events and pipeline triggers fanned out from one stream (on AWS: EventBridge or SNS into SQS into Lambda, each with a DLQ and idempotent handlers).

Measured: a Postgres queue scales only because workers skip each other's rows

400 jobs of 5 ms each on the laptop, the worker holding the row lock while it works. With plain FOR UPDATE every worker queues on the same first row, so 8 workers are no faster than 1 (about 123 jobs a second). With SKIP LOCKED each takes a different row: 960 jobs a second with 8 workers, against an ideal of 1,600 (8 / 5 ms; the gap is Postgres round trips and the timer granularity of time.sleep). Postgres: "Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table" (SELECT docs). Same script, src/lab/pg_lab.py.

Holding the lock while working is fine for milliseconds and harmful for minutes: long transactions hold locks and stop Postgres from cleaning up old row versions. For long jobs, claim with a lease (a visible_at column, as the measured queue did) and commit the claim at once.

Durable workflows are for jobs with many steps that must survive crashes for minutes to weeks: an agent run, a saga, onboarding with waits. You write the steps as ordinary code; the engine records each completed step and, after a crash, resumes from the last one. Temporal calls this durable execution: a workflow keeps its state and progress through failures, crashes and server outages (Temporal docs). Two rules come with it: workflow code must be deterministic, making "the same Workflow API calls in the same sequence" when replayed (workflow definition), so no clocks, random numbers or network calls in it; and side effects go in activities, which are retried, so "Temporal recommends that Activities be idempotent" (activity definition). Lighter alternatives keep the state in your own Postgres (DBOS) or in a log (Restate). How this compares with an agent framework's checkpointing is owned by Topic: agentic-frameworks (its Orchestration lab, "Durable execution").

When to reach for one: when you find yourself writing a state machine over queue messages with timeouts and compensations. When not to: a single-step job is a plain queue's work, and an engine is a new system and a new programming model (the determinism rule bites people).

Scheduling and cron

Classic cron runs a command on one machine at set times, so it inherits that machine's fate: down at 02:00, the job does not run; two machines with the crontab, it runs twice. Distributed schedulers state the same trade. Kubernetes: "A CronJob creates a Job object approximately once per execution time of its schedule. The scheduling is approximate because there are certain circumstances where two Jobs might be created, or no Job might be created ... Therefore, the Jobs that you define should be idempotent" (Kubernetes CronJob). Celery: "You have to ensure only a single scheduler is running for a schedule at a time, otherwise you'd end up with duplicate tasks" (Celery periodic tasks).

  • Key each run by its scheduled time, not by "now": the 02:00 roll-up for 2026-10-03 writes a partition named for that date and overwrites it, so a rerun, a duplicate or a backfill gives the same result. Airflow: "the tasks should produce the same outcome on every re-run" (Airflow best practices): deterministic output locations, overwrite, never append.
  • Decide what overlap and a missed run mean. Kubernetes' concurrencyPolicy is Allow by default (runs may overlap); Forbid skips a run while the previous one is going; Replace kills the old one. startingDeadlineSeconds skips a run that could not start in time; without it, Kubernetes will not start a job that has missed more than 100 schedules.
  • Let the scheduler only enqueue. It puts a message on the queue; ordinary workers, with their retries, DLQ and idempotency, do the work.

The other async shapes around LLMs

  • A streamed reply stays on the request path, but generation should not be tied to the HTTP connection: run it as a background job writing chunks somewhere durable, and make the stream a reader that can reconnect.   • A long agent run is a saga of model and tool calls: return 202 with a run id, run the steps in a worker or workflow engine that records each completed step, give every side-effecting tool call an idempotency key from the run id and step number, record model outputs as completed steps so a resumed run does not pay for the same tokens again, and make leases outlast the slowest step: a 20-minute agent step on a queue with a 5-minute visibility timeout runs four times in parallel.
  • A queue in front of the GPUs must be bounded and shed load early, because an unbounded one turns a traffic spike into minutes of latency for everyone, and autoscaling should follow queue depth or the age of the oldest request, not CPU. Common mistakes, as a checklist (each is taught above)
  • Assuming the queue gives exactly-once. Every common broker delivers at least once in practice; test every consumer by delivering twice.
  • Generating the dedup id in the consumer: new on every redelivery, so nothing is deduplicated.
  • Celery with default acks for important work: a killed worker loses the task; use acks_late plus reject_on_worker_lost, and idempotent tasks.
  • A visibility timeout shorter than the slowest job: slow jobs run on two workers at once; set it above p99, or heartbeat.
  • Publishing right after a commit, "it is usually fine": until a deploy or crash lands between the two lines; then events are lost silently, one per crash.
  • Watching queue length instead of message age.
  • No DLQ, or a DLQ nobody watches: a poison message burns a worker forever, or failed jobs vanish quietly.
  • More consumers than partitions in a Kafka consumer group: the extras sit idle; plan partitions for peak parallelism, or use share groups (Kafka 4.2+).
  • Changing the partition count of a keyed topic: per-key ordering breaks across the change.
  • Slow work inside the transaction that holds the job lock, and unbounded queues in front of expensive resources (bound them, reject early with 429, scale on queue age).

Lease: any time-limited claim on work.
Heartbeat: periodically extending a lease while still working.
Poison message: a message that fails every time.
Dead-letter queue: where messages go after too many failed attempts.
Utilisation: ρ = λS / C, the share of worker capacity in use.
Little's law: L = λW for a stable system's averages.
Backpressure: telling producers to slow down when consumers cannot keep up.
Dual write: writing to two systems with no shared transaction.
Transactional outbox: write the event to a table in the same transaction; relay it later.
Change data capture: reading a database's changes from its log (Debezium).
Inbox: the receiving side's table of handled message ids.
Two-phase commit: prepare everywhere, then commit everywhere; blocks if the coordinator fails.
Saga: a sequence of local transactions with compensations for failure.
Event-driven architecture: services announce facts on a log instead of calling each other.
Event sourcing: the event log is the source of truth; state is replayed from it.
CQRS: separate models for writing and reading.
Task queue library: Celery, RQ, Arq, Dramatiq, Procrastinate.
Activity: a durable workflow's side-effecting step, retried by the engine.
Cron: running jobs at set times.

Queue lab

A simulated queue with the semantics of SQS (and of the measured Postgres queue): messages arrive, wait, are claimed by workers, hidden for a visibility timeout, and deleted when a worker acknowledges them after doing the side effect. You choose the traffic, the workers, the timeout and how often workers crash, and watch the backlog, the age of the oldest message, redeliveries and duplicates. Everything runs in your browser, deterministic for a given seed; the same model in Python is qsim in src/recompute.py.

Try: start with "Healthy" and raise the arrival rate until utilisation passes 100%: the backlog stops draining and the age of the oldest message climbs without limit. Load "Crashes, naive", then tick the idempotent consumer: redeliveries stay, duplicates vanish. Load "Poison, no DLQ" and set max receives to 5. Load the two "Lab run" presets to compare the model with the real Postgres runs.

The model, exactly
  • Arrivals: Poisson at rate λ for T seconds (optionally 3 times λ from T/4 to T/2), or a backlog of N messages at time 0. The run lasts 1.5 T (steady) or T (backlog), so a steady run shows the drain after arrivals stop.
  • Waiting messages are claimed oldest first (a redelivered message goes to the front, as ORDER BY id did in the measured lab). A claim hides the message for the visibility timeout V.
  • Service time: exponential with mean S, or fixed S. At the end of service: the side effect, then the acknowledgement (delete).
  • Crash: with probability p per delivery, after the side effect and before the acknowledgement (the dangerous spot). The worker is down for the restart time, then takes new work. The message reappears when its timeout expires.
  • If a message's timeout expires while its first worker is still busy, another worker may take it; both do the side effect (a duplicate) and the second acknowledgement finds it already deleted.
  • Idempotent consumer: a repeated side effect is detected and skipped (counted as "caught").
  • Poison messages (a fraction of arrivals) fail every time: no effect, no acknowledgement. With max receives M > 0, a message already received M times goes to the dead-letter queue when it is next claimed (the SQS maxReceiveCount rule).
  • Queue bound B: an arrival finding B messages in the system is rejected (the producer would get 429).
  • Little's law check: L is the time-average number of messages in the system over the run; X is completions per second; W the mean time from arrival to acknowledgement. L = XW when the queue ends empty.
