Our running example is the parent topic's chat assistant. When a user sends a message, the reply has to come back now; but a lot of other work hangs off that message and can happen a few seconds later: give the conversation a title, embed an uploaded PDF so it can be searched, count the tokens for billing, send a receipt when someone buys a subscription, tell the analytics system. Three ideas carry most of this page

1. A network cannot give you "exactly once"; you build it. When a crash or a lost reply leaves the sender unsure whether a message arrived, it must either send again (and risk a duplicate) or not (and risk a loss). Real systems choose "send again" and make the receiver ignore repeats. Measured below on a real Postgres: 1,000 jobs with a 5% crash chance were done 1,046 to 1,053 times; with a unique key on the message id, exactly 1,000.

2. Two writes to two systems are never atomic. Saving an order and then publishing its event loses the event whenever the process dies in between (measured: 19 to 28 lost per 500 orders at a 5% crash chance). The outbox turns the two writes into one database transaction, then publishes later, at least once.

3. A queue hides overload instead of removing it. If work arrives faster than workers finish it, nothing errors: the queue just grows, and every job waits longer. Watch the age of the oldest message, size workers with Little's law, and push back on producers.

Why async: taking slow work off the request path

A request path is everything that happens between a client sending a request and receiving the response. On the chat assistant, the path for "send message" is: check the user, save the message, call the model, stream the reply. Anything else done on that path makes every user wait for it, and holds one of the server's limited request slots while they wait. The parent root shows the effect with PDF uploads: 5 uploads among 30 chat messages made chat messages wait up to 3 seconds that should have waited none (the root's Step 3 animation, Topic: swe-and-system-design).

The fix is to separate accepting work from doing it. The request handler writes a description of the job somewhere durable and answers at once; other processes do the job later. That "somewhere" is a message queue or a log (both explained in the next section). Vocabulary used for the rest of the page:

  • A message (or event, or job) is one unit of handed-off work or information: a small record such as {"type": "embed_document", "doc_id": 981}.
  • The producer writes messages; the consumer (or worker) reads and handles them; the broker is the system in between that stores them (SQS, RabbitMQ, Kafka, or a table in Postgres).
  • To acknowledge (ack) a message is to tell the broker "done, you may forget it" (a queue deletes it; a log records how far you got).

The HTTP side of the hand-off is 202 Accepted, which RFC 9110 defines as "the request has been accepted for processing, but the processing has not been completed" (RFC 9110 §15.3.3). The response usually carries a job id and a URL the client can poll, or the client is told later through a webhook or a server-sent event. How to design those endpoints is on Building a backend API.

Goes async on the chat assistant

  • Embedding an uploaded document (tens of seconds)
  • Generating a conversation title after the first reply
  • Usage metering and billing events
  • Receipts, e-mails, outgoing webhooks to customers
  • Nightly evaluation runs, re-embedding the corpus (batch APIs, below)
  • Long agent tasks that run for minutes

Stays on the request path

  • The reply the user is reading (stream it instead: below)
  • Anything the next screen needs to show correctly
  • Checks that must reject the request (auth, rate limits, validation)
  • Writes the user must see confirmed (saving the message itself)
What async costs
The result is late, so the product must show progress and handle "not ready yet". Failures happen where no user sees them, so they need their own alerts. Jobs can run twice (the rest of this page). And the broker is one more system to run, monitor and pay for. A rule of thumb (opinion, not a sourced rule): make work async when it is slow, can fail and be retried independently, or fans out to several consumers; keep it synchronous when the caller needs the result to continue.

Two shapes: queues and logs

Brokers come in two shapes, and most confusion about "queues versus Kafka" is confusion between them.

A queue: a to-do list

Each message is meant for one worker. A worker takes a message, does it, acknowledges, and the broker deletes it. Several workers on one queue share the work (they are called competing consumers). Progress is tracked per message. Examples: Amazon SQS, RabbitMQ queues, a jobs table in Postgres, Redis lists behind Celery or RQ.

A log (a stream): an append-only record

Messages are appended in order and kept for a retention period whether or not anyone has read them. Each reader remembers its own position, a number called the offset. Many independent readers can read the same messages, and a reader can rewind and replay. Examples: Apache Kafka, Amazon Kinesis Data Streams, Redpanda, Apache Pulsar, Redis Streams, RabbitMQ Streams.

Kafka's own introduction states the difference: "events are not deleted after consumption. Instead, you define for how long Kafka should retain your events through a per-topic configuration setting" (Kafka 4.3 introduction); the default retention is 7 days (retention.ms, topic configs). RabbitMQ added a log type for the same reason: "Streams model an append-only log of messages that can be repeatedly read until they expire" (RabbitMQ Streams).

Which to use follows from who reads the messages:

  • A queue when each message is a job for one kind of worker: "embed document 981", "send receipt for order 42". You want per-message acknowledgement, per-message retries and dead-lettering, and you never want the job again once done.
  • A log when the message is a fact several systems care about: "order 42 was placed" read by the e-mail service, the warehouse and analytics, each at its own pace; or when you may need to replay history (rebuild a search index, backfill a new service). You pay with partitions to plan, offsets to manage and usually a cluster to run.

Kafka from zero: topics, partitions, offsets, consumer groups

Kafka is the log most teams meet first, and its vocabulary is used by Redpanda, Kinesis (with different names) and most stream processors.

  • A topic is a named log, such as orders or chat_messages.
  • A topic is split into partitions: several independent logs, each stored and replicated on brokers. Partitions are how Kafka scales: different partitions live on different machines and are read in parallel. (How each partition is replicated, with a leader, followers and a Raft-based controller since Kafka 4.0, is on Distributed systems fundamentals.)
  • Each message in a partition gets an increasing number, its offset. A consumer's progress is "the next offset I will read" for each partition.
  • A message can carry a key. Kafka hashes the key to choose the partition, so "if the key chosen was a user id then all data for a given user would be sent to the same partition" (Kafka design).

Ordering is per partition only. "Events with the same event key (e.g., a customer or vehicle ID) are written to the same partition, and Kafka guarantees that any consumer of a given topic-partition will always read that partition's events in exactly the same order as they were written" (Kafka introduction). Two messages in different partitions have no order between them. So choose the key by what must stay in order: a user's messages, an order's state changes.

Consumer groups share the work. Consumers that share a group id form a consumer group; each partition "is consumed by exactly one consumer within each subscribing consumer group at any given time" (Kafka design). Two consequences: a group can never use more consumers than there are partitions (the extras sit idle), and a different group (analytics, say) gets every message again. When consumers join or leave, the group rebalances, moving partitions between members; Kafka 4.0 made a new protocol (KIP-848) generally available that "says goodbye to 'stop-the-world' rebalances" (Kafka 4.0 release), but clients still default to the classic one (group.protocol "The default value is classic", consumer configs, 4.3).

Try it: keys to partitions, partitions to consumers

Twelve chat messages from four users (user-1, user-4, user-6, user-8), keyed by user id. The partition is computed with Kafka's real default partitioner for keyed records, murmur2(key bytes) mod partitions (a port of Kafka's Utils.murmur2 that reproduces the six test vectors in Kafka's UtilsTest). Partitions are dealt to consumers round-robin for the picture; the real assignor may pair them differently. Message order illustrative

Try: set consumers above partitions and watch consumers go idle; change the partition count and see users move to new partitions (which is why adding partitions to a keyed topic breaks per-key ordering for messages already written).

Committing offsets. A consumer saves its position by committing offsets, which Kafka stores in an internal topic, __consumer_offsets (Kafka implementation). By default the client does it for you: enable.auto.commit is true and commits "periodically ... in the background", every 5 seconds (consumer configs). When to commit relative to the work decides your delivery semantics, which is the next section. Two timers decide when a consumer is declared dead and its partitions handed to someone else: session.timeout.ms (45 s without heartbeats) and max.poll.interval.ms (5 minutes between calls to poll(); slower than that and "the consumer is considered failed and the group will rebalance"). That second timer is Kafka's version of a visibility timeout: a job slower than it gets its partition taken away mid-work.

Lag is how far a group is behind: the partition's latest offset minus the group's committed offset. Kafka ships "a tool that will show the position of all consumers in a consumer group as well as how far behind the end of the log they are" (kafka-consumer-groups.sh --describe, Kafka operations). Lag in messages is the log's queue depth; divide by the consume rate to get it in seconds, the number users feel.

Kafka as a queue, now. Because a partition goes to one consumer, Kafka was a poor job queue: one slow message holds up its whole partition, and parallelism is capped by the partition count. Kafka 4.2 (February 2026) made share groups ("Queues for Kafka", KIP-932) production-ready (Kafka 4.2 release): in a share group "partitions may be assigned to multiple consumers", "The number of consumers in a share group can exceed the number of partitions", "Records are acknowledged individually", and "Delivery attempts to consumers in a share group are counted" (Kafka design, The Share Consumer). A delivered record is locked for 30 seconds by default and can be acknowledged, released, rejected or renewed: the SQS model, inside Kafka. It was early access in 4.0 and a preview in 4.1.

Go deeper (optional). Kafka's design document is unusually readable: Kafka 4.3 design (about 1 h). Replication, ISR and KRaft: Distributed systems fundamentals.

Delivery semantics: at-most-once, at-least-once, "exactly-once"

Every consumer does two things with a message: the work (send the e-mail, write the embedding) and the acknowledgement (delete it from the queue, or commit the offset). A crash can land between them. Which one you do first decides what a crash costs you, and that choice has three names. Kafka's documentation defines them: "At most once: Messages may be lost but are never redelivered. At least once: Messages are never lost but may be redelivered. Exactly once: Each message is processed once and only once" (Kafka design, Message Delivery Semantics).

At-most-once: acknowledge, then work

msg = queue.receive() queue.delete(msg) # ack first send_receipt(msg.order) # crash here: receipt never sent

A crash after the ack loses the job. Kafka: the consumer "crashes after saving its position but before saving the output ... This corresponds to 'at-most-once' semantics". Fine for metrics samples or a "typing..." indicator; wrong for anything a user paid for.

At-least-once: work, then acknowledge

msg = queue.receive() send_receipt(msg.order) # crash after this line... queue.delete(msg) # ...and msg comes back: sent twice

A crash after the work but before the ack redelivers the job, which then runs again. Kafka: "the first few messages it receives will already have been processed. This corresponds to the 'at-least-once' semantics". This is the default almost everywhere, because a duplicate can be detected and a loss cannot.

Why not just "exactly once"? Because the sender cannot know what the receiver did. Kafka's docs give the producer's version: "If a producer attempts to publish a message and experiences a network error, it cannot be sure if this error happened before or after the message was committed." The consumer's version is the crash above. The general result is old. Jim Gray's 1978 notes prove that two parties who can only talk through messengers that may be lost cannot be certain they agree: "Let P be the shortest such protocol. Suppose the last messenger in P gets lost. Then either this messenger is useless or one of the generals doesn't get a needed message" (Gray, Notes on Data Base Operating Systems, §5.8.3.3.1; the "two generals" problem). So no protocol can make the delivery happen exactly once over a network that can lose messages. What systems offer instead is an effect that happens once: at-least-once delivery plus deduplication, sometimes called effectively-once or exactly-once processing.

Read the fine print on "exactly-once"
Kafka's own docs: "Many systems claim to provide 'exactly-once' delivery semantics, but it is important to read the fine print, because sometimes these claims are misleading (i.e. they don't translate to the case where consumers or producers can fail, cases where there are multiple consumer processes, or cases where data written to disk can be lost)." Two current examples: SQS FIFO's "exactly-once processing" means the queue drops a re-sent message with the same deduplication id "within the 5-minute deduplication interval" (SQS FIFO); a consumer that crashes before deleting still gets the message again. And an acknowledgement is only as good as the disk behind it: Jepsen found that NATS JetStream "calls fsync to flush data to disk only once every two minutes, but acknowledges messages immediately", and simulated power failures lost "roughly thirty seconds of writes" (Jepsen, NATS 2.12.1, 2025-12-08).

Where to say it in an interview: "at-least-once delivery, with idempotent consumers, so the effect happens once", then name the deduplication key. That shows you know delivery and effect are different things (advice kept from the old page).

Measured: crashes, redelivery and duplicates on a real Postgres

To see these semantics rather than take them on trust, this page ran three small experiments on a laptop (Apple M1 Pro, PostgreSQL 16 from the pgserver wheel, 2026-10-04; script src/lab/pg_lab.py, about 3 minutes in all). Everything is real: separate OS processes, real transactions, real row locks, real redelivery by timeout. The only artificial part is the crash, injected with os._exit() at a chosen line, which kills the process with no clean-up, as a kill signal or a power cut would.

The queue. A jobs table used the way SQS works. A worker claims the oldest visible job and hides it for a visibility timeout (2 s here), all in one statement:

UPDATE jobs SET visible_at = now() + interval '2 seconds', receives = receives + 1 WHERE id = (SELECT id FROM jobs WHERE visible_at <= now() ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING id, order_id, receives;

It then "sends a receipt" by inserting a row into a second database (standing in for an e-mail provider: outside the queue's transaction, as a real one would be) and finally deletes the job. Four worker processes, 1,000 jobs, a 5% chance of crashing per job; a supervisor restarts crashed workers, as systemd or Kubernetes would. Three runs per mode.

What 1,000 jobs became, three runs per mode

  • At-most-once (delete, then send): 52, 44 and 53 receipts lost, exactly one per crash. No error anywhere.
  • At-least-once (send, then delete): every order got its receipt, and 52, 46 and 53 customers got two. Again one per crash: the redelivered job runs in full.
  • At-least-once with an idempotent receiver: the receipts table has a primary key on the job id, so the second insert does nothing (ON CONFLICT DO NOTHING). Exactly 1,000 receipts in all three runs; the 52, 46 and 53 repeats were caught and counted.
  • No crashes at all, but a visibility timeout of 0.3 s with job times averaging 0.1 s (exponential, so about 5% of jobs take longer than 0.3 s): 20, 24 and 23 duplicates per 600 jobs. A slow job is indistinguishable from a dead worker; the queue hands it to a second worker while the first is still busy (visibility timeouts, below).

The expected count is simple: if each delivery crashes after the side effect with probability p, a job is delivered on average 1/(1 − p) times, so 1,000 jobs at p = 0.05 give about 1,000 × 0.05 / 0.95 = 52.6 duplicates; the three runs gave 50.3 on average. The Queue lab tab simulates the same queue with any settings; its model of these two runs, averaged over 20 seeds, gives 53.0 duplicates (range 38 to 76) for the crash run and 21.5 (range 15 to 28) for the 0.3 s timeout run, against 50.3 and 22.3 measured. The defaults of its two "Lab run" presets reproduce the measurement independently: the model shares the settings and was not fitted to the results (checked in src/recompute.py).

What Kafka's "exactly-once" really guarantees

Kafka is the system that most often advertises exactly-once (EOS, exactly-once semantics), so it is worth knowing precisely what it does. Two mechanisms, added in Kafka 0.11 (2017) by KIP-98:

1. The idempotent producer removes duplicates caused by producer retries. "The broker assigns each producer an ID and deduplicates messages using a sequence number that is sent by the producer along with every message" (Kafka design). If a send times out and is retried, the broker sees the same (producer id, sequence) and does not append it twice. It has been on by default since Kafka 3.0, together with acks=all (wait for all in-sync replicas), though "In 3.0.0 and 3.1.0, a bug prevented the idempotence default from being applied" until 3.0.1, 3.1.1 and 3.2.0 (Kafka 3.0 upgrade notes). It covers one producer session writing to one partition; it says nothing about consumers.

2. Transactions make read-process-write atomic. A stream processor reads from topic A, computes, and writes to topic B. Exactly-once there means: the output and the "I have consumed up to offset N" record become visible together or not at all. The steps, in brief:

  1. The producer is configured with a transactional.id, a stable name that survives restarts. A broker acting as transaction coordinator keeps the state of its transactions in an internal, replicated transaction log.
  2. On start, the producer registers its transactional.id; the coordinator bumps an epoch number, so "any previous zombie instance of the producer is fenced off" (KIP-98). A zombie is an old instance that was presumed dead but is still running; fencing means its writes are rejected.
  3. Within a transaction the producer writes output records to any partitions, and also the consumer's new offsets (sendOffsetsToTransaction). "The consumer's position is stored as a message in an internal topic, so we can write the offset to Kafka in the same transaction as the output topics" (Kafka design).
  4. On commit, the coordinator writes COMMIT markers into every partition involved. Downstream consumers with isolation.level=read_committed only see records of committed transactions. The default is read_uncommitted, which shows aborted records too (consumer configs).

The scope is Kafka to Kafka. The docs: the transactional producer and read-committed consumer "can be used generally to provide exactly-once delivery when reading, processing and writing data on Kafka topics. Exactly-once delivery for other destination systems generally requires cooperation with such systems ... Otherwise, Kafka guarantees at-least-once delivery by default." If the consumer's work is "send an e-mail" or "write to Postgres", Kafka's transaction cannot include it; you are back to at-least-once plus deduplication, or to storing the offset in the same database transaction as the output, which the docs recommend: "letting the consumer store its offset in the same place as its output".

Correction to the old page
The old "Distributed Systems Basics" page listed "Kafka transactional producer + idempotent consumer offsets" as a way to get exactly-once processing. "Idempotent consumer offsets" is loose: what Kafka does is commit the consumer's offsets inside the producer's transaction, and that gives exactly-once only when input and output are both Kafka topics. Any external effect still needs its own deduplication.

What it costs, and how solid it is. Confluent's 2017 measurement: with 1 KB messages and 100 ms transactions, producer throughput fell 3% against an at-least-once, in-order producer, and 20% against the then-default acks=1 (Narkhede, Confluent, 2017); with Kafka Streams and a 100 ms commit interval the loss was 15 to 30%. The docs add that "using a replication factor lower than 3 effectively voids EOS" (recommend 3 with min.insync.replicas=2, Kafka Streams docs). And the protocol had real bugs: in 2024 Jepsen found that "There is no concept of a transaction number. When a server receives a commit (or abort) message, it has no way to know what transaction the client intended to commit", reproduced aborted reads and torn transactions in Kafka itself (KAFKA-17754), and Kafka's engineers expected KIP-890 to fix it (Jepsen, Bufstream 0.1.0, 2024-11-12). KIP-890 bumps the epoch "after every commit/abort marker" so each transaction is identified by (producer id, epoch) (KIP-890); its second phase shipped in Kafka 4.0, where it "reduces the chances of 'zombie transactions'" (Kafka 4.0 release). Whether KAFKA-17754 is fully closed was not checked for this page.

When not to use Kafka transactions: when the output is not a Kafka topic (they cannot cover it), and when a duplicate is cheap to absorb downstream (an idempotent consumer is simpler and faster).

Idempotent consumers and deduplication

At-least-once delivery is safe only if running a job twice does no harm. An operation is idempotent when doing it twice has the same effect as doing it once. There are four ways to get there, from cheapest to most general.

  1. Make the work naturally idempotent. Write absolute values, not increments: "set document 981's embeddings to X" instead of "append embeddings"; UPDATE ... SET status = 'paid' instead of balance = balance + 10; write a file to a path derived from its input and overwrite. Kafka's docs note the common case: "In many cases messages have a primary key and so the updates are idempotent (receiving the same message twice just overwrites a record with another copy of itself)". Costs nothing; not always possible (an e-mail cannot be "set").
  2. Record what you processed, in the same transaction as the effect. This is the idempotent consumer pattern: "the message handler inserts the message's ID into the PROCESSED_MESSAGE table. Since the (subscriberId, messageID) is the PROCESSED_MESSAGE table's primary key the INSERT will fail if the message has been already processed successfully" (microservices.io, Idempotent Consumer). The id must come from the producer (an event id, an order id), never be generated by the consumer. Works whenever the effect lives in your own database.
  3. Pass an idempotency key to the system that does the effect. When the effect is in someone else's system (a payment, an e-mail provider, a model provider), send a key derived from the message (Idempotency-Key: order-42-receipt) and let them deduplicate. Stripe-style idempotency keys, and how a server should implement them, are on Building a backend API. The client half (when to retry) is on Reliability engineering.
  4. Version or sequence checks for state updates that can arrive out of order: keep a version per entity and ignore a message whose version is not newer (UPDATE orders SET ..., version = 7 WHERE id = 42 AND version < 7). Deduplicates and reorders at once.

The code for way 2, in Python with psycopg (the same shape the measured lab used, with the effect in the consumer's own database):

def handle(msg): # called for every delivery, including redeliveries with conn.transaction(): cur = conn.execute( "INSERT INTO processed_events (event_id) VALUES (%s) ON CONFLICT DO NOTHING", (msg["event_id"],)) if cur.rowcount == 0: return # seen before: do nothing, but still ack conn.execute("INSERT INTO receipts (order_id, ...) VALUES (%s, ...)", (msg["order_id"],)) queue.ack(msg) # a crash before this line is now harmless
What it costs
A row per processed message, so the table needs an expiry: keep ids for longer than the longest possible redelivery window (the broker's retention or maximum retry period), then delete them. A dedup window shorter than the redelivery window lets duplicates through: SQS FIFO's 5-minute window means a re-send after 6 minutes is a new message. Some producers send two different ids for one change: Stripe warns that "two separate Event objects are generated and sent" in some cases and says to deduplicate by "the ID of the object in data.object along with the event.type" (Stripe webhooks). Choose the key by what must happen once, not by what the transport calls a message.

Visibility timeouts, leases and redelivery

How does a queue know a worker died? It cannot see the process; it can only see that no acknowledgement came. So it lends each message out for a fixed time. SQS calls it the visibility timeout: "The visibility timeout starts as soon as a message is delivered to you. During this period, you're expected to process and delete the message. If you don't delete it before the timeout expires, the message becomes visible again" (SQS visibility timeout); default 30 s, maximum 12 h. The general name for a time-limited claim is a lease. Every system has one under some name: Kafka's max.poll.interval.ms (5 minutes), Kafka share groups' record lock (30 s), Celery on Redis's visibility_timeout (1 hour), RabbitMQ's redelivery when a consumer's channel closes.

The timeout trades two failures against each other:

  • Too short: a slow job looks dead and is handed to a second worker while the first is still working: duplicates without any crash (measured above: 20 to 24 per 600 jobs at a 0.3 s timeout). Even a correct setting is not a hard guarantee: SQS says "there's no absolute guarantee that a message won't be delivered more than once during the visibility timeout period".
  • Too long: after a real crash the job waits the whole timeout before anyone retries it; with a 12-hour timeout, a crashed job is 12 hours late.

The production answer is a timeout comfortably above the normal job time plus a heartbeat: a long job periodically extends its own lease. SQS: "use the ChangeMessageVisibility action to extend the visibility timeout while processing the message", within the 12-hour limit from first receipt; Kafka share groups added a RENEW acknowledgement in 4.2 "for extended processing times". To give a message back early (you cannot handle it now), set its timeout to 0.

A real trap: Celery's defaults
Celery acknowledges before running a task by default: "the default behavior is to acknowledge the message in advance, just before it's executed, so that a task invocation that already started is never executed again" (Celery 5.6.3 tasks guide). That is at-most-once: a worker killed mid-task loses the task. task_acks_late = True makes it at-least-once, but "Even if task_acks_late is enabled, the worker will acknowledge tasks when the worker process executing them abruptly exits or is signaled" unless task_reject_on_worker_lost = True, which the docs warn "can cause message loops" (Celery configuration). On Redis, a task not acknowledged within the 1-hour visibility timeout "will be redelivered to another worker and executed", which breaks ETA and countdown tasks scheduled further out than that: "it will be executed again, and again in a loop" (Celery Redis broker).

Dead-letter queues and poison messages

A poison message is one that fails every time: malformed data, a bug triggered by one input, a document too large to embed. Under at-least-once delivery it comes back forever, wasting a worker each time, and in an ordered stream it blocks everything behind it. The fix is a dead-letter queue (DLQ): after N failed attempts the message is moved aside to a separate queue for a human or a repair job. SQS: "The maxReceiveCount is the number of times a consumer can receive a message from a source queue before it is moved to a dead-letter queue" (SQS DLQs). RabbitMQ quorum queues count deliveries and default to a limit of 20 since 4.0; without a dead-letter exchange configured, a message over the limit is dropped (quorum queues). Dramatiq moves a message to its dead letter queue after its retries (20 by default) "where it's kept for up to 7 days and then automatically dropped" (Dramatiq 2.2.1 guide). Kafka consumer groups have no built-in DLQ: the application (or Kafka Connect's error handling) writes failures to a separate topic; share groups count delivery attempts and let a consumer reject a record.

Three rules, all about what happens after:

  • Alert on DLQ depth. A DLQ nobody watches is a slower way of losing data. Any message in it means a customer's job did not happen.
  • Design the replay path before you need it. SQS has a "dead-letter queue redrive" that moves messages back to the source queue once the bug is fixed; elsewhere you write a script. Because replayed messages run again, the consumer must be idempotent (previous section). Keep DLQ retention longer than the source queue's: AWS calls it "a best practice to always set the retention period of a dead-letter queue to be longer than the retention period of the original queue."
  • Mind ordering. Moving a message aside lets later ones overtake it: "Don't use a dead-letter queue with a FIFO queue if you don't want to break the exact order of messages or operations" (AWS). For ordered streams, either stop and page someone, or park every later message for the same key too.

How often to retry before dead-lettering, and with what backoff and jitter, is retry policy: owned by Reliability engineering, whose measured retry storm shows why retries without a budget make outages worse.

Backpressure and Little's law on a queue

A queue absorbs bursts: if uploads arrive at 3 times the usual rate for a minute, the queue grows and then drains. But it absorbs everything, including overload that never ends, and it does so silently. David Yanacek of Amazon describes the two modes: "When there is no backlog in the queue, the system's latency is low, and the system is in fast mode. But if a failure or unexpected load pattern causes the arrival rate to exceed the processing rate, it quickly flips into a more sinister operating mode. In this mode, the end-to-end latency grows higher and higher" (Yanacek, Avoiding insurmountable queue backlogs, Amazon Builders' Library; quotes checked against the 2024 archived copy).

The arithmetic. Call the arrival rate λ (messages per second), the time one worker needs per message S, and the number of workers C. The workers can finish at most C / S messages per second, so the utilisation is ρ = λS / C.

  • If ρ < 1 the queue stays short on average, but waiting time rises steeply as ρ approaches 1 (with random arrivals, a queue at 90% utilisation waits several times longer than at 50%; the shape and the formulas are on Capacity planning and performance).
  • If ρ > 1 the backlog grows by λ − C/S messages every second, forever. Adding queue space does not help; only more workers, less work per message, or fewer messages do.
  • Worse, a backlog can keep itself alive after the cause is gone: old messages time out at their callers, who retry and add more. Bronson et al. call this a metastable failure, "a bad state that persists even when the trigger is removed" (Metastable Failures in Distributed Systems, HotOS 2021). Hence the old page's rule: bound the queue, and prefer rejecting at admission over timing out deep in the stack.
  • Draining a backlog of B messages takes B / (C/S − λ): only the spare capacity drains it. Yanacek: after an hour-long outage, "recovering from the outage requires double the system's capacity for another hour after the recovery", and a backlog "10x the capacity that the consumer side was scaled to" took "300 minutes" to work through.

Little's law ties the averages together: "the average number of items in a queuing system, denoted L, equals the average arrival rate of items to the system, λ, multiplied by the average waiting time of an item in the system, W. Thus, L = λW" (Little, Operations Research 59(3), 2011). It holds for long-run averages of a stable system, whatever the distributions; a backlog that keeps growing has no stable average, so the law does not describe it. Two uses: size workers (embedding 5 documents a second at 20 s each keeps 5 × 20 = 100 jobs in progress, so at least 100 worker slots: the parent root's example), and turn a backlog into a wait (500 messages in the queue at 50 per second means about 10 s of waiting). Yanacek uses it to show how latency spikes eat thread pools: 100 messages a second at 100 ms is 10 busy threads; at 10 s it is 1,000. The Queue lab checks L against λW on every run.

Backpressure is how "we cannot keep up" travels back to whoever produces the work, so the system degrades at the edge instead of everywhere:

  • Bound the queue and reject at admission: when the queue is over its limit, the API answers 429 Too Many Requests (RFC 6585 says it "MAY include a Retry-After header", RFC 6585 §4) or 503, and the client backs off. Fail fast at the door rather than time out deep inside.
  • Block the producer: Kafka's producer buffers up to buffer.memory and then blocks send() for up to max.block.ms (producer configs); a bounded asyncio.Queue(maxsize=...) makes await q.put() wait.
  • Limit what each consumer holds: RabbitMQ's prefetch "defines the max number of unacknowledged deliveries that are permitted on a channel" (RabbitMQ confirms); Celery prefetches 4 messages per process by default (worker_prefetch_multiplier), which is why long tasks are usually run with 1.
  • Credit-based flow control in protocols: HTTP/2 and gRPC use per-stream windows (WINDOW_UPDATE, RFC 9113 §5.2); depth on Topic: protocols.
  • Shed or sideline old work: when a backlog has formed, the newest work is often the most valuable. Yanacek: real-time systems "often are implemented with FIFO-ish queues, but prefer LIFO-ish behavior"; Amazon moves messages older than a threshold "into a backlog queue that we work through only after we're caught up on the live queue", drops messages a periodic full sync will redo anyway, and isolates noisy customers by hashing each to a few of many queues (shuffle sharding). Load shedding by priority is on Reliability engineering.

What to watch: the age of the oldest message, not just the queue length. Yanacek: "we focus more on measuring the age of messages that are in the queue. This quickly catches cases where the systems are behind, or are frequently erroring out and causing retries." In SQS that is ApproximateAgeOfOldestMessage; in Kafka, lag converted to time. The parent root's Case files hold a real example of a backlog that never drained ("EC2 could not hand out servers: a queue that never drained", the root's Case files tab).

The dual-write problem and the transactional outbox

When an order is placed, the order service must save the order in its database and publish "order placed" for the e-mail service, the warehouse and analytics. That is a dual write: two writes to two systems that share no transaction. Gunnar Morling, then Debezium's lead: "we cannot have one shared transaction that would span the service's database as well as Apache Kafka, as the latter doesn't support to be enlisted in distributed (XA) transactions" (Debezium blog, 2019-02-19). Whichever write goes first, a crash between them leaves the two systems disagreeing. Watch the same order go through three designs:

Animation: order 42, with a naive dual write and with the outbox

Crash points are the ones the measured lab injects; counts in the captions are from that lab (500 orders, 5% crash chance, three runs).

The transactional outbox (Chris Richardson's name for it): "the service that sends the message to first store the message in the database as part of the transaction that updates the business entities. A separate process then sends the messages to the message broker" (microservices.io, Transactional outbox). Its cost is stated on the same page: the relay "might, for example, crash after publishing a message but before recording the fact that it has done so. When it restarts, it will then publish the message again. As a result, a message consumer must be idempotent". So the outbox converts "sometimes lost" into "sometimes duplicated", and the idempotent consumer converts that into "once".

Measured on the same laptop Postgres (the "broker" is a second database, so there is genuinely no shared transaction; 500 orders, 5% crash chance at the dangerous line, three runs):

With a batch of 10 events per relay transaction, a crash mid-batch rolls back every "sent" mark in the batch, so all of them are published again: about 4 to 5 duplicates per crash. With one event per transaction, duplicates equal crashes. Batching is faster; it multiplies duplicates.

Two ways to run the relay

  • Polling publisher: "Publish messages by polling the database's outbox table" (microservices.io). A loop runs SELECT ... WHERE sent_at IS NULL ORDER BY seq LIMIT 100 FOR UPDATE SKIP LOCKED, publishes, marks sent. Simple, works on any database, adds polling load and a little latency; several relays can run thanks to SKIP LOCKED, but then strict ordering across them is lost.
  • Transaction log tailing, or change data capture (CDC): "Tail the database transaction log and publish each message/event inserted into the outbox to the message broker" (microservices.io). In Postgres this uses logical decoding, "the process of extracting all persistent changes to a database's tables into a coherent, easy to understand format" (PostgreSQL docs), which reads the write-ahead log (WAL). Debezium is the standard tool: its Postgres connector reads the WAL, and its Outbox Event Router expects an outbox table with columns id, aggregatetype, aggregateid, type and payload, routing each row by default to a topic named outbox.event.<aggregatetype> with aggregateid as the message key (Debezium outbox event router). No polling, ordered by commit; costs a Kafka Connect deployment and a replication slot to monitor (an abandoned slot makes Postgres keep WAL forever). Delivery is still at-least-once: "while it is recovering from the fault, it's possible that the connector might emit some duplicate change events" (Debezium Postgres connector).

The receiving side has a mirror pattern, the inbox: store each incoming message's id (and often the message) in the consumer's database in the same transaction as its effects, which is the idempotent consumer by another name. MassTransit: "The inbox is used to keep track of received messages to guarantee exactly-once consumer behavior" (MassTransit); NServiceBus "uses the message identity (MessageId) to deduplicate messages" (NServiceBus outbox).

When you do not need an outbox: when the queue lives in the same database. Postgres-backed job queues let you enqueue in the same transaction as your data: River "encourages the use of the same database for application data and job queue. By enqueueing jobs transactionally along with other database changes, whole classes of distributed systems problems are avoided" (River docs); Oban lists "Transactional Control: Enqueue a job along with other database changes, ensuring that everything is committed or rolled back atomically" (Oban). The outbox is such a queue, with a relay that forwards to Kafka for the consumers that live elsewhere.

Webhooks are the same problem facing outwards. Sending a webhook to a customer after a database change is a dual write to their server. The sending side uses an outbox (write "deliver event X to customer Y" in the transaction, deliver from a worker with retries); the receiving side answers 2xx at once and queues the work. Stripe: "Your endpoint must quickly return a successful status code (2xx) before any complex logic that could cause a timeout", and it retries "for up to three days with an exponential back off in live mode" (Stripe webhooks). GitHub expects a 2XX "within 10 seconds" and "does not automatically redeliver failed deliveries" (GitHub best practices, failed deliveries), so a receiver that is down simply misses them. Webhook API design (signatures, payloads) is on Building a backend API.

What the outbox costs
A table that grows (delete or partition sent rows), a relay process or a CDC pipeline to run and monitor, events that arrive a little later than the commit, and duplicates every consumer must absorb. When not to use it: when the event is not critical (a lost analytics ping is fine), or when the consumers can read your database's job queue directly.

Sagas versus two-phase commit

The outbox makes one service's write and event atomic. A business action often spans several services, each with its own database: the chat product's "upgrade to Pro" must charge the card (payments service), raise the user's token quota (quota service) and send a receipt (e-mail). If the quota update fails after the charge, the user has paid for nothing. Two families of answer:

Two-phase commit (2PC) makes several databases commit together. A coordinator asks every participant to prepare (do the work, hold the locks, promise to commit if told); if all say yes it tells all to commit, otherwise all abort. Its weakness was stated by Jim Gray and Leslie Lamport: "The classic Two-Phase Commit protocol blocks if the coordinator fails" (Gray and Lamport, Consensus on Transaction Commit): prepared participants hold their locks and cannot decide alone. Postgres supports the prepare step but warns "PREPARE TRANSACTION is not intended for use in applications ... Unless you're writing a transaction manager, you probably shouldn't be using PREPARE TRANSACTION" (PostgreSQL docs). And most systems a service talks to (Kafka, SaaS APIs, a payment provider) cannot take part at all. 2PC lives on inside distributed databases (Spanner, CockroachDB), run over consensus so the coordinator cannot simply vanish; the theory is on Distributed systems fundamentals.

A saga gives up atomicity and adds undo. The idea is from Garcia-Molina and Salem (1987): a long transaction "is a saga if it can be written as a sequence of transactions that can be interleaved with other transactions", and the system "guarantees that either all the transactions in a saga are successfully completed or compensating transactions are run to amend a partial execution" (Sagas, SIGMOD 1987). In services: "A saga is a sequence of local transactions. Each local transaction updates the database and publishes a message or event to trigger the next local transaction in the saga. If a local transaction fails because it violates a business rule then the saga executes a series of compensating transactions" (microservices.io, Saga).

The same upgrade, three ways
  • Choreography or orchestration. In choreography "each local transaction publishes domain events that trigger local transactions in other services"; in orchestration "an orchestrator (object) tells the participants what local transactions to execute" (microservices.io). Choreography has no central piece but the flow is spread across services and hard to see; orchestration puts the flow in one place, which is what durable workflow engines (below) are built for.
  • Compensations are business actions, not rollbacks. "Refund the charge" is not "the charge never happened": the customer may have seen it, a receipt may be out. Some steps cannot be compensated (an e-mail sent); put them last.
  • No isolation. Between steps, others see the half-done state. The 1987 paper: "other transactions might see the effects of a partial saga execution"; microservices.io lists "Lack of isolation" as the main drawback. Defences: a status field (PENDING) that other code respects, re-reading values before acting, ordering steps so the riskiest comes first.
  • Every step and every compensation runs at least once, because it is driven by messages: each must be idempotent.
When not to use either: if all the data can live in one database, use one transaction. Splitting data across services is what creates the need for sagas; do it for a reason.

Event-driven architecture, event sourcing and CQRS, in brief

In an event-driven architecture, services announce facts ("order 42 placed") on a log instead of calling each other ("e-mail service, send a receipt"). The old page listed the trade, and it holds: the benefits are temporal decoupling (the e-mail service can be down and catch up later), fan-out (any number of consumers per event, added without touching the producer), a natural audit trail, and replay (rebuild a projection by re-reading the log); the costs are eventual consistency between views, harder end-to-end tracing (use trace ids propagated in message headers: Observability), and schema discipline. Two distinctions that prevent most design mistakes:

  • Events versus commands. An event is a fact in the past tense, owned by its producer, with any number of readers. A command ("send receipt") is a request to one recipient that may refuse. Putting commands on a shared log hides who is responsible.
  • Thin versus fat events. A thin event carries ids ("order 42 changed"), and the consumer fetches current data; a fat event carries the data. Thin events are always current and leak less; fat events let consumers work while the producer is down. Schema changes must be backward compatible (add optional fields, never rename or remove), usually enforced by a schema registry (old page, kept as practice).

Event sourcing goes further: the events are the source of truth. Martin Fowler: "every change to the state of an application is captured in an event object, and that these event objects are themselves stored in the sequence they were applied for the same lifetime as the application state itself" (Fowler, Event Sourcing, 2005); current state is computed by replaying them. CQRS (command query responsibility segregation) uses "a different model to update information than the model you use to read information" (Fowler, CQRS, 2011); event sourcing usually needs it, and a Kafka-to-ClickHouse analytics pipeline is a mild form of it.

When not to
Fowler on CQRS: "beware that for most systems CQRS adds risky complexity." Microsoft's architecture guide on event sourcing (2026): "It's costly to migrate to or from an event sourcing solution ... For most systems and most parts of a system, traditional data management is sufficient", and it is not suitable when systems "have straightforward CRUD operations that don't require auditability, replay, or historical reconstruction of state" (Azure Architecture Center, Event Sourcing). The same page corrects a common belief: "Message brokers such as Apache Kafka typically lack per-entity stream queries and optimistic concurrency. They work well as a distribution layer ... but they aren't a substitute for an event store." The old page's verdict, "rarely worth it outside ledgers", is an opinion, but it matches both sources. For an ML platform the useful part is the log, not event sourcing: usage events, feedback events and pipeline triggers fanned out from one stream (on AWS: EventBridge or SNS into SQS into Lambda, each with a DLQ and idempotent handlers).

Durable workflows are for jobs with many steps that must survive crashes for minutes to weeks: an agent run, a saga, onboarding with waits. Instead of chaining queue messages by hand, you write the steps as ordinary code and the engine records each completed step, so after a crash it resumes from the last one. Temporal calls this durable execution: a workflow keeps its state and progress through failures, crashes and server outages (Temporal docs). Two rules come with it. Workflow code must be deterministic: run again on the same input it must make "the same Workflow API calls in the same sequence" (workflow definition), because the engine rebuilds state by replaying the recorded history; so no clocks, random numbers or network calls in the workflow itself. Side effects go in activities, which are retried by default (1 s initial interval, backoff 2.0, up to 100 s, unlimited attempts, retry policies), so "Temporal recommends that Activities be idempotent" (activity definition). Lighter alternatives keep the state in your own Postgres (DBOS: "Add a few annotations to your application to durably execute it", DBOS) or in a log (Restate); Cloudflare Workflows "persist state for minutes, hours, or even weeks" (Cloudflare).

When not to: a single-step job is a plain queue's work; a workflow engine is a new system and a new programming model (the determinism rule bites people). Reach for one when you find yourself writing a state machine over queue messages with timeouts and compensations.

Scheduling and cron

Scheduled work (nightly evaluation, hourly usage roll-ups, cleanup of old outbox rows) looks simple and fails in its own ways. Classic cron runs a command on one machine at set times, so it inherits that machine's fate: if the machine is down at 02:00, the job does not run; if two machines both have the crontab, it runs twice. Distributed schedulers make the same trade explicit. Kubernetes: "A CronJob creates a Job object approximately once per execution time of its schedule. The scheduling is approximate because there are certain circumstances where two Jobs might be created, or no Job might be created ... Therefore, the Jobs that you define should be idempotent" (Kubernetes CronJob). Celery: "You have to ensure only a single scheduler is running for a schedule at a time, otherwise you'd end up with duplicate tasks" (Celery periodic tasks).

  • Key each run by its scheduled time, not by "now": the 02:00 roll-up for 2026-10-03 writes to a partition named for that date and overwrites it. A rerun, a duplicate or a backfill then produces the same result. Airflow's best practices say the same of pipeline tasks: "Airflow can retry a task if it fails. Thus, the tasks should produce the same outcome on every re-run" (Airflow best practices): write outputs to deterministic locations and overwrite, never append.
  • Decide what overlap means. Kubernetes' concurrencyPolicy is Allow by default (runs may overlap); Forbid skips a run while the previous one is still going; Replace kills the old one.
  • Decide what a missed run means. startingDeadlineSeconds skips a run that could not start in time; without it, Kubernetes will not start a job that has missed more than 100 schedules.
  • Let the scheduler only enqueue. The scheduler puts a message on the queue; ordinary workers, with their retries, DLQ and idempotency, do the work.

Async work around LLMs

LLM products stretch every idea on this page, because one unit of work can take a second (a chat reply), minutes (a deep-research answer, an agent run) or hours (a batch over a million documents), and costs real money each time it runs.

Stream to the user while the work continues

The chat reply stays on the request path but is streamed: the server sends tokens as they are generated over server-sent events (SSE), one long HTTP response with one event per chunk. Anthropic: set "stream": true "to incrementally stream the response using server-sent events (SSE)" (Anthropic streaming). The design question is what happens when the connection drops halfway. If generation is tied to the HTTP connection, a closed tab or a phone switching networks kills a paid-for answer. The better shape separates the two: the generation runs as a background job writing chunks somewhere durable, and the HTTP stream is just a reader that can reconnect. Vercel's AI SDK: "In a resumable stream setup, client-side aborts are treated as disconnects. Closing a tab, refreshing the page, or calling stop() only closes the current HTTP connection and should not cancel the underlying generation" (AI SDK resumable streams). OpenAI's background mode does it on the provider side: create a response with background and stream both true and "keep track of a 'cursor' corresponding to the sequence_number you receive in each streaming event", then resume with starting_after (OpenAI background mode). Note its retention: "Response data is temporarily stored to disk for roughly 10 minutes to enable asynchronous execution and polling". Server-sent events in API design: Building a backend API.

Long-running agent jobs

An agent run is a saga of model calls and tool calls, some with side effects (open a pull request, send an e-mail, charge a card). Treat it as a durable workflow: return 202 with a run id, execute the steps in a worker or workflow engine that records each completed step, and push progress to the client (SSE or WebSocket) or let it poll. Three rules from the sections above, applied:

  • Every tool call with a side effect carries an idempotency key derived from the run id and step number, because a crashed run will be resumed and a timed-out call retried (idempotent consumers).
  • Record model outputs as completed steps, so a resumed run does not pay for the same tokens again; that is the point of durable execution for agents. Temporal's announcement of its OpenAI Agents SDK integration (public preview, July 2025): "Temporal keeps track of application progress and stores all Activity results" (Temporal blog, vendor post). An OpenAI infrastructure VP is quoted in Temporal's September 2026 funding post as saying OpenAI built "a durable orchestration framework powered by Temporal" (Temporal, 2026-09-14; a vendor post, not an OpenAI source).
  • Leases must outlast the slowest step or be renewed: a 20-minute agent step on a queue with a 5-minute visibility timeout runs four times in parallel (visibility timeouts).

Batch APIs: a queue the provider runs for you

For work that can wait hours (evaluations, re-embedding a corpus, classifying a backlog), providers sell a queue with a discount: OpenAI's Batch API offers "50% lower costs, a separate pool of significantly higher rate limits, and a clear 24-hour turnaround time" (OpenAI Batch); Anthropic's Message Batches have "most batches finishing in less than 1 hour while reducing costs by 50%", up to 100,000 requests or 256 MB per batch (Anthropic batch processing). Your side is still a job: submit, store the batch id, poll or get notified, fetch results, and handle the requests that expired or failed (resubmit them, idempotently, keyed by your own request ids). When to batch and what it saves is on ML system design.

A queue in front of the GPUs

Inference servers queue requests internally and batch them on the GPU (the parent root's Step 5). Two lessons from this page carry over: a queue in front of a GPU pool must be bounded and shed load early, because an unbounded one turns a traffic spike into minutes of latency for everyone (the degradation ladder and priorities are on ML system design); and autoscaling should follow queue depth or the age of the oldest request, not CPU. Common mistakes

Assuming the queue gives exactly-once
Every common broker delivers at least once in practice. Design every consumer to receive a message twice; test it by delivering twice.
Generating the dedup id in the consumer
A random id made on receipt is new on every redelivery, so nothing is ever deduplicated. The id must come from the producer, or be derived from the content (order id plus event type).
Running Celery with default acks for important work
The default acknowledges before running, so a killed worker loses the task. Use acks_late plus reject_on_worker_lost, and idempotent tasks.
A visibility timeout shorter than the slowest job
Slow jobs run on two workers at once (measured above). Set it above p99, or heartbeat.
Publishing an event right after a commit, "it is usually fine"
It is fine until a deploy or crash lands between the two lines; then events are lost silently (measured: one per crash). Use an outbox, or enqueue in the database.
Watching queue length instead of message age
A queue of 10,000 may be healthy (fast consumers) and a queue of 50 may be stuck (one poison message retried forever). Age tells you which.
No DLQ, or a DLQ nobody watches
Without one, a poison message burns a worker forever (try it in the Queue lab); with an unwatched one, failed jobs vanish quietly.
More consumers than partitions
In a Kafka consumer group the extra consumers sit idle. Plan partition counts for peak parallelism, or use share groups (Kafka 4.2+).
Changing the partition count of a keyed topic
Keys move to new partitions, so per-key ordering breaks across the change (try it in the Kafka widget above).
Doing slow work inside the database transaction that holds the job lock
Fine for milliseconds (the throughput experiment did it), harmful for minutes: long transactions hold locks and stop Postgres from cleaning up old row versions. For long jobs use a lease (a visible_at column) and commit the claim at once.
Unbounded queues in front of expensive resources
Bound them, reject early with 429, and scale on queue age. An unbounded queue in front of a GPU pool turns a spike into minutes of latency for everyone.

Glossary

Request path: everything between a request arriving and its response.
Message queue: a broker that deletes each message once a worker acknowledges it.
Log (stream): an append-only, retained sequence of messages read by position.
Message: one unit of handed-off work or information (job, event).
Producer: writes messages.
Consumer, worker: reads and handles messages.
Broker: the system that stores messages between them.
Acknowledge (ack): tell the broker a message is done.
Competing consumers: several workers sharing one queue.
Offset: a message's position in a log partition; a reader's progress.
Topic: a named log in Kafka.
Partition: one of the ordered sub-logs a topic is split into.
Key: the value hashed to choose a message's partition.
Consumer group: consumers sharing a topic's partitions, one consumer per partition.
Rebalance: reassigning partitions when group members change.
Commit (offsets): saving a consumer's position.
Share group: Kafka's queue mode (4.2+): many consumers per partition, per-record acks.
At-most-once: ack before work; may lose, never repeats.
At-least-once: ack after work; never loses, may repeat.
Effectively-once: at-least-once delivery plus deduplication, so the effect happens once.
Idempotent producer: Kafka broker drops retried sends by producer id and sequence.
Zombie: an old instance presumed dead but still running; fenced by epochs.
Idempotent: doing it twice has the same effect as once.
Idempotent consumer: records processed message ids with its effects, skipping repeats.
Visibility timeout: how long a claimed message stays hidden before redelivery.
Lease: any time-limited claim on work.
Heartbeat: periodically extending a lease while still working.
Poison message: a message that fails every time.
Dead-letter queue: where messages go after too many failed attempts.
Utilisation: ρ = λS / C, the share of worker capacity in use.
Little's law: L = λW for a stable system's averages.
Backpressure: telling producers to slow down when consumers cannot keep up.
Dual write: writing to two systems with no shared transaction.
Transactional outbox: write the event to a table in the same transaction; relay it later.
Change data capture: reading a database's changes from its log (Debezium).
Inbox: the receiving side's table of handled message ids.
Two-phase commit: prepare everywhere, then commit everywhere; blocks if the coordinator fails.
Saga: a sequence of local transactions with compensations for failure.
Event-driven architecture: services announce facts on a log instead of calling each other.
Event sourcing: the event log is the source of truth; state is replayed from it.
CQRS: separate models for writing and reading.
Task queue library: Celery, RQ, Arq, Dramatiq, Procrastinate.
Activity: a durable workflow's side-effecting step, retried by the engine.
Cron: running jobs at set times.

Queue lab

A simulated queue with the semantics of SQS (and of the measured Postgres queue): messages arrive, wait, are claimed by workers, hidden for a visibility timeout, and deleted when a worker acknowledges them after doing the side effect. You choose the traffic, the workers, the timeout and how often workers crash, and watch the backlog, the age of the oldest message, redeliveries and duplicates. Everything runs in your browser, deterministic for a given seed; the same model in Python is qsim in src/recompute.py.

Try: start with "Healthy" and raise the arrival rate until utilisation passes 100%: the backlog stops draining and the age of the oldest message climbs without limit. Load "Crashes, naive", then tick the idempotent consumer: redeliveries stay, duplicates vanish. Load "Poison, no DLQ" and set max receives to 5. Load the two "Lab run" presets to compare the model with the real Postgres runs.

The model, exactly
  • Arrivals: Poisson at rate λ for T seconds (optionally 3 times λ from T/4 to T/2), or a backlog of N messages at time 0. The run lasts 1.5 T (steady) or T (backlog), so a steady run shows the drain after arrivals stop.
  • Waiting messages are claimed oldest first (a redelivered message goes to the front, as ORDER BY id did in the measured lab). A claim hides the message for the visibility timeout V.
  • Service time: exponential with mean S, or fixed S. At the end of service: the side effect, then the acknowledgement (delete).
  • Crash: with probability p per delivery, after the side effect and before the acknowledgement (the dangerous spot). The worker is down for the restart time, then takes new work. The message reappears when its timeout expires.
  • If a message's timeout expires while its first worker is still busy, another worker may take it; both do the side effect (a duplicate) and the second acknowledgement finds it already deleted.
  • Idempotent consumer: a repeated side effect is detected and skipped (counted as "caught").
  • Poison messages (a fraction of arrivals) fail every time: no effect, no acknowledgement. With max receives M > 0, a message already received M times goes to the dead-letter queue when it is next claimed (the SQS maxReceiveCount rule).
  • Queue bound B: an arrival finding B messages in the system is rejected (the producer would get 429).
  • Little's law check: L is the time-average number of messages in the system over the run; X is completions per second; W the mean time from arrival to acknowledgement. L = XW when the queue ends empty.
