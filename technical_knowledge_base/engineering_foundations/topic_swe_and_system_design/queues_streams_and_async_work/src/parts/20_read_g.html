Job queues for Python, and when to reach for a workflow engine

Most Python services use a task queue library: decorate a function, call .delay() or enqueue() in the handler, and worker processes run it. What separates them is the broker and, above all, the delivery default:

Measured: a Postgres queue scales only because workers skip each other's rows

400 jobs of 5 ms each on the laptop, the worker holding the row lock while it works. With plain FOR UPDATE every worker queues on the same first row, so 8 workers are no faster than 1 (about 123 jobs a second). With SKIP LOCKED each takes a different row: 960 jobs a second with 8 workers, against an ideal of 1,600 (8 / 5 ms; the gap is Postgres round trips and the timer granularity of time.sleep). Postgres: "Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table" ({{SELECT docs|https://www.postgresql.org/docs/current/sql-select.html}}). Same script, src/lab/pg_lab.py.

Holding the lock while working is fine for milliseconds and harmful for minutes: long transactions hold locks and stop Postgres from cleaning up old row versions. For long jobs, claim with a lease (a visible_at column, as the measured queue did) and commit the claim at once.

Durable workflows are for jobs with many steps that must survive crashes for minutes to weeks: an agent run, a saga, onboarding with waits. You write the steps as ordinary code; the engine records each completed step and, after a crash, resumes from the last one. Temporal calls this durable execution: a workflow keeps its state and progress through failures, crashes and server outages ({{Temporal docs|https://docs.temporal.io/temporal}}). Two rules come with it: workflow code must be deterministic, making "the same Workflow API calls in the same sequence" when replayed ({{workflow definition|https://docs.temporal.io/workflow-definition}}), so no clocks, random numbers or network calls in it; and side effects go in activities, which are retried, so "Temporal recommends that Activities be idempotent" ({{activity definition|https://docs.temporal.io/activity-definition}}). Lighter alternatives keep the state in your own Postgres (DBOS) or in a log (Restate). How this compares with an agent framework's checkpointing is owned by {{Topic: agentic-frameworks|n:3c65c17b0d0d81ab8432c54d65b7f8c7}} (its Orchestration lab, "Durable execution").

When to reach for one: when you find yourself writing a state machine over queue messages with timeouts and compensations. When not to: a single-step job is a plain queue's work, and an engine is a new system and a new programming model (the determinism rule bites people).

Postgres queues in other languages, Temporal's retry defaults, other engines (reference)

In other languages the Postgres-backed equivalents are River (Go), Oban (Elixir), Solid Queue (Rails 8's default, which "leverages the FOR UPDATE SKIP LOCKED clause", {{Solid Queue|https://github.com/rails/solid_queue/blob/main/README.md}}), graphile-worker (Node: "each job will execute at least once. Most jobs will execute exactly once", {{graphile-worker|https://github.com/graphile/worker/blob/main/website/docs/index.md}}) and pgmq (an SQS-like extension). Temporal's default activity retry: 1 s initial interval, backoff 2.0, up to 100 s, unlimited attempts ({{retry policies|https://docs.temporal.io/encyclopedia/retry-policies}}); the engine rebuilds state by replaying the recorded history, which is why the determinism rule exists. DBOS: "Add a few annotations to your application to durably execute it" ({{DBOS|https://docs.dbos.dev/}}); Cloudflare Workflows "persist state for minutes, hours, or even weeks" ({{Cloudflare|https://developers.cloudflare.com/workflows/}}).

Scheduling and cron

Classic cron runs a command on one machine at set times, so it inherits that machine's fate: down at 02:00, the job does not run; two machines with the crontab, it runs twice. Distributed schedulers state the same trade. Kubernetes: "A CronJob creates a Job object approximately once per execution time of its schedule. The scheduling is approximate because there are certain circumstances where two Jobs might be created, or no Job might be created ... Therefore, the Jobs that you define should be idempotent" ({{Kubernetes CronJob|https://kubernetes.io/docs/concepts/workloads/controllers/cron-job/}}). Celery: "You have to ensure only a single scheduler is running for a schedule at a time, otherwise you'd end up with duplicate tasks" ({{Celery periodic tasks|https://github.com/celery/celery/blob/v5.6.3/docs/userguide/periodic-tasks.rst}}).

  • Key each run by its scheduled time, not by "now": the 02:00 roll-up for 2026-10-03 writes a partition named for that date and overwrites it, so a rerun, a duplicate or a backfill gives the same result. Airflow: "the tasks should produce the same outcome on every re-run" ({{Airflow best practices|https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html}}): deterministic output locations, overwrite, never append.
  • Decide what overlap and a missed run mean. Kubernetes' concurrencyPolicy is Allow by default (runs may overlap); Forbid skips a run while the previous one is going; Replace kills the old one. startingDeadlineSeconds skips a run that could not start in time; without it, Kubernetes will not start a job that has missed more than 100 schedules.
  • Let the scheduler only enqueue. It puts a message on the queue; ordinary workers, with their retries, DLQ and idempotency, do the work.
