Job queues for Python, and durable workflows

Most Python services do not talk to SQS or Kafka by hand; they use a task queue library: you decorate a function, call .delay() or enqueue() in the request handler, and worker processes run it. The libraries differ mainly in the broker they use and in their delivery defaults, which is what this page has been about.

Measured: why SKIP LOCKED is the whole trick

A Postgres queue works only if workers do not wait for each other. Postgres: "With SKIP LOCKED, any selected rows that cannot be immediately locked are skipped. Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table" ({{SELECT docs|https://www.postgresql.org/docs/current/sql-select.html}}). With SKIP LOCKED each takes a different row: 960 jobs a second with 8 workers, against an ideal of 1,600 (8 / 5 ms; the gap is Postgres round trips and the timer granularity of time.sleep). Durable workflows are for jobs with many steps that must survive crashes for minutes to weeks: an agent run, a saga, onboarding with waits. Instead of chaining queue messages by hand, you write the steps as ordinary code and the engine records each completed step, so after a crash it resumes from the last one. Temporal calls this durable execution: a workflow keeps its state and progress through failures, crashes and server outages ({{Temporal docs|https://docs.temporal.io/temporal}}). Two rules come with it. Workflow code must be deterministic: run again on the same input it must make "the same Workflow API calls in the same sequence" ({{workflow definition|https://docs.temporal.io/workflow-definition}}), because the engine rebuilds state by replaying the recorded history; so no clocks, random numbers or network calls in the workflow itself. Side effects go in activities, which are retried by default (1 s initial interval, backoff 2.0, up to 100 s, unlimited attempts, {{retry policies|https://docs.temporal.io/encyclopedia/retry-policies}}), so "Temporal recommends that Activities be idempotent" ({{activity definition|https://docs.temporal.io/activity-definition}}). Lighter alternatives keep the state in your own Postgres (DBOS: "Add a few annotations to your application to durably execute it", {{DBOS|https://docs.dbos.dev/}}) or in a log (Restate); Cloudflare Workflows "persist state for minutes, hours, or even weeks" ({{Cloudflare|https://developers.cloudflare.com/workflows/}}).

When not to: a single-step job is a plain queue's work; a workflow engine is a new system and a new programming model (the determinism rule bites people). Reach for one when you find yourself writing a state machine over queue messages with timeouts and compensations.

Scheduling and cron

Scheduled work (nightly evaluation, hourly usage roll-ups, cleanup of old outbox rows) looks simple and fails in its own ways. Classic cron runs a command on one machine at set times, so it inherits that machine's fate: if the machine is down at 02:00, the job does not run; if two machines both have the crontab, it runs twice. Distributed schedulers make the same trade explicit. Kubernetes: "A CronJob creates a Job object approximately once per execution time of its schedule. The scheduling is approximate because there are certain circumstances where two Jobs might be created, or no Job might be created ... Therefore, the Jobs that you define should be idempotent" ({{Kubernetes CronJob|https://kubernetes.io/docs/concepts/workloads/controllers/cron-job/}}). Celery: "You have to ensure only a single scheduler is running for a schedule at a time, otherwise you'd end up with duplicate tasks" ({{Celery periodic tasks|https://github.com/celery/celery/blob/v5.6.3/docs/userguide/periodic-tasks.rst}}).

  • Key each run by its scheduled time, not by "now": the 02:00 roll-up for 2026-10-03 writes to a partition named for that date and overwrites it. A rerun, a duplicate or a backfill then produces the same result. Airflow's best practices say the same of pipeline tasks: "Airflow can retry a task if it fails. Thus, the tasks should produce the same outcome on every re-run" ({{Airflow best practices|https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html}}): write outputs to deterministic locations and overwrite, never append.
  • Decide what overlap means. Kubernetes' concurrencyPolicy is Allow by default (runs may overlap); Forbid skips a run while the previous one is still going; Replace kills the old one.
  • Decide what a missed run means. startingDeadlineSeconds skips a run that could not start in time; without it, Kubernetes will not start a job that has missed more than 100 schedules.
  • Let the scheduler only enqueue. The scheduler puts a message on the queue; ordinary workers, with their retries, DLQ and idempotency, do the work.
