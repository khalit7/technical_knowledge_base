Async work around LLMs

LLM products stretch every idea on this page, because one unit of work can take a second (a chat reply), minutes (a deep-research answer, an agent run) or hours (a batch over a million documents), and costs real money each time it runs.

Stream to the user while the work continues

The chat reply stays on the request path but is streamed: the server sends tokens as they are generated over server-sent events (SSE), one long HTTP response with one event per chunk. Anthropic: set "stream": true "to incrementally stream the response using server-sent events (SSE)" ({{Anthropic streaming|https://platform.claude.com/docs/en/build-with-claude/streaming}}). The design question is what happens when the connection drops halfway. If generation is tied to the HTTP connection, a closed tab or a phone switching networks kills a paid-for answer. The better shape separates the two: the generation runs as a background job writing chunks somewhere durable, and the HTTP stream is just a reader that can reconnect. Vercel's AI SDK: "In a resumable stream setup, client-side aborts are treated as disconnects. Closing a tab, refreshing the page, or calling stop() only closes the current HTTP connection and should not cancel the underlying generation" ({{AI SDK resumable streams|https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-resume-streams}}). OpenAI's background mode does it on the provider side: create a response with background and stream both true and "keep track of a 'cursor' corresponding to the sequence_number you receive in each streaming event", then resume with starting_after ({{OpenAI background mode|https://platform.openai.com/docs/guides/background}}). Note its retention: "Response data is temporarily stored to disk for roughly 10 minutes to enable asynchronous execution and polling". Server-sent events in API design: {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}.

Long-running agent jobs

An agent run is a saga of model calls and tool calls, some with side effects (open a pull request, send an e-mail, charge a card). Treat it as a durable workflow: return 202 with a run id, execute the steps in a worker or workflow engine that records each completed step, and push progress to the client (SSE or WebSocket) or let it poll. Three rules from the sections above, applied:

  • Every tool call with a side effect carries an idempotency key derived from the run id and step number, because a crashed run will be resumed and a timed-out call retried (idempotent consumers).
  • Record model outputs as completed steps, so a resumed run does not pay for the same tokens again; that is the point of durable execution for agents. Temporal's announcement of its OpenAI Agents SDK integration (public preview, July 2025): "Temporal keeps track of application progress and stores all Activity results" ({{Temporal blog|https://temporal.io/blog/announcing-openai-agents-sdk-integration}}, vendor post). An OpenAI infrastructure VP is quoted in Temporal's September 2026 funding post as saying OpenAI built "a durable orchestration framework powered by Temporal" ({{Temporal, 2026-09-14|https://temporal.io/blog/temporal-raises-usd550m-series-e-at-usd12-55b-valuation-ai}}; a vendor post, not an OpenAI source).
  • Leases must outlast the slowest step or be renewed: a 20-minute agent step on a queue with a 5-minute visibility timeout runs four times in parallel (visibility timeouts).

Batch APIs: a queue the provider runs for you

For work that can wait hours (evaluations, re-embedding a corpus, classifying a backlog), providers sell a queue with a discount: OpenAI's Batch API offers "50% lower costs, a separate pool of significantly higher rate limits, and a clear 24-hour turnaround time" ({{OpenAI Batch|https://platform.openai.com/docs/guides/batch}}); Anthropic's Message Batches have "most batches finishing in less than 1 hour while reducing costs by 50%", up to 100,000 requests or 256 MB per batch ({{Anthropic batch processing|https://platform.claude.com/docs/en/build-with-claude/batch-processing}}). Your side is still a job: submit, store the batch id, poll or get notified, fetch results, and handle the requests that expired or failed (resubmit them, idempotently, keyed by your own request ids). When to batch and what it saves is on {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}}.

A queue in front of the GPUs

Inference servers queue requests internally and batch them on the GPU (the parent root's Step 5). Two lessons from this page carry over: a queue in front of a GPU pool must be bounded and shed load early, because an unbounded one turns a traffic spike into minutes of latency for everyone (the degradation ladder and priorities are on {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}}); and autoscaling should follow queue depth or the age of the oldest request, not CPU. Common mistakes

Assuming the queue gives exactly-once
Every common broker delivers at least once in practice. Design every consumer to receive a message twice; test it by delivering twice.
Generating the dedup id in the consumer
A random id made on receipt is new on every redelivery, so nothing is ever deduplicated. The id must come from the producer, or be derived from the content (order id plus event type).
Running Celery with default acks for important work
The default acknowledges before running, so a killed worker loses the task. Use acks_late plus reject_on_worker_lost, and idempotent tasks.
A visibility timeout shorter than the slowest job
Slow jobs run on two workers at once (measured above). Set it above p99, or heartbeat.
Publishing an event right after a commit, "it is usually fine"
It is fine until a deploy or crash lands between the two lines; then events are lost silently (measured: one per crash). Use an outbox, or enqueue in the database.
Watching queue length instead of message age
A queue of 10,000 may be healthy (fast consumers) and a queue of 50 may be stuck (one poison message retried forever). Age tells you which.
No DLQ, or a DLQ nobody watches
Without one, a poison message burns a worker forever (try it in the Queue lab); with an unwatched one, failed jobs vanish quietly.
More consumers than partitions
In a Kafka consumer group the extra consumers sit idle. Plan partition counts for peak parallelism, or use share groups (Kafka 4.2+).
Changing the partition count of a keyed topic
Keys move to new partitions, so per-key ordering breaks across the change (try it in the Kafka widget above).
Doing slow work inside the database transaction that holds the job lock
Fine for milliseconds (the throughput experiment did it), harmful for minutes: long transactions hold locks and stop Postgres from cleaning up old row versions. For long jobs use a lease (a visible_at column) and commit the claim at once.
Unbounded queues in front of expensive resources
Bound them, reject early with 429, and scale on queue age. An unbounded queue in front of a GPU pool turns a spike into minutes of latency for everyone.
