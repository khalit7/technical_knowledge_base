Worked example: a nightly batch LLM job, end to end

Every night the chat product classifies the previous day's conversations (topic, safety flags) for its dashboards. It can wait hours, so it goes through a provider's batch API, which is a queue the provider runs for you at a discount: OpenAI's Batch API offers "50% lower costs, a separate pool of significantly higher rate limits, and a clear 24-hour turnaround time" ({{OpenAI Batch|https://platform.openai.com/docs/guides/batch}}); Anthropic's Message Batches have "most batches finishing in less than 1 hour while reducing costs by 50%", up to 100,000 requests or 256 MB per batch ({{Anthropic batch processing|https://platform.claude.com/docs/en/build-with-claude/batch-processing}}). Your side is still a job, and every mechanism on this page shows up in it once. One night's job, step by step: each step has one way to fail and one mechanism that makes a rerun harmless.

  1. Cron enqueues one job, keyed by the scheduled date. INSERT INTO jobs (key, ...) VALUES ('eval:2026-10-23', ...) ON CONFLICT (key) DO NOTHING. Fails if two schedulers fire, or a rerun or backfill fires again. Made harmless by the key: the second insert does nothing (cron).
  2. A worker claims it with a lease, and heartbeats. It builds 20,000 requests, each with custom_id = the conversation id. Fails if the worker dies. Made harmless by the lease: the job reappears for another worker within one timeout, and heartbeats stop a slow build from being taken over (visibility timeouts).
  3. Submit the batch, then record its id. Submitting is a call to someone else's system and recording the id is a write to yours: a dual write. Fails if the worker dies between them; a rerun would submit and pay for a second batch. Made harmless by writing status = submitting first and, on a restart in that state, listing the account's recent batches before submitting again (dual writes).
  4. Poll until the batch ends. The poller is a scheduled task that reads batch_id from the job row and asks for the status. Fails if the poller dies or runs twice. Made harmless by keeping the state in the job row, not in the poller: asking twice is a read.
  5. Fetch results and upsert them by custom_id. INSERT INTO results ... ON CONFLICT (custom_id) DO UPDATE. Fails if the worker dies halfway through the file. Made harmless by the key: fetching and writing again leaves the same rows (idempotent consumers).
  6. Resubmit only the failures; dead-letter the poison. Errored or expired requests go into a smaller batch with the same custom_ids. Fails if a request fails every time (too long, malformed). Made harmless by a try limit: after 3, it goes to a dead-letter table with an alert, instead of looping forever (dead letters).
  7. Mark done and announce it, in one transaction. UPDATE jobs SET status = 'done' and INSERT INTO outbox commit together; the relay publishes "eval-ready" to the log at least once, and the dashboards deduplicate on the event id (outbox). Cost: both providers charge 50% of the synchronous price for this route.

The pattern generalises: the durable state is a row in your database (the job, its batch id, the per-request results), every process around it (scheduler, worker, poller, relay) can die and be rerun, and each rerun is made harmless by a key: the scheduled date, the batch id, the custom_id, the event id. When to batch and what it saves at the system level is on {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}}; batch status, polling and the 29-day results window as an API are on {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}}.

The other async shapes around LLMs

  • A streamed reply stays on the request path, but generation should not be tied to the HTTP connection: run it as a background job writing chunks somewhere durable, and make the stream a reader that can reconnect. Server-sent events, cutting and resuming streams are owned by {{Streaming and real-time|n:3c65c17b0d0d812daa9fdb38719fc82b}}.
  • A long agent run is a saga of model and tool calls: return 202 with a run id, run the steps in a worker or workflow engine that records each completed step, give every side-effecting tool call an idempotency key from the run id and step number, record model outputs as completed steps so a resumed run does not pay for the same tokens again, and make leases outlast the slowest step: a 20-minute agent step on a queue with a 5-minute visibility timeout runs four times in parallel.
  • A queue in front of the GPUs must be bounded and shed load early, because an unbounded one turns a traffic spike into minutes of latency for everyone, and autoscaling should follow queue depth or the age of the oldest request, not CPU. The degradation ladder and priorities are on {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}}; serving engines' internal queues on {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} (the parent root's Step 5).
