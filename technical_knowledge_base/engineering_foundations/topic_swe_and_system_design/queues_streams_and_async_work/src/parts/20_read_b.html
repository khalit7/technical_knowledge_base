Two shapes: queues and logs

Brokers come in two shapes, and most confusion about "queues versus Kafka" is confusion between them.

A queue: a to-do list

Each message is meant for one worker. A worker takes a message, does it, acknowledges, and the broker deletes it. Several workers on one queue share the work (they are called competing consumers). Progress is tracked per message. Examples: Amazon SQS, RabbitMQ queues, a jobs table in Postgres, Redis lists behind Celery or RQ.

A log (a stream): an append-only record

Messages are appended in order and kept for a retention period whether or not anyone has read them. Each reader remembers its own position, a number called the offset. Many independent readers can read the same messages, and a reader can rewind and replay. Examples: Apache Kafka, Amazon Kinesis Data Streams, Redpanda, Apache Pulsar, Redis Streams, RabbitMQ Streams.

Kafka's own introduction states the difference: "events are not deleted after consumption. Instead, you define for how long Kafka should retain your events through a per-topic configuration setting" ({{Kafka 4.3 introduction|https://kafka.apache.org/43/getting-started/introduction/}}); the default retention is 7 days (retention.ms, {{topic configs|https://kafka.apache.org/43/configuration/topic-configs/}}). RabbitMQ added a log type for the same reason: "Streams model an append-only log of messages that can be repeatedly read until they expire" ({{RabbitMQ Streams|https://www.rabbitmq.com/docs/streams}}).

Which to use follows from who reads the messages:

  • A queue when each message is a job for one kind of worker: "embed document 981", "send receipt for order 42". You want per-message acknowledgement, per-message retries and dead-lettering, and you never want the job again once done.
  • A log when the message is a fact several systems care about: "order 42 was placed" read by the e-mail service, the warehouse and analytics, each at its own pace; or when you may need to replay history (rebuild a search index, backfill a new service). You pay with partitions to plan, offsets to manage and usually a cluster to run.

Kafka from zero: topics, partitions, offsets, consumer groups

Kafka is the log most teams meet first, and its vocabulary is used by Redpanda, Kinesis (with different names) and most stream processors.

  • A topic is a named log, such as orders or chat_messages.
  • A topic is split into partitions: several independent logs, each stored and replicated on brokers. Partitions are how Kafka scales: different partitions live on different machines and are read in parallel. (How each partition is replicated, with a leader, followers and a Raft-based controller since Kafka 4.0, is on {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}}.)
  • Each message in a partition gets an increasing number, its offset. A consumer's progress is "the next offset I will read" for each partition.
  • A message can carry a key. Kafka hashes the key to choose the partition, so "if the key chosen was a user id then all data for a given user would be sent to the same partition" ({{Kafka design|https://kafka.apache.org/43/design/design/}}).

Ordering is per partition only. "Events with the same event key (e.g., a customer or vehicle ID) are written to the same partition, and Kafka guarantees that any consumer of a given topic-partition will always read that partition's events in exactly the same order as they were written" ({{Kafka introduction|https://kafka.apache.org/43/getting-started/introduction/}}). Two messages in different partitions have no order between them. So choose the key by what must stay in order: a user's messages, an order's state changes.

Consumer groups share the work. Consumers that share a group id form a consumer group; each partition "is consumed by exactly one consumer within each subscribing consumer group at any given time" ({{Kafka design|https://kafka.apache.org/43/design/design/}}). Two consequences: a group can never use more consumers than there are partitions (the extras sit idle), and a different group (analytics, say) gets every message again. When consumers join or leave, the group rebalances, moving partitions between members; Kafka 4.0 made a new protocol (KIP-848) generally available that "says goodbye to 'stop-the-world' rebalances" ({{Kafka 4.0 release|https://kafka.apache.org/blog/2025/03/18/apache-kafka-4.0.0-release-announcement/}}), but clients still default to the classic one (group.protocol "The default value is classic", {{consumer configs, 4.3|https://kafka.apache.org/43/configuration/consumer-configs/}}).

Committing offsets. A consumer saves its position by committing offsets, which Kafka stores in an internal topic, __consumer_offsets ({{Kafka implementation|https://kafka.apache.org/43/implementation/distribution/}}). By default the client does it for you: enable.auto.commit is true and commits "periodically ... in the background", every 5 seconds ({{consumer configs|https://kafka.apache.org/43/configuration/consumer-configs/}}). When to commit relative to the work decides your delivery semantics, which is the next section. Two timers decide when a consumer is declared dead and its partitions handed to someone else: session.timeout.ms (45 s without heartbeats) and max.poll.interval.ms (5 minutes between calls to poll(); slower than that and "the consumer is considered failed and the group will rebalance"). That second timer is Kafka's version of a visibility timeout: a job slower than it gets its partition taken away mid-work.

Lag is how far a group is behind: the partition's latest offset minus the group's committed offset. Kafka ships "a tool that will show the position of all consumers in a consumer group as well as how far behind the end of the log they are" (kafka-consumer-groups.sh --describe, {{Kafka operations|https://kafka.apache.org/43/operations/basic-kafka-operations/}}). Lag in messages is the log's queue depth; divide by the consume rate to get it in seconds, the number users feel.

Kafka as a queue, now. Because a partition goes to one consumer, Kafka was a poor job queue: one slow message holds up its whole partition, and parallelism is capped by the partition count. Kafka 4.2 (February 2026) made share groups ("Queues for Kafka", KIP-932) production-ready ({{Kafka 4.2 release|https://kafka.apache.org/blog/2026/02/17/apache-kafka-4.2.0-release-announcement/}}): in a share group "partitions may be assigned to multiple consumers", "The number of consumers in a share group can exceed the number of partitions", "Records are acknowledged individually", and "Delivery attempts to consumers in a share group are counted" ({{Kafka design, The Share Consumer|https://kafka.apache.org/43/design/design/}}). A delivered record is locked for 30 seconds by default and can be acknowledged, released, rejected or renewed: the SQS model, inside Kafka. It was early access in 4.0 and a preview in 4.1.
