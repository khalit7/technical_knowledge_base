Two shapes: queues and logs

Most confusion about "queues versus Kafka" is confusion between two shapes of broker. Decide by who reads a message: one worker (a job: "embed document 981") or several systems (a fact: "order 42 was placed", read by e-mail, warehouse and analytics, each at its own pace).

A queue forgets what was done; a log remembers, and each reader keeps its own place

Queue: workers that share it are competing consumers; each message goes to one of them and is deleted on ack, so progress is tracked per message (SQS, RabbitMQ queues, a Postgres jobs table, Redis lists behind Celery or RQ). Log: a log (a stream) keeps every message for a retention period whether read or not; each reader remembers its position, the offset, so many readers see every message and a new one can replay from the start (Kafka, Kinesis Data Streams, Redpanda, Pulsar, Redis Streams, RabbitMQ Streams). A message queue is the first shape.

Kafka states it: "events are not deleted after consumption. Instead, you define for how long Kafka should retain your events through a per-topic configuration setting" ({{Kafka 4.3 introduction|https://kafka.apache.org/43/getting-started/introduction/}}); the default retention is 7 days (retention.ms, {{topic configs|https://kafka.apache.org/43/configuration/topic-configs/}}). RabbitMQ added the log shape for the same reason: "Streams model an append-only log of messages that can be repeatedly read until they expire" ({{RabbitMQ Streams|https://www.rabbitmq.com/docs/streams}}). Choose a queue for jobs (per-message acks, retries and dead-lettering, never wanted again once done); choose a log for facts several systems care about, or when you may need to replay history (rebuild a search index, backfill a new service), and pay with partitions to plan, offsets to manage and usually a cluster to run.

Kafka: partitions, keys, offsets and consumer groups

A topic is a named log (orders, chat_messages), split into partitions: independent logs on different brokers, read in parallel, each message numbered by its offset. A message's key is hashed to pick its partition, so "if the key chosen was a user id then all data for a given user would be sent to the same partition" ({{Kafka design|https://kafka.apache.org/43/design/design/}}). Two rules follow, and the widget shows both:

  • Ordering is per partition only. Kafka "guarantees that any consumer of a given topic-partition will always read that partition's events in exactly the same order as they were written" ({{Kafka introduction|https://kafka.apache.org/43/getting-started/introduction/}}); across partitions there is no order. Key by what must stay in order: a user's messages, an order's state changes.
  • A consumer group gets one consumer per partition. Each partition "is consumed by exactly one consumer within each subscribing consumer group at any given time" (Kafka design). So a group never uses more consumers than partitions, and a different group (analytics) receives every message again.

More consumers than partitions sit idle; a new partition count moves keys

Adding partitions to a keyed topic re-hashes keys onto new partitions, so per-key ordering breaks across the change for messages already written.

Offsets, commits and the two timers. A consumer saves its position by committing offsets. By default the client does it in the background: enable.auto.commit is true, every 5 seconds ({{consumer configs|https://kafka.apache.org/43/configuration/consumer-configs/}}), which is why "when do I commit relative to the work?" (the next section) is decided for you unless you take it over. A consumer is declared dead, and its partitions handed on in a rebalance, after session.timeout.ms (45 s without heartbeats) or max.poll.interval.ms (5 minutes between calls to poll(), after which "the consumer is considered failed and the group will rebalance"). That second timer is Kafka's visibility timeout: a job slower than it loses its partition mid-work.

Lag is the partition's latest offset minus the group's committed offset: the log's queue depth. Divide by the consume rate to get it in seconds, the number users feel (kafka-consumer-groups.sh --describe shows "how far behind the end of the log they are", {{Kafka operations|https://kafka.apache.org/43/operations/basic-kafka-operations/}}).

Kafka as a queue, now. One partition per consumer made Kafka a poor job queue (one slow message holds up its partition; parallelism stops at the partition count). Kafka 4.2 (February 2026) made share groups (KIP-932) production-ready ({{Kafka 4.2 release|https://kafka.apache.org/blog/2026/02/17/apache-kafka-4.2.0-release-announcement/}}): more consumers than partitions, records "acknowledged individually", delivery attempts counted, each record locked for 30 seconds by default: the SQS model, inside Kafka.

More Kafka detail: where offsets live, rebalance protocols, share-group history (depth)

Committed offsets are stored in an internal topic, __consumer_offsets ({{Kafka implementation|https://kafka.apache.org/43/implementation/distribution/}}). Kafka 4.0 made a new consumer rebalance protocol (KIP-848) generally available that "says goodbye to 'stop-the-world' rebalances" ({{Kafka 4.0 release|https://kafka.apache.org/blog/2025/03/18/apache-kafka-4.0.0-release-announcement/}}), but clients still default to the classic one (group.protocol "The default value is classic", {{consumer configs, 4.3|https://kafka.apache.org/43/configuration/consumer-configs/}}). Share groups ("Queues for Kafka") in the design document's words: "partitions may be assigned to multiple consumers", "The number of consumers in a share group can exceed the number of partitions", "Records are acknowledged individually", and "Delivery attempts to consumers in a share group are counted" ({{Kafka design, The Share Consumer|https://kafka.apache.org/43/design/design/}}); a locked record can be acknowledged, released, rejected or renewed. They were early access in 4.0 and a preview in 4.1. How each partition is replicated, with a leader, followers and a Raft-based controller since Kafka 4.0, is on {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}}. Kafka's design document is unusually readable: {{Kafka 4.3 design|https://kafka.apache.org/43/design/design/}} (about 1 h).
