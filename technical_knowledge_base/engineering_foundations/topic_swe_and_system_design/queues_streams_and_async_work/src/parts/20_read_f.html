Sagas versus two-phase commit

The outbox makes one service's write and event atomic. A business action often spans several services, each with its own database: the chat product's "upgrade to Pro" must charge the card (payments service), raise the user's token quota (quota service) and send a receipt (e-mail). If the quota update fails after the charge, the user has paid for nothing. Two families of answer:

Two-phase commit (2PC) makes several databases commit together. A coordinator asks every participant to prepare (do the work, hold the locks, promise to commit if told); if all say yes it tells all to commit, otherwise all abort. Its weakness was stated by Jim Gray and Leslie Lamport: "The classic Two-Phase Commit protocol blocks if the coordinator fails" ({{Gray and Lamport, Consensus on Transaction Commit|https://arxiv.org/abs/cs/0408036}}): prepared participants hold their locks and cannot decide alone. Postgres supports the prepare step but warns "PREPARE TRANSACTION is not intended for use in applications ... Unless you're writing a transaction manager, you probably shouldn't be using PREPARE TRANSACTION" ({{PostgreSQL docs|https://www.postgresql.org/docs/current/sql-prepare-transaction.html}}). And most systems a service talks to (Kafka, SaaS APIs, a payment provider) cannot take part at all. 2PC lives on inside distributed databases (Spanner, CockroachDB), run over consensus so the coordinator cannot simply vanish; the theory is on {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}}.

A saga gives up atomicity and adds undo. The idea is from Garcia-Molina and Salem (1987): a long transaction "is a saga if it can be written as a sequence of transactions that can be interleaved with other transactions", and the system "guarantees that either all the transactions in a saga are successfully completed or compensating transactions are run to amend a partial execution" ({{Sagas, SIGMOD 1987|https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf}}). In services: "A saga is a sequence of local transactions. Each local transaction updates the database and publishes a message or event to trigger the next local transaction in the saga. If a local transaction fails because it violates a business rule then the saga executes a series of compensating transactions" ({{microservices.io, Saga|https://microservices.io/patterns/data/saga.html}}).

The same upgrade, three ways
  • Choreography or orchestration. In choreography "each local transaction publishes domain events that trigger local transactions in other services"; in orchestration "an orchestrator (object) tells the participants what local transactions to execute" (microservices.io). Choreography has no central piece but the flow is spread across services and hard to see; orchestration puts the flow in one place, which is what durable workflow engines (below) are built for.
  • Compensations are business actions, not rollbacks. "Refund the charge" is not "the charge never happened": the customer may have seen it, a receipt may be out. Some steps cannot be compensated (an e-mail sent); put them last.
  • No isolation. Between steps, others see the half-done state. The 1987 paper: "other transactions might see the effects of a partial saga execution"; microservices.io lists "Lack of isolation" as the main drawback. Defences: a status field (PENDING) that other code respects, re-reading values before acting, ordering steps so the riskiest comes first.
  • Every step and every compensation runs at least once, because it is driven by messages: each must be idempotent.
When not to use either: if all the data can live in one database, use one transaction. Splitting data across services is what creates the need for sagas; do it for a reason.

Event-driven architecture, event sourcing and CQRS, in brief

In an event-driven architecture, services announce facts ("order 42 placed") on a log instead of calling each other ("e-mail service, send a receipt"). The old page listed the trade, and it holds: the benefits are temporal decoupling (the e-mail service can be down and catch up later), fan-out (any number of consumers per event, added without touching the producer), a natural audit trail, and replay (rebuild a projection by re-reading the log); the costs are eventual consistency between views, harder end-to-end tracing (use trace ids propagated in message headers: {{Observability|n:3ef5c17b0d0d811e8490c54dd42c2b9b}}), and schema discipline. Two distinctions that prevent most design mistakes:

  • Events versus commands. An event is a fact in the past tense, owned by its producer, with any number of readers. A command ("send receipt") is a request to one recipient that may refuse. Putting commands on a shared log hides who is responsible.
  • Thin versus fat events. A thin event carries ids ("order 42 changed"), and the consumer fetches current data; a fat event carries the data. Thin events are always current and leak less; fat events let consumers work while the producer is down. Schema changes must be backward compatible (add optional fields, never rename or remove), usually enforced by a schema registry (old page, kept as practice).

Event sourcing goes further: the events are the source of truth. Martin Fowler: "every change to the state of an application is captured in an event object, and that these event objects are themselves stored in the sequence they were applied for the same lifetime as the application state itself" ({{Fowler, Event Sourcing, 2005|https://martinfowler.com/eaaDev/EventSourcing.html}}); current state is computed by replaying them. CQRS (command query responsibility segregation) uses "a different model to update information than the model you use to read information" ({{Fowler, CQRS, 2011|https://martinfowler.com/bliki/CQRS.html}}); event sourcing usually needs it, and a Kafka-to-ClickHouse analytics pipeline is a mild form of it.

When not to
Fowler on CQRS: "beware that for most systems CQRS adds risky complexity." Microsoft's architecture guide on event sourcing (2026): "It's costly to migrate to or from an event sourcing solution ... For most systems and most parts of a system, traditional data management is sufficient", and it is not suitable when systems "have straightforward CRUD operations that don't require auditability, replay, or historical reconstruction of state" ({{Azure Architecture Center, Event Sourcing|https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing}}). The same page corrects a common belief: "Message brokers such as Apache Kafka typically lack per-entity stream queries and optimistic concurrency. They work well as a distribution layer ... but they aren't a substitute for an event store." The old page's verdict, "rarely worth it outside ledgers", is an opinion, but it matches both sources. For an ML platform the useful part is the log, not event sourcing: usage events, feedback events and pipeline triggers fanned out from one stream (on AWS: EventBridge or SNS into SQS into Lambda, each with a DLQ and idempotent handlers).
