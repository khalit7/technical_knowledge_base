The dual-write problem and the transactional outbox

Placing an order means saving it in the database and publishing "order placed" for e-mail, warehouse and analytics: a dual write, two writes to two systems that share no transaction. Gunnar Morling, then Debezium's lead: "we cannot have one shared transaction that would span the service's database as well as Apache Kafka, as the latter doesn't support to be enlisted in distributed (XA) transactions" ({{Debezium blog, 2019-02-19|https://debezium.io/blog/2019/02/19/reliable-microservices-data-exchange-with-the-outbox-pattern/}}). Whichever write goes first, a crash between them leaves the systems disagreeing. Fig. 6 steps the same order through three designs; choose one with the buttons. Swapping the two writes swaps the failure; the outbox turns them into one. The crash points are the ones the measured lab injects; the counts are from that lab (500 orders, 5% crash chance, three runs).

  1. Order 42 arrives. A customer places order 42. The order API must do two things: save the order in Postgres, and tell the rest of the company (e-mail, warehouse, analytics) by publishing an "order placed" event to the broker. Two systems, and no transaction spans both.
  2. Write 1: save the order, COMMIT. INSERT INTO orders ...; COMMIT; The order is now durable: Postgres has promised it survives a crash.
  3. The process dies before write 2. A deploy, an out-of-memory kill, a lost network packet to the broker: anything that stops the process between the two writes. In the measured lab this is os._exit() at exactly this line.
  4. Restart: nothing remembers the event. The new process handles the next order. The event for order 42 lived only in the dead process's memory. No error was logged anywhere: the database is fine and the broker is fine.
  5. Result: a lost event. Order 42 exists, but no receipt is ever sent, the warehouse never ships it, analytics never counts it. Measured on a real Postgres: 500 orders with a 5% crash chance lost 19, 28 and 27 events in three runs, one per crash, silently.
  1. Order 42 arrives. Same order, the writes the other way round: publish first, so the event cannot be lost, then save.
  2. Write 1: publish "order 42 placed". The broker has the event durably. Consumers may read it at once.
  3. The process dies before write 2. The order's transaction never commits; Postgres rolls it back.
  4. A consumer acts on an order that does not exist. The e-mail service sends a receipt for order 42; the warehouse may ship it. But order 42 is in no database: a phantom event.
  5. Result: the opposite failure. Swapping the order of two writes only swaps which failure you get. Measured: 19, 28 and 27 phantom events per 500 orders. Any fix must make the two writes one.
  1. Order 42 arrives. The outbox pattern: the API never talks to the broker. It writes the event as a row in an outbox table in the same database as the order.
  2. One transaction: the order and its event. BEGIN; INSERT INTO orders ...; INSERT INTO outbox (event_id, payload) ...; COMMIT; Both rows commit, or neither does. There is only one write.
  3. The API crashes now: nothing is lost. Unlike the naive version, the event is already durable, waiting in the outbox with sent_at empty.
  4. The relay finds unsent rows. A separate process, the relay, polls: SELECT ... FROM outbox WHERE sent_at IS NULL ORDER BY seq LIMIT 10 FOR UPDATE SKIP LOCKED. (Or a change-data-capture tool such as Debezium reads the same rows from the database's log.)
  5. It publishes e42 to the broker. The broker now has the event.
  6. The relay crashes before marking the row sent. The same two-writes gap, moved to a place where it is harmless: the row still says unsent, so the event will be sent again.
  7. Restart: e42 is published again, then marked sent. The broker holds e42 twice. The outbox gives at-least-once publishing: never lost, sometimes duplicated. Measured: 0 events lost in three runs; 24 to 32 duplicates per 500 orders with one event per relay transaction, 147 to 185 with batches of 10.
  8. The consumer handles e42 once. In one transaction it records e42 in its processed_events table (a primary key on the event id) and does its work: one receipt.
  9. The duplicate arrives and is skipped. Inserting e42 again violates the primary key, so the consumer knows it has seen it and acknowledges without acting. This is the idempotent consumer (also called the inbox pattern).
  10. Result: nothing lost, nothing doubled. One order, one event delivered at least once, one e-mail. The outbox removes loss; the consumer's deduplication removes the duplicates. Together they give the effect people mean by "exactly once".

The transactional outbox (Chris Richardson's name): "the service that sends the message to first store the message in the database as part of the transaction that updates the business entities. A separate process then sends the messages to the message broker" ({{microservices.io, Transactional outbox|https://microservices.io/patterns/data/transactional-outbox.html}}). The relay "might, for example, crash after publishing a message but before recording the fact that it has done so. When it restarts, it will then publish the message again. As a result, a message consumer must be idempotent". So the outbox converts "sometimes lost" into "sometimes duplicated", and the idempotent consumer converts that into "once".

Measured on the same laptop Postgres (the "broker" is a second database, so there is genuinely no shared transaction; 500 orders, 5% crash chance at the dangerous line, three runs):

With a batch of 10 events per relay transaction, a crash mid-batch rolls back every "sent" mark in the batch, so all of them are published again: about 4 to 5 duplicates per crash. With one event per transaction, duplicates equal crashes. Batching is faster; it multiplies duplicates.

Two ways to run the relay. A polling publisher loops over SELECT ... WHERE sent_at IS NULL ORDER BY seq LIMIT 100 FOR UPDATE SKIP LOCKED, publishes and marks sent ({{microservices.io|https://microservices.io/patterns/data/polling-publisher.html}}): simple, any database, a little polling load and latency; several relays can run thanks to SKIP LOCKED, but then strict ordering across them is lost. Change data capture (CDC) instead tails the database's log: in Postgres, logical decoding of the write-ahead log, "the process of extracting all persistent changes to a database's tables into a coherent, easy to understand format" ({{PostgreSQL docs|https://www.postgresql.org/docs/current/logicaldecoding-explanation.html}}). Debezium is the standard tool: no polling, ordered by commit, at the cost of a Kafka Connect deployment and a replication slot to monitor (an abandoned slot makes Postgres keep WAL forever). It is still at-least-once: "while it is recovering from the fault, it's possible that the connector might emit some duplicate change events" ({{Debezium Postgres connector|https://debezium.io/documentation/reference/stable/connectors/postgresql.html}}).

When you do not need an outbox: when the queue lives in the same database. River "encourages the use of the same database for application data and job queue. By enqueueing jobs transactionally along with other database changes, whole classes of distributed systems problems are avoided" ({{River docs|https://github.com/riverqueue/river/blob/master/docs/README.md}}). The outbox is such a queue, with a relay that forwards to Kafka for consumers that live elsewhere. And the receiving side's mirror is the inbox: the consumer stores each incoming message id with its effects, which is the idempotent consumer by another name.

Webhooks are the same problem facing outwards: calling a customer's endpoint after a database change is a dual write to their server, so the sender delivers from an outbox with retries and the receiver answers 2xx at once and queues the work (details below). Webhooks as an API are owned by {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}}, section 6.

What the outbox costs: a table that grows (delete or partition sent rows), a relay or CDC pipeline to run and monitor, events a little later than the commit, and duplicates every consumer must absorb. When not to use it: when the event is not critical (a lost analytics ping is fine), or when the consumers can read your database's job queue directly.

The measured counts, Debezium's outbox table, inbox libraries, and webhooks in full (reference)

Debezium's Outbox Event Router expects an outbox table with columns id, aggregatetype, aggregateid, type and payload, routing each row by default to a topic named outbox.event.<aggregatetype> with aggregateid as the message key ({{Debezium outbox event router|https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html}}). Pattern pages: "Publish messages by polling the database's outbox table"; "Tail the database transaction log and publish each message/event inserted into the outbox to the message broker" ({{microservices.io, transaction log tailing|https://microservices.io/patterns/data/transaction-log-tailing.html}}).

Inbox in libraries: MassTransit: "The inbox is used to keep track of received messages to guarantee exactly-once consumer behavior" ({{MassTransit|https://masstransit.io/documentation/patterns/transactional-outbox}}); NServiceBus "uses the message identity (MessageId) to deduplicate messages" ({{NServiceBus outbox|https://docs.particular.net/nservicebus/outbox/}}). Oban lists "Transactional Control: Enqueue a job along with other database changes, ensuring that everything is committed or rolled back atomically" ({{Oban|https://github.com/oban-bg/oban/blob/main/README.md}}).

In numbers: commit-then-publish lost 19, 28 and 27 events; publish-then-commit produced 19, 28 and 27 phantom events; the outbox lost none, with 147 to 185 duplicate events in batches of 10 and 24 to 32 one at a time, and after deduplication exactly 500 orders and 500 events in every run.

Webhooks in full: the sender writes "deliver event X to customer Y" in the transaction and delivers from a worker with retries (Stripe retries "for up to three days"); the receiver answers 2xx at once and queues the work. GitHub "does not automatically redeliver failed deliveries" ({{GitHub, failed deliveries|https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries}}), so a receiver that is down simply misses them. Stripe: "Your endpoint must quickly return a successful status code (2xx) before any complex logic that could cause a timeout", and it retries "for up to three days with an exponential back off in live mode" ({{Stripe webhooks|https://docs.stripe.com/webhooks}}). GitHub expects a 2XX "within 10 seconds" ({{GitHub best practices|https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks}}).

Sagas, not two-phase commit

The outbox makes one service's write and event atomic. "Upgrade to Pro" spans three: charge the card (payments), raise the token quota (quota), send a receipt (e-mail). If the quota update fails after the charge, the user has paid for nothing.

Two-phase commit (2PC) asks every participant to prepare (do the work, hold the locks, promise to commit), then tells all to commit or all to abort. "The classic Two-Phase Commit protocol blocks if the coordinator fails" ({{Gray and Lamport, Consensus on Transaction Commit|https://arxiv.org/abs/cs/0408036}}), and the systems a service talks to (Kafka, SaaS APIs, a payment provider) cannot take part at all. Postgres supports the prepare step but warns "Unless you're writing a transaction manager, you probably shouldn't be using PREPARE TRANSACTION" ({{PostgreSQL docs|https://www.postgresql.org/docs/current/sql-prepare-transaction.html}}). 2PC run over consensus inside distributed databases is on {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}}.

A saga gives up atomicity and adds undo: "A saga is a sequence of local transactions. Each local transaction updates the database and publishes a message or event to trigger the next local transaction in the saga. If a local transaction fails because it violates a business rule then the saga executes a series of compensating transactions" ({{microservices.io, Saga|https://microservices.io/patterns/data/saga.html}}; the idea is Garcia-Molina and Salem's, {{SIGMOD 1987|https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf}}). What that means in practice:

  • Compensations are business actions, not rollbacks. A refund is not "the charge never happened"; some steps cannot be compensated at all (an e-mail sent), so they go last.
  • No isolation. Others see the half-done state between steps; microservices.io lists "Lack of isolation" as the main drawback. Defences: a PENDING status other code respects, re-reading before acting, the riskiest step first.
  • Every step and compensation runs at least once, because messages drive them, so each is idempotent.
  • Choreography or orchestration. In choreography "each local transaction publishes domain events that trigger local transactions in other services"; in orchestration "an orchestrator (object) tells the participants what local transactions to execute". Orchestration keeps the flow in one place, which is what durable workflow engines (below) are for.

A saga commits each step and undoes with compensations; 2PC holds locks and waits

When not to use either: if all the data can live in one database, use one transaction. Splitting data across services is what creates the need for sagas; do it for a reason.

2PC's details, the 1987 definition, and event-driven architecture, event sourcing and CQRS (depth)

In 2PC, prepared participants hold their locks and cannot decide alone while the coordinator is gone. Postgres's warning in full: "PREPARE TRANSACTION is not intended for use in applications ... Unless you're writing a transaction manager, you probably shouldn't be using PREPARE TRANSACTION". 2PC lives on inside distributed databases (Spanner, CockroachDB), run over consensus so the coordinator cannot simply vanish. The 1987 paper: a long transaction "is a saga if it can be written as a sequence of transactions that can be interleaved with other transactions", and the system "guarantees that either all the transactions in a saga are successfully completed or compensating transactions are run to amend a partial execution"; "other transactions might see the effects of a partial saga execution". Choreography has no central piece, but the flow is spread across services and hard to see.

Event-driven architecture. In an event-driven architecture, services announce facts ("order 42 placed") on a log instead of calling each other ("e-mail service, send a receipt"). The old page's trade holds: temporal decoupling (the e-mail service can be down and catch up), fan-out (consumers added without touching the producer), an audit trail and replay; against eventual consistency between views, harder tracing (propagate trace ids in message headers: {{Observability|n:3ef5c17b0d0d811e8490c54dd42c2b9b}}) and schema discipline. An event is a fact in the past tense with any number of readers; a command ("send receipt") is a request to one recipient that may refuse, and putting commands on a shared log hides who is responsible. A thin event carries ids and the consumer fetches current data; a fat event carries the data, so consumers work while the producer is down. Schema changes must be backward compatible (add optional fields, never rename or remove), usually enforced by a schema registry (old page, kept as practice).

Event sourcing and CQRS. In event sourcing the events are the source of truth: "every change to the state of an application is captured in an event object, and that these event objects are themselves stored in the sequence they were applied for the same lifetime as the application state itself" ({{Fowler, Event Sourcing, 2005|https://martinfowler.com/eaaDev/EventSourcing.html}}); state is computed by replaying them. CQRS uses "a different model to update information than the model you use to read information" ({{Fowler, CQRS, 2011|https://martinfowler.com/bliki/CQRS.html}}); a Kafka-to-ClickHouse analytics pipeline is a mild form. Fowler: "beware that for most systems CQRS adds risky complexity." Microsoft (2026): "It's costly to migrate to or from an event sourcing solution ... For most systems and most parts of a system, traditional data management is sufficient", not suitable when systems "have straightforward CRUD operations that don't require auditability, replay, or historical reconstruction of state", and "Message brokers such as Apache Kafka typically lack per-entity stream queries and optimistic concurrency. They work well as a distribution layer ... but they aren't a substitute for an event store" ({{Azure Architecture Center, Event Sourcing|https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing}}). The old page's verdict, "rarely worth it outside ledgers", is an opinion that matches both sources. For an ML platform the useful part is the log: usage events, feedback events and pipeline triggers fanned out from one stream (on AWS: EventBridge or SNS into SQS into Lambda, each with a DLQ and idempotent handlers).
