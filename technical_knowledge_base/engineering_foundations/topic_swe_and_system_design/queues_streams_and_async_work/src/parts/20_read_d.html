Idempotent consumers: making the second delivery harmless

An operation is idempotent when doing it twice has the same effect as once. The measured chart above is the whole argument: the same crashes, the same redeliveries, and the unique key turned 52 duplicates into 52 "caught". Four ways to get there, cheapest first:

  1. Write absolute values, not increments. "Set document 981's embeddings to X", SET status = 'paid' instead of balance = balance + 10, overwrite a file at a path derived from the input. Kafka: "In many cases messages have a primary key and so the updates are idempotent (receiving the same message twice just overwrites a record with another copy of itself)". Free, but an e-mail cannot be "set".
  2. Record the message id in the same transaction as the effect, the idempotent consumer: "the message handler inserts the message's ID into the PROCESSED_MESSAGE table. Since the (subscriberId, messageID) is the PROCESSED_MESSAGE table's primary key the INSERT will fail if the message has been already processed successfully" ({{microservices.io, Idempotent Consumer|https://microservices.io/patterns/communication-style/idempotent-consumer.html}}). Works whenever the effect lives in your own database.
  3. Pass an idempotency key to the system that does the effect (a payment, an e-mail provider, a model provider): Idempotency-Key: order-42-receipt, derived from the message, and they deduplicate. How a server implements such keys is on {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}} (section 4); when a client should retry is on {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}.
  4. Version checks for updates that can arrive out of order: UPDATE orders SET ..., version = 7 WHERE id = 42 AND version < 7 ignores anything not newer, deduplicating and reordering at once.
def handle(msg): # called for every delivery, including redeliveries with conn.transaction(): cur = conn.execute( "INSERT INTO processed_events (event_id) VALUES (%s) ON CONFLICT DO NOTHING", (msg["event_id"],)) if cur.rowcount == 0: return # seen before: do nothing, but still ack conn.execute("INSERT INTO receipts (order_id, ...) VALUES (%s, ...)", (msg["order_id"],)) queue.ack(msg) # a crash before this line is now harmless

The key must come from the producer (an event id, an order id plus event type), never be generated on receipt: a random id made by the consumer is new on every redelivery, so nothing is ever deduplicated. Choose it by what must happen once, not by what the transport calls a message: Stripe warns that sometimes "two separate Event objects are generated and sent" for one change and says to deduplicate by "the ID of the object in data.object along with the event.type" ({{Stripe webhooks|https://docs.stripe.com/webhooks}}).

What it costs: a row per processed message, so the table needs an expiry longer than the longest possible redelivery window (the broker's retention or maximum retry period). A dedup window shorter than the redelivery window lets duplicates through: SQS FIFO's 5-minute window means a re-send after 6 minutes is a new message.

Visibility timeouts, leases and heartbeats

A queue cannot see a worker die; it only sees that no ack came. So it lends each message out for a fixed time, the visibility timeout: "If you don't delete it before the timeout expires, the message becomes visible again" ({{SQS visibility timeout|https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html}}); default 30 s, maximum 12 h. The general name for a time-limited claim is a lease, and every broker has one: Kafka's max.poll.interval.ms (5 minutes), share groups' record lock (30 s), Celery on Redis's visibility_timeout (1 hour), RabbitMQ's redelivery when a consumer's channel closes.

The timeout trades duplicates against delay; a heartbeat removes the trade

Predict: a job takes 45 s on a queue with SQS's default 30 s timeout. How many workers run it? Then compare the three settings.

Times illustrative; the measured version of "too short" is above (0.3 s timeout, 0.1 s mean job: 20 to 24 duplicates per 600 jobs). At SQS's 12-hour maximum, a crashed job is 12 hours late.

The production answer is a timeout comfortably above the normal job time plus a heartbeat: a long job keeps extending its own lease. SQS: "use the ChangeMessageVisibility action to extend the visibility timeout while processing the message", within the 12-hour limit from first receipt; Kafka share groups added a RENEW acknowledgement in 4.2 "for extended processing times". To hand a message back early, set its timeout to 0. Even a correct setting is not a hard guarantee: SQS says "there's no absolute guarantee that a message won't be delivered more than once during the visibility timeout period", which is why the consumer is idempotent anyway.

A real trap: Celery acknowledges before it runs
"the default behavior is to acknowledge the message in advance, just before it's executed, so that a task invocation that already started is never executed again" ({{Celery 5.6.3 tasks guide|https://github.com/celery/celery/blob/v5.6.3/docs/userguide/tasks.rst}}): at-most-once, so a worker killed mid-task loses the task. task_acks_late = True makes it at-least-once, but "Even if task_acks_late is enabled, the worker will acknowledge tasks when the worker process executing them abruptly exits or is signaled" unless task_reject_on_worker_lost = True, which the docs warn "can cause message loops" ({{Celery configuration|https://github.com/celery/celery/blob/v5.6.3/docs/userguide/configuration.rst}}). On Redis, a task not acknowledged within the 1-hour visibility timeout "will be redelivered to another worker and executed", which breaks ETA and countdown tasks scheduled further out: "it will be executed again, and again in a loop" ({{Celery Redis broker|https://github.com/celery/celery/blob/v5.6.3/docs/getting-started/backends-and-brokers/redis.rst}}).

Dead-letter queues and poison messages

A poison message fails every time (malformed data, a bug one input triggers, a document too large to embed). Under at-least-once delivery it comes back forever, burning a worker each time, and in an ordered stream it blocks everything behind it. A dead-letter queue (DLQ) moves it aside after N attempts. SQS: "The maxReceiveCount is the number of times a consumer can receive a message from a source queue before it is moved to a dead-letter queue" ({{SQS DLQs|https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html}}). Load the "Poison, no DLQ" preset in the {{Queue lab|#t-lab}} and watch one bad message hold a worker until you set max receives.

  • Alert on DLQ depth. An unwatched DLQ is a slower way of losing data: every message in it is a customer's job that did not happen.
  • Build the replay path first. SQS has a "dead-letter queue redrive" back to the source queue once the bug is fixed; elsewhere you write a script. Replayed messages run again, so the consumer must be idempotent. AWS: "a best practice to always set the retention period of a dead-letter queue to be longer than the retention period of the original queue."
  • Mind ordering. Moving a message aside lets later ones overtake it: "Don't use a dead-letter queue with a FIFO queue if you don't want to break the exact order of messages or operations" (AWS). For ordered streams, stop and page someone, or park every later message for the same key too.

How many retries and with what backoff and jitter is retry policy, owned by {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}, whose measured retry storm shows why retries without a budget make outages worse.

DLQ defaults in RabbitMQ, Dramatiq and Kafka (reference)

RabbitMQ quorum queues count deliveries and default to a limit of 20 since 4.0; without a dead-letter exchange configured, a message over the limit is dropped ({{quorum queues|https://www.rabbitmq.com/docs/quorum-queues}}). Dramatiq moves a message to its dead letter queue after its retries (20 by default) "where it's kept for up to 7 days and then automatically dropped" ({{Dramatiq 2.2.1 guide|https://github.com/Bogdanp/dramatiq/blob/v2.2.1/docs/source/guide.rst}}). Kafka consumer groups have no built-in DLQ: the application (or Kafka Connect's error handling) writes failures to a separate topic; share groups count delivery attempts and let a consumer reject a record.
