Idempotent consumers and deduplication

At-least-once delivery is safe only if running a job twice does no harm. An operation is idempotent when doing it twice has the same effect as doing it once. There are four ways to get there, from cheapest to most general.

  1. Make the work naturally idempotent. Write absolute values, not increments: "set document 981's embeddings to X" instead of "append embeddings"; UPDATE ... SET status = 'paid' instead of balance = balance + 10; write a file to a path derived from its input and overwrite. Kafka's docs note the common case: "In many cases messages have a primary key and so the updates are idempotent (receiving the same message twice just overwrites a record with another copy of itself)". Costs nothing; not always possible (an e-mail cannot be "set").
  2. Record what you processed, in the same transaction as the effect. This is the idempotent consumer pattern: "the message handler inserts the message's ID into the PROCESSED_MESSAGE table. Since the (subscriberId, messageID) is the PROCESSED_MESSAGE table's primary key the INSERT will fail if the message has been already processed successfully" ({{microservices.io, Idempotent Consumer|https://microservices.io/patterns/communication-style/idempotent-consumer.html}}). The id must come from the producer (an event id, an order id), never be generated by the consumer. Works whenever the effect lives in your own database.
  3. Pass an idempotency key to the system that does the effect. When the effect is in someone else's system (a payment, an e-mail provider, a model provider), send a key derived from the message (Idempotency-Key: order-42-receipt) and let them deduplicate. Stripe-style idempotency keys, and how a server should implement them, are on {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}. The client half (when to retry) is on {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}.
  4. Version or sequence checks for state updates that can arrive out of order: keep a version per entity and ignore a message whose version is not newer (UPDATE orders SET ..., version = 7 WHERE id = 42 AND version < 7). Deduplicates and reorders at once.

The code for way 2, in Python with psycopg (the same shape the measured lab used, with the effect in the consumer's own database):

def handle(msg): # called for every delivery, including redeliveries with conn.transaction(): cur = conn.execute( "INSERT INTO processed_events (event_id) VALUES (%s) ON CONFLICT DO NOTHING", (msg["event_id"],)) if cur.rowcount == 0: return # seen before: do nothing, but still ack conn.execute("INSERT INTO receipts (order_id, ...) VALUES (%s, ...)", (msg["order_id"],)) queue.ack(msg) # a crash before this line is now harmless
What it costs
A row per processed message, so the table needs an expiry: keep ids for longer than the longest possible redelivery window (the broker's retention or maximum retry period), then delete them. A dedup window shorter than the redelivery window lets duplicates through: SQS FIFO's 5-minute window means a re-send after 6 minutes is a new message. Some producers send two different ids for one change: Stripe warns that "two separate Event objects are generated and sent" in some cases and says to deduplicate by "the ID of the object in data.object along with the event.type" ({{Stripe webhooks|https://docs.stripe.com/webhooks}}). Choose the key by what must happen once, not by what the transport calls a message.

Visibility timeouts, leases and redelivery

How does a queue know a worker died? It cannot see the process; it can only see that no acknowledgement came. So it lends each message out for a fixed time. SQS calls it the visibility timeout: "The visibility timeout starts as soon as a message is delivered to you. During this period, you're expected to process and delete the message. If you don't delete it before the timeout expires, the message becomes visible again" ({{SQS visibility timeout|https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html}}); default 30 s, maximum 12 h. The general name for a time-limited claim is a lease. Every system has one under some name: Kafka's max.poll.interval.ms (5 minutes), Kafka share groups' record lock (30 s), Celery on Redis's visibility_timeout (1 hour), RabbitMQ's redelivery when a consumer's channel closes.

The timeout trades two failures against each other:

  • Too short: a slow job looks dead and is handed to a second worker while the first is still working: duplicates without any crash (measured above: 20 to 24 per 600 jobs at a 0.3 s timeout). Even a correct setting is not a hard guarantee: SQS says "there's no absolute guarantee that a message won't be delivered more than once during the visibility timeout period".
  • Too long: after a real crash the job waits the whole timeout before anyone retries it; with a 12-hour timeout, a crashed job is 12 hours late.

The production answer is a timeout comfortably above the normal job time plus a heartbeat: a long job periodically extends its own lease. SQS: "use the ChangeMessageVisibility action to extend the visibility timeout while processing the message", within the 12-hour limit from first receipt; Kafka share groups added a RENEW acknowledgement in 4.2 "for extended processing times". To give a message back early (you cannot handle it now), set its timeout to 0.

A real trap: Celery's defaults
Celery acknowledges before running a task by default: "the default behavior is to acknowledge the message in advance, just before it's executed, so that a task invocation that already started is never executed again" ({{Celery 5.6.3 tasks guide|https://github.com/celery/celery/blob/v5.6.3/docs/userguide/tasks.rst}}). That is at-most-once: a worker killed mid-task loses the task. task_acks_late = True makes it at-least-once, but "Even if task_acks_late is enabled, the worker will acknowledge tasks when the worker process executing them abruptly exits or is signaled" unless task_reject_on_worker_lost = True, which the docs warn "can cause message loops" ({{Celery configuration|https://github.com/celery/celery/blob/v5.6.3/docs/userguide/configuration.rst}}). On Redis, a task not acknowledged within the 1-hour visibility timeout "will be redelivered to another worker and executed", which breaks ETA and countdown tasks scheduled further out than that: "it will be executed again, and again in a loop" ({{Celery Redis broker|https://github.com/celery/celery/blob/v5.6.3/docs/getting-started/backends-and-brokers/redis.rst}}).

Dead-letter queues and poison messages

A poison message is one that fails every time: malformed data, a bug triggered by one input, a document too large to embed. Under at-least-once delivery it comes back forever, wasting a worker each time, and in an ordered stream it blocks everything behind it. The fix is a dead-letter queue (DLQ): after N failed attempts the message is moved aside to a separate queue for a human or a repair job. SQS: "The maxReceiveCount is the number of times a consumer can receive a message from a source queue before it is moved to a dead-letter queue" ({{SQS DLQs|https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html}}). RabbitMQ quorum queues count deliveries and default to a limit of 20 since 4.0; without a dead-letter exchange configured, a message over the limit is dropped ({{quorum queues|https://www.rabbitmq.com/docs/quorum-queues}}). Dramatiq moves a message to its dead letter queue after its retries (20 by default) "where it's kept for up to 7 days and then automatically dropped" ({{Dramatiq 2.2.1 guide|https://github.com/Bogdanp/dramatiq/blob/v2.2.1/docs/source/guide.rst}}). Kafka consumer groups have no built-in DLQ: the application (or Kafka Connect's error handling) writes failures to a separate topic; share groups count delivery attempts and let a consumer reject a record.

Three rules, all about what happens after:

  • Alert on DLQ depth. A DLQ nobody watches is a slower way of losing data. Any message in it means a customer's job did not happen.
  • Design the replay path before you need it. SQS has a "dead-letter queue redrive" that moves messages back to the source queue once the bug is fixed; elsewhere you write a script. Because replayed messages run again, the consumer must be idempotent (previous section). Keep DLQ retention longer than the source queue's: AWS calls it "a best practice to always set the retention period of a dead-letter queue to be longer than the retention period of the original queue."
  • Mind ordering. Moving a message aside lets later ones overtake it: "Don't use a dead-letter queue with a FIFO queue if you don't want to break the exact order of messages or operations" (AWS). For ordered streams, either stop and page someone, or park every later message for the same key too.

How often to retry before dead-lettering, and with what backoff and jitter, is retry policy: owned by {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}, whose measured retry storm shows why retries without a budget make outages worse.
