The idea in one screen

Handing work to a queue or a log means it will be delivered at least once, never exactly once, so you make its effect happen once (an idempotent consumer, an outbox for the hand-off itself) and you watch the age of the oldest message, because a queue hides overload instead of removing it.

Three places where handed-off work goes wrong, and the fix for each

1The hand-off. Saving a row and publishing its event are two writes with no shared transaction; a crash between them loses the event. Fix: the transactional outbox.
2The acknowledgement. A worker that dies after the work but before the ack gets the message back, and the work runs twice. Fix: an idempotent consumer keyed on a producer-assigned id.
3The rate. If arrivals exceed what workers can finish (λ > C/S), nothing errors: the backlog just grows. Fix: backpressure, workers sized by Little's law, an alarm on message age.

Measured on a real Postgres later on this page: 1,000 jobs with a 5% crash chance were done 1,046 to 1,053 times, and exactly 1,000 with a unique key on the job id; a naive dual write lost 19 to 28 events per 500 orders, the outbox none.

You need: nothing beyond a web service and a database transaction. The parent root's Step 3 ("Slow work leaves the request path", {{Topic: swe-and-system-design|n:3c65c17b0d0d81048ae0dd14ac399b4d}}) is the five-minute version. Why "exactly once" is an end-to-end property of any distributed system, and how Kafka's partitions are replicated, are on {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}}; this page is the queue and stream machinery.

Broker
the system that stores messages between producer and consumer (SQS, RabbitMQ, Kafka, a Postgres table).
Queue, log
a queue deletes each message once a worker acknowledges it; a log keeps every message and each reader tracks its own offset.
Ack
telling the broker a message is done.
At-least-once
ack after the work: never lost, sometimes repeated. At-most-once is the reverse.
Idempotent consumer
records each message id with its effect, so a repeat does nothing.
Visibility timeout
how long a claimed message stays hidden before the broker hands it to someone else.
Dead-letter queue
where a message goes after too many failed attempts.
Outbox
the event written as a row in the same transaction as the data, published later by a relay.

Why async: accept now, do later

The request path is everything between a request arriving and its response. Work done on it makes every user wait and holds one of the server's limited request slots: on the parent root, 5 PDF uploads among 30 chat messages made chat messages wait up to 3 seconds that should have waited none (the root's Step 3, {{Topic: swe-and-system-design|n:3c65c17b0d0d81048ae0dd14ac399b4d}}). The fix separates accepting work from doing it: the handler writes a message (a small record such as {"type": "embed_document", "doc_id": 981}) somewhere durable and answers at once. The producer writes messages, the consumer or worker handles them, the broker stores them in between, and to acknowledge (ack) is to tell the broker "done".

Over HTTP the hand-off is 202 Accepted, "the request has been accepted for processing, but the processing has not been completed" ({{RFC 9110 §15.3.3|https://www.rfc-editor.org/rfc/rfc9110#section-15.3.3}}), with a job id to poll or a later webhook. Designing those endpoints, and handing work to a background task inside one service (and what that loses when the process dies), is {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}'s; this page starts where the work crosses into a broker.

Goes async on the chat assistant

  • Embedding an uploaded document (tens of seconds)
  • Generating a conversation title after the first reply
  • Usage metering and billing events
  • Receipts, e-mails, outgoing webhooks to customers
  • Nightly evaluation runs, re-embedding the corpus (the worked example)
  • Long agent tasks that run for minutes

Stays on the request path

  • The reply the user is reading (stream it instead)
  • Anything the next screen needs to show correctly
  • Checks that must reject the request (auth, rate limits, validation)
  • Writes the user must see confirmed (saving the message itself)

What async costs: the result is late, so the product must show progress and handle "not ready yet"; failures happen where no user sees them, so they need their own alerts; jobs can run twice; and the broker is one more system to run. A rule of thumb (opinion, not a sourced rule): make work async when it is slow, can fail and be retried independently, or fans out to several consumers; keep it synchronous when the caller needs the result to continue.
