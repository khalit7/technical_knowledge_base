Delivery semantics: at-most-once, at-least-once, "exactly-once"

Every consumer does two things with a message: the work (send the e-mail, write the embedding) and the acknowledgement (delete it from the queue, or commit the offset). A crash can land between them. Which one you do first decides what a crash costs you, and that choice has three names. Kafka's documentation defines them: "At most once: Messages may be lost but are never redelivered. At least once: Messages are never lost but may be redelivered. Exactly once: Each message is processed once and only once" ({{Kafka design, Message Delivery Semantics|https://kafka.apache.org/43/design/design/}}).

At-most-once: acknowledge, then work

msg = queue.receive() queue.delete(msg) # ack first send_receipt(msg.order) # crash here: receipt never sent

A crash after the ack loses the job. Kafka: the consumer "crashes after saving its position but before saving the output ... This corresponds to 'at-most-once' semantics". Fine for metrics samples or a "typing..." indicator; wrong for anything a user paid for.

At-least-once: work, then acknowledge

msg = queue.receive() send_receipt(msg.order) # crash after this line... queue.delete(msg) # ...and msg comes back: sent twice

A crash after the work but before the ack redelivers the job, which then runs again. Kafka: "the first few messages it receives will already have been processed. This corresponds to the 'at-least-once' semantics". This is the default almost everywhere, because a duplicate can be detected and a loss cannot.

Why not just "exactly once"? Because the sender cannot know what the receiver did. Kafka's docs give the producer's version: "If a producer attempts to publish a message and experiences a network error, it cannot be sure if this error happened before or after the message was committed." The consumer's version is the crash above. The general result is old. Jim Gray's 1978 notes prove that two parties who can only talk through messengers that may be lost cannot be certain they agree: "Let P be the shortest such protocol. Suppose the last messenger in P gets lost. Then either this messenger is useless or one of the generals doesn't get a needed message" ({{Gray, Notes on Data Base Operating Systems, §5.8.3.3.1|https://jimgray.azurewebsites.net/papers/dbos.pdf}}; the "two generals" problem). So no protocol can make the delivery happen exactly once over a network that can lose messages. What systems offer instead is an effect that happens once: at-least-once delivery plus deduplication, sometimes called effectively-once or exactly-once processing.

Read the fine print on "exactly-once"
Kafka's own docs: "Many systems claim to provide 'exactly-once' delivery semantics, but it is important to read the fine print, because sometimes these claims are misleading (i.e. they don't translate to the case where consumers or producers can fail, cases where there are multiple consumer processes, or cases where data written to disk can be lost)." Two current examples: SQS FIFO's "exactly-once processing" means the queue drops a re-sent message with the same deduplication id "within the 5-minute deduplication interval" ({{SQS FIFO|https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/FIFO-queues-exactly-once-processing.html}}); a consumer that crashes before deleting still gets the message again. And an acknowledgement is only as good as the disk behind it: Jepsen found that NATS JetStream "calls fsync to flush data to disk only once every two minutes, but acknowledges messages immediately", and simulated power failures lost "roughly thirty seconds of writes" ({{Jepsen, NATS 2.12.1, 2025-12-08|https://jepsen.io/analyses/nats-2.12.1}}).

Where to say it in an interview: "at-least-once delivery, with idempotent consumers, so the effect happens once", then name the deduplication key. That shows you know delivery and effect are different things (advice kept from the old page).

Measured: crashes, redelivery and duplicates on a real Postgres

To see these semantics rather than take them on trust, this page ran three small experiments on a laptop (Apple M1 Pro, PostgreSQL 16 from the pgserver wheel, 2026-10-04; script src/lab/pg_lab.py, about 3 minutes in all). Everything is real: separate OS processes, real transactions, real row locks, real redelivery by timeout. The only artificial part is the crash, injected with os._exit() at a chosen line, which kills the process with no clean-up, as a kill signal or a power cut would.

The queue. A jobs table used the way SQS works. A worker claims the oldest visible job and hides it for a visibility timeout (2 s here), all in one statement:

UPDATE jobs SET visible_at = now() + interval '2 seconds', receives = receives + 1 WHERE id = (SELECT id FROM jobs WHERE visible_at <= now() ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING id, order_id, receives;

It then "sends a receipt" by inserting a row into a second database (standing in for an e-mail provider: outside the queue's transaction, as a real one would be) and finally deletes the job. Four worker processes, 1,000 jobs, a 5% chance of crashing per job; a supervisor restarts crashed workers, as systemd or Kubernetes would. Three runs per mode.

What 1,000 jobs became, three runs per mode

  • At-most-once (delete, then send): 52, 44 and 53 receipts lost, exactly one per crash. No error anywhere.
  • At-least-once (send, then delete): every order got its receipt, and 52, 46 and 53 customers got two. Again one per crash: the redelivered job runs in full.
  • At-least-once with an idempotent receiver: the receipts table has a primary key on the job id, so the second insert does nothing (ON CONFLICT DO NOTHING). Exactly 1,000 receipts in all three runs; the 52, 46 and 53 repeats were caught and counted.
  • No crashes at all, but a visibility timeout of 0.3 s with job times averaging 0.1 s (exponential, so about 5% of jobs take longer than 0.3 s): 20, 24 and 23 duplicates per 600 jobs. A slow job is indistinguishable from a dead worker; the queue hands it to a second worker while the first is still busy (visibility timeouts, below).

The expected count is simple: if each delivery crashes after the side effect with probability p, a job is delivered on average 1/(1 − p) times, so 1,000 jobs at p = 0.05 give about 1,000 × 0.05 / 0.95 = 52.6 duplicates; the three runs gave 50.3 on average. The {{Queue lab|#t-lab}} tab simulates the same queue with any settings; its model of these two runs, averaged over 20 seeds, gives 53.0 duplicates (range 38 to 76) for the crash run and 21.5 (range 15 to 28) for the 0.3 s timeout run, against 50.3 and 22.3 measured. The defaults of its two "Lab run" presets reproduce the measurement independently: the model shares the settings and was not fitted to the results (checked in src/recompute.py).

What Kafka's "exactly-once" really guarantees

Kafka is the system that most often advertises exactly-once (EOS, exactly-once semantics), so it is worth knowing precisely what it does. Two mechanisms, added in Kafka 0.11 (2017) by {{KIP-98|https://cwiki.apache.org/confluence/display/KAFKA/KIP-98+-+Exactly+Once+Delivery+and+Transactional+Messaging}}:

1. The idempotent producer removes duplicates caused by producer retries. "The broker assigns each producer an ID and deduplicates messages using a sequence number that is sent by the producer along with every message" ({{Kafka design|https://kafka.apache.org/43/design/design/}}). If a send times out and is retried, the broker sees the same (producer id, sequence) and does not append it twice. It has been on by default since Kafka 3.0, together with acks=all (wait for all in-sync replicas), though "In 3.0.0 and 3.1.0, a bug prevented the idempotence default from being applied" until 3.0.1, 3.1.1 and 3.2.0 ({{Kafka 3.0 upgrade notes|https://kafka.apache.org/30/getting-started/upgrade/}}). It covers one producer session writing to one partition; it says nothing about consumers.

2. Transactions make read-process-write atomic. A stream processor reads from topic A, computes, and writes to topic B. Exactly-once there means: the output and the "I have consumed up to offset N" record become visible together or not at all. The steps, in brief:

  1. The producer is configured with a transactional.id, a stable name that survives restarts. A broker acting as transaction coordinator keeps the state of its transactions in an internal, replicated transaction log.
  2. On start, the producer registers its transactional.id; the coordinator bumps an epoch number, so "any previous zombie instance of the producer is fenced off" (KIP-98). A zombie is an old instance that was presumed dead but is still running; fencing means its writes are rejected.
  3. Within a transaction the producer writes output records to any partitions, and also the consumer's new offsets (sendOffsetsToTransaction). "The consumer's position is stored as a message in an internal topic, so we can write the offset to Kafka in the same transaction as the output topics" ({{Kafka design|https://kafka.apache.org/43/design/design/}}).
  4. On commit, the coordinator writes COMMIT markers into every partition involved. Downstream consumers with isolation.level=read_committed only see records of committed transactions. The default is read_uncommitted, which shows aborted records too ({{consumer configs|https://kafka.apache.org/43/configuration/consumer-configs/}}).

The scope is Kafka to Kafka. The docs: the transactional producer and read-committed consumer "can be used generally to provide exactly-once delivery when reading, processing and writing data on Kafka topics. Exactly-once delivery for other destination systems generally requires cooperation with such systems ... Otherwise, Kafka guarantees at-least-once delivery by default." If the consumer's work is "send an e-mail" or "write to Postgres", Kafka's transaction cannot include it; you are back to at-least-once plus deduplication, or to storing the offset in the same database transaction as the output, which the docs recommend: "letting the consumer store its offset in the same place as its output".

Correction to the old page
The old "Distributed Systems Basics" page listed "Kafka transactional producer + idempotent consumer offsets" as a way to get exactly-once processing. "Idempotent consumer offsets" is loose: what Kafka does is commit the consumer's offsets inside the producer's transaction, and that gives exactly-once only when input and output are both Kafka topics. Any external effect still needs its own deduplication.

What it costs, and how solid it is. Confluent's 2017 measurement: with 1 KB messages and 100 ms transactions, producer throughput fell 3% against an at-least-once, in-order producer, and 20% against the then-default acks=1 ({{Narkhede, Confluent, 2017|https://www.confluent.io/blog/exactly-once-semantics-are-possible-heres-how-apache-kafka-does-it/}}); with Kafka Streams and a 100 ms commit interval the loss was 15 to 30%. The docs add that "using a replication factor lower than 3 effectively voids EOS" (recommend 3 with min.insync.replicas=2, {{Kafka Streams docs|https://kafka.apache.org/43/_print/}}). And the protocol had real bugs: in 2024 Jepsen found that "There is no concept of a transaction number. When a server receives a commit (or abort) message, it has no way to know what transaction the client intended to commit", reproduced aborted reads and torn transactions in Kafka itself (KAFKA-17754), and Kafka's engineers expected KIP-890 to fix it ({{Jepsen, Bufstream 0.1.0, 2024-11-12|https://jepsen.io/analyses/bufstream-0.1.0}}). KIP-890 bumps the epoch "after every commit/abort marker" so each transaction is identified by (producer id, epoch) ({{KIP-890|https://cwiki.apache.org/confluence/display/KAFKA/KIP-890%3A+Transactions+Server-Side+Defense}}); its second phase shipped in Kafka 4.0, where it "reduces the chances of 'zombie transactions'" ({{Kafka 4.0 release|https://kafka.apache.org/blog/2025/03/18/apache-kafka-4.0.0-release-announcement/}}). Whether KAFKA-17754 is fully closed was not checked for this page.

When not to use Kafka transactions: when the output is not a Kafka topic (they cannot cover it), and when a duplicate is cheap to absorb downstream (an idempotent consumer is simpler and faster).
