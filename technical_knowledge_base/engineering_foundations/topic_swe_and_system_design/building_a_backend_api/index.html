The idea in one screen

Every request runs the same pipeline inside one worker process (server, middleware, router, dependencies, validation, handler, data layer, response), and building a backend well means keeping each stage bounded: never block the event loop, never hold a database connection across a slow call, and never let a request die half done when the process is told to stop.

The running example is the chat API built for this page (src/service/app.py). Right (below, on a phone): what the handler borrows (a pooled database connection, the model client, somewhere to hand off work) and what the process shares (one event loop, a pool of 40 threads). The bottom strip is the process's own life, from startup to a drained shutdown. Each label is a section below.

You need: what an HTTP request and response contain (HTTP, sections 1 and 2). The contract the service exposes (error shapes, pagination, idempotency keys, rate limits, versioning, OpenAPI) is designed on Service APIs; this page builds the service behind it.

New terms

ASGI: the Python interface between the server that owns the socket (uvicorn) and the application (FastAPI).
Middleware: code wrapped around every request, on the way in and on the way out.
Dependency: a function FastAPI runs before one route (current user, a database session) and passes in.
Event loop: the one thread that runs every async def handler of a process, switching at each await.
Worker: one server process; several share a port to use several cores.
Connection pool: a few open database connections lent to requests and taken back.
N+1 queries: one query for a list, then one more per item, instead of one query in all.
Lifespan: the app's startup and shutdown hook (open the pool, close it).
Liveness, readiness: "is the process alive" against "should traffic come here now".
Graceful shutdown: stop accepting, finish what is in flight, release resources, exit.

2. One request through the service, stage by stage

A Python web service has two programs in one process. The server, uvicorn, owns the socket: it accepts connections and parses the HTTP bytes. The application, FastAPI (built on Starlette), receives each parsed request through ASGI (asgi.readthedocs.io): a dictionary called the scope, plus two functions, receive for the body and send for the response. 3. Validation: parse at the edge, once

Every byte from a client is untrusted: malformed, malicious, or from an app version two years old. The rule is to turn it into typed objects at the edge, once, and reject what does not fit, so code inside never sees a missing field or a string where a number should be. Alexis King calls it "parse, don't validate": the result of checking should be a value whose type proves the check happened (lexi-lambda.github.io, 2019). A pydantic model is exactly that, and FastAPI builds it before the handler runs:

  • Limits on every string and number (Field(min_length=1, max_length=200), max_tokens between 1 and 4096): an unbounded content field is how someone sends you 2 GB, or a prompt that costs a fortune.
  • extra="forbid" rejects unknown fields, catching client typos (max_token) that would otherwise be silently ignored; the cost is that clients cannot send fields from a newer version. Anthropic's API rejects an unknown field with "Extra inputs are not permitted" (Claude API errors), which is pydantic's own wording.
  • Literal["small", "large"] is an enum: any other model name fails with a message listing the allowed values.

Before and after, on the same bad body {"title": "", "colour": "blue"} (both captured): FastAPI's default answer, and the same failure after the demo's twelve-line exception handler rewrites it into the problem-details shape that Service APIs specifies.

Before: FastAPI default (application/json)
After: problem details with a JSON Pointer per field

Both report every failing field at once, so a form can highlight two mistakes in one round trip. The default exposes pydantic's internals (loc, ctx, and the echoed input, which can leak a secret a user pasted into the wrong field); the rewritten one points at each field with a JSON Pointer (RFC 6901), names a query parameter instead ("parameter": "limit" for ?limit=500), and for a body that is not JSON says where it broke ("Invalid JSON at character ...").

Where validation stops
Pydantic v2's validation core is written in Rust (pydantic docs), so it costs little next to network and database time. It checks shape: types, lengths, ranges, allowed values. It cannot check meaning that needs the database: whether the chat exists and belongs to the caller, whether the user has credits. Those are business rules in the handler, and they answer 404, 403 or 409 rather than 422. Keep pydantic models at the boundary rather than deep in the program (Code design).

4. Middleware, dependencies and the handler: what goes where

Three places can hold code that runs for a request, and choosing the wrong one is a common source of bugs. The test is scope: does it apply to every request, to some routes, or to one?

Middleware wraps everything; a dependency wraps one route; the handler is the route

Drawn from the recorded order in section 2: the outer ring (registered last) enters first and leaves last. A dependency runs only for routes that declare it, after routing and before the handler; FastAPI resolves it together with the parsed body, so both are ready when the handler starts.

Authorise the object in the query, every time

Knowing who is calling (authentication, Auth) is not the same as checking they may touch this chat. The first entry of OWASP's API Security Top 10 (2023) is Broken Object Level Authorization (API1:2023): an endpoint takes an ID from the URL and returns or changes that object without checking the caller owns it; change chat_ae81... to someone else's ID and you read their chats. The fix belongs in the data layer of the handler: scope every query by the caller, so a lookup by ID alone does not exist in the code base. The demo's:

It answers 404, not 403, for someone else's chat, so the API does not confirm the chat exists. Add a test per endpoint that tries another user's ID (Testing and quality); roles and scopes (chats:read) come later, as a policy layer in a dependency.

5. The data layer: pools, transactions and round trips

Almost every handler reads or writes the database, and three habits decide whether that scales: borrow connections from a pool, make one unit of work one transaction, and count round trips. The demo uses SQLite in memory; a real service uses Postgres with the same tables (Topic: databases).

Connection pools, and the arithmetic that runs them out

A Postgres connection is a whole operating-system process on the server, and opening one costs a process start plus authentication; Running Postgres in production measures both (section 7). So each service process keeps a pool: a handful of open connections lent to a request and taken back. Then do the arithmetic nobody does: SQLAlchemy's default pool is 5 connections plus up to 10 overflow, so twenty pods open up to 20 x 15 = 300 connections, a deploy briefly runs old and new pods together (600), and Postgres's max_connections defaults to 100. The usual answer is small per-process pools behind a pooler such as PgBouncer in transaction mode, not a bigger max_connections (sizing with Little's law is on Capacity planning and performance).

Never hold a connection across the model call

An LLM handler reads the chat, waits seconds for the model, then saves the reply. If it borrows one connection at the start and returns it at the end, the connection sits idle through the whole model call, and the pool needs one connection per request in flight. Little's law (in-flight = arrival rate x time held) makes the cost exact. Predict: at the root's busy hour of 231.5 model calls a second (only the message request calls the model) and a 10 s model call, how many connections does holding need, and how many does borrowing twice for 1 ms each need? The same rule covers transactions: a transaction left open across the model call holds its locks and its snapshot for seconds. Read what you need, commit or release, call the model, then open a short transaction to save the result.

One unit of work, one transaction

A transaction makes several writes commit together or not at all. In the demo's message handler the reply, the credit charge and the stored response (for idempotent retries) must agree, so they are one transaction:

If they were separate statements, a crash between them would leave credits taken and no reply, or a reply nobody paid for. Isolation levels and the anomalies they allow are Transactions and concurrency's subject; the handler's job is to draw the boundary in the right place.

A bug in this demo, found later: work outside the transaction left a key claimed forever
The handler claims its idempotency key with an INSERT before the transaction above. If anything fails between the claim and the commit (the model call times out, the process is killed, any unexpected exception), the row stays at started, nothing releases it, and every retry with that key gets 409 "still in progress" forever. The demo releases the claim only on the two paths it thought of (unknown chat, streaming). Code design found and measured this while refactoring the same handler. The fix is general handler hygiene: release on every exit that did not save a response (Code design's step 10 wraps the claim in one context manager, idempotency_claim), and give each claim an expiry so a claim left by a process that died without cleanup is taken over after a few minutes. The captures on this page come from the demo as it was and were not rerun.

Count round trips: N+1 queries

The list page of chats with each chat's last message, written the obvious way with an ORM's lazy loading, is one query for 20 chats and then one per chat: 21 round trips. One query with a join returns the same rows. Query planning and performance measured it on one laptop (psycopg 3.3.6, 0.056 ms for SELECT 1): 1.42 ms against 0.22 ms per page, 6.5 times. At 2 ms the 21 trips cost 42 ms against 2 ms for the single query; the root adds 21 x 0.067 ms of lookup time for 43.41 ms.

Every query passes values as parameters (the demo's ? placeholders), so the database never interprets user text as SQL: that is the whole fix for SQL injection. The fix for N+1 is eager loading (selectinload or joinedload in SQLAlchemy, select_related and prefetch_related in Django) or writing the join; the way to notice is a trace that shows how many queries each request made (Observability). Paging itself is one query per page with a cursor (the demo's where (created_at,id) > (?,?); the design is Service APIs's).

An async handler needs an async driver
The demo's message handler is async def but calls sqlite3, a blocking driver. With an in-memory SQLite that blocks for microseconds; with a network database it blocks the whole event loop for every query (section 6 measures what that does). Use an async driver (asyncpg, psycopg 3's async connection, SQLAlchemy's asyncio extension) in async def handlers, or keep the handler a plain def.

6. Async, threads and worker processes: how many requests can wait at once

A handler spends most of its time waiting: on the database, on the model, on another service. What decides throughput is what the process does with the other requests while one waits. FastAPI gives two ways to write a handler, and uvicorn a third lever:

  • async def runs on the process's single event loop. At each await the loop switches to another request; a call that blocks without await (time.sleep, a synchronous HTTP client, a blocking database driver) stops every request on that worker until it returns (FastAPI, async).
  • Plain def runs in a worker thread from AnyIO's pool, so blocking is fine; the pool has 40 threads by default (CapacityLimiter(40) in AnyIO 4.15.1, printed by the run below).
  • --workers N starts N processes sharing the port, each with its own loop and pool.

Predict: 50 requests arrive at once, each waiting 500 ms. Written as async def with time.sleep(0.5), how long until the first one is answered? Then pick a style.

What the bars show:

  • Blocking inside async def: 50 x 500 ms run one after another, 25,460 ms in all, and the median request waited 25,421 ms, not about 12.75 s, the median a fair one-at-a-time queue would give (answers at 0.5, 1.0, ... 25 s): each handler's response is written only after the loop gets back to it, by which time every other request's sleep had run. One blocking call in an async handler hurts every request on the worker, not only the slow one.
  • await asyncio.sleep: all 50 wait at the same time; the last answer came at 745 ms (500 ms of waiting plus the overhead of 50 requests on one loop).
  • Plain def: also concurrent, until the pool runs out: 40 answers by about 740 ms, the last 10 at 1,066 to 1,102 ms, a second wave. The 40-thread cap is a hidden concurrency limit; raise it deliberately or prefer async for many slow waits.
  • Four workers divide the blocking damage but do not remove it: 10,241 ms, because the operating system handed the 50 connections to the workers unevenly (20, 14, 9 and 7 requests on this macOS laptop) and the busiest worker sets the time.

7. Configuration and secrets: read once, typed, at startup

Configuration is, in the Twelve-Factor App's words, "everything that is likely to vary between deploys (staging, production, developer environments, etc)": the database URL, the model name, the provider key, timeouts. Its rule: "The twelve-factor app stores config in environment variables", and its test is "whether the codebase could be made open source at any moment, without compromising any credentials" (12factor.net/config). In Python the usual tool is pydantic-settings: a class whose fields are read from the environment, typed and validated like a request body, once, when the process starts.

Measured: when the same setting comes from five places, the one nearest the code wins

Top row: highest priority; each row is the source added at that step, numbered in the order added, and the value then read. Recorded with pydantic-settings 2.16.1: a Settings class with env_prefix="CHAT_", a .env file and a secrets_dir, each source added in turn for model_name. The value read went small, from-secrets-dir, from-dotenv, from-environment, from-init: an argument in code beats an environment variable, which beats the .env file, which beats a file in the secrets directory, which beats the class default.

  • Fail fast. A required setting that is missing stops the process at startup, not on the first request that needs it. The recorded error: 1 validation error for Required / database_url / Field required [type=missing, ...]. A crash loop at deploy time is visible; a service that starts and fails one request in a hundred is not.
  • Secrets are typed as secrets. A SecretStr field prints as SecretStr('**********'), so the whole settings object can be logged at startup without leaking the key; the value comes out only through provider_key.get_secret_value() at the point of use.
  • Where secrets come from in production: a secret manager (Vault, AWS Secrets Manager, GCP Secret Manager) injected as environment variables or mounted as files; mounted files are what secrets_dir reads (a Kubernetes Secret volume, Docker's /run/secrets). Never in the repository, the image, a URL or a log line. Rotating a secret then means a restart or a reload hook, so design for both keys being valid for a while.
  • Read once, pass down. Build the settings object in the lifespan hook (section 9) or a cached dependency, and pass it to what needs it; code that reads os.environ in the middle of a handler cannot be tested or audited.

Feature flags and gradual config rollouts are configuration that changes while the process runs; rolling them out like code is on Reliability engineering. The code-design view of settings objects is on Code design.

8. Background work: answer first, then do the rest

Some work does not need to finish before the user gets an answer: send a notification, meter the tokens, generate a chat title, index the message for search. Doing it inline makes every user wait for it. There are three places to put it, and the difference is what happens when the process dies.

9. Health checks, startup and graceful shutdown

A service is started, checked and stopped by something else: a load balancer, Kubernetes, a deploy script. Each of those asks a question the service must answer honestly.

Two health endpoints, two questions

Liveness: "is this process alive?"

GET /livez (the demo's /v1/health) answers 200 from the process itself, touching nothing else. Failing it gets the container restarted, so it must not check the database: when the database has a slow minute, every pod would fail liveness and restart at once.

Readiness: "should traffic come here now?"

GET /readyz checks what a request needs (a pooled SELECT 1 with a short timeout, the model client configured) and answers 503 while starting, while a dependency is down, and once shutdown begins. Failing it takes the pod out of the load balancer, without a restart.

Kubernetes' three probes (liveness, readiness, startup), their defaults and the outages caused by probes that check too much are on Reliability engineering.

Startup and shutdown belong to the lifespan hook

Open the pool, read the settings, warm the model client once, in the app's lifespan: code before its yield runs before the first request, code after it once the server has drained. A pool opened lazily inside the first request makes the first users slow; one closed nowhere leaves connections for Postgres to time out.

What a stop actually looks like

Kubernetes stops a pod by sending SIGTERM to the container's main process; "The default terminationGracePeriodSeconds setting is 30 seconds", after which "The container runtime sends SIGKILL to any processes still running" (Kubernetes, pod lifecycle). Removal from the load balancer happens "At the same time as the kubelet is starting graceful shutdown", not before it. With the default, the server stopped accepting at once (a new connection at 1,310 ms was refused), closed the idle keep-alive connection (the request on it failed with RemoteDisconnected), let the slow request finish with 200 at 3,218 ms, waited for the background job (done at 3,317 ms), then ran the lifespan shutdown and exited at 3,426 ms. Both follow uvicorn's Server.shutdown in uvicorn/server.py (0.54.0): close the listeners, ask each connection to shut down, wait for connections and then tasks up to the timeout, cancel what is left, run the lifespan shutdown. The process then re-raises the signal it caught, so its exit status is "killed by SIGTERM" (143 in a shell) even after a clean drain.

The shutdown checklist for a service behind a load balancer
  • Keep serving briefly after SIGTERM. uvicorn refuses new connections immediately, but the balancer may still route to the pod for a moment while endpoints update. The common fix is a preStop hook that sleeps a few seconds before the signal, so the pod leaves the balancer first; the sleep counts against the 30 s.
  • Bound the drain below the grace period. Set --timeout-graceful-shutdown (or your server's equivalent) a few seconds under terminationGracePeriodSeconds, so cancellation and the lifespan shutdown run before SIGKILL, which runs nothing.
  • Long streams outlive any grace period. A model reply can stream for minutes; decide whether to raise the grace period for that deployment, or cut streams and let clients retry with their idempotency key.
  • Background work in the process dies with it once the timeout passes (section 8): what must happen goes on a queue.

10. Worked example: the LLM-backed endpoint, end to end

POST /v1/chats/{chat_id}/messages is where every section meets: it costs money, takes seconds, may stream, and is the request users retry. Step through the demo's real handler; each step shows the code that ran for the captures, what it does, and what a production version adds.

Stepper: the message handler, top to bottom real code

Code from src/service/app.py with its real line numbers. The demo "calls the model" with a sleep and an echo; the captured responses of each branch (401, 429, 400, 201, the replay, 409, 422, the stream) are in the exchanges block of section 2.

The order is the design. Cheap rejections come first (credentials; the rate limit, a bucket of 5 requests refilling at 1 per second; a missing key), so a flood of bad requests costs almost nothing; the rate limit runs before the idempotency claim, so a 429 is not stored against the key; the expensive call happens only after the request is known to be valid, owned and not a duplicate; and everything that must agree afterwards commits in one transaction.

What the production version of this handler adds
  • A timeout on the model call (httpx.AsyncClient(timeout=...) or asyncio.timeout), shorter than the client's, with the provider's own retries counted in; the demo has none, which is how the stuck-key bug of section 5 is triggered. Timeout budgets are Reliability engineering's.
  • One query for the history, then release the connection before the model call (section 5), and an async client so the wait is an await (section 6).
  • Stop when the client goes away. When the user closes the tab mid-stream, check await request.is_disconnected() between chunks (Starlette also raises on a failed send) and cancel the model call, or you pay for tokens nobody reads.
  • Charge by what was used: the provider's usage (input and output tokens) in the same transaction as the stored reply, not a flat 10 credits.
  • Stream after the checks, store at the end. The demo frees the idempotency key on the streaming path and stores nothing; a real one stores the finished message so a retry can fetch it. The status code is gone once streaming starts, so failures become an error event (Streaming and real-time, sections 4 and 5).
  • Hand off the rest (title generation, metering, search indexing) to a queue (section 8), and pin the model version you call, since a model change is a contract change (Production eval engineering).

Depth: mistakes, JSON rules and provenance

Common mistakes that the sections above do not already show
  • A GET that changes something. Link previews, crawlers and retrying proxies send GETs freely because RFC 9110 says GET is safe; GET /unsubscribe?id=... gets triggered by an email scanner.
  • Returning 200 with {"error": ...}. Every proxy, monitor, retry policy and SDK reads the status code: dashboards stay green while users fail.
  • Leaking internals in a 500. Stack traces and SQL tell an attacker your stack and schema; log them under the request ID and return a generic problem.
  • Checking "is the key already there?" with a SELECT, then inserting. Two concurrent retries both see "absent"; let a unique constraint (the demo's primary key(owner, key)) make the second insert fail.
  • A streaming endpoint behind a buffering proxy works on a laptop and arrives as one lump in production; test through the real proxy.
  • Renaming a field "because the old name was ugly" breaks every client that reads it: add the new field, keep the old one, deprecate it with a date, remove it only in a new version.
  • No limits on strings, lists, page sizes or bodies: one request can then exhaust memory, database time or model tokens.
JSON rules every handler's output must respect

JSON has no date type, no integer against decimal distinction and no comments (RFC 8259), hence three rules:

  • Big integers break in browsers. JavaScript numbers are 64-bit floats, exact only up to 253 − 1 = 9,007,199,254,740,991 (RFC 8259 §6 warns about this range). Send IDs as strings with a type prefix, like the demo's "chat_ae8136d1b896" and Stripe's cus_....
  • Dates are strings by convention: one format everywhere, Unix seconds (the demo's created_at) or RFC 3339 with a time zone ("2026-10-04T19:06:35Z").
  • Money is never a float: 0.1 + 0.2 is not 0.3 in binary floating point; send integer minor units (cents, credits), as Stripe does with amount: 2000 for $20.00.

The contract details this page used to keep (PUT against PATCH, about:blank and Stripe-Should-Retry, the empty end token, allow-listed filters bound into the cursor, descending keysets, Hyrum's law, Brandur Leach's atomic phases, OpenAPI 3.2.0 and the LLM call as an ordinary resource) are on Service APIs (sections 2 to 4), and why a 422's reason phrase says "Entity" is on HTTP (section 2). The demo's own cursor is hex-encoded JSON, which a curious client can decode: fine for a demo, a mistake in production.

What changed from the old pages, and the corrections they carried

This page replaced the API half of the old "API and Code Design" page (fetched 2026-09-22, saved in src/live.md, every claim mapped in src/coverage.json); its code-design half went to Code design. On 2026-10-24 the API-contract sections moved to the protocol pages (top of this page) and this page became the owner of the service behind the contract. Corrections it made to the old page, still standing:

  • "Cursor ... O(1) on the DB": a keyset page is an index seek plus the page, logarithmic in table size, measured as flat (0.02 to 0.05 ms) from page 1 to a million rows deep; offset is the one that grows linearly.
  • "Return a conflict if the same key arrives with a different payload": the IETF draft says 422 for that case and 409 for a retry while the first is still running; Brandur Leach's 2017 reference code used 409 for both.
  • Idempotency-Key as a standard: it is an expired IETF draft (draft-07, 2025-10-15), though widely implemented.
  • RFC 9457 obsoleted RFC 7807 in July 2023; the major LLM providers still use their own error shapes.
  • "Stripe ... pins each consumer to the version they onboarded with": confirmed; the pin happens on the account's first API request and a Stripe-Version header overrides it per request.
