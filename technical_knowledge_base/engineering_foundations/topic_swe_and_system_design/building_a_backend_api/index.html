An API is a promise: "send me these bytes and I will do this and answer with those bytes". Building one well means making that promise precise, cheap to keep, safe to call twice, and possible to change without breaking whoever already depends on it. The running example is the chat product from Topic: swe-and-system-design: its API creates chats, sends messages to a model, and streams the reply.

HTTP is text with rules. A request is a method, a path, headers and an optional body; a response is a status code, headers and a body. Methods carry promises: GET is safe, PUT and DELETE are idempotent, POST is neither. HTTP
Parse at the edge. Turn untrusted JSON into typed objects (pydantic) before any code touches it; reject the rest with a precise 422. Validation
Nouns in URLs, verbs in methods. POST /v1/chats creates, answers 201 with a Location header. URLs
Errors are part of the contract. One machine-readable shape (RFC 9457 problem details), 4xx for the caller's mistakes, 5xx for yours, and a request ID in every response. Errors
Paginate with cursors. Offset pagination re-reads every skipped row: measured here at 0.03 ms on page 1 and about ms a million rows in, against ms with a cursor. Pagination
Make POST safe to retry. A client that times out cannot tell "never arrived" from "done, reply lost". An idempotency key lets the server answer the retry from a stored result instead of charging twice. Idempotency
Authenticate, then authorise every object. Know who is calling (API key, session or token) and check they own this chat on every request; the most common API vulnerability is skipping the second check. Auth
Tell clients how to back off. 429 with Retry-After; rate limit headers are still a draft. Rate limits
Webhooks are your API in reverse. Sign them, retry them, and expect receivers to see duplicates and disorder. Webhooks
Stream model output with server-sent events. One long HTTP response, one event per chunk of text. Streaming
Never break a caller. Additive changes only within a version; version the rest (a path prefix, a header, or Stripe-style dated versions). Versioning and the Breaking or not? tab.
Write the contract down as data. OpenAPI describes every endpoint so docs, tests and client libraries are generated, not hand-kept. OpenAPI

What this page does not repeat: the request's trip through DNS, TCP and TLS, load balancers, caches and queues are on the parent root (Reading, Step 1 to 3); retries with backoff and jitter, timeouts and circuit breakers belong to Reliability engineering; how to structure the code behind the endpoints (modules, abstractions, library design, review) is Code design.

1. What an API is, and who is on each side

A API (application programming interface) is the set of requests a program promises to understand, and what it promises to do and answer for each. On the web that program is a server: a process that listens on a network port and answers requests. The program that sends requests is the client: the chat app on a phone, a web page, another company's script, or another service of yours. A backend is the server side of a product: the code that holds the data and the rules, which the user never sees.

The word that matters is promise. Once a client is written against your API you cannot see it, update it, or ask it to change: a phone app version can stay installed for years. So everything you expose (field names, status codes, error shapes, which requests are safe to repeat) becomes a contract. Hyrum's law says it more sharply: "With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody" (Hyrum Wright, hyrumslaw.com). Most of this page is about writing that contract on purpose rather than by accident.

The running example, built and run for this page: a chat API with an API key per user, chats, messages that cost 10 credits each (standing in for a model call, which costs real money), and a streamed reply. The same shapes appear in every LLM provider's API.

2. HTTP, byte by byte

HTTP (hypertext transfer protocol) is the language client and server speak. Its meaning (methods, status codes, headers) is defined in RFC 9110, HTTP Semantics (June 2022); how those are written as bytes over one connection in HTTP/1.1 is RFC 9112. HTTP/1.1 is plain text, so you can read it. Below is a real request to the demo service and the real response, exactly as they crossed the socket. Click any line to see what it means.

Read it top to bottom. The first line of a request is the method (what to do), the path (to what), and the protocol version. Then headers, one Name: value per line: metadata such as who is calling (Authorization), what the body is (Content-Type) and how long it is (Content-Length). An empty line ends the headers; the body follows, here JSON. The response mirrors it: a status line with a three-digit code, headers, an empty line, a body. Header names are case-insensitive (uvicorn writes content-type, the client wrote Content-Type; both are right). Lines end with the two bytes carriage return and line feed (\r\n).

HTTP/2 (RFC 9113) and HTTP/3 send the same methods, headers and status codes in a binary framing that lets many requests share one connection; the meaning, and everything on this page, is unchanged. The bytes before HTTP (DNS lookup, TCP and TLS handshakes) are on the root's Step 1 and in Topic: protocols.

Methods and the two promises they make

RFC 9110 gives each method two properties that matter more than the method's name. Safe: "intended only for retrieving information and should not change the state of the server" (§9.2.1). Idempotent: "an identical request can be made one or more times in succession with the same effect as making a single request" (§9.2.2). Idempotent is the property that makes a retry harmless; it comes back in section 10.

3. JSON: the body almost every API speaks

JSON (JavaScript Object Notation, RFC 8259) is text with six kinds of value: objects {"key": value}, arrays [1, 2], strings in double quotes, numbers, true/false, and null. That is all: there is no date type, no distinction between integers and decimals, no comments. Three consequences every API designer meets:

  • Big integers break in browsers. JavaScript stores every number as a 64-bit float, exact only up to 253 − 1 = 9,007,199,254,740,991; RFC 8259 §6 warns about exactly this range. A 64-bit database ID above it silently changes in a JavaScript client. Send IDs as strings (the demo's are "chat_ae8136d1b896", like Stripe's cus_... prefixes, which also tell a human what kind of object an ID names).
  • Dates are strings by convention. Use one format everywhere: either Unix seconds (the demo's created_at) or an RFC 3339 timestamp with a time zone ("2026-10-04T19:06:35Z"). Mixing them is a classic support ticket.
  • Money is never a float. 0.1 + 0.2 is not 0.3 in binary floating point; send integer minor units (cents, or credits) as Stripe does with amount: 2000 for $20.00.

Content-Type: application/json tells the other side the body is JSON. Errors use the more specific application/problem+json (section 7), and streams use text/event-stream (section 14).

4. A minimal service in FastAPI, line by line

A Python web service has two layers. A server such as uvicorn owns the socket: it accepts connections, parses the bytes you saw above, and hands each request to your application through a standard Python interface called ASGI (asynchronous server gateway interface, asgi.readthedocs.io). FastAPI is the application framework: it routes a method and path to your function, parses and validates the input with pydantic, and turns your return value into a response (FastAPI docs). Flask and Django are the older alternatives; FastAPI is the common choice for new Python APIs and for model serving because validation and documentation come from type hints.

The whole demo is one file. To run it yourself: uv run --no-project --with fastapi --with uvicorn uvicorn app:app --port 8765 from src/service/, then curl localhost:8765/v1/health. Here are the parts that matter, with the explanation under each.

FastAPI(...) creates the application object that uvicorn will call. title and version end up in the generated OpenAPI document (section 16).
sqlite3.connect opens a database. SQLite ships with Python, so the demo runs anywhere; a real service uses Postgres (see Topic: databases) with the same tables. isolation_level=None means "I will say BEGIN and COMMIT myself", which the idempotency code needs.
idempotency_keys has primary key(owner, key): the database itself refuses a second row with the same pair. That one line is what makes the idempotency check safe under concurrency (section 10).
class ChatIn(BaseModel) declares the shape of a valid request body. FastAPI reads the body, parses the JSON, and builds a ChatIn or rejects the request with 422 before your function runs.
Field(min_length=1, max_length=200) are constraints. Limits on every string and number are not pedantry: an unbounded content field is how someone sends you 2 GB.
extra="forbid" rejects unknown fields (the capture's "colour": "blue"). Strict input catches client typos (max_token) that would otherwise be silently ignored; the cost is that clients cannot send fields from a newer version of your API. Anthropic's API, for one, rejects an unknown field with "Extra inputs are not permitted" (Claude API errors), which is pydantic's own wording.
Literal["small", "large"] is an enum: any other model name fails validation with a message listing the allowed values.
@app.post("/v1/chats") is a route: this function handles POST requests to that path.
body: ChatIn: because the parameter's type is a pydantic model, FastAPI takes it from the JSON body. authorization: Header() takes it from the Authorization header (FastAPI converts the parameter name, so idempotency_key reads Idempotency-Key).
who(authorization) turns the API key into a user, or nobody (section 11).
JSONResponse(..., 201, headers={"Location": ...}): 201 plus the URL of the new chat, as RFC 9110 §15.3.2 describes for created resources.
How fast is this layer?
Measured on this laptop (Apple M1 Pro, one uvicorn worker, loopback, keep-alive, 2,000 requests after 200 warm-up): GET /v1/health p50 ms, p99 ms; GET /v1/chats/{id} with a database read p50 ms, p99 ms. An LLM reply takes seconds (the root's Step 5), so the framework is almost never the bottleneck of an LLM product; the model, the database and the network are. Measure before rewriting a service in a "faster" framework.

async def or plain def? FastAPI runs plain def routes in a thread pool and async def routes on the event loop. Inside async def, never call something that blocks (a synchronous HTTP client, time.sleep, a slow database driver): it freezes every other request on that worker (FastAPI, async docs). The demo's message route is async because it awaits the (pretend) model call and streams.

5. Validation: parse, don't trust

Every byte from a client is untrusted: it may be malformed, malicious, or from an old app version. The rule pros follow is to turn it into typed objects at the edge, once, and reject anything that does not fit, so that code inside the service never sees a missing field or a string where a number should be. Alexis King's essay calls this "parse, don't validate": the result of checking should be a value whose type proves the check happened (lexi-lambda.github.io, 2019). Pydantic models are exactly that.

The default shape exposes pydantic's internals (loc, ctx, the echoed input, which can leak a secret a user pasted into the wrong field); the rewritten one uses the standard error shape of section 7 with a JSON Pointer (RFC 6901) to each bad field, as RFC 9457's own validation example does. What validation costs, and where it stops
Pydantic v2's validation core is written in Rust (pydantic docs), so per-request cost is small next to network and database time. Validation checks shape (types, lengths, ranges, allowed values). It cannot check meaning that needs the database: whether the chat exists and belongs to the caller, whether the user has credits. Those are business rules, checked in the route, and they answer 404, 403 or 409 rather than 422. Do not pass pydantic models deep into the core of the program either: they belong at the boundary (the code-design half of this question is on Code design).

6. Resources and URLs: designing in nouns

REST (representational state transfer) is the style Roy Fielding described in his 2000 dissertation (Fielding, ch. 5); in everyday use it means: model your API as resources (things with an identity: a chat, a message), give each a URL, and let the HTTP method say what to do with it. Very few APIs follow Fielding's full definition; what pros copy is the convention, as written down in public style guides such as Zalando's RESTful API guidelines and Google's AIPs.

RuleGoodAvoidWhy
Nouns, plural collectionsPOST /v1/chatsPOST /v1/createChatThe method is already the verb; one URL per thing (Zalando #134 "MUST pluralize resource names")
Nest only real ownership, one level/v1/chats/{id}/messages/v1/users/{u}/chats/{c}/messages/{m}/feedbackDeep paths force clients to know every parent ID
Opaque, prefixed, string IDschat_ae8136d1b89617Sequential numbers leak your volume and invite guessing other users' IDs; strings survive JavaScript

Actions that are not CRUD: a sub-resource or a custom methodPOST /v1/chats/{id}/messages/{m}/cancel or Google style POST /v1/messages/{m}:cancelGET /v1/cancel?msg=...A GET must be safe: crawlers, previews and caches send GETs freely (AIP-136)
Return the created object, with 201 and LocationCaptured above200 with {"ok": true}Saves the client a second request, and shows server-set fields (ID, timestamps)

PUT or PATCH? PUT replaces the whole resource with the body you send, so sending it twice is harmless (idempotent). PATCH sends only what changes; with a JSON merge patch (RFC 7396) {"title": "Trips 2027"} changes the title and leaves the rest. Most JSON APIs use PATCH for edits and POST for creation, and simply do not offer PUT.

Why does a chat API with an LLM behind it still use CRUD resources? Because the expensive call (the model) hangs off an ordinary resource: a message is created, stored, billed and listed like any other row. Treating "generate" as a create on messages gives you storage, idempotency and pagination for free.

7. Errors: a contract of their own

A client's code has to decide, for every failure: show the user a message? retry? give up? ask for a new login? It can only decide if errors are machine-readable and stable. Three layers, from coarse to fine:

  1. The status code says whose fault and whether to retry (the table in section 2).
  2. A stable, documented error type says exactly what happened: idempotency-key-reused, rate-limited, context_length_exceeded. Clients switch on it, so it is append-only: never rename or reuse one.
  3. Human text for the developer reading logs, never parsed by code, free to improve.

Plus a request ID: a unique ID for every request, returned in a header and in error bodies, and written into your logs, so that "it failed" in a support ticket becomes one log search. Anthropic returns it as the request-id header and a request_id field (Claude API errors); OpenAI as x-request-id (OpenAI API reference). (The demo omits it to keep the captures short; the Observability page owns request and trace IDs.)

Rules pros follow
  • Say whether to retry. 429 and 503 with Retry-After mean "yes, later"; 400 and 422 mean "no". Stripe goes further with a Stripe-Should-Retry header for cases the status alone cannot settle (Stripe, advanced error handling).
  • Never leak internals. No stack traces, SQL, file paths or library versions in responses; log them under the request ID instead.
  • 404, not 403, for other people's objects. Answering "forbidden" confirms the chat exists.
  • One shape for every error, including the ones your framework, proxy and load balancer generate (a gateway's HTML 502 page breaks a client that expects JSON). Install handlers for validation errors and unhandled exceptions, as the demo does.
  • Errors after a 200 exist. Once a stream has started, the status code is already sent; Anthropic sends an error event inside the stream instead (Claude API errors). See section 14.

8. Pagination: never return everything

A user with 40,000 chats asks for "my chats". Returning all of them is slow, memory-hungry on both sides, and grows forever. So every list endpoint returns a page (say 20 items) plus a way to ask for the next one. There are two ways to say "the next one".

Offset: "skip N rows"

GET /v1/chats?limit=20&offset=40
SELECT ... ORDER BY created_at, id LIMIT 20 OFFSET 40

Easy, lets a UI jump to page 7. But the database cannot jump: it walks the index from the start and throws away the first 40 rows. And if rows are added or removed while the user pages, everything shifts.

Cursor (keyset): "rows after this one"

GET /v1/chats?limit=20&cursor=...
SELECT ... WHERE (created_at, id) > (:t, :id) ORDER BY created_at, id LIMIT 20

The cursor encodes the sort key of the last row the client saw. With an index on (created_at, id) the database seeks straight to it (Postgres, row comparison). No page numbers, but stable and fast at any depth.

Measured: one page of 20 rows, a million rows in Postgres measured

Offset cost grows in proportion to the depth because every skipped row is still read; the cursor's cost stays flat, because the database seeks to the cursor's position in the index. How the demo does it, and how a real API should

The captured first page (limit 2) ended with "next_cursor": "5b3137..."; sending it back returned the next two chats. Two chats were created in the same second, which is why the cursor carries the id as a tie-breaker: sorting by created_at alone would make the order between equal timestamps arbitrary, and a page boundary between them could skip or repeat one.

The rules, from the big style guides
  • Cursors are opaque. Google's AIP-158: page tokens "must be opaque (but URL-safe) strings, and must not be user-parseable", because anything clients can decode they will depend on. The demo's cursor is hex-encoded JSON, which a curious client can decode: fine for a demo, a mistake in production. Base64 an encrypted or signed blob, so you can change what it contains later.
  • An empty or null next cursor is the only end signal. AIP-158: "If the end of the collection has been reached, the next_page_token field must be empty." Do not make clients guess from a short page.
  • Cap limit. The demo answers 422 above 100; AIP-158 prefers to "coerce down to the maximum". Either way, document it.
  • Skip total_count unless you need it: counting a big filtered set is itself a full scan. AIP-158 allows an estimate, clearly documented.
  • Offset still has a place: small admin tables where users want "page 7 of 9". Zalando: "#160 SHOULD prefer cursor-based pagination, avoid offset-based pagination".

9. Filtering and sorting

Lists need narrowing: GET /v1/chats?created_after=2026-09-01&model=large&order=-created_at. Three rules keep this from becoming a performance and security problem:

  • Allow-list fields. Accept only the filters and sort keys you have indexes for. A generic "filter on any column" becomes a full table scan the first time someone filters on an unindexed one, and a way to probe fields you never meant to expose.
  • Bind filters into the cursor. A cursor made under model=large means nothing under model=small. AIP-158 says that if other arguments change between pages, "the API should send an INVALID_ARGUMENT error"; store a hash of the filters inside the cursor and check it.
  • Never build SQL from strings. Pass values as parameters (the demo's ? placeholders) so the database never interprets user text as SQL. That is the whole fix for SQL injection, OWASP's perennial injection risk.

Sorting descending with keyset needs the comparison reversed (< instead of >) and an index in that order (or one Postgres can scan backwards). Full-text search and "find similar" are different tools (a search engine or a vector index; see Topic: databases).

10. Idempotency keys: making POST safe to retry

Networks fail in a way that is impossible to tell apart from the client's side. The user presses Send; the request leaves the phone; after 30 seconds nothing has come back. Either the request never arrived, or it arrived, the model answered, 10 credits were charged, and the response was lost in a tunnel. The client sees the same timeout in both cases. Retrying risks paying twice; not retrying risks losing the message. Brandur Leach's post for Stripe lays out these cases with payments (Stripe blog, 2017-02-22); the root page's Step 4 shows the double charge in one picture. This section is the full mechanism.

GET, PUT and DELETE are idempotent by definition (section 2), so clients and proxies may retry them. POST is not: each POST creates something new. An idempotency key makes one POST idempotent: the client generates a unique value for one logical action (one message the user sent), sends it in an Idempotency-Key header, and sends the same value on every retry of that action. The server stores the key with the result of the first attempt and answers any repeat from the store.

Animation: one message, a lost reply and a retry, with the server's database step by step

The database states follow the demo service's code (src/service/app.py); the 201 replay, the 409 and the 422 at the end of each "after" run are the real captured responses (Wire lab, "msg_retry", "msg_concurrent", "msg_mismatch"). Timings are illustrative.

The server side, as the demo implements it

1. Claim the key atomically. INSERT a row for (user, key) with status started. The primary key means exactly one of two simultaneous attempts can succeed; the other gets an integrity error. Never "SELECT, and if absent INSERT": two requests can both see "absent" between the two statements (a race).
2. If the key exists, compare and replay. Different request hash: the client reused a key for a different action, a bug, so answer 422. Status started: the first attempt is still running, so answer 409 and let the client retry later. Status done: return the stored status code and body, and mark it with Idempotent-Replayed: true as Stripe does.
3. Do the work and record the result in one transaction. The message, the credit charge and the stored response commit together or not at all. If they were separate statements, a crash between them would leave money taken and no record of the response, or a key stuck at started forever.
A bug in this demo, found later: a crash leaves the key claimed forever
The transaction in step 3 protects the end of the request, not the middle. If the handler fails after step 1 claimed the key and before step 3 commits (the model call times out, the process is killed, any unexpected exception), the row stays at started and nothing ever releases it: every retry with that key then gets 409 "still in progress", forever, and the user's message can never be sent with it. The demo frees the key only on the two paths it thought of (unknown chat, streaming). Code design found and measured this while refactoring the same handler. The fix: release the claim on every exit that did not save a response (Code design's step 10 wraps the claim in one context manager, idempotency_claim, that does exactly that), and give each claim an expiry, so a claim left by a process that died without running any cleanup is taken over after, say, a few minutes. Read the bug, the measurement and the refactor in Code design's sections "5. Abstraction economics" and "10. Refactoring safely: tests first, then small steps". Status of the standard (checked 2026-10-04)
The Idempotency-Key header is not an RFC. The IETF HTTPAPI working group's draft reached version 07 on 2025-10-15 and is listed by the datatracker as an expired Internet-Draft (datatracker). It still documents common practice: its implementation list names Stripe, Adyen, PayPal, Square, Twilio, Chargebee, Razorpay, Google Standard Payments and others. Use the header name; do not cite it as a standard.

The harder case: work outside your database

The single transaction above works because everything the request changes lives in one database. Real requests also call things you cannot roll back: the model provider, a card network, an email service. Brandur's design splits the request into atomic phases ("a set of local state mutations that occur in transactions between foreign state mutations") and records a recovery point after each one, so a retry resumes from the last completed step instead of starting over. His warning: "once we make our first foreign state mutation, we're committed one way or another" (brandur.org). For an LLM call, the practical version is: record that the model was called and store its output before charging and answering, and pass your own idempotency key down to any provider that accepts one.

What it costs, and when not to bother
  • One extra write per request and a table that grows (prune after your published window; Stripe's is 24 hours).
  • Stale started rows after a crash need a lock timeout (Brandur's locked_at), after which a retry may take over.
  • Streaming responses cannot be replayed byte for byte cheaply. The demo does not protect streamed messages; production designs store the finished message and let a retry fetch it, or resume the stream from the last event ID (section 14).
  • Not needed where the operation is naturally idempotent: setting a value with PUT, deleting, or creating with a client-chosen ID (PUT /v1/chats/{client_uuid}), which makes the ID itself the key.

Clients: generate the key once per user action (not per attempt), keep it until you get a definite answer, and retry with backoff and jitter. Retry policy and why retries can take a system down are on Reliability engineering; how queues give the same "at least once, so deduplicate" problem a different shape is on Queues, streams and async work.

11. Authentication and authorisation

Two different questions, often confused. Authentication: who is calling? Authorisation: is this caller allowed to do this to this object? A request can pass the first and must still fail the second: Alice is logged in, and she asks for Bob's chat.

API keys: the simplest credential

An API key is a long random secret that identifies a caller, sent on every request, usually as Authorization: Bearer <key> (the bearer scheme of RFC 6750: whoever bears it is let in). It suits server-to-server calls: a customer's backend calling your API, or your backend calling an LLM provider. The captured 401 shows the required challenge header:

  • Store a hash, not the key. The demo keeps sha256(key); a leaked database then leaks no usable keys. Show the key once at creation; let users create several and revoke each.
  • Give keys a recognisable prefix (sk_live_, ghp_) so secret scanners can find them in leaked code; GitHub explains its formats in "Behind GitHub's new authentication token formats" (2021).
  • Never in URLs. Query strings end up in logs, browser history and proxies; use the header.
  • Never in a browser or mobile app. Anything shipped to a user's device is public. The app talks to your backend with the user's session; your backend holds the provider key.

Sessions or tokens: how a logged-in user is remembered

Server session

After login the server stores a session row and sends a random session ID in a cookie (HttpOnly; Secure; SameSite=Lax, so page scripts cannot read it and other sites cannot easily send it). Each request: look up the ID. Revoking is instant (delete the row). Costs a lookup per request, usually in a fast shared store (root, Step 2). The default for your own web app.

Self-contained token (JWT)

After login an authorisation server signs a token listing who the user is and until when. Each service checks the signature locally, with no lookup. The price: a token cannot be revoked before it expires, so access tokens live minutes, and a longer-lived refresh token gets new ones. The default when many services, or other companies, must verify the caller.

OAuth 2 and OpenID Connect, at the level a backend needs

OAuth 2 (RFC 6749, 2012) solves delegation: letting an app act for a user without ever seeing the user's password ("let this calendar app read my Google Calendar"). Four roles: the user, the client (the app), the authorisation server (which logs the user in and issues tokens) and the resource server (the API that accepts the tokens: that is your backend). The two flows that matter today:

  • Authorisation code with PKCE for apps acting for a user: the browser is redirected to the authorisation server, the user logs in and consents, the app receives a one-time code and exchanges it for tokens. PKCE (RFC 7636) binds the code to the app that asked for it, so a stolen code is useless.
  • Client credentials for machine-to-machine calls: a service authenticates as itself and gets a token, no user involved.

The current security rules are RFC 9700, OAuth 2.0 Security Best Current Practice (January 2025): clients "SHOULD NOT use the implicit grant"; the password grant "MUST NOT be used"; "Public clients MUST use PKCE" (and it is recommended for all); redirect URIs are compared by "exact string matching". OAuth 2.1 folds these into one document; it is still an active draft (draft-16, 2026-09-03). OpenID Connect (OIDC Core 1.0) adds identity on top: besides an access token, the client gets an ID token saying who the user is. "Sign in with Google" is OIDC.

As a backend engineer you rarely implement the authorisation server: you use one (Auth0, Okta, Cognito, Keycloak, or Google and Microsoft directly). Your job is the resource server's: on every request, verify the access token and read who and what it allows.

JWTs and how they go wrong

A JWT (JSON Web Token, RFC 7519) is three base64url pieces joined by dots: a header (which algorithm signed it), a payload of claims (issuer iss, subject sub, audience aud, expiry exp), and a signature over the first two. The payload is encoded, not encrypted: anyone holding the token can read it. The "alg: none" row is the oldest JWT attack: the token says it is unsigned, and a library that trusts the header accepts it. RFC 8725, JWT Best Current Practices (February 2020) lists the failures and the rules:

  • Pin the algorithm. "Libraries MUST enable the caller to specify a supported set of algorithms and MUST NOT use any other algorithms." In PyJWT that is jwt.decode(token, key, algorithms=["RS256"], audience="chat-api"); never let the token choose. This also stops algorithm confusion, where a token signed with HS256 using your public RSA key as the "secret" passes a careless check.
  • Check issuer and audience, not just the signature: a valid token for another service must fail here (RFC 8725 §3.8, §3.9). And exp, with a small clock-skew allowance.
  • No weak HMAC secrets. A human-memorable secret can be brute-forced offline from any token. For tokens checked by many services, use asymmetric keys (RS256 or ES256) published by the issuer as a JWKS (a JSON list of public keys), so verifiers never hold a signing secret.
  • Keep access tokens short-lived (minutes) and nothing secret in the payload.

Authorisation: check the object, every time

The first entry in OWASP's API Security Top 10 (2023) is Broken Object Level Authorization: an endpoint takes an ID from the URL and returns or changes that object without checking the caller may touch it. Change chat_ae81... to someone else's ID and you read their chats. The fix is boring and must be everywhere: scope every query by the caller. The demo never looks a chat up by ID alone:

A rate limit caps how many requests (or, for LLM APIs, tokens) one caller may use per unit of time, so one runaway script cannot take capacity from everyone. How the server counts (a token bucket, per key, per model) is on the root's Step 5; this section is the contract with the client.   • Tell clients where they stand before they hit the wall.   • Limit before expensive work, and before the idempotency layer: Stripe notes that "rate limiters run before the API's idempotency layer", so a 429 is not stored against the key and the retry gets a fresh chance (Stripe). The demo does the same.
  • A quota is not a rate limit. "1,000 messages a month" is a billing quota; tell it apart in the error type, because waiting a second will not fix it (Anthropic's tier spend-cap 429 has no retry-after, its docs say, for exactly this reason).

13. Webhooks: your API in reverse

Some events happen later: a long batch job finishes, a payment clears, a moderation review completes. Clients could poll (GET every few seconds), which is wasteful and slow. A webhook turns it around: the client registers a URL, and your server sends an HTTP POST to it when the event happens. Now you are the client, calling code you do not control, over a network that fails. Everything from the previous sections applies with the roles swapped.

The discipline, with the sources that set it
  • Sign every delivery. The receiver must know the POST came from you and was not altered. Compute an HMAC (a keyed hash) with SHA-256 over an ID, a timestamp and the exact body, using a secret shared with that receiver. The Standard Webhooks spec signs msg_id.timestamp.payload and sends webhook-id, webhook-timestamp and webhook-signature: v1,<base64>; Stripe signs timestamp.payload into Stripe-Signature: t=...,v1=... (Stripe webhooks).
  • Reject old timestamps to stop replays of a captured request: Stripe's libraries default to "a default tolerance of 5 minutes", and Stripe warns that a tolerance of 0 "disables the recency check entirely".
  • Verify against the raw bytes, before any JSON parsing: re-serialising changes spacing and key order and the signature fails. Compare signatures in constant time.
  • Retry with backoff, for days. Stripe retries "for up to three days with an exponential back off in live mode"; Standard Webhooks suggests a schedule from immediately, 5 seconds, 5 minutes, 30 minutes, up to 24 hours. After that, mark the endpoint failing and let the user redeliver.
  • Expect duplicates and disorder. Delivery is at-least-once, so receivers must deduplicate: "Use the webhook-id header as an idempotency key". Stripe "doesn't guarantee the delivery of events in the order that they're generated"; receivers should fetch current state rather than trust event order.
  • Receivers: answer 2xx fast, work later. Stripe: "quickly returns a successful status code (2xx) before any complex logic that might cause a timeout"; put the event on a queue (Queues, streams and async work).
  • Thin events carry only the type and IDs; the receiver fetches the object, so it always gets current data and no personal data travels in the webhook. Stripe now offers both "thin" and "snapshot" events.

14. Streaming model output: server-sent events

A model writes its answer a token at a time over several seconds. Waiting for the whole answer before sending anything makes the product feel dead; streaming shows the first words in a fraction of a second. LLM APIs stream with server-sent events (SSE), defined in the WHATWG HTML standard: one ordinary HTTP response with Content-Type: text/event-stream that stays open while the server writes events. Each event is a few field: value lines (event, data, id, retry) ended by a blank line. The shape mirrors the providers': a start event, many small deltas, a stop event with the reason. Anthropic's API, since version 2023-06-01, sends incremental deltas and named events only (Claude API versioning).

What breaks in production
  • Buffering proxies. A proxy or load balancer that buffers responses turns your stream into one late lump. Send Cache-Control: no-cache (the demo does) and turn buffering off for the route (in nginx, proxy_buffering off or the X-Accel-Buffering: no response header; nginx docs).
  • Idle timeouts. Load balancers drop connections that are silent for too long (AWS's Application Load Balancer defaults to 60 s; AWS docs); long reasoning pauses need periodic comment lines (: ping) as keep-alives.
  • Errors after 200. The status is gone once streaming starts; send an error event and make clients handle it.
  • The client went away. When the user closes the tab, stop generating: detect the disconnect (Starlette raises on send; check await request.is_disconnected()) and cancel the model call, or you pay for tokens nobody reads.
  • Resuming. Browsers' EventSource reconnects and sends the last id it saw in a Last-Event-ID header; supporting it means keeping recent events per stream. Most LLM APIs do not resume; clients re-request.

Why not WebSockets? A WebSocket is a two-way connection that leaves HTTP after the handshake; it suits chat between users, games and voice. A model reply is one request and one long answer, which SSE does with plain HTTP, ordinary auth headers and proxies that already understand it. Details of both are in Topic: protocols; how the model produces tokens and why the first one takes longest is on Topic: inference-and-serving.

15. Versioning and backwards compatibility

You will want to change the API. Clients you cannot see depend on the current one. A breaking change is any change after which a correct, existing client stops working or starts doing something different. The goal of versioning is simple to state: never break an existing client, and still be able to improve.

What breaks and what does not

Usually safe (additive)

  • A new endpoint
  • A new optional request field with a default that keeps old behaviour
  • A new field in a response
  • A new error type or event type, if clients were told to expect unknown ones
  • Loosening validation (a longer max length)

Breaking

  • Removing or renaming a field, endpoint or error type
  • Changing a field's type (123 to "123") or format
  • Making an optional field required; tightening validation
  • Changing a default value (AIP-180: "Changing the default value is considered breaking and must not be done")
  • Changing behaviour under the same shape (now charges per token instead of per message)

The additive column only works if clients are tolerant readers: they ignore fields they do not know and handle unknown enum values (Fowler, TolerantReader; Zalando "#108 MUST prepare clients to accept compatible API extensions"). Anthropic says so in its contract: within a version it may "add additional optional inputs", "add additional values to the output" and "add new variants to enum-like output values (for example, streaming event types)" (Claude API versioning). Note the tension with section 5: be strict about what clients send you, and tell clients to be tolerant of what you send them. Test your judgement on 15 changes in the Breaking or not? tab.

Illustrative versions and changes on the chat API; the mechanism is Stripe's, as described by Brandur Leach ("APIs as infrastructure: future-proofing Stripe with versioning", 2017-08-05).

Stripe's design: "The first time a user makes an API request, their account is automatically pinned to the most recent version available." Each breaking change is a small module that converts a response from the new shape to the old one; the core code only ever produces the newest shape, and the chain of modules walks it back to whatever date the caller is pinned to. A request can override with the Stripe-Version header. The post reports close to 100 backwards-incompatible upgrades over six years handled this way without breaking integrations. It is the gold standard and expensive; most teams should start with /v1/ plus strictly additive changes, and add a version header when the first unavoidable break arrives.

For LLM APIs, the model is part of the contract
The same request to a new model gives different answers, lengths and costs. Pin exact model versions (dated snapshot names rather than moving aliases) in production, publish deprecation dates for the models you serve, and gate a model change behind your evals like any other release (Production eval engineering).

Retiring anything: announce it with a date, return a warning while it still works (the Deprecation (RFC 9745) and Sunset (RFC 8594) headers exist for this), watch your logs until no one calls it, then remove it.

17. gRPC or REST, in one section

19. Common mistakes

Each is a real, frequent failure; click to open.

Returning 200 with {"error": ...} in the body
Every proxy, monitor, retry policy and SDK reads the status code. A 200 error looks like success to all of them: dashboards stay green while users fail. Use the status codes; put detail in a problem body.
A GET that changes something
Link previews, crawlers, prefetching browsers and retrying proxies send GETs freely, because RFC 9110 says GET is safe. GET /unsubscribe?id=... gets triggered by an email scanner. State changes go in POST, PUT, PATCH or DELETE.
Retrying POSTs without an idempotency key
Client libraries and service meshes that retry automatically will duplicate side effects (messages, charges, emails). Either send keys, or configure retries only for idempotent methods.
Checking "is the key already there?" with a SELECT, then inserting
Two concurrent retries both see "absent" and both proceed. Use a unique constraint and let the insert fail (section 10).
Looking up objects by ID without the owner
OWASP's API1:2023, Broken Object Level Authorization. Every query that takes an ID from the request also filters by the caller.
Offset pagination on a big, changing table
Slow at depth (measured above: hundreds of milliseconds a million rows in) and wrong under concurrent writes (duplicates and skipped rows). Use a cursor with a unique tie-breaker.
Renaming a field "because the old name was ugly"
It breaks every client that reads it. Add the new field, keep the old one, deprecate it with a date, remove it only in a new version.
Trusting the JWT header's alg
The "alg: none" and algorithm-confusion attacks. Pin algorithms, check issuer, audience and expiry (RFC 8725).
Parsing the webhook JSON before verifying its signature
The signature is over the raw bytes; frameworks that re-serialise the body make every check fail, and teams then "temporarily" turn verification off.
Leaking internals in errors
Stack traces and SQL in a 500 body tell an attacker your stack and schema. Log them with the request ID; return a generic problem.
Floats for money, numbers for 64-bit IDs
Rounding errors in balances; IDs that change in JavaScript above 253. Integer minor units; string IDs.
No limits: unbounded strings, lists, page sizes, request bodies
Every input needs a maximum, or one request can exhaust memory, database time or model tokens.
A streaming endpoint behind a buffering proxy
Works on a laptop, arrives as one lump in production. Disable buffering for the route and test through the real proxy.
