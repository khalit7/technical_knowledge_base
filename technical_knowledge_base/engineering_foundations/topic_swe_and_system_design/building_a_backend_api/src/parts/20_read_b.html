1. The running example: a chat API in one file

The service built and run for this page is a chat API like any LLM provider's, small enough to read in one sitting: an API key per user, chats, messages that cost 10 credits each (standing in for a model call, which costs real money), and a streamed reply. It is about 200 lines of FastAPI in src/service/app.py, with SQLite standing in for Postgres so it runs anywhere. Every response quoted on this page was captured from it on 2026-10-04 (FastAPI 0.142.2, pydantic 2.13.5, uvicorn 0.54.0, Python 3.12.11); the measurements of sections 2, 6, 7, 8 and 9 come from a second tiny app, src/service/exp_app.py, run on 2026-10-24 (FastAPI 0.162.0, Starlette 1.10.0, AnyIO 4.15.1, pydantic-settings 2.16.1).

The framework is not the bottleneck of an LLM product
Measured on an Apple M1 Pro, one uvicorn worker, loopback, keep-alive, 2,000 requests after 200 warm-up: GET /v1/health p50 0.341 ms, p99 0.451 ms; GET /v1/chats/{id} with a database read p50 0.383 ms, p99 0.597 ms. An LLM reply takes seconds (the root's Step 5), so what decides the service's behaviour is how it waits: on the model, on the database, on other requests. That is what the rest of the page is about.

2. One request through the service, stage by stage

A Python web service has two programs in one process. The server, uvicorn, owns the socket: it accepts connections and parses the HTTP bytes. The application, FastAPI (built on Starlette), receives each parsed request through ASGI ({{asgi.readthedocs.io|https://asgi.readthedocs.io/en/latest/}}): a dictionary called the scope, plus two functions, receive for the body and send for the response. Fig. 2 follows one real request to exp_app.py, GET /trace with an API key; the order of the stages was logged by the app itself recorded, and under the figure is what each stage saw or ran.

  1. uvicorn turns bytes into a scope. The server read the request line and headers off the socket and built the ASGI scope shown under the figure: method, path, query string, headers as byte pairs (lower-cased names), and who is on each end. The body is not in it; the app pulls it with receive() only if a route needs it.
  2. Middleware runs, outermost first. The two middlewares log their entry. The one registered second entered first: Starlette builds the stack so that the last middleware added wraps the others. Middleware sees every request, before any routing.
  3. The router picks the function. Starlette matches the method and path against the routes in order; GET /trace matches this one. No match gives 404; a path that exists with another method gives 405.
  4. Dependencies run, for this route only, 3rd. The handler asked for Depends(current_user), so FastAPI ran it first and passed its result in. This is where authentication, a per-request database session and permission checks live; raising here answers 401 or 403 before the handler runs.
  5. Inputs are parsed and validated. Path and query parameters, headers and the JSON body are converted to the declared types; a failure answers 422 without running the handler (section 3). /trace has no body, so only the header was read. Neither the router nor validation writes to the log, so these two stages carry no number.
  6. The handler runs, 4th. Only now does your code run, with typed arguments and a known user. It returned a dict; FastAPI serialises it to JSON.
  7. The response goes back out, innermost first. The middlewares leave in reverse order (added first leaves 5th, added second 6th), so the outermost one can time the whole request and add headers to every response. Then uvicorn writes the bytes.

Recorded 2026-10-24 by src/service/run_experiments.py. Two middlewares were registered, "added first" then "added second"; the log shows the one added second ran outermost (it entered first and left last). The scope is printed as the app received it (client port elided).

Order is a design decision. The middleware registered last wraps everything else, so register the request-ID and timing middleware last (outermost): then they see every request, including the ones an inner stage rejects (no route: 404 or 405; a dependency: 401; validation: 422), and they time the whole trip back out.
