6. Async, threads and worker processes: how many requests can wait at once

A handler spends most of its time waiting: on the database, on the model, on another service. What decides throughput is what the process does with the other requests while one waits. FastAPI gives two ways to write a handler, and uvicorn a third lever:

  • async def runs on the process's single event loop. At each await the loop switches to another request; a call that blocks without await (time.sleep, a synchronous HTTP client, a blocking database driver) stops every request on that worker until it returns ({{FastAPI, async|https://fastapi.tiangolo.com/async/}}).
  • Plain def runs in a worker thread from AnyIO's pool, so blocking is fine; the pool has 40 threads by default (CapacityLimiter(40) in AnyIO 4.15.1, printed by the run below).
  • --workers N starts N processes sharing the port, each with its own loop and pool.

Predict: 50 requests arrive at once, each waiting 500 ms. Written as async def with time.sleep(0.5), how long until the first one is answered? Then pick a style.

Measured: 50 concurrent requests, each waiting 500 ms, written four ways measured

One bar per request, from send to response. Recorded 2026-10-24 by src/service/run_experiments.py on an Apple M1 Pro laptop over loopback (uvicorn 0.54.0, one worker unless stated; httpx client with 50 open connections; the client takes about 45 ms to send all 50). The summary row puts all four on one scale.

What the bars show:

  • Blocking inside async def: 50 x 500 ms run one after another, 25,460 ms in all, and the median request waited 25,421 ms, not about 12.75 s, the median a fair one-at-a-time queue would give (answers at 0.5, 1.0, ... 25 s): each handler's response is written only after the loop gets back to it, by which time every other request's sleep had run. One blocking call in an async handler hurts every request on the worker, not only the slow one.
  • await asyncio.sleep: all 50 wait at the same time; the last answer came at 745 ms (500 ms of waiting plus the overhead of 50 requests on one loop).
  • Plain def: also concurrent, until the pool runs out: 40 answers by about 740 ms, the last 10 at 1,066 to 1,102 ms, a second wave. The 40-thread cap is a hidden concurrency limit; raise it deliberately or prefer async for many slow waits.
  • Four workers divide the blocking damage but do not remove it: 10,241 ms, because the operating system handed the 50 connections to the workers unevenly (20, 14, 9 and 7 requests on this macOS laptop) and the busiest worker sets the time.

So which shape?

Work the handler waits onWrite it asWhy
Network I/O with an async client (model API via httpx.AsyncClient or the provider's async SDK, asyncpg)async def, await everythingThousands of waits share one thread; best for long model calls and streams
A library that only blocks (a synchronous SDK or driver)Plain def, or await anyio.to_thread.run_sync(f) inside asyncThreads absorb the blocking, up to the pool size
CPU work in Python (tokenising, parsing large JSON, resizing images)More worker processes, a process pool, or a queueThreads do not help under the GIL; processes do

How many processes: on a single machine, uvicorn --workers N with roughly one per core; under Kubernetes, FastAPI's deployment guide says you "will probably not want to use workers and instead run a single Uvicorn process per container" ({{FastAPI, server workers|https://fastapi.tiangolo.com/deployment/server-workers/}}), letting the cluster add replicas and the load balancer spread connections. Gunicorn as a process manager now takes the separate uvicorn-worker package (uvicorn 0.54.0's uvicorn.workers module prints a deprecation warning pointing to it). The GIL, threads against processes for CPU work (measured, with the free-threaded build) and how many replicas a load needs are {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}}'s; asyncio itself is {{Python: concurrency, asyncio and the GIL, section 2|n:4055c17b0d0d81bdbee8c37d80b55a0e#s2}}'s.
