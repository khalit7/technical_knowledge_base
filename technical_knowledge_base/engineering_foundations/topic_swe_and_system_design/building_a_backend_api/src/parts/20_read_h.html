15. Versioning and backwards compatibility

You will want to change the API. Clients you cannot see depend on the current one. A breaking change is any change after which a correct, existing client stops working or starts doing something different. The goal of versioning is simple to state: never break an existing client, and still be able to improve.

What breaks and what does not

Usually safe (additive)

  • A new endpoint
  • A new optional request field with a default that keeps old behaviour
  • A new field in a response
  • A new error type or event type, if clients were told to expect unknown ones
  • Loosening validation (a longer max length)

Breaking

  • Removing or renaming a field, endpoint or error type
  • Changing a field's type (123 to "123") or format
  • Making an optional field required; tightening validation
  • Changing a default value ({{AIP-180|https://google.aip.dev/180}}: "Changing the default value is considered breaking and must not be done")
  • Changing behaviour under the same shape (now charges per token instead of per message)

The additive column only works if clients are tolerant readers: they ignore fields they do not know and handle unknown enum values ({{Fowler, TolerantReader|https://martinfowler.com/bliki/TolerantReader.html}}; Zalando "#108 MUST prepare clients to accept compatible API extensions"). Anthropic says so in its contract: within a version it may "add additional optional inputs", "add additional values to the output" and "add new variants to enum-like output values (for example, streaming event types)" ({{Claude API versioning|https://platform.claude.com/docs/en/api/versioning}}). Note the tension with section 5: be strict about what clients send you, and tell clients to be tolerant of what you send them. Test your judgement on 15 changes in the {{Breaking or not?|#t-break}} tab.

Illustrative versions and changes on the chat API; the mechanism is Stripe's, as described by Brandur Leach ({{"APIs as infrastructure: future-proofing Stripe with versioning", 2017-08-05|https://stripe.com/blog/api-versioning}}).

Stripe's design: "The first time a user makes an API request, their account is automatically pinned to the most recent version available." Each breaking change is a small module that converts a response from the new shape to the old one; the core code only ever produces the newest shape, and the chain of modules walks it back to whatever date the caller is pinned to. A request can override with the Stripe-Version header. The post reports close to 100 backwards-incompatible upgrades over six years handled this way without breaking integrations. It is the gold standard and expensive; most teams should start with /v1/ plus strictly additive changes, and add a version header when the first unavoidable break arrives.

For LLM APIs, the model is part of the contract
The same request to a new model gives different answers, lengths and costs. Pin exact model versions (dated snapshot names rather than moving aliases) in production, publish deprecation dates for the models you serve, and gate a model change behind your evals like any other release ({{Production eval engineering|n:3c65c17b0d0d81b39ad9e96193d21adc}}).

Retiring anything: announce it with a date, return a warning while it still works (the {{Deprecation (RFC 9745)|https://www.rfc-editor.org/rfc/rfc9745.html}} and {{Sunset (RFC 8594)|https://www.rfc-editor.org/rfc/rfc8594.html}} headers exist for this), watch your logs until no one calls it, then remove it.

16. OpenAPI: the contract as data

An OpenAPI document is a machine-readable description of every endpoint: paths, methods, parameters, request and response schemas, auth. FastAPI generates one from the code, served at /openapi.json with interactive docs at /docs; the demo's is OpenAPI . Because the contract is data, you get from it: documentation that cannot drift from the code; generated client libraries in many languages ({{OpenAPI Generator|https://openapi-generator.tech/}} is the open-source standard; several API companies, LLM providers among them, generate their official SDKs from an OpenAPI spec with commercial generators); request validation at a gateway; mock servers; and breaking-change checks in CI that diff the new spec against the published one and fail the build if a field disappeared (tools such as oasdiff do this). Two schools: code-first (write FastAPI, export the spec, as here) and spec-first (write the spec, generate server stubs and clients); larger organisations with many teams tend to the second.

Versions: OpenAPI 3.1 aligned its schemas with JSON Schema; {{OpenAPI 3.2.0 (19 September 2025)|https://spec.openapis.org/oas/v3.2.0.html}} adds sequential and streaming media types such as text/event-stream, so SSE endpoints can finally be described.

17. gRPC or REST, in one section

gRPC is Google's remote procedure call framework: you define services and messages in a .proto file (protocol buffers, a compact binary format), and generated code lets a client call a remote method like a local function. It runs over HTTP/2 and supports four call shapes: unary, server streaming, client streaming and bidirectional streaming, with deadlines built in ({{grpc.io, core concepts|https://grpc.io/docs/what-is-grpc/core-concepts/}}).
