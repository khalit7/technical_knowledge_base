6. Resources and URLs: designing in nouns

REST (representational state transfer) is the style Roy Fielding described in his 2000 dissertation ({{Fielding, ch. 5|https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm}}); in everyday use it means: model your API as resources (things with an identity: a chat, a message), give each a URL, and let the HTTP method say what to do with it. Very few APIs follow Fielding's full definition; what pros copy is the convention, as written down in public style guides such as {{Zalando's RESTful API guidelines|https://opensource.zalando.com/restful-api-guidelines/}} and {{Google's AIPs|https://google.aip.dev/121}}.

RuleGoodAvoidWhy
Nouns, plural collectionsPOST /v1/chatsPOST /v1/createChatThe method is already the verb; one URL per thing (Zalando #134 "MUST pluralize resource names")

Opaque, prefixed, string IDschat_ae8136d1b89617Sequential numbers leak your volume and invite guessing other users' IDs; strings survive JavaScript

PUT or PATCH? PUT replaces the whole resource with the body you send, so sending it twice is harmless (idempotent). PATCH sends only what changes; with a JSON merge patch ({{RFC 7396|https://www.rfc-editor.org/rfc/rfc7396.html}}) {"title": "Trips 2027"} changes the title and leaves the rest. Most JSON APIs use PATCH for edits and POST for creation, and simply do not offer PUT.

Why does a chat API with an LLM behind it still use CRUD resources? Because the expensive call (the model) hangs off an ordinary resource: a message is created, stored, billed and listed like any other row. Treating "generate" as a create on messages gives you storage, idempotency and pagination for free.

7. Errors: a contract of their own

A client's code has to decide, for every failure: show the user a message? retry? give up? ask for a new login? It can only decide if errors are machine-readable and stable. Three layers, from coarse to fine:

  1. The status code says whose fault and whether to retry (the table in section 2).
  2. A stable, documented error type says exactly what happened: idempotency-key-reused, rate-limited, context_length_exceeded. Clients switch on it, so it is append-only: never rename or reuse one.
  3. Human text for the developer reading logs, never parsed by code, free to improve.

Plus a request ID: a unique ID for every request, returned in a header and in error bodies, and written into your logs, so that "it failed" in a support ticket becomes one log search. Anthropic returns it as the request-id header and a request_id field ({{Claude API errors|https://platform.claude.com/docs/en/api/errors}}); OpenAI as x-request-id ({{OpenAI API reference|https://developers.openai.com/api/reference/overview}}). (The demo omits it to keep the captures short; the {{Observability|n:3ef5c17b0d0d811e8490c54dd42c2b9b}} page owns request and trace IDs.)

RFC 9457 problem details: the standard shape

{{RFC 9457 (July 2023, obsoletes RFC 7807)|https://www.rfc-editor.org/rfc/rfc9457.html}} defines one JSON error shape with media type application/problem+json and five standard members:

Anything else is an extension member, such as the errors array with pointers in the validation example. Zalando makes it a rule ("#176 MUST support problem JSON"). The big LLM providers predate it and use their own shapes, which carry the same three layers:

Anthropic's types include invalid_request_error (400), authentication_error (401), permission_error (403), not_found_error (404), conflict_error (409), request_too_large (413), rate_limit_error (429), api_error (500), timeout_error (504) and overloaded_error (529, a non-standard code); its docs warn that "the type values will grow over time", so a client must handle types it does not know. OpenAI's errors carry message, type, param and code inside an error object (shape from the old page, not re-fetched).

Rules pros follow
  • Say whether to retry. 429 and 503 with Retry-After mean "yes, later"; 400 and 422 mean "no". Stripe goes further with a Stripe-Should-Retry header for cases the status alone cannot settle ({{Stripe, advanced error handling|https://docs.stripe.com/error-low-level}}).
  • Never leak internals. No stack traces, SQL, file paths or library versions in responses; log them under the request ID instead.
  • 404, not 403, for other people's objects. Answering "forbidden" confirms the chat exists.
  • One shape for every error, including the ones your framework, proxy and load balancer generate (a gateway's HTML 502 page breaks a client that expects JSON). Install handlers for validation errors and unhandled exceptions, as the demo does.
  • Errors after a 200 exist. Once a stream has started, the status code is already sent; Anthropic sends an error event inside the stream instead ({{Claude API errors|https://platform.claude.com/docs/en/api/errors}}). See section 14.
