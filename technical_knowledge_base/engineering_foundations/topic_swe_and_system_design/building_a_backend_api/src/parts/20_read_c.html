3. Validation: parse at the edge, once

Every byte from a client is untrusted: malformed, malicious, or from an app version two years old. The rule is to turn it into typed objects at the edge, once, and reject what does not fit, so code inside never sees a missing field or a string where a number should be. Alexis King calls it "parse, don't validate": the result of checking should be a value whose type proves the check happened ({{lexi-lambda.github.io, 2019|https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/}}). A pydantic model is exactly that, and FastAPI builds it before the handler runs:

  • Limits on every string and number (Field(min_length=1, max_length=200), max_tokens between 1 and 4096): an unbounded content field is how someone sends you 2 GB, or a prompt that costs a fortune.
  • extra="forbid" rejects unknown fields, catching client typos (max_token) that would otherwise be silently ignored; the cost is that clients cannot send fields from a newer version. Anthropic's API rejects an unknown field with "Extra inputs are not permitted" ({{Claude API errors|https://platform.claude.com/docs/en/api/errors}}), which is pydantic's own wording.
  • Literal["small", "large"] is an enum: any other model name fails with a message listing the allowed values.

Before and after, on the same bad body {"title": "", "colour": "blue"} (both captured): FastAPI's default answer, and the same failure after the demo's twelve-line exception handler rewrites it into the problem-details shape that {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}} specifies.

Before: FastAPI default (application/json)
After: problem details with a JSON Pointer per field

Both report every failing field at once, so a form can highlight two mistakes in one round trip. The default exposes pydantic's internals (loc, ctx, and the echoed input, which can leak a secret a user pasted into the wrong field); the rewritten one points at each field with a JSON Pointer ({{RFC 6901|https://www.rfc-editor.org/rfc/rfc6901.html}}), names a query parameter instead ("parameter": "limit" for ?limit=500), and for a body that is not JSON says where it broke ("Invalid JSON at character ...").

Where validation stops
Pydantic v2's validation core is written in Rust ({{pydantic docs|https://docs.pydantic.dev/latest/}}), so it costs little next to network and database time. It checks shape: types, lengths, ranges, allowed values. It cannot check meaning that needs the database: whether the chat exists and belongs to the caller, whether the user has credits. Those are business rules in the handler, and they answer 404, 403 or 409 rather than 422. Keep pydantic models at the boundary rather than deep in the program ({{Code design|n:3ef5c17b0d0d817b99a0ff9701ff30cd}}).

4. Middleware, dependencies and the handler: what goes where

Three places can hold code that runs for a request, and choosing the wrong one is a common source of bugs. The test is scope: does it apply to every request, to some routes, or to one?

Middleware wraps everything; a dependency wraps one route; the handler is the route

Drawn from the recorded order in section 2: the outer ring (registered last) enters first and leaves last. A dependency runs only for routes that declare it, after routing and before the handler; FastAPI resolves it together with the parsed body, so both are ready when the handler starts.

Authorise the object in the query, every time

Knowing who is calling (authentication, {{Auth|n:3c65c17b0d0d817692dcc8ebd59b5c2b}}) is not the same as checking they may touch this chat. The first entry of {{OWASP's API Security Top 10 (2023)|https://owasp.org/API-Security/editions/2023/en/0x11-t10/}} is Broken Object Level Authorization (API1:2023): an endpoint takes an ID from the URL and returns or changes that object without checking the caller owns it; change chat_ae81... to someone else's ID and you read their chats.
