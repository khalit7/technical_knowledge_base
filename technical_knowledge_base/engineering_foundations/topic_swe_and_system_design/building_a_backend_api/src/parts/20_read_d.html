5. The data layer: pools, transactions and round trips

Almost every handler reads or writes the database, and three habits decide whether that scales: borrow connections from a pool, make one unit of work one transaction, and count round trips. The demo uses SQLite in memory; a real service uses Postgres with the same tables ({{Topic: databases|n:3cd5c17b0d0d815d8841ec845f5f3324}}).

Connection pools, and the arithmetic that runs them out

A Postgres connection is a whole operating-system process on the server, and opening one costs a process start plus authentication; {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} measures both (section 8). So each service process keeps a pool: a handful of open connections lent to a request and taken back. Then do the arithmetic nobody does: SQLAlchemy's default pool is 5 connections plus up to 10 overflow, so twenty pods open up to 20 x 15 = 300 connections, a deploy briefly runs old and new pods together (600), and Postgres's max_connections defaults to 100. The usual answer is small per-process pools behind a pooler such as PgBouncer in transaction mode, not a bigger max_connections (sizing with Little's law is on {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}}).

Never hold a connection across the model call

An LLM handler reads the chat, waits seconds for the model, then saves the reply. If it borrows one connection at the start and returns it at the end, the connection sits idle through the whole model call, and the pool needs one connection per request in flight. Little's law (in-flight = arrival rate x time held) makes the cost exact. Predict: at the root's busy hour of 231.5 model calls a second (only the message request calls the model) and a 10 s model call, how many connections does holding need, and how many does borrowing twice for 1 ms each need? The same rule covers transactions: a transaction left open across the model call holds its locks and its snapshot for seconds. Read what you need, commit or release, call the model, then open a short transaction to save the result.

One unit of work, one transaction

A transaction makes several writes commit together or not at all. In the demo's message handler the reply, the credit charge and the stored response (for idempotent retries) must agree, so they are one transaction:

If they were separate statements, a crash between them would leave credits taken and no reply, or a reply nobody paid for. Isolation levels and the anomalies they allow are {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}}'s subject; the handler's job is to draw the boundary in the right place.

A bug in this demo, found later: work outside the transaction left a key claimed forever
The handler claims its idempotency key with an INSERT before the transaction above. If anything fails between the claim and the commit (the model call times out, the process is killed, any unexpected exception), the row stays at started, nothing releases it, and every retry with that key gets 409 "still in progress" forever. The demo releases the claim only on the two paths it thought of (unknown chat, streaming). {{Code design|n:3ef5c17b0d0d817b99a0ff9701ff30cd}} found and measured this while refactoring the same handler. The fix is general handler hygiene: release on every exit that did not save a response (Code design's step 10 wraps the claim in one context manager, idempotency_claim), and give each claim an expiry so a claim left by a process that died without cleanup is taken over after a few minutes. The captures on this page come from the demo as it was and were not rerun.

Count round trips: N+1 queries

The list page of chats with each chat's last message, written the obvious way with an ORM's lazy loading, is one query for 20 chats and then one per chat: 21 round trips. One query with a join returns the same rows. {{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}} measured it on one laptop (psycopg 3.3.6, 0.056 ms for SELECT 1): 1.42 ms against 0.22 ms per page, 6.5 times. Every query passes values as parameters (the demo's ? placeholders), so the database never interprets user text as SQL: that is the whole fix for SQL injection. The fix for N+1 is eager loading (selectinload or joinedload in SQLAlchemy, select_related and prefetch_related in Django) or writing the join; the way to notice is a trace that shows how many queries each request made ({{Observability|n:3ef5c17b0d0d811e8490c54dd42c2b9b}}). Paging itself is one query per page with a cursor (the demo's where (created_at,id) > (?,?); the design is {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}}'s).

An async handler needs an async driver
The demo's message handler is async def but calls sqlite3, a blocking driver. With an in-memory SQLite that blocks for microseconds; with a network database it blocks the whole event loop for every query (section 6 measures what that does). Use an async driver (asyncpg, psycopg 3's async connection, SQLAlchemy's asyncio extension) in async def handlers, or keep the handler a plain def.
