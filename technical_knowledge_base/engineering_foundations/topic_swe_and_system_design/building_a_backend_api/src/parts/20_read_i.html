19. Common mistakes

Each is a real, frequent failure; click to open.

Returning 200 with {"error": ...} in the body
Every proxy, monitor, retry policy and SDK reads the status code. A 200 error looks like success to all of them: dashboards stay green while users fail. Use the status codes; put detail in a problem body.
A GET that changes something
Link previews, crawlers, prefetching browsers and retrying proxies send GETs freely, because RFC 9110 says GET is safe. GET /unsubscribe?id=... gets triggered by an email scanner. State changes go in POST, PUT, PATCH or DELETE.
Retrying POSTs without an idempotency key
Client libraries and service meshes that retry automatically will duplicate side effects (messages, charges, emails). Either send keys, or configure retries only for idempotent methods.
Checking "is the key already there?" with a SELECT, then inserting
Two concurrent retries both see "absent" and both proceed. Use a unique constraint and let the insert fail (section 10).
Looking up objects by ID without the owner
OWASP's API1:2023, Broken Object Level Authorization. Every query that takes an ID from the request also filters by the caller.
Offset pagination on a big, changing table
Slow at depth (measured above: hundreds of milliseconds a million rows in) and wrong under concurrent writes (duplicates and skipped rows). Use a cursor with a unique tie-breaker.
Renaming a field "because the old name was ugly"
It breaks every client that reads it. Add the new field, keep the old one, deprecate it with a date, remove it only in a new version.
Trusting the JWT header's alg
The "alg: none" and algorithm-confusion attacks. Pin algorithms, check issuer, audience and expiry (RFC 8725).
Parsing the webhook JSON before verifying its signature
The signature is over the raw bytes; frameworks that re-serialise the body make every check fail, and teams then "temporarily" turn verification off.
Leaking internals in errors
Stack traces and SQL in a 500 body tell an attacker your stack and schema. Log them with the request ID; return a generic problem.
Floats for money, numbers for 64-bit IDs
Rounding errors in balances; IDs that change in JavaScript above 253. Integer minor units; string IDs.
No limits: unbounded strings, lists, page sizes, request bodies
Every input needs a maximum, or one request can exhaust memory, database time or model tokens.
A streaming endpoint behind a buffering proxy
Works on a laptop, arrives as one lump in production. Disable buffering for the route and test through the real proxy.

20. What changed from the old page

This page replaces the API half of the old "API and Code Design" page (11 min read, fetched 2026-09-22 and saved in src/live.md); its code-design half (library design, code review, abstractions) now belongs to {{Code design|n:3ef5c17b0d0d817b99a0ff9701ff30cd}}. Every old claim was checked; src/coverage.json maps each one. The corrections:

Corrected or made precise
  • "Cursor ... O(1) on the DB". Not quite: a keyset page is an index seek plus the page, logarithmic in table size, and measured here as flat (0.02 to 0.05 ms) from page 1 to a million rows deep. Offset is the one that grows linearly.
  • "Return a conflict if the same key arrives with a different payload". The IETF draft says 422 for that case and reserves 409 for a retry while the first request is still running; Stripe documents 409 for the concurrent case. Brandur's 2017 reference code used 409 for both. The demo follows the draft.
  • "RFC 9457 (application/problem+json) is the standards-track shape". Right, and worth adding: it obsoleted RFC 7807 in July 2023, and the major LLM providers still use their own shapes.
  • Idempotency-Key as a standard. The old page implied a standard header; it is an expired IETF draft (draft-07, 2025-10-15), though widely implemented.
  • "Stripe ... pins each consumer to the version they onboarded with". Confirmed, with the detail that the pin happens on the account's first API request and a Stripe-Version header overrides it per request.

Glossary

API: the requests a program promises to understand, and its answers.
Contract: everything about an API that clients can observe and therefore depend on.
HTTP: the request and response protocol of the web (RFC 9110).
Method: the verb of a request: GET, POST, PUT, PATCH, DELETE.
Header: a Name: value line of metadata on a request or response.
Status code: the three-digit result; 4xx client's fault, 5xx server's.
Safe method: does not change server state (GET).
Idempotent: repeating it has the same effect as doing it once.
JSON: the text data format of most API bodies (RFC 8259).
ASGI server: the process (uvicorn) that owns the socket and calls your Python app.
Route: the function that handles one method and path.
Resource: a thing with an identity and a URL (a chat).
REST: the convention of resources in URLs and verbs in methods.
Request ID: a unique ID per request, in responses and logs.
Cursor: an opaque token meaning "continue after this row".
Idempotency key: a client-chosen ID that makes retries of one action safe.
Authentication: who is calling.
Authorisation: may they do this to this object.
API key: a long random secret identifying a caller.
OAuth 2: delegated access: an app acts for a user via tokens.
OpenID Connect: identity on top of OAuth 2 (the ID token).
JWT: a signed, readable token of claims.
Rate limit: a cap on requests or tokens per unit of time.
Webhook: an HTTP call your server makes to a client's URL when something happens.
Server-sent events: one long HTTP response carrying a stream of events.
Breaking change: a change after which an existing correct client fails.
OpenAPI: a machine-readable description of an HTTP API.
gRPC: RPC over HTTP/2 with protocol buffers.
