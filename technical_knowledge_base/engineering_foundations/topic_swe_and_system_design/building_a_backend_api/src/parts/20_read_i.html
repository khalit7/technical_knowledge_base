Depth: mistakes, JSON rules and provenance

Common mistakes that the sections above do not already show
  • A GET that changes something. Link previews, crawlers and retrying proxies send GETs freely because RFC 9110 says GET is safe; GET /unsubscribe?id=... gets triggered by an email scanner.
  • Returning 200 with {"error": ...}. Every proxy, monitor, retry policy and SDK reads the status code: dashboards stay green while users fail.
  • Leaking internals in a 500. Stack traces and SQL tell an attacker your stack and schema; log them under the request ID and return a generic problem.
  • Checking "is the key already there?" with a SELECT, then inserting. Two concurrent retries both see "absent"; let a unique constraint (the demo's primary key(owner, key)) make the second insert fail.
  • A streaming endpoint behind a buffering proxy works on a laptop and arrives as one lump in production; test through the real proxy.
  • Renaming a field "because the old name was ugly" breaks every client that reads it: add the new field, keep the old one, deprecate it with a date, remove it only in a new version.
  • No limits on strings, lists, page sizes or bodies: one request can then exhaust memory, database time or model tokens.
JSON rules every handler's output must respect
  • Big integers break in browsers. JavaScript numbers are 64-bit floats, exact only up to 253 − 1 = 9,007,199,254,740,991 ({{RFC 8259|https://www.rfc-editor.org/rfc/rfc8259.html}} §6 warns about this range). Send IDs as strings with a type prefix, like the demo's "chat_ae8136d1b896" and Stripe's cus_....
  • Dates are strings by convention: one format everywhere, Unix seconds (the demo's created_at) or {{RFC 3339|https://www.rfc-editor.org/rfc/rfc3339.html}} with a time zone ("2026-10-04T19:06:35Z").
  • Money is never a float: 0.1 + 0.2 is not 0.3 in binary floating point; send integer minor units (cents, credits), as Stripe does with amount: 2000 for $20.00.
Contract details kept here until Service APIs and HTTP carry them

These came from this page's old contract sections and are not yet on the owner pages; they move there at the next pass.

  • Hyrum's law: "With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody" ({{Hyrum Wright, hyrumslaw.com|https://www.hyrumslaw.com/}}). A phone app version can stay installed for years, so everything observable is contract.
  • Reason phrases are decoration. The demo's captured 422s say 422 Unprocessable Entity (uvicorn takes the phrase from Python's http.HTTPStatus, the older {{RFC 4918|https://www.rfc-editor.org/rfc/rfc4918.html#section-11.2}} name), while RFC 9110 renamed it "Unprocessable Content"; clients must read the number, and HTTP/2 does not even send the phrase.
  • JSON has no date type, no integer against decimal distinction and no comments (RFC 8259); hence the rules in the JSON block above.
  • PUT or PATCH. PUT replaces the whole resource, so sending it twice is harmless; PATCH sends only what changes, and with a JSON merge patch ({{RFC 7396|https://www.rfc-editor.org/rfc/rfc7396.html}}) {"title": "Trips 2027"} changes the title and leaves the rest. Most JSON APIs use PATCH for edits and POST for creation, and do not offer PUT.
  • An LLM call is still CRUD underneath: the expensive call hangs off an ordinary resource (a message is created, stored, billed and listed like any other row), so treating "generate" as a create on messages gives storage, idempotency and pagination for free.
  • Problem details' default type is about:blank: "no additional semantics beyond that of the HTTP status code" (RFC 9457).
  • Stripe-Should-Retry: Stripe sends this header for failures the status code alone cannot settle ({{Stripe, advanced error handling|https://docs.stripe.com/error-low-level}}).
  • The end of a list: AIP-158, "If the end of the collection has been reached, the next_page_token field must be empty"; do not make clients guess from a short page. The demo's cursor is hex-encoded JSON, which a curious client can decode: fine for a demo, a mistake in production.
  • Keyset pagination's sources and corners: Markus Winand's {{"We need tool support for keyset pagination"|https://use-the-index-luke.com/no-offset}} makes the case with Postgres and MySQL plans; sorting descending needs the comparison reversed (< instead of >) and an index in that order, or one Postgres can scan backwards.
  • Allow-list filters and sort keys: accept only those you have indexes for; a generic "filter on any column" becomes a full table scan the first time someone filters on an unindexed one, and a way to probe fields you never meant to expose.
  • Bind filters into the cursor: a cursor made under model=large means nothing under model=small; store a hash of the filters inside the cursor and reject a mismatch.
  • Work outside your database: Brandur Leach's design splits a request into atomic phases ("a set of local state mutations that occur in transactions between foreign state mutations") with a recovery point after each, because "once we make our first foreign state mutation, we're committed one way or another" ({{brandur.org|https://brandur.org/idempotency-keys}}). For an LLM call: record that the model was called and store its output before charging and answering, and pass your own idempotency key to any provider that accepts one.
  • OpenAPI 3.2.0 (19 September 2025) adds sequential and streaming media types such as text/event-stream, so SSE endpoints can be described ({{spec|https://spec.openapis.org/oas/v3.2.0.html}}); 3.1 aligned its schemas with JSON Schema.

Corrections it made to the old page, still standing:

  • "Cursor ... O(1) on the DB": a keyset page is an index seek plus the page, logarithmic in table size, measured as flat (0.02 to 0.05 ms) from page 1 to a million rows deep; offset is the one that grows linearly.
  • "Return a conflict if the same key arrives with a different payload": the IETF draft says 422 for that case and 409 for a retry while the first is still running; Brandur Leach's 2017 reference code used 409 for both.
  • Idempotency-Key as a standard: it is an expired IETF draft (draft-07, 2025-10-15), though widely implemented.
  • RFC 9457 obsoleted RFC 7807 in July 2023; the major LLM providers still use their own error shapes.
  • "Stripe ... pins each consumer to the version they onboarded with": confirmed; the pin happens on the account's first API request and a Stripe-Version header overrides it per request.
