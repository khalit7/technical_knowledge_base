7. Configuration and secrets: read once, typed, at startup

Configuration is, in the Twelve-Factor App's words, "everything that is likely to vary between deploys (staging, production, developer environments, etc)": the database URL, the model name, the provider key, timeouts. Its rule: "The twelve-factor app stores config in environment variables", and its test is "whether the codebase could be made open source at any moment, without compromising any credentials" ({{12factor.net/config|https://12factor.net/config}}). In Python the usual tool is pydantic-settings: a class whose fields are read from the environment, typed and validated like a request body, once, when the process starts.

Measured: when the same setting comes from five places, the one nearest the code wins

Top row: highest priority; each row is the source added at that step, numbered in the order added, and the value then read. Recorded with pydantic-settings 2.16.1: a Settings class with env_prefix="CHAT_", a .env file and a secrets_dir, each source added in turn for model_name. The value read went small, from-secrets-dir, from-dotenv, from-environment, from-init: an argument in code beats an environment variable, which beats the .env file, which beats a file in the secrets directory, which beats the class default.

  • Fail fast. A required setting that is missing stops the process at startup, not on the first request that needs it. The recorded error: 1 validation error for Required / database_url / Field required [type=missing, ...]. A crash loop at deploy time is visible; a service that starts and fails one request in a hundred is not.
  • Secrets are typed as secrets. A SecretStr field prints as SecretStr('**********'), so the whole settings object can be logged at startup without leaking the key; the value comes out only through provider_key.get_secret_value() at the point of use.
  • Where secrets come from in production: a secret manager (Vault, AWS Secrets Manager, GCP Secret Manager) injected as environment variables or mounted as files; mounted files are what secrets_dir reads (a Kubernetes Secret volume, Docker's /run/secrets). Never in the repository, the image, a URL or a log line. Rotating a secret then means a restart or a reload hook, so design for both keys being valid for a while.
  • Read once, pass down. Build the settings object in the lifespan hook (section 9) or a cached dependency, and pass it to what needs it; code that reads os.environ in the middle of a handler cannot be tested or audited.

Feature flags and gradual config rollouts are configuration that changes while the process runs; rolling them out like code is on {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}. The code-design view of settings objects is on {{Code design|n:3ef5c17b0d0d817b99a0ff9701ff30cd}}.

8. Background work: answer first, then do the rest

Some work does not need to finish before the user gets an answer: send a notification, meter the tokens, generate a chat title, index the message for search. Doing it inline makes every user wait for it. There are three places to put it, and the difference is what happens when the process dies.

Measured: the same 500 ms of follow-up work, inline against BackgroundTasks; and where a queue would put it

Medians of seven requests to exp_app.py (2026-10-24): inline, the client waited 506.3 ms; with BackgroundTasks the response came in 4.2 ms and the work finished 501.8 ms after it, in the same process. FastAPI's own guidance draws the same line: background tasks run "after returning a response", and for "heavy background computation" that does not need the same process "you might benefit from using other bigger tools like Celery", which need "a message/job queue manager, like RabbitMQ or Redis" but run "in multiple processes, and especially, in multiple servers" ({{FastAPI, background tasks|https://fastapi.tiangolo.com/tutorial/background-tasks/}}). Section 9 shows the in-process kind being waited for on a graceful shutdown and cancelled on a forced one.
