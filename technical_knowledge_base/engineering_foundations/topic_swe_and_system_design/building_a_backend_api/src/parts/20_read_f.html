11. Authentication and authorisation

Two different questions, often confused. Authentication: who is calling? Authorisation: is this caller allowed to do this to this object? A request can pass the first and must still fail the second: Alice is logged in, and she asks for Bob's chat.

API keys: the simplest credential

An API key is a long random secret that identifies a caller, sent on every request, usually as Authorization: Bearer <key> (the bearer scheme of {{RFC 6750|https://www.rfc-editor.org/rfc/rfc6750.html}}: whoever bears it is let in). It suits server-to-server calls: a customer's backend calling your API, or your backend calling an LLM provider. The captured 401 shows the required challenge header:

  • Store a hash, not the key. The demo keeps sha256(key); a leaked database then leaks no usable keys. Show the key once at creation; let users create several and revoke each.
  • Give keys a recognisable prefix (sk_live_, ghp_) so secret scanners can find them in leaked code; GitHub explains its formats in {{"Behind GitHub's new authentication token formats" (2021)|https://github.blog/engineering/platform-security/behind-githubs-new-authentication-token-formats/}}.
  • Never in URLs. Query strings end up in logs, browser history and proxies; use the header.
  • Never in a browser or mobile app. Anything shipped to a user's device is public. The app talks to your backend with the user's session; your backend holds the provider key.

Sessions or tokens: how a logged-in user is remembered

Server session

After login the server stores a session row and sends a random session ID in a cookie (HttpOnly; Secure; SameSite=Lax, so page scripts cannot read it and other sites cannot easily send it). Each request: look up the ID. Revoking is instant (delete the row). Costs a lookup per request, usually in a fast shared store (root, Step 2). The default for your own web app.

Self-contained token (JWT)

After login an authorisation server signs a token listing who the user is and until when. Each service checks the signature locally, with no lookup. The price: a token cannot be revoked before it expires, so access tokens live minutes, and a longer-lived refresh token gets new ones. The default when many services, or other companies, must verify the caller.

OAuth 2 and OpenID Connect, at the level a backend needs

OAuth 2 ({{RFC 6749, 2012|https://www.rfc-editor.org/rfc/rfc6749.html}}) solves delegation: letting an app act for a user without ever seeing the user's password ("let this calendar app read my Google Calendar"). Four roles: the user, the client (the app), the authorisation server (which logs the user in and issues tokens) and the resource server (the API that accepts the tokens: that is your backend). The two flows that matter today:

  • Authorisation code with PKCE for apps acting for a user: the browser is redirected to the authorisation server, the user logs in and consents, the app receives a one-time code and exchanges it for tokens. PKCE ({{RFC 7636|https://www.rfc-editor.org/rfc/rfc7636.html}}) binds the code to the app that asked for it, so a stolen code is useless.
  • Client credentials for machine-to-machine calls: a service authenticates as itself and gets a token, no user involved.

The current security rules are {{RFC 9700, OAuth 2.0 Security Best Current Practice (January 2025)|https://www.rfc-editor.org/rfc/rfc9700.html}}: clients "SHOULD NOT use the implicit grant"; the password grant "MUST NOT be used"; "Public clients MUST use PKCE" (and it is recommended for all); redirect URIs are compared by "exact string matching". {{OAuth 2.1|https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/}} folds these into one document; it is still an active draft (draft-16, 2026-09-03). OpenID Connect ({{OIDC Core 1.0|https://openid.net/specs/openid-connect-core-1_0.html}}) adds identity on top: besides an access token, the client gets an ID token saying who the user is. "Sign in with Google" is OIDC.

As a backend engineer you rarely implement the authorisation server: you use one (Auth0, Okta, Cognito, Keycloak, or Google and Microsoft directly). Your job is the resource server's: on every request, verify the access token and read who and what it allows.

JWTs and how they go wrong

A JWT (JSON Web Token, {{RFC 7519|https://www.rfc-editor.org/rfc/rfc7519.html}}) is three base64url pieces joined by dots: a header (which algorithm signed it), a payload of claims (issuer iss, subject sub, audience aud, expiry exp), and a signature over the first two. The payload is encoded, not encrypted: anyone holding the token can read it. The "alg: none" row is the oldest JWT attack: the token says it is unsigned, and a library that trusts the header accepts it. {{RFC 8725, JWT Best Current Practices (February 2020)|https://www.rfc-editor.org/rfc/rfc8725.html}} lists the failures and the rules:

  • Pin the algorithm. "Libraries MUST enable the caller to specify a supported set of algorithms and MUST NOT use any other algorithms." In PyJWT that is jwt.decode(token, key, algorithms=["RS256"], audience="chat-api"); never let the token choose. This also stops algorithm confusion, where a token signed with HS256 using your public RSA key as the "secret" passes a careless check.
  • Check issuer and audience, not just the signature: a valid token for another service must fail here (RFC 8725 §3.8, §3.9). And exp, with a small clock-skew allowance.
  • No weak HMAC secrets. A human-memorable secret can be brute-forced offline from any token. For tokens checked by many services, use asymmetric keys (RS256 or ES256) published by the issuer as a JWKS (a JSON list of public keys), so verifiers never hold a signing secret.
  • Keep access tokens short-lived (minutes) and nothing secret in the payload.

Authorisation: check the object, every time

The first entry in {{OWASP's API Security Top 10 (2023)|https://owasp.org/API-Security/editions/2023/en/0x11-t10/}} is Broken Object Level Authorization: an endpoint takes an ID from the URL and returns or changes that object without checking the caller may touch it. Start with ownership checks in every query and a test per endpoint that tries another user's ID; add a policy layer when roles appear.
