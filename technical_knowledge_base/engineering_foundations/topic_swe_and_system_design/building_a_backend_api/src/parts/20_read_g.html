12. Rate limiting, as the client sees it

A rate limit caps how many requests (or, for LLM APIs, tokens) one caller may use per unit of time, so one runaway script cannot take capacity from everyone. How the server counts (a token bucket, per key, per model) is on the root's Step 5; this section is the contract with the client.   • 429 Too Many Requests ({{RFC 6585 §4|https://www.rfc-editor.org/rfc/rfc6585.html#section-4}}) with Retry-After, either seconds or an HTTP date ({{RFC 9110 §10.2.3|https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after}}). A well-behaved client waits that long; Anthropic's SDK honours it automatically when retrying ({{Claude API errors|https://platform.claude.com/docs/en/api/errors}}).
  • Tell clients where they stand before they hit the wall. The IETF's {{RateLimit header fields draft|https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/}} (draft-11, 2026-05-23, still an active draft, not an RFC) defines RateLimit-Policy: "burst";q=5;w=5 (quota 5 per 5-second window) and RateLimit: "burst";r=4;t=0 (4 remaining, resets in 0 s), which the demo sends. Most providers still use their own X- headers: OpenAI sends x-ratelimit-remaining-requests, x-ratelimit-remaining-tokens and their reset times ({{OpenAI API reference|https://developers.openai.com/api/reference/overview}}).
  • Limit before expensive work, and before the idempotency layer: Stripe notes that "rate limiters run before the API's idempotency layer", so a 429 is not stored against the key and the retry gets a fresh chance ({{Stripe|https://docs.stripe.com/error-low-level}}). The demo does the same.
  • A quota is not a rate limit. "1,000 messages a month" is a billing quota; tell it apart in the error type, because waiting a second will not fix it (Anthropic's tier spend-cap 429 has no retry-after, its docs say, for exactly this reason).

13. Webhooks: your API in reverse

Some events happen later: a long batch job finishes, a payment clears, a moderation review completes. Clients could poll (GET every few seconds), which is wasteful and slow. A webhook turns it around: the client registers a URL, and your server sends an HTTP POST to it when the event happens. Now you are the client, calling code you do not control, over a network that fails. Everything from the previous sections applies with the roles swapped.

The discipline, with the sources that set it
  • Sign every delivery. The receiver must know the POST came from you and was not altered. Compute an HMAC (a keyed hash) with SHA-256 over an ID, a timestamp and the exact body, using a secret shared with that receiver. The {{Standard Webhooks spec|https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md}} signs msg_id.timestamp.payload and sends webhook-id, webhook-timestamp and webhook-signature: v1,<base64>; Stripe signs timestamp.payload into Stripe-Signature: t=...,v1=... ({{Stripe webhooks|https://docs.stripe.com/webhooks}}).
  • Reject old timestamps to stop replays of a captured request: Stripe's libraries default to "a default tolerance of 5 minutes", and Stripe warns that a tolerance of 0 "disables the recency check entirely".
  • Verify against the raw bytes, before any JSON parsing: re-serialising changes spacing and key order and the signature fails. Compare signatures in constant time.
  • Retry with backoff, for days. Stripe retries "for up to three days with an exponential back off in live mode"; Standard Webhooks suggests a schedule from immediately, 5 seconds, 5 minutes, 30 minutes, up to 24 hours. After that, mark the endpoint failing and let the user redeliver.
  • Expect duplicates and disorder. Delivery is at-least-once, so receivers must deduplicate: "Use the webhook-id header as an idempotency key". Stripe "doesn't guarantee the delivery of events in the order that they're generated"; receivers should fetch current state rather than trust event order.
  • Receivers: answer 2xx fast, work later. Stripe: "quickly returns a successful status code (2xx) before any complex logic that might cause a timeout"; put the event on a queue ({{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}).
  • Thin events carry only the type and IDs; the receiver fetches the object, so it always gets current data and no personal data travels in the webhook. Stripe now offers both "thin" and "snapshot" events.

14. Streaming model output: server-sent events

A model writes its answer a token at a time over several seconds. Waiting for the whole answer before sending anything makes the product feel dead; streaming shows the first words in a fraction of a second. LLM APIs stream with server-sent events (SSE), defined in the {{WHATWG HTML standard|https://html.spec.whatwg.org/multipage/server-sent-events.html}}: one ordinary HTTP response with Content-Type: text/event-stream that stays open while the server writes events. Each event is a few field: value lines (event, data, id, retry) ended by a blank line. The shape mirrors the providers': a start event, many small deltas, a stop event with the reason. Anthropic's API, since version 2023-06-01, sends incremental deltas and named events only ({{Claude API versioning|https://platform.claude.com/docs/en/api/versioning}}).

What breaks in production
  • Buffering proxies. A proxy or load balancer that buffers responses turns your stream into one late lump. Send Cache-Control: no-cache (the demo does) and turn buffering off for the route (in nginx, proxy_buffering off or the X-Accel-Buffering: no response header; {{nginx docs|https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_buffering}}).
  • Idle timeouts. Load balancers drop connections that are silent for too long (AWS's Application Load Balancer defaults to 60 s; {{AWS docs|https://docs.aws.amazon.com/elasticloadbalancing/latest/application/application-load-balancers.html#load-balancer-attributes}}); long reasoning pauses need periodic comment lines (: ping) as keep-alives.
  • Errors after 200. The status is gone once streaming starts; send an error event and make clients handle it.
  • The client went away. When the user closes the tab, stop generating: detect the disconnect (Starlette raises on send; check await request.is_disconnected()) and cancel the model call, or you pay for tokens nobody reads.
  • Resuming. Browsers' EventSource reconnects and sends the last id it saw in a Last-Event-ID header; supporting it means keeping recent events per stream. Most LLM APIs do not resume; clients re-request.

Why not WebSockets? A WebSocket is a two-way connection that leaves HTTP after the handshake; it suits chat between users, games and voice. A model reply is one request and one long answer, which SSE does with plain HTTP, ordinary auth headers and proxies that already understand it.
