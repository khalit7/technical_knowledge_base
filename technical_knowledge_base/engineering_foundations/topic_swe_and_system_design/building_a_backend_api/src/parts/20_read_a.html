An API is a promise: "send me these bytes and I will do this and answer with those bytes". Building one well means making that promise precise, cheap to keep, safe to call twice, and possible to change without breaking whoever already depends on it. The running example is the chat product from {{Topic: swe-and-system-design|n:3c65c17b0d0d81048ae0dd14ac399b4d}}: its API creates chats, sends messages to a model, and streams the reply.

HTTP is text with rules. A request is a method, a path, headers and an optional body; a response is a status code, headers and a body. Methods carry promises: GET is safe, PUT and DELETE are idempotent, POST is neither. HTTP
Parse at the edge. Turn untrusted JSON into typed objects (pydantic) before any code touches it; reject the rest with a precise 422. Validation
Nouns in URLs, verbs in methods. POST /v1/chats creates, answers 201 with a Location header. URLs
Errors are part of the contract. One machine-readable shape (RFC 9457 problem details), 4xx for the caller's mistakes, 5xx for yours, and a request ID in every response. Errors
Paginate with cursors. Offset pagination re-reads every skipped row: measured here at 0.03 ms on page 1 and about ms a million rows in, against ms with a cursor. Pagination
Make POST safe to retry. A client that times out cannot tell "never arrived" from "done, reply lost". An idempotency key lets the server answer the retry from a stored result instead of charging twice. Idempotency
Authenticate, then authorise every object. Know who is calling (API key, session or token) and check they own this chat on every request; the most common API vulnerability is skipping the second check. Auth
Tell clients how to back off. 429 with Retry-After; rate limit headers are still a draft. Rate limits
Webhooks are your API in reverse. Sign them, retry them, and expect receivers to see duplicates and disorder. Webhooks
Stream model output with server-sent events. One long HTTP response, one event per chunk of text. Streaming
Never break a caller. Additive changes only within a version; version the rest (a path prefix, a header, or Stripe-style dated versions). Versioning and the {{Breaking or not?|#t-break}} tab.
Write the contract down as data. OpenAPI describes every endpoint so docs, tests and client libraries are generated, not hand-kept. OpenAPI

What this page does not repeat: the request's trip through DNS, TCP and TLS, load balancers, caches and queues are on the parent root (Reading, Step 1 to 3); retries with backoff and jitter, timeouts and circuit breakers belong to {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}; how to structure the code behind the endpoints (modules, abstractions, library design, review) is {{Code design|n:3ef5c17b0d0d817b99a0ff9701ff30cd}}.

1. What an API is, and who is on each side

A API (application programming interface) is the set of requests a program promises to understand, and what it promises to do and answer for each. On the web that program is a server: a process that listens on a network port and answers requests. The program that sends requests is the client: the chat app on a phone, a web page, another company's script, or another service of yours. A backend is the server side of a product: the code that holds the data and the rules, which the user never sees.

The word that matters is promise. Once a client is written against your API you cannot see it, update it, or ask it to change: a phone app version can stay installed for years. So everything you expose (field names, status codes, error shapes, which requests are safe to repeat) becomes a contract. Hyrum's law says it more sharply: "With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody" ({{Hyrum Wright, hyrumslaw.com|https://www.hyrumslaw.com/}}). Most of this page is about writing that contract on purpose rather than by accident.

The running example, built and run for this page: a chat API with an API key per user, chats, messages that cost 10 credits each (standing in for a model call, which costs real money), and a streamed reply. The same shapes appear in every LLM provider's API.

2. HTTP, byte by byte

HTTP (hypertext transfer protocol) is the language client and server speak. Its meaning (methods, status codes, headers) is defined in {{RFC 9110, HTTP Semantics (June 2022)|https://www.rfc-editor.org/rfc/rfc9110.html}}; how those are written as bytes over one connection in HTTP/1.1 is {{RFC 9112|https://www.rfc-editor.org/rfc/rfc9112.html}}. Read it top to bottom. The first line of a request is the method (what to do), the path (to what), and the protocol version. Then headers, one Name: value per line: metadata such as who is calling (Authorization), what the body is (Content-Type) and how long it is (Content-Length). An empty line ends the headers; the body follows, here JSON. The response mirrors it: a status line with a three-digit code, headers, an empty line, a body. Header names are case-insensitive (uvicorn writes content-type, the client wrote Content-Type; both are right). Lines end with the two bytes carriage return and line feed (\r\n).

HTTP/2 ({{RFC 9113|https://www.rfc-editor.org/rfc/rfc9113.html}}) and HTTP/3 send the same methods, headers and status codes in a binary framing that lets many requests share one connection; the meaning, and everything on this page, is unchanged. The bytes before HTTP (DNS lookup, TCP and TLS handshakes) are on the root's Step 1 and in {{Topic: protocols|n:3c65c17b0d0d81ec9355f4eecd6eed02}}.

Methods and the two promises they make

RFC 9110 gives each method two properties that matter more than the method's name. Safe: "intended only for retrieving information and should not change the state of the server" (§9.2.1). Idempotent: "an identical request can be made one or more times in succession with the same effect as making a single request" (§9.2.2). Idempotent is the property that makes a retry harmless; it comes back in section 10.

Status codes: the first thing a client reads

The first digit is the class ({{RFC 9110 §15|https://www.rfc-editor.org/rfc/rfc9110.html#name-status-codes}}): 1xx informational, 2xx success, 3xx redirection, 4xx "you, the client, got something wrong" (do not retry unchanged), 5xx "I, the server, failed" (retrying later may work).
