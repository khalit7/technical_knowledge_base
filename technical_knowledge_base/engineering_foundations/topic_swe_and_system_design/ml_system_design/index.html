You have already put a model behind an API: a web framework, a POST /predict route, the model loaded in memory, an answer returned. That is the right start. This page is what changes when that endpoint is a large language model (LLM) serving many customers: each request costs about a thousand times more than an ordinary web request, runs for seconds, streams, gives different answers each time, and needs GPUs that come in large, slow-to-start blocks. Most of the design of an LLM service is a response to those five facts.

The running example is the parent topic's: a chat assistant with ten million registered users, one million of them active on a given day, ten messages each, about 1,000 input and 400 output tokens per message. Assumption used throughout this page: these are the parent page's Scale simulator defaults (1,000 input / 400 output tokens per reply), kept here so the numbers line up; the parent's Reading estimate in Step 6 rounds the reply to 500 tokens. That averages 116 messages a second and about 230 in the busy hour (peak factor 2, illustrative). The parent page drew its GPU layer as two boxes, "model router" and "GPU pools". The one idea to keep
Count tokens, not requests. Cost, GPU capacity, rate limits, autoscaling signals and latency are all set by how many tokens go in and come out, and two requests can differ in tokens by a factor of a thousand. Most mistakes in LLM service design come from carrying the request-counting habits of web services across.

1. From your model endpoint to a production service: what is different

Start from what you built: one process, one model, one request at a time. Ask what happens when ten thousand people call it in the same minute. Six things break that do not break for an ordinary CRUD service (Create, Read, Update, Delete: the web services that store and fetch records, like most of the parent topic's chat app).

It is expensive: a thousand times a web request

The parent topic prices an app server (AWS m7i.xlarge) at $0.2016 an hour. At an illustrative 500 requests a second per server, one web request costs $0.2016 ÷ 3,600 ÷ 500 = $0.00000011. Now one chat reply of 400 output tokens:

  • Self-hosted, Llama 3.3 70B in 8-bit floating point (FP8) on H100 GPUs at $3.99 per GPU-hour (Lambda pricing, read 2026-10-04), producing 2,209 output tokens a second per GPU at maximum load (TensorRT-LLM perf overview at commit 8a9c66c, vendor benchmark, 1,000 input and 1,000 output tokens per request; the parent topic's shared figure), run at half that rate to keep latency acceptable (the parent topic's derating, illustrative): $3.99 ÷ 3,600 ÷ (2,209 × 0.5) = $1.00 per million output tokens, so $0.0004 per reply, about 3,600 times the web request.
  • Through an API, Claude Sonnet 5.5 at $2 per million input tokens and $10 per million output tokens (Anthropic pricing, via the knowledge base's price snapshot of 2026-10-01): 1,000 × $2 + 400 × $10, per million, = $0.006, about 54,000 times.

That is 3.6 to 4.7 orders of magnitude; a 100,000-token document sent to a frontier model reaches 6. The old version of this page said "3 to 6 orders of magnitude above a CRUD call": the arithmetic agrees. The consequence is that cost is an architecture problem. Who may spend how much (quotas), which model a request deserves (routing), and which work need not be done twice (caching) are designed up front, not tuned later.

It is long, and it streams

A reply is generated one token (a word or part of a word) at a time. With 64 conversations sharing one copy of the 70B model on two GPUs, each gets about 69 tokens a second (4,418 ÷ 64; the batch of 64 is the parent's Scale simulator's illustrative engine limit), so a 400-token reply takes about 6 seconds. Users will not stare at a blank screen for 6 seconds, so the reply is streamed: sent token by token over one open HTTP response, usually as server-sent events (SSE), a text format where the server writes data: ... lines as they are ready. Every layer between the user and the GPU (load balancer, gateway, proxy) must pass the stream through without buffering it, and must allow connections that stay open for minutes.

Long requests also multiply how many are open at once. Little's law says the average number in a system equals arrival rate times time in the system (Little, 50th-anniversary paper). For the chat assistant: 116 messages a second × about 6 seconds = about 700 replies streaming at any moment on an average day, 1,400 in the busy hour. A web request of 20 ms at the same rate keeps two or three open.

Its size is unknown until it ends

A web request's cost is roughly known when it arrives. An LLM request's input is known, but its output length is decided by the model, from 1 token to the max_tokens cap. This one fact breaks two web habits: limiting customers by requests per minute (one request can be a thousand times another) and scaling servers on request rate (section 8 shows a pool sized on requests falling behind when replies get longer).

It does not give the same answer twice

Models sample: at temperature above zero the next token is drawn at random from the model's probabilities. Even at temperature zero, serving engines are not deterministic, because the numerical result of a matrix multiplication depends on how many other requests share the batch. Thinking Machines sampled the same prompt 1,000 times at temperature 0 from Qwen3-235B and got 80 different completions; with batch-invariant kernels all 1,000 were identical, at a cost in speed (Thinking Machines, 10 Sep 2025; detail on the Production eval engineering page). So "the tests pass" cannot tell you a new model or prompt is safe to ship: correctness is a statistic over many requests (section 10).

Capacity comes in big blocks that start slowly

The 70B model's FP8 weights are 72.7 GB (model files on Hugging Face; sum of the weight files, as in the parent's Scale simulator). One 80 GB H100 holds them with little room left for conversations, so a replica (one running copy of the model) spans two GPUs, and capacity grows two GPUs at a time; AWS rents H100s eight to a machine (p5.48xlarge, $55.04 an hour on demand, Vantage's AWS price mirror, read 2026-10-04). A new replica must get a GPU machine, download its software image, copy 73 GB of weights into GPU memory and warm up before it serves anyone: a cold start. vLLM's maintainers list what a cold start pays even when weights load instantly: memory allocator setup, recording CUDA graphs (pre-recorded GPU work sequences), compiling GPU kernels, and first-request warm-up, and put a full model reload at "30-100+ seconds per switch" (vLLM blog, sleep mode, 26 Oct 2025). Add finding and booting a GPU machine and minutes are normal. A web server starts in seconds; a GPU replica cannot be added the moment a spike arrives (section 8).

It fails quietly

A broken web service returns errors that a dashboard counts. A broken model service often returns fluent, wrong answers with status 200. In August 2025 a routing bug sent some Claude Sonnet 4 requests to servers configured for a different context length; at the worst hour 16% of Sonnet 4 requests were affected, error rates stayed normal, and users noticed before the evaluations did (the parent topic's Case files tab, "Three serving bugs quietly made Claude's answers worse"; Anthropic, 17 Sep 2025). Monitoring must include quality (section 12).

What this costs you as a designer
Every habit from web services needs checking: count tokens, not requests; expect seconds, not milliseconds; budget money per request; treat "200 OK" as necessary, not sufficient. The rest of the page builds the system that does this, box by box.

2. Anatomy of one LLM request, and the numbers that describe it

Follow one message from the chat assistant through the system. Each phase has its own number, and each number has its own fix, so a pro never says "latency" about an LLM service without saying which one.

1. Arrivenetwork, API server, gateway checks: milliseconds
→
2. Waitin the engine's queue until a batch slot frees: 0 when there is room, unbounded when there is not
→
3. Prefillthe model reads all input tokens at once; ends with the first output token
→
4. Decodeone token per step, each streamed to the user
→
5. Finishstop token or max_tokens; usage recorded
  • Time to first token (TTFT): from sending the request to receiving the first output token. Phases 1 to 3. It is what the user feels as "is it working?", and it is where queueing shows up first.
  • Time per output token (TPOT), also inter-token latency (ITL): the gap between streamed tokens in phase 4. vLLM defines the per-request TPOT as "(end-to-end latency - TTFT) / (number of output tokens - 1)" (vLLM metrics design doc, v0.30.0); ITL is measured gap by gap, and the two differ when a step emits several tokens at once (speculative decoding, owned by Topic: inference-and-serving).
  • End-to-end latency = TTFT + (output tokens − 1) × TPOT. For the chat assistant: about 0.09 s of prefill (derived for 1,000 input tokens on two H100s at an illustrative 40% of peak arithmetic, as in the parent's Scale simulator) plus 399 × 14.5 ms = about 5.9 seconds, of which the user waits only the first 0.09 s before text appears.
  • Tokens per second, which means two different things: per user (1 ÷ TPOT, about 69 here) and per GPU (4,418 ÷ 2 = 2,209 at full load). Bigger batches raise the second and lower the first. Every serving decision is a point on that trade-off.
  • Cost per request: tokens in and out times their prices, or GPU-seconds times the GPU price. It belongs on the same dashboard as latency (section 12).

The engine reports these directly. In vLLM v0.30.0 (released 2026-09-22) the Prometheus metrics a system designer reads are vllm:num_requests_waiting ("Number of requests waiting to be processed"), vllm:num_requests_running ("Number of requests in model execution batches"), vllm:kv_cache_usage_perc ("KV-cache usage. 1 means 100 percent usage", a fraction despite the name), and the histograms vllm:time_to_first_token_seconds, vllm:inter_token_latency_seconds and vllm:e2e_request_latency_seconds (vllm/v1/metrics/loggers.py at v0.30.0). Names change between versions: vllm:gpu_cache_usage_perc was renamed to vllm:kv_cache_usage_perc in 0.9.2 and removed in 0.12, and vllm:time_per_output_token_seconds gave way to vllm:inter_token_latency_seconds in 0.11. Dashboards and autoscalers that query the old names go silent after an upgrade, which is a real way to lose autoscaling.

The KV cache in that list is the engine's memory of each conversation: for every token so far, the model keeps intermediate results (keys and values) so it need not recompute them for the next token. It lives in GPU memory and grows with every token, so it caps how many conversations a replica can hold at once. For this model it is 2 × 80 layers × 8 key-value heads × 128 dimensions × 1 byte = 160 KiB per token (from the model's config; FP8 cache), so one 1,400-token conversation holds about 219 MiB. How engines manage it is the subject of the PagedAttention paper page; a system designer needs only to know that "KV cache full" means "no room for more conversations on this replica".

Targets you will meet
A latency target for an LLM service is a pair: a TTFT target and a TPOT target, usually at a percentile (p50, p99). Chat products care most about TTFT; agents and code tools that read the whole answer care about end-to-end time; batch jobs care only about tokens per dollar. For scale, the industry benchmark MLPerf Inference sets, for Llama 2 70B, TTFT 2,000 ms and TPOT 200 ms in its "conversational" category and 450 ms and 40 ms in its "interactive" one; for DeepSeek-R1, 2,000/80 ms and 1,500/15 ms (MLPerf inference rules, commit d3eba2f). Our chat example's 14.5 ms TPOT would pass the strictest of these; its TTFT depends on the queue, which is the whole of section 8. Goodput is the highest request rate per GPU at which the latency targets are still met for a chosen share of requests (say 90%), as opposed to raw throughput; DistServe introduced it for LLM serving (Zhong et al., OSDI 2024) because a system tuned for raw tokens per second can serve many tokens late.

3. The LLM gateway: one front door for every model call

The problem appears
The first feature calls a model API directly from the app with a key in an environment variable. By the fifth feature there are five copies of retry logic, three provider keys in three services, no idea which team spent $40,000 last month, no way to switch providers during an outage, and a customer's personal data going to a vendor nobody approved.

An LLM gateway is the service every model call in the company passes through: your code speaks one API shape (almost always OpenAI's chat completions format) and the gateway authenticates the caller, checks limits and budget (section 5), redacts personal data and applies input rails (Guardrails), looks up caches (section 9), routes (section 4), calls with a timeout, retries or falls back, streams the reply back unbuffered, and writes one usage event per call for cost and dashboards (section 12). It is the parent topic's load balancer and API gateway idea specialised for model traffic, and it exists for control, not throughput: Uber's served a peak of 25 queries a second. How one works inside, read from LiteLLM's source and recorded call by call (deployment choice, retries, cooldowns and fallbacks, production examples, what it costs and when not to run one), is Gateways and routing. The system designer's decisions are around it: who owns it, which models it allows for which data and tenants (section 6), whether it fails open or closed when its own counters are unreachable, and how its usage events feed cost and quality monitoring (section 12).

4. Routing, fallbacks and model tiers

A router decides which model and which copy of it serves each request, at two levels that are easy to confuse. Which model is the gateway's decision: tier routing (easy requests to a small model; prices differ 2 to 40 times between tiers of one vendor), context routing (long prompts to long-context pools; getting it wrong was Anthropic's August 2025 bug, section 1), policy routing (tenant pinning, data residency, self-hosted only) and fallbacks, which must be planned like a backup generator (enough quota for all the traffic, the same prompt and tool format, the same safety behaviour, a cold prompt cache). All of it, with recorded fallback chains and a learned-router experiment, is on Gateways and routing, sections 3 and 10. Which replica is a second load balancer inside a self-hosted pool, and it must see each replica's queue and prefix cache rather than go round robin; prefix-aware and sticky routing, measured on real replicas, are on LLM serving in production, section 1. What stays with the system designer: a misrouted hard question is a worse answer that no error counter sees, so a tier router is measured as a classifier on labelled traffic, and a fallback needs standing capacity somewhere else. The Cost-quality lab puts numbers on both.

5. Rate limits and quotas, counted in tokens

Two business customers each limited to 60 requests a minute can differ 36 times in load (60 short chats against 60 summaries of a 50,000-token contract), so limits for LLM traffic count tokens. A rate limit caps how fast a caller consumes capacity, answering 429 Too Many Requests past it, usually with a token bucket: a refilling allowance that lets short bursts through and caps the average (the mechanism, animated beside the other algorithms, is on Reliability engineering). A quota or budget caps total use over a period, usually in money. The hard part is that output tokens are unknown at admission: limiters reserve the worst case, count output as it streams, or charge after the response and accept overshoot. Those three answers, Anthropic's and OpenAI's limits, Envoy's per-tenant policy, budgets under concurrency, and the three refusals to keep apart (over your limit, out of budget, out of capacity) are on Gateways and routing, sections 5 and 6. Two decisions stay here: cap concurrent streams per tenant as well as tokens, because a stream holds a batch slot for seconds (section 6), and decide what happens when the shared counter is unreachable (fail open and risk overload, or fail closed and refuse everyone). When not to: an internal tool with a handful of users and a monthly budget alert needs no per-tenant token buckets.

6. Multi-tenancy and isolation

A tenant is one customer organisation sharing your system with others. Multi-tenancy is serving them all from shared infrastructure, which is cheap, while keeping each from hurting or seeing the others, which is the work. Four things must be isolated:

  • Capacity. The noisy neighbour: one tenant's burst fills the batch and every other tenant's TTFT rises. Token limits (section 5) cap the average; fair scheduling handles the moment. The Virtual Token Counter scheduler defines fairness by "a cost function that accounts for the number of input and output tokens processed" and gives "a 2× tight upper bound on the service difference between two backlogged clients" while keeping the GPU busy (Sheng et al., Fairness in Serving Large Language Models, OSDI 2024).
  • Data. Prompts and answers must never cross tenants: not in logs, not in caches. A response cache or semantic cache shared across tenants can hand one customer another's answer; even a shared prefix cache is a timing side channel (a fast first token reveals that someone sent the same beginning). OpenAI states "Caches are not shared across organizations" (OpenAI prompt caching). Put the tenant id in every cache key.
  • Cost. Every usage event carries the tenant, so each one's bill and margin are known (section 12).
  • Customisation. Tenants may have their own fine-tuned adapters on a shared base model; engines can serve many small adapters on one replica (Parameter-Efficient Fine-Tuning).

Real examples of each idea. Priority classes are as old as Google's load shedding: requests are tagged CRITICAL_PLUS, CRITICAL, SHEDDABLE_PLUS ("the default for batch jobs, which can retry requests minutes or even hours later") or SHEDDABLE, and a request's criticality propagates to the calls it makes (SRE book, ch. 21, Handling Overload). The Kubernetes inference stack does the same for model traffic: an early version had Critical, Standard and Sheddable; today llm-d's InferenceObjective carries an integer priority, and "flow control will always allow requests of higher priority to be served first", while "Fairness is only enforced and tracked between requests of the same priority" (inferenceobjective_types.go, llm-d-router v0.11.0). Reserved capacity: Anthropic's Priority Tier committed input and output tokens per minute for 1 to 12 months, "targets 99.5% uptime", and "Requests beyond your committed capacity automatically fall back to standard tier"; it is "no longer available for purchase" to new buyers as of October 2026 (Anthropic service tiers).

What isolation costs
Each step down the table buys predictability with idle hardware. Scoping caches per tenant lowers hit rates. When not to: a product with one customer (your own app) has no tenants to isolate; start with a shared pool and per-tenant limits, and add reserved or dedicated capacity only for a customer who pays for it.

7. Three paths: realtime, streaming and batch

Not every model call is a person waiting. Splitting traffic by how long it may wait is the single biggest cost lever after routing, because work that can wait can run when GPUs are idle or cheap.

Batch through providers costs half. OpenAI's Batch API gives a "50% cost discount compared to synchronous APIs" and each batch "completes within 24 hours (and often more quickly)", with its own higher rate limits (OpenAI Batch API). Anthropic's Message Batches: "All usage is charged at 50% of the standard API prices", "most batches finishing in less than 1 hour", a batch holds up to 100,000 requests or 256 MB, unfinished requests expire after 24 hours and are not billed, and the discount stacks with prompt caching (Anthropic batch processing). Between realtime and batch there are now speed tiers on the same API: OpenAI's Flex processing trades "slower response times and occasional resource unavailability" for batch prices, and returns a 429 it does not charge for when capacity is short; its premium tier, renamed from Priority processing to Fast mode on 30 July 2026, charges more per token for up to 2.5 times the speed (Flex processing, Fast mode).

Batch on your own GPUs means using the trough. The parent topic's estimate showed that a fleet sized for the busy hour sits more than half idle overnight; a batch lane that fills that idle capacity at low priority, and is pushed aside the moment chat traffic needs the slots, turns idle GPU-hours into useful work. That needs a priority scheduler in the engine or router (the vLLM production stack router has a priority option; replica routers are compared on LLM serving in production) and batch jobs that tolerate being paused. The batch lane is also the natural home for preemptible spot GPUs (section 8).

Long jobs behind a person (generate a report, run an agent for ten minutes) use the parent topic's asynchronous pattern: accept the job, return 202 Accepted with a job id, put it on a queue, and let the client poll or receive a callback. Anthropic itself advises "the streaming Messages API or Message Batches API for long-running requests, especially those over 10 minutes". Delivery guarantees, retries and dead-letter queues for that pattern belong to the sibling page Queues, streams and async work.

What splitting costs
Two or three code paths instead of one, and results that arrive later. A batch lane on shared GPUs needs preemption that really works; a batch job that cannot be paused will hold slots during the morning ramp. When not to: if under a tenth of your tokens can wait, the second path is not worth its code.

8. Autoscaling GPUs

Autoscaling adds replicas when load rises and removes them when it falls, and on GPUs the web-service habits fail: CPU utilisation barely moves, GPU utilisation reads near 100% at a tenth of capacity, GPU memory is reserved at start, and requests per second ignores request size (section 1). Queue depth and KV cache use work. A replica takes minutes to start, so a pool keeps headroom: if traffic can grow 20% during one cold start, keep about 20% spare. Spot GPUs, reclaimable with seconds to two minutes of warning, belong first in the batch lane (section 7). The signals, real KServe, KEDA and llm-d thresholds, the cold-start chain and its fixes, spot numbers, and an Autoscaling lab that runs two autoscalers on one spike are on LLM serving in production, sections 2 and 3. For the design: set the TTFT target, size headroom from the measured cold start, give batch work the idle trough, and keep the metrics plumbing working (an autoscaler reading a renamed metric sees zero, section 2). When not to: steady traffic on a fixed fleet, or a fleet so small that one replica is the minimum anyway; then fixed capacity plus load shedding (section 11) is simpler.

9. Caching layers

The parent topic's cache rule holds: do not compute the same thing twice. LLM services have four caches, from outermost to innermost, and they differ in what counts as "the same".

  • Exact response cache. Key = hash of (tenant, model, full prompt, sampling parameters); value = the stored answer. Safe and cheap; hits mostly on retried requests, repeated system jobs and identical FAQ-style prompts. Low hit rate on chat, because conversations rarely repeat exactly. Skip it for requests with temperature above zero if users expect variety.
  • Semantic cache. Embed the new prompt, find the most similar stored prompt, and return its answer if the similarity is above a threshold (GPTCache popularised it; LiteLLM ships one: type: "redis-semantic" with similarity_threshold: 0.8, LiteLLM docs). It is the riskiest cache because "similar" is not "same": "What is my balance?" from two users, "flights to Paris Texas" and "flights to Paris", yesterday's news. GPTCache's own README warns "you may encounter false positives during cache hits". Measured: one study reports hit rates of 61.6 to 68.8% with "positive hit rates exceeding 97%", that is roughly 3% of hits wrong (GPT Semantic Cache, arXiv 2411.05276); vCache finds that a single static threshold gives "unexpected error rates" and learns a threshold per cached prompt, reporting "up to 12.5× higher cache hit and 26× lower error rates" (vCache, arXiv 2502.03771). Huyen's verdict: "semantic cache's value is more dubious because many of its components are prone to failure". Use it only for non-personal, slowly changing answers, scoped per tenant, with the threshold set by an evaluation and the wrong-answer rate monitored.
  • Prefix (KV) cache. Not an answer cache: it keeps the KV cache of a prompt's beginning so the next request with the same beginning skips that part of prefill. It never changes the answer, only the speed and price. Engines do it automatically (vLLM automatic prefix caching) and providers sell it: Anthropic charges 1.25 times the input price to write a 5-minute cache entry and 0.1 times to read it (Anthropic prompt caching); OpenAI caches automatically from 1,024 tokens and now charges 1.25 times for writes on its newest models (GPT-5.6 and later) (OpenAI prompt caching). The read multiplier is no longer 0.1 everywhere: Anthropic bills cache reads at 0.05 times the input price on Claude Opus 5.5 and 0.025 times on Fable 5.1 and Mythos 5.1, and OpenAI at 0.05 times on GPT-6.1 Sol; the current table, with the KV cache and semantic caching beside it, is section 11 of Caching: every layer, eviction, invalidation, and the LLM caches.   • Embedding and retrieval caches. In retrieval-augmented generation, store the embedding of each document chunk (computed once) and of frequent queries. Owned by Topic: rag-and-retrieval.

Real caveats: a cache entry lives 5 minutes unless used (or 1 hour at a higher write price), there is a minimum cacheable length (512 to 4,096 tokens by model on Anthropic), and an entry "only becomes available after the first response begins", so parallel requests sent at once all miss.

Two production details decide whether prefix caching pays. First, the request must reach a machine that has the prefix: provider caches live on individual machines (OpenAI: traffic "above 15 requests per minute" on one prefix "can lead to overflow routing"; a prompt_cache_key helps it route), and for self-hosted pools this is the job of a prefix-aware router (LLM serving in production, section 1) and of Character.AI's sticky sessions, which reached a "95% cache rate" (parent's Case files). Second, prompts must be append-only: anything that changes per request (time, user name, retrieved documents, a shuffled tool list) goes after everything that does not.

What caches cost
Memory and a lookup on every request; invalidation when a model or prompt version changes (put both in the key); per-tenant scoping (section 6), which lowers hit rates; and, for semantic caches, wrong answers. When not to: answers that depend on the user, on time or on live data must not come from a response or semantic cache; prefix caching is almost always worth it.

10. Rolling out a new model or prompt

The problem appears
A new model version scores better on the offline evaluation, so it replaces the old one for everyone at 10:00. By 10:40 support tickets say answers in German got worse, tool calls fail for one customer's schema, and cost per request is up 30% because the new model writes longer replies. None of that was in the evaluation set.

For a model service, "a change" is any of: a new model or provider version, a new prompt, new sampling parameters, a new engine version or GPU type (Anthropic's postmortem shows the same model behaving differently on different hardware stacks), or a new router. Each should ship like risky code, in stages, with the decision at each stage made on numbers. The statistics of those decisions (how much traffic, for how long, which test) are owned by Production eval engineering; here is the machinery a system designer builds.

  1. Pin and version everything. The model id (a dated snapshot, not an alias that the provider moves), prompt version, parameters and router config live in versioned config, and every usage event records them. Then rollback is a config change, not a deploy, and every bad answer can be traced to the exact versions that produced it.
  2. Offline gate. The candidate must pass the regression evaluation before it sees any user (sibling Testing and quality; gates in Production eval engineering).
  3. Shadow. Copy live requests to the candidate and throw its answers away; compare quality (sampled, with judges), latency and cost against the incumbent on the same inputs. Service meshes do the copying: Istio's mirror with mirrorPercentage sends requests "as 'fire and forget,' which means that the responses are discarded" (Istio docs, mirroring), so the shadow service must log its own outputs. Shadowing doubles model cost for the mirrored share: mirror a sample, and never mirror requests with side effects (tool calls that send email or charge cards).
  4. Canary. Send a small share of real traffic to the candidate (1%, then 5%, 25%, 100%), keyed by user or tenant so one user's conversation stays on one version, and stop automatically if a guard metric breaks. KServe does this with one field: canaryTrafficPercent: 10 on the predictor; set it to 0 to roll back (KServe canary example). Argo Rollouts (v1.10.0) adds analysis steps that "block the rollout until the run is completed" and a successCondition such as result[0] >= 0.95 on a Prometheus query (Argo Rollouts analysis).
  5. A/B test when the question is "is it better for users", not "is it safe": a fixed split for long enough to measure user outcomes.
What staged rollout costs
Days instead of minutes per change, shadow compute, and two versions in production at once (two prompt caches, two sets of GPUs if self-hosted). When not to: internal tools and prototypes can switch at once behind a flag; anything customers depend on cannot.

11. Failure modes and degradation ladders

The parent topic's Step 4 and the sibling Reliability engineering teach timeouts, retries with backoff and jitter, circuit breakers and load shedding. Here is how they apply when the dependency is a model.

Provider overloaded (Anthropic 529) or your quota hit (429)status codes, retry-afterhonour retry-after; for 429 on quota, route elsewhere or shed; never retry a spend-cap 429

Never queue without a bound in front of a GPU. Without one, a queue that grows faster than it drains turns overload into minutes of waiting for everyone, and clients that time out and retry add more load. A bounded queue that refuses early keeps the requests it accepts fast. Google's SRE book recommends a client-side version too: each client tracks its requests and the backend's accepts, and keeps sending until "requests is K times as large as accepts", with "We generally prefer the 2x multiplier" (SRE book, ch. 21).

A degradation ladder, decided before the incident

Degrading means serving a worse answer instead of none: "responses that are not as accurate as or that contain less data than normal responses, but that are easier to compute" (SRE book, ch. 21). For the chat assistant, from best to worst:

1. Full servicelarge model, full context, retrieval on
→
2. Second providersame quality, higher cost or latency
→
3. Smaller modelcheaper tier for everyone, or for free users
→
4. Less workshorter context, retrieval off, lower max_tokens
→
5. Cached or canned answerfor known questions
→
6. Honest errorwith a retry time

Each rung needs a trigger (which metric, which threshold), an owner who may pull it, and a test that it works. Shed the cheapest-to-lose traffic first: batch (section 7), then free tier, then paid. Real policies differ, and some choose not to degrade quality at all. GitHub Copilot users who exhaust premium requests "can still use Copilot with one of the included models", which "may be subject to rate limiting" (GitHub docs, Copilot requests); ChatGPT's free tier now pauses: "GPT access pauses until the limit resets" (OpenAI help, free tier FAQ, read 2026-10-04); and Anthropic states "We never reduce model quality due to demand, time of day, or server load", degrading by queueing and limits instead. Whatever you choose, tell users which rung they are on.

Failures that are not yours
The worst outages of model services are often in ordinary infrastructure. OpenAI's 11 December 2024 outage (4 hours 22 minutes) came from a telemetry service that overloaded the Kubernetes control plane, which broke DNS-based service discovery (parent's Case files, "A monitoring tool overloaded the cluster brains"). The gateway, the autoscaler, the metrics pipeline and DNS are part of the model service's reliability.

12. Observing an LLM service

The sibling Observability teaches logs, metrics, traces and alerting. An LLM service needs four families of signals on top of the usual request rate, errors and duration:

  • Latency per phase: TTFT and TPOT as histograms (percentiles, not averages), queue time separately, per model and per tenant. Engines export them (section 2); the gateway should measure TTFT too, because the user's TTFT includes everything before the engine.
  • Capacity: waiting and running requests, KV cache use, prefix cache hit rate (vLLM exports vllm:prefix_cache_queries and vllm:prefix_cache_hits in tokens, so hit rate = hits ÷ queries), tokens per second per GPU, preemptions.
  • Money: one usage event per request (tenant, feature, model and prompt versions, input, cached and output tokens, cost, latency, outcome), streamed to an analytics store. From it come bills, per-team showback, cost per request, and the margin per tenant. Price cached and output tokens separately: they differ by a factor of 50 (Sonnet 5.5: $0.20 against $10 per million).
  • Quality: what no status code shows. Sample production traffic and score it with judges, track user signals (thumbs, regenerations, abandonment), and watch output length and refusal rate, which move when a model changes. Anthropic's lesson from its postmortem: "The evaluations we ran simply didn't capture the degradation users were reporting", and it now runs quality evaluations "continuously on true production systems".

A shared vocabulary is forming: OpenTelemetry's generative-AI semantic conventions (moved in 2026 to their own repository, status "Development") define gen_ai.server.time_to_first_token ("Time to generate first token for successful responses"), gen_ai.server.time_per_output_token and token-usage counters such as gen_ai.client.inference.usage.input_tokens and .cache_read.input_tokens (semantic-conventions-genai at e07f4eb). The earlier gen_ai.client.token.usage histogram is no longer defined there; development-status names still move, so pin the version you instrument against.

What it costs
Storing prompts and outputs for debugging and evaluation is storing customer data: decide retention, redaction and access up front. Per-tenant, per-model labels multiply metric series; keep high-cardinality fields in the usage events, not in metric labels.

13. Classic ML serving: features, skew, batch scoring, embeddings

Most models in production are not LLMs: fraud scores, ranking, recommendations, ETA prediction, search relevance. They are cheap per call (milliseconds of CPU) but bring a problem LLMs mostly hide: the model's inputs are features (numbers computed from data, such as "orders this user placed in the last 7 days") that must be computed the same way when training and when serving.

Online and offline

Uber's Michelangelo platform (2017) is the reference picture. Features for online models were "precomputed and stored in Cassandra where they can be read at low latency", there were "approximately 10,000 features in Feature Store", and serving ran at "P95 latency of less than 5 milliseconds" without stored features and "less than 10ms" with them, with "the highest traffic models right now serving more than 250,000 predictions per second". Offline models wrote predictions "back to Hive" for other jobs to read (Uber Engineering, Meet Michelangelo, 5 Sep 2017). By 2024 there were "more than 5K models in production, serving 10 million real-time predictions per second at peak", and the platform had added a Gen AI Gateway with logging, cost attribution and PII redaction (Uber, From predictive to generative AI, 2 May 2024).

That gives the two serving modes:

  • Batch scoring: run the model over every user or item on a schedule and store the predictions in a table the product reads. Cheap, simple, easy to inspect; stale between runs and wasteful for users who never show up. Good for daily recommendations, churn scores, nightly embeddings.
  • Online inference: compute the prediction inside the request, with fresh features. Needed when the input only exists now (a transaction being authorised, a search query). DoorDash's Sibyl prediction service, for example, fetched features from Redis per prediction, ran shadow predictions for candidate models on the same inputs, and load-tested at "over 100,000 predictions per second" (DoorDash Engineering, 29 Jun 2020).

Training-serving skew, the classic ML bug

Google's Rules of Machine Learning define training-serving skew as "a difference between performance during training and performance during serving", caused by "A discrepancy between how you handle data in the training and serving pipelines", "A change in the data between when you train and when you serve", or "A feedback loop between your model and your algorithm". Its fix, Rule #29: "save the set of features used at serving time, and then pipe those features to a log to use them at training time"; YouTube's home page did this "with significant quality improvements and a reduction in code complexity" (Rules of ML). The deeper version of the same warning is Sculley et al.'s "Hidden Technical Debt in Machine Learning Systems": a mature system might be "(at most) 5% machine learning code and (at least) 95% glue code", and "Changing Anything Changes Everything" (NeurIPS 2015).

A feature store is the tool that removes most skew: features are defined once, computed into an offline store (for training) and an online store (for serving), and read through one API. Its key guarantee is point-in-time correctness: a training example labelled at 8:50 must only see feature values known at 8:50, not ones computed at 8:52, or the model learns from the future and disappoints in production (Databricks docs, point-in-time joins). A point-in-time join measured in DuckDB, with the leak it prevents, is section 11 of Analytics: columnar engines, DuckDB and the lakehouse. In Feast (v0.66.0), the same feature names serve both sides:

# training: features as of each row's timestamp ("point-in-time correct")
training_df = store.get_historical_features(
    entity_df=entity_df,               # driver_id, event_timestamp, label
    features=["driver_hourly_stats:conv_rate",
              "driver_hourly_stats:acc_rate",
              "driver_hourly_stats:avg_daily_trips"],
).to_df()

# serving: copy the latest values into the online store, then read them in the request
#   feast materialize-incremental $CURRENT_TIME
feature_vector = store.get_online_features(
    features=["driver_hourly_stats:conv_rate",
              "driver_hourly_stats:acc_rate",
              "driver_hourly_stats:avg_daily_trips"],
    entity_rows=[{"driver_id": 1004}, {"driver_id": 1005}],
).to_dict()

From the Feast quickstart: Feast "ensures point-in-time correctness so future feature values do not leak to models". Airbnb's Chronon (open-sourced 2024 with Stripe as co-maintainer) lets teams "define their features only once, powering both offline flows for model training as well as online flows for model inference", and measures consistency by comparing logged online fetches with backfilled values (Airbnb Engineering).

LLM services have skew too: a prompt template assembled differently in the evaluation harness and in production, a retrieval index rebuilt between evaluation and launch, a tokenizer or chat template version mismatch. Rule #29 transfers directly: log the exact prompt the model saw.

Embedding services

An embedding model turns text into a vector for search and retrieval. Serving one is a throughput problem: many short inputs, batched by tokens. Hugging Face's Text Embeddings Inference (v1.9.4) has "Token based dynamic batching" with --max-batch-tokens (default 16384; "you could fit 10 queries of total_tokens=100 or a single query of 1000 tokens" for a limit of 1,000) and --max-concurrent-requests (default 512), where "Having a low limit will refuse clients requests instead of having them wait for too long and is usually good to handle backpressure correctly" (TEI CLI arguments). Two design facts: embeddings from different models live in different spaces, so changing the embedding model means re-embedding the whole corpus (a batch job, half price through batch APIs, usually written to a new index and switched over once complete; reasoning, not a sourced rule), and the model version belongs in every stored vector's metadata. Smaller vectors are a cost lever: OpenAI notes a text-embedding-3-large vector "can be shortened to a size of 256 while still outperforming an unshortened text-embedding-ada-002 embedding with a size of 1536" (OpenAI embeddings guide).

14. The ML system design interview, run with the method

The parent topic's Step 6 teaches the general method (requirements, estimates, API, data model, high-level design, deep dives, trade-offs) and Alex Xu's timing for a 45-minute interview: scope 3 to 10 minutes, high-level design 10 to 15, deep dive 10 to 25, wrap-up 3 to 5. ML interviews keep that shape and swap the middle for ML steps. Chip Huyen's booklet uses project setup, data pipeline, modelling and serving (Machine Learning Systems Design); Aminian and Xu's Machine Learning System Design Interview (ByteByteGo, 2023) is commonly summarised as seven steps (clarify requirements, frame as an ML task, data, model, evaluation, deployment and serving, monitoring; the course page is behind a login, so that list is unconfirmed here). For an LLM product, run it like this:

  1. Requirements (5 min). Users and tenants; traffic; what a good answer is; latency as TTFT and TPOT targets; cost per request or per user; data rules (which vendors may see what); realtime or batch. State assumptions aloud.
  2. Metrics (3 min). Offline: task metrics on an evaluation set. Online: resolution rate, thumbs, escalations. System: TTFT and TPOT percentiles, availability, cost per request. Guard metrics: safety violations, wrong-answer rate.
  3. Estimate (5 min). Tokens per second at peak, GPUs or API dollars, concurrent streams (Little's law). Below.
  4. Model and data (5 min). API or self-hosted; which tier; prompt, retrieval or fine-tune, justified by the estimate.
  5. High-level design (10 min). This page's opening diagram, pruned to what the requirements need.
  6. Deep dives (10 to 15 min). Pick the two the numbers flag: usually cost (routing and caching) and capacity (autoscaling and the degradation ladder), or quality (rollout and monitoring).
  7. Wrap-up. What breaks at ten times the traffic, and what you would build next.
Worked estimate: a support assistant for 10,000 business tenants

Illustrative inputs: 500 messages per tenant per day, busy hour 3 times the average, 3,000 input tokens (instructions plus retrieved documents) and 300 output tokens per message, 70% of input tokens a cached prefix.

  • Traffic: 10,000 × 500 = 5 million messages a day = 58 a second on average, 174 a second at peak.
  • Output tokens at peak: 174 × 300 = 52,000 a second.
  • Self-hosted 70B at the derated 1,104 tokens/s per GPU: 52,083 ÷ 1,104.5 = 47.2, so 48 H100s (24 replicas), $4,596 a day at $3.99 if kept for the peak all day; Little's law gives 174 × (300 ÷ 69 tokens/s) = about 755 streams open at peak.
  • Through an API (Sonnet 5.5): 3,000 × $2 + 300 × $10 per million = $0.009 a message, $45,000 a day; with 70% of input read from the prefix cache, 900 × $2 + 2,100 × $0.20 + 300 × $10 per million = $0.00522, $26,100 a day.

What to say next is the point of the exercise: the API costs six to ten times the self-hosted fleet at this volume (with and without caching), but buys a stronger model, no capacity risk and no GPU team; a router that sends easy questions to a small tier and caching change the ratio; and the self-hosted fleet sized for the peak is mostly idle at night unless batch work fills it. Checked in src/recompute.py.

What interviewers reward is quantified trade-offs, not component names: "prefix caching cuts the cost per message by about 40% here because 70% of each prompt is static" beats "add a cache". Frontier-lab interviews go deeper into the engine (KV cache sizing, prefill and decode on separate GPUs, speculative decoding); that depth is in Topic: inference-and-serving. Full worked designs from requirements to bottlenecks are in the sibling System design case studies; its Design 5, an LLM gateway for a company (routing, quotas, fallbacks, cost), runs this interview's method end to end on the gateway this page describes, and is the one to practise with after this section.

Common mistakes

Rate limiting or autoscaling on requests per second
One request can be a thousand times another. Limit and scale on tokens and queues (sections 5 and 8).
Autoscaling on GPU or CPU utilisation
GPU duty cycle does not measure work done, GPU memory is pre-allocated, CPU barely moves. Use queue depth, batch size or KV cache use (section 8).
An unbounded queue in front of the GPUs
It converts overload into minutes of waiting for everyone and invites retry storms. Bound it and refuse early with Retry-After (section 11).
A timestamp or user name at the top of the prompt
It defeats prefix caching for every request. Static content first, append-only, dynamic content last (section 9).
A semantic cache on personal or time-sensitive questions
"Similar" is not "same": wrong answers, sometimes another user's. Scope per tenant, restrict to safe intents, measure the false-hit rate (section 9).
Retrying through every layer
Client, gateway and SDK each retrying three times multiplies load during an outage (the parent topic's 243-times case). Retry in one layer, honour retry-after, then fall back.
Model aliases instead of pinned versions
The provider moves the alias and your quality changes overnight with no deploy to roll back. Pin dated snapshots; record versions in every usage event (section 10).
Huge max_tokens by default
Where limits reserve max_tokens (OpenAI), it burns rate limit that is never used; everywhere it allows runaway cost. Set it per feature.
Monitoring errors but not quality
Model failures are often fluent and 200 OK. Sample and score production traffic continuously (section 12).
Dashboards and autoscalers on renamed metrics
vLLM renamed gpu_cache_usage_perc and time_per_output_token_seconds; queries on old names return nothing after an upgrade. Alert on missing metrics (section 2).
A fallback that has never carried full traffic
Its quota, prompt format, tool-call format and cold cache are untested until the outage. Test failover on a schedule (section 4; the checklist is on Gateways and routing, section 3).
Different feature or prompt code in training and serving
Training-serving skew. Log what the model saw at serving time and train or evaluate on that (section 13).

Glossary

Autoscaling: adding and removing replicas automatically as load changes.
Batch scoring: precomputing predictions for everyone on a schedule.
Cold start: the time for a new replica to get hardware, load weights and warm up.
Cost per request: tokens times prices, or GPU-seconds times GPU price.
CRUD: web services that create, read, update and delete records.
End-to-end latency: TTFT plus the time to stream the rest.
Feature: a number computed from data and given to a model.
Feature store: one definition of features, served offline and online.
LLM gateway: the single service every model call passes through.
Goodput: request rate per GPU that still meets latency targets.
Headroom: spare capacity kept to absorb spikes during cold starts.
Inter-token latency (ITL): the gap between streamed tokens.
KV cache: the engine's per-token memory of a conversation, in GPU memory.
Little's law: items in a system = arrival rate × time each stays.
Multi-tenancy: serving many customers on shared infrastructure.
Noisy neighbour: one tenant's load hurting the others.
Online inference: computing the prediction inside the request.
Point-in-time correctness: training rows see only feature values known at their time.
Quota: a cap on total use over a period, often in money.
Rate limit: a cap on how fast a caller may consume.
Replica: one running copy of the model, often on several GPUs.
Router: picks the model (gateway level) or the replica (pool level).
Server-sent events: a text format for streaming over one HTTP response.
Spot GPU: discounted capacity the cloud can take back on short notice.
Streaming: sending the reply token by token as it is generated.
Tenant: one customer organisation in a shared system.
Token: the unit models read and write, a word or part of one.
Token bucket: a refilling allowance that permits bursts and caps the average.
Tokens per second: per user (speed felt) or per GPU (capacity).
TPOT: average time per output token after the first.
Training-serving skew: a model doing worse in serving than in training because inputs differ.
TTFT: time from sending the request to the first output token.
Usage event: one record per request of who, which model, tokens, cost and latency.

Cost-quality lab

A design lab for the decision a system designer owns: how much quality to trade for cost. Put the chat assistant's traffic through a small and a large model, caches and a fallback provider, and see what each request costs, how long it takes, how many fail, and how many get a worse or wrong answer, against a naive, healthy baseline: the same traffic sent to the large model, no caching, no outage. Every number is an expectation per request (no randomness). How a real gateway retries, cools down and falls back, recorded call by call, is on Gateways and routing.

Try: start from Naive, then Router + prefix cache: cost halves and a few percent of answers get worse (hard questions misrouted to the small model). Then Provider outage, no fallback against with fallback: the fallback turns 40% errors into slower, pricier answers. Then push the semantic cache's hit rate up and watch wrong answers climb.

How it is computed. Requests first meet the exact cache, then (if on) the semantic cache, then the router; the router sends easy requests to the small model with the stated accuracy, and its mistakes send hard requests to the small model (counted as worse answers) and easy ones to the large model (wasted money). Calls to the failing provider either error or go to the fallback, which starts with no cached prefix. Cost per request = (uncached input × input price + cached input × cache-read price + output × output price) ÷ 1,000,000.
