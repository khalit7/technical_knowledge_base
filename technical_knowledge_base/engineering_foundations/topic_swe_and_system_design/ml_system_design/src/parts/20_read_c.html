5. Rate limits and quotas, counted in tokens

The problem appears
The chat assistant opens an API to business customers with a limit of 60 requests a minute each. Customer A sends 60 short chats a minute: 60 × 1,400 = 84,000 tokens. Customer B sends 60 requests a minute, each with a 50,000-token contract to summarise: 3 million tokens, 36 times A's load for the same "60 requests". B fills the GPUs and A's users wait.

A rate limit caps how fast a caller may consume a resource; past it the server answers 429 Too Many Requests, which "MAY include a Retry-After header indicating how long to wait" ({{RFC 6585 §4|https://www.rfc-editor.org/rfc/rfc6585#section-4}}; the header's format is in {{RFC 9110 §10.2.3|https://www.rfc-editor.org/rfc/rfc9110#section-10.2.3}}). The parent topic introduced the token bucket: each caller has a bucket that refills at a steady rate up to a maximum, and each request takes from it, so short bursts pass and the average is capped. For LLMs the fix is to put model tokens in the bucket, not requests. That is what the providers do:

  • Anthropic: "The API uses the token bucket algorithm to do rate limiting. This means that your capacity is continuously replenished up to your maximum limit, rather than being reset at fixed intervals", with separate limits for requests per minute (RPM), input tokens per minute (ITPM) and output tokens per minute (OTPM), per model. "For most Claude models, only uncached input tokens count toward your ITPM rate limits", so caching raises effective capacity: "With a 2,000,000 ITPM limit and an 80% cache hit rate, you could effectively process 10,000,000 total input tokens per minute" ({{Anthropic rate limits|https://platform.claude.com/docs/en/api/rate-limits}}, read 2026-10-04).
  • OpenAI limits RPM, requests per day, TPM and tokens per day, per organisation and project, and reports what is left in x-ratelimit-remaining-tokens and related headers ({{OpenAI rate limits|https://developers.openai.com/api/docs/guides/rate-limits}}).

The hard part: output tokens are unknown at admission

When a request arrives you know its input tokens but not its output. Three real answers:

  1. Reserve the worst case, refund later. OpenAI: "Your rate limit is calculated as the maximum of max_tokens and the estimated number of tokens based on the character count." A careless max_tokens of 32,000 on every call burns limit that is never used.
  2. Count output as it is produced. Anthropic: "OTPM rate limits are evaluated in real time as output tokens are produced, counting only the actual tokens generated. The max_tokens parameter does not factor into OTPM rate limit calculations."
  3. Charge after the response. Envoy AI Gateway (Agent Router) v1.1.0: "Token usage is charged after the response completes", and "If the existing charged usage is over the limit, the request is rejected with a 429 status code". The price is overshoot: it "does not interrupt an already admitted stream", so with a 1,000-token hourly limit one admitted request "can stream 1,200 tokens successfully. The bucket is then 200 tokens over the limit" ({{usage-based rate limiting docs, v1.1.0|https://github.com/theagentrouter/agent-router/blob/v1.1.0/site/docs/capabilities/traffic/usage-based-ratelimiting.md}}).

The Envoy policy that limits each tenant to a token budget per model, trimmed from the same page: the request itself costs 0 and the response costs its total tokens, read from metadata the gateway fills in.

rateLimit:
  type: Global
  global:
    rules:
      - clientSelectors:
          - headers:
              - name: x-tenant-id      # one bucket per distinct tenant
                type: Distinct
              - name: x-ai-eg-model    # ... per model
                type: Exact
                value: gpt-4
        limit:
          requests: 1000               # here: 1000 total tokens per hour
          unit: Hour
        cost:
          request:  {from: Number, number: 0}
          response:
            from: Metadata
            metadata: {namespace: io.envoy.ai_gateway, key: llm_total_token}

Alongside token limits, cap concurrent streams per tenant: a stream holds a batch slot for seconds (section 1), and fifty open streams from one tenant are fifty slots nobody else can use, whatever the token count.

Rate limits are not quotas

A rate limit protects capacity right now; a quota (or budget) caps total use over a billing period, usually in money. Envoy's docs separate them the same way: "Use QuotaPolicy when you need to cap cumulative token spend, and usage-based rate limiting (this page) when you need to control request velocity." LiteLLM sets budgets on keys, users and teams with max_budget (US dollars) and budget_duration such as 30d, and rejects calls past it with errors like "ExceededTokenBudget" ({{LiteLLM docs, budgets and rate limits|https://docs.litellm.ai/docs/proxy/users}}). Tell callers which one they hit: Anthropic returns 429 with a retry-after header for a rate limit, 429 with no retry-after when the monthly spend cap is reached (retrying cannot help), and a different code, 529 overloaded_error, when "the API experiences high traffic across all users" ({{Anthropic errors|https://platform.claude.com/docs/en/api/errors}}). Your own gateway should keep the same three cases apart: you are over your limit; you are out of budget; we are out of capacity.

What token limits cost
A shared counter (usually Redis) that every gateway copy updates on every request; a decision about what happens when that counter is unreachable (fail open and risk overload, or fail closed and refuse everyone); and limits that customers find harder to reason about than "60 requests a minute". When not to: an internal tool with a handful of users and a monthly budget alert needs no per-tenant token buckets.

6. Multi-tenancy and isolation

A tenant is one customer organisation sharing your system with others. Multi-tenancy is serving them all from shared infrastructure, which is cheap, while keeping each from hurting or seeing the others, which is the work. Four things must be isolated:

  • Capacity. The noisy neighbour: one tenant's burst fills the batch and every other tenant's TTFT rises. Token limits (section 5) cap the average; fair scheduling handles the moment. The Virtual Token Counter scheduler defines fairness by "a cost function that accounts for the number of input and output tokens processed" and gives "a 2× tight upper bound on the service difference between two backlogged clients" while keeping the GPU busy ({{Sheng et al., Fairness in Serving Large Language Models, OSDI 2024|https://www.usenix.org/conference/osdi24/presentation/sheng}}).
  • Data. Prompts and answers must never cross tenants: not in logs, not in caches. A response cache or semantic cache shared across tenants can hand one customer another's answer; even a shared prefix cache is a timing side channel (a fast first token reveals that someone sent the same beginning). OpenAI states "Caches are not shared across organizations" ({{OpenAI prompt caching|https://developers.openai.com/api/docs/guides/prompt-caching}}). Put the tenant id in every cache key.
  • Cost. Every usage event carries the tenant, so each one's bill and margin are known (section 12).
  • Customisation. Tenants may have their own fine-tuned adapters on a shared base model; engines can serve many small adapters on one replica ({{Parameter-Efficient Fine-Tuning|n:3c65c17b0d0d81eba08eef56b3e3b4eb}}).

Real examples of each idea. Priority classes are as old as Google's load shedding: requests are tagged CRITICAL_PLUS, CRITICAL, SHEDDABLE_PLUS ("the default for batch jobs, which can retry requests minutes or even hours later") or SHEDDABLE, and a request's criticality propagates to the calls it makes ({{SRE book, ch. 21, Handling Overload|https://sre.google/sre-book/handling-overload/}}). The Kubernetes inference stack does the same for model traffic: an early version had Critical, Standard and Sheddable; today llm-d's InferenceObjective carries an integer priority, and "flow control will always allow requests of higher priority to be served first", while "Fairness is only enforced and tracked between requests of the same priority" ({{inferenceobjective_types.go, llm-d-router v0.11.0|https://github.com/llm-d/llm-d-router/blob/v0.11.0/apix/v1alpha2/inferenceobjective_types.go}}). Reserved capacity: Anthropic's Priority Tier committed input and output tokens per minute for 1 to 12 months, "targets 99.5% uptime", and "Requests beyond your committed capacity automatically fall back to standard tier"; it is "no longer available for purchase" to new buyers as of October 2026 ({{Anthropic service tiers|https://platform.claude.com/docs/en/api/service-tiers}}).

What isolation costs
Each step down the table buys predictability with idle hardware. Scoping caches per tenant lowers hit rates. When not to: a product with one customer (your own app) has no tenants to isolate; start with a shared pool and per-tenant limits, and add reserved or dedicated capacity only for a customer who pays for it.

7. Three paths: realtime, streaming and batch

Not every model call is a person waiting. Splitting traffic by how long it may wait is the single biggest cost lever after routing, because work that can wait can run when GPUs are idle or cheap.

Batch through providers costs half. OpenAI's Batch API gives a "50% cost discount compared to synchronous APIs" and each batch "completes within 24 hours (and often more quickly)", with its own higher rate limits ({{OpenAI Batch API|https://developers.openai.com/api/docs/guides/batch}}). Anthropic's Message Batches: "All usage is charged at 50% of the standard API prices", "most batches finishing in less than 1 hour", a batch holds up to 100,000 requests or 256 MB, unfinished requests expire after 24 hours and are not billed, and the discount stacks with prompt caching ({{Anthropic batch processing|https://platform.claude.com/docs/en/build-with-claude/batch-processing}}). Between realtime and batch there are now speed tiers on the same API: OpenAI's Flex processing trades "slower response times and occasional resource unavailability" for batch prices, and returns a 429 it does not charge for when capacity is short; its premium tier, renamed from Priority processing to Fast mode on 30 July 2026, charges more per token for up to 2.5 times the speed ({{Flex processing|https://developers.openai.com/api/docs/guides/flex-processing}}, {{Fast mode|https://developers.openai.com/api/docs/guides/fast-mode}}).

Batch on your own GPUs means using the trough. The parent topic's estimate showed that a fleet sized for the busy hour sits more than half idle overnight; a batch lane that fills that idle capacity at low priority, and is pushed aside the moment chat traffic needs the slots, turns idle GPU-hours into useful work. That needs a priority scheduler in the engine or router (the vLLM production stack router has a priority option, section 4) and batch jobs that tolerate being paused. The batch lane is also the natural home for preemptible spot GPUs (section 8).

Long jobs behind a person (generate a report, run an agent for ten minutes) use the parent topic's asynchronous pattern: accept the job, return 202 Accepted with a job id, put it on a queue, and let the client poll or receive a callback. Anthropic itself advises "the streaming Messages API or Message Batches API for long-running requests, especially those over 10 minutes". Delivery guarantees, retries and dead-letter queues for that pattern belong to the sibling page {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}.

What splitting costs
Two or three code paths instead of one, and results that arrive later. A batch lane on shared GPUs needs preemption that really works; a batch job that cannot be paused will hold slots during the morning ramp. When not to: if under a tenth of your tokens can wait, the second path is not worth its code.
