4. Serving shape: batch, online or streaming, and the latency budget

The serving shape follows from one question: who waits for the prediction, and how long? Splitting traffic by that answer is the biggest cost lever after model choice, because work that can wait can run when hardware is idle or cheap.

Batch through providers costs half: OpenAI's Batch API gives a "50% cost discount compared to synchronous APIs" and each batch "completes within 24 hours (and often more quickly)" ({{OpenAI Batch API|https://developers.openai.com/api/docs/guides/batch}}). On your own GPUs, a batch lane at low priority fills the overnight trough of a fleet sized for the busy hour.

The latency budget of one streamed reply

A reply is generated one token at a time, so its latency is two numbers. Time to first token (TTFT) covers arrival, waiting in the engine's queue and prefill (reading all input tokens at once); it is what the user feels as "is it working?". Time per output token (TPOT) is the gap between streamed tokens in decode; vLLM defines it per request as "(end-to-end latency - TTFT) / (number of output tokens - 1)" ({{vLLM metrics design doc, v0.30.0|https://github.com/vllm-project/vllm/blob/v0.30.0/docs/design/metrics.md}}). So end-to-end latency = TTFT + (output tokens − 1) × TPOT.

The user waits 0.09 s for text; the reply takes about 5.9 s, almost all of it decoding

Predict first: doubling the reply from 400 to 800 tokens, what happens to TTFT and to end-to-end time? Then drag.

Derived for Llama 3.3 70B in FP8 on two H100s, the parent topic's shared figures: about 0.09 s of prefill for 1,000 input tokens (at an illustrative 40% of peak arithmetic) with an empty queue, and 4,418 output tokens a second per two-GPU replica shared by 64 conversations (the batch of 64 is the parent's illustrative engine limit), so 69 tokens a second each and a TPOT of 14.5 ms: 0.09 + 399 × 14.5 ms = 5.9 s. TTFT does not move with reply length; queueing (section 7) is what moves it.

  • Tokens per second means two things: per user (1 ÷ TPOT, about 69 here) and per GPU (4,418 ÷ 2 = 2,209 at full load). Bigger batches raise the second and lower the first; every serving decision is a point on that trade-off, and the engine side of it is owned by {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}.
  • A latency target is a pair: a TTFT target and a TPOT target, at a percentile. Chat cares most about TTFT; agents and code tools that read the whole answer care about end-to-end time; batch jobs only about tokens per dollar. For scale, MLPerf Inference sets for Llama 2 70B TTFT 2,000 ms and TPOT 200 ms in its "conversational" category and 450 ms and 40 ms in its "interactive" one ({{MLPerf inference rules, commit d3eba2f|https://github.com/mlcommons/inference_policies/blob/d3eba2f21026d868ad65cdcad2bb81e4a17ce3d3/inference_rules.adoc}}); our 14.5 ms TPOT passes both.
  • Goodput is the highest request rate per GPU at which the latency targets are still met for a chosen share of requests (say 90%), as opposed to raw throughput; DistServe introduced it for LLM serving ({{Zhong et al., OSDI 2024|https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin}}) because a system tuned for raw tokens per second can serve many tokens late.
  • Concurrency follows from latency. Little's law: the average number in a system equals arrival rate times time in the system ({{Little, 50th-anniversary paper|https://people.cs.umass.edu/~emery/classes/cmpsci691st/readings/OS/Littles-Law-50-Years-Later.pdf}}). The chat assistant's 116 messages a second × about 6 seconds = about 700 replies streaming at any moment, 1,400 in the busy hour; a 20 ms web request at the same rate keeps two or three open. Every proxy on the path must pass streams through unbuffered as server-sent events (SSE), data: ... lines on one open HTTP response.
Batch and async details: provider batch terms, speed tiers, long jobs, online serving at DoorDash, embedding services (depth)

Provider batches. Anthropic's Message Batches: "All usage is charged at 50% of the standard API prices", "most batches finishing in less than 1 hour", a batch holds up to 100,000 requests or 256 MB, unfinished requests expire after 24 hours and are not billed, and the discount stacks with prompt caching ({{Anthropic batch processing|https://platform.claude.com/docs/en/build-with-claude/batch-processing}}). OpenAI's batches have their own higher rate limits. Between realtime and batch there are speed tiers on the same API: OpenAI's Flex processing trades "slower response times and occasional resource unavailability" for batch prices, and returns a 429 it does not charge for when capacity is short; its premium tier, renamed from Priority processing to Fast mode on 30 July 2026, charges more per token for up to 2.5 times the speed ({{Flex processing|https://developers.openai.com/api/docs/guides/flex-processing}}, {{Fast mode|https://developers.openai.com/api/docs/guides/fast-mode}}).

A batch lane on your own GPUs needs a priority scheduler in the engine or router (the vLLM production stack router has a priority option; replica routers are compared on {{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}) and batch jobs that tolerate being paused; a batch job that cannot be paused holds slots during the morning ramp. It is also the natural home for preemptible spot GPUs. If under a tenth of your tokens can wait, the second path is not worth its code.

Long jobs behind a person (generate a report, run an agent for ten minutes) use the parent topic's asynchronous pattern: accept the job, return 202 Accepted with a job id, queue it, and let the client poll or receive a callback. Anthropic advises "the streaming Messages API or Message Batches API for long-running requests, especially those over 10 minutes". Delivery guarantees, retries and dead-letter queues belong to {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}.

Online inference with shadowing. DoorDash's Sibyl prediction service fetched features from Redis per prediction, ran shadow predictions for candidate models on the same inputs, and load-tested at "over 100,000 predictions per second" ({{DoorDash Engineering, 29 Jun 2020|https://careersatdoordash.com/blog/doordashs-new-prediction-service/}}).

Embedding services are a throughput problem: many short inputs, batched by tokens. Hugging Face's Text Embeddings Inference (v1.9.4) has "Token based dynamic batching" with --max-batch-tokens (default 16384; "you could fit 10 queries of total_tokens=100 or a single query of 1000 tokens" for a limit of 1,000) and --max-concurrent-requests (default 512), where "Having a low limit will refuse clients requests instead of having them wait for too long and is usually good to handle backpressure correctly" ({{TEI CLI arguments|https://huggingface.co/docs/text-embeddings-inference/en/cli_arguments}}). Embeddings from different models live in different spaces, so changing the embedding model means re-embedding the whole corpus (a batch job, usually written to a new index and switched over once complete; reasoning, not a sourced rule), and the model version belongs in every stored vector's metadata. Smaller vectors are a cost lever: a text-embedding-3-large vector "can be shortened to a size of 256 while still outperforming an unshortened text-embedding-ada-002 embedding with a size of 1536" ({{OpenAI embeddings guide|https://developers.openai.com/api/docs/guides/embeddings}}). Embedding models themselves are owned by {{Topic: rag-and-retrieval|n:3c65c17b0d0d81b89145c37dfe8a3b0b}}.

MLPerf for a reasoning model: DeepSeek-R1 targets are 2,000/80 ms and 1,500/15 ms (same source).

5. Feedback loops and drift: monitoring the loop, not just the service

A web service is correct until its code changes. A model gets worse while nothing changes, in two ways. Its own actions select its next training data (a feedback loop), and the world moves away from the data it learned from (drift). Sculley et al. name both: "A model may directly influence the selection of its own future training data", and "Experience has shown that the external world is rarely stable" ({{Hidden Technical Debt in ML Systems, NeurIPS 2015|https://papers.nips.cc/paper_files/paper/2015/hash/86df7dcfd896fcaf2674f757a2463eba-Abstract.html}}).

The escalation model decides which tickets get labels, so it never learns where it is wrong

Illustrative scores and labels for 24 tickets; a stepper (each step a still), not a simulation.

The same paper describes the harder case, hidden feedback loops, "in which two systems influence each other indirectly through the world", for example one system choosing products to show and another choosing reviews. Rules of ML adds the most common one in ranking, Rule #36, "Avoid feedback loops with positional features": "The position of content dramatically affects how likely the user is to interact with it", so a model trained on clicks learns its own ranking back. For an LLM product the loop runs through prompts and evaluations: replies rated by users who saw them, and evaluation sets drawn from traffic the current model shaped.

Two of Sculley et al.'s checks are cheap and general. Prediction bias: "the distribution of predicted labels is equal to the distribution of observed labels" in a system working as intended; "by no means a comprehensive test", but "a surprisingly useful diagnostic", and slicing it "by various dimensions" isolates issues quickly. Action limits: in systems that act in the world, "set and enforce action limits as a sanity check", which alert when hit. For LLMs the outcome layer is the one that matters most, because failures are fluent: in August 2025 a routing bug sent some Claude Sonnet 4 requests to servers configured for a different context length; at the worst hour 16% of Sonnet 4 requests were affected, error rates stayed normal, and users noticed before the evaluations did. Anthropic's lesson: "The evaluations we ran simply didn't capture the degradation users were reporting", and it now runs quality evaluations "continuously on true production systems" ({{Anthropic, 17 Sep 2025|https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues}}; the parent topic's Case files, "Three serving bugs quietly made Claude's answers worse").
