2. Anatomy of one LLM request, and the numbers that describe it

Follow one message from the chat assistant through the system. Each phase has its own number, and each number has its own fix, so a pro never says "latency" about an LLM service without saying which one.

1. Arrivenetwork, API server, gateway checks: milliseconds
→
2. Waitin the engine's queue until a batch slot frees: 0 when there is room, unbounded when there is not
→
3. Prefillthe model reads all input tokens at once; ends with the first output token
→
4. Decodeone token per step, each streamed to the user
→
5. Finishstop token or max_tokens; usage recorded
  • Time to first token (TTFT): from sending the request to receiving the first output token. Phases 1 to 3. It is what the user feels as "is it working?", and it is where queueing shows up first.
  • Time per output token (TPOT), also inter-token latency (ITL): the gap between streamed tokens in phase 4. vLLM defines the per-request TPOT as "(end-to-end latency - TTFT) / (number of output tokens - 1)" ({{vLLM metrics design doc, v0.30.0|https://github.com/vllm-project/vllm/blob/v0.30.0/docs/design/metrics.md}}); ITL is measured gap by gap, and the two differ when a step emits several tokens at once (speculative decoding, owned by {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}).
  • End-to-end latency = TTFT + (output tokens − 1) × TPOT. For the chat assistant: about 0.09 s of prefill (derived for 1,000 input tokens on two H100s at an illustrative 40% of peak arithmetic, as in the parent's Scale simulator) plus 399 × 14.5 ms = about 5.9 seconds, of which the user waits only the first 0.09 s before text appears.
  • Tokens per second, which means two different things: per user (1 ÷ TPOT, about 69 here) and per GPU (4,418 ÷ 2 = 2,209 at full load). Bigger batches raise the second and lower the first. Every serving decision is a point on that trade-off.
  • Cost per request: tokens in and out times their prices, or GPU-seconds times the GPU price. It belongs on the same dashboard as latency (section 12).

The engine reports these directly. In vLLM v0.30.0 (released 2026-09-22) the Prometheus metrics a system designer reads are vllm:num_requests_waiting ("Number of requests waiting to be processed"), vllm:num_requests_running ("Number of requests in model execution batches"), vllm:kv_cache_usage_perc ("KV-cache usage. 1 means 100 percent usage", a fraction despite the name), and the histograms vllm:time_to_first_token_seconds, vllm:inter_token_latency_seconds and vllm:e2e_request_latency_seconds ({{vllm/v1/metrics/loggers.py at v0.30.0|https://github.com/vllm-project/vllm/blob/v0.30.0/vllm/v1/metrics/loggers.py}}). Names change between versions: vllm:gpu_cache_usage_perc was renamed to vllm:kv_cache_usage_perc in 0.9.2 and removed in 0.12, and vllm:time_per_output_token_seconds gave way to vllm:inter_token_latency_seconds in 0.11. Dashboards and autoscalers that query the old names go silent after an upgrade, which is a real way to lose autoscaling.

The KV cache in that list is the engine's memory of each conversation: for every token so far, the model keeps intermediate results (keys and values) so it need not recompute them for the next token. It lives in GPU memory and grows with every token, so it caps how many conversations a replica can hold at once. For this model it is 2 × 80 layers × 8 key-value heads × 128 dimensions × 1 byte = 160 KiB per token (from the model's config; FP8 cache), so one 1,400-token conversation holds about 219 MiB. How engines manage it is the subject of the {{PagedAttention paper page|n:3c65c17b0d0d81bf8b90ca93fee19f5f}}; a system designer needs only to know that "KV cache full" means "no room for more conversations on this replica".

Targets you will meet
A latency target for an LLM service is a pair: a TTFT target and a TPOT target, usually at a percentile (p50, p99). Chat products care most about TTFT; agents and code tools that read the whole answer care about end-to-end time; batch jobs care only about tokens per dollar. For scale, the industry benchmark MLPerf Inference sets, for Llama 2 70B, TTFT 2,000 ms and TPOT 200 ms in its "conversational" category and 450 ms and 40 ms in its "interactive" one; for DeepSeek-R1, 2,000/80 ms and 1,500/15 ms ({{MLPerf inference rules, commit d3eba2f|https://github.com/mlcommons/inference_policies/blob/d3eba2f21026d868ad65cdcad2bb81e4a17ce3d3/inference_rules.adoc}}). Our chat example's 14.5 ms TPOT would pass the strictest of these; its TTFT depends on the queue, which is the whole of section 8. Goodput is the highest request rate per GPU at which the latency targets are still met for a chosen share of requests (say 90%), as opposed to raw throughput; DistServe introduced it for LLM serving ({{Zhong et al., OSDI 2024|https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin}}) because a system tuned for raw tokens per second can serve many tokens late.

3. The LLM gateway: one front door for every model call

The problem appears
The first feature calls a model API directly from the app with a key in an environment variable. By the fifth feature there are five copies of retry logic, three provider keys in three services, no idea which team spent $40,000 last month, no way to switch providers during an outage, and a customer's personal data going to a vendor nobody approved.

An LLM gateway is a service that every model call in the company passes through. Your code calls the gateway with one API shape (almost always OpenAI's chat completions format); the gateway calls the actual model. It is the parent topic's load balancer and API gateway idea, specialised for model traffic. In the order a request meets them, its jobs are:

  1. Authenticate: who is calling (a team, a service, a customer), from a gateway-issued key, so provider keys live in one place.
  2. Authorise: may this caller use this model? (Some data may go only to approved vendors or to self-hosted models.)
  3. Check limits and budget: tokens per minute and money per month (section 5).
  4. Transform and guard: redact personal data, apply input guardrails ({{Guardrails|n:3c65c17b0d0d819bbfa5dffa9246c297}}).
  5. Look up caches (section 9).
  6. Route: pick the model and the deployment (section 4).
  7. Call, with a timeout, retry or fall back on failure (sections 4 and 11).
  8. Stream the reply back unbuffered.
  9. Meter: write one usage event (caller, model, input, cached and output tokens, cost, latency) for billing and dashboards (section 12).

What it looks like in production

Uber built its GenAI Gateway as "a Go service that acts as an encompassing layer around the clients for third-party vendors", and "a pivotal design decision was to mirror the HTTP/JSON interface of the OpenAI API". It includes "a PII redactor that anonymizes sensitive information within requests before forwarding them to third-party vendors" (PII: personally identifiable information), and audit logs used for "cost attribution, security audit purposes, quality evaluation". In mid-2024 it was "used by close to 30 customer teams and serves 16 million queries per month, with a peak QPS of 25" ({{Uber Engineering, 11 Jul 2024|https://www.uber.com/blog/genai-gateway/}}). Note how small 25 queries a second is: the gateway exists for control, not for throughput. Bloomberg and Tetrate started Envoy AI Gateway because "traditional rate-limiting based on number of requests doesn't work for controlling usage of LLM providers" ({{Envoy AI Gateway announcement, 18 Oct 2024|https://github.com/theagentrouter/agent-router/blob/v1.1.0/site/blog/2024/2024-10-18-introducing-envoy-ai-gw.md}}). Chip Huyen's AI Engineering (O'Reilly, 2025) puts "Add Model Router and Gateway" as step 3 of its five-step platform architecture, after enhancing context and adding guardrails and before caches ({{book table of contents|https://github.com/chiphuyen/aie-book/blob/main/ToC.md}}, chapter 10).

Two lessons. A retry before a fallback costs seconds of TTFT, almost all of it backoff, so the order "retry, then fall back" is a latency decision. And spend is computed from a price table shipped with the library: in 1.104.0's bundled copy the newest Claude model is Sonnet 4.5 at $3 and $15 per million tokens, so cost accounting is only as current as that table (LiteLLM can fetch it at start-up, or take your own prices).

What a gateway costs
One more network hop (milliseconds, small against seconds of generation), one more service that must not go down (run several copies behind a load balancer, keep it stateless, keep its own dependencies like Redis for counters off the critical path when they fail), and the risk that it buffers streams or caps connection times. It also concentrates power: whoever owns it decides which models the company may use, which is usually the point.

When not to build one: a single product calling a single provider, owned by one team. A client library with retries and a usage log is enough until a second model, a second team or a budget question appears.

4. Routing, fallbacks and model tiers

A router decides, for each request, which model and which copy of it serves the request. Routing happens at two levels that are easy to confuse.

Level 1: which model (the gateway's decision)

  • Tier routing. Send easy requests to a small, cheap model and hard ones to a large model. Prices differ by a factor of 2 to 40 between tiers of the same vendor (Claude 4.5 Haiku at $1/$5 per million input/output tokens, Sonnet 5.5 at $2/$10, Opus 5.5 at $4/$20; GPT-6 Luna at $0.10/$0.50; knowledge base price snapshot of 2026-10-01). The router is usually a rule ("summaries go small") or a small classifier; Huyen describes "an intent classifier that predicts what the user is trying to do" so "simpler queries" go "to cheaper models" ({{Building A Generative AI Platform, 25 Jul 2024|https://huyenchip.com/2024/07/25/genai-platform.html}}). The cost: a misrouted hard question gets a worse answer, which no error counter sees. Measure the router as a classifier, on labelled traffic.
  • Context routing. Long prompts go to models or pools configured for long context. Getting this wrong is exactly Anthropic's August 2025 bug (section 1).
  • Policy routing. Tenant pinning (a customer contracted for one vendor), region and data-residency rules, and "self-hosted only" for sensitive data.
  • Fallbacks. When the chosen model fails: another deployment of the same model, the same model at another provider (Claude is also sold through AWS Bedrock and Google Vertex AI; open models through many), or a different model. Fallbacks must be planned like a backup generator: is the fallback's quota big enough to take all the traffic, does it understand the same prompt and tool format, and does it have the same safety behaviour? A fallback provider also starts with a cold prompt cache (section 9), so it costs more per request at first.

Level 2: which replica (inside a self-hosted pool)

Below the gateway, a pool of identical replicas still needs a load balancer, and round robin is a poor one for LLMs: requests differ wildly in size, and a replica that already holds a conversation's prefix in its KV cache can skip most of its prefill. LLM-aware load balancers score each replica on its queue, its KV cache use and how much of the prompt it already has cached. Examples, all open source:

  • The vLLM production stack router (Helm chart vllm-stack-0.1.13, 29 Sep 2026) offers roundrobin, session, prefixaware, kvaware, loadaware and others; its load-aware rule is "score(i) = matched_tokens(i) / prompt_tokens - beta * relative_load(i)", so "a warm-but-saturated instance can lose to a cold-but-idle one" ({{routing_logic.py at vllm-stack-0.1.13|https://github.com/vllm-project/production-stack/blob/vllm-stack-0.1.13/src/vllm_router/routers/routing_logic.py}}).
  • Kubernetes' Gateway API Inference Extension (v1.6.2) replaces a plain Kubernetes Service with an InferencePool, "an extensible request scheduling algorithm that is kv-cache and request cost aware" ({{README at v1.6.2|https://github.com/kubernetes-sigs/gateway-api-inference-extension/blob/v1.6.2/README.md}}); its endpoint picker now lives in llm-d, whose scorers include KV cache utilisation ("score = 1 - kvCacheUsagePercent"), queue depth and prefix-cache match ({{llm-d scheduling docs, v0.10.0|https://github.com/llm-d/llm-d/blob/v0.10.0/docs/architecture/core/router/epp/scheduling.md}}). llm-d reports "3x higher output throughput and 2x faster TTFT with prefix-cache-aware routing vs round-robin" on its benchmark (vendor claim, Llama 3.1 70B on 4 MI300X).
  • Character.AI routes all messages of one dialogue to the same server ("sticky sessions") so its cached KV state is reused between turns (parent topic's Case files, "20,000 LLM queries a second").

Stickiness has a price: it concentrates load and it concentrates harm. In Anthropic's postmortem, "some users were affected more severely, as our routing is 'sticky'": a user routed to a bad server kept going back to it. How these engines and schedulers work inside belongs to {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}; the system designer's job is to know that the replica-level balancer must see queue and cache state, and to pick one that does.

What routing costs
A tier router saves money in proportion to the share of easy traffic and loses quality in proportion to its mistakes; the {{Gateway lab|#t-gw}} lets you put numbers on both. Fallbacks add latency (detection plus retries, 2.9 s in the LiteLLM run above) and need standing capacity elsewhere. Sticky and cache-aware routing raise throughput and make load uneven. When not to: one model that is cheap enough and good enough needs no tier router; a pool of two replicas does not need a KV-aware scheduler.
