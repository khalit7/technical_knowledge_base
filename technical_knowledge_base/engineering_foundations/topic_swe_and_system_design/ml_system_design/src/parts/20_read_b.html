2. The data loop: features, two paths, and training-serving skew

The escalation model reads features, numbers computed from data such as "tickets this customer opened in the last 7 days". Each feature is computed twice: offline, for every historical training row, from the warehouse; and online, for the live ticket, in milliseconds. Uber's Michelangelo is the reference picture of the two paths: online features "precomputed and stored in Cassandra where they can be read at low latency", serving at "P95 latency of less than 5 milliseconds" without stored features and "less than 10ms" with them ({{Uber Engineering, Meet Michelangelo, 5 Sep 2017|https://www.uber.com/blog/michelangelo-machine-learning-platform/}}). Two code paths for one number is where the classic ML bug lives.

The same ticket, the same feature name, two different numbers, and nothing raises an error

Illustrative values. The definitions differ the way real ones do: a calendar-day window in UTC against a rolling 168 hours, and a nightly job that has not yet seen today.

Google's Rules of ML define training-serving skew as "a difference between performance during training and performance during serving", caused by "A discrepancy between how you handle data in the training and serving pipelines", "A change in the data between when you train and when you serve", or "A feedback loop between your model and your algorithm" (the last is section 5). Three rules fix the first two causes ({{Rules of ML|https://developers.google.com/machine-learning/guides/rules-of-ml}}):

  • Rule #32: "Re-use code between your training pipeline and your serving pipeline whenever possible."
  • Rule #29: "save the set of features used at serving time, and then pipe those features to a log to use them at training time". YouTube's home page did this "with significant quality improvements and a reduction in code complexity".
  • Rule #31: "Beware that if you join data from a table at training and serving time, the data in the table may change"; "The easiest way to avoid this sort of problem is to log features at serving time".

A feature store productises Rule #32: features are defined once, computed into an offline store for training and an online store for serving, and read through one API. Its key guarantee is point-in-time correctness: a training example labelled at 8:50 must only see feature values known at 8:50, not ones computed at 8:52, or the model learns from the future and disappoints in production ({{Databricks docs, point-in-time joins|https://docs.databricks.com/aws/en/machine-learning/feature-store/time-series}}). How feature stores work (Feast's offline and online calls, materialisation, the point-in-time join) is owned by {{ML platforms and workflows|n:3c65c17b0d0d81b9943cf6c72600f96b}}, section 9; a point-in-time join measured in DuckDB, with the leak it prevents, is section 11 of {{Analytics: columnar engines, DuckDB and the lakehouse|n:3ef5c17b0d0d8157814ec5dd8a0d4fb5}}.

LLM products have skew too, with prompts in place of features: a prompt template assembled differently in the evaluation harness and in production, a retrieval index rebuilt between evaluation and launch, a tokenizer or chat-template version mismatch. Rule #29 transfers directly: log the exact prompt the model saw, and evaluate on logged prompts.

Michelangelo at scale, and Chronon's consistency check (depth)

Michelangelo in 2017 had "approximately 10,000 features in Feature Store", "the highest traffic models right now serving more than 250,000 predictions per second", and offline models wrote predictions "back to Hive" for other jobs to read. By 2024 there were "more than 5K models in production, serving 10 million real-time predictions per second at peak", and the platform had added a Gen AI Gateway with logging, cost attribution and PII redaction ({{Uber, From predictive to generative AI, 2 May 2024|https://www.uber.com/blog/from-predictive-to-generative-ai/}}).

Airbnb's Chronon (open-sourced 2024 with Stripe as co-maintainer) lets teams "define their features only once, powering both offline flows for model training as well as online flows for model inference", and measures consistency by comparing logged online fetches with backfilled values ({{Airbnb Engineering|https://medium.com/airbnb-engineering/chronon-airbnbs-ml-feature-platform-is-now-open-source-d9c4dba859e8}}): Rule #37's third gap (section 3), measured per feature. Feast (v0.66.0) likewise "ensures point-in-time correctness so future feature values do not leak to models" ({{Feast quickstart|https://docs.feast.dev/getting-started/quickstart}}).

3. Offline evaluation against online metrics

An offline score is measured on stored data; the decision to ship is about live traffic. Rules of ML, Rule #37 ("Measure Training/Serving Skew"), splits the distance between them into gaps, each with its own meaning. Adding the gap to the product goal from section 1 gives four.

Each step down is a different problem; only the third is a bug
  1. Training to holdout: "In general, this will always exist, and it is not always bad."
  2. Holdout to next-day: "Again, this will always exist"; tune regularisation for next-day performance, and "large drops in performance between holdout and next-day data may indicate that some features are time-sensitive and possibly degrading model performance."
  3. Next-day to live: "If you apply a model to an example in the training data and the same example at serving, it should give you exactly the same result. Thus, a discrepancy here probably indicates an engineering error": skew, section 2.
  4. Live metric to product goal: the proxy gap of the metric ladder; only an online experiment measures it.

Quotes from {{Rules of ML|https://developers.google.com/machine-learning/guides/rules-of-ml}}, Rule #37. Bar heights are schematic: the rule names the gaps, not their sizes.

For an LLM the offline set is a set of past tickets scored by tests, graders or judges, and it is a statistic, not a test suite: models sample, and even at temperature zero serving engines are not deterministic, because the numerical result of a matrix multiplication depends on how many other requests share the batch. Thinking Machines sampled the same prompt 1,000 times at temperature 0 from Qwen3-235B and got 80 different completions; with batch-invariant kernels all 1,000 were identical, at a cost in speed ({{Thinking Machines, 10 Sep 2025|https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/}}).

So a change ships in stages, each answering a question the one before cannot. A "change" is any of: a new model or provider version, a prompt, sampling parameters, an engine version or GPU type (Anthropic's postmortem shows the same model behaving differently on different hardware stacks), or a router.

0. Pin and versionmodel snapshot, prompt, parameters and router in versioned config, recorded in every usage event; rollback is a config change
→
1. Offline gateis it better on stored cases? (gaps 1 and 2)
→
2. Shadowlive inputs, answers thrown away: same quality, latency, cost? (gap 3)
→
3. Canary1%, 5%, 25%, 100% of real traffic, keyed by user or tenant: is it safe?
→
4. A/B testa fixed split long enough to measure users: is it better? (gap 4)

The statistics of each stage (how much traffic, for how long, which test) and golden sets and CI gates are owned by {{Production eval engineering|n:3c65c17b0d0d81b39ad9e96193d21adc}}; the offline regression suite by the sibling {{Testing and quality|n:3c65c17b0d0d81548848e2ebdd2f63ee}}. Staged rollout costs days instead of minutes per change, shadow compute, and two versions in production at once (two prompt caches, two sets of GPUs if self-hosted); internal tools and prototypes can switch at once behind a flag, anything customers depend on cannot.

The rollout machinery: Istio mirroring, KServe and Argo canaries (depth)

Shadow. Service meshes do the copying: Istio's mirror with mirrorPercentage sends requests "as 'fire and forget,' which means that the responses are discarded" ({{Istio docs, mirroring|https://istio.io/latest/docs/tasks/traffic-management/mirroring/}}), so the shadow service must log its own outputs. Shadowing doubles model cost for the mirrored share: mirror a sample, and never mirror requests with side effects (tool calls that send email or charge cards). Compare quality on sampled pairs with judges.

Canary. KServe does it with one field: canaryTrafficPercent: 10 on the predictor; set it to 0 to roll back ({{KServe canary example|https://kserve.github.io/website/docs/model-serving/predictive-inference/rollout-strategies/canary-example}}). Argo Rollouts (v1.10.0) adds analysis steps that "block the rollout until the run is completed" and a successCondition such as result[0] >= 0.95 on a Prometheus query ({{Argo Rollouts analysis|https://argo-rollouts.readthedocs.io/en/stable/features/analysis/}}). Key the split by user or tenant so one conversation stays on one version.

Pinning. Use a dated model snapshot, not an alias the provider moves: otherwise quality changes overnight with no deploy to roll back.
