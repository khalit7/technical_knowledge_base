The idea in one screen

The core idea
An ML system is designed backwards from the decision the model makes: an objective with a metric and a baseline to beat, then one loop in which the product's logged outcomes become training data and training and serving compute the same inputs, a serving shape chosen by the latency and cost budget, and monitoring for the moment the world or the model's own actions change that data.
Training and serving are two lanes of one loop; most failures live where the lanes meet

Numbers are this page's sections. The dashed links are where the lanes must agree: the same feature values (2, training-serving skew) and the same verdict offline and online (3). The red loop is what makes ML systems unlike other software: the model's actions decide what gets logged, so they decide its next training data (5). The model box is where the serving shape and budget are chosen (4) and, for an LLM product, where prompt, retrieval, fine-tuning or an agent go (6).

The running example is a support assistant sold to 10,000 business tenants: an LLM answers customers' tickets, and a small classifier, the escalation model, decides which tickets a human should take. Its latency figures use the parent topic's chat-assistant shape (1,000 input and 400 output tokens per reply, from the {{Scale simulator|n:3c65c17b0d0d81048ae0dd14ac399b4d}}); its cost figures use the support shape of section 6.

Objective, metric, baseline: what the product wants, how it is counted, and the simple thing the model must beat (section 1).
Offline and online metric: measured on stored data before launch, and on live traffic after it.
Feature: a number computed from data and given to a model.
Training-serving skew: the model sees different inputs, or behaves differently, in serving than in training.
Point-in-time correctness: a training row sees only values known at its own time.
Batch scoring, online inference: predictions precomputed on a schedule, or computed inside the request.
TTFT, TPOT: time to the first output token; time per output token after it.
Feedback loop: the model's own outputs shape its future training data.
Drift: the inputs or the input-to-label relation move away from what the model was trained on.

1. Frame the problem: objective, metric, baseline

Before any model: what decision is being automated, how will anyone know it got better, and what is the cheapest thing that already does it? For the support assistant the decision is "answer this ticket, or hand it to a human". Every metric the system will ever report sits on one ladder under that decision.

Each rung is a proxy for the rung above; design starts at the top

The support assistant's ladder. A model can climb the offline metric while the objective falls: an assistant that answers more tickets alone scores well on "resolved without escalation" and badly on wrong answers, which is why guard metrics sit beside the online metric. System metrics (latency, cost) are requirements, not goals; section 4 sets their budget.

  • Objective, in the product's words. Google's Rules of ML, Rule #39: "Launch decisions are a proxy for long-term product goals"; its example team must "care about engagement, 1 day active users (DAU), 30 DAU, revenue, and advertiser's return on investment", and a model that wins its own metric can still be blocked because "the number of daily active users drops by 5%" ({{Rules of ML|https://developers.google.com/machine-learning/guides/rules-of-ml}}).
  • Metrics first. Rule #2: "First, design and implement metrics", because "Before formalizing what your machine learning system will do, track as much as possible in your current system." The logging that measures the baseline is also the data the first model will train on.
  • Baseline. Rule #1: "Don't be afraid to launch a product without machine learning"; "If machine learning is not absolutely required for your product, don't use it until you have data", and "If you think that machine learning will give you a 100% boost, then a heuristic will get you 50% of the way there." Rule #3 then says when to switch: "A simple heuristic can get your product out the door", but "A complex heuristic is unmaintainable". For the escalation model the baseline is a rule (escalate billing and legal tickets); for the LLM it is one prompt on a small model (section 6).
  • Keep the first model simple. Rule #4: "Keep the first model simple and get the infrastructure right." The first launch tests the loop of the hero figure; later launches improve the model inside it.
How the classic interview books frame it (provenance)

Chip Huyen's booklet uses project setup, data pipeline, modelling and serving ({{Machine Learning Systems Design|https://huyenchip.com/machine-learning-systems-design/toc.html}}); Aminian and Xu's Machine Learning System Design Interview (ByteByteGo, 2023) is commonly summarised as seven steps (clarify requirements, frame as an ML task, data, model, evaluation, deployment and serving, monitoring; the course page is behind a login, so that list is unconfirmed here). Both start where this section does. The deeper warning behind "get the infrastructure right" is Sculley et al.'s "Hidden Technical Debt in Machine Learning Systems": a mature system might be "(at most) 5% machine learning code and (at least) 95% glue code", and "Changing Anything Changes Everything" ({{NeurIPS 2015|https://papers.nips.cc/paper_files/paper/2015/hash/86df7dcfd896fcaf2674f757a2463eba-Abstract.html}}).
