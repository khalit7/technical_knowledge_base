You have already put a model behind an API: a web framework, a POST /predict route, the model loaded in memory, an answer returned. That is the right start. This page is what changes when that endpoint is a large language model (LLM) serving many customers: each request costs about a thousand times more than an ordinary web request, runs for seconds, streams, gives different answers each time, and needs GPUs that come in large, slow-to-start blocks. Most of the design of an LLM service is a response to those five facts.

The running example is the parent topic's: a chat assistant with ten million registered users, one million of them active on a given day, ten messages each, about 1,000 input and 400 output tokens per message. Assumption used throughout this page: these are the parent page's {{Scale simulator|n:3c65c17b0d0d81048ae0dd14ac399b4d}} defaults (1,000 input / 400 output tokens per reply), kept here so the numbers line up; the parent's Reading estimate in Step 6 rounds the reply to 500 tokens. That averages 116 messages a second and about 230 in the busy hour (peak factor 2, illustrative). The parent page drew its GPU layer as two boxes, "model router" and "GPU pools". This page opens those boxes.

The one idea to keep
Count tokens, not requests. Cost, GPU capacity, rate limits, autoscaling signals and latency are all set by how many tokens go in and come out, and two requests can differ in tokens by a factor of a thousand. Most mistakes in LLM service design come from carrying the request-counting habits of web services across.

1. From your model endpoint to a production service: what is different

Start from what you built: one process, one model, one request at a time. Ask what happens when ten thousand people call it in the same minute. Six things break that do not break for an ordinary CRUD service (Create, Read, Update, Delete: the web services that store and fetch records, like most of the parent topic's chat app).

It is expensive: a thousand times a web request

The parent topic prices an app server (AWS m7i.xlarge) at $0.2016 an hour. At an illustrative 500 requests a second per server, one web request costs $0.2016 ÷ 3,600 ÷ 500 = $0.00000011. Now one chat reply of 400 output tokens:

  • Self-hosted, Llama 3.3 70B in 8-bit floating point (FP8) on H100 GPUs at $3.99 per GPU-hour ({{Lambda pricing|https://lambda.ai/pricing}}, read 2026-10-04), producing 2,209 output tokens a second per GPU at maximum load ({{TensorRT-LLM perf overview at commit 8a9c66c|https://github.com/NVIDIA/TensorRT-LLM/blob/8a9c66ce086594054d3722307cfed2d658d25e60/docs/source/developer-guide/perf-overview.md}}, vendor benchmark, 1,000 input and 1,000 output tokens per request; the parent topic's shared figure), run at half that rate to keep latency acceptable (the parent topic's derating, illustrative): $3.99 ÷ 3,600 ÷ (2,209 × 0.5) = $1.00 per million output tokens, so $0.0004 per reply, about 3,600 times the web request.
  • Through an API, Claude Sonnet 5.5 at $2 per million input tokens and $10 per million output tokens ({{Anthropic pricing|https://platform.claude.com/docs/en/about-claude/pricing}}, via the knowledge base's price snapshot of 2026-10-01): 1,000 × $2 + 400 × $10, per million, = $0.006, about 54,000 times.

That is 3.6 to 4.7 orders of magnitude; a 100,000-token document sent to a frontier model reaches 6. The old version of this page said "3 to 6 orders of magnitude above a CRUD call": the arithmetic agrees. The consequence is that cost is an architecture problem. Who may spend how much (quotas), which model a request deserves (routing), and which work need not be done twice (caching) are designed up front, not tuned later.

It is long, and it streams

A reply is generated one token (a word or part of a word) at a time. With 64 conversations sharing one copy of the 70B model on two GPUs, each gets about 69 tokens a second (4,418 ÷ 64; the batch of 64 is the parent's Scale simulator's illustrative engine limit), so a 400-token reply takes about 6 seconds. Users will not stare at a blank screen for 6 seconds, so the reply is streamed: sent token by token over one open HTTP response, usually as server-sent events (SSE), a text format where the server writes data: ... lines as they are ready. Every layer between the user and the GPU (load balancer, gateway, proxy) must pass the stream through without buffering it, and must allow connections that stay open for minutes.

Long requests also multiply how many are open at once. Little's law says the average number in a system equals arrival rate times time in the system ({{Little, 50th-anniversary paper|https://people.cs.umass.edu/~emery/classes/cmpsci691st/readings/OS/Littles-Law-50-Years-Later.pdf}}). For the chat assistant: 116 messages a second × about 6 seconds = about 700 replies streaming at any moment on an average day, 1,400 in the busy hour. A web request of 20 ms at the same rate keeps two or three open.

Its size is unknown until it ends

A web request's cost is roughly known when it arrives. An LLM request's input is known, but its output length is decided by the model, from 1 token to the max_tokens cap. This one fact breaks two web habits: limiting customers by requests per minute (one request can be a thousand times another) and scaling servers on request rate (section 8 shows a pool sized on requests falling behind when replies get longer).

It does not give the same answer twice

Models sample: at temperature above zero the next token is drawn at random from the model's probabilities. Even at temperature zero, serving engines are not deterministic, because the numerical result of a matrix multiplication depends on how many other requests share the batch. Thinking Machines sampled the same prompt 1,000 times at temperature 0 from Qwen3-235B and got 80 different completions; with batch-invariant kernels all 1,000 were identical, at a cost in speed ({{Thinking Machines, 10 Sep 2025|https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/}}; detail on the {{Production eval engineering|n:3c65c17b0d0d81b39ad9e96193d21adc}} page). So "the tests pass" cannot tell you a new model or prompt is safe to ship: correctness is a statistic over many requests (section 10).

Capacity comes in big blocks that start slowly

The 70B model's FP8 weights are 72.7 GB ({{model files on Hugging Face|https://huggingface.co/nvidia/Llama-3.3-70B-Instruct-FP8}}; sum of the weight files, as in the parent's Scale simulator). One 80 GB H100 holds them with little room left for conversations, so a replica (one running copy of the model) spans two GPUs, and capacity grows two GPUs at a time; AWS rents H100s eight to a machine (p5.48xlarge, $55.04 an hour on demand, {{Vantage's AWS price mirror|https://instances.vantage.sh/aws/ec2/p5.48xlarge}}, read 2026-10-04). A new replica must get a GPU machine, download its software image, copy 73 GB of weights into GPU memory and warm up before it serves anyone: a cold start. vLLM's maintainers list what a cold start pays even when weights load instantly: memory allocator setup, recording CUDA graphs (pre-recorded GPU work sequences), compiling GPU kernels, and first-request warm-up, and put a full model reload at "30-100+ seconds per switch" ({{vLLM blog, sleep mode, 26 Oct 2025|https://vllm.ai/blog/2025-10-26-sleep-mode}}). Add finding and booting a GPU machine and minutes are normal. A web server starts in seconds; a GPU replica cannot be added the moment a spike arrives (section 8).

It fails quietly

A broken web service returns errors that a dashboard counts. A broken model service often returns fluent, wrong answers with status 200. In August 2025 a routing bug sent some Claude Sonnet 4 requests to servers configured for a different context length; at the worst hour 16% of Sonnet 4 requests were affected, error rates stayed normal, and users noticed before the evaluations did (the parent topic's {{Case files|n:3c65c17b0d0d81048ae0dd14ac399b4d}} tab, "Three serving bugs quietly made Claude's answers worse"; {{Anthropic, 17 Sep 2025|https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues}}). Monitoring must include quality (section 12).

What this costs you as a designer
Every habit from web services needs checking: count tokens, not requests; expect seconds, not milliseconds; budget money per request; treat "200 OK" as necessary, not sufficient. The rest of the page builds the system that does this, box by box.
