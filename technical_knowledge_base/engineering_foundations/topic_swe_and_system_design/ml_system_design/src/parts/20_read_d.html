8. Autoscaling GPUs

Autoscaling adds replicas when load rises and removes them when it falls. On Kubernetes, the system most model services run on, the built-in Horizontal Pod Autoscaler (HPA) does it with one formula: "desiredReplicas = ceil[currentReplicas * (currentMetricValue / desiredMetricValue)]", checked every 15 seconds by default, ignoring changes within a 10% tolerance, adding at most "4 pods or a 100% of the currently running replicas" per 15 seconds, and waiting 300 seconds before scaling down so a short dip does not throw capacity away ({{Kubernetes docs, Horizontal Pod Autoscaling|https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/}}). With several metrics it computes a replica count for each and takes the largest. The whole question is which metric.

Why the web-service signals fail on GPUs

  • CPU utilisation, the default for web servers, barely moves: the CPU of a GPU server mostly tokenises text and schedules the GPU. Google's GKE guide: "For inference workloads running on GPUs, we don't recommend CPU and memory utilization as the only indicators". The parent topic's Slack case shows the same trap on ordinary servers: threads waiting on a congested network used less CPU, so the autoscaler removed servers during the overload (Case files, "The first Monday of the year: autoscaling made it worse").
  • GPU utilisation "Measures the duty cycle, which is the amount of time that the GPU is active" but "Does not measure how much work is being done while the GPU is active". GPU memory is worse: engines like vLLM reserve almost all GPU memory at start, so the metric "only works for scaling up, and won't scale down when traffic decreases" ({{GKE, Best practices for autoscaling LLM inference workloads with GPUs|https://cloud.google.com/kubernetes-engine/docs/best-practices/machine-learning/inference/autoscaling}}, updated 2026-10-02).
  • Requests per second ignores request size (section 1). NVIDIA's Dynamo documentation puts it plainly: "Latency depends on request content, not just request count. A single request with a 32K-token prompt consumes orders of magnitude more compute than a short one" ({{Dynamo Planner overview, v1.5.0|https://github.com/ai-dynamo/dynamo/blob/v1.5.0/docs/fern/pages/developer-guide/knowledge-base/modular-components/planner/overview.md}}).

The signals that work

  • Queue depth (vllm:num_requests_waiting): requests that have arrived but have no batch slot. GKE: "Queue size directly correlates to request latency" and is "largely workload-agnostic, because queue size is independent of request size, model, or hardware"; continuous batching keeps the queue near zero while there is room, so "use the growth point as a signal to initiate scale-up", starting with a threshold "between 3-5" per replica.
  • Batch size (vllm:num_requests_running): for tighter latency, since it reacts before a queue forms; harder to tune because the right value depends on request sizes.
  • KV cache use (vllm:kv_cache_usage_perc): how full the conversation memory is; near 100% the engine must refuse or evict. llm-d's recommended KEDA setup scales on both waiting requests (threshold 20) and KV cache use (threshold 0.95) per prefill or decode role ({{llm-d-autoscaling blueprint at 3c06c88|https://github.com/llm-d/llm-d-autoscaling/blob/3c06c8814bcde4f7da0c7b4fadeed015e135a9de/README.md}}); GKE's page does not mention KV cache.
  • Tokens in flight or a latency target: Dynamo's planner can "Target specific TTFT/ITL SLA values" and runs a predictive loop (default every 180 s) for the daily curve under a reactive one (every 5 s) for surprises.

Real configuration. KServe (v0.21.0) hands autoscaling to KEDA, an add-on that feeds outside metrics such as Prometheus queries to the HPA. Its documented example scales a vLLM server on running requests, two per replica:

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: huggingface-qwen
  annotations:
    serving.kserve.io/deploymentMode: "Standard"
    serving.kserve.io/autoscalerClass: "keda"
spec:
  predictor:
    model:
      modelFormat: {name: huggingface}
      storageUri: "hf://Qwen/Qwen2.5-0.5B-Instruct"
      resources: {limits: {nvidia.com/gpu: "1"}}
    minReplicas: 1
    maxReplicas: 5
    autoScaling:
      metrics:
        - type: External
          external:
            metric:
              backend: "prometheus"
              serverAddress: "http://prometheus.istio-system.svc.cluster.local:9090"
              query: vllm:num_requests_running
            target: {type: Value, value: "2"}

Trimmed from {{KServe docs, LLM autoscaling with KEDA|https://kserve.github.io/website/docs/model-serving/generative-inference/autoscaling}} (source at kserve/website 71c8b22): "if our LLM receives 6 concurrent requests with our target of 2 requests per pod, the system will scale to 3 replicas". The vLLM production stack's KEDA tutorial does the same on vllm:num_requests_waiting with a threshold of 5 ({{tutorial 20, at 014d070|https://github.com/vllm-project/production-stack/blob/014d070e6f7611978d321bdb05cbe9a934b614e7/tutorials/20-keda-autoscaling.md}}). KEDA's defaults: it polls every 30 s, and its 300 s cooldownPeriod applies only to scaling to zero ({{KEDA 2.21 ScaledObject spec|https://keda.sh/docs/2.21/reference/scaledobject-spec/}}).

Scaling on CPU never fires; scaling on requests gets the direction right but sizes the pool for the old request size and lets a queue build for the whole burst; scaling on the queue and KV cache gets the size right but spends the first minutes of the burst waiting for cold replicas; the warm pool removes that wait. The warm pool's price is not in its GPU-hours column: those standby GPUs must exist somewhere, either paid for idle or running preemptible batch work (section 7) that gives way.

The other side of cold starts is headroom: capacity kept above current demand to absorb a spike while new replicas start. If a replica takes 3 minutes to start and traffic can grow 20% in 3 minutes, you need about 20% headroom at all times. It is a dial between cost and latency, not a planning failure. Scale to zero (no replicas when idle; KEDA and Knative support it) saves the most and makes the first user after a quiet period wait the whole cold start: fine for an internal tool, wrong for a chat product.

Spot GPUs

Spot (preemptible) capacity is spare cloud capacity sold at a discount that can be taken back with little warning: two minutes on AWS ({{EC2 Spot interruption notices|https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-instance-termination-notices.html}}), 0 seconds by default or 120 seconds if configured on Google Cloud, which advertises "up to 91% discounts" ({{GCP Spot VMs|https://cloud.google.com/compute/docs/instances/spot}}), and "up to 30 seconds" on Azure ({{Azure Spot VMs|https://learn.microsoft.com/en-us/azure/virtual-machines/spot-vms}}). Two minutes is less than a cold start, so spot suits the batch lane first. For live serving, research systems mix spot across regions with on-demand fallback: SkyServe "reduces cost by 43% on average" against on-demand replicas ({{SkyServe, EuroSys 2025|https://arxiv.org/abs/2411.01438}}), and SpotServe reports "saving 54% monetary cost compared with only using on-demand instances" ({{SpotServe, ASPLOS 2024|https://arxiv.org/abs/2311.15566}}).

What autoscaling costs
Metrics plumbing that must keep working (an autoscaler reading a renamed metric sees zero, section 2), tuning of thresholds per model and hardware, and headroom you pay for. It can also amplify trouble: an autoscaler that adds replicas while a shared dependency is the real bottleneck makes things worse (Slack). When not to: steady traffic on a fixed fleet, or a fleet so small that one replica is the minimum anyway; then fixed capacity plus load shedding (section 11) is simpler.

9. Caching layers

The parent topic's cache rule holds: do not compute the same thing twice. LLM services have four caches, from outermost to innermost, and they differ in what counts as "the same".

  • Exact response cache. Key = hash of (tenant, model, full prompt, sampling parameters); value = the stored answer. Safe and cheap; hits mostly on retried requests, repeated system jobs and identical FAQ-style prompts. Low hit rate on chat, because conversations rarely repeat exactly. Skip it for requests with temperature above zero if users expect variety.
  • Semantic cache. Embed the new prompt, find the most similar stored prompt, and return its answer if the similarity is above a threshold (GPTCache popularised it; LiteLLM ships one: type: "redis-semantic" with similarity_threshold: 0.8, {{LiteLLM docs|https://docs.litellm.ai/docs/proxy/caching_semantic}}). It is the riskiest cache because "similar" is not "same": "What is my balance?" from two users, "flights to Paris Texas" and "flights to Paris", yesterday's news. GPTCache's own README warns "you may encounter false positives during cache hits". Measured: one study reports hit rates of 61.6 to 68.8% with "positive hit rates exceeding 97%", that is roughly 3% of hits wrong ({{GPT Semantic Cache, arXiv 2411.05276|https://arxiv.org/abs/2411.05276}}); vCache finds that a single static threshold gives "unexpected error rates" and learns a threshold per cached prompt, reporting "up to 12.5× higher cache hit and 26× lower error rates" ({{vCache, arXiv 2502.03771|https://arxiv.org/abs/2502.03771}}). Huyen's verdict: "semantic cache's value is more dubious because many of its components are prone to failure". Use it only for non-personal, slowly changing answers, scoped per tenant, with the threshold set by an evaluation and the wrong-answer rate monitored.
  • Prefix (KV) cache. Not an answer cache: it keeps the KV cache of a prompt's beginning so the next request with the same beginning skips that part of prefill. It never changes the answer, only the speed and price. Engines do it automatically (vLLM automatic prefix caching) and providers sell it: Anthropic charges 1.25 times the input price to write a 5-minute cache entry and 0.1 times to read it ({{Anthropic prompt caching|https://platform.claude.com/docs/en/build-with-claude/prompt-caching}}); OpenAI caches automatically from 1,024 tokens and now charges 1.25 times for writes on its newest models (GPT-5.6 and later) ({{OpenAI prompt caching|https://developers.openai.com/api/docs/guides/prompt-caching}}). The read multiplier is no longer 0.1 everywhere: Anthropic bills cache reads at 0.05 times the input price on Claude Opus 5.5 and 0.025 times on Fable 5.1 and Mythos 5.1, and OpenAI at 0.05 times on GPT-6.1 Sol; the current table, with the KV cache and semantic caching beside it, is section 11 of {{Caching: every layer, eviction, invalidation, and the LLM caches|n:3cd5c17b0d0d817ebd6ccadd4750c23a}}. The rule that makes it work is in the animation below.
  • Embedding and retrieval caches. In retrieval-augmented generation, store the embedding of each document chunk (computed once) and of frequent queries. Owned by {{Topic: rag-and-retrieval|n:3c65c17b0d0d81b89145c37dfe8a3b0b}}.

Real caveats: a cache entry lives 5 minutes unless used (or 1 hour at a higher write price), there is a minimum cacheable length (512 to 4,096 tokens by model on Anthropic), and an entry "only becomes available after the first response begins", so parallel requests sent at once all miss.

Two production details decide whether prefix caching pays. First, the request must reach a machine that has the prefix: provider caches live on individual machines (OpenAI: traffic "above 15 requests per minute" on one prefix "can lead to overflow routing"; a prompt_cache_key helps it route), and for self-hosted pools this is the job of the prefix-aware router in section 4 and of Character.AI's sticky sessions, which reached a "95% cache rate" (parent's Case files). Second, prompts must be append-only: anything that changes per request (time, user name, retrieved documents, a shuffled tool list) goes after everything that does not.

What caches cost
Memory and a lookup on every request; invalidation when a model or prompt version changes (put both in the key); per-tenant scoping (section 6), which lowers hit rates; and, for semantic caches, wrong answers. When not to: answers that depend on the user, on time or on live data must not come from a response or semantic cache; prefix caching is almost always worth it.
