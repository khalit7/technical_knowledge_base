8. Autoscaling GPUs

Autoscaling adds replicas when load rises and removes them when it falls, and on GPUs the web-service habits fail: CPU utilisation barely moves, GPU utilisation reads near 100% at a tenth of capacity, GPU memory is reserved at start, and requests per second ignores request size (section 1). Queue depth and KV cache use work. A replica takes minutes to start, so a pool keeps headroom: if traffic can grow 20% during one cold start, keep about 20% spare. Spot GPUs, reclaimable with seconds to two minutes of warning, belong first in the batch lane (section 7). The signals, real KServe, KEDA and llm-d thresholds, the cold-start chain and its fixes, spot numbers, and an Autoscaling lab that runs two autoscalers on one spike are on {{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}, sections 2 and 3. For the design: set the TTFT target, size headroom from the measured cold start, give batch work the idle trough, and keep the metrics plumbing working (an autoscaler reading a renamed metric sees zero, section 2). When not to: steady traffic on a fixed fleet, or a fleet so small that one replica is the minimum anyway; then fixed capacity plus load shedding (section 11) is simpler.

9. Caching layers

The parent topic's cache rule holds: do not compute the same thing twice. LLM services have four caches, from outermost to innermost, and they differ in what counts as "the same".

  • Exact response cache. Key = hash of (tenant, model, full prompt, sampling parameters); value = the stored answer. Safe and cheap; hits mostly on retried requests, repeated system jobs and identical FAQ-style prompts. Low hit rate on chat, because conversations rarely repeat exactly. Skip it for requests with temperature above zero if users expect variety.
  • Semantic cache. Embed the new prompt, find the most similar stored prompt, and return its answer if the similarity is above a threshold (GPTCache popularised it; LiteLLM ships one: type: "redis-semantic" with similarity_threshold: 0.8, {{LiteLLM docs|https://docs.litellm.ai/docs/proxy/caching_semantic}}). It is the riskiest cache because "similar" is not "same": "What is my balance?" from two users, "flights to Paris Texas" and "flights to Paris", yesterday's news. GPTCache's own README warns "you may encounter false positives during cache hits". Measured: one study reports hit rates of 61.6 to 68.8% with "positive hit rates exceeding 97%", that is roughly 3% of hits wrong ({{GPT Semantic Cache, arXiv 2411.05276|https://arxiv.org/abs/2411.05276}}); vCache finds that a single static threshold gives "unexpected error rates" and learns a threshold per cached prompt, reporting "up to 12.5× higher cache hit and 26× lower error rates" ({{vCache, arXiv 2502.03771|https://arxiv.org/abs/2502.03771}}). Huyen's verdict: "semantic cache's value is more dubious because many of its components are prone to failure". Use it only for non-personal, slowly changing answers, scoped per tenant, with the threshold set by an evaluation and the wrong-answer rate monitored.
  • Prefix (KV) cache. Not an answer cache: it keeps the KV cache of a prompt's beginning so the next request with the same beginning skips that part of prefill. It never changes the answer, only the speed and price. Engines do it automatically (vLLM automatic prefix caching) and providers sell it: Anthropic charges 1.25 times the input price to write a 5-minute cache entry and 0.1 times to read it ({{Anthropic prompt caching|https://platform.claude.com/docs/en/build-with-claude/prompt-caching}}); OpenAI caches automatically from 1,024 tokens and now charges 1.25 times for writes on its newest models (GPT-5.6 and later) ({{OpenAI prompt caching|https://developers.openai.com/api/docs/guides/prompt-caching}}). The read multiplier is no longer 0.1 everywhere: Anthropic bills cache reads at 0.05 times the input price on Claude Opus 5.5 and 0.025 times on Fable 5.1 and Mythos 5.1, and OpenAI at 0.05 times on GPT-6.1 Sol; the current table, with the KV cache and semantic caching beside it, is section 11 of {{Caching: every layer, eviction, invalidation, and the LLM caches|n:3cd5c17b0d0d817ebd6ccadd4750c23a}}. The rule that makes it work is in the animation below.
  • Embedding and retrieval caches. In retrieval-augmented generation, store the embedding of each document chunk (computed once) and of frequent queries. Owned by {{Topic: rag-and-retrieval|n:3c65c17b0d0d81b89145c37dfe8a3b0b}}.

Real caveats: a cache entry lives 5 minutes unless used (or 1 hour at a higher write price), there is a minimum cacheable length (512 to 4,096 tokens by model on Anthropic), and an entry "only becomes available after the first response begins", so parallel requests sent at once all miss.

Two production details decide whether prefix caching pays. First, the request must reach a machine that has the prefix: provider caches live on individual machines (OpenAI: traffic "above 15 requests per minute" on one prefix "can lead to overflow routing"; a prompt_cache_key helps it route), and for self-hosted pools this is the job of a prefix-aware router ({{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}, section 1) and of Character.AI's sticky sessions, which reached a "95% cache rate" (parent's Case files). Second, prompts must be append-only: anything that changes per request (time, user name, retrieved documents, a shuffled tool list) goes after everything that does not.

What caches cost
Memory and a lookup on every request; invalidation when a model or prompt version changes (put both in the key); per-tenant scoping (section 6), which lowers hit rates; and, for semantic caches, wrong answers. When not to: answers that depend on the user, on time or on live data must not come from a response or semantic cache; prefix caching is almost always worth it.
