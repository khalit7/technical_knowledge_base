6. LLM applications: prompt, retrieval, fine-tuning or an agent, inside a budget

With an LLM the "model" box of the hero is a design of its own. The design question is what the base model lacks for this task, answered with the cheapest rung that supplies it; each rung up adds cost, latency and something new to evaluate.

Climb only as far as the task needs: each rung answers a different lack

The baseline is rung 1; the evaluation set of section 3 decides whether a rung earned its cost.

  • Lacks facts (the tenant's help articles, this customer's orders): retrieval. Fine-tuning "changes how a model behaves but is a poor way to add facts: it cannot be updated per document, cannot cite, cannot give two users different views, and still hallucinates on what it saw once"; the two combine: "fine-tune for format and domain style, retrieve for facts" ({{Topic: rag-and-retrieval|n:3c65c17b0d0d81b89145c37dfe8a3b0b}}, which owns the pipeline).
  • Lacks behaviour (a strict output format, a house style, a small model doing one narrow job cheaply): fine-tuning, usually an adapter; many tenants' adapters can share one base model on one replica ({{Parameter-Efficient Fine-Tuning|n:3c65c17b0d0d81eba08eef56b3e3b4eb}}).
  • Lacks steps (look up the order, then check the refund policy, then act): a workflow, model calls "orchestrated through predefined code paths", or an agent, where models "dynamically direct their own processes and tool usage"; Anthropic's advice is "the simplest solution possible, and only increasing complexity when needed" ({{Building effective agents|https://www.anthropic.com/engineering/building-effective-agents}}, compared on {{Topic: agentic-frameworks|n:3c65c17b0d0d81ab8432c54d65b7f8c7}}). An agent's cost and latency are a distribution, not a number: budget steps and tokens per task.

The cost row, derived. An app server (AWS m7i.xlarge, $0.2016 an hour, the parent topic's figure) at an illustrative 500 requests a second costs $0.2016 ÷ 3,600 ÷ 500 = $0.00000011 a request. One chat reply of 400 output tokens self-hosted, Llama 3.3 70B in FP8 on H100s at $3.99 per GPU-hour ({{Lambda pricing|https://lambda.ai/pricing}}, read 2026-10-04) producing 2,209 output tokens a second per GPU ({{TensorRT-LLM perf overview at commit 8a9c66c|https://github.com/NVIDIA/TensorRT-LLM/blob/8a9c66ce086594054d3722307cfed2d658d25e60/docs/source/developer-guide/perf-overview.md}}, vendor benchmark, 1,000 input and 1,000 output tokens) run at half that rate to keep latency acceptable (illustrative derating): $3.99 ÷ 3,600 ÷ (2,209 × 0.5) = $1.00 per million output tokens, so $0.0004 per reply, about 3,600 times the web request. Through an API, Claude Sonnet 5.5 at $2 per million input and $10 per million output tokens ({{Anthropic pricing|https://platform.claude.com/docs/en/about-claude/pricing}}, the knowledge base's price snapshot of 2026-10-01): 1,000 × $2 + 400 × $10, per million, = $0.006, about 54,000 times. That is 3.6 to 4.7 orders of magnitude (a 100,000-token document to a frontier model reaches 6), so cost is an architecture problem: who may spend how much, which model a request deserves and which work need not be done twice are designed up front. Count tokens, not requests: two requests can differ in tokens by a factor of a thousand.

Worked budget: the support assistant for 10,000 business tenants

Illustrative inputs: 500 messages per tenant per day, busy hour 3 times the average, 3,000 input tokens (instructions plus retrieved documents) and 300 output tokens per message, 70% of input tokens a cached prefix.

  • Traffic: 10,000 × 500 = 5 million messages a day = 58 a second on average, 174 a second at peak.
  • Output tokens at peak: 174 × 300 = 52,000 a second.
  • Self-hosted 70B at the derated 1,104 tokens/s per GPU: 52,083 ÷ 1,104.5 = 47.2, so 48 H100s (24 replicas), $4,596 a day at $3.99 if kept for the peak all day; Little's law gives 174 × (300 ÷ 69 tokens/s) = about 755 streams open at peak.
  • Through an API (Sonnet 5.5): 3,000 × $2 + 300 × $10 per million = $0.009 a message, $45,000 a day; with 70% of input read from the prefix cache, 900 × $2 + 2,100 × $0.20 + 300 × $10 per million = $0.00522, $26,100 a day.

The API costs six to ten times the self-hosted fleet at this volume (with and without caching), but buys a stronger model, no capacity risk and no GPU team; a router that sends easy tickets to a small tier and caching change the ratio, and the self-hosted fleet sized for the peak is mostly idle at night unless batch work fills it. "Prefix caching cuts the cost per message by about 40% here because 70% of each prompt is static" is the kind of quantified trade-off a design review wants. Checked in src/recompute.py. Move these levers yourself in the {{Cost-quality lab|#t-gw}}.

The prefix cache is the cheapest lever and the easiest to lose: it keeps the computed state of a prompt's beginning so the next request with the same beginning skips that part of prefill. It never changes the answer, only speed and price, and it matches from the first token, so prompt layout decides whether it works.

One changed line at the top of the prompt makes every turn a cache miss

Six turns of a chat. Each request holds a 2,000-token system prompt (instructions and tool definitions), the conversation so far, and the new message, which includes a 30-token line with the current time and user context. Illustrative token counts; checked in src/recompute.py. Caveats: a cache entry lives 5 minutes unless used (or 1 hour at a higher write price), there is a minimum cacheable length (512 to 4,096 tokens by model on Anthropic), and an entry "only becomes available after the first response begins", so parallel requests sent at once all miss.

The rule: prompts are append-only; anything that changes per request (time, user name, retrieved documents, a shuffled tool list) goes after everything that does not. And the request must reach a machine that has the prefix: provider caches live on individual machines (OpenAI: traffic "above 15 requests per minute" on one prefix "can lead to overflow routing"; a prompt_cache_key helps it route), and self-hosted pools need a prefix-aware router ({{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}, section 1); Character.AI's sticky sessions reached a "95% cache rate" (parent's Case files).
