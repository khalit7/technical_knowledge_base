Serving the model behind one endpoint is where section 6 ends. Serving it to many tenants adds a layer of components between the app and the GPUs, each with a decision that stays with the system designer and internals owned by another page.

Never queue without a bound in front of a GPU. A queue that grows faster than it drains turns overload into minutes of waiting for everyone, and clients that time out and retry add more load. Why each row of the LLM table holds: streams, unknown size, capacity blocks and cold starts (depth)

It streams. Users will not stare at a blank screen for 6 seconds, so the reply is streamed: sent token by token over one open HTTP response. Every layer between the user and the GPU (load balancer, gateway, proxy) must pass the stream through without buffering it, and must allow connections that stay open for minutes.

Its size is unknown until it ends. Input is known; output length is decided by the model, from 1 token to the max_tokens cap. This breaks two web habits: limiting customers by requests per minute (one request can be a thousand times another) and scaling servers on request rate (a pool sized on requests falls behind when replies get longer).

Capacity comes in big blocks that start slowly. The 70B model's FP8 weights are 72.7 GB ({{model files on Hugging Face|https://huggingface.co/nvidia/Llama-3.3-70B-Instruct-FP8}}; sum of the weight files). One 80 GB H100 holds them with little room left for conversations, so a replica (one running copy of the model) spans two GPUs, and capacity grows two GPUs at a time; AWS rents H100s eight to a machine (p5.48xlarge, $55.04 an hour on demand, {{Vantage's AWS price mirror|https://instances.vantage.sh/aws/ec2/p5.48xlarge}}, read 2026-10-04). A new replica must get a GPU machine, download its software image, copy 73 GB of weights into GPU memory and warm up before it serves anyone. vLLM's maintainers list what a cold start pays even when weights load instantly: memory allocator setup, recording CUDA graphs, compiling GPU kernels, and first-request warm-up, and put a full model reload at "30-100+ seconds per switch" ({{vLLM blog, sleep mode, 26 Oct 2025|https://vllm.ai/blog/2025-10-26-sleep-mode}}). Add finding and booting a GPU machine and minutes are normal.

Autoscaling signals. CPU utilisation barely moves, GPU utilisation reads near 100% at a tenth of capacity, GPU memory is reserved at start, and requests per second ignores request size; queue depth and KV cache use work. If traffic can grow 20% during one cold start, keep about 20% spare. Spot GPUs, reclaimable with seconds to two minutes of warning, belong first in the batch lane. Set the TTFT target, size headroom from the measured cold start, and keep the metrics plumbing working: an autoscaler reading a renamed metric sees zero (next block).

Inter-token latency (ITL) is measured gap by gap; it differs from TPOT when a step emits several tokens at once (speculative decoding). In vLLM v0.30.0 (released 2026-09-22) the Prometheus metrics a system designer reads are vllm:num_requests_waiting ("Number of requests waiting to be processed"), vllm:num_requests_running ("Number of requests in model execution batches"), vllm:kv_cache_usage_perc ("KV-cache usage. 1 means 100 percent usage", a fraction despite the name), and the histograms vllm:time_to_first_token_seconds, vllm:inter_token_latency_seconds and vllm:e2e_request_latency_seconds ({{vllm/v1/metrics/loggers.py at v0.30.0|https://github.com/vllm-project/vllm/blob/v0.30.0/vllm/v1/metrics/loggers.py}}). Names change between versions: vllm:gpu_cache_usage_perc was renamed to vllm:kv_cache_usage_perc in 0.9.2 and removed in 0.12, and vllm:time_per_output_token_seconds gave way to vllm:inter_token_latency_seconds in 0.11. Dashboards and autoscalers that query the old names go silent after an upgrade, which is a real way to lose autoscaling: alert on missing metrics.

The KV cache is the engine's memory of each conversation (keys and values for every token so far), in GPU memory, growing with every token, so it caps how many conversations a replica holds. For this model it is 2 × 80 layers × 8 key-value heads × 128 dimensions × 1 byte = 160 KiB per token (FP8 cache), so one 1,400-token conversation holds about 219 MiB. How engines manage it is the subject of the {{PagedAttention paper page|n:3c65c17b0d0d81bf8b90ca93fee19f5f}}; for the system designer, "KV cache full" means "no room for more conversations on this replica".

Gateway, routing and token limits: the points that stay here (depth)

The first feature calls a model API directly with a key in an environment variable; by the fifth there are five copies of retry logic, three provider keys in three services, no idea which team spent $40,000 last month, and no way to switch providers during an outage. The gateway speaks one API shape (almost always OpenAI's chat completions format) and authenticates, checks limits and budget, redacts personal data and applies input rails ({{Guardrails|n:3c65c17b0d0d819bbfa5dffa9246c297}}), looks up caches, routes, calls with a timeout, retries or falls back, streams the reply back unbuffered, and writes one usage event per call. Which model: tier routing (prices differ 2 to 40 times between tiers of one vendor), context routing (long prompts to long-context pools; getting it wrong was Anthropic's August 2025 bug, section 5), policy routing (tenant pinning, data residency). Fallbacks are planned like a backup generator: enough quota for all the traffic, the same prompt and tool format, the same safety behaviour, a cold prompt cache. Which replica: a second load balancer inside a self-hosted pool that sees each replica's queue and prefix cache rather than going round robin.

Two customers each limited to 60 requests a minute can differ 36 times in load (60 short chats against 60 summaries of a 50,000-token contract), so limits count tokens. Output tokens are unknown at admission: limiters reserve the worst case, count output as it streams, or charge after the response and accept overshoot (all three on Gateways and routing, sections 5 and 6). An internal tool with a handful of users and a monthly budget alert needs no per-tenant token buckets.

Multi-tenancy and isolation: four things to isolate, four ways to share GPUs (depth)

Multi-tenancy is serving many customer organisations from shared infrastructure, which is cheap, while keeping each from hurting or seeing the others, which is the work.

  • Capacity. The noisy neighbour: one tenant's burst fills the batch and every other tenant's TTFT rises. Token limits cap the average; fair scheduling handles the moment. The Virtual Token Counter scheduler defines fairness by "a cost function that accounts for the number of input and output tokens processed" and gives "a 2× tight upper bound on the service difference between two backlogged clients" while keeping the GPU busy ({{Sheng et al., Fairness in Serving Large Language Models, OSDI 2024|https://www.usenix.org/conference/osdi24/presentation/sheng}}).
  • Data. Prompts and answers must never cross tenants: not in logs, not in caches. A response or semantic cache shared across tenants can hand one customer another's answer; even a shared prefix cache is a timing side channel (a fast first token reveals that someone sent the same beginning). OpenAI states "Caches are not shared across organizations" ({{OpenAI prompt caching|https://developers.openai.com/api/docs/guides/prompt-caching}}).
  • Cost. Every usage event carries the tenant, so each one's bill and margin are known.
  • Customisation. Tenants' own fine-tuned adapters on a shared base model.

Priority classes are as old as Google's load shedding: requests are tagged CRITICAL_PLUS, CRITICAL, SHEDDABLE_PLUS ("the default for batch jobs, which can retry requests minutes or even hours later") or SHEDDABLE, and criticality propagates to the calls a request makes ({{SRE book, ch. 21, Handling Overload|https://sre.google/sre-book/handling-overload/}}). The Kubernetes inference stack does the same for model traffic: an early version had Critical, Standard and Sheddable; today llm-d's InferenceObjective carries an integer priority, and "flow control will always allow requests of higher priority to be served first", while "Fairness is only enforced and tracked between requests of the same priority" ({{inferenceobjective_types.go, llm-d-router v0.11.0|https://github.com/llm-d/llm-d-router/blob/v0.11.0/apix/v1alpha2/inferenceobjective_types.go}}). Reserved capacity: Anthropic's Priority Tier committed input and output tokens per minute for 1 to 12 months, "targets 99.5% uptime", and "Requests beyond your committed capacity automatically fall back to standard tier"; it is "no longer available for purchase" to new buyers as of October 2026 ({{Anthropic service tiers|https://platform.claude.com/docs/en/api/service-tiers}}).

Each step down the table buys predictability with idle hardware, and scoping caches per tenant lowers hit rates. A product with one customer (your own app) has no tenants to isolate: start with a shared pool and per-tenant limits, and add reserved or dedicated capacity only for a customer who pays for it.

The four caches, and where the semantic cache's error is measured (depth)
  • Exact response cache. Key = hash of (tenant, model, full prompt, sampling parameters). Safe and cheap; hits mostly on retries, repeated system jobs and identical FAQ-style prompts; low hit rate on chat. Skip it at temperature above zero if users expect variety.
  • Semantic cache. Embed the new prompt, find the most similar stored prompt, return its answer above a threshold. The riskiest cache, because "similar" is not "same"; its false hits measured threshold by threshold on labelled pairs, the published hit and error rates (GPT Semantic Cache, vCache) and a gateway's configuration are on {{Caching|n:3cd5c17b0d0d817ebd6ccadd4750c23a}}, section 12. Huyen: "semantic cache's value is more dubious because many of its components are prone to failure". Use it only for non-personal, slowly changing answers, scoped per tenant, with the threshold set by an evaluation and the wrong-answer rate monitored.
  • Prefix (KV) cache. Section 6. Anthropic charges 1.25 times the input price to write a 5-minute entry and 0.1 times to read it; OpenAI caches automatically from 1,024 tokens and charges 1.25 times for writes on GPT-5.6 and later. Read multipliers now differ by model (0.05 times on Claude Opus 5.5 and GPT-6.1 Sol, 0.025 times on Fable 5.1 and Mythos 5.1); the current table is section 11 of the Caching page.
  • Embedding and retrieval caches. Each chunk's embedding computed once, and frequent queries'. Owned by {{Topic: rag-and-retrieval|n:3c65c17b0d0d81b89145c37dfe8a3b0b}}.

Caches cost memory and a lookup on every request, and invalidation when a model or prompt version changes (put both in the key). Answers that depend on the user, on time or on live data must not come from a response or semantic cache; prefix caching is almost always worth it.

Google's SRE book recommends client-side throttling too: each client tracks its requests and the backend's accepts, and keeps sending until "requests is K times as large as accepts", with "We generally prefer the 2x multiplier" ({{SRE book, ch. 21|https://sre.google/sre-book/handling-overload/}}). Retry in one layer only: client, gateway and SDK each retrying three times multiplies load during an outage (the parent topic's 243-times case).

Each rung needs a trigger, an owner who may pull it, and a test that it works; shed batch first, then free tier, then paid. Real policies differ, and some choose not to degrade quality at all. GitHub Copilot users who exhaust premium requests "can still use Copilot with one of the included models", which "may be subject to rate limiting" ({{GitHub docs, Copilot requests|https://docs.github.com/en/copilot/concepts/billing/copilot-requests}}); ChatGPT's free tier pauses: "GPT access pauses until the limit resets" ({{OpenAI help, free tier FAQ|https://help.openai.com/en/articles/9275245-chatgpt-free-tier-faq}}, read 2026-10-04); and Anthropic states "We never reduce model quality due to demand, time of day, or server load", degrading by queueing and limits instead. Tell users which rung they are on.

The worst outages of model services are often in ordinary infrastructure: OpenAI's 11 December 2024 outage (4 hours 22 minutes) came from a telemetry service that overloaded the Kubernetes control plane, which broke DNS-based service discovery (parent's Case files, "A monitoring tool overloaded the cluster brains"). The gateway, the autoscaler, the metrics pipeline and DNS are part of the model service's reliability.

Observability: usage events, prefix-cache hit rate, OpenTelemetry names (depth)

The gateway should measure TTFT too, because the user's TTFT includes everything before the engine. Capacity signals: waiting and running requests, KV cache use, prefix cache hit rate (vLLM exports vllm:prefix_cache_queries and vllm:prefix_cache_hits in tokens, so hit rate = hits ÷ queries), tokens per second per GPU, preemptions. One usage event per request (tenant, feature, model and prompt versions, input, cached and output tokens, cost, latency, outcome), streamed to an analytics store, gives bills, per-team showback, cost per request and margin per tenant. Price cached and output tokens separately: they differ by a factor of 50 (Sonnet 5.5: $0.20 against $10 per million).

OpenTelemetry's generative-AI semantic conventions (moved in 2026 to their own repository, status "Development") define gen_ai.server.time_to_first_token ("Time to generate first token for successful responses"), gen_ai.server.time_per_output_token and token-usage counters such as gen_ai.client.inference.usage.input_tokens and .cache_read.input_tokens ({{semantic-conventions-genai at e07f4eb|https://github.com/open-telemetry/semantic-conventions-genai/blob/e07f4ebacb08f56db8c4c882d117720333fbca04/docs/gen-ai/gen-ai-metrics.md}}). The earlier gen_ai.client.token.usage histogram is no longer defined there; development-status names still move, so pin the version you instrument against.

Storing prompts and outputs for debugging and evaluation is storing customer data: decide retention, redaction and access up front. Per-tenant, per-model labels multiply metric series; keep high-cardinality fields in the usage events, not in metric labels.
