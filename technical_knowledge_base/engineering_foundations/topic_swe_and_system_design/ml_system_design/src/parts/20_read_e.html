10. Rolling out a new model or prompt

The problem appears
A new model version scores better on the offline evaluation, so it replaces the old one for everyone at 10:00. By 10:40 support tickets say answers in German got worse, tool calls fail for one customer's schema, and cost per request is up 30% because the new model writes longer replies. None of that was in the evaluation set.

For a model service, "a change" is any of: a new model or provider version, a new prompt, new sampling parameters, a new engine version or GPU type (Anthropic's postmortem shows the same model behaving differently on different hardware stacks), or a new router. Each should ship like risky code, in stages, with the decision at each stage made on numbers. The statistics of those decisions (how much traffic, for how long, which test) are owned by {{Production eval engineering|n:3c65c17b0d0d81b39ad9e96193d21adc}}; here is the machinery a system designer builds.

  1. Pin and version everything. The model id (a dated snapshot, not an alias that the provider moves), prompt version, parameters and router config live in versioned config, and every usage event records them. Then rollback is a config change, not a deploy, and every bad answer can be traced to the exact versions that produced it.
  2. Offline gate. The candidate must pass the regression evaluation before it sees any user (sibling {{Testing and quality|n:3c65c17b0d0d81548848e2ebdd2f63ee}}; gates in Production eval engineering).
  3. Shadow. Copy live requests to the candidate and throw its answers away; compare quality (sampled, with judges), latency and cost against the incumbent on the same inputs. Service meshes do the copying: Istio's mirror with mirrorPercentage sends requests "as 'fire and forget,' which means that the responses are discarded" ({{Istio docs, mirroring|https://istio.io/latest/docs/tasks/traffic-management/mirroring/}}), so the shadow service must log its own outputs. Shadowing doubles model cost for the mirrored share: mirror a sample, and never mirror requests with side effects (tool calls that send email or charge cards).
  4. Canary. Send a small share of real traffic to the candidate (1%, then 5%, 25%, 100%), keyed by user or tenant so one user's conversation stays on one version, and stop automatically if a guard metric breaks. KServe does this with one field: canaryTrafficPercent: 10 on the predictor; set it to 0 to roll back ({{KServe canary example|https://kserve.github.io/website/docs/model-serving/predictive-inference/rollout-strategies/canary-example}}). Argo Rollouts (v1.10.0) adds analysis steps that "block the rollout until the run is completed" and a successCondition such as result[0] >= 0.95 on a Prometheus query ({{Argo Rollouts analysis|https://argo-rollouts.readthedocs.io/en/stable/features/analysis/}}).
  5. A/B test when the question is "is it better for users", not "is it safe": a fixed split for long enough to measure user outcomes.
What staged rollout costs
Days instead of minutes per change, shadow compute, and two versions in production at once (two prompt caches, two sets of GPUs if self-hosted). When not to: internal tools and prototypes can switch at once behind a flag; anything customers depend on cannot.

11. Failure modes and degradation ladders

The parent topic's Step 4 and the sibling {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}} teach timeouts, retries with backoff and jitter, circuit breakers and load shedding. Here is how they apply when the dependency is a model.

LinkedIn found its model produced invalid YAML about 10% of the time and cut errors "to ~0.01%" with a defensive parser ({{LinkedIn Engineering, 25 Apr 2024|https://www.linkedin.com/blog/engineering/generative-ai/musings-on-building-a-generative-ai-product}})

Never queue without a bound in front of a GPU. The autoscaling animation's CPU policy shows why: a queue that grows faster than it drains turns overload into minutes of waiting for everyone, and clients that time out and retry add more load. A bounded queue that refuses early keeps the requests it accepts fast. Google's SRE book recommends a client-side version too: each client tracks its requests and the backend's accepts, and keeps sending until "requests is K times as large as accepts", with "We generally prefer the 2x multiplier" ({{SRE book, ch. 21|https://sre.google/sre-book/handling-overload/}}).

A degradation ladder, decided before the incident

Degrading means serving a worse answer instead of none: "responses that are not as accurate as or that contain less data than normal responses, but that are easier to compute" (SRE book, ch. 21). For the chat assistant, from best to worst:

1. Full servicelarge model, full context, retrieval on
→
2. Second providersame quality, higher cost or latency
→
3. Smaller modelcheaper tier for everyone, or for free users
→
4. Less workshorter context, retrieval off, lower max_tokens
→
5. Cached or canned answerfor known questions
→
6. Honest errorwith a retry time

Each rung needs a trigger (which metric, which threshold), an owner who may pull it, and a test that it works. Shed the cheapest-to-lose traffic first: batch (section 7), then free tier, then paid. Real policies differ, and some choose not to degrade quality at all. GitHub Copilot users who exhaust premium requests "can still use Copilot with one of the included models", which "may be subject to rate limiting" ({{GitHub docs, Copilot requests|https://docs.github.com/en/copilot/concepts/billing/copilot-requests}}); ChatGPT's free tier now pauses: "GPT access pauses until the limit resets" ({{OpenAI help, free tier FAQ|https://help.openai.com/en/articles/9275245-chatgpt-free-tier-faq}}, read 2026-10-04); and Anthropic states "We never reduce model quality due to demand, time of day, or server load", degrading by queueing and limits instead. Whatever you choose, tell users which rung they are on.

Failures that are not yours
The worst outages of model services are often in ordinary infrastructure. OpenAI's 11 December 2024 outage (4 hours 22 minutes) came from a telemetry service that overloaded the Kubernetes control plane, which broke DNS-based service discovery (parent's Case files, "A monitoring tool overloaded the cluster brains"). The gateway, the autoscaler, the metrics pipeline and DNS are part of the model service's reliability.

12. Observing an LLM service

The sibling {{Observability|n:3ef5c17b0d0d811e8490c54dd42c2b9b}} teaches logs, metrics, traces and alerting. An LLM service needs four families of signals on top of the usual request rate, errors and duration:

  • Latency per phase: TTFT and TPOT as histograms (percentiles, not averages), queue time separately, per model and per tenant. Engines export them (section 2); the gateway should measure TTFT too, because the user's TTFT includes everything before the engine.
  • Capacity: waiting and running requests, KV cache use, prefix cache hit rate (vLLM exports vllm:prefix_cache_queries and vllm:prefix_cache_hits in tokens, so hit rate = hits ÷ queries), tokens per second per GPU, preemptions.
  • Money: one usage event per request (tenant, feature, model and prompt versions, input, cached and output tokens, cost, latency, outcome), streamed to an analytics store. From it come bills, per-team showback, cost per request, and the margin per tenant. Price cached and output tokens separately: they differ by a factor of 50 (Sonnet 5.5: $0.20 against $10 per million).
  • Quality: what no status code shows. Sample production traffic and score it with judges, track user signals (thumbs, regenerations, abandonment), and watch output length and refusal rate, which move when a model changes. Anthropic's lesson from its postmortem: "The evaluations we ran simply didn't capture the degradation users were reporting", and it now runs quality evaluations "continuously on true production systems".

A shared vocabulary is forming: OpenTelemetry's generative-AI semantic conventions (moved in 2026 to their own repository, status "Development") define gen_ai.server.time_to_first_token ("Time to generate first token for successful responses"), gen_ai.server.time_per_output_token and token-usage counters such as gen_ai.client.inference.usage.input_tokens and .cache_read.input_tokens ({{semantic-conventions-genai at e07f4eb|https://github.com/open-telemetry/semantic-conventions-genai/blob/e07f4ebacb08f56db8c4c882d117720333fbca04/docs/gen-ai/gen-ai-metrics.md}}). The earlier gen_ai.client.token.usage histogram is no longer defined there; development-status names still move, so pin the version you instrument against.

What it costs
Storing prompts and outputs for debugging and evaluation is storing customer data: decide retention, redaction and access up front. Per-tenant, per-model labels multiply metric series; keep high-cardinality fields in the usage events, not in metric labels.
