Step 2 The database becomes the bottleneck

The problem appears
App servers can be added forever; they all talk to one database. Opening a chat reads its history; sending a message writes two rows and reads the history again for the model. Say that at a few hundred thousand users the servers together send the database 1,000 reads per second and it can answer about 600 (illustrative). Same law as Step 1, and now every server waits on it. Reads far outnumber writes here, so start with reads.

First, the cheap fix: an index

Asked for "all messages of chat 42" with no help, the database reads every row: a full scan, fine at a thousand rows, hopeless at a billion. An index is a separate, sorted structure that maps a column's values to where the rows live, exactly like the index at the back of a book: look up "chat 42", jump to its pages ({{Postgres docs|https://www.postgresql.org/docs/current/indexes-intro.html}}). Cost: every write also updates every index, and indexes take space, so index only the columns you search by. Many "the database is slow" incidents end with one missing index.

Then a cache: do not ask the same question twice

A cache is a small, fast store (usually in memory, such as Redis) holding copies of answers the system has already computed. Memory answers far faster than a database query (see {{Numbers to know|#t-num}}). The usual pattern is cache-aside: the server first asks the cache; on a hit it is done; on a miss it reads the database, then stores the answer in the cache for next time ({{Microsoft pattern guide|https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside}}; Amazon calls it a "side cache", {{Builders' Library|https://aws.amazon.com/builders-library/caching-challenges-and-strategies/}}). The share of reads answered by the cache is the hit rate; at a 90% hit rate the database sees one read in ten.

A copy can go stale. A TTL (time to live) makes each entry expire after a set time, bounding staleness ("at most 60 seconds old"). Invalidation deletes the cached copy when the data changes: rename a chat, and the server writes the database, then deletes that chat's cache entry. A cache of static files (images, the app's code) placed in many cities near users is a CDN (content delivery network).

Animation: the same reads, straight to the database against through a cache

Illustrative traffic: one square is 50 reads per second (20 squares, 1,000 reads/s); the database answers 12 squares (600 reads/s). The hit rate warming from 0% to 90% is an assumption: real hit rates depend on how often the same data is read again.

What a cache costs
Stale reads (bounded by the TTL, or fixed by invalidation, which is easy to forget in one code path); one more system to run; and a dangerous dependency. If the cache empties (a restart, a new server with a cold cache), the full read load lands on a database sized for 10% of it. Amazon's engineers name this risk and the usual fix, letting only one request fetch a missing key while the others wait for it ("request coalescing", {{Brinkley and Chhabra|https://aws.amazon.com/builders-library/caching-challenges-and-strategies/}}).

Copies of the database: read replicas

Some reads cache badly (every chat list differs and changes constantly). Next comes a read replica: a full copy of the database. All writes go to one primary, which streams every change to the replicas; reads spread over them ({{Postgres hot standby|https://www.postgresql.org/docs/current/hot-standby.html}}), and a replica can take over if the primary dies. Cost: copying takes time, the replication lag, sometimes seconds. A user sends a message, the page refreshes, the read hits a replica that has not caught up, and the message has vanished; the usual fix is to read your own recent writes from the primary.

Splitting the database: sharding

Replicas multiply reads, but every write still goes through one primary. When writes or data outgrow one machine, split the data: sharding (or partitioning) gives each of several databases a slice, chosen by a shard key. Shard by user: user 17's chats live on shard 17 mod 8. Cost: anything across users (global search, weekly totals) must ask every shard; adding shards means moving data; one very busy user still lands on one shard. It is usually the last resort.

What you give up: consistency

Caches and replicas keep several copies, and copies disagree for a moment after every change. Strong consistency (linearizability, in the precise vocabulary) means every read sees the latest write, as if there were only one copy. Eventual consistency means copies may differ for a while but converge once writes stop. Strong costs coordination: waiting for copies to agree. Jepsen keeps a map of the many levels in between ({{Jepsen consistency models|https://jepsen.io/consistency}}).

Two well-known statements make the trade explicit. CAP: when the network between copies breaks (a partition), a system must choose to stay consistent (refuse some requests) or stay available (answer, possibly with stale data); it cannot have both during the partition ({{Gilbert and Lynch, 2002|https://users.ece.cmu.edu/~adrian/731-sp04/readings/GL-cap.pdf}}). Partitions are rare, so Abadi's PACELC adds the everyday half: "else (E), when the system is running normally ... how does the system trade off latency (L) and consistency (C)?" ({{Abadi, IEEE Computer 2012|https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf}}). In practice you choose per piece of data: a user's paid credit balance must be strongly consistent (never spend the same credit twice); the order of chats in the sidebar can be a second stale and nobody will notice.
