Step 1 One server, then too many requests for it

One message is a short chain: DNS turns chat.example.com into an address, TCP opens a connection (one round trip), TLS encrypts it (one more in TLS 1.3; reusing an open connection skips both), and an HTTP request such as POST /chats/42/messages reaches a server process, which checks who you are, reads and writes the database (which keeps data safe on disk: the server can crash and restart, the data must never be lost), calls the model and streams the reply. Each hop's typical time is in {{Numbers to know|#t-num}}; the wire itself is {{Topic: protocols|n:3c65c17b0d0d81ec9355f4eecd6eed02}}.

Two words measure it all. Latency is how long one request takes; throughput is how many finish per second. Latency is quoted as percentiles (p50 the typical request, p99 the slowest 1 in 100), because an average hides the slow tail.

The wall
Say one server answers 400 requests a second and 600 arrive (illustrative). Every second 200 more arrive than leave, the line grows, and every user's latency grows with it. When work arrives faster than it is finished, waiting does not rise a little, it rises without bound.

Vertical scaling (a bigger machine) needs no code change and is the right first move, but it has a ceiling and stays a single point of failure. Horizontal scaling adds machines behind a load balancer, which hands each request to one of them and stops sending to any that fails its health checks. It has one precondition that changes how code is written: servers must be stateless, so the session moves into the database, a shared cache or a signed token, and any server can answer any request.

The price, across pages
More machines to run, a balancer that must not become the new single point of failure, and every piece of state now in one shared place, the database: Step 2's wall.

Step 2 The database becomes the bottleneck

The wall
App servers can be added forever; they all talk to one database. Say the servers together send it 1,000 reads a second and it answers about 600 (illustrative): Step 1's law again, and now every server waits on it. Reads far outnumber writes here, so the fixes start with reads, cheapest first.

What every copy gives up: consistency. Caches and replicas keep several copies, and copies disagree for a moment after every change. Strong consistency (linearisability) means every read sees the latest write, as if there were one copy; eventual consistency means copies converge once writes stop. CAP: while the network between copies is broken, a system either refuses some requests or answers with possibly stale data. PACELC adds the everyday half: when nothing is broken, it trades latency against consistency. In practice the choice is made per piece of data: a paid credit balance must be strongly consistent (never spend the same credit twice); the order of chats in the sidebar can be a second stale.
