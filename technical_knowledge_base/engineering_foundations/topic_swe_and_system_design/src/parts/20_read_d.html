Step 5 The GPU layer: a backend unlike the others

The wall
A chat reply costs seconds of a GPU. A model writes one token at a time and reads all its weights for each: an 8-billion-parameter model in 16-bit numbers is 16 GB per token, and an H100 reads 3.35 TB/s ({{NVIDIA|https://www.nvidia.com/en-us/data-center/h100/}}), so one conversation gets at most about 210 tokens a second and a 500-token reply takes at least 2.4 seconds (derived: 16 GB ÷ 3.35 TB/s = 4.8 ms per token).

Four properties break the web playbook of Steps 1 to 4:

  • Two phases. Prefill reads the whole prompt at once and is limited by arithmetic; decode writes one token per step and is limited by memory bandwidth, as above.
  • Long-lived responses. Replies are streamed token by token, so each holds a connection open for seconds; Little's law counts them in Step 6.
  • Capacity in big, slow blocks. A 70-billion-parameter model in 16-bit numbers is 140 GB, more than one 80 GB GPU, so one model replica spans several; loading 140 GB at an illustrative 2 GB/s takes 70 seconds before the server even starts, so cold starts take minutes and GPUs cannot be added the moment a spike arrives.
  • Memory per conversation. The KV cache keeps intermediate results for every token so far, in scarce GPU memory, and often limits how many users one GPU serves.

The fixes all do less work per reply. Batching uses one read of the weights for many conversations: with 64 in a batch, the 4.8 ms read yields 64 tokens, a ceiling of about 13,000 tokens a second (derived); continuous batching refills a freed slot at every step instead of waiting for the longest reply. Prefix caching keeps the KV cache of a shared prompt beginning, so what never changes goes first in the prompt; a semantic cache returns a stored answer for a question that merely looks similar, cheap and wrong whenever the answer depends on who asks. A model router sends easy requests to a small model and doubles as Step 4's degradation path. A rate limit per customer, usually a token bucket, must count tokens as well as requests, because one 100,000-token document costs as much as a thousand short questions.

The price, across pages
Batching trades a little latency per user for much more throughput per GPU; caches can serve the wrong answer to the wrong person; routers misjudge difficulty; and GPUs are expensive idle and slow to add, so the fleet size is a bet on tomorrow's traffic, which Step 6 estimates.
Published throughput figures behind these ceilings (depth)

NVIDIA's published performance overview (v0.21 data) reports about 15,000 output tokens a second for Llama 3.1 8B in 8-bit on one H100, 1,000 input and 1,000 output tokens per request, at maximum load (vendor benchmark; see {{Numbers to know|#t-num}}). Continuous batching was introduced by Orca ({{OSDI 2022|https://www.usenix.org/conference/osdi22/presentation/yu}}); Anyscale's benchmark reported up to 23x the throughput of naive static batching when combined with vLLM's memory management ({{Anyscale, 2023|https://www.anyscale.com/blog/continuous-batching-llm-inference}}; a single benchmark by an interested party, so read it as "large", not as a constant).

Step 6 Designing it on purpose: the method

The wall
Steps 1 to 5 were reactive. That works until a fix takes months (sharding a live database, buying GPUs), or someone asks for the design before the system exists. Without numbers, a design is a guess drawn in boxes.

The method experienced engineers follow, in roughly this order, which is also what system design interviews expect (Alex Xu compresses it into four phases for 45 minutes: scope 3 to 10 minutes, high-level design 10 to 15, deep dive 10 to 25, wrap-up 3 to 5; {{ByteByteGo|https://bytebytego.com/courses/system-design-interview/a-framework-for-system-design-interviews}}):

Requirements. Functional ones say what the system does; non-functional ones say how well (users, time to first token at p99, the SLO, cost, privacy). The non-functional ones decide the architecture; ask them first.
Estimates. Back-of-the-envelope arithmetic that turns users into requests, tokens, GPUs and bytes, and says which part is hard (below).
API and data model. The endpoints (what is idempotent, what streams, what returns 202) and the tables, each query on an index and carrying the likely shard key.
High-level design, deep dives, trade-offs. The boxes, each justified by a requirement or an estimate; then the two or three parts the estimates flagged; then what breaks at ten times the traffic and what each choice cost.
The estimate step by step: a fleet sized for the average day is short every evening

Predict before you step: if the busy hour runs at twice the average, how many hours of the day does a fleet sized for the average fall short? Then switch to the peak-sized fleet and look at the night.

Every input is an assumption, labelled as such: 10% of users active each day, 10 messages each, 1,000 input and 400 output tokens per reply (the same request shape as the {{Scale simulator|#t-sim}}), a busy hour twice the daily average, 2,000 output tokens per second per GPU, replies streaming for 10 seconds, 2 KB of text per message. The daily traffic shape is invented to average exactly 1. Checked in src/read/recompute.py. The results the child pages reuse: 10 million messages a day, about 116 requests a second on average and 231.5 in the busy hour, 56 GPUs for the busy hour with 20% headroom, 2,315 streams open at once.

Where the peak factor and the GPU figure come from (depth)

The busy hour at twice the daily average is a fair figure for a product used in one region: {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}} measured Wikipedia's busy hour against its day's average for September 2026 at 1.92 for German, 1.63 for Japanese and 1.24 for the worldwide English site; per second, peaks are much sharper, as Twitter's busiest second in August 2013 ran at 25 times its average (see {{Case files|#t-cases}}). The 2,000 output tokens per second per GPU is a round planning number, a little below NVIDIA's maximum-load benchmark row for Llama 3.3 70B in FP8 on two H100s with 1,000 input and 1,000 output tokens per request: 2,209 output tokens/s per GPU ({{TensorRT-LLM perf overview, commit 8a9c66c|https://github.com/NVIDIA/TensorRT-LLM/blob/8a9c66ce086594054d3722307cfed2d658d25e60/docs/source/developer-guide/perf-overview.md}}, vendor figure, the same row the Scale simulator uses); a service holding latency targets gets less, so measure your own; more figures in {{Numbers to know|#t-num}}. Changing any input changes the answer in proportion, which is the point: the method, not the numbers, is what carries over.

Two lessons fall out of the arithmetic. The model layer dominates: 116 requests a second is a small load for app servers and a database, while the same traffic needs tens of GPUs. And the peak sets the size, not the average: a fleet sized for the average is short of capacity for 14 hours of the day, and one sized for the peak sits more than half idle overnight, which is why autoscaling, night-time batch work and routing to smaller models matter so much.

Machine learning design interviews keep this method and swap part of the middle for the metrics that define success offline and online, the data, the model choice, then serving and monitoring (Chip Huyen's free {{Machine Learning Systems Design|https://huyenchip.com/machine-learning-systems-design/toc.html}} booklet uses this framing). In both, what is judged is whether you quantify and name trade-offs, not how many component names you know.
