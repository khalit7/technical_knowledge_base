Step 3 Slow work leaves the request path

The problem appears
A new feature: upload a PDF and chat with it. The server must extract the text, cut it into pieces and compute an embedding for each (a list of numbers representing its meaning, used later to find the passages relevant to a question). For a long document that takes tens of seconds, and done inside the request it holds one of the server's few request slots (threads) the whole time. A handful of uploads fill every slot and quick chat messages queue behind them. In the animation below, 5 uploads among 30 chat messages make chat messages wait up to 3 seconds that should have waited none (illustrative).

The insight: the user does not need the result now; they need to know it is being done. Separate "accept the work" from "do the work".

The building block: a queue and background workers
A message queue is a durable list of jobs that sits between the part of the system that creates work and the part that does it (Amazon SQS, RabbitMQ, Kafka and Redis streams are common ones). The request handler writes "process document 981" to the queue and immediately answers 202 Accepted. Separate workers, processes whose only job is to take jobs off the queue, do the slow work in the background, then mark the document ready; the app shows a spinner until then. This is asynchronous processing: the response does not wait for the work.
Animation: the same uploads, processed inside the request against put on a queue

Illustrative traffic: one server with 4 request slots; 3 chat messages a second (each needs a slot for one second); 5 uploads in the first 6 seconds, each needing 4 seconds of work. Checked in src/read/recompute.py.

Three things a queue makes you think about

Jobs can run twice. A worker can crash halfway through a job. So that nothing is lost, the queue deletes a job only when a worker confirms it (an acknowledgement) and hands unconfirmed jobs out again: at-least-once delivery, whose other face is that a job can run twice. So make jobs idempotent: running one twice has the same effect as running it once ("set document 981's embeddings to X", not "append embeddings"). HTTP defines idempotent the same way: "the intended effect on the server of multiple identical requests ... is the same as the effect for a single such request" ({{RFC 9110 §9.2.2|https://www.rfc-editor.org/rfc/rfc9110#section-9.2.2}}). A job that keeps failing is moved aside to a dead-letter queue for a human to look at, so it does not block the rest.

A queue can hide overload. If jobs arrive faster than workers finish them, the queue grows and nothing looks broken; results just arrive later and later. Amazon's David Yanacek describes queue systems as having two modes: with no backlog "the system's latency is low", and once a backlog forms, "end-to-end latency grows higher and higher" and it can take a long time to recover ({{Avoiding insurmountable queue backlogs|https://builder.aws.com/content/3EuRcgkTP1MI0c7zM8W6HL3WIqA/avoiding-insurmountable-queue-backlogs}}). So you watch the age of the oldest job, not just errors, and you apply backpressure: when the queue is too long, tell the producers to slow down or refuse new work (for example with HTTP 429 Too Many Requests, {{RFC 6585|https://www.rfc-editor.org/rfc/rfc6585}}) instead of accepting work you cannot finish.

How many workers you need is arithmetic. Little's law says that, on average, the number of things in a system equals the rate they arrive times the time each one stays: L = λW ({{Little, 50th-anniversary paper|https://people.cs.umass.edu/~emery/classes/cmpsci691st/readings/OS/Littles-Law-50-Years-Later.pdf}}). If 5 documents arrive per second and each takes 20 seconds of work (illustrative), then on average 5 × 20 = 100 documents are being processed at once, so you need at least 100 worker slots; with fewer, the queue grows without bound. The same law sizes the model layer in Steps 5 and 6.

What it costs
The result arrives later and the product must show progress; failures happen out of sight and need their own alerts; jobs must be idempotent; and the queue is one more system to run. Use it for slow work that can be late, not for the reply the user is staring at.
