Step 3 Slow work leaves the request path

The wall
Uploading a PDF to chat with it means extracting text, cutting it into pieces and computing an embedding for each (a list of numbers standing for its meaning): tens of seconds. Done inside the request, it holds one of the server's few request slots the whole time, and quick messages queue behind it. On a server with 4 slots, 5 uploads among 30 chat messages made chat messages wait up to 3 seconds that should have waited none (illustrative, checked in src/read/recompute.py).

The user does not need the result now; they need to know it is being done. So the handler writes "process document 981" to a message queue and answers 202 Accepted at once, and separate workers do the work in the background: asynchronous processing.

Three consequences follow, and each has an owner. Jobs can run twice: so that nothing is lost, the queue deletes a job only when a worker confirms it (at-least-once delivery), so jobs must be idempotent, and a job that keeps failing goes to a dead-letter queue. A queue can hide overload: the backlog grows while nothing looks broken, so watch the age of the oldest job and apply backpressure (slow producers down, or refuse work with 429). Workers are sized by arithmetic: Little's law, L = λW, says 5 documents a second at 20 seconds each keeps 5 × 20 = 100 jobs in progress, so at least 100 worker slots (illustrative); the same law sizes the model layer in Steps 5 and 6.

The price, across pages
Results arrive later and the product must show progress; failures happen out of sight and need their own alerts; every job must survive running twice. A queue is for work that can be late, never for the reply the user is staring at.

Step 4 Things fail, and the fixes can make it worse

The wall
At dozens of machines and several outside services, something is always failing. Say 1 request in 100 to the model provider hangs for a minute during a slow hour (illustrative): each hung call holds a slot, slots run out, and one dependency's problem takes the whole product down.

The defences, each a fix with a price, in the order a request meets them:

DefenceWhat it doesHow it backfires
TimeoutA deadline on every call; give up and free the slotToo long and slots pile up; too short and calls that would have succeeded are abandoned
Retry with exponential backoff and jitterTries again after a growing, randomised waitRetries add load exactly when the system struggles: five layers that each try three times multiply the load on the bottom one 243 times (35), a retry storm. Jitter spreads retries out but removes no work; a retry budget or a bounded queue does
Idempotency keyA client-chosen ID per action, so a retried charge returns the stored result instead of charging twiceNeeds storage, an expiry and an atomic claim
Circuit breaker, load shedding, graceful degradationStop calling what is broken; reject excess early; fall back to a smaller model or no searchThe least-tested code you own: it runs only when something is already wrong

A failure that sustains itself after its trigger is gone, usually because retries keep the overload going, is a metastable failure. Reliability engineering measured one on a laptop service: with backoff and full jitter, success stayed at 25%, the same as retrying at once; a retry budget reached 72% and a bounded queue that rejects the excess at once 87%.

How reliable is enough gets a number. An SLI measures the service (the share of messages answered within 10 seconds), an SLO is its target, an SLA the contract built on it, and the gap to perfection is the error budget, spent on shipping. An SLO of 99.9% at 10 million messages a day (Step 6's estimate) allows 10,000 failures a day, about 300,000 in a 30-day month. Seeing whether it holds is observability: logs (one line per event), metrics (numbers over time) and traces (one request followed across every service), joined by one trace ID.
