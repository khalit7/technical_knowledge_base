The idea in one screen

A production service is one request path through a few layers (servers, data, slow work, failure handling, the model), and every building block on that path fixes one bottleneck at a price you can name; add it only when its bottleneck has arrived.

System design is the craft of keeping a product fast, correct and affordable as more people use it. The running example. A chat assistant powered by a large language model (LLM): people sign in, chat, upload documents and come back to their history. It starts on one machine with one user and grows to ten million registered users. Every child page of this topic uses the same product, so its numbers line up from page to page. Fig. 1 grows it one wall at a time, in the order the walls arrive: the part that breaks turns red, the building block that fixes it arrives green and names the child page that owns it, and the dots are requests on the paths they take.

Fig. 1 · The product grown wall by wall, each fix with its owner

  1. 1 user: everything on one machine. App code, database and a call to a model API share one server, and requests are a trickle. Nothing is wrong yet, so nothing is added yet.
  2. Step 1: too many requests for one server. 600 a second arrive at a server that answers 400 (illustrative), and the line grows without bound. The fix: a load balancer in front of stateless servers, with the state moved into one shared database. Owners: {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}} and {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}.
  3. Step 2: the database becomes the bottleneck. 1,000 reads a second against about 600 answered (illustrative). The fix: a cache that answers nine reads in ten, then read replicas. Owners: {{Topic: databases|n:3cd5c17b0d0d815d8841ec845f5f3324}} and {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}}.
  4. Step 3: slow work leaves the request path. Uploads take tens of seconds and hold the server’s few slots, so chat messages wait behind them. The fix: a queue and workers, the request answered 202 Accepted at once. Owner: {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}.
  5. Step 4: things fail, and the fixes can make it worse. 1 call in 100 to the model provider hangs for a minute (illustrative), and the hung calls use up every slot. The fix: timeouts, retries with backoff and jitter and a breaker, watched against an SLO. Owners: {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}} and {{Observability|n:3ef5c17b0d0d811e8490c54dd42c2b9b}}.
  6. Step 5: the GPU layer. Reading an 8-billion-parameter model’s weights takes 4.8 ms per token, so one conversation gets at most about 210 tokens a second. The fix: batching (64 conversations share each read, about 13,000 tokens a second) and a model router. Owners: {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}}, {{Gateways and routing|n:3f15c17b0d0d81e4a964c129a3e520ae}} and {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}.
  7. Step 6: designing it on purpose. Estimate before building: 10 million messages a day is 231.5 requests a second in the busy hour, 56 GPUs and 2,315 streams open at once, so the model layer is the hard part. Owners: {{System design case studies|n:3ef5c17b0d0d81c3b211d75127ef5ded}} and Capacity planning.
  8. Every step: the code under the boxes. Each fix is code someone must change safely later: tests at the right layer, modules that hide their decisions. Owners: {{Testing and quality|n:3c65c17b0d0d81548848e2ebdd2f63ee}} and {{Code design|n:3ef5c17b0d0d817b99a0ff9701ff30cd}}.

The walls' numbers are the illustrative ones of Steps 1 to 4 below, the derived ceilings of Step 5 and the estimate of Step 6, and the map below gives each fix its price; the layout (the request path in the middle, the model in front, slow work behind) is a drawing, not a deployment. A cache makes reads fast and data slightly stale; a queue makes requests fast and results late; a retry rescues one request and can sink the whole system: every green block is a fix with a price.

You need: nothing from other pages. The wire under Step 1 (DNS, TCP, TLS, HTTP) is {{Topic: protocols|n:3c65c17b0d0d81ec9355f4eecd6eed02}}, the database under Step 2 is {{Topic: databases|n:3cd5c17b0d0d815d8841ec845f5f3324}}, and the engine under Step 5 is {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}; this page needs only their one-line definitions, given where they are used.

New terms (each defined where it first appears, and only these):

Latency, throughput: how long one request takes; how many finish per second.
p50, p99: the latency that 50% or 99% of requests beat.
Stateless: a server that keeps nothing another server would need.
Replica, shard: a full copy of the database; a slice of it.
At-least-once, idempotent: no job is lost, so one can run twice; running twice has the effect of once.
SLO, error budget: the reliability target; the failures it allows.
Prefill, decode: reading the prompt at once; writing the reply one token per step.
Back-of-the-envelope estimate: arithmetic accurate to a factor of two that finds the hard part.

Three tools on this page span every child: the {{Scale simulator|#t-sim}} pushes traffic through the whole design and shows which part breaks first, {{Numbers to know|#t-num}} holds the latency, throughput and price figures every page estimates with, and {{Case files|#t-cases}} tells real outages and redesigns, each tagged with the step it belongs to.
