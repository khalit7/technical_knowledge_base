Across the steps: how a senior engineer reasons

The habits that use all six steps; each is a question asked before adding anything, and each is taught in depth by the page named.

Start from the invariant, not the component. Write down what must never happen ("never charge twice", "never lose a message") and what may ("the sidebar is a second stale"), then choose consistency and retries per invariant (Distributed systems fundamentals, Reliability engineering).
Do the arithmetic first. Requests, tokens, GPUs, bytes: the numbers say which part is hard (Step 6, System design case studies).
Add a block only when its problem has arrived. A cache before reads hurt or sharding before one machine is full adds cost and failure modes for nothing. A bigger machine and one Postgres go a long way.
Name the cost of every choice. "We cache chat lists for 30 seconds; a renamed chat can show the old name for up to 30 seconds; acceptable." If you cannot say what a choice gives up, you do not yet understand it.
Design for failure as the normal case. Every call gets a timeout; retries get backoff, jitter and a cap; every retried write gets an idempotency key; every queue is bounded; there is a planned worse-but-working mode; and those paths are tested on purpose (Reliability engineering, Testing and quality).
Measure before and after. Percentiles, not averages; an SLO that says when reliability is good enough. Unmeasured "fixes" often move the problem (Observability, Capacity planning).
Prefer reversible decisions, and decide the irreversible ones late. A function can be rewritten tomorrow; a public API, a schema and a shard key are very expensive to change later, so spend your care there (Code design, Service APIs).

The code under every step. Each fix above is code someone must change safely later.
