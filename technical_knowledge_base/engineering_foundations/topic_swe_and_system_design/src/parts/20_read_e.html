Step 5 The GPU layer: a backend unlike the others

The problem appears
Everything so far assumed a request costs milliseconds of an ordinary processor. A chat reply costs seconds of a GPU (the graphics processor that models run on, with its own fast memory). A model generates text one token (a word or piece of a word) at a time, and for every token it must read all of its weights from GPU memory. For an 8-billion-parameter model in 16-bit numbers that is 16 GB per token; an NVIDIA H100 reads memory at 3.35 TB/s ({{NVIDIA|https://www.nvidia.com/en-us/data-center/h100/}}), so one conversation can get at most about 210 tokens a second, and a 500-token reply takes at least 2.4 seconds (derived: 16 GB ÷ 3.35 TB/s = 4.8 ms per token). One user at a time per GPU will not serve ten million.

Why a model is not a normal backend

  • Two phases. Reading the prompt (prefill) handles all its tokens at once and is limited by arithmetic; writing the answer (decode) makes one token per step and is limited by memory bandwidth, as above.
  • Long-lived responses. Replies are streamed token by token over one open connection (commonly server-sent events, SSE), so each reply holds a connection open for seconds (Little's law counts them in Step 6).
  • Capacity comes in big, slow blocks. A 70-billion-parameter model in 16-bit numbers is 140 GB of weights, more than one 80 GB H100 holds, so one copy of the model (a model replica) spans several GPUs. You add capacity a replica at a time, and a new replica must load its weights before serving: 140 GB at an illustrative 2 GB/s is 70 seconds, before starting the packaged program (the container) and warming up. These cold starts take minutes, so GPUs cannot be added the moment a spike arrives.
  • Memory per conversation. To avoid recomputing the conversation for every new token, the model keeps intermediate results for every token so far: the KV cache. It grows with the conversation in scarce GPU memory, so it often limits how many users a GPU serves at once ({{PagedAttention, KB paper page|n:3c65c17b0d0d81bf8b90ca93fee19f5f}}).

Batching: one read of the weights, many users

Since each decode step reads all the weights anyway, the same read can produce the next token for many conversations at once: batching. With 64 conversations in a batch, the 4.8 ms weight read yields 64 tokens instead of one, a ceiling of about 13,000 tokens a second (derived, ignoring KV cache reads and arithmetic). Real engines go further with bigger batches and smaller number formats: NVIDIA's published performance overview (v0.21 data) reports about 15,000 output tokens a second for Llama 3.1 8B in 8-bit on one H100, 1,000 input and 1,000 output tokens per request, at maximum load (vendor benchmark; see {{Numbers to know|#t-num}}). The catch is that replies have different lengths. In static batching the batch runs until its longest reply finishes, and slots whose reply ended early sit idle. Continuous batching (iteration-level scheduling, introduced by Orca, {{OSDI 2022|https://www.usenix.org/conference/osdi22/presentation/yu}}) lets a new request take a slot the moment one frees up, at every step. Anyscale's benchmark reported up to 23x the throughput of naive static batching when combined with vLLM's memory management ({{Anyscale, 2023|https://www.anyscale.com/blog/continuous-batching-llm-inference}}; a single benchmark by an interested party, so read it as "large", not as a constant).

Do less work: caching prompts, routing, limits

Prefix caching. Requests in a conversation start with the same system prompt and history; engines can keep the KV cache of that shared beginning and skip its prefill: prefix caching ({{vLLM docs|https://docs.vllm.ai/en/latest/features/automatic_prefix_caching.html}}). Model providers sell the same idea: Anthropic says prompt caching reduces "costs by up to 90% and latency by up to 85% for long prompts" ({{Anthropic|https://claude.com/blog/prompt-caching}}; vendor figure), and OpenAI applies it automatically to long prompts and advises putting "stable developer instructions and shared reference material first" ({{OpenAI docs|https://developers.openai.com/api/docs/guides/prompt-caching}}). Lesson: what never changes goes first in the prompt. A riskier cousin, the semantic cache, returns a stored answer when a new question merely looks similar to an old one; it is cheap and wrong whenever the answer should depend on who is asking or when.

Routing across models. A model router sends easy requests to a small, cheap model and hard ones to the large model, and doubles as Step 4's degradation path.

Rate limits per customer. A rate limit caps how much each user or tenant (a customer organisation) may send per minute; past it they get 429 Too Many Requests. The common algorithm is the token bucket: each customer has a bucket that refills at a steady rate, and each request takes from it, which allows short bursts but caps the average (Stripe: "We use the token bucket algorithm", {{Stripe, 2017|https://stripe.com/blog/rate-limiters}}). For a model, limit tokens per minute as well as requests, because one request with a 100,000-token document costs as much as a thousand short ones.

What it costs
Batching trades a little latency per user for much more throughput per GPU. Output caches can serve the wrong answer to the wrong person; routers misjudge difficulty. And GPUs are expensive idle and slow to add, so fleet size is a bet on tomorrow's traffic, which Step 6 estimates.
