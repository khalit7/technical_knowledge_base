Step 4 Things fail, and the fixes can make it worse

The problem appears
The system is now dozens of machines and several outside services. At this size something is always failing: a server reboots, a link drops packets, the model provider has a slow hour. Say 1 request in 100 to the model provider hangs for a minute during that hour (illustrative). Each hung call holds a request slot (Step 3) for a minute, slots run out, and one dependency's problem takes down your whole product.

Timeouts: never wait forever

A timeout is a deadline on every call to another system: if no answer comes within it, give up and free the slot. Too long and slots pile up; too short and you abandon calls that would have succeeded. Marc Brooker of AWS describes the usual way to choose: pick an acceptable rate of false timeouts, "such as 0.1%", then set the timeout at the matching latency percentile of the service you call, "p99.9 in this example" ({{Timeouts, retries and backoff with jitter|https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter}}).

Retries, and why they need backoff and jitter

Many failures are momentary, so the natural fix is a retry. Retries rescue single requests and can sink the system: each is extra load arriving exactly when it struggles. Brooker's example: if each of five layers of a system retries three times, "the load on the database will increase 243x" (35), "making it unlikely to ever recover". A flood of retries that keeps a recovering system down is a retry storm, and the general pattern, a system that stays broken after its trigger is gone because something (often retries) sustains the overload, is what Bronson and colleagues called a metastable failure ({{HotOS 2021|https://sigops.org/s/conferences/hotos/2021/papers/hotos21-s11-bronson.pdf}}).

Two habits fix it. Exponential backoff waits longer after each failure (1, 2, 4, 8 seconds, up to a cap), so retries thin out. Jitter makes each wait random, because clients that failed together and back off by the same amounts retry together again, in synchronised waves. Brooker's simulation compared the variants and found that backoff without jitter "is the clear loser"; his recommended "full jitter" waits a random time between zero and the backoff ({{AWS Architecture Blog, 2015|https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/}}). Know what jitter does and does not do: it spreads retries out in time, so they can fit into spare capacity, but every retry still arrives eventually; it does not remove work. When new requests keep coming (an "open" system) and there is no spare capacity left, backoff with jitter alone does not end a retry storm. {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}} measured exactly this on a laptop service ("A retry storm, measured"): with backoff and full jitter success stayed at 25%, the same as retrying at once, while a retry budget (retries capped at a share of requests) reached 72% and a bounded queue that rejects the excess at once reached 87%. So cap the number of attempts, keep a retry budget, retry at one layer only, and retry only requests that are safe to repeat, which is the second half of the animation.

The double charge, and idempotency keys

A user buys 1,000 credits for $20. The server charges the card and the response is lost (the phone went into a tunnel). To the client, a failure before the charge and one after it look identical. Retry, and the user may pay twice; don't, and they may get nothing. Brandur Leach of Stripe lays out the cases ({{Stripe, 2017|https://stripe.com/blog/idempotency}}). The fix is an idempotency key: the client invents a unique ID for this one purchase and sends it with every attempt. The server records the key together with the result; a retry with the same key gets the stored result back instead of a second charge. AWS does the same with "client request tokens", and returns an error if the same token arrives with different parameters ({{Featonby, Builders' Library|https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/}}). This is how a request that is not naturally idempotent (Step 3) is made safe to retry.

Failing well: circuit breakers, load shedding, degradation

A circuit breaker wraps calls to a dependency and counts failures; past a threshold it "opens" and fails calls immediately for a while, without calling, then lets a few test calls through to see whether the dependency has recovered ({{Fowler|https://martinfowler.com/bliki/CircuitBreaker.html}}). Load shedding is the same reflex applied to your own service: when nearly overloaded, reject the excess quickly so the requests you accept still succeed ({{Yanacek, Builders' Library|https://builder.aws.com/content/3Eun1EEyX6p2e3VYNyRLSJzLuMV/using-load-shedding-to-avoid-overload}}). Graceful degradation decides in advance what a worse-but-working product looks like: if the large model is down, answer with a smaller one; if search is slow, answer without it; and only then show an honest error.

How reliable is reliable enough: SLOs and error budgets

"Never fail" is impossible, so reliability gets a number. An SLI (service level indicator) is "a carefully defined quantitative measure" of service, such as the share of chat requests answered successfully within 10 seconds; an SLO (objective) is "a target value ... for a service level that is measured by an SLI"; an SLA (agreement) is the contract, with consequences, built on them ({{SRE book, ch. 4|https://sre.google/sre-book/service-level-objectives/}}). The gap between the SLO and perfection is the error budget: Google's SRE teams treat it as "the 'budget' of how much 'unreliability' is remaining", and "as long as there is error budget remaining ... new releases can be pushed" ({{SRE book, ch. 3|https://sre.google/sre-book/embracing-risk/}}). For our product: an SLO of 99.9% of messages succeeding, at 10 million messages a day (Step 6's estimate), allows 10,000 failures a day, about 300,000 in a 30-day month. Spend it on shipping; when it is gone, slow down and fix.

Seeing inside: observability

Observability, seeing inside a running system, rests on three kinds of signal ({{OpenTelemetry|https://opentelemetry.io/docs/concepts/signals/}}): logs (a timestamped line per event: "request 7f3 failed: provider timeout"), metrics (numbers over time: requests per second, p99 latency, error rate), and traces (one request followed across every service it touched, with the time spent in each, which is how you find which of twelve hops was slow). Google's starting set of metrics is the four golden signals: latency, traffic, errors and saturation, "how 'full' your service is" ({{SRE book, ch. 6|https://sre.google/sre-book/monitoring-distributed-systems/}}).

What it costs
Each adds code that only runs when something is already wrong, the least tested code you own. Retries add load; idempotency keys need storage and an expiry; observability costs money per log line. Name the failure each mechanism defends against, and test it on purpose.
