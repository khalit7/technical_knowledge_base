A system design question gives you a product ("design a URL shortener") and an hour, and asks for the machines, data and connections that would run it for millions of people. What every design on this page has in common

1. Requirements before boxes. Every design starts with a box of functional and non-functional requirements; the second kind (scale, latency, how wrong you may be) decides the architecture.

2. A computed estimate, live. Each design has a table you can change (try "10× the traffic"); rows turn red when they cross a single machine's capacity. That is how a bottleneck is found rather than guessed.

3. A diagram that grows. Each design is animated from its naive version, then each bottleneck is found (red) and fixed (green) in turn, with counters showing the naive design's number beside the current one on the same load.

4. What was rejected, and why. A design is a list of trade-offs. Each section says what it chose, what it turned down, and what real companies did.

The estimating toolkit

Every estimate on this page uses the same few constants, taken from the parent root's Numbers to know tab so the topic stays consistent:

  • A day is 86,400 seconds (call it 100,000 for mental arithmetic: a million a day is about 12 a second), and a month is 2.6 million seconds.
  • Peak over average: traffic is not flat. The root uses 2 as an illustrative planning factor; Twitter's record second in 2013 was 25 times its average (root, Case files: Twitter 2013). Say which you assume.
  • One app server (AWS m7i.xlarge, $0.2016 an hour): 500 requests a second, the root's illustrative default.
  • One PostgreSQL database: about 35,000 read queries a second, 18,000 in a mixed read-write benchmark (PlanetScale, 4 vCPU; root Numbers). We plan at half a benchmark, the root's derating.
  • One Redis node: 180,180 SETs a second with 50 clients (Redis docs benchmark); planned at half, 90,090. A Redis operation answers in about 0.14 ms locally; a round trip inside one cloud region is about 0.5 ms.
  • GPUs: 2,209 output tokens a second per H100 for Llama 3.3 70B in FP8 (TensorRT-LLM, commit 8a9c66c), $3.99 per GPU-hour (Lambda); see ML system design, section 1.
  • Little's law: things in the system = arrival rate × time each one stays. It turns "requests a second" into "connections open" or "jobs running" (Capacity planning and performance, Queueing theory you actually use).
The commonest failure: no numbers, or numbers that change nothing

An estimate earns its minutes only if it changes a decision. "36 billion links do not fit in 6 base62 characters" changes the code length; "18 TB" changes whether you shard; "333,000 presence heartbeats a second" changes what you optimise first in chat. If a number would not change any box, skip it and say so.

Design 1URL shortener: IDs, base62, caching, read-heavy scaling

The warm-up question, asked because it is small enough to finish and still touches IDs, caching, HTTP and storage. A URL shortener turns a long address into a short one (sho.rt/aZ3kQ9x); visiting the short one redirects the browser, meaning the server answers "go here instead" with the long address, and the browser follows it.

Requirements (agreed with the interviewer)
Functional
  • Create a short link for a long URL; optionally a custom alias.
  • Visiting the short link redirects to the long URL.
  • Count clicks per link (owners see analytics).
  • Out of scope: accounts, editing, link previews.
Non-functional
  • Sized like Bitly in 2014: 600 million new links and 6 billion clicks a month (High Scalability, 2014, a summary of a Bitly engineer's talk).
  • Redirect fast: under 50 ms at the server, p99.
  • Links never break, kept 5 years; never give two users the same code.
  • Click counts may lag by minutes; a few lost clicks are acceptable.

What the numbers say. Writes are 230 a second: one database handles that with ease. Redirects are 10 times more, and under 5,000 a second at peak: still within one database (about 17,500 a second at our half-benchmark planning figure), so the cache is about latency and headroom, not survival. Two numbers do change the design: 36 billion links after five years fill 63% of the 6-character code space, so random 6-character codes would collide on most attempts and 7 characters are needed; and 18 TB of rows is more than one comfortable database server, so the storage must be split later. The app tier needs about a dozen servers, which matches the order of magnitude Bitly reported: "~30 servers handle all incoming traffic from the outside world including shortens, redirects, api requests, web ui, etc." (same source).

API

POST /v1/links create; Idempotency-Key header makes retries safe {"url": "https://example.com/a/very/long/path", "alias": null} -> 201 {"code": "aZ3kQ9x", "short_url": "https://sho.rt/aZ3kQ9x"} -> 409 if the alias is taken; 422 if the URL is not http(s) GET /{code} the redirect: the hot path -> 302 Found, Location: https://example.com/a/very/long/path -> 404 if unknown, 410 Gone if taken down for abuse GET /v1/links/{code}/stats?from=.. owner analytics, read from the analytics store

Status codes, the Idempotency-Key header (a client-chosen ID that lets the server recognise a retried request and return the first answer instead of creating a second link) and error bodies are taught in Building a backend API, sections 7 and 10.

Data model

Deep dive: where do short codes come from?

Base62 writes a number with 62 symbols (0 to 9, a to z, A to Z), so each character carries one of 62 values: 6 characters give 626 = 56.8 billion codes, 7 give 3.52 trillion. Three ways to fill them, each with a cost:

  • Hash the long URL (for example the first 7 base62 characters of its SHA-256). The same URL always gets the same code, which deduplicates for free. But different URLs can produce the same 7 characters, so every create must check and handle a collision, and two users shortening the same URL share one code and one click count, which breaks per-owner analytics. Rejected as the main scheme.
  • Random codes, checked for uniqueness on insert (a unique index makes the database refuse a duplicate, and the server retries). Simple and unguessable; the chance a new code collides is the share of the space already used: about 1% at 7 characters after five years, 63% at 6. Acceptable at 7 characters.
  • A counter turned into base62. No collisions ever, and IDs are short. Its two costs: a single counter is a coordination point every create must reach, and sequential codes let anyone walk through every link (aZ3kQ9x, aZ3kQ9y, ...), which leaks private links. Chosen, with both costs removed: each app server leases a block of, say, 10,000 numbers at a time from an ID range service (one row incremented in a database), so a create needs no network call, and the number is passed through a fixed reversible scramble (a permutation of the 7-character space) before encoding, so neighbouring numbers give unrelated codes.
What real companies built

Flickr, 2010: "Ticket servers give us globally (Flickr-wide) unique integers to serve as primary keys in our distributed setup": a MySQL table where REPLACE INTO plus LAST_INSERT_ID() hands out the next number, run on two servers, one giving odd and one even numbers, so either can fail (Kremerskothen, Flickr, 2010-02-08).

Twitter Snowflake, 2010: a 64-bit ID made of "time - 41 bits (millisecond precision w/ a custom epoch gives us 69 years)", a "configured machine id - 10 bits - gives us up to 1024 machines" and a "sequence number - 12 bits - rolls over every 4096 per machine", so machines "should not have to coordinate with each other" and IDs sort roughly by time (snowflake README, 2010; announcement, 2010-06-01). Snowflake IDs are too long for a shortener (a 64-bit number needs 11 base62 characters) but are the standard answer for "unique IDs across many machines", and Discord uses them for every message (design 3). Instagram built the same idea inside PostgreSQL (root Case files: Instagram 2012).

Deep dive: 301 or 302?

Both status codes redirect. The difference is caching. RFC 9110 says "A 301 response is heuristically cacheable", meaning a browser or proxy may reuse it without asking again, while 302 "Found" says the target "resides temporarily under a different URI" and is not on the list of heuristically cacheable codes (RFC 9110 §15.4.2, §15.4.3, §15.1). A cached 301 is free for you, but the browser stops coming back, so you lose its later clicks and cannot change or take down the destination for that browser. Choose 302 (or 301 with an explicit short cache lifetime) when analytics or takedowns matter. Bitly answers 301 with cache-control: private, max-age=90 (checked with curl -I on 2026-10-04, src/inputs/bitly_headers.txt): shared caches may not store it and a browser may reuse it for only 90 seconds, so nearly every click still reaches Bitly. Bitly's reason is not published; this is an observation, not their statement.

Deep dive: the cache, and counting clicks without slowing redirects

The redirect path is: look up the code in Redis (an in-memory key-value store, about 0.14 ms a lookup); on a miss, read the database and put the answer in Redis with a TTL (time to live, after which the entry expires). That pattern is cache-aside, taught with its traps (stampedes when a hot key expires, stale entries after a takedown: delete the key on takedown) in Capacity planning and performance, Caching strategy. Links are written once and almost never change, the easiest possible thing to cache. Click counting must not sit on the redirect path: an UPDATE links SET clicks = clicks + 1 on every visit turns each redirect into a write, and a viral link becomes one row that thousands of requests lock in turn. Instead the server emits a click event to a queue and answers immediately; consumers aggregate counts per link per hour. Bitly did exactly this: "Data about the conversion is popped onto a queue for the analytics and other downstream systems" (High Scalability, 2014). Delivery is at-least-once (an event may arrive twice after a crash), which a few duplicate clicks tolerate; how queues behave is in Queues, streams and async work.

Deep dive: 18 TB, and when to split the database

The access pattern is a pure key lookup by code, with no joins: the easiest data to partition (split rows across several databases by a key). Hash the code to pick a shard; each shard has a replica for failover. Do not do this on day one: the first year is 3.6 TB and 230 writes a second, which one PostgreSQL primary with a replica handles. Plan the split (use a shard key now, so moving later is mechanical) and execute it when storage or write rate demands it. A partitioned key-value store (DynamoDB, Cassandra) fits this pattern natively and is an equally good answer; pick what the team can operate. How partitioning and consistent hashing work: Distributed systems fundamentals, Partitioning.

Design 2Rate limiter as a service: algorithms, distributed counters, Redis Lua

A rate limiter caps how often one client (an API key, a user, an IP address) may call you, and rejects the excess with 429 Too Many Requests. The algorithms themselves (fixed window, sliding window, token bucket, leaky bucket) are taught, animated on one burst of traffic, in Reliability engineering, Rate limiting: per-client fairness, and what a client sees (the 429, Retry-After, remaining-allowance headers) in Building a backend API, section 12. The design question is different: many servers must enforce one limit together, in well under a millisecond, without becoming the thing that takes the API down.

Requirements
Functional
  • Limits per API key per second and per minute, configurable per plan.
  • A check call: "may key K do one more request?" answering allow or deny, plus remaining allowance.
  • Rules change without a deploy.
Non-functional
  • 50,000 requests a second at peak across 50 gateway servers; 1 million active keys (illustrative).
  • Adds under 1 ms at p99.
  • Accuracy: a few percent over the limit is fine; 50 times over is not.
  • If the limiter breaks, the API must keep working (fail open).

What the numbers say. One Redis node, planned at half its benchmark, handles the whole fleet's checks today, and the counters fit in 200 MB, so this is not a big-data problem. Two things are hard. First, the network round trip (about 0.5 ms in a region) is most of the latency budget, so a check must be one round trip, not three. Second, counting only inside each server gives a client up to 50 times its limit if its requests spread over all 50 servers: the row turns red. At 10× traffic you need several Redis primaries, which brings sharding and hot keys.

API

// internal gRPC or HTTP call from each gateway, or a library that talks to Redis directly Check(domain="public_api", descriptors=[("key","k_123"),("plan","pro")], cost=1) -> {allowed: true, remaining: 41, reset_after_ms: 380} // what the public client sees when denied HTTP/1.1 429 Too Many Requests Retry-After: 1

The shape mirrors Envoy's open-source limiter, "a Go/gRPC service designed to enable generic rate limit scenarios", where "A descriptor is a list of key/value pairs owned by a domain that the Ratelimit service uses to select the correct rate limit" and counters live in Redis (envoyproxy/ratelimit README).

Data model

-- token bucket per key: two fields, one Redis hash, expiring when idle rl:{k_123} -> tokens = 41.7, ts = 1759600000123 TTL 2 x (capacity / refill rate) -- rules: a small table or config file, cached in every gateway rules(plan, window, limit, burst)

The design, built step by step

Deep dive: the race, measured

The naive shared counter reads the count, compares it with the limit, then writes count + 1. Between the read and the write another server can read the same count, so both admit a request the limit should have refused. This is a race condition (the result depends on the timing of concurrent operations), the same check-then-act bug that makes a retried payment charge twice. It is easy to dismiss as rare; it is not.

Measured for this page: one key, limit 100, 32 clients at once (PostgreSQL 16.2, laptop, 3 runs)

Each of 32 threads sent 25 requests for the same key at the same moment. Check-then-act (SELECT n, then UPDATE n = n + 1 if under the limit) admitted . Atomic (UPDATE ... SET n = n + 1 WHERE n < 100 RETURNING n, one statement) admitted exactly 100 every time. Measured on PostgreSQL because no Redis was installed on this machine; the race and the fix are the same in Redis, where GET then SET races and a Lua script or INCR-then-compare does not. src/lab/measure_pg.py, 2026-10-04.

Redis gives two atomic forms. INCR increments and returns the new value in one step; the Redis docs show the classic "Pattern: rate limiter" with INCR and EXPIRE, and warn that "If for some reason the client performs the INCR command but does not perform the EXPIRE the key will be leaked" (Redis INCR docs). For anything more than a counter (a token bucket reads tokens and a timestamp, computes, writes both), send a Lua script: "Redis guarantees the script's atomic execution. While executing the script, all server activities are blocked during its entire runtime" (Redis scripting docs). The cost is that a slow script blocks every other client of that node, so scripts must be short.

-- token bucket in one round trip (KEYS[1] = rl:{key}; ARGV = rate, capacity, now_ms, cost) local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts') local rate, cap, now, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4]) local tokens = tonumber(b[1]) or cap local ts = tonumber(b[2]) or now tokens = math.min(cap, tokens + (now - ts) / 1000 * rate) -- refill for the time elapsed local ok = tokens >= cost if ok then tokens = tokens - cost end redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now) redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 2000)) return {ok and 1 or 0, tokens}

Written for this page, following the structure of Stripe's published gist (below); the clock comes from the caller, so gateways need roughly synchronised clocks, or the script can call TIME on the Redis server instead.

Deep dive: where the limiter lives, and what happens when it breaks

  • In each server's memory only. No network call, zero added latency. Each server enforces limit ÷ servers, which is exact only if the load balancer spreads every client evenly; a client hitting few servers is throttled too hard, and one hitting all of them less. Rejected as the only layer; kept as a coarse local backstop for when Redis is unreachable.
  • A central store (Redis), one atomic call per request. Accurate, one round trip. Chosen.
  • Batching: each server takes a lease of N tokens from the central store and spends them locally. Fewer round trips, slightly over-admits when leases go unused. Kept in reserve for hot keys at 10× traffic.

Fail open. When the limiter cannot answer (Redis timeout, script error), allow the request and count the failure. A limiter that fails closed turns a Redis blip into a full API outage. Stripe's rule: "Make sure that if there were bugs in the rate limiting code (or if Redis were to go down), requests wouldn't be affected", plus "Dark launch each rate limiter to watch the traffic they would block" (Tarjan, Stripe, 2017-03-30). The call to Redis needs a short timeout (a few milliseconds) and a circuit breaker, as taught in Reliability engineering, Circuit breakers.

Sharding and hot keys. Beyond one node, shard counters by key (hash of the key picks the node), so each key's counter lives on exactly one node and stays atomic. One enormous tenant still lands on one node; give it leased tokens or its own node. Replicas help availability but not accuracy: a replica can serve a stale count, and GitHub hit a subtler bug, below.

What real companies built

Stripe (2017-03-30): "At Stripe, we operate 4 different types of limiters in production. The first one, the Request Rate Limiter, is by far the most important one", restricting "each user to N requests per second"; then a concurrent-requests limiter ("You can only have 20 API requests in progress at the same time") and two load shedders that reserve capacity for critical traffic. "We use the token bucket algorithm to do rate limiting. ... We implement our rate limiters using Redis" (one quote joined from two sentences; Stripe blog). The companion gist "relies on the fact that Redis scripts execute atomically. No other operations can run between fetching the count and writing the new count" (gist).

Cloudflare (2017-06-07): counts in memcache inside each data centre, where "the only operations available were GET, SET and INCR", using the sliding window counter approximation (worked example: "rate = 42 * ((60-15)/60) + 18 = 42 * 0.75 + 18 = 49.5 requests"). Measured on real traffic, "0.003% of requests have been wrongly allowed or rate limited"; increments run asynchronously "without slowing down the requests"; it "handles several billion requests per day" and absorbed "as many as 400,000 requests per second to a single domain" (Desgats, Cloudflare). Note the trade: Cloudflare counts per data centre, not globally, accepting that an attacker spread across the world is judged locally.

GitHub (2021-04-05, updated 2023): moved off shared Memcached because "when it filled up, it would sometimes evict rate limiter data, even when it was still active", to "a replicated Redis backend with client-side sharding", with storage logic "in Lua, to guarantee atomicity", rolled out behind a feature flag. The surprise: "replicas don't expire data until they receive instructions to do so from their primaries", so reads from replicas saw expired windows; they stored the reset time explicitly (Mosolgo, GitHub).

Design 3Chat and messaging: WebSockets, fan-out, ordering, presence, storage

A chat system delivers a message from one person to the others in a conversation within a second, keeps the history forever, and shows who is online. The new ingredient compared with designs 1 and 2 is that the server must push: a message arrives for you while you are not asking for anything.

Requirements
Functional
  • One-to-one and group conversations (we call both channels), groups up to a few thousand members.
  • Real-time delivery to online members; offline members see the messages when they return, and get a push notification.
  • Full history, scrollable; presence (online dots); read receipts.
Non-functional
  • 50 million daily users, 40 messages each a day, 20% connected at the peak (illustrative).
  • Delivery under 500 ms for online members.
  • Messages are never lost once acknowledged; order within a channel is the same for everyone.
  • History kept forever.

What the numbers say. The message rate (46,000 a second at peak) is not the hard part. Three numbers are: 10 million open connections, which need about 100 servers that do nothing but hold connections; 333,000 presence heartbeats a second, seven times the message rate, so presence must be cheap and lossy; and 657 TB a year of stored messages with three copies, which no single database holds. If clients instead asked "anything new?" every 5 seconds, that is 2 million mostly empty requests a second, 43 times the real message rate: the row turns red, and that is why chat uses persistent connections.

The connection: why WebSockets

HTTP is request and response: the client asks, the server answers. To push, the server needs a connection that stays open. A WebSocket is that connection: "The protocol consists of an opening handshake followed by basic message framing, layered over TCP" (RFC 6455), meaning it starts as an HTTP request that asks to "upgrade" and then both sides can send messages at any time for as long as it lasts. Alternatives: long polling (the server holds each request open until there is news, then the client asks again: works everywhere, costs a request per message) and server-sent events (one-way server push over HTTP, what LLM APIs use to stream tokens: Building a backend API, section 14). Chat needs both directions often, so WebSockets, with long polling as a fallback for hostile networks. Connection setup and TLS cost are in Topic: protocols.

API

// over the WebSocket, as small JSON frames client -> {"op":"send", "channel":"c_42", "client_msg_id":"7f3a...", "text":"hi"} server -> {"op":"ack", "client_msg_id":"7f3a...", "msg_id":"1124203949381050368"} server -> {"op":"message", "channel":"c_42", "msg_id":"1124...", "from":"u_9", "text":"hi"} server -> {"op":"presence", "user":"u_9", "status":"online"} // over plain HTTP GET /v1/channels/c_42/messages?before=1124203949381050368&limit=50 history, by cursor

The client_msg_id is an idempotency key: if the acknowledgement is lost and the phone resends, the server recognises the ID and does not store the message twice. The server-assigned msg_id is a Snowflake-style ID (time first), so sorting by it sorts by time, and it doubles as the pagination cursor (Building a backend API, section 8).

Data model

messages PRIMARY KEY ((channel_id, bucket), message_id) -- Discord's key, below author_id, content, edited_at, ... -- bucket = time window (Discord: about 10 days), so one channel's history is many bounded partitions channel_members(channel_id, user_id, last_read_message_id) -- read receipts and unread counts sessions (in memory, e.g. Redis): user_id -> set of gateway servers holding that user's connections presence (in memory, with TTL): user_id -> online, expires unless refreshed by a heartbeat

The design, built step by step

Deep dive: getting a message to the right connection

The sender is connected to gateway server 17; the recipients to servers 3, 58 and 90. Something must know who is where and fan the message out. Two shapes work:

  • A session registry plus direct routing: every gateway records "user u is on me" in a shared store; the message service looks up each recipient and forwards to their gateways. Simple for one-to-one chat; for a 5,000-member group it is 5,000 lookups per message.
  • Channel servers (publish and subscribe): each channel is owned by one server, chosen by consistent hashing (a way to map keys to servers so adding a server moves only a small share of keys: Distributed systems fundamentals, Partitioning). Gateways subscribe to the channels their users are in; a message goes to the channel's server, which forwards it once to each subscribed gateway, which forwards it to its local connections. Chosen: the fan-out is one message per gateway, not per user, and the channel's server is a natural place to assign order.

Ordering. "Same order for everyone" needs one place that decides the order per channel: the channel's server assigns increasing message IDs as messages arrive. Order across channels is not promised (nobody can see it). Clients sort by ID and use it to detect gaps after a reconnect: "give me everything after the last ID I have".

Offline and reconnect. The message is stored before it is acknowledged, so delivery to connections is best effort: a recipient who misses a push catches up from storage with the cursor. Recipients with no live connection get a mobile push notification through a separate, asynchronous path (a queue, as in Queues, streams and async work).

Presence, cheaply. Each connection sends a heartbeat; presence is a key with a TTL that the heartbeat refreshes, so a dead phone goes offline when the key expires instead of needing a "goodbye" message. To keep 333,000 updates a second from becoming millions of fan-out messages, presence changes go only to people who are looking (open conversations, visible contacts), are batched, and may be seconds stale. Discord's own numbers show why: "When a user comes online, they connect to a guild, and the guild publishes a presence to all other connected sessions", and in servers with "up to 30,000 concurrent users", "publishing an event from a large guild could take anywhere from 900ms to 2.1s" until they batched sends per node (Vishnevskiy, Discord, 2017-07-06).

Deep dive: storing every message forever

Reads are "the latest 50 messages in channel c, then the 50 before that", always within one channel. That access pattern points to a wide-column store (Cassandra, ScyllaDB: tables partitioned by a key across many machines, rows sorted within a partition) keyed by channel. Bucketing by time keeps a busy channel's partition from growing without limit. Writes are spread by channel; a very busy channel is a hot partition (one key getting a large share of traffic). Fixes: cache recent messages in the channel servers, and coalesce identical concurrent reads.

What real companies built

Discord, 2017: from one MongoDB collection "with a single compound index on channel_id and created_at" to Cassandra, because "our read/write ratio was about 50/50" and "Cassandra was the only database that fulfilled all of our requirements"; "channel_id became the partition key", message IDs are Snowflakes, and "if we stored about 10 days of messages within a bucket that we could comfortably stay under 100MB", giving the key "((channel_id, bucket), message_id)". They ran "a 12 node cluster with a replica factor of 3" at "well past 120 million" messages a day (Vishnevskiy, Discord, 2017-01-13).

Discord, 2023: "At the beginning of 2022, it had 177 nodes with trillions of messages"; hot partitions led to data services that coalesce reads ("If multiple users are requesting the same row at the same time, we'll only query the database once") and a move to "just 72 ScyllaDB nodes", with history p99 from "between 40-125ms" to 15 ms (Ingram, Discord, 2023-03-06; root Case files: Discord 2023).

Slack, 2023: "Every Slack client has a persistent websocket connection to Slack's servers"; Channel Servers "are stateful and in-memory", mapped to channels "based on consistent hashing"; a message goes from the web app to an Admin Server, which "discovers CS through a consistent hash ring", then to Gateway Servers and clients; "At peak times, about 16 million channels are served per host", messages arrive "across the world in 500ms", and "a new CS is ready to serve traffic in under 20 seconds" (Thangudu, Slack, 2023-04-11). Slack's January 2021 outage (root Case files: Slack 2021) shows the other side: when the network, not the servers, is the bottleneck, autoscaling on CPU misreads it.

WhatsApp, 2012: one tuned Erlang server held "over 2 million tcp connections", "with plenty of CPU and memory to spare" (WhatsApp blog, 2012-01-06). Our planning figure of 100,000 per server is deliberately 20 times lower: a conservative default you would raise after load testing.

Design 4News feed and timeline: fan-out on write against on read, and celebrities

A news feed (or home timeline) shows each user the recent posts of the accounts they follow, newest first. The classic case is Twitter around 2012, because its engineers published the numbers and because one design decision, when to do the merging work, dominates everything else.

Requirements
Functional
  • Post a short message; follow and unfollow.
  • Home timeline: newest posts from followed accounts, paginated.
  • Out of scope at first: ranking, search, replies.
Non-functional
  • Twitter's published scale (2012): "150M world wide active users, handles 300K QPS to generate timelines"; "5K/sec daily average; 7K/sec daily peak; >12K/sec during large events" for posts; "30b deliveries / day" (High Scalability, 2013-07-08, notes on Raffi Krikorian's QCon 2012 talk Timelines at Scale; these are the blogger's notes, not a transcript).
  • Timeline reads fast (hundreds of ms end to end); a new post visible to followers within seconds.

What the numbers say. Reads outnumber posts 60 to 1. If each read assembles the timeline from scratch (fan-out on read: look up everyone you follow, fetch their recent posts, merge), that is about 22 million index lookups a second. If instead each post is copied into every follower's timeline when it is written (fan-out on write), a read is one lookup, and the work moves to 375,000 deliveries a second, about 1.1 million inserts counting three copies. Twitter chose write. The bill: 2.9 TB of RAM to hold 800 entries for every user, and one post by an account with 31 million followers is 93 million inserts.

API

POST /v1/posts {"text": "..."} -> 201 {"id": "..."} POST /v1/follows {"followee": "u_7"} GET /v1/timeline?cursor=...&limit=50 -> {"items": [...], "next_cursor": "..."}

Data model

posts(id BIGINT PRIMARY KEY, author_id, created_at, text) -- id is time-ordered (Snowflake) follows(follower_id, followee_id) + an index on followee_id -- "who must receive this post?" timeline:{user_id} -> list of up to 800 post ids, newest first -- in Redis, 3 copies

The design, built step by step

Deep dive: the two strategies, measured

Measured for this page: PostgreSQL 16.2 on a laptop, 10,000 users following 100 accounts each, 100,000 posts

Followed accounts are chosen with a Zipf-like skew (illustrative: a few accounts are followed by almost everyone, like real social graphs, but this graph is synthetic). On read joins follows to posts (indexed by author and id) for the newest 50; precomputed reads 50 rows from a timelines table capped at 800 entries per user. Fan-out cost is the time to insert one new post into every follower's timeline. 500 users, median and p99. src/lab/measure_pg.py, 2026-10-04. Absolute numbers are a laptop's; the ratios are the lesson.

Reading the precomputed timeline was times faster, and that gap widens with the number of accounts followed, because on-read work grows with it while a precomputed read stays one index range. The price shows in the other two rows: the timelines table holds every post once per follower (8 million rows, 766 MB for this toy), and writing one post by the most-followed account took times longer than one by a median account. Scale that to 31 million followers and it is minutes.

Deep dive: celebrities, and the hybrid

Fan-out on write is wrong for a handful of accounts. The talk notes: "it can take up to 5 minutes for a tweet to flow from Lady Gaga's fingers to her 31 million followers", and the plan was "Not fanning out the high value users anymore. For people like Taylor Swift don't bother with fanout anymore, instead merge in her timeline at read time. Balances read and write paths" (High Scalability, 2013). This hybrid is the expected interview answer:

  • Accounts under a follower threshold: fan out on write.
  • Accounts over it: store their posts once; at read time, merge the user's precomputed timeline with the recent posts of the few celebrities they follow (a handful of extra lookups, not hundreds).
  • Inactive users: do not maintain their timeline at all; rebuild it on login from the follow graph. This cuts the 2.9 TB of RAM to the active users' share.

Other considerations to say out loud: deleting a post must remove it from millions of timelines (store ids, not copies of the text, and filter deleted ids at read time); unfollowing leaves old entries (filter at read time or accept it); the fan-out runs on a queue of delivery jobs, so a burst of posts delays delivery rather than failing posts (backpressure: Queues, streams and async work, Backpressure and Little's law).

Deep dive: ranking changes the question

A chronological timeline is a merge; a ranked one ("For You") is a search problem. Twitter's 2023 description: the system must "distill the roughly 500 million Tweets posted daily down to a handful", first by candidate sourcing ("we attempt to extract the best 1500 Tweets from a pool of hundreds of millions"), then a "~48M parameter neural network" ranks them; the timeline is "50% In-Network Tweets and 50% Out-of-Network Tweets on average"; the pipeline "runs approximately 5 billion times per day and completes in under 1.5 seconds on average", and "A single pipeline execution requires 220 seconds of CPU time". Most strikingly: "We recently stopped using Fanout Service, a 12-year old service that was previously used to provide In-Network Tweets from a cache of Tweets for each user" (Twitter engineering, 2023-03-31, Wayback copy). Once most of a feed comes from accounts you do not follow, precomputing per-follower lists stops paying, and the work moves back to read time, with heavy caching and machine learning. Facebook had made the read-time choice from the start: an aggregator "fanned out the request to all the leaves to fetch data, rank and filter data", where leaves keep recent actions in memory (Zhu, Facebook Multifeed, 2015-03-10).

The lesson that generalises

"On write or on read" is a question about where to spend work: when something is produced, or when it is consumed. Spend it at write time when reads vastly outnumber writes and the result is reused; spend it at read time when writes fan out enormously, or when the result is personal and changes per read. Caches (design 1), materialised views and search indexes are the same decision under other names.

Design 5An LLM gateway for a company: routing, quotas, fallbacks, cost

Every team in the company now calls large language models (LLMs): a support bot, a code assistant, a document summariser, pipelines that classify tickets. Each team has its own API keys, its own retry code and its own surprise bill. An LLM gateway is one internal service that every model call goes through. The mechanisms (authentication, routing, token-based limits, caching, fallbacks, the degradation ladder) are taught in depth in ML system design, sections 3 to 11, with a lab where you can turn each one on (its Gateway lab tab); this section runs the interview: what to ask, what the numbers say, what to build first.

Requirements
Functional

  • Routing to vendors and self-hosted models; automatic fallback when one fails.
  • Remove personal data before it leaves the company; audit log of every call.
Non-functional
  • 10,000 employees, 40% using AI daily, 30 requests each, plus 400,000 automated requests a day (illustrative).
  • Adds under 50 ms before the first token; streams pass through unbuffered.
  • Available more than the providers behind it (fallbacks).
  • Spend is correct to the cent per team per month.

What the numbers say. This is the design where the estimate tells you throughput is not the problem: 18 requests a second at peak fits on one small server (the row says one, for throughput alone; run at least two). Uber's gateway, a real one, reported "16 million queries per month, with a peak QPS of 25" for "close to 30 customer teams" (Wang and Bansal, Uber, 2024-07-11), the same order as ours (an independent comparison, not a reproduction). What is big is money: about $4,200 a day, $1.5 million a year at the illustrative Sonnet 5.5 price of $2 and $10 per million input and output tokens (from ML system design, section 1), where a 10% routing mistake is a salary. The design, built step by step

Deep dive: what to build first, in order

  1. Virtual keys and usage events. The gateway holds the real provider keys; teams get gateway keys. Every call emits a usage event to a queue and on to a warehouse. This alone answers "who spends what", and it is the precondition for everything else. Uber's gateway generates "audit logs for comprehensive cost attribution", and its "centralized nature ... streamlines the management of usage and budgeting across various teams".
  2. Budgets and limits in tokens. A request's cost is unknown until it finishes, so reserve the worst case (input tokens plus max_tokens) before the call and refund the difference after, with atomic counters as in design 2; the reasoning is in ML system design, section 5. Off-the-shelf gateways expose exactly these knobs: LiteLLM's proxy takes per-team tpm_limit, rpm_limit, max_parallel_requests and a max_budget with a budget_duration (LiteLLM docs).
  3. Fallbacks with one retry layer. An ordered route per alias (vendor A, then vendor B, then a self-hosted model), a timeout per hop and a cooldown for a failing route. Retry in the gateway only; tell team SDKs not to retry on top, or the retries multiply (the 243× case in Reliability engineering, Retries). LiteLLM names the same settings fallbacks, num_retries, allowed_fails, cooldown_time, request_timeout (LiteLLM reliability docs); what a fallback really costs in time is measured in ML system design, section 3.
  4. Data protection. Redact personal data before external calls according to each team's policy, and route data that may not leave to self-hosted models. Uber: a "PII redactor that anonymizes sensitive information within requests before forwarding them to third-party vendors", restoring the entities in the response. Wealthsimple's gateway did the same, "enhanced by a PII removal model we developed in-house" (Wealthsimple engineering, date unconfirmed (2023 or 2024)). Policy enforcement beyond redaction belongs to Guardrails.
  5. Cost cuts. Only after measuring: prompt (prefix) caching, tier routing of easy requests to a cheaper model, batch APIs for pipelines that can wait (ML system design, sections 4, 7 and 9).

Trade-offs considered and rejected

  • A shared client library instead of a service. No extra hop, but every language needs a copy, keys still live in every service, and budgets cannot be enforced across processes. Rejected: the extra few milliseconds are nothing against seconds of generation.
  • Logging full prompts and responses forever. Useful for evaluation, dangerous for privacy. Chosen instead: metadata always; content sampled, redacted, with a retention limit and access controls.
  • Exact-match response cache for everything. Cheap, but personal answers can leak between users. Only per team and per opted-in feature; semantic caching only with a measured false-hit rate (ML system design, section 9).
  • Building it. LiteLLM, Envoy AI Gateway, Kong and Portkey exist. Buy or adopt first unless data rules force you; build when your policy needs outgrow theirs.

Design 6A RAG service over company documents: ingestion, embeddings, vector index, freshness, evaluation

Retrieval-augmented generation (RAG) answers a question by first finding the relevant passages in your own documents and then asking an LLM to answer from them, citing them (the original paper: RAG, Lewis et al. 2020). The design question is the system around that idea: getting millions of documents in, keeping them fresh, never showing someone a document they may not open, and knowing whether the answers are right.

Requirements
Functional
  • Ask a question in a chat box; get an answer with links to the source passages.
  • Sources: wiki, shared drives, tickets (5 million documents, illustrative).
  • Answers use only documents the asker is allowed to read.
Non-functional
  • An edited document is searchable within 10 minutes.
  • First token in under 3 seconds at p95.
  • 50,000 questions a day.
  • Measured answer quality, tracked over time.

What the numbers say. Queries are trivial (under 2 a second at peak). The corpus is not: 35 million chunks of about 500 tokens, whose 1,536-dimension vectors take 215 GB as 4-byte floats, more RAM than a typical database server, before the index's own graph. Options the numbers suggest: half-precision storage (pgvector's halfvec, 2 bytes a dimension, halves it), fewer dimensions, or a sharded vector store. Embedding the whole corpus once costs about $350 at $0.02 per million tokens (OpenAI, text-embedding-3-small, read 2026-10-04), so re-embedding is cheap in money; in time, keeping up with 2% of documents changing a day is only 8 chunks a second. Answers cost about $650 a day, mostly the input tokens of the retrieved chunks: the number of chunks per prompt is the cost dial.

API

POST /v1/ask {"question": "How do I rotate the staging database password?", "conversation_id": "..."} -> SSE stream of the answer, then {"citations": [{"doc_id": "...", "chunk": 3, "url": "...", "title": "..."}]} POST /v1/feedback {"answer_id": "...", "rating": "down", "reason": "outdated"} // ingestion is driven by the sources' change events, not by an API users call

Data model

documents(doc_id, source, url, title, version, updated_at, acl_groups TEXT[]) chunks(doc_id, chunk_no, version, text, embedding VECTOR(1536), acl_groups TEXT[], PRIMARY KEY (doc_id, chunk_no)) -- HNSW index on embedding; GIN index on acl_groups; full-text index on text for keyword search eval_set(question, expected_doc_ids, reference_answer) -- the golden set

The design, built step by step

Deep dive: the ingestion pipeline

Ingestion is an asynchronous pipeline: a connector per source receives change events (or polls for changes), puts "document d changed" on a queue, and workers fetch the document, extract text, split it into chunks (passages small enough to retrieve precisely; overlapping a little so a sentence cut at a boundary survives), compute an embedding for each (a vector of numbers from a model, placed so that passages with similar meaning have nearby vectors) and upsert them. Three rules make it reliable. Key every chunk by (doc_id, chunk_no) and write it with the document's version, so a redelivered or reordered event is harmless (an older version never overwrites a newer one): the idempotent-consumer pattern of Queues, streams and async work, Idempotent consumers. Delete chunks beyond the new chunk count when a document shrinks. And keep the embedding model's name with every vector: changing the model means re-embedding everything, because vectors from different models are not comparable (ML system design, section 13).

Deep dive: retrieval that actually finds the passage

A vector index finds the chunks nearest to the question's embedding without comparing against all 35 million. The common choice is HNSW (hierarchical navigable small world), a layered graph searched from coarse to fine, which "allows a logarithmic complexity scaling" (Malkov and Yashunin, 2016). In PostgreSQL, pgvector offers HNSW, which "has better query performance than IVFFlat (in terms of speed-recall tradeoff), but has slower build times and uses more memory", and IVFFlat, which "has faster build times and uses less memory than HNSW, but has lower query performance"; indexable vectors go up to 2,000 dimensions, and halfvec up to 4,000 (pgvector README). Start with pgvector if you already run PostgreSQL and the index fits in memory; move to a dedicated vector store when it does not. Database choices in general: Topic: databases.

Vectors alone miss exact terms (error codes, product names, people). The fix is hybrid retrieval: run keyword search (BM25, the classic ranking by term frequency) alongside vector search, merge, then rerank the top candidates with a slower, more accurate model. Anthropic measured the effect on its own benchmark: adding a short generated context to each chunk ("usually 50-100 tokens") and combining contextual embeddings with contextual BM25 "reduced the top-20-chunk retrieval failure rate by 49% (5.7% → 2.9%)", and "when combined with reranking, by 67%"; the one-time cost of generating the context was "$1.02 per million document tokens" with prompt caching (Anthropic, Introducing Contextual Retrieval, 2024-09-19).

Deep dive: permissions and freshness

Permissions. Copy each document's access groups onto its chunks and filter at query time by the asker's groups. Beware a trap in approximate indexes: pgvector warns "With approximate indexes, filtering is applied after the index is scanned", so a filter matching few rows can return fewer results than asked unless iterative index scans are enabled (pgvector README). Permission changes must flow through the same pipeline as edits, and fast: a revoked permission that takes a day to apply is a data leak for a day. Never rely on the LLM to "not mention" documents it was given.

Freshness. Event-driven connectors plus a short queue meet "searchable in 10 minutes"; a nightly full re-sync catches missed events. Show each citation's last-updated date so users can judge staleness.

Deep dive: knowing whether it works

A RAG system fails in two separate places: retrieval did not find the passage, or generation did not use it faithfully. Measure both, on a golden set of real questions with the documents that answer them, before every change of chunking, model or prompt, and on sampled production traffic. The metrics (recall at k, faithfulness, groundedness), how to build the test set from your own corpus and how LLM judges fail are on RAG and retrieval evaluation; gates and shadow tests on Production eval engineering.

What real companies built

LinkedIn (2024): customer-service question answering over a knowledge graph built from past tickets, which "outperforms the baseline by 77.6% in MRR" and, deployed, "reduced the median per-issue resolution time by 28.6%" (Xu et al., arXiv 2404.17723).

DoorDash (2024): a support assistant that "first condenses the entire conversation to pinpoint the core problem" and then searches past resolved cases and articles; an LLM guardrail "reduced overall hallucinations by 90% and cut down potentially severe compliance issues by 99%" (DoorDash engineering, repost dated 2024-09-17).

Uber (2025-05-29): moving from plain RAG to an agentic version with "an additional BM25-based retriever alongside traditional vector search" raised acceptable answers "by a relative 27%" and cut incorrect advice "by a relative 60%" (Uber, Enhanced Agentic-RAG). All three are vendor-reported results on their own data.

Design 7A distributed job scheduler: cron for a whole company

The brief offered a notification system or a job scheduler; the scheduler has the better public sources (Google's distributed cron, Dropbox's task framework, Slack's job queue, all with numbers), so it is the worked design here. A notification system reuses most of designs 3 and 7, and is a prompt in the Design drill, with Netflix's published design as its reference.

A job scheduler runs work at a given time: "every day at 02:00, rebuild the search index"; "in 30 minutes, send this reminder"; "every 5 minutes, poll this partner". Cron is the classic Unix program that does this on one machine, from a table of schedules written like 0 2 * * * (minute, hour, day, month, weekday). The company-wide version must survive machines dying without running jobs twice or skipping them silently.

Requirements
Functional
  • Register recurring (cron syntax) and one-off delayed jobs; cancel; pause.
  • Run each due job on a worker; record each run (start, end, result, logs link).
  • Retries with backoff for failed runs; alert the owner after N failures.
Non-functional
  • 10 million runs a day, 30% of them scheduled at the top of an hour (illustrative).
  • Start within a few seconds of the due time (Dropbox's target: 95% within 5 s, below).
  • No double runs of non-idempotent jobs; no silent skips.
  • Survives the loss of any machine.

What the numbers say. The average is small: 116 runs a second, about 2,300 running at once, 48 worker machines. The danger is the clock: people write 0 * * * *, so 30% of the day's runs, 125,000 of them, become due in the same second, which would need 2,500 machines for one second and 48 the rest of the time. Spreading each hourly batch over a minute with jitter (a random delay per job) brings the burst to about 2,100 a second. Run history (5 GB a day) is easy.

API

POST /v1/jobs {"name": "rebuild-index", "schedule": "0 2 * * *", "timezone": "Europe/London", "target": {"queue": "search", "payload": {...}}, "max_runtime_s": 3600, "overlap": "skip" | "queue" | "allow", "misfire": "run_once" | "skip"} POST /v1/jobs/{id}/pause DELETE /v1/jobs/{id} GET /v1/jobs/{id}/runs?cursor=...

overlap says what happens if the previous run is still going; misfire says what happens to runs missed while the scheduler was down: two decisions every scheduler forces, which the queues sibling discusses under Queues, streams and async work, Scheduling and cron.

Data model

The design, built step by step

Deep dive: deciding what is due, exactly once

Two machines both reading "what is due?" will both run the same job. Two standard fixes:

  • One leader. The scheduler replicas elect a leader (with a consensus system such as etcd or ZooKeeper, or Paxos/Raft directly) and only the leader launches. Clean, but failover takes seconds, and a deposed leader that does not yet know it is deposed can still launch, hence leases and fencing tokens (Distributed systems fundamentals, Leader election, leases and fencing tokens).
  • Row claiming in the database. Every scheduler instance runs SELECT ... FROM jobs WHERE next_run_at <= now() ORDER BY next_run_at LIMIT 100 FOR UPDATE SKIP LOCKED; SKIP LOCKED makes each instance skip rows another has locked, so they divide the work without a leader. In the same transaction each inserts the run row and advances next_run_at. Chosen at this scale: no extra system, and the database's transaction is the coordination.

Either way, the runs primary key (job_id, scheduled_for) makes "the 02:00 run of job 7" one row that can exist only once: a second scheduler that tries to create it gets a conflict instead of a second run. That is idempotency on the launch side.

Deep dive: the scheduler only enqueues

The scheduler must never run jobs itself: a slow job would delay every other launch. It writes the run to a queue; workers pull from the queue, take a lease on the run (a claim that expires unless renewed by heartbeats) and execute. If a worker dies, its lease expires and another worker retries the run. That gives at-least-once execution: a run that finished its work but died before recording success will run again. So jobs with side effects must be idempotent (use job_id plus scheduled_for as the idempotency key for anything they write or send), or they must check whether their effect already happened. Delivery semantics, visibility timeouts and dead-letter queues are taught in Queues, streams and async work.

Skip or double-run? Say which you prefer, and why

Google's distributed cron, which keeps its state consistent with Paxos across replicas, chose: "In general, we favor skipping launches rather than risking double launches, as much as the infrastructure allows", because "it is more acceptable to not launch Cron jobs for a while than to mistakenly launch the same Cron job ten times instead of once", and "all operations on external systems, which we may need to continue upon re-election, either have to be idempotent ... or we need to be able to look up their state" (Google SRE book, Distributed Periodic Scheduling with Cron; Davidovič and Guliani, ACM Queue, 2015). A billing job prefers a skip plus an alert; a cache-warming job prefers a double run. Make it a per-job setting.

Deep dive: time is harder than it looks

  • Time zones and daylight saving: "02:30 every day" does not exist on the spring-forward day in London and happens twice on the autumn one. Store the job's time zone, compute next_run_at in UTC with a real time-zone library, and decide the rule for missing and repeated local times.
  • Thundering herd: add deterministic jitter (hash of the job id modulo the spread) to jobs that do not need an exact minute, so the same job runs at the same offset every hour.
  • Clock skew: scheduler machines disagree by milliseconds; use the database's now() as the one clock for "due".
What real companies built

Dropbox ATF (2020-11-11): "currently serving 9,000 async tasks scheduled per second and in use by 28 engineering teams". It guarantees "that a task is executed at least once after being scheduled" and "that at most one instance of a task will be actively executing at any given in point"; "95% of tasks begin execution within five seconds from their scheduled execution time". Its parts match this design: a Store Consumer "periodically polls the task store to find tasks that are ready for execution and pushes them onto the right queues" (Amazon SQS), and executors send heartbeats while they run (Krishnan, Dropbox).

Slack's job queue: "On our busiest days, the system processes over 1.4 billion jobs at a peak rate of 33,000 per second". When a database slowdown filled Redis to its memory limit, Slack "decided to add Kafka in front of Redis rather than replacing Redis with Kafka outright": a durable log absorbs the burst, and a relay feeds Redis at the rate it can take (Slack engineering, page dated 2017-12-06, updated 2020-06-25).

Netflix Maestro (2024-07-22): a workflow orchestrator that "runs half a million jobs daily on average, and has completed around 2 million jobs on particularly busy days" (Netflix tech blog): when jobs depend on each other, a scheduler grows into a workflow engine (durable workflows are in the queues sibling).

What interviewers listen for
  • You separated "decide what is due" from "do the work" with a queue between.

How to practise

Reading worked designs builds recognition; only producing designs under a clock builds the skill. A routine that works:

  1. Timed drills, out loud. Pick a prompt in the Design drill tab, start the 45-minute clock, and talk through each step before revealing it. Write the estimate on paper. Then compare with the reveal and tick the self-check list honestly. One drill a day for two weeks beats ten designs read in an evening.
  2. Redo the seven designs from a blank page a week after reading them. If you cannot reproduce an estimate, you understood the answer, not the method.
  3. Change one requirement and redesign. The shortener with editable destinations; chat with end-to-end encryption; the feed ranked instead of chronological; the scheduler with jobs that depend on each other. This is what interviewers do in the last ten minutes.
  4. Read one real write-up a week from the root's Case files or the sources cited here, and write its design in this page's template: requirements, numbers, boxes, what broke.
  5. Practise with a person once you can finish in time: a mock interviewer interrupts, which is the part solo drills cannot train.

The common traps

Drawing boxes before asking a single question
The first five minutes decide the design. "How many users? Read-heavy or write-heavy? What may be stale, lost or duplicated?" Each answer removes a branch of possible designs.
Estimates that change nothing
Arithmetic is worth time only when its result moves a decision: the code length, whether to shard, whether to push or poll. State the decision the number made.
Scaling what does not need it
Sharding a database that takes 230 writes a second, or Kafka for 18 requests a second, signals that you add components by habit. Say "one Postgres is enough until X, and here is how I would split it then".
Naming products instead of mechanisms
"Use Kafka" is not a design. "A durable, partitioned log so the fan-out can lag behind posts without losing them, keyed by author so order per author holds" is. Products are fine once the mechanism is said.
Ignoring failure
For every box, say what happens when it is slow or gone. Most interview designs fail on "what if the cache dies?" or "what if the worker crashes after charging the card?". The answers are in Reliability engineering.
Promising exactly-once, global order or strong consistency everywhere
Each costs latency or availability. Say which data needs which guarantee: per-channel order, at-least-once plus idempotency, stale presence. CAP is about what happens during a network partition, not "pick two" (Distributed systems fundamentals, CAP stated correctly).
Going deep too early, or never
Get a complete, simple design on the board first (about 15 minutes in), then deepen the two parts the numbers flagged. A beautiful ID generator with no storage design is an incomplete answer.
Silent thinking and no trade-offs
The interviewer grades reasoning they can hear. "I considered X, chose Y because Z, and I would revisit if W" is the sentence to practise.
Forgetting observability and rollout
How would you know it works in production, and how would you ship a change safely? One sentence each (Observability; canaries in Reliability engineering, Deployment safety).

Glossary

At-least-once: a delivery or execution guarantee where nothing is lost but something may happen twice; paired with idempotency.
Base62: writing numbers with 62 symbols (0 to 9, a to z, A to Z); 7 characters give 3.52 trillion codes.
BM25: a classic keyword ranking function based on how often query terms appear in a passage.
Cache-aside: read the cache; on a miss read the database and fill the cache.
Channel server: in chat, the server that owns a conversation, orders its messages and forwards them to subscribed gateways.
Chunk: a passage of a document (a few hundred tokens) embedded and retrieved as one unit.
Consistent hashing: mapping keys to servers so adding or removing a server moves only a small share of keys.
Cron: the Unix scheduler, and its five-field schedule syntax (minute, hour, day, month, weekday).
Design document: the written proposal for a system, reviewed before building; the work-world form of the interview.
Embedding: a vector of numbers representing a text, close to the vectors of similar texts.
Fail open: when a check cannot run, allow the request (a rate limiter); fail closed means deny (a permission check).
Fan-out on write / on read: copy a post to every follower's timeline when posted, or assemble each timeline when read.
Functional / non-functional requirements: what the system does / how much, how fast, how reliably, how cheaply.
Golden set: a fixed set of questions with known good answers or sources, used to evaluate changes.
HNSW: a layered graph index for approximate nearest-neighbour search over vectors.
Hot partition (hot key): one key receiving a disproportionate share of traffic.
Hybrid retrieval: keyword and vector search combined, often followed by reranking.
Idempotency key: a client-chosen id that makes a retried request return the first result instead of acting twice.
Jitter: a random delay added so that many clients or jobs do not act at the same instant.
Lease: a claim that expires unless renewed; lets a crashed holder's work be taken over.
Little's law: items in a system = arrival rate × time each stays.
LLM gateway: one internal service every model call passes through, for keys, limits, routing, redaction and cost.
Lua script (Redis): code that Redis runs atomically, so a read-compute-write cannot interleave with other clients.
Presence: whether a user is online, kept as a key with a TTL refreshed by heartbeats.
Race condition: a bug where the result depends on the timing of concurrent operations (check, then act).
RAG: retrieval-augmented generation; answer from retrieved passages, citing them.
Rate limiter: caps one client's request rate; excess gets 429.
Redirect (301, 302): an HTTP answer telling the browser to go elsewhere; 301 is cacheable by default, 302 is not.
Rerank: re-order retrieval candidates with a slower, more accurate model.
Snowflake ID: a 64-bit id of timestamp, machine number and sequence, unique without coordination and sortable by time.
TTL: time to live; how long a cached or stored entry lasts before it expires.
Vector index: a structure that finds the nearest vectors without comparing against all of them.
WebSocket: a long-lived, two-way connection over TCP that starts as an HTTP upgrade.
