Design 1URL shortener: IDs, base62, caching, read-heavy scaling

The warm-up question, asked because it is small enough to finish and still touches IDs, caching, HTTP and storage. A URL shortener turns a long address into a short one (sho.rt/aZ3kQ9x); visiting the short one redirects the browser, meaning the server answers "go here instead" with the long address, and the browser follows it.

Requirements (agreed with the interviewer)
Functional
  • Create a short link for a long URL; optionally a custom alias.
  • Visiting the short link redirects to the long URL.
  • Count clicks per link (owners see analytics).
  • Out of scope: accounts, editing, link previews.
Non-functional
  • Sized like Bitly in 2014: 600 million new links and 6 billion clicks a month ({{High Scalability, 2014|http://web.archive.org/web/2015/http://highscalability.com/blog/2014/7/14/bitly-lessons-learned-building-a-distributed-system-that-han.html}}, a summary of a Bitly engineer's talk).
  • Redirect fast: under 50 ms at the server, p99.
  • Links never break, kept 5 years; never give two users the same code.
  • Click counts may lag by minutes; a few lost clicks are acceptable.

What the numbers say. Writes are 230 a second: one database handles that with ease. Redirects are 10 times more, and under 5,000 a second at peak: still within one database (about 17,500 a second at our half-benchmark planning figure), so the cache is about latency and headroom, not survival. Two numbers do change the design: 36 billion links after five years fill 63% of the 6-character code space, so random 6-character codes would collide on most attempts and 7 characters are needed; and 18 TB of rows is more than one comfortable database server, so the storage must be split later. The app tier needs about a dozen servers, which matches the order of magnitude Bitly reported: "~30 servers handle all incoming traffic from the outside world including shortens, redirects, api requests, web ui, etc." (same source).

API

POST /v1/links create; Idempotency-Key header makes retries safe {"url": "https://example.com/a/very/long/path", "alias": null} -> 201 {"code": "aZ3kQ9x", "short_url": "https://sho.rt/aZ3kQ9x"} -> 409 if the alias is taken; 422 if the URL is not http(s) GET /{code} the redirect: the hot path -> 302 Found, Location: https://example.com/a/very/long/path -> 404 if unknown, 410 Gone if taken down for abuse GET /v1/links/{code}/stats?from=.. owner analytics, read from the analytics store

Status codes, the Idempotency-Key header (a client-chosen ID that lets the server recognise a retried request and return the first answer instead of creating a second link) and error bodies are taught in {{Building a backend API, sections 7 and 10|n:3c65c17b0d0d8190ade6c34e8f653e79}}.

Data model

links(code TEXT PRIMARY KEY, 7 base62 characters long_url TEXT NOT NULL, owner_id BIGINT, created_at TIMESTAMPTZ, status SMALLINT) -- the redirect is one primary-key lookup: no other index is on the hot path click_events -> a queue, then an analytics store (counts per link per hour)

Deep dive: where do short codes come from?

Base62 writes a number with 62 symbols (0 to 9, a to z, A to Z), so each character carries one of 62 values: 6 characters give 626 = 56.8 billion codes, 7 give 3.52 trillion. Three ways to fill them, each with a cost:

  • Hash the long URL (for example the first 7 base62 characters of its SHA-256). The same URL always gets the same code, which deduplicates for free. But different URLs can produce the same 7 characters, so every create must check and handle a collision, and two users shortening the same URL share one code and one click count, which breaks per-owner analytics. Rejected as the main scheme.
  • Random codes, checked for uniqueness on insert (a unique index makes the database refuse a duplicate, and the server retries). Simple and unguessable; the chance a new code collides is the share of the space already used: about 1% at 7 characters after five years, 63% at 6. Acceptable at 7 characters.
  • A counter turned into base62. No collisions ever, and IDs are short. Its two costs: a single counter is a coordination point every create must reach, and sequential codes let anyone walk through every link (aZ3kQ9x, aZ3kQ9y, ...), which leaks private links. Chosen, with both costs removed: each app server leases a block of, say, 10,000 numbers at a time from an ID range service (one row incremented in a database), so a create needs no network call, and the number is passed through a fixed reversible scramble (a permutation of the 7-character space) before encoding, so neighbouring numbers give unrelated codes.
What real companies built

Flickr, 2010: "Ticket servers give us globally (Flickr-wide) unique integers to serve as primary keys in our distributed setup": a MySQL table where REPLACE INTO plus LAST_INSERT_ID() hands out the next number, run on two servers, one giving odd and one even numbers, so either can fail ({{Kremerskothen, Flickr, 2010-02-08|https://code.flickr.net/2010/02/08/ticket-servers-distributed-unique-primary-keys-on-the-cheap/}}).

Twitter Snowflake, 2010: a 64-bit ID made of "time - 41 bits (millisecond precision w/ a custom epoch gives us 69 years)", a "configured machine id - 10 bits - gives us up to 1024 machines" and a "sequence number - 12 bits - rolls over every 4096 per machine", so machines "should not have to coordinate with each other" and IDs sort roughly by time ({{snowflake README, 2010|https://github.com/twitter-archive/snowflake/blob/snowflake-2010/README.mkd}}; {{announcement, 2010-06-01|http://web.archive.org/web/2011/http://engineering.twitter.com/2010/06/announcing-snowflake.html}}). Snowflake IDs are too long for a shortener (a 64-bit number needs 11 base62 characters) but are the standard answer for "unique IDs across many machines", and Discord uses them for every message (design 3). Instagram built the same idea inside PostgreSQL (root {{Case files: Instagram 2012|n:3c65c17b0d0d81048ae0dd14ac399b4d}}).

Deep dive: 301 or 302?

Both status codes redirect. The difference is caching. RFC 9110 says "A 301 response is heuristically cacheable", meaning a browser or proxy may reuse it without asking again, while 302 "Found" says the target "resides temporarily under a different URI" and is not on the list of heuristically cacheable codes ({{RFC 9110 §15.4.2, §15.4.3, §15.1|https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.2}}). A cached 301 is free for you, but the browser stops coming back, so you lose its later clicks and cannot change or take down the destination for that browser. Choose 302 (or 301 with an explicit short cache lifetime) when analytics or takedowns matter. Bitly answers 301 with cache-control: private, max-age=90 (checked with curl -I on 2026-10-04, src/inputs/bitly_headers.txt): shared caches may not store it and a browser may reuse it for only 90 seconds, so nearly every click still reaches Bitly. Bitly's reason is not published; this is an observation, not their statement.

Deep dive: the cache, and counting clicks without slowing redirects

The redirect path is: look up the code in Redis (an in-memory key-value store, about 0.14 ms a lookup); on a miss, read the database and put the answer in Redis with a TTL (time to live, after which the entry expires). That pattern is cache-aside, taught with its traps (stampedes when a hot key expires, stale entries after a takedown: delete the key on takedown) in {{Capacity planning and performance, Caching strategy|n:3ef5c17b0d0d81458291d55d7443700c}}. Links are written once and almost never change, the easiest possible thing to cache. Click counting must not sit on the redirect path: an UPDATE links SET clicks = clicks + 1 on every visit turns each redirect into a write, and a viral link becomes one row that thousands of requests lock in turn. Instead the server emits a click event to a queue and answers immediately; consumers aggregate counts per link per hour. Bitly did exactly this: "Data about the conversion is popped onto a queue for the analytics and other downstream systems" (High Scalability, 2014). Delivery is at-least-once (an event may arrive twice after a crash), which a few duplicate clicks tolerate; how queues behave is in {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}.

Deep dive: 18 TB, and when to split the database

The access pattern is a pure key lookup by code, with no joins: the easiest data to partition (split rows across several databases by a key). Hash the code to pick a shard; each shard has a replica for failover. Do not do this on day one: the first year is 3.6 TB and 230 writes a second, which one PostgreSQL primary with a replica handles. Plan the split (use a shard key now, so moving later is mechanical) and execute it when storage or write rate demands it. A partitioned key-value store (DynamoDB, Cassandra) fits this pattern natively and is an equally good answer; pick what the team can operate. How partitioning and consistent hashing work: {{Distributed systems fundamentals, Partitioning|n:3c65c17b0d0d8115bc45c31d915b4d33}}.

What interviewers listen for
  • You asked about the read-to-write ratio and computed the code space instead of picking "6 characters" by habit.
  • You named at least two ID schemes and why you rejected one (collisions, enumeration, coordination).
  • You said 301 versus 302 out loud and tied it to analytics.
  • Click counting is off the hot path, and you said what at-least-once means for counts.
  • You did not shard on day one, and you said when you would.
