Design 1URL shortener: IDs, base62, caching, read-heavy scaling

The warm-up: small enough to finish, and it still touches IDs, caching, HTTP and storage. A URL shortener turns a long address into a short one (sho.rt/aZ3kQ9x); visiting the short one redirects: the server answers "go here instead" and the browser follows.

Requirements (agreed with the interviewer)
Functional
  • Create a short link (optionally a custom alias); visiting it redirects.
  • Click counts per link for owners.
  • Out of scope: accounts, editing, link previews.
Non-functional
  • Sized like Bitly in 2014: 600 million new links and 6 billion clicks a month ({{High Scalability, 2014|http://web.archive.org/web/2015/http://highscalability.com/blog/2014/7/14/bitly-lessons-learned-building-a-distributed-system-that-han.html}}, a summary of a Bitly engineer's talk).
  • Redirect under 50 ms at the server, p99. Links never break, kept 5 years; never give two users the same code.
  • Click counts may lag by minutes; a few lost clicks are acceptable.

What the numbers say. Writes are 230 a second and redirects under 5,000 a second at peak: both within one database (about 17,500 a second at our half-benchmark planning figure), so the cache is about latency and headroom, not survival. Two numbers do change the design: 36 billion links after five years fill 63% of the 6-character code space, so random 6-character codes would collide on most attempts and 7 characters are needed; and 18 TB of rows is more than one comfortable database server, so storage must be split later. The app tier needs about a dozen servers, the order Bitly reported: "~30 servers handle all incoming traffic from the outside world including shortens, redirects, api requests, web ui, etc." (same source).

The decision that matters: where short codes come from

Base62 writes a number with 62 symbols (0 to 9, a to z, A to Z): 6 characters give 626 = 56.8 billion codes, 7 give 3.52 trillion. Three schemes:

  • Hash the long URL (the first 7 base62 characters of its SHA-256). Deduplicates for free, but different URLs can collide, so every create must check, and two users shortening one URL share one code and one click count. Rejected as the main scheme.
  • Random codes, made unique by a unique index (the database refuses a duplicate and the server retries). The chance a new code collides is the share already used: about 1% at 7 characters after five years, 63% at 6. Acceptable at 7 characters.
  • A counter turned into base62. Never collides, but a single counter is a coordination point and sequential codes let anyone walk every link (aZ3kQ9x, aZ3kQ9y, ...). Chosen, with both costs removed: each app server leases a block of 10,000 numbers from an ID range service (one row incremented in a database), so a create needs no network call, and a fixed reversible scramble (a permutation of the 7-character space) makes neighbouring numbers give unrelated codes.

Three smaller decisions finish the design: answer 302, not a cacheable 301, so every click still reaches you (analytics, takedowns); put a cache in front and send each click to a queue instead of updating the row, so the redirect writes nothing; and pick the shard key (the code) now but split the database only when storage demands it. Deep dives: 301 or 302, the cache and click counting, when to split (with sources)

301 or 302?

Both redirect; the difference is caching. RFC 9110 says "A 301 response is heuristically cacheable", meaning a browser or proxy may reuse it without asking again, while 302 "Found" says the target "resides temporarily under a different URI" and is not on the list of heuristically cacheable codes ({{RFC 9110 §15.4.2, §15.4.3, §15.1|https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.2}}). A cached 301 is free for you, but the browser stops coming back, so you lose its later clicks and cannot change or take down the destination for that browser. Choose 302 (or 301 with an explicit short cache lifetime) when analytics or takedowns matter. Bitly answers 301 with cache-control: private, max-age=90 (checked with curl -I on 2026-10-04, src/inputs/bitly_headers.txt): shared caches may not store it and a browser may reuse it for only 90 seconds, so nearly every click still reaches Bitly. Bitly's reason is not published; this is an observation, not their statement.

The cache, and counting clicks without slowing redirects

The redirect looks up the code in Redis (an in-memory key-value store, about 0.14 ms a lookup); on a miss it reads the database and puts the answer in Redis with a TTL (time to live, after which the entry expires). That is cache-aside, taught with its traps (stampedes when a hot key expires, stale entries after a takedown: delete the key on takedown) in {{Capacity planning and performance, Caching strategy|n:3ef5c17b0d0d81458291d55d7443700c}}. Links are written once and almost never change, the easiest possible thing to cache. An UPDATE links SET clicks = clicks + 1 on every visit turns each redirect into a write, and a viral link becomes one row that thousands of requests lock in turn; instead the server emits a click event to a queue and answers immediately, and consumers aggregate counts per link per hour. Bitly did exactly this: "Data about the conversion is popped onto a queue for the analytics and other downstream systems" (High Scalability, 2014). Delivery is at-least-once (an event may arrive twice after a crash), which a few duplicate clicks tolerate ({{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}).

18 TB, and when to split the database

The access pattern is a pure key lookup by code, with no joins: the easiest data to partition (split rows across several databases by a key). Hash the code to pick a shard; each shard has a replica for failover. Not on day one: the first year is 3.6 TB and 230 writes a second, which one PostgreSQL primary with a replica handles. Use the shard key now, so moving later is mechanical. A partitioned key-value store (DynamoDB, Cassandra) fits this pattern natively and is an equally good answer; pick what the team can operate. How partitioning and consistent hashing work: {{Distributed systems fundamentals, Partitioning|n:3c65c17b0d0d8115bc45c31d915b4d33}}.

What real companies built: Flickr's ticket servers, Twitter Snowflake

Flickr, 2010: "Ticket servers give us globally (Flickr-wide) unique integers to serve as primary keys in our distributed setup": a MySQL table where REPLACE INTO plus LAST_INSERT_ID() hands out the next number, run on two servers, one giving odd and one even numbers, so either can fail ({{Kremerskothen, Flickr, 2010-02-08|https://code.flickr.net/2010/02/08/ticket-servers-distributed-unique-primary-keys-on-the-cheap/}}).

Twitter Snowflake, 2010: a 64-bit ID made of "time - 41 bits (millisecond precision w/ a custom epoch gives us 69 years)", a "configured machine id - 10 bits - gives us up to 1024 machines" and a "sequence number - 12 bits - rolls over every 4096 per machine", so machines "should not have to coordinate with each other" and IDs sort roughly by time ({{snowflake README, 2010|https://github.com/twitter-archive/snowflake/blob/snowflake-2010/README.mkd}}; {{announcement, 2010-06-01|http://web.archive.org/web/2011/http://engineering.twitter.com/2010/06/announcing-snowflake.html}}). Snowflake IDs are too long for a shortener (a 64-bit number needs 11 base62 characters) but are the standard answer for "unique IDs across many machines", and Discord uses them for every message (design 3). Instagram built the same idea inside PostgreSQL (root {{Case files: Instagram 2012|n:3c65c17b0d0d81048ae0dd14ac399b4d}}).

What interviewers listen for
  • You asked about the read-to-write ratio and computed the code space instead of picking "6 characters" by habit.
  • You named at least two ID schemes and why you rejected one (collisions, enumeration, coordination).
  • You said 301 versus 302 out loud and tied it to analytics.
  • Click counting is off the hot path, and you said what at-least-once means for counts.
  • You did not shard on day one, and you said when you would.
