Design 7A distributed job scheduler: cron for a whole company

The brief offered a notification system or a job scheduler; the scheduler has the better public sources (Google's distributed cron, Dropbox's task framework, Slack's job queue, all with numbers), so it is the worked design here. A notification system reuses most of designs 3 and 7, and is a prompt in the {{Design drill|#t-drill}}, with Netflix's published design as its reference.

A job scheduler runs work at a given time: "every day at 02:00, rebuild the search index"; "in 30 minutes, send this reminder"; "every 5 minutes, poll this partner". Cron is the classic Unix program that does this on one machine, from a table of schedules written like 0 2 * * * (minute, hour, day, month, weekday). The company-wide version must survive machines dying without running jobs twice or skipping them silently.

Requirements
Functional
  • Register recurring (cron syntax) and one-off delayed jobs; cancel; pause.
  • Run each due job on a worker; record each run (start, end, result, logs link).
  • Retries with backoff for failed runs; alert the owner after N failures.
Non-functional
  • 10 million runs a day, 30% of them scheduled at the top of an hour (illustrative).
  • Start within a few seconds of the due time (Dropbox's target: 95% within 5 s, below).
  • No double runs of non-idempotent jobs; no silent skips.
  • Survives the loss of any machine.

What the numbers say. The average is small: 116 runs a second, about 2,300 running at once, 48 worker machines. The danger is the clock: people write 0 * * * *, so 30% of the day's runs, 125,000 of them, become due in the same second, which would need 2,500 machines for one second and 48 the rest of the time. Spreading each hourly batch over a minute with jitter (a random delay per job) brings the burst to about 2,100 a second. Run history (5 GB a day) is easy.

API

POST /v1/jobs {"name": "rebuild-index", "schedule": "0 2 * * *", "timezone": "Europe/London", "target": {"queue": "search", "payload": {...}}, "max_runtime_s": 3600, "overlap": "skip" | "queue" | "allow", "misfire": "run_once" | "skip"} POST /v1/jobs/{id}/pause DELETE /v1/jobs/{id} GET /v1/jobs/{id}/runs?cursor=...

overlap says what happens if the previous run is still going; misfire says what happens to runs missed while the scheduler was down: two decisions every scheduler forces, which the queues sibling discusses under {{Queues, streams and async work, Scheduling and cron|n:3ef5c17b0d0d81aebf91df927f215b6e}}.

Data model

jobs(id, schedule, timezone, next_run_at TIMESTAMPTZ, target, overlap, misfire, paused) INDEX ON (next_run_at) WHERE NOT paused runs(job_id, scheduled_for, attempt, state, lease_until, started_at, ended_at, result, PRIMARY KEY (job_id, scheduled_for)) -- one row per intended run: the idempotency key

The design, built step by step

Deep dive: deciding what is due, exactly once

Two machines both reading "what is due?" will both run the same job. Two standard fixes:

  • One leader. The scheduler replicas elect a leader (with a consensus system such as etcd or ZooKeeper, or Paxos/Raft directly) and only the leader launches. Clean, but failover takes seconds, and a deposed leader that does not yet know it is deposed can still launch, hence leases and fencing tokens ({{Distributed systems fundamentals, Leader election, leases and fencing tokens|n:3c65c17b0d0d8115bc45c31d915b4d33}}).
  • Row claiming in the database. Every scheduler instance runs SELECT ... FROM jobs WHERE next_run_at <= now() ORDER BY next_run_at LIMIT 100 FOR UPDATE SKIP LOCKED; SKIP LOCKED makes each instance skip rows another has locked, so they divide the work without a leader. In the same transaction each inserts the run row and advances next_run_at. Chosen at this scale: no extra system, and the database's transaction is the coordination.

Either way, the runs primary key (job_id, scheduled_for) makes "the 02:00 run of job 7" one row that can exist only once: a second scheduler that tries to create it gets a conflict instead of a second run. That is idempotency on the launch side.

Deep dive: the scheduler only enqueues

The scheduler must never run jobs itself: a slow job would delay every other launch. It writes the run to a queue; workers pull from the queue, take a lease on the run (a claim that expires unless renewed by heartbeats) and execute. If a worker dies, its lease expires and another worker retries the run. That gives at-least-once execution: a run that finished its work but died before recording success will run again. So jobs with side effects must be idempotent (use job_id plus scheduled_for as the idempotency key for anything they write or send), or they must check whether their effect already happened. Delivery semantics, visibility timeouts and dead-letter queues are taught in {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}.

Skip or double-run? Say which you prefer, and why

Google's distributed cron, which keeps its state consistent with Paxos across replicas, chose: "In general, we favor skipping launches rather than risking double launches, as much as the infrastructure allows", because "it is more acceptable to not launch Cron jobs for a while than to mistakenly launch the same Cron job ten times instead of once", and "all operations on external systems, which we may need to continue upon re-election, either have to be idempotent ... or we need to be able to look up their state" ({{Google SRE book, Distributed Periodic Scheduling with Cron|https://sre.google/sre-book/distributed-periodic-scheduling/}}; {{Davidovič and Guliani, ACM Queue, 2015|https://queue.acm.org/detail.cfm?id=2745840}}). A billing job prefers a skip plus an alert; a cache-warming job prefers a double run. Make it a per-job setting.

Deep dive: time is harder than it looks

  • Time zones and daylight saving: "02:30 every day" does not exist on the spring-forward day in London and happens twice on the autumn one. Store the job's time zone, compute next_run_at in UTC with a real time-zone library, and decide the rule for missing and repeated local times.
  • Thundering herd: add deterministic jitter (hash of the job id modulo the spread) to jobs that do not need an exact minute, so the same job runs at the same offset every hour.
  • Clock skew: scheduler machines disagree by milliseconds; use the database's now() as the one clock for "due".
What real companies built

Dropbox ATF (2020-11-11): "currently serving 9,000 async tasks scheduled per second and in use by 28 engineering teams". It guarantees "that a task is executed at least once after being scheduled" and "that at most one instance of a task will be actively executing at any given in point"; "95% of tasks begin execution within five seconds from their scheduled execution time". Its parts match this design: a Store Consumer "periodically polls the task store to find tasks that are ready for execution and pushes them onto the right queues" (Amazon SQS), and executors send heartbeats while they run ({{Krishnan, Dropbox|https://dropbox.tech/infrastructure/asynchronous-task-scheduling-at-dropbox}}).

Slack's job queue: "On our busiest days, the system processes over 1.4 billion jobs at a peak rate of 33,000 per second". When a database slowdown filled Redis to its memory limit, Slack "decided to add Kafka in front of Redis rather than replacing Redis with Kafka outright": a durable log absorbs the burst, and a relay feeds Redis at the rate it can take ({{Slack engineering, page dated 2017-12-06, updated 2020-06-25|https://slack.engineering/scaling-slacks-job-queue/}}).

Netflix Maestro (2024-07-22): a workflow orchestrator that "runs half a million jobs daily on average, and has completed around 2 million jobs on particularly busy days" ({{Netflix tech blog|https://netflixtechblog.com/maestro-netflixs-workflow-orchestrator-ee13a06f9c78}}): when jobs depend on each other, a scheduler grows into a workflow engine (durable workflows are in the queues sibling).

What interviewers listen for
  • You separated "decide what is due" from "do the work" with a queue between.
  • You made a run unique by (job, scheduled time) and explained at-least-once execution.
  • You found the top-of-the-hour spike from the numbers and answered it with jitter.
  • You chose between skipping and double-running per job, citing why.
  • Time zones, daylight saving and misfires were mentioned.
