Design 3Chat and messaging: WebSockets, fan-out, ordering, presence, storage

A chat system delivers a message to the others in a conversation within a second, keeps the history forever and shows who is online. The new ingredient after designs 1 and 2: the server must push, sending you a message while you are not asking for anything.

Requirements
Functional
  • One-to-one and group conversations (both called channels), groups up to a few thousand members.
  • Real-time delivery to online members; offline members catch up on return and get a push notification.
  • Full scrollable history; presence (online dots); read receipts.
Non-functional
  • 50 million daily users, 40 messages each a day, 20% connected at the peak (illustrative).
  • Delivery under 500 ms for online members.
  • Never lost once acknowledged; order within a channel the same for everyone; history kept forever.

What the numbers say. The message rate (46,000 a second at peak) is not the hard part. Three numbers are: 10 million open connections, about 100 servers that do nothing but hold connections; 333,000 presence heartbeats a second, seven times the message rate, so presence must be cheap and lossy; and 657 TB a year of stored messages with three copies, which no single database holds. If clients instead asked "anything new?" every 5 seconds, that is 2 million mostly empty requests a second, 43 times the real message rate: the row turns red, and that is why chat uses persistent connections.

The design, built step by step: from polling to channel servers and partitioned storage

The decisions that matter

The connection. A WebSocket ({{RFC 6455|https://www.rfc-editor.org/rfc/rfc6455}}) starts as an HTTP request that asks to "upgrade", then either side can send at any time over the same TCP connection. Long polling (the server holds each request until there is news) works everywhere but costs a request per message; server-sent events are one-way server push, what LLM APIs use to stream tokens ({{Building a backend API, section 14|n:3c65c17b0d0d8190ade6c34e8f653e79}}). Chat needs both directions often: WebSockets, with long polling as a fallback for hostile networks. Connection setup and TLS cost: {{Topic: protocols|n:3c65c17b0d0d81ec9355f4eecd6eed02}}.

Routing to the right connection. The sender is on gateway 17, recipients on 3, 58 and 90. A session registry ("user u is on gateway g") with direct forwarding is simple for one-to-one chat but costs 5,000 lookups per message in a 5,000-member group. Chosen: channel servers: each channel is owned by one server, picked by consistent hashing (adding a server moves only a small share of keys: {{Distributed systems fundamentals, Partitioning|n:3c65c17b0d0d8115bc45c31d915b4d33}}); gateways subscribe to their users' channels, so fan-out is one message per gateway, not per user.

Ordering, offline, presence. The channel's server assigns increasing message IDs, so order is per channel, decided in one place; order across channels is not promised (nobody can see it), and clients use the last ID to ask for what they missed after a reconnect. A message is stored before it is acknowledged, so pushing to connections is best effort and a missed push is caught up from storage by cursor; recipients with no connection get a mobile push through a queue ({{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}). Presence is a key with a TTL that heartbeats refresh, so a dead phone goes offline when the key expires; changes go only to people who are looking, batched, and may be seconds stale.

Storage. Reads are always "the latest 50 messages in channel c, then the 50 before", which points to a wide-column store (Cassandra, ScyllaDB: partitioned by a key across machines, rows sorted within a partition) keyed by channel and a time bucket, so a busy channel's partition stays bounded. A very busy channel is a hot partition (one key with a large share of traffic): cache recent messages in the channel servers and coalesce identical concurrent reads.

API and data model (frames over the WebSocket, Discord's storage key)
// over the WebSocket, as small JSON frames client -> {"op":"send", "channel":"c_42", "client_msg_id":"7f3a...", "text":"hi"} server -> {"op":"ack", "client_msg_id":"7f3a...", "msg_id":"1124203949381050368"} server -> {"op":"message", "channel":"c_42", "msg_id":"1124...", "from":"u_9", "text":"hi"} server -> {"op":"presence", "user":"u_9", "status":"online"} // over plain HTTP GET /v1/channels/c_42/messages?before=1124203949381050368&limit=50 history, by cursor

The client_msg_id is an idempotency key: if the acknowledgement is lost and the phone resends, the server recognises the ID and does not store the message twice. The server-assigned msg_id is a Snowflake-style ID (time first), so sorting by it sorts by time, and it doubles as the pagination cursor ({{Building a backend API, section 8|n:3c65c17b0d0d8190ade6c34e8f653e79}}).

messages PRIMARY KEY ((channel_id, bucket), message_id) -- Discord's key, below author_id, content, edited_at, ... -- bucket = time window (Discord: about 10 days), so one channel's history is many bounded partitions channel_members(channel_id, user_id, last_read_message_id) -- read receipts and unread counts sessions (in memory, e.g. Redis): user_id -> set of gateway servers holding that user's connections presence (in memory, with TTL): user_id -> online, expires unless refreshed by a heartbeat
What real companies built: Discord, Slack, WhatsApp

Discord presence, 2017: "When a user comes online, they connect to a guild, and the guild publishes a presence to all other connected sessions", and in servers with "up to 30,000 concurrent users", "publishing an event from a large guild could take anywhere from 900ms to 2.1s" until they batched sends per node ({{Vishnevskiy, Discord, 2017-07-06|https://discord.com/blog/how-discord-scaled-elixir-to-5-000-000-concurrent-users}}).

Discord storage, 2017: from one MongoDB collection "with a single compound index on channel_id and created_at" to Cassandra, because "our read/write ratio was about 50/50" and "Cassandra was the only database that fulfilled all of our requirements"; "channel_id became the partition key", message IDs are Snowflakes, and "if we stored about 10 days of messages within a bucket that we could comfortably stay under 100MB", giving the key "((channel_id, bucket), message_id)". They ran "a 12 node cluster with a replica factor of 3" at "well past 120 million" messages a day ({{Vishnevskiy, Discord, 2017-01-13|https://discord.com/blog/how-discord-stores-billions-of-messages}}).

Discord, 2023: "At the beginning of 2022, it had 177 nodes with trillions of messages"; hot partitions led to data services that coalesce reads ("If multiple users are requesting the same row at the same time, we'll only query the database once") and a move to "just 72 ScyllaDB nodes", with history p99 from "between 40-125ms" to 15 ms ({{Ingram, Discord, 2023-03-06|https://discord.com/blog/how-discord-stores-trillions-of-messages}}; root {{Case files: Discord 2023|n:3c65c17b0d0d81048ae0dd14ac399b4d}}).

Slack, 2023: "Every Slack client has a persistent websocket connection to Slack's servers"; Channel Servers "are stateful and in-memory", mapped to channels "based on consistent hashing"; a message goes from the web app to an Admin Server, which "discovers CS through a consistent hash ring", then to Gateway Servers and clients; "At peak times, about 16 million channels are served per host", messages arrive "across the world in 500ms", and "a new CS is ready to serve traffic in under 20 seconds" ({{Thangudu, Slack, 2023-04-11|https://slack.engineering/real-time-messaging/}}). Slack's January 2021 outage (root {{Case files: Slack 2021|n:3c65c17b0d0d81048ae0dd14ac399b4d}}) shows the other side: when the network, not the servers, is the bottleneck, autoscaling on CPU misreads it.

WhatsApp, 2012: one tuned Erlang server held "over 2 million tcp connections", "with plenty of CPU and memory to spare" ({{WhatsApp blog, 2012-01-06|https://blog.whatsapp.com/1-million-is-so-2011}}). Our planning figure of 100,000 per server is deliberately 20 times lower: a conservative default you would raise after load testing.

A gateway server100,000 clients disconnect at once and reconnect at onceReconnect with jittered backoff; catch up by cursor from storage, not from the server that died

What interviewers listen for
  • You computed connections, not just messages, and noticed presence outweighs messaging.
  • You justified WebSockets against polling with a number.
  • Order is per channel, assigned in one place; you did not promise global order.
  • Store before acknowledging; deliver best effort; catch up by cursor.
  • The storage key follows the read pattern (channel and time), and you named the hot-partition risk.
