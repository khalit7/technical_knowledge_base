The idea in one screen

Every design is the same seven steps; what differs is which number binds. Requirements give the load, the estimate turns it into per-second rates and bytes, and the one quantity that crosses a single machine's limit (storage, open connections, a shared counter, a burst, or money) is the part you design; everything else stays the simplest thing that works.

Functional / non-functional
what the system does / how much, how fast, how reliably, how consistently, how cheaply. The second kind decides the architecture.
Back-of-the-envelope estimate
users to requests a second, bytes and machines, one significant figure, each row compared with one machine's capacity.
Bottleneck
the first resource to run out as load grows; in the step diagrams it turns red and the next step fixes it (green).
Fan-out
one event delivered to many recipients (followers, gateways, subscribers); where it happens (on write or on read) is a recurring choice.
Fail open
when a check cannot run, allow the request (a rate limiter); fail closed denies (a permission check).

The method, out loud

What each step sounds like in a 45-minute interview (Alex Xu's ranges, quoted on the root: scope 3 to 10 minutes, high-level design 10 to 15, deep dive 10 to 25, wrap-up 3 to 5; {{ByteByteGo|https://bytebytego.com/courses/system-design-interview/a-framework-for-system-design-interviews}}). At work the same steps become a design document, the written proposal a team reviews before building.

StepWhat you doWhat it sounds like
1. RequirementsFunctional and non-functional; agree what is out of scope."Before I draw anything: who uses this, how many, and what happens if a click is lost or counted twice?"
2. EstimateUsers to requests a second, to storage, to machines. Round hard; keep one significant figure."600 million new links a month is about 230 a second, so writes are easy. 6 billion clicks is 2,300 a second; doubled for the peak, under 5,000."
3. APIThe calls clients make, with method, path, body and errors ({{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}})."POST /links returns the code; the redirect is a GET that answers 302."
4. Data modelTables or keys, and how each read finds its row (which index, which partition key)."One table keyed by code; the redirect is a primary-key lookup."
5. High-level designThe boxes and arrows, each justified by a requirement or a number."Stateless app servers behind a load balancer, a cache, one database."
6. Deep divesThe two or three parts the estimate flagged. Let the interviewer steer."The interesting parts are ID generation and the cache; which would you like first?"
7. Bottlenecks and failureWhat breaks at 10×, what happens when each box dies, what each choice cost."If the cache dies, 4,600 reads a second land on the database: within one machine's capacity, so we survive degraded."

The estimating toolkit

Every estimate here uses the parent root's {{Numbers to know|n:3c65c17b0d0d81048ae0dd14ac399b4d}} constants, so the topic stays consistent (recompute.py asserts they match):

  • A day is 86,400 seconds (call it 100,000: a million a day is about 12 a second); a month is 2.6 million seconds.
  • Peak over average: the root uses 2 as an illustrative planning factor; Twitter's record second in 2013 was 25 times its average (root, {{Case files: Twitter 2013|n:3c65c17b0d0d81048ae0dd14ac399b4d}}). Say which you assume.
  • One app server (AWS m7i.xlarge, $0.2016 an hour): 500 requests a second, the root's illustrative default.
  • One PostgreSQL database: about 35,000 read queries a second, 18,000 mixed read-write (PlanetScale, 4 vCPU; root Numbers), planned at half a benchmark (the root's derating).
  • One Redis node: 180,180 SETs a second with 50 clients (Redis docs benchmark), planned at 90,090; about 0.14 ms an operation locally, about 0.5 ms a round trip inside one cloud region.
  • GPUs: 2,209 output tokens a second per H100 for Llama 3.3 70B in FP8 (TensorRT-LLM, commit 8a9c66c), $3.99 per GPU-hour (Lambda); see {{ML system design, section 6|n:3c65c17b0d0d8117b057dc2586836ec8}}.
  • Little's law: things in the system = arrival rate × time each stays; it turns requests a second into connections open or jobs running ({{Capacity planning and performance, Queueing theory you actually use|n:3ef5c17b0d0d81458291d55d7443700c}}).
An estimate earns its minutes only if it changes a decision

"36 billion links do not fit in 6 base62 characters" changes the code length; "18 TB" changes whether you shard; "333,000 presence heartbeats a second" changes what you optimise first in chat. If a number would not change any box, skip it and say so.
