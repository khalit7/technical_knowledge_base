In one screen

A system design question gives you a product ("design a URL shortener") and an hour, and asks for the machines, data and connections that would run it for millions of people. There is no single right answer. What separates a strong answer from a weak one is a method: find out what is really being asked, put numbers on it, and let the numbers tell you which part is hard. The parent topic's Step 6 introduced that method ({{Topic: swe-and-system-design, Reading, Step 6|n:3c65c17b0d0d81048ae0dd14ac399b4d}}); this page runs it seven times, end to end, the way a senior engineer would say it out loud.

What every design on this page has in common

1. Requirements before boxes. Every design starts with a box of functional and non-functional requirements; the second kind (scale, latency, how wrong you may be) decides the architecture.

2. A computed estimate, live. Each design has a table you can change (try "10× the traffic"); rows turn red when they cross a single machine's capacity. That is how a bottleneck is found rather than guessed.

3. A diagram that grows. Each design is animated from its naive version, then each bottleneck is found (red) and fixed (green) in turn, with counters showing the naive design's number beside the current one on the same load.

4. What was rejected, and why. A design is a list of trade-offs. Each section says what it chose, what it turned down, and what real companies did.

Two measurements were run for this page on a laptop with a real PostgreSQL database (src/lab/measure_pg.py, about 2 minutes): the rate limiter race (a check-then-act counter let 17 to 19% too many requests through; the atomic form, exactly 0) and fan-out on read against on write (reading a precomputed timeline was 34 times faster). To practise, use the {{Design drill|#t-drill}} tab: pick a prompt, run the clock, reveal the method one step at a time and tick a self-check list.

The method, out loud

The parent root lists the steps; here is what each sounds like in the room, and how long it gets in a 45-minute interview (timings from Alex Xu's framework, quoted on the root: scope 3 to 10 minutes, high-level design 10 to 15, deep dive 10 to 25, wrap-up 3 to 5; {{ByteByteGo|https://bytebytego.com/courses/system-design-interview/a-framework-for-system-design-interviews}}). In real work the same steps go into a design document, the written proposal a team reviews before building.

StepWhat you doWhat it sounds like
1. RequirementsFunctional (what it does) and non-functional (how much, how fast, how reliable, how consistent, how cheap). Agree what is out of scope."Before I draw anything: who uses this, how many, and what happens if a click is lost or counted twice?"
2. EstimateUsers to requests a second, to storage, to machines. Round hard; keep one significant figure."600 million new links a month is about 230 a second, so writes are easy. 6 billion clicks is 2,300 a second; doubled for the peak, under 5,000."
3. APIThe calls clients make, with method, path, body and errors (the {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}} page teaches this)."POST /links returns the code; the redirect is a GET that answers 302."
4. Data modelTables or keys, and how each read finds its row (which index, which partition key)."One table keyed by code; the redirect is a primary-key lookup."
5. High-level designThe boxes and arrows, each justified by a requirement or a number."Stateless app servers behind a load balancer, a cache, one database."
6. Deep divesThe two or three parts the estimate flagged. Let the interviewer steer."The interesting parts are ID generation and the cache; which would you like first?"
7. Bottlenecks and failureWhat breaks at 10×, what happens when each box dies, what each choice cost."If the cache dies, 4,600 reads a second land on the database: within one machine's capacity, so we survive degraded."

The estimating toolkit

Every estimate on this page uses the same few constants, taken from the parent root's {{Numbers to know|n:3c65c17b0d0d81048ae0dd14ac399b4d}} tab so the topic stays consistent:

  • A day is 86,400 seconds (call it 100,000 for mental arithmetic: a million a day is about 12 a second), and a month is 2.6 million seconds.
  • Peak over average: traffic is not flat. The root uses 2 as an illustrative planning factor; Twitter's record second in 2013 was 25 times its average (root, {{Case files: Twitter 2013|n:3c65c17b0d0d81048ae0dd14ac399b4d}}). Say which you assume.
  • One app server (AWS m7i.xlarge, $0.2016 an hour): 500 requests a second, the root's illustrative default.
  • One PostgreSQL database: about 35,000 read queries a second, 18,000 in a mixed read-write benchmark (PlanetScale, 4 vCPU; root Numbers). We plan at half a benchmark, the root's derating.
  • One Redis node: 180,180 SETs a second with 50 clients (Redis docs benchmark); planned at half, 90,090. A Redis operation answers in about 0.14 ms locally; a round trip inside one cloud region is about 0.5 ms.
  • GPUs: 2,209 output tokens a second per H100 for Llama 3.3 70B in FP8 (TensorRT-LLM, commit 8a9c66c), $3.99 per GPU-hour (Lambda); see {{ML system design, section 1|n:3c65c17b0d0d8117b057dc2586836ec8}}.
  • Little's law: things in the system = arrival rate × time each one stays. It turns "requests a second" into "connections open" or "jobs running" ({{Capacity planning and performance, Queueing theory you actually use|n:3ef5c17b0d0d81458291d55d7443700c}}).
The commonest failure: no numbers, or numbers that change nothing

An estimate earns its minutes only if it changes a decision. "36 billion links do not fit in 6 base62 characters" changes the code length; "18 TB" changes whether you shard; "333,000 presence heartbeats a second" changes what you optimise first in chat. If a number would not change any box, skip it and say so.
