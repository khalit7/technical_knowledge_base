The whole journey in one screen

About 25 minutes to read (a little over the usual root page because it starts from zero), plus the optional animations; every term is explained where it first appears and collected in the Glossary.

System design is the craft of keeping a product fast, correct and affordable as more people use it. Nothing here has to be memorised as a list. Every building block you will meet exists because, at some number of users, something broke. So this page follows one product as it grows and lets each problem arrive before its fix.

The running example. A chat assistant powered by a large language model (LLM): people sign in, chat, and come back to their history. It starts on one machine with one user (you) and grows to ten million registered users. You have already served a model behind an API, so the first picture will look familiar; the second is where this page takes you.

The one idea to keep
Every building block is a fix for a specific problem that has a price. A cache makes reads fast and makes data slightly stale; a queue makes requests fast and makes results arrive later; a retry rescues one request and can sink the whole system. A senior engineer adds a block only when the problem it solves has actually arrived, and can say what it costs.

Step 1 One server, then too many requests for it

What happens when someone sends a message

Before anything can scale, it helps to see one request whole. You type "summarise this" and press Enter. Your browser or phone app is the client: the program that asks. Somewhere a server answers: a program (and, loosely, the machine it runs on) that waits for requests and sends back responses. Between them, six things happen in order.

1. DNSThe name chat.example.com is looked up and turned into an IP address.
→
2. TCPA connection is opened to that address: one round trip.
→
3. TLSThe connection is encrypted: one more round trip in TLS 1.3.
→
4. HTTP requestPOST /chats/42/messages with your text.
→
5. Server processCode checks who you are, reads and writes the database, calls the model.
→
6. HTTP response200 OK and the reply, often streamed word by word.

DNS is the internet's phone book: it maps a name to an IP address, a machine's numeric address (RFC 1034). TCP gives both sides a reliable, ordered stream of bytes, and opening it costs one network round trip (there and back) (RFC 9293). TLS encrypts the stream (the "S" in HTTPS) for one more round trip (RFC 8446); reusing an open connection skips both. HTTP is the request itself: a method (GET reads, POST creates, PUT replaces, DELETE removes), a path, a body, and in the answer a status code: 2xx worked, 4xx the client's mistake, 5xx the server's (RFC 9110). An API is the set of requests a server promises to understand; each method plus path is an endpoint, the thing you already built around a model.

Behind the server sits the database: a program that keeps data safe on disk and answers questions about it quickly. Users, chats and messages are rows in tables, fetched with SQL, a query language: SELECT * FROM messages WHERE chat_id = 42. A server can crash and restart; the data must never be lost. Postgres and MySQL are the usual first choices.

Two words measure all of this. Latency is how long one request takes, from the user's point of view. Throughput is how many requests the system finishes per second. A highway can carry many cars (throughput) while each still takes an hour (latency). Requests vary, so latency is quoted as percentiles: the p50 (median) is the typical request, the p99 the slowest 1 in 100. Averages hide the slow tail; Google's SRE book says to treat metrics "as distributions rather than averages" (SRE book, ch. 4). Typical latencies for each hop (a round trip, a disk read, a database query) are in Numbers to know.

The problem appears
On launch day the app works. Then a post goes viral. Say your one server can answer 400 requests per second and 600 per second arrive (both numbers illustrative: real capacity depends entirely on what each request does). Every second, 200 more requests arrive than leave. They wait in line, the line grows, and every user's latency grows with it, without limit, until clients give up. This is the first law of capacity: when work arrives faster than it is finished, waiting time does not rise a little, it rises without bound.

There are two ways out. Vertical scaling buys a bigger machine: more cores, more memory. It needs no code changes, so it is the right first move, but it has a ceiling and the one machine stays a single point of failure: when it reboots, the product is down. Horizontal scaling adds more machines of the same size. It has no hard ceiling and survives one machine dying, but something must now decide which machine gets each request.

The building block: a load balancer
A load balancer is a small, fast program that sits in front of the servers and hands each incoming request to one of them: in turn (round robin), or to whichever has the fewest requests in progress. It also sends small health checks to each server and stops sending traffic to one that fails them, so a crashed machine stops being a crashed product.

Horizontal scaling has one precondition that changes how you write code. If server A remembers you signed in and your next request lands on server B, B has never heard of you. Servers must be stateless: nothing another server would need stays on them between requests. That remembered state, the session, moves out: into the database, a shared fast store (Step 2's cache), or a signed token the client sends with every request. Then any server can answer any request.

Illustrative traffic: one dot is 100 requests; each server finishes 4 dots (400 requests) per second; arrivals vary between 5 and 8 dots a second. Requests are handed out in turn (round robin). Numbers checked in src/read/recompute.py.

What it costs
More machines to pay for and run; the load balancer itself must not become the new single point of failure (in practice it is a managed service or a redundant pair); and every piece of state you moved out of the servers now lives in one shared place, the database. That is where the next wall is.

Step 2 The database becomes the bottleneck

The problem appears
App servers can be added forever; they all talk to one database. Opening a chat reads its history; sending a message writes two rows and reads the history again for the model. Say that at a few hundred thousand users the servers together send the database 1,000 reads per second and it can answer about 600 (illustrative). Same law as Step 1, and now every server waits on it. Reads far outnumber writes here, so start with reads.

First, the cheap fix: an index

Asked for "all messages of chat 42" with no help, the database reads every row: a full scan, fine at a thousand rows, hopeless at a billion. An index is a separate, sorted structure that maps a column's values to where the rows live, exactly like the index at the back of a book: look up "chat 42", jump to its pages (Postgres docs). Cost: every write also updates every index, and indexes take space, so index only the columns you search by. Many "the database is slow" incidents end with one missing index.

Then a cache: do not ask the same question twice

A cache is a small, fast store (usually in memory, such as Redis) holding copies of answers the system has already computed. Memory answers far faster than a database query (see Numbers to know). The usual pattern is cache-aside: the server first asks the cache; on a hit it is done; on a miss it reads the database, then stores the answer in the cache for next time (Microsoft pattern guide; Amazon calls it a "side cache", Builders' Library). The share of reads answered by the cache is the hit rate; at a 90% hit rate the database sees one read in ten.

A copy can go stale. A TTL (time to live) makes each entry expire after a set time, bounding staleness ("at most 60 seconds old"). Invalidation deletes the cached copy when the data changes: rename a chat, and the server writes the database, then deletes that chat's cache entry. A cache of static files (images, the app's code) placed in many cities near users is a CDN (content delivery network).

Animation: the same reads, straight to the database against through a cache

Illustrative traffic: one square is 50 reads per second (20 squares, 1,000 reads/s); the database answers 12 squares (600 reads/s). The hit rate warming from 0% to 90% is an assumption: real hit rates depend on how often the same data is read again.

What a cache costs
Stale reads (bounded by the TTL, or fixed by invalidation, which is easy to forget in one code path); one more system to run; and a dangerous dependency. If the cache empties (a restart, a new server with a cold cache), the full read load lands on a database sized for 10% of it. Amazon's engineers name this risk and the usual fix, letting only one request fetch a missing key while the others wait for it ("request coalescing", Brinkley and Chhabra).

Copies of the database: read replicas

Some reads cache badly (every chat list differs and changes constantly). Next comes a read replica: a full copy of the database. All writes go to one primary, which streams every change to the replicas; reads spread over them (Postgres hot standby), and a replica can take over if the primary dies. Cost: copying takes time, the replication lag, sometimes seconds. A user sends a message, the page refreshes, the read hits a replica that has not caught up, and the message has vanished; the usual fix is to read your own recent writes from the primary.

Splitting the database: sharding

Replicas multiply reads, but every write still goes through one primary. When writes or data outgrow one machine, split the data: sharding (or partitioning) gives each of several databases a slice, chosen by a shard key. Shard by user: user 17's chats live on shard 17 mod 8. Cost: anything across users (global search, weekly totals) must ask every shard; adding shards means moving data; one very busy user still lands on one shard. It is usually the last resort.

What you give up: consistency

Caches and replicas keep several copies, and copies disagree for a moment after every change. Strong consistency (linearizability, in the precise vocabulary) means every read sees the latest write, as if there were only one copy. Eventual consistency means copies may differ for a while but converge once writes stop. Strong costs coordination: waiting for copies to agree. Jepsen keeps a map of the many levels in between (Jepsen consistency models).

Two well-known statements make the trade explicit. CAP: when the network between copies breaks (a partition), a system must choose to stay consistent (refuse some requests) or stay available (answer, possibly with stale data); it cannot have both during the partition (Gilbert and Lynch, 2002). Partitions are rare, so Abadi's PACELC adds the everyday half: "else (E), when the system is running normally ... how does the system trade off latency (L) and consistency (C)?" (Abadi, IEEE Computer 2012). In practice you choose per piece of data: a user's paid credit balance must be strongly consistent (never spend the same credit twice); the order of chats in the sidebar can be a second stale and nobody will notice.

Step 3 Slow work leaves the request path

The problem appears
A new feature: upload a PDF and chat with it. The server must extract the text, cut it into pieces and compute an embedding for each (a list of numbers representing its meaning, used later to find the passages relevant to a question). For a long document that takes tens of seconds, and done inside the request it holds one of the server's few request slots (threads) the whole time. A handful of uploads fill every slot and quick chat messages queue behind them. In the animation below, 5 uploads among 30 chat messages make chat messages wait up to 3 seconds that should have waited none (illustrative).

The insight: the user does not need the result now; they need to know it is being done. Separate "accept the work" from "do the work".

The building block: a queue and background workers
A message queue is a durable list of jobs that sits between the part of the system that creates work and the part that does it (Amazon SQS, RabbitMQ, Kafka and Redis streams are common ones). The request handler writes "process document 981" to the queue and immediately answers 202 Accepted. Separate workers, processes whose only job is to take jobs off the queue, do the slow work in the background, then mark the document ready; the app shows a spinner until then. This is asynchronous processing: the response does not wait for the work.

Illustrative traffic: one server with 4 request slots; 3 chat messages a second (each needs a slot for one second); 5 uploads in the first 6 seconds, each needing 4 seconds of work. Checked in src/read/recompute.py.

Three things a queue makes you think about

Jobs can run twice. A worker can crash halfway through a job. So that nothing is lost, the queue deletes a job only when a worker confirms it (an acknowledgement) and hands unconfirmed jobs out again: at-least-once delivery, whose other face is that a job can run twice. So make jobs idempotent: running one twice has the same effect as running it once ("set document 981's embeddings to X", not "append embeddings"). HTTP defines idempotent the same way: "the intended effect on the server of multiple identical requests ... is the same as the effect for a single such request" (RFC 9110 §9.2.2). A job that keeps failing is moved aside to a dead-letter queue for a human to look at, so it does not block the rest.

A queue can hide overload. If jobs arrive faster than workers finish them, the queue grows and nothing looks broken; results just arrive later and later. Amazon's David Yanacek describes queue systems as having two modes: with no backlog "the system's latency is low", and once a backlog forms, "end-to-end latency grows higher and higher" and it can take a long time to recover (Avoiding insurmountable queue backlogs). So you watch the age of the oldest job, not just errors, and you apply backpressure: when the queue is too long, tell the producers to slow down or refuse new work (for example with HTTP 429 Too Many Requests, RFC 6585) instead of accepting work you cannot finish.

How many workers you need is arithmetic. Little's law says that, on average, the number of things in a system equals the rate they arrive times the time each one stays: L = λW (Little, 50th-anniversary paper). If 5 documents arrive per second and each takes 20 seconds of work (illustrative), then on average 5 × 20 = 100 documents are being processed at once, so you need at least 100 worker slots; with fewer, the queue grows without bound. The same law sizes the model layer in Steps 5 and 6.

What it costs
The result arrives later and the product must show progress; failures happen out of sight and need their own alerts; jobs must be idempotent; and the queue is one more system to run. Use it for slow work that can be late, not for the reply the user is staring at.

Step 4 Things fail, and the fixes can make it worse

The problem appears
The system is now dozens of machines and several outside services. At this size something is always failing: a server reboots, a link drops packets, the model provider has a slow hour. Say 1 request in 100 to the model provider hangs for a minute during that hour (illustrative). Each hung call holds a request slot (Step 3) for a minute, slots run out, and one dependency's problem takes down your whole product.

Timeouts: never wait forever

A timeout is a deadline on every call to another system: if no answer comes within it, give up and free the slot. Too long and slots pile up; too short and you abandon calls that would have succeeded. Marc Brooker of AWS describes the usual way to choose: pick an acceptable rate of false timeouts, "such as 0.1%", then set the timeout at the matching latency percentile of the service you call, "p99.9 in this example" (Timeouts, retries and backoff with jitter).

Retries, and why they need backoff and jitter

Many failures are momentary, so the natural fix is a retry. Retries rescue single requests and can sink the system: each is extra load arriving exactly when it struggles. Brooker's example: if each of five layers of a system retries three times, "the load on the database will increase 243x" (35), "making it unlikely to ever recover". A flood of retries that keeps a recovering system down is a retry storm, and the general pattern, a system that stays broken after its trigger is gone because something (often retries) sustains the overload, is what Bronson and colleagues called a metastable failure (HotOS 2021).

Two habits fix it. Exponential backoff waits longer after each failure (1, 2, 4, 8 seconds, up to a cap), so retries thin out. Jitter makes each wait random, because clients that failed together and back off by the same amounts retry together again, in synchronised waves. Brooker's simulation compared the variants and found that backoff without jitter "is the clear loser"; his recommended "full jitter" waits a random time between zero and the backoff (AWS Architecture Blog, 2015). Cap the number of attempts, retry at one layer only, and retry only requests that are safe to repeat, which is the second half of the animation.

The double charge, and idempotency keys

A user buys 1,000 credits for $20. The server charges the card and the response is lost (the phone went into a tunnel). To the client, a failure before the charge and one after it look identical. Retry, and the user may pay twice; don't, and they may get nothing. Brandur Leach of Stripe lays out the cases (Stripe, 2017). The fix is an idempotency key: the client invents a unique ID for this one purchase and sends it with every attempt. The server records the key together with the result; a retry with the same key gets the stored result back instead of a second charge. AWS does the same with "client request tokens", and returns an error if the same token arrives with different parameters (Featonby, Builders' Library). This is how a request that is not naturally idempotent (Step 3) is made safe to retry.

Failing well: circuit breakers, load shedding, degradation

A circuit breaker wraps calls to a dependency and counts failures; past a threshold it "opens" and fails calls immediately for a while, without calling, then lets a few test calls through to see whether the dependency has recovered (Fowler). Load shedding is the same reflex applied to your own service: when nearly overloaded, reject the excess quickly so the requests you accept still succeed (Yanacek, Builders' Library). Graceful degradation decides in advance what a worse-but-working product looks like: if the large model is down, answer with a smaller one; if search is slow, answer without it; and only then show an honest error.

How reliable is reliable enough: SLOs and error budgets

"Never fail" is impossible, so reliability gets a number. An SLI (service level indicator) is "a carefully defined quantitative measure" of service, such as the share of chat requests answered successfully within 10 seconds; an SLO (objective) is "a target value ... for a service level that is measured by an SLI"; an SLA (agreement) is the contract, with consequences, built on them (SRE book, ch. 4). The gap between the SLO and perfection is the error budget: Google's SRE teams treat it as "the 'budget' of how much 'unreliability' is remaining", and "as long as there is error budget remaining ... new releases can be pushed" (SRE book, ch. 3). For our product: an SLO of 99.9% of messages succeeding, at 10 million messages a day (Step 6's estimate), allows 10,000 failures a day, about 300,000 in a 30-day month. Spend it on shipping; when it is gone, slow down and fix.

Seeing inside: observability

Observability, seeing inside a running system, rests on three kinds of signal (OpenTelemetry): logs (a timestamped line per event: "request 7f3 failed: provider timeout"), metrics (numbers over time: requests per second, p99 latency, error rate), and traces (one request followed across every service it touched, with the time spent in each, which is how you find which of twelve hops was slow). Google's starting set of metrics is the four golden signals: latency, traffic, errors and saturation, "how 'full' your service is" (SRE book, ch. 6).

What it costs
Each adds code that only runs when something is already wrong, the least tested code you own. Retries add load; idempotency keys need storage and an expiry; observability costs money per log line. Name the failure each mechanism defends against, and test it on purpose.

Step 5 The GPU layer: a backend unlike the others

The problem appears
Everything so far assumed a request costs milliseconds of an ordinary processor. A chat reply costs seconds of a GPU (the graphics processor that models run on, with its own fast memory). A model generates text one token (a word or piece of a word) at a time, and for every token it must read all of its weights from GPU memory. For an 8-billion-parameter model in 16-bit numbers that is 16 GB per token; an NVIDIA H100 reads memory at 3.35 TB/s (NVIDIA), so one conversation can get at most about 210 tokens a second, and a 500-token reply takes at least 2.4 seconds (derived: 16 GB ÷ 3.35 TB/s = 4.8 ms per token). One user at a time per GPU will not serve ten million.

Why a model is not a normal backend

  • Two phases. Reading the prompt (prefill) handles all its tokens at once and is limited by arithmetic; writing the answer (decode) makes one token per step and is limited by memory bandwidth, as above.
  • Long-lived responses. Replies are streamed token by token over one open connection (commonly server-sent events, SSE), so each reply holds a connection open for seconds (Little's law counts them in Step 6).
  • Capacity comes in big, slow blocks. A 70-billion-parameter model in 16-bit numbers is 140 GB of weights, more than one 80 GB H100 holds, so one copy of the model (a model replica) spans several GPUs. You add capacity a replica at a time, and a new replica must load its weights before serving: 140 GB at an illustrative 2 GB/s is 70 seconds, before starting the packaged program (the container) and warming up. These cold starts take minutes, so GPUs cannot be added the moment a spike arrives.
  • Memory per conversation. To avoid recomputing the conversation for every new token, the model keeps intermediate results for every token so far: the KV cache. It grows with the conversation in scarce GPU memory, so it often limits how many users a GPU serves at once (PagedAttention, KB paper page).

Batching: one read of the weights, many users

Since each decode step reads all the weights anyway, the same read can produce the next token for many conversations at once: batching. With 64 conversations in a batch, the 4.8 ms weight read yields 64 tokens instead of one, a ceiling of about 13,000 tokens a second (derived, ignoring KV cache reads and arithmetic). Real engines go further with bigger batches and smaller number formats: NVIDIA's published performance overview (v0.21 data) reports about 15,000 output tokens a second for Llama 3.1 8B in 8-bit on one H100, 1,000 input and 1,000 output tokens per request, at maximum load (vendor benchmark; see Numbers to know). The catch is that replies have different lengths. In static batching the batch runs until its longest reply finishes, and slots whose reply ended early sit idle. Continuous batching (iteration-level scheduling, introduced by Orca, OSDI 2022) lets a new request take a slot the moment one frees up, at every step. Anyscale's benchmark reported up to 23x the throughput of naive static batching when combined with vLLM's memory management (Anyscale, 2023; a single benchmark by an interested party, so read it as "large", not as a constant).

Do less work: caching prompts, routing, limits

Prefix caching. Requests in a conversation start with the same system prompt and history; engines can keep the KV cache of that shared beginning and skip its prefill: prefix caching (vLLM docs). Model providers sell the same idea: Anthropic says prompt caching reduces "costs by up to 90% and latency by up to 85% for long prompts" (Anthropic; vendor figure), and OpenAI applies it automatically to long prompts and advises putting "stable developer instructions and shared reference material first" (OpenAI docs). Lesson: what never changes goes first in the prompt. A riskier cousin, the semantic cache, returns a stored answer when a new question merely looks similar to an old one; it is cheap and wrong whenever the answer should depend on who is asking or when.

Routing across models. A model router sends easy requests to a small, cheap model and hard ones to the large model, and doubles as Step 4's degradation path.

Rate limits per customer. A rate limit caps how much each user or tenant (a customer organisation) may send per minute; past it they get 429 Too Many Requests. The common algorithm is the token bucket: each customer has a bucket that refills at a steady rate, and each request takes from it, which allows short bursts but caps the average (Stripe: "We use the token bucket algorithm", Stripe, 2017). For a model, limit tokens per minute as well as requests, because one request with a 100,000-token document costs as much as a thousand short ones.

What it costs
Batching trades a little latency per user for much more throughput per GPU. Output caches can serve the wrong answer to the wrong person; routers misjudge difficulty. And GPUs are expensive idle and slow to add, so fleet size is a bet on tomorrow's traffic, which Step 6 estimates.

Step 6 Designing it on purpose: the method

The problem appears
Steps 1 to 5 were reactive. That works until a fix takes months (sharding a live database, buying GPUs), or someone asks for the design before the system exists. How many GPUs do ten million users mean, and what breaks first? Without numbers, a design is a guess drawn in boxes.

The method below is what experienced engineers do, in roughly this order, and it is also the structure that system design interviews expect (Alex Xu's System Design Interview compresses it into four phases for a 45-minute interview: understand the problem and establish design scope, 3 to 10 minutes; propose a high-level design, 10 to 15; deep dive, 10 to 25; wrap up, 3 to 5; ByteByteGo). Each step narrows the next.

Requirements. Functional requirements say what the system does: sign in, chat, keep history, upload documents. Non-functional requirements say how well: how many users, how fast (time to first token under 1 second at p99, say), how reliable (an SLO), how cheap, what privacy rules. The non-functional ones decide the architecture; ask them first.
Back-of-the-envelope estimates. Rough arithmetic, accurate to a factor of two or so, that turns users into requests per second, tokens per second, GPUs and storage. It tells you which part is the hard part. The animation below does it for our product.
API. The endpoints the clients will call: POST /chats, POST /chats/{id}/messages (streams the reply), GET /chats/{id}/messages?cursor=..., POST /documents (returns 202, Step 3). Writing them forces decisions: what is idempotent, what streams.
Data model. The tables and how they are found: users, chats (owned by a user), messages (in a chat, in order), documents. Every query should hit an index and carry the likely shard key (user).
High-level design. The boxes and arrows: the right-hand picture at the top of this page. Each box should be justified by a requirement or an estimate.
Deep dives. The two or three parts the estimates flagged as hard. For this product: the GPU fleet (Step 5) and the message store (Step 2). Go into those, not into everything.
Bottlenecks and trade-offs. What breaks at ten times the traffic, what fails when a dependency fails (Step 4), and what each choice cost.

Two lessons fall out of the arithmetic. First, the model layer dominates: 115 requests per second is a small load for app servers and a database, while the same traffic needs tens of GPUs. Second, the peak sets the size, not the average: a fleet sized for the average day is short of capacity for 14 hours of it, and a fleet sized for the peak sits more than half idle overnight. Closing that gap is why autoscaling (adding and removing model replicas automatically as traffic moves; slow for GPUs because of cold starts), cheaper batch work at night and routing to smaller models matter so much in practice (Step 5).

How this maps to interviews
A general system design interview (45 to 60 minutes) is this method out loud: clarify requirements, estimate, sketch the API and data model, draw the high-level design, then let the interviewer pick a deep dive. Machine learning system design interviews swap part of the middle for ML-specific steps: the metrics that define success offline and online, the data, the model choice, then serving and monitoring (Chip Huyen's free Machine Learning Systems Design booklet uses this framing). In both, what is judged is whether you quantify and name trade-offs, not how many component names you know.

How a senior engineer reasons

The habits of mind that use the six steps; each is a question asked before adding anything.

Start from the invariant, not the component. Write down what must never happen ("never charge twice", "never lose a message") and what may happen ("the sidebar is a second stale"). Then choose consistency and retries per invariant (Steps 2 and 4).
Do the arithmetic first. Requests per second, tokens, GPUs, bytes: the numbers say which part is hard (Step 6).
Add a block only when its problem has arrived. A cache before reads hurt or sharding before one machine is full adds cost and failure modes for nothing. A bigger machine and one Postgres go a long way.
Name the cost of every choice. "We cache chat lists for 30 seconds; a renamed chat can show the old name for up to 30 seconds; acceptable." If you cannot say what a choice gives up, you do not yet understand it.
Design for failure as the normal case. Every call gets a timeout; retries get backoff, jitter and a cap; every retried write gets an idempotency key; every queue is bounded; there is a planned worse-but-working mode (Step 4). Test those paths on purpose.
Measure before and after. Percentiles, not averages; an SLO that says when reliability is good enough. Unmeasured "fixes" often move the problem.
Prefer reversible decisions, and decide the irreversible ones late. A function can be rewritten tomorrow; a public API, a schema and a shard key are very expensive to change later. Spend your care there.

In an interview, the same habits are what is assessed: clarify before drawing, estimate before choosing, and say the trade-off of every box.

Glossary

Every term this page introduces, in the order of the steps. Each name links back to where it is explained.

Step 1: one request, one server

Client: the program that sends a request (browser, app).
Server: the program (or machine) that answers requests.
DNS: turns a name into an IP address.
IP address: the numeric network address of a machine.
TCP: a reliable, ordered connection between two machines.
Round trip: a message there and its answer back.
TLS: encryption of a connection (the S in HTTPS).
HTTP: the request and response format: method, path, headers, body.
Status code: the number saying how a request went (2xx, 4xx, 5xx).
API: the set of requests a server promises to understand.
Endpoint: one method plus path of an API.
Database: the program that keeps data safe and answers queries.
SQL: the query language for tables of rows.
Latency: how long one request takes.
Throughput: how many requests finish per second.
Percentile (p50, p99): the latency that 50% or 99% of requests beat.
Vertical scaling: a bigger machine.
Single point of failure: one part whose failure stops everything.
Horizontal scaling: more machines of the same size.
Load balancer: hands each request to one of several servers.
Health check: a probe that takes failing servers out of rotation.
Stateless server: keeps nothing between requests that another server would need.
Session: what the system remembers about a signed-in user between requests.

Step 2: the database

Index: a sorted lookup structure that avoids scanning a whole table.
Cache: a fast store of copies of answers already computed.
Cache-aside: check the cache; on a miss read the database and fill the cache.
Hit rate: the share of reads the cache answers.
TTL: how long a cached copy lives before it expires.
Invalidation: deleting a cached copy when the data changes.
CDN: caches of static files placed close to users.
Read replica: a copy of the database that serves reads.
Primary: the one database copy that takes writes.
Replication lag: how far a replica is behind the primary.
Sharding: splitting data across several databases.
Shard key: the value that decides which shard holds a row.
Strong consistency: every read sees the latest write.
Eventual consistency: copies may differ briefly, then converge.
CAP: during a network partition, choose consistency or availability.
PACELC: and otherwise, choose latency or consistency.

Step 3: slow work

Embedding: a list of numbers representing a text's meaning.
Message queue: a durable list of jobs between producers and workers.
Worker: a process that takes jobs off a queue and does them.
Asynchronous: the response does not wait for the work.
At-least-once delivery: no job is lost, so a job can run twice.
Idempotent: doing it twice has the same effect as once.
Dead-letter queue: where jobs that keep failing are set aside.
Backpressure: telling producers to slow down when consumers cannot keep up.
Little's law: items in a system = arrival rate × time each stays.

Step 4: failure

Timeout: a deadline after which a call is abandoned.
Retry: trying a failed call again.
Retry storm: retries that keep a struggling system overloaded.
Metastable failure: a failure that sustains itself after its trigger is gone.
Exponential backoff: waiting longer after each failed try.
Jitter: randomising the wait so clients do not retry in step.
Idempotency key: a client-chosen ID that lets the server recognise a retry.
Circuit breaker: stops calling a failing dependency for a while.
Load shedding: rejecting excess requests early to protect the rest.
Graceful degradation: a planned worse-but-working mode.
SLI: a measured indicator of service quality.
SLO: the target for an SLI.
SLA: a contract built on SLOs, with consequences.
Error budget: the failures an SLO allows; spent on change.
Observability: being able to see inside a running system.
Logs: a timestamped line per event.
Metrics: numbers over time.
Traces: one request followed across every service.

Step 5: the GPU layer

GPU: the processor models run on, with its own fast memory.
Token: a word or piece of a word; models read and write tokens.
Prefill: processing the whole prompt at once.
Decode: generating the reply one token per step.
Streaming: sending the reply token by token as it is generated.
Model replica: one running copy of a model, often over several GPUs.
Cold start: the time a new replica needs before it can serve.
KV cache: per-conversation results kept in GPU memory to avoid recomputation.
Batching: serving many conversations with one read of the weights.
Continuous batching: refilling a freed batch slot at every step.
Prefix caching: reusing the KV cache of a shared prompt beginning.
Semantic cache: reusing an answer for a similar-looking question.
Model router: sends each request to a small or large model.
Rate limit: a cap on what one user or tenant may send per minute.
Token bucket: a refilling allowance that permits bursts but caps the average.

Step 6: the method

Functional requirements: what the system does.
Non-functional requirements: how well: scale, speed, reliability, cost.
Back-of-the-envelope estimate: rough arithmetic that finds the hard part.
Autoscaling: adding and removing capacity automatically as traffic moves.

How the numbers are computed

Arrivals. Every daily active user sends 10 chat messages a day, and each message brings 4 other API calls (load the history, list chats, refresh the login). Traffic is not flat: the busiest hour runs at 2 times the daily average by default (the Traffic control changes it), and every tier except the queue is sized for that hour. So the message rate is users × 10 / 86,400 s × 2, written λ (lambda, arrivals per second). All three numbers are illustrative: your product's own logs replace them.

ρ = λ × S / c
ρ
utilisation (rho): the share of capacity in use. Capacity is c / S requests per second, so this is arrival rate divided by capacity.
λ
arrival rate at this component, requests per second
S
mean service time: how long one request keeps one server busy (5 ms of CPU for an API call, for example)
c
servers working in parallel: CPU cores of a machine, or batch slots of a GPU replica
L = λ × W
L
average number of requests inside the component (waiting or being served)
W
average time each spends inside

Little's law holds for any queue that is not growing, whatever the arrival pattern or service times (Little, 1961). The squares under each box are Lq = λ × Wq, the requests waiting; the GPU card uses it to find how many streams are being generated at once.

C(c, A) = (Ac/c!) · c/(c−A)Σk<c Ak/k! + (Ac/c!) · c/(c−A),  Wq = C / (c/S − λ)
A
offered load λ × S, in servers' worth of work
C
the Erlang C formula: the probability an arriving request finds all c servers busy and has to wait (computed with the stable recursion through Erlang B, so it works for a million GPU slots)
Wq
mean wait in the queue

Which queue model, and why it is an approximation. Each component is treated as M/M/c: in Kendall's notation, arrivals are random and independent (Poisson, the first M), service times are random with an exponential distribution (the second M), and there are c servers taking requests first come, first served. Waits then follow a known distribution (zero with probability 1 − C, otherwise exponential with rate c/S − λ), which gives the p50 and p99 directly; p50 is the median request, p99 the one slower than 99 in 100, the number users notice. Real systems break every assumption: arrivals come in bursts (a launch, a retry storm), a GPU reply's length is fixed once the request is known rather than exponential, a load balancer sends each request to one server instead of a shared line (each app server here is its own M/M/4), and components influence each other. The point of the model is the shape: wait time grows like 1/(1 − ρ), so going from 80% to 90% busy doubles the queueing, and 90% to 95% doubles it again.

One chat message, end to end. 20,000 sampled messages each pass through an app server, 3 reads (the cache, then the database on a miss), one write (saving the message), the GPU queue and the prefill (the time to read the prompt, which ends at the first token: TTFT, time to first token), then the reply is generated token by token. Times are server-side only: the user's network adds its own round trips. The sampler uses a fixed seed, so the same settings always show the same numbers.

The GPU replica. One replica is two H100 GPUs serving Llama 3.3 70B in FP8, the configuration NVIDIA benchmarks. Generation runs in steps: each step reads all the weights once and produces one token for every stream in the batch, so a step takes t(n) = a + b × n for n streams. a = 36.3 GB of weights per GPU / 3.35 TB/s = 10.8 ms (derived); b = 0.092 ms per stream (fitted so that at 1,000 input and 1,000 output tokens, with the largest batch memory allows, a replica makes 2 × 2,209 = 4,418 output tokens per second, NVIDIA's published maximum-load figure; reproduced by construction). The fitted b is within 3% of the compute one token needs at 40% of the GPU's FP8 peak (0.089 ms), which is why the fit is believable. Reading the prompt (prefill) costs 2 × 70.55 B × input tokens / (2 × 1,979 TFLOPS × 40%), 89 ms for 1,000 tokens. Each stream holds a KV cache (the model's memory of the conversation so far): 2 × 80 layers × 8 KV heads × 128 × 1 byte = 163,840 bytes per token, and 90% of what the weights leave free (2 × 80 GB − 72.7 GB) is 78.6 GB, so the batch can never exceed 78.6 GB / (163,840 × tokens per stream). The concurrency actually in use comes from Little's law (n = arrivals per replica × time per request at n). Batch slots are the GPU's c.

The database costs (1 ms of CPU per indexed read, 3 ms per write) are illustrative round numbers for a database server; measured latencies for PostgreSQL, Redis and disks are on Numbers to know.

How to read these numbers

Units. A nanosecond (ns) is a billionth of a second; a microsecond (µs) is a thousand ns; a millisecond (ms) is a thousand µs. A screen refresh takes about 16 ms; a blink about 100 ms. The span from a CPU cache to a model loading onto a GPU is eleven powers of ten, which is why the ladder below uses a logarithmic scale: each step to the right is ten times longer than the last, so 1 ns and 1 µs are as far apart as 1 ms and 1 s.

Latency and throughput. Latency is how long one thing takes; throughput is how many things finish per second. They are linked by Little's law: things in flight = throughput × latency. One database connection that waits 0.067 ms per query can do at most 1 / 0.067 ms ≈ 15,000 queries a second; to do more you need more in flight at once (more connections, or batching).

Percentiles. "p50" is the median: half of the requests were faster. "p99" means 99% were faster and 1% slower. Users notice the slow tail, so systems are judged on p99, not on the average.

How many requests one app server handles

Databases, caches and queues

GPUs: tokens per second

Two different numbers that are easy to confuse. Per-user speed is how fast one conversation's tokens arrive. GPU throughput is the total across every conversation the GPU serves at once: serving engines batch many requests together, so each weight read from memory produces a token for many users. Maximum-throughput figures run the GPU flat out, where each user's tokens arrive slowly; a chat product runs below that to keep replies quick.

Prices (on-demand, read 2026-10-04)

Availability arithmetic

Availability is the share of time (or of requests) a service works. It is quoted in "nines": 99.9% is three nines. Each extra nine divides the allowed downtime by ten.

Chains and replicas

If a request needs several components and each must work (in series), their availabilities multiply: five parts at 99.9% give 99.5%. If you run copies side by side and any one is enough (in parallel), the request fails only when all copies fail together: 1 − (1 − a)n. Both formulas assume failures are independent; copies in the same zone, on the same bad deploy, fail together, which is why the parallel number is an upper bound.

Error budgets

An SLO (service level objective) is the target you commit to, such as "99.9% of messages succeed over 30 days". The error budget is the rest: the failures you may spend on releases and experiments before you must stop and fix reliability.
