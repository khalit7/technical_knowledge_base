3. Logs: what happened, one event at a time

A log is a timestamped record of one event, written by the program as it runs. The beginner's version is a line of text: 2026-10-04 19:36:42 request failed for user7 after 1014ms. A human can read it; a machine has to guess where the user name ends. At 10 million messages a day (the parent root's estimate) nobody reads lines; you query them. So write structured logs: one JSON object per line, with named fields. Here is a real line from the demo, written by the incident's first failed request:

Every field can now be filtered and counted: level="ERROR" and route="/v1/chat", average duration_ms by status. Three fields do most of the work:

  • level, how serious the event is. Python's standard levels, in order: DEBUG (detail for developers, normally off in production), INFO (normal events worth keeping), WARNING (something unexpected that the program handled), ERROR (an operation failed), CRITICAL (the program itself is in trouble) ({{Python logging docs|https://docs.python.org/3/library/logging.html#logging-levels}}). Production usually runs at INFO. A DEBUG call that is switched off costs almost nothing: we measured 0.14 microseconds, against 17 for a JSON line actually written (Profiling).
  • request_id, a random ID given to each request at the edge and returned to the client in an X-Request-Id header (a common convention, not a standard), so a user's support ticket can be matched to your logs.
  • trace_id and span_id, the IDs of the trace this event belongs to. This is the field that ties the three signals together: from a slow trace you jump to exactly its log lines, in every service. Our JsonFormatter reads them from the current OpenTelemetry span, so no handler code has to pass them around.

What never to log

Logs are copied to many places (agents, storage, backups, laptops during an incident) and readable by many people, so a secret in a log is a leaked secret. OWASP's logging cheat sheet lists what "should usually not be recorded directly in the logs, but instead should be removed, masked, sanitized, hashed, or encrypted", including "Session identification values", "Access tokens", "Authentication passwords", "Database connection strings", "Encryption keys and other primary secrets", "Bank account or payment card holder data" and sensitive personal data; it adds that even "non sensitive personal data (e.g. personal names, telephone numbers, email addresses)" may need special treatment ({{OWASP Logging Cheat Sheet|https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html}}). For the chat product that means: never log prompts or replies by default (they are customer data, see the sibling {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}} section 12 on retention), API keys, or bearer tokens.

What reached the log file

Our demo deliberately passes the user's email and the Authorization header to the logger, and a redaction filter in the formatter masks them (real output above). Treat such a filter as a seatbelt, not as the plan: the plan is not to pass secrets to the logger at all, because a filter only catches the patterns it knows.

From the program to a place you can search

The modern pipeline: the program writes JSON lines to standard output; an agent on each machine (Fluent Bit, Vector, or the OpenTelemetry Collector) reads them, adds fields such as the host and the Kubernetes pod, and ships them to a store. Stores differ in what they index (build a lookup structure for, so a search is fast):

  • Full-text index (Elasticsearch, OpenSearch, Datadog's indexed logs): any word in any line is searchable in milliseconds; you pay for the index, per gigabyte or per line.
  • Labels only (Grafana Loki): "Loki does not index the contents of the logs, but only indexes metadata about your logs as a set of labels for each log stream" ({{Loki overview|https://grafana.com/docs/loki/latest/get-started/overview/}}). A search scans the compressed lines of the matching streams. Much cheaper to store, slower to search across everything.
What logs cost, worked for the chat product

Measured: chat-api's lines average bytes, retrieval's ; one message makes one line in each. At 10 million messages a day that is GB a day, GB per 30 days. At Datadog's list prices on 2026-10-04 (annual billing: $0.10 per ingested GB, and $1.70 per million log events indexed with 15-day retention, {{Datadog pricing|https://www.datadoghq.com/pricing/}}), ingesting costs about a month but indexing lines costs about . The count of lines, not their size, drives the bill. Turn on DEBUG at 20 lines per request (illustrative) and the indexing line becomes ten times larger. The usual answers: index only WARNING and above, keep INFO in cheap archive storage, sample repetitive success lines, and use metrics instead of logs for counting.
