2. Logs: what happened, one event at a time

A log is a timestamped record of one event. A line of text such as 2026-10-04 19:36:42 request failed for user7 after 1014ms reads well, but a machine has to guess where the user name ends, and at 10 million messages a day (the parent root's estimate) nobody reads lines; you query them. Now level="ERROR" and route="/v1/chat" is a filter and the average duration_ms by status is a query. Three fields do most of the work:

  • level: Python's standard levels, in order, are DEBUG, INFO, WARNING, ERROR, CRITICAL ({{Python logging docs|https://docs.python.org/3/library/logging.html#logging-levels}}); production usually runs at INFO. A DEBUG call that is switched off costs almost nothing: we measured 0.14 microseconds, against 17 for a JSON line actually written.
  • request_id: a random ID given at the edge and returned to the client in an X-Request-Id header (a common convention, not a standard), so a support ticket can be matched to your logs.
  • trace_id and span_id: the trace this event belongs to, the field that ties the three signals together. Our JsonFormatter reads them from the current OpenTelemetry span, so no handler code passes them around.

What never to log

Logs are copied to agents, storage, backups and laptops, and read by many people, so a secret in a log is a leaked secret. OWASP lists what "should usually not be recorded directly in the logs, but instead should be removed, masked, sanitized, hashed, or encrypted": session identifiers, access tokens, passwords, database connection strings, encryption keys, payment card data and sensitive personal data ({{OWASP Logging Cheat Sheet|https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html}}). For the chat product: never log prompts or replies by default (customer data; retention is on {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}} section 7), API keys or bearer tokens. Where logs go, and what they cost

The program writes JSON lines to standard output; an agent on each machine (Fluent Bit, Vector or the OpenTelemetry Collector) adds the host and pod and ships them to a store. A full-text index (Elasticsearch, OpenSearch, Datadog's indexed logs) makes any word searchable in milliseconds and charges for the index; labels only (Grafana Loki: "Loki does not index the contents of the logs, but only indexes metadata about your logs as a set of labels for each log stream", {{Loki overview|https://grafana.com/docs/loki/latest/get-started/overview/}}) scans compressed lines at query time: cheaper to keep, slower to search widely.

The count of lines, not their size, drives the bill

Measured: chat-api's lines average bytes, retrieval's ; one message makes one line in each. At 10 million messages a day that is GB a day, GB per 30 days. At Datadog's list prices on 2026-10-04 ($0.10 per ingested GB and $1.70 per million log events indexed with 15-day retention, annual billing, {{Datadog pricing|https://www.datadoghq.com/pricing/}}), ingesting costs about a month but indexing lines costs about . DEBUG at 20 lines per request (illustrative) makes the indexing line ten times larger. The usual answers: index only WARNING and above, keep INFO in cheap archive storage, sample repetitive success lines, and count with metrics, not logs.
