4. Metrics: numbers over time

A metric is a number your program keeps up to date in memory, such as "requests handled so far". A monitoring system reads it every few seconds and stores each reading with its time, giving a time series: a list of (time, value) pairs. Because the program only updates a number per request (we measured 0.8 to 1 microsecond per update), metrics are the cheapest way to see all requests, at any traffic.

This page uses Prometheus, the open-source metrics system most teams start with. It pulls: each program serves its current numbers as text at /metrics, and Prometheus fetches ("scrapes") that page on a timer (the configuration default is 1 minute, {{Prometheus configuration|https://prometheus.io/docs/prometheus/latest/configuration/configuration/}}; the demo used 1 second). Why averages lie, and how percentiles come out of a histogram

Latency (how long one request takes) varies from request to request, so a single number must summarise a distribution. The average (mean) is the obvious choice and a bad one. A percentile is better: the p99 is the latency that 99% of requests beat, so it describes the slowest 1 in 100; the p50 (median) describes the typical request. The SRE book's warning: "If you run a web service with an average latency of 100 ms at 1,000 requests per second, 1% of requests might easily take 5 seconds" ({{SRE book, ch. 6|https://sre.google/sre-book/monitoring-distributed-systems/}}). The average moved by about a third: enough to notice, wrong about what happened. It suggests every user got a bit slower. The truth is that the median barely moved while the slowest requests became about 2.5 times slower: most users saw nothing, some saw a reply take a second longer, and about 2% got an error (12 requests over the whole incident). One request's journey through several such services makes it worse: "the 99th percentile of one backend can easily become the median response of your frontend" (SRE book), because a page that calls 100 backends almost always hits one slow one.

How Prometheus gets a percentile from buckets

Prometheus never sees individual requests, only bucket counts, so it estimates. histogram_quantile(0.99, ...) computes the rank (0.99 times the total count), finds the bucket that contains that rank, and assumes the requests inside the bucket are spread evenly between its lower and upper bound (linear interpolation, {{PromQL functions|https://prometheus.io/docs/prometheus/latest/querying/functions/}}). Move the slider; the bars are the real bucket counts from the incident's last minute.

The error is bounded by the bucket's width: "Error is limited by the width of the bucket the quantile is located in" ({{Prometheus histograms|https://prometheus.io/docs/practices/histograms/}}). So choose buckets around the numbers you care about: if your target is "first token within 2 s", have a bucket boundary at 2. The SRE book suggests boundaries roughly a factor of 3 apart (10 ms, 30 ms, 100 ms, 300 ms...). The newer fix is the native histogram: exponentially spaced buckets chosen automatically at high resolution and stored as one series. They were experimental from Prometheus 2.40 (November 2022) and are "supported as a stable feature" from v3.8.0, though scraping them must still be switched on with scrape_native_histograms ({{native histograms spec|https://prometheus.io/docs/specs/native_histograms/}}). OpenTelemetry's equivalent is the exponential histogram.

PromQL: asking questions of metrics

PromQL is Prometheus's query language. Four pieces cover most daily use: a selector picks series by name and labels (http_requests_total{job="chat-api",status=~"5.."}, where =~ is a regular-expression match), a range in square brackets takes the last N seconds of samples ([1m]), rate() turns a counter's samples into a per-second rate, and sum by (label) adds series together, keeping only the labels named. Cardinality: why one label can cost a fortune

Cardinality is the number of distinct time series. Prometheus's own warning: "every unique combination of key-value label pairs represents a new time series, which can dramatically increase the amount of data stored. Do not use labels to store dimensions with high cardinality (many different label values), such as user IDs, email addresses, or other unbounded sets of values" ({{Prometheus naming|https://prometheus.io/docs/practices/naming/}}). The multiplication is easy to underestimate, because a histogram is already many series per combination. Try adding a tenant label:

series = (buckets + 2) × routes × status codes × instances × extra label values, for one latency histogram (the +2 are _sum and _count). Samples per second = series / 15 s scrape interval. Disk = samples × 86,400 × 1.5 bytes, the middle of Prometheus's "an average of only 1-2 bytes per sample" ({{Prometheus storage|https://prometheus.io/docs/prometheus/latest/storage/}}); memory and query cost grow with series too. Not every combination occurs in practice, so read these as upper bounds.

The rule of thumb that follows: labels for things with a few, known values (route template, status class, region, model name); high-cardinality detail (user, tenant, request ID, prompt length) goes into traces and logs, which are priced per event, not per combination. Honeycomb's pitch is the other side of this trade: their event store is built for high-cardinality fields, which "pinpoint the specific components, transactions, or users affected" ({{Honeycomb|https://www.honeycomb.io/what-is-observability}}). One subtle trap: use the route template (/v1/chats/{id}), never the raw path, as a label; OpenTelemetry's HTTP conventions require http.route to "be low-cardinality" for this reason ({{OTel HTTP spans|https://opentelemetry.io/docs/specs/semconv/http/http-spans/}}).

Two details from the SRE book that beginners miss. Track the latency of errors separately: a fast 500 pulls the average down, while "a slow error is even worse than a fast error". And count implicit errors: a 200 response "coupled with the wrong content", or a reply slower than your promise, is an error to the user. For an LLM product that last point is large (wrong answers with status 200); the sibling {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}} section 12 covers quality signals.
