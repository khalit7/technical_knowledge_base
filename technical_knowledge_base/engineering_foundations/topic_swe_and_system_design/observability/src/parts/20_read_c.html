3. Metrics: numbers over time

A metric is a number the program keeps up to date in memory ("requests handled so far"). A monitoring system reads it every few seconds and stores each reading, giving a time series of (time, value) pairs. The program only updates a number per request (we measured 0.8 to 1 microsecond per update), so metrics are the cheapest way to see all requests at any traffic. Prometheus, the open-source system most teams start with, pulls: each program serves its numbers as text at /metrics, and Prometheus scrapes that page on a timer (default 1 minute, {{Prometheus configuration|https://prometheus.io/docs/prometheus/latest/configuration/configuration/}}; the demo used 1 second). 4. Percentiles: why averages, and averaged percentiles, lie

Latency varies from request to request, so one number must summarise a distribution. A percentile does it honestly: p99 is the latency 99% of requests beat (the slowest 1 in 100), p50 the median. The average does not: "If you run a web service with an average latency of 100 ms at 1,000 requests per second, 1% of requests might easily take 5 seconds" ({{SRE book, ch. 6|https://sre.google/sre-book/monitoring-distributed-systems/}}). Predict: in our incident, 15% of retrieval calls became 900 ms slower. How much did the median move? Then toggle (exact values from the load generator's record of every request, last 60 seconds of each phase):

The average rose by about a third and suggests every user got a bit slower. In fact the median barely moved while the slowest requests became about 2.5 times slower: most users saw nothing, some waited a second longer, and about 2% got an error (12 requests over the whole incident). Fan-out makes the tail matter more: "the 99th percentile of one backend can easily become the median response of your frontend" (SRE book), because a page that calls 100 backends almost always hits one slow one.

Averaging percentiles is the second trap

A dashboard that shows the fleet's p99 as the mean of each server's p99 reports a number no request had. Real case: the three retrieval replicas during the incident.

Mean of the three p99s: 527.2 ms, a latency no lookup was near (r1 and r2 under 37 ms, r3-cold all over 500 ms). The true p99 of all 701 lookups is at least 909.7 ms: the slowest 1% (8 lookups) all came from r3-cold, whose median alone is 909.7 ms. Derived in src/avgpct.py from the replica statistics; per-lookup times were not kept, so the pooled value is a bound.

The fix is to combine the raw counts, then take the percentile: sum the histogram buckets across servers (sum by (le)), then histogram_quantile. That is why histograms beat summaries: a summary has only the per-server percentiles left.

How Prometheus gets a percentile from buckets

Prometheus never sees individual requests, only bucket counts. histogram_quantile(0.99, ...) computes the rank (0.99 times the total count), finds the bucket holding that rank, and assumes the requests inside it are spread evenly between its bounds (linear interpolation, {{PromQL functions|https://prometheus.io/docs/prometheus/latest/querying/functions/}}). The bars are the real bucket counts from the incident's last minute; move the slider.

At φ = 0.99 the estimate is 1.4619 s, exactly Prometheus's own answer, against an exact 1.306 s. "Error is limited by the width of the bucket the quantile is located in" ({{Prometheus histograms|https://prometheus.io/docs/practices/histograms/}}), so put bucket boundaries at the numbers you care about: if the target is "first token within 2 s", have a boundary at 2. The SRE book suggests boundaries roughly a factor of 3 apart (10 ms, 30 ms, 100 ms, 300 ms). The newer fix is the native histogram: exponentially spaced buckets chosen automatically at high resolution and stored as one series; OpenTelemetry's equivalent is the exponential histogram.

Native histograms: history and status (under 1 min)

Experimental from Prometheus 2.40 (November 2022) and "supported as a stable feature" from v3.8.0, though scraping them must still be switched on with scrape_native_histograms ({{native histograms spec|https://prometheus.io/docs/specs/native_histograms/}}).

5. PromQL: asking questions of metrics

Four pieces cover most daily use: a selector picks series by name and labels (http_requests_total{job="chat-api",status=~"5.."}, =~ being a regular-expression match), a range takes the last N seconds of samples ([1m]), rate() turns a counter into a per-second rate, and sum by (label) adds series, keeping only the labels named. 6. Cardinality: why one label can cost a fortune

Cardinality is the number of distinct time series. Prometheus: "every unique combination of key-value label pairs represents a new time series, which can dramatically increase the amount of data stored. Do not use labels to store dimensions with high cardinality (many different label values), such as user IDs, email addresses, or other unbounded sets of values" ({{Prometheus naming|https://prometheus.io/docs/practices/naming/}}). The multiplication is easy to underestimate, because a histogram is already many series per combination. Predict the series count for one latency histogram once you add a tenant label, then press it:

series = (buckets + 2) × routes × status codes × instances × extra label values (the +2 are _sum and _count); defaults give 2,400. Samples per second = series / 15 s scrape interval. Disk = samples × 86,400 × 1.5 bytes, the middle of Prometheus's "an average of only 1-2 bytes per sample" ({{Prometheus storage|https://prometheus.io/docs/prometheus/latest/storage/}}). Not every combination occurs, so these are upper bounds.

The rule that follows: labels for things with a few known values (route template, status class, region, model name); high-cardinality detail (user, tenant, request ID, prompt length) goes on spans and log lines, which are priced per event, not per combination. Honeycomb's event store is built for that side of the trade: high-cardinality fields "pinpoint the specific components, transactions, or users affected" ({{Honeycomb|https://www.honeycomb.io/what-is-observability}}). Use the route template (/v1/chats/{id}), never the raw path; OpenTelemetry's HTTP conventions require http.route to "be low-cardinality" ({{OTel HTTP spans|https://opentelemetry.io/docs/specs/semconv/http/http-spans/}}).
