The idea in one sentence. Count every request into a histogram (metrics), follow a sample of requests across services (traces), write one structured line per event (logs), tie the three together with one trace ID, and page a human only when users' error budget is burning fast.

It is one count in the 1.0 to 1.5 s bucket of the latency histogram (about 63 of that minute's 481 requests). Cheap enough to record every request; the ringed dot is an exemplar, its trace ID kept with the bucket.
Cost: per time series (name × label values).
Traces: where this request's time went

The join: the same trace ID sits in the exemplar, in every span and in every log line, so a spike on a graph leads to a trace, and a trace to its logs. The alert sits on the metrics: the share of failing requests divided by the error budget (the burn rate) pages a human when it is high enough to matter (section 15).

1. Monitoring, observability, and the running example

Monitoring answers questions decided in advance: is the error rate above 1%, is the disk 90% full? Google's SRE book defines it as "collecting, processing, aggregating, and displaying real-time quantitative data about a system, such as query counts and types, error counts and types, processing times, and server lifetimes" ({{SRE book, ch. 6|https://sre.google/sre-book/monitoring-distributed-systems/}}). Production keeps producing failures nobody predicted (one replica with a cold cache, one tenant whose documents are huge), and for those you need observability: "the ability to investigate a system by asking any question about its behavior without needing to predict those questions in advance" ({{Honeycomb, What is observability|https://www.honeycomb.io/what-is-observability}}): slice requests by any field, follow one request across services, without new code and a redeploy first.

Monitoring: the known failures

Fixed questions: dashboards and alert rules over a few metrics. Cheap, fast, reliable. Tells you that something is wrong.

Observability: the unknown ones

Open questions, asked after the fact, by route, tenant, replica, model version. Tells you where and why. Costs more data.

A second line from the SRE book runs through this page. Black-box monitoring is "testing externally visible behavior as a user would see it": it shows symptoms happening now. White-box monitoring is "based on metrics exposed by the internals of the system, including logs": it shows causes, and can warn before users notice. Page humans on the first; debug with the second (section 15).

The running example, instrumented for real. The parent topic's chat assistant, built small on a laptop and broken on purpose on 2026-10-04 (code in src/demo/):

load generator4 clients in a loop, about 10 requests a second
→
chat-api (port 8701) auth, load history (real SQLite), call retrieval, model call (simulated: a sleep), save
→
retrieval (port 8702) a separate process; normally about 15 ms
Prometheus 3.15.0 scrapes /metrics on both every second
OpenTelemetry SDK 1.45.0 writes every span to a file
JSON log lines carry the trace ID

The incident. 90 seconds normal, 90 seconds of incident, 45 seconds of recovery. During the incident one retrieval replica went cold: 15% of retrieval calls took 900 ms and 2% hung for 1.5 s, past chat-api's 1-second timeout, so those requests failed with HTTP 503. The model call and the database were unchanged. One dependency, some of the time, for some users: the classic shape of a real slowdown, debugged twice in section 13. The incident shape is chosen; its numbers are measured. All of it is browsable in the {{Real telemetry|#t-real}} tab.

Versions, the cost of the second data system, and three real outages (1 min)

Versions: Python 3.12.11, opentelemetry-sdk 1.45.0 (released 2026-09-25), prometheus-client 0.26.0 (2026-07-24), Prometheus 3.15.0 (2026-09-25). The word observability comes from control theory, where a system is observable if its internal state can be worked out from its outputs.

Observability is a second data system beside your product: code to emit the data (about 96 microseconds of CPU per request in our measurement, section 12), pipelines, storage and people. The SRE book notes that a Google SRE team of 10 to 12 "typically has one or sometimes two members whose primary assignment is to build and maintain monitoring systems".

Three outages from the parent root's {{Case files tab|n:3c65c17b0d0d81048ae0dd14ac399b4d}}: "73 hours down: the service directory everything depends on choked" (Roblox, 2021: the monitoring depended on the system that failed, so keep it outside); "A monitoring tool overloaded the cluster brains, and DNS went with them" (OpenAI, December 2024: a new telemetry agent on every node made expensive Kubernetes API calls that overloaded the control plane); and "Three serving bugs quietly made Claude's answers worse" (Anthropic, 2025), a failure no error counter sees.
