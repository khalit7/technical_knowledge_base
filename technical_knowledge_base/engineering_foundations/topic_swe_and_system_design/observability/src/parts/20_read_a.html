In one screen

Our running example is the parent topic's chat assistant. A user sends a message; chat-api (the program we run) loads the conversation history from a database, asks a retrieval service for relevant documents, calls a model, saves the reply and answers. One day replies get slower for some users. Observability is whatever lets you answer "what is wrong, for whom, and where" from the outside, without adding new code and redeploying first. It rests on a few kinds of recorded data, called signals:

The five ideas that matter most
  1. Percentiles, not averages. In our real run the average latency rose 37% while 85% of requests were unchanged and the slowest 1% got 2.5 times slower (Percentiles).
  2. One ID through everything. Put the trace ID in every log line and pass it in the traceparent header to every service you call; then a metric spike leads to a trace, and a trace to its logs (traceparent).
  3. Labels are a budget. Every distinct label combination is a new time series; a user ID in a label can multiply your bill by a million (Cardinality).
  4. Page on symptoms users feel, measured against an SLO, using burn-rate alerts; investigate causes with dashboards and traces (Alerting; try the {{Alert lab|#t-alab}}).
  5. Instrument with OpenTelemetry so the data is vendor-neutral, then choose storage by cost (OpenTelemetry, Tools and cost).

1. Why observability: known failures and unknown ones

Start from what you already know. When you served a model behind an API, you probably watched whether it was up and how long requests took. That is monitoring, which Google's SRE book defines as "collecting, processing, aggregating, and displaying real-time quantitative data about a system, such as query counts and types, error counts and types, processing times, and server lifetimes" ({{SRE book, ch. 6|https://sre.google/sre-book/monitoring-distributed-systems/}}). Monitoring answers questions you thought of in advance: is the error rate above 1%? Is the disk 90% full?

Production keeps producing failures nobody predicted: one replica with a cold cache, one tenant whose documents are huge, one client library that retries too fast. For those you need to ask new questions of data you already have. Honeycomb, whose founders popularised the term in software, puts it this way: "Observability is the ability to investigate a system by asking any question about its behavior without needing to predict those questions in advance" ({{Honeycomb, What is observability|https://www.honeycomb.io/what-is-observability}}). The word comes from control theory, where a system is observable if its internal state can be worked out from its outputs.

Monitoring: the known failures

Fixed questions, decided in advance: dashboards and alert rules over a few metrics. Cheap, fast, reliable. Tells you that something is wrong.

Observability: the unknown ones

Open questions, asked after the fact: slice requests by any field (route, tenant, replica, model version), follow one request across services. Tells you where and why. Costs more data.

The SRE book draws a second line that this page uses throughout. Black-box monitoring is "testing externally visible behavior as a user would see it"; white-box monitoring is "based on metrics exposed by the internals of the system, including logs" and HTTP endpoints. Black-box tells you users are hurting now; white-box tells you why, and can warn before users notice. Both books say to page humans on the first and debug with the second (Alerting).

What it costs

Observability is a second data system beside your product: code to emit the data (about 96 microseconds of CPU per request in our real measurement, Profiling), pipelines to move it, storage to keep it, and people to look at it. The SRE book notes that a Google SRE team of 10 to 12 "typically has one or sometimes two members whose primary assignment is to build and maintain monitoring systems". The money side is in Tools and cost.

Two real outages where observability itself was the problem (from the parent root's {{Case files tab|n:3c65c17b0d0d81048ae0dd14ac399b4d}}): "73 hours down: the service directory everything depends on choked" (Roblox, 2021: the monitoring depended on the system that failed, so keep it outside) and "A monitoring tool overloaded the cluster brains, and DNS went with them" (OpenAI, December 2024: a new telemetry agent on every node made expensive Kubernetes API calls that overloaded the control plane). A third, "Three serving bugs quietly made Claude's answers worse" (Anthropic, 2025), shows a failure no error counter sees.
