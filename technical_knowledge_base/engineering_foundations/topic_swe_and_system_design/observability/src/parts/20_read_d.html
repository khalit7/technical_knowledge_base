5. Traces: one request, followed everywhere

Metrics say the slowest requests got slower; they cannot say where the time went. A trace can. It records one request's whole journey as a tree of spans. A span is one timed operation: a name ("load history"), a start time and duration, the ID of its parent span (the operation that called it), attributes (key-value details such as http.route or db.system.name), events (timestamped notes inside it, such as an exception), and a status (unset, OK or error). Each span also has a kind: SERVER for handling an incoming request, CLIENT for an outgoing call, INTERNAL for work inside one service. Here is a real, typical trace from the normal phase, drawn as a waterfall (one row per span, bars on a shared time axis; click a row for its details):

Two things to notice. The GET /search span comes from a different process (retrieval) yet sits inside chat-api's tree, because the two processes passed the trace's identity between them. And the model call dominates: in this demo, as in a real LLM product, a normal request is mostly waiting for the model. Instrumentation is a few lines per operation (real code from src/demo/api.py):

# once, at start-up: who we are, and where finished spans go provider = TracerProvider(resource=Resource.create({"service.name": "chat-api"})) provider.add_span_processor(BatchSpanProcessor(exporter)) # sends spans in the background trace.set_tracer_provider(provider) tracer = trace.get_tracer("chat-api") # per request with tracer.start_as_current_span("POST /v1/chat", kind=SpanKind.SERVER, attributes={"http.route": "/v1/chat"}) as sp: with tracer.start_as_current_span("load history"): # child: parent is set automatically rows = db().execute(...) with tracer.start_as_current_span("GET retrieval /search", kind=SpanKind.CLIENT): headers = {} inject(headers) # writes the traceparent header urllib.request.urlopen(Request(url, headers=headers), timeout=1.0)

Context propagation: the traceparent header, byte by byte

Context propagation is how the trace's identity crosses a network call. The caller writes it into a header; the callee reads it and makes its spans children of the caller's span. The format is a W3C standard, Trace Context: a W3C Recommendation since February 2020, edited in November 2021 ({{W3C Trace Context|https://www.w3.org/TR/trace-context/}}), with a Level 2 draft adding a "random" flag ({{Trace Context Level 2, Candidate Recommendation Draft, 28 March 2024|https://www.w3.org/TR/trace-context-2/}}). This is the real header chat-api sent to retrieval on the incident's first failed request. Click each part:

Rules worth knowing from the spec: IDs are lowercase hex, an all-zero trace ID or parent ID is invalid and the header "MUST" then be ignored, and "Vendors MUST expect the header name in any case (upper, lower, mixed), and SHOULD send the header name in lowercase." That last rule bit this page's demo: Python's urllib sent the header as Traceparent, the receiving code looked it up case-sensitively, missed it, and every retrieval span silently started a new trace. Nothing errored; the traces were just broken in two. The fix was one line (lower-case the header names before extract); the lesson is to check that a cross-service trace actually joins up before you need it. A companion header, tracestate, carries vendor-specific data; baggage (a separate W3C header) carries your own key-value pairs, such as a tenant ID, to every downstream service.

Propagation also crosses queues: put traceparent in the message's headers when you publish and extract it in the consumer, so an async job joins the trace of the request that created it (see the sibling {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}). For LLM agents, a trace per conversation turn with a span per model and tool call is how agent runs are evaluated; that use is on {{Agent and trajectory evaluation|n:3ef5c17b0d0d81fdbabaf3582bff37f2}}.

Sampling: which traces to keep

Every request produces a trace of about eight spans in our demo; at 10 million messages a day that is 80 million spans a day, most of them boring. Sampling keeps a subset. Two places to decide (definitions from {{OpenTelemetry sampling|https://opentelemetry.io/docs/concepts/sampling/}}):

  • Head sampling decides at the start of the trace, usually from the trace ID ("keep 10%"), and passes the decision downstream in the traceparent flags so every service agrees. Cheap and stateless. Its weakness: "you cannot ensure that all traces with an error within them are sampled with head sampling alone", because nobody knows yet whether this request will fail or be slow.
  • Tail sampling decides after the trace is complete, "by considering all or most of the spans within the trace": keep every error, every slow trace, and a small share of the rest. Its costs: it is stateful (spans wait in memory, 30 seconds by default), and "All spans for a given trace MUST be received by the same collector instance" ({{tail sampling processor README at 9056197|https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/9056197f9bf1320dc8d15bf0c6eb631d7f71dbbc/processor/tailsamplingprocessor/README.md}}), so at scale a load-balancing layer routes by trace ID in front of the samplers.

Remember what sampling does to counting: if you keep 5% of normal traces, you cannot count requests from traces. Count with metrics (computed before sampling) and explain with traces.

6. OpenTelemetry: one standard for all of it

OpenTelemetry (OTel) is the open, vendor-neutral standard for producing telemetry, a Cloud Native Computing Foundation project born from the merger of two earlier projects, OpenTracing and OpenCensus ({{What is OpenTelemetry|https://opentelemetry.io/docs/what-is-opentelemetry/}}). You instrument your code once against its API, and send the data to any backend (Prometheus, Tempo, Jaeger, Datadog, Honeycomb and most others accept it). Its parts:

Maturity differs by signal and language, so check before you rely on it. OpenTelemetry's status page lists Python as Stable for traces and metrics and "Development" for logs; Go logs are a release candidate; Java is Stable for all three ({{OTel status|https://opentelemetry.io/status/}}, fetched 2026-10-04). That is why this demo wrote logs through Python's standard logging with the trace ID added, which is what most Python teams do today; the collector can still ingest those lines. Profiles became a fourth OTel signal in public alpha on 2026-03-26 (next section). For model calls, the GenAI conventions (status "Development") are covered in the sibling {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}} section 12.

Why the collector is worth running

Without it each service talks to the backend directly, so changing vendors, adding redaction or adding tail sampling means changing every service. With it, services send OTLP to localhost and the pipeline is one config file. Put memory_limiter first in every pipeline so an overloaded collector refuses data instead of crashing, and remember that the collector is now part of your production path: monitor it (it exports its own metrics) and keep it outside the systems it watches (the Roblox lesson).

7. Profiling: the fourth signal

Traces say which operation was slow; when that operation is your own code burning CPU, you need to know which function. A profiler answers by sampling: many times a second it records the stack (the chain of functions currently running), then counts how often each function appears. A flame graph draws the result: "The x-axis shows the stack profile population, sorted alphabetically (it is not the passage of time), and the y-axis shows stack depth... The wider a frame is, the more often it was present in the stacks" ({{Brendan Gregg, Flame Graphs|https://www.brendangregg.com/flamegraphs.html}}). Continuous profiling runs a low-overhead sampler on every production process all the time; Google described doing so fleet-wide in 2010 "with negligible overhead" ({{Google-Wide Profiling, IEEE Micro 2010|https://research.google/pubs/google-wide-profiling-a-continuous-profiling-infrastructure-for-data-centers/}}). Tools in 2026: Grafana Pyroscope, Parca, Datadog's profiler, and OpenTelemetry Profiles, which entered public alpha on 2026-03-26 with an eBPF-based reference profiler ({{OTel blog|https://opentelemetry.io/blog/2026/profiles-alpha/}}).

A real example, and an answer to "what does all this telemetry cost my service?". We timed each kind of telemetry call as the demo makes it, then profiled a loop emitting one request's worth (six spans, two histogram observations, one counter, one JSON log line) with a 30-line sampling profiler of exactly the kind described above (stacks read every millisecond):

Reading it: about 96 microseconds of CPU per request in Python, against a request of about 320 ms, is 0.03%: negligible for this service. The flame graph shows where it goes: span creation and the JSON log line, not the metrics. At 10,000 requests a second on one machine the same cost is about one CPU core, which is when teams sample traces, drop INFO logs on hot paths, or move work to the collector.
