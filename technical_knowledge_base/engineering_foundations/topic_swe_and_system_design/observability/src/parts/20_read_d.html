8. Traces: one request, followed everywhere

Metrics say the slowest requests got slower; they cannot say where the time went. A trace can: it records one request's journey as a tree of spans. A span is one timed operation with a name ("load history"), a start and duration, the ID of its parent span, attributes (http.route, db.system.name), events (timestamped notes such as an exception), a status (unset, OK or error) and a kind (SERVER for an incoming request, CLIENT for an outgoing call, INTERNAL for work inside one service). The GET /search span comes from a different process (retrieval) yet sits inside chat-api's tree, because the two processes passed the trace's identity between them (next section). And the model call dominates: a normal request is mostly waiting for the model. Instrumentation is a few lines per operation (real code from src/demo/api.py):

9. Context propagation: the traceparent header, byte by byte

Context propagation carries the trace's identity across a network call: the caller writes it into a header, the callee reads it and makes its spans children of the caller's span. The format is the W3C Trace Context standard, a Recommendation since February 2020, edited November 2021 ({{W3C Trace Context|https://www.w3.org/TR/trace-context/}}), with a Level 2 draft adding a "random" flag ({{Trace Context Level 2, Candidate Recommendation Draft, 28 March 2024|https://www.w3.org/TR/trace-context-2/}}). The real header chat-api sent to retrieval on the incident's first failed request; click each part:

From the spec: IDs are lowercase hex; an all-zero trace ID or parent ID is invalid and the header "MUST" then be ignored; and "Vendors MUST expect the header name in any case (upper, lower, mixed), and SHOULD send the header name in lowercase." That last rule bit this page's demo: Python's urllib sent the header as Traceparent, the receiving code looked it up case-sensitively, missed it, and every retrieval span silently started a new trace. Nothing errored; the traces were just broken in two. The fix was one line (lower-case the header names before extract); the lesson is to check that a cross-service trace actually joins up before you need it. A companion header, tracestate, carries vendor-specific data; baggage (a separate W3C header) carries your own key-value pairs, such as a tenant ID, downstream.

Propagation also crosses queues: put traceparent in the message headers when you publish and extract it in the consumer, so an async job joins the trace of the request that created it (sibling {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}). A trace per agent turn, with a span per model and tool call, is how agent runs are evaluated: {{Agent and trajectory evaluation|n:3ef5c17b0d0d81fdbabaf3582bff37f2}}.

10. Sampling and exemplars: which traces to keep, and how to find them

About eight spans per request in our demo; at 10 million messages a day, 80 million spans a day, most of them boring. Sampling keeps a subset ({{OpenTelemetry sampling|https://opentelemetry.io/docs/concepts/sampling/}}):

  • Head sampling decides at the start, usually from the trace ID ("keep 10%"), and passes the decision downstream in the traceparent flags so every service agrees. Cheap and stateless, but "you cannot ensure that all traces with an error within them are sampled with head sampling alone": nobody knows yet whether this request will fail or be slow.
  • Tail sampling decides after the trace completes, "by considering all or most of the spans within the trace": keep every error, every slow trace, a small share of the rest. It is stateful (spans wait in memory, 30 seconds by default), and "All spans for a given trace MUST be received by the same collector instance" ({{tail sampling processor README at 9056197|https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/9056197f9bf1320dc8d15bf0c6eb631d7f71dbbc/processor/tailsamplingprocessor/README.md}}), so at scale a load-balancing layer routes by trace ID in front of the samplers.

Both, replayed on the real incident phase's 657 trace IDs (head: OpenTelemetry's trace-ID-ratio rule at 10%; tail: keep errors, keep anything over 1 s, plus 5% of the rest). At 10% head sampling the run kept 8 of the 90 traces you would want:

Count with metrics (computed before sampling) and explain with traces: if you keep 5% of normal traces you cannot count requests from them. The collector configuration for this tail policy is in the {{Real telemetry|#t-real}} tab; it passes otelcol-contrib validate (version 0.162.0), and the processor's stability is "beta" for traces.

An exemplar is a trace ID attached to one histogram observation, so a dot on a latency graph links to a real request that landed in that bucket (the ringed dot in the figure at the top). Our chat-api attached one to every observation; in the OpenMetrics text format they follow a # (real lines):

11. OpenTelemetry: one standard for producing all of it

OpenTelemetry (OTel) is the open, vendor-neutral standard for producing telemetry, a Cloud Native Computing Foundation project born from the merger of OpenTracing and OpenCensus ({{What is OpenTelemetry|https://opentelemetry.io/docs/what-is-opentelemetry/}}). You instrument once against its API and send the data to any backend (Prometheus, Tempo, Jaeger, Datadog, Honeycomb and most others accept it). The path, drawn from the collector configuration this page validated:

Services call the API; the SDK samples, batches and exports over OTLP (gRPC on port 4317, HTTP on 4318) to a Collector, which receives, processes (memory_limiter first, so an overloaded collector refuses data instead of crashing; tail_sampling for traces, batch) and exports each signal to its store. Change vendors, add redaction or tail sampling in one config file instead of in every service.

12. Profiling: the fourth signal

When the slow span is your own code burning CPU, you need the function. A profiler samples: many times a second it records the stack (the chain of functions running), then counts how often each function appears. A flame graph draws the counts: "The x-axis shows the stack profile population, sorted alphabetically (it is not the passage of time), and the y-axis shows stack depth... The wider a frame is, the more often it was present in the stacks" ({{Brendan Gregg, Flame Graphs|https://www.brendangregg.com/flamegraphs.html}}). Continuous profiling runs a low-overhead sampler on every production process; Google did so fleet-wide in 2010 "with negligible overhead" ({{Google-Wide Profiling, IEEE Micro 2010|https://research.google/pubs/google-wide-profiling-a-continuous-profiling-infrastructure-for-data-centers/}}). Tools: Grafana Pyroscope, Parca, Datadog's profiler, and OpenTelemetry Profiles, a fourth OTel signal in public alpha since 2026-03-26 with an eBPF-based reference profiler ({{OTel blog|https://opentelemetry.io/blog/2026/profiles-alpha/}}).

A real use, answering "what does all this telemetry cost my service?": each kind of telemetry call timed as the demo makes it, then one request's worth (six spans, two histogram observations, one counter, one JSON log line) profiled with a 30-line sampling profiler of exactly this kind (stacks read every millisecond):

About 96 microseconds of CPU per request in Python, against a request of about 320 ms, is 0.03%: negligible here. The flame graph shows where it goes: span creation and the JSON log line, not the metrics. At 10,000 requests a second on one machine the same cost is about one CPU core, which is when teams sample traces, drop INFO logs on hot paths, or move work to the collector.
