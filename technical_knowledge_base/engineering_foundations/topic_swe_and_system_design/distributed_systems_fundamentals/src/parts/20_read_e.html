Quorums: N, R and W

In a leaderless system each piece of data is stored on N replicas. A write is sent to all N and counts as successful once W of them confirm. A read asks replicas and waits for R answers, then takes the newest version among them (every value carries a version). The rule that makes this work is one line:

R + W > N
N
replicas that hold each item
W
replicas that must confirm a write
R
replicas a read must hear from

If R + W > N, every read set and every write set share at least R + W − N replicas, so at least one replica the read hears from has the latest successful write. This overlapping set is a quorum. Amazon's Dynamo paper: "The common (N,R,W) configuration used by several instances of Dynamo is (3,2,2)" ({{DeCandia et al., SOSP 2007|https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf}}). Try it; the read is drawn picking the worst replicas it could.

The knobs trade against each other: lower W makes writes faster and keeps them working with more replicas down (N − W may be down), lower R does the same for reads (N − R). Cassandra exposes this per query as consistency levels: "QUORUM: A majority (n/2 + 1) of the replicas must respond", ONE, ALL, LOCAL_QUORUM (a majority in the local data centre) and others, and its docs call them "a version of Dynamo's R + W > N consistency mechanism" ({{Apache Cassandra docs, Dynamo architecture|https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html}}). Replicas that missed a write catch up by read repair (a read that sees an old version writes the new one back) and by anti-entropy: background comparison of Merkle trees, hash trees that let two replicas find differing ranges without sending all the data (Dynamo, Table 1).

R + W > N is not the same as strong consistency
It guarantees overlap, not linearizability (defined below). Abadi: by increasing R + W such systems "gain more consistency at the expense of latency (although they cannot achieve full consistency as defined by Gilbert and Lynch, even if R + W > N)" ({{Abadi, IEEE Computer, Feb 2012|https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf}}). The gaps: two concurrent writes, settled by timestamps (Cassandra uses "a simpler last-write-wins model where every mutation is timestamped", so a skewed clock picks the winner); a write that reached fewer than W replicas reports failure but is not rolled back where it landed; and a sloppy quorum, Dynamo's choice under failures, accepts writes on replicas outside the usual N ("hinted handoff") so the overlap no longer holds. Discord, which read and wrote "with quorum consistency level" on Cassandra, also found that one slow replica in a busy partition slowed everyone ("discord-2023" in the parent's Case files).

Partitioning: splitting the data

Replication copies everything everywhere, so it cannot help when the data or the write rate outgrow one machine. Partitioning (sharding; each piece is a partition or shard) gives each machine a slice. Each slice is usually also replicated, so a real cluster is partitioned and replicated: DynamoDB keeps every partition as three replicas in three availability zones ({{Elhemali et al., USENIX ATC 2022|https://www.usenix.org/system/files/atc22-elhemali.pdf}}). The design question is which machine holds which key.

By key range or by hash

  • Key-range partitioning: shard 1 holds users A to F, shard 2 G to M, and so on, like volumes of an encyclopedia. Range queries ("all messages in this chat between Monday and Friday") hit one shard. Danger: keys that arrive in order all land on the same shard; partitioning messages by timestamp sends every new message to the last shard.
  • Hash partitioning: run the key through a hash function and use the hash to pick the shard. Keys spread evenly whatever their pattern. Cost: range queries must ask every shard.

The obvious way to turn a hash into a shard is hash(key) mod N. It is a trap: add one machine (N to N + 1) and almost every key's remainder changes, so almost all data must move. Consistent hashing fixes this. Place each machine at several random points on a circle of hash values; a key belongs to the first machine point clockwise from its own hash. Adding a machine only takes over the arcs just before its points, about 1/(N + 1) of the keys. Each machine gets many points (virtual nodes, Dynamo's "tokens") so its share is even. More is not free: the Cassandra docs warn that every token adds ring neighbours, so "The more tokens you have, the higher the probability of an outage" when several machines fail at once ({{Cassandra docs|https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html}}). Hot keys, rebalancing, and finding the right shard

  • Hot keys. Hashing spreads keys, not load. One celebrity user, or one busy Discord channel, is one key on one shard. Discord's fix was to stop sending the same query a thousand times (request coalescing) before buying a bigger database ("discord-2023" in Case files). Other fixes: add a random suffix to a hot key so it spreads over several shards (reads must then gather all of them), or cache it.
  • Rebalancing. Rather than consistent hashing, many databases create many more partitions than machines from day one and move whole partitions when machines are added: Instagram created thousands of logical shards on a few Postgres servers in 2012, and Notion split its Postgres into 480 logical shards on 32 physical databases in 2021, choosing 480 because it divides evenly over 40 or 48 hosts later ("insta-2012" and "notion-2021" in the parent's {{Case files|n:3c65c17b0d0d81048ae0dd14ac399b4d}}). Moving data is slow and loads the network, so it is throttled and usually triggered by a person or a careful controller.
  • Secondary indexes. Looking a chat up by id is one shard; "all chats mentioning Lisbon" is all of them. A local index (one per shard) makes writes cheap and reads ask every shard; a global index is itself partitioned and kept up to date asynchronously. In DynamoDB, "All reads from GSIs and streams are eventually consistent" ({{DynamoDB read consistency|https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html}}).
  • Routing. Someone must know the map from key to shard: the client library (Cassandra drivers), a routing tier (Vitess, MongoDB's mongos), or any node that forwards. The map itself must be agreed, which is a job for consensus.

Choose the shard key so the common queries hit one shard and related data lands together: for the chat product, by user (or by workspace, as Notion did). It is among the most expensive decisions to change later.
