2. Time and order without a shared clock

Last-write-wins, leases and "which happened first?" all need an order of events across machines, and wall clocks cannot give it reliably. Two ways out: give up physical time and track cause and effect (logical clocks), or keep physical time but bound its error (hybrid and bounded clocks).

Leslie Lamport (1978) defined happened-before (→): a → b if a came before b on the same machine, or a is sending a message and b is receiving it, or there is a chain of these. If neither a → b nor b → a, the events are concurrent: neither could have influenced the other.

  • A Lamport clock is one counter per machine: add one at every event; put the counter on every message; on receiving, set yours to max(yours, received) + 1. It satisfies Lamport's "Clock Condition. For any events a, b: if a→b then C(a) < C(b)", and he points out the converse fails: "we cannot expect the converse condition to hold as well" ({{Lamport, CACM 1978|https://lamport.azurewebsites.net/pubs/time-clocks.pdf}}). A smaller number does not mean "happened before"; it may be concurrent.
  • A vector clock keeps one counter per machine: add one to your own entry at every event; on receiving, take the element-wise maximum, then add one to your own. Now a → b exactly when a's vector is ≤ b's in every entry (and differs somewhere); if each is larger somewhere, they are concurrent. The cost is one number per participant on every message. Dynamo used vector clocks to keep concurrent versions of an item side by side for the application to merge (the shopping cart that keeps both additions); Cassandra chose last-write-wins timestamps instead.

  • Hybrid logical clocks (Kulkarni et al., 2014) pair the wall-clock time with a small logical counter: they capture causality like a Lamport clock while staying close to real time, and fit in a 64-bit timestamp ("HLC captures the causality relationship like logical clocks ... Moreover HLC fits in to 64 bits NTP timestamp format", {{Kulkarni et al.|https://cse.buffalo.edu/tech-reports/2014-04.pdf}}). CockroachDB uses them.
  • TrueTime (Google Spanner) returns not a time but an interval, [earliest, latest], guaranteed to contain the true time, from GPS receivers and atomic clocks in every data centre. In 2012 the uncertainty ε was "typically a sawtooth function of time, varying from about 1 to 7 ms over each poll interval" (the 6 ms climb is the drift budget above). Spanner then waits out the uncertainty before making a commit visible (commit wait), so any transaction that starts after another finished gets a larger timestamp. That is how it offers external consistency, under which "the system behaves as if all transactions run sequentially" ({{Spanner docs, TrueTime and external consistency|https://docs.cloud.google.com/spanner/docs/true-time-external-consistency}}). Better clocks mean shorter waits.
Clock bounds in CockroachDB and on AWS (optional)

CockroachDB still needs synchronised clocks: when a node's clock is off from at least half the others "by 80% of the maximum offset allowed, it spontaneously shuts down. This offset defaults to 500ms", with 250 ms recommended for new clusters ({{CockroachDB operational FAQs|https://docs.cockroachlabs.com/docs/stable/operational-faqs}}).

In November 2023 AWS announced "microsecond-level clock accuracy on supported Amazon EC2 instances" and ClockBound, an open-source daemon that reports the time with an error bound, TrueTime-style ({{AWS Compute Blog, 16 Nov 2023|https://aws.amazon.com/blogs/compute/its-about-time-microsecond-accurate-clocks-on-amazon-ec2-instances/}}).
