What can go wrong across a network

Partial failure: the new kind of failure

A program on one computer mostly either works or crashes. A distributed system has a third state: partial failure, where some machines or links work and others do not, and nobody can be sure which. Your app server sends "save hello" to the database and hears nothing back. Four very different things look exactly the same from where the app server sits:

Silence has four causes

The app server cannot tell these apart. The only tool it has is a timeout: wait so long, then assume something failed. A timeout cannot say what failed, and in two of the four cases the write did happen. That single fact drives most of this page: it is why retries need idempotency (owned by {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}), why a "dead" leader may still be alive (leases and fencing), and why Kafka's documentation says of a producer that sees a network error: "it cannot be sure if this error happened before or after the message was committed" ({{Kafka 4.2 design docs|https://kafka.apache.org/42/design/design/}}).

Choosing the timeout is a trade with no free answer. Too short, and a slow but healthy node is declared dead, a replacement takes over, and now two think they are in charge. Too long, and every real failure means a long wait. Systems that elect leaders make this explicit: etcd defaults to a 100 ms heartbeat and a 1,000 ms election timeout, and its docs say the election timeout "must be at least 10 times the round-trip time" ({{etcd v3.6 tuning|https://etcd.io/docs/v3.6/tuning/}}).

The eight fallacies

In the 1990s L. Peter Deutsch and others at Sun Microsystems listed the false assumptions that programmers new to distributed systems "invariably make" ({{Wikipedia, with the original list|https://en.wikipedia.org/wiki/Fallacies_of_distributed_computing}}). Each still causes outages; here is what each one breaks:

The false beliefWhat actually happens, and what you do about it
1. The network is reliablePackets are dropped, links are cut, switches are misconfigured. Every call needs a timeout and a plan for "unknown outcome".
2. Latency is zeroA round trip is about 0.5 ms inside a data centre and 69 ms across the US ({{Numbers to know|n:3c65c17b0d0d81048ae0dd14ac399b4d}}). Ten sequential calls across regions is most of a second: batch, parallelise, keep chatty calls local.
3. Bandwidth is infiniteCopying a big table to a new replica, or rebalancing shards, can saturate links and slow live traffic. Throttle background copies.
4. The network is secureAnything on the wire can be read or forged unless encrypted and authenticated (TLS between services, not only at the edge).
5. Topology does not changeMachines come and go, IP addresses move, autoscaling adds nodes. Discover peers dynamically; never hard-code addresses.
6. There is one administratorYour system spans a cloud provider, a DNS provider, other teams' services. Their changes are your outages (the parent's Case files hold several).
7. Transport cost is zeroSerialising data costs CPU, and cross-zone and cross-region traffic is billed per GB (egress prices in Numbers to know).
8. The network is homogeneousDifferent hardware, kernels, MTUs and client versions behave differently. Test across the mix you really run.

Partitions are real, and short ones do long damage

A network partition is a split: two groups of machines are each up but cannot reach each other. It is easy to think of it as rare and exotic. Two real records:

  • GitHub, 21 October 2018: maintenance cut the US East Coast data centre off for 43 seconds. Automation promoted West Coast database replicas to leaders; both coasts then held writes the other lacked, and repair took 24 hours and 11 minutes ({{GitHub post-incident analysis|https://github.blog/news-insights/company-news/oct21-post-incident-analysis/}}; "gh-2018-10" in the parent's {{Case files|n:3c65c17b0d0d81048ae0dd14ac399b4d}}). You will see below why "automatic failover" is a consistency decision.
  • Google, 2017: Eric Brewer's analysis of Spanner incidents put the network category "under 8%", and "Nor was a Spanner quorum ever on the minority side of a partition", but "We did see individual data centers or regions get cut off from the rest of the network" ({{Brewer, Spanner, TrueTime and the CAP Theorem, 14 Feb 2017|https://storage.googleapis.com/gweb-research2023-media/pubtools/pdf/45855.pdf}}). Even with Google's private network, partitions happen; they are just not the most common failure.

Pauses: a process can stop without knowing it stopped

A running program can freeze for seconds: a garbage collector's "stop the world" phase, a virtual machine being live-migrated, the OS swapping memory to disk, a laptop lid closing. When it resumes, its code continues from the next line as if no time passed. If it held a lock or a lease (permission that expires), that permission may have expired meanwhile and been given to someone else. This is the scenario behind fencing tokens, and Jepsen found that it breaks real lock services.

Clocks lie

Every machine has a quartz clock that drifts. Google's Spanner paper budgets a worst-case drift of "200 microseconds/second" between synchronisations every 30 seconds ({{Corbett et al., OSDI 2012|https://static.googleusercontent.com/media/research.google.com/en//archive/spanner-osdi2012.pdf}}), so even Google's machines can be 200 µs/s × 30 s = 6 ms apart before correction. Machines correct with NTP (Network Time Protocol), which can step the clock backwards. A computer has two clocks for this reason:

  • the time-of-day clock (wall clock): the date and time, comparable across machines only roughly, and it can jump;
  • the monotonic clock: only ever moves forward, meaningless across machines, the right tool for measuring a duration or a timeout.

Cloudflare learned this on 1 January 2017: at the leap second "a number went negative when it should always have been, at worst, zero", because Go's time.Now() "does not guarantee monotonicity", and DNS resolutions failed for some customers ({{Graham-Cumming, Cloudflare blog|https://blog.cloudflare.com/how-and-why-the-leap-second-affected-cloudflare-dns/}}). Go added "transparent monotonic time support" in version 1.9 later that year ({{Go 1.9 release notes|https://go.dev/doc/go1.9}}). The rule: measure durations with the monotonic clock; never order events across machines by their wall clocks unless the system bounds the error (see Clocks).

The models people reason in
Papers and docs state which failures they tolerate. Crash-stop: a node works correctly until it halts for good. Crash-recovery: it may halt and come back with what it saved to disk (most databases assume this). Byzantine: a node may lie or behave arbitrarily (blockchains; rarely inside one company). On timing: synchronous (delays have a known bound), asynchronous (no bound at all), and the realistic middle, partially synchronous (usually bounded, sometimes not). The consensus algorithms below are safe in the asynchronous model and make progress only when the network behaves for a while.
