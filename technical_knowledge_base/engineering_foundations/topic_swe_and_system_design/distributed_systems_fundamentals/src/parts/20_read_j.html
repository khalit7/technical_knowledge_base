9. Idempotency and exactly-once: an end-to-end property

Go back to the fourth silence: the database saved the charge and the reply was lost. The client cannot tell this from "request lost", so it has two choices. Never retry, and some charges silently never happen (at-most-once); or retry until it hears "done", and some charges happen twice (at-least-once). No protocol on the wire removes that choice, because the sender never learns which silence it got. What can happen exactly once is the effect: deliver at least once, and make the receiver recognise a repeat. An operation is idempotent when doing it twice has the same effect as doing it once ("set the title to Trip" is; "add 10 credits" is not).

Where the repeat is recognised matters, and that is the end-to-end argument (Saltzer, Reed and Clark, ACM Transactions on Computer Systems, 1984): "The function in question can completely and correctly be implemented only with the knowledge and help of the application standing at the end points of the communication system." On duplicates specifically: "even if the network suppresses duplicates, the application itself may accidentally originate duplicate requests, in its own failure/retry procedures. These application level duplications look like different messages to the communication system, so it cannot suppress them" ({{Saltzer, Reed and Clark|https://web.mit.edu/Saltzer/www/publications/endtoend/endtoend.pdf}}).

One charge, one lost reply, one retry: only a key checked at the end stops the double charge

Predict: the gateway in the middle drops duplicate messages. Does that save Ana from a double charge when her app retries? Compare the middle mode with the last one.

Illustrative amounts and key.

The recipe, wherever the end is (a payment service, a database, a job handler):

  • The originator names the operation. The client generates a unique idempotency key once, before the first attempt, and sends the same key on every retry. A key minted by a middle hop is a new key per attempt, which is the middle mode above.
  • The end records the key with the effect, atomically. Insert the key and apply the charge in one transaction (a unique constraint on the key does the checking). If they are separate steps, a crash between them leaves a charge with no key, or a key with no charge. On a repeat, return the stored result instead of running again.
  • Or make the operation idempotent by shape: "set to X" instead of "add X", a conditional write on a version number (compare-and-set), or a fencing token, which is the same idea applied to who may write.

Read "exactly-once" claims with this in mind. Kafka's transactions give exactly-once only while input and output are both Kafka topics; any external side effect needs its own deduplication, which {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}} shows in detail. Retries done for you are the usual source of the duplicate: Jepsen found that the official etcd Java client "incorrectly retries non-idempotent requests which may have actually succeeded" ({{Jepsen, jetcd 0.8.2, 2024-08-08|https://jepsen.io/analyses/jetcd-0.8.2}}). How many times to retry, with what backoff, is {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}; the HTTP shape of an idempotency key (header, expiry, the stored response) is {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}.
