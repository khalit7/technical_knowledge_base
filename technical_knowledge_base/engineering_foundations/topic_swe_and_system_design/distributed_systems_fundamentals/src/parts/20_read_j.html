9. Idempotency and exactly-once: an end-to-end property

Go back to the fourth silence: the database saved the charge and the reply was lost. The client cannot tell this from "request lost", so it has two choices. Never retry, and some charges silently never happen (at-most-once); or retry until it hears "done", and some charges happen twice (at-least-once). No protocol on the wire removes that choice, because the sender never learns which silence it got. What can happen exactly once is the effect: deliver at least once, and make the receiver recognise a repeat. An operation is idempotent when doing it twice has the same effect as doing it once ("set the title to Trip" is; "add 10 credits" is not).

Where the repeat is recognised matters, and that is the end-to-end argument (Saltzer, Reed and Clark, ACM Transactions on Computer Systems, 1984): "The function in question can completely and correctly be implemented only with the knowledge and help of the application standing at the end points of the communication system." On duplicates specifically: "even if the network suppresses duplicates, the application itself may accidentally originate duplicate requests, in its own failure/retry procedures. These application level duplications look like different messages to the communication system, so it cannot suppress them" ({{Saltzer, Reed and Clark|https://web.mit.edu/Saltzer/www/publications/endtoend/endtoend.pdf}}).

Predict: the gateway in the middle drops duplicate messages. Does that save Ana from a double charge when her app retries? Compare the middle mode with the last one.

  1. Ana's app sends the charge. The app asks for a 10-credit charge. Nothing identifies this operation except its content.
  2. Payments charges: 100 becomes 90. The charge is applied and the reply sent.
  3. The reply is lost; the app's timeout fires. The fourth silence: the charge happened, and the app cannot know it. It retries, as it must.
  4. The app retries. The retry looks exactly like a new charge.
  5. Charged twice: 90 becomes 80. Payments has no way to tell a retry from a second purchase. Ana paid 20 credits for one request.
  1. Ana's app sends the charge. The gateway tags each message it forwards with its own id (m-1) and drops any message whose id it has already seen, as many brokers do.
  2. Payments charges: 100 becomes 90. The charge is applied and the reply sent. (If the gateway re-sent m-1 after its own timeout, it would drop the duplicate correctly.)
  3. The reply is lost; the app's timeout fires. The fourth silence: the charge happened, and the app cannot know it. It retries, as it must.
  4. The app retries. To the gateway the retry is a new message, so it gets a new id, m-2, and passes the duplicate check. This is Saltzer, Reed and Clark's point: application-level duplicates "look like different messages to the communication system".
  5. Charged twice anyway. Deduplication in the middle removed only the duplicates the middle created. The end received two different-looking requests and charged twice. Only the end can do this job.
  1. Ana's app sends the charge. Before the first attempt the app generates a key, k-7f3, that names this one charge, and will reuse it on every retry.
  2. Payments charges: 100 becomes 90. In one transaction, payments applies the charge and inserts k-7f3 with its result into a table with a unique key.
  3. The reply is lost; the app's timeout fires. The fourth silence: the charge happened, and the app cannot know it. It retries with the same key.
  4. The app retries. The retry carries k-7f3 again: the operation has a name the end can recognise.
  5. Key found: return the stored result, charge nothing. The insert of k-7f3 fails on the unique key, so payments returns the result it stored the first time. One charge, and the app finally hears "ok, balance 90". At-least-once delivery plus this check is the exactly-once effect.

The recipe, wherever the end is (a payment service, a database, a job handler):

  • The originator names the operation. The client generates a unique idempotency key once, before the first attempt, and sends the same key on every retry. A key minted by a middle hop is a new key per attempt, which is the middle mode above.
  • The end records the key with the effect, atomically. Insert the key and apply the charge in one transaction (a unique constraint on the key does the checking). If they are separate steps, a crash between them leaves a charge with no key, or a key with no charge. On a repeat, return the stored result instead of running again.
  • Or make the operation idempotent by shape: "set to X" instead of "add X", a conditional write on a version number (compare-and-set), or a fencing token, which is the same idea applied to who may write.

Read "exactly-once" claims with this in mind. Kafka's transactions give exactly-once only while input and output are both Kafka topics; any external side effect needs its own deduplication, which {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}} shows in detail. Retries done for you are the usual source of the duplicate: Jepsen found that the official etcd Java client "incorrectly retries non-idempotent requests which may have actually succeeded" ({{Jepsen, jetcd 0.8.2, 2024-08-08|https://jepsen.io/analyses/jetcd-0.8.2}}). How many times to retry, with what backoff, is {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}; the HTTP shape of an idempotency key (header, expiry, the stored response) is {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}} (section 4).
