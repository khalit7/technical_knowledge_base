Transactions and isolation, in brief

A transaction groups several reads and writes so they succeed or fail together (atomicity) and so concurrent transactions do not see each other's half-done work (isolation). The I in ACID comes in levels, and the default is rarely the strongest:

LevelWhat it preventsWhat still gets through
Read committedReading another transaction's uncommitted writesTwo reads in one transaction can see different data; lost updates
Snapshot isolationEach transaction reads one consistent snapshot; concurrent writes to the same row conflictWrite skew: two transactions read the same rows, each writes a different row, both commit
SerializableEverything: same result as running one transaction at a timeNothing, at the price of aborts and retries under contention

Write skew in our product: a team shares a credit pool split over two rows, and the rule is "spend only if the pool total is at least the cost". Two members each spend 60 from a pool of 100 at the same moment; each transaction reads total 100, each debits its own row, both commit, and the pool is at −20. Snapshot isolation allows this; serializable does not. Postgres's default is read committed ("Read Committed is the default isolation level in PostgreSQL", {{PostgreSQL 18 docs|https://www.postgresql.org/docs/current/transaction-iso.html}}), and its "Repeatable Read" level "actually provides Snapshot Isolation" (Jepsen, below).

Isolation levels are where tested reality and documentation most often disagree. Jepsen's findings, each dated:

  • PostgreSQL 12.3 (2020-06-12): "transactions with serializable isolation on a single PostgreSQL instance were not, in fact, serializable" (a G2-item anomaly), a bug the PostgreSQL team patched for the next minor release, on 13 August 2020 ({{Jepsen|https://jepsen.io/analyses/postgresql-12.3}}).
  • MySQL 8.0.34 (2023-12-19): "MySQL's Repeatable Read still allows G2-item, G-single, and lost update", and "AWS RDS MySQL clusters routinely violate Serializability" ({{Jepsen|https://jepsen.io/analyses/mysql-8.0.34}}).
  • Amazon RDS for PostgreSQL 17.4 (2025-04-29): multi-AZ clusters "violate Snapshot Isolation"; "Healthy clusters occasionally allow Long Fork". The cause, found afterwards: the primary makes transactions visible in the order of an in-memory lock, while "Secondaries, however, make transactions visible based on their order in the Write-Ahead Log (WAL)", so a replica can show two transactions in the opposite order to the primary ({{Jepsen|https://jepsen.io/analyses/amazon-rds-for-postgresql-17.4}}). Replication lag is not the only way a replica disagrees.

Transactions across machines

When one transaction touches two partitions, or a database and a message queue, no single machine can commit it. Two-phase commit (2PC) uses a coordinator: phase 1 asks every participant "can you commit?" (each makes the change durable but invisible and promises to obey); phase 2 tells all to commit, or all to abort. Its weakness: a participant that has said yes must wait, holding locks, until it hears the decision, so a dead coordinator blocks everyone. Spanner's answer is to make each participant and the coordinator a Paxos group, so none of them is a single machine: "Running two-phase commit over Paxos mitigates the availability problems" ({{Corbett et al., OSDI 2012|https://static.googleusercontent.com/media/research.google.com/en//archive/spanner-osdi2012.pdf}}). The everyday version of this problem is the dual write: save a row in Postgres and publish an event to Kafka; a crash between the two leaves them disagreeing. The standard fix, the transactional outbox, is taught in {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}.

Clocks: ordering events without a shared time

Last-write-wins, leases, "which happened first?" all need an order of events across machines. Wall clocks cannot give it reliably (section 2). There are two ways out: give up physical time and track cause and effect (logical clocks), or keep physical time but bound its error (hybrid and bounded clocks).

Lamport clocks

Leslie Lamport (1978) defined happened-before (→): a → b if a came before b on the same machine, or a is sending a message and b is receiving it, or there is a chain of these. If neither a → b nor b → a, the events are concurrent: neither could have influenced the other. A Lamport clock is one counter per machine: add one at every event; put the counter on every message; on receiving, set yours to max(yours, received) + 1. It satisfies Lamport's "Clock Condition. For any events a, b: if a→b then C(a) < C(b)", and he points out the converse fails: "we cannot expect the converse condition to hold as well" ({{Lamport, CACM 1978|https://lamport.azurewebsites.net/pubs/time-clocks.pdf}}). A smaller number does not mean "happened before"; it may be concurrent.

Vector clocks

A vector clock keeps one counter per machine: add one to your own entry at every event; on receiving, take the element-wise maximum, then add one to your own. Now a → b exactly when a's vector is ≤ b's in every entry (and differs somewhere); if each is larger somewhere, they are concurrent. The cost is one number per participant on every message. Dynamo used vector clocks to keep concurrent versions of an item side by side for the application to merge (the shopping cart that keeps both additions); Cassandra chose last-write-wins timestamps instead (the Cassandra docs above). Hybrid logical clocks and bounded clocks

  • Hybrid logical clocks (Kulkarni et al., 2014) pair the wall-clock time with a small logical counter: they capture causality like a Lamport clock while staying close to real time, and fit in a 64-bit timestamp ("HLC captures the causality relationship like logical clocks ... Moreover HLC fits in to 64 bits NTP timestamp format", {{Kulkarni et al.|https://cse.buffalo.edu/tech-reports/2014-04.pdf}}). CockroachDB uses them and still needs synchronised clocks: when a node's clock is off from at least half the others "by 80% of the maximum offset allowed, it spontaneously shuts down. This offset defaults to 500ms", with 250 ms recommended for new clusters ({{CockroachDB operational FAQs|https://docs.cockroachlabs.com/docs/stable/operational-faqs}}).
  • TrueTime (Google Spanner) returns not a time but an interval, [earliest, latest], guaranteed to contain the true time, from GPS receivers and atomic clocks in every data centre. In 2012 the uncertainty ε was "typically a sawtooth function of time, varying from about 1 to 7 ms over each poll interval" (the 6 ms climb is the drift budget above). Spanner then waits out the uncertainty before making a commit visible (commit wait), so any transaction that starts after another finished gets a larger timestamp. That is how it offers external consistency, under which "the system behaves as if all transactions run sequentially" ({{Spanner docs, TrueTime and external consistency|https://docs.cloud.google.com/spanner/docs/true-time-external-consistency}}). Better clocks mean shorter waits.
  • Bounded clocks for everyone. In November 2023 AWS announced "microsecond-level clock accuracy on supported Amazon EC2 instances" and ClockBound, an open-source daemon that reports the time with an error bound, TrueTime-style ({{AWS Compute Blog, 16 Nov 2023|https://aws.amazon.com/blogs/compute/its-about-time-microsecond-accurate-clocks-on-amazon-ec2-instances/}}).
