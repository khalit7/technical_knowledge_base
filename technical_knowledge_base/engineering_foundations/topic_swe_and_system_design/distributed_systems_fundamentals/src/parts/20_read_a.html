The idea in one screen

Machines that share data can only talk by messages, and a missing reply never tells you what happened; every technique on this page (replicas, quorums, consensus, fencing, idempotency) is a way to stay correct anyway, paid for in latency or availability.

One chat product, four jobs: split the data, copy each piece, choose what a read may see, agree on who is in charge

  1. Partitioning: users are split over shards, so no machine holds everything.
  2. Replication: each shard has a leader that takes writes and followers that replay its log, a little behind.
  3. Consistency: a read that lands on a lagging follower can miss Ana's own "hello"; a consistency model says whether that is allowed.
  4. Consensus: a small Raft group (etcd) decides which node leads each shard; leases and fencing tokens stop an old leader that has not noticed.

The running example is the parent page's LLM chat product ({{Topic: swe-and-system-design|n:3c65c17b0d0d81048ae0dd14ac399b4d}}): users, their chats, the messages in each chat, and each user's paid credit balance. Ana sends "hello" and her page refreshes. The question the whole page answers: which copy does that refresh read, and is "hello" in it?

You need: nothing beyond a database and an HTTP request. The parent page's {{Numbers to know|n:3c65c17b0d0d81048ae0dd14ac399b4d}} tab holds the round-trip times used here (0.5 ms in a data centre, 69 ms across the US).

The habit to take away
Start from the invariant, the thing that must never happen ("never spend the same credit twice", "a sent message never vanishes for its sender"), then pick the weakest guarantee that still protects it, per piece of data. The sidebar's chat order can be a second stale; the credit balance cannot. The parent page's {{How a senior engineer reasons|n:3c65c17b0d0d81048ae0dd14ac399b4d}} section says the same.

New terms on this page

Partial failure: some machines or links work, others do not, and nobody can be sure which.
Replica, leader, follower: one copy; the copy that takes writes; the copies that replay its log.
Replication lag: how far a follower is behind its leader.
Quorum: enough replicas that any two such sets overlap (R + W > N, or a majority).
Consistency model: the set of histories a system may show its clients.
Linearisable: behaves like one copy, in real-time order.
Consensus: machines agreeing on one value or one log while some fail.
Lease, fencing token: permission that expires; a number that grows with each grant, checked by the storage.
Idempotent: doing it twice has the same effect as doing it once.
Partition (shard), and network partition: a slice of the data; a split in the network. Two different things with one name.
