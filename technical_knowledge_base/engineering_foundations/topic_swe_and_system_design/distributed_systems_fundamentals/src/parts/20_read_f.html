5. Consistency models: the ladder from linearisable to eventual

"Consistent" is used loosely. A consistency model is a precise promise: Jepsen defines it as "a safety property which declares what a system can do. Formally, a consistency model defines a set of histories that a system can legally execute" ({{Jepsen, Consistency|https://jepsen.io/consistency}}). A history is what clients observed: who called which operation, when it started, when it returned, and what it returned. To make each model concrete, take one value x (say, the title of Ana's chat, encoded as a number), initially 0. Each bar below is one operation, from the moment the client sent it to the moment the answer came back; w(1) writes 1 and r→0 is a read that returned 0.

Predict: history 4, "A new value, then an old one": both reads overlap the slow write, so is it linearisable? Pick it, then tap any read bar to change what it returned and watch the rungs flip.

Strongest at the top: Jepsen's {{map of consistency models|https://jepsen.io/consistency}} places linearisable above sequential above causal above read-your-writes; eventual is a convergence promise and sits at the bottom. Availability per rung is Jepsen's: linearisability and sequential consistency "cannot be totally or sticky available"; causal and read-your-writes are "sticky available" (every node can make progress during a partition "so long as clients never change which server they talk to").

How the verdicts are computed (optional)

Linearisable and sequentially consistent are checked by brute force in your browser: try every ordering of the operations, keep those that respect each client's own order (and, for linearisability, real time: if one operation ended before another began, it must come first), and accept if in one of them every read returns the latest preceding write. With at most six operations that is at most 720 orderings. src/recompute.py runs the same check in Python for every preset. Causal, read-your-writes and eventual verdicts are written by hand for the presets, with the reasoning shown; once you edit a read they show "?" rather than guess.

Now the models, strongest first. Each one is a rule for which histories are allowed:

  • Linearisability (Herlihy and Wing, 1990): "every operation appears to take place atomically, in some order, consistent with the real-time ordering of those operations: e.g., if operation A completes before operation B begins, then B should logically take effect after A" ({{Jepsen, Linearizability|https://jepsen.io/consistency/models/linearizable}}). Picture each operation taking effect at one instant somewhere inside its bar. History 2 fails (the write ended before the read began, so the read must see 1). History 4 fails too, and it is the subtle one: both reads overlap the write, so either answer alone would be fine, but once client 2 has seen 1 and returned, nobody may see 0 afterwards. Linearisability is what makes a system behave like one copy; it is what you need for a lock, a leader, a unique username or "never spend the same credit twice". It is the "strong consistency" of the parent page.
  • Sequential consistency (Lamport, 1979): all operations appear in one total order that every client agrees on, and each client's own operations are in that order in the order it issued them, but the order need not match real time. Histories 2 and 4 both pass: put the read of 0 before the write. A client may be behind, but everyone sees the same story.
  • Causal consistency: operations that are causally related must be seen by everyone in that order; unrelated (concurrent) ones may be seen in different orders by different clients. Jepsen's example is a chat: Attiya asks "shall we have lunch?", Barbarella says "yes" and Cyrus "no"; "no participant ever observes 'yes' or 'no' prior to the question 'lunch?'", but they may disagree on the order of "yes" and "no" ({{Jepsen, Causal|https://jepsen.io/consistency/models/causal}}). Its great property: it can stay available during a partition, as long as each client sticks to the same server.
  • Eventual consistency: if writes stop, all copies eventually return the same value. It promises nothing about what you read meanwhile, not even your own write. DynamoDB's default read is this: "the responses might not reflect the results of a recently completed write operation" ({{DynamoDB read consistency|https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html}}).

Between causal and eventual sit the session guarantees from the replication section: read-your-writes, monotonic reads, and two more (monotonic writes: one client's writes are applied in order; writes follow reads: a write made after reading something is ordered after it). They are cheap and they fix most of what users notice.

Linearisable is not serialisable

Two words sound alike and are different. Linearisability is about single operations on one object and respects real time. Serialisability is about transactions (groups of reads and writes on many objects): the result equals some one-at-a-time order of the transactions, but not necessarily the real-time order. Strict serialisability is both: Jepsen describes it as "serializability's total order of transactional multi-object operations, plus linearizability's real-time constraints" ({{Jepsen, Strong Serializability|https://jepsen.io/consistency/models/strong-serializable}}). Spanner calls its version external consistency (below). Isolation levels inside one database are taught in {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}}; transactions across machines get a short section here.

Correction to the old page
The old page grouped "Sequential / causal: causally related ops are ordered everywhere; concurrent ops may interleave differently". That sentence describes causal consistency only. Sequential consistency is stronger: everyone sees the same single order, concurrent operations included. History 6, "Two observers disagree", separates them: allowed under causal, forbidden under sequential.
The sources behind the correction, and causal+ (optional)

Jepsen: under sequential consistency "operations appear to take place in some total order, and that that order is consistent with the order of operations on each individual process" ({{Jepsen, Sequential|https://jepsen.io/consistency/models/sequential}}). The old page's "Causal+ is the sweet spot for geo-replicated data" is an opinion; it is the argument of the COPS paper that introduced causal+ (causal plus convergence) for wide-area stores ({{Lloyd et al., SOSP 2011|https://www.cs.cmu.edu/~dga/papers/cops-sosp2011.pdf}}), and Jepsen notes "Most 'causally consistent' systems actually provide these stronger properties, such as RTC or causal+".
