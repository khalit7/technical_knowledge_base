Replication: keeping copies

Replication means keeping a copy of the same data on several machines, each copy a replica. It solves reasons 1, 2 and 4 above (a dead machine, too many reads, far-away users). Copying data that never changes is trivial; all the difficulty is in changes. There are three ways to organise who accepts changes.

Single leader (leader and followers)

One replica is the leader (also called primary or master): every write goes to it. It records each change in an ordered log (Postgres calls it the write-ahead log, WAL: every change is written there before the tables are touched, which is also how it survives a crash). The other replicas, followers (secondaries, standbys, read replicas), receive that log and replay it in the same order, so they pass through the same states. Reads may go to any replica. This is Postgres streaming replication, MySQL replication, MongoDB replica sets and Kafka partitions; it is what the parent page called a read replica.

Synchronous or asynchronous: when does the leader say "saved"?

The leader can confirm a write to the client before or after followers have it:

  • Asynchronous: confirm after the leader's own disk has it. Fast, and a slow follower never slows writes. Cost: if the leader dies, writes its followers had not received are lost, even though the client was told "saved".
  • Synchronous: confirm only after a follower has it too. A confirmed write survives the leader's death. Cost: every commit waits a round trip to the follower, and if that follower is down, writes stop (so real setups wait for "any one of several").

Postgres makes this one setting, synchronous_commit, and its documentation is exact about what each value waits for ({{PostgreSQL 18 docs, synchronous_commit|https://www.postgresql.org/docs/current/runtime-config-wal.html}}). With no synchronous standby named, only the leader's flush counts. With one named in synchronous_standby_names: on waits until the standby has "flushed it to durable storage"; remote_apply waits until it has "applied it, so that it has become visible to queries on the standby(s)". Those are different moments, and the difference is exactly the stale-read question. So it was measured.

How to read it. Even with both copies on one machine, asynchronous replication missed nearly every immediate read: the write became visible on the replica a median 0.236 ms later (worst 6.8 ms), but the read was faster. Synchronous on is not read-your-writes: it guarantees the write is durable on the replica, not visible there, and one read in 2,000 still slipped through the gap between flush and replay. Only remote_apply, or the client waiting for the replica to reach its own write position (median extra wait 0.105 ms, p99 0.624 ms), closed it.

What does not transfer to production: here the "network" is loopback and macOS fsync returns before the drive truly flushes (see the parent's {{Numbers to know|n:3c65c17b0d0d81048ae0dd14ac399b4d}}), so every commit is unrealistically cheap. With the replica in another availability zone, each synchronous commit adds at least one round trip (Microsoft targets under about 2 ms between zones); across the US, 69 ms. Lag grows the same way, so stale reads get more likely, not less.

What lag does to readers: the before and after

Asynchronous followers are behind by some amount, the replication lag: usually milliseconds, sometimes seconds or minutes when a follower is overloaded or recovering. Three anomalies follow, and each has a standard fix. The animation runs the same write ("hello") through four ways of reading it back.

Illustrative positions and timing; the stale-read rate and the wait are the measured ones above.

  • Read-your-writes (read-after-write): a user always sees their own writes. Fixes: read data the user may have just changed from the leader (for example, for one minute after their last write), or remember the log position of their last write and have the replica wait until it has replayed that far. In Postgres the second is two functions:
    -- on the primary, right after the write commits
    SELECT pg_current_wal_insert_lsn(); -- e.g. 0/3000148, keep it in the session
    -- on the replica, before reading
    SELECT pg_last_wal_replay_lsn() >= '0/3000148'::pg_lsn; -- wait until true
    This is exactly what the measurement's fourth row ran. The cost is a short wait on the reads that need it, and the session must carry a position.
  • Monotonic reads: once a user has seen some state, they never see an older one. Fix: send each user's reads to the same replica (hash the user id), as in the animation.
  • Consistent prefix reads: if writes happened in an order, readers see them in that order. In the chat, Ben asks "lunch?" and Ana answers "yes". If the two messages are stored on different machines with different lag, a third user can see "yes" before "lunch?". Fix: keep things that are causally related (one chat's messages) on the same partition, so one log orders them; the general tool is causal ordering.

Failover: when the leader dies

If the leader dies, a follower must be promoted to leader and clients must switch to it: failover. Done by hand it takes minutes; done automatically it is fast and dangerous, for three reasons:

  1. Is it really dead? Only a timeout says so (the four silences above). A leader that was merely slow or cut off comes back still believing it is the leader: two leaders accepting writes, split brain. Preventing this is what consensus and fencing are for.
  2. Lost writes. With asynchronous replication, the promoted follower may lack the last writes the old leader confirmed. Those confirmed writes are gone, and if the old leader returns its extra writes conflict with the new history.
  3. Across regions. GitHub's 2018 outage is all three in one: 43 seconds of partition, automatic promotion of the other coast's replicas, writes on both sides, and a 24-hour repair because GitHub "chose data integrity" over a fast fail-back ({{GitHub|https://github.blog/news-insights/company-news/oct21-post-incident-analysis/}}). Afterwards it stopped automatic promotion across regions.

In practice, Postgres itself never promotes anything; tools such as Patroni do it. Patroni "supports a variety of distributed configuration stores like ZooKeeper, etcd, Consul or Kubernetes" ({{Patroni 4.1 documentation|https://patroni.readthedocs.io/en/latest/}}): consensus-backed stores that decide which single node holds the leader key at any moment. Managed services (Amazon RDS Multi-AZ, Cloud SQL) do the same internally.

Multi-leader: writes in several places

With users on several continents, you may want a leader in each region so writes do not cross an ocean. Each leader accepts writes and replicates them to the others. The price is write conflicts: Ana renames a chat to "Trip" on her phone (Europe leader) while her laptop renames it to "Holiday" (US leader). Both succeed locally; when the changes meet, something must choose. Options: last write wins (keep the one with the later timestamp; simple, silently discards the other, and clocks can lie), merge both values, ask the user, or use data types designed to merge automatically (CRDTs, conflict-free replicated data types: counters, sets and text that merge the same way whatever the order). Avoid multi-leader unless you need it; the usual trick is to route all writes for one item (one user, one chat) to one "home" leader, which avoids most conflicts.

Leaderless: any replica takes writes

Amazon's Dynamo paper (2007) made the third style famous: no leader at all. The client (or a coordinator acting for it) sends each write to several replicas and each read to several replicas, and counts answers. Cassandra, Riak and ScyllaDB work this way. Its central idea, the quorum, is the next section.
