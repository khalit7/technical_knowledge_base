A distributed system is several computers that talk only by sending messages over a network and still have to behave like one. The moment your data lives on more than one machine you get four new jobs: keep copies in step (replication), decide which machine holds which data (partitioning), decide what a reader is allowed to see while copies disagree (consistency), and make machines agree on one answer when some of them are down (consensus). Each job has a handful of standard techniques, and every one of them is paid for in latency, availability or complexity.

The running example is the one from the parent page, Topic: swe-and-system-design: an LLM chat product. Its data is users, their chats, the messages in each chat, and each user's paid credit balance. Ana is a user. She sends "hello", the page refreshes, and the question this whole page answers is: which copy of the data does that refresh read, and is "hello" in it?

Why one machine is not enough

Start with the honest default: one database server. One machine has one copy of the truth; a write is visible to the next read; there is nothing to disagree with. The parent page's advice stands: "a bigger machine and one Postgres go a long way". You leave it for four reasons, and it pays to know which one you are leaving for, because each points at a different technique:

1. It dies

A disk fails, a kernel panics, a data centre loses power. With one machine the product is down until it is repaired, and writes since the last backup may be gone. Fix: replication (copies elsewhere, ready to take over).

2. Too many reads

Every page load reads chats and messages. Reads usually outnumber writes many times over. Fix: replication again (spread reads over copies), or a cache (parent page, Step 2).

3. Too many writes or too much data

Copies do not help here: every copy must take every write. Fix: partitioning (each machine holds a slice).

4. Users far away

Light in fibre needs about 59 ms just to cross the Atlantic and back; Azure measures 78 ms East US to UK South (Numbers to know on the parent page). Fix: replicas near the users, which makes the copies far from each other.

Each fix puts the same data, or related data, on machines that can only talk by message. That is the whole source of difficulty, so the next section is about what messages do.

What can go wrong across a network

Partial failure: the new kind of failure

A program on one computer mostly either works or crashes. A distributed system has a third state: partial failure, where some machines or links work and others do not, and nobody can be sure which. Your app server sends "save hello" to the database and hears nothing back. Four very different things look exactly the same from where the app server sits:

Silence has four causes

The app server cannot tell these apart. The only tool it has is a timeout: wait so long, then assume something failed. A timeout cannot say what failed, and in two of the four cases the write did happen. That single fact drives most of this page: it is why retries need idempotency (owned by Reliability engineering), why a "dead" leader may still be alive (leases and fencing), and why Kafka's documentation says of a producer that sees a network error: "it cannot be sure if this error happened before or after the message was committed" (Kafka 4.2 design docs).

Choosing the timeout is a trade with no free answer. Too short, and a slow but healthy node is declared dead, a replacement takes over, and now two think they are in charge. Too long, and every real failure means a long wait. Systems that elect leaders make this explicit: etcd defaults to a 100 ms heartbeat and a 1,000 ms election timeout, and its docs say the election timeout "must be at least 10 times the round-trip time" (etcd v3.6 tuning).

The eight fallacies

In the 1990s L. Peter Deutsch and others at Sun Microsystems listed the false assumptions that programmers new to distributed systems "invariably make" (Wikipedia, with the original list). Each still causes outages; here is what each one breaks:

The false beliefWhat actually happens, and what you do about it
1. The network is reliablePackets are dropped, links are cut, switches are misconfigured. Every call needs a timeout and a plan for "unknown outcome".
2. Latency is zeroA round trip is about 0.5 ms inside a data centre and 69 ms across the US (Numbers to know). Ten sequential calls across regions is most of a second: batch, parallelise, keep chatty calls local.
3. Bandwidth is infiniteCopying a big table to a new replica, or rebalancing shards, can saturate links and slow live traffic. Throttle background copies.
4. The network is secureAnything on the wire can be read or forged unless encrypted and authenticated (TLS between services, not only at the edge).
5. Topology does not changeMachines come and go, IP addresses move, autoscaling adds nodes. Discover peers dynamically; never hard-code addresses.
6. There is one administratorYour system spans a cloud provider, a DNS provider, other teams' services. Their changes are your outages (the parent's Case files hold several).
7. Transport cost is zeroSerialising data costs CPU, and cross-zone and cross-region traffic is billed per GB (egress prices in Numbers to know).
8. The network is homogeneousDifferent hardware, kernels, MTUs and client versions behave differently. Test across the mix you really run.

Partitions are real, and short ones do long damage

A network partition is a split: two groups of machines are each up but cannot reach each other. It is easy to think of it as rare and exotic. Two real records:

  • GitHub, 21 October 2018: maintenance cut the US East Coast data centre off for 43 seconds. Automation promoted West Coast database replicas to leaders; both coasts then held writes the other lacked, and repair took 24 hours and 11 minutes (GitHub post-incident analysis; "gh-2018-10" in the parent's Case files). You will see below why "automatic failover" is a consistency decision.
  • Google, 2017: Eric Brewer's analysis of Spanner incidents put the network category "under 8%", and "Nor was a Spanner quorum ever on the minority side of a partition", but "We did see individual data centers or regions get cut off from the rest of the network" (Brewer, Spanner, TrueTime and the CAP Theorem, 14 Feb 2017). Even with Google's private network, partitions happen; they are just not the most common failure.

Pauses: a process can stop without knowing it stopped

A running program can freeze for seconds: a garbage collector's "stop the world" phase, a virtual machine being live-migrated, the OS swapping memory to disk, a laptop lid closing. When it resumes, its code continues from the next line as if no time passed. If it held a lock or a lease (permission that expires), that permission may have expired meanwhile and been given to someone else. This is the scenario behind fencing tokens, and Jepsen found that it breaks real lock services.

Clocks lie

Every machine has a quartz clock that drifts. Google's Spanner paper budgets a worst-case drift of "200 microseconds/second" between synchronisations every 30 seconds (Corbett et al., OSDI 2012), so even Google's machines can be 200 µs/s × 30 s = 6 ms apart before correction. Machines correct with NTP (Network Time Protocol), which can step the clock backwards. A computer has two clocks for this reason:

  • the time-of-day clock (wall clock): the date and time, comparable across machines only roughly, and it can jump;
  • the monotonic clock: only ever moves forward, meaningless across machines, the right tool for measuring a duration or a timeout.

Cloudflare learned this on 1 January 2017: at the leap second "a number went negative when it should always have been, at worst, zero", because Go's time.Now() "does not guarantee monotonicity", and DNS resolutions failed for some customers (Graham-Cumming, Cloudflare blog). Go added "transparent monotonic time support" in version 1.9 later that year (Go 1.9 release notes). The rule: measure durations with the monotonic clock; never order events across machines by their wall clocks unless the system bounds the error (see Clocks).

The models people reason in
Papers and docs state which failures they tolerate. Crash-stop: a node works correctly until it halts for good. Crash-recovery: it may halt and come back with what it saved to disk (most databases assume this). Byzantine: a node may lie or behave arbitrarily (blockchains; rarely inside one company). On timing: synchronous (delays have a known bound), asynchronous (no bound at all), and the realistic middle, partially synchronous (usually bounded, sometimes not). The consensus algorithms below are safe in the asynchronous model and make progress only when the network behaves for a while.

Replication: keeping copies

Replication means keeping a copy of the same data on several machines, each copy a replica. It solves reasons 1, 2 and 4 above (a dead machine, too many reads, far-away users). Copying data that never changes is trivial; all the difficulty is in changes. There are three ways to organise who accepts changes.

Single leader (leader and followers)

One replica is the leader (also called primary or master): every write goes to it. It records each change in an ordered log (Postgres calls it the write-ahead log, WAL: every change is written there before the tables are touched, which is also how it survives a crash). The other replicas, followers (secondaries, standbys, read replicas), receive that log and replay it in the same order, so they pass through the same states. Reads may go to any replica. This is Postgres streaming replication, MySQL replication, MongoDB replica sets and Kafka partitions; it is what the parent page called a read replica.

Synchronous or asynchronous: when does the leader say "saved"?

The leader can confirm a write to the client before or after followers have it:

  • Asynchronous: confirm after the leader's own disk has it. Fast, and a slow follower never slows writes. Cost: if the leader dies, writes its followers had not received are lost, even though the client was told "saved".
  • Synchronous: confirm only after a follower has it too. A confirmed write survives the leader's death. Cost: every commit waits a round trip to the follower, and if that follower is down, writes stop (so real setups wait for "any one of several").

Postgres makes this one setting, synchronous_commit, and its documentation is exact about what each value waits for (PostgreSQL 18 docs, synchronous_commit). With no synchronous standby named, only the leader's flush counts. With one named in synchronous_standby_names: on waits until the standby has "flushed it to durable storage"; remote_apply waits until it has "applied it, so that it has become visible to queries on the standby(s)". Those are different moments, and the difference is exactly the stale-read question. So it was measured.

Even with both copies on one machine, asynchronous replication missed nearly every immediate read: the write became visible on the replica a median 0.236 ms later (worst 6.8 ms), but the read was faster. What does not transfer to production: here the "network" is loopback and macOS fsync returns before the drive truly flushes (see the parent's Numbers to know), so every commit is unrealistically cheap. With the replica in another availability zone, each synchronous commit adds at least one round trip (Microsoft targets under about 2 ms between zones); across the US, 69 ms. Lag grows the same way, so stale reads get more likely, not less.

What lag does to readers: the before and after

Asynchronous followers are behind by some amount, the replication lag: usually milliseconds, sometimes seconds or minutes when a follower is overloaded or recovering. Three anomalies follow, and each has a standard fix. The animation runs the same write ("hello") through four ways of reading it back.

Illustrative positions and timing; the stale-read rate and the wait are the measured ones above.

  • Read-your-writes (read-after-write): a user always sees their own writes. Fixes: read data the user may have just changed from the leader (for example, for one minute after their last write), or remember the log position of their last write and have the replica wait until it has replayed that far. In Postgres the second is two functions:
    -- on the primary, right after the write commits
    SELECT pg_current_wal_insert_lsn(); -- e.g. 0/3000148, keep it in the session
    -- on the replica, before reading
    SELECT pg_last_wal_replay_lsn() >= '0/3000148'::pg_lsn; -- wait until true
    This is exactly what the measurement's fourth row ran. The cost is a short wait on the reads that need it, and the session must carry a position.
  • Monotonic reads: once a user has seen some state, they never see an older one. Fix: send each user's reads to the same replica (hash the user id), as in the animation.
  • Consistent prefix reads: if writes happened in an order, readers see them in that order. In the chat, Ben asks "lunch?" and Ana answers "yes". If the two messages are stored on different machines with different lag, a third user can see "yes" before "lunch?". Fix: keep things that are causally related (one chat's messages) on the same partition, so one log orders them; the general tool is causal ordering.

Failover: when the leader dies

If the leader dies, a follower must be promoted to leader and clients must switch to it: failover. Done by hand it takes minutes; done automatically it is fast and dangerous, for three reasons:

  1. Is it really dead? Only a timeout says so (the four silences above). A leader that was merely slow or cut off comes back still believing it is the leader: two leaders accepting writes, split brain. Preventing this is what consensus and fencing are for.
  2. Lost writes. With asynchronous replication, the promoted follower may lack the last writes the old leader confirmed. Those confirmed writes are gone, and if the old leader returns its extra writes conflict with the new history.
  3. Across regions. GitHub's 2018 outage is all three in one: 43 seconds of partition, automatic promotion of the other coast's replicas, writes on both sides, and a 24-hour repair because GitHub "chose data integrity" over a fast fail-back (GitHub). Afterwards it stopped automatic promotion across regions.

In practice, Postgres itself never promotes anything; tools such as Patroni do it. Patroni "supports a variety of distributed configuration stores like ZooKeeper, etcd, Consul or Kubernetes" (Patroni 4.1 documentation): consensus-backed stores that decide which single node holds the leader key at any moment. Managed services (Amazon RDS Multi-AZ, Cloud SQL) do the same internally.

Multi-leader: writes in several places

With users on several continents, you may want a leader in each region so writes do not cross an ocean. Each leader accepts writes and replicates them to the others. The price is write conflicts: Ana renames a chat to "Trip" on her phone (Europe leader) while her laptop renames it to "Holiday" (US leader). Both succeed locally; when the changes meet, something must choose. Options: last write wins (keep the one with the later timestamp; simple, silently discards the other, and clocks can lie), merge both values, ask the user, or use data types designed to merge automatically (CRDTs, conflict-free replicated data types: counters, sets and text that merge the same way whatever the order). Avoid multi-leader unless you need it; the usual trick is to route all writes for one item (one user, one chat) to one "home" leader, which avoids most conflicts.

Leaderless: any replica takes writes

Amazon's Dynamo paper (2007) made the third style famous: no leader at all. The client (or a coordinator acting for it) sends each write to several replicas and each read to several replicas, and counts answers. Cassandra, Riak and ScyllaDB work this way. Its central idea, the quorum, is the next section.

Quorums: N, R and W

In a leaderless system each piece of data is stored on N replicas. A write is sent to all N and counts as successful once W of them confirm. A read asks replicas and waits for R answers, then takes the newest version among them (every value carries a version). The rule that makes this work is one line:

R + W > N
N
replicas that hold each item
W
replicas that must confirm a write
R
replicas a read must hear from

If R + W > N, every read set and every write set share at least R + W − N replicas, so at least one replica the read hears from has the latest successful write. This overlapping set is a quorum. Amazon's Dynamo paper: "The common (N,R,W) configuration used by several instances of Dynamo is (3,2,2)" (DeCandia et al., SOSP 2007). Try it; the read is drawn picking the worst replicas it could.

The knobs trade against each other: lower W makes writes faster and keeps them working with more replicas down (N − W may be down), lower R does the same for reads (N − R). Cassandra exposes this per query as consistency levels: "QUORUM: A majority (n/2 + 1) of the replicas must respond", ONE, ALL, LOCAL_QUORUM (a majority in the local data centre) and others, and its docs call them "a version of Dynamo's R + W > N consistency mechanism" (Apache Cassandra docs, Dynamo architecture). Replicas that missed a write catch up by read repair (a read that sees an old version writes the new one back) and by anti-entropy: background comparison of Merkle trees, hash trees that let two replicas find differing ranges without sending all the data (Dynamo, Table 1).

R + W > N is not the same as strong consistency
It guarantees overlap, not linearizability (defined below). Abadi: by increasing R + W such systems "gain more consistency at the expense of latency (although they cannot achieve full consistency as defined by Gilbert and Lynch, even if R + W > N)" (Abadi, IEEE Computer, Feb 2012). The gaps: two concurrent writes, settled by timestamps (Cassandra uses "a simpler last-write-wins model where every mutation is timestamped", so a skewed clock picks the winner); a write that reached fewer than W replicas reports failure but is not rolled back where it landed; and a sloppy quorum, Dynamo's choice under failures, accepts writes on replicas outside the usual N ("hinted handoff") so the overlap no longer holds. Discord, which read and wrote "with quorum consistency level" on Cassandra, also found that one slow replica in a busy partition slowed everyone ("discord-2023" in the parent's Case files).

Partitioning: splitting the data

Replication copies everything everywhere, so it cannot help when the data or the write rate outgrow one machine. Partitioning (sharding; each piece is a partition or shard) gives each machine a slice. Each slice is usually also replicated, so a real cluster is partitioned and replicated: DynamoDB keeps every partition as three replicas in three availability zones (Elhemali et al., USENIX ATC 2022). The design question is which machine holds which key.

By key range or by hash

  • Key-range partitioning: shard 1 holds users A to F, shard 2 G to M, and so on, like volumes of an encyclopedia. Range queries ("all messages in this chat between Monday and Friday") hit one shard. Danger: keys that arrive in order all land on the same shard; partitioning messages by timestamp sends every new message to the last shard.
  • Hash partitioning: run the key through a hash function and use the hash to pick the shard. Keys spread evenly whatever their pattern. Cost: range queries must ask every shard.

The obvious way to turn a hash into a shard is hash(key) mod N. It is a trap: add one machine (N to N + 1) and almost every key's remainder changes, so almost all data must move. Consistent hashing fixes this. Place each machine at several random points on a circle of hash values; a key belongs to the first machine point clockwise from its own hash. Adding a machine only takes over the arcs just before its points, about 1/(N + 1) of the keys. Each machine gets many points (virtual nodes, Dynamo's "tokens") so its share is even. More is not free: the Cassandra docs warn that every token adds ring neighbours, so "The more tokens you have, the higher the probability of an outage" when several machines fail at once (Cassandra docs). Hot keys, rebalancing, and finding the right shard

  • Hot keys. Hashing spreads keys, not load. One celebrity user, or one busy Discord channel, is one key on one shard. Discord's fix was to stop sending the same query a thousand times (request coalescing) before buying a bigger database ("discord-2023" in Case files). Other fixes: add a random suffix to a hot key so it spreads over several shards (reads must then gather all of them), or cache it.
  • Rebalancing. Rather than consistent hashing, many databases create many more partitions than machines from day one and move whole partitions when machines are added: Instagram created thousands of logical shards on a few Postgres servers in 2012, and Notion split its Postgres into 480 logical shards on 32 physical databases in 2021, choosing 480 because it divides evenly over 40 or 48 hosts later ("insta-2012" and "notion-2021" in the parent's Case files). Moving data is slow and loads the network, so it is throttled and usually triggered by a person or a careful controller.
  • Secondary indexes. Looking a chat up by id is one shard; "all chats mentioning Lisbon" is all of them. A local index (one per shard) makes writes cheap and reads ask every shard; a global index is itself partitioned and kept up to date asynchronously. In DynamoDB, "All reads from GSIs and streams are eventually consistent" (DynamoDB read consistency).
  • Routing. Someone must know the map from key to shard: the client library (Cassandra drivers), a routing tier (Vitess, MongoDB's mongos), or any node that forwards. The map itself must be agreed, which is a job for consensus.

Choose the shard key so the common queries hit one shard and related data lands together: for the chat product, by user (or by workspace, as Notion did). It is among the most expensive decisions to change later.

Consistency models: what a reader is allowed to see

"Consistent" is used loosely. A consistency model is a precise promise: Jepsen defines it as "a safety property which declares what a system can do. Formally, a consistency model defines a set of histories that a system can legally execute" (Jepsen, Consistency). A history is what clients observed: who called which operation, when it started, when it returned, and what it returned. To make each model concrete, take one value x (say, the title of Ana's chat, encoded as a number), initially 0, and look at histories drawn as bars on a time line: each bar is one operation, from the moment the client sent it to the moment the answer came back.

History A: a stale read after the write finished

Client 1 writes 1 and gets "done". Afterwards client 2 reads 0, and later 1. This is the replica lag from the animation.

History B: a new value, then an old one

A slow write of 1 is in progress. Client 2 reads 1; after that read returns, client 3 reads 0.

Now the models, strongest first. Each one is a rule for which histories are allowed:

  • Linearizability (Herlihy and Wing, 1990): "every operation appears to take place atomically, in some order, consistent with the real-time ordering of those operations: e.g., if operation A completes before operation B begins, then B should logically take effect after A" (Jepsen, Linearizability). Picture each operation taking effect at one instant somewhere inside its bar. History A fails (the write ended before the read began, so the read must see 1). History B fails too, and it is the subtle one: both reads overlap the write, so either answer alone would be fine, but once client 2 has seen 1 and returned, nobody may see 0 afterwards. Linearizability is what makes a system behave like one copy; it is what you need for a lock, a leader, a unique username or "never spend the same credit twice". It is the "strong consistency" of the parent page.
  • Sequential consistency (Lamport, 1979): all operations appear in one total order that every client agrees on, and each client's own operations are in that order in the order it issued them, but the order need not match real time. Histories A and B both pass: put client 2's read of 0 before the write. A client may be behind, but everyone sees the same story.
  • Causal consistency: operations that are causally related must be seen by everyone in that order; unrelated (concurrent) ones may be seen in different orders by different clients. Jepsen's example is a chat: Attiya asks "shall we have lunch?", Barbarella says "yes" and Cyrus "no"; "no participant ever observes 'yes' or 'no' prior to the question 'lunch?'", but they may disagree on the order of "yes" and "no" (Jepsen, Causal). Its great property: it can stay available during a partition, as long as each client sticks to the same server.
  • Eventual consistency: if writes stop, all copies eventually return the same value. It promises nothing about what you read meanwhile, not even your own write. DynamoDB's default read is this: "the responses might not reflect the results of a recently completed write operation" (DynamoDB read consistency).

Between causal and eventual sit the session guarantees from the replication section: read-your-writes, monotonic reads, and two more (monotonic writes: one client's writes are applied in order; writes follow reads: a write made after reading something is ordered after it). They are cheap and they fix most of what users notice.

Try it. The Consistency lab tab has seven histories (these two and five more) with every model's verdict, checks linearizability and sequential consistency by brute force, and lets you change what each read returned to see the verdicts flip.

Linearizable is not serializable

Two words sound alike and are different. Linearizability is about single operations on one object and respects real time. Serializability is about transactions (groups of reads and writes on many objects): the result equals some one-at-a-time order of the transactions, but not necessarily the real-time order. Strict serializability is both: Jepsen describes it as "serializability's total order of transactional multi-object operations, plus linearizability's real-time constraints" (Jepsen, Strong Serializability). Spanner calls its version external consistency (below). Transactions get their own short section.

Correction to the old page
The old page grouped "Sequential / causal: causally related ops are ordered everywhere; concurrent ops may interleave differently". That sentence describes causal consistency only. Sequential consistency is stronger: everyone sees the same single order, concurrent operations included ("operations appear to take place in some total order, and that that order is consistent with the order of operations on each individual process", Jepsen, Sequential). The lab's history "Two observers disagree" separates them: allowed under causal, forbidden under sequential. The old page's "Causal+ is the sweet spot for geo-replicated data" is an opinion; it is the argument of the COPS paper that introduced causal+ (causal plus convergence) for wide-area stores (Lloyd et al., SOSP 2011), and Jepsen notes "Most 'causally consistent' systems actually provide these stronger properties, such as RTC or causal+".

CAP, stated correctly, and PACELC

CAP is the most quoted and most misquoted result in the field. Eric Brewer conjectured it in 2000; Seth Gilbert and Nancy Lynch proved it in 2002 (Gilbert and Lynch, 2002). Their theorem, in their terms: in an asynchronous network where messages can be lost, it is impossible to implement a read/write object that guarantees both

  • Consistency, meaning precisely linearizability ("atomic" consistency), and
  • Availability, meaning every request received by a non-failing node gets a response (not "the system is mostly up"),

in all executions, including those where the network Partitions. The proof is short: split the replicas into two groups that cannot talk; a write lands in one group; a read arrives in the other. To be available the second group must answer, and it cannot know the new value, so it answers with the old one and breaks linearizability. To stay linearizable it must refuse, and so it is not available.

What CAP does not say
  • Not "pick two of three". You cannot opt out of partitions; they happen. The real statement: during a partition, a system that keeps linearizability must refuse some requests. Brewer himself: "you only need forfeit something during an actual partition" (Brewer, 2017).
  • Its C and A are narrow. A system that is neither linearizable nor CAP-available (most real databases in some configuration) is not "breaking" CAP; CAP simply says nothing about it. Causal consistency can be available under partition; linearizability cannot.
  • "CA" is a label for "we assume partitions are rare". Brewer on Spanner: "It is technically a CP system", yet "effectively CA" because Google's network makes partitions so rare that users do not write code for them; he cites Chubby at "an average availability of 99.99958%" and Spanner incidents with the network category "under 8%".
  • It says nothing about latency, which is what you trade every day. That is PACELC.

PACELC (Daniel Abadi, 2012): if there is a Partition, choose Availability or Consistency; Else, in normal running, choose Latency or Consistency, because keeping copies in step means waiting for them (Abadi, IEEE Computer, Feb 2012). Abadi's own classification (2012, of the default settings):

ClassMeaningAbadi's examples (2012)
PA/ELGive up consistency both under partition and for speed"The default versions of Dynamo, Cassandra, and Riak"
PC/ECNever give up consistency; pay in availability and latency"Fully ACID systems such as VoltDB/H-Store and Megastore", BigTable and HBase
PA/ECConsistent normally, available under partitionMongoDB (as of 2012)
PC/ELFast normally; under partition it does not reduce consistency furtherYahoo's PNUTS

In our product: Ana's chat list is PA/EL territory (serve from a nearby replica, slightly stale is fine). Her credit balance is PC/EC (the spend must go through one linearizable place, and if that place is unreachable the spend is refused). One product, two choices, one per invariant.

Consensus: making machines agree

Why it is needed

Several jobs above quietly assumed that the machines agree on something: which node is the leader (or failover makes two), which machine owns which shard, the order of writes in the log. Consensus is the problem of getting several machines to agree on one value, or one sequence of values, such that: everyone who decides decides the same thing; the decided value was actually proposed by someone; and the group keeps deciding as long as a majority is up and can talk.

Why a majority? Two majorities of the same group always share at least one member, so two conflicting decisions can never both collect one. With 2f + 1 machines you survive f failures: 3 machines survive 1, 5 survive 2. An even size buys nothing (4 machines still survive only 1, because the majority is 3). This is the quorum idea again, used for agreement rather than for reading values.

It is harder than it sounds. In 1985 Fischer, Lynch and Paterson proved that in a fully asynchronous network no deterministic algorithm can guarantee to reach agreement if even one process may crash (FLP, JACM 1985): you cannot tell a crashed process from a slow one. Practical algorithms therefore promise safety always (never two different decisions) and progress only when the network behaves for long enough, using timeouts to suspect failures. Paxos (Lamport) was the first widely used one; Raft (2014) was designed to give the same result while being easier to understand and build: "It produces a result equivalent to (multi-)Paxos, and it is as efficient as Paxos", and "Results from a user study demonstrate that Raft is easier for students to learn than Paxos" (Ongaro and Ousterhout, USENIX ATC 2014).

Raft, step by step

Raft keeps a replicated log: an ordered list of commands that every machine applies in the same order, so every machine computes the same state (a key-value map, the cluster's configuration). Everything below quotes or follows the paper.

  1. Roles. Each server is a follower, a candidate or the leader. Normally there is one leader and the rest are followers. Clients talk to the leader.
  2. Terms. "Time is divided into terms of arbitrary length, numbered with consecutive integers. Each term begins with an election". A term is a logical clock: every message carries the sender's term, and a server that sees a higher term immediately adopts it and steps down to follower. A leader from an old term is therefore ignored as soon as it talks to anyone.
  3. Heartbeats and the election timeout. The leader sends periodic heartbeats (empty AppendEntries messages). A follower that hears nothing for its election timeout assumes the leader is gone, adds one to its term, becomes a candidate, votes for itself and asks the others for votes (RequestVote). The timeout is random, "chosen randomly from a fixed interval (e.g., 150–300ms)", so usually one follower times out first and wins before others start.
  4. Voting. Each server votes for at most one candidate per term, first come first served. A candidate with votes from a majority becomes leader. This gives the first guarantee: "Election Safety: at most one leader can be elected in a given term." If the vote splits, nobody wins, the term ends, and new random timeouts break the tie.
  5. The election restriction. A server refuses its vote to a candidate whose log is less up to date than its own (compare the term of the last entry first; if equal, the longer log wins). Since a committed entry is on a majority, and a winner needs a majority of votes, every new leader already has every committed entry ("Leader Completeness").
  6. Log replication. A client command becomes a new entry (index, term, command) appended to the leader's log and sent to followers with AppendEntries. Each AppendEntries also carries the index and term of the entry just before the new ones; "If the follower does not find an entry in its log with the same index and term, then it refuses the new entries." The leader then backs up and resends earlier entries until the follower's log matches, overwriting a follower's conflicting uncommitted entries. Result: "if two logs contain an entry with the same index and term, then the logs are identical in all entries up through the given index."
  7. Commit. Once an entry from the leader's current term is stored on a majority, it is committed: it will never be lost or changed. The leader applies it, answers the client, and tells followers the new commit index in later messages. One subtle rule: a leader never counts replicas to commit an entry from an older term (the paper's Figure 8 shows such an entry can still be overwritten); it commits its own term's entry, which commits everything before it.
  8. Reads. A read served by a leader that has silently been replaced returns stale data. Raft's fix: a new leader first commits a blank entry, and "the leader exchange[s] heartbeat messages with a majority of the cluster before responding to read-only requests" (or relies on a time-based lease, if clocks are trusted). Jepsen found etcd 0.4.1 got this wrong in 2014: it "exhibited stale reads by default" because it "performed reads on any leader, locally"; etcd 3.0 "made linearizability the default for all operations except for watches" (Jepsen, etcd 3.4.3, 2020-01-30).
Do it yourself. The Raft lab tab runs a five-server Raft cluster in your browser: a guided tour (an election, a write committing, the leader crashing, a re-election, a partitioned old leader whose writes never commit) and a free mode where you crash, restart and isolate servers and send writes.

How fast, measured

The paper crashed the leader of a five-server cluster repeatedly (broadcast time about 15 ms). With timeouts of 150 to 150 ms (no randomness), elections "consistently took longer than 10 seconds" because of split votes; "Adding just 5ms of randomness helps significantly, resulting in a median downtime of 287ms"; with 12 to 24 ms timeouts "it takes only 35ms on average to elect a leader (the longest trial took 152ms)". The timing rule they give is broadcastTime ≪ electionTimeout ≪ MTBF (mean time between failures), with broadcast "0.5ms to 20ms, depending on storage technology", so "the election timeout is likely to be somewhere between 10ms and 500ms". Production systems are more conservative: etcd's defaults are a 100 ms heartbeat and a 1,000 ms election timeout.

What consensus costs
Every committed write waits for a round trip to a majority plus a disk flush on each (a durable log entry). Throughput is limited by one leader. A minority side of a partition cannot write at all (that is CAP's "C over A"). So you put small, critical state through consensus (who is leader, which shard lives where, configuration, locks), and keep bulk data in systems that use consensus only to pick a leader. etcd stores "a small volume of infrequently-updated state (by default, up to 8 GB)" (Jepsen, 2020). Never write your own consensus; use etcd, ZooKeeper or Consul, or a database that embeds Raft or Paxos.

Leader election, leases and fencing tokens

Most systems do not run consensus on every write. They use it to elect one leader, then let that leader work alone. To make "one leader" survive crashes, leadership is a lease: permission that expires after a fixed time (the TTL, time to live) unless renewed. If the leader dies, the lease runs out and someone else takes it. DynamoDB works this way per partition: its replication group "uses Multi-Paxos for leader election and consensus", and "Once elected leader, a replica can maintain leadership as long as it periodically renews its leadership lease" (Elhemali et al., USENIX ATC 2022).

The trap is the pause from the network section. A lease holder that freezes does not know its lease ran out. When it wakes, it carries on writing as if it were still the leader. Martin Kleppmann's 2016 analysis of the Redlock algorithm walks through this with a garbage-collection pause and gives the fix (Kleppmann, How to do distributed locking, 2016-02-08): every time the lock is granted, the lock service hands out a number that only grows, a fencing token, and the storage rejects any write carrying a token lower than one it has already seen: "the storage server remembers that it has already processed a write with a higher token number (34), and so it rejects the request with token 33." Real evidence that this matters:

  • Jepsen, etcd 3.4.3 (2020-01-30): "etcd locks are fundamentally unsafe". With "two-second leases TTLs, five concurrent processes, and process pauses every five seconds, we could reliably induce the loss of ~18% of acknowledged updates", and short TTLs of 1 to 3 seconds "generally failed to provide mutual exclusion after only a few minutes of testing, even in healthy clusters". The fix Jepsen names: "users can use the revision of their lock key as a globally ordered fencing token" (Google's Chubby calls these sequencers; in ZooKeeper, Kleppmann suggests the zxid).
  • AWS, 19 October 2025: two DynamoDB DNS automation workers raced; a slow one had checked its plan was newer than the live one, but "The check that was made at the start of the plan application process ... was stale by this time", and it overwrote a newer plan, leaving the regional endpoint with an empty DNS record for hours (AWS summary; "aws-2025-dns" in the parent's Case files). A check made on old information is not a check; the store itself must reject the older write, which is exactly what a fencing token does.
Correction to the old page
The old page advised taking a lease from etcd or ZooKeeper and to "keep the lease TTL well above GC pauses". A long TTL makes the failure rarer, not impossible: a pause can always outlast it, and Jepsen showed mutual exclusion failing even "in healthy clusters". The old page's next sentence is the real fix and is kept: fence every write with a monotonically increasing token, checked by the storage. Jepsen adds that this gives isolation but "does not guarantee atomicity": a holder that dies halfway through a multi-step update still leaves a half-done state.

Kleppmann's other useful distinction: a lock for efficiency (stop two workers doing the same job twice; an occasional double is harmless) can be simple, even a single Redis key; a lock for correctness (two writers would corrupt data) needs consensus plus fencing.

Transactions and isolation, in brief

A transaction groups several reads and writes so they succeed or fail together (atomicity) and so concurrent transactions do not see each other's half-done work (isolation). The I in ACID comes in levels, and the default is rarely the strongest:

LevelWhat it preventsWhat still gets through
Read committedReading another transaction's uncommitted writesTwo reads in one transaction can see different data; lost updates
Snapshot isolationEach transaction reads one consistent snapshot; concurrent writes to the same row conflictWrite skew: two transactions read the same rows, each writes a different row, both commit
SerializableEverything: same result as running one transaction at a timeNothing, at the price of aborts and retries under contention

Write skew in our product: a team shares a credit pool split over two rows, and the rule is "spend only if the pool total is at least the cost". Two members each spend 60 from a pool of 100 at the same moment; each transaction reads total 100, each debits its own row, both commit, and the pool is at −20. Snapshot isolation allows this; serializable does not. Postgres's default is read committed ("Read Committed is the default isolation level in PostgreSQL", PostgreSQL 18 docs), and its "Repeatable Read" level "actually provides Snapshot Isolation" (Jepsen, below).

Isolation levels are where tested reality and documentation most often disagree. Jepsen's findings, each dated:

  • PostgreSQL 12.3 (2020-06-12): "transactions with serializable isolation on a single PostgreSQL instance were not, in fact, serializable" (a G2-item anomaly), a bug the PostgreSQL team patched for the next minor release, on 13 August 2020 (Jepsen).
  • MySQL 8.0.34 (2023-12-19): "MySQL's Repeatable Read still allows G2-item, G-single, and lost update", and "AWS RDS MySQL clusters routinely violate Serializability" (Jepsen).
  • Amazon RDS for PostgreSQL 17.4 (2025-04-29): multi-AZ clusters "violate Snapshot Isolation"; "Healthy clusters occasionally allow Long Fork". The cause, found afterwards: the primary makes transactions visible in the order of an in-memory lock, while "Secondaries, however, make transactions visible based on their order in the Write-Ahead Log (WAL)", so a replica can show two transactions in the opposite order to the primary (Jepsen). Replication lag is not the only way a replica disagrees.

Transactions across machines

When one transaction touches two partitions, or a database and a message queue, no single machine can commit it. Two-phase commit (2PC) uses a coordinator: phase 1 asks every participant "can you commit?" (each makes the change durable but invisible and promises to obey); phase 2 tells all to commit, or all to abort. Its weakness: a participant that has said yes must wait, holding locks, until it hears the decision, so a dead coordinator blocks everyone. Spanner's answer is to make each participant and the coordinator a Paxos group, so none of them is a single machine: "Running two-phase commit over Paxos mitigates the availability problems" (Corbett et al., OSDI 2012). The everyday version of this problem is the dual write: save a row in Postgres and publish an event to Kafka; a crash between the two leaves them disagreeing. The standard fix, the transactional outbox, is taught in Queues, streams and async work.

Clocks: ordering events without a shared time

Last-write-wins, leases, "which happened first?" all need an order of events across machines. Wall clocks cannot give it reliably (section 2). There are two ways out: give up physical time and track cause and effect (logical clocks), or keep physical time but bound its error (hybrid and bounded clocks).

Lamport clocks

Leslie Lamport (1978) defined happened-before (→): a → b if a came before b on the same machine, or a is sending a message and b is receiving it, or there is a chain of these. If neither a → b nor b → a, the events are concurrent: neither could have influenced the other. A Lamport clock is one counter per machine: add one at every event; put the counter on every message; on receiving, set yours to max(yours, received) + 1. It satisfies Lamport's "Clock Condition. For any events a, b: if a→b then C(a) < C(b)", and he points out the converse fails: "we cannot expect the converse condition to hold as well" (Lamport, CACM 1978). A smaller number does not mean "happened before"; it may be concurrent.

Vector clocks

A vector clock keeps one counter per machine: add one to your own entry at every event; on receiving, take the element-wise maximum, then add one to your own. Now a → b exactly when a's vector is ≤ b's in every entry (and differs somewhere); if each is larger somewhere, they are concurrent. The cost is one number per participant on every message. Dynamo used vector clocks to keep concurrent versions of an item side by side for the application to merge (the shopping cart that keeps both additions); Cassandra chose last-write-wins timestamps instead (the Cassandra docs above). Hybrid logical clocks and bounded clocks

  • Hybrid logical clocks (Kulkarni et al., 2014) pair the wall-clock time with a small logical counter: they capture causality like a Lamport clock while staying close to real time, and fit in a 64-bit timestamp ("HLC captures the causality relationship like logical clocks ... Moreover HLC fits in to 64 bits NTP timestamp format", Kulkarni et al.). CockroachDB uses them and still needs synchronised clocks: when a node's clock is off from at least half the others "by 80% of the maximum offset allowed, it spontaneously shuts down. This offset defaults to 500ms", with 250 ms recommended for new clusters (CockroachDB operational FAQs).
  • TrueTime (Google Spanner) returns not a time but an interval, [earliest, latest], guaranteed to contain the true time, from GPS receivers and atomic clocks in every data centre. In 2012 the uncertainty ε was "typically a sawtooth function of time, varying from about 1 to 7 ms over each poll interval" (the 6 ms climb is the drift budget above). Spanner then waits out the uncertainty before making a commit visible (commit wait), so any transaction that starts after another finished gets a larger timestamp. That is how it offers external consistency, under which "the system behaves as if all transactions run sequentially" (Spanner docs, TrueTime and external consistency). Better clocks mean shorter waits.
  • Bounded clocks for everyone. In November 2023 AWS announced "microsecond-level clock accuracy on supported Amazon EC2 instances" and ClockBound, an open-source daemon that reports the time with an error bound, TrueTime-style (AWS Compute Blog, 16 Nov 2023).

A Postgres replica gotcha worth knowing
A long query on a standby can conflict with changes the primary has made (for example, rows it vacuumed away). By default the standby waits up to max_standby_streaming_delay, "The default is 30 seconds", and then cancels the query; hot_standby_feedback ("The default value is off") lets the standby ask the primary to keep those rows, at the cost of bloat on the primary (PostgreSQL 18 docs). Analytics on a read replica is the classic way to meet this.

Common mistakes

Each one has caused real outages or data loss; open one to see why and what to do instead.

Treating a timeout as "it failed"
A timeout means "unknown". In the "reply lost" case the write happened, and a blind retry does it twice. Make retried writes idempotent (an idempotency key, or "set to X" instead of "add X"); Jepsen found the official etcd Java client retrying non-idempotent requests in 2024. Retry policy itself: Reliability engineering.
Reading from a replica right after a write
Measured above: 99.65% of immediate replica reads missed the write, on one laptop. Read the user's own recent changes from the leader, or wait for the replica to reach their write position.
Assuming synchronous replication gives read-your-writes
Postgres synchronous_commit = on waits until the standby has flushed the WAL, not applied it: 1 stale read in 2,000 in the measurement. You need remote_apply (which waits for replay on every commit) or a client-side position wait.
"We use quorums (R + W > N), so we are strongly consistent"
Overlap is not linearizability: concurrent writes settled by timestamps, partial writes that are not rolled back and sloppy quorums all break it (Abadi). If you need linearizable behaviour, use a system built on consensus, or a compare-and-set that goes through one (Cassandra's lightweight transactions).
Sharding with hash(key) mod N
Adding one machine to four moves 79.6% of keys in the widget above. Use consistent hashing, or many fixed logical shards moved whole (Instagram, Notion).
A shard key that sends new data to one place
Partitioning by time or by an increasing id sends every new write to the newest shard. Partition by something with many independent values that your queries also use (user, workspace, chat).
A distributed lock without a fencing token
Leases expire during pauses; the old holder wakes up and writes. A longer TTL only makes it rarer. Have the storage check a monotonically increasing token (the lock key's revision in etcd, the zxid in ZooKeeper), or make the protected update a conditional write in the same store.
Ordering events across machines by their wall clocks
Clocks drift and can step backwards; last-write-wins then keeps the write from the machine whose clock runs fast, not the latest. Use a single leader's log order, logical clocks, or a database that bounds clock error (TrueTime, CockroachDB's max offset). For durations and timeouts, always use the monotonic clock.
"CAP: pick two", or calling a system "CA"
Partitions are not optional. The real choice applies only during a partition, and the everyday trade is latency against consistency (PACELC). Say what the system does when a partition happens.
Four (or six) consensus nodes "for extra safety"
A majority of 4 is 3, so 4 nodes survive one failure, like 3, while every write waits for one more node. Use 3 or 5; more members also make every commit slower.
Writing your own leader election or consensus
Jepsen has found bugs in nearly every implementation it tested, including Raft-based ones built by experts (Redis-Raft: 21 issues). Use etcd, ZooKeeper or Consul, or a database that does it internally.
Putting bulk data or high write rates through a consensus store
etcd is for small, critical, rarely changing data (8 GB by default); every write is a majority round trip and a disk flush. Store data in a database; store the pointer, the leader or the configuration in etcd.
Assuming the default isolation level is serializable
Postgres defaults to read committed, and "repeatable read" in Postgres is snapshot isolation, which allows write skew. Ask for SERIALIZABLE where an invariant spans rows, and be ready to retry aborted transactions.
Automatic failover across regions with asynchronous replication
GitHub 2018: a 43-second partition became 24 hours of repair, because both sides took writes. Keep automatic failover inside a region (where synchronous replication is cheap) and make cross-region promotion a deliberate decision.

Glossary

Partial failure: some machines or links work, others do not, and you cannot be sure which.
Timeout: giving up after a set wait; it does not tell you what failed.
Network partition: two groups of working machines that cannot reach each other.
NTP: the protocol machines use to correct their clocks; it can step a clock backwards.
Time-of-day clock: the date and time; can jump; roughly comparable across machines.
Monotonic clock: only moves forward; for durations on one machine.
Replication, replica: keeping copies of the same data on several machines; one copy.
Leader / follower: the replica that takes writes / the ones that replay its log.
Log: the ordered list of changes (Postgres: the WAL) that followers replay.
Asynchronous / synchronous replication: confirm a write before / after a follower has it.
Replication lag: how far a follower is behind the leader.
Read-your-writes: a user always sees their own writes.
Monotonic reads: a user never sees an older state after a newer one.
Consistent prefix reads: writes are seen in the order they happened.
Failover, promotion: making a follower the new leader when the leader dies.
Split brain: two nodes both acting as leader.
Write conflict: two leaders accepted different changes to the same item.
CRDT: a data type whose copies merge automatically in any order.
Quorum: enough replicas that any two such sets overlap (R + W > N, or a majority).
Consistency level: Cassandra's per-query choice of R or W (ONE, QUORUM, ALL...).
Partitioning (sharding): giving each machine a slice of the data.
Key-range / hash partitioning: slices by ranges of the key / by its hash.
Consistent hashing: keys and machines on a hash circle; adding a machine moves about 1/(N+1) of keys.
Virtual node: one of many points a machine takes on the circle.
Hot key: one key with far more traffic than others.
Rebalancing: moving data when machines are added or removed.
Shard key: the value that decides which partition holds a row.
Consistency model: the set of histories a system may produce.
History: the operations clients saw, with start, end and result.
Linearizability: behaves like one copy; respects real-time order.
Sequential consistency: one order everyone agrees on, not tied to real time.
Causal consistency: causes are seen before effects; concurrent writes in any order.
Eventual consistency: copies agree once writes stop.
Session guarantees: read-your-writes, monotonic reads and writes, writes follow reads.
Serializability: transactions behave as if run one at a time.
Strict serializability: serializable and in real-time order.
PACELC: under partition, availability or consistency; else, latency or consistency.
Consensus: machines agreeing on one value or one log, tolerating failures.
Term: Raft's election number; a higher term always wins.
Election timeout: how long a Raft follower waits for the leader before running.
Committed (Raft): stored on a majority; never lost.
Lease: permission that expires unless renewed.
Fencing token: a number that grows with each lock grant; storage rejects older ones.
Transaction: reads and writes that succeed or fail together, isolated from others.
Two-phase commit: prepare everywhere, then commit everywhere, via a coordinator.
Happened-before, concurrent: could have influenced / could not.
Lamport clock: one counter; respects happened-before but cannot detect concurrency.
Vector clock: one counter per machine; detects concurrency.
Hybrid logical clock: wall time plus a logical counter.
TrueTime, commit wait: time as a bounded interval; wait out the uncertainty before commit.

Raft lab: a five-server cluster you can break

A real Raft implementation (following the paper's Figure 2) runs in your browser: five servers, random election timeouts of 150 to 300 ms, heartbeats every 50 ms, message delays of 12 to 24 ms, all in simulated time and slowed down so you can watch. The guided tour walks through elections, commits, a crash, a restart and a network split, one step at a time. Free mode lets you crash, restart and isolate servers and send writes yourself. Each step's mechanism is explained in the Reading tab, Consensus: making machines agree.

Logs

One row per server; each cell is a log entry (its term above, its command below). Green cells are committed on that server; outlined cells are not (yet).

What just happened

The model is checked by src/check_raft.mjs: 300 random runs of crashes, restarts, splits and writes, asserting after every event that no term has two leaders and that no committed entry ever differs between servers or changes, and that a write commits once the network heals (0 failures). Simplifications, stated plainly: no log compaction or snapshots, no membership changes, a client write goes to the newest reachable leader, and a restarted server forgets its commit index until the leader tells it (as in the paper, where it is volatile state).

Consistency lab: which models allow this history?

Each history is what clients observed on one register x (initially 0): a bar per operation, from when the client sent it to when the answer came back. w(1) writes 1; r→0 is a read that returned 0. For each consistency model the lab says whether the history is allowed and why. Models are explained in the Reading tab, Consistency models.

Try: start with "A stale read after the write finished", then "A new value, then an old one" (the subtle one). Then tap any read bar to change what it returned and watch the verdicts flip.

How the verdicts are computed
Linearizable and sequentially consistent are checked by brute force in your browser: try every ordering of the operations, keep those that respect each client's own order (and, for linearizability, real time: if one operation ended before another began, it must come first), and accept if in one of them every read returns the latest preceding write. With at most six operations that is at most 720 orderings. src/recompute.py runs the same check in Python for every preset. Causal, read-your-writes and eventual verdicts are written by hand for the presets, with the reasoning shown; once you edit a read they show "?" rather than guess.
