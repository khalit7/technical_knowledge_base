12. Memory cgroups and the OOM killer: why a container dies

On a shared host each job (container, pod, Slurm step) gets a memory budget. A cgroup v2 memory controller charges every page a process in the group allocates to the group, and reclaims within the group when it reaches its limit. What is charged: "userland memory - page cache and anonymous memory", kernel structures such as dentries and inodes, and TCP socket buffers ({{cgroup-v2 docs, Memory|https://docs.kernel.org/admin-guide/cgroup-v2.html#memory}}). Four files carry most of it, in each cgroup's directory (/sys/fs/cgroup/ inside a container): memory.current (bytes charged now, page cache included), memory.max (the hard limit: reclaim, then the OOM killer inside the group; docker --memory, a Kubernetes memory limit), memory.events (counters high, max, oom, oom_kill) and memory.stat (the breakdown: anon, file, shmem, ...).

Four real runs at a 512 MiB limit: page cache is given back at the line, anonymous memory and /dev/shm are not

    measured: sampled every 25 ms from inside the container, replayed at the real pace; each scenario starts from the same empty container (src/exp/cg_replay.sh, raw src/raw/cg_*.txt). Predict first: "Page cache only" and "Grow until killed" both reach the line; which one dies? Then play "/dev/shm counts" to the end: the shmem area outlives the killed process.

    The fourth run is the one to remember for data loading: files in /dev/shm are shared memory charged to the cgroup, they survive the process that wrote them, and no process's RSS shows them. DataLoader workers hand batches to the main process through such files; the root's Debug lab case "DataLoader workers run out of /dev/shm" shows the other way it fails (Docker's default 64 MiB /dev/shm), and PyTorch's own README says to raise it "either with --ipc=host or --shm-size" ({{PyTorch README|https://github.com/pytorch/pytorch#docker-image}}).

    Who the OOM killer picks, from the source

    When reclaim fails, oom_badness scores every candidate process ({{mm/oom_kill.c lines 201 to 238|https://github.com/torvalds/linux/blob/v5.10/mm/oom_kill.c#L201}}) and the highest score is sent SIGKILL:

    points = rss + swap + page_tables / 4 KiB + oom_score_adj × ⌊totalpages / 1000⌋
    rss
    resident pages: anonymous, file-mapped and shmem (in pages)
    swap
    pages of this process in swap
    oom_score_adj
    -1000 (never kill) to +1000, per process, in /proc/PID/oom_score_adj
    totalpages
    machine OOM: RAM + swap. cgroup OOM: memory.max + allowed swap ({{mem_cgroup_get_max, line 1690|https://github.com/torvalds/linux/blob/v5.10/mm/memcontrol.c#L1690}})

    In a 1 GiB container with no swap, process A holds 450 MiB (adj 0) and process B 250 MiB but set its own oom_score_adj to 500. The group hits its limit. Who dies?

    totalpages = 262,144 (1 GiB of 4 KiB pages), so adj 500 adds 500 × 262 = 131,000 points, worth 512 MiB of RSS. A scores about 115,200 + 0; B about 64,000 + 131,000 = 195,000. B dies. The root's Debug lab case "Which process the OOM killer picks: oom_score and oom_score_adj" ran exactly this and B was killed. Raising your own adj is allowed; lowering it below its current value needs CAP_SYS_RESOURCE, which a default container lacks (measured: refused).
    The kernel's own number: oom_score reproduced on four processes, and the formula live

    /proc/PID/oom_score shows (1000 + points × 1000 / totalpages) × 2 / 3, always with the machine's RAM + swap ({{fs/proc/base.c lines 549 to 566|https://github.com/torvalds/linux/blob/v5.10/fs/proc/base.c#L549}}).     Kubernetes sets the adj for you by quality-of-service class: Guaranteed -997, BestEffort 1000, Burstable min(max(2, 1000 - (1000 × memoryRequestBytes) / machineMemoryCapacityBytes), 999) ({{node-pressure eviction docs|https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/}}). So when the node runs out, a pod with a small request relative to the node is killed first; when a container exceeds its own limit, its cgroup OOM kills inside it regardless. Requests, limits and the rest of cgroups v2 are the sibling {{Containers and isolation|n:3f05c17b0d0d8156a841e4bf28f11293}}'s.

    What an OOM kill looks like
    No Python exception, no traceback: SIGKILL cannot be caught. The shell says Killed; the exit code is 137 (128 + 9); Kubernetes reports OOMKilled; the kernel log has "Memory cgroup out of memory: Killed process" (dmesg, not readable in an unprivileged container); memory.events counts oom_kill. A Python MemoryError is a different event: an allocation the kernel refused (mode 2, an rlimit, a 32-bit limit), which the root's Debug lab sets side by side.

    cat /sys/fs/cgroup/memory.{current,max,events}; grep -E '^(anon|file|shmem) ' /sys/fs/cgroup/memory.stat; cat /proc/PID/oom_score{,_adj}

    13. VSZ, RSS, PSS, USS: four answers to "how much memory does it use?"

    Shared pages (libraries, the page cache of a mapped file, copy-on-write pages after fork) are resident for several processes at once, so adding up per-process numbers counts them several times. Four measures, from /proc/PID/status and /proc/PID/smaps_rollup:

    VSZvirtual size: every mapped range, touched or not (section 1). Says nothing about memory.
    RSSresident set: every resident page mapped by the process, shared or not. Sums overcount.
    PSSproportional set: each page divided by the number of processes mapping it. Sums are right.
    USSunique set: Private_Clean + Private_Dirty, what you would get back by killing this one process.

    Three processes show 815 MiB of RSS but own 104 MiB: the workers' RSS is almost all inherited Shared_Dirty

    The running job, measured while training (main process and its two fork-started DataLoader workers): the workers' RSS of about 250 MiB each is nearly all Shared_Dirty, the parent's heap and the imported torch, inherited by fork and not yet written. Their USS, what each really adds, is under 9 MiB. Over an epoch, copy-on-write (section 7) turns Shared_Dirty into Private_Dirty, so watch USS per worker, not RSS. Which number a tool reports: ps and top show VSZ and RSS; smem shows PSS and USS; container tools and Kubernetes read the cgroup (memory.current, which also includes page cache), a fifth answer.

    for p in $(pgrep -f train.py); do grep -E '^(Rss|Pss|Private)' /proc/$p/smaps_rollup; done; smem -P train.py
