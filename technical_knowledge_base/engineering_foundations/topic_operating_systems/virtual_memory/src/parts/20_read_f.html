9. Locked and pinned memory: pages that must not move

The problem. Normally the kernel may move a page (compaction, NUMA migration, THP collapse) or write it to swap, because only the page table knows where it is and the table is updated. A device that copies memory by itself (DMA: a GPU, a network card doing RDMA) holds a physical address and does not consult the page table. If the page moves mid-copy, the device reads someone else's data.

Two mechanisms. mlock(addr, len) faults the range in and keeps it resident: never swapped ({{mlock(2)|https://man7.org/linux/man-pages/man2/mlock.2.html}}). Pinning is stronger and kernel-internal: a driver calls pin_user_pages (the FOLL_PIN flavour of get_user_pages, {{pin_user_pages docs|https://docs.kernel.org/core-api/pin_user_pages.html}}) and the pages may not be moved or freed until it unpins them. Both take memory out of what reclaim can use.

The limit measured. Unprivileged locking is capped by RLIMIT_MEMLOCK, which is 64 KiB in a default Docker container:



That ENOMEM ("Cannot allocate memory") is the error an RDMA library or a pinned-memory allocator reports inside a container whose limit was never raised, and it does not mention the limit. Raise it with docker run --ulimit memlock=-1, LimitMEMLOCK=infinity in a systemd unit, or /etc/security/limits.conf; CAP_IPC_LOCK bypasses it.


Pinned memory for GPU copies not run here


cudaHostAlloc / cudaMallocHost "Allocates size bytes of host memory that is page-locked and accessible to the device", with the warning that "allocating excessive amounts of pinned memory may degrade system performance, since it reduces the amount of memory available to the system for paging"; cudaHostRegister page-locks an existing range ({{CUDA runtime API, memory management|https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__MEMORY.html}}). The reason it matters: "when CUDA sends pageable data from CPU to GPU, it must first create a page-locked copy of that data before making the transfer" ({{PyTorch pinned memory tutorial|https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html}}), an extra copy through a staging buffer. In PyTorch:


    

  • DataLoader(pin_memory=True) runs a thread that copies each batch into pinned memory, so x.to("cuda", non_blocking=True) can be an asynchronous DMA that overlaps compute.
    • 

  • Calling t.pin_memory() right before one copy is usually slower than copying directly (it pays the staging copy itself); pin once, reuse.
    • 

  • The tutorial warns that "allocating a large number of tensors or sizable tensors in pinned memory can monopolize a substantial portion of RAM": pinned pages cannot be reclaimed, so the page cache that feeds your data loader shrinks.
    • 

  • Copies from pinned memory with non_blocking=True are asynchronous: modifying the source tensor before the copy finished corrupts the GPU copy.
    • 

  • PyTorch's pinned memory comes from its CachingHostAllocator, which rounds each request up to the next power of two by default, so a 600 MB pinned buffer locks 1 GiB of RAM ({{Memory allocators|n:3f05c17b0d0d81209ae9d856695dc958}} reads the source).
    •

10. Overcommit: promising more memory than exists


The problem. Programs reserve far more than they touch (allocator arenas, thread stacks, sparse arrays, a 1 GiB reservation by PyTorch's allocator). Refusing every reservation that exceeds RAM would waste memory; accepting all means some promise may not be kept. The kernel's choice is vm.overcommit_memory source ({{overcommit-accounting|https://docs.kernel.org/mm/overcommit-accounting.html}}; {{mm/util.c lines 860 to 876|https://github.com/torvalds/linux/blob/v5.10/mm/util.c#L860}}):


ModeRule in 5.10Consequence


0, heuristic (default)refuse one request larger than RAM + swap; accept the restwild requests fail, everything else succeeds; the OOM killer settles the bill


1, always (this VM)accept everythingsparse arrays work; the 64 GiB request below succeeded


2, nevertotal commitments (Committed_AS) may not exceed CommitLimit = RAM × overcommit_ratio% + swap; "In mode 2 the MAP_NORESERVE flag is ignored"allocations fail with ENOMEM instead of later OOM kills; programs that reserve big address ranges fail to start

A private writable 64 GiB mapping succeeded and pushed Committed_AS to about 11.6 times CommitLimit; with MAP_NORESERVE it was not counted at all; malloc(32 GiB) returned a pointer:

Containers cannot change this setting: it is one value for the whole kernel. When it bites: a cluster that sets mode 2 for safety makes large virtual reservations (CUDA's and allocators' address-space reservations, big np.empty scratch buffers) fail at allocation time; read CommitLimit and Committed_AS before blaming the framework.

11. Swap, zswap and memory pressure


ch. 21 Beyond Physical Memory: Mechanisms, ch. 22 Policies


How it works. Anonymous pages have no file to be re-read from, so to reclaim one the kernel writes it to a swap device, replaces the table entry with a not-present entry holding the swap location, and frees the frame. The next access is a major fault: do_swap_page reads it back ({{handle_pte_fault, mm/memory.c line 4377|https://github.com/torvalds/linux/blob/v5.10/mm/memory.c#L4377}}), reading 2page-cluster = 8 neighbouring swap slots at once (vm.page-cluster = 3 here).


What it costs measured. A process that needs 640 MiB in a container limited to 512 MiB with 512 MiB of swap allowed did not die; it ran with about 260 MiB in swap and every pass over its memory took 4 to 5 seconds, the same pass that takes milliseconds when it fits ({{Memory replay|#t-cg}} tab, scenario "Swap allowed"; the root's Debug lab case "Not dead, just slow: the working set spills into swap" has the per-pass numbers). For a training job that is usually worse than being killed: it looks alive, holds its GPUs, and makes no progress.


zswap and zram not run here (neither is built into this kernel). zswap is a compressed cache in front of a swap device: pages being swapped out are compressed into a RAM pool first and written to disk only when the pool is full ({{zswap docs|https://docs.kernel.org/admin-guide/mm/zswap.html}}). zram is a compressed RAM block device used as swap. Both trade CPU for fewer disk reads.


Pressure stall information not run here (not enabled in this kernel). With PSI, /proc/pressure/memory and each cgroup's memory.pressure report the share of time tasks were stalled waiting for memory (some and full, over 10, 60 and 300 s) ({{PSI docs|https://docs.kernel.org/accounting/psi.html}}). It is the best single "is this job memory-starved" signal; systemd-oomd kills on it ({{systemd-oomd|https://www.freedesktop.org/software/systemd/man/latest/systemd-oomd.service.html}}).


swapon --show; vmstat 1   # si/so columns; grep -E 'pswpin|pswpout' /proc/vmstat
