12. Memory cgroups and the OOM killer: what happens at the limit

The problem. On a shared host each job (container, pod, Slurm step) needs a memory budget, and when the budget or the machine runs out, someone must lose. How it works. A cgroup v2 memory controller charges every page a process in the group allocates to the group, and reclaims within the group when it reaches its limit. What is charged: "userland memory - page cache and anonymous memory", kernel structures such as dentries and inodes, and TCP socket buffers ({{cgroup-v2 docs, Memory|https://docs.kernel.org/admin-guide/cgroup-v2.html#memory}}). The files, in each cgroup's directory (/sys/fs/cgroup/ inside a container):

FileMeaning
memory.currentbytes charged now, page cache included
memory.maxhard limit: reclaim, then the OOM killer inside the group (docker --memory, a Kubernetes memory limit)
memory.high"Memory usage throttle limit... Going over the high limit never invokes the OOM killer": the group's tasks are made to reclaim and are put to sleep, up to 2 s per return to user space in 5.10 ({{MEMCG_MAX_HIGH_DELAY_JIFFIES, mm/memcontrol.c line 2466|https://github.com/torvalds/linux/blob/v5.10/mm/memcontrol.c#L2466}}) not run here (Docker 20.10 has no flag for it and the container cannot write its own cgroup)
memory.low, memory.minprotection: below these the group's memory is reclaimed only reluctantly, or never
memory.swap.maxswap allowed (docker --memory-swap minus --memory)
memory.eventscounters: high, max (times the limit forced reclaim), oom, oom_kill
memory.statthe breakdown: anon, file (page cache, includes shmem), shmem, file_dirty, sock, ...
memory.oom.groupif 1, "all tasks belonging to the cgroup or to its descendants are killed together or not at all"

The fourth run is the one to remember for data loading: files in /dev/shm are shared memory charged to the cgroup, they survive the process that wrote them, and no process's RSS shows them. DataLoader workers hand batches to the main process through such files; the root's Debug lab case "DataLoader workers run out of /dev/shm" shows the other way it fails (Docker's default 64 MiB /dev/shm), and PyTorch's own README says to raise it "either with --ipc=host or --shm-size" ({{PyTorch README|https://github.com/pytorch/pytorch#docker-image}}).

Who the OOM killer picks, from the source

When reclaim fails, oom_badness scores every candidate process ({{mm/oom_kill.c lines 201 to 238|https://github.com/torvalds/linux/blob/v5.10/mm/oom_kill.c#L201}}) and the highest score is sent SIGKILL:

points = rss + swap + page_tables / 4 KiB + oom_score_adj × ⌊totalpages / 1000⌋
rss
resident pages: anonymous, file-mapped and shmem (in pages)
swap
pages of this process in swap
oom_score_adj
-1000 (never kill) to +1000, per process, in /proc/PID/oom_score_adj
totalpages
machine OOM: RAM + swap. cgroup OOM: memory.max + allowed swap ({{mem_cgroup_get_max, line 1690|https://github.com/torvalds/linux/blob/v5.10/mm/memcontrol.c#L1690}})

/proc/PID/oom_score shows (1000 + points × 1000 / totalpages) × 2 / 3, always with the machine's RAM + swap ({{fs/proc/base.c lines 549 to 566|https://github.com/torvalds/linux/blob/v5.10/fs/proc/base.c#L549}}). Four processes in a 1 GiB container, the formula against the kernel's number measured:

In a 1 GiB container with no swap, process A holds 450 MiB (adj 0) and process B 250 MiB but set its own oom_score_adj to 500. The group hits its limit. Who dies?

totalpages = 262,144 (1 GiB of 4 KiB pages), so adj 500 adds 500 × 262 = 131,000 points, worth 512 MiB of RSS. A scores about 115,200 + 0; B about 64,000 + 131,000 = 195,000. B dies. The root's Debug lab case "Which process the OOM killer picks: oom_score and oom_score_adj" ran exactly this and B was killed. Raising your own adj is allowed; lowering it below its current value needs CAP_SYS_RESOURCE, which a default container lacks (measured: refused).

Kubernetes sets the adj for you by quality-of-service class: Guaranteed -997, BestEffort 1000, Burstable min(max(2, 1000 - (1000 × memoryRequestBytes) / machineMemoryCapacityBytes), 999) ({{node-pressure eviction docs|https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/}}). So when the node runs out, a pod with a small request relative to the node is killed first; when a container exceeds its own limit, its cgroup OOM kills inside it regardless.

What an OOM kill looks like
No Python exception, no traceback: SIGKILL cannot be caught. The shell says Killed; the exit code is 137 (128 + 9); Kubernetes reports OOMKilled; the kernel log has "Memory cgroup out of memory: Killed process" (dmesg, not readable in an unprivileged container); memory.events counts oom_kill. A Python MemoryError is a different event: an allocation the kernel refused (mode 2, an rlimit, a 32-bit limit), which the root's Debug lab sets side by side.

cat /sys/fs/cgroup/memory.{current,max,events}; grep -E '^(anon|file|shmem) ' /sys/fs/cgroup/memory.stat; cat /proc/PID/oom_score{,_adj}

13. RSS, PSS, USS: three answers to "how much memory does it use?"

The problem. Shared pages (libraries, the page cache of a mapped file, copy-on-write pages after fork) are resident for several processes at once. Adding up per-process numbers counts them several times. Three measures, all from /proc/PID/smaps_rollup:

RSSresident set: every resident page mapped by the process, shared or not. Sums overcount.
PSSproportional set: each page divided by the number of processes mapping it. Sums are right.
USSunique set: Private_Clean + Private_Dirty, what you would get back by killing this one process.

The running job, measured while training (main process and its two fork-started DataLoader workers):

The workers' RSS of about 250 MiB each is nearly all Shared_Dirty: the parent's heap and the imported torch, inherited by fork and not yet written. Their USS, what each really adds, is under 9 MiB. Over an epoch, copy-on-write (section 7) is what turns Shared_Dirty into Private_Dirty, so watch USS per worker, not RSS. Which number a tool reports: ps and top show RSS; smem shows PSS and USS; container tools and Kubernetes read the cgroup (memory.current, which also includes page cache), which is a fourth answer.

for p in $(pgrep -f train.py); do grep -E '^(Rss|Pss|Private)' /proc/$p/smaps_rollup; done; smem -P train.py

14. NUMA: when some memory is farther away not run here

A server with two CPU sockets has memory attached to each; a CPU reaches its own node's memory faster than the other's (non-uniform memory access). This lab has one node (numactl --hardware reports none). The policies, from {{set_mempolicy(2)|https://man7.org/linux/man-pages/man2/set_mempolicy.2.html}} and {{mbind(2)|https://man7.org/linux/man-pages/man2/mbind.2.html}}:

PolicyWhere pages goUse
MPOL_DEFAULT (local)the node of the CPU that first touches the page ("first touch")the default; why the thread that initialises a buffer decides where it lives
MPOL_BINDonly the given nodesnumactl --membind; strict, can OOM while another node is free
MPOL_PREFERREDthe given node if possiblesoft placement
MPOL_INTERLEAVEround-robin over nodes, page by pagebig shared tables read from all sockets

Automatic NUMA balancing (kernel.numa_balancing) periodically makes pages inaccessible so the next access faults (do_numa_page, the pte_protnone branch in {{handle_pte_fault, line 4380|https://github.com/torvalds/linux/blob/v5.10/mm/memory.c#L4380}}), notes which node touched it, and migrates pages or tasks to match; each migration is a TLB shootdown (section 3) ({{sysctl kernel docs, numa_balancing|https://docs.kernel.org/admin-guide/sysctl/kernel.html#numa-balancing}}). Cgroups restrict nodes with cpuset.mems.

In ML. Each GPU hangs off one socket's PCIe; nvidia-smi topo -m prints each GPU's CPU and NUMA affinity. A data loader and pinned buffers on the other socket send every batch across the inter-socket link. Launch per-GPU processes with matching numactl --cpunodebind=N --membind=N (or the launcher's affinity options).
