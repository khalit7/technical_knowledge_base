Four real runs of a container with a 512 MiB memory limit, sampled every 25 ms from inside the container (memory.current, memory.stat, memory.swap.current, memory.events), replayed at their real pace. Each scenario starts from the same empty container; compare what fills the limit and what happens when it is reached. Scripts: src/exp/cg_replay.sh, sampler.py; raw samples: src/raw/cg_*.txt.

1. Replay a container reaching its memory limit

    Try: "Page cache only" and "Grow until killed" both reach the line, but only one dies: watch the file area shrink to make room for anonymous memory in the second. Then "/dev/shm": after the kill the shmem area stays, because a file in /dev/shm belongs to no process.

    2. Who the OOM killer picks: the formula, live

    Set up to three processes in one cgroup. The score is Linux 5.10's oom_badness: rss + swap + page tables (pages) + oom_score_adj × ⌊totalpages / 1000⌋, where totalpages is the cgroup's limit plus allowed swap; /proc/PID/oom_score instead uses the whole machine's RAM + swap (). Defaults: the measured run of the Reading tab's section 12, whose oom_score values this formula reproduces exactly.
