5. mmap: files and memory as one thing

read() copies bytes from the kernel's cache of the file (the page cache, section 6) into your buffer: two copies of the data in memory, a system call per read, and a buffer you must manage. mmap(addr, length, prot, flags, fd, offset) instead adds a VMA whose pages are the page-cache pages of the file ({{mmap(2)|https://man7.org/linux/man-pages/man2/mmap.2.html}}). The first touch of each page faults (section 4) and maps the cached page directly; nothing is copied. Two choices make four kinds of mapping:

MAP_PRIVATEMAP_SHARED
FileReads see the file; a write copies that page into private anonymous memory (copy-on-write), the file never changes. Used by: the loader for code and data of every .so; np.memmap(mode="c").Reads and writes go to the page cache, other mappers see them at once, writeback puts them in the file (msync to force it). Used by: np.memmap(mode="r+"), databases, the job's dataset (read-only, r--s in its maps).

Used by: malloc of large blocks, thread stacks, every allocator's arenas, all your tensors.Memory shared with children after fork (backed by an invisible shmem file). Used by: multiprocessing shared values. Named shared memory is a file in /dev/shm, which is how DataLoader workers pass batches.
SIGBUS, not an exception
If the file shrinks under a mapping (another process truncates or rewrites a dataset shard), touching a page past the new end raises SIGBUS and the process dies ({{mmap(2), SIGBUS|https://man7.org/linux/man-pages/man2/mmap.2.html}}). So does an I/O error on a network file system while faulting. Replace shared datasets by writing a new file and renaming it over the old one; mappings of the old file keep working.

Random rows from a dataset: read() against mmap measured

20,000 random rows of 1,028 bytes (the job's row format) from a 256 MiB file, warm (in the page cache) and cold (evicted with posix_fadvise(POSIX_FADV_DONTNEED), which any process may do for clean pages). The rows are 19.6 MiB of useful data; "read from storage" is read_bytes in /proc/self/io.

Cold, a plain mapping read the whole file to serve 20,000 rows; MADV_RANDOM read a quarter of it but paid a device trip per row

Warm, all three cost 1 to 2 microseconds a row (Python dominates). Cold, a fault on a mapping reads around the faulting page (read_ahead_kb, 128 KiB by default): on this small file that pulled in the whole file (13x the useful bytes) and then served the rest from memory, the fastest here; on a dataset much larger than RAM the same bet reads 32 pages to use one and fills the cache with neighbours you will not touch. madvise(MADV_RANDOM) turns read-around off: one page per fault, 3.4x amplification, one device round trip per row. So a shuffled index over a huge file wants MADV_RANDOM or explicit pread; a sequential pass or a small hot file wants the default (or MADV_SEQUENTIAL, MADV_WILLNEED).

Loading weights: copy or map measured

A 256 MiB state dict (eight 32 MiB float32 tensors) saved with torch.save and with safetensors, loaded cold four ways. "Return" is the time until the call returns; then every tensor is summed once.

torch.load reads every byte into fresh anonymous memory before returning. torch.load(mmap=True), in its own words, maps the file "rather than loading all the storages into memory" (docstring of torch 2.14.1), and safetensors (whose format is "fast (zero-copy)", {{safetensors docs|https://huggingface.co/docs/safetensors/index}}) returns tensors whose storage is the mapping: the call returns in milliseconds and the bytes arrive as page faults when first used (measured: torch.load returned after 194 ms holding 243 MiB, torch.load(mmap=True) after 4.5 ms holding none). The pages are clean page cache: the kernel can drop and re-read them, and every process mapping the file shares one copy. The first forward pass pays the faults the load call skipped. safe_open plus get_tensor reads only the tensors asked for, which is how one rank of a sharded model loads only its shard.

Eight inference processes on one host each torch.load(path, mmap=True) the same 14 GB checkpoint and run. Free memory drops by about how much for the weights?

All eight map the same page-cache pages of one file, so the weights occupy RAM once (as "buff/cache" in free). Each process's RSS still shows up to 14 GB, which is why RSS sums mislead (section 13). The catch: if a process converts or moves the tensors (to another dtype, or to a GPU and then keeps a CPU copy), that copy is private anonymous memory, eight times over.

6. The page cache and reclaim: where "free" memory went

Linux keeps file data that was read or written in otherwise unused RAM, the page cache, because RAM that holds nothing is wasted. free shows it as "buff/cache"; "available" estimates what could be handed to programs if they asked, mostly by dropping clean cache. Writing, flushing and fsync of cached data belong to the sibling {{Storage and file systems|n:3f05c17b0d0d8141be7acc1313570cbf}}; here the question is how memory is taken back.

Three watermarks decide who reclaims: kswapd in the background, or the allocating process itself

Free memory on this VM, to scale, summed over zones. min is the measured min_free_kbytes; low and high are derived from the 5.10 formula below.

Reclaim. Each memory zone has three watermarks of free pages. Below low, the kernel thread kswapd wakes and reclaims in the background until high; below min, an allocating process must reclaim by itself before it gets memory (direct reclaim), which shows up as stalls in that process. In 5.10, low = min + max(min / 4, managed × watermark_scale_factor / 10,000) and high = min + 2 × that ({{mm/page_alloc.c lines 7874 to 7880|https://github.com/torvalds/linux/blob/v5.10/mm/page_alloc.c#L7874}}). Here min_free_kbytes is KiB and the scale factor is 10, so low and high sit about 11 MiB and 22 MiB above min. Raising watermark_scale_factor starts background reclaim earlier, a common fix for allocation stalls on big-memory hosts.

Which pages go. Linux 5.10 keeps two lists per type (anonymous and file), active and inactive, an approximation of least-recently-used built on the hardware accessed bit (section 2): pages are scanned from the inactive tail, and one referenced since gets another chance. Clean file pages are cheapest to drop (re-read later); dirty ones must be written first; anonymous pages can only go to swap. vm.swappiness (60 here, the default, {{mm/vmscan.c line 172|https://github.com/torvalds/linux/blob/v5.10/mm/vmscan.c#L172}}) weighs anonymous against file reclaim.

Inside a container the same reclaim runs against the cgroup's limit instead of the machine's: reading a 768 MiB file in a 512 MiB container filled the cache up to the limit and recycled it, with thousands of "max" events and no OOM kill (the replay in section 12, scenario "Page cache only").

Since 6.1: the multi-generational LRU not run here

Linux 6.1 added the multi-generational LRU, which replaces the two lists with several age generations and scans page tables instead of reverse mappings ({{multigen_lru docs|https://docs.kernel.org/admin-guide/mm/multigen_lru.html}}).
