3. The TLB: why translation is usually free, and when it is not

ch. 19 Translation Lookaside Buffers

The problem. A four-level walk is four extra memory reads for every load and store. How it works. The CPU keeps recent translations in a translation lookaside buffer (TLB): a small cache from virtual page number to frame and permissions. A hit adds nothing; a miss triggers a hardware page-table walk (the walk's reads are themselves cached in the data caches, so a miss costs nanoseconds, not four trips to DRAM). The root page measured it on this machine: one access costs 1.1 ns while the touched pages fit in the TLB and 7.6 ns once they do not, with the knee between 2,048 and 4,096 pages (8 to 16 MiB of TLB reach, entries times page size); with 2 MiB pages the same walk stays at 1.1 ns ({{Topic: operating-systems|n:3f05c17b0d0d81c5a97ce991644af140}}, section 4 and the OS simulators tab, which also replays OSTEP's TLB homework).

Address-space identifiers. After a switch to another process, the old translations are wrong. Flushing the whole TLB on every switch would make every switch expensive, so entries are tagged with an ASID (arm64: 8 or 16 bits, read from the CPU at boot, {{arch/arm64/mm/context.c line 42|https://github.com/torvalds/linux/blob/v5.10/arch/arm64/mm/context.c#L42}}; x86-64 calls it PCID, 12 bits). Kernel mappings are marked global and shared by all processes; user mappings are "not global" (the nG bit in section 2's table).

TLB shootdowns: the cost of changing a mapping

When a process changes or removes a mapping (munmap, mprotect, madvise(MADV_DONTNEED), page migration, swapping a page out), every CPU that may have cached the old translation must drop it, or a thread there would keep using a page that is no longer theirs. That is a TLB shootdown. The two architectures do it very differently source:

x86-64: interrupt the other CPUs

The kernel sends an inter-processor interrupt to each CPU running the address space and waits for all to flush ({{arch/x86/mm/tlb.c lines 798 to 825|https://github.com/torvalds/linux/blob/v5.10/arch/x86/mm/tlb.c#L798}}, smp_call_function_many); over 33 pages it flushes everything instead ({{line 842|https://github.com/torvalds/linux/blob/v5.10/arch/x86/mm/tlb.c#L842}}). Cost grows with the number of CPUs the process has run on.

arm64: one broadcast instruction

The kernel issues TLBI VALE1IS ("inner shareable"), which the hardware broadcasts to every CPU, then waits with a barrier ({{arch/arm64/include/asm/tlbflush.h lines 255 to 272|https://github.com/torvalds/linux/blob/v5.10/arch/arm64/include/asm/tlbflush.h#L255}}). No interrupt, no other CPU's code runs.

When it bites in ML. A CPU-heavy process with many threads (PyTorch's intra-op pool, a data loader with threads) whose allocator keeps returning memory to the kernel and asking for it again triggers a shootdown each time; on large x86 servers each costs interrupts on every CPU that ran the process. Symptoms: high system time with no obvious system calls in your code. Fix: keep memory cached in the allocator instead of returning it (the {{Memory allocators|n:3f05c17b0d0d81209ae9d856695dc958}} page covers the knobs), fewer threads, huge pages.

4. Page faults: memory is filled in on first touch

ch. 21 Swapping: Mechanisms, ch. 23 Complete VM Systems

The idea. mmap and malloc only add a VMA; no frame is allocated and no table entry written. The first access finds an invalid (or read-only) entry and the CPU raises an exception: a page fault. The kernel looks up the VMA, decides what the page should contain, fills the entry and re-runs the instruction. The program never notices, except in time. A minor fault needs no I/O; a major fault waited for a device ({{getrusage(2)|https://man7.org/linux/man-pages/man2/getrusage.2.html}}; in 5.10 a fault that had to be retried also counts as major, {{mm/memory.c lines 4548 to 4557|https://github.com/torvalds/linux/blob/v5.10/mm/memory.c#L4548}}).

One access, followed through the kernel. Pick a case; the stepper walks the real 5.10 code path on arm64 and shows what this machine measured for it.

Three details that matter. (1) The zero page: a read of never-written anonymous memory maps one shared, read-only page of zeros ({{mm/memory.c lines 3496 to 3500|https://github.com/torvalds/linux/blob/v5.10/mm/memory.c#L3496}}): measured, reading 64 MiB took faults and added 0 KiB of RSS; writing it afterwards took the same number of faults again. So "I allocated and read it, but RSS did not grow" is expected. (2) Fault-around: a read fault on a cached file page maps up to 16 neighbouring cached pages at once (fault_around_bytes = 64 KiB, {{line 3875|https://github.com/torvalds/linux/blob/v5.10/mm/memory.c#L3875}}). The root's warm read of the 2,056-page dataset took exactly 129 minor faults, which is 2,056 / 16 rounded up. (3) MAP_POPULATE (or madvise(MADV_POPULATE_WRITE) since 5.14) pays all faults inside the mmap call: 64 MiB took ms in the call against ms by touching page by page, because one call avoids 16,384 trips into the kernel.

You np.empty(10**9, dtype=np.uint8) and immediately call .sum(). Memory use (RSS) afterwards?

A large np.empty is a fresh anonymous mapping (glibc serves big requests with mmap). Reading it faults each page onto the shared zero page: 244,141 minor faults, no new frames. The sum is 0. RSS grows only when you write. (With transparent huge pages enabled for the range, a read fault can instead map a huge zero page; same outcome.)

When it bites in ML. The first epoch is slower than the rest (major faults on the dataset; the root's Debug lab case "The first epoch is slower than the rest: cold and warm page cache"); the first iteration of a step that allocates a big new buffer pays one fault per 4 KiB (1 GiB = 262,144 faults, about 0.27 s at the 1 us measured here, per process); a latency-sensitive server sees spikes when pages are first touched. Fixes: pre-touch (MAP_POPULATE, a warm-up step), huge pages (section 8), keep buffers alive across steps instead of reallocating.
