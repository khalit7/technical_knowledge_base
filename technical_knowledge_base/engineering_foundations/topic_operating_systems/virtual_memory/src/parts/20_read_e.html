9. Locked and pinned memory, and GPU memory mapping

Normally the kernel may move a page (compaction, NUMA migration, THP collapse) or write it to swap, because only the page table knows where it is and the table is updated. A device that copies memory by itself (DMA: a GPU, a network card doing RDMA) holds a physical address and does not consult the page table; if the page moves mid-copy, the device reads someone else's data. Two mechanisms stop that. mlock(addr, len) faults the range in and keeps it resident, never swapped ({{mlock(2)|https://man7.org/linux/man-pages/man2/mlock.2.html}}). Pinning is stronger and kernel-internal: a driver calls pin_user_pages (the FOLL_PIN flavour of get_user_pages, {{pin_user_pages docs|https://docs.kernel.org/core-api/pin_user_pages.html}}) and the pages may not be moved or freed until it unpins them. Both take memory out of what reclaim can use.

Pageable memory needs a staging copy before the GPU can DMA it; pinned memory is copied directly, and asynchronously

Static before/after diagram of one host-to-GPU copy, from the CUDA and PyTorch documentation quoted below not run here (no GPU in this VM).

Pinned memory for GPU copies not run here. cudaHostAlloc / cudaMallocHost "Allocates size bytes of host memory that is page-locked and accessible to the device", with the warning that "allocating excessive amounts of pinned memory may degrade system performance, since it reduces the amount of memory available to the system for paging"; cudaHostRegister page-locks an existing range ({{CUDA runtime API, memory management|https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__MEMORY.html}}). Why it matters: "when CUDA sends pageable data from CPU to GPU, it must first create a page-locked copy of that data before making the transfer" ({{PyTorch pinned memory tutorial|https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html}}), an extra copy through a staging buffer. In PyTorch:

  • DataLoader(pin_memory=True) runs a thread that copies each batch into pinned memory, so x.to("cuda", non_blocking=True) can be an asynchronous DMA that overlaps compute.
  • Calling t.pin_memory() right before one copy is usually slower than copying directly (it pays the staging copy itself); pin once, reuse.
  • The tutorial warns that "allocating a large number of tensors or sizable tensors in pinned memory can monopolize a substantial portion of RAM": pinned pages cannot be reclaimed, so the page cache that feeds your data loader shrinks.
Two more pinned-memory traps: asynchronous corruption, power-of-two rounding
  • Copies from pinned memory with non_blocking=True are asynchronous: modifying the source tensor before the copy finished corrupts the GPU copy.
  • PyTorch's pinned memory comes from its CachingHostAllocator, which rounds each request up to the next power of two by default, so a 600 MB pinned buffer locks 1 GiB of RAM ({{Memory allocators|n:3f05c17b0d0d81209ae9d856695dc958}} reads the source).

The limit measured. Unprivileged locking is capped by RLIMIT_MEMLOCK, which is 64 KiB in a default Docker container:

Unified (managed) memory: page faults that cross to the GPU. cudaMallocManaged gives one pointer valid on CPU and GPU; its pages live on one side at a time and migrate on a page fault from the other side, the same demand paging as section 4 with a device on the far end. The fault is serviced by NVIDIA's nvidia-uvm kernel module, and on systems with Linux's HMM or hardware coherence (Grace Hopper) the GPU uses the process's own page tables. The sibling {{Virtualization and the GPU driver stack|n:3f05c17b0d0d8158b029e9b2ba2e161b}} (section 11, "GPU memory and the driver, from the operating system's side") follows the driver's side; the CUDA programmer's view of pinned, mapped and managed memory, with prefetching, is {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}} (section 8).

10. Overcommit: promising more memory than exists


Programs reserve far more than they touch (allocator arenas, thread stacks, sparse arrays, a 1 GiB reservation by PyTorch's allocator). Refusing every reservation that exceeds RAM would waste memory; accepting all means some promise may not be kept. The kernel's choice is vm.overcommit_memory source ({{overcommit-accounting|https://docs.kernel.org/mm/overcommit-accounting.html}}; {{mm/util.c lines 860 to 876|https://github.com/torvalds/linux/blob/v5.10/mm/util.c#L860}}):

11. Swap: anonymous pages written to disk


Anonymous pages have no file to be re-read from, so to reclaim one the kernel writes it to a swap device, replaces the table entry with a not-present entry holding the swap location, and frees the frame. The next access is a major fault: do_swap_page reads it back ({{handle_pte_fault, mm/memory.c line 4377|https://github.com/torvalds/linux/blob/v5.10/mm/memory.c#L4377}}), reading 2page-cluster = 8 neighbouring swap slots at once (vm.page-cluster = 3 here).


What it costs measured. A process that needs 640 MiB in a container limited to 512 MiB with 512 MiB of swap allowed did not die; it ran with about 260 MiB in swap and every pass over its memory took 4 to 5 seconds, the same pass that takes milliseconds when it fits (the replay in section 12, scenario "Swap allowed"; the root's Debug lab case "Not dead, just slow: the working set spills into swap" has the per-pass numbers). For a training job that is usually worse than being killed: it looks alive, holds its GPUs, and makes no progress.


The signal to watch is pressure, not free memory: with pressure stall information (PSI), /proc/pressure/memory and each cgroup's memory.pressure report the share of time tasks were stalled waiting for memory.


zswap, zram and PSI in detail not run here
Neither zswap nor zram is built into this kernel. zswap is a compressed cache in front of a swap device: pages being swapped out are compressed into a RAM pool first and written to disk only when the pool is full ({{zswap docs|https://docs.kernel.org/admin-guide/mm/zswap.html}}). zram is a compressed RAM block device used as swap. Both trade CPU for fewer disk reads.


PSI is not enabled in this kernel. Where it is, the files report some and full stall shares over 10, 60 and 300 s ({{PSI docs|https://docs.kernel.org/accounting/psi.html}}). It is the best single "is this job memory-starved" signal; systemd-oomd kills on it ({{systemd-oomd|https://www.freedesktop.org/software/systemd/man/latest/systemd-oomd.service.html}}).
