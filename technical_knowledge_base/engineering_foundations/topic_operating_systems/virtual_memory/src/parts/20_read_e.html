7. Copy-on-write: fork copies tables, writes copy pages

ch. 23 Complete VM Systems (copy-on-write); the fork API: the sibling {{Processes and the system-call API|n:3f05c17b0d0d811e99f7cb8c15d12697}}

The problem. fork must give the child an exact copy of the parent's memory. Copying gigabytes for a DataLoader worker that will read a few batches would take seconds and double memory. How it works source: fork copies the page tables, not the pages, and marks every private writable entry read-only in both parent and child ({{copy_present_pte, mm/memory.c lines 878 to 880|https://github.com/torvalds/linux/blob/v5.10/mm/memory.c#L878}}). Both now share each frame. The first write by either side faults on a read-only entry of a writable VMA; do_wp_page sees the frame is shared and wp_page_copy ({{line 2817|https://github.com/torvalds/linux/blob/v5.10/mm/memory.c#L2817}}) copies that one 4 KiB page and gives the writer its own. A page with only one user left is simply made writable again.

What this costs measured. fork + exit + wait grows with the parent's resident memory, about 19 microseconds per resident MiB with 4 KiB pages (the tables being copied), and is 30x cheaper at 1 GiB when the memory is in transparent huge pages (one entry per 2 MiB, {{copy_huge_pmd|https://github.com/torvalds/linux/blob/v5.10/mm/huge_memory.c#L997}}). Each later write costs a fault and a copy: ns per 4 KiB page. With huge pages the first write does not copy 2 MiB: 5.10 splits the huge entry and falls back to 4 KiB copies ({{mm/huge_memory.c lines 1315 to 1317|https://github.com/torvalds/linux/blob/v5.10/mm/huge_memory.c#L1315}}); measured, the child's writes took the same 65,538 faults at ns each.

Python turns reads into writes, twice

The root page showed reference counts: reading a Python object increments and decrements its count, which writes the page it sits on, so a forked worker that only reads a list of a million objects copies the pages holding them (PyTorch's "memory leak" that is not a leak, {{torch.utils.data docs|https://docs.pytorch.org/docs/stable/data.html#multi-process-data-loading}}). The second writer is the cyclic garbage collector: a full collection writes a counter (gc_refs) into the header of every container object it tracks, so a gc.collect() in a worker copies every page of tracked objects even if your code never reads them. Measured: a parent builds one million two-element lists, forks, and the child does one thing:

Pages the child copied (growth of its Private_Dirty in /proc/self/smaps_rollup), Python 3.11.2, numpy 2.4.6. Reading every list copied about 61 MiB: the pages that hold the list objects themselves (the integers inside were not touched).

The fix the Python docs give for exactly this: "call gc.disable() early in the parent process, gc.freeze() right before fork(), and gc.enable() early in child processes" ({{gc.freeze, Python 3.7+|https://docs.python.org/3/library/gc.html#gc.freeze}}). gc.freeze() moves every tracked object into a permanent generation that collections skip: 30 pages copied instead of 16,817. It does not stop reference-count writes; for data you iterate, store it as NumPy arrays, Arrow tables or one big bytes buffer with offsets (63 pages), not as millions of Python objects.

Your Dataset holds a list of 50 million file paths (Python strings). With 8 fork-started workers, what happens to memory over the first epoch?

Every access to paths[i] touches the string's reference count, and any garbage collection in a worker touches every tracked container. Shared pages turn private one 4 KiB page at a time, so each worker's USS climbs as the epoch reads more of the list. Store the paths as one NumPy byte array plus offsets (or Arrow), and gc.freeze() before the DataLoader forks. The root's Debug lab case "Worker memory grows: copy-on-write meets reference counts" measures it per worker.

Related flags. madvise(MADV_DONTFORK) keeps a range out of the child entirely, "useful to prevent copy-on-write semantics from changing the physical location of a page if the parent writes to it after a fork" (DMA buffers, section 9); MADV_WIPEONFORK gives the child zeros instead ({{madvise(2)|https://man7.org/linux/man-pages/man2/madvise.2.html}}). Forking a process that runs threads has its own trap (a lock held by a thread that does not exist in the child): the root's Debug lab case "A worker hangs forever: fork while another thread holds a lock".

8. Huge pages: one entry for 2 MiB

ch. 19 TLBs (larger pages), ch. 20 Advanced Page Tables

The idea. A level-2 entry can point straight at a 2 MiB block instead of a table (with 4 KiB base pages; 1 GiB at level 1). One TLB entry then covers 512 small pages, a walk is one level shorter, and a fault fills 2 MiB at once. Linux offers two ways: transparent huge pages (THP), used automatically for anonymous memory where possible, and hugetlbfs, a pool of huge pages reserved in advance.

The same 64 MiB buffer, with 4 KiB pages and with THP measured. Toggle the mode; every number is from this machine.

The knobs (values read on this VM). /sys/kernel/mm/transparent_hugepage/enabled is always, madvise (only ranges marked madvise(MADV_HUGEPAGE)) or never; here madvise. defrag says whether a fault may stall to compact memory into a free 2 MiB block; here madvise (stall only for marked ranges). The background thread khugepaged later collapses 512 small pages into a huge one, scanning pages per pass, and with max_ptes_none = it will collapse a range in which 511 of 512 pages were never touched, filling them with zeros ({{transhuge docs|https://docs.kernel.org/admin-guide/mm/transhuge.html}}). Watch AnonHugePages in /proc/meminfo or a process's smaps_rollup.

The costs
(1) Bloat: touching one byte in every 2 MiB of 256 MiB cost KiB with 4 KiB pages and KiB with THP, x more, for sparse structures (hash tables, sparse embedding rows, an arena with holes). (2) Latency: the first THP run took ms against ms later, consistent with the kernel having to find or compact free 2 MiB blocks (cause not confirmed here); on a long-running, fragmented host, compaction stalls are the classic THP complaint. (3) No page-table saving: for each huge page the kernel deposits a spare 4 KiB table so it can split the page later ({{mm/huge_memory.c line 623|https://github.com/torvalds/linux/blob/v5.10/mm/huge_memory.c#L623}}), so VmPTE after touching 1 GiB was KiB either way.

hugetlbfs not run here. An administrator reserves a pool (vm.nr_hugepages, or per size under /sys/kernel/mm/hugepages/); programs get pages from it with mmap(MAP_HUGETLB) or files in a hugetlbfs mount. Pool pages are never swapped, never split, and never bloat, but are taken from the machine even when unused. This arm64 kernel offers 64 KiB, 2 MiB, 32 MiB and 1 GiB sizes (its cgroup lists hugetlb.64KB, 2MB, 32MB, 1GB; 64 KiB and 32 MiB use arm64's contiguous bit, 16 adjacent entries cached as one); the pool here is empty (HugePages_Total: 0) and filling it needs privileges ({{hugetlbpage docs|https://docs.kernel.org/admin-guide/mm/hugetlbpage.html}}).

In ML. The root found that this PyTorch wheel's allocator reserves 1 GiB and marks it MADV_HUGEPAGE, so tensor memory gets THP even in madvise mode (Syscall tracer tab of {{Topic: operating-systems|n:3f05c17b0d0d81c5a97ce991644af140}}). Big dense tensors and pinned staging buffers are ideal THP users; sparse, long-lived structures in a always system are where bloat appears. Fix for bloat: madvise mode, or MADV_NOHUGEPAGE on the sparse range, or max_ptes_none lower.
