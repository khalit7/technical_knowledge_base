The idea

Every address a program uses is virtual: the hardware translates it page by page through a per-process tree of tables, and the kernel fills that tree lazily, one page at a time, at first touch. Everything else (mmap, copy-on-write, huge pages, swap, the OOM killer) is a way of filling, sharing, enlarging or taking back pages.

1. The address space: what one process sees

Every process gets its own address space: a private range of addresses that the hardware translates to real memory on every access, so processes cannot see each other's data yet can share what is identical (the code of libtorch_cpu.so, the dataset file). On 64-bit Linux the user part is 248 bytes (256 TiB) on arm64 with 4 KiB pages and 247 bytes (128 TiB) on x86-64 with four-level tables ({{arm64 memory layout|https://docs.kernel.org/arch/arm64/memory.html}}; {{x86-64 memory map|https://docs.kernel.org/arch/x86/x86_64/mm.html}}). Almost all of it is empty. What exists is a list of mappings (virtual memory areas, VMAs): contiguous ranges with one set of permissions and one source, a file or anonymous zero-filled memory. Threads of one process share one address space; that is all "sharing memory" means for threads.

The running job reserves 2 GiB of addresses; most of it is one allocator reservation, not memory

That total is what ps and top report as VSZ (virtual size): address space, not memory (section 13). measured: the root's recording of the main process just after its DataLoader workers were forked.

Selected lines of the real /proc/PID/maps

One line per VMA: start-end, permissions (r, w, x, and p private or s shared), file offset, device, inode, path. 



The 54 anonymous mappings add up to 1.5 GiB mainly because of one 1 GiB reservation by the allocator inside libc10.so (the sibling {{Memory allocators|n:3f05c17b0d0d81209ae9d856695dc958}} owns that story). Pages are only spent when touched (section 4).


A limit you can hit
vm.max_map_count caps the number of VMAs per process (default 65,530 in the {{kernel docs|https://docs.kernel.org/admin-guide/sysctl/vm.html#max-map-count}}; Docker Desktop's VM sets 262,144, read here). The job uses about 456. A process that maps thousands of files or shards, or an allocator that splits its arena into many protected pieces, gets ENOMEM from mmap long before memory is short, and the error says nothing about VMAs.


cat /proc/PID/maps | wc -l; pmap -x PID | tail -1; cat /proc/sys/vm/max_map_count


In the kernel: mm_struct and vm_area_struct
source: one struct mm_struct per address space holds pgd, the root of its page-table tree, and the set of VMAs ({{include/linux/mm_types.h line 388|https://github.com/torvalds/linux/blob/v5.10/include/linux/mm_types.h#L388}}; a red-black tree in 5.10, a maple tree since 6.1); each VMA is a struct vm_area_struct with vm_start, vm_end, flags, an optional vm_file and a table of operations vm_ops that says how to fill a page when it is first touched ({{line 305|https://github.com/torvalds/linux/blob/v5.10/include/linux/mm_types.h#L305}}). Threads of one process share one mm_struct.







2. Page tables: the tree that translates every address


Memory is managed in fixed-size pages: 4 KiB here (getconf PAGESIZE prints 4096). A virtual address splits into a virtual page number (high bits) and an offset inside the page (low 12 bits, passed through unchanged). The page table maps each virtual page to a physical page frame, plus permission bits.


Why a tree. One flat table for 236 virtual pages at 8 bytes an entry would be 512 GiB per process. Instead the 36 bits are cut into four 9-bit pieces; each indexes a 4 KiB table of 512 eight-byte entries, which points to the next table. Only the tables on the path to a mapped page exist, so a sparse address space costs almost nothing. The arm64 kernel computes the number of levels as (VA_BITS - 4) / (PAGE_SHIFT - 3) ({{pgtable-hwdef.h line 26|https://github.com/torvalds/linux/blob/v5.10/arch/arm64/include/asm/pgtable-hwdef.h#L26}}): (48 - 4) / (12 - 3) = 4 levels for 4 KiB pages.


The first byte of the job's memory-mapped dataset, 0xffff81fd2000 (from the maps lines above), cut into its four table indices and offset. The {{Address translator|#t-addr}} tab does this for any address, on arm64 with 4, 16 or 64 KiB pages and on x86-64 with four or five levels.


The walk: four dependent reads, one per level, then the TLB remembers the answer










Stepper on the same dataset address, arm64, 4 KiB pages. Indices are computed from the address; table and frame numbers are illustrative (reading real frame numbers from /proc/PID/pagemap needs privileges).


The bits do work. Accessed is set by hardware on use: page reclaim reads and clears it to find cold pages (section 6). Dirty says a file page must be written back before reuse. Read-only on a writable mapping is how copy-on-write traps the first write (section 7). Not present is how swap and lazy allocation trap the first access (section 4).


What the tables cost measured
One last-level table (4 KiB) maps 512 pages = 2 MiB, so touching 1 GiB needs 512 tables = 2,048 KiB, plus a few upper-level tables. Measured: VmPTE grew by  KiB after touching 1 GiB. That is 0.2% of the memory mapped, per process: 64 workers each touching the same 10 GiB shared dataset carry 64 copies of its tables (1.3 GiB). With huge pages the kernel still sets aside one table per 2 MiB (section 8), so the measured VmPTE did not shrink.


A process maps a 64 GiB file but only ever reads 1 MiB of it at one spot. Roughly how much page-table memory does that cost?




Tables exist only along paths to touched pages. 1 MiB at one spot needs one last-level table plus one table at each upper level: four 4 KiB tables, 16 KiB. The 128 MiB answer would hold only if every 2 MiB of the file were touched. Mapping is free; touching costs tables and frames.


grep -E 'VmPTE|VmRSS|VmSize' /proc/PID/status
