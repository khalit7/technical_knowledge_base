15. ML recipes: the mechanisms put to work

Datasets: map, do not load

Store samples in one or a few large files (a NumPy array, Arrow, a packed binary with an index) and np.memmap them, as the running job does. Workers then share one page-cache copy and pay only faults. For shuffled access to a dataset larger than RAM, prefer MADV_RANDOM or pread per sample (section 5); for sequential shards, the default read-around. Never replace a mapped file in place (SIGBUS); write and rename.

Weights: safetensors or mmap=True

Loading returns in milliseconds and many processes share one copy; the first forward pass pays the faults. Read only your shard with safe_open. Converting dtype or moving to GPU creates private copies: drop the CPU tensors afterwards.

DataLoader workers: keep the parent lean

Fork-started workers share the parent copy-on-write, and Python's reference counts and GC copy whatever they touch. Hold metadata in NumPy or Arrow, not lists of objects; call gc.freeze() before creating the iterator; watch USS per worker (section 13). Spawn or forkserver avoid the sharing altogether at the cost of start-up time (the root measured 0.021 s fork against 0.836 s spawn to the first batch).

/dev/shm: size it and count it

Batches travel through shared memory: give the container --shm-size (or --ipc=host) of at least workers × prefetch factor × batch bytes, and remember it is charged to the memory limit and survives a killed process (section 12).

Pinned memory: pin once, not too much

pin_memory=True plus non_blocking=True overlaps host-to-device copies with compute; raise memlock in containers; budget pinned bytes as unreclaimable (section 9).

Limits: know which one kills you

Read memory.max, memory.events and memory.stat from inside the job and log them; an exit code 137 with oom_kill incremented is the cgroup, not your code. Leave headroom for page cache and /dev/shm. If swap is allowed, alert on memory.swap.current: a swapping training job is a stalled one.

Common mistakes

"RSS says each worker uses 250 MiB, so 8 workers need 2 GB."
RSS counts shared pages in every process. Measured here: three processes, 815 MiB of RSS, 345 MiB of PSS, 104 MiB of USS. Use PSS for totals and USS for "what does one more worker cost".
"The allocation succeeded, so the memory is there."
With overcommit (modes 0 and 1) an allocation is a promise; memory is taken at first touch, and the OOM killer settles any shortfall later, at a random-looking moment.
"free shows almost no free memory: we have a leak."
Look at "available", not "free". The page cache fills idle RAM on purpose and is given back on demand.
"The container's memory is full of page cache, so it is about to be killed."
Clean page cache is reclaimed at the limit (measured: thousands of "max" events, no kill). What kills is anonymous memory and shared memory that cannot be reclaimed without swap.
"Our workers only read the dataset, so copy-on-write cannot copy anything."
In Python, reading an object writes its reference count, and the garbage collector writes every tracked object's header. Measured: 15,732 pages copied by reading a list, 16,817 by one gc.collect(), 30 after gc.freeze().
"Huge pages always help."
They cut faults and TLB misses for dense memory, but bloat sparse memory (298x in the measurement here), can stall allocations on compaction, and do not reduce page-table memory in Linux.
"Set oom_score_adj = -1000 on the trainer so it is never killed."
Inside a default container you cannot lower it (no CAP_SYS_RESOURCE), and if you could, the kernel would kill something else, perhaps the data loader or the node agent. Size the limit instead.
"pin_memory() before every .to('cuda') makes copies faster."
Pinning is itself a copy; doing it per transfer is usually slower than letting CUDA stage the copy. Pin buffers you reuse (the DataLoader's pinning thread does this).

Interview questions

Walk through what happens on the first write to a freshly malloc'd 1 GiB buffer.
glibc serves it with an anonymous private mmap: a new VMA, no frames. The first store to each page misses the TLB; the hardware walk finds no valid entry; the CPU raises a fault; the kernel finds the VMA (writable, anonymous), allocates any missing table levels, takes a zeroed frame, writes the entry and resumes the store (do_anonymous_page). 262,144 such faults, about 1 us each here. With THP for the range, 512 faults of 2 MiB each. RSS grows as pages are touched, not at malloc.
Why is fork fast even for a process using 50 GB, and when is it not?
Fork copies page tables and marks private pages read-only; pages are copied lazily on write. The table copy is still proportional to resident memory: about 19 us per resident MiB measured here with 4 KiB pages (about 1 s for 50 GB), 30x less with huge pages. After fork, every page either side writes costs a fault and a 4 KiB copy, which is where DataLoader worker memory comes from.
What is a TLB shootdown and why can munmap be expensive in a multi-threaded program?
Removing or changing a mapping requires every CPU that may cache the old translation to drop it. x86 interrupts each such CPU and waits; arm64 broadcasts a TLBI instruction. Measured here on arm64, an mprotect that must flush cost about 1.9 us regardless of how many other threads ran, against 0.65 us when nothing was cached.
Explain RSS, PSS and USS, and which one you would alert on for a fleet of identical workers.
RSS counts all resident mapped pages, PSS divides shared pages among sharers, USS counts private pages only. Alert on USS growth per worker (copy-on-write and leaks show there) and on the cgroup's memory.current minus reclaimable cache for the pod as a whole.
A training pod dies with exit code 137 and no traceback. How do you confirm the cause and fix it?
137 = 128 + SIGKILL. Check memory.events (oom_kill), Kubernetes' OOMKilled reason, or the kernel log. Then find what grew: memory.stat anon vs file vs shmem (DataLoader shared memory counts), worker USS (copy-on-write), pinned memory. Fix the growth or raise the limit; do not rely on swap.
Why does mmap'ing model weights let 8 server processes share memory, and what breaks the sharing?
All map the same page-cache pages of the file (MAP_SHARED or read-only private), so RAM holds one copy. Any write to a private mapping, a dtype conversion, or a copy into a new tensor creates private anonymous pages per process.

Glossary

address space: a process's private range of virtual addresses
VMA: one mapping, a line of /proc/PID/maps
page / frame: 4 KiB unit of virtual / physical memory
page table: the per-process tree from virtual pages to frames
TLB: CPU cache of translations; reach = entries x page size
ASID / PCID: tag that lets TLB entries of many processes coexist
TLB shootdown: invalidating a translation on all CPUs
page fault: trap on access to a page with no valid entry; minor / major
page cache: file data cached in RAM
watermarks, direct reclaim: when the kernel frees memory, and who pays
THP / hugetlbfs: automatic / reserved huge pages
DMA, pinning: device copies, and pages that may not move
swap: disk space for anonymous pages
