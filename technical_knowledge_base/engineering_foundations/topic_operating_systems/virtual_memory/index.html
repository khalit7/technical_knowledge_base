In one screen

Every address your training job touches is a virtual address. Hardware translates it, page by page, through a tree of tables the kernel keeps for each process; a small cache (the TLB) makes that free most of the time; and the kernel fills the tables only when a page is first touched (a page fault). Everything else on this page, from mmap and copy-on-write to huge pages and the OOM killer, is a way of filling, sharing, enlarging or taking back those pages.

The root page, Topic: operating-systems section 4, gave the intuition and measured the TLB, page faults and copy-on-write on the running job. This page goes one level down: the kernel's actual code paths (Linux v5.10, the kernel these runs used, file and line), every knob that matters in ML work, and new measurements. Each mechanism follows the same pattern: problem, how it works, what it costs here, when it bites in ML, the command that shows it, the fix.

Five things to remember
  1. Allocating is not using. A 64 GiB mmap succeeded here on a 10 GB machine; memory is spent page by page, at first touch.
  2. Resident is not owned. The job's three processes report 815 MiB of RSS together but own only 104 MiB alone; the rest is shared (section 13).
  3. Reading a Python object writes to it (reference counts, the garbage collector), so forked DataLoader workers copy what they read. NumPy arrays and gc.freeze() stop it (section 7).
  4. The page cache counts toward your container's limit but is given back; anonymous memory and /dev/shm are not (section 12).
  5. The OOM killer sends SIGKILL: no exception, no traceback, exit code 137.

1. The address space: what one process sees

ch. 13 Address Spaces, ch. 14 Memory API

The problem. Many processes run at once, each written as if it owned all of memory from address 0 upward. They must not see each other's data, yet they should share what is identical (the code of libtorch_cpu.so, the dataset file), and together they may ask for more than the machine has.

The idea. Give every process its own address space: a private range of numbers (addresses) that the hardware translates to real memory on every access. On 64-bit Linux the user part of that range is 248 bytes (256 TiB) on arm64 with 4 KiB pages, and 247 bytes (128 TiB) on x86-64 with four-level tables (arm64 memory layout; x86-64 memory map). Almost all of it is empty. What exists is a list of mappings (virtual memory areas, VMAs): contiguous ranges with one set of permissions and one source (a file, or anonymous zero-filled memory).

In the kernel source: one struct mm_struct per address space holds pgd, the root of its page-table tree, and the set of VMAs (include/linux/mm_types.h line 388; a red-black tree in 5.10, a maple tree since 6.1); each VMA is a struct vm_area_struct with vm_start, vm_end, flags, an optional vm_file and a table of operations vm_ops that says how to fill a page when it is first touched (line 305). Threads of one process share one mm_struct; that is all "sharing memory" means for threads.

The running job's address space measured (the root's recording of the main process just after its DataLoader workers were forked). Each line of /proc/PID/maps is one VMA: start-end, permissions (r, w, x, and p private or s shared), file offset, device, inode, path.

Selected lines of the real /proc/PID/maps


Read the bars as reserved address space, not memory used: the 54 anonymous mappings add up to 1.5 GiB mainly because of one 1 GiB reservation by the allocator inside libc10.so (the sibling page Memory allocators owns that story). Pages are only spent when touched (section 4).


Limits you can hit
vm.max_map_count caps the number of VMAs per process (default 65,530 in the kernel docs; Docker Desktop's VM sets 262,144, read here). The job uses about 456. A process that maps thousands of files or shards, or an allocator that splits its arena into many protected pieces, gets ENOMEM from mmap long before memory is short; the error message says nothing about VMAs.


cat /proc/PID/maps | wc -l; pmap -x PID | tail -1; cat /proc/sys/vm/max_map_count







2. Page tables: the tree that translates every address


ch. 18 Introduction to Paging, ch. 20 Advanced Page Tables


Pages. Memory is managed in fixed-size pages: 4 KiB on this Linux VM (getconf PAGESIZE prints 4096). A virtual address splits into a virtual page number (high bits) and an offset inside the page (low 12 bits, passed through unchanged). The page table maps each virtual page to a physical page frame, plus permission bits.


Why a tree. One flat table for 236 virtual pages at 8 bytes an entry would be 512 GiB per process. Instead the 36 bits are cut into four 9-bit pieces; each piece indexes a 4 KiB table of 512 eight-byte entries, which points to the next table. Only the tables on the path to a mapped page exist, so a sparse address space costs almost nothing. The arm64 kernel computes the number of levels as (VA_BITS - 4) / (PAGE_SHIFT - 3) (pgtable-hwdef.h line 26): (48 - 4) / (12 - 3) = 4 levels for 4 KiB pages.


The first byte of the job's memory-mapped dataset, 0xffff81fd2000 (from the maps lines above), cut into its four table indices and offset. The Address translator tab does this for any address, on arm64 with 4, 16 or 64 KiB pages and on x86-64 with four or five levels.

The bits do work. Accessed is set by hardware on use: page reclaim reads and clears it to find cold pages (section 6). Dirty says a file page must be written back before reuse. Read-only on a writable mapping is how copy-on-write traps the first write (section 7). Not present is how swap and lazy allocation trap the first access (section 4).


What the tables cost measured
One last-level table (4 KiB) maps 512 pages = 2 MiB, so touching 1 GiB needs 512 tables = 2,048 KiB, plus a few upper-level tables. Measured: VmPTE grew by  KiB after touching 1 GiB. That is 0.2% of the memory mapped, per process: 64 workers each touching the same 10 GiB shared dataset carry 64 copies of its tables (1.3 GiB). With huge pages the kernel still sets aside one table per 2 MiB (section 8), so the measured VmPTE did not shrink.


A process maps a 64 GiB file but only ever reads 1 MiB of it at one spot. Roughly how much page-table memory does that cost?




Tables exist only along paths to touched pages. 1 MiB at one spot needs one last-level table plus one table at each upper level: four 4 KiB tables, 16 KiB. The 128 MiB answer would hold only if every 2 MiB of the file were touched. Mapping is free; touching costs tables and frames.

3. The TLB: why translation is usually free, and when it is not


ch. 19 Translation Lookaside Buffers


The problem. A four-level walk is four extra memory reads for every load and store. How it works. The CPU keeps recent translations in a translation lookaside buffer (TLB): a small cache from virtual page number to frame and permissions. A hit adds nothing; a miss triggers a hardware page-table walk (the walk's reads are themselves cached in the data caches, so a miss costs nanoseconds, not four trips to DRAM). The root page measured it on this machine: one access costs 1.1 ns while the touched pages fit in the TLB and 7.6 ns once they do not, with the knee between 2,048 and 4,096 pages (8 to 16 MiB of TLB reach, entries times page size); with 2 MiB pages the same walk stays at 1.1 ns (Topic: operating-systems, section 4 and the OS simulators tab, which also replays OSTEP's TLB homework).


Address-space identifiers. After a switch to another process, the old translations are wrong. Flushing the whole TLB on every switch would make every switch expensive, so entries are tagged with an ASID (arm64: 8 or 16 bits, read from the CPU at boot, arch/arm64/mm/context.c line 42; x86-64 calls it PCID, 12 bits). Kernel mappings are marked global and shared by all processes; user mappings are "not global" (the nG bit in section 2's table).


TLB shootdowns: the cost of changing a mapping


When a process changes or removes a mapping (munmap, mprotect, madvise(MADV_DONTNEED), page migration, swapping a page out), every CPU that may have cached the old translation must drop it, or a thread there would keep using a page that is no longer theirs. That is a TLB shootdown. The two architectures do it very differently source:


x86-64: interrupt the other CPUs
The kernel sends an inter-processor interrupt to each CPU running the address space and waits for all to flush (arch/x86/mm/tlb.c lines 798 to 825, smp_call_function_many); over 33 pages it flushes everything instead (line 842). Cost grows with the number of CPUs the process has run on.


arm64: one broadcast instruction
The kernel issues TLBI VALE1IS ("inner shareable"), which the hardware broadcasts to every CPU, then waits with a barrier (arch/arm64/include/asm/tlbflush.h lines 255 to 272). No interrupt, no other CPU's code runs.




When it bites in ML. A CPU-heavy process with many threads (PyTorch's intra-op pool, a data loader with threads) whose allocator keeps returning memory to the kernel and asking for it again triggers a shootdown each time; on large x86 servers each costs interrupts on every CPU that ran the process. Symptoms: high system time with no obvious system calls in your code. Fix: keep memory cached in the allocator instead of returning it (the Memory allocators page covers the knobs), fewer threads, huge pages.

4. Page faults: memory is filled in on first touch


ch. 21 Swapping: Mechanisms, ch. 23 Complete VM Systems


The idea. mmap and malloc only add a VMA; no frame is allocated and no table entry written. The first access finds an invalid (or read-only) entry and the CPU raises an exception: a page fault. The kernel looks up the VMA, decides what the page should contain, fills the entry and re-runs the instruction. The program never notices, except in time. A minor fault needs no I/O; a major fault waited for a device (getrusage(2); in 5.10 a fault that had to be retried also counts as major, mm/memory.c lines 4548 to 4557).


One access, followed through the kernel. Pick a case; the stepper walks the real 5.10 code path on arm64 and shows what this machine measured for it.


















Three details that matter. (1) The zero page: a read of never-written anonymous memory maps one shared, read-only page of zeros (mm/memory.c lines 3496 to 3500): measured, reading 64 MiB took  faults and added 0 KiB of RSS; writing it afterwards took the same number of faults again. So "I allocated and read it, but RSS did not grow" is expected. (2) Fault-around: a read fault on a cached file page maps up to 16 neighbouring cached pages at once (fault_around_bytes = 64 KiB, line 3875). The root's warm read of the 2,056-page dataset took exactly 129 minor faults, which is 2,056 / 16 rounded up. (3) MAP_POPULATE (or madvise(MADV_POPULATE_WRITE) since 5.14) pays all faults inside the mmap call: 64 MiB took  ms in the call against  ms by touching page by page, because one call avoids 16,384 trips into the kernel.


You np.empty(10**9, dtype=np.uint8) and immediately call .sum(). Memory use (RSS) afterwards?




A large np.empty is a fresh anonymous mapping (glibc serves big requests with mmap). Reading it faults each page onto the shared zero page: 244,141 minor faults, no new frames. The sum is 0. RSS grows only when you write. (With transparent huge pages enabled for the range, a read fault can instead map a huge zero page; same outcome.)


When it bites in ML. The first epoch is slower than the rest (major faults on the dataset; the root's Debug lab case "The first epoch is slower than the rest: cold and warm page cache"); the first iteration of a step that allocates a big new buffer pays one fault per 4 KiB (1 GiB = 262,144 faults, about 0.27 s at the 1 us measured here, per process); a latency-sensitive server sees spikes when pages are first touched. Fixes: pre-touch (MAP_POPULATE, a warm-up step), huge pages (section 8), keep buffers alive across steps instead of reallocating.

5. mmap: files and memory as one thing


ch. 23 Complete VM Systems (memory-mapped files); the call itself: mmap(2)


The problem. read() copies bytes from the kernel's cache of the file (the page cache, section 6) into your buffer: two copies of the data in memory, a system call per read, and a buffer you must manage. The idea. mmap(addr, length, prot, flags, fd, offset) adds a VMA whose pages are the page-cache pages of the file. The first touch of each page faults (section 4) and maps the cached page directly; nothing is copied.


Two choices make four kinds of mapping. Every mmap is either file-backed or anonymous (MAP_ANONYMOUS: zero-filled, no file), and either shared or private:

SIGBUS, not an exception
If the file shrinks under a mapping (another process truncates or rewrites a dataset shard), touching a page past the new end raises SIGBUS and the process dies (mmap(2), SIGBUS). So does an I/O error on a network file system while faulting. Replace shared datasets by writing a new file and renaming it over the old one; mappings of the old file keep working.


Random rows from a dataset: read() against mmap measured


20,000 random rows of 1,028 bytes (the job's row format) from a 256 MiB file, warm (in the page cache) and cold (evicted with posix_fadvise(POSIX_FADV_DONTNEED), which any process may do for clean pages). The rows are 19.6 MiB of useful data. "Read from storage" is read_bytes in /proc/self/io.




What happened. Warm, all three cost about 1 to 2 microseconds a row, dominated by Python. Cold, a fault on a mapping reads around the faulting page (a window of read_ahead_kb, 128 KiB by default), betting on locality: for random rows over a small file it pulled in the whole file (13x the useful bytes) and then served the rest from memory, which made it the fastest here. On a dataset much larger than RAM the same bet reads 32 pages to use one, and fills the page cache with neighbours you will not touch. madvise(MADV_RANDOM) turns read-around off: one page per fault, 3.4x amplification, but one device round trip per row. The right setting depends on whether neighbours will be used: a shuffled index over a huge file wants MADV_RANDOM or explicit pread; a sequential pass or a small hot file wants the default (or MADV_SEQUENTIAL, MADV_WILLNEED).


Loading weights: copy or map measured


A 256 MiB state dict (eight 32 MiB float32 tensors) saved with torch.save and with safetensors, loaded cold four ways. "Return" is the time until the call returns; then every tensor is summed once.




torch.load reads every byte into fresh anonymous memory before returning. torch.load(mmap=True), in its own words, maps the file "rather than loading all the storages into memory" (docstring of torch 2.14.1), and safetensors (whose format is "fast (zero-copy)", safetensors docs) returns tensors whose storage is the mapping: the call returns in milliseconds, and the bytes arrive as page faults when first used. Two consequences: (1) RSS after reading counts those file pages, but they are clean page cache, so the kernel can drop and re-read them, and every process mapping the same file shares one copy (eight inference workers on one host cost one copy of the weights, not eight); (2) the first forward pass is slower, by the fault and I/O cost moved out of the load call. safe_open plus get_tensor reads only the tensors asked for, which is how one rank of a sharded model loads only its shard.


Eight inference processes on one host each torch.load(path, mmap=True) the same 14 GB checkpoint and run. Free memory drops by about how much for the weights?




All eight map the same page-cache pages of one file, so the weights occupy RAM once (as "buff/cache" in free). Each process's RSS still shows up to 14 GB, which is why RSS sums mislead (section 13). The catch: if a process converts or moves the tensors (to another dtype, or to a GPU and then keeps a CPU copy), that copy is private anonymous memory, eight times over.

6. The page cache and reclaim: where "free" memory went


ch. 22 Swapping: Policies (LRU and its approximations)


The idea. Linux keeps file data that was read or written in otherwise unused RAM, the page cache, because RAM that holds nothing is wasted. free shows it as "buff/cache"; "available" estimates what could be handed to programs if they asked, mostly by dropping clean cache. Writing, flushing and fsync of cached data belong to the sibling page Storage and file systems; here we care about how memory is taken back.


Reclaim. Each memory zone has three watermarks of free pages. Below low, the kernel thread kswapd wakes and reclaims in the background until high; below min, an allocating process must reclaim by itself before it gets memory (direct reclaim), which shows up as stalls in that process. In 5.10, low = min + max(min / 4, managed × watermark_scale_factor / 10,000) and high = min + 2 × that (mm/page_alloc.c lines 7874 to 7880). Here min_free_kbytes is  KiB and the scale factor is 10, so low and high sit about 11 MiB and 22 MiB above min (summed over zones). Raising watermark_scale_factor starts background reclaim earlier, a common fix for allocation stalls on big-memory hosts.


Which pages go. Linux 5.10 keeps two lists per type (anonymous and file), active and inactive, an approximation of least-recently-used built on the hardware accessed bit (section 2): pages are scanned from the inactive tail; one that was referenced since gets another chance. Clean file pages are cheapest to drop (re-read later); dirty ones must be written first; anonymous pages can only go to swap. vm.swappiness (60 here, the default, mm/vmscan.c line 172) weighs anonymous against file reclaim. Linux 6.1 added the multi-generational LRU, which replaces the two lists with several age generations and scans page tables instead of reverse mappings (multigen_lru docs) not run here.


Inside a container, the same reclaim runs against the cgroup's limit instead of the machine's: reading a 768 MiB file in a 512 MiB container filled the cache up to the limit and recycled it, with thousands of "max" events and no OOM kill. The Memory replay tab replays it sample by sample.

7. Copy-on-write: fork copies tables, writes copy pages


ch. 23 Complete VM Systems (copy-on-write); the fork API: the sibling Processes and the system-call API


The problem. fork must give the child an exact copy of the parent's memory. Copying gigabytes for a DataLoader worker that will read a few batches would take seconds and double memory. How it works source: fork copies the page tables, not the pages, and marks every private writable entry read-only in both parent and child (copy_present_pte, mm/memory.c lines 878 to 880). Both now share each frame. The first write by either side faults on a read-only entry of a writable VMA; do_wp_page sees the frame is shared and wp_page_copy (line 2817) copies that one 4 KiB page and gives the writer its own. A page with only one user left is simply made writable again.




What this costs measured. fork + exit + wait grows with the parent's resident memory, about 19 microseconds per resident MiB with 4 KiB pages (the tables being copied), and is 30x cheaper at 1 GiB when the memory is in transparent huge pages (one entry per 2 MiB, copy_huge_pmd). Each later write costs a fault and a copy:  ns per 4 KiB page. With huge pages the first write does not copy 2 MiB: 5.10 splits the huge entry and falls back to 4 KiB copies (mm/huge_memory.c lines 1315 to 1317); measured, the child's writes took the same 65,538 faults at  ns each.


Python turns reads into writes, twice


The root page showed reference counts: reading a Python object increments and decrements its count, which writes the page it sits on, so a forked worker that only reads a list of a million objects copies the pages holding them (PyTorch's "memory leak" that is not a leak, torch.utils.data docs). The second writer is the cyclic garbage collector: a full collection writes a counter (gc_refs) into the header of every container object it tracks, so a gc.collect() in a worker copies every page of tracked objects even if your code never reads them. Measured: a parent builds one million two-element lists, forks, and the child does one thing:


Pages the child copied (growth of its Private_Dirty in /proc/self/smaps_rollup), Python 3.11.2, numpy 2.4.6. Reading every list copied about 61 MiB: the pages that hold the list objects themselves (the integers inside were not touched).


The fix the Python docs give for exactly this: "call gc.disable() early in the parent process, gc.freeze() right before fork(), and gc.enable() early in child processes" (gc.freeze, Python 3.7+). gc.freeze() moves every tracked object into a permanent generation that collections skip: 30 pages copied instead of 16,817. It does not stop reference-count writes; for data you iterate, store it as NumPy arrays, Arrow tables or one big bytes buffer with offsets (63 pages), not as millions of Python objects.


Your Dataset holds a list of 50 million file paths (Python strings). With 8 fork-started workers, what happens to memory over the first epoch?




Every access to paths[i] touches the string's reference count, and any garbage collection in a worker touches every tracked container. Shared pages turn private one 4 KiB page at a time, so each worker's USS climbs as the epoch reads more of the list. Store the paths as one NumPy byte array plus offsets (or Arrow), and gc.freeze() before the DataLoader forks. The root's Debug lab case "Worker memory grows: copy-on-write meets reference counts" measures it per worker.


Related flags. madvise(MADV_DONTFORK) keeps a range out of the child entirely, "useful to prevent copy-on-write semantics from changing the physical location of a page if the parent writes to it after a fork" (DMA buffers, section 9); MADV_WIPEONFORK gives the child zeros instead (madvise(2)). Forking a process that runs threads has its own trap (a lock held by a thread that does not exist in the child): the root's Debug lab case "A worker hangs forever: fork while another thread holds a lock".

8. Huge pages: one entry for 2 MiB


ch. 19 TLBs (larger pages), ch. 20 Advanced Page Tables


The idea. A level-2 entry can point straight at a 2 MiB block instead of a table (with 4 KiB base pages; 1 GiB at level 1). One TLB entry then covers 512 small pages, a walk is one level shorter, and a fault fills 2 MiB at once. Linux offers two ways: transparent huge pages (THP), used automatically for anonymous memory where possible, and hugetlbfs, a pool of huge pages reserved in advance.


The same 64 MiB buffer, with 4 KiB pages and with THP measured. Toggle the mode; every number is from this machine.















The knobs (values read on this VM). /sys/kernel/mm/transparent_hugepage/enabled is always, madvise (only ranges marked madvise(MADV_HUGEPAGE)) or never; here madvise. defrag says whether a fault may stall to compact memory into a free 2 MiB block; here madvise (stall only for marked ranges). The background thread khugepaged later collapses 512 small pages into a huge one, scanning  pages per pass, and with max_ptes_none =  it will collapse a range in which 511 of 512 pages were never touched, filling them with zeros (transhuge docs). Watch AnonHugePages in /proc/meminfo or a process's smaps_rollup.


The costs
(1) Bloat: touching one byte in every 2 MiB of 256 MiB cost  KiB with 4 KiB pages and  KiB with THP, x more, for sparse structures (hash tables, sparse embedding rows, an arena with holes). (2) Latency: the first THP run took  ms against  ms later, consistent with the kernel having to find or compact free 2 MiB blocks (cause not confirmed here); on a long-running, fragmented host, compaction stalls are the classic THP complaint. (3) No page-table saving: for each huge page the kernel deposits a spare 4 KiB table so it can split the page later (mm/huge_memory.c line 623), so VmPTE after touching 1 GiB was  KiB either way.


Where huge pages do save: fork. fork copies one table entry per huge page instead of 512. The sibling Processes and the system-call API measured os.fork() from a process holding torch and 1 GiB of NumPy at 5.96 ms with NumPy's huge pages (its default) against 22.5 ms with NUMPY_MADVISE_HUGEPAGE=0.


hugetlbfs not run here. An administrator reserves a pool (vm.nr_hugepages, or per size under /sys/kernel/mm/hugepages/); programs get pages from it with mmap(MAP_HUGETLB) or files in a hugetlbfs mount. Pool pages are never swapped, never split, and never bloat, but are taken from the machine even when unused. This arm64 kernel offers 64 KiB, 2 MiB, 32 MiB and 1 GiB sizes (its cgroup lists hugetlb.64KB, 2MB, 32MB, 1GB; 64 KiB and 32 MiB use arm64's contiguous bit, 16 adjacent entries cached as one); the pool here is empty (HugePages_Total: 0) and filling it needs privileges (hugetlbpage docs).


In ML. The root found that this PyTorch wheel's allocator reserves 1 GiB and marks it MADV_HUGEPAGE, so tensor memory gets THP even in madvise mode (Syscall tracer tab of Topic: operating-systems). Big dense tensors and pinned staging buffers are ideal THP users; sparse, long-lived structures in a always system are where bloat appears. Fix for bloat: madvise mode, or MADV_NOHUGEPAGE on the sparse range, or max_ptes_none lower.


cat /sys/kernel/mm/transparent_hugepage/{enabled,defrag}; grep -E 'AnonHugePages|HugePages_' /proc/meminfo; grep thp /proc/vmstat






9. Locked and pinned memory: pages that must not move


The problem. Normally the kernel may move a page (compaction, NUMA migration, THP collapse) or write it to swap, because only the page table knows where it is and the table is updated. A device that copies memory by itself (DMA: a GPU, a network card doing RDMA) holds a physical address and does not consult the page table. If the page moves mid-copy, the device reads someone else's data.


Two mechanisms. mlock(addr, len) faults the range in and keeps it resident: never swapped (mlock(2)). Pinning is stronger and kernel-internal: a driver calls pin_user_pages (the FOLL_PIN flavour of get_user_pages, pin_user_pages docs) and the pages may not be moved or freed until it unpins them. Both take memory out of what reclaim can use.


The limit measured. Unprivileged locking is capped by RLIMIT_MEMLOCK, which is 64 KiB in a default Docker container:




That ENOMEM ("Cannot allocate memory") is the error an RDMA library or a pinned-memory allocator reports inside a container whose limit was never raised, and it does not mention the limit. Raise it with docker run --ulimit memlock=-1, LimitMEMLOCK=infinity in a systemd unit, or /etc/security/limits.conf; CAP_IPC_LOCK bypasses it.


Pinned memory for GPU copies not run here


cudaHostAlloc / cudaMallocHost "Allocates size bytes of host memory that is page-locked and accessible to the device", with the warning that "allocating excessive amounts of pinned memory may degrade system performance, since it reduces the amount of memory available to the system for paging"; cudaHostRegister page-locks an existing range (CUDA runtime API, memory management). The reason it matters: "when CUDA sends pageable data from CPU to GPU, it must first create a page-locked copy of that data before making the transfer" (PyTorch pinned memory tutorial), an extra copy through a staging buffer. In PyTorch:


    

  • DataLoader(pin_memory=True) runs a thread that copies each batch into pinned memory, so x.to("cuda", non_blocking=True) can be an asynchronous DMA that overlaps compute.
    • 

  • Calling t.pin_memory() right before one copy is usually slower than copying directly (it pays the staging copy itself); pin once, reuse.
    • 

  • The tutorial warns that "allocating a large number of tensors or sizable tensors in pinned memory can monopolize a substantial portion of RAM": pinned pages cannot be reclaimed, so the page cache that feeds your data loader shrinks.
    • 

  • Copies from pinned memory with non_blocking=True are asynchronous: modifying the source tensor before the copy finished corrupts the GPU copy.
    • 

  • PyTorch's pinned memory comes from its CachingHostAllocator, which rounds each request up to the next power of two by default, so a 600 MB pinned buffer locks 1 GiB of RAM (Memory allocators reads the source).
    • 



The GPU driver's own side of this (its kernel module, unified memory, IOMMU mappings) is in the sibling Virtualization and the GPU driver stack.


ulimit -l; grep VmLck /proc/PID/status; grep -E 'Mlocked|Unevictable' /proc/meminfo







10. Overcommit: promising more memory than exists


The problem. Programs reserve far more than they touch (allocator arenas, thread stacks, sparse arrays, a 1 GiB reservation by PyTorch's allocator). Refusing every reservation that exceeds RAM would waste memory; accepting all means some promise may not be kept. The kernel's choice is vm.overcommit_memory source (overcommit-accounting; mm/util.c lines 860 to 876):


ModeRule in 5.10Consequence


0, heuristic (default)refuse one request larger than RAM + swap; accept the restwild requests fail, everything else succeeds; the OOM killer settles the bill


1, always (this VM)accept everythingsparse arrays work; the 64 GiB request below succeeded


2, nevertotal commitments (Committed_AS) may not exceed CommitLimit = RAM × overcommit_ratio% + swap; "In mode 2 the MAP_NORESERVE flag is ignored"allocations fail with ENOMEM instead of later OOM kills; programs that reserve big address ranges fail to start




Measured on this VM (mode 1, ratio 50). CommitLimit = 10,189,980 × 50% + 1,048,572 = 6,143,562 KiB against  KiB reported (the same, to page rounding; vm_commit_limit, mm/util.c line 805). A private writable 64 GiB mapping succeeded and pushed Committed_AS to about 11.6 times CommitLimit; with MAP_NORESERVE it was not counted at all; malloc(32 GiB) returned a pointer:




Under mode 0 the 64 GiB request would have failed (larger than RAM + swap, 10.7 GiB); under mode 2 so would anything that took commitments past 5.9 GiB. Containers cannot change this setting: it is one value for the whole kernel. When it bites: a cluster that sets mode 2 for safety makes large virtual reservations (CUDA's and allocators' address-space reservations, big np.empty scratch buffers) fail at allocation time; read CommitLimit and Committed_AS before blaming the framework.

11. Swap, zswap and memory pressure


ch. 21 Beyond Physical Memory: Mechanisms, ch. 22 Policies


How it works. Anonymous pages have no file to be re-read from, so to reclaim one the kernel writes it to a swap device, replaces the table entry with a not-present entry holding the swap location, and frees the frame. The next access is a major fault: do_swap_page reads it back (handle_pte_fault, mm/memory.c line 4377), reading 2page-cluster = 8 neighbouring swap slots at once (vm.page-cluster = 3 here).


What it costs measured. A process that needs 640 MiB in a container limited to 512 MiB with 512 MiB of swap allowed did not die; it ran with about 260 MiB in swap and every pass over its memory took 4 to 5 seconds, the same pass that takes milliseconds when it fits (Memory replay tab, scenario "Swap allowed"; the root's Debug lab case "Not dead, just slow: the working set spills into swap" has the per-pass numbers). For a training job that is usually worse than being killed: it looks alive, holds its GPUs, and makes no progress.


zswap and zram not run here (neither is built into this kernel). zswap is a compressed cache in front of a swap device: pages being swapped out are compressed into a RAM pool first and written to disk only when the pool is full (zswap docs). zram is a compressed RAM block device used as swap. Both trade CPU for fewer disk reads.


Pressure stall information not run here (not enabled in this kernel). With PSI, /proc/pressure/memory and each cgroup's memory.pressure report the share of time tasks were stalled waiting for memory (some and full, over 10, 60 and 300 s) (PSI docs). It is the best single "is this job memory-starved" signal; systemd-oomd kills on it (systemd-oomd).


swapon --show; vmstat 1   # si/so columns; grep -E 'pswpin|pswpout' /proc/vmstat






12. Memory cgroups and the OOM killer: what happens at the limit


The problem. On a shared host each job (container, pod, Slurm step) needs a memory budget, and when the budget or the machine runs out, someone must lose. How it works. A cgroup v2 memory controller charges every page a process in the group allocates to the group, and reclaims within the group when it reaches its limit. What is charged: "userland memory - page cache and anonymous memory", kernel structures such as dentries and inodes, and TCP socket buffers (cgroup-v2 docs, Memory). The files, in each cgroup's directory (/sys/fs/cgroup/ inside a container):


FileMeaning


memory.currentbytes charged now, page cache included


memory.maxhard limit: reclaim, then the OOM killer inside the group (docker --memory, a Kubernetes memory limit)


memory.high"Memory usage throttle limit... Going over the high limit never invokes the OOM killer": the group's tasks are made to reclaim and are put to sleep, up to 2 s per return to user space in 5.10 (MEMCG_MAX_HIGH_DELAY_JIFFIES, mm/memcontrol.c line 2466) (not run on this page: Docker 20.10 has no flag for it and the container cannot write its own cgroup; Containers and isolation ran it from the host, with and without swap)


memory.low, memory.minprotection: below these the group's memory is reclaimed only reluctantly, or never


memory.swap.maxswap allowed (docker --memory-swap minus --memory)


memory.eventscounters: high, max (times the limit forced reclaim), oom, oom_kill


memory.statthe breakdown: anon, file (page cache, includes shmem), shmem, file_dirty, sock, ...


memory.oom.groupif 1, "all tasks belonging to the cgroup or to its descendants are killed together or not at all"




Four runs at a 512 MiB limit measured, replayed sample by sample in the Memory replay tab:




The fourth run is the one to remember for data loading: files in /dev/shm are shared memory charged to the cgroup, they survive the process that wrote them, and no process's RSS shows them. DataLoader workers hand batches to the main process through such files; the root's Debug lab case "DataLoader workers run out of /dev/shm" shows the other way it fails (Docker's default 64 MiB /dev/shm), and PyTorch's own README says to raise it "either with --ipc=host or --shm-size" (PyTorch README).


Who the OOM killer picks, from the source


When reclaim fails, oom_badness scores every candidate process (mm/oom_kill.c lines 201 to 238) and the highest score is sent SIGKILL:


points = rss + swap + page_tables / 4 KiB + oom_score_adj × ⌊totalpages / 1000⌋


rss
resident pages: anonymous, file-mapped and shmem (in pages)
swap
pages of this process in swap
oom_score_adj
-1000 (never kill) to +1000, per process, in /proc/PID/oom_score_adj
totalpages
machine OOM: RAM + swap. cgroup OOM: memory.max + allowed swap (mem_cgroup_get_max, line 1690)


/proc/PID/oom_score shows (1000 + points × 1000 / totalpages) × 2 / 3, always with the machine's RAM + swap (fs/proc/base.c lines 549 to 566). Four processes in a 1 GiB container, the formula against the kernel's number measured:






In a 1 GiB container with no swap, process A holds 450 MiB (adj 0) and process B 250 MiB but set its own oom_score_adj to 500. The group hits its limit. Who dies?




totalpages = 262,144 (1 GiB of 4 KiB pages), so adj 500 adds 500 × 262 = 131,000 points, worth 512 MiB of RSS. A scores about 115,200 + 0; B about 64,000 + 131,000 = 195,000. B dies. The root's Debug lab case "Which process the OOM killer picks: oom_score and oom_score_adj" ran exactly this and B was killed. Raising your own adj is allowed; lowering it below its current value needs CAP_SYS_RESOURCE, which a default container lacks (measured: refused).


Kubernetes sets the adj for you by quality-of-service class: Guaranteed -997, BestEffort 1000, Burstable min(max(2, 1000 - (1000 × memoryRequestBytes) / machineMemoryCapacityBytes), 999) (node-pressure eviction docs). So when the node runs out, a pod with a small request relative to the node is killed first; when a container exceeds its own limit, its cgroup OOM kills inside it regardless.


What an OOM kill looks like
No Python exception, no traceback: SIGKILL cannot be caught. The shell says Killed; the exit code is 137 (128 + 9); Kubernetes reports OOMKilled; the kernel log has "Memory cgroup out of memory: Killed process" (dmesg, not readable in an unprivileged container); memory.events counts oom_kill. A Python MemoryError is a different event: an allocation the kernel refused (mode 2, an rlimit, a 32-bit limit), which the root's Debug lab sets side by side.


cat /sys/fs/cgroup/memory.{current,max,events}; grep -E '^(anon|file|shmem) ' /sys/fs/cgroup/memory.stat; cat /proc/PID/oom_score{,_adj}







13. RSS, PSS, USS: three answers to "how much memory does it use?"


The problem. Shared pages (libraries, the page cache of a mapped file, copy-on-write pages after fork) are resident for several processes at once. Adding up per-process numbers counts them several times. Three measures, all from /proc/PID/smaps_rollup:


RSSresident set: every resident page mapped by the process, shared or not. Sums overcount.
PSSproportional set: each page divided by the number of processes mapping it. Sums are right.
USSunique set: Private_Clean + Private_Dirty, what you would get back by killing this one process.


The running job, measured while training (main process and its two fork-started DataLoader workers):




The workers' RSS of about 250 MiB each is nearly all Shared_Dirty: the parent's heap and the imported torch, inherited by fork and not yet written. Their USS, what each really adds, is under 9 MiB. Over an epoch, copy-on-write (section 7) is what turns Shared_Dirty into Private_Dirty, so watch USS per worker, not RSS. Which number a tool reports: ps and top show RSS; smem shows PSS and USS; container tools and Kubernetes read the cgroup (memory.current, which also includes page cache), which is a fourth answer.


for p in $(pgrep -f train.py); do grep -E '^(Rss|Pss|Private)' /proc/$p/smaps_rollup; done; smem -P train.py

15. ML recipes: the mechanisms put to work




Datasets: map, do not load
Store samples in one or a few large files (a NumPy array, Arrow, a packed binary with an index) and np.memmap them, as the running job does. Workers then share one page-cache copy and pay only faults. For shuffled access to a dataset larger than RAM, prefer MADV_RANDOM or pread per sample (section 5); for sequential shards, the default read-around. Never replace a mapped file in place (SIGBUS); write and rename.


Weights: safetensors or mmap=True
Loading returns in milliseconds and many processes share one copy; the first forward pass pays the faults. Read only your shard with safe_open. Converting dtype or moving to GPU creates private copies: drop the CPU tensors afterwards.


DataLoader workers: keep the parent lean
Fork-started workers share the parent copy-on-write, and Python's reference counts and GC copy whatever they touch. Hold metadata in NumPy or Arrow, not lists of objects; call gc.freeze() before creating the iterator; watch USS per worker (section 13). Spawn or forkserver avoid the sharing altogether at the cost of start-up time (the root measured 0.021 s fork against 0.836 s spawn to the first batch).


/dev/shm: size it and count it
Batches travel through shared memory: give the container --shm-size (or --ipc=host) of at least workers × prefetch factor × batch bytes, and remember it is charged to the memory limit and survives a killed process (section 12).


Pinned memory: pin once, not too much
pin_memory=True plus non_blocking=True overlaps host-to-device copies with compute; raise memlock in containers; budget pinned bytes as unreclaimable (section 9).


Limits: know which one kills you
Read memory.max, memory.events and memory.stat from inside the job and log them; an exit code 137 with oom_kill incremented is the cgroup, not your code. Leave headroom for page cache and /dev/shm. If swap is allowed, alert on memory.swap.current: a swapping training job is a stalled one.









Common mistakes


"RSS says each worker uses 250 MiB, so 8 workers need 2 GB."
RSS counts shared pages in every process. Measured here: three processes, 815 MiB of RSS, 345 MiB of PSS, 104 MiB of USS. Use PSS for totals and USS for "what does one more worker cost".


"The allocation succeeded, so the memory is there."
With overcommit (modes 0 and 1) an allocation is a promise; memory is taken at first touch, and the OOM killer settles any shortfall later, at a random-looking moment.


"free shows almost no free memory: we have a leak."
Look at "available", not "free". The page cache fills idle RAM on purpose and is given back on demand.


"The container's memory is full of page cache, so it is about to be killed."
Clean page cache is reclaimed at the limit (measured: thousands of "max" events, no kill). What kills is anonymous memory and shared memory that cannot be reclaimed without swap.


"Our workers only read the dataset, so copy-on-write cannot copy anything."
In Python, reading an object writes its reference count, and the garbage collector writes every tracked object's header. Measured: 15,732 pages copied by reading a list, 16,817 by one gc.collect(), 30 after gc.freeze().


"Huge pages always help."
They cut faults and TLB misses for dense memory, but bloat sparse memory (298x in the measurement here), can stall allocations on compaction, and do not reduce page-table memory in Linux.


"Set oom_score_adj = -1000 on the trainer so it is never killed."
Inside a default container you cannot lower it (no CAP_SYS_RESOURCE), and if you could, the kernel would kill something else, perhaps the data loader or the node agent. Size the limit instead.


"pin_memory() before every .to('cuda') makes copies faster."
Pinning is itself a copy; doing it per transfer is usually slower than letting CUDA stage the copy. Pin buffers you reuse (the DataLoader's pinning thread does this).







Interview questions


Walk through what happens on the first write to a freshly malloc'd 1 GiB buffer.
glibc serves it with an anonymous private mmap: a new VMA, no frames. The first store to each page misses the TLB; the hardware walk finds no valid entry; the CPU raises a fault; the kernel finds the VMA (writable, anonymous), allocates any missing table levels, takes a zeroed frame, writes the entry and resumes the store (do_anonymous_page). 262,144 such faults, about 1 us each here. With THP for the range, 512 faults of 2 MiB each. RSS grows as pages are touched, not at malloc.


Why is fork fast even for a process using 50 GB, and when is it not?
Fork copies page tables and marks private pages read-only; pages are copied lazily on write. The table copy is still proportional to resident memory: about 19 us per resident MiB measured here with 4 KiB pages (about 1 s for 50 GB), 30x less with huge pages. After fork, every page either side writes costs a fault and a 4 KiB copy, which is where DataLoader worker memory comes from.


What is a TLB shootdown and why can munmap be expensive in a multi-threaded program?
Removing or changing a mapping requires every CPU that may cache the old translation to drop it. x86 interrupts each such CPU and waits; arm64 broadcasts a TLBI instruction. Measured here on arm64, an mprotect that must flush cost about 1.9 us regardless of how many other threads ran, against 0.65 us when nothing was cached.


Explain RSS, PSS and USS, and which one you would alert on for a fleet of identical workers.
RSS counts all resident mapped pages, PSS divides shared pages among sharers, USS counts private pages only. Alert on USS growth per worker (copy-on-write and leaks show there) and on the cgroup's memory.current minus reclaimable cache for the pod as a whole.


A training pod dies with exit code 137 and no traceback. How do you confirm the cause and fix it?
137 = 128 + SIGKILL. Check memory.events (oom_kill), Kubernetes' OOMKilled reason, or the kernel log. Then find what grew: memory.stat anon vs file vs shmem (DataLoader shared memory counts), worker USS (copy-on-write), pinned memory. Fix the growth or raise the limit; do not rely on swap.


Why does mmap'ing model weights let 8 server processes share memory, and what breaks the sharing?
All map the same page-cache pages of the file (MAP_SHARED or read-only private), so RAM holds one copy. Any write to a private mapping, a dtype conversion, or a copy into a new tensor creates private anonymous pages per process.
