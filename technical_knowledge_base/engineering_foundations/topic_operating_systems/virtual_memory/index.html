The idea

Every address a program uses is virtual: the hardware translates it page by page through a per-process tree of tables, and the kernel fills that tree lazily, one page at a time, at first touch. Everything else (mmap, copy-on-write, huge pages, swap, the OOM killer) is a way of filling, sharing, enlarging or taking back pages.

  1. One process, one address space. The running job's main process as the root recorded it in /proc/PID/maps (section 1): the code of its .so files, the memory-mapped dataset, /dev/shm, the heap, the stack and anonymous memory that is mostly one 1 GiB allocator reservation. Widths follow the address space each kind takes, on a square-root scale.
  2. Every access is translated. Every load and store goes through the TLB and, on a miss, the page tables (sections 2 and 3) before it reaches a physical frame.
  3. Frames come from three places. Written anonymous memory (heap, tensors) gets its own zeroed frames (section 4); file mappings are the page cache's frames, shared by every process that maps the file (sections 5 and 6); anonymous memory that was only read maps the one shared zero page. The untouched reservation maps nothing.
  4. Below memory: files and swap. Clean page-cache frames can be dropped and read again from their file; anonymous frames have no file, so reclaim can only write them to swap (sections 6 and 11).
  5. The container's budget. The dashed box is what the container's memory.max counts: anonymous frames, page cache and /dev/shm alike (section 12). Copy-on-write, huge pages and the OOM killer are ways of sharing, enlarging or taking back these frames.

1. The address space: what one process sees

Every process gets its own address space: a private range of addresses that the hardware translates to real memory on every access, so processes cannot see each other's data yet can share what is identical (the code of libtorch_cpu.so, the dataset file). On 64-bit Linux the user part is 248 bytes (256 TiB) on arm64 with 4 KiB pages and 247 bytes (128 TiB) on x86-64 with four-level tables (arm64 memory layout; x86-64 memory map). Almost all of it is empty. What exists is a list of mappings (virtual memory areas, VMAs): contiguous ranges with one set of permissions and one source, a file or anonymous zero-filled memory. Threads of one process share one address space; that is all "sharing memory" means for threads.

The 54 anonymous mappings add up to 1.5 GiB mainly because of one 1 GiB reservation by the allocator inside libc10.so (the sibling Memory allocators owns that story). Pages are only spent when touched (section 4).

A limit you can hit
vm.max_map_count caps the number of VMAs per process (default 65,530 in the kernel docs; Docker Desktop's VM sets 262,144, read here). The job uses about 456. A process that maps thousands of files or shards, or an allocator that splits its arena into many protected pieces, gets ENOMEM from mmap long before memory is short, and the error says nothing about VMAs.

2. Page tables: the tree that translates every address


Memory is managed in fixed-size pages: 4 KiB here (getconf PAGESIZE prints 4096). A virtual address splits into a virtual page number (high bits) and an offset inside the page (low 12 bits, passed through unchanged). The page table maps each virtual page to a physical page frame, plus permission bits.


Why a tree. One flat table for 236 virtual pages at 8 bytes an entry would be 512 GiB per process. Instead the 36 bits are cut into four 9-bit pieces; each indexes a 4 KiB table of 512 eight-byte entries, which points to the next table. Only the tables on the path to a mapped page exist, so a sparse address space costs almost nothing. The arm64 kernel computes the number of levels as (VA_BITS - 4) / (PAGE_SHIFT - 3) (pgtable-hwdef.h line 26): (48 - 4) / (12 - 3) = 4 levels for 4 KiB pages.


    

  1. The address. 0xffff81fd2000, the first byte of the job's memory-mapped dataset (from the maps lines in section 1), splits into four 9-bit indices (511, 510, 15, 466) and a 12-bit offset (0x0). Each index picks one of 512 entries in a 4 KiB table. The Address translator tab does this for any address, on arm64 with 4, 16 or 64 KiB pages and on x86-64 with four or five levels.
    2. 

  2. TLB miss. The CPU looks for virtual page 0xffff81fd2 in the TLB and misses. The walk starts at TTBR0_EL1, the register holding the physical address of this process's level 0 table (CR3 on x86-64); a process switch reloads it.
    3. 

  3. Level 0. Memory read 1: entry 511 of the level 0 table holds the frame of a level 1 table. Each level 0 entry covers 512 GiB of addresses.
    4. 

  4. Level 1. Memory read 2: entry 510 of the level 1 table points at a level 2 table. A level 1 entry covers 1 GiB; a 1 GiB huge page would end the walk here.
    5. 

  5. Level 2. Memory read 3: entry 15 points at a level 3 table. A level 2 entry covers 2 MiB; a 2 MiB huge page (section 8) ends the walk here, one level shorter.
    6. 

  6. Level 3. Memory read 4: entry 466 holds the frame number of the data page and its permission bits. Physical address = frame x 4096 + offset.
    7. 

  7. TLB fill. The translation is cached in the TLB: every later access to this 4 KiB page skips all four reads. The root measured 1.1 ns per access while the pages fit in the TLB and 7.6 ns once they do not.
    8. 



The indices are computed from the address (arm64, 4 KiB pages); table and frame numbers are illustrative (reading real frame numbers from /proc/PID/pagemap needs privileges).


The bits do work. Accessed is set by hardware on use: page reclaim reads and clears it to find cold pages (section 6). Dirty says a file page must be written back before reuse. Read-only on a writable mapping is how copy-on-write traps the first write (section 7). Not present is how swap and lazy allocation trap the first access (section 4).


What the tables cost measured
One last-level table (4 KiB) maps 512 pages = 2 MiB, so touching 1 GiB needs 512 tables = 2,048 KiB, plus a few upper-level tables. Measured: VmPTE grew by  KiB after touching 1 GiB. That is 0.2% of the memory mapped, per process: 64 workers each touching the same 10 GiB shared dataset carry 64 copies of its tables (1.3 GiB). With huge pages the kernel still sets aside one table per 2 MiB (section 8), so the measured VmPTE did not shrink.


A process maps a 64 GiB file but only ever reads 1 MiB of it at one spot. Roughly how much page-table memory does that cost?




Tables exist only along paths to touched pages. 1 MiB at one spot needs one last-level table plus one table at each upper level: four 4 KiB tables, 16 KiB. The 128 MiB answer would hold only if every 2 MiB of the file were touched. Mapping is free; touching costs tables and frames.

3. The TLB: why translation is usually free, and when it is not


A four-level walk is four extra memory reads for every load and store, so the CPU keeps recent translations in a translation lookaside buffer (TLB), a small cache from virtual page number to frame and permissions. A hit adds nothing; a miss triggers the hardware walk of section 2 (its reads are themselves cached in the data caches, so a miss costs nanoseconds, not four trips to DRAM). The root page measured it on this machine: one access costs 1.1 ns while the touched pages fit in the TLB and 7.6 ns once they do not, with the knee between 2,048 and 4,096 pages (8 to 16 MiB of TLB reach, entries times page size); with 2 MiB pages the same walk stays at 1.1 ns (Topic: operating-systems, section 4 and the OS simulators tab, which also replays OSTEP's TLB homework). The Address translator tab sizes the reach for any footprint.


Address-space identifiers: why a process switch does not flush the TLB
After a switch to another process the old translations are wrong, and flushing the whole TLB on every switch would make switches expensive, so entries are tagged with an ASID (arm64: 8 or 16 bits, read from the CPU at boot, arch/arm64/mm/context.c line 42; x86-64 calls it PCID, 12 bits). Kernel mappings are global and shared by all processes; user mappings are "not global" (the nG bit).


TLB shootdowns: the cost of changing a mapping


When a process changes or removes a mapping (munmap, mprotect, madvise(MADV_DONTNEED), page migration, swapping a page out), every CPU that may have cached the old translation must drop it, or a thread there would keep using a page that is no longer its own. That is a TLB shootdown, and the two architectures do it very differently source:


x86-64: interrupt the other CPUs
The kernel sends an inter-processor interrupt to each CPU running the address space and waits for all to flush (arch/x86/mm/tlb.c lines 798 to 825, smp_call_function_many); over 33 pages it flushes everything instead (line 842). Cost grows with the number of CPUs the process has run on.


arm64: one broadcast instruction
The kernel issues TLBI VALE1IS ("inner shareable"), which the hardware broadcasts to every CPU, then waits with a barrier (arch/arm64/include/asm/tlbflush.h lines 255 to 272). No interrupt, no other CPU's code runs.


When it bites in ML. A CPU-heavy process with many threads (PyTorch's intra-op pool, a data loader with threads) whose allocator keeps returning memory to the kernel and asking for it again triggers a shootdown each time; on large x86 servers each costs interrupts on every CPU that ran the process. Symptom: high system time with no obvious system calls in your code. Fix: keep memory cached in the allocator instead of returning it (the Memory allocators page covers the knobs), fewer threads, huge pages.

4. Page faults: memory is filled in on first touch


mmap and malloc only add a VMA; no frame is allocated and no table entry written (demand paging). The first access finds an invalid (or read-only) entry and the CPU raises a page fault: the kernel looks up the VMA, decides what the page should contain, fills the entry and re-runs the instruction. The program never notices, except in time. A minor fault needs no I/O; a major fault waited for a device (getrusage(2); in 5.10 a fault that had to be retried also counts as major, mm/memory.c lines 4548 to 4557).

5. mmap: files and memory as one thing


read() copies bytes from the kernel's cache of the file (the page cache, section 6) into your buffer: two copies of the data in memory, a system call per read, and a buffer you must manage. mmap(addr, length, prot, flags, fd, offset) instead adds a VMA whose pages are the page-cache pages of the file (mmap(2)). The first touch of each page faults (section 4) and maps the cached page directly; nothing is copied. Two choices make four kinds of mapping:


    

  1. The file and the page cache. The first read of a file fills the kernel's page cache: one copy of each 4 KiB page in RAM, kept after the read (section 6).
    2. 

  2. read(): a second copy. read() copies those bytes into the process's own buffer: two copies of the data in memory, a system call per read, and anonymous memory that counts against the process.
    3. 

  3. mmap: the mapping is the cache. Instead, the page-table entries of the mapping point at the page-cache pages themselves. Each first touch faults (section 4) and maps the cached page; nothing is copied.
    4. 

  4. A second process maps the same file. Its entries point at the same frames, so RAM holds one copy however many processes map it; each process's RSS still counts all of it (section 13).
    5. 

  5. A write to a private mapping copies one page. With MAP_PRIVATE the first write copies that page into anonymous memory for the writer only (copy-on-write, section 7); the file and the other process are untouched.
    6. 

  6. A cold fault reads around. A fault on a page not yet cached reads its neighbours too (read_ahead_kb, 128 KiB by default): good for a sequential pass, wasted on random rows. madvise(MADV_RANDOM) reads one page per fault. Measured below.

6. The page cache and reclaim: where "free" memory went


Linux keeps file data that was read or written in otherwise unused RAM, the page cache, because RAM that holds nothing is wasted. free shows it as "buff/cache"; "available" estimates what could be handed to programs if they asked, mostly by dropping clean cache. Writing, flushing and fsync of cached data belong to the sibling Storage and file systems; here the question is how memory is taken back.


Reclaim. Each memory zone has three watermarks of free pages. Below low, the kernel thread kswapd wakes and reclaims in the background until high; below min, an allocating process must reclaim by itself before it gets memory (direct reclaim), which shows up as stalls in that process. In 5.10, low = min + max(min / 4, managed × watermark_scale_factor / 10,000) and high = min + 2 × that (mm/page_alloc.c lines 7874 to 7880). Here min_free_kbytes is  KiB and the scale factor is 10, so low and high sit about 11 MiB and 22 MiB above min. Raising watermark_scale_factor starts background reclaim earlier, a common fix for allocation stalls on big-memory hosts.


Which pages go. Linux 5.10 keeps two lists per type (anonymous and file), active and inactive, an approximation of least-recently-used built on the hardware accessed bit (section 2): pages are scanned from the inactive tail, and one referenced since gets another chance. Clean file pages are cheapest to drop (re-read later); dirty ones must be written first; anonymous pages can only go to swap. vm.swappiness (60 here, the default, mm/vmscan.c line 172) weighs anonymous against file reclaim.


Inside a container the same reclaim runs against the cgroup's limit instead of the machine's: reading a 768 MiB file in a 512 MiB container filled the cache up to the limit and recycled it, with thousands of "max" events and no OOM kill (the replay in section 12, scenario "Page cache only").


Since 6.1: the multi-generational LRU not run here
Linux 6.1 added the multi-generational LRU, which replaces the two lists with several age generations and scans page tables instead of reverse mappings (multigen_lru docs).

7. Copy-on-write: fork copies tables, writes copy pages


fork must give the child an exact copy of the parent's memory; copying gigabytes for a DataLoader worker that reads a few batches would take seconds and double memory. So fork copies the page tables, not the pages, and marks every private writable entry read-only in both processes; the first write by either side faults and copies just that page. (The fork API itself is the sibling Processes and the system-call API's.)


    

  1. Before fork. The parent maps four private pages, each writable, each in its own frame. Frames in use: 4.
    2. 

  2. fork copies the tables. The child gets a copy of the parent's page tables, not of the pages: both point at frames A to D, and every entry is now read-only in both processes. Measured cost: about 19 us per resident MiB with 4 KiB pages, the table copy.
    3.

9. Locked and pinned memory, and GPU memory mapping


Normally the kernel may move a page (compaction, NUMA migration, THP collapse) or write it to swap, because only the page table knows where it is and the table is updated. A device that copies memory by itself (DMA: a GPU, a network card doing RDMA) holds a physical address and does not consult the page table; if the page moves mid-copy, the device reads someone else's data. Two mechanisms stop that. mlock(addr, len) faults the range in and keeps it resident, never swapped (mlock(2)). Pinning is stronger and kernel-internal: a driver calls pin_user_pages (the FOLL_PIN flavour of get_user_pages, pin_user_pages docs) and the pages may not be moved or freed until it unpins them. Both take memory out of what reclaim can use.


Pinned memory for GPU copies not run here. cudaHostAlloc / cudaMallocHost "Allocates size bytes of host memory that is page-locked and accessible to the device", with the warning that "allocating excessive amounts of pinned memory may degrade system performance, since it reduces the amount of memory available to the system for paging"; cudaHostRegister page-locks an existing range (CUDA runtime API, memory management). Why it matters: "when CUDA sends pageable data from CPU to GPU, it must first create a page-locked copy of that data before making the transfer" (PyTorch pinned memory tutorial), an extra copy through a staging buffer. In PyTorch:


    

  • DataLoader(pin_memory=True) runs a thread that copies each batch into pinned memory, so x.to("cuda", non_blocking=True) can be an asynchronous DMA that overlaps compute.
    • 

  • Calling t.pin_memory() right before one copy is usually slower than copying directly (it pays the staging copy itself); pin once, reuse.
    • 

  • The tutorial warns that "allocating a large number of tensors or sizable tensors in pinned memory can monopolize a substantial portion of RAM": pinned pages cannot be reclaimed, so the page cache that feeds your data loader shrinks.

11. Swap: anonymous pages written to disk


Anonymous pages have no file to be re-read from, so to reclaim one the kernel writes it to a swap device, replaces the table entry with a not-present entry holding the swap location, and frees the frame. The next access is a major fault: do_swap_page reads it back (handle_pte_fault, mm/memory.c line 4377), reading 2page-cluster = 8 neighbouring swap slots at once (vm.page-cluster = 3 here).


What it costs measured. A process that needs 640 MiB in a container limited to 512 MiB with 512 MiB of swap allowed did not die; it ran with about 260 MiB in swap and every pass over its memory took 4 to 5 seconds, the same pass that takes milliseconds when it fits (the replay in section 12, scenario "Swap allowed"; the root's Debug lab case "Not dead, just slow: the working set spills into swap" has the per-pass numbers). For a training job that is usually worse than being killed: it looks alive, holds its GPUs, and makes no progress.


The signal to watch is pressure, not free memory: with pressure stall information (PSI), /proc/pressure/memory and each cgroup's memory.pressure report the share of time tasks were stalled waiting for memory.

12. Memory cgroups and the OOM killer: why a container dies


On a shared host each job (container, pod, Slurm step) gets a memory budget. A cgroup v2 memory controller charges every page a process in the group allocates to the group, and reclaims within the group when it reaches its limit. What is charged: "userland memory - page cache and anonymous memory", kernel structures such as dentries and inodes, and TCP socket buffers (cgroup-v2 docs, Memory). 13. VSZ, RSS, PSS, USS: four answers to "how much memory does it use?"


Shared pages (libraries, the page cache of a mapped file, copy-on-write pages after fork) are resident for several processes at once, so adding up per-process numbers counts them several times. Four measures, from /proc/PID/status and /proc/PID/smaps_rollup:

PSSproportional set: each page divided by the number of processes mapping it. Sums are right.

Mistakes and rehearsal


Common mistakes, each with what was measured


"RSS says each worker uses 250 MiB, so 8 workers need 2 GB."
RSS counts shared pages in every process. Measured here: three processes, 815 MiB of RSS, 345 MiB of PSS, 104 MiB of USS. Use PSS for totals and USS for "what does one more worker cost".


"The allocation succeeded, so the memory is there."
With overcommit (modes 0 and 1) an allocation is a promise; memory is taken at first touch, and the OOM killer settles any shortfall later, at a random-looking moment.


"free shows almost no free memory: we have a leak."
Look at "available", not "free". The page cache fills idle RAM on purpose and is given back on demand.


"The container's memory is full of page cache, so it is about to be killed."
Clean page cache is reclaimed at the limit (measured: thousands of "max" events, no kill). What kills is anonymous memory and shared memory that cannot be reclaimed without swap.


"Our workers only read the dataset, so copy-on-write cannot copy anything."
In Python, reading an object writes its reference count, and the garbage collector writes every tracked object's header. Measured: 15,732 pages copied by reading a list, 16,817 by one gc.collect(), 30 after gc.freeze().


"Huge pages always help."
They cut faults and TLB misses for dense memory, but bloat sparse memory (298x in the measurement here), can stall allocations on compaction, and do not reduce page-table memory in Linux.


"Set oom_score_adj = -1000 on the trainer so it is never killed."
Inside a default container you cannot lower it (no CAP_SYS_RESOURCE), and if you could, the kernel would kill something else, perhaps the data loader or the node agent. Size the limit instead.


"pin_memory() before every .to('cuda') makes copies faster."
Pinning is itself a copy; doing it per transfer is usually slower than letting CUDA stage the copy. Pin buffers you reuse (the DataLoader's pinning thread does this).




Interview rehearsal: six questions with answers


Walk through what happens on the first write to a freshly malloc'd 1 GiB buffer.
glibc serves it with an anonymous private mmap: a new VMA, no frames. The first store to each page misses the TLB; the hardware walk finds no valid entry; the CPU raises a fault; the kernel finds the VMA (writable, anonymous), allocates any missing table levels, takes a zeroed frame, writes the entry and resumes the store (do_anonymous_page). 262,144 such faults, about 1 us each here. With THP for the range, 512 faults of 2 MiB each. RSS grows as pages are touched, not at malloc.


Why is fork fast even for a process using 50 GB, and when is it not?
Fork copies page tables and marks private pages read-only; pages are copied lazily on write. The table copy is still proportional to resident memory: about 19 us per resident MiB measured here with 4 KiB pages (about 1 s for 50 GB), 30x less with huge pages. After fork, every page either side writes costs a fault and a 4 KiB copy, which is where DataLoader worker memory comes from.


What is a TLB shootdown and why can munmap be expensive in a multi-threaded program?
Removing or changing a mapping requires every CPU that may cache the old translation to drop it. x86 interrupts each such CPU and waits; arm64 broadcasts a TLBI instruction. Measured here on arm64, an mprotect that must flush cost about 1.9 us regardless of how many other threads ran, against 0.65 us when nothing was cached.


Explain RSS, PSS and USS, and which one you would alert on for a fleet of identical workers.
RSS counts all resident mapped pages, PSS divides shared pages among sharers, USS counts private pages only. Alert on USS growth per worker (copy-on-write and leaks show there) and on the cgroup's memory.current minus reclaimable cache for the pod as a whole.


A training pod dies with exit code 137 and no traceback. How do you confirm the cause and fix it?
137 = 128 + SIGKILL. Check memory.events (oom_kill), Kubernetes' OOMKilled reason, or the kernel log. Then find what grew: memory.stat anon vs file vs shmem (DataLoader shared memory counts), worker USS (copy-on-write), pinned memory. Fix the growth or raise the limit; do not rely on swap.


Why does mmap'ing model weights let 8 server processes share memory, and what breaks the sharing?
All map the same page-cache pages of the file (MAP_SHARED or read-only private), so RAM holds one copy. Any write to a private mapping, a dtype conversion, or a copy into a new tensor creates private anonymous pages per process.
