The idea

A container is not a thing the kernel knows about: it is ordinary processes on the host's one kernel, given a private view (namespaces), a budget (cgroups), fewer powers (capabilities, seccomp, LSMs) and a layered root file system (an image). Because the kernel is shared, a container keeps well-behaved jobs apart but is not a security boundary like a VM: hostile code needs another kernel in the way.

Fig. 1: one kernel, many containers, step by step

  1. One kernel, ordinary processes. Two containers on one machine, an illustrative pair: a training job (python train.py and two DataLoader workers) and a notebook. To the kernel floor below they are just processes; "container" is not a kernel object.
  2. SEE: namespaces. Each group gets a private view: its own PID numbers, mount table, network stack, hostname, IPC, user IDs, cgroup path and clocks. The sleep 60 container of section 9 was PID 1 inside and PID 68321 on the VM (sections 1 to 3).
  3. USE: a cgroup. A budget for the whole group, workers included: memory.max, cpu.max, io.max, pids.max. Usage that reaches the ceiling is pushed back: reclaim, a failed fork, an OOM kill (sections 4, 5).
  4. HAVE: an image. Read-only layers plus one writable layer, merged by overlayfs into the container's /; the image measured here, kb-os-cont:1, has six (section 3).
  5. DO: the gate. Capabilities, seccomp and LSMs check each system call before the kernel acts: Docker's default 14 capabilities, and a filter that refused perf_event_open with EPERM (sections 6 to 8).
  6. Nothing else in between. An allowed call runs the host kernel's own code, the same kernel for both containers. Everything a runtime such as Docker does is a sequence of ordinary system calls (section 0 makes them by hand, section 9 shows who makes them for real), and a kernel bug reachable through an allowed call is a way out: hostile code needs another kernel in the way (section 10).

In one screen: eight things to remember
  1. A container is processes plus restrictions. The same kernel runs it; a kernel bug reachable through an allowed system call is a way out. Code you do not trust needs a sandbox with its own kernel or a kernel in user space (section 10).
  2. Namespaces are cheap, except the network one. Creating a UTS, PID, cgroup or time namespace took 3 to 5 microseconds here; a network namespace took 2.4 ms (section 1).
  3. When PID 1 of a container dies, the kernel SIGKILLs everything else in it. A shell or --init between docker stop and Python lost the checkpoint in all three such setups here (0.24 to 0.27 s, exit 143); exec, a forwarding trap, or Python as PID 1 saved it in 1.3 to 1.9 s (section 2).
  4. memory.max kills; memory.high stalls. The same 300 MiB allocation was OOM-killed at 190 MiB under memory.max=200M, but under memory.high=200M with no swap it hung for the full 60 s without an error, and with swap it finished in 0.3 s (section 5).
  5. Kubernetes kills the whole container on an OOM. On cgroup v2 the kubelet sets memory.oom.group=1, so a DataLoader worker going over the limit takes the main process with it; under Docker's default only the worker dies (section 5).
  6. Root inside is not all of root. Docker's 14 default capabilities cannot raise priority, pin 64 MiB of memory or mount anything; Docker's default seccomp profile changed the answer for 7 of the 12 calls probed, five of which worked without it (6, 7).
  7. Some limits are per user, not per container. io_uring rings and BPF programs on Linux 5.10 are charged to the UID: two containers running as the same UID shared one 64 KiB budget, and root's was already spent (section 7).
  8. Kubernetes requests become cgroup files by formulas you can check: requests.cpu becomes cpu.weight (1 CPU gives 39 under runc 1.1, 100 under newer runc), limits.cpu becomes cpu.max, limits.memory becomes memory.max, the QoS class becomes oom_score_adj (section 12).

0. A container in ten system calls


A container runtime in about 170 lines of C (src/exp/minictr.c) starts as an ordinary root process, applies one restriction per step, and after each step prints everything the process can observe: its PID, hostname, namespace numbers, how many processes and mounts it sees, its network interfaces, its cgroup and visible limits, its capabilities and seccomp state. Then it execves a busybox shell that runs a small workload. Step through it before the mechanisms: every later section explains one of these steps. The steps are numbered from 0, as the program numbers them.


    

  1. Start: an ordinary root process. The baseline, inside the outer Docker container: its namespaces, 22 entries in /, 23 mounts, eth0, the outer cgroup /init, and no seccomp filter (the outer container ran unconfined). It creates one System V shared memory segment, to watch at step 6.
    2. 

  2. A new UTS namespace. Only the uts namespace number and the hostname change. The outer container still has its own hostname: this process now has a private copy (kernel side: unshare_nsproxy_namespaces).
    3. 

  3. A new PID namespace, then fork. The child is PID 1 with parent 0 (its parent is outside the namespace): the pid becomes 1 only after the fork, because unshare sets only pid_ns_for_children (alloc_pid in fork.c). Yet it still sees 3 processes: /proc is the old namespace's until step 4 mounts a new one.
    4. 

  4. Join the limited cgroup, then a cgroup namespace. /proc/self/cgroup becomes 0::/ (this cgroup looks like the root), but the visible memory.max is still the outer container's 1.5 GB: a cgroup namespace changes how paths are shown, and the mounted cgroup file system is the old view until step 4 remounts it.
    5. 

  5. A mount namespace, an overlay root, pivot_root. The busybox tree is now / and the old root is unmounted: one visible process, seven root entries, eight mounts. The host's tree is gone from this mount namespace, not merely hidden. The new cgroup2 mount shows /ctr as its root: memory.max 64 MiB, pids.max 16.
    6. 

  6. A network namespace. eth0 is gone; lo, tunl0 and ip6tnl0 are new devices of the new namespace (all down), two tunnel devices this kernel creates in every namespace (setup_net, about 2.4 ms, section 1). A real runtime would now add one end of a virtual Ethernet pair.
    7. 

  7. An IPC namespace. The System V shared memory segment created at step 0 is no longer visible: zero segments.
    8. 

  8. Drop capabilities to Docker's default 14. CapEff drops from a82425fb (Docker's 14 plus CAP_SYS_ADMIN) to a80425fb, Docker's 14: bit 21 gone. Root can still chown, but sethostname and mount now fail with EPERM.

  9. no_new_privs and a seccomp filter. Seccomp becomes 2 (filter mode) and NoNewPrivs 1. mkdir and unshare fail before reaching the kernel's code for them; getpid is unaffected (seccomp_run_filters).

1. Namespaces: a private view of one global resource


ch. 4 to 5 (the process), then beyond source namespaces(7); include/linux/nsproxy.h v5.10


The problem. Many things in Linux are global: process IDs, the mount table, network interfaces and ports, the hostname, System V shared memory, user ID numbers. Two training jobs on one machine would see each other's processes, could bind the same port and would share one /tmp. We want each to believe it is alone, without a second kernel.


How it works. A namespace "wraps a global system resource in an abstraction that makes it appear to the processes within the namespace that they have their own isolated instance of the global resource" (namespaces(7)). In the kernel it is one pointer per kind: every task's task_struct (the processes page walks it) points to a small struct nsproxy holding one pointer per namespace kind, and code that looks up a global thing ("which network interfaces exist") follows the current task's pointer first. Two processes with different pointers see different worlds; the kernel underneath is one.


Fig. 2: the same process seen from outside and inside


    

  1. One pointer per kind. The process at step 0 of section 0, in front, and the outer container's processes, behind, share one nsproxy: eight pointers to the outer container's namespaces. readlink /proc/self/ns/* gives an inode number per namespace, such as net:[4026532319]; two processes with the same number share it.
    2. 

  2. UTS and PID. Section 0's steps 1 and 2 swing two pointers to new namespaces: the hostname becomes trainer-0 for this process only, and the forked child is PID 1 with parent 0. Behind, nothing changed.
    3. 

  3. cgroup and mount. Steps 3 and 4: the cgroup path reads 0::/; the mount table drops from 23 mounts to 8 and / from 22 entries to 7, and a fresh /proc shows one process.
    4. 

  4. Network and IPC. Steps 5 and 6: eth0 is gone (only lo, tunl0, ip6tnl0), and the System V segment made at step 0 is no longer visible.
    5. 

  5. Six of eight. The build never unshared the user or time namespace, so those pointers still lead to the host's: six of eight pointers now lead to new namespaces. Every number on the figure is measured (src/raw/minictr.txt), and the kernel underneath is still one.

What it costs here
The UTS, PID, cgroup, time and user namespaces cost under 10 microseconds each: a small structure and a pointer swap. The mount namespace copies the caller's whole mount table (23 mounts here) and costs about 19 microseconds; the IPC namespace about 43, because it mounts a private instance of the POSIX message-queue file system (ipc/namespace.c line 58). The network namespace costs about 2.4 ms, roughly 500 times more: setup_net runs every registered per-network initialiser in turn (net_namespace.c line 341), creating a loopback device, routing tables, firewall state and per-namespace sysctls (and, on this kernel, the two tunnel devices tunl0 and ip6tnl0 of step 5). As whole commands: /bin/true took  ms, unshare with five namespaces  ms, and with the network namespace as well  ms; docker run --rm of the same image took  s (median of 5). The kernel's part of starting a container is about 1% of docker run; the rest is the daemon, containerd, the shim, runc, and setting up the image's mount and the network (section 9).

2. PID namespaces and PID 1: the stop that loses a checkpoint


ch. 5 Interlude: Process API source pid_namespaces(7); kernel/pid_namespace.c, kernel/exit.c, kernel/signal.c v5.10


The problem. Inside a container the first process must look like the init of a whole machine: PID 1, the ancestor of everything. Kubernetes and Docker stop a container by signalling exactly that process. Which process is PID 1, and what it does with the signal, decides whether your training job writes its last checkpoint.


How it works. PID namespaces nest: a process has one PID in its own namespace and another in each ancestor namespace (the sleep 60 container of section 9 was PID 1 inside and PID 68321 on the VM). The first process created in a new PID namespace gets PID 1 and becomes the namespace's init: orphans in the namespace are re-parented to it (the processes page covers reaping and zombies in section 5). Two kernel rules make it special:


    

  1. It ignores signals it has no handler for. The namespace's init is marked SIGNAL_UNKILLABLE, and sig_task_ignored drops a signal whose action is the default (signal.c lines 89 to 91, v5.10). SIGTERM with no handler does nothing to PID 1. SIGKILL from an ancestor namespace (the container runtime) still works.
    2. 

  2. When it dies, everything else dies. "If the 'init' process of a PID namespace terminates, the kernel terminates all of the processes in the namespace via a SIGKILL signal" (pid_namespaces(7)). In the source: when init exits, find_child_reaper finds no other reaper and calls zap_pid_ns_processes (exit.c line 527), which walks every PID in the namespace and sends SIGKILL (pid_namespace.c lines 172 to 211). No handler runs; no checkpoint is written.
    3. 



Rule 1 is why people add an init (docker run --init starts tini as PID 1, which forwards signals and reaps zombies). Rule 2 is the trap in that fix, which the processes page measured first: tini forwards SIGTERM to its one child; when that child is a shell running Python, the shell dies at once, tini exits, and the kernel kills Python. The job is a stand-in for the root's training loop: on SIGTERM it writes a checkpoint that takes about 1 s (src/exp/stopjob.py), and logs every event with a time stamp.

    3. Mount namespaces, images and overlayfs: what files it has
    

    ch. 39 to 40 (files, file system implementation) source mount_namespaces(7), pivot_root(2), overlayfs docs, OCI image spec
    

    The problem. A training image brings its own Python, PyTorch and CUDA runtime, which must not clash with the host's or another job's. Copying a whole 2 GB file tree for every container would be slow and waste disk; ten containers of one image should share one copy.
    

    The mount namespace and the new root
    

    A new mount namespace starts as a copy of the caller's mount table; after that, mounts on either side are private (once the runtime marks its copy private, step 4 of section 0). Then the process gets a new / with pivot_root(new_root, put_old), which swaps the root mount of the whole mount namespace and moves the old one under put_old, which the runtime then unmounts: the host's tree is no longer in the namespace at all. chroot would only change where path lookups start, with the old root still mounted and reachable.
    

    Mount propagation, chroot against pivot_root, and why the container never calls pivot_root itself
    

    A new mount namespace starts as a copy of the caller's mount table; after that, mounts and unmounts on either side are private, unless mount propagation says otherwise. Each mount is shared (events propagate both ways within its peer group), slave (receives, does not send) or private. systemd makes / shared on most hosts, so a runtime first marks its copy private, recursively, or its mounts would appear on the host: that is the first mount call at step 4 of section 0 (mount(NULL, "/", NULL, MS_REC|MS_PRIVATE, NULL)).
    

    Then the process needs a different /. chroot(dir) only changes where path lookups start for this process; the old root is still mounted and reachable, and a process with CAP_SYS_CHROOT can break out ("This call does not change the current working directory", and it "is not intended to be used for any kind of security purpose", chroot(2)). pivot_root(new_root, put_old) instead swaps the root mount of the whole mount namespace and moves the old one under put_old, which the runtime then unmounts, so the host's tree is no longer in the namespace at all. runc uses pivot_root unless told not to (--no-pivot, for a root on a ramdisk, which cannot be pivoted; it then uses a move-mount plus chroot). Docker 20.10's default seccomp profile does not list pivot_root at all (measured: the hand-built container needed seccomp=unconfined for it): runc calls it before it installs the container's filter, and the container itself never needs to.
    

    

    overlayfs: layers, copy-up and whiteouts
    

    The new root is an overlay mount: several read-only lower directories (the image layers), one writable upper directory (this container's changes) and a workdir for atomic operations, merged into one tree. A lookup returns the topmost layer's version of a name. Writing to a file that exists only in a lower layer triggers a copy-up: overlayfs copies the whole file into the upper layer first (ovl_copy_up_data, fs/overlayfs/copy_up.c line 132), then lets the write proceed. Deleting a lower-layer file creates a whiteout in the upper layer, a character device with device number 0/0 that hides the name. An overlay cannot use another overlay as its upper layer (the first attempt of this page's experiment failed with EINVAL until the layers moved to a tmpfs).

    4. cgroups v2: the tree, delegation, PIDs, I/O and freezing
    

    ch. 9 Proportional Share, applied to groups source cgroup v2 (kernel docs); kernel/cgroup/cgroup.c, kernel/cgroup/pids.c v5.10
    

    The problem. Namespaces hide things but limit nothing: a process in its own namespaces can still use every CPU, all memory and the whole disk bandwidth. We need to group processes, including the ones they will fork later, and give each group a budget, with accounting we can read.
    

    How it works. A control group (cgroup) is a directory in one tree mounted at /sys/fs/cgroup (cgroup v2, the "unified hierarchy"; v1 had one tree per controller and is legacy). Every process is in exactly one cgroup, listed in its cgroup.procs file; children of a fork start in the parent's cgroup, so a whole job stays together. Controllers (cpu, memory, io, pids, cpuset, hugetlb, rdma here) each add interface files to the directories where they are enabled, such as memory.max or pids.max. A controller is available in a cgroup's children only if it is listed in that cgroup's cgroup.subtree_control. Limits are hierarchical: nothing below can escape a limit set above.
    

    Two rules shape every container runtime:
    

      

    • No internal processes. A cgroup (other than the root) that has processes cannot enable domain controllers for children; otherwise the parent's own processes would compete with its children for the same budget. In the source, cgroup_vet_subtree_control_enable returns -EBUSY when the cgroup has tasks (cgroup.c lines 3203 to 3208). So processes live in leaves, and a manager first moves itself into a leaf.
      • 

    • Delegation. "A cgroup can be delegated in two ways": by giving a less privileged user write access to the directory and its cgroup.procs, cgroup.threads and cgroup.subtree_control files, or, with the nsdelegate mount option, automatically to a cgroup namespace. "Once delegated, the user can build sub-hierarchy under the directory ... and further distribute the resources it received from the parent" (cgroup v2 docs, "Delegation"). systemd does the first for a unit with Delegate=yes; rootless Podman and Kubernetes nodes running as systemd services rely on it.
      •

    5. Memory limits: memory.max kills, memory.high stalls
    

    ch. 13 to 23, applied to a group source cgroup v2: memory; mm/memcontrol.c v5.10
    

    The problem. A training job's memory grows: DataLoader workers copy pages on write, a prefetch queue fills, a leak creeps. On a shared node something must stop one job before it takes memory from the others. There are two ways to stop it, a wall and a brake, and they fail very differently.
    

    How it works. The memory controller charges each page to the cgroup of the task that first touched it: anonymous memory (heap, tensors), page cache from the files it reads and writes, and kernel memory on its behalf (socket buffers, slab). memory.current is the total. Four knobs act on it; the virtual memory page explains the OOM killer and how it picks a victim, so here we measure the knobs against each other.
    

    FileWhat happens at the boundary
    

    memory.maxthe wall: "If a cgroup's memory usage reaches this limit and can't be reduced, the OOM killer is invoked in the cgroup"
    

    memory.highthe brake: "the processes of the cgroup are throttled and put under heavy reclaim pressure. Going over the high limit never invokes the OOM killer and under extreme conditions the limit may be breached"
    

    memory.swap.maxhow much of the group may be swapped out (0: none, so anonymous memory cannot be reclaimed at all)
    

    memory.min, memory.lowprotection: memory below them is not reclaimed (min) or reclaimed only as a last resort (low) when others need memory
    

    

    Quotes from the kernel's cgroup v2 documentation, memory interface files.
    

    The brake: over memory.high the kernel reclaims, then puts the task to sleep on its way back to user space, up to 2 s each time, growing with the square of the overage; if nothing can be freed, it sleeps again on the next allocation, indefinitely.
    

    The brake in the kernel source
    The brake in the source: when a charge pushes a group over memory.high, the kernel reclaims, and on the way back to user space mem_cgroup_handle_over_high puts the task to sleep for a penalty that grows with the square of the overage (penalty_jiffies = max_overage * max_overage * HZ, scaled, in calculate_high_delay, memcontrol.c line 2583), capped at 2 s per return to user space (MEMCG_MAX_HIGH_DELAY_JIFFIES, line 2466). If reclaim frees enough, the task runs on; if nothing can be freed, it sleeps again on the next allocation, indefinitely.

    6. Capabilities and user namespaces: root, but not all of root
    

    ch. 55 Access Control source capabilities(7), user_namespaces(7)
    

    The problem. Most images run as root (user ID 0), and many programs expect to. Classic Unix has one test: UID 0 may do anything. A container's root must be able to install packages in its own file system and bind its own ports, but not load kernel modules, change the host's clock or reconfigure the host's network.
    

    Capabilities. Linux splits root's power into about 40 capabilities, each a bit checked by the kernel at one kind of operation: CAP_CHOWN before changing a file's owner, CAP_NET_ADMIN before reconfiguring interfaces, CAP_SYS_ADMIN (the catch-all) before mounting, and so on. Docker starts containers with 14 capabilities, CapEff 00000000a80425fb (the root page decoded them). prctl(PR_SET_NO_NEW_PRIVS) adds a one-way switch: after it, execve can never grant more privilege, not even through a setuid binary; it is what lets an unprivileged process install a seccomp filter (section 7).
    

    The five capability sets
    A process has several sets: permitted (what it may use), effective (what is switched on now, the set the kernel checks), inheritable and ambient (what passes across execve), and the bounding set (a ceiling no descendant can exceed). The CapEff line of /proc/<pid>/status is the effective set as a hexadecimal bit mask.

    User namespaces: root inside, an ordinary user outside
    

    A user namespace gives a process its own numbering of user and group IDs and a full set of capabilities that apply only to resources owned by that namespace. A map in /proc/<pid>/uid_map (lines of "inside outside count") translates IDs at the boundary: files created by "root" inside are owned by the real user outside, and the host's files keep their real owners inside. Namespaces of other kinds created by a process in a user namespace are owned by it, so inside you may change the hostname of your own UTS namespace or mount a tmpfs in your own mount namespace, but not the host's. This is how rootless containers (Podman, rootless Docker, Apptainer on HPC clusters) work: a breakout lands as an ordinary user.
    

    The cost of user namespaces
    Every capability inside a user namespace exposes kernel code that used to be reachable only by real root (mounting some file systems, creating network devices). Canonical: "unprivileged user namespaces are now broadly used as a step in several privilege escalation exploit chains", citing Google's finding that 44% of the exploits it observed relied on them; Ubuntu 23.10 started restricting them (Ubuntu blog). Docker's default seccomp profile blocks creating them unless the container has CAP_SYS_ADMIN. Rootless gains you a lot if the container runtime has a bug; it adds kernel attack surface if the kernel has one.

    7. seccomp-bpf: a filter on every system call
    

    beyond OSTEP source seccomp(2), kernel seccomp filter docs; kernel/seccomp.c v5.10
    

    The problem. Linux has about 400 system calls (Docker's default profile names 396 across its rules). A training job uses a few dozen. Every other call is kernel code an attacker can reach from inside the container; capabilities guard only some of them.
    

    How it works. A process installs a small program in classic BPF (a tiny register machine with loads, compares, jumps and returns; no loops) with prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog) or seccomp(2). On every system call entry, before the call runs, the kernel runs the program on a struct seccomp_data: the call number, the architecture, the instruction pointer and the six argument values. The program returns an action: ALLOW, ERRNO (fail the call with a chosen error), KILL_PROCESS or KILL_THREAD, TRAP (deliver SIGSYS), LOG, TRACE, or USER_NOTIF (Linux 5.0: let a supervising process decide). Filters stack and are inherited across fork and execve; none can be removed; with several, all run and the most restrictive answer wins (seccomp_run_filters, seccomp.c lines 311 to 327). Installing one requires CAP_SYS_ADMIN or no_new_privs, so a filtered process can never execve a setuid program that would run with the filter but more privilege.

Later kernels moved both to the memory cgroup: kernel/bpf/syscall.c no longer touches locked_vm at v5.11, and at v5.12 io_uring allocates its rings with __GFP_ACCOUNT (fs/io_uring.c line 8061, v5.12) instead of charging ring_pages to the user.
    

    When it bites in ML
      

    • Fast data readers built on io_uring fail with EPERM on Docker 25 and later and in Kubernetes runtimes with similar profiles; a library that does not fall back to ordinary reads breaks. On older kernels the same reader can fail with ENOMEM because some other container running as the same UID holds rings. Fix: a custom profile that allows io_uring, a different UID per job (or user namespaces), or --ulimit memlock high enough.
      • 

    • perf, bpftrace and some profilers need perf_event_open and bpf, blocked by default. Profile on the host, or start a debugging container with a custom profile and the needed capabilities, never --privileged on a shared node.
      • 

    • Kubernetes: securityContext.seccompProfile.type: RuntimeDefault applies the container runtime's profile; the Pod Security Standards' "restricted" level requires a profile (Pod Security Standards).

    Check it: grep Seccomp /proc/<pid>/status (0 none, 1 strict, 2 filter; Seccomp_filters counts them), docker run --security-opt seccomp=profile.json, strace -f (a blocked call shows as -1 EPERM with no other cause).

    9. Container runtimes: who makes all those calls
    

    beyond OSTEP source OCI runtime spec, containerd, runc
    

    The problem. Sections 1 to 8 are a few hundred lines of system calls in the right order. Somebody has to pull the image, unpack the layers, write the cgroup files, create the namespaces, mount the overlay, drop the capabilities, install the filter, start the process, keep its output and report its exit code, for thousands of containers, surviving restarts of the managing daemon.
    

    How it works. The work is split into layers with standard interfaces between them. The OCI runtime specification defines a bundle: a root file system directory plus a config.json listing the process, its namespaces, mounts, cgroup limits, capabilities, seccomp profile and hooks. A low-level runtime (runc, written in Go; crun in C; youki in Rust) turns one bundle into one running process with exactly the system calls of section 0, then exits. A high-level runtime (containerd, CRI-O) pulls and stores images, prepares bundles, and starts one small shim process per container that becomes the container's parent, holds its standard streams, and collects its exit status, so containerd itself can restart without killing containers. Docker's daemon sits above containerd; Kubernetes' kubelet talks to containerd or CRI-O through the Container Runtime Interface (CRI).

    10. Sandboxes for code you do not trust not run here

    The problem. Everything so far narrows what a container can ask of the host kernel, but the kernel answering is the host's. A container runs model-generated code, a user's notebook or an untrusted evaluation submission; one kernel bug reachable through an allowed call and the code is on the host, next to other customers' data. The fix is to put another kernel between the code and the host, and to make that kernel either smaller or isolated by hardware.

    11. GPU containers: the driver stays on the host not run here
    

    source NVIDIA Container Toolkit, CDI support, CDI specification
    

    The problem. The GPU's kernel driver (nvidia.ko) belongs to the host kernel, and the user-space driver library (libcuda.so) must match it exactly. The image brings the CUDA runtime and PyTorch, but must not bring its own libcuda. The container needs the device files (/dev/nvidia0, /dev/nvidiactl, /dev/nvidia-uvm), the host's matching libraries, and permission in the device cgroup to open them.
    


    How it works. Three pieces, all from the host, as the figure shows. The device files are bind-mounted into the container's mount namespace. The device cgroup must allow them: on cgroup v2 there is no devices.allow file; runc attaches a small BPF program to the container's cgroup that checks every device open (the same kind of program that likely used up root's locked-memory budget in section 7). The driver libraries (libcuda.so, libnvidia-ml.so, the nvidia-smi binary) are bind-mounted from the host. The NVIDIA Container Toolkit does all three. Its newer interface is the Container Device Interface (CDI), "an open specification for container runtimes that abstracts what access to a device, such as an NVIDIA GPU, means": a generated file lists, per device name such as nvidia.com/gpu=0, the device nodes, mounts, environment variables and hooks to apply (NVIDIA CDI docs).
    

    The device cgroup measured, and the CDI commands
    Without the BPF program's permission, a device node the container creates still cannot be opened: Virtualization and the GPU driver stack, section 9, made /dev/nvidiactl (195:255) with mknod and got EPERM on open, and with --device-cgroup-rule 'c 195:* rwm' the same open got past the cgroup and failed only with ENXIO, because no GPU driver is loaded there. CDI: nvidia-ctk cdi generate --output=/var/run/cdi/nvidia.yaml writes the file, and a CDI-aware runtime applies it on --device nvidia.com/gpu=all.
    

    When it bites in ML
      

    • "CUDA driver version is insufficient for CUDA runtime version": the image's CUDA runtime is newer than the host driver supports (the virtualization page covers driver and runtime compatibility in section 10).
      • 

    • An image that ships its own libcuda.so (copied from a build machine) shadows the host's and fails on a different driver version. Never put driver libraries in images.
      • 

    • GPU visibility is not GPU isolation: two containers given the same GPU share it by time-slicing with no memory limit between them; MIG gives hardware partitions (the virtualization page). In Kubernetes the NVIDIA device plugin advertises nvidia.com/gpu as a resource and the kubelet passes the chosen devices to the runtime.

    Interview rehearsal: six questions this page answers
    

    What is a container, at the kernel level?
    Not a kernel object: ordinary processes whose task_struct points at non-default namespaces (what they see), that sit in a cgroup (what they may use), with a reduced capability set, a seccomp filter and possibly an LSM profile (what they may do), and whose root is an overlay of image layers. The same kernel serves them, which is both why they start in milliseconds and why they are a weaker boundary than a VM.
    

    Why does a training job sometimes ignore docker stop, and sometimes die instantly without checkpointing?
    PID 1 of a PID namespace ignores signals whose action is the default, so a PID 1 without a SIGTERM handler (a shell) ignores the stop until SIGKILL. And when PID 1 exits, the kernel SIGKILLs every other process in the namespace, so an init or shell that dies on SIGTERM takes Python with it before its handler runs. Fix: the process that handles SIGTERM must be PID 1's direct target and must outlive the job's shutdown: exec, exec-form CMD, a forwarding trap.
    

    memory.high or memory.max for a job's limit?
    memory.max is a wall: reclaim, then OOM kill in the group. memory.high is a brake: reclaim and sleep up to 2 s per return to user space, never an OOM kill. Without swap and with anonymous memory, the brake becomes an indefinite stall that looks like a hang. Use memory.max as the limit; use memory.high only with something watching pressure (PSI) that can act.
    

    Why can't seccomp filter by file path, and what does?
    The filter is classic BPF over struct seccomp_data: the call number, architecture, instruction pointer and argument values. A path is behind a pointer in user memory, and reading it would race with other threads changing it. LSMs (AppArmor, SELinux, Landlock) check inside the kernel after the path is resolved to an inode.
    

    A pod requests 1 CPU. What cpu.weight does it get, and why might that differ between clusters?
    The kubelet converts 1000 milli-CPUs to 1024 cgroup v1 shares; the OCI runtime converts shares to a v2 weight. runc 1.1's linear map gives 39; the quadratic map in opencontainers/cgroups v0.0.3 and later (runc 1.3.6, 1.4.0) gives 100. Same pod spec, different share of a contended node, depending only on the runtime version.
    

    When is a container not enough isolation, and what do you use instead?
    When the code inside is hostile: one exploitable bug in any reachable kernel path gives the host. Use a sandbox that puts another kernel in the way: gVisor (a user-space kernel answering the calls, host exposed to a small enumerated set) or a microVM such as Firecracker or Kata (a guest kernel isolated by hardware virtualization), plus no network, tight cgroups and timeouts.
