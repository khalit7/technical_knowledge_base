In one screen

A container is not a thing the kernel knows about. There is no "container" object in Linux. A container is ordinary processes on the host's one kernel, started with four kinds of restriction: namespaces (what they can see), cgroups (how much they can use), capabilities, seccomp and LSMs (what they may do) and a layered root file system (what files they have). Everything a container runtime such as Docker does is a sequence of ordinary system calls you can make yourself, and the Build a container tab does exactly that, one call at a time, printing what the process sees after each.

The root page, Topic: operating-systems section 8, read these four restrictions from inside one container; its Debug lab reproduces the OOM kill, the /dev/shm limit, CPU throttling and the pids limit. This page goes one level down: how each restriction works in the kernel (Linux v5.10, the kernel these runs used, file and line), what it costs, where it bites a training or serving job, the command that shows it, and the fix. Each mechanism follows one pattern: problem, how it works, what it costs here, when it bites in ML, the command that shows it, the fix.

Eight things to remember
  1. A container is processes plus restrictions. The same kernel runs it; a kernel bug reachable through an allowed system call is a way out. Code you do not trust needs a sandbox with its own kernel or a kernel in user space (section 10).
  2. Namespaces are cheap, except the network one. Creating a UTS, PID, cgroup or time namespace took 3 to 5 microseconds here; a network namespace took 2.4 ms (section 1).
  3. When PID 1 of a container dies, the kernel SIGKILLs everything else in it. A shell or --init between docker stop and Python lost the checkpoint in all three such setups here (0.24 to 0.27 s, exit 143); exec, a forwarding trap, or Python as PID 1 saved it in 1.3 to 1.9 s (section 2).
  4. memory.max kills; memory.high stalls. The same 300 MiB allocation was OOM-killed at 190 MiB under memory.max=200M, but under memory.high=200M with no swap it hung for the full 60 s without an error, and with swap it finished in 0.3 s (section 5).
  5. Kubernetes kills the whole container on an OOM. On cgroup v2 the kubelet sets memory.oom.group=1, so a DataLoader worker going over the limit takes the main process with it; under Docker's default only the worker dies (section 5).
  6. Root inside is not all of root. Docker's 14 default capabilities cannot raise priority, pin 64 MiB of memory or mount anything; Docker's default seccomp profile changed the answer for 7 of the 12 calls probed, five of which worked without it (6, 7).
  7. Some limits are per user, not per container. io_uring rings and BPF programs on Linux 5.10 are charged to the UID: two containers running as the same UID shared one 64 KiB budget, and root's was already spent (section 7).
  8. Kubernetes requests become cgroup files by formulas you can check: requests.cpu becomes cpu.weight (1 CPU gives 39 under runc 1.1, 100 under newer runc), limits.cpu becomes cpu.max, limits.memory becomes memory.max, the QoS class becomes oom_score_adj (Pod to cgroup, section 12).

1. Namespaces: a private view of one global resource

ch. 4 to 5 (the process), then beyond source namespaces(7); include/linux/nsproxy.h v5.10

The problem. Many things in Linux are global: the list of process IDs, the mount table, network interfaces and ports, the hostname, System V shared memory, the user ID numbers. Two training jobs on one machine would see each other's processes, could bind the same port, would share one /tmp. We want each job to believe it is alone, without paying for a second kernel.

How it works. A namespace "wraps a global system resource in an abstraction that makes it appear to the processes within the namespace that they have their own isolated instance of the global resource" (namespaces(7)). In the kernel this is one pointer per kind. Every task (thread) has a task_struct (the processes page walks it), and in it a pointer to a small struct nsproxy holding one pointer per namespace kind (nsproxy.h lines 31 to 41: uts_ns, ipc_ns, mnt_ns, pid_ns_for_children, net_ns, time_ns, time_ns_for_children, cgroup_ns; the user namespace lives in the task's credentials). Code that looks up a global thing, such as "which network interfaces exist", first follows the current task's pointer. Two processes with different pointers see different worlds; the kernel underneath is one.

Three system calls manage them: clone(flags) starts a child in new namespaces, unshare(flags) moves the caller into new ones, setns(fd) joins an existing one through a file such as /proc/<pid>/ns/net (which is how docker exec and nsenter get in). A namespace lives while anything refers to it: a process in it, an open file descriptor of its /proc/<pid>/ns/ file, or a bind mount of that file. The number in readlink /proc/self/ns/net, such as net:[4026532319], is an inode number that identifies the namespace: two processes with the same number share it.

What it costs here
The UTS, PID, cgroup, time and user namespaces cost under 10 microseconds each: a small structure and a pointer swap. The mount namespace copies the caller's whole mount table (23 mounts here) and costs about 19 microseconds; the IPC namespace about 43, because it mounts a private instance of the POSIX message-queue file system (ipc/namespace.c line 58). The network namespace costs about 2.4 ms, roughly 500 times more: setup_net runs every registered per-network initialiser in turn (net_namespace.c line 341), creating a loopback device, routing tables, firewall state and per-namespace sysctls. On this kernel it also creates two tunnel devices, tunl0 and ip6tnl0, in every new namespace, which the Build a container tab shows. As whole commands: /bin/true took ms, unshare with five namespaces ms, and with the network namespace as well ms; docker run --rm of the same image took s (median of 5). The kernel's part of starting a container is about 1% of docker run; the rest is the daemon, containerd, the shim, runc, and setting up the image's mount and the network (section 9).
When it bites in ML
  • Multi-node training and the network namespace. A container's own network namespace reaches the outside through a virtual Ethernet pair and NAT. NCCL and RDMA jobs usually run with the host's network namespace (docker run --network host, Kubernetes hostNetwork: true) or with the RDMA device passed in, so collectives use the real interfaces.
  • DataLoader workers and IPC. Workers pass batches through shared memory files in /dev/shm, which Docker mounts as a private 64 MiB tmpfs in each container (that is the mount namespace, not the IPC one). Too small, and workers die with "No space left on device" or a bus error: the root's Debug lab case "DataLoader workers run out of /dev/shm". Fix: --shm-size 8g, or --ipc host, which also shares System V shared memory with the host.
  • Debugging a running job from outside. nsenter -t <pid> -n ss -tnp runs the host's ss inside the job's network namespace without a shell in the image.
Commands that show it
lsns (every namespace and its first process), readlink /proc/<pid>/ns/*, nsenter -t <pid> -m -u -n -p, unshare --fork --pid --mount-proc bash (a shell that sees only itself), ip netns (named network namespaces, bind mounts in /run/netns).
A process calls unshare(CLONE_NEWPID) and then getpid(). What does it get?
A process's PID cannot change while it runs, so unshare(CLONE_NEWPID) only sets pid_ns_for_children: the next child it forks becomes PID 1 of the new namespace. That is why the field is named "for children", and why unshare --pid needs --fork. The Build a container tab shows it at step 2: the PID becomes 1 only after the fork. The time namespace works the same way.

2. PID namespaces and PID 1: the stop that loses a checkpoint

ch. 5 Interlude: Process API source pid_namespaces(7); kernel/pid_namespace.c, kernel/exit.c, kernel/signal.c v5.10

The problem. Inside a container the first process must look like the init of a whole machine: PID 1, the ancestor of everything. Kubernetes and Docker stop a container by signalling exactly that process. Which process is PID 1, and what it does with the signal, decides whether your training job writes its last checkpoint.

How it works. PID namespaces nest: a process has one PID in its own namespace and another in each ancestor namespace (the sleep 60 container of section 9 was PID 1 inside and PID 68321 on the VM). The first process created in a new PID namespace gets PID 1 and becomes the namespace's init: orphans in the namespace are re-parented to it (the processes page covers reaping and zombies). Two kernel rules make it special:

  1. It ignores signals it has no handler for. The namespace's init is marked SIGNAL_UNKILLABLE, and sig_task_ignored drops a signal whose action is the default (signal.c lines 89 to 91, v5.10). SIGTERM with no handler does nothing to PID 1. SIGKILL from an ancestor namespace (the container runtime) still works.
  2. When it dies, everything else dies. "If the 'init' process of a PID namespace terminates, the kernel terminates all of the processes in the namespace via a SIGKILL signal" (pid_namespaces(7)). In the source: when init exits, find_child_reaper finds no other reaper and calls zap_pid_ns_processes (exit.c line 527), which walks every PID in the namespace and sends SIGKILL (pid_namespace.c lines 172 to 211). No handler runs; no checkpoint is written.

Rule 1 is why people add an init (docker run --init starts tini as PID 1, which forwards signals and reaps zombies). Rule 2 is the trap in that fix, which the processes page measured first: tini forwards SIGTERM to its one child; when that child is a shell running Python, the shell dies at once, tini exits, and the kernel kills Python. The job is a stand-in for the root's training loop: on SIGTERM it writes a checkpoint that takes about 1 s (src/exp/stopjob.py), and logs every event with a time stamp.

Why the process-group variants fail too
tini with TINI_KILL_PROCESS_GROUP=1 (the -g flag) and dumb-init (which signals the whole process group by default) send SIGTERM to the shell and to Python (tini.c line 526, dumb-init.c line 66). It does not help: the shell still dies at once, the init still exits with it, and the namespace's SIGKILL follows within milliseconds. Python's handler is a Python function that runs between bytecodes, after the C-level signal handler has set a flag; the job's log has no "SIGTERM received" line in either run, so the SIGKILL arrived before that function ran. What saves the checkpoint is that the process holding PID 1 outlives the job.


The fix


    

  • Let Python be the process the signal reaches: exec python train.py at the end of any launcher script (the shell is replaced, keeping the PID), or the exec form CMD ["python", "train.py"] in a Dockerfile (the shell form CMD python train.py runs /bin/sh -c as PID 1).
    • 

  • If a shell must stay, make it forward and wait: python train.py & pid=$!; trap 'kill -TERM $pid' TERM; wait $pid; wait $pid (the second wait because the first returns as soon as the trap runs).
    • 

  • Install a SIGTERM handler in the job (the root's training job does); then even as PID 1 the signal is delivered.
    • 

  • With several processes per container (torchrun and its workers), let torchrun be the process that receives SIGTERM: it forwards it to the workers (Distributed Training covers elastic launch).
    • 



When it bites in ML
Preemptible and spot capacity, Kubernetes evictions and Slurm time limits all stop jobs this way: SIGTERM to PID 1, a grace period (Kubernetes' terminationGracePeriodSeconds, default 30 s), then SIGKILL (the processes page section 10 has the Kubernetes and Slurm sequences). In Kubernetes, shareProcessNamespace: true makes the pod's pause container PID 1 of a shared namespace (Kubernetes docs): your process is then not PID 1, so rule 1 no longer protects or hurts it, and the pause container reaps zombies.


A Dockerfile ends with CMD python train.py (no brackets), and the script has a SIGTERM handler that checkpoints. What happens on docker stop?




The shell form runs /bin/sh -c "python train.py", so the shell is PID 1: Debian's dash does not replace itself with a single command (measured: Python got PID 7, not 1). PID 1 with no SIGTERM handler ignores SIGTERM (rule 1), Python never hears about it, and after the grace period the runtime's SIGKILL kills the shell and then, by rule 2, Python: the "sh as PID 1" row above, 10.28 s and 137. Use CMD ["python", "train.py"].






3. Mount namespaces, images and overlayfs: what files it has


ch. 39 to 40 (files, file system implementation) source mount_namespaces(7), pivot_root(2), overlayfs docs, OCI image spec


The problem. A training image brings its own Python, PyTorch and CUDA runtime, which must not clash with the host's or another job's. Copying a whole 2 GB file tree for every container would be slow and waste disk; ten containers of one image should share one copy.


The mount namespace and the new root


A new mount namespace starts as a copy of the caller's mount table; after that, mounts and unmounts on either side are private, unless mount propagation says otherwise. Each mount is shared (events propagate both ways within its peer group), slave (receives, does not send) or private. systemd makes / shared on most hosts, so a runtime first marks its copy private, recursively, or its mounts would appear on the host: that is the first mount call at step 4 of the Build a container tab (mount(NULL, "/", NULL, MS_REC|MS_PRIVATE, NULL)).


Then the process needs a different /. chroot(dir) only changes where path lookups start for this process; the old root is still mounted and reachable, and a process with CAP_SYS_CHROOT can break out ("This call does not change the current working directory", and it "is not intended to be used for any kind of security purpose", chroot(2)). pivot_root(new_root, put_old) instead swaps the root mount of the whole mount namespace and moves the old one under put_old, which the runtime then unmounts, so the host's tree is no longer in the namespace at all. runc uses pivot_root unless told not to (--no-pivot, for a root on a ramdisk, which cannot be pivoted; it then uses a move-mount plus chroot). Docker 20.10's default seccomp profile does not list pivot_root at all (measured: the hand-built container needed seccomp=unconfined for it): runc calls it before it installs the container's filter, and the container itself never needs to.


overlayfs: layers, copy-up and whiteouts


The new root is an overlay mount: several read-only lower directories (the image layers), one writable upper directory (this container's changes) and a workdir for atomic operations, merged into one tree. A lookup returns the topmost layer's version of a name. Writing to a file that exists only in a lower layer triggers a copy-up: overlayfs copies the whole file into the upper layer first (ovl_copy_up_data, fs/overlayfs/copy_up.c line 132), then lets the write proceed. Deleting a lower-layer file creates a whiteout in the upper layer, a character device with device number 0/0 that hides the name. An overlay cannot use another overlay as its upper layer (the first attempt of this page's experiment failed with EINVAL until the layers moved to a tmpfs).

Images: what docker pull downloads


An OCI image is a manifest (a JSON list of content hashes), a config (environment, entry point, the ordered list of layer hashes) and the layers, each a tar archive of the files one build step added, changed or deleted (deletions stored as whiteout files). Identical layers are stored and downloaded once and shared by every image that uses them. Each RUN, COPY or ADD line of a Dockerfile makes a layer; ENV and WORKDIR only change the config (the 0B rows below).

When it bites in ML
    

  • Checkpoints and datasets written inside the container land in the upper layer on the node's disk: they vanish with the container, count against the node's ephemeral storage (Kubernetes evicts pods that exceed ephemeral-storage limits), and a later edit of a big file copies it up whole. Write them to a volume (a bind mount or a persistent volume is not part of the overlay); the storage page covers making them durable.
    • 

  • Model weights baked into an image make every node pull them before the job starts, and a change to one byte rebuilds and re-uploads the whole layer. Keep weights in object storage or a volume and the image for code and libraries; put the layers that change most (your code) last in the Dockerfile so the big ones (CUDA, PyTorch) stay cached.
    • 

  • pip install at container start writes thousands of files to the upper layer on every start. Bake dependencies into the image instead.
    •

4. cgroups v2: the tree, delegation, PIDs, I/O and freezing


ch. 9 Proportional Share, applied to groups source cgroup v2 (kernel docs); kernel/cgroup/cgroup.c, kernel/cgroup/pids.c v5.10


The problem. Namespaces hide things but limit nothing: a process in its own namespaces can still use every CPU, all memory and the whole disk bandwidth. We need to group processes, including the ones they will fork later, and give each group a budget, with accounting we can read.


How it works. A control group (cgroup) is a directory in one tree mounted at /sys/fs/cgroup (cgroup v2, the "unified hierarchy"; v1 had one tree per controller and is legacy). Every process is in exactly one cgroup, listed in its cgroup.procs file; children of a fork start in the parent's cgroup, so a whole job stays together. Controllers (cpu, memory, io, pids, cpuset, hugetlb, rdma here) each add interface files to the directories where they are enabled, such as memory.max or pids.max. A controller is available in a cgroup's children only if it is listed in that cgroup's cgroup.subtree_control. Limits are hierarchical: nothing below can escape a limit set above.


Two rules shape every container runtime:


    

  • No internal processes. A cgroup (other than the root) that has processes cannot enable domain controllers for children; otherwise the parent's own processes would compete with its children for the same budget. In the source, cgroup_vet_subtree_control_enable returns -EBUSY when the cgroup has tasks (cgroup.c lines 3203 to 3208). So processes live in leaves, and a manager first moves itself into a leaf.
    • 

  • Delegation. "A cgroup can be delegated in two ways": by giving a less privileged user write access to the directory and its cgroup.procs, cgroup.threads and cgroup.subtree_control files, or, with the nsdelegate mount option, automatically to a cgroup namespace. "Once delegated, the user can build sub-hierarchy under the directory ... and further distribute the resources it received from the parent" (cgroup v2 docs, "Delegation"). systemd does the first for a unit with Delegate=yes; rootless Podman and Kubernetes nodes running as systemd services rely on it.
    •

When it bites in ML
    

  • The pids limit counts threads. PyTorch, OpenMP and every DataLoader worker start threads; a Kubernetes pod PID limit or --pids-limit sized for "processes" fails at fork or thread creation (the root's Debug lab case "BlockingIOError on fork: the pids limit counts threads too").
    • 

  • io.max throttles data loading silently: the reads simply take longer, and only io.stat and the step time show it. Shared nodes use it (and io.weight) to stop one job's data pipeline from starving another's checkpoint writes.
    •

5. Memory limits: memory.max kills, memory.high stalls


ch. 13 to 23, applied to a group source cgroup v2: memory; mm/memcontrol.c v5.10


The problem. A training job's memory grows: DataLoader workers copy pages on write, a prefetch queue fills, a leak creeps. On a shared node something must stop one job before it takes memory from the others. There are two ways to stop it, a wall and a brake, and they fail very differently.


How it works. The memory controller charges each page to the cgroup of the task that first touched it: anonymous memory (heap, tensors), page cache from the files it reads and writes, and kernel memory on its behalf (socket buffers, slab). memory.current is the total. Four knobs act on it; the virtual memory page explains the OOM killer and how it picks a victim, so here we measure the knobs against each other.


FileWhat happens at the boundary


memory.maxthe wall: "If a cgroup's memory usage reaches this limit and can't be reduced, the OOM killer is invoked in the cgroup"


memory.highthe brake: "the processes of the cgroup are throttled and put under heavy reclaim pressure. Going over the high limit never invokes the OOM killer and under extreme conditions the limit may be breached"


memory.swap.maxhow much of the group may be swapped out (0: none, so anonymous memory cannot be reclaimed at all)


memory.min, memory.lowprotection: memory below them is not reclaimed (min) or reclaimed only as a last resort (low) when others need memory




Quotes from the kernel's cgroup v2 documentation, memory interface files.


The brake in the source: when a charge pushes a group over memory.high, the kernel reclaims, and on the way back to user space mem_cgroup_handle_over_high puts the task to sleep for a penalty that grows with the square of the overage (penalty_jiffies = max_overage * max_overage * HZ, scaled, in calculate_high_delay, memcontrol.c line 2583), capped at 2 s per return to user space (MEMCG_MAX_HIGH_DELAY_JIFFIES, line 2466). If reclaim frees enough, the task runs on; if nothing can be freed, it sleeps again on the next allocation, indefinitely.

Pressure stall information not run here


PSI measures the share of wall time in which tasks were stalled waiting for memory (also CPU and I/O): some (at least one task stalled) and full (all non-idle tasks stalled at once), averaged over 10, 60 and 300 s, in /proc/pressure/memory and in each cgroup's memory.pressure (PSI docs). When it bites in ML
    

  • Exit 137 and "OOMKilled" mean memory.max. Check memory.events (oom_kill) and memory.peak (Linux 5.19 and later) or your monitoring's peak; size the limit for the peak, including the page cache your data loading creates (reclaimable, but it counts until reclaimed).

  • A job that stops making progress with no error inside a cgroup with memory.high set close to its working set and no swap is throttled, not deadlocked: memory.events high keeps rising. You set memory.high 10% below memory.max as an early warning, with no swap. The job's working set grows past memory.high but stays under memory.max. What happens?




Over memory.high the kernel reclaims and then makes the task sleep, up to 2 s per return to user space, for as long as the overage lasts. With no swap and mostly anonymous memory there is nothing to reclaim, so it never gets back under: the "memory.high, no swap" run above stopped progressing after 210 MiB. 6. Capabilities and user namespaces: root, but not all of root


ch. 55 Access Control source capabilities(7), user_namespaces(7)


The problem. Most images run as root (user ID 0), and many programs expect to. Classic Unix has one test: UID 0 may do anything. A container's root must be able to install packages in its own file system and bind its own ports, but not load kernel modules, change the host's clock or reconfigure the host's network.


Capabilities. Linux splits root's power into about 40 capabilities, each a bit checked by the kernel at one kind of operation: CAP_CHOWN before changing a file's owner, CAP_NET_ADMIN before reconfiguring interfaces, CAP_SYS_ADMIN (the catch-all) before mounting, and so on. A process has several sets: permitted (what it may use), effective (what is switched on now, the set the kernel checks), inheritable and ambient (what passes across execve), and the bounding set (a ceiling no descendant can exceed). Docker starts containers with 14 capabilities, CapEff 00000000a80425fb (the root page decoded them). prctl(PR_SET_NO_NEW_PRIVS) adds a one-way switch: after it, execve can never grant more privilege, not even through a setuid binary; it is what lets an unprivileged process install a seccomp filter (section 7).


Eight privileged operations, each needing one capability, tried in four containers (measured, src/exp/caps_ops.py):




Port 80 worked even with no capabilities because Docker sets net.ipv4.ip_unprivileged_port_start to  in each container's network namespace, so binding low ports needs no privilege there. "not allowed to raise maximum limit" is Python's message for EPERM from setrlimit.


When it bites in ML
    

  • Pinned memory. pin_memory=True in a DataLoader and CUDA's cudaHostAlloc lock host pages so the GPU can copy from them by DMA (the virtual memory page). Locking is limited by RLIMIT_MEMLOCK, 64 KiB by default in these containers (src/raw/env.txt), unless the process has CAP_IPC_LOCK. Above, mlock of 64 MiB failed everywhere except with --cap-add IPC_LOCK. RDMA and GPUDirect stacks need it too: training containers usually run with --ulimit memlock=-1 or that capability.
    • 

  • Profilers and debuggers: py-spy dump, gdb -p and strace -p attach with ptrace; this page's siblings ran strace with --cap-add SYS_PTRACE. perf needs perf_event_open, which Docker's seccomp profile blocks (section 7).
    • 

  • Priorities: nice -5 for a data-feeding process failed without CAP_SYS_NICE.
    • 



User namespaces: root inside, an ordinary user outside


A user namespace gives a process its own numbering of user and group IDs and a full set of capabilities that apply only to resources owned by that namespace. A map in /proc/<pid>/uid_map (lines of "inside outside count") translates IDs at the boundary: files created by "root" inside are owned by the real user outside, and the host's files keep their real owners inside. Namespaces of other kinds created by a process in a user namespace are owned by it, so inside you may change the hostname of your own UTS namespace or mount a tmpfs in your own mount namespace, but not the host's. This is how rootless containers (Podman, rootless Docker, Apptainer on HPC clusters) work: a breakout lands as an ordinary user.




measured as UID 1000 in a container started with --user 1000:1000 --security-opt seccomp=unconfined (Docker's default profile blocks unshare(CLONE_NEWUSER) for a process without CAP_SYS_ADMIN). Inside, CapEff 000001ffffffffff is every capability, yet /etc/shadow (owned by the real root) stayed unreadable and the host's hostname unchangeable; the namespace's own new UTS and mount namespaces were fully its own. The time namespace shifted CLOCK_BOOTTIME by one day for its children only.


The cost of user namespaces
Every capability inside a user namespace exposes kernel code that used to be reachable only by real root (mounting some file systems, creating network devices). Canonical: "unprivileged user namespaces are now broadly used as a step in several privilege escalation exploit chains", citing Google's finding that 44% of the exploits it observed relied on them; Ubuntu 23.10 started restricting them (Ubuntu blog). Docker's default seccomp profile blocks creating them unless the container has CAP_SYS_ADMIN. Rootless gains you a lot if the container runtime has a bug; it adds kernel attack surface if the kernel has one.






7. seccomp-bpf: a filter on every system call


beyond OSTEP source seccomp(2), kernel seccomp filter docs; kernel/seccomp.c v5.10


The problem. Linux has about 400 system calls (Docker's default profile names 396 across its rules). A training job uses a few dozen. Every other call is kernel code an attacker can reach from inside the container; capabilities guard only some of them.


How it works. A process installs a small program in classic BPF (a tiny register machine with loads, compares, jumps and returns; no loops) with prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog) or seccomp(2). On every system call entry, before the call runs, the kernel runs the program on a struct seccomp_data: the call number, the architecture, the instruction pointer and the six argument values. The program returns an action: ALLOW, ERRNO (fail the call with a chosen error), KILL_PROCESS or KILL_THREAD, TRAP (deliver SIGSYS), LOG, TRACE, or USER_NOTIF (Linux 5.0: let a supervising process decide). Filters stack and are inherited across fork and execve; none can be removed; with several, all run and the most restrictive answer wins (seccomp_run_filters, seccomp.c lines 311 to 327). Installing one requires CAP_SYS_ADMIN or no_new_privs, so a filtered process can never execve a setuid program that would run with the filter but more privilege.


The filter the hand-built container installs at its step 8, all nine instructions:


/* arch first: a call number means different calls on different architectures */

BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL_PROCESS),

BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | EPERM),

BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | EPERM),

From src/exp/minictr.c. After it, mkdir and unshare failed with "Operation not permitted" and getpid worked (Build a container, step 8). A filter sees argument values only: it cannot follow a pointer to read a path, because the memory could change between the check and the use. Path rules are the job of LSMs (section 8).


Docker's default profile


Docker's profile is an allowlist with default action ERRNO (EPERM): 340 calls allowed outright, more allowed only with a capability (mount with CAP_SYS_ADMIN) or with certain arguments (clone without namespace flags). One trick: clone3 passes its flags inside a structure behind a pointer, which a filter cannot read, so the profile answers it with ENOSYS ("not implemented", error 38) and glibc falls back to the old clone, whose flags are visible (default.json at v20.10.17). io_uring: blocked in Docker 25, and charged per user


io_uring (the concurrency page teaches it) moves I/O submission into rings of memory shared with the kernel: one io_uring_enter call, or none with polling, submits many reads, writes, opens and socket operations, executed by the kernel. A seccomp filter sees the io_uring_enter, not the operations inside it. Docker 25.0 removed the three io_uring calls from its default profile (moby PR #46762, merged 2 November 2023), citing that "Google ChromeOS and Android have turned it off, plus all Google production servers turn it off" and that io_uring vulnerabilities have been used to break out of containers. Passing Docker 25's default.json to this 20.10 daemon reproduced it: io_uring_setup became "Operation not permitted" (table above, third column).


The 20.10 failure is a different limit. On Linux 5.10 every ring's pages are charged against RLIMIT_MEMLOCK, but counted in user->locked_vm, a counter that belongs to the user ID, not to the process, the container or the cgroup (__io_account_mem, fs/io_uring.c lines 7863 to 7880; skipped for processes with CAP_IPC_LOCK, line 9273). Containers without a user namespace share the host's UIDs, so every container running as UID 2000 draws on one budget:




measured src/exp/uring.sh: 1-entry rings (2 pages, 8 KiB each) created until one fails; 64 KiB allows 8. Container B, with its own namespaces and cgroup, got none while A held its rings, and 8 after A exited. Root got none even alone: other root-owned things on this VM had already used UID 0's 64 KiB. On 5.10 BPF programs and maps are charged to the same counter (__bpf_prog_charge, kernel/bpf/syscall.c line 1631), and runc attaches a BPF program to every cgroup v2 container to enforce its device rules, so running containers alone may account for it (likely, not traced). Later kernels moved both to the memory cgroup: kernel/bpf/syscall.c no longer touches locked_vm at v5.11, and at v5.12 io_uring allocates its rings with __GFP_ACCOUNT (fs/io_uring.c line 8061, v5.12) instead of charging ring_pages to the user.


When it bites in ML
    

  • Fast data readers built on io_uring fail with EPERM on Docker 25 and later and in Kubernetes runtimes with similar profiles; a library that does not fall back to ordinary reads breaks. On older kernels the same reader can fail with ENOMEM because some other container running as the same UID holds rings. Fix: a custom profile that allows io_uring, a different UID per job (or user namespaces), or --ulimit memlock high enough.
    • 

  • perf, bpftrace and some profilers need perf_event_open and bpf, blocked by default. Profile on the host, or start a debugging container with a custom profile and the needed capabilities, never --privileged on a shared node.
    • 

  • Kubernetes: securityContext.seccompProfile.type: RuntimeDefault applies the container runtime's profile; the Pod Security Standards' "restricted" level requires a profile (Pod Security Standards).

A seccomp filter must block opening /etc/shadow but allow every other openat. Can it?




The path is in the process's memory; the filter sees only the address in args[1]. Even if it could read the string, another thread could change it after the check (a time-of-check to time-of-use race). USER_NOTIF and TRACE hand the decision to another process, which has the same race to handle. Path policies belong to LSMs such as AppArmor, SELinux or Landlock, which check the resolved file inside the kernel.

9. Container runtimes: who makes all those calls


beyond OSTEP source OCI runtime spec, containerd, runc


The problem. Sections 1 to 8 are a few hundred lines of system calls in the right order. Somebody has to pull the image, unpack the layers, write the cgroup files, create the namespaces, mount the overlay, drop the capabilities, install the filter, start the process, keep its output and report its exit code, for thousands of containers, surviving restarts of the managing daemon.


How it works. The work is split into layers with standard interfaces between them. The OCI runtime specification defines a bundle: a root file system directory plus a config.json listing the process, its namespaces, mounts, cgroup limits, capabilities, seccomp profile and hooks. A low-level runtime (runc, written in Go; crun in C; youki in Rust) turns one bundle into one running process with exactly the system calls of the Build a container tab, then exits. A high-level runtime (containerd, CRI-O) pulls and stores images, prepares bundles, and starts one small shim process per container that becomes the container's parent, holds its standard streams, and collects its exit status, so containerd itself can restart without killing containers. Docker's daemon sits above containerd; Kubernetes' kubelet talks to containerd or CRI-O through the Container Runtime Interface (CRI).


docker CLIdockerd (REST API)containerd (images, snapshots, tasks)containerd-shim-runc-v2 (one per container)runc (creates it, then exits)your process

When it bites in ML
    

  • Restarting Docker does not have to kill training: with "live-restore": true in the daemon configuration, containers keep running under their shims while dockerd restarts (Docker docs).

  • HPC clusters usually have no daemon at all: Apptainer (formerly Singularity) runs a single-file image (SIF) as the submitting user, typically sharing the host's network and PID namespaces, which suits MPI and Slurm (Apptainer docs). 11. GPU containers: the driver stays on the host not run here


source NVIDIA Container Toolkit, CDI support, CDI specification


The problem. The GPU's kernel driver (nvidia.ko) belongs to the host kernel, and the user-space driver library (libcuda.so) must match it exactly. The image brings the CUDA runtime and PyTorch, but must not bring its own libcuda. The container needs the device files (/dev/nvidia0, /dev/nvidiactl, /dev/nvidia-uvm), the host's matching libraries, and permission in the device cgroup to open them.


How it works. Three pieces, all from the host. The device files are bind-mounted into the container's mount namespace. The device cgroup must allow them: on cgroup v2 there is no devices.allow file; runc attaches a small BPF program to the container's cgroup that checks every device open (the same kind of program that likely used up root's locked-memory budget in section 7). The driver libraries (libcuda.so, libnvidia-ml.so, the nvidia-smi binary) are bind-mounted from the host. The NVIDIA Container Toolkit does all three. Its newer interface is the Container Device Interface (CDI), "an open specification for container runtimes that abstracts what access to a device, such as an NVIDIA GPU, means": nvidia-ctk cdi generate --output=/var/run/cdi/nvidia.yaml writes a file listing, per device name such as nvidia.com/gpu=0, the device nodes, mounts, environment variables and hooks to apply, and a CDI-aware runtime applies them on --device nvidia.com/gpu=all (NVIDIA CDI docs).


When it bites in ML
    

  • "CUDA driver version is insufficient for CUDA runtime version": the image's CUDA runtime is newer than the host driver supports (the virtualization page covers driver and runtime compatibility).
    • 

  • An image that ships its own libcuda.so (copied from a build machine) shadows the host's and fails on a different driver version. Never put driver libraries in images.
    • 

  • GPU visibility is not GPU isolation: two containers given the same GPU share it by time-slicing with no memory limit between them; MIG gives hardware partitions (the virtualization page). In Kubernetes the NVIDIA device plugin advertises nvidia.com/gpu as a resource and the kubelet passes the chosen devices to the runtime.

Interview questions


What is a container, at the kernel level?
Not a kernel object: ordinary processes whose task_struct points at non-default namespaces (what they see), that sit in a cgroup (what they may use), with a reduced capability set, a seccomp filter and possibly an LSM profile (what they may do), and whose root is an overlay of image layers. The same kernel serves them, which is both why they start in milliseconds and why they are a weaker boundary than a VM.


Why does a training job sometimes ignore docker stop, and sometimes die instantly without checkpointing?
PID 1 of a PID namespace ignores signals whose action is the default, so a PID 1 without a SIGTERM handler (a shell) ignores the stop until SIGKILL. And when PID 1 exits, the kernel SIGKILLs every other process in the namespace, so an init or shell that dies on SIGTERM takes Python with it before its handler runs. Fix: the process that handles SIGTERM must be PID 1's direct target and must outlive the job's shutdown: exec, exec-form CMD, a forwarding trap.


memory.high or memory.max for a job's limit?
memory.max is a wall: reclaim, then OOM kill in the group. memory.high is a brake: reclaim and sleep up to 2 s per return to user space, never an OOM kill. Without swap and with anonymous memory, the brake becomes an indefinite stall that looks like a hang. Use memory.max as the limit; use memory.high only with something watching pressure (PSI) that can act.


Why can't seccomp filter by file path, and what does?
The filter is classic BPF over struct seccomp_data: the call number, architecture, instruction pointer and argument values. A path is behind a pointer in user memory, and reading it would race with other threads changing it. LSMs (AppArmor, SELinux, Landlock) check inside the kernel after the path is resolved to an inode.


A pod requests 1 CPU. What cpu.weight does it get, and why might that differ between clusters?
The kubelet converts 1000 milli-CPUs to 1024 cgroup v1 shares; the OCI runtime converts shares to a v2 weight. runc 1.1's linear map gives 39; the quadratic map in opencontainers/cgroups v0.0.3 and later (runc 1.3.6, 1.4.0) gives 100. Same pod spec, different share of a contended node, depending only on the runtime version.


When is a container not enough isolation, and what do you use instead?
When the code inside is hostile: one exploitable bug in any reachable kernel path gives the host. Use a sandbox that puts another kernel in the way: gVisor (a user-space kernel answering the calls, host exposed to a small enumerated set) or a microVM such as Firecracker or Kata (a guest kernel isolated by hardware virtualization), plus no network, tight cgroups and timeouts.









Build a container, one system call at a time


This is a container runtime in about 170 lines of C (src/exp/minictr.c). It starts as an ordinary root process, applies one restriction per step, and after each step prints everything the process can observe about its world: its PID, hostname, namespace numbers, how many processes and mounts it can see, its network interfaces, its cgroup and the limits visible to it, its capabilities and its seccomp state. Before it ran, a shell script made a busybox root file system for the overlay's lower layer and a cgroup /ctr with memory.max 64 MiB, memory.swap.max 0 and pids.max 16 (src/exp/minictr.sh).
