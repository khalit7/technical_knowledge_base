Build a container, one system call at a time

This is a container runtime in about 170 lines of C (src/exp/minictr.c). It starts as an ordinary root process, applies one restriction per step, and after each step prints everything the process can observe about its world: its PID, hostname, namespace numbers, how many processes and mounts it can see, its network interfaces, its cgroup and the limits visible to it, its capabilities and its seccomp state. At the end it execves a busybox shell that runs a small workload inside. Every value below was printed by that run measured (src/raw/minictr.txt).

It ran inside a Docker container started with --cap-add SYS_ADMIN --security-opt seccomp=unconfined, so that it could do what runc does on the host: create namespaces, mount, and call pivot_root (which Docker 20.10's default profile blocks). Before it ran, a shell script made a busybox root file system for the overlay's lower layer and a cgroup /ctr with memory.max 64 MiB, memory.swap.max 0 and pids.max 16 (src/exp/minictr.sh). Changed values are highlighted, with the old value struck through.

What to notice
    

  • Step 2: the PID becomes 1 only after the fork, yet ps would still see the outer processes: /proc is the old namespace's until step 4 mounts a new one.
    • 

  • Step 3: /proc/self/cgroup becomes 0::/, but the visible memory.max is still the outer container's 1.5 GB: a cgroup namespace changes how paths are shown, and the mounted cgroup file system is the old view until step 4 remounts it.
    • 

  • Step 4: one visible process, seven root entries, eight mounts: the host's tree is gone from this mount namespace, not merely hidden.
    • 

  • Step 5: the network namespace has no eth0, only loopback and two tunnel devices this kernel creates in every namespace. A real runtime would now add one end of a virtual Ethernet pair.
    • 

  • Step 7: CapEff drops from a82425fb (Docker's 14 plus CAP_SYS_ADMIN) to a80425fb, Docker's 14: bit 21 gone. Root can still chown, but no longer change the hostname or mount.
    • 

  • Step 9: the cgroup limits bite: a fork past 16 tasks fails, and a 100 MB allocation is OOM-killed inside the 64 MiB group while the shell survives. The deleted /etc/passwd becomes a whiteout in the upper layer.
    •
