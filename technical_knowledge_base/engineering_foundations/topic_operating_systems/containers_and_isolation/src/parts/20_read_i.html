9. Container runtimes: who makes all those calls

beyond OSTEP source {{OCI runtime spec|https://github.com/opencontainers/runtime-spec/blob/main/spec.md}}, {{containerd|https://containerd.io/docs/}}, {{runc|https://github.com/opencontainers/runc}}

The problem. Sections 1 to 8 are a few hundred lines of system calls in the right order. Somebody has to pull the image, unpack the layers, write the cgroup files, create the namespaces, mount the overlay, drop the capabilities, install the filter, start the process, keep its output and report its exit code, for thousands of containers, surviving restarts of the managing daemon.

How it works. The work is split into layers with standard interfaces between them. The OCI runtime specification defines a bundle: a root file system directory plus a config.json listing the process, its namespaces, mounts, cgroup limits, capabilities, seccomp profile and hooks. A low-level runtime (runc, written in Go; crun in C; youki in Rust) turns one bundle into one running process with exactly the system calls of the {{Build a container|#t-build}} tab, then exits. A high-level runtime (containerd, CRI-O) pulls and stores images, prepares bundles, and starts one small shim process per container that becomes the container's parent, holds its standard streams, and collects its exit status, so containerd itself can restart without killing containers. Docker's daemon sits above containerd; Kubernetes' kubelet talks to containerd or CRI-O through the Container Runtime Interface (CRI).

docker CLIdockerd (REST API)containerd (images, snapshots, tasks)containerd-shim-runc-v2 (one per container)runc (creates it, then exits)your process

The real chain on this VM, seen from a container that shares the VM's PID namespace (--pid host, a read-only listing) while a sleep 60 container ran (measured, src/exp/runtime.sh; Docker Desktop also runs its own system services as containers under a second containerd, omitted):



The container's process is a child of its shim, not of dockerd or containerd; runc is gone. Its PID is 68321 on the VM and 1 inside. Docker Desktop's dockerd is itself a service running under the VM's system containerd.


When it bites in ML
    

  • Restarting Docker does not have to kill training: with "live-restore": true in the daemon configuration, containers keep running under their shims while dockerd restarts ({{Docker docs|https://docs.docker.com/engine/daemon/live-restore/}}).
    • 

  • HPC clusters usually have no daemon at all: Apptainer (formerly Singularity) runs a single-file image (SIF) as the submitting user, typically sharing the host's network and PID namespaces, which suits MPI and Slurm ({{Apptainer docs|https://apptainer.org/docs/user/latest/introduction.html}}). The GPU and InfiniBand devices are simply visible, and there is no root inside to escape from.
    • 

  • Start-up: docker run --rm took about 0.4 s here, of which the namespaces were about 4 ms (section 1). A job that starts thousands of short containers (evaluation sandboxes, RL environments) is dominated by the runtime, not the kernel.

10. Sandboxes for code you do not trust not run here


appendix Virtual Machines source {{gVisor security model|https://gvisor.dev/docs/architecture_guide/security/}}, {{Firecracker design|https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md}}, {{Firecracker specification|https://github.com/firecracker-microvm/firecracker/blob/main/SPECIFICATION.md}}, {{Kata Containers|https://katacontainers.io/}}


The problem. Everything so far narrows what a container can ask of the host kernel, but the kernel answering is the host's. A container runs model-generated code, a user's notebook or an untrusted evaluation submission; one kernel bug reachable through an allowed call and the code is on the host, next to other customers' data. The fix is to put another kernel between the code and the host, and to make that kernel either smaller or isolated by hardware.

When it bites in ML
    

  • GPUs in sandboxes: a VM needs the GPU passed through (VFIO, the {{virtualization page|n:3f05c17b0d0d8158b029e9b2ba2e161b}}); gVisor's nvproxy forwards the NVIDIA driver's ioctl calls and "supports running most CUDA applications on preselected versions of NVIDIA's open source driver" ({{gVisor GPU docs|https://gvisor.dev/docs/user_guide/gpu/}}).
    • 

  • RL environments and evaluation harnesses that execute model output (unit-test rewards, code benchmarks) should run each episode in a sandbox of this kind, with no network unless needed, a CPU and memory cgroup limit, and a wall-clock timeout; a plain container with the default profile is not a security boundary against code written to escape it.

11. GPU containers: the driver stays on the host not run here


source {{NVIDIA Container Toolkit|https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/index.html}}, {{CDI support|https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/cdi-support.html}}, {{CDI specification|https://github.com/cncf-tags/container-device-interface/blob/main/SPEC.md}}


The problem. The GPU's kernel driver (nvidia.ko) belongs to the host kernel, and the user-space driver library (libcuda.so) must match it exactly. The image brings the CUDA runtime and PyTorch, but must not bring its own libcuda. The container needs the device files (/dev/nvidia0, /dev/nvidiactl, /dev/nvidia-uvm), the host's matching libraries, and permission in the device cgroup to open them.


How it works. Three pieces, all from the host. The device files are bind-mounted into the container's mount namespace. The device cgroup must allow them: on cgroup v2 there is no devices.allow file; runc attaches a small BPF program to the container's cgroup that checks every device open (the same kind of program that likely used up root's locked-memory budget in section 7). Without it, a device node the container creates still cannot be opened: {{Virtualization and the GPU driver stack|n:3f05c17b0d0d8158b029e9b2ba2e161b}}, section 9, made /dev/nvidiactl (195:255) with mknod and got EPERM on open, and with --device-cgroup-rule 'c 195:* rwm' the same open got past the cgroup and failed only with ENXIO, because no GPU driver is loaded there. The driver libraries (libcuda.so, libnvidia-ml.so, the nvidia-smi binary) are bind-mounted from the host. The NVIDIA Container Toolkit does all three. Its newer interface is the Container Device Interface (CDI), "an open specification for container runtimes that abstracts what access to a device, such as an NVIDIA GPU, means": nvidia-ctk cdi generate --output=/var/run/cdi/nvidia.yaml writes a file listing, per device name such as nvidia.com/gpu=0, the device nodes, mounts, environment variables and hooks to apply, and a CDI-aware runtime applies them on --device nvidia.com/gpu=all (NVIDIA CDI docs).


When it bites in ML
    

  • "CUDA driver version is insufficient for CUDA runtime version": the image's CUDA runtime is newer than the host driver supports (the {{virtualization page|n:3f05c17b0d0d8158b029e9b2ba2e161b}} covers driver and runtime compatibility).
    • 

  • An image that ships its own libcuda.so (copied from a build machine) shadows the host's and fails on a different driver version. Never put driver libraries in images.
    • 

  • GPU visibility is not GPU isolation: two containers given the same GPU share it by time-slicing with no memory limit between them; MIG gives hardware partitions (the {{virtualization page|n:3f05c17b0d0d8158b029e9b2ba2e161b}}). In Kubernetes the NVIDIA device plugin advertises nvidia.com/gpu as a resource and the kubelet passes the chosen devices to the runtime.
    •
