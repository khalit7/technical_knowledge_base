1. Namespaces: a private view of one global resource

ch. 4 to 5 (the process), then beyond source {{namespaces(7)|https://man7.org/linux/man-pages/man7/namespaces.7.html}}; include/linux/nsproxy.h v5.10

The problem. Many things in Linux are global: the list of process IDs, the mount table, network interfaces and ports, the hostname, System V shared memory, the user ID numbers. Two training jobs on one machine would see each other's processes, could bind the same port, would share one /tmp. We want each job to believe it is alone, without paying for a second kernel.

How it works. A namespace "wraps a global system resource in an abstraction that makes it appear to the processes within the namespace that they have their own isolated instance of the global resource" (namespaces(7)). In the kernel this is one pointer per kind. Every task (thread) has a task_struct (the {{processes page|n:3f05c17b0d0d811e99f7cb8c15d12697}} walks it), and in it a pointer to a small struct nsproxy holding one pointer per namespace kind ({{nsproxy.h lines 31 to 41|https://github.com/torvalds/linux/blob/v5.10/include/linux/nsproxy.h#L31}}: uts_ns, ipc_ns, mnt_ns, pid_ns_for_children, net_ns, time_ns, time_ns_for_children, cgroup_ns; the user namespace lives in the task's credentials). Code that looks up a global thing, such as "which network interfaces exist", first follows the current task's pointer. Two processes with different pointers see different worlds; the kernel underneath is one.

Three system calls manage them: clone(flags) starts a child in new namespaces, unshare(flags) moves the caller into new ones, setns(fd) joins an existing one through a file such as /proc/<pid>/ns/net (which is how docker exec and nsenter get in). A namespace lives while anything refers to it: a process in it, an open file descriptor of its /proc/<pid>/ns/ file, or a bind mount of that file. The number in readlink /proc/self/ns/net, such as net:[4026532319], is an inode number that identifies the namespace: two processes with the same number share it.

What it costs here
The UTS, PID, cgroup, time and user namespaces cost under 10 microseconds each: a small structure and a pointer swap. The mount namespace copies the caller's whole mount table (23 mounts here) and costs about 19 microseconds; the IPC namespace about 43, because it mounts a private instance of the POSIX message-queue file system ({{ipc/namespace.c line 58|https://github.com/torvalds/linux/blob/v5.10/ipc/namespace.c#L58}}). The network namespace costs about 2.4 ms, roughly 500 times more: setup_net runs every registered per-network initialiser in turn ({{net_namespace.c line 341|https://github.com/torvalds/linux/blob/v5.10/net/core/net_namespace.c#L341}}), creating a loopback device, routing tables, firewall state and per-namespace sysctls. On this kernel it also creates two tunnel devices, tunl0 and ip6tnl0, in every new namespace, which the {{Build a container|#t-build}} tab shows. As whole commands: /bin/true took ms, unshare with five namespaces ms, and with the network namespace as well ms; docker run --rm of the same image took s (median of 5). The kernel's part of starting a container is about 1% of docker run; the rest is the daemon, containerd, the shim, runc, and setting up the image's mount and the network (section 9).
When it bites in ML
  • Multi-node training and the network namespace. A container's own network namespace reaches the outside through a virtual Ethernet pair and NAT. NCCL and RDMA jobs usually run with the host's network namespace (docker run --network host, Kubernetes hostNetwork: true) or with the RDMA device passed in, so collectives use the real interfaces.
  • DataLoader workers and IPC. Workers pass batches through shared memory files in /dev/shm, which Docker mounts as a private 64 MiB tmpfs in each container (that is the mount namespace, not the IPC one). Too small, and workers die with "No space left on device" or a bus error: the root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} case "DataLoader workers run out of /dev/shm". Fix: --shm-size 8g, or --ipc host, which also shares System V shared memory with the host.
  • Debugging a running job from outside. nsenter -t <pid> -n ss -tnp runs the host's ss inside the job's network namespace without a shell in the image.
Commands that show it
lsns (every namespace and its first process), readlink /proc/<pid>/ns/*, nsenter -t <pid> -m -u -n -p, unshare --fork --pid --mount-proc bash (a shell that sees only itself), ip netns (named network namespaces, bind mounts in /run/netns).
A process calls unshare(CLONE_NEWPID) and then getpid(). What does it get?
A process's PID cannot change while it runs, so unshare(CLONE_NEWPID) only sets pid_ns_for_children: the next child it forks becomes PID 1 of the new namespace. That is why the field is named "for children", and why unshare --pid needs --fork. The {{Build a container|#t-build}} tab shows it at step 2: the PID becomes 1 only after the fork. The time namespace works the same way.
