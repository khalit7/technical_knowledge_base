2. PID namespaces and PID 1: the stop that loses a checkpoint

ch. 5 Interlude: Process API source {{pid_namespaces(7)|https://man7.org/linux/man-pages/man7/pid_namespaces.7.html}}; kernel/pid_namespace.c, kernel/exit.c, kernel/signal.c v5.10

The problem. Inside a container the first process must look like the init of a whole machine: PID 1, the ancestor of everything. Kubernetes and Docker stop a container by signalling exactly that process. Which process is PID 1, and what it does with the signal, decides whether your training job writes its last checkpoint.

How it works. PID namespaces nest: a process has one PID in its own namespace and another in each ancestor namespace (the sleep 60 container of section 9 was PID 1 inside and PID 68321 on the VM). The first process created in a new PID namespace gets PID 1 and becomes the namespace's init: orphans in the namespace are re-parented to it (the {{processes page|n:3f05c17b0d0d811e99f7cb8c15d12697}} covers reaping and zombies). Two kernel rules make it special:

  1. It ignores signals it has no handler for. The namespace's init is marked SIGNAL_UNKILLABLE, and sig_task_ignored drops a signal whose action is the default ({{signal.c lines 89 to 91, v5.10|https://github.com/torvalds/linux/blob/v5.10/kernel/signal.c#L89}}). SIGTERM with no handler does nothing to PID 1. SIGKILL from an ancestor namespace (the container runtime) still works.
  2. When it dies, everything else dies. "If the 'init' process of a PID namespace terminates, the kernel terminates all of the processes in the namespace via a SIGKILL signal" (pid_namespaces(7)). In the source: when init exits, find_child_reaper finds no other reaper and calls zap_pid_ns_processes ({{exit.c line 527|https://github.com/torvalds/linux/blob/v5.10/kernel/exit.c#L527}}), which walks every PID in the namespace and sends SIGKILL ({{pid_namespace.c lines 172 to 211|https://github.com/torvalds/linux/blob/v5.10/kernel/pid_namespace.c#L172}}). No handler runs; no checkpoint is written.

Rule 1 is why people add an init (docker run --init starts {{tini|https://github.com/krallin/tini}} as PID 1, which forwards signals and reaps zombies). Rule 2 is the trap in that fix, which the {{processes page|n:3f05c17b0d0d811e99f7cb8c15d12697}} measured first: tini forwards SIGTERM to its one child; when that child is a shell running Python, the shell dies at once, tini exits, and the kernel kills Python. Why the process-group variants fail too
tini with TINI_KILL_PROCESS_GROUP=1 (the -g flag) and dumb-init (which signals the whole process group by default) send SIGTERM to the shell and to Python ({{tini.c line 526|https://github.com/krallin/tini/blob/v0.19.0/src/tini.c#L526}}, {{dumb-init.c line 66|https://github.com/Yelp/dumb-init/blob/v1.2.5/dumb-init.c#L66}}). It does not help: the shell still dies at once, the init still exits with it, and the namespace's SIGKILL follows within milliseconds. Python's handler is a Python function that runs between bytecodes, after the C-level signal handler has set a flag; the job's log has no "SIGTERM received" line in either run, so the SIGKILL arrived before that function ran. What saves the checkpoint is that the process holding PID 1 outlives the job.


The fix


    

  • Let Python be the process the signal reaches: exec python train.py at the end of any launcher script (the shell is replaced, keeping the PID), or the exec form CMD ["python", "train.py"] in a Dockerfile (the shell form CMD python train.py runs /bin/sh -c as PID 1).
    • 

  • If a shell must stay, make it forward and wait: python train.py & pid=$!; trap 'kill -TERM $pid' TERM; wait $pid; wait $pid (the second wait because the first returns as soon as the trap runs).
    • 

  • Install a SIGTERM handler in the job (the root's training job does); then even as PID 1 the signal is delivered.
    • 

  • With several processes per container (torchrun and its workers), let torchrun be the process that receives SIGTERM: it forwards it to the workers ({{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}} covers elastic launch).
    • 



When it bites in ML
Preemptible and spot capacity, Kubernetes evictions and Slurm time limits all stop jobs this way: SIGTERM to PID 1, a grace period (Kubernetes' terminationGracePeriodSeconds, default 30 s), then SIGKILL (the {{processes page|n:3f05c17b0d0d811e99f7cb8c15d12697}} section 10 has the Kubernetes and Slurm sequences). In Kubernetes, shareProcessNamespace: true makes the pod's pause container PID 1 of a shared namespace ({{Kubernetes docs|https://kubernetes.io/docs/tasks/configure-pod-container/share-process-namespace/}}): your process is then not PID 1, so rule 1 no longer protects or hurts it, and the pause container reaps zombies.

The shell form runs /bin/sh -c "python train.py", so the shell is PID 1: Debian's dash does not replace itself with a single command (measured: Python got PID 7, not 1). PID 1 with no SIGTERM handler ignores SIGTERM (rule 1), Python never hears about it, and after the grace period the runtime's SIGKILL kills the shell and then, by rule 2, Python: the "sh as PID 1" row above, 10.28 s and 137.
