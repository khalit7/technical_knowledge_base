5. Memory limits: memory.max kills, memory.high stalls

ch. 13 to 23, applied to a group source {{cgroup v2: memory|https://docs.kernel.org/admin-guide/cgroup-v2.html#memory}}; mm/memcontrol.c v5.10

The problem. A training job's memory grows: DataLoader workers copy pages on write, a prefetch queue fills, a leak creeps. On a shared node something must stop one job before it takes memory from the others. There are two ways to stop it, a wall and a brake, and they fail very differently.

How it works. The memory controller charges each page to the cgroup of the task that first touched it: anonymous memory (heap, tensors), page cache from the files it reads and writes, and kernel memory on its behalf (socket buffers, slab). memory.current is the total. Four knobs act on it; the {{virtual memory page|n:3f05c17b0d0d81a48892cea154ce950b}} explains the OOM killer and how it picks a victim, so here we measure the knobs against each other.

FileWhat happens at the boundary
memory.maxthe wall: "If a cgroup's memory usage reaches this limit and can't be reduced, the OOM killer is invoked in the cgroup"
memory.highthe brake: "the processes of the cgroup are throttled and put under heavy reclaim pressure. Going over the high limit never invokes the OOM killer and under extreme conditions the limit may be breached"
memory.swap.maxhow much of the group may be swapped out (0: none, so anonymous memory cannot be reclaimed at all)
memory.min, memory.lowprotection: memory below them is not reclaimed (min) or reclaimed only as a last resort (low) when others need memory

Quotes from the kernel's cgroup v2 documentation, memory interface files.

The brake in the source: when a charge pushes a group over memory.high, the kernel reclaims, and on the way back to user space mem_cgroup_handle_over_high puts the task to sleep for a penalty that grows with the square of the overage (penalty_jiffies = max_overage * max_overage * HZ, scaled, in {{calculate_high_delay, memcontrol.c line 2583|https://github.com/torvalds/linux/blob/v5.10/mm/memcontrol.c#L2583}}), capped at 2 s per return to user space ({{MEMCG_MAX_HIGH_DELAY_JIFFIES, line 2466|https://github.com/torvalds/linux/blob/v5.10/mm/memcontrol.c#L2466}}). If reclaim frees enough, the task runs on; if nothing can be freed, it sleeps again on the next allocation, indefinitely.

The same input three ways: a process allocates 300 MiB, 10 MiB at a time, touching every page (src/exp/hog.py), in a cgroup capped at 200 MiB by each knob in turn (measured, src/raw/cgroup.txt).

What the three runs show
  • memory.max: the allocation ran at full speed to MiB, then the cgroup's OOM killer sent SIGKILL (exit 137, oom_kill 1). Fast, loud, unambiguous.
  • memory.high, no swap: nothing could be reclaimed (anonymous memory, nowhere to swap it). The step past 200 MiB took ms, the next s, and then the process made no further progress until the 60 s timeout killed it. memory.events counted high events and no OOM. To the outside it looks hung, with no error anywhere.
  • memory.high, swap allowed: reclaim swapped the overflow out (memory.current stayed at 199 MiB while the process held 300) and the run finished in ms. Fine here because nothing reads the swapped pages back; a training step that touches them pays a major fault each time (pgmajfault already).

Who dies: memory.oom.group

By default the OOM killer kills one process, the one with the highest score in the group. With memory.oom.group=1, "all tasks belonging to the cgroup or to its descendants ... are killed together or not at all". Measured with a long-running "main" process and a "worker" that grows past memory.max:

memory.oom.groupworkermainmemory.events

That difference matters because Kubernetes sets memory.oom.group=1 on every container on cgroup v2 unless the node's kubelet is configured with singleProcessOOMKill: true ({{kuberuntime_container_linux.go lines 314 to 319, v1.34.0|https://github.com/kubernetes/kubernetes/blob/v1.34.0/pkg/kubelet/kuberuntime/kuberuntime_container_linux.go#L314}}; the default is false on cgroup v2, {{kubelet.go lines 734 to 743|https://github.com/kubernetes/kubernetes/blob/v1.34.0/pkg/kubelet/kubelet.go#L734}}). Under Docker (group 0), a DataLoader worker that goes over the limit dies alone and the main process raises "DataLoader worker (pid N) is killed by signal: Killed." (the root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} case "Killed with exit code 137"). Under Kubernetes the same event kills the main process and every worker: the pod shows OOMKilled and restarts from the last checkpoint.

Pressure stall information not run here

PSI measures the share of wall time in which tasks were stalled waiting for memory (also CPU and I/O): some (at least one task stalled) and full (all non-idle tasks stalled at once), averaged over 10, 60 and 300 s, in /proc/pressure/memory and in each cgroup's memory.pressure ({{PSI docs|https://docs.kernel.org/accounting/psi.html}}). It is the signal that tells a stall like the "memory.high, no swap" run above from a job that is merely slow: there full would have sat near 100%. systemd-oomd kills cgroups on it ({{systemd-oomd|https://www.freedesktop.org/software/systemd/man/latest/systemd-oomd.service.html}}). This kernel was built without it (CONFIG_PSI is not set, src/raw/env.txt), so the only trace of the stall here was the high counter in memory.events.

When it bites in ML
  • Exit 137 and "OOMKilled" mean memory.max. Check memory.events (oom_kill) and memory.peak (Linux 5.19 and later) or your monitoring's peak; size the limit for the peak, including the page cache your data loading creates (reclaimable, but it counts until reclaimed).
  • A job that stops making progress with no error inside a cgroup with memory.high set close to its working set and no swap is throttled, not deadlocked: memory.events high keeps rising. Kubernetes' MemoryQoS feature would set memory.high for you; it is still alpha and off by default at v1.34 ({{kube_features.go line 1478|https://github.com/kubernetes/kubernetes/blob/v1.34.0/pkg/features/kube_features.go#L1478}}).
  • Swap and training don't mix: a swapped-out parameter or optimizer page is a major fault on the next step. The {{virtual memory page|n:3f05c17b0d0d81a48892cea154ce950b}} measured the slowdown.
Commands that show it
cat memory.current memory.max memory.high memory.events memory.stat in the job's cgroup (/sys/fs/cgroup inside a container with a cgroup namespace), dmesg | grep -i "memory cgroup out of memory" on the host (not available in this VM), kubectl describe pod (Last State: OOMKilled).
You set memory.high 10% below memory.max as an early warning, with no swap. The job's working set grows past memory.high but stays under memory.max. What happens?
Over memory.high the kernel reclaims and then makes the task sleep, up to 2 s per return to user space, for as long as the overage lasts. With no swap and mostly anonymous memory there is nothing to reclaim, so it never gets back under: the "memory.high, no swap" run above stopped progressing after 210 MiB. Use memory.high only with something watching it (PSI, a controller that raises it), or not at all.
