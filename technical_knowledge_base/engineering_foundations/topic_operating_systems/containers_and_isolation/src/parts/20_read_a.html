The idea

A container is not a thing the kernel knows about: it is ordinary processes on the host's one kernel, given a private view (namespaces), a budget (cgroups), fewer powers (capabilities, seccomp, LSMs) and a layered root file system (an image). Because the kernel is shared, a container keeps well-behaved jobs apart but is not a security boundary like a VM: hostile code needs another kernel in the way.

Fig. 1: one kernel, many containers, step by step

  1. One kernel, ordinary processes. Two containers on one machine, an illustrative pair: a training job (python train.py and two DataLoader workers) and a notebook. To the kernel floor below they are just processes; "container" is not a kernel object.
  2. SEE: namespaces. Each group gets a private view: its own PID numbers, mount table, network stack, hostname, IPC, user IDs, cgroup path and clocks. The sleep 60 container of section 9 was PID 1 inside and PID 68321 on the VM (sections 1 to 3).
  3. USE: a cgroup. A budget for the whole group, workers included: memory.max, cpu.max, io.max, pids.max. Usage that reaches the ceiling is pushed back: reclaim, a failed fork, an OOM kill (sections 4, 5).
  4. HAVE: an image. Read-only layers plus one writable layer, merged by overlayfs into the container's /; the image measured here, kb-os-cont:1, has six (section 3).
  5. DO: the gate. Capabilities, seccomp and LSMs check each system call before the kernel acts: Docker's default 14 capabilities, and a filter that refused perf_event_open with EPERM (sections 6 to 8).
  6. Nothing else in between. An allowed call runs the host kernel's own code, the same kernel for both containers. Everything a runtime such as Docker does is a sequence of ordinary system calls (section 0 makes them by hand, section 9 shows who makes them for real), and a kernel bug reachable through an allowed call is a way out: hostile code needs another kernel in the way (section 10).

New terms (each defined again where it is taught):

namespace: a private copy of one global kernel table (PIDs, mounts, network...)
cgroup, controller: a group of processes in one tree; the code that limits one resource for it
overlayfs, copy-up, whiteout: layers merged into one tree; a file copied to the writable layer on first write; a marker that hides a deleted name
OCI image, bundle: a manifest, a config and layer archives; a root file system plus config.json
capability: one of about 40 slices of root's power
user namespace, rootless: its own user-ID numbering; root inside, an ordinary user outside
seccomp-bpf: a small program run on every system call entry
LSM: a mandatory policy checked on objects (AppArmor, SELinux, Landlock)
runtime, shim: runc and containerd; the per-container parent process
gVisor, microVM: a kernel in user space; a minimal VM with its own kernel
CDI: a file listing what giving a container a device means
QoS class: Kubernetes' Guaranteed, Burstable or BestEffort
In one screen: eight things to remember
  1. A container is processes plus restrictions. The same kernel runs it; a kernel bug reachable through an allowed system call is a way out. Code you do not trust needs a sandbox with its own kernel or a kernel in user space (section 10).
  2. Namespaces are cheap, except the network one. Creating a UTS, PID, cgroup or time namespace took 3 to 5 microseconds here; a network namespace took 2.4 ms (section 1).
  3. When PID 1 of a container dies, the kernel SIGKILLs everything else in it. A shell or --init between docker stop and Python lost the checkpoint in all three such setups here (0.24 to 0.27 s, exit 143); exec, a forwarding trap, or Python as PID 1 saved it in 1.3 to 1.9 s (section 2).
  4. memory.max kills; memory.high stalls. The same 300 MiB allocation was OOM-killed at 190 MiB under memory.max=200M, but under memory.high=200M with no swap it hung for the full 60 s without an error, and with swap it finished in 0.3 s (section 5).
  5. Kubernetes kills the whole container on an OOM. On cgroup v2 the kubelet sets memory.oom.group=1, so a DataLoader worker going over the limit takes the main process with it; under Docker's default only the worker dies (section 5).
  6. Root inside is not all of root. Docker's 14 default capabilities cannot raise priority, pin 64 MiB of memory or mount anything; Docker's default seccomp profile changed the answer for 7 of the 12 calls probed, five of which worked without it (6, 7).
  7. Some limits are per user, not per container. io_uring rings and BPF programs on Linux 5.10 are charged to the UID: two containers running as the same UID shared one 64 KiB budget, and root's was already spent (section 7).
  8. Kubernetes requests become cgroup files by formulas you can check: requests.cpu becomes cpu.weight (1 CPU gives 39 under runc 1.1, 100 under newer runc), limits.cpu becomes cpu.max, limits.memory becomes memory.max, the QoS class becomes oom_score_adj (section 12).
How this page was measured, and the OSTEP chapter map

Docker Desktop's Linux VM on an Apple M1 laptop (Linux 5.10.104-linuxkit, arm64, 5 CPUs, about 10 GB, cgroup v2 with the cgroupfs driver), Docker 20.10.17 with runc v1.1.2, October 2026, image kb-os-cont:1 (the root's lab image plus busybox, tini 0.19 and dumb-init 1.2.5). No container was privileged. Two experiments needed one extra right each, stated where used: --cap-add SYS_ADMIN to create namespaces and to remount the container's own cgroup subtree writable; --security-opt seccomp=unconfined where Docker's default filter blocks the very call being taught (pivot_root, or unshare(CLONE_NEWUSER) as a non-root user). This kernel has no pressure stall information (CONFIG_PSI is not set) and no AppArmor or SELinux, so those are taught from the kernel source and documentation and tagged not run here, as are gVisor, Firecracker, GPU containers and Kubernetes itself. Labels: measured ran here; source read from source or documentation. Scripts and raw outputs: src/exp/ and src/raw/ in the repository.

What the process sees now






Every value was printed by that run measured (src/raw/minictr.txt). It ran inside a Docker container started with --cap-add SYS_ADMIN --security-opt seccomp=unconfined, so that it could do what runc does on the host: create namespaces, mount, and call pivot_root (which Docker 20.10's default profile blocks). Beforehand a shell script made a busybox root file system for the overlay's lower layer and a cgroup /ctr with memory.max 64 MiB, memory.swap.max 0 and pids.max 16 (src/exp/minictr.sh).






0. A container in ten system calls


A container runtime in about 170 lines of C (src/exp/minictr.c) starts as an ordinary root process, applies one restriction per step, and after each step prints everything the process can observe: its PID, hostname, namespace numbers, how many processes and mounts it sees, its network interfaces, its cgroup and visible limits, its capabilities and seccomp state. Then it execves a busybox shell that runs a small workload. Step through it before the mechanisms: every later section explains one of these steps. The steps are numbered from 0, as the program numbers them.


    

  1. Start: an ordinary root process. The baseline, inside the outer Docker container: its namespaces, 22 entries in /, 23 mounts, eth0, the outer cgroup /init, and no seccomp filter (the outer container ran unconfined). It creates one System V shared memory segment, to watch at step 6.
    2. 

  2. A new UTS namespace. Only the uts namespace number and the hostname change. The outer container still has its own hostname: this process now has a private copy (kernel side: unshare_nsproxy_namespaces).
    3. 

  3. A new PID namespace, then fork. The child is PID 1 with parent 0 (its parent is outside the namespace): the pid becomes 1 only after the fork, because unshare sets only pid_ns_for_children (alloc_pid in fork.c). Yet it still sees 3 processes: /proc is the old namespace's until step 4 mounts a new one.
    4. 

  4. Join the limited cgroup, then a cgroup namespace. /proc/self/cgroup becomes 0::/ (this cgroup looks like the root), but the visible memory.max is still the outer container's 1.5 GB: a cgroup namespace changes how paths are shown, and the mounted cgroup file system is the old view until step 4 remounts it.
    5. 

  5. A mount namespace, an overlay root, pivot_root. The busybox tree is now / and the old root is unmounted: one visible process, seven root entries, eight mounts. The host's tree is gone from this mount namespace, not merely hidden. The new cgroup2 mount shows /ctr as its root: memory.max 64 MiB, pids.max 16.
    6. 

  6. A network namespace. eth0 is gone; lo, tunl0 and ip6tnl0 are new devices of the new namespace (all down), two tunnel devices this kernel creates in every namespace (setup_net, about 2.4 ms, section 1). A real runtime would now add one end of a virtual Ethernet pair.
    7. 

  7. An IPC namespace. The System V shared memory segment created at step 0 is no longer visible: zero segments.
    8. 

  8. Drop capabilities to Docker's default 14. CapEff drops from a82425fb (Docker's 14 plus CAP_SYS_ADMIN) to a80425fb, Docker's 14: bit 21 gone. Root can still chown, but sethostname and mount now fail with EPERM.
    9. 

  9. no_new_privs and a seccomp filter. Seccomp becomes 2 (filter mode) and NoNewPrivs 1. mkdir and unshare fail before reaching the kernel's code for them; getpid is unaffected (seccomp_run_filters).
    10. 

  10. execve the workload. busybox sh replaces the program and keeps every restriction. The cgroup limits bite: a fork past 16 tasks fails, and a 100 MB allocation is OOM-killed inside the 64 MiB group while the shell survives. The deleted /etc/passwd becomes a whiteout in the upper layer (the workload's output and the upper layer are under the card).
    11.
