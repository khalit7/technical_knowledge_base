In one screen

A container is not a thing the kernel knows about. There is no "container" object in Linux. A container is ordinary processes on the host's one kernel, started with four kinds of restriction: namespaces (what they can see), cgroups (how much they can use), capabilities, seccomp and LSMs (what they may do) and a layered root file system (what files they have). Everything a container runtime such as Docker does is a sequence of ordinary system calls you can make yourself, and the {{Build a container|#t-build}} tab does exactly that, one call at a time, printing what the process sees after each.

The root page, {{Topic: operating-systems|n:3f05c17b0d0d81c5a97ce991644af140}} section 8, read these four restrictions from inside one container; its {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} reproduces the OOM kill, the /dev/shm limit, CPU throttling and the pids limit. This page goes one level down: how each restriction works in the kernel (Linux v5.10, the kernel these runs used, file and line), what it costs, where it bites a training or serving job, the command that shows it, and the fix. Each mechanism follows one pattern: problem, how it works, what it costs here, when it bites in ML, the command that shows it, the fix.

Eight things to remember
  1. A container is processes plus restrictions. The same kernel runs it; a kernel bug reachable through an allowed system call is a way out. Code you do not trust needs a sandbox with its own kernel or a kernel in user space (section 10).
  2. Namespaces are cheap, except the network one. Creating a UTS, PID, cgroup or time namespace took 3 to 5 microseconds here; a network namespace took 2.4 ms (section 1).
  3. When PID 1 of a container dies, the kernel SIGKILLs everything else in it. A shell or --init between docker stop and Python lost the checkpoint in all three such setups here (0.24 to 0.27 s, exit 143); exec, a forwarding trap, or Python as PID 1 saved it in 1.3 to 1.9 s (section 2).
  4. memory.max kills; memory.high stalls. The same 300 MiB allocation was OOM-killed at 190 MiB under memory.max=200M, but under memory.high=200M with no swap it hung for the full 60 s without an error, and with swap it finished in 0.3 s (section 5).
  5. Kubernetes kills the whole container on an OOM. On cgroup v2 the kubelet sets memory.oom.group=1, so a DataLoader worker going over the limit takes the main process with it; under Docker's default only the worker dies (section 5).
  6. Root inside is not all of root. Docker's 14 default capabilities cannot raise priority, pin 64 MiB of memory or mount anything; Docker's default seccomp profile changed the answer for 7 of the 12 calls probed, five of which worked without it (6, 7).
  7. Some limits are per user, not per container. io_uring rings and BPF programs on Linux 5.10 are charged to the UID: two containers running as the same UID shared one 64 KiB budget, and root's was already spent (section 7).
  8. Kubernetes requests become cgroup files by formulas you can check: requests.cpu becomes cpu.weight (1 CPU gives 39 under runc 1.1, 100 under newer runc), limits.cpu becomes cpu.max, limits.memory becomes memory.max, the QoS class becomes oom_score_adj ({{Pod to cgroup|#t-pod}}, section 12).

How this page was measured: Docker Desktop's Linux VM on an Apple M1 laptop (Linux 5.10.104-linuxkit, arm64, 5 CPUs, about 10 GB, cgroup v2 with the cgroupfs driver), Docker 20.10.17 with runc v1.1.2, October 2026, image kb-os-cont:1 (the root's lab image plus busybox, tini 0.19 and dumb-init 1.2.5). No container was privileged. Two experiments needed one extra right each, stated where used: --cap-add SYS_ADMIN to create namespaces and to remount the container's own cgroup subtree writable; --security-opt seccomp=unconfined where Docker's default filter blocks the very call being taught (pivot_root, or unshare(CLONE_NEWUSER) as a non-root user). This kernel has no pressure stall information (CONFIG_PSI is not set) and no AppArmor or SELinux, so those are taught from the kernel source and documentation and tagged not run here, as are gVisor, Firecracker, GPU containers and Kubernetes itself.
