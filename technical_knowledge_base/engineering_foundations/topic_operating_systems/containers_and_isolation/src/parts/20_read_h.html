7. seccomp-bpf: a filter on every system call

beyond OSTEP source {{seccomp(2)|https://man7.org/linux/man-pages/man2/seccomp.2.html}}, {{kernel seccomp filter docs|https://docs.kernel.org/userspace-api/seccomp_filter.html}}; kernel/seccomp.c v5.10

The problem. Linux has about 400 system calls (Docker's default profile names 396 across its rules). A training job uses a few dozen. Every other call is kernel code an attacker can reach from inside the container; capabilities guard only some of them.

How it works. A process installs a small program in classic BPF (a tiny register machine with loads, compares, jumps and returns; no loops) with prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog) or seccomp(2). On every system call entry, before the call runs, the kernel runs the program on a struct seccomp_data: the call number, the architecture, the instruction pointer and the six argument values. The program returns an action: ALLOW, ERRNO (fail the call with a chosen error), KILL_PROCESS or KILL_THREAD, TRAP (deliver SIGSYS), LOG, TRACE, or USER_NOTIF (Linux 5.0: let a supervising process decide). Filters stack and are inherited across fork and execve; none can be removed; with several, all run and the most restrictive answer wins ({{seccomp_run_filters, seccomp.c lines 311 to 327|https://github.com/torvalds/linux/blob/v5.10/kernel/seccomp.c#L311}}). Installing one requires CAP_SYS_ADMIN or no_new_privs, so a filtered process can never execve a setuid program that would run with the filter but more privilege.

The filter the hand-built container installs at its step 8, all nine instructions:

/* arch first: a call number means different calls on different architectures */
BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, arch)),
BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, AUDIT_ARCH_AARCH64, 1, 0),
BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL_PROCESS),
BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, nr)),
BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_mkdirat, 0, 1),
BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | EPERM),
BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_unshare, 0, 1),
BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | EPERM),
BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),

From src/exp/minictr.c. After it, mkdir and unshare failed with "Operation not permitted" and getpid worked ({{Build a container|#t-build}}, step 8). A filter sees argument values only: it cannot follow a pointer to read a path, because the memory could change between the check and the use. Path rules are the job of LSMs (section 8).

Docker's default profile

Docker's profile is an allowlist with default action ERRNO (EPERM): 340 calls allowed outright, more allowed only with a capability (mount with CAP_SYS_ADMIN) or with certain arguments (clone without namespace flags). One trick: clone3 passes its flags inside a structure behind a pointer, which a filter cannot read, so the profile answers it with ENOSYS ("not implemented", error 38) and glibc falls back to the old clone, whose flags are visible ({{default.json at v20.10.17|https://github.com/moby/moby/blob/v20.10.17/profiles/seccomp/default.json}}). What it costs here measured
getppid() 3,000,000 times, best of 5, nanoseconds per call (median of 3 container runs): . Docker's filter adds about ns to every system call; eight more trivial filters added ns. On 5.10 every allowed call runs the whole program; Linux 5.11 added a per-architecture bitmap of calls a filter always allows, which skips the program for them ({{seccomp_cache_check_allow, seccomp.c line 167, v5.11|https://github.com/torvalds/linux/blob/v5.11/kernel/seccomp.c#L167}}). Against the root's 316 ns read it is about a tenth: noticeable only for code that makes millions of tiny calls (the root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} case "High system time: millions of tiny reads").

io_uring: blocked in Docker 25, and charged per user

io_uring (the {{concurrency page|n:3f05c17b0d0d8112ad1af99308fa913f}} teaches it) moves I/O submission into rings of memory shared with the kernel: one io_uring_enter call, or none with polling, submits many reads, writes, opens and socket operations, executed by the kernel. A seccomp filter sees the io_uring_enter, not the operations inside it. Docker 25.0 removed the three io_uring calls from its default profile ({{moby PR #46762|https://github.com/moby/moby/pull/46762}}, merged 2 November 2023), citing that "Google ChromeOS and Android have turned it off, plus all Google production servers turn it off" and that io_uring vulnerabilities have been used to break out of containers. Passing Docker 25's default.json to this 20.10 daemon reproduced it: io_uring_setup became "Operation not permitted" (table above, third column).

The 20.10 failure is a different limit. On Linux 5.10 every ring's pages are charged against RLIMIT_MEMLOCK, but counted in user->locked_vm, a counter that belongs to the user ID, not to the process, the container or the cgroup ({{__io_account_mem, fs/io_uring.c lines 7863 to 7880|https://github.com/torvalds/linux/blob/v5.10/fs/io_uring.c#L7863}}; skipped for processes with CAP_IPC_LOCK, {{line 9273|https://github.com/torvalds/linux/blob/v5.10/fs/io_uring.c#L9273}}). Containers without a user namespace share the host's UIDs, so every container running as UID 2000 draws on one budget:

measured src/exp/uring.sh: 1-entry rings (2 pages, 8 KiB each) created until one fails; 64 KiB allows 8. Container B, with its own namespaces and cgroup, got none while A held its rings, and 8 after A exited. Root got none even alone: other root-owned things on this VM had already used UID 0's 64 KiB. On 5.10 BPF programs and maps are charged to the same counter (__bpf_prog_charge, {{kernel/bpf/syscall.c line 1631|https://github.com/torvalds/linux/blob/v5.10/kernel/bpf/syscall.c#L1631}}), and runc attaches a BPF program to every cgroup v2 container to enforce its device rules, so running containers alone may account for it (likely, not traced). Later kernels moved both to the memory cgroup: kernel/bpf/syscall.c no longer touches locked_vm at v5.11, and at v5.12 io_uring allocates its rings with __GFP_ACCOUNT ({{fs/io_uring.c line 8061, v5.12|https://github.com/torvalds/linux/blob/v5.12/fs/io_uring.c#L8061}}) instead of charging ring_pages to the user.

When it bites in ML
  • Fast data readers built on io_uring fail with EPERM on Docker 25 and later and in Kubernetes runtimes with similar profiles; a library that does not fall back to ordinary reads breaks. On older kernels the same reader can fail with ENOMEM because some other container running as the same UID holds rings. Fix: a custom profile that allows io_uring, a different UID per job (or user namespaces), or --ulimit memlock high enough.
  • perf, bpftrace and some profilers need perf_event_open and bpf, blocked by default. Profile on the host, or start a debugging container with a custom profile and the needed capabilities, never --privileged on a shared node.
  • Kubernetes: securityContext.seccompProfile.type: RuntimeDefault applies the container runtime's profile; the Pod Security Standards' "restricted" level requires a profile ({{Pod Security Standards|https://kubernetes.io/docs/concepts/security/pod-security-standards/}}).
Commands that show it
grep Seccomp /proc/<pid>/status (0 none, 1 strict, 2 filter; Seccomp_filters counts them), docker run --security-opt seccomp=profile.json, strace -f (a blocked call shows as -1 EPERM with no other cause).
A seccomp filter must block opening /etc/shadow but allow every other openat. Can it?
The path is in the process's memory; the filter sees only the address in args[1]. Even if it could read the string, another thread could change it after the check (a time-of-check to time-of-use race). USER_NOTIF and TRACE hand the decision to another process, which has the same race to handle. Path policies belong to LSMs such as AppArmor, SELinux or Landlock, which check the resolved file inside the kernel.

8. Linux Security Modules: AppArmor, SELinux, Landlock not run here

ch. 55 Access Control source {{LSM docs|https://docs.kernel.org/admin-guide/LSM/index.html}}

Capabilities and seccomp decide which kinds of operation a process may attempt. Linux Security Modules add a mandatory policy on objects: hooks throughout the kernel ask the active modules before a file is opened, a socket bound or a program executed, after the kernel has resolved the actual inode, so path tricks do not help. "Mandatory" means the file's owner cannot loosen it.

ModulePolicy is aboutWhere you meet it
AppArmorpaths: per-program profiles listing which files, capabilities and network access are allowedUbuntu and Debian; Docker applies its docker-default profile when AppArmor is on ({{Docker docs|https://docs.docker.com/engine/security/apparmor/}}), which denies writes to most of /proc and /sys and all mounts
SELinuxlabels: every process and file carries a type, and a policy says which types may act on whichRHEL, Fedora; containers get the container_t type and a per-container category pair so two containers cannot touch each other's files ({{Red Hat docs|https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html/using_selinux/index}})
Landlockunprivileged self-sandboxing: a process restricts its own file access with three system calls (Linux 5.13)sandboxes for tools and agents; Docker 25's profile allows the three landlock_* calls (the profile diff in src/inputs/)

This VM's kernel has neither AppArmor nor SELinux (src/raw/env.txt), so the default Docker containers measured on this page had namespaces, cgroups, capabilities and seccomp, but no LSM: one layer fewer than on a typical Ubuntu or RHEL node.

When it bites in ML
A volume mounted from the host that the job cannot read on a RHEL node, although the Unix permissions look right, is usually SELinux labelling: mount it with the :z or :Z option so the runtime relabels it. ausearch -m avc (SELinux) or dmesg | grep apparmor on the host shows the denial.
