3. Mount namespaces, images and overlayfs: what files it has

ch. 39 to 40 (files, file system implementation) source {{mount_namespaces(7)|https://man7.org/linux/man-pages/man7/mount_namespaces.7.html}}, {{pivot_root(2)|https://man7.org/linux/man-pages/man2/pivot_root.2.html}}, {{overlayfs docs|https://docs.kernel.org/filesystems/overlayfs.html}}, {{OCI image spec|https://github.com/opencontainers/image-spec/blob/main/spec.md}}

The problem. A training image brings its own Python, PyTorch and CUDA runtime, which must not clash with the host's or another job's. Copying a whole 2 GB file tree for every container would be slow and waste disk; ten containers of one image should share one copy.

The mount namespace and the new root

A new mount namespace starts as a copy of the caller's mount table; after that, mounts and unmounts on either side are private, unless mount propagation says otherwise. Each mount is shared (events propagate both ways within its peer group), slave (receives, does not send) or private. systemd makes / shared on most hosts, so a runtime first marks its copy private, recursively, or its mounts would appear on the host: that is the first mount call at step 4 of the {{Build a container|#t-build}} tab (mount(NULL, "/", NULL, MS_REC|MS_PRIVATE, NULL)).

Then the process needs a different /. chroot(dir) only changes where path lookups start for this process; the old root is still mounted and reachable, and a process with CAP_SYS_CHROOT can break out ("This call does not change the current working directory", and it "is not intended to be used for any kind of security purpose", {{chroot(2)|https://man7.org/linux/man-pages/man2/chroot.2.html}}). pivot_root(new_root, put_old) instead swaps the root mount of the whole mount namespace and moves the old one under put_old, which the runtime then unmounts, so the host's tree is no longer in the namespace at all. runc uses pivot_root unless told not to (--no-pivot, for a root on a ramdisk, which cannot be pivoted; it then uses a move-mount plus chroot). Docker 20.10's default seccomp profile does not list pivot_root at all (measured: the hand-built container needed seccomp=unconfined for it): runc calls it before it installs the container's filter, and the container itself never needs to.

overlayfs: layers, copy-up and whiteouts

The new root is an overlay mount: several read-only lower directories (the image layers), one writable upper directory (this container's changes) and a workdir for atomic operations, merged into one tree. A lookup returns the topmost layer's version of a name. Writing to a file that exists only in a lower layer triggers a copy-up: overlayfs copies the whole file into the upper layer first ({{ovl_copy_up_data, fs/overlayfs/copy_up.c line 132|https://github.com/torvalds/linux/blob/v5.10/fs/overlayfs/copy_up.c#L132}}), then lets the write proceed. Deleting a lower-layer file creates a whiteout in the upper layer, a character device with device number 0/0 that hides the name. An overlay cannot use another overlay as its upper layer (the first attempt of this page's experiment failed with EINVAL until the layers moved to a tmpfs).

Images: what docker pull downloads


An OCI image is a manifest (a JSON list of content hashes), a config (environment, entry point, the ordered list of layer hashes) and the layers, each a tar archive of the files one build step added, changed or deleted (deletions stored as whiteout files). Identical layers are stored and downloaded once and shared by every image that uses them. Each RUN, COPY or ADD line of a Dockerfile makes a layer; ENV and WORKDIR only change the config (the 0B rows below).




The image has 6 layers; the root mount had 7 lower directories because Docker adds one small "init" layer per container holding /etc/hosts, /etc/resolv.conf and /etc/hostname. docker diff reads the upper layer: A added, C changed, D deleted (the whiteout).


When it bites in ML
    

  • Checkpoints and datasets written inside the container land in the upper layer on the node's disk: they vanish with the container, count against the node's ephemeral storage (Kubernetes evicts pods that exceed ephemeral-storage limits), and a later edit of a big file copies it up whole. Write them to a volume (a bind mount or a persistent volume is not part of the overlay); the {{storage page|n:3f05c17b0d0d8141be7acc1313570cbf}} covers making them durable.
    • 

  • Model weights baked into an image make every node pull them before the job starts, and a change to one byte rebuilds and re-uploads the whole layer. Keep weights in object storage or a volume and the image for code and libraries; put the layers that change most (your code) last in the Dockerfile so the big ones (CUDA, PyTorch) stay cached.
    • 

  • pip install at container start writes thousands of files to the upper layer on every start. Bake dependencies into the image instead.
    •
