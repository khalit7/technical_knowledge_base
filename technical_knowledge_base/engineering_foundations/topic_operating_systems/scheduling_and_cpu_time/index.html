In one screen

A CPU core runs one thread at a time. The scheduler is the kernel code that decides which runnable thread gets each core next and for how long; a context switch is the act of swapping one thread out and another in. On Linux, ordinary threads share CPUs fairly by weight (CFS until kernel 6.5, EEVDF from 6.6), a few classes jump the queue (real-time, deadline), and containers add a second layer on top: a weight that decides how contended CPUs are split between groups, and a quota that stops a group cold when it has used its share of each 100 ms.

The root page, Topic: operating-systems section 3, gave the intuition, its OS simulators tab runs OSTEP's policies, and its Debug lab measured the two classic training-job failures (a CPU limit and too many threads). This page goes one level down: what the kernel actually does, line by line where it helps (Linux v5.10, the kernel these runs used, and v6.12 for EEVDF), what each step costs on a real kernel, and how it shows up in ML work. Each mechanism follows the same pattern: problem, how it works, what it costs here, when it bites in ML, the command that shows it, the fix.

Five things to remember
  1. A CPU limit is a quota, not fewer CPUs. Threads beyond the quota do not wait politely: the whole container runs flat out and then stops until the next period (section 9).
  2. Nothing inside a container tells PyTorch about the quota. os.cpu_count() and torch.get_num_threads() ignore cpu.max; only CPU affinity (cpuset) is seen. Set thread counts yourself (section 11).
  3. Fair means proportional to weight. Nice levels are weights spaced by 1.25 times; a cgroup's cpu.weight is the same idea one level up (section 4).
  4. A switch is cheap; waking across CPUs and losing caches are not. A switch between two threads on one CPU took about 1.5 us here; in this VM, waking a thread on another, idle CPU took 29 times longer (section 2).
  5. Load average is not CPU use. On Linux it also counts tasks blocked in uninterruptible waits, such as a stuck network file system (section 10).

1. What gets scheduled: threads, states, run queues

ch. 4 The Process; ch. 6 Limited Direct Execution; ch. 26 Concurrency

The unit is the thread. Linux schedules tasks, and every thread is its own task with its own struct task_struct and its own thread id (TID); a process is just a group of tasks that share one address space and one process id (the thread-group id). Inside each task_struct sits a struct sched_entity (the bookkeeping the fair scheduler keeps: weight, virtual runtime, total CPU time), the scheduling policy, the priority and the set of CPUs the task may use (include/linux/sched.h, v5.10). So a PyTorch process with 5 compute threads competes as 5 tasks, not as 1.

States. At any instant a task is in one of a few states, the letter ps prints in its STAT column: R running or runnable (ready, waiting only for a CPU), S sleeping until an event (data on a pipe, a lock, a timer), D sleeping uninterruptibly (usually inside the kernel waiting for I/O; signals cannot wake it), T stopped, Z zombie (exited, not yet reaped). Only R tasks need the scheduler; the art is choosing among them.

Run queues. Every CPU has its own run queue, struct rq, holding the runnable tasks that will run on that CPU, split by scheduling class: a deadline queue, a real-time queue and a fair queue (cfs_rq) (kernel/sched/sched.h, v5.10). The classes are tried in a fixed order, highest first: stop (a per-CPU kernel helper), deadline, real-time, fair, idle (the linker script lists them lowest first, include/asm-generic/vmlinux.lds.h line 128). A runnable real-time task therefore always runs before any ordinary thread on that CPU; almost everything you run is in the fair class.

1. it blocksThe running thread waits (a read, a lock, sleep): it leaves the run queue, the CPU picks another. A voluntary switch.
2. the timer tickEvery 1 ms here (CONFIG_HZ=1000) an interrupt enters the kernel, which charges the running thread and may decide it has had enough. An involuntary switch.
3. a wake-upA sleeping thread becomes runnable; if it deserves the CPU more than the current one, the kernel preempts at once (wake-up preemption).
4. the switch pointThe decision only sets a "need to reschedule" flag; the switch happens at the next safe point. With CONFIG_PREEMPT=y (this VM) that includes most kernel code, not only the return to user space.

This is OSTEP's limited direct execution in practice: user code runs directly on the CPU at full speed, and the kernel takes control back only through system calls, interrupts (the timer above all) and faults. Without the timer a thread spinning in a loop would keep the CPU forever.

2. The context switch: what is saved and what it costs


ch. 6 Limited Direct Execution (6.3 Saving and Restoring Context); ch. 10 Multiprocessor Scheduling (cache affinity)


The problem. To run another thread, the CPU's state for the current one must be put somewhere and the other's brought back, so that each thread resumes as if it had never stopped. How it works. When a thread enters the kernel (system call, interrupt, fault), the hardware and the entry code have already saved its user registers on that thread's own kernel stack. The switch itself, in context_switch() (kernel/sched/core.c line 3728, v5.10), is then three steps:


1 pick the next task2 switch the address space3 switch registers and stack


    

  • Pick: __schedule() asks each class in order (section 1) for its best task.
    • 

  • Address space: switch_mm_irqs_off() (line 3765) points the MMU at the next process's page tables. Skipped between threads of one process (same address space). On arm64 each address space carries an ASID tag in the TLB, so the TLB is not flushed (the sibling Virtual memory page, section 3).
    • 

  • Registers and stack: switch_to() (line 3779) calls __switch_to(), which hands over the floating-point and SIMD registers lazily (arch/arm64/kernel/process.c line 552), then cpu_switch_to, about twenty instructions of assembly that store the callee-saved registers x19 to x28, the frame pointer, the stack pointer and the return address of the old task and load the new task's (arch/arm64/kernel/entry.S line 892). Its final ret returns into the other task's kernel stack, which later returns to that task's user code.
    •

The Debug lab's "Too many threads" case ran 5 PyTorch threads on a 1-CPU quota. Which counter should explode?




A voluntary switch happens when the thread blocks; an involuntary one when the kernel takes the CPU away (tick or wake-up preemption, or throttling). Five busy threads fighting for one CPU's worth of quota are preempted constantly: the root's Debug lab case "Too many threads for the CPUs you have" recorded 3,571 involuntary switches with 5 threads against 16 with one, for the same arithmetic.


When it bites in ML. Rarely through the switch itself: a training step is milliseconds, a switch microseconds. It bites through numbers (hundreds of threads from per-process thread pools on a few cores, section 11), through hand-offs (a DataLoader batch crosses processes with at least two wake-ups; fine per batch, ruinous per sample), and through busy waiting: libraries that spin instead of sleeping (GNU OpenMP's idle threads spin before they sleep unless OMP_WAIT_POLICY=passive, libgomp docs) trade a whole CPU for microseconds of latency, which is right on a dedicated node and wrong under a CPU quota.

3. Policies, from OSTEP to proportional share


ch. 7 Scheduling: Introduction; ch. 8 Multi-level Feedback Queue; ch. 9 Proportional Share


Two yardsticks. Turnaround time (finish minus arrival) measures how long batch work takes; response time (first run minus arrival) measures how long an interactive thread waits before anything happens. OSTEP builds policies one flaw at a time: FIFO (a long job delays everyone behind it), shortest-job-first and shortest-time-to-completion-first (best turnaround, but they need to know job lengths), round robin (best response, worst turnaround), and the multi-level feedback queue, which learns lengths from behaviour. The root's OS simulators tab runs all of them on the same jobs, reproducing OSTEP's figures; this page does not repeat them.


Proportional share asks a different question: not "who finishes first" but "does each job get its share". OSTEP chapter 9 gives three answers, and the third is Linux's:




Lottery (1994)Each job holds tickets; every slice the scheduler draws a random ticket. Shares are right on average, noisy over short windows (Waldspurger and Weihl, OSDI 1994).


StrideDeterministic: each job has a stride = a big number / its tickets and a pass counter; run the job with the smallest pass, then add its stride to its pass. Exact shares every round.


CFS (2007)Stride scheduling in units of time: the pass is virtual runtime, which grows by the CPU time used divided by the weight. Run the smallest. Section 4.




OSTEP's stride example: A, B and C hold 100, 50 and 250 tickets, so with a big number of 10,000 their strides are . Starting from zero (ties to A, then B), the first eight picks are : C runs five times in eight, A twice, B once, and over any long window the shares are exactly 250 : 100 : 50. Replace "tickets" by "weight" and "stride" by "1024 / weight per unit of CPU time" and you have the core of CFS.


What a real scheduler must add
Jobs that sleep (should a thread that slept for an hour get an hour of catch-up? CFS: no, at most half a latency period, section 4), new jobs (where to start their counter), many CPUs (one queue or many, section 7), and groups of jobs (containers, section 9). Most of the kernel code is about these, not about the pick.






4. CFS in depth (Linux 2.6.23 to 6.5; the kernel measured here)


ch. 9.7 The Linux Completely Fair Scheduler; CFS design doc


The problem. Give every runnable thread a share of the CPU proportional to its weight, keep interactive threads responsive, and do it in a few hundred nanoseconds per decision on queues of any length. The idea (from the design doc): CFS "basically models an ideal, precise multi-tasking CPU", one that would run all n threads at once, each at 1/n speed. Real CPUs run one at a time, so CFS tracks how far each thread is behind that ideal and runs the one furthest behind.


Weights: what nice means


A thread's nice value (-20 to 19, default 0) indexes a fixed table of weights, sched_prio_to_weight (kernel/sched/core.c line 8457, v5.10): nice 0 is 1024, each step multiplies by about 1.25 (nice -1 is 1277, nice 1 is 820, nice 5 is 335, nice 19 is 15). The comment above it explains the choice: one nice level is "a gentle 10% change" in CPU share against a competitor. Two busy threads on one CPU get wa / (wa + wb) each: nice 0 against nice 5 is 1024 / 1359 = ; the root measured 75.38%, and this page  (below, with the two threads in different sessions).


Three busy threads share one CPU: two at nice 0 and one at nice 5. What does each nice-0 thread get?




1024 / (1024 + 1024 + 335) = 42.97% each, and 14.06% for the nice-5 thread. Shares depend on who else is runnable: nice 5 means "a third of a nice-0 thread's weight", not "75%".


Virtual runtime: the one number CFS sorts by


Every time the running thread is charged (at each tick, and whenever it stops), update_curr() adds the CPU time it used, scaled by its weight, to its virtual runtime (fair.c line 842, using calc_delta_fair() at line 671):


vruntime += Δexec × 1024 / weight
Δexec

from the nice table; 1024 at nice 0, so a nice-0 thread's vruntime is its CPU time


A nice-5 thread's vruntime grows 3.06 times faster than its CPU time. Runnable threads sit in a red-black tree ordered by vruntime (__enqueue_entity, line 575); the next thread is the leftmost, the one with the least virtual runtime (pick_next_entity, line 4435). Running pushes a thread to the right, so heavier threads, whose vruntime grows slowly, are picked more often: exactly stride scheduling. The queue also keeps min_vruntime, a floor that only moves forward (line 540), used to place threads that arrive or wake.

What it shows. The two busy loops' vruntimes advance together (never more than  ms apart, under one slice), while their CPU time diverges by  times, the weight ratio 1024 / 335 = 3.057. That is the whole invariant of CFS: equal virtual time, unequal real time. The sleeper's vruntime trails the others by a median  ms: each time it wakes it is placed at most half a latency period (9 ms here) behind min_vruntime, so it always looks "behind" and runs at once, but cannot bank more than 9 ms of credit however long it slept.


How long a thread runs: period, slice, granularity


CFS does not use a fixed time slice. It aims to run every runnable thread once per scheduling period and gives each a slice proportional to its weight (__sched_period and sched_slice, lines 687 and 701):

So on this VM: . Two nice-0 threads get 9 ms each; eight get 2.25 ms; beyond eight the period stretches instead of slices shrinking (sixteen threads: a 36 ms period), which is what keeps oversubscribed nodes from switching themselves to death and also what makes their latency grow.




Preemption at the tick (check_preempt_tick, line 4355): the running thread is switched out when it has run longer than its slice, or, once it has run at least min_granularity, when its vruntime is ahead of the leftmost thread's by more than a slice. Preemption at wake-up (place_entity, line 4108; check_preempt_wakeup, line 6916): the woken thread is placed at max(its own vruntime, min_vruntime - latency / 2), and it preempts the running thread at once if the running thread's vruntime is ahead of it by more than the wake-up granularity (1 ms × factor = 3 ms here, scaled by the woken thread's weight). A new thread (after fork) starts one virtual slice after min_vruntime (the START_DEBIT feature), so forking cannot be used to jump the queue.


// kernel/sched/fair.c, v5.10, lines 6869-6880: should the woken thread se preempt curr?
static int wakeup_preempt_entity(struct sched_entity *curr, struct sched_entity *se)
{
	s64 gran, vdiff = curr->vruntime - se->vruntime;
	if (vdiff <= 0)
		return -1;
	gran = wakeup_gran(se);
	if (vdiff > gran)
		return 1;
	return 0;
}

5. EEVDF: the same fairness, with deadlines (Linux 6.6 and later) not run here


ch. 9 extended; EEVDF doc; LWN, 2023-03-09; LWN, Completing the EEVDF scheduler, 2024


The problem with CFS. CFS's fairness is clean, but its latency comes from heuristics bolted on: the sleeper credit, the wake-up granularity, the "buddies" that bias the pick, each with a tunable. A thread had no way to say "I only need short bursts, but I need them soon" except raising its weight, which also gives it more CPU. The idea, from Stoica and Abdel-Wahab's 1995 paper (Earliest Eligible Virtual Deadline First), merged into Linux 6.6 to replace CFS's pick: keep virtual runtime, and add a request size per thread (its slice) and a virtual deadline.




V, the virtual clockThe weighted average of the queued threads' vruntimes (avg_vruntime, fair.c line 653, v6.12): where an ideal fair CPU would have everyone now.


lagw × (V - v): service a thread is owed (positive) or has had too much of (negative). The lags sum to zero.


eligiblelag ≥ 0, that is v ≤ V (vruntime_eligible, line 726): only threads that are owed service may run.


virtual deadlined = v + slice × 1024 / w, renewed each time a slice is used up (update_deadline, line 1007).


the pickAmong eligible threads, the earliest virtual deadline (pick_eevdf, line 907). A short slice means an early deadline, so latency is requested, not earned.


run to parityOnce picked, a thread keeps the CPU until its slice is used up or it becomes ineligible (RUN_TO_PARITY, features.h line 20): no CFS-style "wake-up granularity" race.




Sleeping and waking. CFS forgot a sleeper's history (max(own, min_vruntime - 9 ms)). EEVDF remembers its lag (PLACE_LAG, place_entity, line 5266): a thread that slept while owed service comes back owed it, and one that slept after running ahead comes back behind. A thread that blocks while ineligible is not removed at all until it becomes eligible (DELAY_DEQUEUE, features.h line 49), so sleeping cannot be used to shed negative lag. The slice is sysctl_sched_base_slice = 0.75 ms (line 76) times the same CPU factor as CFS's tunables (update_sysctl, line 212): 2.25 ms on this VM's 5 CPUs, 3 ms on machines with 8 or more. Since 6.12 a thread can ask for its own slice with sched_setattr() and a sched_runtime while staying an ordinary thread, clamped to 0.1 to 100 ms (kernel/sched/syscalls.c line 306, v6.12); a woken thread with a shorter slice may then cut the current one's slice short (PREEMPT_SHORT). CFS's sched_latency_ns, sched_min_granularity_ns and sched_wakeup_granularity_ns are gone.


One CPU, three threads, two schedulers model


The same input under Linux 5.10's CFS rules and Linux 6.12's EEVDF rules, as this page's simulator implements them (each rule cites its source line; the Fair-share stepper tab lists what it leaves out): a trainer thread and a preproc thread are busy loops at nice 0; a loader thread wakes every 4 ms, needs 0.4 ms of CPU, and sleeps again, like a thread that receives a batch and queues the next prefetch. All on one CPU with a 1 ms tick and this VM's tunables (factor 3). Watch the loader's wake-up delay.


















What it shows. Under CFS the loader is placed 9 ms behind min_vruntime at every wake-up, is always more than the 3 ms wake-up granularity behind the running thread, and preempts at once: zero wait. Under EEVDF it wakes with the lag it left with (about zero), is eligible with a deadline 2.25 ms ahead, but the running busy loop keeps its slice (run to parity): the loader waits up to the end of that slice. Give the loader a 0.1 ms slice and its deadline comes first and PREEMPT_SHORT lets it in: the wait nearly vanishes, with no change in its CPU share. The busy loops get the same total CPU under all three; EEVDF switches more often because its slices are shorter than CFS's 6 ms.


How far to trust this
A one-CPU model of the pick, placement and preemption rules, checked line by line against the source but not against a 6.6+ kernel (this VM runs 5.10). On a real machine with an idle CPU the loader would simply be woken there (section 7), so the difference matters when every CPU is busy, which is exactly an oversubscribed training node. The custom-slice interface (6.12) was added as "a new feature intended to help latency-sensitive tasks" (LWN, Completing the EEVDF scheduler).


On a 6.12 kernel, a serving process's request thread wakes, runs 200 us and sleeps, next to batch jobs on every core. Which change cuts its wake-up delay without giving it more CPU?




A custom slice moves its deadline earlier, which EEVDF uses to pick, and lets it preempt a thread with a longer slice; its share is unchanged because weight is unchanged. nice -10 also helps, by taking about 9 times the weight, which is more CPU, not lower latency. SCHED_BATCH does the opposite: batch threads never preempt on wake-up (section 6 measures 2 ms of delay).

Real-time throttling. A SCHED_FIFO thread in an infinite loop would own its CPU forever, so the kernel caps all real-time threads together at sched_rt_runtime_us per sched_rt_period_us: 950,000 us of every 1,000,000 here, leaving 50 ms a second for everything else. In containers it is simply refused: this kernel is built with RT group scheduling, which gives each cgroup its own real-time budget, zero by default, and the kernel rejects real-time policies in a group with no budget (core.c line 5370), even with CAP_SYS_NICE added:




SCHED_DEADLINE is the opposite design: instead of a priority, the task declares how much CPU it needs (runtime) by when (deadline) how often (period), the kernel admits it only if the sum of all declared bandwidths fits, and then runs the task with the earliest deadline first, stopping it the moment it overruns its runtime until its next period (the constant bandwidth server: update_curr_dl, deadline.c line 1239). Admission is checked over a set of CPUs, so the task must be allowed to run on all of them (core.c line 5387). Both rules are visible from an unprivileged container (with CAP_SYS_NICE):






The busy loop got exactly its 2 ms per 10 ms, 20% of a CPU, although the container's quota allowed a whole CPU (cpu.max limits only the fair class) and the VM had idle CPUs: deadline tasks get what they reserved, no more. (The negative dl.runtime is its overrun at the moment of reading.)

7. Many CPUs: run queues, load balancing, affinity


ch. 10 Multiprocessor Scheduling (single queue against multi-queue, cache affinity, load imbalance, work stealing); sched-domains doc


The problem. One shared queue for all CPUs (OSTEP's SQMS) is simple and balanced but needs a lock every CPU fights over, and it bounces threads between CPUs, losing their caches. Linux uses one queue per CPU (OSTEP's MQMS) and pays instead with imbalance: one CPU's queue may hold three threads while another idles. Three mechanisms fix it:




at wake-upselect_task_rq_fair() (fair.c line 6697) chooses where a waking thread goes: its previous CPU if still a good idea, the waker's CPU if they share data (wake_affine, line 5854), or an idle CPU nearby (select_idle_sibling, line 6213).


periodicallyEach CPU runs load_balance() (line 9532) over a hierarchy of scheduling domains (cores sharing a cache, then a package, then NUMA nodes), pulling threads from the busiest group to itself, more often for close levels.


when idleA CPU about to go idle first tries to pull work (newidle balancing): work stealing, in OSTEP's words.


cache hotA thread that ran within sched_migration_cost_ns (500,000 ns here) is "cache hot" and not moved if anything else can be (task_hot, line 7419).




Migrations show up per thread as se.nr_migrations in /proc/PID/sched, and the CPU a thread last ran on is the PSR column of ps (the running job's threads in section 1 were spread over CPUs 2, 3 and 4). Section 2 measured why placement matters in this VM: waking a thread on an idle CPU cost  us, against about 1.5 us for a switch on the same CPU.


Affinity: telling the scheduler where a thread may run


A thread's CPU affinity is a set of CPUs it may run on (sched_setaffinity(2); taskset; os.sched_setaffinity in Python), inherited by its children. A container's --cpuset-cpus sets the same thing for every task in the cgroup (the cpuset controller). This is a different mechanism from the quota of section 9, and programs see one and not the other measured:




Under --cpus 2 everything still reports 5 CPUs and PyTorch starts 5 threads per pool; under --cpuset-cpus 0,1 affinity, nproc and PyTorch all say 2, while os.cpu_count() still says 5 (it counts the machine). Python 3.13 added os.process_cpu_count(), which follows affinity (os docs); nothing standard reads the quota. So a cpuset is the one limit a program sizes itself to automatically.

8. NUMA and pinning for GPU feeding not run here


ch. 10 (cache affinity); NUMA memory policy doc; numactl(8)


The problem. A two-socket GPU server is two computers sharing one address space: each socket (or each die on some CPUs) has its own memory controller, PCIe lanes and GPUs, and reaching the other socket's memory or devices crosses an interconnect. That is NUMA (non-uniform memory access). A process feeding GPU 3 should run on the CPUs of GPU 3's node and allocate its pinned host buffers there, or every host-to-device copy crosses sockets. 9. cgroup CPU control: cpu.weight, cpu.max and throttling


beyond OSTEP; cgroup v2: CPU interface files; CFS bandwidth control doc


A container is a cgroup, and the cgroup's cpu controller has two independent knobs. cpu.weight is relative: it only matters when CPUs are contended, and then splits them between groups the way nice splits them between threads. cpu.max is absolute: a cap that applies even on an idle machine. (A third, cpuset.cpus, is affinity: section 7.) Namespaces, delegation and pressure stall information are the sibling Containers and isolation page's subject; here we look at how the scheduler enforces the two knobs.


cpu.weight: shares of a contended CPU


cpu.weight runs from 1 to 10,000, default 100. The kernel turns it into the group's CFS weight as weight × 1024 / 100 (core.c line 8286), so a default group weighs the same as one nice-0 thread in its parent's queue. The trap is the translation from older interfaces: Docker's --cpu-shares and Kubernetes' requests.cpu speak cgroup v1 "shares" (default 1024; Kubernetes uses milli-CPUs × 1024 / 1000, pkg/kubelet/cm/helpers_linux.go line 88, v1.34.0), and the OCI runtime converts shares to a v2 weight. runc 1.1 used a linear map, 1 + (shares - 2) × 9,999 / 262,142 (libcontainer/cgroups/utils.go line 423, runc v1.1.2), which sends the default 1024 shares to weight 39, well below the default weight 100. A newer quadratic map in the opencontainers/cgroups library (from v0.0.3, utils.go line 425; runc v1.3.6 and v1.4.0 depend on versions that have it, per their go.mod) sends 1024 to 100.




Measured with this VM's Docker 20.10 (the old map): two busy containers pinned to the same CPU with --cpu-shares 1024 and 512 got weights  and split the CPU  (predicted 39 / 59 = 66.1%). Then a one-thread training step (eight 512 × 512 matmuls) in a container started with no shares flag (weight 100):

Weight protects you only in proportion to everyone else's, and only when you are actually competing for the same CPUs.


cpu.max: the quota, and why it stalls


cpu.max holds "$MAX $PERIOD": the group may use $MAX microseconds of CPU in each $PERIOD (default 100,000 us). --cpus 2 writes 200000 100000. The kernel's CFS bandwidth control enforces it like this:


    

  1. Each group has a global pool, refilled to the quota at every period by a timer (__refill_cfs_bandwidth_runtime, fair.c line 4601; do_sched_cfs_period_timer, line 4942).
    2. 

  2. Each CPU running the group's threads borrows from the pool in slices of sched_cfs_bandwidth_slice_us = 5,000 us (line 129; the same value read here) and charges the time its threads run (__account_cfs_rq_runtime, line 4653).
    3. 

  3. When a CPU's slice runs out and the pool is empty, throttle_cfs_rq() (line 4741) removes the whole group from that CPU's run queue: every thread of the container stops, runnable or not, until the next refill.
    4. 



So the quota is spent at the speed of however many threads are running. Five threads on a 1-CPU quota burn 100 ms of CPU in 20 ms of wall time and then all stop for 80 ms. Periods may be 1 ms to 1 s and quotas at least 1 ms (core.c lines 7891 to 7919). Kernels from 5.14 add cpu.max.burst, which lets unused quota carry over to absorb short bursts (sched-bwc doc) not on this kernel.

The total CPU used is the same in every run: throttling does not cost work, it costs latency, which is what a training step, a request or a GPU waiting for its next batch feels. 10. Accounting: where CPU time goes, and what load average means


ch. 6 (the timer is also the accountant); proc_stat(5); proc_loadavg(5)


Three ledgers. The kernel counts CPU time per task (utime and stime, fields 14 and 15 of /proc/PID/stat, what getrusage and time report), per cgroup (cpu.stat: usage_usec, user_usec, system_usec) and per CPU (/proc/stat). User time is your code; system time is the kernel working for you (system calls, page faults). With threads, user + system can exceed real (wall) time:




Four threads finished the same matmuls in 1.46 s instead of 2.39 s, using about the same total CPU time (user 2.52 s against 2.40 s): parallelism shortens wall time, not CPU time. "CPU 182%" means 1.82 CPUs busy on average, not 4, because only part of the program is parallel.


The per-CPU ledger (/proc/stat, in ticks of 10 ms) splits time into user, nice (user time of positively niced tasks), system, idle, iowait (idle while some I/O was outstanding: not busy, just waiting), irq, softirq and steal:




Steal is time a virtual CPU wanted to run but the hypervisor ran something else; the guest can only count it if the hypervisor provides a paravirtual steal clock (kernel/sched/cputime.c line 237). Here it is 0, which does not mean nothing was stolen: this guest is not told. On cloud VMs that report it, a rising steal column is the first thing to check when the same job gets slower on the same instance type.

Load average: not what most people think


The three numbers in uptime and /proc/loadavg are exponentially decaying averages, over about 1, 5 and 15 minutes, of the number of tasks that are runnable or in uninterruptible sleep (D state), summed over all CPUs. Every 5 seconds (LOAD_FREQ, include/linux/sched/loadavg.h line 20) the kernel computes, in fixed point with 11 fractional bits:


load = load × e + n × (1 - e),   e = exp(-5 s / 1 min) = 1884 / 2048
n

e
EXP_1 = 1884 (line 21); EXP_5 = 2014 and EXP_15 = 2037 for the other two


Counting D-state tasks is a Linux change from the classic Unix definition, which counts runnable tasks only; it makes load reflect demand for disks as well as CPUs (Brendan Gregg, Linux Load Averages: Solving the Mystery, 2017). Common mistakes


"The container has 2 CPUs, so it has 2 CPUs."
It has 200 ms of CPU time per 100 ms, spendable on all 5 (or 128) CPUs at once. Programs see the whole machine and size themselves to it; the quota then stops them in bursts (section 9).


"More DataLoader workers is always faster."
Only while there are idle CPUs to run them. On a 1-CPU quota, adding workers made every configuration slower here (CPU budget lab). Workers count against the same budget as compute threads.


"nice 19 means it gets 5% of the CPU."
Nice is a weight, so the share depends on who else is runnable: alone, a nice-19 thread gets the whole CPU; against one nice-0 thread it gets 15 / 1039 = 1.4%.


"High load average means the CPUs are saturated."
On Linux it also counts tasks in uninterruptible sleep, usually I/O; three D-state tasks using no CPU raised it here (section 10). Look at run-queue waiting and throttling instead.


"Pinning threads makes things faster."
Pinning removes the load balancer's freedom; two busy threads pinned to one core run at half speed while others idle. Pin whole processes to NUMA nodes or exclusive core sets, not individual threads, unless you have measured.


"Give the important process real-time priority."
A SCHED_FIFO thread that spins can starve kernel threads on its CPU (until the 95% real-time cap) and every ordinary thread; inside containers it is refused anyway (section 6). Use weight (nice, cpu.weight) or exclusive cores.


"cpu.stat's throttled_usec is how long my job was stopped."
It is summed over the CPUs the group was throttled on, so it can exceed wall time (3.8 s of throttling in a 1.1 s run with 5 threads, section 9). Compare nr_throttled with nr_periods instead.


"EEVDF settings are the CFS sysctls."
On 6.6+ kernels sched_latency_ns, sched_min_granularity_ns and sched_wakeup_granularity_ns no longer exist; latency is requested per thread with a slice (section 5). Tuning guides written for CFS do not apply.







Interview questions


What exactly happens in a context switch, and what does it cost?
The current thread enters the kernel (its user registers are saved on its kernel stack), the scheduler picks the next task, the address space is switched if the process differs (on arm64 with ASIDs, without a TLB flush), and the callee-saved registers and stack pointer are swapped (cpu_switch_to). Direct cost here: about 1.5 us including the sleep and wake path; the bigger costs are indirect (cold caches and TLB) and, across CPUs, the wake-up interrupt (26 to 51 us in this VM).


How does CFS decide who runs next, and how does nice change it?
Each thread accumulates virtual runtime = CPU time × 1024 / weight; CFS runs the thread with the smallest, kept in a red-black tree. Nice maps to a weight (1024 at nice 0, × 1.25 per step), so a heavier thread's vruntime grows more slowly and it is picked more often: shares are proportional to weights. Slices are the period (6 ms × factor, stretched beyond 8 threads) times the weight fraction.


Why did Linux move from CFS to EEVDF, and what changes for a latency-sensitive thread?
CFS achieved latency through heuristics (sleeper credit, wake-up granularity, buddies). EEVDF keeps vruntime but adds lag, eligibility and a virtual deadline (vruntime + slice / weight), picking the eligible thread with the earliest deadline. A thread can request a shorter slice (6.12, sched_setattr), getting earlier deadlines and lower wake-up delay without more CPU share.


A pod with a 4-CPU limit on a 64-core node trains 5 times slower than on a laptop. Diagnose.
PyTorch, OpenMP and every library size their pools from the visible CPUs (64), not from the quota. 64 threads burn the 400 ms quota in about 6 ms of each 100 ms period and the whole pod is throttled for the rest. Evidence: nr_throttled close to nr_periods, huge involuntary switch counts. Fix: set thread and worker counts from the quota, remove the limit (keep a request), or use exclusive cores.


What is the difference between cpu.weight and cpu.max?
Weight is relative and work-conserving: it only divides contended CPU time, and an idle machine gives any group everything. Max is a hard cap enforced per period even when CPUs are idle, implemented by throttling the whole group when its runtime pool is empty. Kubernetes requests become weights, limits become cpu.max.


What does load average measure on Linux?
An exponentially damped average (1, 5, 15 minutes, updated every 5 s) of runnable plus uninterruptible tasks over the whole machine. It is not utilisation, not per CPU and not per container; D-state tasks raise it without using CPU.


Why can't you run SCHED_FIFO in a Docker container, and what is SCHED_DEADLINE for?
With RT group scheduling each cgroup has its own real-time budget, zero by default, and setting a real-time policy in a group with no budget fails with EPERM. SCHED_DEADLINE reserves runtime per period with admission control and EDF ordering; the kernel throttles it at its reservation, which makes it suitable for periodic control loops.

CFS, Linux v5.10 kernel/sched/fair.c: vruntime += Δ × 1024 / weight (update_curr 842, calc_delta_fair 671); weights from sched_prio_to_weight (core.c 8457); pick the smallest vruntime, with the wake-up "next buddy" (pick_next_entity 4435); period and slice (687, 701) with latency 6 ms, min_granularity 0.75 ms and wake-up granularity 1 ms, each × factor (lines 38, 59, 82; factor 1 + log2(min(CPUs, 8)), line 159); tick preemption (check_preempt_tick 4355); wake-up placement at max(own vruntime, min_vruntime - latency / 2) (place_entity 4108) and wake-up preemption (wakeup_preempt_entity 6869, check_preempt_wakeup 6916).


EEVDF, Linux v6.12 kernel/sched/fair.c: V = weighted mean vruntime (avg_vruntime 653); eligible when v ≤ V (726); deadline = v + slice × 1024 / weight, renewed with a reschedule when reached (update_deadline 1007, update_curr 1216); pick the eligible thread with the earliest deadline, keeping the current one until its slice ends (pick_eevdf 907, RUN_TO_PARITY); lag kept across sleep and inflated on placement, half a slice for a new thread (place_entity 5266); a thread that sleeps while ineligible stays queued until picked, then leaves with its lag clipped to zero (DELAY_DEQUEUE, DELAY_ZERO; dequeue_entity 5476, pick_next_entity 5613, requeue_delayed_entity 6919); a woken thread with a shorter slice may cancel the current one's protection (PREEMPT_SHORT, 1166 and 1177); base slice 0.75 ms × factor (line 76); custom slices clamped to 0.1 to 100 ms (syscalls.c 306).


Left out: more than one CPU and load balancing (section 7), group scheduling, the "last buddy" (only with 8 or more runnable threads), the skip buddy of sched_yield, PELT load tracking, hrtick, fixed-point rounding (floats here; nanosecond differences), the cost of the switch itself, and anything outside the fair class. All threads start at t = 0 (busy loops runnable, periodic threads asleep until their first wake-up; under CFS a periodic thread starts as if it had slept for a long time).
