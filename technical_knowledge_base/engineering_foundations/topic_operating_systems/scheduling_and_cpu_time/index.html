The idea in one screen

A CPU runs one thread at a time. Linux keeps a run queue per CPU; ordinary threads share it in proportion to their weight (the one with the least weighted CPU time, its virtual runtime, runs next), and a container's CPU limit is a quota per 100 ms period that, once spent, stops every thread of the container until the next period.

Who runs next is a sort by virtual runtime; a CPU limit is a stop, not fewer CPUs

One CPU's run queue measured

The fair class opened out: three threads on one CPU placed by their se.vruntime from /proc/PID/sched, 1 s into section 4's run. The nice-5 loop keeps pace with the nice-0 loop on a third of the CPU because its virtual runtime grows 3.06 times faster; the sleeper is always behind and runs as soon as it wakes.

A container with a 1-CPU quota and 5 busy threads measured

The first 300 ms of section 9's run: five threads spend the 100 ms quota in a burst (100 / 5 = 20 ms of wall time if each has a CPU), then all of them stop (here ms at a stretch) until the period timer refills it. The CPU work done is the same as with one thread; the stall is the cost.

1. What gets scheduled: threads, states, run queues

The unit is the thread. Every thread is its own task (task_struct); a process is a group of tasks sharing one address space, so a PyTorch process with 5 compute threads competes as 5 tasks. The STAT letter of ps gives the state: R running or runnable (waiting only for a CPU), S sleeping until an event, D sleeping uninterruptibly (usually on I/O in the kernel), T stopped, Z exited, not yet reaped. Only R tasks need the scheduler.

Run queues. Each CPU has its own, split by scheduling class and tried highest first: stop (a per-CPU kernel helper), deadline, real-time, fair, idle (the hero's top row). Almost everything you run is fair. The CPU changes thread at four kinds of moment:

1. it blocksA read, a lock, sleep: it leaves the run queue. A voluntary switch.
2. the timer tickEvery 1 ms here (CONFIG_HZ=1000) an interrupt charges the running thread and may take the CPU away. An involuntary switch. Without it a spinning thread would keep the CPU forever (OSTEP's limited direct execution).
3. a wake-upA woken thread that deserves the CPU more than the current one preempts it at once.
4. the switch pointThe decision sets a "need to reschedule" flag; the switch happens at the next safe point, which with CONFIG_PREEMPT=y (this VM) includes most kernel code.

The running job, seen by the scheduler measured

The root's training job (2 DataLoader workers, --threads 2) in a 2-CPU container, every thread read from /proc/PID/task/TID/ 7 s after start; "waiting" is time runnable but not running (schedstat, sched-stats docs), throttled time included.

2. The context switch: what is saved and what it costs

To run another thread, the CPU's state for the current one must be put away and the other's brought back, so that each resumes as if it had never stopped. On Linux v5.10 (arm64) that is context_switch() (kernel/sched/core.c line 3728); step through what moves where:


A switch is a pick, a page-table pointer and about twenty instructions of register swap








Thread A blue, thread B green; the lit box is what changes at each step. source: v5.10 __schedule, switch_mm_irqs_off (core.c line 3765), switch_to (line 3779), cpu_switch_to (arch/arm64/kernel/entry.S line 892). The address-space step is skipped between threads of one process; on arm64 the ASID means no TLB flush (the sibling Virtual memory page, section 3).


What it costs here measured


Two processes on one CPU pass a byte through two pipes 200,000 times (lmbench's method, as on the root); then two threads with a futex (the wait-and-wake primitive under every lock); then hand-offs across two CPUs. Five runs each, VM load about 5.


A switch on one CPU is microseconds; waking a thread on another CPU is tens


A switch between two processes on one CPU costs  us (the root measured 1.33 us), between two threads no less ( us): with ASIDs the address space is nearly free, and the cost is the kernel's sleep-and-wake path. A cache line crosses CPUs in  ns, but waking a sleeping thread on another CPU took  us when that CPU was idle, 29 times longer than a switch ( us when a low-priority loop kept it awake): an inter-processor interrupt, and an idle virtual CPU woken by the hypervisor. That is this VM, not bare metal (why: section 5 of Virtualization and the GPU driver stack).


The indirect cost is cold caches (the new thread finds them full of someone else's data). Long slices keep it small: refilling 4 MiB at an illustrative 50 GB/s takes about 84 us, under 1% of a 9 ms slice (section 4: 9 ms each for two tasks). Our measurement in this VM was inconclusive (closed block below).


The Debug lab's "Too many threads" case ran 5 PyTorch threads on a 1-CPU quota. Which counter should explode?




A voluntary switch happens when the thread blocks; an involuntary one when the kernel takes the CPU away (tick or wake-up preemption, or throttling). Five busy threads fighting for one CPU's worth of quota are preempted constantly: the root's Debug lab case "Too many threads for the CPUs you have" recorded 3,571 involuntary switches with 5 threads against 16 with one, for the same arithmetic.


When it bites in ML. Not through one switch (a step is milliseconds) but through numbers (hundreds of threads on a few cores, section 11), hand-offs (a DataLoader batch costs at least two wake-ups: fine per batch, ruinous per sample) and busy waiting: GNU OpenMP's idle threads spin before sleeping unless OMP_WAIT_POLICY=passive (libgomp docs), right on a dedicated node, wrong under a CPU quota.

3. Fair share: from stride scheduling to CFS


ch. 7 Scheduling: Introduction; ch. 8 MLFQ; ch. 9 Proportional Share


OSTEP's first policies (FIFO, shortest job first, round robin, MLFQ) optimise turnaround time (finish minus arrival) or response time (first run minus arrival); the root's OS simulators tab runs them. Linux asks instead for proportional share: does each thread get its share? OSTEP chapter 9 gives three answers, the third Linux's:




Lottery (1994)Each job holds tickets; every slice the scheduler draws a random ticket. Shares are right on average, noisy over short windows (Waldspurger and Weihl, OSDI 1994).


StrideDeterministic: each job has a stride = a big number / its tickets and a pass counter; run the job with the smallest pass, then add its stride to its pass. Exact shares every round.


CFS (2007)Stride scheduling in units of time: the pass is virtual runtime, which grows by the CPU time used divided by the weight. Run the smallest. Section 4.




OSTEP's stride example: A, B and C hold 100, 50 and 250 tickets, so with a big number of 10,000 their strides are . Starting from zero (ties to A, then B), the first eight picks are : C runs five times in eight, A twice, B once, and over any long window the shares are exactly 250 : 100 : 50. Replace "tickets" by "weight" and "stride" by "1024 / weight per unit of CPU time" and you have the core of CFS; the rest of the kernel code handles what the toy leaves out: sleepers, new threads, many CPUs (section 7) and groups (section 9).






4. CFS: weights, virtual runtime, slices (Linux 2.6.23 to 6.5; the kernel measured here)


ch. 9.7 The Linux Completely Fair Scheduler; CFS design doc


CFS "basically models an ideal, precise multi-tasking CPU" (the design doc), one that runs all n threads at once at 1/n speed each; it tracks how far each thread is behind that ideal and runs the one furthest behind.


Weights: what nice means


A thread's nice value (-20 to 19, default 0) indexes a fixed table of weights, sched_prio_to_weight (core.c line 8457): nice 0 is 1024, each step about 1.25 times (nice -1 is 1277, nice 1 is 820, nice 5 is 335, nice 19 is 15), so that one level is "a gentle 10% change" in share against a competitor (the comment above the table). Two busy threads on one CPU get wa / (wa + wb) each: nice 0 against nice 5 is 1024 / 1359 = ; the root measured 75.38%, and this page  (below).


Three busy threads share one CPU: two at nice 0 and one at nice 5. What does each nice-0 thread get?




1024 / (1024 + 1024 + 335) = 42.97% each, and 14.06% for the nice-5 thread. Shares depend on who else is runnable: nice 5 means "a third of a nice-0 thread's weight", not "75%".


Virtual runtime: the one number CFS sorts by measured


Three tasks on one CPU: busy loops at nice 0 and nice 5, and a "sleeper" (runs about 1 ms, sleeps 5 ms); every 50 ms for 2 s we read se.vruntime and se.sum_exec_runtime from /proc/PID/sched. Predict: which lines stay together, virtual runtime or CPU time?


Equal virtual time, unequal real time


The two busy loops' vruntimes advance together (never more than  ms apart, under one slice) while their CPU time diverges  times, the weight ratio 1024 / 335 = 3.057. That is the whole invariant of CFS, and the rule that produces it is charged at every tick and whenever the thread stops (update_curr(), fair.c line 842):


vruntime += Δexec × 1024 / weight
Δexec

weight

Runnable threads sit in a red-black tree ordered by vruntime and the leftmost runs next (the hero's axis): exactly stride scheduling. The queue keeps min_vruntime, a floor that only moves forward. The sleeper trails by a median  ms: on each wake-up it is placed at most half a latency period (9 ms here) behind min_vruntime, so it runs at once but cannot bank more than 9 ms of credit however long it slept.


How long a thread runs: period and slice


No fixed time slice: CFS aims to run every runnable thread once per scheduling period and gives each a share of it by weight. On this VM: .

Two nice-0 threads get 9 ms each, eight get 2.25 ms; beyond eight the period stretches (sixteen threads: 36 ms), which stops oversubscribed nodes switching themselves to death and is why their latency grows. A thread is preempted at the tick when its slice is used, or by a waking thread that is behind it by more than the wake-up granularity (1 ms × factor = 3 ms here). A new thread starts one virtual slice after min_vruntime (START_DEBIT), so forking cannot jump the queue.

At wake-up (place_entity, line 4108; check_preempt_wakeup, line 6916): the woken thread is placed at max(its own vruntime, min_vruntime - latency / 2) and preempts if the running thread is ahead of it by more than the wake-up granularity, scaled by the woken thread's weight:


// kernel/sched/fair.c, v5.10, lines 6869-6880: should the woken thread se preempt curr?
static int wakeup_preempt_entity(struct sched_entity *curr, struct sched_entity *se)
{
	s64 gran, vdiff = curr->vruntime - se->vruntime;
	if (vdiff <= 0)
		return -1;
	gran = wakeup_gran(se);
	if (vdiff > gran)
		return 1;
	return 0;
}

5. EEVDF: the same fairness, with deadlines (Linux 6.6 and later) not run here


ch. 9 extended; EEVDF doc; LWN, 2023-03-09; LWN, Completing the EEVDF scheduler, 2024


The problem with CFS. Its latency comes from heuristics (the sleeper credit, the wake-up granularity, "buddies"), and a thread cannot say "short bursts, but soon" except by raising its weight, which also gives it more CPU. EEVDF (Stoica and Abdel-Wahab, 1995, Earliest Eligible Virtual Deadline First), merged in Linux 6.6 to replace CFS's pick, keeps virtual runtime and adds a request size per thread (its slice) and a virtual deadline:




V, the virtual clockThe weighted mean of the queued vruntimes (avg_vruntime, fair.c line 653, v6.12): where an ideal fair CPU would have everyone now.


lagw × (V - v): service owed (positive) or overdrawn (negative); lags sum to zero.


eligiblelag ≥ 0, that is v ≤ V (line 726): only threads owed service may run.


virtual deadlined = v + slice × 1024 / w, renewed when a slice is used up (line 1007).


the pickThe eligible thread with the earliest deadline (pick_eevdf, line 907): a short slice means an early deadline, so latency is requested, not earned.


run to parityA picked thread keeps the CPU until its slice ends or it turns ineligible (RUN_TO_PARITY, features.h line 20).




The slice is 0.75 ms (sysctl_sched_base_slice) times the CPU factor: 2.25 ms on this VM's 5 CPUs, 3 ms on machines with 8 or more. Since 6.12 an ordinary thread can ask for its own with sched_setattr() and a sched_runtime, clamped to 0.1 to 100 ms (kernel/sched/syscalls.c line 306, v6.12); a woken thread with a shorter slice may then cut the current one's slice short (PREEMPT_SHORT). CFS's sched_latency_ns, sched_min_granularity_ns and sched_wakeup_granularity_ns are gone.


One CPU, three threads, two schedulers model


A trainer and a preproc thread are busy loops at nice 0; a loader wakes every 4 ms, needs 0.4 ms of CPU and sleeps (a thread that receives a batch and queues the next prefetch). One CPU, 1 ms tick, this VM's tunables, under 5.10's CFS rules and 6.12's EEVDF rules as this page's simulator implements them (the Fair-share stepper tab lists each rule's source line and what it leaves out). Predict: under which scheduler does the loader wait longest after waking?


EEVDF makes latency a request: the loader waits until it asks for a short slice
















Under CFS the loader wakes 9 ms behind min_vruntime, more than the 3 ms wake-up granularity, and preempts at once: zero wait. Under EEVDF it wakes with the lag it left with (about zero), eligible but with a deadline 2.25 ms ahead, and the running loop keeps its slice (run to parity): it waits up to the end of that slice. With a 0.1 ms slice its deadline comes first and PREEMPT_SHORT lets it in: the wait nearly vanishes, its CPU share unchanged. Total CPU per thread is the same in all three; EEVDF switches more often because its slices are shorter.


How far to trust this
A one-CPU model checked line by line against the source, not against a 6.6+ kernel (this VM runs 5.10). With an idle CPU the loader would simply be woken there (section 7); the difference matters when every CPU is busy, as on an oversubscribed training node. Custom slices (6.12) were added as "a new feature intended to help latency-sensitive tasks" (LWN, Completing the EEVDF scheduler).


On a 6.12 kernel, a serving process's request thread wakes, runs 200 us and sleeps, next to batch jobs on every core. Which change cuts its wake-up delay without giving it more CPU?




A custom slice moves its deadline earlier, which EEVDF uses to pick, and lets it preempt a thread with a longer slice; its share is unchanged because weight is unchanged. nice -10 also helps, by taking about 9 times the weight, which is more CPU, not lower latency. SCHED_BATCH does the opposite: batch threads never preempt on wake-up (section 6 measures 2 ms of delay).


Sleeping and waking under EEVDF: lag kept, delayed dequeue (depth)


CFS forgot a sleeper's history (max(own, min_vruntime - 9 ms)). EEVDF remembers its lag (PLACE_LAG, place_entity, v6.12 line 5266): a thread that slept while owed service comes back owed it, and one that slept after running ahead comes back behind. A thread that blocks while ineligible is not removed at all until it becomes eligible (DELAY_DEQUEUE, features.h line 49), so sleeping cannot be used to shed negative lag. The base slice is set at line 76 and scaled by the CPU factor in update_sysctl (line 212).

Real-time is capped, and refused in containers. A SCHED_FIFO thread in an infinite loop would own its CPU forever, so all real-time threads together get at most sched_rt_runtime_us per sched_rt_period_us: 950,000 us of every 1,000,000 here, leaving 50 ms a second for everything else. This kernel is built with RT group scheduling, which gives each cgroup its own real-time budget, zero by default, and rejects real-time policies in a group with no budget (core.c line 5370), even with CAP_SYS_NICE (the recorded refusal is in the closed block).


SCHED_DEADLINE is the opposite design: declare runtime per period, be admitted only if all reservations fit, run earliest deadline first, be stopped at the reservation. A busy loop got exactly its 2 ms per 10 ms, 20% of a CPU, although its container's quota allowed a whole CPU (cpu.max limits only the fair class).

The task declares how much CPU (runtime) it needs by when (deadline) how often (period); the kernel admits it only if all declared bandwidths fit and stops it the moment it overruns until its next period, even when the VM has idle CPUs. 7. Many CPUs: load balancing and affinity

One shared queue would need a lock every CPU fights over and would bounce threads between caches; Linux keeps one queue per CPU and pays with imbalance (three threads on one CPU while another idles). Three mechanisms fix it; a fourth stops them moving threads too eagerly:




at wake-upselect_task_rq_fair() (fair.c line 6697) chooses where a waking thread goes: its previous CPU if still a good idea, the waker's CPU if they share data (wake_affine), or an idle CPU nearby (select_idle_sibling).


periodicallyEach CPU runs load_balance() (line 9532) over a hierarchy of scheduling domains (cores sharing a cache, then a package, then NUMA nodes), pulling threads from the busiest group to itself, more often for close levels.


when idleA CPU about to go idle first tries to pull work (newidle balancing): work stealing, in OSTEP's words.

9. cgroup CPU control: cpu.weight, cpu.max and throttling

A container's cgroup has two independent CPU knobs. cpu.weight is relative: it matters only when CPUs are contended, and splits them between groups the way nice splits them between threads. cpu.max is absolute: a cap even on an idle machine. (cpuset.cpus is affinity, section 7; the rest of cgroups is Containers and isolation's.)


cpu.weight: shares of a contended CPU


cpu.weight runs from 1 to 10,000, default 100, and becomes the group's CFS weight as weight × 1024 / 100: a default group weighs one nice-0 thread in its parent's queue. The trap is the translation. Docker's --cpu-shares and Kubernetes' requests.cpu speak cgroup v1 "shares" (default 1024), which the runtime converts to a weight: runc 1.1's linear map, 1 + (shares - 2) × 9,999 / 262,142, sends the default 1024 shares to weight 39, not 100; the newer quadratic map in the opencontainers/cgroups library sends 1024 to 100 (sources in the closed block).

cpu.max: the quota, and why it stalls


cpu.max holds "$MAX $PERIOD": $MAX microseconds of CPU per $PERIOD (default 100,000 us); --cpus 2 writes 200000 100000. CFS bandwidth control enforces it in three steps:


    

  1. Each group has a global pool, refilled to the quota at every period by a timer.
    2. 

  2. Each CPU running the group's threads borrows from the pool in slices of sched_cfs_bandwidth_slice_us = 5,000 us and charges the time its threads run.
    3. 

  3. When a CPU's slice runs out and the pool is empty, throttle_cfs_rq() removes the whole group from that CPU's run queue: every thread of the container stops, runnable or not, until the next refill.
    4. 



So the quota is spent at the speed of however many threads are running. Five threads on a 1-CPU quota burn 100 ms of CPU in 20 ms of wall time and then all stop for 80 ms. Predict what one thread, two and five threads look like on the same quota, then step through:

Depth: mistakes and interview rehearsal


Common mistakes, each with what this page measured (8)


"The container has 2 CPUs, so it has 2 CPUs."It has 200 ms of CPU time per 100 ms, spendable on all 5 (or 128) CPUs at once. Programs see the whole machine and size themselves to it; the quota then stops them in bursts (section 9).


"More DataLoader workers is always faster."Only while there are idle CPUs to run them. On a 1-CPU quota, adding workers made every configuration slower here (section 11). Workers count against the same budget as compute threads.


"nice 19 means it gets 5% of the CPU."Nice is a weight, so the share depends on who else is runnable: alone, a nice-19 thread gets the whole CPU; against one nice-0 thread it gets 15 / 1039 = 1.4%.


"High load average means the CPUs are saturated."On Linux it also counts tasks in uninterruptible sleep, usually I/O; three D-state tasks using no CPU raised it here (section 10). Look at run-queue waiting and throttling instead.


"Pinning threads makes things faster."Pinning removes the load balancer's freedom; two busy threads pinned to one core run at half speed while others idle. Pin whole processes to NUMA nodes or exclusive core sets, not individual threads, unless you have measured.


"Give the important process real-time priority."A SCHED_FIFO thread that spins can starve kernel threads on its CPU (until the 95% real-time cap) and every ordinary thread; inside containers it is refused anyway (section 6). Use weight (nice, cpu.weight) or exclusive cores.


"cpu.stat's throttled_usec is how long my job was stopped."It is summed over the CPUs the group was throttled on, so it can exceed wall time (3.8 s of throttling in a 1.1 s run with 5 threads, section 9). Compare nr_throttled with nr_periods instead.


"EEVDF settings are the CFS sysctls."On 6.6+ kernels sched_latency_ns, sched_min_granularity_ns and sched_wakeup_granularity_ns no longer exist; latency is requested per thread with a slice (section 5). Tuning guides written for CFS do not apply.




Interview rehearsal: seven questions with short answers (optional)


What exactly happens in a context switch, and what does it cost?The current thread enters the kernel (its user registers are saved on its kernel stack), the scheduler picks the next task, the address space is switched if the process differs (on arm64 with ASIDs, without a TLB flush), and the callee-saved registers and stack pointer are swapped (cpu_switch_to). Direct cost here: about 1.5 us including the sleep and wake path; the bigger costs are indirect (cold caches and TLB) and, across CPUs, the wake-up interrupt (26 to 51 us in this VM).


How does CFS decide who runs next, and how does nice change it?Each thread accumulates virtual runtime = CPU time × 1024 / weight; CFS runs the thread with the smallest, kept in a red-black tree. Nice maps to a weight (1024 at nice 0, × 1.25 per step), so a heavier thread's vruntime grows more slowly and it is picked more often: shares are proportional to weights. Slices are the period (6 ms × factor, stretched beyond 8 threads) times the weight fraction.


Why did Linux move from CFS to EEVDF, and what changes for a latency-sensitive thread?CFS achieved latency through heuristics (sleeper credit, wake-up granularity, buddies). EEVDF keeps vruntime but adds lag, eligibility and a virtual deadline (vruntime + slice / weight), picking the eligible thread with the earliest deadline. A thread can request a shorter slice (6.12, sched_setattr), getting earlier deadlines and lower wake-up delay without more CPU share.


A pod with a 4-CPU limit on a 64-core node trains 5 times slower than on a laptop. Diagnose.PyTorch, OpenMP and every library size their pools from the visible CPUs (64), not from the quota. 64 threads burn the 400 ms quota in about 6 ms of each 100 ms period and the whole pod is throttled for the rest. Evidence: nr_throttled close to nr_periods, huge involuntary switch counts. Fix: set thread and worker counts from the quota, remove the limit (keep a request), or use exclusive cores.


What is the difference between cpu.weight and cpu.max?Weight is relative and work-conserving: it only divides contended CPU time, and an idle machine gives any group everything. Max is a hard cap enforced per period even when CPUs are idle, implemented by throttling the whole group when its runtime pool is empty. Kubernetes requests become weights, limits become cpu.max.


What does load average measure on Linux?An exponentially damped average (1, 5, 15 minutes, updated every 5 s) of runnable plus uninterruptible tasks over the whole machine. It is not utilisation, not per CPU and not per container; D-state tasks raise it without using CPU.


Why can't you run SCHED_FIFO in a Docker container, and what is SCHED_DEADLINE for?With RT group scheduling each cgroup has its own real-time budget, zero by default, and setting a real-time policy in a group with no budget fails with EPERM. SCHED_DEADLINE reserves runtime per period with admission control and EDF ordering; the kernel throttles it at its reservation, which makes it suitable for periodic control loops.

The rules, with their place in the kernel source

EEVDF, Linux v6.12 kernel/sched/fair.c: V = weighted mean vruntime (avg_vruntime 653); eligible when v ≤ V (726); deadline = v + slice × 1024 / weight, renewed with a reschedule when reached (update_deadline 1007, update_curr 1216); pick the eligible thread with the earliest deadline, keeping the current one until its slice ends (pick_eevdf 907, RUN_TO_PARITY); lag kept across sleep and inflated on placement, half a slice for a new thread (place_entity 5266); a thread that sleeps while ineligible stays queued until picked, then leaves with its lag clipped to zero (DELAY_DEQUEUE, DELAY_ZERO; dequeue_entity 5476, pick_next_entity 5613, requeue_delayed_entity 6919); a woken thread with a shorter slice may cancel the current one's protection (PREEMPT_SHORT, 1166 and 1177); base slice 0.75 ms × factor (line 76); custom slices clamped to 0.1 to 100 ms (syscalls.c 306).
