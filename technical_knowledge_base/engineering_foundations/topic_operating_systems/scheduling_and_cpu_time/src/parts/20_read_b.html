The idea in one screen

A CPU runs one thread at a time. Linux keeps a run queue per CPU; ordinary threads share it in proportion to their weight (the one with the least weighted CPU time, its virtual runtime, runs next), and a container's CPU limit is a quota per 100 ms period that, once spent, stops every thread of the container until the next period.

Who runs next is a sort by virtual runtime; a CPU limit is a stop, not fewer CPUs

One CPU's run queue measured

The fair class opened out: three threads on one CPU placed by their se.vruntime from /proc/PID/sched, 1 s into section 4's run. The nice-5 loop keeps pace with the nice-0 loop on a third of the CPU because its virtual runtime grows 3.06 times faster; the sleeper is always behind and runs as soon as it wakes.

A container with a 1-CPU quota and 5 busy threads measured

The first 300 ms of section 9's run: five threads spend the 100 ms quota in a burst (100 / 5 = 20 ms of wall time if each has a CPU), then all of them stop (here ms at a stretch) until the period timer refills it. The CPU work done is the same as with one thread; the stall is the cost.

1. What gets scheduled: threads, states, run queues

The unit is the thread. Every thread is its own task (task_struct); a process is a group of tasks sharing one address space, so a PyTorch process with 5 compute threads competes as 5 tasks. The STAT letter of ps gives the state: R running or runnable (waiting only for a CPU), S sleeping until an event, D sleeping uninterruptibly (usually on I/O in the kernel), T stopped, Z exited, not yet reaped. Only R tasks need the scheduler.

Run queues. Each CPU has its own, split by scheduling class and tried highest first: stop (a per-CPU kernel helper), deadline, real-time, fair, idle (the hero's top row). Almost everything you run is fair. The CPU changes thread at four kinds of moment:

1. it blocksA read, a lock, sleep: it leaves the run queue. A voluntary switch.
2. the timer tickEvery 1 ms here (CONFIG_HZ=1000) an interrupt charges the running thread and may take the CPU away. An involuntary switch. Without it a spinning thread would keep the CPU forever (OSTEP's limited direct execution).
3. a wake-upA woken thread that deserves the CPU more than the current one preempts it at once.
4. the switch pointThe decision sets a "need to reschedule" flag; the switch happens at the next safe point, which with CONFIG_PREEMPT=y (this VM) includes most kernel code.

The running job, seen by the scheduler measured

The root's training job (2 DataLoader workers, --threads 2) in a 2-CPU container, every thread read from /proc/PID/task/TID/ 7 s after start; "waiting" is time runnable but not running (schedstat, {{sched-stats docs|https://docs.kernel.org/scheduler/sched-stats.html}}), throttled time included.

The DataLoader workers above have run for less than a second. The job has been running for 7. Why?

Each for batch in loader creates a new iterator, and without persistent_workers=True each iterator forks fresh worker processes and joins the old ones (PyTorch's {{DataLoader docs|https://docs.pytorch.org/docs/stable/data.html}}). This job's epoch is 128 steps, about half a second here, so the worker pids changed every half second: . Each fork costs the start-up the root's Syscall tracer measured; at real epoch lengths it is negligible, at tiny ones it is not.

In the source, and the raw ps output (depth)

Inside each struct task_struct sits a struct sched_entity (weight, virtual runtime, total CPU time), the scheduling policy, the priority and the set of allowed CPUs ({{include/linux/sched.h, v5.10|https://github.com/torvalds/linux/blob/v5.10/include/linux/sched.h#L640}}); the process id is the thread-group id. The per-CPU struct rq holds a deadline queue, a real-time queue and a fair queue (cfs_rq) ({{kernel/sched/sched.h, v5.10|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/sched.h#L895}}); the class order comes from the linker script, which lists them lowest first ({{include/asm-generic/vmlinux.lds.h line 128|https://github.com/torvalds/linux/blob/v5.10/include/asm-generic/vmlinux.lds.h#L128}}).
