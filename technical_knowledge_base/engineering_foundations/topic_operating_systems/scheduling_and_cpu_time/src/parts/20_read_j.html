9. cgroup CPU control: cpu.weight, cpu.max and throttling

beyond OSTEP; {{cgroup v2: CPU interface files|https://docs.kernel.org/admin-guide/cgroup-v2.html#cpu-interface-files}}; {{CFS bandwidth control doc|https://docs.kernel.org/scheduler/sched-bwc.html}}

A container is a cgroup, and the cgroup's cpu controller has two independent knobs. cpu.weight is relative: it only matters when CPUs are contended, and then splits them between groups the way nice splits them between threads. cpu.max is absolute: a cap that applies even on an idle machine. (A third, cpuset.cpus, is affinity: section 7.) Namespaces, delegation and pressure stall information are the sibling {{Containers and isolation|n:3f05c17b0d0d8156a841e4bf28f11293}} page's subject; here we look at how the scheduler enforces the two knobs.

cpu.weight: shares of a contended CPU

cpu.weight runs from 1 to 10,000, default 100. The kernel turns it into the group's CFS weight as weight × 1024 / 100 ({{core.c line 8286|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/core.c#L8286}}), so a default group weighs the same as one nice-0 thread in its parent's queue. The trap is the translation from older interfaces: Docker's --cpu-shares and Kubernetes' requests.cpu speak cgroup v1 "shares" (default 1024; Kubernetes uses milli-CPUs × 1024 / 1000, {{pkg/kubelet/cm/helpers_linux.go line 88, v1.34.0|https://github.com/kubernetes/kubernetes/blob/v1.34.0/pkg/kubelet/cm/helpers_linux.go#L88}}), and the OCI runtime converts shares to a v2 weight. runc 1.1 used a linear map, 1 + (shares - 2) × 9,999 / 262,142 ({{libcontainer/cgroups/utils.go line 423, runc v1.1.2|https://github.com/opencontainers/runc/blob/v1.1.2/libcontainer/cgroups/utils.go#L423}}), which sends the default 1024 shares to weight 39, well below the default weight 100. A newer quadratic map in the opencontainers/cgroups library (from v0.0.3, {{utils.go line 425|https://github.com/opencontainers/cgroups/blob/v0.0.3/utils.go#L425}}; runc v1.3.6 and v1.4.0 depend on versions that have it, per their go.mod) sends 1024 to 100.

Measured with this VM's Docker 20.10 (the old map): two busy containers pinned to the same CPU with --cpu-shares 1024 and 512 got weights and split the CPU (predicted 39 / 59 = 66.1%). Weight protects you only in proportion to everyone else's, and only when you are actually competing for the same CPUs.

cpu.max: the quota, and why it stalls

cpu.max holds "$MAX $PERIOD": the group may use $MAX microseconds of CPU in each $PERIOD (default 100,000 us). --cpus 2 writes 200000 100000. The kernel's CFS bandwidth control enforces it like this:

  1. Each group has a global pool, refilled to the quota at every period by a timer (__refill_cfs_bandwidth_runtime, {{fair.c line 4601|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/fair.c#L4601}}; do_sched_cfs_period_timer, line 4942).
  2. Each CPU running the group's threads borrows from the pool in slices of sched_cfs_bandwidth_slice_us = 5,000 us (line 129; the same value read here) and charges the time its threads run (__account_cfs_rq_runtime, line 4653).
  3. When a CPU's slice runs out and the pool is empty, throttle_cfs_rq() (line 4741) removes the whole group from that CPU's run queue: every thread of the container stops, runnable or not, until the next refill.

So the quota is spent at the speed of however many threads are running. Five threads on a 1-CPU quota burn 100 ms of CPU in 20 ms of wall time and then all stop for 80 ms. Periods may be 1 ms to 1 s and quotas at least 1 ms ({{core.c lines 7891 to 7919|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/core.c#L7891}}). Kernels from 5.14 add cpu.max.burst, which lets unused quota carry over to absorb short bursts ({{sched-bwc doc|https://docs.kernel.org/scheduler/sched-bwc.html}}) not on this kernel.

Replay: threads against a quota, period by period measured

Inside a container with a CPU limit, N threads spin for 1 s, and each records every gap of more than 300 us in its own progress (a gap is time it was not running). Drawn to scale: one lane per thread, dark where the thread ran, light where it was stopped, period boundaries as ticks. Step through the periods; switch runs to compare the same quota with one thread and five, or the same five threads with a 100 ms and a 10 ms period.

What it shows. With as many threads as the quota allows, nothing stops. With five, every thread stops for ms in each 100 ms period (predicted: 100 - 100 / 5 = 80 ms), and the container's cpu.stat counts the periods. The total CPU used is the same in every run: throttling does not cost work, it costs latency, which is what a training step, a request or a GPU waiting for its next batch feels. A 10 ms period caps the stall near 8 ms (measured up to ms) at the price of ten times as many throttling events. throttled_usec adds up the throttled time of every CPU the group was on, which is why it can exceed the wall-clock time of the run.

Measured on the root page
The root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} case "Step time quadruples under a CPU limit: cgroup throttling" ran the same matmul step at 138 ms per step with 2 CPUs and 701 ms with half a CPU (2 threads), throttled in every period; "Too many threads for the CPUs you have" ran 5 threads on 1 CPU at 496 ms per step against 210 ms with 1 thread. The CPU budget lab tab of this page extends that to the whole grid of threads, DataLoader workers and quotas.

Fixes. Size thread pools and workers to the quota (section 11); in Kubernetes, some clusters set CPU requests without limits so pods share idle CPU by weight instead of being throttled; the kubelet can use a shorter period (the CPUCFSQuotaPeriod feature gate, {{helpers_linux.go line 73|https://github.com/kubernetes/kubernetes/blob/v1.34.0/pkg/kubelet/cm/helpers_linux.go#L73}}); or give the pod exclusive cores with the static CPU manager policy (section 7).
