Real-time throttling. A SCHED_FIFO thread in an infinite loop would own its CPU forever, so the kernel caps all real-time threads together at sched_rt_runtime_us per sched_rt_period_us: 950,000 us of every 1,000,000 here, leaving 50 ms a second for everything else. In containers it is simply refused: this kernel is built with RT group scheduling, which gives each cgroup its own real-time budget, zero by default, and the kernel rejects real-time policies in a group with no budget ({{core.c line 5370|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/core.c#L5370}}), even with CAP_SYS_NICE added:



SCHED_DEADLINE is the opposite design: instead of a priority, the task declares how much CPU it needs (runtime) by when (deadline) how often (period), the kernel admits it only if the sum of all declared bandwidths fits, and then runs the task with the earliest deadline first, stopping it the moment it overruns its runtime until its next period (the constant bandwidth server: update_curr_dl, {{deadline.c line 1239|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/deadline.c#L1239}}). Admission is checked over a set of CPUs, so the task must be allowed to run on all of them ({{core.c line 5387|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/core.c#L5387}}). For a training job
Never run training threads as real-time: they would starve the kernel's own threads and the DataLoader, hit the 950 ms per second cap, and containers forbid it anyway. For work that should yield to training on the same cores, use nice -n 10 or SCHED_BATCH (preprocessing, evaluation) and SCHED_IDLE for truly background jobs (log compaction, uploads). SCHED_DEADLINE is for periodic control loops (robotics, audio), not for ML throughput.
