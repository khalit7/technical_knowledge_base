Real-time is capped, and refused in containers. A SCHED_FIFO thread in an infinite loop would own its CPU forever, so all real-time threads together get at most sched_rt_runtime_us per sched_rt_period_us: 950,000 us of every 1,000,000 here, leaving 50 ms a second for everything else. This kernel is built with RT group scheduling, which gives each cgroup its own real-time budget, zero by default, and rejects real-time policies in a group with no budget ({{core.c line 5370|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/core.c#L5370}}), even with CAP_SYS_NICE (the recorded refusal is in the closed block).

SCHED_DEADLINE is the opposite design: declare runtime per period, be admitted only if all reservations fit, run earliest deadline first, be stopped at the reservation. A busy loop got exactly its 2 ms per 10 ms, 20% of a CPU, although its container's quota allowed a whole CPU (cpu.max limits only the fair class).

Wake-up delay by policy and neighbour measured

A thread sleeps 1 ms 3,000 times on one CPU and records how late each wake-up ran, beside busy loops of different classes and niceness. Predict: does a CPU crowded with four busy loops wake the sleeper later or sooner than an idle one?

Batch threads wait for the tick; normal ones preempt at once

Alone, the median wake-up was us late: the idle CPU had to wake (in a VM, through the hypervisor). With four busy loops it was lower, us: the CPU never sleeps and the sleeper credit lets the woken thread preempt at once. As SCHED_BATCH it waited us: no wake-up preemption, so it waits for a tick to end the running loop's slice. SCHED_IDLE loops ( us) and nice-19 ones ( us) are nearly invisible. The multi-millisecond maxima are the shared VM's.

For a training job
Never real-time: it starves kernel threads and the DataLoader, hits the 950 ms per second cap, and containers forbid it. Work that should yield to training: nice -n 10 or SCHED_BATCH (preprocessing, evaluation), SCHED_IDLE for background jobs (log compaction, uploads). SCHED_DEADLINE is for periodic control loops (robotics, audio), not ML throughput.

The task declares how much CPU (runtime) it needs by when (deadline) how often (period); the kernel admits it only if all declared bandwidths fit and stops it the moment it overruns until its next period, even when the VM has idle CPUs. The constant bandwidth server: update_curr_dl ({{deadline.c line 1239|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/deadline.c#L1239}}) stops the task when its runtime is spent. Admission is checked over a set of CPUs, so the task must be allowed to run on all of them ({{core.c line 5387|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/core.c#L5387}}).
