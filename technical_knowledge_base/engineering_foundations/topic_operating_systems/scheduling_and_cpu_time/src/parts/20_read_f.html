4. CFS in depth (Linux 2.6.23 to 6.5; the kernel measured here)

ch. 9.7 The Linux Completely Fair Scheduler; {{CFS design doc|https://docs.kernel.org/scheduler/sched-design-CFS.html}}

The problem. Give every runnable thread a share of the CPU proportional to its weight, keep interactive threads responsive, and do it in a few hundred nanoseconds per decision on queues of any length. The idea (from the design doc): CFS "basically models an ideal, precise multi-tasking CPU", one that would run all n threads at once, each at 1/n speed. Real CPUs run one at a time, so CFS tracks how far each thread is behind that ideal and runs the one furthest behind.

Weights: what nice means

A thread's nice value (-20 to 19, default 0) indexes a fixed table of weights, sched_prio_to_weight ({{kernel/sched/core.c line 8457, v5.10|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/core.c#L8457}}): nice 0 is 1024, each step multiplies by about 1.25 (nice -1 is 1277, nice 1 is 820, nice 5 is 335, nice 19 is 15). The comment above it explains the choice: one nice level is "a gentle 10% change" in CPU share against a competitor. Two busy threads on one CPU get wa / (wa + wb) each: nice 0 against nice 5 is 1024 / 1359 = ; the root measured 75.38%, and this page (below, with the two threads in different sessions).

1024 / (1024 + 1024 + 335) = 42.97% each, and 14.06% for the nice-5 thread. Shares depend on who else is runnable: nice 5 means "a third of a nice-0 thread's weight", not "75%".

Virtual runtime: the one number CFS sorts by

Every time the running thread is charged (at each tick, and whenever it stops), update_curr() adds the CPU time it used, scaled by its weight, to its virtual runtime ({{fair.c line 842|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/fair.c#L842}}, using calc_delta_fair() at line 671):

vruntime += Δexec × 1024 / weight
Δexec
nanoseconds of CPU just used
weight
from the nice table; 1024 at nice 0, so a nice-0 thread's vruntime is its CPU time

A nice-5 thread's vruntime grows 3.06 times faster than its CPU time. Runnable threads sit in a red-black tree ordered by vruntime ({{__enqueue_entity, line 575|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/fair.c#L575}}); the next thread is the leftmost, the one with the least virtual runtime (pick_next_entity, line 4435). Running pushes a thread to the right, so heavier threads, whose vruntime grows slowly, are picked more often: exactly stride scheduling. The queue also keeps min_vruntime, a floor that only moves forward (line 540), used to place threads that arrive or wake.

Watching it on a real kernel measured

Three tasks pinned to one CPU: a busy loop at nice 0, a busy loop at nice 5, and a "sleeper" that runs about 1 ms then sleeps 5 ms. Every 50 ms for 2 s we read se.vruntime and se.sum_exec_runtime from /proc/PID/sched (available with CONFIG_SCHED_DEBUG, which this kernel has).

What it shows. The two busy loops' vruntimes advance together (never more than ms apart, under one slice), while their CPU time diverges by times, the weight ratio 1024 / 335 = 3.057. That is the whole invariant of CFS: equal virtual time, unequal real time. The sleeper's vruntime trails the others by a median ms: each time it wakes it is placed at most half a latency period (9 ms here) behind min_vruntime, so it always looks "behind" and runs at once, but cannot bank more than 9 ms of credit however long it slept.

How long a thread runs: period, slice, granularity

CFS does not use a fixed time slice. It aims to run every runnable thread once per scheduling period and gives each a slice proportional to its weight ({{__sched_period and sched_slice, lines 687 and 701|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/fair.c#L687}}):

period = latency if n ≤ 8, else n × min_granularity; slicei = period × wi / Σw
latency
6 ms × factor (sysctl_sched_latency, line 38)
min_granularity
0.75 ms × factor (line 59); 8 = latency / min_granularity
factor
1 + log2(min(CPUs, 8)) (get_update_sysctl_factor, line 159): 3 on this VM's 5 CPUs, 4 on 8 or more

So on this VM: . Two nice-0 threads get 9 ms each; eight get 2.25 ms; beyond eight the period stretches instead of slices shrinking (sixteen threads: a 36 ms period), which is what keeps oversubscribed nodes from switching themselves to death and also what makes their latency grow.

Preemption at the tick (check_preempt_tick, line 4355): the running thread is switched out when it has run longer than its slice, or, once it has run at least min_granularity, when its vruntime is ahead of the leftmost thread's by more than a slice. Preemption at wake-up (place_entity, line 4108; check_preempt_wakeup, line 6916): the woken thread is placed at max(its own vruntime, min_vruntime - latency / 2), and it preempts the running thread at once if the running thread's vruntime is ahead of it by more than the wake-up granularity (1 ms × factor = 3 ms here, scaled by the woken thread's weight). A new thread (after fork) starts one virtual slice after min_vruntime (the START_DEBIT feature), so forking cannot be used to jump the queue.

// kernel/sched/fair.c, v5.10, lines 6869-6880: should the woken thread se preempt curr?
static int wakeup_preempt_entity(struct sched_entity *curr, struct sched_entity *se)
{
	s64 gran, vdiff = curr->vruntime - se->vruntime;
	if (vdiff <= 0)
		return -1;
	gran = wakeup_gran(se);
	if (vdiff > gran)
		return 1;
	return 0;
}

Groups and autogroup

With cgroups, fairness is applied per level: a container is one entity in its parent's run queue with its own weight (cpu.weight, section 9), and threads compete inside it. Desktop kernels add autogroup: each session (a terminal, say) becomes its own group, so a make -j64 in one terminal cannot starve another; the side effect is that nice only works within a session. This kernel has it on (sched_autogroup_enabled = 1) but it only applies to tasks in the root cgroup ({{kernel/sched/autogroup.c line 109|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/autogroup.c#L109}}), never inside a container: two busy loops in different sessions (setsid) still split 75 : 25 by nice:
