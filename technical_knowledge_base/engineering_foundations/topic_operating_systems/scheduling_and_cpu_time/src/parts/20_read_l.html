11. ML recipes: threads, workers, pinning, neighbours

Everything above comes down to a budget: a training process gets some number of CPUs (a quota, a cpuset, or a whole node), and every thread it starts spends from it. The defaults are sized for the whole machine, so they overspend whenever the job is given less.

Add them up for one process with 4 workers that each start a 5-thread tokenizer pool, plus PyTorch's own pools, and a container allowed 2 CPUs runs dozens of busy threads: oversubscription, more busy threads than CPUs to run them.

The budget, measured measured

The {{CPU budget lab|#t-budget}} tab runs one loop (a DataLoader decoding samples with real CPU work, a model step of matmuls) for every combination of 1, 2, 4 or 5 torch threads and 0, 1, 2 or 4 workers, under quotas of 1, 2 and 4 CPUs, three times each. The best and the default:

The default (5 threads, sized from the machine) was the worst or near the worst choice at every quota smaller than the machine. With one CPU, workers did not help at all (they only add more threads to throttle); with two or four, the best was a couple of compute threads plus a couple of workers, about one busy thread per CPU of quota. The exact best point depends on how heavy your decode is against your model step; the rule does not.

Recipes

  1. Read the budget, then set every pool. quota = cpu.max[0] / cpu.max[1] (or the cpuset size, or the Kubernetes limit), divided by the number of training processes on the node. Set torch.set_num_threads and num_workers so that compute threads + busy workers ≈ budget.
  2. Keep workers alive. Without persistent_workers=True every epoch forks a new set (section 1 measured new pids every half second on a tiny epoch).
  3. Check the signature of a starving GPU. Rising nr_throttled in cpu.stat, involuntary switches in the thousands, or the main thread waiting on a run queue (schedstat) all mean the feeding CPUs are short; py-spy dump shows whether the main thread waits in next(it) (the root's Debug lab case "The training loop waits for data: DataLoader-bound").
  4. On multi-socket GPU nodes, bind each rank near its GPU: torchrun --numa-binding=node (section 8).
  5. Against noisy neighbours, weights help only under contention and in proportion (section 9); exclusive cores (a cpuset, the kubelet's static CPU manager) are the only real isolation.
  6. Background work yields: preprocessing and evaluation at nice -n 10 or SCHED_BATCH, uploads at SCHED_IDLE (section 6); never real-time.
# size PyTorch's pools from the container's quota (or affinity), not from os.cpu_count()
import os, math, torch
def cpu_budget():
    n = len(os.sched_getaffinity(0))                    # cpuset / taskset
    try:
        q, p = open("/sys/fs/cgroup/cpu.max").read().split()
        if q != "max": n = min(n, max(1, math.floor(int(q) / int(p))))
    except OSError: pass                              # cgroup v1 or no cgroup
    return n
b = cpu_budget() // int(os.environ.get("LOCAL_WORLD_SIZE", "1"))
torch.set_num_threads(max(1, b // 2)); num_workers = max(0, b - b // 2)

The split between threads and workers in the last line is a starting point, not a rule; measure your own step with the lab's method.
