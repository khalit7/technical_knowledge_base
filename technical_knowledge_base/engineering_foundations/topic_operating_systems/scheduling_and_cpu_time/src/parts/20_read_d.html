2. The context switch: what is saved and what it costs

ch. 6 Limited Direct Execution (6.3 Saving and Restoring Context); ch. 10 Multiprocessor Scheduling (cache affinity)

The problem. To run another thread, the CPU's state for the current one must be put somewhere and the other's brought back, so that each thread resumes as if it had never stopped. How it works. When a thread enters the kernel (system call, interrupt, fault), the hardware and the entry code have already saved its user registers on that thread's own kernel stack. The switch itself, in context_switch() ({{kernel/sched/core.c line 3728, v5.10|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/core.c#L3728}}), is then three steps:

1 pick the next task2 switch the address space3 switch registers and stack
  • Pick: __schedule() asks each class in order (section 1) for its best task.
  • Address space: switch_mm_irqs_off() (line 3765) points the MMU at the next process's page tables. Skipped between threads of one process (same address space). On arm64 each address space carries an ASID tag in the TLB, so the TLB is not flushed (the sibling {{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}} page, section 3).
  • Registers and stack: switch_to() (line 3779) calls __switch_to(), which hands over the floating-point and SIMD registers lazily ({{arch/arm64/kernel/process.c line 552|https://github.com/torvalds/linux/blob/v5.10/arch/arm64/kernel/process.c#L552}}), then cpu_switch_to, about twenty instructions of assembly that store the callee-saved registers x19 to x28, the frame pointer, the stack pointer and the return address of the old task and load the new task's ({{arch/arm64/kernel/entry.S line 892|https://github.com/torvalds/linux/blob/v5.10/arch/arm64/kernel/entry.S#L892}}). Its final ret returns into the other task's kernel stack, which later returns to that task's user code.
// arch/arm64/kernel/entry.S, v5.10, lines 892-905 (abridged)
SYM_FUNC_START(cpu_switch_to)
	mov	x10, #THREAD_CPU_CONTEXT
	add	x8, x0, x10              // x0 = previous task
	mov	x9, sp
	stp	x19, x20, [x8], #16      // store callee-saved registers
	...
	stp	x29, x9, [x8], #16       // frame pointer and stack pointer
	str	lr, [x8]                 // where to resume
	add	x8, x1, x10              // x1 = next task
	ldp	x19, x20, [x8], #16      // restore callee-saved registers ...

What it costs here measured

Two processes pinned to one CPU pass one byte back and forth through two pipes, 200,000 times (the lmbench method the root used: subtract the cost of the same pipe calls without a switch, divide by two switches per round trip). Then the same with two threads of one process and a futex (the kernel's wait-and-wake primitive under every lock), then hand-offs across two CPUs. Five runs each, VM load average about 5 at the time.

Reading it. A switch between two processes on one CPU costs us (the root measured 1.33 us with the same method), and between two threads of one process no less ( us): on this CPU, changing address space is nearly free thanks to ASIDs, and the cost is the kernel's sleep-and-wake path, not the register swap. Across CPUs the hardware is fast: a token passed through one shared cache line by two spinning threads takes ns one way. But waking a sleeping thread on another CPU took us one way when that CPU was idle and us when a low-priority busy loop kept it awake: the wake-up needs an inter-processor interrupt, and an idle virtual CPU must first be woken by the hypervisor. That is this VM; we did not measure bare metal. Why it costs this much here (a GICv2 emulated in QEMU on Hypervisor.framework) is section 5 of {{Virtualization and the GPU driver stack|n:3f05c17b0d0d8158b029e9b2ba2e161b}}. sched_yield() is only a hint in CFS (it marks the caller to be skipped once, {{fair.c line 7167|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/fair.c#L7167}}): of the calls actually switched.

The indirect cost: cold caches measured

After a switch the new thread finds the caches and TLB full of someone else's data and pays to refill them. To see it, a loop walks a working set of 4 MiB in random order (each load depends on the previous one) for 3 s alone on a CPU, then 6 s sharing that CPU with a busy loop that touches no memory, then with one that streams through 64 MiB; we compare nanoseconds per load over the CPU time it actually got. Three rounds:

The spread between rounds (alone: ns per load, as the VM's load rose) is as large as the effect, so this VM cannot give a clean number. Two things held in all three rounds: sharing with the streaming loop was the slowest, which is the cache effect; and sharing with the memory-free loop was also slower than alone, which is not a cache effect, and which we cannot explain from inside the VM (the host may move virtual CPUs between core types). CFS's long slices (section 4: 9 ms each for two tasks) are what keep this cost small: refilling 4 MiB at an illustrative 50 GB/s takes about 84 us, paid once per slice, under 1% of 9 ms.

The Debug lab's "Too many threads" case ran 5 PyTorch threads on a 1-CPU quota. Which counter should explode?

A voluntary switch happens when the thread blocks; an involuntary one when the kernel takes the CPU away (tick or wake-up preemption, or throttling). Five busy threads fighting for one CPU's worth of quota are preempted constantly: the root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} case "Too many threads for the CPUs you have" recorded 3,571 involuntary switches with 5 threads against 16 with one, for the same arithmetic.

When it bites in ML. Rarely through the switch itself: a training step is milliseconds, a switch microseconds. It bites through numbers (hundreds of threads from per-process thread pools on a few cores, section 11), through hand-offs (a DataLoader batch crosses processes with at least two wake-ups; fine per batch, ruinous per sample), and through busy waiting: libraries that spin instead of sleeping (GNU OpenMP's idle threads spin before they sleep unless OMP_WAIT_POLICY=passive, {{libgomp docs|https://gcc.gnu.org/onlinedocs/libgomp/GOMP_005fSPINCOUNT.html}}) trade a whole CPU for microseconds of latency, which is right on a dedicated node and wrong under a CPU quota.
