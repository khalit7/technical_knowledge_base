3. Fair share: from stride scheduling to CFS

ch. 7 Scheduling: Introduction; ch. 8 MLFQ; ch. 9 Proportional Share

OSTEP's first policies (FIFO, shortest job first, round robin, MLFQ) optimise turnaround time (finish minus arrival) or response time (first run minus arrival); the root's {{OS simulators|n:3f05c17b0d0d81c5a97ce991644af140}} tab runs them. Linux asks instead for proportional share: does each thread get its share? OSTEP chapter 9 gives three answers, the third Linux's:

Lottery (1994)Each job holds tickets; every slice the scheduler draws a random ticket. Shares are right on average, noisy over short windows ({{Waldspurger and Weihl, OSDI 1994|https://www.usenix.org/legacy/publications/library/proceedings/osdi/full_papers/waldspurger.pdf}}).
StrideDeterministic: each job has a stride = a big number / its tickets and a pass counter; run the job with the smallest pass, then add its stride to its pass. Exact shares every round.
CFS (2007)Stride scheduling in units of time: the pass is virtual runtime, which grows by the CPU time used divided by the weight. Run the smallest. Section 4.

Replace "tickets" by "weight" and "stride" by "1024 / weight per unit of CPU time" and you have the core of CFS; the rest of the kernel code handles what the toy leaves out: sleepers, new threads, many CPUs (section 7) and groups (section 9).

4. CFS: weights, virtual runtime, slices (Linux 2.6.23 to 6.5; the kernel measured here)

ch. 9.7 The Linux Completely Fair Scheduler; {{CFS design doc|https://docs.kernel.org/scheduler/sched-design-CFS.html}}

CFS "basically models an ideal, precise multi-tasking CPU" (the design doc), one that runs all n threads at once at 1/n speed each; it tracks how far each thread is behind that ideal and runs the one furthest behind.

Weights: what nice means

A thread's nice value (-20 to 19, default 0) indexes a fixed table of weights, sched_prio_to_weight ({{core.c line 8457|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/core.c#L8457}}): nice 0 is 1024, each step about 1.25 times (nice -1 is 1277, nice 1 is 820, nice 5 is 335, nice 19 is 15), so that one level is "a gentle 10% change" in share against a competitor (the comment above the table). Two busy threads on one CPU get wa / (wa + wb) each: nice 0 against nice 5 is 1024 / 1359 = ; the root measured 75.38%, and this page (below).

Three busy threads share one CPU: two at nice 0 and one at nice 5. What does each nice-0 thread get?

1024 / (1024 + 1024 + 335) = 42.97% each, and 14.06% for the nice-5 thread. Shares depend on who else is runnable: nice 5 means "a third of a nice-0 thread's weight", not "75%".

Virtual runtime: the one number CFS sorts by measured

Three tasks on one CPU: busy loops at nice 0 and nice 5, and a "sleeper" (runs about 1 ms, sleeps 5 ms); every 50 ms for 2 s we read se.vruntime and se.sum_exec_runtime from /proc/PID/sched. Predict: which lines stay together, virtual runtime or CPU time?

Equal virtual time, unequal real time

The two busy loops' vruntimes advance together (never more than ms apart, under one slice) while their CPU time diverges times, the weight ratio 1024 / 335 = 3.057. That is the whole invariant of CFS, and the rule that produces it is charged at every tick and whenever the thread stops (update_curr(), {{fair.c line 842|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/fair.c#L842}}):

vruntime += Δexec × 1024 / weight
Δexec
nanoseconds of CPU just used
weight
from the nice table; 1024 at nice 0, so a nice-0 thread's vruntime is its CPU time

Runnable threads sit in a red-black tree ordered by vruntime and the leftmost runs next (the hero's axis): exactly stride scheduling. The queue keeps min_vruntime, a floor that only moves forward. The sleeper trails by a median ms: on each wake-up it is placed at most half a latency period (9 ms here) behind min_vruntime, so it runs at once but cannot bank more than 9 ms of credit however long it slept.

How long a thread runs: period and slice

No fixed time slice: CFS aims to run every runnable thread once per scheduling period and gives each a share of it by weight. On this VM: .

period = latency if n ≤ 8, else n × min_granularity; slicei = period × wi / Σw
latency
6 ms × factor
min_granularity
0.75 ms × factor; 8 = latency / min_granularity
factor
1 + log2(min(CPUs, 8)): 3 on this VM's 5 CPUs, 4 on 8 or more

Two nice-0 threads get 9 ms each, eight get 2.25 ms; beyond eight the period stretches (sixteen threads: 36 ms), which stops oversubscribed nodes switching themselves to death and is why their latency grows. A thread is preempted at the tick when its slice is used, or by a waking thread that is behind it by more than the wake-up granularity (1 ms × factor = 3 ms here). A new thread starts one virtual slice after min_vruntime (START_DEBIT), so forking cannot jump the queue.

The rules line by line, and autogroup (depth)

Charging. update_curr() uses calc_delta_fair() (fair.c line 671); insertion is __enqueue_entity ({{line 575|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/fair.c#L575}}), the pick pick_next_entity (line 4435), the floor min_vruntime (line 540). A nice-5 thread's vruntime grows 3.06 times faster than its CPU time.

Period and slice. __sched_period and sched_slice ({{lines 687 and 701|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/fair.c#L687}}); sysctl_sched_latency (line 38), sysctl_sched_min_granularity (line 59); the factor from get_update_sysctl_factor (line 159).

Preemption at the tick (check_preempt_tick, line 4355): switched out when it has run longer than its slice, or, once it has run at least min_granularity, when its vruntime is ahead of the leftmost thread's by more than a slice. At wake-up (place_entity, line 4108; check_preempt_wakeup, line 6916): the woken thread is placed at max(its own vruntime, min_vruntime - latency / 2) and preempts if the running thread is ahead of it by more than the wake-up granularity, scaled by the woken thread's weight:

// kernel/sched/fair.c, v5.10, lines 6869-6880: should the woken thread se preempt curr?
static int wakeup_preempt_entity(struct sched_entity *curr, struct sched_entity *se)
{
	s64 gran, vdiff = curr->vruntime - se->vruntime;
	if (vdiff <= 0)
		return -1;
	gran = wakeup_gran(se);
	if (vdiff > gran)
		return 1;
	return 0;
}

Groups and autogroup. With cgroups, fairness is applied per level: a container is one entity in its parent's run queue with its own weight (cpu.weight, section 9), and threads compete inside it. Desktop kernels add autogroup: each session (a terminal, say) becomes its own group, so a make -j64 in one terminal cannot starve another; the side effect is that nice only works within a session.
