Three ledgers. The kernel counts CPU time per task (utime and stime, fields 14 and 15 of /proc/PID/stat, what getrusage and time report), per cgroup (cpu.stat: usage_usec, user_usec, system_usec) and per CPU (/proc/stat). User time is your code; system time is the kernel working for you (system calls, page faults). With threads, user + system can exceed real (wall) time:



Four threads finished the same matmuls in 1.46 s instead of 2.39 s, using about the same total CPU time (user 2.52 s against 2.40 s): parallelism shortens wall time, not CPU time. "CPU 182%" means 1.82 CPUs busy on average, not 4, because only part of the program is parallel.


The per-CPU ledger (/proc/stat, in ticks of 10 ms) splits time into user, nice (user time of positively niced tasks), system, idle, iowait (idle while some I/O was outstanding: not busy, just waiting), irq, softirq and steal:




Steal is time a virtual CPU wanted to run but the hypervisor ran something else; the guest can only count it if the hypervisor provides a paravirtual steal clock ({{kernel/sched/cputime.c line 237|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/cputime.c#L237}}). Here it is 0, which does not mean nothing was stolen: this guest is not told. On cloud VMs that report it, a rising steal column is the first thing to check when the same job gets slower on the same instance type.


Waiting for a CPU, per thread measured


Utilisation says how busy a CPU was, not how long threads queued for it. The second field of /proc/PID/task/TID/schedstat does: nanoseconds spent runnable but not running ({{sched-stats doc|https://docs.kernel.org/scheduler/sched-stats.html}}). For the 4-thread matmul in a container allowed 4 CPUs on a VM that other agents were using:




The main thread and the three pool threads each ran 2.7 to 3.3 s and waited 0.11 to 0.31 s for a CPU. In section 1, the training job's main thread had waited  for a CPU in 7 s. Kernels with pressure stall information expose the same idea per cgroup as cpu.pressure ("some" = share of time at least one task waited, {{PSI doc|https://docs.kernel.org/accounting/psi.html}}); this kernel is built without it (CONFIG_PSI is not set) not run here.


Load average: not what most people think


The three numbers in uptime and /proc/loadavg are exponentially decaying averages, over about 1, 5 and 15 minutes, of the number of tasks that are runnable or in uninterruptible sleep (D state), summed over all CPUs. Every 5 seconds (LOAD_FREQ, {{include/linux/sched/loadavg.h line 20|https://github.com/torvalds/linux/blob/v5.10/include/linux/sched/loadavg.h#L20}}) the kernel computes, in fixed point with 11 fractional bits:


load = load × e + n × (1 - e),   e = exp(-5 s / 1 min) = 1884 / 2048
n
runnable tasks + tasks in uninterruptible sleep (calc_load_fold_active, {{loadavg.c line 79|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/loadavg.c#L79}}); a task going to sleep is counted as uninterruptible when its state is TASK_UNINTERRUPTIBLE without TASK_NOLOAD ({{core.c line 4467|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/core.c#L4467}})
e
EXP_1 = 1884 (line 21); EXP_5 = 2014 and EXP_15 = 2037 for the other two


Counting D-state tasks is a Linux change from the classic Unix definition, which counts runnable tasks only; it makes load reflect demand for disks as well as CPUs ({{Brendan Gregg, Linux Load Averages: Solving the Mystery, 2017|https://www.brendangregg.com/blog/2017-08-08/linux-load-averages.html}}). To see it, three processes sit in D state for 60 s without using any CPU (a vfork parent waits uninterruptibly for its child):






The 1-minute load rose by about one over the minute although the container used almost no CPU. The dashed line is what the formula predicts from the three D-state tasks alone, starting from the measured value when they began; the measured line sits slightly above it because other agents' work on the VM counts too (load average is machine-wide, not per container). Three tasks held for a full minute would add 1.9 (3 × (1 - 1/e)), not 3: the average needs about 5 minutes to settle.


For a training node
"Load 40" on a node whose CPUs show idle almost always means tasks stuck in D state: a hung NFS, Lustre or FUSE mount, or a dying disk. Check ps -eo pid,stat,wchan:30,comm | awk '$2 ~ /D/' before blaming the scheduler. To ask "are my threads short of CPU", read run-queue waiting (schedstat, or cpu.pressure where it exists) and nr_throttled, not load.
