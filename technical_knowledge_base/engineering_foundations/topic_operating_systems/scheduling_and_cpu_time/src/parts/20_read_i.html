7. Many CPUs: run queues, load balancing, affinity

ch. 10 Multiprocessor Scheduling (single queue against multi-queue, cache affinity, load imbalance, work stealing); {{sched-domains doc|https://docs.kernel.org/scheduler/sched-domains.html}}

The problem. One shared queue for all CPUs (OSTEP's SQMS) is simple and balanced but needs a lock every CPU fights over, and it bounces threads between CPUs, losing their caches. Linux uses one queue per CPU (OSTEP's MQMS) and pays instead with imbalance: one CPU's queue may hold three threads while another idles. Three mechanisms fix it:

at wake-upselect_task_rq_fair() ({{fair.c line 6697|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/fair.c#L6697}}) chooses where a waking thread goes: its previous CPU if still a good idea, the waker's CPU if they share data (wake_affine, line 5854), or an idle CPU nearby (select_idle_sibling, line 6213).
periodicallyEach CPU runs load_balance() (line 9532) over a hierarchy of scheduling domains (cores sharing a cache, then a package, then NUMA nodes), pulling threads from the busiest group to itself, more often for close levels.
when idleA CPU about to go idle first tries to pull work (newidle balancing): work stealing, in OSTEP's words.
cache hotA thread that ran within sched_migration_cost_ns (500,000 ns here) is "cache hot" and not moved if anything else can be (task_hot, line 7419).

Migrations show up per thread as se.nr_migrations in /proc/PID/sched, and the CPU a thread last ran on is the PSR column of ps (the running job's threads in section 1 were spread over CPUs 2, 3 and 4). Section 2 measured why placement matters in this VM: waking a thread on an idle CPU cost us, against about 1.5 us for a switch on the same CPU.

Affinity: telling the scheduler where a thread may run

A thread's CPU affinity is a set of CPUs it may run on (sched_setaffinity(2); taskset; os.sched_setaffinity in Python), inherited by its children. A container's --cpuset-cpus sets the same thing for every task in the cgroup (the cpuset controller). This is a different mechanism from the quota of section 9, and programs see one and not the other measured:

Under --cpus 2 everything still reports 5 CPUs and PyTorch starts 5 threads per pool; under --cpuset-cpus 0,1 affinity, nproc and PyTorch all say 2, while os.cpu_count() still says 5 (it counts the machine). Python 3.13 added os.process_cpu_count(), which follows affinity ({{os docs|https://docs.python.org/3/library/os.html#os.process_cpu_count}}); nothing standard reads the quota. So a cpuset is the one limit a program sizes itself to automatically.

A Kubernetes pod with limits.cpu: 4 lands on a 64-core node (no CPU manager policy). What does torch.get_num_threads() return inside it?

A CPU limit becomes a quota (cpu.max), which no thread-count default reads; the pod's affinity is the whole node unless the kubelet's static CPU manager pins it to exclusive cores (pods with integer CPU requests equal to limits, {{Kubernetes CPU management policies|https://kubernetes.io/docs/tasks/administer-cluster/cpu-management-policies/}}). So PyTorch starts a pool sized for the node and runs it on 4 CPUs' worth of quota: section 9 shows what that does.

Isolating CPUs not run here

For latency-critical pinned threads, the boot parameters isolcpus= (remove CPUs from load balancing) and nohz_full= (stop the scheduler tick on CPUs that run a single task) keep the kernel out of their way ({{kernel-parameters|https://docs.kernel.org/admin-guide/kernel-parameters.html}}, {{NO_HZ doc|https://docs.kernel.org/timers/no_hz.html}}); interrupts are steered separately through /proc/irq/N/smp_affinity. They need boot-time control of the host, so this VM cannot show them; they matter for trading and robotics far more than for training throughput.

8. NUMA and pinning for GPU feeding not run here

ch. 10 (cache affinity); {{NUMA memory policy doc|https://docs.kernel.org/admin-guide/mm/numa_memory_policy.html}}; {{numactl(8)|https://man7.org/linux/man-pages/man8/numactl.8.html}}

The problem. A two-socket GPU server is two computers sharing one address space: each socket (or each die on some CPUs) has its own memory controller, PCIe lanes and GPUs, and reaching the other socket's memory or devices crosses an interconnect. That is NUMA (non-uniform memory access). A process feeding GPU 3 should run on the CPUs of GPU 3's node and allocate its pinned host buffers there, or every host-to-device copy crosses sockets. This VM has a single NUMA node, so this section is from sources only; memory placement policies (mbind, interleave) belong to the sibling {{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}} page, section 14.

  • See the topology: numactl --hardware (nodes, their CPUs and memory, distances); nvidia-smi topo -m (which CPUs and NUMA node each GPU and NIC is closest to); lscpu.
  • Bind by hand: numactl --cpunodebind=1 --membind=1 python train.py runs on node 1's CPUs and allocates from its memory.
  • Bind per rank with torchrun: PyTorch 2.14.1 has torchrun --numa-binding=node ({{torch/distributed/run.py line 754|https://github.com/pytorch/pytorch/blob/v2.14.1/torch/distributed/run.py#L754}}), which binds each local rank and its threads to the CPUs of the NUMA node holding its GPU; the modes node, socket, exclusive and core-complex are documented in {{torch/numa/binding.py line 44|https://github.com/pytorch/pytorch/blob/v2.14.1/torch/numa/binding.py#L44}}, whose docstring says binding "typically results in 1-10% overall performance improvements".
  • Automatic NUMA balancing (kernel.numa_balancing): the kernel periodically unmaps pages to sample which node touches them, then moves tasks or pages to match (task_numa_fault, {{fair.c line 2626|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/fair.c#L2626}}). Helpful for unpinned services, sometimes a source of latency spikes; explicit binding makes it moot.
