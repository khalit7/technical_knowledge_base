Three ledgers: per task (utime, stime: what time reports), per cgroup (cpu.stat), per CPU (/proc/stat). User time is your code; system time is the kernel working for you (system calls, page faults). With threads, user + system can exceed wall time measured:



Four threads finished the same matmuls in 1.46 s instead of 2.39 s, with about the same CPU time (user 2.52 s against 2.40 s): parallelism shortens wall time, not CPU time. "CPU 182%" means 1.82 CPUs busy on average, not 4.


Waiting for a CPU, per thread measured


Utilisation says how busy a CPU was, not how long threads queued for it; the second field of /proc/PID/task/TID/schedstat does ({{sched-stats doc|https://docs.kernel.org/scheduler/sched-stats.html}}). For the 4-thread matmul, 4 CPUs allowed, on the shared VM, the main thread and the three pool threads each ran 2.7 to 3.3 s and waited 0.11 to 0.31 s for a CPU (raw output in the closed block). In section 1, the training job's main thread had waited  for a CPU in 7 s. Kernels with pressure stall information expose the same idea per cgroup as cpu.pressure ("some" = share of time at least one task waited, {{PSI doc|https://docs.kernel.org/accounting/psi.html}}); this kernel is built without it not run here.


Load average: runnable plus uninterruptible, machine-wide measured


The three numbers of /proc/loadavg are decaying averages (about 1, 5 and 15 minutes) of the tasks runnable or in uninterruptible sleep (D state), over all CPUs: a Linux change from classic Unix, so that load reflects demand for disks too ({{Brendan Gregg, Linux Load Averages: Solving the Mystery, 2017|https://www.brendangregg.com/blog/2017-08-08/linux-load-averages.html}}). Here three processes sit in D state for 60 s using no CPU (a vfork parent waits for its child). Predict how far the 1-minute load rises:


Three tasks using no CPU still raise the load


The 1-minute load rose by about one over the minute although the container used almost no CPU. The dashed line is the kernel's formula fed with the three tasks alone; the measured line sits above it because other agents' work counts too (load is machine-wide, not per container). Every 5 seconds, in fixed point with 11 fractional bits:


load = load × e + n × (1 - e),   e = exp(-5 s / 1 min) = 1884 / 2048
n
runnable tasks + tasks in uninterruptible sleep
e
EXP_1 = 1884; EXP_5 = 2014 and EXP_15 = 2037 for the other two


Three tasks held for a full minute would add 1.9 (3 × (1 - 1/e)), not 3: the average needs about 5 minutes to settle.


For a training node
"Load 40" on a node whose CPUs show idle almost always means tasks stuck in D state: a hung NFS, Lustre or FUSE mount, or a dying disk. Check ps -eo pid,stat,wchan:30,comm | awk '$2 ~ /D/' before blaming the scheduler. To ask "are my threads short of CPU", read run-queue waiting (schedstat, or cpu.pressure where it exists) and nr_throttled, not load.


cat /proc/loadavg; vmstat 1   # r = runnable, b = blocked (D), us sy id wa st


cat /proc/PID/task/*/schedstat   # on-CPU ns, waiting ns, timeslices, per thread


Where the CPU goes: which tool answers which question not run here


Accounting says how much CPU a job used; a profiler says on what. A sampling profiler records running stacks many times a second, so it sees only time on a CPU: waiting for one (run queue, throttling), for I/O or for a lock is invisible to it. Match the question to the tool:

The per-CPU ledger, steal time, and the load formula in the source (depth)




Per task: utime and stime are fields 14 and 15 of /proc/PID/stat; per cgroup, cpu.stat has usage_usec, user_usec and system_usec. The per-CPU ledger (/proc/stat, in ticks of 10 ms) splits time into user, nice (user time of positively niced tasks), system, idle, iowait (idle while some I/O was outstanding: not busy, just waiting), irq, softirq and steal:




Steal is time a virtual CPU wanted to run but the hypervisor ran something else; the guest can only count it if the hypervisor provides a paravirtual steal clock ({{kernel/sched/cputime.c line 237|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/cputime.c#L237}}). Here it is 0, which does not mean nothing was stolen: this guest is not told. On cloud VMs that report it, a rising steal column is the first thing to check when the same job gets slower on the same instance type. CONFIG_PSI is not set on this kernel.


The load update runs every LOAD_FREQ = 5 s ({{include/linux/sched/loadavg.h line 20|https://github.com/torvalds/linux/blob/v5.10/include/linux/sched/loadavg.h#L20}}; EXP_1 at line 21); n is folded by calc_load_fold_active ({{loadavg.c line 79|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/loadavg.c#L79}}); a task going to sleep counts as uninterruptible when its state is TASK_UNINTERRUPTIBLE without TASK_NOLOAD ({{core.c line 4467|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/core.c#L4467}}).
