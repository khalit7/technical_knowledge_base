2. The context switch: what is saved and what it costs

ch. 6 Limited Direct Execution (6.3 Saving and Restoring Context); ch. 10 (cache affinity)

To run another thread, the CPU's state for the current one must be put away and the other's brought back, so that each resumes as if it had never stopped. On Linux v5.10 (arm64) that is context_switch() ({{kernel/sched/core.c line 3728|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/core.c#L3728}}); step through what moves where:

A switch is a pick, a page-table pointer and about twenty instructions of register swap

Thread A blue, thread B green; the lit box is what changes at each step. source: v5.10 __schedule, switch_mm_irqs_off (core.c line 3765), switch_to (line 3779), cpu_switch_to ({{arch/arm64/kernel/entry.S line 892|https://github.com/torvalds/linux/blob/v5.10/arch/arm64/kernel/entry.S#L892}}). The address-space step is skipped between threads of one process; on arm64 the ASID means no TLB flush (the sibling {{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}} page, section 3).

What it costs here measured

Two processes on one CPU pass a byte through two pipes 200,000 times (lmbench's method, as on the root); then two threads with a futex (the wait-and-wake primitive under every lock); then hand-offs across two CPUs. Five runs each, VM load about 5.

A switch on one CPU is microseconds; waking a thread on another CPU is tens

A switch between two processes on one CPU costs us (the root measured 1.33 us), between two threads no less ( us): with ASIDs the address space is nearly free, and the cost is the kernel's sleep-and-wake path. A cache line crosses CPUs in ns, but waking a sleeping thread on another CPU took us when that CPU was idle, 29 times longer than a switch ( us when a low-priority loop kept it awake): an inter-processor interrupt, and an idle virtual CPU woken by the hypervisor. That is this VM, not bare metal (why: section 5 of {{Virtualization and the GPU driver stack|n:3f05c17b0d0d8158b029e9b2ba2e161b}}).

The indirect cost is cold caches (the new thread finds them full of someone else's data). Long slices keep it small: refilling 4 MiB at an illustrative 50 GB/s takes about 84 us, under 1% of a 9 ms slice (section 4: 9 ms each for two tasks). Our measurement in this VM was inconclusive (closed block below).

The Debug lab's "Too many threads" case ran 5 PyTorch threads on a 1-CPU quota. Which counter should explode?

A voluntary switch happens when the thread blocks; an involuntary one when the kernel takes the CPU away (tick or wake-up preemption, or throttling). Five busy threads fighting for one CPU's worth of quota are preempted constantly: the root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} case "Too many threads for the CPUs you have" recorded 3,571 involuntary switches with 5 threads against 16 with one, for the same arithmetic.

When it bites in ML. Not through one switch (a step is milliseconds) but through numbers (hundreds of threads on a few cores, section 11), hand-offs (a DataLoader batch costs at least two wake-ups: fine per batch, ruinous per sample) and busy waiting: GNU OpenMP's idle threads spin before sleeping unless OMP_WAIT_POLICY=passive ({{libgomp docs|https://gcc.gnu.org/onlinedocs/libgomp/GOMP_005fSPINCOUNT.html}}), right on a dedicated node, wrong under a CPU quota.

The switch in the source, sched_yield, and the cache-pollution measurement (depth)

When a thread enters the kernel, the hardware and the entry code have already saved its user registers on that thread's own kernel stack. __switch_to() hands over the floating-point and SIMD registers lazily ({{arch/arm64/kernel/process.c line 552|https://github.com/torvalds/linux/blob/v5.10/arch/arm64/kernel/process.c#L552}}), then cpu_switch_to runs. Its final ret returns into the other task's kernel stack, which later returns to that task's user code.

// arch/arm64/kernel/entry.S, v5.10, lines 892-905 (abridged)
SYM_FUNC_START(cpu_switch_to)
	mov	x10, #THREAD_CPU_CONTEXT
	add	x8, x0, x10              // x0 = previous task
	mov	x9, sp
	stp	x19, x20, [x8], #16      // store callee-saved registers
	...
	stp	x29, x9, [x8], #16       // frame pointer and stack pointer
	str	lr, [x8]                 // where to resume
	add	x8, x1, x10              // x1 = next task
	ldp	x19, x20, [x8], #16      // restore callee-saved registers ...

sched_yield() is only a hint in CFS (it marks the caller to be skipped once, {{fair.c line 7167|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/fair.c#L7167}}): of the calls actually switched.
