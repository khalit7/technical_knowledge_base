7. Python's own layer: pymalloc, free lists, and memory that does not come back

ch. 17 (segregated lists, again)

Why Python has its own allocator. A Python program creates and destroys small objects constantly: every integer result, every tuple, every frame. CPython routes requests of 512 bytes or less to pymalloc: "a pymalloc allocator optimized for small objects (smaller or equal to 512 bytes) with a short lifetime. It uses memory mappings called arenas with a fixed size of either 256 KiB on 32-bit platforms or 1 MiB on 64-bit platforms" ({{Python 3.11 memory management|https://docs.python.org/3.11/c-api/memory.html#the-pymalloc-allocator}}). Larger requests go to malloc.

Three levels ({{Objects/obmalloc.c at v3.11.2|https://github.com/python/cpython/blob/v3.11.2/Objects/obmalloc.c#L879}}): arenas of 1 MiB got with mmap (ARENA_BITS 20, line 958; _PyObject_ArenaMmap, line 149), cut into pools of 16 KiB (POOL_BITS 14, line 973), each pool serving one size class in steps of 16 bytes (ALIGNMENT 16, line 879) up to 512 (SMALL_REQUEST_THRESHOLD, line 904). A 1-element tuple (48 bytes) and an int (28 bytes, class 32) come from different pools. Pymalloc returns an arena to the kernel only when every object in all 64 of its pools is dead. On top of that, several types keep free lists of recently freed objects for instant reuse, and small integers from -5 to 256 are preallocated once.

Measured: 2,000,000 one-element tuples of fresh ints (about 160 MB of objects), then keep every 1,000th and drop the rest, then drop those too.



measured here src/exp/pymalloc_demo.py, run as is and with PYTHONMALLOC=malloc (which sends every object to glibc). Arena counts from sys._debugmallocstats().


Two lessons. With 2,000 survivors (0.1% of the objects) pymalloc still held all 158 arenas, 163.1 MiB: one live object pins its pool and therefore its arena, the Python version of section 5's pinned pages. This is why the memory of a long-running Python process rarely drops after del of a big structure if anything from it survives (a cached element, a reference in a log, an exception traceback). And when everything died, pymalloc gave its arenas back at once (12.3 MiB), while glibc kept 222.3 MiB until malloc_trim(0) (9.3 MiB): its freed chunks sat below a live chunk near the top of the heap, which blocks trimming.


Seeing it. tracemalloc records the Python line that allocated every block still alive: tracemalloc.start(25), then tracemalloc.take_snapshot().statistics("lineno")[:10], or compare two snapshots with snapshot2.compare_to(snapshot1, "lineno") to find what grows between two points of a training loop ({{tracemalloc|https://docs.python.org/3.11/library/tracemalloc.html}}). It sees only memory allocated through Python's allocators, which includes NumPy array data (NumPy reports it to tracemalloc) but not memory allocated inside other C libraries. For those, compare RSS with what tracemalloc reports: the gap is native memory or allocator overhead.


In ML work. Python objects matter most in DataLoader workers: a dataset held as millions of Python objects (lists of strings, dicts of ints) is touched by reference counting on every access, which copies the shared pages after fork into every worker. The root measured 7,880 copied pages for 1M Python ints against 38 to 67 for a NumPy array of the same data, and the {{virtual memory page|n:3f05c17b0d0d81a48892cea154ce950b}} owns copy-on-write in depth. The fix is the same one: keep large datasets in NumPy arrays, Arrow buffers or memory-mapped files, not in Python objects.






8. NumPy and PyTorch on the CPU: who calls whom


NumPy allocates array data with malloc, plus two tricks ({{numpy/_core/src/multiarray/alloc.c at v2.4.6|https://github.com/numpy/numpy/blob/v2.4.6/numpy/_core/src/multiarray/alloc.c#L45}}): a small cache of freed buffers under 1,024 bytes, 7 per size (NBUCKETS and NCACHE, lines 45 to 47), and, for arrays of 4 MiB or more on Linux, madvise(MADV_HUGEPAGE) on the data (indicate_hugepages, lines 99 to 112), so with THP in "madvise" mode large arrays may get 2 MiB pages.


PyTorch's CPU tensors go through c10::alloc_cpu ({{c10/core/impl/alloc_cpu.cpp at v2.14.1|https://github.com/pytorch/pytorch/blob/v2.14.1/c10/core/impl/alloc_cpu.cpp#L92}}). Which allocator that is depends on the build: mi_malloc_aligned when PyTorch is built with mimalloc (lines 111 to 117), which its CMakeLists turns on "on Windows and AArch64" Linux (lines 451 to 468 of {{CMakeLists.txt|https://github.com/pytorch/pytorch/blob/v2.14.1/CMakeLists.txt#L451}}); otherwise posix_memalign from glibc (line 126) with 64-byte alignment, "enough for computation up to AVX512" (c10/core/alignment.h, line 15). On Linux, THP_MEM_ALLOC_ENABLE=1 makes buffers of 2 MiB or more page-aligned and madvised for huge pages (lines 58 to 70 and 136 to 147). So the same Python code allocates tensors with glibc on an x86-64 Linux box and with mimalloc on a Graviton or Grace host, and LD_PRELOAD=libjemalloc.so changes tensor allocation only on the first.


The root's 1 GiB reservation, explained. Traced here, the first CPU tensor in a process makes mimalloc reserve 1 GiB of address space and mark it for huge pages:




measured here strace -s 200 -e trace=mmap,munmap,madvise,brk,write python src/exp/torch_cpu.py; each marker prints RSS before the action; thread-stack mmaps from the first multi-threaded fill are cut. The root's gdb stack (its src/trace/raw/hugepage_stack.txt) shows the caller is mimalloc inside libc10.so.


The source agrees: the vendored mimalloc ({{commit 30ac9d5, version 2.4.1|https://github.com/microsoft/mimalloc/blob/30ac9d56b8b9ea57ae84bc8ef17ef39000da08fe/src/options.c#L69}}) reserves arenas "N KiB at a time (=1GiB)" (MI_DEFAULT_ARENA_RESERVE, src/options.c lines 69 to 75 and 152), with MAP_NORESERVE, and calls madvise(MADV_HUGEPAGE) on it (src/prim/unix/prim.c lines 391 to 400). It costs nothing until touched (overcommit; the {{virtual memory page|n:3f05c17b0d0d81a48892cea154ce950b}}). Then: a 64 MiB tensor made no system call at all, it was carved from the reservation and its pages faulted in on first touch (RSS 228.1 to 294.1 MiB), and after del RSS stayed at 294.1 MiB to the end: mimalloc keeps freed memory for reuse. NumPy's 64 MiB array, by contrast, took its own mmap (above glibc's threshold), got its huge-page hint, and went back with munmap on del.


Pinned host memory from source; not run here. pin_memory() and DataLoader(pin_memory=True) allocate page-locked host memory through PyTorch's CachingHostAllocator, which calls cudaHostAlloc ({{CachingHostAllocator.cpp line 77 at v2.14.1|https://github.com/pytorch/pytorch/blob/v2.14.1/aten/src/ATen/cuda/CachingHostAllocator.cpp#L77}}), caches freed blocks like its GPU counterpart, and rounds each request up to the next power of two "to improve reuse" ({{CachingHostAllocator.h lines 339 to 347|https://github.com/pytorch/pytorch/blob/v2.14.1/aten/src/ATen/core/CachingHostAllocator.h#L339}}; no upper limit on the rounding by default, pinned_max_round_threshold in AllocatorConfig.h line 360). A 600 MB pinned buffer therefore takes 1 GiB of locked RAM, which the kernel can never swap or reclaim. Why pinning exists and what it costs the kernel belongs to the {{virtual memory page|n:3f05c17b0d0d81a48892cea154ce950b}}.
