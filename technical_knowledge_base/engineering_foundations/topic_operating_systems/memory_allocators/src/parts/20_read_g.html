8. NumPy and PyTorch on the CPU: who calls whom

NumPy allocates array data with malloc, plus two tricks ({{numpy/_core/src/multiarray/alloc.c at v2.4.6|https://github.com/numpy/numpy/blob/v2.4.6/numpy/_core/src/multiarray/alloc.c#L45}}): a small cache of freed buffers under 1,024 bytes, 7 per size (NBUCKETS and NCACHE, lines 45 to 47), and, for arrays of 4 MiB or more on Linux, madvise(MADV_HUGEPAGE) on the data (indicate_hugepages, lines 99 to 112), so with THP in "madvise" mode large arrays may get 2 MiB pages.

PyTorch's CPU tensors go through c10::alloc_cpu ({{c10/core/impl/alloc_cpu.cpp at v2.14.1|https://github.com/pytorch/pytorch/blob/v2.14.1/c10/core/impl/alloc_cpu.cpp#L92}}), and which allocator that is depends on the build: mi_malloc_aligned when PyTorch is built with mimalloc (lines 111 to 117), which its CMakeLists turns on "on Windows and AArch64" Linux (lines 451 to 468 of {{CMakeLists.txt|https://github.com/pytorch/pytorch/blob/v2.14.1/CMakeLists.txt#L451}}); otherwise posix_memalign from glibc (line 126) with 64-byte alignment, "enough for computation up to AVX512" (c10/core/alignment.h, line 15). On Linux, THP_MEM_ALLOC_ENABLE=1 makes buffers of 2 MiB or more page-aligned and madvised for huge pages (lines 58 to 70 and 136 to 147). So the same Python code allocates tensors with glibc on an x86-64 Linux box and with mimalloc on a Graviton or Grace host, and LD_PRELOAD=libjemalloc.so changes tensor allocation only on the first.

The root's 1 GiB reservation, explained. Traced here, the first CPU tensor in a process makes mimalloc reserve 1 GiB of address space and mark it for huge pages (the highlighted mmap and madvise lines of the trace).

The reservation costs nothing until touched (overcommit; the {{virtual memory page|n:3f05c17b0d0d81a48892cea154ce950b}}). A 64 MiB tensor then made no system call at all: it was carved from the reservation and its pages faulted in on first touch (RSS 228.1 to 294.1 MiB), and after del RSS stayed at 294.1 MiB to the end: mimalloc keeps freed memory for reuse. NumPy's 64 MiB array, by contrast, took its own mmap (above glibc's threshold), got its huge-page hint, and went back with munmap on del.


The same in mimalloc's source (provenance)
The vendored mimalloc ({{commit 30ac9d5, version 2.4.1|https://github.com/microsoft/mimalloc/blob/30ac9d56b8b9ea57ae84bc8ef17ef39000da08fe/src/options.c#L69}}) reserves arenas "N KiB at a time (=1GiB)" (MI_DEFAULT_ARENA_RESERVE, src/options.c lines 69 to 75 and 152), with MAP_NORESERVE, and calls madvise(MADV_HUGEPAGE) on it (src/prim/unix/prim.c lines 391 to 400).


Pinned host memory from source; not run here. pin_memory() and DataLoader(pin_memory=True) allocate page-locked host memory through PyTorch's CachingHostAllocator, which calls cudaHostAlloc ({{CachingHostAllocator.cpp line 77 at v2.14.1|https://github.com/pytorch/pytorch/blob/v2.14.1/aten/src/ATen/cuda/CachingHostAllocator.cpp#L77}}), caches freed blocks like its GPU counterpart, and rounds each request up to the next power of two "to improve reuse" ({{CachingHostAllocator.h lines 339 to 347|https://github.com/pytorch/pytorch/blob/v2.14.1/aten/src/ATen/core/CachingHostAllocator.h#L339}}; no upper limit on the rounding by default, pinned_max_round_threshold in AllocatorConfig.h line 360). A 600 MB pinned buffer therefore takes 1 GiB of locked RAM, which the kernel can never swap or reclaim. Why pinning exists and what it costs the kernel belongs to the {{virtual memory page|n:3f05c17b0d0d81a48892cea154ce950b}}.
