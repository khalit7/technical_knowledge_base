7. Python's own layer: pymalloc, reference counts, and memory that does not come back

ch. 17 (segregated lists, again)

Why Python has its own allocator. A Python program creates and destroys small objects constantly: every integer result, every tuple, every frame. CPython routes requests of 512 bytes or less to pymalloc: "a pymalloc allocator optimized for small objects (smaller or equal to 512 bytes) with a short lifetime. It uses memory mappings called arenas with a fixed size of either 256 KiB on 32-bit platforms or 1 MiB on 64-bit platforms" ({{Python 3.11 memory management|https://docs.python.org/3.11/c-api/memory.html#the-pymalloc-allocator}}). Larger requests go to malloc.

One live object keeps its pool, and its pool keeps the whole 1 MiB arena

Three levels ({{Objects/obmalloc.c at v3.11.2|https://github.com/python/cpython/blob/v3.11.2/Objects/obmalloc.c#L879}}): arenas of 1 MiB got with mmap (ARENA_BITS 20, line 958; _PyObject_ArenaMmap, line 149), cut into 64 pools of 16 KiB (POOL_BITS 14, line 973), each pool serving one size class in steps of 16 bytes (ALIGNMENT 16, line 879) up to 512 (SMALL_REQUEST_THRESHOLD, line 904). A 1-element tuple (48 bytes) and an int (28 bytes, class 32) come from different pools. An arena goes back to the kernel only when every object in all 64 pools is dead. Pool contents drawn illustrative; the sizes are the source's.

On top of that, several types keep free lists of recently freed objects for instant reuse, and small integers from -5 to 256 are preallocated once. Measured: 2,000,000 one-element tuples of fresh ints (about 160 MB of objects), then keep every 1,000th and drop the rest, then drop those too.



measured here src/exp/pymalloc_demo.py, run as is and with PYTHONMALLOC=malloc (which sends every object to glibc). Arena counts from sys._debugmallocstats().


With 2,000 survivors (0.1% of the objects) pymalloc still held all 158 arenas, 163.1 MiB: the Python version of section 5's pinned pages. This is why a long-running Python process rarely shrinks after del of a big structure if anything from it survives (a cached element, a reference in a log, an exception traceback). When everything died, pymalloc gave its arenas back at once (12.3 MiB), while glibc kept 222.3 MiB until malloc_trim(0) (9.3 MiB): its freed chunks sat below a live chunk near the top of the heap, which blocks trimming.


When an object is freed: reference counts at once, cycles later


CPython frees an object the moment its reference count reaches zero: the block goes straight back to its pymalloc pool (or to malloc). Objects that refer to each other in a cycle never reach zero, so a separate cycle collector finds them; it runs when allocations minus deallocations of tracked objects pass a threshold (gc.set_threshold, {{gc module|https://docs.python.org/3.11/library/gc.html#gc.set_threshold}}). Until it runs, everything a cycle holds stays allocated: payloads, NumPy buffers, CPU or GPU tensors.


The same 2,000 records: freed at once without a cycle, held until the collector runs with one




measured on Apple M1 Pro, macOS, Python 3.11.9 src/exp/gc_cycles.py: each record owns a 10,000-byte payload; bars are the most memory tracemalloc saw still allocated after a record was dropped. No cycle: 0.2 KiB. In two-object cycles with the collector on (default threshold 700, 10, 10): up to 6.7 MiB waits for a collection. With gc.disable(): 38.5 MiB (2,000 × 2 × 10,000 bytes = 38.1 MiB of payloads, plus the objects) until gc.collect() found 4,000 objects and freed them. Python 3.14.8 reports a threshold of 2000, 10, 10 and held up to 19.2 MiB in the same cycle run: what waits for the collector depends on the version.


In ML work. Python objects matter most in DataLoader workers: a dataset held as millions of Python objects (lists of strings, dicts of ints) is touched by reference counting on every access, which copies the shared pages after fork into every worker. The root measured 7,880 copied pages for 1M Python ints against 38 to 67 for a NumPy array of the same data; the {{virtual memory page|n:3f05c17b0d0d81a48892cea154ce950b}} owns copy-on-write. Keep large datasets in NumPy arrays, Arrow buffers or memory-mapped files, not in Python objects. The {{gc.freeze|https://docs.python.org/3.11/library/gc.html#gc.freeze}} recipe (gc.disable() early in the parent, gc.freeze() right before fork(), gc.enable() in the child) stops the collector from touching the parent's objects, "avoiding unnecessary copy-on-write in child processes", but reference counting still writes. And break cycles that hold tensors (a stored exception with its traceback, an object that keeps a closure over itself), or that memory waits for the collector.
