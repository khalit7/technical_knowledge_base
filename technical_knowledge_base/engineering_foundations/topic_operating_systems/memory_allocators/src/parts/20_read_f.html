6. jemalloc, tcmalloc, mimalloc: the same job, other designs

ch. 17 (segregated lists), beyond OSTEP

All three replace glibc's one-heap-with-bins design by size classes in their own runs of pages: every object of a given class lives in a block of memory that holds only that class, so finding a free object is a pop from a short list and fragmentation is bounded per class. They differ in how threads are kept apart and in when memory goes back to the kernel.

Switching needs no code change. malloc is resolved by the dynamic linker, so preloading another library replaces it for the whole process: LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2 python train.py (the path differs per distribution and architecture; here it is under aarch64-linux-gnu). PyTorch's {{performance tuning guide|https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html}} recommends exactly this for CPU workloads ("Jemalloc or TCMalloc can get better performance by reusing memory as much as possible"). Check it took: grep -c jemalloc /proc/<pid>/maps is nonzero. Child processes inherit the environment, so DataLoader workers get it too. Three caveats: memory allocated by one allocator must be freed by the same one (preloading guarantees that; loading an allocator later with dlopen does not); a library with its own allocator built in is unaffected (section 8: this wheel's tensors); and container images often lack the library, so a missing path silently does nothing but print a loader warning.

Cost of one malloc and free, measured. Nanoseconds per pair, one thread, best of 5 runs:

measured here src/exp/bench.c. "Pairs": malloc, touch one byte, free, repeated, the allocator's fast path. "Batch": 1,000 mallocs then 1,000 frees. Two-thread figures are in src/raw/bench.txt. Microbenchmarks flatter the fast paths; real code mixes sizes and threads.

Read across a row, not down: each allocator has a size where it falls off a cliff. glibc's is the 4 KiB batch (the trim churn of section 3); jemalloc's and mimalloc's are the large sizes, which they hand to the kernel with their own mappings (mimalloc's 1 MiB pair costs 789.3 ns); tcmalloc's fast path is the quickest at every small size (5.4 ns).

The running job under four allocators. The root's job, 40 steps with two DataLoader workers, three runs each:

measured here src/exp/job_alloc.sh and job_wrap.py: peak and final RSS of the main process from /proc/self/status, wall time from start to exit (including import torch).

The differences are a few MiB and within the run-to-run spread of time. That is the honest result for this job: most of its memory is the PyTorch and NumPy libraries themselves and the tensors, and on this arm64 wheel the tensors do not go through malloc at all (section 8), so swapping malloc changes only the Python and NumPy side. Allocator choice matters for processes that allocate and free a lot of native memory from many threads for a long time: data loading with decoding, tokenization services, inference servers, and CPU training on x86-64, where tensors do use malloc.
