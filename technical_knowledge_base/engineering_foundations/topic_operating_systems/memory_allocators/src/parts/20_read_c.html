1. Free space from zero: headers, free lists, splitting, coalescing

ch. 17 Free-Space Management

The problem. An allocator owns a region of bytes (the heap) and answers two calls: malloc(n) returns the address of at least n free bytes, free(p) gives them back. Requests come in any size and any order, and once the allocator hands out an address it can never move that block, because the program holds raw pointers into it. Everything below follows from those two facts.

The header. free(p) passes only the address, not the size, so the allocator writes a small header just before every block it hands out, holding at least the size. OSTEP's example header has a size and a "magic" number used to catch corruption; glibc's holds the size and three flag bits in 8 bytes (section 3).

The free list, stored in the free space itself. Free regions are linked into a free list, and the links live inside the free regions (there is nowhere else to put them): each free chunk starts with its size and a pointer to the next free chunk. A fresh heap is one free chunk.

Splitting and coalescing. When a request is smaller than the chunk chosen for it, the allocator splits it: the front goes to the program, the rest stays on the list. When a chunk is freed next to another free chunk, a good allocator coalesces them into one, otherwise the heap fills with free slivers too small for anything.

Fragmentation, the two kinds. External fragmentation: free memory exists but in pieces, so a request fails (or the allocator grows the heap) although the total free is enough. Internal fragmentation: a block handed out is larger than what was asked for (rounding, size classes, headers), and the excess is wasted inside it. The classic survey measures it as the memory the allocator uses at its peak against the peak of live data ({{Wilson et al. 1995|https://www.cs.hmc.edu/~oneill/gc-library/Wilson-Alloc-Survey-1995.pdf}}); this page uses the same idea with RSS against live bytes.

Which free chunk to pick. Best fit takes the smallest chunk that fits (little waste, but a full search, and it leaves tiny leftovers); worst fit takes the largest (leaves big leftovers, full search, fragments badly in practice); first fit takes the first that fits (fast, but the front of the list fills with small pieces); next fit continues from where the last search stopped. Keeping the list sorted by address makes coalescing cheap; sorting by size turns first fit into best or worst fit.

Predict: a 100-byte heap, ten requests of 10 bytes (it is now full), then free every other one. 50 bytes are free. Can a request for 15 bytes succeed, with coalescing on?
No. The five free pieces are 10 bytes each and none are next to each other, so coalescing has nothing to join: 50 bytes free, largest piece 10. That is external fragmentation, and no search policy fixes it, because a C allocator cannot move live blocks to close the gaps (a compacting garbage collector can; malloc cannot). Better than one list: segregated lists and size classes. Most real programs allocate a few sizes over and over. A segregated list allocator keeps a separate list per size class (16, 32, 48, ... bytes), so a request is a pop from the right list with no search, and objects of one size sit together. The kernel's own version is the slab allocator (Bonwick, {{USENIX 1994|https://www.usenix.org/legacy/publications/library/proceedings/bos94/full_papers/bonwick.a}}): a cache per object type (a task_struct, an inode), each cache made of slabs of pages pre-cut into objects. A task_struct, the kernel's record of one thread, is 3,712 bytes, one per slab page; dentries (cached path components) are 200 bytes, 20 per page. The nonzero "tunables" columns are printed only by the older SLAB implementation (SLUB, the default in most distribution kernels, prints zeros), so this linuxkit kernel uses SLAB: an inference from the format, not checked against its config.


Buddy allocation. For runs of whole pages the kernel uses a buddy allocator: free memory is kept in blocks of 2k pages (order k); a request takes the smallest order that fits, splitting a bigger block into two "buddies" as needed; when a block is freed and its buddy is free too, they merge back. Coalescing is a cheap address calculation, at the price of internal fragmentation (a 9-page request takes 16). This kernel's free blocks per order, 0 (4 KiB) to 10 (4 MiB):

Each column is the number of free blocks of that order; a huge page (2 MiB, order 9) can be found only while order-9 or order-10 blocks remain, which is why huge pages get harder to find on a long-running, fragmented machine (the {{virtual memory page|n:3f05c17b0d0d81a48892cea154ce950b}} owns THP).

What a request really costs in glibc. A chunk is the request plus an 8-byte size field, rounded up to a multiple of 16, at least 32 bytes: request2size (malloc.c line 1326, {{glibc 2.36|https://sourceware.org/git/?p=glibc.git;a=blob;f=malloc/malloc.c;hb=refs/tags/glibc-2.36#l1326}}). Measured with two back-to-back mallocs, whose distance is the chunk size:




measured here src/exp/sizes.c. Usable is what malloc_usable_size reports; the stride is the chunk size. Formula: chunk = max(32, (request + 8 + 15) rounded down to a multiple of 16); a 1-byte request costs 32 bytes, a 25-byte one 48. Next to a 256-byte request the 8-byte header is 3% overhead; next to a 16-byte one it is half the chunk, which is why allocating millions of tiny objects one by one is expensive in memory as well as time.


The bugs. C trusts the program completely, and each mistake corrupts the allocator's own data, often far from where it happened:


    

  • Leak: memory never freed. Harmless in a short process, fatal in a server or a long training run.
    • 

  • Use after free: writing through a pointer after free, into a chunk that may already belong to someone else or whose first bytes now hold the free list's links.
    • 

  • Double free: glibc catches the common case and aborts with free(): double free detected in tcache 2.
    • 

  • Overflow: writing past the end tramples the next chunk's header; glibc notices later with messages such as malloc(): corrupted top size.
    •
