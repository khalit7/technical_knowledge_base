The idea in one screen

An allocator buys memory from the kernel (or the CUDA driver) rarely and in big pieces, and hands it out in small pieces often; what you free stays with the allocator and goes back only when a whole page, arena or segment is empty, so a process's RSS measures what its allocators hold, not what it uses, and free memory in the wrong-shaped pieces is fragmentation.

Allocator
user-space code that gets big regions from the kernel and cuts them into the blocks malloc (or torch.empty) returns.
Chunk, bin
one piece handed out, with a header saying its size; a bin is a list of free chunks of one size range.
Size class
a fixed size (16, 32, 48 ... bytes) that requests are rounded up to, so blocks of one class can share a page.
Internal, external fragmentation
waste inside handed-out blocks (rounding); free memory in pieces too small or in the wrong place for the next request.
Arena
one independent heap; glibc and pymalloc both use the word, for different things.
RSS
resident set size: the pages of the process actually in RAM, live data or not.
Segment (CUDA)
a region the caching allocator got from cudaMalloc; tensors are blocks cut from it.

The running job meets every layer. In the {{root's training job|n:3f05c17b0d0d81c5a97ce991644af140}} (a 256-128-10 MLP on 8 MiB of memory-mapped data, two DataLoader workers), Python objects go through pymalloc, NumPy batches through glibc's malloc, weights and activations through mimalloc inside libc10.so (the 1 GiB reservation the root's {{Syscall tracer|n:3f05c17b0d0d81c5a97ce991644af140}} tab found), and its threads get their own glibc arenas (the 64 MiB reservations of section 4). On a GPU the tensors would go through the caching allocator.

Where everything was measured (provenance)

Measured in Docker Desktop's Linux VM (Linux 5.10.104-linuxkit, arm64, 4 KiB pages, 5 CPUs; glibc 2.36, Python 3.11.2, torch 2.14.1+cpu, NumPy 2.4.6; jemalloc 5.3.0, gperftools tcmalloc 2.10, mimalloc 2.0.9 from Debian 12), image kb-os-alloc:1, 2026-10-05; scripts and raw outputs in src/. Each container was capped at 1 or 2 CPUs and 1,500 MiB, on a VM shared with other experiments, so times carry some noise; repeated runs are shown where it matters. The cycle-collector run (section 7) is on an Apple M1 Pro, macOS, 2026-10-24. A trap every C benchmark here avoids: the root page's first strace of malloc sizes showed no calls at all, because gcc -O2 removed the malloc, memset and free as dead code; the buffer must escape (into a global, or a volatile sink) for the calls to happen.
