In one screen: who hands out your memory

The kernel gives a process memory in whole pages (4 KiB here), and only through system calls that cost hundreds of nanoseconds. A training job asks for memory millions of times: a 32-byte Python tuple, a 600-byte string, a 1 MiB NumPy batch, a 64 MiB tensor, a 300 MiB activation on the GPU. In between sits a stack of allocators, user-space libraries that get big regions from the kernel rarely, cut them into pieces quickly, and keep freed pieces to hand out again. This page follows the {{root's running training job|n:3f05c17b0d0d81c5a97ce991644af140}} down that stack, measures each layer on a real Linux kernel, and reads the source where it explains a number.

the kernel: brk, mmap, munmap, madvisewhole pages, mapped on first touch; the kernel's own allocators (buddy, slab) underneath. Pages, faults, THP and the OOM killer belong to the {{virtual memory page|n:3f05c17b0d0d81a48892cea154ce950b}}
free() rarely gives memory back. Freeing 98% of 400,000 small blocks left resident memory (RSS) at 110,524 KiB for 1,562 KiB of live data under glibc; malloc_trim(0) brought it to 29,404 KiB. RSS is not live data (section 5).
One live object pins a page, or an arena. The 6,250 surviving 272-byte chunks still pinned about 24 MiB of pages after the trim; 2,000 surviving Python tuples kept all 158 of CPython's 1 MiB arenas (sections 5 and 7).
Free one big block and the next ones change path. glibc serves a 1 MiB request with its own mmap, but freeing it raises the threshold, and the same request then comes from the heap and stays resident (section 3, traced).
No allocator wins everything. On one data-loader-like workload, the allocator with the least memory was 4 times slower, and the fastest held the most (section 6, measured). Measure yours.
On the GPU, "reserved" is not "allocated". PyTorch caches freed GPU blocks; when tensor sizes vary, free memory ends up in pieces no request fits, and you get "out of memory" with gigabytes free. expandable_segments:True is the fix (section 9, simulated from source).

Where the running job meets each layer. The root's job (a 256-128-10 MLP on 8 MiB of memory-mapped data, two DataLoader workers) touches all of them: its Python objects and the DataLoader's bookkeeping go through pymalloc; each batch NumPy builds goes through glibc's malloc; the model's weights and every activation go through mimalloc inside libc10.so, which is why building the model made the 1 GiB address-space reservation the root's {{Syscall tracer|n:3f05c17b0d0d81c5a97ce991644af140}} tab found; its threads (OpenMP, the DataLoader's) get their own glibc arenas, the 64 MiB reservations the root's section 5 saw in the memory map. On a GPU, the same tensors would go through the caching allocator. Section 6 runs the job under four allocators.
