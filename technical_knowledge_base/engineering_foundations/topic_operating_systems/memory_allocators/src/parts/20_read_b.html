1. Free space from zero: headers, free lists, splitting, coalescing

ch. 17 Free-Space Management

The problem. An allocator owns a region of bytes (the heap) and answers malloc(n) with the address of at least n free bytes and free(p) by taking them back. Requests come in any size and order, and a block can never move once handed out, because the program holds raw pointers into it.

The header and the free list. free(p) passes only the address, so the allocator writes a header just before every block, holding at least the size (OSTEP's example adds a "magic" number to catch corruption; glibc's header is the size and three flag bits in 8 bytes, section 3). Free regions are linked into a free list whose links live inside the free regions themselves: there is nowhere else to put them. A fresh heap is one free chunk.

Splitting and coalescing. A request smaller than the chosen chunk splits it: the front goes to the program, the rest stays on the list. A freed chunk next to another free chunk is coalesced with it into one; without that the heap fills with free slivers too small for anything.

Fragmentation, the two kinds. External fragmentation: enough memory is free in total, but in pieces, so a request fails (or the heap grows). Internal fragmentation: a block is larger than asked for (rounding, size classes, headers), and the excess is wasted inside it. The classic survey measures it as the allocator's peak memory against the peak of live data ({{Wilson et al. 1995|https://www.cs.hmc.edu/~oneill/gc-library/Wilson-Alloc-Survey-1995.pdf}}); this page uses RSS against live bytes.

Which free chunk to pick. Best fit takes the smallest chunk that fits (little waste, a full search, tiny leftovers); worst fit the largest (big leftovers, a full search, fragments badly in practice); first fit the first that fits (fast, but the front of the list fills with small pieces); next fit continues from where the last search stopped. A list sorted by address makes coalescing cheap; sorted by size, first fit becomes best or worst fit.

Predict: a 100-byte heap, ten requests of 10 bytes (it is now full), then free every other one. 50 bytes are free. Can a request for 15 bytes succeed, with coalescing on?
No. The five free pieces are 10 bytes each and none are next to each other, so coalescing has nothing to join: 50 bytes free, largest piece 10. That is external fragmentation, and no search policy fixes it, because a C allocator cannot move live blocks to close the gaps (a compacting garbage collector can; malloc cannot). Better than one list: size classes. Most programs allocate a few sizes over and over. A segregated list allocator keeps one list per size class (16, 32, 48, ... bytes), so a request is a pop with no search and objects of one size sit together: every allocator below does this. The kernel's own are the slab allocator (a cache of pre-cut objects per type; Bonwick, {{USENIX 1994|https://www.usenix.org/legacy/publications/library/proceedings/bos94/full_papers/bonwick.a}}) and, for runs of whole pages, the buddy allocator: blocks of 2k pages that split in halves and merge with their "buddy", cheap to coalesce at the price of internal fragmentation (a 9-page request takes 16).

2. What one request really costs


ch. 14 Interlude: Memory API


In glibc a chunk is the request plus an 8-byte size field, rounded up to a multiple of 16, at least 32 bytes: request2size (malloc.c line 1326, {{glibc 2.36|https://sourceware.org/git/?p=glibc.git;a=blob;f=malloc/malloc.c;hb=refs/tags/glibc-2.36#l1326}}). Measured with two back-to-back mallocs, whose distance is the chunk size:




measured here src/exp/sizes.c. Usable is what malloc_usable_size reports; the stride is the chunk size. Formula: chunk = max(32, (request + 8 + 15) rounded down to a multiple of 16); a 1-byte request costs 32 bytes, a 25-byte one 48. Next to a 256-byte request the 8-byte header is 3% overhead; next to a 16-byte one it is half the chunk, which is why allocating millions of tiny objects one by one is expensive in memory as well as time.


C trusts the program completely: a use after free, a double free or an overflow corrupts the allocator's own data, often far from where it happened. In ML work these bugs live in C and C++ extensions, and from Python they surface as a segmentation fault or a malloc(): ... abort with no Python traceback; the {{root's Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} shows how to get a native stack.
