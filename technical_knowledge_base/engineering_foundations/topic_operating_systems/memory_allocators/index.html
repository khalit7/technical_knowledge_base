In one screen: who hands out your memory

The kernel gives a process memory in whole pages (4 KiB here), and only through system calls that cost hundreds of nanoseconds. A training job asks for memory millions of times: a 32-byte Python tuple, a 600-byte string, a 1 MiB NumPy batch, a 64 MiB tensor, a 300 MiB activation on the GPU. In between sits a stack of allocators, user-space libraries that get big regions from the kernel rarely, cut them into pieces quickly, and keep freed pieces to hand out again. This page follows the root's running training job down that stack, measures each layer on a real Linux kernel, and reads the source where it explains a number.

1. Free space from zero: headers, free lists, splitting, coalescing

ch. 17 Free-Space Management

The problem. An allocator owns a region of bytes (the heap) and answers two calls: malloc(n) returns the address of at least n free bytes, free(p) gives them back. Requests come in any size and any order, and once the allocator hands out an address it can never move that block, because the program holds raw pointers into it. Everything below follows from those two facts.

The header. free(p) passes only the address, not the size, so the allocator writes a small header just before every block it hands out, holding at least the size. OSTEP's example header has a size and a "magic" number used to catch corruption; glibc's holds the size and three flag bits in 8 bytes (section 3).

header: size
the bytes the program uses (the pointer malloc returned points here)

The free list, stored in the free space itself. Free regions are linked into a free list, and the links live inside the free regions (there is nowhere else to put them): each free chunk starts with its size and a pointer to the next free chunk. A fresh heap is one free chunk.

Splitting and coalescing. When a request is smaller than the chunk chosen for it, the allocator splits it: the front goes to the program, the rest stays on the list. When a chunk is freed next to another free chunk, a good allocator coalesces them into one, otherwise the heap fills with free slivers too small for anything.

Fragmentation, the two kinds. External fragmentation: free memory exists but in pieces, so a request fails (or the allocator grows the heap) although the total free is enough. Internal fragmentation: a block handed out is larger than what was asked for (rounding, size classes, headers), and the excess is wasted inside it. The classic survey measures it as the memory the allocator uses at its peak against the peak of live data (Wilson et al. 1995); this page uses the same idea with RSS against live bytes.

Which free chunk to pick. Best fit takes the smallest chunk that fits (little waste, but a full search, and it leaves tiny leftovers); worst fit takes the largest (leaves big leftovers, full search, fragments badly in practice); first fit takes the first that fits (fast, but the front of the list fills with small pieces); next fit continues from where the last search stopped. Keeping the list sorted by address makes coalescing cheap; sorting by size turns first fit into best or worst fit.

Predict: a 100-byte heap, ten requests of 10 bytes (it is now full), then free every other one. 50 bytes are free. Can a request for 15 bytes succeed, with coalescing on?
No. The five free pieces are 10 bytes each and none are next to each other, so coalescing has nothing to join: 50 bytes free, largest piece 10. That is external fragmentation, and no search policy fixes it, because a C allocator cannot move live blocks to close the gaps (a compacting garbage collector can; malloc cannot). Run it in the Free-list lab tab, preset Q7.

Better than one list: segregated lists and size classes. Most real programs allocate a few sizes over and over. A segregated list allocator keeps a separate list per size class (16, 32, 48, ... bytes), so a request is a pop from the right list with no search, and objects of one size sit together. The kernel's own version is the slab allocator (Bonwick, USENIX 1994): a cache per object type (a task_struct, an inode), each cache made of slabs of pages pre-cut into objects. You can read this kernel's caches directly:



measured here /proc/slabinfo in a container (excerpt). A task_struct, the kernel's record of one thread, is 3,712 bytes, one per slab page; dentries (cached path components) are 200 bytes, 20 per page. The nonzero "tunables" columns are printed only by the older SLAB implementation (SLUB, the default in most distribution kernels, prints zeros), so this linuxkit kernel uses SLAB: an inference from the format, not checked against its config.


Buddy allocation. For runs of whole pages the kernel uses a buddy allocator: free memory is kept in blocks of 2k pages (order k); a request takes the smallest order that fits, splitting a bigger block into two "buddies" as needed; when a block is freed and its buddy is free too, they merge back. Coalescing is a cheap address calculation, at the price of internal fragmentation (a 9-page request takes 16). This kernel's free blocks per order, 0 (4 KiB) to 10 (4 MiB):




measured here cat /proc/buddyinfo. Each column is the number of free blocks of that order; a huge page (2 MiB, order 9) can be found only while order-9 or order-10 blocks remain, which is why huge pages get harder to find on a long-running, fragmented machine (the virtual memory page owns THP).

What a request really costs in glibc. A chunk is the request plus an 8-byte size field, rounded up to a multiple of 16, at least 32 bytes: request2size (malloc.c line 1326, glibc 2.36). Measured with two back-to-back mallocs, whose distance is the chunk size:

Formula: chunk = max(32, (request + 8 + 15) rounded down to a multiple of 16); a 1-byte request costs 32 bytes, a 25-byte one 48. Next to a 256-byte request the 8-byte header is 3% overhead; next to a 16-byte one it is half the chunk, which is why allocating millions of tiny objects one by one is expensive in memory as well as time.


The bugs. C trusts the program completely, and each mistake corrupts the allocator's own data, often far from where it happened:


    

  • Leak: memory never freed. Harmless in a short process, fatal in a server or a long training run.
    • 

  • Use after free: writing through a pointer after free, into a chunk that may already belong to someone else or whose first bytes now hold the free list's links.
    • 

  • Double free: glibc catches the common case and aborts with free(): double free detected in tcache 2.
    • 

  • Overflow: writing past the end tramples the next chunk's header; glibc notices later with messages such as malloc(): corrupted top size.

Tools: AddressSanitizer (gcc -fsanitize=address, which puts poisoned red zones around every block and keeps freed memory in quarantine), Valgrind's memcheck, and glibc's own checks. In ML work these bugs live in C and C++ extensions; from Python they surface as a segmentation fault or a malloc(): ... abort with no Python traceback, and the root's Debug lab shows how to get a native stack.






3. Inside glibc's malloc: chunks, bins, the heap's top, and two thresholds


ch. 17 (real allocators), beyond OSTEP


glibc's allocator (called ptmalloc, descended from Doug Lea's dlmalloc) is what malloc means on Debian, Ubuntu and most Linux machines a training job runs on. Its source is one file, malloc/malloc.c, plus arena.c; line numbers below are glibc 2.36, the version in the lab image, and glibc's own MallocInternals page is the best tour.


A chunk. struct malloc_chunk (line 1148) starts with the previous chunk's size (used only while that one is free) and this chunk's size. Sizes are multiples of 16, so the three low bits of the size are free for flags: P (PREV_INUSE, line 1366: the chunk before me is in use, so do not merge with it), M (IS_MMAPPED, line 1373: I came from my own mmap) and A (NON_MAIN_ARENA, line 1382: I belong to a thread arena, section 4). A free chunk reuses its first user bytes for the list links fd and bk (large free chunks also fd_nextsize, bk_nextsize).

Freeing merges a chunk with free neighbours (except into tcache and fastbins, which keep chunks whole for speed) and, if the merged chunk touches the top, grows the top. That cost shows in a measurement: a malloc plus free of the same small size, repeated, is a tcache push and pop, 11.1 ns here; a thousand mallocs followed by a thousand frees overflow the 7-entry tcache and go through the bins, still cheap for 256 bytes (28.9 ns a pair) but 899.1 ns for 4 KiB. That jump is the second threshold below.


Where the bytes come from: brk, mmap, and the dynamic threshold


glibc gets memory from the kernel two ways. The main heap sits after the program's data and grows by moving its end, the "program break", with brk (brk(2)): cheap, but only the top can ever be given back. A request at or above M_MMAP_THRESHOLD gets its own anonymous mmap instead, given back with munmap the moment it is freed. The threshold starts at 128 KiB (DEFAULT_MMAP_THRESHOLD_MIN, line 961) and is dynamic: when you free an mmapped chunk larger than the current threshold, glibc raises the threshold to that chunk's size and the trim threshold to twice that (lines 3366 to 3371), up to 32 MiB on 64-bit (4 * 1024 * 1024 * sizeof(long), line 972). The reasoning, from mallopt(3): a program that frees a big block probably allocates blocks that size again, and serving them from the heap avoids an mmap, a munmap and fresh page faults each time.


Predict: malloc 1 MiB, touch it, free it, then malloc 1 MiB again and free it. Which system calls does the second malloc make?




The first free raised the threshold to about 1 MiB, so the second request is below it and comes from the heap (one brk), and freeing it gives nothing back: the trim threshold is now about 2 MiB. Step through both traces below, the default and with the threshold pinned.

The trim threshold, and the 899 ns. When the top chunk grows past M_TRIM_THRESHOLD (128 KiB to start, line 919), free shrinks the heap with brk (systrim, line 2971). In the batch benchmark, a thousand 4 KiB blocks freed together merge into a 4 MiB top, glibc trims it, and the next round grows the heap again and takes a page fault on every new page: 899.1 ns a pair. With MALLOC_TRIM_THRESHOLD_=67108864 the heap is kept and the same loop costs 28.4 ns. The price moves elsewhere: the setting also pins the mmap threshold, so 1 MiB blocks now take an mmap and munmap every time (4,723.3 ns a pair, against 2,142.4 by default). Every knob here trades memory held against system calls and page faults.


The knobs and the views. Each tunable can be set three ways: mallopt() in C; an environment variable with a trailing underscore (MALLOC_ARENA_MAX, MALLOC_MMAP_THRESHOLD_, MALLOC_TRIM_THRESHOLD_, MALLOC_TOP_PAD_); or GLIBC_TUNABLES=glibc.malloc.trim_threshold=...:glibc.malloc.arena_max=2 (glibc manual, memory allocation tunables). To look inside a running process: malloc_stats() prints per-arena totals, malloc_info(0, stdout) prints XML with every bin, mallinfo2() returns the totals as a struct (mallinfo(3)). From Python, ctypes.CDLL("libc.so.6").malloc_stats() works in any process; gdb -p <pid> -batch -ex 'call (void)malloc_stats()' works in one you did not write.


malloc_trim. malloc_trim(0) (malloc_trim(3)) does more than its name says: it consolidates every arena and then calls madvise(MADV_DONTNEED) on every whole free page inside free chunks anywhere in the heap, not just at the top (mtrim, lines 5035 to 5089). The kernel drops those pages from RSS while the addresses stay valid. Section 5 measures what that recovers, and what it cannot.






4. Arenas: one heap per group of threads


ch. 17, ch. 28 Locks (why a shared heap needs one)


The problem. One heap shared by every thread needs a lock around every malloc and free, and a training process has many threads: PyTorch's intra-op pool, the DataLoader's pin-memory thread, the main thread, sometimes a gRPC or logging thread. glibc's answer is several arenas, each a separate heap with its own lock and bins. A thread sticks to the arena it last used; if that arena's lock is taken it moves to a free one, and while there are fewer arenas than the limit it creates a new one (arena_get2, arena.c line 924). The limit is 8 per CPU on 64-bit (NARENAS_FROM_NCORES, malloc.c line 1935), so 40 on this 5-CPU VM and 1,024 on a 128-core training host, unless MALLOC_ARENA_MAX says otherwise. Every thread arena reserves a 64 MiB heap (HEAP_MAX_SIZE, arena.c line 31) and commits pages as it grows: the root's section 5 saw exactly these, 132 KiB used and 65,404 KiB reserved, appear when the DataLoader started.


The cost. Each arena keeps its own free chunks, and a chunk freed by another thread goes back to the arena it came from, so memory freed in one arena cannot serve a request in another. With many threads each holding some free memory, the total held grows with the number of arenas. That is the documented reason behind the common MALLOC_ARENA_MAX=2 advice for multi-threaded servers.


Measured. Eight producer threads allocate buffers of random size (64 B to 64 KiB) and hand them to one consumer thread that frees them, at most 4,096 in flight: the shape of a data pipeline. Three runs each on 2 CPUs (median shown):




measured here src/exp/arenas.c, 2,000,000 buffers. Bars are peak RSS; end RSS (everything freed) and time are in the labels. glibc used 10 arenas by default (main, eight producers, the consumer), counted from malloc_stats().


What this run says, and does not. With one arena glibc held the least at peak (136.4 MiB against 220.8) but took 9.37 s instead of 5.88: the lock was the bottleneck it was designed away. And glibc gave almost everything back when the work ended (2.3 MiB), while jemalloc, tcmalloc and mimalloc still held about 125 to 235 MiB at that moment, because they return memory on a timer or a rate rather than at once (section 6). Arena bloat is real in long-running servers with many threads and long-lived objects mixed with short-lived ones; this workload frees everything it allocates, so it does not show it. The lesson is the method: measure peak and steady RSS and time for your own pattern before setting a knob.

Predict: a process allocated 2 GB of small objects, then freed all but 1% of them, scattered. RSS stays near 2 GB. Will malloc_trim(0) bring it near 20 MB?




It returns every whole free page, anywhere in the heap (glibc's mtrim calls MADV_DONTNEED inside free chunks, not only at the top), but a page holding even one live chunk stays. With 1% of objects alive and spread out, many pages still hold one: here 1.5% live left RSS at 27% of its peak after the trim. The real fix is to not interleave long-lived and short-lived objects in the same memory (separate arenas or pools, or allocate the long-lived ones first), or to restart worker processes periodically.


Test 2: long-run growth in a data loader. What it shows: glibc's default holds about 211.1 MiB at the end against 68.7 MiB live. 6. jemalloc, tcmalloc, mimalloc: the same job, other designs


ch. 17 (segregated lists), beyond OSTEP


All three replace glibc's one-heap-with-bins design by size classes in their own runs of pages: every object of a given class lives in a block of memory that holds only that class, so finding a free object is a pop from a short list and fragmentation is bounded per class. Switching needs no code change. malloc is resolved by the dynamic linker, so preloading another library replaces it for the whole process: LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2 python train.py (the path differs per distribution and architecture; here it is under aarch64-linux-gnu). 7. Python's own layer: pymalloc, free lists, and memory that does not come back


ch. 17 (segregated lists, again)


Why Python has its own allocator. A Python program creates and destroys small objects constantly: every integer result, every tuple, every frame. CPython routes requests of 512 bytes or less to pymalloc: "a pymalloc allocator optimized for small objects (smaller or equal to 512 bytes) with a short lifetime. It uses memory mappings called arenas with a fixed size of either 256 KiB on 32-bit platforms or 1 MiB on 64-bit platforms" (Python 3.11 memory management). Larger requests go to malloc.


Three levels (Objects/obmalloc.c at v3.11.2): arenas of 1 MiB got with mmap (ARENA_BITS 20, line 958; _PyObject_ArenaMmap, line 149), cut into pools of 16 KiB (POOL_BITS 14, line 973), each pool serving one size class in steps of 16 bytes (ALIGNMENT 16, line 879) up to 512 (SMALL_REQUEST_THRESHOLD, line 904). A 1-element tuple (48 bytes) and an int (28 bytes, class 32) come from different pools. Pymalloc returns an arena to the kernel only when every object in all 64 of its pools is dead. On top of that, several types keep free lists of recently freed objects for instant reuse, and small integers from -5 to 256 are preallocated once.


Measured: 2,000,000 one-element tuples of fresh ints (about 160 MB of objects), then keep every 1,000th and drop the rest, then drop those too.




measured here src/exp/pymalloc_demo.py, run as is and with PYTHONMALLOC=malloc (which sends every object to glibc). Arena counts from sys._debugmallocstats().


Two lessons. With 2,000 survivors (0.1% of the objects) pymalloc still held all 158 arenas, 163.1 MiB: one live object pins its pool and therefore its arena, the Python version of section 5's pinned pages. This is why the memory of a long-running Python process rarely drops after del of a big structure if anything from it survives (a cached element, a reference in a log, an exception traceback). And when everything died, pymalloc gave its arenas back at once (12.3 MiB), while glibc kept 222.3 MiB until malloc_trim(0) (9.3 MiB): its freed chunks sat below a live chunk near the top of the heap, which blocks trimming.


Seeing it. tracemalloc records the Python line that allocated every block still alive: tracemalloc.start(25), then tracemalloc.take_snapshot().statistics("lineno")[:10], or compare two snapshots with snapshot2.compare_to(snapshot1, "lineno") to find what grows between two points of a training loop (tracemalloc). It sees only memory allocated through Python's allocators, which includes NumPy array data (NumPy reports it to tracemalloc) but not memory allocated inside other C libraries. For those, compare RSS with what tracemalloc reports: the gap is native memory or allocator overhead.


In ML work. Python objects matter most in DataLoader workers: a dataset held as millions of Python objects (lists of strings, dicts of ints) is touched by reference counting on every access, which copies the shared pages after fork into every worker. The root measured 7,880 copied pages for 1M Python ints against 38 to 67 for a NumPy array of the same data, and the virtual memory page owns copy-on-write in depth. The fix is the same one: keep large datasets in NumPy arrays, Arrow buffers or memory-mapped files, not in Python objects.






8. NumPy and PyTorch on the CPU: who calls whom


NumPy allocates array data with malloc, plus two tricks (numpy/_core/src/multiarray/alloc.c at v2.4.6): a small cache of freed buffers under 1,024 bytes, 7 per size (NBUCKETS and NCACHE, lines 45 to 47), and, for arrays of 4 MiB or more on Linux, madvise(MADV_HUGEPAGE) on the data (indicate_hugepages, lines 99 to 112), so with THP in "madvise" mode large arrays may get 2 MiB pages.


PyTorch's CPU tensors go through c10::alloc_cpu (c10/core/impl/alloc_cpu.cpp at v2.14.1). Which allocator that is depends on the build: mi_malloc_aligned when PyTorch is built with mimalloc (lines 111 to 117), which its CMakeLists turns on "on Windows and AArch64" Linux (lines 451 to 468 of CMakeLists.txt); otherwise posix_memalign from glibc (line 126) with 64-byte alignment, "enough for computation up to AVX512" (c10/core/alignment.h, line 15). On Linux, THP_MEM_ALLOC_ENABLE=1 makes buffers of 2 MiB or more page-aligned and madvised for huge pages (lines 58 to 70 and 136 to 147). So the same Python code allocates tensors with glibc on an x86-64 Linux box and with mimalloc on a Graviton or Grace host, and LD_PRELOAD=libjemalloc.so changes tensor allocation only on the first.


The root's 1 GiB reservation, explained. Traced here, the first CPU tensor in a process makes mimalloc reserve 1 GiB of address space and mark it for huge pages:




measured here strace -s 200 -e trace=mmap,munmap,madvise,brk,write python src/exp/torch_cpu.py; each marker prints RSS before the action; thread-stack mmaps from the first multi-threaded fill are cut. The root's gdb stack (its src/trace/raw/hugepage_stack.txt) shows the caller is mimalloc inside libc10.so.


The source agrees: the vendored mimalloc (commit 30ac9d5, version 2.4.1) reserves arenas "N KiB at a time (=1GiB)" (MI_DEFAULT_ARENA_RESERVE, src/options.c lines 69 to 75 and 152), with MAP_NORESERVE, and calls madvise(MADV_HUGEPAGE) on it (src/prim/unix/prim.c lines 391 to 400). It costs nothing until touched (overcommit; the virtual memory page). Then: a 64 MiB tensor made no system call at all, it was carved from the reservation and its pages faulted in on first touch (RSS 228.1 to 294.1 MiB), and after del RSS stayed at 294.1 MiB to the end: mimalloc keeps freed memory for reuse. NumPy's 64 MiB array, by contrast, took its own mmap (above glibc's threshold), got its huge-page hint, and went back with munmap on del.


Pinned host memory from source; not run here. pin_memory() and DataLoader(pin_memory=True) allocate page-locked host memory through PyTorch's CachingHostAllocator, which calls cudaHostAlloc (CachingHostAllocator.cpp line 77 at v2.14.1), caches freed blocks like its GPU counterpart, and rounds each request up to the next power of two "to improve reuse" (CachingHostAllocator.h lines 339 to 347; no upper limit on the rounding by default, pinned_max_round_threshold in AllocatorConfig.h line 360). A 600 MB pinned buffer therefore takes 1 GiB of locked RAM, which the kernel can never swap or reclaim. Why pinning exists and what it costs the kernel belongs to the virtual memory page.






9. PyTorch's CUDA caching allocator, and "out of memory" with memory free


ch. 17 again, one level up


from source and docs; not run here: no GPU Line numbers are c10/cuda/CUDACachingAllocator.cpp at v2.14.1 unless named; constants are in c10/core/AllocatorConfig.h. Zach DeVito's guide to the caching allocator is the best walkthrough by one of its authors.


The problem. GPU memory comes from the CUDA driver, and asking it is slow; PyTorch's notes give the reason for caching: "This allows fast memory deallocation without device synchronizations" (CUDA semantics, memory management). A training step allocates and frees hundreds of tensors, so PyTorch keeps every freed block and reuses it, which is the same idea as glibc's bins, with the GPU's own constraints. The docs warn about the visible consequence: "the unused memory managed by the allocator will still show as if used in nvidia-smi".


The rules, from the comment at the top of the file (lines 93 to 122) and the code:


    

  • Rounding. Every request is rounded up to a multiple of 512 bytes (round_size, lines 3060 to 3072; kMinBlockSize 512). With roundup_power2_divisions:N large requests are instead rounded to one of N steps between powers of two (lines 3036 to 3058), which makes sizes repeat and blocks reusable.
    • 

  • Two pools. Requests up to 1 MiB (kSmallSize) go to the small pool, packed into 2 MiB segments (kSmallBuffer); larger ones to the large pool (get_pool, lines 3640 to 3667).
    • 

  • Segment size. When nothing cached fits, a new segment comes from cudaMalloc: 2 MiB for small requests, 20 MiB for requests from 1 to 10 MiB (so several share one), and the request rounded up to 2 MiB above that (get_allocation_size, lines 3695 to 3703).
    • 

  • Best fit. The free blocks of a pool are kept sorted by stream, size, segment age and address; a request takes the smallest one that fits (get_free_block, lines 3705 to 3762).
    • 

  • Splitting. If the chosen block is bigger, the front is handed out and the rest stays cached, in the small pool if at least 512 bytes remain, in the large pool only if more than 1 MiB remains (should_split, lines 3675 to 3693).
    • 

  • Freeing never calls the driver: the block goes back to its pool and merges with free neighbours in the same segment (free_block and try_merge_blocks, lines 3502 to 3612). A block is tied to the stream it was allocated on; using it on another stream needs tensor.record_stream(s), or it may be reused too early.
    • 

  • Out of memory: the retry chain. If cudaMalloc fails, the allocator frees cached blocks and tries again: first just enough oversize blocks (only when max_split_size_mb is set), then every cached segment that is not split, then raises (malloc, lines 1720 to 1792). A segment with even one live block cannot be returned.
    • 



The failure. Segments are created at the sizes of the first requests that needed them. When later requests are a little bigger (batch 9 after batch 8, a longer sequence), they do not fit the free holes, new segments are made, and the leftover slivers at the ends of old segments are stranded inside segments that still hold something live. Eventually cudaMalloc fails with hundreds of megabytes free in total. The error message says so in its own words (lines 1927 to 1953):


torch.OutOfMemoryError: CUDA out of memory. Tried to allocate <segment size>. GPU 0 has a total capacity of <total> of which <free> is free. ... Of the allocated memory <a> is allocated by PyTorch, and <r> is reserved by PyTorch but unallocated. If reserved but unallocated memory is large try setting PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True to avoid fragmentation.


"Tried to allocate" reports the segment size the allocator asked the driver for (alloc_size), so a 3 MiB tensor can fail as "Tried to allocate 20.00 MiB". "Reserved but unallocated" is the fragmentation: cached memory no request fit.


The fix: expandable segments. The file's Note [Expandable Segments] (lines 311 to 401) tells the batch-size story and the cure: "Instead of making one segment per allocation, it tries to make one segment (per stream) that grows as necessary". It reserves a range of GPU virtual addresses as large as the device memory (cuMemAddressReserve) and maps physical memory into it in pages, 2 MiB for the small pool and 20 MiB for the large one, with cuMemCreate and cuMemMap, so new memory lands right after the old and free space at the end of the segment joins with what is mapped next. Virtual memory (the virtual memory page), applied by a user-space allocator to the GPU. The limits the note lists: slightly slower first allocations, and no CUDA IPC of such memory (sharing GPU tensors between processes).

Choosing an allocator for a training host. The measurements above give the rule: start with the defaults, find out whether allocation is a problem at all (the running job did not care), and change one thing at a time with peak RSS, steady RSS and step time recorded. When a change is needed: jemalloc is the common choice for long-running multi-threaded data and serving processes whose RSS drifts (enable its background thread, or it may never give memory back); tcmalloc for the fastest small-object paths; glibc with MALLOC_ARENA_MAX=2 when you cannot ship a library. On x86-64 CPU training, PyTorch's tuning guide suggests jemalloc or tcmalloc via LD_PRELOAD; on arm64 the tensors already use mimalloc. Remember that a container's memory limit counts RSS: memory an allocator keeps "for reuse" is memory the OOM killer counts.


Common mistakes


"I deleted the big object, so memory should drop."
Freed memory usually stays in the allocator (glibc keeps anything below the heap's top, pymalloc keeps arenas with one survivor, jemalloc waits for decay, PyTorch's caches keep everything). RSS measures what the process holds, not what it uses. Measured: 1.6 MB live in 110 MB of RSS.


"nvidia-smi says the GPU is full, so my model needs that much."
nvidia-smi shows what the caching allocator reserved plus the CUDA context. Compare torch.cuda.memory_allocated() with memory_reserved().


"torch.cuda.empty_cache() in the training loop prevents OOM."
It returns only unused, unsplit segments; it cannot fix fragmentation inside segments that still hold live tensors, and it makes the next step pay for cudaMalloc again. Use it when handing the GPU to another process.


"MALLOC_ARENA_MAX=2 is always good."
It trades memory for lock contention: one arena cut peak RSS by 38% here but made the run 59% slower (section 4: 136.4 against 220.8 MiB, 9.37 against 5.88 s).


"LD_PRELOAD=libjemalloc.so changed nothing, so allocation is not the problem."
Check the library loaded (grep jemalloc /proc/<pid>/maps) and whether the memory goes through malloc at all: tensors on an arm64 PyTorch wheel use mimalloc inside libc10, GPU memory uses the caching allocator.






Interview questions


Why doesn't free() return memory to the operating system?
The kernel works in pages and only gives memory back by unmapping or advising whole pages. A freed chunk is usually a small piece of a page that also holds live chunks, or sits below other live chunks in the heap, which can only shrink from its top. Allocators keep freed memory to serve the next request without a system call. glibc returns big blocks (above the mmap threshold) at once, trims the top of the heap past the trim threshold, and malloc_trim releases whole free pages anywhere; others return memory after a delay.


Internal against external fragmentation, with an example of each.
Internal: waste inside handed-out blocks, such as glibc's 32-byte chunk for a 1-byte request, a buddy allocator giving 16 pages for 9, PyTorch rounding to 512 bytes or a pinned buffer to a power of two. External: free memory in pieces too small for the request, such as ten 10-byte blocks with every other one freed (50 free, none fits 15), or GPU segments with free slivers no new tensor fits. Compaction fixes external fragmentation only where blocks can move (garbage-collected runtimes); C allocators and PyTorch's cannot move them, so they prevent it with size classes, splitting rules and, on the GPU, virtual memory (expandable segments).


What does the CUDA OOM message's "reserved but unallocated" mean, and what do you do?
Memory the caching allocator holds in segments but no live tensor uses: after it already released every fully free segment, what remains is free space inside segments that still contain live blocks, so it is fragmentation. Try PYTORCH_ALLOC_CONF=expandable_segments:True; check with a memory snapshot which allocations straddle; make sizes regular (pad or bucket sequence lengths, fixed batch sizes, roundup_power2_divisions); then reduce the peak (activation checkpointing, smaller micro-batches).


How does glibc decide between brk and mmap for a request, and why is the threshold dynamic?
Requests at or above M_MMAP_THRESHOLD (128 KiB to start) get their own mmap; smaller ones come from the heap. Freeing an mmapped chunk raises the threshold to that size (up to 32 MiB on 64-bit) and the trim threshold to twice it, on the guess that the program will allocate that size again and should not pay mmap, munmap and page faults every time. The cost is that later big blocks live in the heap and can stay resident; setting the threshold explicitly turns the adjustment off.


Why do multi-threaded programs on glibc sometimes use far more memory than single-threaded ones?
glibc creates up to 8 arenas per CPU, each with its own free chunks; memory freed in one arena cannot serve requests in another, and a chunk freed by another thread returns to its own arena. Free memory spread over many arenas adds up. MALLOC_ARENA_MAX caps it at the cost of lock contention; jemalloc and mimalloc handle cross-thread frees differently (mimalloc with a per-page thread-free list).


A Python service's memory never goes down after a large request. Why, and how do you confirm?
Likely pymalloc arenas pinned by a few surviving objects, or glibc chunks below a live chunk at the heap's top. Confirm: tracemalloc's current total is low while RSS is high; sys._debugmallocstats() shows many arenas with few used pools; malloc_trim(0) from ctypes drops RSS if it is glibc. Fixes: avoid keeping references to per-request objects, move bulk data to arrays, or recycle worker processes.
