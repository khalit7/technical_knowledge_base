In one screen

Concurrency means several activities in progress at the same time inside one program; parallelism means some of them really run at the same instant, on different CPU cores. A training job is concurrent everywhere: the training loop, a pool of math threads inside PyTorch, DataLoader worker processes and the threads that feed their queues, a checkpoint writer, and on a GPU node NCCL's communication threads and PyTorch's watchdog. This page is about the machinery that lets those activities share memory and wait for each other without corrupting data or wasting CPUs.

The running example is the training job of the root page (a CPU-only PyTorch run with a memory-mapped dataset and two DataLoader workers). Seen as threads, while it trains (measured in section 10):

main process (the training loop) ├─ MainThread runs forward, backward, optimizer step; holds the GIL while in Python ├─ QueueFeederThread x2 pickles batch indices into each worker's pipe └─ native threads OpenMP's pool for PyTorch's math; asleep in futex_wait between operators worker process x2 (fork of main) ├─ pt_data_worker reads samples, builds a batch, puts it on the result queue └─ helper threads queue feeder, file-descriptor server; asleep in poll or futex_wait

Almost every one of those threads is asleep at any instant, and nearly all of them are asleep in the same kernel function, futex_wait. The rest of the page explains why.

1. Threads: several flows of control, one address space

ch. 26 Concurrency: an introduction, ch. 27 Thread API

The problem. A process (the sibling page Processes and the system-call API owns it) is one running program with one flow of control: one program counter (the address of the next instruction) and one stack (the memory holding local variables and return addresses of the functions in progress). To use several cores on one shared data structure, a program needs several flows of control that see the same memory. That is a thread: its own registers, program counter and stack, and everything else (heap, globals, open files, signal handlers) shared with the other threads of its process.

How Linux makes one. The kernel has no separate thread object: a thread is a task (the kernel's schedulable unit, a task_struct) that shares its parent's memory and tables because of the flags it was created with. pthread_create in glibc 2.36 asks for exactly this sharing (nptl/pthread_create.c L277-281), and strace shows the whole recipe for one thread measured here:





CLONE_VM, CLONE_FILES, CLONE_FS, CLONE_SIGHANDshare the address space, the file-descriptor table, the working directory, and the signal handlers


CLONE_THREADsame thread group: same process id for getpid(), a new thread id (gettid())


CLONE_SETTLSpoint the thread-pointer register (tpidr_el0 on arm64, fs on x86-64) at this thread's thread-local storage


CLONE_CHILD_CLEARTIDwhen the thread exits, the kernel writes 0 to its id word and does a futex wake on it: that is how pthread_join learns it ended




Before the clone, glibc maps the new thread's stack: 8 MiB (the default comes from the stack resource limit, ulimit -s = 8192 KiB) plus a guard region mapped PROT_NONE so that a stack overflow faults instead of silently overwriting a neighbour. The guard is 64 KiB here although pthread_attr_getguardsize reports 4096 bytes: glibc rounds it up to the architecture minimum on arm64 (sysdeps/aarch64/nptl/pthreaddef.h L23, nptl/allocatestack.c L345-346). Newer glibc versions try clone3 first and fall back to clone (clone-internal.c L52-55); glibc 2.36 on arm64 has no clone3 wrapper, so the trace shows plain clone.


Thread-local storage (TLS) is a variable declared __thread (C) or thread_local (C++): one copy per thread, found through the thread pointer. errno is one, which is why two threads can make failing system calls at once without overwriting each other's error code. The same program printed its variables' addresses from three threads:




Thread 0 is the main thread. The shared global has one address; tls_var and the stack differ between the main thread and the others. Threads 1 and 2 print the same addresses because the program joins thread 1 before creating thread 2, and glibc reuses the cached stack and TLS block.


Cost measured here: creating and joining an empty thread took 136.0 µs with 4 CPUs available and 12.0 µs pinned to one CPU (best of 5 × 2000). The difference is the cross-CPU wake-up, which is unusually expensive in this VM (section 4 measures it). The 8 MiB stack costs address space, not memory: 2,000 idle threads in section 9 reserved 18683 MiB of virtual memory but added only 13 MiB of resident memory, because untouched stack pages are never allocated (copy-on-write and demand paging: the sibling Virtual memory page).


Thread or process? A thread is cheaper to create and shares memory for free; a process gets a separate address space, so a crash or a corrupted heap in one cannot touch the other, and in CPython each process has its own GIL (section 8). PyTorch's DataLoader uses processes for that reason, and pays with pickling and shared memory to move batches. On Linux both are tasks, so a container's pids.max limit counts threads too: the root's Debug lab case "BlockingIOError on fork: the pids limit counts threads too" shows it.


Predict: one thread of a training process calls exit(1) from a background thread. What happens to the other threads?




exit calls exit_group, which ends every thread in the thread group. To end only the calling thread, return from its function or call pthread_exit. The same holds for a signal whose default action is to terminate: it kills the whole process, whichever thread it was delivered to.






2. Races, atomic instructions and memory order


ch. 26.3 to 26.5, ch. 28.6 to 28.11


The problem. When two threads update the same memory and nothing orders them, the result depends on timing: a race condition. The classic one, count = count + 1 on two threads, is three instructions (load, add, store); if both threads load the same old value, one increment is lost. The root page measured it (two threads, 10 million increments each, about half lost) and its OS simulators tab steps the three instructions one at a time. A piece of code that touches shared data and must not run in two threads at once is a critical section; the guarantee that at most one thread is inside is mutual exclusion.


Atomic instructions. The hardware fix is an instruction that reads, modifies and writes one memory word as one indivisible step, which no other core can split. Three families matter:




Fetch-and-addold = *p; *p = old + v in one step. arm64 v8.1 has ldadd; x86-64 has lock xadd. Counters and reference counts.


Exchange (test-and-set)old = *p; *p = v. The simplest lock: while (xchg(&l, 1) == 1) ;


Compare-and-swap (CAS)if *p == expected then *p = new, and say whether it did. Everything lock-free is built on it. arm64 v8.1 cas; x86-64 lock cmpxchg.


Load-linked / store-conditionalthe older arm64 form (ldaxr then stlxr): the store fails if anyone wrote the word in between, and the code loops. GCC's "outline atomics" pick LSE or LL/SC at run time (the root's assembly shows a call to __aarch64_ldadd8_acq_rel).




An atomic update is not free: on one thread it cost 8.3 ns here against well under a nanosecond for a plain add, and with four threads updating one counter the cache line holding it bounces between cores (the C++ page's false-sharing measurement shows the same effect for neighbouring variables).


Memory order. A second, subtler problem: cores do not make their writes visible to each other in program order. Each core puts stores in a private store buffer and lets later loads run ahead of them. On x86-64 only that one reordering (a later load passing an earlier store) is allowed; arm64 allows more. Part 2 of the C++ page measures the message-passing reordering on this same chip and explains acquire, release and sequentially consistent orders; here is what it does to a lock.


Peterson's algorithm (OSTEP 28.6) is a correct lock for two threads using only loads and stores, proved in 1981 on the assumption that memory is sequentially consistent:


void lock(int me) {  int other = 1 - me;
    flag[me] = 1;                         // I want in
    turn = other;                         // but you go first if you also want in
    while (flag[other] && turn == other) ;  // wait while you want in and it is your turn
}
void unlock(int me) { flag[me] = 0; }


If the store flag[me] = 1 is still in this core's store buffer when the load flag[other] runs, both threads can read the other's flag as 0 and both enter. Two threads, each entering 20 million times, with a non-atomic count = count + 1 inside measured here (src/runs/c/peterson.c):






The fix is to declare the order you need: with sequentially consistent atomics the compiler emits the ordering instructions (stlr and ldar on arm64, or a full barrier dmb ish), and the lock is correct. Real locks never rely on plain loads and stores; they use an atomic exchange or CAS, which carry the ordering with them (acquire on lock, release on unlock).


Predict: a volatile int counter, incremented by two threads. Does volatile make count++ safe?




No. volatile only stops the compiler from removing or merging the accesses; the load, add and store are still three steps, and nothing orders them across cores. The root's race measurement used a volatile counter and lost about half the increments. Use an atomic (std::atomic, __atomic_fetch_add) or a lock.







3. Locks: spin, yield, or sleep


ch. 28 Locks, ch. 29 Lock-based concurrent data structures


A lock (or mutex, for mutual exclusion) is a word in memory plus two operations: lock() returns only when the caller owns it, unlock() gives it up. OSTEP judges a lock on three things: correctness (mutual exclusion), fairness (does every waiter eventually get it, or can one starve?) and performance (with no contention, with contention on many CPUs, and with contention on one CPU). The design question is what a thread does when the lock is taken:




Spinkeep retrying the atomic exchange. Best when the holder is running on another core and will release within nanoseconds. Terrible when the holder is not running: the spinner burns its whole time slice.


Yieldretry, and call sched_yield() after each failure to give the CPU away (OSTEP 28.13). A system call per failed attempt, and no promise about who runs next.


Sleepask the kernel to put the thread on a wait queue and wake it when the lock is released. Costs two system calls and a wake-up when contended, nothing else.


Spin, then sleep(two-phase or adaptive locks) spin briefly in case the holder is about to release, then sleep. glibc's PTHREAD_MUTEX_ADAPTIVE_NP spins at most 100 rounds by default, with exponential backoff (nptl/pthread_mutex_lock.c L139-158; tunable glibc.pthread.mutex_spin_count).




Seven ways to protect one shared counter, measured in four situations measured here (src/runs/c/locks.c; "work" is a loop of about 0.3 ns per iteration; median of 3 runs; per-run values in the raw output):










What to take from it:


    

  • Uncontended, a good lock costs about as much as one atomic instruction (9.2 ns for the hand-built futex lock, 10.1 ns for pthread_mutex_t), because it never enters the kernel. A lock that makes a system call on every unlock costs 288.6 ns: about thirty times more, for nothing.
    • 

  • Contended on enough CPUs, spinning burns CPU: with a short critical section the spinlock used 910.3 ns of CPU per acquisition against 437.2 ns for the mutex, and was slower in wall time too, because four cores fighting over one cache line slow each other down.
    • 

  • With more threads than CPUs, a spinner can wait for a thread that is not running. On one CPU with a long critical section, the holder is often preempted inside it; each spinner then burns a whole time slice before the holder runs again: 1492.5 ns per acquisition against 815.9 ns for the mutex and 791.5 ns for one thread doing the same work alone.
    • 

  • Hammering a lock rewards unfairness. In the no-work scenario the yield lock looks fastest, because a thread that just released the lock usually takes it again while its cache line is still hot and the others are yielding; the work is done, but by one thread at a time in long runs. Fairness costs throughput; a ticket lock (OSTEP 28.11: fetch-and-add a ticket, wait for your number) is fair and slower.
    • 

  • Never use a spinlock in user space unless every thread has its own CPU (as with pinned threads in a low-latency system). This is why the Linux kernel spins (kernel code can disable preemption while holding a spinlock) and user space sleeps.
    • 



Predict: a container with a one-CPU limit runs a job whose 8 threads take a spinlock around a 50 µs critical section. Roughly how long can one waiter spin before the holder runs again?




The holder can be descheduled inside the critical section; then every spinner that runs uses its full slice (a few milliseconds under CFS) doing nothing, and under a CPU quota the whole cgroup can be throttled until the next 100 ms period (the root's Debug lab, "CPU limit" cases). The measured one-CPU case above shows the effect at small scale.






4. The futex: how every Linux lock sleeps


ch. 28.14 to 28.16 (Linux futex, two-phase locks) from source measured here


The problem. Sleeping needs the kernel (only the kernel can take a thread off the CPU and put it back), but entering the kernel costs about 300 ns, thirty times an uncontended lock. Before futexes, user-space locks paid for a system call either on every operation or on none (and then spun). The futex ("fast user-space mutex", Linux 2.6, 2003) splits the job: the lock word lives in ordinary user memory and is changed with atomic instructions; the kernel is asked only to sleep on that word or to wake sleepers on it (futex(2); Drepper, Futexes Are Tricky, 2011). Two operations do almost all the work:




futex_wait(addr, val)"if *addr still equals val, put me to sleep on addr; otherwise return at once with EAGAIN". The comparison and the going to sleep happen together inside the kernel, under a lock no waker can slip past.


futex_wake(addr, n)"wake up to n threads sleeping on addr". It does not change *addr; the user-space code changed it already.




glibc's mutex protocol uses three values for the lock word: 0 free, 1 locked with nobody waiting, 2 locked and someone may be waiting. Simplified from sysdeps/nptl/lowlevellock.h L94-106 and L145-160 and nptl/lowlevellock.c L38-50:


void lock(int *w) {
    if (CAS(w, 0, 1)) return;                 // fast path: free, now mine, no system call
    if (*w == 2) goto wait;
    while (xchg(w, 2) != 0)                 // mark "waiters"; if it was 0 I own it now (as 2)
  wait: futex_wait(w, 2);                    // sleep, but only if it is still 2
}
void unlock(int *w) {
    if (xchg(w, 0) > 1)                      // was 2: someone may be asleep
        futex_wake(w, 1);                      // wake one; it retries the xchg
}


Uncontended, lock is one CAS and unlock one exchange: no system call. Only a thread that finds the lock taken calls futex_wait, and only an unlock that sees 2 calls futex_wake. A thread that takes the lock after a wait sets it to 2, not 1, because it cannot know whether others are still asleep: an occasional unneeded wake-up is the price of never missing one. The hand-built version in locks.c counts its own system calls: with four threads and short critical sections it made 208840 futex waits in 2 million acquisitions (about one acquisition in ten had to sleep).


Why the kernel must compare: the lost wake-up


Why not check the lock word in user space and then call a plain "sleep"? Because between the check and the sleep, the holder can unlock and send its wake-up to a thread that is not asleep yet; the wake-up is lost, and the waiter then sleeps forever. The kernel source states the rule (kernel/futex.c L2633-2648, v5.10):


 * The basic logical guarantee of a futex is that it blocks ONLY
 * if cond(var) is known to be true at the time of blocking, for
 * any cond.  If we locked the hash-bucket after testing *uaddr, that
 * would open a race condition where we could block indefinitely with
 * cond(var) false, which would violate the guarantee.


So futex_wait_setup locks the wait queue first, then reads *uaddr, and returns EAGAIN if it changed (L2650-2678). The Interleaving lab lets you produce the lost wake-up yourself in the "check, then sleep" lock (54 of its 376 possible schedules leave a thread asleep forever) and shows that the futex version has none.


Where the sleepers are kept


The kernel does not allocate anything per futex while nobody waits. Sleepers go into one global hash table of wait queues, indexed by a key for the address: for a private futex (threads of one process; glibc passes FUTEX_PRIVATE_FLAG) the key is the address space and the virtual address; for a shared futex (a lock in memory mapped by several processes) it is the underlying page and offset, so different virtual addresses in different processes meet in the same queue (get_futex_key, kernel/futex.c L487-653). The table has roundup_pow_of_two(256 × CPUs) buckets (L4050), 2,048 on this 5-CPU VM. Python's multiprocessing.Lock is a POSIX semaphore in a /dev/shm/sem.* file mapped by both processes, so its futex is shared: no _PRIVATE in the trace measured here:

Costs are this VM's measured ones where they exist: a futex system call 0.3 µs (the "wake on every unlock" lock's 288.6 ns per pair), and a wake-up of 1.7 µs (same CPU) or 23.5 µs (across CPUs in this VM; switch below), half a ping-pong round trip. Switch to the cross-CPU wake-up: the futex's hand-offs become far slower than spinning, which is exactly why glibc offers an adaptive mutex and why the kernel and NCCL spin when they expect the wait to be short.


What a wake-up costs


Two threads passing a turn back and forth 200,000 times measured here (pingpong.c; round trip = two hand-offs; median of 5):




On one CPU a hand-off is a context switch: 1.7 µs, in line with the root's 1.33 µs pipe ping-pong. Across CPUs it is slower here because the sleeping CPU has gone idle and must be woken by an inter-processor interrupt, which a virtual machine turns into a trip through the hypervisor (here a GICv2 emulated in QEMU, with the idle vCPU a host thread that must itself be woken: Virtualization and the GPU driver stack, section 5, measures each step); how much lower it is on bare metal was not measured here not run here. The rest of the futex family


    

  • FUTEX_WAIT_BITSET with FUTEX_CLOCK_REALTIME: a wait with an absolute deadline; glibc uses it for timed waits and POSIX semaphores (the trace above).
    • 

  • FUTEX_CMP_REQUEUE: wake one waiter and move the rest from a condition variable's futex to the mutex's, so a broadcast does not wake a herd that would immediately fight for the mutex (the thundering herd). glibc 2.25 (2017) replaced its condition variables with an algorithm based on groups of waiters that never requeues (no requeue call appears in nptl/pthread_cond_wait.c, glibc 2.36); the operation remains in use for priority-inheritance locks.
    • 

  • FUTEX_LOCK_PI: priority inheritance; the kernel knows the owner (its thread id is in the word) and boosts it while a higher-priority thread waits. It fixes priority inversion, the bug that kept resetting NASA's Mars Pathfinder in 1997 (account by Glenn Reeves).
    • 

  • Robust futexes: the kernel walks a per-thread list at exit and marks locks held by a dead thread (EOWNERDEAD), for locks in memory shared between processes.
    • 

  • futex_waitv (Linux 5.16) waits on several futexes at once, added for Wine and game engines (futex2 docs); not on this 5.10 kernel.
    • 



In ML work Every lock and queue in the stack sleeps on a futex: Python's threading.Lock and queue.Queue, PyTorch's thread pools, libgomp's barriers, NCCL's proxy thread when idle. So when a training process hangs, cat /proc/<pid>/task/*/wchan shows futex_wait_queue_me (5.10; futex_wait_queue on 6.x) for nearly every thread, and the question becomes which address each one waits on and who should have woken it: py-spy dump for Python frames, gdb -p <pid> -ex "thread apply all bt" for native ones (section 6).


Predict: under strace, a busy training process shows futex(..., FUTEX_WAIT_PRIVATE, 2, NULL) = -1 EAGAIN thousands of times. A bug?




EAGAIN from futex_wait is the futex working as designed: by the time the kernel compared, the holder had released (or someone changed the word), so sleeping would have been wrong. The caller simply retries. In the job's trace in section 10, about a fifth of all futex calls return an error (strace -c counts errors without naming them; for these waits the usual ones are EAGAIN and, for timed waits, ETIMEDOUT).






5. Waiting for something: condition variables, semaphores, reader-writer locks, barriers


ch. 30 Condition variables, ch. 31 Semaphores


The problem. A lock says "one at a time"; it cannot say "wait until a batch is ready" or "wait until there is room in the queue". Checking a flag in a loop (spinning) wastes a CPU; a thread needs to sleep until another thread says the condition may now hold.


A condition variable is a queue of sleeping threads attached to a condition the program tracks in its own variables, always used with a mutex: wait(cv, m) atomically releases m and sleeps, and re-takes m before returning; signal(cv) wakes one sleeper, broadcast(cv) wakes all. The atomic "release and sleep" is the same lost-wake-up problem as in section 4, solved the same way (glibc builds it on futexes).


Rule 1: re-check the condition in a while loop. POSIX and Linux use Mesa semantics: a woken thread is only told that the condition was true at some moment; another thread may have run in between and made it false again (and implementations may wake a thread spuriously). OSTEP's producer/consumer with one slot, one producer and two consumers, run for 200,000 items measured here (condvar.c):




With if, a consumer woke up to an empty slot 45 to 88 times per run: in real code that is reading garbage or an exception from an empty queue, rarely enough to pass every test. With while, the same situations happen (37 to 70 re-checks per run) and are harmless.


Rule 2: one condition variable per condition. With one variable shared by "slot full" and "slot empty", a consumer's signal can wake the other consumer instead of the producer; then all three sleep, and the program hangs at 0% CPU. It hung in 3 of 3 runs, after a handful of items. Use two condition variables (or broadcast, which is correct but wakes everyone).


The Interleaving lab counts every possible schedule of a two-item version: with if, 64,228 of 42,827,788 schedules make a consumer read an empty slot; with while, none of 91,732,872 do.


A semaphore (Dijkstra, 1960s) is a counter with two operations: wait (also P, down) decrements it and sleeps while it would go below zero; post (V, up) increments it and wakes a sleeper. Initialised to 1 it is a lock; to N it admits at most N holders at once ("at most 2 prefetched batches per worker" is this idea: the DataLoader's prefetch_factor); to 0 it is a "wait until done" signal. POSIX sem_t is a futex word; multiprocessing's locks, semaphores and queues are sem_t in /dev/shm (section 4's trace). Semaphores are easy to misuse because, unlike a mutex, any thread can post them: nothing records an owner.


A reader-writer lock lets many readers in at once or one writer alone; good for data read far more than written (a model registry, a config). The catch is starvation: glibc's pthread_rwlock_t prefers readers by default, so a steady stream of readers can keep a writer waiting indefinitely (PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP changes it; pthread_rwlockattr_setkind_np(3)). For short critical sections an rwlock is often slower than a mutex, since even readers write the shared reader count.


A barrier makes N threads wait until all N arrive. OpenMP puts one at the end of every parallel region, which is where PyTorch's math threads sit between operators: libgomp spins at the barrier for a while (do_spin in libgomp/config/linux/wait.h; tuned by GOMP_SPINCOUNT and OMP_WAIT_POLICY) and then sleeps on a futex. The gdb snapshots in section 10 find the pool threads asleep in futex_wait inside gomp_barrier_wait_end.


In ML work NCCL's proxy thread sleeps on a C++ condition variable when it has nothing to progress, with the predicate the comment calls out: "Predicate avoids lost wakeups and guarantees we observe stop after ncclProxyProgressDestroy" (src/proxy.cc L849-851, NCCL v2.32.3-1). pool->cond.wait(lock, predicate) is exactly rule 1, the while loop written as a lambda.







6. Deadlock, and the other concurrency bugs


ch. 32 Common concurrency problems


Lu et al. studied 105 concurrency bugs in MySQL, Apache, Mozilla and OpenOffice: 74 were not deadlocks and 31 were; 97% of the non-deadlock bugs were of two kinds (as summarised in OSTEP ch. 32, from Learning from Mistakes, ASPLOS 2008):




Atomicity violationcode assumed two steps happen together, and another thread ran between them: if (p) use(p); while another thread sets p = NULL. Fix: one lock around both steps.


Order violationcode assumed A happens before B, and nothing enforced it: a thread uses an object before its creator finished initialising it. Fix: a condition variable or semaphore that B waits on.




A deadlock is a set of threads each waiting for something another member of the set holds, so none can move. It needs four conditions at once (Coffman, 1971): mutual exclusion (resources are held exclusively), hold and wait (a thread holds one while waiting for another), no preemption (nobody can take a held lock away), and a circular wait. Remove any one and deadlock is impossible. In practice:

The signature of a deadlock: every thread in state S (sleeping), every wait channel futex_wait_queue_me, 0% CPU, and py-spy pointing at the two with lines. A busy-looping bug looks the opposite (state R, 100% CPU). With --ordered the same program finishes.


Fixes and tools One lock order per program, written down; never call unknown code (callbacks, logging handlers, __del__) while holding a lock; lock.acquire(timeout=...) in Python turns a silent hang into an error you can log; faulthandler.dump_traceback_later(timeout) prints every thread's stack if the job stops progressing; glibc's PTHREAD_MUTEX_ERRORCHECK returns EDEADLK when a thread re-locks a mutex it holds; ThreadSanitizer (-fsanitize=thread) reports lock-order inversions as well as data races.


The training-job deadlock everyone meets is not two locks but fork while another thread holds one: the child gets a copy of the locked lock and no thread to release it. The root's Debug lab reproduces it ("A worker hangs forever: fork while another thread holds a lock") and the sibling Processes page covers start methods; it is why Python 3.14 made forkserver the default on Linux. Database transactions face the same four conditions with a different cure (detect the cycle and abort a victim): Transactions and concurrency.


Predict: thread A holds lock L and calls logging.info(); a logging handler, on another thread B, holds the handler's lock and calls a function that takes L. What can happen?




"Thread-safe" only means each call is safe on its own. A holds L and wants the handler's lock; B holds the handler's lock and wants L: a circular wait. The rule "never call out while holding a lock" exists for this case.







7. Lock-free, briefly


A lock-free data structure guarantees that some thread always makes progress, even if others are paused at any instruction, because nobody ever holds a lock. The building block is a CAS loop: read the current value, compute the new one, and CAS it in; if another thread changed it meanwhile, the CAS fails and you retry. A stack push:


do { n->next = head; } while (!CAS(&head, n->next, n));


The traps: the ABA problem (the head was A, became B, became A again; the CAS succeeds although the list changed underneath; fixed with version counters or safe memory reclamation), and freeing memory another thread may still be reading (fixed by hazard pointers, epochs, or RCU, read-copy-update, which the Linux kernel uses so that readers take no lock at all: What is RCU). The common, safe case in practice is a single-producer single-consumer ring buffer: one thread only advances the tail, the other only the head, and each reads the other's index with acquire order. io_uring's two rings (section 9) are exactly that, shared between a program and the kernel. Use lock-free structures from a library (the C++ page's atomics, Rust's crossbeam, std::atomic counters); a lock is usually fast enough (section 3: 10 ns uncontended) and far easier to get right.






8. The GIL, seen as an operating-system lock


from source measured here


CPython's global interpreter lock lets one thread at a time run Python bytecode. The Python page covers what it means for your code and how the free-threaded build (3.13t, 3.14t) removes it; this section is about how it is built and what it does to latency. In CPython 3.11 it is the textbook construction of section 5: "The GIL is just a boolean variable (locked) whose access is protected by a mutex (gil_mutex), and whose changes are signalled by a condition variable (gil_cond)" (Python/ceval_gil.h L13-16, v3.11.2).


A thread that wants the GIL waits on the condition variable for at most the switch interval (5 ms by default, DEFAULT_INTERVAL 5000 µs, L91); if the wait times out, it sets gil_drop_request, which the running thread checks between bytecodes, and the running thread then releases the GIL and waits until someone else has taken it (so it cannot grab it straight back). A thread that blocks in a system call (sleep, recv, read) or in C code that releases the GIL (NumPy, PyTorch operators) lets others run meanwhile.


The consequence for latency: a thread that wakes up from I/O must get the GIL back, and if another thread is busy in Python it waits up to a whole switch interval. An "I/O" thread sleeping 2 ms, 300 times, next to 0, 1 or 2 threads doing pure-Python arithmetic, on 2 CPUs (gil_latency.py; median of 3 runs):






Next to one busy thread the I/O thread wakes 8.0 ms late (the 5 ms interval plus the wake-ups on both sides); next to two, 17.5 ms, with a 99th percentile of 86.9 ms, because the I/O thread competes with another waiter for each hand-over. sys.setswitchinterval(0.0005) brings it to 1.4 ms, at the price of more switching. This is the convoy effect David Beazley measured in 2010 for the GIL that 3.2 introduced (Understanding the Python GIL).


In ML work A thread in the training process that must react quickly (a heartbeat to the cluster scheduler, a metrics sender, an asyncio loop serving requests next to Python preprocessing) is delayed by milliseconds whenever other Python threads compute. Move the CPU work to processes or into GIL-releasing native code, or use a free-threaded build; the Python page measures free-threaded scaling and the lost updates it brings back.







9. Event-driven I/O: one thread, thousands of waits


ch. 33 Event-based concurrency from source measured here


The problem. A server with thousands of open connections (an inference server streaming tokens, a data service) spends almost all its time waiting. One thread per connection works but each thread is a stack, a kernel task and a context switch per event. 2,000 connections, each a Unix socket pair, served by one thread each or by one asyncio loop (conns.py; median of 3):




Threads reserve 8 MiB of address space each but touch little of it; the real costs are start-up and a context switch per message. The alternative is to ask the kernel one question, "which of these file descriptors are ready?", and handle only those. A file descriptor is the small integer naming an open file, pipe or socket (the sibling Processes page owns them); it is ready when a read or write on it would not block. Put it in non-blocking mode (O_NONBLOCK) and a read that would block returns EAGAIN instead.


select and poll: the whole list, every time


select (BSD, 1983) passes three bitmaps of descriptor numbers; poll (System V) passes an array of {fd, events}. On every call the kernel copies the list in, checks every descriptor's state, registers a wait on each, sleeps, and on wake-up checks them all again (fs/select.c L512-534 and L909, v5.10); the program then scans the whole list again for the ready ones. Cost grows with the number watched, not the number ready. select also has a hard limit: FD_SETSIZE is 1024, so it cannot watch descriptor 1024 or higher at all (select(2)).


epoll: the list lives in the kernel


epoll (Linux 2.6, 2002) splits registration from waiting: epoll_ctl(ADD) registers a descriptor once, and the kernel keeps the interest list in a red-black tree and a separate ready list (fs/eventpoll.c L195-204). When data arrives on a socket, the socket's wait-queue callback ep_poll_callback appends that one item to the ready list (L1244-1248); epoll_wait just takes items off the ready list. Its cost depends on the number ready, not the number watched. With N pipes watched and exactly one readable (evloop.c, one call returning one ready descriptor):






Level-triggered and edge-triggered


By default epoll is level-triggered: a descriptor is reported on every epoll_wait while data remains, because after reporting it the kernel puts it back on the ready list (L1758-1771). With EPOLLET it is edge-triggered: reported once per change (new data arriving), and not put back. Write 10 bytes to a pipe, read only 4, and ask again measured here:




Edge-triggered is cheaper (no re-reporting) but has one rule: after an edge, read (or accept, or write) until EAGAIN, or the remaining 6 bytes sit there unreported until more data happens to arrive, which on a quiet connection is never. Tokio's I/O layer, mio, registers every descriptor edge-triggered (let mut kind = EPOLLET;, mio src/sys/unix/selector/epoll.rs L115, v1.0.4) and its readiness tracking enforces the read-until-EAGAIN rule; Python's asyncio and libuv use level-triggered mode. macOS and the BSDs have the same idea under another name, kqueue (kqueue(2)), with filters for sockets, files, processes, signals and timers in one call; Python's selectors module prefers it where it exists (Lib/selectors.py L610-618).

All three follow the same readiness model: the kernel says "you can now read without blocking", and the program then makes the read itself. One cost remains: a system call per read and write, plus one per wait.


io_uring: the completion model


io_uring (Linux 5.1, 2019) changes the question to "do these operations and tell me when they are done". The program and the kernel share two ring buffers in memory: the program writes submission queue entries (SQEs: read this fd at this offset into this buffer) into one, and the kernel writes completion queue entries (CQEs: result, user tag) into the other (io_uring(7)). One io_uring_enter call submits a whole batch and can wait for completions; with IORING_SETUP_SQPOLL a kernel thread polls the submission ring and the program makes no system call at all. The rings are single-producer single-consumer queues (section 7). On this lab's kernel 5.10 measured here:




Three lessons from those lines. First, io_uring_setup failed in a default Docker container: Linux 5.10 charges the rings to the user's locked-memory limit (RLIMIT_MEMLOCK, 64 KiB in Docker) unless the process has CAP_IPC_LOCK (fs/io_uring.c L7869-7876 and L9274, v5.10), and the counter is per user, shared by every container running as root; the run passed --ulimit memlock=-1. Linux 5.12 moved the rings to memory-cgroup accounting from source (the ring_pages charge is gone from fs/io_uring.c at v5.12). Second, SQPOLL needs CAP_SYS_ADMIN before 5.11 (L7786). Third, reading 16,384 cached 4 KiB blocks, io_uring at depth 32 made 512 system calls instead of 16384, and the time per block fell from 1171 to 908 ns (22% less; medians of 3 noisy runs, which overlap): with the data already in memory, the 4 KiB copy and the per-request bookkeeping remain, and only the system-call entries are saved. io_uring pays off when operations really wait (disk, network) and many are in flight, when operations are tiny, or with SQPOLL and registered buffers on newer kernels not run here.


io_uring and security
Google reported that 60% of the Linux kernel exploits submitted to its kCTF bug bounty in the year to June 2023 used io_uring, and disabled it in ChromeOS and on its production servers (Google security blog, 2023-06-14). Docker 25.0 blocks the io_uring system calls in its default seccomp profile (moby #46762); this lab's Docker 20.10 still allows them. Expect io_uring to be unavailable in many containers.


In ML work Model servers are event loops: vLLM's OpenAI-compatible server is a uvicorn server started with uvloop.run(run_server(args)) (vllm/entrypoints/launchers/api_server/entry.py L222, v0.31.0) and SGLang passes loop="uvloop" to uvicorn (http_server.py L2713, v0.5.21): uvloop is libuv underneath, so one thread streams tokens to many clients while the GPU work runs in an engine loop. A blocking call inside an async handler (a synchronous tokenizer call, requests.get, a big JSON encode) stalls every connection on that loop: the Rust page's "blocking the runtime" experiment measures it. Data clients that stream shards from object storage use the same machinery (aiohttp, or Rust/C++ readers on tokio or io_uring).


Predict: an asyncio server is moved from 100 to 10,000 idle WebSocket clients. How does the cost of each epoll_wait call change?




About the same: epoll's cost follows the number of ready descriptors. The measurement above: 393 ns with 100 watched, 352 ns with 10,000. With poll it would grow about a hundredfold; with select it would fail, since descriptors above 1023 cannot be watched at all. (The open-file limit, ulimit -n, still has to allow 10,000 sockets.)

11. Common mistakes, interview questions, and the OSTEP map


Common mistakes


Checking a condition with if before wait()
Mesa semantics: re-check in a while loop (section 5 measured the failure 45 to 88 times in 200,000 items).


Spinning in user space
A spinlock with more runnable threads than CPUs, or under a CPU quota, wastes whole time slices (section 3). Use a mutex; glibc's adaptive mutex if you have measured that spinning helps.


Holding a lock while calling out
Callbacks, logging, I/O and __del__ inside a critical section create lock-order cycles and long hold times. Copy what you need, release, then call.


Forking a process that has threads
The child gets the memory, including locked locks, but only the forking thread. Use spawn or forkserver, or fork before starting threads.


Trusting volatile or plain variables between threads
No atomicity and no ordering (section 2: Peterson's lock failed on this CPU). Use atomics with the order you need, or a lock.


Blocking inside an event loop
A synchronous call in an async handler stops every connection on that loop; use asyncio.to_thread or a process pool for blocking and CPU work.


Edge-triggered epoll without draining
Read until EAGAIN after every edge, or the rest of the data waits forever (section 9).


Sizing thread pools from os.cpu_count() in a container
It reports the machine, not the quota; multiply by the number of worker processes and every library's own pool.


Interview questions, with model answers


What is the difference between a process and a thread on Linux?
Both are tasks the scheduler runs. A thread is created with clone flags that share the address space, file table and signal handlers with its creator (CLONE_VM, CLONE_FILES, CLONE_SIGHAND, CLONE_THREAD); a process gets copies (copy-on-write for memory). Threads communicate through memory for free and need synchronisation; processes need IPC but are isolated from each other's crashes, and in CPython each has its own GIL.


How does a mutex work, down to the kernel?
A word in user memory. Lock: CAS 0 to 1; if that fails, exchange in 2 ("contended") and call futex_wait(word, 2), which sleeps only if the word is still 2, checked in the kernel under the wait-queue lock. Unlock: exchange in 0; if the old value was 2, futex_wake(word, 1). Uncontended: two atomic instructions, no system call.


Why must the kernel re-check the value in futex_wait?
To avoid the lost wake-up: between a user-space check and going to sleep, the holder could release and send a wake-up to a thread not yet asleep. Comparing under the hash-bucket lock makes "check and sleep" atomic with respect to wakers.


Spinlock or mutex?
Spin only if the expected wait is shorter than a sleep and wake-up (a few microseconds) and the holder is guaranteed to be running (its own CPU, preemption disabled: kernel code). Otherwise sleep. Adaptive locks spin briefly then sleep.


What are the four conditions for deadlock, and how do you prevent it in practice?
Mutual exclusion, hold and wait, no preemption, circular wait. In practice: a global lock order (break the circle), checked with tools such as lockdep or TSan; trylock with backoff; not holding locks across calls into unknown code.


Why must you wait on a condition variable in a while loop?
Mesa semantics: wake-up means "the condition may have changed", and other threads can run between the signal and your return from wait; spurious wake-ups are also allowed. Re-check under the mutex.


select, poll, epoll: what is the difference, and when would you use io_uring?
select and poll pass the whole interest list on every call and the kernel checks each entry: O(watched); select is also capped at descriptor 1023. epoll keeps the list in the kernel and a ready list filled by callbacks: O(ready). io_uring is a completion model with shared submission and completion rings: batch many operations per system call or none (SQPOLL); worth it for many small or truly asynchronous operations (disk I/O at high queue depth), and often disabled in containers for security.


Level-triggered vs edge-triggered epoll?
Level: reported on every wait while ready. Edge: reported once per new event; you must drain to EAGAIN. Edge avoids repeated reports and thundering herds with several waiters; level is harder to misuse.


Why does a Python I/O thread get slow when another thread computes?
It must re-take the GIL after its I/O completes; the computing thread releases it only when asked, after the 5 ms switch interval. Measured: a 2 ms sleep came back about 8 ms late next to one busy thread.


A training job hangs with 0% CPU. How do you find out why?
top -H or ps -L to confirm all threads sleep; /proc/<pid>/task/*/wchan (futex waits mean locks, queues or condition variables; poll or read means waiting for data); py-spy dump --pid for Python stacks on every rank and worker; gdb -p with thread apply all bt for native threads; then find who should have released or sent what each one waits for.
