2. Races, atomic instructions and memory order

ch. 26.3 to 26.5, ch. 28.6 to 28.11

The problem. When two threads update the same memory and nothing orders them, the result depends on timing: a race condition. The classic one, count = count + 1 on two threads, is three instructions (load, add, store); if both threads load the same old value, one increment is lost. The root page measured it (two threads, 10 million increments each, about half lost) and its {{OS simulators|n:3f05c17b0d0d81c5a97ce991644af140}} tab steps the three instructions one at a time. A piece of code that touches shared data and must not run in two threads at once is a critical section; the guarantee that at most one thread is inside is mutual exclusion.

Atomic instructions. The hardware fix is an instruction that reads, modifies and writes one memory word as one indivisible step, which no other core can split. Three families matter:

Fetch-and-addold = *p; *p = old + v in one step. arm64 v8.1 has ldadd; x86-64 has lock xadd. Counters and reference counts.
Exchange (test-and-set)old = *p; *p = v. The simplest lock: while (xchg(&l, 1) == 1) ;
Compare-and-swap (CAS)if *p == expected then *p = new, and say whether it did. Everything lock-free is built on it. arm64 v8.1 cas; x86-64 lock cmpxchg.
Load-linked / store-conditionalthe older arm64 form (ldaxr then stlxr): the store fails if anyone wrote the word in between, and the code loops. GCC's "outline atomics" pick LSE or LL/SC at run time (the root's assembly shows a call to __aarch64_ldadd8_acq_rel).

An atomic update is not free: on one thread it cost 8.3 ns here against well under a nanosecond for a plain add, and with four threads updating one counter the cache line holding it bounces between cores (the C++ page's false-sharing measurement shows the same effect for neighbouring variables).

Memory order. A second, subtler problem: cores do not make their writes visible to each other in program order. Each core puts stores in a private store buffer and lets later loads run ahead of them. On x86-64 only that one reordering (a later load passing an earlier store) is allowed; arm64 allows more. Part 2 of the {{C++ page|n:3cd5c17b0d0d81ceadcee44fe9c023a0}} measures the message-passing reordering on this same chip and explains acquire, release and sequentially consistent orders; here is what it does to a lock.

Peterson's algorithm (OSTEP 28.6) is a correct lock for two threads using only loads and stores, proved in 1981 on the assumption that memory is sequentially consistent:

void lock(int me) {  int other = 1 - me;
    flag[me] = 1;                         // I want in
    turn = other;                         // but you go first if you also want in
    while (flag[other] && turn == other) ;  // wait while you want in and it is your turn
}
void unlock(int me) { flag[me] = 0; }

If the store flag[me] = 1 is still in this core's store buffer when the load flag[other] runs, both threads can read the other's flag as 0 and both enter. Two threads, each entering 20 million times, with a non-atomic count = count + 1 inside measured here (src/runs/c/peterson.c):





The fix is to declare the order you need: with sequentially consistent atomics the compiler emits the ordering instructions (stlr and ldar on arm64, or a full barrier dmb ish), and the lock is correct. Real locks never rely on plain loads and stores; they use an atomic exchange or CAS, which carry the ordering with them (acquire on lock, release on unlock).


Predict: a volatile int counter, incremented by two threads. Does volatile make count++ safe?




No. volatile only stops the compiler from removing or merging the accesses; the load, add and store are still three steps, and nothing orders them across cores. The root's race measurement used a volatile counter and lost about half the increments. Use an atomic (std::atomic, __atomic_fetch_add) or a lock.







3. Locks: spin, yield, or sleep


ch. 28 Locks, ch. 29 Lock-based concurrent data structures


A lock (or mutex, for mutual exclusion) is a word in memory plus two operations: lock() returns only when the caller owns it, unlock() gives it up. OSTEP judges a lock on three things: correctness (mutual exclusion), fairness (does every waiter eventually get it, or can one starve?) and performance (with no contention, with contention on many CPUs, and with contention on one CPU). The design question is what a thread does when the lock is taken:




Spinkeep retrying the atomic exchange. Best when the holder is running on another core and will release within nanoseconds. Terrible when the holder is not running: the spinner burns its whole time slice.


Yieldretry, and call sched_yield() after each failure to give the CPU away (OSTEP 28.13). A system call per failed attempt, and no promise about who runs next.


Sleepask the kernel to put the thread on a wait queue and wake it when the lock is released. Costs two system calls and a wake-up when contended, nothing else.


Spin, then sleep(two-phase or adaptive locks) spin briefly in case the holder is about to release, then sleep. glibc's PTHREAD_MUTEX_ADAPTIVE_NP spins at most 100 rounds by default, with exponential backoff ({{nptl/pthread_mutex_lock.c L139-158|https://github.com/bminor/glibc/blob/glibc-2.36/nptl/pthread_mutex_lock.c#L139-L158}}; tunable glibc.pthread.mutex_spin_count).

What to take from it:


    

  • Uncontended, a good lock costs about as much as one atomic instruction (9.2 ns for the hand-built futex lock, 10.1 ns for pthread_mutex_t), because it never enters the kernel. A lock that makes a system call on every unlock costs 288.6 ns: about thirty times more, for nothing.
    • 

  • Contended on enough CPUs, spinning burns CPU: with a short critical section the spinlock used 910.3 ns of CPU per acquisition against 437.2 ns for the mutex, and was slower in wall time too, because four cores fighting over one cache line slow each other down.
    • 

  • With more threads than CPUs, a spinner can wait for a thread that is not running. On one CPU with a long critical section, the holder is often preempted inside it; each spinner then burns a whole time slice before the holder runs again: 1492.5 ns per acquisition against 815.9 ns for the mutex and 791.5 ns for one thread doing the same work alone.
    • 

  • Hammering a lock rewards unfairness. In the no-work scenario the yield lock looks fastest, because a thread that just released the lock usually takes it again while its cache line is still hot and the others are yielding; the work is done, but by one thread at a time in long runs. Fairness costs throughput; a ticket lock (OSTEP 28.11: fetch-and-add a ticket, wait for your number) is fair and slower.
    • 

  • Never use a spinlock in user space unless every thread has its own CPU (as with pinned threads in a low-latency system). This is why the Linux kernel spins (kernel code can disable preemption while holding a spinlock) and user space sleeps.
    • 



Predict: a container with a one-CPU limit runs a job whose 8 threads take a spinlock around a 50 µs critical section. Roughly how long can one waiter spin before the holder runs again?




The holder can be descheduled inside the critical section; then every spinner that runs uses its full slice (a few milliseconds under CFS) doing nothing, and under a CPU quota the whole cgroup can be throttled until the next 100 ms period (the root's Debug lab, "CPU limit" cases). The measured one-CPU case above shows the effect at small scale.
