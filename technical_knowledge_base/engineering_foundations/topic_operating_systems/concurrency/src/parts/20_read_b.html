1. Threads: several flows of control, one address space

ch. 26 Concurrency: an introduction, ch. 27 Thread API

A process (owned by {{Processes and the system-call API|n:3f05c17b0d0d811e99f7cb8c15d12697}}) has one flow of control: one program counter and one stack. To use several cores on one shared data structure, a program needs several flows of control that see the same memory. That is a thread: its own registers, program counter and stack; everything else (heap, globals, open files, signal handlers) shared with the other threads of its process. Concurrency is several activities in progress at once; parallelism is some of them running at the same instant on different cores.

How Linux makes one. The kernel has no separate thread object: a thread is a task (a task_struct, the kernel's schedulable unit) created with flags that make it share its parent's memory and tables. pthread_create in glibc 2.36 asks for exactly this sharing ({{nptl/pthread_create.c L277-281|https://github.com/bminor/glibc/blob/glibc-2.36/nptl/pthread_create.c#L277-L281}}); strace shows the recipe measured here:





CLONE_VM, CLONE_FILES, CLONE_FS, CLONE_SIGHANDshare the address space, the file-descriptor table, the working directory, and the signal handlers


CLONE_THREADsame thread group: same process id for getpid(), a new thread id (gettid())


CLONE_SETTLSpoint the thread-pointer register (tpidr_el0 on arm64, fs on x86-64) at this thread's thread-local storage


CLONE_CHILD_CLEARTIDwhen the thread exits, the kernel writes 0 to its id word and does a futex wake on it: that is how pthread_join learns it ended




Cost measured here: creating and joining an empty thread took 136.0 µs with 4 CPUs available and 12.0 µs pinned to one CPU (best of 5 × 2000); the difference is the cross-CPU wake-up, unusually expensive in this VM (section 4). Each thread's stack reserves 8 MiB (from ulimit -s = 8192 KiB) of address space, not memory: 2,000 idle threads in section 8 reserved 18683 MiB of virtual memory but added only 13 MiB of resident memory, because untouched stack pages are never allocated (demand paging: {{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}}). On Linux threads and processes are both tasks, so a container's pids.max counts threads too (the root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}}, "BlockingIOError on fork: the pids limit counts threads too").


Stack guard, clone3, thread-local storage, and what exit() does (depth)


Before the clone, glibc maps the stack plus a guard region mapped PROT_NONE, so that a stack overflow faults instead of silently overwriting a neighbour. The guard is 64 KiB here although pthread_attr_getguardsize reports 4096 bytes: glibc rounds it up to the architecture minimum on arm64 ({{sysdeps/aarch64/nptl/pthreaddef.h L23|https://github.com/bminor/glibc/blob/glibc-2.36/sysdeps/aarch64/nptl/pthreaddef.h#L23}}, {{nptl/allocatestack.c L345-346|https://github.com/bminor/glibc/blob/glibc-2.36/nptl/allocatestack.c#L345-L346}}). Newer glibc versions try clone3 first and fall back to clone ({{clone-internal.c L52-55|https://github.com/bminor/glibc/blob/glibc-2.36/sysdeps/unix/sysv/linux/clone-internal.c#L52-L55}}); glibc 2.36 on arm64 has no clone3 wrapper, so the trace shows plain clone.


Thread-local storage (TLS) is a variable declared __thread (C) or thread_local (C++): one copy per thread, found through the thread pointer. errno is one, which is why two threads can make failing system calls at once without overwriting each other's error code. The same program printed its variables' addresses from three threads:




Thread 0 is the main thread. The shared global has one address; tls_var and the stack differ between the main thread and the others. Threads 1 and 2 print the same addresses because the program joins thread 1 before creating thread 2, and glibc reuses the cached stack and TLS block.


exit() from any thread ends the whole process. exit calls exit_group, which ends every thread in the thread group; to end only the calling thread, return from its function or call pthread_exit. The same holds for a signal whose default action is to terminate: it kills the whole process, whichever thread it was delivered to.









2. Races, atomic instructions and memory order


ch. 26.3 to 26.5, ch. 28.6 to 28.11


When two threads update the same memory and nothing orders them, the result depends on timing: a race condition. Two unordered accesses to one location, at least one a write, are a data race; in C, C++ and Rust's unsafe code that is undefined behaviour, not merely a wrong number. The classic one, count = count + 1 on two threads, is three instructions (load, add, store). Predict the final count after two increments from 41, then step it:




Two increments, one lost: the interleaving is the bug












The root page measured the same race at full speed (two threads, 10 million increments each, about half lost) and its {{OS simulators|n:3f05c17b0d0d81c5a97ce991644af140}} tab runs OSTEP's x86.py programs. A concurrency bug needs a particular order of steps, which is why it passes tests and fails in production. Code that touches shared data and must not run in two threads at once is a critical section.


Atomic instructions are the hardware fix: one read-modify-write of one word as one indivisible step. Three families matter:




Fetch-and-addold = *p; *p = old + v in one step. arm64 v8.1 has ldadd; x86-64 has lock xadd. Counters and reference counts.


Exchange (test-and-set)old = *p; *p = v. The simplest lock: while (xchg(&l, 1) == 1) ;


Compare-and-swap (CAS)if *p == expected then *p = new, and say whether it did. Everything lock-free is built on it. arm64 v8.1 cas; x86-64 lock cmpxchg.




An atomic update is not free: on one thread it cost 8.3 ns here against well under a nanosecond for a plain add, and with four threads updating one counter the cache line holding it bounces between cores ({{C++: the machine underneath, section 8|n:4055c17b0d0d811fa947ee576a97a516#cb-s8}} measures false sharing and shows the same effect for neighbouring variables).


Memory order. Cores also do not make their writes visible to each other in program order: each core puts stores in a private store buffer and lets later loads run ahead of them. x86-64 allows only that one reordering (a later load passing an earlier store); arm64 allows more. {{C++: the machine underneath, section 8|n:4055c17b0d0d811fa947ee576a97a516#cb-s8}} measures the message-passing reordering on this chip and explains acquire, release and sequentially consistent orders; here is what it does to a lock. Peterson's algorithm (OSTEP 28.6) is a correct two-thread lock using only loads and stores, proved in 1981 on the assumption that memory is sequentially consistent:


void lock(int me) {  int other = 1 - me;
    flag[me] = 1;                         // I want in
    turn = other;                         // but you go first if you also want in
    while (flag[other] && turn == other) ;  // wait while you want in and it is your turn
}
void unlock(int me) { flag[me] = 0; }


If the store flag[me] = 1 is still in this core's store buffer when the load flag[other] runs, both threads read the other's flag as 0 and both enter. Two threads, each entering 20 million times, with a non-atomic count = count + 1 inside measured here (src/runs/c/peterson.c):




The raw output of the ten runs (evidence)


The fix is to declare the order you need: with sequentially consistent atomics the compiler emits the ordering instructions (stlr and ldar on arm64, or a full barrier dmb ish) and the lock is correct. Real locks never rely on plain loads and stores; they use an atomic exchange or CAS, which carry the ordering with them (acquire on lock, release on unlock). volatile is not a fix: it only stops the compiler from removing or merging accesses; the load, add and store stay three steps, unordered across cores (the root's race measurement used a volatile counter).


Load-linked / store-conditional, and lock-free structures in brief (depth)


Load-linked / store-conditional is the older arm64 form (ldaxr then stlxr): the store fails if anyone wrote the word in between, and the code loops. GCC's "outline atomics" pick LSE or LL/SC at run time (the root's assembly shows a call to __aarch64_ldadd8_acq_rel).


A lock-free data structure guarantees that some thread always makes progress, even if others are paused at any instruction, because nobody ever holds a lock. The building block is a CAS loop: read the current value, compute the new one, and CAS it in; if another thread changed it meanwhile, the CAS fails and you retry. A stack push:


do { n->next = head; } while (!CAS(&head, n->next, n));


The traps: the ABA problem (the head was A, became B, became A again; the CAS succeeds although the list changed underneath; fixed with version counters or safe memory reclamation), and freeing memory another thread may still be reading (fixed by hazard pointers, epochs, or RCU, read-copy-update, which the Linux kernel uses so that readers take no lock at all: {{What is RCU|https://docs.kernel.org/RCU/whatisRCU.html}}). The common, safe case in practice is a single-producer single-consumer ring buffer: one thread only advances the tail, the other only the head, and each reads the other's index with acquire order. io_uring's two rings (section 8) are exactly that, shared between a program and the kernel. Use lock-free structures from a library ({{C++: the machine underneath|n:4055c17b0d0d811fa947ee576a97a516#cb-s8}}'s atomics, Rust's crossbeam, std::atomic counters); a lock is usually fast enough (section 3: 10 ns uncontended) and far easier to get right.
