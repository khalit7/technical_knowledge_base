9. Choosing threads, processes or an event loop

The three differ in what they share and what a wait costs, so the choice follows from what the work waits on and whether it computes in Python:

Waiting picks between an event loop and threads; computing in Python picks processes (or free-threaded threads)

Threads

  • Share memory for free, so shared state needs locks (sections 2 to 6).
  • Create + join 136.0 µs here; 8 MiB of address space each, about 7 KiB resident when idle (13 MiB added for 2,000 threads).
  • Parallel for native code that releases the GIL, and for Python on the free-threaded build; under the GIL, concurrency for waiting only.
  • No isolation: a crash or a corrupted heap takes every thread down.

Processes

  • A separate address space: a crash or a corrupted heap in one cannot touch the other, and in CPython each process has its own GIL.
  • Data moves by pickling or shared memory; PyTorch's DataLoader uses worker processes for exactly that trade.
  • fork after threads exist copies held locks (section 6); spawn and forkserver avoid it.
  • Start-up and copies cost: the four-process pool in {{Python: concurrency, asyncio and the GIL, section 1|n:4055c17b0d0d81bdbee8c37d80b55a0e#s1}} ran 2.7 times faster, not four.

One event loop

  • One thread, thousands of waits: 2,000 connections added 5 MiB and started serving in 22 ms (section 8).
  • Callbacks run one at a time, so no locks between them, but one blocking call or CPU-heavy handler stalls every connection.
  • Needs non-blocking libraries all the way down; CPU work goes to a thread or process pool.

"About 7 KiB" is derived: 13 × 1,024 KiB / 2,000 threads = 6.7 KiB. Real systems combine them: vLLM is an event loop in front of an engine process; a training job is processes (workers) of threads (pools).

The thread count is a design input. Each worker runs its own copy of every thread pool a library creates (PyTorch sets torch.set_num_threads(1) in workers, but tokenizers, OpenCV and NumPy's BLAS have their own), and in a container every thread counts against pids.max and shares the CPU quota (the root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}}, "Too many threads for the CPUs you have"; scheduling is {{Scheduling and CPU time|n:3f05c17b0d0d81ed9c18cc47c6bfdf76}}). os.cpu_count() reports the machine, not the quota: multiply by the number of worker processes and every library's own pool.


When a job hangs at 0% CPU top -H or ps -L to confirm all threads sleep; /proc/<pid>/task/*/wchan (futex waits mean locks, queues or condition variables; poll or read means waiting for data); py-spy dump --pid for Python stacks on every rank and worker; gdb -p <pid> -ex "thread apply all bt" for native threads; then find who should have released or sent what each one waits for. In a distributed job the usual cause is not a lock but a collective that one rank never reaches (one rank skipped an all-reduce, or is stuck in its data loader): every other rank's main thread sits in a CUDA synchronisation or a futex while the GPU kernel spins waiting for the missing peer, and the watchdog fires after the process group's timeout. py-spy dump --pid on every rank (or PyTorch's flight recorder, TORCH_NCCL_TRACE_BUFFER_SIZE) shows which rank is somewhere else; {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}} covers the collectives, and GPU-side concurrency (streams) is {{Streams, CUDA graphs and multi-GPU programming|n:3f05c17b0d0d81b19a6acab65c370b75}}'s.
