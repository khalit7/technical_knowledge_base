10. In a training job: every thread, and what it waits on

measured here from source GPU parts not run here

The root's job (2 DataLoader workers, fork, torch.set_num_threads(n)), stopped while stepping and looked at three ways: /proc/<pid>/task/* (name, state, wait channel), py-spy dump (the Python threads), and gdb backtraces of every thread classified by the functions on their stacks (job_threads.sh, classify_threads.py):



Reading it:


    

  • The main process runs the training loop in its main thread. Its other threads are PyTorch's OpenMP pool (libgomp; between operators they wait at a barrier, spinning briefly in do_spin and then sleeping in futex_wait), two Python QueueFeederThreads (each multiprocessing.Queue has one: put() appends to an in-process buffer and the feeder thread pickles it into the pipe to the worker), and a libtorch_cpu thread asleep on a futex.
    • 

  • Each worker (named pt_data_worker by PyTorch) waits in poll for the next indices, plus a feeder thread for its result queue and a _serve thread: multiprocessing's resource sharer, which hands file descriptors for shared-memory tensors to the main process over a Unix socket (the recvmsg calls below).
    • 

  • Nearly every thread is asleep on a futex. Attached for 3 seconds with strace, the job made about 59 futex calls per training step with 2 torch threads (39 with 1, 86 with 4), about a fifth of them EAGAIN (section 4): barrier wake-ups for each parallel operator and the queues' locks and semaphores. Strace slows the job about tenfold, so count, do not time, under it.
    • 



The thread count is a design input. Each worker runs its own copy of every thread pool a library creates (PyTorch sets torch.set_num_threads(1) in workers, but tokenizers, OpenCV and NumPy's BLAS have their own), and in a container every thread counts against pids.max and shares the CPU quota (the root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}}, "Too many threads for the CPUs you have"; scheduling is the sibling {{Scheduling and CPU time|n:3f05c17b0d0d81ed9c18cc47c6bfdf76}} page).

When a distributed job hangs The usual cause is not a lock but a collective that one rank never reaches (one rank skipped an all-reduce, or is stuck in its data loader). Every other rank's main thread sits in a CUDA synchronisation or a futex while the GPU kernel spins waiting for the missing peer; the watchdog fires after the process group's timeout. py-spy dump --pid on every rank (or PyTorch's flight recorder, TORCH_NCCL_TRACE_BUFFER_SIZE) shows which rank is somewhere else. {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}} covers the collectives themselves.







11. Common mistakes, interview questions, and the OSTEP map


Common mistakes


Checking a condition with if before wait()
Mesa semantics: re-check in a while loop (section 5 measured the failure 45 to 88 times in 200,000 items).


Spinning in user space
A spinlock with more runnable threads than CPUs, or under a CPU quota, wastes whole time slices (section 3). Use a mutex; glibc's adaptive mutex if you have measured that spinning helps.


Holding a lock while calling out
Callbacks, logging, I/O and __del__ inside a critical section create lock-order cycles and long hold times. Copy what you need, release, then call.


Forking a process that has threads
The child gets the memory, including locked locks, but only the forking thread. Use spawn or forkserver, or fork before starting threads.


Trusting volatile or plain variables between threads
No atomicity and no ordering (section 2: Peterson's lock failed on this CPU). Use atomics with the order you need, or a lock.


Blocking inside an event loop
A synchronous call in an async handler stops every connection on that loop; use asyncio.to_thread or a process pool for blocking and CPU work.


Edge-triggered epoll without draining
Read until EAGAIN after every edge, or the rest of the data waits forever (section 9).


Sizing thread pools from os.cpu_count() in a container
It reports the machine, not the quota; multiply by the number of worker processes and every library's own pool.


Interview questions, with model answers


What is the difference between a process and a thread on Linux?
Both are tasks the scheduler runs. A thread is created with clone flags that share the address space, file table and signal handlers with its creator (CLONE_VM, CLONE_FILES, CLONE_SIGHAND, CLONE_THREAD); a process gets copies (copy-on-write for memory). Threads communicate through memory for free and need synchronisation; processes need IPC but are isolated from each other's crashes, and in CPython each has its own GIL.


How does a mutex work, down to the kernel?
A word in user memory. Lock: CAS 0 to 1; if that fails, exchange in 2 ("contended") and call futex_wait(word, 2), which sleeps only if the word is still 2, checked in the kernel under the wait-queue lock. Unlock: exchange in 0; if the old value was 2, futex_wake(word, 1). Uncontended: two atomic instructions, no system call.


Why must the kernel re-check the value in futex_wait?
To avoid the lost wake-up: between a user-space check and going to sleep, the holder could release and send a wake-up to a thread not yet asleep. Comparing under the hash-bucket lock makes "check and sleep" atomic with respect to wakers.


Spinlock or mutex?
Spin only if the expected wait is shorter than a sleep and wake-up (a few microseconds) and the holder is guaranteed to be running (its own CPU, preemption disabled: kernel code). Otherwise sleep. Adaptive locks spin briefly then sleep.


What are the four conditions for deadlock, and how do you prevent it in practice?
Mutual exclusion, hold and wait, no preemption, circular wait. In practice: a global lock order (break the circle), checked with tools such as lockdep or TSan; trylock with backoff; not holding locks across calls into unknown code.


Why must you wait on a condition variable in a while loop?
Mesa semantics: wake-up means "the condition may have changed", and other threads can run between the signal and your return from wait; spurious wake-ups are also allowed. Re-check under the mutex.


select, poll, epoll: what is the difference, and when would you use io_uring?
select and poll pass the whole interest list on every call and the kernel checks each entry: O(watched); select is also capped at descriptor 1023. epoll keeps the list in the kernel and a ready list filled by callbacks: O(ready). io_uring is a completion model with shared submission and completion rings: batch many operations per system call or none (SQPOLL); worth it for many small or truly asynchronous operations (disk I/O at high queue depth), and often disabled in containers for security.


Level-triggered vs edge-triggered epoll?
Level: reported on every wait while ready. Edge: reported once per new event; you must drain to EAGAIN. Edge avoids repeated reports and thundering herds with several waiters; level is harder to misuse.


Why does a Python I/O thread get slow when another thread computes?
It must re-take the GIL after its I/O completes; the computing thread releases it only when asked, after the 5 ms switch interval. Measured: a 2 ms sleep came back about 8 ms late next to one busy thread.


A training job hangs with 0% CPU. How do you find out why?
top -H or ps -L to confirm all threads sleep; /proc/<pid>/task/*/wchan (futex waits mean locks, queues or condition variables; poll or read means waiting for data); py-spy dump --pid for Python stacks on every rank and worker; gdb -p with thread apply all bt for native threads; then find who should have released or sent what each one waits for.
