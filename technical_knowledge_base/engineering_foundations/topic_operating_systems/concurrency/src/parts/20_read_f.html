8. Event-driven I/O: one thread, thousands of waits

ch. 33 Event-based concurrency from source measured here

A server with thousands of open connections (an inference server streaming tokens, a data service) spends almost all its time waiting. Blocking I/O with a thread per connection works, but each thread is a stack, a kernel task and a context switch per event. 2,000 connections, each a Unix socket pair, served by one thread each or by one asyncio loop (conns.py; median of 3):

The alternative is non-blocking I/O plus one question to the kernel, "which of these file descriptors are ready?". A descriptor (the integer naming an open file, pipe or socket) is ready when a read or write on it would not block; put it in non-blocking mode (O_NONBLOCK) and a read that would block returns EAGAIN instead. The designs differ in how the question is asked:

select, poll: the whole list, every timeselect (BSD, 1983) passes three bitmaps of descriptor numbers, poll (System V) an array of {fd, events}. On every call the kernel copies the list in, checks every descriptor, registers a wait on each, sleeps, and on wake-up checks them all again ({{fs/select.c, v5.10|https://github.com/torvalds/linux/blob/v5.10/fs/select.c#L505-L536}}); the program then scans the whole list again. Cost grows with the number watched. FD_SETSIZE is 1024, so select cannot watch descriptor 1024 or higher at all ({{select(2)|https://man7.org/linux/man-pages/man2/select.2.html}}).
epoll: the list lives in the kernel(Linux 2.6, 2002) epoll_ctl(ADD) registers a descriptor once into an interest list (a red-black tree) with a separate ready list ({{fs/eventpoll.c L195-204|https://github.com/torvalds/linux/blob/v5.10/fs/eventpoll.c#L195-L204}}). When data arrives, the socket's wait-queue callback ep_poll_callback appends that one item to the ready list ({{L1244-1248|https://github.com/torvalds/linux/blob/v5.10/fs/eventpoll.c#L1240-L1248}}); epoll_wait just takes items off it. Cost follows the number ready.
io_uring: completions, not readiness(Linux 5.1, 2019) "do these operations and tell me when they are done": the program writes submission queue entries (SQEs) into a ring shared with the kernel, the kernel does the I/O and writes completion queue entries (CQEs) into another ({{io_uring(7)|https://man7.org/linux/man-pages/man7/io_uring.7.html}}).

At 10,000 idle clients, epoll_wait costs 352 ns against 393 ns at 100; poll 650 µs: from 100 to 10,000 watched, poll grows about a hundredfold, and select cannot go past descriptor 1023 at all.

Level-triggered and edge-triggered

By default epoll is level-triggered: a descriptor is reported on every epoll_wait while data remains, because after reporting it the kernel puts it back on the ready list ({{L1758-1771|https://github.com/torvalds/linux/blob/v5.10/fs/eventpoll.c#L1756-L1772}}). With EPOLLET it is edge-triggered: reported once per change (new data arriving), and not put back. Write 10 bytes to a pipe, read only 4, and ask again measured here:



Edge-triggered is cheaper (no re-reporting) but has one rule: after an edge, read (or accept, or write) until EAGAIN, or the remaining 6 bytes sit unreported until more data happens to arrive, which on a quiet connection is never. asyncio and libuv use level-triggered mode, tokio edge-triggered; macOS and the BSDs have the same design as kqueue (depth block below).


What each runtime waits with, and its loop in one line (depth)


Tokio's I/O layer, mio, registers every descriptor edge-triggered (let mut kind = EPOLLET;, {{mio src/sys/unix/selector/epoll.rs L115, v1.0.4|https://github.com/tokio-rs/mio/blob/v1.0.4/src/sys/unix/selector/epoll.rs#L112-L117}}) and its readiness tracking enforces the rule; Python's asyncio and libuv use level-triggered mode. macOS and the BSDs have the same idea as kqueue ({{kqueue(2)|https://man.freebsd.org/cgi/man.cgi?query=kqueue&sektion=2}}), with filters for sockets, files, processes, signals and timers in one call; Python's selectors module prefers it where it exists ({{Lib/selectors.py L610-618|https://github.com/python/cpython/blob/v3.11.2/Lib/selectors.py#L606-L618}}).


All follow the readiness model (the kernel says "you can read now"; the program then makes the read itself: one system call per read and write, plus one per wait). Python asyncio waits with epoll, level-triggered, via selectors.EpollSelector; Node.js's libuv and uvloop with epoll_pwait plus a thread pool for file I/O and DNS; Rust's tokio with epoll, edge-triggered, via mio, under a work-stealing pool of threads. Their loops are taught on the {{Python|n:3cd5c17b0d0d81b28acdea39e7a4d998}}, {{JS/TS|n:3cd5c17b0d0d81dbac7be3b8686be023}} and {{Rust|n:3c65c17b0d0d8156bed9ead8a22f33b0}} pages.

io_uring on a real kernel


One io_uring_enter call submits a whole batch and can wait for completions; with IORING_SETUP_SQPOLL a kernel thread polls the submission ring and the program makes no system call at all. The rings are single-producer single-consumer queues (section 2, depth). On this lab's kernel 5.10 measured here (raw output, with the setup failures, in the closed block below), reading 16,384 cached 4 KiB blocks, io_uring at depth 32 made 512 system calls instead of 16384, and the time per block fell from 1171 to 908 ns (22% less; medians of 3 noisy runs, which overlap): with the data already in memory, the 4 KiB copy and the per-request bookkeeping remain and only the system-call entries are saved. io_uring pays off when operations really wait (disk, network) and many are in flight, when operations are tiny, or with SQPOLL and registered buffers on newer kernels not run here.


io_uring is often unavailable in containers
Google reported that 60% of the Linux kernel exploits submitted to its kCTF bug bounty in the year to June 2023 used io_uring, and disabled it in ChromeOS and on its production servers ({{Google security blog, 2023-06-14|https://security.googleblog.com/2023/06/learnings-from-kctf-vrps-42-linux.html}}). Docker 25.0 blocks the io_uring system calls in its default seccomp profile ({{moby #46762|https://github.com/moby/moby/pull/46762}}); this lab's Docker 20.10 still allows them.


The io_uring runs, and why io_uring_setup failed here at first (depth)




First, io_uring_setup failed in a default Docker container: Linux 5.10 charges the rings to the user's locked-memory limit (RLIMIT_MEMLOCK, 64 KiB in Docker) unless the process has CAP_IPC_LOCK ({{fs/io_uring.c L7869-7876 and L9274, v5.10|https://github.com/torvalds/linux/blob/v5.10/fs/io_uring.c#L7862-L7880}}), and the counter is per user, shared by every container running as root; the run passed --ulimit memlock=-1. Linux 5.12 moved the rings to memory-cgroup accounting from source (the ring_pages charge is gone from fs/io_uring.c at v5.12). Second, SQPOLL needs CAP_SYS_ADMIN before 5.11 ({{L7786|https://github.com/torvalds/linux/blob/v5.10/fs/io_uring.c#L7782-L7790}}).




In ML work Model servers are event loops: vLLM's OpenAI-compatible server is a uvicorn server started with uvloop.run(run_server(args)) ({{vllm/entrypoints/launchers/api_server/entry.py L222, v0.31.0|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/entrypoints/launchers/api_server/entry.py#L222}}) and SGLang passes loop="uvloop" to uvicorn ({{http_server.py L2713, v0.5.21|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/entrypoints/http_server.py#L2713}}): uvloop is libuv underneath, so one thread streams tokens to many clients while the GPU work runs in an engine loop. A blocking call in an async handler (a synchronous tokenizer call, requests.get, a big JSON encode) stalls every connection on that loop; use asyncio.to_thread or a process pool (the Rust page's "blocking the runtime" experiment measures the stall). Data clients that stream shards from object storage use the same machinery (aiohttp, or Rust/C++ readers on tokio or io_uring). At 10,000 sockets the open-file limit, ulimit -n, must allow them.
