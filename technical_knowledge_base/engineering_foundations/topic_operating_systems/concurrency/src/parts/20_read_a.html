In one screen

Concurrency means several activities in progress at the same time inside one program; parallelism means some of them really run at the same instant, on different CPU cores. A training job is concurrent everywhere: the training loop, a pool of math threads inside PyTorch, DataLoader worker processes and the threads that feed their queues, a checkpoint writer, and on a GPU node NCCL's communication threads and PyTorch's watchdog. This page is about the machinery that lets those activities share memory and wait for each other without corrupting data or wasting CPUs.

The running example is the training job of the {{root page|n:3f05c17b0d0d81c5a97ce991644af140}} (a CPU-only PyTorch run with a memory-mapped dataset and two DataLoader workers). Seen as threads, while it trains (measured in section 10):

main process (the training loop) ├─ MainThread runs forward, backward, optimizer step; holds the GIL while in Python ├─ QueueFeederThread x2 pickles batch indices into each worker's pipe └─ native threads OpenMP's pool for PyTorch's math; asleep in futex_wait between operators worker process x2 (fork of main) ├─ pt_data_worker reads samples, builds a batch, puts it on the result queue └─ helper threads queue feeder, file-descriptor server; asleep in poll or futex_wait

Almost every one of those threads is asleep at any instant, and nearly all of them are asleep in the same kernel function, futex_wait. The rest of the page explains why.

1. Threads: several flows of control, one address space

ch. 26 Concurrency: an introduction, ch. 27 Thread API

The problem. A process (the sibling page {{Processes and the system-call API|n:3f05c17b0d0d811e99f7cb8c15d12697}} owns it) is one running program with one flow of control: one program counter (the address of the next instruction) and one stack (the memory holding local variables and return addresses of the functions in progress). To use several cores on one shared data structure, a program needs several flows of control that see the same memory. That is a thread: its own registers, program counter and stack, and everything else (heap, globals, open files, signal handlers) shared with the other threads of its process.

How Linux makes one. The kernel has no separate thread object: a thread is a task (the kernel's schedulable unit, a task_struct) that shares its parent's memory and tables because of the flags it was created with. pthread_create in glibc 2.36 asks for exactly this sharing ({{nptl/pthread_create.c L277-281|https://github.com/bminor/glibc/blob/glibc-2.36/nptl/pthread_create.c#L277-L281}}), and strace shows the whole recipe for one thread measured here:





CLONE_VM, CLONE_FILES, CLONE_FS, CLONE_SIGHANDshare the address space, the file-descriptor table, the working directory, and the signal handlers


CLONE_THREADsame thread group: same process id for getpid(), a new thread id (gettid())


CLONE_SETTLSpoint the thread-pointer register (tpidr_el0 on arm64, fs on x86-64) at this thread's thread-local storage


CLONE_CHILD_CLEARTIDwhen the thread exits, the kernel writes 0 to its id word and does a futex wake on it: that is how pthread_join learns it ended




Before the clone, glibc maps the new thread's stack: 8 MiB (the default comes from the stack resource limit, ulimit -s = 8192 KiB) plus a guard region mapped PROT_NONE so that a stack overflow faults instead of silently overwriting a neighbour. The guard is 64 KiB here although pthread_attr_getguardsize reports 4096 bytes: glibc rounds it up to the architecture minimum on arm64 ({{sysdeps/aarch64/nptl/pthreaddef.h L23|https://github.com/bminor/glibc/blob/glibc-2.36/sysdeps/aarch64/nptl/pthreaddef.h#L23}}, {{nptl/allocatestack.c L345-346|https://github.com/bminor/glibc/blob/glibc-2.36/nptl/allocatestack.c#L345-L346}}). Newer glibc versions try clone3 first and fall back to clone ({{clone-internal.c L52-55|https://github.com/bminor/glibc/blob/glibc-2.36/sysdeps/unix/sysv/linux/clone-internal.c#L52-L55}}); glibc 2.36 on arm64 has no clone3 wrapper, so the trace shows plain clone.


Thread-local storage (TLS) is a variable declared __thread (C) or thread_local (C++): one copy per thread, found through the thread pointer. errno is one, which is why two threads can make failing system calls at once without overwriting each other's error code. The same program printed its variables' addresses from three threads:




Thread 0 is the main thread. The shared global has one address; tls_var and the stack differ between the main thread and the others. Threads 1 and 2 print the same addresses because the program joins thread 1 before creating thread 2, and glibc reuses the cached stack and TLS block.


Cost measured here: creating and joining an empty thread took 136.0 µs with 4 CPUs available and 12.0 µs pinned to one CPU (best of 5 × 2000). The difference is the cross-CPU wake-up, which is unusually expensive in this VM (section 4 measures it). The 8 MiB stack costs address space, not memory: 2,000 idle threads in section 9 reserved 18683 MiB of virtual memory but added only 13 MiB of resident memory, because untouched stack pages are never allocated (copy-on-write and demand paging: the sibling {{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}} page).


Thread or process? A thread is cheaper to create and shares memory for free; a process gets a separate address space, so a crash or a corrupted heap in one cannot touch the other, and in CPython each process has its own GIL (section 8). PyTorch's DataLoader uses processes for that reason, and pays with pickling and shared memory to move batches. On Linux both are tasks, so a container's pids.max limit counts threads too: the root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} case "BlockingIOError on fork: the pids limit counts threads too" shows it.


Predict: one thread of a training process calls exit(1) from a background thread. What happens to the other threads?




exit calls exit_group, which ends every thread in the thread group. To end only the calling thread, return from its function or call pthread_exit. The same holds for a signal whose default action is to terminate: it kills the whole process, whichever thread it was delivered to.
