The idea in one screen

Threads share one address space, so every shared update needs an atomic instruction that orders it, and a wait should cost nothing until it is real: an uncontended lock is one atomic instruction (about 10 ns), and only a thread that truly has to wait asks the kernel to put it to sleep, on a futex when it waits for another thread, on epoll or io_uring when it waits for I/O.

Every wait on Linux ends in one of two kernel queues

Threads: a lock, condition variable, queue, barrier or the GIL is a word in your memory; the kernel is involved only when the word says someone must sleep. I/O: an event loop registers its sockets once and is woken only with the ready ones. In the root's training job (section 10), the main thread, PyTorch's OpenMP pool and the queue feeder threads sleep on futexes; the DataLoader workers sleep in poll. Numbers measured here (sections 3, 4, 8).

Thread
a flow of control (registers, stack) that shares its process's memory and files.
Race, data race
a result that depends on timing; a data race is two unordered accesses to one location, at least one a write.
Critical section
code on shared data that at most one thread may run at a time (mutual exclusion).
Atomic instruction
a read-modify-write of one word that no other core can split (CAS, exchange, fetch-and-add).
Memory order
which of a core's writes other cores see, and in what order; acquire and release say what must not be reordered.
Futex
a lock word in user memory plus two kernel calls: sleep if the word still equals v, wake n sleepers.
Condition variable, semaphore
sleep until another thread says a condition may hold; a counter that blocks at zero.
Deadlock
a cycle of threads each holding what the next one waits for.
GIL
CPython's single lock around bytecode; the free-threaded build replaces it with per-object locks.
Readiness, completion
"this descriptor can be read now" (epoll, kqueue) against "this read is done" (io_uring).
