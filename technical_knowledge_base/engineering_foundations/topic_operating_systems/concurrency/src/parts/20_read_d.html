5. Waiting for something: condition variables, semaphores, barriers

ch. 30 Condition variables, ch. 31 Semaphores

A lock says "one at a time"; it cannot say "wait until a batch is ready" or "until there is room in the queue". A condition variable is a queue of sleeping threads attached to a condition the program tracks in its own variables, always used with a mutex: wait(cv, m) atomically releases m and sleeps, and re-takes m before returning; signal(cv) wakes one sleeper, broadcast(cv) all. The atomic "release and sleep" is section 4's lost-wake-up problem, solved the same way (glibc builds it on futexes).

Rule 1: re-check the condition in a while loop. POSIX and Linux use Mesa semantics: a woken thread is only told the condition was true at some moment; another thread may have run in between and made it false again (and implementations may wake a thread spuriously). OSTEP's producer/consumer with one slot, one producer and two consumers, 200,000 items measured here (condvar.c, three runs of each version; raw output in the closed block below). With if, a consumer woke up to an empty slot 45 to 88 times per run: in real code, reading garbage or an exception from an empty queue, rarely enough to pass every test. With while, the same situations happen (37 to 70 re-checks per run) and are harmless. The lab in section 4 counts every schedule of a two-item version: with if, 64,228 of 42,827,788 schedules make a consumer read an empty slot; with while, none of 91,732,872 do. Open the "if" scenario in the lab and let C2 barge in between P's signal and C1's return.

Rule 2: one condition variable per condition. With one variable shared by "slot full" and "slot empty", a consumer's signal can wake the other consumer instead of the producer; then all three sleep and the program hangs at 0% CPU. It hung in 3 of 3 runs, after a handful of items. Use two condition variables (or broadcast, which is correct but wakes everyone). NCCL's proxy thread follows rule 1 with a predicate lambda: "Predicate avoids lost wakeups and guarantees we observe stop after ncclProxyProgressDestroy" ({{src/proxy.cc L849-851, NCCL v2.32.3-1|https://github.com/NVIDIA/nccl/blob/v2.32.3-1/src/proxy.cc#L849-L851}}).

A semaphore (Dijkstra, 1960s) is a counter: wait (P, down) decrements it and sleeps while it would go below zero; post (V, up) increments it and wakes a sleeper. Initialised to 1 it is a lock; to N it admits at most N holders ("at most 2 prefetched batches per worker", the DataLoader's prefetch_factor, is this idea); to 0 it is a "wait until done" signal. POSIX sem_t is a futex word; multiprocessing's locks, semaphores and queues are sem_t in /dev/shm. Unlike a mutex, any thread can post a semaphore: nothing records an owner, which makes it easy to misuse.

A barrier makes N threads wait until all N arrive. OpenMP puts one at the end of every parallel region, which is where PyTorch's math threads sit between operators: libgomp spins at the barrier for a while (do_spin in libgomp/config/linux/wait.h; tuned by {{GOMP_SPINCOUNT|https://gcc.gnu.org/onlinedocs/libgomp/GOMP_005fSPINCOUNT.html}} and OMP_WAIT_POLICY) and then sleeps on a futex; section 10's gdb snapshots find the pool threads in futex_wait inside gomp_barrier_wait_end.

The condition-variable runs, and reader-writer locks (depth)


A reader-writer lock lets many readers in at once or one writer alone; good for data read far more than written (a model registry, a config). The catch is starvation: glibc's pthread_rwlock_t prefers readers by default, so a steady stream of readers can keep a writer waiting indefinitely (PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP changes it; {{pthread_rwlockattr_setkind_np(3)|https://man7.org/linux/man-pages/man3/pthread_rwlockattr_setkind_np.3.html}}). For short critical sections an rwlock is often slower than a mutex, since even readers write the shared reader count.









6. Deadlock, and the other concurrency bugs


ch. 32 Common concurrency problems


A deadlock is a set of threads each waiting for something another member holds, so none can move. It needs four conditions at once (Coffman, 1971): mutual exclusion, hold and wait, no preemption (nobody can take a held lock away), and a circular wait. Remove any one and deadlock is impossible.


Two threads, two locks, opposite orders: a cycle in the wait-for graph




T1 holds A and waits for B; T2 holds B and waits for A. Each arrow is one of the four conditions doing its part. Taking locks in one global order (A before B, everywhere) removes the arrow that closes the cycle; this is the program below run with --ordered, which finishes.

The signature of a deadlock: every thread in state S (sleeping), every wait channel futex_wait_queue_me, 0% CPU, and py-spy pointing at the two with lines. A busy-looping bug looks the opposite (state R, 100% CPU).


Fixes and tools One lock order per program, written down; never call unknown code (callbacks, logging handlers, __del__) while holding a lock (copy what you need, release, then call): thread A holding L and calling logging.info() while a handler thread holds the handler's lock and wants L is a circular wait, although logging is "thread-safe" (each call is safe on its own); lock.acquire(timeout=...) in Python turns a silent hang into an error you can log; faulthandler.dump_traceback_later(timeout) prints every thread's stack if the job stops progressing; glibc's PTHREAD_MUTEX_ERRORCHECK returns EDEADLK when a thread re-locks a mutex it holds; ThreadSanitizer (-fsanitize=thread) reports lock-order inversions as well as data races.


The training-job deadlock everyone meets is not two locks but fork while another thread holds one: the child gets a copy of the locked lock and no thread to release it. The root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} reproduces it ("A worker hangs forever: fork while another thread holds a lock") and {{Processes|n:3f05c17b0d0d811e99f7cb8c15d12697}} covers start methods (spawn or forkserver, or fork before starting threads); it is why Python 3.14 made forkserver the default on Linux. Databases face the same four conditions with a different cure (detect the cycle and abort a victim): {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}}.


Most concurrency bugs are not deadlocks (depth)
Lu et al. studied 105 concurrency bugs in MySQL, Apache, Mozilla and OpenOffice: 74 were not deadlocks and 31 were; 97% of the non-deadlock bugs were of two kinds (as summarised in OSTEP ch. 32, from {{Learning from Mistakes, ASPLOS 2008|https://dl.acm.org/doi/10.1145/1346281.1346323}}):




Atomicity violationcode assumed two steps happen together, and another thread ran between them: if (p) use(p); while another thread sets p = NULL. Fix: one lock around both steps.


Order violationcode assumed A happens before B, and nothing enforced it: a thread uses an object before its creator finished initialising it. Fix: a condition variable or semaphore that B waits on.
