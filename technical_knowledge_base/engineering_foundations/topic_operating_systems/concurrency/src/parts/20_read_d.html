5. Waiting for something: condition variables, semaphores, reader-writer locks, barriers

ch. 30 Condition variables, ch. 31 Semaphores

The problem. A lock says "one at a time"; it cannot say "wait until a batch is ready" or "wait until there is room in the queue". Checking a flag in a loop (spinning) wastes a CPU; a thread needs to sleep until another thread says the condition may now hold.

A condition variable is a queue of sleeping threads attached to a condition the program tracks in its own variables, always used with a mutex: wait(cv, m) atomically releases m and sleeps, and re-takes m before returning; signal(cv) wakes one sleeper, broadcast(cv) wakes all. The atomic "release and sleep" is the same lost-wake-up problem as in section 4, solved the same way (glibc builds it on futexes).

Rule 1: re-check the condition in a while loop. POSIX and Linux use Mesa semantics: a woken thread is only told that the condition was true at some moment; another thread may have run in between and made it false again (and implementations may wake a thread spuriously). OSTEP's producer/consumer with one slot, one producer and two consumers, run for 200,000 items measured here (condvar.c):



With if, a consumer woke up to an empty slot 45 to 88 times per run: in real code that is reading garbage or an exception from an empty queue, rarely enough to pass every test. With while, the same situations happen (37 to 70 re-checks per run) and are harmless.


Rule 2: one condition variable per condition. With one variable shared by "slot full" and "slot empty", a consumer's signal can wake the other consumer instead of the producer; then all three sleep, and the program hangs at 0% CPU. It hung in 3 of 3 runs, after a handful of items. Use two condition variables (or broadcast, which is correct but wakes everyone).


The {{Interleaving lab|#t-lock}} counts every possible schedule of a two-item version: with if, 64,228 of 42,827,788 schedules make a consumer read an empty slot; with while, none of 91,732,872 do.


A semaphore (Dijkstra, 1960s) is a counter with two operations: wait (also P, down) decrements it and sleeps while it would go below zero; post (V, up) increments it and wakes a sleeper. Initialised to 1 it is a lock; to N it admits at most N holders at once ("at most 2 prefetched batches per worker" is this idea: the DataLoader's prefetch_factor); to 0 it is a "wait until done" signal. POSIX sem_t is a futex word; multiprocessing's locks, semaphores and queues are sem_t in /dev/shm (section 4's trace). Semaphores are easy to misuse because, unlike a mutex, any thread can post them: nothing records an owner.


A reader-writer lock lets many readers in at once or one writer alone; good for data read far more than written (a model registry, a config). The catch is starvation: glibc's pthread_rwlock_t prefers readers by default, so a steady stream of readers can keep a writer waiting indefinitely (PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP changes it; {{pthread_rwlockattr_setkind_np(3)|https://man7.org/linux/man-pages/man3/pthread_rwlockattr_setkind_np.3.html}}). For short critical sections an rwlock is often slower than a mutex, since even readers write the shared reader count.


A barrier makes N threads wait until all N arrive. OpenMP puts one at the end of every parallel region, which is where PyTorch's math threads sit between operators: libgomp spins at the barrier for a while (do_spin in libgomp/config/linux/wait.h; tuned by {{GOMP_SPINCOUNT|https://gcc.gnu.org/onlinedocs/libgomp/GOMP_005fSPINCOUNT.html}} and OMP_WAIT_POLICY) and then sleeps on a futex. The gdb snapshots in section 10 find the pool threads asleep in futex_wait inside gomp_barrier_wait_end.


In ML work NCCL's proxy thread sleeps on a C++ condition variable when it has nothing to progress, with the predicate the comment calls out: "Predicate avoids lost wakeups and guarantees we observe stop after ncclProxyProgressDestroy" ({{src/proxy.cc L849-851, NCCL v2.32.3-1|https://github.com/NVIDIA/nccl/blob/v2.32.3-1/src/proxy.cc#L849-L851}}). pool->cond.wait(lock, predicate) is exactly rule 1, the while loop written as a lambda.







6. Deadlock, and the other concurrency bugs


ch. 32 Common concurrency problems


Lu et al. studied 105 concurrency bugs in MySQL, Apache, Mozilla and OpenOffice: 74 were not deadlocks and 31 were; 97% of the non-deadlock bugs were of two kinds (as summarised in OSTEP ch. 32, from {{Learning from Mistakes, ASPLOS 2008|https://dl.acm.org/doi/10.1145/1346281.1346323}}):




Atomicity violationcode assumed two steps happen together, and another thread ran between them: if (p) use(p); while another thread sets p = NULL. Fix: one lock around both steps.


Order violationcode assumed A happens before B, and nothing enforced it: a thread uses an object before its creator finished initialising it. Fix: a condition variable or semaphore that B waits on.




A deadlock is a set of threads each waiting for something another member of the set holds, so none can move. It needs four conditions at once (Coffman, 1971): mutual exclusion (resources are held exclusively), hold and wait (a thread holds one while waiting for another), no preemption (nobody can take a held lock away), and a circular wait. Remove any one and deadlock is impossible. In practice:

The signature of a deadlock: every thread in state S (sleeping), every wait channel futex_wait_queue_me, 0% CPU, and py-spy pointing at the two with lines. A busy-looping bug looks the opposite (state R, 100% CPU). With --ordered the same program finishes.


Fixes and tools One lock order per program, written down; never call unknown code (callbacks, logging handlers, __del__) while holding a lock; lock.acquire(timeout=...) in Python turns a silent hang into an error you can log; faulthandler.dump_traceback_later(timeout) prints every thread's stack if the job stops progressing; glibc's PTHREAD_MUTEX_ERRORCHECK returns EDEADLK when a thread re-locks a mutex it holds; ThreadSanitizer (-fsanitize=thread) reports lock-order inversions as well as data races.


The training-job deadlock everyone meets is not two locks but fork while another thread holds one: the child gets a copy of the locked lock and no thread to release it. The root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} reproduces it ("A worker hangs forever: fork while another thread holds a lock") and the sibling {{Processes|n:3f05c17b0d0d811e99f7cb8c15d12697}} page covers start methods; it is why Python 3.14 made forkserver the default on Linux. Database transactions face the same four conditions with a different cure (detect the cycle and abort a victim): {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}}.


Predict: thread A holds lock L and calls logging.info(); a logging handler, on another thread B, holds the handler's lock and calls a function that takes L. What can happen?




"Thread-safe" only means each call is safe on its own. A holds L and wants the handler's lock; B holds the handler's lock and wants L: a circular wait. The rule "never call out while holding a lock" exists for this case.







7. Lock-free, briefly


A lock-free data structure guarantees that some thread always makes progress, even if others are paused at any instruction, because nobody ever holds a lock. The building block is a CAS loop: read the current value, compute the new one, and CAS it in; if another thread changed it meanwhile, the CAS fails and you retry. A stack push:


do { n->next = head; } while (!CAS(&head, n->next, n));


The traps: the ABA problem (the head was A, became B, became A again; the CAS succeeds although the list changed underneath; fixed with version counters or safe memory reclamation), and freeing memory another thread may still be reading (fixed by hazard pointers, epochs, or RCU, read-copy-update, which the Linux kernel uses so that readers take no lock at all: {{What is RCU|https://docs.kernel.org/RCU/whatisRCU.html}}). The common, safe case in practice is a single-producer single-consumer ring buffer: one thread only advances the tail, the other only the head, and each reads the other's index with acquire order. io_uring's two rings (section 9) are exactly that, shared between a program and the kernel. Use lock-free structures from a library (the C++ page's atomics, Rust's crossbeam, std::atomic counters); a lock is usually fast enough (section 3: 10 ns uncontended) and far easier to get right.
