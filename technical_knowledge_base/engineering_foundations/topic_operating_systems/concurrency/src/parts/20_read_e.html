7. The worked case: the GIL and free-threaded Python

from source measured here

CPython's global interpreter lock lets one thread at a time run Python bytecode, and it is built from exactly the parts of sections 4 and 5: "The GIL is just a boolean variable (locked) whose access is protected by a mutex (gil_mutex), and whose changes are signalled by a condition variable (gil_cond)" ({{Python/ceval_gil.h L13-16, v3.11.2|https://github.com/python/cpython/blob/v3.11.2/Python/ceval_gil.h#L13-L16}}). A thread that wants the GIL waits on the condition variable for at most the switch interval (5 ms by default, DEFAULT_INTERVAL 5000 µs, {{L91|https://github.com/python/cpython/blob/v3.11.2/Python/ceval_gil.h#L91}}); if the wait times out it sets gil_drop_request, which the running thread checks between bytecodes; the running thread then releases the GIL and waits until someone else has taken it, so it cannot grab it straight back. A thread blocked in a system call (sleep, recv, read) or in C code that releases the GIL (NumPy, PyTorch operators) lets others run meanwhile; how to write Python around it is the {{Python page|n:3cd5c17b0d0d81b28acdea39e7a4d998}}'s.

What it does to latency. A thread waking from I/O must get the GIL back; if another thread is busy in Python it waits up to a whole switch interval. An "I/O" thread sleeping 2 ms, 300 times, next to 0, 1 or 2 threads doing pure-Python arithmetic, on 2 CPUs (gil_latency.py; median of 3 runs). Predict how late it wakes next to one busy thread:

Next to busy Python threads, a 2 ms sleep comes back a whole switch interval late

Next to one busy thread the I/O thread wakes 8.0 ms late (the 5 ms interval plus the wake-ups on both sides); next to two, 17.5 ms, with a 99th percentile of 86.9 ms, because it competes with another waiter for each hand-over. sys.setswitchinterval(0.0005) brings it to 1.4 ms, at the price of more switching. This is the convoy effect David Beazley measured in 2010 for the GIL that 3.2 introduced ({{Understanding the Python GIL|https://www.dabeaz.com/python/UnderstandingGIL.pdf}}): a heartbeat to the cluster scheduler, a metrics sender or an asyncio loop next to Python preprocessing is delayed by milliseconds.

The free-threaded build: the same job, before and after

Python 3.14's free-threaded build (python3.14t, officially supported since 3.14, {{PEP 779|https://peps.python.org/pep-0779/}}; design in {{PEP 703|https://peps.python.org/pep-0703/}}) removes the GIL. Removing one lock means every object needs another way to stay consistent, and the replacement is this page's toolbox applied to the interpreter:

One lock for the interpreter, or a small lock and a thread-owned reference count per object

  • Built-in containers lock themselves. "Built-in types like dict, list, and set use internal locks to protect against concurrent modifications in ways that behave similarly to the GIL" ({{free-threading how-to, 3.14|https://docs.python.org/3.14/howto/free-threading-python.html}}): a dictionary never corrupts, but d[k] += 1 from two threads is still section 2's lost update, now happening for real.
  • Reference counts stop being a shared hot word. "Biased reference counting, with a fast-path for objects owned by the current thread and a slow path for other objects" (same page): the owner changes its count with a plain add, other threads with an atomic one (section 2's 8.3 ns). Some objects (code constants, interned strings) are immortal, so their count is never written at all, and objects such as module functions use deferred reference counting.
  • The cost: "On the pyperformance benchmark suite, the average overhead ranges from about 1% on macOS aarch64 to 8% on x86-64 Linux systems" for single-threaded code (same page), and every C extension must declare support or importing it turns the GIL back on.

Measured on the Python page (Python 3.14.8, a 10-CPU laptop under load, best of three): counting primes four times took 0.99 s on four threads with the GIL (0.96 s serially) and 0.37 s on four threads free-threaded (0.94 s serially); four processes took 0.36 s and 0.31 s. Scaling, overhead and which extensions are ready are measured there (Part 2).
