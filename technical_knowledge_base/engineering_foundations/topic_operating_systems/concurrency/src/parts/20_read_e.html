8. The GIL, seen as an operating-system lock

from source measured here

CPython's global interpreter lock lets one thread at a time run Python bytecode. The {{Python page|n:3cd5c17b0d0d81b28acdea39e7a4d998}} covers what it means for your code and how the free-threaded build (3.13t, 3.14t) removes it; this section is about how it is built and what it does to latency. In CPython 3.11 it is the textbook construction of section 5: "The GIL is just a boolean variable (locked) whose access is protected by a mutex (gil_mutex), and whose changes are signalled by a condition variable (gil_cond)" ({{Python/ceval_gil.h L13-16, v3.11.2|https://github.com/python/cpython/blob/v3.11.2/Python/ceval_gil.h#L13-L16}}).

A thread that wants the GIL waits on the condition variable for at most the switch interval (5 ms by default, DEFAULT_INTERVAL 5000 µs, {{L91|https://github.com/python/cpython/blob/v3.11.2/Python/ceval_gil.h#L91}}); if the wait times out, it sets gil_drop_request, which the running thread checks between bytecodes, and the running thread then releases the GIL and waits until someone else has taken it (so it cannot grab it straight back). A thread that blocks in a system call (sleep, recv, read) or in C code that releases the GIL (NumPy, PyTorch operators) lets others run meanwhile.

The consequence for latency: a thread that wakes up from I/O must get the GIL back, and if another thread is busy in Python it waits up to a whole switch interval. An "I/O" thread sleeping 2 ms, 300 times, next to 0, 1 or 2 threads doing pure-Python arithmetic, on 2 CPUs (gil_latency.py; median of 3 runs):

Next to one busy thread the I/O thread wakes 8.0 ms late (the 5 ms interval plus the wake-ups on both sides); next to two, 17.5 ms, with a 99th percentile of 86.9 ms, because the I/O thread competes with another waiter for each hand-over. sys.setswitchinterval(0.0005) brings it to 1.4 ms, at the price of more switching. This is the convoy effect David Beazley measured in 2010 for the GIL that 3.2 introduced ({{Understanding the Python GIL|https://www.dabeaz.com/python/UnderstandingGIL.pdf}}).

In ML work A thread in the training process that must react quickly (a heartbeat to the cluster scheduler, a metrics sender, an asyncio loop serving requests next to Python preprocessing) is delayed by milliseconds whenever other Python threads compute. Move the CPU work to processes or into GIL-releasing native code, or use a free-threaded build; the Python page measures free-threaded scaling and the lost updates it brings back.

9. Event-driven I/O: one thread, thousands of waits

ch. 33 Event-based concurrency from source measured here

The problem. A server with thousands of open connections (an inference server streaming tokens, a data service) spends almost all its time waiting. One thread per connection works but each thread is a stack, a kernel task and a context switch per event. 2,000 connections, each a Unix socket pair, served by one thread each or by one asyncio loop (conns.py; median of 3):

Threads reserve 8 MiB of address space each but touch little of it; the real costs are start-up and a context switch per message. The alternative is to ask the kernel one question, "which of these file descriptors are ready?", and handle only those. A file descriptor is the small integer naming an open file, pipe or socket (the sibling {{Processes|n:3f05c17b0d0d811e99f7cb8c15d12697}} page owns them); it is ready when a read or write on it would not block. Put it in non-blocking mode (O_NONBLOCK) and a read that would block returns EAGAIN instead.

select and poll: the whole list, every time

select (BSD, 1983) passes three bitmaps of descriptor numbers; poll (System V) passes an array of {fd, events}. On every call the kernel copies the list in, checks every descriptor's state, registers a wait on each, sleeps, and on wake-up checks them all again ({{fs/select.c L512-534 and L909, v5.10|https://github.com/torvalds/linux/blob/v5.10/fs/select.c#L505-L536}}); the program then scans the whole list again for the ready ones. Cost grows with the number watched, not the number ready. select also has a hard limit: FD_SETSIZE is 1024, so it cannot watch descriptor 1024 or higher at all ({{select(2)|https://man7.org/linux/man-pages/man2/select.2.html}}).

epoll: the list lives in the kernel

epoll (Linux 2.6, 2002) splits registration from waiting: epoll_ctl(ADD) registers a descriptor once, and the kernel keeps the interest list in a red-black tree and a separate ready list ({{fs/eventpoll.c L195-204|https://github.com/torvalds/linux/blob/v5.10/fs/eventpoll.c#L195-L204}}). When data arrives on a socket, the socket's wait-queue callback ep_poll_callback appends that one item to the ready list ({{L1244-1248|https://github.com/torvalds/linux/blob/v5.10/fs/eventpoll.c#L1240-L1248}}); epoll_wait just takes items off the ready list. Its cost depends on the number ready, not the number watched. With N pipes watched and exactly one readable (evloop.c, one call returning one ready descriptor):

Level-triggered and edge-triggered

By default epoll is level-triggered: a descriptor is reported on every epoll_wait while data remains, because after reporting it the kernel puts it back on the ready list ({{L1758-1771|https://github.com/torvalds/linux/blob/v5.10/fs/eventpoll.c#L1756-L1772}}). With EPOLLET it is edge-triggered: reported once per change (new data arriving), and not put back. Write 10 bytes to a pipe, read only 4, and ask again measured here:



Edge-triggered is cheaper (no re-reporting) but has one rule: after an edge, read (or accept, or write) until EAGAIN, or the remaining 6 bytes sit there unreported until more data happens to arrive, which on a quiet connection is never. Tokio's I/O layer, mio, registers every descriptor edge-triggered (let mut kind = EPOLLET;, {{mio src/sys/unix/selector/epoll.rs L115, v1.0.4|https://github.com/tokio-rs/mio/blob/v1.0.4/src/sys/unix/selector/epoll.rs#L112-L117}}) and its readiness tracking enforces the read-until-EAGAIN rule; Python's asyncio and libuv use level-triggered mode. macOS and the BSDs have the same idea under another name, kqueue ({{kqueue(2)|https://man.freebsd.org/cgi/man.cgi?query=kqueue&sektion=2}}), with filters for sockets, files, processes, signals and timers in one call; Python's selectors module prefers it where it exists ({{Lib/selectors.py L610-618|https://github.com/python/cpython/blob/v3.11.2/Lib/selectors.py#L606-L618}}).

All three follow the same readiness model: the kernel says "you can now read without blocking", and the program then makes the read itself. One cost remains: a system call per read and write, plus one per wait.


io_uring: the completion model


io_uring (Linux 5.1, 2019) changes the question to "do these operations and tell me when they are done". The program and the kernel share two ring buffers in memory: the program writes submission queue entries (SQEs: read this fd at this offset into this buffer) into one, and the kernel writes completion queue entries (CQEs: result, user tag) into the other ({{io_uring(7)|https://man7.org/linux/man-pages/man7/io_uring.7.html}}). One io_uring_enter call submits a whole batch and can wait for completions; with IORING_SETUP_SQPOLL a kernel thread polls the submission ring and the program makes no system call at all. The rings are single-producer single-consumer queues (section 7). On this lab's kernel 5.10 measured here:




Three lessons from those lines. First, io_uring_setup failed in a default Docker container: Linux 5.10 charges the rings to the user's locked-memory limit (RLIMIT_MEMLOCK, 64 KiB in Docker) unless the process has CAP_IPC_LOCK ({{fs/io_uring.c L7869-7876 and L9274, v5.10|https://github.com/torvalds/linux/blob/v5.10/fs/io_uring.c#L7862-L7880}}), and the counter is per user, shared by every container running as root; the run passed --ulimit memlock=-1. Linux 5.12 moved the rings to memory-cgroup accounting from source (the ring_pages charge is gone from fs/io_uring.c at v5.12). Second, SQPOLL needs CAP_SYS_ADMIN before 5.11 ({{L7786|https://github.com/torvalds/linux/blob/v5.10/fs/io_uring.c#L7782-L7790}}). Third, reading 16,384 cached 4 KiB blocks, io_uring at depth 32 made 512 system calls instead of 16384, and the time per block fell from 1171 to 908 ns (22% less; medians of 3 noisy runs, which overlap): with the data already in memory, the 4 KiB copy and the per-request bookkeeping remain, and only the system-call entries are saved. io_uring pays off when operations really wait (disk, network) and many are in flight, when operations are tiny, or with SQPOLL and registered buffers on newer kernels not run here.


io_uring and security
Google reported that 60% of the Linux kernel exploits submitted to its kCTF bug bounty in the year to June 2023 used io_uring, and disabled it in ChromeOS and on its production servers ({{Google security blog, 2023-06-14|https://security.googleblog.com/2023/06/learnings-from-kctf-vrps-42-linux.html}}). Docker 25.0 blocks the io_uring system calls in its default seccomp profile ({{moby #46762|https://github.com/moby/moby/pull/46762}}); this lab's Docker 20.10 still allows them. Expect io_uring to be unavailable in many containers.


In ML work Model servers are event loops: vLLM's OpenAI-compatible server is a uvicorn server started with uvloop.run(run_server(args)) ({{vllm/entrypoints/launchers/api_server/entry.py L222, v0.31.0|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/entrypoints/launchers/api_server/entry.py#L222}}) and SGLang passes loop="uvloop" to uvicorn ({{http_server.py L2713, v0.5.21|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/entrypoints/http_server.py#L2713}}): uvloop is libuv underneath, so one thread streams tokens to many clients while the GPU work runs in an engine loop. A blocking call inside an async handler (a synchronous tokenizer call, requests.get, a big JSON encode) stalls every connection on that loop: the Rust page's "blocking the runtime" experiment measures it. Data clients that stream shards from object storage use the same machinery (aiohttp, or Rust/C++ readers on tokio or io_uring).
