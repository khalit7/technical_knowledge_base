3. Locks: spin, yield, or sleep

ch. 28 Locks, ch. 29 Lock-based concurrent data structures

A lock (or mutex) is a word in memory plus two operations: lock() returns only when the caller owns it, unlock() gives it up. OSTEP judges a lock on correctness (mutual exclusion), fairness (can a waiter starve?) and performance (uncontended, contended on many CPUs, contended on one CPU). The design question is what a thread does when the lock is taken:

Spinkeep retrying the atomic exchange. Best when the holder runs on another core and will release within nanoseconds; terrible when the holder is not running, since the spinner burns its whole time slice.
Yieldretry, calling sched_yield() after each failure (OSTEP 28.13): a system call per failed attempt, and no promise about who runs next.
Sleepask the kernel to put the thread on a wait queue and wake it at release: two system calls and a wake-up when contended, nothing else.
Spin, then sleep(two-phase or adaptive) spin briefly in case the holder is about to release, then sleep. glibc's PTHREAD_MUTEX_ADAPTIVE_NP spins at most 100 rounds by default, with exponential backoff ({{nptl/pthread_mutex_lock.c L139-158|https://github.com/bminor/glibc/blob/glibc-2.36/nptl/pthread_mutex_lock.c#L139-L158}}; tunable glibc.pthread.mutex_spin_count).

A good lock costs one atomic instruction until it is contended; then the situation picks the winner

Seven ways to protect one shared counter in four situations measured here (src/runs/c/locks.c; "work" is a loop of about 0.3 ns per iteration; median of 3 runs). Predict which design wins with four threads on one CPU, then pick that situation.

  • Uncontended, a good lock costs about one atomic instruction (9.2 ns for the hand-built futex lock, 10.1 ns for pthread_mutex_t), because it never enters the kernel. A lock that makes a system call on every unlock costs 288.6 ns: about thirty times more, for nothing.
  • Contended on enough CPUs, spinning burns CPU: with a short critical section the spinlock used 910.3 ns of CPU per acquisition against 437.2 ns for the mutex, and was slower in wall time too, because four cores fighting over one cache line slow each other down.
  • With more threads than CPUs, a spinner waits for a thread that is not running. On one CPU with a long critical section the holder is often preempted inside it, and each spinner burns a whole time slice: 1492.5 ns per acquisition against 815.9 ns for the mutex and 791.5 ns for one thread doing the same work alone. In a container with a one-CPU limit and a long critical section, that slice is milliseconds, and under a CPU quota the whole cgroup can be throttled until the next 100 ms period (the root's Debug lab, "CPU limit" cases).
  • Hammering a lock rewards unfairness: with no work the yield lock looks fastest because the releasing thread retakes it while its cache line is hot. A ticket lock (OSTEP 28.11: fetch-and-add a ticket, wait for your number) is fair and slower.

Rule: never spin in user space unless every thread has its own CPU (pinned threads in a low-latency system). The Linux kernel spins because kernel code can disable preemption while holding a spinlock; user space sleeps.

4. The futex: how every Linux lock sleeps

ch. 28.14 to 28.16 (Linux futex, two-phase locks) from source measured here

Sleeping needs the kernel, but entering it costs about 300 ns, thirty times an uncontended lock. The futex ("fast user-space mutex", Linux 2.6, 2003) splits the job: the lock word lives in ordinary user memory and is changed with atomic instructions; the kernel is asked only to sleep on that word or to wake sleepers on it ({{futex(2)|https://man7.org/linux/man-pages/man2/futex.2.html}}; Drepper, {{Futexes Are Tricky|https://www.akkadia.org/drepper/futex.pdf}}, 2011). Two operations do almost all the work:

futex_wait(addr, val)"if *addr still equals val, put me to sleep on addr; otherwise return at once with EAGAIN". The comparison and the going to sleep happen together inside the kernel, under a lock no waker can slip past.
futex_wake(addr, n)"wake up to n threads sleeping on addr". It does not change *addr; the user-space code changed it already.

glibc's mutex protocol uses three values for the lock word: 0 free, 1 locked with nobody waiting, 2 locked and someone may be waiting. Simplified from {{sysdeps/nptl/lowlevellock.h L94-106 and L145-160|https://github.com/bminor/glibc/blob/glibc-2.36/sysdeps/nptl/lowlevellock.h#L94-L160}} and {{nptl/lowlevellock.c L38-50|https://github.com/bminor/glibc/blob/glibc-2.36/nptl/lowlevellock.c#L38-L50}}:

void lock(int *w) {
    if (CAS(w, 0, 1)) return;                 // fast path: free, now mine, no system call
    if (*w == 2) goto wait;
    while (xchg(w, 2) != 0)                 // mark "waiters"; if it was 0 I own it now (as 2)
  wait: futex_wait(w, 2);                    // sleep, but only if it is still 2
}
void unlock(int *w) {
    if (xchg(w, 0) > 1)                      // was 2: someone may be asleep
        futex_wake(w, 1);                      // wake one; it retries the xchg
}

Uncontended, lock is one CAS and unlock one exchange: no system call. A thread that takes the lock after a wait sets it to 2, not 1, because it cannot know whether others are still asleep: an occasional unneeded wake-up is the price of never missing one. The hand-built version in locks.c counts its own system calls: with four threads and short critical sections it made 208840 futex waits in 2 million acquisitions (about one acquisition in ten had to sleep).

Why the kernel must compare: the lost wake-up

Why not check the word in user space and then call a plain "sleep"? Because between the check and the sleep the holder can unlock and send its wake-up to a thread that is not asleep yet; the wake-up is lost and the waiter sleeps forever. The kernel source states the rule ({{kernel/futex.c L2633-2648, v5.10|https://github.com/torvalds/linux/blob/v5.10/kernel/futex.c#L2633-L2648}}): "The basic logical guarantee of a futex is that it blocks ONLY if cond(var) is known to be true at the time of blocking". So futex_wait_setup locks the wait queue first, then reads *uaddr, and returns EAGAIN if it changed ({{L2650-2678|https://github.com/torvalds/linux/blob/v5.10/kernel/futex.c#L2650-L2678}}). One contended lock, four ways: before and after the futex

Threads A and B each need the lock twice (a 2 µs critical section, 1 µs of other work between), while thread C has 8 µs of unrelated work and no lock, all on 2 CPUs. Costs are this VM's measured ones: a futex system call 0.3 µs (the "wake on every unlock" lock's 288.6 ns per pair), and a wake-up of 1.7 µs (same CPU) or 23.5 µs (across CPUs in this VM), half a ping-pong round trip. The futex frees the CPU for C; each hand-off now pays a wake-up

Switch to the cross-CPU wake-up: the futex's hand-offs become far slower than spinning, which is why glibc offers an adaptive mutex and why the kernel and NCCL spin when they expect the wait to be short.

What a wake-up costs. Two threads passing a turn back and forth 200,000 times measured here (pingpong.c; round trip = two hand-offs; median of 5):

On one CPU a hand-off is a context switch: 1.7 µs, in line with the root's 1.33 µs pipe ping-pong. Across CPUs the idle CPU must be woken by an inter-processor interrupt, which a virtual machine turns into a trip through the hypervisor ({{Virtualization and the GPU driver stack|n:3f05c17b0d0d8158b029e9b2ba2e161b}}, section 5); bare metal not run here. Spinning across two CPUs never sleeps (0.09 µs per round trip), but on one CPU each spin waits for a whole time slice: 19.8 ms per round trip, about 220,000 times slower.

In ML work Python's threading.Lock and queue.Queue, PyTorch's thread pools, libgomp's barriers and NCCL's idle proxy thread all sleep on futexes, so in a hung process cat /proc/<pid>/task/*/wchan shows futex_wait_queue_me (5.10; futex_wait_queue on 6.x) for nearly every thread. Thousands of futex(..., FUTEX_WAIT_PRIVATE, 2, NULL) = -1 EAGAIN lines under strace are not a bug: the word changed before the kernel compared, and the caller retries (about a fifth of the job's futex calls in section 10 return an error; strace -c does not name it, and for these waits the usual ones are EAGAIN and, for timed waits, ETIMEDOUT).
Where the sleepers are kept, shared futexes, and the rest of the futex family (depth)

The kernel does not allocate anything per futex while nobody waits. Sleepers go into one global hash table of wait queues, indexed by a key for the address: for a private futex (threads of one process; glibc passes FUTEX_PRIVATE_FLAG) the key is the address space and the virtual address; for a shared futex (a lock in memory mapped by several processes) it is the underlying page and offset, so different virtual addresses in different processes meet in the same queue ({{get_futex_key, kernel/futex.c L487-653|https://github.com/torvalds/linux/blob/v5.10/kernel/futex.c#L487-L653}}). The table has roundup_pow_of_two(256 × CPUs) buckets ({{L4050|https://github.com/torvalds/linux/blob/v5.10/kernel/futex.c#L4050}}), 2,048 on this 5-CPU VM. The full comment: "If we locked the hash-bucket after testing *uaddr, that would open a race condition where we could block indefinitely with cond(var) false, which would violate the guarantee." Python's multiprocessing.Lock is a POSIX semaphore in a /dev/shm/sem.* file mapped by both processes, so its futex is shared: no _PRIVATE in the trace measured here:
