4. The futex: how every Linux lock sleeps

ch. 28.14 to 28.16 (Linux futex, two-phase locks) from source measured here

The problem. Sleeping needs the kernel (only the kernel can take a thread off the CPU and put it back), but entering the kernel costs about 300 ns, thirty times an uncontended lock. Before futexes, user-space locks paid for a system call either on every operation or on none (and then spun). The futex ("fast user-space mutex", Linux 2.6, 2003) splits the job: the lock word lives in ordinary user memory and is changed with atomic instructions; the kernel is asked only to sleep on that word or to wake sleepers on it ({{futex(2)|https://man7.org/linux/man-pages/man2/futex.2.html}}; Drepper, {{Futexes Are Tricky|https://www.akkadia.org/drepper/futex.pdf}}, 2011). Two operations do almost all the work:

futex_wait(addr, val)"if *addr still equals val, put me to sleep on addr; otherwise return at once with EAGAIN". The comparison and the going to sleep happen together inside the kernel, under a lock no waker can slip past.
futex_wake(addr, n)"wake up to n threads sleeping on addr". It does not change *addr; the user-space code changed it already.

glibc's mutex protocol uses three values for the lock word: 0 free, 1 locked with nobody waiting, 2 locked and someone may be waiting. Simplified from {{sysdeps/nptl/lowlevellock.h L94-106 and L145-160|https://github.com/bminor/glibc/blob/glibc-2.36/sysdeps/nptl/lowlevellock.h#L94-L160}} and {{nptl/lowlevellock.c L38-50|https://github.com/bminor/glibc/blob/glibc-2.36/nptl/lowlevellock.c#L38-L50}}:

void lock(int *w) {
    if (CAS(w, 0, 1)) return;                 // fast path: free, now mine, no system call
    if (*w == 2) goto wait;
    while (xchg(w, 2) != 0)                 // mark "waiters"; if it was 0 I own it now (as 2)
  wait: futex_wait(w, 2);                    // sleep, but only if it is still 2
}
void unlock(int *w) {
    if (xchg(w, 0) > 1)                      // was 2: someone may be asleep
        futex_wake(w, 1);                      // wake one; it retries the xchg
}

Uncontended, lock is one CAS and unlock one exchange: no system call. Only a thread that finds the lock taken calls futex_wait, and only an unlock that sees 2 calls futex_wake. A thread that takes the lock after a wait sets it to 2, not 1, because it cannot know whether others are still asleep: an occasional unneeded wake-up is the price of never missing one. The hand-built version in locks.c counts its own system calls: with four threads and short critical sections it made 208840 futex waits in 2 million acquisitions (about one acquisition in ten had to sleep).

Why the kernel must compare: the lost wake-up

Why not check the lock word in user space and then call a plain "sleep"? Because between the check and the sleep, the holder can unlock and send its wake-up to a thread that is not asleep yet; the wake-up is lost, and the waiter then sleeps forever. The kernel source states the rule ({{kernel/futex.c L2633-2648, v5.10|https://github.com/torvalds/linux/blob/v5.10/kernel/futex.c#L2633-L2648}}):

 * The basic logical guarantee of a futex is that it blocks ONLY
 * if cond(var) is known to be true at the time of blocking, for
 * any cond.  If we locked the hash-bucket after testing *uaddr, that
 * would open a race condition where we could block indefinitely with
 * cond(var) false, which would violate the guarantee.

So futex_wait_setup locks the wait queue first, then reads *uaddr, and returns EAGAIN if it changed ({{L2650-2678|https://github.com/torvalds/linux/blob/v5.10/kernel/futex.c#L2650-L2678}}). The {{Interleaving lab|#t-lock}} lets you produce the lost wake-up yourself in the "check, then sleep" lock (54 of its 376 possible schedules leave a thread asleep forever) and shows that the futex version has none.

Where the sleepers are kept

The kernel does not allocate anything per futex while nobody waits. Sleepers go into one global hash table of wait queues, indexed by a key for the address: for a private futex (threads of one process; glibc passes FUTEX_PRIVATE_FLAG) the key is the address space and the virtual address; for a shared futex (a lock in memory mapped by several processes) it is the underlying page and offset, so different virtual addresses in different processes meet in the same queue ({{get_futex_key, kernel/futex.c L487-653|https://github.com/torvalds/linux/blob/v5.10/kernel/futex.c#L487-L653}}). The table has roundup_pow_of_two(256 × CPUs) buckets ({{L4050|https://github.com/torvalds/linux/blob/v5.10/kernel/futex.c#L4050}}), 2,048 on this 5-CPU VM. What a wake-up costs


Two threads passing a turn back and forth 200,000 times measured here (pingpong.c; round trip = two hand-offs; median of 5):




On one CPU a hand-off is a context switch: 1.7 µs, in line with the root's 1.33 µs pipe ping-pong. Across CPUs it is slower here because the sleeping CPU has gone idle and must be woken by an inter-processor interrupt, which a virtual machine turns into a trip through the hypervisor (here a GICv2 emulated in QEMU, with the idle vCPU a host thread that must itself be woken: {{Virtualization and the GPU driver stack|n:3f05c17b0d0d8158b029e9b2ba2e161b}}, section 5, measures each step); how much lower it is on bare metal was not measured here not run here. Spinning across two CPUs never sleeps (0.09 µs per round trip, median of 5; one run took 44.8 µs when another workload took one of the CPUs), but on one CPU each spin waits for a whole time slice: 19.8 ms per round trip, about 220,000 times slower.


The rest of the futex family


    

  • FUTEX_WAIT_BITSET with FUTEX_CLOCK_REALTIME: a wait with an absolute deadline; glibc uses it for timed waits and POSIX semaphores (the trace above).
    • 

  • FUTEX_CMP_REQUEUE: wake one waiter and move the rest from a condition variable's futex to the mutex's, so a broadcast does not wake a herd that would immediately fight for the mutex (the thundering herd). glibc 2.25 (2017) replaced its condition variables with an algorithm based on groups of waiters that never requeues (no requeue call appears in {{nptl/pthread_cond_wait.c, glibc 2.36|https://github.com/bminor/glibc/blob/glibc-2.36/nptl/pthread_cond_wait.c}}); the operation remains in use for priority-inheritance locks.
    • 

  • FUTEX_LOCK_PI: priority inheritance; the kernel knows the owner (its thread id is in the word) and boosts it while a higher-priority thread waits. It fixes priority inversion, the bug that kept resetting NASA's Mars Pathfinder in 1997 ({{account by Glenn Reeves|https://www.cs.cornell.edu/courses/cs614/1999sp/papers/pathfinder.html}}).
    • 

  • Robust futexes: the kernel walks a per-thread list at exit and marks locks held by a dead thread (EOWNERDEAD), for locks in memory shared between processes.
    • 

  • futex_waitv (Linux 5.16) waits on several futexes at once, added for Wine and game engines ({{futex2 docs|https://docs.kernel.org/userspace-api/futex2.html}}); not on this 5.10 kernel.
    • 



In ML work Every lock and queue in the stack sleeps on a futex: Python's threading.Lock and queue.Queue, PyTorch's thread pools, libgomp's barriers, NCCL's proxy thread when idle. So when a training process hangs, cat /proc/<pid>/task/*/wchan shows futex_wait_queue_me (5.10; futex_wait_queue on 6.x) for nearly every thread, and the question becomes which address each one waits on and who should have woken it: py-spy dump for Python frames, gdb -p <pid> -ex "thread apply all bt" for native ones (section 6).


Predict: under strace, a busy training process shows futex(..., FUTEX_WAIT_PRIVATE, 2, NULL) = -1 EAGAIN thousands of times. A bug?




EAGAIN from futex_wait is the futex working as designed: by the time the kernel compared, the holder had released (or someone changed the word), so sleeping would have been wrong. The caller simply retries. In the job's trace in section 10, about a fifth of all futex calls return an error (strace -c counts errors without naming them; for these waits the usual ones are EAGAIN and, for timed waits, ETIMEDOUT).
