In one screen

When torch.save returns, your checkpoint is in memory, not on the disk. The kernel keeps file data in a cache (the page cache) and writes it to the device later, in its own order, on its own schedule. Everything on this page is about that gap: how data moves between your program, the cache and the device, what each system call promises about it, and how to write a checkpoint that a crash can never destroy.

The root page, Topic: operating-systems section 7, gave the intuition, animated one write's journey, and traced the running job's checkpoint (its Syscall tracer tab); its OS simulators tab crashes a block-level write with and without a journal. This page goes one level down: the kernel's code paths (Linux v5.10, the kernel these runs used, file and line), the exact guarantee of every call, new measurements, and the checkpoint libraries you actually use. Each mechanism follows one pattern: problem, how it works, what it costs here, when it bites in ML, the command that shows it, the fix.

Six things to remember
  1. Returned is not durable. The 256 MiB checkpoint below left MiB of dirty (not yet written) data in memory when torch.save returned (section 5).
  2. When the kernel writes it is not a promise. The textbook says "within 30 seconds"; here the same 16 MiB stayed dirty anywhere from to seconds, depending on what else the machine was doing (section 5).
  3. The safe checkpoint is five calls: write to ckpt.pt.tmp, fsync it, rename it over ckpt.pt, fsync the directory; and never overwrite the last good checkpoint in place. It cost ms against ms for the plain save (section 7, Crash lab).
  4. Libraries differ. PyTorch's distributed checkpoint fsyncs every file but deletes the old .metadata before renaming the new one in, and never fsyncs the directory: save each step to a new directory (section 11).
  5. Sequential beats random, because the kernel reads ahead: 512 small reads of a cold file became device requests (section 4). Shards, not millions of small files.
  6. If fsync fails, the data is gone: the kernel may already have dropped the dirty pages. Rewrite the checkpoint from memory; never retry the fsync and carry on (section 6).

1. Devices: what is actually at the bottom

ch. 36 I/O Devices, ch. 37 Hard Disk Drives, ch. 44 Flash-based SSDs

The problem. Memory (DRAM) loses its contents without power; a storage device keeps them. But devices are thousands of times slower than memory, they work in blocks, not bytes, and most of them have their own volatile cache. Everything the kernel does above them exists to hide these three facts, and every durability bug comes from forgetting one of them.

Three kinds of device

Hard disk (HDD)A spinning platter and a moving arm. A random read waits for the arm to move (seek) and the platter to turn (rotation): several milliseconds, so a few hundred random reads per second; sequential reads are fast because nothing moves. OSTEP ch. 37 works the numbers.
Flash SSDNo moving parts. Flash is read and written in pages (a few KiB) but can be erased only in much larger erase blocks, and a page cannot be rewritten before its block is erased. A flash translation layer (FTL) inside the drive therefore writes every update to a fresh page and remaps it, and garbage-collects old blocks in the background; the extra internal writes are write amplification. OSTEP ch. 44 lists typical times: read about 25 us, program (write) 200 to 300 us, erase 1.5 to 2 ms for SLC flash (OSTEP ch. 44).
NVMeThe interface modern SSDs speak over PCIe. The host and the drive share submission and completion queues in memory: the driver writes a command into a submission queue and rings a doorbell register; the drive fetches it by DMA, does the work, writes a completion entry and raises an interrupt. The specification allows up to 65,535 I/O queue pairs of up to 65,536 entries each (NVM Express base specification), so Linux can give each CPU its own queue and never take a shared lock. not run here

TRIM, or discard. When a file is deleted, the file system knows the blocks are free but the SSD does not, and its garbage collector keeps copying dead data. A discard (TRIM on SATA, Deallocate on NVMe) tells it. ext4 can send discards at every delete (mount option discard) or you run fstrim periodically. This VM mounts its disk nodiscard and runs a small service that calls /sbin/fstrim /var/lib/docker after deletes (seen in the VM's process list with docker run --pid host ... ps) measured.

The device's own cache, and why fsync must flush it

Most drives acknowledge a write as soon as it is in their internal DRAM cache. If power fails before the drive moves it to flash or platter, the write is lost even though the drive said "done". So the kernel has two extra tools (kernel docs: writeback cache control): a cache flush (the REQ_PREFLUSH flag: "flush the volatile cache before this I/O") and FUA, Force Unit Access (the REQ_FUA flag: "this write completes only once it is on stable storage"). A file system's fsync ends with one of them; that, not the write itself, is what makes data survive power loss. You can read what the kernel believes about your disk:



This disk reports a write-back cache and no FUA support, so the kernel emulates FUA with a write followed by a full cache flush. A drive that wrongly reports write through, or firmware that ignores flushes, silently breaks every guarantee on this page; this cannot be tested from software, only with power-cut tests.

Why it bites in ML. A data loader that reads one sample at a time from one thread runs at queue depth 1, the left end of that chart. More DataLoader workers, prefetching, or asynchronous I/O raise the queue depth and the throughput, until the device saturates and latency only grows. Little's law ties the three: requests in flight = throughput x latency.






2. The block layer: from a request to the device's queues


ch. 36 I/O Devices


The problem. Many processes and the file system issue reads and writes of all sizes; the device wants few, large, well-ordered requests spread across its queues. The block layer sits between them.


How it works. A file system describes an I/O as a bio: a direction, a starting sector and a list of memory pages (struct bio, include/linux/blk_types.h). Bios that touch neighbouring sectors are merged into a request. Since Linux 3.13 the layer is blk-mq, multi-queue: each CPU puts requests in its own software queue, which feeds one of the device's hardware queues, so CPUs do not contend on one lock (kernel docs: blk-mq). A thread may also plug its queue while it submits a batch, so the batch is merged before it is sent. An optional I/O scheduler may reorder requests: none, mq-deadline (bounds how long a request waits), kyber (latency targets) or bfq (fair shares between processes). For fast NVMe drives none is the usual choice because reordering costs more than it saves.

When it bites in ML. Rarely directly: you seldom tune the block layer, but you read its counters. "The disk is at 100% util" on iostat while r/s keeps rising with more workers means the device still has room; a large r_await with a small aqu-sz means each request is slow (a remote or throttled device), not that you are queueing.


At queue depth 64, fio measured about 54,700 reads per second at a mean latency near 1.15 ms. What throughput does Little's law predict for 64 requests in flight at 1.15 ms each?




Throughput = requests in flight / latency = 64 / 0.0011526 s = about 55,500 per second, within 2% of what fio measured: the device was busy all the time, and each extra request in flight only waited longer. At queue depth 1 the same law gives 1 / 80 us = 12,500 per second; fio saw 10,741 because fio's own per-request work adds to the device's time.






3. File systems and the VFS: names, inodes and open files


ch. 39 Files and Directories, ch. 40 File System Implementation, ch. 41 Locality and FFS


The problem. A device is a flat array of blocks. Programs want named files in directories, permissions, sizes and times, and they want the same open, read, write to work on ext4, XFS, tmpfs, NFS or /proc. The kernel solves the second problem with the VFS (virtual file system switch): one set of objects and calls that every file system implements (kernel docs: VFS).


Four objects




superblockOne per mounted file system: its type, block size, and the operations to read and write inodes (struct super_block, include/linux/fs.h line 1416, v5.10).


inodeOne per file, whatever its names: type, permissions, owner, size, times, link count, and where its data lives (struct inode, fs.h line 610). It holds an address_space (line 451): that file's pages in the page cache.


dentryOne per name in a path, cached: "the name ckpt.pt in directory X is inode 13" (struct dentry, include/linux/dcache.h line 89). A negative dentry caches "this name does not exist".


fileOne per open(): the current offset, the open flags, and a pointer to the dentry and inode (struct file, fs.h line 916). File descriptors are indexes into a per-process table of these; the sibling page Processes and the system-call API section 7 draws the three tables.




Path lookup. open("/data/out/ckpt.pt") walks the path one component at a time, looking each name up in the dentry cache and asking the file system only on a miss (fs/namei.c). The root's Syscall tracer shows import torch making hundreds of newfstatat calls that fail with ENOENT: Python searching its path. Each failure leaves a negative dentry, so the second import is cheap.


Names are not files. A directory is itself a file whose content is a table of (name, inode number). A hard link is a second entry pointing at the same inode; a symbolic link is a small file containing a path. The inode counts its names (its link count) and is freed when that count is zero and no process has it open. So deleting a checkpoint that a running process still holds open frees no space until that process closes it or exits; lsof +L1 lists such deleted-but-open files.


An ext4 inode, for real


Below, mke2fs built a 64 MiB ext4 file system inside an ordinary file and debugfs (which reads and writes the image directly, so no mount and no privileges were needed) copied in a 3,000,000-byte "checkpoint" and a small file with two names. measured




Read it from the bottom of the stack up. The directory out is a table: ckpt.pt is inode 13, and hello.txt and hardlink.txt are both inode 14 (one file, Links: 2). Inode 13's data is one extent: logical blocks 0 to 732 stored in physical blocks 2066 to 2798, contiguous. That is 733 blocks of 4,096 bytes, the smallest number that holds 3,000,000 bytes (3,000,000 / 4,096 = 732.4), and Blockcount: 5864 counts the same space in 512-byte sectors (733 x 8). Old file systems (ext2, ext3) listed every block number; an extent says "start, length" once, which is why a large file costs ext4 almost no metadata. ext4 also groups inodes and their data into block groups so a file's inode sits near its data, the idea OSTEP ch. 41 credits to FFS. The journal (section 8) is itself an inode inside the file system, 4 MiB here.

Why. Every small file pays for a path lookup, an inode allocation, a directory entry, a journal transaction share and a separate block allocation; every cold read of one is at least one device request that readahead cannot merge with its neighbours (section 4). On a network or parallel file system each open and stat is also a round trip to a metadata server (section 10), so the gap grows from tens to thousands of times.

4. Reading: the page cache and readahead


ch. 40 File System Implementation (caching and buffering)


The problem. A device request has a large fixed cost; a program often reads a file 4 KiB at a time, and often reads the same file again (every epoch). Two answers: keep what was read in memory, the page cache, and when a program reads sequentially, fetch the next pages before it asks, readahead. The sibling page Virtual memory section 6 covers how the page cache competes for memory and is reclaimed; this section is about how data gets into it.


The read path, in the source


source read(fd, buf, 4096) reaches ext4's ext4_file_read_iter, which calls the generic generic_file_buffered_read (mm/filemap.c line 2185, v5.10). For each page of the request it looks the page up in the file's address_space. A hit is a memory copy. A miss calls page_cache_sync_readahead (line 2235), which decides how much to fetch, allocates the pages, builds bios and submits them; the reader then sleeps until its page is unlocked. That sleep is the D state with wait channel wait_on_page_bit_common that the root's Debug lab case "Slow storage: workers sleep in D state on page faults" caught on a throttled disk. A page that carries the PG_readahead mark triggers page_cache_async_readahead (line 2247): the next window is fetched while the program is still reading the current one.


The readahead window, from the source and on the device


source mm/readahead.c (v5.10) sizes the first window with get_init_ra_size (line 311): round the request up to a power of two, then multiply by 4 if it is at most 1/32 of the maximum, by 2 if at most 1/4, else use the maximum. Each later window comes from get_next_ra_size (line 329): 4 times the previous one while it is under 1/16 of the maximum, then 2 times, capped at the maximum. The maximum is read_ahead_kb (128 KiB here, 32 pages); posix_fadvise(POSIX_FADV_SEQUENTIAL) doubles it for that open file (mm/fadvise.c line 92) and POSIX_FADV_RANDOM turns readahead off (line 88).


measured A cold 8 MiB file read 4 KiB at a time; after every read() the script looked at the container's io.stat, so each device request and its size is visible. The animation replays the measured requests; the sizes predicted from the two source rules are drawn as outlines.


















Read the two before/after cases together. With readahead on, the window grew 4, 8, 16, 32 pages and then stayed at the 32-page maximum, and each window was requested one window ahead of the reader (the marker page), so most reads never waited for the device. With readahead off the same reads cost one device request each. Random reads get no readahead at all: the kernel only predicts sequential access, and the measured random case fetched exactly one page per read.


Cold and warm, and the honest caveat


The root's Debug lab case "The first epoch is slower than the rest: cold and warm page cache" measured a 512 MiB shard at 858 MiB/s cold against 3,831 MiB/s warm, and readahead off at 16,384 requests for 64 MiB against 516 with it on. On this VM, "cold" still means "in macOS's cache of the virtual disk file": on a real local NVMe drive the cold number would be lower, and on a network file system much lower. Here the cold small-files read of section 3 was  times slower than reading the same 40 MiB as one file.

5. Writing: dirty pages, writeback and throttling


ch. 39 Files and Directories (fsync), ch. 40 (write buffering)


The problem. If every write() waited for the device, a program writing a checkpoint in 4 KiB pieces would pay a device round trip for each. So writes go to the page cache and return; the device is updated later, in large batches. The cost of that speed is the gap this page is about.


How it works


source write() on ext4 runs generic_perform_write (mm/filemap.c line 3288, v5.10): for each page, ext4_da_write_begin (fs/ext4/inode.c line 2934) finds or creates the page in the cache and reserves space without choosing disk blocks (delayed allocation, section 8), the bytes are copied in, the page is marked dirty (changed in memory, not yet on the device), and balance_dirty_pages_ratelimited (line 3365) checks whether this writer has dirtied too much. Then write() returns. Nothing has touched the device.


Dirty pages are written back by per-device flusher threads (kernel workers named kworker/u*:*-flush-*) for three reasons (vm sysctl docs; mm/page-writeback.c lines 74 to 109):


    

  1. Age: every dirty_writeback_centisecs (500, so 5 s) the flusher wakes and writes data that has been dirty longer than dirty_expire_centisecs (3000, so 30 s).
    2. 

  2. Background threshold: when dirty data passes dirty_background_ratio (10%) of dirtyable memory (free memory plus file pages that could be reclaimed, not total RAM: global_dirtyable_memory, line 362), the flusher starts writing everything, regardless of age.
    3. 

  3. Hard threshold: near dirty_ratio (20%) the writing process itself is paused in balance_dirty_pages (line 1555, the pause at line 1795) so it cannot dirty memory faster than the device drains it. This is dirty throttling: write() becomes slow without any error.
    4. 



On this VM the kernel computed a background threshold of  MiB and a hard threshold of  MiB VM-wide (/proc/vmstat) measured. With cgroup v2 each memory cgroup is also its own writeback domain with thresholds scaled to its memory, so a container with a 1.5 GB limit is throttled long before the machine is (cgroup v2 docs, Writeback).


Watching it happen


measured Each run wrote a file into a fresh container (limit 1,500 MB) and sampled its memory.stat (dirty and under-writeback page cache) and io.stat (bytes the device received) every 100 ms.














Six runs wrote 16 MiB (or 256 MiB) and then waited, with nothing calling fsync. The textbook rule is "written back once it is 30 s old". How long did the 16 MiB actually stay dirty?




 In a fresh container the data left at the flusher's next 5-second wake-up, long before it was 30 s old. Our reading of the source: wb_over_bg_thresh (mm/page-writeback.c line 1960) also compares this writeback domain's dirty pages with its share of the background threshold, a share proportional to how much it recently wrote back. A brand-new container has almost no share, so even 16 MiB counts as "over its threshold" and is written in the background. After the container had just written and synced 1 GiB (the "primed" runs), it had a share, and the same 16 MiB waited between 2 and 32 s as that share decayed. We could not trace the flusher here (that needs privileges), so treat the explanation as the likely one, not a proven one. The lesson does not depend on it: when dirty data reaches the device is not a promise you can use. Only fsync is.


What it costs, and when it bites in ML


    

  • A crash in the window loses data that every call said was written. The 256 MiB checkpoint of section 11 left  MiB dirty when torch.save returned. (Killing the process does not lose it: the dirty pages belong to the kernel. Only a kernel crash, a power loss or a VM or node being killed does.)
    • 

  • Dirty throttling stalls training. In the "1.5 GiB, as fast as possible" run the writer was caught sleeping in balance_dirty_pages and the container's dirty data hovered at the domain's limits while the device drained it. A training loop that saves a large checkpoint synchronously stalls the same way; a background writer thread does not stop the stall from happening, but it moves it off the training thread.
    • 

  • Dirty pages count toward your container's memory and cannot be dropped until they are written, so a memory-limited container that writes faster than its device can be pushed toward the OOM killer by its own page cache (Virtual memory section 12).
    •

6. Durability: fsync and its relatives


ch. 39 Files and Directories, ch. 45 Data Integrity and Protection


The problem. Some data must survive a crash: a checkpoint, a database log, the "this checkpoint is complete" marker. The program needs a call that returns only when the data is on stable storage, and it needs to know exactly what that call covers.


The family, and what each one promises




CallCoversSource


fsync(fd)all of the file's dirty data and all its metadata, then a device cache flush. "This includes writing through or flushing a disk cache if present." Not the directory entry that names the file.fsync(2)


fdatasync(fd)the data, plus only the metadata "needed in order to allow a subsequent data retrieval to be correctly handled": the size and block map yes, the modification time nofsync(2)


open(..., O_DSYNC) / O_SYNCevery write() behaves as if followed by fdatasync / fsyncopen(2)


sync_file_range(fd, off, n, flags)starts and/or waits for writeback of a byte range; no metadata, no cache flush. The kernel's own comment: "there are no guarantees here that the data will be available on disk after a crash"fs/sync.c lines 351 to 355 (v5.10)


syncfs(fd), sync()everything dirty on one file system, or on all of them; heavy, and in a shared machine you wait for other people's data toosync(2)




Inside ext4's fsync


source ext4_sync_file (fs/ext4/fsync.c line 129, v5.10) does three things in order. (1) file_write_and_wait_range: write the file's dirty pages and wait for them. (2) ext4_fsync_journal (line 104): wait until the journal transaction that last changed this inode has committed; for fdatasync it waits only for the transaction that last changed what data retrieval needs (i_datasync_tid against i_sync_tid, line 109), and if that already committed there is nothing to wait for. The wait goes through ext4_fc_commit (line 115), which is a full journal commit unless the newer "fast commit" feature was enabled when the file system was created (a feature flag that needs privileges to read on this VM). (3) If needed, blkdev_issue_flush (line 177): the device cache flush of section 1. The animation runs one 4 KiB overwrite of a preallocated file through three calls, with this VM's measured median times.
















What each call costs per 4 KiB record measured


1,000 records each; median and 99th percentile in microseconds. "Append" grows the file (size changes every time); "overwrite" rewrites a preallocated, already-synced file (only data and times change). tmpfs keeps files only in memory, so it has nothing to flush.










On an overwrite, fdatasync cost about a third of fsync here. Why, given that both wrote the same 4 KiB?




An overwrite changes no size and no block map, only the data and the inode's times. fdatasync's required metadata is unchanged, so it writes the page and flushes; fsync must also log the time change in a journal transaction and wait for its commit, which is a second ordered write and flush. On append the size changes, so fdatasync needs the journal too and costs nearly as much as fsync: preallocating a log file (fallocate) and overwriting it is how databases make fdatasync cheap.


When fsync fails


A device error during writeback is reported to the next fsync. Before Linux 4.13 the error could be reported to one caller only and the failed pages were marked clean, so a second fsync returned success with the data lost: the PostgreSQL "fsyncgate" story in the root's section 7. Since 4.13 the kernel records writeback errors in an errseq_t, a counter plus error code that "allow[s] any number of 'subscribers' to tell whether it has changed since a previous point where it was sampled" (lib/errseq.c lines 8 to 10, v5.10), so every file descriptor open at the time sees the error once (LWN, Improved block-layer error handling). The pages may still be gone. The rule: a failed fsync means that file's recent writes are lost; rewrite it from memory, or abort. With delayed allocation, running out of space can also surface only at fsync or close rather than at write, so check both: Python's f.close() raises OSError if the underlying close fails.


When it bites in ML, and the fix
    

  • An fsync per step is about a millisecond per call here and can be tens of milliseconds on cloud block storage not run here: fine once per checkpoint, ruinous once per logged metric line. Buffer logs and fsync on a timer.
    • 

  • Count the calls: strace -f -e trace=fsync,fdatasync,sync_file_range,rename,renameat -p PID, or strace -c for totals.

  • Never retry a failed fsync and continue. Save the checkpoint again to a new file.

7. Atomic replace: making a crash see old or new, never half


ch. 39 Files and Directories (rename), ch. 42 Crash Consistency


The problem. fsync makes data durable, but it does not make an update atomic: a crash in the middle of rewriting ckpt.pt leaves a file that is partly new, partly old or partly missing, and the previous good checkpoint is already destroyed. We need a way to switch from the old version to the new one in a single step.


The tools




rename"If newpath already exists, it will be atomically replaced, so that there is no point at which another process attempting to access newpath will find it missing" (rename(2)). Atomic for readers now; durable only once the directory change is committed.


fsync of the directory"Calling fsync() does not necessarily ensure that the entry in the directory containing the file has also reached disk. For that an explicit fsync() on a file descriptor for the directory is also needed" (fsync(2)). Open the directory O_RDONLY and fsync that descriptor.


renameat2 flagsRENAME_NOREPLACE fails instead of overwriting (two writers cannot clobber each other); RENAME_EXCHANGE swaps two names atomically (rename(2)).

What ALICE found, and what ext4 does to help


Pillai and colleagues recorded the system calls of eleven widely used systems ("databases, key-value stores, version control systems, distributed systems, and virtualization software") and computed every state a crash could leave under the guarantees file systems actually give. They found "a total of 60 vulnerabilities, many of which lead to severe consequences" (All File Systems Are Not Created Equal, OSDI 2014). They also showed the answer depends on the file system and its mount options: code that is safe on one can corrupt on another.


source ext4 carries a heuristic for the most common unsafe pattern, born from the 2009 zero-length-files story in the root's section 7: with the default auto_da_alloc mount option (this VM has it), renaming a file over an existing one makes ext4 allocate and start writing the source file's delayed data first (fs/ext4/namei.c lines 3782 to 3783, ext4_alloc_da_blocks), and closing a file that had been truncated to zero does the same (fs/ext4/file.c lines 140 to 143). With data=ordered, the commit that records the rename then waits for that data. So on ext4, write-then-rename without fsync usually ends with old or new rather than an empty file; but the rename is still not durable until the next commit, the heuristic exists only on ext4, and the ext4 documentation introduces it as help for "broken applications" that replace files without fsync(), providing "roughly the same level of guarantees as ext3" (ext4 docs, auto_da_alloc). 8. Journaling in ext4 and XFS, and copy-on-write file systems


ch. 42 Crash Consistency: FSCK and Journaling, ch. 43 Log-structured File Systems


The problem. Creating, growing or renaming a file changes several blocks (the inode, a bitmap of free blocks, the directory). A crash between them leaves the file system's own structures inconsistent. The root's OS simulators tab ("crash consistency") crashes such an update at every block write, with no journal, data journaling and ordered journaling, and repairs it with fsck or a journal replay. Here: how Linux's file systems really do it, and what it means for your files.


ext4's journal: jbd2


ext4 hands its journaling to a generic layer, jbd2. Every operation that changes metadata opens a handle on the current running transaction; many operations share one transaction. The transaction is committed (its blocks written to the journal, then a commit block) when it is 5 seconds old (JBD2_DEFAULT_MAX_COMMIT_AGE, include/linux/jbd2.h line 48, v5.10; the commit=5 mount option), when the journal fills, or when someone's fsync needs it. Later the blocks are written to their real places (a checkpoint, in journaling's sense) and that journal space is reused. After a crash, mount replays committed transactions and discards incomplete ones: seconds, not the full scan of fsck.

Three data modes


The journal always covers metadata. What happens to file data is the data= mount option (ext4 docs):

Delayed allocation (the delalloc option, on here) interacts with ordered mode in a way that matters for checkpoints. ext4 does not choose disk blocks at write(); it chooses them at writeback, when it knows how big the file is, which gives large contiguous extents (the single extent of section 3). But until then there are no blocks to order, so the journal can commit a new file's name and size while its data is still only in memory. That is the mechanism behind the zero-length files of 2009 and the reason for the auto_da_alloc heuristic of section 7.


Barriers. A commit block must not reach the platter before the blocks it commits. jbd2 writes the commit block with a cache flush and FUA (REQ_PREFLUSH | REQ_FUA, fs/jbd2/commit.c line 157, v5.10; section 1) unless mounted barrier=0 (this VM: barrier, the default). Turning barriers off on a drive with a volatile cache trades crash safety for speed; never do it for a checkpoint volume.


XFS, and file systems that never overwrite


XFS, common on large local arrays, journals metadata only, with a design ("delayed logging") that batches many changes into each log write (kernel docs: XFS delayed logging). Do not count on ext4's auto_da_alloc rename rule there or anywhere else: the fsync rules of section 7 are what every file system promises to honour. not run here (the kernel knows XFS, but mounting needs privileges)


Copy-on-write file systems (btrfs, ZFS) never overwrite a block in place: a change writes new blocks and new copies of every tree node above them, up to a new root, and the commit is the single write that switches to the new root. The file system is always consistent with no journal replay, and snapshots cost almost nothing (keep the old root). OSTEP ch. 43 develops the same idea as the log-structured file system. Durability of your file still needs fsync. not run here

9. Direct I/O and asynchronous I/O


ch. 36 I/O Devices (DMA)


The problem. The page cache is a bargain for data you read twice and for small writes, but a training job also streams data it reads once (a dataset bigger than RAM) and writes data it will not read back (a checkpoint). Copying that through the cache costs a memory copy per byte, evicts useful pages, and creates the dirty-page throttling of section 5.


O_DIRECT


Opening with O_DIRECT asks the kernel to move data by DMA straight between your buffer and the device, skipping the page cache (open(2), O_DIRECT). The price is alignment: the buffer address, the length and the file offset must be multiples of the device's logical block size (512 bytes here), or the call fails. measured




tmpfs has no device to DMA to, so on this kernel it refuses O_DIRECT at open. Linux 6.1 added STATX_DIOALIGN to statx to ask a file for its exact alignment rules (statx(2)) not run here.


O_DIRECT is not durable. It skips the page cache, not the device's cache, and it does not commit metadata such as a new file size; you still need fdatasync. In the fio runs below, adding fdatasync after each direct 4 KiB write cut the rate from  to  writes per second.

When to use it in ML. Checkpoint writers and data loaders that manage their own buffers use it to keep the page cache for what matters and to make throughput predictable; GPUDirect Storage requires it (section 10). Do not use it for small reads you will repeat (you lose caching and readahead), or from Python on unaligned bytes objects (use an aligned buffer, e.g. mmap.mmap(-1, n), which is page aligned).


Asynchronous I/O: libaio and io_uring


A plain read blocks the thread until the data arrives, so a single thread only ever has one request in flight (queue depth 1, section 1). Two kernel interfaces let one thread keep many in flight. libaio (io_submit, io_getevents) is truly asynchronous only with O_DIRECT. io_uring (Linux 5.1+) shares two ring buffers between the program and the kernel: the program writes submission entries and reads completion entries, often with no system call per I/O (io_uring(7)). The sibling page Concurrency covers its design and the event loops built on it.

10. Storage you do not own: NFS, Lustre, object stores, FUSE, GPUDirect


ch. 48 Distributed Systems, ch. 49 Sun's Network File System


The problem. On a cluster the dataset and the checkpoint directory are rarely on a local disk. They live on a server, a parallel file system or an object store, reached over the network, and each one keeps a different subset of the local guarantees above. Nothing in this section ran here (no network storage in the VM) not run here; it is taught from each system's own documentation.


SystemHow it worksWhat changes for you


NFSOne server exports a file system; clients cache data and attributes. Linux's client gives close-to-open consistency: at open it revalidates with the server, and "when the application closes the file, the NFS client writes back any pending changes to the file so that the next opener can view the changes. This also gives the NFS client an opportunity to report write errors to the application via the return code from close(2)" (nfs(5)).Another node sees your file only after you close it and it opens it. Check the return value of close: on NFS that is where write errors appear. fsync asks the server to commit the data to its own stable storage (the COMMIT procedure of RFC 1813). Many small files cost a network round trip each for open and stat.


Lustre (and GPFS, WekaFS, ...)Metadata servers (MDS) "manage the names and directories"; file data is split across object storage targets (OSTs): "the file data is striped across the objects using RAID 0, and each object is stored on a different OST" (Lustre manual, ch. 1).Huge aggregate bandwidth for big files spread over many OSTs (set the stripe count with lfs setstripe -c N dir); metadata operations go to few servers, so millions of small files, or thousands of ranks all calling stat at start-up, are the classic way to slow a whole cluster.


Object stores (S3, GCS, Azure Blob)Objects are written whole (or in multipart uploads) and appear atomically when the upload completes; S3 has given "strong read-after-write consistency" for all applications since December 2020 (AWS, 2020-12). There is no rename and no fsync. Since August 2024 a PUT can carry If-None-Match to fail rather than overwrite an existing key (AWS, 2024-08)."Write then rename" becomes "upload under a new key, then write a small pointer or marker object last". A checkpoint is complete when its marker exists; a conditional write keeps two jobs from overwriting each other's checkpoint.


FUSE mounts of object stores (Mountpoint for S3, gcsfuse, s3fs)A user-space process implements the file system calls on top of the object API. Mountpoint, for example, writes "sequentially from a single client at a time", uploads asynchronously, and on general-purpose buckets "does not emulate operations like rename"; "if your application needs to guarantee that a new file has been uploaded to S3, it should call fsync on the file before closing it" (Mountpoint semantics).Code that relies on os.replace, on appending, or on rewriting part of a file fails or behaves differently on these mounts. Read each mount's semantics page before pointing a checkpoint writer at it.


GPUDirect Storage"enables a direct data path for direct memory access (DMA) transfers between GPU memory and storage, which avoids a bounce buffer through the CPU" (GDS overview). Programs use the cuFile API; its reference guide's examples open the file with O_DIRECT before registering it (cuFile API reference).Skips the page cache and pinned host memory entirely (section 9's rules apply: alignment, and durability still needs a sync). Worth it when host memory bandwidth or CPU copies limit checkpoint or data loading speed on GPU servers with supported NVMe or network storage.




A job on 64 nodes writes its checkpoint shards to an NFS mount, each rank calls fsync on its shard, and rank 0 then writes a COMPLETE marker file. A restarted job on another node sees the marker. Is every shard guaranteed to be readable there?




Close-to-open: once a writer has closed (or fsynced) a file and a reader opens it afterwards, the reader sees the writes. The ordering that matters is across ranks: rank 0 must write the marker only after every rank reported its shard closed and synced (a barrier), which is exactly what checkpoint libraries do before writing their metadata file.

The window this leaves, and the fix

Saving again into the same directory truncates the old shards at openat(..., O_TRUNC), so the old checkpoint is gone at the first call. Between unlinkat(.metadata) and the moment the rename is durable (the next journal commit, up to 5 s on ext4), a crash leaves a directory with no .metadata, which DCP cannot load: no checkpoint at all. 12. Data loading throughput


The problem. A GPU that waits for input wastes its time. Mohan and colleagues measured nine models on production servers at Microsoft and found that "in many cases, DNN training time is dominated by data stall time: time spent waiting for data to be fetched and preprocessed" (Analyzing and Mitigating Data Stalls in DNN Training, VLDB 2021). The storage half of that is this page's mechanisms, applied:


    

  • Few big files, read sequentially. Readahead (section 4) and large requests need sequential access; metadata costs per file (section 3: x slower cold for small files here; far worse on a network file system). Hence tar shards (WebDataset), Arrow and Parquet files, and memory-mapped token arrays. Shuffle the order of shards and shuffle within an in-memory buffer instead of reading random records.
    • 

  • Queue depth. One reader thread is queue depth 1 (section 1); DataLoader workers, prefetching and asynchronous readers keep many requests in flight. On remote storage, where each request has a long latency, this matters most.
    • 

  • The page cache is your free dataset cache while the dataset fits in memory: epoch 2 reads RAM. Size node memory with the page cache in mind, and remember it counts toward a container's memory limit (Virtual memory section 12).

Interview questions, with model answers


What does write() guarantee when it returns, and what does fsync() add?
write guarantees the bytes are in the kernel's page cache: visible to every process on this machine, but only in memory. fsync returns when the file's data and metadata have reached stable storage, including flushing the device's volatile cache. It does not cover the directory entry naming the file; that needs an fsync of the directory.


How do you replace a file atomically and durably on Linux?
Write the new contents to a temporary file in the same directory, fsync it, rename it over the target (atomic for readers: they see old or new), then fsync the directory so the rename survives a crash. Same directory, because rename is atomic only within one file system. Alternatives: O_TMPFILE plus linkat for new names, renameat2(RENAME_EXCHANGE) to swap.


fsync versus fdatasync: when is fdatasync cheaper?
fdatasync skips metadata not needed to read the data back, chiefly timestamps. When a write changes only data (an overwrite of allocated blocks), fdatasync needs no journal commit, only the data write and a cache flush; fsync still has to log the new mtime. When the write extends the file, the size must be persisted, so both need the journal. Measured here on an overwrite: about 0.39 ms against 1.3 ms.


Explain ext4's data=ordered mode and delayed allocation, and how they interact.
Ordered mode journals metadata only but writes a file's data blocks before committing the metadata that points to them, so metadata never points at stale blocks. Delayed allocation picks blocks only at writeback; until then there is nothing to order, so a commit can record a new file's name with no data yet, which after a crash gives an empty file. ext4's auto_da_alloc forces allocation on rename-over-existing and truncate-then-close to cover the common unsafe patterns, but the portable fix is fsync.


A program writes 10 GB quickly and then its writes become very slow without any errors. What is happening?
Dirty throttling: once dirty page-cache data passes the dirty limits (for the machine, or for the program's cgroup writeback domain), balance_dirty_pages pauses the writer so it cannot outrun the device. /proc/PID/wchan shows balance_dirty_pages; Dirty and Writeback in /proc/meminfo stay high. Fixes: accept device speed, write in a background thread, use dirty_bytes limits, start writeback early with sync_file_range, or O_DIRECT.


What is readahead and when does it not help?
When the kernel sees sequential reads, it fetches the following pages before they are requested, growing the window (4, 8, 16, 32 pages here) up to read_ahead_kb, and triggers the next window asynchronously from a marked page. It does nothing for random access, which is why random small reads cost one device request each and why datasets are stored as sequential shards.


Why can O_DIRECT be slower than buffered I/O, and does it make writes durable?
It removes caching and readahead, so small or repeated reads each go to the device, and it imposes alignment. It does not flush the device cache or commit metadata, so durability still needs fdatasync. It wins for large streaming transfers you will not reuse, and when you manage your own cache.


How would you checkpoint a 64-rank job to a shared file system so that a crash at any moment leaves a loadable checkpoint?
New directory per step; each rank writes and fsyncs its shard; barrier; one rank writes the metadata (or a COMPLETE marker) to a temporary name, fsyncs, renames, fsyncs the step directory and the parent; keep the previous complete checkpoint until then; on restart pick the newest directory that has the marker and loads. On an object store, the same with new keys and a marker object written last.


A dataset reads at 3 GB/s in your benchmark but 300 MB/s in the real job. What do you check?
Whether the benchmark hit the page cache (it ran twice, or the file was just written); whether the job's access pattern is random (no readahead) or small-file (metadata); the queue depth (worker count); whether the job's container has an io.max limit or a smaller memory limit (less cache); and whether workers sit in state D (ps -eo stat,wchan).

The two models, exactly


POSIX only. Durable: a file's data and its own metadata after an fsync of that file returns (fsync(2)); a directory's entries (create, rename, unlink, mkdir) after an fsync of that directory. Everything else may or may not have reached the disk, independently (each name change is atomic in itself, rename(2)). File data not yet synced may be absent, cut short, fully there, or (for a file rewritten in place without truncation persisting) a mix of old and new.


ext4 as configured here. Name and size changes go through one journal and reach the disk in order, so after a crash some prefix of them is there. An fsync of anything commits the whole running transaction, so every earlier name change is durable after it (fs/ext4/fsync.c, ext4_fsync_journal). File data is written by writeback or fsync; with delayed allocation, a file whose data was not yet written has size 0 or a shorter size after a crash, never garbage (data=ordered). auto_da_alloc: renaming over an existing file, or closing a file that was truncated, starts writing its data, and the commit that records a later name change waits for it (fs/ext4/namei.c lines 3782 to 3783, fs/ext4/file.c lines 140 to 143, ext4 docs).


Simplifications: the crash happens at some moment after the listed step and before the next; device caches honour flushes; one writer; a DCP checkpoint "loads" if its .metadata and shard come from the same save.
