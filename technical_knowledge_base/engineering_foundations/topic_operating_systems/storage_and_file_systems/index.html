The idea in one screen

Returned is not durable. write() and torch.save return once the bytes are in kernel memory, the page cache; the kernel moves them to the device later, in its own order and on its own schedule. What a crash can leave is decided only by fsync (of the file, and of its directory) and rename; what a read costs is decided by whether the page cache and readahead can serve it.

  1. write() returns at the page cache: 1.4 us. The 4 KiB is copied into a cached page, which is marked dirty. The device has received nothing.
  2. sync_file_range returns when the device acknowledges: 161 us. The page went through the block layer to the drive, which acknowledges from its volatile cache. No metadata, no cache flush.
  3. fdatasync pushes the data to stable media: 393 us. A cache flush gets it past the device cache. An overwrite changes neither the size nor the block map, so there is no journal commit; the new modification time stays in memory.
  4. fsync also commits the metadata: 1,305 us. The inode's change (the new time) goes through a journal commit as well, a second ordered write and flush (section 5).
  5. Power cut: only what is below the red line survives. The bytes of write and sync_file_range are lost although both calls returned; fdatasync keeps the data and loses only the time stamp; fsync keeps everything.

The page in six claims
  1. Returned is not durable. The 256 MiB checkpoint of section 10 left 256 MiB of dirty data in memory when torch.save returned (section 4).
  2. When the kernel writes is not a promise. The textbook says "within 30 seconds"; here the same 16 MiB stayed dirty anywhere from 0.4 to 30 seconds after the write, depending on what else the machine was doing (section 4).
  3. The safe checkpoint is five calls: write to ckpt.pt.tmp, fsync it, rename it over ckpt.pt, fsync the directory; and never overwrite the last good checkpoint in place. It cost 365 ms against 263 ms for the plain save (section 6).
  4. Libraries differ. PyTorch's distributed checkpoint fsyncs every file but deletes the old .metadata before renaming the new one in, and never fsyncs the directory: save each step to a new directory (section 10).
  5. Sequential beats random, because the kernel reads ahead: 512 small reads of a cold file became 20 device requests (section 3). Shards, not millions of small files.
  6. If fsync fails, the data is gone: the kernel may already have dropped the dirty pages. Rewrite the checkpoint from memory; never retry the fsync and carry on (section 5).

1. Devices and the block layer: what is at the bottom

A storage device keeps data without power, but it is thousands of times slower than memory, works in blocks rather than bytes, and usually has its own volatile cache. Everything above it exists to hide those three facts; every durability bug forgets one of them.

Latency is not one number: it depends on how many requests are in flight

A device serves many requests in parallel, so more in flight buys throughput until it saturates; after that, each extra request only waits longer. A DataLoader that reads one sample at a time from one thread runs at QD 1, the top bar. More workers, prefetching or asynchronous I/O move it down the chart.

At queue depth 64, fio measured about 54,700 reads per second at a mean latency near 1.15 ms. What throughput does Little's law predict for 64 requests in flight at 1.15 ms each?
Throughput = requests in flight / latency = 64 / 0.0011526 s = about 55,500 per second, within 2% of what fio measured: the device was busy all the time, and each extra request in flight only waited longer. At queue depth 1 the same law gives 1 / 80 us = 12,500 per second; fio saw 10,741 because fio's own per-request work adds to the device's time.
4 KiB random reads at four queue depths measured

fio, O_DIRECT (no page cache, section 8) on a 1 GiB file, 5 s per point. Queue depth (QD) is how many requests are in flight at once.

QD 1 to 64: throughput x5.1, mean latency x14.4. Little's law (requests in flight = throughput x latency) at QD 64: 64 / 1,152.6 us = 55,527 per second, against 54,723 measured (+1.5%). The virtual disk reports itself as rotational: 1, which it is not; read the shape, not the absolute numbers.

How a request reaches the device: per-CPU queues all the way down

A file system describes an I/O as a bio (direction, starting sector, list of memory pages); bios that touch neighbouring sectors merge into a request. Since Linux 3.13 the block layer is blk-mq: each CPU puts requests in its own software queue, which feeds one of the device's hardware queues (kernel docs: blk-mq). On NVMe, the interface modern SSDs speak over PCIe, each hardware queue is a submission and completion queue pair in host memory: the driver writes a command and rings a doorbell register; the drive fetches it by DMA, does the work, posts a completion and raises an interrupt. The specification allows up to 65,535 I/O queue pairs of up to 65,536 entries each (NVM Express base specification).

Each CPU has its own path to the drive, so no shared lock

This VM's disk as the kernel reports it: 5 CPUs, scheduler none, 5 hardware queues (one per CPU), up to 256 requests per queue, at most 1,280 KiB per request measured. The NVMe part is from the specification not run here (this disk is virtio).

Why an SSD writes more than you asked: remapping and garbage collection

Two erase blocks of four pages each illustrative; real blocks hold hundreds of pages. Mechanism and typical times from OSTEP ch. 44.

Inside a flash drive: every overwrite goes to a fresh page

Flash is read and written in pages of a few KiB but erased only in much larger erase blocks, and a page cannot be rewritten before its block is erased. The flash translation layer (FTL) inside the drive therefore writes every update to a fresh page, remaps it, and garbage-collects old blocks in the background; the extra internal writes are write amplification. Typical times for SLC flash: read about 25 us, program (write) 200 to 300 us, erase 1.5 to 2 ms (OSTEP ch. 44).

  1. A new drive: every page is erased. Two erase blocks of four pages. A page can be programmed (written) once after its block is erased.
  2. Write A, B and C. The FTL places them in free pages of block 0 and records logical page to physical page in its map.
  3. Overwrite A: it goes to a fresh page. Flash cannot rewrite page 0 in place, so the new A goes to page 3, the map now points there, and the old copy is marked invalid. One host write, one flash write.
  4. Overwrite B: block 0 is full, so block 1. Block 0 now holds two dead pages that cannot be reused until the whole block is erased.
  5. Garbage collection copies the live pages out. To free block 0 the FTL copies its valid pages (C and A′) to block 1: two flash writes the host never asked for. This is write amplification.
  6. Erase block 0. An erase takes 1.5 to 2 ms against 200 to 300 us to program a page (SLC, OSTEP ch. 44). A discard (TRIM) of dead data would have spared the copies. Write amplification here: 7 flash writes / 5 host writes = 1.4.

The device's cache. Most drives acknowledge a write once it is in their internal DRAM. If power fails before it reaches flash or platter, the write is lost although the drive said "done". The kernel has two tools for this (kernel docs: writeback cache control): a cache flush (REQ_PREFLUSH: "flush the volatile cache before this I/O") and FUA, Force Unit Access (REQ_FUA: "this write completes only once it is on stable storage"). A file system's fsync ends with one of them: that, not the write, is the red line in the hero figure.

Disks, schedulers, TRIM on this VM, and the commands that show the block layer (depth)

Hard disks. A spinning platter and a moving arm: a random read waits for the arm to move (seek) and the platter to turn (rotation), several milliseconds, so a few hundred random reads per second; sequential reads are fast because nothing moves. OSTEP ch. 37 works the numbers.

Plugging and schedulers. A thread may plug its queue while it submits a batch, so the batch is merged before it is sent. An optional I/O scheduler may reorder requests: none, mq-deadline (bounds how long a request waits), kyber (latency targets) or bfq (fair shares between processes). For fast NVMe drives none is the usual choice because reordering costs more than it saves.

TRIM. A discard (TRIM on SATA, Deallocate on NVMe) tells the drive which blocks a deleted file freed, so its garbage collector stops copying dead data. ext4 can send discards at every delete (mount option discard) or you run fstrim periodically. This VM mounts its disk nodiscard and runs a small service that calls /sbin/fstrim /var/lib/docker after deletes (seen in the VM's process list with docker run --pid host ... ps) measured.

This disk reports a write-back cache and no FUA support, so the kernel emulates FUA with a write followed by a full flush. A drive that wrongly reports write through, or firmware that ignores flushes, silently breaks every guarantee on this page; only power-cut tests can find that. 2. Files, names and inodes: the VFS and ext4's layout


Programs want named files with sizes, owners and times, and they want the same open, read, write to work on ext4, XFS, tmpfs, NFS or /proc. The VFS (virtual file system switch) gives every file system one set of objects and calls to implement (kernel docs: VFS). Below, mke2fs built a 64 MiB ext4 file system inside an ordinary file and debugfs (which reads the image directly, so no mount and no privileges) copied in a 3,000,000-byte "checkpoint" and a small file with two names measured. The figure is that real image seen through the kernel's objects.


Four objects. The superblock, one per mounted file system: its type, block size, and the operations on its inodes (struct super_block, fs.h line 1416). The inode, one per file whatever its names: type, permissions, owner, size, times, link count, where its data lives, and an address_space (line 451) holding that file's pages in the page cache. The dentry, one per name in a path, cached: "the name ckpt.pt in directory X is inode 13"; a negative dentry caches "this name does not exist". The file, one per open(): offset, open flags, pointers to dentry and inode; file descriptors index a per-process table of these (Processes and the system-call API section 7 draws the three tables).


Names are not files. A directory is itself a file whose content is a table of (name, inode number). A hard link is a second entry for the same inode (hello.txt and hardlink.txt are both inode 14, Links: 2); a symbolic link is a small file containing a path. The inode is freed when its link count is zero and no process has it open, so deleting a checkpoint that a running process still holds open frees no space until it closes; lsof +L1 lists such deleted-but-open files.


Extents. Inode 13's data is one extent: logical blocks 0 to 732 stored in physical blocks 2066 to 2798, contiguous. That is 733 blocks of 4,096 bytes, the fewest that hold 3,000,000 bytes (3,000,000 / 4,096 = 732.4), and Blockcount: 5864 counts the same space in 512-byte sectors (733 x 8). ext2 and ext3 listed every block number; an extent says "start, length" once, so a large file costs ext4 almost no metadata. ext4 also groups inodes and their data into block groups so a file's inode sits near its data (OSTEP ch. 41 credits the idea to FFS). The journal (section 7) is itself an inode, 4 MiB here.

On a network file system each open and stat is also a round trip to a server (section 9), so the gap grows from tens to thousands of times.

3. Reading: the page cache and readahead


A device request has a large fixed cost; programs often read 4 KiB at a time, and often read the same file again (every epoch). Two answers: keep what was read in memory, the page cache, and when a program reads sequentially, fetch the next pages before it asks, readahead. How the page cache competes for memory and is reclaimed is Virtual memory's; this section is how data gets into it.

The rule, from mm/readahead.c source (v5.10). First window, get_init_ra_size (line 311): round the request up to a power of two, then x4 if it is at most 1/32 of the maximum, x2 if at most 1/4, else the maximum. Each later window, get_next_ra_size (line 329): x4 while under 1/16 of the maximum, then x2, capped at the maximum. The read path in the source, and the knobs (depth)


source read(fd, buf, 4096) reaches ext4's ext4_file_read_iter, which calls the generic generic_file_buffered_read (mm/filemap.c line 2185, v5.10). 4. Writing: dirty pages, writeback and throttling


If every write() waited for the device, a checkpoint written in 4 KiB pieces would pay a device round trip for each. So write() copies the bytes into the cached page, marks it dirty (changed in memory, not yet on the device) and returns. Per-device flusher threads (kernel workers named kworker/u*:*-flush-*) write dirty pages back for one of three reasons (vm sysctl docs; mm/page-writeback.c lines 74 to 109):


    

  1. Age: every dirty_writeback_centisecs (500, so 5 s) the flusher wakes and writes data that has been dirty longer than dirty_expire_centisecs (3000, so 30 s).
    2. 

  2. Background threshold: when dirty data passes dirty_background_ratio (10%) of dirtyable memory (free memory plus file pages that could be reclaimed, not total RAM: global_dirtyable_memory, line 362), the flusher writes everything, whatever its age.
    3. 

  3. Hard threshold: near dirty_ratio (20%) the writing process itself is paused in balance_dirty_pages (line 1555, the pause at line 1795) so it cannot dirty memory faster than the device drains it. This is dirty throttling: write() becomes slow without any error.
    4.

Our reading of the source: wb_over_bg_thresh (mm/page-writeback.c line 1960) also compares this writeback domain's dirty pages with its share of the background threshold, a share proportional to how much it recently wrote back. A brand-new container has almost no share, so even 16 MiB counts as "over its threshold" and is written in the background. After the container had just written and synced 1 GiB (the "primed" runs), it had a share, and the same 16 MiB waited between 0.4 and 30 s as that share decayed. 5. Durability: fsync, fdatasync, and when fsync fails


A checkpoint, a database log or a "this checkpoint is complete" marker must survive a crash, so the program needs a call that returns only when the data is on stable storage, and it must know exactly what that call covers. fsync(fd) covers the file's data and all its metadata, then a device cache flush ("This includes writing through or flushing a disk cache if present", fsync(2)); not the directory entry that names the file. fdatasync(fd) covers the data plus only the metadata "needed in order to allow a subsequent data retrieval to be correctly handled": size and block map yes, modification time no. sync_file_range only starts or waits for writeback of a byte range; the kernel's own comment: "there are no guarantees here that the data will be available on disk after a crash" (fs/sync.c lines 351 to 355, v5.10).

When fsync fails


A device error during writeback is reported to the next fsync. 6. Atomic replace: a crash sees old or new, never half

POSIX only. Durable: a file's data and its own metadata after an fsync of that file returns (fsync(2)); a directory's entries (create, rename, unlink, mkdir) after an fsync of that directory. ext4 as configured here. Name and size changes go through one journal and reach the disk in order, so after a crash some prefix of them is there. 7. Journaling: how ext4 keeps its own structures consistent


Creating, growing or renaming a file changes several blocks (the inode, a free-block bitmap, the directory). A crash between them leaves the file system's own structures inconsistent. ext4 hands the fix to a generic journaling layer, jbd2: every operation that changes metadata opens a handle on the current running transaction, many operations share one transaction, and the transaction is committed (its blocks written to the journal, then a commit block) when it is 5 seconds old (JBD2_DEFAULT_MAX_COMMIT_AGE, include/linux/jbd2.h line 48, v5.10; the commit=5 mount option), when the journal fills, or when someone's fsync needs it. After a crash, mount replays committed transactions and discards incomplete ones: seconds, not the full scan of fsck. The root's OS simulators tab crashes such an update at every block write; Fig. 6 is the order ext4 really uses; pick a data mode.

The page cache is a bargain for data you read twice and for small writes, but a training job also streams data it reads once (a dataset bigger than RAM) and writes data it will not read back (a checkpoint). O_DIRECT is not durable. It skips the page cache, not the device's cache, and does not commit metadata such as a new file size. In the fio runs below, adding fdatasync after each direct 4 KiB write cut the rate from 12,706 to 6,270 writes per second.




Where the bytes are copied on each path




Buffered I/O copies once by CPU into the page cache, and the device later moves it by DMA. O_DIRECT moves it by DMA between your (aligned) buffer and the device. GPUDirect Storage moves it between GPU memory and storage, with no bounce buffer through the CPU not run here. None of the three flushes the device's cache: durability still needs fdatasync.






When to use it. Checkpoint writers and data loaders that manage their own buffers use it to keep the page cache for what matters and make throughput predictable; GPUDirect Storage requires it. Not for small reads you will repeat (no caching, no readahead), nor from Python on unaligned bytes objects (use an aligned buffer, e.g. mmap.mmap(-1, n), which is page aligned).

9. Storage you do not own: what network file systems promise


On a cluster the dataset and the checkpoint directory usually live on a server, a parallel file system or an object store, and each keeps a different subset of the local guarantees above. Nothing in this section ran here (no network storage in the VM) not run here; it is taught from each system's own documentation. How those systems are built and sized (Lustre's servers and striping, object stores, staging, bandwidth) is Storage and data movement's; this section is the semantics a checkpoint writer depends on.


NFS: close-to-open. One server exports a file system; clients cache data and attributes. Linux's client gives close-to-open consistency: at open it revalidates with the server, and "when the application closes the file, the NFS client writes back any pending changes to the file so that the next opener can view the changes. This also gives the NFS client an opportunity to report write errors to the application via the return code from close(2)" (nfs(5)). fsync asks the server to commit the data to its own stable storage (the COMMIT procedure of RFC 1813).


A job on 64 nodes writes its checkpoint shards to an NFS mount, each rank calls fsync on its shard, and rank 0 then writes a COMPLETE marker file. A restarted job on another node sees the marker. Is every shard guaranteed to be readable there?




Close-to-open: once a writer has closed (or fsynced) a file and a reader opens it afterwards, the reader sees the writes. The ordering that matters is across ranks: rank 0 must write the marker only after every rank reported its shard closed and synced (a barrier), which is exactly what checkpoint libraries do before writing their metadata file.




Another node sees your shard only after you close it and it opens it




Time runs down. Rank 7 writes a shard, rank 0 writes the marker after a barrier, and a restarted job on node B reads them. The ordering that matters is across ranks: the marker is written only after every rank has closed (or fsynced) its shard. Per nfs(5); the message names are NFSv3's.






Check the return value of close: on NFS that is where write errors appear. And many small files cost a network round trip each for open and stat.


Object stores and FUSE mounts have no rename and no fsync in the local sense, so "write then rename" becomes "upload under a new key, then write a small pointer or marker object last": a checkpoint is complete when its marker exists. Code that relies on os.replace, on appending, or on rewriting part of a file fails or behaves differently on such mounts; read each mount's semantics page before pointing a checkpoint writer at it.

The window this leaves, and the fix

Saving again into the same directory truncates the old shards at openat(..., O_TRUNC), so the old checkpoint is gone at the first call. Between unlinkat(.metadata) and the moment the rename is durable (the next journal commit, up to 5 s on ext4), a crash leaves a directory with no .metadata, which DCP cannot load: no checkpoint at all. And because the directory is never fsynced, even after dcp.save has returned a crash can bring back the old .metadata next to the new, fsynced shard: a checkpoint whose metadata and data come from different saves. With a new directory per step there is nothing to delete or truncate, and a crash can only lose the step being written. This is what torchtitan does ("Standardized checkpoint path, e.g. checkpoints/step-100", torchtitan base.py line 379). Add an fsync of the parent directory after the save so the new directory's name is durable too, and treat a step directory without .metadata as incomplete. This is our reading of the source and the trace, shown as states in the crash lab (pick the two DCP protocols); it is not a reported incident.


Asynchronous saves. dcp.async_save first stages the state (copies tensors to CPU memory), returns a future, and writes in the background, so training continues during the slow part. Here it blocked training for 66 ms of a 501 ms save. Two costs remain: a second copy of the state in host memory while it is written, and the writes still compete for the device and the dirty-page budget (section 4), so a step that runs during the background write can be slower.

Interview questions, with model answers (optional rehearsal)


What does write() guarantee when it returns, and what does fsync() add?
write guarantees the bytes are in the kernel's page cache: visible to every process on this machine, but only in memory. fsync returns when the file's data and metadata have reached stable storage, including flushing the device's volatile cache. It does not cover the directory entry naming the file; that needs an fsync of the directory.


How do you replace a file atomically and durably on Linux?
Write the new contents to a temporary file in the same directory, fsync it, rename it over the target (atomic for readers: they see old or new), then fsync the directory so the rename survives a crash. Same directory, because rename is atomic only within one file system. Alternatives: O_TMPFILE plus linkat for new names, renameat2(RENAME_EXCHANGE) to swap.


fsync versus fdatasync: when is fdatasync cheaper?
fdatasync skips metadata not needed to read the data back, chiefly timestamps. When a write changes only data (an overwrite of allocated blocks), fdatasync needs no journal commit, only the data write and a cache flush; fsync still has to log the new mtime. When the write extends the file, the size must be persisted, so both need the journal. Measured here on an overwrite: about 0.39 ms against 1.3 ms.


Explain ext4's data=ordered mode and delayed allocation, and how they interact.
Ordered mode journals metadata only but writes a file's data blocks before committing the metadata that points to them, so metadata never points at stale blocks. Delayed allocation picks blocks only at writeback; until then there is nothing to order, so a commit can record a new file's name with no data yet, which after a crash gives an empty file. ext4's auto_da_alloc forces allocation on rename-over-existing and truncate-then-close to cover the common unsafe patterns, but the portable fix is fsync.


A program writes 10 GB quickly and then its writes become very slow without any errors. What is happening?
Dirty throttling: once dirty page-cache data passes the dirty limits (for the machine, or for the program's cgroup writeback domain), balance_dirty_pages pauses the writer so it cannot outrun the device. /proc/PID/wchan shows balance_dirty_pages; Dirty and Writeback in /proc/meminfo stay high. Fixes: accept device speed, write in a background thread, use dirty_bytes limits, start writeback early with sync_file_range, or O_DIRECT.


What is readahead and when does it not help?
When the kernel sees sequential reads, it fetches the following pages before they are requested, growing the window (4, 8, 16, 32 pages here) up to read_ahead_kb, and triggers the next window asynchronously from a marked page. It does nothing for random access, which is why random small reads cost one device request each and why datasets are stored as sequential shards.


Why can O_DIRECT be slower than buffered I/O, and does it make writes durable?
It removes caching and readahead, so small or repeated reads each go to the device, and it imposes alignment. It does not flush the device cache or commit metadata, so durability still needs fdatasync. It wins for large streaming transfers you will not reuse, and when you manage your own cache.


How would you checkpoint a 64-rank job to a shared file system so that a crash at any moment leaves a loadable checkpoint?
New directory per step; each rank writes and fsyncs its shard; barrier; one rank writes the metadata (or a COMPLETE marker) to a temporary name, fsyncs, renames, fsyncs the step directory and the parent; keep the previous complete checkpoint until then; on restart pick the newest directory that has the marker and loads. On an object store, the same with new keys and a marker object written last.


A dataset reads at 3 GB/s in your benchmark but 300 MB/s in the real job. What do you check?
Whether the benchmark hit the page cache (it ran twice, or the file was just written); whether the job's access pattern is random (no readahead) or small-file (metadata); the queue depth (worker count); whether the job's container has an io.max limit or a smaller memory limit (less cache); and whether workers sit in state D (ps -eo stat,wchan).
