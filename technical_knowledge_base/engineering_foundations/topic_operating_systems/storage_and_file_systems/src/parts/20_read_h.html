8. Journaling in ext4 and XFS, and copy-on-write file systems

ch. 42 Crash Consistency: FSCK and Journaling, ch. 43 Log-structured File Systems

The problem. Creating, growing or renaming a file changes several blocks (the inode, a bitmap of free blocks, the directory). A crash between them leaves the file system's own structures inconsistent. The root's {{OS simulators|n:3f05c17b0d0d81c5a97ce991644af140}} tab ("crash consistency") crashes such an update at every block write, with no journal, data journaling and ordered journaling, and repairs it with fsck or a journal replay. Here: how Linux's file systems really do it, and what it means for your files.

ext4's journal: jbd2

ext4 hands its journaling to a generic layer, jbd2. Every operation that changes metadata opens a handle on the current running transaction; many operations share one transaction. The transaction is committed (its blocks written to the journal, then a commit block) when it is 5 seconds old (JBD2_DEFAULT_MAX_COMMIT_AGE, include/linux/jbd2.h line 48, v5.10; the commit=5 mount option), when the journal fills, or when someone's fsync needs it. Later the blocks are written to their real places (a checkpoint, in journaling's sense) and that journal space is reused. After a crash, mount replays committed transactions and discards incomplete ones: seconds, not the full scan of fsck.

Three data modes


The journal always covers metadata. What happens to file data is the data= mount option ({{ext4 docs|https://docs.kernel.org/admin-guide/ext4.html}}):


ModeFile dataAfter a crash


data=journalwritten to the journal too, then in place"bringing both data and metadata into a consistent state"; slowest for most workloads (every byte written twice)


data=ordered (default, this VM)"All data are forced directly out to the main file system prior to its metadata being committed to the journal"a file's metadata never points at blocks with stale contents; recently written data may be missing, never garbage


data=writeback"Data ordering is not preserved""incorrect data [can] appear in files which were written shortly before the crash"; the same level as "XFS and JFS in its default mode - metadata journaling"




Delayed allocation (the delalloc option, on here) interacts with ordered mode in a way that matters for checkpoints. ext4 does not choose disk blocks at write(); it chooses them at writeback, when it knows how big the file is, which gives large contiguous extents (the single extent of section 3). But until then there are no blocks to order, so the journal can commit a new file's name and size while its data is still only in memory. That is the mechanism behind the zero-length files of 2009 and the reason for the auto_da_alloc heuristic of section 7.


Barriers. A commit block must not reach the platter before the blocks it commits. jbd2 writes the commit block with a cache flush and FUA (REQ_PREFLUSH | REQ_FUA, fs/jbd2/commit.c line 157, v5.10; section 1) unless mounted barrier=0 (this VM: barrier, the default). Turning barriers off on a drive with a volatile cache trades crash safety for speed; never do it for a checkpoint volume.


XFS, and file systems that never overwrite


XFS, common on large local arrays, journals metadata only, with a design ("delayed logging") that batches many changes into each log write ({{kernel docs: XFS delayed logging|https://docs.kernel.org/filesystems/xfs/xfs-delayed-logging-design.html}}). Do not count on ext4's auto_da_alloc rename rule there or anywhere else: the fsync rules of section 7 are what every file system promises to honour. not run here (the kernel knows XFS, but mounting needs privileges)


Copy-on-write file systems (btrfs, ZFS) never overwrite a block in place: a change writes new blocks and new copies of every tree node above them, up to a new root, and the commit is the single write that switches to the new root. The file system is always consistent with no journal replay, and snapshots cost almost nothing (keep the old root). OSTEP ch. 43 develops the same idea as the log-structured file system. Durability of your file still needs fsync. not run here

When it bites in ML. Rarely through the journal itself. It bites through its defaults: a 5-second commit window during which renames and new names are not durable, ordered mode that keeps file systems sane but does not make your file complete, and different file systems on different clusters (ext4 locally, XFS on the big array, something else entirely over the network) making "it worked on my machine" checkpoint code unsafe elsewhere.
