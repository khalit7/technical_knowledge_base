7. Journaling: how ext4 keeps its own structures consistent

Creating, growing or renaming a file changes several blocks (the inode, a free-block bitmap, the directory). A crash between them leaves the file system's own structures inconsistent. ext4 hands the fix to a generic journaling layer, jbd2: every operation that changes metadata opens a handle on the current running transaction, many operations share one transaction, and the transaction is committed (its blocks written to the journal, then a commit block) when it is 5 seconds old (JBD2_DEFAULT_MAX_COMMIT_AGE, include/linux/jbd2.h line 48, v5.10; the commit=5 mount option), when the journal fills, or when someone's fsync needs it. After a crash, mount replays committed transactions and discards incomplete ones: seconds, not the full scan of fsck. The root's {{OS simulators|n:3f05c17b0d0d81c5a97ce991644af140}} tab crashes such an update at every block write; Fig. 6 is the order ext4 really uses; pick a data mode.

  1. Handles join the running transaction. The rename or create changed the inode, a directory block and a bitmap, in memory; the file's data is dirty in the page cache. Crash now: nothing new is on disk. Old state.
  2. Commit starts (5 s old, or an fsync): data first. Ordered mode writes the data blocks to their home locations before any metadata that points at them is logged. Crash now: new data sits in blocks nothing points to. Old state, no harm.
  3. Metadata blocks to the journal. The changed metadata blocks are copied into the journal area, the next slots of its ring. Crash now: no commit block, so replay discards the transaction. Old state.
  4. Commit block, with PREFLUSH and FUA. The device cache is flushed and the commit block written through to stable media: the transaction is committed. Crash now: replay copies the metadata home. The new file, with its data.
  5. Checkpoint: metadata written home, later. In the background the metadata blocks are written to their real places. Crash now: replay is harmless (it writes the same blocks again).
  6. Journal space freed. That part of the journal is reused by later transactions. Crash now: the new state, nothing to replay.
  1. Handles join the running transaction. As in ordered mode: metadata and data are changed in memory. Crash now: old state.
  2. Data and metadata to the journal. In data=journal mode the file's data is logged too: every byte is written twice. Crash now: no commit block, replay discards both. Old state.
  3. Commit block, with PREFLUSH and FUA. Data and metadata are committed together. Crash now: replay writes both home. Consistent data and metadata.
  4. Checkpoint: both written home. The second write of every byte. Crash now: replay is harmless.
  5. Journal space freed. Reused by later transactions. Crash now: the new state.
  1. Handles join the running transaction. As in the other modes. Crash now: old state.
  2. Metadata to the journal; data not waited for. data=writeback does not order data before metadata: the data may still be dirty in memory. Crash now: no commit block. Old state.
  3. Commit block, with PREFLUSH and FUA. The metadata is committed while the data has not reached its blocks. Crash now: replay installs an inode that points at blocks whose new data never arrived, so their stale contents appear in the file.
  4. Data written later by ordinary writeback. Whenever the flusher gets to it. Crash now: replay gives the new file with its data.
  5. Checkpoint and journal space freed. As in the other modes. Crash now: the new state.

Fig. 6: one commit, step by step: in ordered mode the data reaches home before the metadata that points to it is committed. One transaction holding a new file's inode, its directory entry and a bitmap block (orange), plus the file's 4 data blocks (blue; grey with a red edge where a block still holds stale contents). Order from fs/jbd2/commit.c and the ext4 documentation; "Crash now" is what replay finds.

The journal always covers metadata; the data= mount option decides what happens to file data:

ModeFile dataAfter a crash ({{ext4 docs|https://docs.kernel.org/admin-guide/ext4.html}})
data=journalwritten to the journal too, then in place"bringing both data and metadata into a consistent state"; slowest for most workloads (every byte written twice)
data=ordered (default, this VM)"All data are forced directly out to the main file system prior to its metadata being committed to the journal"a file's metadata never points at blocks with stale contents; recently written data may be missing, never garbage
data=writeback"Data ordering is not preserved""incorrect data [can] appear in files which were written shortly before the crash"; the same level as "XFS and JFS in its default mode - metadata journaling"

Delayed allocation (delalloc, on here) is why ordered mode does not make your file complete. ext4 chooses disk blocks at writeback, not at write(), when it knows how big the file is, which gives large contiguous extents (the single extent of section 2). Until then there are no blocks to order, so the journal can commit a new file's name and size while its data is still only in memory: the zero-length files of 2009, and the reason for the auto_da_alloc heuristic of section 6.

Barriers. A commit block must not reach the media before the blocks it commits, so jbd2 writes it with a cache flush and FUA (REQ_PREFLUSH | REQ_FUA, fs/jbd2/commit.c line 157, v5.10; section 1) unless mounted barrier=0 (this VM: barrier, the default). Turning barriers off on a drive with a volatile cache trades crash safety for speed; never do it for a checkpoint volume.

When it bites in ML: through its defaults. A 5-second window in which renames and new names are not durable; ordered mode that keeps the file system sane but does not make your file complete; and different file systems on different clusters (ext4 locally, XFS on the big array, something else over the network) making "it worked on my machine" checkpoint code unsafe elsewhere.

XFS, common on large local arrays, journals metadata only, with a design ("delayed logging") that batches many changes into each log write ({{kernel docs: XFS delayed logging|https://docs.kernel.org/filesystems/xfs/xfs-delayed-logging-design.html}}). Do not count on ext4's auto_da_alloc rename rule there or anywhere else: the fsync rules of section 6 are what every file system promises to honour. not run here (the kernel knows XFS, but mounting needs privileges)


Copy-on-write file systems (btrfs, ZFS) never overwrite a block in place: a change writes new blocks and new copies of every tree node above them, up to a new root, and the commit is the single write that switches to the new root. The file system is always consistent with no journal replay, and snapshots cost almost nothing (keep the old root). OSTEP ch. 43 develops the same idea as the log-structured file system.
