10. Storage you do not own: NFS, Lustre, object stores, FUSE, GPUDirect

ch. 48 Distributed Systems, ch. 49 Sun's Network File System

The problem. On a cluster the dataset and the checkpoint directory are rarely on a local disk. They live on a server, a parallel file system or an object store, reached over the network, and each one keeps a different subset of the local guarantees above. Nothing in this section ran here (no network storage in the VM) not run here; it is taught from each system's own documentation.

SystemHow it worksWhat changes for you
NFSOne server exports a file system; clients cache data and attributes. Linux's client gives close-to-open consistency: at open it revalidates with the server, and "when the application closes the file, the NFS client writes back any pending changes to the file so that the next opener can view the changes. This also gives the NFS client an opportunity to report write errors to the application via the return code from close(2)" ({{nfs(5)|https://man7.org/linux/man-pages/man5/nfs.5.html}}).Another node sees your file only after you close it and it opens it. Check the return value of close: on NFS that is where write errors appear. fsync asks the server to commit the data to its own stable storage (the COMMIT procedure of {{RFC 1813|https://www.rfc-editor.org/rfc/rfc1813#section-3.3.21}}). Many small files cost a network round trip each for open and stat.
Lustre (and GPFS, WekaFS, ...)Metadata servers (MDS) "manage the names and directories"; file data is split across object storage targets (OSTs): "the file data is striped across the objects using RAID 0, and each object is stored on a different OST" ({{Lustre manual, ch. 1|https://doc.lustre.org/lustre_manual.xhtml}}).Huge aggregate bandwidth for big files spread over many OSTs (set the stripe count with lfs setstripe -c N dir); metadata operations go to few servers, so millions of small files, or thousands of ranks all calling stat at start-up, are the classic way to slow a whole cluster.
Object stores (S3, GCS, Azure Blob)Objects are written whole (or in multipart uploads) and appear atomically when the upload completes; S3 has given "strong read-after-write consistency" for all applications since December 2020 ({{AWS, 2020-12|https://aws.amazon.com/about-aws/whats-new/2020/12/amazon-s3-now-delivers-strong-read-after-write-consistency-automatically-for-all-applications/}}). There is no rename and no fsync. Since August 2024 a PUT can carry If-None-Match to fail rather than overwrite an existing key ({{AWS, 2024-08|https://aws.amazon.com/about-aws/whats-new/2024/08/amazon-s3-conditional-writes/}})."Write then rename" becomes "upload under a new key, then write a small pointer or marker object last". A checkpoint is complete when its marker exists; a conditional write keeps two jobs from overwriting each other's checkpoint.
FUSE mounts of object stores (Mountpoint for S3, gcsfuse, s3fs)A user-space process implements the file system calls on top of the object API. Mountpoint, for example, writes "sequentially from a single client at a time", uploads asynchronously, and on general-purpose buckets "does not emulate operations like rename"; "if your application needs to guarantee that a new file has been uploaded to S3, it should call fsync on the file before closing it" ({{Mountpoint semantics|https://github.com/awslabs/mountpoint-s3/blob/main/doc/SEMANTICS.md}}).Code that relies on os.replace, on appending, or on rewriting part of a file fails or behaves differently on these mounts. Read each mount's semantics page before pointing a checkpoint writer at it.
GPUDirect Storage"enables a direct data path for direct memory access (DMA) transfers between GPU memory and storage, which avoids a bounce buffer through the CPU" ({{GDS overview|https://docs.nvidia.com/gpudirect-storage/overview-guide/index.html}}). Programs use the cuFile API; its reference guide's examples open the file with O_DIRECT before registering it ({{cuFile API reference|https://docs.nvidia.com/gpudirect-storage/api-reference-guide/index.html}}).Skips the page cache and pinned host memory entirely (section 9's rules apply: alignment, and durability still needs a sync). Worth it when host memory bandwidth or CPU copies limit checkpoint or data loading speed on GPU servers with supported NVMe or network storage.
A job on 64 nodes writes its checkpoint shards to an NFS mount, each rank calls fsync on its shard, and rank 0 then writes a COMPLETE marker file. A restarted job on another node sees the marker. Is every shard guaranteed to be readable there?
Close-to-open: once a writer has closed (or fsynced) a file and a reader opens it afterwards, the reader sees the writes. The ordering that matters is across ranks: rank 0 must write the marker only after every rank reported its shard closed and synced (a barrier), which is exactly what checkpoint libraries do before writing their metadata file.
