9. Storage you do not own: what network file systems promise

On a cluster the dataset and the checkpoint directory usually live on a server, a parallel file system or an object store, and each keeps a different subset of the local guarantees above. Nothing in this section ran here (no network storage in the VM) not run here; it is taught from each system's own documentation. How those systems are built and sized (Lustre's servers and striping, object stores, staging, bandwidth) is {{Storage and data movement|n:3fc5c17b0d0d818a94ced3fc7c3331fe}}'s; this section is the semantics a checkpoint writer depends on.

NFS: close-to-open. One server exports a file system; clients cache data and attributes. Linux's client gives close-to-open consistency: at open it revalidates with the server, and "when the application closes the file, the NFS client writes back any pending changes to the file so that the next opener can view the changes. This also gives the NFS client an opportunity to report write errors to the application via the return code from close(2)" ({{nfs(5)|https://man7.org/linux/man-pages/man5/nfs.5.html}}). fsync asks the server to commit the data to its own stable storage (the COMMIT procedure of {{RFC 1813|https://www.rfc-editor.org/rfc/rfc1813#section-3.3.21}}).

Another node sees your shard only after you close it and it opens it

Time runs down. Rank 7 writes a shard, rank 0 writes the marker after a barrier, and a restarted job on node B reads them. The ordering that matters is across ranks: the marker is written only after every rank has closed (or fsynced) its shard. Per nfs(5); the message names are NFSv3's.

A job on 64 nodes writes its checkpoint shards to an NFS mount, each rank calls fsync on its shard, and rank 0 then writes a COMPLETE marker file. A restarted job on another node sees the marker. Is every shard guaranteed to be readable there?
Close-to-open: once a writer has closed (or fsynced) a file and a reader opens it afterwards, the reader sees the writes. The ordering that matters is across ranks: rank 0 must write the marker only after every rank reported its shard closed and synced (a barrier), which is exactly what checkpoint libraries do before writing their metadata file.

Check the return value of close: on NFS that is where write errors appear. And many small files cost a network round trip each for open and stat.

Object stores and FUSE mounts have no rename and no fsync in the local sense, so "write then rename" becomes "upload under a new key, then write a small pointer or marker object last": a checkpoint is complete when its marker exists. Code that relies on os.replace, on appending, or on rewriting part of a file fails or behaves differently on such mounts; read each mount's semantics page before pointing a checkpoint writer at it.

Object stores (S3, GCS, Azure Blob)Objects are written whole (or in multipart uploads) and appear atomically when the upload completes; S3 has given "strong read-after-write consistency" for all applications since December 2020 ({{AWS, 2020-12|https://aws.amazon.com/about-aws/whats-new/2020/12/amazon-s3-now-delivers-strong-read-after-write-consistency-automatically-for-all-applications/}}). Since August 2024 a PUT can carry If-None-Match to fail rather than overwrite an existing key ({{AWS, 2024-08|https://aws.amazon.com/about-aws/whats-new/2024/08/amazon-s3-conditional-writes/}}).New key, marker last. A conditional write keeps two jobs from overwriting each other's checkpoint.
FUSE mounts of object stores (Mountpoint for S3, gcsfuse, s3fs)A user-space process implements the file system calls on top of the object API. Mountpoint, for example, writes "sequentially from a single client at a time", uploads asynchronously, and on general-purpose buckets "does not emulate operations like rename"; "if your application needs to guarantee that a new file has been uploaded to S3, it should call fsync on the file before closing it" ({{Mountpoint semantics|https://github.com/awslabs/mountpoint-s3/blob/main/doc/SEMANTICS.md}}).No os.replace, no appends, no partial rewrites; fsync before close.
GPUDirect Storage"enables a direct data path for direct memory access (DMA) transfers between GPU memory and storage, which avoids a bounce buffer through the CPU" ({{GDS overview|https://docs.nvidia.com/gpudirect-storage/overview-guide/index.html}}). Programs use the cuFile API; its reference guide's examples open the file with O_DIRECT before registering it ({{cuFile API reference|https://docs.nvidia.com/gpudirect-storage/api-reference-guide/index.html}}).Skips the page cache and pinned host memory entirely (section 8's rules apply: alignment, and durability still needs a sync). Worth it when host memory bandwidth or CPU copies limit checkpoint or data loading speed on GPU servers with supported NVMe or network storage.
