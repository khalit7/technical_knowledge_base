Here the same write paths save a 256 MiB state (), five times each on ext4, plus PyTorch's distributed checkpoint (DCP) in three settings and its asynchronous save. "Dirty after" is how much of the checkpoint was still only in memory when the call returned. measured

Safety costs about 100 ms on a 263 ms save; the saves that skip fsync return with all 256 MiB still in memory

Medians of 5 runs (min and max in src/raw/ckpt_time.txt). fsync added 86 ms to a 263 ms save; the full safe protocol 102 ms, of which the directory fsync was 2.3 ms. Four writer threads made DCP faster than one. On this VM the device absorbs 256 MiB in about a tenth of a second; a device that writes 250 MB/s (an illustrative cloud-volume rate) would need 268 MB / 250 MB/s = about 1.1 s for the same fsync.

torch.save writes a zip archive: a pickle of the object structure plus one record per tensor storage. Given a path, it opens the file itself (O_WRONLY|O_CREAT|O_TRUNC in the trace of section 6), writes and closes: no fsync, and the old file's contents are discarded at open. Loading needs the zip's central directory, written last; a file cut short anywhere fails to load, the error the root's Debug lab case "Disk full mid-checkpoint: a cryptic error and a destroyed checkpoint" shows (failed finding central directory).

torch.distributed.checkpoint source PyTorch 2.14.1 (the version in this image, git 5c48869), {{torch/distributed/checkpoint/filesystem.py|https://github.com/pytorch/pytorch/blob/v2.14.1/torch/distributed/checkpoint/filesystem.py#L762}}. Every rank writes its own files, named __{rank}_{n}.distcp, one per writer thread (thread_count); with sync_files=True (the default) each is flushed and fsynced before closing (lines 470 to 474). Then the coordinator rank, in finish (line 762), writes the global .metadata.tmp, fsyncs it (lines 779 to 783), deletes any existing .metadata (line 796) and renames the temporary file into place (line 798). It never fsyncs a directory. The traced save, overwriting an existing checkpoint directory:



The window this leaves, and the fix

Saving again into the same directory truncates the old shards at openat(..., O_TRUNC), so the old checkpoint is gone at the first call. Between unlinkat(.metadata) and the moment the rename is durable (the next journal commit, up to 5 s on ext4), a crash leaves a directory with no .metadata, which DCP cannot load: no checkpoint at all. And because the directory is never fsynced, even after dcp.save has returned a crash can bring back the old .metadata next to the new, fsynced shard: a checkpoint whose metadata and data come from different saves. With a new directory per step there is nothing to delete or truncate, and a crash can only lose the step being written. This is what torchtitan does ("Standardized checkpoint path, e.g. checkpoints/step-100", {{torchtitan base.py line 379|https://github.com/pytorch/torchtitan/blob/d75ddfaace477e18f4e9ae3b5aec060299ca6251/torchtitan/components/checkpointer/base.py#L379}}). Add an fsync of the parent directory after the save so the new directory's name is durable too, and treat a step directory without .metadata as incomplete. This is our reading of the source and the trace, shown as states in the crash lab (pick the two DCP protocols); it is not a reported incident.


Asynchronous saves. dcp.async_save first stages the state (copies tensors to CPU memory), returns a future, and writes in the background, so training continues during the slow part. Here it blocked training for 66 ms of a 501 ms save. Two costs remain: a second copy of the state in host memory while it is written, and the writes still compete for the device and the dirty-page budget (section 4), so a step that runs during the background write can be slower.


Checkpoint checklist for a real job
    

  • One directory per step (step-000200/); each rank writes and fsyncs its own shard; barrier; one rank writes the metadata or a COMPLETE marker, fsyncs it, then fsyncs the step directory and its parent.
    • 

  • Keep the last two or three; delete older ones only after the new one is complete; on restart choose the newest complete one and fall back if loading fails.
    • 

  • Check free space and inodes first (shutil.disk_usage); handle OSError from write, fsync and close as "this checkpoint failed".
    • 

  • On object stores and FUSE mounts follow section 9: new keys, marker last.

torch.save with a file object, and CheckFreq (depth)


Given a file object instead of a path, torch.save writes into it and leaves flushing, syncing and renaming to you: that is how the safe protocol of section 6 wraps it. CheckFreq describes the same split as async_save, a quick in-memory "snapshot" and a background "persist", and chooses how often to checkpoint from measured costs ({{CheckFreq, FAST 2021|https://www.usenix.org/conference/fast21/presentation/mohan}}).








11. Data loading: the same mechanisms, applied


Mohan and colleagues measured nine models on production servers at Microsoft and found that "in many cases, DNN training time is dominated by data stall time: time spent waiting for data to be fetched and preprocessed" ({{Analyzing and Mitigating Data Stalls in DNN Training, VLDB 2021|https://arxiv.org/abs/2007.06775}}). The storage half of that is this page's mechanisms; dataset formats, sharding and loader prefetch are {{Storage and loading at scale|n:3f95c17b0d0d81398782efcb29d950d4}}'s.


    

  • Few big files, read sequentially: readahead (section 3) needs sequential access and every file pays metadata (section 2: 56x slower cold for small files here; far worse on a network file system). Hence tar shards, Arrow and Parquet files, and memory-mapped token arrays; shuffle the order of shards and within an in-memory buffer instead of reading random records.
    • 

  • Queue depth: one reader thread is queue depth 1 (section 1); workers, prefetching and asynchronous readers keep many requests in flight, which matters most on remote storage with long latencies.
    • 

  • The page cache is a free dataset cache while the dataset fits in memory: epoch 2 reads RAM. When the dataset is a little larger than memory, an LRU-like cache can evict each page just before it is needed again; the same paper reports this thrashing and proposes a cache that keeps a fixed subset instead. The page cache counts toward a container's memory limit ({{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}}).
    • 

  • Stage to local disk when the shared file system is slow or shared with many jobs: copy shards to local NVMe at start, then read locally.
    • 

  • Look before tuning: workers in state D with wait channel wait_on_page_bit_common or io_schedule wait for storage; high system time with many small read calls is the root's Debug lab case "High system time: millions of tiny reads"; iostat -x shows whether the device is busy.
