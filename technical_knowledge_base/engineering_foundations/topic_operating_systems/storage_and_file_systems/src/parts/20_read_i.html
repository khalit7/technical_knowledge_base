8. Direct and asynchronous I/O

The page cache is a bargain for data you read twice and for small writes, but a training job also streams data it reads once (a dataset bigger than RAM) and writes data it will not read back (a checkpoint). Copying that through the cache costs a memory copy per byte, evicts useful pages, and creates the dirty throttling of section 4. Two tools: skip the cache, and keep many requests in flight from one thread.

Where the bytes are copied on each path

Buffered I/O copies once by CPU into the page cache, and the device later moves it by DMA. O_DIRECT moves it by DMA between your (aligned) buffer and the device. GPUDirect Storage moves it between GPU memory and storage, with no bounce buffer through the CPU not run here. None of the three flushes the device's cache: durability still needs fdatasync.

O_DIRECT asks the kernel to move data by DMA straight between your buffer and the device ({{open(2), O_DIRECT|https://man7.org/linux/man-pages/man2/open.2.html}}). The price is alignment: the buffer address, the length and the file offset must be multiples of the device's logical block size (512 bytes here), or the call fails measured:



O_DIRECT is not durable. It skips the page cache, not the device's cache, and does not commit metadata such as a new file size. In the fio runs below, adding fdatasync after each direct 4 KiB write cut the rate from 12,706 to 6,270 writes per second.

The direct sequential numbers are far above any single NVMe drive's because macOS serves the VM's disk file from its own cache; read the relations (direct sequential at queue depth 8 beats buffered single-threaded writes; random 4 KiB costs the same either way when nothing is cached), not the absolute values.


When to use it. Checkpoint writers and data loaders that manage their own buffers use it to keep the page cache for what matters and make throughput predictable; GPUDirect Storage requires it. Not for small reads you will repeat (no caching, no readahead), nor from Python on unaligned bytes objects (use an aligned buffer, e.g. mmap.mmap(-1, n), which is page aligned).


Asynchronous I/O. A plain read blocks the thread, so one thread has one request in flight: queue depth 1 in section 1. libaio (io_submit, io_getevents) is truly asynchronous only with O_DIRECT. io_uring (Linux 5.1+) shares two ring buffers between program and kernel: the program writes submission entries and reads completion entries, often with no system call per I/O ({{io_uring(7)|https://man7.org/linux/man-pages/man7/io_uring.7.html}}); {{Concurrency|n:3f05c17b0d0d8112ad1af99308fa913f}} owns the ring design and the event loops built on it.
