9. Direct I/O and asynchronous I/O

ch. 36 I/O Devices (DMA)

The problem. The page cache is a bargain for data you read twice and for small writes, but a training job also streams data it reads once (a dataset bigger than RAM) and writes data it will not read back (a checkpoint). Copying that through the cache costs a memory copy per byte, evicts useful pages, and creates the dirty-page throttling of section 5.

O_DIRECT

Opening with O_DIRECT asks the kernel to move data by DMA straight between your buffer and the device, skipping the page cache ({{open(2), O_DIRECT|https://man7.org/linux/man-pages/man2/open.2.html}}). The price is alignment: the buffer address, the length and the file offset must be multiples of the device's logical block size (512 bytes here), or the call fails. measured



tmpfs has no device to DMA to, so on this kernel it refuses O_DIRECT at open. Linux 6.1 added STATX_DIOALIGN to statx to ask a file for its exact alignment rules ({{statx(2)|https://man7.org/linux/man-pages/man2/statx.2.html}}) not run here.


O_DIRECT is not durable. It skips the page cache, not the device's cache, and it does not commit metadata such as a new file size; you still need fdatasync. In the fio runs below, adding fdatasync after each direct 4 KiB write cut the rate from  to  writes per second.

When to use it in ML. Checkpoint writers and data loaders that manage their own buffers use it to keep the page cache for what matters and to make throughput predictable; GPUDirect Storage requires it (section 10). Do not use it for small reads you will repeat (you lose caching and readahead), or from Python on unaligned bytes objects (use an aligned buffer, e.g. mmap.mmap(-1, n), which is page aligned).


Asynchronous I/O: libaio and io_uring


A plain read blocks the thread until the data arrives, so a single thread only ever has one request in flight (queue depth 1, section 1). Two kernel interfaces let one thread keep many in flight. libaio (io_submit, io_getevents) is truly asynchronous only with O_DIRECT. io_uring (Linux 5.1+) shares two ring buffers between the program and the kernel: the program writes submission entries and reads completion entries, often with no system call per I/O ({{io_uring(7)|https://man7.org/linux/man-pages/man7/io_uring.7.html}}). The sibling page {{Concurrency|n:3f05c17b0d0d8112ad1af99308fa913f}} covers its design and the event loops built on it.
