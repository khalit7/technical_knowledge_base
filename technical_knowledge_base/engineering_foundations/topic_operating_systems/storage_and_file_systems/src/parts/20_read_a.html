The idea in one screen

Returned is not durable. write() and torch.save return once the bytes are in kernel memory, the page cache; the kernel moves them to the device later, in its own order and on its own schedule. What a crash can leave is decided only by fsync (of the file, and of its directory) and rename; what a read costs is decided by whether the page cache and readahead can serve it.

How far each call pushes one 4 KiB write before it returns

Rows are the layers your bytes cross, top to bottom (section numbers in brackets). Each column is one call: the solid bar is how far the data has got when the call returns, the dashed bar how far the file's metadata (size, block map, times) has got. Only what is below the red line survives a power cut. Medians of 1,000 overwrites of one 4 KiB record on ext4 measured; fsync needs a journal commit, fdatasync on an overwrite does not (section 5).

Page cache
kernel memory holding file pages; every buffered read and write goes through it.
Dirty page
a cached page changed in memory and not yet written to the device.
Writeback
the kernel writing dirty pages to the device, by age, by threshold, or because someone called fsync.
Device cache, FLUSH, FUA
the drive's own volatile memory; a flush or a Force Unit Access write is what pushes data past it.
Inode, extent
the per-file record (size, owner, where the data lives); an extent is one "start, length" run of blocks.
Journal (jbd2)
ext4's log: metadata changes are written there first and committed as transactions, so a crash replays or discards them whole.
Readahead
the kernel fetching the next pages of a file before a sequential reader asks.
O_DIRECT
an open flag that moves data between your buffer and the device without the page cache.
The page in six claims
  1. Returned is not durable. The 256 MiB checkpoint of section 10 left 256 MiB of dirty data in memory when torch.save returned (section 4).
  2. When the kernel writes is not a promise. The textbook says "within 30 seconds"; here the same 16 MiB stayed dirty anywhere from 2 to 32 seconds, depending on what else the machine was doing (section 4).
  3. The safe checkpoint is five calls: write to ckpt.pt.tmp, fsync it, rename it over ckpt.pt, fsync the directory; and never overwrite the last good checkpoint in place. It cost 365 ms against 263 ms for the plain save (section 6).
  4. Libraries differ. PyTorch's distributed checkpoint fsyncs every file but deletes the old .metadata before renaming the new one in, and never fsyncs the directory: save each step to a new directory (section 10).
  5. Sequential beats random, because the kernel reads ahead: 512 small reads of a cold file became 20 device requests (section 3). Shards, not millions of small files.
  6. If fsync fails, the data is gone: the kernel may already have dropped the dirty pages. Rewrite the checkpoint from memory; never retry the fsync and carry on (section 5).
How this page was measured (provenance)

Docker Desktop's Linux VM on an Apple M1 laptop (Linux 5.10.104-linuxkit, arm64, 5 CPUs, about 10 GB), October 2026, image kb-os-lab:1 (the root's lab image: fio 3.33, strace 6.1, e2fsprogs 1.47, PyTorch 2.14.1 CPU). Files were written to /data, an anonymous Docker volume: a directory on the VM's ext4 disk (data=ordered, commit=5, delayed allocation), with no overlay file system in between. Containers were not privileged. The disk is virtual: a virtio block device backed by a file on the laptop's SSD, which macOS caches, so device reads and flushes here are faster than on a real NVMe drive and cold reads are inflated; the ratios between methods carry over, the absolute numbers do not. Things that need privileges, a real crash, NVMe hardware, a network file system or a GPU are taught from primary sources and tagged not run here.
