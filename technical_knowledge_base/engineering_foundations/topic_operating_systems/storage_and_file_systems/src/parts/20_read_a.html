In one screen

When torch.save returns, your checkpoint is in memory, not on the disk. The kernel keeps file data in a cache (the page cache) and writes it to the device later, in its own order, on its own schedule. Everything on this page is about that gap: how data moves between your program, the cache and the device, what each system call promises about it, and how to write a checkpoint that a crash can never destroy.

The root page, {{Topic: operating-systems|n:3f05c17b0d0d81c5a97ce991644af140}} section 7, gave the intuition, animated one write's journey, and traced the running job's checkpoint (its {{Syscall tracer|n:3f05c17b0d0d81c5a97ce991644af140}} tab); its OS simulators tab crashes a block-level write with and without a journal. This page goes one level down: the kernel's code paths (Linux v5.10, the kernel these runs used, file and line), the exact guarantee of every call, new measurements, and the checkpoint libraries you actually use. Each mechanism follows one pattern: problem, how it works, what it costs here, when it bites in ML, the command that shows it, the fix.

Six things to remember
  1. Returned is not durable. The 256 MiB checkpoint below left MiB of dirty (not yet written) data in memory when torch.save returned (section 5).
  2. When the kernel writes it is not a promise. The textbook says "within 30 seconds"; here the same 16 MiB stayed dirty anywhere from to seconds, depending on what else the machine was doing (section 5).
  3. The safe checkpoint is five calls: write to ckpt.pt.tmp, fsync it, rename it over ckpt.pt, fsync the directory; and never overwrite the last good checkpoint in place. It cost ms against ms for the plain save (section 7, {{Crash lab|#t-crash}}).
  4. Libraries differ. PyTorch's distributed checkpoint fsyncs every file but deletes the old .metadata before renaming the new one in, and never fsyncs the directory: save each step to a new directory (section 11).
  5. Sequential beats random, because the kernel reads ahead: 512 small reads of a cold file became device requests (section 4). Shards, not millions of small files.
  6. If fsync fails, the data is gone: the kernel may already have dropped the dirty pages. Rewrite the checkpoint from memory; never retry the fsync and carry on (section 6).

How this page was measured: Docker Desktop's Linux VM on an Apple M1 laptop (Linux 5.10.104-linuxkit, arm64, 5 CPUs, about 10 GB), October 2026, image kb-os-lab:1 (the root's lab image: fio 3.33, strace 6.1, e2fsprogs 1.47, PyTorch 2.14.1 CPU). Files were written to /data, an anonymous Docker volume: a directory on the VM's ext4 disk (data=ordered, commit=5, delayed allocation), with no overlay file system in between. Containers were not privileged. The disk is virtual: a virtio block device backed by a file on the laptop's SSD, which macOS caches, so device reads and flushes here are faster than on a real NVMe drive and cold reads are inflated; the ratios between methods carry over, the absolute numbers do not. Things that need privileges, a real crash, NVMe hardware, a network file system or a GPU are taught from primary sources and tagged not run here.
