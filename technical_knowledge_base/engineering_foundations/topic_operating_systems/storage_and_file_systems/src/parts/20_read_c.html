3. File systems and the VFS: names, inodes and open files

ch. 39 Files and Directories, ch. 40 File System Implementation, ch. 41 Locality and FFS

The problem. A device is a flat array of blocks. Programs want named files in directories, permissions, sizes and times, and they want the same open, read, write to work on ext4, XFS, tmpfs, NFS or /proc. The kernel solves the second problem with the VFS (virtual file system switch): one set of objects and calls that every file system implements ({{kernel docs: VFS|https://docs.kernel.org/filesystems/vfs.html}}).

Four objects

superblockOne per mounted file system: its type, block size, and the operations to read and write inodes (struct super_block, include/linux/fs.h line 1416, v5.10).
inodeOne per file, whatever its names: type, permissions, owner, size, times, link count, and where its data lives (struct inode, fs.h line 610). It holds an address_space (line 451): that file's pages in the page cache.
dentryOne per name in a path, cached: "the name ckpt.pt in directory X is inode 13" (struct dentry, include/linux/dcache.h line 89). A negative dentry caches "this name does not exist".
fileOne per open(): the current offset, the open flags, and a pointer to the dentry and inode (struct file, fs.h line 916). File descriptors are indexes into a per-process table of these; the sibling page {{Processes and the system-call API|n:3f05c17b0d0d811e99f7cb8c15d12697}} section 7 draws the three tables.

Path lookup. open("/data/out/ckpt.pt") walks the path one component at a time, looking each name up in the dentry cache and asking the file system only on a miss (fs/namei.c). The root's Syscall tracer shows import torch making hundreds of newfstatat calls that fail with ENOENT: Python searching its path. Each failure leaves a negative dentry, so the second import is cheap.

Names are not files. A directory is itself a file whose content is a table of (name, inode number). A hard link is a second entry pointing at the same inode; a symbolic link is a small file containing a path. The inode counts its names (its link count) and is freed when that count is zero and no process has it open. So deleting a checkpoint that a running process still holds open frees no space until that process closes it or exits; lsof +L1 lists such deleted-but-open files.

Read it from the bottom of the stack up. The directory out is a table: ckpt.pt is inode 13, and hello.txt and hardlink.txt are both inode 14 (one file, Links: 2). Inode 13's data is one extent: logical blocks 0 to 732 stored in physical blocks 2066 to 2798, contiguous. That is 733 blocks of 4,096 bytes, the smallest number that holds 3,000,000 bytes (3,000,000 / 4,096 = 732.4), and Blockcount: 5864 counts the same space in 512-byte sectors (733 x 8). Old file systems (ext2, ext3) listed every block number; an extent says "start, length" once, which is why a large file costs ext4 almost no metadata. ext4 also groups inodes and their data into block groups so a file's inode sits near its data, the idea OSTEP ch. 41 credits to FFS. The journal (section 8) is itself an inode inside the file system, 4 MiB here.

Why. Every small file pays for a path lookup, an inode allocation, a directory entry, a journal transaction share and a separate block allocation; every cold read of one is at least one device request that readahead cannot merge with its neighbours (section 4). On a network or parallel file system each open and stat is also a round trip to a metadata server (section 10), so the gap grows from tens to thousands of times.
