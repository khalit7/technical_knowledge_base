Interview questions, with model answers

What does write() guarantee when it returns, and what does fsync() add?
write guarantees the bytes are in the kernel's page cache: visible to every process on this machine, but only in memory. fsync returns when the file's data and metadata have reached stable storage, including flushing the device's volatile cache. It does not cover the directory entry naming the file; that needs an fsync of the directory.
How do you replace a file atomically and durably on Linux?
Write the new contents to a temporary file in the same directory, fsync it, rename it over the target (atomic for readers: they see old or new), then fsync the directory so the rename survives a crash. Same directory, because rename is atomic only within one file system. Alternatives: O_TMPFILE plus linkat for new names, renameat2(RENAME_EXCHANGE) to swap.
fsync versus fdatasync: when is fdatasync cheaper?
fdatasync skips metadata not needed to read the data back, chiefly timestamps. When a write changes only data (an overwrite of allocated blocks), fdatasync needs no journal commit, only the data write and a cache flush; fsync still has to log the new mtime. When the write extends the file, the size must be persisted, so both need the journal. Measured here on an overwrite: about 0.39 ms against 1.3 ms.
Explain ext4's data=ordered mode and delayed allocation, and how they interact.
Ordered mode journals metadata only but writes a file's data blocks before committing the metadata that points to them, so metadata never points at stale blocks. Delayed allocation picks blocks only at writeback; until then there is nothing to order, so a commit can record a new file's name with no data yet, which after a crash gives an empty file. ext4's auto_da_alloc forces allocation on rename-over-existing and truncate-then-close to cover the common unsafe patterns, but the portable fix is fsync.
A program writes 10 GB quickly and then its writes become very slow without any errors. What is happening?
Dirty throttling: once dirty page-cache data passes the dirty limits (for the machine, or for the program's cgroup writeback domain), balance_dirty_pages pauses the writer so it cannot outrun the device. /proc/PID/wchan shows balance_dirty_pages; Dirty and Writeback in /proc/meminfo stay high. Fixes: accept device speed, write in a background thread, use dirty_bytes limits, start writeback early with sync_file_range, or O_DIRECT.
What is readahead and when does it not help?
When the kernel sees sequential reads, it fetches the following pages before they are requested, growing the window (4, 8, 16, 32 pages here) up to read_ahead_kb, and triggers the next window asynchronously from a marked page. It does nothing for random access, which is why random small reads cost one device request each and why datasets are stored as sequential shards.
Why can O_DIRECT be slower than buffered I/O, and does it make writes durable?
It removes caching and readahead, so small or repeated reads each go to the device, and it imposes alignment. It does not flush the device cache or commit metadata, so durability still needs fdatasync. It wins for large streaming transfers you will not reuse, and when you manage your own cache.
How would you checkpoint a 64-rank job to a shared file system so that a crash at any moment leaves a loadable checkpoint?
New directory per step; each rank writes and fsyncs its shard; barrier; one rank writes the metadata (or a COMPLETE marker) to a temporary name, fsyncs, renames, fsyncs the step directory and the parent; keep the previous complete checkpoint until then; on restart pick the newest directory that has the marker and loads. On an object store, the same with new keys and a marker object written last.
A dataset reads at 3 GB/s in your benchmark but 300 MB/s in the real job. What do you check?
Whether the benchmark hit the page cache (it ran twice, or the file was just written); whether the job's access pattern is random (no readahead) or small-file (metadata); the queue depth (worker count); whether the job's container has an io.max limit or a smaller memory limit (less cache); and whether workers sit in state D (ps -eo stat,wchan).
