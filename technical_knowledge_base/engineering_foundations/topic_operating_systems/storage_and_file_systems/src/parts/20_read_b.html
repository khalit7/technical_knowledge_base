1. Devices: what is actually at the bottom

ch. 36 I/O Devices, ch. 37 Hard Disk Drives, ch. 44 Flash-based SSDs

The problem. Memory (DRAM) loses its contents without power; a storage device keeps them. But devices are thousands of times slower than memory, they work in blocks, not bytes, and most of them have their own volatile cache. Everything the kernel does above them exists to hide these three facts, and every durability bug comes from forgetting one of them.

Three kinds of device

Hard disk (HDD)A spinning platter and a moving arm. A random read waits for the arm to move (seek) and the platter to turn (rotation): several milliseconds, so a few hundred random reads per second; sequential reads are fast because nothing moves. OSTEP ch. 37 works the numbers.
Flash SSDNo moving parts. Flash is read and written in pages (a few KiB) but can be erased only in much larger erase blocks, and a page cannot be rewritten before its block is erased. A flash translation layer (FTL) inside the drive therefore writes every update to a fresh page and remaps it, and garbage-collects old blocks in the background; the extra internal writes are write amplification. OSTEP ch. 44 lists typical times: read about 25 us, program (write) 200 to 300 us, erase 1.5 to 2 ms for SLC flash ({{OSTEP ch. 44|https://pages.cs.wisc.edu/~remzi/OSTEP/file-ssd.pdf}}).
NVMeThe interface modern SSDs speak over PCIe. The host and the drive share submission and completion queues in memory: the driver writes a command into a submission queue and rings a doorbell register; the drive fetches it by DMA, does the work, writes a completion entry and raises an interrupt. The specification allows up to 65,535 I/O queue pairs of up to 65,536 entries each ({{NVM Express base specification|https://nvmexpress.org/specifications/}}), so Linux can give each CPU its own queue and never take a shared lock. not run here

TRIM, or discard. When a file is deleted, the file system knows the blocks are free but the SSD does not, and its garbage collector keeps copying dead data. A discard (TRIM on SATA, Deallocate on NVMe) tells it. ext4 can send discards at every delete (mount option discard) or you run fstrim periodically. This VM mounts its disk nodiscard and runs a small service that calls /sbin/fstrim /var/lib/docker after deletes (seen in the VM's process list with docker run --pid host ... ps) measured.

The device's own cache, and why fsync must flush it

Most drives acknowledge a write as soon as it is in their internal DRAM cache. If power fails before the drive moves it to flash or platter, the write is lost even though the drive said "done". So the kernel has two extra tools ({{kernel docs: writeback cache control|https://docs.kernel.org/block/writeback_cache_control.html}}): a cache flush (the REQ_PREFLUSH flag: "flush the volatile cache before this I/O") and FUA, Force Unit Access (the REQ_FUA flag: "this write completes only once it is on stable storage"). A file system's fsync ends with one of them; that, not the write itself, is what makes data survive power loss. You can read what the kernel believes about your disk:



This disk reports a write-back cache and no FUA support, so the kernel emulates FUA with a write followed by a full cache flush. A drive that wrongly reports write through, or firmware that ignores flushes, silently breaks every guarantee on this page; this cannot be tested from software, only with power-cut tests.

2. The block layer: from a request to the device's queues


ch. 36 I/O Devices


The problem. Many processes and the file system issue reads and writes of all sizes; the device wants few, large, well-ordered requests spread across its queues. The block layer sits between them.


How it works. A file system describes an I/O as a bio: a direction, a starting sector and a list of memory pages (struct bio, include/linux/blk_types.h). Bios that touch neighbouring sectors are merged into a request. Since Linux 3.13 the layer is blk-mq, multi-queue: each CPU puts requests in its own software queue, which feeds one of the device's hardware queues, so CPUs do not contend on one lock ({{kernel docs: blk-mq|https://docs.kernel.org/block/blk-mq.html}}). A thread may also plug its queue while it submits a batch, so the batch is merged before it is sent. An optional I/O scheduler may reorder requests: none, mq-deadline (bounds how long a request waits), kyber (latency targets) or bfq (fair shares between processes). For fast NVMe drives none is the usual choice because reordering costs more than it saves.

When it bites in ML. Rarely directly: you seldom tune the block layer, but you read its counters. "The disk is at 100% util" on iostat while r/s keeps rising with more workers means the device still has room; a large r_await with a small aqu-sz means each request is slow (a remote or throttled device), not that you are queueing.


At queue depth 64, fio measured about 54,700 reads per second at a mean latency near 1.15 ms. What throughput does Little's law predict for 64 requests in flight at 1.15 ms each?




Throughput = requests in flight / latency = 64 / 0.0011526 s = about 55,500 per second, within 2% of what fio measured: the device was busy all the time, and each extra request in flight only waited longer. At queue depth 1 the same law gives 1 / 80 us = 12,500 per second; fio saw 10,741 because fio's own per-request work adds to the device's time.
