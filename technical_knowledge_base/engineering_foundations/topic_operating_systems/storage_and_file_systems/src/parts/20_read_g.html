7. Atomic replace: making a crash see old or new, never half

ch. 39 Files and Directories (rename), ch. 42 Crash Consistency

The problem. fsync makes data durable, but it does not make an update atomic: a crash in the middle of rewriting ckpt.pt leaves a file that is partly new, partly old or partly missing, and the previous good checkpoint is already destroyed. We need a way to switch from the old version to the new one in a single step.

The tools

rename"If newpath already exists, it will be atomically replaced, so that there is no point at which another process attempting to access newpath will find it missing" ({{rename(2)|https://man7.org/linux/man-pages/man2/rename.2.html}}). Atomic for readers now; durable only once the directory change is committed.
fsync of the directory"Calling fsync() does not necessarily ensure that the entry in the directory containing the file has also reached disk. For that an explicit fsync() on a file descriptor for the directory is also needed" ({{fsync(2)|https://man7.org/linux/man-pages/man2/fsync.2.html}}). Open the directory O_RDONLY and fsync that descriptor.
renameat2 flagsRENAME_NOREPLACE fails instead of overwriting (two writers cannot clobber each other); RENAME_EXCHANGE swaps two names atomically ({{rename(2)|https://man7.org/linux/man-pages/man2/rename.2.html}}).
O_TMPFILE + linkatCreate a file with no name at all, write and fsync it, then give it a name with linkat: it can never be seen half-written, and a crash leaves no .tmp litter ({{open(2), O_TMPFILE|https://man7.org/linux/man-pages/man2/open.2.html}}). linkat will not replace an existing name, so it suits "write once" files such as shards.

The protocol, as the kernel sees it

measured The running job's checkpoint written two ways, under strace -f -y, keeping only calls on the checkpoint directory (shown as DIR) between the phase markers, with runs of writes folded into one line:

torch.save(obj, "ckpt.pt")


tmp, fsync, rename, fsync the directory




The plain save opens the existing ckpt.pt with O_TRUNC: the old checkpoint's contents are thrown away at the first system call, and the new contents exist only in the page cache until writeback. The safe version never touches ckpt.pt until a complete, durable new file exists; renameat is the single switch; the directory fsync makes the switch itself durable. The {{Crash lab|#t-crash}} tab takes these exact call sequences (and two more) and shows, crash point by crash point, what a restarted job could find.


What ALICE found, and what ext4 does to help


Pillai and colleagues recorded the system calls of eleven widely used systems ("databases, key-value stores, version control systems, distributed systems, and virtualization software") and computed every state a crash could leave under the guarantees file systems actually give. They found "a total of 60 vulnerabilities, many of which lead to severe consequences" ({{All File Systems Are Not Created Equal, OSDI 2014|https://www.usenix.org/conference/osdi14/technical-sessions/presentation/pillai}}). They also showed the answer depends on the file system and its mount options: code that is safe on one can corrupt on another.


source ext4 carries a heuristic for the most common unsafe pattern, born from the 2009 zero-length-files story in the root's section 7: with the default auto_da_alloc mount option (this VM has it), renaming a file over an existing one makes ext4 allocate and start writing the source file's delayed data first (fs/ext4/namei.c lines 3782 to 3783, ext4_alloc_da_blocks), and closing a file that had been truncated to zero does the same (fs/ext4/file.c lines 140 to 143). With data=ordered, the commit that records the rename then waits for that data. So on ext4, write-then-rename without fsync usually ends with old or new rather than an empty file; but the rename is still not durable until the next commit, the heuristic exists only on ext4, and the ext4 documentation introduces it as help for "broken applications" that replace files without fsync(), providing "roughly the same level of guarantees as ext3" ({{ext4 docs, auto_da_alloc|https://docs.kernel.org/admin-guide/ext4.html}}). Write the fsyncs.


The checkpoint rules


    

  1. Write to a new name (ckpt.pt.tmp, or a new step_000200/ directory). Never open the last good checkpoint for writing.
    2. 

  2. flush() Python's buffer, then os.fsync(f.fileno()) every file you wrote.
    3. 

  3. os.replace(tmp, final) (a rename), or for a directory of shards, write a small "complete" marker last.
    4. 

  4. os.fsync a descriptor of the directory that holds the name you changed.
    5. 

  5. Keep the previous checkpoint (two or three) until the new one is durable, and on restart verify before trusting: load the newest, fall back to the previous one if it fails.
    6. 

  6. If any fsync, write or close fails, treat that checkpoint as lost and write it again.

A job runs torch.save(state, "ckpt.pt.tmp"); os.replace("ckpt.pt.tmp", "ckpt.pt") with no fsync at all, on ext4 with default options. The machine loses power 2 seconds later. What can the restarted job find at ckpt.pt?




The rename is in a journal transaction that commits every 5 s (commit=5), so after 2 s it may not be on disk yet: the old checkpoint is still there. If it did commit, auto_da_alloc made ext4 push the new data out first, so the new file is complete. On XFS, btrfs or a network file system, or with noauto_da_alloc, the empty-file outcome is back. The {{Crash lab|#t-crash}} shows both models.
