6. Atomic replace: a crash sees old or new, never half

fsync makes data durable, not an update atomic: a crash in the middle of rewriting ckpt.pt leaves a file that is partly new, partly old or partly missing, and the previous good checkpoint is already destroyed. The fix is to build the new version under another name and switch in one step. rename: "If newpath already exists, it will be atomically replaced, so that there is no point at which another process attempting to access newpath will find it missing" ({{rename(2)|https://man7.org/linux/man-pages/man2/rename.2.html}}). Atomic for readers now; durable only once the directory change is committed, which is what an fsync of the directory forces: "Calling fsync() does not necessarily ensure that the entry in the directory containing the file has also reached disk. For that an explicit fsync() on a file descriptor for the directory is also needed" ({{fsync(2)|https://man7.org/linux/man-pages/man2/fsync.2.html}}).

Every crash point at once, and the two models exactly (depth)






POSIX only. Durable: a file's data and its own metadata after an fsync of that file returns ({{fsync(2)|https://man7.org/linux/man-pages/man2/fsync.2.html}}); a directory's entries (create, rename, unlink, mkdir) after an fsync of that directory. Everything else may or may not have reached the disk, independently (each name change is atomic in itself, {{rename(2)|https://man7.org/linux/man-pages/man2/rename.2.html}}). File data not yet synced may be absent, cut short, fully there, or (for a file rewritten in place without truncation persisting) a mix of old and new.


ext4 as configured here. Name and size changes go through one journal and reach the disk in order, so after a crash some prefix of them is there. An fsync of anything commits the whole running transaction, so every earlier name change is durable after it (fs/ext4/fsync.c, ext4_fsync_journal). File data is written by writeback or fsync; with delayed allocation, a file whose data was not yet written has size 0 or a shorter size after a crash, never garbage (data=ordered). auto_da_alloc: renaming over an existing file, or closing a file that was truncated, starts writing its data, and the commit that records a later name change waits for it (fs/ext4/namei.c lines 3782 to 3783, fs/ext4/file.c lines 140 to 143, {{ext4 docs|https://docs.kernel.org/admin-guide/ext4.html}}).


Simplifications: the crash happens at some moment after the listed step and before the next; device caches honour flushes; one writer; a DCP checkpoint "loads" if its .metadata and shard come from the same save.






The checkpoint rules


    

  1. Write to a new name (ckpt.pt.tmp, or a new step_000200/ directory). Never open the last good checkpoint for writing.
    2. 

  2. flush() Python's buffer, then os.fsync(f.fileno()) every file you wrote.
    3. 

  3. os.replace(tmp, final) (a rename), or for a directory of shards, write a small "complete" marker last.
    4. 

  4. os.fsync a descriptor of the directory that holds the name you changed (open it O_RDONLY).
    5. 

  5. Keep the previous checkpoint (two or three) until the new one is durable, and on restart verify before trusting: load the newest, fall back to the previous one if it fails.
    6. 

  6. If any fsync, write or close fails, treat that checkpoint as lost and write it again.
    7.

The rename is in a journal transaction that commits every 5 s (commit=5), so after 2 s it may not be on disk yet: the old checkpoint is still there. If it did commit, auto_da_alloc made ext4 push the new data out first, so the new file is complete. On XFS, btrfs or a network file system, or with noauto_da_alloc, the empty-file outcome is back. The crash lab above shows both models.


What ALICE found, ext4's auto_da_alloc heuristic, and two more tools (depth)


Pillai and colleagues recorded the system calls of eleven widely used systems ("databases, key-value stores, version control systems, distributed systems, and virtualization software") and computed every state a crash could leave under the guarantees file systems actually give. They found "a total of 60 vulnerabilities, many of which lead to severe consequences" ({{All File Systems Are Not Created Equal, OSDI 2014|https://www.usenix.org/conference/osdi14/technical-sessions/presentation/pillai}}). The answer depends on the file system and its mount options: code that is safe on one can corrupt on another.


source ext4 carries a heuristic for the most common unsafe pattern, born from the 2009 zero-length-files story in the root's section 7: with the default auto_da_alloc mount option (this VM has it), renaming a file over an existing one makes ext4 allocate and start writing the source file's delayed data first (fs/ext4/namei.c lines 3782 to 3783, ext4_alloc_da_blocks), and closing a file that had been truncated to zero does the same (fs/ext4/file.c lines 140 to 143). With data=ordered, the commit that records the rename then waits for that data. So on ext4, write-then-rename without fsync usually ends with old or new rather than an empty file; but the rename is still not durable until the next commit, the heuristic exists only on ext4, and the ext4 documentation introduces it as help for "broken applications" that replace files without fsync(), providing "roughly the same level of guarantees as ext3" ({{ext4 docs, auto_da_alloc|https://docs.kernel.org/admin-guide/ext4.html}}). Write the fsyncs.


renameat2 flags. RENAME_NOREPLACE fails instead of overwriting (two writers cannot clobber each other); RENAME_EXCHANGE swaps two names atomically ({{rename(2)|https://man7.org/linux/man-pages/man2/rename.2.html}}). Rename is atomic only within one file system, so the temporary file goes in the same directory.


O_TMPFILE + linkat. Create a file with no name at all, write and fsync it, then give it a name with linkat: it can never be seen half-written, and a crash leaves no .tmp litter ({{open(2), O_TMPFILE|https://man7.org/linux/man-pages/man2/open.2.html}}). linkat will not replace an existing name, so it suits "write once" files such as shards.
