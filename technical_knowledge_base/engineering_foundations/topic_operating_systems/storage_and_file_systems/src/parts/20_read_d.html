3. Reading: the page cache and readahead

A device request has a large fixed cost; programs often read 4 KiB at a time, and often read the same file again (every epoch). Two answers: keep what was read in memory, the page cache, and when a program reads sequentially, fetch the next pages before it asks, readahead. How the page cache competes for memory and is reclaimed is {{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}}'s; this section is how data gets into it.

measured A cold 8 MiB file read 4 KiB at a time; after every read() the script read the container's io.stat, so each device request and its size is visible. Predict first: with a 128 KiB (32-page) maximum window, how many device requests do 512 sequential 4 KiB reads cost? Then watch Fig. 2.

  1. A cold file. It was just evicted from the page cache with posix_fadvise(DONTNEED): nothing is cached. The maximum window is 32 pages (128 KiB).
  2. read() 1 misses: a synchronous readahead of 4 pages. get_init_ra_size(1) = 4: pages 0 to 3 in one request, the program waits for it. Page 1 carries the readahead mark.
  3. read() 2 hits the mark: 8 pages, fetched ahead. The next window (pages 4 to 11) is requested asynchronously while the program keeps reading pages already in memory.
  4. Reads 3 to 5: the window doubles to 16 pages. Reading page 4, the first page of the last window, fetches pages 12 to 27.
  5. Reads 6 to 13: 32 pages, the maximum. Page 12 triggers pages 28 to 59; from now on every window is 32 pages.
  6. Reads 14 to 29: one window ahead, always. Page 28 triggers pages 60 to 91. Most reads are memory copies; the device works ahead of the program.
  7. Reads 30 to 128: steady state. Windows of 32 pages at reads 61, 93 and 125: 128 reads cost 8 device requests (188 pages).
  8. The whole run: 512 reads, 20 requests. 572 pages fetched; with POSIX_FADV_SEQUENTIAL the window doubles to 64 pages and the same reads cost 13 requests. With readahead off, or at random offsets, every read is its own request: 64 reads, 64 requests.

Fig. 2: sequential reads cost few requests because each window is fetched one window ahead. Page 0 is front left, 16 pages to a row. Blue tiles are pages in the page cache, orange the windows fetched in the current step (streaming up from the device in front), dashed outlines pages not yet read; the dark glow is the page the latest read() asked for. Measured: 512 sequential reads cost 20 requests (572 pages) by default and 13 requests (636 pages) with POSIX_FADV_SEQUENTIAL; readahead off and random offsets cost one request per read. Defaults reproduce the measurement independently: the two source rules below predict every request of both sequential runs. Times are this VM's: the "device" is macOS's cache of the disk file.

With readahead on, the window grew 4, 8, 16, 32 pages and then stayed at the 32-page maximum, each requested one window ahead of the reader, so most reads never waited for the device. With readahead off the same reads cost one request each. Random reads get no readahead: the kernel only predicts sequential access, and the measured random case fetched exactly one page per read.

The rule, from mm/readahead.c source (v5.10). First window, get_init_ra_size (line 311): round the request up to a power of two, then x4 if it is at most 1/32 of the maximum, x2 if at most 1/4, else the maximum. Each later window, get_next_ra_size (line 329): x4 while under 1/16 of the maximum, then x2, capped at the maximum. The maximum is read_ahead_kb (128 KiB here, 32 pages); posix_fadvise(POSIX_FADV_SEQUENTIAL) doubles it for that open file (mm/fadvise.c line 92) and POSIX_FADV_RANDOM turns readahead off (line 88).

A DataLoader reads samples at random offsets from one big uncompressed file of fixed-size records, 4 KiB each, cold. How many device requests do 1,000 samples cost, roughly?
About one per sample: readahead only triggers on sequential patterns, as the measured random case shows (64 random reads, 64 requests). Throughput then depends on queue depth, so more workers help; reading in a shuffled order of large shards (shuffle shards, then shuffle within a buffer) turns it back into sequential reads.
Cold and warm, and the honest caveat

The root's Debug lab case "The first epoch is slower than the rest: cold and warm page cache" measured a 512 MiB shard at 858 MiB/s cold against 3,831 MiB/s warm, and readahead off at 16,384 requests for 64 MiB against 516 with it on. On this VM "cold" still means "in macOS's cache of the virtual disk file": on a real local NVMe drive the cold number would be lower, and on a network file system much lower. Here the cold small-files read of section 2 was 56 times slower than reading the same 40 MiB as one file.

The read path in the source, and the knobs (depth)

source read(fd, buf, 4096) reaches ext4's ext4_file_read_iter, which calls the generic generic_file_buffered_read (mm/filemap.c line 2185, v5.10). For each page of the request it looks the page up in the file's address_space. A hit is a memory copy. A miss calls page_cache_sync_readahead (line 2235), which decides how much to fetch, allocates the pages, builds bios and submits them; the reader then sleeps until its page is unlocked. That sleep is the D state with wait channel wait_on_page_bit_common that the root's Debug lab case "Slow storage: workers sleep in D state on page faults" caught on a throttled disk. A page that carries the PG_readahead mark triggers page_cache_async_readahead (line 2247): the next window is fetched while the program is still reading the current one.

Commands and knobs
  • Per device: cat /sys/block/DEV/queue/read_ahead_kb, change with blockdev --setra SECTORS /dev/DEV (root; network file systems have their own, e.g. NFS's read_ahead_kb under /sys/class/bdi/).
  • Per open file: posix_fadvise(fd, 0, 0, POSIX_FADV_SEQUENTIAL | RANDOM | WILLNEED | DONTNEED), from Python os.posix_fadvise ({{posix_fadvise(2)|https://man7.org/linux/man-pages/man2/posix_fadvise.2.html}}); WILLNEED starts reading a range now; DONTNEED drops a file's clean pages (how this page made files cold without root).
  • For a mapping: madvise(MADV_SEQUENTIAL | MADV_RANDOM | MADV_WILLNEED); {{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}} measured random rows through mmap fetching 13x more than they used, and MADV_RANDOM cutting it to 3.4x.
  • How much of a file is cached: fincore file (util-linux); whole system: free -m (buff/cache), grep -E "^(Cached|Dirty|Writeback):" /proc/meminfo; your container: grep -E "^file " /sys/fs/cgroup/memory.stat.
