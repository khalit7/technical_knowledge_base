4. Reading: the page cache and readahead

ch. 40 File System Implementation (caching and buffering)

The problem. A device request has a large fixed cost; a program often reads a file 4 KiB at a time, and often reads the same file again (every epoch). Two answers: keep what was read in memory, the page cache, and when a program reads sequentially, fetch the next pages before it asks, readahead. The sibling page {{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}} section 6 covers how the page cache competes for memory and is reclaimed; this section is about how data gets into it.

The read path, in the source

source read(fd, buf, 4096) reaches ext4's ext4_file_read_iter, which calls the generic generic_file_buffered_read (mm/filemap.c line 2185, v5.10). For each page of the request it looks the page up in the file's address_space. A hit is a memory copy. A miss calls page_cache_sync_readahead (line 2235), which decides how much to fetch, allocates the pages, builds bios and submits them; the reader then sleeps until its page is unlocked. That sleep is the D state with wait channel wait_on_page_bit_common that the root's Debug lab case "Slow storage: workers sleep in D state on page faults" caught on a throttled disk. A page that carries the PG_readahead mark triggers page_cache_async_readahead (line 2247): the next window is fetched while the program is still reading the current one.

The readahead window, from the source and on the device

source mm/readahead.c (v5.10) sizes the first window with get_init_ra_size (line 311): round the request up to a power of two, then multiply by 4 if it is at most 1/32 of the maximum, by 2 if at most 1/4, else use the maximum. Each later window comes from get_next_ra_size (line 329): 4 times the previous one while it is under 1/16 of the maximum, then 2 times, capped at the maximum. The maximum is read_ahead_kb (128 KiB here, 32 pages); posix_fadvise(POSIX_FADV_SEQUENTIAL) doubles it for that open file (mm/fadvise.c line 92) and POSIX_FADV_RANDOM turns readahead off (line 88).

measured A cold 8 MiB file read 4 KiB at a time; after every read() the script looked at the container's io.stat, so each device request and its size is visible. The animation replays the measured requests; the sizes predicted from the two source rules are drawn as outlines.

Read the two before/after cases together. With readahead on, the window grew 4, 8, 16, 32 pages and then stayed at the 32-page maximum, and each window was requested one window ahead of the reader (the marker page), so most reads never waited for the device. With readahead off the same reads cost one device request each. Random reads get no readahead at all: the kernel only predicts sequential access, and the measured random case fetched exactly one page per read.

Cold and warm, and the honest caveat

The root's Debug lab case "The first epoch is slower than the rest: cold and warm page cache" measured a 512 MiB shard at 858 MiB/s cold against 3,831 MiB/s warm, and readahead off at 16,384 requests for 64 MiB against 516 with it on. On this VM, "cold" still means "in macOS's cache of the virtual disk file": on a real local NVMe drive the cold number would be lower, and on a network file system much lower. Commands and knobs
  • Per device: cat /sys/block/DEV/queue/read_ahead_kb, change with blockdev --setra SECTORS /dev/DEV (root; network file systems have their own, e.g. NFS's read_ahead_kb under /sys/class/bdi/).
  • Per open file: posix_fadvise(fd, 0, 0, POSIX_FADV_SEQUENTIAL | RANDOM | WILLNEED | DONTNEED), from Python os.posix_fadvise ({{posix_fadvise(2)|https://man7.org/linux/man-pages/man2/posix_fadvise.2.html}}); WILLNEED starts reading a range now; DONTNEED drops a file's clean pages (how this page made files cold without root).
  • For a mapping: madvise(MADV_SEQUENTIAL | MADV_RANDOM | MADV_WILLNEED); the sibling {{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}} section 5 measured random rows through mmap fetching 13x more than they used, and MADV_RANDOM cutting it to 3.4x.
  • How much of a file is cached: fincore file (util-linux); whole system: free -m (buff/cache), grep -E "^(Cached|Dirty|Writeback):" /proc/meminfo; your container: grep -E "^file " /sys/fs/cgroup/memory.stat.
A DataLoader reads samples at random offsets from one big uncompressed file of fixed-size records, 4 KiB each, cold. How many device requests do 1,000 samples cost, roughly?
About one per sample: readahead only triggers on sequential patterns, as the measured random case shows (64 random reads, 64 requests). Throughput then depends on queue depth, so more workers help; reading in a shuffled order of large shards (shuffle shards, then shuffle within a buffer) turns it back into sequential reads.
