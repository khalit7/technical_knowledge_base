5. Durability: fsync, fdatasync, and when fsync fails

A checkpoint, a database log or a "this checkpoint is complete" marker must survive a crash, so the program needs a call that returns only when the data is on stable storage, and it must know exactly what that call covers. fsync(fd) covers the file's data and all its metadata, then a device cache flush ("This includes writing through or flushing a disk cache if present", {{fsync(2)|https://man7.org/linux/man-pages/man2/fsync.2.html}}); not the directory entry that names the file. fdatasync(fd) covers the data plus only the metadata "needed in order to allow a subsequent data retrieval to be correctly handled": size and block map yes, modification time no. sync_file_range only starts or waits for writeback of a byte range; the kernel's own comment: "there are no guarantees here that the data will be available on disk after a crash" (fs/sync.c lines 351 to 355, v5.10).

source ext4_sync_file (fs/ext4/fsync.c line 129, v5.10) does three things in order: write the file's dirty pages and wait; wait for the journal transaction that last changed what this call covers; flush the device cache. Step through one 4 KiB overwrite under each call, then compare the measured costs below.

fsync pays for a journal commit that fdatasync skips on an overwrite; sync_file_range never reaches the media
What each call costs per 4 KiB record measured

1,000 records each; median and 99th percentile in microseconds. "Append" grows the file (size changes every time); "overwrite" rewrites a preallocated, already-synced file (only data and times change). tmpfs keeps files only in memory, so it has nothing to flush.

Log scale. On an overwrite, fdatasync cost 3.3x less than fsync (393 against 1,305 us); on an append only 1.3x less (997 against 1,265 us). sync_file_range is cheaper because it flushes nothing and commits nothing: it is not a durability call. On tmpfs every call costs about a microsecond.

On an overwrite, fdatasync cost about a third of fsync here. Why, given that both wrote the same 4 KiB?
An overwrite changes no size and no block map, only the data and the inode's times. fdatasync's required metadata is unchanged, so it writes the page and flushes; fsync must also log the time change in a journal transaction and wait for its commit, which is a second ordered write and flush. On append the size changes, so fdatasync needs the journal too and costs nearly as much as fsync: preallocating a log file (fallocate) and overwriting it is how databases make fdatasync cheap.

When fsync fails

A device error during writeback is reported to the next fsync. Before Linux 4.13 the error could reach one caller only and the failed pages were marked clean, so a second fsync returned success with the data lost: the PostgreSQL "fsyncgate" story in the root's section 7. Since 4.13 the kernel records writeback errors in an errseq_t, a counter plus error code that "allow[s] any number of 'subscribers' to tell whether it has changed since a previous point where it was sampled" (lib/errseq.c lines 8 to 10, v5.10), so every file descriptor open at the time sees the error once ({{LWN, Improved block-layer error handling|https://lwn.net/Articles/724307/}}). The pages may still be gone.

The error now reaches everyone, but the data is still lost

Two descriptors on one file: A (the checkpoint writer) and B (another process, say a log shipper). Sequence from the LWN article and lib/errseq.c; simplified to one page.

The rule: a failed fsync means that file's recent writes are lost; rewrite it from memory, or abort. With delayed allocation, running out of space can also surface only at fsync or close rather than at write, so check both: Python's f.close() raises OSError if the underlying close fails.

  • Count the calls: strace -f -e trace=fsync,fdatasync,sync_file_range,rename,renameat -p PID, or strace -c for totals.
  • Never retry a failed fsync and continue. Save the checkpoint again to a new file.
