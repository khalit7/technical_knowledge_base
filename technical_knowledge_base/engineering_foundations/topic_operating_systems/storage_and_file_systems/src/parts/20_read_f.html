5. Durability: fsync, fdatasync, and when fsync fails

A checkpoint, a database log or a "this checkpoint is complete" marker must survive a crash, so the program needs a call that returns only when the data is on stable storage, and it must know exactly what that call covers. fsync(fd) covers the file's data and all its metadata, then a device cache flush ("This includes writing through or flushing a disk cache if present", {{fsync(2)|https://man7.org/linux/man-pages/man2/fsync.2.html}}); not the directory entry that names the file. fdatasync(fd) covers the data plus only the metadata "needed in order to allow a subsequent data retrieval to be correctly handled": size and block map yes, modification time no. sync_file_range only starts or waits for writeback of a byte range; the kernel's own comment: "there are no guarantees here that the data will be available on disk after a crash" (fs/sync.c lines 351 to 355, v5.10).

source ext4_sync_file (fs/ext4/fsync.c line 129, v5.10) does three things in order: write the file's dirty pages and wait; wait for the journal transaction that last changed what this call covers; flush the device cache. Fig. 4 follows one 4 KiB overwrite through each call; pick a call, then compare the measured costs.

  1. pwrite() of 4 KiB. The call starts in your program with the 4 KiB record.
  2. pwrite() returns: 1.4 us. The bytes are copied into the cached page, which is marked dirty; the inode's new modification time joins the running journal transaction, in memory.
  3. Write the page and wait. file_write_and_wait_range (called from ext4_sync_file): the dirty page becomes a bio and goes through blk-mq to the driver.
  4. The device acknowledges. It reports the write complete as soon as it is in its volatile cache (write_cache: write back). A power cut now still loses it.
  5. Commit the journal transaction. ext4_fsync_journal (line 104): this inode last changed in the running transaction (i_sync_tid), so jbd2 must commit it: journal blocks, then the commit block.
  6. Commit block with PREFLUSH and FUA. jbd2 writes the commit block with REQ_PREFLUSH | REQ_FUA (fs/jbd2/commit.c line 157): the device flushes its cache, so the data page and the journal reach stable media.
  7. fsync returns: 1,305 us. Data and all metadata are durable.
  1. pwrite() of 4 KiB. As for fsync.
  2. pwrite() returns. The page is dirty; the mtime change is in the running transaction.
  3. Write the page and wait. The same first step as fsync.
  4. The device acknowledges from its volatile cache.
  5. No commit needed. For fdatasync the journal wait uses i_datasync_tid (line 109): an overwrite changed nothing data retrieval needs (size and block map unchanged), and that transaction committed long ago, so there is nothing to wait for. The mtime change stays in the running transaction.
  6. blkdev_issue_flush. needs_barrier is set, so ext4_sync_file sends a cache flush (line 177): the data page reaches stable media.
  7. fdatasync returns: 393 us. The data is durable; the new mtime will be committed within about 5 s by the journal timer. Losing that on a crash is harmless.
  1. pwrite() of 4 KiB. As for fsync.
  2. pwrite() returns. The page is dirty.
  3. Write the page and wait. SYNC_FILE_RANGE_WRITE starts writeback of the range.
  4. The device acknowledges from its volatile cache.
  5. sync_file_range returns: 161 us. WAIT_BEFORE | WRITE | WAIT_AFTER waited for writeback only: no journal commit, no cache flush. The kernel's own comment says there are "no guarantees here that the data will be available on disk after a crash" (fs/sync.c line 355).

Fig. 4: fsync pays for a journal commit that fdatasync skips on an overwrite; sync_file_range never reaches the media. Orange is the data page, purple the inode change; only what reaches the bottom block survives a power cut. Order from fs/ext4/fsync.c (v5.10), whole-call times measured.

On an overwrite, fdatasync cost about a third of fsync here. Why, given that both wrote the same 4 KiB?
An overwrite changes no size and no block map, only the data and the inode's times. fdatasync's required metadata is unchanged, so it writes the page and flushes; fsync must also log the time change in a journal transaction and wait for its commit, which is a second ordered write and flush. On append the size changes, so fdatasync needs the journal too and costs nearly as much as fsync: preallocating a log file (fallocate) and overwriting it is how databases make fdatasync cheap.
What each call costs per 4 KiB record measured

1,000 records each; median and 99th percentile in microseconds. "Append" grows the file (size changes every time); "overwrite" rewrites a preallocated, already-synced file (only data and times change). tmpfs keeps files only in memory, so it has nothing to flush.

Log scale. On an overwrite, fdatasync cost 3.3x less than fsync (393 against 1,305 us); on an append only 1.3x less (997 against 1,265 us). sync_file_range is cheaper because it flushes nothing and commits nothing: it is not a durability call. On tmpfs every call costs about a microsecond.

When fsync fails

A device error during writeback is reported to the next fsync. Before Linux 4.13 the error could reach one caller only and the failed pages were marked clean, so a second fsync returned success with the data lost: the PostgreSQL "fsyncgate" story in the root's section 7. Since 4.13 the kernel records writeback errors in an errseq_t, a counter plus error code that "allow[s] any number of 'subscribers' to tell whether it has changed since a previous point where it was sampled" (lib/errseq.c lines 8 to 10, v5.10), so every file descriptor open at the time sees the error once ({{LWN, Improved block-layer error handling|https://lwn.net/Articles/724307/}}). The pages may still be gone.

  1. write() on A returns. The new checkpoint bytes are only in the page cache, dirty. No error is recorded.
  2. Writeback fails: the device returns EIO. The failed page is marked clean (so nothing will try to write it again, and it may be dropped), and an error flag (AS_EIO) is set on the file's mapping.
  3. B calls fsync first. B gets EIO. The flag is now cleared.
  4. A calls fsync. A, the writer that cares, gets 0: success. It believes the checkpoint is durable. This is the fsyncgate failure PostgreSQL hit.
  5. A calls fsync again. 0 again: retrying fsync cannot bring the bytes back, and does not even report the loss.
  1. write() on A returns. Each open file descriptor remembers the errseq_t value it last saw: A and B both sampled counter 0 at open.
  2. Writeback fails: the device returns EIO. The write failed and the page may be dropped; the error is recorded once in the mapping, with a counter (now 1, EIO).
  3. B calls fsync first. B sees that the counter moved since its sample: EIO; B's sample moves to 1.
  4. A calls fsync. A sees it too: EIO. Every descriptor open at the time gets the error once, so A knows to rewrite from memory.
  5. A calls fsync again. Nothing new since A's sample: 0. A retry looks like success; the data is still gone. Rewrite the checkpoint; do not retry the fsync and carry on.

The rule: a failed fsync means that file's recent writes are lost; rewrite it from memory, or abort. With delayed allocation, running out of space can also surface only at fsync or close rather than at write, so check both: Python's f.close() raises OSError if the underlying close fails.
