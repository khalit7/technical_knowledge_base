6. Durability: fsync and its relatives

ch. 39 Files and Directories, ch. 45 Data Integrity and Protection

The problem. Some data must survive a crash: a checkpoint, a database log, the "this checkpoint is complete" marker. The program needs a call that returns only when the data is on stable storage, and it needs to know exactly what that call covers.

The family, and what each one promises

CallCoversSource
fsync(fd)all of the file's dirty data and all its metadata, then a device cache flush. "This includes writing through or flushing a disk cache if present." Not the directory entry that names the file.{{fsync(2)|https://man7.org/linux/man-pages/man2/fsync.2.html}}
fdatasync(fd)the data, plus only the metadata "needed in order to allow a subsequent data retrieval to be correctly handled": the size and block map yes, the modification time no{{fsync(2)|https://man7.org/linux/man-pages/man2/fsync.2.html}}
open(..., O_DSYNC) / O_SYNCevery write() behaves as if followed by fdatasync / fsync{{open(2)|https://man7.org/linux/man-pages/man2/open.2.html}}
sync_file_range(fd, off, n, flags)starts and/or waits for writeback of a byte range; no metadata, no cache flush. The kernel's own comment: "there are no guarantees here that the data will be available on disk after a crash"fs/sync.c lines 351 to 355 (v5.10)
syncfs(fd), sync()everything dirty on one file system, or on all of them; heavy, and in a shared machine you wait for other people's data too{{sync(2)|https://man7.org/linux/man-pages/man2/sync.2.html}}

Inside ext4's fsync

source ext4_sync_file (fs/ext4/fsync.c line 129, v5.10) does three things in order. (1) file_write_and_wait_range: write the file's dirty pages and wait for them. (2) ext4_fsync_journal (line 104): wait until the journal transaction that last changed this inode has committed; for fdatasync it waits only for the transaction that last changed what data retrieval needs (i_datasync_tid against i_sync_tid, line 109), and if that already committed there is nothing to wait for. The wait goes through ext4_fc_commit (line 115), which is a full journal commit unless the newer "fast commit" feature was enabled when the file system was created (a feature flag that needs privileges to read on this VM). (3) If needed, blkdev_issue_flush (line 177): the device cache flush of section 1. The animation runs one 4 KiB overwrite of a preallocated file through three calls, with this VM's measured median times.

What each call costs per 4 KiB record measured

1,000 records each; median and 99th percentile in microseconds. "Append" grows the file (size changes every time); "overwrite" rewrites a preallocated, already-synced file (only data and times change). tmpfs keeps files only in memory, so it has nothing to flush.

On an overwrite, fdatasync cost about a third of fsync here. Why, given that both wrote the same 4 KiB?
An overwrite changes no size and no block map, only the data and the inode's times. fdatasync's required metadata is unchanged, so it writes the page and flushes; fsync must also log the time change in a journal transaction and wait for its commit, which is a second ordered write and flush. On append the size changes, so fdatasync needs the journal too and costs nearly as much as fsync: preallocating a log file (fallocate) and overwriting it is how databases make fdatasync cheap.

When fsync fails

A device error during writeback is reported to the next fsync. Before Linux 4.13 the error could be reported to one caller only and the failed pages were marked clean, so a second fsync returned success with the data lost: the PostgreSQL "fsyncgate" story in the root's section 7. Since 4.13 the kernel records writeback errors in an errseq_t, a counter plus error code that "allow[s] any number of 'subscribers' to tell whether it has changed since a previous point where it was sampled" (lib/errseq.c lines 8 to 10, v5.10), so every file descriptor open at the time sees the error once ({{LWN, Improved block-layer error handling|https://lwn.net/Articles/724307/}}). The pages may still be gone. The rule: a failed fsync means that file's recent writes are lost; rewrite it from memory, or abort. With delayed allocation, running out of space can also surface only at fsync or close rather than at write, so check both: Python's f.close() raises OSError if the underlying close fails.

When it bites in ML, and the fix
  • An fsync per step is about a millisecond per call here and can be tens of milliseconds on cloud block storage not run here: fine once per checkpoint, ruinous once per logged metric line. Buffer logs and fsync on a timer.
  • Count the calls: strace -f -e trace=fsync,fdatasync,sync_file_range,rename,renameat -p PID, or strace -c for totals.
  • Never retry a failed fsync and continue. Save the checkpoint again to a new file.
