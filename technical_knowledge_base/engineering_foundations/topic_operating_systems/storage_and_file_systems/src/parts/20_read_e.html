5. Writing: dirty pages, writeback and throttling

ch. 39 Files and Directories (fsync), ch. 40 (write buffering)

The problem. If every write() waited for the device, a program writing a checkpoint in 4 KiB pieces would pay a device round trip for each. So writes go to the page cache and return; the device is updated later, in large batches. The cost of that speed is the gap this page is about.

How it works

source write() on ext4 runs generic_perform_write (mm/filemap.c line 3288, v5.10): for each page, ext4_da_write_begin (fs/ext4/inode.c line 2934) finds or creates the page in the cache and reserves space without choosing disk blocks (delayed allocation, section 8), the bytes are copied in, the page is marked dirty (changed in memory, not yet on the device), and balance_dirty_pages_ratelimited (line 3365) checks whether this writer has dirtied too much. Then write() returns. Nothing has touched the device.

Dirty pages are written back by per-device flusher threads (kernel workers named kworker/u*:*-flush-*) for three reasons ({{vm sysctl docs|https://docs.kernel.org/admin-guide/sysctl/vm.html}}; mm/page-writeback.c lines 74 to 109):

  1. Age: every dirty_writeback_centisecs (500, so 5 s) the flusher wakes and writes data that has been dirty longer than dirty_expire_centisecs (3000, so 30 s).
  2. Background threshold: when dirty data passes dirty_background_ratio (10%) of dirtyable memory (free memory plus file pages that could be reclaimed, not total RAM: global_dirtyable_memory, line 362), the flusher starts writing everything, regardless of age.
  3. Hard threshold: near dirty_ratio (20%) the writing process itself is paused in balance_dirty_pages (line 1555, the pause at line 1795) so it cannot dirty memory faster than the device drains it. This is dirty throttling: write() becomes slow without any error.

On this VM the kernel computed a background threshold of MiB and a hard threshold of MiB VM-wide (/proc/vmstat) measured. With cgroup v2 each memory cgroup is also its own writeback domain with thresholds scaled to its memory, so a container with a 1.5 GB limit is throttled long before the machine is ({{cgroup v2 docs, Writeback|https://docs.kernel.org/admin-guide/cgroup-v2.html#writeback}}).

Watching it happen

measured Each run wrote a file into a fresh container (limit 1,500 MB) and sampled its memory.stat (dirty and under-writeback page cache) and io.stat (bytes the device received) every 100 ms.

Six runs wrote 16 MiB (or 256 MiB) and then waited, with nothing calling fsync. The textbook rule is "written back once it is 30 s old". How long did the 16 MiB actually stay dirty?
In a fresh container the data left at the flusher's next 5-second wake-up, long before it was 30 s old. Our reading of the source: wb_over_bg_thresh (mm/page-writeback.c line 1960) also compares this writeback domain's dirty pages with its share of the background threshold, a share proportional to how much it recently wrote back. A brand-new container has almost no share, so even 16 MiB counts as "over its threshold" and is written in the background. After the container had just written and synced 1 GiB (the "primed" runs), it had a share, and the same 16 MiB waited between 2 and 32 s as that share decayed. We could not trace the flusher here (that needs privileges), so treat the explanation as the likely one, not a proven one. The lesson does not depend on it: when dirty data reaches the device is not a promise you can use. Only fsync is.
What it costs, and when it bites in ML
  • A crash in the window loses data that every call said was written. The 256 MiB checkpoint of section 11 left MiB dirty when torch.save returned. (Killing the process does not lose it: the dirty pages belong to the kernel. Only a kernel crash, a power loss or a VM or node being killed does.)
  • Dirty throttling stalls training. In the "1.5 GiB, as fast as possible" run the writer was caught sleeping in balance_dirty_pages and the container's dirty data hovered at the domain's limits while the device drained it. A training loop that saves a large checkpoint synchronously stalls the same way; a background writer thread does not stop the stall from happening, but it moves it off the training thread.
  • Dirty pages count toward your container's memory and cannot be dropped until they are written, so a memory-limited container that writes faster than its device can be pushed toward the OOM killer by its own page cache ({{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}} section 12).
Commands and fixes
  • See it: grep -E "^(Dirty|Writeback):" /proc/meminfo (machine), grep -E "file_(dirty|writeback)" /sys/fs/cgroup/memory.stat (container), cat /proc/PID/wchan (a writer in balance_dirty_pages is being throttled), grep -E "nr_dirty(_background)?_threshold" /proc/vmstat.
  • Tune (hosts you own): vm.dirty_background_bytes and vm.dirty_bytes set absolute limits instead of ratios, which is saner on machines with hundreds of GB of RAM where 20% is far more than a device can drain in seconds.
  • In code: fsync what must survive (section 6); for a long streaming write, start writeback early with sync_file_range(SYNC_FILE_RANGE_WRITE) on each finished chunk and fdatasync once at the end, which keeps dirty data and the final fsync small.
