1. CPU scheduling: who runs next?


The problem. A CPU core runs one thread at a time, but a training node has many runnable threads: the training loop, DataLoader workers, a logging thread, your shell. The scheduler is the kernel code that decides which one runs on the core for the next slice of time. Each policy below is a different answer, and each is good at one thing and bad at another. Two numbers judge them (OSTEP chapter 7): turnaround time = finish time minus arrival time (how long a batch job takes), and response time = first time it runs minus arrival time (how long an interactive program waits before anything happens).


    

  • FIFO runs jobs in arrival order, each to completion. SJF (shortest job first) picks the shortest waiting job, still to completion. STCF (shortest time-to-completion first) may preempt: stop a running job when a shorter one arrives.
    • 

  • Round robin gives each job a fixed time slice (quantum) in turn: good response, bad turnaround.
    • 

  • MLFQ (multi-level feedback queue, chapter 8) learns from behaviour: a job starts at top priority and drops a level each time it uses up its allotment; jobs that block for I/O early stay high. A periodic boost lifts everyone back so nothing starves.
    • 

  • CFS (Linux's Completely Fair Scheduler, chapter 9.7; Linux 2.6.23 to 6.5) gives each job a virtual runtime (vruntime) that grows as it runs, more slowly for a higher weight, and always runs the job with the smallest vruntime. A nice value from -20 to 19 picks the weight. Since Linux 6.6 the default is EEVDF, which this kernel (5.10) cannot run; it is described from sources in the Reading tab.
    • 



The model: time in ticks; one CPU; a job with "I/O every k" runs k ticks then blocks for the I/O time (as in OSTEP's mlfq.py). At each tick, newly arrived jobs join the queue first, then jobs whose I/O finished, then the job whose slice just ended; ties go to whoever queued first. The CFS here keeps the kernel's slice formula, weights and placement rules (sources below) and leaves out wake-up preemption and multi-CPU load balancing.

All from SourceLinux v5.10 kernel/sched/fair.c (the kernel running the real measurements):

    • 

  • Slice = period × weight / total weight of the runnable threads (sched_slice, line 701), where the period is sched_latency, or (number of threads × min_granularity) when more threads than sched_nr_latency = latency / granularity are runnable (__sched_period, line 687).     • 

  • Placement (place_entity, line 4108): a new thread starts one virtual slice after the queue's minimum vruntime (the START_DEBIT feature), so it cannot jump the queue; a thread waking from I/O is placed at most half a latency behind the minimum, so sleeping does not bank unlimited credit.

2. Paging and the TLB: from a virtual address to a physical one


The problem. Every process believes it owns one large, private range of addresses (its virtual address space), but all processes share one physical memory. On every load and store, the CPU's memory management unit (MMU) translates the virtual address the program used into a physical one. Memory is cut into fixed-size pages (4 KiB on this machine); the page table, kept by the kernel in memory, maps each virtual page number (VPN) to a physical frame number (PFN). A page-table entry (PTE) also holds a valid bit: an access to an invalid page traps into the kernel as a page fault. Reading the page table on every access would double the cost of memory, so the CPU caches recent translations in the TLB (translation lookaside buffer): a hit costs nothing extra, a miss costs a walk of the table. OSTEP chapters 18 to 22.

2b. The TLB on an array walk: row-major against column-major


A 2-D array of 4-byte integers is stored row after row. Walking it along rows touches consecutive addresses, so one TLB entry serves a whole page of accesses; walking it down columns jumps a whole row each time and may need a different page on every access. Same data, same sum, different order. (OSTEP Fig. 19.2 is the 1-D version: ten integers on 16-byte pages, 70% hits; choose "OSTEP Fig. 19.2" to reproduce it.)









Pages are tiny here so that a few fit on the screen; on the real machine a page is 4,096 bytes and the TLB has hundreds to thousands of entries. The proportions are what carry over.

RealThe TLB on this machine, by timing


OSTEP's chapter 19 homework, done for real (src/sim/real/tlb.c): touch one integer on each of N pages, over and over, and time each access. While the N translations fit in the TLB, an access costs about a nanosecond; past it, each access pays for a page-table walk. The catch is that the cache footprint grows with N too, so the same loop is run a second time on 2 MiB huge pages (one TLB entry covers 512 of the 4 KiB pages): same addresses, same cache lines, only the translation differs. Where the two lines part, it is the TLB.




From 2,048 to 4,096 pages the 4 KiB line jumps from about 1.1 to 7.6 ns per access and keeps rising, while the huge-page line stays near 1.1 ns until 16,384 pages: a second-level TLB of a few thousand entries is consistent with that, but the hardware's exact size is not measured here. In this VM a TLB miss is also a two-stage walk (the guest's page table, then the hypervisor's), which makes misses dearer than on bare metal. The 16,384-page jump on huge pages is not explained by this experiment. The first rows (1 to 8 pages) are slower only because the loop's own overhead is spread over few accesses. 2c. When memory is full: which page to evict


When a process touches more pages than fit in memory, each access to a page that is not resident is a major page fault: the kernel reads the page from disk (swap, or the file it maps) and must first evict another page. The policy decides which. OPT evicts the page used furthest in the future (perfect, impossible in practice, the yardstick); FIFO the oldest; LRU the least recently used; CLOCK approximates LRU cheaply: a hand sweeps the frames, clearing each page's use bit, and evicts the first page whose bit is already clear (OSTEP chapter 22; Linux's real policy keeps active and inactive lists, a refinement of the same idea).



















Predict. FIFO on Belady's sequence 1 2 3 4 1 2 5 1 2 3 4 5. With 3 frames there are 9 page faults. With 4 frames (more memory)?



 10: more memory, more faults. This is Belady's anomaly (Belady, Nelson and Shedler, 1969), cited in OSTEP chapter 22. LRU and OPT can never do this: they have what OSTEP calls the stack property (the pages kept with k frames are always among those kept with k + 1). Choose the Belady sequence above and move the frames slider from 3 to 4 with FIFO.



For a training job. A dataset opened with np.memmap or a safetensors file is mapped, not read: its pages come in by page fault on first touch, from the page cache if another process (or an earlier epoch) already read them, and are evicted under memory pressure by the policy above. The Syscall tracer shows the job's real mmap of its dataset, and the {{Debug lab|#t-debug}} measures a cold and a warm page cache. 3. Copy-on-write after fork: why DataLoader workers grow


The problem. fork() creates a child process with a copy of the parent's whole address space. Copying gigabytes for every child would be slow, so the kernel copies nothing: parent and child share every physical page, marked read-only, and only when one of them writes to a page does the write trap (a page fault), and the kernel give the writer its own copy of that one page. This is copy-on-write (CoW; OSTEP chapter 23 describes it as part of complete VM systems, chapter 5 introduces fork). PyTorch's DataLoader starts its workers with Python's default start method, which on Linux is fork up to Python 3.13 (3.14 changed it to forkserver; multiprocessing docs), so with fork a dataset held in the parent is shared with every worker for free, until something writes to it.


The catch in Python. Every Python object starts with a reference count, and merely reading an object from Python code (looping over a list, indexing it) increments and decrements that count: a write to the page the object lives on. So a worker that only reads a Python list of a million objects ends up copying every page those objects occupy. A numpy array is one object whose numbers sit in a plain buffer: reading the numbers never touches a reference count. The Python documentation describes the same problem for the garbage collector's own writes and offers gc.freeze() for it; PyTorch's DataLoader documentation warns that "the loader worker processes will consume the same amount of CPU memory as the parent process for all Python objects in the parent process which are accessed from the worker processes", recommends "non-refcounted representations such as Pandas, Numpy or PyArrow objects", and links issue 13246 (quoted from docs/source/data.md on the main branch, 2026-10-05).

For a training job. 4. Two threads, one counter: races, locks and deadlock


The problem. Threads of one process share memory. count = count + 1 looks like one step, but the CPU does it in three instructions: load count into a register, add 1, store it back. The real compiler output for it on this machine (gcc 12, -O2, arm64; src/sim/real/inc.c) is ldr, add, str:




If the scheduler switches threads (or a second core runs the other thread) between the load and the store, both threads load the same old value and one increment is lost: a race condition. The three instructions form a critical section that needs mutual exclusion. A lock provides it, built on a hardware instruction that reads and writes memory indivisibly (here xchg, test-and-set); an atomic add does the whole read-modify-write as one indivisible operation (on this machine gcc calls a helper, __aarch64_ldadd8_acq_rel, in the listing above). OSTEP chapters 26 and 28.

Deadlock: two locks, two threads


Thread 1 takes lock A, then lock B. Thread 2 takes B, then A. If each gets its first lock before the other asks for its second, each waits forever for the lock the other holds: a deadlock (OSTEP chapter 32). The standard fix is a lock order: everyone takes A before B, so the cycle cannot form. You are the scheduler: step either thread.














RealThe deadlock, seen from /proc


src/sim/real/deadlock.c: the same two threads with pthread mutexes and a 100 ms pause between the two locks. After 2 seconds the program reads each thread's state from /proc/self/task/<tid>/stat (S = sleeping) and the system call it is blocked in from /proc/self/task/<tid>/syscall: 98 is futex on arm64, the kernel call a contended mutex sleeps in. The ordered version finishes.






Predict. The racy counter on 1 CPU, 10 million increments per thread. How many are lost?



 Zero in all three real runs: on one CPU the threads only interleave at a preemption, a few times per second, and a preemption must land between one thread's load and its store. On 2 CPUs, 8.0 to 9.4 million of 20 million were lost. The bug is the same; only the odds changed. In the simulator, "switch every 100 instructions" shows the same thing.


For a training job. Python's GIL makes some single operations atomic but not count += 1, which is several bytecodes (Python FAQ); PyTorch's own data structures are guarded by C++ mutexes, which is where a hang in a DataLoader or NCCL thread sits (futex in py-spy dump or /proc). 5. Crash consistency: power fails in the middle of a write


The problem. Appending one block to a file changes three places on disk: the file's inode (I, its metadata: size and a pointer to the new block), the data bitmap (B, which blocks are in use) and the data block itself (Db, written to block 5). The disk writes them one at a time, and in whatever order it likes; a crash or power cut can leave any subset on disk. OSTEP chapter 42 lists what each subset means; a journal (write-ahead log: first describe the whole update in a separate log area, mark it complete with a commit block TxE, then write it in place) turns "any subset" into "all or nothing". Linux ext4's default data=ordered mode is the "ordered" protocol below, and its data=writeback mode allows the "data written last" one (ext4 documentation).


How to read it: blocks in a dashed box are issued together and may reach the disk in any order or not at all; a new box starts only after the previous one is completely on disk (a write barrier, a cache FLUSH on a real drive). Each step of the animation is one possible crash: green blocks reached the disk, faded ones did not. Then recovery runs: fsck without a journal, or journal replay (copy every transaction whose TxE is on disk to its final place).

"Old file": the append is lost but everything is consistent (acceptable: the application never got confirmation). "New file": the append survived. "Garbage": the metadata is consistent but the file now contains whatever was in block 5 before, which no checker can detect. Counts are of distinct crash states, not probabilities.


Predict. With data journaling, the file system sends TxB, I, B, Db and TxE to the journal all at once (one batch, no wait before TxE) to save a round trip. The disk writes TxE first and power fails before the journal's copy of Db lands. What does recovery do?



 Recovery trusts TxE: the transaction looks committed, so it copies the journal's slot for Db (whatever was there before) into block 5. That is why the protocol waits for the first four blocks before writing TxE (OSTEP 42.3), or, as ext4 can with journal_checksum, puts a checksum of the transaction in the commit block so a torn transaction is detected. The "TxE sent with the rest" protocol above shows the 8 crash points that end this way.
