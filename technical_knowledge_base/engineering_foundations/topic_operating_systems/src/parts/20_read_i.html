8. Containers and isolation: one kernel, many private views

not in OSTEP's three pieces; builds on ch. 4 (processes) and the Security chapters (53 to 57)

The problem. A training job needs a precise set of libraries (one CUDA, one PyTorch, one Python), must not see or disturb the other jobs on the node, and must stay inside its share of CPU and memory. A virtual machine (section 9) would give all that by running a whole second kernel; a container gets most of it with no second kernel at all. A container is ordinary processes on the host's kernel, started with four kinds of restriction.

Namespaces: what it can see"A namespace wraps a global system resource in an abstraction that makes it appear to the processes within the namespace that they have their own isolated instance" ({{namespaces(7)|https://man7.org/linux/man-pages/man7/namespaces.7.html}}): its own PIDs, mounts, network, hostname, IPC, users.
cgroups: how much it can useControl groups "allow processes to be organized into hierarchical groups whose usage of various types of resources can then be limited and monitored" ({{cgroups(7)|https://man7.org/linux/man-pages/man7/cgroups.7.html}}): CPU quota, memory limit, PIDs, I/O.
Capabilities and seccomp: what it may doRoot's powers split into separate capabilities, most dropped ({{capabilities(7)|https://man7.org/linux/man-pages/man7/capabilities.7.html}}); a seccomp filter checks every system call against an allowlist at kernel entry (section 1).
An image: what files it hasA stack of read-only layers plus one writable layer, merged by a union file system (overlayfs), mounted as its root.

What to notice: each namespace is a separate kernel object (the numbers in brackets), except time (4026531834) and user (4026531837), which are the kernel's initial namespaces, 0xEFFFFFFA and 0xEFFFFFFD in include/linux/proc_ns.h lines 45 and 48 (v6.12): shared with the host; the process sees itself at the root of its own cgroup (0::/); the limits are plain files; ps sees only two processes, with the shell as PID 1; 14 capabilities remain of root's full set (no cap_sys_admin, no cap_sys_ptrace, which is why this page's strace runs needed --cap-add SYS_PTRACE); Seccomp: 2 means a filter is active (Docker's default profile "is an allowlist which specifies the calls that are allowed", {{Docker docs|https://docs.docker.com/engine/security/seccomp/}}); and the root file system is overlay.


The OOM kill inside a container. When the processes of a cgroup reach memory.max and the kernel cannot reclaim enough, "the OOM killer is invoked in the cgroup" ({{cgroup v2|https://docs.kernel.org/admin-guide/cgroup-v2.html#memory-interface-files}}) and kills one of them with SIGKILL: the container exits with code 137 (128 + 9), Kubernetes reports OOMKilled, and memory.events counts it in oom_kill (zero above). memory.high instead throttles: "Going over the high limit never invokes the OOM killer". A DataLoader worker is often the process killed, which surfaces in the main process as "DataLoader worker (pid N) is killed by signal: Killed." (the format string is in {{torch/csrc/DataLoader.cpp line 158 at v2.14.1|https://github.com/pytorch/pytorch/blob/v2.14.1/torch/csrc/DataLoader.cpp#L158}}). The {{Debug lab|#t-debug}} reproduces it.


Rootless. By default the container's root is the host's root with fewer capabilities. Rootless containers (Podman, rootless Docker) also use a user namespace so that root inside maps to an ordinary user outside: a breakout lands as nobody special. HPC clusters use Apptainer (formerly Singularity) for the same reason: the job runs as the submitting user.


Sandboxes for code you do not trust


Containers share the host kernel, so a kernel bug reachable through an allowed system call is a way out. For running code an agent or a user wrote, two stronger designs are common. gVisor "intercepts application system calls and acts as the guest kernel": a user-space "application kernel" implements Linux's interface, so the host kernel sees far fewer, simpler calls ({{gVisor docs|https://gvisor.dev/docs/}}). Firecracker runs each sandbox as a minimal virtual machine (a microVM) with its own kernel, "lightweight virtual machines (microVMs) that provide enhanced security and workload isolation over traditional VMs, while enabling the speed and resource efficiency of containers" ({{firecracker-microvm.github.io|https://firecracker-microvm.github.io/}}). The {{agentic-harnesses topic|n:3c65c17b0d0d81d881a8fe98b4cff7bb}} covers code-execution sandboxes for agents.


GPU containers not run here


A container image does not contain the GPU driver: the kernel module belongs to the host, and the user-space driver library must match it exactly. The NVIDIA Container Toolkit ("a collection of libraries and utilities that enable you to build and run GPU-accelerated containers", {{NVIDIA docs|https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/index.html}}) hooks into container start-up to mount the host's device files (/dev/nvidia*) and driver libraries into the container. The image brings the CUDA runtime and PyTorch; the host brings the driver. Section 9 explains why those two versions must be compatible.

9. Virtualization and the GPU driver stack


appendix Virtual Machines


not run here except where marked: this lab has no GPU. It does, however, run inside a virtual machine (Docker Desktop's Linux VM on macOS), which is why section 3's cross-CPU wake-up and section 4's TLB misses were dearer than on bare metal. The wake-up is slow because this VM's interrupt controller is a GICv2 emulated inside QEMU on macOS's Hypervisor.framework: every inter-processor interrupt is a trip out of the guest, and an idle target vCPU is a host thread that must itself be woken ({{Virtualization and the GPU driver stack|n:3f05c17b0d0d8158b029e9b2ba2e161b}}, section 5, measures each step).


Virtual machines. A hypervisor (KVM in Linux, Xen, Apple's Hypervisor framework under Docker Desktop, the cloud providers' own) runs whole guest operating systems, each believing it owns a machine. Modern CPUs help in hardware: an extra privilege level for the hypervisor (EL2 on ARM64, VMX root mode on x86), and a second layer of page tables so that guest-physical addresses are translated to host-physical ones by the MMU (the two-dimensional walk of section 4). A cloud GPU instance is almost always such a guest.


The IOMMU and passthrough. A device that does DMA writes straight into physical memory, so a guest given a real device could overwrite anything. The IOMMU is an MMU for devices: it translates and checks every DMA address against tables the hypervisor controls. With it, a whole GPU can be handed to one VM (passthrough, via Linux's VFIO) and the guest's driver talks to the hardware directly at near-native speed.


Sharing one GPU. SR-IOV lets one PCIe device present several "virtual functions", each passed to a different guest. NVIDIA's MIG (Multi-Instance GPU) goes further on data-centre GPUs: it can "partition supported NVIDIA GPUs into multiple isolated instances, each with dedicated compute and memory resources" ({{MIG user guide|https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/index.html}}), so two small inference jobs cannot slow each other down the way two processes sharing one GPU by time-slicing can.


One CUDA call, from Python to the GPU


    

  1. Python: y = x @ w on CUDA tensors calls into PyTorch's C++ dispatcher, which picks a CUDA kernel (or a cuBLAS routine).
    2. 

  2. CUDA runtime (libcudart, shipped with PyTorch's wheel): the kernel launch is turned into a call to the CUDA driver API.
    3. 

  3. User-space driver (libcuda.so, installed with the host's driver): writes the launch into a command buffer in memory the GPU can read, and, for most launches, notifies the GPU through a register mapped into the process, so routine launches need no system call (the doorbell path is verified in NVIDIA's open kernel driver: its UVM channel code writes commands to memory and rings a "usermode" register of the class VOLTA_USERMODE_A; that the closed libcuda launches kernels the same way remains inferred; {{Virtualization and the GPU driver stack|n:3f05c17b0d0d8158b029e9b2ba2e161b}}, section 9).
    4. 

  4. Kernel driver (nvidia.ko): entered through ioctl system calls on /dev/nvidia* for setup: creating contexts, allocating and mapping GPU memory, pinning host pages (section 4), and handling interrupts and faults.
    5. 

  5. GPU: fetches the commands by DMA (through the IOMMU in a VM) and runs the kernel; the Python call returned long ago, because CUDA launches are asynchronous until something waits (.item(), .cpu(), torch.cuda.synchronize()).
    6. 



An strace -f of a CUDA PyTorch program shows exactly that pattern: a burst of openat("/dev/nvidia..."), mmap and ioctl calls at start-up and very few during steady training. Writing kernels is the {{cuda-and-gpu-programming topic|n:3c65c17b0d0d81c39f34d5e070d783c1}}; the hardware itself, the {{hardware topic|n:3c65c17b0d0d8118beeefaed56da6f8e}}.


Driver against runtime versions. Two version numbers, from two places: the driver (host, with nvidia.ko; nvidia-smi shows it and the newest CUDA version it supports) and the runtime (inside your image or wheel; torch.version.cuda). The runtime must not be newer than the driver supports, apart from the compatibility paths NVIDIA documents ("Minor Version Compatibility", "Forward Compatibility" in the {{CUDA compatibility guide|https://docs.nvidia.com/deploy/cuda-compatibility/index.html}}). "CUDA driver version is insufficient for CUDA runtime version" means a new image on an old host.
