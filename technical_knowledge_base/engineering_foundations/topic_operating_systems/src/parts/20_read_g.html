6. Concurrency: threads that share memory

ch. 26 Concurrency and Threads, ch. 27 Thread API, ch. 28 Locks, ch. 30 Condition Variables, ch. 31 Semaphores, ch. 32 Concurrency Bugs, ch. 33 Event-based Concurrency

The problem. Threads (section 2) share one address space, which is what makes them useful: PyTorch's operator threads all write into one output tensor, the DataLoader's helper threads hand batches to the training loop. But the scheduler can stop a thread between any two instructions, and on several CPUs two threads really do run at the same instant. Any piece of shared data that more than one thread updates is a race waiting to happen: the result depends on the timing.

Locks, and the futex underneath. A lock (mutex) makes a critical section: only one thread at a time runs the code between lock() and unlock(). Built naively, a waiting thread either spins (burning a CPU) or makes a system call every time. Linux's answer is the futex, "fast user-space locking": "In the uncontended case, a thread can access or modify the lock state with atomic instructions ... performed entirely in user mode" and only a thread that must wait asks the kernel to put it to sleep ({{futex(2)|https://man7.org/linux/man-pages/man2/futex.2.html}}; futex_wait, kernel/futex/waitwake.c line 688, v6.12). An atomic instruction (fetch-and-add) does the read-modify-write as one indivisible step in hardware, with no lock and no kernel; it is how counters, reference counts and lock-free queues are built. Which writes other CPUs see, and in what order, is the memory model: covered with measurements (atomics, false sharing) in Part 2 of the {{C++ page|n:3cd5c17b0d0d81ceadcee44fe9c023a0}}.


Waiting for something. A condition variable lets a thread sleep until another signals that a condition may now hold ("a batch is ready"), always rechecking the condition under the lock. A semaphore is a counter that blocks at zero, good for "at most N in flight" (the DataLoader's prefetch_factor is this idea). The sem.* files in section 2's /dev/shm are the semaphores behind multiprocessing's queues.


Deadlock. Thread A holds lock 1 and waits for lock 2; thread B holds lock 2 and waits for lock 1; neither can proceed, forever. It needs four conditions at once (mutual exclusion, hold and wait, no preemption, a circular wait), and the usual cure removes the circle: always take locks in one global order. A training-specific variant: fork() copies only the calling thread (section 2), so a lock that another thread held at the moment of the fork stays locked forever in the child, and the child hangs at its first malloc or log call. That is the reason behind Python 3.12's fork DeprecationWarning, Python 3.14's switch to forkserver, and PyTorch's "poison fork". The {{Debug lab|#t-debug}} reproduces the hang.


Python's GIL. In CPython (before the free-threaded build) one global interpreter lock lets only one thread run Python bytecode at a time; threads still help for I/O and for C code that releases the GIL (NumPy, PyTorch operators), which is why the DataLoader uses processes for Python-heavy work. The {{Python page|n:3cd5c17b0d0d81b28acdea39e7a4d998}} covers the GIL and free-threading.


Event-driven I/O: what asyncio, tokio and Node are built on


A server with ten thousand open connections cannot afford ten thousand threads, each mostly asleep. The alternative is one thread and one question to the kernel: "which of these file descriptors are ready?". select and poll ask it with the whole list every time; epoll keeps the list in the kernel, so the cost depends on the ready ones only: it "performs a similar task to poll(2) ... and scales well to large numbers of watched file descriptors" ({{epoll(7)|https://man7.org/linux/man-pages/man7/epoll.7.html}}). Python's asyncio event loop is a loop around epoll_wait; so are Node's libuv (Part 1 of the {{JS/TS page|n:3cd5c17b0d0d81dbac7be3b8686be023}}) and Rust's tokio (Part 3 of the {{Rust page|n:3c65c17b0d0d8156bed9ead8a22f33b0}}). On macOS the same role is played by kqueue. A tiny asyncio echo over a local socket, traced:

io_uring goes one step further: "io_uring is a Linux-specific API for asynchronous I/O ... ring buffers which are shared between user space and kernel space" ({{io_uring(7)|https://man7.org/linux/man-pages/man7/io_uring.7.html}}). The program queues reads and writes in one ring and collects completions from another, often with no system call per operation ({{LWN, 2019-01-15|https://lwn.net/Articles/776703/}}). It exists on this lab's kernel 5.10 but in an early form; newer data loaders and storage engines use it on 6.x kernels.
