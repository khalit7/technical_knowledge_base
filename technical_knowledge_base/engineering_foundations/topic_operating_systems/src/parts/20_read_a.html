The idea

The core idea. An operating system turns one machine into many private ones: every program gets its own memory, a share of the CPUs and handles on files and devices, all owned by one kernel that the program can reach only through a system call. A training job runs at full speed between those crossings and pays at each one: a system call, a page fault, a context switch, a CPU-quota stall, an fsync, a VM exit.

  1. One job, three layers. The running job of this topic, a tiny CPU-only PyTorch run, once its DataLoader has started: the trainer python train.py (PID 13, 5 threads) and its two worker processes (PIDs 19 and 21, 4 threads each), on the glass plate of user space. Below it the kernel, which alone touches the hardware: the CPUs, RAM, the drive and the GPU. A program runs on the CPU directly, in user mode, and the kernel regains control only at a system call, a fault or an interrupt (OSTEP's limited direct execution). Owner: {{Processes and the system-call API|n:3f05c17b0d0d811e99f7cb8c15d12697}}, whose {{Fig. 1|n:3f05c17b0d0d811e99f7cb8c15d12697#stg-hero}} draws these processes over their kernel records.
  2. One door: the system call. Whatever the job needs from the kernel goes down through one trapping instruction (svc #0, syscall) and comes back as a number: 281 ns for getppid here, against 1.3 ns for a function call. CPython, libtorch and glibc all end in the same few hundred calls (the {{Syscall tracer|#t-trace}} records them). Section 1 prices every crossing; {{Fig. 2 on Processes|n:3f05c17b0d0d811e99f7cb8c15d12697#stg-sc}} follows one os.read() down and back.
  3. CPU time: the scheduler. Thirteen threads, five CPUs. Each CPU has a run queue; the scheduler, woken by the timer interrupt, decides which thread runs next, and a container's CPU limit is a quota that stops the whole group once spent (section 3). Owner: {{Scheduling and CPU time|n:3f05c17b0d0d81ed9c18cc47c6bfdf76}}, {{Fig. 1|n:3f05c17b0d0d81ed9c18cc47c6bfdf76#stg-hero}}.
  4. Memory: the page tables. Every address a thread uses goes through its process's page tables to a 4 KiB frame of RAM. Fork shares frames copy-on-write, so the three processes' RSS adds up to 815 MiB while their PSS is 345 MiB (section 4). Owner: {{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}}, {{Fig. 1|n:3f05c17b0d0d81a48892cea154ce950b#stg-hero}}; fork's sharing is its {{Fig. 6|n:3f05c17b0d0d81a48892cea154ce950b#stg-cow}}.
  5. Inside the process: the allocator. Allocators get large regions from the kernel rarely and hand out small pieces often; what your code frees stays with them, which is why RSS rarely drops after del (section 5). Owner: {{Memory allocators|n:3f05c17b0d0d81209ae9d856695dc958}}, {{Fig. 1|n:3f05c17b0d0d81209ae9d856695dc958#stg-hero}}.
  6. Waiting: two kernel queues. A thread waiting for another thread sleeps on a futex, and enters the kernel only when the lock is contended (8,382 futex calls for 20 million lock and unlock pairs here); a thread waiting for I/O sleeps in epoll (section 6). Owner: {{Concurrency|n:3f05c17b0d0d8112ad1af99308fa913f}}, {{Fig. 1|n:3f05c17b0d0d8112ad1af99308fa913f#stg-hero}}.
  7. A checkpoint: the page cache, then the drive. torch.save's write() returns once the bytes are in the page cache (1.4 µs for 4 KiB); only fsync waits for the drive (1,305 µs), and only fsync and rename decide what a crash leaves (section 7). Owner: {{Storage and file systems|n:3f05c17b0d0d8141be7acc1313570cbf}}, {{Fig. 1|n:3f05c17b0d0d8141be7acc1313570cbf#stg-hero}}; the safe save is its {{Fig. 5|n:3f05c17b0d0d8141be7acc1313570cbf#stg-ar}}.
  8. A container: a fence, not a second kernel. The same processes, started with namespaces (what they see) and a cgroup (what they may use; this topic's containers ran with --cpus 2 --memory 3g), on the one shared kernel (section 8). Owner: {{Containers and isolation|n:3f05c17b0d0d8156a841e4bf28f11293}}, {{Fig. 1|n:3f05c17b0d0d8156a841e4bf28f11293#stg-hero}}.
  9. The GPU: the hot path skips the kernel. libcuda, in the trainer, writes commands into memory the GPU reads and rings a doorbell; the kernel driver nvidia.ko is entered by ioctl only for setup, allocation and errors. In a cloud VM a hypervisor sits under the kernel, and this lab runs in one too (section 9). Owner: {{Virtualization and the GPU driver stack|n:3f05c17b0d0d8158b029e9b2ba2e161b}}, whose {{Fig. 10|n:3f05c17b0d0d8158b029e9b2ba2e161b#stg-cuda}} takes one CUDA call down.

A map, not a mechanism: each step lights the part one child page owns. PIDs, threads, RSS, PSS, the CPU count, the system-call cost and the futex count are this page's own runs (src/read/code/out/); the write and fsync costs are the ladder's, from Storage and file systems.

You need nothing beyond Python: this root starts from zero. Caches and the machine under the OS, from the programmer's side, are {{C++: the machine underneath|n:4055c17b0d0d811fa947ee576a97a516}}.

New terms on this page (each used in the comparisons below):
Kernel: the core of the OS, running in the CPU's privileged mode with full control of the hardware; on this page Linux means the kernel.
User mode, kernel mode: the CPU's two privilege modes (EL0 and EL1 on ARM64, rings 3 and 0 on x86-64); user mode cannot touch devices or the memory map.
System call: a numbered request to the kernel through one trapping instruction, the only way in.
Process: a running program: an address space, registers, open file descriptors, credentials and a PID.
Thread: a second flow of execution in the same process: own registers and stack, shared memory and files.
Virtual address, page: every address a program uses is translated by the MMU, page by page (4 KiB here), through per-process page tables.
Page fault: the trap on a page with no valid entry; minor if no I/O is needed, major if the device must be read.
Page cache: file data the kernel keeps in otherwise free memory; read and write go through it.
Context switch: saving one thread's registers and loading another's, plus a new address space if the process changes.
Namespace, cgroup: what a group of processes can see; how much of each resource it may use. A container is both.
fsync: the call that returns only when a file's data and metadata are on the device.
Hypervisor, driver: the program that runs whole operating systems as guests; kernel code that runs one kind of device.

How this topic knows what it says

Every output on these pages was produced for real, on 2026-10-05, inside the Docker image kb-os-lab:1 (Debian 12, Python 3.11.2, PyTorch 2.14.1 CPU build), on Linux 5.10.104 running in Docker Desktop's virtual machine on an Apple M1 laptop with 5 CPUs and about 10 GB of memory: measured here. A virtual machine on a laptop is not a training server, so absolute numbers are this machine's, and ratios are the lesson. What needs a GPU, a newer kernel (6.6 and later) or several memory nodes is taught from man pages, kernel documentation, kernel source at a pinned version, or vendor documentation and labelled not run here.
