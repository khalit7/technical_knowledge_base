In one screen: one training job, followed through the operating system

An operating system (OS) is the program that owns the machine: it shares the CPUs, the memory and the devices among all the programs that run, and it gives each of them a simpler, safer machine to program against than the bare hardware. Every line of a training script eventually asks it for something. This page follows one real job, a tiny CPU-only PyTorch run, from python train.py to its last checkpoint, and stops at each point where the OS does work.

The script asks the kernel for everythingOpening a file, allocating memory, starting a thread: each is a system call, the only door from a program into the kernel. Section 1. torchrun and the DataLoader start processesWorkers are created with fork, spawn or forkserver; each is a separate address space. Section 2. Threads and processes share a few CPUsThe scheduler decides who runs; a container's CPU limit can pause your job every 100 ms. Section 3. The dataset is memory-mappedPages of the file appear in memory on first touch (a page fault); copy-on-write shares pages after fork. Section 4. Tensors need memorymalloc, arenas and PyTorch's caching allocator sit between your code and the kernel's pages. Section 5. Threads contend for locksLocks, futexes, and the event loops that asyncio and tokio are built on. Section 6. A checkpoint goes to diskwrite() only reaches memory; fsync and an atomic rename make it survive a crash. Section 7. It all runs in a containerNamespaces hide the rest of the machine, cgroups cap CPU and memory, and the OOM killer ends the job with exit 137. Section 8. On a real cluster: a VM and a GPU driverHypervisors, the IOMMU, MIG, and one CUDA call from Python down to the GPU. Section 9. When it breaksA symptom-to-subsystem table, the tools that show each subsystem, and ten interview questions. Section 10.

The three easy pieces. The book this page follows, Operating Systems: Three Easy Pieces (OSTEP, by Remzi and Andrea Arpaci-Dusseau, free online), organises the whole subject into three ideas, and so does this page:

VirtualizationThe OS turns one CPU into the illusion of many (processes, scheduling) and one physical memory into a private, huge memory for each program (virtual memory). Sections 2 to 5.
ConcurrencySeveral threads of execution share memory at once; the OS gives them locks and ways to wait. Section 6.
PersistenceData must survive a crash or power loss: devices, file systems, and the exact promise that fsync makes. Section 7.
Beyond the bookContainers, virtual machines and the GPU driver stack are where an ML job actually runs. Sections 8 and 9.
How this page knows what it says
Every output on this page was produced for real, on 2026-10-05, inside the Docker image kb-os-lab:1 (Debian 12, Python 3.11.2, PyTorch 2.14.1 CPU build), on Linux 5.10.104 running in Docker Desktop's virtual machine on an Apple M1 laptop with 5 CPUs and about 10 GB of memory: measured here. A virtual machine on a laptop is not a training server, so absolute numbers are this machine's, and ratios are the lesson. What needs a GPU, a newer kernel (6.6 and later) or several memory nodes is taught from man pages, kernel documentation, kernel source at a pinned version, or vendor documentation and labelled not run here.
