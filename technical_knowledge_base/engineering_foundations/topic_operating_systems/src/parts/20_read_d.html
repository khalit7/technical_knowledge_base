6. Concurrency: threads that share memory

Threads share one address space, which is what makes them useful and what makes them dangerous: the scheduler can stop a thread between any two instructions, and on several CPUs two threads really do run at once. count = count + 1 is three instructions (load, add, store); two threads that each add 1 ten million times on two CPUs ended at 10,747,160 instead of 20,000,000 here. Code on shared data that must not run in two threads at once is a critical section; a lock or an atomic instruction (one indivisible read-modify-write) protects it. Two locks taken in opposite orders can wait for each other forever: a deadlock, cured by one global lock order. CPython's GIL lets one thread run bytecode at a time, which is why the DataLoader uses processes for Python-heavy work.

The distinction: every wait on Linux ends in one of two kernel queues. A thread waiting for another thread sleeps on a futex: the lock word lives in user memory, is taken with an atomic instruction, and only a thread that must wait asks the kernel to put it to sleep (20 million lock and unlock pairs under contention made 8,382 futex calls here). A thread waiting for I/O sleeps in epoll (asyncio, Node's libuv and tokio are loops around it) or collects completions from io_uring's rings. Choosing threads, processes or an event loop is choosing which queue your work waits in.

7. Persistence: getting a checkpoint safely onto disk

A storage device sits behind a driver and the block layer; a file system (ext4, XFS) turns its blocks into files, directories and names, keeping an inode per file (size, owner, block locations); the page cache (section 4) sits on top. write() and torch.save return once the bytes are in the page cache; the kernel's flusher threads write dirty pages out later, on their own schedule. A journal keeps the file system's own structures consistent across a crash; it does not protect your file's contents.

The distinction: returned is not durable. What a crash can leave is decided only by fsync (of the file, and of its directory, since fsync does not cover the file's name) and rename, which replaces a name atomically. The safe checkpoint is: write to a temporary file, fsync it, rename it over the old one, fsync the directory; a restart then sees the whole old checkpoint or the whole new one. Measured here, a 4 KiB write() took 1.4 us and an fsync of it 1,305 us; the protocol costs milliseconds against a training step and saves days. On a cluster the same rule applies to the whole set of shards, and object stores have no rename at all.

Depth: two real stories behind the protocol (2009, 2018)

2009, ext4's zero-length files. With delayed allocation, ext4 wrote file data much later than its rename; after crashes, users found "pretty much any file written to by any application (during the previous boot) was 0 bytes". Ted Ts'o's answer: applications had come to depend on ext3's behaviour "even though POSIX never really made any such guarantee"; ext4 then added a heuristic that forces the data out when a file is renamed over another ({{LWN, 2009-03-11|https://lwn.net/Articles/322823/}}). Do not rely on that heuristic: call fsync.

2018, fsyncgate. PostgreSQL assumed that a successful fsync meant everything written since the last one was safe. After a device error, Linux could report the error once and mark the pages clean, so a retried fsync succeeded with the data lost ({{LWN, 2018-04-18|https://lwn.net/Articles/752063/}}). Lesson for checkpoints: if fsync fails, treat that checkpoint as lost and write it again from memory; never just retry the fsync.
