3. Scheduling: sharing a few CPUs among many threads

ch. 6 Direct Execution, ch. 7 CPU Scheduling, ch. 8 Multi-level Feedback, ch. 9 Lottery Scheduling, ch. 10 Multi-CPU Scheduling

The problem. The running job alone has a main thread, a pool of compute threads for PyTorch's operators, two worker processes, and a few helper threads, on a machine with 5 CPUs that also runs other people's containers. At any moment there are more threads that could run (runnable) than CPUs. The kernel's scheduler decides which thread runs on which CPU and for how long, many times a second, so that each makes progress and the important or interactive ones are not starved.

How it gets control. A running thread does not hand the CPU back voluntarily unless it blocks (waits for I/O, a lock, a sleep). So at boot the kernel programs a hardware timer interrupt: every few milliseconds the CPU stops whatever it runs and jumps into the kernel, which can then decide to keep the current thread or switch. That switch is a context switch: save the current thread's registers into its kernel record, load another thread's, and, if the other thread belongs to a different process, switch the address space too (section 4), which makes the new thread's first memory accesses slower while the caches and the TLB warm up.

Policies, from OSTEP's to Linux's

OSTEP builds scheduling up from simple policies, each fixing the previous one's flaw: FIFO (run in arrival order: a long job delays everyone behind it), SJF and STCF (shortest job first, or shortest time to completion first: great average turnaround, but needs to know job lengths), round robin (a short time slice each in turn: good response time, poor turnaround), and the multi-level feedback queue (MLFQ: learn from behaviour, so threads that keep using whole slices sink in priority and threads that block quickly, like interactive ones, stay high). Two numbers judge them: turnaround time (finish minus arrival) and response time (first run minus arrival). The {{OS simulators|#t-sim}} tab runs all of them on the same jobs, with Gantt charts.

Linux: CFS, then EEVDF. From 2.6.23 (2007) Linux used the Completely Fair Scheduler, which "basically models an ideal, precise multi-tasking CPU on real hardware" ({{CFS design doc|https://docs.kernel.org/scheduler/sched-design-CFS.html}}). Each thread accumulates virtual runtime, its CPU time divided by its weight; the scheduler always runs the thread with the smallest virtual runtime, kept in a sorted tree. Since Linux 6.6 the same fair-share accounting is driven by EEVDF (Earliest Eligible Virtual Deadline First), which also gives each thread a virtual deadline so that threads asking for short slices get lower latency ({{EEVDF doc|https://docs.kernel.org/scheduler/sched-eevdf.html}}, {{LWN, 2023-03-09|https://lwn.net/Articles/925371/}}). The base slice is 0.75 ms (sysctl_sched_base_slice = 750000ULL, kernel/sched/fair.c line 76 at v6.12), scaled at boot by 1 + log2(min(CPUs, 8)) with the logarithm rounded down: 2.25 ms on a 5-CPU machine like this lab's VM, 3 ms on 8 CPUs or more ({{Scheduling and CPU time|n:3f05c17b0d0d81ed9c18cc47c6bfdf76}} works it through). not run here: this lab's kernel is 5.10, which still runs CFS.

Priorities: nice. A thread's weight comes from its nice value, from -20 (most CPU) to 19 (least). The table in the kernel (sched_prio_to_weight, kernel/sched/core.c line 10012 at v6.12) gives nice 0 a weight of 1024, nice 1 820 and nice -1 1277: each step is a factor of about 1.25, which the source comment explains as "the 10% effect": one nice level up or down moves a CPU-bound thread's share by about 10% against a competitor. nice -n 10 python preprocess.py makes a background job yield to training.

Which CPU: affinity. A thread may be restricted to a set of CPUs (taskset, os.sched_setaffinity). Staying on one CPU keeps its caches warm; on a machine with several memory nodes, staying near its memory matters more (section 4). The scheduler also migrates threads between CPUs to balance load, which is part of why identical training steps take slightly different times.

Container CPU limits: quota, period, throttling

A container's CPU limit is not "2 CPUs". It is a cgroup quota: "$MAX $PERIOD, which indicates that the group may consume up to $MAX in each $PERIOD duration" ({{cgroup v2 doc|https://docs.kernel.org/admin-guide/cgroup-v2.html#cpu-interface-files}}). Inside this page's containers, started with --cpus 2, the file reads:



200 ms of CPU time per 100 ms period, spent on any of the 5 CPUs. A job running 5 busy threads uses its 200 ms in the first 40 ms of each period and is then throttled: not scheduled at all for the remaining 60 ms. Training steps look fine on average and spiky in detail, and cpu.stat's nr_throttled counts the periods it happened. The catch for ML jobs is that the limit is invisible to the usual way of counting CPUs:




Python, and PyTorch's default thread pool, see 5 CPUs inside a container allowed 2. Set torch.set_num_threads and the DataLoader's num_workers from the quota (or Kubernetes' CPU limit), not from os.cpu_count(). The {{Debug lab|#t-debug}} measures the step-time cost of getting this wrong, with cpu.stat before and after.


In a training job


    

  • A starving GPU is often a CPU scheduling problem. If the DataLoader's workers cannot produce batches as fast as the GPU consumes them, the GPU waits. Too few workers, workers throttled by a CPU limit, or workers competing with too many compute threads all show up the same way: low GPU utilisation and the main process sleeping in next(it).

  • Kubernetes CPU limits become exactly this cgroup quota; requests become a relative weight (cpu.weight). Some clusters set CPU requests but no CPU limit on training pods for this reason.

  • Oversubscription. 8 GPU processes on a node, each with PyTorch's default threads equal to all cores, plus 8 workers each: hundreds of runnable threads on a few dozen cores.
