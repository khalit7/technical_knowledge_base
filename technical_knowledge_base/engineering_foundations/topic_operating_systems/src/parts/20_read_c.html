2. Processes: the running program

ch. 4 The Abstraction: The Process, ch. 5 Interlude: Process API, ch. 26 Concurrency: An Introduction

The problem. A program is a file on disk: instructions and some initial data. To run it, the OS needs to give it memory, load its code, point a CPU at the first instruction, and keep track of everything it opens, so it can be paused, resumed, and cleaned up when it ends, all while other programs do the same. The bundle of all that state is a process: a program in execution.

Address spaceThe memory the process can see: its code, data, heap, stacks and mapped files, at addresses that are private to it (section 4).
RegistersIncluding the program counter (the next instruction) and the stack pointer. Saved by the kernel whenever the process stops running.
File descriptorsSmall integers (0, 1, 2 are stdin, stdout, stderr) naming the files, pipes and sockets it has open.
Credentials and bookkeepingUser and group ids, a process id (PID), its parent's PID, its state, its signal handlers, its limits.

The process API: fork, exec, wait, exit, and signals

Unix builds every process from four calls (OSTEP ch. 5). fork() makes a near-exact copy of the caller: same code, same memory contents, same open files; it returns twice, 0 in the new child and the child's PID in the parent. exec() (the execve system call) replaces the program running in the current process with a new one, keeping the PID and open files. wait() lets a parent sleep until a child ends and collect its exit status. exit() ends the process. A shell running python train.py is just fork, then exec in the child, then wait in the parent. Splitting create from run looks odd until you see what it allows: between fork and exec the child can redirect its output, change directory or drop privileges, with no extra API.

A signal is the kernel's way to interrupt a process with a small numbered message. A process can install a handler for most of them. The ones a training job meets: SIGTERM ("please stop": what Kubernetes, Slurm and spot-instance preemption send first), SIGKILL (stop now: cannot be caught, blocked or ignored), SIGINT (Ctrl-C), SIGCHLD (a child changed state), SIGSEGV and SIGBUS (a bad memory access; a DataLoader "bus error" is usually a full /dev/shm, reproduced in the {{Debug lab|#t-debug}}).

/proc. The kernel publishes each process's state as files under /proc/<pid>/: status (state, memory, threads), maps (the address space), fd/ (open files), stack, cgroup. Nothing there is stored on disk; the kernel generates the text when you read it. ps, top and htop are just readers of /proc.

Each line of maps is one mapping: a range of virtual addresses, its permissions (r, w, x, and p for private or s for shared), and what backs it (a file, or nothing: "anonymous" memory).

The real lines behind the picture






The cost of fork. fork does not copy memory; it copies the page tables that describe it (section 4) and marks every page read-only and shared, so a page is copied only when one side writes to it: copy-on-write. Copying page tables is still work proportional to the memory in use.  A process with tens of gigabytes resident (a big model in CPU memory) pays proportionally more on every fork.


Threads, states, zombies and orphans


A thread is a second flow of execution inside the same process: its own registers and stack, but the same address space, files and PID group. On Linux, processes and threads are both made by one system call, clone(), whose flags say what to share; the {{Syscall tracer|#t-trace}} tab shows the exact flags for import torch's thread pool and for the DataLoader's workers. Threads are cheaper to create and communicate through shared memory; processes are isolated, so a crash or a leak in one does not take the others down, and in CPython each process has its own GIL.


A process is running (on a CPU), runnable (waiting for one), sleeping (waiting for an event; S in ps if a signal can wake it, D if it cannot, usually because it is inside a device or network file system operation), stopped (T), or a zombie (Z): it has exited but its parent has not yet called wait(), so its PID and exit status are kept. A child whose parent dies is an orphan, and is adopted by PID 1 (or the nearest "subreaper"), which is expected to wait() for it. Inside a container your script is often PID 1 itself, and a Python script does not reap orphans it did not start: a crashed DataLoader can leave zombie workers behind. The {{Debug lab|#t-debug}} reproduces this; the usual fix is a tiny init process (docker run --init, or tini).


In a training job


Start methods. Python's multiprocessing, which the PyTorch DataLoader uses for its workers, can start a child in three ways:




MethodWhat happensGoodBad



forkfork() only: the child is a copy of the parent at that momentInstant; the dataset object and everything built so far are already thereUnsafe if the parent has threads (only the calling thread is copied, so a lock another thread held stays locked forever in the child) or has initialised CUDA


spawna fresh Python interpreter (fork then exec, or posix_spawn), which re-imports your main module and receives the pickled datasetClean child, safe with threads and CUDASlow (every worker re-imports torch); needs if __name__ == "__main__":; everything passed must pickle


forkservera single clean "server" process is started once (like spawn); each new worker is forked from itSafe, and faster than spawn after the firstStill pickles arguments; the server costs one interpreter start




Which one you get by default depends on the Python version and the platform: on Linux, fork through Python 3.13 and forkserver from 3.14 ("On POSIX platforms the default start method was changed from fork to forkserver to retain the performance but avoid common multithreaded process incompatibilities", {{Python 3.14 docs|https://docs.python.org/3.14/library/multiprocessing.html#contexts-and-start-methods}}); on macOS, spawn since 3.8, because "macOS system libraries may start threads" ({{Python 3.11 docs|https://docs.python.org/3.11/library/multiprocessing.html#contexts-and-start-methods}}). Since 3.12, os.fork() raises a DeprecationWarning when Python detects that the process has several threads. PyTorch's DataLoader follows the same defaults ({{torch.utils.data docs, 2.14|https://docs.pytorch.org/docs/stable/data.html#multi-process-data-loading}}). The running job uses Python 3.11 on Linux, so fork. Code that relies on fork-only behaviour, such as a global built at import and read by workers, changes behaviour on upgrading to 3.14: name the start method explicitly (multiprocessing_context=).


On the running job, time from iter(DataLoader) to the first batch was 0.021 s with fork against 0.836 s with spawn and 0.763 s with forkserver (medians of 7 runs each with 2 CPUs, 2026-10-05, recorded by the {{Syscall tracer|#t-trace}} tab in src/trace/raw/timing_first_batch.txt; that tab shows the spread and the system calls behind the difference). Spawn and forkserver pay for a fresh interpreter that re-imports torch. With a persistent_workers=True DataLoader that cost is paid once per run instead of once per epoch.


Fork after CUDA. A GPU runtime keeps threads, driver handles and device mappings that a forked child cannot inherit safely. PyTorch's documentation: "either the spawn or forkserver start method are required to use CUDA in subprocesses" ({{Multiprocessing best practices|https://docs.pytorch.org/docs/stable/notes/multiprocessing.html}}), and it calls the failure "poison fork". The usual trap is touching CUDA (even torch.cuda.is_available() on some versions, or moving a tensor to the GPU) in the parent before the DataLoader forks; keep the workers on the CPU and move batches to the GPU in the main process. not run here (no GPU).


torchrun is itself a parent process: it starts one worker process per GPU (--nproc-per-node), gives each its rank through environment variables (RANK, LOCAL_RANK, WORLD_SIZE), watches them, and if one fails it stops the rest and, if allowed, restarts the group. So a training node runs a small tree of processes: the launcher, one trainer per GPU, and each trainer's DataLoader workers.


Graceful preemption. On Kubernetes, deleting a pod makes the container runtime "send a TERM signal to process 1 inside each container", waits the grace period ("The default terminationGracePeriodSeconds setting is 30 seconds"), then sends SIGKILL to anything still running ({{Kubernetes, Pod Lifecycle|https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination}}). Slurm does the same with SIGCONT, SIGTERM, then SIGKILL after its configured KillWait ({{scancel(1)|https://slurm.schedmd.com/scancel.html}}), and torchrun's agent stops its workers with SIGTERM and a 30 s timeout before SIGKILL ({{torch.distributed.elastic agent|https://docs.pytorch.org/docs/stable/elastic/agent.html}}). Note "process 1": if your container starts sh -c "python train.py", the shell is PID 1 and may not pass the signal on, so the job never hears it and is killed 30 s later. The running job installs a SIGTERM handler that only sets a flag; the training loop notices the flag after the current step, writes a checkpoint (section 7) and exits 0. Doing the checkpoint inside the handler itself is a classic bug: a Python handler does not run when the signal arrives; "the low-level signal handler sets a flag which tells the virtual machine to execute the corresponding Python signal handler at a later point (for example, at the next bytecode instruction)", always in the main thread, and "Synchronization primitives such as threading.Lock should not be used within signal handlers" ({{Python signal docs|https://docs.python.org/3/library/signal.html#execution-of-python-signal-handlers}}). A long torch.save inside the handler can deadlock or run while the model is half-updated. The {{Debug lab|#t-debug}} shows a job that ignores SIGTERM and the fix.
