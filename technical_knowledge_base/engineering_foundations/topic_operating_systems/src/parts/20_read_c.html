3. Scheduling: more runnable threads than CPUs

The running job alone has a main thread, PyTorch's operator threads, two worker processes and some helpers, on 5 CPUs shared with other containers. The scheduler decides which thread runs on which CPU and for how long. It gets control because the kernel programs a timer interrupt at boot; a switch saves one thread's registers into its kernel record and loads another's (a context switch, section 1). OSTEP builds policies up from FIFO (run in arrival order: a long job delays everyone behind it), through SJF and STCF (excellent turnaround, but they need to know job lengths) and round robin (good response, poor turnaround), to the multi-level feedback queue, which learns from behaviour; the {{OS simulators|#t-sim}} run all of them on the same jobs. Linux shares CPUs in proportion to weight instead: CFS from 2.6.23, EEVDF since 6.6, with nice from -20 to 19 picking the weight.

The distinction that matters for a training job: a CPU limit is a stop, not fewer CPUs. A container's limit is a cgroup quota per period: with --cpus 2 the file cpu.max reads 200 ms per 100 ms period, spendable on any of the 5 CPUs. Five busy threads spend it in the first 40 ms and are then throttled, not scheduled at all, for the remaining 60 ms; cpu.stat's nr_throttled counts the periods. Python and PyTorch's default thread pool still see 5 CPUs, so size torch.set_num_threads and num_workers from the quota, not from os.cpu_count(). A starving GPU is often this: workers that cannot produce batches as fast as the GPU consumes them. Kubernetes CPU limits become exactly this quota (requests become a relative weight, cpu.weight), which is why some clusters set CPU requests but no CPU limit on training pods.

4. Virtual memory: a private, huge memory for every process

Every address a program uses is a virtual address. On every load and store the MMU translates it, page by page (4 KiB here), through a per-process page table: a tree of four levels of 512 entries on ARM64 and x86-64 with 48-bit addresses. The TLB caches recent translations, so a hit costs nothing and a miss costs a walk. The kernel fills the tree lazily: allocating memory or mapping a file only records a promise, and the first touch of each page traps as a page fault. File pages live in the page cache, which mmap maps straight into the process (how np.memmap and safetensors read without copying). After fork, parent and child share every page read-only until one writes (copy-on-write), and Python's reference counts turn reads into writes. When memory runs out the kernel reclaims cache, may swap, and finally the OOM killer sends SIGKILL: inside a container the job vanishes with exit code 137 (128 + 9), no traceback.

The distinction across the children: memory promised, resident, shared and private are four different numbers. VSZ counts what was promised (the job reserves 1 GiB it never touches; this lab's VM overcommits), RSS what is resident, counting shared pages once per process, PSS divides each shared page among its sharers, USS is what only this process holds. For the running job's three processes, 815 MiB of RSS were 345 MiB of PSS, so summing workers' RSS overstates memory; and RSS also counts what allocators hold but no longer use (section 5).

Depth: what a TLB miss costs here, measured with a pointer chase

measured here (src/read/code/tlb.c, median of 5 runs): a pointer chase visits N cache lines in random order. Packed, the N lines sit side by side and fit in few pages; spread, each line sits in its own 4 KiB page, so every access needs a different translation; a third run spreads the lines the same way inside memory advised to use 2 MiB transparent huge pages. Same number of cache lines, so the gap between the runs is mostly translation. Nanoseconds per access, packed, spread and spread on huge pages: 1.01, 3.08 and 1.00 at 256 lines; 1.01, 8.03 and 6.90 at 1,024; 5.70, 33.64 and 8.37 at 4,096; 7.22, 76.09 and 46.67 at 32,768. Huge pages remove most of the miss cost until they too run out of TLB reach. In this VM a miss is also a two-stage walk (the guest's tables, then the hypervisor's), dearer than on bare metal. The {{OS simulators|#t-sim}} time the same effect per page and replay OSTEP's TLB homework; {{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}}, section 3, explains reach.

5. Allocators: between your tensors and the kernel's pages

The kernel hands out memory in whole pages and only through system calls; programs ask for millions of small, short-lived pieces. A user-space allocator sits in between: it gets large regions rarely (brk or mmap), cuts them into pieces often, and keeps freed pieces for reuse. One training job runs several: pymalloc for small Python objects, glibc's malloc (with an arena per thread, roughly) for NumPy and C extensions, mimalloc inside PyTorch's Linux arm64 wheels for CPU tensors, and on a GPU PyTorch's caching allocator, which keeps freed GPU blocks instead of returning them to the driver.

The distinction: freed is not returned. Freed memory stays with the allocator until a whole page, arena or segment is empty, so RSS measures what allocators hold, and free memory in the wrong-shaped pieces is fragmentation. The same shape appears one level up on the GPU: "CUDA out of memory" with gigabytes reserved by PyTorch but no single free block large enough, which PyTorch's own message answers with expandable_segments:True. torch.cuda.memory_allocated() counts live tensors, memory_reserved() everything the cache holds.
