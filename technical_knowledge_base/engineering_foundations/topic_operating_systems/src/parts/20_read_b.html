1. What an operating system is and does

ch. 2 Introduction, ch. 6 Limited Direct Execution

The problem. A computer has a few CPUs, one physical memory, and devices (disks, network cards, GPUs). Dozens of programs want to use them at once, none of them trusts the others, and none of them wants to know how an NVMe drive is programmed. Something has to share the hardware fairly, stop one program from reading or corrupting another's memory, and offer one simple interface ("open this file, give me memory, start a thread") over every kind of device. That something is the kernel, the core of the operating system that runs with full control of the hardware. (The "operating system" in everyday speech also includes the libraries, shells and tools around the kernel; on this page Linux means the kernel.)

What the kernel owns. Five things: CPU time (who runs, on which core, for how long), memory (which physical bytes belong to which program), devices (disks, network cards, GPUs, each driven by a piece of kernel code called a driver), files (names, directories and permissions on top of raw storage) and the network (sockets, TCP, see {{Topic: protocols|n:3c65c17b0d0d81ec9355f4eecd6eed02}}). A program never touches any of them directly.

User mode, kernel mode, and the one door between them

The CPU itself enforces the separation. It always runs in one of (at least) two privilege modes: user mode, where your program runs and any attempt to touch a device, change the memory map or disable interrupts is refused by the hardware, and kernel mode, where the kernel runs with no restrictions. On ARM64 (the M1 this page was measured on, and many cloud servers) these are called exception levels EL0 and EL1; on x86-64 they are rings 3 and 0. A program that needs something privileged makes a system call: it puts a call number and arguments in registers and executes one special instruction (svc #0 on ARM64, syscall on x86-64), which switches the CPU to kernel mode and jumps to a fixed entry point the kernel chose at boot. The kernel checks the request, does the work on the program's behalf, and returns to user mode at the next instruction. There is no other way in: no function call, no pointer, reaches kernel code. OSTEP calls this limited direct execution: your program runs directly on the CPU at full speed, but limited, with the kernel regaining control at every system call, fault and timer interrupt.

The cost. Crossing the boundary is cheap but not free: the CPU saves the program's registers, switches stacks, and on current CPUs the kernel also flushes or isolates some predictor state as protection against side-channel attacks like Spectre. Measured here, a call to an ordinary function takes about a nanosecond while the cheapest real system call takes a few hundred: a ratio in the hundreds. That one ratio explains several habits of fast code: buffered I/O (collect many small writes in user memory, then make one write()), reading files in large chunks rather than byte by byte, and the vDSO, a small piece of kernel-provided code mapped into every process so that asking for the time (clock_gettime, which Python's time.perf_counter() calls) never enters the kernel at all. The {{Syscall tracer|#t-trace}} tab shows buffered against unbuffered writes on the same job.

How a language runtime sits on top

Python, C++, Rust and Node.js do not talk to the kernel in their own ways: they all end in the same few hundred system calls. On Linux the usual path is through the C library (libc, here GNU glibc), which wraps each system call in a C function (read(), mmap(), clone()):
