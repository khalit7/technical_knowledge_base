1. The boundary, and what each crossing costs

A computer has a few CPUs, one physical memory and some devices; dozens of programs want them at once, none trusts the others, and none wants to know how an NVMe drive is programmed. The kernel owns five things on their behalf: CPU time, memory, devices (each run by a driver), files and the network (sockets and TCP: {{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}}). A program never touches any of them directly. It runs on the CPU at full speed in user mode, and the kernel regains control only at a system call, a fault or a timer interrupt; OSTEP calls this limited direct execution. Every subsystem in the table above is a kind of crossing, and the children measure what each one costs.

The ratio between a function call and the cheapest system call, in the hundreds, explains buffered I/O, large reads, and the vDSO (kernel code mapped into every process so that asking the time never enters the kernel).

Python, C++, Rust and Node do not talk to the kernel in their own ways: they all end in the same few hundred system calls, usually through the C library (glibc here). The {{Syscall tracer|#t-trace}} records every call of the running job and traces one small file read in five languages.

2. Processes and threads: the unit the kernel runs

A process is a program in execution: an address space (its private memory), registers, a table of open file descriptors (small integers naming files, pipes and sockets; 0, 1 and 2 are stdin, stdout and stderr), credentials and a PID. Unix builds every process from four calls: fork() copies the caller, exec() replaces the program inside the process, wait() collects a child's exit status, exit() ends it; a shell running python train.py is fork, exec in the child, wait in the parent. A signal interrupts a process with a small numbered message: SIGTERM asks it to stop (what Kubernetes, Slurm and spot preemption send first), SIGKILL stops it and cannot be caught. The kernel publishes each process's state as text under /proc/<pid>/; ps and top only read it.

The distinction that runs through every child: process or thread. On Linux both are made by clone(), whose flags say what to share. Threads share memory, so they are cheap and need locks ({{Concurrency|n:3f05c17b0d0d8112ad1af99308fa913f}}); processes are isolated, so a crash or a leak in one does not take the others down and, in CPython, each has its own GIL. A training node is a small tree of both: torchrun, one trainer process per GPU, each trainer's operator threads, and its DataLoader worker processes. How the workers start changes their cost: on the running job, time from iter(DataLoader) to the first batch was 0.021 s with fork against 0.836 s with spawn and 0.763 s with forkserver (medians of 7 runs each with 2 CPUs, 2026-10-05, in src/trace/raw/timing_first_batch.txt); spawn and forkserver pay for a fresh interpreter that re-imports torch. Linux's default is fork through Python 3.13 and forkserver from 3.14; fork is cheap because it copies page tables, not pages ({{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}}, section 7), and unsafe once the parent has threads or has initialised CUDA.

Depth: the three start methods, and which one you get

Python's multiprocessing, which the PyTorch DataLoader uses for its workers, can start a child in three ways:

MethodWhat happensGoodBad
forkfork() only: the child is a copy of the parent at that momentInstant; the dataset object and everything built so far are already thereUnsafe if the parent has threads (only the calling thread is copied, so a lock another thread held stays locked forever in the child) or has initialised CUDA
spawna fresh Python interpreter (fork then exec, or posix_spawn), which re-imports your main module and receives the pickled datasetClean child, safe with threads and CUDASlow (every worker re-imports torch); needs if __name__ == "__main__":; everything passed must pickle
forkservera single clean "server" process is started once (like spawn); each new worker is forked from itSafe, and faster than spawn after the firstStill pickles arguments; the server costs one interpreter start

Which one you get by default depends on the Python version and the platform: on Linux, fork through Python 3.13 and forkserver from 3.14 ("On POSIX platforms the default start method was changed from fork to forkserver to retain the performance but avoid common multithreaded process incompatibilities", {{Python 3.14 docs|https://docs.python.org/3.14/library/multiprocessing.html#contexts-and-start-methods}}); on macOS, spawn since 3.8, because "macOS system libraries may start threads" ({{Python 3.11 docs|https://docs.python.org/3.11/library/multiprocessing.html#contexts-and-start-methods}}). Since 3.12, os.fork() raises a DeprecationWarning when Python detects that the process has several threads. PyTorch's DataLoader follows the same defaults ({{torch.utils.data docs, 2.14|https://docs.pytorch.org/docs/stable/data.html#multi-process-data-loading}}). The running job uses Python 3.11 on Linux, so fork. Code that relies on fork-only behaviour, such as a global built at import and read by workers, changes behaviour on upgrading to 3.14: name the start method explicitly (multiprocessing_context=).
