7. Persistence: getting a checkpoint safely onto disk

ch. 36 I/O Devices, ch. 39 Files and Directories, ch. 40 File System Implementation, ch. 42 FSCK and Journaling, ch. 44 Flash-based SSDs, ch. 49 NFS

The problem. Memory forgets everything on a crash or power loss; a training run that loses its checkpoint loses days. But devices are slow and work in large blocks, so the OS hides them behind a cache and writes later. The whole difficulty of persistence is in that "later": what exactly is on the device when the machine dies?

Devices and drivers, in one picture

A storage device (an NVMe SSD, a network block device in the cloud) is controlled by a driver in the kernel, which places requests in queues the device reads by DMA and learns of completion through an interrupt. Above the driver the kernel offers a block device: an array of fixed-size blocks (/dev/nvme0n1). Above that a file system (ext4, XFS) turns blocks into files, directories, names and permissions, and keeps its own bookkeeping (inodes: the record of a file's size, owner and block locations; directories: tables from names to inodes). Above that, the page cache (section 4) holds file data in memory. A write() stops at the page cache.

A write's journey

Below, the running job's checkpoint (here a 64 MiB file, the size of a small model's state) is written two ways. The counters are real: the system-wide Dirty line of /proc/meminfo (page-cache data not yet on the device) and the time of each call, measured here.

Why "later" can be 30 seconds. The kernel's flusher threads wake every 5 seconds and write out dirty data older than 30 seconds, and start writing earlier when dirty data passes 10% of available memory (in the background) or 20% (then the writing process must write back itself and slows down): dirty_writeback_interval = 5 * 100, dirty_expire_interval = 30 * 100 centiseconds, dirty_background_ratio = 10, vm_dirty_ratio = 20 (mm/page-writeback.c lines 74 to 109, v6.12; this lab's /proc/sys/vm shows the same values). So after torch.save returns, a crash in the next half minute can lose the checkpoint, and with the naive pattern the previous one is already gone.

The three calls that make it safe. fsync(fd) returns only when the file's data and metadata are on the device. It does not cover the file's name: "Calling fsync() does not necessarily ensure that the entry in the directory containing the file has also reached disk. For that an explicit fsync() on a file descriptor for the directory is also needed" ({{fsync(2)|https://man7.org/linux/man-pages/man2/fsync.2.html}}). rename(tmp, final) swaps names atomically: "If newpath already exists, it will be atomically replaced, so that there is no point at which another process attempting to access newpath will find it missing" ({{rename(2)|https://man7.org/linux/man-pages/man2/rename.2.html}}). Together: a reader, or a restart after a crash, sees either the whole old checkpoint or the whole new one. The running job's save_checkpoint does exactly this, and the {{Syscall tracer|#t-trace}} tab shows the system calls of both patterns on the real job.

Two real stories
2009, ext4's zero-length files. With delayed allocation, ext4 wrote file data much later than its rename; after crashes, users found "pretty much any file written to by any application (during the previous boot) was 0 bytes". Ted Ts'o's answer: applications had come to depend on ext3's behaviour "even though POSIX never really made any such guarantee"; ext4 then added a heuristic that forces the data out when a file is renamed over another ({{LWN, 2009-03-11|https://lwn.net/Articles/322823/}}). Do not rely on that heuristic: call fsync.
2018, fsyncgate. PostgreSQL assumed that a successful fsync meant everything written since the last one was safe. After a device error, Linux could report the error once and mark the pages clean, so a retried fsync succeeded with the data lost ({{LWN, 2018-04-18|https://lwn.net/Articles/752063/}}). Lesson for checkpoints: if fsync fails, treat that checkpoint as lost and write it again from memory; never just retry the fsync.

Journaling, direct I/O, and storage you do not own

Journaling. Creating or renaming a file updates several blocks (the directory, the inode, the free-block bitmap); a crash between them leaves the file system inconsistent, which old systems repaired with a full scan (fsck). A journal writes the intended changes to a log first and only then in place, so after a crash the log is replayed or discarded in seconds. ext4's default data=ordered: "All data are forced directly out to the main file system prior to its metadata being committed to the journal" ({{ext4 docs|https://docs.kernel.org/admin-guide/ext4.html}}). Journaling protects the file system's structure, not your file's contents: that is still fsync's job. The {{OS simulators|#t-sim}} tab crashes a write at every step with and without a journal; the write-ahead log of the {{databases topic|n:3cd5c17b0d0d815d8841ec845f5f3324}} is the same idea in a database.

Direct I/O. Opening a file with O_DIRECT bypasses the page cache: transfers go straight between your buffer and the device, with alignment rules. Databases and some checkpoint writers use it to avoid filling memory with data they will not read again, and to make write timing predictable.

Network and parallel file systems, and object storage. On a cluster the checkpoint directory is rarely a local disk. NFS exports one server's file system over the network, and its caching makes close-to-open the only consistency you can rely on. Lustre and similar parallel file systems stripe each file across many storage servers so thousands of GPUs can read and write at once, at the cost of slow metadata operations (opening millions of small files hurts). Object storage (S3, GCS) has no rename or fsync at all: an object is written whole and appears atomically when the upload completes, so "write then rename" becomes "upload to a new key, then update a pointer". Checkpoint libraries hide these differences; knowing them explains their options.

In a training job

  • Data loading throughput. Reading a dataset cold from storage is the page-fault table of section 4 at scale: readahead and large sequential reads matter, and many small files are slow on network file systems. Sharded formats (WebDataset tar shards, Arrow or Parquet files, memory-mapped token arrays) exist to turn many small reads into few big ones. The {{Debug lab|#t-debug}} measures cold against warm reads and a throttled device.
  • Sharded and asynchronous checkpoints. A large model is saved by every rank writing its own shard in parallel, and asynchronously: the state is first copied to CPU memory, training resumes, and a background thread writes and fsyncs (PyTorch's {{distributed checkpoint|https://docs.pytorch.org/docs/stable/distributed.checkpoint.html}} offers async_save). The same atomicity rule applies to the whole set: write a marker, or rename a directory, only when every shard is durable. The {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}} and {{Training Infrastructure|n:3c65c17b0d0d81c9b2cac997583bf572}} pages cover checkpoint strategy.
  • GPUDirect Storage not run here: NVIDIA's path that "enables a direct data path for direct memory access (DMA) transfers between GPU memory and storage, which avoids a bounce buffer through the CPU" ({{GDS overview guide|https://docs.nvidia.com/gpudirect-storage/overview-guide/index.html}}): the device writes into GPU memory without passing through the page cache and pinned host memory.
