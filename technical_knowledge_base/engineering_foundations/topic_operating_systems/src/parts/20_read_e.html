8. Containers: one kernel, many private views

A container is ordinary processes on the host's kernel, started with four kinds of restriction: namespaces (what it can see: its own PIDs, mounts, network, hostname, IPC, users), cgroups (how much it may use: CPU quota, memory limit, PIDs, I/O), capabilities and seccomp (what it may do: root's powers split up and mostly dropped, every system call checked against an allowlist at kernel entry), and an image (what files it has: read-only layers plus one writable layer, merged by overlayfs as its root).

The distinction: a container is not a VM. There is no second kernel, so a container keeps well-behaved jobs apart but a kernel bug reachable through an allowed system call is a way out; untrusted code goes in gVisor (a user-space kernel) or a microVM such as Firecracker. Read from inside one of this topic's containers (docker run --cpus 2 --memory 3g --pids-limit 256): ps sees two processes with the shell as PID 1, 14 capabilities remain, Seccomp: 2 means a filter is active, the root file system is overlay, and the limits are plain files under /sys/fs/cgroup. Reaching memory.max runs the OOM killer inside the cgroup (exit 137, OOMKilled, counted in memory.events); a GPU image brings the CUDA runtime and PyTorch, the host brings the driver.

9. Virtual machines and the GPU driver stack

A hypervisor (KVM, Xen, the cloud providers' own, Apple's Hypervisor.framework under Docker Desktop) runs whole guest operating systems, each believing it owns a machine; the CPU helps with an extra privilege level and a second layer of page tables from guest-physical to host-physical addresses. A cloud GPU instance is almost always such a guest, and this lab is one too: its cross-CPU wake-ups and TLB misses are dearer than on bare metal. The IOMMU translates and checks every DMA address a device issues, which is what lets a whole GPU be passed to one VM; MIG, MPS and time slicing share one GPU among jobs.

The distinction: the hot path never asks permission. Guest code runs directly on the CPU and exits to the hypervisor only at boundaries; a CUDA kernel launch goes from PyTorch through the runtime (libcudart, in your wheel) to the user-mode driver (libcuda, installed with the host's driver), which writes commands into memory the GPU reads and rings a doorbell, while the kernel driver (nvidia.ko) is entered by ioctl only for setup, allocation and errors. The Python call returns long before the GPU finishes, because launches are asynchronous until something waits (.item(), .cpu(), torch.cuda.synchronize()); an strace -f of a CUDA PyTorch program shows a burst of openat("/dev/nvidia..."), mmap and ioctl calls at start-up and very few during steady training. So the two version numbers come from two places: the driver from the host (nvidia-smi), the runtime from the image (torch.version.cuda); "CUDA driver version is insufficient for CUDA runtime version" means a new image on an old host.
