4. Virtual memory: a private, huge memory for every process

ch. 13 Address Spaces, ch. 15 Address Translation, ch. 18 Introduction to Paging, ch. 19 Translation Lookaside Buffers, ch. 20 Advanced Page Tables, ch. 21 and 22 Swapping, ch. 23 Complete VM Systems

The problem. Every process in section 2 believed it owned addresses from 0 up to about 248, and the three processes of the job used the very same addresses for different data. Physical memory is one shared array of about 10 GB here. Something has to map each process's addresses onto real memory, keep processes from seeing each other's, let them share what should be shared (library code, the dataset), and let the total promised exceed what exists.

Pages and page tables. Memory is managed in fixed-size pages, 4 KiB here (getconf PAGESIZE prints 4096). Every address a program uses is a virtual address; the hardware's memory management unit (MMU) translates it, on every single load and store, into a physical address. The low 12 bits (the offset inside a 4 KiB page) pass through unchanged; the high bits name a virtual page, which a per-process page table maps to a physical page frame, along with permission bits (read, write, execute, user or kernel). A flat table for 236 virtual pages would be huge, so it is a tree: on ARM64 and x86-64 with 4 KiB pages and 48-bit addresses, four levels of 512 entries each, using 9 bits of the address per level. Switching processes (section 3) means pointing the MMU at a different tree.

The TLB. Walking four levels of table in memory on every access would make every load five loads. The CPU caches recent translations in a small, fast translation lookaside buffer (TLB). A hit costs nothing extra; a miss costs a page-table walk. What a miss costs, measured. A pointer chase visits N cache lines in random order. Packed, the N lines sit side by side and fit in few pages; spread, each line sits in its own 4 KiB page, so every access needs a different translation. Same number of cache lines, so the gap between the two curves is mostly translation. The third curve spreads the lines the same way inside memory advised to use 2 MiB transparent huge pages.

Page faults: memory on demand

The kernel does not fill in page tables in advance. Allocating memory or mapping a file only records a promise (a mapping, as in section 2's maps); the first access to each page finds no valid entry and traps into the kernel: a page fault. The kernel finds or makes the page, fills in the entry and resumes the instruction. A minor fault needs no I/O (a zeroed page for new memory, or a file page already in memory); a major fault must read the device ("page faults serviced that required I/O activity", {{getrusage(2)|https://man7.org/linux/man-pages/man2/getrusage.2.html}}). mmap and the page cache

The kernel keeps recently used file data in otherwise free memory, the page cache; read() copies from it, and mmap maps its pages straight into your address space, so the dataset's bytes are never copied at all: np.memmap, safetensors and llama.cpp's weight loading (Part 3 of the {{C++ page|n:3cd5c17b0d0d81ceadcee44fe9c023a0}}) all work this way. A mapping is MAP_SHARED (writes go to the file, other mappers see them) or MAP_PRIVATE, "a private copy-on-write mapping" ({{mmap(2)|https://man7.org/linux/man-pages/man2/mmap.2.html}}). That is why free shows "buff/cache" as large and "available" as much bigger than "free": cached file pages are given back whenever a program needs the memory.

Copy-on-write, and the DataLoader memory leak that is not a leak

After fork, parent and children share every page read-only; the first write to a page by either side faults, and the kernel copies that one page (in the kernel source: __copy_present_ptes write-protects both sides at fork, mm/memory.c lines 955 to 958, and wp_page_copy, line 3331, makes the copy; Linux v6.12). Section 2 showed it on the real job. Python adds a twist: every object carries a reference count, and merely reading an object from a list increments and decrements it, which is a write to the page holding it. A Dataset that holds millions of Python objects (a list of file names, a dict of labels) is copied page by page into every worker as the epoch touches it, so worker memory climbs towards the parent's. PyTorch's documentation: "the loader worker processes will consume the same amount of CPU memory as the parent process for all Python objects in the parent process which are accessed from the worker processes... The simplest workaround is to replace Python objects with non-refcounted representations such as Pandas, Numpy or PyArrow objects" ({{torch.utils.data|https://docs.pytorch.org/docs/stable/data.html#multi-process-data-loading}}; {{issue 13246, opened 2018-10-29|https://github.com/pytorch/pytorch/issues/13246}}). The {{OS simulators|#t-sim}} tab animates it page by page and the {{Debug lab|#t-debug}} measures it per worker.

Huge pages, overcommit, swap and the OOM killer

Huge pages. One 2 MiB page replaces 512 small ones: one TLB entry instead of 512, one fewer level to walk. Linux can do this transparently (THP) for anonymous memory; here it is set to "madvise", so only ranges marked with madvise(MADV_HUGEPAGE) get them ({{transhuge doc|https://docs.kernel.org/admin-guide/mm/transhuge.html}}). The running job does exactly that: it reserves 1 GiB of address space and marks it MADV_HUGEPAGE (the {{Syscall tracer|#t-trace}} tab shows the calls and which library makes them). The cost: a huge page must be found or assembled from 512 free contiguous small pages, which can stall an allocation, and a mostly empty huge page wastes memory.

Overcommit. Linux lets processes reserve more memory than exists, betting that much of it will never be touched: overcommit_memory 0 is the default heuristic, 1 "always overcommit, never check", 2 "always check, never overcommit" ({{proc_sys_vm(5)|https://man7.org/linux/man-pages/man5/proc_sys_vm.5.html}}). This lab's VM runs with 1, which is why the job's 1 GiB reservation and every 64 MiB malloc arena cost nothing until touched.



Swap and the OOM killer. When memory runs out, the kernel first reclaims page cache, then may write anonymous pages to swap (disk), which turns memory accesses into disk reads and a fast job into a crawling one. If it still cannot find memory, the OOM killer picks a process and kills it with SIGKILL: the one with the highest badness, roughly the share of memory it uses, adjusted by oom_score_adj from -1000 (never) to +1000 ({{proc(5) section 3.1|https://docs.kernel.org/filesystems/proc.html}}; oom_badness, mm/oom_kill.c line 202, v6.12). In a container the same happens inside its cgroup when it reaches memory.max (section 8): the job just disappears with exit code 137 (128 + 9, SIGKILL), with no Python traceback. The {{Debug lab|#t-debug}} reproduces it next to a Python MemoryError.


NUMA and pinned memory not run here


NUMA. A server with two CPU sockets has two memory banks; each socket reaches its own bank faster than the other's (non-uniform memory access). By default Linux allocates a page on the node of the CPU that first touches it (MPOL_DEFAULT in {{set_mempolicy(2)|https://man7.org/linux/man-pages/man2/set_mempolicy.2.html}}), so a DataLoader worker or a GPU's feeding process on the wrong socket reads every batch across the interconnect. numactl --hardware lists the nodes; inside this lab it reports none (a single-socket laptop VM), so the CPU and memory hardware is left to the {{hardware topic|n:3c65c17b0d0d8118beeefaed56da6f8e}}.


Pinned memory. A GPU copies from host memory by DMA (direct memory access, the device reading RAM itself), which needs the physical pages to stay put; ordinary pages could be swapped or moved. So CUDA copies first into pinned (page-locked) memory, which the kernel promises never to move or swap (the mechanism behind {{mlock(2)|https://man7.org/linux/man-pages/man2/mlock.2.html}}). "Host to GPU copies are much faster when they originate from pinned (page-locked) memory", so DataLoader(pin_memory=True) puts batches there directly ({{torch.utils.data, memory pinning|https://docs.pytorch.org/docs/stable/data.html#memory-pinning}}). Pinned memory is taken out of the pool the kernel can reclaim, so pinning too much starves the rest of the machine.
