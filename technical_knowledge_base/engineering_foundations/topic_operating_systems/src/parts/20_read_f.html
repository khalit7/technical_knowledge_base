5. Allocators: between your tensors and the kernel's pages

ch. 14 Interlude: Memory API, ch. 17 Free-Space Management

The problem. The kernel hands out memory in whole pages and only through system calls (section 1), which cost hundreds of nanoseconds. Programs ask for millions of small, short-lived pieces: a 56-byte Python integer, a 2 KB string, a 1 MB tensor. A user-space allocator sits in between: it gets large regions from the kernel rarely, cuts them into pieces for malloc often, and keeps freed pieces for reuse. Its job is to be fast, to waste little, and to not get in the way of threads.

Where glibc's malloc gets memory. Two kernel interfaces. The heap is one region just after the program's data, grown by moving its end (the "program break") with brk. Large requests instead get their own anonymous mmap, which can be returned to the kernel independently on free. The switch point is M_MMAP_THRESHOLD, whose "initial value ... is 128*1024" and which glibc then adjusts dynamically ({{mallopt(3)|https://man7.org/linux/man-pages/man3/mallopt.3.html}}). Traced here: a 64 KiB request grows the heap, a 200 KiB one gets its own mapping and gives it back on free.

Arenas: one heap per thread, roughly. If every thread shared one heap, every malloc would take a lock. glibc gives threads separate arenas, up to a limit computed from the CPU count, each a 64 MiB reservation on 64-bit (HEAP_MAX_SIZE (2 * DEFAULT_MMAP_THRESHOLD_MAX), malloc/arena.c line 31, with the threshold maximum 4 * 1024 * 1024 * sizeof(long), malloc/malloc.c line 972, glibc 2.36, the version in this image). You can see them in section 2's maps: when the DataLoader started, three new pairs appeared in the main process, each 132 KiB readable and writable followed by 65,404 KiB with no access: 64 MiB reserved, 132 KiB used. Reservations cost nothing until touched (overcommit, section 4), but a long-running multi-threaded server can hold freed memory in many arenas: the usual cure is MALLOC_ARENA_MAX=2 or a different allocator.


Fragmentation. After many allocations and frees of mixed sizes, free memory is scattered in holes between live blocks: there may be plenty free in total but no single hole big enough. That is external fragmentation; rounding requests up to size classes wastes the rest of each block (internal fragmentation). OSTEP ch. 17 covers the classic strategies (best fit, first fit, segregated lists, buddy allocation).


Other allocators. jemalloc (FreeBSD, Meta) and tcmalloc (Google) use per-thread caches and size classes to cut lock contention and fragmentation; swapping one in for glibc's needs no code change (LD_PRELOAD=libjemalloc.so python train.py), which is a common fix for slowly growing memory in data-loading and serving processes. CPython has its own layer on top: "a pymalloc allocator optimized for small objects (smaller or equal to 512 bytes) with a short lifetime. It uses memory mappings called arenas with a fixed size of either 256 KiB on 32-bit platforms or 1 MiB on 64-bit platforms" ({{Python memory management|https://docs.python.org/3.11/c-api/memory.html#the-pymalloc-allocator}}). A Python process whose objects were freed may keep its pymalloc arenas because one live object pins each one, which is why memory often does not drop after del. PyTorch itself brings a third: its Linux arm64 wheels build mimalloc into libc10.so for CPU tensors, and mimalloc's arena reservation is section 4's 1 GiB MADV_HUGEPAGE range; the x86-64 wheels use glibc's malloc ({{Memory allocators|n:3f05c17b0d0d81209ae9d856695dc958}} compares them on this job).

not run here (no GPU). Asking the CUDA driver for memory (cudaMalloc) and returning it is slow and synchronises the device, so PyTorch keeps freed GPU blocks in a cache and reuses them: "PyTorch uses a caching memory allocator to speed up memory allocations... However, the unused memory managed by the allocator will still show as if used in nvidia-smi" ({{CUDA semantics|https://docs.pytorch.org/docs/stable/notes/cuda.html#memory-management}}). Two counters matter: torch.cuda.memory_allocated() (bytes in live tensors) and torch.cuda.memory_reserved() (everything the cache holds). The cache carves tensors out of large segments; when tensor sizes keep changing (variable sequence lengths, a changing batch size), segments become fragmented exactly as in OSTEP ch. 17, and an allocation can fail with gigabytes reserved but no single free block large enough. PyTorch's own error message spells it out:


CUDA out of memory. Tried to allocate <size>. GPU <n> has a total capacity of <total> of which <free> is free. ... Of the allocated memory <a> is allocated by PyTorch, and <r> is reserved by PyTorch but unallocated. If reserved but unallocated memory is large try setting PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True to avoid fragmentation.


The message as assembled in {{c10/cuda/CUDACachingAllocator.cpp lines 1930 to 1953 at v2.14.1|https://github.com/pytorch/pytorch/blob/v2.14.1/c10/cuda/CUDACachingAllocator.cpp#L1930}}; angle brackets mark the values it fills in.


The fix it names, expandable_segments ("experimental, default: False"), changes the allocator's strategy: "Instead of making one segment per allocation, it tries to make one segment (per stream) that grows as necessary", by reserving a large range of GPU virtual addresses and mapping physical memory into it as needed with CUDA's virtual memory calls (cuMemAddressReserve, cuMemCreate, cuMemMap: the comment above struct ExpandableSegment, lines 352 to 353 of the same file), so freed space at the end of a segment can be reused for a larger block instead of stranded. The same trick as virtual memory in section 4, one level up ({{CUDA semantics, optimizing memory usage|https://docs.pytorch.org/docs/stable/notes/cuda.html#optimizing-memory-usage-with-pytorch-cuda-alloc-conf}}). The environment variable's current name is PYTORCH_ALLOC_CONF; PYTORCH_CUDA_ALLOC_CONF is kept as an alias. torch.cuda.empty_cache() returns cached, unused blocks to the driver (useful when another process needs the GPU) but never frees memory held by live tensors. The details (memory snapshots, the allocator's pools, CUDA graphs) belong to the {{pytorch-ecosystem topic|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}}.
