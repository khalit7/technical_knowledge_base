Debug lab: training-job failures reproduced on a real Linux kernel

Each case below is a failure that ML training jobs really hit, reproduced on purpose in a container and recorded: the error exactly as it appears, the subsystem of the operating system behind it, the commands that pinpoint it with their real output, the cause, the fix, and where it bites in training. Three ways in: browse and filter the cases, follow the decision tree from a symptom, or drill: see a symptom and pick what you would check first.

Where and how this was run

Every output was recorded on 2026-10-05 in Docker containers on a laptop: Docker Desktop's Linux VM (kernel 5.10.104, arm64, 5 CPUs, about 10 GB of memory, cgroups v2, one NUMA node, no GPU), image kb-os-dbg:1 (the shared lab image kb-os-lab:1 with Python 3.11.2, torch 2.14.1 CPU build, numpy 2.4.6, plus pyarrow). No container was privileged; five added only CAP_SYS_PTRACE, for strace and py-spy. Each case's first grey line is the exact docker run that recorded it: the limits (--memory, --cpus, --shm-size, ...) are part of the experiment. Timings come from one run each on a shared VM and vary between runs; the shapes (which is slower, what dies, what the counters say) are what repeat. The CUDA case is quoted from PyTorch's source, not run. Scripts and raw recordings: src/debug/ (run_all.sh reruns everything); the page quotes them verbatim.
