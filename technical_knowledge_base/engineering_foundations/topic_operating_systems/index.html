1. What an operating system is and does

ch. 2 Introduction, ch. 6 Limited Direct Execution

The problem. A computer has a few CPUs, one physical memory, and devices (disks, network cards, GPUs). Dozens of programs want to use them at once, none of them trusts the others, and none of them wants to know how an NVMe drive is programmed. Something has to share the hardware fairly, stop one program from reading or corrupting another's memory, and offer one simple interface ("open this file, give me memory, start a thread") over every kind of device. That something is the kernel, the core of the operating system that runs with full control of the hardware. (The "operating system" in everyday speech also includes the libraries, shells and tools around the kernel; on this page Linux means the kernel.)

What the kernel owns. Five things: CPU time (who runs, on which core, for how long), memory (which physical bytes belong to which program), devices (disks, network cards, GPUs, each driven by a piece of kernel code called a driver), files (names, directories and permissions on top of raw storage) and the network (sockets, TCP, see Topic: protocols). A program never touches any of them directly.

User mode, kernel mode, and the one door between them

The CPU itself enforces the separation. It always runs in one of (at least) two privilege modes: user mode, where your program runs and any attempt to touch a device, change the memory map or disable interrupts is refused by the hardware, and kernel mode, where the kernel runs with no restrictions. On ARM64 (the M1 this page was measured on, and many cloud servers) these are called exception levels EL0 and EL1; on x86-64 they are rings 3 and 0. A program that needs something privileged makes a system call: it puts a call number and arguments in registers and executes one special instruction (svc #0 on ARM64, syscall on x86-64), which switches the CPU to kernel mode and jumps to a fixed entry point the kernel chose at boot. The kernel checks the request, does the work on the program's behalf, and returns to user mode at the next instruction. There is no other way in: no function call, no pointer, reaches kernel code. OSTEP calls this limited direct execution: your program runs directly on the CPU at full speed, but limited, with the kernel regaining control at every system call, fault and timer interrupt.

The cost. Crossing the boundary is cheap but not free: the CPU saves the program's registers, switches stacks, and on current CPUs the kernel also flushes or isolates some predictor state as protection against side-channel attacks like Spectre. Measured here, a call to an ordinary function takes about a nanosecond while the cheapest real system call takes a few hundred: a ratio in the hundreds. That one ratio explains several habits of fast code: buffered I/O (collect many small writes in user memory, then make one write()), reading files in large chunks rather than byte by byte, and the vDSO, a small piece of kernel-provided code mapped into every process so that asking for the time (clock_gettime, which Python's time.perf_counter() calls) never enters the kernel at all. The Syscall tracer tab shows buffered against unbuffered writes on the same job.

2. Processes: the running program

ch. 4 The Abstraction: The Process, ch. 5 Interlude: Process API, ch. 26 Concurrency: An Introduction

The problem. A program is a file on disk: instructions and some initial data. To run it, the OS needs to give it memory, load its code, point a CPU at the first instruction, and keep track of everything it opens, so it can be paused, resumed, and cleaned up when it ends, all while other programs do the same. The bundle of all that state is a process: a program in execution.

Address spaceThe memory the process can see: its code, data, heap, stacks and mapped files, at addresses that are private to it (section 4).
RegistersIncluding the program counter (the next instruction) and the stack pointer. Saved by the kernel whenever the process stops running.
File descriptorsSmall integers (0, 1, 2 are stdin, stdout, stderr) naming the files, pipes and sockets it has open.
Credentials and bookkeepingUser and group ids, a process id (PID), its parent's PID, its state, its signal handlers, its limits.

The process API: fork, exec, wait, exit, and signals

Unix builds every process from four calls (OSTEP ch. 5). fork() makes a near-exact copy of the caller: same code, same memory contents, same open files; it returns twice, 0 in the new child and the child's PID in the parent. exec() (the execve system call) replaces the program running in the current process with a new one, keeping the PID and open files. wait() lets a parent sleep until a child ends and collect its exit status. exit() ends the process. A shell running python train.py is just fork, then exec in the child, then wait in the parent. Splitting create from run looks odd until you see what it allows: between fork and exec the child can redirect its output, change directory or drop privileges, with no extra API.

A signal is the kernel's way to interrupt a process with a small numbered message. A process can install a handler for most of them. The ones a training job meets: SIGTERM ("please stop": what Kubernetes, Slurm and spot-instance preemption send first), SIGKILL (stop now: cannot be caught, blocked or ignored), SIGINT (Ctrl-C), SIGCHLD (a child changed state), SIGSEGV and SIGBUS (a bad memory access; a DataLoader "bus error" is usually a full /dev/shm, reproduced in the Debug lab).

/proc. The kernel publishes each process's state as files under /proc/<pid>/: status (state, memory, threads), maps (the address space), fd/ (open files), stack, cgroup. Nothing there is stored on disk; the kernel generates the text when you read it. ps, top and htop are just readers of /proc.

The real lines behind the picture






The cost of fork. fork does not copy memory; it copies the page tables that describe it (section 4) and marks every page read-only and shared, so a page is copied only when one side writes to it: copy-on-write. Copying page tables is still work proportional to the memory in use.  A process with tens of gigabytes resident (a big model in CPU memory) pays proportionally more on every fork.


Threads, states, zombies and orphans


A thread is a second flow of execution inside the same process: its own registers and stack, but the same address space, files and PID group. On Linux, processes and threads are both made by one system call, clone(), whose flags say what to share; the Syscall tracer tab shows the exact flags for import torch's thread pool and for the DataLoader's workers. Threads are cheaper to create and communicate through shared memory; processes are isolated, so a crash or a leak in one does not take the others down, and in CPython each process has its own GIL. How many threads does the job have? The tracer's fork run labels the main process with 38 threads, but that counts every thread ID seen over the whole run; only 5 to 10 are alive at any one time (Concurrency lists the live ones and what each does).


A process is running (on a CPU), runnable (waiting for one), sleeping (waiting for an event; S in ps if a signal can wake it, D if it cannot, usually because it is inside a device or network file system operation), stopped (T), or a zombie (Z): it has exited but its parent has not yet called wait(), so its PID and exit status are kept. A child whose parent dies is an orphan, and is adopted by PID 1 (or the nearest "subreaper"), which is expected to wait() for it. Inside a container your script is often PID 1 itself, and a Python script does not reap orphans it did not start: a crashed DataLoader can leave zombie workers behind. The Debug lab reproduces this; the usual fix is a tiny init process (docker run --init, or tini).

Spawn and forkserver pay for a fresh interpreter that re-imports torch. With a persistent_workers=True DataLoader that cost is paid once per run instead of once per epoch.


Fork after CUDA. A GPU runtime keeps threads, driver handles and device mappings that a forked child cannot inherit safely. PyTorch's documentation: "either the spawn or forkserver start method are required to use CUDA in subprocesses" (Multiprocessing best practices), and it calls the failure "poison fork". The usual trap is touching CUDA (even torch.cuda.is_available() on some versions, or moving a tensor to the GPU) in the parent before the DataLoader forks; keep the workers on the CPU and move batches to the GPU in the main process. not run here (no GPU).


torchrun is itself a parent process: it starts one worker process per GPU (--nproc-per-node), gives each its rank through environment variables (RANK, LOCAL_RANK, WORLD_SIZE), watches them, and if one fails it stops the rest and, if allowed, restarts the group. So a training node runs a small tree of processes: the launcher, one trainer per GPU, and each trainer's DataLoader workers.


Graceful preemption. On Kubernetes, deleting a pod makes the container runtime "send a TERM signal to process 1 inside each container", waits the grace period ("The default terminationGracePeriodSeconds setting is 30 seconds"), then sends SIGKILL to anything still running (Kubernetes, Pod Lifecycle). Slurm does the same with SIGCONT, SIGTERM, then SIGKILL after its configured KillWait (scancel(1)), and torchrun's agent stops its workers with SIGTERM and a 30 s timeout before SIGKILL (torch.distributed.elastic agent), sending both to each worker's whole process group (os.killpg), so the DataLoader worker processes a trainer started are hit too, not only the trainer (Processes and the system-call API traces it). Note "process 1": if your container starts sh -c "python train.py", the shell is PID 1 and may not pass the signal on, so the job never hears it and is killed 30 s later. The running job installs a SIGTERM handler that only sets a flag; the training loop notices the flag after the current step, writes a checkpoint (section 7) and exits 0. Doing the checkpoint inside the handler itself is a classic bug: a Python handler does not run when the signal arrives; "the low-level signal handler sets a flag which tells the virtual machine to execute the corresponding Python signal handler at a later point (for example, at the next bytecode instruction)", always in the main thread, and "Synchronization primitives such as threading.Lock should not be used within signal handlers" (Python signal docs). A long torch.save inside the handler can deadlock or run while the model is half-updated. The Debug lab shows a job that ignores SIGTERM and the fix.

3. Scheduling: sharing a few CPUs among many threads


ch. 6 Direct Execution, ch. 7 CPU Scheduling, ch. 8 Multi-level Feedback, ch. 9 Lottery Scheduling, ch. 10 Multi-CPU Scheduling


The problem. The running job alone has a main thread, a pool of compute threads for PyTorch's operators, two worker processes, and a few helper threads, on a machine with 5 CPUs that also runs other people's containers. At any moment there are more threads that could run (runnable) than CPUs. The kernel's scheduler decides which thread runs on which CPU and for how long, many times a second, so that each makes progress and the important or interactive ones are not starved.


How it gets control. A running thread does not hand the CPU back voluntarily unless it blocks (waits for I/O, a lock, a sleep). So at boot the kernel programs a hardware timer interrupt: every few milliseconds the CPU stops whatever it runs and jumps into the kernel, which can then decide to keep the current thread or switch. That switch is a context switch: save the current thread's registers into its kernel record, load another thread's, and, if the other thread belongs to a different process, switch the address space too (section 4), which makes the new thread's first memory accesses slower while the caches and the TLB warm up.


What a context switch costs, measured


Policies, from OSTEP's to Linux's


OSTEP builds scheduling up from simple policies, each fixing the previous one's flaw: FIFO (run in arrival order: a long job delays everyone behind it), SJF and STCF (shortest job first, or shortest time to completion first: great average turnaround, but needs to know job lengths), round robin (a short time slice each in turn: good response time, poor turnaround), and the multi-level feedback queue (MLFQ: learn from behaviour, so threads that keep using whole slices sink in priority and threads that block quickly, like interactive ones, stay high). Two numbers judge them: turnaround time (finish minus arrival) and response time (first run minus arrival). The OS simulators tab runs all of them on the same jobs, with Gantt charts.


Linux: CFS, then EEVDF. From 2.6.23 (2007) Linux used the Completely Fair Scheduler, which "basically models an ideal, precise multi-tasking CPU on real hardware" (CFS design doc). Each thread accumulates virtual runtime, its CPU time divided by its weight; the scheduler always runs the thread with the smallest virtual runtime, kept in a sorted tree. Since Linux 6.6 the same fair-share accounting is driven by EEVDF (Earliest Eligible Virtual Deadline First), which also gives each thread a virtual deadline so that threads asking for short slices get lower latency (EEVDF doc, LWN, 2023-03-09). The base slice is 0.75 ms (sysctl_sched_base_slice = 750000ULL, kernel/sched/fair.c line 76 at v6.12), scaled at boot by 1 + log2(min(CPUs, 8)) with the logarithm rounded down: 2.25 ms on a 5-CPU machine like this lab's VM, 3 ms on 8 CPUs or more (Scheduling and CPU time works it through). not run here: this lab's kernel is 5.10, which still runs CFS.


Priorities: nice. A thread's weight comes from its nice value, from -20 (most CPU) to 19 (least). The table in the kernel (sched_prio_to_weight, kernel/sched/core.c line 10012 at v6.12) gives nice 0 a weight of 1024, nice 1 820 and nice -1 1277: each step is a factor of about 1.25, which the source comment explains as "the 10% effect": one nice level up or down moves a CPU-bound thread's share by about 10% against a competitor.  nice -n 10 python preprocess.py makes a background job yield to training.


Which CPU: affinity. A thread may be restricted to a set of CPUs (taskset, os.sched_setaffinity). Staying on one CPU keeps its caches warm; on a machine with several memory nodes, staying near its memory matters more (section 4). The scheduler also migrates threads between CPUs to balance load, which is part of why identical training steps take slightly different times.

4. Virtual memory: a private, huge memory for every process


ch. 13 Address Spaces, ch. 15 Address Translation, ch. 18 Introduction to Paging, ch. 19 Translation Lookaside Buffers, ch. 20 Advanced Page Tables, ch. 21 and 22 Swapping, ch. 23 Complete VM Systems


The problem. Every process in section 2 believed it owned addresses from 0 up to about 248, and the three processes of the job used the very same addresses for different data. Physical memory is one shared array of about 10 GB here. Something has to map each process's addresses onto real memory, keep processes from seeing each other's, let them share what should be shared (library code, the dataset), and let the total promised exceed what exists.


Pages and page tables. Memory is managed in fixed-size pages, 4 KiB here (getconf PAGESIZE prints 4096). Every address a program uses is a virtual address; the hardware's memory management unit (MMU) translates it, on every single load and store, into a physical address. The low 12 bits (the offset inside a 4 KiB page) pass through unchanged; the high bits name a virtual page, which a per-process page table maps to a physical page frame, along with permission bits (read, write, execute, user or kernel). A flat table for 236 virtual pages would be huge, so it is a tree: on ARM64 and x86-64 with 4 KiB pages and 48-bit addresses, four levels of 512 entries each, using 9 bits of the address per level. Switching processes (section 3) means pointing the MMU at a different tree.


The TLB. Walking four levels of table in memory on every access would make every load five loads. The CPU caches recent translations in a small, fast translation lookaside buffer (TLB). A hit costs nothing extra; a miss costs a page-table walk. Page faults: memory on demand


The kernel does not fill in page tables in advance. Allocating memory or mapping a file only records a promise (a mapping, as in section 2's maps); the first access to each page finds no valid entry and traps into the kernel: a page fault. The kernel finds or makes the page, fills in the entry and resumes the instruction. A minor fault needs no I/O (a zeroed page for new memory, or a file page already in memory); a major fault must read the device ("page faults serviced that required I/O activity", getrusage(2)). mmap and the page cache


The kernel keeps recently used file data in otherwise free memory, the page cache; read() copies from it, and mmap maps its pages straight into your address space, so the dataset's bytes are never copied at all: np.memmap, safetensors and llama.cpp's weight loading (Part 3 of the C++ page) all work this way. A mapping is MAP_SHARED (writes go to the file, other mappers see them) or MAP_PRIVATE, "a private copy-on-write mapping" (mmap(2)). That is why free shows "buff/cache" as large and "available" as much bigger than "free": cached file pages are given back whenever a program needs the memory.


Copy-on-write, and the DataLoader memory leak that is not a leak


After fork, parent and children share every page read-only; the first write to a page by either side faults, and the kernel copies that one page (in the kernel source: __copy_present_ptes write-protects both sides at fork, mm/memory.c lines 955 to 958, and wp_page_copy, line 3331, makes the copy; Linux v6.12). Section 2 showed it on the real job. Python adds a twist: every object carries a reference count, and merely reading an object from a list increments and decrements it, which is a write to the page holding it. A Dataset that holds millions of Python objects (a list of file names, a dict of labels) is copied page by page into every worker as the epoch touches it, so worker memory climbs towards the parent's. PyTorch's documentation: "the loader worker processes will consume the same amount of CPU memory as the parent process for all Python objects in the parent process which are accessed from the worker processes... The simplest workaround is to replace Python objects with non-refcounted representations such as Pandas, Numpy or PyArrow objects" (torch.utils.data; issue 13246, opened 2018-10-29).  The OS simulators tab animates it page by page and the Debug lab measures it per worker.


Huge pages, overcommit, swap and the OOM killer


Huge pages. One 2 MiB page replaces 512 small ones: one TLB entry instead of 512, one fewer level to walk. Linux can do this transparently (THP) for anonymous memory; here it is set to "madvise", so only ranges marked with madvise(MADV_HUGEPAGE) get them (transhuge doc). The running job does exactly that: it reserves 1 GiB of address space and marks it MADV_HUGEPAGE (the Syscall tracer tab shows the calls and which library makes them: the mimalloc allocator inside PyTorch's Linux arm64 wheels reserving its arena; x86-64 wheels use glibc's malloc and make no such reservation; Memory allocators explains it). The cost: a huge page must be found or assembled from 512 free contiguous small pages, which can stall an allocation, and a mostly empty huge page wastes memory.


Overcommit. Linux lets processes reserve more memory than exists, betting that much of it will never be touched: overcommit_memory 0 is the default heuristic, 1 "always overcommit, never check", 2 "always check, never overcommit" (proc_sys_vm(5)). This lab's VM runs with 1, which is why the job's 1 GiB reservation and every 64 MiB malloc arena cost nothing until touched.




Swap and the OOM killer. When memory runs out, the kernel first reclaims page cache, then may write anonymous pages to swap (disk), which turns memory accesses into disk reads and a fast job into a crawling one. If it still cannot find memory, the OOM killer picks a process and kills it with SIGKILL: the one with the highest badness, roughly the share of memory it uses, adjusted by oom_score_adj from -1000 (never) to +1000 (proc(5) section 3.1; oom_badness, mm/oom_kill.c line 202, v6.12). /proc/<pid>/oom_score shows that badness, rescaled, but always computed against the whole machine's RAM plus swap (here the VM's; fs/proc/base.c line 552 at v5.10), even inside a container, while an OOM kill in a cgroup scores against the cgroup's limit (Virtual memory checks the formula against the kernel's numbers). In a container the OOM killer runs inside its cgroup when it reaches memory.max (section 8): the job just disappears with exit code 137 (128 + 9, SIGKILL), with no Python traceback. The Debug lab reproduces it next to a Python MemoryError.


NUMA and pinned memory not run here


NUMA. A server with two CPU sockets has two memory banks; each socket reaches its own bank faster than the other's (non-uniform memory access). By default Linux allocates a page on the node of the CPU that first touches it (MPOL_DEFAULT in set_mempolicy(2)), so a DataLoader worker or a GPU's feeding process on the wrong socket reads every batch across the interconnect. numactl --hardware lists the nodes; inside this lab it reports none (a single-socket laptop VM), so the CPU and memory hardware is left to the hardware topic.


Pinned memory. A GPU copies from host memory by DMA (direct memory access, the device reading RAM itself), which needs the physical pages to stay put; ordinary pages could be swapped or moved. So CUDA copies first into pinned (page-locked) memory, which the kernel promises never to move or swap (the mechanism behind mlock(2)). "Host to GPU copies are much faster when they originate from pinned (page-locked) memory", so DataLoader(pin_memory=True) puts batches there directly (torch.utils.data, memory pinning). Pinned memory is taken out of the pool the kernel can reclaim, so pinning too much starves the rest of the machine.

5. Allocators: between your tensors and the kernel's pages


ch. 14 Interlude: Memory API, ch. 17 Free-Space Management


The problem. The kernel hands out memory in whole pages and only through system calls (section 1), which cost hundreds of nanoseconds. Programs ask for millions of small, short-lived pieces: a 56-byte Python integer, a 2 KB string, a 1 MB tensor. A user-space allocator sits in between: it gets large regions from the kernel rarely, cuts them into pieces for malloc often, and keeps freed pieces for reuse. Its job is to be fast, to waste little, and to not get in the way of threads.


Where glibc's malloc gets memory. Two kernel interfaces. The heap is one region just after the program's data, grown by moving its end (the "program break") with brk. Large requests instead get their own anonymous mmap, which can be returned to the kernel independently on free. The switch point is M_MMAP_THRESHOLD, whose "initial value ... is 128*1024" and which glibc then adjusts dynamically (mallopt(3)). Traced here: a 64 KiB request grows the heap, a 200 KiB one gets its own mapping and gives it back on free.




measured here strace -e trace=brk,mmap,munmap,write ./malloc_sizes (src/read/code/malloc_sizes.c); the program writes the "---" markers itself; the start-up calls of the dynamic loader are cut. The first version of this test showed no calls at all: gcc -O2 removed the malloc, memset and free as dead code, so the buffer now escapes into a global.


Arenas: one heap per thread, roughly. If every thread shared one heap, every malloc would take a lock. glibc gives threads separate arenas, up to a limit computed from the CPU count, each a 64 MiB reservation on 64-bit (HEAP_MAX_SIZE (2 * DEFAULT_MMAP_THRESHOLD_MAX), malloc/arena.c line 31, with the threshold maximum 4 * 1024 * 1024 * sizeof(long), malloc/malloc.c line 972, glibc 2.36, the version in this image). You can see them in section 2's maps: when the DataLoader started, three new pairs appeared in the main process, each 132 KiB readable and writable followed by 65,404 KiB with no access: 64 MiB reserved, 132 KiB used. Reservations cost nothing until touched (overcommit, section 4), but a long-running multi-threaded server can hold freed memory in many arenas: the usual cure is MALLOC_ARENA_MAX=2 or a different allocator.


Fragmentation. After many allocations and frees of mixed sizes, free memory is scattered in holes between live blocks: there may be plenty free in total but no single hole big enough. That is external fragmentation; rounding requests up to size classes wastes the rest of each block (internal fragmentation). OSTEP ch. 17 covers the classic strategies (best fit, first fit, segregated lists, buddy allocation).


Other allocators. jemalloc (FreeBSD, Meta) and tcmalloc (Google) use per-thread caches and size classes to cut lock contention and fragmentation; swapping one in for glibc's needs no code change (LD_PRELOAD=libjemalloc.so python train.py), which is a common fix for slowly growing memory in data-loading and serving processes. CPython has its own layer on top: "a pymalloc allocator optimized for small objects (smaller or equal to 512 bytes) with a short lifetime. It uses memory mappings called arenas with a fixed size of either 256 KiB on 32-bit platforms or 1 MiB on 64-bit platforms" (Python memory management). A Python process whose objects were freed may keep its pymalloc arenas because one live object pins each one, which is why memory often does not drop after del. PyTorch itself brings a third: its Linux arm64 wheels build mimalloc into libc10.so for CPU tensors, and mimalloc's arena reservation is section 4's 1 GiB MADV_HUGEPAGE range; the x86-64 wheels use glibc's malloc (Memory allocators compares them on this job).

6. Concurrency: threads that share memory


ch. 26 Concurrency and Threads, ch. 27 Thread API, ch. 28 Locks, ch. 30 Condition Variables, ch. 31 Semaphores, ch. 32 Concurrency Bugs, ch. 33 Event-based Concurrency


The problem. Threads (section 2) share one address space, which is what makes them useful: PyTorch's operator threads all write into one output tensor, the DataLoader's helper threads hand batches to the training loop. But the scheduler can stop a thread between any two instructions, and on several CPUs two threads really do run at the same instant. Any piece of shared data that more than one thread updates is a race waiting to happen: the result depends on the timing.


The lost update, measured. Two threads each add 1 to a shared counter ten million times. count = count + 1 is three steps for the CPU (load, add, store); if both threads load the same old value, one increment is lost. Run here on two CPUs:

Locks, and the futex underneath. A lock (mutex) makes a critical section: only one thread at a time runs the code between lock() and unlock(). Built naively, a waiting thread either spins (burning a CPU) or makes a system call every time. Linux's answer is the futex, "fast user-space locking": "In the uncontended case, a thread can access or modify the lock state with atomic instructions ... performed entirely in user mode" and only a thread that must wait asks the kernel to put it to sleep (futex(2); futex_wait, kernel/futex/waitwake.c line 688, v6.12). Counting the system calls of the mutex version above:






An atomic instruction (fetch-and-add) does the read-modify-write as one indivisible step in hardware, with no lock and no kernel; it is how counters, reference counts and lock-free queues are built. Which writes other CPUs see, and in what order, is the memory model: covered with measurements (atomics, false sharing) in Part 2 of the C++ page.


Waiting for something. A condition variable lets a thread sleep until another signals that a condition may now hold ("a batch is ready"), always rechecking the condition under the lock. A semaphore is a counter that blocks at zero, good for "at most N in flight" (the DataLoader's prefetch_factor is this idea). The sem.* files in section 2's /dev/shm are the semaphores behind multiprocessing's queues.


Deadlock. Thread A holds lock 1 and waits for lock 2; thread B holds lock 2 and waits for lock 1; neither can proceed, forever. It needs four conditions at once (mutual exclusion, hold and wait, no preemption, a circular wait), and the usual cure removes the circle: always take locks in one global order. A training-specific variant: fork() copies only the calling thread (section 2), so a lock that another thread held at the moment of the fork stays locked forever in the child, and the child hangs at its first malloc or log call. That is the reason behind Python 3.12's fork DeprecationWarning, Python 3.14's switch to forkserver, and PyTorch's "poison fork". The Debug lab reproduces the hang.


Python's GIL. In CPython (before the free-threaded build) one global interpreter lock lets only one thread run Python bytecode at a time; threads still help for I/O and for C code that releases the GIL (NumPy, PyTorch operators), which is why the DataLoader uses processes for Python-heavy work. The Python page covers the GIL and free-threading.


Event-driven I/O: what asyncio, tokio and Node are built on


A server with ten thousand open connections cannot afford ten thousand threads, each mostly asleep. The alternative is one thread and one question to the kernel: "which of these file descriptors are ready?". select and poll ask it with the whole list every time; epoll keeps the list in the kernel, so the cost depends on the ready ones only: it "performs a similar task to poll(2) ... and scales well to large numbers of watched file descriptors" (epoll(7)). Python's asyncio event loop is a loop around epoll_wait; so are Node's libuv (Part 1 of the JS/TS page) and Rust's tokio (Part 3 of the Rust page). On macOS the same role is played by kqueue. 7. Persistence: getting a checkpoint safely onto disk


ch. 36 I/O Devices, ch. 39 Files and Directories, ch. 40 File System Implementation, ch. 42 FSCK and Journaling, ch. 44 Flash-based SSDs, ch. 49 NFS


The problem. Memory forgets everything on a crash or power loss; a training run that loses its checkpoint loses days. But devices are slow and work in large blocks, so the OS hides them behind a cache and writes later. The whole difficulty of persistence is in that "later": what exactly is on the device when the machine dies?


Devices and drivers, in one picture


A storage device (an NVMe SSD, a network block device in the cloud) is controlled by a driver in the kernel, which places requests in queues the device reads by DMA and learns of completion through an interrupt. Above the driver the kernel offers a block device: an array of fixed-size blocks (/dev/nvme0n1). Above that a file system (ext4, XFS) turns blocks into files, directories, names and permissions, and keeps its own bookkeeping (inodes: the record of a file's size, owner and block locations; directories: tables from names to inodes). Above that, the page cache (section 4) holds file data in memory. A write() stops at the page cache.


A write's journey


Below, the running job's checkpoint (here a 64 MiB file, the size of a small model's state) is written two ways. The counters are real: the system-wide Dirty line of /proc/meminfo (page-cache data not yet on the device) and the time of each call, measured here.


















How much later. The kernel's flusher threads wake every 5 seconds and write out dirty data older than 30 seconds, and start writing earlier when dirty data passes 10% of available memory (in the background) or 20% (then the writing process must write back itself and slows down): dirty_writeback_interval = 5 * 100, dirty_expire_interval = 30 * 100 centiseconds, dirty_background_ratio = 10, vm_dirty_ratio = 20 (mm/page-writeback.c lines 74 to 109, v6.12; this lab's /proc/sys/vm shows the same values). Measured on this VM, though, the same 16 MiB stayed dirty anywhere from about 2 to 32 s, and in fresh containers it often left at the flusher's next 5-second wake-up, long before it was 30 s old; the likely reason (read from the source, not traced) is wb_over_bg_thresh, which compares each writeback domain's dirty pages with its own share of the background threshold (Storage and file systems). So after torch.save returns, a crash in the next few seconds, and at worst the next half minute, can lose the checkpoint, and with the naive pattern the previous one is already gone.


The three calls that make it safe. fsync(fd) returns only when the file's data and metadata are on the device. It does not cover the file's name: "Calling fsync() does not necessarily ensure that the entry in the directory containing the file has also reached disk. For that an explicit fsync() on a file descriptor for the directory is also needed" (fsync(2)). rename(tmp, final) swaps names atomically: "If newpath already exists, it will be atomically replaced, so that there is no point at which another process attempting to access newpath will find it missing" (rename(2)). Together: a reader, or a restart after a crash, sees either the whole old checkpoint or the whole new one. The running job's save_checkpoint does exactly this, and the Syscall tracer tab shows the system calls of both patterns on the real job.


Two real stories

2009, ext4's zero-length files. With delayed allocation, ext4 wrote file data much later than its rename; after crashes, users found "pretty much any file written to by any application (during the previous boot) was 0 bytes". Ted Ts'o's answer: applications had come to depend on ext3's behaviour "even though POSIX never really made any such guarantee"; ext4 then added a heuristic that forces the data out when a file is renamed over another (LWN, 2009-03-11). Do not rely on that heuristic: call fsync.

2018, fsyncgate. PostgreSQL assumed that a successful fsync meant everything written since the last one was safe. After a device error, Linux could report the error once and mark the pages clean, so a retried fsync succeeded with the data lost (LWN, 2018-04-18). Lesson for checkpoints: if fsync fails, treat that checkpoint as lost and write it again from memory; never just retry the fsync.


Journaling, direct I/O, and storage you do not own


Journaling. Creating or renaming a file updates several blocks (the directory, the inode, the free-block bitmap); a crash between them leaves the file system inconsistent, which old systems repaired with a full scan (fsck). A journal writes the intended changes to a log first and only then in place, so after a crash the log is replayed or discarded in seconds. ext4's default data=ordered: "All data are forced directly out to the main file system prior to its metadata being committed to the journal" (ext4 docs). Journaling protects the file system's structure, not your file's contents: that is still fsync's job. The OS simulators tab crashes a write at every step with and without a journal; the write-ahead log of the databases topic is the same idea in a database.


Direct I/O. Opening a file with O_DIRECT bypasses the page cache: transfers go straight between your buffer and the device, with alignment rules. Databases and some checkpoint writers use it to avoid filling memory with data they will not read again, and to make write timing predictable.


Network and parallel file systems, and object storage. On a cluster the checkpoint directory is rarely a local disk. NFS exports one server's file system over the network, and its caching makes close-to-open the only consistency you can rely on. Lustre and similar parallel file systems stripe each file across many storage servers so thousands of GPUs can read and write at once, at the cost of slow metadata operations (opening millions of small files hurts). Object storage (S3, GCS) has no rename or fsync at all: an object is written whole and appears atomically when the upload completes, so "write then rename" becomes "upload to a new key, then update a pointer". Checkpoint libraries hide these differences; knowing them explains their options.

Sharded formats (WebDataset tar shards, Arrow or Parquet files, memory-mapped token arrays) exist to turn many small reads into few big ones. The Debug lab measures cold against warm reads and a throttled device.

  • Sharded and asynchronous checkpoints. The problem. A training job needs a precise set of libraries (one CUDA, one PyTorch, one Python), must not see or disturb the other jobs on the node, and must stay inside its share of CPU and memory. A virtual machine (section 9) would give all that by running a whole second kernel; a container gets most of it with no second kernel at all. The OOM kill inside a container. Rootless. By default the container's root is the host's root with fewer capabilities. Rootless containers (Podman, rootless Docker) also use a user namespace so that root inside maps to an ordinary user outside: a breakout lands as nobody special. HPC clusters use Apptainer (formerly Singularity) for the same reason: the job runs as the submitting user.


Sandboxes for code you do not trust


Containers share the host kernel, so a kernel bug reachable through an allowed system call is a way out. For running code an agent or a user wrote, two stronger designs are common. gVisor "intercepts application system calls and acts as the guest kernel": a user-space "application kernel" implements Linux's interface, so the host kernel sees far fewer, simpler calls (gVisor docs). Firecracker runs each sandbox as a minimal virtual machine (a microVM) with its own kernel, "lightweight virtual machines (microVMs) that provide enhanced security and workload isolation over traditional VMs, while enabling the speed and resource efficiency of containers" (firecracker-microvm.github.io). 9. Virtualization and the GPU driver stack


appendix Virtual Machines


not run here except where marked: this lab has no GPU. It does, however, run inside a virtual machine (Docker Desktop's Linux VM on macOS), which is why section 3's cross-CPU wake-up and section 4's TLB misses were dearer than on bare metal. The wake-up is slow because this VM's interrupt controller is a GICv2 emulated inside QEMU on macOS's Hypervisor.framework: every inter-processor interrupt is a trip out of the guest, and an idle target vCPU is a host thread that must itself be woken (Virtualization and the GPU driver stack, section 5, measures each step).


Virtual machines. A hypervisor (KVM in Linux, Xen, Apple's Hypervisor framework under Docker Desktop, the cloud providers' own) runs whole guest operating systems, each believing it owns a machine. Modern CPUs help in hardware: an extra privilege level for the hypervisor (EL2 on ARM64, VMX root mode on x86), and a second layer of page tables so that guest-physical addresses are translated to host-physical ones by the MMU (the two-dimensional walk of section 4). A cloud GPU instance is almost always such a guest.


The IOMMU and passthrough. A device that does DMA writes straight into physical memory, so a guest given a real device could overwrite anything. The IOMMU is an MMU for devices: it translates and checks every DMA address against tables the hypervisor controls. With it, a whole GPU can be handed to one VM (passthrough, via Linux's VFIO) and the guest's driver talks to the hardware directly at near-native speed.


Sharing one GPU. SR-IOV lets one PCIe device present several "virtual functions", each passed to a different guest. NVIDIA's MIG (Multi-Instance GPU) goes further on data-centre GPUs: it can "partition supported NVIDIA GPUs into multiple isolated instances, each with dedicated compute and memory resources" (MIG user guide), so two small inference jobs cannot slow each other down the way two processes sharing one GPU by time-slicing can.

Ten interview questions, with short answers


1. What happens, at the OS level, when you run python train.py?
The shell forks; the child execs the Python binary; the kernel maps the executable and the dynamic loader, which maps libpython and libc; the interpreter starts, opens and reads your script, and imports modules (many openat, read and mmap calls). The parent shell waits. Sections 1 and 2.


2. Process against thread?
A process has its own address space and resources; threads share their process's address space and files and have only their own registers and stack. On Linux both are made by clone() with different sharing flags. Threads are cheaper and share data directly; processes isolate failures and, in CPython, get their own GIL.


3. Why is fork fast even for a 20 GB process, and when is it not?
It copies page tables, not pages, and marks pages copy-on-write. It is still proportional to resident memory (6.8 ms for 512 MiB here, against 80 µs for a small process), and every page either side writes later is copied then. Python refcount updates make reading objects count as writing.


4. What is a page fault, and minor against major?
A trap on access to a page with no valid page-table entry. Minor: the kernel fixes the entry without I/O (zeroed page, page already cached). Major: it must read from the device. Measured here: 65 major faults to touch a cold 8 MiB file (readahead), 129 minor ones once warm (fault-around).


5. Why does the sum of RSS of my DataLoader workers exceed the machine's memory?
RSS counts shared pages once per process. PSS divides each shared page among its sharers and adds up correctly: 815 MiB of RSS against 345 MiB of PSS for the running job's three processes.


6. What does fsync guarantee, and what does it not?
That the file's data and metadata reached the device before it returns (if the device honours flushes). Not that the file's name is durable (fsync the directory), not atomicity of replacement (use rename), and after an error, not that a retry recovers lost pages.


7. How does a mutex avoid a system call?
A futex: the lock word lives in user memory and is taken with an atomic instruction; only a thread that must wait calls futex() to sleep, and the unlocker calls it only if someone is waiting. Here 20 million lock/unlock pairs under contention made 8,382 futex calls.


8. What is a container, exactly?
Processes on the host kernel with namespaces (what they see), cgroups (how much they use), dropped capabilities and a seccomp filter (what they may do), and an image mounted as root through overlayfs. No second kernel: that is a VM.


9. Why might a training job get slower when moved into Kubernetes with a CPU limit of 4?
The limit is a CFS quota (400 ms per 100 ms period). PyTorch and the DataLoader size their threads from the host's CPU count, burn the quota early in each period and are throttled for the rest. Size threads and workers from the limit; watch nr_throttled.


10. Why is "CUDA out of memory" possible when nvidia-smi or the error says gigabytes are free?
The caching allocator holds freed blocks; fragmented segments may have plenty reserved but no contiguous block of the requested size, or the free memory belongs to another process. memory_allocated against memory_reserved tells which; expandable_segments reduces fragmentation.

1. CPU scheduling: who runs next?


The problem. A CPU core runs one thread at a time, but a training node has many runnable threads: the training loop, DataLoader workers, a logging thread, your shell. The scheduler is the kernel code that decides which one runs on the core for the next slice of time. Each policy below is a different answer, and each is good at one thing and bad at another. Two numbers judge them (OSTEP chapter 7): turnaround time = finish time minus arrival time (how long a batch job takes), and response time = first time it runs minus arrival time (how long an interactive program waits before anything happens).


    

  • FIFO runs jobs in arrival order, each to completion. SJF (shortest job first) picks the shortest waiting job, still to completion. STCF (shortest time-to-completion first) may preempt: stop a running job when a shorter one arrives.
    • 

  • Round robin gives each job a fixed time slice (quantum) in turn: good response, bad turnaround.
    • 

  • MLFQ (multi-level feedback queue, chapter 8) learns from behaviour: a job starts at top priority and drops a level each time it uses up its allotment; jobs that block for I/O early stay high. A periodic boost lifts everyone back so nothing starves.
    • 

  • CFS (Linux's Completely Fair Scheduler, chapter 9.7; Linux 2.6.23 to 6.5) gives each job a virtual runtime (vruntime) that grows as it runs, more slowly for a higher weight, and always runs the job with the smallest vruntime. A nice value from -20 to 19 picks the weight. Since Linux 6.6 the default is EEVDF, which this kernel (5.10) cannot run; it is described from sources in the Reading tab.
    • 



The model: time in ticks; one CPU; a job with "I/O every k" runs k ticks then blocks for the I/O time (as in OSTEP's mlfq.py). At each tick, newly arrived jobs join the queue first, then jobs whose I/O finished, then the job whose slice just ended; ties go to whoever queued first. The CFS here keeps the kernel's slice formula, weights and placement rules (sources below) and leaves out wake-up preemption and multi-CPU load balancing.

2. Paging and the TLB: from a virtual address to a physical one


The problem. Every process believes it owns one large, private range of addresses (its virtual address space), but all processes share one physical memory. On every load and store, the CPU's memory management unit (MMU) translates the virtual address the program used into a physical one. Memory is cut into fixed-size pages (4 KiB on this machine); the page table, kept by the kernel in memory, maps each virtual page number (VPN) to a physical frame number (PFN). A page-table entry (PTE) also holds a valid bit: an access to an invalid page traps into the kernel as a page fault. Reading the page table on every access would double the cost of memory, so the CPU caches recent translations in the TLB (translation lookaside buffer): a hit costs nothing extra, a miss costs a walk of the table. OSTEP chapters 18 to 22.

2c. When memory is full: which page to evict


When a process touches more pages than fit in memory, each access to a page that is not resident is a major page fault: the kernel reads the page from disk (swap, or the file it maps) and must first evict another page. The policy decides which. OPT evicts the page used furthest in the future (perfect, impossible in practice, the yardstick); FIFO the oldest; LRU the least recently used; CLOCK approximates LRU cheaply: a hand sweeps the frames, clearing each page's use bit, and evicts the first page whose bit is already clear (OSTEP chapter 22; Linux's real policy keeps active and inactive lists, a refinement of the same idea).

3. Copy-on-write after fork: why DataLoader workers grow


The problem. fork() creates a child process with a copy of the parent's whole address space. Copying gigabytes for every child would be slow, so the kernel copies nothing: parent and child share every physical page, marked read-only, and only when one of them writes to a page does the write trap (a page fault), and the kernel give the writer its own copy of that one page. This is copy-on-write (CoW; OSTEP chapter 23 describes it as part of complete VM systems, chapter 5 introduces fork). PyTorch's DataLoader starts its workers with Python's default start method, which on Linux is fork up to Python 3.13 (3.14 changed it to forkserver; multiprocessing docs), so with fork a dataset held in the parent is shared with every worker for free, until something writes to it.


The catch in Python. Every Python object starts with a reference count, and merely reading an object from Python code (looping over a list, indexing it) increments and decrements that count: a write to the page the object lives on. So a worker that only reads a Python list of a million objects ends up copying every page those objects occupy. A numpy array is one object whose numbers sit in a plain buffer: reading the numbers never touches a reference count. The Python documentation describes the same problem for the garbage collector's own writes and offers gc.freeze() for it; PyTorch's DataLoader documentation warns that "the loader worker processes will consume the same amount of CPU memory as the parent process for all Python objects in the parent process which are accessed from the worker processes", recommends "non-refcounted representations such as Pandas, Numpy or PyArrow objects", and links issue 13246 (quoted from docs/source/data.md on the main branch, 2026-10-05).

5. Crash consistency: power fails in the middle of a write


The problem. Appending one block to a file changes three places on disk: the file's inode (I, its metadata: size and a pointer to the new block), the data bitmap (B, which blocks are in use) and the data block itself (Db, written to block 5). The disk writes them one at a time, and in whatever order it likes; a crash or power cut can leave any subset on disk. OSTEP chapter 42 lists what each subset means; a journal (write-ahead log: first describe the whole update in a separate log area, mark it complete with a commit block TxE, then write it in place) turns "any subset" into "all or nothing". Linux ext4's default data=ordered mode is the "ordered" protocol below, and its data=writeback mode allows the "data written last" one (ext4 documentation).

Words used below. A system call (syscall) is a request a program makes to the kernel, the only way it can open a file, get memory, start a process or talk to another process; the program stops, the CPU switches into kernel mode, the kernel does the work and returns a number. strace is a tool that asks the kernel to stop the traced program at every system call and print it (it uses the ptrace(2) interface). A file descriptor (fd) is the small integer a process uses to name an open file, pipe or socket. A process has its own memory; a thread runs inside a process and shares its memory. Each has an id (pid; a thread's id is a tid). The Reading explains each idea properly; this tab shows them happening.

3. Two import storms: what import torch asks of the kernel


Importing a Python package means finding files and reading them. For every name in an import, Python's import system (the path finder) checks each directory on sys.path for a matching package, module, compiled extension or bytecode file, which is why most of the calls below are newfstatat (a stat: "does this path exist, and what is it?"), many of them failing with ENOENT ("no such file"). Each compiled extension (.so) is opened and memory-mapped by the dynamic loader. The import system is described in the Python 3.11 reference, section 5.5.




The surprise: the first optimizer imports a compiler
The job's second storm is not import torch. It happens on the line torch.optim.SGD(model.parameters(), lr=0.1): building the first optimizer imports torch._dynamo (the torch.compile front end), which pulls in sympy and torch.distributed, about as many calls as import torch itself. Measured without strace, constructing that first optimizer took  (median of 7 fresh interpreters), against  for import torch. It is a one-off per process, but every spawned DataLoader worker or new process pays its own imports again (section 4).


The 1 GiB reservation when the model is built
Building the model makes an mmap of 1 GiB (MAP_NORESERVE: address space only, no memory committed) followed by madvise(MADV_HUGEPAGE). A gdb catchpoint on that madvise shows the caller: mi_reserve_os_memory_ex and _mi_prim_alloc in torch/lib/libc10.so, the mimalloc allocator built into this PyTorch wheel. See it in the explorer with the jump button "the 1 GiB reservation".







4. Starting the workers: fork, spawn, forkserver


A DataLoader with num_workers=2 starts two worker processes. How they start is Python's start method (multiprocessing docs). fork: the kernel copies the parent (copy-on-write: no memory is copied until someone writes), so the worker starts with torch already imported. spawn: a brand new Python is execve'd and must import everything again. forkserver: a small server process is spawned once, and each worker is forked from it. In CPython 3.11 the default is fork on Linux and spawn on macOS (context.py lines 322 to 327); Python 3.14 changed the Linux default to forkserver (docs, "Changed in version 3.14"). 5. Buffered and unbuffered writes


A system call is not free: the CPU has to switch into kernel mode and back. Python's file objects therefore keep a buffer in user memory and call write(2) only when it fills. Its size is "chosen using a heuristic trying to determine the underlying device's block size and falling back on io.DEFAULT_BUFFER_SIZE" (open() in the 3.11 docs); here the file system reports 4,096-byte blocks, and the trace shows exactly 4,096-byte writes. The experiment writes the same 1 MiB as 4,096 pieces of 256 bytes, once through a normal file object and once with buffering=0.

6. A checkpoint, three ways, and a crash


The same checkpoint (the job's model and optimizer state, about 270 KB) written three ways. naive: torch.save(obj, "ckpt.pt") over the old file. fsync: write through a file object, then os.fsync. safe: write ckpt.pt.tmp, fsync it, os.replace it over ckpt.pt, fsync the directory. A write only copies bytes into the kernel's page cache (memory); fsync waits until the storage device has them (fsync(2)); a rename replaces a name atomically, so a reader sees the old file or the new one, never a mixture (rename(2)). Step through the real calls and see what a crash at that moment would leave on disk.

7. The SIGTERM path


Before a preempted node or a cancelled job is killed, the scheduler sends SIGTERM (Kubernetes waits a grace period, 30 seconds by default, then sends SIGKILL: pod termination). The job installs a handler that only sets a flag; the training loop sees the flag, saves a checkpoint and exits 0. Here is that path in the real trace, with one twist the trace exposed.









8. Language to kernel: one small file, five languages


The same task, read /work/hello.txt (27 bytes) into memory, in C, C++, Rust, Python and Node, each traced.
