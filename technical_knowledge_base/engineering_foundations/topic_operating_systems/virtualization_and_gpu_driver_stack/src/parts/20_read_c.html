3. The VM you are running in, seen from both sides

The problem. Every number measured on these OS pages came from inside a virtual machine. To read them correctly, and to recognise a VM when you are inside one on a cloud, you need to know what this one is made of.

From the host side. On macOS, Docker Desktop 4.11 starts the Linux VM as an ordinary process: QEMU, accelerated by Hypervisor.framework. Its command line (disk path, console pipe, MAC address and network token removed) says almost everything:



measured ps -o args= of the VM process and qemu-system-aarch64 --version on the macOS host (src/exp/host_qemu.sh; raw: src/raw/host_qemu.txt).


ArgumentMeans


-accel hvfrun guest code directly on the CPU through Apple's Hypervisor.framework (the exits of section 2), instead of emulating every instruction in software


-cpu host -smp 5 -m 10240the guest sees this CPU's features, 5 virtual CPUs (each a thread of the QEMU process) and 10 GiB of "physical" memory, which is ordinary memory of the QEMU process


-machine virt,highmem=offQEMU's generic arm64 board: a PL011 serial port, a PL031 clock, a PCIe host bridge, and, when no version is asked for and KVM is not in use, a GICv2 interrupt controller emulated by QEMU itself ({{finalize_gic_version, hw/arm/virt.c L1802-1806, QEMU v6.2.0|https://github.com/qemu/qemu/blob/v6.2.0/hw/arm/virt.c#L1802-L1806}})


-device virtio-blk-pci, virtio-net-devicea paravirtual disk on PCI and a paravirtual network card on a memory-mapped bus (section 6)


-kernel ... -append ... mitigations=offboot the linuxkit kernel directly, with CPU side-channel mitigations off

The QEMU process on the Mac has 5 vCPU threads. While your training job in this VM is idle, what are those threads doing on macOS?




The guest's idle loop executes wfi, which exits to QEMU; QEMU then puts the vCPU thread to sleep in pselect until the guest's timer is due or another thread signals it ({{hvf_wfi and hvf_wait_for_ipi, QEMU v6.2.0|https://github.com/qemu/qemu/blob/v6.2.0/target/arm/hvf/hvf.c#L1011-L1021}}). That is OSTEP's "information gap" handled well: the VMM notices the guest went idle and gives the CPU back. Section 5 shows what it costs to wake such a thread.
