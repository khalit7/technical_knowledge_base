3. Cloud instances, and the VM these pages ran in

Why it matters. Every number on these OS pages came from inside a VM, and so does almost every cloud GPU you will train on. Both are recognisable from inside, and both pay the same kinds of cost: exits for idle and devices, slower cross-CPU wake-ups, two-stage page walks, and time the host takes without telling you.

On a cloud instance, the questions to ask
  • systemd-detect-virt names the hypervisor (kvm, amazon, microsoft, xen) from firmware tables; lspci -nn shows virtio or vendor-specific devices next to the passed-through GPU.
  • grep -c ^processor /proc/cpuinfo counts vCPUs, which on many instance types are hyperthreads, not cores; lscpu shows threads per core.
  • top's st column is steal time where the hypervisor reports it; a large value means your vCPUs wait for the host (section 5).

This VM, in one line. On macOS, Docker Desktop 4.11 starts the Linux VM as an ordinary process: QEMU 5.2 with -accel hvf (guest code runs directly through Hypervisor.framework), -smp 5 -m 10240 (5 vCPUs, each a thread of the QEMU process, and 10 GiB of "physical" memory that is ordinary memory of that process), QEMU's generic virt board with a GICv2 interrupt controller emulated by QEMU itself, and virtio disk and network. Inside, arm64 has no CPUID "hypervisor" bit, but the hardware gives it away: GIC-0 on every interrupt line, millions of IPIs, a virtio disk with one queue per vCPU, steal time always 0, no /dev/kvm and no IOMMU (table in the closed block below).

The QEMU process on the Mac has 5 vCPU threads. While your training job in this VM is idle, what are those threads doing on macOS?




The guest's idle loop executes wfi, which exits to QEMU; QEMU then puts the vCPU thread to sleep in pselect until the guest's timer is due or another thread signals it ({{hvf_wfi and hvf_wait_for_ipi, QEMU v6.2.0|https://github.com/qemu/qemu/blob/v6.2.0/target/arm/hvf/hvf.c#L1011-L1021}}). That is OSTEP's "information gap" handled well: the VMM notices the guest went idle and gives the CPU back. Section 5 shows what it costs to wake such a thread.
