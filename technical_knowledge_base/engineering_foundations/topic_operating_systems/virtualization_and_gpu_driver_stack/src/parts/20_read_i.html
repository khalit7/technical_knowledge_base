9. One CUDA call down: from Python to the GPU

36

The problem. y = x @ w on CUDA tensors returns in a few microseconds and the GPU does the work later. Between the two sits a stack of libraries and a kernel driver that you normally never see, until it fails. This section names every layer, shows what each one does when there is no GPU (all run for real here), and reads the open part of NVIDIA's driver to see how work reaches the GPU without a system call. Writing kernels and the GPU's hardware are other pages' subjects: {{Topic: cuda-and-gpu-programming|n:3c65c17b0d0d81c39f34d5e070d783c1}} (its Compiler explorer has the same CUDA 13.4 toolchain) and {{Topic: hardware|n:3c65c17b0d0d8118beeefaed56da6f8e}}.

How the kernel side is organised. nvidia.ko registers one set of file operations for all its device files: open, unlocked_ioctl, mmap, poll, release ({{nvidia_fops, nv.c L259-269|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/kernel-open/nvidia/nv.c#L259-L269}}). A handful of ioctls are handled in the Linux layer, such as the version handshake (below); everything else goes to the resource manager (RM), the OS-independent core of the driver ({{default: rm_ioctl, nv.c L2981-2982|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/kernel-open/nvidia/nv.c#L2981-L2982}}). In RM everything is an object with a handle: a client (your process), a device, a subdevice, a memory allocation, a channel. The escapes allocate objects ({{NV_ESC_RM_ALLOC 0x2B|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/src/nvidia/arch/nvalloc/unix/src/escape.c#L461}}), free them, run control calls on them ({{NV_ESC_RM_CONTROL|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/src/nvidia/arch/nvalloc/unix/src/escape.c#L796}}), and map them into the process ({{NV_ESC_RM_MAP_MEMORY|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/src/nvidia/arch/nvalloc/unix/src/escape.c#L587}}, followed by an mmap of the device file, {{nvidia_mmap|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/kernel-open/nvidia/nv-mmap.c#L772}}). Unified memory has its own device, /dev/nvidia-uvm, with ioctls such as {{UVM_REGISTER_GPU and UVM_MIGRATE|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/kernel-open/nvidia-uvm/uvm_ioctl.h#L405}}.


The version handshake. Among the first things a client sends on /dev/nvidiactl is {{NV_ESC_CHECK_VERSION_STR|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/kernel-open/nvidia/nv.c#L2846-L2853}}. The kernel compares the client's version string with its own, exactly, or only up to the first dot if the client asks for "relaxed" checking; on a mismatch it logs "NVRM: API mismatch: the client ... has the version ..., but this kernel module has the version ... Please make sure that this kernel module and all NVIDIA driver components have the same version" ({{RmPerformVersionCheck, osapi.c L1199-1302|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/src/nvidia/arch/nvalloc/unix/src/osapi.c#L1199-L1302}}). That is the message in dmesg after a driver upgrade without a reboot: the new user-mode libraries meet the old module still loaded.


Launching work without a system call. A GPU channel is a queue of work: a pushbuffer in memory holds the commands ("methods": launch this kernel with these parameters, copy this, wait for that semaphore), a ring called the GPFIFO holds pointers to pushbuffer segments, and a doorbell register tells the GPU's host interface that the ring moved. The open driver's own unified-memory module submits work exactly like this, and its code shows each step: fill a GPFIFO entry pointing at the pushbuffer, a memory barrier, write the new put pointer, a write barrier, and ring the doorbell by storing a token into the doorbell register ({{internal_channel_submit_work, uvm_channel.c L984-1015|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/kernel-open/nvidia-uvm/uvm_channel.c#L984-L1015}}; {{write_gpu_put, uvm_turing_host.c L222-236|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/kernel-open/nvidia-uvm/uvm_turing_host.c#L222-L236}}). The doorbell lives in a "usermode" register page, the class VOLTA_USERMODE_A with NOTIFY_CHANNEL_PENDING at offset 0x90 ({{clc361.h|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/src/common/sdk/nvidia/inc/class/clc361.h#L27-L33}}), an object any RM client can allocate and map. Every piece is ordinary memory once mapped, so a process holding the mappings can launch with plain stores: no system call, no exit even in a VM.


What is verified and what is inferred
Verified from the open source: the device files, the ioctl protocol, the RM object model, the channel, GPFIFO and doorbell mechanism, and that kernel-side code (UVM) submits work with stores alone. Inferred: that the closed libcuda launches kernels the same way, by mapping its channels and the usermode page at context creation; it is the design the open interface supports, and the root page's description, but libcuda itself cannot be read. On a GPU machine, strace -f -c over a steady training loop confirms or refutes it in a minute. This replaces the root page's "not verified from a primary source" with this narrower statement.

Inside the binary: what the driver loads. Your program's GPU code is not in the CPU part of the executable. It sits in a section called .nv_fatbin, a container (fatbin) holding machine code for specific GPUs (cubin, SASS) and the portable intermediate form (PTX). The test program was built for sm_80 and sm_90 plus PTX for compute_90:




measured cuobjdump -lelf -lptx and readelf -S on the built executable (raw: src/raw/cuda.txt; the tab shows the cubin sizes and the PTX). The executable carries two cubins per architecture: the two holding vadd come from this file; the object file alone has one per architecture, so the two small cubins with no kernels were added when nvcc linked the program (most likely by its device-link step).


At load time the driver picks, for the GPU it finds: a cubin for the same major compute capability and an equal or lower minor ("a cubin with code compiled for compute capability 8.6 ... can be loaded and executed on GPUs with compute capability 8.6 or 8.9"); otherwise it JIT-compiles the PTX, which works on any equal or newer GPU, and caches the result in the "compute cache" (~/.nv/ComputeCache, CUDA_CACHE_PATH) ({{CUDA Programming Guide 1.3.4|https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html}}; {{environment variables|https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html}}). Since CUDA 12.3 modules load lazily by default: a kernel is loaded at its first launch, not at start-up (CUDA_MODULE_LOADING, {{Lazy Loading|https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/lazy-loading.html}}).
