6. Devices without the exits: virtio

36

The problem. The simplest way to give a guest a disk is to emulate a real one: the guest's normal driver pokes the device's registers, and every poke exits to the hypervisor, which pretends to be the hardware. A real disk controller's driver touches several registers per request, so one 4 KiB read costs several exits, plus an emulated interrupt with its own exits (section 5).

How virtio works. virtio is a device interface designed for VMs, where both sides know the other is software ({{Russell, virtio, 2008|https://doi.org/10.1145/1400097.1400108}}; {{OASIS VIRTIO 1.2 specification|https://docs.oasis-open.org/virtio/virtio/v1.2/virtio-v1.2.html}}). The guest and the hypervisor share a virtqueue in guest memory, made of three parts ({{include/uapi/linux/virtio_ring.h, Linux v5.10|https://github.com/torvalds/linux/blob/v5.10/include/uapi/linux/virtio_ring.h#L97-L135}}):

Descriptor tableentries of (guest address, length, flags, next): "here is a buffer" (struct vring_desc)
Available ringwritten by the guest: "these descriptor chains are ready for you" (struct vring_avail)
Used ringwritten by the device: "I finished these, this many bytes" (struct vring_used)

A request is three descriptors (a header saying "read sector N", the data buffer, a status byte). The guest adds them, bumps the available index, and only then kicks the device: one register write, one exit. The device side reads the request straight out of guest memory (for QEMU, its own memory), does the I/O, writes the used ring, and injects one interrupt. Both directions can be suppressed: with the event index feature (VIRTIO_RING_F_EVENT_IDX, bit 29), each side publishes "notify me only when your index passes N", so a busy queue needs neither a kick per request nor an interrupt per completion ({{vring_need_event|https://github.com/torvalds/linux/blob/v5.10/include/uapi/linux/virtio_ring.h#L216}}, used by {{virtqueue_kick_prepare_split|https://github.com/torvalds/linux/blob/v5.10/drivers/virtio/virtio_ring.c#L589-L608}}). Both of this VM's virtio devices offer it (section 3's feature bits).

Reading it. At queue depth 1, every request pays its own kick and its own interrupt, each with its exits; at depth 32, the event index lets one interrupt report about nine completions and the rate nearly quadruples. This is the I/O version of section 5's lesson: in a VM, notifications are the expensive part, and batching is how you buy them back.

Device in QEMU (here)The kick exits to QEMU in user space, which does the I/O with ordinary system calls on the disk image.
vhostThe device's data path moves into the host kernel (vhost-net; this kernel builds it as a module, CONFIG_VHOST_NET=m): the kick wakes a kernel thread, no trip to QEMU.
vhost-userThe data path runs in another user-space process polling the rings (DPDK for networks, SPDK for storage): no notifications at all while busy.
vDPA, passthroughThe NIC itself implements virtqueues (vDPA), or the guest gets a real device or a slice of one (sections 7, 8): the hypervisor leaves the data path.
When it bites in ML
  • Small random reads from a virtual disk at queue depth 1 (a dataset of millions of small files read one at a time) pay the notification costs on every file. Shards read sequentially with several outstanding requests do not.
  • The network of a cloud VM is a virtio or vendor paravirtual NIC unless RDMA NICs are passed through: the data path for checkpoints to object storage, not for NCCL on GPU clusters (section 7).
