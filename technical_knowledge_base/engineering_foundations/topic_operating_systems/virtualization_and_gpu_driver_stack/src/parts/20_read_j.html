10. Two versions: the driver and the runtime

The problem. A CUDA program depends on two independently installed things: the runtime it was built with (inside your image or wheel: torch.version.cuda) and the driver on the machine it runs on (host: nvidia-smi prints its version and the newest CUDA version it supports). Clusters upgrade drivers rarely and carefully; images change every week. "CUDA driver version is insufficient for CUDA runtime version" is the result of the two drifting apart.

Measured here. The runtime reported 13040 (CUDA 13.4) in every case. The driver version was 0 with no libcuda (case 1 of section 9), and 13040 with the 615.71.09 user-mode driver from the image's /usr/local/cuda/compat. The image also declares what it needs, for the NVIDIA container toolkit to check before starting it: NVIDIA_REQUIRE_CUDA=cuda>=13.4 plus a list of accepted driver branches for data-centre GPUs (brand=tesla,driver>=535,driver<536, and likewise 570, 580, 590, 595, 610). "If the version of the NVIDIA driver is insufficient to run this version of CUDA, the container does not start" ({{container toolkit, NVIDIA_REQUIRE_CUDA|https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/docker-specialized.html}}).

From {{CUDA Compatibility: why|https://docs.nvidia.com/deploy/cuda-compatibility/why-cuda-compatibility.html}} and {{minor version compatibility|https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html}}: minimum drivers CUDA 13.x ">= 580", 12.x ">= 525", 11.x ">= 450"; "Applications that compile device code to PTX will not work on older drivers". {{Forward compatibility|https://docs.nvidia.com/deploy/cuda-compatibility/forward-compatibility.html}}: "the cuda-compat-13-4 package is built using the NVIDIA driver libraries version 615", installed into /usr/local/cuda-13.4/compat/, and "This package only provides the libraries, and does not configure the system to find such libraries" (you set LD_LIBRARY_PATH); errors 803 CUDA_ERROR_SYSTEM_DRIVER_MISMATCH and 804 CUDA_ERROR_COMPAT_NOT_SUPPORTED_ON_DEVICE. Since CUDA 13.4 the Linux driver is no longer bundled with the toolkit.

Why forward compatibility can work at all. Section 9's version handshake is between the user-mode driver and the kernel module. Forward compatibility swaps only the user-mode half: a newer libcuda (from the compat package) talks to an older nvidia.ko. NVIDIA: "forward compatibility is defined between the kernel driver and the CUDA driver", which is also why it can JIT PTX where minor version compatibility cannot (the compat package brings its own PTX compiler, libnvidia-ptxjitcompiler, visible in this image's compat directory).

Will it run? Pick the host's driver branch and what your application was built with. The rules and the forward-compatibility matrix are NVIDIA's (Table 3 of the forward compatibility page, driver branches 535 to 615).
When it bites in ML
  • A new PyTorch wheel on an old cluster: PyTorch's CUDA wheels ship the runtime; the cluster's driver is older. Within the same CUDA major and with SASS for your GPU it runs (minor version compatibility); across a major version it needs the compat package or an older wheel. PyTorch's own error for an old driver: "The NVIDIA driver on your system is too old (found version ...)" ({{CUDAFunctions.cpp|https://github.com/pytorch/pytorch/blob/v2.14.1/c10/cuda/CUDAFunctions.cpp#L45-L54}}).
  • Custom kernels compiled to PTX only (a JIT extension, some Triton or third-party builds) fail under minor version compatibility even when everything else works.
  • A driver upgraded without a reboot: user-mode libraries and module disagree: section 9's "API mismatch" in dmesg.
