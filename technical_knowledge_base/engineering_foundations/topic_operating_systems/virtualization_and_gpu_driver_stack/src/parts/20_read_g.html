The problem. virtio is fast enough for disks and ordinary networks, but a GPU cannot be emulated at any useful speed: its driver talks to thousands of registers, and its whole point is raw throughput. The fastest answer is to give the guest the real device. But a device writes to memory by DMA (direct memory access: the device itself reads and writes RAM, without the CPU), using physical addresses. A guest driver programs the GPU with guest-physical addresses, which are wrong on the host; worse, a malicious guest could program it to write anywhere in the host's memory.

How it works: an MMU for devices. The IOMMU (Intel VT-d, AMD-Vi, ARM SMMU) sits between devices and memory and translates every DMA address through page tables of its own, one set per device domain. The hypervisor fills them so that the device's addresses are the guest's physical addresses and map to exactly the host pages backing that guest, and nothing else. The device sees the guest's world; the host stays safe. The same unit remaps the device's interrupts so they reach the right guest.

VFIO: the Linux interface. "The VFIO driver is an IOMMU/device agnostic framework for exposing direct device access to userspace, in a secure, IOMMU protected environment", and "from a device and host perspective, this simply turns the VM into a userspace driver" ({{VFIO documentation, Linux v6.12|https://github.com/torvalds/linux/blob/v6.12/Documentation/driver-api/vfio.rst}}). The steps of its own example:

int container = open("/dev/vfio/vfio", O_RDWR);          // an IOMMU context
int group = open("/dev/vfio/26", O_RDWR);              // the device's IOMMU group
ioctl(group, VFIO_GROUP_SET_CONTAINER, &container);
ioctl(container, VFIO_SET_IOMMU, VFIO_TYPE1_IOMMU);
ioctl(container, VFIO_IOMMU_MAP_DMA, &dma_map);       // "device address X is this memory": pins it
int device = ioctl(group, VFIO_GROUP_GET_DEVICE_FD, "0000:06:0d.0");
// then mmap the device's registers (BARs) and hand them to the guest

From {{vfio.rst lines 177-213|https://github.com/torvalds/linux/blob/v6.12/Documentation/driver-api/vfio.rst#L177-L213}}. Mapping pins the pages ({{vfio_pin_pages_remote|https://github.com/torvalds/linux/blob/v6.12/drivers/vfio/vfio_iommu_type1.c#L597}}), which is section 4's "a GPU VM cannot overcommit memory". Newer kernels add iommufd, a general replacement for the container.

IOMMU groups and ACS. The IOMMU can only isolate what it can tell apart. Devices behind a bridge that lets them talk to each other directly, without passing the IOMMU, are inseparable: "a group is a set of devices which is isolatable from all other devices in the system. Groups are therefore the unit of ownership used by VFIO" ({{vfio.rst lines 55-71|https://github.com/torvalds/linux/blob/v6.12/Documentation/driver-api/vfio.rst#L55-L71}}). PCIe switches use Access Control Services (ACS) to force device-to-device traffic up through the IOMMU, which makes small groups possible. That is exactly the tension with GPU clusters:

Peer-to-peer GPU traffic against isolation

NCCL's guide: on bare metal, "IO virtualization (also known as VT-d or IOMMU) can interfere with GPU Direct by redirecting all PCI point-to-point traffic to the CPU root complex, causing a significant performance reduction or even a hang", so bare-metal clusters disable ACS on their PCIe switches. In a VM that is not an option: "Virtual machines require ACS to function, hence disabling ACS is not an option. To run with maximum performance inside virtual machines, ATS needs to be enabled in network adapters" (ATS, Address Translation Services, lets the device cache IOMMU translations itself). And NCCL reads the PCI topology from /sys: "Having /sys expose a virtual PCI topology can result in sub-optimal performance" ({{NCCL GPU troubleshooting|https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting/gpu_troubleshooting.html}}).

What passthrough costs. Once set up, almost nothing on the data path: the GPU's registers are mapped into the guest by stage-2 page tables, so a doorbell write is an ordinary store, and the GPU's DMA goes through the IOMMU's translation cache. The costs are at the edges: pinning all guest memory at boot, IOTLB misses for scattered DMA, interrupts that must be remapped, and a guest that sees whatever PCI topology the hypervisor chose to show it.

When it bites in ML
  • Multi-GPU training inside VMs: whether GPU-to-GPU and GPU-to-NIC traffic goes peer to peer or through the CPU decides all-reduce bandwidth. Check what NCCL saw (NCCL_DEBUG=INFO) and the topology (nvidia-smi topo -m); a VM's real topology can be given to NCCL as an XML file (NCCL_TOPO_FILE; "by default, NCCL will load /var/run/nvidia-topologyd/virtualTopology.xml if present", {{NCCL environment variables|https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/env.html}}).
  • Slow or failing peer-to-peer with "OK" from nvidia-smi topo -p2p on bare metal: IOMMU settings or ACS, per the NCCL guide.
  • A GPU VM that takes minutes to boot: its memory is being pinned and mapped.

ls /sys/kernel/iommu_groups/; lspci -nnk | grep -A3 -i nvidia

On a host, a passed-through GPU shows Kernel driver in use: vfio-pci; inside the guest the same GPU shows nvidia.

A VM with a passed-through GPU is given 512 GiB of memory. Why can the host not lend 200 GiB of it to another VM while this one is idle?
Overcommit (balloon, KSM, host swap) relies on the host being able to take a page away and fault it back later. A device doing DMA cannot take a fault the way a CPU can, so VFIO pins every page it maps into the IOMMU, and QEMU maps all of guest RAM for the device.
