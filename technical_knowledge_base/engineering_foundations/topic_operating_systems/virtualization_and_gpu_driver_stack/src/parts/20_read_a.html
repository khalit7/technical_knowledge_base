In one screen

Almost every GPU you will train on in a cloud is reached through two extra layers that a laptop does not have. A hypervisor runs your whole operating system as a guest, so your "machine" is a virtual machine sharing a physical one; and a GPU driver stack turns each CUDA call into commands the GPU fetches from memory. Both layers are mostly invisible, until a wake-up costs ten times what it should, a container says "no CUDA-capable device", or a new image dies with "driver version is insufficient". This page takes both layers apart, from zero.

The root page, {{Topic: operating-systems|n:3f05c17b0d0d81c5a97ce991644af140}} section 9, gave the intuition in one screen. This page goes down to the code: the Linux kernel at the version that ran here (v5.10) and a current one (v6.12), the hypervisor that ran here (QEMU with Apple's Hypervisor.framework), NVIDIA's open kernel modules at 615.71.09, and the CUDA 13.4 runtime and user-mode driver run for real in a container with no GPU. Each mechanism follows one pattern: problem, how it works, what it costs (measured where it can be), when it bites in ML, the command that shows it, the fix.

Six things to remember
  1. A VM runs your code directly on the CPU and only stops it (a VM exit) for the few things the hypervisor must see. Each exit cost about 0.92 µs here; virtualization is cheap until something exits thousands of times a second (section 2).
  2. Interrupts are the expensive part. Waking a thread on another CPU took 12.7 times as long as on the same CPU in this VM, because the inter-processor interrupt and the sleeping virtual CPU both go through the hypervisor (section 5; this answers the question the {{Scheduling|n:3f05c17b0d0d81ed9c18cc47c6bfdf76}} and {{Concurrency|n:3f05c17b0d0d8112ad1af99308fa913f}} pages left open).
  3. A whole GPU in a VM is a real GPU handed to the guest through the IOMMU (passthrough), so CUDA itself runs at full speed; what differs is topology, peer-to-peer traffic and pinned memory (section 7).
  4. Sharing a GPU is a choice of isolation: time slicing and MPS share memory and faults; MIG splits the hardware into up to seven isolated instances ({{Sharing a GPU|#t-share}} tab).
  5. Steady-state CUDA launches make no system call: the driver writes commands into memory and rings a doorbell register; the ioctls happen at start-up and for memory management (section 9, {{One CUDA call|#t-cuda}} tab).
  6. Two versions, two places: the runtime comes with your image, the driver with the host. A runtime newer than the driver's major family needs the compatibility package or a new driver (section 10).

How this page was measured. Linux runs: Docker Desktop's Linux VM on an Apple M1 Pro (Linux 5.10.104-linuxkit, arm64, 5 virtual CPUs, about 10 GB), October 2026, images kb-os-lab:1 (the root's lab image) and kb-os-virt:1 (the CUDA topic's kb-gpu-lab:1: CUDA 13.4.2 toolkit for arm64, plus strace). Containers were not privileged; strace needed --cap-add SYS_PTRACE, and one CUDA case used --device-cgroup-rule 'c 195:* rwm', both stated where used. macOS runs, labelled as contrasts: the hypervisor process that runs the VM, and a tiny VM of our own built on Apple's Hypervisor.framework. There is no GPU here: everything above the kernel driver was run for real; the kernel driver and the GPU are taught from NVIDIA's open source and documentation and tagged not run here. Labels: measured ran here; source read from source or documentation. Timings on a shared laptop VM vary from run to run, so each is a median of three runs and the raw files show the spread.
