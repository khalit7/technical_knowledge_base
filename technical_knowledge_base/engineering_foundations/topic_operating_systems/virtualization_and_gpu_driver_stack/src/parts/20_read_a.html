The idea in one screen

Both layers between your training code and a cloud GPU get out of the way on the hot path: guest code runs directly on the CPU and a CUDA launch is a few stores into mapped memory plus a doorbell, so you pay only at the boundaries: a VM exit (about 0.92 µs here) each time the guest touches what the hypervisor must see, and a system call into the driver at start-up, allocation and errors.

Two stacks, one rule: the hot path never asks permission

First: the VM this page ran in (QEMU 5.2 on Apple's Hypervisor.framework; a cloud uses KVM or Nitro in the same place). Second: one CUDA call, from PyTorch to the GPU, as NVIDIA's open kernel modules 615.71.09 lay it out. Hypervisor (VMM)
the program that runs whole operating systems as guests, as a kernel runs processes.
VM exit
the CPU stopping the guest and handing control to the hypervisor with a reason, then resuming it.
Nested paging (EPT, stage 2)
a second page table, owned by the hypervisor, from guest-physical to host-physical addresses.
IPI
an inter-processor interrupt: one CPU interrupting another, for example to wake a thread.
virtio, virtqueue
a device interface made for VMs: shared rings in guest memory instead of emulated registers.
IOMMU
an MMU for devices: it translates and checks every DMA address a device issues.
MIG, MPS, time slicing
three ways to share one GPU, from hardware partitions to taking turns.
User-mode driver
libcuda.so.1, installed with the host's driver; the kernel driver is nvidia.ko.
GSP
the GPU System Processor: a processor on Turing and later GPUs that runs the driver's resource manager as firmware.
Channel, doorbell
a GPU work queue in memory, and the register store that tells the GPU the queue moved.

How this page was measured, and the OSTEP chapter map (provenance)

Linux runs: Docker Desktop's Linux VM on an Apple M1 Pro (Linux 5.10.104-linuxkit, arm64, 5 virtual CPUs, about 10 GB), October 2026, images kb-os-lab:1 (the root's lab image) and kb-os-virt:1 (the CUDA topic's kb-gpu-lab:1: CUDA 13.4.2 toolkit for arm64, plus strace). Containers were not privileged; strace needed --cap-add SYS_PTRACE, and one CUDA case used --device-cgroup-rule 'c 195:* rwm', both stated where used. macOS runs, labelled as contrasts: the hypervisor process that runs the VM, and a tiny VM of our own built on Apple's Hypervisor.framework. There is no GPU here: everything above the kernel driver was run for real; the kernel driver and the GPU are taught from NVIDIA's open source and documentation and tagged not run here. Labels: measured ran here; source read from source or documentation. Timings on a shared laptop VM vary from run to run, so each is a median of three runs and the raw files show the spread. Scripts and raw outputs: src/exp/ and src/raw/ in the repository. The root page, section 9, gave the intuition in one screen; this page goes down to the code: the Linux kernel at the version that ran here (v5.10) and a current one (v6.12), QEMU with Apple's Hypervisor.framework, NVIDIA's open kernel modules at 615.71.09, and the CUDA 13.4 runtime and user-mode driver run for real in a container with no GPU.
