4. Memory: two translations, and the 24-step page walk

Appendix B, 19, 20

The problem. The guest kernel believes it owns "physical" memory from address 0 and builds page tables onto it. That memory is really part of the hypervisor's process (QEMU's 10 GiB here), scattered across the host's RAM. So every guest access needs two translations: guest virtual to guest physical (the guest's tables), then guest physical to host physical (tables the hypervisor owns and the guest cannot see). {{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}} owns the first translation, the TLB and huge pages; this is the second layer.

Shadow page tables, then nested paging. Before hardware help, the hypervisor kept a shadow page table from guest virtual straight to host physical and write-protected the guest's own tables, so every page-table update exited to be mirrored. With nested paging (Intel EPT, AMD NPT, ARM stage 2) the CPU walks both sets itself, the guest edits its tables with no exits, and the TLB caches the combined result tagged with a VM identifier (VMID on arm64, VPID on Intel) so switching VMs does not flush it. The price moves to the TLB miss: every pointer in the guest's walk is guest-physical and needs a host walk of its own.

Fig. 4: one TLB miss in a VM, each plate one memory reference

Predict before it plays: with 4 guest levels and 4 host levels, how many memory reads does one miss take?

  1. A TLB miss in a VM. The guest's table register holds a guest-physical address, so the CPU cannot read even the first guest table until the host's tables have translated that address. The four large plates are the guest's tables; the small plates in front of each are the host's (stage-2) tables. Every plate is one memory reference.
  2. Guest level 0: a host walk, then the entry. Four host reads turn the table's guest-physical address into a host-physical one; then one read of the guest's own entry: 5 references so far.
  3. Guest level 1: the same again. The entry gave the next table's address, again guest-physical: another four host reads plus the entry, 10.
  4. Guest level 2. Four host reads and the entry: 15.
  5. Guest level 3. Four host reads and the entry: 20. This entry gives the data page's guest-physical address.
  6. The data page needs one more host walk. Four reads: 24 references in all for one miss, against 4 without a VM.
  7. The TLB caches the combined result. One entry from guest virtual to host physical, tagged with the VM's identifier (VMID on arm64, VPID on Intel) so switching VMs does not flush it. Page-walk caches keep most real misses far shorter than this worst case.
  8. Huge pages shorten both walks. With 2 MiB pages backing the guest on the host, every host walk ends one level early: 19 references. With 2 MiB pages in both stages: 15.

derived with g guest levels and h host levels, each of the g guest table pointers needs a host walk (h reads) plus the read of the guest entry, and the final data address one more host walk: g(h+1) + h = (g+1)(h+1) - 1 references. Analysed in {{Bhargava et al., ASPLOS 2008|https://doi.org/10.1145/1346281.1346286}}, which also proposed the page-walk caches that keep most misses far shorter in practice.

That already includes the stage-2 walk; separating it needs the same test on bare metal, which this setup cannot run. Most misses are far shorter than the worst case because the walk's upper levels are cached.
When it bites in ML
  • Large, random memory access: embedding tables, a shuffled in-memory dataset, a hash join in a data pipeline. Sequential tensor work hits the TLB and barely notices.
  • Huge pages help twice in a VM, and only if both layers use them: transparent huge pages in the guest, and huge pages backing the guest on the host (the cloud's choice, not yours).

Memory overcommit, and why GPU VMs cannot do it. Because guest memory is memory of the hypervisor's process, a host can promise its VMs more than it has: a balloon driver in the guest gives pages back on request, KSM merges identical pages across VMs, and the host can swap. A VM with a passed-through device cannot: the device writes guest memory by DMA at any moment, so every page it might touch must stay put. VFIO pins the pages it maps for a device, and QEMU maps all of guest RAM for it, so a GPU VM's whole memory is pinned when it starts: one reason large GPU VMs boot slowly and cannot be overcommitted.
