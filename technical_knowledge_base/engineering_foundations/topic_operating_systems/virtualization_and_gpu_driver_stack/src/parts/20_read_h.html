8. SR-IOV and the ways to share one GPU

not run here: no GPU; from NVIDIA's MIG, MPS, vGPU and GPU Operator documentation and the kernel's SR-IOV documentation.

The problem. Passthrough gives one guest a whole device. An 80 GB data-centre GPU is far more than a notebook, a small model's inference server or a CI job needs, and an idle GPU is expensive. The question is how to split one GPU between several processes, containers or VMs, and what each split gives up.

SR-IOV first, because NICs use it. Single Root I/O Virtualization lets one PCIe device present a physical function (PF, the full device, managed by the host) and many lightweight virtual functions (VFs), each with its own PCI identity, so each can be passed through to a different VM with section 7's machinery. On Linux you create them by writing a number to /sys/bus/pci/devices/<address>/sriov_numvfs ({{pci-iov-howto.rst, Linux v6.12|https://github.com/torvalds/linux/blob/v6.12/Documentation/PCI/pci-iov-howto.rst#L77}}). This is how a GPU VM gets its own slice of an InfiniBand or RoCE NIC for RDMA.

Why GPUs are harder: how the GPU itself schedules. A GPU runs work from one CUDA context (the per-process state: address space, loaded kernels, streams) concurrently, but "work launched to the compute engine from work queues belonging to different CUDA contexts cannot execute concurrently": between processes the GPU time-slices ({{MPS architecture|https://docs.nvidia.com/deploy/mps/architecture.html}}). Time slicing from the {{GPU Operator guide|https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/gpu-sharing.html}}: "A request for more than one time-sliced GPU does not guarantee that the pod receives access to a proportional amount of GPU compute power." vGPU's time-sliced schedulers are "best effort" (the default), "equal share" and "fixed share" ({{vGPU scheduling policies|https://docs.nvidia.com/vgpu/latest/grid-vgpu-user-guide/changing-vgpu-scheduling-policy.html}}).

MIG in practice. A MIG-capable GPU (A100 and later data-centre parts) is enabled once (on A100 and A30, "setting MIG mode ... requires a GPU reset"), then carved into GPU instances from fixed profiles, each named by its compute slices and memory: on an H100 80GB, 1g.10gb (1/7 of the SMs, 1/8 of the memory, up to 7 of them), 2g.20gb, 3g.40gb, 4g.40gb, 7g.80gb ({{MIG supported profiles|https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/supported-mig-profiles.html}}). Profiles can only sit at certain positions, so the order you create them in matters; the {{Sharing a GPU|#t-share}} tab lets you place them on an A100 40GB with NVIDIA's published placement rules. Each instance then appears to CUDA as its own device: CUDA_VISIBLE_DEVICES=MIG-<uuid>.

When it bites in ML
  • Training wants whole GPUs. Sharing is for inference, notebooks, small fine-tunes and CI. A training job on a time-sliced GPU shares memory with strangers and can be slowed or killed by their faults.
  • "My job got slower and nothing changed" on a shared node: another pod was scheduled on the same time-sliced GPU. nvidia-smi on the node lists every process on the GPU.
  • MIG memory is a hard wall: a 1g.10gb instance is a 10 GB GPU to PyTorch, and NCCL between MIG instances is limited ("only P2P between MIG instances on the same GPU is supported" with R570, {{MIG deployment considerations|https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/deployment-considerations.html}}).
