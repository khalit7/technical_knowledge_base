8. SR-IOV and the ways to share one GPU

not run here: no GPU; from NVIDIA's MIG, MPS, vGPU and GPU Operator documentation and the kernel's SR-IOV documentation.

The problem. Passthrough gives one guest a whole device. An 80 GB data-centre GPU is far more than a notebook, a small model's inference server or a CI job needs, and an idle GPU is expensive. The question is how to split one GPU between several processes, containers or VMs, and what each split gives up.

SR-IOV first, because NICs use it. Single Root I/O Virtualization lets one PCIe device present a physical function (PF, the full device, managed by the host) and many lightweight virtual functions (VFs), each with its own PCI identity, so each can be passed through to a different VM with section 7's machinery. On Linux you create them by writing a number to /sys/bus/pci/devices/<address>/sriov_numvfs ({{pci-iov-howto.rst, Linux v6.12|https://github.com/torvalds/linux/blob/v6.12/Documentation/PCI/pci-iov-howto.rst#L77}}). This is how a GPU VM gets its own slice of an InfiniBand or RoCE NIC for RDMA.

Why GPUs are harder: how the GPU itself schedules. A GPU runs work from one CUDA context (the per-process state: address space, loaded kernels, streams) concurrently, but "work launched to the compute engine from work queues belonging to different CUDA contexts cannot execute concurrently": between processes the GPU time-slices ({{MPS architecture|https://docs.nvidia.com/deploy/mps/architecture.html}}). Every sharing scheme is a different answer to that:

Three ways to put jobs A and B on one GPU: take turns, merge, or cut

Each panel: the GPU's SMs (up) over time (across), and its memory below. Time slicing runs one context at a time and shares all memory; MPS merges both clients' work onto the SMs at once, with separate address spaces but shared memory bandwidth and no full fault isolation; MIG gives each its own SMs, L2 slices and memory. vGPU puts either form behind a hypervisor; passthrough is one whole GPU per VM. MIG in practice. A MIG-capable GPU (A100 and later data-centre parts) is enabled once (on A100 and A30, "setting MIG mode ... requires a GPU reset"), then carved into GPU instances from fixed profiles, each named by its compute slices and memory: on an H100 80GB, 1g.10gb (1/7 of the SMs, 1/8 of the memory, up to 7 of them), 2g.20gb, 3g.40gb, 4g.40gb, 7g.80gb ({{MIG supported profiles|https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/supported-mig-profiles.html}}). Profiles can only sit at certain positions, so the order you create them in matters. Each instance then appears to CUDA as its own device: CUDA_VISIBLE_DEVICES=MIG-<uuid>.

"The syntax of the placement is {<index>}:<GPU Slice Count>". Instances may not overlap, and the compute slices (the number before "g") add up to at most 7. The guide warns: "As GPU Instances are created and destroyed at different locations, fragmentation can occur, and the physical position of one GPU Instance will play a role in which other GPU Instances can be instantiated next to it" ({{MIG concepts|https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/concepts.html}}); and "due to a known issue with the APIs, the profile ID 9 or 3g.20gb must be specified first", because the driver's automatic placement of smaller instances can take the positions a 3g.20gb needs. Try the "1-1-2, then 3g" example to see it. The H100 80GB has the same seven profiles at twice the memory (1g.10gb, 1g.10gb+me, 1g.20gb, 2g.20gb, 3g.40gb, 4g.40gb, 7g.80gb) ({{supported profiles|https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/supported-mig-profiles.html}}); its placement listing is not reproduced here.

After creating GPU instances you create compute instances inside them (nvidia-smi mig -cgi 9,3g.20gb -C does both), and each appears to CUDA as its own device: CUDA_VISIBLE_DEVICES=MIG-<uuid>. "The created MIG devices are not persistent across system reboots."

When it bites in ML
  • Training wants whole GPUs. Sharing is for inference, notebooks, small fine-tunes and CI. A training job on a time-sliced GPU shares memory with strangers and can be slowed or killed by their faults.
  • "My job got slower and nothing changed" on a shared node: another pod was scheduled on the same time-sliced GPU. nvidia-smi on the node lists every process on the GPU.
  • MIG memory is a hard wall: a 1g.10gb instance is a 10 GB GPU to PyTorch, and NCCL between MIG instances is limited ("only P2P between MIG instances on the same GPU is supported" with R570, {{MIG deployment considerations|https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/deployment-considerations.html}}).
