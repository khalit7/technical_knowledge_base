1. Why virtual machines, and what makes a CPU virtualizable

Appendix B, 6

The problem. A cloud provider owns a big machine and wants to sell slices of it to strangers. Each customer wants root, their own kernel version, their own drivers, and the certainty that the neighbour cannot read their memory or crash their kernel. A container (the {{Containers and isolation|n:3f05c17b0d0d8156a841e4bf28f11293}} page) cannot promise that: every container shares one kernel, so a kernel bug is everyone's bug. A virtual machine (VM) gives each customer a whole kernel of their own. The program that makes this possible is the hypervisor (also called a virtual machine monitor, VMM): it does for operating systems what an operating system does for processes.

How it works: limited direct execution, one level down. The root page explained how a kernel runs your program directly on the CPU and only takes control back on a system call, a fault or a timer interrupt (OSTEP chapter 6). A hypervisor does the same to a whole kernel: the guest kernel's instructions run directly on the real CPU, at full speed, and the hypervisor only takes over when the guest does something it must not do alone, such as touch a device or reprogram the interrupt controller. That hand-over is a trap; in a VM it is called a VM exit. OSTEP's appendix calls the key method extending "the notion of limited direct execution" so the VMM can "interpose on key events (such as traps)" ({{OSTEP Appendix B|https://pages.cs.wisc.edu/~remzi/OSTEP/vmm-intro.pdf}}).

Which instructions must trap. In 1974 Popek and Goldberg stated the condition (Theorem 1, paraphrased): a VMM can be built for a machine if every sensitive instruction (one that reads or changes the machine's control state) is also privileged (traps when run outside the most privileged mode) ({{Popek and Goldberg, CACM 1974|https://doi.org/10.1145/361011.361073}}). Then the guest kernel can run deprivileged, and every sensitive thing it does traps to the hypervisor, which emulates it on the guest's virtual state. This is trap and emulate.

x86 broke the rule. Robin and Irvine examined the Pentium's instruction set in 2000 and "found that seventeen instructions violate" the requirement, for example POPF, which in user mode silently ignores a change to the interrupt flag instead of trapping, and SGDT/SIDT, which reveal where the real descriptor tables are ({{Robin and Irvine, USENIX Security 2000|https://www.usenix.org/legacy/events/sec2000/full_papers/robin/robin_html/index.html}}). A guest kernel that executes POPF thinking it disabled interrupts would be wrong, and the hypervisor would never know. Three answers followed:

Binary translationVMware's approach: scan the guest kernel's code before it runs and rewrite the problem instructions into safe sequences. Works on any x86; complex.
ParavirtualizationXen's approach: change the guest kernel so it calls the hypervisor directly (a hypercall) instead of executing sensitive instructions. Fast; needs a modified guest. OSTEP: such a system "can be made to be nearly as efficient a system without a VMM".
Hardware supportIntel VT-x and AMD-V added a new mode for the hypervisor (VMX root) and made the guest's sensitive instructions exit to it; ARM added EL2. Every cloud uses this now, plus paravirtual devices (section 6).

Who is the hypervisor? In a type 1 (bare-metal) design the hypervisor is the thing that boots (Xen, VMware ESXi). In a type 2 (hosted) design it is a program on an ordinary OS: here, QEMU running on macOS and asking the macOS kernel, through Hypervisor.framework, to enter the guest (section 3). Linux's KVM blurs the two: a kernel module turns Linux itself into the hypervisor, and a user-space program (QEMU, Firecracker, cloud-hypervisor) provides the virtual devices. AWS's Nitro System uses "a custom-developed, minimized hypervisor based on KVM" with device work moved onto dedicated cards ({{AWS Nitro whitepaper|https://docs.aws.amazon.com/whitepapers/latest/security-design-of-aws-nitro-system/the-nitro-system-journey.html}}).

Inside a hardware-virtualized VM, which loop slows down more against bare metal: a million getpid() system calls, or a million 4 KiB disk reads?
A system call goes from EL0 to the guest kernel at EL1 without involving the hypervisor at all: hardware virtualization exists so that this path does not exit. A disk read touches a (virtual) device: the guest writes a device register to say "go", which exits to the hypervisor, and the completion arrives as an interrupt the hypervisor injects. Sections 2, 5 and 6 measure those exits.

2. A VM exit, measured

Appendix B

What an exit is. When the guest does something the hypervisor asked to see, the CPU stops the guest, saves its registers, switches to the hypervisor's privilege level and jumps to the hypervisor's handler with a syndrome describing why (on arm64 the exception class, EC; on x86 the exit reason). The handler emulates the effect, then resumes the guest. Everything a guest does is either free (runs directly) or costs one of these round trips.

The hypervisor's API, as a program. KVM exposes all of this to an ordinary Linux process through one device file. The shape of every VMM (QEMU, Firecracker) is this loop; LWN's {{Using the KVM API|https://lwn.net/Articles/658511/}} builds a complete one in about 100 lines.

a minimal KVM monitor (C; the calls of LWN's example; not run here: this VM has no /dev/kvm)
int kvm  = open("/dev/kvm", O_RDWR);
int vm   = ioctl(kvm, KVM_CREATE_VM, 0);             // a VM is a file descriptor
void *mem = mmap(NULL, 0x1000, PROT_READ|PROT_WRITE, MAP_SHARED|MAP_ANONYMOUS, -1, 0);
// guest "physical" memory is ordinary memory of this process
struct kvm_userspace_memory_region r = { .guest_phys_addr = 0x1000, .memory_size = 0x1000, .userspace_addr = (long)mem };
ioctl(vm, KVM_SET_USER_MEMORY_REGION, &r);
int vcpu = ioctl(vm, KVM_CREATE_VCPU, 0);             // a virtual CPU is another fd
struct kvm_run *run = mmap(NULL, mmap_size, PROT_READ|PROT_WRITE, MAP_SHARED, vcpu, 0);
for (;;) {
    ioctl(vcpu, KVM_RUN, 0);                          // enter the guest; returns on an exit
    switch (run->exit_reason) {
    case KVM_EXIT_IO:   /* the guest touched an I/O port: emulate the device */  break;
    case KVM_EXIT_MMIO: /* a device register in memory: emulate it */          break;
    case KVM_EXIT_HLT:  return 0;                                    // the guest idled
    }
}

Only exits the kernel cannot finish itself come back to user space; many (timer, some interrupt work) are handled inside KVM.

Measured: our own tiny VM on this laptop. This VM cannot run KVM (no /dev/kvm: the M1 Pro has no nested virtualization, see section 3). Reading it. About 0.9 µs per exit, whatever the reason, is the floor: the hardware switch to EL2, Apple's kernel code, the return to our user-space loop, and back. That is roughly three system calls' worth (the root measured a read system call at 0.316 µs). It is cheap once, and the whole design of a fast VM is about keeping it rare: the guest's own system calls, page faults and arithmetic never exit. What does exit in practice:

When it bites in ML
  • A GPU's work does not exit: with passthrough the GPU's registers are mapped straight into the guest, so writing a doorbell is an ordinary store (sections 7 and 9). The CUDA kernel itself never notices the VM.
  • What exits is the CPU side: interrupts, idle and wake-ups (section 5), disk and network I/O (section 6). A data loader with many threads handing work to each other is the part of a training job that pays.
