1. Virtual machines against containers, and what makes a CPU virtualizable

Appendix B, 6

The problem. A cloud provider sells slices of one big machine to strangers. Each wants root, their own kernel and drivers, and the certainty that the neighbour cannot read their memory or crash their kernel. A container cannot promise that: every container shares one kernel, so a kernel bug is everyone's bug. A virtual machine (VM) gives each customer a whole kernel of their own; the hypervisor (or virtual machine monitor, VMM) does for operating systems what an operating system does for processes.

Where the isolation boundary sits

Containers: one kernel, separated by namespaces and cgroups (the {{Containers and isolation|n:3f05c17b0d0d8156a841e4bf28f11293}} page owns how). VMs: one kernel per guest, separated by the CPU's virtualization hardware, so a guest kernel crash or exploit stays in its guest. The price is the boundary crossings of sections 2 to 6. Sandboxes for untrusted code (Firecracker, gVisor) sit between the two and are on the containers page.

How it works: limited direct execution, one level down. A kernel runs your program directly on the CPU and takes control back only on a system call, fault or timer (OSTEP chapter 6). A hypervisor does the same to a whole kernel: the guest kernel's instructions run directly, at full speed, and the hypervisor takes over only when the guest does something it must not do alone, such as touch a device or reprogram the interrupt controller. That hand-over is a trap; in a VM it is a VM exit. OSTEP's appendix calls it extending "the notion of limited direct execution" so the VMM can "interpose on key events (such as traps)" ({{OSTEP Appendix B|https://pages.cs.wisc.edu/~remzi/OSTEP/vmm-intro.pdf}}).

Which instructions must trap. Popek and Goldberg (1974, Theorem 1, paraphrased): a VMM can be built if every sensitive instruction (one that reads or changes the machine's control state) is also privileged (traps outside the most privileged mode). Then the deprivileged guest kernel traps on every sensitive act and the hypervisor emulates it: trap and emulate. x86 broke the rule: Robin and Irvine "found that seventeen instructions violate" it, for example POPF, which in user mode silently ignores a change to the interrupt flag instead of trapping. Three answers followed:

Binary translationVMware: rewrite the guest kernel's problem instructions before they run. Any x86; complex.
ParavirtualizationXen: change the guest kernel to call the hypervisor directly (a hypercall). Fast; needs a modified guest.
Hardware supportIntel VT-x and AMD-V added a mode for the hypervisor (VMX root) and made sensitive guest instructions exit to it; ARM added EL2. Every cloud uses this, plus paravirtual devices (section 6).

Who is the hypervisor? Type 1 (bare metal): the hypervisor is what boots (Xen, VMware ESXi). Type 2 (hosted): a program on an ordinary OS; here, QEMU on macOS asking the macOS kernel, through Hypervisor.framework, to enter the guest. Linux's KVM blurs the two: a kernel module turns Linux into the hypervisor, and a user-space program (QEMU, Firecracker, cloud-hypervisor) provides the virtual devices. AWS's Nitro System uses "a custom-developed, minimized hypervisor based on KVM" with device work moved onto dedicated cards ({{AWS Nitro whitepaper|https://docs.aws.amazon.com/whitepapers/latest/security-design-of-aws-nitro-system/the-nitro-system-journey.html}}).

The sources and examples behind trap and emulate (depth)

Popek and Goldberg: {{CACM 1974|https://doi.org/10.1145/361011.361073}}. Robin and Irvine examined the Pentium's instruction set in 2000 ({{USENIX Security 2000|https://www.usenix.org/legacy/events/sec2000/full_papers/robin/robin_html/index.html}}); besides POPF, SGDT/SIDT reveal where the real descriptor tables are. A guest kernel that executes POPF thinking it disabled interrupts would be wrong, and the hypervisor would never know. Binary translation scans the guest kernel's code before it runs and rewrites the problem instructions into safe sequences. On paravirtualization OSTEP says such a system "can be made to be nearly as efficient a system without a VMM".

Inside a hardware-virtualized VM, which loop slows down more against bare metal: a million getpid() system calls, or a million 4 KiB disk reads?
A system call goes from EL0 to the guest kernel at EL1 without involving the hypervisor at all: hardware virtualization exists so that this path does not exit. A disk read touches a (virtual) device: the guest writes a device register to say "go", which exits to the hypervisor, and the completion arrives as an interrupt the hypervisor injects. Sections 2, 5 and 6 measure those exits.

2. A VM exit, measured

Appendix B

What an exit is. When the guest does something the hypervisor asked to see, the CPU stops the guest, saves its registers, switches to the hypervisor's privilege level and jumps to its handler with a syndrome saying why (on arm64 the exception class, EC; on x86 the exit reason). The handler emulates the effect and resumes the guest. Everything a guest does is either free (runs directly) or costs one of these round trips.

A system call never leaves the guest; a device register store does

Privilege levels over time on arm64. The guest's getpid() goes EL0 to EL1 and back, exactly as on bare metal. A store to an emulated device register (MMIO) exits from EL1 to EL2, runs the hypervisor's handler, and resumes: 0.92 µs measured on this laptop.

Measured: our own tiny VM on this laptop. This VM cannot run KVM (no /dev/kvm: the M1 Pro has no nested virtualization), but macOS's Hypervisor.framework has the same shape (create a VM, map memory, create a vCPU, hv_vcpu_run until an exit). src/exp/hvf_exits.c builds a VM with one vCPU and two instructions of guest code, an instruction that exits and a branch back to it, and times one exit round trip 20,000 times.

Reading it. About 0.9 µs per exit, whatever the reason, is the floor: the switch to EL2, Apple's kernel code, the return to our user-space loop, and back. That is roughly three system calls' worth (the root measured a read system call at 0.316 µs). Cheap once; a fast VM is designed to keep it rare. The guest's own system calls, page faults and arithmetic never exit; idle, device registers, timer and interrupt-controller registers, hypercalls and host interrupts do.

When it bites in ML
  • A GPU's work does not exit: with passthrough the GPU's registers are mapped straight into the guest, so writing a doorbell is an ordinary store (sections 7 and 9). The CUDA kernel itself never notices the VM.
  • What exits is the CPU side: interrupts, idle and wake-ups (section 5), disk and network I/O (section 6). A data loader with many threads handing work to each other is the part of a training job that pays.

The hypervisor's API as a program: a minimal KVM monitor, and where each exit is handled (depth)

KVM exposes all of this to an ordinary Linux process through one device file. The shape of every VMM (QEMU, Firecracker) is this loop; LWN's {{Using the KVM API|https://lwn.net/Articles/658511/}} builds a complete one in about 100 lines.

a minimal KVM monitor (C; the calls of LWN's example; not run here: this VM has no /dev/kvm)
int kvm  = open("/dev/kvm", O_RDWR);
int vm   = ioctl(kvm, KVM_CREATE_VM, 0);             // a VM is a file descriptor
void *mem = mmap(NULL, 0x1000, PROT_READ|PROT_WRITE, MAP_SHARED|MAP_ANONYMOUS, -1, 0);
// guest "physical" memory is ordinary memory of this process
struct kvm_userspace_memory_region r = { .guest_phys_addr = 0x1000, .memory_size = 0x1000, .userspace_addr = (long)mem };
ioctl(vm, KVM_SET_USER_MEMORY_REGION, &r);
int vcpu = ioctl(vm, KVM_CREATE_VCPU, 0);             // a virtual CPU is another fd
struct kvm_run *run = mmap(NULL, mmap_size, PROT_READ|PROT_WRITE, MAP_SHARED, vcpu, 0);
for (;;) {
    ioctl(vcpu, KVM_RUN, 0);                          // enter the guest; returns on an exit
    switch (run->exit_reason) {
    case KVM_EXIT_IO:   /* the guest touched an I/O port: emulate the device */  break;
    case KVM_EXIT_MMIO: /* a device register in memory: emulate it */          break;
    case KVM_EXIT_HLT:  return 0;                                    // the guest idled
    }
}

Only exits the kernel cannot finish itself come back to user space; many (timer, some interrupt work) are handled inside KVM.
