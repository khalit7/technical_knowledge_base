5. Interrupts, and why a cross-CPU wake-up costs ten times more here

Appendix B, 26 to 28

The question the sibling pages left open. The {{Scheduling|n:3f05c17b0d0d81ed9c18cc47c6bfdf76}} page measured a context switch on one CPU at 1.30 to 1.56 µs but a hand-off between two CPUs at 25.6 to 51.4 µs in this VM; the {{Concurrency|n:3f05c17b0d0d8112ad1af99308fa913f}} page found the same when a futex woke a thread on another CPU. Both suspected the hypervisor. This section measures it and follows the path through the hypervisor's source.

Inter-processor interrupts. An interrupt is a signal that makes a CPU stop what it is doing and run a handler. An inter-processor interrupt (IPI) is one CPU interrupting another. Linux uses two kinds all the time: a reschedule IPI ("a thread you should run just woke up") and a function-call IPI ("run this function on your CPU now"). When thread A on CPU 1 writes to a pipe and thread B, asleep on it, last ran on CPU 2, the kernel marks B runnable on CPU 2's run queue and calls {{resched_curr|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/core.c#L609-L628}}, which sends CPU 2 a reschedule IPI ({{smp_send_reschedule|https://github.com/torvalds/linux/blob/v5.10/arch/arm64/kernel/smp.c#L1006-L1008}}). The only way to skip it is a CPU that is idle but polling a flag ({{set_nr_if_polling|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/core.c#L482}}); an arm64 CPU idles in wfi ({{__cpu_do_idle|https://github.com/torvalds/linux/blob/v5.10/arch/arm64/kernel/process.c#L75-L78}}), so it always needs the interrupt.

Measured. Two processes pass one byte back and forth through two pipes (the root's method), and a third test uses membarrier(), a system call that sends a function-call IPI to every CPU running a thread of the caller and waits for each to answer ({{membarrier.c L170 and L264, Linux v5.10|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/membarrier.c#L264}}): a direct way to time an IPI round trip from user space. Reading it. Moving the byte between CPUs through memory costs 0.054 µs, so the cache-coherence hardware is fast. What is slow is the interrupt: one IPI round trip costs about 14.5 µs (membarrier with one peer, minus the bare system call), and a sleeping wake-up 12.7 times a same-CPU switch. Three IPIs at once cost 30.2 µs each, 2.1 times what three independent ones would: they queue behind each other somewhere.

Where the time goes: the path through this hypervisor. Section 3 found that this guest's interrupt controller is a GICv2, emulated by QEMU. On a GICv2, sending an IPI is a store to a distributor register ({{gic_ipi_send_mask writes GIC_DIST_SOFTINT|https://github.com/torvalds/linux/blob/v5.10/drivers/irqchip/irq-gic.c#L800-L808}}), and taking one is a load from the CPU interface to acknowledge it and a store to end it ({{gic_handle_irq: GIC_CPU_INTACK, GIC_CPU_EOI|https://github.com/torvalds/linux/blob/v5.10/drivers/irqchip/irq-gic.c#L334-L348}}). All three are device registers, so all three are VM exits into QEMU, which emulates the controller while holding its one global lock ({{hv_vcpu_run between unlocking and relocking the global lock; MMIO exits become address_space_write, hvf.c L1119-1175, QEMU v6.2.0|https://github.com/qemu/qemu/blob/v6.2.0/target/arm/hvf/hvf.c#L1119-L1175}}). If the target vCPU was idle, its host thread is asleep in pselect and must be woken with a signal ({{hvf_wait_for_ipi, hvf_kick_vcpu_thread|https://github.com/qemu/qemu/blob/v6.2.0/target/arm/hvf/hvf.c#L602-L606}}). So. With the target idle, the wake-up is dominated by the host waking a sleeping vCPU thread: about 29 µs for an idle host thread on this laptop, the same size as the 25.3 µs measured inside (the host's idle cores sleep deeply, and a woken thread may land on a core that was asleep). With the target kept busy, no host thread sleeps, and 15.4 µs remain: exits and the kick explain 3.8 µs; the other 11.5 µs are QEMU's emulation of the interrupt controller and the guest's scheduler work, not measured separately. The superlinear cost of three IPIs fits exits queuing on QEMU's single global lock (likely, not traced). A hand-off inside the VM was 14.0 times the same hand-off natively on the host.

How real hypervisors avoid most of this source
  • Interrupt controller in the hypervisor's kernel, helped by hardware. KVM emulates the interrupt controller in the kernel (no trip to user space), and with GICv3's virtual CPU interface (arm64), APICv and posted interrupts (Intel) or AVIC (AMD), the guest acknowledges and ends interrupts without exiting at all.
  • Halt polling. KVM can poll briefly before putting an idle vCPU to sleep, "at least saving us a trip through the scheduler, normally on the order of a few micro-seconds" ({{halt-polling.rst, Linux v6.12|https://github.com/torvalds/linux/blob/v6.12/Documentation/virt/kvm/halt-polling.rst}}); and a guest can poll before halting, so that "a remote vCPU [can] avoid sending an IPI" and "the VM-exit cost can be avoided" ({{guest-halt-polling.rst|https://github.com/torvalds/linux/blob/v6.12/Documentation/virt/guest-halt-polling.rst}}).
  • Dedicated cores. Cloud instances that pin each vCPU to its own physical core never wait for the host scheduler; small or burstable instances share cores and do.

Steal time: the part you cannot see here. When the host runs something else while your vCPU wants to run, the guest only learns of it if the hypervisor reports it through a paravirtual clock ({{steal time accounting, cputime.c L237-243|https://github.com/torvalds/linux/blob/v5.10/kernel/sched/cputime.c#L237-L243}}; arm64 asks the hypervisor through a firmware call, {{has_pv_steal_clock|https://github.com/torvalds/linux/blob/v5.10/arch/arm64/kernel/paravirt.c#L122-L136}}). This hypervisor does not, so the steal column here is 0 on every CPU even while macOS runs other programs. KVM reports it; on a cloud VM, top's st or the 8th number of the cpu lines in /proc/stat is the noisy neighbour made visible ({{Scheduling|n:3f05c17b0d0d81ed9c18cc47c6bfdf76}} page, CPU accounting).

When it bites in ML
  • Fine-grained hand-offs between threads: DataLoader workers handing batches to the main process, a pin-memory thread, thread pools that sleep between tasks (OpenMP, Python's ThreadPoolExecutor), the futex wake-ups of the {{Concurrency|n:3f05c17b0d0d8112ad1af99308fa913f}} page. Each hand-off pays a cross-CPU wake-up; in a VM, each is 10 to 30 µs instead of 1 to 2.
  • Step-time jitter on small or shared instances: steal time and slow wake-ups show up as a long tail, not a mean shift.
  • NCCL's proxy threads busy-poll while work is in flight, which sidesteps the wake-up cost at the price of a CPU each (the {{Concurrency|n:3f05c17b0d0d8112ad1af99308fa913f}} page, NCCL threads).
Fixes for the training job
  • Hand off less often: bigger work items per queue message (a batch, not a sample), prefetch_factor so a worker is never woken for one item.
  • Keep communicating threads near each other and let short waits spin (glibc's adaptive mutexes, OpenMP's wait policy) where a core can be spared.
  • Prefer instance types with dedicated physical cores for latency-sensitive input pipelines; watch st.

The VM's vCPU 2 is running a busy loop when vCPU 1 sends it an IPI. Which of these does not happen in this VM?
vCPU 2 is running, so its host thread is inside hv_vcpu_run, not asleep in pselect: QEMU forces it out with hv_vcpus_exit (about 1.1 µs). That is why the busy case (15.4 µs) is faster than the idle one (25.3 µs): the idle case adds a host thread wake-up.
