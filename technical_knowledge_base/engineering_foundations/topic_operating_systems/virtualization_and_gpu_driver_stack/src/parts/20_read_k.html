11. GPU memory and the driver, from the operating system's side

not run here except where marked: no GPU; from the open kernel modules at 615.71.09 and NVIDIA's documentation.

GPU memory is not Linux's memory. The kernel's page allocator, page cache, swap and OOM killer (the {{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}} page) know nothing about the GPU's own memory. The driver's resource manager hands it out in response to RM allocation ioctls; above it, PyTorch's caching allocator keeps freed blocks for reuse (the {{Memory allocators|n:3f05c17b0d0d81209ae9d856695dc958}} page). So "CUDA out of memory" is never solved by the host's swap, and GPU memory a crashed process held comes back only when the driver tears its client down.

Unified memory: page faults on the GPU. With managed memory, one pointer works on both sides. On systems where CPU and GPU each have their own page tables, a fault means the page must be unmapped from its owner, mapped for the requester, and "the physical page backing this virtual page must be moved/migrated to the processor requesting access: this can be an expensive operation, and the amount of work is proportional to the page size" ({{CUDA Programming Guide, unified memory|https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/unified-memory.html}}). The GPU records its faults in a buffer and the UVM driver services them in batches ({{uvm_parent_gpu_service_replayable_faults|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/kernel-open/nvidia-uvm/uvm_gpu_replayable_faults.c#L2900}}). With Linux's HMM (heterogeneous memory management), even plain malloc memory becomes reachable from the GPU; it "requires Linux kernel version 6.1.24+, 6.2.11+ or 6.3+, devices with compute capability 7.5 or higher and a CUDA driver version 535+ installed with Open Kernel Modules" (same guide; the open module's support starts at {{uvm_hmm.c|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/kernel-open/nvidia-uvm/uvm_hmm.c#L27}}).

GPUDirect RDMA: the NIC writes into GPU memory. For multi-node training the network card should move data straight to and from GPU memory. The nvidia-peermem module lets the InfiniBand stack pin GPU pages for the NIC ({{nvidia_p2p_get_pages|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/kernel-open/nvidia-peermem/nvidia-peermem.c#L216}}); "GDRDMA can also be enabled by using the DMA-BUF feature of recent Linux kernels combined with the open source Nvidia GPU driver. In this case, NCCL will automatically detect and enable DMA-BUF so the nvidia-peermem module will not be necessary" ({{NCCL GPU troubleshooting|https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting/gpu_troubleshooting.html}}). In a VM, both devices sit behind the IOMMU and section 7's ACS and ATS rules apply.

Driver state lives as long as someone holds it open. The kernel module "tears down the device on the last file close" ({{nv_stop_device, nv.c L2216|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/kernel-open/nvidia/nv.c#L2216}}). Without a long-lived client, every short CUDA job re-initialises the GPU, which "leads to long load times for each CUDA job, on the order of seconds" ({{driver persistence|https://docs.nvidia.com/deploy/driver-persistence/background.html}}). The old fix, persistence mode (nvidia-smi -pm 1), now logs "Persistence mode is deprecated and will be removed in a future release. Please use nvidia-persistenced instead" ({{nv.c L2259-2265|https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.71.09/kernel-open/nvidia/nv.c#L2259-L2265}}): a daemon that simply keeps the device files open.

When the GPU fails, the kernel log says so. GPU errors (a kernel's illegal memory access, a fallen-off-the-bus GPU, ECC errors) are logged by the kernel driver as Xid messages: "Under Linux, the Xid error messages are logged in the kernel log buffer ... Grep for 'NVRM: Xid'" ({{Xid errors|https://docs.nvidia.com/deploy/xid-errors/working-with-xid-errors.html}}). A training job that dies with a vague CUDA error should be read together with dmesg on the host; inside a container or a VM you may not be allowed to read it (this page's containers could not), so ask whoever runs the host.

Which GPUs a process sees. CUDA_VISIBLE_DEVICES filters and reorders devices for the CUDA runtime: "setting CUDA_VISIBLE_DEVICES=2,1 makes device 0 not visible and enumerates device 2 before device 1", accepts UUIDs and MIG instance names, and cudaGetDeviceCount() "includes only the visible devices" ({{CUDA environment variables|https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html}}). Below it, a container only sees the device files it was given, and its device cgroup decides which it may open (section 9, cases 3 and 4).

When it bites in ML
  • GPU memory "used" with no process running: a zombie or a process in another container still holds the device open; the driver frees its memory when the last handle closes.
  • Each job's first CUDA call takes seconds on a node without nvidia-persistenced.
  • Managed memory "works" but is slow: pages migrate back and forth on faults; prefetch (cudaMemPrefetchAsync) or use device memory.
  • Ranks pick the wrong GPUs: a launcher sets CUDA_VISIBLE_DEVICES and the code also indexes devices by local rank, or CUDA_DEVICE_ORDER differs from nvidia-smi's PCI order.

nvidia-smi -q -d MEMORY,ECC; dmesg | grep -i "NVRM: Xid"; systemctl status nvidia-persistenced; ls -l /dev/nvidia*

Common mistakes

BeliefWhat is true
"A VM is slow because it emulates the CPU."Guest code runs directly on the CPU; only exits cost (about 0.92 µs each here). Interrupts, idle and device access are where the time goes (sections 2, 5).
"GPU passthrough adds overhead to every kernel."The GPU's registers and DMA go through stage-2 tables and the IOMMU, not through the hypervisor; launches do not exit. The costs are pinned memory, topology and peer-to-peer (section 7).
"Containers isolate GPUs like VMs do."A container sees device files the host passed in; the GPU is shared with whatever else uses it unless MIG or exclusive scheduling separates them (section 8).
"Time-sliced GPUs give each pod a fair share.""A request for more than one time-sliced GPU does not guarantee that the pod receives access to a proportional amount of GPU compute power", and there is no memory or fault isolation (section 8).
"nvidia-smi shows CUDA 13.0, so I cannot run a CUDA 13.4 build."That is the newest CUDA the driver was released with; minor version compatibility runs any 13.x build with SASS for the GPU (section 10).
"The CUDA toolkit in my image includes the driver."The image has the runtime and a stub libcuda; the real driver comes from the host (section 9, cases 1 and 2).
"torch.cuda.is_available() is False, so there is no GPU."It is False with no driver library, with no device files, and with a forbidden device cgroup: four different fixes (section 9).
"Steal time is zero, so nothing else runs on my host."Only if the hypervisor reports it; this one does not (section 5).

Interview questions

What is a VM exit, and name three things that cause one.
The CPU stopping the guest and handing control to the hypervisor with the reason (exception class or exit reason), which emulates the effect and resumes the guest. Causes: accessing an emulated device register (MMIO, port I/O), the idle instruction (wfi, hlt), accessing interrupt-controller or timer registers that are not virtualized in hardware, hypercalls, and host interrupts. Guest system calls and page faults do not exit with hardware virtualization and nested paging. About 0.9 µs per exit was measured on an M1 Pro's hypervisor.
Why can a TLB miss cost up to 24 memory reads in a VM?
With nested paging the guest's page-table pointers are guest-physical addresses, so each of the 4 guest levels needs a 4-level host walk plus its own read (20), and the final guest-physical address needs one more host walk (4): (4+1)(4+1)-1 = 24. Huge pages in either stage shorten it (19 with 2 MiB host pages); page-walk caches make most misses much cheaper.
A thread hand-off between CPUs is 10 times slower in a VM than on bare metal. Why, and what would you do?
The wake-up needs an inter-processor interrupt. Sending it, acknowledging it and ending it can each exit to the hypervisor if the interrupt controller is emulated, and if the target vCPU was idle its host thread must be woken by the host scheduler. Fixes at the platform level: in-kernel and hardware-assisted interrupt virtualization (vGIC on GICv3/v4, APICv and posted interrupts, AVIC), halt polling, dedicated cores. In the application: fewer, larger hand-offs, brief spinning where a core can be spared.
What does the IOMMU do in GPU passthrough, and why do GPU VMs pin all their memory?
It translates and checks every DMA address the device issues, so a guest's GPU sees guest-physical addresses mapped to that guest's host pages and nothing else; it also remaps interrupts. Because a device cannot take page faults like a CPU, the pages it may DMA into must stay resident: VFIO pins every page it maps, and QEMU maps all guest RAM, so balloon, KSM or swap-based overcommit cannot apply.
Compare time slicing, MPS and MIG for sharing a GPU between two inference services.
Time slicing: contexts take turns; no concurrency, no memory limit or fault isolation between users. MPS: one server merges the clients' work so it runs concurrently; separate address spaces but shared memory bandwidth and caches and no full error isolation. MIG: hardware partitions with their own SMs, L2 slices, memory controllers and DRAM; predictable latency and fault isolation, up to 7 instances, reconfigured only when idle. For two latency-sensitive services from different teams, MIG.
Walk me through what happens below cudaMalloc on the first call in a process.
The runtime loads libcuda.so.1 (the user-mode driver, from the host), which initialises: opens /dev/nvidiactl, checks versions with the kernel module, allocates RM objects (client, device, subdevice) by ioctl, opens /dev/nvidiaN, creates a context with its channels and maps them; then the allocation itself is an RM allocation ioctl plus a mapping into the GPU's address space. Later kernel launches write into mapped command buffers and ring a doorbell without a system call.
A container prints "no CUDA-capable device is detected" on a GPU node. How do you debug it?
Check, in order: is libcuda.so.1 present (the NVIDIA container runtime or CDI injects it; without it the error is "driver version is insufficient"), do /dev/nvidiactl and /dev/nvidiaN exist in the container, may the container open them (device cgroup: EPERM), is CUDA_VISIBLE_DEVICES empty or wrong, and does the host see the GPU (nvidia-smi, dmesg Xid). strace -f -e openat,ioctl shows which step fails.
Your image is built with CUDA 13.4 and the cluster runs driver 570. Will it run?
Driver 570 belongs to CUDA 12.8, a different major version, so minor version compatibility does not apply; the toolkit's minimum for 13.x is 580. On data-centre GPUs, install cuda-compat-13-4 in the image and put /usr/local/cuda/compat on LD_LIBRARY_PATH: NVIDIA's matrix marks that combination compatible. On consumer GPUs, use a 12.x build or upgrade the driver.
