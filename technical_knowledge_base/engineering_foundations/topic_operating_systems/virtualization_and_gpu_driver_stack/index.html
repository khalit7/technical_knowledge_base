Six things to remember
  1. A VM runs your code directly on the CPU and only stops it (a VM exit) for the few things the hypervisor must see. Each exit cost about 0.92 µs here; virtualization is cheap until something exits thousands of times a second (section 2).
  2. Interrupts are the expensive part. Waking a thread on another CPU took 12.7 times as long as on the same CPU in this VM, because the inter-processor interrupt and the sleeping virtual CPU both go through the hypervisor (section 5; this answers the question the Scheduling and Concurrency pages left open).
  3. A whole GPU in a VM is a real GPU handed to the guest through the IOMMU (passthrough), so CUDA itself runs at full speed; what differs is topology, peer-to-peer traffic and pinned memory (section 7).
  4. Sharing a GPU is a choice of isolation: time slicing and MPS share memory and faults; MIG splits the hardware into up to seven isolated instances (Sharing a GPU tab).
  5. Steady-state CUDA launches make no system call: the driver writes commands into memory and rings a doorbell register; the ioctls happen at start-up and for memory management (section 9, One CUDA call tab).
  6. Two versions, two places: the runtime comes with your image, the driver with the host. A runtime newer than the driver's major family needs the compatibility package or a new driver (section 10).

1. Why virtual machines, and what makes a CPU virtualizable

Appendix B, 6

The problem. A cloud provider owns a big machine and wants to sell slices of it to strangers. Each customer wants root, their own kernel version, their own drivers, and the certainty that the neighbour cannot read their memory or crash their kernel. A container (the Containers and isolation page) cannot promise that: every container shares one kernel, so a kernel bug is everyone's bug. A virtual machine (VM) gives each customer a whole kernel of their own. The program that makes this possible is the hypervisor (also called a virtual machine monitor, VMM): it does for operating systems what an operating system does for processes.

How it works: limited direct execution, one level down. The root page explained how a kernel runs your program directly on the CPU and only takes control back on a system call, a fault or a timer interrupt (OSTEP chapter 6). A hypervisor does the same to a whole kernel: the guest kernel's instructions run directly on the real CPU, at full speed, and the hypervisor only takes over when the guest does something it must not do alone, such as touch a device or reprogram the interrupt controller. That hand-over is a trap; in a VM it is called a VM exit. OSTEP's appendix calls the key method extending "the notion of limited direct execution" so the VMM can "interpose on key events (such as traps)" (OSTEP Appendix B).

Which instructions must trap. In 1974 Popek and Goldberg stated the condition (Theorem 1, paraphrased): a VMM can be built for a machine if every sensitive instruction (one that reads or changes the machine's control state) is also privileged (traps when run outside the most privileged mode) (Popek and Goldberg, CACM 1974). Then the guest kernel can run deprivileged, and every sensitive thing it does traps to the hypervisor, which emulates it on the guest's virtual state. This is trap and emulate.

x86 broke the rule. Robin and Irvine examined the Pentium's instruction set in 2000 and "found that seventeen instructions violate" the requirement, for example POPF, which in user mode silently ignores a change to the interrupt flag instead of trapping, and SGDT/SIDT, which reveal where the real descriptor tables are (Robin and Irvine, USENIX Security 2000). A guest kernel that executes POPF thinking it disabled interrupts would be wrong, and the hypervisor would never know. Three answers followed:

Binary translationVMware's approach: scan the guest kernel's code before it runs and rewrite the problem instructions into safe sequences. Works on any x86; complex.
ParavirtualizationXen's approach: change the guest kernel so it calls the hypervisor directly (a hypercall) instead of executing sensitive instructions. Fast; needs a modified guest. OSTEP: such a system "can be made to be nearly as efficient a system without a VMM".
Hardware supportIntel VT-x and AMD-V added a new mode for the hypervisor (VMX root) and made the guest's sensitive instructions exit to it; ARM added EL2. Every cloud uses this now, plus paravirtual devices (section 6).

Who is the hypervisor? In a type 1 (bare-metal) design the hypervisor is the thing that boots (Xen, VMware ESXi). In a type 2 (hosted) design it is a program on an ordinary OS: here, QEMU running on macOS and asking the macOS kernel, through Hypervisor.framework, to enter the guest (section 3). Linux's KVM blurs the two: a kernel module turns Linux itself into the hypervisor, and a user-space program (QEMU, Firecracker, cloud-hypervisor) provides the virtual devices. AWS's Nitro System uses "a custom-developed, minimized hypervisor based on KVM" with device work moved onto dedicated cards (AWS Nitro whitepaper).

Inside a hardware-virtualized VM, which loop slows down more against bare metal: a million getpid() system calls, or a million 4 KiB disk reads?
A system call goes from EL0 to the guest kernel at EL1 without involving the hypervisor at all: hardware virtualization exists so that this path does not exit. A disk read touches a (virtual) device: the guest writes a device register to say "go", which exits to the hypervisor, and the completion arrives as an interrupt the hypervisor injects. Sections 2, 5 and 6 measure those exits.

2. A VM exit, measured

Appendix B

What an exit is. When the guest does something the hypervisor asked to see, the CPU stops the guest, saves its registers, switches to the hypervisor's privilege level and jumps to the hypervisor's handler with a syndrome describing why (on arm64 the exception class, EC; on x86 the exit reason). The handler emulates the effect, then resumes the guest. Everything a guest does is either free (runs directly) or costs one of these round trips.

The hypervisor's API, as a program. KVM exposes all of this to an ordinary Linux process through one device file. The shape of every VMM (QEMU, Firecracker) is this loop; LWN's Using the KVM API builds a complete one in about 100 lines.

a minimal KVM monitor (C; the calls of LWN's example; not run here: this VM has no /dev/kvm)
int kvm  = open("/dev/kvm", O_RDWR);
int vm   = ioctl(kvm, KVM_CREATE_VM, 0);             // a VM is a file descriptor
void *mem = mmap(NULL, 0x1000, PROT_READ|PROT_WRITE, MAP_SHARED|MAP_ANONYMOUS, -1, 0);
// guest "physical" memory is ordinary memory of this process
struct kvm_userspace_memory_region r = { .guest_phys_addr = 0x1000, .memory_size = 0x1000, .userspace_addr = (long)mem };
ioctl(vm, KVM_SET_USER_MEMORY_REGION, &r);
int vcpu = ioctl(vm, KVM_CREATE_VCPU, 0);             // a virtual CPU is another fd
struct kvm_run *run = mmap(NULL, mmap_size, PROT_READ|PROT_WRITE, MAP_SHARED, vcpu, 0);
for (;;) {
    ioctl(vcpu, KVM_RUN, 0);                          // enter the guest; returns on an exit
    switch (run->exit_reason) {
    case KVM_EXIT_IO:   /* the guest touched an I/O port: emulate the device */  break;
    case KVM_EXIT_MMIO: /* a device register in memory: emulate it */          break;
    case KVM_EXIT_HLT:  return 0;                                    // the guest idled
    }
}

4. Memory: two translations, and the 24-step page walk

Appendix B, 19, 20

The problem. The guest kernel believes it owns "physical" memory starting at address 0, and builds page tables that map its processes' virtual addresses onto it. But that memory is really part of the hypervisor's process (QEMU's 10 GiB here), scattered across the host's real memory. So every guest memory access needs two translations: guest virtual to guest physical (the guest's page tables), then guest physical to host physical (tables the hypervisor owns, which the guest cannot see or touch). The Virtual memory page explained one translation, the TLB and huge pages; this section is the second layer.


The old way: shadow page tables. Before hardware help, the hypervisor kept a shadow page table mapping guest virtual straight to host physical, installed it whenever the guest switched page tables, and write-protected the guest's own tables so that every change to them exited and could be mirrored (OSTEP Appendix B). Correct, but every page-table update and many page faults cost an exit.


The new way: nested paging. The CPU walks both sets of tables itself: Intel calls the second set EPT (extended page tables), AMD NPT, ARM stage 2. The guest edits its own page tables freely, with no exits. The TLB caches the final guest-virtual to host-physical result, tagged with a VM identifier (VMID on arm64, VPID on Intel) so switching VMs does not flush it. The price is paid on a TLB miss: every pointer in the guest's walk is a guest-physical address that must itself be translated by a host walk.

Memory overcommit, and why GPU VMs cannot do it. Because guest memory is just memory of the hypervisor's process, a host can promise its VMs more than it has: a balloon driver in the guest (this kernel has CONFIG_VIRTIO_BALLOON=y) gives pages back on request, KSM merges identical pages across VMs (KSM, kernel docs), and the host can swap. A VM with a passed-through device cannot play these games: the device writes to guest memory by DMA at any moment, so every guest page it might touch must stay put. VFIO pins the pages it maps for a device, charging them against the locked-memory limit (vfio_pin_map_dma checks RLIMIT_MEMLOCK, Linux v6.12). QEMU, for one, maps every RAM region of the guest for the device as the region appears (vfio_listener_region_add calls vfio_dma_map, hw/vfio/common.c L864 and L1063, QEMU v6.2.0), so a GPU VM's whole memory is pinned when it starts: one reason large GPU VMs take long to boot and cannot be overcommitted.






5. Interrupts, and why a cross-CPU wake-up costs ten times more here

Appendix B, 26 to 28

The question the sibling pages left open. The Scheduling page measured a context switch on one CPU at 1.30 to 1.56 µs but a hand-off between two CPUs at 25.6 to 51.4 µs in this VM; the Concurrency page found the same when a futex woke a thread on another CPU. Both suspected the hypervisor. This section measures it and follows the path through the hypervisor's source.


Inter-processor interrupts. An interrupt is a signal that makes a CPU stop what it is doing and run a handler. An inter-processor interrupt (IPI) is one CPU interrupting another. Linux uses two kinds all the time: a reschedule IPI ("a thread you should run just woke up") and a function-call IPI ("run this function on your CPU now"). When thread A on CPU 1 writes to a pipe and thread B, asleep on it, last ran on CPU 2, the kernel marks B runnable on CPU 2's run queue and calls resched_curr, which sends CPU 2 a reschedule IPI (smp_send_reschedule). The only way to skip it is a CPU that is idle but polling a flag (set_nr_if_polling); an arm64 CPU idles in wfi (__cpu_do_idle), so it always needs the interrupt.


Measured. Where the time goes: the path through this hypervisor. Section 3 found that this guest's interrupt controller is a GICv2, emulated by QEMU. On a GICv2, sending an IPI is a store to a distributor register (gic_ipi_send_mask writes GIC_DIST_SOFTINT), and taking one is a load from the CPU interface to acknowledge it and a store to end it (gic_handle_irq: GIC_CPU_INTACK, GIC_CPU_EOI). All three are device registers, so all three are VM exits into QEMU, which emulates the controller while holding its one global lock (hv_vcpu_run between unlocking and relocking the global lock; MMIO exits become address_space_write, hvf.c L1119-1175, QEMU v6.2.0). If the target vCPU was idle, its host thread is asleep in pselect and must be woken with a signal (hvf_wait_for_ipi, hvf_kick_vcpu_thread). How real hypervisors avoid most of this source
    

  • Interrupt controller in the hypervisor's kernel, helped by hardware. 6. Devices without the exits: virtio

36

The problem. The simplest way to give a guest a disk is to emulate a real one: the guest's normal driver pokes the device's registers, and every poke exits to the hypervisor, which pretends to be the hardware. A real disk controller's driver touches several registers per request, so one 4 KiB read costs several exits, plus an emulated interrupt with its own exits (section 5).


How virtio works. virtio is a device interface designed for VMs, where both sides know the other is software (Russell, virtio, 2008; OASIS VIRTIO 1.2 specification). The guest and the hypervisor share a virtqueue in guest memory, made of three parts (include/uapi/linux/virtio_ring.h, Linux v5.10):




Descriptor tableentries of (guest address, length, flags, next): "here is a buffer" (struct vring_desc)


Available ringwritten by the guest: "these descriptor chains are ready for you" (struct vring_avail)


Used ringwritten by the device: "I finished these, this many bytes" (struct vring_used)




A request is three descriptors (a header saying "read sector N", the data buffer, a status byte). The guest adds them, bumps the available index, and only then kicks the device: one register write, one exit. The device side reads the request straight out of guest memory (for QEMU, its own memory), does the I/O, writes the used ring, and injects one interrupt. Both directions can be suppressed: with the event index feature (VIRTIO_RING_F_EVENT_IDX, bit 29), each side publishes "notify me only when your index passes N", so a busy queue needs neither a kick per request nor an interrupt per completion (vring_need_event, used by virtqueue_kick_prepare_split). Both of this VM's virtio devices offer it (section 3's feature bits).

7. The IOMMU and device passthrough: giving a VM a real GPU

36

not run here: this VM has no IOMMU and no device to pass through; taught from the kernel's VFIO documentation and source, and NVIDIA's NCCL guide.


The problem. virtio is fast enough for disks and ordinary networks, but a GPU cannot be emulated at any useful speed: its driver talks to thousands of registers, and its whole point is raw throughput. The fastest answer is to give the guest the real device. But a device writes to memory by DMA (direct memory access: the device itself reads and writes RAM, without the CPU), using physical addresses. A guest driver programs the GPU with guest-physical addresses, which are wrong on the host; worse, a malicious guest could program it to write anywhere in the host's memory.


How it works: an MMU for devices. The IOMMU (Intel VT-d, AMD-Vi, ARM SMMU) sits between devices and memory and translates every DMA address through page tables of its own, one set per device domain. The hypervisor fills them so that the device's addresses are the guest's physical addresses and map to exactly the host pages backing that guest, and nothing else. The device sees the guest's world; the host stays safe. The same unit remaps the device's interrupts so they reach the right guest.


VFIO: the Linux interface. "The VFIO driver is an IOMMU/device agnostic framework for exposing direct device access to userspace, in a secure, IOMMU protected environment", and "from a device and host perspective, this simply turns the VM into a userspace driver" (VFIO documentation, Linux v6.12). The steps of its own example:


int container = open("/dev/vfio/vfio", O_RDWR);          // an IOMMU context
int group = open("/dev/vfio/26", O_RDWR);              // the device's IOMMU group
ioctl(group, VFIO_GROUP_SET_CONTAINER, &container);
ioctl(container, VFIO_SET_IOMMU, VFIO_TYPE1_IOMMU);
ioctl(container, VFIO_IOMMU_MAP_DMA, &dma_map);       // "device address X is this memory": pins it
int device = ioctl(group, VFIO_GROUP_GET_DEVICE_FD, "0000:06:0d.0");
// then mmap the device's registers (BARs) and hand them to the guest


From vfio.rst lines 177-213. Mapping pins the pages (vfio_pin_pages_remote), which is section 4's "a GPU VM cannot overcommit memory". Newer kernels add iommufd, a general replacement for the container.


IOMMU groups and ACS. The IOMMU can only isolate what it can tell apart. Devices behind a bridge that lets them talk to each other directly, without passing the IOMMU, are inseparable: "a group is a set of devices which is isolatable from all other devices in the system. Groups are therefore the unit of ownership used by VFIO" (vfio.rst lines 55-71). PCIe switches use Access Control Services (ACS) to force device-to-device traffic up through the IOMMU, which makes small groups possible. That is exactly the tension with GPU clusters:


Peer-to-peer GPU traffic against isolation


NCCL's guide: on bare metal, "IO virtualization (also known as VT-d or IOMMU) can interfere with GPU Direct by redirecting all PCI point-to-point traffic to the CPU root complex, causing a significant performance reduction or even a hang", so bare-metal clusters disable ACS on their PCIe switches. In a VM that is not an option: "Virtual machines require ACS to function, hence disabling ACS is not an option. To run with maximum performance inside virtual machines, ATS needs to be enabled in network adapters" (ATS, Address Translation Services, lets the device cache IOMMU translations itself). And NCCL reads the PCI topology from /sys: "Having /sys expose a virtual PCI topology can result in sub-optimal performance" (NCCL GPU troubleshooting).


What passthrough costs. Once set up, almost nothing on the data path: the GPU's registers are mapped into the guest by stage-2 page tables, so a doorbell write is an ordinary store, and the GPU's DMA goes through the IOMMU's translation cache. The costs are at the edges: pinning all guest memory at boot, IOTLB misses for scattered DMA, interrupts that must be remapped, and a guest that sees whatever PCI topology the hypervisor chose to show it.

  • Multi-GPU training inside VMs: whether GPU-to-GPU and GPU-to-NIC traffic goes peer to peer or through the CPU decides all-reduce bandwidth.   • Slow or failing peer-to-peer with "OK" from nvidia-smi topo -p2p on bare metal: IOMMU settings or ACS, per the NCCL guide.

  • A GPU VM that takes minutes to boot: its memory is being pinned and mapped.

Overcommit (balloon, KSM, host swap) relies on the host being able to take a page away and fault it back later. A device doing DMA cannot take a fault the way a CPU can, so VFIO pins every page it maps into the IOMMU, and QEMU maps all of guest RAM for the device.

How the kernel side is organised. nvidia.ko registers one set of file operations for all its device files: open, unlocked_ioctl, mmap, poll, release (nvidia_fops, nv.c L259-269). A handful of ioctls are handled in the Linux layer, such as the version handshake (below); everything else goes to the resource manager (RM), the OS-independent core of the driver (default: rm_ioctl, nv.c L2981-2982). In RM everything is an object with a handle: a client (your process), a device, a subdevice, a memory allocation, a channel. The escapes allocate objects (NV_ESC_RM_ALLOC 0x2B), free them, run control calls on them (NV_ESC_RM_CONTROL), and map them into the process (NV_ESC_RM_MAP_MEMORY, followed by an mmap of the device file, nvidia_mmap). Launching work without a system call. A GPU channel is a queue of work: a pushbuffer in memory holds the commands ("methods": launch this kernel with these parameters, copy this, wait for that semaphore), a ring called the GPFIFO holds pointers to pushbuffer segments, and a doorbell register tells the GPU's host interface that the ring moved. The open driver's own unified-memory module submits work exactly like this, and its code shows each step: fill a GPFIFO entry pointing at the pushbuffer, a memory barrier, write the new put pointer, a write barrier, and ring the doorbell by storing a token into the doorbell register (internal_channel_submit_work, uvm_channel.c L984-1015; write_gpu_put, uvm_turing_host.c L222-236). The doorbell lives in a "usermode" register page, the class VOLTA_USERMODE_A with NOTIFY_CHANNEL_PENDING at offset 0x90 (clc361.h), an object any RM client can allocate and map. Every piece is ordinary memory once mapped, so a process holding the mappings can launch with plain stores: no system call, no exit even in a VM.

11. GPU memory and the driver, from the operating system's side


not run here except where marked: no GPU; from the open kernel modules at 615.71.09 and NVIDIA's documentation.


GPU memory is not Linux's memory. The kernel's page allocator, page cache, swap and OOM killer (the Virtual memory page) know nothing about the GPU's own memory. The driver's resource manager hands it out in response to RM allocation ioctls; above it, PyTorch's caching allocator keeps freed blocks for reuse (the Memory allocators page). So "CUDA out of memory" is never solved by the host's swap, and GPU memory a crashed process held comes back only when the driver tears its client down.

Unified memory: page faults on the GPU. With managed memory, one pointer works on both sides. On systems where CPU and GPU each have their own page tables, a fault means the page must be unmapped from its owner, mapped for the requester, and "the physical page backing this virtual page must be moved/migrated to the processor requesting access: this can be an expensive operation, and the amount of work is proportional to the page size" (CUDA Programming Guide, unified memory). The GPU records its faults in a buffer and the UVM driver services them in batches (uvm_parent_gpu_service_replayable_faults). With Linux's HMM (heterogeneous memory management), even plain malloc memory becomes reachable from the GPU; it "requires Linux kernel version 6.1.24+, 6.2.11+ or 6.3+, devices with compute capability 7.5 or higher and a CUDA driver version 535+ installed with Open Kernel Modules" (same guide; the open module's support starts at uvm_hmm.c).


GPUDirect RDMA: the NIC writes into GPU memory. For multi-node training the network card should move data straight to and from GPU memory. The nvidia-peermem module lets the InfiniBand stack pin GPU pages for the NIC (nvidia_p2p_get_pages); "GDRDMA can also be enabled by using the DMA-BUF feature of recent Linux kernels combined with the open source Nvidia GPU driver. In this case, NCCL will automatically detect and enable DMA-BUF so the nvidia-peermem module will not be necessary" (NCCL GPU troubleshooting). In a VM, both devices sit behind the IOMMU and section 7's ACS and ATS rules apply.


Driver state lives as long as someone holds it open. The kernel module "tears down the device on the last file close" (nv_stop_device, nv.c L2216). Without a long-lived client, every short CUDA job re-initialises the GPU, which "leads to long load times for each CUDA job, on the order of seconds" (driver persistence). The old fix, persistence mode (nvidia-smi -pm 1), now logs "Persistence mode is deprecated and will be removed in a future release. Please use nvidia-persistenced instead" (nv.c L2259-2265): a daemon that simply keeps the device files open.


When the GPU fails, the kernel log says so. GPU errors (a kernel's illegal memory access, a fallen-off-the-bus GPU, ECC errors) are logged by the kernel driver as Xid messages: "Under Linux, the Xid error messages are logged in the kernel log buffer ... Grep for 'NVRM: Xid'" (Xid errors). A training job that dies with a vague CUDA error should be read together with dmesg on the host; inside a container or a VM you may not be allowed to read it (this page's containers could not), so ask whoever runs the host.


Which GPUs a process sees. CUDA_VISIBLE_DEVICES filters and reorders devices for the CUDA runtime: "setting CUDA_VISIBLE_DEVICES=2,1 makes device 0 not visible and enumerates device 2 before device 1", accepts UUIDs and MIG instance names, and cudaGetDeviceCount() "includes only the visible devices" (CUDA environment variables). Below it, a container only sees the device files it was given, and its device cgroup decides which it may open (section 9, cases 3 and 4).

"A VM is slow because it emulates the CPU."Guest code runs directly on the CPU; only exits cost (about 0.92 µs each here). Interrupts, idle and device access are where the time goes (sections 2, 5).


"GPU passthrough adds overhead to every kernel."The GPU's registers and DMA go through stage-2 tables and the IOMMU, not through the hypervisor; launches do not exit. The costs are pinned memory, topology and peer-to-peer (section 7).

Interview questions


What is a VM exit, and name three things that cause one.
The CPU stopping the guest and handing control to the hypervisor with the reason (exception class or exit reason), which emulates the effect and resumes the guest. Causes: accessing an emulated device register (MMIO, port I/O), the idle instruction (wfi, hlt), accessing interrupt-controller or timer registers that are not virtualized in hardware, hypercalls, and host interrupts. Guest system calls and page faults do not exit with hardware virtualization and nested paging. About 0.9 µs per exit was measured on an M1 Pro's hypervisor.


Why can a TLB miss cost up to 24 memory reads in a VM?
With nested paging the guest's page-table pointers are guest-physical addresses, so each of the 4 guest levels needs a 4-level host walk plus its own read (20), and the final guest-physical address needs one more host walk (4): (4+1)(4+1)-1 = 24. Huge pages in either stage shorten it (19 with 2 MiB host pages); page-walk caches make most misses much cheaper.


A thread hand-off between CPUs is 10 times slower in a VM than on bare metal. Why, and what would you do?
The wake-up needs an inter-processor interrupt. Sending it, acknowledging it and ending it can each exit to the hypervisor if the interrupt controller is emulated, and if the target vCPU was idle its host thread must be woken by the host scheduler. Fixes at the platform level: in-kernel and hardware-assisted interrupt virtualization (vGIC on GICv3/v4, APICv and posted interrupts, AVIC), halt polling, dedicated cores. In the application: fewer, larger hand-offs, brief spinning where a core can be spared.


What does the IOMMU do in GPU passthrough, and why do GPU VMs pin all their memory?
It translates and checks every DMA address the device issues, so a guest's GPU sees guest-physical addresses mapped to that guest's host pages and nothing else; it also remaps interrupts. Because a device cannot take page faults like a CPU, the pages it may DMA into must stay resident: VFIO pins every page it maps, and QEMU maps all guest RAM, so balloon, KSM or swap-based overcommit cannot apply.


Compare time slicing, MPS and MIG for sharing a GPU between two inference services.
Time slicing: contexts take turns; no concurrency, no memory limit or fault isolation between users. MPS: one server merges the clients' work so it runs concurrently; separate address spaces but shared memory bandwidth and caches and no full error isolation. MIG: hardware partitions with their own SMs, L2 slices, memory controllers and DRAM; predictable latency and fault isolation, up to 7 instances, reconfigured only when idle. For two latency-sensitive services from different teams, MIG.


Walk me through what happens below cudaMalloc on the first call in a process.
The runtime loads libcuda.so.1 (the user-mode driver, from the host), which initialises: opens /dev/nvidiactl, checks versions with the kernel module, allocates RM objects (client, device, subdevice) by ioctl, opens /dev/nvidiaN, creates a context with its channels and maps them; then the allocation itself is an RM allocation ioctl plus a mapping into the GPU's address space. Later kernel launches write into mapped command buffers and ring a doorbell without a system call.


A container prints "no CUDA-capable device is detected" on a GPU node. How do you debug it?
Check, in order: is libcuda.so.1 present (the NVIDIA container runtime or CDI injects it; without it the error is "driver version is insufficient"), do /dev/nvidiactl and /dev/nvidiaN exist in the container, may the container open them (device cgroup: EPERM), is CUDA_VISIBLE_DEVICES empty or wrong, and does the host see the GPU (nvidia-smi, dmesg Xid). strace -f -e openat,ioctl shows which step fails.


Your image is built with CUDA 13.4 and the cluster runs driver 570. Will it run?
Driver 570 belongs to CUDA 12.8, a different major version, so minor version compatibility does not apply; the toolkit's minimum for 13.x is 580. On data-centre GPUs, install cuda-compat-13-4 in the image and put /usr/local/cuda/compat on LD_LIBRARY_PATH: NVIDIA's matrix marks that combination compatible. On consumer GPUs, use a 12.x build or upgrade the driver.
