1. Virtual machines against containers, and what makes a CPU virtualizable

Appendix B, 6

The problem. A cloud provider sells slices of one big machine to strangers. Each wants root, their own kernel and drivers, and the certainty that the neighbour cannot read their memory or crash their kernel. A container cannot promise that: every container shares one kernel, so a kernel bug is everyone's bug. A virtual machine (VM) gives each customer a whole kernel of their own; the hypervisor (or virtual machine monitor, VMM) does for operating systems what an operating system does for processes.

Where the isolation boundary sits

Containers: one kernel, separated by namespaces and cgroups (the Containers and isolation page owns how). VMs: one kernel per guest, separated by the CPU's virtualization hardware, so a guest kernel crash or exploit stays in its guest. The price is the boundary crossings of sections 2 to 6. Sandboxes for untrusted code (Firecracker, gVisor) sit between the two and are on the containers page.

How it works: limited direct execution, one level down. A kernel runs your program directly on the CPU and takes control back only on a system call, fault or timer (OSTEP chapter 6). A hypervisor does the same to a whole kernel: the guest kernel's instructions run directly, at full speed, and the hypervisor takes over only when the guest does something it must not do alone, such as touch a device or reprogram the interrupt controller. That hand-over is a trap; in a VM it is a VM exit. OSTEP's appendix calls it extending "the notion of limited direct execution" so the VMM can "interpose on key events (such as traps)" (OSTEP Appendix B).

Which instructions must trap. Popek and Goldberg (1974, Theorem 1, paraphrased): a VMM can be built if every sensitive instruction (one that reads or changes the machine's control state) is also privileged (traps outside the most privileged mode). Then the deprivileged guest kernel traps on every sensitive act and the hypervisor emulates it: trap and emulate. x86 broke the rule: Robin and Irvine "found that seventeen instructions violate" it, for example POPF, which in user mode silently ignores a change to the interrupt flag instead of trapping. Three answers followed:

Binary translationVMware: rewrite the guest kernel's problem instructions before they run. Any x86; complex.
ParavirtualizationXen: change the guest kernel to call the hypervisor directly (a hypercall). Fast; needs a modified guest.
Hardware supportIntel VT-x and AMD-V added a mode for the hypervisor (VMX root) and made sensitive guest instructions exit to it; ARM added EL2. Every cloud uses this, plus paravirtual devices (section 6).

Who is the hypervisor? Type 1 (bare metal): the hypervisor is what boots (Xen, VMware ESXi). Type 2 (hosted): a program on an ordinary OS; here, QEMU on macOS asking the macOS kernel, through Hypervisor.framework, to enter the guest. Linux's KVM blurs the two: a kernel module turns Linux into the hypervisor, and a user-space program (QEMU, Firecracker, cloud-hypervisor) provides the virtual devices. AWS's Nitro System uses "a custom-developed, minimized hypervisor based on KVM" with device work moved onto dedicated cards (AWS Nitro whitepaper).

The sources and examples behind trap and emulate (depth)

Popek and Goldberg: CACM 1974. Robin and Irvine examined the Pentium's instruction set in 2000 (USENIX Security 2000); besides POPF, SGDT/SIDT reveal where the real descriptor tables are. A guest kernel that executes POPF thinking it disabled interrupts would be wrong, and the hypervisor would never know. Binary translation scans the guest kernel's code before it runs and rewrites the problem instructions into safe sequences. On paravirtualization OSTEP says such a system "can be made to be nearly as efficient a system without a VMM".

Inside a hardware-virtualized VM, which loop slows down more against bare metal: a million getpid() system calls, or a million 4 KiB disk reads?
A system call goes from EL0 to the guest kernel at EL1 without involving the hypervisor at all: hardware virtualization exists so that this path does not exit. A disk read touches a (virtual) device: the guest writes a device register to say "go", which exits to the hypervisor, and the completion arrives as an interrupt the hypervisor injects. Sections 2, 5 and 6 measure those exits.

2. A VM exit, measured

Appendix B

What an exit is. When the guest does something the hypervisor asked to see, the CPU stops the guest, saves its registers, switches to the hypervisor's privilege level and jumps to its handler with a syndrome saying why (on arm64 the exception class, EC; on x86 the exit reason). The handler emulates the effect and resumes the guest. Everything a guest does is either free (runs directly) or costs one of these round trips.

A system call never leaves the guest; a device register store does

Privilege levels over time on arm64. The guest's getpid() goes EL0 to EL1 and back, exactly as on bare metal. A store to an emulated device register (MMIO) exits from EL1 to EL2, runs the hypervisor's handler, and resumes: 0.92 µs measured on this laptop.

The hypervisor's API as a program: a minimal KVM monitor, and where each exit is handled (depth)

KVM exposes all of this to an ordinary Linux process through one device file. The shape of every VMM (QEMU, Firecracker) is this loop; LWN's Using the KVM API builds a complete one in about 100 lines.

a minimal KVM monitor (C; the calls of LWN's example; not run here: this VM has no /dev/kvm)
int kvm  = open("/dev/kvm", O_RDWR);
int vm   = ioctl(kvm, KVM_CREATE_VM, 0);             // a VM is a file descriptor
void *mem = mmap(NULL, 0x1000, PROT_READ|PROT_WRITE, MAP_SHARED|MAP_ANONYMOUS, -1, 0);
// guest "physical" memory is ordinary memory of this process
struct kvm_userspace_memory_region r = { .guest_phys_addr = 0x1000, .memory_size = 0x1000, .userspace_addr = (long)mem };
ioctl(vm, KVM_SET_USER_MEMORY_REGION, &r);
int vcpu = ioctl(vm, KVM_CREATE_VCPU, 0);             // a virtual CPU is another fd
struct kvm_run *run = mmap(NULL, mmap_size, PROT_READ|PROT_WRITE, MAP_SHARED, vcpu, 0);
for (;;) {
    ioctl(vcpu, KVM_RUN, 0);                          // enter the guest; returns on an exit
    switch (run->exit_reason) {
    case KVM_EXIT_IO:   /* the guest touched an I/O port: emulate the device */  break;
    case KVM_EXIT_MMIO: /* a device register in memory: emulate it */          break;
    case KVM_EXIT_HLT:  return 0;                                    // the guest idled
    }
}

4. Memory: two translations, and the 24-step page walk

Appendix B, 19, 20

The problem. The guest kernel believes it owns "physical" memory from address 0 and builds page tables onto it. That memory is really part of the hypervisor's process (QEMU's 10 GiB here), scattered across the host's RAM. So every guest access needs two translations: guest virtual to guest physical (the guest's tables), then guest physical to host physical (tables the hypervisor owns and the guest cannot see). Virtual memory owns the first translation, the TLB and huge pages; this is the second layer.


Shadow page tables, then nested paging. Before hardware help, the hypervisor kept a shadow page table from guest virtual straight to host physical and write-protected the guest's own tables, so every page-table update exited to be mirrored. With nested paging (Intel EPT, AMD NPT, ARM stage 2) the CPU walks both sets itself, the guest edits its tables with no exits, and the TLB caches the combined result tagged with a VM identifier (VMID on arm64, VPID on Intel) so switching VMs does not flush it. The price moves to the TLB miss: every pointer in the guest's walk is guest-physical and needs a host walk of its own.

Memory overcommit, and why GPU VMs cannot do it. Because guest memory is memory of the hypervisor's process, a host can promise its VMs more than it has: a balloon driver in the guest gives pages back on request, KSM merges identical pages across VMs, and the host can swap. A VM with a passed-through device cannot: the device writes guest memory by DMA at any moment, so every page it might touch must stay put. VFIO pins the pages it maps for a device, and QEMU maps all of guest RAM for it, so a GPU VM's whole memory is pinned when it starts: one reason large GPU VMs boot slowly and cannot be overcommitted.

5. Interrupts, and why a cross-CPU wake-up costs ten times more here

Appendix B, 26 to 28

The question the sibling pages left open. Scheduling measured a context switch on one CPU at 1.30 to 1.56 µs but a hand-off between two CPUs at 25.6 to 51.4 µs in this VM; Concurrency found the same for a futex wake-up on another CPU. Both suspected the hypervisor. This section measures it and follows the path through the hypervisor's source.


Inter-processor interrupts. An IPI is one CPU interrupting another. When thread A on CPU 1 writes to a pipe and thread B, asleep on it, last ran on CPU 2, the kernel marks B runnable on CPU 2 and sends CPU 2 a reschedule IPI. An idle arm64 CPU sleeps in wfi, so it always needs the interrupt. Linux also sends function-call IPIs ("run this on your CPU now"); membarrier() sends one to every CPU running a thread of the caller and waits, a direct way to time an IPI round trip from user space.

The problem. An emulated real disk means the guest's normal driver pokes device registers, and every poke exits to the hypervisor: several exits per 4 KiB read, plus an emulated interrupt with its own exits (section 5).


How virtio works. virtio is a device interface made for VMs: guest and hypervisor share a virtqueue in guest memory, in three parts:




Descriptor tableentries of (guest address, length, flags, next): "here is a buffer" (struct vring_desc)


Available ringwritten by the guest: "these descriptor chains are ready for you" (struct vring_avail)


Used ringwritten by the device: "I finished these, this many bytes" (struct vring_used)




A request is three descriptors (header "read sector N", data buffer, status byte). The guest adds them, bumps the available index, and only then kicks the device: one register write, one exit. The device reads the request straight out of guest memory, does the I/O, writes the used ring and injects one interrupt. With the event index feature each side says "notify me only when your index passes N", so a busy queue needs neither a kick per request nor an interrupt per completion.

7. The IOMMU and device passthrough: giving a VM a real GPU

36

not run here: this VM has no IOMMU and no device to pass through; taught from the kernel's VFIO documentation and source, and NVIDIA's NCCL guide.


The problem. A GPU cannot be emulated at any useful speed, so the guest is given the real device (passthrough). But a device writes to memory by DMA (direct memory access: the device itself reads and writes RAM, without the CPU), using physical addresses. A guest driver programs the GPU with guest-physical addresses, which are wrong on the host; worse, a malicious guest could program it to write anywhere in the host's memory.


How it works: an MMU for devices. The IOMMU (Intel VT-d, AMD-Vi, ARM SMMU) sits between devices and memory and translates every DMA address through page tables of its own, one set per device domain. The hypervisor fills them so the device's addresses are the guest's physical addresses, mapped to exactly the host pages backing that guest and nothing else. The same unit remaps the device's interrupts so they reach the right guest.


The GPU speaks guest-physical; the IOMMU makes it land in this guest only




The guest's driver programs the GPU with guest-physical address 0x1000. The IOMMU's table for VM A's domain maps it to the host page that backs VM A's 0x1000; an address outside VM A's mappings has no entry and the DMA is blocked. Linux exposes this as VFIO: "from a device and host perspective, this simply turns the VM into a userspace driver" (VFIO documentation, Linux v6.12).


VFIO as a program: the steps of the kernel documentation's example (depth)
"The VFIO driver is an IOMMU/device agnostic framework for exposing direct device access to userspace, in a secure, IOMMU protected environment". The steps of its own example:

From vfio.rst lines 177-213. Mapping pins the pages (vfio_pin_pages_remote), which is section 4's "a GPU VM cannot overcommit memory". Newer kernels add iommufd, a general replacement for the container.




IOMMU groups and ACS. The IOMMU can only isolate what it can tell apart. Devices behind a bridge that lets them talk to each other directly, without passing the IOMMU, are inseparable: "a group is a set of devices which is isolatable from all other devices in the system. Groups are therefore the unit of ownership used by VFIO" (vfio.rst lines 55-71). PCIe switches use Access Control Services (ACS) to force device-to-device traffic up through the IOMMU, which makes small groups possible. That is exactly the tension with GPU clusters:


Peer-to-peer GPU traffic against isolation


NCCL's guide: on bare metal, "IO virtualization (also known as VT-d or IOMMU) can interfere with GPU Direct by redirecting all PCI point-to-point traffic to the CPU root complex, causing a significant performance reduction or even a hang", so bare-metal clusters disable ACS on their PCIe switches. In a VM that is not an option: "Virtual machines require ACS to function, hence disabling ACS is not an option. To run with maximum performance inside virtual machines, ATS needs to be enabled in network adapters" (ATS, Address Translation Services, lets the device cache IOMMU translations itself). And NCCL reads the PCI topology from /sys: "Having /sys expose a virtual PCI topology can result in sub-optimal performance" (NCCL GPU troubleshooting).


What passthrough costs. Once set up, almost nothing on the data path: the GPU's registers are mapped into the guest by stage-2 page tables, so a doorbell write is an ordinary store, and the GPU's DMA goes through the IOMMU's translation cache. The costs are at the edges: pinning all guest memory at boot, IOTLB misses for scattered DMA, interrupts that must be remapped, and a guest that sees whatever PCI topology the hypervisor chose to show it.

The kernel compares the client's version string with its own, exactly, or only up to the first dot if the client asks for "relaxed" checking; on a mismatch it logs "NVRM: API mismatch: the client ... has the version ..., but this kernel module has the version ... Please make sure that this kernel module and all NVIDIA driver components have the same version" (RmPerformVersionCheck, osapi.c L1199-1302). That is the message in dmesg after a driver upgrade without a reboot: the new user-mode libraries meet the old module still loaded.


Launching work without a system call. A GPU channel is a queue of work: a pushbuffer in memory holds the commands ("methods": launch this kernel with these parameters, copy this, wait for that semaphore), a ring called the GPFIFO holds pointers to pushbuffer segments, and a doorbell register tells the GPU's host interface that the ring moved. The open driver's own unified-memory module submits work exactly like this, and its code shows each step: fill a GPFIFO entry pointing at the pushbuffer, a memory barrier, write the new put pointer, a write barrier, and ring the doorbell by storing a token into the doorbell register (internal_channel_submit_work, uvm_channel.c L984-1015; write_gpu_put, uvm_turing_host.c L222-236). The doorbell lives in a "usermode" register page, the class VOLTA_USERMODE_A with NOTIFY_CHANNEL_PENDING at offset 0x90 (clc361.h), an object any RM client can allocate and map. Every piece is ordinary memory once mapped, so a process holding the mappings can launch with plain stores: no system call, no exit even in a VM.




What is verified and what is inferred
Verified from the open source: the device files, the ioctl protocol, the RM object model, the channel, GPFIFO and doorbell mechanism, and that kernel-side code (UVM) submits work with stores alone. Inferred: that the closed libcuda launches kernels the same way, by mapping its channels and the usermode page at context creation; it is the design the open interface supports, and the root page's description, but libcuda itself cannot be read. On a GPU machine, strace -f -c over a steady training loop confirms or refutes it in a minute. This replaces the root page's "not verified from a primary source" with this narrower statement.

GPU memory is not Linux's memory. The kernel's page allocator, page cache, swap and OOM killer (the Virtual memory page) know nothing about the GPU's own memory. Interview rehearsal: eight questions with answers (optional)


What is a VM exit, and name three things that cause one.
The CPU stopping the guest and handing control to the hypervisor with the reason (exception class or exit reason), which emulates the effect and resumes the guest. Causes: accessing an emulated device register (MMIO, port I/O), the idle instruction (wfi, hlt), accessing interrupt-controller or timer registers that are not virtualized in hardware, hypercalls, and host interrupts. Guest system calls and page faults do not exit with hardware virtualization and nested paging. About 0.9 µs per exit was measured on an M1 Pro's hypervisor.


Why can a TLB miss cost up to 24 memory reads in a VM?
With nested paging the guest's page-table pointers are guest-physical addresses, so each of the 4 guest levels needs a 4-level host walk plus its own read (20), and the final guest-physical address needs one more host walk (4): (4+1)(4+1)-1 = 24. Huge pages in either stage shorten it (19 with 2 MiB host pages); page-walk caches make most misses much cheaper.


A thread hand-off between CPUs is 10 times slower in a VM than on bare metal. Why, and what would you do?
The wake-up needs an inter-processor interrupt. Sending it, acknowledging it and ending it can each exit to the hypervisor if the interrupt controller is emulated, and if the target vCPU was idle its host thread must be woken by the host scheduler. Fixes at the platform level: in-kernel and hardware-assisted interrupt virtualization (vGIC on GICv3/v4, APICv and posted interrupts, AVIC), halt polling, dedicated cores. In the application: fewer, larger hand-offs, brief spinning where a core can be spared.


What does the IOMMU do in GPU passthrough, and why do GPU VMs pin all their memory?
It translates and checks every DMA address the device issues, so a guest's GPU sees guest-physical addresses mapped to that guest's host pages and nothing else; it also remaps interrupts. Because a device cannot take page faults like a CPU, the pages it may DMA into must stay resident: VFIO pins every page it maps, and QEMU maps all guest RAM, so balloon, KSM or swap-based overcommit cannot apply.


Compare time slicing, MPS and MIG for sharing a GPU between two inference services.
Time slicing: contexts take turns; no concurrency, no memory limit or fault isolation between users. MPS: one server merges the clients' work so it runs concurrently; separate address spaces but shared memory bandwidth and caches and no full error isolation. MIG: hardware partitions with their own SMs, L2 slices, memory controllers and DRAM; predictable latency and fault isolation, up to 7 instances, reconfigured only when idle. For two latency-sensitive services from different teams, MIG.


Walk me through what happens below cudaMalloc on the first call in a process.
The runtime loads libcuda.so.1 (the user-mode driver, from the host), which initialises: opens /dev/nvidiactl, checks versions with the kernel module, allocates RM objects (client, device, subdevice) by ioctl, opens /dev/nvidiaN, creates a context with its channels and maps them; then the allocation itself is an RM allocation ioctl plus a mapping into the GPU's address space. Later kernel launches write into mapped command buffers and ring a doorbell without a system call.


A container prints "no CUDA-capable device is detected" on a GPU node. How do you debug it?
Check, in order: is libcuda.so.1 present (the NVIDIA container runtime or CDI injects it; without it the error is "driver version is insufficient"), do /dev/nvidiactl and /dev/nvidiaN exist in the container, may the container open them (device cgroup: EPERM), is CUDA_VISIBLE_DEVICES empty or wrong, and does the host see the GPU (nvidia-smi, dmesg Xid). strace -f -e openat,ioctl shows which step fails.


Your image is built with CUDA 13.4 and the cluster runs driver 570. Will it run?
Driver 570 belongs to CUDA 12.8, a different major version, so minor version compatibility does not apply; the toolkit's minimum for 13.x is 580. On data-centre GPUs, install cuda-compat-13-4 in the image and put /usr/local/cuda/compat on LD_LIBRARY_PATH: NVIDIA's matrix marks that combination compatible. On consumer GPUs, use a 12.x build or upgrade the driver.
