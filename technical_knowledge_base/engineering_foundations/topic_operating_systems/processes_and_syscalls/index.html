1. The process, as the kernel sees it

ch. 4 The Abstraction: The Process

A program is a file: instructions and initial data. Running it needs memory to hold it, a CPU pointed at its first instruction, a record of every file it opens, and a way to stop, resume and clean up after it. OSTEP calls the bundle a process's machine state: its memory (the address space), its registers (including the program counter and stack pointer), and its I/O state (open files). In Linux the record is struct task_struct (include/linux/sched.h line 778), several kilobytes, and the surprise for most people is that there is one per thread, not one per process. Linux calls each a task; a "process" is a group of tasks that point at the same memory, the same file table and the same signal handlers (the bottom row of the figure above).

PID and TGID. Every thread has its own id, stored in pid. What user space calls the process id is the thread group id tgid, the id of the first thread. getpid() returns the tgid; gettid() (Python's threading.get_native_id()) returns the task's own id. top -H and /proc/<pid>/task/ show the threads one by one.

2. System calls: the one door into the kernel

ch. 6 Limited Direct Execution

Your program runs directly on the CPU at full speed, but in user mode, where the hardware refuses anything that could harm other programs: touching a device, changing the memory map, disabling interrupts. The kernel runs in kernel mode. A program that wants something privileged must ask, and the request has to be a controlled jump into kernel code at a place the kernel chose, never at an address the program picks. That jump is a system call (the root's section 1 introduced it; here is exactly how it works).


The contract: a number, six registers, one instruction. The program puts the call number and up to six arguments in fixed registers and executes one trapping instruction; the kernel puts the result back in a register. That convention is the system-call ABI (application binary interface): on arm64 (this page's runs) the number goes in x8, the arguments in x0 to x5, the instruction is svc #0 ("supervisor call") and read is number 63; on x86-64 (most GPU servers) they are rax, rdi, rsi, rdx, r10, r8, r9, syscall and number 0. Failure is a number too: the kernel returns a negative error number between -4095 and -1, never sets a variable; the C library's wrapper negates it into errno (a per-thread variable) and returns -1, and CPython turns -1 plus errno into an exception: errno 9 (EBADF) becomes OSError: [Errno 9] Bad file descriptor, errno 2 becomes FileNotFoundError. Why strace is so slow, and what to use instead
strace uses ptrace(2): at every system call entry and exit the kernel stops your thread and wakes strace, which reads your registers with more system calls, prints, and resumes you. Counts and order from strace are exact; durations are not (the root's job ran about 170 s under strace against about 2 s without). For timing use perf trace or perf stat -e 'syscalls:sys_enter_*' (kernel tracepoints, no stops), or strace --seccomp-bpf -e trace=..., which uses a seccomp filter so the tracee stops only on the calls you asked for.


The bill, measured by tracing the tracer; PEP 475 word for word (depth)
PEP 475: "System call wrappers provided in the standard library should be retried automatically when they fail with EINTR", and "the system call is only retried if the signal handler does not raise an exception".
For each extra call traced, strace itself made 4 wait4, 4 ptrace and 2 write calls (the difference between tracing 5,000 and 10,000 getppid calls, src/runs/out/strace_meta.txt), plus two stops of your thread, each a round trip through the scheduler.


Predict: a data loader makes 2 million small read calls per epoch and takes 10 s. You run it under strace -f to find out why. About how long will the epoch take?

Interrupted calls: EINTR and restarting


A call that blocks (a read from an empty pipe, a wait, a sleep) can be interrupted by a signal whose handler runs (section 6). The kernel then restarts the call after the handler returns, if the handler was installed with SA_RESTART and the call is restartable, or fails it with EINTR ("interrupted system call") and leaves the retry to you (signal(7), "Interruption of system calls"). C code that forgets this has a bug that shows only when a signal arrives, for example on preemption. Python retries for you since 3.5, unless the handler raises (PEP 475); that is why time.sleep keeps sleeping after its handler ran in section 6. The root's Syscall tracer tab lists every call the job makes; seccomp, the filter that decides which numbers a container may call, is Containers and isolation.






3. Creating processes: fork, threads, vfork, posix_spawn

ch. 5 Interlude: Process API

A new process needs everything a process has: an address space, a descriptor table, signal settings, an identity. Unix's answer, from 1970 and still the default, is to copy the caller with fork(): one call, two returns. The copy is then free to change itself (redirect its output, drop privileges) and, usually, to replace its program with exec (section 4).


pid_t pid = fork();          /* one call, two returns */
if (pid == 0) {               /* in the child: fork returned 0 */
    execlp("python", "python", "train.py", NULL);   /* only returns on failure */
    _exit(127);
}
int status; waitpid(pid, &status, 0);   /* in the parent: pid is the child's PID */


Threads and processes are the same call with different flags


Every way of making a task ends in one kernel function, copy_process in kernel/fork.c. It allocates a new task_struct and then, for each resource, either shares the parent's or copies it, decided by clone flags. Plain fork passes none of the sharing flags, so everything is copied; a thread passes all of them; vfork shares only the memory. Copying the address space copies the page tables of private memory, with writable pages marked read-only so the first write copies the page (copy-on-write); copying the descriptor table gives new entries that point to the same open files (section 7).

vfork and posix_spawn: start a program without copying the parent


If the child is going to call exec straight away, copying the parent's page tables is wasted work. vfork (clone with CLONE_VM | CLONE_VFORK) lets the child borrow the parent's memory and suspends the parent until the child calls exec or _exit (the kernel waits in wait_for_vfork_done). It is fast and dangerous: the child must not return from the function that called vfork or touch the parent's variables, because it is running on the parent's memory. posix_spawn wraps that danger in a safe API: glibc 2.36 implements it with CLONE_VM | CLONE_VFORK on a separate stack (spawni.c line 385), and lets you list the descriptor and signal changes to apply in the child.

Fork in a multi-threaded process


Only the calling thread survives fork, but all of memory is copied, including every lock. If another thread held a lock at that instant (the allocator's, a logging handler's, an OpenMP runtime's), the child has a lock that no thread will ever release, and the first time the child needs it, it hangs forever. POSIX says that after fork in a multi-threaded process the child may only call async-signal-safe functions until it calls exec (fork(2), NOTES). pthread_atfork handlers let libraries reset their locks around fork, and CPython does this for its own locks, but not every library does. Python 3.12 started warning: "if Python is able to detect that your process has multiple threads, os.fork() now raises a DeprecationWarning" (os.fork docs), and Python 3.14 moved the Linux default start method to forkserver for this reason. The root's Debug lab reproduces the hang ("A worker hangs forever: fork while another thread holds a lock"), and the root covers fork after CUDA. What happens to the pages after fork (copy-on-write faults, the reference-count problem that makes DataLoader workers grow) is Virtual memory and the root's OS simulators tab.






4. exec: replacing the program, keeping the process

ch. 5 Interlude: Process API

fork gives you a second copy of the same program. To run a different one, the process throws away its code and memory and loads a new program, while staying the same process: same PID, same parent, same place in the tree. That is execve(path, argv, envp), the one system call behind execl, execvp, os.execv and every shell command. On success it never returns, because the code that called it no longer exists. The point of no return is begin_new_exec: it drops the old address space, kills the process's other threads, closes every descriptor marked close-on-exec, and resets every caught signal to its default action, because the handler functions lived in the memory that was just discarded.

Why fork and exec are separate
Splitting "make a process" from "run a program" means the child can set itself up with ordinary calls in between: dup2 a log file onto fd 1, chdir, setsid, drop privileges, set rlimits, close descriptors. No special API needed. OSTEP's chapter 5 makes this argument, and it is why a shell can implement python train.py > log 2>&1 & in a few lines (step through it in section 7). The cost is the fork itself (section 3), which is why posix_spawn takes those set-up steps as a list of "file actions" instead. How a program's file is mapped into memory is Virtual memory.






5. wait, exit, zombies, orphans and PID 1

ch. 5 Interlude: Process API

When a process ends, someone usually needs to know how: did the worker finish, crash, or get killed? The kernel keeps the answer until the parent asks for it. What a handler may do: async-signal safety


A handler runs in the middle of whatever the thread was doing, possibly halfway through malloc with the allocator's lock held, or halfway through printf with stdout's lock held. If the handler then calls malloc or printf, it waits for a lock its own thread holds: a deadlock that happens once in a thousand runs. POSIX lists the functions that are safe to call from a handler, the async-signal-safe ones (write, _exit, kill, sigaction and a few dozen more; not malloc, printf, or anything that takes a lock; signal-safety(7)). The safe patterns are: set a volatile sig_atomic_t flag and return; write one byte to a pipe that the main loop watches (the "self-pipe trick"); or block the signal and receive it as data, with sigwaitinfo or a signalfd, a descriptor you can read and put in epoll like any other (signalfd(2)).


Python's handlers run later, and only in the main thread


CPython installs one C handler for every signal you register. It does the async-signal-safe minimum: it records the signal number and sets a flag (and writes to the wakeup descriptor if one was set). Your Python function runs later, at the next bytecode, and always in the main thread (signal docs). So the question that matters for preemption is: how long until the main thread next executes bytecode? 7. File descriptors: three tables, pipes and sockets

ch. 39 Files and Directories (open file table, fork and dup)

A process uses files, pipes, sockets, terminals and devices, and the kernel must not hand it raw pointers to any of them. So it hands out small integers, file descriptors, that index a table the kernel keeps for that process. "Everything is a file" in Unix really means "everything is reached through a descriptor": the same read, write, close and poll work on all of them.


Three tables, not one


The offset lives in the description, so fork and dup share it and a second open does not




1. Per process: the fd table, an array of pointers indexed by fd number plus a close-on-exec bit per fd. 2. System-wide: open file descriptions, one per open() call, holding a reference count, the open flags and the current offset. 3. The object: the inode of a file on disk, a pipe's buffer, a socket, a terminal. The figure is this page's model of the tables after a parent opened train.log as fd 3, forked, the child opened the same file again as fd 4, and the parent wrote 7 bytes: the child's fd 3 sees offset 7 too, its fd 4 is still at 0.


The three structures in the kernel source (v6.12) (reference)
The fd table is struct files_struct; the first 64 slots are built in (NR_OPEN_DEFAULT is the word size, line 24) and it grows as needed. A description is struct file: the reference count f_count (line 1033), the flags you opened with f_flags (1040) and the offset f_pos (1051).




Everything that confuses people about descriptors follows from where each piece of state lives. open() creates a new description and gives it the lowest free fd number; that rule is what makes close(1); open("log") redirect stdout, and it is why fd numbers in the listings below are reused. dup(fd) and dup2(old, new) create a second fd pointing to the same description. fork copies table 1 (dup_fd, section 3), so parent and child point to the same descriptions too, and share the offset. Pipes: a 64 KiB buffer, and EOF that needs every writer gone


A pipe is a kernel buffer with a read end and a write end, each a description. A writer that fills the 65,536-byte buffer blocks (or gets EAGAIN if non-blocking) until the reader drains it; that is how a slow consumer slows the producer, the back-pressure every pipeline relies on. Writes of up to PIPE_BUF (4,096) bytes are atomic: they never interleave with another writer's (pipe(7)); bigger writes can. The default size comes from PIPE_DEF_BUFFERS = 16 pages (pipe_fs_i.h line 5) and can be raised per pipe to pipe-max-size (1 MiB here) with F_SETPIPE_SZ. Writing to a pipe whose read ends are all closed raises SIGPIPE, or EPIPE where SIGPIPE is ignored, as in Python, where it becomes BrokenPipeError (python train.py | head).

Descriptors that travel: how batches reach the trainer


A DataLoader worker does not copy a batch to the main process. It creates a file in /dev/shm, maps it, deletes its name at once, and sends the descriptor over a Unix domain socket; the main process maps the same memory. The job's real tables below show the result: files named torch_29_... open in the main process, created by worker PID 29.


Passing a descriptor between processes uses sendmsg with an SCM_RIGHTS control message on a Unix socket: the kernel installs a new fd in the receiver pointing to the same description (unix(7)). 8. Process groups, sessions, limits and identity

beyond OSTEP: credentials(7), getrlimit(2)

Process groups and sessions: who gets signalled together


Every process belongs to a process group (identified by a PGID, the PID of its first member) and every group to a session (SID). A child inherits both. They exist for job control: a shell puts each pipeline in its own group, and the terminal sends Ctrl-C's SIGINT to every process in the foreground group at once. kill(-pgid, sig) (Python os.killpg) does the same from code. setsid() starts a new session and group, detached from any terminal: what daemons do, and what start_new_session=True does in subprocess (credentials(7) describes both).


Two consequences for training:


    

  • Ctrl-C reaches the workers too. In a terminal, the trainer and its DataLoader workers are one foreground group, so all of them get SIGINT. The workers catch the resulting KeyboardInterrupt and exit quietly ("Main process will raise KeyboardInterrupt anyways", torch 2.14 _utils/worker.py line 396), and the main process unwinds.
    • 

  • torchrun signals groups, not processes. torchrun starts each trainer with start_new_session=True (subprocess_handler.py), so each trainer leads its own session and group, and its DataLoader workers join that group. To stop a trainer it calls os.killpg(trainer_pid, SIGTERM). In the recorded process tree under torchrun (section 9), PGID and SID of the trainer and its two workers are all the trainer's PID; the SIGTERM therefore reaches the workers directly, which section 9 shows has a cost.
    • 



Resource limits


Each process carries soft and hard resource limits: the soft one is enforced, and a process may raise it up to the hard one (only a privileged process can raise the hard one). They are inherited across fork and exec, which is why ulimit -n 65536 in a launcher script applies to everything it starts. Two bite training jobs most: open files (Docker here sets 1,048,576, but many hosts and Slurm jobs start with a soft limit of 1,024, which the file_descriptor tensor-sharing strategy and many-shard data loaders exceed: Errno 24) and locked memory (64 KiB here; RDMA pins buffers against it, so GPU containers run with --ulimit memlock=-1).


Change them with ulimit in a shell, prlimit --pid <pid> for a running process, resource.setrlimit in Python, docker run --ulimit, or Slurm's --propagate.

In _worker_loop each worker installs C-level handlers for SIGBUS, SIGSEGV, SIGFPE and SIGTERM that print an error and die (exactly the worker SigCgt decoded in section 6), names its thread pt_data_worker (the comm in section 1), sets torch.set_num_threads(1), seeds its random generators with base_seed + worker_id, and calls your worker_init_fn.
    3. 

  3. Loop. While the ManagerWatchdog sees the original parent (section 5), it waits up to MP_STATUS_CHECK_INTERVAL = 5.0 s for an index, builds the batch, and puts it on the result queue; tensors travel as shared-memory descriptors (section 7).
    4. 

  4. Failure. If a worker dies, the main process gets SIGCHLD; its handler calls _error_if_any_worker_fails(), which uses waitid to find a worker that died and raises RuntimeError: DataLoader worker (pid N) is killed by signal: ... in the main thread, wherever it is (the NOTE at the top of signal_handling.py).
    5. 

  5. Shutdown. When the iterator is deleted or exhausted, _shutdown_workers sets a done event, sends each worker a stop message, joins each with a timeout of 5.0 s, and terminates any that remain. Workers are re-created for the next epoch unless persistent_workers=True.

torchrun, and the trap in its shutdown


torchrun runs an elastic agent that starts one trainer process per GPU (environment variables RANK, LOCAL_RANK, WORLD_SIZE, MASTER_ADDR, MASTER_PORT tell each who it is), each in its own session (section 8), then polls them. If one fails it stops the others and, up to --max-restarts, starts the group again. For a stop request it registers handlers for SIGTERM, SIGINT, SIGHUP and SIGQUIT (overridable with TORCHELASTIC_SIGNALS_TO_HANDLE); the handler raises SignalException, the agent sends SIGTERM to each trainer's process group, waits up to 30 s, then sends SIGKILL, and finally re-raises, so torchrun itself exits 1 (torch 2.14 torch/distributed/elastic/multiprocessing/api.py lines 76 to 86 and 1023 to 1068; elastic agent docs).

10. Depth: interview rehearsal and the OSTEP map


Interview rehearsal: nine questions, with model answers (optional)


What happens, step by step, when a program calls read()?
The libc wrapper puts the call number and arguments in registers and executes the trap instruction (svc on arm64, syscall on x86-64). The CPU switches to kernel mode and jumps to the kernel's entry; the kernel saves registers, looks the number up in the system-call table, runs sys_read (fd table, then the file's read method, often a copy from the page cache), stores the result in the return register and returns to user mode. The wrapper turns a negative result into errno and -1. A few hundred nanoseconds when nothing blocks.


What is the difference between a process and a thread on Linux?
Both are tasks made by clone. Threads share the address space, descriptor table, signal handlers and thread group id (flags CLONE_VM | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD...); a process gets copies. Threads share memory cheaply and crash together; processes are isolated and each has its own GIL in CPython.


Why does fork return twice, and what does the child inherit?
The kernel creates a second task that resumes from the same point; it sets the return register to 0 in the child and the child's PID in the parent. The child gets copies of the address space (copy-on-write), the descriptor table (same open file descriptions, shared offsets), signal handlers and mask, credentials, limits and current directory; not pending signals, timers, locks or other threads.


What is a zombie, and how do you get rid of one?
A process that has exited but whose parent has not yet called wait; only its PID and exit status remain. You cannot kill it (it is already dead): the parent must wait, or die so that init or a subreaper adopts and reaps it. In containers, make sure PID 1 reaps (an init such as tini).


Why might docker stop take 10 seconds and end with 137?
SIGTERM went to PID 1, which ignored it: either PID 1 has no handler (a namespace's init drops default-action signals) or it is a shell that does not forward. After the grace period Docker sent SIGKILL: 128 + 9 = 137.


Can a signal handler call printf or malloc?
No: they are not async-signal-safe. The handler may have interrupted the same function holding the same lock, and would deadlock. Set a sig_atomic_t flag, write to a pipe, or receive signals synchronously with signalfd or sigwaitinfo.


What is the difference between a file descriptor and an open file description?
The descriptor is an index in one process's table; the description is the kernel object created by open, holding the offset and flags. dup and fork create new descriptors for the same description (shared offset); a second open creates a new description.


Why can a reader of a pipe hang even after the writer closed it?
EOF requires every write-end descriptor in every process to be closed. A forked or exec'd process that inherited a write end keeps the pipe open. Close unused ends after fork and use O_CLOEXEC.


How would you make a PyTorch job survive preemption?
The trainer receives SIGTERM directly (exec form or a forwarding init); its handler sets a flag; the loop checkpoints atomically after the step and exits 0; DataLoader workers ignore SIGTERM so a group signal cannot crash the trainer first; steps and collectives are bounded so the grace period is enough; resume from the last checkpoint on restart.
