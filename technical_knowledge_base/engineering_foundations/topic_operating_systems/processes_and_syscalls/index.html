In one screen

A process is a running program plus everything the kernel keeps for it: its memory, its open files, its signal settings, its identity. A program can do almost nothing by itself: to open a file, start a worker, or hear that it is being shut down, it must ask the kernel, and the only way to ask is a system call. 1. The process, as the kernel sees it

ch. 4 The Abstraction: The Process

The problem. A program is a file: instructions and initial data. Running it needs much more: memory to hold it, a CPU pointed at its first instruction, a record of every file it opens, and a way to stop it, resume it, and clean up after it, while dozens of other programs do the same. OSTEP calls the bundle a process's machine state: its memory (the address space), its registers (including the program counter and stack pointer), and its I/O state (open files). The kernel keeps one record per process holding or pointing to all of it.

task_struct: one record per thread

In Linux that record is struct task_struct (include/linux/sched.h line 778), a structure of several kilobytes. The surprise for most people: there is one per thread, not one per process. Linux calls each a task. A "process" is a group of tasks that point at the same memory, the same file table and the same signal handlers. The fields that this page keeps coming back to:

2. System calls: the one door into the kernel

ch. 6 Limited Direct Execution

The problem. Your program runs directly on the CPU at full speed, but in user mode, where the hardware refuses anything that could harm other programs: touching a device, changing the memory map, disabling interrupts. The kernel runs in kernel mode. A program that wants something privileged must ask, and the request has to be a controlled jump into kernel code at a place the kernel chose, never at an address the program picks. That jump is a system call. The root page's section 1 introduced it; here is exactly how it works.

Why strace is so slow, and what to use instead
strace uses ptrace(2): at every system call entry and exit the kernel stops your thread, wakes the strace process, which reads your registers (more system calls), prints, and resumes you. Tracing the tracer shows the bill: for each extra call traced, strace itself made 4 wait4, 4 ptrace and 2 write calls (the difference between tracing 5,000 and 10,000 getppid calls, src/runs/out/strace_meta.txt), plus two stops of your thread, each a round trip through the scheduler. Counts and order from strace are exact; durations are not (the root's job ran about 170 s under strace against about 2 s without). For timing use perf trace or perf stat -e 'syscalls:sys_enter_*' (kernel tracepoints, no stops), or strace --seccomp-bpf -e trace=..., which uses a seccomp filter so the tracee stops only on the calls you asked for.

Interrupted calls: EINTR and restarting


A call that blocks (a read from a pipe that is empty, a wait, a sleep) can be interrupted by a signal whose handler runs (section 6). The kernel then either restarts the call after the handler returns, if the handler was installed with SA_RESTART and the call is restartable, or fails it with EINTR ("interrupted system call") and leaves the retry to you (signal(7), "Interruption of system calls"). C code that forgets this has a bug that only shows when a signal arrives, for example on preemption. Python retries for you since 3.5: "System call wrappers provided in the standard library should be retried automatically when they fail with EINTR", and "the system call is only retried if the signal handler does not raise an exception" (PEP 475); that is why the handler-latency experiment in section 6 sees time.sleep keep sleeping after its handler ran.

3. Creating processes: fork, vfork, clone, posix_spawn

ch. 5 Interlude: Process API

The problem. A new process needs everything a process has: an address space, a descriptor table, signal settings, an identity. Unix's answer, from 1970 and still the default, is to copy the caller: fork(). The copy is then free to change itself (redirect its output, drop privileges) and, usually, to replace its program with exec (section 4).


pid_t pid = fork();          /* one call, two returns */
if (pid == 0) {               /* in the child: fork returned 0 */
    execlp("python", "python", "train.py", NULL);   /* only returns on failure */
    _exit(127);
}
int status; waitpid(pid, &status, 0);   /* in the parent: pid is the child's PID */

vfork and posix_spawn: start a program without copying the parent


If the child is going to call exec straight away, copying the parent's page tables is wasted work. vfork (clone with CLONE_VM | CLONE_VFORK) lets the child borrow the parent's memory and suspends the parent until the child calls exec or _exit (the kernel waits in wait_for_vfork_done). It is fast and dangerous: the child must not return from the function that called vfork or touch the parent's variables, because it is running on the parent's memory. posix_spawn wraps that danger in a safe API: glibc 2.36 implements it with CLONE_VM | CLONE_VFORK on a separate stack (spawni.c line 385), and lets you list the descriptor and signal changes to apply in the child.

Fork in a multi-threaded process


Only the calling thread survives fork, but all of memory is copied, including every lock. If another thread held a lock at that instant (the allocator's, a logging handler's, an OpenMP runtime's), the child has a lock that no thread will ever release, and the first time the child needs it, it hangs forever. POSIX says that after fork in a multi-threaded process the child may only call async-signal-safe functions until it calls exec (fork(2), NOTES). pthread_atfork handlers let libraries reset their locks around fork, and CPython does this for its own locks, but not every library does. Python 3.12 started warning: "if Python is able to detect that your process has multiple threads, os.fork() now raises a DeprecationWarning" (os.fork docs), and Python 3.14 moved the Linux default start method to forkserver for this reason. The root's Debug lab reproduces the hang ("A worker hangs forever: fork while another thread holds a lock"), and the root covers fork after CUDA.

4. exec: replacing the program, keeping the process

ch. 5 Interlude: Process API

The problem. fork gives you a second copy of the same program. To run a different one, the process must throw away its code and memory and load a new program, while staying the same process: same PID, same parent, same place in the tree. That is execve(path, argv, envp), the one system call behind execl, execvp, os.execv and every shell command. On success it never returns, because the code that called it no longer exists.

Why fork and exec are separate
Splitting "make a process" from "run a program" means the child can set itself up with ordinary calls in between: dup2 a log file onto fd 1, chdir, setsid, drop privileges, set rlimits, close descriptors. No special API needed. OSTEP's chapter 5 makes this argument, and it is why a shell can implement python train.py > log 2>&1 & in a few lines. The cost is the fork itself (section 3), which is why posix_spawn takes those set-up steps as a list of "file actions" instead.

5. wait, exit, zombies, orphans and PID 1

ch. 5 Interlude: Process API

The problem. When a process ends, someone usually needs to know how: did the worker finish, crash, or get killed? The kernel keeps the answer until the parent asks for it. Between "ended" and "asked" the process is a zombie; a process whose parent ends first is an orphan and needs a new parent. Containers make PID 1 your problem.

Generated, pending, delivered


A signal has a life in three stages, and most bugs live between them.


    

  1. Generated. kill(pid, SIGTERM) enters __send_signal_locked. prepare_signal drops it at once if the target ignores it (and for PID 1, if no handler is installed: section 5).
    2. 

  2. Pending. It is recorded in a pending set: the thread's own (for a signal aimed at one thread, such as a SIGSEGV caused by that thread) or the process's shared one (for kill to a PID). A standard signal that is already pending is not recorded again: legacy_queue returns true for "sig < SIGRTMIN and already a member", and the second one is lost. Real-time signals are queued one by one, each with its sender's information, up to the RLIMIT_SIGPENDING limit (39,345 here). complete_signal then picks a thread that is not blocking it and wakes it.
    3. 

  3. Delivered. Only when that thread is about to return to user mode (after a system call, an interrupt, or being scheduled) does get_signal take it off the pending set and act. For a handler, the kernel writes a frame on the user stack with the interrupted registers, points the program counter at the handler, and when the handler returns, a trampoline calls rt_sigreturn to restore everything. A thread that has the signal blocked (in its mask, set with sigprocmask or pthread_sigmask) leaves it pending until it unblocks.
    4. 



Predict: a process blocks SIGUSR1 and SIGRTMIN, sends itself 1,000 of each, then unblocks them. Its handler counts arrivals. What does it count?




A standard signal is one bit in a set: "at least one arrived". Real-time signals are a queue. So never count events with standard signals; a SIGCHLD handler, for example, must loop on waitpid(-1, ..., WNOHANG) until no child is left, because three children dying together may produce one SIGCHLD. Reading them through a signalfd (part B) gives the same counts: it changes how you receive signals, not how they are queued.


What a handler may do: async-signal safety


A handler runs in the middle of whatever the thread was doing, possibly halfway through malloc with the allocator's lock held, or halfway through printf with stdout's lock held. If the handler then calls malloc or printf, it waits for a lock its own thread holds: a deadlock that happens once in a thousand runs. POSIX lists the functions that are safe to call from a handler, the async-signal-safe ones (write, _exit, kill, sigaction and a few dozen more; not malloc, printf, or anything that takes a lock; signal-safety(7)). The safe patterns are: set a volatile sig_atomic_t flag and return; write one byte to a pipe that the main loop watches (the "self-pipe trick"); or block the signal and receive it as data, with sigwaitinfo or a signalfd, a descriptor you can read and put in epoll like any other (signalfd(2)).


Python's handlers run later, and only in the main thread


CPython installs one C handler for every signal you register. It does the async-signal-safe minimum: it records the signal number and sets a flag (and writes to the wakeup descriptor if one was set). Your Python function runs later: "the low-level signal handler sets a flag which tells the virtual machine to execute the corresponding Python signal handler at a later point (for example, at the next bytecode instruction)", and "Python signal handlers are always executed in the main Python thread of the main interpreter, even if the signal was received in another thread" (signal docs). So the question that matters for preemption is: how long until the main thread next executes bytecode? 7. File descriptors: three tables, pipes and sockets

ch. 39 Files and Directories (open file table, fork and dup)

The problem. A process uses files, pipes, sockets, terminals and devices, and the kernel must not hand it raw pointers to any of them. So it hands out small integers, file descriptors, that index a table the kernel keeps for that process. "Everything is a file" in Unix really means "everything is reached through a descriptor": the same read, write, close and poll work on all of them.


Three tables, not one




1. Per process: the fd tablestruct files_struct holds an array of pointers indexed by fd number, plus a close-on-exec bit per fd. The first 64 slots are built in (NR_OPEN_DEFAULT is the word size, line 24); it grows as needed.


2. System-wide: open file descriptionsOne struct file per open() call: a reference count (f_count, line 1033), the flags you opened with (f_flags, 1040) and the current offset (f_pos, 1051).


3. The objectThe inode of a file on disk, a pipe's buffer, a socket, a terminal: what the description reads from and writes to.




Everything that confuses people about descriptors follows from where each piece of state lives. open() creates a new description and gives it the lowest free fd number; that rule is what makes close(1); open("log") redirect stdout, and it is why fd numbers in the listings below are reused. dup(fd) and dup2(old, new) create a second fd pointing to the same description. fork copies table 1 (dup_fd, section 3), so parent and child point to the same descriptions too, and share the offset. Pipes: a 64 KiB buffer, and EOF that needs every writer gone


A pipe is a kernel buffer with a read end and a write end, each a description. Measured on this kernel (src/runs/c/pipes.c):




A writer that fills the 65,536-byte buffer blocks (or gets EAGAIN if non-blocking) until the reader drains it; that is how a slow consumer slows the producer, the back-pressure every pipeline relies on. 8. Process groups, sessions, limits and identity

beyond OSTEP: credentials(7), getrlimit(2)

Process groups and sessions: who gets signalled together


Every process belongs to a process group (identified by a PGID, the PID of its first member) and every group to a session (SID). A child inherits both. They exist for job control: a shell puts each pipeline in its own group, and the terminal sends Ctrl-C's SIGINT to every process in the foreground group at once. kill(-pgid, sig) (Python os.killpg) does the same from code. setsid() starts a new session and group, detached from any terminal: what daemons do, and what start_new_session=True does in subprocess (credentials(7) describes both).


Two consequences for training:


    

  • Ctrl-C reaches the workers too. In a terminal, the trainer and its DataLoader workers are one foreground group, so all of them get SIGINT. The workers catch the resulting KeyboardInterrupt and exit quietly ("Main process will raise KeyboardInterrupt anyways", torch 2.14 _utils/worker.py line 396), and the main process unwinds.
    • 

  • torchrun signals groups, not processes. torchrun starts each trainer with start_new_session=True (subprocess_handler.py), so each trainer leads its own session and group, and its DataLoader workers join that group. To stop a trainer it calls os.killpg(trainer_pid, SIGTERM). In the Shutdown lab's process tree under torchrun, PGID and SID of the trainer and its two workers are all the trainer's PID; the SIGTERM therefore reaches the workers directly, which section 9 shows has a cost.
    •

10. Common mistakes, interview questions, and the OSTEP map


Common mistakes


Starting the job with sh -c "python train.py" in a container
Debian's dash stays as PID 1 and drops SIGTERM; the job is SIGKILLed after the grace period (10.3 to 10.4 s and exit 137 in all runs here). Use the exec form, or exec python .... Bash happens to exec a single simple command, which is why the same line works on some images and not others.


Checkpointing inside the signal handler
In C it is not async-signal-safe; in Python the handler runs between bytecodes in the main thread, possibly in the middle of an optimizer step, and cannot run at all while a long C++ call is in progress. Set a flag; checkpoint in the loop.


Expecting one SIGCHLD (or SIGUSR1) per event
Standard signals coalesce: 1,000 sent, 1 handled (section 6). Loop on waitpid(-1, WNOHANG); use real-time signals or a descriptor if you need counts.


Calling exit() in a forked child
It flushes the parent's buffered output a second time and runs the parent's atexit handlers. Use _exit/os._exit, and flush before forking.


Forgetting a write end, or a descriptor without close-on-exec
The reader never sees EOF while any copy is open anywhere (2.0 s here, forever in practice). Close unused ends after fork; open with O_CLOEXEC.


Writing 2>&1 > log
Redirections apply left to right: stderr is copied from stdout before stdout moves to the log, so tracebacks go to the terminal. Write > log 2>&1.


Forking a large trainer for small jobs
fork scales with the parent's page tables: 17 ms per GiB of 4 KiB pages here, plus copy-on-write faults afterwards. Use subprocess (vfork) or a forkserver started early.


Profiling with strace

Interview questions, with model answers


What happens, step by step, when a program calls read()?
The libc wrapper puts the call number and arguments in registers and executes the trap instruction (svc on arm64, syscall on x86-64). The CPU switches to kernel mode and jumps to the kernel's entry; the kernel saves registers, looks the number up in the system-call table, runs sys_read (fd table, then the file's read method, often a copy from the page cache), stores the result in the return register and returns to user mode. The wrapper turns a negative result into errno and -1. A few hundred nanoseconds when nothing blocks.


What is the difference between a process and a thread on Linux?
Both are tasks made by clone. Threads share the address space, descriptor table, signal handlers and thread group id (flags CLONE_VM | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD...); a process gets copies. Threads share memory cheaply and crash together; processes are isolated and each has its own GIL in CPython.


Why does fork return twice, and what does the child inherit?
The kernel creates a second task that resumes from the same point; it sets the return register to 0 in the child and the child's PID in the parent. The child gets copies of the address space (copy-on-write), the descriptor table (same open file descriptions, shared offsets), signal handlers and mask, credentials, limits and current directory; not pending signals, timers, locks or other threads.


What is a zombie, and how do you get rid of one?
A process that has exited but whose parent has not yet called wait; only its PID and exit status remain. You cannot kill it (it is already dead): the parent must wait, or die so that init or a subreaper adopts and reaps it. In containers, make sure PID 1 reaps (an init such as tini).


Why might docker stop take 10 seconds and end with 137?
SIGTERM went to PID 1, which ignored it: either PID 1 has no handler (a namespace's init drops default-action signals) or it is a shell that does not forward. After the grace period Docker sent SIGKILL: 128 + 9 = 137.


Can a signal handler call printf or malloc?
No: they are not async-signal-safe. The handler may have interrupted the same function holding the same lock, and would deadlock. Set a sig_atomic_t flag, write to a pipe, or receive signals synchronously with signalfd or sigwaitinfo.


What is the difference between a file descriptor and an open file description?
The descriptor is an index in one process's table; the description is the kernel object created by open, holding the offset and flags. dup and fork create new descriptors for the same description (shared offset); a second open creates a new description.


Why can a reader of a pipe hang even after the writer closed it?
EOF requires every write-end descriptor in every process to be closed. A forked or exec'd process that inherited a write end keeps the pipe open. Close unused ends after fork and use O_CLOEXEC.


How would you make a PyTorch job survive preemption?
The trainer receives SIGTERM directly (exec form or a forwarding init); its handler sets a flag; the loop checkpoints atomically after the step and exits 0; DataLoader workers ignore SIGTERM so a group signal cannot crash the trainer first; steps and collectives are bounded so the grace period is enough; resume from the last checkpoint on restart.
