1. The process, as the kernel sees it

ch. 4 The Abstraction: The Process

The problem. A program is a file: instructions and initial data. Running it needs much more: memory to hold it, a CPU pointed at its first instruction, a record of every file it opens, and a way to stop it, resume it, and clean up after it, while dozens of other programs do the same. OSTEP calls the bundle a process's machine state: its memory (the address space), its registers (including the program counter and stack pointer), and its I/O state (open files). The kernel keeps one record per process holding or pointing to all of it.

task_struct: one record per thread

In Linux that record is struct task_struct ({{include/linux/sched.h line 778|https://github.com/torvalds/linux/blob/v6.12/include/linux/sched.h#L778}}), a structure of several kilobytes. The surprise for most people: there is one per thread, not one per process. Linux calls each a task. A "process" is a group of tasks that point at the same memory, the same file table and the same signal handlers. The fields that this page keeps coming back to:

PID and TGID. Because every thread is a task, every thread has its own id, stored in pid. What user space calls the process id is the thread group id tgid, the id of the first thread. getpid() returns the tgid; gettid() (Python's threading.get_native_id()) returns the task's own id. top -H and /proc/<pid>/task/ show the threads one by one.

The running job, read from /proc

Here is the job with two fork DataLoader workers, captured from inside its container while it trained (src/runs/in_container_proc.sh). /proc is not on any disk: the kernel writes this text when you read it ({{proc(5)|https://man7.org/linux/man-pages/man5/proc.5.html}}).



Main process: /proc/<main>/status (selected lines)
A DataLoader worker


Read it line by line. Tgid equals Pid for both: these are the leaders of their thread groups. The main process has 8 threads (the root's {{Syscall tracer|n:3f05c17b0d0d81c5a97ce991644af140}} tab shows the clone calls that create them); each worker has 4 even though DataLoader sets torch.set_num_threads(1) inside it, because a forked child inherits only the thread that called fork and starts new ones as it imports and computes. The worker's PPid is the main process; the main process's PPid is 1, the container's shell. SigIgn and SigCgt are bit masks of ignored and caught signals: section 6 decodes them, and they show that torch caught different signals in the worker than in the main process. Seccomp: 2 means a seccomp filter is active (Docker's default profile); the ctxt_switches counters are how often this task gave up the CPU voluntarily (blocking) or was preempted.

A lowercase s, l or + after the letter in ps means session leader, multi-threaded, and in the foreground process group (section 8). So Sl is "sleeping, has threads": exactly the workers above.
