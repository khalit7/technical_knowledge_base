The DataLoader uses the multiprocessing default unless you pass multiprocessing_context. Costs on this machine (section 3 and the root): a fork worker is ready in milliseconds; a spawn or forkserver worker needs a fresh interpreter that imports torch, about 0.65 to 0.94 s, paid again at every epoch unless persistent_workers=True. With forkserver, multiprocessing.set_forkserver_preload(["torch"]) pays the import once in the server (the root measured 0.035 s per new iterator after a 0.703 s first one). Name the start method in code; do not let a Python upgrade choose it.

The DataLoader's worker processes, from the source

Read from torch 2.14's torch/utils/data/dataloader.py and _utils/worker.py inside the lab image:

  1. Start. iter(loader) creates one index queue per worker and one shared result queue, then starts each worker as a multiprocessing.Process with daemon = True (line 1168), so it is killed if the main process exits normally without shutting it down. The main process installs its SIGCHLD handler (_set_SIGCHLD_handler).
  2. Worker set-up. In _worker_loop each worker installs C-level handlers for SIGBUS, SIGSEGV, SIGFPE and SIGTERM that print an error and die (exactly the worker SigCgt decoded in section 6), names its thread pt_data_worker (the comm in section 1), sets torch.set_num_threads(1), seeds its random generators with base_seed + worker_id, and calls your worker_init_fn.
  3. Loop. While the ManagerWatchdog sees the original parent (section 5), it waits up to MP_STATUS_CHECK_INTERVAL = 5.0 s for an index, builds the batch, and puts it on the result queue; tensors travel as shared-memory descriptors (section 7).
  4. Failure. If a worker dies, the main process gets SIGCHLD; its handler calls _error_if_any_worker_fails(), which uses waitid to find a worker that died and raises RuntimeError: DataLoader worker (pid N) is killed by signal: ... in the main thread, wherever it is (the NOTE at the top of signal_handling.py).
  5. Shutdown. When the iterator is deleted or exhausted, _shutdown_workers sets a done event, sends each worker a stop message, joins each with a timeout of 5.0 s, and terminates any that remain. Workers are re-created for the next epoch unless persistent_workers=True.

torchrun, and the trap in its shutdown

torchrun runs an elastic agent that starts one trainer process per GPU (environment variables RANK, LOCAL_RANK, WORLD_SIZE, MASTER_ADDR, MASTER_PORT tell each who it is), each in its own session (section 8), then polls them. If one fails it stops the others and, up to --max-restarts, starts the group again. For a stop request it registers handlers for SIGTERM, SIGINT, SIGHUP and SIGQUIT (overridable with TORCHELASTIC_SIGNALS_TO_HANDLE); the handler raises SignalException, the agent sends SIGTERM to each trainer's process group, waits up to 30 s, then sends SIGKILL, and finally re-raises, so torchrun itself exits 1 (torch 2.14 torch/distributed/elastic/multiprocessing/api.py lines 76 to 86 and 1023 to 1068; {{elastic agent docs|https://docs.pytorch.org/docs/stable/elastic/agent.html}}).

Predict: the running job, whose SIGTERM handler sets a flag and checkpoints after the step, is launched with torchrun --nproc-per-node 1 and two DataLoader workers. docker stop sends SIGTERM to torchrun. Does the trainer write its checkpoint?
No, in all three runs. torchrun's killpg delivers SIGTERM to the trainer and to its two DataLoader workers, which are in the trainer's process group. The trainer's handler sets its flag, but the workers' C handlers kill them immediately; the trainer gets SIGCHLD, and the DataLoader's handler raises RuntimeError: DataLoader worker (pid ...) is killed by signal: Terminated. in the middle of the forward pass, before the loop can reach its checkpoint. The fix that worked in all three runs: make the workers ignore SIGTERM in worker_init_fn (which runs after torch installs its handler), so only the trainer reacts and then shuts its workers down itself. See the {{Shutdown lab|#t-stop}}, variants "torchrun" and "torchrun, workers ignore SIGTERM".
def ignore_term(worker_id):                 # runs in each worker, after torch's own handlers
    signal.signal(signal.SIGTERM, signal.SIG_IGN)
loader = DataLoader(ds, num_workers=2, worker_init_fn=ignore_term,
                    multiprocessing_context="forkserver", persistent_workers=True)

The runs used a wrapper (src/runs/py/ignore_term_in_workers.py) that adds this worker_init_fn to the root's unchanged train.py. The same group-signal effect appears without torchrun when anything signals the whole group (pkill -f train.py, kill -- -PGID): the root's Debug lab case "pkill -TERM also hits the workers".

The checklist
  1. Make the trainer PID 1 or have PID 1 forward signals: the exec form in the Dockerfile, exec python ... in scripts, or a real init (--init, tini) whose child is Python itself, not a shell (Shutdown lab).
  2. Install a SIGTERM handler that only sets a flag; checkpoint in the loop, after the step, with the write-fsync-rename pattern of the {{storage page|n:3f05c17b0d0d8141be7acc1313570cbf}}.
  3. Make DataLoader workers ignore SIGTERM when anything may signal the whole group (torchrun does).
  4. Keep the slowest step, plus the checkpoint, shorter than the grace period; set collective timeouts so a dead peer cannot hold the main thread past it (section 6).
  5. Exit 0 after a requested stop, so the scheduler does not count it as a failure and restart it in a loop; check how your launcher reports it (torchrun exits 1).
