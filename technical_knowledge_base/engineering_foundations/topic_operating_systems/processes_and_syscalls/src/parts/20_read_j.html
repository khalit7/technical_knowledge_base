The DataLoader's worker processes, from the source

Read from torch 2.14's torch/utils/data/dataloader.py and _utils/worker.py inside the lab image. Every arrow in the figure is a mechanism from sections 3 to 7:

Workers are forked children fed by queues; the main process learns of a death through SIGCHLD, a worker of an orphaning through polling

In short: each worker is a daemon multiprocessing.Process with its own index queue and a shared result queue; it installs torch's C handlers (the worker SigCgt of section 6), runs with one thread, and polls whether its parent still lives; the main process notices a dead worker through SIGCHLD and raises in the main thread; shutdown is a stop message and a join with a timeout.

The five stages from the source, with line numbers (depth)
  1. Start. iter(loader) creates one index queue per worker and one shared result queue, then starts each worker as a multiprocessing.Process with daemon = True (line 1168), so it is killed if the main process exits normally without shutting it down. The main process installs its SIGCHLD handler (_set_SIGCHLD_handler).
  2. Worker set-up. In _worker_loop each worker installs C-level handlers for SIGBUS, SIGSEGV, SIGFPE and SIGTERM that print an error and die (exactly the worker SigCgt decoded in section 6), names its thread pt_data_worker (the comm in section 1), sets torch.set_num_threads(1), seeds its random generators with base_seed + worker_id, and calls your worker_init_fn.
  3. Loop. While the ManagerWatchdog sees the original parent (section 5), it waits up to MP_STATUS_CHECK_INTERVAL = 5.0 s for an index, builds the batch, and puts it on the result queue; tensors travel as shared-memory descriptors (section 7).
  4. Failure. If a worker dies, the main process gets SIGCHLD; its handler calls _error_if_any_worker_fails(), which uses waitid to find a worker that died and raises RuntimeError: DataLoader worker (pid N) is killed by signal: ... in the main thread, wherever it is (the NOTE at the top of signal_handling.py).
  5. Shutdown. When the iterator is deleted or exhausted, _shutdown_workers sets a done event, sends each worker a stop message, joins each with a timeout of 5.0 s, and terminates any that remain. Workers are re-created for the next epoch unless persistent_workers=True.

torchrun, and the trap in its shutdown

torchrun runs an elastic agent that starts one trainer process per GPU (environment variables RANK, LOCAL_RANK, WORLD_SIZE, MASTER_ADDR, MASTER_PORT tell each who it is), each in its own session (section 8), then polls them. If one fails it stops the others and, up to --max-restarts, starts the group again. For a stop request it registers handlers for SIGTERM, SIGINT, SIGHUP and SIGQUIT (overridable with TORCHELASTIC_SIGNALS_TO_HANDLE); the handler raises SignalException, the agent sends SIGTERM to each trainer's process group, waits up to 30 s, then sends SIGKILL, and finally re-raises, so torchrun itself exits 1 (torch 2.14 torch/distributed/elastic/multiprocessing/api.py lines 76 to 86 and 1023 to 1068; {{elastic agent docs|https://docs.pytorch.org/docs/stable/elastic/agent.html}}).

Predict: the running job, whose SIGTERM handler sets a flag and checkpoints after the step, is launched with torchrun --nproc-per-node 1 and two DataLoader workers. docker stop sends SIGTERM to torchrun. Does the trainer write its checkpoint?
No, in all three runs. torchrun's killpg delivers SIGTERM to the trainer and to its two DataLoader workers, which are in the trainer's process group. The trainer's handler sets its flag, but the workers' C handlers kill them immediately; the trainer gets SIGCHLD, and the DataLoader's handler raises RuntimeError: DataLoader worker (pid ...) is killed by signal: Terminated. in the middle of the forward pass, before the loop can reach its checkpoint. The fix that worked in all three runs: make the workers ignore SIGTERM in worker_init_fn (which runs after torch installs its handler), so only the trainer reacts and then shuts its workers down itself. See the shutdown runs below, variants "torchrun" and "torchrun, workers ignore SIGTERM".
def ignore_term(worker_id):                 # runs in each worker, after torch's own handlers
    signal.signal(signal.SIGTERM, signal.SIG_IGN)
loader = DataLoader(ds, num_workers=2, worker_init_fn=ignore_term,
                    multiprocessing_context="forkserver", persistent_workers=True)

The runs used a wrapper (src/runs/py/ignore_term_in_workers.py) that adds this worker_init_fn to the root's unchanged train.py. The same group-signal effect appears without torchrun when anything signals the whole group (pkill -f train.py, kill -- -PGID): the root's Debug lab case "pkill -TERM also hits the workers".

Ten ways to start the job, and what docker stop did

Ten ways to start the same training job in a container, and what docker stop did to each. docker stop -t 10 sends SIGTERM to the container's PID 1, waits 10 s, then sends SIGKILL: the same sequence as a Kubernetes pod deletion or a Slurm cancellation, with a shorter grace period.

Only the starts that make Python PID 1, or tini's direct child, checkpoint before the SIGKILL line

How the runs were made, and the selected variant's command, process tree and log (real data; click a row above to choose)

The job is the root's running example (src/trace/job/train.py: SIGTERM handler that sets a flag, checkpoint after the step, exit 0) with 2 fork DataLoader workers, 2 CPUs, in kb-os-lab:1 (Debian 12: dash 0.5.12 as sh, bash 5.2.15; Docker 20.10.17, whose --init is tini). Each variant ran 3 times, 2026-10-05: started, waited for training step 5, recorded the process tree with ps, then timed docker stop and read the exit code and the log. Script: src/runs/run_shutdown.sh; raw records: src/runs/out/shutdown/.

In the "--init, exec form" runs the recorded tree caught two workers of the previous epoch as zombies (Z, <defunct>) for a moment, between their exit and the DataLoader's join; tini, as PID 1, would reap any that were orphaned.

  • Whether Python is PID 1 decides everything. The exec form, sh -c "exec ..." and bash -c (bash replaces itself with a single simple command, which is why the same line works on some images and not others) made Python PID 1: clean stop in under a second. Plain sh -c left dash as PID 1, which neither forwards SIGTERM nor dies from it (section 5): 10.3 to 10.4 s, exit 137, every run.
  • An init is not a fix by itself. --init forwards SIGTERM to its one child; a shell child dies at once (it is not PID 1, so the default action applies), tini exits with 143, and the kernel kills the rest of the namespace: no checkpoint, in a third of a second. TINI_KILL_PROCESS_GROUP=1 does not help, because the shell still dies first. With Python as tini's direct child everything works, and orphans are reaped too.
  • torchrun signals process groups (the trap above); ignoring SIGTERM in the workers fixed it in all three runs, and torchrun still exits 1 after a death signal by design.
Predict: docker run --init image sh -c "python train.py; echo done", then docker stop. The Python script has a correct SIGTERM handler. Checkpoint written?
Measured 0.28 to 0.41 s, exit 143, no checkpoint in 3 of 3 runs (variant "--init, sh -c with two commands"). tini forwarded SIGTERM to the shell; the shell died; tini exited; the kernel SIGKILLed Python with the namespace.

The checklist
  1. Make the trainer PID 1 or have PID 1 forward signals: the exec form in the Dockerfile, exec python ... in scripts, or a real init (--init, tini) whose child is Python itself, not a shell (the shutdown runs above).
  2. Install a SIGTERM handler that only sets a flag; checkpoint in the loop, after the step, with the write-fsync-rename pattern of the {{storage page|n:3f05c17b0d0d8141be7acc1313570cbf}}.
  3. Make DataLoader workers ignore SIGTERM when anything may signal the whole group (torchrun does).
  4. Keep the slowest step, plus the checkpoint, shorter than the grace period; set collective timeouts so a dead peer cannot hold the main thread past it (section 6).
  5. Exit 0 after a requested stop, so the scheduler does not count it as a failure and restart it in a loop; check how your launcher reports it (torchrun exits 1).
