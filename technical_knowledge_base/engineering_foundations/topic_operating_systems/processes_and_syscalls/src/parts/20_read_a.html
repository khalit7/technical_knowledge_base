In one screen

A process is a running program plus everything the kernel keeps for it: its memory, its open files, its signal settings, its identity. A program can do almost nothing by itself: to open a file, start a worker, or hear that it is being shut down, it must ask the kernel, and the only way to ask is a system call. This page is about that interface, the few dozen calls that every training script, launcher and container runtime is built from, and the failures that come from misunderstanding them.

The running example is the training job of the {{root page|n:3f05c17b0d0d81c5a97ce991644af140}}: a CPU-only PyTorch run with a memory-mapped dataset, two DataLoader worker processes, a SIGTERM handler and a safe checkpoint. On a real GPU node the same job is a small tree of processes:

torchrun (the launcher, "elastic agent": starts, watches and stops the trainers) ├─ python train.py rank 0 (one trainer per GPU, in its own session) │ ├─ threads: OpenMP/ATen workers, pin_memory thread, NCCL threads (same process) │ ├─ pt_data_worker 0 (DataLoader worker process: fork, spawn or forkserver) │ └─ pt_data_worker 1 └─ python train.py rank 1 ... (and so on, --nproc-per-node of them)

Everything on this page is a question about that tree: how each box was created, what it inherited, how they talk, who is told when one dies, and what happens to all of them when the cluster says "stop".
