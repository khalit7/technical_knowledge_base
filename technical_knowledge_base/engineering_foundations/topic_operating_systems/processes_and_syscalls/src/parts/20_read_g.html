6. Signals: interrupting a process from outside

ch. 5 (signals in brief); beyond OSTEP: {{signal(7)|https://man7.org/linux/man-pages/man7/signal.7.html}}

The problem. A process is busy running its own code. Sometimes the outside world must interrupt it: the user pressed Ctrl-C, a child died, it touched memory it does not own, the cluster wants the node back. A signal is that interruption: a small number delivered asynchronously, which the process can ignore, let the default action happen, or catch with a function of its own, the handler.

Generated, pending, delivered

A signal has a life in three stages, and most bugs live between them.

  1. Generated. kill(pid, SIGTERM) enters {{__send_signal_locked|https://github.com/torvalds/linux/blob/v6.12/kernel/signal.c#L1073}}. {{prepare_signal|https://github.com/torvalds/linux/blob/v6.12/kernel/signal.c#L902}} drops it at once if the target ignores it (and for PID 1, if no handler is installed: section 5).
  2. Pending. It is recorded in a pending set: the thread's own (for a signal aimed at one thread, such as a SIGSEGV caused by that thread) or the process's shared one (for kill to a PID). A standard signal that is already pending is not recorded again: {{legacy_queue|https://github.com/torvalds/linux/blob/v6.12/kernel/signal.c#L1068}} returns true for "sig < SIGRTMIN and already a member", and the second one is lost. Real-time signals are queued one by one, each with its sender's information, up to the RLIMIT_SIGPENDING limit (39,345 here). {{complete_signal|https://github.com/torvalds/linux/blob/v6.12/kernel/signal.c#L994}} then picks a thread that is not blocking it and wakes it.
  3. Delivered. Only when that thread is about to return to user mode (after a system call, an interrupt, or being scheduled) does {{get_signal|https://github.com/torvalds/linux/blob/v6.12/kernel/signal.c#L2683}} take it off the pending set and act. For a handler, the kernel writes a frame on the user stack with the interrupted registers, points the program counter at the handler, and when the handler returns, a trampoline calls rt_sigreturn to restore everything. A thread that has the signal blocked (in its mask, set with sigprocmask or pthread_sigmask) leaves it pending until it unblocks.
Predict: a process blocks SIGUSR1 and SIGRTMIN, sends itself 1,000 of each, then unblocks them. Its handler counts arrivals. What does it count?
A standard signal is one bit in a set: "at least one arrived". Real-time signals are a queue. So never count events with standard signals; a SIGCHLD handler, for example, must loop on waitpid(-1, ..., WNOHANG) until no child is left, because three children dying together may produce one SIGCHLD. Reading them through a signalfd (part B) gives the same counts: it changes how you receive signals, not how they are queued.


What a handler may do: async-signal safety


A handler runs in the middle of whatever the thread was doing, possibly halfway through malloc with the allocator's lock held, or halfway through printf with stdout's lock held. If the handler then calls malloc or printf, it waits for a lock its own thread holds: a deadlock that happens once in a thousand runs. POSIX lists the functions that are safe to call from a handler, the async-signal-safe ones (write, _exit, kill, sigaction and a few dozen more; not malloc, printf, or anything that takes a lock; {{signal-safety(7)|https://man7.org/linux/man-pages/man7/signal-safety.7.html}}). The safe patterns are: set a volatile sig_atomic_t flag and return; write one byte to a pipe that the main loop watches (the "self-pipe trick"); or block the signal and receive it as data, with sigwaitinfo or a signalfd, a descriptor you can read and put in epoll like any other ({{signalfd(2)|https://man7.org/linux/man-pages/man2/signalfd.2.html}}).


Python's handlers run later, and only in the main thread


CPython installs one C handler for every signal you register. It does the async-signal-safe minimum: it records the signal number and sets a flag (and writes to the wakeup descriptor if one was set). Your Python function runs later: "the low-level signal handler sets a flag which tells the virtual machine to execute the corresponding Python signal handler at a later point (for example, at the next bytecode instruction)", and "Python signal handlers are always executed in the main Python thread of the main interpreter, even if the signal was received in another thread" ({{signal docs|https://docs.python.org/3/library/signal.html#execution-of-python-signal-handlers}}). So the question that matters for preemption is: how long until the main thread next executes bytecode? When the main thread is running Python or is blocked in an interruptible wait (sleep, a lock with a timeout), the handler runs within a fraction of a millisecond: the C handler interrupts the wait (which PEP 475 then resumes). When the main thread is inside one long call into C or C++, the handler waits for the call to return: about 1.2 s for one torch.linalg.solve on 4,000 × 4,000 matrices, the whole remaining duration. The np.sort row shows the same in two of three runs; in one run the handler ran after 70 ms, which these runs do not explain. On a GPU node the long calls are a torch.cuda.synchronize(), a blocking .item(), or a collective waiting for a peer that will never answer: the handler cannot run until it returns, which is why preemption-safe training sets collective timeouts and keeps the grace period longer than the slowest step.
