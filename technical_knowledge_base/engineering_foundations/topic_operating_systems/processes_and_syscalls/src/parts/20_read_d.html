3. Creating processes: fork, vfork, clone, posix_spawn

ch. 5 Interlude: Process API

The problem. A new process needs everything a process has: an address space, a descriptor table, signal settings, an identity. Unix's answer, from 1970 and still the default, is to copy the caller: fork(). The copy is then free to change itself (redirect its output, drop privileges) and, usually, to replace its program with exec (section 4).

pid_t pid = fork();          /* one call, two returns */
if (pid == 0) {               /* in the child: fork returned 0 */
    execlp("python", "python", "train.py", NULL);   /* only returns on failure */
    _exit(127);
}
int status; waitpid(pid, &status, 0);   /* in the parent: pid is the child's PID */

What the child gets

The kernel side of every way of making a task is one function, {{copy_process|https://github.com/torvalds/linux/blob/v6.12/kernel/fork.c#L2118}} in kernel/fork.c. It allocates a new task_struct and then, for each resource, either shares the parent's or copies it, decided by clone flags:

The kernel refuses inconsistent combinations: CLONE_THREAD without CLONE_SIGHAND, and CLONE_SIGHAND without CLONE_VM ({{fork.c lines 2145 and 2153|https://github.com/torvalds/linux/blob/v6.12/kernel/fork.c#L2145}}). The child also does not inherit: its parent's PID, pending signals, timers, record locks, memory locks (mlock), and resource counters, which copy_mm resets to zero (page-fault and context-switch counts, line 1701); the full list is in {{fork(2)|https://man7.org/linux/man-pages/man2/fork.2.html}}. And only the thread that called fork exists in the child.

vfork and posix_spawn: start a program without copying the parent


If the child is going to call exec straight away, copying the parent's page tables is wasted work. vfork (clone with CLONE_VM | CLONE_VFORK) lets the child borrow the parent's memory and suspends the parent until the child calls exec or _exit (the kernel waits in {{wait_for_vfork_done|https://github.com/torvalds/linux/blob/v6.12/kernel/fork.c#L1572}}). It is fast and dangerous: the child must not return from the function that called vfork or touch the parent's variables, because it is running on the parent's memory. posix_spawn wraps that danger in a safe API: glibc 2.36 implements it with CLONE_VM | CLONE_VFORK on a separate stack ({{spawni.c line 385|https://sourceware.org/git/?p=glibc.git;a=blob;f=sysdeps/unix/sysv/linux/spawni.c;hb=glibc-2.36#l385}}), and lets you list the descriptor and signal changes to apply in the child.

The pattern is the point: anything built on fork scales with the parent's memory; vfork and posix_spawn do not. A trainer with tens of gigabytes resident that shells out (os.system, a fork-based multiprocessing child, a monitoring script started with fork) pays milliseconds to tens of milliseconds per child, and the copy-on-write faults afterwards on top. Three things come out of this table. First, os.fork() from a process that imported torch costs about 6 ms even with no big arrays, and subprocess.run stays under 1 ms because of vfork. Second, adding 1 GiB of NumPy did not slow fork down at all, because NumPy asked the kernel for transparent huge pages on that array (AnonHugePages 1,022 MiB): one page-table entry covers 2 MiB instead of 4 KiB, so there are 512 times fewer entries to copy. With NUMPY_MADVISE_HUGEPAGE=0 (NumPy's switch, {{numpy docs|https://numpy.org/doc/stable/reference/global_state.html}}) the same fork took 22.5 ms. This VM's THP setting is madvise, so only memory that asks for huge pages gets them; PyTorch's CPU tensors use a different allocator (the {{allocators page|n:3f05c17b0d0d81209ae9d856695dc958}}). Third, the start methods: a spawn or forkserver child is a fresh interpreter that imports torch again, about 0.65 to 0.94 s here, matching the root's 0.836 s and 0.763 s to the first batch.


Fork in a multi-threaded process


Only the calling thread survives fork, but all of memory is copied, including every lock. If another thread held a lock at that instant (the allocator's, a logging handler's, an OpenMP runtime's), the child has a lock that no thread will ever release, and the first time the child needs it, it hangs forever. POSIX says that after fork in a multi-threaded process the child may only call async-signal-safe functions until it calls exec ({{fork(2), NOTES|https://man7.org/linux/man-pages/man2/fork.2.html}}). pthread_atfork handlers let libraries reset their locks around fork, and CPython does this for its own locks, but not every library does. Python 3.12 started warning: "if Python is able to detect that your process has multiple threads, os.fork() now raises a DeprecationWarning" ({{os.fork docs|https://docs.python.org/3/library/os.html#os.fork}}), and Python 3.14 moved the Linux default start method to forkserver for this reason. The root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} reproduces the hang ("A worker hangs forever: fork while another thread holds a lock"), and the root covers fork after CUDA.
