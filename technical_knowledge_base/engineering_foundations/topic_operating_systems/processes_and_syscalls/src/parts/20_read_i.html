Process groups and sessions: who gets signalled together

Every process belongs to a process group (identified by a PGID, the PID of its first member) and every group to a session (SID). A child inherits both. They exist for job control: a shell puts each pipeline in its own group, and the terminal sends Ctrl-C's SIGINT to every process in the foreground group at once. kill(-pgid, sig) (Python os.killpg) does the same from code. setsid() starts a new session and group, detached from any terminal: what daemons do, and what start_new_session=True does in subprocess ({{credentials(7)|https://man7.org/linux/man-pages/man7/credentials.7.html}} describes both).

Two consequences for training:

  • Ctrl-C reaches the workers too. In a terminal, the trainer and its DataLoader workers are one foreground group, so all of them get SIGINT. The workers catch the resulting KeyboardInterrupt and exit quietly ("Main process will raise KeyboardInterrupt anyways", torch 2.14 _utils/worker.py line 396), and the main process unwinds.
  • torchrun signals groups, not processes. torchrun starts each trainer with start_new_session=True (subprocess_handler.py), so each trainer leads its own session and group, and its DataLoader workers join that group. To stop a trainer it calls os.killpg(trainer_pid, SIGTERM). In the Shutdown lab's process tree under torchrun, PGID and SID of the trainer and its two workers are all the trainer's PID; the SIGTERM therefore reaches the workers directly, which section 9 shows has a cost.

Resource limits

Each process carries soft and hard resource limits: the soft one is enforced, and a process may raise it up to the hard one (only a privileged process can raise the hard one). They are inherited across fork and exec, which is why ulimit -n 65536 in a launcher script applies to everything it starts. The job's limits, from the snapshot:

Identity: user ids and capabilities


A process has a real user id (who started it), an effective user id (whose permissions it uses), a saved id (so a privileged program can drop and regain privilege), and group ids likewise; the Uid: line in status lists real, effective, saved and file-system ids, all 0 for the job. Root inside a container is not all of root: the effective capability set CapEff 00000000a80425fb is Docker's reduced default set, and Seccomp: 2 shows a filter on system calls. Capabilities, user namespaces and seccomp are the {{containers child page|n:3f05c17b0d0d8156a841e4bf28f11293}}. One flag belongs here because it is inherited like a limit: prctl(PR_SET_NO_NEW_PRIVS) makes sure no exec'd program can gain privileges (no set-user-ID), and once set it cannot be cleared; sandboxes for untrusted code rely on it.
