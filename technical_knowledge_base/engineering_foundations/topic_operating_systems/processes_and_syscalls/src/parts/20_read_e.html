4. exec: replacing the program, keeping the process

ch. 5 Interlude: Process API

The problem. fork gives you a second copy of the same program. To run a different one, the process must throw away its code and memory and load a new program, while staying the same process: same PID, same parent, same place in the tree. That is execve(path, argv, envp), the one system call behind execl, execvp, os.execv and every shell command. On success it never returns, because the code that called it no longer exists.

What the kernel does

  1. {{do_execveat_common|https://github.com/torvalds/linux/blob/v6.12/fs/exec.c#L1876}} opens the file and builds a linux_binprm, the description of the program to load; {{bprm_execve|https://github.com/torvalds/linux/blob/v6.12/fs/exec.c#L1821}} checks permissions and asks each binary format handler whether it recognises the first bytes.
  2. An ELF executable (the format of compiled programs on Linux) is mapped by binfmt_elf; a file starting with #! is a script, handled by binfmt_script, which restarts exec with the interpreter named on that line and the script as an argument. That is how ./train.py with #!/usr/bin/env python3 runs.
  3. {{begin_new_exec|https://github.com/torvalds/linux/blob/v6.12/fs/exec.c#L1222}} is the point of no return. It drops the old address space and installs a new one, kills other threads of the process, closes every descriptor marked close-on-exec ({{do_close_on_exec, line 1318|https://github.com/torvalds/linux/blob/v6.12/fs/exec.c#L1318}}), and resets every caught signal to its default action ({{flush_signal_handlers, line 1355|https://github.com/torvalds/linux/blob/v6.12/fs/exec.c#L1355}}): the handler functions lived in the memory that was just discarded.
  4. For a dynamically linked program, the kernel maps the program and its dynamic loader (ld-linux-aarch64.so.1 here) and jumps to the loader, which maps libc and every shared library and then calls the program's entry point. The root's {{Syscall tracer|n:3f05c17b0d0d81c5a97ce991644af140}} tab shows this storm of openat and mmap calls for import torch.

Two rows cause real bugs. Ignored stays ignored: a launcher that ignores SIGTERM or SIGINT (or a non-interactive shell that starts a job in the background, which by POSIX sets SIGINT and SIGQUIT to ignored, visible in the job's SigIgn decoded in section 6) passes that on to everything it execs, and a program that never installs its own handler cannot be stopped with that signal. Blocked stays blocked: a signal blocked by a parent is still blocked in the new program, and a pending one waits. Python's subprocess undoes only its own part: with the default restore_signals=True it resets the signals CPython itself ignores ("Currently this includes the SIGPIPE, SIGXFZ and SIGXFSZ signals", {{subprocess docs|https://docs.python.org/3/library/subprocess.html#subprocess.Popen}}); anything else a launcher ignored or blocked reaches the child unchanged.


The first version of this experiment exec'd /bin/sh to print its state and saw an empty mask and two caught signals: Debian's dash clears the mask and installs its own handlers when it starts. Measuring what a mechanism does through a program that changes the thing you measure is a classic trap; the version above uses a program that changes nothing.


Why fork and exec are separate
Splitting "make a process" from "run a program" means the child can set itself up with ordinary calls in between: dup2 a log file onto fd 1, chdir, setsid, drop privileges, set rlimits, close descriptors. No special API needed. OSTEP's chapter 5 makes this argument, and it is why a shell can implement python train.py > log 2>&1 & in a few lines. The cost is the fork itself (section 3), which is why posix_spawn takes those set-up steps as a list of "file actions" instead.
