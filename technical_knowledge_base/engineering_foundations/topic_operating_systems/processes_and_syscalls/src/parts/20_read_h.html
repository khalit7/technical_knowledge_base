7. File descriptors: three tables, pipes and sockets

ch. 39 Files and Directories (open file table, fork and dup)

The problem. A process uses files, pipes, sockets, terminals and devices, and the kernel must not hand it raw pointers to any of them. So it hands out small integers, file descriptors, that index a table the kernel keeps for that process. "Everything is a file" in Unix really means "everything is reached through a descriptor": the same read, write, close and poll work on all of them.

Three tables, not one

1. Per process: the fd table{{struct files_struct|https://github.com/torvalds/linux/blob/v6.12/include/linux/fdtable.h#L38}} holds an array of pointers indexed by fd number, plus a close-on-exec bit per fd. The first 64 slots are built in (NR_OPEN_DEFAULT is the word size, line 24); it grows as needed.
2. System-wide: open file descriptionsOne {{struct file|https://github.com/torvalds/linux/blob/v6.12/include/linux/fs.h#L1032}} per open() call: a reference count (f_count, line 1033), the flags you opened with (f_flags, 1040) and the current offset (f_pos, 1051).
3. The objectThe inode of a file on disk, a pipe's buffer, a socket, a terminal: what the description reads from and writes to.

Everything that confuses people about descriptors follows from where each piece of state lives. open() creates a new description and gives it the lowest free fd number; that rule is what makes close(1); open("log") redirect stdout, and it is why fd numbers in the listings below are reused. dup(fd) and dup2(old, new) create a second fd pointing to the same description. fork copies table 1 (dup_fd, section 3), so parent and child point to the same descriptions too, and share the offset. Case 2 is two descriptions with two offsets: each process writes from offset 0 and they overwrite each other, leaving "NT" from a "PARENT" line at the end.

Read them together. fds 4 to 8 are identical in both: the same pipes (inodes 1066456 and 1066457), because the worker got them by fork. fd 5 is the memory-mapped dataset, inherited too. The worker's fd 9 is /dev/null: multiprocessing points a child's stdin there. The interesting ones are the /dev/shm/torch_* files. A worker puts each batch in shared memory: it creates a file in /dev/shm, maps it, deletes its name at once (the listing of /dev/shm below is empty: the files exist only through open descriptors and mappings), and sends the descriptor to the main process over a Unix domain socket (multiprocessing's resource sharer listens on one in the sending process; the worker's fd 15 is a socket). The main process's fds 14 and 15 are files whose names say torch_29_...: they were created by the worker with PID 29 and arrived through that socket. Two descriptors in the main process were closed while ls was reading the table; the listing shows the moment, not a stable state.




Passing a descriptor between processes uses sendmsg with an SCM_RIGHTS control message on a Unix socket: the kernel installs a new fd in the receiver pointing to the same description ({{unix(7)|https://man7.org/linux/man-pages/man7/unix.7.html}}). PyTorch calls this the file_descriptor sharing strategy, the default on Linux, and it warns that it keeps one descriptor open per shared tensor, so code that keeps many batches alive can hit the open-file limit; the alternative file_system strategy names files instead and can leak them if a process dies ({{torch.multiprocessing, sharing strategies|https://docs.pytorch.org/docs/stable/multiprocessing.html#sharing-strategies}}). The root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} reproduces "OSError: [Errno 24] Too many open files".


Pipes: a 64 KiB buffer, and EOF that needs every writer gone


A pipe is a kernel buffer with a read end and a write end, each a description. Measured on this kernel (src/runs/c/pipes.c):




A writer that fills the 65,536-byte buffer blocks (or gets EAGAIN if non-blocking) until the reader drains it; that is how a slow consumer slows the producer, the back-pressure every pipeline relies on. Writes of up to PIPE_BUF (4,096) bytes are atomic: they never interleave with another writer's ({{pipe(7)|https://man7.org/linux/man-pages/man7/pipe.7.html}}); bigger writes can. The default size comes from PIPE_DEF_BUFFERS = 16 pages ({{pipe_fs_i.h line 5|https://github.com/torvalds/linux/blob/v6.12/include/linux/pipe_fs_i.h#L5}}) and can be raised per pipe to pipe-max-size (1 MiB here) with F_SETPIPE_SZ. Writing to a pipe whose read ends are all closed raises SIGPIPE, or EPIPE where SIGPIPE is ignored, as in Python, where it becomes BrokenPipeError (python train.py | head).

Python made the fix the default: since 3.4 "newly created file descriptors are non-inheritable" ({{PEP 446|https://peps.python.org/pep-0446/}}), and subprocess closes everything except 0, 1 and 2 in the child (close_fds=True). C, C++ and Rust code, and libraries that call fork and exec themselves, still need O_CLOEXEC, pipe2(O_CLOEXEC), SOCK_CLOEXEC and accept4(SOCK_CLOEXEC). Rust's standard library sets close-on-exec on everything it opens.


Unix domain sockets


A Unix domain socket is a socket whose address is a path (or an abstract name) on the same machine: no network stack, no checksums, two-way, and it can carry descriptors and the sender's credentials. multiprocessing's forkserver talks to its server over one and passes the new worker's pipes through it; Docker's API is /var/run/docker.sock; NCCL and many inference servers use them for local control channels. Network sockets are the {{protocols topic|n:3c65c17b0d0d8117b21dcb9041879564}}.
