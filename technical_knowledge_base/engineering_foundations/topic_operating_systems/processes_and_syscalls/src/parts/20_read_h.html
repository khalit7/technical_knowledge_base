7. File descriptors: three tables, pipes and sockets

ch. 39 Files and Directories (open file table, fork and dup)

A process uses files, pipes, sockets, terminals and devices, and the kernel must not hand it raw pointers to any of them. So it hands out small integers, file descriptors, that index a table the kernel keeps for that process. "Everything is a file" in Unix really means "everything is reached through a descriptor": the same read, write, close and poll work on all of them.

Three tables, not one

The offset lives in the description, so fork and dup share it and a second open does not

1. Per process: the fd table, an array of pointers indexed by fd number plus a close-on-exec bit per fd. 2. System-wide: open file descriptions, one per open() call, holding a reference count, the open flags and the current offset. 3. The object: the inode of a file on disk, a pipe's buffer, a socket, a terminal. The figure is this page's model of the tables after a parent opened train.log as fd 3, forked, the child opened the same file again as fd 4, and the parent wrote 7 bytes: the child's fd 3 sees offset 7 too, its fd 4 is still at 0.

The three structures in the kernel source (v6.12) (reference)

The fd table is {{struct files_struct|https://github.com/torvalds/linux/blob/v6.12/include/linux/fdtable.h#L38}}; the first 64 slots are built in (NR_OPEN_DEFAULT is the word size, line 24) and it grows as needed. A description is {{struct file|https://github.com/torvalds/linux/blob/v6.12/include/linux/fs.h#L1032}}: the reference count f_count (line 1033), the flags you opened with f_flags (1040) and the offset f_pos (1051).

Everything that confuses people about descriptors follows from where each piece of state lives. open() creates a new description and gives it the lowest free fd number; that rule is what makes close(1); open("log") redirect stdout, and it is why fd numbers in the listings below are reused. dup(fd) and dup2(old, new) create a second fd pointing to the same description. fork copies table 1 (dup_fd, section 3), so parent and child point to the same descriptions too, and share the offset. Pipes: a 64 KiB buffer, and EOF that needs every writer gone


A pipe is a kernel buffer with a read end and a write end, each a description. A writer that fills the 65,536-byte buffer blocks (or gets EAGAIN if non-blocking) until the reader drains it; that is how a slow consumer slows the producer, the back-pressure every pipeline relies on. Writes of up to PIPE_BUF (4,096) bytes are atomic: they never interleave with another writer's ({{pipe(7)|https://man7.org/linux/man-pages/man7/pipe.7.html}}); bigger writes can. The default size comes from PIPE_DEF_BUFFERS = 16 pages ({{pipe_fs_i.h line 5|https://github.com/torvalds/linux/blob/v6.12/include/linux/pipe_fs_i.h#L5}}) and can be raised per pipe to pipe-max-size (1 MiB here) with F_SETPIPE_SZ. Writing to a pipe whose read ends are all closed raises SIGPIPE, or EPIPE where SIGPIPE is ignored, as in Python, where it becomes BrokenPipeError (python train.py | head).

The leak and the fix, timed (raw output of cloexec.c)


The leak, measured: the reader waited 2.0 s for EOF, until the forked process that inherited the write end exited; with pipe2(O_CLOEXEC) it saw EOF at once. Every process that inherited a write end and forgot to close it keeps the reader waiting.


Python made the fix the default: since 3.4 "newly created file descriptors are non-inheritable" ({{PEP 446|https://peps.python.org/pep-0446/}}), and subprocess closes everything except 0, 1 and 2 in the child (close_fds=True). C, C++ and Rust code, and libraries that call fork and exec themselves, still need O_CLOEXEC, pipe2(O_CLOEXEC), SOCK_CLOEXEC and accept4(SOCK_CLOEXEC). Rust's standard library sets close-on-exec on everything it opens.


Descriptors that travel: how batches reach the trainer


A DataLoader worker does not copy a batch to the main process. It creates a file in /dev/shm, maps it, deletes its name at once, and sends the descriptor over a Unix domain socket; the main process maps the same memory. The job's real tables below show the result: files named torch_29_... open in the main process, created by worker PID 29.


Passing a descriptor between processes uses sendmsg with an SCM_RIGHTS control message on a Unix socket: the kernel installs a new fd in the receiver pointing to the same description ({{unix(7)|https://man7.org/linux/man-pages/man7/unix.7.html}}). PyTorch calls this the file_descriptor sharing strategy, the default on Linux, and it warns that it keeps one descriptor open per shared tensor, so code that keeps many batches alive can hit the open-file limit; the alternative file_system strategy names files instead and can leak them if a process dies ({{torch.multiprocessing, sharing strategies|https://docs.pytorch.org/docs/stable/multiprocessing.html#sharing-strategies}}). The root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} reproduces "OSError: [Errno 24] Too many open files".

Unix domain sockets


A Unix domain socket is a socket whose address is a path (or an abstract name) on the same machine: no network stack, no checksums, two-way, and it can carry descriptors and the sender's credentials. multiprocessing's forkserver talks to its server over one and passes the new worker's pipes through it; Docker's API is /var/run/docker.sock; NCCL and many inference servers use them for local control channels. Network sockets are {{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}}.
