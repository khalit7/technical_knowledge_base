2. System calls: the one door into the kernel

ch. 6 Limited Direct Execution

The problem. Your program runs directly on the CPU at full speed, but in user mode, where the hardware refuses anything that could harm other programs: touching a device, changing the memory map, disabling interrupts. The kernel runs in kernel mode. A program that wants something privileged must ask, and the request has to be a controlled jump into kernel code at a place the kernel chose, never at an address the program picks. That jump is a system call. The root page's {{section 1|n:3f05c17b0d0d81c5a97ce991644af140}} introduced it; here is exactly how it works.

The contract: a number, six registers, one instruction

Every system call has a number. The program puts the number and up to six arguments in fixed registers and executes one trapping instruction; the kernel puts the result back in a register. That register convention is the system-call ABI (application binary interface), and it differs by CPU:

Four things to notice. (1) The single-threaded fast path: glibc checks __libc_single_threaded (gdb names the variable) and, if other threads exist, takes a second path that wraps the same svc in calls that make read a thread cancellation point ({{SYSCALL_CANCEL in sysdep.h line 118|https://sourceware.org/git/?p=glibc.git;a=blob;f=sysdeps/unix/sysdep.h;hb=glibc-2.36#l118}}; {{read.c line 26|https://sourceware.org/git/?p=glibc.git;a=blob;f=sysdeps/unix/sysv/linux/read.c;hb=glibc-2.36#l26}}). After import torch your process is multi-threaded, so it always takes the slower path. (2) mov x8, #63, then svc #0: the door. (3) cmn x0, #0x1, lsl #12 compares the result with -4096: the kernel reports failure by returning a negative error number between -4095 and -1, never by setting a variable. (4) On failure the wrapper negates it, stores it in errno (a per-thread variable, reached through the thread pointer register tpidr_el0) and returns -1. CPython then turns -1 plus errno into an exception: errno 9 (EBADF) becomes OSError: [Errno 9] Bad file descriptor, errno 2 becomes FileNotFoundError.

What a crossing costs




The root measured the ladder on this machine: a function call about 1.3 ns, clock_gettime about 24 ns because the vDSO serves it without entering the kernel ({{vdso(7)|https://man7.org/linux/man-pages/man7/vdso.7.html}}), the cheapest real call (getppid) about 281 ns, a 1-byte read about 316 ns. This page repeated getppid through glibc's generic syscall(): 269 ns per call, and Python's os.getppid() came out about the same (250 ns, best of 5 against a median of 5, so treat them as equal: the kernel crossing dominates and Python's call overhead is small beside it). Under strace the same loop took 124 µs per call, about 460 times slower.


Why strace is so slow, and what to use instead
strace uses {{ptrace(2)|https://man7.org/linux/man-pages/man2/ptrace.2.html}}: at every system call entry and exit the kernel stops your thread, wakes the strace process, which reads your registers (more system calls), prints, and resumes you. Tracing the tracer shows the bill: for each extra call traced, strace itself made 4 wait4, 4 ptrace and 2 write calls (the difference between tracing 5,000 and 10,000 getppid calls, src/runs/out/strace_meta.txt), plus two stops of your thread, each a round trip through the scheduler. Counts and order from strace are exact; durations are not (the root's job ran about 170 s under strace against about 2 s without). For timing use perf trace or perf stat -e 'syscalls:sys_enter_*' (kernel tracepoints, no stops), or strace --seccomp-bpf -e trace=..., which uses a seccomp filter so the tracee stops only on the calls you asked for.


Predict: a data loader makes 2 million small read calls per epoch and takes 10 s. You run it under strace -f to find out why. About how long will the epoch take?




At about 124 µs per traced call (measured here, against 269 ns untraced), 2,000,000 calls add about 2,000,000 × 124 µs ≈ 248 s. strace turns a syscall-heavy program into a different program; use it to see which calls happen, then measure without it.


Interrupted calls: EINTR and restarting


A call that blocks (a read from a pipe that is empty, a wait, a sleep) can be interrupted by a signal whose handler runs (section 6). The kernel then either restarts the call after the handler returns, if the handler was installed with SA_RESTART and the call is restartable, or fails it with EINTR ("interrupted system call") and leaves the retry to you ({{signal(7), "Interruption of system calls"|https://man7.org/linux/man-pages/man7/signal.7.html}}). C code that forgets this has a bug that only shows when a signal arrives, for example on preemption. Python retries for you since 3.5: "System call wrappers provided in the standard library should be retried automatically when they fail with EINTR", and "the system call is only retried if the signal handler does not raise an exception" ({{PEP 475|https://peps.python.org/pep-0475/}}); that is why the handler-latency experiment in section 6 sees time.sleep keep sleeping after its handler ran.
