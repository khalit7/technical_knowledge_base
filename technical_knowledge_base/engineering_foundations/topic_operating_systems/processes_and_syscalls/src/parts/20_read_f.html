5. wait, exit, zombies, orphans and PID 1

ch. 5 Interlude: Process API

When a process ends, someone usually needs to know how: did the worker finish, crash, or get killed? The kernel keeps the answer until the parent asks for it. Between "ended" and "asked" the process is a zombie; a process whose parent ends first is an orphan and needs a new parent. Containers make PID 1 your problem.

Why _exit in a child matters: after fork the child has a copy of everything the parent buffered but has not written yet. If both call exit, both flush, and the text is written twice. Measured with stdout going to a file (src/runs/c/fdshare.c):

Predict: printf("buffered line from pid %d ", getpid()); with no newline, then fork(); the child prints "(child)\n" and calls exit, the parent prints "(parent)\n" and returns. stdout is a file. How many times does "buffered line" appear in the file?
Twice, with the parent's PID both times: the text was in the parent's stdio buffer in user memory when fork copied it, and each process flushed its own copy at exit. On a terminal stdout is line-buffered and you might see it once, which is why this bug appears only when output is redirected to a log file. Python's multiprocessing ends every forked child with os._exit(code) ({{popen_fork.py line 73|https://github.com/python/cpython/blob/v3.11.2/Lib/multiprocessing/popen_fork.py#L73}}) for this reason; sys.stdout.flush() before forking is the habit to keep.


Exit status, and where 137 and 143 come from


wait4 (or waitpid, waitid) gives the parent a status word. WIFEXITED(s) and WEXITSTATUS(s) say it exited and with which number (0 to 255); WIFSIGNALED(s) and WTERMSIG(s) say a signal killed it ({{wait(2)|https://man7.org/linux/man-pages/man2/wait.2.html}}). Shells, Docker and Kubernetes fold the two into one number: an exit code below 128 is the program's own; 128 + n means "killed by signal n".

Zombies: ended, not yet collected


When a process exits, the kernel frees its memory and descriptors but keeps its task_struct, its PID and its exit status, and sends SIGCHLD to the parent. The entry stays until the parent waits ({{wait_task_zombie|https://github.com/torvalds/linux/blob/v6.12/kernel/exit.c#L1143}} releases it). Measured (src/runs/c/lifecycle.c): the exited child shows state Z with its parent's PID until waitpid returns its status (WEXITSTATUS 7), and then /proc/<pid> is gone; an orphaned grandchild's getppid() becomes 1, or the subreaper's PID when the parent marked itself one.


The zombie, before and after wait (raw output)


A zombie costs no CPU and almost no memory, but it holds a PID, and PIDs are limited: per container by the cgroup's pids.max, which counts threads too (the root's {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} case "BlockingIOError on fork: the pids limit counts threads too"). A parent that never waits, in a long run that starts many short-lived children, eventually cannot fork.


Orphans: who adopts a child whose parent died


When a process exits, {{forget_original_parent|https://github.com/torvalds/linux/blob/v6.12/kernel/exit.c#L692}} gives each of its children a new parent chosen by {{find_new_reaper|https://github.com/torvalds/linux/blob/v6.12/kernel/exit.c#L625}}: the nearest ancestor that marked itself a subreaper with prctl(PR_SET_CHILD_SUBREAPER), otherwise PID 1 of the PID namespace. The rules. Linux: an exiting process becomes a zombie (Z) until its parent waits; its direct children move to the nearest subreaper ancestor, or to PID 1; grandchildren stay where they are; a zombie whose parent is PID 1 stays until PID 1 waits, unless PID 1 reaps (tini does). fork.py default: every descendant of the exiting process moves directly under the root. fork.py -R: the exiting process's children move to its parent. fork.py -L: only leaves may exit. PID 1 is special, twice


Inside a container, the first process gets PID 1 of its PID namespace, and it inherits two duties it may not know about.


    

  • It must reap orphans. Every orphan in the container becomes its child. A Python training script as PID 1 waits only for children it started through subprocess or multiprocessing; orphans of crashed workers or of shell scripts it ran pile up as zombies (root {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} case "Zombies pile up when the training script is PID 1").
    • 

  • Signals with no handler do nothing to it. The kernel marks a namespace's init SIGNAL_UNKILLABLE, and {{sig_task_ignored|https://github.com/torvalds/linux/blob/v6.12/kernel/signal.c#L82}} drops any signal whose action is the default (lines 92 to 93). SIGTERM's default is "terminate", so a PID 1 with no SIGTERM handler simply ignores docker stop, and is SIGKILLed after the grace period: exit 137, no checkpoint. SIGKILL from outside the namespace still works (the comment at {{line 2838|https://github.com/torvalds/linux/blob/v6.12/kernel/signal.c#L2838}}). With a handler installed, as in the running job, PID 1 receives SIGTERM normally.
    • 



The usual fix is a tiny init as PID 1 that reaps and forwards signals: docker run --init (Docker ships {{tini|https://github.com/krallin/tini}}), or tini/dumb-init in the image; but tini forwards SIGTERM to its one child, so its child must be Python, not a shell (the shutdown runs of section 9 found the trap: tini exits with 143 and the kernel kills Python before it can checkpoint).


Knowing when your parent dies: PR_SET_PDEATHSIG, and how DataLoader workers notice (depth)

A child can ask to be signalled when its parent dies: prctl(PR_SET_PDEATHSIG, SIGTERM) ({{kernel/sys.c line 2470|https://github.com/torvalds/linux/blob/v6.12/kernel/sys.c#L2470}}; note that "parent" means the parent thread, so a child started from a short-lived thread gets the signal when that thread exits, {{PR_SET_PDEATHSIG(2const)|https://man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html}}). PyTorch's DataLoader workers do not use it; they poll instead: a ManagerWatchdog checks whether os.getppid() still returns the original parent, between waits of MP_STATUS_CHECK_INTERVAL = 5.0 seconds (torch 2.14 torch/utils/data/_utils/worker.py and _utils/__init__.py line 19). So after the trainer is SIGKILLed, its workers notice within about 5 s and exit (root {{Debug lab|n:3f05c17b0d0d81c5a97ce991644af140}} case "The main process is SIGKILLed: what happens to its workers").
