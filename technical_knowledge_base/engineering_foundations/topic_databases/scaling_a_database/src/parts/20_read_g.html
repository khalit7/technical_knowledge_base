8. Cross-shard work: lookups, joins, transactions, IDs

Some work will cross shards whatever key you pick. Each kind has a standard answer, and each was measured on the Citus cluster.

Lookups by another column: login by email

Login knows the email, not the user id, so it cannot be routed: Citus sends it to all 32 shards (each uses its local index). Measured over 250 logins: median ms sharded against ms on one node, about times slower, and every login now uses every shard. The fix is a lookup table that maps email to user id, itself sharded by email: one single-shard read to find the user, then one to fetch them. Vitess builds this in as a lookup vindex (Vitess docs). The cost: two writes per signup that must stay consistent.

Joins: co-location and reference tables

Two tables sharded on the same key with the same hash ranges are co-located: user 4242's chats and messages sit on the same server, so joining them on user_id runs inside each shard. That is why the chat product shards messages by user_id even though a message "belongs" to a chat: the shard key is copied into every table that should live with it (Figma calls such a group a "colo"). Small tables everyone joins against (the list of models and prices) become reference tables, copied to every server (Citus docs). A join that is neither is refused by default, measured on Citus with a chat_tags table sharded by chat_id:

SELECT t.tag, count(*) FROM chats c JOIN chat_tags t ON t.chat_id = c.id GROUP BY t.tag;
ERROR:  the query contains a join that requires repartitioning

With citus.enable_repartition_joins on, Citus reshuffles one side across the network to make the join possible: ms, against ms for the same join on one Postgres. Designing tables so joins are co-located is most of the work of sharding a schema.

Crossing shards, measured: the same work on one server and across the cluster

Each pair shares one scale; medians on the laptop cluster (measured), so the network is not included and real ratios are larger.

Transactions across shards

A transaction touching two shards needs every shard to commit or none. Citus uses two-phase commit (2PC: every server first promises it can commit, then all commit) for writes that span nodes (Citus README; how 2PC works and why it blocks is {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}}, section 11). Fig. 4 replays the measured test: 300 transactions, each UPDATE users SET plan = plan WHERE id = ... for one user, then for users 11 and 13, which live on different workers.

Fig. 4: one shard commits alone; two workers need a vote before anyone commits

  1. One user, one shard: an ordinary commit. User 11's row lives on one worker, so the coordinator forwards the update and the commit there; nothing else is involved. Median ms.
  2. Two users on two workers. The coordinator sends each update to the worker holding that user's shard. Each worker changes its row and holds a row lock, but neither has committed.
  3. Phase 1: PREPARE TRANSACTION. The coordinator asks both workers to prepare: each writes its changes and the prepared state to disk, keeps its locks, and answers yes. A prepared transaction survives a crash and can still go either way.
  4. The decision is recorded. With both yes votes in, a commit record is stored on the coordinator. From here the transaction counts as committed even if a server crashes: Citus's maintenance daemon compares the coordinator's commit records with the workers' pending prepared transactions, and a present record means commit, an absent one abort (Citus README, checked 6 Nov 2026).
  5. Phase 2: COMMIT PREPARED. Both workers commit and release their locks. Median ms and ms at p99, against ms for one shard and ms for the same two users on one Postgres: the extra round trips are the price of atomicity.
  6. Atomic, but not one snapshot. The two COMMIT PREPAREDs do not happen at the same instant: between them, a reader on worker 1 already sees user 11's change while worker 2 still shows user 13's old row. Citus's multi-node transactions are atomic but have "no distributed snapshot isolation".

Vitess's default mode across shards is "best effort", not atomic, with an opt-in TWOPC mode (Vitess docs). Keep transactions inside one shard by design; that is the shard key's other job.

Unique ids

Each shard's own sequence would hand out the same ids. Options: UUIDs (version 7 sorts by time), a central id service, or ids that embed the shard. Instagram's 64-bit ids are 41 bits of milliseconds, 13 bits of logical shard id and 10 bits of a per-shard sequence, so the shard is readable from the id ({{Case files: insta-2012|n:3c65c17b0d0d81048ae0dd14ac399b4d}}).

9. Resharding, and why the shard key is a one-way door

Adding a shard: how much data moves

Three shards are full; a fourth arrives. How many rows must move depends on how keys map to shards. Counted on the real users and their messages, from 3 shards to 4:

Predict: going from 3 to 4 shards, what share of the messages must move under hash(key) mod N? A quarter would be the minimum.

  • hash(key) mod N: changing N from 3 to 4 changes the remainder of about three keys in four, so % of messages move. Never route with a bare modulus over servers.
  • Consistent hashing (each shard owns arcs of a hash ring, 64 points each; explained and animated on {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}}): only the keys the new shard takes over move, %. But with 64 points per shard the four shards end up holding between % and % of the data, not 25% each.
  • Logical shards: hash keys into a fixed, large number of buckets (here 48) once, forever, and map buckets to servers in a small table. Adding a server moves whole buckets: 12 of 48, % of messages, and the result is even. This is what Instagram (thousands of logical shards), Notion (480) and Citus (32 shards per table by default) do; moving a bucket is copying one table or schema, which tools do well.

Adding a fourth shard: a bare modulus moves three quarters of the data, logical shards move the minimum

Measured: Citus adds a fourth worker with writes running

The real thing, on the Citus cluster: 32 shards per table on 3 workers, a fourth worker added, and citus_rebalance_start() run while a client inserted messages for random users throughout. It uses logical replication, so reads and writes continue during the copy.

Fig. 5: a fourth worker joins and a quarter of the shard groups move to it, with writes running

  1. Three workers, 32 shard groups. Before the move the workers hold 10, 11 and 11 shard groups. A shard group is the matching shard of every co-located table, so a user's chats and messages move together. Inserts keep arriving (purple).
  2. A fourth worker joins, empty. citus_add_node registers it; nothing moves by itself, and no query goes there yet.
  3. The rebalancer copies 8 groups. It takes 2 groups from the first worker and 3 from each of the others. Each is copied with logical replication: a snapshot of the shard, then a stream of the changes made meanwhile. Writes still go to the old placement.
  4. Catch up, then switch. Once the copy has caught up, Citus blocks writes to the group with metadata locks, waits for the last changes to replicate, and updates pg_dist_placement to point at worker 4; the old copy is dropped once ongoing reads finish (Citus README, checked 6 Nov 2026). Insert latency over the whole move: median 0.22 ms, p99 1.38 ms, worst 124 ms.
  5. Even again. 8 groups on every worker: 841 MB of the 3,311 MB of messages (25.4%) moved in 36.1 s, with 140,600 inserts during the move and 0 errors. Which groups moved is drawn for illustration; the counts and sizes are measured.

Two real errors the rebalance hit (depth)

Two real errors along the way are worth knowing. The first attempt refused to start: cannot use logical replication to transfer shards of the relation chat_tags since it doesn't have a REPLICA IDENTITY or PRIMARY KEY (every table you shard needs a primary key). The second stalled because the rebalancer keeps a disk safety margin on the target: not enough empty space on node if the shard is moved (the laptop's disk was 96% full), fixed by lowering citus.desired_percent_disk_available_after_move for this test.

Changing the shard key: the one-way door

Adding shards moves a quarter of the data. Changing the key moves almost all of it: re-sharding the chat data from user to chat on 3 shards puts % of messages on a different shard. Worse, every query was written for the old key: each single-shard query becomes a scatter and the other way round, unique keys and co-location change, and the ids may embed the old shard. That is a rewrite of the data layer under live traffic, done with double-writes, a backfill, verification and a cutover (Notion's 2021 migration took a backfill of about three days before a five-minute cutover: Notion). Hence the root's warning: choose the shard key from the queries, and treat it as permanent. Notion's own second move, from 32 to 96 machines in 2023, kept the key and the 480 logical shards and only moved them, which took them from 15 to 5 schemas per machine (Notion, 17 Jul 2023).
