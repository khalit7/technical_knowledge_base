11. Distributed SQL: a database that shards itself

The problem appears

Sections 6 to 10 left a lot of machinery to the team: the router, resharding, cross-shard transactions, failover of every shard. A family of databases does all of it inside the database and still speaks SQL with real transactions: Google Spanner (2012 paper), CockroachDB, YugabyteDB, TiDB, and Amazon Aurora DSQL.

The idea, in three parts

  1. Ranges. All rows, sorted by primary key, are cut into contiguous pieces: CockroachDB calls them ranges (split when they pass 512 MiB by default), TiDB regions (256 MiB since v8.4), YugabyteDB tablets, Spanner splits. The database splits and moves them by size and load, so resharding is automatic.
  2. Consensus per range. Each range is kept on three (or five) servers, which agree on every write with a consensus protocol, Raft in CockroachDB, TiDB and YugabyteDB, Paxos in Spanner (how Raft works, with a lab: {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}}, Raft lab tab). A write commits once a majority has it, so losing one of three copies loses nothing and the range keeps working.
  3. Distributed transactions. A transaction touching several ranges is committed atomically by the database, with serializable isolation by default in CockroachDB and Spanner (the root's {{Database atlas|n:3cd5c17b0d0d815d8841ec845f5f3324}} lists each system's isolation and Jepsen history).

Measured: CockroachDB, three nodes, then two, then one

CockroachDB v26.3.0, three nodes on this laptop, a table of 200,000 messages split into four ranges, each range replicated to all three nodes; one replica per range, the leaseholder, serves its reads and proposes its writes. A client kept inserting through node 1 while nodes were killed with kill -9 (no warning, like a power cut).

How to read it. With one node of three gone, every range still has two of its three copies, a majority, so writes simply continue. In this run every lease sat on node 1, the node the client was connected to, so killing node 3 caused no pause at all; had node 3 held leases, the ranges it led would have paused until their leases moved to a survivor. With two nodes gone no range has a majority: writes stop (each insert timed out after 3 s) rather than risk two divergent histories, which is the "consistency over availability" choice that the CAP section of Distributed systems fundamentals explains. Restarting node 2 restored a majority and writes resumed by themselves about 3 s later; nobody ran a failover.


The latency floor, and where it comes from


Every write waits for a majority of a range's replicas. Inside one data centre that is one fast round trip; across regions it is physics. Median round trips between AWS regions, measured by CloudPing (5 Oct 2026): us-east-1 (Virginia) to us-east-2 (Ohio) about 13 ms, to us-west-2 (Oregon) about 70 ms, to eu-west-1 (Ireland) about 68 ms, to ap-southeast-1 (Singapore) about 218 ms (cloudping.co).

Commit at least = round trip from the leaseholder to the nearest other replica (a majority of three is the leader plus one), plus the client's round trip to the leaseholder if it is far away. The intra-region figure is the one cited on Distributed systems fundamentals; the rest are CloudPing medians.


Spanner adds one more wait. Its clocks (TrueTime) report an interval of uncertainty, epsilon, "typically a sawtooth function of time, varying from about 1 to 7 ms"; to make commit order match real time, a commit waits out that uncertainty ("commit wait", about twice epsilon) before becoming visible, which overlaps with the Paxos round (Spanner paper, OSDI 2012).


Cheaper reads: follower reads


Reading from the leaseholder means crossing the ocean too. A follower read reads a nearby replica at a timestamp slightly in the past, so it never waits: SELECT ... AS OF SYSTEM TIME follower_read_timestamp(). Measured on this cluster, the timestamp was  s in the past, matching the follower-reads page's "at least 4.2 seconds" (docs; the function reference says 4.8 s without a licence key, which this unlicensed cluster did not show). It is a read replica's trade, made explicit per query.

What you give up
Latency: every write pays a consensus round trip: a median insert took  ms on this three-node loopback cluster against  ms on plain Postgres with macOS's default flush and  ms with a real SSD flush per commit, as CockroachDB does, and tens of milliseconds across regions. Compatibility: "Postgres-compatible" means the wire protocol and much of the SQL, not every extension, isolation level or planner behaviour. Hotspots still exist: a sequential key sends all inserts to the last range. Retries: serializable and optimistic systems abort conflicting transactions, so the application must retry. Cost and skills: more nodes per byte, a new system to learn, and for some, licence terms. Worth it when you need writes beyond one machine, or must survive a zone or region without a failover runbook, and you would otherwise build sections 6 to 10 yourself.







12. Multi-region: putting data near users, and where the law says


Users in Singapore pay about 218 ms per round trip to a database in Virginia. Three patterns, from simplest:




One primary, replicas everywhere
Reads are local, writes cross the world. OpenAI's "nearly 50 read replicas across multiple geographic regions" with one primary is this pattern. Simple; writes from far away are slow, and failover to another region risks the split brain GitHub hit in 2018 ({{Case files: gh-2018-10|n:3c65c17b0d0d81048ae0dd14ac399b4d}}).


Geo-partitioning (each row lives near its owner)
Rows carry a region, and each region's rows are stored and led there: a European user's messages commit in Europe. CockroachDB calls this a REGIONAL BY ROW table; with sharding you get it by making region part of the shard key (one cell or pod per region, as Shopify does per pod). It is also how data residency is done, keeping some users' data inside a jurisdiction, which some laws and many enterprise contracts require.


Global tables (read everywhere, write rarely)
Small, read-mostly data (the list of models, feature flags, prices) is copied to every region for local reads, and each write pays the cost of reaching all of them. CockroachDB: GLOBAL tables, "fast reads everywhere, slower writes" (table localities); sharded systems: reference tables.




Surviving a whole region failing needs replicas in at least three regions, and then every write waits for a second region: CockroachDB's REGION survival goal "adds at least one inter-region round trip to writes", while the default ZONE goal keeps writes inside a region (survival goals). Decide which failure you must survive, then pay for exactly that.
