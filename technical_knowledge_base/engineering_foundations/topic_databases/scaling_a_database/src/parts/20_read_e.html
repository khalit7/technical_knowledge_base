5. Functional splits: different tables on different databases

The single primary takes every write: messages, credits, billing events, audit logs, rate-limit counters. They have nothing to do with each other except that they share a machine, and the busiest one slows all the others.

A functional split (Figma calls it vertical partitioning) moves whole groups of tables to their own database server: messages to one, billing to another. Each group keeps full SQL and transactions inside itself, and each server now carries only its share of writes. For the chat product: users, chats and messages stay together (they are read together), billing moves out, rate-limit counters move to Redis. Splitting along service boundaries ("a database per service") is the same move, and the same test decides it: split a group of tables off when it has its own owner and its own load, and no frequent transaction or join crosses the line.

A functional split divides the writes between servers, and cuts every transaction that crossed the line

GitHub, 2019 to 2021

GitHub grouped its tables into "schema domains", added linters that fail the build when a query or transaction crosses a domain, then moved domains to their own MySQL clusters, 130 tables in one move. The main cluster had served 950,000 queries per second in 2019 (900,000 on replicas); after the splits the same tables served 1.2 million per second with half the load per host (GitHub, 27 Sep 2021).

Figma, 2020 to 2022

After scaling up, Figma moved groups of tables to separate databases, growing from 2 to 50 tables moved by October 2022, each move costing about 30 seconds of partial impact (about 2% of requests) (Figma, 4 Apr 2023). It bought them time; their largest tables still outgrew one machine.

What it costs

Every JOIN and every transaction that crossed the split is gone. In the chat product, "deduct a credit and save the reply" was one transaction (the root's section 3); with billing on another server it becomes two writes that can half-fail, so it needs the outbox pattern or a saga ({{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}). That is why GitHub built linters before moving anything: first stop new code from crossing the line, then move. Enough when no single group of tables is too big or too busy for one server. Not enough when one table (here, messages) is.

6. Sharding: split one table's rows across servers

The messages table alone writes more than the largest machine can absorb, or is larger than it can hold. No rung below splits a single table across machines.

Sharding (horizontal partitioning across servers) gives each server a slice of the rows. Each slice is a shard; the column that decides a row's shard is the shard key (Citus calls it the distribution column). Something must know which shard holds which key: the router, which can be application code, a proxy or the database itself. Each shard is a normal Postgres server, usually with its own replicas. The theory (range against hash, consistent hashing, hot keys) is on {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}} (section 10, "Partitioning: splitting the data"); this page does it for real on the chat data.

The rule that decides everything: a query that names the shard key goes to one shard; a query that does not must ask every shard and combine the answers (scatter-gather, or fan-out). Fig. 3 runs two of the chat product's queries against one big Postgres and against the same data sharded by user with Citus (3 workers, 32 shards), both measured on this laptop.

Predict: after sharding, does the single-user chat list get faster or slower? And the search across everyone?

Fig. 3: before and after sharding by user: the query with the key touches one shard, the one without it touches all 32

  1. One server: a user's chat list. SELECT id, title FROM chats WHERE user_id = 4242 ORDER BY created_at DESC LIMIT 20 goes to the one Postgres that holds everything; the index on chats(user_id) finds the user's chats in a few pages. Median over 250 random users, measured: 0.10 ms.
  2. One server: search everyone's messages. content LIKE '%c0ffee%' can use no index, so Postgres scans all 10,000,000 messages with 2 parallel workers plus the leader process (its default). 16 matches; median of 5 warm runs: 1,502 ms.
  3. The same data, sharded by user. Citus spreads each table over 32 shards on 3 workers (11, 11 and 10 shards, about 300,000 messages each; the box heights are the real counts), and the application now sends its SQL to the coordinator, which routes it.
  4. With the key: one shard, and slower. WHERE user_id = 4242 names the distribution column, so hash(4242) picks one shard on worker 1 (Citus plan: Task Count: 1). Median 0.46 ms against 0.10 ms: the extra hop through the coordinator. With a real network each hop adds a round trip, typically a few hundred microseconds inside one data centre.
  5. Without the key: all 32 shards. The search says nothing about user_id, so any shard might hold a match (Task Count: 32). Every shard scans its slice and returns its top 50; the coordinator merges them into the final 16. 375 ms against 1,502 ms, faster only because 32 scans ran on more of the laptop's 10 cores at once.
  6. The total work did not shrink, it was spread out. Keyed queries each occupy one shard, so many of them spread over the cluster; every scatter query occupies every shard. On a busy cluster, scatter queries are what stop a sharded system from scaling.
The common misunderstanding
Sharding does not make single queries faster. It makes the system able to hold more data and take more writes, by adding servers. Single-shard queries pay an extra hop; scatter queries pay every shard. A shard key is good when almost every frequent query is single-shard.
