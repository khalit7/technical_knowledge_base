2. The cheap rungs: fix the queries, buy a bigger box, pool, cache

The problem appears

The chat product's database CPU sits at 80% at the evening peak and the p99 latency of opening a chat has doubled in a month. The tempting conclusion is "Postgres does not scale". The professional's first move is to ask which queries use the machine, because the four rungs in this section are each about ten times cheaper than the ones after it and they keep working after you shard, so none of them is wasted.

Rung 1: fix the queries and the indexes

A handful of queries usually use most of the database. pg_stat_statements (a standard extension that sums time per query shape) lists them; EXPLAIN (ANALYZE, BUFFERS) shows why each is slow; an index, a rewritten query or a fixed statistic usually makes it ten to a thousand times cheaper. On this page's data, adding one index on created_at took the dashboard query from about 373 ms to about 23 ms (section 4). OpenAI found that "an extremely costly query that joined 12 tables" was behind several of its worst incidents, and moved such joins into the application (OpenAI, 22 Jan 2026).

Enough when the load is dominated by a few fixable queries. Not enough when every query is already cheap and there are simply too many of them. The method is {{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}}; the root's {{Query plans tab|n:3cd5c17b0d0d815d8841ec845f5f3324}} runs real plans on this data.

Rung 2: a bigger machine (vertical scaling)

Vertical scaling (scaling up) means moving the same database to a machine with more CPU, memory and faster disks. Nothing in the application changes; on a managed service it is a setting and a failover of seconds to minutes. It is the most underrated rung, because the largest machines are very large:

What it costs: price roughly doubles with each size step while the ceiling is fixed; a bigger box takes longer to back up, restore and fail over; and one machine is still one failure domain. Figma's first move was exactly this, from an r5.12xlarge to an r5.24xlarge, before it started splitting tables off (Figma, 4 Apr 2023). Enough when growth is steady and you are below about half of the largest box. Not enough when you are already near the top size, or a forecast says you will be within a year: start the next rung while you still have headroom, because the later rungs take months.

Rung 3: connection pooling

Each Postgres connection is a separate operating-system process, so thousands of application processes each holding a connection waste memory and slow everything down. A connection pooler such as PgBouncer sits in between and lends a few real connections to many clients. OpenAI reports average connection time dropping from 50 ms to 5 ms with PgBouncer (OpenAI, 2026). Pooling modes, the two ways transaction pooling bites, and timeouts are measured on {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} (section 8): link, not repeated here. Enough when the symptom is connection count. It does nothing for slow queries.

Rung 4: caching

A cache keeps the answer to a frequent read (the chat list, a user's profile) in memory, usually Redis, so the database is not asked again. It removes reads, often most of them, and adds the problem of stale data and of every cache entry expiring at once (a stampede, which OpenAI handles with "cache locking"). Strategy, invalidation and stampedes live on {{Caching|n:3cd5c17b0d0d817ebd6ccadd4750c23a}} and {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}}. Enough when the load is repeated reads of the same keys. Useless for writes and for reads that are all different.

Pro habit: OpenAI ran ChatGPT on "a single primary Azure PostgreSQL flexible server instance" with "nearly 50 read replicas", at load that "has grown by more than 10x" in a year, by staying on these rungs plus read replicas, rate limiting, and moving only new or write-heavy, shardable workloads to other systems (section 13). The lesson is not "never shard"; it is "do not shard what the cheap rungs can still carry".

3. Read replicas in practice

The problem appears

The queries are fixed, the box is big, but reads (opening chats, listing chats, search) are 90% of the traffic and still growing. Reads do not change data, so any exact copy of the database could answer them.

The idea

A read replica (a standby, a follower) is a second Postgres server that receives the primary's write-ahead log as it is written and replays it, so it holds the same data a moment later. Postgres calls a replica that answers queries a hot standby; its data is "eventually consistent with the primary" (PostgreSQL docs, Hot standby). How replication works, synchronous against asynchronous, and the anomalies of reading behind the primary (measured on a real Postgres replica: 1,993 of 2,000 immediate reads missed the write) are on {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}} (section "Replication: keeping copies"); setting one up, replication slots and failover are on {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} (sections 4 and 5). This section is what the application does with replicas.

Routing: who decides which server a query goes to

The database does not route for you. Three places can:

The application (most common)

Two connection pools, "primary" and "replica". Writes, and reads that must be current, use the primary; everything else uses a replica. Frameworks have it built in: Rails multiple databases (with automatic switching back to the primary after a write), Django database routers.

The driver

libpq (the C client library under most Postgres drivers) accepts several hosts and a role: target_session_attrs is one of any, read-write, read-only, primary, standby or prefer-standby, and since PostgreSQL 16 load_balance_hosts=random spreads connections across them (libpq docs). It picks a server per connection, not per query.

A proxy or the cloud

A managed reader endpoint (Aurora) or a proxy that sends queries to replicas (Pgpool-II, PgDog). Convenient, but a proxy that guesses "SELECT means read" will send a SELECT that must see the user's last write to a replica.

# the pattern every team ends up writing (Python, psycopg pools)
def db_for_read(user):
    # read-your-writes: this user wrote recently, so the replica may not have it yet
    if now() - user.last_write_at < STICKY_SECONDS: return primary_pool
    replica = pick(r for r in replicas if r.lag_seconds < MAX_LAG)   # skip lagging replicas
    return replica or primary_pool

Read-your-writes in the application

A user sends a message and the chat reloads from a replica that has not replayed it yet: the message seems lost. Two fixes are standard. Sticky primary: after a user writes, send that user's reads to the primary for a few seconds (simple; costs primary capacity). Wait for position: remember the log position of the user's last commit (pg_current_wal_insert_lsn()) and read from a replica only once pg_last_wal_replay_lsn() there has passed it (docs). PostgreSQL 19, in beta 4 since 24 September 2026, adds a WAIT FOR LSN command for the second pattern (release notes); version 18 has nothing built in. The measured cost of the wait (median 0.105 ms on loopback) is on Distributed systems fundamentals.

Lag: monitor it, and route around it

On the primary, pg_stat_replication shows write_lag, flush_lag and replay_lag per replica (docs); alert on replay lag, and have the router stop sending reads to a replica past a threshold. Lag is normally milliseconds (AWS says Aurora replica lag is "usually much less than 100 milliseconds"), but a write spike makes it minutes: OpenAI's PGConf.dev 2025 talk lists an incident with replica lag above 10 minutes after a write spike drove the primary past 90% CPU (slides). A replica also replays every write, in one process, so a primary that writes too fast for one replay process leaves every replica behind.

A correctness surprise: Jepsen's Long Fork on replicas (29 April 2025)

Jepsen tested Amazon RDS for PostgreSQL 17.4 Multi-AZ clusters and found that reads on replicas can violate snapshot isolation with a Long Fork: two transactions update two different rows; one reader sees the first update and not the second, another sees the second and not the first, so the two readers disagree about which happened first. The cause: the primary makes commits visible in one order (the order transactions release a lock on its list of running transactions), replicas in another (the order of the log) (Jepsen). AWS replied that it is not RDS-specific and reproduces on self-managed Postgres with replicas; the proposed fix (commit sequence numbers) had not shipped as of the PostgreSQL 19 beta notes (AWS, 2 May 2025). What to do: a read that combines several rows to make a decision (a balance check, an invariant across rows) belongs on the primary.

What replicas cost, and when they are enough

Each replica is a full copy (same storage, same instance price), replays all writes, and gives stale reads the application must reason about. RDS allows 15 replicas per primary, and cascading replicas (replicas of replicas) up to three levels deep with 5 per source below the first level (AWS docs). Enough when reads are the bottleneck and writes fit one primary, which is the situation of most products, OpenAI included. Never enough for writes: adding a replica adds write work, it never removes any.
