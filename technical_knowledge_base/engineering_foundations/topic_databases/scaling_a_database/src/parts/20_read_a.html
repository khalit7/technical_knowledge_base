Scaling a database in one screen

The chat product from {{Topic: databases|n:3cd5c17b0d0d815d8841ec845f5f3324}} keeps its users, chats and 10 million messages in one PostgreSQL server. One day that server is not enough. Scaling means making the database handle more (more data, more reads, more writes, more users far away) without getting slower or losing data. There is no single trick: professionals climb a ladder, one rung at a time, and stop at the first rung that solves the problem they measured, because every rung up costs more than the one below it.

Click a rung to see what it fixes, what it costs, and when it is enough. The colours mark the three kinds of step: still one machine, more copies, split the data.

The whole page in five sentences
  1. Find what actually runs out first (CPU, memory, disk input/output, connections, or the write rate) before choosing a fix; most "we need to shard" moments are a missing index or too many connections (sections 1 and 2).
  2. Read replicas multiply reads, never writes, and they are slightly behind, so the application must decide which reads may be stale (section 3).
  3. Partitioning splits one big table into pieces inside one server; it makes deleting old data nearly free and helps queries that name the partition key, and does nothing for the server's limits (section 4).
  4. Sharding splits the data across servers by a shard key: queries that name the key go to one shard, the rest ask every shard, and the key is nearly impossible to change later (sections 6 to 10).
  5. Distributed SQL databases do the sharding, replication and failover for you, at the price of a latency floor on every write and a different system to run (sections 11 and 12).

Everything on this page that says "measured" was run for real on one Apple M1 Pro laptop on 5 October 2026: PostgreSQL 16.2 (the pgserver wheel), Citus 14.2.0 built from source against it (a coordinator and three, then four, workers), and CockroachDB v26.3.0 (three nodes). The data is the root page's chat dataset, generated by the same script with the same seeds: 100,000 users, 1 million chats, 10 million messages. Every server on one machine means no real network between them: latencies here are lower bounds, and section 11 says how to add the network back. Scripts and raw outputs are in src/measure/ and src/inputs/.

1. What runs out first on one server

The problem appears

"The database is slow" is not a diagnosis. A database server is a machine with a few separate resources, and each one runs out in its own way, with its own fix. Picking a fix before knowing which resource ran out is the most expensive mistake in this whole subject: teams shard a database whose real problem was one query without an index.

The resources, and what exhausting each looks like

ResourceWhat uses itHow you noticeFirst fix
CPURunning queries: scanning rows, sorting, joining, computing aggregates.CPU near 100%; every query slower at the same time.Find the few queries using most of it (pg_stat_statements) and fix them (section 2).
Memory (the working set: the data that is read often)Postgres keeps recently used 8 KB pages in its own cache (shared_buffers) and the operating system caches more.Reads start going to disk: the cache hit ratio drops and the same query is suddenly much slower. Measured here: the dashboard query scanning all 10 million messages took 2,766 ms the first time (pages on disk) and about 373 ms once they were in memory.More memory (a bigger machine), or make the hot data smaller (indexes, partitions, archiving old rows).
Disk input/output (IOPS: reads and writes per second the disk allows)Reading pages not in memory; writing the log and the tables.High disk wait times; on a cloud volume, hitting the provisioned IOPS limit. Figma's highest-write tables were heading past the largest IOPS Amazon RDS supports ({{Case files: figma-2024|n:3c65c17b0d0d81048ae0dd14ac399b4d}}).Faster or provisioned storage, fewer writes (batching), or split the data.
ConnectionsEvery client connection is a separate Postgres process with its own memory."too many clients already" errors; memory pressure from thousands of idle connections.A connection pooler (section 2).
Write rateAll writes go to one server and one ordered log (the write-ahead log, WAL: every change is written there first so it survives a crash).Commits queue up; replicas fall behind because they replay the log in one process.Batch writes, move write-heavy data elsewhere (section 5); in the end, sharding (section 6).
Size and operationsThe table on disk.Backups and restores take hours, a schema change on a billion-row table is risky, vacuum (Postgres's cleanup of dead row versions) cannot keep up. Notion's engineers found that even "simple catalog-only migrations became unsafe and uncertain" on their monolith ({{Case files: notion-2021|n:3c65c17b0d0d81048ae0dd14ac399b4d}}).Partitioning (section 4), archiving, then sharding.

The root page measured how much one laptop does: about 2,133 small write transactions per second with each commit truly flushed to the SSD, and about 65,000 indexed reads per second ({{Database atlas|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab of the root, claim "pg_tps"). A large cloud server does several times that. Most products never outgrow one well-run Postgres server plus replicas; the ones that do usually outgrow it on writes or size, not reads.

Measure before you climb
Four numbers tell you where you are: CPU use, cache hit ratio (blks_hit / (blks_hit + blks_read) in pg_stat_database), disk IOPS against the volume's limit, and write-ahead log bytes per second (pg_stat_wal). Watch their trend, not one value: the useful question is "at this growth rate, which one hits its ceiling first, and when?". {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} (section 11, Monitoring) sets these up; {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}} turns them into a forecast.
