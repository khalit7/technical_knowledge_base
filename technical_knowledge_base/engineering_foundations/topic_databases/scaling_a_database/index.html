Scaling a database in one screen

The chat product from Topic: databases keeps its users, chats and 10 million messages in one PostgreSQL server. One day that server is not enough. Scaling means making the database handle more (more data, more reads, more writes, more users far away) without getting slower or losing data. There is no single trick: professionals climb a ladder, one rung at a time, and stop at the first rung that solves the problem they measured, because every rung up costs more than the one below it.

About 41 minutes to read (9,379 words), plus the animations and the Shard-key lab.

Click a rung to see what it fixes, what it costs, and when it is enough. The colours mark the three kinds of step: still one machine, more copies, split the data.

The whole page in five sentences
  1. Find what actually runs out first (CPU, memory, disk input/output, connections, or the write rate) before choosing a fix; most "we need to shard" moments are a missing index or too many connections (sections 1 and 2).
  2. Read replicas multiply reads, never writes, and they are slightly behind, so the application must decide which reads may be stale (section 3).
  3. Partitioning splits one big table into pieces inside one server; it makes deleting old data nearly free and helps queries that name the partition key, and does nothing for the server's limits (section 4).
  4. Sharding splits the data across servers by a shard key: queries that name the key go to one shard, the rest ask every shard, and the key is nearly impossible to change later (sections 6 to 10).
  5. Distributed SQL databases do the sharding, replication and failover for you, at the price of a latency floor on every write and a different system to run (sections 11 and 12).

Everything on this page that says "measured" was run for real on one Apple M1 Pro laptop on 5 October 2026: PostgreSQL 16.2 (the pgserver wheel), Citus 14.2.0 built from source against it (a coordinator and three, then four, workers), and CockroachDB v26.3.0 (three nodes). The data is the root page's chat dataset, generated by the same script with the same seeds: 100,000 users, 1 million chats, 10 million messages. Every server on one machine means no real network between them: latencies here are lower bounds, and section 11 says how to add the network back. Scripts and raw outputs are in src/measure/ and src/inputs/.

1. What runs out first on one server

The problem appears

"The database is slow" is not a diagnosis. A database server is a machine with a few separate resources, and each one runs out in its own way, with its own fix. Picking a fix before knowing which resource ran out is the most expensive mistake in this whole subject: teams shard a database whose real problem was one query without an index.

Measure before you climb
Four numbers tell you where you are: CPU use, cache hit ratio (blks_hit / (blks_hit + blks_read) in pg_stat_database), disk IOPS against the volume's limit, and write-ahead log bytes per second (pg_stat_wal). Watch their trend, not one value: the useful question is "at this growth rate, which one hits its ceiling first, and when?". Running Postgres in production (section 11, Monitoring) sets these up; Capacity planning and performance turns them into a forecast.

2. The cheap rungs: fix the queries, buy a bigger box, pool, cache

The problem appears

The chat product's database CPU sits at 80% at the evening peak and the p99 latency of opening a chat has doubled in a month. The tempting conclusion is "Postgres does not scale". The professional's first move is to ask which queries use the machine, because the four rungs in this section are each about ten times cheaper than the ones after it and they keep working after you shard, so none of them is wasted.

Rung 1: fix the queries and the indexes

A handful of queries usually use most of the database. pg_stat_statements (a standard extension that sums time per query shape) lists them; EXPLAIN (ANALYZE, BUFFERS) shows why each is slow; an index, a rewritten query or a fixed statistic usually makes it ten to a thousand times cheaper. On this page's data, adding one index on created_at took the dashboard query from about 373 ms to about 23 ms (section 4). OpenAI found that "an extremely costly query that joined 12 tables" was behind several of its worst incidents, and moved such joins into the application (OpenAI, 22 Jan 2026).

Enough when the load is dominated by a few fixable queries. Not enough when every query is already cheap and there are simply too many of them. The method is Query planning and performance; the root's Query plans tab runs real plans on this data.

Rung 2: a bigger machine (vertical scaling)

Vertical scaling (scaling up) means moving the same database to a machine with more CPU, memory and faster disks. Nothing in the application changes; on a managed service it is a setting and a failover of seconds to minutes. It is the most underrated rung, because the largest machines are very large:

What it costs: price roughly doubles with each size step while the ceiling is fixed; a bigger box takes longer to back up, restore and fail over; and one machine is still one failure domain. Figma's first move was exactly this, from an r5.12xlarge to an r5.24xlarge, before it started splitting tables off (Figma, 4 Apr 2023). Enough when growth is steady and you are below about half of the largest box. Not enough when you are already near the top size, or a forecast says you will be within a year: start the next rung while you still have headroom, because the later rungs take months.

Rung 3: connection pooling

Each Postgres connection is a separate operating-system process, so thousands of application processes each holding a connection waste memory and slow everything down. A connection pooler such as PgBouncer sits in between and lends a few real connections to many clients. OpenAI reports average connection time dropping from 50 ms to 5 ms with PgBouncer (OpenAI, 2026). Pooling modes, the two ways transaction pooling bites, and timeouts are measured on Running Postgres in production (section 8): link, not repeated here. Enough when the symptom is connection count. It does nothing for slow queries.

Rung 4: caching

A cache keeps the answer to a frequent read (the chat list, a user's profile) in memory, usually Redis, so the database is not asked again. It removes reads, often most of them, and adds the problem of stale data and of every cache entry expiring at once (a stampede, which OpenAI handles with "cache locking"). Strategy, invalidation and stampedes live on Caching and Capacity planning and performance. Enough when the load is repeated reads of the same keys. Useless for writes and for reads that are all different.

Pro habit: OpenAI ran ChatGPT on "a single primary Azure PostgreSQL flexible server instance" with "nearly 50 read replicas", at load that "has grown by more than 10x" in a year, by staying on these rungs plus read replicas, rate limiting, and moving only new or write-heavy, shardable workloads to other systems (section 13). The lesson is not "never shard"; it is "do not shard what the cheap rungs can still carry".

3. Read replicas in practice

The problem appears

The queries are fixed, the box is big, but reads (opening chats, listing chats, search) are 90% of the traffic and still growing. Reads do not change data, so any exact copy of the database could answer them.

The idea

A read replica (a standby, a follower) is a second Postgres server that receives the primary's write-ahead log as it is written and replays it, so it holds the same data a moment later. Postgres calls a replica that answers queries a hot standby; its data is "eventually consistent with the primary" (PostgreSQL docs, Hot standby). How replication works, synchronous against asynchronous, and the anomalies of reading behind the primary (measured on a real Postgres replica: 1,993 of 2,000 immediate reads missed the write) are on Distributed systems fundamentals (section "Replication: keeping copies"); setting one up, replication slots and failover are on Running Postgres in production (sections 4 and 5). This section is what the application does with replicas.

Routing: who decides which server a query goes to

The database does not route for you. Three places can:

The application (most common)

Two connection pools, "primary" and "replica". Writes, and reads that must be current, use the primary; everything else uses a replica. Frameworks have it built in: Rails multiple databases (with automatic switching back to the primary after a write), Django database routers.

The driver

libpq (the C client library under most Postgres drivers) accepts several hosts and a role: target_session_attrs is one of any, read-write, read-only, primary, standby or prefer-standby, and since PostgreSQL 16 load_balance_hosts=random spreads connections across them (libpq docs). It picks a server per connection, not per query.

A proxy or the cloud

A managed reader endpoint (Aurora) or a proxy that sends queries to replicas (Pgpool-II, PgDog). Convenient, but a proxy that guesses "SELECT means read" will send a SELECT that must see the user's last write to a replica.

# the pattern every team ends up writing (Python, psycopg pools)
def db_for_read(user):
    # read-your-writes: this user wrote recently, so the replica may not have it yet
    if now() - user.last_write_at < STICKY_SECONDS: return primary_pool
    replica = pick(r for r in replicas if r.lag_seconds < MAX_LAG)   # skip lagging replicas
    return replica or primary_pool

Read-your-writes in the application

A user sends a message and the chat reloads from a replica that has not replayed it yet: the message seems lost. Two fixes are standard. Sticky primary: after a user writes, send that user's reads to the primary for a few seconds (simple; costs primary capacity). Wait for position: remember the log position of the user's last commit (pg_current_wal_insert_lsn()) and read from a replica only once pg_last_wal_replay_lsn() there has passed it (docs). PostgreSQL 19, in beta 4 since 24 September 2026, adds a WAIT FOR LSN command for the second pattern (release notes); version 18 has nothing built in. The measured cost of the wait (median 0.105 ms on loopback) is on Distributed systems fundamentals.

Lag: monitor it, and route around it

On the primary, pg_stat_replication shows write_lag, flush_lag and replay_lag per replica (docs); alert on replay lag, and have the router stop sending reads to a replica past a threshold. Lag is normally milliseconds (AWS says Aurora replica lag is "usually much less than 100 milliseconds"), but a write spike makes it minutes: OpenAI's PGConf.dev 2025 talk lists an incident with replica lag above 10 minutes after a write spike drove the primary past 90% CPU (slides). A replica also replays every write, in one process, so a primary that writes too fast for one replay process leaves every replica behind.

A correctness surprise: Jepsen's Long Fork on replicas (29 April 2025)

Jepsen tested Amazon RDS for PostgreSQL 17.4 Multi-AZ clusters and found that reads on replicas can violate snapshot isolation with a Long Fork: two transactions update two different rows; one reader sees the first update and not the second, another sees the second and not the first, so the two readers disagree about which happened first. The cause: the primary makes commits visible in one order (the order transactions release a lock on its list of running transactions), replicas in another (the order of the log) (Jepsen). AWS replied that it is not RDS-specific and reproduces on self-managed Postgres with replicas; the proposed fix (commit sequence numbers) had not shipped as of the PostgreSQL 19 beta notes (AWS, 2 May 2025). What to do: a read that combines several rows to make a decision (a balance check, an invariant across rows) belongs on the primary.

What replicas cost, and when they are enough

Each replica is a full copy (same storage, same instance price), replays all writes, and gives stale reads the application must reason about. RDS allows 15 replicas per primary, and cascading replicas (replicas of replicas) up to three levels deep with 5 per source below the first level (AWS docs). Enough when reads are the bottleneck and writes fit one primary, which is the situation of most products, OpenAI included. Never enough for writes: adding a replica adds write work, it never removes any.

4. Partitioning inside one Postgres

The problem appears

The messages table is the chat product's biggest: 10 million rows here, billions in a real product, growing every second. The product keeps one year of messages, so every night a job deletes the oldest day, and that job now runs for minutes, writes gigabytes of log, and leaves dead rows behind for vacuum to clean. Dashboards that look only at last week still read pages of old data.

The idea

Partitioning splits one logical table into several physical tables, the partitions, each holding the rows whose partition key falls in its slice. Queries still name the parent table; Postgres sends each row to its partition and, when a query's WHERE clause names the partition key, skips the partitions that cannot contain matches. That skipping is partition pruning, done when planning and again when executing (PostgreSQL docs, Table partitioning). Everything stays on one server: partitioning is not sharding.

Postgres has had this built in ("declarative partitioning") since version 10 (range and list) and hash partitioning since 11 (release notes). Three ways to slice:

Range

Each partition holds a range of values, usually time: one partition per month. The natural choice for anything that grows with time and is deleted by age.

List

Each partition holds listed values: country IN ('DE','FR','NL'). Useful when the data has a few natural groups, for example to put EU users' rows on separate storage.

Hash

Rows are spread by a hash of the key into N partitions: MODULUS 8, REMAINDER 3. Evens out size when there is no natural range; pruning only helps queries with key equality.

-- the chat messages, one partition per month (what this page measured)
CREATE TABLE messages_month (LIKE messages INCLUDING DEFAULTS, PRIMARY KEY (id, created_at))
  PARTITION BY RANGE (created_at);
CREATE TABLE messages_m2025_09 PARTITION OF messages_month
  FOR VALUES FROM ('2025-09-01 00:00+00') TO ('2025-10-01 00:00+00');
-- ... one per month to 2026-08; an index created on the parent is created on every partition
CREATE INDEX ON messages_month (chat_id, created_at);

Note the primary key: (id, created_at), not (id). Each partition can only check uniqueness inside itself, so a unique key must include the partition key. Asking for PRIMARY KEY (id) fails, measured: ERROR: unique constraint on partitioned table must include all partitioning columns. If you need id unique on its own, generate it so it cannot collide (a sequence or an ID that embeds time).

Where partitioning really pays: deleting old data




Deleting September 2025 from the plain table means finding and marking 863,999 rows, writing 160 MB of log (which every replica must replay, and every backup must store), and leaving 864 thousand dead rows for vacuum. Dropping the September partition removes one file. This, more than speed, is why time-series and log-like tables are partitioned. Archiving works the same way: detach a partition (DETACH PARTITION ... CONCURRENTLY, since PostgreSQL 14, takes only a weak lock on the parent), copy it to cheap storage, drop it.

What partitioning does not solve
It does not add CPU, memory, disk or connections: all partitions live on the same server, so a server that is out of any of them stays out. It makes queries that do not name the key slightly slower, constrains unique keys, and adds jobs to run. Partitionwise join and aggregate (planning joins partition by partition) exist but are off by default because they raise planning cost (enable_partitionwise_join, docs). Enough when the pain is a huge, time-ordered table: retention, vacuum, index size, archiving. Not the answer when the server itself is full.






5. Functional splits: different tables on different databases


The problem appears


The single primary takes every write: messages, credits, billing events, audit logs, rate-limit counters. They have nothing to do with each other except that they share a machine, and the busiest one slows all the others.


The idea


A functional split (Figma calls it vertical partitioning) moves whole groups of tables to their own database server: messages to one, billing to another. Each group keeps full SQL and transactions inside itself, and each server now carries only its share of writes. For the chat product: users, chats and messages stay together (they are read together), billing moves out, rate-limit counters move to Redis.




GitHub, 2019 to 2021
GitHub grouped its tables into "schema domains", added linters that fail the build when a query or transaction crosses a domain, then moved domains to their own MySQL clusters, 130 tables in one move. The main cluster had served 950,000 queries per second in 2019 (900,000 on replicas); after the splits the same tables served 1.2 million per second with half the load per host (GitHub, 27 Sep 2021).


Figma, 2020 to 2022
After scaling up, Figma moved groups of tables to separate databases, growing from 2 to 50 tables moved by October 2022, each move costing about 30 seconds of partial impact (about 2% of requests) (Figma, 4 Apr 2023). It bought them time; their largest tables still outgrew one machine.




What it costs
Every JOIN and every transaction that crossed the split is gone. In the chat product, "deduct a credit and save the reply" was one transaction (the root's section 3); with billing on another server it becomes two writes that can half-fail, so it needs the outbox pattern or a saga (Queues, streams and async work). That is why GitHub built linters before moving anything: first stop new code from crossing the line, then move. Enough when no single group of tables is too big or too busy for one server. Not enough when one table (here, messages) is.







6. Sharding: split one table's rows across servers


The problem appears


The messages table alone writes more than the largest machine can absorb, or is larger than it can hold. No rung below splits a single table across machines.


The idea


Sharding (horizontal partitioning across servers) gives each server a slice of the rows. Each slice is a shard; the column that decides a row's shard is the shard key (Citus calls it the distribution column). Something must know which shard holds which key: the router, which can be application code, a proxy or the database itself. Each shard is a normal Postgres server, usually with its own replicas. The theory (range against hash, consistent hashing, hot keys) is on Distributed systems fundamentals (section "Partitioning: splitting the data"); this page does it for real on the chat data.


The rule that decides everything: a query that names the shard key goes to one shard; a query that does not must ask every shard and combine the answers (scatter-gather, or fan-out). The animation runs two of the chat product's queries against one big Postgres and against the same data sharded by user with Citus (3 workers, 32 shards), both measured on this laptop.


















How to read it. The chat list names user_id, the shard key: the router sends it to the one shard that holds user 4242 (Task Count: 1 in Citus's plan). It got slower, about 0.46 ms against 0.10 ms at the median, because it now crosses an extra hop (the coordinator) before reaching Postgres; with a real network each hop adds a round trip, typically a few hundred microseconds inside one data centre. The mention search names no shard key, so it goes to all 32 shards (Task Count: 32), each scans its slice, and the coordinator merges the top 50. Here it got faster, about 375 ms against 1,502 ms, because 32 shard scans ran on more of the laptop's 10 cores at once than one Postgres query uses (2 parallel workers by default): the total work did not shrink, it was spread out. On a busy cluster every scatter query occupies every shard, so scatter queries are what stop a sharded system from scaling.


The common misunderstanding
Sharding does not make single queries faster. It makes the system able to hold more data and take more writes, by adding servers. Single-shard queries pay an extra hop; scatter queries pay every shard. A shard key is good when almost every frequent query is single-shard.






7. Choosing the shard key for the chat product


The method


List the frequent queries and writes, with their rates. For each candidate key, ask two questions: which of them become single-shard, and does the load spread evenly, both in stored data and in today's writes. Then check the biggest single key: no shard can be smaller than the busiest key it holds. The candidates for the chat product, counted on the real 10 million messages (8 shards):




Shard keySingle-shardMust scatterBiggest shard, storedBiggest shard, last week's writes




Counted from the data (src/measure/labdata.py): "stored" is the share of all 10M messages on the fullest of 8 shards (even would be 12.5%); "last week" is the share of the 208,001 messages written in the data's final 7 days. Hash shards use the page's hash function; range by user splits user ids 1 to 100,000 into 8 equal ranges; time puts consecutive months on consecutive shards; country hashes each country code to a shard.




By user (hash): the usual answer
Everything a user does (open a chat, list chats, send a message, delete my account) names the user, so it is single-shard, and the user's chats and messages live together, so joins between them stay on one server. Load is even: the busiest user here has 7,586 messages, 0.076% of the total. Scatters: anything across users (admin search, global dashboards) and login by email, which does not know the user id yet (section 8).


By chat (hash)
Even too, and "open a chat" is single-shard, but a user's chat list touches every shard holding one of their chats, and deleting a user scatters. Better only if chats are shared between many users (Discord partitions messages by channel for this reason: Discord, 2017).


By tenant (workspace, team, shop)
For a business product the tenant is the natural key: Notion shards by workspace, Slack sharded by workspace before Vitess, Shopify by shop (section 13). Everything inside a tenant stays together, and one tenant can be moved or isolated. The risk is the giant tenant: one customer bigger than a shard. The chat product's consumers are each their own tenant, which is why "by user" wins here; the closest coarse key in this data is country, and the US alone is 22% of all messages.


By time, or by a range of ids: the trap
Range by user id puts the oldest, most active users on shard 1 (27% of messages on 8 shards). Range by time puts every new write on the newest shard: 100% of last week's writes on one server while seven sit idle. Spanner warns about exactly this: monotonically increasing keys create a write hotspot (Spanner docs).




The Shard-key lab tab lets you choose a key and a shard count and see the per-shard load, the hot-shard risk and which of nine access patterns become single-shard or scatter.


Hot shards and hot keys


A hot shard gets far more than its share of load. Two causes: a bad key (range or time, above), fixed by a better key; and a hot key, one key so busy that even alone it overloads its shard (a celebrity, a giant tenant, one viral channel). Hashing cannot split a single key. Fixes, from cheapest: cache its reads; coalesce identical concurrent requests (Discord: Case files: discord-2023); give the giant tenant its own shard; or split the key with a suffix (tenant:42#0 to #7) and pay a small scatter for its reads.







8. Cross-shard work: lookups, joins, transactions, IDs


Some work will cross shards whatever key you pick. Each kind has a standard answer, and each was measured on the Citus cluster.


Lookups by another column: login by email


Login knows the email, not the user id, so it cannot be routed: Citus sends it to all 32 shards (each uses its local index). Measured over 250 logins: median  ms sharded against  ms on one node, about  times slower, and every login now uses every shard. The fix is a lookup table that maps email to user id, itself sharded by email: one single-shard read to find the user, then one to fetch them. Vitess builds this in as a lookup vindex (Vitess docs). The cost: two writes per signup that must stay consistent.


Joins: co-location and reference tables


Two tables sharded on the same key with the same hash ranges are co-located: user 4242's chats and messages sit on the same server, so joining them on user_id runs inside each shard. That is why the chat product shards messages by user_id even though a message "belongs" to a chat: the shard key is copied into every table that should live with it (Figma calls such a group a "colo"). Small tables everyone joins against (the list of models and prices) become reference tables, copied to every server (Citus docs). A join that is neither is refused by default, measured on Citus with a chat_tags table sharded by chat_id:


SELECT t.tag, count(*) FROM chats c JOIN chat_tags t ON t.chat_id = c.id GROUP BY t.tag;
ERROR:  the query contains a join that requires repartitioning


With citus.enable_repartition_joins on, Citus reshuffles one side across the network to make the join possible:  ms, against  ms for the same join on one Postgres. Designing tables so joins are co-located is most of the work of sharding a schema.


Transactions across shards


A transaction touching two shards needs every shard to commit or none. Citus uses two-phase commit (2PC: every server first promises it can commit, then all commit) for writes that span nodes (Citus README). Measured, 300 transactions updating users: one user  ms median; two users on different workers  ms median and  ms at p99. Two caveats pros know: Citus's multi-node transactions are atomic but have "no distributed snapshot isolation" (a reader can see one node's half before the other's), and Vitess's default mode across shards is "best effort", not atomic, with an opt-in TWOPC mode (Vitess docs). Keep transactions inside one shard by design; that is the shard key's other job.


Unique ids


Each shard's own sequence would hand out the same ids. Options: UUIDs (version 7 sorts by time), a central id service, or ids that embed the shard. Instagram's 64-bit ids are 41 bits of milliseconds, 13 bits of logical shard id and 10 bits of a per-shard sequence, so the shard is readable from the id (Case files: insta-2012).






9. Resharding, and why the shard key is a one-way door


Adding a shard: how much data moves


Three shards are full; a fourth arrives. How many rows must move depends on how keys map to shards. Counted on the real users and their messages, from 3 shards to 4:




    

  • hash(key) mod N: changing N from 3 to 4 changes the remainder of about three keys in four, so % of messages move. Never route with a bare modulus over servers.
    • 

  • Consistent hashing (each shard owns arcs of a hash ring, 64 points each; explained and animated on Distributed systems fundamentals): only the keys the new shard takes over move, %. But with 64 points per shard the four shards end up holding between % and % of the data, not 25% each.
    • 

  • Logical shards: hash keys into a fixed, large number of buckets (here 48) once, forever, and map buckets to servers in a small table. Adding a server moves whole buckets: 12 of 48, % of messages, and the result is even. This is what Instagram (thousands of logical shards), Notion (480) and Citus (32 shards per table by default) do; moving a bucket is copying one table or schema, which tools do well.
    • 



Measured: Citus adds a fourth worker with writes running


The Citus cluster's 32 shards per table sat on 3 workers (11, 11, 10). A fourth worker was added and citus_rebalance_start() moved shard groups to it (a shard group is the matching shard of every co-located table, so a user's chats and messages move together), using logical replication so reads and writes continue during the copy. A client inserted messages for random users throughout.






Two real errors along the way are worth knowing. The first attempt refused to start: cannot use logical replication to transfer shards of the relation chat_tags since it doesn't have a REPLICA IDENTITY or PRIMARY KEY (every table you shard needs a primary key). The second stalled because the rebalancer keeps a disk safety margin on the target: not enough empty space on node if the shard is moved (the laptop's disk was 96% full), fixed by lowering citus.desired_percent_disk_available_after_move for this test.


Changing the shard key: the one-way door


Adding shards moves a quarter of the data. Changing the key moves almost all of it: re-sharding the chat data from user to chat on 3 shards puts % of messages on a different shard. Worse, every query was written for the old key: each single-shard query becomes a scatter and the other way round, unique keys and co-location change, and the ids may embed the old shard. That is a rewrite of the data layer under live traffic, done with double-writes, a backfill, verification and a cutover (Notion's 2021 migration took a backfill of about three days before a five-minute cutover: Notion). Hence the root's warning: choose the shard key from the queries, and treat it as permanent. Notion's own second move, from 32 to 96 machines in 2023, kept the key and the 480 logical shards and only moved them, which took them from 15 to 5 schemas per machine (Notion, 17 Jul 2023).







10. Sharding Postgres in practice: by hand, Citus, or a proxy


Postgres has no built-in sharding. Teams get it in one of four ways, and the choice decides how much of sections 6 to 9 you write yourself.




In the application
The application computes the shard from the key and holds one connection pool per shard. Notion (480 logical shards, workspace id), Instagram (user id) and, with a SQL-parsing proxy of its own called DBProxy, Figma. Full control, and nothing new to operate; but you write the router, the scatter-gather, the resharding tooling and the cross-shard rules, and every engineer must know them.


def shard_for(user_id):
    bucket = h32(f"user:{user_id}") % 480   # logical shard, fixed forever
    return BUCKET_TO_HOST[bucket]          # small table, changes when moving


Citus (an extension inside Postgres)
Measured on this page. A coordinator plans queries over workers. create_distributed_table('messages', 'user_id', colocate_with => 'users') shards a table (32 shards by default), create_reference_table('models') copies one everywhere, and the rebalancer moves shards online. Real Postgres underneath, so extensions and SQL mostly work. AGPL v3 since 2022 (root's Database atlas); owned by Microsoft since 2019, offered on Azure as elastic clusters in Azure Database for PostgreSQL, while Azure Cosmos DB for PostgreSQL "is on a retirement path" (Microsoft Learn). Since Citus 12 it can also shard by schema, one schema per tenant.


Vitess (for MySQL)
Created at YouTube in 2010; Slack runs 99% of its MySQL traffic through it (root's Database atlas). A keyspace is a logical database split into shards named by hash ranges (-80, 80-); the VSchema says how each table is sharded; a vindex maps a column to a shard (a hash vindex, or a lookup vindex backed by a table); vtgate is the stateless proxy that routes queries; resharding is a workflow that copies, streams changes, verifies (VDiff) and switches traffic (Vitess docs v24). Cross-shard commits are not atomic unless you choose TWOPC.


The new Postgres proxies and services (2024 to 2026)
Several projects now bring Vitess's ideas to Postgres. PgDog: a pooler that parses queries, routes by shard key, merges cross-shard results and reshards with logical replication; says it is "used in production", some features experimental. Neki (PlanetScale; "not a fork of Vitess"): available, cross-shard transactions "coming soon". Multigres (Supabase, led by a Vitess co-creator): early development. Aurora PostgreSQL Limitless (generally available since 31 Oct 2024): routers plus hash-sharded, collocated and reference tables, managed by AWS. All read 5 Oct 2026; check status before betting on one.




How a pro chooses among them
If you are on Postgres and need sharding now, Citus (self-run or managed on Azure) is the most proven; if you are on AWS and want it managed, Limitless; if you need full control or your access pattern is simple and tenant-shaped, application-level logical shards, as Notion and Figma did. On MySQL, Vitess (or PlanetScale). Whatever you choose, the shard key, co-location and the ban on cross-shard transactions are your design work; no tool does them for you.






11. Distributed SQL: a database that shards itself


The problem appears


Sections 6 to 10 left a lot of machinery to the team: the router, resharding, cross-shard transactions, failover of every shard. A family of databases does all of it inside the database and still speaks SQL with real transactions: Google Spanner (2012 paper), CockroachDB, YugabyteDB, TiDB, and Amazon Aurora DSQL.


The idea, in three parts


    

  1. Ranges. All rows, sorted by primary key, are cut into contiguous pieces: CockroachDB calls them ranges (split when they pass 512 MiB by default), TiDB regions (256 MiB since v8.4), YugabyteDB tablets, Spanner splits. The database splits and moves them by size and load, so resharding is automatic.
    2. 

  2. Consensus per range. Each range is kept on three (or five) servers, which agree on every write with a consensus protocol, Raft in CockroachDB, TiDB and YugabyteDB, Paxos in Spanner (how Raft works, with a lab: Distributed systems fundamentals, Raft lab tab). A write commits once a majority has it, so losing one of three copies loses nothing and the range keeps working.
    3. 

  3. Distributed transactions. A transaction touching several ranges is committed atomically by the database, with serializable isolation by default in CockroachDB and Spanner (the root's Database atlas lists each system's isolation and Jepsen history).
    4. 



Measured: CockroachDB, three nodes, then two, then one


CockroachDB v26.3.0, three nodes on this laptop, a table of 200,000 messages split into four ranges, each range replicated to all three nodes; one replica per range, the leaseholder, serves its reads and proposes its writes. A client kept inserting through node 1 while nodes were killed with kill -9 (no warning, like a power cut).




successful inserts per secondseconds with no successful insert (each attempt timed out after 3 s)








The four ranges at the end of the run (SHOW RANGES ... WITH DETAILS)


How to read it. With one node of three gone, every range still has two of its three copies, a majority, so writes simply continue. In this run every lease sat on node 1, the node the client was connected to, so killing node 3 caused no pause at all; had node 3 held leases, the ranges it led would have paused until their leases moved to a survivor. With two nodes gone no range has a majority: writes stop (each insert timed out after 3 s) rather than risk two divergent histories, which is the "consistency over availability" choice that the CAP section of Distributed systems fundamentals explains. Restarting node 2 restored a majority and writes resumed by themselves about 3 s later; nobody ran a failover.


The latency floor, and where it comes from


Every write waits for a majority of a range's replicas. Inside one data centre that is one fast round trip; across regions it is physics. Median round trips between AWS regions, measured by CloudPing (5 Oct 2026): us-east-1 (Virginia) to us-east-2 (Ohio) about 13 ms, to us-west-2 (Oregon) about 70 ms, to eu-west-1 (Ireland) about 68 ms, to ap-southeast-1 (Singapore) about 218 ms (cloudping.co).

Commit at least = round trip from the leaseholder to the nearest other replica (a majority of three is the leader plus one), plus the client's round trip to the leaseholder if it is far away. The intra-region figure is the one cited on Distributed systems fundamentals; the rest are CloudPing medians.


Spanner adds one more wait. Its clocks (TrueTime) report an interval of uncertainty, epsilon, "typically a sawtooth function of time, varying from about 1 to 7 ms"; to make commit order match real time, a commit waits out that uncertainty ("commit wait", about twice epsilon) before becoming visible, which overlaps with the Paxos round (Spanner paper, OSDI 2012).


Cheaper reads: follower reads


Reading from the leaseholder means crossing the ocean too. A follower read reads a nearby replica at a timestamp slightly in the past, so it never waits: SELECT ... AS OF SYSTEM TIME follower_read_timestamp(). Measured on this cluster, the timestamp was  s in the past, matching the follower-reads page's "at least 4.2 seconds" (docs; the function reference says 4.8 s without a licence key, which this unlicensed cluster did not show). It is a read replica's trade, made explicit per query.

What you give up
Latency: every write pays a consensus round trip: a median insert took  ms on this three-node loopback cluster against  ms on plain Postgres with macOS's default flush and  ms with a real SSD flush per commit, as CockroachDB does, and tens of milliseconds across regions. 12. Multi-region: putting data near users, and where the law says


Users in Singapore pay about 218 ms per round trip to a database in Virginia. Three patterns, from simplest:




One primary, replicas everywhere
Reads are local, writes cross the world. OpenAI's "nearly 50 read replicas across multiple geographic regions" with one primary is this pattern. Simple; writes from far away are slow, and failover to another region risks the split brain GitHub hit in 2018 (Case files: gh-2018-10).


Geo-partitioning (each row lives near its owner)
Rows carry a region, and each region's rows are stored and led there: a European user's messages commit in Europe. CockroachDB calls this a REGIONAL BY ROW table; with sharding you get it by making region part of the shard key (one cell or pod per region, as Shopify does per pod). It is also how data residency is done, keeping some users' data inside a jurisdiction, which some laws and many enterprise contracts require.


Global tables (read everywhere, write rarely)
Small, read-mostly data (the list of models, feature flags, prices) is copied to every region for local reads, and each write pays the cost of reaching all of them. CockroachDB: GLOBAL tables, "fast reads everywhere, slower writes" (table localities); sharded systems: reference tables.




Surviving a whole region failing needs replicas in at least three regions, and then every write waits for a second region: CockroachDB's REGION survival goal "adds at least one inter-region round trip to writes", while the default ZONE goal keeps writes inside a region (survival goals). Decide which failure you must survive, then pay for exactly that.

Common mistakes


Sharding before measuring
Most "the database cannot keep up" moments are a missing index, a query that should not run per request, or too many connections. Fix those (section 2); they are needed after sharding anyway.


Expecting replicas to help with writes
Every replica replays every write. Replicas scale reads only, and their lag grows with write load (section 3).


Reading your own write from a replica
A user saves and the page reloads without the change. Route a user's reads to the primary briefly after their write, or wait for the replica to pass the write's log position (section 3).


Partitioning to fix a server that is full
Partitions share the server's CPU, memory and disk. Partition for retention, vacuum and archiving; shard for capacity (section 4).


Partitioning by a column the queries do not use
Queries without the partition key read every partition and plan slower: 0.21 ms against 0.05 ms for opening a chat, measured (section 4).


A shard key that increases (time, sequential id)
All new writes land on one shard: 100% of last week's writes on one of 8 shards, counted on the chat data (section 7).


Routing with hash(key) mod number_of_servers
Going from 3 to 4 servers moves about 75% of the data. Use many logical shards mapped to servers, or consistent hashing (section 9).


Forgetting the lookups that do not carry the shard key
Login by email, admin search, uniqueness of usernames: each becomes a scatter on every request unless you add a lookup table (section 8).


Cross-shard transactions in the hot path
2PC more than doubles commit time and makes failures harder; Vitess's default is not even atomic. Design the key so a transaction stays in one shard (section 8).


Treating "Postgres-compatible" as "Postgres"
Distributed SQL systems differ in isolation, extensions, limits (DSQL: 3,000 rows per transaction) and performance. Test your real queries and your retry logic (section 11).


Starting the next rung too late
Sharding a live system took Notion, Figma and Slack many months. Start when the forecast shows the ceiling a year away, not when the pager does.







Glossary




Vertical scaling: a bigger machine for the same database.


Horizontal scaling: more machines, each with part of the work.


Read replica: a copy that replays the primary's log and answers reads, a little behind.


Replication lag: how far a replica is behind the primary, in time or log bytes.


Read-your-writes: a user always sees their own last write.


Long Fork: two readers see two independent writes in opposite orders.


Partition: a physical piece of one table on the same server.


Partition pruning: skipping partitions a query cannot need.


Functional split (vertical partitioning): whole tables moved to another database.


Shard: a slice of a table's rows on its own server.


Shard key (distribution column): the column that decides a row's shard.


Router: the code or proxy that maps a key to its shard.


Scatter-gather (fan-out): sending a query to every shard and merging the answers.


Logical shard: a small fixed bucket of keys; many live on one server and move as a unit.


Co-location: related tables sharded on the same key so their rows share a server.


Reference table: a small table copied to every server.


Lookup table (lookup vindex): maps a non-key column (email) to the shard key.


Two-phase commit (2PC): prepare on every server, then commit on all.


Hot shard / hot key: a shard or single key receiving far more than its share of load.


Resharding: changing the number of shards or the key; moves data.


Range (region, tablet, split): a contiguous piece of a distributed SQL table, replicated by consensus.


Leaseholder: the replica of a range that serves its reads and proposes its writes.


Follower read: a read from a nearby replica at a slightly past timestamp.


Geo-partitioning: storing and leading each row in its owner's region.


Data residency: keeping data inside a given jurisdiction.













Shard-key lab: choose a shard key for the chat product


The load per shard is counted on the real chat data (100,000 users, 1,000,000 chats, 10,000,000 messages; the root page's generator) for every key and every shard count from 2 to 16 (src/measure/labdata.py). The access patterns are the chat product's; which of them become single-shard follows from the key. Read section 7 of the Reading tab first.

Which requests stay on one shard




"One shard": the request carries the key, so the router sends it to one server. "Every shard": it must fan out to all N. "One shard, hot": single-shard but every such request hits the same shard. The giant tenant is not in the data: it adds one key with the chosen share of all load to show that no key choice can spread a single key.
