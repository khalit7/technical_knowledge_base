The five habits of a professional
  1. Write a check and the change it guards as one statement where you can: UPDATE credits SET balance = balance - 10 WHERE user_id = 7 AND balance >= 10, then read how many rows changed.
  2. Know your database's default isolation level and what it lets through. Postgres defaults to read committed; MySQL defaults to repeatable read, which on this laptop still lost an update that Postgres's repeatable read refused (section 4).
  3. When a rule spans several rows, use serializable (Postgres) and retry on SQLSTATE 40001, or lock one row that every competing transaction must lock first.
  4. Keep transactions short: never hold one open across a call to a language model, a payment provider or a user's think time.
  5. Make every retried operation idempotent, so running it twice does no harm.

1. Why transactions: two requests, one balance

The problem appears

Ines (user 7, the same user as in the root's SQL playground) has 30 prepaid credits. She has the chat open in two browser tabs. In tab A she asks for a long answer that costs 10 credits; a second later, in tab B, a short one that costs 5. The server code for "charge a message" is reasonable on its own:

balance = db.execute("SELECT balance FROM credits WHERE user_id = 7")   # 30
if balance >= cost:
    reply = call_model(prompt)                                          # seconds
    db.execute("INSERT INTO messages ...")
    db.execute("UPDATE credits SET balance = %s WHERE user_id = 7", (balance - cost,))

Run once at a time, it is correct: 30, then 20, then 15. Run twice at once, both copies read 30 before either writes. Tab A writes 30 - 10 = 20, tab B writes 30 - 5 = 25, and the last write wins: Ines paid 5 credits for 15 credits of answers. Nothing failed, no constraint was broken, no error was logged. This is the lost update, and on this page it was reproduced on a real Postgres and a real MySQL: final balance 25 instead of 15 measured.

Two words before going on. A session is one connection from a program to the database; the database runs the statements of one session in order, but statements of different sessions interleave, in whatever order they happen to arrive. Concurrency is that interleaving. Each of the anomalies on this page is one unlucky interleaving.

The idea: a transaction

A transaction is a group of statements the database treats as one unit. BEGIN opens it; COMMIT makes all of its changes permanent and visible to others at the same instant; ROLLBACK throws them all away. Outside BEGIN, each statement is its own one-statement transaction, which is called autocommit.

A transaction gives two separate promises, and beginners usually expect only the first:

All or nothing (atomicity)

If anything fails half-way, none of the transaction's changes survive: the credits are never taken without the reply being saved. This is about failures, and every relational database gives it in full.

As if alone (isolation)

Concurrent transactions should not see each other's half-done work or trample each other's decisions. This is about concurrency, and how much of it you get depends on the isolation level, a setting. Wrapping Ines's code in BEGIN and COMMIT at Postgres's default level still loses the update: atomicity is not isolation.

What your code must do when a statement fails

When one statement inside a transaction fails (a constraint refuses it, a deadlock is detected), Postgres marks the whole transaction failed: every later statement is answered with ERROR 25P02: current transaction is aborted, commands ignored until end of transaction block, and COMMIT is answered with ROLLBACK (SQLSTATE 25P02, in_failed_sql_transaction in the Postgres 16 error codes; the Isolation lab shows a failed transaction's COMMIT answered with ROLLBACK). SQLite instead undoes only the failed statement and lets you commit the rest, which is how the root's SQL playground tab, lesson 10, ends up with a +50 credit and no matching debit (Topic: databases, SQL playground tab). The rule that works everywhere: on any error, roll back and decide whether to retry the whole transaction.

Python drivers do this for you if you let them. With psycopg 3 (the current Postgres driver for Python), with conn.transaction(): issues BEGIN, then COMMIT at the end of the block, or ROLLBACK if an exception escapes. One trap: by default "even a simple SELECT will start a transaction", which then stays open until you commit, holding back clean-up (psycopg 3 docs, transactions; section 10 measures the cost).

Where this goes next: section 2 takes the four ACID letters one at a time with what each costs; sections 3 to 5 are isolation, the hard one.

2. ACID, one letter at a time, and what each costs

The four guarantees of a transaction are known as ACID, a name from Haerder and Reuter's 1983 survey (ACM Computing Surveys). The letters are not equally hard: A and D are solved problems with a price tag, C is mostly your job, and I is where the rest of this page lives.

A: atomicity, and why rollback is cheap in Postgres

Postgres never overwrites a row in place. An UPDATE writes a new version of the row stamped with the writing transaction's number, and leaves the old version where it is (section 5 shows the real versions). Whether a version counts depends only on whether its transaction committed, which Postgres records in a small commit log (pg_xact). So ROLLBACK just marks the transaction aborted: its versions become invisible at once, whatever their number, and are removed later by VACUUM. MySQL's InnoDB does the opposite: it updates the row in place and keeps the old values in an undo log, so a rollback must replay the undo log, and rolling back a huge transaction takes about as long as making it (MySQL 8.4 manual, InnoDB multi-versioning).

What it costs
Postgres pays for cheap rollback with dead row versions that someone must clean up (sections 5 and 10). InnoDB pays with undo logs that grow while any old transaction might still need them.

C: consistency, which is mostly yours

The database guarantees the rules you declared: NOT NULL, UNIQUE, foreign keys, and CHECK (balance >= 0) hold after every commit, whichever code path wrote the row. Rules you did not declare ("at least one engineer on call", "at most 3 messages a day") are only as safe as your code and your isolation level: sections 3 and 4 show both being broken with every statement succeeding. Declare every rule you can; for the rest, read section 4.

A constraint can be checked at commit instead of after each statement with DEFERRABLE INITIALLY DEFERRED (unique, primary key, foreign key and exclusion constraints; not CHECK or NOT NULL), which lets two rows briefly swap values inside one transaction (Postgres 16, CREATE TABLE).

I: isolation

D: durability, and the price of one disk flush

A committed transaction must survive a crash or a power cut. Postgres writes every change to its write-ahead log (WAL: an append-only file of changes, written before the data pages; the root's section 4 introduces it) and, at COMMIT, waits until the operating system confirms that the log reached the disk. That wait is a flush (the fsync family of system calls), and it is the whole cost of durability for small transactions.

Measured on this page's laptop, one client committing one small INSERT per transaction, 5 seconds per setting measured:

Three things to read in it. First, the Mac's default flush (open_datasync) is fast because macOS's ordinary flush does not force the drive to empty its own volatile cache; Postgres's documentation says that "on macOS, write caching can be prevented by setting wal_sync_method to fsync_writethrough" (Postgres 16, reliability and the WAL). With it, the true cost of a durable commit on this machine appears: tens of times slower. On a Linux server the default is fdatasync and the honesty depends on the drive; datacentre SSDs with power-loss protection make honest flushes cheap. Second, synchronous_commit = off returns before the flush, so what it buys depends entirely on how expensive an honest flush is: about 1.5 times more commits per second with the Mac's default flush, about 86 times with the drive cache really flushed. Third, many concurrent commits share one flush (group commit), so throughput with many clients is far better than one client's figure suggests.

Correction to the old storage page
The former "Storage engines, indexes, and the physics of a query" page said synchronous_commit = off "buys enormous throughput". Measured here, that holds only when an honest flush is slow (about 86 times with the drive cache flushed); with a fast or cached flush the gain was about 1.5 times (one client in both cases).
What professionals do with this
  • Never turn fsync off on a database you cannot rebuild: "this can result in unrecoverable data corruption in the event of a power failure or system crash" (Postgres 16, WAL settings).
  • synchronous_commit = off is safe in a different way: a crash can lose the last moments of commits (at most three times wal_writer_delay, 200 ms by default, so about 0.6 s), but "the database state will be just the same as if those transactions had been aborted cleanly" (same page). Set it per transaction for writes you could afford to lose, such as a typing indicator or an analytics event: SET LOCAL synchronous_commit = off inside that transaction. Keep it on for credits and messages.
  • Durability across machines (waiting for a replica before acknowledging, synchronous_commit = remote_apply) is a replication question: see Running Postgres in production and Distributed systems fundamentals.

3. The anomalies: eight ways two transactions collide

An anomaly is an outcome that could not have happened if the transactions had run one after the other, in some order. Each one below is a real recording: two (or three) live sessions on a real database, driven step by step by a script that hands each session one statement, waits up to half a second, and if the statement has not finished records it as blocked (and asks Postgres what it is waiting for) before moving on. A statement that finishes later, because the other session committed or a deadlock was found, is shown in the step during which it finished. The scripts are in src/measure/.

How to read a recording: one column per session, one row per step; the highlighted cell is the statement issued at that step, and what it returned is under it in grey. A dashed red border means the statement is waiting for a lock. The chips under each recording are every isolation level on both databases: red means the anomaly happened, green means it was prevented (and how). Click a chip to see that run. The Isolation lab steps through any of them one statement at a time.

1. Dirty read: reading what was never committed

Session B reads a change that session A has made but not committed, and A then rolls back. B has acted on data that never existed. Here tab A debits all 30 of Ines's credits for a long reply, the model call fails, and A rolls back; meanwhile a billing check in B reads the balance.

Postgres never shows uncommitted data, at any level: it runs READ UNCOMMITTED as read committed, "the only sensible way to map the standard isolation levels to PostgreSQL's multiversion concurrency control architecture" (Postgres 16, transaction isolation). MySQL means it: at READ UNCOMMITTED, B read 0 measured.

2. Non-repeatable read: the same row, two values

B reads a row, A changes it and commits, B reads the row again in the same transaction and gets a different value. An invoice job that reads Ines's balance for the header and again for the footer prints two numbers.

At read committed every statement sees everything committed before it started, so the second read sees A's commit. At repeatable read the whole transaction reads one snapshot taken at its first statement.

3. Phantom: rows appear in a range

The same as a non-repeatable read, but for a condition instead of a row: B counts Ines's messages today, A inserts one and commits, B counts again and gets one more. The new row is the phantom. The SQL standard allows phantoms at repeatable read; Postgres's repeatable read prevents them because a snapshot hides new rows too (the documentation's table says "allowed, but not in PG"); MySQL's plain reads at repeatable read also use a snapshot, so they did not see it either measured.

4. Lost update: read, compute in the app, write back

Section 1's bug. A and B both read 30; A writes 20 and commits; B writes 25 over it. Berenson and colleagues named it P4 in "A Critique of ANSI SQL Isolation Levels" (Berenson et al., 1995), the paper that showed the SQL standard's definitions miss it.

This is the first place the two databases disagree. At repeatable read, Postgres refused B's write: "could not serialize access due to concurrent update" (SQLSTATE 40001), because B tried to change a row that a transaction committed after B's snapshot had already changed. MySQL at repeatable read let B's write through and lost A's 10 credits measured: InnoDB's UPDATE always works on the latest committed row, not on the snapshot, and does not check that the row changed since the transaction's snapshot (its manual: the snapshot "applies to SELECT statements within a transaction, not necessarily to DML statements", MySQL 8.4, consistent reads). Two fixes work everywhere and are the chips marked fix: one atomic UPDATE ... SET balance = balance - 10, or SELECT ... FOR UPDATE before computing.

5. Read skew: two rows from two different moments

A moves 10 credits from Ines (user 7) to Quinn (user 12), the transfer from the root's SQL playground lesson 10; the total is always 50. B, an audit job, reads Ines's balance before the transfer and Quinn's after it, and adds them up to 60. Every row B read was committed; the mix is from two moments. Backups, exports and reports that run for minutes at read committed are exposed to exactly this.

6. Write skew: two valid decisions, one broken rule

The chat product's incident rota needs at least one engineer on call. Ana and Raj are both on call and both feel ill. Each runs "if someone else is on call, take me off": each counts 2, each updates their own row. No row is written twice, so no lock conflicts and no update is lost, yet nobody is on call. This is the on-call doctors example from Kleppmann's Designing Data-Intensive Applications; Berenson et al. named the pattern A5B.

Repeatable read does not help: both snapshots honestly showed 2. Only serializable caught it on Postgres, at B's COMMIT, with "could not serialize access due to read/write dependencies among transactions" (SQLSTATE 40001). Or lock the rows you read: SELECT ... FROM oncall WHERE on_call FOR UPDATE makes the second engineer wait, then see 1 measured.

7. Write skew on a quota: the row that does not exist yet

Ines may send 3 messages a day and has sent 2. Two tabs each count today's messages, see 2, and insert one: 4 messages. The same shape as the rota, with one twist that defeats the usual fix: there is no row to lock. FOR UPDATE on the count would lock the two existing messages, while the conflict is over a third row that neither transaction can see yet.

Three fixes, best first. Materialise the conflict (Kleppmann's term): keep a daily_usage(user_id, day, n) row and make the check and the increment one statement, UPDATE daily_usage SET n = n + 1 WHERE user_id = 7 AND day = ... AND n < 3; zero rows changed means over quota, and two tabs now collide on one row, which read committed handles (section 1's atomic update). Lock a row both must touch: SELECT ... FROM users WHERE id = 7 FOR UPDATE first (the chip marked fix). Use serializable and retry, which caught it on Postgres measured. MySQL's gap locks, its answer to phantoms, protect only locking reads; the plain SELECT count(*) took none, so MySQL's repeatable read let the fourth message through too.

8. A serialization anomaly with a read-only transaction

The subtlest one, found by Fekete, O'Neil and O'Neil in 2004 ("A Read-Only Transaction Anomaly Under Snapshot Isolation") and used on the PostgreSQL wiki as the "deposit report" (PostgreSQL wiki, SSI). Credit purchases are filed under the open billing batch. A, a purchase, reads "batch 1 is open". B closes batch 1 and commits. C, a report, sees batch 1 closed and totals it: 100. A then files its purchase in batch 1 and commits: batch 1 now totals 150, after a report on the closed batch said 100. Remove the report and the history is fine; the read-only transaction is what makes it impossible.

A serialization anomaly is the general name for any result that no one-at-a-time order could produce; write skew is the common case. Only serializable prevents all of them: Postgres aborted the purchase A (SQLSTATE 40001), so its retry files under batch 2 measured.

4. Isolation levels: what each one lets through, measured

Where the levels come from

The SQL standard (1992) defines four isolation levels by which of three phenomena they forbid: dirty reads, non-repeatable reads and phantoms. Three years later Berenson, Bernstein, Gray and colleagues showed that these definitions are ambiguous and miss whole classes of anomaly, including lost update, read skew and write skew, and that the popular snapshot isolation (each transaction reads one consistent snapshot; a write fails if the row changed since the snapshot) fits none of the four levels (Berenson et al., 1995). Adya's 1999 thesis restated every level as which cycles of dependencies between transactions are allowed (Adya, MIT, 1999), and that is how testers such as Kleppmann's Hermitage suite (2014, github.com/ept/hermitage) and Jepsen describe databases today. The practical lesson: a level's name tells you little; what matters is which anomalies a given database lets through at it.

The measured matrix

How to read it
  • Postgres read committed (the default) blocks only dirty reads. Everything else in the table got through, including the lost update.
  • Postgres repeatable read is snapshot isolation. Jepsen's 2020 analysis agrees: "PostgreSQL's 'repeatable read' isolation level is actually snapshot isolation" (Jepsen, PostgreSQL 12.3, 2020-06-12). It stops the lost update with an error, but not write skew in either form, nor the read-only anomaly.
  • Postgres serializable stopped everything, in these runs always by aborting one transaction with SQLSTATE 40001 rather than by making anyone wait (two writes to the same row still wait for each other's row lock first). Your code must retry (section 9).
  • MySQL's default, repeatable read, lost the update that Postgres's repeatable read refused, and let both write skews through. Jepsen's analysis of MySQL 8.0.34 (2023-12-19) found lost updates, read skew and non-repeatable reads at this level and concluded "it isn't clear what MySQL Repeatable Read actually is" (Jepsen, MySQL 8.0.34). Our read skew run was prevented because B only read; Hermitage records MySQL's repeatable read as preventing read skew in read-only transactions only.
  • MySQL serializable works by locking instead: every plain SELECT becomes SELECT ... FOR SHARE when autocommit is off (MySQL 8.4, isolation levels), so conflicting transactions wait for each other, and the lost update and both write skews ended in a deadlock (error 1213) that killed one transaction.

These results agree with Hermitage's published table for both databases. Other databases, from the same table: Oracle's default is read committed and its "serializable" is snapshot isolation, so it allows write skew; SQL Server defaults to a locking read committed; CockroachDB and FoundationDB default to serializable (Hermitage; CockroachDB docs).

How Postgres's serializable works without locking everything

Since PostgreSQL 9.1 (2011), serializable is serializable snapshot isolation (SSI). Transactions still read snapshots and never wait for readers. In addition, Postgres records what each serializable transaction read (in "SIREAD" locks, which block nobody) and watches for a read-write dependency: T1 read something that T2 then wrote. One such dependency is harmless. Two in a row, T1 to T2 to T3, is the "dangerous structure" that every serialization anomaly under snapshot isolation contains (Cahill, Röhm and Fekete, SIGMOD 2008), and Postgres aborts one transaction in it, sometimes when no real anomaly would have followed (a false positive). Ports and Grittner, who built it, report that it performs "only slightly below that of snapshot isolation" and "significantly outperforms" classic two-phase locking on read-heavy workloads (Ports and Grittner, VLDB 2012).

The error messages in the recordings say which case fired: "could not serialize access due to concurrent update" is the simple first-updater-wins rule (you tried to change a row changed since your snapshot); "due to read/write dependencies among transactions", with "Reason code: Canceled on identification as a pivot", is SSI's dangerous structure. Reads are tracked by row, by page or by whole table, coarser when memory runs short, and "a sequential scan will always necessitate a relation-level predicate lock", so a missing index raises the failure rate (Postgres 16, transaction isolation). Guarantees are also only as good as the code: Jepsen's 2020 analysis found a bug that let a write skew through Postgres's serializable in 9.5 to 13 under normal operation, with a fix scheduled for the 13 August 2020 minor releases (same Jepsen report).

Which level to use
  • Read committed (Postgres's default) is right for most single-statement work and for transactions whose every check is folded into its writes (atomic UPDATE ... WHERE, constraints, FOR UPDATE where needed).
  • Repeatable read for anything that reads many rows and needs them consistent: reports, exports, audits, a backup (pg_dump takes one snapshot for this reason).
  • Serializable when a business rule spans rows and you cannot or will not reason about every interleaving: quotas, rotas, inventory, double-booking. Declare read-only transactions READ ONLY (they then cause fewer aborts), keep the retry loop in one place, and keep the transactions short. It does not protect against transactions running at lower levels: every transaction that touches the rule must be serializable.

5. MVCC: how a database isolates without stopping everyone

The problem

The simplest way to isolate transactions is to lock everything each one reads or writes until it commits, so everyone else waits. That was how databases worked for decades (two-phase locking), and it makes a long report block every writer it touches. Postgres, MySQL's InnoDB, Oracle and most modern databases instead keep several versions of a row, so a reader can see an older version while a writer prepares a newer one: multi-version concurrency control (MVCC). In the Postgres documentation's words, "reading never blocks writing and writing never blocks reading" (Postgres 16, MVCC introduction).

Row versions in Postgres: xmin and xmax

Every transaction that writes gets a number, its transaction id (xid), from a counter. Every row version (Postgres calls it a tuple) carries two hidden fields: xmin, the xid that created it, and xmax, the xid that deleted or replaced it (0 if none). An UPDATE sets xmax on the old version and writes a new version with xmin = its own xid. You can see them: SELECT xmin, xmax, * FROM credits.

A snapshot is a note of which transactions had committed at one moment, written xmin:xmax:list: every xid below the first number had finished, every xid from the second number on had not started, and the list names those in between still running. A version is visible to a snapshot if its creator had committed by then and its deleter had not. At read committed each statement takes a new snapshot; at repeatable read and serializable the first statement's snapshot serves the whole transaction.

Three things the recording shows. At read committed, B's UPDATE ran with a fresh snapshot that includes A's commit, and wrote the value it had computed from an old read: the database did exactly what it was told. With FOR UPDATE, A's lock is itself written into the row (xmax set to A's xid, marked lock-only), and B waits on A's transaction, then reads the new version. Under serializable, B's snapshot is fixed at its first read, so its update finds that the version it can see has already been replaced by a transaction it cannot see, and Postgres refuses.

Why VACUUM exists

Old versions are not removed when they stop being current, because some transaction with an old snapshot might still need them. Once no running transaction can see a dead version, its space can be reused, and that is VACUUM's job (run automatically by autovacuum). It also freezes very old versions so the 32-bit transaction counter can wrap around safely; skipping that for about 2 billion transactions makes Postgres refuse writes, which is what took Sentry's writes down for hours in July 2015 (Postgres 16, routine vacuuming; Sentry, 2015). Plain VACUUM makes space reusable but does not give it back to the operating system; the table stays large, which is called bloat. Tuning autovacuum, freezing and fixing bloat belong to Running Postgres in production; the part that is about transactions, a long transaction stopping clean-up, is measured in section 10.

Updating a row only within its own page, with no indexed column changed, is a HOT update (heap-only tuple): no index entry is added, and later readers can prune the dead versions on that page without waiting for VACUUM. That is why section 10's control run updated one row 20,000 times and the table never grew past one page.

6. Locks: making the other transaction wait

A lock is a claim a transaction holds on something (a row, a table, a number) that makes conflicting claims wait until it commits or rolls back. MVCC removed locks from plain reads; writes and explicit locking reads still take them. Postgres has two families (Postgres 16, explicit locking).

Row locks

Every UPDATE and DELETE locks the rows it changes until the end of the transaction; that is why, in section 3, the second atomic UPDATE of Ines's balance waited for the first. You can take the same lock on a read:

The job queue is the classic use. The chat product keeps a jobs table (summarise a chat, index an uploaded file); several workers each run SELECT id FROM jobs WHERE status = 'queued' ORDER BY id LIMIT 1 FOR UPDATE. Recorded on Postgres with two workers measured:

Table locks and the lock queue

Every statement also takes a lock on each table it touches, in one of eight modes. Ordinary reads and writes take weak modes that never conflict with each other. Many ALTER TABLE forms, DROP, TRUNCATE and VACUUM FULL take ACCESS EXCLUSIVE, and "only an ACCESS EXCLUSIVE lock blocks a SELECT" (same explicit-locking page). The trap is the queue: a lock request that must wait queues, and every later request that conflicts with it queues behind it, even if it would not have conflicted with the holder. Recorded with three sessions measured:

An analytics query left its transaction open; the migration's ALTER TABLE waited for it; and an ordinary one-row read by session C, which needs only the weakest lock, waited behind the migration until the analytics transaction ended. In production, C is every request of your API. This is how GoCardless had about 15 seconds of API downtime from a migration that should have been instant: "Set lock_timeout in your migration scripts to a pause your app can tolerate. It's better to abort a deploy than take your application down" (GoCardless engineering blog, Chris Sinjakli). With lock_timeout the migration gave up after 200 ms with SQLSTATE 55P03, and C never waited. Running migrations safely is on SQL and data modelling.

Advisory locks: a lock on a number

Sometimes the thing to protect is not a row: "only one summariser runs per user at a time". Postgres lets you lock any 64-bit number, with a meaning only your application knows: pg_advisory_xact_lock(7) waits for and holds the lock until the transaction ends, pg_try_advisory_lock(7) returns false at once if someone holds it. Session-level advisory locks survive ROLLBACK and must be released explicitly. Recorded: A's try returned true, B's returned false until A released it measured. A common production use is making sure only one instance of a scheduled job or migration runs.

What locks cost
Waiting. Every lock turns a conflict into latency for someone, and the lock is held until COMMIT, not until the statement ends: whatever your code does between the locking statement and the commit (a model call, a network request) is time everyone else waits. And two transactions can each wait for the other, which is the next section.

7. Deadlocks: waiting for each other forever

A deadlock is a cycle of waits: A holds a lock B needs while waiting for a lock B holds. Neither can move. It needs nothing unusual, just two transactions touching the same rows in opposite orders: A transfers 5 credits from Ines (7) to Quinn (12), B transfers 3 from Quinn to Ines, at the same time measured:

Postgres checks for a cycle only after a lock wait has lasted deadlock_timeout (1 second by default), because the check is expensive and most waits end on their own. It then aborts one transaction with SQLSTATE 40P01 and a detail that names both processes; which one is chosen "is difficult to predict and should not be relied upon" (Postgres 16, deadlocks). In the recording B was killed after 1.0 s and A's update went through. MySQL detects deadlocks immediately by default (innodb_deadlock_detect) and returns error 1213, as in its serializable runs in section 4.

How professionals avoid them
  • Take locks in one global order. The documentation: "the best defense against deadlocks is generally to avoid them by being certain that all applications using a database acquire locks on multiple objects in a consistent order". The second recording locks both credit rows lowest id first with one SELECT ... ORDER BY user_id FOR UPDATE: B simply waits, and both transfers complete.
  • Keep transactions short, so the window for a cycle is small.
  • Retry on 40P01 like a serialization failure: a deadlock victim's transaction did nothing, so running it again is safe if the work is idempotent (section 9).
  • Watch for them: log_lock_waits = on logs every wait longer than deadlock_timeout, and pg_stat_database.deadlocks counts them.

8. Optimistic concurrency: check at write time instead of locking

Locks are pessimistic: they assume a conflict and make others wait in advance. Optimistic concurrency control assumes there will be no conflict, lets everyone read freely, and checks at write time that nobody changed the row in between. The usual form is a version column and a compare-and-set: read the row with its version, then UPDATE ... SET ..., version = version + 1 WHERE id = ... AND version = <the version I read>. If someone else wrote first, the version moved and the update changes 0 rows; you re-read and try again. No transaction is held open between the read and the write. Recorded on Postgres measured:

B's first write reported UPDATE 0, so B re-read (20, version 2) and wrote 15. The final row is balance 15, version 3: both spends counted, nobody waited.

This is what web applications do when the read and the write are separated by a person: the user opens a chat's settings, edits the title for a minute, and saves. Holding a transaction (and a lock) open for that minute is out of the question; the version column catches the case where someone else saved in between. Over HTTP the same idea is the ETag header and a conditional If-Match request (Building a backend API). ORMs build it in: SQLAlchemy's version_id_col adds the version check to every UPDATE and raises StaleDataError when it matches zero rows (SQLAlchemy 2.0 docs); Rails does the same with a lock_version column.

What it costs, and when not to use it
Wasted work under contention: every lost race is a re-read and a retry. It shines when conflicts are rare (a user editing their own settings) and does badly on a hot row that many writers hit at once (a shared counter, a team's credit pool), where a lock or one atomic UPDATE ... SET n = n + 1 wins. Always check the affected-row count: an optimistic update that ignores UPDATE 0 is just the lost update again.

9. Retries in application code, and what serializable costs

A real retry loop

Serializable and repeatable read refuse a conflicting transaction with SQLSTATE 40001, a deadlock victim gets 40P01, and the Postgres documentation is direct about it: the application "should abort the current transaction and retry the whole transaction from the beginning" (Postgres 16, transaction isolation). The whole transaction, including its reads, because the decisions were made on data that has changed. This is the loop the benchmark below ran, unchanged, with psycopg 3:

import random, time
from psycopg import errors

RETRYABLE = (errors.SerializationFailure, errors.DeadlockDetected)   # SQLSTATE 40001 and 40P01

def run_in_transaction(conn, work, max_attempts=10):
    """Run work(conn) in a transaction; on a serialization failure or deadlock, roll back and run it again."""
    for attempt in range(1, max_attempts + 1):
        try:
            with conn.transaction():          # BEGIN ... COMMIT, or ROLLBACK if work raises
                return work(conn), attempt
        except RETRYABLE:
            if attempt == max_attempts:
                raise
            time.sleep(random.uniform(0, min(0.05, 0.001 * 2 ** attempt)))   # full jitter, capped

conn.isolation_level = psycopg.IsolationLevel.SERIALIZABLE
run_in_transaction(conn, lambda c: spend(c, user_id=7, cost=10))

Four rules make it safe. Everything inside work must be repeatable: no model call, no e-mail, no payment inside the transaction, because a retry would do it twice; do the slow or external part before or after, and keep only database work inside. Retry only the retryable codes; a constraint violation will fail again. Wait a random, growing time between attempts (exponential backoff with jitter) so that the colliding transactions do not collide again in lock-step. Cap the attempts and surface an error, because under a hot spot some transaction will keep losing.

When the external step must happen once (charge a card, then record it), the retry belongs to the whole request, and the tool is an idempotency key: the client sends a unique key with the request, the server stores the key and the result in the same transaction as the work, and a repeated key returns the stored result instead of acting again. The pattern, with "atomic phases" between external calls, is Brandur Leach's "Implementing Stripe-like Idempotency Keys in Postgres" (brandur.org, 2017-10-27), and it is taught in full on Building a backend API (section 10).

Measured: the price of correctness under contention

The chat product's "spend one credit and save the message" transaction, run by 2, 8 and 32 concurrent clients for 8 seconds each on Postgres 16.2, four ways: read committed with the naive read-then-write (section 1's code), read committed with one atomic UPDATE, read committed with FOR UPDATE, and serializable running the naive code inside the retry loop above. Two contention levels: every client spends from one of 4 hot users, or from 10,000 users measured.

What it says. With the load spread over 10,000 users, correctness was free: all four ways ran at about the same speed, and serializable retried about one transaction in a hundred or fewer. On 4 hot users it was not: serializable fell well behind the atomic UPDATE, with more than one retry per commit and hundreds of transactions that lost ten times in a row at 32 clients, while the naive code was fast and lost tens of thousands of updates. The atomic UPDATE was fastest-correct under contention because the row lock is held only from the UPDATE to the COMMIT, and nothing is computed in between. Even with only 2 clients, dozens of serializable transactions failed ten attempts in a row. A debugging rerun logged the errors: most were SSI's "Canceled on identification as a pivot", not the simple concurrent-update case. With only four users, every read lands on one index page, and Postgres may track reads by page rather than by row, so transactions can look dependent when they are not; this run did not separate that from genuine conflicts on the same user.

One 32-client serializable run (10,000 users) on Postgres 16.2 stalled for over nine minutes: every session waited on an internal lock named SerializableFinishedList while one backend used CPU at COMMIT. Two reruns on 16.2 and one on 16.15 did not stall, so the cause is unconfirmed; the benchmark now has a watchdog and the figures shown are from a complete rerun. It is a reminder that serializable's bookkeeping is real work inside the server.

10. Long transactions and what they cost

A transaction that stays open costs the whole database, not just its own session, in three ways: it holds its locks (section 6), it holds back clean-up of old row versions, and in Postgres it can hold back transaction-id freezing. The second is invisible until it is large, so it was measured: one session opened a repeatable read transaction, read one row and then did nothing (a forgotten BEGIN, a notebook left open, a request stuck on a model call), while another session updated Ines's balance 20,000 times. Then the same 20,000 updates with no transaction left open, as the control measured:

With nothing held open, each update's old version was pruned on the spot (section 5's HOT updates) and the table never grew past one 8 KB page. With one idle transaction holding an old snapshot, not one of the 20,000 dead versions could be removed: VACUUM VERBOSE reported them as "dead but not yet removable", the table grew to over a hundred pages, the same updates took more than twice as long, and reading Ines's one row became several times slower, because every read now walks a chain of dead versions. After the idle transaction ended, VACUUM removed all 20,000, but the file stayed the same size: the space is reusable, not returned. The same thing on a live server, with autovacuum on: Running Postgres in production (section 6) ran 1,500 updates a second against a 100,000-row table and left one session idle in a transaction; autovacuum kept firing every time its trigger was passed and removed nothing, so dead rows and table size climbed in a straight line until the session ended measured there.

What professionals set (Postgres)
  • idle_in_transaction_session_timeout: ends a session that sits idle inside an open transaction; the documentation notes it is for exactly this, because "an open transaction prevents vacuuming away recently-dead tuples" (Postgres 17, client settings).
  • transaction_timeout (new in PostgreSQL 17, 2024): ends any transaction that runs longer than the limit, busy or idle. statement_timeout caps one statement; lock_timeout caps one lock wait. All default to 0 (off); the documentation advises setting statement_timeout, lock_timeout and transaction_timeout per role, session or transaction rather than in postgresql.conf, "because it would affect all sessions".
  • A dashboard query for the oldest open transactions: SELECT pid, state, now() - xact_start AS age, left(query, 60) FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY age DESC LIMIT 5. Alert when the oldest is minutes old.
  • In application code: never call a language model, a payment provider or anything slow while a transaction is open. Read, commit, call the model, then write the result in a new short transaction (with the checks of sections 3 and 8 at write time).

Replicas add a twist: a long query on a read replica either gets cancelled ("canceling statement due to conflict with recovery") or, with hot_standby_feedback = on, holds back clean-up on the primary as if it ran there. That trade-off is on Running Postgres in production and Scaling a database.

11. Transactions across more than one database

Everything so far happened inside one database. The chat product soon has more than one place to write: Postgres for credits, a search index for messages, a queue for background jobs, a payment provider. No single COMMIT covers them, and three answers exist.

Two-phase commit (2PC)

A coordinator asks every participant to prepare (do everything but the final commit, and promise to be able to commit), then tells all of them to commit. Postgres supports it with PREPARE TRANSACTION and COMMIT PREPARED, off by default (max_prepared_transactions = 0) (Postgres 16, PREPARE TRANSACTION). Its cost is blocking: a participant that has prepared holds its locks until it hears from the coordinator, and if the coordinator dies, it waits. A forgotten prepared transaction also holds back VACUUM like section 10's idle session.

Sagas

Give up atomicity across systems: run a sequence of local transactions, and if a later step fails, run compensating transactions that undo the earlier ones (refund the credits). Each step is short and local; the price is that other requests can see the in-between states, and every step needs an undo.

The transactional outbox

Write the business change and a row in an outbox table in one local transaction; a separate process publishes the outbox rows to the queue afterwards, at least once. This turns "write to two systems" into "write to one database", and is the usual answer for database plus queue.

All three, with measured crash and redelivery behaviour on a real Postgres, are taught on Queues, streams and async work (sections on the outbox and on sagas against two-phase commit). Databases that spread one logical database over many machines and still offer serializable transactions (Spanner, CockroachDB) use consensus and careful clocks under the hood: see Distributed systems fundamentals and Scaling a database.

What professionals do in production (as of October 2026)

  • Postgres at its default, read committed, plus discipline is what most Postgres applications run: checks folded into writes (UPDATE ... WHERE balance >= 10, then read the row count), constraints for every rule that can be declared, FOR UPDATE where a read must not go stale, and serializable for the few transactions that guard multi-row rules. Teams that choose serializable everywhere (CockroachDB's default, for instance) accept the retry loop as part of every data access path.
  • Know the MySQL difference: code written for MySQL's repeatable read is not protected from lost updates, as recorded in section 4. Use atomic updates or SELECT ... FOR UPDATE; many MySQL shops run read committed for its simpler locking.
  • Short transactions as a rule, enforced by settings: idle_in_transaction_session_timeout on application roles, lock_timeout on migrations, a statement timeout per endpoint, and an alert on the age of the oldest open transaction.
  • One retry helper for 40001 and 40P01, with jitter and a cap, used by every transaction, and idempotency keys at the API edge so that a retried request cannot charge twice.
  • Queues in the database with FOR UPDATE SKIP LOCKED until throughput says otherwise; a single job at a time with an advisory lock.
  • Lock-aware migrations: SET lock_timeout, small steps, retries of the migration rather than of the app.
  • Never a model call inside a transaction. LLM calls take seconds; a transaction held across one holds its row locks and its snapshot for that long, for every request in flight.

Common mistakes

Believing that BEGIN ... COMMIT prevents race conditions
It gives atomicity, not full isolation. At Postgres's default level a transaction-wrapped read-then-write still lost an update (section 3, lost update, read committed).
Reading, computing in Python, writing back
The lost update's shape. Write SET balance = balance - 10 instead of SET balance = 20, or lock the row when you read it.
Ignoring the affected-row count
UPDATE ... WHERE balance >= 10 that changed 0 rows means "not enough credits"; an optimistic update that changed 0 rows means "someone else wrote first". Code that does not read the count turns both into silent bugs.
Assuming "repeatable read" means the same thing everywhere
Postgres's is snapshot isolation and refuses lost updates; MySQL's let one through on this page; the SQL standard's allows phantoms. Test the anomaly you care about on your database (the scripts in src/measure/ are a starting point).
Using FOR UPDATE to protect a rule over rows that do not exist yet
The quota case: nothing to lock. Materialise the conflict in a counter row, lock a parent row, or use serializable.
Switching to serializable without a retry loop
Users then see the 40001 errors. Retry the whole transaction, not the failed statement, and keep external calls out of it.
Mixing isolation levels for one rule
Serializable's guarantee holds among serializable transactions. One code path at read committed that writes the same rows can still produce the anomaly.
Leaving a transaction open
A Python driver starts a transaction on the first query, even a SELECT; a script or notebook that never commits holds back VACUUM for the whole database (section 10 measured 20,000 dead versions kept alive by one idle session).
Taking locks in different orders in different code paths
The recipe for deadlocks (section 7). Sort the ids before locking several rows.
Running a migration without lock_timeout
One long read in front of it, and every query on the table queues behind the migration (section 6).
Turning fsync off for speed
Corruption after a power cut. If commits are too slow, batch more work per transaction, rely on group commit, or use synchronous_commit = off for writes you can afford to lose.

Glossary

ACID: atomicity, consistency, isolation, durability; the four promises of a transaction.
Anomaly: an outcome no one-at-a-time order of the transactions could produce.
Autocommit: each statement outside BEGIN is its own transaction.
Autovacuum: Postgres's background process that runs VACUUM and ANALYZE.
Bloat: space in a table or index taken by dead or reusable versions.
Concurrency: statements of several sessions interleaving.
Deadlock: transactions each waiting for a lock another holds; one is killed (40P01, MySQL 1213).
Dirty read: reading another transaction's uncommitted change.
Flush (fsync): forcing written data from memory to the disk; the cost of durability.
HOT update: a new row version on the same page with no index change; prunable without VACUUM.
Idempotency key: a client-chosen key that makes a repeated request return the first result instead of acting twice.
Isolation level: the setting that decides which anomalies the database still allows.
Lock: a claim that makes conflicting claims wait until commit or rollback.
Lost update: two read-modify-write cycles on one value; the second overwrites the first.
MVCC: multi-version concurrency control; readers see old versions while writers make new ones.
Non-repeatable read: the same row read twice in one transaction gives two values.
Optimistic concurrency: no lock; check at write time that the row did not change (version column).
Phantom: a repeated query with a condition returns new or missing rows.
Read skew: reading related rows from two different moments.
Serialization anomaly: any anomaly, including write skew, that only serializable prevents.
Session: one connection to the database; runs one transaction at a time.
Snapshot: which transactions had committed at one moment, xmin:xmax:list.
Snapshot isolation: one snapshot per transaction, writes refused if the row changed since; Postgres's repeatable read.
SSI: serializable snapshot isolation; Postgres's serializable since 9.1.
Transaction: statements treated as one unit: BEGIN, then COMMIT or ROLLBACK.
Transaction id (xid): the number a writing Postgres transaction gets.
Version column: a counter checked and incremented by every update (compare-and-set).
WAL: write-ahead log; changes are logged and flushed before commit returns.
Write skew: two transactions read the same rows and write different ones, together breaking a rule.
xmin, xmax: the ids of the transactions that created and deleted a row version.
