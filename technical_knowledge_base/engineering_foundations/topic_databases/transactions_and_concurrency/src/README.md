## Measurements (all real, recorded 2026-10-04 on an Apple M1 Pro laptop, macOS)
Run from a scratch directory, never inside the repo, with `uv run --no-project`:
```
TX_SCRATCH=$PWD uv run --no-project --python 3.12 --with pgserver --with 'psycopg[binary]' --with pymysql python <this folder>/measure/run_matrix.py pg
TX_SCRATCH=$PWD MYSQL_ENV=$PWD/mysqlenv uv run ... run_matrix.py mysql
TX_SCRATCH=$PWD uv run ... extras.py
TX_SCRATCH=$PWD uv run ... bench.py            # about 5 minutes; TAG, PG_BIN, ONLY env vars for partial reruns
TX_SCRATCH=$PWD PGX_ENV=$PWD/pgenv uv run ... mvcc_trace.py
python3 measure/build_data.py && python3 recompute.py && sh build.sh
```
- `measure/txharness.py`: the coordinator. Each session is a real connection in its own thread; each step hands one statement to one session, waits 0.5 s, and if it has not finished records it as blocked (asking `pg_stat_activity` what it waits for), then waits 1.5 s more (longer than `deadlock_timeout`) while anything is blocked. Statements that finish later are recorded with the step during which they finished. Refuses to start on a port another server holds (another agent's Postgres was on the first port tried).
- `measure/scenarios.py`: the eight anomalies on the chat product (credits of users 7 and 12 as in the root's SQL playground, a daily quota of 3, an on-call rota, billing batches), each with a checker deciding from the recorded results whether the anomaly happened; fix variants.
- `measure/run_matrix.py`: every scenario at every level on PostgreSQL 16.2 (pgserver wheel, the root's build) and MySQL 9.7.2 (InnoDB, conda-forge build installed with a standalone micromamba binary into the scratch directory; nothing system-wide). Writes `inputs/matrix_pg.json`, `inputs/matrix_mysql.json`.
- `measure/extras.py`: deadlock and ordered locking, the lock queue with and without `lock_timeout`, job queue with FOR UPDATE / SKIP LOCKED / NOWAIT, optimistic version column, advisory locks, a long transaction against 20,000 updates (with a control run), durability at four settings. Writes `inputs/extras_pg.json`.
- `measure/bench.py`: the contention benchmark (4 ways x 2, 8, 32 client processes x 4 hot users or 10,000 users, 8 s each), with a stall watchdog. Writes `inputs/bench_pg.json`. The retry loop on the page is copied verbatim from this file.
- `measure/mvcc_trace.py`: the lost update three ways with `pageinspect` page dumps and `pg_current_snapshot()`, on PostgreSQL 16.15 from conda-forge (the pgserver wheel has no contrib extensions). Writes `inputs/mvcc_trace.json`.
- `measure/debug_retries.py`: logs every serialization error for 2 clients on 4 hot users; counts kept in `inputs/notes_bench.json` with the record of one stalled run.
- `recompute.py`: asserts every number and claim stated in the Reading prose against the inputs and that `22_js_data.js` is current (47 checks, all pass).
- `check_ui.mjs`: clicks every control (anomaly chips, every Fig. 3 step in every mode, every segmented control, every lab scenario x database x level stepped to the end) at 390 dark and 920 light; run from the repo root.

## Departures from the method
- The child-page method suggests one before/after animation; this page has one (section 5) and replaces most other illustrations with *recorded* traces, because concurrency can be recorded for real more cheaply than it can be animated faithfully.
- A second database (MySQL) is measured, not only cited, because the most practical difference on the page (MySQL's repeatable read loses updates that Postgres's refuses) is exactly the kind of claim the reader was told not to trust.
- Section 2's durability numbers come from a Mac, where the default flush does not empty the drive cache; the page says so and shows `fsync_writethrough` beside it.

## Data sizes
`22_js_data.js` about 100 KB (every recorded step of 88 runs: 76 anomaly runs, 9 lock recordings, 3 MVCC traces). The page is about 253 KB.
