1. Why transactions: two requests, one balance

The problem appears

Ines (user 7, the same user as in the root's SQL playground) has 30 prepaid credits. She has the chat open in two browser tabs. In tab A she asks for a long answer that costs 10 credits; a second later, in tab B, a short one that costs 5. The server code for "charge a message" is reasonable on its own:

balance = db.execute("SELECT balance FROM credits WHERE user_id = 7")   # 30
if balance >= cost:
    reply = call_model(prompt)                                          # seconds
    db.execute("INSERT INTO messages ...")
    db.execute("UPDATE credits SET balance = %s WHERE user_id = 7", (balance - cost,))

Run once at a time, it is correct: 30, then 20, then 15. Run twice at once, both copies read 30 before either writes. Tab A writes 30 - 10 = 20, tab B writes 30 - 5 = 25, and the last write wins: Ines paid 5 credits for 15 credits of answers. Nothing failed, no constraint was broken, no error was logged. This is the lost update, and on this page it was reproduced on a real Postgres and a real MySQL: final balance 25 instead of 15 measured.

Two words before going on. A session is one connection from a program to the database; the database runs the statements of one session in order, but statements of different sessions interleave, in whatever order they happen to arrive. Concurrency is that interleaving. Each of the anomalies on this page is one unlucky interleaving.

The idea: a transaction

A transaction is a group of statements the database treats as one unit. BEGIN opens it; COMMIT makes all of its changes permanent and visible to others at the same instant; ROLLBACK throws them all away. Outside BEGIN, each statement is its own one-statement transaction, which is called autocommit.

A transaction gives two separate promises, and beginners usually expect only the first:

All or nothing (atomicity)

If anything fails half-way, none of the transaction's changes survive: the credits are never taken without the reply being saved. This is about failures, and every relational database gives it in full.

As if alone (isolation)

Concurrent transactions should not see each other's half-done work or trample each other's decisions. This is about concurrency, and how much of it you get depends on the isolation level, a setting. Wrapping Ines's code in BEGIN and COMMIT at Postgres's default level still loses the update: atomicity is not isolation.

What your code must do when a statement fails

When one statement inside a transaction fails (a constraint refuses it, a deadlock is detected), Postgres marks the whole transaction failed: every later statement is answered with ERROR 25P02: current transaction is aborted, commands ignored until end of transaction block, and COMMIT is answered with ROLLBACK (SQLSTATE 25P02, in_failed_sql_transaction in the Postgres 16 error codes; the {{Isolation lab|#t-lab}} shows a failed transaction's COMMIT answered with ROLLBACK). SQLite instead undoes only the failed statement and lets you commit the rest, which is how the root's SQL playground tab, lesson 10, ends up with a +50 credit and no matching debit ({{Topic: databases, SQL playground tab|n:3cd5c17b0d0d815d8841ec845f5f3324}}). The rule that works everywhere: on any error, roll back and decide whether to retry the whole transaction.

Python drivers do this for you if you let them. With psycopg 3 (the current Postgres driver for Python), with conn.transaction(): issues BEGIN, then COMMIT at the end of the block, or ROLLBACK if an exception escapes. One trap: by default "even a simple SELECT will start a transaction", which then stays open until you commit, holding back clean-up (psycopg 3 docs, transactions; section 10 measures the cost).
