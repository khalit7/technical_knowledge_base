4. Isolation levels: what each one lets through, measured

Where the levels come from

The SQL standard (1992) defines four isolation levels by which of three phenomena they forbid: dirty reads, non-repeatable reads and phantoms. Three years later Berenson, Bernstein, Gray and colleagues showed that these definitions are ambiguous and miss whole classes of anomaly, including lost update, read skew and write skew, and that the popular snapshot isolation (each transaction reads one consistent snapshot; a write fails if the row changed since the snapshot) fits none of the four levels (Berenson et al., 1995). Adya's 1999 thesis restated every level as which cycles of dependencies between transactions are allowed (Adya, MIT, 1999), and that is how testers such as Kleppmann's Hermitage suite (2014, github.com/ept/hermitage) and Jepsen describe databases today. The practical lesson: a level's name tells you little; what matters is which anomalies a given database lets through at it.

How to read it
  • Postgres read committed (the default) blocks only dirty reads. Everything else in the table got through, including the lost update.
  • Postgres repeatable read is snapshot isolation. Jepsen's 2020 analysis agrees: "PostgreSQL's 'repeatable read' isolation level is actually snapshot isolation" (Jepsen, PostgreSQL 12.3, 2020-06-12). It stops the lost update with an error, but not write skew in either form, nor the read-only anomaly.
  • Postgres serializable stopped everything, in these runs always by aborting one transaction with SQLSTATE 40001 rather than by making anyone wait (two writes to the same row still wait for each other's row lock first). Your code must retry (section 9).
  • MySQL's default, repeatable read, lost the update that Postgres's repeatable read refused, and let both write skews through. Jepsen's analysis of MySQL 8.0.34 (2023-12-19) found lost updates, read skew and non-repeatable reads at this level and concluded "it isn't clear what MySQL Repeatable Read actually is" (Jepsen, MySQL 8.0.34). Our read skew run was prevented because B only read; Hermitage records MySQL's repeatable read as preventing read skew in read-only transactions only.
  • MySQL serializable works by locking instead: every plain SELECT becomes SELECT ... FOR SHARE when autocommit is off (MySQL 8.4, isolation levels), so conflicting transactions wait for each other, and the lost update and both write skews ended in a deadlock (error 1213) that killed one transaction.

These results agree with Hermitage's published table for both databases. Other databases, from the same table: Oracle's default is read committed and its "serializable" is snapshot isolation, so it allows write skew; SQL Server defaults to a locking read committed; CockroachDB and FoundationDB default to serializable (Hermitage; CockroachDB docs).

How Postgres's serializable works without locking everything

Since PostgreSQL 9.1 (2011), serializable is serializable snapshot isolation (SSI). Transactions still read snapshots and never wait for readers. In addition, Postgres records what each serializable transaction read (in "SIREAD" locks, which block nobody) and watches for a read-write dependency: T1 read something that T2 then wrote. One such dependency is harmless. Two in a row, T1 to T2 to T3, is the "dangerous structure" that every serialization anomaly under snapshot isolation contains (Cahill, Röhm and Fekete, SIGMOD 2008), and Postgres aborts one transaction in it, sometimes when no real anomaly would have followed (a false positive). Ports and Grittner, who built it, report that it performs "only slightly below that of snapshot isolation" and "significantly outperforms" classic two-phase locking on read-heavy workloads (Ports and Grittner, VLDB 2012).

The error messages in the recordings say which case fired: "could not serialize access due to concurrent update" is the simple first-updater-wins rule (you tried to change a row changed since your snapshot); "due to read/write dependencies among transactions", with "Reason code: Canceled on identification as a pivot", is SSI's dangerous structure. Reads are tracked by row, by page or by whole table, coarser when memory runs short, and "a sequential scan will always necessitate a relation-level predicate lock", so a missing index raises the failure rate (Postgres 16, transaction isolation). Guarantees are also only as good as the code: Jepsen's 2020 analysis found a bug that let a write skew through Postgres's serializable in 9.5 to 13 under normal operation, with a fix scheduled for the 13 August 2020 minor releases (same Jepsen report).

Which level to use
  • Read committed (Postgres's default) is right for most single-statement work and for transactions whose every check is folded into its writes (atomic UPDATE ... WHERE, constraints, FOR UPDATE where needed).
  • Repeatable read for anything that reads many rows and needs them consistent: reports, exports, audits, a backup (pg_dump takes one snapshot for this reason).
  • Serializable when a business rule spans rows and you cannot or will not reason about every interleaving: quotas, rotas, inventory, double-booking. Declare read-only transactions READ ONLY (they then cause fewer aborts), keep the retry loop in one place, and keep the transactions short. It does not protect against transactions running at lower levels: every transaction that touches the rule must be serializable.
