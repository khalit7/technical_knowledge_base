What professionals do in production (as of October 2026)

  • Postgres at its default, read committed, plus discipline is what most Postgres applications run: checks folded into writes (UPDATE ... WHERE balance >= 10, then read the row count), constraints for every rule that can be declared, FOR UPDATE where a read must not go stale, and serializable for the few transactions that guard multi-row rules. Teams that choose serializable everywhere (CockroachDB's default, for instance) accept the retry loop as part of every data access path.
  • Know the MySQL difference: code written for MySQL's repeatable read is not protected from lost updates, as recorded in section 4. Use atomic updates or SELECT ... FOR UPDATE; many MySQL shops run read committed for its simpler locking.
  • Short transactions as a rule, enforced by settings: idle_in_transaction_session_timeout on application roles, lock_timeout on migrations, a statement timeout per endpoint, and an alert on the age of the oldest open transaction.
  • One retry helper for 40001 and 40P01, with jitter and a cap, used by every transaction, and idempotency keys at the API edge so that a retried request cannot charge twice.
  • Queues in the database with FOR UPDATE SKIP LOCKED until throughput says otherwise; a single job at a time with an advisory lock.
  • Lock-aware migrations: SET lock_timeout, small steps, retries of the migration rather than of the app.
  • Never a model call inside a transaction. LLM calls take seconds; a transaction held across one holds its row locks and its snapshot for that long, for every request in flight.

Common mistakes

Believing that BEGIN ... COMMIT prevents race conditions
It gives atomicity, not full isolation. At Postgres's default level a transaction-wrapped read-then-write still lost an update (section 3, lost update, read committed).
Reading, computing in Python, writing back
The lost update's shape. Write SET balance = balance - 10 instead of SET balance = 20, or lock the row when you read it.
Ignoring the affected-row count
UPDATE ... WHERE balance >= 10 that changed 0 rows means "not enough credits"; an optimistic update that changed 0 rows means "someone else wrote first". Code that does not read the count turns both into silent bugs.
Assuming "repeatable read" means the same thing everywhere
Postgres's is snapshot isolation and refuses lost updates; MySQL's let one through on this page; the SQL standard's allows phantoms. Test the anomaly you care about on your database (the scripts in src/measure/ are a starting point).
Using FOR UPDATE to protect a rule over rows that do not exist yet
The quota case: nothing to lock. Materialise the conflict in a counter row, lock a parent row, or use serializable.
Switching to serializable without a retry loop
Users then see the 40001 errors. Retry the whole transaction, not the failed statement, and keep external calls out of it.
Mixing isolation levels for one rule
Serializable's guarantee holds among serializable transactions. One code path at read committed that writes the same rows can still produce the anomaly.
Leaving a transaction open
A Python driver starts a transaction on the first query, even a SELECT; a script or notebook that never commits holds back VACUUM for the whole database (section 10 measured 20,000 dead versions kept alive by one idle session).
Taking locks in different orders in different code paths
The recipe for deadlocks (section 7). Sort the ids before locking several rows.
Running a migration without lock_timeout
One long read in front of it, and every query on the table queues behind the migration (section 6).
Turning fsync off for speed
Corruption after a power cut. If commits are too slow, batch more work per transaction, rely on group commit, or use synchronous_commit = off for writes you can afford to lose.

Glossary

ACID: atomicity, consistency, isolation, durability; the four promises of a transaction.
Anomaly: an outcome no one-at-a-time order of the transactions could produce.
Autocommit: each statement outside BEGIN is its own transaction.
Autovacuum: Postgres's background process that runs VACUUM and ANALYZE.
Bloat: space in a table or index taken by dead or reusable versions.
Concurrency: statements of several sessions interleaving.
Deadlock: transactions each waiting for a lock another holds; one is killed (40P01, MySQL 1213).
Dirty read: reading another transaction's uncommitted change.
Flush (fsync): forcing written data from memory to the disk; the cost of durability.
HOT update: a new row version on the same page with no index change; prunable without VACUUM.
Idempotency key: a client-chosen key that makes a repeated request return the first result instead of acting twice.
Isolation level: the setting that decides which anomalies the database still allows.
Lock: a claim that makes conflicting claims wait until commit or rollback.
Lost update: two read-modify-write cycles on one value; the second overwrites the first.
MVCC: multi-version concurrency control; readers see old versions while writers make new ones.
Non-repeatable read: the same row read twice in one transaction gives two values.
Optimistic concurrency: no lock; check at write time that the row did not change (version column).
Phantom: a repeated query with a condition returns new or missing rows.
Read skew: reading related rows from two different moments.
Serialization anomaly: any anomaly, including write skew, that only serializable prevents.
Session: one connection to the database; runs one transaction at a time.
Snapshot: which transactions had committed at one moment, xmin:xmax:list.
Snapshot isolation: one snapshot per transaction, writes refused if the row changed since; Postgres's repeatable read.
SSI: serializable snapshot isolation; Postgres's serializable since 9.1.
Transaction: statements treated as one unit: BEGIN, then COMMIT or ROLLBACK.
Transaction id (xid): the number a writing Postgres transaction gets.
Version column: a counter checked and incremented by every update (compare-and-set).
WAL: write-ahead log; changes are logged and flushed before commit returns.
Write skew: two transactions read the same rows and write different ones, together breaking a rule.
xmin, xmax: the ids of the transactions that created and deleted a row version.
