6. Locks: making the other transaction wait

A lock is a claim a transaction holds on something (a row, a table, a number) that makes conflicting claims wait until it commits or rolls back. MVCC removed locks from plain reads; writes and explicit locking reads still take them. Postgres has two families (Postgres 16, explicit locking).

Row locks

Every UPDATE and DELETE locks the rows it changes until the end of the transaction; that is why, in section 3, the second atomic UPDATE of Ines's balance waited for the first. You can take the same lock on a read:

ClauseWhat it doesUse it for
SELECT ... FOR UPDATEExclusive row lock: blocks other FOR UPDATE, UPDATE, DELETE on those rows (plain reads still pass)Read-then-write on the rows you read (the lost update fix)
FOR NO KEY UPDATEWeaker: does not block FOR KEY SHARE, which foreign-key checks take. A plain UPDATE that changes no key column takes this oneMostly automatic
FOR SHARE / FOR KEY SHAREShared: others may also share-lock, nobody may change"This row must not change until I commit" (a parent row while you insert children)
... NOWAITFail at once with SQLSTATE 55P03 instead of waitingInteractive actions where waiting is worse than "try again"
... SKIP LOCKEDSilently skip rows another transaction has lockedMany workers taking jobs from one queue table

The job queue is the classic use. The chat product keeps a jobs table (summarise a chat, index an uploaded file); several workers each run SELECT id FROM jobs WHERE status = 'queued' ORDER BY id LIMIT 1 FOR UPDATE. Recorded on Postgres with two workers measured:

With plain FOR UPDATE worker B waited for A's whole job, then got job 2: the workers run one at a time. With SKIP LOCKED B took job 2 at once. The documentation's warning is the reason it is for queues only: "skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work" (Postgres 16, the locking clause). Table locks and the lock queue

Every statement also takes a lock on each table it touches, in one of eight modes. Ordinary reads and writes take weak modes that never conflict with each other. Many ALTER TABLE forms, DROP, TRUNCATE and VACUUM FULL take ACCESS EXCLUSIVE, and "only an ACCESS EXCLUSIVE lock blocks a SELECT" (same explicit-locking page). The trap is the queue: a lock request that must wait queues, and every later request that conflicts with it queues behind it, even if it would not have conflicted with the holder. An analytics query left its transaction open; the migration's ALTER TABLE waited for it; and an ordinary one-row read by session C, which needs only the weakest lock, waited behind the migration until the analytics transaction ended. In production, C is every request of your API. This is how GoCardless had about 15 seconds of API downtime from a migration that should have been instant: "Set lock_timeout in your migration scripts to a pause your app can tolerate. It's better to abort a deploy than take your application down" (GoCardless engineering blog, Chris Sinjakli). With lock_timeout the migration gave up after 200 ms with SQLSTATE 55P03, and C never waited. Running migrations safely is on {{SQL and data modelling|n:3ef5c17b0d0d813980dcd474e19f6c3f}}.

Advisory locks: a lock on a number

Sometimes the thing to protect is not a row: "only one summariser runs per user at a time". Postgres lets you lock any 64-bit number, with a meaning only your application knows: pg_advisory_xact_lock(7) waits for and holds the lock until the transaction ends, pg_try_advisory_lock(7) returns false at once if someone holds it. Session-level advisory locks survive ROLLBACK and must be released explicitly. Recorded: A's try returned true, B's returned false until A released it measured. A common production use is making sure only one instance of a scheduled job or migration runs.

What locks cost
Waiting. Every lock turns a conflict into latency for someone, and the lock is held until COMMIT, not until the statement ends: whatever your code does between the locking statement and the commit (a model call, a network request) is time everyone else waits. And two transactions can each wait for the other, which is the next section.

7. Deadlocks: waiting for each other forever

A deadlock is a cycle of waits: A holds a lock B needs while waiting for a lock B holds. Neither can move. It needs nothing unusual, just two transactions touching the same rows in opposite orders: A transfers 5 credits from Ines (7) to Quinn (12), B transfers 3 from Quinn to Ines, at the same time measured:

Postgres checks for a cycle only after a lock wait has lasted deadlock_timeout (1 second by default), because the check is expensive and most waits end on their own. It then aborts one transaction with SQLSTATE 40P01 and a detail that names both processes; which one is chosen "is difficult to predict and should not be relied upon" (Postgres 16, deadlocks). In the recording B was killed after 1.0 s and A's update went through. MySQL detects deadlocks immediately by default (innodb_deadlock_detect) and returns error 1213, as in its serializable runs in section 4.

How professionals avoid them
  • Take locks in one global order. The documentation: "the best defense against deadlocks is generally to avoid them by being certain that all applications using a database acquire locks on multiple objects in a consistent order". The second recording locks both credit rows lowest id first with one SELECT ... ORDER BY user_id FOR UPDATE: B simply waits, and both transfers complete.
  • Keep transactions short, so the window for a cycle is small.
  • Retry on 40P01 like a serialization failure: a deadlock victim's transaction did nothing, so running it again is safe if the work is idempotent (section 9).
  • Watch for them: log_lock_waits = on logs every wait longer than deadlock_timeout, and pg_stat_database.deadlocks counts them.
