3. The anomalies: eight ways two transactions collide

An anomaly is an outcome that could not have happened if the transactions had run one after the other, in some order. Each one below is a real recording: two (or three) live sessions on a real database, driven step by step by a script that hands each session one statement, waits up to half a second, and if the statement has not finished records it as blocked (and asks Postgres what it is waiting for) before moving on. A statement that finishes later, because the other session committed or a deadlock was found, is shown in the step during which it finished. The scripts are in src/measure/.

How to read a recording: one column per session, one row per step; the highlighted cell is the statement issued at that step, and what it returned is under it in grey. A dashed red border means the statement is waiting for a lock. The chips under each recording are every isolation level on both databases: red means the anomaly happened, green means it was prevented (and how). Click a chip to see that run. The {{Isolation lab|#t-lab}} steps through any of them one statement at a time.

1. Dirty read: reading what was never committed

Session B reads a change that session A has made but not committed, and A then rolls back. B has acted on data that never existed. Here tab A debits all 30 of Ines's credits for a long reply, the model call fails, and A rolls back; meanwhile a billing check in B reads the balance.

Postgres never shows uncommitted data, at any level: it runs READ UNCOMMITTED as read committed, "the only sensible way to map the standard isolation levels to PostgreSQL's multiversion concurrency control architecture" (Postgres 16, transaction isolation). MySQL means it: at READ UNCOMMITTED, B read 0 measured.

2. Non-repeatable read: the same row, two values

B reads a row, A changes it and commits, B reads the row again in the same transaction and gets a different value. An invoice job that reads Ines's balance for the header and again for the footer prints two numbers.

At read committed every statement sees everything committed before it started, so the second read sees A's commit. At repeatable read the whole transaction reads one snapshot taken at its first statement.

3. Phantom: rows appear in a range

The same as a non-repeatable read, but for a condition instead of a row: B counts Ines's messages today, A inserts one and commits, B counts again and gets one more. The new row is the phantom. The SQL standard allows phantoms at repeatable read; Postgres's repeatable read prevents them because a snapshot hides new rows too (the documentation's table says "allowed, but not in PG"); MySQL's plain reads at repeatable read also use a snapshot, so they did not see it either measured.

4. Lost update: read, compute in the app, write back

Section 1's bug. A and B both read 30; A writes 20 and commits; B writes 25 over it. Berenson and colleagues named it P4 in "A Critique of ANSI SQL Isolation Levels" (Berenson et al., 1995), the paper that showed the SQL standard's definitions miss it.

This is the first place the two databases disagree. At repeatable read, Postgres refused B's write: "could not serialize access due to concurrent update" (SQLSTATE 40001), because B tried to change a row that a transaction committed after B's snapshot had already changed. MySQL at repeatable read let B's write through and lost A's 10 credits measured: InnoDB's UPDATE always works on the latest committed row, not on the snapshot, and does not check that the row changed since the transaction's snapshot (its manual: the snapshot "applies to SELECT statements within a transaction, not necessarily to DML statements", MySQL 8.4, consistent reads). Two fixes work everywhere and are the chips marked fix: one atomic UPDATE ... SET balance = balance - 10, or SELECT ... FOR UPDATE before computing.

5. Read skew: two rows from two different moments

A moves 10 credits from Ines (user 7) to Quinn (user 12), the transfer from the root's SQL playground lesson 10; the total is always 50. B, an audit job, reads Ines's balance before the transfer and Quinn's after it, and adds them up to 60. Every row B read was committed; the mix is from two moments. Backups, exports and reports that run for minutes at read committed are exposed to exactly this.

6. Write skew: two valid decisions, one broken rule

The chat product's incident rota needs at least one engineer on call. Ana and Raj are both on call and both feel ill. Each runs "if someone else is on call, take me off": each counts 2, each updates their own row. No row is written twice, so no lock conflicts and no update is lost, yet nobody is on call. This is the on-call doctors example from Kleppmann's Designing Data-Intensive Applications; Berenson et al. named the pattern A5B.

Repeatable read does not help: both snapshots honestly showed 2. Only serializable caught it on Postgres, at B's COMMIT, with "could not serialize access due to read/write dependencies among transactions" (SQLSTATE 40001). Or lock the rows you read: SELECT ... FROM oncall WHERE on_call FOR UPDATE makes the second engineer wait, then see 1 measured.

7. Write skew on a quota: the row that does not exist yet

Ines may send 3 messages a day and has sent 2. Two tabs each count today's messages, see 2, and insert one: 4 messages. The same shape as the rota, with one twist that defeats the usual fix: there is no row to lock. FOR UPDATE on the count would lock the two existing messages, while the conflict is over a third row that neither transaction can see yet.

Three fixes, best first. Materialise the conflict (Kleppmann's term): keep a daily_usage(user_id, day, n) row and make the check and the increment one statement, UPDATE daily_usage SET n = n + 1 WHERE user_id = 7 AND day = ... AND n < 3; zero rows changed means over quota, and two tabs now collide on one row, which read committed handles (section 1's atomic update). Lock a row both must touch: SELECT ... FROM users WHERE id = 7 FOR UPDATE first (the chip marked fix). Use serializable and retry, which caught it on Postgres measured. MySQL's gap locks, its answer to phantoms, protect only locking reads; the plain SELECT count(*) took none, so MySQL's repeatable read let the fourth message through too.

8. A serialization anomaly with a read-only transaction

The subtlest one, found by Fekete, O'Neil and O'Neil in 2004 ("A Read-Only Transaction Anomaly Under Snapshot Isolation") and used on the PostgreSQL wiki as the "deposit report" (PostgreSQL wiki, SSI). Credit purchases are filed under the open billing batch. A, a purchase, reads "batch 1 is open". B closes batch 1 and commits. C, a report, sees batch 1 closed and totals it: 100. A then files its purchase in batch 1 and commits: batch 1 now totals 150, after a report on the closed batch said 100. Remove the report and the history is fine; the read-only transaction is what makes it impossible.

A serialization anomaly is the general name for any result that no one-at-a-time order could produce; write skew is the common case. Only serializable prevents all of them: Postgres aborted the purchase A (SQLSTATE 40001), so its retry files under batch 2 measured.
