8. Optimistic concurrency: check at write time instead of locking

Locks are pessimistic: they assume a conflict and make others wait in advance. Optimistic concurrency control assumes there will be no conflict, lets everyone read freely, and checks at write time that nobody changed the row in between. The usual form is a version column and a compare-and-set: read the row with its version, then UPDATE ... SET ..., version = version + 1 WHERE id = ... AND version = <the version I read>. If someone else wrote first, the version moved and the update changes 0 rows; you re-read and try again. No transaction is held open between the read and the write. Recorded on Postgres measured:

B's first write reported UPDATE 0, so B re-read (20, version 2) and wrote 15. The final row is balance 15, version 3: both spends counted, nobody waited.

This is what web applications do when the read and the write are separated by a person: the user opens a chat's settings, edits the title for a minute, and saves. Holding a transaction (and a lock) open for that minute is out of the question; the version column catches the case where someone else saved in between. Over HTTP the same idea is the ETag header and a conditional If-Match request ({{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}). ORMs build it in: SQLAlchemy's version_id_col adds the version check to every UPDATE and raises StaleDataError when it matches zero rows (SQLAlchemy 2.0 docs); Rails does the same with a lock_version column.

What it costs, and when not to use it
Wasted work under contention: every lost race is a re-read and a retry. It shines when conflicts are rare (a user editing their own settings) and does badly on a hot row that many writers hit at once (a shared counter, a team's credit pool), where a lock or one atomic UPDATE ... SET n = n + 1 wins. Always check the affected-row count: an optimistic update that ignores UPDATE 0 is just the lost update again.

9. Retries in application code, and what serializable costs

A real retry loop

Serializable and repeatable read refuse a conflicting transaction with SQLSTATE 40001, a deadlock victim gets 40P01, and the Postgres documentation is direct about it: the application "should abort the current transaction and retry the whole transaction from the beginning" (Postgres 16, transaction isolation). The whole transaction, including its reads, because the decisions were made on data that has changed. This is the loop the benchmark below ran, unchanged, with psycopg 3:

import random, time
from psycopg import errors

RETRYABLE = (errors.SerializationFailure, errors.DeadlockDetected)   # SQLSTATE 40001 and 40P01

def run_in_transaction(conn, work, max_attempts=10):
    """Run work(conn) in a transaction; on a serialization failure or deadlock, roll back and run it again."""
    for attempt in range(1, max_attempts + 1):
        try:
            with conn.transaction():          # BEGIN ... COMMIT, or ROLLBACK if work raises
                return work(conn), attempt
        except RETRYABLE:
            if attempt == max_attempts:
                raise
            time.sleep(random.uniform(0, min(0.05, 0.001 * 2 ** attempt)))   # full jitter, capped

conn.isolation_level = psycopg.IsolationLevel.SERIALIZABLE
run_in_transaction(conn, lambda c: spend(c, user_id=7, cost=10))

Four rules make it safe. Everything inside work must be repeatable: no model call, no e-mail, no payment inside the transaction, because a retry would do it twice; do the slow or external part before or after, and keep only database work inside. Retry only the retryable codes; a constraint violation will fail again. Wait a random, growing time between attempts (exponential backoff with jitter) so that the colliding transactions do not collide again in lock-step. Cap the attempts and surface an error, because under a hot spot some transaction will keep losing.

When the external step must happen once (charge a card, then record it), the retry belongs to the whole request, and the tool is an idempotency key: the client sends a unique key with the request, the server stores the key and the result in the same transaction as the work, and a repeated key returns the stored result instead of acting again. The pattern, with "atomic phases" between external calls, is Brandur Leach's "Implementing Stripe-like Idempotency Keys in Postgres" (brandur.org, 2017-10-27), and it is taught in full on {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}} (section 10).

Measured: the price of correctness under contention

The chat product's "spend one credit and save the message" transaction, run by 2, 8 and 32 concurrent clients for 8 seconds each on Postgres 16.2, four ways: read committed with the naive read-then-write (section 1's code), read committed with one atomic UPDATE, read committed with FOR UPDATE, and serializable running the naive code inside the retry loop above. Two contention levels: every client spends from one of 4 hot users, or from 10,000 users measured.

What it says. With the load spread over 10,000 users, correctness was free: all four ways ran at about the same speed, and serializable retried about one transaction in a hundred or fewer. On 4 hot users it was not: serializable fell well behind the atomic UPDATE, with more than one retry per commit and hundreds of transactions that lost ten times in a row at 32 clients, while the naive code was fast and lost tens of thousands of updates. The atomic UPDATE was fastest-correct under contention because the row lock is held only from the UPDATE to the COMMIT, and nothing is computed in between. Even with only 2 clients, dozens of serializable transactions failed ten attempts in a row. A debugging rerun logged the errors: most were SSI's "Canceled on identification as a pivot", not the simple concurrent-update case. With only four users, every read lands on one index page, and Postgres may track reads by page rather than by row, so transactions can look dependent when they are not; this run did not separate that from genuine conflicts on the same user.

One 32-client serializable run (10,000 users) on Postgres 16.2 stalled for over nine minutes: every session waited on an internal lock named SerializableFinishedList while one backend used CPU at COMMIT. Two reruns on 16.2 and one on 16.15 did not stall, so the cause is unconfirmed; the benchmark now has a watchdog and the figures shown are from a complete rerun. It is a reminder that serializable's bookkeeping is real work inside the server.
