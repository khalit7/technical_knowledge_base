5. MVCC: how a database isolates without stopping everyone

The problem

The simplest way to isolate transactions is to lock everything each one reads or writes until it commits, so everyone else waits. That was how databases worked for decades (two-phase locking), and it makes a long report block every writer it touches. Postgres, MySQL's InnoDB, Oracle and most modern databases instead keep several versions of a row, so a reader can see an older version while a writer prepares a newer one: multi-version concurrency control (MVCC). In the Postgres documentation's words, "reading never blocks writing and writing never blocks reading" (Postgres 16, MVCC introduction).

Row versions in Postgres: xmin and xmax

Every transaction that writes gets a number, its transaction id (xid), from a counter. Every row version (Postgres calls it a tuple) carries two hidden fields: xmin, the xid that created it, and xmax, the xid that deleted or replaced it (0 if none). An UPDATE sets xmax on the old version and writes a new version with xmin = its own xid. You can see them: SELECT xmin, xmax, * FROM credits.

A snapshot is a note of which transactions had committed at one moment, written xmin:xmax:list: every xid below the first number had finished, every xid from the second number on had not started, and the list names those in between still running. A version is visible to a snapshot if its creator had committed by then and its deleter had not. At read committed each statement takes a new snapshot; at repeatable read and serializable the first statement's snapshot serves the whole transaction.

Three things the recording shows. At read committed, B's UPDATE ran with a fresh snapshot that includes A's commit, and wrote the value it had computed from an old read: the database did exactly what it was told. With FOR UPDATE, A's lock is itself written into the row (xmax set to A's xid, marked lock-only), and B waits on A's transaction, then reads the new version. Under serializable, B's snapshot is fixed at its first read, so its update finds that the version it can see has already been replaced by a transaction it cannot see, and Postgres refuses.

Why VACUUM exists

Old versions are not removed when they stop being current, because some transaction with an old snapshot might still need them. Once no running transaction can see a dead version, its space can be reused, and that is VACUUM's job (run automatically by autovacuum). It also freezes very old versions so the 32-bit transaction counter can wrap around safely; skipping that for about 2 billion transactions makes Postgres refuse writes, which is what took Sentry's writes down for hours in July 2015 (Postgres 16, routine vacuuming; Sentry, 2015). Plain VACUUM makes space reusable but does not give it back to the operating system; the table stays large, which is called bloat. Tuning autovacuum, freezing and fixing bloat belong to {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}}; the part that is about transactions, a long transaction stopping clean-up, is measured in section 10.

Updating a row only within its own page, with no indexed column changed, is a HOT update (heap-only tuple): no index entry is added, and later readers can prune the dead versions on that page without waiting for VACUUM. That is why section 10's control run updated one row 20,000 times and the table never grew past one page.
