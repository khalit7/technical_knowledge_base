About 40 minutes to read, plus the optional animations and the {{Isolation lab|#t-lab}}. It starts from zero: every term is explained where it first appears and collected in the Glossary. Results marked measured were recorded for this page on a laptop (an Apple M1 Pro) against a real PostgreSQL 16.2 and a real MySQL 9.7.2, with two or three live sessions; anything marked illustrative is made up to show a shape.

A web service runs the same code for many users at once. Most of the time those requests touch different rows and never meet. This page is about the moments they do meet: two tabs spending the same user's last credits, two engineers signing off the same on-call rota, a report reading balances while a transfer moves them. The database's answer is the transaction, and the hard part of a transaction is not the word but its isolation level: which of these collisions the database still lets through.

The five habits of a professional
  1. Write a check and the change it guards as one statement where you can: UPDATE credits SET balance = balance - 10 WHERE user_id = 7 AND balance >= 10, then read how many rows changed.
  2. Know your database's default isolation level and what it lets through. Postgres defaults to read committed; MySQL defaults to repeatable read, which on this laptop still lost an update that Postgres's repeatable read refused (section 4).
  3. When a rule spans several rows, use serializable (Postgres) and retry on SQLSTATE 40001, or lock one row that every competing transaction must lock first.
  4. Keep transactions short: never hold one open across a call to a language model, a payment provider or a user's think time.
  5. Make every retried operation idempotent, so running it twice does no harm.
