10. Long transactions and what they cost

A transaction that stays open costs the whole database, not just its own session, in three ways: it holds its locks (section 6), it holds back clean-up of old row versions, and in Postgres it can hold back transaction-id freezing. The second is invisible until it is large, so it was measured: one session opened a repeatable read transaction, read one row and then did nothing (a forgotten BEGIN, a notebook left open, a request stuck on a model call), while another session updated Ines's balance 20,000 times. Then the same 20,000 updates with no transaction left open, as the control measured:

With nothing held open, each update's old version was pruned on the spot (section 5's HOT updates) and the table never grew past one 8 KB page. With one idle transaction holding an old snapshot, not one of the 20,000 dead versions could be removed: VACUUM VERBOSE reported them as "dead but not yet removable", the table grew to over a hundred pages, the same updates took more than twice as long, and reading Ines's one row became several times slower, because every read now walks a chain of dead versions. After the idle transaction ended, VACUUM removed all 20,000, but the file stayed the same size: the space is reusable, not returned. The same thing on a live server, with autovacuum on: {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} (section 6) ran 1,500 updates a second against a 100,000-row table and left one session idle in a transaction; autovacuum kept firing every time its trigger was passed and removed nothing, so dead rows and table size climbed in a straight line until the session ended measured there.

What professionals set (Postgres)
  • idle_in_transaction_session_timeout: ends a session that sits idle inside an open transaction; the documentation notes it is for exactly this, because "an open transaction prevents vacuuming away recently-dead tuples" (Postgres 17, client settings).
  • transaction_timeout (new in PostgreSQL 17, 2024): ends any transaction that runs longer than the limit, busy or idle. statement_timeout caps one statement; lock_timeout caps one lock wait. All default to 0 (off); the documentation advises setting statement_timeout, lock_timeout and transaction_timeout per role, session or transaction rather than in postgresql.conf, "because it would affect all sessions".
  • A dashboard query for the oldest open transactions: SELECT pid, state, now() - xact_start AS age, left(query, 60) FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY age DESC LIMIT 5. Alert when the oldest is minutes old.
  • In application code: never call a language model, a payment provider or anything slow while a transaction is open. Read, commit, call the model, then write the result in a new short transaction (with the checks of sections 3 and 8 at write time).

Replicas add a twist: a long query on a read replica either gets cancelled ("canceling statement due to conflict with recovery") or, with hot_standby_feedback = on, holds back clean-up on the primary as if it ran there. That trade-off is on {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} and {{Scaling a database|n:3ef5c17b0d0d81f0aaceee1e21b972be}}.

11. Transactions across more than one database

Everything so far happened inside one database. The chat product soon has more than one place to write: Postgres for credits, a search index for messages, a queue for background jobs, a payment provider. No single COMMIT covers them, and three answers exist.

Two-phase commit (2PC)

A coordinator asks every participant to prepare (do everything but the final commit, and promise to be able to commit), then tells all of them to commit. Postgres supports it with PREPARE TRANSACTION and COMMIT PREPARED, off by default (max_prepared_transactions = 0) (Postgres 16, PREPARE TRANSACTION). Its cost is blocking: a participant that has prepared holds its locks until it hears from the coordinator, and if the coordinator dies, it waits. A forgotten prepared transaction also holds back VACUUM like section 10's idle session.

Sagas

Give up atomicity across systems: run a sequence of local transactions, and if a later step fails, run compensating transactions that undo the earlier ones (refund the credits). Each step is short and local; the price is that other requests can see the in-between states, and every step needs an undo.

The transactional outbox

Write the business change and a row in an outbox table in one local transaction; a separate process publishes the outbox rows to the queue afterwards, at least once. This turns "write to two systems" into "write to one database", and is the usual answer for database plus queue.

All three, with measured crash and redelivery behaviour on a real Postgres, are taught on {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}} (sections on the outbox and on sagas against two-phase commit). Databases that spread one logical database over many machines and still offer serializable transactions (Spanner, CockroachDB) use consensus and careful clocks under the hood: see {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}} and {{Scaling a database|n:3ef5c17b0d0d81f0aaceee1e21b972be}}.
