Storage engines and indexes in one screen

It assumes only the parent page's first four sections; every new term is explained where it first appears and collected in the Glossary. Numbers marked measured were measured for this page on a laptop (Apple M1 Pro, 16 GB, internal SSD, PostgreSQL 16.2 and 18.6, RocksDB through the rocksdict binding, 2026-10-04; other jobs shared the machine, so treat times as plus or minus 30%); numbers marked illustrative are drawn to explain, not measured.

A storage engine is the part of a database that decides how rows are laid out on disk, how a change is made durable, and how one row is found again without reading everything. Two designs dominate: the B-tree (Postgres, MySQL, SQLite, SQL Server) updates sorted pages in place; the LSM-tree (RocksDB, Cassandra, ScyllaDB) appends changes and merges them later. Both sit on the same two tools: fixed-size pages cached in memory, and a write-ahead log that makes a commit survive a power cut.

The running example is the parent page's chat product: one table, messages, with a million rows (id, chat_id, role, model, tokens, content, created_at), generated by the same script with the same seed as the root's measurements, so the numbers agree: 19,235 pages of 8 KB, 157 MB, and a 9.3 MB index on chat_id measured.

1. Pages: how a table sits on disk

The problem appears

A disk (or SSD) does not hand out single rows. It reads and writes blocks of a few kilobytes, and one random read from a fast SSD takes about 100 microseconds, roughly a thousand times longer than reading memory (the root page's section 4 has the measurements). So a database must decide which rows share a block, because rows that share a block are fetched together for the price of one read.

The idea: fixed-size pages, and a row address

Postgres stores each table and each index as its own file, under the data directory at base/<database id>/<file number> (the messages table is base/16384/16460 measured). A file larger than 1 GB is split into 1 GB segment files (Postgres file layout). Inside, the file is an array of pages (also called blocks) of 8 KB each, numbered from 0, and Postgres always reads and writes a whole page (Postgres page layout). Our million messages fill 19,235 pages; MySQL's InnoDB uses 16 KB pages and SQLite 4 KB by default, the same idea at another size.

Every row version stored in a table page is called a tuple, and every tuple has an address, the ctid: (page number, slot number). The first message lives at (0,1): page 0, slot 1. Indexes (section 5) store these addresses, which is how an index lookup jumps straight to the right page.

Inside one page

A page is laid out from both ends. A 24-byte page header sits at the start (where free space begins and ends, the page's position in the log). After it comes an array of 4-byte line pointers, one per slot, each saying where its tuple sits and how long it is. Tuples are written from the end of the page backwards. Free space is the gap in the middle; the page is full when the two meet. This is page 0 of the messages table, drawn to scale from the numbers Postgres reports about itself (page_header in the pageinspect extension) measured:

Header, 24 bytes52 line pointers, 208 bytesFree, 88 bytes52 tuples, 7,872 bytes

lower = 232 (24 + 52 x 4: where free space starts), upper = 320 (where the tuples start), page size 8,192. Every table page here holds between 34 and 58 messages, 52 on average, because content length varies measured. The slot-by-slot view is in Inside real pages.

The line-pointer indirection is what lets Postgres move a tuple inside its page (to squeeze out a hole) without changing its ctid, so no index needs updating.

The tuple header: 23 bytes before your data

Each tuple starts with a 23-byte header (padded to 24 here), before any column value (page layout docs). The fields that matter:

  • xmin: the number of the transaction that created this version; xmax: the transaction that deleted or replaced it (0 if none). Together they decide which transactions can see this version: this is MVCC, the multi-version scheme the parent's section 3 introduced and Transactions and concurrency owns.
  • t_ctid: for a current version its own address; for an old version, the address of its replacement, so readers can follow the chain.
  • infomask bits: flags such as "has nulls" (then a null bitmap follows) and hint bits that cache whether xmin and xmax committed.

So a message whose data is about 90 bytes takes about 120 to 200 bytes on the page: the 24-byte header, alignment padding to 8-byte boundaries, and the 4-byte line pointer. On a narrow table the overhead dominates: a table of a single bigint column uses 36 to 40 bytes per 8-byte value derived (24 + 8, aligned, plus 4).

An update is a new tuple

Postgres never overwrites a row in place. An UPDATE writes a new tuple and stamps the old one's xmax. We changed the token count of message 60, on a full page measured: the old tuple at (1,8) got xmax = 735 and a t_ctid pointing to (19234,35), the new version at the end of the table, because page 1 had no room. Every index on the table then needs a new entry pointing to (19234,35), even though no indexed column changed.

Postgres avoids that when it can, with a HOT update (heap-only tuple): if no indexed column changed and the new version fits on the same page, the old tuple points to the new one inside the page and the indexes are not touched (HOT docs). On a copy of the table created with fillfactor = 90 (inserts stop at 90% full, leaving 10% of each page for updates), the same update stayed on page 0: old tuple (0,10) flagged "HOT updated", new tuple (0,48) flagged "heap only", and the statistics counted n_tup_hot_upd = 1 against 0 on the full table measured. A lower fillfactor is the standard setting for tables that are updated often.

Big values: TOAST

A tuple must fit in a page, so a row wider than about 2 KB has its large values compressed and, if still too big, cut into chunks stored in a side table; the main tuple keeps a pointer. This is TOAST (TOAST docs: threshold "normally 2 kB", values up to 1 GB). Compression is pglz by default; lz4 has been available since Postgres 14 (default_toast_compression). Two 13 KB assistant answers measured: a repetitive one (the same sentence 600 times) was compressed to 186 bytes and stayed in the page; one made of hexadecimal hashes barely compresses, so its 13,199 bytes went out to the TOAST table (16 KB). Long LLM answers are exactly this case: reading content costs extra page reads, and SELECT * pays them even when you do not need the text.

Two small maps beside every table

  • The free space map (file suffix _fsm) records about how much room each page has, one byte per page in 32-byte steps, as a small tree, so an insert finds a page with room without scanning (FSM docs). For 19,235 pages it is 56 KB measured. VACUUM keeps it up to date.
  • The visibility map (suffix _vm) keeps two bits per page: all-visible (every tuple is visible to every transaction) and all-frozen (VM docs). VACUUM skips all-visible pages, and an index-only scan (answering from the index alone) can skip the table page only when its bit is set. After a VACUUM, 19,234 of 19,235 pages were all-visible; deleting rows on pages 0 and 1 cleared their bits measured. That is why index-only scans slow down on a table that has not been vacuumed: the root's Query plans tab measures it (case 7, before and after VACUUM).
What pages cost
Reading one 150-byte row costs a whole 8 KB page read, so rows that are read together should live together (section 8 shows how InnoDB and clustering do that). About 24 + 4 bytes of every row are bookkeeping. Updates leave dead tuples that only VACUUM reclaims (Running Postgres in production owns VACUUM tuning).

2. The buffer pool, and the operating system's cache under it

The problem appears

Opening chat 42000 needs about a dozen pages (the root measured 12 page touches for its 6 messages). If every one came from the SSD at about 100 microseconds, a busy server doing thousands of lookups a second would spend most of its time waiting on the disk, re-reading the same popular pages (the top levels of every index, the newest messages) again and again.

The idea: keep hot pages in memory, evict the cold ones

The buffer pool is a fixed area of RAM divided into 8 KB slots (buffers), plus a hash table from "file, page number" to slot. In Postgres it is shared_buffers, 128 MB by default; the docs suggest starting at 25% of RAM on a dedicated server and say more than 40% is unlikely to help, "because PostgreSQL also relies on the operating system cache" (resource settings). Every page access goes through it: a hit costs a memory lookup; a miss must pick a victim slot (writing it out first if it was changed, or dirty), then read the page in.

Which slot to evict? Keeping exact "least recently used" order would need a lock on a shared list for every access, so Postgres uses a clock sweep (buffer manager README): each buffer has a usage count, raised by one on every access up to a cap of 5 (BM_MAX_USAGE_COUNT in buf_internals.h). A "clock hand" walks round the buffers; each buffer it passes loses one point, and the first one found at zero is evicted. Pages used often survive several sweeps; a page read once is gone after one.

illustrative Eight buffers and a scripted list of page requests: the index root and an inner page are asked for often; table pages once each. The rule (raise to at most 5 on access, lower by one as the hand passes, evict at zero) is the real one; the real pool has 16,384 buffers at 128 MB.

On the real server, after a mixed workload, the 611 buffers in use had usage counts 1: 154, 2: 122, 3: 90, 4: 54, 5: 191 measured with the pg_buffercache extension: a quarter of them were touched only once, while a hot set of 191 (index upper levels, catalog pages) sat at the cap.

A big scan must not flush the cache: ring buffers

A full scan of a large table would push every hot page out for pages it will never read again. So a sequential scan of a table larger than a quarter of shared_buffers reuses a small private ring of 256 kB (32 buffers); VACUUM uses a 2 MB ring and bulk writes 16 MB (README, sizes in freelist.c). Measured on the 157 MB table with a 128 MB pool, after a restart measured: a full scan read all 19,235 pages and left exactly 32 of them in shared_buffers; a second scan found only those 32 and "read" the other 19,203 again. Both scans took about 74 ms because every one of those reads was served by the operating system's cache (next paragraph), not by the SSD; the root's Query plans tab (case 8) measures a truly cold read.

Double buffering: the operating system caches the same pages

A Postgres "read" is a normal file read, so the operating system keeps its own copy of recently read file blocks in otherwise unused RAM (the page cache). A page can therefore be cached twice, once in shared_buffers and once in the page cache: double buffering. Postgres accepts it and leans on the OS cache (hence the modest 25%); the planner's effective_cache_size (default 4 GB) tells it how much the two caches hold together. InnoDB takes the other road: a large buffer pool (up to 80% of memory on a dedicated server) and, since MySQL 8.4, O_DIRECT on Linux so its reads bypass the OS cache (InnoDB buffer pool, 8.4 defaults). Postgres 18 added asynchronous I/O (io_method, default worker, or io_uring on Linux builds), which lets a scan queue many reads at once rather than one at a time (PG 18 release notes).

What the cache costs, and the cliff
RAM. The hit ratio is the strongest single predictor of OLTP latency, and it does not degrade smoothly: while the working set (the pages your traffic touches) fits in RAM, almost every access is a memory hit; once it does not, a fraction of accesses each pay a disk read, a hundred to a thousand times slower, and p99 latency changes character. Watch blks_hit against blks_read in pg_stat_database; the root's Query plans tab measures the same query cold and warm (case 8).

3. The write-ahead log: what is written, when, and what it costs

The problem appears

A commit must survive a power cut the moment the database says "saved". Writing every changed page to its place on disk at commit time would mean several random writes per transaction, and a crash halfway through would leave some pages new and some old. The parent page's section 4 introduced the fix, the write-ahead log (WAL), with an animation; here is what is really in it and what it costs.

What is logged

Every change to a page produces a WAL record: which subsystem (heap, B-tree, transaction), which page, and just enough bytes to redo the change. Records are appended to one sequential stream, stored as 16 MB segment files in pg_wal/. A record's position in that stream, in bytes, is its LSN (log sequence number), shown as two hex numbers such as 0/111CFE90 (WAL internals). Each page header stores the LSN of the last record that changed it, and the buffer pool refuses to write a dirty page to disk until the log is flushed up to that LSN: that ordering is the whole "write-ahead" rule.

Checkpoints, and why the first change after one is expensive

The log cannot grow forever and recovery should not replay a week of it. A checkpoint writes every dirty page in the buffer pool to its file, then records "everything before this LSN is on disk"; older WAL can then be recycled. Postgres starts one every checkpoint_timeout (5 minutes) or when max_wal_size (1 GB) of WAL has accumulated, and spreads its writes over 90% of the interval (checkpoint_completion_target 0.9) to avoid an I/O spike (WAL settings).

Now the subtle part. A disk writes in sectors of 512 bytes or 4 KB, so an 8 KB page write interrupted by a power cut can leave a torn page: half new, half old. A small delta record cannot repair a page whose old contents are garbage. So with full_page_writes on (the default), the first change to each page after a checkpoint logs a copy of the whole page, a full-page image (FPI); later changes to that page until the next checkpoint log only deltas (full_page_writes). InnoDB solves the same problem differently, with a doublewrite buffer (MySQL docs).

measured PostgreSQL 16.2, the 1M-message table with its primary key and chat_id index. The lesson is about access patterns more than settings: the 1,000 random updates produced 19.3 MB of WAL right after a checkpoint, 50 times the 0.39 MB they produce without page images, and 0.50 MB when repeated once those pages had been imaged measured. Writes that land on few pages (appends at the end of a table, inserts in key order) pay few images; writes scattered over many pages pay one image per page per checkpoint. wal_compression = pglz cut the images to 6.2 MB here (lz4 and zstd are also available since Postgres 15). Longer checkpoint intervals mean fewer images but more WAL to replay after a crash.

Do not turn full_page_writes off
The docs warn that turning it off "might lead to either unrecoverable data corruption, or silent data corruption, after a system failure". It is safe only on storage that guarantees atomic 8 KB writes (for example ZFS, which is copy-on-write). Use wal_compression and checkpoint tuning instead.

fsync: the moment "saved" becomes true

write() only copies bytes into the operating system's page cache; fsync() (or fdatasync()) asks the OS to push them to the device and waits until the device says they are stored. A commit waits for the WAL flush and nothing else: the data pages are written later by the checkpointer and background writer. On Linux Postgres flushes with fdatasync by default (wal_sync_method). On macOS the default does not empty the drive's own cache; fsync_writethrough does, and that is the setting used for the numbers below, so they are real flushes.

Correction to the old page
The old page said stable storage is "10,000 times slower than memory" and put an enterprise-SSD fsync at "0.1 to 1 ms". It depends on the hardware: an SSD with power-loss protection acknowledges a flush in about 1.6 to 12 microseconds (its capacitor-backed cache counts as stable), a consumer SSD takes about 0.9 to 3 ms, network block storage about 0.7 ms (the root's notes and the system design page's Numbers to know tab). This laptop: 6.0 ms per single-client commit measured.

Group commit and synchronous_commit

Because one flush covers everything written to the log before it, transactions committing at the same moment share it: that is group commit ("one fsync of the WAL file may suffice to commit many transactions", WAL introduction; commit_delay can make the flushing transaction wait a few microseconds to gather more, commit_delay). For the cases where losing the last instant of commits is acceptable, synchronous_commit = off acknowledges the commit before the flush; the WAL writer flushes a moment later. A crash can then lose the last transactions, at most three times wal_writer_delay (3 x 200 ms), but it "does not create any risk of database inconsistency": the lost transactions vanish whole (synchronous_commit).

measured pgbench, 20 s per run, each transaction one UPDATE of a random user's credit row, real flushes (fsync_writethrough), loopback connection on the same laptop. The root measured the same shape with pgbench's default script: 148 and 2,133 per second with the flush.

Read it this way: with the flush, one client waits 6 ms per commit, so at most about 165 commits a second; 32 clients share flushes and reach 2,603 (16 times more for 32 times the clients). Without waiting for the flush, the same work runs at 7,504 and 71,439 a second: the flush, not the update, was the cost. The professional move is to choose per transaction: SET LOCAL synchronous_commit = off inside a transaction that logs a page view or a token-usage event, never inside one that spends credits. The other values (local, remote_write, remote_apply) decide how long a commit waits for replicas; Running Postgres in production owns replication.

When fsync fails

In 2018 PostgreSQL developers found that on Linux a failed fsync could drop the dirty pages and report success on the next call, so "retry the fsync" could silently lose data (LWN, "PostgreSQL's fsync() surprise", 2018-04-18). Since the February 2019 minor releases (11.2 and the back branches), Postgres instead stops with a PANIC on a failed data-file flush and recovers from the WAL on restart; data_sync_retry (default off) controls it (error handling settings, 11.2 notes).

The same log is reused far beyond crash safety: shipped to another server it keeps a replica current; replayed up to a chosen moment it restores a backup to that moment (point-in-time recovery); decoded by another program it becomes a stream of changes (change data capture, as Debezium does). Redo log, journal, binlog, commit log and oplog are the same idea in other products. Running Postgres in production owns backups and replication; Queues, streams and async work owns change data capture.

What recovery costs
Time proportional to the WAL written since the last checkpoint. A max_wal_size of tens of GB on a write-heavy server means minutes of replay after a crash; that is the other side of fewer checkpoints and fewer page images. 5. B-trees: the default index, from page to production


The problem appears


"The messages of chat 42000" are 6 rows scattered over 19,235 pages. Without help the database reads every page (the root measured 19,349 page reads and 28 ms for 6 rows). We need a structure that leads from a value to the pages holding it in a handful of reads, stays correct while thousands of inserts arrive, and also answers "between" and "in order".


The idea: a sorted tree of pages


A B-tree (strictly a B+tree, the variant every relational database uses) is a tree whose nodes are pages. Leaf pages hold the indexed values in sorted order, each with the ctid of its row; each leaf links to its right neighbour, so a range scan walks sideways along the leaves. Internal pages hold only separator keys and downlinks (page numbers of children): "keys below 25,047 are under page 3". The root is the single page at the top; page 0 of the file, the metapage, says where the root is. Postgres's version follows Lehman and Yao's 1981 design for concurrency: every page also stores a high key (an upper bound for its contents) and a link to its right sibling, so a reader that arrives at a page just split can notice and step right instead of waiting for a lock (nbtree README).

Fan-out: why a billion rows need only about four levels


The number of children per internal page, the fan-out, is what keeps the tree shallow. An index entry is an 8-byte header plus the key, rounded up to 8 bytes, plus a 4-byte line pointer: 20 bytes for a bigint. A page has 8,152 usable bytes (8,192 minus the 24-byte header and a 16-byte trailer), so about 407 entries fit; Postgres fills leaves to 90% when it builds an index or appends at the right edge (367 entries) and internal pages to 70% (about 285) (B-tree fillfactor, constants in nbtree.h). The top one or two levels are touched by every lookup, so they stay in the buffer pool; a lookup on a big table costs about one or two physical reads, not four. That is why the old page's "3 to 4 page reads for a large table plus one heap fetch, mostly cached" holds, and why the root measured 12 page touches, all cache hits, for the 6-row chat lookup.


Inserting: splits, and why random keys waste space


An insert walks down to the right leaf and adds the entry in order. When the leaf is full it splits: a new page is allocated, the upper half of the entries moves there, and a separator for the new page is added to the parent; if the parent is full it splits too, and when the root splits the tree gains a level (it grows at the top, which is why every leaf is always at the same depth). Section 6 animates one split next to the LSM-tree's way of absorbing the same insert, and the B-tree and LSM lab runs thousands.


Postgres splits the rightmost leaf differently when the new key is the largest: it keeps the left page at the fillfactor (90%) instead of half, because an index on an increasing key (ids, timestamps) never inserts into the left page again (nbtree.h: "The fillfactor is applied during index build and when splitting a rightmost page"). What a B-tree costs
Every insert dirties at least one leaf page somewhere in the file; random keys dirty pages all over it (random writes, more full-page images, about 30% empty space); splits need short page locks; and every index on a table repeats all of this for every row. When NOT to use one: on a column you never search by; on a tiny table (a sequential scan of a few pages is cheaper); on a huge append-only table queried by time ranges (BRIN, section 9, was about 3,000 times smaller here); on a write stream far faster than random page writes can absorb (an LSM-tree, next).






6. LSM-trees: write first, sort later


The problem appears


Suppose the chat product logs every token-usage event, hundreds of thousands per second, keyed by a random request id. A B-tree turns each event into a change to a random leaf page: random reads to find it, random writes to put it back, a full-page image after each checkpoint. Flash and disks are far faster at writing long sequential runs than scattered pages. Can an index be maintained using only sequential writes?


The idea: buffer in memory, write sorted files, merge them later


The LSM-tree (log-structured merge-tree, O'Neil, Cheng, Gawlick and O'Neil, Acta Informatica, 1996; the names memtable and SSTable come from Google's Bigtable paper, OSDI 2006) works like this:


    

  1. Log it. Append the change to a write-ahead log, exactly as Postgres does, so a crash loses nothing.
    2. 

  2. Memtable. Insert it into a sorted structure in memory (RocksDB uses a skip list). Nothing on disk is read or changed.
    3. 

  3. Flush. When the memtable is full (64 MB by default in RocksDB) it is written out in one sequential pass as an immutable sorted file, an SSTable (sorted string table): key-value blocks, an index of the blocks, and a bloom filter. A new memtable takes over.
    4. 

  4. Compact. Background threads merge-sort files together, keeping only the newest version of each key and dropping deleted ones, so the number of files stays bounded.
    5. 

  5. Read. Look in the memtable, then in the files from newest to oldest, stopping at the first hit; per-file bloom filters and block indexes avoid most disk reads.
    6. 



The same insert, through a B-tree and through an LSM-tree illustrative (four keys per page or file so the whole structure fits on screen):
















Compaction is the real design choice


Files on disk are grouped in levels. Level 0 holds freshly flushed files, which may overlap in key range; deeper levels are larger. How files move down is the compaction strategy:




Leveled (RocksDB's default)
Each level from 1 down is one sorted run, split into files with no overlap, and each level is about 10 times larger than the one above (RocksDB: level 0 compacts at 4 files, level 1 is 256 MB, multiplier 10, options.h). A file pushed into the next level is merged with the overlapping files there, rewriting them. Few runs to search, little wasted space, many rewrites: RocksDB's tuning guide works an example to a write amplification of "approximately 1 + 2 + 10 + 10 + 10 = 33" (tuning guide). Cassandra calls it LCS.


Tiered (RocksDB "universal", Cassandra STCS)
Runs of similar size accumulate; when there are enough, they are merged into one bigger run ("waits for several sorted runs with similar size and merge them together", universal compaction). Each key is rewritten fewer times, but a read may search many runs and old versions take space until merged. Size-tiered is still Cassandra's default (cassandra.yaml); Cassandra 5.0 added a Unified Compaction Strategy that can behave like either (Cassandra compaction).




Luo and Carey's survey gives the textbook costs with size ratio T between levels, L levels and B entries per page: writing an entry costs O(T·L/B) I/O under leveling and O(L/B) under tiering; a point lookup without bloom filters searches O(L) runs under leveling and O(T·L) under tiering (LSM survey, VLDB Journal 2020, section 2.3). Section 7 measures both on RocksDB.


Bloom filters: skipping files that cannot hold the key


A bloom filter is a bit array plus k hash functions. Adding a key sets k bits; asking "is key x here?" checks x's k bits: if any is 0 the answer is a certain no; if all are 1 it is maybe (other keys may have set them). With m bits for n keys the false-positive rate is about


p ≈ (1 − e−k n / m)k, best at k = (m/n) ln 2


At 10 bits per key the best k is 6.9; with k = 7, p = 0.82% derived (RocksDB's wiki: "9.9 bits per key (1% false positive rate)", RocksDB bloom filter). So looking up a key that does not exist costs, on average, under 0.01 file reads per level instead of one. Bloom filters cannot help a range scan ("all keys between a and b" must still visit every run), which is the LSM-tree's weak spot.




Deletes are writes: tombstones


Files are immutable, so a delete writes a tombstone, a marker saying "this key is gone". The old value stays on disk until a compaction carrying the tombstone reaches the level that holds it; until then every read of that range must step over the tombstones. RocksDB's DeleteRange writes one range tombstone for a whole key range (DeleteRange). Cassandra keeps tombstones for gc_grace_seconds, 864,000 (10 days) by default, so a replica that was down can still learn about the delete (CREATE TABLE); it warns when a query reads 1,000 tombstones and aborts at 100,000 (cassandra.yaml). That is why using a Cassandra table as a queue (insert, read, delete, repeat) is a classic failure: the live rows are few, the tombstones many, and reads slow down before compaction catches up.


What an LSM-tree costs
Background compaction rewrites data many times (write amplification, measured in section 7) and competes with your queries for disk and CPU. Reads may search several runs; range scans cannot use bloom filters. Space is used by old versions and tombstones until compaction. The characteristic failure: compaction falls behind a sustained write burst, level 0 piles up, reads slow down, and the engine finally throttles or stops writes (RocksDB write stalls). Alert on pending compaction bytes, not just disk space. When NOT to use one: read-mostly data with range queries, small data, or when you want Postgres's features; ingest-heavy key-value or time-series streams are its home (Cassandra, ScyllaDB, RocksDB inside many systems; the root's Database atlas tab lists the products).






7. The RUM trade-off, measured


The idea


Every way of storing and indexing data pays three overheads: extra Reads beyond the data you asked for, extra Update work beyond the bytes you changed, and extra Memory or space beyond the data itself. The RUM conjecture says you cannot minimise all three: "designing access methods that set an upper bound for two of the RUM overheads, leads to a hard lower bound for the third overhead which cannot be further reduced" (Athanassoulis et al., EDBT 2016). A B-tree bounds reads and space and pays on updates; an LSM-tree bounds update cost and pays on reads (several runs) or space (old versions); an index pays space and update cost to cut reads; compression pays CPU to cut space. The three overheads are measured as amplification factors:


    

  • Write amplification: bytes written to storage per byte of data the application wrote (log, pages, compaction rewrites).
    • 

  • Read amplification: pages or files read per lookup.
    • 

  • Space amplification: bytes on disk per byte of live data.
    • 



Measured on two real engines

Correction to the old page
The old page gave B-tree write amplification as "easily 10x to 40x", LSM leveled as "roughly 10x to 30x", and space amplification as 1.3x (B-tree), 1.1x (leveled) and "up to 2x or more" (tiered), without sources. The measurements above show why a single number misleads: a Postgres B-tree measured about 3.4 times for appends and about 300 times for scattered single-row updates right after a checkpoint; RocksDB measured about 5 to 6 times for leveled compaction, a figure that grows with the number of levels the data spans (half a gigabyte here sits in two levels; RocksDB's own worked example reaches 33). Tiered (universal) compaction wrote about as much as leveled at this size but needed 1.7 times the space against 1.1: the space penalty holds; the write saving appears as data spans more levels (Luo and Carey: L against T times L). Quote amplification with its workload, or measure your own.


How a pro uses this
Name the corner you are giving up before choosing: a ledger that is read and updated by key wants bounded reads (B-tree); an event firehose wants cheap writes (LSM, or an append-only Postgres table with BRIN); a cold archive wants little space (columnar, compressed, section 12). Then measure write amplification on your own workload; on flash it decides how fast you wear out the drives and how much I/O budget compaction or checkpoints take from your queries.







8. Heap tables and clustered tables: where the row itself lives


The problem appears


Opening chat 42000 read 6 table pages for 6 messages because the rows sit in arrival order and the chat's messages arrived at different times. If the table itself were sorted by chat, those messages would share one page.


Two designs




Heap plus indexes (Postgres)
The table is a heap: rows go wherever there is room, in no particular order. Every index, the primary key included, is a separate B-tree whose leaves point to ctids. All indexes are equal, a lookup by any of them costs the same, and a row's address changes only when a non-HOT update moves it (then every index gets a new entry, section 1). CLUSTER can sort the table once by an index, but new rows are not kept in order.


Index-organised (InnoDB, SQLite)
The table is the primary-key B-tree: its leaves hold the whole rows, in key order, a clustered index. InnoDB clusters on the primary key, or the first unique non-null index, or a hidden 6-byte row id; every secondary index stores the primary key, not a page address, so a lookup by a secondary index walks two B-trees (InnoDB index types). SQLite tables are B-trees keyed by rowid; WITHOUT ROWID tables cluster on the primary key (SQLite docs).




Consequences a pro knows. In InnoDB, a primary key of (chat_id, id) puts each chat's messages together, so reading a chat is one or two leaf pages, the effect Postgres lacks; but a random primary key (UUID v4) scatters every insert across the whole table, not just across an index, and every secondary index carries the full 16-byte key. In Postgres the primary key's order barely affects the table, a secondary-index lookup costs the same as a primary-key lookup, and moving rows is cheap for indexes only when updates are HOT. Postgres can approximate clustering for a read-heavy access path with a covering index (section 10) or with partitioning.


What clustering costs
Clustered tables make primary-key range reads cheap and secondary lookups dearer (two descents), and the choice of primary key now decides physical layout: changing it rewrites the table. Heap tables pay one table-page read per matching row unless the index covers the query.

Hash against B-tree, and combining indexes




Postgres has no stored bitmap index, but it builds bitmaps on the fly: a bitmap index scan collects the matching ctids from an index into a bitmap of pages, two such bitmaps can be combined with AND or OR, and a bitmap heap scan then reads each needed page once, in file order. That is why two single-column indexes can still answer WHERE a = 1 AND b = 2 reasonably, and why the plans in the root's Query plans tab often show "Bitmap Heap Scan". Analytical stores do keep bitmap indexes (one bitmap per distinct value of a low-cardinality column).







10. Index shapes: multicolumn, partial, expression, covering


Beyond the type, the shape of an index decides which queries it serves. Four shapes cover most production indexes (Use The Index, Luke is the best practical guide):


    

  • Multicolumn (composite): CREATE INDEX ON messages (chat_id, created_at) sorts by chat, then by time within a chat. It serves WHERE chat_id = 42000 ORDER BY created_at perfectly, and WHERE chat_id = 42000 alone; before Postgres 18 it barely served WHERE created_at > ... alone (skip scan, section 5, now helps when the first column has few distinct values). The rule: equality columns first, then the range or sort column, because after the first range condition the rest of the index is not ordered by the later columns (multicolumn indexes, Use The Index, Luke on concatenated keys).
    • 

  • Partial: CREATE INDEX ON messages (tokens) WHERE role = 'assistant' AND tokens > 1000 indexes only the rows that a known query looks for (long answers, unprocessed jobs, active users).  (partial indexes)
    • 

  • Expression: CREATE INDEX ON users (lower(email)) indexes a computed value, so WHERE lower(email) = ... can use it. Without it, wrapping the column in a function hides it from an ordinary index (expression indexes); why a predicate can or cannot use an index is the planner's story, owned by Query planning and performance.
    • 

  • Covering (INCLUDE, Postgres 11): CREATE INDEX ON messages (chat_id) INCLUDE (role, tokens) stores extra columns in the leaves without sorting by them, so a query that needs only those columns is answered by an index-only scan, skipping the table pages (if the visibility map allows, section 1). 
    • 



What shapes cost
Each is one more index to maintain on every write. Wider entries (INCLUDE, long expressions) mean fewer entries per page and a deeper, bigger index. A partial index is used only when the query's WHERE clause implies the index's condition, so a query written differently silently misses it.






11. What indexes cost on writes, measured


The parent page warns that every index slows writes. Here is by how much: the same million messages copied with one INSERT ... SELECT into an empty table with 0, 1, 3 and 6 indexes, three times each (median shown), with a 128 MB buffer pool measured:




Three lessons. First, an index on an increasing key (the primary key, created_at) is cheap: each one adds a sequential stream of leaf pages and its share of WAL. Second, the expensive index is the one whose keys arrive in random order and whose size exceeds memory: the B-tree on content (random-looking text, 144 MB against a 128 MB buffer pool) turned an insert of about 10 seconds into about 2 minutes, because every row now needs a random leaf page that is probably not cached. Third, the single-row insert rate through a connection (pgbench, 4 clients, commit not waiting for the flush) did not show a trend: it moved between about 12,600 and 23,500 per second with no order across 0 to 6 indexes, because per-row index work of a few microseconds hides behind the round trip and commit overhead until the indexes stop fitting in memory. Index cost is invisible in a small benchmark and decisive at scale.

12. Column stores, in one section


Everything above stores a row's columns together, which suits "fetch this chat". Analytics asks the opposite ("total tokens per model over a year") and reads one or two columns of every row. A column store keeps each column in its own compressed chunks, so such a query reads only the bytes it needs: on the parent page the same aggregate needed 94 times fewer bytes from Parquet than from the Postgres heap measured there. Column stores rarely use B-trees. They rely on sort order and zone maps (min and max per block, the same idea as BRIN) to skip blocks, and their storage is LSM-shaped: ClickHouse's MergeTree writes each insert as an immutable sorted part and merges parts in the background, with a sparse primary index of one entry per 8,192 rows (MergeTree). Because skipping depends on how data was sorted when it was written, sort order matters more there than any index added later. Analytics: columnar engines, DuckDB and the lakehouse owns the details (Parquet layout, encodings, DuckDB, the lakehouse).

Common mistakes


Random UUID v4 primary keys on a big, growing table
Every insert lands on a random leaf page: more page images in the WAL, about 30% empty space, cache misses once the index outgrows memory (section 5 measured it). Use a sequence or UUID v7.


Indexing every column "just in case"
Each index is paid on every insert and non-HOT update; one random-order index that does not fit in memory made a bulk insert about 12 times slower here (section 11). Index what queries search by, then measure.


Composite index columns in the wrong order
(created_at, chat_id) cannot serve "this chat, newest first" well; (chat_id, created_at) can. Equality columns first, then the range or sort column (section 10).


Expecting index-only scans on a table that is never vacuumed
Without the visibility map's all-visible bits, an index-only scan still visits the table pages (section 1; the root's Query plans tab, case 7).


Turning off fsync, full_page_writes or synchronous_commit globally for speed
The first two risk corruption; the third loses the last instant of commits for every table, money included. Use group commit, wal_compression, and per-transaction synchronous_commit instead (section 3).


SELECT * on tables with long text
Long values are TOASTed: fetching them costs extra page reads and decompression. List the columns you need (section 1).


BRIN on a column that does not follow the row order
Each block range then spans almost the whole value range and nothing is skipped (section 9 measured it). BRIN suits append-only time columns.


Using an LSM store as a queue, and ignoring compaction debt
Deletes become tombstones that reads must step over; compaction that falls behind a write burst ends in write stalls (section 6).


Benchmarking with data that fits in memory
Everything is a cache hit and index costs vanish (section 11's single-row inserts). Test at production size, or at least with data larger than shared_buffers and the OS cache.


A huge shared_buffers
Postgres also relies on the OS page cache; above about 40% of RAM the docs say it is unlikely to help, and checkpoints have more dirty pages to write (section 2).

B-tree and LSM lab


Insert the same keys into a small B-tree and a small LSM-tree and watch what each one writes. Pages here hold a handful of keys instead of hundreds, so a few hundred inserts show what millions do on a real server. Write amplification counts every slot written to storage per key inserted: for the B-tree, page writes at checkpoints plus full-page images in the log plus one log record per insert; for the LSM-tree, one log record per insert plus every slot written by flushes and compactions. Athanassoulis et al., EDBT 2016: the six-page paper behind section 7. About 30 min.


LSM-based Storage Techniques: A Survey
Luo and Carey, VLDB Journal 2020: compaction strategies, bloom filters and cost analysis. About 1 h 30 min.


The Log-Structured Merge-Tree
O'Neil, Cheng, Gawlick and O'Neil, Acta Informatica 1996: the original paper. About 1 h.


RocksDB wiki: Leveled Compaction and Universal Compaction
How a production LSM engine sizes levels and picks files, with diagrams. About 30 min.


CMU 15-445/645 Database Systems
Andy Pavlo's course; the lectures on storage, buffer pools, B+trees and logging and recovery are the best free videos on this page's material. About 6 h for those lectures.


Interactive latency numbers
Colin Scott's version of Jeff Dean's list, with a slider for the hardware year (extrapolated, not measured; see the Numbers section). About 10 min.
