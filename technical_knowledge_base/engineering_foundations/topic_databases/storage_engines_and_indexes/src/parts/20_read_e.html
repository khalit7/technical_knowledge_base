8. Heap tables and clustered tables: where the row itself lives

Opening chat 42000 read 6 table pages for 6 messages because rows sit in arrival order. If the table itself were sorted by chat, those messages would share one page. Two designs decide this:

In a heap every index points at row addresses; in a clustered table the primary-key tree holds the rows and other indexes point at the key

illustrative Two indexes on the same few messages. Left: Postgres, where any index costs one descent plus one table page per row. Right: InnoDB, where a primary-key range is one walk along the leaves, but a secondary lookup descends two trees.

Heap plus indexes (Postgres)

The table is a heap: rows go wherever there is room, in no particular order. Every index, the primary key included, is a separate B-tree whose leaves point to ctids. All indexes are equal, and a row's address changes only when a non-HOT update moves it (then every index gets a new entry, section 1). CLUSTER can sort the table once by an index, but new rows are not kept in order.

Index-organised (InnoDB, SQLite)

The table is the primary-key B-tree: its leaves hold whole rows in key order, a clustered index. InnoDB clusters on the primary key, or the first unique non-null index, or a hidden 6-byte row id; every secondary index stores the primary key, not a page address, so a secondary lookup walks two B-trees ({{InnoDB index types|https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html}}). SQLite tables are B-trees keyed by rowid; WITHOUT ROWID tables cluster on the primary key ({{SQLite docs|https://www.sqlite.org/withoutrowid.html}}).

In InnoDB a primary key of (chat_id, id) puts each chat's messages together, so reading a chat is one or two leaf pages, which Postgres lacks; but a random primary key (UUID v4) scatters every insert across the whole table, and every secondary index carries the full 16-byte key. In Postgres the key's order barely affects the table and a secondary lookup costs the same as a primary-key one; it can approximate clustering for a read-heavy path with a covering index (section 10) or partitioning.

What clustering costs
Primary-key range reads get cheap and secondary lookups dearer (two descents), and the primary key now decides physical layout: changing it rewrites the table. Heap tables pay one table-page read per matching row unless the index covers the query.

9. Index types in Postgres, and when to use each

A B-tree answers questions about order: equal, less than, between, sorted by. Many real questions are not: "messages whose metadata contains {"tool": "search"}", "documents containing refund", "users within 5 km", "bookings that overlap this range", "the last hour of a 10-billion-row event table". Postgres gives each kind of question its own structure, an access method ({{index types|https://www.postgresql.org/docs/18/indexes-types.html}}):

The old page called GiST "historically the ANN index in early pgvector". It was not: pgvector's first release (0.1.0, 2021-04-20) shipped IVFFlat, and HNSW arrived in 0.5.0 (2023-08-28); it has never used GiST ({{pgvector changelog|https://github.com/pgvector/pgvector/blob/master/CHANGELOG.md}}).

On a time-ordered column, BRIN reads about as many pages as a B-tree from an index 3,047 times smaller

measured PostgreSQL 16.2, 10,000,000 messages (1.58 GB) where created_at grows with row position, warm cache, one worker. BRIN returns whole 128-page ranges whose rows are rechecked one by one. On a shuffled copy of 2M rows, where created_at no longer follows the row order, the same one-hour query through BRIN read 38,602 pages, more than the whole table of 38,592 pages, and took 230 ms against 150 ms for a plain sequential scan: every block range spans almost all dates.

Hash against B-tree measured: a hash index on chat_id is 33.1 MB against 9.3 MB for the B-tree, because deduplication stores each chat once with a list of rows while a hash index stores one entry per row; both found chat 42000 by touching 12 pages. Hash indexes pay off only for long keys that deduplication cannot help.

Bitmap scans: how two single-column indexes combine (depth)

Postgres has no stored bitmap index, but it builds bitmaps on the fly: a bitmap index scan collects the matching ctids from an index into a bitmap of pages, two such bitmaps can be combined with AND or OR, and a bitmap heap scan then reads each needed page once, in file order. That is why two single-column indexes can still answer WHERE a = 1 AND b = 2 reasonably, and why the plans in the root's {{Query plans|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab often show "Bitmap Heap Scan". Analytical stores do keep bitmap indexes (one bitmap per distinct value of a low-cardinality column).

10. Index shapes: multicolumn, partial, expression, covering

Beyond the type, the shape of an index decides which queries it serves ({{Use The Index, Luke|https://use-the-index-luke.com/}} is the best practical guide). Multicolumn (composite): CREATE INDEX ON messages (chat_id, created_at) sorts by chat, then by time within a chat. The rule is equality columns first, then the range or sort column, because after the first range condition the rest of the index is not ordered by the later columns ({{multicolumn indexes|https://www.postgresql.org/docs/18/indexes-multicolumn.html}}, {{concatenated keys|https://use-the-index-luke.com/sql/where-clause/the-equals-operator/concatenated-keys}}). Equality first: the matching entries are one contiguous run; range first: they are scattered through the range

(chat_id, created_at) also serves WHERE chat_id = 42000 ORDER BY created_at and WHERE chat_id = 42000 alone; before Postgres 18 it barely served WHERE created_at > ... alone (skip scan, section 5, now helps when the first column has few distinct values).

  • Partial: CREATE INDEX ON messages (tokens) WHERE role = 'assistant' AND tokens > 1000 indexes only the rows a known query looks for (long answers, unprocessed jobs, active users). Measured: 95,287 of 1M rows qualify; the partial index is 680 kB against 7.1 MB for an index on tokens over all rows ({{partial indexes|https://www.postgresql.org/docs/18/indexes-partial.html}}).
  • Expression: CREATE INDEX ON users (lower(email)) indexes a computed value, so WHERE lower(email) = ... can use it; wrapping a column in a function hides it from an ordinary index ({{expression indexes|https://www.postgresql.org/docs/18/indexes-expressional.html}}). Why a predicate can or cannot use an index is the planner's story, owned by {{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}}.
  • Covering (INCLUDE, Postgres 11): CREATE INDEX ON messages (chat_id) INCLUDE (role, tokens) stores extra columns in the leaves without sorting by them, so a query that needs only those columns is an index-only scan, skipping the table pages (if the visibility map allows, section 1). Measured: fetching role and tokens of chat 42000 touched 12 pages with the plain index and 7 with the covering one, at the price of a 40.6 MB index instead of 9.3 MB.
What shapes cost
Each is one more index to maintain on every write. Wider entries (INCLUDE, long expressions) mean fewer entries per page and a deeper, bigger index. A partial index is used only when the query's WHERE clause implies the index's condition, so a query written differently silently misses it.
