7. The RUM trade-off, measured

The idea

Every way of storing and indexing data pays three overheads: extra Reads beyond the data you asked for, extra Update work beyond the bytes you changed, and extra Memory or space beyond the data itself. The RUM conjecture says you cannot minimise all three: "designing access methods that set an upper bound for two of the RUM overheads, leads to a hard lower bound for the third overhead which cannot be further reduced" ({{Athanassoulis et al., EDBT 2016|https://openproceedings.org/2016/conf/edbt/paper-12.pdf}}). A B-tree bounds reads and space and pays on updates; an LSM-tree bounds update cost and pays on reads (several runs) or space (old versions); an index pays space and update cost to cut reads; compression pays CPU to cut space. The three overheads are measured as amplification factors:

  • Write amplification: bytes written to storage per byte of data the application wrote (log, pages, compaction rewrites).
  • Read amplification: pages or files read per lookup.
  • Space amplification: bytes on disk per byte of live data.

The old page gave B-tree write amplification as "easily 10x to 40x", LSM leveled as "roughly 10x to 30x", and space amplification as 1.3x (B-tree), 1.1x (leveled) and "up to 2x or more" (tiered), without sources. The measurements above show why a single number misleads: a Postgres B-tree measured about 3.4 times for appends and about 300 times for scattered single-row updates right after a checkpoint; RocksDB measured about 5 to 6 times for leveled compaction, a figure that grows with the number of levels the data spans (half a gigabyte here sits in two levels; RocksDB's own worked example reaches 33). Tiered (universal) compaction wrote about as much as leveled at this size but needed 1.7 times the space against 1.1: the space penalty holds; the write saving appears as data spans more levels (Luo and Carey: L against T times L). Quote amplification with its workload, or measure your own.
How a pro uses this
Name the corner you are giving up before choosing: a ledger that is read and updated by key wants bounded reads (B-tree); an event firehose wants cheap writes (LSM, or an append-only Postgres table with BRIN); a cold archive wants little space (columnar, compressed, section 12). Then measure write amplification on your own workload; on flash it decides how fast you wear out the drives and how much I/O budget compaction or checkpoints take from your queries.

8. Heap tables and clustered tables: where the row itself lives

The problem appears

Opening chat 42000 read 6 table pages for 6 messages because the rows sit in arrival order and the chat's messages arrived at different times. If the table itself were sorted by chat, those messages would share one page.

Two designs

Heap plus indexes (Postgres)

The table is a heap: rows go wherever there is room, in no particular order. Every index, the primary key included, is a separate B-tree whose leaves point to ctids. All indexes are equal, a lookup by any of them costs the same, and a row's address changes only when a non-HOT update moves it (then every index gets a new entry, section 1). CLUSTER can sort the table once by an index, but new rows are not kept in order.

Index-organised (InnoDB, SQLite)

The table is the primary-key B-tree: its leaves hold the whole rows, in key order, a clustered index. InnoDB clusters on the primary key, or the first unique non-null index, or a hidden 6-byte row id; every secondary index stores the primary key, not a page address, so a lookup by a secondary index walks two B-trees ({{InnoDB index types|https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html}}). SQLite tables are B-trees keyed by rowid; WITHOUT ROWID tables cluster on the primary key ({{SQLite docs|https://www.sqlite.org/withoutrowid.html}}).

Consequences a pro knows. In InnoDB, a primary key of (chat_id, id) puts each chat's messages together, so reading a chat is one or two leaf pages, the effect Postgres lacks; but a random primary key (UUID v4) scatters every insert across the whole table, not just across an index, and every secondary index carries the full 16-byte key. In Postgres the primary key's order barely affects the table, a secondary-index lookup costs the same as a primary-key lookup, and moving rows is cheap for indexes only when updates are HOT. Postgres can approximate clustering for a read-heavy access path with a covering index (section 10) or with partitioning.

What clustering costs
Clustered tables make primary-key range reads cheap and secondary lookups dearer (two descents), and the choice of primary key now decides physical layout: changing it rewrites the table. Heap tables pay one table-page read per matching row unless the index covers the query.
