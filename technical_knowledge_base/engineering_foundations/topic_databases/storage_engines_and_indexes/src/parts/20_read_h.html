9. Index types in Postgres, and when to use each

The problem appears

A B-tree answers questions about order: equal to, less than, between, sorted by. Many real questions are not about order: "messages whose metadata contains {"tool": "search"}", "documents containing the word refund", "users within 5 km", "bookings that overlap this time range", "the last hour of a 10-billion-row event table". Postgres lets each kind of question have its own index structure, an access method ({{index types|https://www.postgresql.org/docs/18/indexes-types.html}}).

Only B-trees always support index-only scans; GiST and SP-GiST support them for some operator classes; the others never do. Hash against B-tree, and combining indexes

Postgres has no stored bitmap index, but it builds bitmaps on the fly: a bitmap index scan collects the matching ctids from an index into a bitmap of pages, two such bitmaps can be combined with AND or OR, and a bitmap heap scan then reads each needed page once, in file order. That is why two single-column indexes can still answer WHERE a = 1 AND b = 2 reasonably, and why the plans in the root's {{Query plans|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab often show "Bitmap Heap Scan". Analytical stores do keep bitmap indexes (one bitmap per distinct value of a low-cardinality column).

10. Index shapes: multicolumn, partial, expression, covering

Beyond the type, the shape of an index decides which queries it serves. Four shapes cover most production indexes ({{Use The Index, Luke|https://use-the-index-luke.com/}} is the best practical guide):

  • Multicolumn (composite): CREATE INDEX ON messages (chat_id, created_at) sorts by chat, then by time within a chat. It serves WHERE chat_id = 42000 ORDER BY created_at perfectly, and WHERE chat_id = 42000 alone; before Postgres 18 it barely served WHERE created_at > ... alone (skip scan, section 5, now helps when the first column has few distinct values). The rule: equality columns first, then the range or sort column, because after the first range condition the rest of the index is not ordered by the later columns ({{multicolumn indexes|https://www.postgresql.org/docs/18/indexes-multicolumn.html}}, {{Use The Index, Luke on concatenated keys|https://use-the-index-luke.com/sql/where-clause/the-equals-operator/concatenated-keys}}).
  • Partial: CREATE INDEX ON messages (tokens) WHERE role = 'assistant' AND tokens > 1000 indexes only the rows that a known query looks for (long answers, unprocessed jobs, active users). ({{partial indexes|https://www.postgresql.org/docs/18/indexes-partial.html}})
  • Expression: CREATE INDEX ON users (lower(email)) indexes a computed value, so WHERE lower(email) = ... can use it. Without it, wrapping the column in a function hides it from an ordinary index ({{expression indexes|https://www.postgresql.org/docs/18/indexes-expressional.html}}); why a predicate can or cannot use an index is the planner's story, owned by {{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}}.
  • Covering (INCLUDE, Postgres 11): CREATE INDEX ON messages (chat_id) INCLUDE (role, tokens) stores extra columns in the leaves without sorting by them, so a query that needs only those columns is answered by an index-only scan, skipping the table pages (if the visibility map allows, section 1).
What shapes cost
Each is one more index to maintain on every write. Wider entries (INCLUDE, long expressions) mean fewer entries per page and a deeper, bigger index. A partial index is used only when the query's WHERE clause implies the index's condition, so a query written differently silently misses it.
