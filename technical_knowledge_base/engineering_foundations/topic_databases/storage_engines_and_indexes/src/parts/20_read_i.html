11. What indexes cost on writes, measured

The parent page warns that every index slows writes. Here is by how much: the same million messages copied with one INSERT ... SELECT into an empty table with 0, 1, 3 and 6 indexes, three times each (median shown), with a 128 MB buffer pool measured:

Three lessons. First, an index on an increasing key (the primary key, created_at) is cheap: each one adds a sequential stream of leaf pages and its share of WAL. Second, the expensive index is the one whose keys arrive in random order and whose size exceeds memory: the B-tree on content (random-looking text, 144 MB against a 128 MB buffer pool) turned an insert of about 10 seconds into about 2 minutes, because every row now needs a random leaf page that is probably not cached. Third, the single-row insert rate through a connection (pgbench, 4 clients, commit not waiting for the flush) did not show a trend: it moved between about 12,600 and 23,500 per second with no order across 0 to 6 indexes, because per-row index work of a few microseconds hides behind the round trip and commit overhead until the indexes stop fitting in memory. Index cost is invisible in a small benchmark and decisive at scale.

Find indexes nobody uses
SELECT indexrelid::regclass, idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) FROM pg_stat_user_indexes ORDER BY idx_scan, pg_relation_size(indexrelid) DESC; An index with idx_scan = 0 after weeks of normal traffic (and not backing a constraint) is pure write cost; check replicas too, since the counters are per server ({{statistics views|https://www.postgresql.org/docs/18/monitoring-stats.html}}). Build new indexes with CREATE INDEX CONCURRENTLY so writes are not blocked.

12. Column stores, in one section

Everything above stores a row's columns together, which suits "fetch this chat". Analytics asks the opposite ("total tokens per model over a year") and reads one or two columns of every row. A column store keeps each column in its own compressed chunks, so such a query reads only the bytes it needs: on the parent page the same aggregate needed 94 times fewer bytes from Parquet than from the Postgres heap measured there. Column stores rarely use B-trees. They rely on sort order and zone maps (min and max per block, the same idea as BRIN) to skip blocks, and their storage is LSM-shaped: ClickHouse's MergeTree writes each insert as an immutable sorted part and merges parts in the background, with a sparse primary index of one entry per 8,192 rows ({{MergeTree|https://clickhouse.com/docs/engines/table-engines/mergetree-family/mergetree}}). Because skipping depends on how data was sorted when it was written, sort order matters more there than any index added later. {{Analytics: columnar engines, DuckDB and the lakehouse|n:3ef5c17b0d0d8157814ec5dd8a0d4fb5}} owns the details (Parquet layout, encodings, DuckDB, the lakehouse).
