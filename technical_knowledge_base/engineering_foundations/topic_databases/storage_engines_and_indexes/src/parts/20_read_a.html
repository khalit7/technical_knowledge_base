The idea in one screen

A storage engine keeps rows in fixed-size pages cached in RAM, makes a commit durable by appending it to a log and flushing that log, and finds rows through an index whose design decides when the write cost is paid: a B-tree pays now, with random in-place page writes; an LSM-tree pays later, by merging sorted files in the background.

Both engines commit the same way (log, then flush); they differ in where the changed data goes next

Numbered arrows are the order of events for one insert. The highlighted arrow is where each design pays for its writes: the B-tree at checkpoints (one random 8 KB write per changed page), the LSM-tree in compaction (every key rewritten once per level it passes through). Reads go the other way: a B-tree reads about 3 pages from root to leaf; an LSM-tree checks the memtable, then sorted files newest first, skipping most with bloom filters.

LSM-tree
log-structured merge-tree: an in-memory table flushed to immutable sorted files that are merged later.

1. Pages: how a table sits on disk

Disks read blocks, not rows (one random SSD read takes about 100 microseconds, roughly a thousand memory reads), so rows that share a block are fetched for the price of one read. Postgres keeps each table and each index in its own file (messages is base/16384/16460 measured, cut into 1 GB segment files, {{file layout|https://www.postgresql.org/docs/18/storage-file-layout.html}}): an array of 8 KB pages numbered from 0, always read and written whole ({{page layout|https://www.postgresql.org/docs/18/storage-page-layout.html}}). Our million messages fill 19,235 pages; InnoDB uses 16 KB pages and SQLite 4 KB. Each stored row version is a tuple, addressed by its ctid (page, slot): the first message lives at (0,1), and indexes store ctids to jump straight to a page.

The 4-byte line pointers let Postgres move a tuple inside its page without changing its ctid, so no index needs updating.

All 52 slots of page 0 (the raw pageinspect rows)

Each tuple starts with a 23-byte header (padded to 24): xmin and xmax, the transactions that created and deleted or replaced this version (0 if none), which decide who can see it (MVCC, owned by {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}}); t_ctid, its own address or its replacement's; and infomask flags (has nulls, hint bits caching whether xmin and xmax committed). So a message with about 90 bytes of data takes about 120 to 200 bytes on the page, and a single-bigint table uses 36 to 40 bytes per 8-byte value derived (24 + 8, aligned, plus 4).

An update is a new tuple

Postgres never overwrites a row in place: an UPDATE writes a new tuple and stamps the old one's xmax. If the new version lands on another page, every index needs a new entry, even when no indexed column changed. A HOT update (heap-only tuple) avoids that: when no indexed column changed and the new version fits on the same page, the old tuple points to the new one and the indexes are untouched ({{HOT|https://www.postgresql.org/docs/18/storage-hot.html}}). Predict before you switch: on a full page, where can the new version go?

The visibility map, and big values

The visibility map (_vm) keeps two bits per page, all-visible and all-frozen ({{VM|https://www.postgresql.org/docs/18/storage-vm.html}}): VACUUM skips all-visible pages, and an index-only scan can skip the table page only when its bit is set. After a VACUUM, 19,234 of 19,235 pages were all-visible; deleting rows on pages 0 and 1 cleared their bits measured: hence slow index-only scans on a table that is not vacuumed (the root's {{Query plans|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab, case 7). Values over about 2 KB are compressed or moved out of line (TOAST), so SELECT * on long LLM answers pays extra page reads.

Big values (TOAST) and the free space map (depth)

A tuple must fit in a page, so a row wider than about 2 KB has its large values compressed and, if still too big, cut into chunks in a side table: TOAST (threshold "normally 2 kB", values up to 1 GB, {{TOAST|https://www.postgresql.org/docs/18/storage-toast.html}}; pglz by default, lz4 since Postgres 14 via default_toast_compression). Two 13 KB assistant answers measured: a repetitive one compressed to 186 bytes and stayed in the page; one of hexadecimal hashes barely compresses, so its 13,199 bytes went to the TOAST table (16 KB). Long LLM answers are this case: SELECT * pays the extra page reads even when you do not need the text.

The free space map (_fsm, one byte per page in 32-byte steps, 56 KB for our 19,235 pages measured) lets an insert find a page with room ({{FSM|https://www.postgresql.org/docs/18/storage-fsm.html}}). VACUUM keeps it up to date.

What pages cost
One 150-byte row costs a whole 8 KB page, so rows read together should live together (section 8); about 24 + 4 bytes of every row are bookkeeping; updates leave dead tuples that only VACUUM reclaims ({{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} owns VACUUM tuning).
