6. LSM-trees: write first, sort later

The problem appears

Suppose the chat product logs every token-usage event, hundreds of thousands per second, keyed by a random request id. A B-tree turns each event into a change to a random leaf page: random reads to find it, random writes to put it back, a full-page image after each checkpoint. Flash and disks are far faster at writing long sequential runs than scattered pages. Can an index be maintained using only sequential writes?

The idea: buffer in memory, write sorted files, merge them later

The LSM-tree (log-structured merge-tree, {{O'Neil, Cheng, Gawlick and O'Neil, Acta Informatica, 1996|https://doi.org/10.1007/s002360050048}}; the names memtable and SSTable come from Google's {{Bigtable paper, OSDI 2006|https://research.google/pubs/bigtable-a-distributed-storage-system-for-structured-data/}}) works like this:

  1. Log it. Append the change to a write-ahead log, exactly as Postgres does, so a crash loses nothing.
  2. Memtable. Insert it into a sorted structure in memory (RocksDB uses a skip list). Nothing on disk is read or changed.
  3. Flush. When the memtable is full (64 MB by default in RocksDB) it is written out in one sequential pass as an immutable sorted file, an SSTable (sorted string table): key-value blocks, an index of the blocks, and a bloom filter. A new memtable takes over.
  4. Compact. Background threads merge-sort files together, keeping only the newest version of each key and dropping deleted ones, so the number of files stays bounded.
  5. Read. Look in the memtable, then in the files from newest to oldest, stopping at the first hit; per-file bloom filters and block indexes avoid most disk reads.

Compaction is the real design choice

Files on disk are grouped in levels. Level 0 holds freshly flushed files, which may overlap in key range; deeper levels are larger. How files move down is the compaction strategy:

Leveled (RocksDB's default)

Each level from 1 down is one sorted run, split into files with no overlap, and each level is about 10 times larger than the one above (RocksDB: level 0 compacts at 4 files, level 1 is 256 MB, multiplier 10, {{options.h|https://github.com/facebook/rocksdb/blob/main/include/rocksdb/options.h}}). A file pushed into the next level is merged with the overlapping files there, rewriting them. Few runs to search, little wasted space, many rewrites: RocksDB's tuning guide works an example to a write amplification of "approximately 1 + 2 + 10 + 10 + 10 = 33" ({{tuning guide|https://github.com/facebook/rocksdb/wiki/RocksDB-Tuning-Guide}}). Cassandra calls it LCS.

Tiered (RocksDB "universal", Cassandra STCS)

Runs of similar size accumulate; when there are enough, they are merged into one bigger run ("waits for several sorted runs with similar size and merge them together", {{universal compaction|https://github.com/facebook/rocksdb/wiki/Universal-Compaction}}). Each key is rewritten fewer times, but a read may search many runs and old versions take space until merged. Size-tiered is still Cassandra's default (cassandra.yaml); Cassandra 5.0 added a Unified Compaction Strategy that can behave like either ({{Cassandra compaction|https://cassandra.apache.org/doc/latest/cassandra/managing/operating/compaction/index.html}}).

Luo and Carey's survey gives the textbook costs with size ratio T between levels, L levels and B entries per page: writing an entry costs O(T·L/B) I/O under leveling and O(L/B) under tiering; a point lookup without bloom filters searches O(L) runs under leveling and O(T·L) under tiering ({{LSM survey, VLDB Journal 2020|https://arxiv.org/abs/1812.07527}}, section 2.3). Section 7 measures both on RocksDB.

Bloom filters: skipping files that cannot hold the key

A bloom filter is a bit array plus k hash functions. Adding a key sets k bits; asking "is key x here?" checks x's k bits: if any is 0 the answer is a certain no; if all are 1 it is maybe (other keys may have set them). With m bits for n keys the false-positive rate is about

p ≈ (1 − e−k n / m)k, best at k = (m/n) ln 2

At 10 bits per key the best k is 6.9; with k = 7, p = 0.82% derived (RocksDB's wiki: "9.9 bits per key (1% false positive rate)", {{RocksDB bloom filter|https://github.com/facebook/rocksdb/wiki/RocksDB-Bloom-Filter}}). So looking up a key that does not exist costs, on average, under 0.01 file reads per level instead of one. Bloom filters cannot help a range scan ("all keys between a and b" must still visit every run), which is the LSM-tree's weak spot.

Deletes are writes: tombstones

Files are immutable, so a delete writes a tombstone, a marker saying "this key is gone". The old value stays on disk until a compaction carrying the tombstone reaches the level that holds it; until then every read of that range must step over the tombstones. RocksDB's DeleteRange writes one range tombstone for a whole key range ({{DeleteRange|https://github.com/facebook/rocksdb/wiki/DeleteRange}}). Cassandra keeps tombstones for gc_grace_seconds, 864,000 (10 days) by default, so a replica that was down can still learn about the delete ({{CREATE TABLE|https://cassandra.apache.org/doc/latest/cassandra/reference/cql-commands/create-table.html}}); it warns when a query reads 1,000 tombstones and aborts at 100,000 (cassandra.yaml). That is why using a Cassandra table as a queue (insert, read, delete, repeat) is a classic failure: the live rows are few, the tombstones many, and reads slow down before compaction catches up.

What an LSM-tree costs
Background compaction rewrites data many times (write amplification, measured in section 7) and competes with your queries for disk and CPU. Reads may search several runs; range scans cannot use bloom filters. Space is used by old versions and tombstones until compaction. The characteristic failure: compaction falls behind a sustained write burst, level 0 piles up, reads slow down, and the engine finally throttles or stops writes ({{RocksDB write stalls|https://github.com/facebook/rocksdb/wiki/Write-Stalls}}). Alert on pending compaction bytes, not just disk space. When NOT to use one: read-mostly data with range queries, small data, or when you want Postgres's features; ingest-heavy key-value or time-series streams are its home (Cassandra, ScyllaDB, RocksDB inside many systems; the root's {{Database atlas|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab lists the products).
