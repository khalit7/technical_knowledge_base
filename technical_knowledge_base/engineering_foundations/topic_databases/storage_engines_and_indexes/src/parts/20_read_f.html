11. What indexes cost on writes, measured

The root warns that every index slows writes. By how much: the same million messages copied with one INSERT ... SELECT into an empty table with 0, 1, 3 and 6 indexes, three times each, 128 MB buffer pool measured. Predict which index is the expensive one.

Cheap until one index has random keys and outgrows memory: then 10 seconds become 2 minutes

PostgreSQL 16.2, shared_buffers 128 MB, median of 3 runs (1.7, 2.1, 10.6 and 129.8 seconds; the 6-index runs took 92.5, 129.8 and 135.2). WAL grew from 185 MB with no index to 864 MB with six, and index files to 261 MB. Index names: pkey (id), chat_created (chat_id, created_at), created (created_at), model_tokens, role_chat, content (the message text, random-looking, 30 to 130 characters).

An index on an increasing key (the primary key, created_at) is cheap: a sequential stream of leaf pages and its share of WAL. The expensive one has random-order keys and outgrows memory: the B-tree on content (random-looking text, 144 MB against a 128 MB buffer pool) turned an insert of about 10 seconds into about 2 minutes, because each row needs a random leaf page that is probably not cached. Single-row inserts through a connection (pgbench, 4 clients, commit not waiting for the flush) showed no trend, between about 12,600 and 23,500 per second across 0 to 6 indexes: microseconds of index work hide behind the round trip until the indexes stop fitting in memory. Index cost is invisible in a small benchmark and decisive at scale.

Find indexes nobody uses
SELECT indexrelid::regclass, idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) FROM pg_stat_user_indexes ORDER BY idx_scan, pg_relation_size(indexrelid) DESC; An index with idx_scan = 0 after weeks of normal traffic (and not backing a constraint) is pure write cost; check replicas too, since the counters are per server ({{statistics views|https://www.postgresql.org/docs/18/monitoring-stats.html}}). Build new indexes with CREATE INDEX CONCURRENTLY so writes are not blocked.

12. Column stores, in one section

Everything above keeps a row's columns together, which suits "fetch this chat". Analytics reads one or two columns of every row ("total tokens per model over a year"), so a column store keeps each column in its own compressed chunks: on the root page the same aggregate needed 94 times fewer bytes from Parquet than from the Postgres heap measured there. Column stores skip blocks by sort order and zone maps (min and max per block, BRIN's idea) rather than B-trees, and their storage is LSM-shaped. {{Analytics: columnar engines, DuckDB and the lakehouse|n:3ef5c17b0d0d8157814ec5dd8a0d4fb5}} owns the details.

ClickHouse's MergeTree as an example (depth)

ClickHouse's MergeTree writes each insert as an immutable sorted part and merges parts in the background, with a sparse primary index of one entry per 8,192 rows ({{MergeTree|https://clickhouse.com/docs/engines/table-engines/mergetree-family/mergetree}}). Because skipping depends on how data was sorted when it was written, sort order matters more there than any index added later. The analytics page covers Parquet layout, encodings, DuckDB and the lakehouse.
