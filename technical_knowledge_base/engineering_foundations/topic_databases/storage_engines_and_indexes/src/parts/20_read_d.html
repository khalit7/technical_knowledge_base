6. LSM-trees: write first, sort later

Suppose the chat product logs every token-usage event, hundreds of thousands a second, keyed by a random request id. A B-tree turns each into a random leaf read and write plus a page image after each checkpoint, while flash and disks are far faster at long sequential writes. The LSM-tree (log-structured merge-tree, {{O'Neil, Cheng, Gawlick and O'Neil, Acta Informatica, 1996|https://doi.org/10.1007/s002360050048}}; memtable and SSTable are names from Google's {{Bigtable paper, OSDI 2006|https://research.google/pubs/bigtable-a-distributed-storage-system-for-structured-data/}}) maintains an index with sequential writes only:

  1. Log it. Append the change to a write-ahead log, exactly as Postgres does, so a crash loses nothing.
  2. Memtable. Insert it into a sorted structure in memory (RocksDB uses a skip list). Nothing on disk is read or changed.
  3. Flush. When the memtable is full (64 MB by default in RocksDB) it is written in one sequential pass as an immutable sorted file, an SSTable (sorted string table): key-value blocks, an index of the blocks, and a bloom filter. A new memtable takes over.
  4. Compact. Background threads merge-sort files together, keeping only the newest version of each key and dropping deleted ones, so the number of files stays bounded.
  5. Read. Look in the memtable, then in the files from newest to oldest, stopping at the first hit; per-file bloom filters and block indexes avoid most disk reads.

The same key into both engines: the B-tree pays three random page writes now, the LSM-tree pays a rewrite later

illustrative Four keys per page or file (a real leaf holds about 367 bigint keys). B-tree: key 42 splits a full leaf, the parent gains separator 40, three dirty pages are written back at the checkpoint. LSM: one log append and a memtable insert; the flush writes 4 keys sequentially; compaction later rewrites 16 keys to place 4 new ones.

Compaction is the real design choice

Files on disk are grouped in levels: level 0 holds freshly flushed files, which may overlap in key range; deeper levels are larger. How files move down is the compaction strategy:

Leveled (RocksDB's default)

Each level from 1 down is one sorted run, split into files with no overlap, each level about 10 times the one above (RocksDB: level 0 compacts at 4 files, level 1 is 256 MB, multiplier 10, {{options.h|https://github.com/facebook/rocksdb/blob/main/include/rocksdb/options.h}}). A file pushed down is merged with the overlapping files there, rewriting them. Few runs to search, little wasted space, many rewrites: RocksDB's tuning guide works an example to a write amplification of "approximately 1 + 2 + 10 + 10 + 10 = 33" ({{tuning guide|https://github.com/facebook/rocksdb/wiki/RocksDB-Tuning-Guide}}). Cassandra calls it LCS.

Tiered (RocksDB "universal", Cassandra STCS)

Runs of similar size accumulate; when there are enough, they merge into one bigger run ("waits for several sorted runs with similar size and merge them together", {{universal compaction|https://github.com/facebook/rocksdb/wiki/Universal-Compaction}}). Each key is rewritten fewer times, but a read may search many runs and old versions take space until merged. Size-tiered is still Cassandra's default (cassandra.yaml); Cassandra 5.0 added a Unified Compaction Strategy that can behave like either ({{Cassandra compaction|https://cassandra.apache.org/doc/latest/cassandra/managing/operating/compaction/index.html}}).

The textbook costs of leveling and tiering (formulas)

With size ratio T between levels, L levels and B entries per page, Luo and Carey give the textbook costs: writing an entry costs O(T·L/B) I/O under leveling and O(L/B) under tiering; a point lookup without bloom filters searches O(L) runs under leveling and O(T·L) under tiering ({{LSM survey, VLDB Journal 2020|https://arxiv.org/abs/1812.07527}}, section 2.3). Section 7 measures both on RocksDB.

Bloom filters: skipping files that cannot hold the key

A bloom filter is a bit array plus k hash functions. Adding a key sets k bits; asking "is x here?" checks x's k bits: any 0 is a certain no; all 1 is maybe (other keys may have set them). With m bits for n keys the false-positive rate is about

p ≈ (1 − e−k n / m)k, best at k = (m/n) ln 2

At 10 bits per key the best k is 6.9; with k = 7, p = 0.82% derived (RocksDB's wiki: "9.9 bits per key (1% false positive rate)", {{RocksDB bloom filter|https://github.com/facebook/rocksdb/wiki/RocksDB-Bloom-Filter}}). A lookup for a key that does not exist then costs under 0.01 file reads per level instead of one. Bloom filters cannot help a range scan ("all keys between a and b" must visit every run), the LSM-tree's weak spot.

Each extra bit per key cuts false positives by about 38% (p ≈ 0.62 to the power of the bits per key, at the best k), for 125 kB more memory per million keys

Deletes are writes: tombstones

Files are immutable, so a delete writes a tombstone, a marker saying "this key is gone". The old value stays on disk until a compaction carrying the tombstone reaches its level, and until then every read of that range steps over the tombstones. RocksDB's DeleteRange writes one range tombstone for a whole key range ({{DeleteRange|https://github.com/facebook/rocksdb/wiki/DeleteRange}}). That is why using a Cassandra table as a queue (insert, read, delete, repeat) is a classic failure: the live rows are few, the tombstones many, and reads slow down before compaction catches up.

Cassandra's tombstone settings (depth)

Cassandra keeps tombstones for gc_grace_seconds, 864,000 (10 days) by default, so a replica that was down can still learn about the delete ({{CREATE TABLE|https://cassandra.apache.org/doc/latest/cassandra/reference/cql-commands/create-table.html}}); it warns when a query reads 1,000 tombstones and aborts at 100,000 (cassandra.yaml). {{NoSQL in practice|n:3ef5c17b0d0d81ec8456c41e4e8f5f6b}} covers Cassandra in use.

What an LSM-tree costs
Compaction rewrites data many times (section 7) and competes with queries for disk and CPU; reads may search several runs and range scans cannot use bloom filters; old versions and tombstones take space until merged. The characteristic failure: compaction falls behind a write burst, level 0 piles up, reads slow, and the engine throttles or stops writes ({{RocksDB write stalls|https://github.com/facebook/rocksdb/wiki/Write-Stalls}}); alert on pending compaction bytes, not just disk space. Its home is ingest-heavy key-value and time-series streams (Cassandra, ScyllaDB, RocksDB inside many systems; the root's {{Database atlas|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab lists the products), not read-mostly data with range queries or small data.

7. The RUM trade-off, measured

Every way of storing and indexing data pays three overheads: extra Reads beyond the data asked for, extra Update work beyond the bytes changed, and extra Memory or space beyond the data itself. The RUM conjecture: "designing access methods that set an upper bound for two of the RUM overheads, leads to a hard lower bound for the third overhead which cannot be further reduced" ({{Athanassoulis et al., EDBT 2016|https://openproceedings.org/2016/conf/edbt/paper-12.pdf}}). They are measured as amplification factors: write amplification, bytes written to storage per byte the application wrote (log, pages, compaction rewrites); read amplification, pages or files read per lookup; space amplification, bytes on disk per byte of live data.

Each design sits near the corner it optimises and pays on the far side

Placement is qualitative, from this page's measurements: a B-tree bounds reads (3 pages) and space and pays on updates (up to 307x for scattered updates after a checkpoint); leveled LSM bounds space (1.10x) and pays rewrites; tiered LSM rewrites less at scale but needed 1.71x the space and searches more runs; BRIN is tiny (73.7 kB for 10M rows) and reads whole 128-page ranges. An index pays space and update cost to cut reads; compression pays CPU to cut space.

Measured on two real engines

RocksDB through the rocksdict Python binding, statistics on measured: 4,000,000 unique random 16-byte keys with 100-byte values (464 MB of data), then 4,000,000 overwrites of random existing keys; memtable 8 MB, level 1 32 MB, ratio 10, no compression, bloom filters 10 bits per key; 100,000 lookups of present and of absent keys.

Leveled compaction wrote 5.0x on load and 6.2x on overwrite (flushes plus compaction over the bytes the application wrote; the write-ahead log adds 1 more) and kept 1.10x space; universal (tiered) wrote about as much at this size but held 1.71x. Bloom filters at work: an absent-key lookup read 0.01 data blocks on average with them and 4.43 without; the measured false-positive rate was 0.97% per filter checked (formula: 0.82%).

How the RocksDB factors were computed (method)

Space amplification is SST bytes on disk after the overwrites divided by the SST bytes of the same unique keys fully compacted (the leveled run after loading); RocksDB's own live-data estimate was unreliable under universal compaction. Write amplification counts memtable flushes plus compaction writes divided by the bytes the application wrote.

Postgres on the 1M-message table measured: write amplification depends on where the writes land far more than on the engine.

Logical bytes are the rows without their 24-byte headers (128 bytes per message on average, from pgstattuple). Append: WAL plus the table and index files (251 MB + 158 MB + 22.5 MB), 3.4x. Updates: WAL (19.3 MB) plus the 2,448 pages the checkpoint will write back, counted as one write each (the number of page images, a lower bound), 307x. Read amplification for a point lookup is the tree height (3 here) plus one table page per row; the table's space amplification is about 1.23x (headers, alignment, free space).

Correction to the old page
The old page gave B-tree write amplification as "easily 10x to 40x", LSM leveled as "roughly 10x to 30x", and space amplification as 1.3x (B-tree), 1.1x (leveled) and "up to 2x or more" (tiered), without sources. One number misleads: Postgres measured about 3.4 times for appends and about 300 times for scattered updates after a checkpoint; leveled RocksDB about 5 to 6 times, growing with the levels the data spans (half a gigabyte sits in two levels here; RocksDB's worked example reaches 33). Tiered wrote about as much at this size but needed 1.7 times the space against 1.1; its write saving appears as data spans more levels (Luo and Carey: L against T times L). Quote amplification with its workload.
How to use this
Name the corner you give up: a ledger read and updated by key wants bounded reads (B-tree); an event firehose wants cheap writes (LSM, or an append-only Postgres table with BRIN); a cold archive wants little space (columnar, compressed, section 12). Then measure write amplification on your workload: on flash it sets how fast drives wear out and how much I/O compaction or checkpoints take from queries.
