3. The write-ahead log: what is written, when, and what it costs

The problem appears

A commit must survive a power cut the moment the database says "saved". Writing every changed page to its place on disk at commit time would mean several random writes per transaction, and a crash halfway through would leave some pages new and some old. The parent page's section 4 introduced the fix, the write-ahead log (WAL), with an animation; here is what is really in it and what it costs.

What is logged

Every change to a page produces a WAL record: which subsystem (heap, B-tree, transaction), which page, and just enough bytes to redo the change. Records are appended to one sequential stream, stored as 16 MB segment files in pg_wal/. A record's position in that stream, in bytes, is its LSN (log sequence number), shown as two hex numbers such as 0/111CFE90 ({{WAL internals|https://www.postgresql.org/docs/18/wal-internals.html}}). Each page header stores the LSN of the last record that changed it, and the buffer pool refuses to write a dirty page to disk until the log is flushed up to that LSN: that ordering is the whole "write-ahead" rule.

Checkpoints, and why the first change after one is expensive

The log cannot grow forever and recovery should not replay a week of it. A checkpoint writes every dirty page in the buffer pool to its file, then records "everything before this LSN is on disk"; older WAL can then be recycled. Postgres starts one every checkpoint_timeout (5 minutes) or when max_wal_size (1 GB) of WAL has accumulated, and spreads its writes over 90% of the interval (checkpoint_completion_target 0.9) to avoid an I/O spike ({{WAL settings|https://www.postgresql.org/docs/18/runtime-config-wal.html}}).

Now the subtle part. A disk writes in sectors of 512 bytes or 4 KB, so an 8 KB page write interrupted by a power cut can leave a torn page: half new, half old. A small delta record cannot repair a page whose old contents are garbage. So with full_page_writes on (the default), the first change to each page after a checkpoint logs a copy of the whole page, a full-page image (FPI); later changes to that page until the next checkpoint log only deltas ({{full_page_writes|https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-FULL-PAGE-WRITES}}). InnoDB solves the same problem differently, with a doublewrite buffer ({{MySQL docs|https://dev.mysql.com/doc/refman/8.4/en/innodb-doublewrite-buffer.html}}).

Bottom: 1,000 updates of random messages (977 different table pages) just after a CHECKPOINT, then the same 1,000 updates again.

The lesson is about access patterns more than settings: the 1,000 random updates produced 19.3 MB of WAL right after a checkpoint, 50 times the 0.39 MB they produce without page images, and 0.50 MB when repeated once those pages had been imaged measured. Writes that land on few pages (appends at the end of a table, inserts in key order) pay few images; writes scattered over many pages pay one image per page per checkpoint. wal_compression = pglz cut the images to 6.2 MB here (lz4 and zstd are also available since Postgres 15). Longer checkpoint intervals mean fewer images but more WAL to replay after a crash.

Do not turn full_page_writes off
The docs warn that turning it off "might lead to either unrecoverable data corruption, or silent data corruption, after a system failure". It is safe only on storage that guarantees atomic 8 KB writes (for example ZFS, which is copy-on-write). Use wal_compression and checkpoint tuning instead.

fsync: the moment "saved" becomes true

write() only copies bytes into the operating system's page cache; fsync() (or fdatasync()) asks the OS to push them to the device and waits until the device says they are stored. A commit waits for the WAL flush and nothing else: the data pages are written later by the checkpointer and background writer. On Linux Postgres flushes with fdatasync by default ({{wal_sync_method|https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-WAL-SYNC-METHOD}}). On macOS the default does not empty the drive's own cache; fsync_writethrough does, and that is the setting used for the numbers below, so they are real flushes.

Correction to the old page
The old page said stable storage is "10,000 times slower than memory" and put an enterprise-SSD fsync at "0.1 to 1 ms". It depends on the hardware: an SSD with power-loss protection acknowledges a flush in about 1.6 to 12 microseconds (its capacitor-backed cache counts as stable), a consumer SSD takes about 0.9 to 3 ms, network block storage about 0.7 ms (the root's notes and the system design page's Numbers to know tab). This laptop: 6.0 ms per single-client commit measured.

Group commit and synchronous_commit

Because one flush covers everything written to the log before it, transactions committing at the same moment share it: that is group commit ("one fsync of the WAL file may suffice to commit many transactions", {{WAL introduction|https://www.postgresql.org/docs/18/wal-intro.html}}; commit_delay can make the flushing transaction wait a few microseconds to gather more, {{commit_delay|https://www.postgresql.org/docs/18/runtime-config-wal.html}}). For the cases where losing the last instant of commits is acceptable, synchronous_commit = off acknowledges the commit before the flush; the WAL writer flushes a moment later. A crash can then lose the last transactions, at most three times wal_writer_delay (3 x 200 ms), but it "does not create any risk of database inconsistency": the lost transactions vanish whole ({{synchronous_commit|https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT}}).

measured pgbench, 20 s per run, each transaction one UPDATE of a random user's credit row, real flushes (fsync_writethrough), loopback connection on the same laptop. The root measured the same shape with pgbench's default script: 148 and 2,133 per second with the flush.

Read it this way: with the flush, one client waits 6 ms per commit, so at most about 165 commits a second; 32 clients share flushes and reach 2,603 (16 times more for 32 times the clients). Without waiting for the flush, the same work runs at 7,504 and 71,439 a second: the flush, not the update, was the cost. The professional move is to choose per transaction: SET LOCAL synchronous_commit = off inside a transaction that logs a page view or a token-usage event, never inside one that spends credits. The other values (local, remote_write, remote_apply) decide how long a commit waits for replicas; {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} owns replication.

When fsync fails

In 2018 PostgreSQL developers found that on Linux a failed fsync could drop the dirty pages and report success on the next call, so "retry the fsync" could silently lose data ({{LWN, "PostgreSQL's fsync() surprise", 2018-04-18|https://lwn.net/Articles/752063/}}). Since the February 2019 minor releases (11.2 and the back branches), Postgres instead stops with a PANIC on a failed data-file flush and recovers from the WAL on restart; data_sync_retry (default off) controls it ({{error handling settings|https://www.postgresql.org/docs/18/runtime-config-error-handling.html#GUC-DATA-SYNC-RETRY}}, {{11.2 notes|https://www.postgresql.org/docs/release/11.2/}}).

The same log is reused far beyond crash safety: shipped to another server it keeps a replica current; replayed up to a chosen moment it restores a backup to that moment (point-in-time recovery); decoded by another program it becomes a stream of changes (change data capture, as Debezium does). Redo log, journal, binlog, commit log and oplog are the same idea in other products. {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} owns backups and replication; {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}} owns change data capture.

To see recovery work, we took a checkpoint, inserted 1,000 messages in one committed transaction, then killed the server process with kill -9 (no chance to write anything) and restarted it measured.   2. Go to the redo point. The checkpoint record names the LSN from which every change might be missing from the data files: "redo starts at 0/111CFE90" ({{WAL internals|https://www.postgresql.org/docs/18/wal-internals.html}}: "performs the REDO operation by scanning forward from the WAL location indicated in the checkpoint record").

  3. Replay each record. A record with a full-page image overwrites the page with it, which also repairs a torn page. A delta record is applied only if the page's stored LSN is older than the record's; otherwise the change is already on disk and is skipped. That comparison makes replay safe to repeat if the server crashes again during recovery ({{xlogutils.c|https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/access/transam/xlogutils.c}}).

  4. Find the end of the log. Each record carries a CRC checksum; the first record that is missing or fails its check marks the end: "invalid record length at 0/119D8C78: expected at least 24, got 0" is the normal end, not an error. Transactions whose commit record was not reached never become visible.

  5. Checkpoint and open. An end-of-recovery checkpoint wrote the 1,015 pages the replay had rebuilt, and the server accepted connections. All 1,000 committed rows were there; the restart took 0.22 seconds for 8.4 MB of log.

What recovery costs
Time proportional to the WAL written since the last checkpoint. A max_wal_size of tens of GB on a write-heavy server means minutes of replay after a crash; that is the other side of fewer checkpoints and fewer page images. Recovery protects committed transactions against a crash, not against a lost disk or a bad DELETE: that takes backups and replicas.
