2. The buffer pool, and the operating system's cache under it

The problem appears

Opening chat 42000 needs about a dozen pages (the root measured 12 page touches for its 6 messages). If every one came from the SSD at about 100 microseconds, a busy server doing thousands of lookups a second would spend most of its time waiting on the disk, re-reading the same popular pages (the top levels of every index, the newest messages) again and again.

The idea: keep hot pages in memory, evict the cold ones

The buffer pool is a fixed area of RAM divided into 8 KB slots (buffers), plus a hash table from "file, page number" to slot. In Postgres it is shared_buffers, 128 MB by default; the docs suggest starting at 25% of RAM on a dedicated server and say more than 40% is unlikely to help, "because PostgreSQL also relies on the operating system cache" ({{resource settings|https://www.postgresql.org/docs/18/runtime-config-resource.html#GUC-SHARED-BUFFERS}}). Every page access goes through it: a hit costs a memory lookup; a miss must pick a victim slot (writing it out first if it was changed, or dirty), then read the page in.

Which slot to evict? Keeping exact "least recently used" order would need a lock on a shared list for every access, so Postgres uses a clock sweep ({{buffer manager README|https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/storage/buffer/README}}): each buffer has a usage count, raised by one on every access up to a cap of 5 (BM_MAX_USAGE_COUNT in {{buf_internals.h|https://github.com/postgres/postgres/blob/REL_18_STABLE/src/include/storage/buf_internals.h}}). A "clock hand" walks round the buffers; each buffer it passes loses one point, and the first one found at zero is evicted. Pages used often survive several sweeps; a page read once is gone after one.

illustrative Eight buffers and a scripted list of page requests: the index root and an inner page are asked for often; table pages once each. The rule (raise to at most 5 on access, lower by one as the hand passes, evict at zero) is the real one; the real pool has 16,384 buffers at 128 MB.

On the real server, after a mixed workload, the 611 buffers in use had usage counts 1: 154, 2: 122, 3: 90, 4: 54, 5: 191 measured with the {{pg_buffercache|https://www.postgresql.org/docs/18/pgbuffercache.html}} extension: a quarter of them were touched only once, while a hot set of 191 (index upper levels, catalog pages) sat at the cap.

A big scan must not flush the cache: ring buffers

A full scan of a large table would push every hot page out for pages it will never read again. So a sequential scan of a table larger than a quarter of shared_buffers reuses a small private ring of 256 kB (32 buffers); VACUUM uses a 2 MB ring and bulk writes 16 MB ({{README|https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/storage/buffer/README}}, sizes in {{freelist.c|https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/storage/buffer/freelist.c}}). Measured on the 157 MB table with a 128 MB pool, after a restart measured: a full scan read all 19,235 pages and left exactly 32 of them in shared_buffers; a second scan found only those 32 and "read" the other 19,203 again. Both scans took about 74 ms because every one of those reads was served by the operating system's cache (next paragraph), not by the SSD; the root's {{Query plans|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab (case 8) measures a truly cold read.

Double buffering: the operating system caches the same pages

A Postgres "read" is a normal file read, so the operating system keeps its own copy of recently read file blocks in otherwise unused RAM (the page cache). A page can therefore be cached twice, once in shared_buffers and once in the page cache: double buffering. Postgres accepts it and leans on the OS cache (hence the modest 25%); the planner's effective_cache_size (default 4 GB) tells it how much the two caches hold together. InnoDB takes the other road: a large buffer pool (up to 80% of memory on a dedicated server) and, since MySQL 8.4, O_DIRECT on Linux so its reads bypass the OS cache ({{InnoDB buffer pool|https://dev.mysql.com/doc/refman/8.4/en/innodb-buffer-pool.html}}, {{8.4 defaults|https://dev.mysql.com/doc/refman/8.4/en/mysql-nutshell.html}}). Postgres 18 added asynchronous I/O (io_method, default worker, or io_uring on Linux builds), which lets a scan queue many reads at once rather than one at a time ({{PG 18 release notes|https://www.postgresql.org/docs/18/release-18.html}}).

What the cache costs, and the cliff
RAM. The hit ratio is the strongest single predictor of OLTP latency, and it does not degrade smoothly: while the working set (the pages your traffic touches) fits in RAM, almost every access is a memory hit; once it does not, a fraction of accesses each pay a disk read, a hundred to a thousand times slower, and p99 latency changes character. Watch blks_hit against blks_read in pg_stat_database; the root's {{Query plans|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab measures the same query cold and warm (case 8).
