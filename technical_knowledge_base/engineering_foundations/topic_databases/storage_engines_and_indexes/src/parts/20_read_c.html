5. B-trees: the default index

Chat 42000's 6 messages are scattered over 19,235 pages; without an index the database reads every page (the root measured 19,349 page reads and 28 ms). A B-tree (strictly a B+tree, the variant relational databases use) reaches them in a handful of reads, stays correct under concurrent inserts, and also answers "between" and "in order". Its nodes are pages: leaf pages hold the keys in sorted order, each with its row's ctid, linked to their right neighbour so a range scan walks sideways; internal pages hold separator keys and downlinks ("keys below 25,047 are under page 3"); the root is the page at the top, and page 0, the metapage, says where it is.

Concurrency: high keys and right links (Lehman and Yao) (depth)

Postgres follows Lehman and Yao's 1981 design: each page also stores a high key (an upper bound for its contents) and a right-sibling link, so a reader that arrives at a page just split can step right instead of waiting for a lock ({{nbtree README|https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/access/nbtree/README}}).

  3. Internal page (page 288): 285 entries, each a separator and a downlink; binary search leads to leaf page 478.

Fan-out: why a billion rows need about four levels

The children per internal page, the fan-out, keeps the tree shallow. A bigint entry is an 8-byte header plus the key, rounded up to 8 bytes, plus a 4-byte line pointer: 20 bytes. A page has 8,152 usable bytes (8,192 minus a 24-byte header and a 16-byte trailer), so about 407 entries fit; Postgres fills leaves to 90% when it builds an index or appends at the right edge (367 entries) and internal pages to 70% (about 285) ({{B-tree fillfactor|https://www.postgresql.org/docs/18/sql-createindex.html}}, {{nbtree.h|https://github.com/postgres/postgres/blob/REL_18_STABLE/src/include/access/nbtree.h}}):

levels = 1 + ⌈logf(N / l)⌉
N
number of keys
l
keys per leaf page (367 for bigint at 90% fill)
f
fan-out of internal pages (about 285 for bigint at 70% fill)

Predict the levels for a billion bigint keys, then drag; wider keys cost levels sooner

Defaults reproduce the measurement independently: 367 keys per leaf and 3 levels at 1M bigint rows, as Postgres reported. At 100 million rows Postgres built 4 levels with a root of only 4 entries, room for about 71 times more keys, so a billion rows need 4 levels derived. A 36-character text key (a UUID stored as text) fits 141 entries per leaf instead of 367: 59.1 MB at 1M rows against 22.5 MB for bigint (text counted as 1 length byte plus the characters; collation and compression also matter).

The top one or two levels are touched by every lookup, so they stay cached: a lookup on a big table costs one or two physical reads, not four (the old page's "3 to 4 page reads for a large table plus one heap fetch, mostly cached" holds; the root measured 12 page touches, all cache hits, for the 6-row chat).

Inserting: splits, and why random keys waste space

An insert walks down to its leaf and adds the entry in order. A full leaf splits: a new page takes the upper half and the parent gets a separator for it; a full parent splits too, and a root split adds a level (the tree grows at the top, so every leaf stays at the same depth). Section 6 steps through one split; the {{B-tree and LSM lab|#t-lab}} runs thousands. When the new key is the largest, Postgres keeps the left page at the fillfactor (90%) instead of half, because an increasing key never inserts there again ({{nbtree.h|https://github.com/postgres/postgres/blob/REL_18_STABLE/src/include/access/nbtree.h}}: "The fillfactor is applied during index build and when splitting a rightmost page"). Random keys split pages in the middle and half-empty pages fill only partly before splitting again: the classic result is about 69% average fill (ln 2).

The same million keys in random order need 38% more leaf pages

measured PostgreSQL 16.2, 1M bigint keys. Random order ended 66% full on average (close to the textbook 69%) and took 1.6 times as long, with everything still in memory.

Primary keys: bigint, UUID v4 or UUID v7

This matters most for the primary key, which every row inserts into. A UUID is a 16-byte identifier generated anywhere without coordination: version 4 is random, so consecutive rows land on random leaves; version 7 starts with a timestamp, so new rows go to the right edge like a sequence ({{RFC 9562|https://www.rfc-editor.org/rfc/rfc9562}}, 2024; Postgres 18 added uuidv7(), {{PG 18 release notes|https://www.postgresql.org/docs/18/release-18.html}}).

A random key leaves the primary-key index a third emptier, and bigger, than a time-ordered one

measured PostgreSQL 18.6, 3M rows inserted in batches of 100,000 into a table whose only index is the primary key, 128 MB buffer pool. The UUID v4 index ended 68% full against 90% for v7, so it is 1.33 times the size; it wrote 9% more WAL and took 1.4 times as long. Part of the gap to bigint is generating UUIDs, not the index. The 126 MB index still almost fits the 128 MB pool; a random-key index several times larger than memory also waits for a disk read per insert (section 11: about 12 times slower).

{{SQL and data modelling|n:3ef5c17b0d0d813980dcd474e19f6c3f}} (section 7) turns this into a key choice and measures the three key types at 1M and 10M rows: random UUID v4 keys cost a bigger index and more WAL than v7 for the same rows. On InnoDB the penalty is larger, because the primary key orders the whole table (section 8).

Duplicates, dead entries, skip scan and size limits (depth)
  • Deduplication (Postgres 13): when many rows share a key, the leaf stores the key once followed by a sorted list of ctids, a posting list ({{PG 13 notes|https://www.postgresql.org/docs/release/13.0/}}; deduplicate_items, on by default). Chat 42000's entry is one 56-byte item holding 6 ctids. On a column with 4 distinct values (model), the index is 7.0 MB with deduplication and 27.1 MB without (3.9 times larger) measured.
  • Bottom-up deletion (Postgres 14): an update that is not HOT adds a new entry to every index even when the key did not change. Before splitting a page full of such versions, Postgres checks which entries point to dead row versions and deletes them, so version churn does not bloat the index ({{PG 14 notes|https://www.postgresql.org/docs/release/14.0/}}, {{B-tree deletion|https://www.postgresql.org/docs/18/btree.html#BTREE-DELETION}}).
  • Skip scan (Postgres 18): an index on (a, b) used to be nearly useless for a query on b alone. Postgres 18 can "skip" through the distinct values of a, one small descent per value ({{PG 18 notes|https://www.postgresql.org/docs/18/release-18.html}}: "allows multi-column btree indexes to be used in more cases such as when there are no restrictions on the first or early indexed columns"). An index on (model, created_at), four models, a one-hour window on created_at measured: Postgres 16 read the whole index, 4,382 pages (54.4 ms as it chose, 23.8 ms forced onto the index); Postgres 18 used an Index Only Scan with 9 index searches, 46 pages, 0.26 ms.
  • Limits: an index entry cannot exceed about a third of a page (2,704 bytes), so long text needs a hash or expression index; an index can have up to 32 columns; only B-trees can enforce UNIQUE ({{B-tree docs|https://www.postgresql.org/docs/18/btree.html}}, {{unique indexes|https://www.postgresql.org/docs/18/indexes-unique.html}}).
What a B-tree costs
Every insert dirties a leaf; random keys dirty pages all over the file (random writes, more page images, about 30% empty space), and every index on a table repeats this for every row. Skip it for a column you never search by, a tiny table, a huge append-only table queried by time (BRIN, section 9, was about 3,000 times smaller), or a write stream faster than random page writes can absorb (an LSM-tree, next).
