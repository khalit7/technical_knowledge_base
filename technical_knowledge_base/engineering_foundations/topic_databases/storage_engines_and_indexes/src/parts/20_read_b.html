2. The buffer pool, and the operating system's cache under it

Opening chat 42000 touches about a dozen pages (the root measured 12 for its 6 messages); at about 100 microseconds per SSD read, a busy server would spend its time re-reading the same popular pages, the top of every index and the newest messages. The buffer pool keeps them in RAM: 8 KB slots plus a hash table from (file, page) to slot. In Postgres it is shared_buffers, 128 MB by default; the docs suggest 25% of RAM on a dedicated server and say more than 40% is unlikely to help, "because PostgreSQL also relies on the operating system cache" ({{resource settings|https://www.postgresql.org/docs/18/runtime-config-resource.html#GUC-SHARED-BUFFERS}}). A hit is a memory lookup; a miss evicts a victim (writing it first if dirty, changed since read) and reads the page in.

Exact least-recently-used order would need a lock on a shared list for every access, so Postgres uses a clock sweep ({{buffer manager README|https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/storage/buffer/README}}): each buffer has a usage count, raised by one on every access up to 5 (BM_MAX_USAGE_COUNT in {{buf_internals.h|https://github.com/postgres/postgres/blob/REL_18_STABLE/src/include/storage/buf_internals.h}}); a hand walks round the buffers taking one point from each, and evicts the first at zero. Predict: after twenty requests, which pages are still cached?

Pages used often survive every sweep; a page read once is gone after one

illustrative Eight buffers and a scripted list of requests: the index root and an inner page are asked for often, table pages once each. The rule is the real one; the real pool has 16,384 buffers at 128 MB. On the real server after a mixed workload, the 611 buffers in use had usage counts 1: 154, 2: 122, 3: 90, 4: 54, 5: 191 measured with {{pg_buffercache|https://www.postgresql.org/docs/18/pgbuffercache.html}}: a quarter touched once, a hot set of 191 (index upper levels, catalog pages) at the cap.

A big scan must not flush the cache. A sequential scan of a table larger than a quarter of shared_buffers reuses a private ring of 256 kB (32 buffers); VACUUM uses 2 MB and bulk writes 16 MB ({{README|https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/storage/buffer/README}}, {{freelist.c|https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/storage/buffer/freelist.c}}). On the 157 MB table with a 128 MB pool, after a restart measured: a full scan read all 19,235 pages and left exactly 32 cached; a second scan found those 32 and "read" the other 19,203 again, both in about 74 ms because the operating system's cache served them (the root's {{Query plans|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab, case 8, measures a truly cold read).

That is double buffering: a Postgres read is a normal file read, so the OS keeps its own copy in its page cache ({{Storage and file systems|n:3f05c17b0d0d8141be7acc1313570cbf}} owns it) and a page can be cached twice. Postgres leans on that, hence the modest 25%.

InnoDB's other road, effective_cache_size, and Postgres 18's asynchronous I/O (depth)

The planner's effective_cache_size (default 4 GB) tells Postgres how much the two caches hold together. InnoDB takes the other road: a large buffer pool (up to 80% of memory on a dedicated server) and, since MySQL 8.4, O_DIRECT on Linux so its reads bypass the OS cache ({{InnoDB buffer pool|https://dev.mysql.com/doc/refman/8.4/en/innodb-buffer-pool.html}}, {{8.4 defaults|https://dev.mysql.com/doc/refman/8.4/en/mysql-nutshell.html}}). Postgres 18 added asynchronous I/O (io_method, default worker, or io_uring on Linux builds), which lets a scan queue many reads at once ({{PG 18 release notes|https://www.postgresql.org/docs/18/release-18.html}}).

What the cache costs, and the cliff
RAM. The hit ratio is the strongest single predictor of OLTP latency and it does not degrade smoothly: while the working set (the pages your traffic touches) fits in RAM almost every access is a hit; beyond that a fraction of accesses pay a disk read, a hundred to a thousand times slower, and p99 latency changes character. Watch blks_hit against blks_read in pg_stat_database.

3. The write-ahead log: what is written, when, and what it costs

A commit must survive a power cut the moment the database says "saved", but writing every changed page in place at commit means several random writes, and a crash halfway leaves some pages new and some old. So every change first becomes a WAL record (subsystem, page, just enough bytes to redo it) appended to one sequential stream, the write-ahead log, kept as 16 MB files in pg_wal/. A record's byte position is its LSN (log sequence number, such as 0/111CFEA0). Each page header stores the LSN of the last record that changed it, and a dirty page may not be written until the log is flushed up to that LSN: the whole "write-ahead" rule ({{WAL internals|https://www.postgresql.org/docs/18/wal-internals.html}}). Checkpoints, and why the first change after one is expensive

A checkpoint writes every dirty page to its file and records "everything before this LSN is on disk", so older WAL can be recycled and recovery starts there; Postgres starts one every checkpoint_timeout (5 minutes) or after max_wal_size (1 GB) of WAL, spread over 90% of the interval (checkpoint_completion_target 0.9, {{WAL settings|https://www.postgresql.org/docs/18/runtime-config-wal.html}}); setting them in operation, and why pg_wal/ grows, is {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} section 1. The subtle part: disks write 512-byte or 4 KB sectors, so a power cut during an 8 KB page write can leave a torn page, half new and half old, that no small delta can repair. So with full_page_writes on (the default) the first change to each page after a checkpoint logs the whole page, a full-page image (FPI), and later changes only deltas ({{full_page_writes|https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-FULL-PAGE-WRITES}}; InnoDB uses a {{doublewrite buffer|https://dev.mysql.com/doc/refman/8.4/en/innodb-doublewrite-buffer.html}} instead). Predict: 1,000 updates of random rows right after a checkpoint, how much WAL?

Scattered writes after a checkpoint pay one whole-page image per page: 50 times the WAL

measured PostgreSQL 16.2, the 1M-message table with its primary key and chat_id index. Top: one insert just after a CHECKPOINT, page images off and on (the 17,638 bytes are three page images, with the empty middle of each page left out, plus the commit). Bottom: 1,000 updates of random messages (977 different table pages) just after a CHECKPOINT, then the same 1,000 again.

They wrote 19.3 MB of WAL, 50 times the 0.39 MB without page images, and 0.50 MB when repeated once those pages had been imaged. Access pattern matters more than settings: writes on few pages (appends, inserts in key order) pay few images; writes scattered over many pages pay one per page per checkpoint. wal_compression = pglz cut it to 6.2 MB (lz4 and zstd since Postgres 15). Longer checkpoint intervals mean fewer images but more WAL to replay after a crash.

Do not turn full_page_writes off
The docs warn that turning it off "might lead to either unrecoverable data corruption, or silent data corruption, after a system failure". It is safe only on storage that guarantees atomic 8 KB writes (for example ZFS, which is copy-on-write). Use wal_compression and checkpoint tuning instead.

fsync, group commit and synchronous_commit

write() only copies bytes into the OS page cache; fsync() (or fdatasync(), Postgres's default on Linux, {{wal_sync_method|https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-WAL-SYNC-METHOD}}) waits until the device says they are stored. A commit waits for the WAL flush and nothing else; the checkpointer and background writer write data pages later. One flush covers everything written before it, so transactions committing together share it: group commit ("one fsync of the WAL file may suffice to commit many transactions", {{WAL introduction|https://www.postgresql.org/docs/18/wal-intro.html}}; commit_delay can wait a few microseconds to gather more). synchronous_commit = off acknowledges before the flush: a crash can lose the last transactions, at most three times wal_writer_delay (3 x 200 ms), but it "does not create any risk of database inconsistency"; they vanish whole ({{synchronous_commit|https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT}}).

The flush, not the update, is the cost of a commit; 32 clients share it

measured pgbench, 20 s per run, each transaction one UPDATE of a random user's credit row, real flushes (on macOS the default does not empty the drive's own cache; fsync_writethrough does, and was used), loopback connection. The root measured the same shape with pgbench's default script: 148 and 2,133 per second with the flush.

With the flush, one client waits 6 ms per commit, so at most about 165 commits a second; 32 clients share flushes and reach 2,603 (16 times more for 32 times the clients); without waiting, 7,504 and 71,439. Choose per transaction: SET LOCAL synchronous_commit = off for a page view or a token-usage event, never for spending credits. The other values (local, remote_write, remote_apply) set how long a commit waits for replicas ({{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} owns replication).

Correction to the old page
The old page said stable storage is "10,000 times slower than memory" and put an enterprise-SSD fsync at "0.1 to 1 ms". It depends on the hardware: an SSD with power-loss protection acknowledges a flush in about 1.6 to 12 microseconds (its capacitor-backed cache counts as stable), a consumer SSD takes about 0.9 to 3 ms, network block storage about 0.7 ms (the root's notes and the system design page's Numbers to know tab). This laptop: 6.0 ms per single-client commit measured.
The same log, reused: replicas, point-in-time recovery, change data capture (links)

The same log is reused far beyond crash safety: shipped to another server it keeps a replica current; replayed to a chosen moment it restores a backup to that moment (point-in-time recovery); decoded by another program it becomes a stream of changes (change data capture, as Debezium does). Redo log, journal, binlog, commit log and oplog are the same idea in other products. {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} owns backups and replication; {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}} owns change data capture.

When fsync fails: the 2018 Linux surprise and Postgres's PANIC (depth)

In 2018 PostgreSQL developers found that on Linux a failed fsync could drop the dirty pages and report success on the next call, so "retry the fsync" could silently lose data ({{LWN, "PostgreSQL's fsync() surprise", 2018-04-18|https://lwn.net/Articles/752063/}}; the kernel side is {{Storage and file systems|n:3f05c17b0d0d8141be7acc1313570cbf}}). Since the February 2019 minor releases (11.2 and the back branches), Postgres instead stops with a PANIC on a failed data-file flush and recovers from the WAL on restart; data_sync_retry (default off) controls it ({{error handling settings|https://www.postgresql.org/docs/18/runtime-config-error-handling.html#GUC-DATA-SYNC-RETRY}}, {{11.2 notes|https://www.postgresql.org/docs/release/11.2/}}).

4. Crash recovery, step by step, on a real crash

We took a checkpoint, inserted 1,000 messages in one committed transaction, killed the server with kill -9 and restarted it measured. The rows went into gaps on many old pages, so they generated 8.4 MB of WAL, mostly page images. Step through what the server did; highlighted lines are what it printed.

Recovery replays the log forward from the checkpoint's redo point until the first broken record

  1. Notice the crash. On start Postgres reads the control file pg_control, sees the server was not shut down cleanly, and finds the last checkpoint record ("database system was interrupted ... automatic recovery in progress").
  2. Go to the redo point. The checkpoint record names the LSN from which changes might be missing from the data files: "redo starts at 0/111CFEA0" ({{WAL internals|https://www.postgresql.org/docs/18/wal-internals.html}}: "performs the REDO operation by scanning forward from the WAL location indicated in the checkpoint record").
  3. Replay each record. A record with a full-page image overwrites the page with it, which also repairs a torn page. A delta record is applied only if the page's stored LSN is older than the record's; otherwise the change is already on disk and is skipped.
  4. Find the end of the log. Each record carries a CRC checksum; the first record that is missing or fails its check marks the end: "invalid record length at 0/119D8C88: expected at least 24, got 0" is the normal end, not an error. Transactions whose commit record was not reached never become visible.
  5. Checkpoint and open. An end-of-recovery checkpoint wrote the 1,015 pages the replay had rebuilt, and the server accepted connections. All 1,000 committed rows were there; the restart took 0.22 seconds for 8.4 MB of log.

Redo starts at 0/111CFEA0 and the log ends at 0/119D8C88, 8,227 kB later (in the drawing, orange records carry page images and green ones deltas, an illustrative mix: most of these records carried page images; the checkpoint itself was logged at 0/111CFF50, just after its redo point). The LSN comparison of step 3 makes replay safe to repeat if the server crashes again during recovery ({{xlogutils.c|https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/access/transam/xlogutils.c}}).


What recovery costs
Time proportional to the WAL written since the last checkpoint: a max_wal_size of tens of GB on a write-heavy server means minutes of replay, the other side of fewer checkpoints and fewer page images. Recovery protects committed transactions against a crash, not against a lost disk or a bad DELETE: that takes backups and replicas.
