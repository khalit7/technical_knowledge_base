1. Pages: how a table sits on disk

The problem appears

A disk (or SSD) does not hand out single rows. It reads and writes blocks of a few kilobytes, and one random read from a fast SSD takes about 100 microseconds, roughly a thousand times longer than reading memory (the root page's section 4 has the measurements). So a database must decide which rows share a block, because rows that share a block are fetched together for the price of one read.

The idea: fixed-size pages, and a row address

Postgres stores each table and each index as its own file, under the data directory at base/<database id>/<file number> (the messages table is base/16384/16460 measured). A file larger than 1 GB is split into 1 GB segment files ({{Postgres file layout|https://www.postgresql.org/docs/18/storage-file-layout.html}}). Inside, the file is an array of pages (also called blocks) of 8 KB each, numbered from 0, and Postgres always reads and writes a whole page ({{Postgres page layout|https://www.postgresql.org/docs/18/storage-page-layout.html}}). Our million messages fill 19,235 pages; MySQL's InnoDB uses 16 KB pages and SQLite 4 KB by default, the same idea at another size.

Every row version stored in a table page is called a tuple, and every tuple has an address, the ctid: (page number, slot number). The first message lives at (0,1): page 0, slot 1. Indexes (section 5) store these addresses, which is how an index lookup jumps straight to the right page.

Inside one page

A page is laid out from both ends. A 24-byte page header sits at the start (where free space begins and ends, the page's position in the log). After it comes an array of 4-byte line pointers, one per slot, each saying where its tuple sits and how long it is. Tuples are written from the end of the page backwards. Free space is the gap in the middle; the page is full when the two meet. This is page 0 of the messages table, drawn to scale from the numbers Postgres reports about itself (page_header in the {{pageinspect|https://www.postgresql.org/docs/18/pageinspect.html}} extension) measured:

Header, 24 bytes52 line pointers, 208 bytesFree, 88 bytes52 tuples, 7,872 bytes

lower = 232 (24 + 52 x 4: where free space starts), upper = 320 (where the tuples start), page size 8,192. Every table page here holds between 34 and 58 messages, 52 on average, because content length varies measured. The slot-by-slot view is in {{Inside real pages|#t-page}}.

The line-pointer indirection is what lets Postgres move a tuple inside its page (to squeeze out a hole) without changing its ctid, so no index needs updating.

The tuple header: 23 bytes before your data

Each tuple starts with a 23-byte header (padded to 24 here), before any column value ({{page layout docs|https://www.postgresql.org/docs/18/storage-page-layout.html}}). The fields that matter:

  • xmin: the number of the transaction that created this version; xmax: the transaction that deleted or replaced it (0 if none). Together they decide which transactions can see this version: this is MVCC, the multi-version scheme the parent's section 3 introduced and {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}} owns.
  • t_ctid: for a current version its own address; for an old version, the address of its replacement, so readers can follow the chain.
  • infomask bits: flags such as "has nulls" (then a null bitmap follows) and hint bits that cache whether xmin and xmax committed.

So a message whose data is about 90 bytes takes about 120 to 200 bytes on the page: the 24-byte header, alignment padding to 8-byte boundaries, and the 4-byte line pointer. On a narrow table the overhead dominates: a table of a single bigint column uses 36 to 40 bytes per 8-byte value derived (24 + 8, aligned, plus 4).

An update is a new tuple

Postgres never overwrites a row in place. An UPDATE writes a new tuple and stamps the old one's xmax. We changed the token count of message 60, on a full page measured: the old tuple at (1,8) got xmax = 735 and a t_ctid pointing to (19234,35), the new version at the end of the table, because page 1 had no room. Every index on the table then needs a new entry pointing to (19234,35), even though no indexed column changed.

Postgres avoids that when it can, with a HOT update (heap-only tuple): if no indexed column changed and the new version fits on the same page, the old tuple points to the new one inside the page and the indexes are not touched ({{HOT docs|https://www.postgresql.org/docs/18/storage-hot.html}}). On a copy of the table created with fillfactor = 90 (inserts stop at 90% full, leaving 10% of each page for updates), the same update stayed on page 0: old tuple (0,10) flagged "HOT updated", new tuple (0,48) flagged "heap only", and the statistics counted n_tup_hot_upd = 1 against 0 on the full table measured. A lower fillfactor is the standard setting for tables that are updated often.

The payoff shows over time. {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} (section 6) updated a 100,000-row table 1,500 times a second: with no index on the updated columns, HOT updates and on-the-spot pruning kept dead tuples in the low thousands, under the autovacuum trigger (50 + 0.2 x 100,000 = 20,050), with no VACUUM at all; after one index was added on the updated column (last_message_at), every update became a full one and dead tuples rose to the trigger and fell after each autovacuum run, a sawtooth measured there.

Big values: TOAST

A tuple must fit in a page, so a row wider than about 2 KB has its large values compressed and, if still too big, cut into chunks stored in a side table; the main tuple keeps a pointer. This is TOAST ({{TOAST docs|https://www.postgresql.org/docs/18/storage-toast.html}}: threshold "normally 2 kB", values up to 1 GB). Compression is pglz by default; lz4 has been available since Postgres 14 (default_toast_compression). Two 13 KB assistant answers measured: a repetitive one (the same sentence 600 times) was compressed to 186 bytes and stayed in the page; one made of hexadecimal hashes barely compresses, so its 13,199 bytes went out to the TOAST table (16 KB). Long LLM answers are exactly this case: reading content costs extra page reads, and SELECT * pays them even when you do not need the text.

Two small maps beside every table

  • The free space map (file suffix _fsm) records about how much room each page has, one byte per page in 32-byte steps, as a small tree, so an insert finds a page with room without scanning ({{FSM docs|https://www.postgresql.org/docs/18/storage-fsm.html}}). For 19,235 pages it is 56 KB measured. VACUUM keeps it up to date.
  • The visibility map (suffix _vm) keeps two bits per page: all-visible (every tuple is visible to every transaction) and all-frozen ({{VM docs|https://www.postgresql.org/docs/18/storage-vm.html}}). VACUUM skips all-visible pages, and an index-only scan (answering from the index alone) can skip the table page only when its bit is set. After a VACUUM, 19,234 of 19,235 pages were all-visible; deleting rows on pages 0 and 1 cleared their bits measured. That is why index-only scans slow down on a table that has not been vacuumed: the root's {{Query plans|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab measures it (case 7, before and after VACUUM).
What pages cost
Reading one 150-byte row costs a whole 8 KB page read, so rows that are read together should live together (section 8 shows how InnoDB and clustering do that). About 24 + 4 bytes of every row are bookkeeping. Updates leave dead tuples that only VACUUM reclaims ({{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} owns VACUUM tuning).
