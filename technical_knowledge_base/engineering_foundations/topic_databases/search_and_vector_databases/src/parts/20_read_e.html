11. Smaller vectors in pgvector

Memory is what makes vector search expensive at scale, and most of it is the vectors themselves. Quantisation stores each number in fewer bits; how scalar, binary and product quantisation work, and what each byte budget keeps, is on {{Vector indexes from the inside|n:3f85c17b0d0d81f29707c130b2ebcfb1}} (its section 4 and IVF-PQ lab). pgvector offers two forms beside the float32 vector (6,144 bytes at 1,536 dimensions):

  • halfvec (float16, pgvector 0.7.0+): 3,072 bytes, 2× smaller, with a very small recall loss (measured below); it also lifts HNSW's limit from 2,000 to 4,000 dimensions.
  • bit via binary_quantize (1 bit, the sign of each number): 192 bytes, 32× smaller, compared by Hamming distance; it needs re-ranking with the full vectors.

Measured on the 522,931 questions (indexes on an expression, so the table keeps full float32 vectors for re-ranking) measured:

Binary quantisation needs re-ranking, and a model that tolerates it. Alone, the 1-bit index found @@bin_rec@@ of the true top 10: 384 signs keep too little of a small model's meaning. Fetching more candidates by Hamming distance and re-ordering them by the full vectors recovers recall (@@bin100_rec@@ with 100 candidates, @@bin400_rec@@ with 400). Larger models lose less; measure yours.

CREATE INDEX ON q USING hnsw ((binary_quantize(embedding)::bit(384)) bit_hamming_ops);
SELECT id FROM (
  SELECT id, embedding FROM q
  ORDER BY binary_quantize(embedding)::bit(384) <~> binary_quantize($1) LIMIT 100  -- needs hnsw.ef_search >= 100
) s ORDER BY embedding <=> $1 LIMIT 10;

Fewer dimensions. Models trained with Matryoshka representation learning (taught on {{Embedding models|n:3c65c17b0d0d81508f99e1fa78c2bb41}}) keep a usable embedding in the first 256 or 512 numbers. In pgvector, index a prefix with subvector(embedding, 1, 256)::vector(256) and re-rank with the full vector. all-MiniLM-L6-v2 was not trained this way, so it was not tested here. A 3,072-dimension vector exceeds HNSW's 2,000 limit for vector: index it as halfvec or shortened.

12. Filtered search in pgvector

Real queries carry conditions: "nearest questions from this workspace", "documents this user may see". An ANN index orders by distance only; it knows nothing about tenant_id. The strategies (post-filter, pre-filter then exact, filter-aware graphs such as ACORN and Qdrant's payload links) and where each breaks are taught, with an animation and a Filter lab, on {{Vector indexes from the inside|n:3f85c17b0d0d81f29707c130b2ebcfb1}} (its section 9). In pgvector they come down to three choices:

  • Post-filter (the default before 0.8.0, and still with iterative scans off): the index returns its ef_search candidates, then the WHERE clause drops the rest. If the condition keeps 1% of rows, the 40 candidates of a default HNSW scan hold on average 0.4 matching rows ({{pgvector README, Filtering|https://github.com/pgvector/pgvector#filtering}}).
  • Pre-filter: a B-tree finds the matching rows, then exact distances over just those. Exact and fast when the filter is selective; a brute-force scan of most of the table when it is not.
  • Filter during the search: pgvector 0.8.0 (2024-10-30) added iterative index scans: hnsw.iterative_scan = strict_order or relaxed_order resumes the scan until enough rows pass, up to hnsw.max_scan_tuples (20,000 by default).

What to do in pgvector
  • Turn on iterative scans for any filtered vector query: SET hnsw.iterative_scan = relaxed_order; (wrap in a materialised CTE and re-sort if exact order matters, as the README shows).
  • Keep a B-tree on the filter column so pre-filtering is possible, but do not trust the planner to pick it: here, with the B-tree present and iterative scans off, it chose the HNSW index for the 1% filter on every query and returned @@plan_rows@@ rows on average (EXPLAIN ANALYZE showed Rows Removed by Filter: 41 and rows=0) measured. The planner does not know the index scan stops at ef_search candidates. Check the plan, and force the pre-filter with a materialised CTE when you know the filter is selective.
  • For a few large tenants, a partial index per tenant (CREATE INDEX ... WHERE tenant_id = 7); for many tenants, list partitioning by tenant so each partition has its own small index. pgvector's README notes that a shared index lets one tenant's vectors affect another's recall and speed.
