11. Quantisation: smaller vectors

Memory is what makes vector search expensive at scale, and most of it is the vectors themselves. Quantisation stores each number in fewer bits:

FormBits per numberSize of a 1,536-d vectorNotes
float32 (vector)326,144 bytesthe model's output
float16 (halfvec, pgvector 0.7.0+)163,072 bytes (2× smaller)a very small recall loss (measured below); also lifts HNSW's limit from 2,000 to 4,000 dimensions
int8 (scalar quantisation)81,536 bytes (4×)Elasticsearch's default before BBQ; Qdrant, Milvus; not in pgvector
binary (bit, binary_quantize)1192 bytes (32×)keeps only the sign of each number; Hamming distance; re-rank with full vectors
PQ codesabout 0.596 bytes (64×)section 9

Binary quantisation needs re-ranking, and a model that tolerates it. Alone, the 1-bit index found @@bin_rec@@ of the true top 10: 384 signs keep too little of a small model's meaning. Fetching more candidates by Hamming distance and re-ordering them by the full vectors recovers recall (@@bin100_rec@@ with 100 candidates, @@bin400_rec@@ with 400). Hugging Face's measurements on larger models report about 96% of retrieval quality kept with re-scoring and 32× less memory, and int8 keeping about 99% ({{blog, 2024-03-22|https://huggingface.co/blog/embedding-quantization}}); results depend strongly on the model, so measure.

CREATE INDEX ON q USING hnsw ((binary_quantize(embedding)::bit(384)) bit_hamming_ops);
SELECT id FROM (
  SELECT id, embedding FROM q
  ORDER BY binary_quantize(embedding)::bit(384) <~> binary_quantize($1) LIMIT 100  -- needs hnsw.ef_search >= 100
) s ORDER BY embedding <=> $1 LIMIT 10;

Matryoshka dimensions. Some models are trained with {{Matryoshka Representation Learning|https://arxiv.org/abs/2205.13147}} (Kusupati et al., NeurIPS 2022) so that the first 256 or 512 numbers of a vector are themselves a usable embedding. OpenAI's text-embedding-3 models expose this as a dimensions parameter (1,536 by default for -small, 3,072 for -large); its docs state that "a text-embedding-3-large embedding can be shortened to a size of 256 while still outperforming an unshortened text-embedding-ada-002 embedding with a size of 1536" ({{OpenAI docs|https://developers.openai.com/api/docs/guides/embeddings}}). In pgvector, index a prefix with subvector(embedding, 1, 256)::vector(256) and re-rank with the full vector. all-MiniLM-L6-v2 was not trained this way, so it was not tested here. Note that 3,072 dimensions exceed HNSW's 2,000 limit for vector: index them as halfvec or shortened.

12. Filtered search: where vector indexes break

Real queries carry conditions: "nearest questions from this workspace", "documents this user may see", "created this year". An ANN index orders by distance only; it knows nothing about tenant_id. There are three ways to combine them, shown on the toy with a 10% filter:

  • Post-filter: search the ANN index for the top candidates, then drop those that fail the condition. Fast, but if the condition keeps 1% of rows, the 40 candidates of a default HNSW scan hold on average 0.4 matching rows ({{pgvector README, Filtering|https://github.com/pgvector/pgvector#filtering}}). This is what pgvector did before 0.8.0, and still does with iterative scans off.
  • Pre-filter: use an ordinary index to find the matching rows, then compute exact distances over just those. Exact and fast when the filter is selective; a brute-force scan of most of the table when it is not.
  • Filter during the search: skip non-matching nodes while walking the graph but keep walking until enough matches are found. pgvector 0.8.0 (2024-10-30) added iterative index scans: hnsw.iterative_scan = strict_order or relaxed_order resumes the scan until enough rows pass, up to hnsw.max_scan_tuples (20,000 by default). Qdrant evaluates the filter while traversing and adds extra links per indexed payload value so filtered regions stay connected, and switches to a plain scan of the matching points below a size threshold ({{Qdrant indexing docs|https://qdrant.tech/documentation/concepts/indexing/}}); Weaviate's ACORN strategy (added in 1.27, default since 1.34) does a similar thing.

What to do in pgvector
  • Turn on iterative scans for any filtered vector query: SET hnsw.iterative_scan = relaxed_order; (wrap in a materialised CTE and re-sort if exact order matters, as the README shows).
  • Keep a B-tree on the filter column so pre-filtering is possible, but do not trust the planner to pick it: here, with the B-tree present and iterative scans off, it chose the HNSW index for the 1% filter on every query and returned @@plan_rows@@ rows on average (EXPLAIN ANALYZE showed Rows Removed by Filter: 41 and rows=0) measured. The planner does not know the index scan stops at ef_search candidates. Check the plan, and force the pre-filter with a materialised CTE when you know the filter is selective.
  • For a few large tenants, a partial index per tenant (CREATE INDEX ... WHERE tenant_id = 7); for many tenants, list partitioning by tenant so each partition has its own small index. pgvector's README notes that a shared index lets one tenant's vectors affect another's recall and speed.
