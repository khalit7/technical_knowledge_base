4. Ranking with BM25

An inverted index finds the matches; it does not order them. On the full table, the running query's words match thousands of questions. Ranking answers "which first?" with three intuitions, each fixing a flaw of the one before:

  1. Term frequency (tf): a document that uses the query word more often is probably more about it. Flaw: "the" would dominate, and ten mentions are not ten times better than one.
  2. Inverse document frequency (idf): a word found in few documents tells you more than a word found in many. "invest" in 3 of 6 questions says less than "start" in 1 of 6. Multiplying the two gives the classic TF-IDF score.
  3. Saturation and length normalisation: the score for repeats should level off, and a long document that mentions a word once should count less than a short one that does.

BM25 ("Best Match 25", from the Okapi system at City University London, first run at {{TREC-3 in 1994|https://trec.nist.gov/pubs/trec3/papers/city.ps.gz}}; theory in {{Robertson and Zaragoza 2009|https://doi.org/10.1561/1500000019}}) puts all three into one formula and is the default ranking in Lucene, Elasticsearch (since 5.0, {{docs|https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity}}) and OpenSearch:

score(D, Q) = Σt in Q idf(t) · tf(t,D)·(k1+1) / ( tf(t,D) + k1·(1 − b + b·|D| / avgdl) )
idf(t) = ln( 1 + (N − n(t) + 0.5) / (n(t) + 0.5) )
tf(t,D)
how many times term t occurs in document D
|D|, avgdl
D's length in terms, and the average length over the collection
N, n(t)
number of documents, and how many contain t
k1
how fast repeats saturate (Lucene default 1.2); 0 ignores tf entirely
b
how much length matters (default 0.75); 0 ignores length, 1 fully normalises

Lucene's {{BM25Similarity|https://github.com/apache/lucene/blob/main/lucene/core/src/java/org/apache/lucene/search/similarities/BM25Similarity.java}} uses this idf and these defaults. Since Lucene 8.0 it drops the (k1+1) factor from the numerator, which multiplies every score by the same constant and so "doesn't affect ordering" ({{CHANGES.txt, LUCENE-8563|https://github.com/apache/lucene/blob/main/lucene/CHANGES.txt}}); this page keeps the textbook form. Lucene also stores each document's length in one byte, so its lengths are slightly rounded.

"start" (in one question) carries the largest idf, which is why "How can I get started in stock market?" ranks high on one word.

Postgres's ts_rank is not BM25
Postgres ships ts_rank (term frequency, optionally weighted by document part) and ts_rank_cd (cover density: how close the matched terms sit). Its manual is explicit: "the ranking functions do not use any global information" ({{PostgreSQL docs, 12.3.3|https://www.postgresql.org/docs/18/textsearch-controls.html}}), so there is no idf: a match on "market" counts as much as a match on "kohinoor". Same tokens, same matches, different order: the idf is worth that much. For real BM25 inside Postgres, use an extension (ParadeDB's pg_search, section 6) or compute it yourself.

nDCG@10, used above and in section 13, is a score between 0 and 1 for a ranked list: 1 when the labelled relevant results fill the top in the ideal order, discounted the further down they appear. The {{RAG and retrieval evaluation|n:3ef5c17b0d0d8194a914d1843ee26f13}} page defines it with a calculator; here it simply lets two rankers be compared on the same labelled questions.

6. Search engines: Postgres, Lucene and the rest

Everything above runs inside Postgres. Most large search deployments instead use a separate search engine, almost always built on Apache Lucene. Knowing how they differ explains when to add one.

Lucene, Elasticsearch and OpenSearch

Apache Lucene (Java, latest 10.5.2 on 2026-10-04, {{Lucene news|https://lucene.apache.org/core/corenews.html}}) is a library: inverted indexes, BM25, and since 9.0 (2021-12-07) HNSW vector search. Elasticsearch and its fork OpenSearch wrap it in a distributed server with a JSON API. Their write path is the part that surprises people coming from Postgres:

  1. Segments. New documents are buffered in memory, then written as a new immutable segment: a small complete inverted index. A search reads every segment and merges the results. A delete only marks the document as dead in a per-segment bitset; an update is a delete plus a new document. Background merges combine small segments into bigger ones and finally drop the dead documents (Lucene's default is the TieredMergePolicy). Until then, deleted documents still count in the idf statistics, so scores drift slightly.
  2. Refresh and near-real-time. A document becomes searchable only when the in-memory buffer is turned into a segment, a refresh, by default every second ({{index.refresh_interval|https://www.elastic.co/docs/reference/elasticsearch/index-settings/index-modules}}, {{near real-time search|https://www.elastic.co/docs/manage-data/data-store/near-real-time-search}}), and only on shards that received a search in the last 30 seconds. Elastic calls this near real-time: a write acknowledged now may not appear in a search for about a second.
  3. Durability by translog. Each shard appends every operation to a transaction log, fsynced before acknowledging by default (index.translog.durability: request, {{translog|https://www.elastic.co/docs/reference/elasticsearch/index-settings/translog}}), the same idea as Postgres's write-ahead log.
  4. Shards and replicas. An index is split into a fixed number of primary shards at creation (changing it needs the split or shrink APIs, {{docs|https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-indices-split}}), each copied to replicas. Replicas refresh independently, so two identical searches can briefly disagree: the cluster is eventually consistent for reads.
  5. Reindexing is routine. You cannot change an existing field's type or analyzer in place; you create a new index with the new mapping and copy every document into it with the Reindex API, then switch an alias ({{docs|https://www.elastic.co/docs/manage-data/data-store/mapping/update-mappings-examples}}). Teams plan for this from day one.
Not a system of record
Elasticsearch has no multi-document transactions, and Jepsen's tests (2014 and 2015) lost acknowledged documents under network partitions; the advice that followed was to keep a separate primary database. The parent page's {{Database atlas|n:3cd5c17b0d0d815d8841ec845f5f3324}} lists those findings. The normal design: Postgres holds the truth, and changes flow to the search engine (by an outbox or change data capture, taught on {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}); the search index can always be rebuilt from Postgres.

The lighter engines

Typesense

C++, GPL-3.0, v30.2 (2026-04-19). "Stores the entire search index in-memory" with a raw copy on disk ({{docs|https://typesense.org/docs/guide/system-requirements.html}}); no sharding, so one node's RAM caps the data. Built for search-as-you-type with typo tolerance out of the box.

Meilisearch

Rust, storage in LMDB ({{docs|https://www.meilisearch.com/docs/learn/engine/storage}}), v1.54.3 (2026-10-01). Licence "MIT AND BUSL-1.1": the enterprise parts (sharding first, v1.19, August 2025) are source-available ({{LICENSE|https://github.com/meilisearch/meilisearch/blob/main/LICENSE}}). Typo-tolerant instant search; hybrid search stable since v1.13 (2025-02-17).

ParadeDB pg_search

A Postgres extension (not a fork) that adds a real BM25 index inside Postgres, built on Tantivy, a Rust library modelled on Lucene. AGPL-3.0, v0.26.0 (2026-10-03), still 0.x; Postgres 15 to 18 ({{GitHub|https://github.com/paradedb/paradedb}}). The way to get BM25 without a second system; check its maturity against your write load.
