2. From text to terms

Before anything can be indexed, text must be cut into the units a search compares. This step is called analysis (Lucene and Elasticsearch) or parsing plus dictionaries (Postgres), and it runs twice: when a document is stored and when a query arrives. If the two runs differ, nothing matches.

  1. Tokenise: split the text into tokens, usually words, numbers and some punctuation-aware pieces (an email address, a hyphenated word, a URL).
  2. Normalise: lower-case, and often strip accents, so "Market" and "market" are one term.
  3. Drop stop words: very common words ("the", "is", "how", "do") that appear in almost every text and carry little meaning. Postgres's English configuration drops 127 of them from its english.stop list.
  4. Stem: cut endings so "investing", "invested" and "invests" become the same lexeme invest. A stemmer applies suffix rules, the classic being {{Porter (1980)|https://tartarus.org/martin/PorterStemmer/}}, now usually its successor Snowball; it can produce non-words ("stori" for "story"). Lemmatisation instead looks words up in a dictionary to return the real base form ("better" to "good"); it is slower and language-specific ({{Manning, Raghavan and Schuetze, section 2.2.4|https://nlp.stanford.edu/IR-book/html/htmledition/stemming-and-lemmatization-1.html}}).

The language setting is a silent default
Stemming rules are per language. Postgres picks the configuration from default_text_search_config, which initdb sets from the server's locale; the built-in fallback is simple, which lower-cases but neither stems nor drops stop words ({{PostgreSQL docs, 12.1 and 19.11|https://www.postgresql.org/docs/18/textsearch-intro.html}}). Always name the configuration in both the index and the query (to_tsvector('english', body)): an index built under one configuration is not used by a query written under another, and results change if a server's default differs.

3. The inverted index, built step by step

A book's index at the back maps a word to the pages where it appears. An inverted index is the same thing for a database: a dictionary of every term, and for each term a postings list, the sorted list of document ids that contain it, usually with how often (term frequency) and where (positions). It is "inverted" because a document maps to its words, and the index maps each word back to its documents.

The answers differ by one row because a substring is not a word: ILIKE also matched "TheDiamondMinecart", a channel name that the tokeniser keeps as one word. Words match "diamonds" too (stemming), substrings only by luck of spelling. A trigram index (section 5) is the way to make arbitrary LIKE '%...%' fast when you truly need substrings.

How real engines store postings. Ids in a postings list are sorted, so engines store the gaps between them (5, 9, 12 becomes 5, 4, 3) in as few bits as each gap needs; common words compress best. Lucene adds skip data so an AND query can jump through a long list instead of reading it all ({{Lucene postings format|https://lucene.apache.org/core/10_5_0/core/org/apache/lucene/codecs/lucene104/package-summary.html}}). Postgres stores postings inside a GIN (generalized inverted) index: a B-tree over the terms whose leaf entries hold the posting list, or a pointer to a posting tree when the list is long; "GIN indexes are the preferred text search index type" ({{PostgreSQL docs, 12.9|https://www.postgresql.org/docs/18/textsearch-indexes.html}}). GiST can also index a tsvector, but it stores a fixed-size signature per document, so it is lossy and every hit must be rechecked.

Every insert must now add an entry to the postings list of each of its words; GIN softens that with a pending list merged later (the {{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}} page explains GIN's pending list and fastupdate).
Inverted indexes are LSM-shaped in search engines. Lucene never edits an index file in place: new documents go to a new small segment, deletes are marks, and segments are merged in the background, the same write pattern as the LSM-trees taught on {{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}}.
