2. From text to terms

Before text can be indexed it is cut into the units a search compares: analysis (Lucene's word; Postgres says a parser plus dictionaries). It runs twice, when a document is stored and when a query arrives, and if the two runs differ nothing matches. The language setting is a silent default
Postgres picks the configuration from default_text_search_config, which initdb sets from the server's locale; the built-in fallback is simple, which lower-cases but neither stems nor drops stop words ({{PostgreSQL docs, 12.1 and 19.11|https://www.postgresql.org/docs/18/textsearch-intro.html}}). Tokens, normalising, lemmatisation, and a full ts_debug table

Tokens are usually words and numbers, with punctuation-aware pieces (an email address, a hyphenated word, a URL); normalising lower-cases and often strips accents. Lemmatisation instead looks words up in a dictionary to return the real base form ("better" to "good"); it is slower and language-specific ({{Manning, Raghavan and Schuetze, section 2.2.4|https://nlp.stanford.edu/IR-book/html/htmledition/stemming-and-lemmatization-1.html}}). 3. The inverted index, built step by step

An inverted index is the index at the back of a book: a dictionary of every term and, for each, a postings list, the sorted ids of the documents that contain it, usually with how often (term frequency) and where (positions). "Inverted" because a document maps to its words and the index maps each word back. The figure builds one for six real questions (rows are lexemes, columns are questions, a block's height is the term frequency), answers the running query, then runs the same query without an index.

  1. Six stored questions, an empty index. The questions stand at the back; the index in front will map every word to the list of questions that contain it, its postings list. On the whole table that dictionary held @@lexemes@@ distinct lexemes.
  2. Add question 1. Postgres turns the text into lexemes (lower case, stop words such as "how", "do", "i", "in", "the" dropped, endings stemmed). Each lexeme gets this question's number appended to its postings list, with the word positions (for phrase queries): "step" occurs twice, so its block is twice as tall.
  3. Add questions 2 to 6. Each question appends one entry per lexeme. "market" is in five questions, the Kohinoor question adds six lexemes no other question has; the postings lists stay sorted by question number.
  4. The query is tokenised the same way. "How do I start investing in shares?" becomes the lexemes invest, share and start. The same tokeniser must run at index time and at query time, or nothing matches.
  5. Look up three postings lists, never the texts. Each query lexeme is one lookup in the sorted dictionary; its postings list names the matching questions directly (questions 1 to 5). Question 6 is in no list and is never read.
  6. Rank the matches. A question can match one lexeme or several. Ranking (BM25, next section, with k1 1.2 and b 0.75) orders them: questions 2 and 4 at 1.54, then 1 at 1.15, 5 at 0.87, 3 at 0.77.
  7. No index: LIKE '%invest%'. Without an inverted index the database must read every stored text and look for the substring, character by character. A substring test also knows nothing about words: "invest" matches "investing" only because it is a prefix; "shares" would not match "share".

Postgres keeps postings in a GIN (generalized inverted) index, "the preferred text search index type" ({{PostgreSQL docs, 12.9|https://www.postgresql.org/docs/18/textsearch-indexes.html}}). The cost moves to writes: every insert adds an entry to the postings list of each of its words, which GIN softens with a pending list merged later ({{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}} owns GIN's pending list and fastupdate).

How engines store postings: gaps, skip data, GIN's posting trees, GiST, and why Lucene looks like an LSM-tree

Ids in a postings list are sorted, so engines store the gaps between them (5, 9, 12 becomes 5, 4, 3) in as few bits as each gap needs; common words compress best. Lucene adds skip data so an AND query can jump through a long list instead of reading it all ({{Lucene postings format|https://lucene.apache.org/core/10_5_0/core/org/apache/lucene/codecs/lucene104/package-summary.html}}). Postgres's GIN is a B-tree over the terms whose leaf entries hold the posting list, or a pointer to a posting tree when the list is long. GiST can also index a tsvector, but it stores a fixed-size signature per document, so it is lossy and every hit must be rechecked.

Lucene never edits an index file in place: new documents go to a new small segment, deletes are marks, and segments are merged in the background, the write pattern of the LSM-trees taught on {{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}}. Section 6 steps through it.
