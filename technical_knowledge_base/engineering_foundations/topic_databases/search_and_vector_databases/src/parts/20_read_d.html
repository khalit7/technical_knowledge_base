7. Embeddings in one section

A vector here is just an ordered list of numbers. An embedding model is a neural network trained so that texts with similar meaning get vectors that point in similar directions. all-MiniLM-L6-v2 turns the running query into 384 numbers; the first eight are , and the list has length (norm) @@qnorm@@ because the model's output is normalised to unit length. No single number means anything on its own; only distances between vectors do. Which model to use, and how to judge it (MTEB), belongs to {{Topic: rag-and-retrieval|n:3c65c17b0d0d81b89145c37dfe8a3b0b}} and the evaluation page.

When they agree
If every vector has length 1 (normalised), then cosine = dot product, and |a−b|2 = 2 − 2·cos(a,b), so all three rank results in exactly the same order. Most text embedding models normalise (all-MiniLM-L6-v2 does; OpenAI says its embeddings are normalised to length 1, {{OpenAI embeddings guide|https://developers.openai.com/api/docs/guides/embeddings}}). Then pick the cheapest operator: pgvector's {{README|https://github.com/pgvector/pgvector#exact-search}} advises inner product for normalised vectors, and here the exact scan with <#> took @@exact_ip_p50@@ ms against @@exact_p50@@ ms with cosine measured. They disagree when vectors are not normalised: dot product then favours long vectors, and a vector's length can carry meaning of its own (some recommendation models let it encode popularity). Use the measure the model was trained with, and index with the matching operator class, or the index is not used.

A real example. For the test question "@@ex_q@@", the three nearest of the 522,931 stored questions by cosine similarity were "@@ex1@@" (@@ex1c@@), "@@ex2@@" (@@ex2c@@) and "@@ex3@@" (@@ex3c@@) measured.

What a vector costs to store. pgvector stores a vector(n) as 4 bytes per number plus 8 bytes of header: 384 × 4 + 8 = 1,544 bytes (confirmed by pg_column_size measured), and for the common 1,536-dimension models 6,144 bytes of floats, 6,152 stored ({{README|https://github.com/pgvector/pgvector#vector-type}}). The 522,931 vectors take @@vec_mb@@ MB, about @@vec_share@@% of the whole @@heap_mb@@ MB table; the question texts are tiny next to them. At 100 million 1,536-dimension vectors that is 615 GB before any index, the figure the parent page's atlas carries.

8. Exact nearest neighbours, and what they cost

"Find the k stored vectors closest to the query" is k-nearest-neighbour (kNN) search. Done exactly, it is simple: compute the distance to every stored vector and keep the k smallest. In SQL, with no index:

SELECT id, body FROM q
ORDER BY embedding <=> $1   -- $1 is the query's vector
LIMIT 10;

The cost is N distance computations of n multiplications each: 522,931 × 384 = about 201 million multiply-adds per query. Postgres ran it as a parallel sequential scan with a top-N heap sort, reading @@exact_buf@@ pages of 8 KB (all from memory) in @@exact_p50@@ ms median, @@exact_p95@@ ms p95, over 60 test queries measured. That is fine for a nightly job and far too slow for a search box or for many queries per second: the cost grows linearly with the table.

Exact search is still the right tool when
  • the set is small (thousands to roughly 100,000 vectors; the old page's "below about 100k" is a rule of thumb, not a measured line: at 100k vectors of 384 numbers it would be about a fifth of the time measured here);
  • a filter has already cut the candidates to a few thousand (section 12: a B-tree finds one tenant's rows, then exact search over them);
  • you need the ground truth to measure an ANN index's recall (every recall number on this page was computed against exact search).

9. ANN indexes, step by step

An approximate nearest neighbour (ANN) index answers "which stored vectors are closest" by looking at only a small part of the data, accepting that it will sometimes miss a true neighbour. Its quality is recall@k: of the true k nearest (found by exact search), the share the index returned. Quote recall and latency together, never latency alone: any index is fast at low enough recall.

The animation runs one query four ways on a toy of 300 points in two dimensions (real embeddings have 384; the toy is illustrative, but its graph and lists are built with the real algorithms and its counts are exact for the toy).

IVF and IVFFlat: cluster first, then search a few clusters

An inverted file (IVF) index runs k-means once over the data to find a number of centroids (pgvector calls the count lists) and files every vector under its nearest centroid. A query compares itself with the centroids, then scans only the closest probes lists. pgvector's IVFFlat keeps the full vectors in the lists ("flat"). Its README's starting points: lists = rows / 1000 up to 1M rows, √rows above; probes = √lists; default probes 1 ({{README, IVFFlat|https://github.com/pgvector/pgvector#ivfflat}}).

  • Solves: exact search's linear cost, with a fast build and small memory.
  • Costs: the boundary problem (a neighbour filed under an unprobed list is lost, shown above), a training step (the index must be built after the data is loaded, or the centroids describe the wrong data), and slow decay as new data drifts away from the old centroids, fixed only by rebuilding.
  • Avoid when the data changes a lot or you need high recall at low latency; HNSW does better on both (measured in section 10).

Product quantisation: compress the vectors

Product quantisation (PQ) ({{Jégou, Douze and Schmid, TPAMI 2011|https://doi.org/10.1109/TPAMI.2010.57}}) splits each vector into m sub-vectors, learns a codebook of 256 centroids for each part, and stores each part as the 1-byte id of its nearest centroid. A 1,536-dimension float32 vector (6,144 bytes) split into 96 parts becomes 96 bytes, 64 times smaller (codes only; the codebooks are shared). Distances are computed approximately from lookup tables, so systems re-rank the best few hundred candidates with the full vectors. IVF plus PQ (written IVF4096,PQ64 in {{FAISS's index factory|https://github.com/facebookresearch/faiss/wiki/The-index-factory}}) is the classic billion-vector recipe; pgvector does not implement PQ (LanceDB's default index is IVF_PQ; Milvus and Qdrant offer it).

HNSW: a graph you walk greedily

HNSW (hierarchical navigable small world; {{Malkov and Yashunin, arXiv 2016|https://arxiv.org/abs/1603.09320}}, IEEE TPAMI 2020) links every vector to a few of its near neighbours, forming a graph in which a greedy walk ("always step to the neighbour closest to the query") reaches the query's region quickly. To avoid crawling across a huge graph in short steps, it adds sparser layers on top, like an express train over local stops: each vector is placed on layer 0, and on each higher layer with probability shrinking by a factor of M (the paper's mL = 1/ln M). A search enters at the top, walks greedily, drops a layer, and at layer 0 runs a wider beam search that keeps the best ef_search candidates.

  • Costs: slow builds, memory (the graph is fastest when it sits in RAM), slower inserts (each insert searches the graph), and deletes that leave holes repaired only by VACUUM (section 15).
  • Avoid when memory is the binding constraint at hundreds of millions of vectors: then quantise (section 11) or use a disk-based index.

DiskANN (Vamana): the graph on SSD

DiskANN ({{Subramanya et al., NeurIPS 2019|https://papers.nips.cc/paper/2019/hash/09853c7fb1d3f8ee67a61b6bf4a7f8e6-Abstract.html}}) builds a single-layer graph called Vamana whose pruning rule (a parameter α > 1) keeps some long links, so searches need few hops; the full vectors and graph live on SSD and only PQ-compressed vectors stay in RAM to steer the search. The paper's claim: a billion SIFT vectors on one workstation with 64 GB RAM and an SSD, "> 5000 queries a second with < 3ms mean latency and 95%+ 1-recall@1". In products: Milvus's DISKANN index ({{docs|https://milvus.io/docs/diskann.md}}), Azure Cosmos DB's diskANN vector index ({{docs|https://learn.microsoft.com/en-us/azure/cosmos-db/vector-search}}), Azure Database for PostgreSQL's pg_diskann extension (GA May 2025), SQL Server 2025's vector index (preview there; GA in Azure SQL), and Tiger Data's open pgvectorscale extension for Postgres (StreamingDiskANN, v0.9.1, 2026-09-04, {{GitHub|https://github.com/timescale/pgvectorscale}}).

ScaNN: quantise for ranking, not reconstruction

ScaNN ({{Guo et al., ICML 2020|https://proceedings.mlr.press/v119/guo20h.html}}) is Google's library. Its key idea, anisotropic vector quantisation, trains the compression to preserve inner-product ranking (errors parallel to the query direction hurt more than errors across it) rather than to reconstruct each vector faithfully. It powers Vertex AI Vector Search and, in Postgres, Google AlloyDB's alloydb_scann index ({{AlloyDB docs|https://docs.cloud.google.com/alloydb/docs/ai/store-index-query-vectors}}).
