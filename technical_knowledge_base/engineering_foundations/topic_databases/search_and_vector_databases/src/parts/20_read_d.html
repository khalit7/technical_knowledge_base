6. Search engines: freshness, segments and reindexing

Most large search deployments use a separate search engine built on Apache Lucene, a Java library of inverted indexes, BM25 and, since 9.0 (2021-12-07), HNSW vector search. Elasticsearch and its fork OpenSearch wrap it in a distributed JSON server. What surprises people coming from Postgres is the write path: a write is durable at once but searchable only later. Step one document through a shard.

The clock is illustrative; the defaults are Elastic's: {{index.refresh_interval|https://www.elastic.co/docs/reference/elasticsearch/index-settings/index-modules}}, {{near real-time search|https://www.elastic.co/docs/manage-data/data-store/near-real-time-search}}, {{translog|https://www.elastic.co/docs/reference/elasticsearch/index-settings/translog}}.

Three consequences follow. A write acknowledged now may not appear in a search for about a second: near real-time, where Postgres full-text is consistent with the last commit. An index is split into a fixed number of primary shards at creation (changing it needs the split or shrink APIs, {{docs|https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-indices-split}}), each copied to replicas that refresh independently, so two identical searches can briefly disagree: reads are eventually consistent. And reindexing is routine: an existing field's type or analyser cannot change in place, so you create a new index, copy every document with the Reindex API, and switch an alias ({{docs|https://www.elastic.co/docs/manage-data/data-store/mapping/update-mappings-examples}}; section 13 draws it).

Not a system of record
Elasticsearch has no multi-document transactions, and Jepsen's tests (2014 and 2015) lost acknowledged documents under network partitions; the advice that followed was to keep a separate primary database (the parent's {{Database atlas|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab lists those findings). The normal design: Postgres holds the truth, changes flow to the engine by an outbox or change data capture ({{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}), and the search index can always be rebuilt from Postgres.

Typo-tolerant instant search; hybrid search stable since v1.13 (2025-02-17).

The way to get BM25 without a second system; check its maturity against your write load.

The stepper as text. New documents are buffered in memory, then written as a new immutable segment: a small complete inverted index. A search reads every segment and merges the results. A delete only marks the document as dead in a per-segment bitset; an update is a delete plus a new document. Background merges combine small segments into bigger ones and finally drop the dead documents (Lucene's default is the TieredMergePolicy); until then, deleted documents still count in the idf statistics. The translog is fsynced before each write is acknowledged (index.translog.durability: request), the same idea as Postgres's write-ahead log. A refresh, every second by default and only on shards searched in the last 30 seconds, turns the buffer into a searchable segment. A flush is a Lucene commit that fsyncs the segments and trims the translog. Versions are in the one dated table of section 12.
