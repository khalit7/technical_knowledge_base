10. Filtered search in pgvector

Real queries carry conditions: "nearest questions from this workspace". An ANN index orders by distance only and knows nothing of tenant_id. The general strategies (post-filter, pre-filter, filter-aware graphs such as ACORN) and where each breaks are {{Vector indexes from the inside|n:3f85c17b0d0d81f29707c130b2ebcfb1}}'s section 9; in pgvector they come down to three choices:

  • Post-filter (the default before 0.8.0, and with iterative scans off): the index returns its ef_search candidates, then WHERE drops the rest. If the condition keeps 1% of rows, the 40 candidates of a default scan hold on average 0.4 matching rows ({{pgvector README, Filtering|https://github.com/pgvector/pgvector#filtering}}).
  • Pre-filter: a B-tree finds the matching rows, then exact distances over just those; exact and fast when the filter is selective, a scan of most of the table when it is not.
  • Filter during the search: pgvector 0.8.0 (2024-10-30) added iterative index scans: hnsw.iterative_scan = strict_order or relaxed_order resumes the scan until enough rows pass, up to hnsw.max_scan_tuples (20,000 by default).

Predict before you look: with a filter that keeps 1% of rows and iterative scans off, how many of the 10 requested rows come back?

What to do in pgvector
  • Turn on iterative scans for any filtered vector query: SET hnsw.iterative_scan = relaxed_order; (wrap in a materialised CTE and re-sort if exact order matters, as the README shows).
  • Keep a B-tree on the filter column, but do not trust the planner to use it: with both indexes present and iterative scans off, it chose HNSW for the 1% filter on every query and returned @@plan_rows@@ rows on average (EXPLAIN ANALYZE: Rows Removed by Filter: 41, rows=0) measured. The planner does not know the index scan stops at ef_search candidates. Check the plan, and force the pre-filter with a materialised CTE when you know the filter is selective.
  • For a few large tenants, a partial index per tenant (CREATE INDEX ... WHERE tenant_id = 7); for many, list partitioning by tenant so each partition has its own small index. The README notes that a shared index lets one tenant's vectors affect another's recall and speed.

11. Hybrid search inside one database

BM25 misses paraphrases ("stock" for "share"); vectors miss exact identifiers and rare names. The two scores cannot be added (a BM25 of 12.3 and a cosine of 0.81 are on unrelated scales), so the usual merge is reciprocal rank fusion (RRF) ({{Cormack, Clarke and Buettcher, SIGIR 2009|http://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf}}): each document scores Σ 1 / (k + rank) over the lists it appears in, with k = 60. Why that works, what it throws away and the score-fusion family it competes with are {{The retrieval pipeline|n:3c65c17b0d0d819899fde889e1e8b782}}'s (section 4). This section measures it in Postgres, on 1,000 Quora test questions and all 300 SciFact claims over 5,183 scientific abstracts (the set the evaluation page uses), top 100 from each retriever. Predict: does fusion beat the better single retriever on both?

The SQL you would deploy is one statement (the pattern of {{pgvector-python's RRF example|https://github.com/pgvector/pgvector-python/blob/master/examples/hybrid_search/rrf.py}}). Its lexical half ranks by ts_rank, so it inherits section 4's weakness; it scored @@q_rrf_sql@@ on Quora at @@rrf_sql_p50@@ ms median measured:

WITH lex AS (
  SELECT id, row_number() OVER (ORDER BY ts_rank(tsv, query) DESC) AS r
  FROM q, websearch_to_tsquery('english', $1) query
  WHERE tsv @@ query ORDER BY ts_rank(tsv, query) DESC LIMIT 100),
sem AS (
  SELECT id, row_number() OVER (ORDER BY embedding <=> $2) AS r
  FROM (SELECT id, embedding FROM q ORDER BY embedding <=> $2 LIMIT 100) s)
SELECT coalesce(lex.id, sem.id) AS id,
       coalesce(1.0 / (60 + lex.r), 0) + coalesce(1.0 / (60 + sem.r), 0) AS score
FROM lex FULL JOIN sem USING (id)
ORDER BY score DESC LIMIT 10;

The measured version OR-ed the query's lexemes instead of websearch_to_tsquery's AND, because AND left half the Quora questions with no lexical match. On Quora, where duplicates are paraphrases, the right weight for BM25 would be low; on SciFact, where claims share rare terms with their abstracts, BM25 earns its place. After fusion many systems re-order the top 20 to 100 with a cross-encoder reranker ({{Rerankers and late interaction|n:3f85c17b0d0d813fba53fc883f8a2c8f}}); learned sparse vectors (SPLADE-style, stored in pgvector as sparsevec) are a third retriever some teams add (the same page's section 10).
