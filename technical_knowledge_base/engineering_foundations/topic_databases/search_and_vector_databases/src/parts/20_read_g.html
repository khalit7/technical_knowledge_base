12. Postgres or a dedicated vector database?

A "vector database" is an ANN index plus storage, filtering and an API, run as its own system; pgvector adds the same index types to the Postgres you may already run. Most of them run HNSW, so the comparison is about where the data lives, how filters and tenants are handled, and what you pay for, not about the algorithm.

Stay in Postgres (pgvector) when

  • the vectors describe rows you already keep there, and queries join or filter on them (tenant, permissions, dates);
  • the vector, its text and its metadata must change in one transaction, deletes must take effect at once (a deleted document's embedding must stop being found), and you want one backup and failover story;
  • the index fits comfortably in the server's memory (the calculator below).

Consider a dedicated store when

  • the index no longer fits one server's memory, or vector load would crowd out the transactional workload;
  • most queries are heavily filtered and need in-graph filtering, or there are thousands of isolated tenants;
  • you want disk-based or quantised indexes Postgres lacks (DiskANN, PQ, int8), GPU builds, or object-storage economics;
  • a separate team owns search and wants to scale and rebuild it independently.

13. Operating a search index: rebuilds, writes and recall

Both kinds of index get rebuilt: a search engine when a mapping or analyser changes, a vector index when the embedding model changes (vectors from two models are not comparable). The safe pattern is the same in both: build the new one beside the old, compare, switch, drop.

Building

  • Load first, index after: indexes build faster after the data is in, and IVFFlat must be built after. COPY loaded the 522,931 rows in @@copy_s@@ s measured.
  • Give the build memory: HNSW builds "significantly faster when the graph fits into maintenance_work_mem". A 200,000-row copy built in @@b200_s@@ s with 2 GB and @@b200_64_s@@ s with 64 MB, where Postgres printed "@@notice@@" measured. Not so high that a build exhausts the server.
  • Parallel workers (0.6.0+): max_parallel_maintenance_workers (here 3, plus the leader).
  • CREATE INDEX CONCURRENTLY builds without locking out inserts (slower, and a failure leaves an invalid index to drop); watch pg_stat_progress_create_index.

Writes and deletes

  • Inserts get slower: each insert searches the graph for its neighbours. 5,000 single-row inserts took @@ins_h@@ s with HNSW and @@ins_n@@ s without measured: batch them.
  • Deletes leave holes: a deleted or updated row stays in the graph until VACUUM removes it and repairs the links; meanwhile scans skip dead entries and can return fewer rows. After deleting 10% of 200,000 rows VACUUM took @@vac_s@@ s, a full REINDEX @@reidx_s@@ s measured; the README advises REINDEX INDEX CONCURRENTLY before VACUUM when vacuuming is slow. Lucene has the same problem as dead documents waiting for a merge (section 6).
Keeping it honest: monitor recall, not just latency
Recall changes silently as data grows, drifts from IVF centroids, or gains a filter. Sample a few queries an hour, run them exactly (SET enable_indexscan = off in a transaction, or on a replica) and compare with the index's answer; keep a labelled set of 100 to 1,000 real queries and rescore it after every model, index or parameter change (the evaluation page shows how). Set ef_search per query with SET LOCAL, so a high-recall feature does not slow every other query. Check pg_relation_size of each vector index against shared_buffers and RAM: an HNSW index that falls out of memory turns page reads into SSD reads at every hop.

What teams do in production (2026). Postgres first: pgvector beside the data, HNSW at defaults with the operator class matching the model, iterative scans on for filtered queries, and the labelled set before any tuning. Hybrid (BM25 from a search engine or pg_search, plus vectors, fused with RRF, then a reranker when quality matters more than a few tens of milliseconds) is the usual start for user-facing search, kept only if it beats the better single retriever. The search engine is fed from the primary database, never written to directly, and can be rebuilt at any time. halfvec for storage, binary or int8 for the index and full vectors for re-ranking once memory is the cost. Tenants isolated by design: partitions or partial indexes in Postgres, namespaces in Pinecone and Turbopuffer, a shard per tenant in Weaviate, a tenant payload field in Qdrant.

Common mistakes, each with the measurement that shows it
  • Using LIKE '%word%' as search: it scans every row, matches substrings, ignores stemming and ranks nothing (@@like_ms@@ ms against @@fts_ms@@ ms with GIN).
  • Calling ts_rank "BM25": no idf; @@q_fts_or@@ against @@q_bm25@@ nDCG@10 on Quora.
  • Requiring every word (plainto_tsquery) for natural-language questions: no match at all for @@q_and_empty@@% of Quora test questions; use OR with ranking, websearch syntax, or BM25.
  • Different text configuration at index and query time: an index on to_tsvector('english', body) is not used by a query on to_tsvector(body) under another default, and stems differ.
  • Quoting ANN latency without recall: HNSW m 8 at ef_search 10 answered in @@m8_10_p50@@ ms but found only @@m8_10_rec@@ of the true top 10.
  • Post-filtering a selective condition: @@post1_rows@@ rows on average instead of 10 at a 1% filter.
  • Expecting more than ef_search rows from one HNSW scan: LIMIT 100 with the default ef_search of 40 returns at most 40 rows (pgvector README, Troubleshooting); raise ef_search to at least the LIMIT.
  • Building IVFFlat on an empty or small table: the centroids describe the wrong data and recall collapses; build after loading, rebuild after large changes.
  • Mismatched operator and operator class: an index built with vector_l2_ops is not used by ORDER BY embedding <=> $1, which silently falls back to a sequential scan; and the ORDER BY must be the bare operator ascending (not 1 - (a <=> b) DESC).
  • Mixing embeddings from two models or versions: distances between them are meaningless.
  • Treating the search engine as the database: no multi-document transactions, about a second of staleness, and a history of lost writes under partitions.
