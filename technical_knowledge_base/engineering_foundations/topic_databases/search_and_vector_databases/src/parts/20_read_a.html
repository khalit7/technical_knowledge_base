The idea in one screen

A search index is a precomputed shortcut from a question to its few best rows: an inverted index maps each word to the rows that contain it, a vector index maps a point in meaning-space to its neighbours, and every design on this page is a trade between how fresh, how exact and how cheap that shortcut is.

You need: tables, indexes and query plans from the parent {{Topic: databases|n:3cd5c17b0d0d815d8841ec845f5f3324}}; what an embedding is from {{Embedding models|n:3c65c17b0d0d81508f99e1fa78c2bb41}}. How ANN indexes work inside (IVF, PQ, HNSW, DiskANN, filtered ANN) is {{Vector indexes from the inside|n:3f85c17b0d0d81f29707c130b2ebcfb1}}'s; this page uses them as Postgres and the vector databases ship them. Retrieval metrics (recall@k, nDCG) are defined on {{RAG and retrieval evaluation|n:3ef5c17b0d0d8194a914d1843ee26f13}}.

New terms, each defined where it first appears:

analysis: text to index terms (tokenise, drop stop words, stem)
inverted index, postings list: term to the sorted ids of rows containing it
tsvector, tsquery, GIN: Postgres's stored terms, its search condition, and the index that holds postings
BM25: the standard word-match score (idf, saturating term frequency, length)
segment, refresh: Lucene's immutable mini-index; turning buffered writes into one
ANN, recall@k: an approximate nearest-neighbour index; the share of the true top k it returns
iterative scan: pgvector resuming an index scan until enough rows pass the filter
RRF: reciprocal rank fusion, merging ranked lists by 1 / (60 + rank)

The running example. The parent page's chat product wants, when a user types a question, the earlier questions that ask the same thing (reuse an answer, merge duplicates, suggest help articles). The real stand-in is the public {{BEIR|https://github.com/beir-cellar/beir}} copy of Quora duplicate questions: 522,931 real questions plus 10,000 test questions whose true duplicates people labelled, so every method can be scored. Each question was embedded with {{all-MiniLM-L6-v2|https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2}} (384 numbers, @@embed_s@@ seconds for the whole set on the laptop's GPU) and loaded into one table, q(id, body, embedding vector(384)) measured. 1. Two ways to search

The user types "How do I start investing in shares?". Stored are "How do I invest in share market?" (three shared words) and "How do I invest in stock market?" (one shared word, same meaning). A good search returns both above "What is the share market?", which shares words but asks something else.

Lexical (keyword) search

Compares words. Exact, explainable ("it matched invest and share"), cheap, no model, and strong on names, codes, error messages and rare terms (ERR_SSL_PROTOCOL, a product SKU). Blind to synonyms: "stock" is not "share".

Semantic (vector) search

Compares meaning through embeddings. Finds paraphrases and other languages, works on images. Needs a model at write and query time, is hard to explain, and can miss exact identifiers (a part number embeds close to other part numbers).

Each side needs a way to find candidates fast (an index) and a way to order them (a score): sections 2 to 6 for words, 7 to 10 for vectors, 11 combines them, 12 and 13 choose and run the system.
