Numbers marked measured were measured for this page on a laptop (Apple M1 Pro, 10 cores, 16 GB RAM, PostgreSQL 18.6 built from source, pgvector 0.8.7 built against it, 2026-10-04; other jobs shared the machine, so treat times as plus or minus 30%); numbers marked illustrative are drawn to explain, not measured.

Search means finding the stored texts that best answer a question, ranked, in milliseconds. There are two ways to decide "best". Lexical search matches the words: an inverted index lists, for every word, the documents that contain it, and BM25 scores how well each one matches. Semantic search matches the meaning: a model turns each text into a list of numbers (an embedding), and the database finds the stored embeddings nearest to the question's, usually with an approximate nearest neighbour (ANN) index such as HNSW because the exact search reads everything. Production systems often run both and merge the two rankings (hybrid search).

The running example. The one idea to keep
Every fast search trades something away on purpose. An inverted index trades write speed and space for reads; BM25 trades meaning for exact words; an ANN index trades a little recall (the share of the true nearest neighbours it returns) for a speed-up of about a hundred times. A professional states the trade in numbers (recall at a latency, on their own data) and measures it again whenever the data, the filter or the model changes.

1. Two ways to search

A user types "How do I start investing in shares?". Among the stored questions are "How do I invest in share market?" and "How do I invest in stock market?". The first shares three words with the query; the second shares only "invest" and means the same thing. A good search returns both, and ranks them above "What is the share market?", which shares words but asks something else.

Lexical (keyword) search

Compares words. Exact, explainable ("it matched invest and share"), cheap, no model needed, and very good at names, codes, error messages and rare terms (ERR_SSL_PROTOCOL, a product SKU). Blind to synonyms and paraphrase: "stock" is not "share".

Semantic (vector) search

Compares meaning through embeddings. Finds paraphrases and other languages, works on images too. Needs a model at write and query time, is hard to explain, and can miss exact identifiers the model never learned (a part number embeds close to other part numbers).

Two questions decide every design on this page: how to find candidates fast (an index, so a query does not read every row) and how to order them (a score). Sections 2 to 6 answer both for words, sections 7 to 12 for vectors, and section 13 combines them. Judging which retriever is better on your data (recall@k, nDCG, building a labelled test set) belongs to the evaluation topic's RAG and retrieval evaluation page; this page uses its metric definitions and links it.

2. From text to terms

Before anything can be indexed, text must be cut into the units a search compares. This step is called analysis (Lucene and Elasticsearch) or parsing plus dictionaries (Postgres), and it runs twice: when a document is stored and when a query arrives. If the two runs differ, nothing matches.

  1. Tokenise: split the text into tokens, usually words, numbers and some punctuation-aware pieces (an email address, a hyphenated word, a URL).
  2. Normalise: lower-case, and often strip accents, so "Market" and "market" are one term.
  3. Drop stop words: very common words ("the", "is", "how", "do") that appear in almost every text and carry little meaning. Postgres's English configuration drops 127 of them from its english.stop list.
  4. Stem: cut endings so "investing", "invested" and "invests" become the same lexeme invest. A stemmer applies suffix rules, the classic being Porter (1980), now usually its successor Snowball; it can produce non-words ("stori" for "story"). Lemmatisation instead looks words up in a dictionary to return the real base form ("better" to "good"); it is slower and language-specific (Manning, Raghavan and Schuetze, section 2.2.4).

The language setting is a silent default
Stemming rules are per language. Postgres picks the configuration from default_text_search_config, which initdb sets from the server's locale; the built-in fallback is simple, which lower-cases but neither stems nor drops stop words (PostgreSQL docs, 12.1 and 19.11). Always name the configuration in both the index and the query (to_tsvector('english', body)): an index built under one configuration is not used by a query written under another, and results change if a server's default differs.

3. The inverted index, built step by step

A book's index at the back maps a word to the pages where it appears. An inverted index is the same thing for a database: a dictionary of every term, and for each term a postings list, the sorted list of document ids that contain it, usually with how often (term frequency) and where (positions). It is "inverted" because a document maps to its words, and the index maps each word back to its documents.

Why it is fast. A query reads a handful of postings lists instead of every text. On the full table, counting the questions that mention "diamond" measured:

The answers differ by one row because a substring is not a word: ILIKE also matched "TheDiamondMinecart", a channel name that the tokeniser keeps as one word. Words match "diamonds" too (stemming), substrings only by luck of spelling. A trigram index (section 5) is the way to make arbitrary LIKE '%...%' fast when you truly need substrings.

How real engines store postings. Ids in a postings list are sorted, so engines store the gaps between them (5, 9, 12 becomes 5, 4, 3) in as few bits as each gap needs; common words compress best. Lucene adds skip data so an AND query can jump through a long list instead of reading it all (Lucene postings format). Postgres stores postings inside a GIN (generalized inverted) index: a B-tree over the terms whose leaf entries hold the posting list, or a pointer to a posting tree when the list is long; "GIN indexes are the preferred text search index type" (PostgreSQL docs, 12.9). GiST can also index a tsvector, but it stores a fixed-size signature per document, so it is lossy and every hit must be rechecked.

What it cost here
Adding the stored tsvector column to the 522,931-row table took 6 s and 43 MB; building the GIN index took 0.6 s and 20 MB for 87,014 distinct lexemes measured. Every insert must now add an entry to the postings list of each of its words; GIN softens that with a pending list merged later (the Storage engines and indexes page explains GIN's pending list and fastupdate).
Inverted indexes are LSM-shaped in search engines. Lucene never edits an index file in place: new documents go to a new small segment, deletes are marks, and segments are merged in the background, the same write pattern as the LSM-trees taught on Storage engines and indexes. Section 6 shows what that means for freshness.

4. Ranking with BM25

An inverted index finds the matches; it does not order them. On the full table, the running query's words match thousands of questions. Ranking answers "which first?" with three intuitions, each fixing a flaw of the one before:

  1. Term frequency (tf): a document that uses the query word more often is probably more about it. Flaw: "the" would dominate, and ten mentions are not ten times better than one.
  2. Inverse document frequency (idf): a word found in few documents tells you more than a word found in many. "invest" in 3 of 6 questions says less than "start" in 1 of 6. Multiplying the two gives the classic TF-IDF score.
  3. Saturation and length normalisation: the score for repeats should level off, and a long document that mentions a word once should count less than a short one that does.

BM25 ("Best Match 25", from the Okapi system at City University London, first run at TREC-3 in 1994; theory in Robertson and Zaragoza 2009) puts all three into one formula and is the default ranking in Lucene, Elasticsearch (since 5.0, docs) and OpenSearch:

score(D, Q) = Σt in Q idf(t) · tf(t,D)·(k1+1) / ( tf(t,D) + k1·(1 − b + b·|D| / avgdl) )
idf(t) = ln( 1 + (N − n(t) + 0.5) / (n(t) + 0.5) )
tf(t,D)
how many times term t occurs in document D
|D|, avgdl
D's length in terms, and the average length over the collection
N, n(t)
number of documents, and how many contain t
k1
how fast repeats saturate (Lucene default 1.2); 0 ignores tf entirely
b
how much length matters (default 0.75); 0 ignores length, 1 fully normalises

Lucene's BM25Similarity uses this idf and these defaults. Since Lucene 8.0 it drops the (k1+1) factor from the numerator, which multiplies every score by the same constant and so "doesn't affect ordering" (CHANGES.txt, LUCENE-8563); this page keeps the textbook form. Lucene also stores each document's length in one byte, so its lengths are slightly rounded.

BM25 worked on the six questions. Query: "How do I start investing in shares?", lexemes from Postgres. Move the sliders.

Try: set b to 0 and the long "step by step guide" question rises, because its length no longer counts against it; set k1 to 0 and every match of a term scores just its idf. "start" (in one question) carries the largest idf, which is why "How can I get started in stock market?" ranks high on one word.

Postgres's ts_rank is not BM25
Postgres ships ts_rank (term frequency, optionally weighted by document part) and ts_rank_cd (cover density: how close the matched terms sit). Its manual is explicit: "the ranking functions do not use any global information" (PostgreSQL docs, 12.3.3), so there is no idf: a match on "market" counts as much as a match on "kohinoor". Measured on 1,000 Quora test questions, ranking the OR-matches by ts_rank scored nDCG@10 0.627; BM25 over exactly the same Postgres lexemes scored 0.733 measured. Same tokens, same matches, different order: the idf is worth that much. For real BM25 inside Postgres, use an extension (ParadeDB's pg_search, section 6) or compute it yourself.

nDCG@10, used above and in section 13, is a score between 0 and 1 for a ranked list: 1 when the labelled relevant results fill the top in the ideal order, discounted the further down they appear. The RAG and retrieval evaluation page defines it with a calculator; here it simply lets two rankers be compared on the same labelled questions.

5. Phrases, prefixes and typos

Phrases. Because postings keep word positions, an engine can require words to be adjacent and in order. In Postgres, phraseto_tsquery('english', 'share market') becomes : "share" immediately followed by "market". On the full table it matched 86 questions, against 157 that merely contain both words measured. websearch_to_tsquery accepts what users type into search boxes: quotes for phrases, or, and a minus sign to exclude: "share market" -india or stocks becomes .

Prefixes. to_tsquery('english', 'invest:*') matches every lexeme starting with invest, which is how search-as-you-type is done in Postgres; GIN supports it.

Typos. Stemming does not fix spelling: "kohinor diamnd" matched 0 questions through full-text search measured. Fuzzy matching needs a notion of "close spelling":

  • Edit distance (Levenshtein): the number of single-letter insertions, deletions or substitutions between two words. Lucene's fuzzy queries allow up to 2 edits (Lucene FuzzyQuery docs: maxEdits is capped at MAXIMUM_SUPPORTED_DISTANCE, 2); Meilisearch allows 1 typo in words of 5 or more letters and 2 from 9 letters by default (Meilisearch docs).
  • Trigrams: cut words into overlapping three-letter pieces and count the shared pieces. Postgres's pg_trgm extension does this: show_trgm('kohinor') is . With a GIN trigram index (3 s to build, 82 MB measured), the misspelt query found:

Word similarity: the share of trigrams in the best-matching stretch of the question; this run kept results at 0.5 or more (the default threshold for <% is 0.6, docs). The query took 7 ms measured. A common production pattern: try full-text first, fall back to trigrams when it returns nothing.

6. Search engines: Postgres, Lucene and the rest

Everything above runs inside Postgres. Most large search deployments instead use a separate search engine, almost always built on Apache Lucene. Knowing how they differ explains when to add one.

Lucene, Elasticsearch and OpenSearch

Apache Lucene (Java, latest 10.5.2 on 2026-10-04, Lucene news) is a library: inverted indexes, BM25, and since 9.0 (2021-12-07) HNSW vector search. Elasticsearch and its fork OpenSearch wrap it in a distributed server with a JSON API. Their write path is the part that surprises people coming from Postgres:

  1. Segments. New documents are buffered in memory, then written as a new immutable segment: a small complete inverted index. A search reads every segment and merges the results. A delete only marks the document as dead in a per-segment bitset; an update is a delete plus a new document. Background merges combine small segments into bigger ones and finally drop the dead documents (Lucene's default is the TieredMergePolicy). Until then, deleted documents still count in the idf statistics, so scores drift slightly.
  2. Refresh and near-real-time. A document becomes searchable only when the in-memory buffer is turned into a segment, a refresh, by default every second (index.refresh_interval, near real-time search), and only on shards that received a search in the last 30 seconds. Elastic calls this near real-time: a write acknowledged now may not appear in a search for about a second.
  3. Durability by translog. Each shard appends every operation to a transaction log, fsynced before acknowledging by default (index.translog.durability: request, translog), the same idea as Postgres's write-ahead log.
  4. Shards and replicas. An index is split into a fixed number of primary shards at creation (changing it needs the split or shrink APIs, docs), each copied to replicas. Replicas refresh independently, so two identical searches can briefly disagree: the cluster is eventually consistent for reads.
  5. Reindexing is routine. You cannot change an existing field's type or analyzer in place; you create a new index with the new mapping and copy every document into it with the Reindex API, then switch an alias (docs). Teams plan for this from day one.
Not a system of record
Elasticsearch has no multi-document transactions, and Jepsen's tests (2014 and 2015) lost acknowledged documents under network partitions; the advice that followed was to keep a separate primary database. The parent page's Database atlas lists those findings. The normal design: Postgres holds the truth, and changes flow to the search engine (by an outbox or change data capture, taught on Queues, streams and async work); the search index can always be rebuilt from Postgres.

Typesense

C++, GPL-3.0, v30.2 (2026-04-19). "Stores the entire search index in-memory" with a raw copy on disk (docs); no sharding, so one node's RAM caps the data. Built for search-as-you-type with typo tolerance out of the box.

Meilisearch

Rust, storage in LMDB (docs), v1.54.3 (2026-10-01). Licence "MIT AND BUSL-1.1": the enterprise parts (sharding first, v1.19, August 2025) are source-available (LICENSE). Typo-tolerant instant search; hybrid search stable since v1.13 (2025-02-17).

ParadeDB pg_search

A Postgres extension (not a fork) that adds a real BM25 index inside Postgres, built on Tantivy, a Rust library modelled on Lucene. AGPL-3.0, v0.26.0 (2026-10-03), still 0.x; Postgres 15 to 18 (GitHub). The way to get BM25 without a second system; check its maturity against your write load.

7. Embeddings in one section

A vector here is just an ordered list of numbers. An embedding model is a neural network trained so that texts with similar meaning get vectors that point in similar directions. all-MiniLM-L6-v2 turns the running query into 384 numbers; the first eight are , and the list has length (norm) 1.0000 because the model's output is normalised to unit length. No single number means anything on its own; only distances between vectors do. Which model to use, and how to judge it (MTEB), belongs to Topic: rag-and-retrieval and the evaluation page.

Three ways to measure "close", for vectors a and b with n numbers each:

When they agree
If every vector has length 1 (normalised), then cosine = dot product, and |a−b|2 = 2 − 2·cos(a,b), so all three rank results in exactly the same order. Most text embedding models normalise (all-MiniLM-L6-v2 does; OpenAI says its embeddings are normalised to length 1, OpenAI embeddings guide). Then pick the cheapest operator: pgvector's README advises inner product for normalised vectors, and here the exact scan with <#> took 76 ms against 91 ms with cosine measured. They disagree when vectors are not normalised: dot product then favours long vectors, and a vector's length can carry meaning of its own (some recommendation models let it encode popularity). Use the measure the model was trained with, and index with the matching operator class, or the index is not used.

A real example. For the test question "Which question should I ask on Quora?", the three nearest of the 522,931 stored questions by cosine similarity were "What question can I ask on Quora?" (0.886), "What is the best question to question on Quora?" (0.854) and "What's the best question to ask in Quora?" (0.848) measured.

What a vector costs to store. pgvector stores a vector(n) as 4 bytes per number plus 8 bytes of header: 384 × 4 + 8 = 1,544 bytes (confirmed by pg_column_size measured), and for the common 1,536-dimension models 6,144 bytes of floats, 6,152 stored (README). The 522,931 vectors take 807 MB, about 78% of the whole 1,031 MB table; the question texts are tiny next to them. At 100 million 1,536-dimension vectors that is 615 GB before any index, the figure the parent page's atlas carries.

8. Exact nearest neighbours, and what they cost

"Find the k stored vectors closest to the query" is k-nearest-neighbour (kNN) search. Done exactly, it is simple: compute the distance to every stored vector and keep the k smallest. In SQL, with no index:

SELECT id, body FROM q
ORDER BY embedding <=> $1   -- $1 is the query's vector
LIMIT 10;

The cost is N distance computations of n multiplications each: 522,931 × 384 = about 201 million multiply-adds per query. Postgres ran it as a parallel sequential scan with a top-N heap sort, reading 126,020 pages of 8 KB (all from memory) in 91 ms median, 118 ms p95, over 60 test queries measured. That is fine for a nightly job and far too slow for a search box or for many queries per second: the cost grows linearly with the table.

Exact search is still the right tool when
  • the set is small (thousands to roughly 100,000 vectors; the old page's "below about 100k" is a rule of thumb, not a measured line: at 100k vectors of 384 numbers it would be about a fifth of the time measured here);
  • a filter has already cut the candidates to a few thousand (section 12: a B-tree finds one tenant's rows, then exact search over them);
  • you need the ground truth to measure an ANN index's recall (every recall number on this page was computed against exact search).

9. ANN indexes, step by step

An approximate nearest neighbour (ANN) index answers "which stored vectors are closest" by looking at only a small part of the data, accepting that it will sometimes miss a true neighbour. Its quality is recall@k: of the true k nearest (found by exact search), the share the index returned. Quote recall and latency together, never latency alone: any index is fast at low enough recall.

The animation runs one query four ways on a toy of 300 points in two dimensions (real embeddings have 384; the toy is illustrative, but its graph and lists are built with the real algorithms and its counts are exact for the toy).

IVF and IVFFlat: cluster first, then search a few clusters

An inverted file (IVF) index runs k-means once over the data to find a number of centroids (pgvector calls the count lists) and files every vector under its nearest centroid. A query compares itself with the centroids, then scans only the closest probes lists. pgvector's IVFFlat keeps the full vectors in the lists ("flat"). Its README's starting points: lists = rows / 1000 up to 1M rows, √rows above; probes = √lists; default probes 1 (README, IVFFlat).

  • Solves: exact search's linear cost, with a fast build and small memory.
  • Costs: the boundary problem (a neighbour filed under an unprobed list is lost, shown above), a training step (the index must be built after the data is loaded, or the centroids describe the wrong data), and slow decay as new data drifts away from the old centroids, fixed only by rebuilding.
  • Avoid when the data changes a lot or you need high recall at low latency; HNSW does better on both (measured in section 10).

Product quantisation: compress the vectors

Product quantisation (PQ) (Jégou, Douze and Schmid, TPAMI 2011) splits each vector into m sub-vectors, learns a codebook of 256 centroids for each part, and stores each part as the 1-byte id of its nearest centroid. A 1,536-dimension float32 vector (6,144 bytes) split into 96 parts becomes 96 bytes, 64 times smaller (codes only; the codebooks are shared). Distances are computed approximately from lookup tables, so systems re-rank the best few hundred candidates with the full vectors. IVF plus PQ (written IVF4096,PQ64 in FAISS's index factory) is the classic billion-vector recipe; pgvector does not implement PQ (LanceDB's default index is IVF_PQ; Milvus and Qdrant offer it).

HNSW: a graph you walk greedily

HNSW (hierarchical navigable small world; Malkov and Yashunin, arXiv 2016, IEEE TPAMI 2020) links every vector to a few of its near neighbours, forming a graph in which a greedy walk ("always step to the neighbour closest to the query") reaches the query's region quickly. To avoid crawling across a huge graph in short steps, it adds sparser layers on top, like an express train over local stops: each vector is placed on layer 0, and on each higher layer with probability shrinking by a factor of M (the paper's mL = 1/ln M). A search enters at the top, walks greedily, drops a layer, and at layer 0 runs a wider beam search that keeps the best ef_search candidates.

  • Solves: high recall at low latency, with no training step (an HNSW index can be created on an empty table).
  • Costs: slow builds, memory (the graph is fastest when it sits in RAM), slower inserts (each insert searches the graph), and deletes that leave holes repaired only by VACUUM (section 15).
  • Avoid when memory is the binding constraint at hundreds of millions of vectors: then quantise (section 11) or use a disk-based index.

DiskANN (Vamana): the graph on SSD

DiskANN (Subramanya et al., NeurIPS 2019) builds a single-layer graph called Vamana whose pruning rule (a parameter α > 1) keeps some long links, so searches need few hops; the full vectors and graph live on SSD and only PQ-compressed vectors stay in RAM to steer the search. The paper's claim: a billion SIFT vectors on one workstation with 64 GB RAM and an SSD, "> 5000 queries a second with < 3ms mean latency and 95%+ 1-recall@1". In products: Milvus's DISKANN index (docs), Azure Cosmos DB's diskANN vector index (docs), Azure Database for PostgreSQL's pg_diskann extension (GA May 2025), SQL Server 2025's vector index (preview there; GA in Azure SQL), and Tiger Data's open pgvectorscale extension for Postgres (StreamingDiskANN, v0.9.1, 2026-09-04, GitHub).

ScaNN: quantise for ranking, not reconstruction

ScaNN (Guo et al., ICML 2020) is Google's library. Its key idea, anisotropic vector quantisation, trains the compression to preserve inner-product ranking (errors parallel to the query direction hurt more than errors across it) rather than to reconstruct each vector faithfully. It powers Vertex AI Vector Search and, in Postgres, Google AlloyDB's alloydb_scann index (AlloyDB docs).

10. Measured: recall against latency in pgvector

The same measurement every team should run on its own data, done here on the 522,931 questions: for 1,000 test questions, the exact top 10 (computed outside the database), then each index at several settings, recording recall@10 and the latency of the full SQL query from a client on the same machine (second pass, so caches are warm; shared_buffers 4 GB holds the table and every index) measured.

CREATE INDEX q_hnsw ON q USING hnsw (embedding vector_cosine_ops);   -- m 16, ef_construction 64
SET hnsw.ef_search = 40;                                          -- per session, or SET LOCAL per transaction
SELECT id FROM q ORDER BY embedding <=> $1 LIMIT 10;

What the numbers say:

  • HNSW at its defaults is about 119 times faster than exact search (0.76 ms against 91 ms median) and returns 98.9% of the true top 10. Its query plan read 657 pages from memory, against 126,020 for the exact scan.
  • ef_search is the dial. From 10 to 640, recall rose from 0.958 to 0.998 while latency grew about 13 times. Past about 0.99 each extra point of recall costs more than the last.
  • m changes the curve, not just a point. m 8 builds in 25 s but tops out lower (0.983 at ef_search 640); m 32 with ef_construction 128 took 191 s to build and reached 0.998 already at ef_search 40. The defaults sit in between.
  • IVFFlat needs many probes. With 523 lists (rows / 1000), 1 probe gave recall 0.651; reaching 0.971 took 23 probes (√lists) at 5.8 ms, slower than HNSW at higher recall. It built in 40 s against 61 s for HNSW.
  • Size. The HNSW index was 1,069 MB, about 2,045 bytes per vector: the 1,544-byte vector is copied into the index, plus its links. IVFFlat was 859 MB.

ANN lab plots all of these as curves with the knobs, plus the quantised variants of section 11 and a memory calculator for your own sizes.

Re-based on a measurement
The old page's latency row "HNSW ANN query, 1M vectors, in memory: 1 to 5 ms" was unconfirmed. Measured here at 523k vectors of 384 dimensions: 0.76 ms median, 1.14 ms p95 at the defaults, including the client round trip. 11. Quantisation: smaller vectors

Memory is what makes vector search expensive at scale, and most of it is the vectors themselves. Quantisation stores each number in fewer bits:

FormBits per numberSize of a 1,536-d vectorNotes
float32 (vector)326,144 bytesthe model's output
float16 (halfvec, pgvector 0.7.0+)163,072 bytes (2× smaller)a very small recall loss (measured below); also lifts HNSW's limit from 2,000 to 4,000 dimensions
int8 (scalar quantisation)81,536 bytes (4×)Elasticsearch's default before BBQ; Qdrant, Milvus; not in pgvector
binary (bit, binary_quantize)1192 bytes (32×)keeps only the sign of each number; Hamming distance; re-rank with full vectors
PQ codesabout 0.596 bytes (64×)section 9

Measured on the 522,931 questions (indexes on an expression, so the table keeps full float32 vectors for re-ranking) measured:

Binary quantisation needs re-ranking, and a model that tolerates it. Alone, the 1-bit index found 0.728 of the true top 10: 384 signs keep too little of a small model's meaning. Fetching more candidates by Hamming distance and re-ordering them by the full vectors recovers recall (0.984 with 100 candidates, 0.997 with 400). Hugging Face's measurements on larger models report about 96% of retrieval quality kept with re-scoring and 32× less memory, and int8 keeping about 99% (blog, 2024-03-22); results depend strongly on the model, so measure.

CREATE INDEX ON q USING hnsw ((binary_quantize(embedding)::bit(384)) bit_hamming_ops);
SELECT id FROM (
  SELECT id, embedding FROM q
  ORDER BY binary_quantize(embedding)::bit(384) <~> binary_quantize($1) LIMIT 100  -- needs hnsw.ef_search >= 100
) s ORDER BY embedding <=> $1 LIMIT 10;

Matryoshka dimensions. Some models are trained with Matryoshka Representation Learning (Kusupati et al., NeurIPS 2022) so that the first 256 or 512 numbers of a vector are themselves a usable embedding. OpenAI's text-embedding-3 models expose this as a dimensions parameter (1,536 by default for -small, 3,072 for -large); its docs state that "a text-embedding-3-large embedding can be shortened to a size of 256 while still outperforming an unshortened text-embedding-ada-002 embedding with a size of 1536" (OpenAI docs). In pgvector, index a prefix with subvector(embedding, 1, 256)::vector(256) and re-rank with the full vector. all-MiniLM-L6-v2 was not trained this way, so it was not tested here. Note that 3,072 dimensions exceed HNSW's 2,000 limit for vector: index them as halfvec or shortened.

12. Filtered search: where vector indexes break

Real queries carry conditions: "nearest questions from this workspace", "documents this user may see", "created this year". An ANN index orders by distance only; it knows nothing about tenant_id. There are three ways to combine them, shown on the toy with a 10% filter:

  • Post-filter: search the ANN index for the top candidates, then drop those that fail the condition. Fast, but if the condition keeps 1% of rows, the 40 candidates of a default HNSW scan hold on average 0.4 matching rows (pgvector README, Filtering). This is what pgvector did before 0.8.0, and still does with iterative scans off.
  • Pre-filter: use an ordinary index to find the matching rows, then compute exact distances over just those. Exact and fast when the filter is selective; a brute-force scan of most of the table when it is not.
  • Filter during the search: skip non-matching nodes while walking the graph but keep walking until enough matches are found. pgvector 0.8.0 (2024-10-30) added iterative index scans: hnsw.iterative_scan = strict_order or relaxed_order resumes the scan until enough rows pass, up to hnsw.max_scan_tuples (20,000 by default). Qdrant evaluates the filter while traversing and adds extra links per indexed payload value so filtered regions stay connected, and switches to a plain scan of the matching points below a size threshold (Qdrant indexing docs); Weaviate's ACORN strategy (added in 1.27, default since 1.34) does a similar thing.

Measured on the 522,931 questions, 1,000 test queries, each with a filter on a synthetic tenant column (row id modulo 100, so 1% of rows; and modulo 10, 10%), HNSW at defaults, recall against the exact filtered top 10 measured:

With a 1% filter and iterative scans off, the HNSW scan returned 0.38 rows on average instead of 10 (68% of queries returned nothing; recall 0.04). strict_order returned 10.00 rows at recall 0.935 in 22.7 ms; relaxed_order 10.00 rows at recall 0.975 in 15.6 ms; the B-tree pre-filter with exact search was always right (recall 1.000) in 6.6 ms. With a 10% filter and iterative scans off, the HNSW scan returned 3.97 rows on average instead of 10 (1% of queries returned nothing; recall 0.40). strict_order returned 10.00 rows at recall 0.961 in 1.6 ms; relaxed_order 10.00 rows at recall 0.979 in 1.6 ms; the B-tree pre-filter with exact search was always right (recall 1.000) in 154.0 ms. Iterative scans fix the empty results; the price is latency and, at the 1% filter, the 20,000-tuple scan limit. Pre-filtering wins when the filter is selective, because exact search over about 5,230 rows is cheap; at 10% it must compute about 52,300 distances per query.

What to do in pgvector
  • Turn on iterative scans for any filtered vector query: SET hnsw.iterative_scan = relaxed_order; (wrap in a materialised CTE and re-sort if exact order matters, as the README shows).
  • Keep a B-tree on the filter column so pre-filtering is possible, but do not trust the planner to pick it: here, with the B-tree present and iterative scans off, it chose the HNSW index for the 1% filter on every query and returned 0.38 rows on average (EXPLAIN ANALYZE showed Rows Removed by Filter: 41 and rows=0) measured. The planner does not know the index scan stops at ef_search candidates. Check the plan, and force the pre-filter with a materialised CTE when you know the filter is selective.
  • For a few large tenants, a partial index per tenant (CREATE INDEX ... WHERE tenant_id = 7); for many tenants, list partitioning by tenant so each partition has its own small index. pgvector's README notes that a shared index lets one tenant's vectors affect another's recall and speed.

13. Hybrid search: words and meaning together

Lexical and vector search fail differently. BM25 misses paraphrases ("stock" for "share"); vectors miss exact identifiers and rare names, and sometimes rank a vaguely related text above an exact match. Running both and merging the two ranked lists often beats either, but not always: when one retriever is much stronger on your data, an equal-weight fusion can pull it down. Measure it. The two scores cannot simply be added: a BM25 score of 12.3 and a cosine of 0.81 are on unrelated scales. Reciprocal rank fusion (RRF) (Cormack, Clarke and Buettcher, SIGIR 2009) ignores the scores and uses only the ranks:

RRF(d) = Σlists L 1 / (k + rankL(d))
rankL(d)
d's position in list L, starting at 1 (a list that does not contain d adds nothing)
k
60 in the paper ("fixed during a pilot investigation"); Elasticsearch's and OpenSearch's default rank_constant is also 60

RRF on the six questions: the BM25 ranking from section 4 and the cosine ranking from all-MiniLM-L6-v2 for the same query measured.

Try: with a small k the top of each list dominates; with a large k, appearing in both lists matters more than where. "How do I invest in stock market?" lacks the word "share" but ranks well by meaning, so fusion keeps it near the top; the Kohinoor question matches no query word, so only the vector list contributes to it.

Measured on real labelled data (1,000 Quora test questions over the 522,931, and all 300 SciFact claims over 5,183 scientific abstracts, the set the evaluation page also uses; top 100 from each retriever, scored with nDCG@10 and recall@10) measured:

On Quora, vectors beat BM25 (nDCG@10 0.839 against 0.733) and fusion landed between them (0.825). On SciFact, BM25 beat vectors (nDCG@10 0.686 against 0.645) and fusion beat both (0.714). Per question on Quora, BM25 was better on 150, vectors on 388, and they tied on 462: the two retrievers fail on different questions, which is what fusion exploits when both are comparably strong (SciFact) and why an equal-weight fusion costs a little when one is much stronger (Quora). Requiring every word (fts_and) or ranking without idf (fts_or) costs the most; the HNSW index (ef_search 100) gave up little against exact vector search.

The SQL you would deploy, one statement in Postgres (the pattern of pgvector-python's RRF example; the lexical half here ranks by ts_rank, so it inherits section 4's weakness; it scored 0.823 on Quora at 15.4 ms median measured):

WITH lex AS (
  SELECT id, row_number() OVER (ORDER BY ts_rank(tsv, query) DESC) AS r
  FROM q, websearch_to_tsquery('english', $1) query
  WHERE tsv @@ query ORDER BY ts_rank(tsv, query) DESC LIMIT 100),
sem AS (
  SELECT id, row_number() OVER (ORDER BY embedding <=> $2) AS r
  FROM (SELECT id, embedding FROM q ORDER BY embedding <=> $2 LIMIT 100) s)
SELECT coalesce(lex.id, sem.id) AS id,
       coalesce(1.0 / (60 + lex.r), 0) + coalesce(1.0 / (60 + sem.r), 0) AS score
FROM lex FULL JOIN sem USING (id)
ORDER BY score DESC LIMIT 10;

The measured version OR-ed the query's lexemes instead of websearch_to_tsquery's AND, because requiring every word left 50% of Quora questions with no lexical match at all.

Weighting. Elasticsearch, OpenSearch and Weaviate let you weight the lists or fuse normalised scores instead of ranks (OpenSearch's normalization processor, docs); tune the weights on a labelled set, never by eye. On Quora, where duplicates are paraphrases, the right weight for BM25 would be low; on SciFact, where claims share rare scientific terms with their abstracts, BM25 earns its place.

After fusion, many systems re-order the top 20 to 100 with a cross-encoder reranker, a model that reads query and document together; chunking, reranking and the rest of retrieval-augmented generation belong to Topic: rag-and-retrieval. Learned sparse vectors (SPLADE-style, stored in pgvector as sparsevec) are a third retriever some teams add.

14. pgvector or a dedicated vector database?

A "vector database" is an ANN index plus storage, filtering and an API, sold as its own system. pgvector adds the same index types to the Postgres you may already run. The honest comparison is about operations and size, not about the algorithm: most of them run HNSW.

Stay in Postgres (pgvector) when

  • the vectors describe rows you already keep there, and queries join or filter on them (tenant, permissions, dates);
  • you need the vector, its text and its metadata to change in one transaction, deletes to take effect at once (a user deletes a document; its embedding must stop being found), and one backup and failover story;
  • the index fits comfortably in the server's memory (see the arithmetic below).

Consider a dedicated store when

  • the index no longer fits one server's memory, or vector load would crowd out your transactional workload;
  • most queries are heavily filtered and you need in-graph filtering tuned for it, or thousands of isolated tenants;
  • you want disk-based or quantised indexes Postgres lacks (DiskANN, PQ, int8), GPU builds, or object-storage economics;
  • a separate team owns search and wants to scale and rebuild it independently.

The memory arithmetic. Using the measured pgvector HNSW size per vector at 384 dimensions (2,045 bytes, of which 1,544 is the vector), the link overhead is roughly 501 bytes per vector. For 1,536-dimension vectors that is about 6,152 + 501 bytes each, so 10 million need about 67 GB of index (plus the same again in the table), and 100 million about 665 GB. halfvec halves the vector part; binary quantisation of the index cuts it to 192 bytes plus links. The ANN lab's memory calculator does this for any size.

"Under 10M vectors pgvector wins": unconfirmed
The often-quoted thresholds (pgvector below about 10 million vectors, a dedicated store above about 100 million) have no primary measurement behind them; the parent page's atlas marks them unconfirmed. They are where to start measuring, not a crossover. The evidence that exists is vendor-run: Tiger Data reported Postgres with pgvector plus their pgvectorscale extension (not plain pgvector) on 50M 768-dimension vectors at 99% recall with 28 times lower p95 latency than Pinecone's s1 pods (vendor blog, 2024-06-11); Zilliz, the company behind Milvus, publishes VectorDBBench. Neither is independent. Measure your own data at your own recall target.

15. Operations: building, updating and keeping an index honest

Building

  • Load first, index after. pgvector's README: indexes build faster after the initial data is loaded, and IVFFlat must be built after (its centroids come from the data). Use COPY for loading: the 522,931 rows went in by binary COPY in 3.3 s measured.
  • Give the build memory. HNSW builds "significantly faster when the graph fits into maintenance_work_mem". Measured on a 200,000-row copy of the table: 22 s with 2 GB, 87 s with 64 MB, where Postgres printed "hnsw graph no longer fits into maintenance_work_mem after 28373 tuples" measured. Do not set it so high that a build exhausts the server's memory.
  • Use parallel workers. Parallel HNSW builds arrived in 0.6.0; max_parallel_maintenance_workers (here 3, plus the leader) sets how many.
  • Never block writes in production: CREATE INDEX CONCURRENTLY builds without locking out inserts (slower, and it can fail and leave an invalid index to drop). Watch progress in pg_stat_progress_create_index.

Updating

  • Inserts get slower. Each insert into an HNSW-indexed table searches the graph to find its neighbours. 5,000 single-row inserts (each its own transaction) took 11.4 s with the index and 1.8 s without measured: batch inserts where you can.
  • Deletes leave holes. A deleted or updated row stays in the graph until VACUUM removes it and repairs the links around it; meanwhile scans skip dead entries, which can return fewer rows. After deleting 10% of the 200,000 rows, VACUUM took 124 s; rebuilding the index from scratch (REINDEX) took 22 s measured. The README advises REINDEX INDEX CONCURRENTLY before VACUUM when vacuuming is slow. Search engines have the same problem in another form (deleted documents live until a segment merge, section 6).
  • Changing the embedding model means re-embedding everything. Vectors from two models are not comparable. The safe pattern: add a new column (or table) for the new model, backfill it in batches, build its index concurrently, compare recall and relevance on a labelled set, switch queries over, then drop the old column. Store the model name and version beside every vector.

Keeping it honest

  • Monitor recall, not just latency. Recall changes silently as data grows, drifts from IVF centroids, or gains a filter. Sample a few queries an hour, run them exactly (SET enable_indexscan = off in a transaction, or on a replica) and compare with the index's answer.
  • Set ef_search per query, not globally, with SET LOCAL inside a transaction, so a high-recall feature does not slow every other query.
  • Size memory for the index. Check pg_relation_size of each vector index against shared_buffers and the machine's RAM; an HNSW index that falls out of memory turns microsecond page reads into SSD reads at every hop.

What professionals do in production (2026)

  • Postgres first. Start with pgvector beside the data, HNSW with default parameters, vector_cosine_ops or vector_ip_ops matching the model, iterative scans on for filtered queries, and a labelled set of 100 to 1,000 real queries with known good answers before tuning anything.
  • Hybrid as the usual starting point for user-facing search: BM25 (a search engine, or pg_search) plus vectors, fused with RRF, then a reranker for the top results when quality matters more than a few tens of milliseconds; kept only if it beats the better single retriever on the labelled set (it did on SciFact here, not on Quora).
  • The search engine is fed, never written to directly: changes flow from the primary database through an outbox or CDC, and the index can be rebuilt from scratch at any time (aliases make the switch atomic in Elasticsearch).
  • halfvec for storage, binary or int8 for the index, full vectors for re-ranking once memory becomes the cost.
  • Tenant isolation by design: partitions or partial indexes per large tenant in Postgres, namespaces in Pinecone and Turbopuffer, multi-tenancy shards in Weaviate, payload-indexed tenant fields in Qdrant.
  • Recall and relevance dashboards beside latency, measured on the labelled set after every model, index or parameter change (the evaluation page shows how).

Common mistakes

Using LIKE '%word%' as search
It scans every row, matches substrings instead of words, ignores stemming and ranks nothing. Measured: 258 ms against 0.25 ms with a GIN index.
Calling ts_rank "BM25"
Postgres's ranking has no idf; on the labelled Quora set it scored 0.627 nDCG@10 against 0.733 for BM25 over the same lexemes.
Requiring every word (plainto_tsquery) for natural-language questions
AND semantics returned no match at all for 50% of Quora test questions. Use OR with ranking, or websearch syntax, or let BM25 do the weighting.
Different text configuration at index and query time
An index on to_tsvector('english', body) is not used by a query on to_tsvector(body) under a different default configuration, and stems differ. Name the configuration everywhere.
Quoting ANN latency without recall
Any index is fast at low recall: HNSW with m 8 at ef_search 10 answered in 0.31 ms but found only 0.82 of the true top 10.
Post-filtering a selective condition
With a 1% filter and iterative scans off, pgvector returned 0.38 rows on average instead of 10. Turn on iterative scans, add a B-tree for pre-filtering, or partition by tenant.
Expecting more than ef_search rows from one HNSW scan
LIMIT 100 with the default ef_search of 40 returns at most 40 rows (pgvector README, Troubleshooting). Raise ef_search to at least the LIMIT.
Building IVFFlat on an empty or small table
The centroids are learned from the rows present at build time; built too early they describe the wrong data and recall collapses. Build after loading, rebuild after large changes.
Mismatched distance operator and operator class
An index built with vector_l2_ops is not used by an ORDER BY embedding <=> $1 (cosine) query; the query silently falls back to a sequential scan. Also, the ORDER BY must be the bare operator in ascending order (not 1 - (a <=> b) DESC).
Mixing embeddings from two models or versions
Distances between them are meaningless. Store the model id with each vector and re-embed everything when the model changes.
Treating the search engine as the database
No multi-document transactions, about a second of staleness, and a history of lost writes under partitions. Keep the truth in Postgres and rebuild the index from it.
