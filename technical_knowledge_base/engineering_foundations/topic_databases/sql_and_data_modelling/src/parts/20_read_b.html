2. Joins: every pair, filtered

A join pairs every row of a left table with every row of a right table and keeps the pairs for which the ON condition is true. Read it that way and every kind of join follows. It is not a set intersection, which is why Venn-diagram pictures mislead: a left row appears once per matching right row, so zero, one or many times ({{Lukas Eder, "Say NO to Venn diagrams when explaining JOINs", jOOQ blog, 2016|https://blog.jooq.org/say-no-to-venn-diagrams-when-explaining-joins/}}). So draw the pairs: in Fig. 2 every cell is one pair of a user and a market, raised where ON m.code = u.country is true, flat where false, U where it is unknown because a NULL is involved. Predict each join's rows before its step.

  1. CROSS keeps every pair. No condition: 5 × 3 = 15 rows. On the chat data, 50 users and 200 chats make 10,000. Useful on purpose for a grid of every combination (report empty combinations as zero); a forgotten join condition does the same by accident.
  2. INNER keeps the true cells. 3 rows. Chen (IN is not a market) and Dara (no country) vanish; US appears twice because two users match it. A user with no chats disappears; a user with seven chats appears seven times.
  3. LEFT also keeps unmatched left rows. Every user, with NULLs for the market columns where no market matches: 5 rows ("every user, with their chats if any").
  4. RIGHT is the mirror image. Every market: Germany has no users and comes back with NULL user columns; Chen and Dara are gone again. 4 rows. Usually rewritten as a LEFT with the tables swapped.
  5. FULL keeps both sides. The unmatched users and the unmatched market: 6 rows, the join for reconciling two lists. SQLite gained RIGHT and FULL only in {{version 3.39.0, 2022-06-25|https://www.sqlite.org/releaselog/3_39_0.html}}.
  6. Semi join (EXISTS) keeps a row, once. EXISTS or IN (subquery) keeps a user once if any cell in the row is true, however many match: 3 rows. Writing it as a plain JOIN repeats rows, the classic source of "why do I have duplicates?" and of a DISTINCT added to hide it: 42 joined rows against 27 users in the box below.
  7. Anti join (NOT EXISTS) keeps rows with no match. Chen and Dara, 2 rows (also written as a LEFT JOIN keeping rows where the right key IS NULL). NOT EXISTS asks "is there a matching row?", so a NULL anywhere does not change its answer.
  8. NOT IN looks like the anti join, but is not. Dara is missing: her country is NULL, and NULL NOT IN (...) is unknown, not true. 1 row.
  9. Add one NULL market and NOT IN returns nothing. Every comparison against the NULL code is unknown, so no row can pass: 0 rows. NOT EXISTS still returns Chen and Dara.

Three joins that run and return the wrong answer


A LEFT JOIN filtered in WHERE becomes an inner join. A condition on the right table in WHERE throws away the NULL rows LEFT JOIN kept, because NULL = 'reasoning' is unknown, not true: 27 users instead of 50. Conditions that should only limit what is matched belong in ON.








NOT IN with a NULL returns nothing. x NOT IN (a, b, NULL) means x <> a AND x <> b AND x <> NULL; the last term is unknown for every x, so by the AND table the whole condition is never true (the last step of Fig. 2). Two of the five team-plan users have no country, so the subquery holds a NULL: 0 rows against NOT EXISTS's 31. NOT EXISTS asks a different question ("is there a matching row?") and is not affected. The Postgres project's advice is blunt, {{"Don't use NOT IN"|https://wiki.postgresql.org/wiki/Don't_Do_This#Don.27t_use_NOT_IN}} (PostgreSQL wiki), and it also tends to plan badly on large subqueries. Use NOT EXISTS.




Fan-out doubles your totals. Join a parent to a child and a grandchild (or to two child tables) and aggregate, and each parent and child row is repeated once per grandchild row before the aggregate runs. Nothing errors. The rule: aggregate each child table on its own, then join the results (CTEs make this readable, section 5). COUNT(DISTINCT c.id) fixes a count but not a sum.

How the database finds matching pairs (a loop, a hash table, or two sorted inputs) is on {{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}}. One modelling consequence belongs here: Postgres indexes primary keys and UNIQUE columns automatically, but not foreign key columns; the {{documentation on foreign keys|https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-FK}} recommends indexing the referencing column yourself, because joins and deletes of the parent need it.
