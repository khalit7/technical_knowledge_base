1. How a query runs: written in one order, evaluated in another

The problem. You write SELECT first, so it is natural to think the database starts there. It does not, and that mismatch causes most beginner errors: an alias that "does not exist", an aggregate that is "not allowed here", a ranking you cannot filter on.

The idea. A SELECT statement is defined as a pipeline of steps, each producing a table that feeds the next. The {{PostgreSQL SELECT reference|https://www.postgresql.org/docs/current/sql-select.html}} lists the processing order; every SQL database follows the same logical order:

The order you write

  1. SELECT (and DISTINCT)
  2. FROM, JOIN
  3. WHERE
  4. GROUP BY
  5. HAVING
  6. WINDOW
  7. ORDER BY
  8. LIMIT, OFFSET

The order it is evaluated

  1. FROM and JOIN: build the combined rows
  2. WHERE: keep rows whose condition is true
  3. GROUP BY: collapse rows into one per group
  4. HAVING: keep groups whose condition is true
  5. SELECT: compute the output columns, including window functions
  6. DISTINCT: remove duplicate output rows
  7. ORDER BY: sort (it can use output names)
  8. LIMIT, OFFSET: cut

The root page animates this pipeline on nine sample rows ({{Topic: databases|n:3cd5c17b0d0d815d8841ec845f5f3324}}, Reading tab, section 2). Four rules follow from the order, and each one is a common error message:

  • WHERE cannot use a name defined in SELECT, because SELECT has not run yet. ORDER BY can, because it runs after.
  • WHERE cannot use an aggregate such as COUNT(*), because groups do not exist yet; filter groups with HAVING.
  • WHERE cannot use a window function (section 4), because those are computed in the SELECT step; compute it in a subquery and filter outside.
  • LIMIT without ORDER BY returns whichever rows the engine found first. Without an ORDER BY, SQL promises no order at all, and the order can change when the data or the plan changes.

This first box already shows a difference between engines: SQLite accepts the alias in WHERE, Postgres reports column "doubled" does not exist. Write WHERE tokens * 2 > 1780 and both agree. The lesson generalises: test against the database you run in production; SQLite is a fine engine, but its dialect is more permissive.

NULL and three-valued logic. NULL means "unknown", not zero or empty. Any comparison with NULL (= NULL, <> 'US' when the country is NULL) is neither true nor false but unknown, and WHERE keeps only rows where the condition is true. The root's playground has a NULL lesson (COUNT(*) against COUNT(column), IS NULL, where NULLs sort); section 2 shows the most expensive consequence, in NOT IN.

The logical order is not the execution order
The pipeline above defines what the answer must be, not how it is computed. The planner (the part of the database that chooses how to run a query) is free to filter before joining, use an index instead of reading everything, or stop early under a LIMIT, as long as the result is the same. How it chooses, and how to read its plan, is the {{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}} page and the root's Query plans tab.
