2. Joins: every pair, filtered

A join pairs every row of a left table with every row of a right table and keeps the pairs for which the ON condition is true. Read it that way and every kind of join follows. It is not a set intersection, which is why Venn-diagram pictures mislead: a left row appears once per matching right row, so zero, one or many times ({{Lukas Eder, "Say NO to Venn diagrams when explaining JOINs", jOOQ blog, 2016|https://blog.jooq.org/say-no-to-venn-diagrams-when-explaining-joins/}}). Every join is the same grid of pairs; the kinds differ only in what they keep

Five users (one with no country) against a list of markets (one market has no users). Each cell is one pair: filled where ON m.code = u.country is true, blank where false, U where it is unknown because a NULL is involved. Predict which rows each join returns, then pick it; then add a market whose code is NULL and watch NOT IN.









    

  • INNER keeps the filled cells. A user with no chats disappears; a user with seven chats appears seven times.
    • 

  • LEFT also keeps each left row that has no filled cell, with NULLs for the right side ("every user, with their chats if any"); RIGHT is the mirror image (usually rewritten as a LEFT with the tables swapped); FULL keeps unmatched rows from both sides, the join for reconciling two lists. SQLite gained RIGHT and FULL only in {{version 3.39.0, 2022-06-25|https://www.sqlite.org/releaselog/3_39_0.html}}.
    • 

  • CROSS keeps every cell: 50 users and 200 chats make 10,000 rows. Useful on purpose for a grid of every combination (report empty combinations as zero); a forgotten join condition does the same by accident.
    • 

  • Semi (EXISTS or IN (subquery)) keeps a left row once if its row has any filled cell; anti (NOT EXISTS, or LEFT JOIN keeping rows where the right key IS NULL) keeps it if none. Writing a semi join as a plain JOIN repeats rows, the classic source of "why do I have duplicates?" and of a DISTINCT added to hide it: 42 joined rows against 27 users below.
    •

Three joins that run and return the wrong answer


A LEFT JOIN filtered in WHERE becomes an inner join. A condition on the right table in WHERE throws away the NULL rows LEFT JOIN kept, because NULL = 'reasoning' is unknown, not true: 27 users instead of 50. Conditions that should only limit what is matched belong in ON.








NOT IN with a NULL returns nothing. x NOT IN (a, b, NULL) means x <> a AND x <> b AND x <> NULL; the last term is unknown for every x, so by the AND table the whole condition is never true (the U column in the grid above). Two of the five team-plan users have no country, so the subquery holds a NULL: 0 rows against NOT EXISTS's 31. NOT EXISTS asks a different question ("is there a matching row?") and is not affected. The Postgres project's advice is blunt, {{"Don't use NOT IN"|https://wiki.postgresql.org/wiki/Don't_Do_This#Don.27t_use_NOT_IN}} (PostgreSQL wiki), and it also tends to plan badly on large subqueries. Use NOT EXISTS.


Fan-out: joining down two levels repeats each chat once per message






Fan-out doubles your totals. Join a parent to a child and a grandchild (or to two child tables) and aggregate, and each parent and child row is repeated once per grandchild row before the aggregate runs. Nothing errors. The rule: aggregate each child table on its own, then join the results (CTEs make this readable, section 5). COUNT(DISTINCT c.id) fixes a count but not a sum.




What a join costs, and the index this page owns
How the database finds matching pairs (a loop, a hash table, or two sorted inputs) is on {{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}}. One modelling consequence belongs here: Postgres indexes primary keys and UNIQUE columns automatically, but not foreign key columns; the {{documentation on foreign keys|https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-FK}} recommends indexing the referencing column yourself, because joins and deletes of the parent need it.
