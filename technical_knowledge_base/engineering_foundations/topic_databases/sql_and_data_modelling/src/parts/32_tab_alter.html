ALTER TABLE, measured: what each schema change locks, rewrites and costs

Twenty-one common schema changes, each run on a copy of the chat messages grown to rows ( of table data) on PostgreSQL 16.2, with what it actually did.

How it was measured (src/pg/measure_alter.py): each change ran inside its own transaction; while that transaction was still open, pg_locks was read for the locks it held on the table, and a second session tried a point SELECT and an INSERT with lock_timeout = 300ms to see whether they were blocked; the table's file node was compared before and after to see whether the table was rewritten; then the transaction was rolled back so every change started from the same table. CREATE INDEX CONCURRENTLY cannot run in a transaction, so it was watched from a second session while it ran. Times are medians of 3 runs on a laptop. Lock names: AccessExclusive blocks everything, reads included; ShareRowExclusive and Share block writes but not reads; ShareUpdateExclusive blocks neither, only other schema changes and VACUUM ({{PostgreSQL table-level locks|https://www.postgresql.org/docs/current/explicit-locking.html}}).

Read the times in context
A metadata-only change finishes in about a millisecond whatever the table size; the danger is the lock queue in front of it (Reading, section 11). A rewrite or a scan grows with the table: the "your table" column scales the measured time linearly with the row count, which is a rough guide only (it ignores memory, disk speed, indexes and concurrent load). Plan with a measurement on a production-sized copy.
