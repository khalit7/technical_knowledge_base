2. Joins in depth

The problem. Normalised data (section 9) puts each fact in one table, so almost every real question needs rows from two or more tables at once: a chat's title with its owner's name, users with no chats, each reply next to its prompt. A join combines them.

The idea. A join pairs rows from a left table and a right table and keeps the pairs for which the ON condition is true. Read it that way, as "every pair, filtered", and every kind of join below follows. It is not a set intersection, which is why the familiar Venn-diagram pictures mislead: a left row appears once per matching right row, so zero, one or many times ({{Lukas Eder, "Say NO to Venn diagrams when explaining JOINs", jOOQ blog, 2016|https://blog.jooq.org/say-no-to-venn-diagrams-when-explaining-joins/}}).

Inner, left, right, full, cross


    

  • INNER JOIN keeps only pairs that match. A user with no chats disappears; a user with seven chats appears seven times.
    • 

  • LEFT JOIN (LEFT OUTER JOIN) keeps every left row; where nothing matches, the right side's columns are NULL. This is how you get "every user, with their chats if any". RIGHT JOIN is the mirror image; most people rewrite it as a LEFT JOIN with the tables swapped.
    • 

  • FULL OUTER JOIN keeps unmatched rows from both sides. It is the join for reconciling two lists ("which markets have no users, and which users are in no market?"). SQLite gained RIGHT and FULL joins only in {{version 3.39.0, 2022-06-25|https://www.sqlite.org/releaselog/3_39_0.html}}.
    • 

  • CROSS JOIN pairs every row with every row (no ON). 50 users and 200 chats make 10,000 rows. Useful on purpose for building a grid of every combination, as below; dangerous by accident (a forgotten join condition does the same).
    •

Semi and anti joins: "has at least one" and "has none"


A semi join keeps a left row if some right row matches, without repeating it per match: EXISTS (subquery) or IN (subquery). An anti join keeps a left row if no right row matches: NOT EXISTS, or a LEFT JOIN keeping rows where the right key IS NULL. Writing a semi join as a plain JOIN repeats rows, the classic source of "why do I have duplicates?" and of a DISTINCT added to hide it:










Why. x NOT IN (a, b, NULL) means x <> a AND x <> b AND x <> NULL; the last comparison is unknown for every x, so the whole condition is never true and every row is dropped. Two of the five team-plan users have no country, so the subquery contains NULL. NOT EXISTS asks a different question ("is there a matching row?") and is not affected. The Postgres project's own advice is blunt: {{"Don't use NOT IN"|https://wiki.postgresql.org/wiki/Don't_Do_This#Don.27t_use_NOT_IN}} (PostgreSQL wiki); it also tends to plan badly on large subqueries. Use NOT EXISTS.


Fan-out: the join that doubles your totals


Join a parent to two different child tables (or to a child and a grandchild) and aggregate, and each parent row is repeated once per child row before the aggregate runs. Counts and sums come out too large, and nothing errors:




The rule: aggregate each child table on its own, then join the results (CTEs make this readable, section 5). COUNT(DISTINCT c.id) fixes a count but not a sum.


What a join costs
A join is work proportional to how the database finds matching rows: by looping, by building a hash table, or by walking two sorted inputs. Which one it picks, and why joining on an indexed column matters, is on {{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}}. One modelling consequence belongs here: Postgres indexes primary keys and UNIQUE columns automatically, but not foreign key columns; the {{documentation on foreign keys|https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-FK}} recommends indexing the referencing column yourself, because joins and deletes of the parent need it.
