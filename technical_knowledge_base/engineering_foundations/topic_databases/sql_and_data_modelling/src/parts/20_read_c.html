3. Grouping: many rows become one per group

GROUP BY collapses all rows sharing the grouping values into one row, and aggregate functions (COUNT, SUM, AVG, MIN, MAX) summarise each group. Every column in the SELECT list must then be grouped or aggregated; SQLite's leniency here (it picks an arbitrary row) is a lesson in the root's playground. A window function (section 4) computes the same aggregate but keeps every row. Same 16 rows, both ways, at one scale, so a stack is literally its sum:

  1. Sixteen rows. The real messages of chat 11, 8 from the user and 8 from the assistant, each bar as tall as its tokens.
  2. GROUP BY role splits them. The user rows go to one group, the assistant rows to the other (PARTITION BY role splits a window the same way).
  3. Each group folds into one row. SELECT role, COUNT(*), SUM(tokens) FROM messages WHERE chat_id = 11 GROUP BY role: user 8 rows and 477 tokens, assistant 8 rows and 3,826. 16 rows in, 2 rows out; the ids are gone, so a column such as id can no longer be selected unless it is grouped or aggregated.
  4. A window keeps every row. SUM(tokens) OVER (PARTITION BY role) writes its partition's total on each row: 477 on every user row, 3,826 on every assistant row. 16 rows in, 16 rows out.
  5. ORDER BY inside OVER: a running total. OVER (PARTITION BY role ORDER BY id) sums from the partition's first row to the current one: the user rows read 103, 204, 223 ... 477. Which rows the sum sees is the frame, section 4.

Several counts in one pass. "Per model: messages, replies, reply tokens, distinct users" is conditional aggregation. The NULL cells of aggregation: COUNT(column) skips NULLs, so after a LEFT JOIN count the right table's key, not *, or every empty group counts as 1; SUM over zero rows is NULL, not 0 (wrap it in COALESCE(SUM(x), 0)); and an average of averages is wrong when groups differ in size (average the raw rows, or weight by count).

Subtotals with ROLLUP, CUBE and GROUPING SETS, and the AVG type difference (depth)

GROUP BY ROLLUP (plan, model) returns the per-plan-and-model rows, a subtotal row per plan (model shown as NULL) and a grand total (both NULL). CUBE and GROUPING SETS generalise it. SQLite has none of them, so this box is Postgres only. AVG of an integer column is a numeric with many digits in Postgres and a float in SQLite: round explicitly when you compare.

4. Window functions: a value per row from its neighbours

Many questions need every row and something about its neighbours: rank each user by tokens, the time since the previous message, a running total, the latest message per chat (before window functions, slow self joins or correlated subqueries). A window function's OVER (...) has three parts: PARTITION BY splits rows into independent groups (all rows if absent); ORDER BY orders rows inside each partition (ranking and LAG/LEAD need it); the frame says which rows around the current one an aggregate sees (ROWS BETWEEN 2 PRECEDING AND CURRENT ROW: this row and the two before). With an ORDER BY and no frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW: from the start of the partition to the current row and every row tied with it ({{SQLite window functions|https://www.sqlite.org/windowfunctions.html}}; Postgres {{documents the same default|https://www.postgresql.org/docs/current/sql-expressions.html#SYNTAX-WINDOW-FUNCTIONS}}).

  1. The rows, in window order. The 16 messages of chat 11 ordered by id (back row): one partition here. Each function below is computed for every row in turn; the glass box is the frame it sees for the current row, the front row its results.
  2. SUM(tokens) OVER (ORDER BY id). The default frame runs from the first row to the current one, so the sum is a running total: 103, 548, 649 ... 4,303.
  3. AVG over ROWS BETWEEN 2 PRECEDING AND CURRENT ROW. A three-row frame slides along: 103.0, 274.0, 216.3 ... 261.0. Near the start the frame is shorter, which is why the first values are noisier.
  4. LAG(tokens) reads the previous row. The first row has none, so it gets NULL. Subtracting timestamps the same way gives the gap between messages.
  5. RANK() OVER (ORDER BY tokens DESC). No frame: the rank counts the rows that sort before this one (lit), plus one. The 889-token reply ranks 1, the 16-token message 16; ties would share a rank and leave a gap.
  6. LAST_VALUE(tokens) with the default frame. The frame ends at the current row, so the "last value" is always the current row's own tokens: the front row copies the back row. Almost never what was meant.
  7. LAST_VALUE over the whole partition. ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING: every row sees the chat's last message, 338 tokens.

Two frame traps. LAST_VALUE with the default frame returns the current row's value, because the frame ends at the current row; ask for the whole partition. And the default frame is RANGE, so rows tied on the ORDER BY value enter together: two chats opened on the same day get the same running count. Say ROWS when you mean rows.

Rankings. ROW_NUMBER() numbers 1, 2, 3 even through ties (add a tie-breaker to its ORDER BY, or two runs can number tied rows differently); RANK() gives ties one number and leaves a gap (1, 1, 3); DENSE_RANK() leaves none (1, 1, 2). Top N per group, the most common production use: number the rows per partition in a subquery and keep rn <= N outside (a window result cannot be filtered in the same SELECT's WHERE, section 1). Postgres also has DISTINCT ON (user_id) ... ORDER BY user_id, ... for N = 1.

5. CTEs and recursive queries

A common table expression, WITH name AS (SELECT ...), names a step of a query so later steps use it like a table (the fan-out fix in section 2 used two). It usually costs nothing: since PostgreSQL 12, a CTE that is referenced once, is not recursive and has no side effects is inlined into the main query and optimised with it; MATERIALIZED forces it to be computed once on its own, NOT MATERIALIZED forces inlining ({{PostgreSQL 12 release notes|https://www.postgresql.org/docs/release/12.0/}}; {{WITH queries|https://www.postgresql.org/docs/current/queries-with.html}}). Advice that "CTEs are an optimisation fence" describes Postgres 11 and earlier.

Each iteration joins only the rows the last one added, and stops when it adds none

When recursion goes wrong
A recursive query on a cycle (a message that is its own ancestor through bad data) never ends: guard with a depth limit (WHERE depth < 100) or, in Postgres 14 and later, the CYCLE clause. Trees read far more than written are often stored differently (section 8); traversals many hops deep across large graphs are the graph section of {{NoSQL in practice|n:3ef5c17b0d0d81ec8456c41e4e8f5f6b}}.
