11. Migrations: changing a schema that is in use

The problem. The schema must change as the product does (a new column, a new table, a renamed field), but the database is serving traffic, several copies of the application are running, and during a deploy old and new versions of the code run at the same time. Edit the schema by hand and environments drift apart; change it carelessly and you lock a busy table.

The idea. A migration is a small versioned script that moves the schema from one version to the next, stored in the repository next to the code that needs it. A migration tool applies the scripts in order and records which ones ran in a table of its own (Alembic's is alembic_version), so every environment, from a laptop to production, reaches the same schema by the same steps. Two rules follow: never edit a migration that has run somewhere else (write a new one), and never change production's schema except through one.

On a big table, edit the script to use op.create_index(..., postgresql_concurrently=True) inside an autocommit_block(), because Postgres refuses CREATE INDEX CONCURRENTLY inside a transaction.


Every ALTER TABLE takes a lock


Postgres protects a table's definition with table locks. An ordinary SELECT takes the weakest, ACCESS SHARE; an INSERT, UPDATE or DELETE takes ROW EXCLUSIVE. Most ALTER TABLE forms take the strongest, ACCESS EXCLUSIVE, which {{"guarantees that the holder is the only transaction accessing the table in any way"|https://www.postgresql.org/docs/current/explicit-locking.html}}: while it is held, even reads wait. What separates a safe change from an outage is how long that lock is held, and the measured tab shows it for 21 changes. The short version, on the 2,000,000-row copy of messages:




    

  • Metadata-only changes take milliseconds: adding a nullable column, adding a column with a constant default (since {{PostgreSQL 11|https://www.postgresql.org/docs/release/11.0/}} the default is stored once in the catalog, not written to every row), dropping or renaming a column, changing a default, widening a varchar.
    • 

  • Rewrites hold ACCESS EXCLUSIVE for the whole copy: a volatile default such as clock_timestamp(), a stored generated column, most type changes (integer to bigint, text to varchar(200)). Seconds here, hours on a big table.
    • 

  • Scans hold the lock while they check every row: SET NOT NULL, ADD CHECK, ADD FOREIGN KEY (which takes SHARE ROW EXCLUSIVE: reads continue, writes wait).
    • 



Each slow form has a safe recipe: CREATE INDEX CONCURRENTLY (builds without blocking writes, slower, cannot run in a transaction); ADD CONSTRAINT ... NOT VALID (instant, checks only new rows) followed by VALIDATE CONSTRAINT (checks old rows under a lock that blocks neither reads nor writes); for NOT NULL, a validated CHECK (col IS NOT NULL) lets SET NOT NULL skip its scan (PostgreSQL 12 and later; PostgreSQL 18 also accepts NOT VALID on not-null constraints directly); for a volatile default, add the column nullable, backfill in batches, then set the default.


Older guides are out of date on two points
Many migration guides still say adding a column with a default rewrites the table; that stopped being true for constant defaults in PostgreSQL 11 (2018), and the measurement agrees ( ms on 2,000,000 rows). GoCardless's widely shared {{"Zero-downtime Postgres migrations: the hard parts"|https://gocardless.com/blog/zero-downtime-postgres-migrations-the-hard-parts/}} was written against PostgreSQL 9.4 (its footnotes say so) and says adding a foreign key takes ACCESS EXCLUSIVE locks on both tables. {{PostgreSQL 9.5|https://www.postgresql.org/docs/release/9.5.0/}} reduced the lock level of foreign key commands; current Postgres takes {{SHARE ROW EXCLUSIVE|https://www.postgresql.org/docs/current/sql-altertable.html}} on both tables, which was measured here: reads continue, writes wait. Its central lesson, the lock queue below, is still exactly right.


The lock queue: how a 1 ms change causes an outage


Locks are granted in order. If a long transaction holds even the weakest lock on a table (a report running a slow SELECT, or a request that opened a transaction and is waiting on a model call), an ALTER TABLE asking for ACCESS EXCLUSIVE must wait for it. Worse, every query that arrives after the ALTER queues behind it, because granting them would starve the ALTER. A change that would take a millisecond blocks all traffic to the table for as long as the oldest transaction lasts. The animation replays three real runs on the 2,000,000-row table: one long transaction holding the table for 4 seconds, one ADD COLUMN ... DEFAULT 0 (metadata only), and seven ordinary point reads arriving every half second.

The fix is to bound the wait, not to hope. Set lock_timeout in every migration session (SET lock_timeout = '500ms'): the ALTER gives up instead of queueing indefinitely ({{documentation|https://www.postgresql.org/docs/current/runtime-config-client.html#GUC-LOCK-TIMEOUT}}), and the migration retries with a pause. Readers then wait at most the timeout. Set statement_timeout on backfills, keep application transactions short, and set idle_in_transaction_session_timeout so a forgotten open transaction cannot hold locks forever.


Expand and contract: changes that never break running code


During a rolling deploy, old and new versions of the application run at the same time, so every intermediate schema must work with both. Expand and contract (also called parallel change) splits a breaking change into backward-compatible steps, each deployed on its own. Renaming chats.title to chats.name:


    

  1. Expand: ALTER TABLE chats ADD COLUMN name text (metadata only).
    2. 

  2. Write both: deploy code that writes title and name (or add a trigger that copies one to the other).
    3. 

  3. Backfill in batches: UPDATE chats SET name = title WHERE id BETWEEN $1 AND $2 AND name IS NULL, a few thousand rows per transaction, with a pause between batches, so no lock or replication lag builds up.
    4. 

  4. Read the new column: deploy code that reads name.
    5. 

  5. Stop writing the old one once no running version reads it.
    6. 

  6. Contract: ALTER TABLE chats DROP COLUMN title, a release or more later.
    7. 



Each step can be rolled back by redeploying the previous code. RENAME COLUMN itself is instant, but it breaks every running instance that still uses the old name; that, not the lock, is why renames go through these six steps.


What professionals do
Migrations in the repository, applied by CI/CD (continuous integration and delivery: automated testing and deployment) before the code that needs them; reviewed as SQL, not just as model diffs; linted (Squawk, strong_migrations); timed on a production-sized copy; run with lock_timeout and retries; one risky operation per migration; roll forward with a new migration rather than run "down" migrations in production, with backups and point-in-time recovery as the real safety net ({{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}}).
