7. Entities, relationships and keys

Start from the nouns the product must remember, each with its own identity and lifecycle (a user, a chat, a message): each becomes a table, an entity, and its facts become columns, attributes. The verbs between them become relationships, and the kind decides where the key goes (all three are in the hero figure and the shapes of section 8):

One to many

A user has many chats; a chat has one user. The foreign key goes on the "many" side: chats.user_id. Most relationships.

Many to many

Shared chats: a chat has many members, a user many shared chats. Neither table can hold the other's key, so a join table holds pairs, chat_members(chat_id, user_id, role) with the pair as its primary key, and is the natural place for facts about the membership itself (the role, when it started).

One to one

A user has one credits balance: credits.user_id is both primary key and foreign key. Split one-to-one only for a reason: a different write rate (a balance changes on every message, a profile rarely), optional data, or tighter access control.

Natural or surrogate key

A natural key is a real-world value that already identifies the row (an email address); a surrogate key is an id the database invents, with no meaning. Natural keys age badly: people change emails, case and whitespace make two spellings of one address, and a key copied into every foreign key must change everywhere when it changes. The production default: a surrogate primary key, plus a UNIQUE constraint on the natural key so duplicates are still refused. Join tables are the exception: the pair is the right primary key.

bigint, UUID v4 or UUID v7

  • bigint identity (bigint GENERATED ALWAYS AS IDENTITY, the SQL-standard spelling Postgres has supported since version 10; the older serial is on the wiki's {{Don't Do This|https://wiki.postgresql.org/wiki/Don't_Do_This#Don.27t_use_serial}} list): 8 bytes, sequential, compact. Use bigint, not integer: a 4-byte integer runs out at 2,147,483,647, and changing a key's type later rewrites the table and every index ({{ALTER TABLE, measured|#t-alter}}).
  • UUID version 4: 16 bytes, 122 bits of them random. Any machine can generate one without asking the database (clients create ids offline, ids from separate databases never collide, nobody can guess the next one), but each new key lands at a random place in the index.
  • UUID version 7 ({{RFC 9562, May 2024|https://www.rfc-editor.org/rfc/rfc9562.html#name-uuid-version-7}}): the Unix time in milliseconds in the first 48 bits, random bits after. Generated anywhere like v4, but new keys sort after old ones like bigint; it reveals when a row was created. PostgreSQL 18 (released {{2025-09-25|https://www.postgresql.org/docs/18/release-18.html}}) has a built-in uuidv7(); on 16 and 17 generate it in the application or with a small function (the measurement below used one).

Why order matters is a B-tree mechanism: sequential keys append to the last leaf page, random keys split pages all over the index, leave them about 69% full and write more whole pages to the WAL (the write-ahead log, the record of every change written before the data, which replicas and backups also consume). {{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}} owns it: section 5 draws and measures it, and its B-tree and LSM lab lets you insert ascending against random keys. What it means for choosing a key, measured here:

Random UUID v4 keys cost a bigger index and more WAL than v7 for the same rows measured

PostgreSQL 16.2 on a laptop, default settings (128 MB of shared buffers). Keys generated first into a temporary table (generation timed apart: gen_random_uuid took 12.9 s per 1M here, more than the insert), then inserted in generation order with one INSERT ... SELECT into a table of the key plus two integers. 1M figures are medians of 3 runs, 10M single runs.

Reading the measurement: two effects are mixed in it (depth)

A UUID is twice as wide as a bigint, so its index is bigger whatever the order. Random order adds half-empty pages after splits and writes scattered over the whole index, which stops fitting in memory as the table grows, and a larger WAL, because after each checkpoint the first change to a page writes the whole 8 KB page ({{full_page_writes|https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-FULL-PAGE-WRITES}}). Version 7 removes the second cost and keeps the first.

The choice: bigint identity for internal keys; UUID v7 when ids must be generated outside the database or merged across databases; UUID v4 only when unguessable, time-free ids matter more than write cost. If a public id must not reveal volume or creation time, keep a bigint primary key and add a separate random public id with a UNIQUE index.
