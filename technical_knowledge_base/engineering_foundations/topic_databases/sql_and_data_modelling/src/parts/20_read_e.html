6. Set operations, upserts and MERGE

Set operations combine the results of two queries with the same columns. UNION stacks them and removes duplicates; UNION ALL stacks them and keeps everything, which is cheaper (no de-duplication step) and is what you want unless duplicates are genuinely wrong. INTERSECT keeps rows in both; EXCEPT keeps rows in the first but not the second. All three compare whole rows and, unlike =, treat two NULLs as equal. Postgres requires an alias on a subquery in FROM; SQLite does not, another small dialect difference:

Upsert: insert, or update if it already exists

The problem. Count each user's tokens per day. The naive code reads the row, then inserts it if missing or updates it if present. Two requests at once both read "missing" and both insert: one fails on the primary key, or, without a key, you get two rows. This is a race condition (two operations interleaving so that the result depends on timing); the {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}} page covers the family.

The idea. Let the database do both in one atomic statement: INSERT ... ON CONFLICT (key) DO UPDATE SET ..., where excluded names the row you tried to insert. It needs a UNIQUE constraint or primary key to detect the conflict. Postgres has had it since 9.5; SQLite copied the syntax in {{3.24.0, 2018-06-04|https://www.sqlite.org/lang_upsert.html}}. MySQL spells it INSERT ... ON DUPLICATE KEY UPDATE.

ON CONFLICT DO NOTHING plus RETURNING (which returns the inserted rows) is the standard way to make a handler idempotent: safe to run twice with the same input, as a retried request or a webhook delivered twice will be. The {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}} page builds idempotency keys on exactly this.

MERGE (SQL standard; Postgres since {{version 15|https://www.postgresql.org/docs/15/release-15.html}}) states several cases in one statement: update when matched, insert when not matched, optionally delete. It reads well for syncing a table from a batch. What it costs: unlike ON CONFLICT, a Postgres MERGE with both INSERT and UPDATE branches {{"does not guarantee that either INSERT or UPDATE will occur"|https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED}} when another transaction is changing the same rows, so two concurrent MERGEs inserting the same new key can fail with a unique violation; the {{MERGE page|https://www.postgresql.org/docs/current/sql-merge.html}} itself points to INSERT ... ON CONFLICT for that case. Use MERGE for batch syncs, ON CONFLICT for concurrent single-row upserts.

7. JSON columns and time zones

JSON in Postgres: jsonb

The problem. Some data has a shape that varies row by row and that you rarely query field by field: an LLM's tool calls and their arguments, a provider's raw response, user preferences, a webhook payload. A column per possible field would be mostly empty; a separate table per shape would be dozens of tables.

The idea. Store it as JSON in a column. Postgres has two types: json keeps the text exactly; jsonb stores a parsed binary form, so fields can be read and indexed without re-parsing. The documentation's advice: {{"most applications should prefer to store JSON data as jsonb"|https://www.postgresql.org/docs/current/datatype-json.html}}. The operators to know: -> returns a JSON value, ->> returns text, @> tests containment ("does this document contain this sub-document?"), and a GIN index (a generalised inverted index: for each key and value, the list of rows containing it) makes containment queries fast. Use jsonb when

  • the shape genuinely varies, or belongs to someone else (an API response kept for audit);
  • you read the document whole, and filter on a few fields at most;
  • it is an attachment to a row that has real columns for everything you join, group or constrain on.

Use columns when

  • you join on it, group by it, or need a foreign key or a CHECK on it;
  • every row has the field (a "flexible" document where every row has the same keys is a table in disguise, without types or constraints);
  • you update single fields often (jsonb is rewritten whole on update).

The root's Database atlas compares this with a document database; the short version is that Postgres jsonb covers most document needs while keeping joins and constraints ({{Topic: databases|n:3cd5c17b0d0d815d8841ec845f5f3324}}, section 6).

Dates and time zones

The problem. A user in Tokyo asks for "today's messages". The server runs in UTC (Coordinated Universal Time, the time zone with no offset). Daylight saving time moves clocks in some zones twice a year. Times stored without saying which zone they are in become ambiguous the moment a second zone is involved.

The idea. Postgres has timestamp (a date and wall-clock time, with no zone) and timestamptz (an absolute instant). Despite its name, timestamptz does not store a zone: the input is converted to UTC and stored as UTC, and on output it is shown in the session's TimeZone setting ({{documentation|https://www.postgresql.org/docs/current/datatype-datetime.html}}). What professionals do
Store instants as timestamptz (the Postgres wiki's {{Don't Do This|https://wiki.postgresql.org/wiki/Don't_Do_This#Don.27t_use_timestamp_.28without_time_zone.29}} page says not to use plain timestamp for them); keep sessions in UTC; convert to the user's zone (an IANA name such as Asia/Tokyo, never a fixed offset like +09:00, which ignores daylight saving) only when bucketing by day or displaying; store a user's zone as a column if reports need their days. Use date for calendar dates with no time (a birthday). SQLite has no date type at all: store ISO 8601 text in UTC or integer Unix seconds, and be consistent.
