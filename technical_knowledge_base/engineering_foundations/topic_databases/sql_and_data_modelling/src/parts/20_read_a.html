The idea in one screen

A query is a pipeline over tables (pair rows, keep the true ones, group, compute, order), and most SQL bugs are queries that run and return plausible wrong numbers; a schema is the rules every write must pass, so put each fact in one place, every rule in a constraint, and change the schema only in small, backward-compatible steps.

The whole page happens on these four tables: joins follow the arrows, rules sit on the columns

The root's chat data: 50 users, 200 chats, 2,000 messages, one credits balance per user. PK is a primary key (a column whose value names exactly one row), FK a foreign key (a column holding another table's primary key). This page adds one column, messages.parent_id (the previous message in its chat; empty for the first), the arrow back into messages that makes a thread a tree.

You need: the first six clauses (SELECT, FROM, WHERE, GROUP BY, ORDER BY, LIMIT) on this data, taught in the {{root page|n:3cd5c17b0d0d815d8841ec845f5f3324}} (Reading section 2 and its SQL playground). How the database runs a query is {{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}}; transactions and isolation are {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}}; how rows and indexes sit on disk is {{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}}; analytics engines are {{Analytics: columnar engines, DuckDB and the lakehouse|n:3ef5c17b0d0d8157814ec5dd8a0d4fb5}}. Three-valued logic

Semi, anti join
keep a row if some (semi) or no (anti) matching row exists, without repeating it per match.
Fan-out
a join that repeats a row once per matching child, inflating counts and sums.
Window function
a value computed for each row from related rows (its window), without collapsing them.
CTE

1. Written in one order, evaluated in another; NULL is unknown

A SELECT is defined as a pipeline of steps, each producing a table for the next, in an order that is not the order you write it (the {{PostgreSQL SELECT reference|https://www.postgresql.org/docs/current/sql-select.html}} lists it; every SQL database follows the same logical order). The order explains most "why is this an error" moments:

A name exists only from the step that makes it: aliases from SELECT, aggregates from GROUP BY

Read top to bottom: the evaluation order. A dot means the step can use it. Hence WHERE cannot use a SELECT alias (SELECT has not run) but ORDER BY can; WHERE cannot use an aggregate such as COUNT(*) (filter groups with HAVING); WHERE cannot use a window function (compute it in a subquery, filter outside); and LIMIT without ORDER BY returns whichever rows the engine found first, an order that can change when the data or the plan changes. The root animates the same pipeline on nine rows.

SQLite accepts the alias, Postgres reports column "doubled" does not exist; write WHERE tokens * 2 > 1780 and both agree. Test against the database you run in production: SQLite's dialect is more permissive (aliases in WHERE, loose GROUP BY, foreign keys off by default, loose typing); run Postgres in a container or with pgserver in CI.

NULL means "unknown", not zero or empty, and SQL computes with three truth values. Any comparison with NULL (= NULL, <> 'US' when the country is NULL) is unknown, and WHERE, ON and HAVING keep only rows where the condition is true, so unknown rows silently vanish. T true, F false, U unknown. IS NULL, IS DISTINCT FROM and COALESCE are the operators that turn unknown into a definite answer. Aggregates skip NULLs: COUNT(*) counts rows, COUNT(column) counts non-NULL values (the root's playground has a NULL lesson, including where NULLs sort). Set operations and GROUP BY are the exceptions that treat two NULLs as equal (section 6).

The logical order is not the execution order
The pipeline defines what the answer must be, not how it is computed. The planner (the part of the database that chooses how to run a query) may filter before joining, use an index instead of reading everything, or stop early under a LIMIT, as long as the result is the same. How it chooses, and how to read its plan, is {{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}} and the root's Query plans tab.
