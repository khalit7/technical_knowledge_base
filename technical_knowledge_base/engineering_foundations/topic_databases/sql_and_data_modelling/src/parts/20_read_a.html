SQL and data modelling in one screen

About 45 minutes to read (the longest sections are joins, normalisation and migrations), plus the runnable examples and animations. Each numbered section can be read on its own. Numbers marked measured were measured for this page on a laptop (Apple M1 Pro, PostgreSQL 16.2 from the pgserver wheel); illustrative marks anything made up to show a shape.

SQL is how you ask a relational database questions; data modelling is deciding which tables, columns, keys and rules to give it so that the answers stay right as the product changes. The {{root page|n:3cd5c17b0d0d815d8841ec845f5f3324}} (Reading tab, section 2, and its SQL playground tab) teaches the first six clauses on the chat product's data. This page takes the same data from there to the level a professional backend engineer works at.

The data is the root's: 50 users, 200 chats, 2,000 messages and one credits balance per user. A table is a named set of rows with fixed columns; a primary key is a column whose value names exactly one row; a foreign key is a column holding another table's primary key (chats.user_id says which user owns a chat). This page adds one column, messages.parent_id: the message each message replies to (the previous one in its chat; empty for a chat's first message), so that threads can be walked in section 5.

The four tables and how they point at each other. PK marks a primary key, FK a foreign key; the arrow from parent_id back into messages is what makes a thread a tree.

Every grey box with a Run button is a real database. It is SQLite (an embedded SQL database that its authors call {{the most widely deployed|https://www.sqlite.org/mostdeployed.html}} database engine) compiled to WebAssembly and running inside this page, the same engine the root's playground uses. Next to its live result sits the result of the same query on a real PostgreSQL server (Postgres for short: the free relational database the root recommends as the default), recorded offline. Where the two disagree, the box says so: those differences are where real teams get bitten. Edit any query and run it; nothing you do leaves your browser.

The three ideas to keep
1. Write the query for the result, then check the rows: most SQL bugs return plausible numbers, not errors (a LEFT JOIN filtered in WHERE, NOT IN with a NULL, a join that repeats rows). 2. Put every rule the data must obey into the schema (keys, NOT NULL, CHECK, UNIQUE, foreign keys), because the schema is the only code every writer must pass through. 3. Change a live schema in small, backward-compatible steps with a lock timeout, because the dangerous part of a migration is rarely the change itself; it is what waits behind it.
