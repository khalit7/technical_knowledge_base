12. SQL that an ORM or an LLM writes for you

Much production SQL is not written by hand: an ORM (object-relational mapper) generates it from classes, and LLMs generate it from questions (text-to-SQL features, agents with a database tool). Both produce SQL that runs; the two failures that matter are SQL that is slow by shape (too many round trips) and SQL that is wrong or unsafe (it returns plausible numbers, or does more than it should). This section shows each on the chat data, then the checks that catch them.

The N+1 query problem

An ORM maps tables to classes and rows to objects, writes the SQL, and tracks changes so it can save them; in Python the standard is {{SQLAlchemy|https://docs.sqlalchemy.org/en/21/}} (2.1.3, released 2026-10-03 per {{PyPI|https://pypi.org/project/SQLAlchemy/}}), whose 2.x style declares typed models and builds queries with select(). What it hides is the SQL and, above all, the number of round trips (one request and its reply over the network: a fraction of a millisecond to a millisecond or two inside one data centre, paid per query however small):

class Chat(Base):
    __tablename__ = "chats"
    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    title: Mapped[str | None]
    created_at: Mapped[datetime.datetime]
    messages: Mapped[list["Message"]] = relationship(order_by="Message.id")

chats = session.scalars(select(Chat).order_by(Chat.created_at.desc()).limit(50)).all()
for c in chats:
    print(c.id, len(c.messages))      # each c.messages here is a new query

The loop runs 1 query for the chats and then, because relationships load lazily by default (only when first touched), 1 more per chat: N+1 in total. The {{SQLAlchemy documentation|https://docs.sqlalchemy.org/en/21/orm/queryguide/relationships.html}} names it as "one of the most common issues referred to in object relational mapping". It is invisible in development, where the database is on the same machine and there are ten rows, and grows linearly with the page size and the network distance. What an ORM gives you in return (depth)

Less boilerplate for create, read, update and delete; queries composed from Python pieces; parameters bound safely by default; an identity map (one object per row per session); a unit of work (changes flushed in a valid order); and models Alembic can diff.

The fixes: selectinload(Chat.messages) loads all the children with a second query WHERE chat_id IN (...), 2 queries whatever N (the documentation calls it {{"the most simple and efficient way to eagerly load collections"|https://docs.sqlalchemy.org/en/21/orm/queryguide/relationships.html}}); joinedload(Chat.messages) uses one LEFT JOIN, but each chat's columns repeat once per message (fan-out again), so it suits many-to-one (a message's chat) better than one-to-many; raiseload("*") in tests or on hot paths turns any accidental lazy load into an error, so N+1 cannot creep back; or write one SQL statement that aggregates in the database and returns only what the screen needs. In practice: the ORM for ordinary reads and writes, hand-written SQL (SQLAlchemy Core, text(), or sqlc) for reports and anything performance-critical, and paginate by key, not by OFFSET ({{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}} measures why).

SQL injection, live

If a program builds SQL by pasting input into the query text, the input can change the query's meaning: SQL injection, still near the top of the {{OWASP|https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html}} list of web risks. The fix: parameterised queries. Write placeholders (? in SQLite, %s in psycopg, :name in SQLAlchemy's text()) and pass the values separately; the value is then data, never SQL, and an apostrophe in a real name stops being a bug too. Psycopg 3 {{"sends the query and the parameters to the server separately"|https://www.psycopg.org/psycopg3/docs/basic/from_pg2.html}}; its rule is {{"Never use % or + to merge values into queries"|https://www.psycopg.org/psycopg3/docs/basic/params.html}}.


# wrong: the input becomes part of the SQL
cur.execute(f"SELECT id FROM users WHERE email = '{email}'")
# right: the input is a value
cur.execute("SELECT id FROM users WHERE email = %s", (email,))
# SQLAlchemy
session.execute(text("SELECT id FROM users WHERE email = :e"), {"e": email})


Identifiers cannot be parameters: a table name, a sort column or ASC/DESC from input must come from an allow-list in your code, or be quoted with psycopg.sql.Identifier ({{psycopg.sql|https://www.psycopg.org/psycopg3/docs/api/sql.html}}). An ORM protects you only while you use it as intended: text() or raw SQL built with f-strings is as vulnerable as anything else. Defence in depth: the application's role gets only the privileges it needs (no DDL, no superuser), and row-level security (section 8) limits what a successful injection could read.

Depth: a review checklist


The mistakes this page teaches, one line each, with the habit that prevents it (review list)


    

  • A LEFT JOIN filtered in WHERE turns into an inner join: conditions on the right table go in ON (section 2).
    • 

  • NOT IN over a column that can be NULL returns no rows: use NOT EXISTS (section 2).
    • 

  • Aggregating across two joined child tables multiplies counts and sums: aggregate each child, then join (section 2).
    • 

  • LIMIT without ORDER BY, or ROW_NUMBER without a tie-breaker: rows can change between runs; order by something unique (sections 1 and 4).
    • 

  • Window frames left to the default: LAST_VALUE returns the current row, RANGE includes ties; write the frame you mean (section 4).
    • 

  • Read, then insert or update, in application code races: one atomic INSERT ... ON CONFLICT (section 6).
    • 

  • Plain timestamp for instants, fixed offsets for zones: ambiguous times and wrong day boundaries twice a year; timestamptz and IANA names (section 10).
    • 

  • A natural key (email) as the primary key; integer instead of bigint: keys that change or run out; surrogate bigint or UUID v7 plus UNIQUE on the natural key (section 7).
    • 

  • Copying facts without an owner: copies drift; a sync mechanism and a reconciliation query for each (section 9).
    • 

  • Rules only in application code; unindexed foreign keys: rules in the schema; index the referencing column of every foreign key you join on or delete through (sections 2 and 10).
    • 

  • Soft deletes everywhere by default: leaks deleted data, breaks unique constraints and foreign keys, erases nothing; only where users undo, with a partial unique index and a purge job (section 8).
    • 

  • A migration without lock_timeout; an index built without CONCURRENTLY: a queued ACCESS EXCLUSIVE lock blocks every query behind it, a plain CREATE INDEX blocks writes (section 11).
    • 

  • Renaming or dropping a column in one step breaks the old code still running during the deploy: expand and contract (section 11).
    • 

  • Lazy loading in a loop: N+1 queries, hundreds of milliseconds at 200 rows over 1 ms of network; selectinload, raiseload in tests, or one SQL query (section 12).
    • 

  • Building SQL with string formatting: injection, and broken queries for names with apostrophes; bound parameters, allow-lists for identifiers (section 12).
    • 

  • Testing on SQLite, running on Postgres: the dialects differ in ways that matter; test against the production engine (section 1).
    •
