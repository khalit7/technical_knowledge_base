12. ORMs against raw SQL, and the N+1 query problem

The problem. Application code works with objects (a Chat with a list of Messages); the database works with rows. Writing the SQL and the conversion by hand for every screen is repetitive and easy to get subtly wrong.

The idea. An ORM (object-relational mapper) maps tables to classes and rows to objects, writes the SQL for you, and tracks changes to objects so it can save them. In Python the standard is {{SQLAlchemy|https://docs.sqlalchemy.org/en/21/}} (2.1.3, released 2026-10-03 per {{PyPI|https://pypi.org/project/SQLAlchemy/}}); its 2.x style declares typed models and builds queries with select(). These are the models the measurement below used, mapped onto the existing chat tables:

class Chat(Base):
    __tablename__ = "chats"
    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    title: Mapped[str | None]
    created_at: Mapped[datetime.datetime]
    messages: Mapped[list["Message"]] = relationship(order_by="Message.id")

chats = session.scalars(select(Chat).order_by(Chat.created_at.desc()).limit(50)).all()
for c in chats:
    print(c.id, len(c.messages))      # each c.messages here is a new query

What an ORM gives you: less boilerplate for create, read, update and delete; queries composed from Python pieces; parameters bound safely by default (section 13); an identity map (one object per row per session) and a unit of work (changes flushed in a valid order); and models that Alembic can diff. What it costs: the SQL and, above all, the number of round trips to the database are hidden. A round trip is one request and its reply over the network; inside one data centre it is a fraction of a millisecond to a millisecond or two, and it is paid per query, however small the query.

The N+1 query problem. The loop above runs 1 query for the chats and then, because relationships load lazily by default (only when first touched), 1 more query per chat: N+1 in total. The {{SQLAlchemy documentation|https://docs.sqlalchemy.org/en/21/orm/queryguide/relationships.html}} names it as "one of the most common issues referred to in object relational mapping". It is invisible in development, where the database is on the same machine and there are ten rows, and it grows linearly with the page size and the network distance. Measured for this page:

Four ways to load N chats with their messages measured

PostgreSQL 16.2, SQLAlchemy 2.1.3, psycopg 3.3.6, the chat data with an index on messages.chat_id. Each bar is the median of 30 runs of "load the N most recent chats, with each one's message count and last message"; every SQL statement sent was counted. "Through 1 ms of network" sends the same traffic through a small proxy that adds 0.5 ms each way, about the round trip between two machines in one region. All four return identical results.

The fixes, in SQLAlchemy

  • selectinload(Chat.messages): a second query WHERE chat_id IN (...) loads all the children at once; 2 queries whatever N. The documentation calls it {{"the most simple and efficient way to eagerly load collections"|https://docs.sqlalchemy.org/en/21/orm/queryguide/relationships.html}}.
  • joinedload(Chat.messages): one query with a LEFT JOIN; each chat's columns repeat once per message, so it suits many-to-one (a message's chat) better than one-to-many.
  • raiseload("*") in tests or on hot paths turns any accidental lazy load into an error, so N+1 cannot creep back.
  • Or write the query: one SQL statement that aggregates in the database returns only what the screen needs.

What professionals do

  • ORM for ordinary reads and writes; hand-written SQL (SQLAlchemy Core, text(), or sqlc) for reports and anything performance-critical.
  • Look at the SQL: create_engine(..., echo=True) in development, and per-request query counts in tracing ({{Observability|n:3ef5c17b0d0d811e8490c54dd42c2b9b}}).
  • Assert query counts in tests for important endpoints.
  • Paginate by key, not by OFFSET ({{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}} measures why).

13. SQL injection and parameterised queries

The problem. If a program builds SQL by pasting user input into the query text, the input can change the query's meaning. That is SQL injection, still near the top of the {{OWASP|https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html}} list of web risks. The fix: parameterised queries. Write the query with placeholders (? in SQLite, %s in psycopg, :name in SQLAlchemy's text()) and pass the values separately. The value is then data, never SQL, whatever it contains; an apostrophe in a real name stops being a bug too. Psycopg 3 goes further and {{"sends the query and the parameters to the server separately"|https://www.psycopg.org/psycopg3/docs/basic/from_pg2.html}}; its documentation's rule is {{"Never use % or + to merge values into queries"|https://www.psycopg.org/psycopg3/docs/basic/params.html}}.


# wrong: the input becomes part of the SQL
cur.execute(f"SELECT id FROM users WHERE email = '{email}'")
# right: the input is a value
cur.execute("SELECT id FROM users WHERE email = %s", (email,))
# SQLAlchemy
session.execute(text("SELECT id FROM users WHERE email = :e"), {"e": email})

14. Common mistakes, and the habits that prevent them




A LEFT JOIN filtered in WHERE
Turns into an inner join and drops the rows you kept on purpose. Put conditions on the right table in ON (section 2).


NOT IN over a column that can be NULL
Returns no rows at all. Use NOT EXISTS (section 2).


Aggregating across two joined child tables
Fan-out multiplies counts and sums. Aggregate each child on its own, then join (section 2).


LIMIT without ORDER BY, or ROW_NUMBER without a tie-breaker
The rows you get can change between runs. Order by something unique (section 1, section 4).


Window frames left to the default
LAST_VALUE returns the current row; RANGE includes ties. Write the frame you mean (section 4).


Read, then insert or update, in application code
Races under concurrency. Use one atomic INSERT ... ON CONFLICT (section 6).


Plain timestamp for instants, fixed offsets for zones
Ambiguous times and wrong day boundaries twice a year. timestamptz, IANA zone names, convert at the edges (section 7).


A natural key (email) as the primary key; integer instead of bigint
Keys that change or run out. Surrogate bigint or UUID v7 plus UNIQUE on the natural key (section 8).


Copying facts without an owner
Denormalised copies drift. Every copy needs a sync mechanism and a reconciliation query (section 9).


Rules only in application code; unindexed foreign keys
Put rules in the schema; index the referencing column of every foreign key you join on or delete through (sections 2 and 10).


Soft deletes everywhere by default
Leaks deleted data, breaks unique constraints and foreign keys, and does not erase anything. Use them only where users undo, with a partial unique index and a purge job (section 10).


A migration without lock_timeout; an index built without CONCURRENTLY
A queued ACCESS EXCLUSIVE lock blocks every query behind it; a plain CREATE INDEX blocks writes. Bound the wait and use the non-blocking forms (section 11 and the ALTER TABLE tab).


Renaming or dropping a column in one step
Breaks the old code still running during the deploy. Expand and contract (section 11).


Lazy loading in a loop
N+1 queries; at 200 rows over 1 ms of network, measured at hundreds of milliseconds. selectinload, raiseload in tests, or one SQL query (section 12).


Building SQL with string formatting
Injection, and broken queries for names with apostrophes. Bound parameters; allow-lists for identifiers (section 13).


Testing on SQLite, running on Postgres
The dialects differ in ways that matter (aliases in WHERE, loose GROUP BY, foreign keys off by default, typing). Test against the production engine; run Postgres in a container or with pgserver in CI.




The habits, in one list
Write the expected result before the query, then check the rows, not just that it ran. Name things consistently. Every rule you can in the schema. Every schema change through a reviewed, linted, timed migration with a lock timeout. Look at the SQL your ORM sends and count it. Bind every value. Test on the engine you run. Then, when it is correct, make it fast: {{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}} and {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}} are the next pages.
