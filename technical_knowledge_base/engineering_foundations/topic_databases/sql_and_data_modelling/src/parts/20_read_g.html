10. Constraints and types: correctness the database enforces

A rule written only in application code ("a chat always has an owner", "a balance is never negative") holds only while every code path, script, migration and teammate remembers it. The schema is the one place every write must pass through, so write every rule you can as a constraint; each also tells the next reader something true about the data, which a comment cannot guarantee.

Each constraint refuses one kind of bad row at the moment it is written

Bad writes against the chat schema and the constraint that refuses each; the error names are Postgres's. Without them, every one of these rows would be accepted and found months later, after reports were built on it.

  • NOT NULL on everything that must exist; nullable should be a decision, not a default.
  • CHECK for value rules: CHECK (balance >= 0), CHECK (role IN ('user', 'assistant')).
  • UNIQUE for natural keys, and partial unique indexes for rules over a subset of rows: "at most one pinned chat per user", "one live account per email" (soft deletes, section 8).
  • FOREIGN KEY with a deliberate ON DELETE: CASCADE (deleting the parent deletes the children: right for a folder's links), RESTRICT (refuse while children exist: right for anything with history, such as messages), SET NULL. SQLite enforces foreign keys only after PRAGMA foreign_keys = ON ({{SQLite docs|https://www.sqlite.org/foreignkeys.html}}); Postgres always does.
  • Exclusion constraints (Postgres) for "no two rows overlap": no two active subscriptions of one user with overlapping date ranges ({{documentation|https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-EXCLUSION}}). PostgreSQL 18 added WITHOUT OVERLAPS primary keys and unique constraints for the same idea ({{release notes|https://www.postgresql.org/docs/18/release-18.html}}).

What constraints cost: a check on every write (small; a foreign key check is an index lookup on the parent), and adding one to a big live table needs care (section 11). Their absence costs far more.

Types are constraints too: time

A user in Tokyo asks for "today's messages"; the server runs in UTC; daylight saving moves clocks in some zones twice a year. Postgres has timestamp (a date and wall-clock time with no zone) and timestamptz (an absolute instant). Despite its name, timestamptz stores no zone: the input is converted to UTC and stored as UTC, and on output it is shown in the session's TimeZone setting ({{documentation|https://www.postgresql.org/docs/current/datatype-datetime.html}}). So the same instant prints differently in different sessions, while a plain timestamp prints the same digits everywhere and means nothing on its own. Interval arithmetic respects the calendar: across the night New York moves its clocks forward, adding 1 day keeps the wall-clock time while adding 24 hours lands an hour later.

The rule for time
Store instants as timestamptz (the Postgres wiki's {{Don't Do This|https://wiki.postgresql.org/wiki/Don't_Do_This#Don.27t_use_timestamp_.28without_time_zone.29}} page says not to use plain timestamp for them); keep sessions in UTC; convert to the user's zone (an IANA name such as Asia/Tokyo, never a fixed offset like +09:00, which ignores daylight saving) only when bucketing by day or displaying; store a user's zone as a column if reports need their days. date for calendar dates with no time (a birthday). SQLite has no date type: store ISO 8601 text in UTC or integer Unix seconds, consistently.

Fixed sets of values: enums, CHECK lists and lookup tables (depth)

A column with a fixed set of values (a plan, a role, a status) can be declared three ways. A Postgres enum type is compact (4 bytes) and sorts in declared order, and a value can be added, but {{"existing values cannot be removed from an enum type, nor can the sort ordering of such values be changed"|https://www.postgresql.org/docs/current/datatype-enum.html}} short of recreating the type. A text column with a CHECK (what the chat schema uses for role) is portable and easy to change. A lookup table with a foreign key is the most flexible: adding a value is an INSERT, and the value can carry data (a price, a label, a sort order, an "active" flag). Rule of thumb: CHECK for small sets owned by the code (role); a lookup table when the values carry data or are managed by people (plans, countries); an enum only for sets that will genuinely never shrink.

Naming conventions (depth)

Names are read far more often than written, by people and by tools. The conventions most Postgres teams converge on:

  • lower_snake_case for everything. Postgres folds unquoted names to lower case, so a table created as "ChatTags" must be quoted forever (the wiki: {{don't use upper case names|https://wiki.postgresql.org/wiki/Don't_Do_This#Don.27t_use_upper_case_table_or_column_names}}).
  • Tables plural (users, messages) or singular, but one choice for the whole schema. The primary key id; foreign keys <singular>_id (user_id); timestamps <verb>_at (created_at, deleted_at) as timestamptz; booleans as is_ or has_ predicates.
  • No reserved words (user, order, group need quoting); no abbreviations only the author knows.
  • Name constraints and indexes explicitly (chats_user_id_fkey, messages_chat_id_idx): migration tools and error messages refer to them by name, and Alembic {{cannot detect changes to anonymous constraints|https://alembic.sqlalchemy.org/en/latest/autogenerate.html}}.
