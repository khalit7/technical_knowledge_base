10. Schema rules: constraints, soft deletes, tenants, enums, names

Constraints are documentation that the database enforces

The problem. A rule written only in application code ("a chat always has an owner", "a balance is never negative") holds only as long as every code path, script, migration and teammate remembers it. The schema is the one place every write must pass through.

So the professional habit is to write every rule you can as a constraint. Each one also tells the next reader something true about the data, which a comment cannot guarantee:

  • NOT NULL on everything that must exist. Nullable should be a decision, not a default.
  • CHECK for value rules: CHECK (balance >= 0), CHECK (role IN ('user', 'assistant')).
  • UNIQUE for natural keys, and partial unique indexes for rules that apply to a subset of rows: "at most one pinned chat per user", "one live account per email" (soft deletes, below).
  • FOREIGN KEY with a deliberate ON DELETE: CASCADE (deleting the parent deletes the children: right for a folder's links), RESTRICT (refuse while children exist: right for anything with history, such as messages), SET NULL. SQLite enforces foreign keys only after PRAGMA foreign_keys = ON ({{SQLite docs|https://www.sqlite.org/foreignkeys.html}}); Postgres always does.
  • Exclusion constraints (Postgres) for "no two rows overlap": no two active subscriptions of one user with overlapping date ranges ({{documentation|https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-EXCLUSION}}). PostgreSQL 18 added WITHOUT OVERLAPS primary keys and unique constraints for the same idea ({{release notes|https://www.postgresql.org/docs/18/release-18.html}}).

What constraints cost: a check on every write (small; a foreign key check is an index lookup on the parent), and adding one to a big live table needs care (section 11). Their absence costs far more: bad rows found months later, after reports were built on them.

Soft deletes and their cost

The idea. Instead of DELETE, set deleted_at = now() and hide those rows, so a deletion can be undone and audited. What it costs, as Brandur Leach catalogued in {{"Soft deletion probably isn't worth it" (2022)|https://brandur.org/soft-deletion}}:

  • Every query, report and join must remember WHERE deleted_at IS NULL; one that forgets shows deleted data.
  • Foreign keys stop meaning much: a live chat can point at a "deleted" user, and ON DELETE CASCADE never fires.
  • UNIQUE constraints break: a user who deletes their account and signs up again collides with their own deleted row, unless the unique index is partial (below).
  • The data is not deleted. Privacy law's right to erasure (GDPR Article 17) requires real deletion of personal data, so you still need a purge job.

Alternatives: delete for real and copy the row into an archive or audit table first (a trigger, or the application in the same transaction); or keep history as an append-only event table. Use soft deletes where users genuinely undo (a trash folder), with a view or row-level security policy that hides deleted rows by default and a scheduled hard delete after the retention period.

Multi-tenancy: many customers in one database

The problem. A business product serves many customer organisations (tenants). Tenant A must never see tenant B's rows, and one bug in one query is enough to leak.

PatternHowGood forCosts
Shared tables, tenant_id column ("pool")Every tenant-owned table has tenant_id; every index and key starts with itMany small tenants; the default for most SaaS productsEvery query must filter by tenant; a noisy tenant affects others
Schema per tenantSame tables in one Postgres schema per tenantTens to hundreds of tenants needing separationEvery migration runs N times; thousands of schemas strain the catalog and tooling
Database per tenant ("silo")A separate database or server eachFew large tenants, regulated data, data residencyCost and operations multiply; cross-tenant reports need a pipeline

For the shared-table pattern, Postgres row-level security (RLS) moves the tenant filter into the database: a policy attached to the table adds its condition to every query and checks every write, using a setting the application sets per request. Two details decide whether it protects you: superusers and roles with BYPASSRLS always bypass it, and the table's owner bypasses it unless you run ALTER TABLE ... FORCE ROW LEVEL SECURITY ({{documentation|https://www.postgresql.org/docs/current/ddl-rowsecurity.html}}). So the application must connect as a role that does not own the tables:

Also include tenant_id in foreign keys (FOREIGN KEY (tenant_id, chat_id) REFERENCES chats (tenant_id, id)) so a row cannot point across tenants, and lead indexes with it. With a connection pool, set the tenant with SET LOCAL inside each transaction so it cannot leak into the next request on the same connection (pooling is on {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}}).

Enums, CHECK lists and lookup tables

A column with a fixed set of values (a plan, a role, a status) can be declared three ways. A Postgres enum type is compact (4 bytes) and sorts in declared order, and a value can be added, but {{"existing values cannot be removed from an enum type, nor can the sort ordering of such values be changed"|https://www.postgresql.org/docs/current/datatype-enum.html}} short of recreating the type. A text column with a CHECK (what the chat schema uses for role) is portable and easy to change. A lookup table with a foreign key is the most flexible: adding a value is an INSERT, and the value can carry data (a price, a label, a sort order, an "active" flag).

Rule of thumb: CHECK for small sets owned by the code (role); a lookup table when the values carry data or are managed by people (plans, countries); an enum only for sets that will genuinely never shrink.

Naming conventions

Names are read far more often than written, by people and by tools. The conventions most Postgres teams converge on:

  • lower_snake_case for everything. Postgres folds unquoted names to lower case, so a table created as "ChatTags" must be quoted forever (the wiki: {{don't use upper case names|https://wiki.postgresql.org/wiki/Don't_Do_This#Don.27t_use_upper_case_table_or_column_names}}).
  • Tables plural (users, messages) or singular, but one choice for the whole schema. The primary key id; foreign keys <singular>_id (user_id); timestamps <verb>_at (created_at, deleted_at) as timestamptz; booleans as is_ or has_ predicates.
  • No reserved words (user, order, group need quoting); no abbreviations only the author knows.
  • Name constraints and indexes explicitly (chats_user_id_fkey, messages_chat_id_idx): migration tools and error messages refer to them by name, and Alembic {{cannot detect changes to anonymous constraints|https://alembic.sqlalchemy.org/en/latest/autogenerate.html}}.
