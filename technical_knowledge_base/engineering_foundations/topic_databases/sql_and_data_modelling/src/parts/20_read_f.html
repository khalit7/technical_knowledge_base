8. Data modelling: entities, relationships and keys

The problem. Before any SQL, someone decides which tables exist. Get it wrong and every later query fights the shape: facts duplicated, relationships that cannot be expressed, keys that change.

Entities and attributes. Start from the nouns the product must remember, each with its own identity and lifecycle: a user, a chat, a message. Each becomes a table (an entity); its facts become columns (attributes). Then the verbs between them become relationships, and the kind of relationship decides where the key goes:

One to many

A user has many chats; a chat has one user. The foreign key goes on the "many" side: chats.user_id. This is most relationships.

Many to many

If chats could be shared, a chat would have many members and a user many shared chats. Neither table can hold the other's key, so a third join table holds pairs: chat_members(chat_id, user_id, role) with the pair as its primary key. The pair is the natural place for facts about the membership itself (the role, when it started).

One to one

A user has one credits balance: credits.user_id is both the primary key and a foreign key to users. Split one-to-one only for a reason: a different write rate (a balance changes on every message; a profile rarely), optional data, or tighter access control.

Which column is the key

A natural key is a real-world value that already identifies the row, such as an email address. A surrogate key is an id the database invents, with no meaning. Natural keys look attractive and age badly: people change emails, case and whitespace make two spellings of one address, a key copied into every foreign key must change everywhere when it changes. The production default: a surrogate primary key, plus a UNIQUE constraint on the natural key so duplicates are still refused. Join tables are the exception: their natural key, the pair, is the right primary key.

Which surrogate? Three serious options in 2026:

  • bigint identity (bigint GENERATED ALWAYS AS IDENTITY, the SQL-standard spelling Postgres has supported since version 10; the older serial is on the wiki's {{Don't Do This|https://wiki.postgresql.org/wiki/Don't_Do_This#Don.27t_use_serial}} list). 8 bytes, sequential, compact. Use bigint rather than integer: a 4-byte integer runs out at 2,147,483,647, and changing a key's type later rewrites the table and every index (see the {{ALTER TABLE, measured|#t-alter}} tab).
  • UUID version 4: 16 random bytes (122 of them random). Any machine can generate one without asking the database, so clients can create ids offline, ids from separate databases never collide, and nobody can guess the next one. The cost: each new key lands at a random place in the index.
  • UUID version 7: standardised in {{RFC 9562 (May 2024)|https://www.rfc-editor.org/rfc/rfc9562.html#name-uuid-version-7}}, it puts the Unix time in milliseconds in the first 48 bits and random bits after. Generated anywhere like v4, but new keys sort after old ones like bigint. It reveals when a row was created, which matters for some public ids. PostgreSQL 18 (released {{2025-09-25|https://www.postgresql.org/docs/18/release-18.html}}) has a built-in uuidv7(); on 16 and 17 generate it in the application or with a small function (the measurement below used one).

Why the order of keys matters: the same inserts into an index, twice

An index stores keys sorted in fixed-size pages (8 KB in Postgres; here each page holds 6 keys so it fits on screen). The same 36 inserts arrive in time order. With sequential keys (bigint, UUID v7) each new key belongs at the end, so only the last page is touched and full pages are left full. With random keys (UUID v4) each key belongs somewhere in the middle: pages split in half when full, and almost every page is touched. Illustrative page size; the measured effect on a real server follows.

Measured: 1 million and 10 million inserts by key type measured

PostgreSQL 16.2 on a laptop, default settings (128 MB of shared buffers). For each key type, the keys were generated first into a temporary table (generation timed apart) and then inserted in generation order with one INSERT ... SELECT; the table has the key plus two integers. Choose the measure; the 1M figures are medians of 3 runs, the 10M figures single runs.

Reading the measurement. Two effects are mixed in it. A UUID is twice as wide as a bigint, so its index is bigger whatever the order. Random order adds a second cost: half-empty pages after splits (a bigger index for the same keys) and writes scattered over the whole index, which stops fitting in memory as the table grows and makes the write-ahead log (WAL: the record of every change, written before the data, which replicas and backups also consume) larger, because after each checkpoint the first change to a page writes the whole 8 KB page to the WAL ({{full_page_writes|https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-FULL-PAGE-WRITES}}), and random inserts touch many more pages. Version 7 removes the second cost and keeps the first. What professionals do: bigint identity for internal keys is the simple default; UUID v7 when ids must be generated outside the database or merged across databases; UUID v4 only when unguessable, time-free ids matter more than write cost. If a public id must not reveal volume or creation time, keep a bigint primary key and add a separate random public id with a UNIQUE index.

9. Normalisation: one fact in one place

The problem. The tempting first design is one wide table: every message row also carries its chat's title and its user's name, email and plan, so any screen is one query with no joins. It works until a fact changes. The root page gives the one-line rule; this section makes it precise and shows what each step prevents.

The vocabulary. Column B depends on column A (a functional dependency, written A → B) if knowing A fixes B: user_id → email. A candidate key is a minimal set of columns that fixes all the others. An anomaly is a change the design makes easy to get wrong:

  • Update anomaly: one fact is stored in many rows, so changing it means changing all of them, and missing one leaves two versions.
  • Insert anomaly: a fact cannot be stored without some unrelated fact (in the wide table, a user who has not sent a message has no row).
  • Delete anomaly: removing one fact removes another (delete a user's last message and their email is gone).

The normal forms, by the anomaly each one removes

Codd defined the first normal form with the relational model in {{1970|https://doi.org/10.1145/362384.362685}}, the second and third in 1971, and Boyce and Codd the stricter BCNF in 1974 (history summarised on {{Wikipedia|https://en.wikipedia.org/wiki/Third_normal_form}}). William Kent's {{four-page guide (CACM, 1983)|https://doi.org/10.1145/358024.358054}} is still the best short explanation. Each form adds one rule:

2NFIn a table with a multi-column key, no column depends on only part of the key.chat_members(chat_id, user_id, role, user_email): the email depends on user_id alone.Update: an email change must touch every membership row.Keep email in users.
3NFNo column depends on another non-key column.users(id, country, country_name): the name depends on the country code; or messages(id, chat_id, chat_title).Update: renaming a country or a chat touches many rows; insert: no country without a user.A countries table; keep the title in chats.
BCNFEvery column set that determines another column is a candidate key.Reviews (chat_id, language, reviewer), each chat has one reviewer per language, each reviewer handles one language. Beyond BCNF, the fourth and fifth normal forms deal with independent multi-valued facts in one table (a user's languages and a user's devices stored as all combinations); Kent's guide covers them. In practice, a schema designed from entities and relationships as in section 8 is usually in BCNF already, and the forms are most useful as a checklist when reviewing a table that "has everything in it".

When to denormalise, and how to keep the copy right

Denormalisation is storing a derived or copied fact on purpose to make reads cheaper. It is right when a hot read path would otherwise do expensive work on every request, and you accept owning the copy. Every copy needs three things: an owner, a mechanism that keeps it in step, and a check that it still is.

  • Counters and totals on the parent (chats.message_count): kept by a trigger (code the database runs on every insert, as below) or by the application in the same transaction as the write.
  • Materialised views (Postgres CREATE MATERIALIZED VIEW): a stored query result, refreshed on a schedule; stale between refreshes.
  • Read models and search indexes built from the change stream; the outbox and change data capture patterns are on {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}. Caches are the {{Caching|n:3cd5c17b0d0d817ebd6ccadd4750c23a}} page.
  • Analytics: wide denormalised tables in a columnar store, rebuilt from the normalised source (root section 5; {{Analytics: columnar engines, DuckDB and the lakehouse|n:3ef5c17b0d0d8157814ec5dd8a0d4fb5}}).
A copy that is not denormalisation
A snapshot of a historical fact is a different fact, not a copy: the price a customer paid (not today's price), the model that produced a message (not the chat's current model), the billing address on an invoice. Storing it on the row is correct normalised design, and looking it up "live" would be the bug.
Check that a copy is still right
A reconciliation query compares the copy with the source and should return nothing: SELECT id FROM chats c WHERE message_count <> (SELECT COUNT(*) FROM messages m WHERE m.chat_id = c.id). Run it on a schedule and alert on any row. The Exercises lab has one ("Find the impossible rows").
