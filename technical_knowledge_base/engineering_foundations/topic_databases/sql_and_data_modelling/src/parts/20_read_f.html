8. Modelling common shapes

Most schemas are built from a handful of shapes. Each has a standard layout whose keys and constraints carry the rules; pick a shape to see its tables.

Where the keys go decides what the database can enforce

  • Many to many: a join table whose primary key is the pair; facts about the relationship live on it (section 7).
  • Trees: an adjacency list (parent_id, as the chat data does) is cheap to write and to move a subtree, and is walked with a recursive CTE (section 5). Trees read far more than written are often stored as a materialised path ('1/7/12': a subtree is a prefix match, a move rewrites the subtree) or a closure table (one row per ancestor and descendant pair: a subtree is one join, an insert writes one row per ancestor).
  • Time series (usage per minute, model latency, token counts): append-only rows keyed by (series_id, ts), usually range-partitioned on time with Postgres {{declarative partitioning|https://www.postgresql.org/docs/current/ddl-partitioning.html}}, so old data leaves by dropping or detaching a whole partition, which the documentation calls far faster than a bulk DELETE. Columnar engines for large-scale analytics are {{Analytics: columnar engines, DuckDB and the lakehouse|n:3ef5c17b0d0d8157814ec5dd8a0d4fb5}}; time-ordered indexes such as BRIN are {{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}}.
  • Soft deletes and JSON columns have costs that are easy to miss; they follow.

Soft deletes and their cost

Instead of DELETE, set deleted_at = now() and hide those rows, so a deletion can be undone and audited. The costs, as Brandur Leach catalogued in {{"Soft deletion probably isn't worth it" (2022)|https://brandur.org/soft-deletion}}: every query, report and join must remember WHERE deleted_at IS NULL (one that forgets shows deleted data); foreign keys stop meaning much (a live chat can point at a "deleted" user, and ON DELETE CASCADE never fires); UNIQUE constraints break (a user who deletes their account and signs up again collides with their own deleted row) unless the unique index is partial; and nothing is deleted, while privacy law's right to erasure (GDPR Article 17) requires real deletion of personal data, so you still need a purge job.

Use soft deletes only where users genuinely undo (a trash folder), with a view or row-level security policy that hides deleted rows by default and a scheduled hard delete after the retention period; elsewhere delete for real and copy the row into an archive or audit table first (a trigger, or the application in the same transaction), or keep history as an append-only event table.

JSON columns: jsonb

Some data varies in shape row by row and is rarely queried field by field: an LLM's tool calls and their arguments, a provider's raw response, preferences, a webhook payload. A column per possible field would be mostly empty; a table per shape, dozens of tables. Postgres has json (the text exactly) and jsonb (a parsed binary form, read and indexed without re-parsing; the documentation: {{"most applications should prefer to store JSON data as jsonb"|https://www.postgresql.org/docs/current/datatype-json.html}}). -> returns a JSON value, ->> text, @> tests containment, and a GIN index (a generalised inverted index: for each key and value, the rows containing it) makes containment fast. SQLite stores JSON as text, with json_extract and, since {{3.38.0|https://www.sqlite.org/json1.html}}, the same -> and ->>.

The Postgres version's last statement shows the planner using the GIN index (sequential scans switched off for the demonstration; at 2,000 rows a scan would be cheaper and the planner would choose it).

Use jsonb when

  • the shape genuinely varies, or belongs to someone else (an API response kept for audit);
  • you read the document whole and filter on a few fields at most;
  • it is an attachment to a row that has real columns for everything you join, group or constrain on.

Use columns when

  • you join on it, group by it, or need a foreign key or a CHECK on it;
  • every row has the field (a "flexible" document where every row has the same keys is a table in disguise, without types or constraints);
  • you update single fields often (jsonb is rewritten whole on update).

The root's Database atlas compares this with a document database: Postgres jsonb covers most document needs while keeping joins and constraints ({{Topic: databases|n:3cd5c17b0d0d815d8841ec845f5f3324}}, section 6).

Many customers in one database

A business product serves many customer organisations (tenants), and one bug in one query is enough to leak one tenant's rows to another. The default for most SaaS products is shared tables with a tenant_id column leading every key, index and foreign key (the "many tenants" shape above). Postgres row-level security (RLS) moves the tenant filter into the database: a policy adds its condition to every query and checks every write, using a setting the application sets per request. But superusers and BYPASSRLS roles always bypass it, and the table's owner bypasses it unless you run ALTER TABLE ... FORCE ROW LEVEL SECURITY ({{documentation|https://www.postgresql.org/docs/current/ddl-rowsecurity.html}}), so the application must connect as a role that does not own the tables.

RLS runnable, connection pools, and the three tenancy patterns compared (depth)

The composite foreign key (FOREIGN KEY (tenant_id, chat_id) REFERENCES chats (tenant_id, id)) is what stops a row pointing across tenants. With a connection pool, set the tenant with SET LOCAL inside each transaction so it cannot leak into the next request on the same connection (pooling is {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}}).

9. Normalisation: one fact in one place

The tempting first design is one wide table: every message row also carries its chat's title and its user's name, email and plan, so any screen is one query with no joins. It works until a fact changes. Column B depends on column A (a functional dependency, A → B) if knowing A fixes B: user_id → email. A candidate key is a minimal set of columns that fixes all the others. Storing a dependent fact beside something other than its key causes anomalies: an update anomaly (one fact in many rows; miss one and there are two versions), an insert anomaly (a fact cannot be stored without an unrelated one: a user who has sent no message has no row) and a delete anomaly (removing one fact removes another: delete a user's last message and their email is gone). The normal forms, by the anomaly each removes

Each form adds one rule (William Kent's {{four-page guide, CACM 1983|https://doi.org/10.1145/358024.358054}} is still the best short explanation). A schema designed from entities and relationships (section 7) is usually in BCNF already; the forms are most useful as a checklist when reviewing a table that "has everything in it".

History, and beyond BCNF (depth)

Codd defined the first normal form with the relational model in {{1970|https://doi.org/10.1145/362384.362685}}, the second and third in 1971, and Boyce and Codd the stricter BCNF in 1974 (history summarised on {{Wikipedia|https://en.wikipedia.org/wiki/Third_normal_form}}). Beyond BCNF, the fourth and fifth normal forms deal with independent multi-valued facts in one table (a user's languages and devices stored as all combinations); Kent's guide covers them.

When to denormalise, and how to keep the copy right

Denormalisation is storing a derived or copied fact on purpose to make reads cheaper. It is right when a hot read path would otherwise do expensive work on every request and you accept owning the copy, and every copy needs three things: an owner, a mechanism that keeps it in step, and a check that it still is.

  • Counters and totals on the parent (chats.message_count), kept by a trigger (code the database runs on every insert, below) or by the application in the same transaction as the write.
  • Materialised views (CREATE MATERIALIZED VIEW): a stored query result, refreshed on a schedule; stale between refreshes.
  • Read models and search indexes built from the change stream (the outbox and change data capture patterns are on {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}); caches are {{Caching|n:3cd5c17b0d0d817ebd6ccadd4750c23a}}.
  • Analytics: wide denormalised tables in a columnar store, rebuilt from the normalised source (root section 5; {{Analytics: columnar engines, DuckDB and the lakehouse|n:3ef5c17b0d0d8157814ec5dd8a0d4fb5}}).

The check is a reconciliation query that compares the copy with the source and should return nothing, run on a schedule with an alert on any row: SELECT id FROM chats c WHERE message_count <> (SELECT COUNT(*) FROM messages m WHERE m.chat_id = c.id) (the Exercises lab has one, "Find the impossible rows").

A copy that is not denormalisation
A snapshot of a historical fact is a different fact, not a copy: the price a customer paid (not today's price), the model that produced a message (not the chat's current model), the billing address on an invoice. Storing it on the row is correct normalised design; looking it up "live" would be the bug.
