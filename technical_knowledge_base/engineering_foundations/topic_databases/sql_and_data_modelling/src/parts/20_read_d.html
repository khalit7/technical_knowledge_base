6. Writes: upserts, idempotency, MERGE, set operations

Upsert: insert, or update if the key exists. Count each user's tokens per day. Code that reads the row, then inserts it if missing or updates it if present, races (a race condition: two operations interleaving so that the result depends on timing): two requests at once both read "missing" and both insert, so one fails on the primary key or, without a key, you get two rows. Let the database do both in one atomic statement: INSERT ... ON CONFLICT (key) DO UPDATE SET ..., where excluded names the row you tried to insert. It needs a UNIQUE constraint or primary key to detect the conflict. Postgres has had it since 9.5; SQLite copied the syntax in {{3.24.0, 2018-06-04|https://www.sqlite.org/lang_upsert.html}}; MySQL spells it INSERT ... ON DUPLICATE KEY UPDATE. (Races in general, and isolation levels, are {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}}.)

Two requests at once: read-then-write loses one, one ON CONFLICT statement counts both

Idempotency. ON CONFLICT DO NOTHING plus RETURNING (which returns the inserted rows) makes a handler idempotent: safe to run twice with the same input, as a retried request or a webhook delivered twice will be. {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}} builds idempotency keys on exactly this.

MERGE (SQL standard; Postgres since {{version 15|https://www.postgresql.org/docs/15/release-15.html}}) states several cases in one statement: update when matched, insert when not, optionally delete; it reads well for syncing a table from a batch. But unlike ON CONFLICT, a Postgres MERGE with both INSERT and UPDATE branches {{"does not guarantee that either INSERT or UPDATE will occur"|https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED}} when another transaction is changing the same rows, so two concurrent MERGEs inserting the same new key can fail with a unique violation; the {{MERGE page|https://www.postgresql.org/docs/current/sql-merge.html}} points to INSERT ... ON CONFLICT for that case. MERGE for batch syncs, ON CONFLICT for concurrent single-row upserts.

MERGE, runnable; set operations (UNION, UNION ALL, INTERSECT, EXCEPT) (examples)

Set operations combine two queries with the same columns. UNION stacks them and removes duplicates; UNION ALL keeps everything and is cheaper (no de-duplication step), so use it unless duplicates are genuinely wrong. INTERSECT keeps rows in both; EXCEPT rows in the first but not the second. All compare whole rows and, unlike =, treat two NULLs as equal. Postgres requires an alias on a subquery in FROM; SQLite does not.
