3. Aggregation: GROUP BY, HAVING, FILTER, ROLLUP

The problem. Reports ask for one number per thing: messages per model, tokens per user per month. GROUP BY collapses all rows sharing the grouping values into one row, and aggregate functions (COUNT, SUM, AVG, MIN, MAX) summarise each group. Every column in the SELECT list must then be either grouped or aggregated; SQLite's leniency here (it picks an arbitrary row) is a lesson in the root's playground.

Several counts in one pass. A question like "per model: messages, replies, reply tokens, distinct users" needs conditional aggregation. The standard spelling is the FILTER (WHERE ...) clause, supported by Postgres and SQLite (see {{modern-sql.com's support table|https://modern-sql.com/feature/filter}}); in databases without it, write SUM(CASE WHEN ... THEN 1 ELSE 0 END). One scan replaces four queries:

Subtotals. GROUP BY ROLLUP (plan, model) returns the per-plan-and-model rows, a subtotal row per plan (model shown as NULL) and a grand total (both NULL). CUBE and GROUPING SETS generalise it. SQLite has none of them, which is why this box is Postgres only:

Common aggregation mistakes
  • AVG of an integer column in Postgres is a numeric with many digits, in SQLite a float: round explicitly when you compare.
  • COUNT(column) skips NULLs; COUNT(*) counts rows. After a LEFT JOIN, count the right table's key, not *, or every empty group counts as 1.
  • Averages of averages are wrong when groups differ in size: average the raw rows, or weight by count.
  • SUM over zero rows is NULL, not 0: wrap it in COALESCE(SUM(x), 0) when a zero is meant.

4. Window functions: calculations across rows without collapsing them

The problem. GROUP BY gives one row per group, but many questions need every row and something about its neighbours: rank each user by tokens, the time since the previous message, a running total, the latest message per chat. Before window functions these needed self joins or correlated subqueries that were slow and hard to read.

The idea. A window function computes a value for each row from a set of related rows, its window, and leaves the rows in place. Its OVER (...) clause has three parts:

  • PARTITION BY splits rows into independent groups (each chat, each user). Without it, all rows form one partition.
  • ORDER BY orders rows inside each partition; ranking and LAG/LEAD need it.
  • The frame says which rows around the current one an aggregate sees: ROWS BETWEEN 2 PRECEDING AND CURRENT ROW means "this row and the two before it". If you give an ORDER BY and no frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW: from the start of the partition to the current row and every row tied with it ({{SQLite window functions|https://www.sqlite.org/windowfunctions.html}}; Postgres {{documents the same default|https://www.postgresql.org/docs/current/sql-expressions.html#SYNTAX-WINDOW-FUNCTIONS}}).

5. CTEs and recursive queries


The problem. A real query has steps (aggregate messages per chat, then rank chats per user, then keep the top two). Nested subqueries hide the steps inside each other.


The idea. A common table expression (CTE), WITH name AS (SELECT ...), names a step so later steps can use it like a table. The fan-out fix in section 2 used two. What it costs: usually nothing. Since PostgreSQL 12, a CTE that is referenced once, is not recursive and has no side effects is inlined into the main query and optimised with it; MATERIALIZED forces it to be computed once on its own, NOT MATERIALIZED forces inlining ({{PostgreSQL 12 release notes|https://www.postgresql.org/docs/release/12.0/}}; {{WITH queries|https://www.postgresql.org/docs/current/queries-with.html}}). Older advice that "CTEs are an optimisation fence" describes Postgres 11 and earlier.


Recursion. WITH RECURSIVE lets a CTE refer to itself: a starting query (the anchor), UNION ALL, and a step that joins the CTE's previous rows to find the next ones, repeated until a step adds no rows. It is how SQL walks a tree or a graph of unknown depth: a reply thread, an org chart, a bill of materials, a category tree.

What it costs, and when not to
A recursive query on a cycle (a message that is its own ancestor through bad data) never ends: guard with a depth limit (WHERE depth < 100) or, in Postgres 14 and later, the CYCLE clause. Deep trees read many times are often better stored with a materialised path or a closure table (one row per ancestor and descendant pair); for traversals many hops deep across large graphs, see the graph section of {{NoSQL in practice|n:3ef5c17b0d0d81ec8456c41e4e8f5f6b}}.
