6. Wide-column: Cassandra and ScyllaDB

The problem

Suppose the chat product's messages arrive faster than one primary database can write them, users are on several continents, and losing a whole data centre must not stop anyone sending messages. A single-primary database cannot give all three. Apache Cassandra (and ScyllaDB, its C++ reimplementation) spreads every table over many equal machines, with no primary at all.

How it models data

  • A table's PRIMARY KEY ((a, b), c, d) has two parts. The partition key (a, b) is hashed to a number called a token; the machines (nodes) form a ring in which each owns ranges of tokens, so the token decides which nodes hold the partition. The clustering columns c, d sort the rows inside the partition.
  • Each partition is copied to RF nodes (the replication factor, usually 3, placed in different racks or data centres). Every node accepts reads and writes for any key and forwards them to the replicas: there is no leader (root atlas).
  • Storage is an LSM-tree: a commit log and an in-memory table, flushed to immutable sorted files (SSTables) that background compaction merges ({{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}} measures LSM-trees on RocksDB).
  • The query language, CQL, looks like SQL but has no joins, and a query must name the partition key: "data is modeled around specific queries", one table per query, with data duplicated across tables on purpose ({{Cassandra data modelling|https://cassandra.apache.org/doc/latest/cassandra/developing/data-modeling/intro.html}}).

Tunable consistency, with the quorum arithmetic


Each request chooses how many of the RF replicas must answer: ONE, QUORUM (a majority: floor(RF/2) + 1), LOCAL_QUORUM (a majority inside the local data centre) or ALL ({{Cassandra, Dynamo architecture|https://cassandra.apache.org/doc/5.0/cassandra/architecture/dynamo.html}}). If the replicas a write waited for (W) and the replicas a read asks (R) must overlap, W + R > RF, every read meets at least one replica with the latest acknowledged write. The default is ONE, so by default a read can be stale (root atlas). Choose levels and knock nodes out:


















Three things this arithmetic does not say. Conflicting writes are resolved by timestamp, last write wins, so two clients updating the same cell lose one update silently (Jepsen showed acknowledged writes lost this way in 2013; root atlas). For compare-and-set ("insert only if absent") Cassandra has lightweight transactions, which run a Paxos consensus round among the replicas for each operation and so cost extra round trips. And multi-partition ACID transactions (Accord) arrive only with Cassandra 6.0, still in alpha (root atlas).


Tombstones: why deleting slows reads


An LSM-tree cannot erase a row in place: the row may sit in several immutable files on several replicas. So a delete writes a tombstone, a marker that hides older data, and the tombstone is kept for gc_grace_seconds (default 864,000 seconds, 10 days) so that every replica learns of it; a replica that misses the delete for longer can bring the data back ("zombie" rows) ({{Cassandra, tombstones|https://cassandra.apache.org/doc/5.0/cassandra/managing/operating/compaction/tombstones.html}}). Until compaction drops them, a read has to step over every tombstone in its way. Measured: a partition of 130,000 messages, the newest ones deleted one by one, then "the latest 50" read:

Discord's 2017 post describes hitting this six months into production: a public channel with millions of deleted messages and one remaining message made Cassandra "scan millions of message tombstones", causing 10-second garbage-collection pauses; they cut the grace period from 10 days to 2 and stopped re-reading empty buckets (same Discord post). The lesson: a table used like a queue (insert, read, delete) is the classic anti-pattern; expire data with a TTL in time-ordered tables, and choose compaction to match.

ScyllaDB and the others


ScyllaDB reimplements Cassandra in C++ with one shard per CPU core and no garbage collector, speaks CQL (and a DynamoDB-compatible API), and is what Discord moved to: 177 Cassandra nodes became 72 ScyllaDB nodes (the system design page's {{Case files|n:3c65c17b0d0d81048ae0dd14ac399b4d}}, "Trillions of messages", March 2023). Its licence changed: the AGPL open-source edition ended with 6.2 and since 2025.1 there is one source-available product, free only within 10 TB and 50 vCPUs (licence v1.1, April 2026; root atlas). Google Bigtable and HBase share the wide-column shape (row key to column families), with single-row atomicity and no multi-row transactions.


What it costs
One table per question, written in step by your code; no joins; no ad hoc queries; deletes that slow reads for 10 days; last-write-wins conflicts; repairs and compaction to operate, on many machines.


When Postgres would still do
Until write volume or the need to survive a data-centre loss with no failover pause actually exceeds what one primary (plus replicas, plus partitioning by time) can do. Most products never get there; Discord did at billions of messages.
