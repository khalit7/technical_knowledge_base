The idea in one screen

Every non-relational family stores together, in the order wanted, what one planned question reads, so that question stays one cheap read at any scale; the price is that a question you did not plan becomes a scan, a new table or impossible. That is why Postgres stays the default until a measurement says otherwise.

Each family makes one shape of question cheap by how it lays data out, and pays for every other shape

Key-value in memory

Redis 8.8, Valkey

Cheap: counters, rate limits, leaderboards, queues hit thousands of times a second; pick the data structure that answers the question (a sorted set for ranks); every command is atomic.

Hard: data must fit in memory; replication is asynchronous, so a failover lost acknowledged writes here.

Postgres still does it: a counter row with UPDATE ... SET n = n + 1, a job queue with SKIP LOCKED, at low rates.

Key-value, managed and partitioned

DynamoDB

Cheap: any planned question is one request at any scale, with no servers to run; list the access patterns first, then choose partition and sort keys (often one table for everything).

Hard: a question you did not plan becomes a scan of the whole table; one busy key is capped at 1,000 writes a second.

Postgres still does it: you are not on AWS at that scale, or your questions still change every week.

Document

MongoDB 8.0

Cheap: records whose shape varies, read and written as one unit; embed what is read together, reference what grows without bound.

Hard: a document is capped at 16 MB; appends grow the document; cross-document invariants need transactions.

Postgres still does it: almost always: a jsonb column next to normal columns (measured in section 5).

Wide-column

Cassandra 5.0, ScyllaDB

Cheap: writes beyond one machine, many regions, no single point of failure; one table per query, the partition key groups what it reads, the clustering key sorts it.

Hard: no joins, no ad hoc queries; deletes leave tombstones that later reads must skip.

Postgres still does it: while one server keeps up with the writes: the root measured 2,133 to 9,212 small write transactions a second on this laptop, depending on whether each commit is really flushed to disk.

Time series

Postgres partitions, Prometheus, TimescaleDB, ClickHouse

Cheap: appends in time order, recent time ranges, rollups, dropping whole partitions for retention.

Hard: anything that is not a time range; high cardinality (a label per user) explodes memory.

Postgres still does it: native partitioning plus a rollup table, measured in section 7.

Graph

Neo4j 2026.09, Kuzu 0.11

Cheap: questions of unknown or large depth over connected data: paths, fraud rings, patterns written in Cypher.

Hard: another system to run; a fixed one or two hops is no faster than Postgres.

Postgres still does it: fixed one or two hops: a join per hop is fast (measured in section 8).

Access pattern
one question the app asks: what it knows, what it wants back, how often.
Partition key
the part of a key that decides which group, and so which machine, a record lives in.
Sort key
the part of a key that orders records inside their partition (clustering columns in Cassandra).
Denormalisation
storing a fact more than once, on purpose, so each question reads one place.
Hot partition
one key that gets so much traffic it hits its partition's ceiling.
Tombstone
a delete marker in an LSM store, kept until every replica has seen it.
Cardinality
the number of distinct values (of a label, a key).

Results marked measured were recorded for this page on a laptop (an Apple M1 Pro, 16 GB) on 4 and 5 October 2026 against real servers running locally; illustrative marks drawings made to explain a shape. A laptop has no network between client and server, so absolute timings are best cases; the counts (pages, rows, items, partitions) are what carries over to production.

The five habits of a professional
  1. Write the access patterns down first: every question, with its inputs, sort order and frequency. The schema comes from that list, not from the shape of the data.
  2. Choose the partition key from the busiest question and check its spread: no key may get a large share of the traffic, and no partition may grow without bound (add a time bucket).
  3. Count what a request reads, not what it returns: a filter after a scan still reads, and pays for, every item.
  4. Know the durability and replication defaults: Redis acknowledges before the replica has the write; Cassandra flushes its commit log every 10 seconds; MongoDB reads at "local" by default.
  5. Keep Postgres as the source of truth until a measurement says otherwise, and treat every other store as a copy you can rebuild.

1. Queries first: the one idea behind every family

A relational database is designed from the data (each fact stored once: normalisation) and answers any question by joining at query time. A join needs the rows of both tables in one place, which is why it lives on one machine. The non-relational families turn the design around: you write down the access patterns first, then store the data so that each question reads one contiguous piece of storage, by giving every record a partition key (which group, and so which machine) and a sort key (its order inside the group). Data needed by two questions is often stored twice: denormalisation. The chat product's questions run through the whole page:

What it costs
Every question not on the list is a problem later: in DynamoDB or Cassandra it means a new table or index (written to on every write) and a backfill of all existing data. Relational databases are the right default precisely because they do not need this list in advance. The admin question is the typical one no partitioned store answers well: it goes to an analytics copy (the {{Analytics: columnar engines, DuckDB and the lakehouse|n:3ef5c17b0d0d8157814ec5dd8a0d4fb5}} child).
