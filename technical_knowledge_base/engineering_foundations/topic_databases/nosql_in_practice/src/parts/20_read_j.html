Choosing, and running them in production

How pros decide

  1. Start with Postgres as the source of truth and write down the access patterns (section 1). Most of the families' tricks exist in Postgres in smaller form: a composite index (section 2), jsonb (section 5), partitions and rollups (section 7), a join per hop (section 8), SKIP LOCKED queues.
  2. Add a store only for a measured problem, named in one sentence: "ranks for 100,000 players on every page view cost 9 ms each" (Redis); "message writes exceed one primary" (Cassandra, ScyllaDB or DynamoDB); "every dashboard query scans 30 days" (a rollup, then a time-series or column store).
  3. Treat every extra store as a copy that can be rebuilt from the source of truth, fed by an outbox or change data capture ({{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}), with its own backups, monitoring and on-call knowledge. "Polyglot persistence" (several stores, each for what it does best) is real at scale and an expensive habit before it.
SystemSettings pros check first (each explained on this page)
Redis / Valkeymaxmemory and an eviction policy when it is a cache, noeviction when it holds data you need; appendonly yes with appendfsync everysec if losing a minute matters; replicas plus Sentinel or Cluster for failover, knowing that failover can drop acknowledged writes; no KEYS * in production (use SCAN); short scripts.
DynamoDBaccess patterns and keys reviewed before the first write; on-demand capacity until traffic is predictable; alarms on throttled requests; Contributor Insights to find hot keys; a TTL attribute to expire items; incremental export to S3 for analytics.
MongoDBwrite concern majority (the default since 5.0); a $jsonSchema validator per collection; one index per access pattern, ordered by ESR; no unbounded arrays; transactions short and retried on TransientTransactionError.
Cassandra / ScyllaDBreplication factor 3 across racks or zones, LOCAL_QUORUM for reads and writes that must agree; partitions bounded by a time bucket; repair run more often than gc_grace_seconds; alerts on tombstone warnings and large partitions; compaction chosen per table.
Prometheus and friendsno unbounded label values; retention and rollups set on purpose; long-term storage (Thanos, Mimir, VictoriaMetrics) only when one server's retention is not enough.

These are configuration names and documented behaviours from the sources linked in each section; they are a checklist, not a complete production guide. Backups, replication and failover for Postgres itself are on {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}}; sharding Postgres and distributed SQL on {{Scaling a database|n:3ef5c17b0d0d81f0aaceee1e21b972be}}; consistency models and quorums in general on {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}}.

Common mistakes

Choosing the database before listing the questions
The family follows from the access patterns. A store chosen for its reputation, before the list exists, leaves the questions nobody planned for as scans (section 4) or new tables (section 6).
Read, decide, write in the application
Measured: 188 requests passed a limit of 20. Use the store's atomic operation (INCR, a Lua script, a conditional write, UPDATE ... SET n = n - 1 WHERE n > 0).
Redis as the only copy
A failover lost 4,947 of 5,000 acknowledged writes here; an RDB-only server lost every write since its last snapshot. Keep the source of truth in a database.
Believing a filter makes a scan cheap
DynamoDB charges for items read, not returned: a Scan that returned nothing still read 1,000 items in its first page.
A partition key that concentrates traffic
The current date, a tenant with most of the traffic, one celebrity chat. Every partition has a ceiling (1,000 writes a second in DynamoDB); spread with a suffix or rethink the key.
Partitions or documents that grow forever
A chat document hit the 16 MB limit at 15,220 messages; a Cassandra partition per chat grows without limit. Bucket by time or count.
Using Cassandra as a queue, or deleting in bulk
5,000 tombstones made a read about nine times slower; 101,000 made it fail. Prefer TTLs on time-ordered tables with TimeWindow compaction, and never a read-and-delete queue.
"Schemaless" without validation
Without a validator, every reader must handle every shape ever written. Add $jsonSchema or keep the fixed fields as Postgres columns.
Reading your own write from an index or replica
DynamoDB GSIs, MongoDB secondaries, Redis replicas and Cassandra at ONE can all return data from before your write. Read from the primary, or use a strong read where one exists, for the request right after a write.
User ids as metric labels
One label with 100,000 values multiplies every metric's series by 100,000 (the calculator in section 7). Per-user detail goes in logs or an events table.
Deleting old time-series rows with DELETE
Measured: 1.9 s and 65 MB of log for 7 days, and the table did not shrink; dropping 7 daily partitions took 0.06 s.
A graph database for two hops
Friends of friends was faster in Postgres than in either graph engine here. Graph databases pay off for paths and variable-depth patterns.
