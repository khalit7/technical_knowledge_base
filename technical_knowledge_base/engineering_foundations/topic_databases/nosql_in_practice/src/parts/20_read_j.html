  1. Start with Postgres as the source of truth and write down the access patterns (section 1). Most of the families' tricks exist in Postgres in smaller form: a composite index (section 2), jsonb (section 5), partitions and rollups (section 7), a join per hop (section 8), SKIP LOCKED queues.
  2. Add a store only for a measured problem, named in one sentence: "ranks for 100,000 players on every page view cost 9 ms each" (Redis); "message writes exceed one primary" (Cassandra, ScyllaDB or DynamoDB); "every dashboard query scans 30 days" (a rollup, then a time-series or column store).
  3. Treat every extra store as a copy that can be rebuilt from the source of truth, fed by an outbox or change data capture ({{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}), with its own backups, monitoring and on-call knowledge. "Polyglot persistence" (several stores, each for what it does best) is real at scale and an expensive habit before it.

Backups, replication and failover for Postgres itself are {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}}'s; sharding Postgres and distributed SQL are {{Scaling a database|n:3ef5c17b0d0d81f0aaceee1e21b972be}}'s.

Mistakes with a measured cost (each points back to its section)
  • Read, decide, write in the application: 188 requests passed a limit of 20. Use the store's atomic operation (INCR, a Lua script, a conditional write, UPDATE ... SET n = n - 1 WHERE n > 0).
  • Redis as the only copy: a failover lost 4,947 of 5,000 acknowledged writes here; an RDB-only server lost every write since its last snapshot.
  • A partition key that concentrates traffic: the current date, a tenant with most of the traffic, one celebrity chat. Every partition has a ceiling (1,000 writes a second in DynamoDB).
  • Partitions or documents that grow forever: a chat document hit the 16 MB limit at 15,220 messages; a Cassandra partition per chat grows without limit. Bucket by time or count.
  • Cassandra as a queue, or bulk deletes: 5,000 tombstones made a read about nine times slower; 101,000 made it fail.
  • Reading your own write from an index or replica: DynamoDB GSIs, MongoDB secondaries, Redis replicas and Cassandra at ONE can all return data from before your write. Read from the primary, or use a strong read where one exists, for the request right after a write.
  • Deleting old time-series rows with DELETE: Measured: 1.9 s and 65 MB of log for 7 days, and the table did not shrink.
Embedded key-value engines: RocksDB and LMDB (the libraries under other systems)

Every database above sits on a storage engine: the library that turns "put this key and value" into bytes on disk. RocksDB is an embedded LSM-tree: a write-ahead log and a memtable, sorted files, background compaction; fast writes, tunable read, write and space amplification, many knobs. It is inside CockroachDB (via Pebble, its Go port), TiKV, Kafka Streams' state stores and many others; by default its WAL is not flushed to disk on every write, so a machine crash can lose the last writes (root atlas). {{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}} measures its amplification against Postgres. LMDB is a copy-on-write B+tree in one memory-mapped file: no WAL, no compaction, readers never block and see a consistent snapshot, but one writer at a time; very fast reads from many threads or processes; commits are flushed by default.

Reach for one directly only when building a storage component (a queue, a persistent cache, an index) inside one process and you want neither a server nor SQL. Otherwise SQLite (rows, SQL, one writer) and DuckDB (columns, analytics), on the root page, are the embedded databases to use.
