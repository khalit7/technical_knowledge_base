4. Key-value at any scale: DynamoDB and single-table design

Suppose the chat product needs a store that grows without limit, survives the loss of a data centre, has no servers, upgrades or vacuum to manage, and every request already knows its key. That is what Amazon DynamoDB sells: a managed, partitioned key-value and document store, billed per request or per reserved capacity.

The model

  • A table holds items (a map of attributes, at most 400 KB each). Each item has a primary key: a partition key, optionally with a sort key. Items with the same partition key form an item collection, stored together and sorted by sort key.
  • DynamoDB hashes the partition key to pick a partition; each partition is a Multi-Paxos group of three replicas, each with a write-ahead log and a B-tree (root atlas; {{Elhemali et al., Amazon DynamoDB, USENIX ATC 2022|https://www.usenix.org/conference/atc22/presentation/elhemali}}). Partitions split automatically as data and traffic grow.
  • Reads: GetItem (the full key: one item), Query (one partition key, optionally a sort key condition such as begins_with or between; items in sort order, up to 1 MB per page) and Scan (every item in the table). Nothing else: no joins, no query on a non-key attribute without an index.
  • Reads are eventually consistent by default; a strongly consistent read costs twice as much and is not available on global secondary indexes. Single-item writes are atomic; transactions cover up to 100 items in one Region and cost double (root atlas, claim corrected).
  • One read unit is a strongly consistent read of up to 4 KB (eventually consistent: half a unit); one write unit is a write of up to 1 KB. Each partition serves at most 3,000 read units and 1,000 write units a second ({{AWS, partition key design|https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-design.html}}).

Single-table design on the chat product

With no joins, a screen that needs a user, their chats and a chat's messages would take several requests if each kind of item had its own table. Single-table design puts every kind of item in one table, with generic key strings (PK, SK) holding a type prefix and an id, chosen so that the items one screen needs share a partition key and come back in one Query, sorted ({{Alex DeBrie, The What, Why, and When of Single-Table Design, 2020-02-05|https://www.alexdebrie.com/posts/dynamodb-single-table/}}). From the access patterns of section 1:

  1. Open a chat: messages get PK = CHAT#<chatId>, SK = MSG#<createdAt>#<messageId> (an ISO timestamp sorts correctly as a string; the id breaks ties). Query PK = CHAT#7, SK begins_with MSG#, descending, limit 50.
  2. Usage per day: PK = USER#<userId>, SK = USAGE#<day>, updated with an atomic ADD; Query SK begins_with USAGE#2025-09. The profile (SK = PROFILE) shares the partition, so one Query can fetch both.
  3. Chat list, most recently active first: chats sit under PK = USER#<userId>, SK = CHAT#<chatId>, sorted by id; a global secondary index (GSI1) re-keys them: GSI1PK = USER#<userId>, GSI1SK = LAST#<lastMessageAt>#<chatId>. Sending a message updates GSI1SK, and the chat moves to the top.
  4. Log in by email, emails unique: a lookup item PK = EMAIL#<email> holds the user id; registration writes the user and the lookup item in one transaction, each with attribute_not_exists(PK), so a duplicate email fails.
  5. Admin, every message of one model on one day: no key serves it without a partition that takes a quarter of all writes; it goes to an analytics copy (DynamoDB exports a table to S3 in full or incrementally, every 15 minutes to 24 hours, {{AWS quotas|https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ServiceQuotas.html}}).

Try it: start from Relational habit (one kind of item per table, keyed by its own id) and predict how many questions become scans; then switch to Single-table design. Change only the message key to MSG#{messageId} and watch "latest 50 messages" collapse into a scan.

Secondary indexes are copies, updated later


A global secondary index is a second copy of chosen attributes under a different key, maintained by DynamoDB asynchronously ("eventually consistent fashion ... within a fraction of a second, under normal conditions", {{AWS, GSI|https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/GSI.html}}): a chat list read right after sending a message can still show the old order, and a strongly consistent read on it is refused. Each index is paid on every write: changing an indexed key costs two index writes (delete the old entry, put the new one), and an index short of write capacity throttles writes to the table.


Index limits, writes, conditions and transactions, measured (depth)


A table has at most 20 GSIs by default and 5 local secondary indexes (same partition key, different sort key, strongly consistent, but they cap an item collection at 10 GB and stop adaptive capacity from splitting it).


Measured: one message put cost 1 write unit (a message item is about 173 bytes as DynamoDB counts size); the transaction that writes the message and moves the chat to the top of GSI1 cost 8 write units as DynamoDB Local accounted it. Registering a second account with an existing email failed with TransactionCanceledException, reasons [None, ConditionalCheckFailed]: the user item would have been fine, the email item already existed, so neither was written. An item over 400 KB was refused; a long document or file goes to S3 with its key stored in the item.


Unconfirmed: 8 write units against the documented 6
The documented rules give 6 (2 for each of the two transactional writes, 2 for moving the index entry), so Local appears to charge the index move at the transactional rate as well; unconfirmed against the real service.




Hot partitions: the limit is per key, not per table


All of one chat's messages share a partition key, so one very busy group chat can take at most 1,000 one-KB writes a second. DynamoDB keeps up to 300 seconds of unused capacity for bursts, and adaptive capacity moves busy items onto partitions of their own, "provided that traffic does not exceed ... the partition maximum capacity" ({{AWS, burst and adaptive capacity|https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/burst-adaptive-capacity.html}}). Past that the fix is write sharding: spread one hot key over CHAT#7#0 to CHAT#7#9 and have readers query all ten and merge. Move the write rate past 1,000, then add shards:

Single table or several?
DeBrie lists the costs of single-table design: a steep learning curve, new access patterns that need data migrations, and exports for analytics that are hard to read ("looks more like machine code than a simple spreadsheet", quoted there); he advises against it for early-stage applications that still need flexibility and for GraphQL back ends, whose resolvers issue separate requests anyway. AWS's own guidance makes the same trade ({{AWS Compute Blog, 2021-07-26|https://aws.amazon.com/blogs/compute/creating-a-single-table-design-with-amazon-dynamodb/}}). GSIs can now use up to four attributes each for the partition and sort keys, so an index no longer needs a hand-built composite string (DynamoDB Local added it in January 2026).


What it costs
The schema is the list of access patterns: a new question means a new index (written on every write) or a migration. Ad hoc questions, joins and aggregates belong elsewhere (export to S3, then DuckDB, Athena or a warehouse). Indexes are eventually consistent. A busy key is capped. And it runs only on AWS (DynamoDB Local is for development).


When Postgres would still do
Whenever one Postgres server (with replicas for reads) can carry the load and the team would rather keep SQL's flexibility: that covers most products for years. DynamoDB wins when you are on AWS, want no database to operate, and traffic is either huge and key-shaped or tiny and spiky (on-demand costs near zero when idle).
