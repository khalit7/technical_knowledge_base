4. Key-value at any scale: DynamoDB and single-table design

The problem

Redis is one machine's memory. Suppose the chat product needs a store that grows without limit, survives the loss of a data centre, and has no servers, upgrades or vacuum to manage, and every request already knows the key it wants (a user id, a chat id). That is what Amazon DynamoDB sells: a managed, partitioned key-value and document store, billed per request or per reserved capacity.

4.1 The model

  • A table holds items (a map of attributes, at most 400 KB each). Each item has a primary key: a partition key, optionally with a sort key. Items with the same partition key form an item collection, stored together and sorted by sort key.
  • DynamoDB hashes the partition key to pick a partition; each partition is a Multi-Paxos group of three replicas, each with a write-ahead log and a B-tree (root atlas; {{Elhemali et al., Amazon DynamoDB, USENIX ATC 2022|https://www.usenix.org/conference/atc22/presentation/elhemali}}). Partitions split automatically as data and traffic grow.
  • Reads: GetItem (the full key: one item), Query (one partition key, optionally a sort key condition such as begins_with or between; returns items in sort order, ascending or descending, up to 1 MB per page) and Scan (every item in the table). Nothing else: no joins, no query on a non-key attribute without an index.
  • Consistency: reads are eventually consistent by default (they may miss a write from the last moment); a strongly consistent read costs twice as much and is not available on global secondary indexes. Single-item writes are atomic; transactions cover up to 100 items in one Region and cost double (root atlas, claim corrected).
  • Capacity is counted in units: one read unit is a strongly consistent read of up to 4 KB (an eventually consistent read is half a unit); one write unit is a write of up to 1 KB. Each partition serves at most 3,000 read units and 1,000 write units a second ({{AWS, partition key design|https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-design.html}}).

4.2 Single-table design, step by step on the chat product

Because there are no joins, a page that needs a user, their chats and a chat's messages would need several requests if each kind of item lived in its own table, keyed by its own id. Single-table design puts every kind of item in one table and chooses keys so that the items one screen needs share a partition key and come back in one Query, sorted ({{Alex DeBrie, The What, Why, and When of Single-Table Design, 2020-02-05|https://www.alexdebrie.com/posts/dynamodb-single-table/}}). The keys are generic strings (PK, SK) holding a type prefix and an id. Built step by step from the access patterns of section 1:

  1. Open a chat (latest 50 messages). The request knows the chat id and wants messages newest first, so messages get PK = CHAT#<chatId> and SK = MSG#<createdAt>#<messageId>: an ISO timestamp sorts correctly as a string, and the id breaks ties. Query PK = CHAT#7, SK begins_with MSG#, descending, limit 50.
  2. Usage per day. The request knows the user and a month: PK = USER#<userId>, SK = USAGE#<day>, one item per user per day updated with an atomic ADD. Query SK begins_with USAGE#2025-09.
  3. User profile. PK = USER#<userId>, SK = PROFILE: it shares the user's partition with the usage items, so one Query could fetch the profile and the month together.
  4. Chat list, most recently active first. Chats get PK = USER#<userId>, SK = CHAT#<chatId>, but that sorts by id, not by activity. A global secondary index (GSI1) re-keys the same items: GSI1PK = USER#<userId>, GSI1SK = LAST#<lastMessageAt>#<chatId>. Sending a message updates the chat's GSI1SK, and the index moves it to the top.
  5. Log in by email, emails unique. A lookup item PK = EMAIL#<email> holds the user id. Registration writes the user and the lookup item in one transaction, each with the condition attribute_not_exists(PK), so a second account with the same email fails.
  6. Admin: every message of one model on one day. No key can serve this without a partition that receives a quarter of all writes; it goes to an analytics copy (DynamoDB exports a table to S3 in full or incrementally, every 15 minutes to 24 hours, {{AWS quotas|https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ServiceQuotas.html}}).

Measured on DynamoDB Local 3.3.1 (AWS's downloadable version of the API) with the chat data: 400 users, 2,999 chats, 49,517 messages, 54,775 items in all. DynamoDB Local runs the real API, key rules and capacity accounting, but not the service's partitions, throughput limits or latency, so only counts are shown.

Every question on the list is one request that reads only the items it returns. The two wrong ways show what a missing key costs: a Scan with a filter for chat 7 read 1,000 items in its first page and returned none of them (the filter runs after the read, and you pay for every item read), and answering the admin question by scanning read all 54,775 items in 9 pages of 1 MB for 1,111.5 read units. At a billion items the same scan would read a billion items.

4.3 Secondary indexes


A global secondary index is a second copy of chosen attributes under a different key, maintained by DynamoDB. It is updated asynchronously ("eventually consistent fashion ... within a fraction of a second, under normal conditions", {{AWS, GSI|https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/GSI.html}}), so a chat list read right after sending a message can still show the old order; a strongly consistent read on it is refused (the error above). Each index is paid for on every write: changing an indexed key costs two index writes (delete the old entry, put the new one), and if an index lacks write capacity, writes to the table are throttled. A table has at most 20 GSIs by default and 5 local secondary indexes (same partition key, different sort key, strongly consistent, but they cap an item collection at 10 GB and stop adaptive capacity from splitting it).


4.4 Writes, conditions and transactions


Measured: one message put cost 1 write unit (a message item is about 173 bytes as DynamoDB counts size); the transaction that writes the message and moves the chat to the top of GSI1 cost 8 write units as DynamoDB Local accounted it. The documented rules give 6 (2 for each of the two transactional writes, 2 for moving the index entry), so Local appears to charge the index move at the transactional rate as well; unconfirmed against the real service. Registering a second account with an existing email failed with TransactionCanceledException, reasons [None, ConditionalCheckFailed]: the user item would have been fine, the email item already existed, so neither was written. An item over 400 KB was refused. Chat messages fit easily; a long document or a file does not, and goes to S3 with its key stored in the item.


4.5 Capacity, price and hot partitions


Two billing modes, priced for US East (N. Virginia), standard table class, as read on 4 October 2026: on-demand charges $0.625 per million write units and $0.125 per million read units ({{AWS on-demand pricing|https://aws.amazon.com/dynamodb/pricing/on-demand/}}); provisioned charges for reserved units per hour, $0.00065 per write unit-hour and $0.00013 per read unit-hour, with auto scaling to follow load ({{AWS provisioned pricing|https://aws.amazon.com/dynamodb/pricing/provisioned/}}); storage is $0.25 per GB-month. On-demand is simplest and right for spiky or unknown traffic; provisioned is cheaper for steady traffic you can predict. The lab's calculator prices the chat product's messages both ways from the units measured above.


The limit that bites is per key, not per table. All of one chat's messages share a partition key, so one very busy group chat can take at most 1,000 one-KB writes a second. DynamoDB keeps up to 300 seconds of unused capacity for bursts, and adaptive capacity moves busy items onto partitions of their own, "provided that traffic does not exceed ... the partition maximum capacity" ({{AWS, burst and adaptive capacity|https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/burst-adaptive-capacity.html}}). Past that, the fix is write sharding: spread one hot key over CHAT#7#0 to CHAT#7#9 and have readers query all ten and merge. Discord hit the same wall in Cassandra with its busiest channels (section 6).


Single table or several?
DeBrie lists the costs of single-table design: a steep learning curve, new access patterns that need data migrations, and exports for analytics that are hard to read ("looks more like machine code than a simple spreadsheet", quoted there); he advises against it for early-stage applications that still need flexibility and for GraphQL back ends, whose resolvers issue separate requests anyway. AWS's own guidance makes the same trade ({{AWS Compute Blog, 2021-07-26|https://aws.amazon.com/blogs/compute/creating-a-single-table-design-with-amazon-dynamodb/}}). A newer feature narrows the gap: GSIs can now use up to four attributes each for the partition and sort keys, so an index no longer needs a hand-built composite string (DynamoDB Local added it in January 2026).


What it costs
The schema is the list of access patterns: a new question means a new index (written on every write) or a migration. Ad hoc questions, joins and aggregates belong elsewhere (export to S3, then DuckDB, Athena or a warehouse). Indexes are eventually consistent. A busy key is capped. And it runs only on AWS (DynamoDB Local is for development).


When Postgres would still do
Whenever one Postgres server (with replicas for reads) can carry the load and the team would rather keep SQL's flexibility: that covers most products for years. DynamoDB wins when you are on AWS, want no database to operate, and either traffic is huge and key-shaped or it is tiny and spiky (on-demand at near-zero cost when idle).
