7. Time series: metrics, events and what makes them special

The operations dashboard wants requests per minute, median latency and tokens per model for the last hour, refreshed every few seconds, and a 30-day trend; every chat request produces one measurement. That data is append-only in time order, read by time range, and matters less as it ages: last hour in full, last month per minute (downsampling), then deleted (retention). Every time-series database exploits the same three facts: time-sliced chunks so a range touches few chunks, precomputed rollups, and expiry by dropping whole chunks instead of deleting rows. All three exist in plain Postgres, which is what was measured (5,184,000 request rows over 30 days: 4 models, 8 servers, about 2 a second).

Chunks by time turn a range into a few chunks, a chart into a rollup, and retention into a drop

measured PostgreSQL 16.2, one big table against 30 daily partitions. A one-minute rollup table of 172,800 rows drew the 30-day hourly chart in 45.6 ms instead of 1,405 ms from the raw rows, with the same answer (checked with EXCEPT). Dropping 7 daily partitions took 0.06 s and 29,816 bytes of log; a DELETE of the same rows from one table took 1.9 s and 65 MB of log, and the table stayed 317 MB on disk even after VACUUM (the space is reused, not returned).

Because rows arrive in time order, a BRIN index (the minimum and maximum timestamp per block range) on ts is KB against MB for a B-tree. The same rows as compressed Parquet are about a tenth of the size, and DuckDB drew the 30-day chart straight from the file in ms: column stores are very good at this ({{Analytics|n:3ef5c17b0d0d8157814ec5dd8a0d4fb5}} owns them).

Cardinality: the number that breaks metrics systems


In Prometheus-style systems a series is one metric name plus one combination of label values, and every series costs memory and an index entry. "Every unique combination of key-value label pairs represents a new time series ... Do not use labels to store dimensions with high cardinality (many different label values), such as user IDs, email addresses, or other unbounded sets of values" ({{Prometheus naming|https://prometheus.io/docs/practices/naming/}}). Series = product of the label value counts (an upper bound: only combinations that occur create series). Samples per day = series x 86,400 / scrape interval of 15 s. Disk per day uses Prometheus's "1-2 bytes per sample" ({{Prometheus storage|https://prometheus.io/docs/prometheus/latest/storage/}}; 2 used here); head memory per series is not documented as a fixed figure, so none is shown.




Per-user and per-request detail belongs in logs, traces or an events table in a column store, where a row per request is normal; metrics stay aggregate. Instrumenting in practice is {{Observability|n:3ef5c17b0d0d811e8490c54dd42c2b9b}}'s.

When Postgres would still do
Up to hundreds of millions of rows on one server with native partitioning by day, a BRIN or B-tree index on time, a rollup table refreshed by a scheduled job, and DROP of old partitions; TimescaleDB automates exactly this. Service metrics with alerting belong in Prometheus (or a hosted equivalent) regardless; analytics over billions of events in a column store.
