7. Time series: metrics, events and what makes them special

The problem

The operations team wants a dashboard: requests per minute, median latency and tokens per model, for the last hour, refreshed every few seconds, and a 30-day trend. Every chat request produces one measurement. That data has a peculiar shape:

  • Append-only, in time order: rows are never updated, and new rows always have the newest timestamp.
  • Read by time range: almost every query says "the last hour" or "this month", grouped into time buckets.
  • Old data matters less: last hour at full detail, last month per minute, last year per hour (downsampling), and then deleted (retention).

Every time-series database exploits the same three facts: store data in time-sliced chunks so a time range touches few chunks; precompute rollups; and expire data by dropping whole chunks instead of deleting rows. All three can be done in plain Postgres, which is what was measured here (5,184,000 request rows over 30 days: 4 models, 8 servers, about 2 a second).

Measured in PostgreSQL 16.2 and DuckDB

Three results to take away. First, dropping a day's partition is a metadata change: s and KB of log for 7 days, against s and MB of log to DELETE the same rows from one big table, which then stays MB on disk even after VACUUM (the space is reused, not returned). Second, a one-minute rollup table of rows answered the 30-day hourly chart in ms instead of ms, with the same answer (checked with EXCEPT). Third, because rows arrive in time order, a BRIN index (one summary of the minimum and maximum timestamp per block range) on ts is KB against MB for a B-tree. The same rows as compressed Parquet are about a tenth of the size, and DuckDB drew the 30-day chart straight from the file in ms: column stores are very good at this (the coming {{Analytics|n:3ef5c17b0d0d8157814ec5dd8a0d4fb5}} child).

Cardinality: the number that breaks metrics systems


In Prometheus-style systems, a series is one metric name plus one combination of label values, and every series costs memory in the head block and an entry in the index. "Every unique combination of key-value label pairs represents a new time series ... Do not use labels to store dimensions with high cardinality (many different label values), such as user IDs, email addresses, or other unbounded sets of values" ({{Prometheus naming|https://prometheus.io/docs/practices/naming/}}). The number of series is the product of the label value counts:















Series = product of the label value counts (an upper bound: only combinations that occur create series). Samples per day = series x 86,400 / scrape interval of 15 s. Disk per day uses Prometheus's "1-2 bytes per sample" (2 used here); head memory per series is not documented as a fixed figure, so none is shown.




Per-user and per-request detail belongs in logs, traces or an events table in a column store, where a row per request is normal; metrics stay aggregate. Instrumenting these numbers in practice is on {{Observability|n:3ef5c17b0d0d811e8490c54dd42c2b9b}}.


When Postgres would still do
Up to hundreds of millions of rows on one server with native partitioning by day, a BRIN or B-tree index on time, a rollup table refreshed by a scheduled job, and DROP of old partitions; TimescaleDB automates exactly this. Service metrics with alerting belong in Prometheus (or a hosted equivalent) regardless; analytics over billions of events in a column store.
