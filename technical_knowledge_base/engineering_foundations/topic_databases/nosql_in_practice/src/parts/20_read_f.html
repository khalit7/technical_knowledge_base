5. Documents: MongoDB, and Postgres jsonb beside it

The problem

Some records do not have one fixed shape. A tool call in the chat product carries different arguments for each tool; a user's settings grow a new field every month. Splitting each shape into its own table, or adding a nullable column per field, gets clumsy. A document stores the record as one nested JSON-like value, fields and arrays included, read and written as a unit.

How MongoDB models data

MongoDB stores documents in collections, in BSON (binary JSON with real dates and integers), each with a unique _id. You can index any field, including fields inside arrays, and query with a JSON query language or an aggregation pipeline (a list of stages: filter, group, sort, join). Underneath, the WiredTiger engine keeps B-trees with compression and a journal (a write-ahead log); a replica set has one primary and copies; sharding splits a collection over machines by a shard key you choose (root atlas). Measured here: MongoDB 8.0.23 (conda-forge) as a one-member replica set, because transactions need one; MongoDB 9.0 reached general availability on 28 September 2026 (root atlas), after these runs were set up. The server is under the SSPL, a source-available licence, since 16 October 2018.

Embed or reference? Worked on chats and messages

The central design choice is whether related data lives inside a document (embedding) or in its own documents that point back (referencing). MongoDB's guidance: embed when you have a "contains" relationship, "query pieces of information together" and update them together; reference when "the child side of the relationship has high cardinality" or "your embedded data grows without bounds" ({{MongoDB, embedding vs references|https://www.mongodb.com/docs/manual/data-modeling/concepts/embedding-vs-references/}}). A chat's messages are the textbook hard case: always read together, and growing without bound. Both shapes were loaded with the same 1M messages:

Then the hard limit: a BSON document may not exceed 16 MiB ({{MongoDB limits|https://www.mongodb.com/docs/manual/reference/limits/}}). Pushing messages of about 1 KB into one chat, the th fit (the document reached bytes) and the next failed with Resulting document after update is larger than 16777216 (error 10334). A busy group chat would hit it in weeks, and long before that every read of the chat drags the whole history along.

The design pros use: the chat document holds its metadata and perhaps the last few messages for the chat list (embedding a bounded subset), and messages are referenced, one document each or grouped in fixed-size "buckets" of, say, 100 messages per document (MongoDB's {{bucket pattern|https://www.mongodb.com/docs/manual/data-modeling/design-patterns/group-data/bucket-pattern/}}). Tool-call arguments, whose shape varies and which are always read with their message, are embedded in the message. Every write here took several milliseconds because the default write concern (w: "majority", measured: ) waits for the journal to be flushed before acknowledging.

Indexes and the aggregation pipeline

Indexes work as in Postgres: B-trees on one or more fields, used for equality, ranges and sorts. For compound indexes MongoDB's rule of thumb is ESR: equality fields first, then sort fields, then range fields ({{MongoDB, the ESR guideline|https://www.mongodb.com/docs/manual/tutorial/equality-sort-range-guideline/}}); the {chat_id: 1, created_at: -1} index above is equality then sort. Transactions and schema validation


A write to one document is atomic. Since version 4.0 (replica sets) and 4.2 (sharded clusters), multi-document transactions run with snapshot isolation, but the docs advise modelling so that most operations touch one document, and a transaction may run for at most 60 seconds by default (root atlas; {{MongoDB limits|https://www.mongodb.com/docs/manual/reference/limits/}}). Measured: moving one credit from user 7 to user 12 in a transaction committed ( and  credits). Then two transactions updated user 7's document at once: the second failed immediately with WriteConflict (code ), labelled . MongoDB does not make the second writer wait as Postgres does; it aborts it and expects the client to retry the whole transaction, which the drivers' with_transaction helper does for that label. Defaults matter: reads use read concern "", which can return data that a failover later rolls back, and Jepsen found in 2020 (4.2.6) that transactions did not give snapshot isolation at the default settings (root atlas).


"Schemaless" is optional: a collection can carry a $jsonSchema validator. A collection requiring chat_id and role in user, assistant or tool refused {role: "admin"} with . Teams that skip validation tend to find, a year later, that "no schema" became several schemas that every reader must handle.


The same documents in Postgres

What it costs
Documents move schema checks from the database into every reader; relationships across documents (a user's chats, a chat's messages) become application code or $lookup stages; growing arrays hit the 16 MB limit and make every write rewrite more. Multi-document invariants need transactions that abort on conflict and must be retried.


When Postgres would still do
Nearly always. Keep the columns you filter, join and aggregate on as columns, and put the genuinely variable part (tool arguments, settings, raw provider responses) in a jsonb column, with a GIN or expression index if you query inside it. MongoDB earns its place when most data really is document-shaped, read and written whole, and the team wants its built-in sharding or Atlas's managed service.
