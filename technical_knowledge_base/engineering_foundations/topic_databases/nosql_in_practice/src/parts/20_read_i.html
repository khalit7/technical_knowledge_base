8. Graph: Neo4j, Kuzu, and the recursive query

The problem

Some questions are about connections: "people you may know" (friends of friends), "is this new account linked to a known fraud ring within four steps", "how is user A connected to user B". In tables, each step along a connection is a join, and the number of steps is not known when you write the query.

How graph databases model data

A property graph has nodes (a user, a chat) and relationships between them (FRIEND, OWNS), each with a type, a direction and properties. Queries are written as patterns in Cypher (Neo4j also accepts GQL, the ISO graph query language that grew out of it): MATCH (u:User {uid: $u})-[:FRIEND*1..3]-(v) RETURN count(DISTINCT v) reads "from user u, follow one to three FRIEND relationships in either direction". Neo4j stores each relationship as a record that points directly at its two nodes and at the next relationship of each node, so following a relationship is a pointer lookup rather than an index search, a design its authors call index-free adjacency (root atlas; Robinson, Webber and Eifrem, {{Graph Databases, 2nd edition, O'Reilly 2015, chapter 6|https://neo4j.com/graph-databases-book/}}).

The work is set by the answer: by 3 hops a typical user reaches about a third of the graph, by 4 hops nearly all of it, and every engine must touch those rows. Two details matter for writing it in SQL. A naive recursive query that carries no memory of where it has been (UNION removes only exact duplicate (user, depth) rows) still finished here, but on denser graphs it revisits the same users along many paths; writing one DISTINCT join per hop keeps each frontier small. Neo4j's planner made the same move by itself: its profile shows VarLengthExpand(Pruning,BFS,All), a breadth-first expansion that drops nodes already seen.

The SQL that carries the path is short but explores every path rather than every user, which is why it slows down sharply with depth; the version that keeps a visited set has to be driven from application code, one query per hop. Graph databases earn their place when such questions are the product (fraud rings, recommendation paths, permissions inherited through groups, knowledge graphs), when the depth is variable or large, and when patterns with several node and relationship types ("accounts that share a device with an account that shares a card with a flagged account") would be a page of SQL.


Caveats with dates
Neo4j runs transactions at read committed: "a transaction that reads a node/relationship does not block another transaction from writing" it, so lost updates are possible unless a write lock is taken; Cypher takes one automatically for SET n.x = n.x + 1 ({{Neo4j, concurrent data access|https://neo4j.com/docs/operations-manual/current/database-internals/concurrent-data-access/}}). Clustering is Enterprise-only (Community is GPLv3; root atlas). Kuzu's GitHub repository was archived by its owners on 10 October 2025; its last release, 0.11.3, still works but receives no fixes, so treat it as a demonstration, not a dependency ({{kuzudb/kuzu|https://github.com/kuzudb/kuzu}}). Apache AGE adds Cypher inside Postgres, with traversals planned as joins (root atlas).


When Postgres would still do
Fixed one to three hops (friends, friends of friends, a group's members' chats): one join per hop with an index on both ends, measured above. Bounded hierarchies (an org chart, folders) with a recursive CTE. Move to a graph database when variable-depth path questions are central and frequent, or the pattern queries become unmaintainable in SQL.







9. Embedded key-value engines: RocksDB and LMDB


Every database above sits on a storage engine: the library that turns "put this key and value" into bytes on disk. Two are worth knowing by name because you will meet them inside other systems, and occasionally use one directly.




RocksDB (11.8)
An embedded LSM-tree: writes go to a write-ahead log and a memtable, flush to sorted files, and compaction merges them in the background. Fast writes, tunable read, write and space amplification, and a lot of knobs. Inside CockroachDB (via Pebble, its Go port), TiKV, Kafka Streams' state stores and many others. By default its WAL is not flushed to disk on every write, so a machine crash can lose the last writes (root atlas). The {{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}} page measures its write, read and space amplification against Postgres.


LMDB (1.0)
A copy-on-write B+tree in one memory-mapped file: no WAL, no compaction, readers never block and see a consistent snapshot, but only one writer at a time. Very fast reads from many threads or processes; commits are flushed by default. LMDB 1.0.0 arrived on 30 June 2026 after the long 0.9 line (root atlas).




Reach for one directly only when you are building a storage component (a queue, a cache with persistence, an index) inside one process and want neither a server nor SQL. Otherwise SQLite (rows, SQL, one writer) and DuckDB (columns, analytics), on the root page, are the embedded databases to use.
