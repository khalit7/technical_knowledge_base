8. Graph: Neo4j, Kuzu, and the recursive query

Some questions are about connections: "people you may know" (friends of friends), "is this account linked to a known fraud ring within four steps", "how is user A connected to user B". In tables each step is a join, and the number of steps is not known when you write the query. A property graph has nodes (a user, a chat) and relationships (FRIEND, OWNS), each with a type, a direction and properties. Queries are patterns in Cypher (Neo4j also accepts GQL, the ISO graph query language that grew out of it): MATCH (u:User {uid: $u})-[:FRIEND*1..3]-(v) RETURN count(DISTINCT v) reads "from user u, follow one to three FRIEND relationships in either direction". Neo4j stores each relationship as a record pointing directly at its two nodes and at the next relationship of each, so following one is a pointer lookup rather than an index search: index-free adjacency (root atlas; Robinson, Webber and Eifrem, {{Graph Databases, 2nd edition, O'Reilly 2015, chapter 6|https://neo4j.com/graph-databases-book/}}).

Measured: friends of friends, on the same graph

A synthetic social graph grown the way real ones grow (each new user befriends 10 existing users, chosen in proportion to how many friends they already have): users, friendships, a median of friends but a most-connected user with . For 10 random users, count everyone within k hops on PostgreSQL 16.2 (two ways), Neo4j Community and Kuzu , an embedded graph engine (a library, like DuckDB). Predict which engine wins at two hops.

For counting neighbours, the graph engines did not win: Postgres was fastest up to three hops

All four engines agree on every count. At four hops, where every engine touches nearly the whole graph, Neo4j was only than Postgres's better query. Times are measured from the client (Neo4j and Postgres over a local connection, Kuzu in process). The work is set by the answer: by 3 hops a typical user reaches about a third of the graph, by 4 nearly all of it, and every engine must touch those rows. In SQL, write one DISTINCT join per hop to keep each frontier small; a naive recursive query (whose UNION removes only exact duplicate (user, depth) rows) finished here but revisits users along many paths on denser graphs. Neo4j's planner made the same move by itself: VarLengthExpand(Pruning,BFS,All), a breadth-first expansion that drops nodes already seen.

The SQL that carries the path is short but explores every path rather than every user, so it slows sharply with depth; the version with a visited set must be driven from application code, one query per hop. Graph databases earn their place when such questions are the product (fraud rings, recommendation paths, permissions inherited through groups, knowledge graphs), when depth is variable or large, and when patterns over several node and relationship types ("accounts that share a device with an account that shares a card with a flagged account") would be a page of SQL. Caveats
Neo4j runs transactions at read committed: "a transaction that reads a node/relationship does not block another transaction from writing" it, so lost updates are possible unless a write lock is taken; Cypher takes one automatically for SET n.x = n.x + 1 ({{Neo4j, concurrent data access|https://neo4j.com/docs/operations-manual/current/database-internals/concurrent-data-access/}}). Kuzu's repository was archived by its owners, so treat it as a demonstration, not a dependency (dated table in Depth). Apache AGE adds Cypher inside Postgres, with traversals planned as joins (root atlas).


When Postgres would still do
Fixed one to three hops (friends, friends of friends, a group's members' chats): one join per hop with an index on both ends, measured above. Bounded hierarchies (an org chart, folders) with a recursive CTE. Move to a graph database when variable-depth path questions are central and frequent, or the pattern queries become unmaintainable in SQL.
