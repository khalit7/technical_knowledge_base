3. Key-value in memory: Redis

The problem

Some questions are tiny and asked constantly: "has this user sent more than 20 requests this minute?", "what rank is this player?", "is there a job waiting?". Each answer is a few bytes, but asked on every request it becomes most of the database's work, and some (a rank among 100,000 players) are expensive in SQL however you index them.

How it works

Redis is a server that keeps every key and its value in memory. A value is not just a string: it is one of a handful of data structures, each with its own commands, and the server executes commands one at a time on a single thread, so every command is atomic: no other client's command runs halfway through it (the root's Database atlas tab has Redis's row with sources). The version measured here is Redis 8.8.0 (conda-forge build) in its default configuration unless stated.

They are useful, but each one is a reason to keep more state in a store whose durability is weaker than your database's (below).

How fast, measured

On this laptop one GET took a median 52.1 µs (p99 121 µs) over 20,000 calls from Python: almost all of it is the client library and the loopback network, not Redis. That is why one client does only about 16,000 to 18,000 operations a second, 50 clients about 33,000 to 35,000 (one request in flight each), and 50 clients that pipeline 16 commands per round trip (send many, then read all the replies) over 520,000 (redis-benchmark, the tool that ships with Redis). In production, the network between your app and Redis dominates (Jeff Dean's classic figure is 0.5 ms for a round trip inside one data centre, and Microsoft aims for under about 2 ms between availability zones: the system design page's {{Numbers to know|n:3c65c17b0d0d81048ae0dd14ac399b4d}} tab), so the habits that matter are fewer round trips: pipelines, multi-key commands and scripts.

A leaderboard with a sorted set

A sorted set keeps members ordered by score. Redis implements it as two structures at once: a hash table (member to score) and a skip list, a sorted linked list with extra "express lane" links that let a search skip ahead, so finding a member's position takes about log2(N) steps ({{Redis sorted sets|https://redis.io/docs/latest/develop/data-types/sorted-sets/}}: "most sorted set operations are O(log(n))"). Measured with 100,000 players:

Redis sorted set

  • 100,000 members in 8.9 MB (about 93 bytes each, MEMORY USAGE)
  • top 10 (ZRANGE lb 0 9 REV WITHSCORES): median 99 µs
  • one player's rank (ZREVRANK): median 91 µs, wherever the player stands
  • score update (ZINCRBY): about 10,500 a second from one client

PostgreSQL 16.2, same scores, index on (score DESC)

  • top 10: 3 page reads, 0.059 ms: as good as Redis
  • rank = count of players above you: SELECT count(*) FROM scores WHERE score > (SELECT score FROM scores WHERE user_id = $1)
  • rank 50,000: 142 page reads, 4.67 ms; rank 95,359: 266 page reads, 8.98 ms
  • the cost grows with the rank: the index visits one entry per player above
When Postgres would still do
Top-N lists ("the 10 best") are an index read in Postgres. Exact ranks for everyone, asked on every page view, are what the sorted set is for; with only a few thousand players, or ranks shown as "top 5%", Postgres (or a rank recomputed every minute) is fine.

Rate limiting, and why it needs atomicity

A rate limiter decides, on every request, whether a user may make another one. The obvious code reads the user's remaining allowance, decides in the application, and writes the new value back. Run by many servers at once, two requests read the same allowance before either writes, and both pass. Measured: 16 processes each made 50 attempts against an allowance of 20.

"Read, decide, write" in the application let 188 of 800 attempts through a limit of 20. The same limit as one Lua script inside Redis let exactly 20 through, because a script runs atomically: "while executing the script, all server activities are blocked during its entire runtime" ({{Redis docs, scripting with Lua|https://redis.io/docs/latest/develop/programmability/eval-intro/}}).

A token bucket holds up to capacity tokens, refills at a steady rate, and each request takes one: it allows short bursts up to the capacity and a long-run average equal to the refill rate.     That is at-least-once delivery: a job can run twice (the first worker may have done the work and died before acknowledging), so the job must be safe to repeat. Durable logs, the outbox pattern and Kafka are on {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}; a Redis stream is the small version, with Redis's durability.
    

    Durability: what survives a crash
    

    Redis writes to disk in two optional ways ({{Redis persistence|https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/}}). An RDB snapshot is a point-in-time copy written by a forked child every so often ("you should be prepared to lose the latest minutes of data"). The append-only file (AOF) logs every write; with appendfsync everysec, the default when AOF is on, the file is flushed to disk once a second, so a power cut loses about a second of writes; with always it is flushed before each reply.     A kill -9 is a process crash, not a power cut: the operating system still holds what Redis wrote, which is why AOF lost nothing here. A power cut loses whatever was not yet flushed, up to about a second with everysec. On macOS a flush does not force the drive's own cache (the transactions page measures the same caveat for Postgres), so always is cheaper here than on a Linux server with a real flush.
    

    Replication: acknowledged writes that vanish
    

    Redis copies writes to its replicas after replying to the client: replication is asynchronous. If the primary dies before a replica has a write and the replica is promoted, the write is gone even though the client was told "OK". Measured: a primary and a replica on this laptop; the replica is paused (as a long garbage-collection pause or a network problem would), the primary acknowledges 5,000 writes of 10 KB, the primary is killed, the replica resumes and is promoted.
    

    

    The WAIT 1 500 call made after the writes returned 0: it reports how many replicas confirmed, it does not make the writes safe, and Redis's own documentation says "WAIT does not make Redis a strongly consistent store" ({{Redis WAIT|https://redis.io/docs/latest/commands/wait/}}). Jepsen measured the same with Sentinel failover in 2013 (56% of acknowledged writes lost; root atlas). So Redis must not be the only copy of anything you cannot rebuild.
    

    Licence: Redis and Valkey
    Redis moved from the BSD licence to a dual source-available licence (RSALv2 or SSPLv1) from version 7.4 on 20 March 2024; the Linux Foundation launched Valkey, a BSD fork of Redis 7.2.4, on 28 March 2024, backed by AWS, Google Cloud, Oracle and others; Redis 8 added AGPLv3 as a third option on 1 May 2025 (all in the root's Database atlas, with sources). Valkey speaks the same protocol and commands as Redis 7.2, so clients and the code on this page work unchanged; Redis 8-only features (built-in JSON, vector sets, the query engine) do not exist in Valkey under those names.
    

    What it costs
    Memory: everything lives in RAM, plus overhead per key (93 bytes per sorted-set member above). One thread executes commands, so a slow command (a KEYS *, a long script, a ZRANGE returning a million members) stalls every client. Durability and replication are weaker than a database's by default, as measured above. Redis Cluster shards keys over 16,384 hash slots, and a multi-key command or script works only when all its keys are in one slot (use hash tags such as {user:7}:bucket).
    

    When Postgres would still do
    A counter updated a few times a second (UPDATE ... SET n = n + 1 is atomic); a job queue with SELECT ... FOR UPDATE SKIP LOCKED (measured on {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}}); a rate limit at tens of requests a second; top-N lists. Using Redis as a cache in front of Postgres (cache-aside, eviction, invalidation, stampedes) is the {{Caching|n:3cd5c17b0d0d817ebd6ccadd4750c23a}} page's subject.
