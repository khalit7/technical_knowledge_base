3. Key-value in memory: Redis

Some questions are tiny and asked constantly: "has this user sent more than 20 requests this minute?", "what rank is this player?", "is there a job waiting?". Redis keeps every key and value in memory, and a value is one of a handful of data structures, each with its own commands. The server executes commands one at a time on a single thread, so every command is atomic: no other client's command runs halfway through it. Measured here: Redis 8.8.0 in its default configuration unless stated.

Speed is mostly the round trip: one GET took a median 52.1 µs (p99 121 µs) from Python, almost all of it client library and loopback, so one client does about 16,000 to 18,000 operations a second and 50 clients that pipeline 16 commands per round trip (send many, then read all replies) over 520,000. In production the network dominates (Jeff Dean's classic figure is 0.5 ms for a round trip inside one data centre, and Microsoft aims for under about 2 ms between availability zones: the system design page's {{Numbers to know|n:3c65c17b0d0d81048ae0dd14ac399b4d}} tab), so the habit that matters is fewer round trips: pipelines, multi-key commands and scripts.

Throughput measured with redis-benchmark, and what else Redis 8 ships (depth)

50 clients with one request in flight each did about 33,000 to 35,000 operations a second (redis-benchmark, the tool that ships with Redis). Redis 8 also ships JSON documents, vector sets, time series and a query engine in the main server; HyperLogLog (approximate counts of unique items), bitmaps and geo indexes have existed for years. Each is a reason to keep more state in a store whose durability is weaker than your database's (below).

A leaderboard: a sorted set against a count in SQL

A sorted set is a hash table (member to score) plus a skip list, a sorted linked list with "express lane" links, so a member's position takes about log2(N) steps ({{Redis sorted sets|https://redis.io/docs/latest/develop/data-types/sorted-sets/}}: "most sorted set operations are O(log(n))"). In Postgres a rank is a count of the players above you, and the index visits one entry per player above. Measured with 100,000 players:

A rank in SQL costs more the lower the player stands; in a sorted set it costs the same everywhere

measured Postgres 16.2, index on (score DESC), SELECT count(*) FROM scores WHERE score > (SELECT score FROM scores WHERE user_id = $1): rank 3 took 6 page reads, rank 50,000 took 142 page reads, 4.67 ms; rank 95,359 took 266 page reads, 8.98 ms (server time). Redis ZREVRANK: median 91 µs wherever the player stands, from the client, so it includes the round trip. The top 10 is cheap in both: 3 page reads, 0.059 ms in Postgres, median 99 µs for ZRANGE lb 0 9 REV WITHSCORES. The set holds 100,000 members in 8.9 MB (about 93 bytes each, MEMORY USAGE) and takes score updates (ZINCRBY) at about 10,500 a second from one client.

When Postgres would still do
Top-N lists are an index read in Postgres. Exact ranks for everyone on every page view are what the sorted set is for; with a few thousand players, or ranks shown as "top 5%", Postgres (or a rank recomputed every minute) is fine.

Rate limiting, and why it needs atomicity

A rate limiter decides, on every request, whether a user may make another one. The obvious code reads the remaining allowance, decides in the application and writes back; run by many servers at once, two requests read the same allowance before either writes, and both pass. Predict: 16 processes each make 50 attempts against an allowance of 20; how many get through?

Read, decide, write lets nine times the limit through; one atomic script lets exactly the limit through

"Read, decide, write" in the application let 188 of 800 attempts through a limit of 20. The same limit as one Lua script inside Redis let exactly 20 through, because "while executing the script, all server activities are blocked during its entire runtime" ({{Redis docs, scripting with Lua|https://redis.io/docs/latest/develop/programmability/eval-intro/}}).

The script is a token bucket: up to capacity tokens, refilled at a steady rate, one taken per request, so bursts up to the capacity and a long-run average equal to the refill rate. It uses the server's clock (TIME) so every app server agrees on "now", and passes the bucket's name in KEYS, which Redis Cluster needs to route the script to the server that owns the key. Choosing among limiter algorithms and where limits sit in a system is {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}'s and {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}}'s.

Durability: what survives a crash


Redis writes to disk in two optional ways ({{Redis persistence|https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/}}). An RDB snapshot is a point-in-time copy written by a forked child every so often ("you should be prepared to lose the latest minutes of data"). The append-only file (AOF) logs every write; with appendfsync everysec, the default when AOF is on, it is flushed once a second, so a power cut loses about a second of writes; with always it is flushed before each reply. Measured (SET throughput from redis-benchmark, then a writer incrementing a counter for 3 seconds before kill -9):




RDB only: 40,255 acknowledged, all lost (no snapshot had been taken yet); AOF everysec: 50,324 acknowledged, 0 lost. A kill -9 is a process crash, not a power cut: the operating system still holds what Redis wrote, which is why AOF lost nothing. On macOS a flush does not force the drive's own cache, so always is cheaper here than on a Linux server with a real flush.



Replication: acknowledged writes that vanish


Redis copies writes to its replicas after replying to the client: replication is asynchronous. Step through the measured run: a primary and a replica on this laptop, the replica paused (as a long garbage-collection pause or a network problem would), 10 KB writes, the primary killed, the replica promoted.


"OK" from the primary is not "on the replica": a failover lost 4,947 of 5,000 acknowledged writes












The WAIT 1 500 call after the writes returned 0: it reports how many replicas confirmed, it does not make the writes safe ("WAIT does not make Redis a strongly consistent store", {{Redis WAIT|https://redis.io/docs/latest/commands/wait/}}). Jepsen measured the same with Sentinel failover in 2013 (56% of acknowledged writes lost; root atlas). So Redis must not be the only copy of anything you cannot rebuild.



Streams: a job queue that survives a crashed worker


A list makes a queue, but a worker that pops a job and crashes loses it. A stream is an append-only log; a consumer group hands each entry to one consumer and keeps it in a pending entries list until the consumer acknowledges it with XACK; another worker can claim an idle pending entry with XAUTOCLAIM. That is at-least-once delivery: a job can run twice, so it must be safe to repeat. Durable logs, the outbox pattern and Kafka are {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}'s; a Redis stream is the small version, with Redis's durability.

    What it costs
    Memory: everything lives in RAM, plus overhead per key (93 bytes per sorted-set member above). One thread executes commands, so a slow command (a KEYS *, a long script, a ZRANGE returning a million members) stalls every client. Durability and replication are weaker than a database's by default, as measured. Redis Cluster shards keys over 16,384 hash slots, and a multi-key command or script works only when all its keys are in one slot (use hash tags such as {user:7}:bucket). The licence changed in 2024 and Valkey forked (dated table in Depth); Valkey speaks the same protocol and commands as Redis 7.2, so the code here works on both.
    

    When Postgres would still do
    A counter updated a few times a second (UPDATE ... SET n = n + 1 is atomic); a job queue with SELECT ... FOR UPDATE SKIP LOCKED (measured on {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}}); a rate limit at tens of requests a second; top-N lists. Redis as a cache in front of Postgres (cache-aside, eviction, invalidation, stampedes) is {{Caching|n:3cd5c17b0d0d817ebd6ccadd4750c23a}}'s subject.
