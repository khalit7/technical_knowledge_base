2. One question, four storage layouts: "the latest 50 messages of a chat"

Opening a chat is the most frequent read of the chat product. The table below is the root page's 1M-message table (the same generator and seed) with one addition so that long chats exist: 2% of messages belong to 20 long-running chats, so chat 7 has measured messages spread over days. Because messages are appended in time order, a long chat's messages end up scattered through the whole table: in this table they sit on different 8 KB pages out of .

The animation runs the same request four ways. The first three are real EXPLAIN (ANALYZE, BUFFERS) runs on PostgreSQL 16.2; the fourth is the same rows loaded into Apache Cassandra 5.0.9 in a table designed for this question, read with tracing on. The strip is the table's data on disk drawn to scale: each cell is pages, and the lit cells are the ones the request had to read.

What changed between the second and third runs is only where rows live. An index tells the database where each of chat 7's rows is, but if they are scattered, it still reads one page per row: . Putting a chat's rows next to each other (CLUSTER rewrites the table in index order) makes the same 50 rows one page. That is the whole idea of a partition in a wide-column store or DynamoDB: rows that one question reads together are stored together, sorted the way the question wants them, and the layout is maintained on every write instead of by an occasional rewrite.


What each step costs
The index costs a little on every insert (the root and the {{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}} page measure it) and is the right fix in Postgres. CLUSTER took  seconds here but locks the table and is not maintained: new rows land at the end again, so it is a one-off, not a design. The Cassandra table answers this question and no other: "every message by message id" needs another table.


When Postgres would still do
Almost always, for this question: with the composite index the 50 rows came back in  ms on the server. A partitioned store earns its place when the writes outgrow one machine or must survive the loss of a whole data centre, not because one read is slow. Discord described its Cassandra message store at billions of messages in January 2017 and its move to ScyllaDB at trillions in March 2023 (the system design page's {{Case files|n:3c65c17b0d0d81048ae0dd14ac399b4d}} tab, "Trillions of messages"); section 6 shows their table.
