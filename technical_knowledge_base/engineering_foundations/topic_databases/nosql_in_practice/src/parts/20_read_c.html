2. One question, four storage layouts: "the latest 50 messages of a chat"

Opening a chat is the chat product's most frequent read. The table is the root page's 1M-message table (same generator and seed) plus 20 long-running chats holding 2% of the messages, so chat 7 has measured messages over days. Messages are appended in time order, so a long chat's rows end up scattered: they sit on different 8 KB pages out of . Predict before you step: with an index on (chat_id, created_at), how many table pages does Postgres read for 50 rows?

An index finds the rows; only storing them together makes the read one page

The first three are real EXPLAIN (ANALYZE, BUFFERS) runs on PostgreSQL 16.2; the fourth is the same rows in Apache Cassandra 5.0.9 in a table designed for this question, read with tracing on. The strip is the table's data on disk to scale: each cell is pages, lit cells were read. Measured: no index 19,347 page reads, 38 ms; index 57 page reads (49 table pages), 0.129 ms; after CLUSTER 9 page reads (1 table page), 0.043 ms.

The real plans and the Cassandra trace




An index tells the database where each of chat 7's rows is, but if they are scattered it still reads one page per row: . Putting a chat's rows next to each other (CLUSTER rewrites the table in index order) makes the same 50 rows one page. That is the whole idea of a partition in a wide-column store or DynamoDB: rows one question reads together are stored together, sorted the way the question wants, and the layout is maintained on every write instead of by an occasional rewrite.


What each step costs
The index costs a little on every insert ({{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}} measures it) and is the right fix in Postgres. CLUSTER took  seconds here but locks the table and is not maintained: new rows land at the end again, so it is a one-off, not a design. The Cassandra table answers this question and no other: "every message by message id" needs another table.


When Postgres would still do
Almost always, for this question: with the composite index the 50 rows came back in  ms on the server. A partitioned store earns its place when the writes outgrow one machine or must survive the loss of a whole data centre, not because one read is slow. Discord described its Cassandra message store at billions of messages in January 2017 and its move to ScyllaDB at trillions in March 2023 (the system design page's {{Case files|n:3c65c17b0d0d81048ae0dd14ac399b4d}} tab, "Trillions of messages"); section 6 shows their table.
