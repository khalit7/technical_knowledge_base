A laptop has no network between client and server, so its absolute timings are best cases; the counts (pages, rows, items, partitions) are what carries over to production.

"NoSQL" is not one thing. It is a name for databases that are not relational: they do not store your data as normalised tables joined at query time. Each family below gave up something relational databases offer (joins, ad hoc queries, multi-row transactions, a fixed schema) to get something one machine running Postgres cannot easily give: memory speed, writes spread over hundreds of machines, a record read as one unit, cheap time ranges, cheap hops between connected things. The trade is the same every time: you design the storage around the questions you will ask, and a question you did not plan for becomes slow or impossible.

The five habits of a professional
  1. Write the access patterns down first: every question the app will ask, with its inputs, its sort order and how often it runs. The schema is designed from that list, not from the shape of the data.
  2. Choose the partition key from the busiest question and check its spread: no key may get a large share of the traffic, and no partition may grow without bound (add a time bucket).
  3. Count what a request reads, not what it returns: a filter after a scan still reads, and pays for, every item.
  4. Know the durability and replication defaults: Redis acknowledges before the replica has the write; Cassandra flushes its commit log every 10 seconds; MongoDB reads at "local" by default.
  5. Keep Postgres as the source of truth until a measurement says otherwise, and treat every other store as a copy you can rebuild.

1. Queries first: the one idea behind every family

The problem

In a relational database you design tables from the data (one table per kind of thing, each fact stored once: normalisation), and the database works out at query time how to answer any question, joining tables as needed. That is what makes it flexible, and it is why it lives on one machine: a join needs the rows of both tables in one place. When the data or the traffic outgrows one machine, the data must be split across machines, and a question that needs rows from many machines becomes slow.

The idea

The non-relational families turn the design around. You first write down the access patterns: each question the application asks, with what it knows (a user id, a chat id) and what it wants back (the newest 50 messages, sorted). Then you store the data so that each question reads one contiguous piece of storage, usually by giving every record a partition key (which group, and so which machine, it belongs to) and a sort key (its order inside the group). Data needed by two different questions is often stored twice, on purpose: denormalisation.

3. Key-value in memory: Redis


The problem


Some questions are tiny and asked constantly: "has this user sent more than 20 requests this minute?", "what rank is this player?", "is there a job waiting?". Each answer is a few bytes, but asked on every request it becomes most of the database's work, and some (a rank among 100,000 players) are expensive in SQL however you index them.


How it works


Redis is a server that keeps every key and its value in memory. A value is not just a string: it is one of a handful of data structures, each with its own commands, and the server executes commands one at a time on a single thread, so every command is atomic: no other client's command runs halfway through it (the root's Database atlas tab has Redis's row with sources). The version measured here is Redis 8.8.0 (conda-forge build) in its default configuration unless stated.

How fast, measured




On this laptop one GET took a median 52.1 µs (p99 121 µs) over 20,000 calls from Python: almost all of it is the client library and the loopback network, not Redis. That is why one client does only about 16,000 to 18,000 operations a second, 50 clients about 33,000 to 35,000 (one request in flight each), and 50 clients that pipeline 16 commands per round trip (send many, then read all the replies) over 520,000 (redis-benchmark, the tool that ships with Redis). In production, the network between your app and Redis dominates (Jeff Dean's classic figure is 0.5 ms for a round trip inside one data centre, and Microsoft aims for under about 2 ms between availability zones: the system design page's Numbers to know tab), so the habits that matter are fewer round trips: pipelines, multi-key commands and scripts.


A leaderboard with a sorted set


A sorted set keeps members ordered by score. Redis implements it as two structures at once: a hash table (member to score) and a skip list, a sorted linked list with extra "express lane" links that let a search skip ahead, so finding a member's position takes about log2(N) steps (Redis sorted sets: "most sorted set operations are O(log(n))"). When Postgres would still do
Top-N lists ("the 10 best") are an index read in Postgres. Exact ranks for everyone, asked on every page view, are what the sorted set is for; with only a few thousand players, or ranks shown as "top 5%", Postgres (or a rank recomputed every minute) is fine.


Rate limiting, and why it needs atomicity


A rate limiter decides, on every request, whether a user may make another one. The obvious code reads the user's remaining allowance, decides in the application, and writes the new value back. Run by many servers at once, two requests read the same allowance before either writes, and both pass. Measured: 16 processes each made 50 attempts against an allowance of 20.

Streams: a job queue that survives a crashed worker


A list makes a queue, but a worker that pops a job and crashes loses it. A stream is an append-only log; a consumer group hands each entry to one consumer and remembers it in a pending entries list until the consumer acknowledges it with XACK. Measured run, real ids:


    

    That is at-least-once delivery: a job can run twice (the first worker may have done the work and died before acknowledging), so the job must be safe to repeat. Durable logs, the outbox pattern and Kafka are on Queues, streams and async work; a Redis stream is the small version, with Redis's durability.
    

    Durability: what survives a crash
    

    Redis writes to disk in two optional ways (Redis persistence). An RDB snapshot is a point-in-time copy written by a forked child every so often ("you should be prepared to lose the latest minutes of data"). The append-only file (AOF) logs every write; with appendfsync everysec, the default when AOF is on, the file is flushed to disk once a second, so a power cut loses about a second of writes; with always it is flushed before each reply. Measured (SET throughput from redis-benchmark, then a writer incrementing a counter for 3 seconds before kill -9):
    

    

    A kill -9 is a process crash, not a power cut: the operating system still holds what Redis wrote, which is why AOF lost nothing here. A power cut loses whatever was not yet flushed, up to about a second with everysec. On macOS a flush does not force the drive's own cache (the transactions page measures the same caveat for Postgres), so always is cheaper here than on a Linux server with a real flush.
    

    Replication: acknowledged writes that vanish
    

    Redis copies writes to its replicas after replying to the client: replication is asynchronous. If the primary dies before a replica has a write and the replica is promoted, the write is gone even though the client was told "OK". Measured: a primary and a replica on this laptop; the replica is paused (as a long garbage-collection pause or a network problem would), the primary acknowledges 5,000 writes of 10 KB, the primary is killed, the replica resumes and is promoted.
    

    

    The WAIT 1 500 call made after the writes returned 0: it reports how many replicas confirmed, it does not make the writes safe, and Redis's own documentation says "WAIT does not make Redis a strongly consistent store" (Redis WAIT). Jepsen measured the same with Sentinel failover in 2013 (56% of acknowledged writes lost; root atlas). So Redis must not be the only copy of anything you cannot rebuild.
    

    Licence: Redis and Valkey
    Redis moved from the BSD licence to a dual source-available licence (RSALv2 or SSPLv1) from version 7.4 on 20 March 2024; the Linux Foundation launched Valkey, a BSD fork of Redis 7.2.4, on 28 March 2024, backed by AWS, Google Cloud, Oracle and others; Redis 8 added AGPLv3 as a third option on 1 May 2025 (all in the root's Database atlas, with sources). Valkey speaks the same protocol and commands as Redis 7.2, so clients and the code on this page work unchanged; Redis 8-only features (built-in JSON, vector sets, the query engine) do not exist in Valkey under those names.
    

    What it costs
    Memory: everything lives in RAM, plus overhead per key (93 bytes per sorted-set member above). One thread executes commands, so a slow command (a KEYS *, a long script, a ZRANGE returning a million members) stalls every client. Durability and replication are weaker than a database's by default, as measured above. Redis Cluster shards keys over 16,384 hash slots, and a multi-key command or script works only when all its keys are in one slot (use hash tags such as {user:7}:bucket).
    

    When Postgres would still do
    A counter updated a few times a second (UPDATE ... SET n = n + 1 is atomic); a job queue with SELECT ... FOR UPDATE SKIP LOCKED (measured on Transactions and concurrency); a rate limit at tens of requests a second; top-N lists. Using Redis as a cache in front of Postgres (cache-aside, eviction, invalidation, stampedes) is the Caching page's subject.
    

    

    

    4. Key-value at any scale: DynamoDB and single-table design
    

    The problem
    

    Redis is one machine's memory. Suppose the chat product needs a store that grows without limit, survives the loss of a data centre, and has no servers, upgrades or vacuum to manage, and every request already knows the key it wants (a user id, a chat id). That is what Amazon DynamoDB sells: a managed, partitioned key-value and document store, billed per request or per reserved capacity.
    

    4.1 The model
    

      

    • A table holds items (a map of attributes, at most 400 KB each). Each item has a primary key: a partition key, optionally with a sort key. Items with the same partition key form an item collection, stored together and sorted by sort key.
      • 

    • DynamoDB hashes the partition key to pick a partition; each partition is a Multi-Paxos group of three replicas, each with a write-ahead log and a B-tree (root atlas; Elhemali et al., Amazon DynamoDB, USENIX ATC 2022). Partitions split automatically as data and traffic grow.
      • 

    • Reads: GetItem (the full key: one item), Query (one partition key, optionally a sort key condition such as begins_with or between; returns items in sort order, ascending or descending, up to 1 MB per page) and Scan (every item in the table). Nothing else: no joins, no query on a non-key attribute without an index.
      • 

    • Consistency: reads are eventually consistent by default (they may miss a write from the last moment); a strongly consistent read costs twice as much and is not available on global secondary indexes. Single-item writes are atomic; transactions cover up to 100 items in one Region and cost double (root atlas, claim corrected).
      • 

    • Capacity is counted in units: one read unit is a strongly consistent read of up to 4 KB (an eventually consistent read is half a unit); one write unit is a write of up to 1 KB. Each partition serves at most 3,000 read units and 1,000 write units a second (AWS, partition key design).
      • 

    

    4.2 Single-table design, step by step on the chat product
    

    Because there are no joins, a page that needs a user, their chats and a chat's messages would need several requests if each kind of item lived in its own table, keyed by its own id. Single-table design puts every kind of item in one table and chooses keys so that the items one screen needs share a partition key and come back in one Query, sorted (Alex DeBrie, The What, Why, and When of Single-Table Design, 2020-02-05). The keys are generic strings (PK, SK) holding a type prefix and an id. Built step by step from the access patterns of section 1:
    

      

    1. Open a chat (latest 50 messages). The request knows the chat id and wants messages newest first, so messages get PK = CHAT#<chatId> and SK = MSG#<createdAt>#<messageId>: an ISO timestamp sorts correctly as a string, and the id breaks ties. Query PK = CHAT#7, SK begins_with MSG#, descending, limit 50.
      2. 

    2. Usage per day. The request knows the user and a month: PK = USER#<userId>, SK = USAGE#<day>, one item per user per day updated with an atomic ADD. Query SK begins_with USAGE#2025-09.
      3. 

    3. User profile. PK = USER#<userId>, SK = PROFILE: it shares the user's partition with the usage items, so one Query could fetch the profile and the month together.
      4. 

    4. Chat list, most recently active first. Chats get PK = USER#<userId>, SK = CHAT#<chatId>, but that sorts by id, not by activity. A global secondary index (GSI1) re-keys the same items: GSI1PK = USER#<userId>, GSI1SK = LAST#<lastMessageAt>#<chatId>. Sending a message updates the chat's GSI1SK, and the index moves it to the top.
      5. 

    5. Log in by email, emails unique. A lookup item PK = EMAIL#<email> holds the user id. Registration writes the user and the lookup item in one transaction, each with the condition attribute_not_exists(PK), so a second account with the same email fails.
      6. 

    6. Admin: every message of one model on one day. No key can serve this without a partition that receives a quarter of all writes; it goes to an analytics copy (DynamoDB exports a table to S3 in full or incrementally, every 15 minutes to 24 hours, AWS quotas).
      7. 

    

    Measured on DynamoDB Local 3.3.1 (AWS's downloadable version of the API) with the chat data: 400 users, 2,999 chats, 49,517 messages, 54,775 items in all. DynamoDB Local runs the real API, key rules and capacity accounting, but not the service's partitions, throughput limits or latency, so only counts are shown.
    

    

    Every question on the list is one request that reads only the items it returns. The two wrong ways show what a missing key costs: a Scan with a filter for chat 7 read 1,000 items in its first page and returned none of them (the filter runs after the read, and you pay for every item read), and answering the admin question by scanning read all 54,775 items in 9 pages of 1 MB for 1,111.5 read units. At a billion items the same scan would read a billion items.

    4.3 Secondary indexes
    

    A global secondary index is a second copy of chosen attributes under a different key, maintained by DynamoDB. It is updated asynchronously ("eventually consistent fashion ... within a fraction of a second, under normal conditions", AWS, GSI), so a chat list read right after sending a message can still show the old order; a strongly consistent read on it is refused (the error above). Each index is paid for on every write: changing an indexed key costs two index writes (delete the old entry, put the new one), and if an index lacks write capacity, writes to the table are throttled. A table has at most 20 GSIs by default and 5 local secondary indexes (same partition key, different sort key, strongly consistent, but they cap an item collection at 10 GB and stop adaptive capacity from splitting it).
    

    4.4 Writes, conditions and transactions
    

    Measured: one message put cost 1 write unit (a message item is about 173 bytes as DynamoDB counts size); the transaction that writes the message and moves the chat to the top of GSI1 cost 8 write units as DynamoDB Local accounted it. The documented rules give 6 (2 for each of the two transactional writes, 2 for moving the index entry), so Local appears to charge the index move at the transactional rate as well; unconfirmed against the real service. Registering a second account with an existing email failed with TransactionCanceledException, reasons [None, ConditionalCheckFailed]: the user item would have been fine, the email item already existed, so neither was written. An item over 400 KB was refused. Chat messages fit easily; a long document or a file does not, and goes to S3 with its key stored in the item.
    

    4.5 Capacity, price and hot partitions
    

    Two billing modes, priced for US East (N. Virginia), standard table class, as read on 4 October 2026: on-demand charges $0.625 per million write units and $0.125 per million read units (AWS on-demand pricing); provisioned charges for reserved units per hour, $0.00065 per write unit-hour and $0.00013 per read unit-hour, with auto scaling to follow load (AWS provisioned pricing); storage is $0.25 per GB-month. On-demand is simplest and right for spiky or unknown traffic; provisioned is cheaper for steady traffic you can predict. The lab's calculator prices the chat product's messages both ways from the units measured above.
    

    The limit that bites is per key, not per table. All of one chat's messages share a partition key, so one very busy group chat can take at most 1,000 one-KB writes a second. DynamoDB keeps up to 300 seconds of unused capacity for bursts, and adaptive capacity moves busy items onto partitions of their own, "provided that traffic does not exceed ... the partition maximum capacity" (AWS, burst and adaptive capacity). Past that, the fix is write sharding: spread one hot key over CHAT#7#0 to CHAT#7#9 and have readers query all ten and merge. Discord hit the same wall in Cassandra with its busiest channels (section 6).
    

    Single table or several?
    DeBrie lists the costs of single-table design: a steep learning curve, new access patterns that need data migrations, and exports for analytics that are hard to read ("looks more like machine code than a simple spreadsheet", quoted there); he advises against it for early-stage applications that still need flexibility and for GraphQL back ends, whose resolvers issue separate requests anyway. AWS's own guidance makes the same trade (AWS Compute Blog, 2021-07-26). A newer feature narrows the gap: GSIs can now use up to four attributes each for the partition and sort keys, so an index no longer needs a hand-built composite string (DynamoDB Local added it in January 2026).
    

    What it costs
    The schema is the list of access patterns: a new question means a new index (written on every write) or a migration. Ad hoc questions, joins and aggregates belong elsewhere (export to S3, then DuckDB, Athena or a warehouse). Indexes are eventually consistent. A busy key is capped. And it runs only on AWS (DynamoDB Local is for development).
    

    When Postgres would still do
    Whenever one Postgres server (with replicas for reads) can carry the load and the team would rather keep SQL's flexibility: that covers most products for years. DynamoDB wins when you are on AWS, want no database to operate, and either traffic is huge and key-shaped or it is tiny and spiky (on-demand at near-zero cost when idle).
    

    

    

    5. Documents: MongoDB, and Postgres jsonb beside it
    

    The problem
    

    Some records do not have one fixed shape. A tool call in the chat product carries different arguments for each tool; a user's settings grow a new field every month. Splitting each shape into its own table, or adding a nullable column per field, gets clumsy. A document stores the record as one nested JSON-like value, fields and arrays included, read and written as a unit.
    

    How MongoDB models data
    

    MongoDB stores documents in collections, in BSON (binary JSON with real dates and integers), each with a unique _id. You can index any field, including fields inside arrays, and query with a JSON query language or an aggregation pipeline (a list of stages: filter, group, sort, join). Underneath, the WiredTiger engine keeps B-trees with compression and a journal (a write-ahead log); a replica set has one primary and copies; sharding splits a collection over machines by a shard key you choose (root atlas). Measured here: MongoDB 8.0.23 (conda-forge) as a one-member replica set, because transactions need one; MongoDB 9.0 reached general availability on 28 September 2026 (root atlas), after these runs were set up. The server is under the SSPL, a source-available licence, since 16 October 2018.
    

    Embed or reference? Worked on chats and messages
    

    The central design choice is whether related data lives inside a document (embedding) or in its own documents that point back (referencing). MongoDB's guidance: embed when you have a "contains" relationship, "query pieces of information together" and update them together; reference when "the child side of the relationship has high cardinality" or "your embedded data grows without bounds" (MongoDB, embedding vs references). A chat's messages are the textbook hard case: always read together, and growing without bound. Both shapes were loaded with the same 1M messages:

    6. Wide-column: Cassandra and ScyllaDB
    

    The problem
    

    Suppose the chat product's messages arrive faster than one primary database can write them, users are on several continents, and losing a whole data centre must not stop anyone sending messages. A single-primary database cannot give all three. Apache Cassandra (and ScyllaDB, its C++ reimplementation) spreads every table over many equal machines, with no primary at all.
    

    How it models data
    

      

    • A table's PRIMARY KEY ((a, b), c, d) has two parts. The partition key (a, b) is hashed to a number called a token; the machines (nodes) form a ring in which each owns ranges of tokens, so the token decides which nodes hold the partition. The clustering columns c, d sort the rows inside the partition.
      • 

    • Each partition is copied to RF nodes (the replication factor, usually 3, placed in different racks or data centres). Every node accepts reads and writes for any key and forwards them to the replicas: there is no leader (root atlas).
      • 

    • Storage is an LSM-tree: a commit log and an in-memory table, flushed to immutable sorted files (SSTables) that background compaction merges (Storage engines and indexes measures LSM-trees on RocksDB).
      • 

    • The query language, CQL, looks like SQL but has no joins, and a query must name the partition key: "data is modeled around specific queries", one table per query, with data duplicated across tables on purpose (Cassandra data modelling).
      • 

    

    Designing the "latest 50" table

    Tunable consistency, with the quorum arithmetic
    

    Each request chooses how many of the RF replicas must answer: ONE, QUORUM (a majority: floor(RF/2) + 1), LOCAL_QUORUM (a majority inside the local data centre) or ALL (Cassandra, Dynamo architecture). If the replicas a write waited for (W) and the replicas a read asks (R) must overlap, W + R > RF, every read meets at least one replica with the latest acknowledged write. The default is ONE, so by default a read can be stale (root atlas). Choose levels and knock nodes out:
    

    

    





    

    

    

    

    Three things this arithmetic does not say. Conflicting writes are resolved by timestamp, last write wins, so two clients updating the same cell lose one update silently (Jepsen showed acknowledged writes lost this way in 2013; root atlas). For compare-and-set ("insert only if absent") Cassandra has lightweight transactions, which run a Paxos consensus round among the replicas for each operation and so cost extra round trips. And multi-partition ACID transactions (Accord) arrive only with Cassandra 6.0, still in alpha (root atlas).
    

    Tombstones: why deleting slows reads
    

    An LSM-tree cannot erase a row in place: the row may sit in several immutable files on several replicas. So a delete writes a tombstone, a marker that hides older data, and the tombstone is kept for gc_grace_seconds (default 864,000 seconds, 10 days) so that every replica learns of it; a replica that misses the delete for longer can bring the data back ("zombie" rows) (Cassandra, tombstones). Until compaction drops them, a read has to step over every tombstone in its way. Measured: a partition of 130,000 messages, the newest ones deleted one by one, then "the latest 50" read:

Discord's 2017 post describes hitting this six months into production: a public channel with millions of deleted messages and one remaining message made Cassandra "scan millions of message tombstones", causing 10-second garbage-collection pauses; they cut the grace period from 10 days to 2 and stopped re-reading empty buckets (same Discord post). The lesson: a table used like a queue (insert, read, delete) is the classic anti-pattern; expire data with a TTL in time-ordered tables, and choose compaction to match.

    ScyllaDB and the others
    

    ScyllaDB reimplements Cassandra in C++ with one shard per CPU core and no garbage collector, speaks CQL (and a DynamoDB-compatible API), and is what Discord moved to: 177 Cassandra nodes became 72 ScyllaDB nodes (the system design page's Case files, "Trillions of messages", March 2023).     What it costs
    One table per question, written in step by your code; no joins; no ad hoc queries; deletes that slow reads for 10 days; last-write-wins conflicts; repairs and compaction to operate, on many machines.
    

    When Postgres would still do
    Until write volume or the need to survive a data-centre loss with no failover pause actually exceeds what one primary (plus replicas, plus partitioning by time) can do. Most products never get there; Discord did at billions of messages.
    

    

    

    7. Time series: metrics, events and what makes them special
    

    The problem
    

    The operations team wants a dashboard: requests per minute, median latency and tokens per model, for the last hour, refreshed every few seconds, and a 30-day trend. Every chat request produces one measurement. That data has a peculiar shape:
    

      

    • Append-only, in time order: rows are never updated, and new rows always have the newest timestamp.
      • 

    • Read by time range: almost every query says "the last hour" or "this month", grouped into time buckets.
      • 

    • Old data matters less: last hour at full detail, last month per minute, last year per hour (downsampling), and then deleted (retention).
      • 

    

    Every time-series database exploits the same three facts: store data in time-sliced chunks so a time range touches few chunks; precompute rollups; and expire data by dropping whole chunks instead of deleting rows. All three can be done in plain Postgres, which is what was measured here (5,184,000 request rows over 30 days: 4 models, 8 servers, about 2 a second).

    8. Graph: Neo4j, Kuzu, and the recursive query
    

    The problem
    

    Some questions are about connections: "people you may know" (friends of friends), "is this new account linked to a known fraud ring within four steps", "how is user A connected to user B". In tables, each step along a connection is a join, and the number of steps is not known when you write the query.
    

    How graph databases model data
    

    A property graph has nodes (a user, a chat) and relationships between them (FRIEND, OWNS), each with a type, a direction and properties. Queries are written as patterns in Cypher (Neo4j also accepts GQL, the ISO graph query language that grew out of it): MATCH (u:User {uid: $u})-[:FRIEND*1..3]-(v) RETURN count(DISTINCT v) reads "from user u, follow one to three FRIEND relationships in either direction". Neo4j stores each relationship as a record that points directly at its two nodes and at the next relationship of each node, so following a relationship is a pointer lookup rather than an index search, a design its authors call index-free adjacency (root atlas; Robinson, Webber and Eifrem, Graph Databases, 2nd edition, O'Reilly 2015, chapter 6).
    

    Measured: friends of friends, on the same graph
    

    A synthetic social graph built the way real ones grow (each new user befriends 10 existing users, chosen in proportion to how many friends they already have):  users,  friendships, a median of  friends but a most-connected user with . For 10 random users, count everyone within k hops, on PostgreSQL 16.2 (two ways), Neo4j Community  and Kuzu , an embedded graph engine (a library, like DuckDB):
    

    

    

    

    

    On this graph and this question, the graph engines did not win: all four agree on every count, Postgres was fastest up to three hops, and at four hops, where every engine touches nearly the whole graph, Neo4j was only  than Postgres's better query. All times are measured from the client (Neo4j and Postgres over a local connection, Kuzu in the same process). The work is set by the answer: by 3 hops a typical user reaches about a third of the graph, by 4 hops nearly all of it, and every engine must touch those rows. Two details matter for writing it in SQL. A naive recursive query that carries no memory of where it has been (UNION removes only exact duplicate (user, depth) rows) still finished here, but on denser graphs it revisits the same users along many paths; writing one DISTINCT join per hop keeps each frontier small. Neo4j's planner made the same move by itself: its profile shows VarLengthExpand(Pruning,BFS,All), a breadth-first expansion that drops nodes already seen.

    The SQL that carries the path is short but explores every path rather than every user, which is why it slows down sharply with depth; the version that keeps a visited set has to be driven from application code, one query per hop. Graph databases earn their place when such questions are the product (fraud rings, recommendation paths, permissions inherited through groups, knowledge graphs), when the depth is variable or large, and when patterns with several node and relationship types ("accounts that share a device with an account that shares a card with a flagged account") would be a page of SQL.
    

    Caveats with dates
    Neo4j runs transactions at read committed: "a transaction that reads a node/relationship does not block another transaction from writing" it, so lost updates are possible unless a write lock is taken; Cypher takes one automatically for SET n.x = n.x + 1 (Neo4j, concurrent data access). Clustering is Enterprise-only (Community is GPLv3; root atlas). Kuzu's GitHub repository was archived by its owners on 10 October 2025; its last release, 0.11.3, still works but receives no fixes, so treat it as a demonstration, not a dependency (kuzudb/kuzu). Apache AGE adds Cypher inside Postgres, with traversals planned as joins (root atlas).
    

    When Postgres would still do
    Fixed one to three hops (friends, friends of friends, a group's members' chats): one join per hop with an index on both ends, measured above. Bounded hierarchies (an org chart, folders) with a recursive CTE. Move to a graph database when variable-depth path questions are central and frequent, or the pattern queries become unmaintainable in SQL.
    

    


    

    9. Embedded key-value engines: RocksDB and LMDB
    

    Every database above sits on a storage engine: the library that turns "put this key and value" into bytes on disk. Two are worth knowing by name because you will meet them inside other systems, and occasionally use one directly.
    

    

    RocksDB (11.8)
    An embedded LSM-tree: writes go to a write-ahead log and a memtable, flush to sorted files, and compaction merges them in the background. Fast writes, tunable read, write and space amplification, and a lot of knobs. Inside CockroachDB (via Pebble, its Go port), TiKV, Kafka Streams' state stores and many others. By default its WAL is not flushed to disk on every write, so a machine crash can lose the last writes (root atlas). The Storage engines and indexes page measures its write, read and space amplification against Postgres.
    

    LMDB (1.0)
    A copy-on-write B+tree in one memory-mapped file: no WAL, no compaction, readers never block and see a consistent snapshot, but only one writer at a time. Very fast reads from many threads or processes; commits are flushed by default. LMDB 1.0.0 arrived on 30 June 2026 after the long 0.9 line (root atlas).
    

    

    Reach for one directly only when you are building a storage component (a queue, a cache with persistence, an index) inside one process and want neither a server nor SQL. Otherwise SQLite (rows, SQL, one writer) and DuckDB (columns, analytics), on the root page, are the embedded databases to use.
    

    

    

    Choosing, and running them in production
    

    How pros decide
    

      

    1. Start with Postgres as the source of truth and write down the access patterns (section 1). Most of the families' tricks exist in Postgres in smaller form: a composite index (section 2), jsonb (section 5), partitions and rollups (section 7), a join per hop (section 8), SKIP LOCKED queues.
      2. 

    2. Add a store only for a measured problem, named in one sentence: "ranks for 100,000 players on every page view cost 9 ms each" (Redis); "message writes exceed one primary" (Cassandra, ScyllaDB or DynamoDB); "every dashboard query scans 30 days" (a rollup, then a time-series or column store).
      3. 

    3. Treat every extra store as a copy that can be rebuilt from the source of truth, fed by an outbox or change data capture (Queues, streams and async work), with its own backups, monitoring and on-call knowledge. "Polyglot persistence" (several stores, each for what it does best) is real at scale and an expensive habit before it.
      4.

    Common mistakes
    

    Choosing the database before listing the questions
    The family follows from the access patterns. A store chosen for its reputation, before the list exists, leaves the questions nobody planned for as scans (section 4) or new tables (section 6).
    

    Read, decide, write in the application
    Measured: 188 requests passed a limit of 20. Use the store's atomic operation (INCR, a Lua script, a conditional write, UPDATE ... SET n = n - 1 WHERE n > 0).
    

    Redis as the only copy
    A failover lost 4,947 of 5,000 acknowledged writes here; an RDB-only server lost every write since its last snapshot. Keep the source of truth in a database.
    

    Believing a filter makes a scan cheap
    DynamoDB charges for items read, not returned: a Scan that returned nothing still read 1,000 items in its first page.
    

    A partition key that concentrates traffic
    The current date, a tenant with most of the traffic, one celebrity chat. Every partition has a ceiling (1,000 writes a second in DynamoDB); spread with a suffix or rethink the key.
    

    Partitions or documents that grow forever
    A chat document hit the 16 MB limit at 15,220 messages; a Cassandra partition per chat grows without limit. Bucket by time or count.
    

    Using Cassandra as a queue, or deleting in bulk
    5,000 tombstones made a read about nine times slower; 101,000 made it fail. Prefer TTLs on time-ordered tables with TimeWindow compaction, and never a read-and-delete queue.
    

    "Schemaless" without validation
    Without a validator, every reader must handle every shape ever written. Add $jsonSchema or keep the fixed fields as Postgres columns.
    

    Reading your own write from an index or replica
    DynamoDB GSIs, MongoDB secondaries, Redis replicas and Cassandra at ONE can all return data from before your write. Read from the primary, or use a strong read where one exists, for the request right after a write.
    

    User ids as metric labels
    One label with 100,000 values multiplies every metric's series by 100,000 (the calculator in section 7). Per-user detail goes in logs or an events table.
    

    Deleting old time-series rows with DELETE
    Measured: 1.9 s and 65 MB of log for 7 days, and the table did not shrink; dropping 7 daily partitions took 0.06 s.
    

    A graph database for two hops
    Friends of friends was faster in Postgres than in either graph engine here. Graph databases pay off for paths and variable-depth patterns.

    Hot partitions and what it costs
    

    Every partition serves at most 3,000 read units and 1,000 write units a second (DynamoDB docs, partition key design). A key that concentrates traffic, such as one very busy group chat or "all messages of model X today", hits that ceiling however large the table is. Adaptive capacity moves busy items onto their own partitions, but a single key still cannot pass the per-partition maximum (burst and adaptive capacity).
