The idea in one screen

Every non-relational family stores together, in the order wanted, what one planned question reads, so that question stays one cheap read at any scale; the price is that a question you did not plan becomes a scan, a new table or impossible. That is why Postgres stays the default until a measurement says otherwise.

Fig. 1 puts the six families side by side; in each, the part one planned question reads turns orange and streams to the app. The shapes are drawn to explain (illustrative); the numbers are this page's measurements.

  1. Six layouts. Key-value in memory, key-value partitioned, document, wide-column, time series, graph: each lays its data out around the questions it expects.
  2. Redis. A key points at a data structure in memory (a hash, a sorted set, a stream); one atomic command reads or changes it, here a rank from a sorted set.
  3. DynamoDB. The partition key is hashed to pick a partition; the items of CHAT#7 sit there together in sort-key order, so a Query returns the newest ones in one request.
  4. Document. The chat is one document read whole: its metadata and a bounded subset of messages embedded, the unbounded messages referenced as documents of their own.
  5. Wide-column. The partition key (chat 7, bucket 3) is hashed to a token on a ring of nodes, copied to three replicas, and its rows are stored sorted newest first.
  6. Time series. Data is cut into one chunk per day: the last hour reads today's chunk, and retention drops whole old chunks instead of deleting rows.
  7. Graph. Users are nodes joined by FRIEND relationships; a path query follows pointers hop by hop: the measured shortest path from user 24204 to user 24891 took 4 hops.

Each family makes one shape of question cheap by how it lays data out, and pays for every other shape

Key-value in memory

Redis 8.8, Valkey

Cheap: counters, rate limits, leaderboards, queues hit thousands of times a second; pick the data structure that answers the question (a sorted set for ranks); every command is atomic.

Hard: data must fit in memory; replication is asynchronous, so a failover lost acknowledged writes here.

Postgres still does it: a counter row with UPDATE ... SET n = n + 1, a job queue with SKIP LOCKED, at low rates.

Key-value, managed and partitioned

DynamoDB

Cheap: any planned question is one request at any scale, with no servers to run; list the access patterns first, then choose partition and sort keys (often one table for everything).

Hard: a question you did not plan becomes a scan of the whole table; one busy key is capped at 1,000 writes a second.

Postgres still does it: you are not on AWS at that scale, or your questions still change every week.

Document

MongoDB 8.0

Cheap: records whose shape varies, read and written as one unit; embed what is read together, reference what grows without bound.

Hard: a document is capped at 16 MB; appends grow the document; cross-document invariants need transactions.

Postgres still does it: almost always: a jsonb column next to normal columns (measured in section 5).

Wide-column

Cassandra 5.0, ScyllaDB

Cheap: writes beyond one machine, many regions, no single point of failure; one table per query, the partition key groups what it reads, the clustering key sorts it.

Hard: no joins, no ad hoc queries; deletes leave tombstones that later reads must skip.

Postgres still does it: while one server keeps up with the writes: the root measured 2,133 to 9,212 small write transactions a second on this laptop, depending on whether each commit is really flushed to disk.

Time series

Postgres partitions, Prometheus, TimescaleDB, ClickHouse

Cheap: appends in time order, recent time ranges, rollups, dropping whole partitions for retention.

Hard: anything that is not a time range; high cardinality (a label per user) explodes memory.

Postgres still does it: native partitioning plus a rollup table, measured in section 7.

Graph

Neo4j 2026.09, Kuzu 0.11

Cheap: questions of unknown or large depth over connected data: paths, fraud rings, patterns written in Cypher.

Hard: another system to run; a fixed one or two hops is no faster than Postgres.

Postgres still does it: fixed one or two hops: a join per hop is fast (measured in section 8).

The five habits of a professional
  1. Write the access patterns down first: every question, with its inputs, sort order and frequency. The schema comes from that list, not from the shape of the data.
  2. Choose the partition key from the busiest question and check its spread: no key may get a large share of the traffic, and no partition may grow without bound (add a time bucket).
  3. Count what a request reads, not what it returns: a filter after a scan still reads, and pays for, every item.
  4. Know the durability and replication defaults: Redis acknowledges before the replica has the write; Cassandra flushes its commit log every 10 seconds; MongoDB reads at "local" by default.
  5. Keep Postgres as the source of truth until a measurement says otherwise, and treat every other store as a copy you can rebuild.

1. Queries first: the one idea behind every family

A relational database is designed from the data (each fact stored once: normalisation) and answers any question by joining at query time. A join needs the rows of both tables in one place, which is why it lives on one machine. The non-relational families turn the design around: you write down the access patterns first, then store the data so that each question reads one contiguous piece of storage, by giving every record a partition key (which group, and so which machine) and a sort key (its order inside the group). Data needed by two questions is often stored twice: denormalisation. The chat product's questions run through the whole page:

          3. Key-value in memory: Redis
          

          Some questions are tiny and asked constantly: "has this user sent more than 20 requests this minute?", "what rank is this player?", "is there a job waiting?". Redis keeps every key and value in memory, and a value is one of a handful of data structures, each with its own commands. The server executes commands one at a time on a single thread, so every command is atomic: no other client's command runs halfway through it. Each is a reason to keep more state in a store whose durability is weaker than your database's (below).
          


          

          A leaderboard: a sorted set against a count in SQL
          

          A sorted set is a hash table (member to score) plus a skip list, a sorted linked list with "express lane" links, so a member's position takes about log2(N) steps (Redis sorted sets: "most sorted set operations are O(log(n))"). In Postgres a rank is a count of the players above you, and the index visits one entry per player above. Measured with 100,000 players:
          

          When Postgres would still do
          Top-N lists are an index read in Postgres. Exact ranks for everyone on every page view are what the sorted set is for; with a few thousand players, or ranks shown as "top 5%", Postgres (or a rank recomputed every minute) is fine.

          Rate limiting, and why it needs atomicity
          

          A rate limiter decides, on every request, whether a user may make another one. The obvious code reads the remaining allowance, decides in the application and writes back; run by many servers at once, two requests read the same allowance before either writes, and both pass. Predict: 16 processes each make 50 attempts against an allowance of 20; how many get through?
          

          The script is a token bucket: up to capacity tokens, refilled at a steady rate, one taken per request, so bursts up to the capacity and a long-run average equal to the refill rate. It uses the server's clock (TIME) so every app server agrees on "now", and passes the bucket's name in KEYS, which Redis Cluster needs to route the script to the server that owns the key. Choosing among limiter algorithms and where limits sit in a system is Reliability engineering's and Capacity planning and performance's.

          Durability: what survives a crash
          

          Redis writes to disk in two optional ways (Redis persistence). An RDB snapshot is a point-in-time copy written by a forked child every so often ("you should be prepared to lose the latest minutes of data"). The append-only file (AOF) logs every write; with appendfsync everysec, the default when AOF is on, it is flushed once a second, so a power cut loses about a second of writes; with always it is flushed before each reply. Measured (SET throughput from redis-benchmark, then a writer incrementing a counter for 3 seconds before kill -9):
          

          

          RDB only: 40,255 acknowledged, all lost (no snapshot had been taken yet); AOF everysec: 50,324 acknowledged, 0 lost. A kill -9 is a process crash, not a power cut: the operating system still holds what Redis wrote, which is why AOF lost nothing. On macOS a flush does not force the drive's own cache, so always is cheaper here than on a Linux server with a real flush.

          Streams: a job queue that survives a crashed worker
          

          A list makes a queue, but a worker that pops a job and crashes loses it. A stream is an append-only log; a consumer group hands each entry to one consumer and keeps it in a pending entries list until the consumer acknowledges it with XACK; another worker can claim an idle pending entry with XAUTOCLAIM. That is at-least-once delivery: a job can run twice, so it must be safe to repeat. Durable logs, the outbox pattern and Kafka are Queues, streams and async work's; a Redis stream is the small version, with Redis's durability.
          

          The measured stream run with real ids (depth)
            

            What it costs
            Memory: everything lives in RAM, plus overhead per key (93 bytes per sorted-set member above). One thread executes commands, so a slow command (a KEYS *, a long script, a ZRANGE returning a million members) stalls every client. Durability and replication are weaker than a database's by default, as measured. Redis Cluster shards keys over 16,384 hash slots, and a multi-key command or script works only when all its keys are in one slot (use hash tags such as {user:7}:bucket). The licence changed in 2024 and Valkey forked (dated table in Depth); Valkey speaks the same protocol and commands as Redis 7.2, so the code here works on both.
            

            When Postgres would still do
            A counter updated a few times a second (UPDATE ... SET n = n + 1 is atomic); a job queue with SELECT ... FOR UPDATE SKIP LOCKED (measured on Transactions and concurrency); a rate limit at tens of requests a second; top-N lists. Redis as a cache in front of Postgres (cache-aside, eviction, invalidation, stampedes) is Caching's subject.
            

            

            

            4. Key-value at any scale: DynamoDB and single-table design
            

            Suppose the chat product needs a store that grows without limit, survives the loss of a data centre, has no servers, upgrades or vacuum to manage, and every request already knows its key. That is what Amazon DynamoDB sells: a managed, partitioned key-value and document store, billed per request or per reserved capacity.
            

            The model
            

              

            • A table holds items (a map of attributes, at most 400 KB each). Each item has a primary key: a partition key, optionally with a sort key. Items with the same partition key form an item collection, stored together and sorted by sort key.
              • 

            • DynamoDB hashes the partition key to pick a partition; each partition is a Multi-Paxos group of three replicas, each with a write-ahead log and a B-tree (root atlas; Elhemali et al., Amazon DynamoDB, USENIX ATC 2022). Partitions split automatically as data and traffic grow.
              • 

            • Reads: GetItem (the full key: one item), Query (one partition key, optionally a sort key condition such as begins_with or between; items in sort order, up to 1 MB per page) and Scan (every item in the table). Nothing else: no joins, no query on a non-key attribute without an index.
              • 

            • Reads are eventually consistent by default; a strongly consistent read costs twice as much and is not available on global secondary indexes. Single-item writes are atomic; transactions cover up to 100 items in one Region and cost double (root atlas, claim corrected).
              • 

            • One read unit is a strongly consistent read of up to 4 KB (eventually consistent: half a unit); one write unit is a write of up to 1 KB. Each partition serves at most 3,000 read units and 1,000 write units a second (AWS, partition key design).
              • 

            

            

            Single-table design on the chat product
            

            With no joins, a screen that needs a user, their chats and a chat's messages would take several requests if each kind of item had its own table. Single-table design puts every kind of item in one table, with generic key strings (PK, SK) holding a type prefix and an id, chosen so that the items one screen needs share a partition key and come back in one Query, sorted (Alex DeBrie, The What, Why, and When of Single-Table Design, 2020-02-05). From the access patterns of section 1:
            

              

            1. Open a chat: messages get PK = CHAT#<chatId>, SK = MSG#<createdAt>#<messageId> (an ISO timestamp sorts correctly as a string; the id breaks ties). Query PK = CHAT#7, SK begins_with MSG#, descending, limit 50.
              2. 

            2. Usage per day: PK = USER#<userId>, SK = USAGE#<day>, updated with an atomic ADD; Query SK begins_with USAGE#2025-09. The profile (SK = PROFILE) shares the partition, so one Query can fetch both.
              3. 

            3. Chat list, most recently active first: chats sit under PK = USER#<userId>, SK = CHAT#<chatId>, sorted by id; a global secondary index (GSI1) re-keys them: GSI1PK = USER#<userId>, GSI1SK = LAST#<lastMessageAt>#<chatId>. Sending a message updates GSI1SK, and the chat moves to the top.
              4. 

            4. Log in by email, emails unique: a lookup item PK = EMAIL#<email> holds the user id; registration writes the user and the lookup item in one transaction, each with attribute_not_exists(PK), so a duplicate email fails.
              5. 

            5. Admin, every message of one model on one day: no key serves it without a partition that takes a quarter of all writes; it goes to an analytics copy (DynamoDB exports a table to S3 in full or incrementally, every 15 minutes to 24 hours, AWS quotas).
              6. 

            

            Try it: start from Relational habit (one kind of item per table, keyed by its own id) and predict how many questions become scans; then switch to Single-table design. Change only the message key to MSG#{messageId} and watch "latest 50 messages" collapse into a scan.
            

            Every planned question is one request that reads only the items it returns. The wrong ways show what a missing key costs: a Scan with a filter for chat 7 read 1,000 items in its first page and returned none of them (the filter runs after the read, and you pay for every item read), and answering the admin question by scanning read all 54,775 items in 9 pages of 1 MB for 1,111.5 read units. At a billion items the same scan reads a billion items.

            Secondary indexes are copies, updated later
            

            A global secondary index is a second copy of chosen attributes under a different key, maintained by DynamoDB asynchronously ("eventually consistent fashion ... within a fraction of a second, under normal conditions", AWS, GSI): a chat list read right after sending a message can still show the old order, and a strongly consistent read on it is refused. Each index is paid on every write: changing an indexed key costs two index writes (delete the old entry, put the new one), and an index short of write capacity throttles writes to the table.
            

            Index limits, writes, conditions and transactions, measured (depth)
            

            A table has at most 20 GSIs by default and 5 local secondary indexes (same partition key, different sort key, strongly consistent, but they cap an item collection at 10 GB and stop adaptive capacity from splitting it).
            

            Measured: one message put cost 1 write unit (a message item is about 173 bytes as DynamoDB counts size); the transaction that writes the message and moves the chat to the top of GSI1 cost 8 write units as DynamoDB Local accounted it. Registering a second account with an existing email failed with TransactionCanceledException, reasons [None, ConditionalCheckFailed]: the user item would have been fine, the email item already existed, so neither was written. An item over 400 KB was refused; a long document or file goes to S3 with its key stored in the item.
            

            Unconfirmed: 8 write units against the documented 6
            The documented rules give 6 (2 for each of the two transactional writes, 2 for moving the index entry), so Local appears to charge the index move at the transactional rate as well; unconfirmed against the real service.
            

            

            

            Hot partitions: the limit is per key, not per table
            

            All of one chat's messages share a partition key, so one very busy group chat can take at most 1,000 one-KB writes a second. DynamoDB keeps up to 300 seconds of unused capacity for bursts, and adaptive capacity moves busy items onto partitions of their own, "provided that traffic does not exceed ... the partition maximum capacity" (AWS, burst and adaptive capacity). Past that the fix is write sharding: spread one hot key over CHAT#7#0 to CHAT#7#9 and have readers query all ten and merge. Move the write rate past 1,000, then add shards:
            

            Two billing modes: on-demand per request (simplest, right for spiky or unknown traffic) and provisioned reserved units per hour with auto scaling (cheaper for steady, predictable traffic); dated prices are in the calculator note above and the table in Depth. Discord hit the same per-key wall in Cassandra with its busiest channels (section 6).

            Single table or several?
            DeBrie lists the costs of single-table design: a steep learning curve, new access patterns that need data migrations, and exports for analytics that are hard to read ("looks more like machine code than a simple spreadsheet", quoted there); he advises against it for early-stage applications that still need flexibility and for GraphQL back ends, whose resolvers issue separate requests anyway. AWS's own guidance makes the same trade (AWS Compute Blog, 2021-07-26). GSIs can now use up to four attributes each for the partition and sort keys, so an index no longer needs a hand-built composite string (DynamoDB Local added it in January 2026).
            

            What it costs
            The schema is the list of access patterns: a new question means a new index (written on every write) or a migration. Ad hoc questions, joins and aggregates belong elsewhere (export to S3, then DuckDB, Athena or a warehouse). Indexes are eventually consistent. A busy key is capped. And it runs only on AWS (DynamoDB Local is for development).
            

            When Postgres would still do
            Whenever one Postgres server (with replicas for reads) can carry the load and the team would rather keep SQL's flexibility: that covers most products for years. DynamoDB wins when you are on AWS, want no database to operate, and traffic is either huge and key-shaped or tiny and spiky (on-demand costs near zero when idle).
            

            

            

            5. Documents: MongoDB, and Postgres jsonb beside it
            

            Some records have no fixed shape: a tool call carries different arguments per tool; a user's settings grow a field every month. A document stores the record as one nested JSON-like value, read and written as a unit. MongoDB keeps documents in collections, in BSON (binary JSON with real dates and integers), each with a unique _id; any field can be indexed, including fields inside arrays; queries use a JSON query language or an aggregation pipeline of stages. Underneath, WiredTiger keeps compressed B-trees and a journal; a replica set has one primary and copies; sharding splits a collection by a shard key you choose (root atlas). Measured here: MongoDB 8.0.23 as a one-member replica set, because transactions need one.
            

            

            Embed or reference? Worked on chats and messages
            

            MongoDB's guidance: embed when you "query pieces of information together" and update them together; reference when "the child side of the relationship has high cardinality" or "your embedded data grows without bounds" (MongoDB, embedding vs references). A chat's messages are the textbook hard case: always read together, and growing without bound. Both shapes were loaded with the same 1M messages. Predict: which shape reads fewer bytes to show chat 7's newest 50?
            

            Then the hard limit: a BSON document may not exceed 16 MiB (MongoDB limits). Pushing messages of about 1 KB into one chat, the th fit (the document reached  bytes) and the next failed with Resulting document after update is larger than 16777216 (error 10334): the limit was hit at 15,220 messages. Appends also slow as the array grows: a $push took 6.2 ms into a 10-message chat and 13.1 ms into a 20,000-message chat of 3.4 MB, against 6.0 ms to insert one referenced message. A busy group chat would hit it in weeks, and long before that every read drags the whole history along.
            

            The design pros use: the chat document holds its metadata and perhaps the last few messages for the chat list (embedding a bounded subset); messages are referenced, one document each or grouped in fixed-size "buckets" of, say, 100 per document (MongoDB's bucket pattern). Tool-call arguments, whose shape varies and which are always read with their message, are embedded in the message.             6. Wide-column: Cassandra and ScyllaDB
            

            Suppose messages arrive faster than one primary can write them, users are on several continents, and losing a whole data centre must not stop anyone sending. A single-primary database cannot give all three. Apache Cassandra (and ScyllaDB, its C++ reimplementation) spreads every table over many equal machines, with no primary at all.
            

              

            • A table's PRIMARY KEY ((a, b), c, d) has two parts. The partition key (a, b) is hashed to a token; the nodes form a ring in which each owns ranges of tokens, so the token decides which nodes hold the partition. The clustering columns c, d sort the rows inside it.
              • 

            • Each partition is copied to RF nodes (the replication factor, usually 3, in different racks or data centres). Every node accepts reads and writes for any key and forwards them to the replicas: there is no leader (root atlas).
              • 

            • Storage is an LSM-tree: a commit log and an in-memory table, flushed to immutable sorted files (SSTables) that background compaction merges (Storage engines and indexes owns how LSM-trees work).
              • 

            • CQL looks like SQL but has no joins, and a query must name the partition key: "data is modeled around specific queries", one table per query, data duplicated across tables on purpose (Cassandra data modelling).
              •

            The write path and tunable consistency
            

            Each request chooses how many of the RF replicas must answer: ONE, QUORUM (a majority: floor(RF/2) + 1), LOCAL_QUORUM (a majority inside the local data centre) or ALL (Cassandra, Dynamo architecture). Fig. 3 steps one write at QUORUM with one replica down:

              2. 

            2. Hash the partition key. The coordinator hashes (7, 3) to a token; the ring says replicas A, B and C own it. C is down.
              3. 

            3. Each live replica logs, then buffers. A and B append the write to their commit log and insert it into their memtable (sorted, in memory). The default commitlog_sync: periodic flushes the log every 10 seconds, so the write is not yet on disk on either node.
              4. 

            4. Two of three is a QUORUM: reply OK. RF = 3, so QUORUM = floor(3/2) + 1 = 2. A and B answered, the coordinator replies OK. At ONE it would reply after the first answer; at ALL this write would fail, because C is down.
              5. 

            5. C gets a hint, not a failure. The coordinator stores a hint for C on its own disk and replays it when C comes back, if that is within max_hint_window (3 hours by default). After longer, C stays out of sync until read repair or a full repair copies the write.
              6. 

            6. Later: flush and compaction. Each memtable is flushed to an immutable SSTable and compaction merges files in the background (Storage engines and indexes owns how). A read at QUORUM asks two replicas and keeps the newest timestamp.

            Compare-and-set and multi-partition transactions (depth)
            For compare-and-set ("insert only if absent") Cassandra has lightweight transactions, which run a Paxos consensus round among the replicas for each operation and so cost extra round trips. Multi-partition ACID transactions (Accord) arrive only with Cassandra 6.0, still in alpha (root atlas). Durability: the default periodic commit log acknowledges writes before they are flushed, so one node can lose up to 10 seconds of writes in a power cut; replicas on other machines are what make the write safe.
            

            Tombstones: why deleting slows reads
            

            An LSM-tree cannot erase a row in place: the row may sit in several immutable files on several replicas. So a delete writes a tombstone, a marker that hides older data, kept for gc_grace_seconds (default 864,000 seconds, 10 days) so every replica learns of it; a replica that misses the delete for longer can bring the data back ("zombie" rows) (Cassandra, tombstones). Until compaction drops them, a read steps over every tombstone in its way. Measured: a partition of 130,000 messages, the newest deleted one by one, then "the latest 50":
            

            

            measured: 5,000 tombstones made the read about nine times slower; 101,000 made it fail, past the default tombstone_warn_threshold:  and tombstone_failure_threshold: .
            

            Discord hit this six months into production: a public channel with millions of deleted messages and one remaining message made Cassandra "scan millions of message tombstones", causing 10-second garbage-collection pauses; they cut the grace period from 10 days to 2 and stopped re-reading empty buckets (same Discord post). The lesson: a table used like a queue (insert, read, delete) is the classic anti-pattern; expire data with a TTL in time-ordered tables, and choose compaction to match.

            7. Time series: metrics, events and what makes them special
            

            The operations dashboard wants requests per minute, median latency and tokens per model for the last hour, refreshed every few seconds, and a 30-day trend; every chat request produces one measurement.             8. Graph: Neo4j, Kuzu, and the recursive query
            

            Some questions are about connections: "people you may know" (friends of friends), "is this account linked to a known fraud ring within four steps", "how is user A connected to user B". In tables each step is a join, and the number of steps is not known when you write the query. A property graph has nodes (a user, a chat) and relationships (FRIEND, OWNS), each with a type, a direction and properties. Queries are patterns in Cypher (Neo4j also accepts GQL, the ISO graph query language that grew out of it): MATCH (u:User {uid: $u})-[:FRIEND*1..3]-(v) RETURN count(DISTINCT v) reads "from user u, follow one to three FRIEND relationships in either direction". Neo4j stores each relationship as a record pointing directly at its two nodes and at the next relationship of each, so following one is a pointer lookup rather than an index search: index-free adjacency (root atlas; Robinson, Webber and Eifrem, Graph Databases, 2nd edition, O'Reilly 2015, chapter 6).

            • Read, decide, write in the application: 188 requests passed a limit of 20. Use the store's atomic operation (INCR, a Lua script, a conditional write, UPDATE ... SET n = n - 1 WHERE n > 0).
              • 

            • Redis as the only copy: a failover lost 4,947 of 5,000 acknowledged writes here; an RDB-only server lost every write since its last snapshot.
              • 

            • A partition key that concentrates traffic: the current date, a tenant with most of the traffic, one celebrity chat. Every partition has a ceiling (1,000 writes a second in DynamoDB).
              • 

            • Partitions or documents that grow forever: a chat document hit the 16 MB limit at 15,220 messages; a Cassandra partition per chat grows without limit. Bucket by time or count.
              • 

            • Cassandra as a queue, or bulk deletes: 5,000 tombstones made a read about nine times slower; 101,000 made it fail.
              • 

            • Reading your own write from an index or replica: DynamoDB GSIs, MongoDB secondaries, Redis replicas and Cassandra at ONE can all return data from before your write. Read from the primary, or use a strong read where one exists, for the request right after a write.
              • 

            • Deleting old time-series rows with DELETE: Measured: 1.9 s and 65 MB of log for 7 days, and the table did not shrink.
              • 

            


            Embedded key-value engines: RocksDB and LMDB (the libraries under other systems)
            

            Every database above sits on a storage engine: the library that turns "put this key and value" into bytes on disk. RocksDB is an embedded LSM-tree: a write-ahead log and a memtable, sorted files, background compaction; fast writes, tunable read, write and space amplification, many knobs. It is inside CockroachDB (via Pebble, its Go port), TiKV, Kafka Streams' state stores and many others; by default its WAL is not flushed to disk on every write, so a machine crash can lose the last writes (root atlas). Storage engines and indexes measures its amplification against Postgres. LMDB is a copy-on-write B+tree in one memory-mapped file: no WAL, no compaction, readers never block and see a consistent snapshot, but one writer at a time; very fast reads from many threads or processes; commits are flushed by default.
            

            Reach for one directly only when building a storage component (a queue, a persistent cache, an index) inside one process and you want neither a server nor SQL. Otherwise SQLite (rows, SQL, one writer) and DuckDB (columns, analytics), on the root page, are the embedded databases to use.
