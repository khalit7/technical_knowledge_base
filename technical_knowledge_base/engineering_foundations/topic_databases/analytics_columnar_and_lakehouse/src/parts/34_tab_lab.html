Parquet lab: one table, 36 files, four questions

The same 10 million chat messages (the root page's generator) written by DuckDB 1.5.6 as 36 different Parquet files: four sort orders, three row-group sizes, three codecs. On each file, four queries were run: the bytes DuckDB actually read from the file were counted (a counting file system wrapped around the file), and each query was timed five times warm, median shown. Nothing here is simulated: every number is a measurement from src/measure/parquet_lab.py, run 2026-10-04 on an Apple M1 Pro laptop (10 threads) that was shared with other jobs, so treat timings within about 2 times of each other as equal.

Try: keep "One chat" selected and switch the sort order from Time to Chat to Random: the bytes read go from under a megabyte to tens of megabytes. Then set row groups to 10,000 and watch time rise even when fewer bytes are read: 977 row groups mean 977 sets of statistics to check.

How to read it

  • Row groups read comes from the file's own footer: a row group is skipped when its min/max for the filtered column cannot contain a match. Bytes read is what DuckDB really fetched, including the footer; the footer arithmetic ("needed") assumes every needed column chunk of every surviving row group is fetched. DuckDB often reads less: it reads the filter column first and fetches tokens only for row groups where some row matched, which is late materialisation (section 4 of Reading) visible in bytes. Shuffled rows, one chat: 64 MB needed by the footer, 50 MB read. It reads a little more than predicted for the footer itself and, for tiny row groups, per-group overheads.
