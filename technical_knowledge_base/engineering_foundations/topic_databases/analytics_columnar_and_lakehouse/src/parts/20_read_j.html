9. The lakehouse: making a folder of Parquet files behave like a table

The problem. Object storage (S3, Google Cloud Storage, Azure Blob) is the cheapest durable place to keep terabytes, and Parquet is the format every engine reads. So teams put Parquet files in a bucket and called it a data lake. A folder of files is not a table, though: it has no atomic commit, no safe change, no schema history, no time travel, and planning starts by listing objects.

The five gaps, as the chat product hits them within a month (depth)
  • No atomic commit. A nightly job writes 40 files; a reader that lists the folder halfway through sees 23 of them and reports wrong totals. A job that crashes leaves half its files behind.
  • No safe change. Deleting one user's messages (a privacy request) means rewriting files while others read them. Two writers at once can overwrite each other.
  • No schema history. Add a lang column and old files lack it; rename a column and readers that match by name break.
  • No time travel. "What did this table look like when we trained last Tuesday's model?" has no answer once files are rewritten.
  • Slow planning. Listing a folder of a million objects on S3 takes many API calls before a single byte of data is read.

So teams kept a warehouse beside the lake and copied data between them with ETL, two copies that drift apart. The lakehouse is the alternative named in the CIDR 2021 paper by Armbrust, Ghodsi, Xin and Zaharia ({{Lakehouse paper|https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf}}): one copy in open files on the lake, with a metadata layer that gives it warehouse-style tables.

The idea. A table format keeps, next to the data files, a small set of metadata files that list exactly which data files make up the table at each moment, with their statistics. A commit writes new data files first (invisible), then new metadata, and finally makes the new metadata current with one atomic step. Readers read whichever metadata is current when they start, so they always see a whole commit or none of it. Old metadata stays, so old versions stay readable. Three formats matter: Iceberg, Delta Lake and Hudi.

Apache Iceberg: a tree of metadata, built for real

The spec ({{iceberg.apache.org/spec|https://iceberg.apache.org/spec/}}) tracks individual files, not directories, in four layers under a catalog. A real table was built on the local disk with pyiceberg 0.12.0 and a SQLite catalog, one day of chat messages at a time (src/measure/iceberg_walk.py, 2026-10-04): Fig. 4 steps through its commits.

  1. Catalog: holds one pointer per table, the location of the current metadata.json.
  2. metadata.json: the table's schemas (each column with a permanent field id), partition specs, and the list of snapshots, each one the complete state of the table after one commit. Every commit writes a new one; ours grew from 1,036 bytes to 7,761 bytes over eight steps.
  3. Manifest list (snap-...avro): one per snapshot, listing the manifests that make it up, with partition value ranges so a reader can skip whole manifests.
  4. Manifests (...-m0.avro): each lists data files with their partition values, row counts, and per-column lower and upper bounds (min/max, like Parquet's) so the planner can skip files without opening them.
  5. Data files: ordinary Parquet. One day of our messages is one 323 KB file.
  1. Create, partition by day(created_at). Two metadata.json files and no data yet: a table is its metadata. Adding the partition spec was itself a commit; the catalog points at the newer one.
  2. Append 2026-03-01 (28,800 rows). 1 Parquet, 1 manifest, 1 manifest list, 1 metadata.json. The data file lands in created_at_day=2026-03-01/; snapshot 1 exists only once metadata.json 00002 is current. The dots show a reader following the pointer down the tree.
  3. Append 2026-03-02. The same four kinds of file. The new manifest list names both manifests: snapshots share unchanged manifests rather than copying them, so a commit costs one new manifest, not a copy of the table's file list.
  4. Add column lang. 1 metadata.json only. Schema evolution rewrites no data: schema 1 adds field id 7. Old files simply have no field 7, read as null.
  5. Append a third day, with lang filled. Four new files again; the table now holds 86,400 rows in three data files.
  6. Delete chat 520912. 1 Parquet, 2 manifests, 1 list, 1 metadata.json. pyiceberg rewrote the one affected file (28,798 rows) and recorded the old one as DELETED: copy-on-write. The old file stays on disk for time travel (faded: no current snapshot uses it).
  7. Partition spec day to month. 1 metadata.json only. Partition evolution: new data uses month; old files keep their day layout; queries need no change, because they filter on created_at, never on the partition column (hidden partitioning).
  8. Append a fourth day under the month spec. Its file lands in created_at_month=2026-03/; the current snapshot has 115,198 rows. Every box is a file the table really wrote. Nothing is modified in place: every commit writes new files and a new metadata.json (Iceberg) or the next numbered log file (Delta), and the newest metadata decides which files are the table.
  9. Time travel to snapshot 1. No new files: the reader takes snapshot 1's branch of the tree. Reading snapshot 1899985093966477424 returns 28,800 rows and the 6 original columns; the current snapshot has 115,198 rows and 7 columns.
  1. Create the table from one day. Commit 00000000000000000000.json (1,837 bytes) holds the protocol, metaData (schema) and add actions, beside one data file of 28,800 rows.
  2. Append a second day. Commit 1 is one add; creating that file atomically (put-if-absent) is the commit.
  3. Append a third day with a new column lang. Commit 2 carries a new metaData action (the merged schema) and an add.
  4. Delete chat 520912. Commit 3 is one add (28,798 rows copied) and one remove: copy-on-write, exactly like Iceberg's. The removed file fades but stays on disk.
  5. Time travel to version 0. A reader replays the log only up to commit 0: 28,800 rows and the 6 original columns.

A query for one day planned exactly one of the table's four live data files, from manifest bounds alone, before opening any Parquet: the same min/max pruning as section 3, one level up. The alternative to copy-on-write is merge-on-read: write a small delete file now, pay at read time.

The commit is one compare-and-swap on the catalog pointer; the loser retries on top of the winner

Metadata files: solid, committed; dashed, written but not visible; faded, superseded or orphaned; orange, current. illustrative snapshot numbers; the protocol is the spec's. In the Iceberg REST catalog a commit sends requirements such as "the current snapshot is still 42" plus the updates.

Two writers at once: optimistic concurrency

A writer builds new metadata from the snapshot it read, then asks the catalog to swap the pointer only if it still points where it did; if another writer won, it re-checks for conflicts and retries ({{spec|https://iceberg.apache.org/spec/}}). No locks are held while files are written, which is why many engines can write one table.

  1. Both read v42. The catalog points at metadata v42. Writers A and B both start from it; neither takes a lock.
  2. Both write. Each writes its new data files and a new metadata file built on v42. Nothing is visible yet: readers still follow the pointer to v42.
  3. A swaps first. A asks the catalog to swap the pointer from v42 to v43a only if it still points at v42. It does, so the swap succeeds: A's commit is visible, whole, to every reader that starts now.
  4. B is refused. B asks for the same swap from v42. The pointer is now v43a, so the catalog refuses. v43b is never visible; its files become orphans for clean-up.
  5. B retries on top. B re-reads v43a, checks that A's change does not conflict with its own (two appends never do; two rewrites of the same file would), writes v44 on top of v43a and swaps again. Both commits are in the table, in order.

Delta Lake and Apache Hudi

Delta Lake keeps a folder _delta_log/ of numbered JSON files; commit n is 00000000000000000003.json for n = 3, and creating it atomically (put-if-absent) is the commit ({{PROTOCOL.md|https://github.com/delta-io/delta/blob/master/PROTOCOL.md}}). Each holds actions: add a file (with per-file stats), remove a file, metaData (schema), protocol, commitInfo. The same steps with deltalake 1.6.6 (src/measure/delta_walk.py) wrote four commits; the delete wrote one add (28,798 rows copied) and one remove, exactly like Iceberg's copy-on-write.

Delta checkpoints, deletion vectors, liquid clustering and UniForm (depth)

Readers replay the log; to keep replay short, Delta Spark writes a Parquet checkpoint of the whole state every 10 commits by default (an implementation default, not part of the protocol). Delta also has deletion vectors, liquid clustering (changeable clustering keys instead of fixed partitions) and UniForm, which writes Iceberg metadata for the same files so Iceberg readers can read a Delta table ({{UniForm|https://docs.delta.io/latest/delta-uniform.html}}).

Apache Hudi is built for streaming upserts, for example from a change-data feed. Its tables are copy-on-write (rewrite base files on update) or merge-on-read (append updates to log files, merge at read time, compact later), with a record-level index mapping each key to its file group so an upsert finds its row fast ({{table types|https://hudi.apache.org/docs/table_types}}). Iceberg has the broadest engine support today, which is why the atlas suggests it unless you live in Spark and Databricks (Delta) or stream CDC upserts (Hudi).

Catalogs: where the pointer lives. The atomic step needs one place that holds "current metadata for table X" and can compare-and-swap it: the catalog, and in 2026 it is where vendors compete. The Iceberg REST catalog is an OpenAPI spec, so any engine talks to any catalog ({{spec|https://github.com/apache/iceberg/blob/main/open-api/rest-catalog-open-api.yaml}}); AWS Glue, Unity Catalog, Apache Polaris, Nessie and Lakekeeper implement it or something close, and DuckLake (section 6) puts the whole catalog and metadata in a SQL database. The vendors' catalogs, with dates, are in section 12.

Partitioning and the small-files problem, measured

Partitioning puts each value range of a column (usually a day or a month of time) into its own set of files, so a filter on that range skips whole files before a single footer is read. Pick the grain so files stay hundreds of MB: partition by time, cluster or sort by the key inside. Partitioning by a high-cardinality column (a user id) makes one folder per user and millions of tiny files.

Tiny files are the cost to watch. Streaming or frequent small appends create many of them; each costs an open, a footer read and a plan entry, each is compressed on its own, and on S3 each is at least one request. The fix is compaction: rewrite many small files into few large ones as a new commit, which readers never notice. Iceberg's rewrite_data_files procedure targets 512 MB files by default; Delta's OPTIMIZE targets 1 GB, and its auto compaction 128 MB ({{Iceberg procedures|https://iceberg.apache.org/docs/latest/spark-procedures/}}, {{Delta config|https://github.com/delta-io/delta/blob/master/spark/src/main/scala/org/apache/spark/sql/delta/sources/DeltaSQLConf.scala}}). Then expire old snapshots and delete files no snapshot references, or storage grows for ever (and deleted personal data is still on disk): time travel is paid for in bytes.

When not to use a table format
One team, one engine, data that fits in DuckDB or Postgres: a lakehouse adds a catalog to run, compaction jobs to schedule and snapshot expiry to remember. Its pay-off is many engines (Spark for ETL, Trino or a warehouse for BI, Python for ML) sharing one copy of very large tables with safe concurrent writes.
