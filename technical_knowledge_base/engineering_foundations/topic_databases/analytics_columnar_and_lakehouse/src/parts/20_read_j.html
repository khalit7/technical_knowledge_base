9. The lakehouse: making a folder of Parquet files behave like a table

The problem. Object storage (S3, Google Cloud Storage, Azure Blob) is the cheapest durable place to keep terabytes, and Parquet is the format every engine reads. So teams put Parquet files in a bucket and called it a data lake. A folder of files is not a table, though, and the chat product hits every gap within a month:

  • No atomic commit. A nightly job writes 40 files; a reader that lists the folder halfway through sees 23 of them and reports wrong totals. A job that crashes leaves half its files behind.
  • No safe change. Deleting one user's messages (a privacy request) means rewriting files while others read them. Two writers at once can overwrite each other.
  • No schema history. Add a lang column and old files lack it; rename a column and readers that match by name break.
  • No time travel. "What did this table look like when we trained last Tuesday's model?" has no answer once files are rewritten.
  • Slow planning. Listing a folder of a million objects on S3 takes many API calls before a single byte of data is read.

The idea. A table format keeps, next to the data files, a small set of metadata files that list exactly which data files make up the table at each moment, with their statistics. A commit writes new data files first (invisible), then new metadata, and finally makes the new metadata current with one atomic step. Readers read whichever metadata is current when they start, so they always see a whole commit or none of it. Old metadata stays, so old versions stay readable. The lakehouse is that combination, data lake storage with warehouse-style tables on top, named in the CIDR 2021 paper by Armbrust, Ghodsi, Xin and Zaharia ({{Lakehouse paper|https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf}}). Three formats matter:

Apache Iceberg: a tree of metadata, walked through on a real table

The spec ({{iceberg.apache.org/spec|https://iceberg.apache.org/spec/}}) tracks individual files, not directories, in four layers. Built here with pyiceberg 0.12.0 on the local disk (src/measure/iceberg_walk.py), one day of chat messages at a time:

The real files after the second append. Every name is the one pyiceberg wrote; the {{Iceberg, step by step|#t-ice}} tab replays all eight steps and opens each file.
  1. Catalog: holds one pointer per table, the location of the current metadata.json. Here a SQLite file; in production a REST catalog service, AWS Glue, Unity Catalog or Polaris (below).
  2. metadata.json: the table's schemas (each column with a permanent field id), partition specs, and the list of snapshots, each one the complete state of the table after one commit. Every commit writes a new one; ours grew from 1,036 bytes to 7,761 bytes over eight steps.
  3. Manifest list (snap-...avro): one per snapshot, listing the manifests that make it up, with partition value ranges so a reader can skip whole manifests.
  4. Manifests (...-m0.avro): each lists data files with their partition values, row counts, and per-column lower and upper bounds (min/max, like Parquet's) so the planner can skip files without opening them.
  5. Data files: ordinary Parquet. One day of our messages is one 323 KB file.

A query for one day planned exactly one of the table's four live data files, from manifest bounds alone, before opening any Parquet: the same min/max pruning as section 3, one level up. Concurrency is optimistic: a writer builds new metadata from the snapshot it read, then asks the catalog to swap the pointer only if it still points where it did; if another writer won, it re-checks for conflicts and retries ({{spec|https://iceberg.apache.org/spec/}}). Format v2 added row-level deletes through delete files (merge-on-read, the alternative to copy-on-write); v3 adds deletion vectors, row lineage, default values, variant and geospatial types; a v4 is in draft. Current Java release: 1.12.0, 2026-09-29 ({{releases|https://iceberg.apache.org/releases/}}).

Delta Lake: an ordered log of JSON commits

Delta keeps a folder _delta_log/ of numbered JSON files; commit n is 00000000000000000003.json for n = 3, and creating it atomically (put-if-absent) is the commit ({{PROTOCOL.md|https://github.com/delta-io/delta/blob/master/PROTOCOL.md}}). Each holds actions: add a file (with per-file stats), remove a file, metaData (schema), protocol, commitInfo. The same steps with deltalake 1.6.6 (src/measure/delta_walk.py) wrote four commits; the delete wrote one add (28,798 rows copied) and one remove, exactly like Iceberg's copy-on-write. Readers replay the log; to keep replay short, Delta Spark writes a Parquet checkpoint of the whole state every 10 commits by default (an implementation default, not part of the protocol). Delta also has deletion vectors, liquid clustering (changeable clustering keys instead of fixed partitions) and UniForm, which writes Iceberg metadata for the same files so Iceberg readers can read a Delta table ({{UniForm|https://docs.delta.io/latest/delta-uniform.html}}). Current: delta-spark 4.4.0.

Apache Hudi, in brief

Hudi is built for streaming upserts, for example from a change-data feed. Its tables are copy-on-write (rewrite base files on update) or merge-on-read (append updates to log files, merge at read time, compact later), with a record-level index mapping each key to its file group so an upsert finds its row fast ({{table types|https://hudi.apache.org/docs/table_types}}). Current: 1.2.1 (2026-09-24). Iceberg has the broadest engine support today, which is why the atlas suggests it unless you live in Spark and Databricks (Delta) or stream CDC upserts (Hudi).

Catalogs: where the pointer lives

The atomic step needs one place that holds "current metadata for table X" and can compare-and-swap it. That is the catalog, and in 2026 it is where vendors compete:

  • Iceberg REST catalog: an OpenAPI spec, so any engine talks to any catalog; a commit sends requirements such as "the current snapshot is still 42" plus updates ({{spec|https://github.com/apache/iceberg/blob/main/open-api/rest-catalog-open-api.yaml}}).
  • AWS Glue Data Catalog: has an Iceberg REST endpoint ({{docs|https://docs.aws.amazon.com/glue/latest/dg/connect-glu-iceberg-rest.html}}); Amazon S3 Tables (announced 2024-12-03) are buckets that store Iceberg tables and run compaction and snapshot clean-up for you ({{announcement|https://aws.amazon.com/about-aws/whats-new/2024/12/amazon-s3-tables-apache-iceberg-tables-analytics-workloads/}}).
  • Unity Catalog: Databricks' catalog; its open-source version is an LF AI and Data sandbox project, release 0.6.0 (2026-08), serving Delta tables and the Iceberg REST API ({{unitycatalog.io|https://www.unitycatalog.io/}}).
  • Apache Polaris: an Iceberg REST catalog that Snowflake donated; incubating from 2024-08-09, a top-level Apache project since 2026-02-15 ({{Apache|https://incubator.apache.org/projects/polaris.html}}).
  • Nessie (Git-like branches and multi-table commits) and Lakekeeper (a Rust REST catalog) are open-source alternatives; DuckLake (section 6) puts the whole catalog and metadata in a SQL database.

The small-files problem, measured

Streaming or frequent small appends create many small files. Each file costs an open, a footer read and a plan entry; each is compressed on its own, and on S3 each is at least one request. The same 10 million messages, measured with DuckDB 1.5.6 (src/measure/remote_small.py):

The fix is compaction: rewrite many small files into few large ones as a new commit, which readers never notice. Iceberg's rewrite_data_files procedure targets 512 MB files by default; Delta's OPTIMIZE targets 1 GB, and its auto compaction 128 MB ({{Iceberg procedures|https://iceberg.apache.org/docs/latest/spark-procedures/}}, {{Delta config|https://github.com/delta-io/delta/blob/master/spark/src/main/scala/org/apache/spark/sql/delta/sources/DeltaSQLConf.scala}}). Then expire old snapshots and delete files no snapshot references, or storage grows for ever: time travel is paid for in bytes.

When not to use a table format
One team, one engine, data that fits in DuckDB or Postgres: a lakehouse adds a catalog to run, compaction jobs to schedule and snapshot expiry to remember. Its pay-off is many engines (Spark for ETL, Trino or a warehouse for BI, Python for ML) sharing one copy of very large tables with safe concurrent writes.
