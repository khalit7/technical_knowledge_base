7. ClickHouse: a column store server for fresh events

The problem it solves. DuckDB on Parquet is ideal for files that change once a night. A product dashboard wants something else: events arriving every second (messages, token counts, latencies), queried by many people at once, answered in well under a second, over billions of rows. That needs a server that ingests continuously and stays columnar. ClickHouse is the most widely used open-source one (Apache 2.0).

The figures below come from ClickHouse itself, embedded in Python through chDB 3.7.2, which bundles ClickHouse 25.8 (a year behind the current release; the MergeTree behaviour shown is long-standing). The 10 million messages were inserted in 10 batches into

CREATE TABLE chat.messages (id UInt64, chat_id UInt64, role LowCardinality(String),
  model LowCardinality(String), tokens UInt32, content String, created_at DateTime)
ENGINE = MergeTree ORDER BY (chat_id, created_at)
  • Every insert writes a part. A part is an immutable folder of column files, sorted by the table's ORDER BY, written in one go and never modified. After 10 inserts, system.parts listed 10 parts of 1,000,000 rows and 47.6 MiB each. Merges were paused for this step so the parts could be seen.
  • Background merges combine parts, like an LSM-tree's compaction ({{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}}): read sorted parts, write one bigger sorted part, drop the old ones. OPTIMIZE TABLE ... FINAL forced it: one part, all_1_10_2 (blocks 1 to 10, merge level 2), 10,000,000 rows, 476 MiB, in 3.9 s.
  • ORDER BY is the primary index, and it is sparse. Within a part, rows are cut into granules of 8,192 rows (index_granularity, default 8192) and the index stores the key of the first row of each granule, not of every row ({{sparse primary indexes|https://clickhouse.com/docs/guides/best-practices/sparse-primary-indexes}}).

The sparse index finds one chat in one granule of 1,221; a filter on time reads them all

The merged part, from EXPLAIN indexes = 1 measured: Granules: 1/1221 by binary search for the chat (before the merge, Parts: 1/10, Granules: 1/1230); Granules: 1221/1221 by generic exclusion search for one day of created_at. One tick per 8 index entries; a granule is 8,192 rows.

The order chosen for the table decides which questions are cheap; a second order needs a projection or a second table. That is section 3's rule again, made explicit in the schema. Sorting also compresses: with the default LZ4 codec, chat_id (sorted first) shrank from 80 MB to 8.0 MB on disk, while id, unsorted in this order, only halved (80 to 40 MB) and created_at did not shrink at all.

Materialised views as insert triggers. An incremental materialised view in ClickHouse runs its query on every inserted block and writes the result into a target table ({{docs|https://clickhouse.com/docs/materialized-view/incremental-materialized-view}}). Here a view kept tokens per model per day in a SummingMergeTree table: after the 10 inserts it held 1,408 partial rows, to be summed by later merges; summed at query time, 1 March 2026 came to 28,800 messages and 9,134,325 tokens, the same as every other engine on this page. Dashboards read the small table, not the 10 million rows. Refreshable materialised views instead re-run a full query on a schedule.

The defaults that bite. Inserts are not fsynced by default (fsync_after_insert = 0, confirmed in the embedded server too): an acknowledged insert can be lost if the machine loses power before the OS flushes it; replication covers this in practice. Each insert makes a part, so thousands of tiny inserts outrun merging: above 1,000 active parts in a partition inserts are delayed, above 3,000 they fail with "Too many parts" (parts_to_delay_insert, parts_to_throw_insert); batch inserts (thousands of rows each) or use async inserts, which buffer on the server. Updates and deletes are expensive by design (below).

More defaults, a correction to the docs, and scaling (26.9 source, 2026-10-04)
  • ReplacingMergeTree deduplicates rows with the same sorting key only during merges, at unknown times, so queries add FINAL when duplicates matter ({{ReplacingMergeTree|https://clickhouse.com/docs/engines/table-engines/mergetree-family/replacingmergetree}}).
  • Correction: the docs read as if async inserts are opt-in, but since 26.2 async_insert is on by default ({{settings history|https://github.com/ClickHouse/ClickHouse/blob/v26.9.10.4-stable/src/Core/SettingsChangesHistory.cpp}}).
  • Lightweight DELETE marks rows hidden and removes them at later merges; lightweight UPDATE (patch parts) is still Beta.
  • Turn on fsync_after_insert if a single node must not lose data.
  • Scaling: shard across servers with a Distributed table and replicate asynchronously through ClickHouse Keeper; ClickHouse Cloud's SharedMergeTree keeps data in object storage instead ({{SharedMergeTree|https://clickhouse.com/docs/cloud/reference/shared-merge-tree}}).
When to choose it, when not
Choose ClickHouse for append-mostly event data, dashboards and observability where queries must be sub-second over billions of rows and data is minutes old. Do not use it as a system of record: no general transactions, no unique constraints, weak single-row updates, and the not-fsynced default. For data that changes once a day and a few analysts, DuckDB on Parquet is simpler.
