11. Feeding ML: training data, feature history and point-in-time joins

Training data lives in Parquet. Datasets on the Hugging Face Hub are served as Parquet files ({{HF docs|https://huggingface.co/docs/hub/datasets-duckdb}}), so DuckDB can query them by URL with the same range reads as section 6. For your own training sets, everything above applies with two additions. Write shards of a few hundred MB, so many data-loader workers read in parallel and a crashed job resumes from a shard. And choose the sort order for the reads that matter: sorted by time, "everything since the last training run" prunes to a few row groups; sorted by user, "all of this user's data" (a deletion request, a per-user split) does.

Features need history. A feature is an input to a model computed from data ("tokens this user used in the last 7 days", "the user's plan"). To train, each example needs each feature as it was when the example happened. Joining today's value instead is leakage: the model learns from information it will never have at prediction time, scores well offline and disappoints in production.

Measured on the chat data with DuckDB (src/measure/ml_asof.py): one training example per chat (999,951 chats, stamped with their first message), and the user's plan as the feature. The chat data has no plan history, so one was generated (illustrative: 19,968 users, 20%, upgraded from free to pro on a random day). The naive join, today's plan, labelled 198,446 examples "pro"; the point-in-time join labelled 101,517. So 96,929 examples, almost half of the "pro" ones, carried a plan their user did not have yet. Chat 13 started on 2025-09-01; its user upgraded on 2026-05-11; the naive join calls it a pro chat.

-- the plan in force when each chat started: an ASOF join
SELECT e.chat_id, e.ts, p.plan
FROM examples e
ASOF JOIN plan_history p
  ON e.user_id = p.user_id AND e.ts >= p.valid_from

An ASOF join matches each row with the latest row of the other table at or before its timestamp ({{DuckDB ASOF join|https://duckdb.org/docs/stable/guides/sql_features/asof_join}}). A feature store packages this: an offline store (columnar, the full history, for building training sets with point-in-time joins) and an online store (a key-value store with only the latest value per entity, for serving), filled by the same feature definitions so training and serving agree. In Feast, get_historical_features takes a table of entity keys and event timestamps and joins each feature's latest value at or before each timestamp ({{Feast point-in-time joins|https://docs.feast.dev/getting-started/concepts/point-in-time-joins}}; Feast 0.66.0, 2026-08-21). When you need one, and how it fits the serving path, is on {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}}; datasets themselves are on {{Topic: data-curation-and-datasets|n:3c65c17b0d0d811fa5ecda8d365ab00f}}.

The habit that prevents leakage
Keep history instead of overwriting it: an append-only table of changes (valid_from per row), or a lakehouse table you can time-travel, or CDC events landed raw. Then every training set is an ASOF join against an event timestamp, and you can rebuild any past training set exactly.
