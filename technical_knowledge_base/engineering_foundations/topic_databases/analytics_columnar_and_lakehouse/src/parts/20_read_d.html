3. Skipping data: min/max statistics and sort order

The problem. Reading only two columns is good; reading only the part of those columns that can matter is better. "Messages on 1 March 2026" needs 28,800 of 10 million rows. A column store has no B-tree to find them (an index per column would cost as much to maintain as the data), so it needs a cheaper trick.

The idea: a zone map. When a block of rows is written, record the smallest and largest value of each column in it (its min/max statistics). At query time, compare the filter with each block's range: if 1 March lies outside [min, max], no row in the block can match, and the block is skipped without being read. Postgres has the same idea as the BRIN index; Parquet keeps the statistics per row group in its footer; Snowflake keeps them per micro-partition; ClickHouse per granule of 8,192 rows (section 7).

  1. The query. SELECT count(*), sum(tokens) for one day or one chat (the buttons) on 10,000,000 messages in one 534 MB Parquet file. Nothing read yet.
  2. Read the footer. The reader fetches the end of the file (DuckDB asked for the last 256 KiB; the footer is 76,648 bytes). It now knows where every column chunk is and each row group's min and max of the filtered column.
  3. Row groups 0 to 40. Each row group's [min, max] is compared with the filter. Grey: the range excludes the filter, skipped without reading a byte. Green: the range overlaps, so its two chunks are read. Chat 424242 falls in row group 34.
  4. Row groups 41 to 81. The same comparison to the end of the file; 1 March 2026 falls in row group 42.
  5. Done. One row group read, 81 skipped, for either query. For the day, the bytes computed from the footer reproduce DuckDB's measured 1,197,073 (in 3 reads) exactly; for the chat, 708,747 computed against 741,532 measured (in 4 reads). The stat tiles under the chart follow the buttons.
  1. The query. The same SELECT count(*), sum(tokens) for one day or one chat on the 534 MB file. Nothing read yet.
  2. Read the footer. The reader fetches the end of the file and learns where every column chunk is; this reader ignores the statistics.
  3. Row groups 0 to 40. Without statistics every row group might hold a match, so the filter column's and tokens' chunks of each are read and every value is checked. Orange: read, no match.
  4. Row groups 41 to 81. The same to the end of the file: every row group is read.
  5. Done. All 82 row groups read to find 28,800 matching rows (one day) or 7 (one chat): 76 MB or 37 MB, computed from the footer.

The catch: skipping only works on sorted data. The file above was written in time order (message ids grow with time), so each row group covers about four consecutive days and a date filter lands in one or two of them. A chat's messages sit within about 20,000 consecutive rows (the generator interleaves chats active at the same time), so a chat filter also lands in one or two row groups, by luck of how the app writes. Shuffle the rows and every row group spans every date and every chat: nothing can be skipped. Predict what one chat costs in a shuffled file before choosing it below.

  • What it costs: almost nothing to keep (82 pairs of values per column here, inside a 76,648-byte footer), but it constrains how you write: data has to be sorted, or at least clustered, on the column people filter by. You can only pick one primary order, so pick the filter that matters most (usually time, because new data arrives in time order and most questions name a time range), and accept that other filters scan.
  • When it does not help: filters on columns with no order (a model name in a time-sorted file: all 82 row groups contain all four models), and filters that match a few rows spread through the whole file (the 6,950 messages over 1,495 tokens: their row groups' maxima all exceed 1,495, so none is skipped).
  • What pros add: sort within each file by a second key (Snowflake's clustering keys, Delta's liquid clustering, ClickHouse's ORDER BY tuple, Iceberg sort orders), bloom filters for equality on unsorted columns (section 5), and partitioning by time so whole files are skipped before any footer is read (section 9).

Sort order decides what can be skipped, and it is chosen when the file is written
