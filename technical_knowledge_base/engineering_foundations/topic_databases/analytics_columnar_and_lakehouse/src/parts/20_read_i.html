8. Cloud warehouses: storage apart from compute, and how they bill

The problem. DuckDB and ClickHouse run on machines you size. When data reaches tens of terabytes, or twenty teams query it at once, sizing and running those machines becomes a job of its own. A cloud data warehouse is a managed column store that removes that job.

The idea they share: separate storage from compute. The table lives as compressed columnar files in the provider's object storage (cheap, effectively unlimited, durable). Query engines are separate machines that read those files when a query runs and can be added, resized or switched off without moving data. Each team can get its own compute over the same tables, and when nobody queries, compute can cost nothing. The price is a network hop between the two, hidden by local caches.

How BigQuery, Snowflake, Redshift and Databricks name the pieces (depth)

The same shape in each service, with different names: BigQuery keeps columnar files (Capacitor) on Colossus and runs Dremel execution trees whose leaves are slots, units of CPU and memory ({{Google Cloud blog, 2020|https://cloud.google.com/blog/products/data-analytics/new-blog-series-bigquery-explained-overview}}); Snowflake keeps immutable micro-partitions of 50 to 500 MB uncompressed, columnar inside, with per-column value ranges for pruning ({{docs|https://docs.snowflake.com/en/user-guide/tables-clustering-micropartitions}}), read by virtual warehouses you start, suspend and resize (XS uses 1 credit an hour, doubling per size); Redshift keeps Redshift Managed Storage on S3 with local SSD caches, read by provisioned clusters or Serverless; Databricks SQL reads your own cloud storage in open formats (Delta Lake, Iceberg) under Unity Catalog with the Photon vectorised engine ({{docs|https://docs.databricks.com/aws/en/lakehouse/}}).

Isolation differs, and it matters for reports (root's Database atlas): BigQuery gives snapshot isolation for multi-statement transactions; Snowflake offers read committed only, so a report that reads two tables in one transaction can see different moments of each; Redshift defaults to snapshot isolation for new clusters. Isolation levels themselves are on {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}}.

The two billing models change how you design. When you pay per byte scanned (BigQuery on demand, Redshift Spectrum), every column you name and every partition you fail to prune is money, and SELECT * on a wide table is the classic expensive mistake: BigQuery bills the columns you select "even if you set an explicit LIMIT". When you pay for compute time (Snowflake, Redshift Serverless, BigQuery capacity), a scan that takes 2 seconds on a running warehouse is nearly free, but a warehouse kept awake by a dashboard that refreshes every few minutes is not, because of the 60-second minimum each time a warehouse starts or resumes ({{Snowflake docs|https://docs.snowflake.com/en/user-guide/warehouses-overview}}). Predict: at one refresh a minute, which bill grows faster as the table grows from 10 million to 10 billion rows?

Pay-per-byte grows with the table; pay-per-second grows with how often you ask

The root page's case 6 query (tokens per model) reads the model and tokens columns. In BigQuery's billing a STRING is 2 bytes plus its UTF-8 length and an INT64 8 bytes ({{data type sizes|https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/data-types#data_type_sizes}}), so at 10M messages the query is billed 165.0 MB derived. The compute-time services are charged here as one 60-second minimum per refresh, assuming the warehouse suspends between refreshes and the query itself runs under a minute. List prices, US region, fetched 2026-10-04: BigQuery on demand $6.25 per TiB (at least 10 MB per query); Snowflake Enterprise $3 per credit; Redshift Serverless $0.375 per RPU-hour at 8 RPU.

When not to reach for one. If the data fits on one machine (most of it does: section 6), a warehouse adds a bill, a network and a second copy for little gain. If you need per-request answers for an app, warehouses answer in seconds, not milliseconds; the atlas notes that BigQuery's DML is rate limited and Snowflake's billing suits batch analytics.

What pros do
Set auto-suspend short (Snowflake) or cap slots (BigQuery capacity), put a budget alert on day one, partition and cluster big tables by the column most queries filter on (time), materialise expensive dashboard queries into small summary tables, and check the bytes a BigQuery query will bill before running it (the console shows the estimate; a dry run returns it).
