2. Inside a column store: chunks, encodings, compression

The problem. A table of 10 million messages is about 1.5 GB in Postgres. An analytics question usually needs two or three of its seven columns, and it needs every row of them. A layout that keeps each row's values together forces the reader through all seven columns to get two.

The idea. Cut the table into blocks of rows (a row group: in DuckDB's own storage and in the Parquet files it writes, 122,880 rows by default ({{DuckDB Parquet docs|https://duckdb.org/docs/stable/data/parquet/overview}})). Inside each block, store each column on its own, one after another: a column chunk (the bands of the hero figure). A query that names model and tokens reads those two chunks from every block and never touches content: that is the root page's 87 times fewer bytes at 10 million rows ({{Query plans|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab, case 6).

The second win comes free: one column's values are all the same type and usually look alike (two roles, four model names, timestamps three seconds apart), so they fit in far fewer bits. Two layers do it, and they are worth keeping apart. Encoding rewrites values into a smaller form the engine can still read directly, often without decoding everything first; it knows the type. Compression (a codec such as Snappy, LZ4 or Zstandard) then squeezes the encoded bytes as an opaque blob, the way a zip file does, and must be undone before the bytes are used.

Each encoding removes one kind of redundancy; the codec only squeezes what is left

  1. Dictionary, then bit-packing (role, real bytes from the 23,047-byte file of section 5): each distinct string once in a dictionary page, then a code per row, packed into as few bits as the largest code needs: user, assistant repeated is the byte aa (binary 10101010, read from the lowest bit up). Useless when nearly every value is distinct (an id): writers fall back to plain when the dictionary grows too big (pyarrow's default limit is 1 MB per column chunk, {{pyarrow docs|https://arrow.apache.org/docs/python/generated/pyarrow.parquet.ParquetWriter.html}}).
  2. Run-length (RLE) (model, table sorted by model): long runs of one value become (value, repeat count) pairs, a handful per page. Nothing is gained when values alternate; Parquet mixes RLE runs and bit-packed runs in one stream, the RLE/bit-packing hybrid ({{Parquet encodings|https://parquet.apache.org/docs/file-format/data-pages/encodings/}}).
  3. Delta (id): the first value, then the differences minus each block's smallest difference, bit-packed (DELTA_BINARY_PACKED): ids that grow by exactly 1 need 0 bits each, 500 ids in 80 bytes, page header included. Differences of a random column are as big as the values.
  4. Codec only (content): free text has no structure an encoding can use, so only the codec helps.
Byte stream split, and the codecs Parquet allows (depth)

Byte stream split targets numbers whose bytes are noisy at the bottom but similar at the top (floats, measurements): write all first bytes, then all second bytes, and so on, so the codec sees long similar streams. It saves nothing on its own; it only helps the codec that follows.

Codecs: Snappy and LZ4 are fast and modest; Zstandard (zstd) compresses harder for a little more CPU, with levels; gzip and Brotli are slower still. Parquet lists UNCOMPRESSED, SNAPPY, GZIP, LZO, BROTLI, LZ4 (framing deprecated), ZSTD and LZ4_RAW ({{parquet-format|https://github.com/apache/parquet-format/blob/master/Compression.md}}).

Measured on the chat data

Every column of the 10 million messages, written on its own by pyarrow 25.0.1 with each encoding and each codec; the bar is the column chunk's size from the file's footer (src/measure/encodings.py, run 2026-10-04). Predict before you click role: will sorting the table shrink it by 2 times, 10 times or 70 times?

The right encoding shrinks a column hundreds of times; the sort order decides how far

  • id and created_at: 80 MB plain, 0.22 and 0.34 MB with delta encoding (367 and 236 times smaller), before any codec. Consecutive ids differ by 1 and timestamps by 3 seconds, so every delta fits in a couple of bits. Dictionary is the wrong tool here: it gave up and stored 82.7 MB.
  • role: 105 MB of plain strings; a dictionary of two words plus 1 bit per row is 1.29 MB (10 million bits is 1.25 MB). Roles alternate user, assistant, so runs never form. Sort the table by role and the same dictionary encoding gives 17.5 KB, about 73 times smaller: the bits become a handful of RLE runs.
  • model: four values, so 2 bits each: 2.54 MB with a dictionary, and Snappy or zstd on top gain nothing, because bit-packed random codes look like noise to a codec.
  • content: 835 MB plain, 389 MB with Snappy, 223 MB with zstd. Caveat: the generator's text is a repeated hexadecimal hash, which compresses unusually well; real chat text should be measured on your own data.
The rule that falls out
Let the writer pick encodings (every mainstream writer tries dictionary first and falls back), choose the codec on purpose (Snappy is the default in DuckDB and in {{Spark|https://spark.apache.org/docs/latest/sql-data-sources-parquet.html}}, zstd is the usual choice for data kept a long time), and control the one thing that changes the numbers most: sort order. The same 10 million roles are 1.29 MB or 17.5 KB depending only on how rows were ordered when written.

What it costs. Encoded, compressed columns are cheap to scan and expensive to change: updating one message means decoding and rewriting whole chunks, which is why column stores append in bulk, mark deletions on the side, and merge later (sections 7 and 9). Rebuilding a whole row touches one chunk per column. And CPU is spent on every read to undo the codec; with fast disks and a heavy codec, scans can become CPU-bound.
