10. Getting the data there: ETL, ELT, change data capture and dbt

The problem. Every engine on this page holds a copy. The app writes to Postgres; analytics reads somewhere else; something must move the rows, keep the copy fresh enough, and never lose or double-count a message.

Two shapes of pipeline.

  • ETL (extract, transform, load): pull rows out, clean and reshape them in a separate program (a Python job, Spark), then load only the finished tables. It was the norm when warehouse compute was scarce and expensive.
  • ELT (extract, load, transform): copy the raw rows into the warehouse or lake as they are, then transform them inside it with SQL. Cheap separated compute made this the default: the raw copy stays, so a fixed transformation can be re-run over history.

Extracting without hurting the app. A nightly COPY (SELECT ... WHERE created_at >= yesterday) works for append-only tables like messages, as long as it reads from a replica. Rows that change (a user's plan, a deleted chat) need change data capture (CDC): a tool such as {{Debezium|https://debezium.io/documentation/reference/stable/connectors/postgresql.html}} reads Postgres's write-ahead log through a replication slot and emits every insert, update and delete in commit order. That machinery (slots, the outbox pattern, delivery guarantees) is owned by {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}; the leftover risk on the database side, an abandoned slot that keeps WAL forever, is on {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}}. Landing a change stream in a lake is what Hudi's merge-on-read and Iceberg's row-level deletes are for.

dbt, in one section

dbt is the common tool for the T in ELT. You write each transformed table as one SELECT in a file (a model); dbt works out the order from references between models, runs them in the warehouse, and runs tests (not null, unique, accepted values, relationships) on the results. A daily usage table for the chat product, as an incremental model that only processes new rows on each run ({{dbt docs|https://docs.getdbt.com/docs/build/incremental-models-overview}}):

-- models/daily_tokens.sql
{{ config(materialized='incremental', unique_key=['day', 'model']) }}
select cast(created_at as date) as day, model,
       count(*) as messages, sum(tokens) as tokens
from {{ source('app', 'messages') }}
{% if is_incremental() %}
  -- reprocess the last 2 days: late rows still land in the right day
  where created_at >= (select max(day) - interval 2 day from {{ this }})
{% endif %}
group by 1, 2

The double braces above are dbt's Jinja templating, shown verbatim.

State in October 2026: the Python engine is now called dbt Core v1 (1.12.5, 2026-09-15); the Rust Fusion engine is "v2" and the recommended default, with its runtime open-sourced as dbt Core v2.0 alpha ({{dbt Fusion|https://docs.getdbt.com/docs/fusion/about-fusion}}); and dbt Labs merged with Fivetran (announced 2025-10-13, completed 2026-06-01) ({{Fivetran|https://www.fivetran.com/press/fivetran-dbt-labs-complete-merger-to-create-the-data-infrastructure-for-trusted-ai-agents}}).

Mistakes this prevents, and causes
Incremental models skip rows that arrive late unless the filter looks back (the two days above); a pipeline that is not idempotent double-counts on retry (merge on a unique key, never blind-append in a retried job); and a model graph of 400 SQL files with no owner is its own maintenance problem. Start with plain SQL views; reach for dbt when there are more than a handful of transformations or more than one person.
