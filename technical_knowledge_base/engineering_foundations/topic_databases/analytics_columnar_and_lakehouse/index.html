The one-paragraph version. Keep the app on Postgres. Copy the data out (nightly, or as a stream of changes) into Parquet files, sorted by time, and query them with DuckDB until one machine is not enough; then ClickHouse for fresh, fast dashboards, or a cloud warehouse or lakehouse when many teams and engines share terabytes. Whatever the engine, the same few mechanisms decide speed and cost: read only the needed columns, encode them small, skip blocks using statistics (which only works if the data was written sorted), and execute in batches.

1. Two kinds of work: OLTP and OLAP

OLTP (online transaction processing) is what the app does: many small requests, each reading or writing a few whole rows (open chat 424242, save one message), each expected in milliseconds, with transactions keeping concurrent writers correct. OLAP (online analytical processing) is what analysts, dashboards, billing and ML pipelines do: few, large queries that read a few columns of millions or billions of rows and aggregate them, where seconds are fine and rows are rarely changed after they are written.

The chat product's analytics questions look like this, and they are the five queries measured on this page:

  • Tokens per model (the parent page's case 6), and messages per day in March.
  • Tokens by country and plan: a join of all three tables (messages, chats, users).
  • The top 10 users by tokens in the last 30 days, and distinct active chats per model per month.

Measured: the same five questions on three engines. Same rows in each (100,000 users, 1M chats, 10M messages, from the root's generator), every answer checked identical across engines. PostgreSQL 16.2 with its two base indexes and 7 GB of shared buffers warmed so the tables sat in memory; SQLite 3.47.1 with a 2.5 GB page cache; DuckDB 1.5.6 in its own file. Default parallelism (Postgres 2 workers per query, DuckDB 10 threads), and one thread each. Median of 3 warm runs (SQLite 2), on a shared laptop (src/measure/engines.py, 2026-10-04).

Three engines, one machine, same data: the column engine answers in milliseconds what the row engines answer in seconds, and the gap survives taking parallelism away. Sections 2 to 4 explain where each factor comes from. None of this says Postgres or SQLite are slow databases: ask each to fetch one chat's messages by key and the ranking reverses, which is why the app stays on Postgres.

Why not just run analytics on the app's Postgres?
Up to a few million rows, do: a read replica, a few summary tables refreshed by a job, maybe a BRIN index on time (see Storage engines and indexes). Past that, every analytic query reads every page of the table, competes with the app for disk, memory and CPU, and holds back vacuum while it runs (Running Postgres in production). That is the moment to make a second copy in a column format.

2. Inside a column store: chunks, encodings, compression

The problem. A table of 10 million messages is about 1.5 GB in Postgres. An analytics question usually needs two or three of its seven columns, and it needs every row of them. A layout that keeps each row's values together forces the reader through all seven columns to get two.

The idea. Cut the table into blocks of rows (a row group: in DuckDB's own storage and in the Parquet files it writes, 122,880 rows by default (DuckDB Parquet docs)). Inside each block, store each column on its own, one after another: a column chunk. A query that names model and tokens reads those two chunks from every block and never touches content. That is the whole trick behind the root page's 87 times fewer bytes at 10 million rows (Query plans tab, case 6).

The second win comes free: one column's values are all the same type and usually look alike (two roles, four model names, timestamps three seconds apart), so they can be stored in far fewer bits than their plain form. That is done in two layers, and it helps to keep them apart:

  • Encoding rewrites values into a smaller representation that the engine can still read directly, often without decoding everything first. It knows the type (integers, strings).
  • Compression (a codec such as Snappy, LZ4 or Zstandard) then squeezes the encoded bytes as an opaque blob, the way a zip file does. It must be undone before the bytes are used.

The encodings, one problem each

Dictionary

Problem: the same few strings repeated millions of times (model has four values). How: store each distinct value once in a dictionary page, then store small integer codes (0 to 3) instead of the strings. Cost: useless when nearly every value is distinct (an id): writers fall back to plain when the dictionary grows too big (pyarrow's default limit is 1 MB per column chunk, pyarrow docs).

Bit-packing

Problem: codes 0 to 3 need 2 bits, not 32. How: pack each value into exactly as many bits as the largest one needs, eight values at a time. Cost: one big value raises the width for its whole run.

Run-length (RLE)

Problem: long runs of the same value (a column sorted by model). How: write "value 2, repeated 2,500,000 times" as two numbers. Cost: nothing gained when values alternate; Parquet mixes RLE runs and bit-packed runs in one stream, the RLE/bit-packing hybrid (Parquet encodings).

Delta

Problem: sorted or slowly growing numbers (ids, timestamps): 10 million eight-byte values that differ by 1 or by 3 seconds. How: store the first value, then the differences, bit-packed in blocks (DELTA_BINARY_PACKED). Cost: differences of a random column are as big as the values.

Byte stream split

Problem: numbers whose bytes are noisy at the bottom but similar at the top (floats, measurements). How: write all first bytes, then all second bytes, and so on, so the codec sees long similar streams. Cost: no saving on its own; it only helps the codec that follows.

Codecs

Snappy and LZ4 are fast and modest; Zstandard (zstd) compresses harder for a little more CPU, with levels; gzip and Brotli are slower still. Parquet lists UNCOMPRESSED, SNAPPY, GZIP, LZO, BROTLI, LZ4 (framing deprecated), ZSTD and LZ4_RAW (parquet-format).

Measured on the chat data

Every column of the 10 million messages, written on its own by pyarrow 25.0.1 with each encoding and each codec; the bar is the column chunk's size from the file's footer (src/measure/encodings.py, run 2026-10-04). Pick a column; for role and model try the table sorted by those columns.

What the numbers say:

  • id and created_at: 80 MB plain, about 0.2 to 0.3 MB with delta encoding (367 and 236 times smaller), before any codec. Consecutive ids differ by 1 and timestamps by 3 seconds, so every delta fits in a couple of bits. Dictionary is the wrong tool here: it gave up and stored 82.7 MB.
  • role: 105 MB of plain strings; a dictionary of two words plus 1 bit per row is 1.29 MB (10 million bits is 1.25 MB). Roles alternate user, assistant, so runs never form. Sort the table by role and the same dictionary encoding gives 17.5 KB: the bits become a handful of RLE runs.
  • model: four values, so 2 bits each: 2.54 MB with a dictionary, and Snappy or zstd on top gain nothing, because bit-packed random codes look like noise to a codec.
  • content: nothing but the codec helps. 835 MB plain, 389 MB with Snappy, 223 MB with zstd. Caveat: the generator's text is a repeated hexadecimal hash, which compresses unusually well; real chat text should be measured on your own data.
The rule that falls out
Let the writer pick encodings (every mainstream writer tries dictionary first and falls back), choose the codec on purpose (Snappy is the default in DuckDB and in Spark, zstd is the usual choice for data kept a long time), and control the one thing that changes the numbers most: sort order. The same 10 million roles are 1.29 MB or 17.5 KB depending only on how rows were ordered when written.

What it costs. Encoded, compressed columns are cheap to scan and expensive to change: updating one message means decoding and rewriting whole chunks, which is why column stores append in bulk, mark deletions on the side, and merge later (sections 7 and 9). Rebuilding a whole row touches one chunk per column. And CPU is spent on every read to undo the codec; with fast disks and a heavy codec, scans can become CPU-bound.

3. Skipping data: min/max statistics and sort order

The problem. Reading only two columns is good; reading only the part of those columns that can matter is better. "Messages on 1 March 2026" needs 28,800 of 10 million rows. A column store has no B-tree to find them (an index per column would cost as much to maintain as the data), so it needs a cheaper trick.

The idea: a zone map. When a block of rows is written, record the smallest and largest value of each column in it (its min/max statistics, also called a zone map). At query time, compare the filter with each block's range: if 1 March lies outside [min, max], no row in the block can match, and the block is skipped without being read. Postgres has the same idea as the BRIN index; Parquet keeps the statistics per row group in its footer; Snowflake keeps them per micro-partition; ClickHouse per granule of 8,192 rows (section 7).

The animation runs one query on the real 534 MB Parquet file of 10 million messages written by DuckDB (82 row groups of 122,880 rows; each bar is one row group, its height the real compressed bytes of the two columns the query needs). Toggle between a reader that ignores the statistics and one that uses them.

The catch: skipping only works on sorted data. The file above was written in time order (message ids grow with time), so each row group covers about four consecutive days and a date filter lands in one or two of them. A chat's messages are spread over about 20,000 consecutive rows (the generator interleaves chats that are active at the same time), so a chat filter also lands in one or two row groups, by luck of how the app writes. Shuffle the rows and every row group spans every date and every chat: nothing can be skipped. The Parquet lab tab measures this on 36 files; with row groups of 100,000 rows, one chat costs 0.46 to 0.69 MB read from a file sorted by time or by chat, and 34 to 86 MB from a shuffled one (any row-group size).

  • What it costs: almost nothing to keep (82 pairs of values per column here, inside a 76,648-byte footer), but it constrains how you write: data has to be sorted, or at least clustered, on the column people filter by. You can only pick one primary order, so pick the filter that matters most (usually time), and accept that other filters scan.
  • When it does not help: filters on columns with no order (a model name in a time-sorted file: all 82 row groups contain all four models), and filters that match a few rows spread through the whole file (the 6,950 messages over 1,495 tokens: their row groups' maxima all exceed 1,495, so none is skipped).
  • What pros add: sort within each file by a second key (Snowflake's clustering keys, Delta's liquid clustering, ClickHouse's ORDER BY tuple, Iceberg sort orders), bloom filters for equality on unsorted columns (section 5), and partitioning by time so whole files are skipped before any footer is read (section 9).

4. Executing fast: vectorised execution and late materialisation

Reading fewer bytes is half the story. Once the bytes are in memory, the engine still has to add up 10 million numbers, and how it loops over them matters as much as the disk.

Row at a time

Classic engines, Postgres and SQLite included, execute a plan as a tree of operators that pass one row at a time: the aggregate asks the scan for the next row, the scan decodes one row from a page, hands it up, and the aggregate adds one number. This is the iterator or Volcano model. It is flexible and fine for OLTP, where a request touches a few rows. For 10 million rows it means 10 million rounds of function calls, type checks and branches per operator, and the CPU spends most of its time on that overhead rather than on the additions.

A vector at a time

Vectorised execution passes a batch of values, a vector, between operators: in DuckDB 2,048 values of one column per call (DuckDB execution format). The per-call overhead is paid once per 2,048 values, and the inner loop is a tight loop over an array of one type, which the compiler turns into SIMD instructions and the CPU's caches and branch predictor love. The idea comes from MonetDB/X100 (Boncz, Zukowski and Nes, CIDR 2005); DuckDB, ClickHouse, Snowflake, Databricks Photon and Velox all execute this way. (The other modern route attacks the same overhead by compiling to machine code: Postgres's JIT compiles expressions, and engines such as HyPer compile whole queries.)

Measured on one question, the sum of the 10 million tokens values, already in memory, one CPU thread unless marked (src/measure/vec_ooc.py, engines.py):

The two row-at-a-time engines take about a second; DuckDB on one thread takes 7.9 ms, about 136 times less, and numpy, a vectorised loop with no query engine around it, 2.4 ms. The Python loop sits in between because summing machine integers in a list is the simplest possible loop; a database's per-row work (decoding a tuple, checking visibility, evaluating an expression tree) is heavier. Parallel workers help both kinds of engine, but they multiply, they do not remove, the per-row cost.

Late materialisation

The problem. SELECT sum(tokens) WHERE chat_id = 424242 needs tokens only for the 7 rows that match. Fetching and decoding the whole tokens column first and filtering afterwards ("early materialisation", building full rows up front) wastes most of that work.

The idea. Evaluate the filter on chat_id alone, keep a list of the positions that passed, and fetch other columns only for those positions, as late as possible (Abadi, Madden and Hachem, SIGMOD 2008). DuckDB does this per row group when reading Parquet, and the lab shows it in bytes. In a shuffled file, the footer says one chat needs the chat_id and tokens chunks of all 100 row groups (64 MB); DuckDB read 50 MB, because it fetched tokens only from the row groups where the chat actually appeared.

Its limit. The gain is at the granularity of what can be skipped. Selecting the longest content among messages over 1,495 tokens (6,950 rows, in every row group) still read 404 MB, more than reading content for all 10 million rows (390 MB), because every row group had a match and the text of a row group is one chunk. Late materialisation saved the decoding of most strings, not the bytes. Sorting so that matches cluster is again what turns it into fewer bytes.

What this means for you
You do not choose the execution model; you choose the engine. For analytics over more than a few million rows, choose one that executes in vectors and reads columns (DuckDB, ClickHouse, Polars, any warehouse). Then write your data so that its tricks apply: sorted by the main filter, with the columns you filter on kept narrow.

5. The Parquet file, byte by byte

Why a file format matters. Sections 2 to 4 describe what every column store does inside its own storage. Apache Parquet writes the same structure into an ordinary file that any engine can read: DuckDB, ClickHouse, Spark, pandas, Polars, BigQuery, Snowflake, and every lakehouse table format. It is the shared language of analytics data, so knowing its layout explains most performance surprises.

The layout

  1. The file starts with the 4 bytes PAR1 (hex 50 41 52 31), a "magic number" that identifies the format.
  2. Row groups follow, one after another. Each holds one column chunk per column, and each chunk is a sequence of pages: optionally one dictionary page, then data pages. Every page starts with a small page header (its type, sizes, value count, encoding) and is the unit that is encoded and compressed.
  3. At the end comes the footer (the file metadata): the schema, then for every row group and every column chunk its byte offset, sizes, encodings, codec and statistics (min, max, null count). It is serialised with Apache Thrift's compact protocol.
  4. The last 8 bytes are the footer's length (4 bytes, little-endian) and PAR1 again (parquet-format README).

Why the footer is at the end. A writer streams row groups out without knowing in advance how big they will be, then writes the offsets once it knows them. A reader does the reverse: read the last 8 bytes, then the footer, and only then decide which byte ranges of the file it needs. That is why a query on object storage starts with one small request at the end of the file (section 6 shows the requests).

The Inside a Parquet file tab opens a real 23,047-byte file (the first 1,000 messages, two row groups of 500, no compression) region by region, with every header decoded by a small Thrift reader written for this page and checked against pyarrow's own reading. Two details from it worth knowing here:

  • The role column's dictionary page holds just user and assistant (each with a 4-byte length). Its data page starts with the bit width, 01, then one bit-packed run whose bytes are aa aa aa ...: binary 10101010, read from the lowest bit up, is 0, 1, 0, 1: user, assistant, user, assistant. Ten million roles are 10 million bits.
  • The id column of 500 values takes 80 bytes with delta encoding, page header included: the body is a short header, the first value and deltas that need zero bits each.

Two things to notice. DuckDB wrote id and created_at with PLAIN encoding (Snappy then halves id), whereas pyarrow with delta encoding would make them a few hundred kilobytes for the whole file (section 2): writers differ, and it shows in file size. And the created_at min and max of row group 0 are 2025-09-01 00:00:03 and 2025-09-05 06:24:00: about four days per row group, so a one-day query touches one or two of 82 row groups.

Beyond min/max: page index and bloom filters

  • Page index: optional per-page min/max (ColumnIndex) and page locations (OffsetIndex) stored near the footer, so a reader can skip pages inside a column chunk, not just whole row groups (PageIndex.md).
  • Bloom filters: a compact bit array per column chunk that answers "is value X definitely absent?" Min/max cannot rule out chat 424242 when the chunk spans 400,000 to 450,000; a bloom filter can. DuckDB writes them by default (WRITE_BLOOM_FILTER true, target false-positive ratio 0.01, COPY docs).

Row group size and sort order, measured

The spec suggests large row groups (512 MB to 1 GB) for sequential scans; DuckDB defaults to 122,880 rows. The Parquet lab tab measures 36 versions of the same file. The headline, at row groups of 100,000 rows with Snappy:

Sort order decides what can be skipped, and it has to be chosen when the file is written: shuffled rows make every filter read everything, while sorting by the filtered column reads only the matching row groups. Time order is a good default for event data, because new data arrives in time order and most questions name a time range. Row group size trades skipping against overhead: tiny row groups (10,000 rows) skip finely but bloat the footer and slow every query; huge ones skip little. A few hundred thousand to a few million rows, or 100 MB to 1 GB, is the usual range.

6. DuckDB in depth

What it is. DuckDB is a column-oriented, vectorised SQL engine that runs inside your process, like SQLite: pip install duckdb, no server, no network hop, no users to manage (SIGMOD 2019 demo paper). A database is one file (or none, in memory). Version 1.5.6 (2026-09-28); 1.4 is the long-term-support line; a 2.0 is scheduled for 2026-10-21 and was in public preview at the time of writing (release calendar). MIT licensed; in August 2026 DuckLabs agreed to join AWS (announced 2026-08-26, closed 2026-08-31), with DuckDB staying MIT under the non-profit DuckDB Foundation (root's Database atlas, announcement).

Querying files in place

Its most useful habit for analytics: it reads Parquet, CSV and JSON files directly, with no load step, and treats a glob of files as one table.

import duckdb
con = duckdb.connect()                      # in memory; or duckdb.connect('chat.duckdb')
con.sql("""
  SELECT model, count(*) AS messages, sum(tokens) AS tokens
  FROM 'exports/messages/*.parquet'          -- every file in the folder, one table
  WHERE created_at >= '2026-03-01'
  GROUP BY model ORDER BY model
""").df()                                   # a pandas DataFrame; .pl() gives Polars, .arrow() Arrow
con.sql("COPY (SELECT * FROM read_csv('events.csv')) TO 'events.parquet' (FORMAT parquet, COMPRESSION zstd)")

Results move to pandas, Polars and Arrow without copying the data value by value, and DuckDB can query a pandas or Polars DataFrame in scope by its variable name. The same SQL runs over a 10 KB CSV or a folder of 500 GB of Parquet.

Reading from object storage, measured

The httpfs extension reads files over HTTP(S) and S3 and, for Parquet, uses the footer plus HTTP range requests to download only the parts a query needs (httpfs docs). To see exactly which bytes, the 534 MB file was served by a small local HTTP server that logs every request (src/measure/remote_small.py):

On S3 every request costs time (tens of milliseconds of latency) and a small fee, so the shape of the file shows up on the bill: few, large row groups sorted by the main filter mean few requests. DuckDB issues them from many threads at once.

Bigger than memory, measured

Operators that must see all their input before producing output (sorting, grouping, joining, window functions) spill to a temporary directory when they exceed memory_limit, which defaults to 80% of RAM (tuning guide). Sorting all 10 million messages by their text (about 1 GB of strings) with the limit set to 300 MB took 3.6 s and wrote up to 790 MB of temporary files; with the default limit (12.7 GiB on this laptop) it took 2.6 s and spilled nothing (vec_ooc.py). Slower, but it finishes: this is what lets one laptop chew through data several times its memory.

When DuckDB beats Spark, and when it does not

Spark spreads work over a cluster; that costs start-up time, shuffles over the network and an operations burden, and pays off only when the data or the computation is too big for one machine. Most analytical data is not: Jordan Tigani, a founding engineer of BigQuery now running MotherDuck (so not neutral), reported that most BigQuery customers stored under a terabyte and that 90% of queries processed under 100 MB (Big data is dead, 2023). Coiled's TPC-H benchmark (2024, by a Dask vendor) found "no project wins": DuckDB was the clear winner for SQL on 100 GB of local data, Spark was beaten by about 10 times or more at small scales, and at 10 TB the distributed engines scaled where single-machine DuckDB and Polars did not (Coiled TPC-H). The rule of thumb: up to a few hundred GB on one machine, start with DuckDB (or Polars); past what one large machine can hold, or with many concurrent users, use a distributed engine or a warehouse.

Where it stops, and what grew around it

  • One writing process at a time per database file (many threads inside it); snapshot isolation is its only level (atlas). It is not the live store behind a web app with many writers.
  • Lakehouse formats: the iceberg extension reads tables directly and reads and writes through an Iceberg REST catalog; the delta extension, built on Delta Kernel, reads and does blind appends (iceberg, delta).
  • DuckLake, the DuckDB team's own table format, keeps all lakehouse metadata in a SQL database (Postgres, MySQL, SQLite or DuckDB) and the data in Parquet, which gives multi-writer access; announced 2025-05-27, v1.0 declared production-ready 2026-04-13 (ducklake.select).
  • MotherDuck runs DuckDB as a cloud service (storage $0.043 per GB-month; compute instances from $2.93 an hour, or $0.73 per compute-unit hour metered per query; pricing).

7. ClickHouse: a column store server for fresh events

The problem it solves. DuckDB on Parquet is ideal for files that change once a night. A product dashboard wants something else: events arriving every second (messages, token counts, latencies), queried by many people at once, answered in well under a second, over billions of rows. That needs a server that ingests continuously and stays columnar. ClickHouse is the most widely used open-source one (Apache 2.0; 26.9.10.4 stable and 26.8 LTS on 2026-10-04, versions).

MergeTree, run for real

The figures below come from ClickHouse itself, embedded in Python through chDB 3.7.2, which bundles ClickHouse 25.8 (a year behind the current release; the MergeTree behaviour shown is long-standing). The 10 million messages were inserted in 10 batches into

CREATE TABLE chat.messages (id UInt64, chat_id UInt64, role LowCardinality(String),
  model LowCardinality(String), tokens UInt32, content String, created_at DateTime)
ENGINE = MergeTree ORDER BY (chat_id, created_at)
  • Every insert writes a part. A part is an immutable folder of column files, sorted by the table's ORDER BY, written in one go and never modified. After 10 inserts, system.parts listed 10 parts of 1,000,000 rows and 47.6 MiB each. Merges were paused for this step so the parts could be seen.
  • Background merges combine parts, like an LSM-tree's compaction (Storage engines and indexes): read sorted parts, write one bigger sorted part, drop the old ones. OPTIMIZE TABLE ... FINAL forced it: one part, all_1_10_2 (blocks 1 to 10, merge level 2), 10,000,000 rows, 476 MiB, in 3.9 s.
  • ORDER BY is the primary index, and it is sparse. Within a part, rows are cut into granules of 8,192 rows (index_granularity, default 8192) and the index stores the key of the first row of each granule, not of every row (sparse primary indexes). Finding chat 424242 is a binary search over 1,221 index entries, and EXPLAIN indexes = 1 reported Granules: 1/1221: one granule of 8,192 rows read. Before the merge it reported Parts: 1/10, Granules: 1/1230.
  • Other filters scan. The same table filtered on one day of created_at reported Granules: 1221/1221. The order chosen for the table decides which questions are cheap; a second order needs a projection or a second table. That is section 3's rule again, made explicit in the schema.
  • Sorting compresses. With the default LZ4 codec, chat_id (sorted first) shrank from 80 MB to 8.0 MB on disk, while id, unsorted in this order, only halved (80 to 40 MB) and created_at did not shrink at all.

Materialised views as insert triggers

An incremental materialised view in ClickHouse runs its query on every inserted block and writes the result into a target table (docs). Here a view kept tokens per model per day in a SummingMergeTree table: after the 10 inserts it held 1,408 partial rows, to be summed by later merges; summed at query time, 1 March 2026 came to 28,800 messages and 9,134,325 tokens, the same as every other engine on this page. Dashboards read the small table, not the 10 million rows. Refreshable materialised views instead re-run a full query on a schedule.

Defaults and limits worth knowing (26.9 source, 2026-10-04)

  • Inserts are not fsynced by default (fsync_after_insert = 0, confirmed in the embedded server too): an acknowledged insert can be lost if the machine loses power before the OS flushes it. Replication covers this in practice; turn it on if a single node must not lose data.
  • Too many parts: each insert makes a part, so thousands of tiny inserts outrun merging. Above 1,000 active parts in a partition inserts are delayed, above 3,000 they fail with "Too many parts" (parts_to_delay_insert, parts_to_throw_insert). Batch inserts (thousands of rows each) or use async inserts, which buffer on the server; correction the docs read as if async inserts are opt-in, but since 26.2 async_insert is on by default (settings history).
  • Updates and deletes are expensive by design. Lightweight DELETE marks rows hidden and removes them at later merges; lightweight UPDATE (patch parts) is still Beta; ReplacingMergeTree deduplicates rows with the same sorting key only during merges, at unknown times, so queries add FINAL when duplicates matter (ReplacingMergeTree).
  • Scaling: shard across servers with a Distributed table and replicate asynchronously through ClickHouse Keeper; ClickHouse Cloud's SharedMergeTree keeps data in object storage instead (SharedMergeTree).
When to choose it, when not
Choose ClickHouse for append-mostly event data, dashboards and observability where queries must be sub-second over billions of rows and data is minutes old. Do not use it as a system of record: no general transactions, no unique constraints, weak single-row updates, and the not-fsynced default. For data that changes once a day and a few analysts, DuckDB on Parquet is simpler.

8. Cloud warehouses: storage apart from compute, and how they bill

The problem. DuckDB and ClickHouse run on machines you size. When data reaches tens of terabytes, or twenty teams query it at once, sizing and running those machines becomes a job of its own. A cloud data warehouse is a managed column store that removes that job.

The idea they share: separate storage from compute. The table lives as compressed columnar files in the provider's object storage (cheap, effectively unlimited, durable). Query engines are separate machines that read those files when a query runs and can be added, resized or switched off without moving data. Each team can get its own compute over the same tables, and when nobody queries, compute can cost nothing. The price is a network hop between the two, hidden by local caches.

The two billing models change how you design. When you pay per byte scanned (BigQuery on demand, Redshift Spectrum at $5 per TB), every column you name and every partition you fail to prune is money, and SELECT * on a wide table is the classic expensive mistake. When you pay for compute time (Snowflake, Redshift Serverless, BigQuery capacity), a scan that takes 2 seconds on a running warehouse is nearly free, but a warehouse kept awake by a dashboard that refreshes every few minutes is not, because of the 60-second minimum on every resume.

What one dashboard query costs derived from list prices, not measured

The root page's case 6 query (tokens per model) reads the model and tokens columns. In BigQuery's billing a STRING is 2 bytes plus its UTF-8 length and an INT64 8 bytes (data type sizes), so at 10M messages the query is billed 165.0 MB. The compute-time services are charged here as one 60-second minimum per refresh, assuming the warehouse suspends between refreshes and the query itself runs under a minute.

When not to reach for one. If the data fits on one machine (most of it does: section 6), a warehouse adds a bill, a network and a second copy for little gain. If you need per-request answers for an app, warehouses answer in seconds, not milliseconds; the atlas notes that BigQuery's DML is rate limited and Snowflake's billing suits batch analytics. And mind the isolation levels: a report that reads two tables in one Snowflake transaction can see different moments of each, since read committed is all it offers.

What pros do
Set auto-suspend short (Snowflake) or cap slots (BigQuery capacity), put a budget alert on day one, partition and cluster big tables by the column most queries filter on (time), materialise expensive dashboard queries into small summary tables, and check the bytes a BigQuery query will bill before running it (the console shows the estimate; a dry run returns it).

9. The lakehouse: making a folder of Parquet files behave like a table

The problem. Object storage (S3, Google Cloud Storage, Azure Blob) is the cheapest durable place to keep terabytes, and Parquet is the format every engine reads. So teams put Parquet files in a bucket and called it a data lake. A folder of files is not a table, though, and the chat product hits every gap within a month:

  • No atomic commit. A nightly job writes 40 files; a reader that lists the folder halfway through sees 23 of them and reports wrong totals. A job that crashes leaves half its files behind.
  • No safe change. Deleting one user's messages (a privacy request) means rewriting files while others read them. Two writers at once can overwrite each other.
  • No schema history. Add a lang column and old files lack it; rename a column and readers that match by name break.
  • No time travel. "What did this table look like when we trained last Tuesday's model?" has no answer once files are rewritten.
  • Slow planning. Listing a folder of a million objects on S3 takes many API calls before a single byte of data is read.

The idea. A table format keeps, next to the data files, a small set of metadata files that list exactly which data files make up the table at each moment, with their statistics. A commit writes new data files first (invisible), then new metadata, and finally makes the new metadata current with one atomic step. Readers read whichever metadata is current when they start, so they always see a whole commit or none of it. Old metadata stays, so old versions stay readable. The lakehouse is that combination, data lake storage with warehouse-style tables on top, named in the CIDR 2021 paper by Armbrust, Ghodsi, Xin and Zaharia (Lakehouse paper). Three formats matter:

Apache Iceberg: a tree of metadata, walked through on a real table

The spec (iceberg.apache.org/spec) tracks individual files, not directories, in four layers. Built here with pyiceberg 0.12.0 on the local disk (src/measure/iceberg_walk.py), one day of chat messages at a time:

The real files after the second append. Every name is the one pyiceberg wrote; the Iceberg, step by step tab replays all eight steps and opens each file.
  1. Catalog: holds one pointer per table, the location of the current metadata.json. Here a SQLite file; in production a REST catalog service, AWS Glue, Unity Catalog or Polaris (below).
  2. metadata.json: the table's schemas (each column with a permanent field id), partition specs, and the list of snapshots, each one the complete state of the table after one commit. Every commit writes a new one; ours grew from 1,036 bytes to 7,761 bytes over eight steps.
  3. Manifest list (snap-...avro): one per snapshot, listing the manifests that make it up, with partition value ranges so a reader can skip whole manifests.
  4. Manifests (...-m0.avro): each lists data files with their partition values, row counts, and per-column lower and upper bounds (min/max, like Parquet's) so the planner can skip files without opening them.
  5. Data files: ordinary Parquet. One day of our messages is one 323 KB file.

A query for one day planned exactly one of the table's four live data files, from manifest bounds alone, before opening any Parquet: the same min/max pruning as section 3, one level up. Concurrency is optimistic: a writer builds new metadata from the snapshot it read, then asks the catalog to swap the pointer only if it still points where it did; if another writer won, it re-checks for conflicts and retries (spec). Format v2 added row-level deletes through delete files (merge-on-read, the alternative to copy-on-write); v3 adds deletion vectors, row lineage, default values, variant and geospatial types; a v4 is in draft. Current Java release: 1.12.0, 2026-09-29 (releases).

Delta Lake: an ordered log of JSON commits

Delta keeps a folder _delta_log/ of numbered JSON files; commit n is 00000000000000000003.json for n = 3, and creating it atomically (put-if-absent) is the commit (PROTOCOL.md). Each holds actions: add a file (with per-file stats), remove a file, metaData (schema), protocol, commitInfo. The same steps with deltalake 1.6.6 (src/measure/delta_walk.py) wrote four commits; the delete wrote one add (28,798 rows copied) and one remove, exactly like Iceberg's copy-on-write. Readers replay the log; to keep replay short, Delta Spark writes a Parquet checkpoint of the whole state every 10 commits by default (an implementation default, not part of the protocol). Delta also has deletion vectors, liquid clustering (changeable clustering keys instead of fixed partitions) and UniForm, which writes Iceberg metadata for the same files so Iceberg readers can read a Delta table (UniForm). Current: delta-spark 4.4.0.

Apache Hudi, in brief

Hudi is built for streaming upserts, for example from a change-data feed. Its tables are copy-on-write (rewrite base files on update) or merge-on-read (append updates to log files, merge at read time, compact later), with a record-level index mapping each key to its file group so an upsert finds its row fast (table types). Current: 1.2.1 (2026-09-24). Iceberg has the broadest engine support today, which is why the atlas suggests it unless you live in Spark and Databricks (Delta) or stream CDC upserts (Hudi).

Catalogs: where the pointer lives

The atomic step needs one place that holds "current metadata for table X" and can compare-and-swap it. That is the catalog, and in 2026 it is where vendors compete:

  • Iceberg REST catalog: an OpenAPI spec, so any engine talks to any catalog; a commit sends requirements such as "the current snapshot is still 42" plus updates (spec).
  • AWS Glue Data Catalog: has an Iceberg REST endpoint (docs); Amazon S3 Tables (announced 2024-12-03) are buckets that store Iceberg tables and run compaction and snapshot clean-up for you (announcement).
  • Unity Catalog: Databricks' catalog; its open-source version is an LF AI and Data sandbox project, release 0.6.0 (2026-08), serving Delta tables and the Iceberg REST API (unitycatalog.io).
  • Apache Polaris: an Iceberg REST catalog that Snowflake donated; incubating from 2024-08-09, a top-level Apache project since 2026-02-15 (Apache).
  • Nessie (Git-like branches and multi-table commits) and Lakekeeper (a Rust REST catalog) are open-source alternatives; DuckLake (section 6) puts the whole catalog and metadata in a SQL database.

The small-files problem, measured

Streaming or frequent small appends create many small files. Each file costs an open, a footer read and a plan entry; each is compressed on its own, and on S3 each is at least one request. The same 10 million messages, measured with DuckDB 1.5.6 (src/measure/remote_small.py):

The fix is compaction: rewrite many small files into few large ones as a new commit, which readers never notice. Iceberg's rewrite_data_files procedure targets 512 MB files by default; Delta's OPTIMIZE targets 1 GB, and its auto compaction 128 MB (Iceberg procedures, Delta config). Then expire old snapshots and delete files no snapshot references, or storage grows for ever: time travel is paid for in bytes.

When not to use a table format
One team, one engine, data that fits in DuckDB or Postgres: a lakehouse adds a catalog to run, compaction jobs to schedule and snapshot expiry to remember. Its pay-off is many engines (Spark for ETL, Trino or a warehouse for BI, Python for ML) sharing one copy of very large tables with safe concurrent writes.

10. Getting the data there: ETL, ELT, change data capture and dbt

The problem. Every engine on this page holds a copy. The app writes to Postgres; analytics reads somewhere else; something must move the rows, keep the copy fresh enough, and never lose or double-count a message.

Two shapes of pipeline.

  • ETL (extract, transform, load): pull rows out, clean and reshape them in a separate program (a Python job, Spark), then load only the finished tables. It was the norm when warehouse compute was scarce and expensive.
  • ELT (extract, load, transform): copy the raw rows into the warehouse or lake as they are, then transform them inside it with SQL. Cheap separated compute made this the default: the raw copy stays, so a fixed transformation can be re-run over history.

Extracting without hurting the app. A nightly COPY (SELECT ... WHERE created_at >= yesterday) works for append-only tables like messages, as long as it reads from a replica. Rows that change (a user's plan, a deleted chat) need change data capture (CDC): a tool such as Debezium reads Postgres's write-ahead log through a replication slot and emits every insert, update and delete in commit order. That machinery (slots, the outbox pattern, delivery guarantees) is owned by Queues, streams and async work; the leftover risk on the database side, an abandoned slot that keeps WAL forever, is on Running Postgres in production. Landing a change stream in a lake is what Hudi's merge-on-read and Iceberg's row-level deletes are for.

dbt, in one section

dbt is the common tool for the T in ELT. You write each transformed table as one SELECT in a file (a model); dbt works out the order from references between models, runs them in the warehouse, and runs tests (not null, unique, accepted values, relationships) on the results. A daily usage table for the chat product, as an incremental model that only processes new rows on each run (dbt docs):

-- models/daily_tokens.sql
{{ config(materialized='incremental', unique_key=['day', 'model']) }}
select cast(created_at as date) as day, model,
       count(*) as messages, sum(tokens) as tokens
from {{ source('app', 'messages') }}
{% if is_incremental() %}
  -- reprocess the last 2 days: late rows still land in the right day
  where created_at >= (select max(day) - interval 2 day from {{ this }})
{% endif %}
group by 1, 2

The double braces above are dbt's Jinja templating, shown verbatim.

State in October 2026: the Python engine is now called dbt Core v1 (1.12.5, 2026-09-15); the Rust Fusion engine is "v2" and the recommended default, with its runtime open-sourced as dbt Core v2.0 alpha (dbt Fusion); and dbt Labs merged with Fivetran (announced 2025-10-13, completed 2026-06-01) (Fivetran).

Mistakes this prevents, and causes
Incremental models skip rows that arrive late unless the filter looks back (the two days above); a pipeline that is not idempotent double-counts on retry (merge on a unique key, never blind-append in a retried job); and a model graph of 400 SQL files with no owner is its own maintenance problem. Start with plain SQL views; reach for dbt when there are more than a handful of transformations or more than one person.

11. Feeding ML: training data, feature history and point-in-time joins

Training data lives in Parquet. Datasets on the Hugging Face Hub are served as Parquet files (HF docs), so DuckDB can query them by URL with the same range reads as section 6. For your own training sets, everything above applies with two additions. Write shards of a few hundred MB, so many data-loader workers read in parallel and a crashed job resumes from a shard. And choose the sort order for the reads that matter: sorted by time, "everything since the last training run" prunes to a few row groups; sorted by user, "all of this user's data" (a deletion request, a per-user split) does.

Features need history. A feature is an input to a model computed from data ("tokens this user used in the last 7 days", "the user's plan"). To train, each example needs each feature as it was when the example happened. Joining today's value instead is leakage: the model learns from information it will never have at prediction time, scores well offline and disappoints in production.

Measured on the chat data with DuckDB (src/measure/ml_asof.py): one training example per chat (999,951 chats, stamped with their first message), and the user's plan as the feature. The chat data has no plan history, so one was generated (illustrative: 19,968 users, 20%, upgraded from free to pro on a random day). The naive join, today's plan, labelled 198,446 examples "pro"; the point-in-time join labelled 101,517. So 96,929 examples, almost half of the "pro" ones, carried a plan their user did not have yet. Chat 13 started on 2025-09-01; its user upgraded on 2026-05-11; the naive join calls it a pro chat.

-- the plan in force when each chat started: an ASOF join
SELECT e.chat_id, e.ts, p.plan
FROM examples e
ASOF JOIN plan_history p
  ON e.user_id = p.user_id AND e.ts >= p.valid_from

An ASOF join matches each row with the latest row of the other table at or before its timestamp (DuckDB ASOF join). A feature store packages this: an offline store (columnar, the full history, for building training sets with point-in-time joins) and an online store (a key-value store with only the latest value per entity, for serving), filled by the same feature definitions so training and serving agree. In Feast, get_historical_features takes a table of entity keys and event timestamps and joins each feature's latest value at or before each timestamp (Feast point-in-time joins; Feast 0.66.0, 2026-08-21). When you need one, and how it fits the serving path, is on ML system design; datasets themselves are on Topic: data-curation-and-datasets.

The habit that prevents leakage
Keep history instead of overwriting it: an append-only table of changes (valid_from per row), or a lakehouse table you can time-travel, or CDC events landed raw. Then every training set is an ASOF join against an event timestamp, and you can rebuild any past training set exactly.

12. What pros do, and the common mistakes

The path most teams should follow

  1. Start inside Postgres, on a read replica, with a few summary tables refreshed by a job. Under a few million rows of events, that is enough.
  2. When analytic queries take seconds and hurt the app, export to Parquet (nightly, or CDC for changing rows) and query it with DuckDB from notebooks and jobs. One machine handles hundreds of gigabytes.
  3. When dashboards need sub-second answers over billions of fresh events, run ClickHouse (or ClickHouse Cloud), fed by batched inserts.
  4. When many teams, many engines or tens of terabytes share the data, put it in a lakehouse (Iceberg plus a catalog) and/or a cloud warehouse, with dbt for transformations and budget alerts from day one.

Each step adds a system to run and a copy to keep correct, so take the next one only when the current one measurably fails.

Common mistakes

Running analytics on the primary database
Each analytic query over the 10M messages kept Postgres busy for 0.5 to 10 seconds here, reading every page of the table; on the primary that competes with users. Use a replica, or a copy.
Writing Parquet in whatever order rows arrive, then wondering why filters are slow
Pruning works only if the filtered column is clustered: in the lab, one chat's messages cost 0.46 MB sorted by chat and 34 to 86 MB shuffled. Sort by the column most queries filter on (usually time, then a key).
Thousands of tiny files
Streaming jobs that write a file every few seconds: the same 10M rows as about 10,000 files took 124 times longer to aggregate than as one file, and 8% more disk. Batch writes, and schedule compaction.
SELECT * on a pay-per-byte warehouse
BigQuery bills every column selected, even with LIMIT. Name the columns; preview with table previews or a dry run.
Treating a column store as a database for the app
Single-row updates, unique constraints and read-your-writes are where they are weakest (ClickHouse deduplicates only at merge time, and does not fsync inserts by default). Keep the system of record in Postgres.
Partitioning by a high-cardinality column
Partitioning a lakehouse table by user id makes one folder per user and millions of tiny files. Partition by time at a grain that gives files of hundreds of MB; cluster or sort by the key inside.
Never expiring snapshots
Every Iceberg or Delta rewrite keeps the old files for time travel. Without snapshot expiry and orphan clean-up, storage grows for ever, and deleted personal data is still on disk.
Training on today's feature values
Section 11: half of the "pro" examples were leaked. Join features as of each example's timestamp.
Reaching for Spark at 50 GB
A cluster adds minutes of start-up and an operations burden; DuckDB or Polars on one machine finish first at this scale (section 6). Reach for distributed engines when data or concurrency truly exceeds one machine.

OLTP / OLAP
Many small reads and writes of whole rows (the app) / few large reads of a few columns of many rows (analytics).
Row group
A block of rows inside a Parquet file or column store; the unit of skipping.
Column chunk
One column's values within one row group, stored contiguously.
Page
The unit inside a column chunk that is encoded and compressed (a dictionary page, data pages).

How a reader uses this

  1. Read the last 8 bytes: the footer length and PAR1.
  2. Read the footer; decode it (Thrift compact protocol: each field is a one-byte header holding the gap to the previous field id and a type, then the value; integers are variable-length and zigzag-encoded).
  3. For each row group, compare the query's filter with the statistics; skip what cannot match.
  4. For each surviving column chunk the query needs, read its byte range, then page by page: the page header, then the page body (decompress, then decode).

What to notice

  • Nothing is modified in place. Every commit writes new files and a new metadata.json (Iceberg) or the next numbered log file (Delta). That is what makes commits atomic and old versions readable.
  • Schema and partition changes are metadata-only: steps 4 and 7 wrote one metadata.json and no data.
  • The delete rewrote a whole file (copy-on-write, in both formats): 28,798 rows copied to remove 2. Engines that support merge-on-read write a small delete file instead and pay at read time.
  • Snapshots share manifests: the manifest list of each snapshot points at the older manifests unchanged, so a commit costs one new manifest, not a copy of the table's file list.
