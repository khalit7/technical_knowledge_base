The idea in one screen

A Postgres server is one process per connection writing every change first to the write-ahead log (WAL) and leaving old row versions behind. Running it in production is three jobs: ship the WAL somewhere safe (backups, replicas, failover), clean up what it leaves behind (vacuum, freezing), and never let anything pin either in place: an open transaction, an abandoned replication slot, a flood of connections.

Fig. 1, step by step: one server, and the orange pins that page you

  1. One process per connection. The postmaster starts a backend process for every client that connects, and it serves only that client until it disconnects. That is why connections are expensive and poolers exist (sections 1 and 7).
  2. Every change goes to the WAL first. A backend changes 8 KB pages in shared buffers and appends a record of the change to the WAL in pg_wal/. A checkpoint later writes the pages to the table files, and only then is the old WAL recycled (section 1).
  3. Ship the WAL. The WAL is a complete history of every change: archived next to a base backup it is point-in-time recovery (section 2); streamed to another server it is a replica that can take over (sections 3 and 4).
  4. Clean up what it leaves. An update or delete leaves the old row version behind in the table files. VACUUM reclaims the dead versions and freezes old rows so the 32-bit transaction counter can wrap safely (sections 5 and 6).
  5. The two pins. An open transaction stops vacuum and ages transaction IDs; an inactive replication slot keeps WAL until the disk is full. These two, plus a flood of connections, are what pages you.
  6. What a fresh install lacks. No archive, no replica, no pooler and no alerts: a fresh install has none of the blue additions, and adding them is most of this page (sections 2, 3, 7 and 9).

The five rules that prevent most database outages
  1. Backups are continuous and restores are tested: a base backup plus archived WAL, restored on a schedule by a machine, with the restore time written down (section 2).
  2. A replica is not a backup: it copies your mistakes within milliseconds (sections 2 and 3).
  3. Every replication slot has a cap and an alert (max_slot_wal_keep_size), or one dead replica fills the primary's disk (section 3).
  4. Every session has timeouts (statement_timeout, idle_in_transaction_session_timeout), so one forgotten transaction cannot block vacuum and pile up locks (sections 5, 7, 8).
  5. Applications connect through a pooler and max_connections stays in the hundreds, not thousands (section 7).

1. The server: processes, memory, WAL and checkpoints

One process per connection. The postmaster is the parent process; for every client that connects it starts a new operating-system process, a backend, which serves that one connection until it closes (how connections are established). Background processes do the housekeeping: the checkpointer, the WAL writer, the autovacuum launcher and its workers, and WAL senders if you replicate. This one design decision is why connections are expensive and poolers exist (section 7). Everything served by one postmaster from one data directory (often /var/lib/postgresql/18/main, holding every table and index as files, postgresql.conf, pg_hba.conf and the log) is a cluster in Postgres's words: one server, possibly many databases, not a cluster of machines.

Memory: one shared cache, and memory per operation

Two kinds of memory matter (resource settings). shared_buffers is the cache of 8 KB table and index pages shared by every backend: 128 MB by default, about 25% of RAM on a dedicated server is the documented starting point (the operating system's file cache holds much of the rest). work_mem (default 4 MB) is the budget of each sort or hash operation in each running query, and a hash may use hash_mem_multiplier (2.0) times more; past it the operation spills to temporary files. So the server-wide setting multiplies: a query with one sort and one hash join can take three times work_mem, in every active backend at once. Predict: with 100 active connections, what server-wide work_mem takes this 64 GB host past its RAM? Then drag.

The usual answer is a modest server default and a larger work_mem set per role or per session for reports and batch jobs (ALTER ROLE reports SET work_mem = '256MB'; illustrative); how a spill changes a plan, and the temp_files it leaves, is on Query planning and performance. Two more settings round out the memory picture: maintenance_work_mem (default 64 MB) is what VACUUM and CREATE INDEX use, once per autovacuum worker, and effective_cache_size allocates nothing at all: it only tells the planner how much data is likely cached.

WAL and checkpoints: why pg_wal/ grows

Before any change touches a table file, a record describing it is appended to the WAL and flushed; after a crash, Postgres replays the WAL to redo what the table files missed. A checkpoint writes every changed page in memory to the table files; it starts every checkpoint_timeout (5 minutes) or after max_wal_size (1 GB) of WAL, whichever comes first (WAL settings), and after it the WAL before that point is no longer needed for crash recovery, so its segments are recycled. On a healthy server pg_wal/ therefore stays near max_wal_size. For operations, the point is: the WAL is a complete history of every change, so shipping it elsewhere gives you both backups (section 2) and replicas (section 3), and anything that still needs old WAL (a failing archive command, a replica that is behind, a slot) stops the recycling, which is the mechanism behind most disk-full pages. Why the first change to a page after a checkpoint writes the whole page, and what longer checkpoint intervals cost in recovery time, is on Storage engines and indexes.

2. Backups and point-in-time recovery

Two numbers define what "backed up" means, and the product owner agrees them before anyone picks a tool. The recovery point objective (RPO) is how much recent data you may lose, measured in time: "RPO 24 hours" accepts losing a day of writes, which a chat product cannot. The recovery time objective (RTO) is how long the restore may take, from "we need to restore" to "users are back", set by database size, disk and network speed and how practised the procedure is.

Logical against physical

A logical backup (pg_dump) asks the database for its contents: CREATE TABLE statements and the rows. A physical backup (pg_basebackup, or a tool on the same mechanism) copies the data directory's files while the server runs, plus the WAL needed to make that copy consistent. Point-in-time recovery: the most important picture on this page

Because the WAL records every change, a base backup plus every WAL segment written since lets Postgres rebuild the database at any moment you choose. You switch it on with three settings: wal_level = replica (the default), archive_mode = on, and an archive_command that copies each finished 16 MB segment somewhere safe and returns success only once the file is stored (WAL settings). To recover, restore the base backup, tell Postgres where the archive is (restore_command) and when to stop (recovery_target_time), and start it. Below, a nightly backup at midnight, a normal day of messages, and at 14:03 a cleanup that lost its WHERE clause, recovered both ways. Predict how many of the day's messages each method keeps, then watch both (the toggle swaps the method).

  1. 00:00 Nightly backup. pg_dump writes the whole database to one file (33.9 MB here). That file is the database as of midnight, and nothing after.
  2. Morning: messages arrive. Users write messages all morning. None of them is in last night's file, and no WAL is kept.
  3. 14:02:59 The last good moment. 1,012,000 messages: 12,000 of them written today.
  4. 14:03:00 DELETE FROM messages; A cleanup meant for one chat runs without its WHERE clause. Every message is gone, and the replica deleted them too, milliseconds later.
  5. 14:05 Alert; two more messages arrive. Users notice. Two new messages are written to the now empty table.
  6. Restore into a new server. pg_restore loads the midnight file into a fresh server: 1,000,000 messages (2.18 s here, measured).
  7. Replay. Nothing to replay: a dump is one moment. The recovered server stays at midnight.
  8. Result: 12,000 messages lost. Everything written since midnight; the RPO was 14 hours.
  1. 00:00 Base backup. pg_basebackup copies the data files (WAL start point 0/14000028), and from now on every finished 16 MB WAL segment is copied to the archive by archive_command.
  2. Morning: messages arrive. Each change is in the WAL, and full segments go to the archive within seconds.
  3. 14:02:59 The last good moment. 1,012,000 messages; the archive holds every change since midnight.
  4. 14:03:00 DELETE FROM messages; The same mistake. Its 1,012,000 delete records and its COMMIT record (transaction 738, LSN 0/2209DC60, in segment ...22) are now in the WAL like any other change.
  5. 14:05 Alert; two more messages arrive. Users notice. Two new messages are written to the now empty table.
  6. Restore the base backup into a new server. 1,000,000 messages: the state at 00:00.
  7. Replay the archive to 14:02:59. Postgres fetches the archived segments ...14 to ...22 one by one (restore_command), redoes every change, and stops just before the DELETE's commit: recovery stopping before commit of transaction 738.
  8. Result: nothing written before the mistake is lost. All 1,012,000 messages are back (recovery took 1.64 s here). The 2 messages written after 14:03 exist only on the old server; copy them across, or recover to a side server and copy the deleted rows back.

Row counts, segment names, the recovery log line and the recovery times are from the real run; the clock times are illustrative (the run compressed "the day" into ten seconds: six batches of 2,000 messages, then the DELETE).

The recovered server stops replaying just before the DELETE's commit record (recovery stopping before commit of transaction), so the delete simply never happened. Three details decide a real incident:

  • Finding the moment. pg_waldump prints each WAL record; the bad transaction shows up as a million heap delete records followed by one COMMIT with a timestamp. Recover to just before it, or name it with recovery_target_xid and recovery_target_inclusive = false.
  • A new timeline. The recovered server says selected new timeline ID: 2: a branch of history whose WAL files carry the new timeline in their names, so they never mix with the old ones in the archive.
  • Writes after the mistake. Recovering to 14:02:59 also drops everything written after 14:03 (two messages in the run), so you usually recover into a separate server and copy the deleted rows back with SQL. That is a product decision: say it in the incident channel.

A replica is no help here: it applied the DELETE milliseconds later. A delayed replica (recovery_min_apply_delay = '1h') gives you an hour to stop it, a useful extra, never a substitute for archived WAL.

Tools, and what managed services do

Nobody writes cp archive commands in production. Three open-source tools take base backups, archive WAL, keep retention, compress, encrypt and restore against object storage such as S3: pgBackRest (the common choice for self-managed Postgres: full, differential and incremental backups, parallel compression, asynchronous archiving, verification; user guide), WAL-G (one Go binary, popular in Kubernetes and cloud setups, delta backups to S3, GCS or Azure) and Barman (EDB's backup server, pulling from many Postgres servers). Amazon RDS keeps automated backups for up to 35 days and uploads transaction logs to S3 every five minutes, so its point-in-time restore can lose up to about five minutes (RDS PITR docs).

A backup you have not restored is not a backup

GitLab.com lost about six hours of data in January 2017 with every backup method in place and none ever restored (the story is below). A restore that runs on a schedule is the only proof a backup works:

What "tested restores" means in practice
  • A scheduled job (weekly at least) restores the latest backup to a scratch server, replays WAL to a recent moment, and checks that the server starts, key row counts are close to production's and a smoke query works. It alerts if any step fails.
  • It records how long the restore took: that number, not a guess, is your RTO. Here 221 MB took under two seconds; at a realistic 200 MB/s a 2 TB database takes about three hours before any WAL replay (2,000,000 MB / 200 MB/s = 10,000 s; illustrative speed).
  • Backups go to another account or project with delete protection (object lock), so a compromised production account or a bad script cannot delete them too.
  • Alert when the archiver fails (pg_stat_archiver.failed_count rising) and when the newest backup is older than its schedule.
The GitLab 2017 outage (case)

3. Replication: a live copy on another machine

A backup gets the data back after hours. A replica (or standby) is a second server kept within milliseconds of the primary, so it can take over in seconds and serve read-only queries meanwhile. In streaming replication a WAL sender process on the primary streams WAL records over an ordinary connection to a WAL receiver on the replica, which writes them, flushes them and replays them into its table files exactly as crash recovery would (high availability docs). The replica starts as a base backup; pg_basebackup -R also writes the connection settings and a standby.signal file that keeps it a replica.

  1. Commit on the primary. The backend's WAL record is flushed to the primary's own pg_wal/. With asynchronous replication (the default) the client is told "committed" now.
  2. Streamed and written: write_lag ends. The WAL sender sends the record over an ordinary connection and the replica's WAL receiver writes it: the network part (0.000247 s in the run below).
  3. Flushed: flush_lag ends. The receiver flushes it to the replica's disk, so it survives a replica crash (0.000248 s).
  4. Replayed: replay_lag ends. The startup process applies it to the replica's table files exactly as crash recovery would; only now does a query on the replica see the row. Normally this is about 1 ms (median 1.27 ms with 8 writers, measured).
  5. Replay stalls, WAL piles up. Pause replay (or run a long replica query that conflicts with it): records still arrive and are flushed in milliseconds, but wait unapplied. 9.5 s into the pause: replay_lag 00:00:09.355926 and 79 MB not yet replayed.

The primary reports each replica's progress in pg_stat_replication (monitoring docs): write_lag (received and written, not yet flushed), flush_lag (on the replica's disk, survives a replica crash), replay_lag (applied, visible to queries there). They separate the network, the replica's disk, and its single replay process.

Replication slots, and why they fill disks

If a replica disconnects, the primary may recycle WAL the replica still needs. A replication slot prevents that: a bookmark on the primary that keeps all WAL from its position until the consumer confirms it. The other side of the promise: if the replica never comes back, the primary keeps WAL until its disk is full and it stops. Measured with the replica stopped and ordinary updates running, the slot held 1091 MB (wal_status extended) and pg_wal/ reached 1120 MB:

Since PostgreSQL 13 max_slot_wal_keep_size caps what a slot may hold (default -1, unlimited: replication settings); past it the slot is marked lost and the replica must be rebuilt from a fresh base backup (here 2.3 s for 774 MB on one laptop; hours for terabytes over a network). Since PostgreSQL 18 idle_replication_slot_timeout can also invalidate slots inactive too long. wal_status says how close you are: reserved (within max_wal_size), extended (beyond it, still kept), unreserved (removed at the next checkpoint), lost (pg_replication_slots).

Rule
Set max_slot_wal_keep_size to what your disk can afford, alert on slots where active is false or retained WAL exceeds a few GB, and drop slots for replicas that are gone. A slot that carries an xmin (logical slots always do) also holds back vacuum and freezing (sections 5 and 6).

Synchronous replication: no lost commits, at a price

By default replication is asynchronous: the primary confirms a commit once its own WAL is flushed, and the replica gets it a moment later; if the primary dies in that moment, failover loses those commits. With synchronous_standby_names set, a commit waits for a named standby, and synchronous_commit picks how far: remote_write (written there), on (flushed there), remote_apply (replayed, so a read there sees it) (WAL settings). local and off skip the standby; off does not even wait for the primary's own disk, so a crash can lose the last fraction of a second of commits (it never corrupts the database).

With on throughput fell from 27,568 to 11,562 inserts per second, mostly the extra round trip per commit; across availability zones (about 1 ms apart) or regions (tens of ms) the cost grows with distance. The sharp edge: if the only synchronous standby goes away, every commit on the primary waits forever. In the run, the insert sat in wait_event SyncRep; cancelling it printed The transaction has already committed locally, but might not have been replicated to the standby, so cancelling does not undo the commit. The usual production setting is therefore synchronous_standby_names = 'ANY 1 (replica_a, replica_b)': wait for any one of two (quorum commit), so losing one does not stop writes. Patroni can also drop synchronous mode when no standby is healthy, trading a small data-loss window for availability.

Logical replication: copying rows, not files

Streaming replication copies the cluster byte for byte, so the replica runs the same major version and cannot be written to. Logical replication decodes the WAL into row changes and applies them on a subscriber, a normal writable database that may run a different major version and hold only some tables: a PUBLICATION on the source, a SUBSCRIPTION on the target, wal_level = logical. It is used for major upgrades with seconds of downtime (section 10), moving to another host or cloud, feeding tables to analytics, and change data capture into Kafka with Debezium, which reads a logical slot (Queues, streams and async work). Its limits (restrictions): schema changes (DDL), sequence values and large objects are not replicated, and every replicated table needs a primary key or replica identity for updates and deletes.

4. Failover: when the primary dies

Failover is making a replica the new primary and pointing the application at it. Postgres does one step, promotion: the replica stops replaying, starts a new timeline and accepts writes (pg_ctl promote, 0.12 s here). The hard parts are around it: deciding the primary is really dead and not just cut off from the monitor, making sure it can no longer accept writes, moving the connections, and bringing the old primary back. Get the first two wrong and you have split brain: two servers that both accept writes. Watch both ways on the same partition (the toggle swaps them):

  1. Normal. The primary takes every write and streams WAL to the replica.
  2. A partition. The monitor and the replica lose the primary. It is not dead: some clients still reach it and keep writing.
  3. Promote the replica by hand. pg_ctl promote: server promoted in 0.12 s, on a new timeline. Nobody stopped the old primary.
  4. Split brain. Both accept writes. In the run, row 2150968 is written to the OLD primary on one side and written to the NEW primary on the other.
  5. Repair: pg_rewind. The old primary is rewound to the point the histories diverged (0/B1000060), copying 211 MB of 908 MB, and rejoins as a replica. Its write is gone: a data loss for whoever made it.
  1. Normal, with a leader lock. The primary holds the leader lock in the consensus store (etcd) and renews it before its time to live runs out. Only the lock holder may be primary.
  2. A partition. The same partition: the primary can no longer reach etcd to renew the lock.
  3. The lock expires: the old primary fences itself. It demotes itself and stops taking writes (a watchdog resets it if it hangs). Its clients get errors, not a second history.
  4. The replica takes the lock, then promotes. Applications follow the new primary through DNS, a pooler or target_session_attrs=read-write. One history; only commits not yet replicated (asynchronous mode) can be lost.
  5. The old primary rejoins. pg_rewind as before, but it has nothing of its own to discard.

The promotion, the two conflicting rows and the pg_rewind numbers are from the real run (the split brain was staged by promoting the replica while the old primary kept running); the leader-lock frames follow Patroni's documentation, not run here.

In the run, row id 2150968 held written to the OLD primary on one server and written to the NEW primary on the other; neither is right, and merging is manual, row by row. (GitHub's 2018 outage began this way; below.) Fencing prevents it: before promoting, make sure the old primary cannot accept writes, by stopping it, cutting its network or powering it off through the cloud API (the old name is STONITH, "shoot the other node in the head"). The old primary is then repaired with pg_rewind, which copies back only the blocks changed since the histories diverged (211 MB of 908 MB here) and discards the old side's writes: correct for the database, a data loss for whoever wrote them, which is why fencing comes first.

Patroni and managed failover

Patroni (patroni/patroni) runs beside each Postgres server and keeps a leader lock with a time to live in a consensus store (etcd, Consul, ZooKeeper or Kubernetes). Only the holder may be primary: a primary that cannot renew the lock demotes itself, and a replica promotes only after acquiring it, so "who is primary" is answered once by the store, the problem Raft solves (Distributed systems fundamentals). A hardware or software watchdog can reset a primary that hangs. On Kubernetes, CloudNativePG plays the same role. Applications find the current primary through a DNS name, a load balancer, a pooler, or a multi-host connection string with target_session_attrs=read-write. Managed services run the equivalent: Amazon Aurora says a failover typically restores service in under 60 seconds and often under 30 (Aurora high availability). Two things stay yours: the application must reconnect and retry, because connections to the dead primary fail mid-transaction (Reliability engineering), and with asynchronous replication the last commits before the failure may be lost. Jepsen also found that RDS Multi-AZ clusters for PostgreSQL 13.15 to 17.4 could show replica reads that violate snapshot isolation (Long Fork), because of how stock replicas decide which transactions are visible (Jepsen, 2025-04-29): read from the primary when correctness matters.

Versions when read: Patroni v4.1.5 (2026-08-12), CloudNativePG v1.30.1 (2026-09-23).

5. Vacuum and autovacuum: the cleaning crew

Postgres never overwrites a row in place: an UPDATE writes a new version and marks the old one replaced, a DELETE only marks the row, and old versions stay while any running transaction might still see them (MVCC, on Transactions and concurrency). Once no transaction can see a version it is a dead tuple (tuple is Postgres's word for a row version). VACUUM removes dead tuples and their index entries and marks the space reusable; it also records which pages are all-visible (so index-only scans can skip the table) and freezes old rows (section 6). Autovacuum is the background launcher that runs VACUUM and ANALYZE on each table when enough has changed.

When autovacuum runs

A table is vacuumed when its dead tuples exceed autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × rows, by default 50 + 20% of the table (vacuum settings). The launcher checks every autovacuum_naptime (1 minute) with up to autovacuum_max_workers (3) workers, each slowed by a cost limit (autovacuum_vacuum_cost_delay 2 ms per 200 cost units) so it does not swamp the disk. PostgreSQL 18 added autovacuum_vacuum_max_threshold (default 100 million), so a huge table no longer waits for a fifth of itself to die: at the default 0.2, a billion-row table would otherwise collect 200 million dead rows first. Predict that number for a billion rows at 0.01, then drag.

On a big table the default 20% is enormous: per-table scale factors exist for this

Dead tuples before autovacuum starts = 50 + scale factor × rows, capped at 100,000,000 in PostgreSQL 18. Updates per second to reach it in an hour = threshold / 3,600.

Watching it on a churned table

The test table is chat_state: one row per chat (100,000 rows) with an unread count and the time of the last message, updated whenever a chat gets a message, the hottest kind of table a chat product has. pgbench updates random rows at a steady 1,500 per second; the launcher checks every 5 s instead of every minute so a cycle fits on screen; everything else is default. Fig. 5 draws the table's pages through the same four phases, with the run's numbers:

  1. A table is 8 KB pages of row versions. chat_state's 100,000 rows fill 879 pages (autovacuum's own log says so). The visibility map keeps one bit per page, set while every row on it is visible to everyone; vacuum and index-only scans skip those pages.
  2. HOT updates mostly clean up after themselves. When an update changes no indexed column and the page has room, Postgres writes a heap-only tuple (HOT): the new version goes on the same page, no index is touched, and the next visitor to a full page prunes dead versions on the spot. In the run, 93% of the first 58,564 updates were HOT and dead tuples never passed 4,757, with no VACUUM at all.
  3. One index on the updated column: every update is a full one. An index on last_message_at (for "chats by recent activity") makes each update write its new version wherever there is room plus a new index entry, and leave a dead version behind: about 1,500 a second. Before indexing a hot table, compare n_tup_hot_upd with n_tup_upd; free space in each page (fillfactor = 90) makes HOT more likely.
  4. Autovacuum is a sawtooth. Dead tuples rise to the trigger (50 + 0.2 × 100,000 = 20,050) and autovacuum removes them and their index entries, marks the space reusable and sets the visibility bits again. New versions reuse the space, so the table grows a little, then holds: five runs in 80 s, a healthy steady state.
  5. One forgotten transaction stops all cleanup. A session that ran one SELECT inside a transaction and never committed keeps its snapshot, so no row version newer than it can be removed, in any table. Autovacuum keeps running and removes nothing; its log says tuples: 0 removed, 182379 remain, 82363 are dead but not yet removable with a removable cutoff that does not move, and the table grows to 1,552 pages.
  6. End the session; one VACUUM. pg_terminate_backend(pid) ends it; a manual VACUUM then removed 89,743 dead versions in a fraction of a second. 1,615 pages remain: the space is free inside the file, which keeps its size. Set idle_in_transaction_session_timeout (section 7). A replication slot with an old xmin, a replica with hot_standby_feedback = on running a long query, or an abandoned prepared transaction (section 6) pin the snapshot the same way.

VACUUM against VACUUM FULL

Plain VACUUM makes space reusable but almost never returns it to the operating system: the file keeps its size. VACUUM FULL rewrites the table into a new compact file and rebuilds its indexes, which does return space, under an ACCESS EXCLUSIVE lock for the whole rewrite: nothing can even read the table.

On this 200 MB table the lock lasted under two seconds (a reader with lock_timeout gave up while it ran); on a 500 GB table it would be hours of a table nobody can read. Online, you reclaim space with pg_repack or pg_squeeze, which build a copy in the background, replay the changes made meanwhile and take the exclusive lock only for a brief swap (both are extensions missing from the pgserver build, so not measured here). Often you need neither: if the table will grow back, reusable space is fine.

6. Transaction ID wraparound: the outage that stops all writes

Every transaction that writes gets a transaction ID (XID), a 32-bit counter, and every row version records the XID that created it. Visibility asks "was this row created by a transaction older than mine?", and with 32 bits that comparison is done modulo 232: each XID sees about 2.1 billion (231) IDs as the past and the rest as the future. A row whose creator fell more than 231 behind would suddenly look like it came from the future and vanish. So VACUUM freezes old rows, marking them older than every transaction, and each table remembers its oldest unfrozen XID (relfrozenxid; the database's minimum is datfrozenxid) (routine vacuuming). Fig. 6 draws the counter as the circle it is, and walks the run from a healthy age to the refusal and back:

  1. 232 IDs on a circle. Every writing transaction takes the next XID, and comparisons wrap: from the current XID, the 231 IDs behind it are the past and the 231 ahead are the future.
  2. Freezing keeps the past short. VACUUM freezes old rows as it goes, so only the arc from the oldest unfrozen XID (datfrozenxid) to now matters: its length is the age. A healthy database saws between 0 and 200 million.
  3. 200 million: aggressive autovacuum. Past autovacuum_freeze_max_age every table this old gets an anti-wraparound vacuum that scans every unfrozen page, even with autovacuum switched off. If the age keeps rising here, something is holding the oldest XID.
  4. Something holds the oldest XID. A forgotten prepared transaction (refund-42 in the run), an open transaction or a slot's xmin stops freezing at its XID, so the age grows with every transaction: this page's alerts fire at 500 million (warn) and 1 billion (page); at 1.6 billion (vacuum_failsafe_age) vacuum drops its cost limits and skips index cleanup. Still silent in the log: only your alert has fired.
  5. 40 million left: warnings. Every command logs WARNING: database "template0" must be vacuumed within 3000299 transactions (the run was started just short of the limit, so the first warning already shows about 3 million).
  6. 3 million left: writes refused. 308 more inserts succeeded, then ERROR: database is not accepting commands to avoid wraparound data loss, while reads still worked. The holder query found refund-42, a prepared transaction 2,144,483,647 XIDs old.
  7. The fix: remove the holder, then VACUUM. ROLLBACK PREPARED and a normal VACUUM (FREEZE) brought every database back to an age under 300 in 0.36 s; the oldest unfrozen XID jumps to now.

Thresholds from the PostgreSQL 18 documentation: aggressive freezing autovacuum at 200 million (autovacuum_freeze_max_age), even with autovacuum switched off; the failsafe at 1.6 billion (vacuum_failsafe_age) drops the cost limits and skips index cleanup; warnings at 40 million before the wraparound point; refusal of new XIDs at 3 million before it. The 500 million and 1 billion alert lines are this page's suggestion. The circle is to scale: 231 = 2,147,483,648 is half of it, so the last 40 million are under 2% of the half-turn, which is why the figure moves in close for steps 5 and 6.

Freezing can only advance up to the oldest transaction anything still needs, so the causes are those of section 5: a transaction left open, an abandoned prepared transaction (from two-phase commit; it survives restarts until someone commits or rolls it back by name), a replication slot holding an old xmin, or autovacuum too slow for a write-heavy database. Two billion transactions take weeks even on a busy server, so for this page a throwaway server's counter was moved forward with pg_resetwal -x, just short of the refusal point, after leaving behind a forgotten prepared transaction; from then on every line in steps 5 to 7 is real.

Stale advice in the error itself
PostgreSQL 16's refusal message still says Stop the postmaster and vacuum that database in single-user mode. The current documentation says single-user mode should be avoided whenever possible and a normal VACUUM works, which is what fixed it above on this tiny database (routine vacuuming, PostgreSQL 18). Remove what holds the XID back first; a VACUUM before that freezes nothing.

max_connections, and the arithmetic nobody did

max_connections defaults to 100, needs a restart to change, and keeps 3 for superusers (connection settings); in the run the application role got 97 connections and the next was refused with FATAL: remaining connection slots are reserved for roles with the SUPERUSER attribute. It runs out through pools: SQLAlchemy's default is 5 connections plus up to 10 overflow per process (SQLAlchemy pooling), so twenty pods can open 20 × 15 = 300, a deploy briefly runs old and new pods together (600), and workers and cron jobs add theirs. Raising max_connections to thousands is the wrong fix: most would sit idle, and the active ones fight over the same cores and locks. The PostgreSQL wiki's rule of thumb for the number of active connections that gives the best throughput is about (2 × CPU cores) + number of disks (wiki: Number Of Database Connections; a starting point to measure from, not a law).

PgBouncer: many clients, few server connections

PgBouncer is a small single-process pooler that speaks the Postgres protocol, so applications connect to it as if it were the database. Its pool_mode decides when a server connection is lent: session (a client keeps one from connect to disconnect: everything works, it only saves the connect cost), transaction (one transaction at a time, then it goes back: hundreds of mostly idle clients share a few; the mode almost everyone runs) and statement (returned after every statement, so multi-statement transactions are refused; rare). Fig. 7 shows what that buys, with the run's numbers:

  1. Without a pooler: one backend per client. max_connections = 100 with 3 kept for superusers: the application role got 97 backends, and the next connection was refused with remaining connection slots are reserved.
  2. PgBouncer in front: 1,000 clients, 20 server connections. The clients connect to PgBouncer as if it were the database; with default_pool_size = 20, Postgres sees 20 backends.
  3. Transaction mode: lent for one transaction. A client gets a server connection when its transaction starts and gives it back at COMMIT; the next client in line takes it, so a few connections serve hundreds of mostly idle clients.
  4. More work than connections: a short queue. With 300 clients running a 50 ms transaction at once, SHOW POOLS printed cl_active 832, cl_waiting 168, sv_active 20. That queue is far cheaper than a thousand processes fighting over the cores.

A session SET rides the server connection to the next client

The two ways transaction pooling bites

In transaction mode one client's consecutive transactions may run on different server connections, and one server connection serves many clients, so anything that lives in the session breaks: SET, LISTEN, session advisory locks, WITH HOLD cursors, temporary tables kept across transactions, SQL-level PREPARE (PgBouncer feature table). Both of these happened on the first try. The first, step by step:

  1. A borrows server connection 1. Client A starts a transaction; PgBouncer lends it server connection 1. Both server connections have the default statement_timeout (0, off).
  2. A runs SET statement_timeout = '5s'. A session-level SET changes the server connection's session, not client A: PgBouncer passes it through.
  3. A's transaction ends; the connection goes back. Transaction mode returns connection 1 to the pool the moment the transaction ends, still carrying 5s.
  4. B gets connection 1, and A's setting. Client B never ran SET, but SHOW statement_timeout says 5s. Any query of B's longer than 5 s is now cancelled.

Pool of two server connections; which connection each client gets is drawn, the timeouts each client saw are from the run (measured: client B saw 5s in ten of ten SHOW statement_timeout).

No error reports the first: it is a correctness bug. Use SET LOCAL inside a transaction, or set defaults per role (ALTER ROLE app SET statement_timeout = '5s'). The second is a crash that appeared only after the fifth execution: psycopg 3 prepares a query on the server automatically once it has run five times (prepare_threshold), and asyncpg and many JDBC setups do the same; with max_prepared_statements = 0, 3 of 30 runs failed with DuplicatePreparedStatement: prepared statement "_pg3_0" already exists, with 200 none did. PgBouncer has tracked protocol-level prepared statements since 1.21.0 and, since 1.24.0, does so by default with max_prepared_statements = 200 (changelog); the run set 0 to reproduce what older configurations still do. Check the setting before blaming the driver.

8. Safe schema changes: the lock queue

Most ALTER TABLE forms need an ACCESS EXCLUSIVE lock, even when the change itself is metadata-only and takes a millisecond. The danger is not the change but the queue: locks are granted in order, so an ALTER waiting behind one long transaction makes every later query on that table wait behind the ALTER, even plain reads that would not conflict with the long transaction. Staged on users:

The first process, blocked by nobody, is idle inside a transaction that read users; the ALTER TABLE ... ADD COLUMN waits for its exclusive lock; the three SELECTs are blocked by the ALTER, not by the idle transaction. Ending either releases all of them. In production every migration therefore runs with a short lock_timeout and retries, so a blocked ALTER gives up in seconds instead of queueing the site:

SET lock_timeout = '3s';      -- give up instead of queueing every reader behind us
ALTER TABLE users ADD COLUMN locale text;
-- on "canceling statement due to lock timeout": wait, retry with backoff, alert after a few attempts

Slow forms get safe recipes: CREATE INDEX CONCURRENTLY, ADD CONSTRAINT ... NOT VALID then VALIDATE CONSTRAINT, a nullable column backfilled in batches. Which of 21 common changes takes which lock, rewrites the table or scans it, measured with the recipes and a lock-queue animation with and without lock_timeout, is the "ALTER TABLE, measured" tab of SQL and data modelling.

10. Upgrades: minor releases and major versions

In 18.6, 18 is the major version and 6 the minor release. Minor releases only fix bugs and security issues and never change the on-disk format: install the new binaries and restart, after reading the release notes for occasional extra steps; they come roughly quarterly (18.6 and 17.11 on 2026-08-13: release notes). A major version comes once a year, may change the catalogs and storage format, so the data directory must be converted, and is supported for five years (versioning policy):

Five years each: PostgreSQL 14 ends on 2026-11-12

Support windows from the versioning policy page, read 2026-10-04; the vertical line is that day, about five weeks before 14's end. Managed services charge or force-upgrade after end of life (Amazon calls it RDS Extended Support), so "we will upgrade later" has a date: plan major upgrades a year ahead and rehearse them on a restored copy.

pg_upgrade: convert in place

pg_upgrade creates the new version's empty cluster, copies the schema with pg_dump, then moves the data files across unchanged, since the table format rarely changes. Its modes decide how the files move: copy (safe, slow for big databases), --link (hard links: seconds for any size, but the old cluster is unusable once the new one has started), --clone (copy-on-write file systems) and, since PostgreSQL 18, --swap (moves directories, often the fastest) (pg_upgrade docs). Always run --check first. Measured, 16.2 to 17.11, both servers stopped throughout:

On this 221 MB database both modes took about two seconds, almost all of it the fixed cost of dumping and restoring the schema; copy mode adds the time to copy every byte (about 17 minutes per terabyte at 1 GB/s, illustrative disk speed), link mode does not. Before PostgreSQL 18 planner statistics are not carried over, so until vacuumdb --analyze-in-stages finishes, queries can get bad plans; PostgreSQL 18's pg_upgrade keeps them (18 release notes). Downtime is the whole run plus restarts. Physical replicas cannot follow a major upgrade: they are rebuilt, or upgraded with the rsync procedure in the docs.

Logical replication: upgrade with seconds of downtime

For large databases, build a server on the new version, copy the schema, subscribe it to the old one with logical replication (section 3), let it catch up while the old one serves, then switch the application. Measured, 16 publishing to 17, with the classic trap at the end: logical replication copies rows, not sequence positions, so the new server's messages_id_seq was still at 1 (the old one at 1231288) and the first insert failed with duplicate key value violates unique constraint "messages_pkey". At cutover: stop writes, wait for the subscriber to catch up, copy every sequence's value (setval), then move traffic. Also plan for tables without a primary key, schema changes during the migration (not replicated) and large objects. 11. Security basics

The database gets the narrowest door, in four layers from outside in. Network: no public IP; only the application's subnet (and a bastion or VPN for humans) reaches port 5432. Who may connect: pg_hba.conf, where each line is type database user address method, read top to bottom, first match wins (pg_hba.conf docs); use hostssl lines and scram-sha-256 passwords, the default since PostgreSQL 14 (MD5 passwords are deprecated and PostgreSQL 18 warns when one is set: 18 release notes). Encryption in transit: ssl = on on the server and sslmode=verify-full on clients, so they also check the server's certificate (anything weaker can be intercepted). Least privilege: a role is a user or a group; each kind of client gets its own with only what it needs, the application does not own the tables, and nothing runs as a superuser. Least privilege also limits mistakes: a role without DELETE on messages cannot run section 2's 14:03 statement at all.

GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly;
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app;   -- tables created later too
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA public GRANT SELECT ON TABLES TO readonly;

Subnets and role names are illustrative. Since PostgreSQL 15 ordinary roles can no longer create objects in the public schema by default (15 release notes).

Two more layers when the product needs them: row-level security, so the database itself filters rows by tenant and a bug in one query cannot leak another customer's chats (taught with the chat schema on SQL and data modelling; RLS docs), and auditing (the pgaudit extension, or the managed service's audit log) to record who read or changed what. Keep credentials in a secret manager, rotate them, and give humans individual named roles so the log says who did it.

12. Managed Postgres: what it takes off your plate

A managed service runs the server: provisioning, minor upgrades, automated backups and point-in-time restore, a standby with automatic failover, dashboards. It does not design your schema, fix slow queries, size your connection pools, tune autovacuum for your hottest table, choose when to do a major upgrade, or test that a restore gives you what you need: sections 5 to 10 stay your job. How to choose: on a cloud already, its stock managed Postgres (RDS, Cloud SQL, Azure Flexible Server) is the default; Aurora and AlloyDB buy faster failover, more readers and storage that grows by itself, at a higher price and with less portability; Neon and Supabase suit small, spiky or many-database workloads and fast-moving teams; running it yourself (Patroni or CloudNativePG, pgBackRest, PgBouncer, postgres_exporter) is cheapest in money and most expensive in on-call time. Safe to defer: none of the five rules at the top.
