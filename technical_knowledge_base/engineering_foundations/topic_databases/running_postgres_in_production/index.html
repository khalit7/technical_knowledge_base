Running a database in production means keeping three promises: the data survives anything (backups you have actually restored), the database stays up when a machine dies (replication and failover), and it stays fast and healthy as it ages (vacuum, connections, upgrades, monitoring). Postgres (PostgreSQL, the free relational database the root page recommends as the default) keeps none of these promises for you out of the box. A fresh install has no backups, no replica, no connection pooler and no alerts. This page is what you add, why, what it costs, and what to do at 3 a.m. when it goes wrong.

Being on call means you are the person paged (alerted on your phone) when the service breaks, and you are expected to diagnose and fix it, or at least stop the bleeding, within minutes. The rest of this page is organised around what pages you. The data is the root's chat product at one tenth of its size: 10,000 users, 100,000 chats, 1,000,000 messages (about 220 MB on disk), made by the same generator with the same seeds.

The five rules that prevent most database outages
  1. Backups are continuous and restores are tested: a base backup plus archived write-ahead log, restored on a schedule by a machine, with the restore time written down (section 3).
  2. A replica is not a backup: it faithfully copies your mistakes within milliseconds (sections 3 and 4).
  3. Every replication slot has a cap and an alert (max_slot_wal_keep_size), or one dead replica can fill the primary's disk (section 4).
  4. Every session has timeouts (statement_timeout, idle_in_transaction_session_timeout), so one forgotten transaction cannot block vacuum and pile up locks (sections 6 and 8).
  5. Applications connect through a pooler and the server's max_connections stays in the hundreds, not thousands (section 8).

What this page does not repeat: how MVCC (the row versions behind vacuum) and locks work is on Transactions and concurrency; pages, the write-ahead log and indexes are on Storage engines and indexes; finding and fixing slow queries and tuning memory settings is on Query planning and performance; schema migrations and the locks ALTER TABLE takes, measured, are on SQL and data modelling (its tab "ALTER TABLE, measured"); replication theory, consistency and consensus are on Distributed systems fundamentals; read replicas for scale and sharding are on Scaling a database.

1. What a running Postgres server is

You cannot operate what you cannot picture. A Postgres server on one machine is five things, and every operation on this page touches one of them.

One Postgres server (drawn, not to scale). Each client connection gets its own process; all of them share one memory area of cached pages; every change is first written to the write-ahead log, which is also what backups archive and replicas replay.

  • The postmaster and one process per connection. The postmaster is the parent process; for every client that connects it starts a new operating-system process, a backend, which serves that one connection until it closes (PostgreSQL docs: how connections are established). This one design decision is why connections are expensive and why poolers exist (section 8). Background processes do housekeeping: the checkpointer, the WAL writer, the autovacuum launcher and its workers, and, if you replicate, WAL senders.
  • Shared buffers. A block of memory shared by all backends where 8 KB pages of tables and indexes are cached (shared_buffers, default 128 MB; the docs suggest about 25% of RAM on a dedicated server: resource settings).
  • The data directory. One folder on disk (often /var/lib/postgresql/18/main) holding every table and index as files, the configuration (postgresql.conf, pg_hba.conf) and the log. Postgres calls everything served by one postmaster from one data directory a cluster (not a cluster of machines: one server, possibly with many databases).
  • The write-ahead log (WAL). Before any change touches a table file, a record describing it is appended to the WAL and flushed to disk; after a crash, Postgres replays the WAL to redo what the table files missed. It is stored as 16 MB segment files in pg_wal/. A position in the WAL is an LSN (log sequence number), written like 0/2209DC60. How and why this works is on Storage engines and indexes. For operations, the point is: the WAL is a complete history of every change, so shipping it elsewhere gives you both backups and replicas.
  • Checkpoints. Periodically, every changed page in memory is written to the table files and the WAL before that point is no longer needed for crash recovery, so old segments are deleted or recycled. Anything that still needs old WAL (an archive that is failing, a replica that is behind) stops that cleanup, and pg_wal/ grows. That is the mechanism behind half the disk-full incidents in section 4.

3. Backups done right

Two numbers define what "backed up" means for you. Agree them with whoever owns the product before choosing any tool.

RPO: how much data you can lose

The recovery point objective is the age of the newest data you can get back, measured in time. "RPO 24 hours" means losing up to a day of writes is acceptable. For a chat product, losing a day of messages is not.

RTO: how long you can be down

The recovery time objective is how long the restore may take, from "we need to restore" to "users are back". It is set by database size, network and disk speed, and how practised the procedure is.

Logical against physical backups

A logical backup (pg_dump) asks the database for its contents as SQL or a compressed archive: CREATE TABLE statements and the rows. A physical backup (pg_basebackup, or a tool built on the same mechanism) copies the data directory's files as they are on disk, while the server runs, plus the WAL needed to make that copy consistent. WAL archiving and point-in-time recovery

Because the WAL records every change, a base backup plus every WAL segment written since lets Postgres rebuild the database at any moment you choose. This is point-in-time recovery (PITR). You switch it on with three settings: wal_level = replica (the default), archive_mode = on, and an archive_command that copies each finished 16 MB segment somewhere safe; it must return success only once the file is stored (WAL settings). To recover, you restore the base backup, tell Postgres where the archive is (restore_command) and when to stop (recovery_target_time), and start it.

Three details from that output matter in a real incident:

  • Finding the moment. You rarely know the second the mistake happened. pg_waldump reads WAL files and prints each record; the DELETE's transaction shows up as a million heap delete records followed by one COMMIT with a timestamp. You can then recover to just before that time, or name the transaction directly with recovery_target_xid (and recovery_target_inclusive = false).
  • A new timeline. After recovery the server says selected new timeline ID: 2. A timeline is a branch of history: from this point the recovered database has a different future from the old one, and its WAL files are named with the new timeline so they never mix with the old ones in the archive.
  • Writes after the mistake. Recovering to 14:02:59 also discards everything written after 14:03 (two messages in the run). So in practice you usually recover into a separate server and copy just the deleted rows back into production with SQL, rather than replacing production. Either way the decision is a product one: say it out loud in the incident channel.

Tools: what professionals run

Nobody writes cp archive commands in production. Three open-source tools do base backups, WAL archiving, retention, compression, encryption and restores against object storage such as S3:

pgBackRest

The most common choice for self-managed Postgres: full, differential and incremental backups, parallel compression, encryption, asynchronous archiving, backup verification. Latest 2.59.3, 2026-10-04. User guide.

WAL-G

A single Go binary, popular in Kubernetes and cloud setups; delta backups to S3, GCS or Azure; also backs up MySQL and others. Latest v3.0.9, 2026-08-20.

Barman

EDB's backup server: one machine that pulls backups and streams WAL from many Postgres servers. Latest 3.20.1, 2026-09-29.

A minimal pgBackRest setup, following its user guide (bucket and paths are illustrative):

# /etc/pgbackrest/pgbackrest.conf
[global]
repo1-type=s3
repo1-s3-bucket=chat-db-backups
repo1-s3-region=eu-west-1
repo1-path=/pgbackrest
repo1-retention-full=4            # keep four full backups and the WAL they need
repo1-cipher-type=aes-256-cbc     # encrypted before it leaves the machine
process-max=4
archive-async=y
start-fast=y

[main]
pg1-path=/var/lib/postgresql/18/main

# postgresql.conf
archive_mode = on
archive_command = 'pgbackrest --stanza=main archive-push %p'

# weekly full, daily differential (cron); restore to a moment:
pgbackrest --stanza=main --type=full backup
pgbackrest --stanza=main --type=diff backup
pgbackrest --stanza=main --type=time "--target=2026-10-04 14:02:59+00" --target-action=promote restore

Since PostgreSQL 17 the built-in tools can also take incremental backups (pg_basebackup --incremental, merged with pg_combinebackup: release notes), but they do not manage retention or object storage for you. Managed services do all of this for you: Amazon RDS keeps automated backups for up to 35 days and uploads transaction logs to S3 every five minutes, so its point-in-time restore can lose up to about five minutes (RDS PITR docs).

A backup you have not restored is not a backup

On 31 January 2017, GitLab.com lost about six hours of database changes. An engineer, tired and fighting replication lag, deleted the data directory on the primary instead of the replica. Then the team found that the nightly pg_dump backups had been failing silently for a long time (the dump tool's major version did not match the server's) and disk snapshots had never been enabled; the best copy was a manual snapshot six hours old, which took about 18 hours to copy back (GitLab postmortem, 2017-02-10; the full case is in the SWE topic's Case files tab). Every backup method they had existed; none had been restored.

What "tested restores" means in practice
  • A scheduled job (weekly at least) restores the latest backup to a scratch server, replays WAL to a recent moment, and runs checks: the server starts, row counts of key tables are close to production's, an application smoke query works. It alerts if any step fails.
  • It records how long the restore took. That number, not a guess, is your RTO. Here 221 MB took under two seconds; at a realistic 200 MB/s restore speed a 2 TB database takes about three hours before any WAL replay (2,000,000 MB / 200 MB/s = 10,000 s; illustrative speed).
  • Backups go to another account or project with delete protection (object lock), so a compromised production account or a bad script cannot delete them too.
  • Alert when the archiver fails (pg_stat_archiver.failed_count rising) and when the newest backup is older than its schedule.

4. Replication: a live copy on another machine

A backup gets the data back after hours. A replica (also standby) is a second Postgres server that is kept a copy of the first, the primary, within milliseconds, so it can take over in seconds and can serve read-only queries meanwhile. The theory (synchronous against asynchronous replication, what consistency a reader sees, why failover can lose data) is on Distributed systems fundamentals; this section is how Postgres does it and what to watch.

Streaming replication, set up for real

In streaming replication a process on the primary, the WAL sender, streams WAL records over a normal database connection to a WAL receiver on the replica, which writes them to its own pg_wal/, flushes them, and replays them into its table files exactly as crash recovery would (high availability docs). The replica starts as a base backup of the primary; pg_basebackup -R also writes the connection settings and a standby.signal file that tells the new server to stay a replica:

Replication lag, measured three ways

The primary reports each replica's progress in pg_stat_replication as three delays (monitoring docs): write_lag (the replica has received and written the WAL, not yet flushed it to disk), flush_lag (written and flushed: it would survive a crash of the replica) and replay_lag (applied, so queries on the replica can see it). They separate the three ways a replica falls behind: the network (write), the replica's disk (flush), or its replay (one process applying everything, often blocked by queries running on the replica).

write_lagflush_lagreplay_lagMB not yet replayed (right axis)

Pausing replay with pg_wal_replay_pause() stands in for the most common real cause: a long query on the replica that needs rows the replay is about to remove. Postgres then has to choose between cancelling the query and delaying replay; max_standby_streaming_delay (default 30 s) sets how long replay waits, and hot_standby_feedback = on instead tells the primary not to remove those rows (which brings bloat back to the primary: section 6). On a real server, lag also comes from a replica on smaller hardware than the primary, a saturated network, or a burst of writes such as a big UPDATE or an index build.

What lag means for the application (which reads may go to a replica, read-your-writes after a user's own change, and Jepsen's finding that reads on replicas can even disagree about the order of two commits, a Long Fork) is section 3 of Scaling a database, "Read replicas in practice".

Replication slots, and why they fill disks

If a replica disconnects for a while, the primary may already have recycled the WAL it needs to catch up. A replication slot fixes that: it is a bookmark on the primary that says "keep all WAL from this position until this replica confirms it". The danger is the other side of the same promise: if the replica never comes back, the primary keeps WAL forever, until its disk is full and it stops. Measured, with the replica stopped and the chat database taking ordinary updates:

Size of the primary's pg_wal/ after each step (after a checkpoint), colour by the slot's wal_status. measured

Since PostgreSQL 13, max_slot_wal_keep_size caps what a slot may hold (default -1, unlimited: replication settings); past the cap the slot is marked lost and the replica must be rebuilt from a fresh base backup (here 2.3 s for 774 MB on one laptop; hours for terabytes over a network). Since PostgreSQL 18, idle_replication_slot_timeout can also invalidate slots that have been inactive too long. The wal_status column tells you how close you are: reserved (within max_wal_size), extended (beyond it, still kept), unreserved (will be removed at the next checkpoint), lost (pg_replication_slots).

Rule
Set max_slot_wal_keep_size to what your disk can afford, alert on pg_replication_slots where active is false or retained WAL exceeds a few GB, and drop slots for replicas that are gone. Abandoned slots also hold back vacuum when they carry an xmin (logical slots always do), which leads to section 7.

Synchronous replication: no lost commits, at a price

By default replication is asynchronous: the primary confirms a commit to the client as soon as its own WAL is flushed, and the replica gets it a moment later. If the primary dies in that moment, a failover loses those commits. With synchronous_standby_names set, a commit waits until a named standby confirms it, and synchronous_commit chooses how far: remote_write (the standby has written it), on (flushed), remote_apply (replayed, so a read on the standby will see it) (WAL settings). local and off skip the standby; off does not even wait for the primary's own disk, so a crash can lose the last fraction of a second of commits (but never corrupts the database). Two things follow. On one machine, waiting for the standby cut throughput by more than half (27,568 to 11,562 inserts per second with on), mainly from the extra round trip on every commit; across availability zones (about 1 ms apart) or regions (tens of ms) the cost grows with distance. And the synchronous setting has a sharp edge: if the only synchronous standby goes away, every commit on the primary waits forever:

Read the last lines carefully: cancelling the wait does not undo the commit, it was already durable on the primary; it only might not be on the standby. The usual production setting is therefore synchronous_standby_names = 'ANY 1 (replica_a, replica_b)': wait for any one of two standbys (quorum commit), so losing one does not stop writes (syntax). Patroni can also switch synchronous mode off automatically when no standby is healthy, trading a small data-loss window for availability.

Logical replication: copying rows, not files

Streaming replication copies the whole cluster byte for byte, so the replica must run the same major version and cannot be written to. Logical replication instead decodes the WAL into row changes ("insert this row into messages") and applies them on a subscriber, a normal writable database that can run a different major version and hold only some tables. You create a PUBLICATION on the source and a SUBSCRIPTION on the target (it requires wal_level = logical). Its uses: major-version upgrades with minutes of downtime (section 9), moving a database to another host or cloud, feeding a few tables to an analytics database, and change data capture into Kafka with Debezium (which reads a logical slot: see Queues, streams and async work). Its limits (restrictions): schema changes (DDL) are not replicated, sequence values are not replicated, large objects are not replicated, and every replicated table needs a primary key or a replica identity for updates and deletes.

5. Failover: when the primary dies

Failover is making a replica the new primary and pointing the application at it. Postgres itself does exactly one step of it, promotion: the replica stops replaying, starts a new timeline and accepts writes. Measured:

The hard parts are everything around that command: deciding that the primary is really dead (and not just slow or cut off from the monitor), making sure it can no longer accept writes, moving the application's connections, and bringing the old primary back as a replica. Get the first two wrong and you have split brain: two servers that both think they are the primary, each accepting different writes. Staged here by promoting the replica while the old primary keeps running:

The same row id now holds two different messages on the two servers. Neither is "right"; merging them afterwards is manual, row by row. GitHub's 21 October 2018 outage began this way: a 43-second network partition triggered an automated failover across data centres, writes landed on both sides, and reconciling them kept the site degraded for 24 hours and 11 minutes (GitHub post-incident analysis; MySQL, but the lesson is the same).

Fencing is how real systems prevent it: before promoting, make sure the old primary cannot accept writes, by stopping it, cutting its network, or powering it off through the cloud API (the old name is STONITH, "shoot the other node in the head"). The old primary is then repaired with pg_rewind, which copies back only the blocks that changed since the two histories diverged instead of a full base backup:

The write that went to the old primary is gone: pg_rewind discarded it. That is correct for the database and a data loss for whoever wrote it, which is why fencing first is the rule. (pg_rewind needs wal_log_hints = on or data checksums, and the old primary's WAL back to the last common checkpoint; the first attempt for this page failed until wal_keep_size kept it.)

Patroni and managed failover

Doing this by hand at 3 a.m. is how split brains happen, so production setups automate it. Patroni (from Zalando, now patroni/patroni, latest v4.1.5, 2026-08-12) runs beside each Postgres server and keeps a leader lock in a consensus store (etcd, Consul, ZooKeeper or Kubernetes). Only the holder of the lock may be primary; the lock has a time to live, so a primary that cannot renew it (because it is cut off) demotes itself, and a replica promotes only after acquiring the lock. That turns "who is primary" into a question the consensus store answers once, which is exactly the problem Raft solves (theory on Distributed systems fundamentals). Patroni can also use a hardware or software watchdog to reset a primary that hangs. On Kubernetes, CloudNativePG (v1.30.1, 2026-09-23) plays the same role. Applications find the current primary through a DNS name, a load balancer, a pooler, or a multi-host connection string with target_session_attrs=read-write.

Managed services run the equivalent for you. Amazon Aurora says a failover to a replica typically restores service in under 60 seconds and often under 30 (Aurora high availability). Two things remain yours: the application must reconnect and retry (connections to the dead primary fail mid-transaction; see Reliability engineering for retries), and with asynchronous replication the last commits before the failure may be lost. Jepsen also found that RDS Multi-AZ clusters for PostgreSQL 13.15 to 17.4 could show reads on replicas that violate snapshot isolation (Long Fork), because of how stock Postgres replicas decide which transactions are visible (Jepsen, 2025-04-29): read from the primary when correctness matters.

6. Vacuum and autovacuum: the cleaning crew

Postgres never overwrites a row in place. An UPDATE writes a new version of the row and marks the old one as replaced; a DELETE only marks the row. Old versions must stay as long as some running transaction might still need to see them: that is MVCC (multi-version concurrency control), explained properly on Transactions and concurrency. Once no transaction can see an old version it is a dead tuple (tuple is Postgres's word for a row version), taking space for nothing. VACUUM finds dead tuples, removes their index entries, and marks their space reusable for new rows; it also records which pages are all-visible (so index-only scans can skip the table) and freezes old rows (section 7). Autovacuum is the background launcher that runs VACUUM and ANALYZE on each table when enough has changed.

When autovacuum runs

A table is vacuumed when its dead tuples exceed autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × rows, by default 50 + 20% of the table (vacuum settings). The launcher checks every autovacuum_naptime (1 minute) with up to autovacuum_max_workers (3) workers, each slowed by a cost limit so it does not swamp the disk (autovacuum_vacuum_cost_delay 2 ms per 200 cost units). PostgreSQL 18 added autovacuum_vacuum_max_threshold (default 100 million), so a huge table no longer waits for 20% of itself to die.

Dead tuples before autovacuum starts = 50 + scale factor × rows, capped at 100,000,000 in PostgreSQL 18. Try a billion rows at the default 0.2, then the 0.01 many teams set on their biggest tables. Updates per second needed to reach it in an hour = threshold / 3,600.

Three lessons hide in that chart:

  • HOT updates mostly clean up after themselves. When an update changes no indexed column and the page has room, Postgres writes a heap-only tuple (HOT): the new version goes on the same page, no index is touched, and the next visitor to a full page prunes the dead versions on the spot. Adding one index on the updated column (here last_message_at, for "chats by recent activity") turned every update into a full one. Before adding an index to a hot table, check n_tup_hot_upd against n_tup_upd; leaving free space in each page (fillfactor = 90) makes HOT more likely.
  • Autovacuum is a sawtooth: dead tuples rise to the trigger and drop to near zero. The table grows a little and then stops growing, because new versions reuse the freed space. That steady state is healthy.
  • One forgotten transaction stops all cleanup. A session that ran one SELECT inside a transaction and never committed keeps its snapshot, so no row version newer than that snapshot can be removed, in any table. Autovacuum keeps running and removes nothing:

The tell-tale line is dead but not yet removable with a removable cutoff that does not move. The fix is to end the old transaction (pg_terminate_backend(pid)) and, so it does not happen again, to set idle_in_transaction_session_timeout (section 8). The same effect comes from a replication slot with an old xmin, a replica with hot_standby_feedback = on running a long query, or an abandoned prepared transaction (section 7).

VACUUM against VACUUM FULL

Plain VACUUM makes space reusable but almost never gives it back to the operating system: the file keeps its size. VACUUM FULL rewrites the whole table into a new compact file and rebuilds its indexes, which does return space, but it holds an ACCESS EXCLUSIVE lock for the whole rewrite: nothing can even read the table. On a 200 MB table the lock lasted under two seconds; on a 500 GB table it would be hours of a table nobody can read. In production you reclaim space online with pg_repack (reorg/pg_repack, latest tag ver_1.5.3) or pg_squeeze (cybertec-postgresql/pg_squeeze, REL1_9_4, 2026-07-29), which build a new copy in the background, replay the changes made meanwhile, and take the exclusive lock only for a brief swap at the end (both are extensions that are not in the pgserver build, so they were not measured here). Often you need neither: if the table will grow back, reusable space is fine.

7. Transaction ID wraparound: the outage that stops all writes

Every transaction that writes gets a transaction ID (XID), a 32-bit counter, and every row version records the XID that created it. Visibility rules ask "was this row created by a transaction older than mine?", and with 32 bits that comparison is done modulo 232: each XID sees about 2.1 billion (231) IDs as the past and the rest as the future. A row whose creator falls more than 231 behind the current XID would suddenly look like it was created in the future and vanish. To prevent that, VACUUM freezes old rows, marking them as older than every transaction, and each table remembers its oldest unfrozen XID (relfrozenxid; the database's minimum is datfrozenxid) (routine vacuuming docs).

The safety net has four layers: when a table's oldest XID is 200 million old (autovacuum_freeze_max_age), autovacuum runs an aggressive freezing vacuum even if autovacuum is switched off; at 1.6 billion (vacuum_failsafe_age) that vacuum drops its speed limits and skips index cleanup to finish faster; at 40 million XIDs before the wraparound point every command logs a warning; and at 3 million before it, Postgres refuses to assign new XIDs: no more writes until someone fixes it. Freezing can only advance up to the oldest transaction anything still needs, so the real causes are the same as in section 6: a transaction left open, an abandoned prepared transaction, a replication slot holding an old xmin, or autovacuum too slow for a write-heavy database.

Two billion transactions take weeks even on a busy server, so for this page the counter was moved forward on a throwaway server with pg_resetwal -x, just short of the refusal point, after leaving behind a prepared transaction (a transaction from two-phase commit, which survives restarts until someone commits or rolls it back by name) that somebody forgot. Everything after that is real output:

Stale advice in the error itself
PostgreSQL 16's refusal message still says Stop the postmaster and vacuum that database in single-user mode. The current documentation says single-user mode should be avoided whenever possible and a normal VACUUM works, which is what fixed it above in 0.36 s on this tiny database (routine vacuuming, PostgreSQL 18). Remove what holds the XID back first; a VACUUM before that freezes nothing.

This is not theoretical. Sentry was down for most of a US working day on 20 July 2015 when Postgres stopped accepting writes to prevent wraparound (Sentry, 2015-07-23); Mailchimp's Mandrill was down from 4 to 5 February 2019 when one shard hit the limit (Mailchimp); Notion called wraparound "an existential threat to the product" in the post explaining why it sharded (Notion, 2021-10-06). The fix for a big database can take many hours of vacuuming, all of it with writes refused.

The alert that prevents it
Graph SELECT datname, age(datfrozenxid) FROM pg_database and the top tables by age(relfrozenxid). Warn when any database passes about 500 million (a quarter of the way) and page at about 1 billion; in a healthy database the age saws between 0 and 200 million as anti-wraparound vacuums finish (thresholds are this page's suggestion). Alert separately on prepared transactions older than a few minutes and on inactive replication slots.

A backend is cheap when idle and grows with use: each one caches the catalog entries (table and column definitions) it has touched, and memory freed after a big sort is usually kept by the process rather than returned. A thousand long-lived connections that have each touched many tables add up to gigabytes. But memory is not the whole story. Andres Freund's 2020 analysis found that with huge pages the overhead is below 2 MiB per connection, and that the real ceiling was CPU: every query's snapshot had to scan the list of all connections, which PostgreSQL 14 made much cheaper (Analyzing the limits of connection scalability in Postgres, 2020-10-08). The cost that remains is starting a process for every new connection, and the contention of many more active processes than CPU cores:

Trivial queries (SELECT 1) per second, 8 clients. "New connection each time" is pgbench -C: connect, run one query, disconnect, which is what an application without a pool, or a serverless function, does. measured

max_connections, and how it runs out

max_connections defaults to 100 and needs a restart to change; 3 of them are reserved for superusers (connection settings). An application role that asks for one more gets refused:

It usually runs out through arithmetic nobody did. Each application process keeps its own pool: SQLAlchemy's default is 5 connections plus up to 10 overflow (SQLAlchemy pooling). Twenty pods (copies of the service) can open 20 x 15 = 300 connections, a deploy briefly runs old and new pods together (600), and a worker fleet and a cron job add theirs. Raising max_connections to thousands is the wrong fix: most of those connections would be idle, and when many are active at once they compete for the same cores and locks. The PostgreSQL wiki's rule of thumb for the number of active connections that gives the best throughput is about (2 x CPU cores) + number of disks (wiki: Number Of Database Connections; a starting point to measure from, not a law).

PgBouncer: many clients, few server connections

PgBouncer is a small single-process pooler that speaks the Postgres protocol, so applications connect to it as if it were the database. Its pool_mode decides when a server connection is lent out:

session

A client keeps one server connection from connect to disconnect. Everything works; it only saves the connect cost.

transaction

A client gets a server connection for one transaction, then gives it back. Hundreds of mostly idle clients share a few connections. The mode almost everyone runs, with caveats below.

statement

Returned after every statement; multi-statement transactions are not allowed. Rare.

A thousand clients, three hundred of them in a transaction at that moment, and Postgres saw only twenty server connections: the rest waited (cl_waiting) a few milliseconds for a free one. That queue is the point: it is far cheaper than a thousand processes fighting over the cores.

The two ways transaction pooling bites

In transaction mode, consecutive transactions from one client may run on different server connections, and one server connection serves many clients. Anything that lives in the session breaks: SET, LISTEN, session-level advisory locks, WITH HOLD cursors, temporary tables kept across transactions, and SQL-level PREPARE (PgBouncer feature table). Both of these happened on the first try:

The first is a correctness bug that no error reports: client A's 5-second timeout landed on whichever server connection it used and then applied to client B's queries on that connection. Use SET LOCAL inside a transaction, or set defaults per role (ALTER ROLE app SET statement_timeout = '5s'). The second is a crash that appeared only after the fifth execution, because psycopg 3 prepares a query on the server automatically once it has run five times (the prepare_threshold); asyncpg and many JDBC setups do the same. PgBouncer has tracked protocol-level prepared statements since 1.21.0 and, since 1.24.0, does so by default with max_prepared_statements = 200 (changelog); the run above set it to 0 to reproduce what older configurations still do. Check the setting before blaming the driver.

Keep the pooler patched
PgBouncer 1.26.0 (2026-09-23) fixes CVE-2026-19888, an unauthenticated crash in the SCRAM login exchange present since 1.11.0 (changelog). The measurements here used 1.24.1, which is affected; a pooler sits in front of every connection, so a crash there is an outage.

Alternatives exist: Supavisor (Supabase's pooler, v2.9.13), PgDog (pooler, load balancer and sharder, weekly releases, v0.1.60), managed proxies such as RDS Proxy. PgCat has had no release since 2024-11-11 (postgresml/pgcat).

Timeouts: the cheapest protection there is

All of these default to 0 (off) (client settings). Set them per role, so the migration role and the analytics role can have different values from the web application:

ALTER ROLE app SET statement_timeout = '5s';                    -- no web request needs a 5-minute query
ALTER ROLE app SET idle_in_transaction_session_timeout = '30s'; -- a forgotten transaction cannot block vacuum for long
ALTER ROLE app SET transaction_timeout = '60s';                 -- PostgreSQL 17+: the whole transaction
ALTER ROLE migrator SET lock_timeout = '3s';                    -- a migration gives up instead of queueing everyone (section 11)

Values are illustrative; pick them from your own latency targets.

9. Upgrades: minor releases and major versions

Postgres versions look like 18.6: 18 is the major version, 6 the minor release. Minor releases only fix bugs and security issues and never change the on-disk format: install the new binaries and restart, after reading the release notes for occasional extra steps. They come out roughly quarterly (18.6 and 17.11 on 2026-08-13: release notes). A major version comes once a year and may change the system catalogs and the storage format, so the data directory must be converted. Each major version is supported for five years (versioning policy):

Support windows from the versioning policy page, read 2026-10-04. The vertical line is today.

PostgreSQL 14 leaves support on 2026-11-12, about five weeks after this page was written. Managed services charge or force-upgrade after end of life (Amazon calls it RDS Extended Support), so "we will upgrade later" has a date.

pg_upgrade: convert in place

pg_upgrade creates the new version's empty cluster, copies over the schema with pg_dump, and then moves the data files across unchanged, since the table format rarely changes. Its modes decide how the files move: copy (safe, slow for big databases), --link (hard links: seconds for any size, but the old cluster cannot be used once the new one has started), --clone (copy-on-write file systems) and, since PostgreSQL 18, --swap (moves directories, often the fastest) (pg_upgrade docs). Run --check first, always. Measured, 16.2 to 17.11, both servers stopped throughout:

On this 221 MB database both modes took about two seconds, almost all of it the fixed cost of dumping and restoring the schema; copy mode adds the time to copy every byte (about 17 minutes per terabyte at 1 GB/s, illustrative disk speed), link mode does not. Before PostgreSQL 18 the planner statistics are not carried over, so until vacuumdb --analyze-in-stages finishes, queries can get bad plans; PostgreSQL 18's pg_upgrade keeps them (PostgreSQL 18 release notes). Downtime is the whole run plus restarts. Physical replicas cannot follow a major upgrade: they are rebuilt, or upgraded with the rsync procedure in the docs.

Logical replication: upgrade with seconds of downtime

For large databases, set up a new server on the new version, copy the schema, subscribe it to the old one with logical replication (section 4), let it catch up while the old one keeps serving, then switch the application over. Measured, 16 publishing to 17:

The trap at the end is the classic one: logical replication copies rows, not sequence positions, so the new server's messages_id_seq was still at 1 and the first insert collided with an existing row. At cutover, stop writes, wait for the subscriber to catch up, copy every sequence's value (setval), then move the traffic. Other things to plan: tables without a primary key, schema changes during the migration (not replicated), and large objects. PostgreSQL 17 added pg_createsubscriber, which turns a physical replica into a logical one so the initial copy is skipped, and preserves logical slots across pg_upgrade from 17 onwards (PostgreSQL 17 release notes). Managed services wrap the same idea: Amazon RDS Blue/Green Deployments build the new-version copy and switch over for you (RDS Blue/Green).

10. Security basics

A database is where the valuable data is, so it gets the narrowest door. Four layers, from outside in:

  • Network. The database has no public IP address; only the application's subnet (and a bastion or VPN for humans) can reach port 5432.
  • Who may connect, and how: pg_hba.conf. Each line is type database user address method, read top to bottom, first match wins (pg_hba.conf docs). Use hostssl lines (TLS required) and scram-sha-256 passwords, the default since PostgreSQL 14; MD5 passwords are deprecated and PostgreSQL 18 warns when one is set (18 release notes).
  • Encryption in transit. ssl = on on the server, and sslmode=verify-full on clients so they also check the server's certificate (anything weaker can be intercepted).
  • Least privilege. A role is a user or a group; give each kind of client its own role with only what it needs. The application should not own the tables, and nothing should run as a superuser.
# pg_hba.conf: TLS from the app subnet, SCRAM passwords; nothing else gets in
hostssl  chat  app,migrator  10.20.0.0/16  scram-sha-256
hostssl  chat  +readonly     10.30.0.0/24  scram-sha-256
host     all   all           0.0.0.0/0     reject

-- roles: the migration role owns the schema, the app only reads and writes rows
CREATE ROLE migrator LOGIN;                         -- runs schema migrations, owns the tables
CREATE ROLE app LOGIN;                              -- the web service
CREATE ROLE readonly NOLOGIN;                       -- a group for analysts and dashboards
GRANT CONNECT ON DATABASE chat TO app, readonly;
GRANT USAGE ON SCHEMA public TO app, readonly;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly;
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app;   -- tables created later too
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA public GRANT SELECT ON TABLES TO readonly;

Subnets and role names are illustrative. Since PostgreSQL 15 ordinary roles can no longer create objects in the public schema by default (15 release notes).

Two more layers when the product needs them. Row-level security makes the database itself filter rows by tenant or user, so a bug in one query cannot leak another customer's chats; it is taught with the chat schema on SQL and data modelling (RLS docs). Auditing (the pgaudit extension, or the managed service's audit log) records who read or changed what. Least privilege also limits mistakes: the GitLab engineer in section 3 could delete a data directory because one account could do everything everywhere; a role without DELETE on a table cannot run the 14:03 statement at all. Keep credentials in a secret manager, rotate them, and give humans individual named roles so the log says who did it.

Finding the query that is hurting you

pg_cancel_backend(pid) cancels the current query and keeps the connection; pg_terminate_backend(pid) ends the whole session (and rolls back its transaction). Prefer cancel. When everything on one table hangs, the cause is usually a lock queue: a migration waits for a long transaction, and every reader queues behind the migration, because locks are granted in order:

Reading it: the first process (blocked by nobody) is idle inside a transaction that read users; the ALTER TABLE needs an exclusive lock and waits for it; the three simple SELECTs are blocked by the ALTER, not by the idle transaction. Ending the idle transaction (or the migration) releases all of them. Migrations should set lock_timeout and retry; the measurements of which ALTER TABLE takes which lock are on SQL and data modelling ("ALTER TABLE, measured").

13. Common mistakes

Treating a replica as a backup
A replica copies a DELETE within milliseconds (section 3). Only backups with WAL archiving can go back in time. A delayed replica (recovery_min_apply_delay = '1h') is a useful extra, never a substitute.
Backups that nobody has restored
GitLab 2017: every backup mechanism existed and none worked. Automate a restore test and alert on it (section 3).
A replication slot without a cap
One dead replica or one abandoned CDC consumer, and the primary keeps WAL until the disk is full (section 4). Set max_slot_wal_keep_size and alert on inactive slots.
No timeouts
A session left idle in a transaction blocks vacuum everywhere and can hold locks that queue a migration and then every query behind it (sections 6 and 11).
Running VACUUM FULL on a live table
It takes an exclusive lock for the whole rewrite. Use pg_repack or pg_squeeze, or accept reusable free space (section 6).
Turning autovacuum off, or leaving it at defaults on a huge hot table
Off means bloat and, eventually, wraparound. Defaults on a billion-row table mean 200 million dead rows before it starts (section 6 calculator).
Raising max_connections instead of pooling
Thousands of backends cost memory and CPU, and the pool arithmetic still overflows on the next deploy (section 8).
SET and prepared statements through a transaction pooler
Session state leaks between clients; driver-prepared statements collide unless max_prepared_statements is set (section 8).
Failover without fencing
Two primaries accept different writes; one side's writes are thrown away when you rejoin them (section 5).
Forgetting sequences at a logical-replication cutover
The first insert on the new server collides with existing ids (section 9).
Letting a version run out of support
PostgreSQL 14 ends on 2026-11-12. Plan major upgrades a year ahead and rehearse them on a restored copy.
The application connects as a superuser or table owner
Every bug and every leaked credential then has full power. One role per kind of client, least privilege (section 10).
