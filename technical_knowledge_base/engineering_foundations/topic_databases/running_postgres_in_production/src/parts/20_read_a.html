The idea in one screen

A Postgres server is one process per connection writing every change first to the write-ahead log (WAL) and leaving old row versions behind. Running it in production is three jobs: ship the WAL somewhere safe (backups, replicas, failover), clean up what it leaves behind (vacuum, freezing), and never let anything pin either in place: an open transaction, an abandoned replication slot, a flood of connections.

Backend
the operating-system process the postmaster starts for each client connection.
WAL, LSN
the write-ahead log, stored as 16 MB segment files in pg_wal/; an LSN (log sequence number, like 0/2209DC60) is a position in it.
Checkpoint
the moment every changed page is on disk, after which older WAL can be recycled.
RPO, RTO
how much data you may lose, and how long you may be down.
PITR
point-in-time recovery: a base backup plus archived WAL, replayed to any chosen moment.
Replication slot
a bookmark on the primary that keeps WAL until one consumer confirms it.
Dead tuple
a row version no transaction can see any more; VACUUM reclaims it.
XID, freezing
the 32-bit transaction ID; freezing marks old rows so the counter can wrap safely.
Transaction pooling
a pooler lends a server connection for one transaction at a time.

The five rules that prevent most database outages
  1. Backups are continuous and restores are tested: a base backup plus archived WAL, restored on a schedule by a machine, with the restore time written down (section 2).
  2. A replica is not a backup: it copies your mistakes within milliseconds (sections 2 and 3).
  3. Every replication slot has a cap and an alert (max_slot_wal_keep_size), or one dead replica fills the primary's disk (section 3).
  4. Every session has timeouts (statement_timeout, idle_in_transaction_session_timeout), so one forgotten transaction cannot block vacuum and pile up locks (sections 5, 7, 8).
  5. Applications connect through a pooler and max_connections stays in the hundreds, not thousands (section 7).

1. The server: processes, memory, WAL and checkpoints

One process per connection. The postmaster is the parent process; for every client that connects it starts a new operating-system process, a backend, which serves that one connection until it closes ({{how connections are established|https://www.postgresql.org/docs/18/connect-estab.html}}). Background processes do the housekeeping: the checkpointer, the WAL writer, the autovacuum launcher and its workers, and WAL senders if you replicate. This one design decision is why connections are expensive and poolers exist (section 7). Everything served by one postmaster from one data directory (often /var/lib/postgresql/18/main, holding every table and index as files, postgresql.conf, pg_hba.conf and the log) is a cluster in Postgres's words: one server, possibly many databases, not a cluster of machines.

Memory: one shared cache, and memory per operation

Two kinds of memory matter ({{resource settings|https://www.postgresql.org/docs/18/runtime-config-resource.html}}). shared_buffers is the cache of 8 KB table and index pages shared by every backend: 128 MB by default, about 25% of RAM on a dedicated server is the documented starting point (the operating system's file cache holds much of the rest). work_mem (default 4 MB) is the budget of each sort or hash operation in each running query, and a hash may use hash_mem_multiplier (2.0) times more; past it the operation spills to temporary files. So the server-wide setting multiplies: a query with one sort and one hash join can take three times work_mem, in every active backend at once. Predict: with 100 active connections, what server-wide work_mem takes this 64 GB host past its RAM? Then drag.

work_mem is per operation, per backend: the server-wide value multiplies

Worst case = shared_buffers + active backends × (one sort + one hash × 2.0) × work_mem, from the documented per-operation rule. The 64 GB host, shared_buffers at 25% and the query shape are illustrative; real queries rarely all peak at once, which is why this is the ceiling, not the expectation. Measured here: one backend kept MB after a single 64 MB sort, until it exited.

The usual answer is a modest server default and a larger work_mem set per role or per session for reports and batch jobs (ALTER ROLE reports SET work_mem = '256MB'; illustrative); how a spill changes a plan, and the temp_files it leaves, is on {{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}}. Two more settings round out the memory picture: maintenance_work_mem (default 64 MB) is what VACUUM and CREATE INDEX use, once per autovacuum worker, and effective_cache_size allocates nothing at all: it only tells the planner how much data is likely cached.

WAL and checkpoints: why pg_wal/ grows

Before any change touches a table file, a record describing it is appended to the WAL and flushed; after a crash, Postgres replays the WAL to redo what the table files missed. A checkpoint writes every changed page in memory to the table files; it starts every checkpoint_timeout (5 minutes) or after max_wal_size (1 GB) of WAL, whichever comes first ({{WAL settings|https://www.postgresql.org/docs/18/runtime-config-wal.html}}), and after it the WAL before that point is no longer needed for crash recovery, so its segments are recycled. On a healthy server pg_wal/ therefore stays near max_wal_size. For operations, the point is: the WAL is a complete history of every change, so shipping it elsewhere gives you both backups (section 2) and replicas (section 3), and anything that still needs old WAL (a failing archive command, a replica that is behind, a slot) stops the recycling, which is the mechanism behind most disk-full pages. Why the first change to a page after a checkpoint writes the whole page, and what longer checkpoint intervals cost in recovery time, is on {{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}}.
