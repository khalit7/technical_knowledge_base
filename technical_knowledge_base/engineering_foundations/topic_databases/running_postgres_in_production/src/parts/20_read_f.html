10. Upgrades: minor releases and major versions

In 18.6, 18 is the major version and 6 the minor release. Minor releases only fix bugs and security issues and never change the on-disk format: install the new binaries and restart, after reading the release notes for occasional extra steps; they come roughly quarterly (18.6 and 17.11 on 2026-08-13: {{release notes|https://www.postgresql.org/docs/18/release-18-6.html}}). A major version comes once a year, may change the catalogs and storage format, so the data directory must be converted, and is supported for five years ({{versioning policy|https://www.postgresql.org/support/versioning/}}):

Five years each: PostgreSQL 14 ends on 2026-11-12

Support windows from the {{versioning policy page|https://www.postgresql.org/support/versioning/}}, read 2026-10-04; the vertical line is that day, about five weeks before 14's end. Managed services charge or force-upgrade after end of life (Amazon calls it RDS Extended Support), so "we will upgrade later" has a date: plan major upgrades a year ahead and rehearse them on a restored copy.

pg_upgrade: convert in place

pg_upgrade creates the new version's empty cluster, copies the schema with pg_dump, then moves the data files across unchanged, since the table format rarely changes. Its modes decide how the files move: copy (safe, slow for big databases), --link (hard links: seconds for any size, but the old cluster is unusable once the new one has started), --clone (copy-on-write file systems) and, since PostgreSQL 18, --swap (moves directories, often the fastest) ({{pg_upgrade docs|https://www.postgresql.org/docs/18/pgupgrade.html}}). Always run --check first. Measured, 16.2 to 17.11, both servers stopped throughout:

On this 221 MB database both modes took about two seconds, almost all of it the fixed cost of dumping and restoring the schema; copy mode adds the time to copy every byte (about 17 minutes per terabyte at 1 GB/s, illustrative disk speed), link mode does not. Before PostgreSQL 18 planner statistics are not carried over, so until vacuumdb --analyze-in-stages finishes, queries can get bad plans; PostgreSQL 18's pg_upgrade keeps them ({{18 release notes|https://www.postgresql.org/docs/18/release-18.html}}). Downtime is the whole run plus restarts. Physical replicas cannot follow a major upgrade: they are rebuilt, or upgraded with the rsync procedure in the docs.

Real run: pg_upgrade --check, then a server with no statistics (measured output)

Logical replication: upgrade with seconds of downtime

For large databases, build a server on the new version, copy the schema, subscribe it to the old one with logical replication (section 3), let it catch up while the old one serves, then switch the application. Measured, 16 publishing to 17, with the classic trap at the end: logical replication copies rows, not sequence positions, so the new server's messages_id_seq was still at 1 (the old one at 1231288) and the first insert failed with duplicate key value violates unique constraint "messages_pkey". At cutover: stop writes, wait for the subscriber to catch up, copy every sequence's value (setval), then move traffic. Also plan for tables without a primary key, schema changes during the migration (not replicated) and large objects. PostgreSQL 17 added pg_createsubscriber, which turns a physical replica into a logical one so the initial copy is skipped, and keeps logical slots across pg_upgrade from 17 onwards ({{17 release notes|https://www.postgresql.org/docs/17/release-17.html}}). Amazon RDS Blue/Green Deployments wrap the same idea ({{RDS Blue/Green|https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/blue-green-deployments.html}}).

11. Security basics

The database gets the narrowest door, in four layers from outside in. Network: no public IP; only the application's subnet (and a bastion or VPN for humans) reaches port 5432. Who may connect: pg_hba.conf, where each line is type database user address method, read top to bottom, first match wins ({{pg_hba.conf docs|https://www.postgresql.org/docs/18/auth-pg-hba-conf.html}}); use hostssl lines and scram-sha-256 passwords, the default since PostgreSQL 14 (MD5 passwords are deprecated and PostgreSQL 18 warns when one is set: {{18 release notes|https://www.postgresql.org/docs/18/release-18.html}}). Encryption in transit: ssl = on on the server and sslmode=verify-full on clients, so they also check the server's certificate (anything weaker can be intercepted). Least privilege: a role is a user or a group; each kind of client gets its own with only what it needs, the application does not own the tables, and nothing runs as a superuser. Least privilege also limits mistakes: a role without DELETE on messages cannot run section 2's 14:03 statement at all.

pg_hba.conf and roles for the chat product (reference configuration)
# pg_hba.conf: TLS from the app subnet, SCRAM passwords; nothing else gets in
hostssl  chat  app,migrator  10.20.0.0/16  scram-sha-256
hostssl  chat  +readonly     10.30.0.0/24  scram-sha-256
host     all   all           0.0.0.0/0     reject

-- roles: the migration role owns the schema, the app only reads and writes rows
CREATE ROLE migrator LOGIN;                         -- runs schema migrations, owns the tables
CREATE ROLE app LOGIN;                              -- the web service
CREATE ROLE readonly NOLOGIN;                       -- a group for analysts and dashboards
GRANT CONNECT ON DATABASE chat TO app, readonly;
GRANT USAGE ON SCHEMA public TO app, readonly;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly;
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app;   -- tables created later too
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA public GRANT SELECT ON TABLES TO readonly;

Subnets and role names are illustrative. Since PostgreSQL 15 ordinary roles can no longer create objects in the public schema by default ({{15 release notes|https://www.postgresql.org/docs/15/release-15.html}}).

Two more layers when the product needs them: row-level security, so the database itself filters rows by tenant and a bug in one query cannot leak another customer's chats (taught with the chat schema on {{SQL and data modelling|n:3ef5c17b0d0d813980dcd474e19f6c3f}}; {{RLS docs|https://www.postgresql.org/docs/18/ddl-rowsecurity.html}}), and auditing (the pgaudit extension, or the managed service's audit log) to record who read or changed what. Keep credentials in a secret manager, rotate them, and give humans individual named roles so the log says who did it.

12. Managed Postgres: what it takes off your plate

A managed service runs the server: provisioning, minor upgrades, automated backups and point-in-time restore, a standby with automatic failover, dashboards. It does not design your schema, fix slow queries, size your connection pools, tune autovacuum for your hottest table, choose when to do a major upgrade, or test that a restore gives you what you need: sections 5 to 10 stay your job. How to choose: on a cloud already, its stock managed Postgres (RDS, Cloud SQL, Azure Flexible Server) is the default; Aurora and AlloyDB buy faster failover, more readers and storage that grows by itself, at a higher price and with less portability; Neon and Supabase suit small, spiky or many-database workloads and fast-moving teams; running it yourself (Patroni or CloudNativePG, pgBackRest, PgBouncer, postgres_exporter) is cheapest in money and most expensive in on-call time. Safe to defer: none of the five rules at the top.
