10. Security basics

A database is where the valuable data is, so it gets the narrowest door. Four layers, from outside in:

  • Network. The database has no public IP address; only the application's subnet (and a bastion or VPN for humans) can reach port 5432.
  • Who may connect, and how: pg_hba.conf. Each line is type database user address method, read top to bottom, first match wins ({{pg_hba.conf docs|https://www.postgresql.org/docs/18/auth-pg-hba-conf.html}}). Use hostssl lines (TLS required) and scram-sha-256 passwords, the default since PostgreSQL 14; MD5 passwords are deprecated and PostgreSQL 18 warns when one is set ({{18 release notes|https://www.postgresql.org/docs/18/release-18.html}}).
  • Encryption in transit. ssl = on on the server, and sslmode=verify-full on clients so they also check the server's certificate (anything weaker can be intercepted).
  • Least privilege. A role is a user or a group; give each kind of client its own role with only what it needs. The application should not own the tables, and nothing should run as a superuser.
# pg_hba.conf: TLS from the app subnet, SCRAM passwords; nothing else gets in
hostssl  chat  app,migrator  10.20.0.0/16  scram-sha-256
hostssl  chat  +readonly     10.30.0.0/24  scram-sha-256
host     all   all           0.0.0.0/0     reject

-- roles: the migration role owns the schema, the app only reads and writes rows
CREATE ROLE migrator LOGIN;                         -- runs schema migrations, owns the tables
CREATE ROLE app LOGIN;                              -- the web service
CREATE ROLE readonly NOLOGIN;                       -- a group for analysts and dashboards
GRANT CONNECT ON DATABASE chat TO app, readonly;
GRANT USAGE ON SCHEMA public TO app, readonly;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly;
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app;   -- tables created later too
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA public GRANT SELECT ON TABLES TO readonly;

Subnets and role names are illustrative. Since PostgreSQL 15 ordinary roles can no longer create objects in the public schema by default ({{15 release notes|https://www.postgresql.org/docs/15/release-15.html}}).

Two more layers when the product needs them. Row-level security makes the database itself filter rows by tenant or user, so a bug in one query cannot leak another customer's chats; it is taught with the chat schema on {{SQL and data modelling|n:3ef5c17b0d0d813980dcd474e19f6c3f}} ({{RLS docs|https://www.postgresql.org/docs/18/ddl-rowsecurity.html}}). Auditing (the pgaudit extension, or the managed service's audit log) records who read or changed what. Least privilege also limits mistakes: the GitLab engineer in section 3 could delete a data directory because one account could do everything everywhere; a role without DELETE on a table cannot run the 14:03 statement at all. Keep credentials in a secret manager, rotate them, and give humans individual named roles so the log says who did it.

Finding the query that is hurting you

pg_cancel_backend(pid) cancels the current query and keeps the connection; pg_terminate_backend(pid) ends the whole session (and rolls back its transaction). Prefer cancel. When everything on one table hangs, the cause is usually a lock queue: a migration waits for a long transaction, and every reader queues behind the migration, because locks are granted in order:

Reading it: the first process (blocked by nobody) is idle inside a transaction that read users; the ALTER TABLE needs an exclusive lock and waits for it; the three simple SELECTs are blocked by the ALTER, not by the idle transaction. Ending the idle transaction (or the migration) releases all of them. Migrations should set lock_timeout and retry; the measurements of which ALTER TABLE takes which lock are on {{SQL and data modelling|n:3ef5c17b0d0d813980dcd474e19f6c3f}} ("ALTER TABLE, measured").

12. Managed Postgres: what it takes off your plate

A managed service runs the server for you: provisioning, minor upgrades, automated backups and point-in-time restore, a standby with automatic failover, monitoring dashboards. It does not design your schema, fix slow queries, size your connection pools, tune autovacuum for your hottest table, choose when to do a major upgrade, or test that a restore gives you what you need. Everything in sections 6 to 11 stays your job. 13. Common mistakes

Treating a replica as a backup
A replica copies a DELETE within milliseconds (section 3). Only backups with WAL archiving can go back in time. A delayed replica (recovery_min_apply_delay = '1h') is a useful extra, never a substitute.
Backups that nobody has restored
GitLab 2017: every backup mechanism existed and none worked. Automate a restore test and alert on it (section 3).
A replication slot without a cap
One dead replica or one abandoned CDC consumer, and the primary keeps WAL until the disk is full (section 4). Set max_slot_wal_keep_size and alert on inactive slots.
No timeouts
A session left idle in a transaction blocks vacuum everywhere and can hold locks that queue a migration and then every query behind it (sections 6 and 11).
Running VACUUM FULL on a live table
It takes an exclusive lock for the whole rewrite. Use pg_repack or pg_squeeze, or accept reusable free space (section 6).
Turning autovacuum off, or leaving it at defaults on a huge hot table
Off means bloat and, eventually, wraparound. Defaults on a billion-row table mean 200 million dead rows before it starts (section 6 calculator).
Raising max_connections instead of pooling
Thousands of backends cost memory and CPU, and the pool arithmetic still overflows on the next deploy (section 8).
SET and prepared statements through a transaction pooler
Session state leaks between clients; driver-prepared statements collide unless max_prepared_statements is set (section 8).
Failover without fencing
Two primaries accept different writes; one side's writes are thrown away when you rejoin them (section 5).
Forgetting sequences at a logical-replication cutover
The first insert on the new server collides with existing ids (section 9).
Letting a version run out of support
PostgreSQL 14 ends on 2026-11-12. Plan major upgrades a year ahead and rehearse them on a restored copy.
The application connects as a superuser or table owner
Every bug and every leaked credential then has full power. One role per kind of client, least privilege (section 10).
