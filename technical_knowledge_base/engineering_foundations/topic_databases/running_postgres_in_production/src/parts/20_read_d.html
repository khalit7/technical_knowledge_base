6. Vacuum and autovacuum: the cleaning crew

Postgres never overwrites a row in place. An UPDATE writes a new version of the row and marks the old one as replaced; a DELETE only marks the row. Old versions must stay as long as some running transaction might still need to see them: that is MVCC (multi-version concurrency control), explained properly on {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}}. Once no transaction can see an old version it is a dead tuple (tuple is Postgres's word for a row version), taking space for nothing. VACUUM finds dead tuples, removes their index entries, and marks their space reusable for new rows; it also records which pages are all-visible (so index-only scans can skip the table) and freezes old rows (section 7). Autovacuum is the background launcher that runs VACUUM and ANALYZE on each table when enough has changed.

When autovacuum runs

A table is vacuumed when its dead tuples exceed autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × rows, by default 50 + 20% of the table ({{vacuum settings|https://www.postgresql.org/docs/18/runtime-config-vacuum.html}}). The launcher checks every autovacuum_naptime (1 minute) with up to autovacuum_max_workers (3) workers, each slowed by a cost limit so it does not swamp the disk (autovacuum_vacuum_cost_delay 2 ms per 200 cost units). PostgreSQL 18 added autovacuum_vacuum_max_threshold (default 100 million), so a huge table no longer waits for 20% of itself to die.

Dead tuples before autovacuum starts = 50 + scale factor × rows, capped at 100,000,000 in PostgreSQL 18. Try a billion rows at the default 0.2, then the 0.01 many teams set on their biggest tables. Updates per second needed to reach it in an hour = threshold / 3,600.

Three lessons hide in that chart:

  • HOT updates mostly clean up after themselves. When an update changes no indexed column and the page has room, Postgres writes a heap-only tuple (HOT): the new version goes on the same page, no index is touched, and the next visitor to a full page prunes the dead versions on the spot. Adding one index on the updated column (here last_message_at, for "chats by recent activity") turned every update into a full one. Before adding an index to a hot table, check n_tup_hot_upd against n_tup_upd; leaving free space in each page (fillfactor = 90) makes HOT more likely.
  • Autovacuum is a sawtooth: dead tuples rise to the trigger and drop to near zero. The table grows a little and then stops growing, because new versions reuse the freed space. That steady state is healthy.
  • One forgotten transaction stops all cleanup. A session that ran one SELECT inside a transaction and never committed keeps its snapshot, so no row version newer than that snapshot can be removed, in any table. Autovacuum keeps running and removes nothing:

The tell-tale line is dead but not yet removable with a removable cutoff that does not move. The fix is to end the old transaction (pg_terminate_backend(pid)) and, so it does not happen again, to set idle_in_transaction_session_timeout (section 8). The same effect comes from a replication slot with an old xmin, a replica with hot_standby_feedback = on running a long query, or an abandoned prepared transaction (section 7).

VACUUM against VACUUM FULL

Plain VACUUM makes space reusable but almost never gives it back to the operating system: the file keeps its size. VACUUM FULL rewrites the whole table into a new compact file and rebuilds its indexes, which does return space, but it holds an ACCESS EXCLUSIVE lock for the whole rewrite: nothing can even read the table. On a 200 MB table the lock lasted under two seconds; on a 500 GB table it would be hours of a table nobody can read. In production you reclaim space online with pg_repack ({{reorg/pg_repack|https://github.com/reorg/pg_repack/tags}}, latest tag ver_1.5.3) or pg_squeeze ({{cybertec-postgresql/pg_squeeze|https://github.com/cybertec-postgresql/pg_squeeze/releases}}, REL1_9_4, 2026-07-29), which build a new copy in the background, replay the changes made meanwhile, and take the exclusive lock only for a brief swap at the end (both are extensions that are not in the pgserver build, so they were not measured here). Often you need neither: if the table will grow back, reusable space is fine.

Tuning autovacuum: what teams actually change

-- a big, hot table: vacuum after 1% has changed, not 20%, and let it work faster
ALTER TABLE messages SET (autovacuum_vacuum_scale_factor = 0.01, autovacuum_vacuum_threshold = 1000,
                          autovacuum_analyze_scale_factor = 0.02);
ALTER TABLE chat_state SET (fillfactor = 90);          -- room on each page for HOT updates

-- postgresql.conf: more and faster workers on a machine with fast disks
autovacuum_max_workers = 6               -- PostgreSQL 18: changeable without restart, up to autovacuum_worker_slots (16)
autovacuum_vacuum_cost_limit = 2000      -- default -1 uses vacuum_cost_limit (200), shared by all workers
maintenance_work_mem = '1GB'             -- memory for remembering dead tuples during one pass
log_autovacuum_min_duration = '10s'      -- log every slow autovacuum: your best diagnostic

-- the query to watch
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, autovacuum_count
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;

Values are illustrative starting points, not measured optima; the parameters and defaults are from the {{PostgreSQL 18 vacuum settings|https://www.postgresql.org/docs/18/runtime-config-vacuum.html}}. Never turn autovacuum off for a table to "save IO": it is also what prevents section 7.

7. Transaction ID wraparound: the outage that stops all writes

Every transaction that writes gets a transaction ID (XID), a 32-bit counter, and every row version records the XID that created it. Visibility rules ask "was this row created by a transaction older than mine?", and with 32 bits that comparison is done modulo 232: each XID sees about 2.1 billion (231) IDs as the past and the rest as the future. A row whose creator falls more than 231 behind the current XID would suddenly look like it was created in the future and vanish. To prevent that, VACUUM freezes old rows, marking them as older than every transaction, and each table remembers its oldest unfrozen XID (relfrozenxid; the database's minimum is datfrozenxid) ({{routine vacuuming docs|https://www.postgresql.org/docs/18/routine-vacuuming.html}}).

The safety net has four layers: when a table's oldest XID is 200 million old (autovacuum_freeze_max_age), autovacuum runs an aggressive freezing vacuum even if autovacuum is switched off; at 1.6 billion (vacuum_failsafe_age) that vacuum drops its speed limits and skips index cleanup to finish faster; at 40 million XIDs before the wraparound point every command logs a warning; and at 3 million before it, Postgres refuses to assign new XIDs: no more writes until someone fixes it. Freezing can only advance up to the oldest transaction anything still needs, so the real causes are the same as in section 6: a transaction left open, an abandoned prepared transaction, a replication slot holding an old xmin, or autovacuum too slow for a write-heavy database.

Two billion transactions take weeks even on a busy server, so for this page the counter was moved forward on a throwaway server with pg_resetwal -x, just short of the refusal point, after leaving behind a prepared transaction (a transaction from two-phase commit, which survives restarts until someone commits or rolls it back by name) that somebody forgot. Stale advice in the error itself
PostgreSQL 16's refusal message still says Stop the postmaster and vacuum that database in single-user mode. The current documentation says single-user mode should be avoided whenever possible and a normal VACUUM works, which is what fixed it above in 0.36 s on this tiny database ({{routine vacuuming, PostgreSQL 18|https://www.postgresql.org/docs/18/routine-vacuuming.html}}). Remove what holds the XID back first; a VACUUM before that freezes nothing.

This is not theoretical. Sentry was down for most of a US working day on 20 July 2015 when Postgres stopped accepting writes to prevent wraparound ({{Sentry, 2015-07-23|https://blog.sentry.io/transaction-id-wraparound-in-postgres/}}); Mailchimp's Mandrill was down from 4 to 5 February 2019 when one shard hit the limit ({{Mailchimp|https://mailchimp.com/what-we-learned-from-the-recent-mandrill-outage/}}); Notion called wraparound "an existential threat to the product" in the post explaining why it sharded ({{Notion, 2021-10-06|https://www.notion.com/blog/sharding-postgres-at-notion}}). The fix for a big database can take many hours of vacuuming, all of it with writes refused.

The alert that prevents it
Graph SELECT datname, age(datfrozenxid) FROM pg_database and the top tables by age(relfrozenxid). Warn when any database passes about 500 million (a quarter of the way) and page at about 1 billion; in a healthy database the age saws between 0 and 200 million as anti-wraparound vacuums finish (thresholds are this page's suggestion). Alert separately on prepared transactions older than a few minutes and on inactive replication slots.
