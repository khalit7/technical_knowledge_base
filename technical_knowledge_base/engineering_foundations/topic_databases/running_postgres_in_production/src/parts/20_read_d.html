5. Vacuum and autovacuum: the cleaning crew

Postgres never overwrites a row in place: an UPDATE writes a new version and marks the old one replaced, a DELETE only marks the row, and old versions stay while any running transaction might still see them (MVCC, on {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}}). Once no transaction can see a version it is a dead tuple (tuple is Postgres's word for a row version). VACUUM removes dead tuples and their index entries and marks the space reusable; it also records which pages are all-visible (so index-only scans can skip the table) and freezes old rows (section 6). Autovacuum is the background launcher that runs VACUUM and ANALYZE on each table when enough has changed.

When autovacuum runs

A table is vacuumed when its dead tuples exceed autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × rows, by default 50 + 20% of the table ({{vacuum settings|https://www.postgresql.org/docs/18/runtime-config-vacuum.html}}). The launcher checks every autovacuum_naptime (1 minute) with up to autovacuum_max_workers (3) workers, each slowed by a cost limit (autovacuum_vacuum_cost_delay 2 ms per 200 cost units) so it does not swamp the disk. PostgreSQL 18 added autovacuum_vacuum_max_threshold (default 100 million), so a huge table no longer waits for a fifth of itself to die: at the default 0.2, a billion-row table would otherwise collect 200 million dead rows first. Predict that number for a billion rows at 0.01, then drag.

On a big table the default 20% is enormous: per-table scale factors exist for this

Dead tuples before autovacuum starts = 50 + scale factor × rows, capped at 100,000,000 in PostgreSQL 18. Updates per second to reach it in an hour = threshold / 3,600.

Watching it on a churned table

The test table is chat_state: one row per chat (100,000 rows) with an unread count and the time of the last message, updated whenever a chat gets a message, the hottest kind of table a chat product has. pgbench updates random rows at a steady 1,500 per second; the launcher checks every 5 s instead of every minute so a cycle fits on screen; everything else is default.   • HOT updates mostly clean up after themselves. When an update changes no indexed column and the page has room, Postgres writes a heap-only tuple (HOT): the new version goes on the same page, no index is touched, and the next visitor to a full page prunes dead versions on the spot. One index on the updated column (last_message_at, for "chats by recent activity") turned every update into a full one. Before indexing a hot table, compare n_tup_hot_upd with n_tup_upd; free space in each page (fillfactor = 90) makes HOT more likely.
  • Autovacuum is a sawtooth: dead tuples rise to the trigger (50 + 0.2 × 100,000 = 20,050) and drop to near zero; the table grows a little, then holds, because new versions reuse the freed space. That steady state is healthy.
  • One forgotten transaction stops all cleanup. A session that ran one SELECT inside a transaction and never committed keeps its snapshot, so no row version newer than it can be removed, in any table. Autovacuum keeps running and removes nothing; its log says tuples: 0 removed, 182379 remain, 82363 are dead but not yet removable with a removable cutoff that does not move. End the session (pg_terminate_backend(pid)) and set idle_in_transaction_session_timeout (section 7). A replication slot with an old xmin, a replica with hot_standby_feedback = on running a long query, or an abandoned prepared transaction (section 6) do the same.

VACUUM against VACUUM FULL

Plain VACUUM makes space reusable but almost never returns it to the operating system: the file keeps its size. VACUUM FULL rewrites the table into a new compact file and rebuilds its indexes, which does return space, under an ACCESS EXCLUSIVE lock for the whole rewrite: nothing can even read the table.

VACUUM frees space inside the file; only a rewrite shrinks it

On this 200 MB table the lock lasted under two seconds (a reader with lock_timeout gave up while it ran); on a 500 GB table it would be hours of a table nobody can read. Online, you reclaim space with pg_repack or pg_squeeze, which build a copy in the background, replay the changes made meanwhile and take the exclusive lock only for a brief swap (both are extensions missing from the pgserver build, so not measured here). Often you need neither: if the table will grow back, reusable space is fine.

6. Transaction ID wraparound: the outage that stops all writes

Every transaction that writes gets a transaction ID (XID), a 32-bit counter, and every row version records the XID that created it. Visibility asks "was this row created by a transaction older than mine?", and with 32 bits that comparison is done modulo 232: each XID sees about 2.1 billion (231) IDs as the past and the rest as the future. A row whose creator fell more than 231 behind would suddenly look like it came from the future and vanish. So VACUUM freezes old rows, marking them older than every transaction, and each table remembers its oldest unfrozen XID (relfrozenxid; the database's minimum is datfrozenxid) ({{routine vacuuming|https://www.postgresql.org/docs/18/routine-vacuuming.html}}). The safety net has four layers on one axis; drag the age of the oldest unfrozen XID.

Postgres warns only in the last 2% of the range: alert long before

Thresholds from the PostgreSQL 18 documentation: aggressive freezing autovacuum at 200 million (autovacuum_freeze_max_age), even with autovacuum switched off; the failsafe at 1.6 billion (vacuum_failsafe_age) drops the cost limits and skips index cleanup; warnings at 40 million before the wraparound point; refusal of new XIDs at 3 million before it. The 500 million and 1 billion alert lines are this page's suggestion. The slider is linear in XIDs; its end is 231 = 2,147,483,648.

Freezing can only advance up to the oldest transaction anything still needs, so the causes are those of section 5: a transaction left open, an abandoned prepared transaction (from two-phase commit; it survives restarts until someone commits or rolls it back by name), a replication slot holding an old xmin, or autovacuum too slow for a write-heavy database. Two billion transactions take weeks even on a busy server, so for this page a throwaway server's counter was moved forward with pg_resetwal -x, just short of the refusal point, after leaving behind a forgotten prepared transaction. From then on every line is real: inserts printed WARNING: database "template0" must be vacuumed within 3000299 transactions; 308 more succeeded; then ERROR: database is not accepting commands to avoid wraparound data loss, while reads still worked. The holder query found refund-42, a prepared transaction 2,144,483,647 XIDs old; ROLLBACK PREPARED and a normal VACUUM (FREEZE) brought every database back to an age under 300 in 0.36 s.

Stale advice in the error itself
PostgreSQL 16's refusal message still says Stop the postmaster and vacuum that database in single-user mode. The current documentation says single-user mode should be avoided whenever possible and a normal VACUUM works, which is what fixed it above on this tiny database ({{routine vacuuming, PostgreSQL 18|https://www.postgresql.org/docs/18/routine-vacuuming.html}}). Remove what holds the XID back first; a VACUUM before that freezes nothing.
Real run: a wraparound emergency, from warning to fix (measured output)

It happens to real companies (Sentry 2015, Mandrill 2019, Notion before it sharded; below), and on a big database the fix can take many hours of vacuuming, all of it with writes refused.

Three wraparound outages (cases)

It happens. Sentry was down for most of a US working day on 20 July 2015 when Postgres stopped accepting writes to prevent wraparound ({{Sentry, 2015-07-23|https://blog.sentry.io/transaction-id-wraparound-in-postgres/}}); Mailchimp's Mandrill was down from 4 to 5 February 2019 when one shard hit the limit ({{Mailchimp|https://mailchimp.com/what-we-learned-from-the-recent-mandrill-outage/}}); Notion called wraparound "an existential threat to the product" in the post explaining why it sharded ({{Notion, 2021-10-06|https://www.notion.com/blog/sharding-postgres-at-notion}}).

The alert that prevents it
Graph SELECT datname, age(datfrozenxid) FROM pg_database and the top tables by age(relfrozenxid). Warn when any database passes about 500 million (a quarter of the way) and page at about 1 billion; a healthy database saws between 0 and 200 million as anti-wraparound vacuums finish. Alert separately on prepared transactions older than a few minutes and on inactive replication slots.
