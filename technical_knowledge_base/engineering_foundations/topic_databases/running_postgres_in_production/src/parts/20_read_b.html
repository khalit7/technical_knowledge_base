3. Backups done right

Two numbers define what "backed up" means for you. Agree them with whoever owns the product before choosing any tool.

RPO: how much data you can lose

The recovery point objective is the age of the newest data you can get back, measured in time. "RPO 24 hours" means losing up to a day of writes is acceptable. For a chat product, losing a day of messages is not.

RTO: how long you can be down

The recovery time objective is how long the restore may take, from "we need to restore" to "users are back". It is set by database size, network and disk speed, and how practised the procedure is.

Logical against physical backups

A logical backup (pg_dump) asks the database for its contents as SQL or a compressed archive: CREATE TABLE statements and the rows. A physical backup (pg_basebackup, or a tool built on the same mechanism) copies the data directory's files as they are on disk, while the server runs, plus the WAL needed to make that copy consistent. WAL archiving and point-in-time recovery

Because the WAL records every change, a base backup plus every WAL segment written since lets Postgres rebuild the database at any moment you choose. This is point-in-time recovery (PITR). You switch it on with three settings: wal_level = replica (the default), archive_mode = on, and an archive_command that copies each finished 16 MB segment somewhere safe; it must return success only once the file is stored ({{WAL settings|https://www.postgresql.org/docs/18/runtime-config-wal.html}}). To recover, you restore the base backup, tell Postgres where the archive is (restore_command) and when to stop (recovery_target_time), and start it.

Three details from that output matter in a real incident:

  • Finding the moment. You rarely know the second the mistake happened. pg_waldump reads WAL files and prints each record; the DELETE's transaction shows up as a million heap delete records followed by one COMMIT with a timestamp. You can then recover to just before that time, or name the transaction directly with recovery_target_xid (and recovery_target_inclusive = false).
  • A new timeline. After recovery the server says selected new timeline ID: 2. A timeline is a branch of history: from this point the recovered database has a different future from the old one, and its WAL files are named with the new timeline so they never mix with the old ones in the archive.
  • Writes after the mistake. Recovering to 14:02:59 also discards everything written after 14:03 (two messages in the run). So in practice you usually recover into a separate server and copy just the deleted rows back into production with SQL, rather than replacing production. Either way the decision is a product one: say it out loud in the incident channel.

Tools: what professionals run

Nobody writes cp archive commands in production. Three open-source tools do base backups, WAL archiving, retention, compression, encryption and restores against object storage such as S3:

pgBackRest

The most common choice for self-managed Postgres: full, differential and incremental backups, parallel compression, encryption, asynchronous archiving, backup verification. Latest {{2.59.3, 2026-10-04|https://github.com/pgbackrest/pgbackrest/releases}}. {{User guide|https://pgbackrest.org/user-guide.html}}.

WAL-G

A single Go binary, popular in Kubernetes and cloud setups; delta backups to S3, GCS or Azure; also backs up MySQL and others. Latest {{v3.0.9, 2026-08-20|https://github.com/wal-g/wal-g/releases}}.

Barman

EDB's backup server: one machine that pulls backups and streams WAL from many Postgres servers. Latest {{3.20.1, 2026-09-29|https://github.com/EnterpriseDB/barman/releases}}.

A minimal pgBackRest setup, following its user guide (bucket and paths are illustrative):

# /etc/pgbackrest/pgbackrest.conf
[global]
repo1-type=s3
repo1-s3-bucket=chat-db-backups
repo1-s3-region=eu-west-1
repo1-path=/pgbackrest
repo1-retention-full=4            # keep four full backups and the WAL they need
repo1-cipher-type=aes-256-cbc     # encrypted before it leaves the machine
process-max=4
archive-async=y
start-fast=y

[main]
pg1-path=/var/lib/postgresql/18/main

# postgresql.conf
archive_mode = on
archive_command = 'pgbackrest --stanza=main archive-push %p'

# weekly full, daily differential (cron); restore to a moment:
pgbackrest --stanza=main --type=full backup
pgbackrest --stanza=main --type=diff backup
pgbackrest --stanza=main --type=time "--target=2026-10-04 14:02:59+00" --target-action=promote restore

Since PostgreSQL 17 the built-in tools can also take incremental backups (pg_basebackup --incremental, merged with pg_combinebackup: {{release notes|https://www.postgresql.org/docs/17/release-17.html}}), but they do not manage retention or object storage for you. Managed services do all of this for you: Amazon RDS keeps automated backups for up to 35 days and uploads transaction logs to S3 every five minutes, so its point-in-time restore can lose up to about five minutes ({{RDS PITR docs|https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html}}).

A backup you have not restored is not a backup

On 31 January 2017, GitLab.com lost about six hours of database changes. An engineer, tired and fighting replication lag, deleted the data directory on the primary instead of the replica. Then the team found that the nightly pg_dump backups had been failing silently for a long time (the dump tool's major version did not match the server's) and disk snapshots had never been enabled; the best copy was a manual snapshot six hours old, which took about 18 hours to copy back ({{GitLab postmortem, 2017-02-10|https://about.gitlab.com/blog/postmortem-of-database-outage-of-january-31/}}; the full case is in the {{SWE topic's Case files tab|n:3c65c17b0d0d81048ae0dd14ac399b4d}}). Every backup method they had existed; none had been restored.

What "tested restores" means in practice
  • A scheduled job (weekly at least) restores the latest backup to a scratch server, replays WAL to a recent moment, and runs checks: the server starts, row counts of key tables are close to production's, an application smoke query works. It alerts if any step fails.
  • It records how long the restore took. That number, not a guess, is your RTO. Here 221 MB took under two seconds; at a realistic 200 MB/s restore speed a 2 TB database takes about three hours before any WAL replay (2,000,000 MB / 200 MB/s = 10,000 s; illustrative speed).
  • Backups go to another account or project with delete protection (object lock), so a compromised production account or a bad script cannot delete them too.
  • Alert when the archiver fails (pg_stat_archiver.failed_count rising) and when the newest backup is older than its schedule.
