2. Backups and point-in-time recovery

Two numbers define what "backed up" means, and the product owner agrees them before anyone picks a tool. The recovery point objective (RPO) is how much recent data you may lose, measured in time: "RPO 24 hours" accepts losing a day of writes, which a chat product cannot. The recovery time objective (RTO) is how long the restore may take, from "we need to restore" to "users are back", set by database size, disk and network speed and how practised the procedure is.

Logical against physical

A logical backup (pg_dump) asks the database for its contents: CREATE TABLE statements and the rows. A physical backup (pg_basebackup, or a tool on the same mechanism) copies the data directory's files while the server runs, plus the WAL needed to make that copy consistent. Point-in-time recovery: the most important picture on this page

Because the WAL records every change, a base backup plus every WAL segment written since lets Postgres rebuild the database at any moment you choose. You switch it on with three settings: wal_level = replica (the default), archive_mode = on, and an archive_command that copies each finished 16 MB segment somewhere safe and returns success only once the file is stored ({{WAL settings|https://www.postgresql.org/docs/18/runtime-config-wal.html}}). To recover, restore the base backup, tell Postgres where the archive is (restore_command) and when to stop (recovery_target_time), and start it. The recovered server stops replaying just before the DELETE's commit record (recovery stopping before commit of transaction), so the delete simply never happened. Three details decide a real incident:

  • Finding the moment. pg_waldump prints each WAL record; the bad transaction shows up as a million heap delete records followed by one COMMIT with a timestamp. Recover to just before it, or name it with recovery_target_xid and recovery_target_inclusive = false.
  • A new timeline. The recovered server says selected new timeline ID: 2: a branch of history whose WAL files carry the new timeline in their names, so they never mix with the old ones in the archive.
  • Writes after the mistake. Recovering to 14:02:59 also drops everything written after 14:03 (two messages in the run), so you usually recover into a separate server and copy the deleted rows back with SQL. That is a product decision: say it in the incident channel.

A replica is no help here: it applied the DELETE milliseconds later. A delayed replica (recovery_min_apply_delay = '1h') gives you an hour to stop it, a useful extra, never a substitute for archived WAL.

Tools, and what managed services do

Nobody writes cp archive commands in production. Three open-source tools take base backups, archive WAL, keep retention, compress, encrypt and restore against object storage such as S3: pgBackRest (the common choice for self-managed Postgres: full, differential and incremental backups, parallel compression, asynchronous archiving, verification; {{user guide|https://pgbackrest.org/user-guide.html}}), WAL-G (one Go binary, popular in Kubernetes and cloud setups, delta backups to S3, GCS or Azure) and Barman (EDB's backup server, pulling from many Postgres servers). Amazon RDS keeps automated backups for up to 35 days and uploads transaction logs to S3 every five minutes, so its point-in-time restore can lose up to about five minutes ({{RDS PITR docs|https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html}}).

A minimal pgBackRest setup, and the tool versions (reference, versions dated)

PostgreSQL 17's built-in incremental backups (pg_basebackup --incremental, merged with pg_combinebackup: {{release notes|https://www.postgresql.org/docs/17/release-17.html}}) do not manage retention or object storage. The setup below follows the pgBackRest user guide (bucket and paths are illustrative). Latest releases when read: pgBackRest {{2.59.3, 2026-10-04|https://github.com/pgbackrest/pgbackrest/releases}}; WAL-G {{v3.0.9, 2026-08-20|https://github.com/wal-g/wal-g/releases}} (also backs up MySQL and others); Barman {{3.20.1, 2026-09-29|https://github.com/EnterpriseDB/barman/releases}}.

# /etc/pgbackrest/pgbackrest.conf
[global]
repo1-type=s3
repo1-s3-bucket=chat-db-backups
repo1-s3-region=eu-west-1
repo1-path=/pgbackrest
repo1-retention-full=4            # keep four full backups and the WAL they need
repo1-cipher-type=aes-256-cbc     # encrypted before it leaves the machine
process-max=4
archive-async=y
start-fast=y

[main]
pg1-path=/var/lib/postgresql/18/main

# postgresql.conf
archive_mode = on
archive_command = 'pgbackrest --stanza=main archive-push %p'

# weekly full, daily differential (cron); restore to a moment:
pgbackrest --stanza=main --type=full backup
pgbackrest --stanza=main --type=diff backup
pgbackrest --stanza=main --type=time "--target=2026-10-04 14:02:59+00" --target-action=promote restore

A backup you have not restored is not a backup

GitLab.com lost about six hours of data in January 2017 with every backup method in place and none ever restored (the story is below). A restore that runs on a schedule is the only proof a backup works:

What "tested restores" means in practice
  • A scheduled job (weekly at least) restores the latest backup to a scratch server, replays WAL to a recent moment, and checks that the server starts, key row counts are close to production's and a smoke query works. It alerts if any step fails.
  • It records how long the restore took: that number, not a guess, is your RTO. Here 221 MB took under two seconds; at a realistic 200 MB/s a 2 TB database takes about three hours before any WAL replay (2,000,000 MB / 200 MB/s = 10,000 s; illustrative speed).
  • Backups go to another account or project with delete protection (object lock), so a compromised production account or a bad script cannot delete them too.
  • Alert when the archiver fails (pg_stat_archiver.failed_count rising) and when the newest backup is older than its schedule.
The GitLab 2017 outage (case)

On 31 January 2017 GitLab.com lost about six hours of database changes: an engineer fighting replication lag deleted the data directory on the primary instead of the replica, and then the team found the nightly pg_dump had been failing silently (its major version did not match the server's) and disk snapshots had never been enabled; the best copy was a manual snapshot six hours old that took about 18 hours to copy back ({{GitLab postmortem, 2017-02-10|https://about.gitlab.com/blog/postmortem-of-database-outage-of-january-31/}}; the full case is in the {{SWE topic's Case files tab|n:3c65c17b0d0d81048ae0dd14ac399b4d}}). Every backup method existed; none had been restored.
