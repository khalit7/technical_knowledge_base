A backend grows with use (cached catalog entries, memory kept after a big sort), so a thousand long-lived connections add up to gigabytes. But Andres Freund's 2020 analysis found the overhead below 2 MiB per connection with huge pages, and the real ceiling was CPU: every snapshot scanned the list of all connections, which PostgreSQL 14 made much cheaper ({{Analyzing the limits of connection scalability in Postgres, 2020-10-08|https://techcommunity.microsoft.com/blog/adforpostgresql/analyzing-the-limits-of-connection-scalability-in-postgres/1757266}}). What remains is starting a process per new connection, and contention when many more processes are active than there are cores:

Reconnecting for every query keeps 2% of the throughput; reconnecting to PgBouncer instead is 5.6 times faster

Trivial queries (SELECT 1) per second, 8 clients. "New connection each time" is pgbench -C: connect, run one query, disconnect, as an application without a pool or a serverless function does. measured

max_connections, and the arithmetic nobody did

max_connections defaults to 100, needs a restart to change, and keeps 3 for superusers ({{connection settings|https://www.postgresql.org/docs/18/runtime-config-connection.html}}); in the run the application role got 97 connections and the next was refused with FATAL: remaining connection slots are reserved for roles with the SUPERUSER attribute. It runs out through pools: SQLAlchemy's default is 5 connections plus up to 10 overflow per process ({{SQLAlchemy pooling|https://docs.sqlalchemy.org/en/20/core/pooling.html}}), so twenty pods can open 20 × 15 = 300, a deploy briefly runs old and new pods together (600), and workers and cron jobs add theirs. Raising max_connections to thousands is the wrong fix: most would sit idle, and the active ones fight over the same cores and locks. The PostgreSQL wiki's rule of thumb for the number of active connections that gives the best throughput is about (2 × CPU cores) + number of disks ({{wiki: Number Of Database Connections|https://wiki.postgresql.org/wiki/Number_Of_Database_Connections}}; a starting point to measure from, not a law).

PgBouncer: many clients, few server connections

{{PgBouncer|https://www.pgbouncer.org/features.html}} is a small single-process pooler that speaks the Postgres protocol, so applications connect to it as if it were the database. Its pool_mode decides when a server connection is lent: session (a client keeps one from connect to disconnect: everything works, it only saves the connect cost), transaction (one transaction at a time, then it goes back: hundreds of mostly idle clients share a few; the mode almost everyone runs) and statement (returned after every statement, so multi-statement transactions are refused; rare). In the run, 1,000 clients connected in transaction mode with default_pool_size = 20 and 300 of them running a 50 ms transaction at once; SHOW POOLS printed cl_active 832, cl_waiting 168, sv_active 20, and Postgres saw 20 server connections. That short queue is the point: it is far cheaper than a thousand processes fighting over the cores.

Real run: 1,000 clients through PgBouncer (measured output)

The two ways transaction pooling bites

In transaction mode one client's consecutive transactions may run on different server connections, and one server connection serves many clients, so anything that lives in the session breaks: SET, LISTEN, session advisory locks, WITH HOLD cursors, temporary tables kept across transactions, SQL-level PREPARE ({{PgBouncer feature table|https://www.pgbouncer.org/features.html}}). Both of these happened on the first try. Step through the first:

No error reports the first: it is a correctness bug. Use SET LOCAL inside a transaction, or set defaults per role (ALTER ROLE app SET statement_timeout = '5s'). The second is a crash that appeared only after the fifth execution: psycopg 3 prepares a query on the server automatically once it has run five times (prepare_threshold), and asyncpg and many JDBC setups do the same; with max_prepared_statements = 0, 3 of 30 runs failed with DuplicatePreparedStatement: prepared statement "_pg3_0" already exists, with 200 none did. PgBouncer has tracked protocol-level prepared statements since 1.21.0 and, since 1.24.0, does so by default with max_prepared_statements = 200 ({{changelog|https://www.pgbouncer.org/changelog.html}}); the run set 0 to reproduce what older configurations still do. Check the setting before blaming the driver.

Timeouts: the cheapest protection there is

All of these default to 0, off ({{client settings|https://www.postgresql.org/docs/18/runtime-config-client.html}}). Set them per role, so the migration and analytics roles can differ from the web application (values illustrative; pick them from your latency targets):

ALTER ROLE app SET statement_timeout = '5s';                    -- no web request needs a 5-minute query
ALTER ROLE app SET idle_in_transaction_session_timeout = '30s'; -- a forgotten transaction cannot block vacuum for long
ALTER ROLE app SET transaction_timeout = '60s';                 -- PostgreSQL 17+: the whole transaction
ALTER ROLE migrator SET lock_timeout = '3s';                    -- a migration gives up instead of queueing everyone (section 8)

8. Safe schema changes: the lock queue

Most ALTER TABLE forms need an ACCESS EXCLUSIVE lock, even when the change itself is metadata-only and takes a millisecond. The danger is not the change but the queue: locks are granted in order, so an ALTER waiting behind one long transaction makes every later query on that table wait behind the ALTER, even plain reads that would not conflict with the long transaction. Staged on users:

Three reads wait on the ALTER, which waits on one idle transaction

From one real pg_stat_activity snapshot with pg_blocking_pids(pid) (process ids and waits as printed). measured

The first process, blocked by nobody, is idle inside a transaction that read users; the ALTER TABLE ... ADD COLUMN waits for its exclusive lock; the three SELECTs are blocked by the ALTER, not by the idle transaction. Ending either releases all of them. In production every migration therefore runs with a short lock_timeout and retries, so a blocked ALTER gives up in seconds instead of queueing the site:

SET lock_timeout = '3s';      -- give up instead of queueing every reader behind us
ALTER TABLE users ADD COLUMN locale text;
-- on "canceling statement due to lock timeout": wait, retry with backoff, alert after a few attempts

Slow forms get safe recipes: CREATE INDEX CONCURRENTLY, ADD CONSTRAINT ... NOT VALID then VALIDATE CONSTRAINT, a nullable column backfilled in batches. Which of 21 common changes takes which lock, rewrites the table or scans it, measured with the recipes and a lock-queue animation with and without lock_timeout, is the "ALTER TABLE, measured" tab of {{SQL and data modelling|n:3ef5c17b0d0d813980dcd474e19f6c3f}}.
