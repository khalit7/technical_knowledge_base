A backend is cheap when idle and grows with use: each one caches the catalog entries (table and column definitions) it has touched, and memory freed after a big sort is usually kept by the process rather than returned. A thousand long-lived connections that have each touched many tables add up to gigabytes. But memory is not the whole story. Andres Freund's 2020 analysis found that with huge pages the overhead is below 2 MiB per connection, and that the real ceiling was CPU: every query's snapshot had to scan the list of all connections, which PostgreSQL 14 made much cheaper ({{Analyzing the limits of connection scalability in Postgres, 2020-10-08|https://techcommunity.microsoft.com/blog/adforpostgresql/analyzing-the-limits-of-connection-scalability-in-postgres/1757266}}). max_connections, and how it runs out

max_connections defaults to 100 and needs a restart to change; 3 of them are reserved for superusers ({{connection settings|https://www.postgresql.org/docs/18/runtime-config-connection.html}}). An application role that asks for one more gets refused:

It usually runs out through arithmetic nobody did. Each application process keeps its own pool: SQLAlchemy's default is 5 connections plus up to 10 overflow ({{SQLAlchemy pooling|https://docs.sqlalchemy.org/en/20/core/pooling.html}}). Twenty pods (copies of the service) can open 20 x 15 = 300 connections, a deploy briefly runs old and new pods together (600), and a worker fleet and a cron job add theirs. Raising max_connections to thousands is the wrong fix: most of those connections would be idle, and when many are active at once they compete for the same cores and locks. The PostgreSQL wiki's rule of thumb for the number of active connections that gives the best throughput is about (2 x CPU cores) + number of disks ({{wiki: Number Of Database Connections|https://wiki.postgresql.org/wiki/Number_Of_Database_Connections}}; a starting point to measure from, not a law).

PgBouncer: many clients, few server connections

{{PgBouncer|https://www.pgbouncer.org/features.html}} is a small single-process pooler that speaks the Postgres protocol, so applications connect to it as if it were the database. Its pool_mode decides when a server connection is lent out:

session

A client keeps one server connection from connect to disconnect. Everything works; it only saves the connect cost.

transaction

A client gets a server connection for one transaction, then gives it back. Hundreds of mostly idle clients share a few connections. The mode almost everyone runs, with caveats below.

statement

Returned after every statement; multi-statement transactions are not allowed. Rare.

A thousand clients, three hundred of them in a transaction at that moment, and Postgres saw only twenty server connections: the rest waited (cl_waiting) a few milliseconds for a free one. That queue is the point: it is far cheaper than a thousand processes fighting over the cores.

The two ways transaction pooling bites

In transaction mode, consecutive transactions from one client may run on different server connections, and one server connection serves many clients. Anything that lives in the session breaks: SET, LISTEN, session-level advisory locks, WITH HOLD cursors, temporary tables kept across transactions, and SQL-level PREPARE ({{PgBouncer feature table|https://www.pgbouncer.org/features.html}}). Both of these happened on the first try:

The first is a correctness bug that no error reports: client A's 5-second timeout landed on whichever server connection it used and then applied to client B's queries on that connection. Use SET LOCAL inside a transaction, or set defaults per role (ALTER ROLE app SET statement_timeout = '5s'). The second is a crash that appeared only after the fifth execution, because psycopg 3 prepares a query on the server automatically once it has run five times (the prepare_threshold); asyncpg and many JDBC setups do the same. PgBouncer has tracked protocol-level prepared statements since 1.21.0 and, since 1.24.0, does so by default with max_prepared_statements = 200 ({{changelog|https://www.pgbouncer.org/changelog.html}}); the run above set it to 0 to reproduce what older configurations still do. Check the setting before blaming the driver.

Timeouts: the cheapest protection there is

All of these default to 0 (off) ({{client settings|https://www.postgresql.org/docs/18/runtime-config-client.html}}). Set them per role, so the migration role and the analytics role can have different values from the web application:

ALTER ROLE app SET statement_timeout = '5s';                    -- no web request needs a 5-minute query
ALTER ROLE app SET idle_in_transaction_session_timeout = '30s'; -- a forgotten transaction cannot block vacuum for long
ALTER ROLE app SET transaction_timeout = '60s';                 -- PostgreSQL 17+: the whole transaction
ALTER ROLE migrator SET lock_timeout = '3s';                    -- a migration gives up instead of queueing everyone (section 11)

Values are illustrative; pick them from your own latency targets.

9. Upgrades: minor releases and major versions

Postgres versions look like 18.6: 18 is the major version, 6 the minor release. Minor releases only fix bugs and security issues and never change the on-disk format: install the new binaries and restart, after reading the release notes for occasional extra steps. They come out roughly quarterly (18.6 and 17.11 on 2026-08-13: {{release notes|https://www.postgresql.org/docs/18/release-18-6.html}}). A major version comes once a year and may change the system catalogs and the storage format, so the data directory must be converted. Each major version is supported for five years ({{versioning policy|https://www.postgresql.org/support/versioning/}}):

Support windows from the {{versioning policy page|https://www.postgresql.org/support/versioning/}}, read 2026-10-04. The vertical line is today.

PostgreSQL 14 leaves support on 2026-11-12, about five weeks after this page was written. Managed services charge or force-upgrade after end of life (Amazon calls it RDS Extended Support), so "we will upgrade later" has a date.

pg_upgrade: convert in place

pg_upgrade creates the new version's empty cluster, copies over the schema with pg_dump, and then moves the data files across unchanged, since the table format rarely changes. Its modes decide how the files move: copy (safe, slow for big databases), --link (hard links: seconds for any size, but the old cluster cannot be used once the new one has started), --clone (copy-on-write file systems) and, since PostgreSQL 18, --swap (moves directories, often the fastest) ({{pg_upgrade docs|https://www.postgresql.org/docs/18/pgupgrade.html}}). Run --check first, always. Measured, 16.2 to 17.11, both servers stopped throughout:

On this 221 MB database both modes took about two seconds, almost all of it the fixed cost of dumping and restoring the schema; copy mode adds the time to copy every byte (about 17 minutes per terabyte at 1 GB/s, illustrative disk speed), link mode does not. Before PostgreSQL 18 the planner statistics are not carried over, so until vacuumdb --analyze-in-stages finishes, queries can get bad plans; PostgreSQL 18's pg_upgrade keeps them ({{PostgreSQL 18 release notes|https://www.postgresql.org/docs/18/release-18.html}}). Downtime is the whole run plus restarts. Physical replicas cannot follow a major upgrade: they are rebuilt, or upgraded with the rsync procedure in the docs.

Logical replication: upgrade with seconds of downtime

For large databases, set up a new server on the new version, copy the schema, subscribe it to the old one with logical replication (section 4), let it catch up while the old one keeps serving, then switch the application over. Measured, 16 publishing to 17:

The trap at the end is the classic one: logical replication copies rows, not sequence positions, so the new server's messages_id_seq was still at 1 and the first insert collided with an existing row. At cutover, stop writes, wait for the subscriber to catch up, copy every sequence's value (setval), then move the traffic. Other things to plan: tables without a primary key, schema changes during the migration (not replicated), and large objects. PostgreSQL 17 added pg_createsubscriber, which turns a physical replica into a logical one so the initial copy is skipped, and preserves logical slots across pg_upgrade from 17 onwards ({{PostgreSQL 17 release notes|https://www.postgresql.org/docs/17/release-17.html}}). Managed services wrap the same idea: Amazon RDS Blue/Green Deployments build the new-version copy and switch over for you ({{RDS Blue/Green|https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/blue-green-deployments.html}}).
