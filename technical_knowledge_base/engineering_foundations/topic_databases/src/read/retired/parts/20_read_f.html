6. The families: escape hatches from the Postgres default

The problem appears

The product keeps growing, and some requests stop fitting one relational database well: the chat list is rebuilt from the same expensive query thousands of times a minute; users want to search their history by words and by meaning; the operations team stores a latency measurement every second from every server. Each of these has a kind of database built for it. The names multiply quickly (there are hundreds of products), but there are only about nine families, and each exists because of one specific problem.

The idea: a family is a data model plus a storage layout tuned for one access pattern

Read each card as: which problem forces you here, what you pay, and what it would hold in the chat product. Postgres can do a passable version of several of them through extensions, which is why it stays the default until a measurement says otherwise.

Key-value: Redis, Valkey, DynamoDB

Get and set a value by its key, nothing else. Redis keeps everything in memory, so a lookup is a few microseconds of work plus the network hop; writing to disk is optional ({{Redis persistence|https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/}}). DynamoDB is Amazon's managed, replicated version that grows without limit if every access names its key.

Forced by: the same answer read over and over, counters and rate limits, sessions. Costs: no queries beyond the key; as a cache it is a second copy that goes stale (animation below); Redis copies to its replicas asynchronously by default, so a failover can lose writes it already acknowledged ({{Redis replication|https://redis.io/docs/latest/operate/oss_and_stack/management/replication/}}). Chat product: the cached chat list, per-user rate limits.

Document: MongoDB, Firestore

Each record is a nested JSON-like document, read and written whole, with no fixed schema.

Forced by: records whose shape varies a lot and is always read as one unit. Costs: joins and multi-document transactions are weaker or slower; "no schema" becomes many schemas over time. Postgres stores and indexes JSON too (jsonb, {{Postgres JSON types|https://www.postgresql.org/docs/current/datatype-json.html}}), which covers most cases. Chat product: tool-call payloads of varied shape, usually a jsonb column instead.

Wide-column: Cassandra, ScyllaDB, Bigtable

Rows grouped by a partition key that decides which machine holds them, sorted inside the partition; you design one table per query rather than normalising ({{Cassandra data modelling|https://cassandra.apache.org/doc/latest/cassandra/developing/data-modeling/intro.html}}).

Forced by: write volume beyond one machine, many regions, queries known in advance. Costs: no joins, no new queries without a new table, and the partition key can only be changed by rewriting all the data. Chat product: messages at a scale few products reach.

Search: Elasticsearch, OpenSearch

An inverted index maps each word to the documents containing it, like a book index for every word; results are ranked with BM25, a scoring formula that rewards words frequent in the document and rare in the collection (the default in Elasticsearch, {{Elastic docs|https://www.elastic.co/guide/en/elasticsearch/reference/current/index-modules-similarity.html}}).

Forced by: "find messages mentioning invoice", typo tolerance, facets. Costs: another copy, updated with a delay of about a second, that must be rebuildable from the source of truth. Postgres full-text search is enough for modest volumes, but its built-in ranking (ts_rank) is not BM25: it has no rarity weight ({{Postgres docs|https://www.postgresql.org/docs/18/textsearch-controls.html}}). Chat product: search over chat history.

Vector: pgvector, Qdrant, Milvus, Pinecone

Stores embeddings (lists of numbers a model produces so that similar meanings get nearby lists) and finds the nearest ones to a query's embedding, approximately, to be fast. Section 8 covers when the Postgres extension is enough.

Forced by: search by meaning, retrieval for an LLM (RAG). Costs: results are approximate; indexes are large and slow to build. Combining word ranking and vectors (hybrid search) is not always a win: in {{Search and vector databases|n:3ef5c17b0d0d815eb4caef9b4cd4d732}}, scored by nDCG@10 (0 to 1, how good the top 10 results are), vectors alone beat the fusion on Quora questions (0.839 against 0.825) while the fusion won on SciFact (0.714 against 0.645 for vectors) measured. Chat product: "find past chats about this topic", documents for RAG.

Time-series: TimescaleDB, InfluxDB, Prometheus

Timestamped measurements appended in time order, stored in time-sliced chunks, compressed, summarised and deleted on a schedule.

Forced by: metrics at a steady high rate with "last hour" queries. Costs: poor at anything that is not a time range; a column store such as ClickHouse often does the same job. Chat product: latency and tokens-per-second for every request.

Graph: Neo4j, Memgraph

Nodes and edges stored so that following an edge is cheap, for questions about paths and patterns of unknown depth ("the shortest chain of friends from Ada to Chen").

Forced by: path and pattern queries of variable depth (fraud rings, permissions inherited through groups, knowledge graphs). Measured on a friends graph in {{NoSQL in practice|n:3ef5c17b0d0d81ec8456c41e4e8f5f6b}}, Neo4j found a 4-hop shortest path in 5 ms against about 130 ms for a recursive query in Postgres measured. Costs: another system; and it does not win at counting: for "friends of friends" (up to three hops) Postgres joins were the fastest of the engines tried. Chat product: rarely needed.

Embedded: SQLite, DuckDB

A library inside your program, storing data in a local file: no server, no network. SQLite (rows) is likely the most deployed database of all, with over a trillion databases in use ({{sqlite.org|https://www.sqlite.org/mostdeployed.html}}); DuckDB (columns) is its analytics counterpart.

Forced by: a phone or desktop app, tests, notebooks, a single-machine job. Costs: one machine; SQLite allows one writer at a time ({{When to use SQLite|https://www.sqlite.org/whentouse.html}}). Chat product: chat history cached on the phone; analysis in a notebook.

Distributed SQL: CockroachDB, Spanner, TiDB, YugabyteDB

SQL and transactions across many machines and regions; each slice of data is copied to several machines that agree on every change through a consensus protocol (Raft or Paxos).

Forced by: writes or data beyond one Postgres machine, or surviving the loss of a whole region, without giving up SQL. Costs: every write waits for machines to agree (more latency, especially across regions); transactions spanning slices are slower; more to pay and run. Chat product: only at very large scale.

The most common escape hatch by far is the first one, used as a cache: a fast store in front of the database holding copies of answers already computed. Each cached entry usually carries a TTL (time to live) after which it expires. The animation shows what a copy costs. Ada reads her chat list, renames a chat, and reads the list again.

The sequence of events is illustrative. A cache pays off only for answers that are expensive to compute: on the laptop measured for the system design page, a Postgres lookup by primary key took 0.067 ms over a local connection, while the Redis documentation's own benchmark example shows about 0.14 ms per request (vendor figure, different conditions); caching a single-row lookup by key buys nothing. Even "delete on write" has a race: a slow reader can put an old value back just after the delete, which is why production caches add an expiry as a backstop ({{Scaling Memcache at Facebook|https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf}}).

What every extra family costs
Each one is a second copy of some facts with its own lag, its own failure modes, backups, upgrades and on-call knowledge. The question is never "is this tool better at X" but "is X now painful enough, measured, to pay for another system".
