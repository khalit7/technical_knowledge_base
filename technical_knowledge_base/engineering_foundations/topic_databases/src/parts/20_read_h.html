8. The ML and LLM angle

The problem appears

The chat product adds retrieval-augmented generation (RAG): before answering, it finds the passages of a user's uploaded documents closest in meaning to the question and puts them in the prompt. Every passage now has an embedding, plus the facts any app needs: who owns it, who may see it, which document it came from, and a way to delete it when the document is deleted. Separately, the team trains models on chat logs and evaluates them, which means scanning large datasets.

Vectors next to the rows: pgvector first

Finding the exact nearest embeddings means comparing the question with every stored vector. Approximate nearest-neighbour (ANN) indexes trade a little accuracy (recall: the share of the true nearest neighbours returned) for speed. The usual one is HNSW, a layered graph of vectors that a search walks greedily from a sparse top layer down to a dense bottom one ({{Malkov and Yashunin|https://arxiv.org/abs/1603.09320}}). pgvector adds a vector column type and HNSW and IVFFlat indexes to Postgres (version 0.8.7 as of 2026-10-04; {{pgvector README|https://github.com/pgvector/pgvector}}). That makes the passage, its owner, its permissions and its embedding one row: one transaction writes them together, one delete removes them, one backup holds them.

  • Limits worth knowing (from the README): the vector type can be indexed up to 2,000 dimensions, half-precision halfvec up to 4,000; HNSW defaults are m = 16, ef_construction = 64 and hnsw.ef_search = 40 (raise the last for better recall, slower queries).
  • Filtering is where it bites: with an approximate index, a WHERE condition (such as "only this user's documents") is applied after the index scan, so a selective filter can leave fewer results than asked for; version 0.8.0 added iterative scans that keep searching until enough rows pass.
  • Memory arithmetic: a 1,536-dimension embedding in 4-byte floats is 1,536 x 4 = 6,144 bytes (6,152 as pgvector stores it, with an 8-byte header), so a million passages need about 6.2 GB and a hundred million about 615 GB before any index (derived). Half precision halves it.

A dedicated vector database (Qdrant, Milvus, Pinecone and others) earns its place when the vectors outgrow what one Postgres server can hold and search fast, when filtered search dominates and needs filtering inside the graph walk, or when the index must scale separately from the rest of the data. The old version of this page put the line at roughly 10 million and 100 million vectors; those are rules of thumb nobody published a measurement for, so measure recall and latency on your own data instead.

Feature stores are two databases

A model in production needs the same input features it was trained on. A feature store (Feast, Tecton) is a naming convention over two ordinary stores: an offline store holding the history of feature values, used to build training sets and to load the online store, and an online store that serves features "at low latency" and keeps, "for each entity key, only the latest feature values" ({{Feast offline store|https://docs.feast.dev/getting-started/components/offline-store}}, {{online store|https://docs.feast.dev/getting-started/components/online-store}}). In this page's terms: a column store (section 5) plus a key-value store (section 6), fed by the same code so training and serving do not drift apart.

DuckDB on Parquet for datasets and evals

Training data, eval results and logs are mostly Parquet files. DuckDB queries them in place, on a laptop or inside a job, with SQL and no server: the section 5 measurement read two columns of a million rows in 2.6 ms. On 2026-08-26 DuckLabs, the company that develops DuckDB, announced it would join AWS as a subsidiary, with DuckDB and its extensions staying MIT-licensed under the non-profit DuckDB Foundation ({{DuckDB announcement|https://duckdb.org/2026/08/26/ducklabs-to-join-aws.html}}); the {{Database atlas|#t-atlas}} records the deal closing on 2026-08-31.

A language model that writes query plans

Section 4's planner relies on estimates that are often wrong for joins. In September 2026 Rohan Bansal fine-tuned a 4-billion-parameter model (a Qwen 3.8 4B distillation) to write planner hints (for the pg_hint_plan extension) that steer Postgres's join order and join methods, trained on 13,646 queries of the Cardinality Estimation Benchmark and measured on the 113 queries of the Join Order Benchmark ({{write-up, 2026-09-16|https://rohanbansal.com/qorl}}). Untrained, the model produced no usable plan for 99 of the 113 queries. Trained, taking its own pick per query gave a 1.40 times geometric-mean speedup over Postgres's planner, with 7 queries slower; letting it make three attempts per query (up to 15 candidates, each executed and timed) and keeping the fastest gave 1.81 times and a 44.7% latency reduction, with none slower. Read the 1.81 with care: the Join Order Benchmark was also the set watched during development, so it is not a held-out result. The whole project cost about $1,200 in GPU rental and API fees.

Two lessons transfer. The economics: executing several candidate plans costs far more than planning once, so this pays only for the same heavy analytic query run again and again, never for an app's small queries. And the method: the write-up warmed the cache until page hit and read counts were stable within 2% before timing anything, because query timings are easy to fake by accident with a warm or cold cache.

What it costs
Vectors are big (6 KB each at 1,536 dimensions) and their indexes are slow to build and hungry for memory; ANN results are approximate by design. A feature store is two systems kept in step. A learned planner adds a model, GPUs and a measurement harness to answer a question the built-in planner answers for free most of the time.
