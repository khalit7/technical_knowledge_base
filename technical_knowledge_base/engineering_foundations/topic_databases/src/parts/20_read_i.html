How a pro chooses, in one list

1. Start with one Postgres and a normalised schema with keys and constraints, so the database refuses bad data whichever code path sends it (sections 1 and 2).

2. Put every check-then-change inside one statement or one short transaction: a conditional UPDATE ... WHERE balance > 0 first, a row lock or serializable-with-retry when the rule spans rows; never hold a transaction open across a model call (section 3).

3. Index for the queries you actually run, and read the plan: EXPLAIN (ANALYZE, BUFFERS), estimated against actual rows, pages read (section 4).

4. Move analytics off the app database into a column store fed from it, and accept that it lags (section 5).

5. Add a family only for a measured problem, and write down what it costs: the copy, its lag, its staleness and who runs it (section 6).

6. Treat the shard key and the partition key as permanent; everything else can be migrated (section 7).

7. Keep embeddings next to the rows they describe until a measurement says otherwise (section 8).

8. Trust, but test: restore a backup on a schedule, and read what independent testers such as Jepsen found about the systems you run.

Glossary

Every term this page introduces, in the order it appears; each links to where it is explained.

Database: a program that owns data and lets many clients store and query it safely.
Relational: data as tables linked by keys, queried with SQL.
Table, row, column: one table per kind of thing, one row per thing, one column per field.
Primary key: the value that identifies a row uniquely.
Foreign key: a column holding another row's primary key; the link between tables.
Migration: a deliberate, versioned change to the schema.
SQL: the language of relational databases.
Declarative: describing the result, not the steps.
JOIN: combining rows of two tables whose keys match.
GROUP BY: one result row per distinct value, with aggregates such as count and sum.
Schema: the declared tables, columns and rules.
Constraint: a rule checked on every write (NOT NULL, CHECK, REFERENCES, UNIQUE).
Update anomaly: copies of one fact that disagree after a change.
Normalisation: storing each fact once.
Denormalisation: copying facts on purpose to make reads faster.
Lost update: a write based on a stale read silently overwriting another.
Transaction: reads and writes treated as one all-or-nothing unit.
ACID: atomic, consistent, isolated, durable.
Isolation level: how much concurrent transactions may see of each other; read committed, repeatable read, serializable.
Write skew: two transactions each valid alone, breaking a rule together.
MVCC: keeping several versions of a row so readers and writers do not block each other.
Deadlock: two transactions waiting on each other's locks; the database aborts one.
Page: the fixed-size block (8 KB in Postgres) data is stored and read in.
Buffer pool: the database's cache of pages in RAM.
Write-ahead log (WAL): changes appended to a log and flushed before data pages change; replayed after a crash.
fsync: the call that waits until written bytes are on stable storage.
Checkpoint: writing changed pages to the data files so the log can be trimmed.
Replica: a full copy of the database on another machine, kept current from the log.
Index: a sorted structure mapping values to the rows that hold them.
B-tree: the default index: a shallow tree of pages of sorted keys.
Query planner: the part that chooses how to run a query from cost estimates.
EXPLAIN: shows the chosen plan; with ANALYZE, the real counts and times.
OLTP: many small reads and writes of whole rows; what apps do.
OLAP: few large scans and aggregates over a few columns; what analytics does.
Row store / column store: rows kept together, or each column kept together.
Parquet: an open, compressed, column-oriented file format.
DuckDB: an in-process, column-oriented analytical database.
Lakehouse: Parquet files on object storage plus a table format that several engines share.
Partition key: the column that decides which machine holds a row in a wide-column store.
Inverted index: word to the documents that contain it.
BM25: the standard formula for ranking documents by the words they share with a query.
Embedding: a list of numbers a model produces so that similar meanings land close together.
Cache: a fast store holding copies of answers already computed.
TTL: time to live; when a cached entry expires.
Sharding: splitting data across machines by a shard key.
RAG: retrieving relevant passages and putting them in the model's prompt.
ANN: approximate nearest-neighbour search: fast, slightly inexact.
Recall: the share of the true nearest neighbours an ANN search returns.
HNSW: a layered graph index for ANN search.
pgvector: the Postgres extension for vector columns and ANN indexes.
Feature store: an offline history store plus an online latest-value store for model features.
