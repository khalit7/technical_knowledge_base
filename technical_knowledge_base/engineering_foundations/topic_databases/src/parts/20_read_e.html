7. Choosing: five questions, and two doors that only open one way

Every vendor's benchmark shows its product winning, and a database is one of the hardest things to change later. So the choice needs a method, applied when a measured limit forces you off the default. Five questions, in this order:

1. What are the access patterns?Which queries run, how often, how fast they must be. Almost any data fits almost any model; each store is fast only at certain queries (a key-value store only if you always know the key).
2. Which rules must hold across rows?If two things must change together (charge a credit and save a reply), you want real transactions inside one store. This rules out most alternatives for business data.
3. How much writing, and how uneven?This page's laptop, flushing every commit for real, ran 2,133 small write transactions a second with 32 clients measured, and a server SSD flushes far faster; hundreds of thousands a second across regions do not fit one server. Plan for the peak and the busiest single key.
4. How much do you know about future questions?If you cannot list tomorrow's queries, a normalised relational schema answers new ones for free; only queries known and frozen justify a store designed around them.
5. What can your team run at 3 a.m.?Backups that have been restored, failover, upgrades, someone on call who understands it ({{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}}).

The two doors that only open one way. Almost every choice can be undone with a migration; two cannot without rewriting every row. When data is split across machines (sharding), the shard key decides where each row lives: shard by user and "all of one user's chats" is fast while "all chats about a topic, across users" asks every machine. In a wide-column store the partition key plays the same role. Choose either from the queries you will run most and check no single key will be too busy. One more decision is cheapest at schema time: how long each kind of data is kept and how it is deleted (a user's right to erasure, where data may live, audit retention); a store with no practical way to delete one user's rows is one you will migrate off.

A rule of thumb, kept as advice (opinion, not a sourced claim): start with Postgres + S3 (object storage for files and Parquet) + Redis, add a column store when analytics queries hurt, add Kafka when more than two systems need the same events. Each addition is a row of the map with its price; Distributed systems fundamentals keeps the same rule.
