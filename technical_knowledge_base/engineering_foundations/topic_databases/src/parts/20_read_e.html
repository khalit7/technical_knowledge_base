5. Rows and columns: apps and analytics want opposite layouts

The problem appears

The product team asks a new kind of question: "how many tokens did each model produce this month?" It touches every message but needs only two of its seven columns. On the million-message table, Postgres read 157.7 MB (19,251 pages) in 70 ms measured to answer it, because every page holds whole rows, including the message text the question never looks at. At a billion messages that is about 158 GB read per question (derived, scaling linearly), on the same server that is answering users.

The two kinds of work have names. OLTP (online transaction processing) is what the app does: many small reads and writes, each touching a few whole rows (open a chat, save a message), each expected in milliseconds. OLAP (online analytical processing) is what analytics does: few, large queries that read a few columns of a huge number of rows and aggregate them. A layout that is good for one is bad for the other.

The idea: store each column together

A row store such as Postgres keeps each row's values side by side, so fetching one whole row is one page read. A column store keeps all values of one column side by side, so a query reads only the columns it names. Values of one column look alike, so they also compress far better: the role column, which alternates between two words, shrank from 254,530 bytes to 862 measured. The animation answers the same question both ways, on the same million messages: once from Postgres's pages, once from a Parquet file (an open, column-oriented file format: each column of each block of rows is stored and compressed separately, with min and max values recorded so whole blocks can be skipped; {{Parquet docs|https://parquet.apache.org/docs/file-format/}}) read by DuckDB (a column-oriented analytical database that runs inside your program, like a library, with no server; {{duckdb.org|https://duckdb.org/why_duckdb}}).

Both runs return the same four totals (for example 80,277,256 tokens for mini). The column store read about 94 times fewer bytes. Bytes are the fair comparison here; the times come from two different engines and are shown only as a sanity check. {{Query plans|#t-plan}} repeats the measurement at 10 million messages: 1.47 GB read by Postgres against 17.3 MB of two Parquet columns, 87 times fewer bytes and about 50 times faster.

What it costs
Changing one row means rewriting compressed blocks, so column stores are built for appending in bulk, not for updating single rows; reading one whole message touches seven separate column chunks. And the analytics copy is a second copy: something must move the data from Postgres into it (a nightly export, or a stream of changes), and it is always somewhat behind. That is why the fleet picture puts the column store beside Postgres, never instead of it.

Where it runs: DuckDB on Parquet files is the laptop and single-machine end (it happily reads tens of gigabytes); ClickHouse is a column-store server you run yourself; BigQuery, Snowflake and Redshift are managed services that keep storage and compute separate; a lakehouse is Parquet files on cloud object storage plus a table format (Apache Iceberg, Delta Lake) that adds safe concurrent updates, so several engines can read the same files.
