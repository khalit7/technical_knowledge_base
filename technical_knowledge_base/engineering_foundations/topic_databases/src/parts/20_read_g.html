Habits that span the children

1. Start with one Postgres and a normalised schema with keys and constraints, so the database refuses bad data whichever code path sends it (sections 1, 2; SQL and data modelling).

2. Put every check-then-change inside one statement or one short transaction: a conditional UPDATE ... WHERE balance > 0 first, a row lock or serializable with a retry when the rule spans rows; never hold a transaction open across a model call (section 3; Transactions and concurrency).

3. Index for the queries you run, and read the plan: EXPLAIN (ANALYZE, BUFFERS), estimated against actual rows, pages read (section 4; Storage engines and indexes, Query planning and performance).

4. Move analytics off the app database into a column store fed from it, and accept that it lags (section 5; Analytics).

5. Add a family only for a measured problem, and write down its price: the copy, its lag, its staleness and who runs it (section 6; NoSQL in practice, Search and vector databases, Caching).

6. Treat the shard key and the partition key as permanent; everything else can be migrated (section 7; Scaling a database).

7. Keep embeddings next to the rows they describe until a measurement says otherwise (section 8; Search and vector databases).

8. Trust, but test: restore a backup on a schedule, and read what independent testers such as Jepsen found about the systems you run (Running Postgres in production; Transactions and concurrency).
