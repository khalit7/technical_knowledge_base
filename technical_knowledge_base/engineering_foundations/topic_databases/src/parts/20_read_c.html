3. Transactions: when two requests touch the same data

The problem appears

Ben has 1 credit left. He has the chat open in two browser tabs and presses send in both within the same instant. The server code for "send a message" is reasonable on its own: read Ben's balance; if it is above zero, call the model, save the reply, and write the balance minus one. Two copies of that code run at the same time, both read 1, both decide Ben can pay, both write 0. Ben got two answers for one credit.

This is not a thought experiment. Run against a real Postgres for this page (two sessions, each wrapped in BEGIN and COMMIT, the second starting 0.1 seconds after the first): both messages were saved and the balance ended at 0 measured. The same bug shows up as two people booking the last seat, or two withdrawals from one account. Its name is a lost update: one transaction's write silently overwrote a decision based on a value that was already stale.

The idea: transactions, and how isolated they are

A transaction is a group of reads and writes that the database treats as one unit: you say BEGIN, do the work, and say COMMIT (keep it all) or ROLLBACK (undo it all). The guarantees are summed up as ACID, a name from Haerder and Reuter's 1983 survey ({{ACM Computing Surveys|https://dl.acm.org/doi/10.1145/289.291}}):

AtomicAll of the transaction happens, or none of it. Saving the reply without charging the credit cannot happen.
ConsistentEvery constraint holds after each commit (a balance below zero is refused). Consistency of your business rules is still your code's job.
IsolatedTransactions running at the same time do not see each other's half-done work. How isolated is a setting, and it is the hard part.
DurableOnce committed, it survives a crash (section 4).

The measured run above was inside transactions, and Ben still paid once for two answers. That is because Postgres's default isolation level, read committed, lets each statement see everything committed before it started, including another transaction's commit made after yours began. Stronger levels forbid more mix-ups and cost more. The useful way to read them is by the anomaly (the mix-up) each one prevents, as the {{Postgres documentation|https://www.postgresql.org/docs/current/transaction-iso.html}} tabulates:

Read uncommitted exists in the SQL standard, but Postgres runs it as read committed. Write skew is the subtle one: two transactions each read a set of rows, each make a decision that is valid alone, and write different rows, so neither overwrites the other yet the combination breaks a rule (two doctors both going off call because each saw the other on call). It was named in {{Berenson et al., 1995|https://arxiv.org/abs/cs/0701157}}.

How a database isolates without stopping everyone: MVCC

The naive way to isolate is to lock everything a transaction touches, so everyone else waits. Postgres, like most modern databases, instead keeps several versions of a row: an update writes a new version and leaves the old one for transactions that started earlier. Each statement (or, at repeatable read and above, each transaction) reads a consistent snapshot, so, in the documentation's words, "reading never blocks writing and writing never blocks reading" ({{Postgres MVCC|https://www.postgresql.org/docs/current/mvcc-intro.html}}). This is MVCC, multi-version concurrency control. Two writers to the same row still conflict: one waits for the other, or, at the stricter levels, one is told to retry.

The three fixes, in the order a professional reaches for them
  1. Make the check part of the write: UPDATE credits SET balance = balance - 1 WHERE user_id = 2 AND balance > 0, then call the model only if one row changed. Under read committed, a second update waits for the first and re-checks its condition on the new row ({{Postgres docs, read committed|https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED}}), so only one succeeds. One statement, no new concepts.
  2. Lock what you are about to change: SELECT ... FOR UPDATE locks the row until commit; the second tab waits, then reads 0.
  3. Ask for serializable and retry: the database detects any interleaving that could not have happened one transaction at a time and aborts one transaction with a serialization error; your code must retry it. This protects even against anomalies you did not think of, such as write skew.
What it costs
Locks make other transactions wait, and two transactions waiting on each other's locks is a deadlock (the database kills one). Serializable turns conflicts into errors your code must retry. Old row versions pile up until a background clean-up (VACUUM in Postgres) removes them, and a transaction left open for hours stops that clean-up. Keep transactions short: never hold one open while waiting on a model call. And guarantees are only as good as the implementation: Jepsen found that Amazon RDS for PostgreSQL multi-AZ clusters violated snapshot isolation ({{Jepsen, 2025-04-29|https://jepsen.io/analyses/amazon-rds-for-postgresql-17.4}}), where single-node Postgres did not. Defaults differ between products too: MySQL's default level is repeatable read, which Jepsen found weaker than its name ({{Jepsen, MySQL 8.0.34|https://jepsen.io/analyses/mysql-8.0.34}}). Check the default of whatever you run.
