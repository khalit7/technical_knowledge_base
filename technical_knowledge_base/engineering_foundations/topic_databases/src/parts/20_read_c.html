3. Transactions: when two requests touch the same data

Ben has 1 credit and presses send in two browser tabs at once. Each request reads his balance, sees 1, calls the model, saves the reply and writes 0. Run against a real Postgres for this page, each request inside BEGIN and COMMIT: both messages were saved and the balance ended at 0 measured. That is a lost update: a write based on a value that was already stale.

A transaction groups reads and writes into one unit that commits or rolls back whole. ACID (Haerder and Reuter, 1983, {{ACM Computing Surveys|https://dl.acm.org/doi/10.1145/289.291}}) names its promises: atomic (all or nothing), consistent (every constraint holds after each commit; business rules beyond constraints stay your code's job), isolated (concurrent transactions do not see each other's half-done work; how much is a setting) and durable (section 4). Ben's run was inside transactions and still lost the update, because the isolation level Postgres uses by default, read committed, lets each statement see whatever was committed before it started. The levels are best read by the anomalies they still allow ({{Postgres documentation|https://www.postgresql.org/docs/current/transaction-iso.html}}):

Write skew: two transactions each read the same rows, each make a decision valid alone and write different rows, and together they break a rule (two doctors both going off call). Postgres isolates without locking every read through MVCC: an update writes a new row version and readers keep their snapshot, so "reading never blocks writing and writing never blocks reading" ({{Postgres MVCC|https://www.postgresql.org/docs/current/mvcc-intro.html}}).

The three fixes, in the order a professional reaches for them: fold the check into the write (UPDATE ... WHERE balance > 0, and call the model only if one row changed); lock the row you will change (SELECT ... FOR UPDATE); or run serializable and retry on a serialization error, which also catches anomalies you did not think of, such as write skew. The last two were run on Ben's two tabs: one reply sent, balance 0 (serializable aborted the second tab with could not serialize access due to concurrent update) measured. The price: locks make others wait and two waiting on each other is a deadlock; serializable turns conflicts into errors to retry; old row versions pile up until vacuum removes them, and a transaction left open (never across a model call) stops that clean-up.

Go deeper: the eight anomalies at every level on Postgres and MySQL, measured, with MVCC, locks, deadlocks, optimistic concurrency and retries, is {{Transactions and concurrency|n:3ef5c17b0d0d8155aa64ddeb09da144e}}; what a forgotten open transaction does to vacuum on a live server is {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} (section 5); transactions across machines are {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}}; idempotency keys for retried requests are {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}} (section 4).

4. Inside the engine: pages, the log, the index, the planner

On the laptop measured for this page, opening one chat of a 1,000,000-message table (the messages of chat 42000) read 19,349 pages and took 28 ms to return 6 rows measured; with an index it read 12.
