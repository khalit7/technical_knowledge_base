The map: what each kind of store keeps together, what that makes cheap, and its price

A family is a data model plus a storage layout tuned for one access pattern: whatever one planned question reads is stored side by side, so that question is cheap and the questions nobody planned become scans. Read across a row; the price column is the part that only shows when the families are side by side. Postgres does a passable version of several rows through extensions (jsonb, full text, pgvector, partitions), which is why it stays the default until a measurement says otherwise.

One write through the whole stack, and which page owns each step

Ben sends a message that costs one credit. Following that one write from his request to the copies it feeds touches every child of this topic, in this order. Predict before you step: of the eleven steps, how many happen before the database says "committed"?

Six steps decide whether the write is correct and durable; five more keep its copies in step afterwards

  1. Borrow a connection. The app server takes an open connection from its pool instead of opening one (a new connection per query kept 2% of the throughput when measured). Running Postgres in production section 7; Query planning and performance section 8
  2. Send the SQL. UPDATE credits SET balance = balance - 1 WHERE user_id = 2 AND balance > 0, then INSERT INTO messages; constraints refuse a message for a chat that does not exist. SQL and data modelling sections 6, 10
  3. Isolate it. The conditional update locks Ben's credits row; a second tab sending at the same instant waits, re-checks balance > 0 and changes nothing. Transactions and concurrency sections 1, 6
  4. Plan it. The planner estimates rows from its statistics and chooses the index on user_id rather than reading the whole table. Query planning and performance sections 1 to 6
  5. Change pages in memory. The update writes a new version of Ben's row (the old one stays for readers that started earlier) in a page in the buffer pool; the new message gets an entry in every index on messages, while the credits update can skip its indexes when no indexed column changed (a HOT update). Storage engines and indexes sections 1, 2, 5, 11; Transactions and concurrency section 5
  6. Commit. A record of the change is appended to the write-ahead log and flushed to disk; only then does Postgres answer "committed". Storage engines and indexes section 3; Transactions and concurrency section 2
  7. Replicate. A replica receives the same log records and replays them, a little behind; a read sent there just after the commit may not see it. Running Postgres in production section 3; Scaling a database section 3
  8. Invalidate the cache. The app deletes Ben's cached chat list so the next read rebuilds it, and a slow reader can still put the old copy back unless the cache is filled with leases. Caching sections 3, 4
  9. Feed the other copies. Change data capture or a nightly export carries the new row to the column store and the search index, minutes or a second behind. Analytics section 10; Search and vector databases sections 6, 13
  10. Clean up later. A checkpoint writes the changed page to its file; vacuum removes the old row version once no transaction can see it. Storage engines and indexes sections 3, 4; Running Postgres in production section 5
  11. Outgrow one machine. When writes outgrow the server, the same write goes to the shard that owns Ben's user id, and a question across users must ask every shard. Scaling a database sections 6 to 9

The order of events is Postgres's documented behaviour; the user and the statements are the sample rows of section 1.

The answer to the prediction

Six (steps 1 to 6) happen before "committed"; the commit waits only for the log flush, never for the page itself, the replica, the cache or the copies.
