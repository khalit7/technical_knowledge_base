1. Why not just a file

The problem appears

Day one, the chat app keeps everything in one file, chats.json: the server reads it when it starts, changes it in memory, and writes the whole file back after every message. It works for you alone. Then three things go wrong, each at a different number.

  • Two requests at once lose a write. You send a message from your phone and your laptop in the same second. Both requests read the file, each adds its own message, each writes the whole file back: the second write replaces the first, and one message is gone with no error.
  • A crash in the middle breaks the file. The power goes out half-way through writing; the file is now half old, half new, and may not even parse.
  • Every question reads everything. "Show user 17's chats" means loading and scanning the whole file. At a thousand messages nobody notices; at ten million messages (a few gigabytes) every page view reads gigabytes. illustrative

The idea: a database makes four promises

A database (properly a database management system) is a separate program that owns the data and lets many clients use it at once. Your app sends it requests over a connection instead of touching files. In exchange it promises four things a file cannot:

DurabilityOnce it says "saved", the data survives a crash or a power cut (section 4 shows how).
Safe concurrent accessMany requests at once cannot overwrite each other's work by accident (section 3).
QueriesYou ask a question ("user 17's chats, newest first") and it finds the answer without reading everything (sections 2 and 4).
ConstraintsRules the data must always obey ("every message belongs to an existing chat", "a balance is never negative"), checked on every write.

The relational model in plain words

Most databases you will meet first are relational: the data sits in tables, one per kind of thing. A table has named columns (the fields) and rows (one per thing). Each row has a primary key, a value that identifies it uniquely, usually a number called id. A row points to a row of another table by storing that row's key: a foreign key. That pointer is the "relation". The idea is from Edgar Codd's 1970 paper ({{Codd, CACM 1970|https://dl.acm.org/doi/10.1145/362384.362685}}); its lasting point is that you describe data as tables and ask for what you want, and the system decides how to fetch it.

Notice what is not there: the message row does not repeat the user's email or name. It stores only chat_id; the chat stores user_id; the email lives once, in users. Section 2 explains why that matters.

What it costs
A separate server to run, back up and upgrade; a network hop on every request (a fraction of a millisecond in the same data centre); and a schema (the declared tables, columns and rules) that you change through deliberate migrations rather than by editing a file. For anything more than a prototype the trade is overwhelmingly worth it. When you want the promises without a server, an embedded database such as SQLite runs inside your program and stores everything in one file (section 6).
