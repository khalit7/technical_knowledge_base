4. Inside the engine: pages, the log, the index, the planner

The problem appears

The messages table reaches a million rows. Opening a chat runs "the messages of chat 42000", and on the laptop measured for this page that query read 19,349 pages and took 28 ms measured to return 6 rows. Every chat opened by every user pays that, and it grows with the table. Meanwhile section 1 promised that "saved" survives a power cut, yet writing to disk is slow. Both problems are solved inside the engine, and knowing the four pieces below is what lets you read a slow query instead of guessing.

Pages and the buffer pool

A database does not store rows one by one. Postgres keeps every table and index as an array of fixed-size pages, usually 8 KB each ({{Postgres page layout|https://www.postgresql.org/docs/current/storage-page-layout.html}}), and always reads and writes whole pages. The million-message table is 19,235 pages (157 MB) measured; each page holds about 52 rows. Pages in use are kept in RAM in the buffer pool (in Postgres, shared_buffers, 128 MB by default and commonly set to about a quarter of the machine's memory, {{Postgres docs|https://www.postgresql.org/docs/current/runtime-config-resource.html}}). The reason it matters: reading memory takes about 100 nanoseconds, a random read from a fast SSD about 100 microseconds, a thousand times longer (see the {{Numbers to know|n:3c65c17b0d0d81048ae0dd14ac399b4d}} tab of the system design page). Of the 19,349 page reads above, 14,435 were found in the buffer pool and 4,914 had to come from the operating system, because a 157 MB table does not fit in 128 MB.

The write-ahead log: how "saved" survives a crash

Writing every changed page to disk at every commit would be slow (random writes all over the disk) and still unsafe: a crash between two page writes leaves half a transaction on disk. The fix is the write-ahead log (WAL): before any data page changes on disk, a description of the change is appended to a sequential log file and forced to the disk with fsync (the operating-system call that waits until bytes are really on stable storage). The commit is acknowledged once the log record is safe; the changed pages are written later, in bulk, at a checkpoint. After a crash the database replays the log from the last checkpoint and redoes anything missing ({{Postgres WAL|https://www.postgresql.org/docs/current/wal-intro.html}}: "roll-forward recovery, also known as REDO").

One transaction from section 3: save Ben's reply (a page of messages) and charge his credit (a page of credits). The power fails at the same moment in both runs. The order of events is the mechanism Postgres documents; the drawing is illustrative.

The log is one of the most reused ideas in data systems: the same records, shipped to another machine, keep a replica (a full copy of the database on another machine) up to date; replayed to a chosen moment, they restore a backup to that moment; read by another program, they become a stream of changes. Waiting for the fsync is the cost of durability: on this page's laptop a small write transaction took 6.3 ms with a real flush against 0.42 ms without one measured (the {{Numbers to know|n:3c65c17b0d0d81048ae0dd14ac399b4d}} tab has both and server SSDs, which flush far faster). Because one fsync can cover many transactions committing at once, a busy database pays it less than once per commit: with real flushes the same laptop ran 148 write transactions per second from one client and 2,133 from 32 clients measured (pgbench, run for the {{Database atlas|#t-atlas}}).

The B-tree index: a few page reads instead of all of them

An index is a separate structure, kept sorted by some column, that maps each value to where its rows are, like the index at the back of a book. The default kind is the B-tree: a tree of pages, each holding hundreds of sorted keys, so even millions of rows sit only three or four levels below the root ({{Postgres B-tree|https://www.postgresql.org/docs/current/btree.html}}). Finding a value means reading one page per level, then the table pages that hold the matching rows. The animation runs the same lookup without and with CREATE INDEX ON messages (chat_id).

What an index costs
Every insert and update must also update every index on the table, so writes get slower with each index; indexes take space (9.3 MB here, 6% of the table measured); and an index only helps queries that filter or sort on its leading column. Index the columns your queries search by, measure, and drop indexes nobody uses.

The planner, and how to ask it what it did

Because SQL says what, not how, something must choose how. The query planner (or optimiser) considers alternative plans (scan the whole table or use an index; which table to join first; which join method) and estimates the cost of each from statistics it keeps about the data, such as row counts and common values. It runs the cheapest estimate. EXPLAIN shows the chosen plan, and EXPLAIN ANALYZE runs it and adds the real row counts and times ({{Using EXPLAIN|https://www.postgresql.org/docs/current/using-explain.html}}). For the lookup above it prints Index Scan using messages_chat_idx on messages ... (actual rows=6) with Buffers: shared hit=12.

The planner goes wrong when its estimates do: statistics that are stale after a bulk load, or two columns that are correlated (city and country) when it assumes they are independent. The habit that finds the problem is to compare estimated rows with actual rows at each step of the plan; the lowest step where they diverge badly is where to look.

What the planner costs
Planning takes time on every query (a fraction of a millisecond for simple ones; prepared statements reuse plans), and a plan that was right yesterday can go wrong after the data changes. You trade control for convenience: most of the time that is a good trade.
