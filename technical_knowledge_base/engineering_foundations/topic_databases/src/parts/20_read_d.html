5. Rows and columns: apps and analytics want opposite layouts

OLTP (online transaction processing) is what the app does: many small reads and writes, each of a few whole rows, each in milliseconds. OLAP (online analytical processing) is what analytics does: few large queries reading a few columns of a huge number of rows. A row store such as Postgres keeps each row's values side by side, so one whole row is one page read; a column store keeps each column's values side by side, so a query reads only the columns it names, and values that look alike compress far better.

The same question, "tokens per model", over the same 1,000,000 messages: Postgres read 157.7 MB (19,251 pages) in 70 ms, because every page holds whole rows including the text the question never looks at; DuckDB read the two needed columns of a Parquet file (an open column-oriented format, each column of each block of rows compressed separately with its min and max, {{Parquet docs|https://parquet.apache.org/docs/file-format/}}), 1.68 MB in 2.6 ms measured. Both returned the same four totals (80,277,256 tokens for mini); the column store read about 94 times fewer bytes. The role column alone shrank from 254,530 bytes to 862. Bytes are the fair comparison; the times come from two engines. At a billion messages the row store would read about 158 GB per question (derived, linear), on the server that is answering users. {{Query plans|#t-plan}} case 6 repeats it at 10,000,000 messages: 1.47 GB against 17.3 MB of two Parquet columns, 87 times fewer bytes.

The price: a column store rewrites compressed blocks to change one row, so it is built for appending in bulk; and it is a second copy fed from Postgres (a nightly export or a stream of changes), always somewhat behind. Where it runs: DuckDB inside your program on Parquet files; ClickHouse as a server you run; BigQuery, Snowflake and Redshift as managed services with storage apart from compute; a lakehouse is Parquet on object storage plus a table format (Iceberg, Delta Lake) that adds safe concurrent commits, so several engines share the files.

Go deeper: column chunks, encodings, zone maps, vectorised execution, the Parquet file byte by byte, DuckDB, ClickHouse, warehouses and lakehouse tables are {{Analytics: columnar engines, DuckDB and the lakehouse|n:3ef5c17b0d0d8157814ec5dd8a0d4fb5}}; moving changes out of Postgres reliably (the outbox, change streams) is {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}.

6. The families: escape hatches from the Postgres default

The product grows and some requests stop fitting one relational database well: the chat list rebuilt from the same query thousands of times a minute, search by words and by meaning, a latency measurement every second from every server. There are hundreds of products but about ten families (the map above), each the answer to one such problem. Three measured results show the price of reaching for one too early:

  • A cache is not free speed. A cache holds copies of answers already computed, each usually with a TTL. A Postgres lookup by primary key took 0.067 ms over a local connection, while the Redis documentation's own benchmark example shows about 0.14 ms per request (vendor figure, different conditions): caching a single-row lookup by key buys nothing. Even deleting the copy on every write leaves a race in which a slow reader puts the old value back ({{Scaling Memcache at Facebook|https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf}}), which is why caches keep an expiry as a backstop.
  • Hybrid search is not always a win. Scored by nDCG@10, vectors alone beat word-plus-vector fusion on Quora questions (0.839 against 0.825) while the fusion won on SciFact (0.714 against 0.645) measured in {{Search and vector databases|n:3ef5c17b0d0d815eb4caef9b4cd4d732}}.
  • A graph database wins only at depth. On a friends graph Neo4j found a 4-hop shortest path in 5 ms against about 130 ms for a recursive query in Postgres, yet for friends of friends (up to three hops) Postgres joins were the fastest engine tried measured in {{NoSQL in practice|n:3ef5c17b0d0d81ec8456c41e4e8f5f6b}}.

What every extra family costs: a second copy of some facts with its own lag, failure modes, backups, upgrades and on-call knowledge. The question is never "is this tool better at X" but "is X now painful enough, measured, to pay for another system". Postgres's full-text ranking (ts_rank) is not BM25, Redis can lose acknowledged writes in a failover, and a partition key decides forever which machine holds a wide-column row: each family's fine print is on its owner page.
