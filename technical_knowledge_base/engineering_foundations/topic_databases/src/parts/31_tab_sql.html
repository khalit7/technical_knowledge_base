SQL playground: learn SQL by running it

This tab holds a real database engine: SQLite (which its authors describe as the most widely deployed database engine), compiled to WebAssembly and running inside this page with no network. It is loaded with the chat product's data (50 users, 200 chats, 2,000 messages, one credits balance per user). Twelve short lessons take you from your first SELECT to transactions, each with a goal, a hint, a query you can edit and run, and what the result means.

Every lesson was also run, offline, on real PostgreSQL, the database the Reading tab recommends as the default. Its recorded result sits next to the live one, and where the two engines disagree the difference is the lesson: eight of the 45 menu choices differ, and each one is a trap that has bitten real teams.

The data: four tables

A table is a named set of rows with fixed columns. A primary key (PK) is a column whose value is unique and never empty, so it names exactly one row. A foreign key (FK) is a column holding another table's primary key: chats.user_id says which user owns the chat. That pointer is the "relation" in "relational database".

The exact schema (CREATE TABLE statements)
The same text creates the tables in both engines, except that Postgres declares each id as INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY so it, like SQLite, picks the next id when an INSERT leaves it out. The rows come from a seeded generator (src/sql/gen_data.py): the same 2,300 rows every time, with a few gaps on purpose (5 users without a country, 6 users without chats, 37 chats without a title, 8 chats without messages) because gaps are where queries go wrong.


























Watch a JOIN match rows


The same four users and their chats, joined step by step. For each user on the left, the database looks for chats whose user_id equals that user's id, and writes one output row per match. Switch to LEFT JOIN to see the one difference: a user with no match still gets a row, with NULL in the chat columns.










Real rows from the lesson's data. A real engine does not always loop like this: with an index on chats.user_id it jumps straight to the matching chats, and on big tables it may build a hash table of one side first. The {{Query plans|#t-plan}} tab shows which method Postgres picks and why.
