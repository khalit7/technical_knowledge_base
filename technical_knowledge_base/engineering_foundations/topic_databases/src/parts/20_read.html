The idea in one screen

A database keeps an application's data safe, correct and quick to find while many people use it at once; each kind of database buys that for one access pattern by choosing what it stores together, so start with one Postgres and add another store only when a measured problem needs what it makes cheap.

The running example is the one the {{Topic: swe-and-system-design|n:3c65c17b0d0d81048ae0dd14ac399b4d}} page uses: a chat assistant powered by a large language model (LLM). People sign up (users), open conversations (chats), send and receive messages, and spend prepaid credits. Every child page of this topic measures the same product, so their numbers line up. The picture shows where its data lives at three moments; each store on the right is a second copy of some fact, with its own lag, and a child page owns it.

Owners: Postgres and its engine are SQL and data modelling, Transactions and concurrency, Storage engines and indexes, Query planning and performance and Running Postgres in production; Redis is Caching and NoSQL in practice; the vector index is Search and vector databases; the column store is Analytics; outgrowing one machine is Scaling a database.

You need: nothing; the page starts from zero and defines each term where it first appears. The system around the database (servers, queues, failure) is {{Topic: swe-and-system-design|n:3c65c17b0d0d81048ae0dd14ac399b4d}}; the page cache and fsync under it are {{Storage and file systems|n:3f05c17b0d0d8141be7acc1313570cbf}}.

New terms (each defined again where it is used):

Table, row, column, key: one table per kind of thing, one row per thing; a primary key names a row, a foreign key points to another row.
SQL: the declarative language of relational databases: say what you want, the database decides how.
Transaction, isolation level: changes that happen all together or not at all; how much concurrent transactions may see of each other.
Page, WAL, index: the 8 KB block data is read in; the log written before pages so a commit survives a crash; a sorted structure that finds rows without reading all of them.
OLTP, OLAP: many small reads and writes of whole rows (the app); few big scans of a few columns (analytics).
Replica, shard: a full copy of the database on another machine; one slice of the data on its own machine.
Cache, TTL: a fast copy of answers already computed; how long a copy lives before it expires.
Embedding, ANN: a list of numbers a model produces so similar meanings land close together; approximate nearest-neighbour search over them.
