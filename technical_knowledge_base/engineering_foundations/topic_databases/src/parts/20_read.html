One app's data, from a file to a fleet, in one screen

About 27 minutes to read (7,100 words; the glossary at the end can be skimmed), plus the optional animations. It starts from zero: every term is explained where it first appears and collected in the Glossary. Numbers marked measured were measured for this page on a laptop; numbers marked illustrative are made up to show a shape.

A database is a program whose whole job is to keep an application's data safe, correct and quick to find while many people use it at once. This page follows one product's data as it grows, and lets each problem arrive before the idea that fixes it.

The running example is the same one the {{Topic: swe-and-system-design|n:3c65c17b0d0d81048ae0dd14ac399b4d}} page uses: a chat assistant powered by a large language model (LLM). People sign up (users), open conversations (chats), send and receive messages, and spend prepaid credits. The picture shows where that data lives at three moments in the product's life.

Each store is coloured by the section that introduces it. Do not worry about the names yet; each is explained in its section.

The eight sections, one line each

Why not just a fileA file loses writes, breaks on a crash and must be read whole. A database promises the opposite; the relational model organises data into tables linked by keys. SQL from zeroYou say what you want, not how to get it. Six clauses cover most queries; keep one fact in one place. TransactionsTwo requests at once can spend the same credit twice. A transaction makes a group of changes all-or-nothing and isolated; the isolation level says which mix-ups you still allow. Inside the engineData lives in 8 KB pages. A log written before the pages survives crashes; a B-tree index finds one row in a few page reads; the planner picks how to run your query. Rows and columnsApps fetch whole rows; analytics sums one column over millions of rows. Stored by column, the same answer here needed about 94 times fewer bytes. The familiesKey-value, document, wide-column, search, vector, time-series, graph, embedded, distributed SQL: each is an escape hatch from Postgres for one specific problem, with a price. ChoosingFive questions decide the store; two decisions (the shard key and the partition key) cannot be walked back. The ML and LLM angleVectors next to your rows for RAG, feature stores as two ordinary databases, DuckDB on Parquet, and a language model that writes query plans.
The one idea to keep
Start with one PostgreSQL database (Postgres for short: a free, open-source relational database) and add another kind of store only when a measured problem forces you to. Every extra store is a second copy of some fact, and copies drift apart. A professional can name, for each store in the fleet, the problem that justified it and what it costs.
