Query plans: what the database actually does

You write SQL that says what you want; a part of the database called the planner decides how to get it: which table to read first, whether to use an index, how to match rows from two tables. The recipe it picks is the query plan. Here are eight real plans, measured on this page's chat product with 10 million messages, each before and after the change that fixes it.

How to read the numbers
Page
PostgreSQL stores every table and index in fixed blocks of 8 KB called pages. It never reads one row; it reads the page holding it. Counting pages is the honest way to measure work, because time depends on the machine and pages do not.
Buffer pool: "hit" and "read"
PostgreSQL keeps recently used pages in its own memory, the buffer pool (setting shared_buffers, 128 MB here). A page found there is a hit. A page it must ask the operating system for is a read; the operating system may still have it in its own memory, or may have to fetch it from the disk (case 8 shows the three).
Node
A plan is a tree of steps. Each box below is a node: the leaves read tables or indexes, the nodes above them combine, filter, sort or count what the leaves produce. Read a plan from the bottom up.
Estimated rows and actual rows
Before running, the planner guesses how many rows each node will produce, from statistics it keeps about every column. EXPLAIN ANALYZE then runs the query and reports what really happened. When the guess is far off, the planner may have chosen the wrong recipe (case 5).
Loops
How many times a node ran. A node on the inside of a nested loop runs once for every row from the outside, and its rows and time are per run.
