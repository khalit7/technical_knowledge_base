2. SQL from zero

The problem appears

The data is in tables now; the app needs to ask questions of it. "The last 50 messages of chat 11." "How many tokens did each user's replies use this month?" You could write a loop for each question, but then every new question is new code, and the loop decides how to search, which is the part a database is good at.

The idea: say what you want, not how to get it

SQL (Structured Query Language) is the language relational databases speak. It is declarative: you describe the result you want, and the database works out the steps (section 4 shows how it chooses). Six pieces cover most of what an app does:

SELECT id, role, tokens          -- which columns
FROM messages                     -- which table
WHERE chat_id = 11                -- which rows
ORDER BY id DESC LIMIT 50;       -- in what order, how many

JOIN combines rows of two tables whose keys match, which is how the foreign keys of section 1 get used. GROUP BY collapses rows that share a value into one row per value, with an aggregate such as count(*) or sum(tokens) computed over each group. Changing data uses three more statements:

INSERT INTO messages (chat_id, role, tokens) VALUES (11, 'user', 14);
UPDATE chats SET title = 'SQL basics' WHERE id = 11;
DELETE FROM messages WHERE chat_id = 13;

A query is written in one order and evaluated in another. The database starts from the tables (FROM and the joins), filters (WHERE), groups, computes the SELECT list, then sorts; the {{PostgreSQL SELECT reference|https://www.postgresql.org/docs/current/sql-select.html}} lists this processing order. Rules the data must obey: schema and constraints


The schema is the declared shape of the tables. Constraints in it are checked on every write, so bad data cannot get in, whichever code path tries:


CREATE TABLE messages (
  id      INTEGER PRIMARY KEY,                   -- unique, never empty
  chat_id INTEGER NOT NULL REFERENCES chats(id),  -- must name an existing chat
  role    TEXT NOT NULL CHECK (role IN ('user', 'assistant')),
  tokens  INTEGER NOT NULL CHECK (tokens >= 0)
);


Inserting a message for chat 999, which does not exist, shows a constraint doing its job: Postgres refuses it. Try it in lesson 9 of the {{SQL playground|#t-sql}}, which runs SQLite: SQLite accepts the orphan row until foreign keys are switched on with PRAGMA foreign_keys = ON, a default worth knowing.


One fact in one place: normalisation


Suppose, to save a join, every message row also stored the user's email. Ada changes her email: now ten thousand message rows must change, and if one code path forgets, the database holds two emails for one person and nothing says which is right. That is an update anomaly. Normalisation is the discipline of storing each fact once (the email in users, a pointer everywhere else) so that a change is one write. Codd defined the normal forms that make this precise in 1970 and 1971; for daily work the one-line rule is enough.


What it costs
Reading normalised data means joins, which cost work at query time. Copying facts on purpose to avoid joins is denormalisation: it makes reads faster and makes you responsible for keeping every copy in step. Analytics stores (section 5) and wide-column stores (section 6) denormalise deliberately; an app's source of truth usually should not. SQL itself has dialects: the basics above work everywhere, but details (date functions, upserts, JSON operators) differ between Postgres, MySQL and SQLite.
