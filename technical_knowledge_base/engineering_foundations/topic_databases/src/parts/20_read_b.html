1. Why a database, and the relational model

Day one, the chat app keeps everything in one file, chats.json, read at start-up and written back whole after every message. Three things break it, each at a different size: two requests at once each write the whole file and one message vanishes with no error; a power cut half-way through a write leaves a file that may not even parse; and every question ("user 17's chats") reads the whole file, gigabytes at ten million messages illustrative.

A database (properly a database management system) is a separate program that owns the data; the app sends it requests over a connection. It promises four things a file cannot: durability (once it says "saved", a crash cannot lose it; section 4), safe concurrent access (section 3), queries that find answers without reading everything (sections 2 and 4) and constraints, rules checked on every write ("every message belongs to an existing chat").

Most databases you meet first are relational, after Edgar Codd's 1970 paper ({{Codd, CACM 1970|https://dl.acm.org/doi/10.1145/362384.362685}}): data in tables, one per kind of thing, with named columns and one row per thing. A primary key names a row; a foreign key stores another row's key, and that pointer is the "relation". The chat product needs four tables. Click a row: the rows it points to, and the rows that point to it, light up.

The price: a server to run, back up and upgrade; a network hop per request (a fraction of a millisecond in one data centre); and a schema you change by deliberate migrations. An embedded database such as SQLite gives the promises without a server, in one file (the map's Embedded row).

2. SQL: say what you want, not how to get it

SQL (Structured Query Language) is declarative: you describe the result and the database works out the steps (section 4 shows who chooses). Six clauses cover most of what an app asks:

SELECT id, role, tokens          -- which columns
FROM messages                     -- which table
WHERE chat_id = 11                -- which rows
ORDER BY id DESC LIMIT 50;       -- in what order, how many

JOIN combines rows of two tables whose keys match; GROUP BY collapses rows sharing a value into one row with an aggregate such as count(*) or sum(tokens); INSERT, UPDATE and DELETE change data. A query is written in one order and evaluated in another: FROM and the joins, then WHERE, grouping, the SELECT list, then sorting (the {{PostgreSQL SELECT reference|https://www.postgresql.org/docs/current/sql-select.html}} lists the order).

The schema declares the tables, and each constraint in it (NOT NULL, CHECK (tokens >= 0), REFERENCES chats(id), UNIQUE) is checked on every write, whichever code path sends it. Normalisation is storing each fact once (the email in users, a key everywhere else), so a change is one write rather than an update anomaly where two copies disagree. Copying facts on purpose to skip joins is denormalisation: faster reads, and every copy is yours to keep in step; analytics and wide-column stores do it deliberately, an app's source of truth usually should not.

Go deeper: every query here runs in the {{SQL playground|#t-sql}}; joins drawn as pairs, NULL logic, grouping, window functions, recursive queries, upserts, normalisation, constraints and migrations, with 28 graded exercises, are {{SQL and data modelling|n:3ef5c17b0d0d813980dcd474e19f6c3f}}.
