5. Redis as a cache: what it throws away when memory is full, measured

The problem

A cache is always smaller than the data behind it, so when it is full and a new value arrives, something must go. Choosing the victim is the eviction policy. The concepts (LRU evicts the entry used longest ago; LFU the one used least often; TinyLFU only admits a newcomer that looks more popular than the victim) are taught on {{Capacity planning, Eviction|n:3ef5c17b0d0d81458291d55d7443700c}}. This section is about the real thing: Redis's settings, what each one actually does, and how they compare on real traffic.

Two settings, and the default that bites

maxmemory caps the memory Redis uses for data; maxmemory-policy chooses the victim. Out of the box, maxmemory is 0 (no limit on 64-bit systems, so Redis grows until the machine runs out of memory) and the policy is noeviction: "The default is: maxmemory-policy noeviction" ({{redis.conf, 8.8|https://github.com/redis/redis/blob/8.8/redis.conf}}). With a limit and that policy, a full Redis returns an error on every write that needs memory. For a cache, set both, explicitly:

# redis.conf for a pure cache (Redis 8.8). Leave room for replication and persistence buffers,
# which are not counted in maxmemory (Redis key eviction docs).
maxmemory 6gb
maxmemory-policy allkeys-lfu        # or allkeys-lru; see the measurements below
maxmemory-samples 5                 # default; 10 is closer to exact at more CPU
save ""                             # a cache usually needs no snapshots: it can be refilled
appendonly no

The menu: ten policies

PolicyVictimUse it when
noeviction (default)None: writes that need memory failRedis is a store of record (queues, counters you cannot lose), never for a cache
allkeys-lruLeast recently used key, approximatelyA pure cache; the docs call it "a good default option" ({{Redis key eviction|https://redis.io/docs/latest/develop/reference/eviction/}})
allkeys-lfuLeast frequently used, with counts that decay (since 4.0)A pure cache whose popular set is stable
allkeys-lrm (new in 8.6)Least recently modified: only writes refresh the timestampData refreshed by writes, where an unwritten key is stale however often it is read; not for cache-aside (below)
allkeys-randomA random keyEvery key equally likely to be read (rare); a baseline
volatile-lru, volatile-lfu, volatile-lrm (8.6), volatile-randomAs above, but only among keys that have a TTLOne Redis holding both cache keys (with TTLs) and keys that must stay; the docs suggest two instances instead
volatile-ttlThe key whose TTL ends soonestYour code sets short TTLs on keys that are good victims

None of them is exact. Exact LRU would need a linked list updated on every read; Redis instead "samples a small number of keys at random and then evicts the ones with the longest time since last access", keeping a small pool of good candidates between evictions (docs). LFU keeps a frequency estimate of 8 bits per key (a Morris counter: incremented with a probability that falls as it grows, so 255 can stand for about a million hits at the default lfu-log-factor 10) combined "with a decay period so that the counter is reduced over time" (lfu-decay-time 1: one minute). And a volatile-* policy with no TTLs set "behave[s] like noeviction" (docs): the classic 3 a.m. outage, measured below.

Measured: hit ratio by policy and memory, on real traffic

The setup measured: Redis 8.8 on the laptop; a client replays 2,000,000 requests as cache-aside (GET; on a miss, SET a 100-byte value); hit ratio counted after the first 500,000 requests have warmed the cache. Memory is set from the measured cost of one such key, bytes (a 100-byte value plus key, hash table entry and allocator overhead), to hold about 20,000 to 200,000 keys. Five workloads: the real Wikipedia hour, six real hours with drifting popularity, and Zipf at α 0.7, 0.9 and 1.1. Each line also shows exact LRU and Belady's OPT (evict the key whose next use is furthest in the future: the best any policy could do, knowable only offline), simulated on the same requests.

    Caveat on the real traces: inside each hour the order is random (the source has hourly counts, not timestamps), so the short-term bursts that favour LRU in live traffic are missing; the six-hour trace keeps the slower drift. On live traffic with strong bursts, LRU can close the gap to LFU or overtake it, which is why the advice is to try both on a replay of your own traffic.
