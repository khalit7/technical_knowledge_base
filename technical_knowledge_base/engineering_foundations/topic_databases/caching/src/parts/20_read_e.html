4. Consistency: every window in which a reader sees an old value

The useful question is not "is my cache consistent?" (it is a copy, so no) but "in which windows can a reader see a value older than the last commit, and how long can each last?". For cache-aside in front of one Postgres:

WindowHow it opensHow long it lastsFix
Between the commit and the deleteReaders between the writer's two steps get the old cached valueMicroseconds to millisecondsAccept it: it is the minimum for any cache. If one user must see their own write, read from Postgres for that user for a few seconds
Delete before the commit (an ordering bug)The writer deletes, then commits; a reader misses in between, reads the old row (not yet committed) and fillsThe whole TTLAlways commit first, then delete; in an ORM, delete in an after-commit hook, not inside the transaction
Write-through before the commitThe writer sets the cache, then the transaction fails or rolls backThe whole TTL, for a value that never existedNever write a cache inside a transaction that can still fail; delete after commit
The stale set (section 3)A slow reader fills the old value after the writer's deleteThe whole TTLLeases or versioned keys
Fill from a lagging replicaThe reader's miss goes to a read replica that has not yet received the write, and caches the old valueThe whole TTL: the cache turns milliseconds of replication lag into minutes of stalenessFill from the primary for keys just written, or mark "recently written" (Facebook's remote markers, below)
A lost or late invalidationThe delete is dropped (a crash between commit and delete) or the event pipeline lagsUntil the TTL, or until the pipeline catches upThe TTL backstop; an outbox or change data capture makes the delete durable
Write-behindAnything that reads Postgres directly (analytics, other services) sees old data; a cache crash loses acknowledged writesUntil the flush, or foreverUse only for data you can lose or rebuild (counters)

For the chat product the simple version of the replica fix is enough: after a user writes, route that user's reads to the primary for a few seconds (read-your-writes, taught on {{Scaling a database|n:3ef5c17b0d0d81f0aaceee1e21b972be}}; consistency models in full on {{Distributed systems fundamentals|n:3c65c17b0d0d8115bc45c31d915b4d33}}).

Facebook's remote markers and hold-off, in their words (depth)

Facebook's regions read from local replica databases while writes go to one master region, so a cache miss right after a write could fill from a replica that lags. Their fix, the remote marker: the writer "(1) sets a remote marker rk in the region, (2) performs the write to the master embedding k and rk to be invalidated in the SQL statement, and (3) deletes k in the local cluster"; a later miss that finds the marker reads from the master instead (Nishtala et al., "Across Regions: Consistency"). They also delete with a two-second "hold-off" when warming a cold cluster from a warm one, refusing fills for that time, for the same reason.

The rule that ties it together
A cache is an optimisation: the system must stay correct with it empty. If deleting every key would lose data or break behaviour, it is not a cache but a database with no durability, and it needs the treatment of one (the {{NoSQL in practice|n:3ef5c17b0d0d81ec8456c41e4e8f5f6b}} page measured how many acknowledged writes a Redis failover loses).

5. Redis as a cache: what it throws away when memory is full, measured

A cache is smaller than the data behind it, so when it is full something must go: the eviction policy picks the victim. LRU evicts the entry used longest ago (cheap, good for most workloads); LFU the one used least often, with counts that decay (better when a few keys are steadily popular and a scan of one-off keys would flush them out of an LRU); TinyLFU is an admission policy: a newcomer only gets in if a compact frequency sketch says it is read more often than the entry it would evict ({{Einziger, Friedman and Manes, ACM ToS 2017|https://arxiv.org/abs/1512.00727}}; Caffeine, the standard Java cache, uses W-TinyLFU, "a small admission LRU that evicts to a large Segmented LRU if accepted by the TinyLfu admission policy", {{Caffeine wiki|https://github.com/ben-manes/caffeine/wiki/Efficiency}}).

Two settings, and the default that bites

maxmemory caps the memory Redis uses for data; maxmemory-policy chooses the victim. Out of the box, maxmemory is 0 (no limit on 64-bit systems, so Redis grows until the machine runs out of memory) and the policy is noeviction: "The default is: maxmemory-policy noeviction" ({{redis.conf, 8.8|https://github.com/redis/redis/blob/8.8/redis.conf}}). With a limit and that policy, a full Redis returns an error on every write that needs memory. For a cache, set both:

# redis.conf for a pure cache (Redis 8.8). Leave room for replication and persistence buffers,
# which are not counted in maxmemory (Redis key eviction docs).
maxmemory 6gb
maxmemory-policy allkeys-lfu        # or allkeys-lru; see the measurements below
maxmemory-samples 5                 # default; 10 is closer to exact at more CPU
save ""                             # a cache usually needs no snapshots: it can be refilled
appendonly no

Memory per key is more than the value. One cache-aside key with a 100-byte value cost bytes here measured (key, hash-table entry and allocator overhead), and a TTL adds more: size maxmemory from the measured cost of your own keys, not from the values.

None of the policies is exact (Redis samples keys), and a volatile-* policy with no TTLs set behaves like noeviction, the classic 3 a.m. outage measured below.

How Redis approximates LRU and LFU, and the volatile-* trap (depth)

None of the policies is exact. Exact LRU would need a linked list updated on every read; Redis instead "samples a small number of keys at random and then evicts the ones with the longest time since last access", keeping a small pool of good candidates between evictions ({{Redis key eviction|https://redis.io/docs/latest/develop/reference/eviction/}}). LFU keeps 8 bits per key (a Morris counter: incremented with a probability that falls as it grows, so 255 can stand for about a million hits at the default lfu-log-factor 10) combined "with a decay period so that the counter is reduced over time" (lfu-decay-time 1: one minute). And a volatile-* policy with no TTLs set "behave[s] like noeviction" (docs): the classic 3 a.m. outage, measured below.

    All three hold keys and values in memory behind a network protocol, and any of them is a fine cache. They differ in what else they do:

    How to choose. If you already run Redis or Valkey for anything else (rate limits, queues, sessions, leaderboards), use it for caching too: one fewer system. Memcached remains a good choice for a pure, very large cache of opaque blobs where multithreading per box and the absence of persistence are features. Most new systems pick Redis or Valkey; managed services (Amazon ElastiCache, Google Memorystore) offer both.
