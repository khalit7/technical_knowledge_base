8. Postgres's own caches: pages yes, results no, and three tools in between

Postgres caches pages (the buffer pool over the operating system's page cache: {{Storage engines and indexes, section 2|n:3cd5c17b0d0d8102bc1fd11b22606e1a}}), query plans for prepared statements, and catalog data. It does not cache query results: run the same aggregate twice and it is computed twice, from cached pages. MySQL had a query result cache and removed it in 8.0, because invalidating every cached result that touched a table on every write to it scaled badly under concurrency ({{MySQL Server blog, 2017|https://dev.mysql.com/blog-archive/mysql-8-0-retiring-support-for-the-query-cache/}}). Before reaching for Redis, three tools inside the database.

A materialised view, for expensive aggregates

A materialised view is a query whose result Postgres stores as a real table, with its own indexes. A view of daily token usage per user and model on the root's chat data (10 million messages) measured:

CREATE MATERIALIZED VIEW daily_usage AS
  SELECT c.user_id, m.created_at::date AS day, m.model, sum(m.tokens) AS tokens, count(*) AS n
  FROM messages m JOIN chats c ON c.id = m.chat_id GROUP BY 1, 2, 3;
CREATE UNIQUE INDEX daily_usage_key ON daily_usage(user_id, day, model);   -- needed for CONCURRENTLY

The catch is the one this page keeps returning to: the view is a copy. After a new message was inserted, the view still showed user 1's old total ( tokens against in the live tables) until REFRESH MATERIALIZED VIEW recomputed it from scratch in s. A plain refresh takes a lock that blocks readers: a query on the view issued one second into the refresh waited ms. REFRESH MATERIALIZED VIEW CONCURRENTLY builds the new result beside the old one and applies the difference, "without locking out concurrent selects" ({{Postgres docs|https://www.postgresql.org/docs/18/sql-refreshmaterializedview.html}}); it needs a unique index, took s, and the same reader waited only ms.

When to use it: dashboards and reports that tolerate staleness you can state ("usage as of the last 10-minute refresh"), refreshed by a scheduler (cron, pg_cron).

When not, and what to use instead (depth)

When not: data a user expects to see change immediately, or a base table so large that a full recompute every few minutes costs more than it saves; then maintain a summary table incrementally (a trigger or the application adds each new message to its day's row), or use a system that maintains views incrementally (ClickHouse materialised views run on every insert; Materialize is built around it). Postgres itself has no incremental materialised views.

pg_prewarm, for the cold start after a restart

A restart empties shared_buffers, so the database is slowest exactly when traffic returns; measured here, the first lookups after a restart read their blocks at SSD speed, and pg_prewarm (or its autoprewarm worker) made them run at the warm speed from the first request. The same holds for a restarted Redis.

pg_prewarm measured: 20,000 lookups after a restart (depth)

A restart empties shared_buffers, and on a real server, whose OS page cache a reboot also empties, every first miss is an SSD read: the database is slowest exactly when traffic returns. pg_prewarm loads a table or index into the buffer pool on demand, and with shared_preload_libraries = 'pg_prewarm' a background worker "periodically records the contents of shared buffers in a file called autoprewarm.blocks and will, using 2 background workers, reload those same blocks after a restart" ({{pg_prewarm docs|https://www.postgresql.org/docs/18/pgprewarm.html}}). random chat lookups after a restart measured:

With track_io_timing = on, the first pass read blocks in ms, about microseconds each, which is SSD speed: those blocks were in neither cache. After pg_prewarm or an autoprewarm restart, the same lookups ran at the warm speed from the first request. The same holds for Redis: a restarted cache is empty, and the database must survive the miss rate until it refills (Facebook's cold clusters fill from a warm cluster first, "in a few hours instead of a few days").

Memoize, a cache inside one query, measured (depth)

Since Postgres 14 the planner can put a Memoize node above the inner side of a nested-loop join: when the same lookup value comes back (many messages of the same chat), the cached inner result is reused instead of probing the index again; "less commonly looked up results may be evicted" when its memory (work_mem times hash_mem_multiplier) fills ({{enable_memoize|https://www.postgresql.org/docs/18/runtime-config-query.html}}). On a query that looks up the owner of every chat belonging to the 30 heaviest users (6,250 chats, 30 distinct owners) measured:

SELECT u.plan, count(*) FROM chats c JOIN users u ON u.id = c.user_id WHERE c.user_id <= 30 GROUP BY 1;

When it runs, the cache works as designed: 30 index probes instead of 6,250. And the planner did not choose it: it built a hash table of all 100,000 users instead, times slower here, because its cost model did not foresee that so few owners repeat so often (Memoize only appeared with hash and merge joins disabled, done here only to show the node). You cannot request Memoize directly; recognising it, and its absence, in an EXPLAIN plan is the skill, taught on {{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}}, and the usual fix for a misestimate is better statistics, not switching join methods off in production.

9. HTTP caching and CDNs: the copies outside your servers

Every HTTP response can say who may cache it and for how long, and browsers, reverse proxies (nginx, Varnish, Envoy) and CDNs obey the same headers ({{RFC 9111|https://www.rfc-editor.org/rfc/rfc9111}}; {{MDN's HTTP caching guide|https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching}} is the readable version; header semantics are owned by {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}}). A CDN is a cache run for you in hundreds of cities: it serves static files and any public response marked cacheable, and its hit ratio is what you pay for, because every miss crosses the world to your servers (about 20 ms to an edge against 78 ms across the Atlantic on the ladder of section 2). CDNs collapse concurrent misses for the same URL into one request to you (the coalescing of section 7) and support stale-while-revalidate and stale-if-error. A reverse proxy in your own data centre can also be told to drop entries (Varnish has {{purging and banning|https://www.varnish.org/docs/users-guide/purging/}}); it spares the app servers on anonymous traffic and helps little once every response is personalised. The system-level decision is which response gets which policy; for the chat product:

ResponseHeaderMeaning
The app's JavaScript bundle, named by its content hash (app.3f9a1c.js)Cache-Control: public, max-age=31536000, immutableAnyone may cache it for a year and need not even revalidate ({{RFC 8246|https://www.rfc-editor.org/rfc/rfc8246}}); a new release gets a new name, which is the only invalidation that reaches every browser
The public model listCache-Control: public, max-age=60, stale-while-revalidate=300Fresh for 60 s; for 5 minutes after that a cache may serve the old copy while it fetches a new one in the background ({{RFC 5861|https://datatracker.ietf.org/doc/html/rfc5861}})
A user's conversation listCache-Control: private, no-cache plus ETag: "v7"Only the user's browser may store it, and must ask before each use; the browser sends If-None-Match: "v7" and gets 304 Not Modified (no body) if nothing changed
A password reset pageCache-Control: no-storeNobody keeps a copy

Three mistakes cause most HTTP caching incidents: a personalised response cached by a shared cache because it lacked private (one user sees another's page); a cache key that ignores a header the response depends on (fix with Vary, for example Vary: Accept-Encoding); and a long max-age on a URL whose content changes, which no purge can recall from browsers. s-maxage sets a lifetime for shared caches only. An ETag is a versioned key by another name: the server's version of the resource, compared on each request. For the chat assistant the CDN carries the app and static assets; conversations are personal and uncacheable at the edge.
