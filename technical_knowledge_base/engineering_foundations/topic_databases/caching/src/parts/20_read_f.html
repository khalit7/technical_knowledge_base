6. What a hit is worth: hit-rate arithmetic and the cost of a miss

With λ reads a second and hit ratio h, the database sees (1 − h) × λ. So going from 90% to 99% hits looks like a 9-point gain but divides the database's read load by ten (1,000 reads a second become 100, then 10). Mean latency is h × tcache + (1 − h) × (tcache + tdb). Predict: at the defaults the database is comfortable; what happens to it if the cache restarts empty? Then drag.

The database is sized for the misses, so an empty cache sends it more than it can take

Demand 1,000 reads a second against a database that answers about 600 (illustrative, the {{system design root's Step 2|n:3c65c17b0d0d81048ae0dd14ac399b4d}} example); tcache = ms (Redis GET) and tdb = ms (the usage aggregate below), both measured here on loopback. Formulas checked in recompute.py.

Three consequences. The tail is the miss path: at a 95% hit rate the p99 is a database read however fast the cache is, so a cache improves the median far more than the p99. The cache has become capacity: when it empties (a restart, a failover, a deploy that changes every key) the full load lands on a database sized for a fraction of it; Facebook keeps spare "Gutter" servers, about 1% of the memcached fleet, to take a failed server's keys rather than let its misses reach the databases (Nishtala et al.). Warm up before taking traffic: fill a new cache from the old one, or ramp traffic (section 8 measures the same cold start inside Postgres). The queueing behind "more than it can take" is on {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}}.

Not every miss costs the same

A miss on "chat 42 by its id" costs Postgres ms; a miss on "this user's token usage by model" costs ms (medians over random keys on the root's 10-million-message database, client round trips over a local connection) measured; a Redis GET took ms on the same machine. Caching the first saves almost nothing (a Redis round trip costs about as much as the query); caching the second saves times the cost of the lookup. A cache that hits 95% of cheap requests and misses every expensive one has a beautiful hit ratio and saves the database almost nothing. So count work saved:

CWHR = Σhits cost(miss avoided) / Σall requests cost(miss)
cost
what a miss on that request would cost: backend milliseconds, database CPU, or dollars
CWHR
the cost-weighted hit ratio: the share of backend work the cache removed; equal to the hit ratio only when every miss costs the same

In the Redis runs of section 5, one key in ten was marked expensive at random (independent of popularity), so CWHR equals the plain hit ratio up to noise: no Redis policy knows what a miss costs. A cost-aware policy does. GreedyDual (Young 1994; with sizes, Cao and Irani, {{USENIX 1997|https://www.usenix.org/legacy/publications/library/proceedings/usits97/full_papers/cao/cao.pdf}}) gives each entry a priority of "L + the cost of missing it"; the victim is the lowest priority, and L rises to each victim's priority, so cheap entries leave first and expensive ones leave only when they stop being used. On the same Wikipedia requests with the measured costs simulated, not a Redis policy, it gives up plain hits and saves the most work:

Redis has no such policy, so production systems get the same effect by hand: separate pools (Facebook: "a small pool for keys that are accessed frequently but for which a cache miss is inexpensive", and "a large pool for infrequently accessed keys for which cache misses are prohibitively expensive"; in Redis terms, two instances, so cheap churn cannot evict expensive results); longer TTLs for expensive results, or caching only results above a cost threshold (do not cache a 0.07 ms lookup at all); and precomputing the expensive ones (a materialised view, section 8). For an LLM cache the cost has an exact money form (section 11).

What to put on the cache dashboard (reference)

What to put on the dashboard (Redis's INFO stats exposes the first three): hits and misses (keyspace_hits, keyspace_misses); evicted_keys next to expired_keys (many evictions: memory too small or wrong policy; many expiries: TTL too short); latency split by hit and miss; database load with and without the cache; and the number of distinct keys, whose unbounded growth means a timestamp or request id got into a key.

7. TTLs, jitter and stampedes: when a popular copy expires

Choosing a TTL. A TTL is the staleness you accept, stated in seconds: the bound on how long a forgotten invalidation can last and on how long an un-invalidated copy can lie. Short TTLs cost misses; long ones cost staleness. Per-user data that is hot only during a session fits minutes; shared reference data that is invalidated explicitly can carry hours, with the TTL as the backstop.

Jitter. Entries written together with the same TTL expire together: a deploy that refills 10,000 hot keys in the same second sends their next reads to the database in the same second, 300 s later. Adding a random extra 0 to j% to each TTL spreads those expiries over 300 × j seconds. Drag the jitter:

Ten per cent of jitter turns one spike of 10,000 expiries into a plateau the database can absorb

10,000 keys filled at t = 0, TTL 300 s plus a uniform random 0 to j% illustrative. Peak expiries per second = keys / (300 × j), derived; each becomes a database query on its key's next read. The 600 a second line is the same illustrative database as in section 6. TTL jitter is common advice (a random 0 to 10%), not from a single source.

Stampedes. A stampede (dog-piling, a thundering herd) is one hot key expiring: every request that arrives before someone has rebuilt it misses and rebuilds it too. If the rebuild takes 300 ms and the key is read 200 times a second, 60 requests run the same expensive query at once, which makes the query slower, which widens the window. Facebook measured it: "Without leases, all of the cache misses resulted in a peak database query rate of 17K/s. With leases, the peak database query rate was 1.3K/s" (Nishtala et al.). Predict: which defence sends the database one query and makes no request wait?

One expiry, four defences: only the unprotected cache sends 60 queries for one key

served fresh from cachemissed and queried the databasewaited for another request's rebuildserved the old value

The model (ported from {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}}'s model.py, stampede, plus a serve-stale mode): one key read 200 times a second, expiring at t = 1 s, rebuilt by a 300 ms database query; XFetch with β = 1 and Δ = 300 ms on a seeded random draw (seed 5) illustrative rates. The counts (60, 1, 1, 1 database queries) are checked in recompute.py.

  1. Request coalescing (single-flight): the first miss rebuilds; the others wait for its answer (Go's singleflight, nginx's proxy_cache_lock on; Facebook's leases across servers, "a token only once every 10 seconds per key"). Cost: the waiters still wait for the rebuild.
  2. Serve stale while revalidating: keep the old value a little past its TTL and refresh in the background (Cache-Control: stale-while-revalidate=30, {{RFC 5861|https://datatracker.ietf.org/doc/html/rfc5861}}). Cost: a few seconds of staleness.
  3. Probabilistic early expiry (XFetch): each reader recomputes early with a probability that rises as expiry approaches and as the rebuild gets more expensive: recompute if now − Δ · β · ln(rand()) ≥ expiry, Δ the last rebuild's duration ({{Vattani, Chierichetti and Lowenstein, VLDB 2015|https://cseweb.ucsd.edu/~avattani/papers/cache_stampede.pdf}}, proved optimal; β = 1 "already provides effective prevention against cache stampedes"). Cost: one early rebuild per expiry and no locks; only the reader that refreshes waits.
The defences in their sources' words, and a minimal single-flight for asyncio (depth)

Facebook's other clients are told to "wait a short amount of time" and retry. Go's singleflight: "making sure that only one execution is in-flight for a given key at a time. If a duplicate comes in, the duplicate caller waits for the original to complete and receives the same results" ({{golang.org/x/sync v0.23.0|https://pkg.go.dev/golang.org/x/sync/singleflight}}). nginx's proxy_cache_lock on: "only one request at a time will be allowed to populate a new cache element" ({{nginx proxy module|https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_cache_lock}}); its stale-while-revalidate is proxy_cache_use_stale updating plus proxy_cache_background_update on.

import asyncio
_inflight: dict[str, asyncio.Future] = {}

async def get_coalesced(key, load):
    if (fut := _inflight.get(key)) is not None:
        return await fut                   # someone is already loading this key: share their answer
    fut = asyncio.get_running_loop().create_future()
    _inflight[key] = fut
    try:
        value = await load(key)            # the one real database call
        fut.set_result(value)
        return value
    except Exception as e:
        fut.set_exception(e)               # waiters get the error too, not a hang
        raise
    finally:
        del _inflight[key]

Per process only: 8 servers can still send 8 queries. Route each key to one server (consistent hashing) or coalesce in the shared cache (a short lock key with SET key NX PX 3000, as the lease of section 3 does) to go further.
