6. Cost-weighted hit ratio: counting the work saved, not the requests

The problem

The hit ratio treats every request alike. But a miss on "chat 42 by its id" costs Postgres ms, while a miss on "this user's token usage by model" costs ms (medians over random keys, measured on the root's 10-million-message database, client round trips over a local connection) measured; a Redis GET took ms on the same machine. Caching the first kind saves almost nothing (a Redis round trip costs about as much as the query); caching the second saves times the cost of the lookup. A cache that hits 95% of cheap requests and misses every expensive one has a beautiful hit ratio and saves the database almost nothing.

The measure

CWHR = Σhits cost(miss avoided) / Σall requests cost(miss)
cost
what a miss on that request would cost: backend milliseconds, database CPU, or dollars
CWHR
the share of backend work the cache removed; equal to the hit ratio only when every miss costs the same

In the Redis runs of section 5, one key in ten was marked expensive at random (independent of popularity), so the cost-weighted hit ratio equals the plain one up to noise: no Redis policy knows what a miss costs. A cost-aware policy does. GreedyDual (Young 1994; with sizes, Cao and Irani, {{USENIX 1997|https://www.usenix.org/legacy/publications/library/proceedings/usits97/full_papers/cao/cao.pdf}}) gives each entry a priority of "L + the cost of missing it"; the victim is the lowest priority, and L rises to each victim's priority, so cheap entries leave first and expensive ones leave only when they stop being used. The trade is visible: GreedyDual gives up some plain hits to keep the expensive keys, and the work saved goes up. Redis has no such policy, so production systems get the same effect by hand:

  • Separate pools. Facebook partitions memcached into pools: "a small pool for keys that are accessed frequently but for which a cache miss is inexpensive", and "a large pool for infrequently accessed keys for which cache misses are prohibitively expensive" (Nishtala et al.). In Redis terms: two instances (or two logical caches with their own memory), so cheap churn cannot evict expensive results.
  • Longer TTLs for expensive results, or caching only results whose measured cost is above a threshold (do not cache a 0.07 ms lookup at all).
  • Precompute the expensive ones (a materialised view, section 8), which turns the expensive miss into a cheap one.

What to put on the dashboard (Redis exposes the first three in INFO stats): hits and misses (keyspace_hits, keyspace_misses); evicted_keys next to expired_keys (many evictions: memory too small or wrong policy; many expiries: TTL too short); latency split by hit and miss, since the tail of the request latency is the miss path; database load with and without the cache; and the number of distinct keys, whose unbounded growth means a timestamp or request id got into a key. For an LLM cache the cost has an exact money form, section 11.

7. Redis, Valkey or Memcached

All three hold keys and values in memory behind a network protocol, and any of them is a fine cache. They differ in what else they do:

Memcached 1.6Redis 8 / Valkey 9
ValuesOpaque bytes with an expiry; get, set, delete, increment, compare-and-swapStrings plus hashes, lists, sets, sorted sets, streams; Redis 8 adds JSON, vector sets, search and time series
ThreadsMultithreaded: "By default 4 threads are allocated" ({{memcached wiki|https://github.com/memcached/memcached/wiki/ConfiguringServer}})Commands run one at a time on one thread (so each command is atomic); network I/O can use extra threads (io-threads; Valkey 8 reworked this, see its {{1 million requests a second post|https://valkey.io/blog/unlock-one-million-rps-part2/}})
MemoryA slab allocator: memory in 1 MB pages split into fixed-size chunks per size class, each class with its own LRU ({{memcached internals|https://github.com/memcached/memcached/wiki/UserInternals}}), a segmented LRU (hot, warm, cold) since 1.5 ({{memcached blog|https://memcached.org/blog/modern-lru/}})One heap; the ten policies of section 5

How to choose. If you already run Redis or Valkey for anything else (rate limits, queues, sessions, leaderboards), use it for caching too: one fewer system. Memcached remains a good choice for a pure, very large cache of opaque blobs where multithreading per box and the absence of persistence are features. Most new systems pick Redis or Valkey; managed services (Amazon ElastiCache, Google Memorystore) offer both.
