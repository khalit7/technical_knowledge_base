2. The layers: from the CPU to the browser

When a user opens a conversation, the request passes through up to nine caches, and each one exists because the thing behind it is slower. Read the ladder top to bottom as "where could this answer already be?". Every step down the list is between about ten and a hundred times slower than the one above it, which is the whole argument for caching.

Four things change as you move outward, and they explain most design decisions:

  • Who invalidates. Hardware keeps CPU caches correct by itself (a coherence protocol called MESI makes cores agree on each 64-byte line). The kernel keeps the page cache correct; Postgres keeps its buffer pool correct (it is the only copy writers change). From the application cache outward, you must invalidate, and the further out, the fewer tools you have: you can delete a Redis key, ask a CDN to purge (a request that must reach every edge city), but you cannot reach into a browser at all.
  • How many copies. One Redis serves every app server. An in-process cache (a Python dict, functools.lru_cache) exists once per process: 8 servers with 4 workers each hold 32 independent copies, each warming and going stale on its own.
  • Who shares it. A browser cache is one user's; a CDN is everyone's, so a personalised response cached at the edge leaks to other users unless it is marked private (section 9).
  • What a miss costs. An L1 miss costs nanoseconds; a CDN miss crosses an ocean to your servers. The value of a layer is how much it saves per hit, times how often it hits (section 6).
The two caches you do not configure but must understand
The page cache is the operating system keeping recently read file blocks in otherwise free RAM: an 8 KiB read of a cached block took microseconds here, against about 100 microseconds from an NVMe SSD. The buffer pool (Postgres's shared_buffers) is the database's own page cache, on top of the operating system's, so a page can be cached twice ("double buffering"). Both are taught with measurements on {{Storage engines and indexes, section 2|n:3cd5c17b0d0d8102bc1fd11b22606e1a}}; this page measures only what happens to the buffer pool across a restart (section 8). A practical rule from both: before adding Redis in front of Postgres, check that the working set fits in the database server's RAM; a database whose hot pages stay in memory answers a primary-key lookup in well under a millisecond.
