10. The LLM caches, first: the KV cache and prefix caching

An LLM product has three caches that a web product does not, and they differ in the one property that matters most: can a hit return a wrong answer? The KV cache and prompt caching never change the answer; a semantic cache can.

The first two are the same cache seen from two sides. A transformer generates text one token (a word piece) at a time, and every layer's attention needs a key and a value vector for each earlier token; servers keep those in GPU memory instead of recomputing them, the KV cache. It is never stale (the keys and values of a given prefix under a given model are fixed); its problem is size, which is why KV memory, not compute, usually caps how many conversations one GPU serves. Because attention is causal, two requests that start with the same tokens share those keys and values, so a server can keep them and skip that part of the prefill (the first pass over the prompt, which dominates time to first token): prefix caching, exact by construction. How big the cache is (bytes per token from a model's config, Llama 3.1 70B's 320 KiB per token, why decode is memory-bound) is taught from zero in section 2 of {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}; how vLLM's hashed blocks ({{design doc|https://docs.vllm.ai/en/stable/design/prefix_caching/}}) and SGLang's RadixAttention ({{LMSYS blog, January 2024|https://www.lmsys.org/blog/2024-01-17-sglang/}}) find a shared prefix, and which blocks to evict on a day of real traffic, in section 3 of {{Batching, KV cache and scheduling in depth|n:3c65c17b0d0d819db53bd2c48909e5b2}} and its Eviction lab.

What a cache engineer takes from it: prefix caching dictates prompt layout. Stable content first (system prompt, tool definitions, documents), anything that changes per request last; one timestamp at the top of a system prompt makes every request a miss. The {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}} page animates one conversation under both layouts (section 9 there), and routing requests to the replica that holds their prefix is measured on real replicas in {{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}, section 1.

Go deeper (optional): PagedAttention, KV quantisation (FP8 KV halves the bytes per token), offloading cold prefixes to CPU memory or SSD (LMCache, Mooncake, NVIDIA Dynamo), and cache-aware routing belong to {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} and its child Batching, KV cache and scheduling (sections 2 to 4). New architectures shrink the entry itself: DeepSeek-V3's multi-head latent attention stores one 576-number vector per layer (68.6 KiB per token), worked through on the {{DeepSeek page|n:3c65c17b0d0d81a2ae7ec6796947a235}}.

11. Provider prompt caching: the same idea, sold by the token

When you call a hosted model, the provider runs prefix caching for you and passes on part of the saving: input tokens read from its cache are billed at a fraction of the normal price. It never changes the answer. The rules that decide whether a request hits (Anthropic's tools, system, messages order and what invalidates each level, breakpoints and the 20-block lookback, minimum lengths, lifetimes, parallel first requests, the usage fields that report a hit, and OpenAI's and Gemini's versions) are owned by {{Context engineering|n:3f15c17b0d0d811292cee46514370431}}, section 2, which measures one volatile line in three places on a real agent. This section keeps the economics: the prices below (as of 5 October 2026, from each provider's documentation) and when caching pays.

Break-even: does caching pay?

With a write multiplier w (what writing a prefix costs, relative to sending it normally) and a read multiplier r, a prefix used n times costs w + r(n − 1) with caching against n without. Caching pays once

n > 1 + (w − 1) / (1 − r)
Correction to the old page
The old page said Anthropic's caching breaks even at "roughly 1.3 reads inside the TTL". With w = 1.25 and r = 0.1 the break-even is n = 1 + 0.25 / 0.9 = 1.28 total uses: one write plus a single read (2 uses: 1.35 against 2.00) already saves 32.5%. OpenAI's own guide gives the same arithmetic: "writing a prefix once and fully reusing it once costs 1.35× its ordinary input cost, compared with 2×" ({{OpenAI prompt caching|https://developers.openai.com/api/docs/guides/prompt-caching}}). The old page also said OpenAI has no write surcharge: true for models before GPT-5.6, but GPT-5.6 and later charge 1.25× for writes. And the read multiplier is no longer 0.1× everywhere: Anthropic bills reads at 0.05× on Claude Opus 5.5 and 0.025× on Fable 5.1 and Mythos 5.1; OpenAI at 0.05× on GPT-6.1 Sol.
