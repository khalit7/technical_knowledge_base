3. Patterns and invalidation: who fills the copy, and who retires it

The patterns: who reads and writes the cache

Five patterns differ only in who talks to whom on a read and on a write. Pick one: solid arrows happen inside the request, dashed ones later; the numbers are the order.

"There are only two hard things in computer science: cache invalidation and naming things" is attributed to Phil Karlton ({{Martin Fowler's note|https://martinfowler.com/bliki/TwoHardThings.html}}: the attribution is by word of mouth).

The five patterns side by side (reference)
PatternOn a readOn a writeTrade-off
Cache-aside (lazy loading)App checks the cache; on a miss it reads the database and fills the cacheApp writes the database, then deletes the cache entryThe default. Simple, caches only what is read; the first read after a change is slow
Read-throughThe cache library loads missing entries from a function you give itAs cache-asideSame behaviour, less app code; the loader is one place to add coalescing (section 7)
Write-throughAs cache-asideWrite cache and database together, synchronouslyReads after writes are fresh; every write pays twice, and you cache data nobody may read
Write-behind (write-back)From the cacheWrite the cache now, flush to the database later in batchesFast writes, absorbs bursts; a cache crash loses acknowledged writes. Rarely right for user data
Write-aroundAs cache-asideWrite the database only; let the entry expireFor data written often and read rarely

Cache-aside for "load a conversation", with redis-py:

def get_chat(chat_id):
    key = f"chat:{chat_id}:v1"            # version the key so a format change cannot read old entries
    hit = r.get(key)
    if hit is not None:
        return json.loads(hit)
    chat = db_load_chat(chat_id)          # the slow path: a Postgres query
    r.set(key, json.dumps(chat), ex=300)  # TTL 300 s bounds how stale it can ever be
    return chat

def rename_chat(chat_id, title):
    db_rename_chat(chat_id, title)        # 1. write the source of truth (commit)
    r.delete(f"chat:{chat_id}:v1")        # 2. then delete, never update, the cached copy

Cache-aside is the default because the app, not the cache, decides what to fill and when to retire

Why invalidation is hard

Ada renames her chat "Trip plan" to "Trip plan v2". Postgres holds the new title; the cache still holds the old one. A cache makes a second copy of a fact, and two copies of a fact is a small distributed system. Five questions must each have an answer, and every caching bug is one left unanswered: what invalidates this entry, who knows it must happen, how the message gets there, what if it is lost or reordered, and how would you notice.

MethodHow it worksWhat it costsWhen not to use it
TTLEvery entry expires a fixed time after it was written (SET key value EX 300)Stale for up to the whole TTL even right after a change; a miss at expiry even if nothing changedAlone, for anything a user just changed and expects to see (read-your-writes)
Explicit deleteThe code that writes Postgres deletes the cache key right after the commitThe writer must know every key derived from the row; a forgotten path (an admin script, a migration) fails silently; races (below)When many caches in many services derive from one row: use events
Event-drivenPostgres's change stream (logical replication, read by a tool such as Debezium) or an outbox table feeds a consumer that deletes affected keysA pipeline to run; at-least-once delivery and lag of its own; still needs a TTLSmall systems with one writer path: explicit delete is simpler
Versioned keysThe key contains a version (chat:42:v7); a write bumps it, so readers stop asking for the old key, which ages outOne extra lookup for the current version; old entries use memory until evictedWhen the version itself cannot be read cheaply and reliably

Whatever the method, keep a TTL underneath: it is the only mechanism that also repairs the bugs of the others. Facebook runs the event-driven kind at the largest scale on record: daemons called mcsqueal read the committed SQL on every database, extract the cache deletes embedded in it and broadcast them to every cache cluster in the region; "only 4% of all deletes issued result in the actual invalidation of cached data" ({{Nishtala et al., Scaling Memcache at Facebook, NSDI 2013|https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf}}). The outbox and change data capture are taught on {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}.

Delete, do not update. Putting the new value into the cache on a write works with one writer and breaks with two: they can commit in one order and reach the cache in the other, leaving the older value cached until the TTL. Two real writers renaming the same chat, each setting the cache after its commit with a small random delay, left the cache disagreeing with Postgres in of trials measured. A delete is idempotent and order-free, which is why Facebook's write path deletes ("We choose to delete cached data instead of updating it because deletes are idempotent", same paper).

The race that delete alone does not close

The window: a slow reader fills a value it read before the writer's commit, after the writer's delete, and the old title stays cached for the whole TTL: a stale set, in Facebook's words. Trial 5 of 400: reader pause 5.87 ms, writer start 2.40 ms, timestamps as recorded by the two clients.
  1. 0.21 ms · Reader misses. It asks Redis for chat 42's title; the key is empty, so it must go to Postgres.
  2. 0.33 ms · Reader reads the OLD title. Postgres returns "Trip plan": the writer has not committed yet. Then the reader is delayed 5.87 ms (a garbage-collection pause, a busy CPU, a slow hop).
  3. 3.78 ms · Writer commits "Trip plan v2". From this instant any cached "Trip plan" is wrong.
  4. 3.94 ms · Writer deletes the key. After its commit, as cache-aside says. But the key is already empty: this delete removes nothing, and the slow reader still holds the old value.
  5. 8.52 ms · Reader fills the OLD title: a stale set. The slow reader wakes and writes the value it read before the commit. Redis says "Trip plan" while Postgres says "Trip plan v2", and will for the whole 300-second TTL.
  1. 0.48 ms · Reader misses. The key is empty.
  2. 0.99 ms · Reader takes a lease. Redis hands it token #1: only the holder of this token may fill the key, and only while it is still valid.
  3. 1.29 ms · Reader reads the OLD title. Still "Trip plan"; then the same 5.87 ms delay.
  4. 4.40 ms · Writer commits "Trip plan v2". Any cached "Trip plan" is now wrong.
  5. 4.71 ms · Writer deletes the key and the lease. One DEL removes both. The slow reader's token is now void.
  6. 8.01 ms · Fill refused. The Lua script finds the reader's lease gone and refuses the write. The key stays empty; the next reader misses and reads the new title from Postgres.
  1. 0.32 ms · Reader misses on the current version. It first reads the version counter (v0) and asks for that version's key: empty, so it goes to Postgres.
  2. 0.44 ms · Reader reads the OLD title. Then the same 5.87 ms delay.
  3. 3.95 ms · Writer commits "Trip plan v2". Any cached "Trip plan" is now wrong.
  4. 4.09 ms · Writer bumps the version. After its commit the writer increments the counter. Every reader from now on asks for v1's key, which is empty, so it reads the new title from Postgres.
  5. 9.41 ms · Reader fills an old version. The slow reader writes "Trip plan" under v0's key. Nobody asks for that key any more: harmless, and it ages out with its TTL.
  1. 0.21 ms · Reader misses. This is a different trial (the first one double delete lost): the reader will pause 93.64 ms.
  2. 0.33 ms · Reader reads the OLD title. Then the long pause begins.
  3. 10.46 ms · Writer commits "Trip plan v2". Any cached "Trip plan" is now wrong.
  4. 10.66 ms · Writer deletes the key. The key is empty; nothing is removed.
  5. 69.21 ms · Writer deletes again, 50 ms later. The second delete would remove a stale value filled in the last 50 ms. This reader is slower than that: it has not filled yet.
  6. 94.70 ms · Reader fills the OLD title anyway. Two deletes, still a stale set for the whole TTL: any reader slower than the delay wins.

Over trials per strategy, with timings forced to overlap (the reader pauses 0 to 10 ms in 90% of trials and 10 to 100 ms in 10%; the writer starts 0 to 10 ms in) measured: delete on write left stale, a lease and versioned keys 0.

The stale shares are a property of these forced timings, not a production rate: in production the window is rare per request, but a busy key gets millions of requests, and one stale set leaves a wrong value for the whole TTL. The point is the zeros.

A lease is Facebook's fix: "The lease is a 64-bit token bound to the specific key the client originally requested. The client provides the lease token when setting the value in the cache... Verification can fail if memcached has invalidated the lease token due to receiving a delete request for that item." The writer's delete revokes the slow reader's lease, so its old value is refused. The same token tames stampedes (section 7). Redis has no built-in lease, but a few lines emulate it. Costs: a second key per miss and a script call; a client that dies holding a lease blocks fills of that key until the lease expires (10 seconds here, as in the paper). When not to: keys never written while being read (static configuration), or whose staleness for one TTL is harmless.

Versioned keys need no new primitive: the writer commits, then bumps the version (after the commit, never before, so any reader that sees the new version also reads the new row); a slow reader can only fill an old version nobody reads any more. Or take the version from the database row the caller already holds (an updated_at column), as HTTP ETags do (section 9).

Delayed double delete, the folk fix, deletes after the commit and again a little later (here 50 ms), hoping the slow reader has filled by then. It narrows the window but cannot close it: any reader slower than the delay still wins, as of trials showed measured. Cheap, better than nothing, not a guarantee.

The lease and versioned-key code the measurement ran (redis-py, Lua), and the version-counter trap (depth)

One trap the measurement does not show: if the version counter itself is evicted, readers fall back to version 0 and may find an ancient entry. Give version keys no TTL under a volatile-* policy, or take the version from the database row the caller already holds (an updated_at column), which is how many HTTP caches use ETags (section 9).

tok = str(r.incr("lease:ctr"))
if not r.set("lease:" + key, tok, nx=True, px=10_000):
    time.sleep(0.005); retry()                  # someone else is filling: wait and read again
value = db.execute("SELECT title FROM chats WHERE id = %s", (42,)).fetchone()[0]
# fill only while our lease is still valid (one atomic Lua script)
FILL = r.register_script("""
  if redis.call('GET', KEYS[2]) == ARGV[1] then
    redis.call('SET', KEYS[1], ARGV[2], 'EX', 300); redis.call('DEL', KEYS[2]); return 1
  end
  return 0""")
FILL(keys=[key, "lease:" + key], args=[tok, value])
