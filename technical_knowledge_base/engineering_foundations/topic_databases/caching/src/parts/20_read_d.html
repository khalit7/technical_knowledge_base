3. Invalidation: retiring a copy that is no longer true

The problem

Throughout, the app uses cache-aside, the most common pattern: to read, ask the cache; on a miss, read Postgres and put the value in the cache; to write, update Postgres and then delete the cached key. ({{Capacity planning, The patterns|n:3ef5c17b0d0d81458291d55d7443700c}} compares it with read-through, write-through and write-back.)

Ada renames her chat "Trip plan" to "Trip plan v2". Postgres now holds the new title; the cache still holds the old one. Invalidation is whatever retires that old copy. It is hard for a reason that has nothing to do with Redis: a cache creates a second copy of a fact, and two copies of a fact is a small distributed system. Five questions must each have an answer, and every caching bug is one of them left unanswered: what invalidates this entry, who knows it must happen, how the message gets there, what if it is lost or reordered, and how would you notice. (The famous line that "there are only two hard things in computer science: cache invalidation and naming things" is attributed to Phil Karlton; {{Martin Fowler's note on it|https://martinfowler.com/bliki/TwoHardThings.html}} records the attribution, which is by word of mouth.)

Four ways to retire a copy

MethodHow it worksWhat it costsWhen not to use it
TTL (time to live)Every entry expires a fixed time after it was written (SET key value EX 300)Stale for up to the whole TTL even right after a change; a miss at expiry even if nothing changedAlone, for anything a user just changed and expects to see (read-your-writes)
Explicit deleteThe code that writes Postgres deletes the cache key right after the commitThe writer must know every key derived from the row; a forgotten path (an admin script, a migration) fails silently; races (below)When many caches derive from one row in many services: use events
Event-drivenPostgres's change stream (logical replication, read by a tool such as Debezium) or an outbox table feeds a consumer that deletes affected keysA pipeline to run; at-least-once delivery and lag of its own; still needs a TTLSmall systems with one writer path: explicit delete is simpler
Versioned keysThe key contains a version (chat:42:v7); a write bumps the version, so readers simply stop asking for the old key, which ages outOne extra lookup for the current version; old entries use memory until evictedWhen the version itself cannot be read cheaply and reliably

Facebook runs the event-driven kind at the largest scale on record: daemons called mcsqueal on every database read the committed SQL, extract the cache deletes embedded in it and broadcast them to every cache cluster in the region; they report that "only 4% of all deletes issued result in the actual invalidation of cached data" ({{Nishtala et al., Scaling Memcache at Facebook, NSDI 2013|https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf}}). The outbox and change-data-capture machinery is taught on {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}. Whatever the method, keep a TTL underneath: it is the only mechanism that also repairs the bugs of the others.

Delete, do not update

On a write you could put the new value into the cache instead of deleting the key. With one writer that works; with two it breaks, because two writers can commit to Postgres in one order and reach the cache in the other, leaving the older value cached until the TTL. Measured with two real writers renaming the same chat, each setting the cache after its commit with a small random delay: the cache disagreed with Postgres after of trials measured. A delete is idempotent (doing it twice equals doing it once) and order does not matter, which is why Facebook's write path deletes ("We choose to delete cached data instead of updating it because deletes are idempotent", same paper).

The race that delete alone does not close

Cache-aside with delete-on-write still has a hole. A reader misses, reads the old title from Postgres, and is then delayed for a few milliseconds (a garbage-collection pause, a busy CPU, a slow network hop). Meanwhile a writer commits the new title and deletes the key, which is already empty. The reader wakes up and writes the old title into the cache, where it stays until the TTL. Leases, the fix Facebook uses

A lease is a token the cache hands to a client on a miss: "you may fill this key". The paper: "The lease is a 64-bit token bound to the specific key the client originally requested. The client provides the lease token when setting the value in the cache... Verification can fail if memcached has invalidated the lease token due to receiving a delete request for that item." In the race above, the writer's delete revokes the slow reader's lease, so its old value is refused. The same token also fixes the stampede (many clients missing the same hot key at once): memcached hands out "a token only once every 10 seconds per key", and other clients are told to wait briefly and retry, by which time the first has usually filled the key. On keys prone to stampedes this cut the peak database query rate from 17,000 to 1,300 a second (Nishtala et al.). Redis has no built-in lease, but a few lines emulate it; this is the code the measurement ran:

# reader, on a miss: take the lease (fails if another client holds it)
tok = str(r.incr("lease:ctr"))
if not r.set("lease:" + key, tok, nx=True, px=10_000):
    time.sleep(0.005); retry()                  # someone else is filling: wait and read again
value = db.execute("SELECT title FROM chats WHERE id = %s", (42,)).fetchone()[0]
# fill only while our lease is still valid (one atomic Lua script)
FILL = r.register_script("""
  if redis.call('GET', KEYS[2]) == ARGV[1] then
    redis.call('SET', KEYS[1], ARGV[2], 'EX', 300); redis.call('DEL', KEYS[2]); return 1
  end
  return 0""")
FILL(keys=[key, "lease:" + key], args=[tok, value])
# writer: commit first, then delete the value AND the lease in one command
db.execute("UPDATE chats SET title = %s WHERE id = 42", (new,))      # autocommit
r.delete(key, "lease:" + key)

Costs: a second key per miss and a script call; a client that dies holding a lease blocks fills of that key until the lease expires (10 seconds here, as in the paper). When not to: keys that are never written while being read (static configuration) or whose staleness for one TTL is harmless.

Versioned keys, the fix that needs no new primitive

# writer: commit, then bump the version (after the commit, never before)
db.execute("UPDATE chats SET title = %s WHERE id = 42", (new,))
r.incr("ver:chat:42")
# reader: ask for the current version's key; a slow reader can only fill an old version nobody reads any more
v = r.get("ver:chat:42") or b"0"
key = f"chat:42:v{v.decode()}"

The ordering matters: the version is bumped after the commit, so any reader that sees the new version also reads the new row. One trap the measurement does not show: if the version counter itself is evicted, readers fall back to version 0 and may find an ancient entry. Give version keys no TTL under a volatile-* policy, or take the version from the database row the caller already holds (an updated_at column), which is how many HTTP caches use ETags (section 9).

Delayed double delete, the folk fix

Delete after the commit, then delete again a little later (here 50 ms), hoping the slow reader has filled by then. It narrows the window but cannot close it: any reader slower than the delay still wins, as of trials showed measured. It is cheap and better than nothing; it is not a guarantee.

4. Consistency: every window in which a reader sees an old value

Pros do not ask "is my cache consistent?" (it is not; it is a copy) but "in which windows can a reader see a value older than the last commit, and how long can each last?". Listing them is the whole skill. For cache-aside in front of one Postgres:

WindowHow it opensHow long it lastsFix
Between the commit and the deleteReaders between the two steps of the writer get the old cached valueMicroseconds to millisecondsAccept it: it is the minimum for any cache. If one user must see their own write, read from Postgres for that user for a few seconds
Delete before the commit (an ordering bug)The writer deletes, then commits. A reader misses in between, reads the old row (the transaction is not committed yet) and fillsThe whole TTLAlways commit first, then delete. Inside an ORM, delete in an after-commit hook, not inside the transaction
Write-through before the commitThe writer sets the cache, then the transaction fails or rolls backThe whole TTL, for a value that never existedNever write a cache inside a transaction that can still fail; delete after commit
The stale set (section 3)A slow reader fills the old value after the writer's deleteThe whole TTLLeases or versioned keys
Fill from a lagging replicaThe reader's miss goes to a read replica that has not yet received the write, and caches the old valueThe whole TTL: the cache turns milliseconds of replication lag into minutes of stalenessFill from the primary for keys just written, or mark "recently written" (Facebook's remote markers, below)
A lost or late invalidationThe delete message is dropped (a crash between commit and delete) or the event pipeline lagsUntil the TTL, or until the pipeline catches upThe TTL backstop; an outbox or change data capture makes the delete durable
Write-back (write the cache now, Postgres later)Anything that reads Postgres directly (analytics, other services) sees old data; a cache crash loses acknowledged writesUntil the flush, or foreverUse only for data you can lose or rebuild (counters); see {{Capacity planning, The patterns|n:3ef5c17b0d0d81458291d55d7443700c}}

Replicas, in Facebook's words. Their regions read from local replica databases while writes go to one master region, so a cache miss right after a write could fill from a replica that lags. Their fix, the remote marker: the writer "(1) sets a remote marker rk in the region, (2) performs the write to the master embedding k and rk to be invalidated in the SQL statement, and (3) deletes k in the local cluster"; a later miss that finds the marker reads from the master instead (Nishtala et al., "Across Regions: Consistency"). They also delete with a two-second "hold-off" when warming a cold cluster from a warm one, refusing fills for that time, for the same reason. For the chat product the simple version is enough: after a user writes, route that user's reads to the primary for a few seconds (read-your-writes), which is taught on {{Scaling a database|n:3ef5c17b0d0d81f0aaceee1e21b972be}}.

The rule that ties it together
A cache is an optimisation: the system must stay correct with it empty. If deleting every key would lose data or break behaviour, it is not a cache but a database with no durability, and it needs the treatment of one (the {{NoSQL in practice|n:3ef5c17b0d0d81ec8456c41e4e8f5f6b}} page measured how many acknowledged writes a Redis failover loses).
