The idea in one screen

A cache is a second, faster copy of data, and it pays because traffic is skewed: a copy of the popular few absorbs most reads. Everything hard follows from it being a copy: it can go stale (invalidation), it cannot hold everything (eviction), its misses still cost (weigh each hit by the miss it avoids), and one kind, the semantic cache, can hand back a wrong answer.

One chat request passes up to nine copies; the further out, the bigger the saving and the harder to invalidate

The chat product of Topic: databases: a request asks each copy in turn, outermost first, and the source of truth (Postgres, then the SSD) answers only when every copy misses. Hit times are from the ladder in section 2 (measured on the laptop or sourced there). The web copies are exact; the LLM lane's prompt and KV caches are exact too, and only the semantic cache (section 12) answers a question with another question's answer. Sections 3 and 4 are about the copies you must invalidate yourself, 5 about what a full one throws away, 6 about what each hit is worth.

You need: SQL and a primary key (SQL and data modelling), what a commit is (Transactions and concurrency). Running example: the root's chat product, its 10-million-message Postgres database, a Redis in front of it and an LLM behind it. measured: recorded for this page on a laptop (Apple M1 Pro, 16 GB) on 5 October 2026; a laptop has no network between client and server, so its timings are best cases, while hit ratios and counts carry over to production. illustrative: an input made up to show a shape.

1. Why caches work: a few things get most of the requests

A cache only helps if requests repeat. Locality is the name for that: temporal (used now, likely used again soon: a user's open conversation is re-read on every message) and spatial (stored together, used together: why hardware fetches 64-byte lines and Postgres 8 KB pages). Application caches live on the first kind plus skew: a small set of items far more popular than the rest. The chat product has no public access log, so this page uses the largest public one: one hour of English Wikipedia (15 September 2026, 12:00 to 13:00 UTC, desktop and mobile summed by title), 7,869,547 views of 1,683,268 distinct pages (Wikimedia pageviews) measured.

One per cent of the pages got a third of the views

Pages sorted from most to least viewed. A cache that could hold exactly the most popular pages, under requests drawn independently from these counts, would hit on the share of views those pages get: that is the first view. Computed in measure/m_skew.py.

The top 0.1% of pages (about 1,683) got 17% of views, the top 1% 34%, the top 10% 65%. And 933,584 pages (55%) were viewed exactly once: no cache helps with those, because the first request for anything is a miss (a compulsory miss).

On log scales, views against rank fall near a straight line: views ≈ C / rankα, a Zipf distribution. Fitted on ranks 10 to 100,000, this hour gives α = 0.73; the larger α, the more the top dominates (at α = 1 the first item is twice as popular as the second and ten times the tenth). Web caches have been measured near this shape for decades: Breslau et al. found α "ranging from 0.64 to 0.83" across the web proxy traces they studied (INFOCOM 1999), which is why the Cache lab offers Zipf workloads at α 0.7, 0.9 and 1.1 beside the real trace.

Popularity drifts, slowly. Over six consecutive hours (06:00 to 12:00 UTC), 85% of each hour's 10,000 most viewed pages stayed in the next hour's top 10,000 measured. That drift separates eviction policies: pure frequency counting keeps yesterday's news; pure recency forgets steady favourites (measured in section 5). For the chat product: each user's own conversation list is hot only while that user is active, so a TTL of minutes fits it; shared things (the model list, feature flags, a popular shared prompt) are hot forever and need invalidation instead.

How the request trace was built from hourly counts (provenance)

The hourly file has no timestamps inside the hour, so the 2,000,000-request replay used in section 5 draws requests without replacement from the hour's views in random order. That keeps the skew exactly and removes any ordering inside the hour; the six-hour trace keeps the hour-to-hour drift. Both are real popularity, not a synthetic distribution.

2. The layers: from the CPU to the browser

Read the ladder top to bottom as "where could this answer already be?". Each step down is roughly ten to a hundred times slower than the one above, which is the whole argument for caching.

The ladder as a table: what each layer holds, who invalidates it, and the source of each time (reference)

Four things change as you move outward:

  • Who invalidates. Hardware keeps CPU caches correct (a coherence protocol called MESI makes cores agree on each 64-byte line); the kernel keeps the page cache correct; Postgres keeps its buffer pool correct (it is the only copy writers change). From the application cache outward, you invalidate, with fewer tools the further out: you can delete a Redis key, ask a CDN to purge (a request that must reach every edge city), but you cannot reach into a browser at all.
  • Who shares it. A browser cache is one user's; a CDN is everyone's, so a personalised response cached at the edge leaks to other users unless it is marked private (section 9).
  • What a miss costs. An L1 miss costs nanoseconds; a CDN miss crosses an ocean. A layer's value is what it saves per hit times how often it hits (section 6).
  • How many copies: the local against distributed choice, next.

Local against distributed

In-process (local)

A dict, functools.lru_cache, cachetools.TTLCache, Caffeine in Java. A hit costs 11.3 ns in Python here measured: no network, no serialisation. But it exists once per process: 8 servers with 4 workers each hold 32 independent copies, each warming, missing and going stale on its own, and 32 places to invalidate.

Shared (distributed)

Redis, Valkey, Memcached: one hop away (0.060 ms on loopback here, plus a network round trip of about 0.5 ms inside a cloud region), one copy for every server, one place to delete. It is a service to run, and a slow cache must degrade into misses, not stall requests (client timeouts of tens of milliseconds).

The usual design is both: a shared cache for everything worth caching, and an in-process cache in front of it only for a few very hot keys (feature flags, the model list) with a TTL of seconds, which bounds how long the 32 copies can disagree and spares the Redis shard that owns a hot key.

Before adding Redis in front of Postgres, check that the working set fits in the database server's RAM: two caches you do not configure, the operating system's page cache and Postgres's buffer pool, already hold hot pages, and a database whose hot pages stay in memory answers a primary-key lookup in well under a millisecond.

The page cache and the buffer pool, measured (depth)

The page cache is the operating system keeping recently read file blocks in otherwise free RAM: an 8 KiB read of a cached block took 0.94 microseconds here, against about 100 microseconds from an NVMe SSD. The buffer pool (Postgres's shared_buffers) is the database's own page cache, on top of the operating system's, so a page can be cached twice ("double buffering"). Both are taught with measurements on Storage engines and indexes, section 2; this page measures only the buffer pool across a restart (section 8).

3. Patterns and invalidation: who fills the copy, and who retires it

The patterns: who reads and writes the cache

Five patterns differ only in who talks to whom on a read and on a write. Pick one: solid arrows happen inside the request, dashed ones later; the numbers are the order.

Cache-aside is the default because the app, not the cache, decides what to fill and when to retire

"There are only two hard things in computer science: cache invalidation and naming things" is attributed to Phil Karlton (Martin Fowler's note: the attribution is by word of mouth).

Why invalidation is hard

Ada renames her chat "Trip plan" to "Trip plan v2". Postgres holds the new title; the cache still holds the old one. A cache makes a second copy of a fact, and two copies of a fact is a small distributed system. Five questions must each have an answer, and every caching bug is one left unanswered: what invalidates this entry, who knows it must happen, how the message gets there, what if it is lost or reordered, and how would you notice.

Whatever the method, keep a TTL underneath: it is the only mechanism that also repairs the bugs of the others. Facebook runs the event-driven kind at the largest scale on record: daemons called mcsqueal read the committed SQL on every database, extract the cache deletes embedded in it and broadcast them to every cache cluster in the region; "only 4% of all deletes issued result in the actual invalidation of cached data" (Nishtala et al., Scaling Memcache at Facebook, NSDI 2013). The outbox and change data capture are taught on Queues, streams and async work.

Delete, do not update. Putting the new value into the cache on a write works with one writer and breaks with two: they can commit in one order and reach the cache in the other, leaving the older value cached until the TTL. Two real writers renaming the same chat, each setting the cache after its commit with a small random delay, left the cache disagreeing with Postgres in 36% of 400 trials measured. A delete is idempotent and order-free, which is why Facebook's write path deletes ("We choose to delete cached data instead of updating it because deletes are idempotent", same paper).

The race that delete alone does not close

A reader misses, reads the old title from Postgres, and is delayed a few milliseconds (a garbage-collection pause, a busy CPU, a slow hop). Meanwhile a writer commits the new title and deletes the key, which is already empty. The reader wakes and writes the old title into the cache, where it stays for the whole TTL: a stale set, in Facebook's words. Predict before you step: which of the four strategies can still lose? A delete cannot revoke a fill already on its way; a lease or a version can

Over 400 trials per strategy, with timings forced to overlap (the reader pauses 0 to 10 ms in 90% of trials and 10 to 100 ms in 10%; the writer starts 0 to 10 ms in) measured: delete on write left 227 stale, a lease and versioned keys 0.

The stale shares are a property of these forced timings, not a production rate: in production the window is rare per request, but a busy key gets millions of requests, and one stale set leaves a wrong value for the whole TTL. The point is the zeros.

A lease is Facebook's fix: "The lease is a 64-bit token bound to the specific key the client originally requested. The client provides the lease token when setting the value in the cache... Verification can fail if memcached has invalidated the lease token due to receiving a delete request for that item." The writer's delete revokes the slow reader's lease, so its old value is refused. The same token tames stampedes (section 7). Redis has no built-in lease, but a few lines emulate it. Costs: a second key per miss and a script call; a client that dies holding a lease blocks fills of that key until the lease expires (10 seconds here, as in the paper). When not to: keys never written while being read (static configuration), or whose staleness for one TTL is harmless.

Versioned keys need no new primitive: the writer commits, then bumps the version (after the commit, never before, so any reader that sees the new version also reads the new row); a slow reader can only fill an old version nobody reads any more. Or take the version from the database row the caller already holds (an updated_at column), as HTTP ETags do (section 9).

Delayed double delete, the folk fix, deletes after the commit and again a little later (here 50 ms), hoping the slow reader has filled by then. It narrows the window but cannot close it: any reader slower than the delay still wins, as 30 of 400 trials showed measured. Cheap, better than nothing, not a guarantee.

The lease and versioned-key code the measurement ran (redis-py, Lua), and the version-counter trap (depth)

One trap the measurement does not show: if the version counter itself is evicted, readers fall back to version 0 and may find an ancient entry. Give version keys no TTL under a volatile-* policy, or take the version from the database row the caller already holds (an updated_at column), which is how many HTTP caches use ETags (section 9).

4. Consistency: every window in which a reader sees an old value

The useful question is not "is my cache consistent?" (it is a copy, so no) but "in which windows can a reader see a value older than the last commit, and how long can each last?". For cache-aside in front of one Postgres:

For the chat product the simple version of the replica fix is enough: after a user writes, route that user's reads to the primary for a few seconds (read-your-writes, taught on Scaling a database; consistency models in full on Distributed systems fundamentals).

Facebook's remote markers and hold-off, in their words (depth)

Facebook's regions read from local replica databases while writes go to one master region, so a cache miss right after a write could fill from a replica that lags. Their fix, the remote marker: the writer "(1) sets a remote marker rk in the region, (2) performs the write to the master embedding k and rk to be invalidated in the SQL statement, and (3) deletes k in the local cluster"; a later miss that finds the marker reads from the master instead (Nishtala et al., "Across Regions: Consistency"). They also delete with a two-second "hold-off" when warming a cold cluster from a warm one, refusing fills for that time, for the same reason.

The rule that ties it together
A cache is an optimisation: the system must stay correct with it empty. If deleting every key would lose data or break behaviour, it is not a cache but a database with no durability, and it needs the treatment of one (the NoSQL in practice page measured how many acknowledged writes a Redis failover loses).

5. Redis as a cache: what it throws away when memory is full, measured

A cache is smaller than the data behind it, so when it is full something must go: the eviction policy picks the victim. LRU evicts the entry used longest ago (cheap, good for most workloads); LFU the one used least often, with counts that decay (better when a few keys are steadily popular and a scan of one-off keys would flush them out of an LRU); TinyLFU is an admission policy: a newcomer only gets in if a compact frequency sketch says it is read more often than the entry it would evict (Einziger, Friedman and Manes, ACM ToS 2017; Caffeine, the standard Java cache, uses W-TinyLFU, "a small admission LRU that evicts to a large Segmented LRU if accepted by the TinyLfu admission policy", Caffeine wiki).

Two settings, and the default that bites

maxmemory caps the memory Redis uses for data; maxmemory-policy chooses the victim. Out of the box, maxmemory is 0 (no limit on 64-bit systems, so Redis grows until the machine runs out of memory) and the policy is noeviction: "The default is: maxmemory-policy noeviction" (redis.conf, 8.8). With a limit and that policy, a full Redis returns an error on every write that needs memory. For a cache, set both:

# redis.conf for a pure cache (Redis 8.8). Leave room for replication and persistence buffers,
# which are not counted in maxmemory (Redis key eviction docs).
maxmemory 6gb
maxmemory-policy allkeys-lfu        # or allkeys-lru; see the measurements below
maxmemory-samples 5                 # default; 10 is closer to exact at more CPU
save ""                             # a cache usually needs no snapshots: it can be refilled
appendonly no

Memory per key is more than the value. One cache-aside key with a 100-byte value cost 159 bytes here measured (key, hash-table entry and allocator overhead), and a TTL adds more: size maxmemory from the measured cost of your own keys, not from the values.

None of the policies is exact (Redis samples keys), and a volatile-* policy with no TTLs set behaves like noeviction, the classic 3 a.m. outage measured below.

How Redis approximates LRU and LFU, and the volatile-* trap (depth)

None of the policies is exact. Exact LRU would need a linked list updated on every read; Redis instead "samples a small number of keys at random and then evicts the ones with the longest time since last access", keeping a small pool of good candidates between evictions (Redis key eviction). LFU keeps 8 bits per key (a Morris counter: incremented with a probability that falls as it grows, so 255 can stand for about a million hits at the default lfu-log-factor 10) combined "with a decay period so that the counter is reduced over time" (lfu-decay-time 1: one minute). And a volatile-* policy with no TTLs set "behave[s] like noeviction" (docs): the classic 3 a.m. outage, measured below.

    6. What a hit is worth: hit-rate arithmetic and the cost of a miss

    With λ reads a second and hit ratio h, the database sees (1 − h) × λ. So going from 90% to 99% hits looks like a 9-point gain but divides the database's read load by ten (1,000 reads a second become 100, then 10). Mean latency is h × tcache + (1 − h) × (tcache + tdb). Predict: at the defaults the database is comfortable; what happens to it if the cache restarts empty? Then drag.

    The database is sized for the misses, so an empty cache sends it more than it can take

    Demand 1,000 reads a second against a database that answers about 600 (illustrative, the system design root's Step 2 example); tcache = 0.060 ms (Redis GET) and tdb = 10.8 ms (the usage aggregate below), both measured here on loopback. Formulas checked in recompute.py.

    Three consequences. The tail is the miss path: at a 95% hit rate the p99 is a database read however fast the cache is, so a cache improves the median far more than the p99. The cache has become capacity: when it empties (a restart, a failover, a deploy that changes every key) the full load lands on a database sized for a fraction of it; Facebook keeps spare "Gutter" servers, about 1% of the memcached fleet, to take a failed server's keys rather than let its misses reach the databases (Nishtala et al.). Warm up before taking traffic: fill a new cache from the old one, or ramp traffic (section 8 measures the same cold start inside Postgres). The queueing behind "more than it can take" is on Capacity planning and performance.

    Not every miss costs the same

    A miss on "chat 42 by its id" costs Postgres 0.189 ms; a miss on "this user's token usage by model" costs 10.8 ms (medians over random keys on the root's 10-million-message database, client round trips over a local connection) measured; a Redis GET took 0.060 ms on the same machine. Caching the first saves almost nothing (a Redis round trip costs about as much as the query); caching the second saves 182 times the cost of the lookup. A cache that hits 95% of cheap requests and misses every expensive one has a beautiful hit ratio and saves the database almost nothing. So count work saved:

A cost-aware policy does.     7. TTLs, jitter and stampedes: when a popular copy expires

    Choosing a TTL. A TTL is the staleness you accept, stated in seconds: the bound on how long a forgotten invalidation can last and on how long an un-invalidated copy can lie. Short TTLs cost misses; long ones cost staleness. Per-user data that is hot only during a session fits minutes; shared reference data that is invalidated explicitly can carry hours, with the TTL as the backstop.

    Jitter. Entries written together with the same TTL expire together: a deploy that refills 10,000 hot keys in the same second sends their next reads to the database in the same second, 300 s later. Adding a random extra 0 to j% to each TTL spreads those expiries over 300 × j seconds. Drag the jitter:

    Ten per cent of jitter turns one spike of 10,000 expiries into a plateau the database can absorb

    10,000 keys filled at t = 0, TTL 300 s plus a uniform random 0 to j% illustrative. Peak expiries per second = keys / (300 × j), derived; each becomes a database query on its key's next read. The 600 a second line is the same illustrative database as in section 6. TTL jitter is common advice (a random 0 to 10%), not from a single source.

    Stampedes. A stampede (dog-piling, a thundering herd) is one hot key expiring: every request that arrives before someone has rebuilt it misses and rebuilds it too. If the rebuild takes 300 ms and the key is read 200 times a second, 60 requests run the same expensive query at once, which makes the query slower, which widens the window. Facebook measured it: "Without leases, all of the cache misses resulted in a peak database query rate of 17K/s. With leases, the peak database query rate was 1.3K/s" (Nishtala et al.). Predict: which defence sends the database one query and makes no request wait?

    The model (ported from Capacity planning and performance's model.py, stampede, plus a serve-stale mode): one key read 200 times a second, expiring at t = 1 s, rebuilt by a 300 ms database query; XFetch with β = 1 and Δ = 300 ms on a seeded random draw (seed 5) illustrative rates.     1. Request coalescing (single-flight): the first miss rebuilds; the others wait for its answer (Go's singleflight, nginx's proxy_cache_lock on; Facebook's leases across servers, "a token only once every 10 seconds per key"). Cost: the waiters still wait for the rebuild.
    2. Serve stale while revalidating: keep the old value a little past its TTL and refresh in the background (Cache-Control: stale-while-revalidate=30, RFC 5861). Cost: a few seconds of staleness.
    3. Probabilistic early expiry (XFetch): each reader recomputes early with a probability that rises as expiry approaches and as the rebuild gets more expensive: recompute if now − Δ · β · ln(rand()) ≥ expiry, Δ the last rebuild's duration (Vattani, Chierichetti and Lowenstein, VLDB 2015, proved optimal; β = 1 "already provides effective prevention against cache stampedes"). Cost: one early rebuild per expiry and no locks; only the reader that refreshes waits.

    8. Postgres's own caches: pages yes, results no, and three tools in between

    Postgres caches pages (the buffer pool over the operating system's page cache: Storage engines and indexes, section 2), query plans for prepared statements, and catalog data. It does not cache query results: run the same aggregate twice and it is computed twice, from cached pages. MySQL had a query result cache and removed it in 8.0, because invalidating every cached result that touched a table on every write to it scaled badly under concurrency (MySQL Server blog, 2017). Before reaching for Redis, three tools inside the database.

    A materialised view, for expensive aggregates

    A materialised view is a query whose result Postgres stores as a real table, with its own indexes. A view of daily token usage per user and model on the root's chat data (10 million messages) measured:

    CREATE MATERIALIZED VIEW daily_usage AS
  SELECT c.user_id, m.created_at::date AS day, m.model, sum(m.tokens) AS tokens, count(*) AS n
  FROM messages m JOIN chats c ON c.id = m.chat_id GROUP BY 1, 2, 3;
CREATE UNIQUE INDEX daily_usage_key ON daily_usage(user_id, day, model);   -- needed for CONCURRENTLY

    The catch is the one this page keeps returning to: the view is a copy. After a new message was inserted, the view still showed user 1's old total (2,414,930 tokens against 2,415,707 in the live tables) until REFRESH MATERIALIZED VIEW recomputed it from scratch in 14.8 s. A plain refresh takes a lock that blocks readers: a query on the view issued one second into the refresh waited 13,809 ms. REFRESH MATERIALIZED VIEW CONCURRENTLY builds the new result beside the old one and applies the difference, "without locking out concurrent selects" (Postgres docs); it needs a unique index, took 90.3 s, and the same reader waited only 3.9 ms.

    When to use it: dashboards and reports that tolerate staleness you can state ("usage as of the last 10-minute refresh"), refreshed by a scheduler (cron, pg_cron).

    When not, and what to use instead (depth)

    When not: data a user expects to see change immediately, or a base table so large that a full recompute every few minutes costs more than it saves; then maintain a summary table incrementally (a trigger or the application adds each new message to its day's row), or use a system that maintains views incrementally (ClickHouse materialised views run on every insert; Materialize is built around it). Postgres itself has no incremental materialised views.

    pg_prewarm, for the cold start after a restart

    A restart empties shared_buffers, so the database is slowest exactly when traffic returns; measured here, the first lookups after a restart read their blocks at SSD speed, and pg_prewarm (or its autoprewarm worker) made them run at the warm speed from the first request. The same holds for a restarted Redis.

    A restart empties shared_buffers, and on a real server, whose OS page cache a reboot also empties, every first miss is an SSD read: the database is slowest exactly when traffic returns. pg_prewarm loads a table or index into the buffer pool on demand, and with shared_preload_libraries = 'pg_prewarm' a background worker "periodically records the contents of shared buffers in a file called autoprewarm.blocks and will, using 2 background workers, reload those same blocks after a restart" (pg_prewarm docs). 20,000 random chat lookups after a restart measured:

    Memoize, a cache inside one query, measured (depth)

    Since Postgres 14 the planner can put a Memoize node above the inner side of a nested-loop join: when the same lookup value comes back (many messages of the same chat), the cached inner result is reused instead of probing the index again; "less commonly looked up results may be evicted" when its memory (work_mem times hash_mem_multiplier) fills (enable_memoize).     9. HTTP caching and CDNs: the copies outside your servers

    Every HTTP response can say who may cache it and for how long, and browsers, reverse proxies (nginx, Varnish, Envoy) and CDNs obey the same headers (RFC 9111; MDN's HTTP caching guide is the readable version; header semantics are owned by HTTP). A CDN is a cache run for you in hundreds of cities: it serves static files and any public response marked cacheable, and its hit ratio is what you pay for, because every miss crosses the world to your servers (about 20 ms to an edge against 78 ms across the Atlantic on the ladder of section 2). CDNs collapse concurrent misses for the same URL into one request to you (the coalescing of section 7) and support stale-while-revalidate and stale-if-error. A reverse proxy in your own data centre can also be told to drop entries (Varnish has purging and banning); it spares the app servers on anonymous traffic and helps little once every response is personalised.     10. The LLM caches, first: the KV cache and prefix caching

    An LLM product has three caches a web product does not, and they differ in the property that matters most: can a hit return a wrong answer? The KV cache and prompt caching never change the answer; a semantic cache can.

    A transformer generates one token (a word piece) at a time, and every layer's attention needs a key and a value vector for each earlier token; servers keep those in GPU memory instead of recomputing them: the KV cache. It is never stale (the keys and values of a given prefix under a given model are fixed); its problem is size, which is why KV memory, not compute, usually caps how many conversations one GPU serves. Because attention is causal, two requests that start with the same tokens share those keys and values, so a server can keep them and skip that part of the prefill (the first pass over the prompt, which dominates time to first token): prefix caching, exact by construction. How big the cache is (bytes per token from a model's config, Llama 3.1 70B's 320 KiB per token, why decode is memory-bound) is taught from zero in sections 4 and 2 of Topic: inference-and-serving; how vLLM's hashed blocks (design doc) and SGLang's RadixAttention (LMSYS blog, January 2024) find a shared prefix, and which blocks to evict on a day of real traffic, in section 3 of Batching, KV cache and scheduling in depth, which replays the policies on a real trace.

    What a cache engineer takes from it: prefix caching dictates prompt layout. Stable content first (system prompt, tool definitions, documents), anything that changes per request last; one timestamp at the top of a system prompt makes every request a miss. ML system design animates one conversation under both layouts (section 6 there) and lists an LLM service's four caches (section 7); routing requests to the replica that holds their prefix is measured on real replicas in LLM serving in production, section 1.

    Owned elsewhere and linked: PagedAttention, KV quantisation (FP8 KV halves the bytes per token), offloading cold prefixes to CPU memory or SSD (LMCache, Mooncake, NVIDIA Dynamo) and cache-aware routing (Topic: inference-and-serving and its child Batching, KV cache and scheduling, sections 2 to 4); architectures that shrink the entry itself, such as DeepSeek-V3's multi-head latent attention, one 576-number vector per layer (68.6 KiB per token), on the DeepSeek page.

    11. Provider prompt caching: the same idea, sold by the token

    When you call a hosted model, the provider runs prefix caching for you and passes on part of the saving: input tokens read from its cache are billed at a fraction of the normal price, and the answer never changes. It is an ordinary cache with two twists. It lives on individual machines, so a hit needs the request to reach the machine holding the prefix: OpenAI's guide says cached states "live on individual machines, where traffic above 15 requests per minute can lead to overflow routing", and on models before GPT-5.6 a stable prompt_cache_key "helps optimize cache routing" for requests sharing a prefix (busy groups should "aim for about 15 requests per minute in total" per key and split higher volume across keys). It is scoped: "Caches are not shared across organizations" (OpenAI prompt caching, read 2026-10-05), which also closes the timing side channel a shared prefix cache would open.

    The rules that decide whether a request hits (Anthropic's tools, system, messages order and what invalidates each level, breakpoints and the 20-block lookback, minimum lengths, lifetimes, the usage fields that report a hit, and OpenAI's and Gemini's versions) are owned by Context engineering, section 2; Anthropic's prices and what caching does to a Claude agent's bill by the Anthropic provider page. This section keeps the arithmetic that holds for every provider.

    Break-even: does caching pay?

    With a write multiplier w (what writing a prefix costs, relative to sending it normally) and a read multiplier r, a prefix used n times costs w + r(n − 1) with caching against n without. Caching pays once

    n > 1 + (w − 1) / (1 − r)

    12. Semantic caching: the only cache that can be wrong

    An exact cache matches keys byte for byte, which almost never fires on natural language: "What is your refund policy?" and "How do refunds work?" are the same question in different bytes. A semantic cache turns each incoming prompt into an embedding (a vector of a few hundred numbers from a small model, such that texts with similar meaning point in similar directions), finds the most similar stored prompt, and returns its stored answer if the cosine similarity (the cosine of the angle between the two vectors; 1 means the same direction) is above a threshold; otherwise it calls the model and stores the new pair. GPTCache made the design popular (repository; its README warns "you may encounter false positives during cache hits"); LiteLLM ships it as a proxy option (type: "redis-semantic" with similarity_threshold: 0.8, LiteLLM docs); Redis sells it as a service (LangCache, Redis, spring 2025 release). Every other cache on this page is exact, so a hit is provably the right answer; a semantic hit is a guess that two different questions deserve the same answer. That makes it a model-quality change disguised as an infrastructure change. Where it sits in an LLM gateway, beside exact response caching, is on Gateways and routing; this section owns how often it is wrong.

    How to run one safely, if you must

    It works best on high-volume, low-variance, factual traffic (FAQ-style support questions, documentation lookups, classification prompts) and badly on open-ended generation, agent steps, or anything where users expect a fresh answer.

    1. Try the exact caches first: prompt caching (section 11), an exact-match cache on the normalised request (tenant, model, full prompt, temperature, tools), caching retrieval results and embeddings of repeated documents.
    2. Scope the key: tenant, user where answers are personal, model and prompt version, and the retrieved context. "What is my balance?" from two users is the same text with different answers, and a cache shared across tenants can hand one customer another's answer. Never cache answers that depend on live state (stock, balances, order status) or on time ("current pricing").
    3. Verify before serving: require extracted entities, numbers and dates to match exactly; or re-rank the top few candidates with a cross-encoder or a small judge model instead of trusting one cosine score.
    4. Measure your own curve: a few thousand real queries with a no-cache baseline, replayed through the cache, judged; plus a deliberate slice of near-miss pairs from your domain, which the natural distribution under-represents.
    5. In production: log the similarity of every hit, audit a sample of hits, alert on the false-hit rate as a service level objective, and keep a kill switch. When the knowledge behind the answers changes, version the cache namespace (a reindex invalidates everything at once) or tag entries with the documents they came from.

    Choosing: which cache, in which order

    For the chat product, from cheapest and safest to riskiest; each step is worth doing before the next.

    1. Make the database fast without a cache. Indexes, fewer queries per request (no N+1), enough RAM for the working set (Query planning and performance). A missing index is not a caching problem, and every cache you do not add is an invalidation bug you do not have.
    2. Cache what never changes, far out. Static assets with content-hashed names and a year-long max-age on a CDN (section 9).
    3. Use provider prompt caching, always. Put the stable prompt first, check the cached-token fields, and remember that one reuse already pays (section 11). In your own serving stack, prefix caching is on by default in vLLM and SGLang (section 10).
    4. Add a shared cache for expensive, read-heavy, shared results: Redis or Valkey with maxmemory and maxmemory-policy set on purpose (allkeys-lfu or allkeys-lru), the hit ratio watched next to the eviction count; a TTL on everything that states the staleness you accept, in seconds, even where explicit invalidation exists; delete after the commit, never before, and never update the cache on write; leases or versioned keys where a stale value would hurt (sections 3 to 5). Weigh by cost: skip cheap primary-key lookups (section 6). Jitter TTLs and coalesce rebuilds of hot keys (section 7).
    5. Precompute heavy aggregates in a materialised view or a summary table instead of caching each answer (section 8).
    6. An in-process cache in front of the shared one only for a few very hot keys, with a short TTL (section 2).
    7. A semantic cache last, and only after an evaluation on your traffic, scoped per tenant and user, with its false-hit rate monitored (section 12).

    Throughout: the system must stay correct with the cache empty, and the database must survive the load of a cold cache (warm it, or ramp traffic: sections 6 and 8).

    What teams run in production (October 2026) (reference)
    • Python services: redis-py (8.x) or valkey-py clients with connection pools and timeouts of tens of milliseconds, so a slow cache degrades into misses rather than stalling requests; cachetools (TTLCache) for in-process caches; TTL jitter (a random extra 0 to 10%) so keys written together do not expire together.
    • Java services: Caffeine (W-TinyLFU) in process, Redis or Memcached behind it.
    • Managed: Amazon ElastiCache (Valkey, Redis OSS or Memcached), Google Memorystore; replicas for availability, not for correctness.
    • Invalidation at scale: deletes driven by the database's change stream (Debezium reading Postgres logical replication, or an outbox), Facebook-style, with TTLs underneath.
    • LLM products: prompt layout reviewed like an API (stable prefix, append-only history), cache-hit rate and cached-token cost on the main dashboard, exact-match caching of deterministic calls, semantic caching rarely and narrowly.

    Common mistakes

    Each is a real failure mode; the measured ones were run on this page.

    Caching to hide a slow query
    The miss path stays slow, the p99 is the miss path, and a cold cache brings the whole load back. Fix the query or the index first.
    Deleting the cache key before the commit
    A reader between the delete and the commit refills the old row for the whole TTL. Commit, then delete (in an after-commit hook if you use an ORM).
    Updating the cache on write instead of deleting
    Two writers can land in the cache in the opposite order from the database. Measured: 36% of trials ended wrong.
    No TTL because "we invalidate explicitly"
    Some path will forget (a script, a migration, a new service). The TTL is the upper bound on how long that bug lasts.
    Leaving Redis at its defaults
    maxmemory 0 grows until the machine swaps or the process is killed; with a limit, noeviction turns a full cache into write errors (measured: 781,318 failed SETs in one run).
    A volatile-* policy with keys that have no TTL
    Nothing is eligible, so it behaves like noeviction: measured, 1,328,877 failed SETs, against 0 once every key had a TTL.
    Choosing allkeys-lrm for a read-through cache
    LRM only notices writes, and cache-aside writes a key once, when it is filled; so LRM evicts by fill time, like FIFO, ignoring how often the key is read. Measured, it did no better than random eviction.
    Letting requests for missing keys through every time
    A key that does not exist in the database is never cached, so every request for it reaches the database (cache penetration, often a bot probing ids). Cache the "not found" answer with a short TTL, or keep a Bloom filter of keys that exist.
    One hot key on one shard
    A cluster spreads keys, not load: one celebrity chat or one shared prompt key lives on one Redis primary, which saturates while the rest idle. Put the few hottest keys in an in-process cache in front, or copy one key under several names (key:0 to key:7) and read a random copy, which multiplies the writes. Find them first: redis-cli --hotkeys (it needs an LFU policy).
    Reading the hit ratio alone
    Weight hits by what the miss costs (section 6), and watch evictions, expiries and latency on the miss path.
    Filling the cache from a replica right after a write
    Milliseconds of replication lag become a TTL of staleness. Fill from the primary for keys just written, or route the writer's reads to the primary briefly.
    Caching personalised responses in a shared cache
    A CDN or reverse proxy serves user A's page to user B. Mark them Cache-Control: private, and put user and tenant in every application cache key that depends on them.
    A timestamp at the top of the prompt
    Every request differs from the first token, so provider prompt caching never hits and the bill does not fall. Volatile content goes last.
    Copying a semantic-cache threshold
    Measured here, the same 0.90 meant 6% false hits with one model and 11% with another. Fit it on your own labelled traffic.
    Benchmarking with a warm cache and quoting the result as typical
    Report cold and warm runs separately, and say which; the root's Query plans tab shows the difference on real plans.
