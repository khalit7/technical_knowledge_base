Caching: every layer, eviction, invalidation, and the LLM caches

Caching taught from zero on the chat product: why a small cache catches most traffic, every layer from the CPU to the browser, how a cached copy goes stale and the mechanisms that stop it, Redis as a cache measured under real traffic, Postgres's own caches, HTTP caching, and the three caches of an LLM product (the KV cache, provider prompt caching, semantic caching). Everything measured here was run for real on a laptop (Redis 8.8, PostgreSQL 16.2, two sentence-embedding models) on real data (an hour of Wikipedia traffic, Quora and PAWS question pairs). Results marked measured were recorded for this page on a laptop (Apple M1 Pro, 16 GB) on 5 October 2026; anything marked illustrative is made up to show a shape. A laptop has no network between client and server, so its timings are best cases; hit ratios and counts carry over to production.

A cache is a second, faster copy of data whose real home (the source of truth, for us Postgres) is slower or more expensive to ask. A request the cache can answer is a hit; one it cannot is a miss, which goes to the source and usually leaves a copy behind. The share of requests that hit is the hit ratio. Most cached entries carry a TTL (time to live): an expiry time after which the cache drops them by itself. Everything hard about caching follows from one fact: a copy can disagree with the original, and the cache cannot hold everything, so it must decide what to keep.

Five habits of a professional
  1. Fix the query before caching it. A missing index is not a caching problem (the Query planning and performance page).
  2. State the staleness you accept, in seconds, for every cached thing, and make a TTL enforce it even when explicit invalidation exists.
  3. Delete after the commit, never before, and never update the cache on write; use leases or versioned keys where a stale value would hurt.
  4. Configure eviction on purpose: maxmemory and maxmemory-policy set, the hit ratio watched next to the eviction count.
  5. The system must stay correct with the cache empty, and the database must survive the load of a cold cache (warm it, or ramp traffic).

1. Why caches work: a few things get most of the requests

The problem

The chat product's database can answer a few thousand small queries a second. If every page view asked it again for the same popular answer, most of that capacity would be spent recomputing things it computed a moment ago. A cache only helps if requests repeat: if every request were for a different item, a cache would hold copies nobody asks for again.

Two kinds of repetition

Locality is the name for requests repeating. Temporal locality: something used now is likely to be used again soon (a user's open conversation is re-read on every message). Spatial locality: things stored next to each other are used together (the next bytes of an array, the next rows of a page), which is why hardware caches fetch whole 64-byte lines and Postgres whole 8 KB pages. Application caches mostly live on the first kind, plus skew: a small set of items is far more popular than the rest.

Measured: one hour of real traffic

The chat product has no public access log, so this page uses the largest public one: Wikimedia publishes the number of views of every page, every hour. The hour of 15 September 2026, 12:00 to 13:00 UTC, English Wikipedia (desktop and mobile summed by title), has views of distinct pages (Wikimedia pageviews) measured.

Popularity drifts, slowly

Skew alone says which items are popular over the hour, not whether the popular set changes. Six consecutive hours of the same data (06:00 to 12:00 UTC) answer that: from one hour to the next, of the 10,000 most viewed pages stayed in the top 10,000 measured. That drift is what separates eviction policies: a policy that remembers old popularity forever (pure frequency counting) keeps yesterday's news; one that only remembers recency forgets steady favourites. Section 5 measures both on these traces.

What this means for the chat product
Its traffic has the same two shapes. Each user's own conversation list and open chat are re-read on every message (temporal locality, private to the user), while a few things are shared by everyone and read constantly (the model list, feature flags, a popular shared prompt). Per-user data caches well only while that user is active, so a TTL of minutes fits it; shared data caches well forever and needs invalidation instead.

How this trace was built: the hourly file has no timestamps inside the hour, so the 2,000,000-request replay used in section 5 draws requests without replacement from the hour's views in random order. That keeps the skew exactly and removes any ordering inside the hour; the six-hour trace keeps the hour-to-hour drift. Both are real popularity, not a synthetic distribution.

2. The layers: from the CPU to the browser

When a user opens a conversation, the request passes through up to nine caches, and each one exists because the thing behind it is slower. Read the ladder top to bottom as "where could this answer already be?". Every step down the list is between about ten and a hundred times slower than the one above it, which is the whole argument for caching.

Log scale: each grid line is ten times the one before. Sources per bar in the table below; measured bars were timed for this page or for the system design root's Numbers to know on the same laptop.

Four things change as you move outward, and they explain most design decisions:

  • Who invalidates. Hardware keeps CPU caches correct by itself (a coherence protocol called MESI makes cores agree on each 64-byte line). The kernel keeps the page cache correct; Postgres keeps its buffer pool correct (it is the only copy writers change). From the application cache outward, you must invalidate, and the further out, the fewer tools you have: you can delete a Redis key, ask a CDN to purge (a request that must reach every edge city), but you cannot reach into a browser at all.
  • How many copies. One Redis serves every app server. An in-process cache (a Python dict, functools.lru_cache) exists once per process: 8 servers with 4 workers each hold 32 independent copies, each warming and going stale on its own.
  • Who shares it. A browser cache is one user's; a CDN is everyone's, so a personalised response cached at the edge leaks to other users unless it is marked private (section 9).
  • What a miss costs. An L1 miss costs nanoseconds; a CDN miss crosses an ocean to your servers. The value of a layer is how much it saves per hit, times how often it hits (section 6).
The two caches you do not configure but must understand
The page cache is the operating system keeping recently read file blocks in otherwise free RAM: an 8 KiB read of a cached block took microseconds here, against about 100 microseconds from an NVMe SSD. The buffer pool (Postgres's shared_buffers) is the database's own page cache, on top of the operating system's, so a page can be cached twice ("double buffering"). Both are taught with measurements on Storage engines and indexes, section 2; this page measures only what happens to the buffer pool across a restart (section 8). A practical rule from both: before adding Redis in front of Postgres, check that the working set fits in the database server's RAM; a database whose hot pages stay in memory answers a primary-key lookup in well under a millisecond.

3. Invalidation: retiring a copy that is no longer true

The problem

Throughout, the app uses cache-aside, the most common pattern: to read, ask the cache; on a miss, read Postgres and put the value in the cache; to write, update Postgres and then delete the cached key. (Capacity planning, The patterns compares it with read-through, write-through and write-back.)

Ada renames her chat "Trip plan" to "Trip plan v2". Postgres now holds the new title; the cache still holds the old one. Invalidation is whatever retires that old copy. It is hard for a reason that has nothing to do with Redis: a cache creates a second copy of a fact, and two copies of a fact is a small distributed system. Five questions must each have an answer, and every caching bug is one of them left unanswered: what invalidates this entry, who knows it must happen, how the message gets there, what if it is lost or reordered, and how would you notice. (The famous line that "there are only two hard things in computer science: cache invalidation and naming things" is attributed to Phil Karlton; Martin Fowler's note on it records the attribution, which is by word of mouth.)

Four ways to retire a copy

MethodHow it worksWhat it costsWhen not to use it

Facebook runs the event-driven kind at the largest scale on record: daemons called mcsqueal on every database read the committed SQL, extract the cache deletes embedded in it and broadcast them to every cache cluster in the region; they report that "only 4% of all deletes issued result in the actual invalidation of cached data" (Nishtala et al., Scaling Memcache at Facebook, NSDI 2013). The outbox and change-data-capture machinery is taught on Queues, streams and async work. Whatever the method, keep a TTL underneath: it is the only mechanism that also repairs the bugs of the others.

Delete, do not update

On a write you could put the new value into the cache instead of deleting the key. With one writer that works; with two it breaks, because two writers can commit to Postgres in one order and reach the cache in the other, leaving the older value cached until the TTL. Measured with two real writers renaming the same chat, each setting the cache after its commit with a small random delay: the cache disagreed with Postgres after of trials measured. A delete is idempotent (doing it twice equals doing it once) and order does not matter, which is why Facebook's write path deletes ("We choose to delete cached data instead of updating it because deletes are idempotent", same paper).

The race that delete alone does not close

Cache-aside with delete-on-write still has a hole. A reader misses, reads the old title from Postgres, and is then delayed for a few milliseconds (a garbage-collection pause, a busy CPU, a slow network hop). Meanwhile a writer commits the new title and deletes the key, which is already empty. The reader wakes up and writes the old title into the cache, where it stays until the TTL. Facebook calls this a stale set. The animation replays real trials: two Python clients against the local Postgres 16.2 and Redis 8.8, timestamps as recorded. The same trial number has the same delays under every strategy, so you are watching the same race with and without the fix.

The stale shares are a property of these forced timings, not a production rate: in production the window is rare per request, but a busy key gets millions of requests, and one stale set leaves a wrong value for the whole TTL. The point is the zeros.

Leases, the fix Facebook uses

A lease is a token the cache hands to a client on a miss: "you may fill this key". The paper: "The lease is a 64-bit token bound to the specific key the client originally requested. The client provides the lease token when setting the value in the cache... Verification can fail if memcached has invalidated the lease token due to receiving a delete request for that item." In the race above, the writer's delete revokes the slow reader's lease, so its old value is refused. The same token also fixes the stampede (many clients missing the same hot key at once): memcached hands out "a token only once every 10 seconds per key", and other clients are told to wait briefly and retry, by which time the first has usually filled the key. On keys prone to stampedes this cut the peak database query rate from 17,000 to 1,300 a second (Nishtala et al.). Redis has no built-in lease, but a few lines emulate it; this is the code the measurement ran:

# reader, on a miss: take the lease (fails if another client holds it)
tok = str(r.incr("lease:ctr"))
if not r.set("lease:" + key, tok, nx=True, px=10_000):
    time.sleep(0.005); retry()                  # someone else is filling: wait and read again
value = db.execute("SELECT title FROM chats WHERE id = %s", (42,)).fetchone()[0]
# fill only while our lease is still valid (one atomic Lua script)
FILL = r.register_script("""
  if redis.call('GET', KEYS[2]) == ARGV[1] then
    redis.call('SET', KEYS[1], ARGV[2], 'EX', 300); redis.call('DEL', KEYS[2]); return 1
  end
  return 0""")
FILL(keys=[key, "lease:" + key], args=[tok, value])
# writer: commit first, then delete the value AND the lease in one command
db.execute("UPDATE chats SET title = %s WHERE id = 42", (new,))      # autocommit
r.delete(key, "lease:" + key)

Costs: a second key per miss and a script call; a client that dies holding a lease blocks fills of that key until the lease expires (10 seconds here, as in the paper). When not to: keys that are never written while being read (static configuration) or whose staleness for one TTL is harmless.

Versioned keys, the fix that needs no new primitive

# writer: commit, then bump the version (after the commit, never before)
db.execute("UPDATE chats SET title = %s WHERE id = 42", (new,))
r.incr("ver:chat:42")
# reader: ask for the current version's key; a slow reader can only fill an old version nobody reads any more
v = r.get("ver:chat:42") or b"0"
key = f"chat:42:v{v.decode()}"

The ordering matters: the version is bumped after the commit, so any reader that sees the new version also reads the new row. One trap the measurement does not show: if the version counter itself is evicted, readers fall back to version 0 and may find an ancient entry. Give version keys no TTL under a volatile-* policy, or take the version from the database row the caller already holds (an updated_at column), which is how many HTTP caches use ETags (section 9).

Delayed double delete, the folk fix

Delete after the commit, then delete again a little later (here 50 ms), hoping the slow reader has filled by then. It narrows the window but cannot close it: any reader slower than the delay still wins, as of trials showed measured. It is cheap and better than nothing; it is not a guarantee.

4. Consistency: every window in which a reader sees an old value

Pros do not ask "is my cache consistent?" (it is not; it is a copy) but "in which windows can a reader see a value older than the last commit, and how long can each last?". Listing them is the whole skill. For cache-aside in front of one Postgres:

WindowHow it opensHow long it lastsFix
Between the commit and the deleteReaders between the two steps of the writer get the old cached valueMicroseconds to millisecondsAccept it: it is the minimum for any cache. If one user must see their own write, read from Postgres for that user for a few seconds

Write-through before the commitThe writer sets the cache, then the transaction fails or rolls backThe whole TTL, for a value that never existedNever write a cache inside a transaction that can still fail; delete after commit
The stale set (section 3)A slow reader fills the old value after the writer's deleteThe whole TTLLeases or versioned keys
Fill from a lagging replicaThe reader's miss goes to a read replica that has not yet received the write, and caches the old valueThe whole TTL: the cache turns milliseconds of replication lag into minutes of stalenessFill from the primary for keys just written, or mark "recently written" (Facebook's remote markers, below)
A lost or late invalidationThe delete message is dropped (a crash between commit and delete) or the event pipeline lagsUntil the TTL, or until the pipeline catches upThe TTL backstop; an outbox or change data capture makes the delete durable
Write-back (write the cache now, Postgres later)Anything that reads Postgres directly (analytics, other services) sees old data; a cache crash loses acknowledged writesUntil the flush, or foreverUse only for data you can lose or rebuild (counters); see Capacity planning, The patterns

Replicas, in Facebook's words. Their regions read from local replica databases while writes go to one master region, so a cache miss right after a write could fill from a replica that lags. Their fix, the remote marker: the writer "(1) sets a remote marker rk in the region, (2) performs the write to the master embedding k and rk to be invalidated in the SQL statement, and (3) deletes k in the local cluster"; a later miss that finds the marker reads from the master instead (Nishtala et al., "Across Regions: Consistency"). They also delete with a two-second "hold-off" when warming a cold cluster from a warm one, refusing fills for that time, for the same reason. For the chat product the simple version is enough: after a user writes, route that user's reads to the primary for a few seconds (read-your-writes), which is taught on Scaling a database.

The rule that ties it together
A cache is an optimisation: the system must stay correct with it empty. If deleting every key would lose data or break behaviour, it is not a cache but a database with no durability, and it needs the treatment of one (the NoSQL in practice page measured how many acknowledged writes a Redis failover loses).

5. Redis as a cache: what it throws away when memory is full, measured

The problem

A cache is always smaller than the data behind it, so when it is full and a new value arrives, something must go. Choosing the victim is the eviction policy. The concepts (LRU evicts the entry used longest ago; LFU the one used least often; TinyLFU only admits a newcomer that looks more popular than the victim) are taught on Capacity planning, Eviction. This section is about the real thing: Redis's settings, what each one actually does, and how they compare on real traffic.

Two settings, and the default that bites

maxmemory caps the memory Redis uses for data; maxmemory-policy chooses the victim. Out of the box, maxmemory is 0 (no limit on 64-bit systems, so Redis grows until the machine runs out of memory) and the policy is noeviction: "The default is: maxmemory-policy noeviction" (redis.conf, 8.8). With a limit and that policy, a full Redis returns an error on every write that needs memory. For a cache, set both, explicitly:

# redis.conf for a pure cache (Redis 8.8). Leave room for replication and persistence buffers,
# which are not counted in maxmemory (Redis key eviction docs).
maxmemory 6gb
maxmemory-policy allkeys-lfu        # or allkeys-lru; see the measurements below
maxmemory-samples 5                 # default; 10 is closer to exact at more CPU
save ""                             # a cache usually needs no snapshots: it can be refilled
appendonly no

None of them is exact. Exact LRU would need a linked list updated on every read; Redis instead "samples a small number of keys at random and then evicts the ones with the longest time since last access", keeping a small pool of good candidates between evictions (docs). LFU keeps a frequency estimate of 8 bits per key (a Morris counter: incremented with a probability that falls as it grows, so 255 can stand for about a million hits at the default lfu-log-factor 10) combined "with a decay period so that the counter is reduced over time" (lfu-decay-time 1: one minute). And a volatile-* policy with no TTLs set "behave[s] like noeviction" (docs): the classic 3 a.m. outage, measured below.

    6. Cost-weighted hit ratio: counting the work saved, not the requests

    The problem

    The hit ratio treats every request alike. But a miss on "chat 42 by its id" costs Postgres ms, while a miss on "this user's token usage by model" costs ms (medians over random keys, measured on the root's 10-million-message database, client round trips over a local connection) measured; a Redis GET took ms on the same machine. Caching the first kind saves almost nothing (a Redis round trip costs about as much as the query); caching the second saves times the cost of the lookup. A cache that hits 95% of cheap requests and misses every expensive one has a beautiful hit ratio and saves the database almost nothing.

    The measure

    CWHR = Σhits cost(miss avoided) / Σall requests cost(miss)
    cost
    what a miss on that request would cost: backend milliseconds, database CPU, or dollars
    CWHR
    the share of backend work the cache removed; equal to the hit ratio only when every miss costs the same

    In the Redis runs of section 5, one key in ten was marked expensive at random (independent of popularity), so the cost-weighted hit ratio equals the plain one up to noise: no Redis policy knows what a miss costs. A cost-aware policy does. GreedyDual (Young 1994; with sizes, Cao and Irani, USENIX 1997) gives each entry a priority of "L + the cost of missing it"; the victim is the lowest priority, and L rises to each victim's priority, so cheap entries leave first and expensive ones leave only when they stop being used.     The trade is visible: GreedyDual gives up some plain hits to keep the expensive keys, and the work saved goes up. Redis has no such policy, so production systems get the same effect by hand:

    • Separate pools. Facebook partitions memcached into pools: "a small pool for keys that are accessed frequently but for which a cache miss is inexpensive", and "a large pool for infrequently accessed keys for which cache misses are prohibitively expensive" (Nishtala et al.). In Redis terms: two instances (or two logical caches with their own memory), so cheap churn cannot evict expensive results.
    • Longer TTLs for expensive results, or caching only results whose measured cost is above a threshold (do not cache a 0.07 ms lookup at all).
    • Precompute the expensive ones (a materialised view, section 8), which turns the expensive miss into a cheap one.

    What to put on the dashboard (Redis exposes the first three in INFO stats): hits and misses (keyspace_hits, keyspace_misses); evicted_keys next to expired_keys (many evictions: memory too small or wrong policy; many expiries: TTL too short); latency split by hit and miss, since the tail of the request latency is the miss path; database load with and without the cache; and the number of distinct keys, whose unbounded growth means a timestamp or request id got into a key. For an LLM cache the cost has an exact money form, section 11.

Most new systems pick Redis or Valkey; managed services (Amazon ElastiCache, Google Memorystore) offer both.

    8. Postgres's own caches: pages yes, results no, and three tools in between

    What Postgres caches by itself

    Postgres caches pages (the buffer pool, plus the operating system's page cache under it: Storage engines and indexes, section 2), query plans for prepared statements, and catalog data. It does not cache query results: run the same aggregate twice and it is computed twice, from cached pages. MySQL had a query result cache and removed it in 8.0, because invalidating every cached result that touched a table on every write to it scaled badly under concurrency (MySQL Server blog, 2017). Result caching is left to you, with three tools inside the database before you reach for Redis.

    Tool 1: a materialised view, for expensive aggregates

    A materialised view is a query whose result Postgres stores as a real table, with its own indexes. Measured on the root's chat data (10 million messages) measured: a view of daily token usage per user and model,

    CREATE MATERIALIZED VIEW daily_usage AS
  SELECT c.user_id, m.created_at::date AS day, m.model, sum(m.tokens) AS tokens, count(*) AS n
  FROM messages m JOIN chats c ON c.id = m.chat_id GROUP BY 1, 2, 3;
CREATE UNIQUE INDEX daily_usage_key ON daily_usage(user_id, day, model);   -- needed for CONCURRENTLY

    The catch is the one this page keeps returning to: the view is a copy. After a new message was inserted, the view still showed user 1's old total ( tokens against in the live tables) until REFRESH MATERIALIZED VIEW recomputed it from scratch in s. And a plain refresh takes a lock that blocks readers: a query on the view issued one second into the refresh waited ms. REFRESH MATERIALIZED VIEW CONCURRENTLY builds the new result beside the old one and applies the difference, "without locking out concurrent selects" (Postgres docs); it needs a unique index, took s, and the same reader waited only ms.

    When to use it: dashboards and reports that tolerate staleness you can state ("usage as of the last 10-minute refresh"), refreshed by a scheduler (cron, pg_cron). When not: data a user expects to see change immediately, or a base table so large that a full recompute every few minutes costs more than it saves; then maintain a summary table incrementally (a trigger or the application adds each new message to its day's row), or use a system that maintains views incrementally (ClickHouse materialised views run on every insert; Materialize is built around it). Postgres itself has no incremental materialised views.

    Tool 2: Memoize, a cache inside one query

    Since Postgres 14 the planner can put a Memoize node above the inner side of a nested-loop join: when the same lookup value comes back (many messages of the same chat), the cached inner result is reused instead of probing the index again; "less commonly looked up results may be evicted" when its memory (work_mem times hash_mem_multiplier) fills (enable_memoize). Measured on a query that looks up the owner of every chat belonging to the 30 heaviest users (6,250 chats, 30 distinct owners) measured:

    SELECT u.plan, count(*) FROM chats c JOIN users u ON u.id = c.user_id WHERE c.user_id <= 30 GROUP BY 1;

    Two lessons. When it runs, the cache works as designed: 30 index probes instead of 6,250. And the planner did not choose it: it built a hash table of all 100,000 users instead, times slower here, because its cost model did not foresee that so few owners repeat so often. You cannot request Memoize directly; recognising it (and its absence) in an EXPLAIN plan is the skill, taught on Query planning and performance, and the usual fix for a misestimate is better statistics, not switching join methods off in production (done here only to show the node).

    Tool 3: pg_prewarm, for the cold start after a restart

    A restart empties shared_buffers. The first requests afterwards all miss in the buffer pool, and on a real server, whose OS page cache a reboot also empties, every one of those misses is an SSD read: the database is slowest exactly when traffic returns. The pg_prewarm extension loads a table or index into the buffer pool on demand, and with shared_preload_libraries = 'pg_prewarm' a background worker "periodically records the contents of shared buffers in a file called autoprewarm.blocks and will, using 2 background workers, reload those same blocks after a restart" (pg_prewarm docs). random chat lookups after a restart measured:

    Postgres's I/O timing (track_io_timing = on) shows where the first pass lost its time: blocks read in ms, about microseconds each, which is SSD speed: those blocks were in neither cache. After pg_prewarm or an autoprewarm restart, the same lookups ran at the warm speed from the first request. The same holds for Redis: a restarted cache is empty, and the database must survive the miss rate until it refills (Facebook's cold clusters fill from a warm cluster first, "in a few hours instead of a few days").

    9. HTTP caching, briefly: the headers that control browsers and CDNs

    Every HTTP response can say who may cache it and for how long. Browsers, reverse proxies (nginx, Varnish, Envoy) and CDNs obey the same headers (a reverse proxy in your own data centre can also be told to drop entries: Varnish has purging and banning; it spares the app servers on anonymous traffic and helps little once every response is personalised), defined in RFC 9111; MDN's HTTP caching guide is the readable version; the protocols themselves belong to Topic: protocols. For the chat product:

    The public model listCache-Control: public, max-age=60, stale-while-revalidate=300Fresh for 60 s; for 5 minutes after that a cache may serve the old copy while it fetches a new one in the background (RFC 5861)

    Three mistakes cause most HTTP caching incidents: a personalised response cached by a shared cache because it lacked private (one user sees another's page); a cache key that ignores a header the response depends on (fix with Vary, for example Vary: Accept-Encoding); and a long max-age on a URL whose content changes, which no purge can recall from browsers. An ETag is a versioned key by another name: the server's version of the resource, compared on each request.

    10. The LLM caches, first: the KV cache inside the model server

    An LLM product has three caches that a web product does not, and they differ in the one property that matters most: can a hit return a wrong answer? The KV cache and prompt caching never change the answer; a semantic cache can.

    What it stores, and why it exists

    A transformer generates text one token (a word piece) at a time. To produce the next token, every layer's attention compares it with all earlier tokens, using two vectors per earlier token per layer: a key (what the token offers) and a value (what it contributes). Those vectors never change once computed, so servers keep them in GPU memory instead of recomputing them for every new token: the KV cache. Without it, generating token n would redo the work for all n − 1 earlier tokens. It is not optional, and it is never stale: the keys and values of a given prefix under a given model are fixed. Its problem is size.

    bytes per token = 2 × layers × KV heads × head dimension × bytes per number
    2
    one key and one value
    KV heads
    with grouped-query attention (GQA) several query heads share one key/value head, so this is usually 8, not the full head count
    bytes
    2 for 16-bit numbers (BF16), 1 for FP8

    The Llama 3.1 70B row reproduces the old page's 320 KiB per token independently from the model's config.json (80 layers, 8 KV heads, head dimension 8,192 / 64 = 128): one 128K-token conversation holds 40 GiB, more than half of an 80 GB H100 before any weights. That is why KV memory, not compute, usually caps how many conversations one GPU serves at once. It also makes generation memory-bound: every new token reads the weights and that conversation's whole KV cache from GPU memory, and batching shares the weight reads across conversations but never the KV reads, since each conversation has its own. Hence new architectures attack it: DeepSeek-V3's multi-head latent attention stores one compressed 576-number vector per layer (68.6 KiB per token), and DeepSeek reports 890 bytes per token for V4.1-Flash (both worked through on the DeepSeek page).

    Reusing it across requests: prefix caching

    Because attention is causal (token i only looks at tokens 0 to i), two requests that start with the same tokens have identical keys and values for that shared start. A server can keep them and skip recomputing that part of the prompt (prefill, the first pass over the prompt that dominates time to first token). This is prefix caching, and it is exact: a hit returns precisely what recomputing would.

    • vLLM splits the cache into fixed-size blocks and gives each full block a hash of its tokens and its parent block's hash, so a block hash names the whole prefix up to it; a new request looks its blocks up in order and reuses every hit. A block shared by several requests is stored once and reference-counted. Freed blocks wait in an LRU queue and are evicted from its head when memory is needed (vLLM design: automatic prefix caching). The docs call it "almost a free lunch" that "won't change model outputs". The block allocator underneath is PagedAttention (paper page).
    • SGLang's RadixAttention keeps prompts and generations in a radix tree (a prefix tree whose edges hold runs of tokens), evicts least recently used leaves, and schedules requests that share prefixes together to raise the hit rate (LMSYS blog, January 2024).

    Prefix caching dictates prompt layout: stable content first (system prompt, tool definitions, documents), anything that changes per request last. One timestamp at the top of a system prompt makes every request a miss. The ML system design page animates one conversation under both layouts (section 9 there), and routing requests to the replica that holds their prefix is section 4 there.

    Go deeper (optional): PagedAttention, KV quantisation (FP8 KV halves the bytes per token), offloading cold prefixes to CPU memory or SSD (LMCache, Mooncake, NVIDIA Dynamo), and cache-aware routing belong to Topic: inference-and-serving.

    11. Provider prompt caching: the same idea, sold by the token

    When you call a hosted model, the provider runs prefix caching for you and passes on part of the saving: input tokens read from its cache are billed at a fraction of the normal price. It never changes the answer. What differs between providers is whether you opt in, whether writing the cache costs extra, the minimum length, and how long an entry lives. As of 5 October 2026, from each provider's documentation:

    Break-even: does caching pay?

    With a write multiplier w (what writing a prefix costs, relative to sending it normally) and a read multiplier r, a prefix used n times costs w + r(n − 1) with caching against n without. Caching pays once

    n > 1 + (w − 1) / (1 − r)
    Correction to the old page
    The old page said Anthropic's caching breaks even at "roughly 1.3 reads inside the TTL". With w = 1.25 and r = 0.1 the break-even is n = 1 + 0.25 / 0.9 = 1.28 total uses: one write plus a single read (2 uses: 1.35 against 2.00) already saves 32.5%. OpenAI's own guide gives the same arithmetic: "writing a prefix once and fully reusing it once costs 1.35× its ordinary input cost, compared with 2×" (OpenAI prompt caching). The old page also said OpenAI has no write surcharge: true for models before GPT-5.6, but GPT-5.6 and later charge 1.25× for writes. And the read multiplier is no longer 0.1× everywhere: Anthropic bills reads at 0.05× on Claude Opus 5.5 and 0.025× on Fable 5.1 and Mythos 5.1; OpenAI at 0.05× on GPT-6.1 Sol.

    Input cost of the cached prefix only (the uncached suffix and the output cost the same either way). Gemini explicit caching adds a storage charge per million tokens per hour, shown for one hour. Prices from the table above; formula checked in recompute.py.

    What breaks a cache hit

    • Any change before the cached point. The cache is a prefix: Anthropic's docs list what invalidates which level ("tools → system → messages"): changing tool definitions invalidates everything; toggling web search or citations, or the speed setting, invalidates the system prompt and messages; images, tool choice, thinking or effort settings invalidate messages (Anthropic prompt caching). A timestamp, a request id or a shuffled tool list early in the prompt does the same.
    • Too short. Below the minimum (512 to 4,096 tokens on Anthropic depending on the model, 1,024 on OpenAI's GPT-5.6 and later, 2,048 to 4,096 on Gemini) nothing is cached and no error is returned.
    • Too long a gap. An entry lives 5 minutes on Anthropic (refreshed on each use, 1 hour at a 2× write), at least 30 minutes on OpenAI's newest models, and as long as you pay for on Gemini's explicit caches (default 1 hour).
    • Anthropic's 20-block lookback. A read looks back at most 20 content blocks from your breakpoint for an earlier entry; a conversation that grows by 20 or more blocks between writes misses unless you add a second breakpoint.
    • The wrong machine. Provider caches live on individual machines: OpenAI notes that "traffic above 15 requests per minute can lead to overflow routing" for one prefix; a stable prompt_cache_key helps routing on its older models.
    • Parallel first requests. An entry exists only after the first response begins (Anthropic), so ten requests sent at once with a new prefix all pay full price; send one first.

    Verify, never assume: every response reports what it read from cache (cache_read_input_tokens and cache_creation_input_tokens on Anthropic, usage.input_tokens_details.cached_tokens on OpenAI, the usage_metadata field on Gemini (usage.total_cached_tokens in its Interactions API)). The cost-weighted hit ratio of section 6 has an exact form here: the share of the input bill removed is h × (1 − r), less the write premium, so 90% of input tokens read from cache at 0.1× removes 0.9 × 0.9 = 81% of the input bill before writes.

    12. Semantic caching: the only cache that can be wrong

    The idea

    An ordinary cache matches keys byte for byte, which almost never fires on natural language: "What is your refund policy?" and "How do refunds work?" are the same question with different bytes. A semantic cache turns each incoming prompt into an embedding (a vector of a few hundred numbers produced by a small model, such that texts with similar meaning get vectors pointing in similar directions), finds the most similar stored prompt, and returns that prompt's stored answer if the cosine similarity (the cosine of the angle between the two vectors: 1 means the same direction) is above a threshold. Otherwise it calls the model and stores the new pair. GPTCache made the design popular (repository); LiteLLM ships it as a proxy option (docs); Redis sells it as a service (LangCache, Redis, spring 2025 release).

    Every other cache on this page is exact, so a hit is provably the right answer. A semantic hit is a guess that two different questions deserve the same answer, and the threshold trades money saved against wrong answers served. That makes it a model-quality change disguised as an infrastructure change.

    Measured: hit rate against wrong answers as the threshold moves

    Two real labelled datasets and two small open embedding models, run on the laptop's CPU measured:

    • Quora Question Pairs (the GLUE validation split: pairs of real user questions, labelled duplicates by people; dataset). The non-duplicates are hard on purpose: pairs on the same topic with different answers, exactly the near misses a cache must refuse.
    • PAWS ( pairs built by swapping or copying words, so almost every pair shares nearly all its words; are paraphrases; dataset).
    • Models: all-MiniLM-L6-v2 (22.7 million parameters, ms to embed one query on two CPU threads) and BAAI bge-small-en-v1.5 (33.4 million, ms).

    For each pair the cache holds the first question and the second arrives as a query: it is served from cache if their similarity is at least the threshold, and that is right only for a duplicate. The true-hit rate is the share of duplicates served; the false-hit rate is the share of non-duplicates served.

    A real cache looks up the nearest of many entries

    The pair view gives each query one candidate. A real cache compares the query against everything stored. With the first questions of 10,000 Quora pairs stored and each second question looked up against all of them (MiniLM, threshold 0.90), of queries were served from cache: by their own labelled duplicate (right), by their own labelled non-duplicate (wrong), and by a different stored question with no label. Read by eye, most of those high-similarity "other" matches are genuinely the same question asked twice on Quora (the dataset repeats popular questions), so the labelled numbers understate the hit rate a little, and the wrong-answer share remains.

    What published measurements say

    AWS's test on chatbot queries (Claude 3 Haiku answers, Titan embeddings), as reported by Portkey (Portkey, semantic caching thresholds): threshold 0.99, 23.5% hits at 92.1% accuracy; 0.95, 56.0% at 92.6%; 0.90, 74.5% at 92.3%; 0.80, 87.6% at 91.8%; 0.75, 90.3% at 91.2%. On that traffic accuracy barely moved, the opposite of the hard pairs above: the curve is a property of your traffic and your model, which is the whole lesson. Portkey's advice is to start between 0.90 and 0.95, build a validation set with "queries that look similar but should produce different answers", and treat a false-positive rate above roughly 3 to 5% as the limit of the embedding model, not of the threshold. Research systems learn the threshold instead of fixing it: vCache learns one per cached prompt and reports "up to 12.5× higher cache hit and 26× lower error rates" than a static threshold (arXiv 2502.03771).

    How to run one safely, if you must

    It works best on high-volume, low-variance, factual traffic (FAQ-style support questions, documentation lookups, classification prompts) and badly on open-ended generation, agent steps, or anything where users expect a fresh answer.

    1. Try the exact caches first: prompt caching (section 11), an exact-match cache on the normalised request (model, full prompt, temperature, tools), caching retrieval results and embeddings of repeated documents.
    2. Scope the key: tenant, user where answers are personal, model and prompt version, and the retrieved context. "What is my balance?" from two users is the same text with different answers. Never cache answers that depend on live state (stock, balances, order status) or on time ("current pricing").
    3. Verify before serving: require extracted entities, numbers and dates to match exactly; or re-rank the top few candidates with a cross-encoder or a small judge model instead of trusting one cosine score.
    4. Measure your own curve: a few thousand real queries with a no-cache baseline, replayed through the cache, judged; plus a deliberate slice of near-miss pairs from your domain, which the natural distribution under-represents.
    5. In production: log the similarity of every hit, audit a sample of hits, alert on the false-hit rate as a service level objective, and keep a kill switch. When the knowledge behind the answers changes, version the cache namespace (a reindex invalidates everything at once) or tag entries with the documents they came from.

    Choosing: which cache, in which order

    For the chat product, from cheapest and safest to riskiest. Each step is worth doing before the next.

    1. Make the database fast without a cache. Indexes, fewer queries per request (no N+1), and enough RAM for the working set. Every cache you do not add is an invalidation bug you do not have.
    2. Cache what never changes, far out. Static assets with content-hashed names and a year-long max-age on a CDN (section 9).
    3. Use provider prompt caching, always. Put the stable prompt first, check the cached-token fields, and remember that one reuse already pays (section 11). In your own serving stack, prefix caching is on by default in vLLM and SGLang (section 10).
    4. Add a shared cache for expensive, read-heavy, shared results: Redis or Valkey with allkeys-lfu or allkeys-lru, a maxmemory, TTLs on everything, delete after commit, and leases or versioned keys where staleness hurts (sections 3 to 5). Weigh by cost: skip cheap primary-key lookups (section 6).
    5. Precompute heavy aggregates in a materialised view or a summary table instead of caching each answer (section 8).
    6. An in-process cache in front of the shared one only for a few very hot keys (feature flags, the model list), with a short TTL: it removes the network hop and protects the Redis shard that owns a hot key.
    7. A semantic cache last, and only after an evaluation on your traffic, scoped per tenant and user, with its false-hit rate monitored (section 12).

    What pros run in production today

    • Python services: redis-py (8.x) or valkey-py clients with connection pools and timeouts of tens of milliseconds, so a slow cache degrades into misses rather than stalling requests; cachetools (TTLCache) for in-process caches; TTL jitter (a random extra 0 to 10%) so keys written together do not expire together.
    • Java services: Caffeine (W-TinyLFU) in process, Redis or Memcached behind it.
    • Managed: Amazon ElastiCache (Valkey, Redis OSS or Memcached), Google Memorystore; replicas for availability, not for correctness.
    • Invalidation at scale: deletes driven by the database's change stream (Debezium reading Postgres logical replication, or an outbox), Facebook-style, with TTLs underneath.
    • LLM products: prompt layout reviewed like an API (stable prefix, append-only history), cache-hit rate and cached-token cost on the main dashboard, exact-match caching of deterministic calls, semantic caching rarely and narrowly.

    Common mistakes

    Caching to hide a slow query
    The miss path stays slow, the p99 is the miss path, and a cold cache brings the whole load back. Fix the query or the index first.
    Deleting the cache key before the commit
    A reader between the delete and the commit refills the old row for the whole TTL. Commit, then delete (in an after-commit hook if you use an ORM).
    Updating the cache on write instead of deleting
    Two writers can land in the cache in the opposite order from the database. Measured: of trials ended wrong.
    No TTL because "we invalidate explicitly"
    Some path will forget (a script, a migration, a new service). The TTL is the upper bound on how long that bug lasts.
    Leaving Redis at its defaults
    maxmemory 0 grows until the machine swaps or the process is killed; with a limit, noeviction turns a full cache into write errors (measured: failed SETs in one run).
    A volatile-* policy with keys that have no TTL
    Nothing is eligible, so it behaves like noeviction: measured, failed SETs, against once every key had a TTL.
    Choosing allkeys-lrm for a read-through cache
    LRM only notices writes, and cache-aside writes a key once, when it is filled; so LRM evicts by fill time, like FIFO, ignoring how often the key is read. Measured, it did no better than random eviction.
    Letting requests for missing keys through every time
    A key that does not exist in the database is never cached, so every request for it reaches the database (cache penetration, often a bot probing ids). Cache the "not found" answer with a short TTL, or keep a Bloom filter of keys that exist.
    One hot key on one shard
    A cluster spreads keys, not load: one celebrity chat or one shared prompt key lives on one Redis primary, which saturates while the rest idle. Put the few hottest keys in an in-process cache in front, or copy one key under several names (key:0 to key:7) and read a random copy, which multiplies the writes. Find them first: redis-cli --hotkeys (it needs an LFU policy).
    Reading the hit ratio alone
    Weight hits by what the miss costs (section 6), and watch evictions, expiries and latency on the miss path.
    Filling the cache from a replica right after a write
    Milliseconds of replication lag become a TTL of staleness. Fill from the primary for keys just written, or route the writer's reads to the primary briefly.
    Caching personalised responses in a shared cache
    A CDN or reverse proxy serves user A's page to user B. Mark them Cache-Control: private, and put user and tenant in every application cache key that depends on them.
    A timestamp at the top of the prompt
    Every request differs from the first token, so provider prompt caching never hits and the bill does not fall. Volatile content goes last.
    Copying a semantic-cache threshold
    Measured here, the same 0.90 meant false hits with one model and with another. Fit it on your own labelled traffic.
    Benchmarking with a warm cache and quoting the result as typical
    Report cold and warm runs separately, and say which; the root's Query plans tab shows the difference on real plans.
