SQL says what you want, never how to get it. A part of the database called the planner chooses the how, by guessing how much work each possible recipe would take. Most slow queries are a bad guess, a missing index, or an application that asks the database the wrong way; a four-step routine finds which.

The running example is the chat product from the parent page, Topic: databases: 100,000 users, 1,000,000 chats and 10,000,000 messages in one PostgreSQL ("Postgres") database of about 4 GB, generated by the parent's scripts so every number agrees with its Query plans tab. That tab already shows eight measured cases (sequential against index scan, column order in an index, functions that hide a column, the three join algorithms, a misestimate fixed by extended statistics, Postgres against DuckDB, index-only scans and VACUUM, cold against warm cache). This page does not repeat them; it explains the machinery underneath and the routine around it, and adds one table of billing events for section 10.

1. What a planner does

When the app sends SELECT * FROM messages WHERE chat_id = 42 ORDER BY created_at, nothing in that sentence says which file to open, whether to use an index, or in what order to do things. SQL is declarative: it describes the result. Turning that description into steps is the job of a chain of components, the same in every relational database and documented for Postgres in The Path of a Query:

ParseCheck the grammar and build a tree of the statement.
AnalyseLook up every name: which table is messages, which type is chat_id.
RewriteReplace views by the queries that define them and apply rules.
PlanEnumerate ways to run it, estimate the cost of each, keep the cheapest.
ExecuteRun the chosen plan and stream rows back.

Step 4 is the planner (also called the optimizer). Its output, the plan, is a tree of nodes. The leaves read data: a Seq Scan (sequential scan) reads every page of a table in order; an Index Scan walks an index and fetches the matching rows; a Bitmap Heap Scan first collects matching row addresses from an index and then reads their pages in physical order; an Index Only Scan answers from the index without touching the table. Nodes above the leaves combine rows: the three join algorithms (nested loop, hash join, merge join, compared on real data in the parent's Query plans tab), and Sort, Aggregate, Limit and others. Rows flow upward: each node asks its child for the next row, so a Limit at the top can stop the whole tree early.

The planner cannot try the plans; running them would cost more than the query. It predicts. For each candidate it estimates how many rows each node will produce (the cardinality) and what that will cost, using a formula (section 2) fed by statistics about the data (section 3). For a query on one table there are a handful of candidates; for joins the number of candidates explodes, and the planner searches them cleverly (section 5). Planning itself takes time: about a millisecond for the queries on this page, and 1.6 seconds for one 16-table join in section 5 measured.

The one sentence to keep
The planner picks the plan with the lowest estimated cost. Every bad plan on this page is a correct choice made on a wrong estimate, or on a cost model that does not match the machine. That is why the routine in section 7 always compares estimated rows with actual rows.

2. How the planner prices a plan

The units

A cost is a number in arbitrary units, not milliseconds. By convention reading one 8 KB page as part of a sequential run costs 1.0, and everything else is priced relative to that (Planner cost constants, defaults unchanged since long before version 16):

SettingDefaultWhat it prices
seq_page_cost1.0One page read as part of a sequential run
random_page_cost4.0One page read by jumping to it (an index lookup)
cpu_tuple_cost0.01Handling one row
cpu_index_tuple_cost0.005Handling one index entry
cpu_operator_cost0.0025Evaluating one operator, such as = or <=, once
parallel_setup_cost, parallel_tuple_cost1000, 0.1Starting parallel workers; passing one row from a worker to the leader
effective_cache_size4 GBNot a cost: how much of the data the planner may assume is cached, used when pricing repeated index reads

Why is a random page only 4 times a sequential one, when on a spinning disk it is closer to 100 times? The documentation says so directly: random access "is normally much more expensive than four times sequential access", but the default assumes most random reads are served from memory. That assumption matters again in section 9.

A sequential scan, priced by hand

Take SELECT * FROM users WHERE id BETWEEN 5001 AND 25000. Postgres's catalogue (pg_class) says users occupies 1,280 pages and holds 100,000 rows. A sequential scan reads every page and checks two comparisons (>= and <=) on every row:

cost = 1,280 × 1.0 + 100,000 × (0.01 + 2 × 0.0025) = 1,280 + 1,500 = 2,780

EXPLAIN prints exactly Seq Scan on users (cost=0.00..2780.00 ...). The two numbers are the startup cost (before the first row comes out: 0 here) and the total cost (after the last). Startup cost matters when a Limit only wants the first few rows; section 7's slow query turns on exactly that.

An index scan: pages depend on physical order

An index scan pays for the index pages and entries it reads, then one table page fetch per matching row, unless consecutive matches sit on the same page. How often they do depends on the correlation: how closely the table's physical row order follows the column's order, from -1 to 1, measured by ANALYZE. In this database messages.id has correlation 1.00 (messages were inserted in id order) while users.id has -0.03 (rows sit in no useful order) measured. The planner estimates heap pages fetched two ways and interpolates by correlation squared: for no correlation it uses the Mackert and Lohman approximation of how many distinct pages N random fetches touch from a table of T pages, about 2TN/(2T+N) when the table fits in cache, each priced at random_page_cost; for perfect correlation it is the matching fraction of the table read nearly sequentially (one random page, the rest at 1.0) (costsize.c, cost_index).

A bitmap scan sits between the two: it reads the index, sorts the matching row addresses by page, and then visits each page once in physical order, priced between random and sequential depending on how much of the table it touches. What the three cost, for 20,000 users and for a million messages:

Correlation is one number for the whole table; these 20,000 users happen to sit on just 315 of its 1,280 pages (the table was rewritten earlier in its life), which the planner cannot know and which is why the bitmap scan touched so few pages. The planner's ranking matched the stopwatch in both cases, and it chose an index scan for up to 6,000,000 of the 10,000,000 messages because the rows it needs sit together.

What the cost model does not know
Whether a page is already in memory (except through effective_cache_size), how fast your disk really is, what other queries are running, and anything about the data beyond its statistics. It is deliberately crude. Leis and colleagues found on real join queries that the cost model "has much less influence on query performance than the cardinality estimates" (How Good Are Query Optimizers, Really?, PVLDB 2015): get the row counts right and a crude cost model is enough.

3. Statistics: what the planner knows about your data

ANALYZE takes a sample

Every row estimate starts from statistics that the ANALYZE command computes and stores in the catalogue (readable through the pg_stats view; Statistics Used by the Planner). It does not read the whole table: it reads a random sample of 300 × the statistics target rows, and the target defaults to 100, so about 30,000 rows however big the table is (analyze.c; default_statistics_target). For each column it keeps:

Field in pg_statsMeaningA real value from this database
null_fracShare of rows that are NULL0 for every column here
n_distinctNumber of distinct values; a negative number is a fraction of the rows (-1 means every row differs)users.country: 20; users.email: -1
most_common_vals, most_common_freqsThe most common values (MCV list), up to the target's count, with the share of rows each hasusers.plan: free 0.8495, pro 0.1410, team 0.0095 (true: 0.8482, 0.1415, 0.0103)
histogram_boundsBoundaries that split the remaining values into buckets holding equal numbers of rowsmessages.tokens: 101 bounds after 100 common values
correlationHow closely physical row order follows the column's order (section 2)messages.created_at: 1.00; chats.user_id: -0.003

How the numbers become an estimate

For WHERE country = 'GB' the planner finds GB in the MCV list with frequency 0.0699 and multiplies by the row count: 0.0699 × 100,000 = 6,987 estimated; the truth is 6,883 measured. A value not in the list gets an equal share of what the list leaves: (1 − sum of MCV frequencies) / (distinct values − number of MCVs). A range such as tokens < 200 counts the histogram buckets below 200 and assumes values are spread evenly inside the bucket where 200 falls (Row Estimation Examples; the Cost model tab reproduces this for a range on id). And when there is nothing to go on, such as a function applied to a column, the planner falls back to fixed guesses: 0.5% of the rows for an equality, a third for an inequality (selfuncs.h).

Distinct counts are the hardest number to sample

You cannot count distinct values from a sample without guessing how many values the sample missed. Postgres uses an estimator from the sampling literature and it tends to guess low for skewed columns: chats.user_id is stored as 75,971 distinct users when there are 99,945, and messages.chat_id as 872,528 when there are 999,951 measured. Distinct counts drive join estimates (section 4), and Leis and colleagues saw "severe underestimates for large tables" of exactly this statistic (PVLDB 2015, section 3.4). Raising the target enlarges the sample; on a copy of chats:

Sampling is random, so a second run gives slightly different values; at 10,000 the sample is the whole table and the numbers are exact. Set it per column where it matters, rather than globally: ALTER TABLE chats ALTER COLUMN user_id SET STATISTICS 1000; then ANALYZE chats;. The cost is ANALYZE time and a slightly slower planner (longer lists to search).

Statistics go stale

Statistics describe the table at the moment ANALYZE ran. Postgres's background autovacuum process re-analyzes a table after autovacuum_analyze_threshold + autovacuum_analyze_scale_factor × rows have changed, 50 rows plus 10% by default (autovacuum settings): for a 10-million-row table that is a million changes. A bulk load between two analyses is the classic trap. Measured on a small table (this dataset's tables have autovacuum switched off so that nothing changes behind the measurements):

Before the load

1,000 rows, user 7 owns 1% of them. ANALYZE. Estimate for WHERE user_id = 7: 10, truth 10.

After loading 999,000 rows, mostly user 7's

No ANALYZE yet. The planner sees from the file size that the table grew, so it scales up, but it still believes user 7 owns 1%: estimate 9,100, truth 899,110 measured; it picks a Bitmap Heap Scan.

After ANALYZE

Estimate 901,100, and a Seq Scan. Here both plans took about 47 to 49 ms, because the whole table was in memory; the wrong estimate becomes expensive when this table is joined to another and the planner sizes the join for 9,100 rows.

The routine: run ANALYZE (or VACUUM ANALYZE) right after a bulk load or a large delete, and lower the scale factor per table for big tables that change steadily (ALTER TABLE messages SET (autovacuum_analyze_scale_factor = 0.01)). Since PostgreSQL 18, pg_upgrade keeps statistics across a major upgrade; before it, a freshly upgraded database planned blind until it was analyzed (PostgreSQL 18 release notes). Vacuum itself belongs to Running Postgres in production.

Extended statistics: facts about pairs of columns

Per-column statistics cannot know that every London user is in Great Britain. CREATE STATISTICS adds a statistics object over several columns, of three kinds (CREATE STATISTICS; Multivariate statistics examples): dependencies (how strongly one column determines another; here {"city => country": 1.000}), ndistinct (how many distinct combinations exist; here 60, not 20 × 60 = 1,200) and mcv (the most common combinations with their frequencies). Each fixes a different query. On a copy of users, estimated rows against the truth measured:

Green: within a factor of 1.5 of the truth. Note the second row: functional dependencies only know that city implies country, not which pairs exist, so they make the impossible "GB and Paris" look common (1,813 estimated); the documentation warns that when such conditions are incompatible "the correct estimate would be zero rows, but that possibility is not considered" (Statistics Used by the Planner). Only the MCV kind knows the pair never occurs. The parent's Query plans tab (case 5) shows the same fix changing a join on 10 million messages. Cost: ANALYZE does more work, and the objects must be created by someone who knows the columns are related; nothing detects that automatically.

4. Why estimates go wrong

Every misestimate on this page comes from one of four places. In each, the planner did the arithmetic right on an assumption that the data broke.

CauseExample on this dataEstimatedActualOff by
1. Independence. Conditions on two columns are multiplied as if unrelated.
GB is 7% of users and London is a third of GB's users but about 2.3% of all users, so the planner computes 0.07 × 0.023 × 100,000, about 160 rows, when every London user is British and the truth is 2,294. The fix is extended statistics (section 3) or, when the columns are really one fact, storing one column.
2. Joins. Errors multiply up the tree, and Postgres has no statistics about join results.
For an equality join the planner estimates matches as rows(A) × rows(B) / max(distinct values on each side), which assumes every value on the smaller side finds partners. A 10 times error at the bottom of a three-join plan can be 1,000 times at the top. Leis and colleagues built the Join Order Benchmark (113 queries over 21 tables of real IMDb data) to measure this in five systems: "all estimators routinely produce large errors", with misestimates "by a factor of 1000 or more" routine, and a systematic tendency to underestimate, which pushes planners toward nested loops that blow up (PVLDB 2015). Underestimates are the dangerous direction: an overestimate wastes a little memory, an underestimate picks an algorithm meant for small inputs.
3. Expressions, patterns and functions. No statistics exist for computed values.
WHERE lower(email) = ... or WHERE created_at::date = ... have no statistics, so the planner uses its fixed guesses (0.5% for an equality). LIKE 'Chat 123456%' is estimated from the histogram plus a guess for the rest of the pattern: 100 rows estimated, 1 real, and that overestimate is what makes section 7's slow query slow. An index on the expression gives the planner statistics for it as well as a fast path; CREATE STATISTICS on a single expression (PostgreSQL 14 and later) collects the statistics without the cost of maintaining an index (CREATE STATISTICS). Sargability, the rule that an index can only help when the column is left bare, is the parent's Query plans case 3.
4. Unknown parameters. A plan made before the value is known must guess.
A generic plan for WHERE org_id = $1 uses the average share of a non-common value: 290 rows. For the one organisation that owns half the table that is wrong by a factor of 6,897. Section 10 measures what follows.
The habit that finds all four
Run EXPLAIN (ANALYZE, BUFFERS), then walk the plan from the bottom and compare rows= (estimated) with actual rows= × loops at each node. The lowest node where they differ by more than about 10 times is where the plan went wrong; everything above it was planned for the wrong input. Section 6 shows how to read the rest.

5. Join order: a search problem

With two tables the planner compares a handful of plans: which table is outer, which of the three join algorithms, which access path for each side. Every extra table multiplies the choices. With n tables there are n! orders for a simple chain of joins (3,628,800 for ten) and more if intermediate results may themselves be joined ("bushy" trees). Trying them one by one is impossible, so since IBM's System R (Selinger and colleagues, Access Path Selection in a Relational Database Management System, SIGMOD 1979) planners use dynamic programming: find the cheapest way to join every pair, keep it, then build the cheapest plan for every set of three from the kept pairs, and so on. That turns the factorial into "only" exponential, because it still visits every subset of tables that the query's join conditions connect.

Postgres runs this near-exhaustive search while the query has fewer than geqo_threshold (12 by default) items in its FROM list. From 12 on it switches to GEQO, the genetic query optimizer, which treats join order like the travelling salesman problem: it encodes orders as strings such as 4-1-3-2, breeds and mutates a population of them, and keeps the cheapest it finds in a fixed budget (GEQO in PostgreSQL). It is randomised: the result depends on geqo_seed and need not be the best plan.

Two subtleties trip people up. First, explicit JOINs are only reordered in groups of 8: join_collapse_limit and from_collapse_limit (8 by default) stop the planner from flattening longer chains of JOIN ... ON or nested subqueries into one search, so a 14-table query written with JOIN syntax is planned as smaller searches whose boundaries follow how you wrote it, and GEQO never runs; written as a comma-separated FROM list it is one search of 14 items and GEQO does (Controlling the Planner with Explicit JOIN Clauses). Second, exhaustive is not the same as right: the search is only as good as its row estimates, which section 4 showed can be off by 1,000 times on joins. Leis and colleagues still found exhaustive dynamic programming beat heuristic search on their benchmark, despite the bad estimates.

Problem it solvesChoosing a join order among millions without trying them.
HowDynamic programming over subsets up to 11 FROM items; GEQO from 12.
CostPlanning time that grows exponentially with tables; GEQO trades plan quality for a bounded search.
When to actGenerated queries joining 12 or more tables (ORMs, BI tools): measure planning time in EXPLAIN's summary; raise geqo_threshold only if planning stays affordable, or split the query.

6. Reading EXPLAIN like a professional

EXPLAIN shows the plan the planner chose without running it. EXPLAIN ANALYZE runs the query (so it really inserts, updates or deletes: wrap those in BEGIN; ... ROLLBACK;) and adds what happened (EXPLAIN; Using EXPLAIN). Use EXPLAIN (ANALYZE, BUFFERS) by default; PostgreSQL 18 turns BUFFERS on automatically with ANALYZE. Other options worth knowing: SETTINGS (lists settings changed from their defaults, so a plan pasted into a ticket says which work_mem it ran with), VERBOSE (output columns), FORMAT JSON (for tools such as explain.dalibo.com and explain.depesz.com), GENERIC_PLAN (PostgreSQL 16 and later: the plan for a statement with $1 placeholders, without values), and SUMMARY (planning time).

Reading a whole plan

  1. Start at the bottom (the most indented lines) and go up: children produce rows for their parents.
  2. Find the time. Each node's time includes its children; subtract them to see what the node itself cost. Multiply by loops on the inner side of a nested loop.
  3. Compare estimated and actual rows at each node (section 4's habit). The lowest big mismatch is the cause.
  4. Count pages in Buffers: pages are the work, and unlike milliseconds they do not change between a cold and a warm run (the parent's Query plans case 8 shows the same query at three cache temperatures).
  5. Look for waste: Rows Removed by Filter in the millions, Heap Fetches on an Index Only Scan (the table had to be visited after all), Sort Method: external merge or Batches greater than 1 (spilled to disk), Workers Launched fewer than Workers Planned (no free parallel workers).
  6. Check Planning Time against Execution Time: for short queries run thousands of times, planning can be most of the cost (section 10).

What measuring costs

EXPLAIN ANALYZE reads the clock twice per row per node, and that is not free. On this laptop the clock costs 20.6 nanoseconds a read (pg_test_timing), and SELECT count(*) FROM messages took 432 ms plainly, 722 ms under EXPLAIN ANALYZE, and 469 ms with TIMING OFF measured: per-node timing added 67% to a query that pushes 10 million rows through two nodes. Row counts and buffers stay exact either way, so use (ANALYZE, BUFFERS, TIMING OFF) when you only need counts, and trust ratios rather than absolute times from a timed plan. The same cost applies to auto_explain in section 7, which is why its log_timing is often switched off.

7. The slow-query workflow: find, explain, fix, verify

"The app is slow" is not a query. Professionals do not start by staring at the query they suspect; they ask the database which statements consume its time, explain the top one, change one thing, and measure again with the same load. Four steps, each with a standard tool.

Find: pg_stat_statements

pg_stat_statements is an extension shipped with Postgres that keeps running totals for every distinct statement the server executes (pg_stat_statements). It must be loaded at server start (shared_preload_libraries = 'pg_stat_statements', then CREATE EXTENSION pg_stat_statements; in the database). It normalises statements: WHERE chat_id = 42 and WHERE chat_id = 77 become one entry, WHERE chat_id = $1, with calls, total and mean execution time, rows, and pages hit and read, for up to 5,000 statements by default. The question to ask it is which statements use the most total time, because total time is what the server spends and what users wait behind:

SELECT calls, round(total_exec_time) AS total_ms, round(mean_exec_time, 2) AS mean_ms,
       round(100 * total_exec_time / sum(total_exec_time) OVER (), 1) AS pct, query
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

A query that takes 2 ms but runs 50,000 times an hour costs more than a 30-second report run once a day. Sorting by mean time finds the slowest single statements, which is a different question (what users of one page feel).

Explain: get a real plan with real values

pg_stat_statements has no parameter values, only $1. To see the plan you need a real value: from the application's logs, or from Postgres's own logs. Two settings log slow statements: log_min_duration_statement logs the text and duration of any statement slower than a threshold (logging settings), and the auto_explain extension logs its plan as well (auto_explain). Verifying under load catches what a single EXPLAIN cannot: a new index slows every write, and removing the top query moves the bottleneck to the next one.

Why this query was slow, and the two fixes
The search WHERE title LIKE 'Chat 123456%' ORDER BY id LIMIT 10 fell into the Limit trap: the planner estimated 100 matching titles, so walking the primary key in id order and stopping after 10 matches looked cheap (cost 3,780 against sorting all matches). There was one match, so every search read the whole table through the index: 12,053 pages, 91.6 ms in EXPLAIN and 112.9 ms on average under load. An index on title lets LIKE 'prefix%' become a range scan (this database uses the C collation; under other collations create it with text_pattern_ops, Operator Classes): 0.078 ms, about 1,170 times faster for one search, at the price of 31.6 MB and slower inserts into chats. Without an index, a rewrite still helps: ordering by title removes the temptation to walk the primary key, so Postgres scans the table in parallel and sorts the one match: 33 ms instead of 84 ms measured, better but still a full scan per keystroke. A LIKE '%123456%' (a substring, not a prefix) cannot use a B-tree at all; it needs a trigram index (pg_trgm), covered on Search and vector databases.






8. The fixes, in the order to try them


Once the plan shows the cause, the fix usually comes from this list, roughly in order of how often it is the answer and how little it risks. For each: the problem it solves, how, what it costs, and when not to use it.


1. An index, or a better one


Problem: the query reads far more rows than it returns (large Rows Removed by Filter, a Seq Scan feeding a small result). How: a B-tree on the columns the query filters, joins or sorts on (Indexes). Four variations matter: a composite index on several columns, equality columns first and the range or sort column last (the parent's Query plans case 2); an expression index such as ON users (lower(email)) (case 3); a partial index with a WHERE clause, such as ON jobs (created_at) WHERE status = 'pending', small because it covers only the rows the query wants (Partial Indexes); and a covering index, ON chats (user_id) INCLUDE (title), which can answer from the index alone (an Index Only Scan, case 7; Index-Only Scans and Covering Indexes). Cost: space (the title index: 31.6 MB for a million rows, built in 1.4 s measured), and every insert, and every update of an indexed column, now writes one more structure. When not: on columns where most rows match, on tables that are written far more than read, and twice on the same columns; find unused ones with pg_stat_user_indexes.idx_scan = 0 over a full business cycle. In production build with CREATE INDEX CONCURRENTLY, which does not block writes (operations belong to Running Postgres in production; index structures to Storage engines and indexes).


2. Rewrite the query


Problem: the SQL asks for something the planner cannot do cheaply, or hides information from it. The rewrites that come up again and again:


    

  • Leave indexed columns bare: created_at >= '2026-03-01' AND created_at < '2026-03-02', not created_at::date = '2026-03-01' (case 3).
    • 

  • Avoid the Limit trap: ORDER BY x LIMIT n with a rare filter on another column (section 7).
    • 

  • Paginate by key, not by OFFSET: WHERE (created_at, id) < (:t, :id) ORDER BY created_at DESC, id DESC LIMIT 20 seeks straight to the page; OFFSET 100000 reads and discards 100,000 rows. Measured on Building a backend API: the key-based ("cursor" or "keyset") page stayed at 0.02 to 0.05 ms from the first page to a million rows deep, while OFFSET grew in proportion to the depth.
    • 

  • Replace a per-row subquery with a join: a SubPlan with loops= in the thousands runs once per outer row; a join or LEFT JOIN LATERAL runs once (the Plan reading lab has one).
    • 

  • NOT EXISTS, not NOT IN, for "rows with no match": NOT IN returns nothing if the subquery yields a NULL, and it cannot be planned as an anti-join (Subquery Expressions).
    • 

  • Select the columns you need: fewer columns make rows narrower and allow index-only scans.
    • 



Cost: developer time and the risk of changing results; test that the rewritten query returns the same rows. When not: when the plan is fine and the time is elsewhere (the application, the network).


3. Give the planner better statistics


Section 3: ANALYZE after bulk changes, a higher target on skewed columns, extended statistics for related columns, an expression index or expression statistics for computed predicates. Cheap and safe; it fixes estimates, not missing access paths.


4. Change how the application talks to the database


Many "slow database" problems are an application making too many round trips. Two patterns, measured from Python (psycopg 3.3.6) over TCP on the same laptop, the cheapest round trip there is (0.056 ms for SELECT 1):












The N+1 pattern is what an object-relational mapper (ORM: a library such as SQLAlchemy, Django's ORM or ActiveRecord that maps tables to classes) does with lazy loading: one query for a user's 20 chats, then one more query per chat for its last message, 21 round trips. One query with LEFT JOIN LATERAL returns the same 20 rows. On one machine that was 1.42 ms against 0.22 ms per page, 6.5 times; across a network each extra round trip adds its full latency, and the Numbers to know tab of Topic: swe-and-system-design works the same 21 queries at a 2 ms zone-to-zone round trip into 43 ms. ORMs have a switch for it (eager loading: selectinload or joinedload in SQLAlchemy, select_related and prefetch_related in Django); turn on query logging in development to see the counts. Batching is the same idea for writes: 10,000 single-row INSERTs each in its own transaction took 1,391 ms; the same rows by COPY took 7.0 ms, 199 times faster, with multi-row INSERT and arrays in between. Each commit waits for the log to reach disk (the parent page, section 4), and each statement is a round trip.


Cost: code changes; larger batches hold locks longer and fail as a unit. When not: for genuinely interactive single-row work.


5. Settings, then hardware, last


Section 9. A setting changes every query on the server, so it fixes one query only by accident and can break others; hardware multiplies whatever the queries do, including the waste. Both come after the query is right.

work_mem, and what a spill costs


A sort or hash that needs more than work_mem writes partial results to temporary files and reads them back: the Sort becomes external merge, the Hash and HashAggregate split into Batches. Measured on three queries at five settings (serial plans, best of three):












The penalty here, 1.1 to 1.7 times at the default 4 MB, is smaller than folklore suggests because the temporary files never left the operating system's memory on a laptop with free RAM and a fast SSD; on network-attached cloud disks or a memory-starved server it is larger. The bigger danger is the other direction. work_mem is per operation, per process: the documentation warns that "the total memory used could be many times the value of work_mem". A query with three sorts, run by 200 connections at 256 MB each, could ask for 150 GB. So keep the default modest, raise it where it pays (ALTER ROLE reporting SET work_mem = '256MB', or SET LOCAL inside one transaction), and find spills with log_temp_files = 0 or pg_stat_statements' temp_blks_written.


random_page_cost on SSDs


Correction to the old page
The old page said a random_page_cost of 4 "pushes the planner towards sequential scans" on NVMe and that 1.1 "is the common setting". The default is 4.0, but the current documentation gives no SSD value: it explains that 4 is already low because "the majority of random accesses to storage, such as indexed reads, are assumed to be in cache", and suggests lowering it when the data is likely to be fully cached or network latency is high (random_page_cost). 1.1 is a widespread practice, not a documented standard. The parent's Query plans case 4 shows 1.1 changing a real plan; the Cost model tab lets you watch the crossover move. Change it only with before and after measurements across the whole workload.


Parallel query


For a big scan, Postgres can start parallel workers, extra processes that each scan part of the table, with a Gather node combining their rows (How Parallel Query Works). The planner picks the number of workers from the table size: one worker for a table of min_parallel_table_scan_size (8 MB), one more each time the table triples (allpaths.c). For the 1.5 GB messages table that is 5, capped by max_parallel_workers_per_gather:




Parallelism does not reduce the work, it splits it: six processes (five workers and the leader) shared the scan and finished 4.6 times sooner, using six cores to do it. That is right for one big report and wrong for a server already busy with hundreds of small queries, where workers just compete for the same cores. Queries that write data or lock rows never run in parallel (When Can Parallel Query Be Used?), and workers come from a fixed pool (max_worker_processes, max_parallel_workers, 8 each by default), so Workers Launched can be lower than planned at busy times.


JIT compilation


Since PostgreSQL 11 the server can compile a query's expressions to machine code with LLVM, on by default since version 12; it triggers when the estimated cost exceeds jit_above_cost (100,000), with more aggressive inlining and optimisation above 500,000 (JIT decision). The documentation's own caveat: "for short queries the added overhead of performing JIT compilation will often be higher than the time it can save". Because the threshold is a cost, not a time, a fast query with a large estimated cost (a misestimate, or a big table scanned with a Limit) can pay compilation on every run; that shows up as a JIT: block at the end of EXPLAIN ANALYZE with its timings, and the usual fix for transactional workloads is jit = off for the application's role. Not measured here: the server build used for this page has no LLVM (pg_jit_available() returns false).






10. Prepared statements: one plan for every parameter


A prepared statement is parsed once and then executed many times with different parameter values: PREPARE q(int) AS SELECT ... WHERE org_id = $1; then EXECUTE q(42); in SQL, or the same thing done invisibly by a driver over the protocol. It saves parsing and planning on every call and keeps values apart from SQL text (which is also what makes it safe from SQL injection). The catch is planning. Postgres can make a custom plan for each call, knowing the value, or reuse one generic plan built without it. The rule, from the documentation: "the first five executions are done with custom plans and the average estimated cost of those plans is calculated. Then a generic plan is created and its estimated cost is compared to the average custom-plan cost", and the generic plan is used from then on if it is not much more expensive (PREPARE).


Applications rarely type PREPARE; their drivers do it. psycopg 3 prepares a statement on the server after it has run 5 times on a connection (prepare_threshold, 5 by default, read from a live connection for this page; psycopg: prepared statements), and the Java driver PgJDBC does the same at its prepareThreshold of 5 (PgJDBC). PgBouncer, the usual connection pooler, passes such statements through in transaction mode when max_prepared_statements is non-zero (PgBouncer configuration). So the generic-plan switch happens in ordinary application code, on the sixth call or later, which is why it so often appears as "fast in testing, slow in production".


A regression, measured


The page adds one table to the chat product: usage_events, one row per model call billed to a customer organisation, 4,000,000 rows. One enterprise customer, organisation 1, owns half of them (2,000,231 rows); the other half is spread over 20,000 organisations of about 100 rows each illustrative skew, real measurement. The billing page runs, through a prepared statement, SELECT c.model, count(*), sum(e.tokens) FROM usage_events e JOIN chats c ON c.id = e.chat_id WHERE e.org_id = $1 GROUP BY c.model. Eight calls in one session: five small organisations, the enterprise twice, one small one.














What happened, from the plans: calls 1 to 5 got custom plans for about 100 rows each (an index lookup and a nested loop, cost 1,765, under 1 ms). Call 6, the enterprise, still got a custom plan, a parallel hash join priced at 94,481, which took 520 ms. That expensive call pulled the average custom cost up to 17,218, and the generic plan, which assumes a typical organisation has 290 rows, cost only 3,483. So from call 7 Postgres used the generic plan: a nested loop doing 2,000,231 index lookups into chats, 4,419 ms for the enterprise, 8.5 times its custom plan. The generic plan is fine for everyone else (call 8: 0.53 ms), which is exactly why it looked cheap.


Fix 1: custom plans for this statementSET plan_cache_mode = force_custom_plan for the session or role that runs it; planning costs about a millisecond here, against seconds saved. Measured: enterprise 531 to 597 ms on every call.
Fix 2: do not prepare itpsycopg prepare=False on that call, or prepare_threshold=None on the connection.
Fix 3: separate the outlierA separate code path or query for the few giant tenants, so one plan fits each group.
See it comingEXPLAIN (GENERIC_PLAN) (PostgreSQL 16+) shows the generic plan; pg_prepared_statements counts generic and custom plans per statement.







11. Plan regressions, and pinning a plan


A plan regression is a query that was fast and became slow without its SQL changing. The plan changed because one of its inputs did: new statistics after ANALYZE, data growth crossing a cost crossover (the Cost model tab shows how sharp they are), a setting, an index added or dropped, a parameter value (section 10), or a major-version upgrade that taught the planner something new (PostgreSQL 18 added B-tree skip scan, for example).


Detecting them is the workflow of section 7 run continuously: snapshot pg_stat_statements periodically and alert when a statement's mean time jumps (its queryid stays the same while its timing changes; stddev_exec_time rising is the sign of a plan that differs by parameter); keep auto_explain on with a threshold so that the bad plan is in the log; and before a major upgrade, compare the plans of the top statements on a staging copy.


Responding follows section 8's order: fix the estimate (statistics), then the query or index, and only then pin. Core Postgres has no plan pinning, by design: the project's stated position is that it is "not interested in implementing hints in the exact ways they are commonly implemented on other databases" (PostgreSQL wiki: Optimizer Hints). The tools are outside it:


    

  • pg_hint_plan, an extension that reads hints from a comment at the start of the query, such as /*+ HashJoin(e c) SeqScan(e) */, or from a table of hints keyed by query text, and forces scan methods, join methods and join order (pg_hint_plan; this page built its REL16_1_6_1 release).
    • 

  • On Amazon Aurora PostgreSQL, apg_plan_mgmt ("query plan management") captures plans and enforces approved ones (AWS documentation). Other databases build this in: SQL Server's Query Store can force a plan, Oracle has SQL Plan Management.
    • 



The measured warning is section 10's third toggle: pinning the billing query to a hash join with a sequential scan, the right plan for the enterprise, made each small organisation's call take 105 to 124 ms instead of under 1 ms, about 180 times slower, because each now scans all 1,000,000 chats to probe a hash table of 100 rows; and the enterprise still took 1,133 ms, because the hint fixed the join method but not which side to hash, and the planner hashed the 2,000,231 usage rows instead of the 1,000,000 chats. A pinned plan is right for one range of data and parameters and stays pinned when they move. Keep pins few, written down, and reviewed after every upgrade.

QORL, corrected
The old page credited the model with "a 1.81x geometric mean speedup and a 44.7% latency reduction ... with zero regressions". The write-up's results table separates three ways of picking a plan. The model's own choice, per run: 1.40 times geometric-mean speedup over Postgres, with 119 wins and 7 regressions (more than 5% slower) over 339 runs (113 queries, three runs each). Best measured candidate within a run: 1.44 times, 1 regression. Best measured candidate across all three runs (up to 15 candidate plans per query, each executed and timed): 1.81 times, 44.7% lower latency, 0 regressions over the 113 queries. Untrained, the model produced no usable plan for 99 of the 113. Cost: about $1,200 ($800 of GPU rental, $400 of API fees). The 1.81 needs measured feedback on each candidate, which only makes sense for a heavy query that runs again and again; and JOB served as the validation set during development, so it is not a pristine held-out test. Note the method too: queries were warmed until page hits and reads were stable within 2% before timing, the cold-against-warm trap of the parent's case 8.


In production today: none of these ships in PostgreSQL, and the practical lesson from Bao and QORL is that steering an existing planner with hints is far easier to deploy than replacing it. For an application team the takeaway is the reverse direction: everything a learned optimizer learns is a correction to row estimates, and sections 3 and 8 are how a person makes the same corrections today.






What professionals set up before anything is slow


The routine only works if the evidence is already being collected when the problem appears. A common starting point for a Postgres server, each line from the documentation linked above; the thresholds are judgement calls, not standards:


# postgresql.conf (server restart needed for shared_preload_libraries)
shared_preload_libraries = 'pg_stat_statements,auto_explain'
pg_stat_statements.max = 10000        # default 5000; more if the app sends many distinct statements
track_io_timing = on                  # I/O time in EXPLAIN and pg_stat_statements; check the clock cost with pg_test_timing first
log_min_duration_statement = '500ms'  # log text and duration of slow statements
auto_explain.log_min_duration = '1s'  # and the plan of very slow ones
auto_explain.log_analyze = on
auto_explain.log_buffers = on
auto_explain.log_timing = off         # avoid the per-node clock cost (section 6)
auto_explain.sample_rate = 0.1        # explain one statement in ten
log_temp_files = 0                    # log every spill to disk, with its size


    

  • Look weekly, not only during incidents: the top 10 statements by total time, and what changed since last week. Many teams keep snapshots of pg_stat_statements in a table or in their monitoring system, since its counters are cumulative and reset on restart or pg_stat_statements_reset().
    • 

  • Set a statement_timeout per application role, so one runaway query cannot hold a connection and its locks for an hour (operational detail on Running Postgres in production).
    • 

  • Test plans on production-sized data, or at least with production statistics: a plan on a 1,000-row development table says nothing about the 10-million-row one.

    •

Common mistakes


Optimising the query someone complained about instead of the one using the most time
Sort pg_stat_statements by total time. In section 7 the noticed report was 2.4% of database time and the unnoticed search 78.6%.


Reading EXPLAIN without ANALYZE, or without BUFFERS
Plain EXPLAIN shows only estimates, so it cannot show the misestimate that is usually the cause. Without BUFFERS you see time, which changes with the cache, instead of pages, which do not.


Comparing a cold run with a warm one
The first run reads from disk, the second from memory. Run twice, compare page counts, and say which you measured (the parent's Query plans case 8).


Testing plans on a small development database
Plans depend on table sizes and statistics; a Seq Scan is the right plan for a small table and the wrong one for a big one.


One new index per slow query
Each index slows every write and takes space. Check whether an existing composite index can serve the query, and drop indexes that pg_stat_user_indexes shows unused.


Switching off a plan type in production
enable_nestloop = off and its siblings are diagnostic switches for testing, not fixes: they make that plan type look absurdly expensive for every query.


Raising work_mem for the whole server
It is per operation and per process; raise it for the role or session that needs it.


Forgetting ANALYZE after a bulk load or (before PostgreSQL 18) a major upgrade
Section 3: the planner plans on the old picture of the data until statistics are refreshed.


Trusting EXPLAIN ANALYZE's milliseconds as exact
Per-node timing has a cost (67% on one scan here). Use ratios, page counts and row counts; use TIMING OFF when counts are enough.


Not seeing the ORM's queries
Turn on SQL logging in development and count queries per request; N+1 patterns are invisible in the code that causes them.


Expecting an index to help LIKE '%word%'
A B-tree helps only a prefix (LIKE 'word%', with the C collation or text_pattern_ops). Substring search needs a trigram index or a full-text index.


"Fast in testing, slow in production" with prepared statements
Drivers prepare after 5 executions and Postgres may switch to a generic plan after that (section 10). Check EXPLAIN (GENERIC_PLAN).


Copying configuration folklore
random_page_cost = 1.1, huge work_mem, JIT on or off: each is right for some workloads. Change one setting at a time with before and after numbers from your own workload.







Glossary




auto_explain
An extension that logs the plans of statements slower than a threshold (section 7).


Bitmap scan
Collects matching row addresses from an index, sorts them by page, then reads each page once (section 2).


Cardinality
The number of rows a plan node outputs; the planner estimates it before running (section 1).


Correlation
How closely a table's physical row order follows a column's order, from -1 to 1 (section 2).


Cost
The planner's price for a plan in arbitrary units where one sequential page read is 1.0; startup cost is the price before the first row, total cost after the last (section 2).


Custom and generic plan
For a prepared statement, a plan made for the actual parameter values, or one plan reused for all values (section 10).


Dynamic programming
The join-order search that builds the cheapest plan for every subset of tables from the cheapest plans of smaller subsets (section 5).


Extended statistics
Statistics over several columns created with CREATE STATISTICS: dependencies, ndistinct, mcv (section 3).


GEQO
The genetic query optimizer, a randomised join-order search used from 12 FROM items (section 5).


Histogram
Boundaries that split a column's values into buckets with equal numbers of rows (section 3).


MCV list
A column's most common values with their frequencies (section 3).


N+1 queries
One query for a list, then one query per item; usually caused by an ORM's lazy loading (section 8).


Node
One step in a plan tree: a scan, a join, a sort, an aggregate (section 1).


pg_hint_plan
An extension that forces parts of a plan from hints in comments (section 11).


pg_stat_statements
An extension that keeps per-statement totals of calls, time, rows and pages (section 7).


Plan, planner
The tree of steps that runs a query, and the component that chooses it by estimated cost (section 1).


Plan regression
A query that became slow because its plan changed, not its SQL (section 11).


Prepared statement
A statement parsed once and executed many times with parameters (section 10).


Sargable
A condition an index can answer, typically with the indexed column left bare (section 4).


Selectivity
The fraction of rows a condition keeps; estimated rows = selectivity × rows (section 3).


Spill
A sort or hash that outgrows work_mem and writes temporary files (section 9).


Statistics
What ANALYZE stores about each column from a sample: null fraction, distinct count, MCVs, histogram, correlation (section 3).


Statistics target
The size of the MCV list and histogram, and the sample (300 rows per unit); 100 by default (section 3).
