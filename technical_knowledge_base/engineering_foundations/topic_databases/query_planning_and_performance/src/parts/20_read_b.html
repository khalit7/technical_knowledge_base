2. How the planner prices a plan

A cost is a number in arbitrary units, not milliseconds: reading one 8 KB page as part of a sequential run costs 1.0 (seq_page_cost), a page reached by jumping to it 4.0 (random_page_cost), handling a row 0.01, an index entry 0.005, evaluating one operator such as <= 0.0025 ({{Planner cost constants|https://www.postgresql.org/docs/current/runtime-config-query.html#RUNTIME-CONFIG-QUERY-CONSTANTS}}). Random is only 4 times sequential, when on a spinning disk it is closer to 100, because the default assumes most random reads come from memory: random access "is normally much more expensive than four times sequential access", says the documentation (section 9 comes back to this).

A sequential scan, priced by hand

SELECT * FROM users WHERE id BETWEEN 5001 AND 25000. The catalogue (pg_class) says users occupies 1,280 pages and holds 100,000 rows. A sequential scan reads every page and checks two comparisons (>= and <=) on every row:

cost = 1,280 × 1.0 + 100,000 × (0.01 + 2 × 0.0025) = 1,280 + 1,500 = 2,780

EXPLAIN prints exactly Seq Scan on users (cost=0.00..2780.00 ...): startup cost 0, total cost 2,780. Startup cost matters when a Limit only wants the first few rows; the hero's slow search turns on exactly that.

An index scan: pages depend on physical order

An index scan pays for the index pages and entries it reads, then one table page fetch per matching row, unless consecutive matches sit on the same page. How often they do depends on the column's correlation, measured by ANALYZE: messages.id has 1.00 (messages were inserted in id order), users.id -0.03 (no useful order) measured. The planner estimates heap pages two ways and interpolates by correlation squared: with no correlation, the Mackert and Lohman approximation of how many distinct pages N random fetches touch in a table of T pages, about 2TN/(2T+N) when the table fits in cache, each at random_page_cost; with perfect correlation, the matching fraction of the table read nearly sequentially ({{costsize.c, cost_index|https://github.com/postgres/postgres/blob/REL_16_2/src/backend/optimizer/path/costsize.c}}). A bitmap scan sits between the two: it sorts the matching row addresses by page and visits each page once, priced between random and sequential by how much of the table it touches.

Defaults reproduce Postgres's own costs, independently
The calculator's formulas, transcribed from the PostgreSQL 16.2 source (cost_seqscan, cost_index, index_pages_fetched, cost_bitmap_heap_scan, genericcostestimate, btcostestimate and the histogram code), reproduce 150 of 150 figures that EXPLAIN printed (row estimates, sequential, index and bitmap costs) across 25 ranges on the two tables, to the cent (checked in src/recompute.py).
What the cost model does not know
Whether a page is already in memory (except through effective_cache_size), how fast your disk is, what else is running, and anything about the data beyond its statistics. It is deliberately crude. Leis and colleagues found on real join queries that the cost model "has much less influence on query performance than the cardinality estimates" ({{How Good Are Query Optimizers, Really?, PVLDB 2015|https://www.vldb.org/pvldb/vol9/p204-leis.pdf}}): get the row counts right and a crude cost model is enough.
