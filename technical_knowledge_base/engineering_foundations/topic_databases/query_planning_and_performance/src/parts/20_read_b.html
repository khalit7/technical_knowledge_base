1. What a planner does

When the app sends SELECT * FROM messages WHERE chat_id = 42 ORDER BY created_at, nothing in that sentence says which file to open, whether to use an index, or in what order to do things. SQL is declarative: it describes the result. Turning that description into steps is the job of a chain of components, the same in every relational database and documented for Postgres in {{The Path of a Query|https://www.postgresql.org/docs/current/query-path.html}}:

ParseCheck the grammar and build a tree of the statement.
AnalyseLook up every name: which table is messages, which type is chat_id.
RewriteReplace views by the queries that define them and apply rules.
PlanEnumerate ways to run it, estimate the cost of each, keep the cheapest.
ExecuteRun the chosen plan and stream rows back.

Step 4 is the planner (also called the optimizer). Its output, the plan, is a tree of nodes. The leaves read data: a Seq Scan (sequential scan) reads every page of a table in order; an Index Scan walks an index and fetches the matching rows; a Bitmap Heap Scan first collects matching row addresses from an index and then reads their pages in physical order; an Index Only Scan answers from the index without touching the table. Nodes above the leaves combine rows: the three join algorithms (nested loop, hash join, merge join, compared on real data in the parent's {{Query plans|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab), and Sort, Aggregate, Limit and others. Rows flow upward: each node asks its child for the next row, so a Limit at the top can stop the whole tree early.

The planner cannot try the plans; running them would cost more than the query. It predicts. For each candidate it estimates how many rows each node will produce (the cardinality) and what that will cost, using a formula (section 2) fed by statistics about the data (section 3). For a query on one table there are a handful of candidates; for joins the number of candidates explodes, and the planner searches them cleverly (section 5). Planning itself takes time: about a millisecond for the queries on this page, and 1.6 seconds for one 16-table join in section 5 measured.

The one sentence to keep
The planner picks the plan with the lowest estimated cost. Every bad plan on this page is a correct choice made on a wrong estimate, or on a cost model that does not match the machine. That is why the routine in section 7 always compares estimated rows with actual rows.

2. How the planner prices a plan

The units

A cost is a number in arbitrary units, not milliseconds. By convention reading one 8 KB page as part of a sequential run costs 1.0, and everything else is priced relative to that ({{Planner cost constants|https://www.postgresql.org/docs/current/runtime-config-query.html#RUNTIME-CONFIG-QUERY-CONSTANTS}}, defaults unchanged since long before version 16):

SettingDefaultWhat it prices
seq_page_cost1.0One page read as part of a sequential run
random_page_cost4.0One page read by jumping to it (an index lookup)
cpu_tuple_cost0.01Handling one row
cpu_index_tuple_cost0.005Handling one index entry
cpu_operator_cost0.0025Evaluating one operator, such as = or <=, once
parallel_setup_cost, parallel_tuple_cost1000, 0.1Starting parallel workers; passing one row from a worker to the leader
effective_cache_size4 GBNot a cost: how much of the data the planner may assume is cached, used when pricing repeated index reads

Why is a random page only 4 times a sequential one, when on a spinning disk it is closer to 100 times? The documentation says so directly: random access "is normally much more expensive than four times sequential access", but the default assumes most random reads are served from memory. That assumption matters again in section 9.

A sequential scan, priced by hand

Take SELECT * FROM users WHERE id BETWEEN 5001 AND 25000. Postgres's catalogue (pg_class) says users occupies 1,280 pages and holds 100,000 rows. A sequential scan reads every page and checks two comparisons (>= and <=) on every row:

cost = 1,280 × 1.0 + 100,000 × (0.01 + 2 × 0.0025) = 1,280 + 1,500 = 2,780

EXPLAIN prints exactly Seq Scan on users (cost=0.00..2780.00 ...). The two numbers are the startup cost (before the first row comes out: 0 here) and the total cost (after the last). Startup cost matters when a Limit only wants the first few rows; section 7's slow query turns on exactly that.

An index scan: pages depend on physical order

An index scan pays for the index pages and entries it reads, then one table page fetch per matching row, unless consecutive matches sit on the same page. How often they do depends on the correlation: how closely the table's physical row order follows the column's order, from -1 to 1, measured by ANALYZE. In this database messages.id has correlation 1.00 (messages were inserted in id order) while users.id has -0.03 (rows sit in no useful order) measured. The planner estimates heap pages fetched two ways and interpolates by correlation squared: for no correlation it uses the Mackert and Lohman approximation of how many distinct pages N random fetches touch from a table of T pages, about 2TN/(2T+N) when the table fits in cache, each priced at random_page_cost; for perfect correlation it is the matching fraction of the table read nearly sequentially (one random page, the rest at 1.0) ({{costsize.c, cost_index|https://github.com/postgres/postgres/blob/REL_16_2/src/backend/optimizer/path/costsize.c}}).

A bitmap scan sits between the two: it reads the index, sorts the matching row addresses by page, and then visits each page once in physical order, priced between random and sequential depending on how much of the table it touches. What the three cost, for 20,000 users and for a million messages:

Measured: each path forced in turn with the enable_* switches, serial plans, warm cache, best of three; "pages touched" counts buffer hits plus reads, so a page visited twice counts twice: the index scan pays one visit per row fetched, even when the next row is on the page it just read. Correlation is one number for the whole table; these 20,000 users happen to sit on just 315 of its 1,280 pages (the table was rewritten earlier in its life), which the planner cannot know and which is why the bitmap scan touched so few pages. The planner's ranking matched the stopwatch in both cases, and it chose an index scan for up to 6,000,000 of the 10,000,000 messages because the rows it needs sit together.

Defaults reproduce Postgres's own costs, independently
This page's formulas, transcribed from the PostgreSQL 16.2 source (cost_seqscan, cost_index, index_pages_fetched, cost_bitmap_heap_scan, genericcostestimate, btcostestimate and the histogram code), reproduce 150 of 150 figures that EXPLAIN printed (row estimates, sequential, index and bitmap costs) across 25 ranges on the two tables, to the cent (checked in src/recompute.py). The {{Cost model|#t-cost}} tab runs them live: change the range or any cost setting and watch which plan wins.
What the cost model does not know
Whether a page is already in memory (except through effective_cache_size), how fast your disk really is, what other queries are running, and anything about the data beyond its statistics. It is deliberately crude. Leis and colleagues found on real join queries that the cost model "has much less influence on query performance than the cardinality estimates" ({{How Good Are Query Optimizers, Really?, PVLDB 2015|https://www.vldb.org/pvldb/vol9/p204-leis.pdf}}): get the row counts right and a crude cost model is enough.
