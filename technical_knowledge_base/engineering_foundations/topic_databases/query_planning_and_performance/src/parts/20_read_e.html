7. The slow-query workflow: find, explain, fix, verify

"The app is slow" is not a query. Professionals do not start by staring at the query they suspect; they ask the database which statements consume its time, explain the top one, change one thing, and measure again with the same load. Four steps, each with a standard tool.

Find: pg_stat_statements

pg_stat_statements is an extension shipped with Postgres that keeps running totals for every distinct statement the server executes ({{pg_stat_statements|https://www.postgresql.org/docs/current/pgstatstatements.html}}). It must be loaded at server start (shared_preload_libraries = 'pg_stat_statements', then CREATE EXTENSION pg_stat_statements; in the database). It normalises statements: WHERE chat_id = 42 and WHERE chat_id = 77 become one entry, WHERE chat_id = $1, with calls, total and mean execution time, rows, and pages hit and read, for up to 5,000 statements by default. The question to ask it is which statements use the most total time, because total time is what the server spends and what users wait behind:

SELECT calls, round(total_exec_time) AS total_ms, round(mean_exec_time, 2) AS mean_ms,
       round(100 * total_exec_time / sum(total_exec_time) OVER (), 1) AS pct, query
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

A query that takes 2 ms but runs 50,000 times an hour costs more than a 30-second report run once a day. Sorting by mean time finds the slowest single statements, which is a different question (what users of one page feel).

Explain: get a real plan with real values

pg_stat_statements has no parameter values, only $1. To see the plan you need a real value: from the application's logs, or from Postgres's own logs. Two settings log slow statements: log_min_duration_statement logs the text and duration of any statement slower than a threshold ({{logging settings|https://www.postgresql.org/docs/current/runtime-config-logging.html}}), and the auto_explain extension logs its plan as well ({{auto_explain|https://www.postgresql.org/docs/current/auto-explain.html}}). The plan in a log is the plan that actually ran, at the moment it was slow, which matters for problems that come and go (section 10). The price: with auto_explain.log_analyze on, every statement is timed per node whether or not it is logged, which the documentation warns "can have an extremely negative impact on performance"; turn log_timing off (as here) and sample with auto_explain.sample_rate.


Fix one thing, then verify under the same load


Change one thing (section 8 ranks the options), reset the statistics with SELECT pg_stat_statements_reset();, replay the same load, and compare. Verifying under load catches what a single EXPLAIN cannot: a new index slows every write, and removing the top query moves the bottleneck to the next one.

Why this query was slow, and the two fixes
The search WHERE title LIKE 'Chat 123456%' ORDER BY id LIMIT 10 fell into the Limit trap: the planner estimated 100 matching titles, so walking the primary key in id order and stopping after 10 matches looked cheap (cost 3,780 against sorting all matches). There was one match, so every search read the whole table through the index: 12,053 pages, 91.6 ms in EXPLAIN and 112.9 ms on average under load. An index on title lets LIKE 'prefix%' become a range scan (this database uses the C collation; under other collations create it with text_pattern_ops, {{Operator Classes|https://www.postgresql.org/docs/current/indexes-opclass.html}}): 0.078 ms, about 1,170 times faster for one search, at the price of 31.6 MB and slower inserts into chats. Without an index, a rewrite still helps: ordering by title removes the temptation to walk the primary key, so Postgres scans the table in parallel and sorts the one match: 33 ms instead of 84 ms measured, better but still a full scan per keystroke. A LIKE '%123456%' (a substring, not a prefix) cannot use a B-tree at all; it needs a trigram index ({{pg_trgm|https://www.postgresql.org/docs/current/pgtrgm.html}}), covered on {{Search and vector databases|n:3ef5c17b0d0d815eb4caef9b4cd4d732}}.
