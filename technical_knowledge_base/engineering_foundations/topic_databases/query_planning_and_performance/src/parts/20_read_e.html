6. Reading EXPLAIN like a professional

EXPLAIN shows the chosen plan without running it. EXPLAIN ANALYZE runs the query (so it really inserts, updates or deletes: wrap those in BEGIN; ... ROLLBACK;) and adds what happened ({{EXPLAIN|https://www.postgresql.org/docs/current/sql-explain.html}}; {{Using EXPLAIN|https://www.postgresql.org/docs/current/using-explain.html}}). Plain EXPLAIN shows only estimates, so it cannot show the misestimate that is usually the cause: use EXPLAIN (ANALYZE, BUFFERS) by default (PostgreSQL 18 turns BUFFERS on automatically with ANALYZE).

Other EXPLAIN options worth knowing (SETTINGS, VERBOSE, FORMAT JSON, GENERIC_PLAN, SUMMARY)

SETTINGS (lists settings changed from their defaults, so a plan pasted into a ticket says which work_mem it ran with), VERBOSE (output columns), FORMAT JSON (for {{explain.dalibo.com|https://explain.dalibo.com}} and {{explain.depesz.com|https://explain.depesz.com}}), GENERIC_PLAN (PostgreSQL 16+: the plan for a statement with $1 placeholders) and SUMMARY (planning time).

->  Index Scan using chats_pkey on chats  (cost=0.42..37801.43 rows=100 width=19) (actual time=11.819..91.565 rows=1 loops=1)
      Filter: (title ~~ 'Chat 123456%'::text)

Index Scan using chats_pkey on chats
The node type, the index it walks, the table it reads.
cost=0.42..37801.43
Estimated startup and total cost, in the units of section 2.
rows=100
Estimated rows this node will output (per loop).
width=19
Estimated average bytes per output row.
actual time=11.819..91.565
Milliseconds until the first and the last row, per loop, including everything below this node.
rows=1 loops=1
Actual rows per loop, and how many times the node ran. Total rows = rows × loops; total time is roughly time × loops.
Filter, Rows Removed by Filter
A condition checked on each row after fetching it, and how many rows it threw away; a large number is wasted work. An Index Cond instead would mean the index did the filtering.
Buffers: shared hit=12053
8 KB pages found in Postgres's buffer pool (hit), asked from the operating system (read, which may still come from its memory), modified (dirtied) or written out to make room (written); temp pages are sorts and hashes that spilled (section 9).

This is the hero's node: the planner expected 100 matching titles and, walking the primary key in id order, expected to find the first 10 after about a tenth of the table (cost 3,780 at the Limit above it). There was 1 match, so it read all 1,000,000 rows. The estimate (100) against the actual (1) is the whole diagnosis.

Reading a whole plan

Start at the bottom (the most indented lines) and go up; at each node compare estimated rows with actual rows × loops; the lowest big mismatch is the cause. Step through a real plan from this database: the five London users with the most chats.

Bottom up: the first wrong estimate is the cause, and every node above it inherits the error

Real EXPLAIN (ANALYZE, BUFFERS) output on a copy of users (lab_users) joined to chats, PostgreSQL 16.2, 2026-10-04. Before the fix: Seq Scan on lab_users estimated rows=158 against actual rows=2294; the Nested Loop rows=1580 against 22364; Execution Time 14.364 ms. After CREATE STATISTICS on (country, city): 1,335 estimated per process against 1,147 actual, a parallel plan, 10.566 ms. The same plan is exercise 3 of the {{Plan reading lab|#t-lab}}.

Two more things to read: time and pages (a node's time includes its children, so subtract them, and multiply by loops; pages, unlike milliseconds, do not change between a cold and a warm run, the parent's Query plans case 8), and waste: Rows Removed by Filter in the millions, Heap Fetches on an Index Only Scan (the table was visited after all), Sort Method: external merge or Batches above 1 (spilled), Workers Launched below Workers Planned (no free parallel workers), and Planning Time against Execution Time (for short queries run thousands of times, planning can be most of the cost; section 10).

What measuring costs

EXPLAIN ANALYZE reads the clock twice per row per node. On this laptop a clock read costs 20.6 nanoseconds (pg_test_timing), and SELECT count(*) FROM messages took 432 ms plainly, 722 ms under EXPLAIN ANALYZE and 469 ms with TIMING OFF measured: per-node timing added 67% to a query pushing 10 million rows through two nodes. Row counts and buffers stay exact either way, so use (ANALYZE, BUFFERS, TIMING OFF) when counts are enough, and trust ratios rather than absolute times from a timed plan. The same cost applies to auto_explain (section 7), which is why its log_timing is often switched off.
