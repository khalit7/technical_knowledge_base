3. Statistics: what the planner knows about your data

ANALYZE takes a sample

Every row estimate starts from statistics that the ANALYZE command computes and stores in the catalogue (readable through the pg_stats view; {{Statistics Used by the Planner|https://www.postgresql.org/docs/current/planner-stats.html}}). It does not read the whole table: it reads a random sample of 300 × the statistics target rows, and the target defaults to 100, so about 30,000 rows however big the table is ({{analyze.c|https://github.com/postgres/postgres/blob/REL_16_2/src/backend/commands/analyze.c}}; {{default_statistics_target|https://www.postgresql.org/docs/current/runtime-config-query.html#GUC-DEFAULT-STATISTICS-TARGET}}). For each column it keeps:

n_distinctNumber of distinct values; a negative number is a fraction of the rows (-1 means every row differs)users.country: 20; users.email: -1
most_common_vals, most_common_freqsThe most common values (MCV list), up to the target's count, with the share of rows each hasusers.plan: free 0.8495, pro 0.1410, team 0.0095 (true: 0.8482, 0.1415, 0.0103)

How the numbers become an estimate

For WHERE country = 'GB' the planner finds GB in the MCV list with frequency 0.0699 and multiplies by the row count: 0.0699 × 100,000 = 6,987 estimated; the truth is 6,883 measured. A value not in the list gets an equal share of what the list leaves: (1 − sum of MCV frequencies) / (distinct values − number of MCVs). A range such as tokens < 200 counts the histogram buckets below 200 and assumes values are spread evenly inside the bucket where 200 falls ({{Row Estimation Examples|https://www.postgresql.org/docs/current/row-estimation-examples.html}}; the {{Cost model|#t-cost}} tab reproduces this for a range on id). And when there is nothing to go on, such as a function applied to a column, the planner falls back to fixed guesses: 0.5% of the rows for an equality, a third for an inequality ({{selfuncs.h|https://github.com/postgres/postgres/blob/REL_16_2/src/include/utils/selfuncs.h}}).

Distinct counts are the hardest number to sample

You cannot count distinct values from a sample without guessing how many values the sample missed. Postgres uses an estimator from the sampling literature and it tends to guess low for skewed columns: chats.user_id is stored as 75,971 distinct users when there are 99,945, and messages.chat_id as 872,528 when there are 999,951 measured. Distinct counts drive join estimates (section 4), and Leis and colleagues saw "severe underestimates for large tables" of exactly this statistic (PVLDB 2015, section 3.4). Raising the target enlarges the sample; on a copy of chats:

Sampling is random, so a second run gives slightly different values; at 10,000 the sample is the whole table and the numbers are exact. Set it per column where it matters, rather than globally: ALTER TABLE chats ALTER COLUMN user_id SET STATISTICS 1000; then ANALYZE chats;. The cost is ANALYZE time and a slightly slower planner (longer lists to search).

Statistics go stale

Statistics describe the table at the moment ANALYZE ran. Postgres's background autovacuum process re-analyzes a table after autovacuum_analyze_threshold + autovacuum_analyze_scale_factor × rows have changed, 50 rows plus 10% by default ({{autovacuum settings|https://www.postgresql.org/docs/current/runtime-config-autovacuum.html}}): for a 10-million-row table that is a million changes. A bulk load between two analyses is the classic trap. Measured on a small table (this dataset's tables have autovacuum switched off so that nothing changes behind the measurements):

Before the load

1,000 rows, user 7 owns 1% of them. ANALYZE. Estimate for WHERE user_id = 7: 10, truth 10.

After loading 999,000 rows, mostly user 7's

No ANALYZE yet. The planner sees from the file size that the table grew, so it scales up, but it still believes user 7 owns 1%: estimate 9,100, truth 899,110 measured; it picks a Bitmap Heap Scan.

After ANALYZE

Estimate 901,100, and a Seq Scan. Here both plans took about 47 to 49 ms, because the whole table was in memory; the wrong estimate becomes expensive when this table is joined to another and the planner sizes the join for 9,100 rows.

The routine: run ANALYZE (or VACUUM ANALYZE) right after a bulk load or a large delete, and lower the scale factor per table for big tables that change steadily (ALTER TABLE messages SET (autovacuum_analyze_scale_factor = 0.01)). Since PostgreSQL 18, pg_upgrade keeps statistics across a major upgrade; before it, a freshly upgraded database planned blind until it was analyzed ({{PostgreSQL 18 release notes|https://www.postgresql.org/docs/release/18.0/}}). Vacuum itself belongs to {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}}.

Extended statistics: facts about pairs of columns

Per-column statistics cannot know that every London user is in Great Britain. CREATE STATISTICS adds a statistics object over several columns, of three kinds ({{CREATE STATISTICS|https://www.postgresql.org/docs/current/sql-createstatistics.html}}; {{Multivariate statistics examples|https://www.postgresql.org/docs/current/multivariate-statistics-examples.html}}): dependencies (how strongly one column determines another; here {"city => country": 1.000}), ndistinct (how many distinct combinations exist; here 60, not 20 × 60 = 1,200) and mcv (the most common combinations with their frequencies). Green: within a factor of 1.5 of the truth. Note the second row: functional dependencies only know that city implies country, not which pairs exist, so they make the impossible "GB and Paris" look common (1,813 estimated); the documentation warns that when such conditions are incompatible "the correct estimate would be zero rows, but that possibility is not considered" ({{Statistics Used by the Planner|https://www.postgresql.org/docs/current/planner-stats.html}}). Only the MCV kind knows the pair never occurs. The parent's {{Query plans|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab (case 5) shows the same fix changing a join on 10 million messages. Cost: ANALYZE does more work, and the objects must be created by someone who knows the columns are related; nothing detects that automatically.

4. Why estimates go wrong

Every misestimate on this page comes from one of four places. In each, the planner did the arithmetic right on an assumption that the data broke.

CauseExample on this dataEstimatedActualOff by
1. Independence. Conditions on two columns are multiplied as if unrelated.
GB is 7% of users and London is a third of GB's users but about 2.3% of all users, so the planner computes 0.07 × 0.023 × 100,000, about 160 rows, when every London user is British and the truth is 2,294. The fix is extended statistics (section 3) or, when the columns are really one fact, storing one column.
2. Joins. Errors multiply up the tree, and Postgres has no statistics about join results.
For an equality join the planner estimates matches as rows(A) × rows(B) / max(distinct values on each side), which assumes every value on the smaller side finds partners. A 10 times error at the bottom of a three-join plan can be 1,000 times at the top. Leis and colleagues built the Join Order Benchmark (113 queries over 21 tables of real IMDb data) to measure this in five systems: "all estimators routinely produce large errors", with misestimates "by a factor of 1000 or more" routine, and a systematic tendency to underestimate, which pushes planners toward nested loops that blow up ({{PVLDB 2015|https://www.vldb.org/pvldb/vol9/p204-leis.pdf}}). Underestimates are the dangerous direction: an overestimate wastes a little memory, an underestimate picks an algorithm meant for small inputs.
3. Expressions, patterns and functions. No statistics exist for computed values.
WHERE lower(email) = ... or WHERE created_at::date = ... have no statistics, so the planner uses its fixed guesses (0.5% for an equality). LIKE 'Chat 123456%' is estimated from the histogram plus a guess for the rest of the pattern: 100 rows estimated, 1 real, and that overestimate is what makes section 7's slow query slow. An index on the expression gives the planner statistics for it as well as a fast path; CREATE STATISTICS on a single expression (PostgreSQL 14 and later) collects the statistics without the cost of maintaining an index ({{CREATE STATISTICS|https://www.postgresql.org/docs/current/sql-createstatistics.html}}). Sargability, the rule that an index can only help when the column is left bare, is the parent's Query plans case 3.
4. Unknown parameters. A plan made before the value is known must guess.
A generic plan for WHERE org_id = $1 uses the average share of a non-common value: 290 rows. For the one organisation that owns half the table that is wrong by a factor of 6,897. Section 10 measures what follows.
The habit that finds all four
Run EXPLAIN (ANALYZE, BUFFERS), then walk the plan from the bottom and compare rows= (estimated) with actual rows= × loops at each node. The lowest node where they differ by more than about 10 times is where the plan went wrong; everything above it was planned for the wrong input. Section 6 shows how to read the rest.
