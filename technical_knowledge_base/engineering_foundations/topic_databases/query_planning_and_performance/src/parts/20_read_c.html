3. Statistics: what the planner knows about your data

Every row estimate starts from statistics that ANALYZE computes and stores in the catalogue (the pg_stats view; {{Statistics Used by the Planner|https://www.postgresql.org/docs/current/planner-stats.html}}). It reads a random sample of 300 × the statistics target rows, and the target defaults to 100, so about 30,000 rows however big the table is ({{analyze.c|https://github.com/postgres/postgres/blob/REL_16_2/src/backend/commands/analyze.c}}; {{default_statistics_target|https://www.postgresql.org/docs/current/runtime-config-query.html#GUC-DEFAULT-STATISTICS-TARGET}}). The sample gets common values right, and buckets crowd where values are dense

How the numbers become an estimate

For WHERE country = 'GB' the planner finds GB in the MCV list with frequency 0.0699: 0.0699 × 100,000 = 6,987 estimated; the truth is 6,883 measured. A value not in the list gets an equal share of what the list leaves: (1 − sum of MCV frequencies) / (distinct values − number of MCVs). A range such as tokens < 200 counts the histogram buckets below 200 and assumes values spread evenly inside the bucket where 200 falls ({{Row Estimation Examples|https://www.postgresql.org/docs/current/row-estimation-examples.html}}; the calculator in section 2 reproduces this for a range on id). With nothing to go on, such as a function applied to a column, the planner falls back to fixed guesses: 0.5% of the rows for an equality, a third for an inequality ({{selfuncs.h|https://github.com/postgres/postgres/blob/REL_16_2/src/include/utils/selfuncs.h}}).

Distinct counts are the hardest number to sample

A sample cannot count distinct values without guessing how many it missed, and Postgres's estimator guesses low for skewed columns: chats.user_id is stored as 75,971 distinct users when there are 99,945, and messages.chat_id as 872,528 when there are 999,951 measured. Distinct counts drive join estimates (section 4), and Leis and colleagues saw "severe underestimates for large tables" of exactly this statistic (PVLDB 2015, section 3.4). Raise the target per column where it matters, not globally: ALTER TABLE chats ALTER COLUMN user_id SET STATISTICS 1000; then ANALYZE chats;. The cost is ANALYZE time and a slightly slower planner (longer lists to search).

Statistics go stale

Autovacuum re-analyzes a table after autovacuum_analyze_threshold + autovacuum_analyze_scale_factor × rows have changed, 50 rows plus 10% by default ({{autovacuum settings|https://www.postgresql.org/docs/current/runtime-config-autovacuum.html}}): for a 10-million-row table, a million changes. A bulk load between two analyses is the classic trap, measured on a small table:

Before the load

1,000 rows, user 7 owns 1% of them. ANALYZE. Estimate for WHERE user_id = 7: 10, truth 10.

After loading 999,000 rows, mostly user 7's

No ANALYZE yet. The planner sees from the file size that the table grew and scales up, but still believes user 7 owns 1%: estimate 9,100, truth 899,110 measured; it picks a Bitmap Heap Scan.

After ANALYZE

Estimate 901,100, and a Seq Scan. Both plans took 47 to 49 ms here (the table was in memory); the wrong estimate becomes expensive when a join is sized for 9,100 rows.

So run ANALYZE right after a bulk load or a large delete, and lower the scale factor for big tables that change steadily (ALTER TABLE messages SET (autovacuum_analyze_scale_factor = 0.01)). Since PostgreSQL 18, pg_upgrade keeps statistics across a major upgrade; before it, a freshly upgraded database planned blind until analyzed ({{PostgreSQL 18 release notes|https://www.postgresql.org/docs/release/18.0/}}). Vacuum itself belongs to {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}}.

Extended statistics: facts about pairs of columns

Per-column statistics cannot know that every London user is in Great Britain. CREATE STATISTICS adds an object over several columns, of three kinds ({{CREATE STATISTICS|https://www.postgresql.org/docs/current/sql-createstatistics.html}}; {{Multivariate statistics examples|https://www.postgresql.org/docs/current/multivariate-statistics-examples.html}}): dependencies (how strongly one column determines another; here {"city => country": 1.000}), ndistinct (how many distinct combinations exist; here 60, not 20 × 60 = 1,200) and mcv (the most common combinations with their frequencies). Each fixes a different query; on a copy of users, estimated rows against the truth measured:

Green: within a factor of 1.5 of the truth. Dependencies know only that city implies country, not which pairs exist, so they make the impossible "GB and Paris" look common (1,813 estimated; for such incompatible conditions "the correct estimate would be zero rows, but that possibility is not considered", says the documentation). Only the MCV kind knows the pair never occurs. The parent's {{Query plans|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab (case 5) shows the same fix changing a join on 10 million messages. Nothing detects related columns automatically: someone must create the object.

4. Why estimates go wrong

Every misestimate on this page comes from one of four places. In each, the planner did the arithmetic right on an assumption the data broke.

Five estimates from this database: the gap between the dot the planner believed and the dot that happened

Rows on a log scale. Independence: users in GB and London, estimated 165, actual 2,294. Pattern: titles LIKE 'Chat 123456%', 100 against 1. Stale statistics: after a bulk load, 9,100 against 899,110. Join: London users joined to their chats (the Plan reading lab), 1,580 against 22,364. Unknown parameter: the generic plan for the enterprise organisation, 290 against 2,000,231, off by a factor of 6,897.

  1. Independence. Conditions on two columns are multiplied as if unrelated. GB is 7% of users and London about 2.3% of all users, so the planner computes 0.07 × 0.023 × 100,000, about 160 rows, when every London user is British and the truth is 2,294. Fix: extended statistics (section 3), or, when the columns are really one fact, one column.
  2. Joins. Errors multiply up the tree, and Postgres keeps no statistics about join results. For an equality join it estimates rows(A) × rows(B) / max(distinct values on each side), assuming every value on the smaller side finds partners. A 10 times error at the bottom of a three-join plan can be 1,000 times at the top. Leis and colleagues built the Join Order Benchmark (113 queries over 21 tables of real IMDb data) to measure this in five systems: "all estimators routinely produce large errors", misestimates "by a factor of 1000 or more" were routine, and the systematic tendency is to underestimate ({{PVLDB 2015|https://www.vldb.org/pvldb/vol9/p204-leis.pdf}}). Underestimates are the dangerous direction: an overestimate wastes a little memory, an underestimate picks an algorithm meant for small inputs, usually a nested loop that blows up.
  3. Expressions, patterns and functions. WHERE lower(email) = ... or WHERE created_at::date = ... have no statistics, so the planner uses its fixed guesses. LIKE 'Chat 123456%' is estimated from the histogram plus a guess for the rest of the pattern: 100 rows against 1 real, the overestimate that makes section 7's search slow. An index on the expression gives the planner statistics as well as a fast path; CREATE STATISTICS on a single expression (PostgreSQL 14 and later) collects the statistics without maintaining an index. Sargability, the rule that an index helps only when the column is left bare, is the parent's Query plans case 3.
  4. Unknown parameters. A plan made before the value is known must guess: a generic plan for WHERE org_id = $1 uses the average share of a non-common value, 290 rows, which for the one organisation owning half the table is wrong by 6,897 times. Section 10 measures what follows.
The habit that finds all four
Run EXPLAIN (ANALYZE, BUFFERS), walk the plan from the bottom and compare rows= (estimated) with actual rows= × loops at each node. The lowest node where they differ by more than about 10 times is where the plan went wrong; everything above it was planned for the wrong input. Section 6 steps through a real plan this way.
