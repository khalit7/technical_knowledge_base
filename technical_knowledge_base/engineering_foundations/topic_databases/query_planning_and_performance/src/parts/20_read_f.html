8. The fixes, in the order to try them

Once the plan shows the cause, the fix usually comes from this list, roughly in order of how often it is the answer and how little it risks. For each: the problem it solves, how, what it costs, and when not to use it.

1. An index, or a better one

Problem: the query reads far more rows than it returns (large Rows Removed by Filter, a Seq Scan feeding a small result). How: a B-tree on the columns the query filters, joins or sorts on ({{Indexes|https://www.postgresql.org/docs/current/indexes.html}}). Four variations matter: a composite index on several columns, equality columns first and the range or sort column last (the parent's Query plans case 2); an expression index such as ON users (lower(email)) (case 3); a partial index with a WHERE clause, such as ON jobs (created_at) WHERE status = 'pending', small because it covers only the rows the query wants ({{Partial Indexes|https://www.postgresql.org/docs/current/indexes-partial.html}}); and a covering index, ON chats (user_id) INCLUDE (title), which can answer from the index alone (an Index Only Scan, case 7; {{Index-Only Scans and Covering Indexes|https://www.postgresql.org/docs/current/indexes-index-only-scans.html}}). Cost: space (the title index: 31.6 MB for a million rows, built in 1.4 s measured), and every insert, and every update of an indexed column, now writes one more structure. When not: on columns where most rows match, on tables that are written far more than read, and twice on the same columns; find unused ones with pg_stat_user_indexes.idx_scan = 0 over a full business cycle. In production build with CREATE INDEX CONCURRENTLY, which does not block writes (operations belong to {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}}; index structures to {{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}}).

2. Rewrite the query

Problem: the SQL asks for something the planner cannot do cheaply, or hides information from it. The rewrites that come up again and again:

  • Leave indexed columns bare: created_at >= '2026-03-01' AND created_at < '2026-03-02', not created_at::date = '2026-03-01' (case 3).
  • Avoid the Limit trap: ORDER BY x LIMIT n with a rare filter on another column (section 7).
  • Paginate by key, not by OFFSET: WHERE (created_at, id) < (:t, :id) ORDER BY created_at DESC, id DESC LIMIT 20 seeks straight to the page; OFFSET 100000 reads and discards 100,000 rows. Measured on {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}: the key-based ("cursor" or "keyset") page stayed at 0.02 to 0.05 ms from the first page to a million rows deep, while OFFSET grew in proportion to the depth.
  • Replace a per-row subquery with a join: a SubPlan with loops= in the thousands runs once per outer row; a join or LEFT JOIN LATERAL runs once (the {{Plan reading lab|#t-lab}} has one).
  • NOT EXISTS, not NOT IN, for "rows with no match": NOT IN returns nothing if the subquery yields a NULL, and it cannot be planned as an anti-join ({{Subquery Expressions|https://www.postgresql.org/docs/current/functions-subquery.html}}).
  • Select the columns you need: fewer columns make rows narrower and allow index-only scans.

Cost: developer time and the risk of changing results; test that the rewritten query returns the same rows. When not: when the plan is fine and the time is elsewhere (the application, the network).

3. Give the planner better statistics

Section 3: ANALYZE after bulk changes, a higher target on skewed columns, extended statistics for related columns, an expression index or expression statistics for computed predicates. Cheap and safe; it fixes estimates, not missing access paths.

4. Change how the application talks to the database

Many "slow database" problems are an application making too many round trips. Two patterns, measured from Python (psycopg 3.3.6) over TCP on the same laptop, the cheapest round trip there is (0.056 ms for SELECT 1):

The N+1 pattern is what an object-relational mapper (ORM: a library such as SQLAlchemy, Django's ORM or ActiveRecord that maps tables to classes) does with lazy loading: one query for a user's 20 chats, then one more query per chat for its last message, 21 round trips. One query with LEFT JOIN LATERAL returns the same 20 rows. On one machine that was 1.42 ms against 0.22 ms per page, 6.5 times; across a network each extra round trip adds its full latency, and the Numbers to know tab of {{Topic: swe-and-system-design|n:3c65c17b0d0d81048ae0dd14ac399b4d}} works the same 21 queries at a 2 ms zone-to-zone round trip into 43 ms. ORMs have a switch for it (eager loading: selectinload or joinedload in SQLAlchemy, select_related and prefetch_related in Django); turn on query logging in development to see the counts. Batching is the same idea for writes: 10,000 single-row INSERTs each in its own transaction took 1,391 ms; the same rows by COPY took 7.0 ms, 199 times faster, with multi-row INSERT and arrays in between. Each commit waits for the log to reach disk (the parent page, section 4), and each statement is a round trip.

Cost: code changes; larger batches hold locks longer and fail as a unit. When not: for genuinely interactive single-row work.

5. Settings, then hardware, last

Section 9. A setting changes every query on the server, so it fixes one query only by accident and can break others; hardware multiplies whatever the queries do, including the waste. Both come after the query is right.
