Cost model: price three plans by hand, the way Postgres does

The planner chose among a sequential scan, an index scan and a bitmap scan for a range query by computing three numbers. This tab computes the same three numbers from the same inputs, read from the real tables: the page and row counts in pg_class, the index size and B-tree height, and the column's histogram and correlation in pg_stats. With the default settings it reproduces every cost PostgreSQL 16.2 printed for these queries, to the cent (150 of 150 figures, checked in src/recompute.py). Explained step by step in Reading, {{section 2|#t-read}}.

Try: drag "rows wanted" and watch the winner change at the crossover. On users, set the correlation to 1 (as if the table were sorted by id) and the index scan wins far longer. Set random_page_cost to 1.1 and the crossover moves. Lower work_mem to 64 kB on messages and the bitmap goes lossy.

Measured: did the cheapest cost run fastest?

Each path forced in turn (enable_seqscan, enable_indexscan, enable_bitmapscan switched off for the others), serial plans (max_parallel_workers_per_gather = 0), warm cache, best of three, measured 2026-10-04 on PostgreSQL 16.2, Apple M1 Pro. Green: fastest. Pages: buffer hits plus reads at the scan node, so a page visited twice counts twice. Statistics as stored when measured (users' id correlation -0.03 although the rows sit in long runs; see Reading, section 2).

What the inputs are

Simplifications, all of which also hold for the measured queries: one table, one range condition on an indexed bigint column, no NULLs, both ends of the range inside the histogram (the planner looks up the real minimum and maximum through the index when a bound falls in the first or last bucket, which this calculator does not), serial plans. Parallel plans divide CPU costs among workers and add parallel_setup_cost and parallel_tuple_cost.
