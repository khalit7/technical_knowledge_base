The idea in one screen

The planner never runs the alternatives: it predicts how many rows each step will produce from a sampled summary of your data, prices each candidate plan from those row estimates, and runs the cheapest. So a slow query is almost always a wrong estimate, a missing access path, or an application asking the wrong way, and the diagnosis starts by putting the estimated rows next to the actual rows.

One slow search: where the prediction is made, and where EXPLAIN ANALYZE shows it broke

The chat product's title search from section 7, a real plan on PostgreSQL 16.2. The planner believed 100 titles match 'Chat 123456%', so walking the primary key in id order and stopping after 10 matches looked cheap. 1 title matched, so it read all 1,000,000 chats: 999,999 rows removed by the filter, 12,053 pages, 91.6 ms. 1. What a planner does

SELECT * FROM messages WHERE chat_id = 42 ORDER BY created_at says nothing about which file to open, whether to use an index, or in what order to work. SQL is declarative: it describes the result. A chain of components turns it into steps, the same in every relational database ({{The Path of a Query|https://www.postgresql.org/docs/current/query-path.html}}):

ParseCheck the grammar and build a tree of the statement.
AnalyseLook up every name: which table is messages, which type is chat_id.
RewriteReplace views by the queries that define them and apply rules.
PlanEnumerate ways to run it, estimate the cost of each, keep the cheapest.
ExecuteRun the chosen plan and stream rows back.

The plan is a tree of nodes. The leaves read data: a Seq Scan reads every page of a table in order; an Index Scan walks an index and fetches each matching row; a Bitmap Heap Scan collects matching row addresses from an index, then reads their pages in physical order; an Index Only Scan answers from the index without touching the table. Nodes above combine rows: the three join algorithms (section 5), Sort, Aggregate, Limit. Each node asks its child for the next row, so a Limit at the top can stop the whole tree early.

The planner cannot try the plans; running them would cost more than the query. For each candidate it estimates each node's cardinality and the cost that follows (section 2), from statistics about the data (section 3), and for joins it searches the explosion of orders cleverly (section 5). Planning takes about a millisecond for the queries on this page, and 1.6 seconds for one 16-table join measured. Every bad plan on this page is a correct choice made on a wrong estimate, or on a cost model that does not match the machine.
