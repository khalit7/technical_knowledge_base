The whole page in one screen

About 45 minutes to read (10,300 words; the glossary and the collapsed boxes can be skipped), plus the animations. It starts from zero: every term is explained where it first appears and collected in the Glossary. Numbers marked measured were measured for this page on PostgreSQL 16.2 on an Apple M1 Pro laptop (10 cores, 16 GB) with the parent page's chat data; numbers marked illustrative are made up to show a shape. Timings on a laptop shared with other work vary from run to run; each is the best of three unless the text says otherwise, and the page counts (which do not vary) are the more reliable measure.

SQL says what you want, never how to get it. A part of the database called the planner chooses the how, by guessing how much work each possible recipe would take. Most slow queries are a bad guess, a missing index, or an application that asks the database the wrong way; a four-step routine finds which.

The running example is the chat product from the parent page, {{Topic: databases|n:3cd5c17b0d0d815d8841ec845f5f3324}}: 100,000 users, 1,000,000 chats and 10,000,000 messages in one PostgreSQL ("Postgres") database of about 4 GB, generated by the parent's scripts so every number agrees with its {{Query plans|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab. That tab already shows eight measured cases (sequential against index scan, column order in an index, functions that hide a column, the three join algorithms, a misestimate fixed by extended statistics, Postgres against DuckDB, index-only scans and VACUUM, cold against warm cache). This page does not repeat them; it explains the machinery underneath and the routine around it, and adds one table of billing events for section 10.
