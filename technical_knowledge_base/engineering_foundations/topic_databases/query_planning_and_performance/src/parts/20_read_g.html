9. The settings that matter

This PostgreSQL 16.2 server has 384 settings (SELECT count(*) FROM pg_settings, extensions included); a handful decide query performance. All are documented under {{Resource Consumption|https://www.postgresql.org/docs/current/runtime-config-resource.html}} and {{Query Planning|https://www.postgresql.org/docs/current/runtime-config-query.html}}; the server-wide ones live in postgresql.conf (or a managed service's parameter group), and most can also be set per database, per role, per session or per transaction (SET LOCAL).

work_mem, and what a spill costs

A sort or hash that needs more than work_mem writes partial results to temporary files and reads them back: the Sort becomes external merge, the Hash and HashAggregate split into Batches. Measured on three queries at five settings (serial plans, best of three):

The penalty here, 1.1 to 1.7 times at the default 4 MB, is smaller than folklore suggests because the temporary files never left the operating system's memory on a laptop with free RAM and a fast SSD; on network-attached cloud disks or a memory-starved server it is larger. The bigger danger is the other direction. work_mem is per operation, per process: the documentation warns that "the total memory used could be many times the value of work_mem". A query with three sorts, run by 200 connections at 256 MB each, could ask for 150 GB. So keep the default modest, raise it where it pays (ALTER ROLE reporting SET work_mem = '256MB', or SET LOCAL inside one transaction), and find spills with log_temp_files = 0 or pg_stat_statements' temp_blks_written.

random_page_cost on SSDs

Correction to the old page
The old page said a random_page_cost of 4 "pushes the planner towards sequential scans" on NVMe and that 1.1 "is the common setting". The default is 4.0, but the current documentation gives no SSD value: it explains that 4 is already low because "the majority of random accesses to storage, such as indexed reads, are assumed to be in cache", and suggests lowering it when the data is likely to be fully cached or network latency is high ({{random_page_cost|https://www.postgresql.org/docs/current/runtime-config-query.html#GUC-RANDOM-PAGE-COST}}). 1.1 is a widespread practice, not a documented standard. The parent's Query plans case 4 shows 1.1 changing a real plan; the {{Cost model|#t-cost}} tab lets you watch the crossover move. Change it only with before and after measurements across the whole workload.

Parallel query

For a big scan, Postgres can start parallel workers, extra processes that each scan part of the table, with a Gather node combining their rows ({{How Parallel Query Works|https://www.postgresql.org/docs/current/how-parallel-query-works.html}}). The planner picks the number of workers from the table size: one worker for a table of min_parallel_table_scan_size (8 MB), one more each time the table triples ({{allpaths.c|https://github.com/postgres/postgres/blob/REL_16_2/src/backend/optimizer/path/allpaths.c}}). For the 1.5 GB messages table that is 5, capped by max_parallel_workers_per_gather:

Parallelism does not reduce the work, it splits it: six processes (five workers and the leader) shared the scan and finished 4.6 times sooner, using six cores to do it. That is right for one big report and wrong for a server already busy with hundreds of small queries, where workers just compete for the same cores. Queries that write data or lock rows never run in parallel ({{When Can Parallel Query Be Used?|https://www.postgresql.org/docs/current/when-can-parallel-query-be-used.html}}), and workers come from a fixed pool (max_worker_processes, max_parallel_workers, 8 each by default), so Workers Launched can be lower than planned at busy times.

JIT compilation

Since PostgreSQL 11 the server can compile a query's expressions to machine code with LLVM, on by default since version 12; it triggers when the estimated cost exceeds jit_above_cost (100,000), with more aggressive inlining and optimisation above 500,000 ({{JIT decision|https://www.postgresql.org/docs/current/jit-decision.html}}). The documentation's own caveat: "for short queries the added overhead of performing JIT compilation will often be higher than the time it can save". Because the threshold is a cost, not a time, a fast query with a large estimated cost (a misestimate, or a big table scanned with a Limit) can pay compilation on every run; that shows up as a JIT: block at the end of EXPLAIN ANALYZE with its timings, and the usual fix for transactional workloads is jit = off for the application's role. Not measured here: the server build used for this page has no LLVM (pg_jit_available() returns false).
