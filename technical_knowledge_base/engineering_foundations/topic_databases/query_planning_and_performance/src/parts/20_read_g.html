8. The fixes, in the order to try them

Once the plan shows the cause, the fix usually comes from this list, in order of how often it is the answer and how little it risks.

1. An index, or a better one

When: the query reads far more rows than it returns (large Rows Removed by Filter, a Seq Scan feeding a small result). How: a B-tree on the columns it filters, joins or sorts on ({{Indexes|https://www.postgresql.org/docs/current/indexes.html}}), in four variations: a composite index, equality columns first and the range or sort column last (the parent's Query plans case 2); an expression index such as ON users (lower(email)) (case 3); a partial index such as ON jobs (created_at) WHERE status = 'pending', small because it covers only the rows the query wants ({{Partial Indexes|https://www.postgresql.org/docs/current/indexes-partial.html}}); and a covering index, ON chats (user_id) INCLUDE (title), which can answer from the index alone (an Index Only Scan, case 7; {{Index-Only Scans and Covering Indexes|https://www.postgresql.org/docs/current/indexes-index-only-scans.html}}). Cost: space (the title index: 31.6 MB for a million rows, built in 1.4 s measured), and every insert, and every update of an indexed column, writes one more structure. Not: where most rows match, on tables written far more than read, or twice on the same columns (find unused ones with pg_stat_user_indexes.idx_scan = 0 over a business cycle). Build with CREATE INDEX CONCURRENTLY in production. Index structures are {{Storage engines and indexes|n:3cd5c17b0d0d8102bc1fd11b22606e1a}}'s subject.

2. Rewrite the query

The SQL asks for something the planner cannot do cheaply, or hides information from it. The rewrites that come up again and again:

  • Leave indexed columns bare: created_at >= '2026-03-01' AND created_at < '2026-03-02', not created_at::date = '2026-03-01' (case 3).
  • Avoid the Limit trap: ORDER BY x LIMIT n with a rare filter on another column (section 7).
  • Replace a per-row subquery with a join: a SubPlan with loops= in the thousands runs once per outer row; a join or LEFT JOIN LATERAL runs once (the {{Plan reading lab|#t-lab}} has one).
  • NOT EXISTS, not NOT IN, for "rows with no match": NOT IN returns nothing if the subquery yields a NULL, and it cannot be planned as an anti-join ({{Subquery Expressions|https://www.postgresql.org/docs/current/functions-subquery.html}}).
  • Select the columns you need: narrower rows, and index-only scans become possible.
  • Paginate by key, not by OFFSET, below.

Test that a rewrite returns the same rows.

Pagination: OFFSET reads every row it skips

ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 500000 makes the database produce 500,020 rows and throw 500,000 away. A keyset (cursor) page remembers the last row's sort key instead and seeks straight to it: WHERE (created_at, id) < (:t, :id) ORDER BY created_at DESC, id DESC LIMIT 20, with an index on (created_at, id). Predict the cost of page 25,001 under each, then look:

OFFSET grows in proportion to the depth; a keyset page costs the same at every depth

One 20-row page from a 1,000,000-row table, PostgreSQL 16.2, EXPLAIN (ANALYZE, BUFFERS) execution time, median of 7 runs, warm cache, 2026-10-04 on an Apple M1 Pro, recorded by the {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}} page's script. At depth 500,000: OFFSET 98.1 ms and 17,544 pages, keyset 0.032 ms and 4 pages; the keyset page stayed between 0.023 and 0.044 ms from the first page to a million rows deep, an index descent of a few pages. The cost of OFFSET is linear in the rows skipped: 98.1 ms / 500,000 rows, about 0.2 microseconds a row here (derived).

The trade: a keyset page cannot jump to page 7, and the sort key must be unique (add the id as a tiebreaker). How the API exposes it (opaque cursors, filters that change between pages) belongs to {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}}.

3. Give the planner better statistics

Section 3: ANALYZE after bulk changes, a higher target on skewed columns, extended statistics for related columns, an expression index or expression statistics for computed predicates. Cheap and safe; it fixes estimates, not missing access paths.

4. Change how the application talks to the database

Many "slow database" problems are too many round trips. Measured from Python (psycopg 3.3.6) over TCP on the same laptop, the cheapest round trip there is (0.056 ms for SELECT 1):

Round trips, not queries, are the cost: 21 queries against 1, and 10,000 inserts six ways

N+1 is what an ORM (SQLAlchemy, Django's ORM, ActiveRecord) does with lazy loading: one query for a user's 20 chats, then one per chat for its last message, 21 round trips, where one query with LEFT JOIN LATERAL returns the same 20 rows. On one machine: 1.42 ms against 0.22 ms per page, 6.5 times; across a network each extra trip adds its full latency, and the Numbers to know tab of {{Topic: swe-and-system-design|n:3c65c17b0d0d81048ae0dd14ac399b4d}} works the same 21 queries at a 2 ms zone-to-zone round trip into 43 ms. The fix is eager loading (selectinload or joinedload in SQLAlchemy, select_related and prefetch_related in Django); N+1 is invisible in the code that causes it, so count queries per request with SQL logging on in development. Structuring the handler is {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}'s subject. Batching is the same idea for writes: 10,000 single-row INSERTs, each its own transaction, took 1,391 ms; COPY took 7.0 ms, 199 times faster, because each commit waits for the log to reach disk and each statement is a round trip. Larger batches hold locks longer and fail as a unit.

Connections: a pool, not more connections

Each Postgres connection is an operating-system process, so opening one costs a process start and authentication. Measured on {{Running Postgres in production|n:3ef5c17b0d0d8149a0c9d3e2083ed0de}} with pgbench, 8 clients running SELECT 1:

A new connection per transaction costs 53 times the throughput; a pooler recovers part of it

PostgreSQL 16.2 and PgBouncer 1.24.1 on the same Apple M1 Pro, 2026-10-05; "new connection each time" is pgbench -C: connect, one query, disconnect, which is what an application without a pool, or a serverless function, does. Direct: 87,487 against 1,660 transactions a second; through PgBouncer: 32,093 against 9,337 (the extra hop costs on persistent connections, and saves the process start on new ones).

The second question is how many connections should be active at once. Beyond roughly the core count, more concurrent queries add contention for CPU, locks and the buffer pool, not throughput: latency rises while throughput stays flat. The PostgreSQL wiki's starting point is about (2 × CPU cores) + number of disks active connections ({{Number Of Database Connections|https://wiki.postgresql.org/wiki/Number_Of_Database_Connections}}; a point to measure from, not a law); Andres Freund found the cost of many connections was CPU, every snapshot scanning the list of connections, which PostgreSQL 14 made much cheaper ({{Analyzing the limits of connection scalability in Postgres|https://techcommunity.microsoft.com/blog/adforpostgresql/analyzing-the-limits-of-connection-scalability-in-postgres/1757266}}). So: a small pool per application process behind a pooler in transaction mode, with excess requests waiting in the pool's queue (on the same page, 1,000 clients through PgBouncer reached Postgres as 20 server connections). Pool sizing with Little's law is on {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}}; PgBouncer's modes and how transaction pooling breaks session state, on Running Postgres in production.

5. Settings, then hardware, last

Section 9. A setting changes every query on the server, so it fixes one query only by accident; hardware multiplies whatever the queries do, waste included. Both come after the query is right.
