5. Join order: a search problem

With two tables the planner compares a handful of plans: which table is outer, which of the three join algorithms, which access path for each side. Every extra table multiplies the choices. With n tables there are n! orders for a simple chain of joins (3,628,800 for ten) and more if intermediate results may themselves be joined ("bushy" trees). Trying them one by one is impossible, so since IBM's System R (Selinger and colleagues, {{Access Path Selection in a Relational Database Management System, SIGMOD 1979|https://dl.acm.org/doi/10.1145/582095.582099}}) planners use dynamic programming: find the cheapest way to join every pair, keep it, then build the cheapest plan for every set of three from the kept pairs, and so on. That turns the factorial into "only" exponential, because it still visits every subset of tables that the query's join conditions connect.

Postgres runs this near-exhaustive search while the query has fewer than geqo_threshold (12 by default) items in its FROM list. From 12 on it switches to GEQO, the genetic query optimizer, which treats join order like the travelling salesman problem: it encodes orders as strings such as 4-1-3-2, breeds and mutates a population of them, and keeps the cheapest it finds in a fixed budget ({{GEQO in PostgreSQL|https://www.postgresql.org/docs/current/geqo-pg-intro.html}}). It is randomised: the result depends on geqo_seed and need not be the best plan.

Two subtleties trip people up. First, explicit JOINs are only reordered in groups of 8: join_collapse_limit and from_collapse_limit (8 by default) stop the planner from flattening longer chains of JOIN ... ON or nested subqueries into one search, so a 14-table query written with JOIN syntax is planned as smaller searches whose boundaries follow how you wrote it, and GEQO never runs; written as a comma-separated FROM list it is one search of 14 items and GEQO does ({{Controlling the Planner with Explicit JOIN Clauses|https://www.postgresql.org/docs/current/explicit-joins.html}}). Second, exhaustive is not the same as right: the search is only as good as its row estimates, which section 4 showed can be off by 1,000 times on joins. Leis and colleagues still found exhaustive dynamic programming beat heuristic search on their benchmark, despite the bad estimates.

6. Reading EXPLAIN like a professional

EXPLAIN shows the plan the planner chose without running it. EXPLAIN ANALYZE runs the query (so it really inserts, updates or deletes: wrap those in BEGIN; ... ROLLBACK;) and adds what happened ({{EXPLAIN|https://www.postgresql.org/docs/current/sql-explain.html}}; {{Using EXPLAIN|https://www.postgresql.org/docs/current/using-explain.html}}). Use EXPLAIN (ANALYZE, BUFFERS) by default; PostgreSQL 18 turns BUFFERS on automatically with ANALYZE. Other options worth knowing: SETTINGS (lists settings changed from their defaults, so a plan pasted into a ticket says which work_mem it ran with), VERBOSE (output columns), FORMAT JSON (for tools such as {{explain.dalibo.com|https://explain.dalibo.com}} and {{explain.depesz.com|https://explain.depesz.com}}), GENERIC_PLAN (PostgreSQL 16 and later: the plan for a statement with $1 placeholders, without values), and SUMMARY (planning time).

This one node is section 7's slow query: the planner expected 100 matching titles and, walking the primary key in id order, expected to find the first 10 after about a tenth of the table (cost 3,780 at the Limit above it). There was 1 match, so it read all 1,000,000 rows to find it. The estimate on the node (100) against the actual (1) is the whole diagnosis.

Reading a whole plan

  1. Start at the bottom (the most indented lines) and go up: children produce rows for their parents.
  2. Find the time. Each node's time includes its children; subtract them to see what the node itself cost. Multiply by loops on the inner side of a nested loop.
  3. Compare estimated and actual rows at each node (section 4's habit). The lowest big mismatch is the cause.
  4. Count pages in Buffers: pages are the work, and unlike milliseconds they do not change between a cold and a warm run (the parent's Query plans case 8 shows the same query at three cache temperatures).
  5. Look for waste: Rows Removed by Filter in the millions, Heap Fetches on an Index Only Scan (the table had to be visited after all), Sort Method: external merge or Batches greater than 1 (spilled to disk), Workers Launched fewer than Workers Planned (no free parallel workers).
  6. Check Planning Time against Execution Time: for short queries run thousands of times, planning can be most of the cost (section 10).

What measuring costs

EXPLAIN ANALYZE reads the clock twice per row per node, and that is not free. On this laptop the clock costs 20.6 nanoseconds a read (pg_test_timing), and SELECT count(*) FROM messages took 432 ms plainly, 722 ms under EXPLAIN ANALYZE, and 469 ms with TIMING OFF measured: per-node timing added 67% to a query that pushes 10 million rows through two nodes. Row counts and buffers stay exact either way, so use (ANALYZE, BUFFERS, TIMING OFF) when you only need counts, and trust ratios rather than absolute times from a timed plan. The same cost applies to auto_explain in section 7, which is why its log_timing is often switched off.
