5. Joins: three algorithms, and the order to join in

Postgres has three join algorithms and prices all three ({{Planner/Optimizer|https://www.postgresql.org/docs/current/planner-optimizer.html}}). On the chat data, the planner's choice against the next best plan once that choice is switched off measured:

Each algorithm wins where its shape fits: a small outer side, two big unsorted inputs, two inputs already sorted

Nested loop

For each outer row, look up its partners on the inner side, ideally through an index. Wins when the outer side is small. One user's 25 chats with message counts: 25 lookups in the (chat_id, created_at) index, 112 pages, 0.227 ms; forced to hash, all 10 million messages stream past the 25 chats: 192,491 pages, 383 ms.

Hash join

Build a hash table from the smaller input (in work_mem × hash_mem_multiplier), stream the bigger one past it once. Wins when both sides are large and unsorted. All 1,000,000 chats with their users, counted by country: 10,644 pages, 95.4 ms; as a nested loop, 1,000,000 lookups into users (a Memoize node caching repeats): 1,077,750 page visits, 352 ms.

Merge join

Walk two inputs sorted on the join key side by side, like a zipper. Wins when both are already sorted (by an index or an earlier sort), and can stop early under a Limit. The first 1,000 chats in id order with message counts: 48 pages, 1.53 ms; forced to a nested loop, 1,003 separate index descents, 3,053 pages, 2.18 ms.

Measured by the parent's {{Query plans|n:3cd5c17b0d0d815d8841ec845f5f3324}} tab (case 4) on the same data, PostgreSQL 16.2, Apple M1 Pro, 2026-10-04, median of 5 runs; pages are buffer hits plus reads over the whole plan. Forced with SET enable_nestloop = off (or enable_hashjoin, enable_mergejoin): diagnostic switches for a session, never a production fix, since they make that plan type look absurdly expensive for every query. In the sorted case both plans stop after 1,000 chats, so the gap is small; the planner had costed them at 604 and 1,006.

The planner chooses between them on row estimates, which is where section 4 bites: an underestimated outer side makes a nested loop look cheap, and the inner side then runs once per real outer row. In EXPLAIN that shows as an inner node with loops= in the thousands or millions (section 10 has one with 2,000,231).

Join order is a search

With n tables there are n! orders for a simple chain of joins (3,628,800 for ten), more if intermediate results may themselves be joined ("bushy" trees). Since IBM's System R (Selinger and colleagues, {{Access Path Selection in a Relational Database Management System, SIGMOD 1979|https://dl.acm.org/doi/10.1145/582095.582099}}) planners use dynamic programming: find the cheapest way to join every pair, keep it, build the cheapest plan for every set of three from the kept pairs, and so on. That turns the factorial into "only" exponential, because it still visits every subset of tables the join conditions connect.

Postgres runs this near-exhaustive search while the FROM list has fewer than geqo_threshold (12) items. From 12 on it switches to GEQO, which treats join order like the travelling salesman problem: it encodes orders as strings such as 4-1-3-2, breeds and mutates a population of them, and keeps the cheapest found in a fixed budget ({{GEQO in PostgreSQL|https://www.postgresql.org/docs/current/geqo-pg-intro.html}}). It is randomised (the result depends on geqo_seed) and need not find the best plan.

Exhaustive planning time explodes with tables; GEQO stays flat

When to act: generated queries joining 12 or more tables (ORMs, BI tools). Read the planning time in EXPLAIN's summary; raise geqo_threshold only if planning stays affordable, or split the query.

Two subtleties: JOIN syntax limits the search, and exhaustive is not the same as right (depth)

Explicit JOINs are reordered only in groups of 8. join_collapse_limit and from_collapse_limit (8 by default) stop the planner from flattening longer chains of JOIN ... ON or nested subqueries into one search, so a 14-table query written with JOIN syntax is planned as smaller searches whose boundaries follow how you wrote it, and GEQO never runs; written as a comma-separated FROM list it is one search of 14 items and GEQO does ({{Controlling the Planner with Explicit JOIN Clauses|https://www.postgresql.org/docs/current/explicit-joins.html}}).

Exhaustive is not the same as right. The search is only as good as its row estimates, which can be off by 1,000 times on joins. Leis and colleagues still found exhaustive dynamic programming beat heuristic search on their benchmark, despite the bad estimates.
