The idea in one screen

SSH is one encrypted TCP connection in which the server first proves who it is with its host key, you then prove who you are with a key or certificate, and any number of independent channels (a shell, a file copy, a tunnel) then share that pipe. Every cluster pattern on this page is a way of nesting or reusing those channels: ProxyJump runs a second, end-to-end SSH session inside a channel of the first, ControlMaster lets later commands open channels on a pipe that is already authenticated, and port forwarding carries TCP connections as channels.

Fig. 1 builds one login, ssh bastion true, from the bottom up, with the sizes the lab recorded (default key exchange, laptop OpenSSH 10.3p1 to bastion OpenSSH 10.5p1). The lab: a laptop, a bastion published on 127.0.0.1:30922, and two compute nodes on an internal network the laptop cannot route to (gpu-node-01 runs a token-protected stand-in for Jupyter; gpu-node-02 plays an old login node).

  1. One TCP connection. Everything rides one TCP connection to port 22: lose it and every channel goes with it.
  2. Hello, in the clear. Each side sends its identification string (SSH-2.0-OpenSSH_10.3, SSH-2.0-OpenSSH_10.5) and a KEXINIT listing what it supports (1672 and 1040 bytes). Anyone on the path can read all of it (section 1).
  3. Key exchange and the host key. The laptop sends a fresh public value (1232 bytes for the post-quantum hybrid); the bastion replies with its own, its host key and a signature over the exchange (1280 bytes). The laptop checks the host key against known_hosts (sections 3 and 4).
  4. NEWKEYS: encryption on. Both sides switch keys; from here an observer sees only sizes: 888 bytes up and 2040 down for the rest of this login.
  5. User authentication, inside. The laptop signs a message that includes the session identifier H, so the signature is useless on any other connection; the bastion checks it against authorized_keys (section 2).
  6. Channels share the pipe. A shell, an rsync and a tunnel to a notebook are independent channels on the one connection (illustrative lanes; sections 7 and 8).
  7. Nest it: ProxyJump. One channel can carry a complete second SSH session, end to end from the laptop to gpu-node-01: the bastion relays ciphertext it cannot read (sections 5 and 6).

1. One connection on the wire

Before SSH (1995), telnet and rlogin sent everything, passwords included, as readable text, and rcp and ftp copied files the same way. SSH replaced all of them with one protocol that encrypts and authenticates. Version 2, the only one in use, is four RFCs from January 2006: the architecture (RFC 4251), user authentication (RFC 4252), the transport layer (RFC 4253) and the connection protocol (RFC 4254), plus many later extensions.

The three layers on one TCP connection are the stack of Fig. 1 (lose the connection and every channel goes with it):

  • Transport (RFC 4253). After TCP connects, each side sends one text line, its identification string (here SSH-2.0-OpenSSH_10.3 and SSH-2.0-OpenSSH_10.5: anyone on the path sees your software version). Both then send KEXINIT, a list of what they support in ten categories (key exchange, host key type, cipher and MAC each way, compression, languages); in each category the winner is the first entry on the client's list that the server also supports (RFC 4253 section 7.1). Then a key exchange (Diffie-Hellman style: each side sends a fresh public value, both compute the same secret, an eavesdropper cannot), in which the server also signs a hash of everything exchanged so far with its host key. That hash, H, becomes the session identifier. Both send NEWKEYS and switch on encryption.
  • User authentication (RFC 4252) runs inside the encrypted pipe; section 2.
  • Connection (RFC 4254) multiplexes channels, each with its own flow-control window: session (a shell, a command, or a subsystem such as SFTP), direct-tcpip (reach a host and port through the server: -L, -D and ProxyJump), forwarded-tcpip (the server forwards a connection back to you: -R), and channels for X11 and the agent. One login can carry a shell, an rsync and three tunnels at once, and one dead TCP connection kills all of them together.

    The sizes, then the formula. Key-exchange messages: 2512 bytes for the hybrid against 240 for classic X25519; median login 61 ms against 56 ms. In the hybrid, the client's KEX_HYBRID_INIT carries an X25519 public key (32 bytes) and an ML-KEM-768 encapsulation key (1,184 bytes); the reply carries an X25519 key and a 1,088-byte ML-KEM ciphertext, plus the host key and signature (sizes from FIPS 203; layout in RFC 10042 section 2.1). Payload of the recorded init: 1 (message type) + 4 (length) + 32 + 1,184 = 1,221 bytes, exactly what the relay saw. The two secrets are combined as K = HASH(KPQ || KCL) (RFC 10042 section 2.4), so the result is safe if either half holds. The rest of the login (authentication, one channel, exit status) was 888 encrypted bytes up and 2040 down, the same for every key exchange.

    2. Keys, agents and authentication
    

    Passwords sent to a server can be guessed, phished, reused and brute-forced, and they are the whole input of the internet's SSH-guessing botnets. A key pair fixes that: a private key that never leaves your machine and a public key you can hand to anyone. To log in, the client signs a message that includes the session identifier from section 1; the server checks the signature with the public key listed in ~/.ssh/authorized_keys.

    Making and protecting a key
    

    ssh-keygen -t ed25519 -C "dev@laptop"         # Ed25519 is the default type since OpenSSH 9.5
ssh-keygen -p -a 100 -f ~/.ssh/id_ed25519      # add or change the passphrase, with more KDF rounds
    

      

    • Ed25519 (RFC 8709): 32-byte public keys, fast, no parameters to get wrong and no random number needed per signature. RSA still works (signed with rsa-sha2-512); DSA was removed entirely in OpenSSH 10.0 (9 April 2025), "completing the deprecation process that began in 2015" (10.0 release notes).
      • 

    • The passphrase encrypts the private key file on disk, stretched with bcrypt_pbkdf; -a sets the rounds. It protects a stolen file, nothing else: once the key is in an agent, anything that can talk to the agent can use it.
      • 

    • Hardware keys (FIDO tokens, OpenSSH 8.2, February 2020): ssh-keygen -t ed25519-sk keeps the private key inside the token and needs a touch per login; -O resident stores it on the token so you can load it on another machine, -O verify-required adds a PIN. The server must run OpenSSH 8.2 or newer.
      • 

    • On the server, each authorized_keys line can limit the key: restrict (no forwarding, no pty), from="198.51.100.0/24", command="..." (this key may only run one command: backup or CI keys). See sshd(8) AUTHORIZED_KEYS FILE FORMAT.

    The agent
    

    ssh-agent holds your decrypted keys in memory and signs on request through a Unix socket named by SSH_AUTH_SOCK: you type the passphrase once, and ssh, git and rsync use the key without seeing it. Useful flags: ssh-add -t 8h (forget the key after 8 hours), ssh-add -c (confirm every use), ssh-add -l (list). Since 10.1 agent sockets live under ~/.ssh/agent/ instead of /tmp, so a sandboxed process that can read /tmp no longer reaches your keys (the forwarded socket on the bastion in section 6 is at /home/dev/.ssh/agent/s.…); scripts that hard-coded /tmp/ssh-XXXX break.
    

    KDF rounds, and the agent protocol as an RFC
    The default number of bcrypt_pbkdf rounds for -a: the 10.3 manual gives 16; the current OpenBSD manual says 32. The agent protocol is now RFC 9987 (Standards Track, May 2026); since OpenSSH 10.3 the IANA-assigned names are used when the server offers them, which is why the recorded server advertises an agent-forward extension in its EXT_INFO.
    

    Which key gets offered, and "Too many authentication failures"
    

    The client offers keys one at a time, and each refusal counts against the server's MaxAuthTries, 6 by default (recorded with sshd -T). An agent full of keys exhausts it before the right key is tried: recorded with seven unrelated keys in the agent and the right key named in IdentityFile, the server disconnected with "Too many authentication failures". The fix is IdentitiesOnly yes, which offers only the keys your config names. To see the order without connecting, OpenSSH 10.5 added ssh -Z host (recorded with the bastion's 10.5 client; the laptop's 10.3 lacks it); it lists the default identity names, including the new id_mldsa44_ed25519 (section 11).
    

    A trap found while recording: IdentityFile lines add up
    For almost every keyword the first value obtained wins, which is why Host * goes last. IdentityFile is the exception: "Multiple IdentityFile directives will add to the list of identities tried" (ssh_config(5)). The first certificate tests on this page all "succeeded", even the expired certificate, because the Host * block's ordinary key was also offered and accepted. If a test of one key must fail, give it a config where no other IdentityFile applies, and check ssh -G host | grep identityfile.

    3. Host keys, known_hosts and churn
    

    Encryption is worthless if you are encrypting to the attacker. In the key exchange the server signs the exchange hash with its host key, and the client must decide whether that key really belongs to gpu-node-01. TLS answers with certificate authorities; plain SSH answers with trust on first use (TOFU): the first time, it shows the key's fingerprint and asks; after that it remembers the key in ~/.ssh/known_hosts and insists on the same one. The first connection is the weak moment; every later one is protected. The host key is SSH's only defence against a man in the middle (an attacker on the path who pretends to be the server).

And with StrictHostKeyChecking no the client logged in and ran the command: OpenSSH blocks password and keyboard-interactive login (an impostor would capture the password), and agent and port forwarding when requested, but a public-key login proceeds and you are now typing into a machine you have not verified. That is why no must never be a habit. The honest fix after a known rebuild: compare the new fingerprint out of band, then ssh-keygen -R host.

    The real risk of churn is habituation
    A team whose nodes change keys weekly learns to run ssh-keygen -R without looking, and the one day it is a real man in the middle it gets the same treatment. Three ways out, best first: host certificates (section 4: nothing changes on the client when a node is rebuilt); a separate, throwaway known_hosts with accept-new scoped to the ephemeral nodes only (Host gpu-node-*, never Host *, never the bastion); or distributing the keys (a managed /etc/ssh/ssh_known_hosts, or SSHFP below).

    Predict, then reveal: the bastion's key changed and you are sure nobody rebuilt it. What do you do?
    Stop. Do not remove the entry. Read the fingerprint the warning printed, get the real one through another channel (console, admin, a colleague on a different network), and compare. If they differ, someone is on the path or the server was compromised; if they match, the key really changed and you can update known_hosts. On a cluster with host certificates this situation becomes rare and therefore alarming, which is the point.
    

    

    

    

    4. SSH certificates: user and host
    

    With plain keys, trust is a list on every machine: N users' public keys in authorized_keys on M nodes, and M host keys in every user's known_hosts. Adding a person, removing a leaver, rebuilding a node all mean editing lists everywhere. SSH certificates replace the lists with one trusted certificate authority (CA) key: the CA signs a statement "this public key belongs to dev, may log in as dev, until 01:15 tomorrow", and every node trusts anything the CA signed. Not X.509 (the web's format, on TLS and certificates): OpenSSH's own simpler format, since OpenSSH 5.4 in 2010 (PROTOCOL.certkeys), with no chains: one CA signs, and the CA key is configured directly.
    

    

    Before: every node lists every user's key. After: every node trusts one CA line, and nothing changes when people come and go.
    

    Illustrative fleet of 20 users and 50 nodes: plain keys need 20 × 50 = 1,000 authorized_keys entries and 50 host keys in every user's known_hosts; certificates need one TrustedUserCAKeys line per node and one @cert-authority line per user.

# on every node, once:   TrustedUserCAKeys /etc/ssh/user_ca.pub      (sshd_config)

    5. Jump hosts and ProxyJump
    

    Compute nodes are not routable from your laptop; only the bastion is. Logging in to the bastion and running ssh again from there makes the second login use keys on (or forwarded to) the bastion, and every tool (rsync, git, VS Code) would have to do the same dance. ProxyJump (OpenSSH 7.3, August 2016) does it properly: your laptop asks the bastion for a raw TCP stream to gpu-node-01:22 and then runs a second, complete SSH session from the laptop to the node through that stream.
    

    ssh -J bastion gpu-node-01                # one hop
ssh -J bastion,login gpu-node-07          # two hops, in order
# or in ~/.ssh/config, so every tool gets it:
Host gpu-node-*
    ProxyJump bastion
    

      

    1. ProxyJump becomes a helper ssh -W. The client converts ProxyJump bastion into ProxyCommand ssh -W '[gpu-node-01]:22' bastion, a "stdio forward" whose standard input and output become the TCP stream, and logs in to the bastion. Recorded: Executing proxy command: exec ssh ... -W '[gpu-node-01]:22' bastion.
      2. 

    2. The bastion opens a direct-tcpip channel. On the bastion, sshd accepts the key and logs a direct-tcpip request to gpu-node-01 port 22: it connects the stream and relays bytes. Its log shows nothing more about the node session.
      3. 

    3. An end-to-end session with the node. Through that stream the laptop does a second key exchange, checks the node's host key itself and logs in: Authenticated to gpu-node-01 (via proxy).
      4. 

    4. What the bastion sees, and what it costs. Ciphertext only, in both directions; and two logins, the second inside the first: 57 ms to the bastion, 112 ms to the node through it (bars to scale).
      5. 

    

    What the bastion sees. The node's session is encrypted end to end between laptop and node; the bastion relays ciphertext. The relay on the laptop's path, during a ProxyJump session that pulled about 27 KB of output, decoded the bastion's handshake and nothing else: the node's banner, its key exchange and everything after travelled inside the outer encryption, 5116 bytes up and 6732 down, unreadable to the observer and to the bastion alike.
    

    What it costs. Two full logins, the second inside the first. Without added delay, ssh bastion true took 57 ms and ssh gpu-node-01 true through it 112 ms (medians of 10); with 40 ms between laptop and bastion, 429 ms against 850 ms. Section 7 removes most of that. Each hop's options come from its own Host block, so the bastion can use a hardware key and long multiplexing while nodes use a throwaway known_hosts; ProxyJump none disables an inherited jump.
    

    

    Recorded logs: the client's -vvv and the bastion's server log
    

    ProxyCommand, its history, and untrusted input in command lines (CVE-2025-61984)
      

    • History. Before 7.3 the same thing was written ProxyCommand ssh -W %h:%p bastion, and before 5.4, ProxyCommand ssh bastion nc %h %p. ProxyCommand still matters for non-SSH transports: AWS Session Manager, for example, provides one so that plain ssh, -J and rsync work over it (AWS docs).
      • 

    • Untrusted input. CVE-2025-61984 (fixed in 10.1, 6 October 2025): control characters in a user name from the command line or a %-expansion could lead to code execution when a ProxyCommand using %r was configured (CVE record); the scenario is a crafted ssh:// or git URL. 10.3 added validation of user and host names given to -J on the command line (not in config files). OpenSSH's own advice: never build ssh command lines from untrusted input.

    6. Agent forwarding against ProxyJump
    

    Agent forwarding (ssh -A, ForwardAgent yes) solves the same problem the old way: the bastion's sshd creates a socket there that relays signing requests back to the agent on your laptop, so ssh gpu-node-01 typed on the bastion can authenticate as you. The cost: anyone who can open that socket while you are connected can authenticate as you, to any server that trusts your key. That is the bastion's root, or any process running as your user there. Your private key never leaves the laptop, but it does not need to. Recorded three ways: in each, while the session was open, the lab played a malicious root on the bastion (look for agent sockets, list the keys, try to log in to both nodes as dev). Predict which of the three stops root completely. With -A, root on the bastion logged in to both nodes as you; a constrained key limited it to one; ProxyJump left nothing to steal.
    

    

      

    1. The laptop logs in to the bastion with -A. The laptop authenticates with its key. Because of ForwardAgent yes, the bastion's sshd creates a socket for this session that relays signing requests back to the laptop's agent.
      2. 

    2. The bastion's ssh uses the forwarded agent. Typed on the bastion, ssh gpu-node-01 asks the socket to sign; the request travels back to the laptop, which signs. It worked: gpu-node-01.
      3. 

    3. Root on the bastion finds the socket. Root lists sockets under /home/dev/.ssh/agent/ and runs ssh-add -l with it: the laptop's key is listed. Root needs no file and no passphrase.
      4. 

    4. Root logs in to the nodes as dev. With the socket, root ran ssh dev@gpu-node-01 and ssh dev@gpu-node-02. Recorded: both logged in.
      5. 

    

      

    1. Load the key with destination constraints. ssh-add -h bastion -h "bastion>gpu-node-01": the agent may sign for the laptop-to-bastion login and for the bastion-to-gpu-node-01 hop only, identified by host keys (OpenSSH 8.9 and later).
      2. 

    2. Log in with -A; the bastion hops to gpu-node-01. Each login binds the session to the server's host key (session-bind@openssh.com), so the agent knows which hop is asking. The allowed hop worked; the session's own attempt at gpu-node-02 got Permission denied (publickey).
      3. 

    3. Root tries the same trick. Root found the socket and listed the key. Recorded: gpu-node-01 logged in (the allowed hop is still usable by anyone on the bastion), gpu-node-02 refused. Constraints narrow the damage; they do not remove it.
      4. 

    

      

    1. The laptop logs in to the bastion and asks for a stream. It authenticates to the bastion and opens one direct-tcpip channel to gpu-node-01:22. No agent channel exists.
      2. 

    2. A second SSH session runs end to end. The laptop runs a complete handshake and login with gpu-node-01 inside that stream: host key checked by the laptop, signature made by the laptop. The bastion relays ciphertext.
      3. 

    3. Root on the bastion looks for an agent socket. Recorded: nothing found, so nothing to use. Root can see that a connection to gpu-node-01:22 exists and how many bytes cross it, nothing more.
      4. 

    

    The three results, from src/raw/agent_*.txt: with plain forwarding root found /home/dev/.ssh/agent/s.…, listed the laptop's key, and logged in to both nodes as dev. With a destination-constrained key (ssh-add -h bastion -h 'bastion>gpu-node-01', OpenSSH 8.9 and later) root could still use it, but only for the hop you allowed: gpu-node-01 worked, gpu-node-02 was refused, because the agent checks each request against the host keys bound into the session (session-bind@openssh.com). With ProxyJump there was no socket to find.
    

    Rules. Use ProxyJump. If a workflow truly needs a key on a remote machine (pushing to GitHub from a login node), prefer a separate deploy key there (section 13) over forwarding; if you must forward, forward a constrained key, add ssh-add -c so every use asks you, and never put ForwardAgent yes under Host *. On the server, AllowAgentForwarding no on a bastion is reasonable when everyone uses ProxyJump (it was enabled here to record the attack).

    • Agent locking. ssh-add -x locks the agent with a password. 10.5 fixed a bug where a locked agent refused the session-bind messages that identify forwarded use, so operations meant to be local-only (adding PKCS#11 tokens, using destination-restricted keys) could be done remotely (10.5 release notes).

    • Server side. 10.0 fixed DisableForwarding, which had failed to disable agent and X11 forwarding.

    Predict, then reveal: with ProxyJump, can a malicious bastion do anything at all?
    It cannot read or alter the node session (encrypted end to end, and the node's host key is checked by your laptop), cannot use your keys, and cannot replay your signature (bound to the node session). It can refuse to relay, delay traffic, see when and how much you send, and see which node you asked for. If your laptop accepts the node's host key blindly (StrictHostKeyChecking no), the bastion could itself pretend to be the node, which is why host key checking still matters behind a bastion.
    

    

    

    

    7. Multiplexing: one login, many commands
    

    Every ssh, scp, rsync -e ssh, git pull and every VS Code helper starts from zero: TCP, key exchange, authentication, through the bastion and then again to the node, plus a two-factor prompt if the cluster has one. Connection multiplexing keeps the first connection (the master) open and lets later clients ask it, over a local Unix socket, for a new channel on the already-authenticated connection.
    

    Host gpu-node-* bastion
    ControlMaster auto            # use a master if one exists, otherwise become one
    ControlPath ~/.ssh/cm/%C      # where the socket lives; %C hashes local host, host, port, user and jump host
    ControlPersist 4h             # keep the master in the background after the first session ends
    

    Predict: ten ssh gpu-node-01 true in a row through a bastion 40 ms away; how much faster is the multiplexed lane by the tenth command?
    

      

    1. The first command becomes the master. A full login to the bastion and a second one to the node inside it, 821 ms with 40 ms added between laptop and bastion; the connection stays open behind a control socket on the laptop.
      2. 

    2. The next command is one channel. A new ssh gpu-node-01 true finds the socket and asks the master for a channel: one round trip to the bastion and back, 114 ms (median of nine).
      3. 

    3. Many clients, one connection. A shell, an rsync and a git pull each get their own channel on the same authenticated pipe (illustrative names).
      4. 

    4. Ten commands, to scale. Each bar is one recorded run of ssh gpu-node-01 true: fresh logins every time against one master and nine reuses. After the first login, each command is one channel open on the master: 850 ms becomes 114 ms, 7.5 times faster.
      5. 

    5. One master, one fate. ssh -O exit stops the master, and every session riding it ends at once: a session running sleep 20 ended with exit status 255 after 18 ms.
      6. 

    

    Ten commands: 8.4 s fresh against 1.9 s multiplexed. A reused channel needs one round trip to the bastion and back for the channel open and request (the node hop is inside the cluster), against roughly eight per hop for a login (section 1). On a cluster with two-factor login it also means one prompt instead of one per command. ssh -O check host says whether a master is running; -O exit stops it; -O conninfo and -O channels are new in 10.3 (the negotiated algorithms and traffic, and the open channels).
    

    

    What it costs and how it fails
    

      

    • One master, one fate. When the master dies, every session on it dies at once. Recorded in Fig. 7, step 5. A laptop that sleeps and wakes on another network often leaves a master that looks alive but is not: -O check, then -O exit, or a short ServerAliveInterval (section 9) so it notices.
      • 

    • The socket is a key. Anyone who can open the control socket can open sessions as you without authenticating. Keep ControlPath in a directory only you can read (mkdir -m 700 ~/.ssh/cm); never in /tmp on a shared machine.
      • 

    • Authentication happens once, so a revoked key or an expired certificate does not end a master already running; ControlPersist bounds how long that lasts.
      • 

    • Bandwidth is shared. One TCP connection carries everything: a large rsync on the master slows your interactive shell, and one connection's congestion window caps total throughput. For bulk copies a separate connection (-o ControlMaster=no -o ControlPath=none) can be faster.
      • 

    

    Socket path length, scp and sftp since 10.0, and the 10.1 ControlPersist bug
      

    • Socket path length. A Unix socket path is limited (108 bytes on Linux, unix(7); 104 on macOS, sun_path[104] in its sys/un.h). %C is a fixed 40-character hash, which is why it is preferred to the older %r@%h:%p pattern. The lab hit the limit: its working directory alone was 120 characters, so it used the relative path ControlPath cm/%C.
      • 

    • Since 10.0, scp and sftp pass ControlMaster no: they use an existing master but no longer silently create one (10.0 release notes). 10.2 fixed a 10.1 bug that made sessions unusable with ControlPersist active, so avoid 10.1 with multiplexing.
      • 

    

    Recorded logs: -vvv of a reuse, -O conninfo, -O channels, -O exit
    

    Predict, then reveal: you changed User in your config for a host, but ssh host whoami still prints the old name. Why?
    A master from before the change is still running and serving the request: the new client never authenticated. ssh -O exit host and try again. The same trap catches changed forwarding options and agent forwarding: options of the original master apply.
    

    

    

    

    8. Port forwarding, tunnels and notebooks
    

    The notebook, TensorBoard or MLflow you want runs on a node your browser cannot reach. SSH carries TCP connections through its encrypted pipe as channels, in three directions. The flag says which end listens: -L and -D listen on the laptop, -R on the server. Fig. 8 steps through each forward as recorded on the lab.
    

      

    1. -L to the notebook through the bastion. One command, ssh -N -L 30988:127.0.0.1:8888 gpu-node-01 (-N: no remote command, just forward; add -f to go to the background): the laptop listens on 30988 (IPv4 and IPv6) and each browser connection becomes a direct-tcpip channel to 127.0.0.1:8888 as seen from the node. With the token the notebook accepted it; without, it answered 403.
      2. 

    2. -L to a Unix socket. The same forward to a socket in a private directory, -L 30986:/home/dev/.nb/nb.sock, which other users of the node cannot open.
      3. 

    3. -D: one SOCKS proxy. ssh -N -D 30989 bastion reached the notebook bound to all interfaces on gpu-node-01:8889 by name, because the bastion resolved it (--socks5-hostname). Plain --socks5 failed with "Could not resolve host", and the loopback-bound notebook on 8888 was unreachable, since the proxy connects from the bastion.
      4. 

    4. -R: the other way. -R 30991:127.0.0.1:30990 opened a port on the bastion's loopback that leads back to the laptop ("served from the laptop"); GatewayPorts no kept it off the network.
      5. 

    5. Port already taken: a warning, not an error. With only 127.0.0.1:30985 taken, the IPv6 listener succeeded and even ExitOnForwardFailure let the session run, so http://127.0.0.1:30985 reached the other program; with both taken, it exited 255.
      6. 

    

      

    • -D: resolve names on the far side. --socks5-hostname (or the URL scheme socks5h://, as in ALL_PROXY=socks5h://127.0.0.1:30989) sends the name to the bastion, which knows gpu-node-01; plain --socks5 resolves on the laptop and fails. And the proxy connects from the bastion, so a service bound to the node's loopback is unreachable through it; use -L to the node for that one.
      • 

    • -R: the forwarded port opened on the bastion's loopback only, because the server's GatewayPorts defaults to no. Setting it to yes would expose your laptop's service to the whole network behind the bastion.
      • 

    • Forwards fail silently. By default a forward that cannot listen is a warning and the session carries on, so a script believes its tunnel is up. With ExitOnForwardFailure yes it exits 255. Recorded subtlety: -L 30985:... with no bind address listens on localhost in both IPv4 and IPv6; when only 127.0.0.1:30985 was taken, the IPv6 listener on [::1]:30985 still succeeded, so even ExitOnForwardFailure was satisfied, and http://127.0.0.1:30985 reached the other program. Bind explicitly (-L 127.0.0.1:30985:...) and pick ports nobody else uses: deriving the port from your user id (PORT=$((10000 + $(id -u) % 10000))) avoids collisions on shared nodes.

    9. Keeping sessions alive, and noticing when they are dead
    

    A VPN, a NAT gateway or a firewall between you and the cluster forgets idle connections after a few minutes (AWS's NAT gateway after 350 seconds, as recorded on Networking foundations); a laptop sleeps; a server freezes. TCP alone will not tell you: with nothing to send, a dead connection looks exactly like a quiet one, and your terminal just hangs. Recorded: a session to gpu-node-01; three seconds in, the bastion was frozen (docker pause), so packets vanished without any refusal, as with a dead VPN.
    

      

    • ServerAliveInterval 30 with ServerAliveCountMax 3 (client; not TCPKeepAlive, whose kernel probes start only after 2 hours idle on Linux): after 30 s of silence ssh sends a request inside the encrypted connection and expects an answer; after 3 unanswered it disconnects (about 90 s). The probes also keep NAT and firewall state alive. Recorded with 2 and 2: exit after 5.0 s. Without it (the default is 0, off): still hanging after 30 s, when the script killed it.
      • 

    • Keepalives do not keep a job alive. When the connection dies, the shell and whatever runs in its foreground get a hangup. Run long work as a batch job (sbatch), and keep your interactive orchestration in tmux on the login node (section 13).
      • 

    

    

    With SSH-level keepalives the client gave up 5.0 s after the path died; without them it was still hanging at 30 s.
    

    TCPKeepAlive, and the server-side timers
    • TCPKeepAlive (on by default) asks the kernel for TCP keepalives, which on Linux start only after 2 hours idle (derived on Networking foundations: 7,200 s, then 9 probes 75 s apart). It is spoofable, does not go through the SSH layer, and is far too slow for a VPN that drops flows in minutes; ssh_config(5) itself points to ServerAliveInterval as the more robust mechanism.
      • 

    • ClientAliveInterval is the server's mirror image (default 0, recorded in sshd -T): it reaps sessions whose client vanished. ChannelTimeout and UnusedConnectionTimeout (both none by default) close idle channels or connections without channels.
      •

    All of these run over an SSH session channel; they differ in how many round trips each file costs and whether they can resume. Recorded through the bastion with 40 ms added (the same link as section 7), copying to gpu-node-01. Predict: how much slower is scp -r than rsync for 1,000 small files?

      • 

    • One large file (64 MiB): scp 4.5 s, rsync -a 4.1 s: similar, both bounded by one encrypted TCP stream.

    11. Post-quantum SSH
    

    A large enough quantum computer would break the elliptic-curve Diffie-Hellman behind every key exchange in section 1. None exists yet; OpenSSH's own estimate quotes "5-20 years, with many observers expecting them to arrive in the mid-2030s" (OpenSSH, Post-Quantum Cryptography). The danger is already real because of store now, decrypt later: someone who records your session today can decrypt it once they have such a machine. Signatures are different: a forged signature needs the quantum computer at the moment of the login, so there is no urgency for host and user keys yet.
    

    Already the default. mlkem768x25519-sha256 (ML-KEM-768, NIST FIPS 203, plus X25519) has been OpenSSH's default since 10.0 (9 April 2025), "considerably faster than the previous default". That previous default, the hybrid sntrup761x25519-sha512@openssh.com, arrived in 9.0 (April 2022) and made SSH one of the first mainstream protocols with post-quantum key exchange on by default. It is specified in RFC 10042 (August 2026, Informational).
    

    What it cost here (section 1, to scale): 2512 key-exchange bytes against 240, and no login time worth measuring on a link where a round trip costs more than the arithmetic (sntrup761 took 67 ms against ML-KEM's 61 ms, consistent with OpenSSH calling ML-KEM faster). Unlike TLS, where large post-quantum certificates threaten handshake size (TLS and certificates, section 8), SSH sends one host key and one signature, so even future post-quantum signatures add little.
    

    The warning, recorded against gpu-node-02, an OpenSSH 9.7p1 server configured to offer only classic key exchange, as an old login node would. Since 10.1 the client warns when a connection uses a non-post-quantum key exchange; WarnWeakCrypto controls it, on by default:
    

    

    The fix is to upgrade the server or re-enable its post-quantum algorithms (9.0 and later support sntrup761, 9.9 and later ML-KEM). If you cannot, silence it for that host only, as the OpenSSH page recommends: Match host gpu-node-02 then WarnWeakCrypto no-pq-kex. Do not hand-write KexAlgorithms or Ciphers lists copied from old hardening guides: frozen lists are how servers end up without the post-quantum default, exactly as this node was configured.

    12. Security: the bugs worth understanding, and a baseline
    

    regreSSHion (CVE-2024-6387): keys do not protect you from a pre-authentication bug
    

    Disclosed by Qualys on 1 July 2024 (advisory). If a client has not authenticated within LoginGraceTime (120 s by default), sshd gets a SIGALRM whose handler logs a message; on glibc-based Linux, syslog() calls malloc() and free(), which are not safe inside a signal handler, so an alarm arriving in the middle of an allocation leaves the heap inconsistent, and a patient attacker turns that into code execution as root, before authentication. Fixed in 9.8 (1 July 2024); the stop-gap if you could not upgrade was LoginGraceTime 0, trading the exploit for a denial of service. The lesson: an internet-facing sshd is attack surface no matter how good your keys are.
    

    regreSSHion: affected versions, how hard, and a correction
    A regression of CVE-2006-5051, reintroduced in October 2020 (OpenSSH 8.5p1). Affected: portable OpenSSH below 4.4p1 (unless patched) and 8.5p1 up to but not including 9.8p1. OpenBSD was not vulnerable (its handler uses syslog_r()). How hard: Qualys needed about 10,000 tries on average to win the race; on 32-bit Linux with ASLR that took about 6 to 8 hours on average (9.8 release notes); 64-bit exploitation was "believed to be possible" but not demonstrated at disclosure.
    

    Correction to the old page
    It said "roughly one attempt in ten thousand ... glibc-Linux only". The advisory's figure is about 10,000 tries on average to win the race (6 to 8 hours on 32-bit glibc with ASLR); exploitation was shown on glibc Linux, other C libraries were not examined rather than ruled out, and OpenBSD is not vulnerable.
    

    Terrapin (CVE-2023-48795): an attack on the protocol itself
    

    Disclosed 18 December 2023 (terrapin-attack.com). An on-path attacker could tamper with the message sequence across the start of encryption without the integrity check noticing. The fix, strict key exchange in OpenSSH 9.6, aborts on any unexpected handshake message and resets sequence numbers after each key exchange, and only works when both sides support it. You can see it in the recorded handshake: the client lists kex-strict-c-v00@openssh.com in its KEXINIT, and the log says will use strict KEX ordering and resetting send seqnr 3.
    

    Terrapin: which ciphers, what it did to OpenSSH, how widespread
    The attacker inserts an ignorable message during the plaintext handshake and deletes one right after encryption starts; sequence numbers still line up, so the integrity check passes. It works against chacha20-poly1305@openssh.com and against CBC ciphers with encrypt-then-MAC MACs; AES-GCM is not affected. Against OpenSSH the practical impact was small: deleting the EXT_INFO message, which disabled some keystroke-timing protections (OpenSSH 9.6 notes); some other implementations were hurt more. The researchers found at least 77% of internet SSH servers supported an exploitable mode at disclosure.
    

    The version banner is not the patch level
    

    

    A scanner reading OpenSSH_9.7 would flag this node for regreSSHion; Alpine's package 9.7_p1-r4 and later carries the fix, and -r5 also fixes the two 2025 CVEs (Alpine APKBUILD secfixes). Distributions backport; check the package, not the banner.
    

    

    PerSourcePenalties: rate limiting built in, and how it locks out a bastion
    

    Since OpenSSH 9.8, sshd penalises source addresses that fail authentication, connect without authenticating, or crash it, and refuses them for a while, with no log-parsing daemon such as fail2ban. Recorded on gpu-node-01 with the default policy: six failed logins one second apart, all arriving from the bastion's address.
    

    Attempts 5 and 6 were dropped before authentication. Note who got blocked: the bastion. Every user behind it shares that source address, so one broken script locks out the whole team. On nodes reached through a bastion or a NAT gateway, list those addresses in PerSourcePenaltyExemptList (and rate-limit on the bastion instead), or the protection becomes a self-inflicted outage.
    

    

    After four failures the node refused the bastion's address for 16.563 s: every user behind the bastion was locked out together.

    A hardening baseline for a cluster's sshd
      

    • PasswordAuthentication no and KbdInteractiveAuthentication no (unless your two-factor login uses keyboard-interactive), PermitRootLogin no, AllowGroups for who may log in at all.
      • 

    • Keep the defaults for algorithms (recorded sshd -T in section 2): post-quantum first, ChaCha20-Poly1305 then AES-GCM; no CBC, no DSA, no finite-field Diffie-Hellman in sshd's defaults since 10.0. (The old page said non-EtM MACs are off by default: the recorded 10.5 default list still contains them, after the encrypt-then-MAC ones; with ChaCha20-Poly1305 or AES-GCM no separate MAC is used anyway.)
      • 

    • MaxAuthTries (6), MaxStartups (10:30:100: start refusing 30% of unauthenticated connections at 10, all at 100), LoginGraceTime (120 s), PerSourcePenalties (on): defaults recorded above; tighten LoginGraceTime and MaxAuthTries on the internet-facing host.
      • 

    • Forwarding off by default and enabled per Match Group; AllowAgentForwarding no on the bastion if people use ProxyJump.
      • 

    • User certificates with short lifetimes and host certificates (section 4); a KRL for emergencies.
      • 

    • Moving sshd to port 2222 reduces log noise from scanners; it is not a security control (reasoning, not a measured claim).
      • 

    

    Not exposing port 22 at all is the strongest move: AWS Session Manager (no inbound port, IAM-authorised, audited; a ProxyCommand keeps ssh, -J and rsync working: AWS docs), a WireGuard or Tailscale overlay network (devices authenticate before any SSH packet flows), or Teleport (a certificate-issuing proxy with single sign-on and session recording). On a university cluster you rarely choose; ProxyJump plus ControlMaster is what makes a VPN plus two-factor login bearable.

    Interview rehearsal: seven questions with answers
    

    Walk me through what happens when you type ssh gpu-node-01 through a bastion. The client reads its config, finds ProxyJump bastion, and starts a helper ssh -W gpu-node-01:22 bastion. That helper opens TCP to the bastion, exchanges version strings and KEXINIT lists, runs the key exchange (by default the hybrid ML-KEM-768 plus X25519), verifies the bastion's host key signature against known_hosts or a host CA, switches on encryption, authenticates with a key or certificate whose signature covers the session identifier, and opens a direct-tcpip channel to the node's port 22. Through that channel the main client runs a second, independent handshake and authentication with the node, opens a session channel and requests a shell. The bastion only relays ciphertext. About eight round trips per login, doubled by the hop, which is why ControlMaster matters.
    

    Why is agent forwarding dangerous, and what do you use instead? The remote sshd exposes a socket that forwards signing requests to your local agent. Anyone with root on that machine, or running as your user, can use it while you are connected to authenticate as you anywhere your key is accepted; your private key never leaves your laptop but it does not need to. Use ProxyJump, which relays an encrypted stream and never gives the bastion signing ability. If forwarding is unavoidable, use destination-constrained keys (ssh-add -h) and confirmation (ssh-add -c).
    

    How does SSH prevent a man in the middle, and where is it weak? The server signs the key exchange hash with its host key, and the client checks that key against what it knows. The weak points are the first connection (trust on first use: the user must verify the fingerprint) and habituation to "host key changed" warnings on rebuilt machines. Host certificates fix both: the client trusts a CA key, and any properly signed host key for that name is accepted without a prompt. SSHFP records with DNSSEC are an alternative.
    

    What are SSH certificates and why would a company use them? A CA signs a user's public key together with a key ID, principals, a validity window, a serial and options. Servers trust the CA key instead of per-user authorized_keys. Onboarding and offboarding become CA policy, certificates expire on their own (hours), logs name the certificate, and a KRL handles emergencies. Host certificates do the same for server identity. The CA key becomes the crown jewel, usually behind single sign-on (Vault, Teleport).
    

    Your notebook tunnel works but a colleague says they can reach your notebook too. How? They are on the same node: loopback is shared by all local users, so binding to 127.0.0.1 does not isolate you from them, only from other machines. Or the notebook was bound to 0.0.0.0. Keep a token, and preferably serve on a Unix socket in a mode-700 directory and forward to it with -L port:/path/socket.
    

    What does post-quantum key exchange protect against in SSH today, and what does it not? It protects recorded sessions against future decryption (store now, decrypt later), which is why OpenSSH made a hybrid the default in 2022 and ML-KEM in 2025. It does not protect authentication against a future quantum attacker, but that attack would have to happen live, so there is time; experimental ML-DSA composite signatures arrived in 10.4. The hybrid construction means it is no weaker than X25519 even if ML-KEM were broken.
    

    Explain regreSSHion in two minutes. An async-signal-safety bug in sshd's login-grace-time alarm handler, which called syslog (and through it malloc) from a signal handler on glibc Linux. Interrupting an allocation at the right moment corrupts the heap; winning the race, which took about 10,000 tries on average, led to root code execution before authentication. A 2006 bug reintroduced in 8.5p1 (2020), fixed in 9.8 (July 2024). Mitigation without patching: LoginGraceTime 0. Lesson: pre-auth bugs bypass key-only authentication, so limit exposure of sshd.
