5. Jump hosts and ProxyJump

Compute nodes are not routable from your laptop; only the bastion is. Logging in to the bastion and running ssh again from there makes the second login use keys on (or forwarded to) the bastion, and every tool (rsync, git, VS Code) would have to do the same dance. ProxyJump (OpenSSH 7.3, August 2016) does it properly: your laptop asks the bastion for a raw TCP stream to gpu-node-01:22 and then runs a second, complete SSH session from the laptop to the node through that stream.

ssh -J bastion gpu-node-01                # one hop
ssh -J bastion,login gpu-node-07          # two hops, in order
# or in ~/.ssh/config, so every tool gets it:
Host gpu-node-*
    ProxyJump bastion
  1. ProxyJump becomes a helper ssh -W. The client converts ProxyJump bastion into ProxyCommand ssh -W '[gpu-node-01]:22' bastion, a "stdio forward" whose standard input and output become the TCP stream, and logs in to the bastion. Recorded: Executing proxy command: exec ssh ... -W '[gpu-node-01]:22' bastion.
  2. The bastion opens a direct-tcpip channel. On the bastion, sshd accepts the key and logs a direct-tcpip request to gpu-node-01 port 22: it connects the stream and relays bytes. Its log shows nothing more about the node session.
  3. An end-to-end session with the node. Through that stream the laptop does a second key exchange, checks the node's host key itself and logs in: Authenticated to gpu-node-01 (via proxy).
  4. What the bastion sees, and what it costs. Ciphertext only, in both directions; and two logins, the second inside the first: [[jump_b]] ms to the bastion, [[jump_n]] ms to the node through it (bars to scale).

What the bastion sees. The node's session is encrypted end to end between laptop and node; the bastion relays ciphertext. The relay on the laptop's path, during a ProxyJump session that pulled about 27 KB of output, decoded the bastion's handshake and nothing else: the node's banner, its key exchange and everything after travelled inside the outer encryption, [[jw_c2s]] bytes up and [[jw_s2c]] down, unreadable to the observer and to the bastion alike.

What it costs. Two full logins, the second inside the first. Without added delay, ssh bastion true took [[jump_b]] ms and ssh gpu-node-01 true through it [[jump_n]] ms (medians of 10); with 40 ms between laptop and bastion, [[mux_b]] ms against [[mux_n]] ms. Section 7 removes most of that. Each hop's options come from its own Host block, so the bastion can use a hardware key and long multiplexing while nodes use a throwaway known_hosts; ProxyJump none disables an inherited jump.

ProxyCommand, its history, and untrusted input in command lines (CVE-2025-61984)
    

  • History. Before 7.3 the same thing was written ProxyCommand ssh -W %h:%p bastion, and before 5.4, ProxyCommand ssh bastion nc %h %p. ProxyCommand still matters for non-SSH transports: AWS Session Manager, for example, provides one so that plain ssh, -J and rsync work over it ({{AWS docs|https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-getting-started-enable-ssh-connections.html}}).
    • 

  • Untrusted input. CVE-2025-61984 (fixed in 10.1, 6 October 2025): control characters in a user name from the command line or a %-expansion could lead to code execution when a ProxyCommand using %r was configured ({{CVE record|https://www.cve.org/CVERecord?id=CVE-2025-61984}}); the scenario is a crafted ssh:// or git URL. 10.3 added validation of user and host names given to -J on the command line (not in config files). OpenSSH's own advice: never build ssh command lines from untrusted input.

6. Agent forwarding against ProxyJump


Agent forwarding (ssh -A, ForwardAgent yes) solves the same problem the old way: the bastion's sshd creates a socket there that relays signing requests back to the agent on your laptop, so ssh gpu-node-01 typed on the bastion can authenticate as you. The cost: anyone who can open that socket while you are connected can authenticate as you, to any server that trusts your key. That is the bastion's root, or any process running as your user there. Your private key never leaves the laptop, but it does not need to. Recorded three ways: in each, while the session was open, the lab played a malicious root on the bastion (look for agent sockets, list the keys, try to log in to both nodes as dev). Predict which of the three stops root completely. With -A, root on the bastion logged in to both nodes as you; a constrained key limited it to one; ProxyJump left nothing to steal.




    

  1. The laptop logs in to the bastion with -A. The laptop authenticates with its key. Because of ForwardAgent yes, the bastion's sshd creates a socket for this session that relays signing requests back to the laptop's agent.

  2. The bastion's ssh uses the forwarded agent. Typed on the bastion, ssh gpu-node-01 asks the socket to sign; the request travels back to the laptop, which signs. It worked: gpu-node-01.
    3. 

  3. Root on the bastion finds the socket. Root lists sockets under /home/dev/.ssh/agent/ and runs ssh-add -l with it: the laptop's key is listed. Root needs no file and no passphrase.
    4. 

  4. Root logs in to the nodes as dev. With the socket, root ran ssh dev@gpu-node-01 and ssh dev@gpu-node-02. Recorded: both logged in.

  1. Load the key with destination constraints. ssh-add -h bastion -h "bastion>gpu-node-01": the agent may sign for the laptop-to-bastion login and for the bastion-to-gpu-node-01 hop only, identified by host keys (OpenSSH 8.9 and later).
    2. 

  2. Log in with -A; the bastion hops to gpu-node-01. Each login binds the session to the server's host key (session-bind@openssh.com), so the agent knows which hop is asking. The allowed hop worked; the session's own attempt at gpu-node-02 got Permission denied (publickey).
    3. 

  3. Root tries the same trick. Root found the socket and listed the key. Recorded: gpu-node-01 logged in (the allowed hop is still usable by anyone on the bastion), gpu-node-02 refused. Constraints narrow the damage; they do not remove it.
    4. 



    

  1. The laptop logs in to the bastion and asks for a stream. It authenticates to the bastion and opens one direct-tcpip channel to gpu-node-01:22. No agent channel exists.
    2. 

  2. A second SSH session runs end to end. The laptop runs a complete handshake and login with gpu-node-01 inside that stream: host key checked by the laptop, signature made by the laptop. The bastion relays ciphertext.
    3. 

  3. Root on the bastion looks for an agent socket. Recorded: nothing found, so nothing to use. Root can see that a connection to gpu-node-01:22 exists and how many bytes cross it, nothing more.
    4. 



The three results, from src/raw/agent_*.txt: with plain forwarding root found /home/dev/.ssh/agent/s.…, listed the laptop's key, and logged in to both nodes as dev. With a destination-constrained key (ssh-add -h bastion -h 'bastion>gpu-node-01', OpenSSH 8.9 and later) root could still use it, but only for the hop you allowed: gpu-node-01 worked, gpu-node-02 was refused, because the agent checks each request against the host keys bound into the session (session-bind@openssh.com). With ProxyJump there was no socket to find.


Rules. Use ProxyJump. If a workflow truly needs a key on a remote machine (pushing to GitHub from a login node), prefer a separate deploy key there (section 13) over forwarding; if you must forward, forward a constrained key, add ssh-add -c so every use asks you, and never put ForwardAgent yes under Host *. On the server, AllowAgentForwarding no on a bastion is reasonable when everyone uses ProxyJump (it was enabled here to record the attack).

Agent locking and server-side fixes (10.0, 10.5)
    

  • Agent locking. ssh-add -x locks the agent with a password. 10.5 fixed a bug where a locked agent refused the session-bind messages that identify forwarded use, so operations meant to be local-only (adding PKCS#11 tokens, using destination-restricted keys) could be done remotely ({{10.5 release notes|https://www.openssh.com/releasenotes.html}}).
    • 

  • Server side. 10.0 fixed DisableForwarding, which had failed to disable agent and X11 forwarding.

Predict, then reveal: with ProxyJump, can a malicious bastion do anything at all?
It cannot read or alter the node session (encrypted end to end, and the node's host key is checked by your laptop), cannot use your keys, and cannot replay your signature (bound to the node session). It can refuse to relay, delay traffic, see when and how much you send, and see which node you asked for. If your laptop accepts the node's host key blindly (StrictHostKeyChecking no), the bastion could itself pretend to be the node, which is why host key checking still matters behind a bastion.
