7. Multiplexing: one login, many commands

Every ssh, scp, rsync -e ssh, git pull and every VS Code helper starts from zero: TCP, key exchange, authentication, through the bastion and then again to the node, plus a two-factor prompt if the cluster has one. Connection multiplexing keeps the first connection (the master) open and lets later clients ask it, over a local Unix socket, for a new channel on the already-authenticated connection.

Host gpu-node-* bastion
    ControlMaster auto            # use a master if one exists, otherwise become one
    ControlPath ~/.ssh/cm/%C      # where the socket lives; %C hashes local host, host, port, user and jump host
    ControlPersist 4h             # keep the master in the background after the first session ends

Predict: ten ssh gpu-node-01 true in a row through a bastion 40 ms away; how much faster is the multiplexed lane by the tenth command?

  1. The first command becomes the master. A full login to the bastion and a second one to the node inside it, [[mux_first]] ms with 40 ms added between laptop and bastion; the connection stays open behind a control socket on the laptop.
  2. The next command is one channel. A new ssh gpu-node-01 true finds the socket and asks the master for a channel: one round trip to the bastion and back, [[mux_reuse]] ms (median of nine).
  3. Many clients, one connection. A shell, an rsync and a git pull each get their own channel on the same authenticated pipe (illustrative names).
  4. Ten commands, to scale. Each bar is one recorded run of ssh gpu-node-01 true: fresh logins every time against one master and nine reuses. After the first login, each command is one channel open on the master: [[mux_n]] ms becomes [[mux_reuse]] ms, [[mux_x]] times faster.
  5. One master, one fate. ssh -O exit stops the master, and every session riding it ends at once: a session running sleep 20 ended with exit status 255 after 18 ms.

Ten commands: [[mux_10_fresh_s]] s fresh against [[mux_10_mux_s]] s multiplexed. A reused channel needs one round trip to the bastion and back for the channel open and request (the node hop is inside the cluster), against roughly eight per hop for a login (section 1). On a cluster with two-factor login it also means one prompt instead of one per command. ssh -O check host says whether a master is running; -O exit stops it; -O conninfo and -O channels are new in 10.3 (the negotiated algorithms and traffic, and the open channels).

What it costs and how it fails

  • One master, one fate. When the master dies, every session on it dies at once. Recorded in Fig. 7, step 5. A laptop that sleeps and wakes on another network often leaves a master that looks alive but is not: -O check, then -O exit, or a short ServerAliveInterval (section 9) so it notices.
  • The socket is a key. Anyone who can open the control socket can open sessions as you without authenticating. Keep ControlPath in a directory only you can read (mkdir -m 700 ~/.ssh/cm); never in /tmp on a shared machine.
  • Authentication happens once, so a revoked key or an expired certificate does not end a master already running; ControlPersist bounds how long that lasts.
  • Bandwidth is shared. One TCP connection carries everything: a large rsync on the master slows your interactive shell, and one connection's congestion window caps total throughput. For bulk copies a separate connection (-o ControlMaster=no -o ControlPath=none) can be faster.
Socket path length, scp and sftp since 10.0, and the 10.1 ControlPersist bug
  • Socket path length. A Unix socket path is limited (108 bytes on Linux, {{unix(7)|https://man7.org/linux/man-pages/man7/unix.7.html}}; 104 on macOS, sun_path[104] in its sys/un.h). %C is a fixed 40-character hash, which is why it is preferred to the older %r@%h:%p pattern. The lab hit the limit: its working directory alone was 120 characters, so it used the relative path ControlPath cm/%C.
  • Since 10.0, scp and sftp pass ControlMaster no: they use an existing master but no longer silently create one ({{10.0 release notes|https://www.openssh.com/releasenotes.html}}). 10.2 fixed a 10.1 bug that made sessions unusable with ControlPersist active, so avoid 10.1 with multiplexing.

Predict, then reveal: you changed User in your config for a host, but ssh host whoami still prints the old name. Why?
A master from before the change is still running and serving the request: the new client never authenticated. ssh -O exit host and try again. The same trap catches changed forwarding options and agent forwarding: options of the original master apply.
