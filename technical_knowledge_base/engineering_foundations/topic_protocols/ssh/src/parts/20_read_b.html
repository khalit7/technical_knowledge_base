1. One connection on the wire

Before SSH (1995), telnet and rlogin sent everything, passwords included, as readable text, and rcp and ftp copied files the same way. SSH replaced all of them with one protocol that encrypts and authenticates. Version 2, the only one in use, is four RFCs from January 2006: the architecture ({{RFC 4251|https://www.rfc-editor.org/rfc/rfc4251}}), user authentication ({{RFC 4252|https://www.rfc-editor.org/rfc/rfc4252}}), the transport layer ({{RFC 4253|https://www.rfc-editor.org/rfc/rfc4253}}) and the connection protocol ({{RFC 4254|https://www.rfc-editor.org/rfc/rfc4254}}), plus many later extensions.

Three layers on one TCP connection: lose the connection and every channel goes with it.
  • Transport (RFC 4253). After TCP connects, each side sends one text line, its identification string (here SSH-2.0-OpenSSH_10.3 and SSH-2.0-OpenSSH_10.5: anyone on the path sees your software version). Both then send KEXINIT, a list of what they support in ten categories (key exchange, host key type, cipher and MAC each way, compression, languages); in each category the winner is the first entry on the client's list that the server also supports (RFC 4253 section 7.1). Then a key exchange (Diffie-Hellman style: each side sends a fresh public value, both compute the same secret, an eavesdropper cannot), in which the server also signs a hash of everything exchanged so far with its host key. That hash, H, becomes the session identifier. Both send NEWKEYS and switch on encryption.
  • User authentication (RFC 4252) runs inside the encrypted pipe; section 2.
  • Connection (RFC 4254) multiplexes channels, each with its own flow-control window: session (a shell, a command, or a subsystem such as SFTP), direct-tcpip (reach a host and port through the server: -L, -D and ProxyJump), forwarded-tcpip (the server forwards a connection back to you: -R), and channels for X11 and the agent. One login can carry a shell, an rsync and three tunnels at once, and one dead TCP connection kills all of them together.

Watch one login, packet by packet

A relay between the laptop and the bastion decoded every SSH packet of ssh bastion true (log in, run nothing, leave) until encryption started; after NEWKEYS it could see only sizes. Predict before you step: how much bigger is the post-quantum default's key exchange than the classic one, and how much slower is the login?

Everything before NEWKEYS is readable on the path; the post-quantum hybrid makes the key exchange about ten times bigger and the login no measurably slower.

Recorded 5 October 2026, laptop OpenSSH 10.3p1 to bastion OpenSSH 10.5p1, one connection per key exchange (forced with -o KexAlgorithms=). Bars to scale by bytes on the wire; sizes are whole SSH packets (length field, padding included). Time is the median of 15 fresh logins with no added delay; most of it is the container port proxy, not cryptography.

The sizes, then the formula. Key-exchange messages: [[kex_ml_kexbytes]] bytes for the hybrid against [[kex_cv_kexbytes]] for classic X25519; median login [[kex_ml_ms]] ms against [[kex_cv_ms]] ms. In the hybrid, the client's KEX_HYBRID_INIT carries an X25519 public key (32 bytes) and an ML-KEM-768 encapsulation key (1,184 bytes); the reply carries an X25519 key and a 1,088-byte ML-KEM ciphertext, plus the host key and signature (sizes from {{FIPS 203|https://csrc.nist.gov/pubs/fips/203/final}}; layout in {{RFC 10042|https://www.rfc-editor.org/rfc/rfc10042}} section 2.1). Payload of the recorded init: 1 (message type) + 4 (length) + 32 + 1,184 = 1,221 bytes, exactly what the relay saw. The two secrets are combined as K = HASH(KPQ || KCL) (RFC 10042 section 2.4), so the result is safe if either half holds. The rest of the login (authentication, one channel, exit status) was [[enc_c2s]] encrypted bytes up and [[enc_s2c]] down, the same for every key exchange.

Predict, then reveal: what can the relay (or anyone on the Wi-Fi) learn from this login?
Both software versions (the identification strings), every algorithm each side supports and which ones were chosen (KEXINIT is plaintext), the server's host key (it is in the reply, so a passive observer can fingerprint the server), and then the sizes and timing of every encrypted packet. Not visible: the user name, which key was used, the command, its output. Keystroke timing in interactive shells is partly hidden since OpenSSH 9.5's ObscureKeystrokeTiming (on by default; {{OpenSSH 9.5 release notes|https://www.openssh.com/releasenotes.html}}).

How many round trips a login costs

About eight round trips before any work is done: the cost that connection reuse removes.

With 40 ms added between laptop and bastion, the server's banner arrived at [[d40_banner]] ms (TCP setup plus the first round trip, plus the container proxy), keys were in place at [[d40_newkeys]] ms, and the command finished at [[d40_done]] ms: about eight round trips for one ssh host command. Through a jump host you pay that twice, the second set inside the first (section 5); section 7 removes it. Rekeying, and a 10.4 change
A long connection agrees new keys from time to time. RFC 4253 section 9 recommends after each gigabyte or each hour; the log shows OpenSSH's default for ChaCha20-Poly1305, rekey out after 134217728 blocks (227 blocks), and RekeyLimit sets it. Since OpenSSH 10.4 a peer that sends non-key-exchange messages during a post-authentication rekey is disconnected ({{10.4 release notes|https://www.openssh.com/releasenotes.html}}).
