3. Host keys, known_hosts and churn

Encryption is worthless if you are encrypting to the attacker. In the key exchange the server signs the exchange hash with its host key, and the client must decide whether that key really belongs to gpu-node-01. TLS answers with certificate authorities; plain SSH answers with trust on first use (TOFU): the first time, it shows the key's fingerprint and asks; after that it remembers the key in ~/.ssh/known_hosts and insists on the same one. The first connection is the weak moment; every later one is protected. The host key is SSH's only defence against a man in the middle (an attacker on the path who pretends to be the server).

A rebuilt node changes its key: the client refuses it, unless you told it not to care.


Cloud and cluster nodes are often rebuilt from an image that generates new host keys at first boot; the lab did exactly that. Recorded: first contact with a new node (answered yes, with the fingerprint read on the node itself, the comparison you are supposed to make through another channel such as the cloud console, the admin or a provisioning log); the node rebuilt (a new container, so new host keys) under accept-new and under no; the stale line removed. Two details from these logs. <no hostip for proxy command>: through a jump host the client never learns the node's address, so the entry is filed under the name only. And with StrictHostKeyChecking no the client logged in and ran the command: OpenSSH blocks password and keyboard-interactive login (an impostor would capture the password), and agent and port forwarding when requested, but a public-key login proceeds and you are now typing into a machine you have not verified. That is why no must never be a habit. The honest fix after a known rebuild: compare the new fingerprint out of band, then ssh-keygen -R host.

The real risk of churn is habituation
A team whose nodes change keys weekly learns to run ssh-keygen -R without looking, and the one day it is a real man in the middle it gets the same treatment. Three ways out, best first: host certificates (section 4: nothing changes on the client when a node is rebuilt); a separate, throwaway known_hosts with accept-new scoped to the ephemeral nodes only (Host gpu-node-*, never Host *, never the bastion); or distributing the keys (a managed /etc/ssh/ssh_known_hosts, or SSHFP below).

Other knobs: HashKnownHosts, UpdateHostKeys, SSHFP and CVE-2025-26465
    

  • HashKnownHosts yes stores names as hashes so a stolen known_hosts does not list every machine you use (default no upstream; some distributions turn it on). Lookups still work; ssh-keygen -F host finds an entry.
    • 

  • UpdateHostKeys: after login the server can send all its host keys (signed), so the client learns the others before a key rotation (the "hostkeys" extension in {{PROTOCOL|https://cvsweb.openbsd.org/src/usr.bin/ssh/PROTOCOL}}).
    • 

  • SSHFP DNS records publish host key fingerprints; VerifyHostKeyDNS yes makes the client trust them. Only meaningful if the answer is DNSSEC-validated (see {{DNS|n:3c65c17b0d0d812387d8f92b546f07af}}), and it had a real bug: CVE-2025-26465, an on-path attacker could impersonate any server when VerifyHostKeyDNS was on, OpenSSH 6.8p1 to 9.9p1, fixed in 9.9p2 (18 February 2025, found by Qualys; {{release notes|https://www.openssh.com/releasenotes.html}}). Since 10.1 the release notes warn that SHA-1 SSHFP records will be ignored in a future release; publish SHA-256 ones (ssh-keygen -r host).
    • 



Predict, then reveal: the bastion's key changed and you are sure nobody rebuilt it. What do you do?
Stop. Do not remove the entry. Read the fingerprint the warning printed, get the real one through another channel (console, admin, a colleague on a different network), and compare. If they differ, someone is on the path or the server was compromised; if they match, the key really changed and you can update known_hosts. On a cluster with host certificates this situation becomes rare and therefore alarming, which is the point.
