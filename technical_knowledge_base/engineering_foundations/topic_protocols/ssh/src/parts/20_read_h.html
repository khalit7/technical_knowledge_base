8. Port forwarding, tunnels and notebooks

The notebook, TensorBoard or MLflow you want runs on a node your browser cannot reach. SSH carries TCP connections through its encrypted pipe as channels, in three directions. The flag says which end listens: -L and -D listen on the laptop, -R on the server. Fig. 8 steps through each forward as recorded on the lab.

  1. -L to the notebook through the bastion. One command, ssh -N -L 30988:127.0.0.1:8888 gpu-node-01 (-N: no remote command, just forward; add -f to go to the background): the laptop listens on 30988 (IPv4 and IPv6) and each browser connection becomes a direct-tcpip channel to 127.0.0.1:8888 as seen from the node. With the token the notebook accepted it; without, it answered 403.
  2. -L to a Unix socket. The same forward to a socket in a private directory, -L 30986:/home/dev/.nb/nb.sock, which other users of the node cannot open.
  3. -D: one SOCKS proxy. ssh -N -D 30989 bastion reached the notebook bound to all interfaces on gpu-node-01:8889 by name, because the bastion resolved it (--socks5-hostname). Plain --socks5 failed with "Could not resolve host", and the loopback-bound notebook on 8888 was unreachable, since the proxy connects from the bastion.
  4. -R: the other way. -R 30991:127.0.0.1:30990 opened a port on the bastion's loopback that leads back to the laptop ("served from the laptop"); GatewayPorts no kept it off the network.
  5. Port already taken: a warning, not an error. With only 127.0.0.1:30985 taken, the IPv6 listener succeeded and even ExitOnForwardFailure let the session run, so http://127.0.0.1:30985 reached the other program; with both taken, it exited 255.
  • -D: resolve names on the far side. --socks5-hostname (or the URL scheme socks5h://, as in ALL_PROXY=socks5h://127.0.0.1:30989) sends the name to the bastion, which knows gpu-node-01; plain --socks5 resolves on the laptop and fails. And the proxy connects from the bastion, so a service bound to the node's loopback is unreachable through it; use -L to the node for that one.
  • -R: the forwarded port opened on the bastion's loopback only, because the server's GatewayPorts defaults to no. Setting it to yes would expose your laptop's service to the whole network behind the bastion.
  • Forwards fail silently. By default a forward that cannot listen is a warning and the session carries on, so a script believes its tunnel is up. With ExitOnForwardFailure yes it exits 255. Recorded subtlety: -L 30985:... with no bind address listens on localhost in both IPv4 and IPv6; when only 127.0.0.1:30985 was taken, the IPv6 listener on [::1]:30985 still succeeded, so even ExitOnForwardFailure was satisfied, and http://127.0.0.1:30985 reached the other program. Bind explicitly (-L 127.0.0.1:30985:...) and pick ports nobody else uses: deriving the port from your user id (PORT=$((10000 + $(id -u) % 10000))) avoids collisions on shared nodes.

Who else can reach your notebook?

The node ran the same notebook three ways: bound to loopback 127.0.0.1:8888, bound to all interfaces 0.0.0.0:8889, and on a Unix socket inside ~/.nb (mode 700). Then another user on the same node (alice) and another node tried to connect. Predict which of the three alice reaches.

Loopback keeps other machines out, not other users of the same node.
Correction to the old page: loopback is not private to you
The old page said to bind to 127.0.0.1 "or any other user on that node reaches your kernel". Binding to 127.0.0.1 keeps other machines out (the second node was refused), but every user on the same node shares its loopback: alice reached the loopback-bound notebook and, with the token, would have run code as dev. What protects you on a shared login or compute node is the token (Jupyter's default; never disable it) or, better, a Unix socket in a directory only you can enter: alice got Permission denied. Jupyter Server can listen on a Unix socket (--ServerApp.sock, created with mode 0600 by default, {{Jupyter Server config|https://jupyter-server.readthedocs.io/en/latest/other/full-config.html}}), and ssh -L port:/path/to/socket forwards straight to it (recorded: fwd_L_unix).

Escape sequences, Kubernetes, and server-side controls
    

  • Escape sequences at the start of a line in an interactive session: ~C opens a command line to add or cancel forwards, ~. kills a frozen session, ~I (10.3) prints connection information, ~? lists them.
    • 

  • Kubernetes. kubectl port-forward pod/nb 8888:8888 is the same idea through the API server ({{Kubernetes docs|https://kubernetes.io/docs/tasks/access-application-cluster/port-forward-access-application-cluster/}}).
    • 

  • Server controls: AllowTcpForwarding, PermitOpen (which destinations), PermitListen (which -R ports), AllowStreamLocalForwarding, and per-key restrict or permitopen=. 10.4 and 10.5 fixed cases where DisableForwarding and restrict did not cover tunnel forwarding, which is off by default.

Predict, then reveal: you run ssh -L 8888:localhost:8888 gpu-node-01 and the browser shows a different notebook from the one you started. How?
Something else on your laptop was already listening on 8888 (another tunnel, a local Jupyter), so ssh's listener failed with only a warning and the browser reached the other program; or the address family trap above. Check with lsof -nP -iTCP:8888 -sTCP:LISTEN, use a unique port, bind 127.0.0.1 explicitly, and set ExitOnForwardFailure yes.
