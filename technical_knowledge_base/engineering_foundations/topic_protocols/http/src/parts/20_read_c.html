5. HTTP/1.1: text on a connection, one response at a time

HTTP/1.0 (1996) opened a new TCP connection per request, paying a handshake each time. HTTP/1.1 (1997; today {{RFC 9112|https://www.rfc-editor.org/rfc/rfc9112}}) made connections persistent by default (keep-alive): after one response ends, the next request can use the same connection, which is why the body boundary of section 1 matters so much. Messages are lines of text ending in CR LF; a body whose length is unknown when the headers go out (a stream of tokens) uses chunked coding, and chunks can be followed by trailer fields, headers sent after the body (gRPC relies on the HTTP/2 equivalent for its status). Expect: 100-continue asks "will you take this big body?" before sending it; Upgrade switches the connection to another protocol, which is how a WebSocket starts ({{Streaming and real-time|n:3c65c17b0d0d812daa9fdb38719fc82b}}).

The cost: head-of-line blocking at the HTTP layer. On one connection, responses come back in request order. A client may send the next request before the previous answer arrives (pipelining), but a slow first answer then holds up every answer behind it. Browsers never enabled pipelining by default and opened about six connections per host instead; HTTP libraries keep a connection pool for the same reason. Two connections fix it at the price of a second TCP and TLS handshake and twice the server state; HTTP/2 fixes it on one connection. HTTP/1.1 is still often right: a few long calls per connection (most LLM generations) lose nothing, every tool understands it, and you can read it with nc. Python's requests speaks only HTTP/1.1, and httpx needs http2=True (and the h2 package). measured The official Anthropic (1.11.0) and OpenAI (3.24.0) Python SDKs, built on an httpx fork, spoke HTTP/1.1 to the lab server over TLS even though it offered HTTP/2, and HTTP/2 only when given a client with http2=True (raw/sdk_version.json). For an agent firing dozens of parallel calls that means dozens of connections.

How it fails: the keep-alive race
A pooled connection is closed by the server at the moment the client reuses it, and the request fails with "connection reset" or "server disconnected", only after idle periods. Cause: the server's keep-alive idle timeout is shorter than the client pool's. Fix: client keep-alive shorter than the server's, and retry idempotent requests on a fresh connection. The root's Failure lab reproduces it ("Reused keep-alive connection closed by the server"); AWS documents the same race producing 502s behind its load balancer (section 9).
