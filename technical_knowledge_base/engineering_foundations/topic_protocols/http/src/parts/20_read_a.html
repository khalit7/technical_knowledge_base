1. A message, piece by piece

Two programs that have never met must agree on what is asked, about which thing, under which conditions, and where the request ends. HTTP's answer is a message: a start line, header fields (name, colon, value), a blank line, an optional body. The client sends requests, the server answers, and the server that owns the resource (the model API) is the origin; anything in between that receives a message and sends it on is an intermediary, and each leg is a hop.

The URL, split. https://api.llm.test/v1/messages is a scheme (https: HTTP over TLS, port 443), an authority (host and optional port) and a path, optionally with a query (?limit=20). HTTP/1.1 puts the path in the start line and the authority in Host; HTTP/2 and 3 carry both as pseudo-headers (:method, :scheme, :authority, :path). One server hosts many names, so Host is mandatory: an HTTP/1.1 request without it gets 400 (RFC 9112 section 3.2; measured both nginx and hypercorn answered 400).

Where does the body end? A connection is a byte stream with no boundaries, so every version must say where a body stops. HTTP/1.1 has three ways: Content-Length (the request: 117), chunked transfer coding (the response: each piece prefixed by its size in hexadecimal, ended by a zero-size chunk), or closing the connection. HTTP/2 and 3 put the body in DATA frames and flag the last one end-of-stream. Getting this boundary wrong is the root of the worst HTTP bugs (request smuggling).
