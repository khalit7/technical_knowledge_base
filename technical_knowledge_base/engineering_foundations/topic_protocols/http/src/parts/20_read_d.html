6. HTTP/2: binary frames, many streams, compressed headers

HTTP/1.1 needs one connection per request in flight and repeats hundreds of bytes of identical headers on every request. HTTP/2 (2015, from Google's SPDY; today {{RFC 9113, June 2022|https://www.rfc-editor.org/rfc/rfc9113}}) keeps the meaning and changes only the wire: one connection carries many requests at once, and headers are compressed against what both sides already sent.

Frames on streams

Everything is a frame: a 9-byte header (length 24 bits, type 8, flags 8, one reserved bit, a 31-bit stream id) and up to 16,384 bytes of payload unless the peer allows more. A stream is one request and its response; the client numbers its streams 1, 3, 5, so frames of different streams interleave and the receiver sorts them by number; stream 0 is the connection itself. Over TLS the version is chosen by ALPN (the client offers h2; {{TLS and certificates|n:3c65c17b0d0d8105a37ff2d2f602a421}}); the client then sends a fixed 24-byte connection preface and both sides send SETTINGS. HPACK: why the second request's headers cost 7 bytes

Requests to one API repeat the same fields: host, path, content type, key, user agent. HPACK ({{RFC 7541, May 2015|https://www.rfc-editor.org/rfc/rfc7541}}) compresses them with three tools: a static table of 61 common fields (index 2 is :method: GET, 3 is :method: POST), a dynamic table (4,096 bytes by default) to which each side adds fields as it sends them, so a repeat becomes a one-byte index, and a fixed Huffman code for literal text (26% smaller on the SDK header values below: 164 bytes of values became 121). Secrets in a compression table. Compression leaks when an attacker can mix guesses with a secret and watch the size (the CRIME and BREACH attacks). HPACK lets a literal be marked never indexed, sent in full every time and never added to any table ({{RFC 7541 section 7.1.3|https://www.rfc-editor.org/rfc/rfc7541#section-7.1.3}}). measured The h2 library marks authorization never-indexed automatically (the "Bearer" set costs 32 bytes on every request instead of 7), but not x-api-key, which it added to the dynamic table. HPACK's per-connection table and fixed Huffman code make the attack far harder than with gzip, so this is defence in depth, not an open hole; but know your library's list of sensitive headers when the key travels in a custom one.

Flow control: a window, and credit returned by WINDOW_UPDATE

Many streams share one connection, so a receiver needs to say "slow down on this one" without stopping the others (TCP can only throttle the whole connection). Each stream, and the connection, has a window: the DATA bytes the sender may send before it must wait. The receiver returns credit with WINDOW_UPDATE frames as it consumes data. So a stream moves at most one window per round trip: throughput ≤ window / RTT, whatever the link. Predict the stalls for a 200,000-byte body with a 64 KB window, then compare the three.

A small window makes the server stop and wait for credit, once per round trip

measured A 200,000-byte GET /big over HTTP/2 (src/lab/flow_h2.py, raw/flow_h2.json): every DATA frame and WINDOW_UPDATE with its time. simulated Loopback has almost no round trip, so the client holds each WINDOW_UPDATE for 50 ms, standing in for one; the server's behaviour is real. derived Expected time is about ceil(200,000 / window) × 50 ms when the window is the limit.

The default 65,535-byte window caps one stream at about 0.65 MB/s at 100 ms round trip (65,535 / 0.1 s). Servers that move large bodies raise it (SETTINGS_INITIAL_WINDOW_SIZE for streams, a WINDOW_UPDATE on stream 0 for the connection, which always starts at 65,535); the root's Failure lab measures the cap on a real path ("One stream's throughput is capped at window / round trip"). Token streams of a few KB never notice.

Ending streams safely, and how HTTP/2 still fails

RST_STREAM cancels one stream (a user pressed stop). GOAWAY starts a graceful shutdown and carries the highest stream id the server may have processed: requests on higher-numbered streams "are therefore guaranteed to be safe to retry", and so is any request reset with REFUSED_STREAM, "even those with non-idempotent methods" ({{RFC 9113 section 8.7|https://www.rfc-editor.org/rfc/rfc9113#section-8.7}}). A server being deployed should send GOAWAY and let in-flight streams finish; the client retries what was never started (section 10).

  • One lost TCP packet stalls every stream: all streams share one ordered byte stream; the root's {{On the wire|n:3c65c17b0d0d81ec9355f4eecd6eed02}} tab measured one lost packet delaying all three concurrent streams by 43 to 68 ms. HTTP/3 fixes this.
  • Streams queue beyond SETTINGS_MAX_CONCURRENT_STREAMS (100 here); the root's Failure lab shows it ("Max concurrent streams").
  • One connection, one backend: a long-lived HTTP/2 connection through a connection-level (L4) load balancer pins every request to one backend ({{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}}; Failure lab "gRPC behind an L4 load balancer").
What was retired (priorities, server push, h2c upgrade) and two attacks (Rapid Reset, CONTINUATION flood)
  • Priorities. RFC 7540 let clients build a dependency tree of streams with weights. Few servers implemented it well, and RFC 9113 "deprecates the priority signaling defined in RFC 7540" (section 5.3.2). Its replacement is a simple Priority header (urgency 0 to 7, incremental or not) shared with HTTP/3 ({{RFC 9218, June 2022|https://www.rfc-editor.org/rfc/rfc9218}}).
  • Server push. The server could send responses the client had not asked for. Chrome turned it off by default in Chrome 106, after measuring that only 1.25%, later 0.7%, of HTTP/2 sites used it; 103 Early Hints (a hint, not the bytes) replaced it ({{Chrome, 18 Aug 2022|https://developer.chrome.com/blog/removing-push}}). The server recorded here sends ENABLE_PUSH 0.
  • Upgrading a cleartext connection to h2c. The Upgrade: h2c dance is deprecated in RFC 9113 (section 3.1). Cleartext HTTP/2 itself is alive inside clusters, started with "prior knowledge" (the client just sends the preface): that is how much gRPC traffic runs.
  • Rapid Reset (CVE-2023-44487). An attacker opens a stream and immediately cancels it with RST_STREAM, again and again: cancelled streams do not count against the concurrency limit, but the server has already started work on each. Cloudflare saw a peak just above 201 million requests per second from about 20,000 machines; Google saw 398 million ({{Cloudflare, 10 Oct 2023|https://blog.cloudflare.com/technical-breakdown-http2-rapid-reset-ddos-attack/}}; {{Google Cloud|https://cloud.google.com/blog/products/identity-security/how-it-works-the-novel-http2-rapid-reset-ddos-attack}}). Fix: servers now count resets and close abusive connections.
  • CONTINUATION flood (April 2024). HEADERS followed by endless CONTINUATION frames without END_HEADERS makes a server buffer headers forever; one connection could crash many implementations, and because no request ever completes, nothing appears in access logs ({{Nowotarski, 3 Apr 2024|https://nowotarski.info/http2-continuation-flood-technical-details/}}).

7. HTTP/3: the same streams on QUIC

HTTP/2 removed the queue between requests but kept one underneath: TCP delivers one ordered byte stream, so a single lost packet holds every stream until it is resent. HTTP/3 ({{RFC 9114, June 2022|https://www.rfc-editor.org/rfc/rfc9114}}) moves HTTP/2's idea onto QUIC, a transport over UDP with TLS 1.3 built in and many independently ordered streams ({{RFC 9000|https://www.rfc-editor.org/rfc/rfc9000}}; the transport is on {{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}}). A lost packet stalls only its own stream, and setup takes one round trip instead of two.

Each request on its own QUIC stream; settings and the QPACK tables on six one-way streams

measured Every HTTP/3 frame and QPACK instruction of the recorded connection, by QUIC stream and time (raw/h3_frames.json, aioquic 1.3.0): the request alone, again on the same connection, then two at once. A loss on stream 0 would delay only stream 0's row.

How it works. Each request is one client-opened bidirectional stream (ids 0, 4, 8, ...), carrying HTTP/3 HEADERS and DATA frames whose type and length are QUIC variable-length integers rather than HTTP/2's fixed 9-byte header; the stream id lives in QUIC, not in the frame. Connection business moves to unidirectional streams each side opens once: measured the client opened its control stream (id 2, carrying SETTINGS), a QPACK encoder stream (6) and a QPACK decoder stream (10); the server opened the same three as 3, 7 and 11.

QPACK, and why HPACK could not be reused. HPACK assumes both sides see header blocks in the order they were sent; QUIC streams arrive in any order, so a block could refer to a table entry the decoder has not received yet. QPACK ({{RFC 9204|https://www.rfc-editor.org/rfc/rfc9204}}) puts table insertions on the encoder stream and lets the encoder choose, per request, between entries the decoder has acknowledged (never blocks) and newer ones (smaller, but the request waits if the insertion has not arrived: a blocked stream, capped by QPACK_BLOCKED_STREAMS). measured aioquic's encoder sent request 1 with the static table only (59 bytes, plus 3 bytes on the encoder stream to set the table size), then inserted the fields on the encoder stream (53 bytes) and sent request 2's headers in 9 bytes that referred to those not-yet-acknowledged entries. Toggle QPACK in the header animation to compare.

How a client finds HTTP/3. It cannot know a server speaks QUIC before trying, so servers advertise it: Alt-Svc: h3=":443"; ma=86400 ("HTTP/3 on UDP 443; remember for a day", {{RFC 7838|https://www.rfc-editor.org/rfc/rfc7838}}) or an HTTPS record in DNS ({{RFC 9460|https://www.rfc-editor.org/rfc/rfc9460}}; {{DNS|n:3c65c17b0d0d812387d8f92b546f07af}}). Browsers then race QUIC against TCP and keep the winner. measured 5 October 2026: api.openai.com and generativelanguage.googleapis.com advertised h3; api.anthropic.com did not; curl negotiated HTTP/2 with all three (section 11).

0-RTT and 425. A client that has talked to a server before can send its first request inside the first packet (TLS early data). An attacker who copies that packet can replay it, so the request must be safe to repeat; a server that will not take the risk answers 425 Too Early and the client resends after the handshake ({{RFC 8470|https://www.rfc-editor.org/rfc/rfc8470}}). Never let a POST that starts a generation be accepted as early data.

What it costs. QUIC runs in user space and encrypts nearly every header, so it costs more CPU per byte than kernel TCP and packet tools see little. UDP 443 is blocked or throttled on some corporate networks, forcing a fallback to TCP after a delay. Inside a data centre, where loss is rare, HTTP/2 over TCP is simpler and as fast; HTTP/3 pays on lossy, mobile and long-distance client links.
