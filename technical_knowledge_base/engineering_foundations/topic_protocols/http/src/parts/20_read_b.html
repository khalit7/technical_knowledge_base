2. Meaning: methods, status codes, header fields

A client must be understood by a server it has never seen, through intermediaries that know nothing about the application. {{RFC 9110 (HTTP Semantics, June 2022)|https://www.rfc-editor.org/rfc/rfc9110}} defines that shared meaning once, for every version; it is the one HTTP document worth reading end to end.

Methods, and the two promises that decide retries

A method names the operation. Two properties matter more than the names: a method is safe if it asks for no change on the server, and idempotent if sending it twice has the same intended effect as once: "PUT, DELETE, and safe request methods are idempotent" ({{RFC 9110 section 9.2.2|https://www.rfc-editor.org/rfc/rfc9110#section-9.2.2}}). An idempotent request can be repeated after a network error without asking whether the first one ran; that is why the property exists.

Generation is a POST, so if the connection breaks after the request left, the client cannot know whether the model is already generating (and billing); section 10 shows what the SDKs do about it.

Status codes: the first thing a client reads

A status code is three digits whose first digit is its class: 1xx more is coming, 2xx success, 3xx go elsewhere, 4xx the request is wrong, 5xx the server or something in front of it failed. Clients must treat an unknown code as the x00 of its class, which is why APIs can invent 529 and still be read as "server error" ({{RFC 9110 section 15|https://www.rfc-editor.org/rfc/rfc9110#section-15}}). Predict, then reveal

A streamed request returns HTTP/2 200, three tokens arrive, then the stream carries an overloaded_error event and ends. What status code did the request "have"?

200. The status line goes out with the response head, before any of the body, so a later failure can only be reported inside the body (an SSE error event) or by cutting the connection. Logs and dashboards that count status codes record this request as a success: count stream-level errors separately. (HTTP allows trailer fields after a body, but status is not one of them, and SSE clients do not read trailers.)

Header fields: everything else

Fields fall into families. Representation: content-type (application/json, text/event-stream), content-length, content-encoding (gzip, br, zstd). Negotiation: accept, accept-encoding (what the client can take; the server picks and says so). Credentials: authorization or an API's own x-api-key. Caching and conditions: cache-control, etag, if-none-match (section 3). Browsers: origin, access-control-*, cookie, set-cookie (section 4). Limits: retry-after, rate-limit headers. Connection management: connection, keep-alive, transfer-encoding, upgrade, which apply to one hop only and which proxies must strip (section 8). Names are case-insensitive; HTTP/2 and 3 require lower case on the wire, which is why one hop shows Content-Type and the next content-type.

Content negotiation in LLM APIs. With "stream": true in the body, the Claude and OpenAI APIs answer text/event-stream; without it, one application/json body at the end. MCP's Streamable HTTP transport makes the same choice with the Accept header on one endpoint ({{MCP|n:3c65c17b0d0d813f9695dc4175c44cbb}}). Compression is negotiated the same way, with a streaming trap: a proxy that gzips an event stream may hold tokens until it has enough bytes to compress (the root's {{Failure lab|n:3c65c17b0d0d81ec9355f4eecd6eed02}}: "A buffering proxy delays tokens"; it also reproduces 413, 429, 502 and 504 with real client error text). Resource design, error bodies (RFC 9457), pagination and versioning: {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}} (section 2).

3. Caching and conditional requests

Fetching the same unchanged thing again (a model list, a 2 GB weights file, a tokenizer) wastes time. HTTP lets any client or intermediary keep a copy (a cache), and the response itself says how long the copy may be used and how to check it cheaply afterwards ({{RFC 9111, HTTP Caching|https://www.rfc-editor.org/rfc/rfc9111}}). Two mechanisms work together: freshness (reuse without asking) and validation (ask "has it changed?" with a validator the server gave you).

Fresh for 60 s without a request; after that one conditional request, and a 304 with no body

measured headers: the lab server's GET /v1/models answered etag: "models-v1" and cache-control: public, max-age=60; the same request with If-None-Match: "models-v1" got 304 and no body. illustrative timing: the two requests were sent a second apart; the time axis shows what the rule allows.

max-age=60 allows reuse for 60 s; s-maxage applies to shared caches (CDNs) only; private forbids shared caches; no-store forbids keeping it at all; no-cache, despite its name, means "store it, but validate before every use". The validator is an ETag (an opaque version tag) sent back in If-None-Match, or a date in If-Modified-Since. Vary: Accept-Encoding tells caches to keep one copy per value of that request header. On a 2 GB file the 304 is the difference between a round trip and a download, and weight-download tools rely on exactly this (they compare an ETag or a hash before fetching again).

What it costs. A cache serves what was true when it was stored: a stale model list after a deployment, or worse, one user's response served to another if a private answer is cached by a shared proxy. CDNs are shared caches at the edge: cf-cache-status: DYNAMIC on all the LLM API responses in section 11 means "not cached". Generation responses are unique and sent with no-store or no-cache (the root's recording shows cache-control: no-cache on the stream). Provider prompt caching is a different mechanism entirely (the model server reuses computed state for a repeated prefix) and has nothing to do with these headers; every cache layer, CDN invalidation and the LLM caches are on {{Caching|n:3cd5c17b0d0d817ebd6ccadd4750c23a}}.







4. Browsers: CORS and cookies


Two header families exist for one client, the browser, which runs code from one site (an origin: scheme, host and port) while holding the user's cookies for others. They matter to you when a web page calls an LLM API or your own backend directly.


CORS: the server must opt in to cross-origin calls


A page on https://example.com may send a request to api.anthropic.com, but the browser only lets the page read the answer if the response says Access-Control-Allow-Origin for that origin. Anything beyond a "simple" request (methods GET, HEAD or POST, and a Content-Type of only application/x-www-form-urlencoded, multipart/form-data or text/plain) is first checked with a preflight: an OPTIONS request listing the method and headers to come ({{Fetch Standard, CORS protocol|https://fetch.spec.whatwg.org/#http-cors-protocol}}). A JSON body or an x-api-key header always triggers one.

Without the opt-in header listed: 400 and no access-control-allow-origin, so a browser blocks the POST. With it: 200, access-control-allow-origin: *, access-control-max-age: 600. The same preflight to api.openai.com/v1/chat/completions got 200 with the page's own origin echoed and max-age 86400.




The Anthropic SDK's dangerouslyAllowBrowser option is what adds that header: the API serves browsers only when the developer accepts that the key is visible to anyone who opens the page. Three rules explain most CORS errors. CORS protects the user's browser, not the server: curl, Python and servers ignore it entirely. The preflight answer is cached for access-control-max-age seconds. And Access-Control-Allow-Origin: * does not work for requests with credentials, which the Fetch Standard defines as "HTTP cookies, TLS client certificates, and authentication entries" ({{Fetch, CORS protocol and credentials|https://fetch.spec.whatwg.org/#cors-protocol-and-credentials}}): an API key in a custom header is not one of them, so * is enough here.


Cookies: state on a stateless protocol


HTTP keeps no memory between requests. A cookie adds it: the server sends Set-Cookie: name=value; attributes, and the browser returns Cookie: name=value on later requests that match ({{RFC 6265|https://www.rfc-editor.org/rfc/rfc6265}}).
