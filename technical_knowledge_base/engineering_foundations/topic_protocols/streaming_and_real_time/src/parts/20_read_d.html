4. LLM token streams: what the APIs send, and what the client times

A streaming LLM call is an ordinary POST with "stream": true in the JSON body. The server answers 200 with text/event-stream at once, then writes one event per piece of the answer. Because the status line went out first, a later failure (the model overloaded halfway) cannot change it: it arrives as an event inside the stream. measured Fig. 4 is the running answer over SSE on the 50 ms path (median run of 7, section 1's relay); the ruler in front is drawn to scale.

  1. One POST, and 200 at once. The request carries the conversation as JSON (117 bytes of body, 325 bytes up with the headers). The server sends the head and message_start immediately; they reach the client at 57 ms, half a round trip after the request reached the server. The status is now fixed.
  2. The think: nothing to send. The stand-in model waits 120 ms before its first token, standing in for prefill (and, on a real server, queueing). The response is open but nothing travels, which is exactly when idle timeouts on the path bite (heartbeats, below).
  3. First token: the client's time to first token. TTFT as the client saw it: 178 ms = 50 ms round trip + 120 ms stand-in think + about 8 ms of local overhead (derived); on the 100 ms path, 226 ms. On a new connection over a real network add the TCP and TLS handshakes ({{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}}, {{TLS and certificates|n:3c65c17b0d0d8105a37ff2d2f602a421}}); what the think is made of (queueing, prefill, then decode producing the later tokens) is the {{inference topic|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}'s.
  4. Then one event per token. The numbers between the bars are the recorded gaps between tokens, 49, 48, 51 and 49 ms: the stand-in's 50 ms step plus jitter. On a real server this gap is the decode step, and the client sees it unchanged once the stream is open.
  5. message_stop ends it. The last token and message_stop arrive at 376 ms: one request, 325 bytes up and 1,019 bytes down for the whole answer.
  6. A failure after the start (illustrative, not recorded). An overloaded model halfway through sends an error event inside the stream and the stream ends; the 200 already sent stays the call's status.

Anthropic's Messages API ({{streaming docs|https://platform.claude.com/docs/en/build-with-claude/streaming}}, read 5 October 2026) sends named events in a fixed order: message_start (a Message with empty content); per content block content_block_start, one or more content_block_delta, content_block_stop; one or more message_delta (stop reason, cumulative token usage); message_stop. Deltas are text_delta, input_json_delta for a tool call's arguments (partial JSON strings: accumulate and parse at content_block_stop), thinking_delta, and one signature_delta just before a thinking block closes. ping events and error (for example {"type": "error", "error": {"type": "overloaded_error", ...}}, which would have been an HTTP 529 had the response not started) can appear anywhere, and new event types may be added, so ignore types you do not know.

The OpenAI-compatible style sends unnamed events (data lines only) and ends with a sentinel whose data is [DONE]. To SSE that is ordinary data; the client must recognise it. The official Python SDK does, with if sse.data.startswith("[DONE]"): break ({{openai-python _streaming.py|https://github.com/openai/openai-python/blob/main/src/openai/_streaming.py}}), and vLLM's OpenAI-compatible server ends streams with yield "data: [DONE]\n\n" ({{vLLM chat_completion/serving.py|https://github.com/vllm-project/vllm/blob/main/vllm/entrypoints/openai/chat_completion/serving.py}}, read at commit b0eb87fe49, 4 October 2026). A client that forgets it tries to parse [DONE] as JSON and throws on the last event of every answer.

Predict, then reveal

Your app streams from the Claude API. Halfway through, the stream delivers event: error with an overloaded_error, then ends. Your logs record each call's HTTP status. What do they record for this one?

200. The status was sent before the first token and cannot change; the failure lives only in the body (the {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}} page, section 2, has the same lesson). Count stream-level errors, and streams that end without message_stop, as their own metric, or your error rate reads zero during an overload.

What the server must do so the stream really streams (you own this if you serve or proxy a model):

  • Send the head and a first byte at once (an SSE comment works), so every hop sees activity before the first token.
  • Flush after every event, in one write call; never compress text/event-stream (gzip holds bytes until it has enough). Small writes can also be held by TCP itself (Nagle's algorithm, {{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}}, section 7).
  • Mark it unbuffered: X-Accel-Buffering: no for nginx, Incremental for intermediaries that support RFC 10036.
  • Send a heartbeat (a : ping comment or a ping event) more often than the shortest idle timeout on the path. The {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}} page measured a 3 s think surviving a short idle timeout because of a comment every second, and owns the list of proxy timeouts, including total-duration ones that no heartbeat helps.
  • When proxying a stream, forward complete events; never split a line or a UTF-8 character.

The same format in agent protocols. MCP's Streamable HTTP answers each request with plain JSON, or with an SSE stream when it has progress to send first; since the 2026-07-28 revision those streams are no longer resumable (Last-Event-ID was removed) and servers should send X-Accel-Buffering: no ({{MCP|n:3c65c17b0d0d813f9695dc4175c44cbb}} measured both). A2A streams task updates over SSE and also offers polling and push notifications, which are webhooks ({{Agent-to-agent|n:3f05c17b0d0d81199373d4d0b18706d8}}).
