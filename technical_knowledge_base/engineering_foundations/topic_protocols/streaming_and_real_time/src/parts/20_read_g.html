8. WebSockets in production: proxies, heartbeats, scale, security

A WebSocket is a long-lived, stateful connection running through infrastructure built for short requests. Three things were broken on purpose here, through nginx 1.31.6 in front of the lab's websockets server, each seen by three clients.

Three places a socket breaks, and what each client is told
  1. The proxy drops the upgrade. Even with proxy_http_version 1.1 (the default since nginx 1.29.7), nginx does not pass the hop-by-hop Upgrade and Connection unless told; the server sees a plain GET and answers 426 Upgrade Required. Fix: proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade"; ({{nginx: WebSocket proxying|https://nginx.org/en/docs/http/websocket.html}}). JavaScript never sees the 426, only close code 1006: debug with the network panel or curl.
  2. An idle timeout. No bytes from upstream for proxy_read_timeout (60 s by default; 2 s here) and nginx closes both sides with no close frame: every client reports 1006, and nginx logs it only at info level, which the default error level hides. With the client pinging every second (the pong comes back from the server, so the proxy sees upstream bytes) the same quiet 6 s survived and all seven messages arrived.
  3. Cross-site WebSocket hijacking (CSWSH). Browsers apply neither the same-origin policy nor CORS to WebSockets and attach cookies, so any site's page can talk to a cookie-authenticated socket as the logged-in user. Without an origin list the server accepted Origin: https://evil.example and sent all seven messages; with origins=["https://chat.example"] it answered 403.

The fixes generalise. A heartbeat more frequent than the shortest idle timeout on the path: the websockets library pings every 20 s by default, and cloud load balancers and NAT gateways have their own limits (AWS's NAT gateway drops a connection idle for 350 s, {{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}}, section 9); raise the proxy timeout for WebSocket routes too, but never rely on that alone. Check Origin against a list in the handshake (it protects browser users; other clients can send any Origin), prefer tickets to cookies, and re-check authorisation periodically, closing with 1008 when it lapses: the handshake authenticates once, and a socket can outlive a logout.


Predict, then reveal


A notebook's kernel keeps "disconnecting" every 60 s when idle, but only through the company proxy. The browser console shows close code 1006. What is the most likely cause?




An idle timeout. 1006 is never sent by anyone: the browser reports it when the connection vanished without a close frame, which is what a proxy timer does. Jupyter's kernel and terminal channels are WebSockets; a round number of seconds and "only through the proxy" both point at the proxy. Fix the heartbeat interval or the proxy's timeout for that route.


Scale and lifecycle


    

  • Backpressure. A browser's WebSocket.send() never blocks: it queues, and bufferedAmount says how much waits. A producer that ignores it fills memory on a slow network. WebSocketStream gives streams with automatic backpressure, but it is non-standard and, per MDN's compatibility data, shipped only in Chrome (since 124), not Firefox or Safari ({{MDN: WebSocketStream|https://developer.mozilla.org/en-US/docs/Web/API/WebSocketStream}}). Server libraries have their own limits (the websockets library queues at most 16 incoming messages by default, then stops reading, so TCP's flow control pushes back on the sender).
    • 

  • Reconnection is yours. No browser reconnects a WebSocket. Exponential backoff with random jitter and a cap, sequence numbers on messages, a short replay buffer on the server, resume from the last number the client saw: most of what Socket.IO, Phoenix Channels and hosted realtime services sell is this.
    • 

  • Reconnect storms. When a server with 50,000 sockets dies, 50,000 clients come back within seconds; without jitter, together. During deploys, close in batches with 1001 or 1012.
    • 

  • Load balancing. A socket is pinned to one server for life, so balancing applies only to new connections and adding servers does not move existing load. Keep per-user state in a store and use a publish/subscribe backplane (Redis, NATS, Kafka) so a message for user X reaches whichever server holds X's socket.
    • 



Cost per connection, serverless, and what to monitor


    

  • Cost per connection is a file descriptor, kernel buffers and whatever state you keep, including compression contexts (section 7). Raise ulimit -n; cap message size, message rate and connections per IP: the protocol itself has no limits, so an unlimited reader is a denial of service.
    • 

  • Serverless. Request-scoped functions cannot hold a socket. Platforms offer a managed connection layer that calls your function per message (AWS API Gateway WebSocket APIs) or long-lived objects per room (Cloudflare Durable Objects); both change the cost model, so check per-message prices and limits first.
    • 

  • Observability. Open connections per server, messages and bytes per second, close codes (a jump in 1006 is infrastructure, not your code), reconnect rate, send-queue high-water marks.
