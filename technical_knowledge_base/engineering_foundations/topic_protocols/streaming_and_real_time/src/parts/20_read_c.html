2. Server-Sent Events: the format, byte by byte

SSE is an agreed text format for a response that does not end, defined in the HTML standard ({{WHATWG HTML, section 9.2|https://html.spec.whatwg.org/multipage/server-sent-events.html}}, a living standard, last updated 5 October 2026), plus a small browser API, EventSource, that reads it. Here is one token event of the running answer, exactly as sent:

event: content_block_delta␊ data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"The"}}␊ ␊
Click a line. measured This event is 118 bytes: 27 for the event line, 90 for the data line (6 for data: , 83 of JSON, 1 newline), 1 for the blank line. The token itself is 3 of them.

The response head. Content-Type: text/event-stream is the only thing that makes it SSE (EventSource refuses any other type, and any status other than 200). Cache-Control: no-cache, because an event stream is not a document. X-Accel-Buffering: no is not in the standard; it tells nginx-style proxies not to buffer (the parent topic's Failure lab, "A buffering proxy delays tokens"); the standard way is now the Incremental header field ({{RFC 10036|https://www.rfc-editor.org/rfc/rfc10036}}, August 2026). There is no Content-Length: on HTTP/1.1 the body travels in chunked encoding, on HTTP/2 and 3 in DATA frames, and the SSE parser sees neither, only text.

The rules that bite. Lines end in LF, CR LF or a lone CR; exactly one space after the colon is removed (so data:{"text":"hi"} with no space delivers the whole JSON); a line with no colon is a field name with an empty value; a field name the parser does not know is ignored, including data  with a space before the colon; an event the stream ends before its blank line is thrown away; one leading UTF-8 byte order mark is stripped; and a network read can end mid-line or mid-character, so a parser buffers bytes, never decodes each read alone. measured Of 8 real parsers fed 18 byte streams, each testing one rule, only Chrome's EventSource and Node's eventsource package followed the standard on all of them; the four Python parsers (inside the official OpenAI and Anthropic SDKs, httpx-sse, sseclient-py) each lost the first event after a byte order mark. Today's LLM APIs never send those shapes; it matters when you write the server or a proxy that re-frames events.

3. SSE clients: EventSource, fetch, and the six-connection trap

EventSource (new EventSource('/events')) opens, parses, delivers and reconnects on its own, and three limits decide when you can use it. GET only, no body: an LLM request carries the conversation as JSON, so it cannot be an EventSource request. No custom headers: no Authorization or x-api-key, only cookies (with withCredentials plus CORS for another origin), one more reason browser apps never hold an LLM key ({{Auth|n:3c65c17b0d0d817692dcc8ebd59b5c2b}}). Strict: a non-200 status or another content type "fails the connection" with no retry, while a network error or a stream that simply ends makes it reconnect. So LLM apps use fetch() with a POST, read response.body as a stream and run an SSE parser over the bytes ({{JavaScript: the event loop, promises and streams, section 5|n:4055c17b0d0d81fe857de8b34db109ea#s5}} builds it); in Python, httpx streaming plus httpx-sse, or the official SDKs with their own parser. Reconnection is then yours to write.

On HTTP/1.1 each open stream holds one of six connections per host; on HTTP/2 they share one

measured Chrome 148 against this page's HTTP/1.1 lab server: a page opened eight EventSource streams to one host; 6 opened within 10 ms and the other two never opened in the 3.5 s observed; a plain fetch() to the same host, started 0.3 s in, had not finished either. The HTTP/2 panel is illustrative (not run here: EventSource over h2 needs the browser to trust the lab's certificate).

Every request to that host queues behind the streams. MDN notes the limit is per browser and host, across tabs, and that Chrome and Firefox marked the bug "Won't fix" ({{MDN: EventSource|https://developer.mozilla.org/en-US/docs/Web/API/EventSource}}). The fix is HTTP/2 or HTTP/3, where each stream is one of many on a single connection; the server's SETTINGS_MAX_CONCURRENT_STREAMS sets how many, unlimited until it says otherwise, with a recommendation of at least 100 ({{RFC 9113 section 6.5.2|https://www.rfc-editor.org/rfc/rfc9113#section-6.5.2}}).

Correction to a common reading of MDN

MDN says the HTTP/2 limit "defaults to 100". The protocol has no default: until the server's SETTINGS arrive the number of streams is unlimited, and RFC 9113 only recommends that servers not set it below 100. Most servers announce 100 or more, so in practice the advice holds.

A real public stream: four seconds of Wikimedia's EventStreams

measured Wikimedia publishes every edit to its wikis as an SSE stream. Four seconds of curl -N https://stream.wikimedia.org/v2/stream/recentchange on 5 October 2026: HTTP/2, content-type: text/event-stream; charset=utf-8, a first line :ok (a comment, sent at once so every proxy sees bytes), then 150 events and 228,771 bytes. Each event's id is a JSON array naming Kafka topics, partitions and timestamps or offsets: send it back as Last-Event-ID and the service resumes from that point in its log. Its documentation says the connection is cut after 15 minutes regardless, and that "a good SSE / EventSource client should be able to automatically reconnect and begin consuming at the right location" ({{EventStreams docs|https://wikitech.wikimedia.org/wiki/Event_Platform/EventStreams_HTTP_Service}}). Field values were not kept.
