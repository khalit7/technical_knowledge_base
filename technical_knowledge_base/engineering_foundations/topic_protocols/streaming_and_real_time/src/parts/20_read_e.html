5. Cut, resume, stop: when a stream ends early

A stream ends early in three ways, each with its own answer: the network cuts it (a proxy timeout, a deploy draining a server, a phone moving from Wi-Fi to cellular), the user cuts it (Stop), or the server fails partway (the error event of section 4).

The network cuts it: reconnect, and resume if the events are numbered

Predict: an EventSource stream without ids is cut after two tokens; what does a chat UI that appends every token show after the browser reconnects? Then switch the server setting.

Each glass slab is one connection; the row in front is what a chat UI renders by appending every token, red when repeated; the server log adds the Last-Event-ID each reconnect carried.

  1. Connection 1. EventSource opens the stream; message_start, "The" and " sky" arrive between 0.008 and 0.177 s. No event carries an id: line.
  2. The cut, then a wait. After three events the server closes the connection. EventSource reports an error (readyState CONNECTING) and reconnects on its own: without ids, Chrome reconnected after 3.007 s. The request carries no Last-Event-ID: there is nothing to send.
  3. Connection 2 starts over. The server, knowing nothing, started again: "The sky" twice on screen.
  4. Forever. Cut again, and at 6.365 s a third connection repeats it: "The sky" three times, and it never completes. Without ids, the client-side fix is to clear the partial answer on open.
  1. Connection 1, numbered. Every event now carries an id: message_start #0, "The" #1, " sky" #2, then the cut.
  2. Resume from 2. With ids, the reconnect carried Last-Event-ID: 2, the server resumed at event 3, and " is", " blue", "." (#3 to #5) arrived with no repeats. Then the next cut.
  3. Resume from 5. The next reconnect carries Last-Event-ID: 5; the server sends message_stop #6 and the answer completed. The stream then ends normally.
  4. And it reconnects anyway. When the stream then ended normally, Chrome reconnected again (to EventSource an ended stream is a dropped one) every 3 s, carrying Last-Event-ID: 6; the server has nothing left to send.
  1. Numbered, with retry: 500. The stream also sets the reconnection delay to 500 ms; #0 to #2 arrive, then the cut.
  2. Back in half a second. With retry: 500 the reconnects came after 0.504 s; this one carries Last-Event-ID: 2 and #3 to #5 arrive.
  3. Resume from 5, then the end. message_stop #6 completes the answer and the stream ends; EventSource reconnects once more, as before.
  4. 204 stops it. Answering the final reconnect with 204 No Content (not 200, so the connection "fails") stopped it: readyState CLOSED, no more reconnects.

The standard leaves the default delay to the browser, "probably in the region of a few seconds"; 3 s is Chrome's.

Resuming is a server design, not a header. The server must answer "everything after event 2", so events must outlive the connection: generation runs as a job appending to the log, and the HTTP handler only tails it. A dropped connection then neither stops nor duplicates the work, and any server behind the load balancer can take the reconnect. Wikimedia's stream (section 3) is this shape over Kafka. The cost: storage, and a separate cancel path, since a disconnect no longer stops the job; Vercel's AI SDK states the rule: "In a resumable stream setup, client-side aborts are treated as disconnects. Closing a tab, refreshing the page, or calling stop() only closes the current HTTP connection and should not cancel the underlying generation" ({{AI SDK resumable streams|https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-resume-streams}}). On the provider side, OpenAI's background mode is the one LLM API that resumes: create a response with background and stream both true, "keep track of a 'cursor' corresponding to the sequence_number you receive in each streaming event", then resume with starting_after; "Response data is temporarily stored to disk for roughly 10 minutes to enable asynchronous execution and polling" ({{OpenAI background mode|https://platform.openai.com/docs/guides/background}}). Elsewhere a cut stream is a failed request, retried from the start (with an idempotency key where supported, {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}}, section 10), and MCP removed SSE resumability in its 2026-07-28 revision.

A resumable stream: generation writes to a log that outlives the connection; any server tails it from the client's last id

design pattern The log can be a Redis stream, a Kafka topic or a table, keyed by response id with a retention window.

The rule for clients

A stream that ends without its final event (message_stop, [DONE]) is a failure, even when no exception was raised: some proxies close a cut stream cleanly. Check for the terminator before you show or store the answer.

The user cuts it: the server must notice

Stop closes the connection (on HTTP/2 it resets only that stream, RST_STREAM with error code CANCEL, {{RFC 9113 section 7|https://www.rfc-editor.org/rfc/rfc9113#section-7}}). Whether the GPU stops is up to the server, which usually learns of a closed connection only when it next writes; during the think before the first token it writes nothing.

The naive handler burned 3.0 s of "GPU time" for a user gone at 0.5 s, against 0.51 s for the careful one; once tokens flow, both stop within one token, because the next write fails. Real servers do the careful version: vLLM wraps its OpenAI-compatible endpoints in a with_cancellation decorator that runs the handler beside a listener for the ASGI http.disconnect message and cancels the handler when it arrives ({{vllm/entrypoints/serve/utils/api_utils.py|https://github.com/vllm-project/vllm/blob/main/vllm/entrypoints/serve/utils/api_utils.py}}, read at commit 8c1557a79c). What that cannot see: a proxy that keeps its upstream connection open after the client left (some do, to reuse it) hides the disconnect entirely.

A server that waits for its next write keeps working through the whole think after the user has gone
