The idea

A2A lets one agent hand a whole job to another organisation's agent that it cannot see inside: the job becomes a task with an id and eight states that outlives any connection, while MCP stays the way each agent uses its own tools. Commerce, payment and device protocols then add the one thing every irreversible action needs: a protocol state where a person, a signature or a device limit, not text, says yes.

Agents talk to tools over MCP, to each other over A2A, to merchants over UCP, pay with AP2 or x402, and drive devices through MHS; orange marks where something outside the model must approve

Team A and Team B are this page's running example (below). Orange is used for the same idea everywhere on the page: a state or gate where a person, a signature or a device limit decides, never text from a model.

You need

MCP (host, client, server, tools); Streaming and real-time (SSE, webhooks); Auth (OAuth, audience, token exchange). When several agents help at all is Multi-agent patterns; this page is the wire between them.

The running example

Team A trains a model; Team B owns the evaluation stack. Team A's orchestrator agent asks Team B's eval agent to "evaluate checkpoint step-4000". Team A never sees Team B's tools or prompts, only a task, its states and its results. Both agents are scripted; every message is real SDK output (a2a-sdk 1.2.2, mcp 2.3.0).

1. Why agents need a protocol to talk to each other

Two agents are opaque to each other when neither can see the other's prompts, tools, memory or model; like two companies, they see only what the other says. Delegation is giving another agent a goal ("evaluate this checkpoint") rather than a function call ("run shard 2 of suite gsm-mini on handle h-7"). Without a shared protocol N agents calling M agents means up to N × M bespoke integrations, and an evaluation is not one request: it takes minutes, may ask "which suite?", may need "read access to your bucket", and the caller's connection may drop in the middle.

The Agent2Agent protocol (A2A) is the shared contract for exactly that (A2A specification v1.0.1): discovery through an Agent Card (section 2); a task with a life, eight states and output artifacts (3, 4); three ways to hear back, waiting, Server-Sent Events or webhooks (5); one meaning on three wire formats (6); and opacity on purpose: agents "collaborate based on declared capabilities and exchanged information, without needing to share their internal thoughts, plans, or tool implementations" (spec section 1.2).

When not to use it. Every A2A hop is another trust boundary (section 9), another credential (8) and another service with a task store to run. If you own both sides or the other side is really a set of functions, use MCP or a plain API. A2A pays off when the other side is someone else's agent, the work is long or conversational, or any compliant client should reach your agent without a custom integration.

2. Discovery: the Agent Card

The agent serves a JSON document at https://{domain}/.well-known/agent-card.json (spec section 8.2, a registered well-known URI, section 14.3); registries or configuration can also supply cards. The card Team B served, as recorded:

The card is configuration a calling model reads: endpoints in preference order, capabilities, auth, and skills that are claims

measured 5 October 2026, src/lab/run_a2a.py scenario discovery: a GET without credentials, then the same GET with If-None-Match.

  • supportedInterfaces lists bindings in preference order; a client "MUST" pick the first one it supports and use that entry's URL (section 8.3.2). Here JSON-RPC first, HTTP+JSON second.
  • capabilities: if streaming or pushNotifications is absent or false, those calls fail with UnsupportedOperationError (section 3.3.4). Check before relying on either.
  • securitySchemes say how to authenticate (credential obtained out of band, section 8); skills are what a calling model reads to pick the agent: claims, not proof.
  • Caching is HTTP's (HTTP): servers "SHOULD" send Cache-Control and an ETag (section 8.6). The SDK sends a weak ETag and leaves max-age to you; the revalidation came back 304 Not Modified with no body.

Signing: identity beyond TLS. TLS proves you reached the right host (clients "SHOULD" verify the certificate, section 7.2; TLS and certificates); it does not prove that a card copied into a registry or cache is the one the provider published. A card may carry JSON Web Signatures over its canonical bytes: the card minus signatures, in the JSON Canonicalization Scheme (RFC 8785), signed as a JWS (RFC 7515), the key found by kid and jku (section 8.4). An extended card hides skills from strangers: with capabilities.extendedAgentCard true, an authenticated client calls GetExtendedAgentCard and uses the fuller card for its session (sections 3.1.11, 13.3). Put internal URLs or secrets in neither.

3. Messages, tasks, parts and artifacts

Think of a ticket in another team's tracker: your note is a message, the ticket with its number and status is a task, their question back is another message on it, the deliverable is an artifact, and related tickets share a thread, a context (the server may keep model context per contextId).

What contains what: a context holds tasks; a task holds its status, its message history and its artifacts; everything is made of parts

Field names from a2a.proto v1.0.1. A part is exactly one of text, raw (bytes), url (a file by reference) or data (any JSON value), with optional mediaType and filename. A message's role is ROLE_USER from the client or ROLE_AGENT from the server; its messageId is client-made.

The rules that bite (spec sections 3.4 and 3.7):

  • Task ids are made by the server. A taskId it does not know is TaskNotFoundError; a taskId with a different contextId is rejected (recorded: -32602 Context another-context does not match context ...).
  • A contextId without a taskId starts a new task in the same conversation.
  • Results go in artifacts, never only in messages: "Messages SHOULD NOT be used to deliver task outputs", and status messages are not guaranteed to reach a client that reconnects (section 5). Artifacts stream in pieces: later pieces carry append: true, the last lastChunk: true.
  • SendMessage may answer with a plain Message instead of a Task, for something quick that needs no tracking. A client must handle both.

4. The task lifecycle: eight states


Two states wait for someone (orange); four end the task for good. Click a state for its meaning, its way out and the recorded event


States from a2a.proto, enum TaskState (spec section 4.1.3). measured events from scenarios main, in_task_auth, rejected and canceled; failed was not recorded (the scripted agent never fails). The client can cancel from any non-terminal state; only the main transitions are drawn. In words: active is submitted (accepted, not started) and working; interrupted is input-required (the agent needs something from the client) and auth-required (it needs an authorization, section 8), where the task waits and nothing is lost; terminal is completed, failed, canceled, rejected.


    

  • Terminal means terminal. A completed, failed, canceled or rejected task accepts no more messages (UnsupportedOperationError, recorded as -32004) and cannot be canceled (TaskNotCancelableError, -32002). To continue, send a new message in the same context: that makes a new task.
    • 

  • rejected is not failed. Rejected means the agent chose not to (recorded: a request to delete a checkpoint, "this agent only evaluates checkpoints"); failed means it tried and could not. Retrying a rejected task unchanged is pointless; a failed one may work.
    • 

  • "Blocking" returns at interrupted states too. A plain SendMessage waits until the task is terminal or interrupted (section 3.2.2), so it can return in input-required: read the state, never assume a result. With returnImmediately: true it answers at once.
    •

"Clients MAY use contextId without taskId to start a new task within an existing conversation context" (section 3.4.3). The original task waits until someone answers it with its taskId, or it expires under the server's policy. In the recording Team A's second turn carries both ids.

Push notifications


For an hours-long job Team A registers a webhook (taskPushNotificationConfig) and asks for an immediate return; the agent then POSTs every update: seven POSTs for one task (the task, working, four artifact pieces, completed), the "push" mode above.


    

  • Receiving: the payload is the same StreamResponse as a stream event (section 4.3.3; the SDK sent application/json, the spec's example shows application/a2a+json: accept both). The SDK sent your per-task token as X-A2A-Notification-Token and your registered credentials as Authorization: Bearer .... Check them on every POST, accept only task ids you created, answer 2xx, and deduplicate: delivery is "at least once" (webhook discipline).
    • 

  • Sending is an SSRF risk: a webhook URL is a URL your agent fetches for a stranger, who may register a cloud metadata address such as 169.254.169.254 or an internal host. The spec says agents "SHOULD" reject private, loopback and link-local addresses (section 13.2). The SDK ships validate_push_notification_url but its default is no screening: the lab's first agent accepted a loopback webhook, and a second agent with the validator on refused it with InvalidParamsError: Invalid push notification URL (recorded). Turn it on, or send through an egress proxy.

6. One meaning, three wire formats, and versions


Version 1.0 defines the operations once and maps them onto three bindings (spec sections 5, 9 to 11): JSON-RPC 2.0 over HTTP with SSE for streams, gRPC (protobuf over HTTP/2, Service APIs), and HTTP+JSON, a REST style whose URLs come from the same protobuf service. An agent offering several "MUST" behave identically on all (section 5.1). The same blocking request over the two HTTP bindings Team B's card lists cost within a few percent of each other in bytes; the real difference is operational: JSON-RPC answers every A2A error with HTTP 200 and an error object, while HTTP+JSON uses status codes (a missing task is a real 404, section 7). A dashboard counting 4xx and 5xx sees JSON-RPC failures as successes: alert on the error object, or pick the binding your load balancers and monitors understand.


Versions. Clients "MUST" send A2A-Version: 1.0 on every request (section 3.6), and an empty or missing header means 0.3. Recorded: 9.9 gave -32009 A2A version '9.9' is not supported by this handler. Expected version '1.0'., and an empty header was read as '0.3' and refused the same way, so old clients that never send the header are treated as 0.3 clients.

Version skew in the wild
UCP's own A2A binding page in its 2026-08-25 release still shows 0.3-style requests ("method": "message/send", "kind": "message", an X-A2A-Extensions header) (UCP checkout, A2A binding), while A2A 1.0 names the header A2A-Extensions (spec section 3.2.6). A 1.0-only agent rejects those requests: when two "A2A" systems cannot talk, check the version header and the method names first.

Codes are fixed by the spec's mapping table (section 5.4): A2A's own errors are -32001 to -32009 in JSON-RPC; -32700, -32600, -32601, -32602, -32603 keep their JSON-RPC meaning (Service APIs).


    

  • Not found, not forbidden. Team C asking for Team A's task got exactly the answer for a task that does not exist (-32001 Task not found): servers "MUST NOT reveal the existence of resources the client is not authorized to access" (section 3.3.2).
    • 

  • Branch on the code and the reason in error.data, a google.rpc.ErrorInfo (TASK_NOT_FOUND, UNSUPPORTED_OPERATION, ...), never on the message text.
    • 

  • Retry only what can succeed. -32001, -32002, -32004, -32009 and -32601 fail again unchanged; transport errors and -32603 may succeed later. SendMessage "MAY" be idempotent by messageId (section 3.3.1): reuse the same messageId on a retry so a deduplicating server can.

8. Authentication and authorization


Identity lives in HTTP, not in A2A messages: "Identity information is handled at the protocol layer, not within A2A semantics" (section 7). The card declares the schemes (Auth's: API keys, HTTP bearer, OAuth 2.0 flows, OpenID Connect, mutual TLS), the client gets a credential out of band and sends it on every request, and the server authenticates every request (sections 7.3, 7.4). Recorded: without a token the SDK client got HTTP 401 Unauthorized with WWW-Authenticate: Bearer realm="eval-agent" and raised A2AClientError: HTTP Error 401. Discovery carried no credential on purpose: a token sent to every URL you fetch is a token you may leak.


The SDK does not authenticate anyone for you
The official Python SDK takes the caller's identity from the web framework (Starlette's request.user) and scopes tasks by its name (resolve_user_scope returns user_name; owner_resolver.py). With no authentication middleware every caller is the same unauthenticated user, whose name is the empty string (auth/user.py), so all callers share one scope. The lab adds a bearer-token middleware; in production use your gateway or framework, and test that one caller cannot read another's task (the recorded Team C check).


Calling onward: never forward the token. Team A's orchestrator acts for a person; that person's token was issued for Team A's service, and forwarding it to Team B breaks audience binding. Team A instead trades it at the authorization server for a token whose audience is Team B and whose scope is only this call: token exchange (RFC 8693; both ideas with recorded flows on Auth; MCP states the same rule as "no token passthrough").


In-task authorization: auth-required


When the agent learns mid-task that it needs a permission the caller cannot give in a message ("read access to your bucket", "a human must approve this destructive step": the spec's examples, section 7.6), it moves the task to auth-required and gets the credential out of band, directly, not through the chain of agents. 9. Security: the other agent is not on your side


Whatever comes back from outside your system is untrusted input, and with A2A the outside is a whole agent, run by someone else, whose model read who knows what. And the data you send. A message to another organisation's agent is a disclosure: its operator may log it and keep context per contextId. Send the minimum, and review "delegate to an external agent" like "call an external API".

The overlap is growing. MCP's 2026-07-28 revision added input_required results for multi-round-trip requests and moved its long-running Tasks into an official extension (tasks/get, tasks/update) (MCP). What stays A2A's own: an agent as the unit (skills, not functions), multi-turn contexts, artifacts streamed in chunks, subscribe and push as first-class operations, and opacity as a design goal.

Read as a stack, one foundation now holds a standard for each layer of an agent: how it calls a model (Open Responses), what instructions it loads (Agent Skills, AGENTS.md), how it reaches tools (MCP) and how it delegates to another agent (A2A). The commerce protocols above stay with their own owners.


The practical rule: tool access on MCP, delegation between organisations on A2A, commerce on UCP or ACP depending on which platforms you sell through, and the rest as research unless a partner requires it.






12. Agent commerce: UCP and ACP


An agent buying shoes deals with a merchant it does not control, whose rules depend on the cart, the buyer and the country, and the action costs real money. The Universal Commerce Protocol (UCP), published by Shopify and Google (Shopify Engineering), standardises that conversation. Its roles are named by the direction capabilities flow (core concepts): the platform consumes them (a shopping agent, an app, a procurement system); the business exposes them and stays the merchant of record; a credential provider holds payment instruments and personal data (a wallet); a payment service provider moves the money.


Discovery and negotiation by intersection


A business publishes a profile at /.well-known/ucp; a platform sends the URL of its own profile on every request in a UCP-Agent header. The business then computes what the interaction may use ("server-selects"): (1) keep only capabilities both profiles name; (2) for each, keep the latest version both list, dropping it if there is none; (3) drop extensions none of whose parents survived, and repeat until nothing changes. It returns the active set in every response, so an agent degrades predictably instead of failing (HTTP's content negotiation is the same idea). Names, versions and transports
    

  • Names carry authority. Reverse-domain names: dev.ucp.shopping.checkout is governed by UCP's tech council, dev.shopify.catalog by Shopify, com.example.payments.installments by example.com, with no central registry. A platform "MUST" check that an entity's schema URL is on its namespace's domain; that proves provenance, not trustworthiness.
    • 

  • Versions are dates and match exactly. A release is one compatible snapshot; an older date works only if the business lists it in supported_versions.
    • 

  • One service, several transports: REST (OpenAPI), MCP (OpenRPC), A2A (an Agent Card) and Embedded (OpenRPC).
    •

The old page said core, capabilities and extensions are "each versioned independently so a core revision does not break a niche capability". In 2026-08-25 the UCP-authored dev.ucp.* capabilities and extensions are versioned in lockstep with the release; only third-party extensions and payment handlers version on their own (core concepts, Versioning). The January post's "Embedded Checkout Protocol" is now the general Embedded Protocol (EP), with checkout methods under ec.*.


The checkout and its explicit "a person must finish this" state


Six checkout statuses; requires_escalation (orange) is the protocol saying the buyer, not the agent, must finish. Click a status


From the checkout capability, 2026-08-25. canceled is reachable from any status. complete_in_progress means the business is placing the order: no new Update or Complete, poll Get Checkout.


Each problem the business reports carries a severity: recoverable (fix the input and update), requires_buyer_input (information the API cannot collect), requires_buyer_review (policy needs the buyer's own approval), unrecoverable (start again or hand off). Either requires_* produces requires_escalation, and the business "MUST" then provide a continue_url to its own page: "The checkout has to be finalized manually by the user through a trusted UI unless the AP2 Mandates extension is supported." The lab below uses the spec's example message for each severity.


Fix what you can, hand off what you cannot: tick the spec's example messages and read the decision






illustrative the messages are the specification's own examples; an unrecoverable error means no checkout at all (ucp.status "error"); the decision follows its "Error Processing Algorithm" and status rules (checkout capability, Error Handling).


Why this matters beyond shopping. An MCP tool call succeeds or fails, and a failure reaches the model as text. UCP makes "an agent cannot finish this, and a person must" a first-class state with a handoff attached; A2A's auth-required is the same move for authorization (section 15 generalises it).


The handoff channel, payment handlers and request signing in UCP


Embedded Protocol. When escalation happens inside the agent's app, the Embedded Protocol renders the merchant's checkout in an iframe or webview and exchanges JSON-RPC 2.0 messages with it over postMessage (ec.start, ec.complete), so the host supplies its native payment sheet and saved addresses while the merchant keeps control of the order (Embedded Protocol).


Payment handlers are specifications, not companies (com.google.pay, dev.shopify.shop_pay): the business lists the handlers it accepts, the platform runs the handler's flow to get a token from the credential provider, and the business charges it through its own processor. Raw card numbers never touch the agent, and credentials flow platform to business only: businesses "MUST NOT" echo them back. Requests can be signed with HTTP Message Signatures (RFC 9421) with the verifying keys published in the signer's profile, so no prior registration is needed; OAuth 2.0, API keys and mTLS serve pre-arranged partners, and acting for a logged-in buyer uses OAuth account linking (dev.ucp.common.identity_linking).




ACP, the other commerce protocol


OpenAI and Stripe's Agentic Commerce Protocol solves the same problem with a merchant REST API that the agent platform calls (create, update, complete and cancel a checkout session); an agent that cannot perform an intervention the merchant requires gets an intervention_required message, ACP's version of the handoff. UCP adds discovery, negotiation, several transports and verticals beyond shopping; a merchant on Shopify gets UCP through its platform, so which one a given agent supports is the practical question.


ACP's checkout in detail
The RFC names ChatGPT as the agent platform; every request carries a required API-Version header, idempotency keys and request signing (ACP agentic checkout RFC, version 2026-01-16, status Draft). Statuses: not_ready_for_payment, ready_for_payment, in_progress, completed, canceled, plus authentication_required for 3-D Secure. The shape is close to UCP's checkout.


Two adoption stories in the old overview (a consumer agent buying over UCP, and a retailer blocking it) have no primary source and are left out; see src/unconfirmed.md.






13. Agent payments: AP2 and x402


A checkout protocol says what is being bought; a payment protocol must answer a harder question: how does the merchant know the user approved this, if an agent clicked buy? Two published answers take opposite routes: AP2 carries the user's signed approval through the purchase, and x402 makes the payment itself part of an HTTP request.


AP2: mandates signed on a trusted surface


In AP2 (specification v0.2) the user approves on a Trusted Surface, which "MUST be non-agentic" (deterministic code, no model in the loop), and signs mandates: a Checkout Mandate bound by hash to the merchant-signed checkout, and a Payment Mandate bound to the same checkout for the payment side. Mandates are SD-JWTs, so a verifier sees only the constraints relevant to it; verification "MUST happen in deterministic code", and the signed receipts become evidence in a dispute. Its stated threat model: "when either role is agentic, then the Agent itself is a potential attacker."


Human present, the user signs the exact checkout; human not present, the user signs the limits in advance and the agent signs inside them


With the human present, the trusted surface shows the merchant-signed checkout and the user signs the exact checkout and payment mandates; the agent only carries them.


With the human not present, the user signs "open" mandates with constraints (allowed merchants, allowed line items, an amount range, a budget) ahead of time; later the agent signs the final "closed" mandates within them, and verification in deterministic code holds them to those limits.


From the AP2 specification v0.2 and its checkout mandate and payment mandate pages, read 5 October 2026.


x402: the price arrives as an HTTP 402


x402 revives HTTP's long-reserved status 402 Payment Required for pay-per-request access by "any application or agent" (x402 specification, protocol version 2). There is no account and no checkout session: the server answers an unpaid request with its price, the client retries with a signed payment, and a facilitator verifies and settles it on a blockchain for the server.


One request, refused with a price, retried with a signed payment, verified and settled by a facilitator, with no account or checkout session


The HTTP transport, transports-v2/http.md: all x402 data travels in base64 JSON headers. The spec's example price is "amount": "10000" in atomic units of USDC on eip155:84532 (Base Sepolia, a testnet), which is 0.01 USDC at USDC's 6 decimals (derived); maxTimeoutSeconds 60. Read 24 October 2026.


    

  • Over A2A, it reuses the interrupted state: the x402 A2A transport sets the task to input-required with x402.payment.status: "payment-required" and the price in message metadata; the client answers with x402.payment.payload on the same taskId, and the receipt arrives in the completed status (transports-v2/a2a.md). There is an MCP transport too.
    • 

  • The trust gap to notice: x402 proves the payer's wallet signed; it says nothing about whether a person approved. Client-side budget management is explicitly out of scope of the spec, so the limit an agent may spend is yours to enforce below the model (section 15).
    • 



What the client signs, and verify against settle
    

  • What the client signs in the default exact scheme on EVM chains is an EIP-3009 authorization: from, to, value, a validity window and a 32-byte random nonce. Replay is blocked by the nonce (the token contract refuses reuse) and the time window (spec section 10.1).
    • 

  • Verify, then settle. The facilitator's POST /verify is read-only and "MUST NOT" commit payment state; POST /settle commits. In the default flow the server verifies, does the work, then settles; other schemes settle first (upfront) or settle a ceiling then the final charge (escrow) (sections 6.1, 7).
    • 







14. Agents driving devices: the Model Hardware Standard


Lab instruments (liquid handlers, plate readers, robotic arms, microscopes, lasers) each come with their own driver and vendor software, and wiring several together takes an engineer weeks. On 27 August 2026 Anthropic opened a research preview of the Model Hardware Standard (MHS), "a shared specification for AI agents to safely operate physical devices" (Anthropic):


    

  • A standard driver with two primitives, "read" (get temperature) and "write" (set temperature); users describe a device in natural-language tags (a robot arm's weight, say) and the driver generates a reference file with what it can measure, what can be adjusted, and "what safety limits will be enforced".
    • 

  • Above MCP, not beside it: agents control it through MCP, a command line or code; "any agent harness can access it using standard protocols, such as the" Model Context Protocol. Status: shared with partners "ahead of making the standard open source", by waitlist, safety findings promised with the open-source release.
    • 



The lessons that generalise, all from the same post:


    

  • Limits live in the device layer, not the prompt: "MHS enforces device-level safety limits", so a Janelia researcher did not worry about the agent using too much laser power. A rule the model is asked to follow can be talked out of; a limit below the model cannot.
    • 

  • Ship the artefact, not the agent. QuEra's end product "was a deterministic, fully inspectable script capable of running in production without an AI agent controlling it": the agent did the search, a reviewed program does the irreversible work.
    • 

  • Physical failures look like software errors to a model. Bubbles from mixing caused runtime errors and Claude's "default instinct was simply to retry", which made more bubbles. Retrying is safe for idempotent API calls (HTTP); it is not safe for a robot.
    • 

  • Caution costs time and is still preferred. Claude "often stopped to wait for human confirmation before performing an action it deemed even slightly risky", so experiments sometimes paused overnight: "an overly cautious agent is preferable to one that is not cautious enough."
    • 



The partners' reported results (their own measurements)


Genentech had Claude tune liquid-handler flow rates (about 140 µL/s for water, 10 µL/s for a viscous protein solution). Carnegie Mellon ran dose-response experiments "roughly three times faster", with integration taking "eight hours, versus the several weeks" of vendor setups. HHMI Janelia unified seven vendor programs and cut adding a device from a "multi-day project" to "only a few minutes". At QuEra an agent loop running overnight improved a laser-lock recovery script from 58% success at about 150 seconds per attempt to 96% at about six seconds; the finished script, then tested with no agent involved, recovered the lock in 695 of 700 trials (99.3%).




Corrected from the old overview
The old page said QuEra went "from 58% to 99.3%" and Janelia "from weeks to a day". The 58% and 99.3% are two different measurements (the starting script, and the finished script's blind test; the overnight run itself reached 96%), and Janelia's figure is per-device integration time, "multi-day project" to "a few minutes". One device item in the old overview had no primary source and is left out (src/unconfirmed.md).






15. The trust boundary for irreversible actions


Every protocol on this page meets the same moment: an action that cannot be taken back (spending money, deleting data, moving a robot arm, granting access). Text arriving over a protocol, from a tool, a remote agent or a web page, can be written by an attacker, so it must never be enough to authorise such an action. What each protocol provides at that moment, the orange gates of the hero:

The pattern, as a checklist for anything you build:


    

  1. Name the irreversible actions and give each a protocol state, not a sentence in a tool result: a state can be logged, timed out, audited and tested.
    2. 

  2. Put the approval outside the model's channel (a dialog, a merchant page, a signed mandate, an out-of-band grant), something text in the context window cannot fake.
    3. 

  3. Show the person what they approve, rendered by deterministic code (AP2's non-agentic trusted surface), never a model's summary of it.
    4. 

  4. Enforce limits below the model (MHS's device limits, AP2's budget constraints, a wallet's spending cap, an API scope).
    5. 

  5. Bind credentials to one audience and one agent (token exchange, AP2's hash binding, A2A's out-of-band credentials).
    6. 

  6. Prefer producing a reviewable artefact (a script, a closed checkout, a plan) over acting directly, when the action can wait.
    7. 

  7. Never retry an irreversible action blindly; use idempotency keys where the protocol has them (UCP and ACP checkout completion, A2A messageId, x402's nonce) and read the state before trying again.
    8.

Interview rehearsal (design angles, with model answers)


Your orchestrator calls a third-party agent for a user. How do credentials flow? The user's token is for my service only. I exchange it (RFC 8693) for a token whose audience is the third-party agent and whose scope is just this call. If the agent later needs more (the user's bucket), it moves the task to auth-required and obtains the credential out of band, directly, never through my messages.


How would you secure push notifications? On the agent: screen webhook URLs against private and link-local ranges, time out, retry with backoff, authenticate to the webhook as configured. On the receiver: verify the token, accept only known task ids, return 2xx fast, process idempotently, and re-read the task before acting on a terminal state.


An agent may spend money on its own: which protocol, and where is the limit? With a person in the loop, UCP's escalation or AP2's human-present mandate; unattended, AP2's open mandate (merchants, items, amount range, budget) verified in deterministic code, or x402 with a wallet whose spending cap is enforced outside the model. Never a limit stated only in the prompt.


What did the Model Hardware Standard pilots teach about physical actions? Enforce limits in the device layer; models treat physical failures as software errors and retry; the best output may be a reviewed deterministic script (QuEra's 99.3% blind test ran with no agent); a cautious agent costs time and is the safer default.
