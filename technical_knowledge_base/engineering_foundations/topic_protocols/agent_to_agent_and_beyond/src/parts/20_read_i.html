13. Agent payments: AP2 and x402

A checkout protocol says what is being bought; a payment protocol must answer a harder question: how does the merchant know the user approved this, if an agent clicked buy? Two published answers take opposite routes: AP2 carries the user's signed approval through the purchase, and x402 makes the payment itself part of an HTTP request.

AP2: mandates signed on a trusted surface

In AP2 ({{specification v0.2|https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md}}) the user approves on a Trusted Surface, which "MUST be non-agentic" (deterministic code, no model in the loop), and signs mandates: a Checkout Mandate bound by hash to the merchant-signed checkout, and a Payment Mandate bound to the same checkout for the payment side. Mandates are SD-JWTs, so a verifier sees only the constraints relevant to it; verification "MUST happen in deterministic code", and the signed receipts become evidence in a dispute. Its stated threat model: "when either role is agentic, then the Agent itself is a potential attacker."

Fig. 5 · Human present, the user signs the exact checkout; human not present, the user signs the limits in advance and the agent signs inside them

  1. The merchant signs the checkout. Cart, price and terms, signed by the merchant, travel towards the user.
  2. A trusted surface shows it. Non-agentic code renders the merchant-signed checkout; no model is in the loop.
  3. The user signs the mandates. A Checkout Mandate bound by hash to that checkout, and a Payment Mandate bound to the same checkout for the payment side.
  4. The agent only carries them. The Checkout Mandate goes to the merchant, the Payment Mandate to the payment side; the agent cannot change what was signed.
  5. Verified in deterministic code. Merchant and payment side each verify the signature and see only the constraints relevant to them; the signed receipts are kept for disputes.
  1. Earlier: the user signs open mandates. On the trusted surface, ahead of time, the user signs "open" mandates with constraints instead of a cart: allowed merchants, allowed line items, an amount range, a budget.
  2. The user leaves. From here no person is in the loop.
  3. The agent builds a checkout. The merchant signs it as usual.
  4. The agent signs closed mandates. Later the agent signs the final "closed" mandates for this checkout, within the open mandates' constraints.
  5. Held to the limits. Verification in deterministic code holds the closed mandates to the open mandates' limits; receipts for disputes.

From the AP2 specification v0.2 and its {{checkout mandate|https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/checkout_mandate.md}} and {{payment mandate|https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/payment_mandate.md}} pages, read 5 October 2026.

x402: the price arrives as an HTTP 402

x402 revives HTTP's long-reserved status 402 Payment Required for pay-per-request access by "any application or agent" ({{x402 specification, protocol version 2|https://github.com/x402-foundation/x402/blob/11022577a931447912d5c886ee72244b931fc854/specs/x402-specification-v2.md}}). There is no account and no checkout session: the server answers an unpaid request with its price, the client retries with a signed payment, and a facilitator verifies and settles it on a blockchain for the server (right).

  • Over A2A, it reuses the interrupted state: the x402 A2A transport sets the task to input-required with x402.payment.status: "payment-required" and the price in message metadata; the client answers with x402.payment.payload on the same taskId, and the receipt arrives in the completed status ({{transports-v2/a2a.md|https://github.com/x402-foundation/x402/blob/11022577a931447912d5c886ee72244b931fc854/specs/transports-v2/a2a.md}}). There is an MCP transport too.
  • The trust gap to notice: x402 proves the payer's wallet signed; it says nothing about whether a person approved. Client-side budget management is explicitly out of scope of the spec, so the limit an agent may spend is yours to enforce below the model (section 15).
One request, refused with a price, retried with a signed payment, verified and settled by a facilitator, with no account or checkout session

The HTTP transport, {{transports-v2/http.md|https://github.com/x402-foundation/x402/blob/11022577a931447912d5c886ee72244b931fc854/specs/transports-v2/http.md}}: all x402 data travels in base64 JSON headers. The spec's example price is "amount": "10000" in atomic units of USDC on eip155:84532 (Base Sepolia, a testnet), which is 0.01 USDC at USDC's 6 decimals (derived); maxTimeoutSeconds 60. Read 24 October 2026.

What the client signs, and verify against settle
  • What the client signs in the default exact scheme on EVM chains is an EIP-3009 authorization: from, to, value, a validity window and a 32-byte random nonce. Replay is blocked by the nonce (the token contract refuses reuse) and the time window (spec section 10.1).
  • Verify, then settle. The facilitator's POST /verify is read-only and "MUST NOT" commit payment state; POST /settle commits. In the default flow the server verifies, does the work, then settles; other schemes settle first (upfront) or settle a ceiling then the final charge (escrow) (sections 6.1, 7).

14. Agents driving devices: the Model Hardware Standard

Lab instruments (liquid handlers, plate readers, robotic arms, microscopes, lasers) each come with their own driver and vendor software, and wiring several together takes an engineer weeks. On 27 August 2026 Anthropic opened a research preview of the Model Hardware Standard (MHS), "a shared specification for AI agents to safely operate physical devices" ({{Anthropic|https://www.anthropic.com/news/model-hardware-standard-research-preview}}). What it is and the lessons that generalise, all from the same post:

Fig. 6 · The device layer: one driver under many instruments, safety limits below the model

  1. Many instruments, one standard driver. Each instrument comes with its own driver and vendor software; MHS puts one standard driver under them, with two primitives, "read" (get temperature) and "write" (set temperature).
  2. Described once, in a reference file. Users describe a device in natural-language tags (a robot arm's weight, say) and the driver generates a reference file with what it can measure, what can be adjusted, and "what safety limits will be enforced".
  3. Above MCP, not beside it. Agents control it through MCP, a command line or code: "any agent harness can access it using standard protocols, such as the" Model Context Protocol.
  4. Limits live in the device layer, not the prompt. "MHS enforces device-level safety limits", so a Janelia researcher did not worry about the agent using too much laser power. A rule the model is asked to follow can be talked out of; a limit below the model cannot.
  5. Physical failures look like software errors to a model. Bubbles from mixing caused runtime errors and Claude's "default instinct was simply to retry", which made more bubbles. Retrying is safe for idempotent API calls ({{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}}); it is not safe for a robot.
  6. Ship the artefact, not the agent. QuEra's end product "was a deterministic, fully inspectable script capable of running in production without an AI agent controlling it": the agent did the search, a reviewed program does the irreversible work.

Status: shared with partners "ahead of making the standard open source", by waitlist, safety findings promised with the open-source release. Claude also "often stopped to wait for human confirmation before performing an action it deemed even slightly risky", so experiments sometimes paused overnight: "an overly cautious agent is preferable to one that is not cautious enough."

From Anthropic's post of 27 August 2026; the figure shows the layers it describes and carries no measured values. The instruments drawn are the post's examples; which instrument a write or a failure lands on in the figure is illustrative.

The partners' reported results (their own measurements)

Genentech had Claude tune liquid-handler flow rates (about 140 µL/s for water, 10 µL/s for a viscous protein solution). Carnegie Mellon ran dose-response experiments "roughly three times faster", with integration taking "eight hours, versus the several weeks" of vendor setups. HHMI Janelia unified seven vendor programs and cut adding a device from a "multi-day project" to "only a few minutes". At QuEra an agent loop running overnight improved a laser-lock recovery script from 58% success at about 150 seconds per attempt to 96% at about six seconds; the finished script, then tested with no agent involved, recovered the lock in 695 of 700 trials (99.3%).

Corrected from the old overview
The old page said QuEra went "from 58% to 99.3%" and Janelia "from weeks to a day". The 58% and 99.3% are two different measurements (the starting script, and the finished script's blind test; the overnight run itself reached 96%), and Janelia's figure is per-device integration time, "multi-day project" to "a few minutes". One device item in the old overview had no primary source and is left out (src/unconfirmed.md).

15. The trust boundary for irreversible actions

Every protocol on this page meets the same moment: an action that cannot be taken back (spending money, deleting data, moving a robot arm, granting access). Text arriving over a protocol, from a tool, a remote agent or a web page, can be written by an attacker, so it must never be enough to authorise such an action. What each protocol provides at that moment, the orange gates of the hero:

ProtocolThe "stop here" mechanismWho decidesWhat carries the decision
MCPelicitation; tool annotations such as destructiveHint (hints, not enforcement)the user, through the hostthe host's UI

AP2mandates signed on a trusted surfacethe user, in advance or per purchasea signature verified in deterministic code

The pattern, as a checklist for anything you build:

  1. Name the irreversible actions and give each a protocol state, not a sentence in a tool result: a state can be logged, timed out, audited and tested.
  2. Put the approval outside the model's channel (a dialog, a merchant page, a signed mandate, an out-of-band grant), something text in the context window cannot fake.
  3. Show the person what they approve, rendered by deterministic code (AP2's non-agentic trusted surface), never a model's summary of it.
  4. Enforce limits below the model (MHS's device limits, AP2's budget constraints, a wallet's spending cap, an API scope).
  5. Bind credentials to one audience and one agent (token exchange, AP2's hash binding, A2A's out-of-band credentials).
  6. Prefer producing a reviewable artefact (a script, a closed checkout, a plan) over acting directly, when the action can wait.
  7. Never retry an irreversible action blindly; use idempotency keys where the protocol has them (UCP and ACP checkout completion, A2A messageId, x402's nonce) and read the state before trying again.

Interview rehearsal (design angles, with model answers)

Your orchestrator calls a third-party agent for a user. How do credentials flow? The user's token is for my service only. I exchange it (RFC 8693) for a token whose audience is the third-party agent and whose scope is just this call. If the agent later needs more (the user's bucket), it moves the task to auth-required and obtains the credential out of band, directly, never through my messages.

How would you secure push notifications? On the agent: screen webhook URLs against private and link-local ranges, time out, retry with backoff, authenticate to the webhook as configured. On the receiver: verify the token, accept only known task ids, return 2xx fast, process idempotently, and re-read the task before acting on a terminal state.

An agent may spend money on its own: which protocol, and where is the limit? With a person in the loop, UCP's escalation or AP2's human-present mandate; unattended, AP2's open mandate (merchants, items, amount range, budget) verified in deterministic code, or x402 with a wallet whose spending cap is enforced outside the model. Never a limit stated only in the prompt.

What did the Model Hardware Standard pilots teach about physical actions? Enforce limits in the device layer; models treat physical failures as software errors and retry; the best output may be a reviewed deterministic script (QuEra's 99.3% blind test ran with no agent); a cautious agent costs time and is the safer default.
