5. Hearing back: wait, poll, stream, or be called

An evaluation takes minutes, and an HTTP request held open for minutes dies at the first proxy timeout ({{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}}). A2A separates starting work from following it, with four ways to follow (spec section 3.5):

WayHowGood forCosts, and how it fails
WaitSendMessage, blocking by defaultshort tasksheld open; long tasks hit timeouts
PollGetTask every few seconds (historyLength caps the history returned)simple clients, strict firewallsone poll interval of latency, wasted requests
StreamSendStreamingMessage or SubscribeToTask: one response carrying Server-Sent Eventsinteractive use, progressa long-lived connection that can drop; needs capabilities.streaming
Pushregister a webhook; the agent POSTs each updateserver to server, hours-long tasksyou run a reachable, authenticated endpoint; at-least-once, so duplicates

One job, followed four ways

Each streamed update is one SSE event, data: {"result": {...}}, in one text/event-stream response (the format is {{Streaming and real-time|n:3c65c17b0d0d812daa9fdb38719fc82b}}'s). It starts with the Task, then status and artifact updates, and the server closes it when the task is terminal. When the stream drops, the task does not care


The most common A2A bug is treating the stream as the task. The lab started a six-shard job, read four events, hung up, waited and came back (the "Stream dropped" recording above, on a time axis here):


    

  • While nobody was listening the task kept working (a GetTask in between said so). SubscribeToTask "MUST return a Task object as the first event", the current state with every artifact so far (spec section 3.1.6). The snapshot held all four shards finished by then; live events continued from there. Status messages sent while you were away may be gone, which is why results belong in artifacts. So persist task ids and resubscribe or poll on reconnect.

Push notifications


For an hours-long job Team A registers a webhook (taskPushNotificationConfig) and asks for an immediate return; the agent then POSTs every update: seven POSTs for one task (the task, working, four artifact pieces, completed), the "Push to a webhook" recording above.


    

  • Receiving: the payload is the same StreamResponse as a stream event (section 4.3.3; the SDK sent application/json, the spec's example shows application/a2a+json: accept both). The SDK sent your per-task token as X-A2A-Notification-Token and your registered credentials as Authorization: Bearer .... Check them on every POST, accept only task ids you created, answer 2xx, and deduplicate: delivery is "at least once" ({{webhook discipline|n:3c65c17b0d0d812daa9fdb38719fc82b}}).
    • 

  • Sending is an SSRF risk: a webhook URL is a URL your agent fetches for a stranger, who may register a cloud metadata address such as 169.254.169.254 or an internal host. The spec says agents "SHOULD" reject private, loopback and link-local addresses (section 13.2). The SDK ships validate_push_notification_url but its default is no screening: the lab's first agent accepted a loopback webhook, and a second agent with the validator on refused it with InvalidParamsError: Invalid push notification URL (recorded). Turn it on, or send through an egress proxy.
