The idea in one screen

Every request carries a credential that answers two questions, who is calling (authentication) and may they do this (authorization); good auth makes every copy of a credential worth as little as possible to whoever steals it: addressed to one audience, a few scopes, minutes of life, bound to a key where it matters, and never forwarded onward, only exchanged for a new one.

Fig. 1 · Each hop gets its own narrow token; the forwarded one is refused

  1. Token A, for one audience. The agent (an MCP client) runs the code flow with a PKCE verifier and resource = the MCP server, and receives token A: audience (aud) the MCP server, files:read, 300 s, plus a rotating refresh token (section 4).
  2. A opens one server. The agent calls a tool with Authorization: Bearer A; the MCP server checks signature, iss, aud, exp and scope before running it.
  3. Forwarding A is refused. If the MCP server passed A on to the mail API, the mail API would answer 401 "Audience doesn't match": A was never addressed to it (sections 8 and 9).
  4. Exchange A for B. The MCP server instead hands A to the authorization server with an assertion signed by its own key, and receives token B: audience the mail API, narrowed to mail:read, with an act claim naming the MCP server.
  5. B opens the mail API, and names both. The mail API accepts B under the same strict checks and sees alice, acted for by the MCP server: ready for policy and audit.
  6. A stolen copy is worth little. A thief who copies A from a log gets 300 s of files:read at one server, and nothing at the mail API. If A were bound to a key (DPoP or mTLS, section 7) the copy would be useless.

Status of the specs (checked 5 October 2026)
  • OAuth 2.1 is still an Internet-Draft: revision 16, 3 September 2026 (datatracker). It removes the implicit and password grants, requires PKCE (with one narrow exception), drops the PKCE "plain" method and requires exact redirect URI matching.
  • The security rules it consolidates are already an RFC: the OAuth 2.0 Security Best Current Practice, RFC 9700 (January 2025). Browser apps got their own BCP in August 2026: RFC 10017.
  • MCP's 2026-07-28 revision makes Client ID Metadata Documents the preferred way for a client to identify itself and deprecates dynamic client registration (MCP authorization, 2026-07-28). The spec cites the CIMD Internet-Draft at revision 00; the draft has since reached revision 02 (6 July 2026, datatracker). It cites OAuth 2.1 draft 13; the current draft is 16.
  • GitHub Actions OIDC tokens for repositories created after 15 July 2026 carry an immutable subject with owner and repository IDs (GitHub docs): cloud trust policies written against the old format do not match them (section 7).

1. 401 or 403, and where a credential rides

The server first authenticates the credential (genuine, unexpired, meant for me?), then authorizes the action (may this principal read this file?). The two fail with different status codes, and the difference tells a client what to do next:

401 Unauthorized

Despite its name, unauthenticated: no credential, or one the server cannot accept (bad signature, expired, wrong audience). The server MUST say how to authenticate in a WWW-Authenticate header (RFC 9110 s15.5.2). A fresh credential can fix it.

403 Forbidden

The server knows who you are and the answer is no (RFC 9110 s15.5.4). A new token with the same rights will not help; more rights might. OAuth signals the scope case with error="insufficient_scope" (RFC 6750 s3.1).

A real 401 from the lab: a token minted for the mail API, presented to the MCP server. The header names the problem class and, in the MCP style, points to the document that says where to get a proper token (resource_metadata, section 9).



recorded For a request with no credential, RFC 6750 says the server "SHOULD NOT include an error code" (s3.1); the MCP SDK 2.3.0 server sends error="invalid_token" then too (the first step of the recorded flow on MCP, section 7), so a client cannot tell "no token" from "bad token" by the error code alone.

Bearer against bound is the distinction that matters most. RFC 6750 defines a bearer token as one accepted from anyone who presents it (s1.2). API keys, session cookies and ordinary access tokens are all bearer credentials: a copy in a log file, a crash dump, a notebook or a model's context window is as good as the original. A sender-constrained credential also needs proof of a private key (a DPoP proof per request, or the TLS client certificate the token was issued to); section 7 shows a stolen bound token failing three ways.

2. API keys: the simplest credential, done properly




Your backend calls an LLM provider thousands of times a day, with no user to ask and no browser to redirect; the provider only needs to know which account to bill and limit. The root page's running request carries the answer in one header, x-api-key: sk-wirelab-not-a-real-key (a fake): a long random string the provider generated, showed you once and remembers. Whoever presents it is the account.


    

  • One key per service and environment. When staging's key leaks you revoke staging, and per-key usage tells you who spent what. Providers rate-limit per key or per organisation, so one runaway job on a shared key throttles everyone (429 with retry-after; the Failure lab case "429 Too Many Requests with Retry-After" shows the headers).
    • 

  • Store it in a secrets manager and inject it at run time: not in git, a notebook (outputs and cell history get shared), a Docker image layer, or a browser or mobile app (anyone can read it out). Redact Authorization and key headers at the logger: access logs, proxy debug logs and tracing spans are where bearer credentials most often leak.
    • 

  • Rotate with overlap. Create key 2, deploy it everywhere, watch key 1's usage fall to zero, then revoke key 1. Revoking first is an outage.
    • 

  • Show only a hint () in dashboards and logs, so people can tell keys apart.
    • 



What a key cannot do: it carries no user (every call is "the account"), no consent, no expiry unless you add one, and no audience narrower than the whole provider. Fine for your backend calling your provider; wrong once a third party (an app, an agent) acts for one of your users, which is what OAuth is for (section 4).






A good key says what it is, is unguessable, and can be rejected without a database lookup






recorded A lab key in the shape of GitHub's 2021 token redesign (GitHub blog, 5 April 2021). Prefix lab_: secret scanners (GitHub's, your CI's, your log pipeline's) match it with almost no false positives, and an underscore keeps double-click selection whole. Body: 30 characters from 62 symbols carry 30 × log2(62) =  bits (GitHub quotes 178), so the server can store a plain SHA-256 of the key rather than the slow, salted hash a human-chosen password needs: there is nothing to brute-force. Checksum: the last six characters are a CRC32 of the body in base 62.




Predict, then reveal


A notebook that worked yesterday now gets 401 from the LLM provider on every call; your colleague's identical notebook works. The key in your environment variable has the right prefix. What do you check first?


Reveal
Which key the process actually sees, and whether it is still active: print its hint (prefix and last four characters), not the key, and compare with the provider's dashboard. Usual causes: a key revoked in a rotation, a staging key against the production endpoint, or a stale value cached by the kernel or a .env file loaded before the change. A 401 says "this key is not accepted"; a 403 would say "this key is fine but may not use this model or workspace".






3. Sessions against tokens: where the truth lives




HTTP forgets everything between requests, so after one password the site needs every later request to say "still me". The two answers differ in one thing: whether the server keeps the truth or hands it to the client.


The cookie. Set-Cookie: __Host-sid=...; Path=/; Secure; HttpOnly; SameSite=Lax: Secure keeps it off plain HTTP, HttpOnly hides it from page scripts, and SameSite=Lax keeps it off requests other sites trigger in the background, the main defence against CSRF (cross-site request forgery: a malicious page making your browser send a request to your bank, cookie included). The attributes, including the __Host- prefix that stops a sibling subdomain planting or overwriting the session cookie, are taught on HTTP (section 4).


Browser apps and OAuth. A single-page app that holds OAuth tokens in JavaScript exposes them to any injected script. The August 2026 BCP for browser apps, RFC 10017, describes three architectures and "strongly recommends" the BFF (right panel) for business apps, sensitive apps and apps handling personal data (s6.1); the pattern where the browser holds the tokens itself (s6.3) is "not recommended" for those apps.






A session ID points at the truth; a self-contained token is the truth; a BFF keeps tokens off the browser




Session: the cookie is a pointer
Log out, or "sign out everywhere", deletes the row: every copy of the cookie dies at once.


Self-contained token (JWT)
The API trusts the signed contents, so "log out" cannot reach a token already issued: it stays valid until exp (recorded in section 6).


Backend for frontend (BFF)
A small server-side component runs the OAuth flow and keeps the tokens; the browser holds only an HttpOnly cookie.




illustrative For a website's own users, server-side sessions remain the simpler and safer default; tokens earn their place when a third party, a mobile app or another service is involved.




Predict, then reveal


Your internal labelling tool stores a JWT in localStorage and sends it as a Bearer header. Someone proposes moving it to a cookie "for security". What do you gain, and what new risk appears?


Reveal
Gain: with HttpOnly, an injected script can no longer read the token and send it away (it can still act within the page while it runs). New risk: the browser now attaches the credential automatically, which opens CSRF; you need SameSite=Lax or Strict (and for state-changing requests, a CSRF token or a custom header check). RFC 10017's BFF pattern is this move done fully: tokens stay on a server, the browser holds only a session cookie.






4. OAuth 2.1: letting an app act for a user


alice wants a CLI agent to read her files on a cloud drive. Pasting her drive password into the agent would let it do everything she can, forever, indistinguishable from her. OAuth replaces the password with a delegation: the drive's login server asks alice once whether this app may do these things, and if she agrees gives the app a short-lived, limited token. The app never sees her password. Four roles, named in every spec (OAuth 2.1 draft-16 s1.1):




Resource owner
alice, whose data it is.


Client
The app or agent (a CLI, a web app, an MCP client). Public clients (CLIs, desktop and mobile apps, browser code) cannot keep a secret; confidential clients (servers) can.


Authorization server (AS)
Logs alice in, asks for consent, issues tokens: accounts.google.com, Microsoft Entra, Okta, Auth0, Keycloak, or your own.


Resource server (RS)
The API that holds the data and accepts the tokens: the drive API, an MCP server.

The flow for anything a person logs into: web and mobile apps, CLIs, desktop agents, MCP clients. The parameters you will debug in every authorization URL (a recorded one is in the flow on MCP, section 7):


    

  • response_type=code: ask for a one-time authorization code, not a token. The code comes back through the browser, the leaky part; the tokens come back on a direct, TLS-protected call from the client to the AS's token endpoint.
    • 

  • code_challenge, code_challenge_method=S256 (PKCE, RFC 7636): the client invents a random code_verifier, sends only its SHA-256 (base64url), and must present the verifier to redeem the code.     • 

  • state: a random value the client checks on return, so an attacker cannot feed it a response to a request it never made (CSRF on the callback).
    • 

  • redirect_uri: must exactly match a registered value (RFC 9700 s4.1.3); pattern matching let attackers register lookalike paths and receive codes. Correction to the old page
The old page said PKCE is "mandatory even for confidential clients". OAuth 2.1 draft-16 is one notch softer: PKCE is required unless the client is confidential and the AS has reasonable assurance it implements the OpenID Connect nonce correctly; even then PKCE stays recommended, because only PKCE lets the AS refuse an injected code before issuing any token (draft-16 s7.5.1.1). The draft also removed the redirect_uri parameter from the token request (s10.2); the MCP SDK 2.3.0 client still sends it (visible in the recording), and servers ignore it.





Refresh tokens: rotation catches a copy


Access tokens stay short (the lab's live 300 s) so a stolen one expires soon; a refresh token lets the client get new ones without sending alice through the browser again. Being long-lived, it is precious, so OAuth 2.1 requires that a public client's refresh tokens be sender-constrained (DPoP or mTLS) or rotated: each refresh returns a new refresh token and invalidates the old one, and if an old one is ever presented again someone has a copy, so the AS revokes the whole grant (draft-16 s4.3.1).






The thief's replay of a spent refresh token revokes the grant, logging out the real client too




recorded Statuses and error texts from the lab AS: "refresh token reuse detected; grant revoked", then "refresh token invalid or revoked". The AS cannot tell which of the two presenters was the thief, so both lose: one forced re-login against a silent, long-lived compromise. The same mechanism bites honest code: two processes sharing one refresh token look exactly like this (section 10).





Client credentials: a service acting as itself


With no user (a nightly batch job calling an internal API), the client authenticates as itself at the token endpoint and receives a token whose subject is the client. How it authenticates matters more than the grant: a shared secret in a Basic header (a secret to store and rotate), or better private_key_jwt, a short JWT assertion the client signs with its own private key and the AS checks with the registered public key (RFC 7523 s2.2), so no shared secret exists at all (the lab's MCP server authenticates this way in section 8). recorded with a secret:







The device grant: logging in a box with no browser


A GPU node over SSH, a TV, a CLI in a container cannot open a browser. The device asks the AS for a secret device code and a short user code, alice types the user code on her phone, and the device polls the token endpoint until she approves (RFC 8628). Polling rules: wait interval seconds (5 if unspecified); on slow_down, add 5 seconds for good (s3.5).


The user code is short on purpose: RFC 8628's own example, 8 characters from a 20-letter alphabet, carries 8 × log2(20) =  bits, enough only because of rate limiting and expiry (s6.1). The flow's real weakness: the user approves a code someone else started. In the Storm-2372 campaign, attackers sent victims device codes disguised as meeting invitations, and the victims' approvals gave the attackers tokens; Microsoft's advice is to block the device flow wherever it is not needed (Microsoft Threat Intelligence, 13 February 2025).

5. OpenID Connect: who logged in




OAuth answers "may this app call this API?" and deliberately says nothing about who the user is: an access token is addressed to the API, and the client is not even supposed to read it. Apps that wanted "Sign in with Google" abused access tokens as proof of identity, which is unsafe (a token issued to a different app could be replayed to yours). OpenID Connect adds the missing piece on top of the same code flow (OIDC Core 1.0):


    

  • Request scope openid and the token response also carries an ID token: a signed JWT about the login, addressed to your app (aud = your client_id), with iss, sub (a stable user ID, unique per issuer), exp, iat, auth_time and the nonce your app put in the authorization request (s2, s3.1.3.7).
    • 

  • A UserInfo endpoint returns profile claims (email, name) for an access token with the right scopes.
    • 

  • Discovery (OIDC Discovery 1.0): the provider describes itself at /.well-known/openid-configuration, including where its signing keys are (jwks_uri).
    • 



The rule people break: the ID token is for the app to learn who logged in. Never send it to an API as a credential, and never accept one as an access token. They look alike (both JWTs, often from the same issuer and key), which is why the JWT best practices ask for explicit typing (RFC 8725 s3.11); in section 6's validator, "An ID token, not an access token" passes signature, issuer and audience, and only the typ check stops it.






Same issuer, same key, same signature check: only typ (and the login fields) tell an ID token from an access token




recorded Two of the recorded tokens from section 6's validator, decoded; differing rows highlighted. The access token says typ: at+jwt (RFC 9068 s2.1); the ID token says JWT and carries nonce and auth_time. Here the client and the API share one identifier, so even aud matches.

Predict, then reveal


Your app validates the ID token's signature against Google's JWKS and checks exp. It does not check aud. What can an attacker who runs another site with "Sign in with Google" do?


Reveal
Log in to your app as any user who ever signed in to their site: they hold genuine Google ID tokens for those users, signed with the same keys, but with aud = their client_id. Without the audience check, your app accepts them. OIDC Core requires the client to verify that aud contains its own client_id (s3.1.3.7, rule 3), and the nonce check ties the token to your own login request.






6. JWTs: tokens a server can check alone




If every API call made the API ask the AS "is this token good?", the AS would carry the whole system's traffic and latency. A JSON Web Token puts the answer inside the token and signs it, so any API holding the AS's public key verifies it offline in microseconds (RFC 7519). The family, all May 2015: JWS (signed, RFC 7515), JWE (encrypted, RFC 7516), JWK (keys as JSON, RFC 7517), JWA (algorithm names, RFC 7518) and JWT (the claims). "JWT" in conversation almost always means a JWS-signed JWT.






Three base64url pieces: anyone can read the first two; only the signature needs a key






recorded An RS256 access token from the lab, decoded by this page's JavaScript: a header (algorithm and key ID), a payload (the claims) and a signature over the ASCII bytes base64url(header) + "." + base64url(payload). Base64url is an encoding, not encryption: put no secrets and no more personal data than needed in claims; use JWE or an opaque token if the contents must stay private.




The algorithms, measured

  • RS256 is the most widely deployed (Google, Microsoft and GitHub Actions list only RS256 in the discovery documents of section 5). Validating a JWT, in order


Fig. 3 · The recorded good token as three plates, checked in order by a verifier that chooses the algorithm and the key itself


    

  1. Three pieces. The token splits at its two dots into header, payload and signature, drawn to scale with their base64url lengths. Anyone can decode the first two; only the signature needs a key.
    2. 

  2. Choose the algorithm yourself. Accept only the algorithm(s) you expect for this issuer; never let the token's alg header decide (RFC 8725 s3.1). In PyJWT that is algorithms=["RS256"], required since 2.0.0 (changelog); applications that passed "every algorithm" there were still open to key confusion until 2.4.0 (CVE-2022-29217).
    3. 

  3. Choose the key yourself. Look the kid up in the issuer's JWKS, fetched from the jwks_uri in its discovery document and cached. Never fetch keys from a URL inside the token (jku, x5u); never treat kid as a file path or a database query.
    4. 

  4. Verify the signature. RS256 over the ASCII bytes of header, dot, payload, with the key just chosen; for the recorded token the pinned verifier said "RS256 with the issuer's key: signature valid".
    5. 

  5. Check the type (typ: at+jwt) so an ID token or another JWT from the same issuer is not accepted as an access token (RFC 8725 s3.11).
    6. 

  6. Check iss equals the issuer you trust and aud contains your own identifier (s3.8, s3.9). Skipping aud "because it is our own issuer" is the classic bug: the same issuer mints tokens for every API you own, so a token for the least important one opens all of them.
    7. 

  7. Check time: exp in the future, nbf/iat not in the future, with a small leeway (seconds to a couple of minutes) for clock skew.
    8. 

  8. Only now authorize: scopes, roles, tenant, the specific object.

7. Beyond bearer: bound tokens, signed requests, cloud IAM and mTLS


Every credential so far is a bearer credential: steal it and you are the owner. Four designs make a stolen copy not enough.




DPoP: a token that only works with its key


The client generates a key pair and keeps the private key (RFC 9449, September 2023). With every request, to the token endpoint and to the API, it sends a DPoP header: a small JWT signed with that key. The AS puts the key's thumbprint (RFC 7638) into the token; the API checks that the proof was signed by that same key, for this request, just now.


Cost: one ES256 signature per request on the client (about  µs here, from the table in section 6), one verification and a replay cache of recent jti values on the server. Not stopped: malware inside the client can ask it to sign proofs (RFC 9449 s11.4); the server-provided nonce (s8, s9) limits proofs made in advance. Use it for public clients holding valuable refresh tokens (OAuth 2.1 accepts it in place of rotation) and APIs where a token leaked into a log would be serious. The older alternative binds the token to a TLS client certificate (RFC 8705), natural where mTLS already exists.

Fields per RFC 9449 (s4.2 and s6.1); the URL is illustrative, the thumbprint recorded. SigV4: AWS signs every request instead of sending a token


You hold an access key ID (public) and a secret access key (never sent). For each request the SDK builds a canonical request (method, path, sorted query, lowercased sorted headers, the signed-header list, the SHA-256 of the body), hashes it into a string to sign with the timestamp and a credential scope (date, region, service), derives a signing key by chaining HMACs of the secret over date, region, service and the literal aws4_request, and sends the final HMAC as the signature (AWS: create a signed request).


What this buys: the secret never crosses the wire, so a logged request leaks no reusable credential; the body hash stops anyone in the middle changing the request; the timestamp makes a captured request expire ("in most cases, a request must reach AWS within five minutes of the time stamp", AWS SigV4 overview). Cost: every client needs an SDK or these steps done exactly (header case, whitespace and URI encoding cause most SignatureDoesNotMatch errors), and clock skew beyond a few minutes breaks every call.

Cloud IAM and workload identity: no long-lived secrets at all


The best secret is one you never store. Code on an EC2 instance, a Lambda or a pod gets temporary credentials for its role from the platform (access key, secret and a session token sent as X-Amz-Security-Token), the SDK refreshes them before they expire, and IAM policies on the role decide what it may do: calling Bedrock, SageMaker or S3 from your own AWS code needs no key at all. mTLS: identity in the connection


With mutual TLS both sides present certificates in the handshake, so a service's identity is proven before any HTTP byte flows and there is no header to leak. Service meshes automate the hard part (issuing and rotating short-lived certificates per workload; SSH does the same for people and hosts with CA-signed short-lived SSH certificates, SSH section 4); SPIFFE standardises the identity as a URI such as spiffe://prod.example/ns/serving/sa/vllm inside the certificate (SPIFFE ID spec). Authorization then works on that name ("the gateway may call vLLM; the notebook may not"). The handshake, chains and failure modes are on TLS and certificates; the root's Failure lab has "mTLS: client certificate missing".

8. Token exchange: calling onward without forwarding


Service A received alice's token, addressed to A, and must call service B for her. Forwarding her token is wrong: B is not its audience, and if B accepts it anyway every token for A becomes a token for B. Using A's own all-powerful service credential is also wrong: B can no longer tell which user is behind the call, and A can be tricked into acting for the wrong user. The standard answer is token exchange (RFC 8693, January 2020): A authenticates to the AS as itself, hands over the token it received as the subject_token, names the target with resource or audience, and receives a new token for B, usually with narrower scopes.

9. Agent-era auth: MCP authorization, audience binding, no token passthrough


An agent holds credentials and decides what to do with them from text it reads, some written by strangers (a web page, an email, a tool result). Auth cannot stop an agent being talked into misusing a credential it legitimately holds; that is the lethal trifecta and the harness's job (Agent security; Simon Willison named it, 16 June 2025). What auth can do is decide how much each credential is worth when that happens, and keep credentials from travelling further than intended. This section is MCP's authorization part, quoted from MCP 2026-07-28, Authorization and its sub-pages and checked against the official Python SDK; the protocol itself is on MCP.


MCP's authorization profile, seen from OAuth


Authorization is optional in MCP and applies to the HTTP transport; a local server started over stdio "SHOULD NOT follow this specification, and instead retrieve credentials from the environment". For a remote server MCP composes the pieces of sections 4 to 6 into one profile: a 401 whose WWW-Authenticate points to the server's protected resource metadata (RFC 9728), the authorization server's metadata (RFC 8414), a client identity without prior registration (a Client ID Metadata Document; dynamic client registration is now deprecated), PKCE S256, the resource parameter that binds the token to one server, an issuer check (RFC 9207) before the code goes anywhere, and Authorization: Bearer on every request, never the query string. The profile itself, recorded step by step with the official SDK (including the mix-up the SDK refused), is MCP's: MCP, section 7. Two of its OAuth rules apply beyond MCP: the client MUST refuse to proceed if the authorization server's metadata lacks code_challenge_methods_supported, and for public clients the AS MUST rotate refresh tokens. The rest of this section is the OAuth mechanics an MCP deployment depends on.



Audience binding: the server checks the token is for it


"MCP servers MUST validate that access tokens were issued specifically for them as the intended audience" and "MUST only accept tokens that are valid for use with their own resources." The client's half is the resource parameter, which asks the AS to put the server's URI in aud; the server's half is the 401 in section 1, a mail-API token refused by the MCP server.


A default worth knowing (MCP Python SDK 2.3.0)
The SDK's resource-server mode has a setting AuthSettings.validate_token_resource. In 2.3.0 it is off by default: with resource_server_url set and the setting left unset, the SDK warns that bearer tokens "are not checked against resource_server_url" and says the default becomes True in 3.0 (read from the installed package's mcp/server/auth/settings.py). Audience checking is then entirely up to your token verifier. The lab's server turns the setting on and passes the expected audience to PyJWT; do both.



No token passthrough


"MCP servers MUST NOT accept or transit any other tokens"; when a server calls an upstream API, "the access token used at the upstream API is a separate token, issued by the upstream authorization server. The MCP server MUST NOT pass through the token it received" (security considerations). Section 8's before/after is this rule recorded: a careless upstream accepts the forwarded token and believes alice's MCP client called it directly, so the MCP server, the actual caller, is invisible in its logs and to its per-client limits (the accountability failure the spec's best-practices page lists), and anyone holding a token for the MCP server reaches the mail API through it.

The confused deputy, MCP's version


An MCP server that fronts a third-party API with one static OAuth client ID is a deputy acting for many users. The spec's best-practices page walks through the attack (Confused Deputy Problem): alice once approved the proxy at the third-party AS, which set a consent cookie; an attacker registers a new client with the proxy (dynamic registration) using their own redirect URI and sends alice a link; the third-party AS sees the cookie, skips consent, and the code lands at the attacker. Required fixes on the proxy: per-client consent stored server-side before forwarding to the third party; a consent page that names the client, its scopes and its redirect URI; exact redirect matching; a state stored only after consent; consent cookies with the __Host- prefix, Secure, HttpOnly, SameSite=Lax and bound to the specific client_id.



Credential rules for agents


    

  • Out of the model's context. Anything in a prompt or tool result can be repeated into a tool call by an injected instruction, so tokens live in the client and server processes, attached by code to HTTP requests; how a harness enforces that is on Agent security (section 8, "the model cannot leak what it never sees").
    • 

  • Per user, per server. A server keeps upstream tokens per verified user, keyed by the token's sub, never by something the client sends. The same rule covers state handles in the stateless 2026-07-28 protocol: possession of a handle is not authentication; key stored state by <user_id>:<handle> with the user ID from the verified token ("State Handle Hijacking").
    • 

  • Better still, the agent never holds the secret. A broker keeps the credential and injects it outside the model's reach: 1Password for Agents (22 October 2026) has the agent ask for a login, a person approve it in 1Password, and 1Password fill the site's form, "so the agent never sees the password or one-time code" (1Password); NVIDIA's OpenShell runtime injects credentials only into requests to approved endpoints (OpenShell). What the agent can leak is then a request, not a key.
    • 

  • Short-lived, even on a laptop. The long-lived tokens that developer CLIs store are bearer credentials an agent on the same machine can read. In the October 2026 LiteLLM compromise a stolen GitHub CLI token let the attacker override branch protection and publish a backdoored release through the project's own pipeline (LiteLLM incident report); the same week GitHub's CLI added opt-in expiring tokens with a rotating refresh token (gh auth login --expiring), so "a leaked access token becomes unusable within hours instead of lasting indefinitely" (GitHub changelog). That is section 4's refresh-token rotation applied to a CLI.
    • 

  • Local servers get only their own secrets. A stdio server inherits environment variables from the host that starts it; give it only the variables it needs, not your whole shell environment.
    • 

  • Scopes small, then step up. Start read-only and let the server challenge with 403 insufficient_scope when a write is first attempted; the spec lists publishing every scope in scopes_supported, wildcard scopes and bundling unrelated privileges as common mistakes ("Scope Minimization"). Separate destructive scopes let the server enforce human approval of irreversible actions, which a host confirmation outside the conversation provides (Agent security, human approval).
    • 

  • Clients: server-supplied URLs are hostile. An authorization URL from a malicious server can be javascript: or carry shell metacharacters; clients MUST allow only http(s) (http only for loopback) and MUST NOT open URLs through a shell ("OAuth Authorization URL Validation").
    •

Interview rehearsal (eleven questions, model answers)


What is the difference between authentication and authorization, and how does HTTP show it?
Authentication establishes who the caller is; authorization decides whether that caller may perform this action. A failed or missing credential is 401 with a WWW-Authenticate challenge; a valid credential without permission is 403 (with OAuth, error="insufficient_scope").


Walk me through the authorization code flow with PKCE. What does PKCE protect against?
Client creates a random verifier and sends its S256 hash in the authorization request with state, redirect URI, scope and resource; the user authenticates and consents; the AS redirects back with a one-time code (and iss); the client checks state and iss, then redeems the code with the verifier at the token endpoint over a direct TLS call. PKCE stops an intercepted or injected code from being redeemed by anyone who does not hold the verifier, which matters most for public clients that have no secret.


Why did OAuth 2.1 remove the implicit grant?
It returned the access token in the redirect URL, where it leaks through history, referrers, extensions and logs, cannot be sender-constrained, and can be injected. The code flow with PKCE gives browser apps the same result with the token delivered on a back channel.


How would you validate a JWT access token?
Pin the expected algorithm; pick the key by kid from the issuer's cached JWKS (never from jku/x5u or a kid path); verify the signature; check typ (at+jwt), iss, aud (contains me), exp/nbf with small leeway; then authorize on scopes and the resource. Refetch JWKS on unknown kid, rate-limited.


JWT or opaque token with introspection? Trade-offs.
JWT: offline verification in microseconds, no AS on the hot path, but no early revocation and contents visible to anyone. Opaque with introspection: revocable immediately and private, but every call (or cache window) hits the AS. Common answer: short-lived JWTs plus refresh, with introspection or a denylist for high-value operations.


What is refresh token rotation and what does reuse detection buy you?
Each refresh returns a new refresh token and invalidates the old one. If an invalidated one is presented, two parties hold copies, so the AS revokes the whole grant: a stolen refresh token becomes detectable and short-lived, at the cost of logging the real user out too.


How do bearer tokens differ from DPoP or mTLS-bound tokens?
Bearer tokens work for whoever holds them. Bound tokens carry a confirmation (cnf) of a key; each request must prove possession (a signed DPoP proof covering method, URL, time and the token hash, or the TLS client certificate). A token stolen from a log is useless without the key.


Your service received a user's token and needs to call another service for them. What do you do?
Not forward it. Use token exchange (RFC 8693): authenticate as the service, present the received token as subject_token, request the downstream audience and narrower scopes, and prefer a delegation token with an act claim so the downstream sees both the user and the service.


How does a remote MCP server authorize clients, and what must the server check?
It is an OAuth resource server: 401 with resource_metadata, protected resource metadata naming its AS, the client discovers the AS, identifies itself (pre-registered, CIMD, or deprecated DCR), runs code + PKCE S256 with the resource parameter, checks iss, and sends Bearer tokens on every request. The server must validate each token including that its audience is this server, must not accept tokens for other resources, and must not pass tokens through to upstream APIs.


How do you give a CI job cloud access without storing a cloud secret?
Workload identity federation: the CI platform issues an OIDC token for the job; the cloud's token service exchanges it for short-lived credentials if a trust policy matches iss, aud and an exact sub (repository plus protected branch or environment). Watch for wildcards and for subject format changes.


Why is an API key acceptable for calling an LLM provider but not for a third-party integration?
Server to server under one owner, the key's lack of user context and consent does not matter, and secrets management plus rotation handle its risks. A third party acting for your users needs per-user consent, limited scopes, expiry and revocation per grant: OAuth.
