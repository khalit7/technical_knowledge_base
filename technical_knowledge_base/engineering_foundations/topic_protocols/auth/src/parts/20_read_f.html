5. OpenID Connect: who logged in

OAuth answers "may this app call this API?" and deliberately says nothing about who the user is: an access token is addressed to the API, and the client is not even supposed to read it. Apps that wanted "Sign in with Google" abused access tokens as proof of identity, which is unsafe (a token issued to a different app could be replayed to yours). OpenID Connect adds the missing piece on top of the same code flow ({{OIDC Core 1.0|https://openid.net/specs/openid-connect-core-1_0.html}}):

  • Request scope openid and the token response also carries an ID token: a signed JWT about the login, addressed to your app (aud = your client_id), with iss, sub (a stable user ID, unique per issuer), exp, iat, auth_time and the nonce your app put in the authorization request (s2, s3.1.3.7).
  • A UserInfo endpoint returns profile claims (email, name) for an access token with the right scopes.
  • Discovery ({{OIDC Discovery 1.0|https://openid.net/specs/openid-connect-discovery-1_0.html}}): the provider describes itself at /.well-known/openid-configuration, including where its signing keys are (jwks_uri).

Same issuer, same key, same signature check: only typ (and the login fields) tell an ID token from an access token

The access token says typ: at+jwt ({{RFC 9068 s2.1|https://www.rfc-editor.org/rfc/rfc9068#section-2.1}}); the ID token says JWT and carries nonce and auth_time. Here the client and the API share one identifier, so even aud matches.

The rule people break: the ID token is for the app to learn who logged in. Never send it to an API as a credential, and never accept one as an access token. They look alike (both JWTs, often from the same issuer and key), which is why the JWT best practices ask for explicit typing ({{RFC 8725 s3.11|https://www.rfc-editor.org/rfc/rfc8725#section-3.11}}); in section 6's validator, "An ID token, not an access token" passes signature, issuer and audience, and only the typ check stops it.

Real discovery documents

Three providers, fetched read-only on ; each is a contract a client can check before it sends anyone a password.

  • Key rotation. Google signs ID tokens with RS256 and publishes keys at once, with cache-control: : two keys so it can sign with the new one while tokens signed with the old one are still valid, and a cache lifetime of hours so verifiers do not fetch keys per request. The verifier's rule: cache the JWKS, and when a token arrives with a kid you do not know, refetch once (rate-limited), never per request.
  • An issuer with no users. GitHub Actions mints ID tokens about workflow runs, with claims such as repository, ref and environment, which clouds trade for credentials (section 7).
  • An interoperability snag. Microsoft's common endpoint does not list code_challenge_methods_supported; Entra supports PKCE, but an MCP client following the 2026-07-28 rules literally must refuse to proceed when that field is absent ({{MCP authorization security|https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations}}, "Authorization Code Protection"). Visible only by reading the document.
Predict, then reveal

Your app validates the ID token's signature against Google's JWKS and checks exp. It does not check aud. What can an attacker who runs another site with "Sign in with Google" do?

Reveal
Log in to your app as any user who ever signed in to their site: they hold genuine Google ID tokens for those users, signed with the same keys, but with aud = their client_id. Without the audience check, your app accepts them. OIDC Core requires the client to verify that aud contains its own client_id (s3.1.3.7, rule 3), and the nonce check ties the token to your own login request.
