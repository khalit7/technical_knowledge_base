The idea in one screen

Every request carries a credential that answers two questions, who is calling (authentication) and may they do this (authorization); good auth makes every copy of a credential worth as little as possible to whoever steals it: addressed to one audience, a few scopes, minutes of life, bound to a key where it matters, and never forwarded onward, only exchanged for a new one.

Each hop gets its own narrow token; the forwarded one is refused

recorded in this page's lab (sections 4, 8 and 9 replay each arrow byte for byte). Token A names the MCP server as its audience (aud), allows files:read and lives 300 s; the mail API refuses it because it is not the audience. The MCP server instead trades A for token B, addressed to the mail API, narrowed to mail:read, with an act claim naming the MCP server. A thief who copies A from a log gets 300 s of files:read at one server; if A were bound to a key (DPoP or mTLS, section 7) the copy would be useless.

You need HTTP headers and status codes ({{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}}) and, for mTLS, the TLS handshake ({{TLS and certificates|n:3c65c17b0d0d8105a37ff2d2f602a421}}). The whole stack on one LLM request is {{Topic: protocols|n:3c65c17b0d0d81ec9355f4eecd6eed02}}; this page owns credentials and delegation in depth. The running example: alice lets an agent (an MCP client) read her files through an MCP server, which needs her mail from a mail API; a batch job and a CI pipeline stand in for services with no user.

Status of the specs (checked 5 October 2026)
  • OAuth 2.1 is still an Internet-Draft: revision 16, 3 September 2026 ({{datatracker|https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/}}). It removes the implicit and password grants, requires PKCE (with one narrow exception), drops the PKCE "plain" method and requires exact redirect URI matching.
  • The security rules it consolidates are already an RFC: the OAuth 2.0 Security Best Current Practice, {{RFC 9700|https://www.rfc-editor.org/rfc/rfc9700}} (January 2025). Browser apps got their own BCP in August 2026: {{RFC 10017|https://www.rfc-editor.org/rfc/rfc10017}}.
  • MCP's 2026-07-28 revision makes Client ID Metadata Documents the preferred way for a client to identify itself and deprecates dynamic client registration ({{MCP authorization, 2026-07-28|https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization}}). The spec cites the CIMD Internet-Draft at revision 00; the draft has since reached revision 02 (6 July 2026, {{datatracker|https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/}}). It cites OAuth 2.1 draft 13; the current draft is 16.
  • GitHub Actions OIDC tokens for repositories created after 15 July 2026 carry an immutable subject with owner and repository IDs ({{GitHub docs|https://docs.github.com/en/actions/reference/security/oidc}}): cloud trust policies written against the old format do not match them (section 7).
Where and how this page measured (provenance)

Everything marked recorded was produced on 5 October 2026 by a lab built for this page: an OAuth 2.1 authorization server, an MCP server and client from the official Python SDK (mcp 2.3.0), and two upstream APIs (a mail API with strict and careless checks, a DPoP-protected notes API), all on one Apple M1 Pro laptop with Python 3.13.5, PyJWT 2.15.1 and cryptography 50.0.2, with a recording proxy in front of each server so every byte that crossed the wire was saved (scripts and raw output in this page's src/lab/, rerun with src/run_all.sh). Simulated: the browser and the user (a script fetched the authorization URL and the lab AS approved as alice, so no login or consent page appears); the client metadata host's certificate (a throwaway local CA). Real provider discovery documents were fetched read-only the same day. illustrative marks a picture of a shape, not data.
