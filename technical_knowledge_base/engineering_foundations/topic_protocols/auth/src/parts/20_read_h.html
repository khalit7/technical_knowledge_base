7. Beyond bearer: bound tokens, signed requests, cloud IAM and mTLS

Every credential so far is a bearer credential: steal it and you are the owner. Four designs make a stolen copy not enough.

DPoP: a token that only works with its key

The client generates a key pair and keeps the private key ({{RFC 9449|https://www.rfc-editor.org/rfc/rfc9449}}, September 2023). With every request, to the token endpoint and to the API, it sends a DPoP header: a small JWT signed with that key. The AS puts the key's thumbprint ({{RFC 7638|https://www.rfc-editor.org/rfc/rfc7638}}) into the token; the API checks that the proof was signed by that same key, for this request, just now.

The proof carries the public key; the token carries its thumbprint; they must match

The API checks: the proof's signature verifies with its jwk; thumbprint(jwk) equals the token's cnf.jkt; htm and htu match this request; iat is recent; jti was not seen before; ath is the hash of the presented token. Cost: one ES256 signature per request on the client (about µs here, from the table in section 6), one verification and a replay cache of recent jti values on the server. Not stopped: malware inside the client can ask it to sign proofs (RFC 9449 s11.4); the server-provided nonce (s8, s9) limits proofs made in advance. Use it for public clients holding valuable refresh tokens (OAuth 2.1 accepts it in place of rotation) and APIs where a token leaked into a log would be serious. The older alternative binds the token to a TLS client certificate ({{RFC 8705|https://www.rfc-editor.org/rfc/rfc8705}}), natural where mTLS already exists.

SigV4: AWS signs every request instead of sending a token

You hold an access key ID (public) and a secret access key (never sent). For each request the SDK builds a canonical request (method, path, sorted query, lowercased sorted headers, the signed-header list, the SHA-256 of the body), hashes it into a string to sign with the timestamp and a credential scope (date, region, service), derives a signing key by chaining HMACs of the secret over date, region, service and the literal aws4_request, and sends the final HMAC as the signature ({{AWS: create a signed request|https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv-create-signed-request.html}}).

Predict, then try: change the date by one day. The signing key changes too, which is why a leaked derived key is good for one day, one region, one service.




What this buys: the secret never crosses the wire, so a logged request leaks no reusable credential; the body hash stops anyone in the middle changing the request; the timestamp makes a captured request expire ("in most cases, a request must reach AWS within five minutes of the time stamp", {{AWS SigV4 overview|https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv.html}}). Cost: every client needs an SDK or these steps done exactly (header case, whitespace and URI encoding cause most SignatureDoesNotMatch errors), and clock skew beyond a few minutes breaks every call.



Cloud IAM and workload identity: no long-lived secrets at all


The best secret is one you never store. Code on an EC2 instance, a Lambda or a pod gets temporary credentials for its role from the platform (access key, secret and a session token sent as X-Amz-Security-Token), the SDK refreshes them before they expire, and IAM policies on the role decide what it may do: calling Bedrock, SageMaker or S3 from your own AWS code needs no key at all. Two traps. A wildcard condition such as repo:octo-org/* lets every workflow on every branch of every repository in the organisation assume the role, so anyone who can push a branch anywhere holds its permissions: match the exact repository and a protected branch or environment. And a policy written for the old format silently stops matching new repositories, whose subject includes the numeric IDs; GitHub added them because a deleted organisation or repository name could be re-registered by someone else and inherit the old subject.



mTLS: identity in the connection


With mutual TLS both sides present certificates in the handshake, so a service's identity is proven before any HTTP byte flows and there is no header to leak. Service meshes automate the hard part (issuing and rotating short-lived certificates per workload; SSH does the same for people and hosts with CA-signed short-lived SSH certificates, {{SSH|n:3c65c17b0d0d81f88f50e478c94ebdcd#s-cert}} section 4); SPIFFE standardises the identity as a URI such as spiffe://prod.example/ns/serving/sa/vllm inside the certificate ({{SPIFFE ID spec|https://github.com/spiffe/spiffe/blob/main/standards/SPIFFE-ID.md}}). Authorization then works on that name ("the gateway may call vLLM; the notebook may not"). The handshake, chains and failure modes are on {{TLS and certificates|n:3c65c17b0d0d8105a37ff2d2f602a421}}; the root's {{Failure lab|n:3c65c17b0d0d81ec9355f4eecd6eed02}} has "mTLS: client certificate missing".

Predict, then reveal


A CI job's AWS calls work on GitHub-hosted runners but fail on one self-hosted runner with an error about the signature or the request time. Same code, same role. What do you check first?


Reveal
The runner's clock (date -u against a trusted time source). The timestamp is part of the string to sign and AWS refuses requests that arrive more than a few minutes away from it. After that, look for a proxy on that runner's network that rewrites a signed header (Host, Content-Type) or re-encodes the path, which changes the canonical request.
