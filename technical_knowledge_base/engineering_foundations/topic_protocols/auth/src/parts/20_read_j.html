9. Agent-era auth: MCP authorization, audience binding, no token passthrough

An agent holds credentials and decides what to do with them from text it reads, some written by strangers (a web page, an email, a tool result). Auth cannot stop an agent being talked into misusing a credential it legitimately holds; that is the lethal trifecta and the harness's job ({{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}}; Simon Willison named it, {{16 June 2025|https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/}}). What auth can do is decide how much each credential is worth when that happens, and keep credentials from travelling further than intended. This section is MCP's authorization part, quoted from {{MCP 2026-07-28, Authorization|https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization}} and its sub-pages and checked against the official Python SDK; the protocol itself is on {{MCP|n:3c65c17b0d0d813f9695dc4175c44cbb}}.

MCP's authorization profile, seen from OAuth

Authorization is optional in MCP and applies to the HTTP transport; a local server started over stdio "SHOULD NOT follow this specification, and instead retrieve credentials from the environment". For a remote server MCP composes the pieces of sections 4 to 6 into one profile: a 401 whose WWW-Authenticate points to the server's protected resource metadata ({{RFC 9728|https://www.rfc-editor.org/rfc/rfc9728}}), the authorization server's metadata (RFC 8414), a client identity without prior registration (a Client ID Metadata Document; dynamic client registration is now deprecated), PKCE S256, the resource parameter that binds the token to one server, an issuer check (RFC 9207) before the code goes anywhere, and Authorization: Bearer on every request, never the query string. The profile itself, recorded step by step with the official SDK (including the mix-up the SDK refused), is MCP's: {{MCP|n:3c65c17b0d0d813f9695dc4175c44cbb}}, section 7. Two of its OAuth rules apply beyond MCP: the client MUST refuse to proceed if the authorization server's metadata lacks code_challenge_methods_supported, and for public clients the AS MUST rotate refresh tokens. The rest of this section is the OAuth mechanics an MCP deployment depends on.

Audience binding: the server checks the token is for it

"MCP servers MUST validate that access tokens were issued specifically for them as the intended audience" and "MUST only accept tokens that are valid for use with their own resources." The client's half is the resource parameter, which asks the AS to put the server's URI in aud; the server's half is the 401 in section 1, a mail-API token refused by the MCP server.

A default worth knowing (MCP Python SDK 2.3.0)
The SDK's resource-server mode has a setting AuthSettings.validate_token_resource. In 2.3.0 it is off by default: with resource_server_url set and the setting left unset, the SDK warns that bearer tokens "are not checked against resource_server_url" and says the default becomes True in 3.0 (read from the installed package's mcp/server/auth/settings.py). Audience checking is then entirely up to your token verifier. The lab's server turns the setting on and passes the expected audience to PyJWT; do both.

No token passthrough

"MCP servers MUST NOT accept or transit any other tokens"; when a server calls an upstream API, "the access token used at the upstream API is a separate token, issued by the upstream authorization server. The MCP server MUST NOT pass through the token it received" ({{security considerations|https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations}}). Section 8's before/after is this rule recorded: a careless upstream accepts the forwarded token and believes alice's MCP client called it directly, so the MCP server, the actual caller, is invisible in its logs and to its per-client limits (the accountability failure the spec's best-practices page lists), and anyone holding a token for the MCP server reaches the mail API through it.

The confused deputy, MCP's version

An MCP server that fronts a third-party API with one static OAuth client ID is a deputy acting for many users. The spec's best-practices page walks through the attack ({{Confused Deputy Problem|https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices}}): alice once approved the proxy at the third-party AS, which set a consent cookie; an attacker registers a new client with the proxy (dynamic registration) using their own redirect URI and sends alice a link; the third-party AS sees the cookie, skips consent, and the code lands at the attacker. Required fixes on the proxy: per-client consent stored server-side before forwarding to the third party; a consent page that names the client, its scopes and its redirect URI; exact redirect matching; a state stored only after consent; consent cookies with the __Host- prefix, Secure, HttpOnly, SameSite=Lax and bound to the specific client_id.

Credential rules for agents

  • Out of the model's context. Anything in a prompt or tool result can be repeated into a tool call by an injected instruction, so tokens live in the client and server processes, attached by code to HTTP requests; how a harness enforces that is on {{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}} (section 8, "the model cannot leak what it never sees").
  • Per user, per server. A server keeps upstream tokens per verified user, keyed by the token's sub, never by something the client sends. The same rule covers state handles in the stateless 2026-07-28 protocol: possession of a handle is not authentication; key stored state by <user_id>:<handle> with the user ID from the verified token ("State Handle Hijacking").
  • Better still, the agent never holds the secret. A broker keeps the credential and injects it outside the model's reach: 1Password for Agents (22 October 2026) has the agent ask for a login, a person approve it in 1Password, and 1Password fill the site's form, "so the agent never sees the password or one-time code" ({{1Password|https://1password.com/blog/1password-for-ai-agents}}); NVIDIA's OpenShell runtime injects credentials only into requests to approved endpoints ({{OpenShell|https://github.com/NVIDIA/OpenShell}}). What the agent can leak is then a request, not a key.
  • Short-lived, even on a laptop. The long-lived tokens that developer CLIs store are bearer credentials an agent on the same machine can read. In the October 2026 LiteLLM compromise a stolen GitHub CLI token let the attacker override branch protection and publish a backdoored release through the project's own pipeline ({{LiteLLM incident report|https://docs.litellm.ai/blog/security-incident-oct-21-2026}}); the same week GitHub's CLI added opt-in expiring tokens with a rotating refresh token (gh auth login --expiring), so "a leaked access token becomes unusable within hours instead of lasting indefinitely" ({{GitHub changelog|https://github.blog/changelog/2026-10-21-github-cli-opt-in-to-expiring-auto-refreshing-oauth-tokens}}). That is section 4's refresh-token rotation applied to a CLI.
  • Local servers get only their own secrets. A stdio server inherits environment variables from the host that starts it; give it only the variables it needs, not your whole shell environment.
  • Scopes small, then step up. Start read-only and let the server challenge with 403 insufficient_scope when a write is first attempted; the spec lists publishing every scope in scopes_supported, wildcard scopes and bundling unrelated privileges as common mistakes ("Scope Minimization"). Separate destructive scopes let the server enforce human approval of irreversible actions, which a host confirmation outside the conversation provides ({{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}}, human approval).
  • Clients: server-supplied URLs are hostile. An authorization URL from a malicious server can be javascript: or carry shell metacharacters; clients MUST allow only http(s) (http only for loopback) and MUST NOT open URLs through a shell ("OAuth Authorization URL Validation").
Predict, then reveal

Your company runs one MCP server in front of the internal ticketing API. A teammate suggests: "the client already has the user's SSO token for ticketing, just let the MCP server forward it". List two things that break.

Reveal
(1) Audience binding: the MCP server would have to accept a token not issued for it, so any ticketing token (from any app) would work at the MCP server, and the MCP server would be a convenient proxy for stolen ones. (2) Accountability and control: the ticketing API sees the user's original client, not the MCP server, so it cannot rate-limit, scope or audit what the agent does separately. Correct design: the MCP server is a resource server with its own audience, and it obtains its own ticketing token by token exchange (or the enterprise-managed authorization extension), narrowed to what its tools need.
