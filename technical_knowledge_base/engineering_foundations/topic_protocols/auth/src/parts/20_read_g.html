6. JWTs: tokens a server can check alone

If every API call made the API ask the AS "is this token good?", the AS would carry the whole system's traffic and latency. A JSON Web Token puts the answer inside the token and signs it, so any API holding the AS's public key verifies it offline in microseconds ({{RFC 7519|https://www.rfc-editor.org/rfc/rfc7519}}). The family, all May 2015: JWS (signed, {{RFC 7515|https://www.rfc-editor.org/rfc/rfc7515}}), JWE (encrypted, RFC 7516), JWK (keys as JSON, {{RFC 7517|https://www.rfc-editor.org/rfc/rfc7517}}), JWA (algorithm names, {{RFC 7518|https://www.rfc-editor.org/rfc/rfc7518}}) and JWT (the claims). "JWT" in conversation almost always means a JWS-signed JWT.

Three base64url pieces: anyone can read the first two; only the signature needs a key

recorded An RS256 access token from the lab, decoded by this page's JavaScript: a header (algorithm and key ID), a payload (the claims) and a signature over the ASCII bytes base64url(header) + "." + base64url(payload). Base64url is an encoding, not encryption: put no secrets and no more personal data than needed in claims; use JWE or an opaque token if the contents must stay private.

The algorithms, measured

measured The same claims signed five ways with PyJWT 2.15.1 (Apple M1 Pro, one core; median of 7 runs of 200):

  • HS256 is a MAC with a shared secret: smallest and fastest, but every service that can verify can also mint tokens. Fine inside one service; wrong for an issuer with many verifiers.
  • RS256 is the most widely deployed (Google, Microsoft and GitHub Actions list only RS256 in the discovery documents of section 5). Verification is cheap and signing about ten times slower, which suits one issuer and many verifiers; its 256-byte signature makes tokens roughly twice the size of the others.
  • ES256 (P-256) and EdDSA (Ed25519) give 64-byte signatures. ECDSA needs care: Java 17.0.2 and 18 accepted an all-zero signature as valid for any message and any key, because the verifier skipped the check that r and s are at least 1 ({{CVE-2022-21449|https://www.cve.org/CVERecord?id=CVE-2022-21449}}; {{Neil Madden, "Psychic signatures in Java", 19 April 2022|https://neilmadden.blog/2022/04/19/psychic-signatures-in-java/}}).

Validating a JWT, in order

  1. Choose the algorithm yourself. Accept only the algorithm(s) you expect for this issuer; never let the token's alg header decide ({{RFC 8725 s3.1|https://www.rfc-editor.org/rfc/rfc8725#section-3.1}}). In PyJWT that is algorithms=["RS256"], required since 2.0.0 ({{changelog|https://github.com/jpadilla/pyjwt/blob/master/CHANGELOG.rst}}); applications that passed "every algorithm" there were still open to key confusion until 2.4.0 ({{CVE-2022-29217|https://www.cve.org/CVERecord?id=CVE-2022-29217}}).
  2. Choose the key yourself. Look the kid up in the issuer's JWKS, fetched from the jwks_uri in its discovery document and cached. Never fetch keys from a URL inside the token (jku, x5u); never treat kid as a file path or a database query.
  3. Verify the signature.
  4. Check the type (typ: at+jwt) so an ID token or another JWT from the same issuer is not accepted as an access token ({{RFC 8725 s3.11|https://www.rfc-editor.org/rfc/rfc8725#section-3.11}}).
  5. Check iss equals the issuer you trust and aud contains your own identifier ({{s3.8, s3.9|https://www.rfc-editor.org/rfc/rfc8725#section-3.9}}). Skipping aud "because it is our own issuer" is the classic bug: the same issuer mints tokens for every API you own, so a token for the least important one opens all of them.
  6. Check time: exp in the future, nbf/iat not in the future, with a small leeway (seconds to a couple of minutes) for clock skew.
  7. Only now authorize: scopes, roles, tenant, the specific object.

Weak HMAC secrets fall offline

One captured HS256 token lets an attacker test candidate secrets on their own machine, as fast as they can compute HMACs, with no rate limit. measured Plain Python on one core tried candidates in s ( per second) and found secret123. At that rate every 6-character secret of lowercase letters and digits takes 366 / rate = ; dedicated GPU crackers are faster still (not measured here). {{RFC 8725 s3.5|https://www.rfc-editor.org/rfc/rfc8725#section-3.5}} asks for keys with real entropy: use 32 random bytes, never a word. Integrity rests entirely on nobody else knowing the key, so a guessable secret is as bad as no signature.

The price of offline checking: no early revocation

recorded A client-credentials token was revoked at the AS ({{RFC 7009|https://www.rfc-editor.org/rfc/rfc7009}}); the AS's introspection endpoint ({{RFC 7662|https://www.rfc-editor.org/rfc/rfc7662}}) then reported it inactive, and the MCP server, which validates JWTs offline, still accepted it:

The remedies, cheapest first: short lifetimes (minutes), so a revoked token dies soon anyway; a denylist of revoked jti values pushed to verifiers; introspection on every call for high-value operations, which brings the round trip back. Long-lived access tokens "to avoid refresh logic" turn a leak into an incident you cannot stop: keep minutes and add refresh. This is also why JWTs make poor browser sessions (section 3).
