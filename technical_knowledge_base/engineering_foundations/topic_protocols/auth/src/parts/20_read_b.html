1. 401 or 403, and where a credential rides

The server first authenticates the credential (genuine, unexpired, meant for me?), then authorizes the action (may this principal read this file?). The two fail with different status codes, and the difference tells a client what to do next:

401 Unauthorized

Despite its name, unauthenticated: no credential, or one the server cannot accept (bad signature, expired, wrong audience). The server MUST say how to authenticate in a WWW-Authenticate header ({{RFC 9110 s15.5.2|https://www.rfc-editor.org/rfc/rfc9110#section-15.5.2}}). A fresh credential can fix it.

403 Forbidden

The server knows who you are and the answer is no ({{RFC 9110 s15.5.4|https://www.rfc-editor.org/rfc/rfc9110#section-15.5.4}}). A new token with the same rights will not help; more rights might. OAuth signals the scope case with error="insufficient_scope" ({{RFC 6750 s3.1|https://www.rfc-editor.org/rfc/rfc6750#section-3.1}}).

A real 401 from the lab: a token minted for the mail API, presented to the MCP server. The header names the problem class and, in the MCP style, points to the document that says where to get a proper token (resource_metadata, section 9).



recorded For a request with no credential, RFC 6750 says the server "SHOULD NOT include an error code" ({{s3.1|https://www.rfc-editor.org/rfc/rfc6750#section-3.1}}); the MCP SDK 2.3.0 server sends error="invalid_token" then too (step 1 of the flow in section 9), so a client cannot tell "no token" from "bad token" by the error code alone.

Bearer against bound is the distinction that matters most. RFC 6750 defines a bearer token as one accepted from anyone who presents it ({{s1.2|https://www.rfc-editor.org/rfc/rfc6750#section-1.2}}). API keys, session cookies and ordinary access tokens are all bearer credentials: a copy in a log file, a crash dump, a notebook or a model's context window is as good as the original. A sender-constrained credential also needs proof of a private key (a DPoP proof per request, or the TLS client certificate the token was issued to); section 7 shows a stolen bound token failing three ways.

Reveal
403 Forbidden with WWW-Authenticate: Bearer error="insufficient_scope", scope="files:write", resource_metadata="...". The token is genuine (so not 401); the fix is a step-up authorization that requests the union of the old and the new scopes ({{MCP Scope Challenge Handling|https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#scope-challenge-handling}}).
