4. Certificates: what is inside, and how a client checks a chain

A certificate is an X.509 document ({{RFC 5280|https://www.rfc-editor.org/rfc/rfc5280}}) encoded in DER (binary) and usually stored as PEM (that DER in base64 between -----BEGIN CERTIFICATE----- lines). The leaf is signed by an intermediate CA, which is signed by a root. Roots live offline in vaults and sign rarely; intermediates do the daily issuing, so a compromised intermediate can be revoked without changing every trust store on earth. The server must send its leaf and every intermediate; sending the root is useless (the client must already have it to trust it) but harmless. Fig. 4 walks the chain api.anthropic.com served on 5 October 2026.

Two clients can build two valid paths through the same chain. Path building is a search, not a list: a client starts from the leaf and looks for any issuer it can chain to a root in its store. That matters because of cross-signing, and it is the usual reason for "works in Chrome, fails in Java".

What the client checks, in order

  1. The chain as sent. The server sent three certificates, leaf first: api.anthropic.com (894 bytes), the intermediate WE1 (675) and GTS Root R4 (894).
  2. Signatures up the chain, starting at the bottom: the leaf's signature (ecdsa-with-SHA256) must verify with WE1's public key.
  3. Then each CA above it. WE1's signature (ecdsa-with-SHA384) must verify with GTS Root R4's key. Every certificate above the leaf must say CA:TRUE in Basic Constraints and allow keyCertSign, and a pathlen limit, if any, must hold.
  4. Path A: a root in the trust store. A client that already trusts GTS Root R4 stops there. If no root is found the check fails as unable to get local issuer certificate (missing intermediate, or root not trusted here) or self-signed certificate in certificate chain.
  5. Path B: the cross-sign. The third certificate, "GTS Root R4", is itself signed by "GlobalSign Root CA" (sha256WithRSAEncryption). An older client that only knows GlobalSign follows the cross-sign one step further. Different clients can therefore build different valid paths through the same chain.
  6. Dates: now is between notBefore and notAfter for every certificate (this leaf: 2026-09-21 to 2026-12-20, 90 days). Fails as certificate has expired or certificate is not yet valid (the client's clock is behind).
  7. Name and purpose. The host you dialled must match a subject alternative name (SAN); here the only SAN is api.anthropic.com. Extended Key Usage must include serverAuth for a server (and clientAuth for an mTLS client, section 7); this leaf has serverAuth only.

Name matching in detail. The old Common Name field is ignored: Chrome dropped the fallback in Chrome 58 in 2017 ({{Chrome Platform Status|https://chromestatus.com/feature/4981025180483584}}) and {{RFC 9525|https://www.rfc-editor.org/rfc/rfc9525#section-6.3}} says CN "MUST NOT be used". A wildcard matches exactly one whole left-most label: *.example.com covers a.example.com but not a.b.example.com and not example.com. Dialling an IP address needs an IP SAN (the lab leaf has IP:127.0.0.1). Fails as hostname mismatch or ERR_TLS_CERT_ALTNAME_INVALID.

Policy extras that depend on the client: Chrome and Safari require embedded Certificate Transparency proofs (section 5); some check revocation (section 6); Python 3.13 and later apply VERIFY_X509_STRICT by default, rejecting certificates missing fields RFC 5280 requires, such as the Authority Key Identifier ({{Python 3.13 what's new|https://docs.python.org/3/whatsnew/3.13.html#ssl}}). The parent's {{Failure lab|n:3c65c17b0d0d81ec9355f4eecd6eed02}} case "Python 3.13 rejects a certificate that curl and Node accept" shows the same certificate passing curl and Node and failing Python.

Run those checks yourself on twelve real chains, exactly as the servers sent them (one handshake each with OpenSSL 3.6.5, no HTTP request; src/lab/public_chains.py). Predict before you move anything: api.anthropic.com with the date dragged past 20 December 2026, and a.b.api.anthropic.com as the dialled name. Then pick api.deepseek.com (a wildcard) and dial a name two labels deep, and compare a Google-issued chain (three certificates, ending in a cross-signed root) with pypi.org's (two).

The parent's Failure lab reproduces each failure with real error text: "Expired certificate", "Wrong hostname (SAN mismatch)", "Unknown CA: the issuer is not trusted here", "Missing intermediate certificate", "Clock skew: certificate not yet valid". The first command for all of them:

openssl s_client -connect api.example.com:443 -servername api.example.com -showcerts </dev/null
#  look at: the depth lines (how many certificates came back), "Verify return code", the issuer of depth 0
openssl x509 -in leaf.pem -noout -subject -issuer -dates -ext subjectAltName,extendedKeyUsage

Always pass -servername: without SNI, a server hosting many names may send a default certificate and you will debug the wrong one.
