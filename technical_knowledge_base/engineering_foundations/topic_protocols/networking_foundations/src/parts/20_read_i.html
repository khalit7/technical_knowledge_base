8. The server side: accept queues, shared ports, file descriptors

The kernel completes the handshake on its own; accept() only hands your program a connection that is already established. Finished connections wait in an accept queue as long as the backlog passed to listen(), capped by somaxconn: 4,096 on Linux since 5.4 and 128 before ({{ip-sysctl|https://docs.kernel.org/networking/ip-sysctl.html}}; many tuning guides predate the change), and 128 on this Mac (measured kern.ipc.somaxconn). A server that accepts more slowly than clients arrive (a single process busy loading a model, a rendezvous rank before it calls accept) fills it.

When it is full, Linux drops new SYNs (tcp_conn_request in {{tcp_input.c|https://github.com/torvalds/linux/blob/master/net/ipv4/tcp_input.c}} counts a ListenOverflow and drops), so the client resends its SYN after its 1 s initial timeout, then 2 s later: connects that take 1 s or 3 s instead of a millisecond. A handshake that completes while the queue is full has its final ACK ignored, unless tcp_abort_on_overflow is on, which sends the client a reset instead ({{tcp_minisocks.c|https://github.com/torvalds/linux/blob/master/net/ipv4/tcp_minisocks.c}}; off by default).

  1. listen(2). The server's kernel will complete handshakes by itself and keep at most 2 finished connections waiting for accept(): this experiment's backlog, far below the caps above.
  2. Clients 0 and 1 connect. Their handshakes complete in 0.3 to 0.4 ms and the connections wait in the queue; the server is busy and has not called accept().
  3. Clients 2 to 7 connect too. On this Mac five more connect() calls return success in 0.3 to 0.4 ms and client 4's is reset at once: seven of eight connects succeeded, though only two connections fit the queue.
  4. Every connected client sends its request. Clients 0 and 1 send theirs; the other five get BrokenPipeError: at the server, their connection no longer exists.
  5. The server finally accepts. It gets exactly two connections, reads "hello 0" and "hello 1" and answers both; the five others read "Connection reset by peer".
  6. On Linux a full queue drops the SYN instead. The client resends after 1 s, then 2 s more: connects of 1 s or 3 s (the kernel source above, not measured here).
  7. Many workers, one port. With SO_REUSEPORT each worker process binds the same port with its own queue and the kernel spreads new connections across them, so they accept in parallel (illustrative: four workers).

Seven of eight connects succeeded; only two clients were ever served

measured on this Mac with listen(2) and a server that does not call accept() until all eight clients have tried.

The others learned they had been dropped only when they wrote (broken pipe) or read (reset). A successful connect is not a server that will answer: a client needs a read timeout as well as a connect timeout, and a health check should send a request, not just open a socket.

Many workers, one port. SO_REUSEPORT lets several sockets, typically one per worker process, bind the same address and port, and the kernel spreads new connections across them, so N workers accept in parallel instead of fighting over one queue ({{man 7 socket|https://man7.org/linux/man-pages/man7/socket.7.html}}). SO_REUSEADDR is different and older: it lets a restarted server bind its port while old connections on it are still in TIME_WAIT, which is why almost every server sets it.

Every connection is a file descriptor, and processes have a limit (ulimit -n). A server with thousands of streaming clients, or a dataloader whose workers each hold connections, hits it with EMFILE ("Too many open files"); compare ls /proc/PID/fd | wc -l with the limit.

Seeing the queue on Linux, and file limits under Slurm (a correction) (depth)

ss -lnt: for a listening socket, Recv-Q is the current accept-queue length and Send-Q its limit (idiag_rqueue = sk_ack_backlog, idiag_wqueue = sk_max_ack_backlog in {{tcp_diag.c|https://github.com/torvalds/linux/blob/master/net/ipv4/tcp_diag.c}}). nstat -az TcpExtListenOverflows TcpExtListenDrops counts the drops. Fix: accept faster (more workers, an event loop), raise the backlog in the code and somaxconn, and have clients retry with jitter.

On Slurm clusters a job inherits the soft limits of the shell it was submitted from unless the administrator configured otherwise (PropagateResourceLimits, whose default is to propagate all limits, {{slurm.conf|https://slurm.schedmd.com/slurm.conf.html}}); check inside the job with srun bash -c 'ulimit -n' rather than trusting the login node.

Correction to the old page
The old page said that on Slurm "limits are inherited from slurmd's environment rather than your login shell, so ulimit -n in your .bashrc will not help a job". The current slurm.conf documentation says the opposite by default: slurmd reads the soft limits from the user's environment on the submit node and applies them to the job, unless PropagateResourceLimits or PropagateResourceLimitsExcept is configured. What is true: a cluster can be configured not to propagate, and a job cannot raise a limit above what the node allows.
