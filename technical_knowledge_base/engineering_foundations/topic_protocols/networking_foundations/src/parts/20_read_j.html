9. NAT, idle timeouts and dead peers

A machine with a private address (section 1) reaches the internet through network address translation: a NAT device (a home router, a cloud NAT gateway, a Kubernetes node doing SNAT for its pods) rewrites each outgoing packet's source address and port to its own public address and a port it allocates, and remembers the mapping so it can rewrite the replies back. To the NAT, that table entry is the connection. Two limits follow: the table has a size, and entries that look idle are thrown away.

Idle timeouts are shorter than you think. The IETF asks that an established TCP mapping survive at least 2 hours 4 minutes idle ({{RFC 5382 REQ-5|https://www.rfc-editor.org/rfc/rfc5382#section-5}}) and a UDP mapping at least 2 minutes ({{RFC 4787 REQ-5|https://www.rfc-editor.org/rfc/rfc4787#section-4.3}}), but devices choose their own: an AWS NAT gateway times out a connection idle for 350 seconds and answers later packets with a reset, not a FIN ({{AWS NAT troubleshooting|https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateway-troubleshooting.html}}). Load balancers have their own idle timers. Neither end is told: the next write fails with "connection reset by peer", or, if the middlebox drops silently, hangs until a retransmission timer gives up.

  1. The pod opens a connection. The SYN leaves the pod from 10.0.1.23:41000. The NAT gateway rewrites the source to its public address and a free port, 198.51.100.7:1024, and writes the mapping into its table.
  2. The request streams; the mapping is in use. Every packet in either direction refreshes the entry. The response streams back through the same mapping, rewritten to 10.0.1.23:41000.
  3. The client returns the connection to its pool. Nothing is sent now. TCP has no idea anything is wrong: both ends still hold an ESTABLISHED socket.
  4. 300 s of silence. Default keepalive would wait 7,200 s; this socket has none. The mapping ages.
  5. 350 s idle: the gateway deletes the mapping. The NAT gateway times out the connection after 350 s of idleness. It tells neither end.
  6. The pooled connection is reused: reset. The request reaches the gateway, which has no mapping for it, and answers with a reset (AWS documents RST, not FIN). The client sees "Connection reset by peer" (ECONNRESET) and must open a new connection: a new handshake, a new TLS handshake, and a retry it hopefully knows is safe.
  7. Before. This is the shape of "works in testing, fails after lunch": only connections idle longer than a middlebox timer break, and the error blames the peer.
  1. The pod opens a connection. The gateway maps 10.0.1.23:41000 to 198.51.100.7:1024 and writes the entry.
  2. The request streams; the mapping is in use. Every packet in either direction refreshes the entry.
  3. The client returns the connection to its pool. Nothing is sent; both ends still hold an ESTABLISHED socket.
  4. Keepalive probe at 300 s idle. The socket was configured with TCP_KEEPIDLE = 300 s (below the gateway's 350 s). The kernel sends an empty probe; the server's kernel acknowledges it; the mapping is refreshed. Neither program did anything.
  5. 350 s after the request, the mapping is only 50 s old. The gateway's timer counts from the last packet, which was the probe.
  6. The pooled connection is reused: it works. The next request goes out on the same connection, through the same mapping, with no new handshake.
  7. After. Fix: keepalive (or an application ping) more often than the shortest idle timer on the path, or a pool that discards connections idle longer than it. Both are cheap; the failure they prevent shows up only in production, after quiet periods.

TCP keepalive is not a heartbeat by default. With SO_KEEPALIVE on, Linux waits 7,200 s idle, then probes 9 times 75 s apart: 7,200 + 9 × 75 = 7,875 s, 2 hours 11 minutes, before it declares a silent peer dead (TCP_KEEPALIVE_TIME (120*60*HZ), TCP_KEEPALIVE_PROBES 9, TCP_KEEPALIVE_INTVL (75*HZ) in {{tcp.h|https://github.com/torvalds/linux/blob/master/include/net/tcp.h}}). This Mac uses 7,200 s, 75 s and 8 probes (measured sysctl). Both are far longer than a 350 s NAT timeout, so set the per-socket options (TCP_KEEPIDLE, TCP_KEEPINTVL, TCP_KEEPCNT on Linux; TCP_KEEPALIVE on macOS) below the shortest idle timer on the path, as AWS's own fix says, or have the pool discard connections idle longer than that.

Keepalive cannot see a wedged peer. A process that is alive but stuck (a rank deadlocked in a collective, a server in a long garbage collection) still has a kernel that answers probes. For data you have sent, TCP_USER_TIMEOUT bounds how long it may stay unacknowledged before the connection is dropped (Linux 2.6.37 and later, {{man 7 tcp|https://man7.org/linux/man-pages/man7/tcp.7.html}}; standardised as an option in {{RFC 5482|https://www.rfc-editor.org/rfc/rfc5482}}). For everything else you need an application heartbeat and a deadline: NCCL's watchdog timeout in PyTorch, gRPC deadlines, an SSE stream's ping events.

The root's Failure lab cases "Reused keep-alive connection closed by the server" and "Read timeout: connected, then nothing" show both shapes with real client errors; the {{SSH|n:3c65c17b0d0d81f88f50e478c94ebdcd}} page (its section 9) records ServerAliveInterval detecting a dead path in seconds where TCP keepalive would take two hours.

Every connection through a NAT uses one of its source ports. An AWS NAT gateway supports up to 55,000 simultaneous connections per public IPv4 address to each unique destination (destination address, port and protocol), 5 Gbit/s scaling to 100 Gbit/s, and 1 to 10 million packets per second; beyond the connection limit its ErrorPortAllocation metric counts the connections it could not open ({{NAT gateway basics|https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateway-basics.html}}, {{CloudWatch metrics|https://docs.aws.amazon.com/vpc/latest/userguide/metrics-dimensions-nat-gateway.html}}). A fleet of dataloader workers opening fresh connections to one storage endpoint can reach it. Fixes in order: reuse connections; add addresses to the gateway; and for S3 or DynamoDB, take NAT out of the path with a gateway VPC endpoint, which has no additional charge and needs no NAT device ({{gateway endpoints|https://docs.aws.amazon.com/vpc/latest/privatelink/gateway-endpoints.html}}).

Failures only after idle periods, at a suspiciously round interval (350 s, 600 s, 3,600 s): a middlebox idle timer; compare the failure timestamps with each connection's last use. New connections failing while old ones work: a full NAT table (the gateway's port-allocation metric; on a Linux NAT, conntrack -S). ss -to (Linux) shows each socket's keepalive timer.
