The idea in one screen

Every byte you send rides in an IP packet that may be lost, and TCP turns those packets into a reliable stream by numbering bytes, waiting for acknowledgements and never having more than one window unacknowledged, so one connection moves at most one window per round trip. Almost every slow transfer, stalled token stream or hung training job traces back to that sentence, or to one of the boxes that rewrite or drop packets on the way.

Each layer adds one header and one promise; a streamed token pays 52 bytes of header for 124 of data. Fig. 1 follows one token down the server's stack, across two routers and up the client's.

  1. The server writes one token. Token 1 of the running stream is 124 bytes on the wire as a Server-Sent Event (recorded by the root page). The program hands them to its socket and is done; everything below is the kernel's.
  2. TCP adds 20 bytes, usually 32. The two ports, the byte numbers, the acknowledgement and the window (sections 2 to 7); the timestamp option makes it 32. UDP would carry only ports, length and checksum, in 8 (section 11).
  3. IP adds 20 bytes. The two addresses and the hop counter (section 1): 124 + 32 + 20 = 176 bytes on the wire, 30% of them header.
  4. Routers read only the IP header. Each hop looks up the destination address, decrements the hop counter and forwards. Nothing on the path needs the TCP header or the data; the boxes that read them anyway are the trouble of sections 9 and 12.
  5. The client's kernel unwraps it. IP hands the segment to the socket its 5-tuple names; TCP puts the bytes in order and sends an acknowledgement back; the program reads 124 bytes. Loss, windows and timers (sections 4 to 7) all live in this layer.
  6. The link only sets the size limit. To scale: a full segment of a checkpoint download is 1,448 bytes of data (one MSS) plus the same 52 bytes of headers, exactly the 1,500-byte MTU of standard Ethernet (section 10); the token's packet leaves room for 1,324 bytes more, unused.

You need nothing beyond what an engineer who has called an HTTP API knows. The overview of one LLM request through every layer is section 4 of {{Topic: protocols|n:3c65c17b0d0d81ec9355f4eecd6eed02}}; this page is the depth under it. The running example is that root's streaming request: 277 bytes up, then Server-Sent Events, one small write per token about 50 ms apart. Later sections scale it up to the transfer that hurts most in ML work, a checkpoint of hundreds of gigabytes across a long path.
