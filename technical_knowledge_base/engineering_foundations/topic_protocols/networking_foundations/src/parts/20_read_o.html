15. Debugging a connection: from symptom to mechanism

Four tools answer most questions, each at a different layer. ping asks whether a host answers and what the round trip is (ICMP echo; some networks drop it, so silence is not proof the host is down). traceroute and mtr show the path and where loss starts (TTL, section 1). ss (Linux; netstat and lsof on macOS) shows every socket's state, queue, window, RTT and retransmissions as the kernel sees them. tcpdump shows the packets themselves (needs root): SYNs resent with no answer, RSTs, window sizes, segments waiting for ACKs, for example tcpdump -ni any 'tcp port 443 and host 203.0.113.5'. Reading ss -ti. One line per connection: cubic or bbr (algorithm), wscale (send and receive window-scale shifts), rto: (current timer, ms), rtt:x/y (smoothed RTT / variance, ms), mss:, cwnd: (segments), ssthresh:, bytes_acked:, retrans: (in flight / total), pacing_rate, rcv_space: (autotuning's estimate); field list in {{man 8 ss|https://man7.org/linux/man-pages/man8/ss.8.html}}. Small cwnd with climbing retrans: loss-limited. Large cwnd and a throughput equal to window / RTT: window-limited. The macOS counterpart is netstat -s -p tcp for totals; per-connection detail needs getsockopt(TCP_CONNECTION_INFO), which this page's scripts use.

Reference: drills, interview questions, glossary

Eight predict-then-reveal drills (each from a real situation on this page)
Interview questions, with model answers (optional rehearsal)
What happens, at the transport level, when you call requests.post() to an HTTPS API for the first time?
DNS resolves the name (the {{DNS|n:3c65c17b0d0d812387d8f92b546f07af}} page). The kernel picks an ephemeral port and sends a SYN; SYN-ACK and ACK complete the handshake in one round trip, negotiating MSS, window scaling, SACK and timestamps. TLS 1.3 takes one more round trip. The request goes out in one or more segments; the response comes back under flow control (receive window) and congestion control (slow start from 10 segments). The connection is returned to the pool; if it is never reused, whoever closes first holds TIME_WAIT. Total before the first response byte: about three round trips plus server time.
Why can a single TCP connection not use a 10 Gbit/s link across an ocean, and how do you fix it?
Throughput is at most window / RTT. 10 Gbit/s × 100 ms needs 125 MB in flight; a typical autotuning ceiling of a few MB gives tens to hundreds of Mbit/s. Loss caps it further (Mathis: about 45 Mbit/s at one loss in 100,000 with 1,460-byte segments), and clouds cap single flows (5 Gbit/s on AWS outside placement groups). Fixes: raise tcp_rmem/tcp_wmem maxima to the BDP, never pin SO_RCVBUF, consider BBR for lossy paths, and above all use parallel streams (multipart upload, sharded checkpoints).
TCP versus UDP versus QUIC: when do you pick each?
TCP by default for request/response and bulk data between services: reliable, ordered, in the kernel, understood by every middlebox. UDP when late data is useless (media, games), when one packet answers one question (DNS), or as the substrate for your own transport; you must add congestion control. QUIC when you want TCP's guarantees without head-of-line blocking across streams, a combined one-round-trip handshake, and connection migration, typically HTTP/3 to clients on mobile or lossy networks; it costs more CPU and needs a TCP fallback where UDP is blocked.
A service sees thousands of sockets in TIME_WAIT and occasional "Cannot assign requested address". Explain and fix.
The client side closes connections first, so it holds TIME_WAIT for 60 s on Linux; with 28,232 ephemeral ports that allows about 470 new connections per second to one destination address and port. The client is opening a connection per request. Fix: connection pooling with keep-alive (also saves a round trip or two per request). tcp_tw_reuse=1 helps outgoing connections; tcp_tw_recycle no longer exists (removed in 4.12, broke NAT).
Small API calls work but a large upload hangs forever. What do you suspect and how do you prove it?
A path MTU black hole: a smaller-MTU link on the path drops full-size packets, and the ICMP "fragmentation needed" or "packet too big" message is filtered. Prove it with don't-fragment pings of increasing size (ping -M do -s 1472 on Linux): success below a size and silence above it, with no ICMP reply. Fix: allow those ICMP messages, clamp MSS on the tunnel, or enable tcp_mtu_probing.
Why does a streaming endpoint set TCP_NODELAY?
Nagle's algorithm holds a small write while earlier data is unacknowledged. Tokens are small writes 20 to 100 ms apart, so on a real round trip each token after the first would wait for the previous token's ACK (and possibly a 40 ms delayed ACK), turning a smooth stream into bursts. TCP_NODELAY sends each write at once.
How does QUIC survive a phone switching from Wi-Fi to mobile data when TCP does not?
TCP identifies a connection by its 5-tuple, so a new client address matches no socket and the connection is dead; the app must reconnect and redo the handshakes. QUIC identifies it by connection IDs carried in each packet; the server sees the known ID from a new address, validates the new path with PATH_CHALLENGE/PATH_RESPONSE, and continues. This page records exactly that on loopback (section 12).
A pooled HTTP connection fails with "connection reset" only when it was idle for a few minutes. Why?
A NAT gateway or load balancer between the hosts dropped the idle mapping (AWS NAT: 350 s) and answers the next packet with a reset. Neither end was told. Fix: keepalive probes (or application pings) more often than the shortest idle timer, or a pool that discards connections idle longer than it; and retry idempotent requests once on a reset of a reused connection.
Glossary (every term, with its section)
ACK
acknowledgement: "I have every byte up to n" (section 4)
BDP
bandwidth-delay product, link rate × RTT: the bytes that must be in flight to fill a path (section 5)
BBR
congestion control that models bottleneck bandwidth and minimum RTT instead of reacting to loss (section 6)
CIDR, prefix
10.0.0.0/16: all addresses sharing the first 16 bits (section 1)
Congestion window (cwnd)
the sender's estimate of what the network can carry; grows on ACKs, shrinks on loss (section 6)
Connection ID
QUIC's name for a connection, independent of addresses (section 12)
CUBIC
the default congestion control in Linux, Windows and Apple stacks (RFC 9438)
Delayed ACK
a receiver waiting briefly before acknowledging, up to 40 to 200 ms on Linux (section 7)
Ephemeral port
the temporary port the client's kernel picks for its end (section 2)
FIN, RST
orderly close of one direction; abrupt "this connection does not exist" (section 3)
Head-of-line blocking
bytes that arrived waiting behind a missing earlier byte (section 4)
ICMP
IP's control messages: errors such as "time exceeded" and "packet too big", and ping (sections 1, 10)
MSS
maximum segment size: the largest TCP payload per segment, announced in the SYN (section 10)
MTU
maximum transmission unit: the largest IP packet a link carries (section 10)
Nagle's algorithm
holding small writes while data is unacknowledged; off with TCP_NODELAY (section 7)
NAT
network address translation: rewriting private addresses and ports to a public one, with a table of mappings (section 9)
Packet, segment, datagram
an IP unit; a TCP unit inside it; a UDP unit inside it
PMTUD
path MTU discovery, by ICMP "too big" messages or by probing (section 10)
RDMA, RoCEv2, InfiniBand, EFA
direct memory access over the network, and the fabrics that carry it (section 14)
Receive window
free space in the receiver's buffer, advertised in every ACK (section 5)
RTO
retransmission timeout: how long the sender waits before resending (section 4)
RTT
round-trip time: a packet there and the answer back
SACK
selective acknowledgement: which later blocks have arrived (section 4)
Slow start
doubling the congestion window every round trip from 10 segments (section 6)
Socket
the kernel's handle for one end of a conversation (section 2)
SYN
the first segment of a TCP connection, carrying the initial sequence number and options (section 3)
TIME_WAIT
the closed-first side remembering a connection for 2 MSL (60 s on Linux) (section 3)
TTL, hop limit
a per-packet counter each router decrements; at zero the packet is dropped (section 1)
Window scaling
the SYN option that multiplies the 16-bit window field, up to 1 GiB (section 5)
5-tuple
protocol, source address and port, destination address and port: a connection's name (section 2)
