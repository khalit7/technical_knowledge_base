7. Small writes: Nagle, delayed ACKs and streamed tokens

Nagle's algorithm ({{RFC 896|https://www.rfc-editor.org/rfc/rfc896}}, January 1984; {{RFC 9293 s3.7.4|https://www.rfc-editor.org/rfc/rfc9293#section-3.7.4}}) was the fix for terminals sending one 41-byte packet per keystroke (40 bytes of headers, 1 of data): while any sent data is unacknowledged, hold new small writes and send them together when the ACK arrives or a full segment accumulates. On the other side, a receiver may wait before acknowledging, hoping to piggyback the ACK on a reply: a delayed ACK, under 0.5 s, with an ACK for at least every second full-sized segment ({{RFC 1122 s4.2.3.2|https://www.rfc-editor.org/rfc/rfc1122#section-4.2.3.2}}). Linux delays between 40 ms and 200 ms (TCP_DELACK_MIN (HZ/25), TCP_DELACK_MAX (HZ/5) in {{tcp.h|https://github.com/torvalds/linux/blob/master/include/net/tcp.h}}).

Together they stall. A client writes a request in two pieces (headers, then body): the first goes out; Nagle holds the second until the first is acknowledged; the server, holding half a request, has nothing to reply with, so its delayed ACK waits 40 ms or more. Every request pays it. A token stream is bitten the same way: token 2 is written while token 1 is unacknowledged, so Nagle holds it until token 1's ACK returns a full round trip later. On a 100 ms path, tokens that left the model 50 ms apart arrive in clumps, one clump per round trip.

See it in the timeline of section 4
Set Scenario to Clean and Small writes to "Nagle on" at 100 ms: tokens leave in pairs, one pair per round trip. Then set the round trip to 10 ms: Nagle barely matters, which is why it hides on fast networks and in tests.

The fix is one socket option. TCP_NODELAY turns Nagle off so every write goes out at once. Latency-sensitive stacks set it by default: gRPC's C core calls grpc_set_socket_low_latency(fd, 1) on its client and server sockets ({{tcp_client_posix.cc|https://github.com/grpc/grpc/blob/master/src/core/lib/iomgr/tcp_client_posix.cc}}), and Go's TCP connections start with no delay ({{SetNoDelay: "The default is true"|https://pkg.go.dev/net#TCPConn.SetNoDelay}}). TCP_CORK (Linux) is the deliberate opposite: assemble a response from several writes and release it as full segments.

Measured: the asyncio server side was left with Nagle on

Python's asyncio sets TCP_NODELAY on every TCP transport, but only when the socket reports its protocol as TCP (sock.proto == IPPROTO_TCP in asyncio/base_events.py, read in the 3.13.5 source). On this Mac a socket returned by accept() reports protocol 0, so the server side of an asyncio connection kept Nagle on while the client side had it off. Whether your server framework sets the option is worth one getsockopt call. The root's Failure lab could not reproduce the stall on this Mac's loopback (case "Nagle plus delayed ACK (not reproduced on macOS loopback)"): there the ACK returns in microseconds, so nothing waits. The stall needs a real round trip.

How it shows up (commands)

Latency per request of almost exactly 40 ms (or 200 ms) more than the work takes, independent of payload size; streamed tokens arriving in bursts rather than evenly. Check getsockopt(IPPROTO_TCP, TCP_NODELAY) on both ends, or a packet capture (tcpdump, needs root) showing small segments waiting for ACKs. Fix: set TCP_NODELAY on both ends, and write each logical message in one call.
