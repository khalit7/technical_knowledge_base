3. A connection's life, and why round trips are the unit of latency

Opening: the three-way handshake. TCP numbers every byte. Each side picks a random initial sequence number (random so an attacker off the path cannot guess it and inject data, {{RFC 9293 s3.4.1|https://www.rfc-editor.org/rfc/rfc9293#section-3.4.1}}): the client sends SYN ("my bytes start at x"), the server SYN-ACK ("mine start at y; I expect x+1"), the client ACK, with data allowed on that third segment. So a new connection costs exactly one round trip before the request leaves. measured: connect() to Cloudflare's speed-test host took 14.1 to 19.4 ms over twelve connections, against a ping round trip of 14.0 to 18.4 ms to Cloudflare's resolver: one round trip, as predicted.

Closing, and the states in between

Each direction closes separately: the side that has finished sending sends FIN, the other acknowledges, and a half-close is allowed (send the whole request, shut the sending side, keep reading). RST (reset) is the abrupt alternative, "this connection does not exist for me": a kernel sends it for a segment that matches no socket (a refused connection, a NAT that forgot the mapping), and an application forces one by closing with unread data.

Two of these states cause most production tickets; ss -tan (Linux) or netstat -an -p tcp (macOS) prints their names. CLOSE_WAIT piling up means your program received the peer's FIN but never called close() (a leak in your code, not the network); TIME_WAIT piling up means you open and close connections faster than you should. Fig. 2 walks the running request through both kernels:

  1. Before anything. The server has called socket(), bind() and listen(): its kernel now answers SYNs on port 443. The client has no socket yet.
  2. connect(): SYN. The client kernel picks an ephemeral port and a random initial sequence number x, and offers its options (MSS, window scale, SACK, timestamps). They can only be agreed now.
  3. SYN-ACK. The server picks its own sequence number y, acknowledges x+1 and answers with its options. The half-open connection waits in the SYN queue.
  4. ACK, and the request rides along. One round trip after connect() started, both ends are ESTABLISHED and the 277-byte request is on its way. The connection moves to the accept queue until the server calls accept() (section 8). Over HTTPS, the TLS handshake comes first.
  5. The response streams. A 244-byte head, then one small write per token, each segment acknowledged. Sections 4 to 7 are everything that can go wrong here.
  6. Server closes first. The running request asked for Connection: close, so after the last event the server calls close(): its kernel sends FIN, "no more data from me", and enters FIN_WAIT_1.
  7. The client acknowledges; its program has not closed yet. The client kernel acknowledges and the socket enters CLOSE_WAIT: the peer is done, and it is now up to the client program to call close(). A socket stuck here forever is a bug in the program, not the network.
  8. The client closes. The program reads the end of the stream and closes: its FIN goes out and it waits in LAST_ACK for the final acknowledgement.
  9. The last ACK. The client is done. The server, which closed first, enters TIME_WAIT: it keeps the 5-tuple reserved for 2 MSL so a delayed old segment cannot leak into a new connection, and it can resend this ACK if it is lost.
  10. TIME_WAIT expires. After 60 s on Linux (30 s on this Mac) the entry is gone. The eleventh state, CLOSING, happens only when both sides send FIN at the same moment.

The round-trip budget of one request

Light in fibre covers about 200,000 km per second (refractive index about 1.5), so New York to London, 5,585 km, can never take less than a 56 ms round trip ({{High Performance Browser Networking, chapter 1|https://hpbn.co/primer-on-latency-and-bandwidth/}}, table 1-1). Every protocol step that waits for an answer costs one of those.

That is why connection reuse matters more the farther away the API is, and why the root's {{On the wire|n:3c65c17b0d0d81ec9355f4eecd6eed02}} tab measures cold, resumed and reused connections.

A fresh HTTPS connection pays three round trips before the first response byte; a pooled one pays one. Predict how much a connection pool saves on a 160 ms path, then move the round trip. derived: TCP 1 RTT, TLS 1.3 1 RTT ({{TLS|n:3c65c17b0d0d8105a37ff2d2f602a421}}), request and first byte 1 RTT; QUIC combines transport and TLS in one (section 12). Server time and DNS are left out.

TIME_WAIT, and why closing fast runs out of ports

The side that closes first holds the connection in TIME_WAIT for twice the maximum segment lifetime (2 MSL), so a delayed duplicate of an old segment cannot be mistaken for data in a new connection on the same 5-tuple, and so it can resend a lost final ACK ({{RFC 9293 s3.6|https://www.rfc-editor.org/rfc/rfc9293#section-3.6}}). Linux fixes it at 60 seconds (TCP_TIMEWAIT_LEN (60*HZ) in {{include/net/tcp.h|https://github.com/torvalds/linux/blob/master/include/net/tcp.h}}; not a sysctl).

A client that opens a fresh connection per request (no connection pool, an embedding API called in a tight loop, a health checker) hits that wall with EADDRNOTAVAIL ("Cannot assign requested address"). The fix is reuse: a pool with keep-alive, which also saves the round trips above. Whoever closes first holds TIME_WAIT, so a server that closes idle client connections collects them too.

When the SYN gets no answer (a firewall, a security group, a host that is down) the client retries with exponential backoff; Linux's default of 6 retries gives up after about 131 seconds ({{tcp_syn_retries|https://docs.kernel.org/networking/ip-sysctl.html}}). A connect with no timeout of its own can hang for two minutes, so every client needs an explicit connect timeout, much shorter than its read timeout. The root's Failure lab records five clients' errors for "Connect timeout" against an address that never answers, and for "Connection refused" the contrast: an RST back in under a millisecond.

Options agreed in the SYN, TIME_WAIT on macOS, the reuse knobs (depth)

The SYN negotiates options that can never be added later ({{RFC 9293 s3.2|https://www.rfc-editor.org/rfc/rfc9293#section-3.2}}, {{RFC 7323|https://www.rfc-editor.org/rfc/rfc7323}}, {{RFC 2018|https://www.rfc-editor.org/rfc/rfc2018}}): the MSS, window scaling (section 5), SACK permitted (section 4) and timestamps. On every one of this page's connections to Cloudflare the kernel reported all four plus ECN (section 6) as agreed (TCP_CONNECTION_INFO options = 15). A middlebox that strips an option from the SYN removes that feature for the life of the connection, silently.

macOS. This Mac uses an MSL of 15 s, so TIME_WAIT is 30 s (measured net.inet.tcp.msl: 15000); its netstat listed no TIME_WAIT entry after twenty closed loopback connections, so the state could not be seen here and the numbers above are Linux's.

Kernel knobs, a last resort. tcp_tw_reuse lets outgoing connections reuse a TIME_WAIT port when timestamps prove it safe (default 2, loopback only, {{ip-sysctl|https://docs.kernel.org/networking/ip-sysctl.html}}); tcp_tw_recycle, still recommended by old blog posts, was removed in Linux 4.12 because it broke clients behind NAT ({{commit 4396e46187ca|https://github.com/torvalds/linux/commit/4396e46187ca5070219b81773c4e65088dac50cc}}).
