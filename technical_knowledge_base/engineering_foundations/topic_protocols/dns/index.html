The idea in one screen

DNS turns a name into records (mostly addresses) through a chain of caches in front of a tree of servers: your C library asks one recursive resolver, the resolver walks from the root down to the zone's own servers only for what it has not cached, and every answer, "no such name" included, is kept for a number of seconds the owner chose. Nearly every DNS problem you will debug is one of four things: the answer is cached somewhere you did not expect, one name was turned into many queries, one lost packet cost a fixed timeout, or the wrong server was asked.

Fig. 1 · One recursive question, a walk down the tree on a cache miss, and a cache at every hop

  1. One recursive question. Your process calls getaddrinfo(); the stub inside it (glibc or musl, which keep no cache) sends one question, A? api.llm.test with RD (recursion desired) set, to the resolver named in /etc/resolv.conf, and waits.
  2. A cache miss walks the tree. The resolver's cache is empty, so it asks the root, then the test. servers, then llm.test.'s own server: two referrals and one answer with the AA (authoritative) flag, 4 upstream queries counting priming (section 2).
  3. Every answer is cached with its TTL. The address goes into the cache for 60 seconds and the two referrals for 172,800 (the lab's zone files); the reply reaches your process 5 ms after the question (dig, cold).
  4. The second lookup never leaves the resolver. Asked again, the resolver answers from its cache: 0 queries reach any authoritative server, the record comes back with 56 of its 60 seconds left, 2 ms.
  5. Where it goes wrong. The four causes, where they happen: an answer cached longer than you expected (section 5); one name turned into many queries, ndots:5 made api.llm.test 8 (section 7); one lost packet costing the stub's whole timer, 5,037 ms on glibc (section 6); the wrong resolver asked, which answers differently (split horizon, section 8).

1. Names, zones and delegation

The problem. Packets go to addresses, but configuration uses names, and the machines behind a name change all the time. One central table of every name could never keep up (until the 1980s every host downloaded one file, HOSTS.TXT; RFC 1034 s2.1). DNS splits the job by ownership: whoever owns a name runs, or rents, the servers that answer for it, and everyone else finds those servers by asking down a tree (RFC 1034 and RFC 1035, November 1987, still the core of the protocol).

Names are read right to left. api.anthropic.com. is three labels under the root, the empty label written as the final dot; a label is at most 63 bytes and a name at most 255 (RFC 1035 s2.3.4). A name ending in a dot is a fully qualified domain name (FQDN): absolute, never extended. Without the dot, your resolver library may first try to complete it with local suffixes, which is the whole story of section 7.

The servers that hold a zone's records are its authoritative servers. At the top are 13 root server identities, a to m.root-servers.net, run by 12 organisations; on 5 October 2026 they were served by 2,045 machines, each identity answering from many places on one address through anycast (one IP address announced from many sites; routing delivers to the nearest) (root-servers.org).

What delegation costs. A delegation is cached for as long as the parent says: 172,800 seconds (48 hours) for com. in the root zone file, and the same for the delegations inside .com, so moving a domain to new name servers can take two days to reach every cache. And every name under a zone depends on that zone's servers and the chain above them: when one record or one signature high up breaks, everything below it breaks at once (section 11).

2. Resolution, step by step

Two kinds of question. Your program asks its resolver a recursive question: "give me the final answer, do whatever it takes" (the RD, recursion desired, flag is set). The resolver then asks iterative questions down the tree: each authoritative server answers with the record or a referral ("I do not have that; these servers do"), and never asks anyone on your behalf (RFC 1034 s4.3.1 and s5.3.3). A resolver starts with nothing but the root servers' addresses (the root hints); its first act is to ask a root server for the current list (priming, the NS . query below).

The recording. A fresh Unbound with an empty cache was asked for api.llm.test once, then again; each authoritative server's own query log shows exactly what it was asked.   4. So does test. Asked the full name too, it refers to ns1.llm.test (92 bytes).

Every message is from the servers' own logs (measured, CoreDNS log plugin and dig, 5 October 2026); each lab hop takes about a millisecond. On the internet the same walk costs real round trips: the root page measured 212 to 451 ms for an uncached public name and 2.4 ms once cached on the laptop.

What a cold lookup costs. One round trip from your process to the resolver, plus, on a cache miss, one round trip from the resolver to each level it does not already know. The root and top-level domains are almost always cached (their records live for days), so a cold lookup on the internet usually costs the round trip to the domain's own servers, often tens to hundreds of milliseconds. That is why the second lookup is cheap, and why a resolver that is restarted or flushed causes a burst of slow lookups and a burst of load on the authoritative servers.

QNAME minimisation: tell each server only what it needs. Classic resolvers sent the full name to every server, so the root learned every name anyone looked up. With QNAME minimisation (RFC 9156) the root is asked only about test., the test. servers only about llm.test.; in the recording the root's log holds A test. with it on and A api.llm.test. with it off. Unbound has done this by default since 1.7.2 (June 2018; Unbound manual); BIND does a "relaxed" version by default that falls back to the full name when a server answers oddly (BIND 9.20 reference). It costs nothing in the common case and can cost extra queries for names many labels deep. Unbound also sets the CD (checking disabled) flag on its upstream questions: it validates signatures itself (section 9) and wants the raw data.

Why dig +trace cannot show this walk on every network

dig +trace name normally does the walk itself, from the root down, and is the best way to separate "the zone is broken" from "my resolver cached something wrong". It only works if your packets reach the root servers. On the laptop this page was recorded on, a filter answers every plain DNS packet itself, even one addressed to a root server and even from inside a container: asked example.com without recursion, a.root-servers.net's address replied with a final answer and the RA flag set, which a real root server never does (it would refer you to the .com servers). Corporate device management, VPNs and security software often do this. That is why the walk on this page is recorded on a private tree, and why the public lookups were sent over DNS over TLS (section 10).

3. The message on the wire

One format for everything. A question and its answer use the same layout (RFC 1035 s4.1): a 12-byte header, then four sections. The question holds the name, the record type and the class (always IN, Internet); the answer the records asked for; the authority section NS records for a referral, or the zone's SOA record with a "no"; the additional section glue addresses and the EDNS pseudo-record. Each record carries its owner name, type, class, a 32-bit TTL in seconds, and its data.

The header. A 16-bit ID the answer must echo (with the source port, all that ties an answer to its question over UDP: section 10), seven flags (QR response, AA authoritative, TC truncated, RD and RA recursion desired and available, AD validated by DNSSEC, CD checking disabled), four counts, and the 4-bit response code you will debug by: NOERROR; NXDOMAIN (the name does not exist at all); SERVFAIL (the resolver tried and failed, which says nothing about whether the name exists); REFUSED (this server will not answer you). NODATA has no code of its own: NOERROR with an empty answer, the name exists without that type (asking api.llm.test for TXT in the lab returns exactly that, with the SOA in the authority section).

Size: 512 bytes, EDNS, and falling back to TCP

DNS runs on UDP port 53 because one question and one answer usually fit in a datagram each, with no connection to set up. The original limit is 512 bytes per UDP message (RFC 1035 s2.3.4). EDNS(0) (RFC 6891) lets a client add an OPT pseudo-record that says how large an answer it can take, plus a DNSSEC OK bit and options (cookies, client subnet, padding). The operators' Flag Day 2020 settled the default advertised size at 1,232 bytes, small enough that an answer never needs IP fragmentation on a normal path (dnsflagday.net/2020); fragments are lost more often and can be forged more easily (section 10), so bigger is not better. When an answer does not fit, the server sends what fits with TC set and the client must ask again over TCP, which every implementation, stubs included, must support (RFC 7766 s5). How names are compressed
A name is written as length-prefixed labels (03 api 03 llm 04 test 00), and any later occurrence can be replaced by a two-byte pointer: two high bits set, then a 14-bit offset back into the message, which is why a pointer can only reach the first 16,383 bytes (RFC 1035 s4.1.4).

The apex problem: why you cannot CNAME example.com


A CNAME says "this name is an alias; ask about that other name instead", and a name with a CNAME may have no other data (RFC 1034 s3.6.2, RFC 2181 s10.1). The zone apex (the bare domain, llm.test. itself) must hold SOA and NS records, so it can never be a CNAME. 5. Caching: TTLs, negative answers and stale answers




The rule. Every record carries a TTL (time to live), chosen by the zone owner: the number of seconds a cache may keep it. A resolver that fetches a record with TTL 300 serves it for up to 300 seconds, counting down, then asks again. Nothing can push a change into caches or invalidate them from outside. So "DNS propagation" is a myth: the authoritative server has the new data the moment you save it, and you are waiting for every cache that holds the old answer to expire.

Planning a change


Lower the TTL (to 60 to 300 s) at least one old TTL before the change, because caches that fetched just before you lowered it keep the old TTL. Make the change. Keep the old address serving until the old TTL has passed since the change, then raise the TTL again. Clients add their own layer: a JVM caches for 30 s by default, and a long-lived connection never re-resolves at all (section 6). Predict: with a one-hour TTL lowered to 60 s only 30 minutes ahead, how long until every cache has the new address? Then set the lead slider to 30 min.

Negative caching: "no" is cached too


A resolver also caches NXDOMAIN and NODATA, so that a typo hammered in a loop does not reach the authoritative servers every time. For how long is set by the zone's SOA record, which the "no" carries in its authority section: the minimum of the SOA record's own TTL and its last field, MINIMUM (RFC 2308 s5; MINIMUM once meant something else and was repurposed for this). In the lab, llm.test's SOA has TTL 300 and MINIMUM 30, so a "no" lives min(300, 30) = 30 seconds:


For anthropic.com both numbers are 1,800 (SOA ... 604800 1800, measured), so a name looked up a moment before it is created stays missing for up to half an hour for everyone behind that cache; a zone with MINIMUM 86400 would make it a day. Keep MINIMUM between about 300 and 900 seconds on zones that change, and do not let deploy scripts or health checks look up names before they exist (the root's Failure lab "NXDOMAIN" case shows what each client library prints). Failures are cached as well: a resolver that gets no usable answer must remember that for at least 1 second and at most 5 minutes, and back off rather than retry hard (RFC 9520 s3, December 2023), which is why a broken zone can stay broken for a few minutes after it is fixed.

Serving stale answers when the source is down


When an authoritative server is unreachable and a cached record has expired, a resolver normally has nothing to give: SERVFAIL, or, as recorded below, no answer at all before the client gives up. Serve-stale (RFC 8767) lets it return the expired record instead, marked with a short TTL (30 s recommended), after trying the servers for a moment (1.8 s recommended). 6. The resolver inside your process: glibc and musl


Who actually asks. When Python's requests or httpx, curl, Node's default dns.lookup or a gRPC channel opens a connection to a name, it calls getaddrinfo(), and the C library's stub resolver does the DNS work: it reads /etc/resolv.conf, sends the questions, waits, retries, and returns addresses or an error. On Debian, Ubuntu and the CUDA images that is glibc; on Alpine it is musl, and they behave differently in ways that matter, which is why a glibc-based image is the safer default for ML containers.


The knobs live in /etc/resolv.conf: nameserver (up to three), search, and options ndots:n (default 1), timeout:n (default 5 s) and attempts:n (default 2) (resolv.conf(5)).

The 5-second stall: conntrack races


Pods reach the CoreDNS service address through kube-proxy's iptables rules, which rewrite the destination (DNAT) and record each flow in the kernel's connection tracking table (conntrack). glibc and musl send A and AAAA together from one socket, and UDP has no handshake, so the two packets can race through conntrack on different CPUs; Martynas Pumputis found three such races in 2018, in each of which one packet is dropped and the pod waits out its 5-second timeout (Weave blog, archived). The last fix landed in Linux 5.6, so on older nodes it still bites. The symptom is the fingerprint: lookups that take 5.0x seconds (or 2.5 on Alpine), the stub's timeout, never "slow" in general, exactly the number of the lost-packet runs in section 6. Workarounds on old kernels: options single-request-reopen (glibc only), timeout:1, or NodeLocal DNSCache.

The VPC resolver. 9. DNSSEC: what a signed answer proves




The problem. Classic DNS has no authentication: a resolver accepts the first answer that matches its question's ID and port, so anyone who can answer first, or who controls a hop, can send you to the wrong address (section 10). DNSSEC (RFC 4033 to 4035) lets a resolver prove that an answer is exactly what the zone's owner published, and that a "no such name" is genuine.


How it works. Each zone signs every RRset; the signature is an RRSIG record with an inception and an expiry date. The zone publishes its public keys as DNSKEY records, usually in two roles: a key-signing key (KSK) that signs only the key set, and a zone-signing key (ZSK) that signs everything else. The parent vouches for the child's KSK by publishing a hash of it, a DS record, which the parent signs in turn. Following DS to DNSKEY to DS up the tree ends at the root's KSK, which the resolver must already trust: that copy is the trust anchor. A name that does not exist is proven by an NSEC (or hashed NSEC3) record, a signed statement "nothing exists between these two names". Each key is named by a 16-bit key tag, a checksum of the key.

What it does not do. DNSSEC proves origin and integrity, not secrecy: the question and answer still cross the network in the clear. 10. Privacy and attacks


Encrypted DNS: DoT, DoH, DoQ


Plain DNS is readable and rewritable by every network it crosses: your Wi-Fi, your ISP, a filter on your laptop. Three standards encrypt the hop from your machine to the resolver: DNS over TLS (DoT), TCP port 853 (RFC 7858, 2016); DNS over HTTPS (DoH), ordinary HTTPS requests on port 443 (RFC 8484, 2018); and DNS over QUIC (DoQ), UDP port 853 (RFC 9250, 2022). DoT is easy for a network to recognise and block by port, which enterprises like and censors exploit; DoH looks like any other web traffic, which is why enterprises dislike it; DoQ avoids TCP's head-of-line blocking and sets up faster. In one academic measurement DoQ loaded simple pages up to 10% faster than DoH and was only about 2% slower than plain DNS on complex pages (Kosek et al., IMC 2022). corrected The old page's "88 ms against 883 ms, 2026 measurements" could not be found in any source and is not repeated. Encryption protects only that one hop: the resolver still sees every name, and its own upstream queries are plain unless the zone is signed (section 9).


Seen from this laptop: encrypted DNS made the interception visible
Every public lookup on this page went over DoT to 1.1.1.1 with the certificate checked against one.one.one.one, and a test query for the resolver's identity returned a Cloudflare data-centre code, so the answers really came from the public resolver. The same identity query over plain UDP was answered by the laptop's filter instead. Each encrypted answer arrived padded to 468 bytes: the resolver pads responses to a multiple of 468 so the size does not reveal the name (RFC 8467; measured: all ten replies whose size was recorded were exactly 468 bytes, whatever the name). Encryption made the interception visible rather than silent, which is also how the root's Failure lab caught it.


Cache poisoning: forging an answer


Over UDP a resolver accepts the first reply whose 16-bit ID and port match its question. In 2008 Dan Kaminsky showed that an attacker who triggers many lookups of random names in one zone can race the real server with forged replies carrying a forged delegation, and with a fixed source port only the ID (on average 32,768 guesses) stood in the way (CERT VU#800113). The fix was source-port randomisation, adding up to another 16 bits (RFC 5452). DNSSEC is the only complete fix.


Later defences and attacks: cookies, 0x20, SAD DNS, fragments
Later layers are DNS cookies (RFC 7873) and randomising the letter case of the question ("0x20", an expired draft). In 2020 SAD DNS recovered the random port through a side channel in the kernel's global ICMP rate limit, fixed in Linux by randomising that limit (saddns.net, CVE-2020-25705 fix). Fragmented answers are another way around the port check, one more reason for the 1,232-byte limit.

The fix
Resolve once, validate the address (not the name), connect to that literal address and send the name in the Host header (and as TLS SNI); refuse redirects or re-validate them the same way. On AWS, require IMDSv2, whose session token must be fetched with a PUT, so a plain GET from a rebinding page or a naive proxy fails; a response hop limit of 1 also keeps the token from reaching containers behind a bridge (AWS notes that containers then need a limit of 2 if they genuinely need the service; AWS IMDS docs). The MCP specification lists this among the checks a client must make before fetching a URL a server gave it (MCP security best practices).


Exfiltration: data out through your own resolver


Any machine that can resolve names can send data out: encode it in the labels of a name under a domain the attacker controls (c2VjcmV0.x.attacker.example), and your own resolver carries it to the attacker's authoritative server, past egress firewalls that only watch HTTP. It is slow but enough for keys; the SolarWinds SUNBURST backdoor used it for its first stage. Detection watches, per parent domain, the number of unique subdomains, the randomness of labels and the share of NXDOMAIN answers; on AWS that needs Resolver query logging, which is off until you configure it (section 8).


SUNBURST's DNS stage
Disclosed December 2020, it encoded the victim's domain name into subdomains of avsvmcloud[.]com and read its instructions from the answers, then moved to HTTPS for the rest (Mandiant).

12. Debugging DNS: commands and a symptom table


Rule one: ask the way your program asks. dig talks DNS directly to one server and ignores the search list, /etc/hosts and every cache in your C library; your program goes through getaddrinfo. When they disagree, both are telling the truth. Use getent ahosts name on Linux (the same path as your program) and dscacheutil -q host -a name name or scutil --dns on macOS, where apps and dig can use different resolvers.

Interview questions, with model answers


What happens, step by step, when your service calls an API by name for the first time?
getaddrinfo reads /etc/hosts and /etc/resolv.conf, expands the name with the search list if it has fewer than ndots dots, and sends A and AAAA questions over UDP to the configured resolver. On a cache miss the resolver asks a root server (usually cached), the TLD's servers (usually cached) and the zone's servers, following referrals, validating DNSSEC if configured, caching every answer for its TTL. The stub returns the addresses; the client then opens TCP or QUIC to one of them and starts TLS with the name as SNI. Costs: one round trip to the resolver plus up to one per uncached level; failure modes: timeouts, NXDOMAIN, SERVFAIL, stale caches.


You changed a record ten minutes ago; half your users still reach the old server. Why, and what would you have done differently?
Resolvers cached the old answer for its TTL, which was probably long, and some clients cache beyond the TTL (JVM settings, long-lived connections). Nothing propagates; caches expire. Plan: lower the TTL to about 60 s at least one old TTL before the change, make the change, keep the old server running until the old TTL has passed, then raise the TTL. For name-server changes allow 48 hours, the TLD's delegation TTL.


Pods see occasional 5-second delays on outbound calls. How do you diagnose it?
Exactly 5 s (2.5 s on musl) is the stub's retry timeout, so a DNS packet was lost. Measure lookup time separately (curl -w %{time_namelookup}), check the kernel version for the conntrack races (fixed by 5.6), the CoreDNS and node drop counters, the VPC resolver's packet limit, and the query volume from ndots:5. Fixes: NodeLocal DNSCache, trailing dots or lower ndots, single-request-reopen on old kernels, connection reuse to cut lookups.


What does DNSSEC protect against, and what does it not?
It proves an RRset (or a non-existence) is what the zone owner signed, defeating cache poisoning and on-path forgery between resolver and authoritative servers. It does not encrypt, does not protect the stub-to-resolver hop unless the stub validates, does not authenticate the server you connect to, and adds a failure mode: a signing error makes validating resolvers return SERVFAIL (.de, May 2026). Privacy comes from DoT, DoH or DoQ; server identity from TLS.


An agent tool fetches URLs a model chooses. How can DNS be used to make it read cloud credentials, and how do you stop it?
DNS rebinding: the tool checks the URL's host resolves to a public address, then its HTTP library resolves again and gets 169.254.169.254 (TTL 0 defeats caches). Fix: resolve once, validate the IP against a denylist of private, loopback and link-local ranges, connect to that IP with the Host header and SNI set, re-validate on redirects, and require IMDSv2 so a plain GET to the metadata service fails. The lab reproduction on this page shows both versions.


Why is DNS mostly UDP, and when does it use TCP?
A question and an answer usually fit in one datagram, so UDP avoids a handshake. Answers larger than the client's advertised size (512 bytes without EDNS, typically 1,232 with it) come back truncated with TC set and the client retries over TCP; zone transfers use TCP; DoT uses TLS over TCP. TCP support is mandatory (RFC 7766), and blocking TCP 53 breaks large answers.





Glossary (every term, linked to where it is defined)




Trust anchor: the public key (or its DS hash) a validating resolver trusts without proof; for the real DNS, the root KSK.


Anycast: one IP address announced from many sites; routing delivers to the nearest.


Apex: the top name of a zone (example.com.), which must hold SOA and NS and so cannot be a CNAME.


Authoritative server: a server that holds a zone's records and answers from them, never asking others.


conntrack: the Linux kernel's table of tracked flows, used for NAT; the source of the 5-second DNS races.


Delegation: NS records in a parent zone handing a child zone to other servers.


DNSSEC: signatures on DNS data (RRSIG, DNSKEY, DS, NSEC) so a resolver can verify it.


EDNS(0): an OPT pseudo-record that advertises a larger UDP size and carries flags and options.


FQDN: a fully qualified name, ending in a dot; never extended with a search list.


Glue: addresses of a child's name servers kept in the parent when those servers live inside the child.


Header: the 12 bytes at the start of every message: ID, flags, response code, four counts.


Headless service: a Kubernetes Service with clusterIP: None whose name returns every ready pod's address.


Root hints: the built-in list of root server addresses a resolver starts from.


Iterative query: a question a resolver asks an authoritative server, which answers or refers.


Key tag: a 16-bit checksum that names a DNSSEC key (38696 is KSK-2024).


KSK and ZSK: key-signing key (signs the key set; hashed into the parent's DS) and zone-signing key (signs the rest).


Label: one dot-separated part of a name, at most 63 bytes.


NODATA: NOERROR with no answer: the name exists without that type.


Negative trust anchor: an operator's temporary instruction to treat a zone as unsigned.


Priming: a resolver's first question, the current list of root servers.


Compression pointer: two bytes (c0 0c) standing for a name already written earlier in the message.


QNAME minimisation: sending each server only the labels it needs (RFC 9156).


Response code: NOERROR, NXDOMAIN, SERVFAIL, REFUSED and others, in the header.


Recursive query: a question asking the resolver for the final answer (RD flag set).


Referral: an answer naming the servers one level down instead of the record.


Resource record: one name, TTL, class, type and data.


RRset: all records of one name and type, cached and signed as one.


Serve-stale: answering from an expired cache entry when the source is unreachable (RFC 8767).


TTL: seconds a cache may keep a record; for a "no", min(SOA TTL, SOA MINIMUM).


Zone: the part of the name tree one set of authoritative servers answers for.
