7. Kubernetes: search lists, ndots and the cluster DNS

What a pod gets. With the default dnsPolicy: ClusterFirst, kubelet writes every pod a resolv.conf that points at the cluster DNS service (CoreDNS) and adds a search list and ndots:5 ({{Kubernetes docs|https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/#pod-s-dns-policy}}):

search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5

This is what lets code in namespace default say http://llm-proxy and reach llm-proxy.default.svc.cluster.local. CoreDNS answers cluster.local names from the Kubernetes API and forwards everything else upstream. The policy named Default is not the default: it copies the node's resolver settings instead.

The rule that costs. A name with fewer dots than ndots is tried with every search suffix before it is tried as written. api.llm.test has two dots, fewer than five, so the stub first asks for api.llm.test.default.svc.cluster.local, then api.llm.test.svc.cluster.local, then api.llm.test.cluster.local, each for A and AAAA, and only then for api.llm.test. External API names (api.anthropic.com, s3.us-east-1.amazonaws.com: two and three dots) all pay this. Predict how many queries one lookup sends, then step through the recording:

The fixes, in order of preference.

  1. Write external names with a trailing dot (api.anthropic.com.): absolute, one A and one AAAA, nothing else. Most HTTP clients accept it; a few TLS stacks dislike the dot in the server name, so test it.
  2. Lower ndots for the pod with dnsConfig: {options: [{name: ndots, value: "1"}]} (or 2), so external names are tried as written first. The catch, recorded above: in-cluster names with a dot, such as kubernetes.default, are then tried as absolute names first and fail; glibc falls back to the search list, but musl does not retry a name with at least ndots dots against the search list ({{musl wiki|https://wiki.musl-libc.org/functional-differences-from-glibc.html#Name-Resolver/DNS}}), so on Alpine kubernetes.default stopped resolving at all. Use full names (llm-proxy.default.svc.cluster.local.) in configuration if you lower ndots.
  3. Cache on the node: NodeLocal DNSCache (stable since Kubernetes 1.18), a DNS cache on every node as a DaemonSet, reached on a link-local address (default 169.254.20.10) that skips the iptables DNAT and connection tracking below, and able to use TCP towards CoreDNS ({{Kubernetes docs|https://kubernetes.io/docs/tasks/administer-cluster/nodelocaldns/}}, {{add-on README|https://github.com/kubernetes/kubernetes/blob/master/cluster/addons/dns/nodelocaldns/README.md}}). It cuts the load but not the number of queries.
  4. CoreDNS autopath does the search-list walk on the server: the first query returns the final answer, one question instead of eight ({{CoreDNS autopath|https://coredns.io/plugins/autopath/}}). It needs CoreDNS to know every pod, which costs memory on big clusters.
Correction: which short names break when ndots is lowered

corrected The old page said lowering ndots breaks bare short names like myservice; recorded, a name with no dot (myjob-headless) still resolved on both libraries, because zero dots is below any ndots. The names that break are the ones with a dot, and only on musl.

The 5-second stall: conntrack races

Pods reach the CoreDNS service address through kube-proxy's iptables rules, which rewrite the destination (DNAT) and record each flow in the kernel's connection tracking table (conntrack). glibc and musl send A and AAAA together from one socket, and UDP has no handshake, so the two packets can race through conntrack on different CPUs; Martynas Pumputis found three such races in 2018, in each of which one packet is dropped and the pod waits out its 5-second timeout ({{Weave blog, archived|https://web.archive.org/web/20210127131121/https://www.weave.works/blog/racy-conntrack-and-dns-lookup-timeouts}}). The last fix landed in Linux 5.6, so on older nodes it still bites. The symptom is the fingerprint: lookups that take 5.0x seconds (or 2.5 on Alpine), the stub's timeout, never "slow" in general, exactly the number of the lost-packet runs in section 6. Workarounds on old kernels: options single-request-reopen (glibc only), timeout:1, or NodeLocal DNSCache.

The three kernel fixes (with a correction)

Clashing identical entries are resolved (Linux 4.19, {{ed07d9a|https://github.com/torvalds/linux/commit/ed07d9a021df6da53456663a76999189badc432a}}), same-origin NAT clashes skipped (5.0, {{4e35c1c|https://github.com/torvalds/linux/commit/4e35c1cb9460240e983a01745b5f29fe3a4d8e39}}), and clashing UDP entries allowed to coexist briefly, which covers the third race where the two packets were sent to different CoreDNS pods (5.6, {{6a757c0|https://github.com/torvalds/linux/commit/6a757c07e51f80ac34325fcd558490d2d1439e1b}}). corrected The old page said the first two were fixed in 4.17 and the third "never".

CoreDNS in production

  • Forwarding loops crash it on purpose. If CoreDNS forwards to the node's /etc/resolv.conf and that points at a local stub such as systemd-resolved's 127.0.0.53, queries go round in a loop; the loop plugin detects its own probe coming back and stops the process, which shows as CoreDNS pods in CrashLoopBackOff ({{CoreDNS loop|https://coredns.io/plugins/loop/}}). The fix is to point kubelet at the real upstream file (--resolv-conf=/run/systemd/resolve/resolv.conf; kubeadm does it) ({{Kubernetes DNS debugging|https://kubernetes.io/docs/tasks/administer-cluster/dns-debugging-resolution/#known-issues}}).
  • Scale it and watch it. CoreDNS is CPU-bound and its replica count does not follow cluster size unless you add an autoscaler. The rate of coredns_dns_responses_total{rcode="NXDOMAIN"} against the total is the signature of search-list amplification: in the recordings above, three out of four answers to external lookups are NXDOMAIN.

Service discovery: finding the other ranks


A ClusterIP service gives one virtual address that forwards each connection to one random pod, which is useless when every rank of a training job must reach every other rank. A headless service (clusterIP: None) instead returns one A record per ready pod, and pods of a StatefulSet get stable names, myjob-0.myjob-headless.default.svc.cluster.local and so on ({{StatefulSet docs|https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/#stable-network-id}}); the lab's myjob-headless answered with all four pod addresses. The trap: pods get records only once they are ready, and a training pod often cannot become ready until rendezvous succeeds, which needs the records. publishNotReadyAddresses: true on the service publishes them early; the API reference names StatefulSet peer discovery as its main use ({{Service API|https://kubernetes.io/docs/reference/kubernetes-api/service-resources/service-v1/#ServiceSpec}}). A torchrun job that hangs at start-up waiting for its master address is worth checking for this; training jobs also suffer most from the 5-second stall, since every rank resolves at once. Rendezvous and start-up hangs are on {{Launching distributed training|n:3fc5c17b0d0d81b3a8a5c58224bff9fa}}, the rest of Kubernetes networking on {{Kubernetes for ML|n:3c65c17b0d0d81cf9417de52108cfbce}}.


For serving, DNS round-robin across model replicas is a poor load balancer (clients cache one address; DNS knows nothing about queue depth); the {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}} page (its section 8) balances gRPC in the client over every Pod address a headless Service returns (dns:///name).
