9. DNSSEC: what a signed answer proves

The problem. Classic DNS has no authentication: a resolver accepts the first answer that matches its question's ID and port, so anyone who can answer first, or who controls a hop, can send you to the wrong address (section 10). DNSSEC ({{RFC 4033|https://www.rfc-editor.org/rfc/rfc4033}} to 4035) lets a resolver prove that an answer is exactly what the zone's owner published, and that a "no such name" is genuine.

How it works. Each zone signs every RRset; the signature is an RRSIG record with an inception and an expiry date. The zone publishes its public keys as DNSKEY records, usually in two roles: a key-signing key (KSK) that signs only the key set, and a zone-signing key (ZSK) that signs everything else. The parent vouches for the child's KSK by publishing a hash of it, a DS record, which the parent signs in turn. Following DS to DNSKEY to DS up the tree ends at the root's KSK, which the resolver must already trust: that copy is the trust anchor. A name that does not exist is proven by an NSEC (or hashed NSEC3) record, a signed statement "nothing exists between these two names". Each key is named by a 16-bit key tag, a checksum of the key.

What it does not do. DNSSEC proves origin and integrity, not secrecy: the question and answer still cross the network in the clear. It protects the resolver, not the hop from your laptop to the resolver, unless your own stub validates or trusts the AD flag over a secure channel (glibc only honours AD with options trust-ad, since glibc 2.31; {{resolv.conf(5)|https://man7.org/linux/man-pages/man5/resolv.conf.5.html}}). It says nothing about the server you then connect to (that is TLS's job). And signed answers are larger, which makes DNS a better amplifier for denial-of-service floods.


How it fails: one bad signature takes everything below it down


A validating resolver that finds a broken signature must return SERVFAIL, not the unvalidated answer, so a signing mistake looks exactly like an outage. The test is the CD flag: dig +cd name asks the resolver to skip validation; if that returns an answer while the normal query fails, the problem is DNSSEC. A public example, deliberately broken by its owner: dnssec-failed.org returned SERVFAIL through 1.1.1.1, with the Extended DNS Error "9 (DNSKEY Missing): no SEP matching the DS found", and an address with +cd (measured; Extended DNS Errors are {{RFC 8914|https://www.rfc-editor.org/rfc/rfc8914}}).


The .de outage, 5 May 2026. During a routine key roll, DENIC's signer produced signatures that about two thirds of the time could not be validated, and validating resolvers returned SERVFAIL for much of .de for about three hours ({{DENIC analysis|https://blog.denic.de/en/analysis-of-the-dns-outage-on-5-may-2026/}}). Operators mitigated with negative trust anchors ({{RFC 7646|https://www.rfc-editor.org/rfc/rfc7646}}), an instruction to treat one zone as unsigned for a while, and serve-stale (section 5) softened the impact.


The .de outage in detail
DENIC's new signer generated three different key pairs (one per hardware security module) under the same key tag, 33834, but published only one public key. The SERVFAILs started at roughly 19:30 UTC. Cloudflare's negative trust anchor took effect at 22:17 UTC, and serving stale cached answers softened the impact as records expired ({{Cloudflare|https://blog.cloudflare.com/de-tld-outage-dnssec/}}).


Dated: the root key change of 11 October 2026


KSK-2024 (key tag 38696), published in the root zone on 11 January 2025, was scheduled to become the only key signing the root's key set on 11 October 2026, with the old KSK-2017 (20326) to be revoked in the first quarter of 2027 ({{IANA|https://www.iana.org/dnssec/files}}, {{ICANN|https://www.icann.org/resources/pages/ksk-rollover-en}}); on 5 October 2026 the root served both KSKs and the key set was still signed by KSK-2017 (measured over DNS over TLS). Resolvers that follow automated trust-anchor updates ({{RFC 5011|https://www.rfc-editor.org/rfc/rfc5011}}) have trusted KSK-2024 since February 2025. The risk is a trust anchor frozen in a file (a container image, appliance or VM running its own validating resolver with an anchor baked in before 2025): the chain's third mode above shows it returning SERVFAIL for every name, signed or not. Check the anchor file (trust-anchor-file or auto-trust-anchor-file in Unbound, trust-anchors in BIND) for key tag 38696 or its DS digest 683D2D0A....

Adoption. On 3 October 2026, 39.65% of users worldwide sat behind resolvers that fully validate, and another 9.41% behind a mix of validating and non-validating ones ({{APNIC Labs|https://stats.labs.apnic.net/dnssec/XA}}).
