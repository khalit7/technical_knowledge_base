The idea in one screen

DNS turns a name into records (mostly addresses) through a chain of caches in front of a tree of servers: your C library asks one recursive resolver, the resolver walks from the root down to the zone's own servers only for what it has not cached, and every answer, "no such name" included, is kept for a number of seconds the owner chose. Nearly every DNS problem you will debug is one of four things: the answer is cached somewhere you did not expect, one name was turned into many queries, one lost packet cost a fixed timeout, or the wrong server was asked.

One lookup: one recursive question, a walk down the tree on a cache miss, and a cache at every hop

Static diagram of the running example, api.llm.test on this page's lab tree; the four failure causes sit where they happen. Arrow 1 is the recursive question (section 2); arrows 2 to 4 are asked only when the resolver's cache lacks that level, and the root and top-level answers are almost always cached because they live for days (section 5). Recorded in the lab: 4 upstream queries cold, 0 warm; one lost packet cost glibc 5,037 ms (section 6); ndots:5 turned one name into 8 queries (section 7).

Labels: measured here, illustrative, derived (with its formula).

Stub resolver
the DNS client inside your process (getaddrinfo() in glibc or musl); asks, waits, retries, keeps no cache
Recursive resolver
the server that does the walk and keeps the cache (router, VPC resolver, CoreDNS, 1.1.1.1)
Authoritative server
holds one zone's records; answers or refers, never asks anyone
Zone, delegation
the part of the tree one set of servers answers for; the parent's NS records that hand a child zone over
TTL
seconds a cache may keep a record, set by the zone's owner
NXDOMAIN, NODATA, SERVFAIL
the name does not exist; it exists without that type; the resolver tried and failed
Search list, ndots
suffixes the stub tries for short names; the dot count below which it tries them first

Where and how this page measured (provenance)

Everything marked measured was recorded for this page on 5 October 2026, either on a private DNS tree built in containers on an Apple M1 Pro laptop (Docker Desktop, Linux 5.10; Unbound 1.25.2, CoreDNS 1.12.4, glibc 2.41, musl 1.2.6, dig 9.20.29) or with about twenty-five read-only public lookups. The lab tree exists because the laptop this page was recorded on answers every ordinary public DNS packet with a local filter, so public walks cannot be observed from it (the root's Failure lab shows that filter as its "A TLS error caused by DNS" case). The public lookups were sent over encrypted DNS to a public resolver, with its certificate checked, which the filter does not touch. The lab's addresses (10.53.0.0/16) are a private container network with no route out; .test is reserved ({{RFC 6761 s6.2|https://www.rfc-editor.org/rfc/rfc6761#section-6.2}}), so none of these names can leak into the real DNS.
