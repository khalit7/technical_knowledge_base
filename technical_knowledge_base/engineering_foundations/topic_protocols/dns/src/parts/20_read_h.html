6. The resolver inside your process: glibc and musl

Who actually asks. When Python's requests or httpx, curl, Node's default dns.lookup or a gRPC channel opens a connection to a name, it calls getaddrinfo(), and the C library's stub resolver does the DNS work: it reads /etc/resolv.conf, sends the questions, waits, retries, and returns addresses or an error. On Debian, Ubuntu and the CUDA images that is glibc; on Alpine it is musl, and they behave differently in ways that matter, which is why a glibc-based image is the safer default for ML containers.

The knobs live in /etc/resolv.conf: nameserver (up to three), search, and options ndots:n (default 1), timeout:n (default 5 s) and attempts:n (default 2) ({{resolv.conf(5)|https://man7.org/linux/man-pages/man5/resolv.conf.5.html}}).

The glibc-only switches, and where musl differs

glibc also reads single-request, single-request-reopen, use-vc (always TCP), edns0, trust-ad and no-aaaa. musl documents its differences from glibc in one place ({{musl wiki|https://wiki.musl-libc.org/functional-differences-from-glibc.html#Name-Resolver/DNS}}). Go is the exception to "the C library asks": on Linux it normally uses its own resolver, which reads the same file ({{Go net package|https://pkg.go.dev/net#hdr-Name_Resolution}}).

One lost packet, timed

Both libraries send the A and AAAA questions at the same moment from one socket. A pod asked for api.llm.test. through a relay that dropped the first AAAA question and passed everything else; tcpdump inside the pod recorded every packet. Predict: what does one lost packet cost glibc with default settings?

One lost packet costs exactly the library's timer: 5 s on glibc, 2.5 s on musl, 1 s with timeout:1

measured in the lab, each run once; the bars are the duration of the getaddrinfo call, drawn to one scale, the first answer arriving within milliseconds and the rest of each bar the library sitting on its timer. glibc waits its full timeout before resending; musl resends every timeout / attempts (2.5 s by default) to all servers at once; single-request-reopen did not help because this loss was not caused by the shared socket (it helps against the conntrack races of section 7). timeout:1 is a cheap mitigation where loss is real; too short and a slow resolver looks dead. Section 7's resolver lab replays each run packet by packet.

A dead name server, and a server that fails

glibc asks the listed servers in order, moving on only after a timeout, so a dead first server costs every lookup 5 seconds; musl asks all of them in parallel and takes the first answer, so the same dead server cost it almost nothing. So put your most reliable server first for glibc, and do not list servers that disagree (an internal and a public one) for musl, which will take whichever answers first. A SERVFAIL is final for glibc, which reports it at once; musl keeps asking until its timeout runs out.

What the application sees

The error text tells you which failure you have. In Python both libraries raise socket.gaierror; the codes are the C library's EAI_* values:

"Name or service not known" (EAI_NONAME, -2) means a real "no": check the spelling and which resolver you asked (the Failure lab's "NXDOMAIN" and "Wrong resolver" cases). "Temporary failure in name resolution" (EAI_AGAIN, -3) means no usable answer arrived: a SERVFAIL, a timeout, or no reachable server; it is worth one retry with backoff, and if it took 5 or 10 seconds, packets were lost. curl reports both as curl: (6) Could not resolve host, so ask Python or getent ahosts name for the distinction.

Clients that ignore TTLs, in both directions

No cache at all: Python, Node, glibc and musl. socket.getaddrinfo wraps the C function and adds nothing ({{Python docs|https://docs.python.org/3/library/socket.html#socket.getaddrinfo}}); neither requests nor urllib3 caches names. Node's dns.lookup is a blocking getaddrinfo on libuv's thread pool of 4 threads by default, so slow DNS can stall unrelated file and crypto work ({{Node docs|https://nodejs.org/api/dns.html#implementation-considerations}}). What saves you is connection reuse: a pooled connection resolves once. Recorded in the lab pod (with Kubernetes settings, section 7):

measured: 8 queries per lookup because of the pod's search list (section 7). The middle row is the surprise: a "pooled" client gains nothing when the server closes the connection after each response, because every request then opens a new connection and resolves again.

  • A training loop that builds a new client per batch to fetch shards from object storage does the first row thousands of times a second, which is how cluster DNS servers get overloaded. Reuse one session; where you cannot, run a local cache (NodeLocal DNSCache in Kubernetes, section 7; systemd-resolved or nscd on a VM).
  • Caching longer than the TTL: the JVM. Java caches successful lookups for 30 seconds by default and failures for 10 (networkaddress.cache.ttl, networkaddress.cache.negative.ttl); up to JDK 23, installing a security manager made the positive cache last forever ({{JDK java.security|https://github.com/openjdk/jdk17u/blob/master/src/java.base/share/conf/security/java.security}}). Long-lived JVM services that set it to forever keep calling a load balancer's old address after it moves.
  • Long-lived connections never re-resolve, whatever the TTL: a gRPC channel or a keep-alive HTTP/2 connection stays on the old address until it breaks or is recycled. Cap connection age (gRPC's max_connection_age on the server) when backends move.
