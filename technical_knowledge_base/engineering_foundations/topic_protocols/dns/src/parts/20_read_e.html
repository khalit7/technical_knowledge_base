3. The message on the wire

One format for everything. A question and its answer use the same layout ({{RFC 1035 s4.1|https://www.rfc-editor.org/rfc/rfc1035#section-4.1}}): a 12-byte header, then four sections. The question holds the name, the record type and the class (always IN, Internet); the answer the records asked for; the authority section NS records for a referral, or the zone's SOA record with a "no"; the additional section glue addresses and the EDNS pseudo-record. Each record carries its owner name, type, class, a 32-bit TTL in seconds, and its data.

The header. A 16-bit ID the answer must echo (with the source port, all that ties an answer to its question over UDP: section 10), seven flags (QR response, AA authoritative, TC truncated, RD and RA recursion desired and available, AD validated by DNSSEC, CD checking disabled), four counts, and the 4-bit response code you will debug by: NOERROR; NXDOMAIN (the name does not exist at all); SERVFAIL (the resolver tried and failed, which says nothing about whether the name exists); REFUSED (this server will not answer you). NODATA has no code of its own: NOERROR with an empty answer, the name exists without that type (asking api.llm.test for TXT in the lab returns exactly that, with the SOA in the authority section).

Size: 512 bytes, EDNS, and falling back to TCP

DNS runs on UDP port 53 because one question and one answer usually fit in a datagram each, with no connection to set up. The original limit is 512 bytes per UDP message ({{RFC 1035 s2.3.4|https://www.rfc-editor.org/rfc/rfc1035#section-2.3.4}}). EDNS(0) ({{RFC 6891|https://www.rfc-editor.org/rfc/rfc6891}}) lets a client add an OPT pseudo-record that says how large an answer it can take, plus a DNSSEC OK bit and options (cookies, client subnet, padding). The operators' Flag Day 2020 settled the default advertised size at 1,232 bytes, small enough that an answer never needs IP fragmentation on a normal path ({{dnsflagday.net/2020|https://www.dnsflagday.net/2020/}}); fragments are lost more often and can be forged more easily (section 10), so bigger is not better. When an answer does not fit, the server sends what fits with TC set and the client must ask again over TCP, which every implementation, stubs included, must support ({{RFC 7766 s5|https://www.rfc-editor.org/rfc/rfc7766#section-5}}). The lab's pool.llm.test has 40 addresses:

Without EDNS (+noedns, which is how glibc and musl ask unless told otherwise: their queries in section 7's capture are 30 bytes, header plus question) the 671-byte answer does not fit in 512, so the first reply is an empty truncated message and dig repeats the question over TCP. Section 7's resolver lab has pool.llm.test looked up by glibc and musl (preset "A 40-address answer"): both got a truncated UDP answer, opened TCP and received all 40 addresses; glibc did the whole UDP-then-TCP exchange twice within one call.


How it fails
    

  • TCP 53 blocked by a firewall or security group: small answers work, big ones (many addresses, long TXT records, DNSSEC) fail or time out. Check with dig +tcp name and dig +bufsize=512 name.
    • 

  • Fragmented UDP answers dropped on a path with a smaller MTU: a resolver advertising 4,096 gets nothing back for large answers. Advertise 1,232.
    • 

  • A client that never retries over TCP: musl before 1.2.4 (2023) had no TCP fallback, so very large answers failed on older Alpine images.
    • 



How names are compressed
A name is written as length-prefixed labels (03 api 03 llm 04 test 00), and any later occurrence can be replaced by a two-byte pointer: two high bits set, then a 14-bit offset back into the message, which is why a pointer can only reach the first 16,383 bytes ({{RFC 1035 s4.1.4|https://www.rfc-editor.org/rfc/rfc1035#section-4.1.4}}).
