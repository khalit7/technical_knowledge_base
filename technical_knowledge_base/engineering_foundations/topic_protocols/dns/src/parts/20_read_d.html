2. Resolution, step by step

Two kinds of question. Your program asks its resolver a recursive question: "give me the final answer, do whatever it takes" (the RD, recursion desired, flag is set). The resolver then asks iterative questions down the tree: each authoritative server answers with the record or a referral ("I do not have that; these servers do"), and never asks anyone on your behalf ({{RFC 1034 s4.3.1 and s5.3.3|https://www.rfc-editor.org/rfc/rfc1034#section-5.3.3}}). A resolver starts with nothing but the root servers' addresses (the root hints); its first act is to ask a root server for the current list (priming, the NS . query below).

The recording. A fresh Unbound with an empty cache was asked for api.llm.test once, then again; each authoritative server's own query log shows exactly what it was asked. Predict before it plays: in the cold run with QNAME minimisation, which name does the root server see? Then switch to minimisation off, and to the warm cache.

Fig. 2 · Cold, the resolver walks three levels; warm, nothing leaves it; with minimisation on, the root never sees the full name

  1. The question. The stub sends A? api.llm.test with RD set to the resolver; its cache is empty.
  2. Priming. The resolver starts with only the root hints, so it first asks a root server NS .; the root answers with its own server list (AA set, 84 bytes).
  3. The root sees only test. Asked A test., the root refers the resolver to ns1.nic.test (10.53.0.11), with that address as glue: 80 bytes, no AA flag.
  4. test. sees only llm.test. Asked A llm.test., the test. server refers it to ns1.llm.test (10.53.0.12): 88 bytes.
  5. The zone answers. Asked the full name, llm.test.'s own server answers A 10.53.0.80, TTL 60, with the AA flag: 92 bytes, NOERROR.
  6. Cached and returned. The resolver caches the answer for 60 seconds (and the referrals for their own TTLs) and replies: 5 ms for the whole cold lookup (dig), 4 upstream queries.
  1. The question. The same question, to a resolver with QNAME minimisation switched off and an empty cache.
  2. Priming. NS . to a root server, answered with the root server list (AA, 84 bytes).
  3. The root sees the full name. Asked A api.llm.test., the root still only refers (88 bytes), but it has learned exactly what you are looking up.
  4. So does test. Asked the full name too, it refers to ns1.llm.test (92 bytes).
  5. The zone answers. A 10.53.0.80, TTL 60, AA set, 92 bytes.
  6. Cached and returned. 7 ms for the whole cold lookup (dig), 4 upstream queries: the same count, more said.
  1. The question again. The same question, a few seconds after the cold lookup.
  2. Cache hit. The resolver already holds the answer and sends nothing upstream: 0 queries reached any authoritative server.
  3. The TTL, counted down. The answer comes back with 56 of its 60 seconds left; dig measured 2 ms for the whole lookup.

Every message is from the servers' own logs (measured, CoreDNS log plugin and dig, 5 October 2026); each lab hop takes about a millisecond. On the internet the same walk costs real round trips: the root page measured 212 to 451 ms for an uncached public name and 2.4 ms once cached on the laptop.

What a cold lookup costs. One round trip from your process to the resolver, plus, on a cache miss, one round trip from the resolver to each level it does not already know. The root and top-level domains are almost always cached (their records live for days), so a cold lookup on the internet usually costs the round trip to the domain's own servers, often tens to hundreds of milliseconds. That is why the second lookup is cheap, and why a resolver that is restarted or flushed causes a burst of slow lookups and a burst of load on the authoritative servers.

QNAME minimisation: tell each server only what it needs. Classic resolvers sent the full name to every server, so the root learned every name anyone looked up. With QNAME minimisation ({{RFC 9156|https://www.rfc-editor.org/rfc/rfc9156}}) the root is asked only about test., the test. servers only about llm.test.; in the recording the root's log holds A test. with it on and A api.llm.test. with it off. Unbound has done this by default since 1.7.2 (June 2018; {{Unbound manual|https://unbound.docs.nlnetlabs.nl/en/latest/manpages/unbound.conf.html#unbound-conf-qname-minimisation}}); BIND does a "relaxed" version by default that falls back to the full name when a server answers oddly ({{BIND 9.20 reference|https://bind9.readthedocs.io/en/v9.20.0/reference.html#namedconf-statement-qname-minimization}}). It costs nothing in the common case and can cost extra queries for names many labels deep. Unbound also sets the CD (checking disabled) flag on its upstream questions: it validates signatures itself (section 9) and wants the raw data.

Why dig +trace cannot show this walk on every network

dig +trace name normally does the walk itself, from the root down, and is the best way to separate "the zone is broken" from "my resolver cached something wrong". It only works if your packets reach the root servers. On the laptop this page was recorded on, a filter answers every plain DNS packet itself, even one addressed to a root server and even from inside a container: asked example.com without recursion, a.root-servers.net's address replied with a final answer and the RA flag set, which a real root server never does (it would refer you to the .com servers). Corporate device management, VPNs and security software often do this. That is why the walk on this page is recorded on a private tree, and why the public lookups were sent over DNS over TLS (section 10).
