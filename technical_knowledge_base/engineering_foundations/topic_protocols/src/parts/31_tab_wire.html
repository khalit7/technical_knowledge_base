Words used below. A packet is one unit the network carries (a few hundred to about 1,500 bytes). A port is a number that picks the program on a machine; an address plus a port is one end of a connection. A round trip (RTT) is the time for a message to go and an answer to come back: every protocol step that must wait for an answer costs one. A handshake is the exchange that sets a connection up before any request can go. A stream is one request and its answer inside a shared connection; a frame is one labelled piece of a stream. The Reading tab defines each one properly.

1. The request and the answer, as bytes

The app sends a POST to /v1/messages with a JSON body; the server answers 200 with content-type: text/event-stream and then sends Server-Sent Events (SSE): small text blocks, each an event: line, a data: line and a blank line (WHATWG HTML Standard, section 9.2). The event names and JSON shapes follow Anthropic's Messages API streaming format, trimmed to message_start, one content_block_delta per token, and message_stop. No model runs: the five tokens are fixed, the first comes after (standing in for the model reading the prompt) and the rest apart, so every run sends the same bytes.

Under the bytes, each mark is one recv() call returning bytes to the app over plain HTTP/1.1 (port 8080, no encryption), so the timing is the server's, not the network's. Source: raw/h1_arrivals.json.

Before the first byte of the answer can arrive, the client has to find the server (DNS), open a connection (TCP, or QUIC for HTTP/3), and secure it (TLS). 3. Anatomy: the same request down and up the layers


The HTTP/2 run of the request (the version curl and most SDKs pick when the server offers it), message by message: the left stack is the client, the right stack the server, and the panel under them shows the real bytes of each message and the time it happened. Fifteen messages in seven stretches:


One request, every message, on loopback


    

  1. The app builds the request. The SDK turns the chat turn into the JSON body. Nothing has touched the network yet.
    2. 

  2. DNS turns the name into an address. The test name is pinned to 127.0.0.1, so the panel shows the same question asked of a real LLM API with dig: one address and its TTL, and a DNS filter on this laptop that answered even a query sent straight to a root server.
    3. 

  3. TCP: SYN, SYN-ACK, ACK. The kernel picks a free local port and the three-way handshake opens a reliable, ordered byte stream: the first round trip, before anything else can happen.
    4. 

  4. TLS 1.3 in one round trip. The ClientHello carries the hybrid post-quantum key share in the clear; the ServerHello returns the server's half, and from then on everything is encrypted: the certificate, the signature proving the server holds its key, and both Finished messages.
    5. 

  5. The HTTP/2 request. The connection preface, SETTINGS and the request as HPACK-compressed HEADERS plus a DATA frame, all in one encrypted record; the server answers with its SETTINGS and two TLS session tickets for a later, resumed connection (section 6).
    6. 

  6. Response headers, then the first token. :status 200 and text/event-stream open the stream; after the server's pause the first token arrives, drawn to scale layer by layer.
    7. 

  7. Tokens stream, the stream ends. One DATA frame in one TLS record per token; the last frame carries END_STREAM, and the connection stays open for the next request. Of the whole exchange, the network part on loopback is a few milliseconds; the rest is the server thinking.
