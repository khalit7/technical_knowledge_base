7. LLM provider APIs: one design problem, three answers

Every LLM provider faces the same design problem: a conversation that grows each turn, model output that is sometimes text and sometimes a request to run a tool, and a result that has to come back paired with the call that asked for it. OpenAI's Chat Completions, OpenAI's Responses API, which replaced it as the recommended API ("While Chat Completions remains supported, Responses is recommended for all new projects"), and Anthropic's Messages API answer it differently. Same input in all three, one tool-call round trip: the user asks for the weather in Paris, the model calls get_weather, your code sends back "18 C, clear".

Where the conversation lives, and what a tool call is, differ more than the field names
1. Request
POST /v1/chat/completions
{"model": "...", "messages": [{"role": "user", "content": "Weather in Paris?"}],
 "tools": [{"type": "function", "function": {"name": "get_weather", "parameters": {...}}}]}
2. The model asks for a tool
"choices": [{"message": {"role": "assistant",
   "tool_calls": [{"id": "call_1", "type": "function",
     "function": {"name": "get_weather", "arguments": "{\"city\":\"Paris\"}"}}]},
  "finish_reason": "tool_calls"}]
3. Your code sends the result
POST /v1/chat/completions
{"messages": [ ...the whole history again...,
  {"role": "tool", "tool_call_id": "call_1", "content": "18 C, clear"}], "tools": [...]}

The call is a field on an assistant message; arguments is a JSON string the model wrote, so your code parses it and must handle invalid JSON. The client resends the whole conversation every turn; tool definitions are externally tagged ({"type":"function","function":{...}}) and "non-strict by default".

1. Request
POST /v1/responses
{"model": "...", "input": "Weather in Paris?",
 "tools": [{"type": "function", "name": "get_weather", "parameters": {...}}]}
2. The model asks for a tool
{"id": "resp_1", "output": [
  {"type": "function_call", "call_id": "call_1", "name": "get_weather",
   "arguments": "{\"city\":\"Paris\"}"}]}
3. Your code sends the result
POST /v1/responses
{"previous_response_id": "resp_1",
 "input": [{"type": "function_call_output", "call_id": "call_1", "output": "18 C, clear"}]}

Everything is a typed item ("Items are distinct from one another and better represent the basic unit of model context"): messages, function calls, their outputs and reasoning are siblings in one list. The server can hold the conversation: "Responses are stored by default", and previous_response_id lets OpenAI "manage prior response context", so step 3 sends only the new item. Definitions are internally tagged, and "omitting strict attempts strict mode". Arguments are still a JSON string.

1. Request
POST /v1/messages        anthropic-version: 2023-06-01
{"model": "...", "max_tokens": 1024, "messages": [{"role": "user", "content": "Weather in Paris?"}],
 "tools": [{"name": "get_weather", "input_schema": {...}}]}
2. The model asks for a tool
{"content": [
  {"type": "tool_use", "id": "toolu_1", "name": "get_weather", "input": {"city": "Paris"}}],
 "stop_reason": "tool_use"}
3. Your code sends the result
POST /v1/messages
{"messages": [ ...the whole history again...,
  {"role": "user", "content": [{"type": "tool_result", "tool_use_id": "toolu_1", "content": "18 C, clear"}]}],
 "tools": [...]}

A turn's content is a list of typed blocks (text, tool_use, thinking), so text and calls interleave in one message. input is a parsed JSON object; the result goes back as a tool_result block in the next user message. Stateless: the client resends the history (prompt caching makes the repeated prefix cheap). The version is a date header, and max_tokens is required.

The pattern to take away is the stateless-against-stateful choice (section 2's REST constraint, bought or given up), and typed parts over bare strings. Translation between formats loses whatever one has and the other lacks (cache breakpoints, thinking blocks and their signatures, reasoning items): {{Gateways and routing|n:3f15c17b0d0d81e4a964c129a3e520ae}} records a gateway sending the same request as Responses or Chat Completions depending on a prefix. How these formats become tokens inside the model, and the open-model template that has no ids at all, is {{Building a harness|n:3c65c17b0d0d817ca14fc32338707c2f}}'s; their streaming events are {{Streaming and real-time|n:3c65c17b0d0d812daa9fdb38719fc82b}}'s.
