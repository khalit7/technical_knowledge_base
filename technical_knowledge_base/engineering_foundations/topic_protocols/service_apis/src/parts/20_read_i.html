13. Load balancing gRPC: L4, L7 and the client

Three replicas should take a third of the calls each. Where and how often a replica is chosen decides whether they do, or one is hot and two idle; with gRPC's long-lived multiplexed connections this is the number-one production surprise. Predict where backend-3's calls come from in each setup before steps 5 to 8.

L4 (AWS NLB, Linux IPVS, kube-proxy, nginx stream) sees TCP and copies bytes without reading them. L7 (Envoy, nginx grpc_pass, a mesh sidecar, AWS ALB, which has supported gRPC since 29 October 2020, {{AWS|https://aws.amazon.com/about-aws/whats-new/2020/10/application-load-balancers-enable-grpc-workloads-end-to-end-http-2-support/}}) terminates HTTP/2, reads each call's HEADERS and can route on :path, retry and count calls in flight. Client-side: the channel learns every address (DNS or a control plane) and picks per call with a policy: pick_first (the default), round_robin, or xDS policies ({{gRPC load balancing|https://github.com/grpc/grpc/blob/master/doc/load-balancing.md}}).

Fig. 5 · An L4 balancer chooses once per connection; an L7 balancer or the client chooses once per call

  1. Behind an L4 balancer, one choice. One client channel opens one TCP connection; the L4 balancer (nginx stream) picks a replica once, for that connection. It balanced connections, and there was one, so all 30 calls went to backend-1: 30 / 0 / 0.
  2. Behind an L7 balancer, a choice per call. The client still opens one connection, to the proxy (nginx grpc_pass), which reads each call's HEADERS and keeps its own connection to every replica: 10 / 10 / 10.
  3. The client chooses, with the default policy. A client given all three addresses still sent everything to backend-1, because pick_first "attempts to connect to those addresses one at a time, in order, until it finds one that is reachable" and then sends every call there: 30 / 0 / 0.
  4. The client chooses, round_robin. Asked for explicitly ({"loadBalancingConfig": [{"round_robin": {}}]} in the service config, or the channel option), the channel keeps one connection per replica and rotates the calls: 11 / 9 / 10.
  5. A replica joins, behind plain L4. Autoscaling makes it worse. Each run started with backend-1 and backend-2, sent one call every 50 ms for 7 s, and backend-3 joined at 1.5 s (nginx reloaded with the longer list). The existing connection stays where it is until something closes it: of the 96 calls after the join, backend-3 got none.
  6. L4 with MAX_CONNECTION_AGE. With an age of 1 s on the servers, each connection was closed gracefully with GOAWAY about every second and the client reconnected through the balancer, a new choice each time: backend-3 took its first call at 4.28 s and 17 of the 97 calls after the join, with no failed calls.
  7. L7. The proxy sent backend-3 a call 0.22 s after the reload, and 32 of the 100 calls after the join.
  8. A fixed client list. round_robin over the two addresses it was given was perfectly even over what it knew (48 / 47 after the join) and blind to what it did not: backend-3 got nothing.

What to do, in order of preference

  1. An L7 proxy that speaks HTTP/2 (Envoy, nginx grpc_pass, Istio or Linkerd, a cloud L7 balancer). Cost: one more hop to run and scale.
  2. Client-side round_robin over every replica: in Kubernetes a headless Service (clusterIP: None) makes DNS return one record per Pod instead of a virtual IP ({{Kubernetes Services|https://kubernetes.io/docs/concepts/services-networking/service/}}), and the target dns:///name resolves them all. Cost: a connection from every client to every replica; new Pods seen only on re-resolution.
  3. Proxyless xDS: endpoints and policies from a control plane, no proxy in the path; most moving parts.
  4. L4 plus MAX_CONNECTION_AGE when nothing else is possible: it bounds imbalance at the price of reconnects (TCP and maybe TLS each), so minutes, not seconds.

Kubernetes' default ClusterIP Service is L4: in iptables mode kube-proxy picks a backend Pod "at random" for each new connection ({{Kubernetes virtual IPs|https://kubernetes.io/docs/reference/networking/virtual-ips/}}), so a gRPC client of a plain Service behaves like the L4 rows.

LLM calls are not equal. A 50-token turn and a 100,000-token document differ in cost by orders of magnitude, and a replica that already holds a conversation's prefix in its KV cache skips most of the prefill, so an LLM router reads the request and each replica's state (queue depth, cache contents, loaded adapters): L7 by definition. Routing across serving replicas, and its visual, are {{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}'s; balancing algorithms (least outstanding requests, power of two choices, consistent hashing) are {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}}'s.

Depth: the inference gateway's gRPC side channel (Gateway API Inference Extension, llm-d), and when pinning is wanted
  • Gateway API Inference Extension (an official Kubernetes project, v1.6.2 on 17 September 2026) turns any gateway that supports Envoy's external processing into an "inference gateway": an Endpoint Picker chooses the replica per request from model-server metrics such as prefix-cache status and LoRA adapter availability ({{project README|https://github.com/kubernetes-sigs/gateway-api-inference-extension}}). The picker's main implementation has moved to the llm-d project's router.
  • The side channel is gRPC. Envoy asks the picker over ExternalProcessor.Process, a bidirectional gRPC stream (rpc Process(stream ProcessingRequest) returns (stream ProcessingResponse) in Envoy's {{ext_proc API|https://github.com/envoyproxy/envoy/blob/v1.39.2/api/envoy/service/ext_proc/v3/external_processor.proto}}).
  • llm-d (v0.10.0, 29 September 2026) packages prefix-cache-aware and load-aware routing with vLLM and reports "3x higher output throughput and 2x faster TTFT" against round robin on Llama 3.1 70B with 4 AMD MI300X ({{llm-d README|https://github.com/llm-d/llm-d}}; project-reported, not reproduced here).

Sometimes you want the pinning: Triton recommends unary inference calls, but notes that a bidirectional stream "will hold a single connection throughout the lifetime and hence ensure the requests are delivered to the same Triton instance", which sequence models need ({{Triton inference protocols|https://github.com/triton-inference-server/server/blob/main/docs/customization_guide/inference_protocols.md}}).
