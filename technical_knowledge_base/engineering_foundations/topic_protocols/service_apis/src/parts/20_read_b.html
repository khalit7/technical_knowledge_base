2. REST done properly: resources, errors, pages, versions

A public LLM API is called by curl, SDKs, browsers and proxies you have never seen; the one thing they share is HTTP. "REST" in practice means resource-shaped HTTP with JSON (Fielding's full style, below, is rarely followed), and what separates a good one is a handful of decisions client code depends on.

A well-designed call carries its contract in the URL, the headers and the error body

The seven parts: 1. a plural noun with a major version in the path; 2. a dated version in a header, pinned per request; 3. a client-chosen key that makes this POST safe to retry (section 4); 4. the status says whose fault and whether to retry; 5. how long to wait (section 5); 6. a request id to quote to support and to search your logs for; 7. a stable, documented error type that code can switch on.

Resources and methods

Model the API as nouns with URLs (/v1/chats/{id}/messages), plural collections, one level of nesting for real ownership, and opaque prefixed string ids (chat_ae8136d1b896 rather than 17, which leaks volume and invites guessing). Let the method be the verb: GET is safe, PUT and DELETE are idempotent, POST is neither ({{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}} section 2 owns those semantics). Return the created object with 201 and Location. Two shapes cover what CRUD does not:

  • Custom methods. An action that is not create, read, update or delete gets a :verb suffix on the resource, POST /v1/{name=publishers/*/books/*}:archive in Google's rules ({{AIP-136|https://google.aip.dev/136}}). Never a GET with side effects: crawlers, link previews and caches send GETs freely.
  • Long-running work. When a call takes minutes, answer at once with a handle to poll: Google returns an Operation resource ({{AIP-151|https://google.aip.dev/151}}); plain HTTP says 202 Accepted. Anthropic's Message Batches API is this pattern: a batch starts in_progress, you poll until ended, results stay for 29 days ({{Claude docs, batch processing|https://docs.claude.com/en/docs/build-with-claude/batch-processing}}); a webhook (section 6) is the push alternative to polling.

The running request is a function call wearing a resource's URL (POST /v1/messages creates nothing you GET later), which is fine: the expensive call hangs off an ordinary resource that can be stored, billed, listed and made idempotent. For searches with large bodies, RFC 10008 (June 2026) adds QUERY: a safe, idempotent request that carries a body, so a search or GraphQL query no longer has to choose between a huge URL and an uncacheable POST.

Errors: three layers

Client code must decide, for every failure, whether to show a message, retry, give up or re-authenticate. It can only do that if errors have three layers: the status code (whose fault, retry or not), a stable error type that code switches on and that is append-only (never renamed or reused), and human text that no code parses. Add a request id in a header and in the body (Anthropic: request-id; OpenAI: x-request-id). The standard shape is RFC 9457 problem details, application/problem+json with type, status, title, detail, instance ({{RFC 9457|https://www.rfc-editor.org/rfc/rfc9457.html}}, July 2023, obsoletes RFC 7807). LLM providers predate it and keep their own envelopes with the same layers (Anthropic's types run from invalid_request_error, 400, to overloaded_error, a non-standard 529, and "the type values will grow over time"). Two rules people break: one shape for every error, including a proxy's HTML 502 page; and once a stream has started the status is already 200, so later errors arrive as an event inside the stream.

Pagination: offset shifts under writes, a cursor does not

A list endpoint returns a page and a way to ask for the next. Offset (?limit=20&offset=40) is easy and lets a UI jump to page 7, but the database still reads every skipped row, and rows added while the user pages shift everything. A cursor encodes the sort key of the last row seen, WHERE (created_at, id) > (:t, :id), so an index seeks straight to it. The rules from the big style guides: cursors are opaque ("must be opaque (but URL-safe) strings, and must not be user-parseable", {{AIP-158|https://google.aip.dev/158}}), because anything clients can decode they will depend on; an empty next token is the only end signal; cap limit; sort by a unique key (add the id as a tie-breaker, or equal timestamps skip or repeat across a page boundary); skip total_count unless needed, since counting a filtered set is itself a scan. Offset keeps a place in small admin tables.

Versioning: never break a client you cannot see

A breaking change is any change after which a correct existing client stops working or starts doing something different: removing or renaming a field, changing its type, making an optional field required, changing a default ("Changing the default value is considered breaking", {{AIP-180|https://google.aip.dev/180}}), or changing behaviour under the same shape. Adding endpoints, optional fields, response fields and enum values is safe only if clients are tolerant readers that ignore what they do not know; Anthropic's contract reserves the right, within a version, to "add new variants to enum-like output values (for example, streaming event types)" ({{Claude API versioning|https://platform.claude.com/docs/en/api/versioning}}).

What a dated header buys shows in Anthropic's second date. 2023-06-01 served every client for over three years while the API grew additively; the breaking changes then shipped together as anthropic-version: 2026-10-21 (21 October 2026): temperature, top_p and top_k return 400 "even at the parameter's default value", a document block directly in an assistant message returns 400, and so does a non-empty citations array on a text block in a user message ({{migration guide|https://platform.claude.com/docs/en/api/migration-2026-10-21}}). Nothing forces the move: the guide gives no sunset for 2023-06-01 and tells a request that relies on non-default sampling to stay on it. The new SDK major versions send the new date by default, so the upgrade happens when a team bumps a major dependency, the moment it expects to read a changelog.

For an LLM API the model is part of the contract: the same request to a new model gives different answers, lengths and costs, so production code pins dated snapshot names rather than moving aliases.

Depth: what Fielding's REST actually is, the Richardson levels, retiring endpoints

REST is an architectural style Roy Fielding described in chapter 5 of his 2000 dissertation to explain why the web scaled ({{Fielding, chapter 5|https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm}}). Its constraints, each with what it buys: resources, not functions (you transfer representations of a named thing); a uniform interface (a small fixed set of verbs with universal meaning: this, not JSON, is the deepest difference from RPC, since every intermediary knows what a GET may do); statelessness (each request carries everything needed, the API key and the full conversation, which is what lets any replica answer any request); cacheable and layered (proxies and caches can sit in between without understanding your app); and hypermedia (HATEOAS: responses carry links to the next actions; the least followed constraint, whose one mass deployment is the human web of HTML links and forms).

Martin Fowler's write-up of Leonard Richardson's maturity levels is the usual yardstick ({{Fowler, 2010|https://martinfowler.com/articles/richardsonMaturityModel.html}}): level 0 is one endpoint taking POSTs (RPC in JSON), level 1 adds resources with their own URLs, level 2 uses the HTTP verbs and status codes properly, level 3 adds hypermedia links. Level 2 is where almost every good API stops, and the running request is level 2; "HTTP API" is the honest name.

Retire anything with a date, a warning while it still works (the Deprecation header, RFC 9745, and Sunset, RFC 8594), and logs that show nobody still calls it. A fourth versioning school uses no URL versions at all and evolves compatibly, new media types if forced (Zalando's guidelines: "MUST not use URL versioning"). Stripe's post reports close to 100 backwards-incompatible upgrades over six years handled by its transform modules without breaking integrations; most teams should start with /v1/ plus strictly additive changes and add a version header when the first unavoidable break arrives.
