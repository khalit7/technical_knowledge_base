14. Browsers, gateways and the gRPC family

A browser's fetch cannot read HTTP trailers or control HTTP/2 framing, so it cannot speak gRPC as section 9 recorded it; nor can many HTTP/1.1-only proxies, serverless platforms or a developer with only curl. Three answers keep one .proto and change the wire face:

gRPC-Web

The same messages with the trailers moved into the body: a final length-prefixed frame whose flag byte has its top bit set (0x80) carries grpc-status as text. HTTP/1.1 works; unary and server streaming only; a proxy (Envoy's grpc_web filter) translates ({{PROTOCOL-WEB.md|https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-WEB.md}}).

Connect

A protocol and libraries (a CNCF sandbox project, per {{connectrpc.com|https://connectrpc.com/}}): a unary call is a plain POST /package.Service/Method with application/json or application/proto, Connect-Protocol-Version: 1 and Connect-Timeout-Ms for the deadline; errors use ordinary HTTP status codes with a JSON body. Unary and server streaming over HTTP/1.1; bidirectional needs HTTP/2 ({{Connect protocol|https://connectrpc.com/docs/protocol/}}). curl-able, which is the point.

HTTP/JSON transcoding

Annotate each RPC with its REST shape and a gateway (Envoy's JSON transcoder, {{grpc-gateway|https://github.com/grpc-ecosystem/grpc-gateway}}) serves both: option (google.api.http) = { post: "/v1/{parent=publishers/*}/books" body: "book" }. Google's rule is that APIs "must" provide this for every RPC except bidirectional streaming ({{AIP-127|https://google.aip.dev/127}}).

tRPC is not related: no protobuf, no HTTP/2 requirement, no code generation. It is a TypeScript library where the client imports the server router's type, giving "fully typesafe APIs without schemas or code generation"; on the wire it is ordinary JSON over HTTP, with batching and subscriptions ({{tRPC README|https://github.com/trpc/trpc}}, v11.19.0 on 16 September 2026). Use it for a TypeScript product whose only client is its own front end; put REST or gRPC at any boundary another team or language must cross. ML serving never uses it.

15. GraphQL: when the client should choose the shape

A catalogue page wants each model's name and provider, the mobile app adds eval scores, an internal tool wants licences: REST gives one call per object or an endpoint per screen. GraphQL (created at Facebook, now a Linux Foundation specification; current edition September 2025, per the root's atlas) gives one endpoint and a typed schema, and each client names exactly the fields it wants, { models(first: 20) { name provider { name } } }. The server runs a resolver per field and returns JSON of that shape: on the lab's toy catalogue (20 made-up models, 12 fields each) a REST list of every field is bytes, the GraphQL names-only query . The price comes in three parts.

One query, many backend calls. Resolvers run per object, so 20 models whose provider resolver queries the database make 1 + 20 queries: the N+1 problem. A DataLoader fixes it: resolvers ask a loader for a key, it waits one tick of the event loop, then fetches every requested key in one batched call. Measured with graphql-core against a counting fake database:

Database calls are measured; the fake database sleeps 2 ms per call. Wall times were close because the resolvers run concurrently on one event loop: the price of N+1 here is load on the database, which is what falls over in production.

One query can ask for the world. Nesting multiplies: with first: 20 then first: 10 five levels deep, the lab's static estimate (multiply each list's first down the tree, before running anything) came to fields. Public GraphQL APIs price queries before running them: GitHub caps a call at 500,000 nodes, requires first or last between 1 and 100 on every connection, charges computed points against 5,000 per hour per user, allows no more than 2,000 points per minute, and stops any request after 10 seconds ({{GitHub GraphQL limits|https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api}}). Other defences: depth limits and persisted queries (only queries registered in advance, sent by hash).

HTTP stops helping. Queries usually travel as POST, which caches ignore (the GraphQL-over-HTTP draft allows GET for queries, never mutations, "MUST respond with an appropriate 4xx", 405 recommended; RFC 10008's QUERY now offers a cacheable request with a body). And a field can fail while the rest succeeds: in the lab one resolver failed and the result carried data with null there plus an errors array naming its path:



Classic servers answer 200 with that body, so monitoring that counts 5xx sees nothing; the GraphQL-over-HTTP working draft fixes this for clients sending Accept: application/graphql-response+json (400 for a document that does not parse, 422 for one that fails validation; {{draft|https://graphql.github.io/graphql-over-http/draft/}}, read 5 October 2026). Alert on the errors array, not only on status codes. When it fits: many clients needing different shapes of one graph of data, where round trips are expensive (mobile, aggregating many backends). In ML work you will mostly consume it (GitHub's API from tooling and agents); it is rarely right for model serving, where the request shape is fixed and the cost is in the GPU, not in fetching fields.






16. JSON-RPC 2.0: the smallest call format


Sometimes you need named method calls over a channel that is not HTTP at all: a pipe to a child process (an MCP server on stdio, a language server), a WebSocket, a single endpoint. JSON-RPC 2.0 is "a stateless, light-weight remote procedure call (RPC) protocol", "transport agnostic" ({{specification|https://www.jsonrpc.org/specification}}, 2010, updated 2013):




Request
{"jsonrpc": "2.0", "id": 1, "method": "tools/call",
 "params": {"name": "get_weather", "arguments": {"city": "Paris"}}}


Response (same id)
{"jsonrpc": "2.0", "id": 1, "result": {...}}
{"jsonrpc": "2.0", "id": 1,
 "error": {"code": -32601, "message": "Method not found"}}




The id pairs answers with requests, so many calls can be in flight and answers may return in any order; a notification has no id and must not be answered (progress events); a batch is an array answered by an array. Reserved errors: -32700 parse error, -32600 invalid request, -32601 method not found, -32602 invalid params, -32603 internal error, -32000 to -32099 for the server implementation. What it leaves out (schema, streaming, deadlines, transport, auth) is the point: a protocol that adopts it must add those, which is most of what the MCP and A2A specifications are. MCP allowed JSON-RPC batches in its 2025-03-26 revision and removed them in 2025-06-18 ({{MCP|n:3c65c17b0d0d813f9695dc4175c44cbb}}).


Correction carried from the root
The old page said agent protocols "chose JSON-RPC over HTTP (+SSE) rather than gRPC". True of MCP. A2A v1.0 separates the protocol from three bindings: JSON-RPC 2.0, gRPC and HTTP+JSON/REST (root {{Protocol atlas|n:3c65c17b0d0d81ec9355f4eecd6eed02}}, corrections list, item 3; {{A2A v1.0.1 specification|https://github.com/a2aproject/A2A/blob/v1.0.1/docs/specification.md}}; {{Agent-to-agent and beyond|n:3f05c17b0d0d81199373d4d0b18706d8}}).


For a new internal protocol: JSON-RPC when the other end is a model or an editor plugin, messages are few, humans read the logs and the channel may be stdio; gRPC when calls are many, typed and streaming and cross-language teams need generated clients.
