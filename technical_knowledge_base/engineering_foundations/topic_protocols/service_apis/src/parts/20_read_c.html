3. OpenAPI and schema-first design: the contract as data

Without a written contract, clients and servers drift apart silently: a renamed field is found by a customer, not a compiler. A schema turns the contract into data that tools check. For REST that is an OpenAPI document (paths, methods, parameters, request and response schemas, auth schemes); for gRPC it is the .proto file (section 8); for GraphQL its SDL. Everything else is generated from it:

Code-first writes the server and exports the spec (FastAPI serves one at /openapi.json); schema-first writes the spec, reviews it like code, and generates server stubs and clients from it. Larger organisations with many teams tend to the second, because the review happens before anyone depends on the shape, and a CI job that diffs the new spec against the published one fails the build when a field disappears. Several API companies, LLM providers among them, generate their official SDKs from an OpenAPI spec with commercial generators. OpenAPI 3.1 aligned its schemas with JSON Schema; 3.2.0 (19 September 2025) added sequential and streaming media types such as text/event-stream, so SSE endpoints can finally be described; the current release is 3.2.1 (10 September 2026, the root's {{Protocol atlas|n:3c65c17b0d0d81ec9355f4eecd6eed02}} entry).

4. Idempotency keys and retries across services

The user presses Send; after 30 seconds nothing has come back. Either the request never arrived, or it arrived, the model answered, the credits were charged and the reply was lost. The client sees the same timeout in both cases: retrying risks paying twice, not retrying risks losing the message. GET, PUT and DELETE may be retried because they are idempotent; generation is a POST. An idempotency key makes one POST idempotent: the client generates a unique value per logical action, sends it on every retry of that action, and the server answers repeats from what it stored the first time. The page's toy front door ran the same lost reply four ways; pick one:

Fig. 3 · The retry is harmless only when the server remembers the key

  1. The request leaves without a key. The toy client sends the message at 0.000 s with a 0.2 s read timeout; the toy server's "model" takes 0.3 s.
  2. The work commits. At 0.301 s the server saves msg_1 and charges 10 credits in one transaction.
  3. The reply is lost. The client gave up at 0.201 s, so the 201 written at 0.301 s reaches nobody. A tunnel, a proxy reset, a phone that slept: the client cannot tell this from a request that never arrived.
  4. The client retries. It must, or the message is lost. At 0.601 s the same body arrives with nothing to recognise it by, so the model runs again: msg_2 and 10 more credits, answered at 0.902 s.
  5. What the user ends up with. Two messages and 20 credits for one press of Send, and a duplicate in the chat.
  1. Claim the key. The request carries Idempotency-Key: 7f3c9a0e-...; at 0.000 s the server inserts the key with the request's fingerprint and status started, under a unique constraint, so of two simultaneous attempts exactly one wins.
  2. One transaction. At 0.301 s msg_1, the 10-credit charge and the stored 201 response commit together, and the key becomes done.
  3. The reply is lost. The client gave up at 0.200 s, as before.
  4. The retry is answered from the store. At 0.601 s the same key and fingerprint arrive and the key is done, so no work runs: the stored 201 for msg_1 comes back marked Idempotent-Replayed: true, in under a millisecond.
  5. What the user ends up with. One message, 10 credits, and the same response the first attempt would have returned.
  1. Claim the key. The first attempt claims the key at 0.000 s and starts the work.
  2. A retry arrives too early. At 0.250 s, while the key is still started, the same request comes again: 409, retry later. Running it would charge twice; waiting is the only safe answer.
  3. The work commits; the reply is lost. msg_1 commits at 0.301 s; the first attempt's client had given up at 0.201 s.
  4. The later retry is replayed. At 0.600 s the key is done: the stored 201 for msg_1 comes back, Idempotent-Replayed: true. One message, 10 credits.
  1. A normal call. The first request claims its key and succeeds: 201, msg_1, at 0.301 s.
  2. The same key, a different message. The client reuses the key for "What colour is grass?". Its fingerprint (e7b301b3) differs from the stored one (2fc72bdf), so the server answers 422 rather than replay the answer to a different question.
  3. The key is bound to its first request. Still one message and 10 credits; a client bug that reuses keys shows up as 422s, not as wrong answers.

The work time (0.3 s), the client's timeout (0.2 s) and the price (10 credits) are the toy's settings, illustrative; statuses, headers, counts and times are measured. The mechanism follows Stripe's design ({{Stripe, idempotent requests|https://docs.stripe.com/api/idempotent_requests}}; {{Brandur Leach, 2017|https://brandur.org/idempotency-keys}}).

The server side, in three steps. (1) Claim the key atomically: insert (user, key, request fingerprint, status started) under a unique constraint, so exactly one of two simultaneous attempts wins; never "select, and if absent insert", which races. (2) If it exists, compare and replay: a different fingerprint means the client reused a key for a different action (422); started means the first attempt is still running (409, retry later); done means return the stored status and body (Stripe marks it Idempotent-Replayed: true). (3) Do the work and store the result in one transaction, so the message, the charge and the stored response commit together. Then release the claim on every exit that did not store a response, and give claims an expiry, or a crash between steps 1 and 3 leaves the key stuck at started and every retry gets 409 forever ({{Code design|n:3ef5c17b0d0d817b99a0ff9701ff30cd}} found and measured exactly that bug in the Building a backend API demo).

Across services: one retry layer, one deadline, one key

Behind the front door the same request crosses a router and an inference service, and each hop has a client that could retry. Three rules keep that safe:

  • Retry at one layer. If three layers each make 3 attempts, one failing call becomes 3 × 3 × 3 = 27 attempts at the bottom, arriving exactly when the bottom is already failing (attempts multiply: aL for a attempts at each of L layers). Retry at the edge, or in the client closest to the failure, and let the others fail fast. Retry budgets and circuit breakers that cap this system-wide are {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}'s.
  • Every attempt shares the original deadline. gRPC's deadline "applies across all attempts" (section 11); a retry that resets the clock outlives the user who asked.
  • Pass the key down. A retried front-door request must not become a second charge two hops down, so the service that owns the side effect (the billing call, the outbox row) receives a key derived from the caller's, and dedupes on it. When the side effect leaves your database (a payment provider, a message queue), store the intent and the key first and send later: the outbox pattern on {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}. Brandur Leach's design generalises this: split the request into atomic phases ("a set of local state mutations that occur in transactions between foreign state mutations") with a recovery point after each, because "once we make our first foreign state mutation, we're committed one way or another" ({{brandur.org|https://brandur.org/idempotency-keys}}); a retry resumes from the last recovery point. For an LLM call: record that the model was called and store its output before charging and answering, and pass your own idempotency key to any provider that accepts one.

The official Anthropic and OpenAI Python SDKs retry connection errors, 408, 409, 429 and 5xx themselves, with no idempotency key; {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}} section 10 measures their attempts, and is the owner of retry safety at the protocol level.
