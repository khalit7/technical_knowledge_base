11. Status codes, errors and retries

When a call fails the caller must decide in microseconds: give up, retry here, retry elsewhere, or tell the user something specific. HTTP's codes were designed for documents; gRPC's 17 codes, carried in the grpc-status trailer under an HTTP 200, were designed for that decision ({{gRPC status codes|https://grpc.io/docs/guides/status-codes/}}). The decision, drawn:

The code says whether a retry is safe, and at what scope

The rule for three easily confused codes, paraphrased from gRPC's {{statuscodes.md|https://github.com/grpc/grpc/blob/master/doc/statuscodes.md}} and {{google/rpc/code.proto|https://github.com/googleapis/googleapis/blob/master/google/rpc/code.proto}}: UNAVAILABLE if the client can retry just this call, ABORTED if it should retry a larger transaction (a read-modify-write), FAILED_PRECONDITION if it should not retry until someone fixes the state. DEADLINE_EXCEEDED "may be returned even if the operation has completed successfully".

Three of those recordings teach something the table does not. The 5 MB prompt failed with RESOURCE_EXHAUSTED because the default receive limit is 4 MiB (the details give both numbers, 4194304): long contexts and embedding batches hit it, and the fix is grpc.max_receive_message_length on the receiver (vLLM's gRPC server sets it to unlimited). A dead backend behind the L7 balancer reached the client as UNAVAILABLE with "Received http2 header with status: 502": clients synthesise a gRPC status when a proxy answers in plain HTTP. And UNAVAILABLE to a closed port came back in about 1 ms, because a call fails fast when the channel cannot connect unless you ask for wait_for_ready=True ({{wait-for-ready guide|https://grpc.io/docs/guides/wait-for-ready/}}).

Retries: off by default, on by configuration

gRPC retries two ways ({{retry design A6|https://github.com/grpc/proposal/blob/master/A6-client-retries.md}}). Transparent retries are always on: when the call never left the client, or reached the server but not your handler, the library retries, because nothing can have happened twice. A retry policy exists only if the service config (JSON given to the channel, or published by the name resolver) has one: which codes, up to how many attempts (values above 5 are treated as 5), exponential backoff with plus or minus 20% jitter, and the deadline "applies across all attempts". Each retry carries grpc-previous-rpc-attempts.

{"methodConfig": [{"name": [{"service": "llm.v1.Inference", "method": "Who"}],
  "retryPolicy": {"maxAttempts": 4, "initialBackoff": "0.1s", "maxBackoff": "1s",
                  "backoffMultiplier": 2, "retryableStatusCodes": ["UNAVAILABLE"]}}]}

Against a replica that answers UNAVAILABLE twice while "warming up", the call without the policy failed at once; with it, the server log shows three attempts , and the caller saw only success (measured). Two valves stop retries becoming a storm: retry throttling (a per-server token bucket: with "maxTokens": 10, "tokenRatio": 0.1 each failure costs a token, each success returns 0.1, and retries stop while the count is at or below half) and server pushback (grpc-retry-pushback-ms says when, a negative value says never). Hedging sends a second copy after a delay without waiting for the first to fail, for idempotent calls with long tails; Go and C-core had not implemented it when the design was last updated (2024-08-23).

Correction to the old page
The old page said "only UNAVAILABLE-class errors are safely retryable by default". By default no application-level retry happens at all, only the transparent ones. Which codes are safe depends on whether the method is idempotent (or carries an idempotency key, section 4); gRPC's docs say there is "no fixed list of status codes on which it is appropriate to retry in all applications". UNAVAILABLE is the usual choice because it normally means the request was not processed; DEADLINE_EXCEEDED is the dangerous one.

Richer errors. A code and a string are often not enough ("which field?", "retry after how long?"). The trailer grpc-status-details-bin carries a serialised google.rpc.Status with typed details such as BadRequest or RetryInfo ({{AIP-193|https://google.aip.dev/193}}): the gRPC twin of section 2's three error layers.

12. Connections: keepalive, limits, health and reflection

A channel keeps its connections for hours. Meanwhile a NAT box may silently drop an idle connection, a server may drain for a deploy, and a big message may exceed a limit. A keepalive is an HTTP/2 PING on a quiet connection; no ACK within 20 s (the default timeout) and the connection is declared dead, so calls fail with UNAVAILABLE instead of hanging. Client keepalive is off by default in gRPC core, and servers defend themselves against ping floods: by default they expect at least 5 minutes between pings on a connection carrying no data, and after 2 "strikes" they send GOAWAY with ENHANCE_YOUR_CALM ({{keepalive guide|https://github.com/grpc/grpc/blob/master/doc/keepalive.md}}). The lab reproduced it: a client with grpc.keepalive_time_ms=1000 made a call whose first token takes 8 s. At first nothing happened (the client's own brake, max_pings_without_data, default 2, stopped it after two pings); with that brake removed the server cut the connection mid-call:

The client saw UNAVAILABLE: Too many pings and lost the in-flight call. vLLM's gRPC server (v0.31.0) carries exactly this fix, noting that keepalive and BDP-probe pings during a non-streaming Generate "are strikes and eventually earn a GOAWAY(ENHANCE_YOUR_CALM, "too_many_pings") that fails every in-flight RPC", so it sets grpc.http2.max_ping_strikes to 0 ({{grpc_server.py|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/entrypoints/launchers/grpc_server.py}}). Rule: client keepalive slower than the server's minimum interval, or tell the server to accept faster pings. The same file records a second trap: a misspelt option "and gRPC Core silently ignores unknown keys, so the misspelt form left the 300s default in force"; check channel arguments against the {{core list|https://grpc.github.io/grpc/core/group__grpc__arg__keys.html}} and test that behaviour changed.

GOAWAY and connection age. GOAWAY is "no new streams on this connection": it names the last stream accepted, so the client knows which calls to resend elsewhere. Servers send it when shutting down, and on a timer if configured: MAX_CONNECTION_IDLE, MAX_CONNECTION_AGE (plus or minus 10% jitter so clients do not reconnect together) and MAX_CONNECTION_AGE_GRACE, all infinite by default ({{proposal A9|https://github.com/grpc/proposal/blob/master/A9-server-side-conn-mgt.md}}), whose stated purpose includes L4 balancers: "This option can force the client to periodically reconnect to a L4 LB which allows spreading load more quickly." Section 13 measures it.

Depth: message and stream limits, flow-control windows, health checking and reflection
  • Message size: 4 MiB received by default (measured in section 11); sending is unlimited by default in gRPC core.
  • Concurrent streams: a server can cap streams per connection with SETTINGS_MAX_CONCURRENT_STREAMS; calls beyond it queue on the client. The root's Failure lab reproduced it ("Max concurrent streams: calls queue on the connection": six 1-second calls finishing at 1, 2 and 3 s in pairs with a limit of 2). Fix with more connections (a channel pool) or more replicas.
  • Flow-control windows: the recorded SETTINGS show 4 MB windows, grown further by BDP probing; on long links one stream's throughput is window divided by round-trip time ({{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}}). gRPC sets TCP_NODELAY on its sockets, so small messages are not held back by Nagle's algorithm.

Health (grpc.health.v1.Health/Check, answering SERVING or NOT_SERVING, optionally per service) is what balancers and Kubernetes probe; Kubernetes has had native gRPC liveness probes since v1.27, stable ({{Kubernetes probes|https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/}}). The recorded check answered the two bytes 08 01: field 1 = 1, SERVING.
