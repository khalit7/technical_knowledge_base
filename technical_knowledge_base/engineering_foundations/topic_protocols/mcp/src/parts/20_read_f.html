7. Authorization: how a remote server knows who is calling

A stdio server inherits the user's environment, so it needs no protocol for credentials (stdio servers SHOULD NOT use this framework and should read credentials from the environment). A remote server must decide, on every request, whether this caller may do this. MCP does not invent a scheme: it profiles OAuth 2.1 (still an IETF draft, revision 16 of 3 September 2026; the MCP text cites revision 13). OAuth itself, authorization code, PKCE and JWTs are taught on {{Auth|n:3c65c17b0d0d817692dcc8ebd59b5c2b}}; its section 9, "Agent-era auth", covers audience binding and no token passthrough from the OAuth side; this section is how MCP uses them ({{authorization|https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization}}).

Roles. The MCP server is an OAuth resource server: it accepts tokens and serves requests. The MCP client is an OAuth client acting for a user. An authorization server (your company's identity provider, or one built into the service) talks to the user and issues tokens. The design goal: a client that has never heard of a server can still connect to it securely, with no manual setup.

The same flow as eight steps of text, with every parameter
    

  1. Try without a token. POST /mcp returned 401 with WWW-Authenticate: Bearer ..., resource_metadata=".../.well-known/oauth-protected-resource/mcp".
    2. 

  2. Read the server's metadata (RFC 9728 protected resource metadata): it names the resource (http://127.0.0.1:30752/mcp) and its authorization_servers. If the header is missing, clients try the well-known URLs themselves.
    3. 

  3. Read the authorization server's metadata (RFC 8414, or OpenID Connect discovery): endpoints, code_challenge_methods_supported: ["S256"], client_id_metadata_document_supported: true, authorization_response_iss_parameter_supported: true. The client must check that the document's issuer equals the address it fetched it from.
    4. 

  4. Identify the client without registering. With a Client ID Metadata Document, the client_id is an HTTPS URL that serves a JSON description of the client (name, redirect URIs); the authorization server fetches it and checks it describes itself. Here: https://localhost:30744/oauth/client.json. This replaces Dynamic Client Registration (RFC 7591), now deprecated and still available, under which every server's authorization server had to accept registrations from anyone.
    5. 

  5. Authorization request in the user's browser: response_type=code, a PKCE code_challenge (S256), state, scope=ckpt:read and resource=http://127.0.0.1:30752/mcp. That last parameter (RFC 8707) is the MCP-specific must: it says which server the token is for.
    6. 

  6. Redirect back with code, state and iss. The client compares iss with the issuer it recorded before redirecting (RFC 9207, required of clients since 2026-07-28).
    7. 

  7. Token request with the code and the PKCE verifier; the token comes back with aud set to the resource.
    8. 

  8. Retry POST /mcp with Authorization: Bearer ... on every request (never in the URL): 200, three checkpoints.
    9. 



The failures, recorded




Step-up. A 403 with error="insufficient_scope" tells the client to re-authorize with the union of its old scopes and the new ones, retry a few times at most, then give up. The specification wants the needed scope in the challenge (scope="ckpt:write"), every scope an operation needs in one challenge, not one per retry; the recorded SDK server named ckpt:write only in its human-readable error_description.

The rules that matter most




Token passthrough against a server's own upstream token: the audience decides where a token works






    

  • Audience binding. Servers MUST accept only tokens issued for them. A token for another API is useless here, as the 401 above shows, so a token stolen from one server cannot be replayed at another.
    • 

  • No token passthrough. A server that needs to call an upstream API (GitHub, your data warehouse) must get its own token for that API, never forward the one it received. Forwarding breaks audience binding, hides the real caller from the upstream's logs and rate limits, and turns the server into a proxy for stolen tokens ({{security best practices|https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices}}). Token exchange (RFC 8693) is the standard way to get a downstream token; see {{Auth|n:3c65c17b0d0d817692dcc8ebd59b5c2b}}.
    • 

  • Credentials belong to one issuer. Clients key stored client credentials and tokens by the authorization server's issuer and never reuse them with another; a CIMD client ID, being a URL, works with any authorization server.
    • 

  • Machines and enterprises. An agent with no user (a nightly job) uses the OAuth client credentials extension; organisations that want central control use Enterprise-Managed Authorization, where the identity provider decides which servers each employee's client may reach (section 6).
    • 



Two findings from the recording that clients should know


First, the server answered a request with no credentials with error="invalid_token", although RFC 6750 section 3.1 says a request that "lacks any authentication information" SHOULD get a challenge with no error code ({{RFC 6750|https://www.rfc-editor.org/rfc/rfc6750#section-3.1}}); harmless, but clients should not treat the error code as meaning "your token is bad". Second, the 401 challenge carried no scope, which the MCP text says servers SHOULD include so clients request the least privilege; without it a client falls back to everything in scopes_supported.
