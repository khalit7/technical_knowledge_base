1. Roles, and where MCP sits in an agent loop

The problem. A model only produces text; to list your checkpoints or open a pull request, the application around it must call real code. Before MCP every application wired every integration itself: N applications and M tools meant N × M adapters. MCP makes it N + M: write a server once, and every MCP host can use it. Anthropic released it on {{25 November 2024|https://www.anthropic.com/news/model-context-protocol}} and donated it on 9 December 2025 to the Agentic AI Foundation, a fund under the Linux Foundation co-founded with Block and OpenAI ({{Anthropic|https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation}}).

Three roles, drawn in the figure above. The host owns the conversation with the model, decides which servers to start and which tools the model may see, and asks the user for consent; the specification puts security policy here: "Enforces security policies and consent requirements" ({{architecture|https://modelcontextprotocol.io/specification/2026-07-28/architecture}}). A client inside the host speaks MCP to exactly one server, so a host with five servers runs five clients. A server (ckpt-tools, a GitHub server, a database server) sees only the requests sent to it.

The model does not speak MCP. Model APIs have their own tool-calling format (a list of tool definitions in the request, tool_use blocks in the answer), and the host translates, as numbered in the figure:

  1. The client asks each server for its tools (tools/list); the host copies each tool's name, description and inputSchema into the model request's tool list.
  2. The model answers with a tool call, for example list_checkpoints({"run": "llama-7b-sft"}).
  3. The host checks its policy (is this tool allowed? does the user need to confirm?), then its client sends tools/call to the right server.
  4. The server runs the function; the host puts the result's text into the next model request as a tool result, and the model continues.

So everything a server returns ends up in the model's context, and everything in a tool's description shapes what the model does. Both facts drive section 8.

What MCP costs, and when not to use it
It adds a process or a network hop, a JSON layer and a dependency on host support. If one application calls one internal API, ordinary function calling with the model API's own tool format is simpler. MCP pays off when several hosts (an IDE, a CLI agent, a chat app) must reach the same tools, when a team wants to publish tools once, or when tools must run with credentials or isolation the host should not hold.

2. The messages: JSON-RPC 2.0 with an MCP envelope

JSON-RPC 2.0 ({{specification|https://www.jsonrpc.org/specification}}) gives MCP three message kinds ({{MCP basic protocol|https://modelcontextprotocol.io/specification/2026-07-28/basic}}): a request (id, method, params; MCP forbids a null id and reusing an id that is still waiting for its answer), a response with the same id and either a result or an error (code, message, optional data), which is how a client matches answers when several are in flight on one pipe, and a notification with no id and no answer (progress, change notices, cancellation on stdio). Since 2026-07-28 only the client sends requests: when a server needs something from the client, it says so inside its result and the client asks again (section 5).

The four MCP additions to plain JSON-RPC, all visible above:


    

  • _meta on every request. io.modelcontextprotocol/protocolVersion and io.modelcontextprotocol/clientCapabilities are required; clientInfo is recommended. A request missing a required field is rejected with -32602 (on HTTP, status 400).

  • resultType on every result: "complete", or "input_required" when the server needs more input. A client must treat a missing resultType (an older server) as complete.
    • 

  • serverInfo in the result's _meta, so a client can tell who answered without remembering a handshake. Both clientInfo and serverInfo are self-reported: the specification says not to base security decisions on them.

  • Trace context: traceparent, tracestate and baggage may ride in _meta (W3C formats), so one trace can follow a request from the model call through the host into the server.

Reserved names and the error codes that changed in 2026-07-28


Names under the io.modelcontextprotocol/ prefix (and any prefix whose second label is modelcontextprotocol or mcp) are reserved for the protocol. The old "resource not found" code -32002 became -32602, and -32042 (URL elicitation required, 2025-11-25 only) is retired; clients should still accept -32002 from older servers. Codes -32000 to -32019 are legacy, implementation-defined ({{error codes|https://modelcontextprotocol.io/specification/2026-07-28/basic#error-codes}}).
