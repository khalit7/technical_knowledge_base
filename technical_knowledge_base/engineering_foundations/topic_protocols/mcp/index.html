The idea in one screen

MCP is a small JSON-RPC contract between an AI application (the host) and the programs that give it tools and data (servers): the model never speaks it, the host translates and decides, and since revision 2026-07-28 every request carries everything about itself, so a remote server is an ordinary stateless web service protected as an OAuth resource server.

Fig. 1 · The model sees tool definitions; the host runs one client per server and holds the policy

  1. Three roles. The host owns the conversation with the model, decides which servers to start and which tools the model may see, and asks the user for consent. A client inside it speaks MCP to exactly one server. A server sees only the requests sent to it, never the conversation and never other servers. The model API at the back has its own tool format and never speaks MCP.
  2. tools/list. The client asks each server for its tools (tools/list); the host copies each tool's name, description and inputSchema into the model request's tool list. ckpt-tools' answer for its three tools is 1,818 bytes.
  3. The model asks. The model answers with a tool call in the model API's own format, for example list_checkpoints({"run": "llama-7b-sft"}).
  4. Policy, then tools/call. The host checks its policy (is this tool allowed? does the user need to confirm?), then its client sends tools/call to the right server; only that server sees it.
  5. The result becomes model input. The server runs the function; the host puts the result's text into the next model request as a tool result, and the model continues.
  6. Two kinds of credentials. The local server is a child process on stdio: it runs with the user's rights and reads credentials from the environment. The remote server is an OAuth resource server: it accepts only a token issued for it (aud = this server) by its authorization server (section 7).

The running example, ckpt-tools, is a server an ML team might run so an agent can list, evaluate and delete training checkpoints (its checkpoint table is illustrative; nothing is deleted). The size of its tool list is measured (stdio recording, 5 October 2026); the rest is the structure the specification defines. Steps 2 to 5 are one tool call (section 1).

You need HTTP requests, status codes and proxies (HTTP), server-sent events (Streaming and real-time) and OAuth 2.1 with PKCE (Auth), only for sections 4 and 7. 1. Roles, and where MCP sits in an agent loop

The problem. A model only produces text; to list your checkpoints or open a pull request, the application around it must call real code. Before MCP every application wired every integration itself: N applications and M tools meant N × M adapters. MCP makes it N + M: write a server once, and every MCP host can use it. Anthropic released it on 25 November 2024 and donated it on 9 December 2025 to the Agentic AI Foundation, a fund under the Linux Foundation co-founded with Block and OpenAI (Anthropic), which by October 2026 also held A2A, AGENTS.md and Agent Skills among ten projects (the foundation's map: Agent-to-agent and beyond).

Three roles, as in Fig. 1. The specification puts security policy in the host: "Enforces security policies and consent requirements" (architecture). A host with five servers runs five clients; a server (ckpt-tools, a GitHub server, a database server) never sees the others.

The model does not speak MCP. Model APIs have their own tool-calling format (a list of tool definitions in the request, tool_use blocks in the answer), and the host translates both ways: Fig. 1, steps 2 to 5, is one tool call.

So everything a server returns ends up in the model's context, and everything in a tool's description shapes what the model does. Both facts drive section 8.

What MCP costs, and when not to use it
It adds a process or a network hop, a JSON layer and a dependency on host support. If one application calls one internal API, ordinary function calling with the model API's own tool format is simpler. MCP pays off when several hosts (an IDE, a CLI agent, a chat app) must reach the same tools, when a team wants to publish tools once, or when tools must run with credentials or isolation the host should not hold.

2. The messages: JSON-RPC 2.0 with an MCP envelope

JSON-RPC 2.0 (specification) gives MCP three message kinds (MCP basic protocol): a request (id, method, params; MCP forbids a null id and reusing an id that is still waiting for its answer), a response with the same id and either a result or an error (code, message, optional data), which is how a client matches answers when several are in flight on one pipe, and a notification with no id and no answer (progress, change notices, cancellation on stdio). Since 2026-07-28 only the client sends requests: when a server needs something from the client, it says so inside its result and the client asks again (section 5).

Fig. 2 · One stdio conversation with ckpt-tools, message by message

  1. initialize. The legacy client (SDK 1.30.0) opens with initialize (id 1, 153 bytes): protocolVersion 2025-11-25, its capabilities (none) and clientInfo.
  2. The server's half of the negotiation. The result (id 1, 338 bytes) names the version, the server's capabilities (prompts, resources, tools) and its instructions. From here both sides hold that agreement in memory for as long as the connection lives.
  3. A notification. notifications/initialized (55 bytes) has no id and gets no answer; only then may work start.
  4. tools/call, id 2. 119 bytes and no _meta: the version was said once, at the start. The result (706 bytes) comes back with the same id.
  5. tools/list, id 3. 47 bytes; the answer is 1,671 bytes, without the cacheScope and resultType fields of the 2026-07-28 answer. Seven messages in all, three of them only to set the conversation up.
  1. Probe: server/discover. The dual-era client asks first (id 1, 246 bytes); the answer (429 bytes) lists supportedVersions ["2026-07-28"], capabilities and identity, marked cacheScope: "private", so the client may cache it. Optional for clients; servers MUST implement it.
  2. A self-contained request. tools/call, id 2, 302 bytes: the tool name, its arguments and _meta with the protocol version, clientInfo and clientCapabilities. The tinted 183 bytes are what this request carries that the legacy call does not.
  3. The response carries the same id. A result with id 2 (817 bytes), with resultType: "complete" and serverInfo in its _meta. The id is how a client matches answers when several requests are in flight on one pipe.
  4. Every request stands alone. tools/list (id 3, 241 bytes) repeats the _meta; its answer (1,819 bytes with the newline) carries cacheScope: "public". Nothing either side does depends on an earlier message.

measured stdio lines of the cold runs (first call of each client; sizes include the newline). The warm calls of the next figure have longer ids, so their requests are 2 bytes longer.

The four MCP additions to plain JSON-RPC, all visible in the recorded lines beside:

  • _meta on every request. io.modelcontextprotocol/protocolVersion and io.modelcontextprotocol/clientCapabilities are required; clientInfo is recommended. A request missing a required field is rejected with -32602 (on HTTP, status 400).
  • resultType on every result: "complete", or "input_required" when the server needs more input. A client must treat a missing resultType (an older server) as complete.
  • serverInfo in the result's _meta, so a client can tell who answered without remembering a handshake. Both clientInfo and serverInfo are self-reported: the specification says not to base security decisions on them.
  • Trace context: traceparent, tracestate and baggage may ride in _meta (W3C formats), so one trace can follow a request from the model call through the host into the server.

3. What a server offers, and what the client offers back


The three server primitives differ by who decides to use them, which is the single most useful way to remember them (server features):




PrimitiveControlled byMethodsckpt-tools example

ResourcesThe application: it decides what to read into context (a file picker, an attachment)resources/list, resources/templates/list, resources/readckpt://{run}/config, the run's YAML config


PromptsThe user: picked explicitly, often as a slash commandprompts/list, prompts/getpick_best(run)






The definition. A tool has a name, an optional display title, a description written for the model, an inputSchema (JSON Schema, 2020-12 by default) and optionally an outputSchema and annotations. In the Python SDK the type hints are the schema: def list_checkpoints(run: str) -> list[Checkpoint] produced this input schema and a matching output schema with the four Checkpoint fields:


{"type":"object","properties":{"run":{"title":"Run","type":"string"}},"required":["run"],"title":"list_checkpointsArguments"}


Two copies of every structured result. With an output schema, the result carries structuredContent (JSON a program can use) and, for backward compatibility, the same data as text in content, which is what most hosts show the model. For three checkpoints the SDK sent three pretty-printed text blocks plus the structured copy: 818 bytes of result body for about 200 bytes of facts (measured). Every byte of content becomes model input tokens, so return short, task-shaped results and paginate.


Annotations are claims, not guarantees. readOnlyHint, destructiveHint, idempotentHint and openWorldHint (talks to the outside world) tell a host how careful to be: ckpt-tools marks delete_checkpoint destructive and idempotent. The specification is blunt: "clients MUST consider tool annotations to be untrusted unless they come from trusted servers". A malicious server can mark a destructive tool read-only.


Names collide across servers. Tool names are only unique within one server (SHOULD be 1 to 128 characters of letters, digits, _ - .). Two servers that both offer search must be told apart by the host, for example by prefixing a server identifier; serverInfo.name is not unique and should not be used for this. And servers SHOULD return tools/list in a deterministic order, because hosts paste the list into the model request, and a reordered list breaks the model provider's prompt cache.






A tool is text the model reads and a result that becomes model input




ckpt-tools' delete_checkpoint and list_checkpoints, from src/lab/ckpt_server.py; result sizes measured. Field names are the specification's (tools).






State without sessions. A shopping cart, an open browser or a database transaction spans several calls. With no session, the server returns an explicit handle (basket_id: "bsk_a1b2c3") and takes it back as an ordinary argument; the model carries it forward. A handle is a name, not a password: check on every call that it belongs to the caller, make it random, state its lifetime in the tool description, and return a clear tool error when it has expired so the model can start again (stateful tools).

Streamable HTTP: one POST per message


The server exposes one URL, the MCP endpoint (for example https://mcp.example.com/mcp). Every client message is its own HTTP POST with Accept: application/json, text/event-stream. The server answers each request either with one JSON object or with a server-sent events (SSE) stream scoped to that request, carrying progress notifications and then the final response (Streamable HTTP).



Headers that mirror the body. Every POST carries MCP-Protocol-Version, Mcp-Method and, for tools/call, resources/read and prompts/get, Mcp-Name, so an ordinary load balancer, gateway or firewall can route, rate-limit or block by tool without parsing JSON. A tool may also ask for an argument to be copied into a header with x-mcp-header (for example a region, so a gateway can route to the right cluster); sensitive values must not be marked this way, since intermediaries see headers. Because two components could disagree about which copy is true (a gateway allows by header, the server executes by body), servers MUST reject a mismatch with 400 and -32020 HeaderMismatch.

Three rows deserve a word. The Origin check stops a web page you happen to visit from calling a server on your laptop: browsers attach Origin to cross-site requests, and the specification requires a 403 for an invalid one. The Host check (421 Misdirected Request) stops DNS rebinding, where an attacker's domain is made to resolve to 127.0.0.1 after the page loads (DNS explains the trick); local servers should also bind to 127.0.0.1, not 0.0.0.0. And a header that names an older protocol version was not treated as a header mismatch: this dual-era server took it as a legacy request and asked for a session ID, so intermediaries that route on headers should reject versions older than 2026-07-28, as the specification advises, rather than trust unvalidated headers.


Behind a proxy. Servers SHOULD send X-Accel-Buffering: no on event streams so nginx-style proxies pass events immediately. Long-lived streams (subscriptions/listen) should send a comment line : now and then so idle timeouts do not cut them. Streams are not resumable any more: Last-Event-ID was removed, and a broken stream loses its request, which the client re-sends with a new id.

On one machine every transport answers in one to three milliseconds, far below a model call's hundreds of milliseconds, so transport choice is about deployment, not speed. stdio's cost is the process start (and a process per user per server); HTTP's is the network, TLS and authorization you must add to leave the laptop. The legacy session mode pays an extra round trip at the start (initialize, then the initialized notice, then the GET stream) and SSE framing on every reply.

5. The stateless revision (2026-07-28)




Before. From 2024-11-05 to 2025-11-25 a connection began with a handshake: the client sent initialize with its version and capabilities, the server answered with its own, the client sent notifications/initialized, and only then could work start. Over HTTP the server minted an Mcp-Session-Id that the client sent on every later request, opened a GET stream for messages the server wanted to push, and ended the session with DELETE. A server could also send its own requests to the client (a confirmation, a model completion) on an open stream, and wait.


The problem. A session is memory inside one server process. Behind an ordinary round-robin load balancer the second request of a session lands on a replica that never saw the first, so you need sticky routing (the balancer pins each session to a replica) or a shared session store, and a server that pauses mid-call waiting for the client holds that memory open even longer.


After. The 2026-07-28 revision (changelog) removed the handshake, the session, the GET stream, ping, logging/setLevel and server-initiated requests. Every request says everything about itself in _meta. A client that wants to know a server up front may call server/discover (servers MUST implement it), which returns supported versions, capabilities and identity, and is cacheable.


Multi round-trip requests: asking the user without holding a session


The replacement for server-initiated requests is MRTR (multi round-trip requests). The server answers the original request with resultType: "input_required", a map of inputRequests (an elicitation, a sampling request, a roots request) and an opaque requestState. The client gathers the answers and sends the same request again, with a new id, plus inputResponses and the echoed requestState. Any replica can finish it, because everything it needs is in the retry. Only tools/call, resources/read and prompts/get may do this.

No, for a different reason: 0 of 20. The first round went to replica B, which sealed requestState with a key generated when that process started; the retry went to A, which could not open it: -32602 Invalid or expired requestState. The SDK's documentation says it plainly: "Multi-instance deployments must share a key via keys=[...]". With one key shared by both replicas (RequestStateSecurity(keys=[...]), here from an environment variable), 20 of 20. Stateless protocol does not mean stateless deployment: something must still be shared, but it is a key in your secret store rather than live session memory in one process.


requestState is attacker-controlled. It travels through the client, so the specification requires the server to protect its integrity (an HMAC or authenticated encryption) whenever it affects authorization or business logic, and recommends binding it to the authenticated user, a short expiry and the original request. The Python SDK does this for you: it seals every requestState with AES-GCM (the 25-character plaintext delete:llama-7b-step-2000 went out as a 281-character string starting v1., carrying the sealed payload plus the expiry, request binding and audience the SDK adds), and a forged value came back as -32602 Invalid or expired requestState (measured).


What statelessness costs
183 more bytes on every request (section 2); a retry round trip where the old protocol kept a stream open; state handles the model must carry (section 3); and a sealing key to distribute and rotate (the SDK takes a ring of keys: the first seals, all of them open). What it buys: any replica answers any request, gateways can route on headers, list results can be cached, and a crashed server loses only in-flight requests.

"MCP is dead"? A claim not confirmed, and the argument behind it


The old page said "MCP was declared dead" became a recurring headline in August 2026, citing InfoQ; the article could not be retrieved and the root page dropped it. The argument behind it is worth knowing anyway: with no handshake and no session, MCP over HTTP is close to a plain JSON API with conventions for discovery, tool schemas, consent and authorization. Whether those conventions justify a protocol is a fair interview question; the answer is that the value is in the shared conventions (any host, any server), not in the transport.

Eras, and the compatibility matrix run for real


The specification calls versions with a handshake legacy and versions with per-request metadata modern; a dual-era implementation speaks both. A dual-era client probes: on stdio it sends server/discover first and falls back to initialize on any error that is not a recognised modern error; on HTTP it tries a modern request and inspects a 400's body before falling back (versioning). Deprecation and extensions


    

  • Lifecycle. A feature goes Active, then Deprecated (still works; new code should not adopt it), then Removed, with at least twelve months between the release that deprecates it and its removal; the window can be shortened for an active security risk (feature lifecycle).
    • 

  • Extensions are optional additions negotiated in the extensions field of capabilities, named like _meta keys: io.modelcontextprotocol/... for official ones, your reversed domain (com.example/...) for your own. If one side lacks an extension, the other must fall back to core behaviour or refuse (extensions). Official ones: Tasks (io.modelcontextprotocol/tasks: a durable handle for long work, polled with tasks/get, input via tasks/update); MCP Apps (io.modelcontextprotocol/ui: a server returns interactive HTML that renders inside the conversation); OAuth client credentials for machine-to-machine access and Enterprise-Managed Authorization, where an organisation's identity provider grants access to servers centrally; and Skills over MCP.
    • 



Governance
Changes go through Specification Enhancement Proposals (SEPs, numbered by pull request) with working and interest groups; the project sits in the Agentic AI Foundation under the Linux Foundation (section 1).







7. Authorization: how a remote server knows who is calling


A stdio server inherits the user's environment, so it needs no protocol for credentials (stdio servers SHOULD NOT use this framework and should read credentials from the environment). A remote server must decide, on every request, whether this caller may do this. MCP does not invent a scheme: it profiles OAuth 2.1 (still an IETF draft, revision 16 of 3 September 2026; the MCP text cites revision 13). OAuth itself, authorization code, PKCE and JWTs are taught on Auth; its section 9, "Agent-era auth", covers audience binding and no token passthrough from the OAuth side; this section is how MCP uses them (authorization).




Roles. The MCP server is an OAuth resource server: it accepts tokens and serves requests. The MCP client is an OAuth client acting for a user. An authorization server (your company's identity provider, or one built into the service) talks to the user and issues tokens. The design goal: a client that has never heard of a server can still connect to it securely, with no manual setup.

The rules that matter most


    

  • Audience binding. Servers MUST accept only tokens issued for them. A token for another API is useless here, as the 401 above shows, so a token stolen from one server cannot be replayed at another.
    • 

  • No token passthrough. A server that needs to call an upstream API (GitHub, your data warehouse) must get its own token for that API, never forward the one it received. Forwarding breaks audience binding, hides the real caller from the upstream's logs and rate limits, and turns the server into a proxy for stolen tokens (security best practices). Token exchange (RFC 8693) is the standard way to get a downstream token; see Auth.
    • 

  • Credentials belong to one issuer. Clients key stored client credentials and tokens by the authorization server's issuer and never reuse them with another; a CIMD client ID, being a URL, works with any authorization server.
    • 

  • Machines and enterprises. An agent with no user (a nightly job) uses the OAuth client credentials extension; organisations that want central control use Enterprise-Managed Authorization, where the identity provider decides which servers each employee's client may reach (section 6).
    • 







Token passthrough against a server's own upstream token: the audience decides where a token works








Two findings from the recording that clients should know


First, the server answered a request with no credentials with error="invalid_token", although RFC 6750 section 3.1 says a request that "lacks any authentication information" SHOULD get a challenge with no error code (RFC 6750); harmless, but clients should not treat the error code as meaning "your token is bad". Second, the 401 challenge carried no scope, which the MCP text says servers SHOULD include so clients request the least privilege; without it a client falls back to everything in scopes_supported.









8. Security: the protocol-level threats and their specified mitigations




MCP connects a system that follows instructions written in text (the model) to systems that act (tools). Most of its security problems follow from the two facts of section 1: whatever a tool returns becomes part of the model's context, and whatever a server says about its tools shapes what the model does. The protocol can carry the right signals (consent, audiences, annotations), but the decisions are the host's. The clearest way to organise the risks is by who the attacker is; the figure places each one on the architecture.






Five places trust can break, each with the control that holds it




A map of positions, not an attack walkthrough. Agent-side defences in general (permission gates, sandboxes, egress control, human approval) are owned by Agent security; this page owns what the protocol specifies.

The confused deputy, as specified (security best practices, read 24 October 2026). The deputy is an MCP proxy server: it fronts a third-party API and is a single OAuth client there, with one static client ID. The problem needs four conditions at once: that static client ID; the proxy letting MCP clients register dynamically, each with its own client_id and redirect URI; the third-party authorization server setting a consent cookie after the first approval; and no per-client consent in the proxy. Then a user's earlier consent to the proxy is silently reused for a newly registered client, and the MCP authorization code goes to that client's redirect URI. The fix is a MUST in the deputy: keep a registry of approved client_id values per user and check it before forwarding to the third party, with a consent page that names the client and shows its redirect URI; match redirect URIs exactly; generate single-use state and set it only after consent (security best practices). The same page notes that an authorization server accepting Client ID Metadata Documents fetches a URL chosen by an unknown client, so it needs the same SSRF protections as clients.


That page treats the protocol-level items in depth: confused deputy, token passthrough, SSRF, state handle hijacking (the 2026-07-28 replacement for the old "session hijacking"), local server compromise, OAuth URL validation, stdio in proxy setups, mix-up attacks, localhost redirect impersonation, CIMD trust and scope minimisation.


A defensive checklist for a host (the general controls are owned by Agent security)
    

  • Show which servers and tools are active, and show tool inputs before sensitive calls; the specification asks for a human able to deny any tool call.
    • 

  • Expose per task only the tools the task needs; do not combine tools that read private data with tools that read untrusted content and tools that send data out, unless a human approves each outbound action.
    • 

  • Give each server its own credentials with the least scope, from the environment or OAuth, never the user's master tokens; prefer short-lived tokens.
    • 

  • Run local servers with restricted file system and network access; show the exact command before adding a server from a one-click link.
    • 

  • Pin and diff tool definitions; prefix tool names by server to avoid collisions.
    • 

  • Log every tool call with its arguments and result size, so an incident can be reconstructed; set time limits on tool calls.
    • 

  • Treat irreversible actions (deleting, paying, sending, moving hardware) as a different class: confirmation outside the conversation, so text in the context cannot approve them. The root page's note on agents driving instruments makes the same point.
    •

The docstring becomes the description, the type hints become both schemas, a Pydantic model becomes a structured result, a parameter typed Context gives access to progress, input responses and the protocol version. The same server object answers 2025-11-25 and 2026-07-28 clients.


Design tools for a model, not as an API mirror


    

  • Few, task-shaped tools. A model choosing among 40 thin REST wrappers picks worse and pays for 40 definitions in every request (ckpt-tools' list of three tools was 1,818 bytes of JSON). Prefer "list checkpoints of a run with their eval loss" over "GET /runs/{id}/artifacts?type=ckpt".
    • 

  • Write descriptions as documentation for a capable newcomer: what it does, when to use it, units, limits, what an error means. This text is the model's only manual.
    • 

  • Return little. Summaries, identifiers and a cursor beat full dumps; every byte of content is input tokens (section 3).
    • 

  • Errors the model can act on: "checkpoint llama-7b-step-9000 not found; existing: ..." as isError: true, not a stack trace.
    • 

  • Mark side effects honestly (annotations), make destructive tools idempotent where possible (deleting twice is a no-op), and ask for confirmation through elicitation for irreversible ones, as delete_checkpoint does.
    • 

  • No state in the process for an HTTP server: handles in arguments, a shared requestState key, external stores; then any replica can serve any request (section 5).
    • 

  • stdout is sacred on stdio: log to stderr; check that libraries you import do not print.
    • 



Testing: in process, over the real transport, on the wire, by hand, with a model
    

  • In process, no transport. The SDK's Client accepts the server object itself: async with Client(mcp) as c: r = await c.call_tool("list_checkpoints", {"run": "llama-7b-sft"}). Fast unit tests of every tool, both eras (mode="legacy" forces the handshake).
    • 

  • Over the real transport: the same calls through stdio and through HTTP, to catch stdout pollution, serialisation and header problems.
    • 

  • Contract tests on the wire: send the hostile requests of section 4 (wrong headers, bad versions, foreign Origin) and assert the status codes; keep them in CI so an SDK upgrade cannot silently change them.
    • 

  • Interactive: MCP Inspector (uv run mcp dev server.py) lists and calls tools by hand. Use 0.14.1 or later (CVE-2025-49596, section 8), and do not leave it running.
    • 

  • With a model: record real agent transcripts and score whether the model picks the right tool with the right arguments, before and after you change a description. A description change is a behaviour change.
    • 



Deploying across an organisation: packages, stateless replicas, central configuration, the registry, traces
    

  • Local servers are distributed like packages (PyPI, npm, container images) and configured per host. Pin versions; review the launch command.
    • 

  • Remote servers are ordinary web services: behind TLS and a load balancer, several stateless replicas sharing the requestState key, OAuth with your identity provider, rate limits per client, logs with the caller's identity. Header mirroring lets a gateway enforce per-tool policy and route by Mcp-Name without reading bodies.
    • 

  • Central configuration. Hosts let administrators decide which servers people may use: one host's scopes, precedence, managed servers and allow and deny lists are on Claude Code, section 10. On the authorization side, the Enterprise-Managed Authorization extension lets the identity provider grant access centrally.
    • 

  • Finding servers. The official registry (registry.modelcontextprotocol.io) launched in preview on 8 September 2025: an open catalogue and API with namespaced server names. A listing is metadata, not a security review.
    • 

  • Observability. Put traceparent in _meta so traces join across host and server; the Python SDK wraps handling in OpenTelemetry spans.
    • 

  • Dated, 18 October 2026: gateways are tightening the same way: LiteLLM 1.106.0 disables stdio MCP servers by default, so a gateway that launches local processes needs them switched back on deliberately (LiteLLM releases).

Interview rehearsal (eight questions, with model answers)


Does the model call MCP servers?
No. The host lists the servers' tools, translates them into the model API's tool definitions, receives the model's tool calls, applies its own policy, and sends tools/call through the client for that server. MCP is between host and server; the model sees only tool definitions and tool results. That is also why the host, not the protocol, is where consent and scoping live.


Tools, resources and prompts: what is the difference?
Who decides to use them. Tools are model-controlled (the model calls them), resources are application-controlled (the app attaches data to context), prompts are user-controlled (the user picks a template). They differ in risk too: a tool can act, a resource only informs.


Why did MCP remove sessions in 2026-07-28, and what did it cost?
Sessions lived in one server process, so every request of a session had to reach that process: sticky load balancing or a shared session store, and servers holding streams open while waiting for clients. Now every request carries version and capabilities in _meta, server-to-client questions become input-required results that the client answers by retrying (MRTR), and any replica can serve any request. Costs: about 180 bytes of metadata per request, an extra round trip for confirmations, state handles the model must carry, and a key that all replicas must share to seal requestState. In a two-replica test, old sessions failed 20 of 20 calls through round robin; new requests failed 20 of 20 until the replicas shared the key, then succeeded 20 of 20.


A tool fails because of bad input. Error response or result?
A result with isError: true and an explanation, so the model can retry with corrected arguments (clarified in 2025-11-25). JSON-RPC errors are for problems the model cannot fix: malformed requests, unknown methods, protocol versions, header mismatches.


How does a client that has never seen a server get a token for it?
The server's 401 points to its protected resource metadata (RFC 9728), which names its authorization server; the client reads that server's metadata (RFC 8414 or OIDC discovery), identifies itself with a Client ID Metadata Document URL (or falls back to dynamic registration), runs authorization code with PKCE including resource= the server's URL (RFC 8707), checks the iss in the response (RFC 9207), and sends the bearer token on every request. The server accepts only tokens whose audience is itself, and never forwards them upstream.


What is token passthrough and why is it banned?
A server accepting a token that was not issued for it and forwarding it to an upstream API. It breaks audience binding (a token for one service works at another), hides the real caller from the upstream's controls and logs, and makes the server a proxy for stolen tokens. The fix is for the server to hold or exchange for its own upstream credentials.


Your agent reads web pages and can send email. What do you worry about, and what do you do?
Indirect prompt injection: page text reaching the model as if it were instructions. With private data in reach, that is the lethal trifecta. Break a leg per task: do not give a browsing task access to private data, or require a human to approve every outbound message with its full content, or restrict destinations. Detection helps but is not a control; design for the injection getting through.


stdio or Streamable HTTP for a new server?
stdio when it acts on the user's own machine and accounts with the user's rights: no network surface, credentials from the environment, one process per user. Streamable HTTP when it is shared, holds data or credentials that should not be on laptops, or must scale: then it is a web service with TLS, OAuth, stateless replicas and a shared state key. Speed is not the deciding factor: both answered in one to three milliseconds on loopback.
