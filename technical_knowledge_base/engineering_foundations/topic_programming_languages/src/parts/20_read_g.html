9. Concurrency

A thread shares its program's memory and, on several cores (this laptop has 10), really runs at the same instant as the others. counter += 1 is three steps (read, add one, write back); two threads interleaving them lose an update. Two threads touching the same memory, at least one writing, with nothing ordering them, is a data race. The four languages took four positions on it, and on a second question: how to wait for many slow things at once without a thread for each, which is asynchronous code.

Python's threads are real, but the default build has a GIL: one thread runs Python bytecode at a time; the free-threaded build (3.14t) has none and is officially supported since 3.14 ({{PEP 779|https://peps.python.org/pep-0779/}}). C++ threads are free and unchecked. Rust's compiler refuses data races through the Send and Sync rules. JavaScript runs your code on one thread around an event loop; worker threads share memory only through a SharedArrayBuffer.

Predict which of six runs gets 4,000,000, then step: the animation runs the same experiment everywhere: four threads each add 1 to a shared counter a million times, so the right answer is 4,000,000. The step-by-step interleaving is illustrative (it shows how an update is lost); every final number is measured on this laptop, three runs each, from read/code/concurrency/.

Read the results together. Python's GIL made this counter come out right in every run, but the Python FAQ is explicit that i = i + 1 is not one of the operations it guarantees to be atomic ({{Python FAQ|https://docs.python.org/3/faq/library.html#what-kinds-of-global-value-mutation-are-thread-safe}}); remove the GIL (3.14t) and about 70% of the updates vanish. JavaScript cannot have the bug with ordinary code, because only one piece of your code runs at a time and it is only interrupted at an await; it gets it back as soon as workers share memory. C++ loses updates at -O0 and gets the right answer at -O2 only because the optimiser, allowed to assume no data race, turned a million increments into a single addition: the bug is still there, just hidden. Rust does not let the racy program exist.

Waiting for many slow things: async side by side

The second question has three answers built on the same idea (a task gives its thread back at each await) and different rules about threads, cancellation and blocking. C++ has no standard async runtime: threads, a library such as Asio, or C++20 coroutines as a low-level building block. Only Rust's tokio, by default, spreads tasks over several threads.

Python's GIL costs parallelism: the {{Benchmark|#t-bench}} tab runs the token counter on 4 threads, and with the GIL it is no faster than on 1; the free-threaded build costs some single-thread speed (the Python 3.14 docs give two figures: about 1% on macOS aarch64 to 8% on x86-64 Linux in the {{free-threading HOWTO|https://docs.python.org/3.14/howto/free-threading-python.html}}, "roughly 5-10%" in {{What's New in 3.14|https://docs.python.org/3.14/whatsnew/3.14.html}}; on this M1 Pro the {{Benchmark|#t-bench}} measured no penalty within run-to-run spread) and needs extensions built for it. C++ costs vigilance and ThreadSanitizer runs. Rust costs wrapping shared state in Arc<Mutex<T>> or atomics, which the compiler demands. JavaScript costs real parallelism: CPU-heavy work blocks the one thread unless moved to a worker.

  • "Threads in Python cannot run in parallel, so other languages' threads are the same." In C++, Rust and free-threaded Python they really run at once, and your racy Python habits become real bugs.
  • "async makes code run in parallel." In Python and JavaScript it interleaves waiting on one thread; tokio is the exception (above).
  • "JavaScript is single-threaded, so it has no concurrency bugs." Two async functions can still interleave at every await, so a read before an await and a write after it can conflict.
