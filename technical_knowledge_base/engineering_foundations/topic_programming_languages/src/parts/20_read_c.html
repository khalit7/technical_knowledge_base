2. How code runs

A processor only executes machine code. Each language is a different route from your text to it, and the route decides when the translation happens and how much it knows then. Translation time is also checking time: what is checked while translating is caught on every path, including the ones your tests never run (the hero above).

  • Ahead-of-time compilation (C++, Rust): a compiler translates the whole program before it runs. Both clang and rustc hand their work to LLVM, the same optimiser and code generator.
  • Bytecode plus an interpreter (CPython): Python compiles your file into bytecode, then a loop written in C, the interpreter, executes one instruction at a time. Since 3.11 it rewrites hot instructions into type-specialised forms while the program runs ({{PEP 659|https://peps.python.org/pep-0659/}}).
  • Interpret first, compile the hot parts (JavaScript in V8): V8 runs bytecode in its Ignition interpreter, watches which types flow through each function, and compiles hot functions with its optimising compilers (Sparkplug, Maglev and TurboFan; {{V8 blog|https://v8.dev/blog/maglev}}). This is a JIT, a just-in-time compiler; when a guess fails (a new type arrives) it throws the machine code away, a deoptimisation.
  • Erase, then run as JavaScript (TypeScript): tsc checks the types and writes JavaScript with every annotation removed; Node 22.18 and later can also run a .ts file directly by blanking the annotations out ({{Node docs|https://nodejs.org/api/typescript.html}}). Types never exist at run time.

Predict how many instructions each route spends on one character, then step one line of the token loop, if tok and not inside: n += 1, through each. All real output: Python's dis, clang's and rustc's assembly (AArch64: cmp, b.ne, ldrb), V8's bytecode and node --print-opt-code, and tsc's output.

What the counts mean. For each character CPython executes 29 bytecode instructions, each of them dozens of machine instructions inside the interpreter (fetch, jump to the handler, check types, update reference counts). The compilers turned the same loop into 16 (clang) or 17 (rustc) machine instructions per byte, then rewrote it to process 8 (clang) or 32 (rustc) bytes at once with SIMD instructions. V8 got close to the compilers' simple version after watching the function run. That is most of the speed gap of section 12, before any library or algorithm is involved.

Ahead-of-time compilation costs build time (the {{Benchmark|#t-bench}} tab measures it: seconds for the Rust program against nothing for Python) and a separate binary for every processor and operating system you ship to. Interpretation costs speed. A JIT costs memory and warm-up time: the first calls are slow, and V8 compiled our function only after it was "hot and stable". TypeScript's erasure costs nothing at run time and checks nothing at run time.

  • "Python is interpreted line by line." It is compiled to bytecode first (you have seen the .pyc files in __pycache__); only the bytecode is interpreted.
  • "TypeScript is compiled, so it is fast like C++." Its compilation removes types; the speed is V8's, the same as JavaScript.
  • "Python 3.14 has a JIT, so loops are fast now." The JIT ships in the official macOS and Windows installers but is experimental and off unless you set PYTHON_JIT=1 ({{What's new in 3.14|https://docs.python.org/3.14/whatsnew/3.14.html}}); the 3.14 run above shows JUMP_BACKWARD_NO_JIT.
  • "An optimised build is the same program, faster." In C++ optimisation can change what a buggy program does (section 9 shows a data race that disappears at -O2); in Rust, integer overflow panics in a debug build and wraps in a release build (section 7).
