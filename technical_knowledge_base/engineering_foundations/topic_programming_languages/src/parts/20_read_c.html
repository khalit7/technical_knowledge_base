2. How code runs

A processor only executes machine code: simple instructions such as "load this byte", "compare with 97", "add 1", "jump back". Every language is a different route from your text to those instructions, and the route decides two things: when the translation happens and how much it knows when it happens.

  • Ahead-of-time compilation (C++, Rust): a compiler translates the whole program into machine code before it runs, and ships a file the processor executes directly. Both clang (C++) and rustc (Rust) hand their work to LLVM, the same optimiser and code generator.
  • Bytecode plus an interpreter (CPython): Python first compiles your file into bytecode, instructions for an imaginary stack machine, then a loop written in C (the interpreter) reads one bytecode instruction at a time and does what it says. Since 3.11 the interpreter rewrites hot instructions into faster, type-specialised forms while the program runs ({{PEP 659|https://peps.python.org/pep-0659/}}).
  • Interpret first, compile the hot parts (JavaScript in V8): V8 compiles JavaScript to bytecode for its Ignition interpreter, watches which types actually flow through each function, and compiles hot functions to machine code with its optimising compilers (Sparkplug, Maglev and TurboFan; {{V8 blog|https://v8.dev/blog/maglev}}). This is a JIT, a just-in-time compiler. If a guess turns out wrong (a new type arrives), V8 throws the machine code away and goes back to the interpreter: a deoptimisation.
  • Erase, then run as JavaScript (TypeScript): tsc checks the types and writes JavaScript with every type annotation removed; Node 22.18 and later can also run a .ts file directly by blanking the annotations out ({{Node docs|https://nodejs.org/api/typescript.html}}). Either way, what runs is plain JavaScript in V8. Types never exist at run time.

What the instruction counts mean. For each character, CPython executes 29 bytecode instructions, and each bytecode instruction is itself dozens of machine instructions inside the interpreter (fetch the instruction, jump to its handler, check types, update reference counts). The compilers turned the same loop into 16 (clang) or 17 (rustc) machine instructions per byte in its simplest form, and then went further: they noticed that each step only depends on the current and the previous byte, and rewrote the loop to process 8 (clang) or 32 (rustc) bytes at once with SIMD instructions. V8 got close to the compilers' simple version, after it had watched the function run. That is most of the speed gap measured in section 13, before any library or algorithm is involved.

What it costs
Ahead-of-time compilation costs build time (the {{Benchmark|#t-bench}} tab measures it: seconds for the Rust program against nothing for Python) and a separate binary for every processor and operating system you ship to. Interpretation costs speed. A JIT costs memory and warm-up time: the first calls are slow, and V8 compiled our function only after it was "hot and stable". TypeScript's erasure costs nothing at run time and checks nothing at run time.
False friends for a Python programmer
  • "Python is interpreted line by line." It is compiled to bytecode first (you have seen the .pyc files in __pycache__); only the bytecode is interpreted.
  • "TypeScript is compiled, so it is fast like C++." Its compilation removes types; the speed is V8's, the same as JavaScript.
  • "Python 3.14 has a JIT, so loops are fast now." The JIT ships in the official macOS and Windows installers but is experimental and off unless you set PYTHON_JIT=1 ({{What's new in 3.14|https://docs.python.org/3.14/whatsnew/3.14.html}}); the 3.14 run above shows JUMP_BACKWARD_NO_JIT.
  • "An optimised build is the same program, faster." In C++ optimisation can change what a buggy program does (section 9 shows a data race that disappears at -O2); in Rust, integer overflow panics in a debug build and wraps in a release build (section 7).
