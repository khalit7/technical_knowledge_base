6. Errors and nothingness

Two questions every program meets constantly: what to do when an operation fails (the line is not valid JSON), and how to say "there is no value" (a user with no entry). Python answers both with mechanisms that are invisible in a function's signature: an exception can come out of almost any call, and almost any variable could be None. Rust answers both with ordinary return values whose types say so, which the compiler makes you handle.

Nothingness: a key that is not there

None, or an exception.get() returns None, a real object meaning "nothing"; d[k] raises KeyError. Whether you checked is up to you (a type checker can warn when an Optional value is used unchecked).

silently insertsThe false friend of this section: per_user["nobody"] does not fail; it inserts a zero for the missing key and returns it, so the map grew from 1 to 2 entries. Use find() or contains() to ask without changing. C++'s "nothing" for pointers is nullptr, and dereferencing it is undefined behaviour.

refused at compile timeget() returns Option<&u64>: either Some(&value) or None. An Option is not a number, so n + 1 does not compile (E0369); you must say what None means, here with unwrap_or(0). Rust has no null at all in safe code.

refused by tsc, runs to NaNMap.get returns number | undefined. With strict on, tsc refuses the addition (TS18048, 'n' is possibly 'undefined'); run anyway, undefined + 1 is NaN and nothing complains. JavaScript has two "nothings", null and undefined.

Errors: a line that does not parse

The running program has to survive bad lines (the input has eight). Python and TypeScript wrap the parse in try; Rust's serde_json::from_str returns a Result, Ok(value) or Err(error), and C++23 added the same idea as std::expected.

exceptionsDifferent failures arrive as different exception types (here a TypeError and a JSONDecodeError; a missing field would be a KeyError), caught together. Nothing in json.loads's signature says it can raise; you learn it from the documentation or from production.

errors are valuesparse says in its type that it can fail (Result<Message, serde_json::Error>), the ? passes an error up to the caller in one character, and match must handle both Ok and Err or it does not compile. serde also checked the shape (a user that is a number is an error), which Python needed an explicit isinstance for. For bugs rather than expected failures Rust has panic!, which stops the thread (section 10).

expected, uncheckedstd::expected<long, std::string> (C++23, compiled with LLVM clang 23) holds a value or an error, like Rust's Result. But the last line shows the difference in philosophy: *parse_count("94x1") reads the value of an error without any check, which is undefined behaviour, and printed garbage. C++ gives you the vocabulary; Rust makes you use it. Most C++ code, including the standard library, still reports errors with exceptions.

What it costs
Exceptions keep the happy path short and cost nothing until thrown, but hide which calls can fail. Result and Option make every failure visible in the types and force a decision at every call (the ? operator keeps that cheap to write); the cost is verbosity at the edges, and .unwrap() calls that crash when you guessed wrong.
False friends for a Python programmer
  • "map[key] fails for a missing key." In C++ it inserts; in JavaScript a plain object or Map returns undefined; only Python raises.
  • "Rust's panic! is an exception you catch." It is meant for bugs and normally ends the thread; recoverable errors are Results.
  • "catch (e) gives me an Error." In JavaScript anything can be thrown, so TypeScript types e as unknown and makes you check.

7. Numbers and text

Short, because the rules are simple once seen, and dangerous because they look identical across languages until they are not.

no overflowIntegers grow as needed (263 is fine), // rounds down (floor: -7 // 2 is -4), and a str is a sequence of Unicode code points: len("café 日本 😀") is 9, and s[3] is the whole é.

overflow is undefined behaviourIntegers are fixed-size, and overflowing a signed one is undefined behaviour: the optimised build happened to print the wrapped value, and only the UndefinedBehaviorSanitizer (-fsanitize=undefined) reported it. Division truncates towards zero (-7 / 2 is -3). A std::string is bytes: the same text is 17 bytes, and s[3] is half of the é's two-byte UTF-8 encoding.

checked in debugOverflow panics in a debug build ("attempt to add with overflow") and wraps in a release build, unless you choose explicitly with checked_add (returns an Option) or wrapping_add. Division truncates like C++; div_euclid gives Python's answer. A String is UTF-8 bytes (len() is 17) and cannot be indexed by position at all: s[3] is refused (E0277), because byte 3 is not a character. You iterate .chars() or .bytes() instead.

one float typeEvery number is a 64-bit float, so integers are exact only up to 253 (253 + 1 prints as 253), / never rounds, and BigInt (2n ** 63n) is a separate type. Strings are UTF-16 code units: the emoji counts as 2 (length is 10 for 9 characters) and s[8] is half of it, a lone surrogate.

All four print 0.1 + 0.2 as 0.30000000000000004: they share the same IEEE 754 64-bit floating-point hardware, explained on the {{Numerical computing for ML|n:3f05c17b0d0d81d6af0be4a9a2edba8d}} page. The running program counts ASCII letters and digits only, so the "what is a character" question never changes its answer; the {{Rosetta|#t-rosetta}} tab shows how each version walks the text (Python by code points, Rust and C++ by bytes, TypeScript by UTF-16 units).

False friends for a Python programmer
  • "len(s) is the number of characters" is true only in Python. Rust's len() and C++'s size() count bytes; JavaScript's length counts UTF-16 units.
  • "Integer division rounds down." Only Python's // does; C++, Rust and JavaScript's Math.trunc round towards zero, which differs for negative numbers.
  • "An int in C++ is like a Python int." It is usually 32 bits, overflowing past 2,147,483,647, and that overflow is undefined behaviour.

8. Abstraction and polymorphism

Polymorphism means one piece of code working with many types. In Python you get it for free by duck typing: total(items) works on anything that has a .tokens() method, and a Protocol lets a type checker verify it. The other three make the requirement explicit, in three different ways.

checked when calledThe Protocol documents the requirement and lets mypy or ty check it; Python itself only fails when .tokens() is called on an int, deep inside total.

checked at compile timeA template is compiled once per type it is used with. A C++20 concept (HasTokens) states the requirement, so the error says "unsigned int does not satisfy HasTokens" instead of a page of template errors. For run-time choice, C++ also has virtual functions and inheritance.

checked at compile timeA trait is opted into explicitly (impl HasTokens for Message); the error E0277 even lists which types do implement it. Generic code (total<T: HasTokens>) is compiled once per type, called monomorphisation; dyn HasTokens is the alternative with one compiled copy and a table of function pointers looked up at run time. Rust has no inheritance.

checked by tsc, by shapeAn interface is structural: any object with a tokens(): number method fits, with no declaration, like a checked Protocol. Calling total([42]) would be refused by tsc. At run time it is plain JavaScript, so the check exists only before running.

What it costs
Monomorphisation gives the fastest calls and the largest binaries and longest compiles; dynamic dispatch (virtual, dyn, and every Python method call) costs a lookup per call but compiles once. Python and TypeScript need no declarations; C++ concepts and Rust traits make you write the contract down, which is also documentation.
False friends for a Python programmer
  • "A Rust trait is an abstract base class." There is no inheritance of fields; a trait is closer to a Protocol a type must opt into.
  • "Templates are generics." C++ templates are checked when used with a concrete type (concepts help); Rust generics are checked once, against their bounds, when defined.
