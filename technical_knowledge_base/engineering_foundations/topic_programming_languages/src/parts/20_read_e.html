5. Memory and lifetimes

This is the axis where the four differ most, and the one Python hides most completely. It is worth learning the machine underneath once, concretely; C++ is the language that shows it most plainly.

The machine underneath

  • Memory is one long row of numbered bytes. The number of a byte is its address, usually printed in hexadecimal (base 16): 0x10081d500 is 16 bytes after 0x10081d4f0. A pointer is a value that holds an address: 8 bytes on a 64-bit machine.
  • The stack and the heap. Each function call gets a small block of memory for its local variables, the stack frame, released automatically when the function returns. Anything that must outlive the call, or whose size is only known at run time (a list that grows), goes on the heap, which someone has to release explicitly. "Who releases heap memory, and when" is the question this section is about.
  • The processor reads memory in cache lines. Main memory is far slower than the processor, so the processor keeps recently used memory in small fast caches, filled one cache line at a time: this M1 Pro reports 128-byte lines (sysctl hw.cachelinesize; most Intel and AMD processors use 64). Reading one byte brings its whole line in, so data that sits together is read almost for free, and data scattered across memory costs a slow trip per line.
  • Values have a size and an alignment. A record of a 4-byte user id and an 8-byte token count takes 16 bytes in C++ and Rust, not 12: the 8-byte field must start at an address divisible by 8, so the compiler inserts 4 bytes of padding (offsetof(Record, tokens) printed 8).

The same four records, in Python and in C++ or Rust

Below, a list of four (user_id, tokens) records is drawn at its real addresses, read from the running programs: CPython's object headers through ctypes, C++'s and Rust's with &records[i]. Each row is one 128-byte cache line; rows far apart in memory are separated by a gap.

The last step of each view is the consequence, measured on 10 million records (best of several runs, read/code/memory/scan.*): summing the token counts takes ns per record from a contiguous C++ vector and ns from a Python list of tuples. Part of the Python cost is the interpreter (section 2), and part is the layout. The C++ program separates the two: the same compiled loop over one heap object per record, reached through pointers, takes ns per record when the objects happen to sit in allocation order and ns when the pointers are shuffled, about times slower than contiguous: the processor is waiting for cache lines. Shuffling the Python list costs it the same kind of factor ( ns). JavaScript arrays of objects are laid out like Python's (pointers to heap objects), except that V8 stores small integers inside the pointer itself ("Smis", {{V8 blog|https://v8.dev/blog/pointer-compression}}).

Why NumPy and PyTorch are fast from Python
A NumPy array or a PyTorch tensor is one Python object that owns a contiguous C buffer, laid out like the C++ vector above. The loop over it runs in C or C++, so neither the interpreter nor the pointer-chasing is paid per element. That is the whole trick behind "vectorise your Python".

The four strategies differ most on one classic bug. Keep a reference to the first user's name, then keep adding users: the list grows, and growing a list means allocating a bigger buffer, moving the elements and freeing the old buffer. What happens to the reference?

The C++ program compiles without a warning and, run normally, printed first user: followed by nothing: it read whatever was left in freed memory and carried on. Nothing guarantees it will print nothing next time; it could print garbage or crash. Only AddressSanitizer, a checking mode you compile in for testing (-fsanitize=address), turns it into a report. Rust refuses the program at the moment of the push, with error E0502: you may not change users while first borrows from it. Python never has the bug, because first holds its own reference to the string object, not to the list's slot; the object lives until the last reference goes, and CPython frees it at that exact moment.

What it costs
Python's objects cost memory and speed (128 bytes for 12 bytes of data above) but never a dangling reference. C++'s layout is optimal and its mistakes are silent. Rust has C++'s layout and refuses the mistake, at the price of rules about borrowing that you must learn. Garbage-collected languages trade pauses and memory for simplicity.
False friends for a Python programmer
  • "A list is an array." A Python list is an array of pointers; a C++ std::vector<Record> or Rust Vec<Record> holds the records themselves.
  • "A C++ reference keeps the object alive." It does not; it is only another name for memory someone else owns. Python's references are owning; C++'s and Rust's references are borrowing.
  • "del x frees x." It removes one name; the object is freed when the last reference goes. C++'s delete p really frees, whether or not others still point to it.
