3. Types

A type says what kind of value something is and therefore what you may do with it. Every language checks types; the question is when. A dynamically typed language checks each operation as it runs, on the actual values. A statically typed language checks the whole program before it runs. Gradual typing sits between: you annotate where you want and a separate checker reads the annotations, as with Python's hints and TypeScript.

The same mistake in all four: the token counter called with a user id (an integer) instead of the message text. Predict which languages produce a program at all, then pick each one.

runs, then failsPython starts running and prints the first result; the error arrives only when the bad call executes, as a TypeError deep inside the function. A type checker (mypy or Astral's ty, each one command) reads the hint text: str and reports the same line without running anything, but only if you run it: Python itself ignores hints.

refused at compile timeThe compiler refuses: there is no conversion from int to std::string_view. No program is produced, so nothing runs.

refused at compile timeError E0308, "mismatched types", with an arrow under the 42. Rust error messages point at the exact place and often suggest a fix; run rustc --explain E0308 for a page about the error.

refused by tsc, runs anywaytsc reports the wrong type (error TS2345). But types are erased, so the same file still runs: Node strips the annotations and executes it, and the function quietly returns 0 because (42).length does not exist and the loop never starts. TypeScript only protects you if tsc is part of your build.

Two more distinctions. By name or by shape: in C++ and Rust a value fits a type only if it was declared as that type (nominal typing); in TypeScript any object with the right fields fits (structural typing), like Python's duck typing but checked before running (section 8). Sound or not: a sound type system never lets a value of the wrong type through. Rust's safe subset aims for soundness; TypeScript says plainly that it does not (section 1): any, type assertions (x as Foo) and data from JSON.parse pass unchecked. Python's checkers are similar: an unannotated function is not checked at all.

What each choice costs, and false friends (3)

Static types cost writing them (less than you expect: Rust and TypeScript infer most local types) and a compile step. Dynamic types cost finding the mistake later, in tests or in production, and cost speed: an interpreter that does not know n is an integer must check before every addition (section 2). Gradual types cost discipline: the checker sees only what you annotate.

  • "Type hints make Python check types." They do not; only a separate tool does. The same is true of TypeScript at run time: a Message type on JSON.parse(line) is a promise you made, not a check. Validate data at the boundary (Pydantic in Python; zod or a hand-written guard like the Rosetta program's isMessage in TypeScript).
  • "auto in C++ or let in Rust means dynamic." Both mean "infer the type now"; the type is still fixed at compile time and cannot change later.
  • "Rust's u64 is like Python's int." It is a fixed 64-bit unsigned integer; section 7 shows what happens at its limit.

4. Names, values and mutation

In Python a variable is a name attached to an object; b = a attaches a second name to the same object, so a change through either is visible through both. Two names for one object are aliases. JavaScript works the same way for objects and arrays. In C++ and Rust a variable is the value, a region of memory of a known size, so b = a must decide what happens to that memory: C++ copies it; Rust moves it, and a may no longer be used.

sharessaved and top are one list; appending through one changes "both". Copying is explicit: top.copy() or list(top).

copiessaved = top copied the vector and every string in it (new memory for each). Sharing is explicit: a reference, std::vector<std::string>& alias = top, is a second name like Python's. The default copy is safe but can be expensive for large values, which is why C++ code passes const T& everywhere.

moves; refusedError E0382, "borrow of moved value": after let mut saved = top; the vector belongs to saved, and using top is a compile error. Nothing was copied (moving a Vec copies three machine words: pointer, length, capacity). The compiler even suggests .clone() if you really wanted a copy.

sharesExactly like Python: both names reach one array. const only stops the name from being re-pointed; the array can still change.

Why Rust chose moves: if exactly one variable owns each value, the compiler always knows who must free it and when (section 5), and no hidden second name can change the value under you. Rust then lets you borrow a value: any number of shared, read-only borrows (&T), or exactly one exclusive borrow that may change it (&mut T), never both at once. That single rule, "aliasing or mutation, not both", is what sections 5 and 9 build on.

False friends (3)
  • "Passing a vector to a C++ function lets it change my vector." Not unless the parameter is a reference (T&); by default the function gets its own copy.
  • "const means immutable." In JavaScript, const arr = [] can still be pushed to; in C++ const applies to what it is attached to (the pointer or the thing pointed to); in Rust everything is immutable unless declared mut.
  • "Rust's move is like Python's assignment." It is closer to handing over the only key: the old name is dead.
