Why each gap exists

A speed difference is only useful if you know where it comes from, because that tells you what a rewrite would buy. Each box below takes one cause, shows it measured on this program, and says what it costs.

1. Interpreter dispatch: the same characters, run two ways

CPython compiles tokens() to bytecode (a list of small instructions for a virtual machine) and then runs a C loop, the interpreter, that fetches each instruction, jumps to the C code for it, and does it on objects: every character is a one-character str object, every comparison returns a bool object. Rust and C++ compile the same loop ahead of time to machine code, instructions the CPU runs directly on raw bytes in registers. Step through the input below: the top lane shows the bytecode instructions CPython really executed for each character (recorded by tracing CPython ), the bottom lane the ARM64 instructions Apple clang 14 produced for the C++ loop.

How to read it: the counts are instructions, not time, and the two kinds are not the same size: one bytecode instruction costs the CPU many machine instructions (fetch, decode, jump, reference counting, type checks). What was measured is the time: the Python loop spends per character over the whole file, the compiled C++ loop per byte and Rust's per byte. The listing is the loop compiled without vectorisation so it can be read one byte at a time; the real -O2 build handles bytes per pass with SIMD (single instruction, multiple data) instructions. Note also é: one character for Python, two bytes for C++ and Rust, which work on UTF-8 bytes.

5. Crossing from Python into native code has a price per call

A call into an extension module goes through CPython's calling convention: arguments arrive as Python objects, the binding library checks and converts them (a str to a pointer and length of its UTF-8 bytes), the native function runs, and the result is boxed back into a Python int. 6. Threads: the GIL, and the free-threaded build

The GIL (global interpreter lock) lets only one thread run Python bytecode at a time in the standard build, so CPU-bound threads take turns. CPython 3.14 also ships a free-threaded build (python3.14t, PEP 703 and PEP 779) with no GIL. The same threaded program, wall time on the full input:

7. Strings, I/O buffering, startup and the JIT

  • Strings. Python decodes the file's UTF-8 into str objects of code points as it reads; JavaScript strings are UTF-16; C++ std::string and Rust's String keep the UTF-8 bytes (Rust checks they are valid UTF-8, C++ does not). The compiled loops count over bytes, which is correct here only because every non-ASCII byte is 0x80 or above (PROGRAM.md, rule 3).
  • I/O buffering. Every version reads through a buffer (Python's open, C++ std::ifstream, Rust BufReader, Node's read stream), so the 39 MB arrive in large chunks rather than one system call per line. Reading and splitting the lines took Python : I/O is not the bottleneck for any variant. Output is five lines, so stdout buffering does not matter here; it would for a program that prints a line per record.
  • Startup. On an empty file, the native binaries finish in about a millisecond; CPython needs just to start (-c pass) and Node (Startup view above). For a command-line tool run thousands of times by a script, that floor can matter more than throughput. A cold bytecode cache costs Python more: against when every imported module must be compiled again (it happens once, after an install or upgrade). Node's compile cache made no measurable difference to this small script ( against ), and running the .ts file directly cost at startup against for the compiled .js.
  • The JIT. V8 first interprets JavaScript, then compiles hot functions such as countTokens to machine code using the types it has seen (just-in-time compilation). That is why Node is far faster than CPython on the character loop while starting slower than a native binary. CPython 3.14 has an experimental JIT too, built but switched off in the interpreter measured here (--enable-experimental-jit=yes-off).

So when is a rewrite worth it?

  • First, idiomatic Python. Replacing the hand-written character loop with a regex cut the time by for a two-line change.
  • Then move the hot loop, in batches. A PyO3 or nanobind function that takes the whole list costs one crossing; one call per item costs one per item, fine when each item is real work and wasteful for tiny functions (box 5).
  • Move the whole pipeline when the glue dominates. Here, parsing JSON into Python objects is the cost that remains; only the whole-file call removes it.
  • A rewrite in Rust or C++ is worth it for a tool run often on large data, or where startup matters; the price is the build setup and the longer code (Lines of code and Compile time views). Python stays the place to orchestrate.

Method and caveats

  • Wall time: hyperfine runs each command 2 times to warm up, then 7 times; the bar is the median, the whisker the fastest and slowest run, and the dots each run. Commands run without a shell (-N), output discarded.
  • Warm and cold: "warm" means the input is already in the operating system's file cache and the program has run before; every time on this tab is warm. Clearing the file cache needs administrator rights (purge), so a cold-disk start was not measured. What was measured cold is the language runtime's own cache: Python with an empty bytecode cache (every imported module compiled from source again) and Node with an empty compile cache; see the Startup view.
  • Memory: /usr/bin/time -l, maximum resident set size, median of 3 runs.
  • Startup: the same programs on an empty file, 3 warmups then 20 runs; for Python, Node and Bun also the bare runtime (-c pass, -e 0).
  • Lines of code: non-blank lines that are not only a comment, counted by src/bench/loc.py. The C++ count includes the -line JSON parser (json_lite.hpp) the C++ version must carry because the standard library has none; the Rust count includes Cargo.toml but not serde_json.
  • Compile time: hyperfine, median of 3 to 5 runs; Rust and the PyO3 extension from a clean build including their dependencies (serde, pyo3), and Rust again after editing main.rs.
  • Background load: the laptop was in normal use (other programs running); the load average (1, 5 and 15 minutes) at the start was . Single-threaded results are stable to a few per cent (compare the whiskers); thread-scaling results are the most affected.
  • One machine, one input. These numbers rank the languages on this job on an Apple M1 Pro. A program dominated by different work (numeric arrays, network waits, many small allocations) would rank differently.
