14. Choosing, and a learning path for you

Which language for which job

JobLanguageWhy
Research, training, evaluation, notebooks, data wranglingPythonThe libraries are there (PyTorch, NumPy, polars, Transformers), and their fast parts are already C++ or Rust underneath.
Make a hot Python loop fastRust through PyO3 (or C++ through nanobind in a C++ codebase)Memory-safe speed; maturin builds wheels; the pattern of pydantic-core, tokenizers and polars.
Command-line tools and network services that must be fast, small and reliableRustA single binary, start-up in milliseconds, data races refused at compile time; cargo for everything.

Reading and changing PyTorch internals, llama.cpp, inference engines; writing CUDA kernelsC++ (and C)That is the language those systems are written in; CUDA C++ is C++ with extensions.

A learning path, for an ML engineer who knows Python

In the order that pays off soonest. Each step names its milestone, a small program you can show working. The children of this page (below) will teach each language in this order.

  1. TypeScript, through JavaScript's runtime (closest to Python, immediately useful). Learn the event loop and async/await (section 9), objects as shared references (section 4), null and undefined and strict mode (section 6), then types: narrowing, unknown, and validating input at the boundary because types are erased (section 3). Milestone: an MCP server in TypeScript that exposes the token counter as a tool.
  2. Rust, ownership first. Ownership, moves and borrowing (sections 4 and 5; chapter 4 of the Rust Book), then Option and Result (section 6), traits (section 8), cargo and clippy. Milestones: the token counter as a PyO3 extension called from Python and timed against the Python loop; then the same as a command-line tool; then a small HTTP service with tokio.
  3. C++, from the machine up, to reading llama.cpp. The goal is to read real inference-engine source, so learn the features in the order that code uses them (counts at llama.cpp commit , from read/code/llama/excerpts.sh):
    1. C first: structs, fixed-size arrays, pointers and pointer arithmetic, void* casts. ggml_tensor and block_q4_0 (section 5) are plain C structs; the CPU kernels walk arrays of blocks through pointers (x[ib].qs[j]).
    2. Memory and files: stack and heap, alignment and padding, mmap (section 5), and reading a binary format (the GGUF reader is ggml/src/gguf.cpp).
    3. The preprocessor: #if/#ifdef select code per processor and backend (50 such lines in the ARM CPU kernel file alone) and macros such as GGML_RESTRICT.
    4. SIMD intrinsics with a scalar twin: each hot kernel has a portable C loop (ggml-cpu/quants.c) and per-architecture versions full of NEON calls like vld1q_u8 (209 vld1q_ calls in arch/arm/quants.c). Read the scalar one first; it says what the SIMD one computes.
    5. Threads: ggml's CPU backend starts its worker threads with pthread_create behind a ggml_thread_create macro; the data-race rules of section 9 apply.
    6. Modern C++ in src/: classes and RAII (llama_mmap's destructor), std::unique_ptr (60 uses in the headers), std::vector and std::string, lambdas, exceptions (260 throw std::runtime_error), then templates (58 declarations; read, rarely written).
    7. The build: CMake with backend options (GGML_CUDA, GGML_METAL, GGML_VULKAN, GGML_HIP, GGML_SYCL, GGML_BLAS), and sanitizers for your own changes.
    Milestones: the token counter in C++ under AddressSanitizer with no reports; then build llama.cpp from source, run a small GGUF model, and trace one call of ggml_vec_dot_q4_0_q8_0 from the scalar version to the NEON one. Then CUDA, which is {{Topic: cuda-and-gpu-programming|n:3c65c17b0d0d81c39f34d5e070d783c1}}'s path, and what llama.cpp's kernels compute (attention, KV cache, quantisation), which is {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}'s.
  4. Python, deeper (you already use it daily): the object model and data model protocols, what CPython does with your code (sections 2 and 5), packaging with uv, free-threaded 3.14 and the changes in 3.15. Milestone: profile a slow script, then make it faster three ways (algorithm, vectorised library, extension) and explain each gain.
What the children will cover
This page is the overview. Four child pages are proposed, one per language, each written for a Python programmer and following the steps above: Python (the object model, the interpreter, packaging, free threading, current releases), C++ (the machine, RAII, templates, the build, ending in a guided reading of llama.cpp), Rust (ownership to PyO3 extensions, command-line tools and async services), and TypeScript (JavaScript's runtime, then types, ending in an MCP server).
