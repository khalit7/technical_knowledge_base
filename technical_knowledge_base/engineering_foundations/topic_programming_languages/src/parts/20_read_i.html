13. Choosing

Which language for which job

JobLanguageWhy
Research, training, evaluation, notebooks, data wranglingPythonThe libraries are there (PyTorch, NumPy, polars, Transformers), and their fast parts are already C++ or Rust underneath.
Make a hot Python loop fastRust through PyO3 (or C++ through nanobind in a C++ codebase)Memory-safe speed; maturin builds wheels; the pattern of pydantic-core, tokenizers and polars.
Command-line tools and network services that must be fast, small and reliableRustA single binary, start-up in milliseconds, data races refused at compile time; cargo for everything.
LLM applications, agents, MCP servers, anything with a web front endTypeScript on Node or BunThe SDKs and harnesses are written in it (section 1); one language from browser to server. Python is a fine second choice for agents.
Reading and changing PyTorch internals, llama.cpp, inference engines; writing CUDA kernelsC++ (and C)That is the language those systems are written in; CUDA C++ is C++ with extensions.

The language pages

Each language has an essentials page and four children, written for a Python programmer, every output from a real run. They are listed in the order that pays off soonest for an ML engineer who knows Python: TypeScript (through JavaScript's runtime), Rust, C++, then Python more deeply. Each card keeps its step's milestone, a small program you can show working, closed. Times are each page's own header: core reading, plus its closed details.

{{JavaScript and TypeScript: the essentials|n:3cd5c17b0d0d81dbac7be3b8686be023}} 17 min, plus 11

JavaScript runs your code on one thread around an event loop, and TypeScript is a type layer erased before anything runs.

  1. {{JavaScript: values, objects, functions and modules for Python programmers|n:4055c17b0d0d810c982ac6ab36f88539}} 24 min, plus 11Looks like Python with braces; the surprises are one number type, a missing value that is undefined rather than an error, this set by the call, and prototype chains.
  2. {{JavaScript: the event loop, promises and streams|n:4055c17b0d0d81fe857de8b34db109ea}} 14 min, plus 9One thread that never waits: each callback runs to completion, and every microtask drains before the next macrotask.
  3. {{TypeScript: the type system, narrowing and runtime validation|n:4055c17b0d0d81519278df19753ab5ec}} 27 min, plus 49A checker erased before running: narrowing makes unions safe inside the program, and data from outside needs a runtime schema such as zod.
  4. {{TypeScript: LLM apps and agents|n:4055c17b0d0d8109aad6e69a87b3bd6f}} 23 min, plus 25Ordinary server code around one HTTP call: SDK types shape every reply, your loop runs the tools, one zod schema checks the model's JSON.
Milestone for this step

Step 1, closest to Python and immediately useful. The event loop and async/await, objects as shared references, null, undefined and strict mode, then types: narrowing, unknown, and validating input at the boundary because types are erased. Milestone: an MCP server in TypeScript that exposes the token counter as a tool.

{{Rust: the essentials|n:3c65c17b0d0d8156bed9ead8a22f33b0}} 26 min, plus 11

Every value has one owner and every borrow is checked at compile time, so memory and data-race bugs become compile errors.

  1. {{Rust: enums, traits, errors and iterators|n:4055c17b0d0d8129b199c18b4bd56935}} 33 min, plus 13What Python discovers at run time becomes types: enums with exhaustive match, Result in every signature, traits, zero-cost iterators.
  2. {{Rust: lifetimes, smart pointers, threads and unsafe|n:4055c17b0d0d8160aa32df9cda0aef03}} 16 min, plus 14One rule, many readers or one writer: lifetimes check it, Send and Sync carry it across threads, RefCell and Mutex move it to run time, Miri checks unsafe.
  3. {{Rust: speeding up Python with PyO3 and maturin|n:4055c17b0d0d81048311c87e9b76a78a}} 34 min, plus 13An extension pays off only when the whole hot path crosses in one call, borrowing Python's memory and releasing the GIL.
  4. {{Rust: async with tokio, services with axum, and CLIs|n:4055c17b0d0d8148b863faa050cf5456}} 27 min, plus 19A future is a lazy state machine polled by tokio on a few worker threads; axum makes each request a task; the service ships as one file.
Milestone for this step

Step 2, ownership first. Ownership, moves and borrowing (chapter 4 of the Rust Book), then Option and Result, traits, cargo and clippy. Milestones: the token counter as a PyO3 extension called from Python and timed against the Python loop; then the same as a command-line tool; then a small HTTP service with tokio.

{{C++: the essentials|n:3cd5c17b0d0d81ceadcee44fe9c023a0}} 17 min, plus 9

You decide where each object lives and when it dies, and the compiler trusts you: files compile separately and link, and a broken rule is undefined behaviour.

  1. {{C++: ownership, moves and object lifetimes|n:4055c17b0d0d81819d74fa010e68ac2a}} 19 min, plus 13Every object has one lifetime ending at a point in the source; RAII and moves let ownership, not a garbage collector, decide when memory is freed.
  2. {{C++: classes, templates and the standard library|n:4055c17b0d0d818a9509f6035089a7e1}} 22 min, plus 17Abstractions resolve at compile time unless you ask for run-time dispatch, which costs about 1 to 6 ns a call, measured.
  3. {{C++: the machine underneath: caches, layout, SIMD and the memory model|n:4055c17b0d0d811fa947ee576a97a516}} 30 min, plus 20Once a loop is a handful of instructions, memory sets its speed: cache level, layout and SIMD move it 50 times either way.
  4. {{C++: reading llama.cpp, one token through the code|n:4055c17b0d0d8150a5effbb5a667dd9d}} 33 min, plus 36One token is a ggml graph built once, planned once, and walked by a thread pool through a kernel over weights repacked at load.
Milestone for this step

Step 3, from the machine up, to reading llama.cpp. The goal is to read real inference-engine source, so learn the features in the order that code uses them (the seven steps below). Milestones: the token counter in C++ under AddressSanitizer with no reports; then build llama.cpp from source, run a small GGUF model, and count which kernels actually run: on an Apple Silicon Mac with the default build, the ggml_vec_dot_* functions most guides point to run zero times, because the weights are repacked at load and 4x4 gemv/gemm kernels do every product (measured on {{C++: reading llama.cpp, one token through the code|n:4055c17b0d0d8150a5effbb5a667dd9d}}). Reading the scalar ggml_vec_dot_q4_0_q8_0 next to its NEON version is still the best way into ggml's SIMD code. Then CUDA, which is {{Topic: cuda-and-gpu-programming|n:3c65c17b0d0d81c39f34d5e070d783c1}}'s path, and what llama.cpp's kernels compute (attention, KV cache, quantisation), which is {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}'s.

The seven steps into llama.cpp, with counts from its source (optional)

Counts at llama.cpp commit , from read/code/llama/excerpts.sh.

  1. C first: structs, fixed-size arrays, pointers and pointer arithmetic, void* casts. ggml_tensor and block_q4_0 (section 5) are plain C structs; the CPU kernels walk arrays of blocks through pointers (x[ib].qs[j]).
  2. Memory and files: stack and heap, alignment and padding, mmap (section 5), and reading a binary format (the GGUF reader is ggml/src/gguf.cpp).
  3. The preprocessor: #if/#ifdef select code per processor and backend (50 such lines in the ARM CPU kernel file alone) and macros such as GGML_RESTRICT.
  4. SIMD intrinsics with a scalar twin: each hot kernel has a portable C loop (ggml-cpu/quants.c) and per-architecture versions full of NEON calls like vld1q_u8 (209 vld1q_ calls in arch/arm/quants.c). Read the scalar one first; it says what the SIMD one computes.
  5. Threads: ggml's CPU backend starts its worker threads with pthread_create behind a ggml_thread_create macro; the data-race rules of section 9 apply.
  6. Modern C++ in src/: classes and RAII (llama_mmap's destructor), std::unique_ptr (60 uses in the headers), std::vector and std::string, lambdas, exceptions (260 throw std::runtime_error), then templates (58 declarations; read, rarely written).
  7. The build: CMake with backend options (GGML_CUDA, GGML_METAL, GGML_VULKAN, GGML_HIP, GGML_SYCL, GGML_BLAS), and sanitizers for your own changes.

{{Python: the essentials|n:3cd5c17b0d0d81b28acdea39e7a4d998}} 10 min, plus 2

A name is a reference to an object, and every piece of syntax is a method call on its type, run as bytecode by one interpreter.

  1. {{Python: the data model and protocols|n:4055c17b0d0d816a8705e4d3f20b3da7}} 23 min, plus 21Every operator, loop, with and attribute access is a special-method lookup on the type, with fixed fallbacks.
  2. {{Python: concurrency, asyncio and the GIL|n:4055c17b0d0d81bdbee8c37d80b55a0e}} 17 min, plus 10The GIL lets threads overlap waiting but not computing; asyncio swaps threads for one loop that a single blocking call stalls.
  3. {{Python: CPython internals and performance|n:4055c17b0d0d8111872ad7101b7e3c22}} 19 min, plus 6A bytecode loop over heap objects, so speed comes from moving the loop out of Python, after measuring which loop matters.
  4. {{Python: typing, uv, packaging and the toolchain|n:4055c17b0d0d8192878fce7505cc612f}} 19 min, plus 15Hints are checked by tools, never at run time; packaging is four jobs that uv does as one tool with one lock file.
Milestone for this step

Step 4, deeper (you already use it daily): the object model and data model protocols, what CPython does with your code, packaging with uv, free-threaded 3.14 and the changes in 3.15. Milestone: profile a slow script, then make it faster three ways (algorithm, vectorised library, extension) and explain each gain.
