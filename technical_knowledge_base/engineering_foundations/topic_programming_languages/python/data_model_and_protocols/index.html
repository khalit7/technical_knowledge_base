The idea in one screen

Every operator, loop, with block and attribute access is a call to a special method looked up on the object's type, with a fixed order of fallbacks when the method is missing or declines; implement the methods and your class behaves like a built-in, and almost every Python surprise is one of these lookups doing exactly what the rules say.

A small vector class implements a handful of these, and the built-ins start working. Nothing inherits from anything: Python's polymorphism is by protocol (the methods you have), not by declared parent class.

d1_vec.py
class Vec:
    def __init__(self, *xs):
        self.xs = tuple(xs)
    def __repr__(self):                 # what the REPL and debuggers show
        return f"Vec{self.xs}"
    def __len__(self):                  # len(v)
        return len(self.xs)
    def __iter__(self):                 # for, list(), unpacking, sum()
        return iter(self.xs)
    def __getitem__(self, i):           # v[i], v[1:]
        return self.xs[i]
    def __eq__(self, other):            # ==
        if not isinstance(other, Vec):
            return NotImplemented       # "I don't know": let Python try the other side
        return self.xs == other.xs
    def __hash__(self):                 # dict keys, set members; must agree with ==
        return hash(self.xs)
    def __add__(self, other):           # v + w
        if not isinstance(other, Vec):
            return NotImplemented
        return Vec(*(a + b for a, b in zip(self.xs, other.xs, strict=True)))
    def __radd__(self, other):          # 0 + v, which sum() does first
        return self if other == 0 else NotImplemented
    def __bool__(self):                 # if v:
        return any(self.xs)

v, w = Vec(1, 2), Vec(3, 4)

The last three lines are the dispatch rules at work. sum() starts from the integer 0, so it first computes 0 + Vec(1, 2); int.__add__ does not know Vec and returns NotImplemented, so Python tries the right operand's __radd__. v == (1, 2) is False rather than an error because both sides returned NotImplemented and Python fell back to identity. And v + 1 raises TypeError only after both sides declined.

NotImplemented is not NotImplementedError
Returning the singleton NotImplemented means "I do not handle this type; ask the other operand". Raising NotImplementedError means "this abstract method was not written" and stops the dispatch dead. Mixing them up is a common bug in operator methods.

Three rules people learn the hard way

  • Special methods are looked up on the type, not the instance. "Implicit invocations of special methods are only guaranteed to work correctly if defined on an object's type, not in the object's instance dictionary" (Special method lookup). Setting x.__len__ = ... on one object does nothing for len(x). This lets CPython skip the instance dict on every operator.
  • A subclass on the right goes first. "If the operands are of different types, and the right operand's type is a direct or indirect subclass of the left operand's type, the reflected method of the right operand has priority" (same page). So a subclass can override how it combines with its parent from either side.
  • __eq__ and __hash__ travel together. "A class that overrides __eq__() and does not define __hash__() will have its __hash__() implicitly set to None" (same page). Objects that compare equal must have equal hashes, and a hash must not change while the object is in a dict or set; that is why mutable built-ins are unhashable and why a dict key should be immutable.

    Costs and habits (what it solves, what it costs, when not to)
    What it solves
    Your types plug into every built-in, library and syntax form: sorted, sum, dict, f-strings, with, PyTorch's __torch_function__, NumPy's __array__.
    What it costs
    Every operator is a method lookup and call; that is a large part of why pure-Python arithmetic is slow (Python: CPython internals and performance).
    When not to
    Do not overload operators with surprising meanings; + should combine, == should compare. Prefer a dataclass (section 5) when you only need __init__, __repr__ and __eq__.

    2. Copies and calls: what a function receives

    Assignment never copies (the essentials page's first fact). So two questions decide most "who changed my list?" bugs: what a copy copies, and what a function call hands over.

    Shallow and deep copies

    A shallow copy (x.copy(), list(x), x[:], copy.copy) makes a new outer container whose slots point at the same inner objects. A deep copy (copy.deepcopy) copies recursively, keeping a memo so that an object shared twice in the original is shared twice in the copy too.     3. Iterators and generators: laziness as a protocol

    An iterable has __iter__, which returns a fresh iterator each time; an iterator is the one-pass cursor: __next__ returns the next item or raises StopIteration, and its __iter__ returns itself. A list is an iterable; iter(list) is an iterator. The difference shows up when you loop twice (Iterator types).

def timed(fn):                                # a decorator: takes a function, returns one
    @functools.wraps(fn)                      # copy __name__, __doc__, __wrapped__ ...
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            print(f"{fn.__name__} took {time.perf_counter() - t0:.3f} s")
    return wrapper

    A decorator with arguments: a retry helper for a model API (f3_retry.py)

    A decorator with arguments, @retry(times=4), is one level deeper: retry(times=4) runs first and returns the actual decorator.     f3_retry.py
    import functools, random, time

def retry(times=3, base_delay=0.01, on=(ConnectionError, TimeoutError)):
    """A decorator WITH arguments is a function that returns a decorator."""
    def decorate(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            for attempt in range(1, times + 1):
                try:
                    return fn(*args, **kwargs)
                except on as e:
                    if attempt == times:
                        raise                     # out of attempts: re-raise the last error
                    delay = base_delay * 2 ** (attempt - 1) * random.uniform(0.5, 1.5)
                    print(f"attempt {attempt} failed ({e!r}); retrying in {delay * 1000:.0f} ms")
                    time.sleep(delay)
        return wrapper
    return decorate

    5. Classes: the MRO, dataclasses, slots and descriptors

    A class statement runs its body like a function body, collects the names it defined into a dict, and builds a class object from it. An instance stores its own attributes (usually in obj.__dict__); everything else, methods included, lives on the class and is found by looking up the chain of classes.

    Descriptors: how property, methods and self work

    A descriptor is an object stored on a class that defines __get__ (and optionally __set__ and __delete__). When attribute lookup finds one on the class, it calls it instead of returning it (Descriptor guide). One with __set__ is a data descriptor, and the order is fixed: "data descriptors always override instance dictionaries. However, non-data descriptors can be overridden by instance dictionaries" (Invoking descriptors). The full lookup for obj.x (the fourth row of the hero; step each outcome in the explorer of section 1, group "Attribute lookup"):

    1. a data descriptor named x on type(obj) or its MRO (for example a property);
    2. otherwise obj.__dict__["x"];
    3. otherwise a non-data descriptor (a plain function, which becomes a bound method) or plain class attribute;
    4. otherwise __getattr__, if the class defines it; otherwise AttributeError.

    This one mechanism explains a lot of "magic". property is a data descriptor, which is why assigning to a read-only property fails instead of shadowing it. A function is a non-data descriptor: s.describe calls describe.__get__(s, Sampling), which returns a bound method that remembers s and passes it as self. Frameworks (Django fields, SQLAlchemy columns, Pydantic) are descriptors with validation inside, like the Positive below.

    class Positive:
    """A reusable validated attribute: a data descriptor (it defines __set__)."""
    def __set_name__(self, owner, name):
        self.name = "_" + name
    def __get__(self, obj, owner):
        if obj is None:
            return self                    # accessed on the class itself
        return getattr(obj, self.name)
    def __set__(self, obj, value):
        if value <= 0:
            raise ValueError(f"{self.name[1:]} must be > 0, got {value}")
        setattr(obj, self.name, value)

class Sampling:
    temperature = Positive()
    max_tokens = Positive()
    def __init__(self, temperature, max_tokens):
        self.temperature = temperature     # goes through Positive.__set__
        self.max_tokens = max_tokens
    @property                              # property is a data descriptor too
    def budget(self):

    6. Exceptions: the hierarchy, chaining and groups

    An exception is an object; raise unwinds the stack until an except clause whose class matches (by isinstance, in the order written). Since 3.11 a try that raises nothing costs nothing ("zero-cost" exceptions, What's new in 3.11), so "ask forgiveness, not permission" (try it and catch the failure) is not a performance sin. How to design a library's errors (raise rather than return None, what to catch where) is on Code design; this section is the mechanics.

    The hierarchy, and what except Exception does not catch

    Everything derives from BaseException. Ordinary errors derive from its subclass Exception; four do not, on purpose, so that a broad except Exception: lets them through: KeyboardInterrupt (Ctrl-C), SystemExit (sys.exit()), GeneratorExit (section 3) and, since 3.8, asyncio.CancelledError.     7. Context managers: with

    with m as r: calls m.__enter__(), binds its return value to r, runs the body, and then always calls m.__exit__(exc_type, exc, tb), with the exception if one was raised and Nones if not. If __exit__ returns a true value the exception is swallowed (step both cases in the explorer of section 1, group "with"). It is try/finally packaged as an object, for anything that must be released: files, locks, connections, GPU memory pools, timers, temporary settings such as torch.no_grad().

    contextlib.contextmanager writes the class for you from a generator: the code before yield is __enter__, the code after it (in a finally) is __exit__. Several managers in one with are entered left to right and exited right to left. ExitStack handles a number of resources known only at run time (contextlib).

    import contextlib, time

class Timer:
    def __enter__(self):
        self.t0 = time.perf_counter()
        return self                                   # bound to the name after `as`
    def __exit__(self, exc_type, exc, tb):
        self.ms = (time.perf_counter() - self.t0) * 1000
        print(f"Timer exit: exc_type={exc_type.__name__ if exc_type else None}")
        return False                                  # do not swallow exceptions

with Timer() as t:
    sum(range(100_000))
print(f"{t.ms:.1f} ms")

@contextlib.contextmanager                            # the same protocol, written as a generator
def opened(name):
    print(f"open {name}")
    try:
        yield name.upper()                            # the value bound by `as`
    finally:
        print(f"close {name}")                        # runs even if the body raises

try:
    with opened("a") as a, opened("b") as b:          # entered left to right...
        print("body", a, b)
        raise KeyError("oops")
except KeyError:
    print("KeyError reached the caller")              # ...exited right to left

with contextlib.ExitStack() as stack:                 # a number of resources known only at run time
    names = [stack.enter_context(opened(n)) for n in ("x", "y", "z")]
    print("using", names)

with contextlib.suppress(FileNotFoundError):
    open("/no/such/file")
print("suppressed")

    The async form, async with, calls __aenter__ and __aexit__, which may await (opening a connection, releasing a semaphore); asyncio.timeout, TaskGroup and Semaphore use it, on Python: concurrency, asyncio and the GIL.

    The mistake
    Writing @contextmanager without try/finally around the yield. If the body raises, the exception is thrown in at the yield, and any cleanup written after it without finally never runs.
