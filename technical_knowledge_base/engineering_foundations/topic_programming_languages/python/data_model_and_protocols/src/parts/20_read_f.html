5. Classes: the MRO, dataclasses, slots and descriptors

A class statement runs its body like a function body, collects the names it defined into a dict, and builds a class object from it. An instance stores its own attributes (usually in obj.__dict__); everything else, methods included, lives on the class and is found by looking up the chain of classes.

Multiple inheritance and the MRO

That chain is the method resolution order (MRO), Cls.__mro__, computed by the C3 linearisation algorithm ({{The Python 2.3 MRO|https://docs.python.org/3/howto/mro.html}}): every class appears before its parents, and parents keep the order you listed them. super() means "the next class in the MRO of type(self)", not "my parent", which is what lets several mixins each run their part of setup exactly once (cooperative multiple inheritance).

c1_mro.py
class Base:
    def setup(self):
        print("Base.setup")

class Logging(Base):
    def setup(self):
        print("Logging.setup ->"); super().setup()

class Caching(Base):
    def setup(self):
        print("Caching.setup ->"); super().setup()

class Service(Logging, Caching):
    def setup(self):
        print("Service.setup ->"); super().setup()

print([c.__name__ for c in Service.__mro__])
Service().setup()            # super() means "next in the MRO of type(self)", not "my parent"
print([c.__name__ for c in Logging.__mro__])
Logging().setup()

try:
    class Bad(Base, Logging):    # Base listed before its own subclass
        pass
except TypeError as e:
    print("TypeError:", e)
super() follows the MRO
class A:
    def who(self): return 'A'
class B(A):

class C(A):
    def who(self): return 'C' + super().who()
class D(B, C):

Use this sparingly. Mixins with cooperative super() calls are fine; deep hierarchies are rarely worth it. Composition (an object that holds a Cache and a Logger) is usually easier to read and test than inheriting from both; when to choose composition over inheritance is a design question, on {{Code design|n:3ef5c17b0d0d817b99a0ff9701ff30cd}}.

Dataclasses: classes for data, without the boilerplate

@dataclass writes __init__, __repr__ and __eq__ from the annotated class attributes ({{dataclasses|https://docs.python.org/3/library/dataclasses.html}}). frozen=True forbids assignment and makes instances hashable; slots=True (3.10+) adds __slots__; order=True adds comparisons. Mutable defaults must go through field(default_factory=...); the decorator refuses the mistake outright (last error below).

from dataclasses import dataclass, field, asdict, replace

@dataclass(frozen=True, slots=True)
class Message:
    role: str
    text: str
    tokens: int = 0

@dataclass
class Conversation:
    model: str
    messages: list[Message] = field(default_factory=list)   # a fresh list per instance

m = Message("user", "hi", 1)
print(m, m == Message("user", "hi", 1), hash(m) == hash(Message("user", "hi", 1)))
print(replace(m, text="hello"))
try:
    m.text = "changed"
except Exception as e:
    print(type(e).__name__ + ":", e)
c = Conversation("small-model")
c.messages.append(m)
print(asdict(c))
try:
    @dataclass
    class Bad:
        items: list = []
except ValueError as e:
    print("ValueError:", e)
print(Message.__slots__, hasattr(m, "__dict__"))

For data that crosses a boundary (JSON from an API, a config file) a dataclass checks nothing; its annotations are not enforced at run time. Use Pydantic there, which validates and converts; use dataclasses inside your program, where the type checker already guards the values.

__slots__ and what an object really costs

__slots__ = ("user", "n") tells CPython to reserve fixed storage for exactly those attributes and not to create a per-instance __dict__. Measured on 100,000 small records with tracemalloc (each figure includes the 8-byte slot in the list that holds them):

The measuring script and its output (c3_sizes.py)
c3_sizes.py
"""Memory for 100,000 small records, measured with tracemalloc (Python allocations only)."""
import tracemalloc
from collections import namedtuple
from dataclasses import dataclass

class Plain:
    def __init__(self, user, n): self.user, self.n = user, n
class Slotted:
    __slots__ = ("user", "n")
    def __init__(self, user, n): self.user, self.n = user, n
@dataclass
class DC:
    user: str; n: int
@dataclass(slots=True)
class DCS:
    user: str; n: int
NT = namedtuple("NT", "user n")

USERS = [f"u{i:04d}" for i in range(200)]       # shared strings, not counted per record
N = 100_000
kinds = [("class", Plain), ("class + __slots__", Slotted), ("dataclass", DC),
         ("dataclass(slots=True)", DCS), ("namedtuple", NT), ("tuple", lambda u, n: (u, n)),
         ("dict", lambda u, n: {"user": u, "n": n})]
for name, make in kinds:
    tracemalloc.start()
    rows = [make(USERS[i % 200], i % 250) for i in range(N)]   # small ints are cached: no int allocation
    cur, _ = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    del rows
    print(f"{name:22} {cur / N:6.1f} bytes per record")

Slots save 40 bytes per record here (96 against 56). The gap used to be larger: since 3.11 "Objects now require less memory due to lazily created object namespaces" ({{What's new in 3.11|https://docs.python.org/3/whatsnew/3.11.html}}), so a plain instance no longer builds a full dict up front. The costs of slots: no new attributes at run time (the AttributeError below), and some care with multiple inheritance. Use them for classes with millions of instances; ignore them otherwise.

Descriptors: how property, methods and self work

A descriptor is an object stored on a class that defines __get__ (and optionally __set__ and __delete__). When attribute lookup finds one on the class, it calls it instead of returning it ({{Descriptor guide|https://docs.python.org/3/howto/descriptor.html}}). One with __set__ is a data descriptor, and the order is fixed: "data descriptors always override instance dictionaries. However, non-data descriptors can be overridden by instance dictionaries" ({{Invoking descriptors|https://docs.python.org/3/reference/datamodel.html#invoking-descriptors}}). The full lookup for obj.x (the fourth row of the hero; step each outcome in the explorer of section 1, group "Attribute lookup"):

  1. a data descriptor named x on type(obj) or its MRO (for example a property);
  2. otherwise obj.__dict__["x"];
  3. otherwise a non-data descriptor (a plain function, which becomes a bound method) or plain class attribute;
  4. otherwise __getattr__, if the class defines it; otherwise AttributeError.

This one mechanism explains a lot of "magic". property is a data descriptor, which is why assigning to a read-only property fails instead of shadowing it. A function is a non-data descriptor: s.describe calls describe.__get__(s, Sampling), which returns a bound method that remembers s and passes it as self. Frameworks (Django fields, SQLAlchemy columns, Pydantic) are descriptors with validation inside, like the Positive below.

c4_descriptor.py
class Positive:
    """A reusable validated attribute: a data descriptor (it defines __set__)."""
    def __set_name__(self, owner, name):
        self.name = "_" + name
    def __get__(self, obj, owner):
        if obj is None:
            return self                    # accessed on the class itself
        return getattr(obj, self.name)
    def __set__(self, obj, value):
        if value <= 0:
            raise ValueError(f"{self.name[1:]} must be > 0, got {value}")
        setattr(obj, self.name, value)

class Sampling:
    temperature = Positive()
    max_tokens = Positive()
    def __init__(self, temperature, max_tokens):
        self.temperature = temperature     # goes through Positive.__set__
        self.max_tokens = max_tokens
    @property                              # property is a data descriptor too
    def budget(self):
        return self.max_tokens * 4
    def describe(self):
        return f"t={self.temperature} max={self.max_tokens}"

s = Sampling(0.7, 256)
print(s.describe(), s.budget, vars(s))
try:
    s.temperature = 0
except ValueError as e:
    print("ValueError:", e)
try:
    s.budget = 1
except AttributeError as e:
    print("AttributeError:", e)

# A method is a function stored on the class; looking it up on an instance binds it.
f = Sampling.__dict__["describe"]
print(type(f).__name__, type(s.describe).__name__)
bound = f.__get__(s, Sampling)            # exactly what s.describe does
print(bound(), bound.__self__ is s, bound.__func__ is f)
print(s.describe is s.describe, s.describe == s.describe)   # a new bound method each time
Why obj.method() does not build a bound method (bytecode)

The last line above shows that s.describe builds a new bound-method object each time. The direct call form obj.method() skips it: the compiler emits one LOAD_ATTR that pushes the function and self separately, shown as describe + NULL|self below, so no bound-method object is built; the optimisation was called LOAD_METHOD when it arrived in 3.7. Bytecode in general is on {{Python: CPython internals and performance|n:4055c17b0d0d8111872ad7101b7e3c22}}.

And the classic trap, a mutable class attribute, follows from step 3 of the lookup: reading a.tools finds the class's list; assigning a.tools = ... creates an instance entry that shadows it.

c5_classattr.py
class Agent:
    tools = []                    # ONE list, stored on the class, shared by all instances
    def __init__(self, name):
        self.name = name

a, b = Agent("a"), Agent("b")
a.tools.append("search")          # finds Agent.tools via the class, mutates it
print(b.tools, "tools" in vars(a))
a.tools = ["calc"]                # assignment creates an instance attribute that shadows it
print(a.tools, b.tools, Agent.tools)

Costs and habits (what it solves, what it costs, when not to)
Choose
A dataclass for plain records; a frozen dataclass for values and dict keys; Pydantic at trust boundaries; a Protocol (on the typing page) instead of a base class when you only need "has these methods".
Avoid
Inheritance for code reuse alone; metaclasses unless you are writing a framework (__init_subclass__ covers most "run code when a subclass is defined" needs); mutable class attributes.
