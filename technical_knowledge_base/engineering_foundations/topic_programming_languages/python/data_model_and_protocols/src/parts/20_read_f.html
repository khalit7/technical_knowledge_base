5. Classes: the MRO, dataclasses, slots and descriptors

A class statement runs its body like a function body, collects the names it defined into a dict, and builds a class object from it. An instance stores its own attributes (usually in obj.__dict__); everything else, methods included, lives on the class and is found by looking up the chain of classes.

Multiple inheritance and the MRO

That chain is the method resolution order (MRO), Cls.__mro__, computed by the C3 linearisation algorithm ({{The Python 2.3 MRO|https://docs.python.org/3/howto/mro.html}}): every class appears before its parents, and parents keep the order you listed them. super() means "the next class in the MRO of type(self)", not "my parent", which is what lets several mixins each run their part of setup exactly once (cooperative multiple inheritance). Fig. 5 plays c1_mro.py (its output is below the figure's section).

  1. A diamond. class Service(Logging, Caching); Logging and Caching both inherit from Base, and every class from object. The arrows point from a class to its parents: a graph, not a line.
  2. C3 turns the graph into one stack. The run printed Service.__mro__ as ['Service', 'Logging', 'Caching', 'Base', 'object']: each class before its parents, parents in the order listed. Attribute lookup and super() climb this stack from the bottom.
  3. super() follows the stack, not the parent. Service().setup() printed Service.setup ->, Logging.setup ->, Caching.setup ->, Base.setup, each class once. Logging's super() reaches Caching, a class it never names, when self is a Service.
  4. The same class on its own: a shorter stack. Logging.__mro__ printed as ['Logging', 'Base', 'object'], so Logging().setup() on its own goes straight to Base, because Logging's own MRO has no Caching in it: Logging.setup ->, then Base.setup.
  5. No consistent order, no class. class Bad(Base, Logging) lists Base before its own subclass, but C3 must put Logging before its parent Base. No order does both, so the class statement itself fails: TypeError: Cannot create a consistent method resolution order (MRO) for bases Base, Logging.

class Base:
    def setup(self):
        print("Base.setup")

class Logging(Base):
    def setup(self):
        print("Logging.setup ->"); super().setup()

class Caching(Base):
    def setup(self):
        print("Caching.setup ->"); super().setup()

class Service(Logging, Caching):
    def setup(self):
        print("Service.setup ->"); super().setup()

print([c.__name__ for c in Service.__mro__])
Service().setup()            # super() means "next in the MRO of type(self)", not "my parent"

Use this sparingly. Mixins with cooperative super() calls are fine; deep hierarchies are rarely worth it. Composition (an object that holds a Cache and a Logger) is usually easier to read and test than inheriting from both; when to choose composition over inheritance is a design question, on {{Code design|n:3ef5c17b0d0d817b99a0ff9701ff30cd}}.

Dataclasses: classes for data, without the boilerplate

@dataclass writes __init__, __repr__ and __eq__ from the annotated class attributes ({{dataclasses|https://docs.python.org/3/library/dataclasses.html}}). frozen=True forbids assignment and makes instances hashable; slots=True (3.10+) adds __slots__; order=True adds comparisons. Mutable defaults must go through field(default_factory=...); the decorator refuses the mistake outright (last error below).

from dataclasses import dataclass, field, asdict, replace

@dataclass(frozen=True, slots=True)
class Message:
    role: str
    text: str
    tokens: int = 0

@dataclass
class Conversation:
    model: str
    messages: list[Message] = field(default_factory=list)   # a fresh list per instance

m = Message("user", "hi", 1)
print(m, m == Message("user", "hi", 1), hash(m) == hash(Message("user", "hi", 1)))
print(replace(m, text="hello"))
try:
    m.text = "changed"
except Exception as e:
    print(type(e).__name__ + ":", e)
c = Conversation("small-model")
c.messages.append(m)
print(asdict(c))
try:
    @dataclass
    class Bad:
        items: list = []
except ValueError as e:
    print("ValueError:", e)
print(Message.__slots__, hasattr(m, "__dict__"))

For data that crosses a boundary (JSON from an API, a config file) a dataclass checks nothing; its annotations are not enforced at run time. Use Pydantic there, which validates and converts; use dataclasses inside your program, where the type checker already guards the values.

__slots__ and what an object really costs

__slots__ = ("user", "n") tells CPython to reserve fixed storage for exactly those attributes and not to create a per-instance __dict__. Measured on 100,000 small records with tracemalloc (each figure includes the 8-byte slot in the list that holds them), in Fig. 6.

Slots save 40 bytes per record here (96 against 56). The gap used to be larger: since 3.11 "Objects now require less memory due to lazily created object namespaces" ({{What's new in 3.11|https://docs.python.org/3/whatsnew/3.11.html}}), so a plain instance no longer builds a full dict up front. The costs of slots: no new attributes at run time (the AttributeError below), and some care with multiple inheritance. Use them for classes with millions of instances; ignore them otherwise.

c3_sizes.py
"""Memory for 100,000 small records, measured with tracemalloc (Python allocations only)."""
import tracemalloc
from collections import namedtuple
from dataclasses import dataclass

class Plain:
    def __init__(self, user, n): self.user, self.n = user, n
class Slotted:
    __slots__ = ("user", "n")
    def __init__(self, user, n): self.user, self.n = user, n
@dataclass
class DC:
    user: str; n: int
@dataclass(slots=True)
class DCS:
    user: str; n: int
NT = namedtuple("NT", "user n")

USERS = [f"u{i:04d}" for i in range(200)]       # shared strings, not counted per record
N = 100_000
kinds = [("class", Plain), ("class + __slots__", Slotted), ("dataclass", DC),
         ("dataclass(slots=True)", DCS), ("namedtuple", NT), ("tuple", lambda u, n: (u, n)),
         ("dict", lambda u, n: {"user": u, "n": n})]
for name, make in kinds:
    tracemalloc.start()
    rows = [make(USERS[i % 200], i % 250) for i in range(N)]   # small ints are cached: no int allocation
    cur, _ = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    del rows
    print(f"{name:22} {cur / N:6.1f} bytes per record")

Descriptors: how property, methods and self work

A descriptor is an object stored on a class that defines __get__ (and optionally __set__ and __delete__). When attribute lookup finds one on the class, it calls it instead of returning it ({{Descriptor guide|https://docs.python.org/3/howto/descriptor.html}}). One with __set__ is a data descriptor, and the order is fixed: "data descriptors always override instance dictionaries. However, non-data descriptors can be overridden by instance dictionaries" ({{Invoking descriptors|https://docs.python.org/3/reference/datamodel.html#invoking-descriptors}}). Fig. 7 climbs the full lookup for obj.x (the fourth stack of Fig. 1) with the classes of two real runs.

  1. Four places, in a fixed order. For obj.x Python tries: a data descriptor named x on type(obj) or its MRO (for example a property); otherwise obj.__dict__["x"]; otherwise a non-data descriptor (a plain function, which becomes a bound method) or plain class attribute; otherwise __getattr__, if the class defines it; otherwise AttributeError. The blocks are what d2_dispatch.py's class K and its instance o hold: K.d is a data descriptor, K.nd a non-data one, K.plain a string, and o.__dict__ has entries d and nd.
  2. o.d: the data descriptor wins. The first plate already holds d, and it has __set__, so the run logged call Data.__get__(o, K) and returned 'from data descriptor'; o.__dict__['d'], one plate up, is never consulted.
  3. o.nd: the instance dict beats a non-data descriptor. K.nd has no __set__, so the climb goes on to o.__dict__ and returns 'instance dict nd'; NonData.__get__ never runs. Methods are non-data descriptors, which is why obj.method = something shadows a method on one instance.
  4. o.plain: the class. Not a data descriptor and not in o.__dict__, so the value on the class is returned as is: 'class attribute'. This is how methods and class constants are found, and how a mutable class attribute ends up shared.
  5. o.missing: __getattr__, last. All three places miss, so the run logged call K.__getattr__('missing'), which returned 'made up for missing'. __getattr__ is called only after normal lookup fails (unlike __getattribute__, which runs for every access); use it for proxies and lazy attributes.
  6. A method is found on the class and bound. Now c4_descriptor.py's Sampling. Its instance s holds only {'_temperature': 0.7, '_max_tokens': 256}; describe is a plain function on the class (third plate), and looking it up calls its __get__, which returns a bound method: the run printed function method, the type on the class and the type you get.
  7. Writes meet the data descriptors first. temperature and max_tokens are Positive descriptors and budget is a property, all on the first plate, so assignment goes through them: ValueError: temperature must be > 0, got 0, and AttributeError: property 'budget' of 'Sampling' object has no setter instead of a new entry in s.__dict__.

This one mechanism explains a lot of "magic". property is a data descriptor, which is why assigning to a read-only property fails instead of shadowing it (step 7). A function is a non-data descriptor: s.describe calls describe.__get__(s, Sampling), which returns a bound method that remembers s and passes it as self. Frameworks (Django fields, SQLAlchemy columns, Pydantic) are descriptors with validation inside, like the Positive below.

The code (c4_descriptor.py)
c4_descriptor.py
class Positive:
    """A reusable validated attribute: a data descriptor (it defines __set__)."""
    def __set_name__(self, owner, name):
        self.name = "_" + name
    def __get__(self, obj, owner):
        if obj is None:
            return self                    # accessed on the class itself
        return getattr(obj, self.name)
    def __set__(self, obj, value):
        if value <= 0:
            raise ValueError(f"{self.name[1:]} must be > 0, got {value}")
        setattr(obj, self.name, value)

class Sampling:
    temperature = Positive()
    max_tokens = Positive()
    def __init__(self, temperature, max_tokens):
        self.temperature = temperature     # goes through Positive.__set__
        self.max_tokens = max_tokens
    @property                              # property is a data descriptor too
    def budget(self):
        return self.max_tokens * 4
    def describe(self):
        return f"t={self.temperature} max={self.max_tokens}"

s = Sampling(0.7, 256)
print(s.describe(), s.budget, vars(s))
try:
    s.temperature = 0
except ValueError as e:
    print("ValueError:", e)
try:
    s.budget = 1
except AttributeError as e:
    print("AttributeError:", e)

# A method is a function stored on the class; looking it up on an instance binds it.
f = Sampling.__dict__["describe"]
print(type(f).__name__, type(s.describe).__name__)
bound = f.__get__(s, Sampling)            # exactly what s.describe does
print(bound(), bound.__self__ is s, bound.__func__ is f)
print(s.describe is s.describe, s.describe == s.describe)   # a new bound method each time
Why obj.method() does not build a bound method (bytecode)

The last line above shows that s.describe builds a new bound-method object each time. The direct call form obj.method() skips it: the compiler emits one LOAD_ATTR that pushes the function and self separately, shown as describe + NULL|self below, so no bound-method object is built; the optimisation was called LOAD_METHOD when it arrived in 3.7. Bytecode in general is on {{Python: CPython internals and performance|n:4055c17b0d0d8111872ad7101b7e3c22}}.

And the classic trap, a mutable class attribute, follows from the third plate of the lookup: reading a.tools finds the class's list; assigning a.tools = ... creates an instance entry that shadows it.

a, b = Agent("a"), Agent("b")

print(b.tools, "tools" in vars(a))
a.tools = ["calc"]                # assignment creates an instance attribute that shadows it

Costs and habits (what it solves, what it costs, when not to)
Choose
A dataclass for plain records; a frozen dataclass for values and dict keys; Pydantic at trust boundaries; a Protocol (on the typing page) instead of a base class when you only need "has these methods".
Avoid
Inheritance for code reuse alone; metaclasses unless you are writing a framework (__init_subclass__ covers most "run code when a subclass is defined" needs); mutable class attributes.
