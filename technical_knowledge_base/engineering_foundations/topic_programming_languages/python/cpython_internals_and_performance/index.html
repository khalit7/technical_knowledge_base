The idea in one screen

CPython runs your code as bytecode in a loop written in C, and every value is a separate heap object, so a Python loop pays an interpreter step and new objects for every element. Speed comes from moving the loop out of Python (into built-ins, NumPy or native code), and from measuring first to find the one loop that matters.

Fig. 1 is the same reduction over a million floats, the denominator of a softmax: 47.6 ms as a Python loop, 3.2 ms as one NumPy call. Times are the real p2_numpy run of section 4 (CPython 3.14.8, NumPy 2.5.3, Apple M1 Pro); sizes are sys.getsizeof from section 2. The figure draws 8 of the million elements.

  1. A list holds pointers, not numbers. xs is one 8-byte pointer per element, and each pointer leads to a separate float object somewhere on the heap: 24 bytes holding a reference count, a pointer to its type and the 8-byte double. That is 32 bytes per number, against 8. The addresses in the figure are illustrative.
  2. The interpreter visits every element. The C evaluation loop runs the body of for x in xs: s += math.exp(x - m) once per element, follows the pointer, checks the type, and makes 3 new float objects each time (x - m, the exp, the new s). A million times: 47.6 ms.
  3. NumPy keeps the numbers in one buffer. np.exp(a - a.max()).sum() is one Python call; inside it, a.max(), the subtraction, exp and sum are each one tight C loop over a contiguous buffer of 8-byte doubles, with no object per element (the script's comment counts three passes; with a.max() it is four). 3.2 ms.
  4. Same answer, 14.9 times faster. The script asserts that the two sums agree to one part in a million. The speed-up is the per-element interpreter step and the per-element objects removed; section 4 shows it only appears from about a thousand elements up.

Fig. 2 puts the remedies this page measures on one scale. The specialising interpreter (section 1) is already in the "Python loop" time; the JIT (section 5) is off by default.

1. Bytecode, and how it rewrites itself while running

CPython, the standard Python, is a C program. It compiles your source to bytecode, instructions for a virtual stack machine (cached in __pycache__/*.pyc), and an evaluation loop in C executes them one by one. The root page's How code runs section follows one line through Python, C++, Rust and JavaScript; this section is CPython's half, seen with the dis module.

Since 3.11 the interpreter is specialising and adaptive (PEP 659): after an instruction has run a few times it is rewritten in place into a version specialised for the types it saw, guarded by a cheap check; if the check starts failing, it falls back and re-specialises. "Python 3.11 is between 10-60% faster than Python 3.10", 1.25x on average (What's new in 3.11, vendor figure), largely from this. dis.dis(f, adaptive=True) shows the live, rewritten instructions.

Fig. 3 runs one function, total(xs), which sums a list with s = s + x: its frame, its value stack and the six real instructions of its loop (from code/i1_dis.py on Python 3.14.8; stack effects as dis.stack_effect reports them, code/stack_effects.py, run on Python 3.12, the version available on the machine that drew this figure; the fused 3.14 instruction LOAD_FAST_BORROW_LOAD_FAST_BORROW is described from its argument, not measured).

  1. One frame, one value stack. Calling total(xs) makes a frame: the local variables xs, s and x in fixed slots, and a value stack that instructions push to and pop from. GET_ITER has already replaced the list on the stack with an iterator. The figure is the fourth pass of the warm-up call total(list(range(1000))), so s is 0 + 1 + 2 = 3.
  2. FOR_ITER, then STORE_FAST x. FOR_ITER pushes the iterator's next item, 3 (stack effect +1, the iterator stays below it); STORE_FAST pops it into the slot x (-1).
  3. LOAD_FAST_BORROW_LOAD_FAST_BORROW (s, x). One instruction, whose argument names both locals, pushes s and x: 3 and 3.
  4. BINARY_OP (+). Pops two values and pushes their sum, 6 (-1). This generic instruction must find out at run time what + means for these two objects; a sum above 256 would also be a new int object (section 2's small-int cache).
  5. STORE_FAST s, JUMP_BACKWARD. Pops 6 into s, and the back-edge returns to FOR_ITER. Six instructions per element, each one trip round the C evaluation loop: the per-element cost of Fig. 1.
  6. Specialised after 1,000 ints. After the warm-up call the instructions were rewritten in place: BINARY_OP_ADD_INT adds two ints directly after a cheap type check; FOR_ITER_LIST walks a list without the general iterator protocol; JUMP_BACKWARD_NO_JIT is the specialised back-edge (the JIT is off). Outside the loop, RESUME became RESUME_CHECK.
  7. Floats arrive: re-specialised. After 100 calls on lists of 0.5, the int guard failed, the instruction fell back and was specialised again: BINARY_OP_ADD_FLOAT. Code whose types keep changing pays for this churn; code with stable types stays on the fast path.

JUMP_BACKWARD_NO_JIT is the loop's back-edge on a build where the experimental JIT is off, which is the default in 3.14 (What's new in 3.14); section 5 turns it on and measures it. The lesson for speed: hot loops whose types never change are the ones CPython can specialise, and even specialised, each element still costs several instructions.

2. What objects cost

Every value is a heap object with a header: a reference count and a pointer to its type, 16 bytes on a 64-bit build. Fig. 4 draws objects to scale, one byte to one unit of length, from sys.getsizeof on Python 3.14.8 (the full output is in the closed block below).

  1. A C int64: 8 bytes. In C, and in a NumPy int64 array, a number is only its value.
  2. A float: 24 bytes. The 16-byte header, the reference count and a pointer to the type object float (one object that every float points at), then the 8-byte double.
  3. An int: 28 bytes. After the header, a size field and the digits, 30 bits in each 4-byte digit, because ints are arbitrary precision. 0 and 1 both take 28 bytes: a Python int is 28 bytes where a C int64 is 8.
  4. 4 more bytes per 30 bits. 2**30 needs a second digit (32 bytes), 2**60 a third (36), 2**100 a fourth (40).

A str stores 1, 2 or 4 bytes per character for the whole string, chosen by its widest character (PEP 393); a non-ASCII string also carries a larger header, which is why 'é' (1 byte per character) costs 61 bytes against 42 for 'a', and '🙂' (4 bytes per character) 64. A list over-allocates: appends reserve spare room in steps (56, 88, 120, 184 bytes as it grows), which is why append is O(1) on average.

Reference counting and the cycle collector

When an object's count reaches zero it is freed at once, deterministically; that is why a file closed by going out of scope closes immediately in CPython. Counting cannot free a cycle (A points at B, B at A: both counts stay at 1 after your last name is gone), so a separate cycle collector (gc) periodically looks for groups of objects reachable only from each other. Predict when each object below is freed, then Fig. 5 replays the run:

i2_refcount.py
import gc, sys, weakref

class Node:
    def __init__(self, name):
        self.name, self.other = name, None

a = Node("a")
print("refcount:", sys.getrefcount(a))          # +1 for getrefcount's own argument
b = a
print("refcount:", sys.getrefcount(a))
weakref.finalize(a, print, "  a freed")          # prints when the object dies
del a
print("del a: still alive through b")
del b                                            # count hits 0: freed immediately
print("del b done")

x, y = Node("x"), Node("y")
x.other, y.other = y, x                          # a reference cycle
weakref.finalize(x, print, "  x freed")
weakref.finalize(y, print, "  y freed")
del x, y                                         # counts never reach 0
print("after del x, y: nothing freed yet")
print("gc.collect() found", gc.collect(), "unreachable objects")
print("thresholds:", gc.get_threshold())

Fig. 5 follows i2_refcount.py line by line; each step quotes what the run printed (Python 3.14.8). The stacked discs on an object are its reference count.

  1. a = Node("a"): one reference. The name a refers to the new object, so its count is 1. sys.getrefcount reports one more than you expect because its own argument is a reference: it printed "refcount: 2".
  2. b = a: two. A second name for the same object: "refcount: 3".
  3. del a: one. Deleting a name removes a reference, not the object: "del a: still alive through b".
  4. del b: zero, freed at once. a died the instant its last name went: its finaliser printed "a freed" before the next line, "del b done".
  5. A cycle. x.other, y.other = y, x: each object now has two references, its name and the other's .other.
  6. del x, y: both counts stay at 1. The names are gone, but each object still holds the other, so neither count reaches zero: "after del x, y: nothing freed yet".
  7. gc.collect() frees the cycle. The collector found the pair reachable only from each other and freed both ("x freed", "y freed"): the cycle survived del until gc.collect(), which reported "found 4 unreachable objects".

The thresholds (2000, 10, 10) are those of the generational collector: Python 3.14.0 to 3.14.4 shipped an incremental collector, and 3.14.5 reverted to "the generational GC from 3.13" after "reports of significant memory pressure in production environments" (What's new in 3.14, Garbage collection).

Practical consequences: break cycles in long-lived structures (parent pointers, callbacks that capture self) or use weakref; do not rely on __del__ for clean-up (use with); and for PyTorch, a tensor held by a cycle keeps its GPU memory until the collector runs. What both mechanisms do to a process's memory (pymalloc's arenas and pools, freed memory that does not go back to the operating system, the copy-on-write cost in DataLoader workers) is Memory allocators, section 7.

3. Measure first: profiling

The order that works: measure where the time goes, fix the algorithm or data structure, push loops into code that runs in C (built-ins, re, NumPy), and only then write native code. Guessing skips the first step and usually optimises the wrong thing.

The subject is a deliberately slow version of the root page's token counter: it calls a Python function for every character and keeps per-user totals in two parallel lists (p1_slow.py, in the closed block below). cProfile (standard library) records every function call. Before reading its report:

Read tottime (time inside the function itself) first: 2.7 million calls of is_token_char, one per character, dominate. The list scans that look bad on paper (users.index) cost 23 ms, because there are only 200 users. The slow and the fast version (p1_slow.py, p1_fast.py)
p1_slow.py
def count_tokens(text):
    n, inside = 0, False
    for c in text:                          # one Python-level call per character
        tok = is_token_char(c)
        if tok and not inside:
            n += 1
        inside = tok
    return n

def per_user(lines):
    users, totals = [], []                  # parallel lists: `in` and .index() scan them
    for line in lines:
        msg = json.loads(line)
        u = msg["user"]
        if u not in users:
            users.append(u)
            totals.append(0)
        totals[users.index(u)] += count_tokens(msg["text"])
    return sorted(zip(users, totals), key=lambda p: (-p[1], p[0]))[:5]
p1_fast.py
"""The same result after reading the profile: a dict instead of list scans, and a compiled regex
instead of a Python-level loop over characters."""
import json, re
from collections import Counter
from p1_slow import make_log

TOKEN = re.compile(r"[A-Za-z0-9]+")         # the same token rule, run by the C regex engine

def per_user(lines):
    totals = Counter()
    for line in lines:
        msg = json.loads(line)
        totals[msg["user"]] += len(TOKEN.findall(msg["text"]))
    return sorted(totals.items(), key=lambda p: (-p[1], p[0]))[:5]

A deterministic profiler like cProfile adds work to each of 8 million calls, so it distorts call-heavy code: trust its ranking, not its absolute times. A sampling profiler looks at the stack a few hundred times a second and barely slows the program. Two of them:

  • py-spy: "a sampling profiler for Python programs ... without restarting the program or modifying the code in any way" (py-spy); attach to a running server with py-spy top --pid or py-spy dump. On macOS "OSX always requires running as root", which is what happened here (below). Using it on a live service, with flame graphs and off-CPU time, is Capacity planning and performance.
  • Scalene samples per line and splits time into Python and native code (and memory, if asked). Its summary for the whole slow script, which also builds the 20,000-line test log, attributes about half the run (49%) to make_log, the fake-data generator that cProfile was not asked to measure: profile the whole program, not just the function you suspect.

4. Move the loop out of Python

NumPy stores numbers in one contiguous typed buffer and runs each operation as a C loop over it, with no per-element object, method lookup or reference count. The hero's reduction (the denominator of a softmax, sum(exp(x - max(x)))) as a Python loop, as map with math.fsum, and as NumPy, from 10 to a million elements:

The script and its output (p2_numpy.py)
p2_numpy.py
"""Softmax-style work (sum of exp(x - max)) on n floats: a Python loop, a generator with
math.exp, and NumPy, plus the cost of converting the list to an array. Median of timeit repeats, in microseconds per call."""
import math, os, statistics, sys, timeit
import numpy as np

def py_loop(xs):
    m = max(xs)
    s = 0.0
    for x in xs:
        s += math.exp(x - m)
    return s

def py_builtin(xs):
    m = max(xs)
    return math.fsum(map(math.exp, (x - m for x in xs)))

def np_vec(a):
    return np.exp(a - a.max()).sum()       # three passes in C over a contiguous buffer

def us(f, arg):
    t = timeit.Timer(lambda: f(arg))
    n, _ = t.autorange()
    return statistics.median(t.repeat(5, n)) / n * 1e6

print(f"Python {sys.version.split()[0]}, NumPy {np.__version__}, load {os.getloadavg()[0]:.2f}")
print(f"{'n':>9} {'loop':>11} {'map+fsum':>11} {'numpy':>11} {'np.array(list)':>15}  numpy speed-up over loop")
for n in (10, 1_000, 100_000, 1_000_000):
    xs = [((i * 7919) % 1000) / 100 for i in range(n)]
    a = np.array(xs)
    assert abs(py_loop(xs) - np_vec(a)) < 1e-6 * py_loop(xs)
    t1, t2, t3, t4 = us(py_loop, xs), us(py_builtin, xs), us(np_vec, a), us(np.array, xs)
    print(f"{n:>9,} {t1:>9.1f}us {t2:>9.1f}us {t3:>9.1f}us {t4:>13.1f}us  {t1 / t3:6.1f}x")

Three lessons, all from the measurement. At 10 elements NumPy is slower than the loop (a fixed cost of about a microsecond per NumPy call). From a thousand elements up it is 10 to 16 times faster. And converting a Python list to an array costs about 40% of the whole Python loop: keep data in arrays from the start (load with NumPy, pandas, polars or PyTorch), or the conversion eats the gain. Clever pure Python (map, fsum) did not help: the per-element work is still Python objects.

When to drop to native code

When the profile shows a hot loop that is not array arithmetic (a tokenizer, a parser, a graph walk, a custom sampler), no library already does it, and it is called often enough to matter. Then write that one function in a compiled language and call it from Python. Rust: speeding up Python with PyO3 and maturin does exactly this, from one function to a published wheel, and compares the alternatives (Cython, Numba, mypyc, nanobind or pybind11 for C++, cffi); C++: the machine underneath shows what the CPU does underneath. The root's Benchmark tab measures the token counter in all four languages and the cost of each crossing between Python and native code: batch work so you cross once per array, not once per element.

Cheap wins first

A dict or set instead of list membership; str.join instead of += in a loop; built-ins (sum, sorted, re, collections.Counter) over hand loops; local variables in hot loops; caching (Python: the data model and protocols).

Then

NumPy or PyTorch for numbers; processes or the free-threaded build for parallel CPU work, asyncio for waiting (Python: concurrency, asyncio and the GIL); a Rust or C++ extension for the hot loop that is left.

Mistakes

Optimising without a profile; timing once (use timeit or hyperfine, take the median); trusting cProfile's absolute times; micro-benchmarking with a warm cache and deploying with a cold one.

5. The experimental JIT, on and off

A JIT (just-in-time compiler) turns hot code into machine code while the program runs. CPython's (PEP 744, since 3.13) is a copy-and-patch JIT: when the specialising interpreter of section 1 finds a hot loop, it records a trace of its micro-operations and stitches together machine-code templates ("stencils") that were compiled with LLVM when CPython itself was built, so you need no LLVM at run time. It ships compiled into the official macOS and Windows installers and the uv builds used here, but is off unless you set PYTHON_JIT=1; in 3.14 and later, sys._jit.is_enabled() tells you whether it is on.

Read Fig. 8 as: on 3.15 the JIT sped up the plain Python loops (character scanning 1.64x, float arithmetic) by about half or more, helped small-object code less, and did not help (here, slightly slowed) the generator pipeline, inside What's New's own range for 3.15 ("roughly 15% slowdown to over 100% speedup", 11-12% geometric mean on AArch64 macOS; What's new in 3.15, vendor figure). The 3.13 JIT gave the character loop about the same (1.66x); the 3.14 JIT on this machine is mostly a wash, sometimes slower. Trust the direction, not the digits: the final run was made with a load average around 10, and an earlier run the same day (src/pb/out/jit_earlier_run.txt) gave 1.5x instead of 2.4x for json_count on 3.15.

It is off by default in 3.15 too, and a 2x speed-up of a Python loop is still far from moving the loop to NumPy or Rust (section 4; the root's Benchmark tab measures the token counter in all four languages).

The mistake this avoids: measuring the JIT with one run on a busy laptop. The differences here are tens of percent; noise on a loaded machine is several percent. Run each case in several fresh processes, take medians, and record the load, as this page does.

7. Lazy imports (3.15), measured

A Python program's start-up time is mostly imports: each import finds a file, loads or compiles its bytecode and runs all its top-level code, including its own imports. A command-line tool that imports httpx, pydantic and rich at the top pays for all three even when the user only asked for --help. Until now the fix was to move imports inside functions. 3.15 adds lazy import (PEP 810): the name is bound to a lightweight proxy and the module loads the first time the name is used.

import argparse lazy import httpx # was: import httpx lazy import pydantic # was: import pydantic lazy from rich.console import Console # was: from rich.console import Console

That is the only change between the two files measured below (src/pb/lazy/). Both run the fast path, count "hello world", which needs none of the three libraries. Fig. 10 steps through what Python imports, to scale, in five or six stretches; switching mode starts again from the first import:

  1. Start-up machinery: 2.8 ms, 12 modules. _frozen_importlib_external, zipimport, encodings, encodings.utf_8 and _signal: what every Python process imports before your first line, the same in all three runs.
  2. site: 6.8 ms, 26 modules. site sets up sys.path and the environment's site-packages; also the same in every run.
  3. argparse: 4.3 ms, 10 modules. Your first line of code: import argparse, eager in all versions of the file.
  4. httpx: 46.6 ms, 153 modules. The HTTP client and everything it imports at start-up (among them http.client, ssl, socket, email, idna, zstandard), loaded although count never uses it.
  5. pydantic and rich.console: 63.4 ms, 67 modules. pydantic 16.0 ms, rich.console 47.4 ms, both loaded although unused. Three unused imports cost most of the start-up.
  6. Done: 123.9 ms of import time, 268 modules. The program printed 2. Measured without -X importtime, the whole run took 100 ms (median of 30).

What to take from it: the lazy file loads 64 of the eager file's 268 modules and the whole run takes 26 ms instead of 100 ms (hyperfine medians), and the global switch -X lazy_imports=all (or PYTHON_LAZY_IMPORTS=all) gets the same result without editing the file. The work has not disappeared: a run that uses httpx pays for it at the first use instead.

What it costs, and when not to use it
  • Errors move: a misspelled module raises at first use, not at start-up; the traceback shows both places.
  • Import side effects (a plugin registering itself, logging configured at import) happen later or never. Do not make such imports lazy; the global all mode can be filtered with sys.set_lazy_imports_filter.
  • Only at module level: lazy inside a function, a class body or a try block is a SyntaxError, and so is lazy from x import *.
  • Code that must also run on 3.14 or older cannot use the keyword (it is a SyntaxError there; see the Version explorer); list the modules in __lazy_modules__ instead, which older versions ignore.
The PEP and the release disagree on one detail
PEP 810 (status Final) describes three global modes, normal, all and none (none would force every import eager, for debugging). 3.15.0rc3 accepts only two, as What's New says:
Use normal to undo all; there is no switch that forces explicit lazy imports eager.
