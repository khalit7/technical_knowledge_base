3. Measure first: profiling

The order that works: measure where the time goes, fix the algorithm or data structure, push loops into code that runs in C (built-ins, re, NumPy), and only then write native code. Guessing skips the first step and usually optimises the wrong thing.

The subject is a deliberately slow version of the root page's token counter: it calls a Python function for every character and keeps per-user totals in two parallel lists (p1_slow.py, in the closed block below). cProfile (standard library) records every function call. Before reading its report:

[[out:p1_profile|python p1_profile.py: cProfile on per_user(), then both versions timed without it (real output, Python 3.14.8)]]

Read tottime (time inside the function itself) first: 2.7 million calls of is_token_char, one per character, dominate. The list scans that look bad on paper (users.index) cost 23 ms, because there are only 200 users. The fix follows the profile: count with a compiled regular expression (the loop over characters then runs inside the C regex engine) and keep totals in a dict (a Counter). Same answer (the script asserts it), 206 ms down to 74 ms.

The slow and the fast version (p1_slow.py, p1_fast.py)

cProfile made the program 7 times slower; the fix it pointed to made it 2.8 times faster

A deterministic profiler like cProfile adds work to each of 8 million calls, so it distorts call-heavy code: trust its ranking, not its absolute times. A sampling profiler looks at the stack a few hundred times a second and barely slows the program. Two of them:

  • py-spy: "a sampling profiler for Python programs ... without restarting the program or modifying the code in any way" ({{py-spy|https://github.com/benfred/py-spy}}); attach to a running server with py-spy top --pid or py-spy dump. On macOS "OSX always requires running as root", which is what happened here (below). Using it on a live service, with flame graphs and off-CPU time, is {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}}.
  • Scalene samples per line and splits time into Python and native code (and memory, if asked). Its summary for the whole slow script, which also builds the 20,000-line test log, attributes about half the run (49%) to make_log, the fake-data generator that cProfile was not asked to measure: profile the whole program, not just the function you suspect.

4. Move the loop out of Python

NumPy stores numbers in one contiguous typed buffer and runs each operation as a C loop over it, with no per-element object, method lookup or reference count. The hero's reduction (the denominator of a softmax, sum(exp(x - max(x)))) as a Python loop, as map with math.fsum, and as NumPy, from 10 to a million elements:

NumPy loses at 10 elements and wins 10 to 16 times from a thousand up

The script and its output (p2_numpy.py)
[[run:p2_numpy]]

Three lessons, all from the measurement. At 10 elements NumPy is slower than the loop (a fixed cost of about a microsecond per NumPy call). From a thousand elements up it is 10 to 16 times faster. And converting a Python list to an array costs about 40% of the whole Python loop: keep data in arrays from the start (load with NumPy, pandas, polars or PyTorch), or the conversion eats the gain. Clever pure Python (map, fsum) did not help: the per-element work is still Python objects.

When to drop to native code

When the profile shows a hot loop that is not array arithmetic (a tokenizer, a parser, a graph walk, a custom sampler), no library already does it, and it is called often enough to matter. Then write that one function in a compiled language and call it from Python. {{Rust: speeding up Python with PyO3 and maturin|n:4055c17b0d0d81048311c87e9b76a78a}} does exactly this, from one function to a published wheel, and compares the alternatives (Cython, Numba, mypyc, nanobind or pybind11 for C++, cffi); {{C++: the machine underneath|n:4055c17b0d0d811fa947ee576a97a516}} shows what the CPU does underneath. The root's {{Benchmark|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} tab measures the token counter in all four languages and the cost of each crossing between Python and native code: batch work so you cross once per array, not once per element.

Cheap wins first

A dict or set instead of list membership; str.join instead of += in a loop; built-ins (sum, sorted, re, collections.Counter) over hand loops; local variables in hot loops; caching ({{Python: the data model and protocols|n:4055c17b0d0d816a8705e4d3f20b3da7}}).

Then

NumPy or PyTorch for numbers; processes or the free-threaded build for parallel CPU work, asyncio for waiting ({{Python: concurrency, asyncio and the GIL|n:4055c17b0d0d81bdbee8c37d80b55a0e}}); a Rust or C++ extension for the hot loop that is left.

Mistakes

Optimising without a profile; timing once (use timeit or hyperfine, take the median); trusting cProfile's absolute times; micro-benchmarking with a warm cache and deploying with a cold one.
