7. Lazy imports (3.15), measured

A Python program's start-up time is mostly imports: each import finds a file, loads or compiles its bytecode and runs all its top-level code, including its own imports. A command-line tool that imports httpx, pydantic and rich at the top pays for all three even when the user only asked for --help. Until now the fix was to move imports inside functions. 3.15 adds lazy import ({{PEP 810|https://peps.python.org/pep-0810/}}): the name is bound to a lightweight proxy and the module loads the first time the name is used.

import argparse lazy import httpx # was: import httpx lazy import pydantic # was: import pydantic lazy from rich.console import Console # was: from rich.console import Console

That is the only change between the two files measured below (src/pb/lazy/). Both run the fast path, count "hello world", which needs none of the three libraries. Fig. 10 steps through what Python imports, to scale, in five or six stretches; switching mode starts again from the first import:

  1. Start-up machinery: 2.8 ms, 12 modules. _frozen_importlib_external, zipimport, encodings, encodings.utf_8 and _signal: what every Python process imports before your first line, the same in all three runs.
  2. site: 6.8 ms, 26 modules. site sets up sys.path and the environment's site-packages; also the same in every run.
  3. argparse: 4.3 ms, 10 modules. Your first line of code: import argparse, eager in all versions of the file.
  4. httpx: 46.6 ms, 153 modules. The HTTP client and everything it imports at start-up (among them http.client, ssl, socket, email, idna, zstandard), loaded although count never uses it.
  5. pydantic and rich.console: 63.4 ms, 67 modules. pydantic 16.0 ms, rich.console 47.4 ms, both loaded although unused. Three unused imports cost most of the start-up.
  6. Done: 123.9 ms of import time, 268 modules. The program printed 2. Measured without -X importtime, the whole run took 100 ms (median of 30).
  1. Start-up machinery: 5.0 ms, 12 modules. The same 12 modules every process imports before your first line.
  2. site: 5.0 ms, 26 modules. Also the same in every run.
  3. argparse: 4.7 ms, 10 modules. Still eager in this file. The three lazy lines only bind proxies; nothing is loaded for them.
  4. locale and shutil: 4.2 ms, 16 modules. Loaded only when argparse first needs them while parsing the command line. (In the eager run an earlier import had already brought them in, so they never appeared on their own.)
  5. Done: 18.9 ms of import time, 64 modules. The program printed 2; the whole run took 26 ms (median of 30). httpx, pydantic and rich were never loaded: the count path never touched the names.

  2. site: 4.7 ms, 26 modules. Also the same in every run.
  3. argparse: 1.5 ms, 1 module. With every import lazy, even argparse's own imports wait until it uses them, so argparse itself is one module here.
  4. re, gettext, locale and shutil: 7.3 ms, 21 modules. argparse's own imports, loaded when parsing first needs them.
  5. Done: 16.5 ms of import time, 60 modules. The eager file, unedited, run with -X lazy_imports=all: the whole run took 26 ms (median of 30), and httpx, pydantic and rich were never loaded.

What to take from it: the lazy file loads 64 of the eager file's 268 modules and the whole run takes 26 ms instead of 100 ms (hyperfine medians), and the global switch -X lazy_imports=all (or PYTHON_LAZY_IMPORTS=all) gets the same result without editing the file. The work has not disappeared: a run that uses httpx pays for it at the first use instead.

What it costs, and when not to use it
  • Errors move: a misspelled module raises at first use, not at start-up; the traceback shows both places.
  • Import side effects (a plugin registering itself, logging configured at import) happen later or never. Do not make such imports lazy; the global all mode can be filtered with sys.set_lazy_imports_filter.
  • Only at module level: lazy inside a function, a class body or a try block is a SyntaxError, and so is lazy from x import *.
  • Code that must also run on 3.14 or older cannot use the keyword (it is a SyntaxError there; see the {{Version explorer|#t-ver}}); list the modules in __lazy_modules__ instead, which older versions ignore.
The PEP and the release disagree on one detail
PEP 810 (status Final) describes three global modes, normal, all and none (none would force every import eager, for debugging). 3.15.0rc3 accepts only two, as What's New says:
Use normal to undo all; there is no switch that forces explicit lazy imports eager.
