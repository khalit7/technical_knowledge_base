1. Names, objects and references

A Python object is a block of memory that knows its type, its value and how many references point at it. A name (a variable) is an entry in a namespace, a dict-like table from strings to objects. Assignment, b = a, writes a second entry pointing at the same object. Nothing is copied. Two names for one object are aliases.

Whether aliasing matters depends on mutability: whether the object can change after it is made. Lists, dicts, sets and most of your own classes are mutable. Ints, floats, strings, tuples, frozensets and bytes are immutable: every "change" builds a new object and rebinds the name.

n1_alias.py
a = [1, 2]
b = a              # a second name for the same list object
b.append(3)
print(a, a is b)

x = 10
y = x
y += 1             # ints are immutable: += builds a new int and rebinds y
print(x, y)

Copying: shallow and deep

A shallow copy makes a new outer container whose slots point at the same inner objects. A deep copy copies recursively, keeping a memo so that an object shared twice in the original is shared twice in the copy too. Passing arguments: the function gets the object, not a copy

Python passes a reference to the object (sometimes called "call by sharing"). A function can mutate the caller's object, but rebinding its own parameter name changes nothing outside. Default values are evaluated once, when def runs, so a mutable default is shared by every call.

    acc.append(x)

Here is a small vector class that implements a handful of these, and the built-ins that start working as a result. Nothing inherits from anything: Python's polymorphism is by protocol (the methods you have), not by declared parent class.

d1_vec.py
class Vec:
    def __init__(self, *xs):
        self.xs = tuple(xs)
    def __repr__(self):                 # what the REPL and debuggers show
        return f"Vec{self.xs}"
    def __len__(self):                  # len(v)
        return len(self.xs)
    def __iter__(self):                 # for, list(), unpacking, sum()
        return iter(self.xs)
    def __getitem__(self, i):           # v[i], v[1:]
        return self.xs[i]
    def __eq__(self, other):            # ==
        if not isinstance(other, Vec):
            return NotImplemented       # "I don't know": let Python try the other side
        return self.xs == other.xs
    def __hash__(self):                 # dict keys, set members; must agree with ==
        return hash(self.xs)
    def __add__(self, other):           # v + w
        if not isinstance(other, Vec):
            return NotImplemented
        return Vec(*(a + b for a, b in zip(self.xs, other.xs, strict=True)))
    def __radd__(self, other):          # 0 + v, which sum() does first
        return self if other == 0 else NotImplemented
    def __bool__(self):                 # if v:
        return any(self.xs)

v, w = Vec(1, 2), Vec(3, 4)

Read the last three lines carefully. sum() starts from the integer 0, so it first computes 0 + Vec(1, 2); int.__add__ does not know Vec and returns NotImplemented, so Python tries the right operand's __radd__. v == (1, 2) is False rather than an error because both sides returned NotImplemented and Python fell back to identity. And v + 1 raises TypeError only after both sides declined.

NotImplemented is not NotImplementedError
Returning the singleton NotImplemented means "I do not handle this type; ask the other operand". Raising NotImplementedError means "this abstract method was not written" and stops the dispatch dead. Mixing them up is a common bug in operator methods.

Three rules people learn the hard way

  • Special methods are looked up on the type, not the instance. "Implicit invocations of special methods are only guaranteed to work correctly if defined on an object's type, not in the object's instance dictionary" (Special method lookup). Setting x.__len__ = ... on one object does nothing for len(x). This lets CPython skip the instance dict on every operator.
  • A subclass on the right goes first. "If the operands are of different types, and the right operand's type is a direct or indirect subclass of the left operand's type, the reflected method of the right operand has priority" (same page). So a subclass can override how it combines with its parent from either side.
  • __eq__ and __hash__ travel together. "A class that overrides __eq__() and does not define __hash__() will have its __hash__() implicitly set to None" (same page). Objects that compare equal must have equal hashes, and a hash must not change while the object is in a dict or set; that is why mutable built-ins are unhashable and why a dict key should be immutable.

The Data model tab replays 19 of these dispatches step by step, each from a real run that logged which method Python called, in order: the reflected and subclass-first cases of +, == falling back to identity, bool falling back to __len__, the old __getitem__ iteration protocol, with swallowing an exception, and the four outcomes of an attribute lookup.

What it solves
Your types plug into every built-in, library and syntax form: sorted, sum, dict, f-strings, with, PyTorch's __torch_function__, NumPy's __array__.
What it costs
Every operator is a method lookup and call; that is a large part of why pure-Python arithmetic is slow (section 11).
When not to
Do not overload operators with surprising meanings; + should combine, == should compare. Prefer a dataclass (section 5) when you only need __init__, __repr__ and __eq__.

3. Iterators and generators: laziness as a protocol

Two words that are easy to blur. An iterable is anything you can loop over: it has __iter__, which returns a fresh iterator each time. An iterator is the cursor: it has __next__, which returns the next item or raises StopIteration, and its __iter__ returns itself. A list is an iterable; iter(list) is an iterator. The difference shows up when you loop twice (Iterator types).

g1_protocol.py
nums = [1, 2, 3]
it = iter(nums)                 # list.__iter__ returns a NEW list_iterator
print(type(it).__name__, next(it), next(it), next(it))
try:
    next(it)
except StopIteration:
    print("StopIteration: the iterator is used up")

squares = (n * n for n in nums) # a generator is an iterator: one pass only
print(sum(squares), sum(squares))
print(sum(nums), sum(nums))     # a list is an iterable: each for/sum gets a fresh iterator

A generator function is a function containing yield. Calling it runs none of its body; it returns a generator, an iterator whose __next__ runs the body until the next yield, hands that value out, and freezes the function's local variables until it is asked again. A generator expression, (f(x) for x in xs), is the one-line form.

Lazy pipelines: one item at a time through every stage

Write each processing stage as a generator and chain them, and items flow through the whole chain one at a time. Write the same stages as functions that return lists, and each stage finishes before the next begins, holding every intermediate result. The program below does both on three lines of a chat log (the root page's running example: count tokens per user). The animation replays its real printed trace.

Steps are the lines printed by code/g2_order.py (below), in order. "Held" counts items stored in the lists that exist at that moment: the eager version keeps each stage's whole list until the next stage has consumed it.
g2_order.py
import json
LINES = ['{"user": "a", "text": "hi there"}', 'oops', '{"user": "b", "text": "ok"}']

# Eager: each stage builds and returns a full list. Lazy: the same stages with yield.
def read_list(lines):
    out = []
    for line in lines:
        print("  read  ", line[:12]); out.append(line)
    return out
def parse_list(lines):
    out = []
    for line in lines:
        try:
            msg = json.loads(line)
        except json.JSONDecodeError:
            print("  parse  skip"); continue
        print("  parse ", msg["user"]); out.append(msg)
    return out
def count_list(msgs):
    out = []
    for m in msgs:
        n = len(m["text"].split()); print("  count ", m["user"], n); out.append(n)
    return out

def read_gen(lines):
    for line in lines:
        print("  read  ", line[:12]); yield line
def parse_gen(lines):
    for line in lines:
        try:
            msg = json.loads(line)

        print("  parse ", msg["user"]); yield msg

print("eager (lists):")

print("lazy (generators):")
print("total", sum(count_gen(parse_gen(read_gen(LINES)))))

At this size the difference is cosmetic. At a million lines it is the difference between fitting in memory and not: the same token count, eager and lazy, with Python's own allocation tracker (tracemalloc) reporting the peak.

g3_memory.py
"""Peak memory of the same token count, eager lists against a lazy generator pipeline.
1,000,000 synthetic lines made on the fly; tracemalloc measures Python allocations."""
import tracemalloc

N = 1_000_000
def lines():
    for i in range(N):
        yield f'{{"user": "u{i % 200:04d}", "text": "token number {i} here"}}'

def eager():
    rows = list(lines())                         # every line in memory
    words = [len(r.split()) for r in rows]       # plus a list of counts
    return sum(words)

def lazy():
    return sum(len(r.split()) for r in lines())  # one line at a time

for fn in (eager, lazy):
    tracemalloc.start()
    total = fn()
    cur, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    print(f"{fn.__name__:5}  total={total}  peak={peak / 1024:9,.1f} KiB")

yield from, and generators that receive values

yield from sub hands control to a sub-generator until it finishes, passing values (and anything sent in) straight through, and evaluates to the sub-generator's return value (PEP 380). Generators can also receive: g.send(v) resumes the generator and makes the paused yield expression evaluate to v. This "coroutine" use of generators is how asyncio was first built; today you will meet it mostly in library internals.

g4_yield_from.py
def flatten(xs):
    for x in xs:
        if isinstance(x, list):
            yield from flatten(x)       # delegate to a sub-generator
        else:
            yield x

print(list(flatten([1, [2, [3, 4]], 5])))

def worker():
    total = 0
    while (x := (yield)) is not None:   # receives values sent in
        total += x
    return total                        # becomes the value of `yield from`

def manager(results):
    results.append((yield from worker()))

res = []
g = manager(res)
next(g)                                 # run to the first yield
for v in (10, 20, 30):
    g.send(v)
try:
    g.send(None)
except StopIteration:
    pass
print(res)

Streaming tokens like an LLM client

An LLM SDK's streaming response is a generator (or, in async code, an async generator, section 10): each iteration waits for the next chunk from the network. The part to get right is cleanup. If the consumer stops early, the generator is left paused inside its loop; its finally block runs when the generator is closed, either explicitly with close() (which raises GeneratorExit at the paused yield) or when it is garbage-collected. Close it yourself, or wrap it in contextlib.closing, when it holds a connection.

g5_stream.py
"""A generator that streams tokens the way an LLM client does, and what happens
when the consumer stops early: the generator's finally block still runs."""
import time

def fake_model(prompt):
    tokens = ["Py", "thon", " gener", "ators", " stream", " lazily", "."]
    print("[open connection]")
    try:
        for t in tokens:
            time.sleep(0.01)          # stands in for network latency
            yield t
    finally:
        print("[close connection]")   # runs on exhaustion, on close(), and on garbage collection

out = []
for tok in fake_model("hi"):
    out.append(tok)
print(repr("".join(out)))

stream = fake_model("hi")
for i, tok in enumerate(stream):
    if i == 2:
        break                         # stop after three tokens
print("consumer stopped")
stream.close()                        # raises GeneratorExit inside the generator
print("after close")

What it solves
Constant memory over unbounded input; work starts before the input ends; one stage per function.
What it costs
Single use (a consumed iterator is silently empty), harder debugging (nothing runs until something consumes), a little per-item overhead.
When not to
When you need the data twice, random access, or len: materialise a list once, deliberately.

4. Functions, closures and decorators

def is a statement that runs: it builds a function object (code, defaults, a reference to the enclosing scope) and binds it to a name. Functions are values like any other: you can pass them, return them and store them in dicts. Three consequences follow.

Parameters: positional-only, keyword-only and the catch-alls

A / in the parameter list makes everything before it positional-only; a * makes everything after it keyword-only. *args collects extra positional arguments into a tuple and **kwargs extra keyword arguments into a dict. Keyword-only parameters are the cheap way to stop callers from passing 0.2 to the wrong slot.

Closures: functions that remember variables

A function defined inside another can read the outer function's variables after the outer one has returned; it keeps them in cells, visible as __closure__. Two rules cause most closure bugs. A closure captures the variable, not its value at the time, so it sees whatever the variable holds when it finally runs (late binding). And any assignment to a name inside a function makes that name local to the whole function, unless you declare it nonlocal (enclosing function) or global (module).

Decorators

A decorator is a function that takes a function and returns a replacement; @timed above def work means exactly work = timed(work). Decorators stack bottom-up: the one nearest def is applied first. Always wrap with functools.wraps, or the replacement loses the original's name, docstring and signature (and tools such as pytest, FastAPI and debuggers see "wrapper").

f2_decorator.py
import functools, time

def timed(fn):                                # a decorator: takes a function, returns one
    @functools.wraps(fn)                      # copy __name__, __doc__, __wrapped__ ...
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            print(f"{fn.__name__} took {time.perf_counter() - t0:.3f} s")
    return wrapper

@timed                                        # same as: work = timed(work)
def work(n):
    """Sum of squares."""
    return sum(i * i for i in range(n))

print(work(1_000_000))
print(work.__name__, work.__doc__, work.__wrapped__.__name__)

def no_wraps(fn):
    def wrapper(*a, **k):
        return fn(*a, **k)
    return wrapper

@no_wraps
def other():
    """Docs that will be lost."""
print(other.__name__, other.__doc__)

A decorator with arguments, @retry(times=4), is one level deeper: retry(times=4) runs first and returns the actual decorator. This is the shape of a real retry helper for a model API: retry only errors that can succeed on a second try (connection resets, timeouts, rate limits), with exponential backoff and random jitter, and never retry a 400.

f3_retry.py
import functools, random, time

def retry(times=3, base_delay=0.01, on=(ConnectionError, TimeoutError)):
    """A decorator WITH arguments is a function that returns a decorator."""
    def decorate(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            for attempt in range(1, times + 1):
                try:
                    return fn(*args, **kwargs)
                except on as e:
                    if attempt == times:
                        raise                     # out of attempts: re-raise the last error
                    delay = base_delay * 2 ** (attempt - 1) * random.uniform(0.5, 1.5)
                    print(f"attempt {attempt} failed ({e!r}); retrying in {delay * 1000:.0f} ms")
                    time.sleep(delay)
        return wrapper
    return decorate

random.seed(0)

@retry(times=4)

    calls["n"] += 1
    if calls["n"] < 3:
        raise ConnectionError("upstream reset")
    return f"answer to {prompt!r}"

print(flaky_completion("hello"))

@retry(times=2)

    raise ValueError("400: bad request")          # not in `on`: never retried
try:
    bad_request()
except ValueError as e:
    print("not retried:", e)

Caching pitfalls
Arguments become a dict key, so they must be hashable (the TypeError above). The cache holds strong references to every argument and result, so lru_cache on a method keeps each self alive "until they age out of the cache or until the cache is cleared" (with cache, which never evicts, for the life of the process); for methods without arguments the Python FAQ suggests functools.cached_property, which lives and dies with the instance. And a cache is invisible state: a function whose result depends on time, a file or a random seed must not be cached.
What it solves
Cross-cutting behaviour (timing, retries, caching, auth, registration in a framework such as FastAPI's @app.get) written once.
What it costs
An extra call per invocation, and indirection when reading a stack trace.
When not to
When a plain function call at the call site would be clearer, or when the decorator changes the function's signature in ways type checkers cannot follow.

5. Classes: inheritance, the MRO, dataclasses, slots and descriptors

A class statement runs its body like a function body, collects the names it defined into a dict, and builds a class object from it. An instance stores its own attributes (usually in obj.__dict__); everything else, methods included, lives on the class and is found by looking up the chain of classes.

Multiple inheritance and the MRO

That chain is the method resolution order (MRO), Cls.__mro__, computed by the C3 linearisation algorithm (The Python 2.3 MRO): every class appears before its parents, and parents keep the order you listed them. super() means "the next class in the MRO of type(self)", not "my parent", which is what lets several mixins each run their part of setup exactly once (cooperative multiple inheritance). The same Logging class calls a different "next" depending on the object it is working for:

Descriptors: how property, methods and self work

A descriptor is an object stored on a class that defines __get__ (and optionally __set__ and __delete__). When attribute lookup finds one on the class, it calls it instead of returning it (Descriptor guide). One with __set__ is a data descriptor, and the order is fixed: "data descriptors always override instance dictionaries. However, non-data descriptors can be overridden by instance dictionaries" (Invoking descriptors). The full lookup for obj.x:

  1. a data descriptor named x on type(obj) or its MRO (for example a property);
  2. otherwise obj.__dict__["x"];
  3. otherwise a non-data descriptor (a plain function, which becomes a bound method) or plain class attribute;
  4. otherwise __getattr__, if the class defines it; otherwise AttributeError.

This one mechanism explains a lot of "magic". property is a data descriptor, which is why assigning to a read-only property fails instead of shadowing it. A function is a non-data descriptor: s.describe calls describe.__get__(s, Sampling), which returns a bound method that remembers s and passes it as self. Frameworks (Django fields, SQLAlchemy columns, Pydantic) are descriptors with validation inside, like the Positive below.

c4_descriptor.py
class Positive:
    """A reusable validated attribute: a data descriptor (it defines __set__)."""
    def __set_name__(self, owner, name):
        self.name = "_" + name
    def __get__(self, obj, owner):
        if obj is None:
            return self                    # accessed on the class itself
        return getattr(obj, self.name)
    def __set__(self, obj, value):
        if value <= 0:
            raise ValueError(f"{self.name[1:]} must be > 0, got {value}")
        setattr(obj, self.name, value)

class Sampling:
    temperature = Positive()
    max_tokens = Positive()
    def __init__(self, temperature, max_tokens):
        self.temperature = temperature     # goes through Positive.__set__
        self.max_tokens = max_tokens
    @property                              # property is a data descriptor too
    def budget(self):
        return self.max_tokens * 4
    def describe(self):
        return f"t={self.temperature} max={self.max_tokens}"

except ValueError as e:

6. Typing for real code

Annotations (x: int, -> str) are stored on the function and otherwise ignored when the program runs. A separate type checker reads them and reports contradictions before you run anything. The two used on this page are mypy (the reference checker, written in Python, version 2.4.0) and ty (Astral's checker, written in Rust, beta, version 0.0.84); comparing them, and pyright, across a whole project is Part 2's job. Here is what the type system can express and what it actually catches.

The tools you will actually use

  • Built-in generics and unions: list[str], dict[str, int], str | None (no imports since 3.9 and 3.10).
  • Generic functions and classes, with the 3.12 syntax: def first[T](xs: Sequence[T]) -> T (PEP 695). T is a type variable: whatever type goes in, the same comes out.
  • Protocol (PEP 544): structural typing, "anything with a close() method", checked statically. It is duck typing made checkable, and usually the right tool where you would have written an abstract base class.
  • TypedDict (PEP 589): the shape of a plain dict, such as a chat message; NotRequired marks optional keys. Still a plain dict at run time.
  • Literal: an exact set of allowed values, Literal["system", "user", "assistant"].
  • @overload: several signatures for one function whose return type depends on the argument type.
  • Abstract parameter types, concrete return types: accept Iterable, Sequence or Mapping (from collections.abc), return list or dict.

7. Exceptions done well

An exception is an object; raise unwinds the stack until an except clause whose class matches (by isinstance, in the order written). Since 3.11 a try that raises nothing costs nothing ("zero-cost" exceptions, What's new in 3.11), so "ask forgiveness, not permission" (try it and catch the failure) is not a performance sin.

The hierarchy, and what except Exception does not catch

Everything derives from BaseException. Ordinary errors derive from its subclass Exception; four do not, on purpose, so that a broad except Exception: lets them through: KeyboardInterrupt (Ctrl-C), SystemExit (sys.exit()), GeneratorExit (section 3) and, since 3.8, asyncio.CancelledError (section 10). Give your own library one root exception so callers can catch "anything from this client" with one clause, and specific subclasses carrying data (here retry_after) for the cases callers handle differently.

8. Context managers: with

with m as r: calls m.__enter__(), binds its return value to r, runs the body, and then always calls m.__exit__(exc_type, exc, tb), with the exception if one was raised and Nones if not. If __exit__ returns a true value the exception is swallowed. It is try/finally packaged as an object, for anything that must be released: files, locks, connections, GPU memory pools, timers, temporary settings such as torch.no_grad().

contextlib.contextmanager writes the class for you from a generator: the code before yield is __enter__, the code after it (in a finally) is __exit__. Several managers in one with are entered left to right and exited right to left. ExitStack handles a number of resources known only at run time (contextlib).

x1_with.py
import contextlib, time

class Timer:
    def __enter__(self):
        self.t0 = time.perf_counter()
        return self                                   # bound to the name after `as`
    def __exit__(self, exc_type, exc, tb):
        self.ms = (time.perf_counter() - self.t0) * 1000
        print(f"Timer exit: exc_type={exc_type.__name__ if exc_type else None}")
        return False                                  # do not swallow exceptions

with Timer() as t:
    sum(range(100_000))
print(f"{t.ms:.1f} ms")

@contextlib.contextmanager                            # the same protocol, written as a generator
def opened(name):
    print(f"open {name}")
    try:
        yield name.upper()                            # the value bound by `as`
    finally:
        print(f"close {name}")                        # runs even if the body raises

        print("body", a, b)
        raise KeyError("oops")
except KeyError:
    print("KeyError reached the caller")              # ...exited right to left

with contextlib.ExitStack() as stack:                 # a number of resources known only at run time
    names = [stack.enter_context(opened(n)) for n in ("x", "y", "z")]

9. Concurrency: threads, the GIL and processes

Three words first. Concurrency is having several tasks in progress at once; parallelism is running several at the same instant on different CPU cores. A program can be concurrent without being parallel: one cook with three pans. And work is CPU-bound if it is limited by computing (parsing, tokenising, maths in Python) or I/O-bound if it spends its time waiting (network calls, disk, a model API).

CPython's default build has a global interpreter lock (GIL): "the mechanism used by the CPython interpreter to assure that only one thread executes Python bytecode at a time" (glossary). Threads are real operating-system threads, but only the one holding the GIL runs Python code. A thread releases it while it waits for I/O or sleeps, and C extensions such as NumPy release it during long computations. So: threads give concurrency for waiting, not parallelism for Python computing. Processes each have their own interpreter and their own GIL, so they compute in parallel, at the cost of start-up time and of pickling (serialising) every argument and result between processes.

The same CPU job (count primes by trial division, four times) and the same I/O job (four 200 ms waits), each run serially, on four threads and on four processes, best of three:

"""The same CPU-bound job and the same I/O-bound job, run serially, on 4 threads and on 4 processes.
Wall-clock seconds, best of 3. CPU job: count primes below 250,000 by trial division, 4 times.
Pool start-up is inside the timing, as it is in a real script."""
import os, sys, sysconfig, time
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

def count_primes(limit):                 # pure-Python CPU work: holds the GIL while it runs
    n = 0
    for k in range(2, limit):
        for d in range(2, int(k ** 0.5) + 1):
            if k % d == 0:
                break
        else:
            n += 1
    return n

    time.sleep(0.2)
    return 1

def pool(kind, fn, args):
    with kind(max_workers=4) as ex:
        return list(ex.map(fn, args))

def best(f, reps=3):
    ts = []
    for _ in range(reps):
        t0 = time.perf_counter(); f(); ts.append(time.perf_counter() - t0)
    return min(ts)

        print(f"{name:16} {best(f):6.3f} s")

10. asyncio from the event loop up

An event loop is a loop on one thread that keeps a queue of tasks ready to run and a list of things being waited for (sockets, timers). It runs a ready task until that task says "I am waiting for X", then runs the next ready task; when X happens, the waiting task goes back on the ready queue. Nothing is interrupted: a task gives up the thread only at an await. That is cooperative multitasking.

The pieces: async def defines a coroutine function; calling it runs nothing and returns a coroutine object, a paused computation. await c runs c until it finishes, suspending the current coroutine whenever c waits. A task (asyncio.create_task(c)) wraps a coroutine and schedules it on the loop to run concurrently with the others. asyncio.run(main()) creates a loop, runs main to completion and closes the loop.

import asyncio, inspect

A real HTTP fan-out against a local server

The common LLM-application pattern: call an API many times concurrently, but not unboundedly. The server and client below use only the standard library (asyncio.start_server and asyncio.open_connection); the server answers GET /delay/100 after 100 ms, standing in for a model API. Twenty calls:

a3_fanout.py
"""A real HTTP fan-out against a local server, standard library only.
The server answers GET /delay/<ms> after <ms> milliseconds (like a slow model API).
The client opens a TCP connection per request with asyncio.open_connection."""
import asyncio, time

async def handle(reader, writer):              # one coroutine per incoming connection
    request_line = (await reader.readline()).decode()
    while (await reader.readline()) not in (b"\r\n", b""):
        pass                                   # skip headers
    ms = int(request_line.split()[1].rsplit("/", 1)[1])
    await asyncio.sleep(ms / 1000)
    body = f"slept {ms} ms".encode()
    writer.write(b"HTTP/1.1 200 OK\r\nContent-Length: %d\r\nConnection: close\r\n\r\n%s" % (len(body), body))
    await writer.drain()
    writer.close()

async def get(port, path):
    reader, writer = await asyncio.open_connection("127.0.0.1", port)
    writer.write(f"GET {path} HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n".encode())
    await writer.drain()
    raw = await reader.read()                  # read until the server closes
    writer.close()
    await writer.wait_closed()
    return raw.split(b"\r\n\r\n", 1)[1].decode()

async def main():
    server = await asyncio.start_server(handle, "127.0.0.1", 0)
    port = server.sockets[0].getsockname()[1]
    delays = [100] * 20                        # 20 calls of 100 ms each

    t0 = time.perf_counter()
    for d in delays:
        await get(port, f"/delay/{d}")         # one after another
    print(f"sequential, 20 calls      {time.perf_counter() - t0:6.3f} s")

    t0 = time.perf_counter()
    bodies = await asyncio.gather(*(get(port, f"/delay/{d}") for d in delays))
    print(f"gather, 20 at once        {time.perf_counter() - t0:6.3f} s   {bodies[0]!r}")

    limit = asyncio.Semaphore(5)               # at most 5 in flight: be polite to the API
    async def polite(d):
        async with limit:
            return await get(port, f"/delay/{d}")
    t0 = time.perf_counter()
    await asyncio.gather(*(polite(d) for d in delays))
    print(f"gather, at most 5 at once {time.perf_counter() - t0:6.3f} s")

    t0 = time.perf_counter()
    async with asyncio.TaskGroup() as tg:      # 3.11+: same speed, and cancels siblings on failure
        tasks = [tg.create_task(get(port, f"/delay/{d}")) for d in delays]
    print(f"TaskGroup, 20 at once     {time.perf_counter() - t0:6.3f} s   {len(tasks)} results")

    t0 = time.perf_counter()
    try:
        async with asyncio.timeout(0.25):      # one slow call (2 s) with a 250 ms budget
            await get(port, "/delay/2000")
    except TimeoutError:
        print(f"timeout after             {time.perf_counter() - t0:6.3f} s")

    server.close()
    await server.wait_closed()

Cancellation and timeouts

task.cancel() does not stop a task immediately; it arranges for CancelledError to be raised inside it at its current await, so its finally blocks and async with exits run. A timeout is a cancellation that the timeout block turns into TimeoutError. The rule: if you catch CancelledError to clean up, re-raise it. A coroutine that swallows it reports success to whoever cancelled it, and TaskGroup and timeout stop working around it.

a4_cancel.py
import asyncio

async def worker(name):
    try:
        print(f"{name}: working")
        await asyncio.sleep(10)
    except asyncio.CancelledError:
        print(f"{name}: cancelled, cleaning up")
        raise                                   # always re-raise CancelledError
    finally:
        print(f"{name}: finally")

async def swallower():
    try:
        await asyncio.sleep(10)
    except asyncio.CancelledError:
        print("swallower: caught CancelledError and returned (a bug)")
        return "pretends to have finished"

async def main():
    t = asyncio.create_task(worker("w1"))
    await asyncio.sleep(0.01)                   # let it start
    t.cancel()                                  # request: CancelledError is raised at its await
    try:
        await t
    except asyncio.CancelledError:
        print("main: w1 is cancelled:", t.cancelled())

    s = asyncio.create_task(swallower())
    await asyncio.sleep(0.01)
    s.cancel()
    print("main: swallower result:", await s, "| cancelled():", s.cancelled())

    try:
        async with asyncio.timeout(0.05):       # a timeout is a cancellation plus a TimeoutError
            await worker("w2")
    except TimeoutError:
        print("main: w2 timed out")

asyncio.run(main())

Async generators: streaming responses

An async def containing yield is an async generator (PEP 525), consumed with async for. It is exactly how the async LLM SDKs expose a streamed response: each step awaits the next chunk, so other tasks (here a ticker) keep running between tokens. Close it with aclose() when you stop early, so its clean-up runs now and not whenever the garbage collector gets to it.

a5_stream.py
"""Async generators: how LLM SDKs stream tokens. The consumer uses `async for`."""
import asyncio, time

async def stream_tokens(text, delay=0.02):
    try:
        for tok in text.split(" "):
            await asyncio.sleep(delay)          # waiting for the next chunk from the network
            yield tok + " "
    finally:
        print("\n[stream closed]")

async def ticker(stop):
    n = 0
    while not stop.is_set():
        await asyncio.sleep(0.02)
        n += 1
    return n

async def main():
    stop = asyncio.Event()
    tick = asyncio.create_task(ticker(stop))    # other work keeps running while we stream
    t0 = time.perf_counter()
    async for tok in stream_tokens("the event loop interleaves waiting, never computing"):
        print(tok, end="", flush=True)
    stop.set()
    print(f"streamed in {time.perf_counter() - t0:.2f} s; the ticker ran {await tick} times meanwhile")

    agen = stream_tokens("stop me after two tokens please")
    got = []
    async for tok in agen:
        got.append(tok)
        if len(got) == 2:
            break                               # leaves the generator suspended
    await agen.aclose()                         # run the generator's finally now, not at GC
    print("got", got)

asyncio.run(main())

11. CPython internals you can see

CPython, the standard Python, is a C program. It compiles your source to bytecode, instructions for a virtual stack machine (cached in __pycache__/*.pyc), and an evaluation loop in C executes them one by one. The root page's How code runs section follows one line through Python, C++, Rust and JavaScript; here we look inside CPython's half.

Bytecode, and how it rewrites itself while running

The dis module prints a function's bytecode. Since 3.11 the interpreter is specialising and adaptive (PEP 659): after an instruction has run a few times it is rewritten in place into a version specialised for the types it saw, guarded by a cheap check; if the check starts failing, it falls back and re-specialises. "Python 3.11 is between 10-60% faster than Python 3.10", 1.25x on average (What's new in 3.11), largely from this. dis.dis(f, adaptive=True) shows the live, rewritten instructions. Step through the same function before running, after 1,000 integer additions, and after floats arrive:

The lesson for speed: hot loops whose types never change are the ones CPython can specialise.

Reference counting and the cycle collector

Every object carries a count of references to it. When the count reaches zero the object is freed at once, deterministically; that is why a file closed by going out of scope closes immediately in CPython. Counting cannot free a cycle (A points at B, B at A: both counts stay at 1 after your last name is gone), so a separate cycle collector (gc) periodically looks for groups of objects reachable only from each other.

i2_refcount.py
import gc, sys, weakref

class Node:
    def __init__(self, name):
        self.name, self.other = name, None

a = Node("a")
print("refcount:", sys.getrefcount(a))          # +1 for getrefcount's own argument
b = a
print("refcount:", sys.getrefcount(a))
weakref.finalize(a, print, "  a freed")          # prints when the object dies
del a
print("del a: still alive through b")
del b                                            # count hits 0: freed immediately
print("del b done")

x, y = Node("x"), Node("y")
x.other, y.other = y, x                          # a reference cycle
weakref.finalize(x, print, "  x freed")
weakref.finalize(y, print, "  y freed")
del x, y                                         # counts never reach 0
print("after del x, y: nothing freed yet")
print("gc.collect() found", gc.collect(), "unreachable objects")
print("thresholds:", gc.get_threshold())

Practical consequences: break cycles in long-lived structures (parent pointers, callbacks that capture self) or use weakref; do not rely on __del__ for clean-up (use with); and for PyTorch, a tensor held by a cycle keeps its GPU memory until the collector runs.

Every object has a header (a reference count and a type pointer, 16 bytes on a 64-bit build), so a Python int is 28 bytes where a C int64 is 8, and a list of a million floats is a million pointers to a million separate 24-byte objects (NumPy stores 8 bytes each, contiguously). The last line is a list's over-allocation: appends reserve spare room in steps, which is why append is O(1) on average.

12. Performance: measure, then move the loop out of Python

The order that works: measure where the time goes, fix the algorithm or data structure, push loops into code that runs in C (built-ins, re, NumPy), and only then write native code. Guessing skips the first step and usually optimises the wrong thing.

Vectorising with NumPy

NumPy stores numbers in one contiguous typed buffer and runs each operation as a C loop over it, with no per-element object, method lookup or reference count. The same reduction (the denominator of a softmax, sum(exp(x - max(x)))) as a Python loop, as map with math.fsum, and as NumPy, from 10 to a million elements:

p2_numpy.py
"""Softmax-style work (sum of exp(x - max)) on n floats: a Python loop, a generator with
math.exp, and NumPy, plus the cost of converting the list to an array. Median of timeit repeats, in microseconds per call."""
import math, os, statistics, sys, timeit
import numpy as np

def py_loop(xs):
    m = max(xs)
    s = 0.0
    for x in xs:
        s += math.exp(x - m)
    return s

def py_builtin(xs):
    m = max(xs)
    return math.fsum(map(math.exp, (x - m for x in xs)))

def np_vec(a):
    return np.exp(a - a.max()).sum()       # three passes in C over a contiguous buffer

def us(f, arg):
    t = timeit.Timer(lambda: f(arg))
    n, _ = t.autorange()
    return statistics.median(t.repeat(5, n)) / n * 1e6

print(f"Python {sys.version.split()[0]}, NumPy {np.__version__}, load {os.getloadavg()[0]:.2f}")
print(f"{'n':>9} {'loop':>11} {'map+fsum':>11} {'numpy':>11} {'np.array(list)':>15}  numpy speed-up over loop")

When to drop to native code

When the profile shows a hot loop that is not array arithmetic (a tokenizer, a parser, a graph walk, a custom sampler), no library already does it, and it is called often enough to matter. Then write that one function in a compiled language and call it from Python. The Rust page, Part 2 (Speeding up Python) does exactly this with PyO3 and maturin, from one function to a published wheel, and compares the alternatives (Cython, Numba, mypyc, nanobind or pybind11 for C++, cffi); the C++ page (Part 2) shows what the machine does underneath. The root's Benchmark tab measures the running program in all four languages and the cost of each crossing between Python and native code: batch work so you cross once per array, not once per element.

Cheap wins first
A dict or set instead of list membership; str.join instead of += in a loop; built-ins (sum, sorted, re, collections.Counter) over hand loops; local variables in hot loops; caching (section 4).
Then
NumPy or PyTorch for numbers; processes or the free-threaded build for parallel CPU work (section 9); asyncio for waiting (section 10); a Rust or C++ extension for the hot loop that is left.
Mistakes
Optimising without a profile; timing once (use timeit or hyperfine, take the median); trusting cProfile's absolute times; micro-benchmarking with a warm cache and deploying with a cold one.

The event loop, one step at a time

Three coroutines, A, B and C, each wait for something: 100, 200 and 300 ms. The same three, run four ways. Every step below is a real event from code/a2_trace.py (code at the bottom), stamped with the loop's clock in milliseconds and drawn to scale on a 0 to 620 ms axis, so the four modes can be compared by eye. Reading section 10 explains the terms.

Legend: thin bar, suspended at an await (the thread is free); thick dark bar, holding the thread; thick orange bar, a blocking call; dot, the moment a timer is due. The top lane shows what the one thread is doing.
What to notice
  • 1 against 2: the same coroutines; await in a loop runs them back to back (0.6 s), gather wraps each in a task so their waits overlap (0.3 s, the longest single wait).
  • 2 against 3: one time.sleep in B holds the thread for 200 ms. A's timer is due at 100 ms but A cannot resume until 200 ms; C cannot even start until 200 ms. Total 0.5 s. Nothing crashed and nothing warned: a blocked loop is silent unless debug mode is on (Reading section 10).
  • 3 against 4: await asyncio.to_thread(time.sleep, 0.2) runs the same blocking call in a worker thread; B suspends like any other await, and the total is back to 0.3 s.

The code

a2_trace.py
"""Three coroutines, four ways of running them. Every event is stamped with the event
loop's clock (ms since the run started); the Event loop tab replays these traces."""
import asyncio, json, sys, time

EV = []
def ev(who, what, note=""):
    EV.append([who, what, round((time.perf_counter() - T0) * 1000, 1), note])

async def fetch(name, secs):
    ev(name, "start")
    ev(name, "await", f"asyncio.sleep({secs})")
    await asyncio.sleep(secs)                  # suspends: control goes back to the loop
    ev(name, "resume")
    ev(name, "done")
    return name

async def fetch_blocking(name, secs):
    ev(name, "start")
    ev(name, "block", f"time.sleep({secs})")
    time.sleep(secs)                           # blocks the whole thread: no other coroutine can run
    ev(name, "done")
    return name

async def fetch_thread(name, secs):
    ev(name, "start")
    ev(name, "await", f"asyncio.to_thread(time.sleep, {secs})")
    await asyncio.to_thread(time.sleep, secs)  # the blocking call runs in a worker thread
    ev(name, "resume")
    ev(name, "done")
    return name

JOBS = [("A", 0.10), ("B", 0.20), ("C", 0.30)]

async def sequential():
    return [await fetch(n, s) for n, s in JOBS]

async def gathered():
    return await asyncio.gather(*(fetch(n, s) for n, s in JOBS))

async def gathered_blocking():
    return await asyncio.gather(fetch("A", 0.10), fetch_blocking("B", 0.20), fetch("C", 0.30))

async def gathered_thread():
    return await asyncio.gather(fetch("A", 0.10), fetch_thread("B", 0.20), fetch("C", 0.30))

out = {}
for mode in (sequential, gathered, gathered_blocking, gathered_thread):
    EV.clear()
    T0 = time.perf_counter()
    res = asyncio.run(mode())
    total = round((time.perf_counter() - T0) * 1000, 1)
    out[mode.__name__] = {"events": list(EV), "total_ms": total, "result": res}
    print(f"{mode.__name__:18} {total:6.1f} ms  order of events: " +
          " ".join(f"{w}:{e}" for w, e, _, _ in EV))
with open(sys.argv[1] if len(sys.argv) > 1 else "/dev/null", "w") as f:
    json.dump(out, f)

    1. Why Python packaging confuses everyone: four layers

    You have used pip install for years; the reason it still surprises you is that "packaging" is four separate jobs, and each tool bundles a different subset of them. Name the layers once and every tool becomes easy to place.

    LayerThe jobTools (bold: what to use now)
    1. InterpretersInstall and pin Python itself (3.13, 3.14, 3.14t)pyenv, conda, system packages, uv python
    2. IsolationGive each project its own site-packages so projects do not share versionsvenv (standard library), virtualenv, conda environments; uv creates a venv for you
    3. Resolve and installChoose versions that satisfy every constraint, download, install, and record the resultpip, Poetry, PDM, conda, uv
    4. BuildTurn your source into files others can installsetuptools, hatchling, flit, uv_build, maturin (Rust), scikit-build-core (C and C++), meson-python

    The words you need, each once:

    • Distribution package (what pip install names, such as pydantic-core) versus import package (what import names, pydantic_core). They often differ; PyPI only knows the first.
    • PyPI: the public registry every tool downloads from by default.
    • Wheel (.whl): a zip of ready-to-copy files; installing one is unpacking. sdist (.tar.gz): the source, which must be built first, which needs a compiler when there is C or Rust inside. Installing a compiled package is quick when a wheel exists for your exact Python and platform, and slow or broken when it does not (section 6 shows the free-threaded case).
    • Version specifier (httpx>=0.28): the range your code supports. Lock file: the exact versions (and file hashes) one resolution picked, so every machine installs the same thing. Applications commit a lock file; libraries publish ranges and test against their lower bounds.
    • Resolver: the part that finds one version of every package satisfying all ranges at once. When it fails, two of your dependencies disagree about a third.
    • Build backend (uv_build, hatchling, maturin): the library that makes the wheel. Build frontend (uv build, python -m build, pip): the tool that calls it, in a clean environment, as pyproject.toml's [build-system] table says.
    • Editable install (uv pip install -e ., and what uv sync does for your own project): the environment points at your source folder, so edits take effect without reinstalling. Extras (package[fast]): optional named sets of dependencies.

    The tools you will still meet, and why each exists

    • pip ships with Python and installs into whatever environment is active, which is why forgetting to activate a venv is the classic accident. It resolves but does not lock: pip freeze > requirements.txt snapshots what happens to be installed, which is not a lock of a project definition.
    • venv (python -m venv .venv, then source .venv/bin/activate) is the standard-library isolation layer. uv still creates exactly this folder; understand it even when a tool hides it.
    • pipx installs a command-line application (black, httpie) into its own environment; uv tool install and uvx now do the same.
    • Poetry (2018) made one pyproject.toml plus a lock file normal. Its own [tool.poetry] tables predate the standard [project] table (PEP 621), which Poetry 2 adopted. You will meet it in existing repositories: learn to read its pyproject.toml and poetry.lock, and do not start new projects with it.
    • PDM and Hatch are standards-first alternatives; Hatch's build backend, hatchling, is common even where Hatch itself is not used.
    • conda (and mamba, micromamba, pixi) is a different ecosystem: it ships non-Python binaries such as CUDA toolkits, MKL and compilers from channels like conda-forge, which is why some scientific and GPU stacks still use it. If you must mix, install conda packages first and pip packages last, or the two will overwrite each other's files.
    • uv (Astral, written in Rust) collapses layers 1 to 3 and the frontend part of 4 into one fast tool. The next section uses it end to end.
    What to actually do
    Use uv for everything new. Keep pip and venv in your head because every CI example and Dockerfile you will read uses them, and recognise Poetry and conda well enough to work in a repository that already uses them.

    2. uv end to end

    uv replaces pyenv, venv, pip, pip-tools, pipx and Poetry with one binary. The root page's Toolchain atlas replays the first five commands (uv init, uv add, uv run, ruff, pytest); this section covers what you need after that: interpreters, the kinds of project, what uv sync really does, extras and groups, scripts, tools, workspaces and the pip interface.

    Interpreters

    uv downloads standalone CPython builds (from the python-build-standalone project) instead of using whatever the system has. uv python install 3.14 3.14t 3.15 installed every interpreter used on this page; t is the free-threaded build.

    In Python you would have run pyenv install and then pointed a venv at it; with uv, --python 3.15 on any command is enough, and a project's .python-version file pins it.

    Three kinds of project

    Since uv 0.12, plain uv init and uv init --app both make a packaged application: code under src/, a console script, and the uv_build backend (so uv run app-demo works). --no-package gives the old flat layout with a main.py, and --lib makes a library with a py.typed marker (it tells type checkers the package ships annotations).

    Correction to the old page
    The old "zero to expert" page said uv init myproj, uv add requests, uv run main.py. With uv 0.12.23 plain uv init creates no main.py (output above); run the console script with uv run <project-name>, or create the flat layout with uv init --app --no-package. The root page records the same correction.

    The three files that must agree

    A uv project is three things: pyproject.toml (what you asked for: ranges), uv.lock (what one resolution picked: exact versions and hashes for every platform at once, which is what "universal lock" means) and .venv (what is installed). uv add, uv lock and uv sync move them back into agreement, and uv run syncs before it runs.     What the session shows:

    • uv sync is exact: it removes anything the lock does not ask for in this sync, which is why orjson (an extra) disappeared until --extra fast was given.     • Dependency groups ([dependency-groups], PEP 735, here dev) are for you, never published; extras ([project.optional-dependencies]) are for your users (pip install tokcount[fast]). The dev group is installed by default; --no-dev leaves it out.

    Scripts with their dependencies inside (PEP 723)

    A one-file script can declare its own dependencies in a comment block; uv run script.py then builds a cached throwaway environment for it. This replaced "make a venv for this one script".

    Tools: uvx is pipx

    uvx tool@version runs a command-line tool in its own cached environment without installing it into your project; uv tool install puts it on your PATH. Every type checker on this page was run this way, pinned to an exact version.

    Workspaces: several packages, one lock

    A workspace is a repository with several packages (a library and the CLI that uses it, say) that share one uv.lock and one .venv, like a Cargo workspace in Rust. { workspace = true } makes the CLI depend on the library's source, not on a PyPI release.

    The pip interface

    For old repositories and Dockerfiles, uv venv and uv pip install behave like python -m venv and pip, only faster; nothing is locked unless you ask (uv pip compile).

    What uv costs, and when not to use it
    uv is one company's tool (Astral, which announced on 2026-03-19 that it is joining OpenAI, per the Astral blog); the code is open source under MIT and Apache-2.0.     What the grid teaches:

    • Unannotated means unchecked. A parameter without an annotation is Any, and no checker reports add_one("a") by default. mypy's --strict reports that the function has no annotations at all, which is the useful complaint.
    • Defaults differ. pyright reports a possibly unbound variable by default; ty and mypy have the rule but leave it off (--error possibly-unresolved-reference, --enable-error-code possibly-undefined).
    • Messages differ more than verdicts. On the shared cases they agree; ty and mypy add hints (list is invariant, use Sequence; "Maybe you forgot to use await?").
    • Invariance surprises everyone once: a list[int] is not a list[float], because the function could append a float to your list of ints. Accept Sequence[float] when you only read.

    Speed on a real codebase

    Which one to choose
    Speed is not the question on most projects: all three are fast enough on a hundred files. Choose by where you read the errors. If your editor is VS Code, pyright is already running (as Pylance), so using pyright in CI means CI says what the editor said. mypy has the largest plugin ecosystem (Django, SQLAlchemy, pydantic) and the most documentation. ty is the fastest and its messages are the clearest here, but it is a 0.0.x beta whose rules still change. Whichever you pick, pin its version and run it in CI; a type checker that only runs on your laptop checks nothing.

    5. pytest essentials

    pytest finds files named test_*.py, runs every function named test_*, and treats a plain assert as the check. Five features cover most real test suites; all five are in this one file, testing the root page's token-counting rule:

    • Fixtures (chat_file, defined in conftest.py so every test file can use it) are set-up functions that pytest calls for you when a test names them as a parameter. Built-in ones: tmp_path (a fresh folder per test) and monkeypatch (set an environment variable or attribute, undone after the test).
    • @pytest.mark.parametrize runs one test per row of inputs, each reported separately.
    • pytest.raises asserts that a block raises a given exception.
    • Subtests (new in pytest 9.0, 2025-11-05) check several values inside one test and report each failure separately, for cases where the values are only known at run time.
    • Configuration now lives natively in pyproject.toml under [tool.pytest] (pytest 9.0; the older [tool.pytest.ini_options] table still works), and strict = true turns on every strictness option (unknown markers and config keys become errors).

    6. Packaging and publishing: wheels, tags, ABIs and trusted publishing

    Building a pure-Python package is one command. The real output of uv build on the library made in section 2, and what is inside each file:

    The wheel is a zip with your package and a .dist-info folder (METADATA is what PyPI shows; RECORD lists every file with its hash; WHEEL holds the tag). The sdist carries the source and pyproject.toml so any installer can rebuild it.

    Reading a wheel's name

    A wheel's file name says exactly where it can be installed: name-version-python-abi-platform.whl. Pick a real file from PyPI (fetched 2026-10-05):

    • Python tag (cp314, py3): which interpreter. py3 means any Python 3, so pure Python.
    • ABI tag (cp314, cp314t, abi3, none): the ABI the compiled code was built against. A cp314 wheel loads only on CPython 3.14; cp314t only on the free-threaded 3.14t; abi3 (the stable ABI) on every CPython from the tagged version on, so one wheel per platform covers future Pythons. But abi3 does not load on free-threaded builds, which is why projects that ship abi3 wheels must still build a separate cp314t wheel, or their users on 3.14t build from source.
    • Platform tag: manylinux_2_28_x86_64 runs on any Linux with glibc 2.28 or newer (PEP 600); musllinux is for Alpine; macosx_11_0_arm64 needs macOS 11 or newer on Apple silicon; win_amd64 is 64-bit Windows.
    abi3t: the stable ABI for free-threaded builds (Python 3.15, PEP 803)
    3.15 adds abi3t, a stable ABI that free-threaded builds can load: one wheel tagged cp315-abi3.abi3t runs on both builds of 3.15 and later. Porting "usually requires some non-trivial changes to the source code" (What's New in 3.15), and free-threaded 3.14 predates it, so a project supporting 3.11 and up publishes three wheels per platform: cp311-abi3, cp314-cp314t and cp315-abi3.abi3t. What's New says build tools did not support it "at the time of writing"; the community guide, updated 2026-09-25, lists support released in CMake 4.4 with scikit-build-core 1.0, maturin 1.14 (1.14.1+ for both ABI families) and meson-python 0.21, with setuptools still under development (py-free-threading: abi3t).

    Publishing without a stored password: trusted publishing

    The old way was to create a PyPI API token and store it as a CI secret, where it can leak.     8. Lazy imports (3.15), measured

    A Python program's start-up time is mostly imports: each import finds a file, loads or compiles its bytecode and runs all its top-level code, including its own imports. A command-line tool that imports httpx, pydantic and rich at the top pays for all three even when the user only asked for --help. Until now the fix was to move imports inside functions. 3.15 adds lazy import: the name is bound to a lightweight proxy and the module loads the first time the name is used.

    import argparse lazy import httpx # was: import httpx lazy import pydantic # was: import pydantic lazy from rich.console import Console # was: from rich.console import Console

    What it costs, and when not to use it
    • Errors move: a misspelled module raises at first use, not at start-up; the traceback shows both places.
    • Import side effects (a plugin registering itself, logging configured at import) happen later or never. Do not make such imports lazy; the global all mode can be filtered with sys.set_lazy_imports_filter.
    • Only at module level: lazy inside a function, a class body or a try block is a SyntaxError, and so is lazy from x import *.
    • Code that must also run on 3.14 or older cannot use the keyword (it is a SyntaxError there; see the Version explorer); list the modules in __lazy_modules__ instead, which older versions ignore.
    The PEP and the release disagree on one detail
    PEP 810 (status Final) describes three global modes, normal, all and none (none would force every import eager, for debugging). 3.15.0rc3 accepts only two, as What's New says:
    Use normal to undo all; there is no switch that forces explicit lazy imports eager.

    9. Free-threading in practice

    The GIL (global interpreter lock) is the lock in the standard CPython build that lets only one thread run Python bytecode at a time; threads still help when they wait on I/O, but CPU-bound threads take turns (Part 1 explains threads and the GIL from the start). The free-threaded build removes it (PEP 703): experimental in 3.13, officially supported but still optional in 3.14 (PEP 779), installed separately as python3.14t (uv python install 3.14t). Check which one you are on with sys._is_gil_enabled().

    The bug the GIL was hiding (and was not preventing)

    Now the same four threads update one shared dictionary instead of their own: shared[user] = shared.get(user, 0) + n. That line reads, adds and writes back in three steps; if two threads read the same old value, one addition is lost.

    Python's documentation never promised that a read-modify-write like this is atomic under the GIL (Python FAQ); the GIL only made losing an update rare. Without the GIL the same bug happens on most runs. What the free-threaded build does guarantee is that built-in objects stay internally consistent: the dictionary never crashes or corrupts, it only holds the wrong totals. The fixes are the same on both builds: a threading.Lock around the update (exact in every run above), or, better, no shared state, which is what the scaling run did.

    Will your dependencies run without the GIL?

    A C, C++ or Rust extension must declare that it is safe without the GIL. If it does not, importing it on the free-threaded build silently turns the GIL back on for the whole process, with a warning.     What it costs, and when not to use it
    • Single-thread speed. The 3.13 HOWTO measured about 40% overhead; for 3.14, What's New says "roughly 5-10%" and the 3.14 HOWTO "about 1% on macOS aarch64 to 8% on x86-64 Linux" (pyperformance). Measured here on one workload: see the Runtime lab.
    • Memory. PEP 779 set a 20% memory overhead target for phase II; this page did not measure memory.
    • Your own thread safety. Races that the GIL made rare now happen; audit shared mutable state before switching.
    • Dependencies. One unported extension turns the GIL back on for everyone (above).
    • Not for I/O-bound work: threads already overlap waiting under the GIL, and asyncio is the usual tool for many connections.
    Whether the free-threaded build ever becomes the default ("phase III") is "left for a future PEP" (PEP 779); the old page's forecast of 3.16 to 3.17 is a guess, not a plan.

    10. The experimental JIT, on and off

    A JIT (just-in-time compiler) turns hot code into machine code while the program runs. CPython's (PEP 744, since 3.13) is a copy-and-patch JIT: when the specialising interpreter finds a hot loop, it records a trace of its micro-operations and stitches together machine-code templates ("stencils") that were compiled with LLVM when CPython itself was built, so you need no LLVM at run time. It ships compiled into the official macOS and Windows installers and the uv builds used here, but is off unless you set PYTHON_JIT=1; in 3.14 and later, sys._jit.is_enabled() tells you whether it is on.

    Read it as: on 3.15 the JIT sped up the plain Python loops (character scanning, float arithmetic) by about half or more, helped small-object code less, and did not help (here, slightly slowed) the generator pipeline, inside What's New's own range for 3.15 ("roughly 15% slowdown to over 100% speedup", 11-12% geometric mean on AArch64 macOS). The 3.14 JIT on this machine is mostly a wash, sometimes slower. Trust the direction, not the digits: the final run was made with a load average around 10, and an earlier run the same day (src/pb/out/jit_earlier_run.txt) gave 1.5x instead of 2.4x for json_count on 3.15. It is off by default in 3.15 too, and a 2x speed-up of a Python loop is still far from moving the loop to NumPy or Rust (the root's Benchmark tab measures the token counter in all four languages).

    11. Subinterpreters (3.14), measured

    A subinterpreter is a second, isolated Python interpreter inside the same process: its own modules, its own globals and, since 3.12, its own GIL (PEP 684). 3.14 exposed them in the standard library (PEP 734): concurrent.interpreters and InterpreterPoolExecutor, which has the same interface as the thread and process pools. They sit between threads and processes: parallel on the normal GIL build like processes, but cheaper to start, and like processes they share nothing by default: arguments and results cross by pickling, except immutable built-ins (None, bool, bytes, str, int, float and tuples of these), which are shared or copied cheaply, and memoryview and interpreter queues, which really share mutable data (docs).

    from concurrent.futures import InterpreterPoolExecutor with InterpreterPoolExecutor(max_workers=4) as ex: totals = list(ex.map(count_slice, parts)) # same code as with ThreadPoolExecutor

    On this job, subinterpreters and processes both clearly beat threads on the GIL build, because each worker has its own GIL; processes were somewhat faster here. Neither reached 4x with 4 workers: each worker receives 25,000 lines by pickling and returns a pickled Counter, and the machine was busy. A new subinterpreter started more than ten times faster than a spawned process, and about a hundred times slower than a thread.

    13. Common mistakes, and the rest of the old page checked

    Calling pip install inside a uv project
    It installs into whatever environment is active (often none), and the next uv sync removes anything the lock does not list. Use uv add.
    Testing a library only against the newest versions of its dependencies
    Your >= ranges promise that the oldest allowed versions work. Run the tests once with uv sync --resolution lowest-direct (lowest versions of your direct dependencies) in CI.
    Letting a tool's version float
    ruff 0.16 turned on 354 more rules overnight, and ty is a 0.0.x beta. Pin linters and type checkers in the dev group (the lock file then pins them exactly).
    Switching to the free-threaded build for I/O-bound code
    Threads already overlap waits under the GIL. The free-threaded build helps only CPU-bound Python running in several threads, and costs single-thread speed and dependency risk.
    Believing the GIL made x += 1 safe
    It made races rare, not impossible: the GIL build lost updates in section 9's measurement too. Use a lock or per-thread state.
    Measuring the JIT with one run on a busy laptop
    The differences in section 10 are tens of percent; noise on a loaded machine is several percent. Run each case in several fresh processes, take medians, and record the load, as this page does.
    Using a 3.15 feature in a library that supports 3.12
    lazy import, frozendict and [*xs for xs in ...] fail on older versions (as a SyntaxError before any line runs, for the syntax ones). Set ruff's target-version and the type checker's Python version to your minimum, and run CI on your oldest supported version.
