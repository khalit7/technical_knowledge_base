3. Free-threading in practice

The free-threaded build removes the GIL ({{PEP 703|https://peps.python.org/pep-0703/}}): experimental in 3.13, officially supported but still optional in 3.14 ({{PEP 779|https://peps.python.org/pep-0779/}}), installed separately as python3.14t (uv python install 3.14t). Check which one you are on with sys._is_gil_enabled().

The workload is the parent topic's program: count tokens per user over 100,000 JSONL chat lines (the root's generator, seed 7), split across threads, each thread filling its own Counter that the main thread merges (src/pb/ft/). Every thread recorded when it finished each block of 1,000 lines; this is that recording, to scale, for four threads. The bug the GIL was hiding (and was not preventing)

Now the same four threads update one shared dictionary instead of their own: shared[user] = shared.get(user, 0) + n. That line reads, adds and writes back in three steps; if two threads read the same old value, one addition is lost.

Python's documentation never promised that a read-modify-write like this is atomic under the GIL ({{Python FAQ|https://docs.python.org/3/faq/library.html#what-kinds-of-global-value-mutation-are-thread-safe}}); the GIL only made losing an update rare. Without the GIL the same bug happens on most runs (the parent topic's section 9, Concurrency, measured about 70% of unsynchronised counter updates lost, {{Topic: programming-languages|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}}). What the free-threaded build does guarantee is that built-in objects stay internally consistent: the dictionary never crashes or corrupts, it only holds the wrong totals. The fixes are the same on both builds: a threading.Lock around the update (exact in every run), or, better, no shared state, which is what the scaling run did.

Will your dependencies run without the GIL?

A C, C++ or Rust extension must declare that it is safe without the GIL. If it does not, importing it on the free-threaded build silently turns the GIL back on for the whole process, with a warning. What it costs, and when not to use it
  • Single-thread speed. The 3.13 HOWTO measured about 40% overhead; for 3.14, What's New says "roughly 5-10%" and the 3.14 HOWTO "about 1% on macOS aarch64 to 8% on x86-64 Linux" (pyperformance). Measured here on one workload: .
  • Memory. PEP 779 set a 20% memory overhead target for phase II; this page did not measure memory.
  • Your own thread safety. Races that the GIL made rare now happen; audit shared mutable state before switching.
  • Dependencies. One unported extension turns the GIL back on for everyone (above).
  • Not for I/O-bound work: threads already overlap waiting under the GIL, and asyncio is the usual tool for many connections.
Whether the free-threaded build ever becomes the default ("phase III") is "left for a future PEP" (PEP 779); the old page's forecast of 3.16 to 3.17 is a guess, not a plan.
