4. Subinterpreters (3.14), measured

A subinterpreter is a second, isolated Python interpreter inside the same process: its own modules, its own globals and, since 3.12, its own GIL ({{PEP 684|https://peps.python.org/pep-0684/}}). 3.14 exposed them in the standard library ({{PEP 734|https://peps.python.org/pep-0734/}}): concurrent.interpreters and InterpreterPoolExecutor, which has the same interface as the thread and process pools. They sit between threads and processes: parallel on the normal GIL build like processes, but cheaper to start, and like processes they share nothing by default: arguments and results cross by pickling, except immutable built-ins (None, bool, bytes, str, int, float and tuples of these), which are shared or copied cheaply, and memoryview and interpreter queues, which really share mutable data ({{docs|https://docs.python.org/3.14/library/concurrent.interpreters.html}}).

from concurrent.futures import InterpreterPoolExecutor with InterpreterPoolExecutor(max_workers=4) as ex: totals = list(ex.map(count_slice, parts)) # same code as with ThreadPoolExecutor

On this job, subinterpreters and processes both clearly beat threads on the GIL build, because each worker has its own GIL; processes were somewhat faster here. Neither reached 4x with 4 workers: each worker receives 25,000 lines by pickling and returns a pickled Counter, and the machine was busy. A new subinterpreter started more than ten times faster than a spawned process, and about a hundred times slower than a thread.
