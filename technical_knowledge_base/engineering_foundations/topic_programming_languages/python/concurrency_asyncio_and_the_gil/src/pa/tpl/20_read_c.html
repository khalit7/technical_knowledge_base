2. asyncio from the event loop up

An event loop is a loop on one thread that keeps a queue of tasks ready to run and a list of things being waited for (sockets, timers). It runs a ready task until that task says "I am waiting for X", then runs the next ready task; when X happens, the waiting task goes back on the ready queue. Nothing is interrupted: a task gives up the thread only at an await. That is cooperative multitasking. Underneath, the loop asks the operating system which sockets are ready with one call (epoll on Linux, kqueue on macOS), which {{Concurrency|n:3f05c17b0d0d8112ad1af99308fa913f}} section 8 explains.

The pieces: async def defines a coroutine function; calling it runs nothing and returns a coroutine object, a paused computation. await c runs c until it finishes, suspending the current coroutine whenever c waits. A task (asyncio.create_task(c)) wraps a coroutine and schedules it on the loop to run concurrently with the others. asyncio.run(main()) creates a loop, runs main to completion and closes the loop. Three coroutines, four ways

Three coroutines wait 100, 200 and 300 ms. Awaited one after another they take 0.6 s; started together with asyncio.gather they take 0.3 s, the longest single wait. Then the middle one calls blocking time.sleep(0.2) instead of await asyncio.sleep(0.2). Every step below is a real event from a2_trace.py, stamped with the loop's clock and drawn to scale on one 0 to 620 ms axis, so the four modes compare by eye.

One blocking call freezes every task; to_thread gives the time back

Thin bar: suspended at an await (the thread is free). Thick dark bar: holding the thread. Orange bar: a blocking call. Ring: the moment a timer is due. The top lane is what the one thread is doing.
  • 1 against 2: the same coroutines; await in a loop runs them back to back (0.6 s), gather wraps each in a task so their waits overlap (0.3 s).
  • 2 against 3: one time.sleep in B holds the thread for 200 ms. A's timer is due at 100 ms but A cannot resume until 200 ms; C cannot even start until 200 ms; total 0.5 s. Nothing crashed and nothing warned: a blocked loop is silent unless debug mode is on.
  • 3 against 4: await asyncio.to_thread(time.sleep, 0.2) runs the same blocking call in a worker thread; B suspends like any other await, and the total is back to 0.3 s.

Never block the loop
"If a function performs a CPU-intensive calculation for 1 second, all concurrent asyncio Tasks and IO operations would be delayed by 1 second" ({{Developing with asyncio|https://docs.python.org/3/library/asyncio-dev.html}}). Culprits: requests, time.sleep, a synchronous database driver, a big json.loads, tokenising a long document. A real HTTP fan-out against a local server

The common LLM-application pattern: call an API many times concurrently, but not unboundedly. A standard-library server (asyncio.start_server) answers GET /delay/100 after 100 ms, standing in for a model API; the client opens a connection per request with asyncio.open_connection. Twenty calls:

Twenty sequential calls take twenty times 100 ms. gather overlaps all the waits: 0.10 s. A Semaphore(5) keeps at most five requests in flight (rate limits are real), giving four waves of 100 ms. TaskGroup (3.11+) is gather with structured clean-up: if one task fails, the others are cancelled and the errors arrive together as an ExceptionGroup. asyncio.timeout (3.11+) bounds a block of awaits: one 2 s call with a 250 ms budget stopped at 0.252 s.

Cancellation and timeouts

task.cancel() does not stop a task immediately; it arranges for CancelledError to be raised inside it at its current await, so its finally blocks and async with exits run. A timeout is a cancellation that the timeout block turns into TimeoutError. The rule: if you catch CancelledError to clean up, re-raise it. A coroutine that swallows it reports success to whoever cancelled it, and TaskGroup and timeout stop working around it. The real run: w1 re-raises, the swallower returns a value, w2 sits under a 50 ms timeout.

Async generators: streaming responses

An async def containing yield is an async generator ({{PEP 525|https://peps.python.org/pep-0525/}}), consumed with async for. It is exactly how the async LLM SDKs expose a streamed response: each step awaits the next chunk, so other tasks keep running between tokens (in the run below, a ticker task ran 7 times meanwhile). Close it with aclose() when you stop early, so its clean-up runs now and not whenever the garbage collector gets to it.
