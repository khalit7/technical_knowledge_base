7. Wheels: the file name says where it installs

Building a pure-Python package is one command (uv build, transcript in the closed block). The interesting part is the name of what it builds: name-version-python-abi-platform.whl, and an installer picks the one file whose three tags match your interpreter and machine. Pick a real file from PyPI (fetched 2026-10-05):

  • Python tag (cp314, py3): which interpreter. py3 means any Python 3, so pure Python.
  • ABI tag (cp314, cp314t, abi3, none): the ABI the compiled code was built against. A cp314 wheel loads only on CPython 3.14; cp314t only on the free-threaded 3.14t; abi3 (the stable ABI) on every CPython from the tagged version on, so one wheel per platform covers future Pythons. But abi3 does not load on free-threaded builds, which is why projects that ship abi3 wheels must still build a separate cp314t wheel, or their users on 3.14t build from source.
  • Platform tag: manylinux_2_28_x86_64 runs on any Linux with glibc 2.28 or newer (PEP 600); musllinux is for Alpine; macosx_11_0_arm64 needs macOS 11 or newer on Apple silicon; win_amd64 is 64-bit Windows.

abi3t (Python 3.15, PEP 803) is a stable ABI that free-threaded builds can load, so one cp315-abi3.abi3t wheel covers both builds of 3.15 and later; until projects port to it, a library supporting 3.11 and up ships three wheels per platform (details and tool support in the closed block).

abi3t: what it needs and which build tools support it (checked 2026-10-05 and 2026-09-25)
abi3t: the stable ABI for free-threaded builds (Python 3.15, PEP 803)
3.15 adds abi3t, a stable ABI that free-threaded builds can load: one wheel tagged cp315-abi3.abi3t runs on both builds of 3.15 and later. Porting "usually requires some non-trivial changes to the source code" ({{What's New in 3.15|https://docs.python.org/3.15/whatsnew/3.15.html}}), and free-threaded 3.14 predates it, so a project supporting 3.11 and up publishes three wheels per platform: cp311-abi3, cp314-cp314t and cp315-abi3.abi3t. What's New says build tools did not support it "at the time of writing"; the community guide, updated 2026-09-25, lists support released in CMake 4.4 with scikit-build-core 1.0, maturin 1.14 (1.14.1+ for both ABI families) and meson-python 0.21, with setuptools still under development ({{py-free-threading: abi3t|https://py-free-threading.github.io/abi3t/}}).

What a free-threaded build does to threads, and an extension that silently turns the GIL back on, are on {{Python: concurrency, asyncio and the GIL|n:4055c17b0d0d81bdbee8c37d80b55a0e}}; this section is only what the wheel must declare.

A compiled package needs one wheel per Python version (or one abi3), times free-threaded or not, times each operating system and processor: numpy 2.5.3 publishes 65 wheels. Nobody builds those by hand: cibuildwheel runs the build in CI on Linux (inside manylinux containers), macOS and Windows runners, and maturin-action does the same for Rust. Since cibuildwheel 3.1 (2025-07-23) free-threaded 3.14 wheels are built by default, so a project that does not support free-threading must skip them explicitly (cp31?t-*) ({{cibuildwheel changelog|https://cibuildwheel.pypa.io/en/stable/changelog/}}).

Publishing without a stored password: trusted publishing

The old way was a PyPI API token stored as a CI secret, where it can leak. Trusted publishing uses OpenID Connect (OIDC) and leaves no long-lived secret anywhere ({{PyPI docs|https://docs.pypi.org/trusted-publishers/}}):

Once: you tell PyPI "this repository's workflow may publish this project".
At publish time the CI service (GitHub Actions, GitLab CI/CD, Google Cloud and others) issues a short-lived signed token.
PyPI verifies the token came from that repository and workflow, and accepts the upload.

uv publish tries trusted publishing first; run from a laptop (not a CI job), it says so:

What publishing costs
A version number on PyPI can never be reused, even after deleting the file, so try uploads on TestPyPI first. Every compiled wheel you publish is a promise to keep building it for each new Python, including the free-threaded ones, and users on a platform you skip will try to compile from your sdist.
What uv build makes, file by file (the library from section 4, uv 0.12.23)

The wheel is a zip with your package and a .dist-info folder (METADATA is what PyPI shows; RECORD lists every file with its hash; WHEEL holds the tag). The sdist carries the source and pyproject.toml so any installer can rebuild it.

8. Habits that keep a project healthy

Each one comes from a failure measured or shown above:

  1. Commit uv.lock and run CI with uv sync --locked, so a stale lock fails the build (section 4, step 6).
  2. Never pip install inside a uv project. It installs into whatever environment is active (often none), and the next uv sync removes anything the lock does not list. Use uv add.
  3. Pin linters and type checkers in the dev group (the lock file then pins them exactly). ruff 0.16 turned on 354 more rules overnight, and ty is a 0.0.x beta.
  4. Pick one type checker and run it in CI, and learn which checks it leaves off by default (section 2).
  5. Test a library against its lowest allowed versions too: your >= ranges promise that the oldest versions work. Run the tests once with uv sync --resolution lowest-direct (lowest versions of your direct dependencies) in CI.
  6. Set ruff's target-version and the type checker's Python version to your minimum, and run CI on your oldest supported version: a 3.15 feature such as lazy import, frozendict or [*xs for xs in ...] fails on older versions (as a SyntaxError before any line runs, for the syntax ones). What changed in each release is on {{Python: CPython internals and performance|n:4055c17b0d0d8111872ad7101b7e3c22}}.
Designing a library that others install is {{Code design|n:3ef5c17b0d0d817b99a0ff9701ff30cd}}'s subject: its section 12 checks the py.typed marker of PEP 561 inside a real built wheel, section 5 measures pydantic's model_construct against validating, and its Further reading tab has the pre-commit file that runs ruff and the type checker at each commit.
