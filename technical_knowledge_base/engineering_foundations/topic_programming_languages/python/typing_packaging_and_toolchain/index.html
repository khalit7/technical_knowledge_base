The idea in one screen

Type hints are checked by tools before the program runs, never by Python while it runs, so they protect only the code you annotate and only when a checker runs in CI; and packaging is four separate jobs (interpreters, isolation, resolve and install, build) that uv now does as one tool, with one lock file that every machine installs from.

Fig. 1 is the picture the rest of the page fills in: who reads the hints, then which layer each tool covers. Every verdict in it is parsed from the real runs of section 1 (Python 3.14.8, mypy 2.4.0, ty 0.0.84).

  1. One file, five deliberate mistakes. t1_types.py uses every form of section 1 (def first[T](xs: Sequence[T]) -> T, a TypedDict, a Protocol, an overload), then makes five mistakes on lines 43 to 47, one tile each.
  2. The checkers read it and never run it. mypy and ty report 4 of the 5 mistakes on the exact lines (red flags on the plate above). Line 46 stays silent in both: legacy has no annotations, so its argument is "any type".
  3. Python runs it; the hints sit in __annotations__ unchecked. It ran past mistakes 1 to 3 (mistake 3 even printed "hello there", because the user happened to exist) and stopped only at mistake 4, the one that is also a runtime error: TypeError. Mistake 5 was never reached.
  4. The one crash is the one both checkers missed. Type checking protects only the code you annotate, and only when it runs: the four reports came before running, the crash only at run time.
  5. Packaging is four layers. 1 Interpreters: install and pin Python (before uv: pyenv, conda, system). 2 Isolation: one site-packages per project (venv, virtualenv). 3 Resolve, install, lock (pip, pip-tools, Poetry, PDM). 4 Build: source to wheel (setuptools, hatchling, maturin).
  6. uv covers 1 to 3 and drives 4. uv python install and .python-version; the same .venv, made for you; uv add, uv lock, uv sync; and uv build calls a backend (uv_build, maturin). Section 4 steps through its three files: pyproject.toml (the ranges you asked for), uv.lock (exact versions and hashes, every platform) and .venv (what is installed).

You need: everyday Python (Python: the essentials). The first five uv commands (uv init, uv add, uv run, ruff, pytest) and how Python's toolchain compares with Cargo, CMake and npm are replayed in the root's Toolchain atlas tab; this page starts after them.

Type checker
a program that reads annotations and reports contradictions without running the code (ty, mypy, pyright, pyrefly).
Protocol
a type that any class with the right methods satisfies, with no inheritance: duck typing a checker can verify.
Invariant
list[int] is not a list[float]: a mutable container accepts only its exact element type.
Lock file
the exact versions and file hashes one resolution picked (uv.lock, the standard pylock.toml).
Build backend, frontend
the library that makes the wheel (uv_build, hatchling, maturin); the tool that calls it (uv build, pip).
Group, extra
dependencies for you, never published ([dependency-groups]); optional dependencies for your users (pkg[fast]).
ABI tag
the part of a wheel's name saying which compiled interface it needs: cp314, cp314t, abi3, none.
Trusted publishing
uploading to PyPI with a short-lived token the CI service signs, so no password is stored anywhere.

1. Hints are read by tools, not by Python

Annotations (x: int, -> str) are stored on the function and otherwise ignored when the program runs. A type checker reads them and reports contradictions before anything runs. What the type system can say, in the forms worth using in 2026:

To sayWriteNote
Containers and "or None"list[str], dict[str, int], str | NoneBuilt-in generics and unions; no imports since 3.9 and 3.10
Same type in, same type outdef first[T](xs: Sequence[T]) -> TThe 3.12 syntax (PEP 695); T is a type variable
"Anything with a close() method"class SupportsClose(Protocol)Structural typing (PEP 544): duck typing made checkable, usually better than an abstract base class
The shape of a plain dict (a chat message)class Message(TypedDict), NotRequired[str]PEP 589; still a plain dict at run time
An exact set of valuesLiteral["system", "user", "assistant"]
A return type that depends on the argument type@overload, one signature per case
What a function accepts and returnsaccept Iterable, Sequence, Mapping; return list, dictAbstract parameter types, concrete return types

What the table shows
  • Python ran past mistakes 1 to 3 because annotations are not checked at run time; mistake 3 is a crash waiting for the day the user is missing. Both checkers caught 1, 2, 3 and 5 on the exact lines.
  • Neither caught mistake 4, the only one that crashed. legacy has no annotations, so its parameter is "any type" and anything goes; mypy by default does not even check the bodies of unannotated functions (mypy: no errors reported for obviously wrong code). Type checking protects only the code you annotate.
  • Conn never mentions SupportsClose and passes; int fails because it has no close. That is a Protocol at work.
What it buys, what it costs, the habit
Whole classes of bugs found before running (None handling, wrong keys, wrong argument order), editor completion and documentation that cannot go stale, for the time spent writing annotations, occasional fights with the checker over correct code that is hard to express, and nothing at run time. Annotate every public function and every boundary, run the checker in CI, and validate external data at run time with Pydantic, because a TypedDict on json.loads(...) is a promise, not a check (the root's Types section makes the same point for TypeScript).

2. Three checkers on the same code: where their defaults differ

Three checkers are worth knowing: mypy (the original, 2012, now 2.4.0 and actively developed), pyright (Microsoft, written in TypeScript, the engine behind VS Code's Pylance) and ty (Astral, Rust, beta since 2025-12-16, still version 0.0.84). A fourth, pyrefly (Meta, Rust), calls itself stable since 1.0.0 (1.3.2 on 2026-09-28; pyrefly), not run here. The root page shows all three agreeing on the easy case, an int where a str is expected. Here are eight harder ones: pick a case, guess which checkers flag it with default settings, then reveal their real output.

Run with --python-version 3.14 on each file separately: ty 0.0.84, mypy 2.4.0 (--no-incremental), pyright 1.1.414, all through uvx. Source: src/pb/types/run_checkers.sh. Six of the eight cases are flagged by all three; the unannotated function by none; the possibly unbound name by pyright alone.

  • Unannotated means unchecked. A parameter without an annotation is Any, and no checker reports add_one("a") by default. mypy's --strict reports that the function has no annotations at all, which is the useful complaint.
  • Defaults differ. pyright reports a possibly unbound variable by default; ty and mypy have the rule but leave it off (--error possibly-unresolved-reference, --enable-error-code possibly-undefined). Each has a strict setting: mypy --strict turns on a fixed set of extra checks (untyped definitions and calls, Any generics, unused ignores, implicit re-exports); pyright has modes off, basic, standard (the default) and strict, and a file can opt in with # pyright: strict.
  • Messages differ more than verdicts. On the shared cases they agree; ty and mypy add hints (list is invariant, use Sequence; "Maybe you forgot to use await?").
  • Invariance surprises everyone once: a list[int] is not a list[float], because the function could append a float to your list of ints. Accept Sequence[float] when you only read.

Speed on a real codebase: not the deciding factor

All three on the source of rich 15.0.0 (a well-typed terminal library: 100 files, 38,515 lines) in a 3.14 environment; hyperfine, 5 runs after a warm-up; medians ty 0.237 s, mypy 1.316 s without its cache and 0.182 s with it, pyright 5.497 s; load average 20.6 / 16.6 / 12.2. They also disagree on what is wrong: ty "Found 43 diagnostics", mypy "Found 6 errors in 4 files (checked 100 source files)", pyright "46 errors, 7 warnings, 0 informations".

Which one to choose
All three are fast enough on a hundred files, so choose by where you read the errors. If your editor is VS Code, pyright is already running (as Pylance), so pyright in CI says what the editor said. mypy has the largest plugin ecosystem (Django, SQLAlchemy, pydantic) and the most documentation. ty is the fastest and its messages are the clearest here, but it is a 0.0.x beta whose rules still change. Whichever you pick, pin its version and run it in CI; a type checker that only runs on your laptop checks nothing.

3. Packaging is four layers

You have used pip install for years; it still surprises you because "packaging" is four separate jobs (Fig. 1, steps 5 and 6), and each older tool bundles a different subset: pyenv does layer 1, venv layer 2, pip half of layer 3 (it resolves but does not lock), Poetry layers 2 and 3, setuptools layer 4. Name the layer and every tool is easy to place. Two rules follow from the layers:

  • Applications commit a lock file; libraries publish ranges (httpx>=0.28) and test against their lower bounds. A lock is the exact versions and hashes one resolution picked; pip freeze > requirements.txt snapshots what happens to be installed, which is not a lock of a project definition.
  • conda is a different ecosystem (with mamba, micromamba and pixi): it ships non-Python binaries such as CUDA toolkits, MKL and compilers from channels like conda-forge, which is why some scientific and GPU stacks still use it. If you must mix, install conda packages first and pip packages last, or the two overwrite each other's files.
What to actually do
Use uv for everything new. Keep pip and venv in your head because every CI example and Dockerfile you will read uses them, and recognise Poetry and conda well enough to work in a repository that already uses them.

  • Distribution package (what pip install names, such as pydantic-core) versus import package (what import names, pydantic_core). They often differ; PyPI only knows the first. PyPI: the public registry every tool downloads from by default.
  • Wheel (.whl) and sdist (.tar.gz): installing a compiled package is quick when a wheel exists for your exact Python and platform, and slow or broken when it does not, because the sdist needs a compiler when there is C or Rust inside (section 7).
  • Resolver: the part that finds one version of every package satisfying all ranges at once. When it fails, two of your dependencies disagree about a third.
  • Build backend and frontend: the frontend (uv build, python -m build, pip) calls the backend in a clean environment, as pyproject.toml's [build-system] table says.
  • Editable install (uv pip install -e ., and what uv sync does for your own project): the environment points at your source folder, so edits take effect without reinstalling. Extras (package[fast]): optional named sets of dependencies.
  • pip ships with Python and installs into whatever environment is active, which is why forgetting to activate a venv is the classic accident. venv (python -m venv .venv, then source .venv/bin/activate) is the standard-library isolation layer; uv still creates exactly this folder. pipx installs a command-line application into its own environment; uv tool install and uvx now do the same.
  • Poetry (2018) made one pyproject.toml plus a lock file normal. Its own [tool.poetry] tables predate the standard [project] table (PEP 621), which Poetry 2 adopted. Learn to read its pyproject.toml and poetry.lock; do not start new projects with it. PDM and Hatch are standards-first alternatives; Hatch's build backend, hatchling, is common even where Hatch itself is not used.
  • uv (Astral, written in Rust) collapses layers 1 to 3 and the frontend part of 4 into one fast tool.

4. uv: three files that must agree

A uv project is three things: pyproject.toml (what you asked for: ranges), uv.lock (what one resolution picked: exact versions and hashes for every platform at once, which is what "universal lock" means) and .venv (what is installed). uv add, uv lock and uv sync move them back into agreement, and uv run syncs before it runs. Predict before you step: when the extra orjson was installed and you then run a plain uv sync, does it stay? Fig. 2 steps through a real session, one recorded command per step:

  1. uv add, three times. httpx>=0.28 as a dependency, pytest in the dev group, orjson as the extra fast. Each call wrote the range into pyproject.toml, resolved and wrote uv.lock (15 packages) and installed into .venv. All three agree.
  2. uv run. It checks that the lock and the environment are up to date (installing anything missing), then runs the command inside .venv: httpx 0.28.1, and sys.prefix ends in .venv (True).
  3. The system python3. It does not see the project environment, so the same import fails with ModuleNotFoundError: No module named 'httpx'. Nothing was activated, and nothing needs to be when you use uv run.
  4. uv sync --locked is exact. It makes .venv match the lock for what this sync asked for: the extra fast was not requested, so orjson was uninstalled. --locked also checked that the lock still matches pyproject.toml.
  5. An edit by hand. Someone adds rich to the dependencies in pyproject.toml directly, as a pull request might. The lock (15 packages) no longer describes it.
  6. --locked refuses. Resolving now gives 18 packages against the lock's 15, so uv sync --locked exits with code 1 instead of installing. In CI this is the point: the build fails instead of silently resolving whatever versions exist today.
  7. uv lock. It re-resolves (18 packages: rich, markdown-it-py and mdurl added), and the locked sync now passes and installs them.
  8. uv sync --extra fast. Ask for the extra and orjson is installed; the lock already contained it, because a lock covers every extra, group and platform at once.
  9. A plain uv sync. It removes orjson again. If a package keeps disappearing, it is not requested by the sync you ran.
The command and real output of the current step: every one is from src/pb/uvwalk/walk_uv.sh, run with uv 0.12.23 on 2026-10-05. In .venv the figure draws only the packages the transcript names, not their dependencies.
  • uv sync is exact: it removes anything the lock does not ask for in this sync. Use --inexact to keep extra packages. uv run is the opposite: it installs what is missing but removes nothing unless you pass --exact (uv docs: locking and syncing).
  • --locked refuses a stale lock; use it in CI. --frozen goes further and installs from the lock without checking pyproject.toml at all.
  • Dependency groups ([dependency-groups], PEP 735, here dev) are for you, never published; extras ([project.optional-dependencies]) are for your users (pip install tokcount[fast]). The dev group is installed by default; --no-dev leaves it out.
  • The system python3 cannot import httpx: the project's packages live in .venv. That is what uv run does that bare python does not: sync, then run inside the project environment, no activation needed.

Beyond the basics, uv also replaces pyenv (uv python install, and since uv 0.13.0 the default interpreter is 3.15), pipx (uvx tool@version), the throwaway venv for a one-file script (PEP 723 dependencies inside the script, uv run script.py), and pip itself (uv pip); a workspace gives several packages one lock, like a Cargo workspace. How much faster, measured, and where the time goes

The same three packages (httpx, pydantic, rich and their dependencies) into a fresh Python 3.14 environment, three runs each with hyperfine (network included, so treat these as rough). Fig. 3 follows the files in each run:

  1. pip, no cache. pip downloads every wheel from PyPI and unpacks it into the new environment, every time (--no-cache-dir): 5.45 s.
  2. uv, empty cache. uv downloads the same wheels, unpacks each once into its own cache, then puts the files into the environment: 2.07 s, already 2.6x faster than pip.
  3. uv, warm cache. Nothing is downloaded or unpacked: uv puts already unpacked files from its cache into the fresh environment, 0.24 s (23x). This run forced plain copies (UV_LINK_MODE=copy in install_speed.sh); uv's default link mode is clone (copy-on-write) on macOS and Linux and hardlink on Windows (uv settings: link-mode, read 2026-11-07), so a second environment need not even copy the bytes.

What uv costs, and when not to use it
uv is one company's tool (Astral, which announced on 2026-03-19 that it is joining OpenAI, per the Astral blog); the code is open source under MIT and Apache-2.0. Its lock format is its own, though it can export the standard pylock.toml. Where a project needs non-Python binaries (a specific CUDA toolkit, MKL, GDAL), conda or pixi still solve a problem uv does not. And in a repository that already uses Poetry, switching tools is a team decision, not a drive-by change.
Common mistakes with uv
  • Running python script.py instead of uv run script.py and wondering why imports fail: the project environment is not active.
  • Editing pyproject.toml by hand and forgetting uv lock: CI with --locked catches it (step 6 of the session).
  • Not committing uv.lock for an application: every machine then resolves on its own day.
  • Putting test tools in [project.optional-dependencies]: they are then published as an extra; use a dependency group.
  • Expecting uv sync to leave packages you installed by hand with uv pip install: it removes them.

5. ruff: one linter and formatter, and a default that grew sevenfold

A linter reads code without running it and reports likely bugs and style problems; a formatter rewrites layout so nobody argues about it. ruff does both, in Rust, and replaced flake8 and its plugins, isort, pyupgrade and black. Here is a file with eight problems you have probably written yourself:

New in ruff 0.16 (2026-07-23): the default set grew from 59 to 413 rules
That is why the first run already reports isort (I), pyupgrade (UP), bugbear (B), simplify (SIM) and bandit (S) findings with no configuration at all. The release also removed 18 pycodestyle and pyflakes rules from the default set, among them E711 (== None) and E401 (two imports on one line), which appear only once selected explicitly (ruff changelog). Pin ruff in your dev group, or one upgrade can fail every CI run.
What it costs
Nothing at run time. The cost is noise: a large default rule set on an old codebase reports hundreds of findings. Adopt it with ruff check --add-noqa once (it writes suppression comments for existing findings) and fix new code only, or start from an explicit select list.
Fixing, formatting and a starting configuration (real runs, ruff 0.16.10)

--fix applied nine safe fixes (sorted and pruned imports, list for List, str | None for Optional[str], the empty f-string). The five that remain need a human: a mutable default argument (seen=[] is created once and shared by every call), a file opened without with and never closed, a try/except/pass that ruff suggests writing as contextlib.suppress, a bare except that also swallows KeyboardInterrupt, and == None (use is None). "Unsafe" fixes (--unsafe-fixes) are the ones that can change behaviour, so ruff never applies them silently.

6. pytest as a tool: discovery, fixtures and assertion rewriting

pytest finds files named test_*.py, runs every function named test_*, and treats a plain assert as the check. What to test, and how to run tests in CI, is Testing and quality's subject; this section is the tool. Predict first:

That message is pytest's assertion rewriting: at import time it rewrites each assert in test files so that a failure shows the value of every sub-expression (where 2 = tokens('max_tokens')). This is why pytest needs no assertEqual family. Five more features cover most suites; all are in the one test file in the closed block below, testing the root page's token-counting rule:

  • Fixtures (chat_file, defined in conftest.py so every test file can use it) are set-up functions pytest calls when a test names them as a parameter. Built-in ones: tmp_path (a fresh folder per test) and monkeypatch (set an environment variable or attribute, undone after the test).
  • @pytest.mark.parametrize runs one test per row of inputs, each reported separately; pytest.raises asserts that a block raises a given exception.
  • Subtests (new in pytest 9.0, 2025-11-05) check several values inside one test and report each failure separately, for values known only at run time.
  • Configuration lives natively in pyproject.toml under [tool.pytest] (pytest 9.0; the older [tool.pytest.ini_options] table still works), and strict = true turns on every strictness option (unknown markers and config keys become errors).
  • Selecting and spreading: -k selects tests by name, --co lists what would run, and -n 4 from the pytest-xdist plugin spreads tests over four worker processes. On nine tests the workers' start-up made it slower (0.37 s against 0.01 s); it pays off on suites that take minutes.

Common mistakes with pytest
  • Testing implementation details (private functions, exact call counts) instead of behaviour, so every refactor breaks tests that found no bug.
  • A fixture with scope="session" that returns a mutable object: one test's change leaks into the next.
  • Forgetting that test files are imported: module-level code in a test file runs at collection time, even for tests you deselected.
  • Running pytest instead of uv run pytest, so a global pytest without your dependencies runs the suite.

7. Wheels: the file name says where it installs

Building a pure-Python package is one command (uv build, transcript in the closed block at the end of this section). Fig. 4 follows the library of section 4 from its source to an installed package; every file name is from the recorded listings:

  1. Your source. The library uv init --lib made in section 4: pyproject.toml, README.md, src/lib_demo/__init__.py and the py.typed marker.
  2. uv build makes the sdist first. "Building source distribution...": lib_demo-0.1.0.tar.gz holds the same source plus PKG-INFO (its metadata) and pyproject.toml.orig.
  3. The backend builds the wheel from the sdist. "Building wheel from source distribution...": uv_build, the backend named in pyproject.toml's [build-system], writes lib_demo-0.1.0-py3-none-any.whl: the package plus a .dist-info folder whose WHEEL file holds the tag py3-none-any.
  4. Installing a wheel is unpacking. WHEEL says Root-Is-Purelib: true, so an installer unpacks the archive into purelib, that is site-packages: lib_demo/ and lib_demo-0.1.0.dist-info/ land as they are. The wheel specification lists no build step (binary distribution format).
  5. From an sdist, the build runs on the user's machine. When no wheel matches, the installer must run the backend first, and with C or Rust inside that needs a compiler (section 3's sdist entry). That is why the wheel's name matters: it decides whether a user unpacks or compiles.

The interesting part is the name of what it builds: name-version-python-abi-platform.whl, and an installer picks the one file whose three tags match your interpreter and machine. Pick a real file from PyPI (fetched 2026-10-05) in the decoder:

  • Python tag (cp314, py3): which interpreter. py3 means any Python 3, so pure Python.
  • ABI tag (cp314, cp314t, abi3, none): the ABI the compiled code was built against. A cp314 wheel loads only on CPython 3.14; cp314t only on the free-threaded 3.14t; abi3 (the stable ABI) on every CPython from the tagged version on, so one wheel per platform covers future Pythons. But abi3 does not load on free-threaded builds, which is why projects that ship abi3 wheels must still build a separate cp314t wheel, or their users on 3.14t build from source.
  • Platform tag: manylinux_2_28_x86_64 runs on any Linux with glibc 2.28 or newer (PEP 600); musllinux is for Alpine; macosx_11_0_arm64 needs macOS 11 or newer on Apple silicon; win_amd64 is 64-bit Windows.

abi3t (Python 3.15, PEP 803) is a stable ABI that free-threaded builds can load, so one cp315-abi3.abi3t wheel covers both builds of 3.15 and later; until projects port to it, a library supporting 3.11 and up ships three wheels per platform (details and tool support in the closed block).

abi3t: what it needs and which build tools support it (checked 2026-10-05 and 2026-09-25)
abi3t: the stable ABI for free-threaded builds (Python 3.15, PEP 803)
3.15 adds abi3t, a stable ABI that free-threaded builds can load: one wheel tagged cp315-abi3.abi3t runs on both builds of 3.15 and later. Porting "usually requires some non-trivial changes to the source code" (What's New in 3.15), and free-threaded 3.14 predates it, so a project supporting 3.11 and up publishes three wheels per platform: cp311-abi3, cp314-cp314t and cp315-abi3.abi3t. What's New says build tools did not support it "at the time of writing"; the community guide, updated 2026-09-25, lists support released in CMake 4.4 with scikit-build-core 1.0, maturin 1.14 (1.14.1+ for both ABI families) and meson-python 0.21, with setuptools still under development (py-free-threading: abi3t).

8. Habits that keep a project healthy

Each one comes from a failure measured or shown above:

  1. Commit uv.lock and run CI with uv sync --locked, so a stale lock fails the build (section 4, step 6).
  2. Never pip install inside a uv project. It installs into whatever environment is active (often none), and the next uv sync removes anything the lock does not list. Use uv add.
  3. Pin linters and type checkers in the dev group (the lock file then pins them exactly). ruff 0.16 turned on 354 more rules overnight, and ty is a 0.0.x beta.
  4. Pick one type checker and run it in CI, and learn which checks it leaves off by default (section 2).
  5. Test a library against its lowest allowed versions too: your >= ranges promise that the oldest versions work. Run the tests once with uv sync --resolution lowest-direct (lowest versions of your direct dependencies) in CI.
  6. Set ruff's target-version and the type checker's Python version to your minimum, and run CI on your oldest supported version: a 3.15 feature such as lazy import, frozendict or [*xs for xs in ...] fails on older versions (as a SyntaxError before any line runs, for the syntax ones).
