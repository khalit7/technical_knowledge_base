Almost everything that surprises a working Python programmer comes from five facts. Each section below is one of them, opened up.

1. Names point at objectsAssignment never copies. b = a gives one object a second name; mutation through either name is visible through both. Copies happen only when you ask (.copy(), copy.deepcopy, a slice). Sections 1 and 13.
2. Syntax calls methods on the typelen(x), a + b, for, ==, with, x.attr are each a fixed lookup of a double-underscore ("dunder") method on type(x), with documented fallbacks. Implement the methods and your class behaves like a built-in. Section 2 and the {{Data model|#t-pa-dm}} tab.
3. Laziness is a protocolAn iterator is any object with __next__; a generator is a function that pauses at yield. Pipelines of generators hold one item at a time (1.1 KiB against 106 MiB below). Section 3.
4. Functions and classes are objects built at run timedef and class are statements that create objects, which is why decorators, closures, default-argument traps, descriptors and super() work the way they do. Sections 4 and 5.
5. One interpreter thread runs bytecode at a time (default build)The GIL makes threads useful for waiting, not for computing; processes or native code compute in parallel; asyncio runs thousands of waits on one thread, provided nothing blocks it. Sections 9 and 10 and the {{Event loop|#t-pa-loop}} tab.
And: types are for tools, speed is for measurementAnnotations are not checked when the program runs; mypy or ty check them before. CPython compiles to bytecode, specialises it while running, and is still roughly 10x slower than NumPy on array work; profile first. Sections 6, 11 and 12.

1. Names, objects and references

A Python object is a block of memory that knows its type, its value and how many references point at it. A name (a variable) is an entry in a namespace, a dict-like table from strings to objects. Assignment, b = a, writes a second entry pointing at the same object. Nothing is copied. Two names for one object are aliases.

Whether aliasing matters depends on mutability: whether the object can change after it is made. Lists, dicts, sets and most of your own classes are mutable. Ints, floats, strings, tuples, frozensets and bytes are immutable: every "change" builds a new object and rebinds the name.

n1_alias.py
a = [1, 2]
b = a              # a second name for the same list object
b.append(3)
print(a, a is b)

x = 10
y = x
y += 1             # ints are immutable: += builds a new int and rebinds y
print(x, y)
real output, Python 3.14.8
[1, 2, 3] True
10 11

Two questions you can ask about two names: a == b ("equal values?", which calls __eq__) and a is b ("the same object?", which compares identities, the address in CPython). Use is only for singletons such as None; for everything else it answers a question you did not mean to ask.

n2_identity.py
a = [1, 2]
b = [1, 2]
print(a == b, a is b)          # equal values, two objects

x, y = 256, int("256")
print(x is y)                  # CPython keeps one shared object for -5..256
x, y = 257, int("257")
print(x is y)                  # outside that range: two objects
print(x == y)                  # == is the question you meant to ask

The 256 against 257 split is an implementation detail: "The current implementation keeps an array of integer objects for all integers between -5 and 256" ({{C API: integer objects|https://docs.python.org/3/c-api/long.html}}). Copying: shallow and deep

A shallow copy makes a new outer container whose slots point at the same inner objects. A deep copy copies recursively, keeping a memo so that an object shared twice in the original is shared twice in the copy too. The animation runs the same five lines both ways; the boxes are CPython's real objects, labelled by id() as the program ran.

Recorded by code/n7_graph.py: it runs each line with exec and labels every list by id() in order of first appearance. Ints are drawn as values.
n3_copy.py
import copy

grid = [[0, 0], [0, 0]]
shallow = grid.copy()          # new outer list, SAME inner lists
deep = copy.deepcopy(grid)     # new lists all the way down
grid[0][0] = 9
print(shallow[0][0], deep[0][0])

rows = [[0] * 2] * 3           # three references to ONE inner list
rows[0][0] = 1
print(rows)
rows = [[0] * 2 for _ in range(3)]   # three separate lists
rows[0][0] = 1
print(rows)
real output, Python 3.14.8
9 0
[[1, 0], [1, 0], [1, 0]]
[[1, 0], [0, 0], [0, 0]]
The [[0] * n] * m trap
* on a list repeats references, not objects: three rows that are one row. Build nested lists with a comprehension. The same mistake inside a model config (one dict shared by every layer) is harder to see.

Passing arguments: the function gets the object, not a copy

Python passes a reference to the object (sometimes called "call by sharing"). A function can mutate the caller's object, but rebinding its own parameter name changes nothing outside. Default values are evaluated once, when def runs, so a mutable default is shared by every call.

n4_args.py
def add_item(xs):
    xs.append("new")           # mutates the object the caller passed

def replace(xs):
    xs = ["other"]             # rebinds the local name only

items = ["a"]
add_item(items)
replace(items)
print(items)

def bad(x, acc=[]):            # the default list is built ONCE, at def time
    acc.append(x)
    return acc

print(bad(1), bad(2))

def good(x, acc=None):
    if acc is None:
        acc = []
    acc.append(x)
    return acc

print(good(1), good(2))

What it solves
No copying on assignment or call: passing a 10 GB list costs the same as passing an int.
What it costs
Spooky action at a distance: any alias can change what you hold.
Habits
Do not mutate arguments unless that is the function's job (and say so); return new objects; prefer tuples and frozen dataclasses for values that should not change.
