12. Performance: measure, then move the loop out of Python

The order that works: measure where the time goes, fix the algorithm or data structure, push loops into code that runs in C (built-ins, re, NumPy), and only then write native code. Guessing skips the first step and usually optimises the wrong thing.

Profiling: cProfile, and the sampling profilers

The subject is a deliberately slow version of the root page's token counter: it calls a Python function for every character and keeps per-user totals in two parallel lists. cProfile (standard library) records every function call:

p1_slow.py
def count_tokens(text):
    n, inside = 0, False
    for c in text:                          # one Python-level call per character
        tok = is_token_char(c)
        if tok and not inside:
            n += 1
        inside = tok
    return n

def per_user(lines):
    users, totals = [], []                  # parallel lists: `in` and .index() scan them
    for line in lines:
        msg = json.loads(line)
        u = msg["user"]
        if u not in users:
            users.append(u)
            totals.append(0)
        totals[users.index(u)] += count_tokens(msg["text"])
    return sorted(zip(users, totals), key=lambda p: (-p[1], p[0]))[:5]

Read tottime (time inside the function itself) first: 2.7 million calls of is_token_char, one per character, dominate. The list scans that look bad on paper (users.index) cost 23 ms, because there are only 200 users. The fix follows the profile: count with a compiled regular expression (the loop over characters then runs inside the C regex engine) and keep totals in a dict (a Counter):

p1_fast.py
"""The same result after reading the profile: a dict instead of list scans, and a compiled regex
instead of a Python-level loop over characters."""
import json, re
from collections import Counter
from p1_slow import make_log

TOKEN = re.compile(r"[A-Za-z0-9]+")         # the same token rule, run by the C regex engine

def per_user(lines):
    totals = Counter()
    for line in lines:
        msg = json.loads(line)
        totals[msg["user"]] += len(TOKEN.findall(msg["text"]))
    return sorted(totals.items(), key=lambda p: (-p[1], p[0]))[:5]

Same answer (the script asserts it), 206 ms down to 74 ms. Note also what the profiler did to the program: 206 ms became 1.46 s under cProfile, because it adds work to each of 8 million calls. A deterministic profiler like cProfile distorts call-heavy code; a sampling profiler, which looks at the stack a few hundred times a second, barely slows the program. Two of them:

  • py-spy: "a sampling profiler for Python programs ... without restarting the program or modifying the code in any way" ({{py-spy|https://github.com/benfred/py-spy}}); attach to a running server with py-spy top --pid or py-spy dump. On macOS "OSX always requires running as root", which is what happened here:

  • Scalene samples per line and splits time into Python and native code (and memory, if asked). Its summary for the whole slow script, which also includes building the 20,000-line test log:

Vectorising with NumPy

NumPy stores numbers in one contiguous typed buffer and runs each operation as a C loop over it, with no per-element object, method lookup or reference count. The same reduction (the denominator of a softmax, sum(exp(x - max(x)))) as a Python loop, as map with math.fsum, and as NumPy, from 10 to a million elements:

p2_numpy.py
"""Softmax-style work (sum of exp(x - max)) on n floats: a Python loop, a generator with
math.exp, and NumPy, plus the cost of converting the list to an array. Median of timeit repeats, in microseconds per call."""
import math, os, statistics, sys, timeit
import numpy as np

def py_loop(xs):
    m = max(xs)
    s = 0.0
    for x in xs:
        s += math.exp(x - m)
    return s

def py_builtin(xs):
    m = max(xs)
    return math.fsum(map(math.exp, (x - m for x in xs)))

def np_vec(a):
    return np.exp(a - a.max()).sum()       # three passes in C over a contiguous buffer

def us(f, arg):
    t = timeit.Timer(lambda: f(arg))
    n, _ = t.autorange()
    return statistics.median(t.repeat(5, n)) / n * 1e6

print(f"Python {sys.version.split()[0]}, NumPy {np.__version__}, load {os.getloadavg()[0]:.2f}")
print(f"{'n':>9} {'loop':>11} {'map+fsum':>11} {'numpy':>11} {'np.array(list)':>15}  numpy speed-up over loop")
for n in (10, 1_000, 100_000, 1_000_000):
    xs = [((i * 7919) % 1000) / 100 for i in range(n)]
    a = np.array(xs)
    assert abs(py_loop(xs) - np_vec(a)) < 1e-6 * py_loop(xs)
    t1, t2, t3, t4 = us(py_loop, xs), us(py_builtin, xs), us(np_vec, a), us(np.array, xs)
    print(f"{n:>9,} {t1:>9.1f}us {t2:>9.1f}us {t3:>9.1f}us {t4:>13.1f}us  {t1 / t3:6.1f}x")

Three lessons, all from the table. At 10 elements NumPy is slower than the loop (a fixed cost of about a microsecond per NumPy call), which confirms the old page's claim. From a thousand elements up it is 10 to 16 times faster. And converting a Python list to an array costs about 40% of the whole Python loop: keep data in arrays from the start (load with NumPy, pandas, polars or PyTorch), or the conversion eats the gain. Clever pure-Python (map, fsum) did not help: the per-element work is still Python objects.

When to drop to native code

When the profile shows a hot loop that is not array arithmetic (a tokenizer, a parser, a graph walk, a custom sampler), no library already does it, and it is called often enough to matter. Then write that one function in a compiled language and call it from Python. The {{Rust page, Part 2 (Speeding up Python)|n:3c65c17b0d0d8156bed9ead8a22f33b0}} does exactly this with PyO3 and maturin, from one function to a published wheel, and compares the alternatives (Cython, Numba, mypyc, nanobind or pybind11 for C++, cffi); the {{C++ page|n:3cd5c17b0d0d81ceadcee44fe9c023a0}} (Part 2) shows what the machine does underneath. The root's {{Benchmark|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} tab measures the running program in all four languages and the cost of each crossing between Python and native code: batch work so you cross once per array, not once per element.

Cheap wins first
A dict or set instead of list membership; str.join instead of += in a loop; built-ins (sum, sorted, re, collections.Counter) over hand loops; local variables in hot loops; caching (section 4).
Then
NumPy or PyTorch for numbers; processes or the free-threaded build for parallel CPU work (section 9); asyncio for waiting (section 10); a Rust or C++ extension for the hot loop that is left.
Mistakes
Optimising without a profile; timing once (use timeit or hyperfine, take the median); trusting cProfile's absolute times; micro-benchmarking with a warm cache and deploying with a cold one.
