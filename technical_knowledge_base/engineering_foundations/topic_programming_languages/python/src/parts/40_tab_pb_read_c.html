2. uv end to end

uv replaces pyenv, venv, pip, pip-tools, pipx and Poetry with one binary. The root page's {{Toolchain atlas|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} replays the first five commands (uv init, uv add, uv run, ruff, pytest); this section covers what you need after that: interpreters, the kinds of project, what uv sync really does, extras and groups, scripts, tools, workspaces and the pip interface.

Interpreters

uv downloads standalone CPython builds (from the python-build-standalone project) instead of using whatever the system has. uv python install 3.14 3.14t 3.15 installed every interpreter used on this page; t is the free-threaded build.

In Python you would have run pyenv install and then pointed a venv at it; with uv, --python 3.15 on any command is enough, and a project's .python-version file pins it.

Three kinds of project

Since uv 0.12, plain uv init and uv init --app both make a packaged application: code under src/, a console script, and the uv_build backend (so uv run app-demo works). --no-package gives the old flat layout with a main.py, and --lib makes a library with a py.typed marker (it tells type checkers the package ships annotations).

Correction to the old page
The old "zero to expert" page said uv init myproj, uv add requests, uv run main.py. With uv 0.12.23 plain uv init creates no main.py (output above); run the console script with uv run <project-name>, or create the flat layout with uv init --app --no-package. The root page records the same correction.

The three files that must agree

A uv project is three things: pyproject.toml (what you asked for: ranges), uv.lock (what one resolution picked: exact versions and hashes for every platform at once, which is what "universal lock" means) and .venv (what is installed). uv add, uv lock and uv sync move them back into agreement, and uv run syncs before it runs. What the session shows:

  • uv sync is exact: it removes anything the lock does not ask for in this sync, which is why orjson (an extra) disappeared until --extra fast was given. Use --inexact to keep extra packages. uv run is the opposite: it installs what is missing but removes nothing unless you pass --exact (uv docs: locking and syncing).
  • --locked refuses a stale lock: the build fails instead of silently resolving new versions. Use it in CI. --frozen goes further and installs from the lock without checking pyproject.toml at all.
  • Dependency groups ([dependency-groups], PEP 735, here dev) are for you, never published; extras ([project.optional-dependencies]) are for your users (pip install tokcount[fast]). The dev group is installed by default; --no-dev leaves it out.
  • The system python3 cannot import httpx: the project's packages live in .venv. That is what uv run does that bare python does not: sync, then run inside the project environment, no activation needed.

uv tree shows why each package is there; uv export writes a requirements.txt for tools that need one, or the standard pylock.toml (PEP 751, accepted in 2025), the first lock format every installer can share.

Scripts with their dependencies inside (PEP 723)

A one-file script can declare its own dependencies in a comment block; uv run script.py then builds a cached throwaway environment for it. This replaced "make a venv for this one script".

Tools: uvx is pipx

uvx tool@version runs a command-line tool in its own cached environment without installing it into your project; uv tool install puts it on your PATH. Every type checker on this page was run this way, pinned to an exact version.

Workspaces: several packages, one lock

A workspace is a repository with several packages (a library and the CLI that uses it, say) that share one uv.lock and one .venv, like a Cargo workspace in Rust. { workspace = true } makes the CLI depend on the library's source, not on a PyPI release.

The pip interface

For old repositories and Dockerfiles, uv venv and uv pip install behave like python -m venv and pip, only faster; nothing is locked unless you ask (uv pip compile).

What uv costs, and when not to use it
uv is one company's tool (Astral, which announced on 2026-03-19 that it is joining OpenAI, per the Astral blog); the code is open source under MIT and Apache-2.0. Its lock format is its own, though it can export the standard pylock.toml. Where a project needs non-Python binaries (a specific CUDA toolkit, MKL, GDAL), conda or pixi still solve a problem uv does not. And in a repository that already uses Poetry, switching tools is a team decision, not a drive-by change.
Common mistakes with uv
  • Running python script.py instead of uv run script.py and wondering why imports fail: the project environment is not active.
  • Editing pyproject.toml by hand and forgetting uv lock: CI with --locked catches it (the error above).
  • Not committing uv.lock for an application: every machine then resolves on its own day.
  • Putting test tools in [project.optional-dependencies]: they are then published as an extra; use a dependency group.
  • Expecting uv sync to leave packages you installed by hand with uv pip install: it removes them.
