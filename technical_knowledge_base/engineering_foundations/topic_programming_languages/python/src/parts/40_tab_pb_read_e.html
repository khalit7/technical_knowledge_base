5. pytest essentials

pytest finds files named test_*.py, runs every function named test_*, and treats a plain assert as the check. Five features cover most real test suites; all five are in this one file, testing the root page's token-counting rule:

  • Fixtures (chat_file, defined in conftest.py so every test file can use it) are set-up functions that pytest calls for you when a test names them as a parameter. Built-in ones: tmp_path (a fresh folder per test) and monkeypatch (set an environment variable or attribute, undone after the test).
  • @pytest.mark.parametrize runs one test per row of inputs, each reported separately.
  • pytest.raises asserts that a block raises a given exception.
  • Subtests (new in pytest 9.0, 2025-11-05) check several values inside one test and report each failure separately, for cases where the values are only known at run time.
  • Configuration now lives natively in pyproject.toml under [tool.pytest] (pytest 9.0; the older [tool.pytest.ini_options] table still works), and strict = true turns on every strictness option (unknown markers and config keys become errors).

-k selects tests by name, --co lists what would run (note the parametrize ids, with non-ASCII escaped), and -n 4 from the pytest-xdist plugin spreads tests over four worker processes. On nine tests the workers' start-up makes it slower (0.37 s against 0.01 s); it pays off on suites that take minutes.

Common mistakes with pytest
  • Testing implementation details (private functions, exact call counts) instead of behaviour, so every refactor breaks tests that found no bug.
  • A fixture with scope="session" that returns a mutable object: one test's change leaks into the next.
  • Forgetting that test files are imported: module-level code in a test file runs at collection time, even for tests you deselected.
  • Running pytest instead of uv run pytest, so a global pytest without your dependencies runs the suite.

The wheel is a zip with your package and a .dist-info folder (METADATA is what PyPI shows; RECORD lists every file with its hash; WHEEL holds the tag). The sdist carries the source and pyproject.toml so any installer can rebuild it.

Reading a wheel's name

A wheel's file name says exactly where it can be installed: name-version-python-abi-platform.whl. Pick a real file from PyPI (fetched 2026-10-05):

  • Python tag (cp314, py3): which interpreter. py3 means any Python 3, so pure Python.
  • ABI tag (cp314, cp314t, abi3, none): the ABI the compiled code was built against. A cp314 wheel loads only on CPython 3.14; cp314t only on the free-threaded 3.14t; abi3 (the stable ABI) on every CPython from the tagged version on, so one wheel per platform covers future Pythons. But abi3 does not load on free-threaded builds, which is why projects that ship abi3 wheels must still build a separate cp314t wheel, or their users on 3.14t build from source.
  • Platform tag: manylinux_2_28_x86_64 runs on any Linux with glibc 2.28 or newer (PEP 600); musllinux is for Alpine; macosx_11_0_arm64 needs macOS 11 or newer on Apple silicon; win_amd64 is 64-bit Windows.
abi3t: the stable ABI for free-threaded builds (Python 3.15, PEP 803)
3.15 adds abi3t, a stable ABI that free-threaded builds can load: one wheel tagged cp315-abi3.abi3t runs on both builds of 3.15 and later. Porting "usually requires some non-trivial changes to the source code" ({{What's New in 3.15|https://docs.python.org/3.15/whatsnew/3.15.html}}), and free-threaded 3.14 predates it, so a project supporting 3.11 and up publishes three wheels per platform: cp311-abi3, cp314-cp314t and cp315-abi3.abi3t. What's New says build tools did not support it "at the time of writing"; the community guide, updated 2026-09-25, lists support released in CMake 4.4 with scikit-build-core 1.0, maturin 1.14 (1.14.1+ for both ABI families) and meson-python 0.21, with setuptools still under development ({{py-free-threading: abi3t|https://py-free-threading.github.io/abi3t/}}).

A compiled package needs one wheel per Python version (or one abi3), times free-threaded or not, times each operating system and processor: numpy 2.5.3 publishes many wheels. Nobody builds those by hand: cibuildwheel runs the build in CI on Linux (inside manylinux containers), macOS and Windows runners, and maturin-action does the same for Rust. Since cibuildwheel 3.1 (2025-07-23) free-threaded 3.14 wheels are built by default, so a project that does not support free-threading must skip them explicitly (cp31?t-*) ({{cibuildwheel changelog|https://cibuildwheel.pypa.io/en/stable/changelog/}}).

Publishing without a stored password: trusted publishing

The old way was to create a PyPI API token and store it as a CI secret, where it can leak. Trusted publishing uses OpenID Connect (OIDC): you tell PyPI once "this repository's workflow may publish this project"; at publish time the CI service (GitHub Actions, GitLab CI/CD, Google Cloud and others) issues a short-lived signed token, PyPI verifies it came from that repository and workflow, and no long-lived secret exists ({{PyPI docs|https://docs.pypi.org/trusted-publishers/}}). uv publish tries it first, which is what this output from a laptop (not a CI job) shows:

What publishing costs
A version number on PyPI can never be reused, even after deleting the file, so try uploads on TestPyPI first. Every compiled wheel you publish is a promise to keep building it for each new Python, including the free-threaded ones, and users on a platform you skip will try to compile from your sdist.
