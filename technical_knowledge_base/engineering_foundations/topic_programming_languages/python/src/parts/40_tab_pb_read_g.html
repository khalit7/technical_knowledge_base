9. Free-threading in practice

The GIL (global interpreter lock) is the lock in the standard CPython build that lets only one thread run Python bytecode at a time; threads still help when they wait on I/O, but CPU-bound threads take turns ({{Part 1|#t-pa-read}} explains threads and the GIL from the start). The free-threaded build removes it (PEP 703): experimental in 3.13, officially supported but still optional in 3.14 (PEP 779), installed separately as python3.14t (uv python install 3.14t). Check which one you are on with sys._is_gil_enabled().

The workload below is the root page's program: count tokens per user over 100,000 JSONL chat lines (the root's generator, seed 7), split across threads, each thread filling its own Counter that the main thread merges (src/pb/ft/). The bug the GIL was hiding (and was not preventing)

Now the same four threads update one shared dictionary instead of their own: shared[user] = shared.get(user, 0) + n. That line reads, adds and writes back in three steps; if two threads read the same old value, one addition is lost.

Python's documentation never promised that a read-modify-write like this is atomic under the GIL ({{Python FAQ|https://docs.python.org/3/faq/library.html#what-kinds-of-global-value-mutation-are-thread-safe}}); the GIL only made losing an update rare. Without the GIL the same bug happens on most runs. What the free-threaded build does guarantee is that built-in objects stay internally consistent: the dictionary never crashes or corrupts, it only holds the wrong totals. The fixes are the same on both builds: a threading.Lock around the update (exact in every run above), or, better, no shared state, which is what the scaling run did.

Will your dependencies run without the GIL?

A C, C++ or Rust extension must declare that it is safe without the GIL. If it does not, importing it on the free-threaded build silently turns the GIL back on for the whole process, with a warning. What it costs, and when not to use it
  • Single-thread speed. The 3.13 HOWTO measured about 40% overhead; for 3.14, What's New says "roughly 5-10%" and the 3.14 HOWTO "about 1% on macOS aarch64 to 8% on x86-64 Linux" (pyperformance). Measured here on one workload: see the Runtime lab.
  • Memory. PEP 779 set a 20% memory overhead target for phase II; this page did not measure memory.
  • Your own thread safety. Races that the GIL made rare now happen; audit shared mutable state before switching.
  • Dependencies. One unported extension turns the GIL back on for everyone (above).
  • Not for I/O-bound work: threads already overlap waiting under the GIL, and asyncio is the usual tool for many connections.
Whether the free-threaded build ever becomes the default ("phase III") is "left for a future PEP" (PEP 779); the old page's forecast of 3.16 to 3.17 is a guess, not a plan.

10. The experimental JIT, on and off

A JIT (just-in-time compiler) turns hot code into machine code while the program runs. CPython's (PEP 744, since 3.13) is a copy-and-patch JIT: when the specialising interpreter finds a hot loop, it records a trace of its micro-operations and stitches together machine-code templates ("stencils") that were compiled with LLVM when CPython itself was built, so you need no LLVM at run time. It ships compiled into the official macOS and Windows installers and the uv builds used here, but is off unless you set PYTHON_JIT=1; in 3.14 and later, sys._jit.is_enabled() tells you whether it is on.

Read it as: on 3.15 the JIT sped up the plain Python loops (character scanning, float arithmetic) by about half or more, helped small-object code less, and did not help (here, slightly slowed) the generator pipeline, inside What's New's own range for 3.15 ("roughly 15% slowdown to over 100% speedup", 11-12% geometric mean on AArch64 macOS). The 3.14 JIT on this machine is mostly a wash, sometimes slower. Trust the direction, not the digits: the final run was made with a load average around 10, and an earlier run the same day (src/pb/out/jit_earlier_run.txt) gave 1.5x instead of 2.4x for json_count on 3.15. It is off by default in 3.15 too, and a 2x speed-up of a Python loop is still far from moving the loop to NumPy or Rust (the root's {{Benchmark|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} tab measures the token counter in all four languages).

11. Subinterpreters (3.14), measured

A subinterpreter is a second, isolated Python interpreter inside the same process: its own modules, its own globals and, since 3.12, its own GIL (PEP 684). 3.14 exposed them in the standard library (PEP 734): concurrent.interpreters and InterpreterPoolExecutor, which has the same interface as the thread and process pools. They sit between threads and processes: parallel on the normal GIL build like processes, but cheaper to start, and like processes they share nothing by default: arguments and results cross by pickling, except immutable built-ins (None, bool, bytes, str, int, float and tuples of these), which are shared or copied cheaply, and memoryview and interpreter queues, which really share mutable data ({{docs|https://docs.python.org/3.14/library/concurrent.interpreters.html}}).

from concurrent.futures import InterpreterPoolExecutor with InterpreterPoolExecutor(max_workers=4) as ex: totals = list(ex.map(count_slice, parts)) # same code as with ThreadPoolExecutor

On this job, subinterpreters and processes both clearly beat threads on the GIL build, because each worker has its own GIL; processes were somewhat faster here. Neither reached 4x with 4 workers: each worker receives 25,000 lines by pickling and returns a pickled Counter, and the machine was busy. A new subinterpreter started more than ten times faster than a spawned process, and about a hundred times slower than a thread.
