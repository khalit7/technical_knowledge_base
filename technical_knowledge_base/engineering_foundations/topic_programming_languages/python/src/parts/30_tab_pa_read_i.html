11. CPython internals you can see

CPython, the standard Python, is a C program. It compiles your source to bytecode, instructions for a virtual stack machine (cached in __pycache__/*.pyc), and an evaluation loop in C executes them one by one. The root page's {{How code runs|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} section follows one line through Python, C++, Rust and JavaScript; here we look inside CPython's half.

Bytecode, and how it rewrites itself while running

The dis module prints a function's bytecode. Since 3.11 the interpreter is specialising and adaptive ({{PEP 659|https://peps.python.org/pep-0659/}}): after an instruction has run a few times it is rewritten in place into a version specialised for the types it saw, guarded by a cheap check; if the check starts failing, it falls back and re-specialises. "Python 3.11 is between 10-60% faster than Python 3.10", 1.25x on average ({{What's new in 3.11|https://docs.python.org/3/whatsnew/3.11.html}}), largely from this. dis.dis(f, adaptive=True) shows the live, rewritten instructions. Step through the same function before running, after 1,000 integer additions, and after floats arrive:

The three listings are the real output of code/i1_dis.py (below) on Python 3.14.8. Highlighted rows changed since the previous listing.
i1_dis.py
import dis

def total(xs):
    s = 0
    for x in xs:
        s = s + x
    return s

print("--- before running (generic instructions)")
dis.dis(total, adaptive=True)
total(list(range(1000)))            # warm up with ints only
print("--- after 1000 int additions (specialised in place)")
dis.dis(total, adaptive=True)
for _ in range(100):
    total([0.5] * 1000)             # now feed floats
print("--- after floats arrive (re-specialised)")
dis.dis(total, adaptive=True)

Read the changes: BINARY_OP (+), which must handle every type with an __add__, became BINARY_OP_ADD_INT, then BINARY_OP_ADD_FLOAT when the types changed; FOR_ITER became FOR_ITER_LIST. JUMP_BACKWARD_NO_JIT is the loop's back-edge on a build where the experimental JIT is off, which is the default in 3.14 ({{What's new in 3.14|https://docs.python.org/3.14/whatsnew/3.14.html}}; turning it on and measuring it is {{Part 2's Runtime lab|#t-pb-lab}}). The lesson for speed: hot loops whose types never change are the ones CPython can specialise.

Reference counting and the cycle collector

Every object carries a count of references to it. When the count reaches zero the object is freed at once, deterministically; that is why a file closed by going out of scope closes immediately in CPython. Counting cannot free a cycle (A points at B, B at A: both counts stay at 1 after your last name is gone), so a separate cycle collector (gc) periodically looks for groups of objects reachable only from each other.

i2_refcount.py
import gc, sys, weakref

class Node:
    def __init__(self, name):
        self.name, self.other = name, None

a = Node("a")
print("refcount:", sys.getrefcount(a))          # +1 for getrefcount's own argument
b = a
print("refcount:", sys.getrefcount(a))
weakref.finalize(a, print, "  a freed")          # prints when the object dies
del a
print("del a: still alive through b")
del b                                            # count hits 0: freed immediately
print("del b done")

x, y = Node("x"), Node("y")
x.other, y.other = y, x                          # a reference cycle
weakref.finalize(x, print, "  x freed")
weakref.finalize(y, print, "  y freed")
del x, y                                         # counts never reach 0
print("after del x, y: nothing freed yet")
print("gc.collect() found", gc.collect(), "unreachable objects")
print("thresholds:", gc.get_threshold())
real output, Python 3.14.8
refcount: 2
refcount: 3
del a: still alive through b
  a freed
del b done
after del x, y: nothing freed yet
  x freed
  y freed
gc.collect() found 4 unreachable objects
thresholds: (2000, 10, 10)

sys.getrefcount reports one more than you expect because its own argument is a reference. a died the instant its last name went; the cycle survived del until gc.collect(). The thresholds (2000, 10, 10) are those of the generational collector: Python 3.14.0 to 3.14.4 shipped an incremental collector, and 3.14.5 reverted to "the generational GC from 3.13" after "reports of significant memory pressure in production environments" ({{What's new in 3.14, Garbage collection|https://docs.python.org/3.14/whatsnew/3.14.html}}). Practical consequences: break cycles in long-lived structures (parent pointers, callbacks that capture self) or use weakref; do not rely on __del__ for clean-up (use with); and for PyTorch, a tensor held by a cycle keeps its GPU memory until the collector runs.

What objects cost

i3_sizes.py
import sys
for v in [0, 1, 2**30, 2**60, 2**100, 1.5, "", "a", "é", "日", "🙂", b"", (), [], {}, set()]:
    print(f"{v!r:>40}  {type(v).__name__:6} {sys.getsizeof(v):4} bytes")
xs, last = [], None
growth = []
for i in range(33):
    size = sys.getsizeof(xs)
    if size != last:
        growth.append((len(xs), size))
        last = size
    xs.append(i)
print("list size jumps (length, bytes):", growth)

Every object has a header (a reference count and a type pointer, 16 bytes on a 64-bit build), so a Python int is 28 bytes where a C int64 is 8, and a list of a million floats is a million pointers to a million separate 24-byte objects (NumPy stores 8 bytes each, contiguously). Ints grow 4 bytes per 30 bits of magnitude: they are arbitrary precision. A str stores 1, 2 or 4 bytes per character for the whole string, chosen by its widest character ({{PEP 393|https://peps.python.org/pep-0393/}}); a non-ASCII string also carries a larger header, which is why 'é' (1 byte per character) costs 61 bytes against 42 for 'a', and '🙂' (4 bytes per character) 64. The last line is a list's over-allocation: appends reserve spare room in steps, which is why append is O(1) on average.
