The idea in one screen

In Python a name is only a reference to an object, and every piece of syntax is a method call on the object's type, run as bytecode by one interpreter that counts references to each object and, in the default build, lets one thread run at a time. Almost every surprise a working Python programmer meets follows from that sentence.

Three lines: the first copies nothing, the second changes the object both names see, the third calls a method that builds a new one

1. y = x
2. y.append(3)
3. z = x + [4]

Blue is the method looked up on the type, the thing to notice: the name never decides what + or .append does; the object's type does. Reference counts and the method each line called are from the real run below, as are the bytecode names.

Name
an entry in a namespace (a dict-like table from strings to objects); it holds a reference, never a value.
Object
a block of memory that knows its type, its value and how many references point at it.
Alias
a second name for the same object.
Mutable
can change after it is made (list, dict, set, most classes); immutable types (int, float, str, tuple, frozenset, bytes) never do.
Special ("dunder") method
a double-underscore method such as __add__ that syntax calls on the type.
Bytecode
the instructions CPython compiles your code to and runs one at a time in a loop written in C.
GIL
the global interpreter lock: in the default build only the thread holding it runs bytecode.

Five facts behind almost every surprise

Each fact is one child page, opened up. The essentials page keeps the first; the rest are a sentence and a link.

1. Names point at objectsAssignment never copies. b = a gives one object a second name; mutation through either name is visible through both. Copies happen only when you ask (.copy(), copy.deepcopy, a slice).Section 2 below; copies and argument passing: {{the data model and protocols|n:4055c17b0d0d816a8705e4d3f20b3da7}}, section 2.
2. Syntax calls methods on the typelen(x), a + b, for, ==, with, x.attr are each a fixed lookup of a double-underscore ("dunder") method on type(x), with documented fallbacks. Implement the methods and your class behaves like a built-in.{{The data model and protocols|n:4055c17b0d0d816a8705e4d3f20b3da7}}, with its Data model explorer.
3. Laziness is a protocol; functions and classes are objects built at run timeAn iterator is any object with __next__; a generator is a function that pauses at yield. def and class are statements that create objects, which is why decorators, closures and descriptors work the way they do.{{The data model and protocols|n:4055c17b0d0d816a8705e4d3f20b3da7}}, sections 3 to 5.
4. One interpreter thread runs bytecode at a time (default build)The GIL makes threads useful for waiting, not for computing; processes or native code compute in parallel; asyncio runs thousands of waits on one thread, provided nothing blocks it.{{Concurrency, asyncio and the GIL|n:4055c17b0d0d81bdbee8c37d80b55a0e}}.
5. Types are for tools, speed is for measurementAnnotations are not checked when the program runs; mypy or ty check them before. CPython runs bytecode in a loop, so on arrays of a thousand elements and up a Python loop was 10 to 16 times slower than one NumPy call; profile first, then move the loop out of Python.{{Typing, uv, packaging and the toolchain|n:4055c17b0d0d8192878fce7505cc612f}}; {{CPython internals and performance|n:4055c17b0d0d8111872ad7101b7e3c22}}.

Five things the runs showed

Each is measured, with its script and output, on the child page named.

A shared dict updated from threads with no lock lost tokens even with the GIL (3 of 5 runs on 3.14); without the GIL every run lost 24k to 36k. A lock fixed both.{{Concurrency, asyncio and the GIL|n:4055c17b0d0d81bdbee8c37d80b55a0e}}, section 3
One blocking time.sleep inside async code delayed another task by 100 ms; asyncio.to_thread removed the delay.{{Concurrency, asyncio and the GIL|n:4055c17b0d0d81bdbee8c37d80b55a0e}}, section 2
A generator over a million lines peaked at 1.1 KiB; the same work as a list peaked at 106 MiB.{{The data model and protocols|n:4055c17b0d0d816a8705e4d3f20b3da7}}, section 3
Lazy imports (3.15) took a small CLI from 100 ms to 26 ms at start-up, and from 268 to 64 imported modules.{{CPython internals and performance|n:4055c17b0d0d8111872ad7101b7e3c22}}, section 7
