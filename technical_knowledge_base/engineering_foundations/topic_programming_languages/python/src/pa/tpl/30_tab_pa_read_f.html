6. Typing for real code

Annotations (x: int, -> str) are stored on the function and otherwise ignored when the program runs. A separate type checker reads them and reports contradictions before you run anything. The two used on this page are mypy (the reference checker, written in Python, version 2.4.0) and ty (Astral's checker, written in Rust, beta, version 0.0.84); comparing them, and pyright, across a whole project is {{Part 2|#t-pb-read}}'s job. Here is what the type system can express and what it actually catches.

The tools you will actually use

  • Built-in generics and unions: list[str], dict[str, int], str | None (no imports since 3.9 and 3.10).
  • Generic functions and classes, with the 3.12 syntax: def first[T](xs: Sequence[T]) -> T ({{PEP 695|https://peps.python.org/pep-0695/}}). T is a type variable: whatever type goes in, the same comes out.
  • Protocol ({{PEP 544|https://peps.python.org/pep-0544/}}): structural typing, "anything with a close() method", checked statically. It is duck typing made checkable, and usually the right tool where you would have written an abstract base class.
  • TypedDict ({{PEP 589|https://peps.python.org/pep-0589/}}): the shape of a plain dict, such as a chat message; NotRequired marks optional keys. Still a plain dict at run time.
  • Literal: an exact set of allowed values, Literal["system", "user", "assistant"].
  • @overload: several signatures for one function whose return type depends on the argument type.
  • Abstract parameter types, concrete return types: accept Iterable, Sequence or Mapping (from collections.abc), return list or dict.

Python ran straight past mistakes 1 to 3 (a wrong role, a wrong type assigned, a value that might be None but happened not to be), because annotations are not checked at run time. It stopped at mistake 4 only because that one is also a runtime error. Now the checkers, which never run the code:

[[out:t1_mypy|mypy --python-version 3.14 t1_types.py (real output, mypy 2.4.0)]] [[out:t1_ty|ty check --output-format concise t1_types.py (real output, ty 0.0.84)]]
Read the results together
  • Both checkers caught mistakes 1, 2, 3 and 5 on the exact lines, including the one that Python only stumbles on at run time by luck (3: find_user can return None; the run happened to find the user).
  • Neither caught mistake 4, the only one that crashed. legacy has no annotations, so its parameter is treated as "any type", and anything goes. mypy goes further: by default it does not check the bodies of unannotated functions at all ({{mypy: no errors reported for obviously wrong code|https://mypy.readthedocs.io/en/stable/common_issues.html#no-errors-reported-for-obviously-wrong-code}}). Type checking protects only the code you annotate.
  • reveal_type prints the inferred type: str from both checkers, and, at run time (3.11+), Python prints "Runtime type is 'str'".
  • Conn never mentions SupportsClose and passes; int fails because it has no close. That is a Protocol at work.
What it solves
Whole classes of bugs found before running (None handling, wrong keys, wrong argument order); editor completion; documentation that cannot go stale.
What it costs
Time writing annotations; occasional fights with the checker over code that is correct but hard to express; nothing at run time.
Habits
Annotate every public function and every boundary; turn on the checker in CI; validate external data at run time with Pydantic, because a TypedDict on json.loads(...) is a promise, not a check (the root's {{Types section|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} makes the same point for TypeScript).
