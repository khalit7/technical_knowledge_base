2. The data model: how syntax becomes method calls

The data model is the chapter of the language reference that says which method Python calls for each piece of syntax ({{Data model|https://docs.python.org/3/reference/datamodel.html}}; the old page called it "the single highest-value document in Python", and it is). The methods have double underscores on both sides, so people call them dunder methods or special methods. You almost never call them yourself; the syntax does.

Read the last three lines carefully. sum() starts from the integer 0, so it first computes 0 + Vec(1, 2); int.__add__ does not know Vec and returns NotImplemented, so Python tries the right operand's __radd__. v == (1, 2) is False rather than an error because both sides returned NotImplemented and Python fell back to identity. And v + 1 raises TypeError only after both sides declined.

NotImplemented is not NotImplementedError
Returning the singleton NotImplemented means "I do not handle this type; ask the other operand". Raising NotImplementedError means "this abstract method was not written" and stops the dispatch dead. Mixing them up is a common bug in operator methods.

Three rules people learn the hard way

  • Special methods are looked up on the type, not the instance. "Implicit invocations of special methods are only guaranteed to work correctly if defined on an object's type, not in the object's instance dictionary" ({{Special method lookup|https://docs.python.org/3/reference/datamodel.html#special-method-lookup}}). Setting x.__len__ = ... on one object does nothing for len(x). This lets CPython skip the instance dict on every operator.
  • A subclass on the right goes first. "If the operands are of different types, and the right operand's type is a direct or indirect subclass of the left operand's type, the reflected method of the right operand has priority" (same page). So a subclass can override how it combines with its parent from either side.
  • __eq__ and __hash__ travel together. "A class that overrides __eq__() and does not define __hash__() will have its __hash__() implicitly set to None" (same page). Objects that compare equal must have equal hashes, and a hash must not change while the object is in a dict or set; that is why mutable built-ins are unhashable and why a dict key should be immutable.

The {{Data model|#t-pa-dm}} tab replays 19 of these dispatches step by step, each from a real run that logged which method Python called, in order: the reflected and subclass-first cases of +, == falling back to identity, bool falling back to __len__, the old __getitem__ iteration protocol, with swallowing an exception, and the four outcomes of an attribute lookup.

What it solves
Your types plug into every built-in, library and syntax form: sorted, sum, dict, f-strings, with, PyTorch's __torch_function__, NumPy's __array__.
What it costs
Every operator is a method lookup and call; that is a large part of why pure-Python arithmetic is slow (section 11).
When not to
Do not overload operators with surprising meanings; + should combine, == should compare. Prefer a dataclass (section 5) when you only need __init__, __repr__ and __eq__.
