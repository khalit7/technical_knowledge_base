4. Functions, closures and decorators

def is a statement that runs: it builds a function object (code, defaults, a reference to the enclosing scope) and binds it to a name. Functions are values like any other: you can pass them, return them and store them in dicts. Three consequences follow.

Parameters: positional-only, keyword-only and the catch-alls

A / in the parameter list makes everything before it positional-only; a * makes everything after it keyword-only. *args collects extra positional arguments into a tuple and **kwargs extra keyword arguments into a dict. Keyword-only parameters are the cheap way to stop callers from passing 0.2 to the wrong slot.

[[predict:f5_params]]

The first error is worth a second look. Because call has **extra, the keyword model="m1" is not rejected as "positional-only passed as keyword"; it is accepted into extra, and the positional slot is then reported missing.

Closures: functions that remember variables

A function defined inside another can read the outer function's variables after the outer one has returned; it keeps them in cells, visible as __closure__. Two rules cause most closure bugs. A closure captures the variable, not its value at the time, so it sees whatever the variable holds when it finally runs (late binding). And any assignment to a name inside a function makes that name local to the whole function, unless you declare it nonlocal (enclosing function) or global (module).

[[predict:f1_closure]]

Decorators

A decorator is a function that takes a function and returns a replacement; @timed above def work means exactly work = timed(work). Decorators stack bottom-up: the one nearest def is applied first. Always wrap with functools.wraps, or the replacement loses the original's name, docstring and signature (and tools such as pytest, FastAPI and debuggers see "wrapper").

[[run:f2_decorator]]

A decorator with arguments, @retry(times=4), is one level deeper: retry(times=4) runs first and returns the actual decorator. This is the shape of a real retry helper for a model API: retry only errors that can succeed on a second try (connection resets, timeouts, rate limits), with exponential backoff and random jitter, and never retry a 400.

[[run:f3_retry]]

Backoff, jitter and retry budgets as a reliability pattern (and why retries without them make outages worse) are on {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}. In production use a library such as tenacity or the retry built into your SDK client; the point here is that it is twenty lines of ordinary Python.

Caching with functools.cache and lru_cache

@functools.cache (unbounded) and @functools.lru_cache(maxsize=N) (least recently used entries evicted) store results keyed by the arguments ({{functools|https://docs.python.org/3/library/functools.html}}). Recursive Fibonacci makes the effect visible: 81 calls instead of 242,785 for a smaller input.

[[run:f4_cache]]
Caching pitfalls
Arguments become a dict key, so they must be hashable (the TypeError above). The cache holds strong references to every argument and result, so lru_cache on a method keeps each self alive "until they age out of the cache or until the cache is cleared" (with cache, which never evicts, for the life of the process); for methods without arguments the {{Python FAQ|https://docs.python.org/3/faq/programming.html#how-do-i-cache-method-calls}} suggests functools.cached_property, which lives and dies with the instance. And a cache is invisible state: a function whose result depends on time, a file or a random seed must not be cached.
What it solves
Cross-cutting behaviour (timing, retries, caching, auth, registration in a framework such as FastAPI's @app.get) written once.
What it costs
An extra call per invocation, and indirection when reading a stack trace.
When not to
When a plain function call at the call site would be clearer, or when the decorator changes the function's signature in ways type checkers cannot follow.
