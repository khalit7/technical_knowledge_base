A programming language is a set of decisions about what the machine should do for you and what you must do yourself. Python, C++, Rust and TypeScript made those decisions differently because each was built to answer a different founding problem. Once you know the problem, almost every rule of the language follows from it, and the rules stop looking arbitrary.

How this page teaches. You know Python, so Python is the reference column everywhere: each section shows what Python does, then what each other language makes you do instead, and why. Research on experienced programmers learning a second language found that they learn by mapping onto what they already know, and that most of their trouble comes from the places where the mapping silently breaks: in 450 Stack Overflow questions across 18 languages the authors found 276 instances of interference from a faulty assumption carried over from another language, and interviews showed programmers "make failed attempts to relate a new programming language with what they already know" (Shrestha, Botta, Barik and Parnin, ICSE 2020). So every section ends with a false friends box: things that look like Python and are not.

The one idea to keep
Each language moved one kind of mistake to a different moment. Python finds it while the program runs and tells you clearly. C++ trusts you and, when you are wrong, may give no signal at all (undefined behaviour). Rust refuses to compile until it can prove a whole class of mistakes absent. TypeScript checks while you edit, then removes every check before the code runs. Most of what feels strange in a new language is that language catching, at its moment, a mistake Python would have caught at a different one.

1. Four philosophies

A founding value is the goal a language's designers would not give up when two goals conflicted. Each of the four wrote theirs down. Read these four quotes slowly: every later section of this page is one of them playing out.

Python (early 1990s)

"Readability counts." "Explicit is better than implicit." "Errors should never pass silently." "There should be one-- and preferably only one --obvious way to do it."

From PEP 20, The Zen of Python. The programmer's time matters more than the machine's: no declarations, no compile step, everything an object you can inspect, and a mistake produces a clear exception at the line that made it.

Costs: every value carries type information and a reference count, and every operation is looked up while the program runs, so a plain Python loop is tens of times slower than compiled code (section 13).

C++ (1985)

"You don't pay for what you don't use. What you do use is just as efficient as what you could reasonably write by hand."

The zero-overhead principle (cppreference, after Stroustrup), plus compatibility with C: C++ began in 1979 as "C with Classes" and shipped as Cfront 1.0 in 1985 (cppreference history). Nothing is checked unless you ask, so abstractions can compile to the same machine code as hand-written C.

Costs: the language trusts you. Reading freed memory, overflowing a signed integer or racing two threads is undefined behaviour: no error, and no guarantee about what happens (section 10).

Rust (1.0 in 2015)

"with no runtime or garbage collector" ... "Rust's rich type system and ownership model guarantee memory-safety and thread-safety, enabling you to eliminate many classes of bugs at compile-time."

From rust-lang.org ("Performance" and "Reliability"; Rust 1.0 was announced 15 May 2015). C++'s speed without C++'s undefined behaviour, by making the compiler prove who owns each value and who may change it.

Costs: the compiler rejects programs that are correct but that it cannot prove correct, so the first weeks are spent learning its rules; compile times are long.

JavaScript (1997 standard) and TypeScript (2012)

"Use a consistent, fully erasable, structural type system." Non-goal: "Apply a sound or 'provably correct' type system. Instead, strike a balance between correctness and productivity."

From TypeScript's Design Goals. TypeScript (first released as 0.8 in October 2012) is JavaScript plus types that are checked and then deleted. JavaScript itself appeared in Netscape's browser and was standardised as ECMAScript in June 1997 (ECMA-262, Introduction). JavaScript's own rule is older: "'don't break the Web' is the number one design principle" for anything shipped in browsers (Mathias Bynens, V8 team, 2018), so JavaScript's old mistakes can never be removed, only avoided.

Costs: types can be wrong at run time (nothing checks data arriving from the network), and JavaScript's quirks (one number type, two kinds of "nothing") stay forever.

Two of these are about the programmer (Python's readability, TypeScript's productivity) and two about the machine (C++'s zero overhead, Rust's zero overhead plus proof). That split predicts most of this page: Python and TypeScript share objects freely and clean up with a garbage collector; C++ and Rust lay values out exactly as written and free them at a known moment.

2. How code runs

A processor only executes machine code: simple instructions such as "load this byte", "compare with 97", "add 1", "jump back". Every language is a different route from your text to those instructions, and the route decides two things: when the translation happens and how much it knows when it happens.

  • Ahead-of-time compilation (C++, Rust): a compiler translates the whole program into machine code before it runs, and ships a file the processor executes directly. Both clang (C++) and rustc (Rust) hand their work to LLVM, the same optimiser and code generator.
  • Bytecode plus an interpreter (CPython): Python first compiles your file into bytecode, instructions for an imaginary stack machine, then a loop written in C (the interpreter) reads one bytecode instruction at a time and does what it says. Since 3.11 the interpreter rewrites hot instructions into faster, type-specialised forms while the program runs (PEP 659).
  • Interpret first, compile the hot parts (JavaScript in V8): V8 compiles JavaScript to bytecode for its Ignition interpreter, watches which types actually flow through each function, and compiles hot functions to machine code with its optimising compilers (Sparkplug, Maglev and TurboFan; V8 blog). This is a JIT, a just-in-time compiler. If a guess turns out wrong (a new type arrives), V8 throws the machine code away and goes back to the interpreter: a deoptimisation.
  • Erase, then run as JavaScript (TypeScript): tsc checks the types and writes JavaScript with every type annotation removed; Node 22.18 and later can also run a .ts file directly by blanking the annotations out (Node docs). Either way, what runs is plain JavaScript in V8. Types never exist at run time.

Everything shown is real output: Python's own dis module, clang's and rustc's assembly, V8's bytecode and its optimised machine code printed by node --print-opt-code, and tsc's output. What the instruction counts mean. For each character, CPython executes 29 bytecode instructions, and each bytecode instruction is itself dozens of machine instructions inside the interpreter (fetch the instruction, jump to its handler, check types, update reference counts). The compilers turned the same loop into 16 (clang) or 17 (rustc) machine instructions per byte in its simplest form, and then went further: they noticed that each step only depends on the current and the previous byte, and rewrote the loop to process 8 (clang) or 32 (rustc) bytes at once with SIMD instructions. V8 got close to the compilers' simple version, after it had watched the function run. That is most of the speed gap measured in section 13, before any library or algorithm is involved.

False friends for a Python programmer
  • "Python is interpreted line by line." It is compiled to bytecode first (you have seen the .pyc files in __pycache__); only the bytecode is interpreted.

3. Types

A type says what kind of value something is and therefore what you may do with it: you can iterate over a string, not over an integer. Every language checks types; the question is when. A dynamically typed language checks each operation as it runs, on the actual values. A statically typed language checks the whole program before it runs, from what the code declares. Gradual typing sits between: you add annotations where you want them and a separate checker reads them, as with Python's type hints and TypeScript.

Two more distinctions you will meet

  • By name or by shape. In C++ and Rust a value fits a type only if it was declared as that type (nominal typing). In TypeScript any object with the right fields fits (structural typing), much like Python's duck typing, but checked before running; section 8 shows both.
  • Sound or not. A sound type system never lets a value of the wrong type through. Rust's safe subset aims for soundness; TypeScript says plainly that it does not (its non-goal, quoted in section 1): any, type assertions (x as Foo) and data from JSON.parse pass unchecked. Python's checkers are similar: an unannotated function is not checked at all.
What it costs
Static types cost writing them (less than you expect: Rust and TypeScript infer most local types) and a compile step. Dynamic types cost finding the mistake later, in tests or in production, and cost speed: an interpreter that does not know n is an integer must check before every addition (section 2). Gradual types cost discipline: the checker sees only what you annotate.
False friends for a Python programmer
  • "Type hints make Python check types." They do not; only a separate tool does. The same is true of TypeScript at run time: a Message type on JSON.parse(line) is a promise you made, not a check. Validate data at the boundary (Pydantic in Python; zod or a hand-written guard like the Rosetta program's isMessage in TypeScript).
  • "auto in C++ or let in Rust means dynamic." Both mean "infer the type now"; the type is still fixed at compile time and cannot change later.
  • "Rust's u64 is like Python's int." It is a fixed 64-bit unsigned integer; section 7 shows what happens at its limit.

4. Names, values and mutation

In Python a variable is a name attached to an object; b = a attaches a second name to the same object, so a change made through either name is visible through both. Two names for one object are called aliases. JavaScript and TypeScript work the same way for objects and arrays. C++ and Rust do not: there a variable is the value, a region of memory of a known size, and b = a must decide what happens to that memory. C++ copies it. Rust moves it: b becomes the owner and a may no longer be used.

sharessaved and top are one list; appending through one changes "both". Copying is explicit: top.copy() or list(top).

copiessaved = top copied the vector and every string in it (new memory for each). Sharing is explicit: a reference, std::vector<std::string>& alias = top, is a second name like Python's. The default copy is safe but can be expensive for large values, which is why C++ code passes const T& everywhere.

moves; refusedError E0382, "borrow of moved value": after let mut saved = top; the vector belongs to saved, and using top is a compile error. Nothing was copied (moving a Vec copies three machine words: pointer, length, capacity). The compiler even suggests .clone() if you really wanted a copy.

sharesExactly like Python: both names reach one array. const only stops the name from being re-pointed; the array can still change.

Why Rust chose moves: if exactly one variable owns each value, the compiler always knows who must free it and when (section 5), and there is never a hidden second name that could change the value under you. Rust then lets you borrow a value through a reference: any number of shared, read-only borrows (&T), or exactly one exclusive borrow that may change it (&mut T), never both at once. That single rule, "aliasing or mutation, not both", is what sections 5 and 9 build on.

False friends for a Python programmer
  • "Passing a vector to a C++ function lets it change my vector." Not unless the parameter is a reference (T&); by default the function gets its own copy.
  • "const means immutable." In JavaScript, const arr = [] can still be pushed to; in C++ const applies to what it is attached to (the pointer or the thing pointed to); in Rust everything is immutable unless declared mut.
  • "Rust's move is like Python's assignment." It is closer to handing over the only key: the old name is dead.

5. Memory and lifetimes

This is the axis where the four differ most, and the one Python hides most completely. It is worth learning the machine underneath once, concretely; C++ is the language that shows it most plainly.

The machine underneath

  • Memory is one long row of numbered bytes. The number of a byte is its address, usually printed in hexadecimal (base 16): 0x10081d500 is 16 bytes after 0x10081d4f0. A pointer is a value that holds an address: 8 bytes on a 64-bit machine.
  • The stack and the heap. Each function call gets a small block of memory for its local variables, the stack frame, released automatically when the function returns. Anything that must outlive the call, or whose size is only known at run time (a list that grows), goes on the heap, which someone has to release explicitly. "Who releases heap memory, and when" is the question this section is about.
  • The processor reads memory in cache lines. Main memory is far slower than the processor, so the processor keeps recently used memory in small fast caches, filled one cache line at a time: this M1 Pro reports 128-byte lines (sysctl hw.cachelinesize; most Intel and AMD processors use 64). Reading one byte brings its whole line in, so data that sits together is read almost for free, and data scattered across memory costs a slow trip per line.
  • Values have a size and an alignment. A record of a 4-byte user id and an 8-byte token count takes 16 bytes in C++ and Rust, not 12: the 8-byte field must start at an address divisible by 8, so the compiler inserts 4 bytes of padding (offsetof(Record, tokens) printed 8).

JavaScript arrays of objects are laid out like Python's (pointers to heap objects), except that V8 stores small integers inside the pointer itself ("Smis", V8 blog).

Why NumPy and PyTorch are fast from Python
A NumPy array or a PyTorch tensor is one Python object that owns a contiguous C buffer, laid out like the C++ vector above. The loop over it runs in C or C++, so neither the interpreter nor the pointer-chasing is paid per element. That is the whole trick behind "vectorise your Python".

The four strategies differ most on one classic bug. Keep a reference to the first user's name, then keep adding users: the list grows, and growing a list means allocating a bigger buffer, moving the elements and freeing the old buffer. What happens to the reference?

The C++ program compiles without a warning and, run normally, printed first user: followed by nothing: it read whatever was left in freed memory and carried on. Nothing guarantees it will print nothing next time; it could print garbage or crash. Only AddressSanitizer, a checking mode you compile in for testing (-fsanitize=address), turns it into a report. Rust refuses the program at the moment of the push, with error E0502: you may not change users while first borrows from it. Python never has the bug, because first holds its own reference to the string object, not to the list's slot; the object lives until the last reference goes, and CPython frees it at that exact moment.

6. Errors and nothingness

Two questions every program meets constantly: what to do when an operation fails (the line is not valid JSON), and how to say "there is no value" (a user with no entry). Python answers both with mechanisms that are invisible in a function's signature: an exception can come out of almost any call, and almost any variable could be None. Rust answers both with ordinary return values whose types say so, which the compiler makes you handle.

Nothingness: a key that is not there

None, or an exception.get() returns None, a real object meaning "nothing"; d[k] raises KeyError. Whether you checked is up to you (a type checker can warn when an Optional value is used unchecked).

silently insertsThe false friend of this section: per_user["nobody"] does not fail; it inserts a zero for the missing key and returns it, so the map grew from 1 to 2 entries. Use find() or contains() to ask without changing. C++'s "nothing" for pointers is nullptr, and dereferencing it is undefined behaviour.

refused at compile timeget() returns Option<&u64>: either Some(&value) or None. An Option is not a number, so n + 1 does not compile (E0369); you must say what None means, here with unwrap_or(0). Rust has no null at all in safe code.

refused by tsc, runs to NaNMap.get returns number | undefined. With strict on, tsc refuses the addition (TS18048, 'n' is possibly 'undefined'); run anyway, undefined + 1 is NaN and nothing complains. JavaScript has two "nothings", null and undefined.

Errors: a line that does not parse

The running program has to survive bad lines (the input has eight). Python and TypeScript wrap the parse in try; Rust's serde_json::from_str returns a Result, Ok(value) or Err(error), and C++23 added the same idea as std::expected.

exceptionsDifferent failures arrive as different exception types (here a TypeError and a JSONDecodeError; a missing field would be a KeyError), caught together. Nothing in json.loads's signature says it can raise; you learn it from the documentation or from production.

errors are valuesparse says in its type that it can fail (Result<Message, serde_json::Error>), the ? passes an error up to the caller in one character, and match must handle both Ok and Err or it does not compile. serde also checked the shape (a user that is a number is an error), which Python needed an explicit isinstance for. For bugs rather than expected failures Rust has panic!, which stops the thread (section 10).

expected, uncheckedstd::expected<long, std::string> (C++23, compiled with LLVM clang 23) holds a value or an error, like Rust's Result. But the last line shows the difference in philosophy: *parse_count("94x1") reads the value of an error without any check, which is undefined behaviour, and printed garbage. C++ gives you the vocabulary; Rust makes you use it. Most C++ code, including the standard library, still reports errors with exceptions.

What it costs
Exceptions keep the happy path short and cost nothing until thrown, but hide which calls can fail. Result and Option make every failure visible in the types and force a decision at every call (the ? operator keeps that cheap to write); the cost is verbosity at the edges, and .unwrap() calls that crash when you guessed wrong.
False friends for a Python programmer
  • "map[key] fails for a missing key." In C++ it inserts; in JavaScript a plain object or Map returns undefined; only Python raises.
  • "Rust's panic! is an exception you catch." It is meant for bugs and normally ends the thread; recoverable errors are Results.
  • "catch (e) gives me an Error." In JavaScript anything can be thrown, so TypeScript types e as unknown and makes you check.

7. Numbers and text

Short, because the rules are simple once seen, and dangerous because they look identical across languages until they are not.

no overflowIntegers grow as needed (263 is fine), // rounds down (floor: -7 // 2 is -4), and a str is a sequence of Unicode code points: len("café 日本 😀") is 9, and s[3] is the whole é.

overflow is undefined behaviourIntegers are fixed-size, and overflowing a signed one is undefined behaviour: the optimised build happened to print the wrapped value, and only the UndefinedBehaviorSanitizer (-fsanitize=undefined) reported it. Division truncates towards zero (-7 / 2 is -3). A std::string is bytes: the same text is 17 bytes, and s[3] is half of the é's two-byte UTF-8 encoding.

checked in debugOverflow panics in a debug build ("attempt to add with overflow") and wraps in a release build, unless you choose explicitly with checked_add (returns an Option) or wrapping_add. Division truncates like C++; div_euclid gives Python's answer. A String is UTF-8 bytes (len() is 17) and cannot be indexed by position at all: s[3] is refused (E0277), because byte 3 is not a character. You iterate .chars() or .bytes() instead.

one float typeEvery number is a 64-bit float, so integers are exact only up to 253 (253 + 1 prints as 253), / never rounds, and BigInt (2n ** 63n) is a separate type. Strings are UTF-16 code units: the emoji counts as 2 (length is 10 for 9 characters) and s[8] is half of it, a lone surrogate.

All four print 0.1 + 0.2 as 0.30000000000000004: they share the same IEEE 754 64-bit floating-point hardware, explained on the Numerical computing for ML page. The running program counts ASCII letters and digits only, so the "what is a character" question never changes its answer; the Rosetta tab shows how each version walks the text (Python by code points, Rust and C++ by bytes, TypeScript by UTF-16 units).

False friends for a Python programmer
  • "len(s) is the number of characters" is true only in Python. Rust's len() and C++'s size() count bytes; JavaScript's length counts UTF-16 units.
  • "Integer division rounds down." Only Python's // does; C++, Rust and JavaScript's Math.trunc round towards zero, which differs for negative numbers.
  • "An int in C++ is like a Python int." It is usually 32 bits, overflowing past 2,147,483,647, and that overflow is undefined behaviour.

8. Abstraction and polymorphism

Polymorphism means one piece of code working with many types. In Python you get it for free by duck typing: total(items) works on anything that has a .tokens() method, and a Protocol lets a type checker verify it. The other three make the requirement explicit, in three different ways.

checked when calledThe Protocol documents the requirement and lets mypy or ty check it; Python itself only fails when .tokens() is called on an int, deep inside total.

checked at compile timeA template is compiled once per type it is used with. A C++20 concept (HasTokens) states the requirement, so the error says "unsigned int does not satisfy HasTokens" instead of a page of template errors. For run-time choice, C++ also has virtual functions and inheritance.

checked at compile timeA trait is opted into explicitly (impl HasTokens for Message); the error E0277 even lists which types do implement it. Generic code (total<T: HasTokens>) is compiled once per type, called monomorphisation; dyn HasTokens is the alternative with one compiled copy and a table of function pointers looked up at run time. Rust has no inheritance.

checked by tsc, by shapeAn interface is structural: any object with a tokens(): number method fits, with no declaration, like a checked Protocol. Calling total([42]) would be refused by tsc. At run time it is plain JavaScript, so the check exists only before running.

What it costs
Monomorphisation gives the fastest calls and the largest binaries and longest compiles; dynamic dispatch (virtual, dyn, and every Python method call) costs a lookup per call but compiles once. Python and TypeScript need no declarations; C++ concepts and Rust traits make you write the contract down, which is also documentation.
False friends for a Python programmer
  • "A Rust trait is an abstract base class." There is no inheritance of fields; a trait is closer to a Protocol a type must opt into.
  • "Templates are generics." C++ templates are checked when used with a concrete type (concepts help); Rust generics are checked once, against their bounds, when defined.

9. Concurrency

A thread is a separate sequence of instructions inside one program, sharing the program's memory; on a machine with several cores (this one has 10), threads really run at the same instant. Shared memory is the danger: counter += 1 is three steps (read the value, add one, write it back), and if two threads interleave those steps, one update is lost. Two threads touching the same memory, at least one writing, with nothing ordering them, is a data race. The four languages took four positions on it, and on a second, separate question: how to wait for many slow things (network calls) at once without a thread for each, which is asynchronous code.

JavaScript cannot have the bug with ordinary code, because only one piece of your code runs at a time and it is only interrupted at an await; it gets it back as soon as workers share memory. C++ loses updates at -O0 and gets the right answer at -O2 only because the optimiser, allowed to assume no data race, turned a million increments into a single addition: the bug is still there, just hidden. Rust does not let the racy program exist.

What it costs
Python's GIL costs parallelism: the Benchmark tab runs the token counter on 4 threads, and with the GIL it is no faster than on 1; the free-threaded build costs some single-thread speed (the Python 3.14 docs give two figures: about 1% on macOS aarch64 to 8% on x86-64 Linux in the free-threading HOWTO, "roughly 5-10%" in What's New in 3.14; on this M1 Pro the Benchmark measured no penalty within run-to-run spread) and needs extensions built for it. C++ costs vigilance and ThreadSanitizer runs. Rust costs wrapping shared state in Arc<Mutex<T>> or atomics, which the compiler demands. JavaScript costs real parallelism: CPU-heavy work blocks the one thread unless moved to a worker.
False friends for a Python programmer
  • "Threads in Python cannot run in parallel, so other languages' threads are the same." In C++, Rust and free-threaded Python they really run at once, and your racy Python habits become real bugs.
  • "async makes code run in parallel." In Python and JavaScript it interleaves waiting on one thread; only Rust's tokio, by default, spreads tasks over several threads.
  • "JavaScript is single-threaded, so it has no concurrency bugs." Two async functions can still interleave at every await, so a read before an await and a write after it can conflict.

10. Safety and undefined behaviour

A language is memory-safe if no program written in it can read or write memory it does not own. Python, JavaScript and safe Rust are; C++ is not. C++'s alternative is undefined behaviour: a list of operations (reading past the end of an array, reading freed memory, overflowing a signed integer, a data race) that the standard declares meaningless. The compiler is allowed to assume they never happen and optimise accordingly, so a program that does one of them may do anything, including appearing to work. The zero-overhead principle is the reason: checking every index costs time, so C++ does not check unless you ask.

clear errorIndexError, at the exact line. Every access is checked.

undefined behaviourtop[5] is unchecked: it printed 0, whatever happened to be in memory after the vector. top.at(5) is the checked version and throws. AddressSanitizer turns the unchecked read into a "heap-buffer-overflow" report, 8 bytes after the 12-byte buffer. Compilers and standard libraries now offer "hardened" modes that check [] too; they are opt-in.

checked: panicget(5) returns None; top[5] panics with the length and the index. Indexing is always bounds-checked in safe Rust; the optimiser removes checks it can prove unnecessary (iterators, as in section 2, have none).

silent undefinedJavaScript returns undefined and the arithmetic becomes NaN, no error. tsc lets const x: number = top[5] through unless noUncheckedIndexedAccess is on (the Rosetta program turns it on), in which case it is refused.

Rust is not free of the problem; it fences it. Code marked unsafe may dereference raw pointers and call C, and inside it undefined behaviour is possible again. The point is that it is rare and searchable: the standard library is built on small unsafe cores wrapped in safe interfaces, and tools such as Miri check unsafe code for undefined behaviour. The Rustonomicon is the manual for that part of the language (Further reading).

False friends for a Python programmer
  • "If it ran and printed the right thing, it is correct." In C++ a program with undefined behaviour can print the right thing today and the wrong thing after a compiler upgrade. Run tests under AddressSanitizer and UndefinedBehaviorSanitizer.
  • "Rust programs cannot crash." They can panic (out of bounds, unwrap() on None, overflow in debug builds); what they cannot do in safe code is corrupt memory.

12. Tooling

Rust and modern Python have one tool that does almost everything; C++ has many that you assemble; JavaScript has several competing ones.

  • Python: uv (Astral, written in Rust) installs Python itself, creates environments, resolves and locks dependencies and runs scripts; ruff lints and formats; mypy, pyright or Astral's ty (in beta) check types; pytest tests.
  • C++: a compiler (clang, GCC, MSVC), a build system (CMake is the common one), a package manager if any (vcpkg, Conan, or none), sanitizers, clang-format and clang-tidy. There is no standard package manager, because compiled C++ libraries must match the compiler and flags they are linked with. Even the default language version differs: Apple clang 14 on this laptop defaults to C++98, recent Clang to C++17, GCC 16 to C++20, MSVC to C++14, so always pass -std=.
  • Rust: cargo builds, tests, benchmarks, documents, fetches and publishes; clippy lints, rustfmt formats; every published crate's documentation is built on docs.rs. One Cargo.lock pins every version.
  • TypeScript: a runtime (Node, Bun or Deno), a package manager (npm, pnpm, or Bun's), tsc for checking, and a test runner (vitest, or Node's built-in). Node runs .ts files directly by stripping types since 22.18; that does not type-check, so keep tsc --noEmit in CI.

Why each gap exists

A speed difference is only useful if you know where it comes from, because that tells you what a rewrite would buy. Each box below takes one cause, shows it measured on this program, and says what it costs.

1. Interpreter dispatch: the same characters, run two ways

CPython compiles tokens() to bytecode (a list of small instructions for a virtual machine) and then runs a C loop, the interpreter, that fetches each instruction, jumps to the C code for it, and does it on objects: every character is a one-character str object, every comparison returns a bool object. Rust and C++ compile the same loop ahead of time to machine code, instructions the CPU runs directly on raw bytes in registers. 7. Strings, I/O buffering, startup and the JIT

  • Strings. Python decodes the file's UTF-8 into str objects of code points as it reads; JavaScript strings are UTF-16; C++ std::string and Rust's String keep the UTF-8 bytes (Rust checks they are valid UTF-8, C++ does not). The compiled loops count over bytes, which is correct here only because every non-ASCII byte is 0x80 or above (PROGRAM.md, rule 3).
  • I/O buffering. Every version reads through a buffer (Python's open, C++ std::ifstream, Rust BufReader, Node's read stream), so the 39 MB arrive in large chunks rather than one system call per line. Reading and splitting the lines took Python : I/O is not the bottleneck for any variant. Output is five lines, so stdout buffering does not matter here; it would for a program that prints a line per record.
  • Startup. On an empty file, the native binaries finish in about a millisecond; CPython needs just to start (-c pass) and Node (Startup view above). For a command-line tool run thousands of times by a script, that floor can matter more than throughput. A cold bytecode cache costs Python more: against when every imported module must be compiled again (it happens once, after an install or upgrade). Node's compile cache made no measurable difference to this small script ( against ), and running the .ts file directly cost at startup against for the compiled .js.
  • The JIT. V8 first interprets JavaScript, then compiles hot functions such as countTokens to machine code using the types it has seen (just-in-time compilation). That is why Node is far faster than CPython on the character loop while starting slower than a native binary. CPython 3.14 has an experimental JIT too, built but switched off in the interpreter measured here (--enable-experimental-jit=yes-off).

So when is a rewrite worth it?

  • First, idiomatic Python. Replacing the hand-written character loop with a regex cut the time by for a two-line change.
  • Then move the hot loop, in batches. A PyO3 or nanobind function that takes the whole list costs one crossing; one call per item costs one per item, fine when each item is real work and wasteful for tiny functions (box 5).
  • Move the whole pipeline when the glue dominates. Here, parsing JSON into Python objects is the cost that remains; only the whole-file call removes it.
  • A rewrite in Rust or C++ is worth it for a tool run often on large data, or where startup matters; the price is the build setup and the longer code (Lines of code and Compile time views). Python stays the place to orchestrate.

Method and caveats

  • Wall time: hyperfine runs each command 2 times to warm up, then 7 times; the bar is the median, the whisker the fastest and slowest run, and the dots each run. Commands run without a shell (-N), output discarded.
  • Warm and cold: "warm" means the input is already in the operating system's file cache and the program has run before; every time on this tab is warm. Clearing the file cache needs administrator rights (purge), so a cold-disk start was not measured. What was measured cold is the language runtime's own cache: Python with an empty bytecode cache (every imported module compiled from source again) and Node with an empty compile cache; see the Startup view.
  • Memory: /usr/bin/time -l, maximum resident set size, median of 3 runs.
  • Startup: the same programs on an empty file, 3 warmups then 20 runs; for Python, Node and Bun also the bare runtime (-c pass, -e 0).
  • Lines of code: non-blank lines that are not only a comment, counted by src/bench/loc.py. The C++ count includes the -line JSON parser (json_lite.hpp) the C++ version must carry because the standard library has none; the Rust count includes Cargo.toml but not serde_json.
  • Compile time: hyperfine, median of 3 to 5 runs; Rust and the PyO3 extension from a clean build including their dependencies (serde, pyo3), and Rust again after editing main.rs.
  • Background load: the laptop was in normal use (other programs running); the load average (1, 5 and 15 minutes) at the start was . Single-threaded results are stable to a few per cent (compare the whiskers); thread-scaling results are the most affected.
  • One machine, one input. These numbers rank the languages on this job on an Apple M1 Pro. A program dominated by different work (numeric arrays, network waits, many small allocations) would rank differently.
