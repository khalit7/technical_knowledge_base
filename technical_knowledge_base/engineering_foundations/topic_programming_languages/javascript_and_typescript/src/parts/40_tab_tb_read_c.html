Unions and narrowing: where TypeScript earns its keep

A union A | B is a value that is one of several types. You can only use what all members share: on string | number | null you cannot call toFixed, because a string has no such method and null has nothing at all.

Narrowing is how you get to a single member: tsc follows your ifs, switches and early returns and, at each line, knows which members are still possible. Every check JavaScript can do at run time narrows:

CheckNarrows
typeof x === "string"primitives: string, number, boolean, bigint, symbol, undefined, function, object
x === null, x == null, if (x)removes null and undefined (truthiness also removes "", 0, false: a classic bug with numbers)
Array.isArray(x), x instanceof Datearrays, class instances
"text" in xobject members that have that property
x.type === "text"a discriminated union to one member (below)
isCat(x) where isCat(a): a is Catwhatever your own predicate says (unchecked: it can lie)

Discriminated unions: the pattern for LLM events, tool calls and states

A discriminated union is a union of object types that share one literal field (the tag, here type). Checking the tag narrows to exactly one member, with its own fields. This is how every LLM SDK types its streaming events, and how you should model anything with states.

Your own narrowing: type predicates and assertion functions

A function returning a is Cat (a type predicate) narrows its argument where it is called, and .filter(isCat) even returns Cat[]. A function declared asserts v is string narrows everything after the call, or throws. Both are trusted blindly:

Generics and constraints

A generic function has type parameters, written in angle brackets: first<T>(xs: T[]): T | undefined works for any element type and keeps it, instead of losing it to any. tsc infers T from the arguments, so callers almost never write it.

A constraint (T extends { length: number }) says what T must at least have; K extends keyof T says "K is one of T's keys", which is how pluck(rows, "tokens") knows it returns number[]. The constraints are what make the errors precise:

Two rules of thumb. A type parameter that appears only once in a signature does nothing (f<T>(x: T): void is just f(x: unknown): void). And a generic that needs a comment to be understood is probably worse than two plain functions.

From Python
def first[T](xs: list[T]) -> T | None (PEP 695 syntax, Python 3.12+) is the same idea; K extends keyof T has no direct Python equivalent (the closest is a Literal of field names written by hand).

Types from values: keyof, typeof, indexed access, as const, satisfies

TypeScript has a small language for computing types from other types and from values. The four everyday operators, with the types tsc computed (to make tsc print a type, the snippets assign it to never with satisfies and read the error message; the trick is used throughout this page):

  • typeof DEFAULTS in a type position reads the type of a value, so one constant is the single source of truth for both.
  • keyof T is the union of T's keys; T["temperature"] (an indexed access type) is the type of one property.
  • (typeof MODELS)[number] turns an as const array into the union of its elements: write the list once, get the type for free.
  • Note the order in the printed unions: "large" | "medium" | "small" is not the order the array was written in. TypeScript 7 orders union members deterministically (stableTypeOrdering is "true by default, and cannot be turned off", says the 7.0 post), so do not read meaning into the order in an error message.

satisfies: check without forgetting

An annotation (const a: Record<string, Route>) checks the value and then replaces its type with the annotation, so the specific keys are forgotten. satisfies (TypeScript 4.9) checks the value against the type and keeps the inferred type: the wrong auth on line 4 is caught, and so is the typo b.hom. Prefer satisfies for configuration objects and lookup tables; and never as to get the same effect (as checks nothing).

Mapped, conditional and template literal types (at a practical level)

The utility types above are not built in magic: they are written in TypeScript's type language, which has loops over keys, if-then-else and string building. You will read these in library code more often than you write them.

Mapped types loop over keys: { [K in keyof T]: ... }. as renames keys, and -readonly or -? removes a modifier.

The best use of this machinery in application code is deriving types from one source (a schema, a const table, a route list) so they cannot drift apart.
