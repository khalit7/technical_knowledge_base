14. Bun and Deno

Node is not the only runtime. Bun runs on JavaScriptCore (Safari's engine) and bundles a runtime, package manager, test runner and bundler in one binary; it runs TypeScript directly. Bun announced it was joining Anthropic on 2025-12-02, noting that "Claude Code ships as a Bun executable" ({{Bun is joining Anthropic|https://bun.com/blog/bun-joins-anthropic}}); Bun 1.4 (2026-08-20) rewrote Bun itself from Zig to Rust ({{Bun 1.4|https://bun.com/blog/bun-v1.4}}). Deno (by Node's original author) runs on V8, is written in Rust, runs TypeScript directly, and is secure by default: no file, network or environment access without a flag. Since Deno 2 (2024) both run most Node code and npm packages. The same script, three runtimes:

m1_runtimes.sh
# One script, three runtimes. Bun (JavaScriptCore engine) and Deno (V8, Rust) run Node-style code too.
cat > "$WORK/rt.mjs" <<'JS'
import { readFileSync } from "node:fs";
const n = readFileSync(new URL(import.meta.url)).length;
console.log(`${typeof Bun !== "undefined" ? "bun " + Bun.version : typeof Deno !== "undefined" ? "deno " + Deno.version.deno : "node " + process.versions.node}: read my own ${n} bytes`);
JS
cd "$WORK"
echo '$ node rt.mjs'; node rt.mjs
echo '$ bun rt.mjs'; bun rt.mjs
echo '$ deno run rt.mjs   # Deno denies file access unless you grant it'; deno run --no-prompt rt.mjs 2>&1 | sed 's/\x1b\[[0-9;]*m//g' | head -3
echo '$ deno run --allow-read rt.mjs'; deno run --allow-read rt.mjs

Choose Node when
You want the default: the widest compatibility, LTS releases with a published schedule, governance by the OpenJS Foundation, and every tutorial and SDK tested on it.
Choose Bun when
Start-up and install speed matter (CLIs, scripts, tests), or you want one tool instead of five. Check that your native add-ons and edge-case Node APIs work.
Choose Deno when
You run code you do not fully trust (permissions), or want TypeScript, formatter, linter and test runner built in with web-standard APIs.

15. V8 performance notes

V8 does not interpret your code forever. It parses it to bytecode run by the Ignition interpreter, then compiles functions that get hot: Sparkplug (a fast baseline compiler), Maglev (a mid-tier optimising compiler, shipped in Chrome 117 in 2023) and TurboFan (the top tier) ({{V8 blog, Maglev|https://v8.dev/blog/maglev}}). The optimising tiers speculate from what they have seen: "this argument has always been a small integer", "this object always has this shape". When a guess breaks, the code deoptimises back to the interpreter and may be recompiled later. You can watch it:

n3_deopt.mjs
// Run with: node --trace-opt --trace-deopt n3_deopt.mjs | grep add   (V8 tells you when it optimises and when it gives up)
function add(a, b) { return a + b; }
let s = 0;
for (let i = 0; i < 200_000; i++) s = add(i, 1);       // only small integers: V8 compiles add for that
console.log("now call it with strings");
add("a", "b");                                         // assumption broken: deoptimise, back to the interpreter
for (let i = 0; i < 200_000; i++) s = add(i, 2);
console.log(s);

"Not a Smi": a Smi is V8's small-integer representation (31 or 32 bits, stored without allocating). The second lever is the hidden class (V8 calls it a "map"): objects with the same property names added in the same order share one, and each property access site caches the shapes it has seen ("inline caches"). A site that sees one shape is monomorphic and fast; past four it is megamorphic and does a slow lookup.

n1_shapes.mjs
// Run with: node --allow-natives-syntax n1_shapes.mjs  (the % functions are V8 internals, for learning only)
// V8 gives every object a hidden class ("map"): its property names in insertion order. Same order, same map.
const a = { x: 1, y: 2 }, b = { x: 5, y: 6 }, c = { y: 2, x: 1 };
console.log("a and b share a hidden class:", %HaveSameMap(a, b));
console.log("a and c (same keys, other order):", %HaveSameMap(a, c));
const d = { x: 1, y: 2 }; d.z = 3;
console.log("a and d after adding z:", %HaveSameMap(a, d));
const e = { x: 1, y: 2, z: 3 }; delete e.z;
console.log("after delete, e is in dictionary mode:", !%HasFastProperties(e));

n2_shapes_bench.mjs
// The cost of shapes: the same loop over objects of 1 shape and of 8 shapes (V8 inline caches, measured).
function sumX(objs) { let s = 0; for (let r = 0; r < 200; r++) for (let i = 0; i < objs.length; i++) s += objs[i].x; return s; }
function make(nShapes, n) {
  const out = [];
  for (let i = 0; i < n; i++) {
    const o = {}; const k = i % nShapes;
    for (let j = 0; j < k; j++) o["p" + j] = j;    // k extra properties BEFORE x: a different hidden class per k
    o.x = 1; out.push(o);
  }
  return out;
}
function time(label, objs) {
  sumX(objs); sumX(objs);                          // warm up: let the JIT compile sumX for what it has seen
  const t = []; for (let k = 0; k < 7; k++) { const t0 = performance.now(); sumX(objs); t.push(performance.now() - t0); }
  t.sort((p, q) => p - q);
  console.log(`${label.padEnd(36)} median ${t[3].toFixed(1)} ms per 2,000,000 property reads`);
}
time("1 shape (monomorphic call site)", make(1, 10_000));
time("4 shapes (polymorphic)", make(4, 10_000));
time("8 shapes (megamorphic)", make(8, 10_000));
real output, Node 24.21.0
1 shape (monomorphic call site)      median 1.6 ms per 2,000,000 property reads
4 shapes (polymorphic)               median 3.2 ms per 2,000,000 property reads
8 shapes (megamorphic)               median 8.3 ms per 2,000,000 property reads
What to do with this
Create objects of one kind in one place (a constructor, a class, or one literal shape), with all fields set, in the same order; do not add properties later; do not delete (set to undefined instead); keep arrays of one element type.
What not to do
Do not micro-tune before profiling: node --cpu-prof app.mjs writes a profile that Chrome DevTools opens, and node --prof is the lower-level option. Most slow Node services are slow because something blocks the event loop or waits serially, not because of shapes.
