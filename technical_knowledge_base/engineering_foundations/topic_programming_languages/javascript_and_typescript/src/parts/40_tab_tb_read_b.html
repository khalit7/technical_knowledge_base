A project and its tsconfig.json

A TypeScript project is a JavaScript project (package.json and node_modules: Part 1, section 13) with three additions: typescript as a dev dependency, a tsconfig.json that tells tsc what to check and how strictly, and type packages for anything untyped. The root page's Toolchain atlas tab ({{Topic: programming-languages|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}}) walks through creating one from an empty folder, including the two errors a fresh project hits (no "type": "module", and .ts import paths); this section explains what the options mean.

TypeScript 7's npx tsc --init writes this (comments removed; the generated file explains each line):

{
  "compilerOptions": {
    "module": "nodenext",
    "target": "esnext",
    "types": [],
    "sourceMap": true,
    "declaration": true,
    "declarationMap": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "strict": true,
    "jsx": "react-jsx",
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noUncheckedSideEffectImports": true,
    "moduleDetection": "force",
    "skipLibCheck": true,
  }
}

Every snippet on this page is checked with that file, plus "types": ["node"], "noEmit": true and "allowImportingTsExtensions": true (so files can import ./x.ts and run under Node), minus the output and JSX options that noEmit makes irrelevant, in a folder whose package.json says "type": "module". When a snippet changes an option, its file header says so.

Correction to the old page
The old "TypeScript: zero to expert" page said "tsc --init, then set "strict": true" and "add noUncheckedIndexedAccess too". In TypeScript 7 both are already in the generated file, and strict is the default even without a tsconfig since 6.0 (TypeScript 7.0 announcement). It also said @types packages "just work" once installed: since 6.0 types defaults to [], so even @types/node is ignored until you list it (shown below).

The options that matter, each with the error it produces:

strict: the family of checks you always want

strict switches on a group of options; the two you meet first are noImplicitAny (a parameter without a type is an error, not silently any) and strictNullChecks (null and undefined are separate types, not members of every type). The same file with strict off and on:

With strict off, tsc accepted a string | undefined as a string and the program crashed on found.length. With strict on, both lines are caught. Never turn it off; in an old codebase, turn it on and fix file by file.

noUncheckedIndexedAccess: an index may be missing

Without the option, scores[2] has type number even though the array has two elements. With it (the default from tsc --init), every index read is number | undefined until you check, as the output of the same code with the option on shows:

The cost: you write more checks (if (x !== undefined), ?? 0, or for...of instead of indexes). Most new projects keep it.

exactOptionalPropertyTypes: "may be absent" is not "may be undefined"

temperature?: number now means the key may be missing, not that it may hold undefined. Why it matters: JSON.stringify drops a key whose value is undefined, but "temperature" in opts and a spread such as { ...defaults, ...opts } do not: the spread overwrites the default with undefined ({{drill 20|#t-tb-drill}}). If you need both, write temperature?: number | undefined.

types: which global type packages load

process is a Node global, described by @types/node. Installed is not enough: since TypeScript 6.0 the default is "types": [] and you list what your program may use, ["node"] for a Node program. The message says so, which is a good habit with tsc: read the whole error, the fix is often in it.

The module options

  • "module": "nodenext" makes tsc resolve imports exactly as Node does: ES modules or CommonJS decided by the nearest package.json "type" field, and relative imports need their file extension (./tokens.ts or ./tokens.js). Part 1 explains ESM versus CommonJS: Part 1, section 6 (Modules). Use "bundler" resolution instead only when a bundler (Vite, esbuild) builds the code.
  • verbatimModuleSyntax keeps every import you write and drops only those marked import type, so what Node runs matches what you wrote. Write import type { Msg } from "./types.ts" for type-only imports.
  • isolatedModules rejects code that a one-file-at-a-time stripper (Node, esbuild, Bun) cannot handle correctly. Keep it on.
  • skipLibCheck skips checking the .d.ts files in node_modules: one badly typed dependency then does not fail your build. Keep it on.

Each option is documented in the TSConfig reference.

Types, annotations and inference

You annotate with a colon after the name, as in Python: let n: number = 0, function f(x: string): number. The basic types are JavaScript's values: number (one type for ints and floats: a 64-bit double, see Part 1, section 2), string, boolean, bigint, null, undefined, arrays number[] (also written Array<number>), tuples [string, number] and object types { id: number }.

Most of the time you do not write types: tsc infers them from values. To see what it inferred, ask it to write a declaration file (.d.ts: the types of a module without its code). This is the real output:

Four rules show up here, and they explain many surprising errors later:

  • let widens, const keeps the literal. role has the type "user" (a literal type: exactly that string), because a const can never hold anything else; model is any string.
  • Object properties and array elements widen even in a const, because they can be reassigned: msg.role is string, not "user". This is why passing such an object to a function that wants "user" | "assistant" fails ({{drill 2|#t-tb-drill}}).
  • as const freezes everything: fixed is a readonly tuple of literals. Without it, ["ana", 3] is an array of string | number, not a pair.
  • Return types are inferred (avg returns number | null, with the null you might forget). The common convention: annotate parameters always (they cannot be inferred), and return types of exported functions (so a change inside cannot silently change your public API); let everything else be inferred.
From Python
Literal["user"] in Python is a literal type in TypeScript, but TypeScript infers it by itself for every const string. tuple[str, int] is [string, number]; list[int] is number[]; X | None is X | null or X | undefined (JavaScript has two "nothing" values; Part 1, section 2 explains when each appears).

Functions

Optional parameters (stop?: string) have the type string | undefined inside the function; default values (maxTokens = 256) make the parameter optional for callers and give it a type by inference; rest parameters collect into an array; void means "the return value is not meant to be used". A function type is written like an arrow: (text: string) => number, and when a function is passed where such a type is expected, its parameters are inferred from it (t above is a string without annotation). That is contextual typing, and it is why callbacks such as .map(s => s.length) rarely need annotations.

Overloads give one function several signatures, for when the return type depends on the argument type:

The callers see only the first two signatures; the third is the implementation and must handle every case. Use overloads sparingly: a union parameter or a generic (below) is usually clearer.

Objects: interface or type alias

There are two ways to name an object type, and they overlap almost completely:

  • interface names an object shape. Two declarations with the same name merge (that is how libraries let you add fields to their types), and extends builds on another interface.
  • type names any type: an object, but also a union ("user" | "admin"), a tuple, a function, or a computed type. & (an intersection) combines object types.
  • The pragmatic rule many codebases use: interface for object shapes, type for everything else. Pick one convention and move on.
  • ? marks an optional property, readonly a property that cannot be reassigned, and { [model: string]: number } (an index signature, same as Record<string, number>) any number of string keys.

readonly is checked only by tsc; at run time the object is an ordinary mutable object (use Object.freeze if you need run-time enforcement).

Excess property checks: why a typo is caught, sometimes

An object type means "at least these properties", so opts (which has model and an extra key) fits Options. As a special case, a fresh object literal written directly where a type is expected may not have unknown keys, because there the extra key is almost always a typo. Through a variable, the typo passes silently and temperature is never sent.

Structural typing: shape, not name

TypeScript compares types by their structure: a value fits a type if it has the right members, whatever class or name it came from. This is the deepest difference from Java, C# or Rust, and it is what Python's typing.Protocol does.

A string, an array, an instance of an unrelated class and a plain object all have a numeric length, so all four fit HasLength. When you need the opposite, two string types that must not mix (a user id and an order id), add a brand: a fake property that exists only in the type.

The brand costs nothing at run time (the value is still a plain string), and the only way to make a UserId is through a function you control (asUserId, ideally after validating). The root's Design space compares structural typing with Rust traits and C++ templates.

From Python
Python's type checkers are nominal by default (a class matches only its subclasses) and structural only for Protocols. TypeScript is structural everywhere, so you rarely need an interface to be "implemented": any object of the right shape fits.
