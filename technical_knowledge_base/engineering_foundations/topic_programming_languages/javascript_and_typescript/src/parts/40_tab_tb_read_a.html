TypeScript is JavaScript plus a type checker that runs before your program and then disappears. Everything below was run on this Mac on 2026-10-05 with TypeScript 7.0.2 (the native compiler) and Node 22.22.2: every error is the real tsc message, and every output is what Node really printed, crashes included.

In one screen

What it is
A checker (tsc) that reads JavaScript with type annotations and reports mistakes. The types are then deleted: Node, Bun or a bundler run plain JavaScript. Nothing is checked while the program runs.
The Python bridge
It is mypy or ty for JavaScript, with two differences: the community actually runs it on almost all code, and its types are richer (literal types, unions you can narrow, types computed from other types).
Where its value lives
Unions and narrowing: string | null is not a string until you check, and a union of tagged objects ({type: "text"} | {type: "tool_call"}) gets an exhaustive switch.
Where it lies to you
It is unsound on purpose: any, as, !, array covariance and method parameters let ill-typed values through. Data from outside (an LLM, an API, a file) must be checked at run time with zod.
The setup in 2026
npm i -D typescript, npx tsc --init (strict by default now), run .ts files directly with node, check with npx tsc in CI, test with vitest, lint with Biome or ESLint.
What changed in 2026
TypeScript 7.0 (2026-07-08) is the compiler ported to Go: 5.1 times faster here on zod's 37,722 lines, 8 to 12 times on Microsoft's large projects, same type rules, no programmatic API yet (typescript-eslint still needs TypeScript 6).

What TypeScript is: types that are erased

Here is a function with a type annotation (text: string) and a call that breaks it. Before reading the output: what do you think happens when Node runs this file?

Two programs, two jobs. tsc found the mistake (line 5, column 25). node never looked at the types: it deleted them and ran the JavaScript, which crashed on the same line. Running a .ts file does not check it. Only tsc checks.

And one cast is enough to silence the checker too: with 42 as any (an assertion, explained later) tsc reports nothing, and the crash is the same.

That is the whole model: type erasure. TypeScript's own design goals list as non-goals "add or rely on run-time type information in programs" and "apply a sound or 'provably correct' type system" (TypeScript Design Goals). From Python
Python's annotations are also ignored at run time, and mypy or ty is a separate step. Same model. The difference is cultural and practical: TypeScript projects run the checker on every change, almost every npm library ships types, and a TypeScript type is often more precise than its Python equivalent (literal types, narrowing on any field).

How a .ts file becomes something that runs

There are two ways to remove the types, and the animation runs both on the same file. Type stripping (what node file.ts, Bun, tsx and esbuild do) replaces every annotation with spaces, so line and column numbers in errors still point at your source. Compiling with tsc (when you set an outDir) writes new, reformatted JavaScript. Both outputs below are real: Node's own stripTypeScriptTypes function and tsc's emit.

Node's stripping is why some TypeScript syntax is now discouraged. An enum type-checks fine but Node cannot strip it, because an enum is not just a type: it creates a JavaScript object.

Node's strip-only mode rejects syntax that would need generated code. The fix is a TypeScript 5.8 option, erasableSyntaxOnly, which makes tsc reject that syntax up front (TypeScript 5.8), and the idiom that replaces enums: an as const object plus a type read off it.

Line 1 (the enum) and line 2 (a parameter property, constructor(public x: number), which secretly writes this.x = x) are rejected; lines 3 and 4 are the replacement: Role2 is both a value (the object) and a type ("user" | "assistant"). If you run .ts files with Node, turn erasableSyntaxOnly on.
