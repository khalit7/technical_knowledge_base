Checking data at run time with zod

Types are erased, so nothing checks data that arrives while the program runs: an HTTP body, a file, an environment variable, and above all the JSON an LLM writes. JSON.parse(text) as Reply is a promise you cannot keep. The answer is a schema library: you describe the shape once as a run-time object, it validates values, and TypeScript derives the static type from it. zod is the most used (4.6.5 here; zod.dev); valibot and ArkType are alternatives with the same idea.

Parsing LLM output

Model output fails in predictable ways: the JSON is wrapped in a Markdown fence or a sentence, a number arrives as a string, a field is missing, the reply is cut off by the token limit. A robust reader has three steps: find the JSON, JSON.parse it inside try, and validate with the schema, returning a typed result or an error message you can send back to the model for a retry.

The {{LLM JSON lab|#t-tb-zod}} runs ten such replies through a cast and three zod variants (default, strict, coercing) and shows every real outcome, including the two cases where the cast neither crashes nor complains and the program prints a wrong value.

Strict, coerce, transform

  • z.object drops unknown keys silently; z.strictObject rejects them (useful to catch a model inventing fields; harmful if the API adds fields later).
  • z.coerce.number() runs Number(x) first, so "7" becomes 7, but "2.1 million" becomes NaN and fails (see the lab).
  • .transform converts after validating, and z.infer gives the transformed type.

Testing with vitest

Linting and formatting

tsc checks types; a linter checks patterns that are legal but usually wrong, and a formatter fixes layout. Two choices in 2026:

  • Biome (2.5.15 here; biomejs.dev): one Rust binary that lints and formats, with no plugins to install. The ruff of JavaScript.
  • ESLint with typescript-eslint (typescript-eslint.io): the long-standing standard, with type-aware rules that ask the TypeScript compiler about each expression, plus Prettier for formatting.

The TypeScript 7 transition

TypeScript 7.0 was released on 2026-07-08 (npm publish time of 7.0.2 the same day). It is the existing compiler ported from TypeScript to Go, line by line, so the type rules are the same; what changes is speed, the options that were removed, and the missing API (Announcing TypeScript 7.0).

Speed. Microsoft reports 8 to 12 times faster full builds on large projects (VS Code 125.7 s to 10.6 s, Sentry 139.8 s to 15.7 s, Playwright 12.8 s to 1.47 s), from native code and shared-memory multithreading. Measured here on a smaller project, zod's own TypeScript sources:

About 5 times, less than on VS Code-sized projects (start-up is a larger share of a half-second run), and a factor of about 1.4 comes from checking on several threads at once: with --checkers 1 TypeScript 7 is still about 3.6 times faster than 6.0 on one checker.

What was removed or changed (all from the 7.0 post): target: es5, downlevelIteration, moduleResolution node/node10/classic, module amd/umd/systemjs/none and baseUrl are errors now; esModuleInterop and alwaysStrict can no longer be turned off. New defaults: strict true, module esnext, noUncheckedSideEffectImports true, types [], rootDir ./. An old project that compiled on 5.x may need its tsconfig updated before 7.0 accepts it.

No API yet. "TypeScript 7.0 does not ship with an API. We expect TypeScript 7.1 to ship with a new (and different) API." Tools built on the compiler API (typescript-eslint, as shown above; also Vue, Svelte, Astro and MDX tooling, per the post) keep running on TypeScript 6 until then. Editors use TypeScript 7 through its new language server.

Common mistakes

Thinking that running a .ts file checks it
node, tsx, Bun and vitest strip types without checking. Run npx tsc (it uses noEmit or an outDir) in CI and in your editor.
JSON.parse(x) as T on data you did not create
A cast checks nothing. Parse to unknown and validate with a zod schema; derive T from it with z.infer.
Letting any in
From JSON.parse, untyped libraries, catch in old code, or an explicit annotation. It spreads silently. Lint against it (noExplicitAny, no-unsafe-*) and use unknown.
Silencing an error with as or !
Read the error first: it is usually right. If you must assert, assert as late and as narrowly as possible, with a comment saying why it is true.
A bag of optional fields instead of a discriminated union
Every use then needs a check and nothing tells you when a new kind appears. One member per kind, with a literal tag, and a never check in default.
Truthiness checks on numbers and strings
if (count) is false for 0 and if (name) for "". Use !== undefined or != null when 0 or empty are valid.
Floating promises
tsc does not catch a call to an async function whose promise is dropped. await it, return it, or mark it void; let a linter enforce it.
Enums and parameter properties in code that Node runs directly
Node's strip-only mode rejects them. Use as const objects and explicit fields; turn on erasableSyntaxOnly.
A global TypeScript install, or a caret range
Install typescript per project as a dev dependency and run npx tsc, so every machine and CI use the same compiler. Minor releases can add errors to code that compiled before (better inference finds real bugs), so many teams pin with ~ and upgrade in a dedicated change.
Type-level cleverness
Recursive conditional types that nobody else can read and that slow the editor. Derive types from one source; stop there.
