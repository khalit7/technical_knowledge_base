any, unknown, never, and assertions that lie

Three special types, which every TypeScript programmer must keep apart:

  • any switches checking off: every operation is allowed, and the result is any again. JSON.parse returns any, and so does untyped JavaScript.
  • unknown is the safe "could be anything": nothing is allowed until you narrow it. Use it for anything from outside your program.
  • never is the empty type: a function that always throws returns never, and a fully narrowed union is never.

i * "3" is 3 (JavaScript converts the string for *), but "3" + 1 is the string "31", assigned to a variable declared number. No error, no crash, a wrong value. The cure is to type the boundary: const config: unknown = JSON.parse(...) and then check (or parse with zod).

Assertions: as and ! are claims, not checks

x as T (a type assertion, often called a cast) tells tsc "trust me, x is a T". It generates no code and checks nothing at run time. x! (the non-null assertion) says "this is not null or undefined".

Notice the source line in Node's error for bang.ts: users.get("u2") .name. The ! is gone, replaced by a space: that is Node's type stripping, and it shows that the assertion never existed at run time. as does refuse conversions that are obviously wrong, but the double cast through unknown always works, which is why reviewers look for it:

When is as legitimate? When you know something the checker cannot (a DOM element you just created, a value you validated by other means), and in tests. as const is different: it is not a claim, it only makes inference narrower, and it is always safe.

Unsound by design: programs that type-check and then crash

A type system is sound if a program that type-checks can never have a value of the wrong type at run time. TypeScript is not, on purpose: its design goals put "a balance between correctness and productivity" ahead of soundness (Design Goals, non-goal 3). Declaration files and @types

A declaration file (.d.ts) holds only types: what a JavaScript module exports and with which types. It is how TypeScript knows the types of the millions of npm packages written in, or compiled to, plain JavaScript. Import a JavaScript file that has none:

Where types come from, in order of preference:

  1. The package ships them (its package.json points to .d.ts files through "types" or "exports"). Most modern packages, including zod, vitest and the Anthropic and OpenAI SDKs, do.
  2. DefinitelyTyped: a community repository that publishes @types/<package> for untyped packages (DefinitelyTyped). npm i -D @types/node describes Node's own APIs. Global ones must also be listed in "types" (see tsconfig).
  3. Write your own .d.ts, as above, or declare module "untyped-lib" { ... } for a whole package.

When you publish a TypeScript library, tsc with "declaration": true (on in the generated config) writes the .d.ts files for you; the inference demo above is exactly that output.
