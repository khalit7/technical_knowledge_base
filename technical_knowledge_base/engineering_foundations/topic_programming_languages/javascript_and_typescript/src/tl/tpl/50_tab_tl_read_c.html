5. Tool use and the agent loop

Tool use (OpenAI calls it function calling) works like this. You send, with the messages, a list of tools: a name, a description, and a JSON Schema for the arguments. The model never runs anything. When it wants a tool it stops with stop_reason: "tool_use" and a tool_use block (a name, arguments, an id). Your code runs the function, then sends a new request containing the whole conversation plus a tool_result block with the same id. The model reads the result and either asks for more tools or answers. That repetition is the agent loop, and an "agent" is nothing more than this loop plus tools.

The loop is small. Everything that makes it safe is in the guards:

Step limit
A model can ask for tools forever. Stop after maxSteps model calls and report it.
Timeout per tool
AbortSignal.timeout(500) gives every tool a deadline; a stuck tool becomes an error result, not a hung agent.
Validate the input
The arguments are the model's JSON: untrusted. safeParse them with the same zod schema that produced the JSON Schema.
Errors go to the model
A failed tool returns is_error: true with a message the model can act on. Throwing would kill the run.
Run calls concurrently
One turn may ask for several tools. Promise.all runs them together, and all results go back in one user message.
Meter the cost
Add up usage after every call; a loop multiplies the bill (every step resends everything).

The scripted model plays four scenarios: the happy path; a typo in the file name (the tool fails, the model corrects itself); a slow profile service (both lookups hit the 500 ms timeout); and a "runaway" model that keeps asking for one more user and never answers. A for loop with await inside would have taken twice as long (one at a time versus all at once is taught in section 10 of {{Part 1's Reading|#t-ja-read}}). And because runTool catches every error and returns it as a result, Promise.all can never reject halfway and lose the other results. The cost line uses Claude Sonnet 5.5's list price, US$2 per million input tokens and US$10 per million output tokens (Anthropic pricing, checked 2026-10-05) applied to the mock's token estimates, so it shows the arithmetic, not a real bill. From Python
The loop is line for line what you would write in Python. The differences are TypeScript's: msg.content.filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use") is a type guard (a function whose return type b is T tells the compiler what passed the filter), and the SDK's types (Anthropic.MessageParam, Anthropic.ToolResultBlockParam) make a malformed message a compile error instead of a 400 at run time.

6. The tool runner: the same loop, written by the SDK

The SDK ships the loop as a helper (beta in 0.131.0): client.beta.messages.toolRunner with tools made by betaZodTool. You give each tool a zod schema and a run function; the runner sends the schema, validates the model's arguments against it before calling run, sends the results back, and stops when the model answers or after max_iterations.

[[run:c2_tool_runner]]

When to use which: the runner for most custom-tool agents (less code, validation built in). The hand-written loop when you need control the runner does not give, such as your own cost cut-off, a per-step log format, or handling of pause_turn (the SDK's documentation notes the runner does not resume a paused server-tool turn by itself). It is worth writing the loop by hand once, as above, so the runner is not magic.

7. Structured output validated with zod

Often you do not want prose but data: {"user": "u0029", "tokens": 9491, "share_pct": 21.2}. Three layers make that reliable, and zod (taught from zero in "Checking data at run time with zod" in {{Part 2's Reading|#t-tb-read}} and its {{LLM JSON lab|#t-tb-zod}}) gives all three from one schema:

  1. Ask with a schema. output_config.format sends a JSON Schema and the API constrains the model to produce matching JSON (Anthropic calls this structured outputs; docs). zodOutputFormat(schema) converts the zod schema.
  2. Check what came back. client.messages.parse() runs the zod schema on the reply and puts the typed result in parsed_output.
  3. Get the type for free. z.infer<typeof Heaviest> is the TypeScript type, so the rest of your program is checked against the same definition.
[[run:d1_structured]]
Found by running it: not every rule reaches the API
Look at the output_config sent line. The SDK sent user as a plain string and moved the regular expression into the field's description ("{pattern: \"^u\\\\d{4}$\"}"); the same happened to minimum/maximum on the numbers. So the API's constraint guarantees the JSON's shape (fields, types, no extra keys), but rules like a pattern or a range are only hinted to the model and enforced afterwards, by zod, in parse(). That is why case 2 ends in an error raised by the SDK rather than a wrong value in your program. Keep the zod check even when the API constrains output.

With OpenAI the equivalent is zodTextFormat(schema, name) in text.format with client.responses.parse() (from openai/helpers/zod, 7.28.0). With any other provider, or a model without constrained decoding: ask for JSON in the prompt, JSON.parse, then safeParse. On failure, send the zod error message back to the model and ask again, once or twice; the error text (the last block above) is written for exactly that.

An alternative you will see in older code: defining a tool whose input schema is the output you want and forcing the model to call it. On Claude Sonnet 5.5 and Opus 5.5, forcing a specific tool (tool_choice any or tool) is rejected with a 400 (Sonnet 5.5 migration guide), so use structured outputs instead.

8. Conversation state

The Messages API keeps no memory between requests. The conversation is an array in your program; each turn you append the user's message, send the whole array, and append the reply. Forget to resend, and the model has never heard of you:

[[predict:e1_state|the first call says "My name is Khalid." and a second, separate call asks "What is my name?". What does the second call answer? Then, in the kept history, how does the input grow over six turns?]]

The input column grows with every turn because each request carries everything before it, so the total input billed grows with the square of the number of turns: the six turns above billed 636 estimated input tokens for a conversation whose final request was 219. Three tools fight that:

  • Prompt caching. Mark the stable prefix (cache_control); later requests that start with the same bytes read it from cache at 0.1x the input price on most models (0.05x on Opus 5.5; pricing). Any change early in the prefix (a timestamp in the system prompt) silently defeats it.
  • Compaction or trimming. Summarise or drop old turns when the context grows (Anthropic offers server-side compaction as a beta).
  • Server-side state. OpenAI's Responses API can keep the conversation on its servers: pass previous_response_id (conversation state guide) instead of resending (you are still billed for those input tokens; you just do not send them).

Where the array lives is an application decision: in memory for a script, in a database row per conversation for a web app (the {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}} page covers storing and versioning such data).
