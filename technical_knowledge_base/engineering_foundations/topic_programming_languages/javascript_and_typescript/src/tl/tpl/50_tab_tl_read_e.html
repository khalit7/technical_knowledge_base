11. Serving an LLM app: stream to the browser, cancel when it leaves

A web app puts your server between the browser and the model: the browser calls /ask, your server calls the model with the API key (which must never reach the browser), and forwards each text piece as an SSE event. Two things go wrong in production that never show in a demo.

Cancellation. Users close tabs. If your server does not notice, the model keeps generating, and you pay for every token nobody will read. In Node the response's close event fires when the client goes away; hand an AbortController's signal to the SDK call and abort it there. The SDK then closes the upstream HTTP request and throws APIUserAbortError, which you catch. (AbortController and AbortSignal themselves are taught in {{Part 1's Reading|#t-ja-read}}, section 10.) Backpressure. res.write() returns false when the bytes cannot leave as fast as you write them (a slow phone, a congested link); Node then keeps the rest in memory. A server that ignores the false can hold the whole response in RAM for every slow client at once. The fix is one line: when write returns false, await once(res, "drain") before writing more. A client that reads nothing for 300 ms:

[[predict:h2_backpressure|about 2 MB goes to a client that pauses for 300 ms. How much does the server hold in memory at its peak when it ignores write()'s return value, and when it awaits "drain"?]]

The 64 KiB plateau is Node's default stream buffer size (highWaterMark, 65,536 bytes; printed by stream.getDefaultHighWaterMark(false) on Node 24.21.0). With LLM tokens arriving at tens per second the risk is small for one stream, but a proxy that relays many streams, or a server that forwards a fast upstream to slow clients, needs it. stream.pipeline() and .pipe() handle backpressure for you when both ends are Node streams (Node essentials, including reading files as streams, are in section 12 of {{Part 1's Reading|#t-ja-read}}).

The browser side is the same fetch and stream-reading code as the Node "browser" in h1_serve.ts (it runs unchanged in a browser); EventSource also reads SSE but only with GET and no custom headers, so fetch is the usual choice for a chat POST. Bun runs the same server code (it implements node:http: Bun's Node.js compatibility list), or its own Bun.serve with web-standard Request and Response; Part 1 measures Bun and Deno start-up in its section 14. API design (validation, errors, idempotency) for such an endpoint: {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}; load and concurrency limits: {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}}.

12. Evaluation hooks and logging

You cannot improve an LLM app you do not measure, and the measuring starts with two habits. Log every model call as one JSON line: which case, status, latency, how many messages were sent, why it stopped, tokens in and out. Keep a fixed set of cases with checks written in code, and run them on every change of prompt, model or tool. The cheapest hook is the SDK's fetch option: a wrapper that sees every HTTP call, retries included, without touching the agent.

[[run:i1_eval]]

The runaway case fails, as it should: the checks catch a model that never answers, and the step count catches an agent that wanders even when it finally answers. Real evaluations add what this toy cannot: graders for free-text answers (often another model, an "LLM judge", with its biases measured), many more cases with error bars, and traces of every tool call for agents. Those live in {{Topic: evaluation-and-llm-judges|n:3c65c17b0d0d8181b351e1b8fc6a1546}}, especially {{Agent and trajectory evaluation|n:3ef5c17b0d0d81fdbabaf3582bff37f2}} and {{Production eval engineering|n:3c65c17b0d0d81b39ad9e96193d21adc}}; logs, metrics and traces in general: {{Observability|n:3ef5c17b0d0d811e8490c54dd42c2b9b}}.

13. Common mistakes

  • Reading content[0].text without checking the block type or stop_reason. The first block may be thinking or tool_use; a max_tokens stop means the text is cut off. TypeScript's narrowing forces the check if you let it.
  • An agent loop without a step limit or tool timeouts: the runaway run above, in production, with a real bill.
  • Trusting tool arguments. They are model output. Validate with zod, and for paths, URLs or shell commands also check what they point at (a valid string can still be ../../etc/passwd).
  • Throwing from a tool instead of returning is_error: the run dies on a problem the model could have fixed (the typo run fixed its own mistake).
  • await in a for loop over tool calls, running them one after another when Promise.all would run them together; and splitting their results over several messages instead of one.
  • Forgetting that the API is stateless, or never trimming: the bill grows with the square of the conversation's length.
  • Dropping the zod check because the API constrained the output: patterns and ranges are not enforced by the API (section 7).
  • Ignoring disconnects and write()'s return value in the server: paying for unread tokens and holding responses in memory.
  • Logging to stdout in a stdio MCP server: it corrupts the protocol stream.
  • Putting the API key in browser code, or in a logged request. Keys belong in server-side environment variables; this page's scripts unset them before running.
  • Catching errors by message text instead of instanceof Anthropic.RateLimitError and friends; and adding your own retry loop around an SDK that already retries (the SDK's 3 attempts inside your 3 attempts is 9 requests).
  • Relying on a framework default you have not read: generateText's single step, allowedTools meaning "no approval needed" rather than "only these".
