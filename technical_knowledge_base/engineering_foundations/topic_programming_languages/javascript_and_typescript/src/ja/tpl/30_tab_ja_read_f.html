10. The async toolbox

Timers. setTimeout(f, ms) runs f once, no earlier than ms later (later if the thread is busy); setInterval repeats; both return a handle for clearTimeout. import { setTimeout as sleep } from "node:timers/promises" gives Python's asyncio.sleep.

Waiting for several. Python's asyncio.gather is Promise.all: results in input order, rejects as soon as one rejects (the others keep running; nobody cancels them). Promise.allSettled never rejects and reports each outcome (gather(..., return_exceptions=True)). Promise.race settles with the first to settle; Promise.any with the first success, or an AggregateError of all failures.

[[run:i5_combinators]]

Cancellation and timeouts. A promise cannot be cancelled. Instead, the work accepts an AbortSignal (from an AbortController, or AbortSignal.timeout(ms)) and stops when it fires; fetch, timers, streams and most SDKs accept { signal }. Aborting is a request, not preemption: code that never looks at the signal runs to the end. (Python's task.cancel() is stronger: it throws CancelledError into the coroutine at its next await.)

[[run:i6_abort]]

Forgotten promises. Calling an async function without await or .catch ("fire and forget") means its error has nowhere to go. Since Node 15 the default (--unhandled-rejections=throw) is to treat it as an uncaught exception: the process dies, here before a pending timer gets to run ({{Node CLI docs|https://nodejs.org/api/cli.html#--unhandled-rejectionsmode}}).

[[run:i7_unhandled]]

await in loops. forEach ignores the promise its callback returns, so await inside it does not make the loop wait. Use for...of with await for one at a time, or Promise.all(xs.map(...)) for all at once.

[[predict:i8_foreach]]

A concurrency limit. "All at once" is wrong for 10,000 requests to a rate-limited API. The usual fix is a small pool: N workers pulling from a shared index (libraries such as p-limit do the same). Python's equivalent is an asyncio.Semaphore.

[[run:i9_limit]]

11. Async iterators and streams: how LLM tokens arrive

An async generator (async function*) yields values that arrive over time, and for await...of consumes them, exactly like Python's async def with yield and async for. Breaking out of the loop runs the generator's finally, which is where a stream closes its connection.

[[run:j2_async_gen]]

A streaming LLM API sends server-sent events (SSE): an HTTP response that stays open, carrying text lines data: {...}, each event ended by a blank line. With fetch, response.body is a stream of Uint8Array byte chunks that you can for await over. The trap: the network decides where chunks end, not the server. A chunk can end in the middle of an event, and in the middle of a multi-byte UTF-8 character. Code that parses each chunk on its own works on a fast local test and fails in production behind a proxy. The fix is one streaming TextDecoder ({ stream: true } keeps half a character for the next chunk), a text buffer, and parsing only complete events. Official SDKs do this for you; the bug appears when you hand-roll a client, or a proxy, or a test.

The nine chunks are the ones the client really received in the recorded run of j1_sse.mjs (byte lengths saved by the script); the two parsers run live in your browser on those bytes, and their final results are checked against the recorded run.

Node also has its own older stream classes (Readable, Writable, Transform, pipeline) used by files, sockets and HTTP. They handle backpressure: a fast producer is paused while a slow consumer catches up, so memory stays bounded.
