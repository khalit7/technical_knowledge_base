14. Bun and Deno

Node is not the only runtime. Bun runs on JavaScriptCore (Safari's engine) and bundles a runtime, package manager, test runner and bundler in one binary; it runs TypeScript directly. Bun announced it was joining Anthropic on 2025-12-02, noting that "Claude Code ships as a Bun executable" ({{Bun is joining Anthropic|https://bun.com/blog/bun-joins-anthropic}}); Bun 1.4 (2026-08-20) rewrote Bun itself from Zig to Rust ({{Bun 1.4|https://bun.com/blog/bun-v1.4}}). Deno (by Node's original author) runs on V8, is written in Rust, runs TypeScript directly, and is secure by default: no file, network or environment access without a flag. Since Deno 2 (2024) both run most Node code and npm packages. The same script, three runtimes:

Start-up time matters for CLIs, hooks and short scripts (an agent harness may start a tool process hundreds of times per session). Measured on this laptop, an almost empty script:

Node needs about 30 ms to start (it boots V8 and its own JavaScript-written standard library), Bun about 9 ms and Deno about 11 ms; CPython sits between them at about 17 ms. The root's Benchmark measured the same order independently (node -e 0 28.5 ms, bun -e 0 6.6 ms). Newer Node majors are slightly slower to start here, within about 3 ms.

Choose Node when
You want the default: the widest compatibility, LTS releases with a published schedule, governance by the OpenJS Foundation, and every tutorial and SDK tested on it.
Choose Bun when
Start-up and install speed matter (CLIs, scripts, tests), or you want one tool instead of five. Check that your native add-ons and edge-case Node APIs work.
Choose Deno when
You run code you do not fully trust (permissions), or want TypeScript, formatter, linter and test runner built in with web-standard APIs.

15. V8 performance notes

V8 does not interpret your code forever. It parses it to bytecode run by the Ignition interpreter, then compiles functions that get hot: Sparkplug (a fast baseline compiler), Maglev (a mid-tier optimising compiler, shipped in Chrome 117 in 2023) and TurboFan (the top tier) ({{V8 blog, Maglev|https://v8.dev/blog/maglev}}). The optimising tiers speculate from what they have seen: "this argument has always been a small integer", "this object always has this shape". When a guess breaks, the code deoptimises back to the interpreter and may be recompiled later. You can watch it:

[[code:n3_deopt]] [[out:n3_deopt|real output, Node 24.21.0, --trace-opt --trace-deopt (addresses removed); which tier is reached before the string call varies with load]]

"Not a Smi": a Smi is V8's small-integer representation (31 or 32 bits, stored without allocating). The second lever is the hidden class (V8 calls it a "map"): objects with the same property names added in the same order share one, and each property access site caches the shapes it has seen ("inline caches"). A site that sees one shape is monomorphic and fast; past four it is megamorphic and does a slow lookup.

[[run:n1_shapes]] [[run:n2_shapes_bench]]
What to do with this
Create objects of one kind in one place (a constructor, a class, or one literal shape), with all fields set, in the same order; do not add properties later; do not delete (set to undefined instead); keep arrays of one element type.
What not to do
Do not micro-tune before profiling: node --cpu-prof app.mjs writes a profile that Chrome DevTools opens, and node --prof is the lower-level option. Most slow Node services are slow because something blocks the event loop or waits serially, not because of shapes.
