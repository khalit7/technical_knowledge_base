3. Concurrency on one thread, to scale

The same three jobs as the Python page's "Three coroutines, four ways" ({{Python: concurrency, asyncio and the GIL|n:4055c17b0d0d81bdbee8c37d80b55a0e}}, section 2): A, B and C wait 100, 200 and 300 ms, run four ways. Every bar is a real event from i4_trace.mjs, stamped with milliseconds since the start and drawn on the same 0 to 620 ms axis. Before you switch from mode 2 to mode 3, predict when A's 100 ms timer will run.

Waits overlap on one thread; a synchronous loop stops all of them

Thin bar: suspended at an await (the thread is free); dark bar: running on the thread; orange bar: holding the thread in a synchronous loop; ring: the moment a timer is due. Top lane: what the one JavaScript thread is doing.
  1. 0 ms: A starts and waits. main calls A, which runs to await sleep(100) and suspends. The thread is free, but main awaits A before it calls B.
  2. 102.3 ms: A finishes; B starts. A's timer fires, A resumes and returns; only now is B called, and it suspends on sleep(200).
  3. 304.5 ms: B finishes; C starts. The same again: C suspends on sleep(300).
  4. 606.8 ms: all done. C returns. Awaiting one by one costs the sum of the waits.
  1. 0 to 0.1 ms: all three start. Promise.all receives three promises that are already running: calling an async function starts it, so A, B and C each run to their await and suspend. Three timers are pending, due at 100, 200 and 300 ms.
  2. 101.6 ms: A. A's timer fires; A resumes and finishes. B and C are still suspended, costing nothing.
  3. 202.3 ms: B. B's timer fires; B finishes.
  4. 303.0 ms: C, and the total. The waits overlapped, so the total is the longest wait, not the sum.
  1. 0.1 ms: A waits. A suspends on sleep(100); its timer is due at 100 ms.
  2. 0.2 ms: B holds the thread. B runs busyWait(200), a synchronous loop with no await: until it returns, no timer, callback or other job can run, and C has not even been called.
  3. 200.3 ms: B returns; C starts. C is called only now and suspends on sleep(300), due at 500 ms.
  4. 200.4 ms: A, 100 ms late. A's timer was due at 100 ms; its continuation runs at 200.4 ms, as soon as the thread is free. Nothing warns you.
  5. 502.6 ms: all done. C finishes; the busy loop added its 200 ms to the total.
  1. 0.1 ms: A waits. A suspends on sleep(100).
  2. 0.1 ms: B hands the loop to a worker. The same 200 ms busy loop now runs in a worker thread on another core; B just awaits the worker's message, so the main thread is free.
  3. 1.4 ms: C waits. C starts and suspends on sleep(300).
  4. 101.9 ms: A, on time. Nothing holds the thread, so A's timer runs when it is due.
  5. 218.1 ms: B's message arrives. The worker finished its loop; B resumes and returns.
  6. 302.7 ms: all done. The total is back to the longest wait.
What to notice
  • 1 against 2: await in sequence takes the sum (606.8 ms); Promise.all starts all three, so the waits overlap and the total is the longest (303.0 ms). Unlike Python, no "task" wrapper is needed: calling an async function already starts it.
  • 2 against 3: a 200 ms synchronous loop in B holds the only thread. A's timer is due at 100 ms but runs at 200 ms; C cannot even start before 200 ms. Total 502.6 ms, and nothing warns you.
  • 3 against 4: the same busy loop in a worker thread runs on another core; B just awaits a message, and the total is back to 302.7 ms.

Blocking the event loop is the server version of mode 3: a synchronous file read (readFileSync), a big JSON.parse, a CPU loop or synchronous crypto in a request handler stalls every other request. Use the async APIs, stream, or move CPU work to a worker thread (worker_threads, shown with real runs in the Node essentials of {{JavaScript and TypeScript: the essentials|n:3cd5c17b0d0d81dbac7be3b8686be023}}). Under the loop, libuv watches sockets with the operating system's readiness API and hands file-system calls, DNS lookups (dns.lookup), the asynchronous crypto.pbkdf2, scrypt and randomBytes, and zlib to a thread pool, 4 threads by default ({{libuv: thread pool|https://docs.libuv.org/en/v1.x/threadpool.html}}; {{Node: Don't block the event loop|https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop}}). A slow task there blocks the pool the same way.
