5. Async iterators and streams: how LLM tokens arrive

An async generator (async function*) yields values that arrive over time, and for await...of consumes them, exactly like Python's async def with yield and async for. Breaking out of the loop runs the generator's finally, which is where a stream closes its connection: below, the cleanup line prints after the full run, after the early break, and after Array.fromAsync collects a whole stream.

A streaming LLM API sends server-sent events (SSE): an HTTP response that stays open, carrying text lines data: {...}, each event ended by a blank line (the format, its parsing rules and how eight real parsers handle them are on {{Streaming and real-time|n:3c65c17b0d0d812daa9fdb38719fc82b}}). With fetch, response.body is a stream of Uint8Array byte chunks that you can for await over. The trap: the network decides where chunks end, not the server. A chunk can end in the middle of an event, and in the middle of a multi-byte UTF-8 character. Code that parses each chunk on its own works on a fast local test and fails in production behind a proxy. The fix is one streaming TextDecoder ({ stream: true } keeps half a character for the next chunk), a text buffer, and parsing only complete events. Official SDKs do this for you; the bug appears when you hand-roll a client, a proxy or a test.

Node streams and backpressure. Node also has its own older stream classes (Readable, Writable, Transform, pipeline) used by files, sockets and HTTP. They handle backpressure: a fast producer is paused while a slow consumer catches up, so memory stays bounded. Readable streams are async iterable too, which is the easiest way to use them. What happens to a server's memory when it ignores write()'s false, measured, is on {{TypeScript: LLM apps and agents|n:4055c17b0d0d8109aad6e69a87b3bd6f}}.
