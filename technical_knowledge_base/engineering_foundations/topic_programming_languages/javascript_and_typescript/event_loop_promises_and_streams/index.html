The idea in one screen

Node runs your JavaScript on one thread that never waits: an I/O call starts the work and returns at once, and the event loop later runs each callback to completion, draining every microtask (promise callbacks, the code after an await) before it takes the next macrotask (a timer, an I/O completion).

Fig. 1, where a callback waits, and the order the loop takes them

  1. One thread, one call stack. Your code runs on the stack; the function on top runs to completion, and nothing interrupts it.
  2. I/O happens under the thread. An I/O call hands the work to libuv and returns at once. libuv watches sockets with the operating system's readiness API (epoll or kqueue) and runs file-system calls, DNS lookups and some crypto on a thread pool, 4 threads by default (section 3 gives the sources). Each completion comes back up as a callback.
  3. Macrotasks, one at a time, by phase. The loop goes round its phases: timers (setTimeout), then poll (I/O callbacks), then check (setImmediate). Each callback it takes runs alone on the stack. Node's guide lists six phases; these three are the ones the programs on this page use (Node: the event loop).
  4. Between every two: nextTick, then every microtask. After each callback, Node empties its nextTick queue, then the microtask queue (promise callbacks, code after await, queueMicrotask), including microtasks queued while it drains, before it takes the next macrotask. Browsers have the same two main queues, without nextTick.
  5. So a resolved promise beats setTimeout(f, 0). When program 1 of section 2 finishes its synchronous code, C waits in the microtask queue and B in the timers phase; the microtask queue drains first, so Node printed A D C B in all 20 recorded runs. 1. Callbacks, promises, then async/await

A Node process runs your JavaScript on one thread. It never waits: reading a file, a socket or a timer is started, the call returns at once, and the result is delivered later by the event loop. Python's asyncio is the same design, opt-in; in JavaScript it is the only model, and every I/O API is built for it. Three generations of API sit on top.

Callbacks. The original style: pass a function to call when the result is ready. Node's convention puts the error first. Each dependent step nests one level deeper ("callback hell"), and errors must be checked by hand at every level. Line 2 below prints before line 3 because readFile returned before reading anything.

readFile("i1_callbacks.mjs", "utf8", (err, text) => {        // Node's convention: error first, then the result
  if (err) return console.log("failed:", err.code);
  console.log("3. got", text.length, "characters");
  readFile("no_such_file.txt", "utf8", (err2) => {             // the next step nests inside: "callback hell"
    console.log("4. second read failed with", err2.code);
  });
});
console.log("2. readFile has already returned; nothing has been read yet");

Promises. A promise is pending, then once and for all fulfilled or rejected. .then(f) registers what to do next and returns a new promise, so steps chain instead of nesting; .catch and .finally work like except and finally on the chain. async function and await are syntax over promises: an async function always returns a promise, and await p pauses the function until p settles, returning its value or throwing its error, so plain try/catch works.

One difference from Python matters: a promise is eager. The work starts when the promise is created; a Python coroutine does nothing until awaited or wrapped in a task. The first line of the output below is printed by the promise's executor before anything awaits it.

2. The two queues, stepped through

When does a callback run? The event loop keeps two kinds of queue. Macrotasks: timer callbacks, I/O completions, setImmediate. Microtasks: promise reactions (.then callbacks and the continuation after an await) and queueMicrotask. The rule: run the current piece of synchronous code to the end; then run every microtask, including ones queued meanwhile; only then take the next macrotask. So a resolved promise's callback always beats a setTimeout(f, 0). Predict the order of the seven lines:

(async () => {
  console.log("async body, before await");
  await null;
  console.log("async body, after await");

Why "async body, after await" comes after "queueMicrotask": the continuation of an async function is queued when it reaches await, which here is after the .then and queueMicrotask callbacks were queued, and microtasks run in the order they were queued.

The rules the six programs show
    

  • Synchronous code always runs to the end first. An async function runs synchronously until its first await.
    • 

  • Then all microtasks run (promise callbacks, code after await, queueMicrotask), including ones queued while draining, before the loop takes the next macrotask (a timer, an I/O callback, setImmediate). After every macrotask, microtasks are drained again (program 3).

Blocking the event loop is the server version of mode 3: a synchronous file read (readFileSync), a big JSON.parse, a CPU loop or synchronous crypto in a request handler stalls every other request. // Four ways to run them; every event is stamped with ms since the start. The Reading animation replays this file's output.
import { Worker } from "node:worker_threads";
import { setTimeout as sleep } from "node:timers/promises";      // a promise-returning setTimeout
let T0 = 0, EV = [];
const ev = (who, what, note = "") => EV.push([who, what, +(performance.now() - T0).toFixed(1), note]);
const busyWait = ms => { const end = performance.now() + ms; while (performance.now() < end); };  // holds the thread

async function job(name, ms) { ev(name, "start"); ev(name, "await", `sleep(${ms})`); await sleep(ms); ev(name, "resume"); ev(name, "done"); }
async function jobBlocking(name, ms) { ev(name, "start"); ev(name, "block", `busyWait(${ms})`); busyWait(ms); ev(name, "done"); }
async function jobWorker(name, ms) {
  ev(name, "start"); ev(name, "await", `a worker thread busy-waits ${ms} ms`);
  await new Promise((ok, fail) => {
    const w = new Worker(`const e = performance.now() + ${ms}; while (performance.now() < e); require("node:worker_threads").parentPort.postMessage(1)`, { eval: true });
    w.once("message", ok); w.once("error", fail);
  });
  ev(name, "resume"); ev(name, "done");
}
const MODES = {
  sequential: async () => { await job("A", 100); await job("B", 200); await job("C", 300); },
  all: () => Promise.all([job("A", 100), job("B", 200), job("C", 300)]),
  all_blocking: () => Promise.all([job("A", 100), jobBlocking("B", 200), job("C", 300)]),
  all_worker: () => Promise.all([job("A", 100), jobWorker("B", 200), job("C", 300)]),
};
const out = {};
for (const [mode, run] of Object.entries(MODES)) {
  EV = []; T0 = performance.now();
  await run();
  const total = +(performance.now() - T0).toFixed(1);
  out[mode] = { events: EV, total_ms: total };
  console.log(`${mode.padEnd(13)} ${total.toFixed(1).padStart(6)} ms  ` + EV.map(e => `${e[0]}:${e[1]}`).join(" "));
}
if (process.argv[2]) (await import("node:fs")).writeFileSync(process.argv[2], JSON.stringify(out));







4. The async toolbox


Timers. setTimeout(f, ms) runs f once, no earlier than ms later (later if the thread is busy, as mode 3 above showed); setInterval repeats; both return a handle for clearTimeout. import { setTimeout as sleep } from "node:timers/promises" gives Python's asyncio.sleep.


Waiting for several. Python's asyncio.gather is Promise.all: results in input order, rejects as soon as one rejects (the others keep running; nobody cancels them). Promise.allSettled never rejects and reports each outcome (gather(..., return_exceptions=True)). Promise.race settles with the first to settle; Promise.any with the first success, or an AggregateError of all failures. In the output, the 10 ms job finished first but its result is second, and the failing all rejects after 11 ms without waiting for the 50 ms job.

// Waiting for several promises: all (fail fast), allSettled (never rejects), race (first to settle), any (first success).
const ok = (ms, v) => new Promise(r => setTimeout(() => r(v), ms));
const bad = (ms, m) => new Promise((_, j) => setTimeout(() => j(new Error(m)), ms));
let t0 = 0; const start = () => { t0 = performance.now(); }, took = () => `after ${Math.round(performance.now() - t0)} ms`;
start(); console.log("all:", await Promise.all([ok(30, "a"), ok(10, "b")]), took());   // results in INPUT order
start(); try { await Promise.all([ok(50, "a"), bad(10, "b failed")]); } catch (e) { console.log("all:", e.message, took()); }
const settled = await Promise.allSettled([ok(10, "a"), bad(10, "b failed")]);
console.log("allSettled:", settled.map(s => s.status === "fulfilled" ? `ok ${s.value}` : `error ${s.reason.message}`));
console.log("race:", await Promise.race([ok(30, "slow"), ok(10, "fast")]));
try { await Promise.any([bad(5, "x"), bad(5, "y")]); } catch (e) { console.log("any:", e.constructor.name, e.errors.map(x => x.message)); }


Cancellation and timeouts. A promise cannot be cancelled. Instead, the work accepts an AbortSignal (from an AbortController, or AbortSignal.timeout(ms)) and stops when it fires; fetch, timers, streams and most SDKs accept { signal }. Aborting is a request, not preemption: code that never looks at the signal runs to the end (the third line below). Python's task.cancel() is stronger: it throws CancelledError into the coroutine at its next await. // 20 requests of 50 ms each, at most 4 in flight: a worker-pool limiter in eight lines (no library).
const sleep = ms => new Promise(r => setTimeout(r, ms));
async function mapLimit(items, limit, fn) {
  const results = new Array(items.length); let next = 0, inFlight = 0, peak = 0;
  async function worker() {
    while (next < items.length) { const i = next++; inFlight++; peak = Math.max(peak, inFlight); results[i] = await fn(items[i]); inFlight--; }
  }
  await Promise.all(Array.from({ length: limit }, worker));
  return { results, peak };
}
const items = Array.from({ length: 20 }, (_, i) => i);
for (const limit of [1, 4, 20]) {
  const t0 = performance.now();
  const { results, peak } = await mapLimit(items, limit, async i => { await sleep(50); return i * i; });
  console.log(`limit ${String(limit).padStart(2)}: ${Math.round(performance.now() - t0)} ms, peak in flight ${peak}, last result ${results.at(-1)}`);
}

A streaming LLM API sends server-sent events (SSE): an HTTP response that stays open, carrying text lines data: {...}, each event ended by a blank line (the format, its parsing rules and how eight real parsers handle them are on Streaming and real-time). With fetch, response.body is a stream of Uint8Array byte chunks that you can for await over. The trap: the network decides where chunks end, not the server. A chunk can end in the middle of an event, and in the middle of a multi-byte UTF-8 character. Code that parses each chunk on its own works on a fast local test and fails in production behind a proxy. The fix is one streaming TextDecoder ({ stream: true } keeps half a character for the next chunk), a text buffer, and parsing only complete events. Official SDKs do this for you; the bug appears when you hand-roll a client, a proxy or a test.

// delivers bytes in arbitrary chunks (here: 19-byte slices, 15 ms apart), cutting events and even characters in half.

const TOKENS = ["Hello", ",", " wörld", "!", " 🚀", " done"];

const server = createServer(async (req, res) => {
  res.writeHead(200, { "content-type": "text/event-stream" });
  for (let i = 0; i < BODY.length; i += 19) { res.write(BODY.subarray(i, i + 19)); await new Promise(r => setTimeout(r, 15)); }
  res.end();
}).listen(0);

for await (const chunk of (await fetch(url)).body) {        // a web ReadableStream is an async iterable of Uint8Array
  const text = new TextDecoder().decode(chunk);             // a fresh decoder per chunk breaks split characters
  naive.chunks.push(text); naive.lens.push(chunk.length);

    try { naive.events.push(JSON.parse(part.slice(6)).delta); } catch (e) { naive.errors.push(e.message.split(" in JSON")[0]); }
  }
}

  const dec = new TextDecoder(); let buf = "";
  for await (const chunk of body) {
    buf += dec.decode(chunk, { stream: true });              // stream: true keeps half a character for the next chunk
    let end;
    while ((end = buf.indexOf("\n\n")) >= 0) { const ev = buf.slice(0, end); buf = buf.slice(end + 2); yield ev; }
  }
}

Node streams and backpressure. Node also has its own older stream classes (Readable, Writable, Transform, pipeline) used by files, sockets and HTTP. They handle backpressure: a fast producer is paused while a slow consumer catches up, so memory stays bounded. Each stream has a buffer with a highWaterMark; push() and write() return false once it is reached, and pipeline() obeys that signal for you. Readable streams are async iterable too, which is the easiest way to use them. Fig. 3 replays a run of k1_backpressure.mjs recorded for this page (Node 20.20.1 on an AMD Ryzen 9 9950X under Linux, 2026-11-07; every event and buffer level was the same in four runs, the totals within 2 ms). What happens to a server's memory when it ignores write()'s false at scale, measured, is on TypeScript: LLM apps and agents.




    

  1. Three stages, four buffers. A source (Readable), a pass-through Transform and a sink (Writable) that takes 20 ms for each 1 KiB chunk, joined by pipeline(). Every buffer has a highWaterMark of 2 KiB; the Transform has one on each side. At 1.1 ms the source's read() is called for the first time.
    2. 

  2. The source fills its buffer and stops. push() returns true for chunk 0 and false for chunk 1: the buffer has reached its 2 KiB mark, so the source stops pushing. The mark is a threshold, not a cap: the chunk that crossed it is kept.
    3. 

  3. Chunks flow down until every buffer is at its mark. The pipe moves chunks into the Transform and the sink (the sink starts writing chunk 0 at 1.4 ms), and each time the source's buffer drops below its mark, read() asks for one more. By 1.7 ms every buffer is full; the four counters add up to 8 KiB.
    4. 

  4. Paused for 20 ms. From 1.7 to 22.0 ms nobody calls read(): the source is paused, and the only work is the sink writing chunk 0.
    5. 

  5. Room travels up the pipe. The sink finishes chunks 0 and 1 (22.0 and 42.2 ms); the space they leave moves up stage by stage, and at 42.6 ms read() is called twice, for chunks 7 and 8.
    6. 

  6. Steady state, paced by the sink. From then on, about every 40 ms, the sink finishes two chunks and the source pushes two more, up to chunk 19 at 283.9 ms. No buffer ever holds more than its mark plus the one chunk that crossed it.
    7. 

  7. The end. The source pushes null (end of stream), the buffers drain, and the sink finishes chunk 19 at 403.9 ms.
    8. 



    

  1. The same sink, written to in a loop. A for loop calls sink.write() for each of the 20 chunks and ignores what it returns. The first write returns true, and the sink starts on chunk 0 at once.
    2. 

  2. write() says false 19 times; the loop goes on. From the second chunk on, write() returns false: the buffer is at its 2 KiB mark. By 0.1 ms all 20 chunks sit in the sink's buffer: 20 KiB, ten times the mark. Memory now grows with the input, not with the mark.
    3. 

  3. Drained one chunk every 20 ms. The sink still takes 20 ms a chunk; at 201.4 ms it has finished 10 and 10 KiB are still waiting.
    4. 

  4. The same time, 2.5 times the memory. The last chunk finishes at 402.2 ms, against 403.9 ms with pipeline(): the sink sets the pace either way, so ignoring false bought no speed, only memory (20 KiB against 8 KiB here; for a long stream to a slow client, without bound).

// Backpressure in a Node stream pipeline: a fast source, a pass-through Transform, a slow sink (20 ms per 1 KiB chunk).
// Every buffer's highWaterMark is 2 KiB. Mode "pipeline": stream.pipeline() pauses the source when the buffers are full.
// Mode "ignore": a loop calls sink.write() for every chunk and ignores the false it returns, so the sink's buffer grows.
// Each event is stamped with ms since the start and the bytes waiting in every buffer; the Reading stage replays them.
import { Readable, Transform, Writable } from "node:stream";
import { pipeline } from "node:stream/promises";
import { writeFileSync } from "node:fs";
const N = 20, KB = 1024, HWM = 2 * KB, SLOW = 20;
const chunk = i => Buffer.alloc(KB, 97 + (i % 26));
async function run(mode) {
  const EV = [], T0 = performance.now(); let src = null, xf = null, sink = null;
  const lv = () => [src ? src.readableLength : 0, xf ? xf.writableLength : 0, xf ? xf.readableLength : 0, sink.writableLength];
  const ev = (what, i, ok) => EV.push([what, i, +(performance.now() - T0).toFixed(1), ...lv(), ok === undefined ? null : ok]);
  sink = new Writable({ highWaterMark: HWM, write(c, _e, cb) { const i = c[0] - 97; ev("write", i); setTimeout(() => { ev("done", i); cb(); }, SLOW); } });
  if (mode === "pipeline") {
    let i = 0;
    src = new Readable({ highWaterMark: HWM, read() {             // called whenever the source's buffer has room
      ev("read", i);
      while (i < N) { const ok = this.push(chunk(i)); ev("push", i, ok); i++; if (!ok) return; }   // false: stop until read() is called again
      this.push(null);
    } });
    xf = new Transform({ highWaterMark: HWM, transform(c, _e, cb) { cb(null, c); } });
    await pipeline(src, xf, sink);
  } else {
    let falses = 0;
    for (let i = 0; i < N; i++) { const ok = sink.write(chunk(i)); ev("push", i, ok); if (!ok) falses++; }   // ignores false
    await new Promise(r => sink.end(r));
    ev("end", N);
    console.log(`ignore: write() returned false ${falses} times`);
  }
  const peak = Math.max(...EV.map(e => e[3] + e[4] + e[5] + e[6]));
  console.log(`${mode}: ${N} chunks of 1 KiB, highWaterMark 2 KiB, sink 20 ms a chunk: ${EV.at(-1)[2].toFixed(0)} ms, peak buffered ${(peak / KB).toFixed(0)} KiB, peak in the sink ${(Math.max(...EV.map(e => e[6])) / KB).toFixed(0)} KiB`);
  return { events: EV, total_ms: EV.at(-1)[2], peak_kib: peak / KB };
}
const out = { n: N, hwm_kib: HWM / KB, slow_ms: SLOW, cols: ["what", "chunk", "ms", "source", "transform in", "transform out", "sink"] };
out.pipeline = await run("pipeline");
out.ignore = await run("ignore");
if (process.argv[2]) writeFileSync(process.argv[2], JSON.stringify(out));
