8. Around the checker: classes, async, .d.ts, tests, lint and TypeScript 7

Classes. private is checked by tsc only; #field is JavaScript's own private field and does not exist from outside: prefer # when privacy matters.

Classes in TypeScript: implements, the two privates, parameter properties

Classes get type annotations on fields and methods, implements (check that the class fits an interface), and access modifiers. Two kinds of "private" behave differently: private vocab is checked by tsc only (at run time it is a normal property, and (t as any).vocab reads it), while #calls is JavaScript's own private field and does not exist from outside at all. Prefer # when privacy matters. The shorthand constructor(readonly name: string) (a parameter property) saves two lines but is not erasable syntax (section 1). Many TypeScript codebases use few classes: plain objects, interfaces and functions cover most needs, and structural typing means a class is never required to satisfy an interface.

Async code in types is small: an async function returns Promise<T>, await unwraps it, an async function* returns AsyncGenerator<T>, and for await consumes any AsyncIterable<T>, the shape of every LLM token stream (the runtime side is on {{the event-loop page|n:4055c17b0d0d81fe857de8b34db109ea}}). In a catch, the error is unknown (useUnknownInCatchVariables, part of strict), because JavaScript can throw anything, not only Errors: narrow it with instanceof before reading .message. Declaration files. Types for a JavaScript package come from the package itself, from DefinitelyTyped's @types/<package>, or from a .d.ts you write; without one, the import is any.

.d.ts files and @types in detail

A declaration file (.d.ts) holds only types: what a JavaScript module exports and with which types. It is how TypeScript knows the types of the millions of npm packages written in, or compiled to, plain JavaScript. Import a JavaScript file that has none and the import becomes any (an error under strict, though the program runs fine); add a .d.ts next to it and the module is typed. Where types come from, in order of preference: the package ships them (its package.json points to .d.ts files through "types" or "exports"; most modern packages, including zod, vitest and the Anthropic and OpenAI SDKs, do); DefinitelyTyped, a community repository that publishes @types/<package> for untyped packages ({{DefinitelyTyped|https://github.com/DefinitelyTyped/DefinitelyTyped}}; @types/node describes Node's own APIs, and global ones must also be listed in "types"); or write your own .d.ts, or declare module "untyped-lib" { ... } for a whole package. When you publish a library, tsc with "declaration": true (on in the generated config) writes the .d.ts files for you; the inference demo in section 3 is exactly that output.

Publishing: the "exports" map. A library's package.json "exports" field lists its entry points and which file each kind of importer gets: conditions such as "import", "require" and "types" are tried in object order, so put "types" before the files and "default" last. Any subpath it does not list cannot be imported (ERR_PACKAGE_PATH_NOT_EXPORTED), and it takes precedence over "main" ({{Node.js: package entry points and conditional exports|https://nodejs.org/api/packages.html}}, checked 2026-10-26).

A dual ESM and CommonJS package with its types, and when TypeScript reads the map
{
  "name": "tok",
  "type": "module",
  "exports": {
    ".": {
      "import":  { "types": "./dist/index.d.ts",  "default": "./dist/index.js" },
      "require": { "types": "./dist/index.d.cts", "default": "./dist/index.cjs" }
    },
    "./package.json": "./package.json"
  }
}

An illustrative layout in the shape of the TypeScript modules reference's example. import "tok" gets index.js and its types from index.d.ts; require("tok") gets the CommonJS build and .d.cts types (a .d.cts file always describes CommonJS, a .d.mts file ES modules); import "tok/dist/internal.js" fails because the subpath is not listed. TypeScript follows "exports" only when moduleResolution is node16, nodenext or bundler, and always matches the "types" and "default" conditions when present; under the old node10 setting it ignores the map and falls back to "types" and "main" ({{TypeScript: modules reference|https://www.typescriptlang.org/docs/handbook/modules/reference.html}}). Node's own conditions, from most to least specific: "node-addons", "node", "import", "require", "module-sync", "default".

Tests. Vitest runs .ts test files directly and, like Node, does not type-check them: keep npx tsc in CI too. What to test is on {{Testing and quality|n:3c65c17b0d0d81548848e2ebdd2f63ee}}.

Vitest from pytest, expectTypeOf, watch mode

Vitest (5.0.3 here; {{vitest.dev|https://vitest.dev}}) is the common test runner for TypeScript: it runs .ts test files directly, with a Jest-compatible API (describe, it, expect: pytest's classes and functions; expect(x).toBe(y) is assert x is y, toEqual is == on structure). It does not type-check by default (like Node, it strips types), so keep npx tsc in CI too. expectTypeOf tests types, not values, checked by tsc when the test file is type-checked: useful for library code whose types are part of its contract. npx vitest without run stays in watch mode and reruns affected tests on save.

The TypeScript 7 transition

TypeScript 7.0 (released 2026-07-08) is the same compiler ported from TypeScript to Go, line by line: the type rules are unchanged, it is much faster, some old options are gone, and it has no programmatic API yet, which is why typescript-eslint still runs on TypeScript 6. Measured here on zod's own TypeScript sources (125 files, 37,722 lines):

The 7.0 release: Microsoft's numbers, where the speed comes from, the missing API

TypeScript 7.0 was released on 2026-07-08 (npm publish time of 7.0.2 the same day). It is the existing compiler ported from TypeScript to Go, line by line, so the type rules are the same; what changes is speed, the options that were removed, and the missing API ({{Announcing TypeScript 7.0|https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/}}). Microsoft reports 8 to 12 times faster full builds on large projects (VS Code 125.7 s to 10.6 s, Sentry 139.8 s to 15.7 s, Playwright 12.8 s to 1.47 s), from native code and shared-memory multithreading. Measured here on a smaller project, zod's own TypeScript sources, it was about 5 times (the chart above).

About 5 times, less than on VS Code-sized projects (start-up is a larger share of a half-second run), and a factor of about 1.4 comes from checking on several threads at once: with --checkers 1 TypeScript 7 is still about 3.6 times faster than 6.0 on one checker. No API in 7.0: "TypeScript 7.0 does not ship with an API. We expect TypeScript 7.1 to ship with a new (and different) API." Tools built on the compiler API (typescript-eslint, as shown above; also Vue, Svelte, Astro and MDX tooling, per the post) keep running on TypeScript 6 until then; editors use TypeScript 7 through its new language server.

What 7.0 removed or changed (an old tsconfig may need updating)

All from the 7.0 post: target: es5, downlevelIteration, moduleResolution node/node10/classic, module amd/umd/systemjs/none and baseUrl are errors now; esModuleInterop and alwaysStrict can no longer be turned off. New defaults: strict true, module esnext, noUncheckedSideEffectImports true, types [], rootDir ./. An old project that compiled on 5.x may need its tsconfig updated before 7.0 accepts it.

TypeScript 7.1 beta and the Rust port, as of 26 October 2026

7.1, and a port to Rust. The TypeScript 7.1 beta (20 October 2026) ships that API, split into entry points (typescript/sync, typescript/async, typescript/ast, typescript/fs), plus content mappers that let a .vue or .svelte file present a TypeScript view to the checker; tsc runs them only with --runExternalCode, because they are third-party code. Microsoft's table puts 7.1 at 1.2 to 1.9 times the speed of 7.0 with 15.8% to 49.6% less memory on five codebases (--noEmit, 4 checker threads) ({{7.1 beta post|https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/}}). Separately, tsrs ports the compiler to Rust: Cloudflare and VoidZero inside the Oxc toolchain, working alongside the TypeScript team and "not forking TypeScript", claim up to 8 times the speed and about 70% less memory than 7.0 with the same number of checker workers (vendor figures; experimental, and diagnostics can print in a different order). Their case for Rust over Go is WebAssembly: a Go build has to ship Go's garbage collector, so a Rust checker embeds more cheaply in browsers and other hosts ({{Cloudflare|https://blog.cloudflare.com/typescript-rust-port/}}).

9. Mistakes worth a checklist

Each is taught above; the checklist is for review.

Ten mistakes and their fixes
  • Thinking that running a .ts file checks it. node, tsx, Bun and vitest strip types without checking. Run npx tsc (it uses noEmit or an outDir) in CI and in your editor.
  • JSON.parse(x) as T on data you did not create. A cast checks nothing. Parse to unknown and validate with a zod schema; derive T from it with z.infer.
  • Letting any in, from JSON.parse, untyped libraries, catch in old code, or an explicit annotation. It spreads silently. Lint against it (noExplicitAny, no-unsafe-*) and use unknown.
  • Silencing an error with as or !. Read the error first: it is usually right. If you must assert, assert as late and as narrowly as possible, with a comment saying why it is true.
  • A bag of optional fields instead of a discriminated union. One member per kind, with a literal tag, and a never check in default.
  • Truthiness checks on numbers and strings. if (count) is false for 0 and if (name) for "". Use !== undefined or != null when 0 or empty are valid.
  • Floating promises. await it, return it, or mark it void; let a linter enforce it.
  • Enums and parameter properties in code that Node runs directly. Use as const objects and explicit fields; turn on erasableSyntaxOnly.
  • A global TypeScript install, or a caret range. Install typescript per project as a dev dependency and run npx tsc, so every machine and CI use the same compiler. Minor releases can add errors to code that compiled before (better inference finds real bugs), so many teams pin with ~ and upgrade in a dedicated change.
  • Type-level cleverness. Recursive conditional types that nobody else can read and that slow the editor. Derive types from one source; stop there.
