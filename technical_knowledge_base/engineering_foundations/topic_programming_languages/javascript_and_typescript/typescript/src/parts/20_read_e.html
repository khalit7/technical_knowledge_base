7. Checking data at run time with zod

Types are erased, so nothing checks data that arrives while the program runs: an HTTP body, a file, an environment variable, and above all the JSON an LLM writes. JSON.parse(text) as Reply is a promise you cannot keep. The answer is a schema library: you describe the shape once as a run-time object, it validates values, and TypeScript derives the static type from it. zod is the most used (4.6.5 here; {{zod.dev|https://zod.dev}}); valibot and ArkType are alternatives with the same idea.

z.infer<typeof ToolCall> is the static type, computed from the schema, so the two can never drift apart. parse returns the typed value or throws; safeParse returns { success: true, data } or { success: false, error }, a discriminated union you narrow on success. Each issue has a path (which field) and a message, and z.prettifyError formats them, as above. It is pydantic with the direction inverted (the table at the top): validate at the boundary, trust the types inside.

Parsing LLM output

Model output fails in predictable ways: the JSON is wrapped in a Markdown fence or a sentence, a number arrives as a string, a field is missing, the reply is cut off by the token limit. A robust reader has three steps: find the JSON, JSON.parse it inside try, and validate with the schema, returning a typed result or an error message you can send back to the model for a retry.

One schema, three uses: the type, the check, and the tool definition

Tool use (function calling) needs a JSON Schema for each tool's input. zod 4 writes it from the same schema ({{zod: JSON Schema|https://zod.dev/json-schema}}), so the description sent to the model, the type in your code and the validation of the model's arguments come from one definition. A detail that matters: by default the JSON Schema describes the output of parsing, where a field with a default (unit) always exists, so it is listed as required. What a model sends is the input, where unit may be omitted: { io: "input" } gives that version.

How a server forces the model to emit valid JSON in the first place (constrained decoding, provider "structured outputs") is on {{Sampling and decoding|n:3c65c17b0d0d8115bafcda29a2c7086e}}; how agent libraries send the schema, validate and retry is on {{Typed agent libraries|n:3f15c17b0d0d819fba89f9ec88feb859}} (Mastra's createTool() takes a Zod inputSchema). Tool calling and structured output in TypeScript, on real SDKs, are on {{TypeScript: LLM apps and agents|n:4055c17b0d0d8109aad6e69a87b3bd6f}}. A server is not a validator: the schema check stays in your code either way.

z.strictObject rejects unknown keys and z.coerce.number() converts strings first: the lab's last two columns.

strictObject, coerce and transform

z.object drops unknown keys silently; z.strictObject rejects them (useful to catch a model inventing fields; harmful if the API adds fields later). z.coerce.number() runs Number(x) first, so "7" becomes 7, but "2.1 million" becomes NaN and fails (the lab's fifth row). .transform converts after validating, and z.infer gives the transformed type.
