The idea in one sentence. TypeScript is a checker that reads your JavaScript plus its types before the program runs and is then erased, so it proves things only about code it can see: narrowing makes unions safe inside the program, and every value that arrives from outside (an LLM reply, an HTTP body, a file) must be checked at run time by a schema such as zod.

Fig. 1 is the picture the rest of the page fills in; it runs the ten real model replies of section 7 through a cast and through a zod schema.

  1. Compile time: tsc reads code plus types. app.ts is JavaScript plus a layer of type syntax: in the page's demo.ts (section 1), 83 of its 214 non-blank characters are types. tsc, in your editor and CI, checks the code it can see and reports errors, or nothing.
  2. The types are erased on the way down. Before the program runs they are stripped (node, Bun) or compiled away (tsc): what V8 runs is plain JavaScript, with no types left to check anything against.
  3. Data arrives from outside, at run time. An LLM reply, an HTTP body, a file, an environment variable: here the 10 recorded replies of section 7, a model asked for {"city": string, "population": number}.
  4. A cast checks nothing. A cast (JSON.parse(text) as Reply) is only a claim made to tsc; at run time it does not exist, so every reply reaches the program: 4 printed the right answer, 2 printed wrong data without an error, and 4 crashed.
  5. A zod schema stands on both plates. It is a real value, so it exists on both sides of the line: tsc reads the type from it (z.infer) and Node runs the check (.parse). 4 pass, valid and typed; 6 are rejected with a reason you can send back to the model for a retry.

A function with a type annotation and a call that breaks it. Predict before you look.

Two programs, two jobs. tsc found the mistake (line 5, column 25). node never looked at the types: it deleted them and ran the JavaScript, which crashed on the same line. Running a .ts file does not check it. Only tsc checks.

With 42 as any (an assertion, section 6) tsc reports nothing, and the crash is the same.

That is the whole model: type erasure. TypeScript's own design goals list as non-goals "add or rely on run-time type information in programs" and "apply a sound or 'provably correct' type system" ({{TypeScript Design Goals|https://github.com/microsoft/TypeScript/wiki/TypeScript-Design-Goals}}).

Stripping keeps every column; compiling writes a new file

type syntax (erased)written by tsc

There are two ways to remove the types. Type stripping (what node file.ts, Bun, tsx and esbuild do) replaces every annotation with spaces, so line and column numbers in errors still point at your source. Compiling with tsc (when you set an outDir) writes new, reformatted JavaScript. The figure steps through both on the same file; both outputs are real (Node's own stripTypeScriptTypes function and tsc's emit).

  1. The source. demo.ts: an interface, annotations on parameters, variables and the return type, and an as.
  2. Find the type syntax. 83 characters are types (highlighted): they mean something to tsc and nothing to JavaScript.
  3. Replace them with spaces. What remains is plain JavaScript that V8 runs. Every line and column is where it was, so an error message points at the same line and column of your source. This is node file.ts (the real output of stripTypeScriptTypes).
  1. The source. The same demo.ts.
  2. Find the type syntax. tsc removes the same 83 characters.
  3. Write a new file. tsc prints fresh JavaScript: the interface line is gone, the loop is reformatted onto two lines and export {}; is added (the file is a module), so line numbers no longer match the source. That is why tsc --init turns on sourceMap: a map from output positions back to the .ts file. Highlighted lines are not in the source.

Node's stripping is why some TypeScript syntax is now discouraged: an enum is not just a type, it creates a JavaScript object.

Node's strip-only mode rejects syntax that would need generated code. The fix is a TypeScript 5.8 option, erasableSyntaxOnly, which makes tsc reject that syntax up front ({{TypeScript 5.8|https://devblogs.microsoft.com/typescript/announcing-typescript-5-8/}}), and the idiom that replaces enums: an as const object plus a type read off it.

Line 1 (the enum) and line 2 (a parameter property, constructor(public x: number), which secretly writes this.x = x) are rejected; lines 3 and 4 are the replacement: Role2 is both a value (the object) and a type ("user" | "assistant").

If you run .ts files with Node, turn erasableSyntaxOnly on, and use as const objects where you would have written an enum.
