The idea in one sentence. TypeScript is a checker that reads your JavaScript plus its types before the program runs and is then erased, so it proves things only about code it can see: narrowing makes unions safe inside the program, and every value that arrives from outside (an LLM reply, an HTTP body, a file) must be checked at run time by a schema such as zod.

Types live only above the dashed line; data from outside arrives below it

A cast (JSON.parse(text) as Reply) is only a claim made to tsc; at run time it does not exist. A zod schema is a real value, so it exists on both sides of the line: tsc reads the type from it and Node runs the check. Section 7 runs ten real model replies through both.

1. Types are checked, then erased

A function with a type annotation and a call that breaks it. Predict before you look.

Two programs, two jobs. tsc found the mistake (line 5, column 25). node never looked at the types: it deleted them and ran the JavaScript, which crashed on the same line. Running a .ts file does not check it. Only tsc checks.

With 42 as any (an assertion, section 6) tsc reports nothing, and the crash is the same.

That is the whole model: type erasure. TypeScript's own design goals list as non-goals "add or rely on run-time type information in programs" and "apply a sound or 'provably correct' type system" (TypeScript Design Goals).

There are two ways to remove the types. Type stripping (what node file.ts, Bun, tsx and esbuild do) replaces every annotation with spaces, so line and column numbers in errors still point at your source. Compiling with tsc (when you set an outDir) writes new, reformatted JavaScript. Step through both on the same file; both outputs are real (Node's own stripTypeScriptTypes function and tsc's emit).

Without the option, scores[2] has type number even though the array has two elements. With it (the default from tsc --init), every index read is number | undefined until you check:

The cost: you write more checks (if (x !== undefined), ?? 0, or for...of instead of indexes). Most new projects keep it. A length check does not count as one:

With noUncheckedIndexedAccess, a length check does not narrow an index read: scores[0] is still number | undefined. Use const [first] = scores; if (first !== undefined), or scores.at(0) with a check.

The module options: nodenext, verbatimModuleSyntax, isolatedModules, skipLibCheck

3. Inference, objects and structural typing

You annotate with a colon after the name, as in Python: let n: number = 0, function f(x: string): number. The basic types are JavaScript's values: number (one type for ints and floats: a 64-bit double), string, boolean, bigint, null, undefined, arrays number[] (also Array<number>), tuples [string, number] and object types { id: number }. Most of the time you do not write them: tsc infers types from values, by four rules that explain many surprising errors later.

  • let widens, const keeps the literal. const role = "user" has the type "user" (a literal type: exactly that string), because a const can never hold anything else; with let it is any string.
  • Object properties and array elements widen even in a const, because they can be reassigned: msg.role is string, not "user".
  • as const freezes everything: ["ana", 3] as const is a readonly tuple of literals; without it, an array of string | number, not a pair.
  • Return types are inferred, including a number | null with the null you might forget. The common convention: annotate parameters always (they cannot be inferred), and return types of exported functions (so a change inside cannot silently change your public API); let everything else be inferred.

To see what tsc inferred, ask it to write a declaration file (.d.ts: the types of a module without its code).

ev is a const, but its property can still be reassigned, so kind widens to string, which is not "text" | "image". With as const (or the literal written inline in the call) it fits, as the next drill shows.

Functions and object types read as you would guess from Python, with three things to know: a function passed where a function type is expected gets its parameter types from it (contextual typing, why .map(s => s.length) needs no annotations); interface and type overlap almost completely (many codebases use interface for object shapes and type for everything else, such as unions); and readonly is checked only by tsc, the object stays mutable at run time.

Functions, overloads, interface against type, readonly, index signatures

Optional parameters (stop?: string) have the type string | undefined inside; default values make a parameter optional for callers and give it a type by inference; rest parameters collect into an array; void means "the return value is not meant to be used". A function type is written like an arrow, (text: string) => number, and a function passed where one is expected gets its parameter types from it: contextual typing, why .map(s => s.length) rarely needs annotations. Overloads give one function several signatures when the return type depends on the argument type; use them sparingly, a union parameter or a generic is usually clearer.

The callers see only the first two signatures; the third is the implementation and must handle every case.

They overlap almost completely. interface names an object shape; two declarations with the same name merge (how libraries let you add fields to their types), and extends builds on another. type names any type: an object, but also a union, a tuple, a function or a computed type, and & (an intersection) combines object types. The pragmatic rule many codebases use: interface for object shapes, type for everything else. ? marks an optional property, readonly one that cannot be reassigned (checked only by tsc; at run time the object is mutable, use Object.freeze for that), and { [model: string]: number } (an index signature, same as Record<string, number>) any number of string keys.

Excess property checks: why a typo is caught, sometimes.

An object type means "at least these properties", so opts (which has model and an extra key) fits Options. As a special case, a fresh object literal written directly where a type is expected may not have unknown keys, because there the extra key is almost always a typo. Through a variable, the typo passes silently and temperature is never sent.

Structural typing: shape, not name. A value fits a type if it has the right members, whatever class or name it came from: a string, an array, an instance of an unrelated class and a plain object all have a numeric length, so all four fit HasLength. This is the deepest difference from Java, C# or Rust, and it is what Python's typing.Protocol does (the root's Design space compares structural typing with Rust traits and C++ templates). When you need the opposite, two string types that must not mix (a user id and an order id), add a brand: a fake property that exists only in the type. It costs nothing at run time (the value is still a plain string), and the only way to make a UserId is through a function you control (asUserId, ideally after validating).

Object.keys returns string[], not ("small" | "large")[], because an object may have more keys than its type lists (structural typing). Use Object.entries, or a typed key list.

4. Unions and narrowing: where TypeScript earns its keep

A union A | B is a value that is one of several types. You can only use what all members share: on string | number | null you cannot call toFixed, because a string has no such method and null has nothing at all.

Narrowing is how you get to a single member: tsc follows your ifs, switches and early returns and, at each line, knows which members are still possible. Every check JavaScript can do at run time narrows:

Discriminated unions: the pattern for LLM events, tool calls and states

A discriminated union is a union of object types that share one literal field (the tag, here type). Checking the tag narrows to exactly one member, with its own fields. This is how every LLM SDK types its streaming events, and how you should model anything with states. A default branch that assigns the value to a variable of type never (the empty type: no value has it) compiles only if every member was handled. Add a member to the union and forget to handle it:

That is exhaustiveness checking: the compiler lists the case you forgot, with its full shape. The same data modelled as one object with optional fields (the shape a quick port from JSON often produces) makes every field "maybe", so every use needs a check, and nothing tells you when a new kind appears. The rule: make illegal states unrepresentable. If a text event always has a delta and never a name, give it its own member. 5. Generics, and types computed from values

A generic function has type parameters in angle brackets: first<T>(xs: T[]): T | undefined works for any element type and keeps it, instead of losing it to any; tsc infers T from the arguments, so callers almost never write it. A constraint (T extends { length: number }) says what T must at least have, and K extends keyof T says "K is one of T's keys", which is how pluck(rows, "tokens") knows it returns number[]. The constraints are what make the errors precise. Two rules of thumb: a type parameter that appears only once in a signature does nothing (f<T>(x: T): void is just f(x: unknown): void), and a generic that needs a comment to be understood is probably worse than two plain functions.

TypeScript also has a small language for computing types from values, which is how one constant becomes the single source of truth for both:

  • typeof DEFAULTS in a type position reads the type of a value.
  • keyof T is the union of T's keys; T["temperature"] (an indexed access type) is the type of one property.
  • (typeof MODELS)[number] turns an as const array into the union of its elements: write the list once, get the type for free.

To make tsc print a type, the snippets assign it to never with satisfies and read the error message; the trick is used throughout this page. Note the order in the printed unions: "large" | "medium" | "small" is not the order the array was written in. TypeScript 7 orders union members deterministically (stableTypeOrdering is "true by default, and cannot be turned off", says the 7.0 post), so do not read meaning into the order in an error message.

satisfies: check without forgetting. An annotation (const a: Record<string, Route>) checks the value and then replaces its type with the annotation, so the specific keys are forgotten. satisfies (TypeScript 4.9) checks the value against the type and keeps the inferred type: the wrong auth on line 4 is caught, and so is the typo b.hom.

Prefer satisfies for configuration objects and lookup tables, and never as to get the same effect (as checks nothing, section 6).

Mapped, conditional and template literal types, at a practical level

The utility types are not built-in magic: they are written in TypeScript's type language, which has loops over keys, if-then-else and string building. You will read these in library code more often than you write them.

6. Where the checker lies: any, as, and the unsound holes

Three special types every TypeScript programmer must keep apart:

  • any switches checking off: every operation is allowed, and the result is any again. JSON.parse returns any, and so does untyped JavaScript.
  • unknown is the safe "could be anything": nothing is allowed until you narrow it. Use it for anything from outside your program.
  • never is the empty type: a function that always throws returns never, and a fully narrowed union is never.

Only line 4 is an error. a.foo.bar() would crash, and tsc did not say a word.

Worse, any spreads: anything computed from it is unchecked too.

i * "3" is 3 (JavaScript converts the string for *), but "3" + 1 is the string "31", assigned to a variable declared number. No error, no crash, a wrong value. The cure is to type the boundary: const config: unknown = JSON.parse(...) and then check (or parse with zod, section 7).

JSON.parse returns any, so the typo nmae passes and the annotation : string is believed. The crash comes later, far from the cause.

Assertions are claims, not checks. x as T (a type assertion, often called a cast) tells tsc "trust me, x is a T"; it generates no code and checks nothing at run time. x! (the non-null assertion) says "this is not null or undefined". as const is different: it is not a claim, it only makes inference narrower, and it is always safe.

Unsound by design

A type system is sound if a program that type-checks can never have a value of the wrong type at run time. TypeScript is not, on purpose: its design goals put "a balance between correctness and productivity" ahead of soundness (Design Goals, non-goal 3). 7. Checking data at run time with zod

Types are erased, so nothing checks data that arrives while the program runs: an HTTP body, a file, an environment variable, and above all the JSON an LLM writes. JSON.parse(text) as Reply is a promise you cannot keep. The answer is a schema library: you describe the shape once as a run-time object, it validates values, and TypeScript derives the static type from it. zod is the most used (4.6.5 here; zod.dev); valibot and ArkType are alternatives with the same idea.

z.infer<typeof ToolCall> is the static type, computed from the schema, so the two can never drift apart. parse returns the typed value or throws; safeParse returns { success: true, data } or { success: false, error }, a discriminated union you narrow on success. Each issue has a path (which field) and a message, and z.prettifyError formats them, as above. It is pydantic with the direction inverted (the table at the top): validate at the boundary, trust the types inside.

Parsing LLM output

Model output fails in predictable ways: the JSON is wrapped in a Markdown fence or a sentence, a number arrives as a string, a field is missing, the reply is cut off by the token limit. A robust reader has three steps: find the JSON, JSON.parse it inside try, and validate with the schema, returning a typed result or an error message you can send back to the model for a retry.

One schema, three uses: the type, the check, and the tool definition

Tool use (function calling) needs a JSON Schema for each tool's input. zod 4 writes it from the same schema (zod: JSON Schema), so the description sent to the model, the type in your code and the validation of the model's arguments come from one definition. A detail that matters: by default the JSON Schema describes the output of parsing, where a field with a default (unit) always exists, so it is listed as required. What a model sends is the input, where unit may be omitted: { io: "input" } gives that version.

How a server forces the model to emit valid JSON in the first place (constrained decoding, provider "structured outputs") is on Sampling and decoding; how agent libraries send the schema, validate and retry is on Typed agent libraries (Mastra's createTool() takes a Zod inputSchema). Tool calling and structured output in TypeScript, on real SDKs, are on TypeScript: LLM apps and agents. A server is not a validator: the schema check stays in your code either way.

z.strictObject rejects unknown keys and z.coerce.number() converts strings first: the lab's last two columns.

strictObject, coerce and transform

z.object drops unknown keys silently; z.strictObject rejects them (useful to catch a model inventing fields; harmful if the API adds fields later). z.coerce.number() runs Number(x) first, so "7" becomes 7, but "2.1 million" becomes NaN and fails (the lab's fifth row). .transform converts after validating, and z.infer gives the transformed type.

8. Around the checker: classes, async, .d.ts, tests, lint and TypeScript 7

Classes. private is checked by tsc only; #field is JavaScript's own private field and does not exist from outside: prefer # when privacy matters.

Classes in TypeScript: implements, the two privates, parameter properties

Classes get type annotations on fields and methods, implements (check that the class fits an interface), and access modifiers. Two kinds of "private" behave differently: private vocab is checked by tsc only (at run time it is a normal property, and (t as any).vocab reads it), while #calls is JavaScript's own private field and does not exist from outside at all. Prefer # when privacy matters. The shorthand constructor(readonly name: string) (a parameter property) saves two lines but is not erasable syntax (section 1). Many TypeScript codebases use few classes: plain objects, interfaces and functions cover most needs, and structural typing means a class is never required to satisfy an interface.

Async code in types is small: an async function returns Promise<T>, await unwraps it, an async function* returns AsyncGenerator<T>, and for await consumes any AsyncIterable<T>, the shape of every LLM token stream (the runtime side is on the event-loop page). Declaration files. Types for a JavaScript package come from the package itself, from DefinitelyTyped's @types/<package>, or from a .d.ts you write; without one, the import is any.

.d.ts files and @types in detail

A declaration file (.d.ts) holds only types: what a JavaScript module exports and with which types. It is how TypeScript knows the types of the millions of npm packages written in, or compiled to, plain JavaScript. Import a JavaScript file that has none and the import becomes any (an error under strict, though the program runs fine); add a .d.ts next to it and the module is typed. Where types come from, in order of preference: the package ships them (its package.json points to .d.ts files through "types" or "exports"; most modern packages, including zod, vitest and the Anthropic and OpenAI SDKs, do); DefinitelyTyped, a community repository that publishes @types/<package> for untyped packages (DefinitelyTyped; @types/node describes Node's own APIs, and global ones must also be listed in "types"); or write your own .d.ts, or declare module "untyped-lib" { ... } for a whole package. When you publish a library, tsc with "declaration": true (on in the generated config) writes the .d.ts files for you; the inference demo in section 3 is exactly that output.

Publishing: the "exports" map. A library's package.json "exports" field lists its entry points and which file each kind of importer gets: conditions such as "import", "require" and "types" are tried in object order, so put "types" before the files and "default" last. Any subpath it does not list cannot be imported (ERR_PACKAGE_PATH_NOT_EXPORTED), and it takes precedence over "main" (Node.js: package entry points and conditional exports, checked 2026-10-26).

An illustrative layout in the shape of the TypeScript modules reference's example. import "tok" gets index.js and its types from index.d.ts; require("tok") gets the CommonJS build and .d.cts types (a .d.cts file always describes CommonJS, a .d.mts file ES modules); import "tok/dist/internal.js" fails because the subpath is not listed. TypeScript follows "exports" only when moduleResolution is node16, nodenext or bundler, and always matches the "types" and "default" conditions when present; under the old node10 setting it ignores the map and falls back to "types" and "main" (TypeScript: modules reference). Node's own conditions, from most to least specific: "node-addons", "node", "import", "require", "module-sync", "default".

Tests. Vitest runs .ts test files directly and, like Node, does not type-check them: keep npx tsc in CI too. What to test is on Testing and quality.

Vitest from pytest, expectTypeOf, watch mode

Vitest (5.0.3 here; vitest.dev) is the common test runner for TypeScript: it runs .ts test files directly, with a Jest-compatible API (describe, it, expect: pytest's classes and functions; expect(x).toBe(y) is assert x is y, toEqual is == on structure). It does not type-check by default (like Node, it strips types), so keep npx tsc in CI too. expectTypeOf tests types, not values, checked by tsc when the test file is type-checked: useful for library code whose types are part of its contract. npx vitest without run stays in watch mode and reruns affected tests on save.

The 7.0 release: Microsoft's numbers, where the speed comes from, the missing API

TypeScript 7.0 was released on 2026-07-08 (npm publish time of 7.0.2 the same day). It is the existing compiler ported from TypeScript to Go, line by line, so the type rules are the same; what changes is speed, the options that were removed, and the missing API (Announcing TypeScript 7.0). Microsoft reports 8 to 12 times faster full builds on large projects (VS Code 125.7 s to 10.6 s, Sentry 139.8 s to 15.7 s, Playwright 12.8 s to 1.47 s), from native code and shared-memory multithreading. Measured here on a smaller project, zod's own TypeScript sources, it was about 5 times (the chart above).

About 5 times, less than on VS Code-sized projects (start-up is a larger share of a half-second run), and a factor of about 1.4 comes from checking on several threads at once: with --checkers 1 TypeScript 7 is still about 3.6 times faster than 6.0 on one checker. No API in 7.0: "TypeScript 7.0 does not ship with an API. We expect TypeScript 7.1 to ship with a new (and different) API." Tools built on the compiler API (typescript-eslint, as shown above; also Vue, Svelte, Astro and MDX tooling, per the post) keep running on TypeScript 6 until then; editors use TypeScript 7 through its new language server.

What 7.0 removed or changed (an old tsconfig may need updating)

All from the 7.0 post: target: es5, downlevelIteration, moduleResolution node/node10/classic, module amd/umd/systemjs/none and baseUrl are errors now; esModuleInterop and alwaysStrict can no longer be turned off. New defaults: strict true, module esnext, noUncheckedSideEffectImports true, types [], rootDir ./. An old project that compiled on 5.x may need its tsconfig updated before 7.0 accepts it.

TypeScript 7.1 beta and the Rust port, as of 26 October 2026

7.1, and a port to Rust. The TypeScript 7.1 beta (20 October 2026) ships that API, split into entry points (typescript/sync, typescript/async, typescript/ast, typescript/fs), plus content mappers that let a .vue or .svelte file present a TypeScript view to the checker; tsc runs them only with --runExternalCode, because they are third-party code. Their case for Rust over Go is WebAssembly: a Go build has to ship Go's garbage collector, so a Rust checker embeds more cheaply in browsers and other hosts (Cloudflare).

9. Mistakes worth a checklist

Each is taught above; the checklist is for review.

Ten mistakes and their fixes
  • Thinking that running a .ts file checks it. node, tsx, Bun and vitest strip types without checking. Run npx tsc (it uses noEmit or an outDir) in CI and in your editor.
  • JSON.parse(x) as T on data you did not create. A cast checks nothing. Parse to unknown and validate with a zod schema; derive T from it with z.infer.
  • Letting any in, from JSON.parse, untyped libraries, catch in old code, or an explicit annotation. It spreads silently. Lint against it (noExplicitAny, no-unsafe-*) and use unknown.
  • Silencing an error with as or !. Read the error first: it is usually right. If you must assert, assert as late and as narrowly as possible, with a comment saying why it is true.
  • A bag of optional fields instead of a discriminated union. One member per kind, with a literal tag, and a never check in default.
  • Truthiness checks on numbers and strings. if (count) is false for 0 and if (name) for "". Use !== undefined or != null when 0 or empty are valid.
  • Floating promises. await it, return it, or mark it void; let a linter enforce it.
  • Enums and parameter properties in code that Node runs directly. Use as const objects and explicit fields; turn on erasableSyntaxOnly.
  • A global TypeScript install, or a caret range. Install typescript per project as a dev dependency and run npx tsc, so every machine and CI use the same compiler. Minor releases can add errors to code that compiled before (better inference finds real bugs), so many teams pin with ~ and upgrade in a dedicated change.
  • Type-level cleverness. Recursive conditional types that nobody else can read and that slow the editor. Derive types from one source; stop there.
