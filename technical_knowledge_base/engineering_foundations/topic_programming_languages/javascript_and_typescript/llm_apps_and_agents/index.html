The idea in one screen

An LLM app in TypeScript is ordinary server code around one HTTP call: the SDK's types give every reply its shape before you run anything, your loop runs the tools the model asks for, and one zod schema checks every piece of model JSON where it crosses into your program.

  • content is an array of blocks, each with a type: text, tool_use, thinking and others. The response type is a discriminated union, so TypeScript makes you narrow on block.type === "text" before you may read block.text (narrowing: section 4 of the TypeScript page): msg.content[0].text is a type error, and it should be, because the first block is not always text.
  • stop_reason says why the model stopped: end_turn (finished), max_tokens (cut off), tool_use (wants a tool), stop_sequence, pause_turn, refusal and model_context_window_exceeded (the full list from the SDK's StopReason type in 0.131.0). Check it on every response.
  • usage counts input and output tokens: the bill. Real responses also carry cache counts (cache_read_input_tokens, cache_creation_input_tokens).
  • The wire shows what the SDK added for you: the anthropic-version: 2023-06-01 header (the API's version, not the model's), its retry counter, and its timeout (600 s).

2. When the call fails: the SDK already retries

A model API fails in ordinary ways: rate limits (HTTP 429), overload (529 and other 5xx), a slow or dead connection, or a request you got wrong (400). Read from the SDK's source (client.js, 0.131.0): it retries 2 times by default (maxRetries), on 408, 409, 429, every 5xx, and connection errors; it waits with exponential backoff or for the server's retry-after / retry-after-ms header; and its timeout is 10 minutes per attempt (in milliseconds in TypeScript: timeout: 600_000). A 400 is never retried: retrying a wrong request cannot fix it.

Predict: the server answers 429 twice, then succeeds. How many requests does it see, and does your code see an error? And when it never answers, with a 300 ms timeout and maxRetries 1, how long until the error?

// What the SDK does when the API fails: retries (429, 5xx, timeouts) and typed errors you can catch.
import Anthropic from "@anthropic-ai/sdk";
import { createServer } from "node:http";

let attempts = 0, mode = "";
const t0 = Date.now(); const log = (s: string) => console.log(`${String(Date.now() - t0).padStart(5)} ms  ${s}`);
const server = createServer((req, res) => {
  attempts++; req.resume();
  log(`server: attempt ${attempts} (${mode}), retry-count header ${req.headers["x-stainless-retry-count"]}`);
  if (mode === "429" && attempts <= 2) return res.writeHead(429, { "content-type": "application/json", "retry-after-ms": "100" })
    .end(JSON.stringify({ type: "error", error: { type: "rate_limit_error", message: "slow down" } }));
  if (mode === "400") return res.writeHead(400, { "content-type": "application/json" })
    .end(JSON.stringify({ type: "error", error: { type: "invalid_request_error", message: "max_tokens: must be at least 1" } }));
  if (mode === "hang") return;   // never answers
  res.writeHead(200, { "content-type": "application/json" }).end(JSON.stringify({ id: "msg_1", type: "message", role: "assistant",
    model: "m", content: [{ type: "text", text: "ok" }], stop_reason: "end_turn", stop_sequence: null, usage: { input_tokens: 1, output_tokens: 1 } }));
}).listen(0);
const client = new Anthropic({ baseURL: `http://127.0.0.1:${(server.address() as any).port}`, apiKey: "mock-key" });
const ask = (opts?: Anthropic.RequestOptions) =>
  client.messages.create({ model: "claude-sonnet-5-5", max_tokens: 64, messages: [{ role: "user", content: "hi" }] }, opts);

for (const [m, opts] of [["429", undefined], ["400", undefined], ["hang", { timeout: 300, maxRetries: 1 }]] as const) {
  mode = m; attempts = 0; console.log(`\n--- server answers ${m}${opts ? " (timeout 300 ms, maxRetries 1)" : ""}`);
  try {
    const r = await ask(opts);
    log(`client: success after ${attempts} attempts: ${r.content[0]?.type === "text" ? r.content[0].text : ""}`);
  } catch (e) {
    if (e instanceof Anthropic.RateLimitError) log(`client: RateLimitError ${e.status}`);
    else if (e instanceof Anthropic.BadRequestError) log(`client: BadRequestError ${e.status}, not retried: ${e.message}`);
    else if (e instanceof Anthropic.APIConnectionTimeoutError) log(`client: APIConnectionTimeoutError after ${attempts} attempts`);
    else throw e;
  }
}
server.closeAllConnections(); server.close();

Two lessons sit in the last row. First, timeouts are retried, so the worst case is about timeout × (maxRetries + 1) plus backoff (here two 300 ms attempts plus about 450 ms of backoff: about one second from the first attempt to the error). Second, catch the specific error classes (RateLimitError, BadRequestError, APIConnectionTimeoutError, all subclasses of Anthropic.APIError) with instanceof, never by matching message strings. In Python the same classes exist with the same names (anthropic.RateLimitError); TypeScript's catch (e) gives e the type unknown, so instanceof is also how you get a typed error back. And do not wrap the SDK in your own retry loop: its 3 attempts inside your 3 attempts is 9 requests.

3. Streaming: the events, in two wire formats

Streaming sends each piece of the answer as it is produced, as server-sent events on one HTTP response that stays open. The SSE format itself is owned by Streaming and real-time, and parsing raw SSE bytes safely (chunks split events and even UTF-8 characters) by JavaScript: the event loop, promises and streams; the SDK does that parsing for you. What remains is knowing the events. Predict before stepping: in which event does the final stop_reason arrive?

The SDK gives three levels. create({ ..., stream: true }) returns an async iterable of the raw events, already parsed (it drops the ping keep-alive: 23 events arrive, the wire carried 24). messages.stream() is the helper: .on("text", f) for each text piece and await finalMessage() for the assembled Message, identical to what a non-streaming call returns. 4. Tools and the agent loop, in TypeScript

You send a list of tools (a name, a description, a JSON Schema for the arguments). The model never runs anything: it stops with stop_reason: "tool_use" and a tool_use block; your code runs the function and sends the whole conversation back with a tool_result block of the same id; repeat until it answers. That loop plus tools is all an "agent" is; the loop itself, what a harness adds around it, and a lab that steps through real Claude Code runs are on Topic: agentic-harnesses (its Loop lab). This section is what the loop looks like in TypeScript, and the guards that make it safe:

Step limit
A model can ask for tools forever. Stop after maxSteps model calls and report it.
Timeout per tool
AbortSignal.timeout(500) gives every tool a deadline; a stuck tool becomes an error result, not a hung agent.
Validate the input
The arguments are the model's JSON: untrusted. safeParse them with the same zod schema that produced the JSON Schema; for paths, URLs or shell commands also check what they point at (a valid string can still be ../../etc/passwd).
Errors go to the model
A failed tool returns is_error: true with a message the model can act on. Throwing would kill the run.
Run calls concurrently
One turn may ask for several tools. Promise.all runs them together, and all results go back in one user message.
Meter the cost
Add up usage after every call; a loop multiplies the bill (every step resends everything).

const PRICE = { in: 2, out: 10 };   // US$ per million tokens, claude-sonnet-5-5 (Anthropic pricing page, 2026-10-05)
const TASK = "Who are the 3 heaviest users in chat.jsonl, and what share of all tokens do they have? Add the team of the top two.";

const schema = (s: z.ZodType) => { const { $schema, ...rest } = z.toJSONSchema(s) as any; return rest as Anthropic.Tool.InputSchema; };
const tools: Anthropic.Tool[] = [
  { name: "count_tokens", description: "Count word tokens per user in a JSONL chat log; returns totals and the top users.", input_schema: schema(CountArgs) },
  { name: "user_profile", description: "Look up a user's team.", input_schema: schema(ProfileArgs) },
];

export async function runAgent(client: Anthropic, scenario: string, opts: { maxSteps?: number; toolTimeoutMs?: number; profileUrl: string }) {
  const { maxSteps = 5, toolTimeoutMs = 500 } = opts;
  const messages: Anthropic.MessageParam[] = [{ role: "user", content: TASK }];
  const steps: any[] = []; const tot = { in: 0, out: 0, usd: 0 };

  type Result = Anthropic.ToolResultBlockParam & { ms: number };
  async function runTool(call: Anthropic.ToolUseBlock): Promise<Result> {
    const t0 = performance.now();
    const done = (content: string, is_error = false): Result =>
      ({ type: "tool_result" as const, tool_use_id: call.id, content, ...(is_error ? { is_error } : {}), ms: Math.round(performance.now() - t0) });
    try {
      const signal = AbortSignal.timeout(toolTimeoutMs);             // every tool gets a deadline
      if (call.name === "count_tokens") {
        const args = CountArgs.safeParse(call.input);                 // the model's JSON is untrusted input
        if (!args.success) return done(`invalid input: ${z.prettifyError(args.error)}`, true);
        return done(JSON.stringify(await countTokens(args.data)));
      }
      if (call.name === "user_profile") {
        const args = ProfileArgs.safeParse(call.input);
        if (!args.success) return done(`invalid input: ${z.prettifyError(args.error)}`, true);
        return done(await userProfile(opts.profileUrl, args.data, signal));
      }
      return done(`unknown tool ${call.name}`, true);
    } catch (e: any) {                                                  // errors go back to the model, not up the stack
      const why = e.name === "TimeoutError" ? `timed out after ${toolTimeoutMs} ms` : e.code === "ENOENT" ? `cannot open ${(call.input as any).path}: ENOENT` : String(e);
      return done(why, true);
    }
  }

  for (let step = 1; step <= maxSteps; step++) {
    const msg = await client.messages.create({ model: "claude-sonnet-5-5", max_tokens: 2048, tools, messages },
      { headers: { "x-mock-scenario": scenario } });
    tot.in += msg.usage.input_tokens; tot.out += msg.usage.output_tokens;
    tot.usd = (tot.in * PRICE.in + tot.out * PRICE.out) / 1e6;
    messages.push({ role: "assistant", content: msg.content });
    const calls = msg.content.filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use");
    const t0 = performance.now();
    const results = await Promise.all(calls.map(runTool));            // several calls in one turn run concurrently
    const wall = Math.round(performance.now() - t0);
    steps.push({ step, sent: messages.length - 1, content: msg.content, stop: msg.stop_reason, usage: msg.usage, results, wall, tot: { ...tot } });
    if (msg.stop_reason !== "tool_use") {
      const answer = msg.content.filter(b => b.type === "text").map(b => b.text).join(" ");
      return { scenario, outcome: "answered", answer, steps, tot, messages: messages.length };
    }
    messages.push({ role: "user", content: results.map(({ ms, ...r }) => r) });   // all results in ONE user message
  }
  return { scenario, outcome: `stopped: hit maxSteps=${maxSteps}`, answer: null, steps, tot, messages: messages.length };
}

5. Structured output: one zod schema, three jobs

Often you want data, not prose: {"user": "u0029", "tokens": 9491, "share_pct": 21.2}. One zod schema (zod from zero: section 7 of the TypeScript page) does three jobs:

  1. Ask with a schema. output_config.format sends a JSON Schema and the API constrains the model to produce matching JSON (Anthropic calls this structured outputs; docs). zodOutputFormat(schema) converts the zod schema.
  2. Check what came back. client.messages.parse() runs the zod schema on the reply and puts the typed result in parsed_output.
  3. Get the type for free. z.infer<typeof Heaviest> is the TypeScript type, so the rest of your program is checked against the same definition.

Found by running it: not every rule reaches the API
Look at the output_config sent line. The SDK sent user as a plain string and moved the regular expression into the field's description ("{pattern: \"^u\\\\d{4}$\"}"); the same happened to minimum/maximum on the numbers. So the API's constraint guarantees the JSON's shape (fields, types, no extra keys), but rules like a pattern or a range are only hinted to the model and enforced afterwards, by zod, in parse(). That is why case 2 ends in an error raised by the SDK rather than a wrong value in your program. Keep the zod check even when the API constrains output.

With OpenAI the equivalent is zodTextFormat(schema, name) in text.format with client.responses.parse() (from openai/helpers/zod, 7.28.0). With any other provider, or a model without constrained decoding: ask for JSON in the prompt, JSON.parse, then safeParse; on failure, send the zod error message back to the model and ask again, once or twice (the error text, case 3 above, is written for exactly that). How a server forces valid JSON in the first place (constrained decoding) is on Sampling and decoding; how agent libraries send the schema, validate and retry is on Typed agent libraries.

An alternative you will see in older code: defining a tool whose input schema is the output you want and forcing the model to call it. On Claude Sonnet 5.5 and Opus 5.5, forcing a specific tool (tool_choice any or tool) is rejected with a 400 (Sonnet 5.5 migration guide), so use structured outputs instead.

Because each request repeats everything before it, the total input billed grows with the square of the number of turns: the six turns billed 636 estimated input tokens for a conversation whose final request was 219. Three tools fight that: prompt caching (mark the stable prefix with cache_control; later requests that start with the same bytes are billed at a fraction, and any change early in the prefix, such as a timestamp in the system prompt, silently defeats it; prices and economics across providers are on Caching); compaction or trimming (summarise or drop old turns; Anthropic offers server-side compaction as a beta); and server-side state (OpenAI's Responses API keeps the conversation if you pass previous_response_id, conversation state guide; you are still billed for those input tokens, you just do not send them). 9. Serving: stream to the browser, cancel when it leaves

A web app puts your server between the browser and the model: the browser calls /ask, your server calls the model with the API key (which must never reach the browser, nor a logged request), and forwards each text piece as an SSE event. Two things go wrong in production that never show in a demo.

Cancellation. Users close tabs. If your server does not notice, the model keeps generating, and you pay for every token nobody will read. In Node the response's close event fires when the client goes away; hand an AbortController's signal to the SDK call and abort it there. The SDK then closes the upstream HTTP request and throws APIUserAbortError, which you catch. Predict before stepping: with nobody aborting, how many of the 114 events does the model still generate?

Backpressure. res.write() returns false when the bytes cannot leave as fast as you write them (a slow phone, a congested link); Node then keeps the rest in memory, so a server that ignores the false can hold the whole response in RAM for every slow client at once. The fix is one line: when write returns false, await once(res, "drain") before writing more.

h2_backpressure.ts
// Backpressure: res.write() returns false when the socket cannot keep up. Ignore it and Node queues the bytes in memory.
import { createServer, request } from "node:http";
import { once } from "node:events";

const EVENTS = 20000, EVENT = `data: ${JSON.stringify("x".repeat(90))}\n\n`;   // about 2 MB in total
async function run(respect: boolean) {
  let peak = 0, falses = 0;
  const server = createServer(async (_req, res) => {
    res.writeHead(200, { "content-type": "text/event-stream" });
    for (let i = 0; i < EVENTS; i++) {
      const ok = res.write(EVENT);
      peak = Math.max(peak, res.writableLength);              // bytes queued inside this process
      if (!ok) { falses++; if (respect) await once(res, "drain"); }
    }
    res.end();
  });
  await new Promise<void>(r => server.listen(0, "127.0.0.1", r));
  const t0 = performance.now();
  await new Promise<void>(done => request({ port: (server.address() as any).port, path: "/" }, async (res) => {
    res.pause(); await new Promise(r => setTimeout(r, 300));    // a slow reader: reads nothing for 300 ms
    res.resume(); res.on("end", done);
  }).end());
  server.close();
  console.log(`${respect ? "awaits drain " : "ignores false"}: write() returned false ${String(falses).padStart(5)} times, peak queued in the server ${(peak / 1024).toFixed(0).padStart(5)} KiB, ${Math.round(performance.now() - t0)} ms`);
}
console.log(`${EVENTS} events of ${EVENT.length} bytes = ${(EVENTS * EVENT.length / 1024).toFixed(0)} KiB to a client that waits 300 ms before reading`);
await run(false);
await run(true);

The 64 KiB plateau is Node's default stream buffer size (highWaterMark, 65,536 bytes; printed by stream.getDefaultHighWaterMark(false) on Node 24.21.0). With LLM tokens arriving at tens per second the risk is small for one stream, but a proxy that relays many streams, or a server that forwards a fast upstream to slow clients, needs it. stream.pipeline() and .pipe() handle backpressure for you when both ends are Node streams.

Before you ship: the twelve mistakes this page's runs show
  • Reading content[0].text without checking the block type or stop_reason: the first block may be thinking or tool_use, and a max_tokens stop means the text is cut off. TypeScript's narrowing forces the check if you let it.
  • An agent loop without a step limit or tool timeouts: the runaway run, in production, with a real bill.
  • Trusting tool arguments. They are model output: validate with zod, and check what paths and URLs point at.
  • Throwing from a tool instead of returning is_error: the run dies on a problem the model could have fixed (the typo run fixed its own mistake).
  • await in a for loop over tool calls, running them one after another when Promise.all would run them together; and splitting their results over several messages instead of one.
  • Forgetting that the API is stateless, or never trimming: the bill grows with the square of the conversation's length.
  • Dropping the zod check because the API constrained the output: patterns and ranges are not enforced by the API (section 5).
  • Ignoring disconnects and write()'s return value in the server: paying for unread tokens and holding responses in memory.
  • Logging to stdout in a stdio MCP server: it corrupts the protocol stream.
  • Putting the API key in browser code, or in a logged request. Keys belong in server-side environment variables; this page's scripts unset them before running (API keys in general: Auth).
  • Catching errors by message text instead of instanceof Anthropic.RateLimitError and friends; and adding your own retry loop around an SDK that already retries.
  • Relying on a framework default you have not read: generateText's single step, allowedTools meaning "no approval needed" rather than "only these".
