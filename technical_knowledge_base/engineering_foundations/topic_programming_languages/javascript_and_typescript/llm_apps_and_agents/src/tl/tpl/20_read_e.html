9. Serving: stream to the browser, cancel when it leaves

A web app puts your server between the browser and the model: the browser calls /ask, your server calls the model with the API key (which must never reach the browser, nor a logged request), and forwards each text piece as an SSE event. Two things go wrong in production that never show in a demo.

Cancellation. Users close tabs. If your server does not notice, the model keeps generating, and you pay for every token nobody will read. In Node the response's close event fires when the client goes away; hand an AbortController's signal to the SDK call and abort it there. The SDK then closes the upstream HTTP request and throws APIUserAbortError, which you catch. Predict before stepping: with nobody aborting, how many of the 114 events does the model still generate?

Cancelling a stream on the wire (what each side sees, where the provider stops billing) is on {{Streaming and real-time|n:3c65c17b0d0d812daa9fdb38719fc82b}}; AbortController itself on the event-loop page.

Backpressure. res.write() returns false when the bytes cannot leave as fast as you write them (a slow phone, a congested link); Node then keeps the rest in memory, so a server that ignores the false can hold the whole response in RAM for every slow client at once. The fix is one line: when write returns false, await once(res, "drain") before writing more.

[[predictc:h2_backpressure|about 2 MB goes to a client that pauses for 300 ms. How much does the server hold in memory at its peak when it ignores write()'s return value, and when it awaits "drain"?]]

The 64 KiB plateau is Node's default stream buffer size (highWaterMark, 65,536 bytes; printed by stream.getDefaultHighWaterMark(false) on Node 24.21.0). With LLM tokens arriving at tens per second the risk is small for one stream, but a proxy that relays many streams, or a server that forwards a fast upstream to slow clients, needs it. stream.pipeline() and .pipe() handle backpressure for you when both ends are Node streams.

The browser side is the same fetch and stream-reading code as the Node "browser" in h1_serve.ts (it runs unchanged in a browser); EventSource cannot send a POST body or custom headers, so fetch is the usual choice for a chat (its limits: {{Streaming and real-time|n:3c65c17b0d0d812daa9fdb38719fc82b}}). Two habits start the measuring: log every model call as one JSON line (case, status, latency, messages sent, why it stopped, tokens in and out), and keep a fixed set of cases with checks written in code, run on every change of prompt, model or tool. Before you ship: the twelve mistakes this page's runs show
  • Reading content[0].text without checking the block type or stop_reason: the first block may be thinking or tool_use, and a max_tokens stop means the text is cut off. TypeScript's narrowing forces the check if you let it.
  • An agent loop without a step limit or tool timeouts: the runaway run, in production, with a real bill.
  • Trusting tool arguments. They are model output: validate with zod, and check what paths and URLs point at.
  • Throwing from a tool instead of returning is_error: the run dies on a problem the model could have fixed (the typo run fixed its own mistake).
  • await in a for loop over tool calls, running them one after another when Promise.all would run them together; and splitting their results over several messages instead of one.
  • Forgetting that the API is stateless, or never trimming: the bill grows with the square of the conversation's length.
  • Dropping the zod check because the API constrained the output: patterns and ranges are not enforced by the API (section 5).
  • Ignoring disconnects and write()'s return value in the server: paying for unread tokens and holding responses in memory.
  • Logging to stdout in a stdio MCP server: it corrupts the protocol stream.
  • Putting the API key in browser code, or in a logged request. Keys belong in server-side environment variables; this page's scripts unset them before running (API keys in general: {{Auth|n:3c65c17b0d0d817692dcc8ebd59b5c2b}}).
  • Catching errors by message text instead of instanceof Anthropic.RateLimitError and friends; and adding your own retry loop around an SDK that already retries.
  • Relying on a framework default you have not read: generateText's single step, allowedTools meaning "no approval needed" rather than "only these".
