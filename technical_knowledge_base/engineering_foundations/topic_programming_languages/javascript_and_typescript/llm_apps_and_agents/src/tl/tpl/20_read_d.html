5. Structured output: one zod schema, three jobs

Often you want data, not prose: {"user": "u0029", "tokens": 9491, "share_pct": 21.2}. One zod schema (zod from zero: section 7 of {{the TypeScript page|n:4055c17b0d0d81519278df19753ab5ec}}) does three jobs:

  1. Ask with a schema. output_config.format sends a JSON Schema and the API constrains the model to produce matching JSON (Anthropic calls this structured outputs; docs). zodOutputFormat(schema) converts the zod schema.
  2. Check what came back. client.messages.parse() runs the zod schema on the reply and puts the typed result in parsed_output.
  3. Get the type for free. z.infer<typeof Heaviest> is the TypeScript type, so the rest of your program is checked against the same definition.
[[outc:d1_structured]]
Found by running it: not every rule reaches the API
Look at the output_config sent line. The SDK sent user as a plain string and moved the regular expression into the field's description ("{pattern: \"^u\\\\d{4}$\"}"); the same happened to minimum/maximum on the numbers. So the API's constraint guarantees the JSON's shape (fields, types, no extra keys), but rules like a pattern or a range are only hinted to the model and enforced afterwards, by zod, in parse(). That is why case 2 ends in an error raised by the SDK rather than a wrong value in your program. Keep the zod check even when the API constrains output.

With OpenAI the equivalent is zodTextFormat(schema, name) in text.format with client.responses.parse() (from openai/helpers/zod, 7.28.0). With any other provider, or a model without constrained decoding: ask for JSON in the prompt, JSON.parse, then safeParse; on failure, send the zod error message back to the model and ask again, once or twice (the error text, case 3 above, is written for exactly that). How a server forces valid JSON in the first place (constrained decoding) is on {{Sampling and decoding|n:3c65c17b0d0d8115bafcda29a2c7086e}}; how agent libraries send the schema, validate and retry is on {{Typed agent libraries|n:3f15c17b0d0d819fba89f9ec88feb859}}.

An alternative you will see in older code: defining a tool whose input schema is the output you want and forcing the model to call it. On Claude Sonnet 5.5 and Opus 5.5, forcing a specific tool (tool_choice any or tool) is rejected with a 400 (Sonnet 5.5 migration guide), so use structured outputs instead.

6. Conversation state: you resend everything

The Messages API keeps no memory between requests. The conversation is an array in your program; each turn you append the user's message, send the whole array, and append the reply.

[[predictc:e1_state|the first call says "My name is Khalid." and a second, separate call asks "What is my name?". What does the second call answer? Then, in the kept history, how does the input grow over six turns?]]

Each request carries every turn before it, so the input climbs every turn

[[gen:state]]

Because each request repeats everything before it, the total input billed grows with the square of the number of turns: the six turns billed 636 estimated input tokens for a conversation whose final request was 219. Three tools fight that: prompt caching (mark the stable prefix with cache_control; later requests that start with the same bytes are billed at a fraction, and any change early in the prefix, such as a timestamp in the system prompt, silently defeats it; prices and economics across providers are on {{Caching|n:3cd5c17b0d0d817ebd6ccadd4750c23a}}); compaction or trimming (summarise or drop old turns; Anthropic offers server-side compaction as a beta); and server-side state (OpenAI's Responses API keeps the conversation if you pass previous_response_id, conversation state guide; you are still billed for those input tokens, you just do not send them). Where the array lives is an application decision: in memory for a script, a database row per conversation for a web app ({{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}).

7. Higher-level libraries: the Vercel AI SDK and the Claude Agent SDK

The Vercel AI SDK (package ai, version 7) is one TypeScript API over many providers: generateText, streamText, tools with zod schemas, and a loop controlled by stopWhen. You swap anthropic("claude-sonnet-5-5") for openai("gpt-5.5") and the rest stays; its React hooks and stream helpers for web UIs are why front-end teams use it.

[[predictc:f1_aisdk|the first generateText call passes tools but no stopWhen. Does it run the tools and answer, or stop early?]]
A default that bites
In AI SDK 7, generateText and streamText default to stopWhen: isStepCount(1) (the type definitions in ai 7.0.127 say @default isStepCount(1)): one model call. With tools, the first step is usually a tool call, so the result is the model's preamble and finishReason: "tool-calls", not an answer. Pass stopWhen: isStepCount(n) (also exported as stepCountIs). Its ToolLoopAgent class defaults to 20 steps.

The Claude Agent SDK (@anthropic-ai/claude-agent-sdk) is not a thinner client; it is Claude Code as a library, and its own page is {{Claude Agent SDK|n:3c65c17b0d0d813b960fd9857118fbd2}}. What the TypeScript run here adds: query() starts a native binary shipped per platform (here @anthropic-ai/claude-agent-sdk-darwin-arm64), and one tiny question, pointed at the mock through ANTHROPIC_BASE_URL, sent one model request of about 59 KB carrying 20 tool definitions and Claude Code's system prompt (plus a GET /api/hello). That is the trade: a capable coding agent for free, paid for in context on every call. And allowedTools is the list of tools that run without asking for permission, not the list the model sees; the SDK's own documentation (in sdk.d.ts) says to restrict the available tools with the tools option.
