1. One call, read as data

In Python you would write client = anthropic.Anthropic() and client.messages.create(...). The TypeScript SDK is the same API with one difference you feel at once: create returns a promise, so you await it; top-level await works because the file is an ES module. Every SDK takes a base URL; in production you leave it alone (it defaults to https://api.anthropic.com, or reads ANTHROPIC_BASE_URL), and here every script passes the address of mock_model.ts, started on a free local port.

[[outc:a1_first_call]]
  • content is an array of blocks, each with a type: text, tool_use, thinking and others. The response type is a discriminated union, so TypeScript makes you narrow on block.type === "text" before you may read block.text (narrowing: section 4 of {{the TypeScript page|n:4055c17b0d0d81519278df19753ab5ec}}): msg.content[0].text is a type error, and it should be, because the first block is not always text.
  • stop_reason says why the model stopped: end_turn (finished), max_tokens (cut off), tool_use (wants a tool), stop_sequence, pause_turn, refusal and model_context_window_exceeded (the full list from the SDK's StopReason type in 0.131.0). Check it on every response.
  • usage counts input and output tokens: the bill. Real responses also carry cache counts (cache_read_input_tokens, cache_creation_input_tokens).
  • The wire shows what the SDK added for you: the anthropic-version: 2023-06-01 header (the API's version, not the model's), its retry counter, and its timeout (600 s).

The OpenAI SDK has the same shape of code with different names. Its current API is Responses (client.responses.create); the older Chat Completions API still exists.

The same trick is how you should test your own LLM code: a mock server makes tests fast, free, deterministic, and able to produce failures (a 429, a timeout, a malformed tool call) on demand (testing practice in general: {{Testing and quality|n:3c65c17b0d0d81548848e2ebdd2f63ee}}).

2. When the call fails: the SDK already retries

A model API fails in ordinary ways: rate limits (HTTP 429), overload (529 and other 5xx), a slow or dead connection, or a request you got wrong (400). Read from the SDK's source (client.js, 0.131.0): it retries 2 times by default (maxRetries), on 408, 409, 429, every 5xx, and connection errors; it waits with exponential backoff or for the server's retry-after / retry-after-ms header; and its timeout is 10 minutes per attempt (in milliseconds in TypeScript: timeout: 600_000). A 400 is never retried: retrying a wrong request cannot fix it.

Two lessons sit in the last row. First, timeouts are retried, so the worst case is about timeout × (maxRetries + 1) plus backoff (here two 300 ms attempts plus about 450 ms of backoff: about one second from the first attempt to the error). Second, catch the specific error classes (RateLimitError, BadRequestError, APIConnectionTimeoutError, all subclasses of Anthropic.APIError) with instanceof, never by matching message strings. In Python the same classes exist with the same names (anthropic.RateLimitError); TypeScript's catch (e) gives e the type unknown, so instanceof is also how you get a typed error back. And do not wrap the SDK in your own retry loop: its 3 attempts inside your 3 attempts is 9 requests.
