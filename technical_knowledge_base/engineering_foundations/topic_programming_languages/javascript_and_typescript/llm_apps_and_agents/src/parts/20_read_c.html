3. Streaming: the events, in two wire formats

Streaming sends each piece of the answer as it is produced, as server-sent events on one HTTP response that stays open. The SSE format itself is owned by {{Streaming and real-time|n:3c65c17b0d0d812daa9fdb38719fc82b}}, and parsing raw SSE bytes safely (chunks split events and even UTF-8 characters) by {{JavaScript: the event loop, promises and streams|n:4055c17b0d0d81fe857de8b34db109ea}}; the SDK does that parsing for you. What remains is knowing the events. Predict before stepping: in which event does the final stop_reason arrive?

The same answer as Anthropic and OpenAI events, and a tool call's arguments arriving as broken JSON

Every frame is one the mock really sent in the recorded runs of b1_stream.ts and b2_stream_openai.ts (same answer text in both formats); the "assembled so far" column is computed in your browser from those frames, the way the SDK assembles them. The SDK gives three levels. create({ ..., stream: true }) returns an async iterable of the raw events, already parsed (it drops the ping keep-alive: 23 events arrive, the wire carried 24). messages.stream() is the helper: .on("text", f) for each text piece and await finalMessage() for the assembled Message, identical to what a non-streaming call returns. And for tool calls, the arguments stream as partial JSON (input_json_delta): fragments like "t.jsonl\",\"to" that are not JSON on their own; the helper re-parses the snapshot after each one.

When not to stream: a batch job, or anything that needs the whole answer before acting (a classifier, a JSON extraction you validate as a whole); then a plain create is simpler. 4. Tools and the agent loop, in TypeScript

You send a list of tools (a name, a description, a JSON Schema for the arguments). The model never runs anything: it stops with stop_reason: "tool_use" and a tool_use block; your code runs the function and sends the whole conversation back with a tool_result block of the same id; repeat until it answers. That loop plus tools is all an "agent" is; the loop itself, what a harness adds around it, and a lab that steps through real Claude Code runs are on {{Topic: agentic-harnesses|n:3c65c17b0d0d81d881a8fe98b4cff7bb}} (its Loop lab). This section is what the loop looks like in TypeScript, and the guards that make it safe:

Step limit
A model can ask for tools forever. Stop after maxSteps model calls and report it.
Timeout per tool
AbortSignal.timeout(500) gives every tool a deadline; a stuck tool becomes an error result, not a hung agent.
Validate the input
The arguments are the model's JSON: untrusted. safeParse them with the same zod schema that produced the JSON Schema; for paths, URLs or shell commands also check what they point at (a valid string can still be ../../etc/passwd).
Errors go to the model
A failed tool returns is_error: true with a message the model can act on. Throwing would kill the run.
Run calls concurrently
One turn may ask for several tools. Promise.all runs them together, and all results go back in one user message.
Meter the cost
Add up usage after every call; a loop multiplies the bill (every step resends everything).

c1_agent_loop.ts, lines 9-65
const PRICE = { in: 2, out: 10 };   // US$ per million tokens, claude-sonnet-5-5 (Anthropic pricing page, 2026-10-05)
const TASK = "Who are the 3 heaviest users in chat.jsonl, and what share of all tokens do they have? Add the team of the top two.";

const schema = (s: z.ZodType) => { const { $schema, ...rest } = z.toJSONSchema(s) as any; return rest as Anthropic.Tool.InputSchema; };
const tools: Anthropic.Tool[] = [
  { name: "count_tokens", description: "Count word tokens per user in a JSONL chat log; returns totals and the top users.", input_schema: schema(CountArgs) },
  { name: "user_profile", description: "Look up a user's team.", input_schema: schema(ProfileArgs) },
];

export async function runAgent(client: Anthropic, scenario: string, opts: { maxSteps?: number; toolTimeoutMs?: number; profileUrl: string }) {
  const { maxSteps = 5, toolTimeoutMs = 500 } = opts;
  const messages: Anthropic.MessageParam[] = [{ role: "user", content: TASK }];
  const steps: any[] = []; const tot = { in: 0, out: 0, usd: 0 };

  type Result = Anthropic.ToolResultBlockParam & { ms: number };
  async function runTool(call: Anthropic.ToolUseBlock): Promise<Result> {
    const t0 = performance.now();
    const done = (content: string, is_error = false): Result =>
      ({ type: "tool_result" as const, tool_use_id: call.id, content, ...(is_error ? { is_error } : {}), ms: Math.round(performance.now() - t0) });
    try {
      const signal = AbortSignal.timeout(toolTimeoutMs);             // every tool gets a deadline
      if (call.name === "count_tokens") {
        const args = CountArgs.safeParse(call.input);                 // the model's JSON is untrusted input
        if (!args.success) return done(`invalid input: ${z.prettifyError(args.error)}`, true);
        return done(JSON.stringify(await countTokens(args.data)));
      }
      if (call.name === "user_profile") {
        const args = ProfileArgs.safeParse(call.input);
        if (!args.success) return done(`invalid input: ${z.prettifyError(args.error)}`, true);
        return done(await userProfile(opts.profileUrl, args.data, signal));
      }
      return done(`unknown tool ${call.name}`, true);
    } catch (e: any) {                                                  // errors go back to the model, not up the stack
      const why = e.name === "TimeoutError" ? `timed out after ${toolTimeoutMs} ms` : e.code === "ENOENT" ? `cannot open ${(call.input as any).path}: ENOENT` : String(e);
      return done(why, true);
    }
  }

  for (let step = 1; step <= maxSteps; step++) {
    const msg = await client.messages.create({ model: "claude-sonnet-5-5", max_tokens: 2048, tools, messages },
      { headers: { "x-mock-scenario": scenario } });
    tot.in += msg.usage.input_tokens; tot.out += msg.usage.output_tokens;
    tot.usd = (tot.in * PRICE.in + tot.out * PRICE.out) / 1e6;
    messages.push({ role: "assistant", content: msg.content });
    const calls = msg.content.filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use");
    const t0 = performance.now();
    const results = await Promise.all(calls.map(runTool));            // several calls in one turn run concurrently
    const wall = Math.round(performance.now() - t0);
    steps.push({ step, sent: messages.length - 1, content: msg.content, stop: msg.stop_reason, usage: msg.usage, results, wall, tot: { ...tot } });
    if (msg.stop_reason !== "tool_use") {
      const answer = msg.content.filter(b => b.type === "text").map(b => b.text).join(" ");
      return { scenario, outcome: "answered", answer, steps, tot, messages: messages.length };
    }
    messages.push({ role: "user", content: results.map(({ ms, ...r }) => r) });   // all results in ONE user message
  }
  return { scenario, outcome: `stopped: hit maxSteps=${maxSteps}`, answer: null, steps, tot, messages: messages.length };
}

The timeout run's step 2 took about 500 ms, not 1,000: the two lookups waited at the same time, because Promise.all started both before awaiting either. A for loop with await inside would have taken twice as long (one at a time against all at once is on the event-loop page). And because runTool catches every error and returns it as a result, Promise.all can never reject halfway and lose the other results. A real request with tools also carries a hidden tool-use system prompt (286 tokens on Sonnet 5.5, same pricing page).

From Python
The loop is line for line what you would write in Python. The differences are TypeScript's: msg.content.filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use") is a type guard (a function whose return type b is T tells the compiler what passed the filter), and the SDK's types (Anthropic.MessageParam, Anthropic.ToolResultBlockParam) make a malformed message a compile error instead of a 400 at run time.

The tool runner: the same loop, written by the SDK. client.beta.messages.toolRunner (beta in 0.131.0) takes tools made by betaZodTool: a zod schema and a run function each. The runner sends the schema, validates the model's arguments against it before calling run, sends the results back, and stops when the model answers or after max_iterations. It made the same three model calls as the happy run above. Use it for most custom-tool agents (less code, validation built in); write the loop by hand when you need control it does not give, such as your own cost cut-off, a per-step log format, or handling of pause_turn (the SDK's documentation notes the runner does not resume a paused server-tool turn by itself). Writing the loop once by hand is what keeps the runner from being magic.
