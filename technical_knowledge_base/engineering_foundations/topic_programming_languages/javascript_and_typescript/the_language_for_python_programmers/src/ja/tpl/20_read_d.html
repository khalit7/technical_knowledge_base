4. Classes and prototypes

class looks like Python's: a constructor is __init__, this is self (implicit, never a parameter), extends and super work as expected, get defines a property. Differences: fields can be declared in the body; #name fields are truly private, enforced by the parser (Python's _name is a convention); there is single inheritance only; and there is no operator overloading (no __eq__, __add__, __len__).

Under the syntax, there are no classes at all: every object has a prototype, another object where missing properties are looked up, and so on up a chain ending at Object.prototype (the hero figure at the top draws it). A class is a function whose prototype object holds the methods; new makes an object whose prototype is that object. Python's attribute lookup through the MRO is the same idea with more rules ({{Python: the data model and protocols|n:4055c17b0d0d816a8705e4d3f20b3da7}}). Knowing the chain explains instanceof, method sharing, and why changing a prototype changes every instance; Object.create(proto) makes an object with a chosen prototype and no class at all.

Depth: the few hooks instead of dunder methods, and Proxy

The few hooks JavaScript offers instead of dunder methods are keyed by well-known symbols: Symbol.iterator (__iter__), Symbol.asyncIterator (__aiter__), Symbol.toPrimitive (roughly __int__ and __str__), plus toString and toJSON. With no __eq__ or __add__, == on two objects is identity and + goes through toPrimitive.

[[predict:e3_dunders]]

For the rest of Python's attribute hooks (__getattr__, __setattr__), JavaScript has Proxy: a wrapper that intercepts reads, writes and more on any object. Libraries use it for reactivity, mocks and lazy clients. Reach for it rarely: it is slower than plain objects and surprising to readers.

5. Modules: ES modules and CommonJS

JavaScript has two module systems, and Node runs both. ES modules (ESM, the standard since 2015): import and export, loaded and linked before any code runs, asynchronous, with top-level await. CommonJS (CJS, Node's original): require() and module.exports, synchronous, still in many packages. Python has one system; its import is closest to require (synchronous, runs the module once, caches it).

Node picks the system per file, and the two meet in one place that can fail

.mjsalways an ES module
.cjsalways CommonJS
.jsthe "type" field of the nearest package.json: "module" gives ESM, missing or "commonjs" gives CJS
ESM import of CJSworks: module.exports arrives as the default export
CJS require() of ESMworks since Node 22.12 and 20.19, without a flag; stable in 25.4
unless the ESM graph uses top-level awaitERR_REQUIRE_ASYNC_MODULE, because require must finish synchronously

In ESM, relative imports need the file extension, and require, __filename and __dirname do not exist (use import.meta.url, import.meta.filename, import.meta.dirname). A module's body runs once, however many times it is imported.

6. Errors

throw, try/catch/finally work like Python's raise, try/except/finally, with three differences. There is one catch per try, with no type filter: test e instanceof X or e.code inside it and rethrow what you do not handle. Anything can be thrown, but only Error objects carry a stack, so always throw Error or a subclass. And chaining is explicit: new Error(msg, { cause: e }) is Python's raise ... from e.

[[outc:g1_errors]]

An uncaught error prints the stack (innermost call first, the reverse of a Python traceback) and ends the process with exit code 1. Node errors from the system carry a stable code (ENOENT, ECONNREFUSED, ERR_REQUIRE_ASYNC_MODULE): match on the code, not on the message text.

[[outc:g2_uncaught]]

Errors in asynchronous code are the hard part: a rejected promise that nobody awaits or catches does not reach any try, and Node ends the process. The sibling {{JavaScript: the event loop, promises and streams|n:4055c17b0d0d81fe857de8b34db109ea}} shows it (section 4).

7. Iteration: iterators and generators

for (const x of xs) is Python's for x in xs: it works on anything iterable (arrays, strings, maps, sets, generators). for...in is a different, older loop over an object's keys as strings, including inherited ones; it is almost never what you want on an array. The iterator protocol is Python's in disguise: xs[Symbol.iterator]() is iter(xs), and it.next() returns { value, done } instead of raising StopIteration.

[[predict:h1_iter]]

function* defines a generator, exactly Python's function-with-yield: lazy, paused between values, able to describe infinite sequences. Since Node 22 (ES2025 "iterator helpers"), iterators also have lazy map, filter, take, drop, flatMap and toArray methods, which make generator pipelines read like method chains (the last line below).
