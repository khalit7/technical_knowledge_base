The idea in one screen

In C++ you decide where each object lives and when it dies, and the compiler trusts you: each file is compiled separately and the pieces are linked, and a broken rule is undefined behaviour, not an error. Python decides both things for you, which is why C++ is fast where you take care and silently wrong where you do not.

One vector of three floats: in C++ a 24-byte owner on the stack and 12 bytes on the heap, freed at the closing brace; in Python a name, a counted list and three float objects

C++: { std::vector<float> v{1, 2, 3}; ... }
Python: v = [1.0, 2.0, 3.0]

The same three numbers cost 12 bytes in C++ and 88 + 3 × 24 = 160 bytes in Python, and only C++ lets you point at the line where they are freed. Every rule on these pages follows from owning that moment: who frees, when, and what if two owners free the same bytes (the double free, section 2).

You need: everyday Python. Nothing about C++ beyond having seen its syntax; each child page names what it assumes from this one.

translation unit
one .cpp file after the preprocessor has pasted in its headers; the compiler sees only this
object file, symbol
a compiled translation unit (.o) and the names it defines or needs
linker
joins object files and libraries into one program, one definition per symbol
ODR
the one definition rule: one definition of each function in the whole program
undefined behaviour (UB)
an operation the standard gives no meaning; the optimiser assumes it never happens
sanitizer
a compiler mode that adds run-time checks for one family of UB (ASan, UBSan, TSan)
ABI
the binary contract (layouts, calling convention, names) that compiled pieces must share

Six ideas, and where each is taught

C++ is the language underneath most of the ML stack you use from Python: PyTorch's core, llama.cpp, ONNX Runtime, the CUDA kernels. The whole language follows from one decision: C++ gives you the machine's own representation of data and makes you responsible for how long each piece of it lives. Python decides both for you. Six things the runs showed

Every output, compiler error, sanitizer report and number on these pages comes from a real run on an Apple M1 Pro (2026-10-05, reruns 2026-10-26; LLVM clang 23 for the sanitizers, Apple clang 17 otherwise; llama.cpp pinned at commit 8e16421).

FindingWhere it is shown
The optimiser changes what buggy code does: a double free crashed at -O0 and vanished at -O2; a data race lost updates at -O0 and gave the right answer at -O2 by luck. Sanitizers catch both.The UB gallery, here
An exception is free until thrown: throwing and catching one cost about 4.8 µs; returning a std::expected about 1 ns.{{Classes, templates and the standard library|n:4055c17b0d0d818a9509f6035089a7e1}}, section 6
Summing a matrix by columns was 52 to 56 times slower than by rows: same arithmetic, different cache behaviour.{{The machine underneath|n:4055c17b0d0d811fa947ee576a97a516}}, section 2
Two threads writing counters on the same cache line ran 21 to 22 times slower; padding to 64 bytes still left about 2x, because this M1's lines are 128 bytes.{{The machine underneath|n:4055c17b0d0d811fa947ee576a97a516}}, section 8
On Apple Silicon with the default build, the ggml_vec_dot_* kernels most guides tell you to read run zero times: weights are repacked at load and 4x4 gemv/gemm kernels do every product.{{Reading llama.cpp|n:4055c17b0d0d8150a5effbb5a667dd9d}}, section 10
