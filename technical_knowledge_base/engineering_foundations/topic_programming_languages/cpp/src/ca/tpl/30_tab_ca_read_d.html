9. The standard library you will actually use

The standard library ("the STL") is the C++ equivalent of Python's built-ins plus collections and itertools. On macOS it is LLVM's libc++; on Linux usually GCC's libstdc++; on Windows Microsoft's STL. The interfaces are standard; sizes, growth factors and string buffers below are libc++'s, measured.

std::vector: the default container

A growable array, like a Python list, except that it holds the elements themselves, contiguously, not pointers to objects. Use it unless you have measured a reason not to. Growth is geometric, so push_back is cheap on average:

[[code:lang/vector_growth.cpp]] [[pr:l_vector_growth|at which sizes does the capacity change?]]

libc++ doubles (the factor is implementation-defined; do not rely on it). Each change of capacity is a new buffer: every element moves, and every pointer, reference and iterator into the old buffer now dangles. If you know the final size, call reserve(n) first: one allocation, no moves (the {{Object lifetimes|#t-ca-life}} tab's "reserve" scenario).

std::string and std::string_view

std::string owns a growable byte buffer. Short strings are stored inside the 24-byte object itself (the small-string optimisation), so they need no heap allocation; std::string_view is a pointer and a length into characters owned by someone else, so passing one never copies. C++ strings are bytes: size() counts UTF-8 bytes, not characters.

[[code:lang/strings.cpp]] [[out:l_strings]]

A string_view (and a std::span, the same idea for any contiguous elements) is the right parameter type for "read some text" or "read some numbers", and the wrong type to store: it does not keep its characters alive. Initialise one from a temporary string and it dangles at the semicolon; clang warns, and the {{UB gallery|#t-ca-ub}} shows the result.

Maps, spans and algorithms

[[code:lang/containers.cpp]] [[pr:l_containers|what does per_user["u0099"] do to the map, and in what order are the rows printed?]]
  • std::unordered_map is a hash table like dict, but unordered (there is no insertion order) and its [] inserts a default value when the key is missing, so it cannot be used on a const map. Use contains or find to look without inserting. std::map is a sorted tree.
  • std::ranges::sort(rows, cmp) sorts with your comparison; the lambda (section 10) gives the root page's tie-break: count descending, then user id ascending.
  • auto& [user, n] is a structured binding: tuple unpacking.
  • One sum(std::span<const long>) accepted a vector, a plain array and a slice of the vector, with no copies.

Ranges: lazy pipelines

C++20 ranges compose lazily, like Python generators: views::filter, views::transform, views::take build a pipeline that computes nothing until a loop pulls from it. The prints inside the lambdas show the order of evaluation:

[[code:lang/ranges.cpp]] [[pr:l_ranges|which numbers get filtered and squared before the loop stops?]]

Only what the loop needed was computed (31 was filtered but never squared: taking the second element advanced the filter to find a third before take said stop; 5 and 18 were never touched). C++23's std::ranges::to<std::vector>() collects a pipeline into a container, like list(gen). A view does not own its data, so a view of a temporary container dangles, just as a string_view does.

Defaultsvector, string, unordered_map; string_view and span as parameters; algorithms over hand-written loops.
What it costsEvery container owns heap memory; views and spans own nothing and can dangle.
Common mistakesKeeping a reference or iterator across a push_back; map[key] to test membership; std::list (a linked list, almost always slower than vector).

10. Lambdas

A lambda is an inline function, like Python's lambda but with statements allowed. The part in square brackets says which outside variables it captures and how: [x] copies x when the lambda is created; [&x] refers to the variable itself; [=] and [&] capture everything used, by copy or by reference.

[[code:lang/lambdas.cpp]] [[pr:l_lambdas|by_value(50) and by_ref(50) after threshold becomes 100?]]

Under the hood a lambda is an object of a class the compiler writes, with the captures as members and operator() as the body; its size is the size of its captures. Python closures always capture variables by reference and keep them alive; a C++ reference capture does not keep anything alive, so a lambda that outlives the function it was made in (returned, stored, or given to a thread) must capture by value. std::function can hold any callable with a given signature, at the price of a type-erased call and possibly a heap allocation; templates and auto parameters avoid both.

Problem it solvesComparators, callbacks and small helpers written where they are used.
What it costsNothing for a lambda passed to a template; a std::function costs an indirect call.
Common mistakes[&] in a lambda that escapes its scope (the gallery's "dangling capture" case); capturing this and outliving the object.

11. Error handling: exceptions, optional, expected

C++ has three ways to say "this did not work", and real code uses all three:

[[code:lang/errors.cpp]] [[out:l_errors]]
  • Exceptions work like Python's: throw, try/catch, unwinding with destructors (section 4). Use them for errors the immediate caller cannot handle (a missing config file, out of memory).
  • std::optional<T> (C++17) is "a T or nothing", like returning None, with no reason attached.
  • std::expected<T, E> (C++23) is "a T or an error E", like Rust's Result. The caller must look; transform and and_then chain steps that run only on success. Use it for failures that are part of normal operation (parsing user input, a malformed JSONL line).

What each costs, measured with the same tiny function written both ways (10 million successful calls; 100,000 failing calls):

[[out:t_throw]]

On the success path both are about a nanosecond: compilers implement exceptions with tables consulted only when something is thrown ("zero-cost" exceptions, which still cost binary size). Throwing and catching took about [[g:t_throw|throw\+catch (\d+) ns]] ns, thousands of times more than returning an expected. So: exceptions for rare failures, expected or optional where failure is common. Some codebases (game engines, parts of Google's, many embedded ones) compile with exceptions turned off; ggml, the C core under llama.cpp, reports errors with return values and assertions, since C has no exceptions.

Rule of thumbExceptional and far away: throw. Expected and handled by the caller: std::expected. "Not found": std::optional.
noexceptMark functions that never throw, above all move constructors and destructors (section 6).
Common mistakesExceptions as control flow in a hot loop; throwing from a destructor; ignoring an expected (add [[nodiscard]] to the function).
