12. Undefined behaviour

The C++ standard lists operations whose result it does not define: reading outside an array, reading freed memory, overflowing a signed integer, reading an uninitialised variable, two threads writing the same variable without synchronisation, falling off the end of a function that should return a value, and others. Such a program has undefined behaviour (UB): not "a wrong answer" but no meaning at all. The compiler is allowed to assume UB never happens, and its optimiser uses that assumption to delete checks and simplify code. So a program with UB can work at -O0 and break at -O2, or work today and break after a compiler upgrade. This is the deepest difference from Python, where every one of these is either impossible or an exception.

Your defences

  1. Warnings: -Wall -Wextra always; -Werror in CI. They caught the uninitialised read, the dangling string_view and the missing return above.
  2. Sanitizers in tests: -fsanitize=address (ASan: out of bounds, use after free, double free), -fsanitize=undefined (UBSan: overflow, bad shifts, missing return), -fsanitize=thread (TSan: data races). They slow the program down (about 2 times for ASan per its {{documentation|https://clang.llvm.org/docs/AddressSanitizer.html}}, 5 to 15 times for TSan per {{its documentation|https://clang.llvm.org/docs/ThreadSanitizer.html}}), so they run in tests, not production. On this Mac Apple's own ASan did not start (the root's Toolchain atlas records it); LLVM clang 23's worked, and every sanitizer report on this page is from it.
  3. A hardened standard library: libc++ can check v[i], front(), string_view bounds and more, turning silent UB into a trap ({{libc++ hardening|https://libcxx.llvm.org/Hardening.html}}). -D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST is meant for production (cheap checks, a silent trap); the _DEBUG mode prints why:

  1. Initialise everything, or let the compiler do it: -ftrivial-auto-var-init=zero made the uninitialised example print "not seen" at -O2. The honest summary
No tool catches all UB, and sanitizers find only what your tests execute. C++ makes you responsible for memory safety; Rust moves most of this list into compile errors (the root page's section 10, and the {{Rust page|n:3c65c17b0d0d8156bed9ead8a22f33b0}}).

13. Libraries: header-only, static, dynamic, and getting them

Python has pip install and wheels. C++ has no official package manager, and the reason is technical: a compiled C++ library works with your program only if it was built with a compatible compiler, standard library and flags (the same ABI, application binary interface). A mismatch gives link errors or, worse, silent memory corruption. Shipping prebuilt binaries is therefore much harder than in Python, and the community's historical answer was "build it yourself" or "copy the source in". Three ways a library reaches your program:

  • Header-only: the whole library is headers (all inline functions and templates), so there is nothing to build or link: nlohmann/json, Catch2, Eigen. It sidesteps packaging and ABI, and costs compile time in every file that includes it.
  • Static library (.a, .lib): object files copied into your executable at link time, like libtokens.a in section 1. One self-contained binary; every program carries its own copy.
  • Dynamic (shared) library (.dylib, .so, .dll): loaded when the program starts. Smaller binaries and shared updates, but the library must be present, at a compatible version, on the machine that runs it. Even the small program from section 1 depends on two:
