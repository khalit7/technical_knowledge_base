9. The roofline: compute-bound or memory-bound?

Every kernel needs two resources: arithmetic and bytes from memory. The roofline model ({{Williams, Waterman and Patterson, 2009|https://dl.acm.org/doi/10.1145/1498765.1498785}}) asks which one runs out first. Define the kernel's arithmetic intensity I as floating-point operations per byte moved from memory. Then

attainable FLOP/s = min( peak FLOP/s , I × bandwidth )
I
FLOPs per byte read from DRAM (a multiply-add counts as 2 FLOPs)
peak
the core's or chip's maximum arithmetic rate
bandwidth
bytes per second the memory system delivers

Below the ridge point I = peak / bandwidth, a kernel is memory-bound: a faster processor would not help, only fewer bytes would. Above it, it is compute-bound. The inputs, measured here (roof.cpp, compiled with -O3 -ffast-math; three runs each):

The peak loop runs 24 independent fmla.4s chains so that all four floating-point units stay busy (4 units x 4 lanes x 2 FLOPs = 32 FLOPs per cycle, about 102 GFLOP/s at 3.2 GHz; measured ). A first version with 12 chains of the form a = y + a * x reached only 64 GFLOP/s: the compiler had to add a register copy before every fmla, because fmla overwrites its accumulator. The bandwidth row is reading a 512 MB array once: one core reaches about half of the chip's 200 GB/s, all eight about GB/s (the GPU shares the rest).

The matrix-vector product is LLM decoding. Generating one token multiplies every weight matrix by one vector: each weight is read once and used for one multiply-add. In fp32 that is 2 FLOPs per 4 bytes, I = 0.5, far left of the ridge: the bound is 0.5 x bandwidth, and the measured matvec sits right on it. So decoding speed is set by bytes: tokens per second can be at most bandwidth / bytes of weights. Illustrative (not measured): an 8-billion-parameter model in 16-bit weights is 16 GB, so at GB/s this laptop could produce at most about tokens per second however fast its arithmetic; in llama.cpp's 4-bit q4_0 format (18 bytes per 32 weights, 4.5 bits each) it is 4.5 GB and the ceiling rises to about . This is why quantisation speeds up decoding and why batching many users' tokens together (which reuses each weight for many vectors, raising I) is the core of LLM serving; both belong to {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} and the {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}} page.

The matrix-matrix product is compute-bound (I about 85 FLOPs per byte for 512 x 512 matrices read once), yet the simple tiled loop reached only about a quarter of peak: it is limited by loads and stores inside the core, not by DRAM. Libraries close that gap with register blocking (keeping a small tile of the output in registers across the whole inner loop); that craft is the subject of {{Topic: cuda-and-gpu-programming|n:3c65c17b0d0d81c39f34d5e070d783c1}} on the GPU. The {{Roofline|#t-cb-roof}} tab plots these points and lets you move a batch-size slider to see decode cross the ridge.

10. Allocation: the hidden cost

Every new or make_unique calls the allocator (malloc), which must find free space, record it, and later free it; and each object lands somewhere else on the heap, so a container of pointers is a pointer chase (section 1). 11. Measuring: profilers, counters and lying microbenchmarks


Profile before optimising. A sampling profiler interrupts the program thousands of times a second and records where it was, so you see which functions take the time. On macOS that is Instruments' Time Profiler (GUI, or xcrun xctrace record --template 'Time Profiler' --launch -- ./prog on the command line); on Linux it is perf record -g ./prog then perf report, and perf stat for hardware counters ({{perf wiki|https://perf.wiki.kernel.org/index.php/Tutorial}}). Neither was run for this page: xctrace hung here even for xctrace version, the built-in sample tool could not attach in this session, and this is not a Linux machine. Treat those commands as reference.

Why microbenchmarks lie


    

  • The compiler deletes unused work. If a result is never used, the loop may vanish. Every benchmark here passes results to keep(), an empty asm volatile that forces the value to exist (bench.h); {{Google Benchmark|https://github.com/google/benchmark}} calls it benchmark::DoNotOptimize.
    • 

  • Caches are warm. A loop timed a million times on the same few KB runs from L1; the same code in a real program meets cold data. The NEON dot product ran about twice as fast in L1 as from DRAM, and a load from DRAM costs 100 times one from L1 (section 1).
    • 

  • The compiler sees your test data. A constant input can be folded away (section 5's formula).
    • 

  • Cores differ and clocks move. This chip has fast and slow cores; macOS cannot pin a thread to a core, so the benchmarks ask for the highest quality-of-service class and report the best of several runs.
    • 

  • The machine is busy. Every timing on this page says how many runs it took and how far they spread, and records the load average. Multi-threaded results spread most.
