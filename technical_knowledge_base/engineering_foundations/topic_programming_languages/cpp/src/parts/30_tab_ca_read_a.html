Part 1, the language: C++ in one screen

C++ is the language underneath most of the ML stack you use from Python: PyTorch's core, llama.cpp, ONNX Runtime, the CUDA kernels. This part teaches it from zero, using Python as the bridge. Every program on this page was compiled and run on this laptop (Apple M1 Pro, macOS 27), and every output, error and warning you see is the real one, recorded by a script (src/ca/run_all.sh).

The whole language follows from one decision: C++ gives you the machine's own representation of data and makes you responsible for how long each piece of it lives. Python decides both for you. Six ideas follow from that, and the sections below teach each one:

The rest (classes, templates, the standard library, lambdas, error handling) is the toolkit you write with; sections 7 to 11 teach it with the problem each feature solves, what it costs, and the usual mistakes. Sections 13 and 14 cover libraries and where the C++20, C++23 and C++26 standards stand in October 2026.

1. How a C++ program is built

In Python, python main.py reads your source and runs it; import tokens finds tokens.py at run time. C++ has no run-time import. Building a program is a separate step with three stages, and most confusing C++ errors come from not knowing which stage complained.

  1. Preprocessor. Lines starting with # are text commands. #include "tokens.h" pastes the whole file in, literally. The result is one long file per .cpp, called a translation unit.
  2. Compiler. Each translation unit is compiled separately into an object file (.o): machine code plus a table of the names (symbols) it defines and the ones it needs from elsewhere.
  3. Linker. Joins the object files and libraries into one executable, matching every needed symbol to exactly one definition.

Here is the running example from the root page's Rosetta tab, cut down to its token counter and split the way real projects are: a header (.h) that declares the function (its name and types: a promise), and a source file that defines it (the body).

tokens.h
// tokens.h: the declaration (a promise that a definition exists somewhere)
#pragma once
#include <string_view>
int count_tokens(std::string_view text);
main.cpp
// main.cpp: uses count_tokens; only sees the declaration
#include "tokens.h"
#include <cstdio>

int main() {
    std::printf("%d tokens\n", count_tokens("C++ is fun, x86_64 too"));
}
tokens.cpp
// tokens.cpp: the definition
#include "tokens.h"
#include <cctype>

int count_tokens(std::string_view text) {
    int n = 0;
    bool inside = false;
    for (unsigned char c : text) {
        bool tok = std::isalnum(c) && c < 128;
        if (tok && !inside) n += 1;
        inside = tok;
    }
    return n;
}

std::string_view is a read-only view of some characters (section 9); unsigned char c : text loops over the bytes. Stage 1, the preprocessor: how long is the translation unit the compiler actually sees for this 7-line main.cpp?

Every .cpp that includes a standard header recompiles that header from text, which is why C++ builds are slow and why C++20 added modules (section 14) to replace textual inclusion. main.o needs count_tokens (U) and tokens.o provides it (T). The compiler accepted main.cpp on the header's promise alone. Stage 3 is the linker's job, and if you forget to give it the definition, the error comes from the linker (ld), not the compiler:

6 tokens

The other classic link error is the opposite: two definitions. C++'s one definition rule (ODR) says a function may be defined once in the whole program. Put a function body in a header, include the header from two .cpp files, and each object file gets its own copy:

util.h
#pragma once
// A function DEFINED in a header, not marked inline
int twice(int x) { return 2 * x; }
b.cpp
#include "util.h"
int a();
int main() { return a() + twice(2) - 6; }
$ clang++ -std=c++20 -c a.cpp b.cpp && clang++ a.o b.o -o app
duplicate symbol 'twice(int)' in:
    odr/a.o
    odr/b.o
ld: 1 duplicate symbols
clang++: error: linker command failed with exit code 1 (use -v to see invocation)
[exit code 1]

The fix is the keyword inline, which tells the linker "identical copies of this may appear in several object files; keep one". Functions defined inside a class body, templates and constexpr functions are implicitly inline, which is why headers full of them link fine.

util_inline.h
#pragma once
// The fix: inline allows one identical definition per translation unit
inline int twice(int x) { return 2 * x; }
$ sed -i.bak "s/util.h/util_inline.h/" a.cpp b.cpp && clang++ -std=c++20 -c a.cpp b.cpp && clang++ a.o b.o -o app && ./app; echo "exit code $?"
exit code 0
Python bridge
A header is like a .pyi stub (types only) that every user pastes into their file. Python resolves names when the line runs; C++ resolves them at link time, so a missing or duplicated function is a build error, never a run-time NameError.

CMake: the build system

Typing compiler commands does not scale past a few files. CMake is the de facto standard build description: you list targets (executables, libraries) and their properties, and CMake generates the commands for a fast build tool such as Ninja. Three lines make a project:

CMakeLists.txt
cmake_minimum_required(VERSION 3.28)
project(hello LANGUAGES CXX)
add_executable(hello main.cpp)
$ cmake -S . -B build -G Ninja -DCMAKE_CXX_COMPILER=clang++ > /dev/null && cmake --build build && ./build/hello
[1/2] Building CXX object CMakeFiles/hello.dir/main.cpp.o
[2/2] Linking CXX executable hello
hello from CMake

A real project separates a library from the program that uses it. PUBLIC properties travel to every target that links the library; PRIVATE ones do not. This is the single most useful idea in CMake:

CMakeLists.txt
cmake_minimum_required(VERSION 3.28)
project(tokcount LANGUAGES CXX)

# A library target: compiled once, linked into anything that needs it
add_library(tokens src/tokens.cpp)
target_include_directories(tokens PUBLIC src)      # users of tokens see src/
target_compile_features(tokens PUBLIC cxx_std_20)  # and get C++20
target_compile_options(tokens PRIVATE -Wall -Wextra)

add_executable(tokcount src/main.cpp)
target_link_libraries(tokcount PRIVATE tokens)     # brings the include dir and C++20 along
$ cmake -S . -B build -G Ninja && cmake --build build --verbose
clang++  -Icmake2/src -std=gnu++20 -arch arm64 -o CMakeFiles/tokcount.dir/src/main.cpp.o -c cmake2/src/main.cpp
clang++  -Icmake2/src -std=gnu++20 -arch arm64 -Wall -Wextra -o CMakeFiles/tokens.dir/src/tokens.cpp.o -c cmake2/src/tokens.cpp
cmake -E rm -f libtokens.a && ar qc libtokens.a  CMakeFiles/tokens.dir/src/tokens.cpp.o && ranlib libtokens.a && cmake -E touch libtokens.a
clang++ -arch arm64 -Wl,-search_paths_first -Wl,-headerpad_max_install_names CMakeFiles/tokcount.dir/src/main.cpp.o -o tokcount  libtokens.a
$ ./build/tokcount
6 tokens

Read the generated commands: -Icmake2/src and -std=gnu++20 reached main.cpp because they are PUBLIC on tokens; -Wall -Wextra did not, because it is PRIVATE. The library became a static library libtokens.a (an archive of object files, made by ar) and was copied into the executable at link time. The payoff of separate compilation is incremental builds: editing a .cpp recompiles one file, editing a header recompiles everything that includes it.

$ touch src/tokens.cpp && cmake --build build
[1/3] Building CXX object CMakeFiles/tokens.dir/src/tokens.cpp.o
[2/3] Linking CXX static library libtokens.a
[3/3] Linking CXX executable tokcount
$ touch src/tokens.h && cmake --build build
[1/4] Building CXX object CMakeFiles/tokcount.dir/src/main.cpp.o
[2/4] Building CXX object CMakeFiles/tokens.dir/src/tokens.cpp.o
[3/4] Linking CXX static library libtokens.a
[4/4] Linking CXX executable tokcount
$ cmake --build build
ninja: no work to do.
Problem it solvesCompile each file once, in parallel, and rebuild only what changed.
What it costsHeaders are re-parsed in every file that includes them; you maintain declarations and definitions separately.
Common mistakesA definition in a header without inline; global flags instead of per-target properties; forgetting -std= (section 14).
