3. Data layout: size, alignment, padding, AoS and SoA

In C++ a struct is laid out in memory exactly as declared: fields one after another, in order. Two rules shape the result:

  • Alignment. Each type has an alignment (alignof): a 4-byte int32_t must start at an address divisible by 4, an 8-byte double or pointer at one divisible by 8. The processor loads aligned values in one go.
  • Padding. To satisfy alignment the compiler inserts unused bytes between fields, and at the end so that the next element of an array is aligned too. sizeof includes the padding.


Predict. Bad holds 1 + 8 + 4 = 13 bytes of data. What does sizeof(Bad) print? And Good, the same fields largest first?



24 and 16 bytes: 11 of Bad's 24 bytes are padding (7 after flag so that score starts at 8, and 4 at the end so that the struct's size is a multiple of its alignment, 8). Sorting fields from largest to smallest alignment removes most of it: a third less memory, so a third fewer cache lines for an array of them. Clang's -Wpadded warning lists every hole. The last line is explained in section 8.


Array of structs against struct of arrays


An array of structs (AoS) stores records one after another: std::vector<Token>. A struct of arrays (SoA) stores one array per field: all the logprobs together, all the users together. AoS is what object-oriented code produces naturally; SoA is what columnar formats (Arrow, Parquet), dataframes and tensors use. The test: 20 million token records of 8 four-byte fields (32 bytes each), summing one field, then all eight.




Predict. Summing one 4-byte field, AoS drags 32 bytes through the cache per record and SoA 4. Is SoA 8 times faster?





It depends on the field, and the reason is a lesson in itself.


    

  • Integer field:  ns against  ns per record over three runs, about 8x, the ratio of bytes read (32 against 4). Both loops stream memory at roughly the same rate (about 50 GB/s); SoA simply has 8 times fewer bytes to stream.

  • Float field: no difference. Both take about 1 ns per record, because both are limited by something else: adding floats in order. The C++ standard says s += x on floats must happen one after another, since float addition is not associative (rounding makes (a+b)+c differ from a+(b+c)), and each addition waits about 3 cycles for the previous one. The memory system is never the bottleneck. Allow the compiler to reorder the additions with -ffast-math and the 8x appears: AoS  ns, SoA  ns. Section 6 explains why.

  • All 8 fields: AoS only about 1.2x slower, since it uses every byte it reads.

Correction to the old page
"C++: zero to expert" said array-of-structs versus struct-of-arrays "changes throughput by an order of magnitude". Measured here, the gain is the ratio of bytes read to bytes used, and only when memory is the bottleneck: about 8x for one field of a 32-byte record, about 1.2x when all fields are used, and nothing at all when the loop is limited by a chain of dependent float additions. A wider record (64 or 128 bytes) would give more than 10x for one field; a loop that uses every field gives little. Measure your own access pattern.


Why ML code is SoA
A tensor is SoA taken to the limit: one contiguous buffer per quantity. llama.cpp's quantised weights are a careful AoS: each block_q4_0 packs one 2-byte scale with the 32 four-bit weights it scales (18 bytes), because the dot product needs both together (the root's {{Reading, section 5|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} shows the struct, and {{Part 3|#t-cl-read}} reads its kernels).







4. Virtual memory, pages and mmap


The addresses your program sees are not physical locations in the RAM chips. They are virtual addresses: each process has its own private address space, and the operating system keeps a page table that maps it, one page at a time, to physical memory or to nothing yet. On Apple silicon a page is 16 KB (hw.pagesize printed 16384; Intel and most Linux machines use 4 KB). Every load translates its address; the TLB (translation lookaside buffer) is the small cache of recent translations, and a miss in it costs extra loads to walk the page table, part of the slope you saw in the latency ladder.


Two consequences matter for C++ programmers:


    

  • Memory is given lazily. malloc or new of a big block only reserves addresses. The first touch of each page triggers a page fault: the processor stops, the kernel finds a physical page, zeroes it, maps it, and the instruction retries.
    • 

  • A file can be mapped instead of read. mmap puts a file's bytes into your address space; pages are read from disk (or from the operating system's page cache, the copy of recently used files it keeps in RAM) only when touched, and pages that are never touched cost nothing.
    •

Why llama.cpp maps model files


A model file is gigabytes of read-only weights. Mapping it means loading is nearly instant, a second process running the same model shares the same physical pages through the page cache, a restart finds the weights still cached, and the operating system can drop pages under memory pressure and re-read them later instead of swapping.
