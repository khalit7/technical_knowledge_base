12. The ABI: C++'s binary contract

An API is a contract in source code: names, types, what functions do. An ABI (application binary interface) is the contract between already-compiled pieces of machine code: which registers carry arguments (section 5), how structs are laid out (section 3), how virtual tables and exceptions work, and what the symbols are called. Two object files work together only if they agree on all of it. Python programmers meet the ABI as "this wheel does not match your Python" or as a crash after mixing builds.

Name mangling

C has one function per name. C++ allows the same name in different namespaces and overloads with different parameter types, so the compiler encodes the namespace and the parameter types into the symbol, following the {{Itanium C++ ABI|https://itanium-cxx-abi.github.io/cxx-abi/abi.html#mangling}} (used by clang and GCC on every platform except Windows, despite its name). extern "C" turns mangling off, which is why every C++ library meant to be called from another language exposes a C interface.





Read __ZN9ggml_like3dotEPKfS1_i as: _Z a mangled name (macOS adds one more underscore in front), N ... E a nested name made of 9ggml_like (9 characters) and 3dot, then the parameters: PKf pointer to const float, S1_ the same type again, i int. The double overload differs only in d. c_dot is just _c_dot.


What breaks when you mix


    

  • Different standard libraries. clang on macOS uses libc++; GCC on Linux uses libstdc++. Their std::string, std::vector and friends have different layouts, so a std::string cannot cross between code built against the two. Even within one library, flags that change layouts (debug iterators, _GLIBCXX_USE_CXX11_ABI on Linux) must match.
    • 

  • Standard library designs that cannot be fixed. Because programs compiled years ago still link against today's shared standard library, library vendors avoid any change to a type's layout or a function's mangled name; known-slow designs (std::unordered_map's node-based buckets, std::regex) stay as they are for that reason.
    • 

  • Headers and flags out of step. Two translation units that see different definitions of the same struct (a different #define, packing pragma or alignment) break the one-definition rule: no error, just corrupted fields at run time.
    • 

  • Mixing compilers is fine through a C interface, risky through C++ types, and the reason C++ has no universal package of prebuilt binaries like PyPI's wheels ({{Part 1|#t-ca-read}} covers builds and package managers).
    • 



Apple's ARM64 ABI differs from the standard Linux one in a few details (for example, how variadic arguments are passed): {{Writing ARM64 code for Apple platforms|https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms}}.


In Python
ctypes and cffi can call only C symbols, so they need extern "C". pybind11 and nanobind compile C++ against CPython's own C ABI; a wheel built for one Python version works only on that version unless it uses the limited "abi3" stable ABI (the {{Rust page|n:3c65c17b0d0d8156bed9ead8a22f33b0}} covers abi3 wheels with PyO3).

14. Common mistakes


Timing a loop whose result is never used
The optimiser deletes it and you measure nothing. Use the result (print it, or pass it to a DoNotOptimize/keep barrier) and look at the assembly.


"Float sums vectorise automatically"
Not without permission to reorder additions (-ffast-math, -fassociative-math or a local pragma). Integer sums do. Section 6 measured a 13x gap between the two.


Padding to 64 bytes on Apple silicon
Lines are 128 bytes here; 64-byte padding still left a 2x false-sharing penalty. std::hardware_destructive_interference_size said 64.


Using relaxed atomics, or plain variables, to publish data
Correct on x86 by luck of its strong ordering, wrong on ARM: the reader can see the flag before the data. Use release on the store and acquire on the load (or a mutex).


Walking a matrix against its layout
Columns of a row-major matrix cost 50x here. Swap the loops, transpose once, or store the other order.


A vector of pointers where a vector of values would do
Each element is a separate allocation and a pointer chase; std::vector<T> beats std::vector<std::unique_ptr<T>> unless you need stable addresses or polymorphism.


Assuming a debug build's speed means anything
-O0 keeps every variable in memory and calls every function; section 5's loop went from n calls to a formula. Benchmark optimised builds, with debug info (-O2 -g) for profiling.


Optimising FLOPs in a memory-bound kernel
Matrix-vector work (LLM decode) is limited by bytes; faster arithmetic does nothing. Fewer bytes (quantisation) or more reuse (batching) does.


Reading a vectorisation remark as a guarantee
The remark said "vectorized" for a loop whose additions were still serial. The assembly decides.
