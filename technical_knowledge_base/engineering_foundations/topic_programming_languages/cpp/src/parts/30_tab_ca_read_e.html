12. Undefined behaviour

The C++ standard lists operations whose result it does not define: reading outside an array, reading freed memory, overflowing a signed integer, reading an uninitialised variable, two threads writing the same variable without synchronisation, falling off the end of a function that should return a value, and others. Such a program has undefined behaviour (UB): not "a wrong answer" but no meaning at all. The compiler is allowed to assume UB never happens, and its optimiser uses that assumption to delete checks and simplify code. So a program with UB can work at -O0 and break at -O2, or work today and break after a compiler upgrade. This is the deepest difference from Python, where every one of these is either impossible or an exception.

The classic example: "will x + 1 overflow?" written the obvious way.

overflow.cpp
#include <climits>
#include <cstdio>

// "Will adding 1 overflow?" written the way you would in Python
__attribute__((noinline)) bool will_overflow(int x) {
    return x + 1 < x;   // signed overflow is UB, so the compiler may assume x + 1 > x
}

int main() {
    std::printf("will_overflow(INT_MAX) = %d\n", will_overflow(INT_MAX));
}
$ clang++-23 -std=c++23 -O0 overflow.cpp -o overflow && ./overflow
will_overflow(INT_MAX) = 1
$ clang++-23 -std=c++23 -O2 overflow.cpp -o overflow && ./overflow
will_overflow(INT_MAX) = 0

At -O0 the addition wrapped around to a negative number and the test said 1. At -O2 the compiler reasoned "signed overflow cannot happen, so x + 1 < x is always false" and compiled the function to return false. Neither build reported anything. Sanitizers are compiler modes that add run-time checks for UB; UndefinedBehaviorSanitizer (UBSan) catches this one:

$ clang++-23 -std=c++23 -O2 -fsanitize=undefined overflow.cpp -o overflow && ./overflow
overflow.cpp:6:14: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
SUMMARY: UndefinedBehaviorSanitizer: undefined-behavior overflow.cpp:6:14 
will_overflow(INT_MAX) = 1

(Under UBSan the program prints 1 again: the instrumented build computes the addition so it can check it.) The fix is to test before adding: x == INT_MAX, or __builtin_add_overflow, or C++26's <stdckdint.h> checked arithmetic. Unsigned integers do not have this problem: they wrap around by definition.

A second one, the uninitialised variable, shows how odd UB can look. seen is never set when flag is false:

uninit.cpp
#include <cstdio>

__attribute__((noinline)) void report(bool flag) {
    bool seen;                 // never initialised when flag is false
    if (flag) seen = true;
    if (seen) std::printf("seen\n");
    if (!seen) std::printf("not seen\n");
    std::printf("done\n");
}

int main() { report(false); }
$ clang++-23 -std=c++23 -O0 uninit.cpp -o uninit && ./uninit
not seen
done
$ clang++-23 -std=c++23 -O2 uninit.cpp -o uninit && ./uninit
seen
done

The same call printed "not seen" at -O0 and "seen" at -O2. The compiler warned, though only with -Wall:

$ clang++-23 -std=c++23 -Wall -c uninit.cpp -o /dev/null
uninit.cpp:5:9: warning: variable 'seen' is used uninitialized whenever 'if' condition is false [-Wsometimes-uninitialized]
    5 |     if (flag) seen = true;
      |         ^~~~
uninit.cpp:6:9: note: uninitialized use occurs here
    6 |     if (seen) std::printf("seen\n");
      |         ^~~~
uninit.cpp:5:5: note: remove the 'if' if its condition is always true
    5 |     if (flag) seen = true;
      |     ^~~~~~~~~
uninit.cpp:4:14: note: initialize the variable 'seen' to silence this warning
    4 |     bool seen;                 // never initialised when flag is false
      |              ^
      |               = false
1 warning generated.

The {{UB gallery|#t-ca-ub}} tab has ten cases (overflow, uninitialised read, out-of-bounds index, off-by-one loop, reference into a reallocated vector, string_view of a temporary, dangling lambda capture, double free, missing return, data race), each with its -O0 run, -O2 run and the tool that catches it.

Your defences

  1. Warnings: -Wall -Wextra always; -Werror in CI. They caught the uninitialised read, the dangling string_view and the missing return above.
  2. Sanitizers in tests: -fsanitize=address (ASan: out of bounds, use after free, double free), -fsanitize=undefined (UBSan: overflow, bad shifts, missing return), -fsanitize=thread (TSan: data races). They slow the program down (about 2 times for ASan per its {{documentation|https://clang.llvm.org/docs/AddressSanitizer.html}}, 5 to 15 times for TSan per {{its documentation|https://clang.llvm.org/docs/ThreadSanitizer.html}}), so they run in tests, not production. On this Mac Apple's own ASan did not start (the root's Toolchain atlas records it); LLVM clang 23's worked, and every sanitizer report on this page is from it.
  3. A hardened standard library: libc++ can check v[i], front(), string_view bounds and more, turning silent UB into a trap ({{libc++ hardening|https://libcxx.llvm.org/Hardening.html}}). -D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST is meant for production (cheap checks, a silent trap); the _DEBUG mode prints why:
index_oob.cpp
#include <cstdio>
#include <vector>

int main() {
    std::vector<int> top{9491, 4816, 3499};
    std::printf("top[5] = %d\n", top[5]);   // [] does not check the index
}
$ clang++-23 -std=c++23 -O2 index_oob.cpp -o index_oob && ./index_oob
top[5] = 69878144
$ clang++-23 -std=c++23 -O2 -D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_DEBUG index_oob.cpp -o index_oob && ./index_oob
vector.h:414: libc++ Hardening assertion __n < size() failed: vector[] index out of bounds
(the shell reports: Abort trap: 6)
[exit code 134]
  1. Initialise everything, or let the compiler do it: -ftrivial-auto-var-init=zero made the uninitialised example print "not seen" at -O2. C++26 makes this the language rule: reading an uninitialised local becomes erroneous behaviour, a defined (wrong) value the implementation may diagnose, instead of UB ({{P2795|https://wg21.link/P2795}}).
  2. Prefer what cannot be misused: .at(i) or a hardened library over raw indexing in non-hot code, smart pointers over new, values over references when lifetimes are unclear.
The honest summary
No tool catches all UB, and sanitizers find only what your tests execute. C++ makes you responsible for memory safety; Rust moves most of this list into compile errors (the root page's section 10, and the {{Rust page|n:3c65c17b0d0d8156bed9ead8a22f33b0}}).

13. Libraries: header-only, static, dynamic, and getting them

Python has pip install and wheels. C++ has no official package manager, and the reason is technical: a compiled C++ library works with your program only if it was built with a compatible compiler, standard library and flags (the same ABI, application binary interface). A mismatch gives link errors or, worse, silent memory corruption. Shipping prebuilt binaries is therefore much harder than in Python, and the community's historical answer was "build it yourself" or "copy the source in". Three ways a library reaches your program:

  • Header-only: the whole library is headers (all inline functions and templates), so there is nothing to build or link: nlohmann/json, Catch2, Eigen. It sidesteps packaging and ABI, and costs compile time in every file that includes it.
  • Static library (.a, .lib): object files copied into your executable at link time, like libtokens.a in section 1. One self-contained binary; every program carries its own copy.
  • Dynamic (shared) library (.dylib, .so, .dll): loaded when the program starts. Smaller binaries and shared updates, but the library must be present, at a compatible version, on the machine that runs it. Even the small program from section 1 depends on two:
$ otool -L app
app:
	/usr/lib/libc++.1.dylib (compatibility version 1.0.0, current version 2000.63.0)
	/usr/lib/libSystem.B.dylib (compatibility version 1.0.0, current version 1356.0.0)
