2. Values, references and pointers

In Python every variable is a name bound to an object somewhere on the heap, and b = a binds a second name to the same object. In C++ a variable is the object: its bytes live where the variable lives. So assignment and initialisation copy, and if you want a second name you must say so. There are two ways:

  • A reference, T& r = a;, is another name for an existing object. It must be bound when created and can never be re-bound or be null. Using it is exactly like using a.
  • A pointer, T* p = &a;, is a variable holding an address. &a means "the address of a"; *p means "the object at p"; p->f() is short for (*p).f(). A pointer can be re-pointed, and can be nullptr (points at nothing).
copy.cpp
#include <cstdio>
#include <vector>

int main() {
    std::vector<int> a{1, 2, 3};
    std::vector<int> b = a;    // a COPY: b gets its own three ints
    b.push_back(4);
    std::printf("a has %zu, b has %zu\n", a.size(), b.size());

    std::vector<int>& r = a;   // a REFERENCE: another name for a
    r.push_back(99);
    std::printf("a has %zu after r.push_back\n", a.size());

    std::vector<int>* p = &a;  // a POINTER: holds a's address
    p->push_back(7);           // -> follows the pointer
    std::printf("a has %zu after p->push_back; p == &a is %d\n", a.size(), p == &a);

    p = nullptr;               // a pointer can be re-pointed, or point at nothing
    std::printf("p is now %s\n", p ? "set" : "null");
}
Predict, then reveal: what sizes does each line print?

The same three lines in Python give "a has 4, b has 4": one list, two names. C++ printed "a has 3, b has 4": two vectors. Neither reference nor pointer keeps a alive; they only refer to memory that a owns. That is the root of every dangling-reference bug (section 12).

const

const marks something read-only, checked by the compiler. The most common use is the parameter type const T&: "let me read your object without copying it, and I promise not to change it". With pointers, const can apply to the pointed-at object or to the pointer itself; read the declaration right to left (int* const q: q is a const pointer to int).

const.cpp
#include <string>

// const& : read without copying, and promise not to change it
int count_chars(const std::string& s) { return static_cast<int>(s.size()); }

int main() {
    const int limit = 10;
    limit = 11;                     // error: limit is const

    std::string name = "u0029";
    const std::string& view = name;
    view += "!";                    // error: view is a read-only name

    int x = 1, y = 2;
    const int* p = &x;              // pointer to const int: *p is read-only
    p = &y;                         // fine: p itself can move
    int* const q = &x;              // const pointer to int: q cannot move
    *q = 5;                         // fine: what it points at can change
    q = &y;                         // error
    return count_chars(name) + *p;
}

3. The stack and the heap

A C++ object lives in one of three kinds of storage, and the kind decides when it dies:

  • Automatic storage, "the stack". Local variables. Each function call pushes a frame of memory for its locals; the frame is popped when the function returns. Allocation is free (the stack pointer moves) and destruction happens at the closing brace }, in reverse order of creation.
  • Dynamic storage, "the heap". Objects created with new (or, properly, std::make_unique, section 5). They live until someone destroys them. Allocation calls the memory allocator (malloc), which costs tens of nanoseconds and can fragment memory.
  • Static storage. Globals and static variables: they live for the whole program.

Python puts every object on the heap and frees it when its reference count reaches zero. C++ lets you put most things on the stack. Printing the addresses shows the three regions (the exact numbers change on every run, because macOS randomises where each region starts):

stack_heap.cpp
#include <cstdio>
#include <memory>
#include <vector>

int global_counter = 0;            // static storage: lives for the whole program

void show(const char* what, const void* p) { std::printf("%-28s %p\n", what, p); }

int main() {
    int on_stack = 1;                       // automatic storage (the stack)
    int also_on_stack = 2;
    auto on_heap = std::make_unique<int>(3); // dynamic storage (the heap)
    std::vector<int> v{1, 2, 3};            // the vector object is on the stack...

    show("&global_counter (static)", &global_counter);
    show("&on_stack", &on_stack);
    show("&also_on_stack", &also_on_stack);
    show("&v (the vector object)", &v);
    show("on_heap.get() (heap int)", on_heap.get());
    show("v.data() (its elements)", v.data());     // ...its elements are on the heap
    std::printf("sizeof(v) = %zu bytes, whatever v.size() is\n", sizeof(v));
}
$ clang++ -std=c++23 -O2 -Wall -Wextra stack_heap.cpp -o stack_heap && ./stack_heap

The stack addresses (0x16...) go down as variables are added: on this ARM Mac the stack grows towards lower addresses. The vector is a hybrid that you will meet everywhere: the std::vector object itself is 24 bytes on the stack (a pointer to the elements, the size, the capacity), and its elements live in a heap buffer it owns. When the vector dies, its destructor frees the buffer. That pattern, a small owner on the stack and a big buffer on the heap, is how C++ gets automatic cleanup of heap memory. It has a name: RAII.

4. RAII and destructors

A class can define a constructor (runs when an object is created) and a destructor, written ~ClassName(), which runs automatically when the object dies: at the closing brace for a local, when its owner dies for a member, when delete is called for a heap object. RAII ("resource acquisition is initialisation", an awkward name for a simple idea) means: tie every resource (memory, a file, a lock, a GPU buffer, a socket) to an object whose destructor releases it. Then you can never forget to release it, even when an exception jumps out of the function.

To see it happen, this page uses a small class, Tracer, that prints a line from each special member function, numbering objects #1, #2... and saying whether each lives on the stack or the heap (its source is in the {{Object lifetimes|#t-ca-life}} tab). First, scopes:

lifetime.cpp (lines 14 to 22)
void scope() {
    Tracer a{"a"};
    {
        Tracer b{"b"};
        STEP("end of inner block");
    }
    Tracer c{"c"};
    STEP("end of function");
}

    Tracer a{"a"};

        std::printf("caught %s\n", e.what());

}

5. Owning heap objects: unique_ptr and shared_ptr

When you need an object on the heap (it must outlive the function, it is too big for the stack, or its exact type is decided at run time), do not write new and delete. Use a smart pointer: a small stack object that owns the heap object and deletes it in its destructor.

  • std::unique_ptr<T>: exactly one owner. It cannot be copied (two owners would delete twice), only moved (section 6): ownership is handed over and the source becomes null. It is the same size as a raw pointer and costs nothing extra. Create one with std::make_unique<T>(args...). This is the default.
  • std::shared_ptr<T>: shared ownership with a reference count, like a Python object. The object dies when the last shared_ptr to it dies. It costs a separate control block holding the counts, twice the size, and an atomic (thread-safe) increment or decrement on every copy.
  • std::weak_ptr<T>: observes an object owned by shared_ptrs without keeping it alive; it breaks reference cycles, which reference counting alone never frees (Python has a cycle collector; C++ does not).
lifetime.cpp (lines 72 to 78)
void unique() {
    auto p = std::make_unique<Tracer>("h");   // the Tracer lives on the heap
    std::unique_ptr<Tracer> q = std::move(p);  // ownership moves; the Tracer does not
    std::printf("p is %s, q owns #%d\n", p ? "set" : "null", q->id);
    q.reset();                                 // the owner lets go: destroyed now
    STEP("end of function");
}
