llama_context::decode splits the batch into micro-batches, finds room for them in the KV cache, and calls process_ubatch for each. This function is the heart of the engine: build the graph (or reuse the last one), allocate memory for it, copy the inputs in, compute.

Graph reuse. Building nodes and planning their memory costs time, and for the next token the graph is the same except for its inputs. can_reuse checks that the shapes match; if they do, only set_inputs runs. 9. The CPU backend: threads, barriers, chunks


The CPU backend runs the graph with a pool of threads (4 by default, GGML_DEFAULT_N_THREADS). The design is simple and strict: every thread walks every node; each does its share of that node; then all wait at a barrier (a point no thread passes until all have arrived) before the next node. Views, reshapes and permutes are skipped (ggml_op_is_empty), so of the  nodes,  are real operations: up to  barriers per token (a few fewer when fused operations run as one). The barrier itself is a few atomic operations; a waiting thread spins instead of sleeping, which is fast when every thread has a core and wasteful when it does not:




The barriers make the slowest thread set the pace. Inside a node, each operation splits its work with two numbers in params: ith, this thread's index, and nth, the number of threads (the root page's {{Design space|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} tab quotes the two lines from ops.cpp).


For matrix products a static split is fragile: if one thread is slow (an efficiency core, or another program takes its core), everyone waits. So the rows are cut into more chunks than threads, and a thread that finishes takes the next chunk from a shared atomic counter. The generic version:

Two lessons, both visible despite the noise. Generation peaks at a few threads: a token reads 143 MB once, so once memory bandwidth is the limit, more threads add barrier waiting, not speed. And 8 threads collapse ( tokens/s against  at 4) on a laptop where other programs already used most cores: with a barrier after every node, one thread that loses its core stalls the other seven, at each of hundreds of barriers per token. On a quiet machine the 8-thread number would be much better; on a shared server, set the thread count below the number of free cores.
