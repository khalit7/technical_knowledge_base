9. The standard library you will actually use

The standard library ("the STL") is the C++ equivalent of Python's built-ins plus collections and itertools. On macOS it is LLVM's libc++; on Linux usually GCC's libstdc++; on Windows Microsoft's STL. The interfaces are standard; sizes, growth factors and string buffers below are libc++'s, measured.

std::vector: the default container

A growable array, like a Python list, except that it holds the elements themselves, contiguously, not pointers to objects. Use it unless you have measured a reason not to. Growth is geometric, so push_back is cheap on average:

vector_growth.cpp
#include <cstdio>
#include <vector>

int main() {
    std::vector<int> v;
    std::size_t last = v.capacity();
    std::printf("size 0 capacity %zu\n", last);
    for (int i = 0; i < 1000; ++i) {
        v.push_back(i);
        if (v.capacity() != last) {     // a new, bigger buffer: everything was moved
            last = v.capacity();
            std::printf("size %zu capacity %zu\n", v.size(), last);
        }
    }
}

libc++ doubles (the factor is implementation-defined; do not rely on it). Each change of capacity is a new buffer: every element moves, and every pointer, reference and iterator into the old buffer now dangles. If you know the final size, call reserve(n) first: one allocation, no moves (the {{Object lifetimes|#t-ca-life}} tab's "reserve" scenario).

std::string and std::string_view

std::string owns a growable byte buffer. Short strings are stored inside the 24-byte object itself (the small-string optimisation), so they need no heap allocation; std::string_view is a pointer and a length into characters owned by someone else, so passing one never copies. C++ strings are bytes: size() counts UTF-8 bytes, not characters.

strings.cpp
#include <cstdio>
#include <string>
#include <string_view>

// string_view: a pointer and a length into someone else's characters (no copy)
std::string_view first_word(std::string_view s) {
    auto end = s.find(' ');
    return s.substr(0, end);            // still points into the caller's string
}

int main() {
    std::string small = "u0029";
    std::string big = "a user id far too long for the small-string buffer";
    std::printf("capacity of an empty std::string: %zu\n", std::string{}.capacity());
    std::printf("small: size %zu, chars stored inside the object: %d\n", small.size(),
                (const void*)small.data() >= (const void*)&small &&
                (const void*)small.data() < (const void*)(&small + 1));
    std::printf("big:   size %zu, chars stored inside the object: %d\n", big.size(),
                (const void*)big.data() >= (const void*)&big &&
                (const void*)big.data() < (const void*)(&big + 1));

    std::string line = "attention training trained";
    std::string_view w = first_word(line);
    std::printf("first word: %.*s (%zu bytes, no copy)\n", (int)w.size(), w.data(), w.size());
    std::string cafe = "caf\xc3\xa9";   // UTF-8 bytes; size() counts bytes, not characters
    std::printf("\"%s\" size() = %zu\n", cafe.c_str(), cafe.size());
}

A string_view (and a std::span, the same idea for any contiguous elements) is the right parameter type for "read some text" or "read some numbers", and the wrong type to store: it does not keep its characters alive. Initialise one from a temporary string and it dangles at the semicolon; clang warns, and the {{UB gallery|#t-ca-ub}} shows the result.

Maps, spans and algorithms

containers.cpp
#include <algorithm>
#include <cstdio>
#include <span>
#include <string>
#include <unordered_map>
#include <vector>

// span: a view of contiguous elements, whoever owns them
long sum(std::span<const long> xs) {
    long s = 0;
    for (long x : xs) s += x;
    return s;
}

int main() {
    std::unordered_map<std::string, long> per_user;   // Python's dict
    const char* users[] = {"u0029", "u0005", "u0029", "u0042", "u0005", "u0029"};
    const long tokens[] = {10, 7, 5, 9, 1, 3};
    for (int i = 0; i < 6; ++i) per_user[users[i]] += tokens[i];  // [] inserts 0 if missing

    std::printf("contains u0099? %d (contains() does not insert)\n", per_user.contains("u0099"));
    long& ref = per_user["u0099"];                    // operator[] DOES insert
    std::printf("after per_user[\"u0099\"]: size %zu, value %ld\n", per_user.size(), ref);

    std::vector<std::pair<std::string, long>> rows(per_user.begin(), per_user.end());
    std::ranges::sort(rows, [](const auto& a, const auto& b) {
        return a.second != b.second ? a.second > b.second : a.first < b.first;  // count desc, id asc
    });
    for (const auto& [user, n] : rows) std::printf("%s %ld\n", user.c_str(), n);  // structured binding

    std::vector<long> v{3, 1, 4, 1, 5};
    long arr[] = {9, 2, 6};
    std::printf("sum(v)=%ld sum(arr)=%ld sum(first 2 of v)=%ld\n",
                sum(v), sum(arr), sum(std::span(v).first(2)));
}

  • std::unordered_map is a hash table like dict, but unordered (there is no insertion order) and its [] inserts a default value when the key is missing, so it cannot be used on a const map. Use contains or find to look without inserting. std::map is a sorted tree.
  • std::ranges::sort(rows, cmp) sorts with your comparison; the lambda (section 10) gives the root page's tie-break: count descending, then user id ascending.
  • auto& [user, n] is a structured binding: tuple unpacking.
  • One sum(std::span<const long>) accepted a vector, a plain array and a slice of the vector, with no copies.

Ranges: lazy pipelines

C++20 ranges compose lazily, like Python generators: views::filter, views::transform, views::take build a pipeline that computes nothing until a loop pulls from it. The prints inside the lambdas show the order of evaluation:

ranges.cpp
#include <cstdio>
#include <ranges>
#include <vector>

int main() {
    std::vector<int> counts{12, 0, 7, 31, 0, 5, 18};
    // A lazy pipeline: nothing runs until the loop pulls values (like a Python generator)
    auto pipeline = counts
        | std::views::filter([](int n) { std::printf("  filter %d\n", n); return n > 0; })
        | std::views::transform([](int n) { std::printf("  square %d\n", n); return n * n; })
        | std::views::take(2);
    std::printf("pipeline built, nothing computed yet\n");
    for (int x : pipeline) std::printf("got %d\n", x);

    // C++23: collect into a container, like list(...) in Python
    auto evens = std::views::iota(1, 11)
               | std::views::filter([](int n) { return n % 2 == 0; })
               | std::ranges::to<std::vector>();
    std::printf("evens: %zu values, last %d\n", evens.size(), evens.back());
}
Predict, then reveal: which numbers get filtered and squared before the loop stops?
$ clang++ -std=c++23 -O2 -Wall -Wextra ranges.cpp -o ranges && ./ranges

  filter 12
  square 12
got 144
  filter 0
  filter 7
  square 7
got 49
  filter 31
evens: 5 values, last 10

Only what the loop needed was computed (31 was filtered but never squared: taking the second element advanced the filter to find a third before take said stop; 5 and 18 were never touched). C++23's std::ranges::to<std::vector>() collects a pipeline into a container, like list(gen). A view does not own its data, so a view of a temporary container dangles, just as a string_view does.

Defaultsvector, string, unordered_map; string_view and span as parameters; algorithms over hand-written loops.
What it costsEvery container owns heap memory; views and spans own nothing and can dangle.
Common mistakesKeeping a reference or iterator across a push_back; map[key] to test membership; std::list (a linked list, almost always slower than vector).

10. Lambdas

A lambda is an inline function, like Python's lambda but with statements allowed. The part in square brackets says which outside variables it captures and how: [x] copies x when the lambda is created; [&x] refers to the variable itself; [=] and [&] capture everything used, by copy or by reference.

lambdas.cpp
#include <cstdio>
#include <functional>
#include <vector>

int main() {
    int threshold = 10;
    auto by_value = [threshold](int n) { return n > threshold; };   // copies threshold now
    auto by_ref   = [&threshold](int n) { return n > threshold; };  // refers to the variable
    threshold = 100;
    std::printf("by_value(50)=%d by_ref(50)=%d\n", by_value(50), by_ref(50));

    int calls = 0;
    auto counter = [calls]() mutable { return ++calls; };   // mutable: may change its own copy
    counter(); counter();
    std::printf("counter() -> %d, outer calls still %d\n", counter(), calls);

    auto twice = [](auto x) { return x + x; };              // generic lambda (a template)
    std::printf("twice(21)=%d twice(1.5)=%.1f\n", twice(21), twice(1.5));

    // A lambda is an object of a compiler-written class; its size is its captures
    std::printf("sizeof: no capture %zu, one int %zu, one reference %zu\n",
                sizeof([] {}), sizeof(by_value), sizeof(by_ref));
    std::function<bool(int)> f = by_value;   // type-erased holder: can store any callable
    std::printf("sizeof(std::function) %zu\n", sizeof(f));
}
Predict, then reveal: by_value(50) and by_ref(50) after threshold becomes 100?
$ clang++ -std=c++23 -O2 -Wall -Wextra lambdas.cpp -o lambdas && ./lambdas

counter() -> 3, outer calls still 0
twice(21)=42 twice(1.5)=3.0

Under the hood a lambda is an object of a class the compiler writes, with the captures as members and operator() as the body; its size is the size of its captures. Python closures always capture variables by reference and keep them alive; a C++ reference capture does not keep anything alive, so a lambda that outlives the function it was made in (returned, stored, or given to a thread) must capture by value. std::function can hold any callable with a given signature, at the price of a type-erased call and possibly a heap allocation; templates and auto parameters avoid both.

Problem it solvesComparators, callbacks and small helpers written where they are used.
What it costsNothing for a lambda passed to a template; a std::function costs an indirect call.
Common mistakes[&] in a lambda that escapes its scope (the gallery's "dangling capture" case); capturing this and outliving the object.

11. Error handling: exceptions, optional, expected

C++ has three ways to say "this did not work", and real code uses all three:

errors.cpp
#include <charconv>
#include <cstdio>
#include <expected>
#include <optional>
#include <stdexcept>
#include <string>
#include <string_view>

// 1. Exceptions: like Python's raise/except
long parse_or_throw(std::string_view s) {
    long v = 0;
    auto [p, ec] = std::from_chars(s.data(), s.data() + s.size(), v);
    if (ec != std::errc{} || p != s.data() + s.size())
        throw std::invalid_argument("not a number: " + std::string(s));
    return v;
}

// 2. optional: "a value or nothing", no reason given (like returning None)
std::optional<long> parse_opt(std::string_view s) {
    long v = 0;
    auto [p, ec] = std::from_chars(s.data(), s.data() + s.size(), v);
    if (ec != std::errc{} || p != s.data() + s.size()) return std::nullopt;
    return v;
}

// 3. expected (C++23): "a value or an error", like Rust's Result
enum class ParseError { empty, not_a_number };
std::expected<long, ParseError> parse_exp(std::string_view s) {
    if (s.empty()) return std::unexpected(ParseError::empty);
    long v = 0;
    auto [p, ec] = std::from_chars(s.data(), s.data() + s.size(), v);
    if (ec != std::errc{} || p != s.data() + s.size()) return std::unexpected(ParseError::not_a_number);
    return v;
}

int main() {
    try {
        parse_or_throw("12x");
    } catch (const std::invalid_argument& e) {
        std::printf("caught: %s\n", e.what());
    }
    auto o = parse_opt("12x");
    std::printf("optional: has_value=%d, value_or(-1)=%ld\n", o.has_value(), o.value_or(-1));

    for (std::string_view s : {"4816", "", "12x"}) {
        auto r = parse_exp(s)
                   .transform([](long v) { return v * 2; });   // runs only on success
        if (r) std::printf("expected \"%.*s\": value %ld\n", (int)s.size(), s.data(), *r);
        else   std::printf("expected \"%.*s\": error %d\n", (int)s.size(), s.data(), (int)r.error());
    }
}
$ clang++ -std=c++23 -O2 -Wall -Wextra errors.cpp -o errors && ./errors
caught: not a number: 12x
optional: has_value=0, value_or(-1)=-1
expected "4816": value 9632
expected "": error 0
expected "12x": error 1
  • Exceptions work like Python's: throw, try/catch, unwinding with destructors (section 4). Use them for errors the immediate caller cannot handle (a missing config file, out of memory).
  • std::optional<T> (C++17) is "a T or nothing", like returning None, with no reason attached.
  • std::expected<T, E> (C++23) is "a T or an error E", like Rust's Result. The caller must look; transform and and_then chain steps that run only on success. Use it for failures that are part of normal operation (parsing user input, a malformed JSONL line).

What each costs, measured with the same tiny function written both ways (10 million successful calls; 100,000 failing calls):

$ sysctl -n vm.loadavg; clang++ -std=c++23 -O2 throw_cost.cpp -o throw_cost && ./throw_cost
{ 13.33 8.47 7.38 }
success path:  exception-style 1.51 ns/call, expected-style 0.98 ns/call
failure path:  throw+catch 4766 ns/call, expected 0.96 ns/call

On the success path both are about a nanosecond: compilers implement exceptions with tables consulted only when something is thrown ("zero-cost" exceptions, which still cost binary size). Throwing and catching took about 4766 ns, thousands of times more than returning an expected. So: exceptions for rare failures, expected or optional where failure is common. Some codebases (game engines, parts of Google's, many embedded ones) compile with exceptions turned off; ggml, the C core under llama.cpp, reports errors with return values and assertions, since C has no exceptions.

Rule of thumbExceptional and far away: throw. Expected and handled by the caller: std::expected. "Not found": std::optional.
noexceptMark functions that never throw, above all move constructors and destructors (section 6).
Common mistakesExceptions as control flow in a hot loop; throwing from a destructor; ignoring an expected (add [[nodiscard]] to the function).
