One real block of our model, opened byte by byte, and the same 32 weights quantised two ways. The bytes are the first 34 bytes of blk.0.attn_q.weight in the GGUF file (layer 0's query projection, row 0, weights 0 to 31), read by src/cl/code/quant_demo.py; the arithmetic follows quantize_row_q8_0_ref and quantize_row_q4_0_ref in ggml-quants.c, line for line.

The 34 bytes as stored (Q8_0)

The first 2 bytes (highlighted) are the scale d as a 16-bit float, little-endian: . Each of the next 32 bytes is one weight as a signed 8-bit integer q; the weight is d × q. Tap a byte.

Quantise the same 32 weights: Q8_0, then Q4_0

The file's weights are already Q8_0, so requantising them as Q8_0 must give back the stored bytes exactly: that is our check that the Python matches ggml (it does). Q4_0 then shows what 4 bits cost on the same input.

Over the whole matrix (576 × 576 weights, 10,368 blocks), Q4_0 has a relative root-mean-square error of against the Q8_0 weights it was made from: about a tenth of the signal. Methods that keep more accuracy at 4 bits (k-quants, importance matrices) are the {{Quantization and precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}} page's subject; the Reading tab, section 10, shows the change in the model's output.

A k-quant block: Q4_K

The "K" types group 256 weights into a super-block of 8 sub-blocks of 32. Each sub-block gets its own scale and minimum (x = a × q + b), stored in 6 bits each, and those 6-bit numbers are themselves scaled by two 16-bit floats per super-block. The struct, then drawn to scale:

144 bytes for 256 weights: (2 + 2 + 12 + 128) × 8 / 256 = 4.5 bits per weight, the same as Q4_0, but with a scale and a minimum per 32 weights instead of a scale alone.
