10. Quantised blocks and the kernels that read them

A quantised type stores weights in blocks: 32 weights share one scale d, and each weight is a small integer q, with weight ≈ d × q. Why quantise, and how much accuracy it costs, is the {{Quantization and precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}} page's subject; here we read the code. The blocks are plain C structs:

ggml_half is a 16-bit float stored as a uint16_t (C has no portable half type). The static_assert pins the size: 34 bytes for Q8_0 (8.5 bits per weight), 18 for Q4_0 (4.5 bits: two 4-bit values per byte). The reference quantiser for Q8_0, used to write model files, is ten lines:

Find the largest magnitude, divide by 127 so it maps to ±127, round each weight. The {{Quant blocks|#t-cl-quant}} tab runs this and the Q4_0 version on one real block of our model, step by step, and shows the "k-quant" layout (Q4_K: 256 weights in 144 bytes, with 6-bit scales per group of 32).

The dot product, as most guides show it

A matrix-vector product is one dot product per weight row. ggml first quantises the activations to Q8_0 too, so the inner loop multiplies 8-bit integers and applies the two scales once per block. The portable reference version:

And the ARM NEON version of the same function (the middle of it; the full function also has SVE and i8mm paths behind #if):

vld1q_s8 loads 16 signed bytes into one 128-bit register. ggml_vdotq_s32 is the SDOT instruction: it multiplies 16 pairs of bytes and adds each group of four products into one of four 32-bit lanes, 16 multiply-adds in one instruction. Two blocks per iteration, two accumulators (sumv0, sumv1), so two chains of additions run in parallel: the same tricks as Part 2's NEON dot product ({{SIMD lanes|#t-cb-simd}} tab), which uses float lanes where this uses bytes. GGML_RESTRICT is C's restrict: a promise that x and y do not overlap, so the compiler need not reload after each store.

What actually runs on this M1

To check, we built a copy of llama.cpp with a counter at the top of each candidate kernel (src/cl/code/instrument.py adds one atomic increment per function and prints the totals at exit; the pinned clone stays untouched) and ran the same prompt:

With the default build, ggml_vec_dot_q8_0_q8_0 runs 0 times. The weights were repacked at load (section 5), so every product goes to ggml_gemv_q8_0_4x4_q8_0 ("matrix times vector", four interleaved rows per step) for single rows and ggml_gemm_q8_0_4x4_q8_0 ("matrix times matrix") for groups of four token rows; the choice is in the repacked kernel's chunk function:

Here is the loop that really did the work for every token on this page. The repacked block is a template with two integer parameters (a C++ feature C lacks: block<8, 4> is a distinct type computed at compile time), holding 4 rows' scales and their 32 weights each, interleaved 4 bytes at a time (136 bytes for 4 × 32 weights):

Each iteration loads 128 weight bytes (32 from each of 4 rows) and the activation block once, and vdotq_laneq_s32 multiplies 4 bytes of the activation (one "lane" of a register) against 4 bytes of each of the 4 rows: one instruction, 16 multiply-adds, 4 rows advanced together. Eight of them cover the block; one fused multiply-add applies the scales. Against the vec_dot version above, the activation is loaded once per 4 rows instead of once per row, and the weights stream from one contiguous buffer: fewer loads per multiply, which is what the repack copy buys.

The arithmetic checks out exactly. One decoded token: products × 16 chunks = gemv calls. The 5-token prompt: 4 rows go through gemm and the fifth through gemv, except in the last layer, where only the last token's row is kept (the GET_ROWS in section 7), so its three feed-forward products and the output projection have one row: (211 − 4) × 16 = gemm calls. With --repack 0, the generic path runs: ggml_compute_forward_mul_mat ( calls = 211 products × 4 threads × 2 runs, a warm-up and the measured one) offers each product to llamafile's tinyBLAS, which takes the prompt's products but declines single rows (if (n < 2) return false;), and ggml_vec_dot_q8_0_q8_0 computes those one output at a time: (49,152 + 1,536 + 1,536 + 576) rows × 2 runs = calls.

11. KV cache, batches and sampling

What the KV cache is and why it exists is {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}'s subject. In the code it is a class with virtual functions, implementing an abstract interface (C++ inheritance, Part 1 section 7):

llama_memory_i has several implementations (a plain cache, one with a sliding window, one for recurrent models), and the context holds whichever the model needs through a pointer to the interface. Storage is one K tensor and one V tensor per layer. Writing this token's K is a SET_ROWS node: copy rows into the cache at the slot indices chosen for this batch:

Reading K for attention is a 4-dimensional view of the same tensor: no copy, just sizes and strides (section 6). The view in our trace was {64, 3, 256}: 64 numbers per head, 3 KV heads, 256 cells.

Size, from the log: KV buffer size = MiB = 2 (K and V) × 30 layers × cells × 192 numbers × 2 bytes (F16) = bytes. simple.cpp asked for a context of 12 tokens (prompt + 8 − 1); the context rounds it up to cells (cparams.n_ctx = GGML_PAD(cparams.n_ctx, 256); in llama-context.cpp).

Batches. A batch is a list of tokens, each with a position, a sequence id (which conversation it belongs to) and a flag saying whether its logits are wanted. simple.cpp fills one with the prompt and asks for logits only for the last token, which is what lets the graph drop the other rows before the output projection:
