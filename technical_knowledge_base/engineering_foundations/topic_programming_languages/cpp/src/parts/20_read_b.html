1. How a C++ program is built

Python reads your source and runs it; import tokens finds tokens.py at run time. C++ has no run-time import. Building is a separate step with three stages, and most confusing C++ errors come from not knowing which stage complained.

  1. Preprocessor. Lines starting with # are text commands. #include "tokens.h" pastes the whole file in, literally. The result is one long file per .cpp, called a translation unit.
  2. Compiler. Each translation unit is compiled separately into an object file (.o): machine code plus a table of the names (symbols) it defines and the ones it needs from elsewhere.
  3. Linker. Joins the object files and libraries into one executable, matching every needed symbol to exactly one definition.

The root page's token counter, split the way real projects are: a header (.h) declares the function (its name and types: a promise), a source file defines it (the body).

tokens.h
// tokens.h: the declaration (a promise that a definition exists somewhere)
#pragma once
#include <string_view>
int count_tokens(std::string_view text);
main.cpp
// main.cpp: uses count_tokens; only sees the declaration
#include "tokens.h"
#include <cstdio>

int main() {
    std::printf("%d tokens\n", count_tokens("C++ is fun, x86_64 too"));
}
tokens.cpp
// tokens.cpp: the definition
#include "tokens.h"
#include <cctype>

int count_tokens(std::string_view text) {
    int n = 0;
    bool inside = false;
    for (unsigned char c : text) {
        bool tok = std::isalnum(c) && c < 128;
        if (tok && !inside) n += 1;
        inside = tok;
    }
    return n;
}

The pipeline, step by step

The same three files through the three stages, with the real line counts, sizes, symbol tables and messages (Apple clang 17, -std=c++20); bars are to scale by line count. Predict before you pick "Forgot tokens.o": which stage fails, the compiler or the linker?

  1. Three source files. A header that declares count_tokens, a .cpp that defines it, and main.cpp that calls it: 25 lines together.
  2. main.cpp's translation unit. The preprocessor pastes tokens.h, and through it the standard headers, into main.cpp: 55,693 lines for the compiler to read. The last lines are your code (the closed block under the pipeline shows them).
  3. tokens.cpp's translation unit. tokens.cpp becomes its own translation unit of 55,700 lines. The two are processed separately; neither sees the other.
  4. Two object files. Each translation unit compiles to an object file of machine code: main.o needs count_tokens and printf (U); tokens.o defines count_tokens (T). The compiler trusted the declaration in tokens.h.
  5. The link. The linker matches main.o's U count_tokens to tokens.o's T (now green), leaves printf to the dynamic system library, and writes the executable.
  6. It runs. "C++ is fun, x86_64 too" has 6 tokens under the root page's rule (C, is, fun, x86, 64, too).
  1. Two object files, as before. Preprocessing and compiling went exactly as in a correct build: main.o needs count_tokens (U), tokens.o defines it (T).
  2. Link only main.o. Nothing defines count_tokens, so the linker (ld), not the compiler, fails: "Undefined symbols". The compile step had succeeded.
  1. A body in a header. util.h defines a function body, not just a declaration, and both a.cpp and b.cpp include it.
  2. Two copies. After preprocessing, each translation unit contains its own copy of twice().
  3. Two definitions. So each object file defines twice(int): two T entries for one name.
  4. The linker refuses. The one definition rule is broken: "duplicate symbol".
  5. The fix. Mark the function inline (util_inline.h). The linker keeps one copy; the program links and exits with 0.
  1. A CMake build. The CMake project below builds tokens.cpp into a static library, libtokens.a, and links it into tokcount. Ninja records what each output was built from.
  2. Edit tokens.cpp. (Here: touch it.) Only tokens.cpp recompiles; the library and the program relink. main.cpp is untouched.
  3. Edit tokens.h. Both .cpp files include it, so both recompile: headers are why big C++ projects rebuild slowly.
  4. Change nothing. Build again: nothing to do.

Reading a symbol table (nm): T (green) is defined here, U (red) is used here and defined elsewhere. The linker must find exactly one T for each U: none is "Undefined symbols", two is "duplicate symbol". The compiler accepted main.cpp on the header's promise alone, so a missing definition is always the linker's error.

The one definition rule (ODR) says a function may be defined once in the whole program. A function body in a header included from two .cpp files gives each object file its own copy: "duplicate symbol" from ld on macOS (GNU ld says "multiple definition"). The fix is inline ("identical copies may appear; keep one") or only a declaration in the header. Functions defined inside a class body, templates and constexpr functions are implicitly inline, which is why headers full of them link fine.

Python bridge
A header is like a .pyi stub (types only) that every user pastes into their file. Python resolves names when the line runs; C++ resolves them at link time, so a missing or duplicated function is a build error, never a run-time NameError.

CMake: the build system

CMake is the de facto standard build description: you list targets (executables, libraries) and their properties, and CMake generates the commands for a build tool such as Ninja. A real project separates a library from the program that uses it:

CMakeLists.txt
cmake_minimum_required(VERSION 3.28)
project(tokcount LANGUAGES CXX)

# A library target: compiled once, linked into anything that needs it
add_library(tokens src/tokens.cpp)
target_include_directories(tokens PUBLIC src)      # users of tokens see src/
target_compile_features(tokens PUBLIC cxx_std_20)  # and get C++20
target_compile_options(tokens PRIVATE -Wall -Wextra)

add_executable(tokcount src/main.cpp)
target_link_libraries(tokcount PRIVATE tokens)     # brings the include dir and C++20 along

PUBLIC properties travel to every target that links the library; PRIVATE ones do not: the single most useful idea in CMake. In the generated commands, -Icmake2/src and -std=gnu++20 reached main.cpp; -Wall -Wextra did not. The library became a static library libtokens.a (an archive of object files, made by ar). The payoff of separate compilation is incremental builds: editing a .cpp recompiles one file, editing a header recompiles everything that includes it.

What it buys: each file compiles once, in parallel, and only what changed rebuilds. What it costs: headers are re-parsed in every file that includes them, and you maintain declarations and definitions separately. Common mistakes: a definition in a header without inline; global flags instead of per-target properties; forgetting -std= (section 4). llama.cpp's CMake build: {{the llama.cpp page|n:4055c17b0d0d8150a5effbb5a667dd9d}}, section 2.
