7. Branch prediction

A modern core works on hundreds of instructions at once, in a pipeline: fetching and decoding later instructions while earlier ones finish. At an if it cannot wait to learn which way to go, so a branch predictor guesses from the branch's history and the core runs ahead on the guess. A right guess is free. A wrong one (a misprediction) throws away the work done on the wrong path and restarts. Random data makes guessing impossible; sorted data makes it trivial. 8. Threads, atomics and the C++ memory model


The root page's {{Reading, section 9|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} showed the basic danger: two threads updating one counter lose updates, and a data race (two threads touching the same memory, at least one writing, nothing ordering them) is undefined behaviour in C++. {{Part 1|#t-ca-read}} covers std::thread, mutexes and locks. This section is about what the hardware adds: cores do not see each other's writes in the order they were made.


Why order is not guaranteed


Each core writes into a private store buffer before its writes reach the shared caches, and executes loads early, out of order, whenever their addresses are known. On one core this is invisible. Seen from another core, two writes can appear in the opposite order. x86 processors promise to keep stores in order (a strong model); ARM processors, including this one, do not (a weak model). The compiler may reorder too. So C++ defines its own rules, the memory model, and you state what order you need on each atomic operation (a std::atomic<T> read or write that can never be torn or raced) through a memory order ({{cppreference|https://en.cppreference.com/w/cpp/atomic/memory_order}}):

False sharing


Coherence (keeping every core's cached copy of a line consistent) works per cache line: before a core writes to a line, every other core's copy is invalidated. Two threads writing different variables that happen to share a line therefore fight over it as if they shared data. This is false sharing.
