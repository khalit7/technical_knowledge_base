Latency ladder

How long one load takes, as the data grows from 4 KB to 1 GB, measured on this M1 Pro with the pointer chase of {{Reading, section 1|#t-cb-read}} (ladder.cpp, one node per 128-byte cache line). Each point is the best of 3 timings inside a run; the page shows all runs: three in random order (each load's address unpredictable) and two in address order (the prefetcher can guess).

Try: press Play to climb the ladder one buffer size at a time; hover or tap the chart to read any point; switch the vertical axis to linear to feel how far DRAM is.

Level boundaries are the sizes sysctl reports for the performance cores: L1 data 128 KB per core, L2 12 MB shared by the cluster. The system level cache sits between L2 and DRAM; Apple does not publish its size, and here it shows only as a softer ramp. Beyond a few MB the random chase also misses in the TLB (address-translation cache; 16 KB pages), which adds to the steps. Other programs were running (load average recorded in each run: ), so the L2-to-DRAM region varies most between runs.

What it means for code
A hash-table lookup or linked-structure walk over a big table pays the right-hand end of this chart per hop; a scan over a contiguous array pays the bottom curve, or less once SIMD and the prefetcher combine (section 2's row sum read 64 MB at about 0.07 ns per integer). Shrinking the working set by a level (from DRAM-sized to L2-sized) is often worth more than any change to the arithmetic.
