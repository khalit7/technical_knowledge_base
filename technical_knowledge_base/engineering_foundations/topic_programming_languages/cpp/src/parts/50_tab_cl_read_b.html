Start where a user starts: examples/simple/simple.cpp, 238 lines that load a model, generate text and print timings. First the setup: load the weights, turn the prompt into token ids, create a context (the object that holds the KV cache and the compute buffers for one conversation) and a sampler (the rule that picks the next token from the scores).

Then the loop: run the model on the current batch, sample one token, print it, and feed it back as the next batch of one.

4. GGUF: the model file


A model file must carry the weights and everything needed to use them: architecture, sizes, tokenizer, chat template. GGUF is llama.cpp's format for that: one file, read without Python and without parsing JSON. The format is written down at the top of gguf.h:




Every integer has a fixed width and is little-endian; a string is a 64-bit length then the bytes. That is what makes it easy to read from any language. Here is a complete reader in 41 lines of Python, standard library only, run on our model file:








The file to scale. The header is  bytes, mostly the tokenizer's 49,152 token strings and 48,900 merge rules; then padding to a multiple of 32; then  tensors back to back. Tap a block.


Three details to notice. Shapes are stored innermost first: token_embd.weight has ne=[576, 49152], where PyTorch would say (49152, 576); ne[0] is the dimension whose elements are adjacent in memory. Offsets are relative to the start of the data section, which begins at byte , the end of the header rounded up to the alignment of 32 (so every tensor can be loaded with aligned SIMD reads, Part 2). Sizes follow from the type: Q8_0 stores 32 weights in 34 bytes, so the embedding table is 576 × 49,152 / 32 × 34 =  bytes. The C++ reader computes the byte strides from the same numbers:

C++ in gguf.cpp
The reader is C++ behind a C API: a gguf_reader struct with overloaded read() functions for each type (templates, Part 1 section 8), std::vector and std::string for the values, and try/catch (std::bad_alloc &) around reads whose length comes from the file, because a corrupt or malicious file can claim a string of 263 bytes. Every count is checked against SIZE_MAX before allocating: reading untrusted binary input is where C and C++ code gets exploited (Part 1, {{UB gallery|#t-ca-ub}}).


Predict. The model has 134.5 million parameters stored mostly as Q8_0. Before looking: is the file bigger or smaller than 134.5 million bytes, and by roughly how much?


Bigger:  bytes. Q8_0 spends 34 bytes on 32 weights (8.5 bits each, the scale costs the extra half bit), 61 small norm vectors stay in 32-bit float, and the header adds 1.8 MB. The loader reports 8.51 BPW (bits per weight).







5. Loading: mmap, then a surprise copy


llama_model_load_from_file reads the header (section 4), creates one ggml tensor per weight, and then has to put 143 MB of weights somewhere. It does not read them: it maps the file. mmap asks the operating system to make the file appear in the address space; nothing is read until a page is touched, and the pages belong to the OS's file cache, so a second process mapping the same model shares them. {{Part 2|#t-cb-read}} measured this (section 4, Pages and mmap) and shows llama_mmap's call to mmap. The loader then points each tensor straight into the mapping:




(uint8_t *) mapping->addr() + weight->offs is pointer arithmetic: the base address of the mapped file plus the tensor's offset, cast to bytes so that adding offs moves offs bytes (Part 1 section 2). No copy, no allocation. The std::async lambda is an optional parallel check of the bytes (lambdas, section 10).


Now the log of our run. Grep each line and the code explains it:




    

  • CPU_REPACK model buffer size = 136.27 MiB. A second copy of almost all the weights. At load time the CPU backend copies every Q8_0 matrix into an interleaved layout, four rows woven together, because its fastest kernel reads four rows in one stream (section 10 shows that kernel). The choice is made at run time from the processor's features: dotprod (the SDOT instruction) is present on the M1 and i8mm (an 8-bit matrix-multiply instruction) is not (sysctl hw.optional.arm here: FEAT_DotProd: 1, FEAT_I8MM: 0), so it picks the 4x4 layout:
    • 





    

  • token_embd.weight (q8_0) (and 61 others) cannot be used with ... CPU_REPACK. The 61 others are the 32-bit norm vectors. The embedding table stays in the mapping because it is read by row lookups (GET_ROWS: fetch row number token id), which need the plain layout. The model ties its output projection to the embedding table, so the loader creates that tensor a second time (TENSOR_DUPLICATED), and that copy, used for a matrix product, is repacked.

Predict. With repacking, how much memory do the weights take in total, and what happens to the mapped copy of the repacked tensors?


 MiB mapped plus  MiB repacked: about twice the file. The repacked copy is ordinary allocated memory. The mapped pages of those tensors were read once, during the copy, and then only sit in the OS file cache, which the OS may evict under pressure; the embedding table ( MiB) stays in use from the mapping. On a phone or a full laptop, --repack 0 (in llama-bench; use_extra_bufts = false in the API) trades that copy for a slower kernel.
