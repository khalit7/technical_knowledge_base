6. Move semantics

Copy-by-default has an obvious cost: returning a vector of a million elements, or putting a string into a container, would copy every byte. C++11 added moves: when the source object is about to die anyway, the new object may steal its heap buffer (copy three pointers, set the source's to null) instead of copying the contents.

The compiler needs to know when stealing is safe. It sorts expressions into two families (simplified):

  • an lvalue has a name and an address you can take: a, v[3], *p. It will be used again, so it must be copied.
  • an rvalue is a temporary about to disappear: make_name(), a + b, Tracer{"x"}. It may be moved from.

A class gets a move constructor T(T&& other) (the && means "rvalue reference": binds only to things that may be moved from) alongside its copy constructor T(const T& other), and overload resolution picks one. std::move(x) moves nothing. It is a cast that says "treat x as an rvalue; I will not need its value again" ({{cppreference: "exactly equivalent to a static_cast to an rvalue reference type"|https://en.cppreference.com/w/cpp/utility/move}}); the move constructor that it selects does the stealing.

The moved-from a is still a valid object (its destructor runs, #1, at the end) but its value is unspecified; libc++ leaves the string empty. You may assign to it or destroy it; do not read it. What moving buys, and one trap:

moved_from.cpp
#include <cstdio>
#include <string>
#include <utility>
#include <vector>

int main() {
    std::string s = "a string long enough to live on the heap";
    std::string t = std::move(s);       // t steals s's heap buffer
    std::printf("t: %zu chars, s: %zu chars\n", t.size(), s.size());
    s = "reusable";                     // a moved-from object can be assigned to
    std::printf("s: %s\n", s.c_str());

    std::vector<int> v(1'000'000, 7);
    const int* before = v.data();
    std::vector<int> w = std::move(v);  // O(1): three pointers change hands
    std::printf("w.data() == old v.data(): %d, v.size() now %zu\n", w.data() == before, v.size());

    const std::string c = "const";
    std::string d = std::move(c);       // compiles, but COPIES: you cannot steal from const
    std::printf("c after 'move': %s\n", c.c_str());
}

The million-element vector changed hands in constant time: w owns the very same buffer. The last line is the trap: std::move of a const object silently copies, because a move constructor needs to modify its source.

When the compiler copies, moves or does neither

Passing and returning values is where moves matter most. One rule removes most of the worry: since C++17, returning a temporary, and in practice a local variable, constructs the result directly in the caller's variable, with no copy and no move (copy elision, {{cppreference|https://en.cppreference.com/w/cpp/language/copy_elision}}). So return big objects by value; never write return std::move(local);, which can only prevent elision.

Why noexcept on a move constructor matters: one vector, two classes

A std::vector keeps its elements in one buffer. When the buffer is full, push_back allocates a bigger one, transfers the old elements and frees the old buffer. It would like to move them, but if a move threw an exception halfway, the old buffer would be half-emptied and the vector could not restore it. So the standard library moves only if the move constructor is declared noexcept ("this never throws"); otherwise it copies, to keep its strong exception guarantee ({{std::move_if_noexcept|https://en.cppreference.com/w/cpp/utility/move_if_noexcept}}). The animation runs the same three push_back calls on two versions of Tracer that differ only in that one keyword. Everything shown is the program's real output.

With noexcept, each reallocation moves (cheap); without it, the same code copies every existing element on every growth: for a vector of strings, that is a heap allocation and a byte copy per element. The compiler writes a noexcept move constructor for you when every member's is noexcept (the rule of zero, below), which is one more reason not to write them by hand.

The rule of zero and the rule of five

Five special member functions control a class's lifetime: destructor, copy constructor, copy assignment, move constructor, move assignment. The compiler writes all five for you, member by member. That is correct when every member manages itself (std::vector, std::string, std::unique_ptr): the rule of zero says write none of them. A class that owns a raw resource must write all five (the rule of five), because the compiler-written copy would copy the pointer, not the buffer:

rule_of_five.cpp (lines 5 to 35)
// A class that owns a raw buffer must write all five special members.
class Buffer {
    float* data_;
    std::size_t n_;
public:
    explicit Buffer(std::size_t n) : data_(new float[n]()), n_(n) {}
    ~Buffer() { delete[] data_; }                                   // 1 destructor
    Buffer(const Buffer& o) : data_(new float[o.n_]), n_(o.n_) {    // 2 copy constructor
        std::memcpy(data_, o.data_, n_ * sizeof(float));
    }
    Buffer& operator=(const Buffer& o) {                            // 3 copy assignment
        Buffer tmp(o);
        swap(tmp);
        return *this;
    }
    Buffer(Buffer&& o) noexcept                                     // 4 move constructor
        : data_(std::exchange(o.data_, nullptr)), n_(std::exchange(o.n_, 0)) {}
    Buffer& operator=(Buffer&& o) noexcept {                        // 5 move assignment
        Buffer tmp(std::move(o));
        swap(tmp);
        return *this;
    }
    void swap(Buffer& o) noexcept { std::swap(data_, o.data_); std::swap(n_, o.n_); }
    std::size_t size() const { return n_; }
};

// Rule of zero: let a member that already manages itself do the work.
#include <vector>
struct Buffer0 {
    std::vector<float> data;   // the compiler writes all five, correctly
};
$ clang++ -std=c++23 -O2 -Wall -Wextra rule_of_five.cpp -o rule_of_five && ./rule_of_five

Thirty lines of careful code against one line (std::vector<float> data;). Write only a destructor and forget the other four, and copying the object gives two owners of one buffer, freed twice: the {{UB gallery|#t-ca-ub}}'s "double free" case shows the crash, and shows the bug vanishing at -O2, where the compiler removed the allocation altogether.

Problem it solvesCopy-by-default without paying for copies of temporaries and returned values.
What it costsThe rules (value categories, noexcept, moved-from states) are the hardest part of the language to learn.
Common mistakesUsing an object after std::move; return std::move(x); a hand-written move constructor without noexcept; moving from const.

7. Classes, operators, inheritance and virtual functions

A class and a struct are the same thing except for the default: struct members are public, class members private. Python's conventions become rules the compiler checks: private really is private, const methods really cannot modify the object, and members must be declared with their types.

classes.cpp
#include <compare>
#include <cstdio>
#include <string>

class Usage {
public:
    // explicit: no silent conversion from a string to a Usage
    explicit Usage(std::string user, long tokens = 0)
        : user_(std::move(user)), tokens_(tokens) {}   // member initialiser list

    const std::string& user() const { return user_; } // const: does not modify *this
    long tokens() const { return tokens_; }

    Usage& operator+=(long n) { tokens_ += n; return *this; }
    // one line gives ==, !=, <, <=, >, >= comparing members in declaration order
    auto operator<=>(const Usage&) const = default;

private:
    std::string user_;
    long tokens_;
};

Usage operator+(Usage u, long n) { u += n; return u; }

int main() {
    Usage a{"u0005", 4816};
    Usage b = a + 100;
    b += 1;
    std::printf("%s %ld\n", b.user().c_str(), b.tokens());
    std::printf("a < b: %d, a == a: %d\n", a < b, a == a);
}
$ clang++ -std=c++23 -O2 -Wall -Wextra classes.cpp -o classes && ./classes

Inheritance and virtual functions

A virtual function is chosen at run time by the object's actual type, like every method call in Python. A non-virtual one is chosen at compile time by the declared type, and can be inlined. Making a function virtual adds a hidden pointer to every object (the vtable pointer, pointing to a table of function addresses for that class): the Virtual struct above measured 16 bytes against 8. = 0 makes a function pure virtual: the class is abstract, like a Python ABC.

virtual.cpp
#include <cstdio>
#include <memory>
#include <string>
#include <vector>

struct Tokenizer {                       // a base class with a virtual function
    virtual int count(const std::string& s) const = 0;   // = 0: must be overridden
    virtual ~Tokenizer() = default;      // virtual destructor: required for delete via base
};
struct Whitespace : Tokenizer {
    int count(const std::string& s) const override {
        int n = 0; bool in = false;
        for (char c : s) { bool t = c != ' '; n += t && !in; in = t; }
        return n;
    }
};
struct Bytes : Tokenizer {
    int count(const std::string& s) const override { return static_cast<int>(s.size()); }
};

int main() {
    std::vector<std::unique_ptr<Tokenizer>> ts;
    ts.push_back(std::make_unique<Whitespace>());
    ts.push_back(std::make_unique<Bytes>());
    for (const auto& t : ts)             // which count() runs is decided at run time
        std::printf("%d\n", t->count("hello token world"));
}
$ clang++ -std=c++23 -O2 -Wall -Wextra virtual.cpp -o virtual && ./virtual
3
17

#include <cstdio>

struct Base {
    ~Base() { std::printf("~Base\n"); }          // NOT virtual
};
struct Derived : Base {
    int* buf = new int[100];
    ~Derived() { delete[] buf; std::printf("~Derived\n"); }
};

int main() {
    Base* p = new Derived;
    delete p;    // undefined behaviour: only ~Base runs here, buf leaks
}

Non-virtual destructor: deleting a Derived through a Base* ran only ~Base, so the 400-byte buffer leaked; formally it is undefined behaviour. A base class meant for polymorphic use needs virtual ~Base() = default;.

8. Templates and concepts

Python functions accept anything with the right methods (duck typing), checked when the line runs. A C++ template is a pattern from which the compiler writes a separate function or class for each type you use it with (instantiation, or monomorphisation), checked at compile time. The generated code is as fast as if you had written each version by hand: no boxing, no dispatch.

templates.cpp
#include <cstdio>
#include <string>
#include <vector>

// One template, many functions: the compiler writes a copy per type used.
template <typename T>
T total(const std::vector<T>& xs) {
    T sum{};
    for (const T& x : xs) sum += x;
    return sum;
}

template <typename K, typename V>
struct Pair { K key; V value; };       // a class template

int main() {
    std::printf("%d\n", total(std::vector<int>{1, 2, 3}));
    std::printf("%.1f\n", total(std::vector<double>{0.5, 0.25}));
    std::printf("%s\n", total(std::vector<std::string>{"to", "ken"}).c_str());
    Pair<std::string, long> p{"u0029", 9491};
    std::printf("%s %ld\n", p.key.c_str(), p.value);
}
$ clang++ -std=c++23 -O2 -Wall -Wextra templates.cpp -o templates && ./templates
6

A concept is a named, compile-time predicate on types. Using it in a template's signature makes the compiler check it at the call, and the error names the requirement that failed:

concept_err.cpp
#include <vector>
// A concept names the requirement: T must support += and start from T{}
template <typename T>
concept Summable = requires(T a, T b) { T{}; a += b; };

template <Summable T>
T total(const std::vector<T>& xs) {
    T sum{};
    for (const T& x : xs) sum += x;
    return sum;
}
struct Msg { const char* text; };

int main() {
    std::vector<Msg> msgs{{"hi"}, {"there"}};
    total(msgs);    // rejected at the call, with the reason
}
