Start here

This page teaches C++ to someone who knows Python and has seen only the basics of C++, with three goals: read and write modern C++, understand what the machine does with your code, and read a real inference engine, llama.cpp. It has three parts; pick one with the buttons above. Every output, compiler error, sanitizer report and number comes from a real run on an Apple M1 Pro on 2026-10-05 (LLVM clang 23 for the sanitizers, Apple clang 17 and 14 where stated; llama.cpp pinned at commit 8e16421), and each part's sources and run scripts are in the repository.

Part 1: The language

About 33 minutes, plus drills. Tabs: Reading, Build pipeline, Object lifetimes, UB gallery, Predict the output.
How a C++ program is built (headers, translation units, the linker, CMake), values, references and pointers, the stack and the heap, RAII, smart pointers, move semantics, classes and virtual functions, templates and concepts, the standard library, lambdas, errors, undefined behaviour, and what C++20, 23 and 26 actually ship.

  • Why the build is the first hard part: {{Build pipeline|#t-ca-build}}.

Part 2: The machine underneath

About 40 minutes. Tabs: Reading, Latency ladder, Cache simulator, SIMD lanes, Roofline.
What the CPU and memory do with your code, measured on this M1 Pro: the memory hierarchy, cache lines, data layout, pages and mmap, reading assembly, SIMD, branch prediction, threads, atomics and the memory model, the roofline, profiling, the ABI, and what changes on a GPU.
  • Start: {{Reading|#t-cb-read}}.
  • Why LLM decode is memory-bound: {{Roofline|#t-cb-roof}}.

Part 3: Reading llama.cpp

About 40 minutes. Tabs: Reading, Code tour, Quant blocks, Run it.
A guided reading of a real inference engine: the repo map, the build, the C API, the GGUF file, loading with mmap, ggml tensors and the compute graph, threads, quantised kernels, the KV cache and sampling, the server, and one token timed end to end with a 135M-parameter model.

  • One token's path through 12 files: {{Code tour|#t-cl-tour}}.

Three ways through

"I want to read llama.cpp." Part 1 sections on values and pointers, RAII and ownership, and templates (each llama.cpp excerpt in Part 3 links back to the section that teaches its features), then Part 2 sections on pages and mmap, SIMD and threads, then Part 3. Or start in Part 3 and follow its links back when a feature is new.
"I want to understand the hardware before CUDA." Part 2 in order, then the CUDA topic ({{Topic: cuda-and-gpu-programming|n:3c65c17b0d0d81c39f34d5e070d783c1}}), which owns kernels, CUDA C++ and the GPU memory hierarchy.
"I want to write C++ for real." Part 1 in order, with the {{UB gallery|#t-ca-ub}} and {{Predict the output|#t-ca-drill}} as checks, then Part 2 section on profiling.

Six things the runs showed

FindingWhere
The optimiser changes what buggy code does: a double free crashed at -O0 and vanished at -O2; a data race lost updates at -O0 and gave the right answer at -O2 by luck. Sanitizers catch both.Part 1, UB gallery
Throwing and catching an exception cost about 4.8 µs; returning a std::expected about 1 ns.Part 1, errors
Summing a matrix by columns was 52 to 56 times slower than by rows: same arithmetic, different cache behaviour.Part 2, Cache simulator
Two threads writing counters on the same cache line ran 21 to 22 times slower; padding to 64 bytes still left about 2x, because this M1's lines are 128 bytes.Part 2, threads
On Apple Silicon with the default build, llama.cpp's ggml_vec_dot_* kernels that most guides tell you to read run zero times: weights are repacked at load and 4x4 gemv/gemm kernels do every product.Part 3, quantised kernels
For a model this small, Metal generated tokens more slowly than 4 CPU threads: launching many tiny GPU kernels per token costs more than the work.Part 3, one token timed
