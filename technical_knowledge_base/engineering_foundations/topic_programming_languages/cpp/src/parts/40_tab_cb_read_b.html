1. The memory hierarchy: a ladder of caches

A processor core can do an addition in a fraction of a nanosecond, but fetching a number from main memory (DRAM, the RAM chips) takes about a hundred nanoseconds. To hide that gap the chip keeps copies of recently used memory in caches: small, fast memories close to the core. Each level is bigger and slower than the one before. A register is a slot inside the core itself, where the instructions actually compute; everything else is a cache or memory.

Measuring the ladder: pointer chasing


To time one load you must stop the processor from doing many at once. The trick is a pointer chase: a linked list scattered over a buffer, where each node holds the address of the next. The processor cannot start load k+1 before load k returns, because it does not know the address yet. Divide the time by the number of loads and you have the latency of whatever level holds the buffer. Grow the buffer from 4 KB to 1 GB and you see each level overflow.




The result (random order, run 1; the {{Latency ladder|#t-cb-ladder}} tab draws every point of all three runs and the sequential version):




Read it like this. Up to 128 KB, the size of L1, a load costs about 1 ns: three clock cycles. Past that, the buffer lives in L2 and loads cost 5 to 15 ns. From about 8 MB the numbers climb towards DRAM's roughly 125 ns: a hundred times L1. The steps are not clean because other programs share L2 and DRAM, and because past a few MB the processor also misses in its TLB, the small cache of address translations explained in section 4.

The chase still waits for each load, but the hardware prefetcher notices that addresses go up by 128 bytes each time and fetches the next lines before they are asked for. Predictable access is the cheapest optimisation there is: you get it for free by storing data in the order you read it.

2. Cache lines, and spatial and temporal locality


Caches do not hold single bytes. They hold cache lines: aligned blocks of 128 bytes on this M1 Pro (hw.cachelinesize; 64 on most Intel and AMD processors). Reading one byte brings its whole line into L1. Two habits follow:


    

  • Spatial locality: use the neighbours of what you just read, since they arrived with it. A line of 128 bytes holds 32 floats; reading them in order costs one trip to memory per 32 numbers.
    • 

  • Temporal locality: reuse data soon, before other data evicts it from the cache. Blocked ("tiled") matrix multiplication in section 9 is this idea.
    • 



The classic demonstration: a 4096 x 4096 matrix of 32-bit integers (64 MB) stored row after row, as C++ (and NumPy by default) lay it out. Sum it row by row, then column by column. Same additions, same answer.




Predict. How much slower is the column order? 2x? 10x?



Three runs: x. Going down a column, consecutive elements are 4096 x 4 = 16 KB apart, so every addition needs a new cache line and uses 4 of its 128 bytes; by the time the loop comes back for the neighbouring column, the line has long been evicted. Row order uses every byte of every line, the prefetcher sees a simple stream, and the compiler can even process 4 integers per instruction (section 6). Two effects multiply here: cache lines and SIMD.

a.sum(axis=1) and a.sum(axis=0) on a C-ordered array face exactly this choice; NumPy's reductions are written to walk memory well either way, but your own loops over a[:, j], or a Fortran-ordered array passed to code expecting C order, are not. PyTorch's .contiguous() exists for this reason.
