14. Mistakes when reading or running llama.cpp


Reading the generic kernel and assuming it runs
The function a guide shows (ggml_vec_dot_*) may run zero times: repacking, llamafile's tinyBLAS, BLAS or a GPU backend may take the product. Count calls, or check the log for repack, splits and offloaded lines (sections 5, 8, 10).


Reading shapes in PyTorch order
ne[0] is the innermost, contiguous dimension. A weight that PyTorch calls (out, in) is {in, out} in ggml, and ggml_mul_mat(a, b) computes rows of a times rows of b (section 6).


Thinking a ggml call computes something
ggml_add, ggml_mul_mat and friends only add a node to a graph. Values exist after the graph has been computed; inspect them with an eval callback (llama-eval-callback), not by reading tensor->data right after the call.


Forgetting the default GPU offload
simple.cpp and the tools default to offloading every layer (-ngl 99 or "auto"). On a Mac that means Metal; if you are studying the CPU path, pass -ngl 0 and check the log says no layers were offloaded.


Benchmarking on a busy machine, or with too many threads
The barrier after every operation turns one descheduled thread into a stall for all. Use llama-bench with repetitions (-r 5), look at every sample, record the load average, and try fewer threads than cores (section 9).


Building without Release
A Debug build (-O0) is many times slower and teaches nothing about speed. Always -DCMAKE_BUILD_TYPE=Release for timing; keep a Debug build only for stepping through code in a debugger.


Trusting log labels
model type = 256M for a 135M model (section 5). Logs are written by people; when one looks wrong, grep for its text.


Editing the clone you are measuring
Instrument a copy (as src/cl/code/instrument.py does) and keep the pinned clone clean, so every excerpt and line number stays true to the commit.
