6. ggml tensors: sizes, strides, a pointer

Everything in ggml is a struct ggml_tensor, a plain C struct (no methods, no constructor):

Read it field by field. type is the element type (F32, F16, Q8_0, ...). ne holds up to four sizes, innermost first. nb holds the matching strides in bytes: how far to move in memory to step one along each dimension. data points at the first byte. op and src say how this tensor is computed from others (section 7); view_src and view_offs mark a tensor that borrows another's memory. The element at index (i0, i1, i2, i3) lives at data + i0*nb[0] + i1*nb[1] + i2*nb[2] + i3*nb[3].

That formula is why views are free. A transpose swaps two sizes and their strides and touches no data:

Try it on a real tensor from our run: layer 0's K cache, cache_k_l0, F16 (2 bytes per element), 192 numbers per position for 256 positions. Attention reads it as 3 heads of 64 numbers each, through a 3-dimensional view of the same bytes (section 11 reads the code that makes that view).

From Python
NumPy and PyTorch work the same way: a.strides (NumPy, bytes) or a.stride() (PyTorch, elements), and a.T returns a view with swapped strides. The differences: ggml lists sizes innermost first (PyTorch's (49152, 576) is ggml's {576, 49152}), and a quantised type has no per-element stride: nb[0] is the size of a 32-weight block, so you can only address whole blocks.

Nothing is computed when you call an operation. ggml_mul_mat does not multiply: it creates a result tensor, records op = GGML_OP_MUL_MAT and its two sources, and returns.

The result's sizes are {a->ne[1], b->ne[1], ...}: ggml's matrix product multiplies each row of a (the weight, one output feature per row) by each row of b (one token per row), so both operands are read along their contiguous dimension. Calling operations builds a graph; running it is a separate step (section 8).

From Python
This is tracing, as in torch.compile, torch.fx or jax.jit: calls record a graph of operations; a later step plans memory and runs it. PyTorch's default eager mode is the opposite: each call computes immediately.

7. The model as a graph

Each architecture has a file in src/models/ (157 .cpp files at this commit). Our model is a Llama, so its forward pass is written in src/models/llama.cpp. The class is a template:

C++ features, and why they are here
  • template <bool embed>: one source, two compiled classes. graph<false> generates text, graph<true> computes embeddings. The last two lines of the file force both to be compiled (explicit instantiation) so the template's code can stay in this .cpp file instead of a header. Templates: Part 1 section 8.
  • std::conditional_t<embed, A, B> picks a type at compile time, and if constexpr (embed) picks a branch at compile time: the branch not taken is not compiled into that version at all. Part 1 does not cover these two; the program below shows both.
  • std::unique_ptr / std::make_unique (line 95): the graph object is owned and freed automatically (section 5). Inheritance: graph<embed> derives from llm_graph_context, which holds the shared building blocks (build_norm, build_attn, build_ffn) (section 7).

The attention block of each layer: project to Q, K and V, rotate Q and K by position (RoPE), attend. auto [Qcur, Kcur, Vcur] = build_qkv(...) is a structured binding: the function returns three tensors at once and the line names them (Python's q, k, v = build_qkv(...)).

Then the residual add, the feed-forward block, and after the last layer the output projection, compiled only into graph<false>:

Four features in one place, as llama.cpp uses them, in a program you can compile (src/cl/code/features.cpp): a block size checked by static_assert, an interface written two ways (a C struct of function pointers, as in the sampler and the backends, and a C++ class with virtual functions, as in the KV cache), if constexpr with std::conditional_t, and a structured binding.
