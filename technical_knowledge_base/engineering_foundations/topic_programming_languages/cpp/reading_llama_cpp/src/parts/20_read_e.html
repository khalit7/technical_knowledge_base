9. The CPU backend: threads, barriers, chunks

The CPU backend runs the graph with a pool of threads (4 by default, GGML_DEFAULT_N_THREADS), simply and strictly: every thread walks every node, does its share, then waits at a barrier before the next node. The loop each thread runs:

Views, reshapes and permutes are skipped (ggml_op_is_empty), so of the nodes, are real operations: up to barriers per token, and the slowest thread sets the pace at each.

The barrier in the source, and how an operation splits its work

The barrier is a few atomic operations (a few fewer barriers run when fused operations run as one); a waiting thread spins instead of sleeping, which is fast when every thread has a core and wasteful when it does not. Inside a node, each operation splits its work with two numbers in params: ith, this thread's index, and nth, the number of threads (the root page's {{Design space|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} tab quotes the two lines from ops.cpp).

For matrix products a static split is fragile: if one thread is slow (an efficiency core, or another program takes its core), everyone waits. So the rows are cut into more chunks than threads, and a thread that finishes takes the next chunk from a shared atomic counter; the repacked kernel aims at 4 chunks per thread. Measured with call counters (section 10): every decoded token makes kernel calls = matrix products × chunks (4 threads × 4). Predict: with one thread at half speed, how much later than the others does a fixed four-way split finish?

With chunks off a counter, one slow thread costs a little; with fixed shares it doubles the time

Illustrative durations: thread 3 made slow on purpose; the scheme and the 16 chunks are the real ones (counted).

The chunking code: the generic version and the repacked kernel's

The atomics are memory_order_relaxed: a thread only needs a unique chunk number, not to see other threads' writes in order (memory orders: {{C++: the machine underneath|n:4055c17b0d0d811fa947ee576a97a516}}, section 8).

A real mismatch on this machine
The thread pool aligns its counters to GGML_CACHE_LINE, which is 64 on every platform, but the M1 Pro has 128-byte lines (measured in {{C++: the machine underneath|n:4055c17b0d0d811fa947ee576a97a516}}, section 8). So n_barrier_passed and current_chunk share one 128-byte line, as do n_graph and n_barrier: the false sharing the alignment was meant to prevent. The cost per token was not measured here; it is a reading, not a benchmark.

The dot product, as most guides show it


A matrix-vector product is one dot product per weight row. ggml quantises the activations to Q8_0 too, so the inner loop multiplies 8-bit integers and applies the two scales once per block. In the NEON version of ggml_vec_dot_q8_0_q8_0, ggml_vdotq_s32 is the SDOT instruction: 16 byte pairs multiplied and summed in groups of four into four 32-bit lanes, 16 multiply-adds in one instruction.


The portable reference version and the NEON version, read line by line


vld1q_s8 loads 16 signed bytes into one 128-bit register. The repacked block is a template with two integer parameters (block<8, 4>, a distinct type computed at compile time, which C cannot express): 4 rows' scales and their 32 weights each, interleaved 4 bytes at a time (136 bytes). Each iteration loads 128 weight bytes and the activation block once, and vdotq_laneq_s32 multiplies 4 activation bytes (one "lane" of a register) against 4 bytes of each of the 4 rows: 16 multiply-adds, 4 rows advanced together; eight cover the block, one fused multiply-add applies the scales. Against vec_dot, the activation is loaded once per 4 rows instead of once per row, and the weights stream from one contiguous buffer: fewer loads per multiply, which is what the repack copy buys.
