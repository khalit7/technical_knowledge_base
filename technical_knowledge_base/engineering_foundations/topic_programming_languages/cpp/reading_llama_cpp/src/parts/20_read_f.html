11. KV cache, batches and sampling

What the KV cache is and why it exists is taught by {{Batching, KV cache and scheduling|n:3c65c17b0d0d819db53bd2c48909e5b2}} (and how it grows with context by {{Long context|n:3fd5c17b0d0d81059ee1ce20c0326dc5}}); here is how llama.cpp writes it. It is a C++ class with virtual functions behind an abstract interface, llama_memory_i (a plain cache, a sliding-window one, one for recurrent models), storing one K and one V tensor per layer. Writing this token's K is a SET_ROWS node into the cells chosen for this batch; reading K for attention is a 4-dimensional view of the same tensor (section 6), {64, 3, 256} in our trace: 64 numbers per head, 3 KV heads, 256 cells.

The class declaration and the SET_ROWS write, in the source

Size, from the log: KV buffer size = MiB = 2 (K and V) × 30 layers × cells × 192 numbers × 2 bytes (F16) = bytes. simple.cpp asked for a context of 12 tokens (prompt + 8 − 1); the context rounds it up to cells (cparams.n_ctx = GGML_PAD(cparams.n_ctx, 256); in llama-context.cpp).

Batches. A batch is a list of tokens, each with a position, a sequence id (which conversation) and a flag saying whether its logits are wanted; simple.cpp wants only the last token's, which lets the graph drop the other rows before the output projection.

The batch helper in simple.cpp

Sampling (the rules: {{Sampling and decoding|n:3c65c17b0d0d8115bafcda29a2c7086e}}). Samplers are C style, each filling in a struct of function pointers. Greedy takes the highest logit:

The sampler interface and greedy's table of function pointers

So one codebase writes interfaces two ways: the KV cache as a C++ class with virtual functions, samplers and backends as C structs of function pointers, because they are part of the C API other languages call (section 7's small program does both side by side).

12. The server

llama-server (in tools/server/, 20,000 lines of C++) serves the model over HTTP with an OpenAI-compatible API (its options, slots and modes, measured: {{Local and on-device inference|n:3c65c17b0d0d81f7a144fe25d799e811}}, section 6). Several requests share one context, each in a slot (a C++ struct with owning smart pointers), and every step puts the next token of every active slot into one batch (continuous batching: {{Batching, KV cache and scheduling|n:3c65c17b0d0d819db53bd2c48909e5b2}}). The step calls the same llama_process as simple.cpp, inside a lambda capturing by reference ([&]), handed to the task queue so metrics requests are answered while the model runs:
