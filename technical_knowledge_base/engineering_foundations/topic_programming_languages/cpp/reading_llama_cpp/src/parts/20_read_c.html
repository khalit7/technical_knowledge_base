4. GGUF: reading the model file

GGUF is llama.cpp's one-file model format: weights plus architecture, tokenizer and chat template. What it holds and how it compares with safetensors belong to {{Local and on-device inference|n:3c65c17b0d0d81f7a144fe25d799e811}} (section 3); here we read it as code. Every integer has a fixed width and is little-endian, and a string is a 64-bit length then the bytes, so any language reads it: a complete reader is 41 lines of Python, standard library only.

Three details matter in the C++ that consumes it. Shapes are stored innermost first: token_embd.weight has ne=[576, 49152] where PyTorch says (49152, 576). Offsets are relative to the start of the data section, which begins at byte , the end of the header rounded up to the alignment of 32 (so every tensor can be loaded with aligned SIMD reads). C++ in gguf.cpp
A gguf_reader struct with overloaded read() functions per type, std::vector and std::string for the values, behind a C API. Reads whose length comes from the file sit in try/catch (std::bad_alloc &) and every count is checked against SIZE_MAX before allocating, because a corrupt or malicious file can claim a string of 263 bytes: untrusted binary input is where C and C++ code gets exploited (undefined behaviour, {{C++: the essentials|n:3cd5c17b0d0d81ceadcee44fe9c023a0}}).


Predict. The model has 134.5 million parameters stored mostly as Q8_0. Before looking: is the file bigger or smaller than 134.5 million bytes, and by roughly how much?


Bigger:  bytes. Q8_0 spends 34 bytes on 32 weights (8.5 bits each, the scale costs the extra half bit), 61 small norm vectors stay in 32-bit float, and the header adds 1.8 MB. The loader reports 8.51 BPW (bits per weight).







5. Loading: mmap, then a surprise copy


llama_model_load_from_file reads the header, creates one ggml tensor per weight, and does not read the 143 MB of weights: it maps the file, so nothing is read until a page is touched and a second process mapping the same model shares the pages (mmap: {{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}}; mapped against read, measured: {{Local and on-device inference|n:3c65c17b0d0d81f7a144fe25d799e811}}, section 3). Each tensor then points straight into the mapping:




(uint8_t *) mapping->addr() + weight->offs is pointer arithmetic: the base address of the mapped file plus the tensor's offset, cast to bytes so that adding offs moves offs bytes. No copy, no allocation. The std::async lambda is an optional parallel check of the bytes.


Now grep the log, and the code explains each surprising line. The first one:


    

  • CPU_REPACK model buffer size = 136.27 MiB. A second copy of almost all the weights: at load the CPU backend copies every Q8_0 matrix into an interleaved layout, four rows woven together, because its fastest kernel reads four rows in one stream (section 10). The layout is picked at run time from the processor's features: the M1 has dotprod (the SDOT instruction) but not i8mm (sysctl hw.optional.arm: FEAT_DotProd: 1, FEAT_I8MM: 0), so 4x4.

Two more log lines explained: the weights not repacked, and a 135M model labelled 256M; the log and the source


    

  • token_embd.weight (q8_0) (and 61 others) cannot be used with ... CPU_REPACK. The 61 others are the 32-bit norm vectors. The embedding table stays in the mapping because row lookups (GET_ROWS: fetch row number token id) need the plain layout; the output projection tied to it is created a second time (TENSOR_DUPLICATED) and that copy, used for a matrix product, is repacked.
    • 

  • model type = 256M for a 135M model. The label is a guess from the number of layers: 30 layers is SmolDocling's size, so every 30-layer Llama-style model is labelled 256M. A cosmetic bug, but a good habit: when a log line surprises you, find the code that printed it.

Predict. With repacking, how much memory do the weights take in total, and what happens to the mapped copy of the repacked tensors?


 MiB mapped plus  MiB repacked: about twice the file. The repacked copy is ordinary allocated memory. The mapped pages of those tensors were read once, during the copy, and then only sit in the OS file cache, which the OS may evict under pressure; the embedding table ( MiB) stays in use from the mapping. On a phone or a full laptop, --repack 0 (in llama-bench; use_extra_bufts = false in the API) trades that copy for a slower kernel.
