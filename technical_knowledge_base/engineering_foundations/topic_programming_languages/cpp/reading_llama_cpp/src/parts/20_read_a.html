The idea in one sentenceOne generated token is a ggml graph: libllama builds it once from the model file, ggml plans its memory once, and a pool of threads walks it node by node, spending its arithmetic in one SIMD kernel that reads weights repacked at load time, a kernel most guides never mention.

One token goes down through libllama and ggml to a single SIMD kernel, then back up to the sampler

One decoded token on the CPU (SmolLM2-135M in Q8_0, 4 threads, Apple M1 Pro): each layer, the file that does the work, and what was counted there measured. The sections below open each box; section 13 walks the same path stop by stop.

ggml: llama.cpp's tensor library: tensors, the compute graph, the file format and the backends.
Backend: the code that runs operations on one device (CPU, Metal, CUDA, BLAS).
Graph, node: the recorded forward pass; each node is one operation on tensors.
ne, nb: a ggml tensor's sizes and byte strides, innermost dimension first.
Split: a run of consecutive nodes on one backend, with copies between splits.
Repack: copying quantised weights at load into an interleaved layout for a faster CPU kernel.
Chunk: a slice of a matrix product's rows that a thread takes from a shared atomic counter.
Barrier: a point no thread passes until all have arrived; one after every operation.
Q8_0 block: 32 weights as 8-bit integers sharing one 16-bit scale, 34 bytes.
Slot: one request in progress inside llama-server.

The surprise of this tour
Guides (and older notes in this knowledge base) say: to see the hot loop, read ggml_vec_dot_q4_0_q8_0 or ggml_vec_dot_q8_0_q8_0. On this M1 with the default build, call counters show those functions run zero times: the weights are rearranged at load time and a different kernel, ggml_gemv_q8_0_4x4_q8_0, does all matrix products of each new token, in calls (section 10). Reading code is not enough; check what runs.
