6. ggml tensors: sizes, strides, a pointer

Everything in ggml is a struct ggml_tensor, a plain C struct (no methods, no constructor):

ne holds up to four sizes, innermost first (ne[0] is the dimension whose elements are adjacent in memory); nb the matching strides in bytes; data the first byte; op and src say how this tensor is computed from others (section 7); view_src and view_offs mark a tensor that borrows another's memory. Element (i0, i1, i2, i3) lives at data + i0*nb[0] + i1*nb[1] + i2*nb[2] + i3*nb[3], which is why views are free: a transpose swaps two sizes and their strides and touches no data.

A real tensor from our run: layer 0's K cache, cache_k_l0, F16, 192 numbers per position for 256 positions, which attention reads as 3 heads of 64 through a view of the same bytes (section 11). Predict the byte offset where head 1 starts, then switch.

NumPy's a.strides (bytes) and PyTorch's a.stride() (elements) are the same idea, and a.T is the same free view. Two differences: sizes innermost first (a weight PyTorch calls (out, in) is {in, out}), and a quantised type has no per-element stride: nb[0] is the size of a 32-weight block, so only whole blocks are addressable.

Nothing is computed when you call an operation. ggml_mul_mat does not multiply: it creates a result tensor, records op = GGML_OP_MUL_MAT and its two sources, and returns.

The result is {a->ne[1], b->ne[1], ...}: each row of a (the weight, one output feature per row) times each row of b (one token per row), so both operands are read along their contiguous dimension. Calling operations builds a graph; running it is section 8, and values exist only after it runs.

From Python
This is tracing, as in torch.compile, torch.fx or jax.jit: calls record a graph of operations; a later step plans memory and runs it. PyTorch's default eager mode is the opposite: each call computes immediately.

7. The model as a graph

Each architecture has a file in src/models/ (157 .cpp files at this commit). Our model is a Llama, so its forward pass is written in src/models/llama.cpp. The class is a template:

C++ features, and why they are here
  • template <bool embed>: one source, two compiled classes, graph<false> for text and graph<true> for embeddings. The last two lines force both to be compiled (explicit instantiation) so the code can stay in this .cpp instead of a header (templates: {{C++: classes, templates and the standard library|n:4055c17b0d0d818a9509f6035089a7e1}}).
  • std::conditional_t<embed, A, B> picks a type at compile time, and if constexpr (embed) picks a branch at compile time: the branch not taken is not compiled into that version at all.
  • std::unique_ptr / std::make_unique (line 95): the graph object is owned and freed automatically. Inheritance: graph<embed> derives from llm_graph_context, which holds the shared building blocks (build_norm, build_attn, build_ffn).
  • Structured binding: auto [Qcur, Kcur, Vcur] = build_qkv(...) names the three tensors a function returns (Python's q, k, v = build_qkv(...)).

Four features in one small program you can compile, and what static_assert buys

Four features as llama.cpp uses them (src/cl/code/features.cpp): a block size checked by static_assert, an interface written two ways (a C struct of function pointers, as in the sampler and the backends, and a C++ class with virtual functions, as in the KV cache), if constexpr with std::conditional_t, and a structured binding.

8. From graph to memory to compute


llama_process, the C entry point, forwards to llama_context::decode, which splits the batch into micro-batches, finds KV cache room for them, and calls process_ubatch for each: build the graph (or reuse the last one), allocate it, copy the inputs in, compute.


llama_process and process_ubatch in the source








Graph reuse. For the next token the graph is the same except for its inputs, so can_reuse checks that the shapes match and, if they do, only set_inputs runs. Our run logged graphs reused = : the prompt's graph was built, the first one-token graph was built, and the other 6 decoding steps reused it.


Memory planning. The allocator (ggml-alloc.c) gives every intermediate an address in one buffer: walking the nodes in order, it counts how many later nodes still read each tensor, and when the count reaches zero the memory goes to the next node. From the log: CPU compute buffer size =  MiB for every intermediate of a forward pass, against 143 MB of weights. The plan is made once (sched_reserve, at context creation, for the worst case) and reused.

This is CPython's reference counting, done ahead of time: a tensor is freed when the last operation that uses it has run. PyTorch's caching allocator does it at run time, as tensors go out of scope.


The scheduler and backends. A backend is an object that can run operations on one device. In C, "an object with methods" is a struct of function pointers, one per method, filled in differently by each backend:




The scheduler (ggml_backend_sched) sends each node to the backend that already holds its data, so operations on weights go where the weights are, and cuts the graph into splits, runs of consecutive nodes on one backend with copies between them. With repacking off and a 64-token prompt, the graph is cut into  pieces: each large matrix product goes to the BLAS backend (Accelerate), the rest stays on the CPU. With repacking on, the weights live in a buffer only the CPU backend understands: 1 split.
