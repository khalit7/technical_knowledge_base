C++: reading llama.cpp, one token through the code

A guided reading of a real C/C++ inference engine: build it, run a small model, and follow one token from the prompt to the sampled word through the model file, the ggml graph, the scheduler, the thread pool and the SIMD kernel that really runs, with every excerpt pinned to one commit and every count measured on an Apple M1 Pro. Reading: 33 min, plus 36 in closed details. Data as of October 2026.
The idea in one sentenceOne generated token is a ggml graph: libllama builds it once from the model file, ggml plans its memory once, and a pool of threads walks it node by node, spending its arithmetic in one SIMD kernel that reads weights repacked at load time, a kernel most guides never mention.

One token goes down through libllama and ggml to a single SIMD kernel, then back up to the sampler

One decoded token on the CPU (SmolLM2-135M in Q8_0, 4 threads, Apple M1 Pro): each layer, the file that does the work, and what was counted there measured. The sections below open each box; section 13 walks the same path stop by stop.

You need: the build and libraries (C++: the essentials); unique_ptr and RAII (C++: ownership, moves and object lifetimes); templates, virtual functions, lambdas (C++: classes, templates and the standard library); cache lines, SIMD, atomics (C++: the machine underneath). What the code computes (attention, the KV cache, batching, quantisation error) is taught by Topic: inference-and-serving, Local and on-device inference and Quantization and precision; this page reads how it is built.

1. The map: what is where

A codebase of a million lines is read like a city: first the districts, then one street. llama.cpp has two libraries and a ring of programs around them.

  • ggml/, the tensor library: tensors, the compute graph, the file format, and one backend per kind of hardware (CPU, Metal, CUDA, Vulkan and others). Its core is C; most backends are C++ (Metal adds Objective-C and Metal shading language, CUDA adds .cu files).
  • src/, libllama: everything that knows what an LLM is: loading a model file, one graph builder per architecture in src/models/, the KV cache, batches, the tokenizer, samplers. All C++.
  • include/llama.h, the public C API (1,774 lines): every program, and every binding from Python, Go or Swift, goes through it.
The rest of the tree

common/ (argument parsing, chat templates, helpers shared by the tools), tools/ (llama-cli, llama-server, llama-bench, llama-quantize), examples/ (small programs; simple/simple.cpp is the one to read first), gguf-py/ (the Python package that writes model files), tests/ and vendor/ (third-party code such as the HTTP library).

Half the code is C++, and the CPU backend alone is about 95,000 lines of hand-vectorised kernels

Lines per area, counted with git ls-files at the pinned commit (src/cl/code/repo_map.py). Hover or tap a bar.

Of lines, are C++ and C, plus headers shared by both; of the CPU backend's lines, mostly hand-vectorised kernels for each processor family, you will read about 200.

From Python
It is the same shape as PyTorch: a Python API (torch/) over a C++ tensor library (ATen) with one backend per device. Here the "Python API" is the C header llama.h, and the tensor library is ggml. The Python package llama-cpp-python wraps exactly that header with ctypes.

How to read it: start from the smallest program that works (examples/simple/simple.cpp), follow each call one level down with grep -rn "name(" src ggml, skip every backend you are not running, and read declarations in headers before definitions. When a log line puzzles you, grep for its text: the code that printed it is the explanation (section 5).

4. GGUF: reading the model file


GGUF is llama.cpp's one-file model format: weights plus architecture, tokenizer and chat template. What it holds and how it compares with safetensors belong to Local and on-device inference (section 3); here we read it as code. 5. Loading: mmap, then a surprise copy


llama_model_load_from_file reads the header, creates one ggml tensor per weight, and does not read the 143 MB of weights: it maps the file, so nothing is read until a page is touched and a second process mapping the same model shares the pages (mmap: Virtual memory; mapped against read, measured: Local and on-device inference, section 3). Each tensor then points straight into the mapping:




(uint8_t *) mapping->addr() + weight->offs is pointer arithmetic: the base address of the mapped file plus the tensor's offset, cast to bytes so that adding offs moves offs bytes. No copy, no allocation. The std::async lambda is an optional parallel check of the bytes.


Now grep the log, and the code explains each surprising line. The first one:


    

  • CPU_REPACK model buffer size = 136.27 MiB. A second copy of almost all the weights: at load the CPU backend copies every Q8_0 matrix into an interleaved layout, four rows woven together, because its fastest kernel reads four rows in one stream (section 10). The layout is picked at run time from the processor's features: the M1 has dotprod (the SDOT instruction) but not i8mm (sysctl hw.optional.arm: FEAT_DotProd: 1, FEAT_I8MM: 0), so 4x4.

6. ggml tensors: sizes, strides, a pointer


Everything in ggml is a struct ggml_tensor, a plain C struct (no methods, no constructor):




ne holds up to four sizes, innermost first (ne[0] is the dimension whose elements are adjacent in memory); nb the matching strides in bytes; data the first byte; op and src say how this tensor is computed from others (section 7); view_src and view_offs mark a tensor that borrows another's memory. Element (i0, i1, i2, i3) lives at data + i0*nb[0] + i1*nb[1] + i2*nb[2] + i3*nb[3], which is why views are free: a transpose swaps two sizes and their strides and touches no data.


A real tensor from our run: layer 0's K cache, cache_k_l0, F16, 192 numbers per position for 256 positions, which attention reads as 3 heads of 64 through a view of the same bytes (section 11). Predict the byte offset where head 1 starts, then switch.




Three views, one buffer: only the strides change










ggml_transpose in the source


From Python
NumPy's a.strides (bytes) and PyTorch's a.stride() (elements) are the same idea, and a.T is the same free view. Two differences: sizes innermost first (a weight PyTorch calls (out, in) is {in, out}), and a quantised type has no per-element stride: nb[0] is the size of a 32-weight block, so only whole blocks are addressable.


Nothing is computed when you call an operation. ggml_mul_mat does not multiply: it creates a result tensor, records op = GGML_OP_MUL_MAT and its two sources, and returns.




The result is {a->ne[1], b->ne[1], ...}: each row of a (the weight, one output feature per row) times each row of b (one token per row), so both operands are read along their contiguous dimension. Calling operations builds a graph; running it is section 8, and values exist only after it runs.


From Python
This is tracing, as in torch.compile, torch.fx or jax.jit: calls record a graph of operations; a later step plans memory and runs it. PyTorch's default eager mode is the opposite: each call computes immediately.

Memory planning. The allocator (ggml-alloc.c) gives every intermediate an address in one buffer: walking the nodes in order, it counts how many later nodes still read each tensor, and when the count reaches zero the memory goes to the next node. 9. The CPU backend: threads, barriers, chunks


The CPU backend runs the graph with a pool of threads (4 by default, GGML_DEFAULT_N_THREADS), simply and strictly: every thread walks every node, does its share, then waits at a barrier before the next node. The loop each thread runs:




Views, reshapes and permutes are skipped (ggml_op_is_empty), so of the  nodes,  are real operations: up to  barriers per token, and the slowest thread sets the pace at each.


The barrier in the source, and how an operation splits its work


The barrier is a few atomic operations (a few fewer barriers run when fused operations run as one); a waiting thread spins instead of sleeping, which is fast when every thread has a core and wasteful when it does not. Inside a node, each operation splits its work with two numbers in params: ith, this thread's index, and nth, the number of threads (the root page's Design space tab quotes the two lines from ops.cpp).


For matrix products a static split is fragile: if one thread is slow (an efficiency core, or another program takes its core), everyone waits. So the rows are cut into more chunks than threads, and a thread that finishes takes the next chunk from a shared atomic counter; the repacked kernel aims at 4 chunks per thread. Measured with call counters (section 10): every decoded token makes  kernel calls =  matrix products ×  chunks (4 threads × 4). Predict: with one thread at half speed, how much later than the others does a fixed four-way split finish?




With chunks off a counter, one slow thread costs a little; with fixed shares it doubles the time









Illustrative durations: thread 3 made slow on purpose; the scheme and the 16 chunks are the real ones (counted).




The chunking code: the generic version and the repacked kernel's








The atomics are memory_order_relaxed: a thread only needs a unique chunk number, not to see other threads' writes in order (memory orders: C++: the machine underneath, section 8).

10. Quantised blocks and the kernels that read them


A quantised type stores weights in blocks: 32 weights share one scale d, and each weight is a small integer q, with weight ≈ d × q. Why quantise, the block types and what they cost in accuracy belong to Quantization and precision and Local and on-device inference (section 4, which also draws the k-quant block); here we read the code. The blocks are plain C structs:

The dot product, as most guides show it


A matrix-vector product is one dot product per weight row. ggml quantises the activations to Q8_0 too, so the inner loop multiplies 8-bit integers and applies the two scales once per block. In the NEON version of ggml_vec_dot_q8_0_q8_0, ggml_vdotq_s32 is the SDOT instruction: 16 byte pairs multiplied and summed in groups of four into four 32-bit lanes, 16 multiply-adds in one instruction.


The portable reference version and the NEON version, read line by line


vld1q_s8 loads 16 signed bytes into one 128-bit register. Two blocks per iteration, two accumulators (sumv0, sumv1), so two chains of additions run in parallel: the same tricks as the NEON dot product in C++: the machine underneath (section 6), which uses float lanes where this uses bytes. GGML_RESTRICT is C's restrict: a promise that x and y do not overlap, so the compiler need not reload after each store.

The weights were repacked at load (section 5), so every product goes to ggml_gemv_q8_0_4x4_q8_0 ("matrix times vector", four interleaved rows per step) for single rows and ggml_gemm_q8_0_4x4_q8_0 for groups of four token rows. The loop that really did the work for every token on this page:




The repacked block is a template with two integer parameters (block<8, 4>, a distinct type computed at compile time, which C cannot express): 4 rows' scales and their 32 weights each, interleaved 4 bytes at a time (136 bytes). Each iteration loads 128 weight bytes and the activation block once, and vdotq_laneq_s32 multiplies 4 activation bytes (one "lane" of a register) against 4 bytes of each of the 4 rows: 16 multiply-adds, 4 rows advanced together; eight cover the block, one fused multiply-add applies the scales. Against vec_dot, the activation is loaded once per 4 rows instead of once per row, and the weights stream from one contiguous buffer: fewer loads per multiply, which is what the repack copy buys.

11. KV cache, batches and sampling


What the KV cache is and why it exists is taught by Batching, KV cache and scheduling (and how it grows with context by Long context); here is how llama.cpp writes it. It is a C++ class with virtual functions behind an abstract interface, llama_memory_i (a plain cache, a sliding-window one, one for recurrent models), storing one K and one V tensor per layer. Writing this token's K is a SET_ROWS node into the cells chosen for this batch; reading K for attention is a 4-dimensional view of the same tensor (section 6), {64, 3, 256} in our trace: 64 numbers per head, 3 KV heads, 256 cells.
