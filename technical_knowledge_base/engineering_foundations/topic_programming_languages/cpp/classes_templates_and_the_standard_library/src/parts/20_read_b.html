3. Templates and concepts: generic code resolved at compile time

A Python function accepts anything with the right methods (duck typing), checked when the line runs. A C++ template is a pattern from which the compiler writes a separate function or class for each type you use it with (instantiation, or monomorphisation), checked at compile time. Each generated function is as fast as if you had written it by hand: no boxing, no dispatch, and the compiler can inline and vectorise it. That is the "decided at compile time" lane of the hero.

templates.cpp (lines 5 to 14)
// One template, many functions: the compiler writes a copy per type used.
template <typename T>
T total(const std::vector<T>& xs) {
    T sum{};
    for (const T& x : xs) sum += x;
    return sum;
}

template <typename K, typename V>
struct Pair { K key; V value; };       // a class template

A concept is a named, compile-time predicate on types. Put it in a template's signature and the compiler checks it at the call, and the error names the requirement that failed:

concept_err.cpp (lines 2 to 11)
// A concept names the requirement: T must support += and start from T{}
template <typename T>
concept Summable = requires(T a, T b) { T{}; a += b; };

template <Summable T>
T total(const std::vector<T>& xs) {
    T sum{};
    for (const T& x : xs) sum += x;
    return sum;
}

4. The standard library you will actually use

The standard library ("the STL") is C++'s built-ins plus collections and itertools. On macOS it is LLVM's libc++; on Linux usually GCC's libstdc++; on Windows Microsoft's STL. The interfaces are standard; the sizes, growth factors and string buffers below are libc++'s, measured. The defaults: vector, string, unordered_map; string_view and span as parameters; algorithms over hand-written loops.

std::vector: one buffer that moves when it grows

A growable array, like a Python list, except that it holds the elements themselves, contiguously, not pointers to objects; that is why section 2's flat vector beat every pointer layout. Use it unless you have measured a reason not to. Growth is geometric, so push_back is cheap on average:

Capacity doubles; each step is a new buffer, and every old pointer into the vector dangles

The real output of vector_growth.cpp (libc++): the size at which each new buffer was allocated, and its capacity. At every step all elements move to the new buffer and the old one is freed, so every pointer, reference and iterator into the old buffer now dangles (the essentials page's UB gallery runs that bug). If you know the final size, call reserve(n) first: one allocation, no moves. Whether the elements are moved or copied at each step depends on noexcept, replayed on {{the ownership page|n:4055c17b0d0d81819d74fa010e68ac2a}}.

std::string and std::string_view

std::string owns a growable byte buffer. Short strings are stored inside the 24-byte object itself (the small-string optimisation, SSO), so they need no heap allocation; std::string_view is a pointer and a length into characters owned by someone else, so passing one never copies.

Maps, spans and algorithms

containers.cpp (lines 15 to 34)
int main() {
    std::unordered_map<std::string, long> per_user;   // Python's dict
    const char* users[] = {"u0029", "u0005", "u0029", "u0042", "u0005", "u0029"};
    const long tokens[] = {10, 7, 5, 9, 1, 3};
    for (int i = 0; i < 6; ++i) per_user[users[i]] += tokens[i];  // [] inserts 0 if missing

    std::printf("contains u0099? %d (contains() does not insert)\n", per_user.contains("u0099"));
    long& ref = per_user["u0099"];                    // operator[] DOES insert
    std::printf("after per_user[\"u0099\"]: size %zu, value %ld\n", per_user.size(), ref);

    std::vector<std::pair<std::string, long>> rows(per_user.begin(), per_user.end());
    std::ranges::sort(rows, [](const auto& a, const auto& b) {
        return a.second != b.second ? a.second > b.second : a.first < b.first;  // count desc, id asc
    });
    for (const auto& [user, n] : rows) std::printf("%s %ld\n", user.c_str(), n);  // structured binding

    std::vector<long> v{3, 1, 4, 1, 5};
    long arr[] = {9, 2, 6};
    std::printf("sum(v)=%ld sum(arr)=%ld sum(first 2 of v)=%ld\n",
                sum(v), sum(arr), sum(std::span(v).first(2)));

  • std::unordered_map is a hash table like dict, but unordered (no insertion order), and its [] inserts a default value when the key is missing, so it cannot be used on a const map. Python's dict raises KeyError; C++ silently grows. Use contains or find to look without inserting. std::map is a sorted tree.
  • std::ranges::sort(rows, cmp) sorts with your comparison; the lambda gives the root page's tie-break: count descending, then user id ascending. auto& [user, n] is a structured binding: tuple unpacking.
  • One sum(std::span<const long>) accepted a vector, a plain array and a slice of the vector, with no copies.

Ranges: lazy pipelines, like generators

C++20 ranges compose lazily, like Python generators: views::filter, views::transform and views::take build a pipeline that computes nothing until a loop pulls from it. The prints inside the lambdas record the order of evaluation; step through them.

ranges.cpp (lines 6 to 13)
    std::vector<int> counts{12, 0, 7, 31, 0, 5, 18};
    // A lazy pipeline: nothing runs until the loop pulls values (like a Python generator)
    auto pipeline = counts
        | std::views::filter([](int n) { std::printf("  filter %d\n", n); return n > 0; })
        | std::views::transform([](int n) { std::printf("  square %d\n", n); return n * n; })
        | std::views::take(2);
    std::printf("pipeline built, nothing computed yet\n");
    for (int x : pipeline) std::printf("got %d\n", x);

Predict first: the loop takes 2 values from 7 counts. How many counts get filtered, and how many squared?







Only what the loop needed was computed: 31 was filtered but never squared (taking the second value advanced the filter to look for a third before take said stop), and 5 and 18 were never touched. C++23's std::ranges::to<std::vector>() collects a pipeline into a container, like list(gen). A view does not own its data, so a view of a temporary container dangles, just as a string_view does.
