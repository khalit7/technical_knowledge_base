5. Lambdas: a closure is an object you can measure

A lambda is an inline function, like Python's lambda but with statements allowed. The square brackets say which outside variables it captures and how: [x] copies x when the lambda is created; [&x] refers to the variable itself; [=] and [&] capture everything used, by copy or by reference.

lambdas.cpp (lines 6 to 10)
    int threshold = 10;
    auto by_value = [threshold](int n) { return n > threshold; };   // copies threshold now
    auto by_ref   = [&threshold](int n) { return n > threshold; };  // refers to the variable
    threshold = 100;
    std::printf("by_value(50)=%d by_ref(50)=%d\n", by_value(50), by_ref(50));

Python closures always capture variables by reference and keep them alive. A C++ reference capture keeps nothing alive, so a lambda that outlives the function it was made in (returned, stored, or given to a thread) must capture by value; [&] in an escaping lambda is the essentials page's "dangling capture" bug, and capturing this has the same problem with the object. A lambda passed to a template (std::ranges::sort(rows, cmp)) is inlined like any template code: it costs nothing. Stored in a std::function, it pays a type-erased indirect call, and with mixed callables section 2 measured that at 6.01 ns per call; templates and auto parameters avoid it.

6. Errors: exceptions against std::expected, measured

C++ has three ways to say "this did not work", and real code uses all three:

  • Exceptions work like Python's: throw, try/catch, unwinding that runs destructors on the way ({{the ownership page|n:4055c17b0d0d81819d74fa010e68ac2a}} replays it). Use them for errors the immediate caller cannot handle: a missing config file, out of memory.
  • std::optional<T> (C++17) is "a T or nothing", like returning None, with no reason attached.
  • std::expected<T, E> (C++23) is "a T or an error E", like Rust's Result. The caller must look; transform and and_then chain steps that run only on success. Use it for failures that are part of normal operation: parsing user input, a malformed JSONL line.
errors.cpp (lines 26 to 34)
// 3. expected (C++23): "a value or an error", like Rust's Result
enum class ParseError { empty, not_a_number };
std::expected<long, ParseError> parse_exp(std::string_view s) {
    if (s.empty()) return std::unexpected(ParseError::empty);
    long v = 0;
    auto [p, ec] = std::from_chars(s.data(), s.data() + s.size(), v);
    if (ec != std::errc{} || p != s.data() + s.size()) return std::unexpected(ParseError::not_a_number);
    return v;
}

long parse_or_throw(std::string_view s) {
    long v = 0;
    auto [p, ec] = std::from_chars(s.data(), s.data() + s.size(), v);
    if (ec != std::errc{} || p != s.data() + s.size())
        throw std::invalid_argument("not a number: " + std::string(s));
    return v;
}

// 2. optional: "a value or nothing", no reason given (like returning None)
std::optional<long> parse_opt(std::string_view s) {
    long v = 0;
    auto [p, ec] = std::from_chars(s.data(), s.data() + s.size(), v);
    if (ec != std::errc{} || p != s.data() + s.size()) return std::nullopt;
    return v;
}

Compilers implement exceptions with tables that are read only when something is thrown ("zero-cost" exceptions, which still cost binary size). So the success path should be almost free and a throw expensive. How expensive, and when does it matter? The benchmark calls one tiny function written both ways, and varies the share of calls that fail.

Predict, then drag: at what failure rate does the exception version cost twice the expected version? At what rate ten times?

ns per call, log scale, the median of three runs at each of the six measured rates (the slider has no in-between values). Depth 1: the error is handled by the direct caller. Apple M1 Pro, Apple clang 17, -O2.

The rates tell the rule. With no failures the exception version cost 1.61 ns per call against 0.96 (both functions are out-of-line calls; this benchmark does not explain the 0.6 ns gap). At 1 failure in 10,000 it was 2.19 ns; at 1 in 1,000, 6.64; at 1 in 100, 50.79, about 50 times the expected version, which stayed at 0.96 ns at every rate because returning an error is just returning a value. A simple model fits every row: cost per call = success path + failure rate × the cost of one throw, about 4,799 ns (derived from the 50% row). So exceptions for rare failures, expected or optional where failure is common.

How far the error travels

A throw also grows with the number of stack frames it unwinds: the runtime walks each frame's table and runs its destructors. The second sweep makes the error cross 1 to 64 nested calls before it is handled:

A throw pays per frame unwound; an expected pays only the ordinary return

Failure path, ns per call, log scale, medians of three runs. The expected version checks and returns the error at every level; its cost is the same as its success path at that depth (the calls themselves). The throw went from 5,760 ns at depth 1 to 50,586 at depth 64: about 712 ns per frame.

On the success path the two styles cost the same at depth: at 64 frames 329.11 against 321.37 ns, set by the 64 calls, not by the error handling. The one check per level that expected adds is noise beside the call it follows.

exc_cost.cpp (lines 10 to 27)
__attribute__((noinline)) int f_throw(int i) { if (i < 0) throw std::runtime_error("neg"); return i; }
__attribute__((noinline)) std::expected<int, int> f_exp(int i) { if (i < 0) return std::unexpected(1); return i; }

// The error crosses `d` frames: each level calls the next; only the top handles it.
// The empty asm after each call keeps every frame real (clang would otherwise turn the recursion into a loop).
__attribute__((noinline)) int deep_throw(int d, int i) {
    if (d == 0) return f_throw(i);
    int r = deep_throw(d - 1, i);
    asm volatile("");
    return r + 1;
}
__attribute__((noinline)) std::expected<int, int> deep_exp(int d, int i) {
    if (d == 0) return f_exp(i);
    auto r = deep_exp(d - 1, i);
    asm volatile("");
    if (!r) return r;            // every level checks and passes the error up
    return *r + 1;
}

Some codebases (game engines, parts of Google's, many embedded ones) compile with exceptions turned off, and ggml, the C core under llama.cpp, reports errors with return values and assertions, since C has no exceptions. Mark functions that never throw noexcept, above all move constructors and destructors ({{the ownership page|n:4055c17b0d0d81819d74fa010e68ac2a}} shows why a vector needs it), and add [[nodiscard]] to a function returning expected, so ignoring the result is a warning.

Rule of thumbExceptional and far away: throw. Expected and handled by the caller: std::expected. "Not found": std::optional.
What it costsExceptions: about 5.8 µs per throw plus 712 ns per frame, nothing otherwise. expected: a returned value, about 1 ns.
Common mistakesExceptions as control flow in a hot loop; throwing from a destructor; ignoring an expected.
