The idea in one sentenceC++ resolves an abstraction at compile time whenever the compiler can see the type (templates, overloads, lambdas, final classes), so it costs nothing; only when you ask for run-time dispatch (virtual functions, std::function, std::variant) does a call wait to learn the type, and the measured cost of that is about 1 ns when the type is predictable and about 6 ns when it is not, while an exception costs nothing until it is thrown and then about 5 µs.

1. Classes: Python's conventions, checked by the compiler

A class and a struct are the same thing except for the default: struct members are public, class members private. What Python leaves to convention, C++ checks: private really is private, a const method really cannot modify the object, and members are declared with their types. One class shows most of it:

[[code:lang/classes.cpp:5-23]]
  • Member initialiser list (: user_(...), tokens_(...)): members are constructed there, before the body runs, in the order they are declared in the class, not the order you list them (clang warns when they differ).
  • explicit forbids using a one-argument constructor as a silent conversion. Without it, any function taking a Usage would accept a std::string and build a Usage behind your back. With it, that call is an error.
  • Operators are ordinary functions with special names, like Python's __iadd__ and __add__. operator<=> = default (C++20, the "spaceship") generates all six comparisons member by member, like @dataclass(order=True).

2. Virtual functions, and what dispatch really costs

A virtual function is chosen at run time by the object's actual class, like every method call in Python. A non-virtual one is chosen at compile time by the declared type, and can be inlined. = 0 makes a function pure virtual: the class is abstract, like a Python ABC, and override makes the compiler check that you really override something. The price is visible in the object itself:

Measured: one sum, eight ways of calling

Two loads and an indirect jump sound slow. Whether they are depends on something else: a modern CPU does not wait to learn where a jump goes; its branch predictor guesses and runs ahead, and only a wrong guess costs (the mechanism, and about 6 ns per mispredicted if on this M1, are on {{the machine page|n:4055c17b0d0d811fa947ee576a97a516}}, section 7). So the benchmark sums the areas of 10 million shapes eight ways, with the same arithmetic in each, and varies two things: whether the class changes unpredictably from one object to the next, and whether the objects sit next to each other in memory.

Predict, then switch: which is slower, a virtual call when every object has the same class, or a std::variant visit (no pointers, no vtable) over three classes in random order? Then switch to scattered objects: does the virtual call still matter?

ns per object, log scale; the median of three runs, with the range of the three under each label. Rows marked "flat" store the objects inside the vector, so they have no scattered version. 10 million objects, each pass visits every object once, best of 7 passes; Apple M1 Pro, Apple clang 17, -O2.

Three things show, and they are the practical rules:

  1. A predictable virtual call is cheap. One class: [[m:d.virtual, one class.o]] ns per object, against [[m:d.plain struct, pointers.o]] for a plain inlinable call through the same kind of pointer and [[m:d.plain struct, flat vector.o]] for plain structs stored flat. Much of the gap is probably not the jump itself but what it forbids: the compiler cannot inline a function it cannot name, so it cannot vectorise the loop or keep values in registers across the call.
  2. An unpredictable type is what costs, whatever the mechanism. Three classes in random order: virtual [[m:d.virtual, 3 classes mixed.o]] ns, std::function [[m:d.std::function, 3 mixed.o]], std::variant [[m:d.variant + visit, 3 mixed.o]]. The variant has no pointer and no vtable, but visit still branches on the stored type, and with three types in random order no predictor can guess that branch right more than about one time in three. The same objects visited sorted by class: [[m:d.virtual, 3 classes sorted.o]] ns. Sorting by type, or keeping one vector per type, removes most of the cost.
  3. When the data is scattered, memory dominates. With the objects allocated in shuffled order every row through a pointer costs 5 to 17 ns: a cache miss per object. The plain call pays [[m:d.plain struct, pointers.s]] ns, the predictable virtual call [[m:d.virtual, one class.s]] (the jump's target depends on the loaded vptr, so fewer misses overlap), the mixed one [[m:d.virtual, 3 classes mixed.s]]. Flat storage, at [[m:d.plain struct, flat vector.o]], beats every pointer layout by more than any dispatch choice.

A few nanoseconds per call is nothing for a call per request and a lot for a call per element of a tensor. That is why performance code uses templates (section 3) instead of virtual functions in hot loops, keeps data in flat arrays, and keeps virtual interfaces for coarse-grained choices. llama.cpp does exactly this: its KV cache is a class hierarchy with virtual functions, called a few times per token, while its kernels are templates and plain functions ({{C++: reading llama.cpp|n:4055c17b0d0d8150a5effbb5a667dd9d}}).

final tells the compiler no class derives from this one, so a call through a SqFinal* needs no vtable: it measured [[m:d.final class, devirtualised.o]] ns, an inlined call. The compiler devirtualises on its own whenever it can prove the exact class (a local object, a final class, link-time optimisation that sees every derived class).

One misprediction, derived: with three classes in random order a predictor that learns nothing is right about one time in three, so (mixed [[m:d.virtual, 3 classes mixed.o]] - sorted [[m:d.virtual, 3 classes sorted.o]]) ns / (2/3) = [[m:d.misp]] ns per mispredicted call, an upper estimate of the same order as the machine page's 6 ns per mispredicted if (an indirect jump's target is known only after two dependent loads, so the wrong guess is found later). Two inheritance traps, both silent

Slicing: passing a Derived by value as a Base copies only the base part; the copy forgets it was a Derived. Pass polymorphic objects by reference or pointer. Non-virtual destructor: deleting a Derived through a Base* ran only ~Base, so the 400-byte buffer leaked; formally it is undefined behaviour. A base class meant for polymorphic use needs virtual ~Base() = default;.
