5. Lambdas: a closure is an object you can measure

A lambda is an inline function, like Python's lambda but with statements allowed. The square brackets say which outside variables it captures and how: [x] copies x when the lambda is created; [&x] refers to the variable itself; [=] and [&] capture everything used, by copy or by reference.

Python closures always capture variables by reference and keep them alive. A C++ reference capture keeps nothing alive, so a lambda that outlives the function it was made in (returned, stored, or given to a thread) must capture by value; [&] in an escaping lambda is the essentials page's "dangling capture" bug, and capturing this has the same problem with the object. A lambda passed to a template (std::ranges::sort(rows, cmp)) is inlined like any template code: it costs nothing. Stored in a std::function, it pays a type-erased indirect call, and with mixed callables section 2 measured that at [[m:d.std::function, 3 mixed.o]] ns per call; templates and auto parameters avoid it.

6. Errors: exceptions against std::expected, measured

C++ has three ways to say "this did not work", and real code uses all three:

  • Exceptions work like Python's: throw, try/catch, unwinding that runs destructors on the way ({{the ownership page|n:4055c17b0d0d81819d74fa010e68ac2a}} replays it). Use them for errors the immediate caller cannot handle: a missing config file, out of memory.
  • std::optional<T> (C++17) is "a T or nothing", like returning None, with no reason attached.
  • std::expected<T, E> (C++23) is "a T or an error E", like Rust's Result. The caller must look; transform and and_then chain steps that run only on success. Use it for failures that are part of normal operation: parsing user input, a malformed JSONL line.

Compilers implement exceptions with tables that are read only when something is thrown ("zero-cost" exceptions, which still cost binary size). So the success path should be almost free and a throw expensive. How expensive, and when does it matter? The benchmark calls one tiny function written both ways, and varies the share of calls that fail.

The rates tell the rule. With no failures the exception version cost [[m:r.0.t]] ns per call against [[m:r.0.e]] (both functions are out-of-line calls; this benchmark does not explain the 0.6 ns gap). At 1 failure in 10,000 it was [[m:r.0.0001.t]] ns; at 1 in 1,000, [[m:r.0.001.t]]; at 1 in 100, [[m:r.0.01.t]], about 50 times the expected version, which stayed at [[m:r.0.e]] ns at every rate because returning an error is just returning a value. A simple model fits every row: cost per call = success path + failure rate × the cost of one throw, about [[m:r.throw]] ns (derived from the 50% row). So exceptions for rare failures, expected or optional where failure is common.

How far the error travels

A throw also grows with the number of stack frames it unwinds: the runtime walks each frame's table and runs its destructors. The second sweep makes the error cross 1 to 64 nested calls before it is handled:

A throw pays per frame unwound; an expected pays only the ordinary return

The expected version checks and returns the error at every level; its cost is the same as its success path at that depth (the calls themselves). The throw went from [[m:x.1.bt]] ns at depth 1 to [[m:x.64.bt]] at depth 64: about [[m:x.perframe]] ns per frame.

On the success path the two styles cost the same at depth: at 64 frames [[m:x.64.ot]] against [[m:x.64.oe]] ns, set by the 64 calls, not by the error handling. The one check per level that expected adds is noise beside the call it follows.

Some codebases (game engines, parts of Google's, many embedded ones) compile with exceptions turned off, and ggml, the C core under llama.cpp, reports errors with return values and assertions, since C has no exceptions. Mark functions that never throw noexcept, above all move constructors and destructors ({{the ownership page|n:4055c17b0d0d81819d74fa010e68ac2a}} shows why a vector needs it), and add [[nodiscard]] to a function returning expected, so ignoring the result is a warning.
