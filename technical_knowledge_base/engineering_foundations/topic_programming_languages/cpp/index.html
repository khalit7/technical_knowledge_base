1. How a C++ program is built

In Python, python main.py reads your source and runs it; import tokens finds tokens.py at run time. C++ has no run-time import. Building a program is a separate step with three stages, and most confusing C++ errors come from not knowing which stage complained.

  1. Preprocessor. Lines starting with # are text commands. #include "tokens.h" pastes the whole file in, literally. The result is one long file per .cpp, called a translation unit.
  2. Compiler. Each translation unit is compiled separately into an object file (.o): machine code plus a table of the names (symbols) it defines and the ones it needs from elsewhere.
  3. Linker. Joins the object files and libraries into one executable, matching every needed symbol to exactly one definition.

Here is the running example from the root page's Rosetta tab, cut down to its token counter and split the way real projects are: a header (.h) that declares the function (its name and types: a promise), and a source file that defines it (the body).

tokens.h
// tokens.h: the declaration (a promise that a definition exists somewhere)
#pragma once
#include <string_view>
int count_tokens(std::string_view text);
main.cpp
// main.cpp: uses count_tokens; only sees the declaration
#include "tokens.h"
#include <cstdio>

int main() {
    std::printf("%d tokens\n", count_tokens("C++ is fun, x86_64 too"));
}
tokens.cpp
// tokens.cpp: the definition
#include "tokens.h"
#include <cctype>

int count_tokens(std::string_view text) {
    int n = 0;
    bool inside = false;
    for (unsigned char c : text) {
        bool tok = std::isalnum(c) && c < 128;
        if (tok && !inside) n += 1;
        inside = tok;
    }
    return n;
}

std::string_view is a read-only view of some characters (section 9); unsigned char c : text loops over the bytes. Stage 1, the preprocessor: how long is the translation unit the compiler actually sees for this 7-line main.cpp?

The other classic link error is the opposite: two definitions. C++'s one definition rule (ODR) says a function may be defined once in the whole program. Put a function body in a header, include the header from two .cpp files, and each object file gets its own copy:

int a();

The fix is the keyword inline, which tells the linker "identical copies of this may appear in several object files; keep one". Functions defined inside a class body, templates and constexpr functions are implicitly inline, which is why headers full of them link fine.

A header is like a .pyi stub (types only) that every user pastes into their file. Python resolves names when the line runs; C++ resolves them at link time, so a missing or duplicated function is a build error, never a run-time NameError.

CMake: the build system

Typing compiler commands does not scale past a few files. CMake is the de facto standard build description: you list targets (executables, libraries) and their properties, and CMake generates the commands for a fast build tool such as Ninja. Three lines make a project:

CMakeLists.txt
cmake_minimum_required(VERSION 3.28)
project(hello LANGUAGES CXX)
add_executable(hello main.cpp)
$ cmake -S . -B build -G Ninja -DCMAKE_CXX_COMPILER=clang++ > /dev/null && cmake --build build && ./build/hello
[1/2] Building CXX object CMakeFiles/hello.dir/main.cpp.o
[2/2] Linking CXX executable hello
hello from CMake

A real project separates a library from the program that uses it. PUBLIC properties travel to every target that links the library; PRIVATE ones do not. This is the single most useful idea in CMake:

CMakeLists.txt
cmake_minimum_required(VERSION 3.28)
project(tokcount LANGUAGES CXX)

# A library target: compiled once, linked into anything that needs it
add_library(tokens src/tokens.cpp)
target_include_directories(tokens PUBLIC src)      # users of tokens see src/
target_compile_features(tokens PUBLIC cxx_std_20)  # and get C++20
target_compile_options(tokens PRIVATE -Wall -Wextra)

add_executable(tokcount src/main.cpp)
target_link_libraries(tokcount PRIVATE tokens)     # brings the include dir and C++20 along

2. Values, references and pointers

In Python every variable is a name bound to an object somewhere on the heap, and b = a binds a second name to the same object. In C++ a variable is the object: its bytes live where the variable lives. So assignment and initialisation copy, and if you want a second name you must say so. There are two ways:

  • A reference, T& r = a;, is another name for an existing object. It must be bound when created and can never be re-bound or be null. Using it is exactly like using a.
  • A pointer, T* p = &a;, is a variable holding an address. &a means "the address of a"; *p means "the object at p"; p->f() is short for (*p).f(). A pointer can be re-pointed, and can be nullptr (points at nothing).
copy.cpp
#include <cstdio>
#include <vector>

int main() {
    std::vector<int> a{1, 2, 3};
    std::vector<int> b = a;    // a COPY: b gets its own three ints
    b.push_back(4);
    std::printf("a has %zu, b has %zu\n", a.size(), b.size());

    std::vector<int>& r = a;   // a REFERENCE: another name for a
    r.push_back(99);
    std::printf("a has %zu after r.push_back\n", a.size());

    std::vector<int>* p = &a;  // a POINTER: holds a's address
    p->push_back(7);           // -> follows the pointer
    std::printf("a has %zu after p->push_back; p == &a is %d\n", a.size(), p == &a);

    p = nullptr;               // a pointer can be re-pointed, or point at nothing
    std::printf("p is now %s\n", p ? "set" : "null");
}

The same three lines in Python give "a has 4, b has 4": one list, two names. C++ printed "a has 3, b has 4": two vectors. Neither reference nor pointer keeps a alive; they only refer to memory that a owns. That is the root of every dangling-reference bug (section 12).

const

const marks something read-only, checked by the compiler. The most common use is the parameter type const T&: "let me read your object without copying it, and I promise not to change it". With pointers, const can apply to the pointed-at object or to the pointer itself; read the declaration right to left (int* const q: q is a const pointer to int).

const.cpp
#include <string>

// const& : read without copying, and promise not to change it
int count_chars(const std::string& s) { return static_cast<int>(s.size()); }

int main() {
    const int limit = 10;
    limit = 11;                     // error: limit is const

    std::string name = "u0029";
    const std::string& view = name;
    view += "!";                    // error: view is a read-only name

    int x = 1, y = 2;
    const int* p = &x;              // pointer to const int: *p is read-only
    p = &y;                         // fine: p itself can move
    int* const q = &x;              // const pointer to int: q cannot move
    *q = 5;                         // fine: what it points at can change
    q = &y;                         // error
    return count_chars(name) + *p;
}

3. The stack and the heap

A C++ object lives in one of three kinds of storage, and the kind decides when it dies:

  • Automatic storage, "the stack". Local variables. Each function call pushes a frame of memory for its locals; the frame is popped when the function returns. Allocation is free (the stack pointer moves) and destruction happens at the closing brace }, in reverse order of creation.
  • Dynamic storage, "the heap". Objects created with new (or, properly, std::make_unique, section 5). They live until someone destroys them. Allocation calls the memory allocator (malloc), which costs tens of nanoseconds and can fragment memory.
  • Static storage. Globals and static variables: they live for the whole program.

Python puts every object on the heap and frees it when its reference count reaches zero. C++ lets you put most things on the stack. Printing the addresses shows the three regions (the exact numbers change on every run, because macOS randomises where each region starts):

stack_heap.cpp
#include <cstdio>
#include <memory>
#include <vector>

int global_counter = 0;            // static storage: lives for the whole program

void show(const char* what, const void* p) { std::printf("%-28s %p\n", what, p); }

int main() {
    int on_stack = 1;                       // automatic storage (the stack)
    int also_on_stack = 2;
    auto on_heap = std::make_unique<int>(3); // dynamic storage (the heap)
    std::vector<int> v{1, 2, 3};            // the vector object is on the stack...

    show("&global_counter (static)", &global_counter);
    show("&on_stack", &on_stack);
    show("&also_on_stack", &also_on_stack);
    show("&v (the vector object)", &v);
    show("on_heap.get() (heap int)", on_heap.get());
    show("v.data() (its elements)", v.data());     // ...its elements are on the heap
    std::printf("sizeof(v) = %zu bytes, whatever v.size() is\n", sizeof(v));
}

The stack addresses (0x16...) go down as variables are added: on this ARM Mac the stack grows towards lower addresses. The vector is a hybrid that you will meet everywhere: the std::vector object itself is 24 bytes on the stack (a pointer to the elements, the size, the capacity), and its elements live in a heap buffer it owns. When the vector dies, its destructor frees the buffer. That pattern, a small owner on the stack and a big buffer on the heap, is how C++ gets automatic cleanup of heap memory. It has a name: RAII.

4. RAII and destructors

A class can define a constructor (runs when an object is created) and a destructor, written ~ClassName(), which runs automatically when the object dies: at the closing brace for a local, when its owner dies for a member, when delete is called for a heap object. RAII ("resource acquisition is initialisation", an awkward name for a simple idea) means: tie every resource (memory, a file, a lock, a GPU buffer, a socket) to an object whose destructor releases it. Then you can never forget to release it, even when an exception jumps out of the function.

To see it happen, this page uses a small class, Tracer, that prints a line from each special member function, numbering objects #1, #2... and saying whether each lives on the stack or the heap (its source is in the Object lifetimes tab). First, scopes:

5. Owning heap objects: unique_ptr and shared_ptr

When you need an object on the heap (it must outlive the function, it is too big for the stack, or its exact type is decided at run time), do not write new and delete. Use a smart pointer: a small stack object that owns the heap object and deletes it in its destructor.

  • std::unique_ptr<T>: exactly one owner. It cannot be copied (two owners would delete twice), only moved (section 6): ownership is handed over and the source becomes null. It is the same size as a raw pointer and costs nothing extra. Create one with std::make_unique<T>(args...). This is the default.
  • std::shared_ptr<T>: shared ownership with a reference count, like a Python object. The object dies when the last shared_ptr to it dies. It costs a separate control block holding the counts, twice the size, and an atomic (thread-safe) increment or decrement on every copy.
  • std::weak_ptr<T>: observes an object owned by shared_ptrs without keeping it alive; it breaks reference cycles, which reference counting alone never frees (Python has a cycle collector; C++ does not).

6. Move semantics

Copy-by-default has an obvious cost: returning a vector of a million elements, or putting a string into a container, would copy every byte. C++11 added moves: when the source object is about to die anyway, the new object may steal its heap buffer (copy three pointers, set the source's to null) instead of copying the contents.

The compiler needs to know when stealing is safe. It sorts expressions into two families (simplified):

  • an lvalue has a name and an address you can take: a, v[3], *p. It will be used again, so it must be copied.
  • an rvalue is a temporary about to disappear: make_name(), a + b, Tracer{"x"}. It may be moved from.

A class gets a move constructor T(T&& other) (the && means "rvalue reference": binds only to things that may be moved from) alongside its copy constructor T(const T& other), and overload resolution picks one. std::move(x) moves nothing. It is a cast that says "treat x as an rvalue; I will not need its value again" (cppreference: "exactly equivalent to a static_cast to an rvalue reference type"); the move constructor that it selects does the stealing.

Why noexcept on a move constructor matters: one vector, two classes

A std::vector keeps its elements in one buffer. When the buffer is full, push_back allocates a bigger one, transfers the old elements and frees the old buffer. It would like to move them, but if a move threw an exception halfway, the old buffer would be half-emptied and the vector could not restore it. So the standard library moves only if the move constructor is declared noexcept ("this never throws"); otherwise it copies, to keep its strong exception guarantee (std::move_if_noexcept). The animation runs the same three push_back calls on two versions of Tracer that differ only in that one keyword. Everything shown is the program's real output.

With noexcept, each reallocation moves (cheap); without it, the same code copies every existing element on every growth: for a vector of strings, that is a heap allocation and a byte copy per element. The compiler writes a noexcept move constructor for you when every member's is noexcept (the rule of zero, below), which is one more reason not to write them by hand.

The rule of zero and the rule of five

Five special member functions control a class's lifetime: destructor, copy constructor, copy assignment, move constructor, move assignment. The compiler writes all five for you, member by member. That is correct when every member manages itself (std::vector, std::string, std::unique_ptr): the rule of zero says write none of them. A class that owns a raw resource must write all five (the rule of five), because the compiler-written copy would copy the pointer, not the buffer:

rule_of_five.cpp (lines 5 to 35)
// A class that owns a raw buffer must write all five special members.
class Buffer {
    float* data_;
    std::size_t n_;
public:
    explicit Buffer(std::size_t n) : data_(new float[n]()), n_(n) {}
    ~Buffer() { delete[] data_; }                                   // 1 destructor
    Buffer(const Buffer& o) : data_(new float[o.n_]), n_(o.n_) {    // 2 copy constructor
        std::memcpy(data_, o.data_, n_ * sizeof(float));
    }
    Buffer& operator=(const Buffer& o) {                            // 3 copy assignment
        Buffer tmp(o);
        swap(tmp);
        return *this;
    }
    Buffer(Buffer&& o) noexcept                                     // 4 move constructor
        : data_(std::exchange(o.data_, nullptr)), n_(std::exchange(o.n_, 0)) {}
    Buffer& operator=(Buffer&& o) noexcept {                        // 5 move assignment
        Buffer tmp(std::move(o));
        swap(tmp);
        return *this;
    }
    void swap(Buffer& o) noexcept { std::swap(data_, o.data_); std::swap(n_, o.n_); }
    std::size_t size() const { return n_; }
};

9. The standard library you will actually use

The standard library ("the STL") is the C++ equivalent of Python's built-ins plus collections and itertools. On macOS it is LLVM's libc++; on Linux usually GCC's libstdc++; on Windows Microsoft's STL. The interfaces are standard; sizes, growth factors and string buffers below are libc++'s, measured.

std::vector: the default container

A growable array, like a Python list, except that it holds the elements themselves, contiguously, not pointers to objects. Use it unless you have measured a reason not to. Growth is geometric, so push_back is cheap on average:

vector_growth.cpp
#include <cstdio>
#include <vector>

int main() {
    std::vector<int> v;
    std::size_t last = v.capacity();
    std::printf("size 0 capacity %zu\n", last);
    for (int i = 0; i < 1000; ++i) {
        v.push_back(i);
        if (v.capacity() != last) {     // a new, bigger buffer: everything was moved
            last = v.capacity();
            std::printf("size %zu capacity %zu\n", v.size(), last);
        }
    }
}

std::string and std::string_view

std::string owns a growable byte buffer. Short strings are stored inside the 24-byte object itself (the small-string optimisation), so they need no heap allocation; std::string_view is a pointer and a length into characters owned by someone else, so passing one never copies. C++ strings are bytes: size() counts UTF-8 bytes, not characters.

strings.cpp
#include <cstdio>
#include <string>
#include <string_view>

// string_view: a pointer and a length into someone else's characters (no copy)
std::string_view first_word(std::string_view s) {
    auto end = s.find(' ');
    return s.substr(0, end);            // still points into the caller's string
}

int main() {
    std::string small = "u0029";
    std::string big = "a user id far too long for the small-string buffer";
    std::printf("capacity of an empty std::string: %zu\n", std::string{}.capacity());

                (const void*)small.data() >= (const void*)&small &&
                (const void*)small.data() < (const void*)(&small + 1));

Ranges: lazy pipelines

C++20 ranges compose lazily, like Python generators: views::filter, views::transform, views::take build a pipeline that computes nothing until a loop pulls from it. The prints inside the lambdas show the order of evaluation:

ranges.cpp
#include <cstdio>
#include <ranges>
#include <vector>

int main() {
    std::vector<int> counts{12, 0, 7, 31, 0, 5, 18};
    // A lazy pipeline: nothing runs until the loop pulls values (like a Python generator)
    auto pipeline = counts
        | std::views::filter([](int n) { std::printf("  filter %d\n", n); return n > 0; })
        | std::views::transform([](int n) { std::printf("  square %d\n", n); return n * n; })
        | std::views::take(2);
    std::printf("pipeline built, nothing computed yet\n");
    for (int x : pipeline) std::printf("got %d\n", x);

    // C++23: collect into a container, like list(...) in Python
    auto evens = std::views::iota(1, 11)
               | std::views::filter([](int n) { return n % 2 == 0; })
               | std::ranges::to<std::vector>();
    std::printf("evens: %zu values, last %d\n", evens.size(), evens.back());
}

10. Lambdas

A lambda is an inline function, like Python's lambda but with statements allowed. The part in square brackets says which outside variables it captures and how: [x] copies x when the lambda is created; [&x] refers to the variable itself; [=] and [&] capture everything used, by copy or by reference.

lambdas.cpp
#include <cstdio>
#include <functional>
#include <vector>

int main() {
    int threshold = 10;
    auto by_value = [threshold](int n) { return n > threshold; };   // copies threshold now
    auto by_ref   = [&threshold](int n) { return n > threshold; };  // refers to the variable
    threshold = 100;
    std::printf("by_value(50)=%d by_ref(50)=%d\n", by_value(50), by_ref(50));

    int calls = 0;
    auto counter = [calls]() mutable { return ++calls; };   // mutable: may change its own copy
    counter(); counter();
    std::printf("counter() -> %d, outer calls still %d\n", counter(), calls);

    auto twice = [](auto x) { return x + x; };              // generic lambda (a template)
    std::printf("twice(21)=%d twice(1.5)=%.1f\n", twice(21), twice(1.5));

    // A lambda is an object of a compiler-written class; its size is its captures
    std::printf("sizeof: no capture %zu, one int %zu, one reference %zu\n",
                sizeof([] {}), sizeof(by_value), sizeof(by_ref));
    std::function<bool(int)> f = by_value;   // type-erased holder: can store any callable
    std::printf("sizeof(std::function) %zu\n", sizeof(f));
}

Under the hood a lambda is an object of a class the compiler writes, with the captures as members and operator() as the body; its size is the size of its captures. Python closures always capture variables by reference and keep them alive; a C++ reference capture does not keep anything alive, so a lambda that outlives the function it was made in (returned, stored, or given to a thread) must capture by value. std::function can hold any callable with a given signature, at the price of a type-erased call and possibly a heap allocation; templates and auto parameters avoid both.

What it costsNothing for a lambda passed to a template; a std::function costs an indirect call.

11. Error handling: exceptions, optional, expected

C++ has three ways to say "this did not work", and real code uses all three:

errors.cpp
#include <charconv>
#include <cstdio>
#include <expected>
#include <optional>
#include <stdexcept>
#include <string>
#include <string_view>

// 1. Exceptions: like Python's raise/except
long parse_or_throw(std::string_view s) {
    long v = 0;
    auto [p, ec] = std::from_chars(s.data(), s.data() + s.size(), v);
    if (ec != std::errc{} || p != s.data() + s.size())
        throw std::invalid_argument("not a number: " + std::string(s));
    return v;
}

// 2. optional: "a value or nothing", no reason given (like returning None)
std::optional<long> parse_opt(std::string_view s) {
    long v = 0;
    auto [p, ec] = std::from_chars(s.data(), s.data() + s.size(), v);
    if (ec != std::errc{} || p != s.data() + s.size()) return std::nullopt;
    return v;
}

// 3. expected (C++23): "a value or an error", like Rust's Result
enum class ParseError { empty, not_a_number };
std::expected<long, ParseError> parse_exp(std::string_view s) {
    if (s.empty()) return std::unexpected(ParseError::empty);
    long v = 0;
    auto [p, ec] = std::from_chars(s.data(), s.data() + s.size(), v);
    if (ec != std::errc{} || p != s.data() + s.size()) return std::unexpected(ParseError::not_a_number);
    return v;
}

int main() {
    try {
        parse_or_throw("12x");
    } catch (const std::invalid_argument& e) {
        std::printf("caught: %s\n", e.what());
    }
    auto o = parse_opt("12x");
    std::printf("optional: has_value=%d, value_or(-1)=%ld\n", o.has_value(), o.value_or(-1));

    for (std::string_view s : {"4816", "", "12x"}) {
        auto r = parse_exp(s)
                   .transform([](long v) { return v * 2; });   // runs only on success
        if (r) std::printf("expected \"%.*s\": value %ld\n", (int)s.size(), s.data(), *r);
        else   std::printf("expected \"%.*s\": error %d\n", (int)s.size(), s.data(), (int)r.error());
    }
}
$ clang++ -std=c++23 -O2 -Wall -Wextra errors.cpp -o errors && ./errors

optional: has_value=0, value_or(-1)=-1
expected "4816": value 9632
expected "": error 0
expected "12x": error 1
  • Exceptions work like Python's: throw, try/catch, unwinding with destructors (section 4). Use them for errors the immediate caller cannot handle (a missing config file, out of memory).
  • std::optional<T> (C++17) is "a T or nothing", like returning None, with no reason attached.
  • std::expected<T, E> (C++23) is "a T or an error E", like Rust's Result. The caller must look; transform and and_then chain steps that run only on success. Use it for failures that are part of normal operation (parsing user input, a malformed JSONL line).

What each costs, measured with the same tiny function written both ways (10 million successful calls; 100,000 failing calls):

$ sysctl -n vm.loadavg; clang++ -std=c++23 -O2 throw_cost.cpp -o throw_cost && ./throw_cost
{ 13.33 8.47 7.38 }
success path:  exception-style 1.51 ns/call, expected-style 0.98 ns/call
failure path:  throw+catch 4766 ns/call, expected 0.96 ns/call

On the success path both are about a nanosecond: compilers implement exceptions with tables consulted only when something is thrown ("zero-cost" exceptions, which still cost binary size). Throwing and catching took about 4766 ns, thousands of times more than returning an expected. So: exceptions for rare failures, expected or optional where failure is common. Some codebases (game engines, parts of Google's, many embedded ones) compile with exceptions turned off; ggml, the C core under llama.cpp, reports errors with return values and assertions, since C has no exceptions.

Rule of thumbExceptional and far away: throw. Expected and handled by the caller: std::expected. "Not found": std::optional.
noexceptMark functions that never throw, above all move constructors and destructors (section 6).
Common mistakesExceptions as control flow in a hot loop; throwing from a destructor; ignoring an expected (add [[nodiscard]] to the function).

12. Undefined behaviour

The C++ standard lists operations whose result it does not define: reading outside an array, reading freed memory, overflowing a signed integer, reading an uninitialised variable, two threads writing the same variable without synchronisation, falling off the end of a function that should return a value, and others. Such a program has undefined behaviour (UB): not "a wrong answer" but no meaning at all. The compiler is allowed to assume UB never happens, and its optimiser uses that assumption to delete checks and simplify code. So a program with UB can work at -O0 and break at -O2, or work today and break after a compiler upgrade. This is the deepest difference from Python, where every one of these is either impossible or an exception.

The classic example: "will x + 1 overflow?" written the obvious way.

overflow.cpp
#include <climits>
#include <cstdio>

// "Will adding 1 overflow?" written the way you would in Python
__attribute__((noinline)) bool will_overflow(int x) {
    return x + 1 < x;   // signed overflow is UB, so the compiler may assume x + 1 > x
}

int main() {
    std::printf("will_overflow(INT_MAX) = %d\n", will_overflow(INT_MAX));
}
$ clang++-23 -std=c++23 -O0 overflow.cpp -o overflow && ./overflow
will_overflow(INT_MAX) = 1
$ clang++-23 -std=c++23 -O2 overflow.cpp -o overflow && ./overflow
will_overflow(INT_MAX) = 0

At -O0 the addition wrapped around to a negative number and the test said 1. At -O2 the compiler reasoned "signed overflow cannot happen, so x + 1 < x is always false" and compiled the function to return false. Neither build reported anything. Sanitizers are compiler modes that add run-time checks for UB; UndefinedBehaviorSanitizer (UBSan) catches this one:

$ clang++-23 -std=c++23 -O2 -fsanitize=undefined overflow.cpp -o overflow && ./overflow
overflow.cpp:6:14: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
SUMMARY: UndefinedBehaviorSanitizer: undefined-behavior overflow.cpp:6:14 
will_overflow(INT_MAX) = 1

(Under UBSan the program prints 1 again: the instrumented build computes the addition so it can check it.) The fix is to test before adding: x == INT_MAX, or __builtin_add_overflow, or C++26's <stdckdint.h> checked arithmetic. Unsigned integers do not have this problem: they wrap around by definition.

A second one, the uninitialised variable, shows how odd UB can look. seen is never set when flag is false:

13. Libraries: header-only, static, dynamic, and getting them

Python has pip install and wheels. C++ has no official package manager, and the reason is technical: a compiled C++ library works with your program only if it was built with a compatible compiler, standard library and flags (the same ABI, application binary interface). A mismatch gives link errors or, worse, silent memory corruption. Shipping prebuilt binaries is therefore much harder than in Python, and the community's historical answer was "build it yourself" or "copy the source in". Three ways a library reaches your program:

  • Header-only: the whole library is headers (all inline functions and templates), so there is nothing to build or link: nlohmann/json, Catch2, Eigen. It sidesteps packaging and ABI, and costs compile time in every file that includes it.
  • Static library (.a, .lib): object files copied into your executable at link time, like libtokens.a in section 1. One self-contained binary; every program carries its own copy.
  • Dynamic (shared) library (.dylib, .so, .dll): loaded when the program starts. Smaller binaries and shared updates, but the library must be present, at a compatible version, on the machine that runs it. Even the small program from section 1 depends on two:
$ otool -L app

	/usr/lib/libSystem.B.dylib (compatibility version 1.0.0, current version 1356.0.0)

14. Modern C++: where C++20, C++23 and C++26 stand (October 2026)

C++ is standardised by an ISO committee (WG21) on a three-year train: C++11, 14, 17, 20, 23, 26. Nothing old is removed, so "modern C++" is a subset you choose to write, the one this part teaches. Each compiler and standard library implements each standard gradually, and the two can differ: a feature needs both.

Ask for a standard, always

The default language version differs between compilers and even versions of one compiler. Measured here:

$ for c in /usr/bin/clang++ clang++ clang++-23; do printf "%-18s default __cplusplus = " $c; echo __cplusplus | $c -x c++ -E -P - | tail -n 1; done
/usr/bin/clang++   default __cplusplus = 199711L
clang++            default __cplusplus = 201402L
clang++-23         default __cplusplus = 201703L

(199711L is C++98, 201402L C++14, 201703L C++17.) Elsewhere: GCC 16 (released 2026-04-30) is the first major compiler to default to C++20 (GCC 16 changes); upstream Clang has defaulted to C++17 since Clang 16 (Clang status); MSVC still defaults to C++14 (/std). So pass -std=c++20 or newer, or in CMake target_compile_features(t PUBLIC cxx_std_20).

15. Mistakes that catch experienced people, and a hygiene checklist

Each of these compiles. Most were shown above; the ones marked "gallery" crash or misbehave in the UB gallery.

A string_view, span or range view that outlives its owner
Views do not own. Initialising one from a temporary dangles at the semicolon (gallery). Range-for over a member of a temporary, for (auto& x : make().items()), dangled until C++23 extended the lifetime of every temporary in the range-for initializer (P2718); the same expression outside a range-for still dangles, so the old page's "fixed for some cases in C++23, not all" stands.
A reference, pointer or iterator into a vector, kept across push_back
Growth reallocates and frees the old buffer (section 9; gallery). Use indices, or reserve first.
Slicing a derived object into a base by value
Section 7. Pass polymorphic objects by reference or pointer.
A public non-virtual destructor in a base class used through pointers
Only the base part is destroyed (section 7).
Static initialisation order across files
Globals in different .cpp files are initialised in an unspecified order; one global's constructor that uses another may see it unconstructed. Use a function returning a reference to a function-local static, which is initialised on first use.
Unsigned arithmetic going below zero: for (size_t i = v.size() - 1; i >= 0; --i)
size_t is unsigned: i >= 0 is always true and 0 - 1 wraps to 18,446,744,073,709,551,615. An empty vector makes even the first value huge. Mixing signed and unsigned in a comparison converts the signed side to unsigned (clang warns with -Wextra).
Treating a data race as "sometimes a wrong value"
It is UB. The gallery's race printed 1098717 instead of 2000000 at -O0 and the right answer at -O2 (the optimiser turned the loop into one addition), so a test at -O2 passes. Use std::atomic or a mutex; Part 2 covers the memory model.
shared_ptr by reflex
Cycles leak; atomic counting slows single-threaded paths; ownership becomes unclear. unique_ptr first.
Using an object after std::move
Valid but unspecified (section 6). Assign to it or let it die.

Hygiene checklist

  • RAII everywhere; no naked new/delete; unique_ptr by default.
  • Rule of zero; if you must write one special member, write all five, with noexcept moves.
  • Parameters: string_view and span<const T> to read; never store them past the call without thought.
  • const by default; constexpr where a value can be computed at compile time.
  • auto for iterators, lambdas and long type names; concrete types at API boundaries.
  • Build with -std=c++20 or newer and -Wall -Wextra (-Werror in CI); ASan, UBSan and TSan in CI test runs; clang-format and clang-tidy; CMake targets with PUBLIC/PRIVATE properties, presets, and vcpkg or Conan.

What to notice

  • Scopes: destruction is in reverse order of construction, at each closing brace.
  • Copy vs move: b = c is an assignment (b already exists), so no object is created; the moved-from a still gets destroyed.
  • Passing and returning: m is the object constructed inside make() at line 10: returning it cost no copy and no move (copy elision).
  • vector growth, the two versions: the same three push_back calls, 9 objects either way; with a noexcept move the reallocations move the old elements, without it they copy them. Compare the counters.
  • reserve + emplace_back: three objects, built directly in the vector's buffer: no temporaries, no moves.
  • unique_ptr and shared_ptr: one heap object each, never copied; it dies when its last owner lets go.
  • Exception unwinding: b is destroyed before the catch block runs.
The Tracer class (tracer.h)
tracer.h
// tracer.h: a class that reports every special member function call.
// Each object gets a number (#1, #2, ...) and says whether it lives on the stack or the heap.
#pragma once
#include <cstdio>
#include <cstdlib>
#include <cstring>
#include <source_location>
#include <string>
#include <utility>

inline const char* stack_anchor = nullptr;   // set to a local's address in main()
inline int next_id = 1;

inline const char* where(const void* p) {
    long d = static_cast<const char*>(p) - stack_anchor;
    return std::labs(d) < (8L << 20) ? "stack" : "heap";
}
#define STEP(text) std::printf("@%d %s\n", __LINE__, text)
// The line in lifetime.cpp that caused a constructor call (blank when called from inside the library)
inline int at(const std::source_location& l) {
    return std::strstr(l.file_name(), "lifetime.cpp") ? static_cast<int>(l.line()) : 0;
}
using Loc = std::source_location;

template <bool NoexceptMove>
struct BasicTracer {
    int id;
    std::string name;
    explicit BasicTracer(std::string n, Loc l = Loc::current()) : id(next_id++), name(std::move(n)) {
        std::printf("ctor #%d %s %s L%d\n", id, name.c_str(), where(this), at(l));
    }
    BasicTracer(const BasicTracer& o, Loc l = Loc::current()) : id(next_id++), name(o.name) {
        std::printf("copy #%d from #%d %s %s L%d\n", id, o.id, name.c_str(), where(this), at(l));
    }
    BasicTracer(BasicTracer&& o, Loc l = Loc::current()) noexcept(NoexceptMove) : id(next_id++), name(std::move(o.name)) {
        std::printf("move #%d from #%d %s %s L%d\n", id, o.id, name.c_str(), where(this), at(l));
    }
    BasicTracer& operator=(const BasicTracer& o) {
        name = o.name;
        std::printf("copy= #%d from #%d\n", id, o.id);
        return *this;
    }
    BasicTracer& operator=(BasicTracer&& o) noexcept(NoexceptMove) {
        name = std::move(o.name);
        std::printf("move= #%d from #%d\n", id, o.id);
        return *this;
    }
    ~BasicTracer() { std::printf("dtor #%d\n", id); }
};
using Tracer = BasicTracer<true>;     // move constructor marked noexcept
using TracerNX = BasicTracer<false>;  // the same class without noexcept

void copymove() {
    Tracer a{"a"};
    Tracer b = a;             // copy constructor
    Tracer c = std::move(a);  // move constructor: steals a's string

    STEP("end of function");
}
// </copymove>

void calls() {
    Tracer a{"a"};
    by_ref(a);                // no new object
    by_value(a);              // a copy for the parameter
    by_value(std::move(a));   // a move for the parameter
    Tracer m = make("m");     // no copy, no move: built in place
    STEP("end of function");
}
// </calls>

// <growth>
template <class T>
void growth() {
    std::vector<T> v;
    v.push_back(T{"x"});
    STEP("capacity 1, now push y");
    v.push_back(T{"y"});
    STEP("capacity 2, now push z");
    v.push_back(T{"z"});
    STEP("end of function");
}
// </growth>

// <reserve>
void reserve() {
    std::vector<Tracer> v;
    v.reserve(3);             // one allocation up front
    v.emplace_back("x");      // built directly inside the vector
    v.emplace_back("y");
    v.emplace_back("z");
    STEP("end of function");
}
// </reserve>

// <unique>
void unique() {
    auto p = std::make_unique<Tracer>("h");   // the Tracer lives on the heap
    std::unique_ptr<Tracer> q = std::move(p);  // ownership moves; the Tracer does not
    std::printf("p is %s, q owns #%d\n", p ? "set" : "null", q->id);
    q.reset();                                 // the owner lets go: destroyed now
    STEP("end of function");
}
// </unique>

// <shared>
void shared() {
    auto s = std::make_shared<Tracer>("s");
    {
        std::shared_ptr<Tracer> t = s;         // a second owner
        std::printf("use_count %ld\n", s.use_count());
    }
    std::printf("use_count %ld\n", s.use_count());
    STEP("end of function");
}
// </shared>

// <unwind>
void unwind() {
    Tracer a{"a"};
    try {
        Tracer b{"b"};
        throw std::runtime_error("boom");
        STEP("never reached");
    } catch (const std::exception& e) {
        std::printf("caught %s\n", e.what());
    }
    STEP("end of function");
}
// </unwind>

    char here;
    stack_anchor = &here;

The gates, with answers

The questions that end each stage of the learning path (Reading 16). Answer aloud first.

Stage 0: what does the linker say when a non-inline function is defined in a header included from two .cpp files?
"duplicate symbol" (ld on macOS; GNU ld says "multiple definition"). Each translation unit compiled its own copy, so two object files define the same symbol; the one definition rule allows only one. Fix with inline, or keep only a declaration in the header. The Build pipeline tab shows the real error.
Stage 1: when is each object in a function destroyed, and in what order?
Locals: at the closing brace of their block, in reverse order of construction; also during unwinding when an exception leaves the block. Temporaries: at the end of the full expression (the semicolon), unless bound to a const& or && local, which extends them to that local's lifetime. Members: after the class's destructor body, in reverse declaration order. Heap objects: when their owner (a smart pointer) dies or is reset.
Stage 2: a class holds a unique_ptr and a vector. Which special members does the compiler generate, which does it delete, and why?
It generates the destructor, the move constructor and the move assignment (member-wise; noexcept because both members' are). It defines the copy constructor and copy assignment as deleted, because unique_ptr's copy operations are deleted: a member-wise copy is impossible. The class is move-only, like unique_ptr itself. Declaring any of the five yourself would suppress the implicit moves, which is why the rule of zero says declare none.
Stage 3: why is std::vector<bool> a mistake, what does noexcept on a move constructor buy, and what may the optimiser assume about a signed loop counter?
vector<bool> is specialised to pack bits, so it is not a container of bool: v[i] returns a proxy object, not a bool&, so bool& r = v[0] does not compile, &v[0] is not a bool*, and concurrent writes to different elements can race. noexcept lets vector move elements on reallocation instead of copying them (the Object lifetimes tab's two growth scenarios). A signed counter never overflows, so i + 1 > i and the loop's trip count can be computed without wrap-around checks, which enables vectorisation and widening it to 64 bits.

1. The memory hierarchy: a ladder of caches

A processor core can do an addition in a fraction of a nanosecond, but fetching a number from main memory (DRAM, the RAM chips) takes about a hundred nanoseconds. To hide that gap the chip keeps copies of recently used memory in caches: small, fast memories close to the core. Each level is bigger and slower than the one before. A register is a slot inside the core itself, where the instructions actually compute; everything else is a cache or memory.

Measuring the ladder: pointer chasing


To time one load you must stop the processor from doing many at once. The trick is a pointer chase: a linked list scattered over a buffer, where each node holds the address of the next. 2. Cache lines, and spatial and temporal locality


Caches do not hold single bytes. They hold cache lines: aligned blocks of 128 bytes on this M1 Pro (hw.cachelinesize; 64 on most Intel and AMD processors). Reading one byte brings its whole line into L1. Two habits follow:


    

  • Spatial locality: use the neighbours of what you just read, since they arrived with it. A line of 128 bytes holds 32 floats; reading them in order costs one trip to memory per 32 numbers.
    • 

  • Temporal locality: reuse data soon, before other data evicts it from the cache. Blocked ("tiled") matrix multiplication in section 9 is this idea.
    • 



The classic demonstration: a 4096 x 4096 matrix of 32-bit integers (64 MB) stored row after row, as C++ (and NumPy by default) lay it out. Sum it row by row, then column by column. Same additions, same answer.




Predict. How much slower is the column order? 2x? 10x?

Going down a column, consecutive elements are 4096 x 4 = 16 KB apart, so every addition needs a new cache line and uses 4 of its 128 bytes; by the time the loop comes back for the neighbouring column, the line has long been evicted. Row order uses every byte of every line, the prefetcher sees a simple stream, and the compiler can even process 4 integers per instruction (section 6). 4. Virtual memory, pages and mmap


The addresses your program sees are not physical locations in the RAM chips. They are virtual addresses: each process has its own private address space, and the operating system keeps a page table that maps it, one page at a time, to physical memory or to nothing yet. On Apple silicon a page is 16 KB (hw.pagesize printed 16384; Intel and most Linux machines use 4 KB). Every load translates its address; the TLB (translation lookaside buffer) is the small cache of recent translations, and a miss in it costs extra loads to walk the page table, part of the slope you saw in the latency ladder.


Two consequences matter for C++ programmers:


    

  • Memory is given lazily. malloc or new of a big block only reserves addresses. The first touch of each page triggers a page fault: the processor stops, the kernel finds a physical page, zeroes it, maps it, and the instruction retries.
    • 

  • A file can be mapped instead of read. mmap puts a file's bytes into your address space; pages are read from disk (or from the operating system's page cache, the copy of recently used files it keeps in RAM) only when touched, and pages that are never touched cost nothing.
    •

8. Threads, atomics and the C++ memory model


The root page's Reading, section 9 showed the basic danger: two threads updating one counter lose updates, and a data race (two threads touching the same memory, at least one writing, nothing ordering them) is undefined behaviour in C++. Part 1 covers std::thread, mutexes and locks. This section is about what the hardware adds: cores do not see each other's writes in the order they were made.


Why order is not guaranteed


Each core writes into a private store buffer before its writes reach the shared caches, and executes loads early, out of order, whenever their addresses are known. On one core this is invisible. Seen from another core, two writes can appear in the opposite order. x86 processors promise to keep stores in order (a strong model); ARM processors, including this one, do not (a weak model). The compiler may reorder too. 9. The roofline: compute-bound or memory-bound?


Every kernel needs two resources: arithmetic and bytes from memory. The roofline model (Williams, Waterman and Patterson, 2009) asks which one runs out first. Define the kernel's arithmetic intensity I as floating-point operations per byte moved from memory. Then


attainable FLOP/s = min( peak FLOP/s , I × bandwidth )
I
FLOPs per byte read from DRAM (a multiply-add counts as 2 FLOPs)
peak
the core's or chip's maximum arithmetic rate
bandwidth
bytes per second the memory system delivers


Below the ridge point I = peak / bandwidth, a kernel is memory-bound: a faster processor would not help, only fewer bytes would. Above it, it is compute-bound. The inputs, measured here (roof.cpp, compiled with -O3 -ffast-math; three runs each):




The peak loop runs 24 independent fmla.4s chains so that all four floating-point units stay busy (4 units x 4 lanes x 2 FLOPs = 32 FLOPs per cycle, about 102 GFLOP/s at 3.2 GHz; measured ). A first version with 12 chains of the form a = y + a * x reached only 64 GFLOP/s: the compiler had to add a register copy before every fmla, because fmla overwrites its accumulator. The bandwidth row is reading a 512 MB array once: one core reaches about half of the chip's 200 GB/s, all eight about  GB/s (the GPU shares the rest).


The matrix-vector product is LLM decoding. Generating one token multiplies every weight matrix by one vector: each weight is read once and used for one multiply-add. In fp32 that is 2 FLOPs per 4 bytes, I = 0.5, far left of the ridge: the bound is 0.5 x bandwidth, and the measured matvec sits right on it. So decoding speed is set by bytes: tokens per second can be at most bandwidth / bytes of weights. Illustrative (not measured): an 8-billion-parameter model in 16-bit weights is 16 GB, so at  GB/s this laptop could produce at most about  tokens per second however fast its arithmetic; in llama.cpp's 4-bit q4_0 format (18 bytes per 32 weights, 4.5 bits each) it is 4.5 GB and the ceiling rises to about . This is why quantisation speeds up decoding and why batching many users' tokens together (which reuses each weight for many vectors, raising I) is the core of LLM serving; both belong to Topic: inference-and-serving and the Quantization and Precision page.


The matrix-matrix product is compute-bound (I about 85 FLOPs per byte for 512 x 512 matrices read once), yet the simple tiled loop reached only about a quarter of peak: it is limited by loads and stores inside the core, not by DRAM. Libraries close that gap with register blocking (keeping a small tile of the output in registers across the whole inner loop); that craft is the subject of Topic: cuda-and-gpu-programming on the GPU. Why microbenchmarks lie


    

  • The compiler deletes unused work. If a result is never used, the loop may vanish. Every benchmark here passes results to keep(), an empty asm volatile that forces the value to exist (bench.h); Google Benchmark calls it benchmark::DoNotOptimize.

12. The ABI: C++'s binary contract


An API is a contract in source code: names, types, what functions do. An ABI (application binary interface) is the contract between already-compiled pieces of machine code: which registers carry arguments (section 5), how structs are laid out (section 3), how virtual tables and exceptions work, and what the symbols are called. Two object files work together only if they agree on all of it. Python programmers meet the ABI as "this wheel does not match your Python" or as a crash after mixing builds.


Name mangling


C has one function per name. C++ allows the same name in different namespaces and overloads with different parameter types, so the compiler encodes the namespace and the parameter types into the symbol, following the Itanium C++ ABI (used by clang and GCC on every platform except Windows, despite its name). extern "C" turns mangling off, which is why every C++ library meant to be called from another language exposes a C interface.






Read __ZN9ggml_like3dotEPKfS1_i as: _Z a mangled name (macOS adds one more underscore in front), N ... E a nested name made of 9ggml_like (9 characters) and 3dot, then the parameters: PKf pointer to const float, S1_ the same type again, i int. The double overload differs only in d. c_dot is just _c_dot.


What breaks when you mix


    

  • Different standard libraries. clang on macOS uses libc++; GCC on Linux uses libstdc++. Their std::string, std::vector and friends have different layouts, so a std::string cannot cross between code built against the two. Even within one library, flags that change layouts (debug iterators, _GLIBCXX_USE_CXX11_ABI on Linux) must match.
    • 

  • Standard library designs that cannot be fixed. Because programs compiled years ago still link against today's shared standard library, library vendors avoid any change to a type's layout or a function's mangled name; known-slow designs (std::unordered_map's node-based buckets, std::regex) stay as they are for that reason.
    • 

  • Headers and flags out of step. Two translation units that see different definitions of the same struct (a different #define, packing pragma or alignment) break the one-definition rule: no error, just corrupted fields at run time.
    • 

  • Mixing compilers is fine through a C interface, risky through C++ types, and the reason C++ has no universal package of prebuilt binaries like PyPI's wheels (Part 1 covers builds and package managers).
    • 



Apple's ARM64 ABI differs from the standard Linux one in a few details (for example, how variadic arguments are passed): Writing ARM64 code for Apple platforms.


In Python
ctypes and cffi can call only C symbols, so they need extern "C". pybind11 and nanobind compile C++ against CPython's own C ABI; a wheel built for one Python version works only on that version unless it uses the limited "abi3" stable ABI (the Rust page covers abi3 wheels with PyO3).

14. Common mistakes


Timing a loop whose result is never used
The optimiser deletes it and you measure nothing. Use the result (print it, or pass it to a DoNotOptimize/keep barrier) and look at the assembly.


"Float sums vectorise automatically"
Not without permission to reorder additions (-ffast-math, -fassociative-math or a local pragma). Integer sums do. Section 6 measured a 13x gap between the two.


Padding to 64 bytes on Apple silicon
Lines are 128 bytes here; 64-byte padding still left a 2x false-sharing penalty. std::hardware_destructive_interference_size said 64.


Using relaxed atomics, or plain variables, to publish data
Correct on x86 by luck of its strong ordering, wrong on ARM: the reader can see the flag before the data. Use release on the store and acquire on the load (or a mutex).


Walking a matrix against its layout
Columns of a row-major matrix cost 50x here. Swap the loops, transpose once, or store the other order.


A vector of pointers where a vector of values would do
Each element is a separate allocation and a pointer chase; std::vector<T> beats std::vector<std::unique_ptr<T>> unless you need stable addresses or polymorphism.


Assuming a debug build's speed means anything
-O0 keeps every variable in memory and calls every function; section 5's loop went from n calls to a formula. Benchmark optimised builds, with debug info (-O2 -g) for profiling.


Optimising FLOPs in a memory-bound kernel
Matrix-vector work (LLM decode) is limited by bytes; faster arithmetic does nothing. Fewer bytes (quantisation) or more reuse (batching) does.


Reading a vectorisation remark as a guarantee
The remark said "vectorized" for a loop whose additions were still serial. The assembly decides.

6. ggml tensors: sizes, strides, a pointer


Everything in ggml is a struct ggml_tensor, a plain C struct (no methods, no constructor):




Read it field by field. type is the element type (F32, F16, Q8_0, ...). ne holds up to four sizes, innermost first. nb holds the matching strides in bytes: how far to move in memory to step one along each dimension. data points at the first byte. op and src say how this tensor is computed from others (section 7); view_src and view_offs mark a tensor that borrows another's memory. The element at index (i0, i1, i2, i3) lives at data + i0*nb[0] + i1*nb[1] + i2*nb[2] + i3*nb[3].

From Python
NumPy and PyTorch work the same way: a.strides (NumPy, bytes) or a.stride() (PyTorch, elements), and a.T returns a view with swapped strides. The differences: ggml lists sizes innermost first (PyTorch's (49152, 576) is ggml's {576, 49152}), and a quantised type has no per-element stride: nb[0] is the size of a 32-weight block, so you can only address whole blocks.


Nothing is computed when you call an operation. ggml_mul_mat does not multiply: it creates a result tensor, records op = GGML_OP_MUL_MAT and its two sources, and returns.




The result's sizes are {a->ne[1], b->ne[1], ...}: ggml's matrix product multiplies each row of a (the weight, one output feature per row) by each row of b (one token per row), so both operands are read along their contiguous dimension. 14. Mistakes when reading or running llama.cpp


Reading the generic kernel and assuming it runs
The function a guide shows (ggml_vec_dot_*) may run zero times: repacking, llamafile's tinyBLAS, BLAS or a GPU backend may take the product. Count calls, or check the log for repack, splits and offloaded lines (sections 5, 8, 10).


Reading shapes in PyTorch order
ne[0] is the innermost, contiguous dimension. A weight that PyTorch calls (out, in) is {in, out} in ggml, and ggml_mul_mat(a, b) computes rows of a times rows of b (section 6).


Thinking a ggml call computes something
ggml_add, ggml_mul_mat and friends only add a node to a graph. Values exist after the graph has been computed; inspect them with an eval callback (llama-eval-callback), not by reading tensor->data right after the call.


Forgetting the default GPU offload
simple.cpp and the tools default to offloading every layer (-ngl 99 or "auto"). On a Mac that means Metal; if you are studying the CPU path, pass -ngl 0 and check the log says no layers were offloaded.


Benchmarking on a busy machine, or with too many threads
The barrier after every operation turns one descheduled thread into a stall for all. Use llama-bench with repetitions (-r 5), look at every sample, record the load average, and try fewer threads than cores (section 9).


Building without Release
A Debug build (-O0) is many times slower and teaches nothing about speed. Always -DCMAKE_BUILD_TYPE=Release for timing; keep a Debug build only for stepping through code in a debugger.


Trusting log labels
model type = 256M for a 135M model (section 5). Logs are written by people; when one looks wrong, grep for its text.


Editing the clone you are measuring
Instrument a copy (as src/cl/code/instrument.py does) and keep the pinned clone clean, so every excerpt and line number stays true to the commit.
