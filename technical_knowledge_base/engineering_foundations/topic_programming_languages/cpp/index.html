The idea in one screen

In C++ you decide where each object lives and when it dies, and the compiler trusts you: each file is compiled separately and the pieces are linked, and a broken rule is undefined behaviour, not an error. Python decides both things for you, which is why C++ is fast where you take care and silently wrong where you do not.

Fig. 1 follows one small program from its source files to the machine, in the order the pieces meet it. Each step names the section of this page, or the child page, that owns that piece, and links the child's own figure instead of drawing it again. Every number is from a recorded run on this page.

  1. Three source files. main.cpp (7 lines) calls count_tokens, tokens.h (4 lines) declares it, tokens.cpp (14 lines) defines it. Nothing runs yet: C++ has no run-time import, so a separate build turns them into a program (section 1).
  2. The preprocessor pastes. Each #include copies a whole file in, so main.cpp plus tokens.h plus the standard headers becomes one translation unit of 55,693 lines; tokens.cpp's is 55,700. Heights in the figure are on a log scale. Modules, the cure, are section 4.
  3. Each file compiles alone. Each translation unit becomes an object file of machine code and symbols: main.o (928 bytes) needs count_tokens (U), tokens.o (848 bytes) defines it (T). The compiler accepted main.cpp on the header's promise; section 1's stepper shows each stage.
  4. The linker joins. It matches every U to exactly one T and writes app (33,696 bytes). libc++ and libSystem stay outside it, loaded when the program starts: dynamic libraries (section 3).
  5. Run: one owner on the stack, its buffer on the heap. std::vector<float> v{1, 2, 3}: v itself is 24 bytes on the stack (pointer, size, capacity) and its three floats are 12 bytes on the heap, measured with a replaced operator new. Owner: Ownership, moves and lifetimes, whose stack and heap figure replays a real run with a copy and a move.
  6. The closing brace frees. ~vector() runs at the brace: the heap bytes are freed, then v vanishes with its frame. One owner, one moment, no garbage collector: that is RAII (the ownership page, section 3). The vector itself is a class template from the standard library; how it grows its buffer is the vector figure on Classes, templates and the standard library.
  7. Two owners, one buffer: undefined behaviour. Swap the vector for a class with only a destructor: its compiler-written copy copies the pointer, so a and b own one 16-byte array and both free it. At -O0 the program crashed (exit code 133); at -O2 it printed "same array: 1" and exited normally; ASan reported "attempting double-free". No error from the compiler: section 2 and its gallery.
  8. To the CPU. Every load climbs a ladder of caches, DRAM to L2 to L1 to a register, one cache line at a time, so layout sets speed: summing a matrix by columns ran 52 to 56 times slower than by rows. Owner: The machine underneath, whose cache ladder figure times each level on this M1 Pro.
  9. All of it in one engine. llama.cpp is every piece at once: a CMake build with vendored libraries, model weights mapped from a file and repacked at load, a graph walked by threads through SIMD kernels. Owner: Reading llama.cpp, whose Fig. 1 times one token through it.

Six ideas, and where each is taught

C++ is the language underneath most of the ML stack you use from Python: PyTorch's core, llama.cpp, ONNX Runtime, the CUDA kernels. The whole language follows from one decision: C++ gives you the machine's own representation of data and makes you responsible for how long each piece of it lives. 1. How a C++ program is built

Python reads your source and runs it; import tokens finds tokens.py at run time. C++ has no run-time import. Building is a separate step with three stages, and most confusing C++ errors come from not knowing which stage complained.

  1. Preprocessor. Lines starting with # are text commands. #include "tokens.h" pastes the whole file in, literally. The result is one long file per .cpp, called a translation unit.
  2. Compiler. Each translation unit is compiled separately into an object file (.o): machine code plus a table of the names (symbols) it defines and the ones it needs from elsewhere.
  3. Linker. Joins the object files and libraries into one executable, matching every needed symbol to exactly one definition.

The root page's token counter, split the way real projects are: a header (.h) declares the function (its name and types: a promise), a source file defines it (the body).

tokens.h
// tokens.h: the declaration (a promise that a definition exists somewhere)
#pragma once
#include <string_view>
int count_tokens(std::string_view text);
main.cpp
// main.cpp: uses count_tokens; only sees the declaration
#include "tokens.h"
#include <cstdio>

int main() {
    std::printf("%d tokens\n", count_tokens("C++ is fun, x86_64 too"));
}
tokens.cpp
// tokens.cpp: the definition
#include "tokens.h"
#include <cctype>

int count_tokens(std::string_view text) {
    int n = 0;
    bool inside = false;
    for (unsigned char c : text) {
        bool tok = std::isalnum(c) && c < 128;
        if (tok && !inside) n += 1;
        inside = tok;
    }
    return n;
}

The pipeline, step by step

The same three files through the three stages, with the real line counts, sizes, symbol tables and messages (Apple clang 17, -std=c++20); bars are to scale by line count. Predict before you pick "Forgot tokens.o": which stage fails, the compiler or the linker?

  1. Three source files. A header that declares count_tokens, a .cpp that defines it, and main.cpp that calls it: 25 lines together.
  2. main.cpp's translation unit. The preprocessor pastes tokens.h, and through it the standard headers, into main.cpp: 55,693 lines for the compiler to read. The last lines are your code (the closed block under the pipeline shows them).
  3. tokens.cpp's translation unit. tokens.cpp becomes its own translation unit of 55,700 lines. The two are processed separately; neither sees the other.
  4. Two object files. Each translation unit compiles to an object file of machine code: main.o needs count_tokens and printf (U); tokens.o defines count_tokens (T). The compiler trusted the declaration in tokens.h.
  5. The link. The linker matches main.o's U count_tokens to tokens.o's T (now green), leaves printf to the dynamic system library, and writes the executable.
  6. It runs. "C++ is fun, x86_64 too" has 6 tokens under the root page's rule (C, is, fun, x86, 64, too).
  1. Two object files, as before. Preprocessing and compiling went exactly as in a correct build: main.o needs count_tokens (U), tokens.o defines it (T).
  2. Link only main.o. Nothing defines count_tokens, so the linker (ld), not the compiler, fails: "Undefined symbols". The compile step had succeeded.
  1. A body in a header. util.h defines a function body, not just a declaration, and both a.cpp and b.cpp include it.
  2. Two copies. After preprocessing, each translation unit contains its own copy of twice().
  3. Two definitions. So each object file defines twice(int): two T entries for one name.
  4. The linker refuses. The one definition rule is broken: "duplicate symbol".
  5. The fix. Mark the function inline (util_inline.h). The linker keeps one copy; the program links and exits with 0.
  1. A CMake build. The CMake project below builds tokens.cpp into a static library, libtokens.a, and links it into tokcount. Ninja records what each output was built from.
  2. Edit tokens.cpp. (Here: touch it.) Only tokens.cpp recompiles; the library and the program relink. main.cpp is untouched.
  3. Edit tokens.h. Both .cpp files include it, so both recompile: headers are why big C++ projects rebuild slowly.
  4. Change nothing. Build again: nothing to do.

Reading a symbol table (nm): T (green) is defined here, U (red) is used here and defined elsewhere. The linker must find exactly one T for each U: none is "Undefined symbols", two is "duplicate symbol". The compiler accepted main.cpp on the header's promise alone, so a missing definition is always the linker's error.

The one definition rule (ODR) says a function may be defined once in the whole program. A function body in a header included from two .cpp files gives each object file its own copy: "duplicate symbol" from ld on macOS (GNU ld says "multiple definition"). The fix is inline ("identical copies may appear; keep one") or only a declaration in the header. Functions defined inside a class body, templates and constexpr functions are implicitly inline, which is why headers full of them link fine.

Python bridge
A header is like a .pyi stub (types only) that every user pastes into their file. Python resolves names when the line runs; C++ resolves them at link time, so a missing or duplicated function is a build error, never a run-time NameError.

CMake: the build system

CMake is the de facto standard build description: you list targets (executables, libraries) and their properties, and CMake generates the commands for a build tool such as Ninja. A real project separates a library from the program that uses it:

CMakeLists.txt
cmake_minimum_required(VERSION 3.28)
project(tokcount LANGUAGES CXX)

# A library target: compiled once, linked into anything that needs it
add_library(tokens src/tokens.cpp)
target_include_directories(tokens PUBLIC src)      # users of tokens see src/
target_compile_features(tokens PUBLIC cxx_std_20)  # and get C++20
target_compile_options(tokens PRIVATE -Wall -Wextra)

add_executable(tokcount src/main.cpp)
target_link_libraries(tokcount PRIVATE tokens)     # brings the include dir and C++20 along

PUBLIC properties travel to every target that links the library; PRIVATE ones do not: the single most useful idea in CMake. In the generated commands, -Icmake2/src and -std=gnu++20 reached main.cpp; -Wall -Wextra did not. The library became a static library libtokens.a (an archive of object files, made by ar). The payoff of separate compilation is incremental builds: editing a .cpp recompiles one file, editing a header recompiles everything that includes it.

2. Undefined behaviour

The C++ standard lists operations whose result it does not define: reading outside an array or freed memory, overflowing a signed integer, reading an uninitialised variable, two threads writing one variable without synchronisation, falling off the end of a function that returns a value, and others. Such a program has undefined behaviour (UB): not "a wrong answer" but no meaning at all. The compiler is allowed to assume UB never happens, and its optimiser uses that assumption to delete checks and simplify code. So a program with UB can work at -O0 and break at -O2, or work today and break after a compiler upgrade. This is the deepest difference from Python, where every one of these is either impossible or an exception.

The classic example: "will x + 1 overflow?" written the obvious way.

overflow.cpp
#include <climits>
#include <cstdio>

// "Will adding 1 overflow?" written the way you would in Python
__attribute__((noinline)) bool will_overflow(int x) {
    return x + 1 < x;   // signed overflow is UB, so the compiler may assume x + 1 > x
}

int main() {
    std::printf("will_overflow(INT_MAX) = %d\n", will_overflow(INT_MAX));
}
Predict, then reveal: compiled with -O2, what does will_overflow(INT_MAX) return? And at -O0? 
$ clang++-23 -std=c++23 -O0 overflow.cpp -o overflow && ./overflow
will_overflow(INT_MAX) = 1
$ clang++-23 -std=c++23 -O2 overflow.cpp -o overflow && ./overflow
will_overflow(INT_MAX) = 0

At -O0 the addition wrapped around to a negative number and the test said 1. At -O2 the compiler reasoned "signed overflow cannot happen, so x + 1 < x is always false" and compiled the function to return false.

Neither build reported anything. The same assumption is what makes signed loop counters fast: a signed counter never overflows, so i + 1 > i and the loop's trip count can be computed without wrap-around checks, which enables vectorisation and widening it to 64 bits. Sanitizers are compiler modes that add run-time checks for UB; UndefinedBehaviorSanitizer (UBSan) catches this one:

$ clang++-23 -std=c++23 -O2 -fsanitize=undefined overflow.cpp -o overflow && ./overflow
overflow.cpp:6:14: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
SUMMARY: UndefinedBehaviorSanitizer: undefined-behavior overflow.cpp:6:14 
will_overflow(INT_MAX) = 1

(Under UBSan the program prints 1 again: the instrumented build computes the addition so it can check it.) The fix is to test before adding: x == INT_MAX, or __builtin_add_overflow, or C++26's <stdckdint.h> checked arithmetic. Unsigned integers do not have this problem: they wrap around by definition.

Your defences

  1. Warnings: -Wall -Wextra always, -Werror in CI. They caught the uninitialised read, the dangling string_view and the missing return in the gallery.
  2. Sanitizers in tests: ASan (out of bounds, use after free, double free), UBSan (overflow, bad shifts, missing return), TSan (data races). They slow the program, so they run in tests, not production.
  3. A hardened standard library: libc++ can check v[i], front(), string_view bounds and more, turning silent UB into a trap.
  4. Initialise everything; C++26 turns reading an uninitialised local into erroneous behaviour, a defined (wrong) value the implementation may diagnose, instead of UB (P2795).
  5. Prefer what cannot be misused: .at(i) or a hardened library over raw indexing in non-hot code, smart pointers over new, values over references when lifetimes are unclear.
The defences in detail: flags, slowdowns, hardening modes (documentation checked 2026-10-05)
  • Flags: -fsanitize=address (ASan), -fsanitize=undefined (UBSan), -fsanitize=thread (TSan). Slowdown: about 2 times for ASan per its documentation, 5 to 15 times for TSan per its documentation.
  • On this Mac Apple's own ASan did not start (the root's Toolchain atlas records it); LLVM clang 23's worked, and every sanitizer report on this page is from it.
  • libc++ hardening: -D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST is meant for production (cheap checks, a silent trap); the _DEBUG mode prints why (the "Index past the end" case shows both).
  • -ftrivial-auto-var-init=zero made the uninitialised example print "not seen" at -O2.
The honest summary
No tool catches all UB, and sanitizers find only what your tests execute. C++ makes you responsible for memory safety; Rust moves most of this list into compile errors (Rust: the essentials, and the root page's comparison).

3. Libraries: header-only, static, dynamic, and getting them

Python has pip install and wheels. C++ has no official package manager, and the reason is technical: a compiled C++ library works with your program only if it was built with a compatible compiler, standard library and flags (the same ABI, application binary interface; the machine page, section 11). A mismatch gives link errors or, worse, silent memory corruption. So shipping prebuilt binaries is much harder than in Python, and the historical answer was "build it yourself" or "copy the source in". Three ways a library reaches your program:

  • Header-only: the whole library is headers (all inline functions and templates), so there is nothing to build or link: nlohmann/json, Catch2, Eigen. It sidesteps packaging and ABI, and costs compile time in every file that includes it.
  • Static library (.a, .lib): object files copied into your executable at link time, like libtokens.a in section 1. One self-contained binary; every program carries its own copy.
  • Dynamic (shared) library (.dylib, .so, .dll): loaded when the program starts. Smaller binaries and shared updates, but the library must be present, at a compatible version, on the machine that runs it. Even the small program from section 1 depends on two, libc++ and libSystem:
$ otool -L app
app:
	/usr/lib/libc++.1.dylib (compatibility version 1.0.0, current version 2000.63.0)
	/usr/lib/libSystem.B.dylib (compatibility version 1.0.0, current version 1356.0.0)

Getting dependencies, oldest to newest: system packages, vendoring the source (llama.cpp does), CMake FetchContent, then the package managers vcpkg and Conan. The build system (CMake) and the package manager are separate tools, and there is no lock-file culture like uv.lock: pin versions and record the toolchain. Two files compiled with different flags that see different definitions of the same thing break the one definition rule, silently.

4. Which standard: ask for one, always

C++ is standardised by an ISO committee (WG21) on a three-year train: C++11, 14, 17, 20, 23, 26. Nothing old is removed, so "modern C++" is a subset you choose to write, the one these pages teach. Each compiler and standard library implements each standard gradually, and the two can differ: a feature needs both. The default language version differs between compilers and even versions of one compiler; measured here, Apple clang 17 defaults to C++14 and Apple clang 14 to C++98. So pass -std=c++20 or newer, or in CMake target_compile_features(t PUBLIC cxx_std_20). Write C++20 as the baseline and use C++23 where your compilers report it; C++26 is finished on paper and mostly not shipped.

Modules replace textual #include with compiled interfaces (import std;), attacking the 55,000-line problem of section 1. The language feature is in C++20 and import std in C++23, but tooling still lags: GCC 16's notes say modules support "is still experimental and must be enabled by -fmodules", and CMake supports named modules since 3.28 but import std only behind an experimental gate (cmake-cxxmodules). Headers remain the pragmatic default in 2026; llama.cpp uses them.

Corrections to the old "C++: modern practice and standards status" page
  • "C++26 was finalized in March 2026": the technical work finished on 2026-03-28 in London (Croydon); then comes the international ballot (DIS) and ISO publication, which was not confirmed as of 2026-10-05.
  • "C++20 is the production baseline nearly everywhere": as a target, yes; as a default, no. Only GCC 16 defaults to C++20; Clang defaults to C++17, MSVC to C++14, and Apple clang 17 here to C++14 (measured above).
  • "MSVC completes /std:c++23 with Build Tools 14.52": not yet true. The current release is 14.51 in Visual Studio 2026 18.10.3 (2026-09-29) and Microsoft's documentation still lists /std:c++23preview (root page, Toolchain atlas corrections).
  • "Pattern matching did NOT make it": confirmed in the sense that cppreference's C++26 feature list has no pattern matching.
  • The old list of C++26 features is otherwise right; this page adds hardening and erroneous behaviour, the two that change day-to-day safety.

5. Mistakes that catch experienced people, and a hygiene checklist

Each of these compiles. Most are lifetime bugs: a second owner, or a reference that outlives its owner.

MistakeWhat actually happensShown on
A string_view, span or range view that outlives its ownerViews do not own; one made from a temporary dangles at the semicolonGallery

Four of these in detail (range-for temporaries, static order, unsigned loops, the race)
  • Range-for over a member of a temporary, for (auto& x : make().items()), dangled until C++23 extended the lifetime of every temporary in the range-for initializer (P2718); the same expression outside a range-for still dangles, so the old page's "fixed for some cases in C++23, not all" stands.
  • Static initialisation order: one global's constructor that uses another global from a different file may see it unconstructed. Use a function returning a reference to a function-local static, which is initialised on first use.
  • for (size_t i = v.size() - 1; i >= 0; --i): size_t is unsigned, so i >= 0 is always true; an empty vector makes even the first value huge. Mixing signed and unsigned in a comparison converts the signed side to unsigned (clang warns with -Wextra).
  • The race: the optimiser turned each thread's loop into one addition, which hid the lost updates. Use std::atomic or a mutex.

Hygiene checklist

  • RAII everywhere; no naked new/delete; unique_ptr by default.
  • Rule of zero: hold members that clean up after themselves (std::vector, std::string, unique_ptr) and write no special member at all; if you must write one, write all five, with noexcept moves.
  • Parameters: string_view and span<const T> to read; never store them past the call without thought.
  • const by default; constexpr where a value can be computed at compile time.
  • auto for iterators, lambdas and long type names; concrete types at API boundaries.
  • Build with -std=c++20 or newer and -Wall -Wextra (-Werror in CI); ASan, UBSan and TSan in CI test runs; clang-format and clang-tidy; CMake targets with PUBLIC/PRIVATE properties, presets, and vcpkg or Conan.
