C++: the machine underneath: caches, layout, SIMD and the memory model

What the processor and memory do with compiled code: the cache ladder, cache lines and data layout, assembly, SIMD, branch prediction, atomics and memory order, the CPU's measured roofline and the ABI. Every number measured on an Apple M1 Pro by small C++ programs you can read in full. Reading: 30 min, plus 20 in closed details. Data as of October 2026.
The idea in one sentenceOnce a loop compiles to a handful of machine instructions, memory, not arithmetic, sets its speed: where the data sits in the cache ladder, how it is laid out in cache lines and whether the compiler could turn it into independent SIMD work decide whether the same loop runs 50 times faster or slower.

One load from DRAM costs as much time as 13,000 floating-point operations

Time for one operation, log scale, all on this M1 Pro. A load from L1 (about 1 ns) is as cheap as one fused multiply-add; a load whose address the hardware cannot predict, from a 512 MB buffer, takes about 133 ns; in that time one core running at its measured peak of 97.5 GFLOP/s could have done 97.5 x 133 = about 13,000 FLOPs derived. The same 512 MB read in address order costs about 11 ns per load, because the prefetcher fetches ahead. The rest of the page is how to stay on the left of this picture.

You need: how C++ is compiled and linked, and what undefined behaviour means (C++: the essentials); new, RAII and moves (C++: ownership, moves and object lifetimes). Python habits are enough for the rest: each section says where NumPy or CPython meets the same machine.

Cache line: the unit memory moves in, 128 bytes on Apple silicon (64 on most x86).
Prefetcher: hardware that spots a regular address pattern and fetches lines before they are asked for.
AoS / SoA: array of structs (records side by side) / struct of arrays (one array per field).
SIMD, NEON: one instruction on a short vector (4 floats in a 128-bit NEON register on ARM).
Dependency chain: instructions that each wait for the previous result; its length, not the instruction count, sets the time.
Misprediction: the core guessed a branch wrong and throws away the work it did on the guess.
Memory order: what an atomic operation promises about the order other cores see writes in (relaxed, acquire, release, seq_cst).
False sharing: two threads writing different variables on one cache line, fighting over the line.
ABI: the binary contract between compiled pieces: registers, layouts, symbol names.

Why Python never showed you this
In CPython, total += x costs tens of nanoseconds whatever the data looks like, because the interpreter's own work dwarfs the memory access (Python: CPython internals and performance). Once a loop compiles to a few machine instructions, as in C++, Rust or inside NumPy, the memory system is what is left. That is why numpy.sum on a contiguous array is fast and on a strided view can be much slower.

1. The ladder of caches

An addition takes a fraction of a nanosecond; fetching a number from DRAM takes about a hundred. To hide the gap the chip keeps copies of recently used memory in caches, each level bigger and slower than the one before: on this M1 Pro, 128 KB of L1 per performance core, 12 MB of L2 shared by the 8 performance cores, a system level cache shared with the GPU (size unpublished), then 16 GB of DRAM, "up to 200GB/s" for the chip (Apple).

To time one load you must stop the processor from overlapping loads. A pointer chase does it: a linked list scattered over a buffer, each node holding the address of the next, so load k+1 cannot start before load k returns. Time per load is the latency of whatever level holds the buffer; grow the buffer from 4 KB to 1 GB and each level overflows in turn.

Each time the buffer outgrows a cache, a load gets several times dearer

Measured: ladder.cpp, one node per 128-byte line, best of 3 timings inside each run; three runs in random order, two in address order (load average per run: ). Step through the sizes, or hover or tap the chart to read any point; the linear scale shows how far DRAM is.

Up to 128 KB (L1) a load costs about 1 ns, three clock cycles. Past that the buffer lives in L2 and loads cost 5 to 15 ns. From about 8 MB they climb towards DRAM's roughly 125 ns, a hundred times L1. The steps are soft because other programs share L2 and DRAM, and because past a few MB the chase also misses in the TLB, the cache of address translations (Virtual memory owns it).

Predict. The same 512 MB buffer, but the list visits the nodes in address order (node 0, 1, 2, ...). Each load still waits for the previous one. Still about 125 ns per load?

No: ns per load in address order, against ns in random order, over the same 512 MB. The prefetcher notices that addresses go up by 128 bytes each time and fetches the next lines before they are asked for. Predictable access is the cheapest optimisation there is: you get it by storing data in the order you read it.

A hash-table lookup or linked-structure walk over a big table pays the right-hand end of this chart per hop; a scan over a contiguous array pays the bottom curve or less. Shrinking the working set by one level (from DRAM-sized to L2-sized) is often worth more than any change to the arithmetic.

In Python

2. Cache lines: use what you fetched


Caches hold cache lines, aligned blocks of 128 bytes on this M1 Pro (hw.cachelinesize; 64 on most Intel and AMD processors). Reading one byte brings its whole line into L1. Two habits follow. Spatial locality: use the neighbours of what you just read, since they arrived with it (a line holds 32 floats, so reading them in order costs one trip to memory per 32 numbers). Temporal locality: reuse data soon, before other data evicts it; blocked ("tiled") matrix multiplication is this idea.


The test: a 4096 x 4096 matrix of 32-bit integers (64 MB) stored row after row, as C++ and NumPy lay it out by default, summed row by row and then column by column. Same additions, same answer.

Down a column, consecutive elements are 4096 x 4 = 16 KB apart, so every addition needs a new line and uses 4 of its 128 bytes; by the time the loop returns for the next column the line has been evicted. Row order uses every byte of every line, the prefetcher sees a simple stream, and the compiler can add 4 integers per instruction (section 6): cache lines and SIMD multiply.

3. Data layout: padding, AoS and SoA


A C++ struct is laid out exactly as declared, fields in order, under two rules. Alignment: each type must start at an address divisible by its alignof (4 for int32_t, 8 for double or a pointer), so it loads in one go. Padding: the compiler inserts unused bytes to satisfy alignment, between fields and at the end (so the next array element is aligned too); sizeof includes them.




Predict. Bad holds 1 + 8 + 4 = 13 bytes of data. What does sizeof(Bad) print? And Good, the same fields largest first?



24 and 16 bytes: 11 of Bad's 24 bytes are padding (7 after flag so that score starts at 8, and 4 at the end so that the size is a multiple of its alignment, 8). Ordering fields from largest to smallest alignment removes most of it: a third fewer cache lines for an array of them. Clang's -Wpadded lists every hole. The last line returns in section 8.


Array of structs against struct of arrays


An array of structs (AoS, std::vector<Token>) stores records one after another; a struct of arrays (SoA) stores one array per field. AoS is what object-oriented code produces; SoA is what columnar formats (Arrow, Parquet), dataframes and tensors use. 4. Pages and mmap, as a C++ program meets them


Addresses are virtual, mapped one page at a time; on Apple silicon a page is 16 KB (hw.pagesize printed 16384; 4 KB on most Linux machines). The mechanism (page tables, the TLB, page faults, the page cache) belongs to Virtual memory. Two consequences for C++ code, measured here: new of a big block only reserves addresses, and the first touch of each page is a page fault costing about  microseconds (three runs: ); and mmap of a 512 MB file took  ms whatever its size, with pages read only when touched. That is why llama.cpp maps model files: loading is nearly instant, processes running the same model share the physical pages, and a restart finds the weights still cached (Local and on-device inference measures it for safetensors and GGUF).

6. SIMD: one instruction, several numbers


SIMD (single instruction, multiple data) applies one operation to a short vector held in one wide register. On ARM it is NEON: 32 registers of 128 bits, each 4 floats, 8 16-bit values or 16 bytes; fmla v0.4s, v1.4s, v2.4s does four multiply-adds at once. On x86 the same ideas are SSE (128 bits), AVX2 (256 bits: 8 floats) and AVX-512 (16 floats), with intrinsics such as _mm256_fmadd_ps (Intel intrinsics guide). This M1 Pro also reports the 8-bit dot-product extension (FEAT_DotProd: 1) but not BF16, I8MM or SME (all 0 in sysctl); llama.cpp's quantised kernels check for exactly these features.


Three ways to get SIMD code: let the compiler vectorise a plain loop, write intrinsics (C functions that map one to one onto SIMD instructions, from <arm_neon.h>; Arm intrinsics reference), or call a library that did (BLAS, Accelerate, ggml). 7. Branch prediction


A core works on hundreds of instructions at once in a pipeline. At an if it cannot wait to learn which way to go, so a branch predictor guesses from the branch's history and the core runs ahead on the guess. 8. Atomics and the C++ memory model


A data race (two threads touching the same memory, at least one writing, nothing ordering them) is undefined behaviour in C++; threads, locks and atomics as operating-system mechanisms belong to Concurrency. What the hardware adds: cores do not see each other's writes in the order they were made. Each core writes into a private store buffer before the shared caches and runs loads early, out of order. x86 keeps stores in order (a strong model); ARM, including this chip, does not (a weak model); the compiler may reorder too. So C++ defines a memory model, and each atomic operation (a std::atomic<T> read or write that can never be torn) states the order it needs (cppreference):

acquire (on a load)If I see a released value, I also see everything written before it. "Subscribe."ldapr (load-acquire)


seq_cst (the default)Acquire and release, plus one single order of all such operations that every thread agrees on. Easiest to reason about, slightly dearer.stlr / ldar

9. The CPU's roofline, measured


A kernel is limited either by arithmetic or by bytes from memory; the roofline (attainable FLOP/s = min(peak, arithmetic intensity x bandwidth)) says which. The concept, the ridge point and decode and prefill bounds belong to Performance math; the hardware root's Roofline lab plots these CPU roofs beside the M1 GPU and datacenter chips. Here is the C++ that measured the CPU side (roof.cpp, -O3 -ffast-math, three runs each):




The matrix-vector product is LLM decoding. One token multiplies every weight matrix by one vector: each weight is read once for one multiply-add, 2 FLOPs per 4 bytes in fp32 (intensity 0.5), far left of the ridge. The measured matvec sits right on the memory roof, 0.5 x bandwidth, so decode speed is set by bytes: tokens per second are at most bandwidth over bytes of weights. That is why quantisation and batching speed up serving (Topic: inference-and-serving).


How the peak was reached, why the matrix-matrix product stays at a quarter of it, and the decode ceilings on this laptop






The peak loop runs 24 independent fmla.4s chains so that all four floating-point units stay busy (4 units x 4 lanes x 2 FLOPs = 32 FLOPs per cycle, about 102 GFLOP/s at 3.2 GHz; measured ). A first version with 12 chains of the form a = y + a * x reached only 64 GFLOP/s: the compiler had to add a register copy before every fmla, because fmla overwrites its accumulator. The bandwidth row reads a 512 MB array once: one core reaches about half of the chip's 200 GB/s, all eight about  GB/s (the GPU shares the rest).


The matrix-matrix product is compute-bound (intensity about 85 FLOPs per byte for 512 x 512 matrices read once), yet the simple tiled loop reached only about a quarter of peak: it is limited by loads and stores inside the core, not by DRAM. Libraries close that gap with register blocking (keeping a small tile of the output in registers across the whole inner loop); on the GPU that craft is Topic: cuda-and-gpu-programming.

10. Measuring: counters, and why microbenchmarks lie


Profile before optimising: a sampling profiler records where the program is thousands of times a second (which profiler answers which question is Scheduling and CPU time; flame graphs for services are Capacity planning and performance). For one hot loop the quickest health check is two hardware counters, instructions retired and cycles, and their ratio, instructions per cycle (IPC). macOS's /usr/bin/time -l prints both. The column walk ran 4 times as many instructions (no SIMD) and still spent most cycles waiting:  instructions per cycle against . An IPC well below 1 on a loop says "waiting for memory" (or for mispredicted branches); 3 or more says the core is busy computing.


Why microbenchmarks lie, and the profilers not run here




    

  • The compiler deletes unused work. If a result is never used, the loop may vanish. Every benchmark here passes results to keep(), an empty asm volatile that forces the value to exist (bench.h); Google Benchmark calls it benchmark::DoNotOptimize.
    • 

  • Caches are warm. A loop timed a million times on the same few KB runs from L1; the same code in a real program meets cold data. The NEON dot product ran about twice as fast in L1 as from DRAM, and a load from DRAM costs 100 times one from L1 (section 1).
    • 

  • The compiler sees your test data. A constant input can be folded away (section 5's formula).
    • 

  • A debug build means nothing. -O0 keeps every variable in memory and calls every function; benchmark optimised builds, with debug info (-O2 -g) for profiling.
    • 

  • Cores differ and clocks move. This chip has fast and slow cores; macOS cannot pin a thread to a core, so the benchmarks ask for the highest quality-of-service class and report the best of several runs.
    • 

  • The machine is busy. Every timing on this page says how many runs it took and how far they spread, and records the load average. Multi-threaded results spread most.
    • 



Not run here: Instruments' Time Profiler (xcrun xctrace record --template 'Time Profiler' --launch -- ./prog) hung even for xctrace version, the built-in sample tool could not attach in this session, and Linux's perf record -g, perf report and perf stat (perf wiki) need a Linux machine. Treat those commands as reference.









11. The ABI: C++'s binary contract


An API is a contract in source code. An ABI (application binary interface) is the contract between already-compiled machine code: which registers carry arguments (section 5), how structs are laid out (section 3), how virtual tables and exceptions work, and what symbols are called. Two object files work together only if they agree on all of it; Python programmers meet it as "this wheel does not match your Python" or a crash after mixing builds.


Name mangling. C has one function per name; C++ allows the same name in different namespaces and overloads, so the compiler encodes the namespace and parameter types into the symbol, following the Itanium C++ ABI (used by clang and GCC everywhere except Windows, despite its name). extern "C" turns mangling off, which is why every C++ library meant to be called from another language exposes a C interface.






Read __ZN9ggml_like3dotEPKfS1_i as: _Z a mangled name (macOS adds one more underscore), N ... E a nested name of 9ggml_like (9 characters) and 3dot, then the parameters: PKf pointer to const float, S1_ the same type again, i int. The double overload differs only in d; c_dot is just _c_dot.


From Python
ctypes and cffi call only C symbols, so they need extern "C". pybind11 and nanobind compile C++ against CPython's own C ABI; a wheel built for one Python version works only on that version unless it uses the limited "abi3" stable ABI (Rust: speeding up Python with PyO3 and maturin covers abi3 wheels).


What breaks when you mix builds


    

  • Different standard libraries. clang on macOS uses libc++; GCC on Linux uses libstdc++. Their std::string, std::vector and friends have different layouts, so a std::string cannot cross between code built against the two. Within one library, flags that change layouts (debug iterators, _GLIBCXX_USE_CXX11_ABI on Linux) must match.
    • 

  • Standard library designs that cannot be fixed. Programs compiled years ago still link against today's shared standard library, so vendors avoid any change to a type's layout or a function's mangled name; known-slow designs (std::unordered_map's node-based buckets, std::regex) stay as they are for that reason.
    • 

  • Headers and flags out of step. Two translation units that see different definitions of the same struct (a different #define, packing pragma or alignment) break the one-definition rule: no error, just corrupted fields at run time.
    • 

  • Mixing compilers is fine through a C interface, risky through C++ types, and the reason C++ has no universal package of prebuilt binaries like PyPI's wheels (builds and package managers are on C++: the essentials).
    • 



Apple's ARM64 ABI differs from the standard Linux one in a few details (for example, how variadic arguments are passed): Writing ARM64 code for Apple platforms.









12. To the GPU: the same ideas with the dials turned


Everything above carries over to GPUs: SIMD becomes SIMT (a warp of 32 threads runs one instruction together, written as scalar code per thread), cache lines become coalescing (a warp should read neighbouring addresses), a mispredicted branch becomes divergence (both paths run in turn), and the roofline's ridge moves far right, so LLM decode is even more memory-bound. The owners: The CUDA programming model for threads, warps and divergence, GPU memory hierarchy for coalescing and shared-memory tiling. CUDA C++ is C++ with extensions; this page and the essentials are its prerequisites.
