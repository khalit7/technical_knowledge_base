8. Atomics and the C++ memory model

A data race (two threads touching the same memory, at least one writing, nothing ordering them) is undefined behaviour in C++; threads, locks and atomics as operating-system mechanisms belong to {{Concurrency|n:3f05c17b0d0d8112ad1af99308fa913f}}. What the hardware adds: cores do not see each other's writes in the order they were made. Each core writes into a private store buffer before the shared caches and runs loads early, out of order. x86 keeps stores in order (a strong model); ARM, including this chip, does not (a weak model); the compiler may reorder too. So C++ defines a memory model, and each atomic operation (a std::atomic<T> read or write that can never be torn) states the order it needs ({{cppreference|https://en.cppreference.com/w/cpp/atomic/memory_order}}):

OrderIn plain wordsARM64 code (real)
relaxedThis operation is atomic; no promise about the order of other memory operations around it. Right for counters and statistics.plain ldr / str
release (on a store)Every write I made before this store is visible to whoever sees this store. "Publish."stlr (store-release)
acquire (on a load)If I see a released value, I also see everything written before it. "Subscribe."ldapr (load-acquire)
seq_cst (the default)Acquire and release, plus one single order of all such operations that every thread agrees on. Easiest to reason about, slightly dearer.stlr / ldar

Rare and real: a reader on this processor can see the flag before the data, so code that "works in testing" with relaxed atomics or plain variables can fail once in millions of messages in production. Release on the flag's store and acquire on its load forbid the outcome, and the instructions in the table enforce it.


Plain variables are worse: the compiler deletes the wait. The same pattern with an ordinary bool ready, run 300 times, sometimes prints 0 at -O2 and never at -O0. Thread B's assembly at -O2 has no loop at all: a data race is undefined behaviour, so the compiler may assume ready cannot change while while (!ready) {} spins; a side-effect-free loop that never ends is also undefined behaviour ({{[intro.progress]|https://eel.is/c++draft/intro.progress}}), so it assumes the loop ends and deletes it. 9. The CPU's roofline, measured


A kernel is limited either by arithmetic or by bytes from memory; the roofline (attainable FLOP/s = min(peak, arithmetic intensity x bandwidth)) says which. The concept, the ridge point and decode and prefill bounds belong to {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}; the hardware root's {{Roofline lab|n:3c65c17b0d0d8118beeefaed56da6f8e#t-roof}} plots these CPU roofs beside the M1 GPU and datacenter chips. The matrix-vector product is LLM decoding. One token multiplies every weight matrix by one vector: each weight is read once for one multiply-add, 2 FLOPs per 4 bytes in fp32 (intensity 0.5), far left of the ridge. The measured matvec sits right on the memory roof, 0.5 x bandwidth, so decode speed is set by bytes: tokens per second are at most bandwidth over bytes of weights. That is why quantisation and batching speed up serving ({{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}).


How the peak was reached, why the matrix-matrix product stays at a quarter of it, and the decode ceilings on this laptop






The peak loop runs 24 independent fmla.4s chains so that all four floating-point units stay busy (4 units x 4 lanes x 2 FLOPs = 32 FLOPs per cycle, about 102 GFLOP/s at 3.2 GHz; measured ). A first version with 12 chains of the form a = y + a * x reached only 64 GFLOP/s: the compiler had to add a register copy before every fmla, because fmla overwrites its accumulator. The bandwidth row reads a 512 MB array once: one core reaches about half of the chip's 200 GB/s, all eight about  GB/s (the GPU shares the rest).


The matrix-matrix product is compute-bound (intensity about 85 FLOPs per byte for 512 x 512 matrices read once), yet the simple tiled loop reached only about a quarter of peak: it is limited by loads and stores inside the core, not by DRAM. Libraries close that gap with register blocking (keeping a small tile of the output in registers across the whole inner loop); on the GPU that craft is {{Topic: cuda-and-gpu-programming|n:3c65c17b0d0d81c39f34d5e070d783c1}}.
