10. Measuring: counters, and why microbenchmarks lie

Profile before optimising: a sampling profiler records where the program is thousands of times a second (which profiler answers which question is {{Scheduling and CPU time|n:3f05c17b0d0d81ed9c18cc47c6bfdf76}}; flame graphs for services are {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}}). For one hot loop the quickest health check is two hardware counters, instructions retired and cycles, and their ratio, instructions per cycle (IPC). macOS's /usr/bin/time -l prints both. Why microbenchmarks lie, and the profilers not run here




    

  • The compiler deletes unused work. If a result is never used, the loop may vanish. Every benchmark here passes results to keep(), an empty asm volatile that forces the value to exist (bench.h); {{Google Benchmark|https://github.com/google/benchmark}} calls it benchmark::DoNotOptimize.
    • 

  • Caches are warm. A loop timed a million times on the same few KB runs from L1; the same code in a real program meets cold data. The NEON dot product ran about twice as fast in L1 as from DRAM, and a load from DRAM costs 100 times one from L1 (section 1).
    • 

  • The compiler sees your test data. A constant input can be folded away (section 5's formula).
    • 

  • A debug build means nothing. -O0 keeps every variable in memory and calls every function; benchmark optimised builds, with debug info (-O2 -g) for profiling.
    • 

  • Cores differ and clocks move. This chip has fast and slow cores; macOS cannot pin a thread to a core, so the benchmarks ask for the highest quality-of-service class and report the best of several runs.
    • 

  • The machine is busy. Every timing on this page says how many runs it took and how far they spread, and records the load average. Multi-threaded results spread most.
    • 



Not run here: Instruments' Time Profiler (xcrun xctrace record --template 'Time Profiler' --launch -- ./prog) hung even for xctrace version, the built-in sample tool could not attach in this session, and Linux's perf record -g, perf report and perf stat ({{perf wiki|https://perf.wiki.kernel.org/index.php/Tutorial}}) need a Linux machine. Treat those commands as reference.









11. The ABI: C++'s binary contract


An API is a contract in source code. An ABI (application binary interface) is the contract between already-compiled machine code: which registers carry arguments (section 5), how structs are laid out (section 3), how virtual tables and exceptions work, and what symbols are called. Two object files work together only if they agree on all of it; Python programmers meet it as "this wheel does not match your Python" or a crash after mixing builds.


Name mangling. C has one function per name; C++ allows the same name in different namespaces and overloads, so the compiler encodes the namespace and parameter types into the symbol, following the {{Itanium C++ ABI|https://itanium-cxx-abi.github.io/cxx-abi/abi.html#mangling}} (used by clang and GCC everywhere except Windows, despite its name). extern "C" turns mangling off, which is why every C++ library meant to be called from another language exposes a C interface.






Read __ZN9ggml_like3dotEPKfS1_i as: _Z a mangled name (macOS adds one more underscore), N ... E a nested name of 9ggml_like (9 characters) and 3dot, then the parameters: PKf pointer to const float, S1_ the same type again, i int. The double overload differs only in d; c_dot is just _c_dot.


From Python
ctypes and cffi call only C symbols, so they need extern "C". pybind11 and nanobind compile C++ against CPython's own C ABI; a wheel built for one Python version works only on that version unless it uses the limited "abi3" stable ABI ({{Rust: speeding up Python with PyO3 and maturin|n:4055c17b0d0d81048311c87e9b76a78a}} covers abi3 wheels).


What breaks when you mix builds


    

  • Different standard libraries. clang on macOS uses libc++; GCC on Linux uses libstdc++. Their std::string, std::vector and friends have different layouts, so a std::string cannot cross between code built against the two. Within one library, flags that change layouts (debug iterators, _GLIBCXX_USE_CXX11_ABI on Linux) must match.
    • 

  • Standard library designs that cannot be fixed. Programs compiled years ago still link against today's shared standard library, so vendors avoid any change to a type's layout or a function's mangled name; known-slow designs (std::unordered_map's node-based buckets, std::regex) stay as they are for that reason.
    • 

  • Headers and flags out of step. Two translation units that see different definitions of the same struct (a different #define, packing pragma or alignment) break the one-definition rule: no error, just corrupted fields at run time.
    • 

  • Mixing compilers is fine through a C interface, risky through C++ types, and the reason C++ has no universal package of prebuilt binaries like PyPI's wheels (builds and package managers are on {{C++: the essentials|n:3cd5c17b0d0d81ceadcee44fe9c023a0}}).
    • 



Apple's ARM64 ABI differs from the standard Linux one in a few details (for example, how variadic arguments are passed): {{Writing ARM64 code for Apple platforms|https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms}}.









12. To the GPU: the same ideas with the dials turned


Everything above carries over to GPUs: SIMD becomes SIMT (a warp of 32 threads runs one instruction together, written as scalar code per thread), cache lines become coalescing (a warp should read neighbouring addresses), a mispredicted branch becomes divergence (both paths run in turn), and the roofline's ridge moves far right, so LLM decode is even more memory-bound. The owners: {{The CUDA programming model|n:3c65c17b0d0d8162865eec15d9dae87e}} for threads, warps and divergence, {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}} for coalescing and shared-memory tiling. CUDA C++ is C++ with extensions; this page and the essentials are its prerequisites.
