2. Cache lines: use what you fetched

Caches hold cache lines, aligned blocks of 128 bytes on this M1 Pro (hw.cachelinesize; 64 on most Intel and AMD processors). Reading one byte brings its whole line into L1. Two habits follow. Spatial locality: use the neighbours of what you just read, since they arrived with it (a line holds 32 floats, so reading them in order costs one trip to memory per 32 numbers). Temporal locality: reuse data soon, before other data evicts it; blocked ("tiled") matrix multiplication is this idea.

The test: a 4096 x 4096 matrix of 32-bit integers (64 MB) stored row after row, as C++ and NumPy lay it out by default, summed row by row and then column by column. Same additions, same answer.

Down a column, consecutive elements are 4096 x 4 = 16 KB apart, so every addition needs a new line and uses 4 of its 128 bytes; by the time the loop returns for the next column the line has been evicted. Row order uses every byte of every line, the prefetcher sees a simple stream, and the compiler can add 4 integers per instruction (section 6): cache lines and SIMD multiply.




By columns, every element costs a whole line and the cache forgets it before it is reused

In NumPy and PyTorch
a.sum(axis=0) and a.sum(axis=1) face this choice; NumPy's reductions walk memory well either way, but your own loops over a[:, j], or a Fortran-ordered array handed to code expecting C order, do not. PyTorch's .contiguous() exists for this reason.







3. Data layout: padding, AoS and SoA


A C++ struct is laid out exactly as declared, fields in order, under two rules. Alignment: each type must start at an address divisible by its alignof (4 for int32_t, 8 for double or a pointer), so it loads in one go. Padding: the compiler inserts unused bytes to satisfy alignment, between fields and at the end (so the next array element is aligned too); sizeof includes them.




Predict. Bad holds 1 + 8 + 4 = 13 bytes of data. What does sizeof(Bad) print? And Good, the same fields largest first?



24 and 16 bytes: 11 of Bad's 24 bytes are padding (7 after flag so that score starts at 8, and 4 at the end so that the size is a multiple of its alignment, 8). Ordering fields from largest to smallest alignment removes most of it: a third fewer cache lines for an array of them. Clang's -Wpadded lists every hole. The last line returns in section 8.


Array of structs against struct of arrays


An array of structs (AoS, std::vector<Token>) stores records one after another; a struct of arrays (SoA) stores one array per field. AoS is what object-oriented code produces; SoA is what columnar formats (Arrow, Parquet), dataframes and tensors use. The test: 20 million token records of 8 four-byte fields (32 bytes each), summing one field, then all eight.

Correction to the old page
"C++: zero to expert" said array-of-structs versus struct-of-arrays "changes throughput by an order of magnitude". Measured here, the gain is the ratio of bytes read to bytes used, and only when memory is the bottleneck: about 8x for one field of a 32-byte record, about 1.2x when all fields are used, nothing when a chain of dependent float additions is the limit. A 64- or 128-byte record would give more than 10x for one field. Measure your own access pattern.


A tensor is SoA taken to the limit: one contiguous buffer per quantity. llama.cpp's quantised weights are a deliberate AoS: each block_q4_0 packs one 2-byte scale with the 32 four-bit weights it scales (18 bytes), because the dot product needs both together ({{C++: reading llama.cpp|n:4055c17b0d0d8150a5effbb5a667dd9d}} reads its kernels).


Values, not pointers. A container of pointers is a pointer chase too: every make_unique calls the allocator and puts the object somewhere else on the heap. Ten million separate heap objects cost about x as much as one reserved vector of values. How malloc finds space is {{Memory allocators|n:3f05c17b0d0d81209ae9d856695dc958}}' subject.

Rules: reserve when you know the size, store values rather than pointers, reuse buffers across iterations, and make large objects movable so containers move rather than copy them (the ownership page covers moves).
