C++: ownership, moves and object lifetimes

When each C++ object dies and who decides: values and references, the stack and the heap, destructors and RAII, unique_ptr, shared_ptr and weak_ptr, moves, copy elision, noexcept and the rule of zero; every trace and timing from real runs on an Apple M1 Pro. Reading: 19 min, plus 13 in closed details. Data as of October 2026.
The idea in one sentenceEvery C++ object has exactly one lifetime, and it ends at a moment you can point to in the source: the closing brace of its scope, or the destruction of its owner; RAII ties resources to that moment, and moves hand an object's contents to a new owner instead of copying them, so ownership, not a garbage collector, decides when memory is freed.

Python counts references; C++ gives each object one owner and frees it at a known line

Left: in Python, a, b and a dict entry are three names for one heap object; it dies when its reference count reaches 0, at a time no line of your code names, and a cycle waits for the cycle collector. Right: in C++, v is the object: 24 bytes on the stack holding a pointer to its heap buffer, which it owns. A reference r only observes. At the closing brace v's destructor frees the buffer. Every section below is a variation on this picture: who the owner is, when it dies, and how ownership moves.

You need: how a C++ program is compiled and what undefined behaviour means (C++: the essentials). Python is the bridge throughout; nothing else is assumed.

Lifetime: from the end of an object's constructor to the start of its destructor.
Owner: the object whose destructor ends another object's lifetime (a vector owns its buffer).
RAII: "resource acquisition is initialisation": a resource is held by an object whose destructor releases it.
Stack unwinding: destroying the locals of every scope an exception leaves.
unique_ptr, shared_ptr, weak_ptr: one owner; counted owners; an observer of counted owners.
lvalue, rvalue: an expression with a name that will be used again; a temporary about to disappear.
Move: building an object by taking another's contents (its heap buffer) instead of copying them.
Copy elision: the compiler builds a returned object directly in the caller's variable: no copy, no move.
Special members: destructor, copy and move constructors, copy and move assignment.

1. Values, references and pointers

In Python every variable is a name bound to an object on the heap, and b = a binds a second name to the same object. In C++ a variable is the object: its bytes live where the variable lives. So assignment and initialisation copy, and a second name has to be asked for.

copy.cpp (lines 4 to 8)
int main() {
    std::vector<int> a{1, 2, 3};
    std::vector<int> b = a;    // a COPY: b gets its own three ints
    b.push_back(4);
    std::printf("a has %zu, b has %zu\n", a.size(), b.size());

A reference or pointer that outlives its object dangles, and reading through it is undefined behaviour, the root of every dangling-reference bug (the essentials page's undefined behaviour section and its UB gallery show them crash, or worse, not crash).

const marks something read-only, checked by the compiler. Its everyday use is the parameter type const T&: "let me read your object without copying it, and I promise not to change it". With pointers, const can apply to the pointed-at object or to the pointer itself; read the declaration right to left (int* const q: q is a const pointer to int).

2. Where objects live: the stack, the heap and static storage

A C++ object lives in one of three kinds of storage, and the kind decides when it dies:

  • Automatic storage, "the stack": local variables. Each function call pushes a frame for its locals and pops it on return. Allocation is free (the stack pointer moves) and destruction happens at the closing brace }, in reverse order of creation.
  • Dynamic storage, "the heap": objects created with new (properly, with std::make_unique, section 4). They live until someone destroys them. Allocation calls the memory allocator (malloc), which costs tens of nanoseconds and can fragment memory; how it does that is Memory allocators' subject.
  • Static storage: globals and static variables, alive for the whole program.

Python puts every object on the heap and frees it when its reference count reaches zero (Memory allocators also owns reference counting and the cycle collector as memory behaviour). C++ lets you put most things on the stack. One program printing the addresses of each kind:

The vector object sits on the stack; its elements sit on the heap, owned by it

Real addresses from one run of stack_heap.cpp measured (they change on every run: macOS randomises where each region starts). The stack addresses (0x16...) go down as variables are added: on this ARM Mac the stack grows towards lower addresses. The std::vector object itself is 24 bytes on the stack (a pointer to the elements, the size, the capacity), and its elements live in a heap buffer it owns.

When the vector dies, its destructor frees the buffer. That pattern, a small owner on the stack and a big buffer on the heap, is how C++ gets automatic cleanup of heap memory, and it has a name: RAII. Why stack memory is fast (it is almost always in the CPU cache) and what an allocation costs on this machine are measured in C++: the machine underneath; the root page Topic: programming-languages draws the same records laid out in Python, C++ and Rust.

3. Destructors and RAII

A class can define a constructor, which runs when an object is created, and a destructor, written ~ClassName(), which runs automatically when the object dies: at the closing brace for a local, when its owner dies for a member, when delete is called for a heap object. RAII means: tie every resource (memory, a file, a lock, a GPU buffer, a socket) to an object whose destructor releases it. Then you can never forget to release it, even when an exception jumps out of the function.

To watch it happen, this page uses a small class, Tracer, that prints a line from each special member function, numbers its objects #1, #2... and says whether each lives on the stack or the heap. The animations replay that real output one line at a time: the code line that caused the event (taken from std::source_location), the live objects, and the log. Lines starting with @ are the program's own STEP markers, with their line numbers.

Predict, then step: in Scopes, in what order are a, b and c destroyed? In Temporaries, which of t and u outlives its line?

  • Scopes: b dies at its inner brace, before c is even created; at the end, c dies before a: reverse order of construction, always.
  • Temporaries: Tracer{"u"} dies at the semicolon of its own line, right after its size is printed. Tracer{"t"} is bound to const Tracer& r, which extends it to r's lifetime, so it dies at the closing brace. The extension works only for a reference bound directly to the temporary (or to one of its members); a reference returned by a function called on a temporary (make().items()), or a string_view of a temporary string, dangles at the semicolon.
  • Exception unwinding: when throw leaves the try block, C++ unwinds the stack: it destroys every local in the scopes being left (b) before the catch runs. This is why RAII and exceptions work together, and why C++ code almost never needs finally.

The Tracer class (tracer.h) and the whole traced program (lifetime.cpp)
tracer.h
// tracer.h: a class that reports every special member function call.
// Each object gets a number (#1, #2, ...) and says whether it lives on the stack or the heap.
#pragma once
#include <cstdio>
#include <cstdlib>
#include <cstring>
#include <source_location>
#include <string>
#include <utility>

inline const char* stack_anchor = nullptr;   // set to a local's address in main()
inline int next_id = 1;

inline const char* where(const void* p) {
    long d = static_cast<const char*>(p) - stack_anchor;
    return std::labs(d) < (8L << 20) ? "stack" : "heap";
}
#define STEP(text) std::printf("@%d %s\n", __LINE__, text)
// The line in lifetime.cpp that caused a constructor call (blank when called from inside the library)
inline int at(const std::source_location& l) {
    return std::strstr(l.file_name(), "lifetime.cpp") ? static_cast<int>(l.line()) : 0;
}
using Loc = std::source_location;

template <bool NoexceptMove>
struct BasicTracer {
    int id;
    std::string name;
    explicit BasicTracer(std::string n, Loc l = Loc::current()) : id(next_id++), name(std::move(n)) {
        std::printf("ctor #%d %s %s L%d\n", id, name.c_str(), where(this), at(l));
    }
    BasicTracer(const BasicTracer& o, Loc l = Loc::current()) : id(next_id++), name(o.name) {
        std::printf("copy #%d from #%d %s %s L%d\n", id, o.id, name.c_str(), where(this), at(l));
    }
    BasicTracer(BasicTracer&& o, Loc l = Loc::current()) noexcept(NoexceptMove) : id(next_id++), name(std::move(o.name)) {
        std::printf("move #%d from #%d %s %s L%d\n", id, o.id, name.c_str(), where(this), at(l));
    }
    BasicTracer& operator=(const BasicTracer& o) {
        name = o.name;
        std::printf("copy= #%d from #%d\n", id, o.id);
        return *this;
    }
    BasicTracer& operator=(BasicTracer&& o) noexcept(NoexceptMove) {
        name = std::move(o.name);
        std::printf("move= #%d from #%d\n", id, o.id);
        return *this;
    }
    ~BasicTracer() { std::printf("dtor #%d\n", id); }
};
using Tracer = BasicTracer<true>;     // move constructor marked noexcept
using TracerNX = BasicTracer<false>;  // the same class without noexcept

}

// <copymove>
void copymove() {
    Tracer a{"a"};
    Tracer b = a;             // copy constructor
    Tracer c = std::move(a);  // move constructor: steals a's string
    std::printf("a.name is now \"%s\"\n", a.name.c_str());

    STEP("end of function");
}
// </copymove>

// <calls>
void calls() {
    Tracer a{"a"};
    by_ref(a);                // no new object
    by_value(a);              // a copy for the parameter
    by_value(std::move(a));   // a move for the parameter
    Tracer m = make("m");     // no copy, no move: built in place
    STEP("end of function");
}
// </calls>

// <growth>
template <class T>
void growth() {
    std::vector<T> v;
    v.push_back(T{"x"});
    STEP("capacity 1, now push y");
    v.push_back(T{"y"});
    STEP("capacity 2, now push z");
    v.push_back(T{"z"});
    STEP("end of function");
}
// </growth>

    v.emplace_back("y");
    v.emplace_back("z");

}
// </reserve>

// <unique>
void unique() {
    auto p = std::make_unique<Tracer>("h");   // the Tracer lives on the heap
    std::unique_ptr<Tracer> q = std::move(p);  // ownership moves; the Tracer does not
    std::printf("p is %s, q owns #%d\n", p ? "set" : "null", q->id);

    STEP("end of function");
}
// </unique>

// <shared>

    STEP("end of function");
}
// </shared>

// <unwind>
void unwind() {
    Tracer a{"a"};
    try {
        Tracer b{"b"};
        throw std::runtime_error("boom");
        STEP("never reached");
    } catch (const std::exception& e) {
        std::printf("caught %s\n", e.what());
    }
    STEP("end of function");
}
// </unwind>

// <cycle>
struct Node {
    Tracer t;
    std::shared_ptr<Node> next;   // owns the node it points at
    std::weak_ptr<Node> prev;     // observes only
    explicit Node(const char* n) : t{n} {}
};
void cycle() {
    {
        auto a = std::make_shared<Node>("a");
        auto b = std::make_shared<Node>("b");
        a->next = b;
        b->next = a;              // a cycle of owners
    }
    STEP("a and b are unreachable");
    {
        auto c = std::make_shared<Node>("c");
        auto d = std::make_shared<Node>("d");
        c->next = d;
        d->prev = c;              // the back edge only observes
    }
    STEP("end of function");
}
// </cycle>

// <temps>
void temps() {
    const Tracer& r = Tracer{"t"};                // bound to a const&: lives as long as r
    STEP("r is still alive");
    std::printf("size %zu\n", Tracer{"u"}.name.size());  // dies at the semicolon
    STEP("end of function");
}
// </temps>

int main(int argc, char** argv) {

    stack_anchor = &here;

    else if (!std::strcmp(s, "growth")) growth<Tracer>();
    else if (!std::strcmp(s, "growth_nx")) growth<TracerNX>();
    else if (!std::strcmp(s, "reserve")) reserve();
    else if (!std::strcmp(s, "unique")) unique();
    else if (!std::strcmp(s, "shared")) shared();
    else if (!std::strcmp(s, "unwind")) unwind();
    else if (!std::strcmp(s, "cycle")) cycle();
    else if (!std::strcmp(s, "temps")) temps();

}

4. Owning heap objects: unique_ptr, shared_ptr and weak_ptr

When an object must live on the heap (it must outlive the function, it is too big for the stack, or its exact type is decided at run time), do not write new and delete. Use a smart pointer: a small stack object that owns the heap object and deletes it in its destructor.

  • std::unique_ptr<T>: exactly one owner. It cannot be copied (two owners would delete twice), only moved (section 5): ownership is handed over and the source becomes null. It is the same size as a raw pointer and costs nothing extra. Create one with std::make_unique<T>(args...). This is the default.
  • std::shared_ptr<T>: shared ownership with a reference count, like a Python object. The object dies when the last shared_ptr to it dies. It costs a separate control block holding the counts, twice the size, and an atomic (thread-safe) increment or decrement on every copy.
  • std::weak_ptr<T>: observes an object owned by shared_ptrs without keeping it alive. It breaks reference cycles, which reference counting alone never frees: Python has a cycle collector; C++ does not.

Predict, then step: in the cycle, which Tracers are ever destroyed?

  • unique_ptr: the Tracer is created once (#1, on the heap) and never copied or moved: moving the unique_ptr moved only the 8-byte pointer, and p became null. reset() destroyed it at that line, before the end of the function.
  • shared_ptr: the count is 2 while t exists and 1 after; the Tracer dies with the last owner, s.
  • The cycle: a and b own each other, so when both locals go, each node still has a count of 1: no destructor ever runs for #1 and #2, and the memory leaks until the process exits. In the second block the back edge is a weak_ptr, so c's count reaches 0 and both nodes go. Note the order: #4 (d's Tracer) dies before #3 (c's), because destroying node c destroys its members in reverse declaration order: prev, then next (releasing d, whose count reaches 0), then t.

Owning costs nothing until you copy a shared_ptr, and much more when threads share one

ptr_cost.cpp measured on the M1 Pro (Apple clang 17, -O2, best of 5 runs, load average 6.70): one non-inlined call that reads an int, 100 million times. Passing a raw pointer, a const unique_ptr& or a const shared_ptr& costs the same, 0.96 ns per call. Passing the shared_ptr by value copies it, two atomic count updates: 13.50 ns. With 4 threads copying the same shared_ptr, every update fights for the cache line holding the count: 302.42 ns per call per thread (why a shared line is that slow is measured in C++: the machine underneath). Scale is logarithmic.

So pass a smart pointer only when the callee takes part in ownership (the C++ Core Guidelines' rule R.30); a function that only uses the object takes T&, const T& or T*. Sizes on this Mac (sizeof, in bytes): int* 8, std::unique_ptr<int> 8, std::shared_ptr<int> 16 (a pointer to the object and one to the control block).

Ruleunique_ptr by default; shared_ptr only when ownership is genuinely shared (a cache entry used by several requests); raw pointers and references only to observe an object someone else owns.
What it costsunique_ptr: nothing. shared_ptr: 16 bytes, a control block allocation, atomic count updates.
Common mistakesshared_ptr everywhere "to be safe" (slow and hides who owns what); two shared_ptrs made separately from one raw pointer (two counts, double delete); cycles of shared_ptr.
Rust bridge
Box<T> is unique_ptr; Rc<T> and Arc<T> are shared_ptr without and with atomic counts; Weak is weak_ptr. Rust's compiler enforces the "do not use after move" rule that C++ only recommends: Rust: lifetimes, smart pointers, threads and unsafe.
The benchmark (ptr_cost.cpp), its output, and every sizeof on this Mac
ptr_cost.cpp
// What an owner costs per call: the same function called 100 million times with the object passed
// as a raw pointer, a const unique_ptr&, a const shared_ptr&, and a shared_ptr by value (a copy: two atomic
// count updates). Then 4 threads copying one shared_ptr at once, all updating the same count.
// noinline plus an empty asm statement with a memory clobber keep every call real (without them clang hoisted
// the read-only calls out of the loop and printed 0.00 ns); best of 5 runs; ns per call.
#include <atomic>
#include <chrono>
#include <cstdio>
#include <cstdlib>
#include <memory>
#include <thread>
#include <vector>

#define NOINLINE __attribute__((noinline))
#define KEEP asm volatile("" ::: "memory")
NOINLINE long by_raw(const int* p) { KEEP; return *p; }
NOINLINE long by_uref(const std::unique_ptr<int>& p) { KEEP; return *p; }
NOINLINE long by_sref(const std::shared_ptr<int>& p) { KEEP; return *p; }
NOINLINE long by_sval(std::shared_ptr<int> p) { KEEP; return *p; }

constexpr long N = 100'000'000;
volatile long sink;

template <class F> double best_ns(F f) {
    double best = 1e30;
    for (int r = 0; r < 5; ++r) {
        auto t0 = std::chrono::steady_clock::now();
        long s = 0;
        for (long i = 0; i < N; ++i) s += f();
        sink = s;
        double ns = std::chrono::duration<double, std::nano>(std::chrono::steady_clock::now() - t0).count() / N;
        if (ns < best) best = ns;
    }
    return best;
}

int main() {
    double load[1];
    getloadavg(load, 1);
    std::printf("load average %.2f\n", load[0]);
    auto u = std::make_unique<int>(1);
    auto s = std::make_shared<int>(1);
    std::printf("raw pointer              %.2f ns per call\n", best_ns([&] { return by_raw(u.get()); }));
    std::printf("const unique_ptr&        %.2f ns per call\n", best_ns([&] { return by_uref(u); }));
    std::printf("const shared_ptr&        %.2f ns per call\n", best_ns([&] { return by_sref(s); }));
    std::printf("shared_ptr by value      %.2f ns per call\n", best_ns([&] { return by_sval(s); }));
    // 4 threads, each passing the same shared_ptr by value: the count's cache line moves between cores
    for (int threads : {1, 4}) {
        double best = 1e30;
        for (int r = 0; r < 5; ++r) {
            std::vector<std::thread> ts;
            std::atomic<int> ready{0};
            auto t0 = std::chrono::steady_clock::now();
            for (int t = 0; t < threads; ++t)
                ts.emplace_back([&] {
                    ready++;
                    while (ready < threads) {}
                    long acc = 0;
                    for (long i = 0; i < N / 10; ++i) acc += by_sval(s);
                    sink = acc;
                });
            for (auto& t : ts) t.join();
            double ns = std::chrono::duration<double, std::nano>(std::chrono::steady_clock::now() - t0).count() / (N / 10);
            if (ns < best) best = ns;
        }
        std::printf("by value, %d thread%s on one shared_ptr: %.2f ns per call per thread\n", threads, threads > 1 ? "s" : " ", best);
    }
}

5. Moves

Copy-by-default has an obvious cost: returning a vector of a million elements, or putting a string into a container, would copy every byte. C++11 added moves: when the source object is about to die anyway, the new object may steal its heap buffer (copy three pointers, set the source's to null) instead of copying the contents. The compiler needs to know when stealing is safe, so it sorts expressions into two families (simplified):

  • an lvalue has a name and an address you can take: a, v[3], *p. It will be used again, so it must be copied.
  • an rvalue is a temporary about to disappear: make_name(), a + b, Tracer{"x"}. It may be moved from.

A class gets a move constructor T(T&& other) (the && means "rvalue reference": it binds only to things that may be moved from) alongside its copy constructor T(const T& other), and overload resolution picks one. std::move(x) moves nothing. It is a cast that says "treat x as an rvalue; I will not need its value again" (cppreference: "exactly equivalent to a static_cast to an rvalue reference type"); the move constructor that it selects does the stealing.

Predict, then step: in Copy vs move, which constructors run, and what is left in a.name? In Passing and returning, how many Tracers are made in total, and where does m come from?

  • Copy vs move: the moved-from a is still a valid object (its destructor runs, #1, at the end) but its value is unspecified; libc++ leaves the string empty. The standard only promises "valid but unspecified": you may assign to it or destroy it; do not read it. b = c is an assignment (b already exists), so no object is created.
  • Passing and returning: passing by reference makes nothing; by value makes a copy (#2), or a move (#3) when the argument is std::move(a). m is the object constructed inside make() at line 10: returning it cost no copy and no move. Four Tracers in total.

That last line is copy elision: since C++17, returning a temporary constructs the result directly in the caller's variable, guaranteed, and compilers do the same for a returned local variable in practice (cppreference). So return big objects by value, and never write return std::move(local);, which can only prevent elision. What moving buys, and one trap:

6. Why noexcept on a move constructor matters: one vector, two classes

A std::vector keeps its elements in one buffer. When the buffer is full, push_back allocates a bigger one, transfers the old elements and frees the old buffer. It would like to move them, but if a move threw an exception halfway, the old buffer would be half-emptied and the vector could not restore it. So the standard library moves only if the move constructor is declared noexcept ("this never throws"); otherwise it copies, to keep its strong exception guarantee (std::move_if_noexcept). The animation runs the same three push_back calls on two versions of Tracer that differ only in that one keyword.

Predict, then step: without noexcept, how many of the transfers become copies?

Both versions make 9 objects. With noexcept, each reallocation moves the old elements (cheap); without it, the same code copies them: 3 copies here (x at the second growth, x and y at the third). For a vector of strings each copy is a heap allocation and a byte copy, on every growth. With reserve(3) and emplace_back, three objects are built directly in the vector's buffer: no temporaries, no moves. The compiler writes a noexcept move constructor for you when every member's is noexcept (the rule of zero, below), which is one more reason not to write them by hand.

7. The rule of zero and the rule of five

Five special member functions control a class's lifetime: destructor, copy constructor, copy assignment, move constructor, move assignment. The compiler writes all five for you, member by member. That is correct when every member manages itself (std::vector, std::string, std::unique_ptr): the rule of zero says write none of them. A class that owns a raw resource must write all five (the rule of five), because the compiler-written copy would copy the pointer, not the buffer:

rule_of_five.cpp (lines 5 to 29)
// A class that owns a raw buffer must write all five special members.
class Buffer {
    float* data_;
    std::size_t n_;
public:
    explicit Buffer(std::size_t n) : data_(new float[n]()), n_(n) {}
    ~Buffer() { delete[] data_; }                                   // 1 destructor
    Buffer(const Buffer& o) : data_(new float[o.n_]), n_(o.n_) {    // 2 copy constructor
        std::memcpy(data_, o.data_, n_ * sizeof(float));
    }
    Buffer& operator=(const Buffer& o) {                            // 3 copy assignment
        Buffer tmp(o);
        swap(tmp);
        return *this;
    }
    Buffer(Buffer&& o) noexcept                                     // 4 move constructor
        : data_(std::exchange(o.data_, nullptr)), n_(std::exchange(o.n_, 0)) {}
    Buffer& operator=(Buffer&& o) noexcept {                        // 5 move assignment
        Buffer tmp(std::move(o));
        swap(tmp);
        return *this;
    }
    void swap(Buffer& o) noexcept { std::swap(data_, o.data_); std::swap(n_, o.n_); }
    std::size_t size() const { return n_; }
};

Thirty lines of careful code against one line (std::vector<float> data;), with the same behaviour: copies get their own buffer, moved-from objects are empty. Write only a destructor and forget the other four, and copying the object gives two owners of one buffer, freed twice: the UB gallery on C++: the essentials shows its "double free" case crash at -O0, and the bug vanish at -O2, where the compiler removed the allocation altogether.

Which special members does the compiler write for a class holding a unique_ptr and a vector?

It generates the destructor, the move constructor and the move assignment (member-wise; noexcept because both members' are). It defines the copy constructor and copy assignment as deleted, because unique_ptr's copy operations are deleted: a member-wise copy is impossible. The class is move-only, like unique_ptr itself. Declaring any of the five yourself (even ~T() = default;) would suppress the implicit moves, and copies would silently take their place where copying is allowed; that is why the rule of zero says declare none. The exact conditions are listed under "Implicitly-declared move constructor" on cppreference.
