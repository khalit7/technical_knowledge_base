1. Values, references and pointers

In Python every variable is a name bound to an object on the heap, and b = a binds a second name to the same object. In C++ a variable is the object: its bytes live where the variable lives. So assignment and initialisation copy, and a second name has to be asked for.

The last row is the one that matters on this page: neither reference nor pointer keeps a alive; they only refer to memory that a owns. A reference or pointer that outlives its object dangles, and reading through it is undefined behaviour, the root of every dangling-reference bug (the essentials page's undefined behaviour section and its UB gallery show them crash, or worse, not crash).

const marks something read-only, checked by the compiler. Its everyday use is the parameter type const T&: "let me read your object without copying it, and I promise not to change it". With pointers, const can apply to the pointed-at object or to the pointer itself; read the declaration right to left (int* const q: q is a const pointer to int).

2. Where objects live: the stack, the heap and static storage

A C++ object lives in one of three kinds of storage, and the kind decides when it dies:

  • Automatic storage, "the stack": local variables. Each function call pushes a frame for its locals and pops it on return. Allocation is free (the stack pointer moves) and destruction happens at the closing brace }, in reverse order of creation.
  • Dynamic storage, "the heap": objects created with new (properly, with std::make_unique, section 4). They live until someone destroys them. Allocation calls the memory allocator (malloc), which costs tens of nanoseconds and can fragment memory; how it does that is {{Memory allocators|n:3f05c17b0d0d81209ae9d856695dc958}}' subject.
  • Static storage: globals and static variables, alive for the whole program.

Python puts every object on the heap and frees it when its reference count reaches zero ({{Memory allocators|n:3f05c17b0d0d81209ae9d856695dc958}} also owns reference counting and the cycle collector as memory behaviour). C++ lets you put most things on the stack. The stage draws one real run of stack_heap.cpp measured, the stack frame as a raised plate above the heap, then continues the same picture with a copy, a move and the closing brace:

  1. v on the stack, its elements on the heap. std::vector<int> v{1, 2, 3}; The std::vector object itself is [[g:l_stack_heap|sizeof\(v\) = (\d+) bytes]] bytes on the stack (a pointer to the elements, the size, the capacity), at [[g:l_stack_heap|&v \(the vector object\)\s+(0x[0-9a-f]+)]] in this run, and its elements live in a heap buffer it owns, at [[g:l_stack_heap|v\.data\(\) \(its elements\)\s+(0x[0-9a-f]+)]]. The dots are the pointer that links them.
  2. The whole run, region by region. on_stack ([[g:l_stack_heap|&on_stack\s+(0x[0-9a-f]+)]]) and also_on_stack ([[g:l_stack_heap|&also_on_stack\s+(0x[0-9a-f]+)]], 4 bytes lower) sit beside v (24 bytes lower again): on this ARM Mac the stack grows towards lower addresses. on_heap, a unique_ptr, owns one int on the heap at [[g:l_stack_heap|on_heap\.get\(\) \(heap int\)\s+(0x[0-9a-f]+)]], 16 bytes before v's elements; global_counter is in static storage at [[g:l_stack_heap|&global_counter \(static\)\s+(0x[0-9a-f]+)]]. The addresses change on every run: macOS randomises where each region starts.
  3. A copy duplicates the buffer. std::vector<int> b = v; gives b its own heap buffer, and the three ints are copied into it: two owners, two buffers. copy.cpp (section 1) prints "a has [[g:l_copy|a has (\d+), b has]], b has [[g:l_copy|a has \d+, b has (\d+)]]" after b.push_back(4): the two are independent. From this step on, the lines are added for the picture and the positions are illustrative.
  4. A move hands the buffer over. std::vector<int> w = std::move(v); copies three pointers into w and nulls v's: the same buffer, no element touched, and v is left empty. moved_from.cpp (section 5) printed w.data() == old v.data(): [[g:l_moved_from|w\.data\(\) == old v\.data\(\): (\d+)]], v.size() now [[g:l_moved_from|v\.size\(\) now (\d+)]].
  5. The closing brace frees, in reverse order. The destructors run from the last object constructed to the first: w frees the buffer it took, b frees its copy, the moved-from v has nothing to free, and on_heap frees its int. The frame is popped; global_counter lives until after main returns.
  6. A pointer that outlives its owner dangles. Had b.data() been saved in a global int* p, p would still hold the freed buffer's address after the brace. Reading through it is undefined behaviour; the essentials page's UB gallery shows such reads crash, or worse, not crash.

When the vector dies, its destructor frees the buffer. That pattern, a small owner on the stack and a big buffer on the heap, is how C++ gets automatic cleanup of heap memory, and it has a name: RAII. Why stack memory is fast (it is almost always in the CPU cache) and what an allocation costs on this machine are measured in {{C++: the machine underneath|n:4055c17b0d0d811fa947ee576a97a516}}; the root page {{Topic: programming-languages|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} draws the same records laid out in Python, C++ and Rust.
