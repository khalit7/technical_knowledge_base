3. Destructors and RAII

A class can define a constructor, which runs when an object is created, and a destructor, written ~ClassName(), which runs automatically when the object dies: at the closing brace for a local, when its owner dies for a member, when delete is called for a heap object. RAII means: tie every resource (memory, a file, a lock, a GPU buffer, a socket) to an object whose destructor releases it. Then you can never forget to release it, even when an exception jumps out of the function.

To watch it happen, this page uses a small class, Tracer, that prints a line from each special member function, numbers its objects #1, #2... and says whether each lives on the stack or the heap. The replay on the right steps through that real output, a few log lines per step: the code lines that caused the events (taken from std::source_location), the live objects, and the log. Lines starting with @ are the program's own STEP markers, with their line numbers.

Predict, then step: in Scopes, in what order are a, b and c destroyed? In Temporaries, which of t and u outlives its line?

  1. a, then b in an inner block. Both are constructed on the stack: a is #1 (line 15), b is #2 (line 17).
  2. The inner brace ends b. b dies at its inner brace, before c is even created.
  3. c is constructed as #3 at line 20, in the outer block, beside a.
  4. The function's brace: c, then a. At the end, c dies before a: reverse order of construction, always.
  1. A temporary bound to a const&. Tracer{"t"} (#1) is bound to const Tracer& r: its statement has ended, and it is still alive at line 135.
  2. A temporary dies at the semicolon. Tracer{"u"} (#2) dies at the semicolon of its own line, right after its size is printed.
  3. The brace ends t. Binding Tracer{"t"} to r extended it to r's lifetime, so it dies at the closing brace.
  1. a outside the try, b inside. #1 and #2, both on the stack.
  2. throw: the stack unwinds. When throw leaves the try block, C++ unwinds the stack: it destroys every local in the scopes being left (b) before the catch runs.
  3. The catch runs and prints caught boom; the STEP("never reached") line never printed.
  4. The function ends normally, and a dies at its closing brace.

The lifetime extension works only for a reference bound directly to the temporary (or to one of its members); a reference returned by a function called on a temporary (make().items()), or a string_view of a temporary string, dangles at the semicolon. Unwinding is why RAII and exceptions work together, and why C++ code almost never needs finally.

4. Owning heap objects: unique_ptr, shared_ptr and weak_ptr

When an object must live on the heap (it must outlive the function, it is too big for the stack, or its exact type is decided at run time), do not write new and delete. Use a smart pointer: a small stack object that owns the heap object and deletes it in its destructor.

  • std::unique_ptr<T>: exactly one owner. It cannot be copied (two owners would delete twice), only moved (section 5): ownership is handed over and the source becomes null. It is the same size as a raw pointer and costs nothing extra. Create one with std::make_unique<T>(args...). This is the default.
  • std::shared_ptr<T>: shared ownership with a reference count, like a Python object. The object dies when the last shared_ptr to it dies. It costs a separate control block holding the counts, twice the size, and an atomic (thread-safe) increment or decrement on every copy.
  • std::weak_ptr<T>: observes an object owned by shared_ptrs without keeping it alive. It breaks reference cycles, which reference counting alone never frees: Python has a cycle collector; C++ does not.

Predict, then step: in the cycle, which Tracers are ever destroyed?

The stage replays three recorded scenarios of lifetime.cpp (each run numbers its Tracers from #1): owners on the stack plate, the objects and control blocks on the heap floor, the dots running along owning pointers.

  1. unique_ptr: one owner. auto p = std::make_unique<Tracer>("h"); The Tracer is created once (#1, on the heap). p is one pointer, [[g:l_sizes|unique_ptr\s+(\d+)]] bytes, the size of an int*.
  2. Moving the owner, not the object. q = std::move(p): moving the unique_ptr moved only the 8-byte pointer, and p became null; the program prints p is null, q owns #1. The Tracer was never copied or moved.
  3. reset() frees it now. q.reset() destroyed it at that line, before the end of the function.
  4. shared_ptr: two owners, one count. s owns Tracer #1 and points at its control block; copying it into t adds a second owner: the count is 2 while t exists (the program prints use_count 2). Each shared_ptr is [[g:l_sizes|shared_ptr\s+(\d+)]] bytes, two pointers.
  5. One owner leaves. t's block ends and the count is 1 after (use_count 1); the Tracer is untouched.
  6. The last owner leaves. At the end of the function the count reaches 0: the Tracer dies with the last owner, s.
  7. A cycle of owners leaks. a and b own each other, so when both locals go, each node still has a count of 1: no destructor ever runs for #1 and #2, and the memory leaks until the process exits.
  8. weak_ptr breaks the cycle. In the second block the back edge is a weak_ptr, so c's count reaches 0 and both nodes go. Note the order: #4 (d's Tracer) dies before #3 (c's), because destroying node c destroys its members in reverse declaration order: prev, then next (releasing d, whose count reaches 0), then t.

What an owner costs per call

ptr_cost.cpp measured on the M1 Pro (Apple clang 17, -O2, best of 5 runs, load average [[g:t_ptr_cost|load average ([0-9.]+)]]): one non-inlined call that reads an int, 100 million times. Passing a raw pointer, a const unique_ptr& or a const shared_ptr& costs the same, [[g:t_ptr_cost|raw pointer\s+([0-9.]+) ns]] ns per call. Passing the shared_ptr by value copies it, two atomic count updates: [[g:t_ptr_cost|shared_ptr by value\s+([0-9.]+) ns]] ns. With 4 threads copying the same shared_ptr, every update fights for the cache line holding the count: [[g:t_ptr_cost|4 threads on one shared_ptr: ([0-9.]+) ns]] ns per call per thread (why a shared line is that slow is measured in {{C++: the machine underneath|n:4055c17b0d0d811fa947ee576a97a516}}).

So pass a smart pointer only when the callee takes part in ownership (the C++ Core Guidelines' {{rule R.30|https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rr-smartptrparam}}); a function that only uses the object takes T&, const T& or T*.
