3. Destructors and RAII

A class can define a constructor, which runs when an object is created, and a destructor, written ~ClassName(), which runs automatically when the object dies: at the closing brace for a local, when its owner dies for a member, when delete is called for a heap object. RAII means: tie every resource (memory, a file, a lock, a GPU buffer, a socket) to an object whose destructor releases it. Then you can never forget to release it, even when an exception jumps out of the function.

To watch it happen, this page uses a small class, Tracer, that prints a line from each special member function, numbers its objects #1, #2... and says whether each lives on the stack or the heap. The animations replay that real output one line at a time: the code line that caused the event (taken from std::source_location), the live objects, and the log. Lines starting with @ are the program's own STEP markers, with their line numbers.

Predict, then step: in Scopes, in what order are a, b and c destroyed? In Temporaries, which of t and u outlives its line?

  • Scopes: b dies at its inner brace, before c is even created; at the end, c dies before a: reverse order of construction, always.
  • Temporaries: Tracer{"u"} dies at the semicolon of its own line, right after its size is printed. Tracer{"t"} is bound to const Tracer& r, which extends it to r's lifetime, so it dies at the closing brace. The extension works only for a reference bound directly to the temporary (or to one of its members); a reference returned by a function called on a temporary (make().items()), or a string_view of a temporary string, dangles at the semicolon.
  • Exception unwinding: when throw leaves the try block, C++ unwinds the stack: it destroys every local in the scopes being left (b) before the catch runs. This is why RAII and exceptions work together, and why C++ code almost never needs finally.

4. Owning heap objects: unique_ptr, shared_ptr and weak_ptr

When an object must live on the heap (it must outlive the function, it is too big for the stack, or its exact type is decided at run time), do not write new and delete. Use a smart pointer: a small stack object that owns the heap object and deletes it in its destructor.

  • std::unique_ptr<T>: exactly one owner. It cannot be copied (two owners would delete twice), only moved (section 5): ownership is handed over and the source becomes null. It is the same size as a raw pointer and costs nothing extra. Create one with std::make_unique<T>(args...). This is the default.
  • std::shared_ptr<T>: shared ownership with a reference count, like a Python object. The object dies when the last shared_ptr to it dies. It costs a separate control block holding the counts, twice the size, and an atomic (thread-safe) increment or decrement on every copy.
  • std::weak_ptr<T>: observes an object owned by shared_ptrs without keeping it alive. It breaks reference cycles, which reference counting alone never frees: Python has a cycle collector; C++ does not.

Predict, then step: in the cycle, which Tracers are ever destroyed?

  • unique_ptr: the Tracer is created once (#1, on the heap) and never copied or moved: moving the unique_ptr moved only the 8-byte pointer, and p became null. reset() destroyed it at that line, before the end of the function.
  • shared_ptr: the count is 2 while t exists and 1 after; the Tracer dies with the last owner, s.
  • The cycle: a and b own each other, so when both locals go, each node still has a count of 1: no destructor ever runs for #1 and #2, and the memory leaks until the process exits. In the second block the back edge is a weak_ptr, so c's count reaches 0 and both nodes go. Note the order: #4 (d's Tracer) dies before #3 (c's), because destroying node c destroys its members in reverse declaration order: prev, then next (releasing d, whose count reaches 0), then t.

Owning costs nothing until you copy a shared_ptr, and much more when threads share one

ptr_cost.cpp measured on the M1 Pro (Apple clang 17, -O2, best of 5 runs, load average [[g:t_ptr_cost|load average ([0-9.]+)]]): one non-inlined call that reads an int, 100 million times. Passing a raw pointer, a const unique_ptr& or a const shared_ptr& costs the same, [[g:t_ptr_cost|raw pointer\s+([0-9.]+) ns]] ns per call. Passing the shared_ptr by value copies it, two atomic count updates: [[g:t_ptr_cost|shared_ptr by value\s+([0-9.]+) ns]] ns. With 4 threads copying the same shared_ptr, every update fights for the cache line holding the count: [[g:t_ptr_cost|4 threads on one shared_ptr: ([0-9.]+) ns]] ns per call per thread (why a shared line is that slow is measured in {{C++: the machine underneath|n:4055c17b0d0d811fa947ee576a97a516}}). Scale is logarithmic.

So pass a smart pointer only when the callee takes part in ownership (the C++ Core Guidelines' {{rule R.30|https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rr-smartptrparam}}); a function that only uses the object takes T&, const T& or T*. Sizes on this Mac (sizeof, in bytes): int* [[g:l_sizes|^int\*\s+(\d+)]], std::unique_ptr<int> [[g:l_sizes|unique_ptr\s+(\d+)]], std::shared_ptr<int> [[g:l_sizes|shared_ptr\s+(\d+)]] (a pointer to the object and one to the control block).

Ruleunique_ptr by default; shared_ptr only when ownership is genuinely shared (a cache entry used by several requests); raw pointers and references only to observe an object someone else owns.
What it costsunique_ptr: nothing. shared_ptr: 16 bytes, a control block allocation, atomic count updates.
Common mistakesshared_ptr everywhere "to be safe" (slow and hides who owns what); two shared_ptrs made separately from one raw pointer (two counts, double delete); cycles of shared_ptr.
