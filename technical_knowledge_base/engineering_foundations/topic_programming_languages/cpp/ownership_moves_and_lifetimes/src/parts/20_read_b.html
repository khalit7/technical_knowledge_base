1. Values, references and pointers

In Python every variable is a name bound to an object on the heap, and b = a binds a second name to the same object. In C++ a variable is the object: its bytes live where the variable lives. So assignment and initialisation copy, and a second name has to be asked for.

copy.cpp (lines 4 to 8)
int main() {
    std::vector<int> a{1, 2, 3};
    std::vector<int> b = a;    // a COPY: b gets its own three ints
    b.push_back(4);
    std::printf("a has %zu, b has %zu\n", a.size(), b.size());
Predict, then reveal: what sizes does each line print?

copy.py
a = [1, 2, 3]
b = a          # no copy: a second name for the same list
b.append(4)
print(f"a has {len(a)}, b has {len(b)}")
$ python3.14 copy.py
a has 4, b has 4

The same three lines give "a has 4, b has 4" in Python (one list, two names) and "a has 3, b has 4" in C++ (two vectors). The two ways to ask for a second name:

The last row is the one that matters on this page: neither reference nor pointer keeps a alive; they only refer to memory that a owns. A reference or pointer that outlives its object dangles, and reading through it is undefined behaviour, the root of every dangling-reference bug (the essentials page's undefined behaviour section and its UB gallery show them crash, or worse, not crash).

const marks something read-only, checked by the compiler. Its everyday use is the parameter type const T&: "let me read your object without copying it, and I promise not to change it". With pointers, const can apply to the pointed-at object or to the pointer itself; read the declaration right to left (int* const q: q is a const pointer to int).

Pass byT for small values (int, double, a pointer, a string_view); const T& to read a big object; T& to modify the caller's object; T* when "no object" is a valid answer.

}

The second shows a feature of C++ error messages you will meet constantly: the compiler lists every overload of += it tried and why each failed ("method is not marked const"). Read the first line and the line pointing at your own file; skim the candidates. The rest of copy.cpp (a reference and a pointer modifying a, then the pointer set to nullptr):

copy.cpp
#include <cstdio>
#include <vector>

int main() {
    std::vector<int> a{1, 2, 3};
    std::vector<int> b = a;    // a COPY: b gets its own three ints
    b.push_back(4);
    std::printf("a has %zu, b has %zu\n", a.size(), b.size());

    std::vector<int>& r = a;   // a REFERENCE: another name for a
    r.push_back(99);
    std::printf("a has %zu after r.push_back\n", a.size());

    std::vector<int>* p = &a;  // a POINTER: holds a's address
    p->push_back(7);           // -> follows the pointer
    std::printf("a has %zu after p->push_back; p == &a is %d\n", a.size(), p == &a);

    p = nullptr;               // a pointer can be re-pointed, or point at nothing
    std::printf("p is now %s\n", p ? "set" : "null");
}

2. Where objects live: the stack, the heap and static storage

A C++ object lives in one of three kinds of storage, and the kind decides when it dies:

  • Automatic storage, "the stack": local variables. Each function call pushes a frame for its locals and pops it on return. Allocation is free (the stack pointer moves) and destruction happens at the closing brace }, in reverse order of creation.
  • Dynamic storage, "the heap": objects created with new (properly, with std::make_unique, section 4). They live until someone destroys them. Allocation calls the memory allocator (malloc), which costs tens of nanoseconds and can fragment memory; how it does that is {{Memory allocators|n:3f05c17b0d0d81209ae9d856695dc958}}' subject.
  • Static storage: globals and static variables, alive for the whole program.

Python puts every object on the heap and frees it when its reference count reaches zero ({{Memory allocators|n:3f05c17b0d0d81209ae9d856695dc958}} also owns reference counting and the cycle collector as memory behaviour). C++ lets you put most things on the stack. One program printing the addresses of each kind:

The vector object sits on the stack; its elements sit on the heap, owned by it

Real addresses from one run of stack_heap.cpp measured (they change on every run: macOS randomises where each region starts). The stack addresses (0x16...) go down as variables are added: on this ARM Mac the stack grows towards lower addresses. The std::vector object itself is 24 bytes on the stack (a pointer to the elements, the size, the capacity), and its elements live in a heap buffer it owns.

When the vector dies, its destructor frees the buffer. That pattern, a small owner on the stack and a big buffer on the heap, is how C++ gets automatic cleanup of heap memory, and it has a name: RAII. Why stack memory is fast (it is almost always in the CPU cache) and what an allocation costs on this machine are measured in {{C++: the machine underneath|n:4055c17b0d0d811fa947ee576a97a516}}; the root page {{Topic: programming-languages|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} draws the same records laid out in Python, C++ and Rust.

The program and its raw output
stack_heap.cpp
#include <cstdio>
#include <memory>
#include <vector>

int global_counter = 0;            // static storage: lives for the whole program

void show(const char* what, const void* p) { std::printf("%-28s %p\n", what, p); }

int main() {
    int on_stack = 1;                       // automatic storage (the stack)
    int also_on_stack = 2;
    auto on_heap = std::make_unique<int>(3); // dynamic storage (the heap)
    std::vector<int> v{1, 2, 3};            // the vector object is on the stack...

    show("&global_counter (static)", &global_counter);
    show("&on_stack", &on_stack);
    show("&also_on_stack", &also_on_stack);
    show("&v (the vector object)", &v);
    show("on_heap.get() (heap int)", on_heap.get());
    show("v.data() (its elements)", v.data());     // ...its elements are on the heap
    std::printf("sizeof(v) = %zu bytes, whatever v.size() is\n", sizeof(v));
}
