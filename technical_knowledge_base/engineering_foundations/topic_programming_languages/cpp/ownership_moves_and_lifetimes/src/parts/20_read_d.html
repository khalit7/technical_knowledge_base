5. Moves

Copy-by-default has an obvious cost: returning a vector of a million elements, or putting a string into a container, would copy every byte. C++11 added moves: when the source object is about to die anyway, the new object may steal its heap buffer (copy three pointers, set the source's to null) instead of copying the contents. The compiler needs to know when stealing is safe, so it sorts expressions into two families (simplified):

  • an lvalue has a name and an address you can take: a, v[3], *p. It will be used again, so it must be copied.
  • an rvalue is a temporary about to disappear: make_name(), a + b, Tracer{"x"}. It may be moved from.

A class gets a move constructor T(T&& other) (the && means "rvalue reference": it binds only to things that may be moved from) alongside its copy constructor T(const T& other), and overload resolution picks one. std::move(x) moves nothing. It is a cast that says "treat x as an rvalue; I will not need its value again" ({{cppreference: "exactly equivalent to a static_cast to an rvalue reference type"|https://en.cppreference.com/w/cpp/utility/move}}); the move constructor that it selects does the stealing.

Predict, then step: in Copy vs move, which constructors run, and what is left in a.name? In Passing and returning, how many Tracers are made in total, and where does m come from?

  • Copy vs move: the moved-from a is still a valid object (its destructor runs, #1, at the end) but its value is unspecified; libc++ leaves the string empty. The standard only promises "valid but unspecified": you may assign to it or destroy it; do not read it. b = c is an assignment (b already exists), so no object is created.
  • Passing and returning: passing by reference makes nothing; by value makes a copy (#2), or a move (#3) when the argument is std::move(a). m is the object constructed inside make() at line 10: returning it cost no copy and no move. Four Tracers in total.

That last line is copy elision: since C++17, returning a temporary constructs the result directly in the caller's variable, guaranteed, and compilers do the same for a returned local variable in practice ({{cppreference|https://en.cppreference.com/w/cpp/language/copy_elision}}). So return big objects by value, and never write return std::move(local);, which can only prevent elision. What moving buys, and one trap:

moved_from.cpp (lines 7 to 20)
    std::string s = "a string long enough to live on the heap";
    std::string t = std::move(s);       // t steals s's heap buffer
    std::printf("t: %zu chars, s: %zu chars\n", t.size(), s.size());
    s = "reusable";                     // a moved-from object can be assigned to
    std::printf("s: %s\n", s.c_str());

    std::vector<int> v(1'000'000, 7);
    const int* before = v.data();
    std::vector<int> w = std::move(v);  // O(1): three pointers change hands
    std::printf("w.data() == old v.data(): %d, v.size() now %zu\n", w.data() == before, v.size());

    const std::string c = "const";
    std::string d = std::move(c);       // compiles, but COPIES: you cannot steal from const
    std::printf("c after 'move': %s\n", c.c_str());

The million-element vector changed hands in constant time: w owns the very same buffer, and v is empty. A moved-from string can be assigned to and reused. The last line is the trap: std::move of a const object silently copies, because a move constructor needs to modify its source. It compiles and copies, with no warning.

6. Why noexcept on a move constructor matters: one vector, two classes

A std::vector keeps its elements in one buffer. When the buffer is full, push_back allocates a bigger one, transfers the old elements and frees the old buffer. It would like to move them, but if a move threw an exception halfway, the old buffer would be half-emptied and the vector could not restore it. So the standard library moves only if the move constructor is declared noexcept ("this never throws"); otherwise it copies, to keep its strong exception guarantee ({{std::move_if_noexcept|https://en.cppreference.com/w/cpp/utility/move_if_noexcept}}). The animation runs the same three push_back calls on two versions of Tracer that differ only in that one keyword.

Predict, then step: without noexcept, how many of the transfers become copies?

Both versions make 9 objects. With noexcept, each reallocation moves the old elements (cheap); without it, the same code copies them: 3 copies here (x at the second growth, x and y at the third). For a vector of strings each copy is a heap allocation and a byte copy, on every growth. With reserve(3) and emplace_back, three objects are built directly in the vector's buffer: no temporaries, no moves. The compiler writes a noexcept move constructor for you when every member's is noexcept (the rule of zero, below), which is one more reason not to write them by hand.

7. The rule of zero and the rule of five

Five special member functions control a class's lifetime: destructor, copy constructor, copy assignment, move constructor, move assignment. The compiler writes all five for you, member by member. That is correct when every member manages itself (std::vector, std::string, std::unique_ptr): the rule of zero says write none of them. A class that owns a raw resource must write all five (the rule of five), because the compiler-written copy would copy the pointer, not the buffer:

rule_of_five.cpp (lines 5 to 29)
// A class that owns a raw buffer must write all five special members.
class Buffer {
    float* data_;
    std::size_t n_;
public:
    explicit Buffer(std::size_t n) : data_(new float[n]()), n_(n) {}
    ~Buffer() { delete[] data_; }                                   // 1 destructor
    Buffer(const Buffer& o) : data_(new float[o.n_]), n_(o.n_) {    // 2 copy constructor
        std::memcpy(data_, o.data_, n_ * sizeof(float));
    }
    Buffer& operator=(const Buffer& o) {                            // 3 copy assignment
        Buffer tmp(o);
        swap(tmp);
        return *this;
    }
    Buffer(Buffer&& o) noexcept                                     // 4 move constructor
        : data_(std::exchange(o.data_, nullptr)), n_(std::exchange(o.n_, 0)) {}
    Buffer& operator=(Buffer&& o) noexcept {                        // 5 move assignment
        Buffer tmp(std::move(o));
        swap(tmp);
        return *this;
    }
    void swap(Buffer& o) noexcept { std::swap(data_, o.data_); std::swap(n_, o.n_); }
    std::size_t size() const { return n_; }
};

b 4, c 4, moved-from a 0; y 4, z 4, moved-from x 0

Thirty lines of careful code against one line (std::vector<float> data;), with the same behaviour: copies get their own buffer, moved-from objects are empty. Write only a destructor and forget the other four, and copying the object gives two owners of one buffer, freed twice: the UB gallery on {{C++: the essentials|n:3cd5c17b0d0d81ceadcee44fe9c023a0}} shows its "double free" case crash at -O0, and the bug vanish at -O2, where the compiler removed the allocation altogether.

Which special members does the compiler write for a class holding a unique_ptr and a vector?

It generates the destructor, the move constructor and the move assignment (member-wise; noexcept because both members' are). It defines the copy constructor and copy assignment as deleted, because unique_ptr's copy operations are deleted: a member-wise copy is impossible. The class is move-only, like unique_ptr itself. Declaring any of the five yourself (even ~T() = default;) would suppress the implicit moves, and copies would silently take their place where copying is allowed; that is why the rule of zero says declare none. The exact conditions are listed under "Implicitly-declared move constructor" on {{cppreference|https://en.cppreference.com/w/cpp/language/move_constructor}}.
