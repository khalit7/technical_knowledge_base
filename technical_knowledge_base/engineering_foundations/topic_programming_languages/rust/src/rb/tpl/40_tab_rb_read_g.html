12. Wheels: platforms, abi3, CI and publishing

Users should never need Rust to install your package. They need a wheel built for their Python and their machine; pip or uv picks the right one from PyPI by its file name. maturin build --release writes one:

The wheel is a zip of the compiled library, the stub and py.typed (section 11), metadata, and a software bill of materials (sboms/, the Rust crates compiled in, written by maturin). otool -L (macOS's ldd) shows the library does not link to libpython: it finds Python's C API symbols in the process that loads it, which is what lets one wheel work with any CPython 3.14 binary.

abi3: one wheel for many Python versions

A wheel per Python version per platform multiplies fast. CPython's stable ABI (the "limited API", PEP 384) is a subset of the C API that is promised not to change; an extension that uses only that subset gets the abi3 tag and loads on that version and every later one. In PyO3 it is a feature flag: pyo3/abi3-py310 (minimum Python 3.10). Built once, installed into fresh virtual environments:

[[out:b5_abi3.txt|$ maturin build --release --features pyo3/abi3-py310]] [[out:b6_abi3_install.txt|one abi3 wheel on CPython 3.12, 3.13, 3.14 and 3.14t]]

The same file loaded on three versions and was refused by the free-threaded build: abi3 assumes the GIL build's object layout. What it costs at run time, the same calls against both builds on 3.14 (ns per item, medians; code/c9_abi_cost.py):

Callcp314 buildabi3 build

These were measured on a busy laptop (load average about 10) and the spread between runs was wide; only the total_len gap (reading items from a list) repeated across runs here. Under the limited API, PyO3 must call real C functions where the full API uses inline macros (list item access, string data). PyO3's changelog lists such cases, for example "Optimize PyBytes::as_bytes() when not using abi3 or abi3t" (0.29.3).

abi3t is the stable ABI for free-threaded builds, PEP 803 (status Final, Python 3.15), supported by PyO3 0.29 through the abi3t-py315 feature. Built against the 3.15 release candidate:

[[out:b7_abi3t.txt|$ maturin build --release --features pyo3/abi3t-py315 -i python3.15t]] [[out:b8_abi3t_install.txt|the abi3t wheel on CPython 3.15.0rc3, free-threaded and with the GIL]]

The tag abi3.abi3t means one file for both 3.15 builds. Until you can require 3.15, ship an abi3 wheel plus a cp314t wheel per platform (tokenizers, safetensors and polars build abi3-py310 today, section 13).

Building for every platform in CI

You cannot build Windows or Linux wheels on a Mac without cross-compilers, so a CI service builds them on each platform. maturin generate-ci github writes a complete GitHub Actions workflow (PyO3/maturin-action does the builds; the generated file is outputs/b10_ci.yml, 186 lines). What it builds, as generated by maturin 1.15.0:

JobTargets

Change one thing before you use it
The generated job uploads with a long-lived PYPI_API_TOKEN secret. PyPI's trusted publishing removes the secret: you register the repository and workflow on PyPI once, the job (which already has id-token: write) receives a short-lived token from GitHub, and uv publish needs no credentials (uv packaging guide, PyPI trusted publishers). Delete the env: lines after setting it up.

cibuildwheel is the other common route: one tool that builds wheels for every CPython on every platform for any build backend, including maturin; for Rust it must install a Rust toolchain inside its Linux containers (cibuildwheel FAQ, "Building Rust wheels"). maturin-action is the simpler choice for a Rust-only package; cibuildwheel suits projects that also run test suites per wheel or mix C, C++ and Rust. tokrs was not uploaded to PyPI for this page; the steps above are what would publish it.
