8. Releasing the GIL, and parallel Rust with rayon

On the normal (GIL) build of CPython, a thread must hold the global interpreter lock to touch any Python object, and only one thread holds it at a time. While your Rust function runs, the calling thread still holds it, so four Python threads calling the same Rust function take turns, exactly like four threads running Python. But a function that only touches Rust data (bytes already borrowed, a Vec, a HashMap) does not need the interpreter. py.detach(closure) releases the GIL, runs the closure, and takes it back:

Name check (PyO3 0.26 and later)
This method was called allow_threads until PyO3 0.26 (2025-08-29), which renamed it detach; the token type that used to be described as "holding the GIL" is now described as being "attached" to the interpreter, because on free-threaded Python there is no GIL to hold (PyO3 changelog). Code and answers written before mid-2025 say allow_threads.

Can you forget the rule and touch a Python object inside detach? No: the compiler refuses. The closure must be Ungil (on normal builds, the same as Send: safe to use from another thread), and a Bound is deliberately not. This deliberately wrong function (code/send_err/):

The error chain reads bottom-up: detach needs F: Ungil; the closure captures &Bound<PyList>; Bound contains a Python token, which contains a raw pointer marker (NotSend) that is never Sync. In C you would find this bug as a crash under load; here it is a compile error. To use Python data inside detach, copy what you need into Rust values first (that is a reason to own, section 4).

Parallelism inside one call: rayon

If the caller is single-threaded, Rust can split the work itself. rayon turns an iterator into a parallel one (.into_par_iter()) and runs it on a pool of OS threads, one per core by default; reduce merges the partial tallies:

[[rs:tally]] [[rs:step5]]

tally takes only &[u8] and returns plain Rust data, so it is safe to run on any thread; the compiler checks that too (rayon requires Send). The split itself (chunks, in lib.rs) cuts at newlines and remembers each chunk's first line number so "first malformed line" stays exact; the pytest suite (section 11) checks the parallel result equals the serial one for 1, 2, 3, 8 and 64 chunks.

Detach when
the Rust work is long-running and touches no Python objects. Do it on free-threaded Python too: there, a thread that stays attached through long work can stall the interpreter's stop-the-world pauses (garbage collection, sys.settrace, fork) for every other thread (PyO3 free-threading guide).
Mistakes
Detaching around a tiny function (all overhead, no gain); initialising a std::sync::OnceLock or LazyLock with code that calls Python, which can deadlock against the GIL (PyO3's FAQ: use PyOnceLock); starting a rayon pool in a process that already runs one worker per core (oversubscription).

9. Free-threaded Python (3.14t)

CPython 3.14 officially supports a second build without the GIL, python3.14t (PEP 779); the root's {{Reading|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} and the {{Python page|n:3cd5c17b0d0d81b28acdea39e7a4d998}} cover what it costs and what it breaks. For extension authors it changes two things.

1. A module must declare that it is safe without the GIL, or importing it turns the GIL back on for the whole process. Since PyO3 0.28 (2026-02-01) every PyO3 module declares itself safe by default; you opt out with #[pymodule(gil_used = true)] (from 0.23 to 0.27 it was the other way round). A one-function module that opts out (code/gilused/), imported after tokrs on 3.14t:

[[out:c10_ft.txt|$ python3.14t c10_ft.py]]

2. Calls really do run at the same time, so state shared between threads must be protected by Rust, not by the GIL. tokrs functions that only read their arguments are fine. The Counter class of section 7 is not: its add takes &mut self, and PyO3's run-time borrow flag now sees two threads asking for it at once. Eight threads, one shared Counter, 20,000 add calls each:

[[out:c13_ft_borrow.txt|$ python3.14t c13_ft_borrow.py, then python3.14 c13_ft_borrow.py]]

Nothing was corrupted (Rust's guarantee held: added plus raised equals 160,000), but on 3.14t 13% of the calls failed (22% to 27% in three earlier runs of the same script) with RuntimeError: Already borrowed, and the same script on the GIL build never fails, which is how this bug hides in testing. The fix is the Rust way of sharing: make the class frozen (no &mut self, so no borrow flag) and put the mutable part behind a Mutex, which makes threads wait their turn instead of failing ({{Part 1|#t-ra-read}}, sections 15 and 16, covers Mutex and Send):

The token counting happens before lock(), so threads only queue for the short dictionary update. PyO3's guide has the full checklist (free-threading, pyclass thread safety), and py-free-threading.github.io tracks which libraries are ready. PyO3 0.29 supports 3.14t and later only (it dropped 3.13t, which CPython never declared supported).
