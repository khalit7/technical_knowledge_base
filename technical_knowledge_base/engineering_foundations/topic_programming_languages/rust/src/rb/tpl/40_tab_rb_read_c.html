4. Crossing the boundary: what each conversion costs

A Python str and a Rust String are different things in memory. A Python str is an object on Python's heap with a refcount, a length and its characters in one of three fixed widths (1, 2 or 4 bytes each, whichever fits the widest character). A Rust &str is just a pointer and a length into UTF-8 bytes ({{Part 1|#t-ra-read}}, section 7: String against &str). So every argument crosses the boundary in one of two ways:

  • Borrowed (a view): Rust gets a pointer into memory Python owns. &str from a str, &[u8] from bytes, a NumPy array view. No allocation, no copy, but the view only lives for the call.
  • Owned (a copy): Rust builds its own value. String, Vec<T>, HashMap<K, V>: one allocation per string, one conversion per element. The value can then outlive the call, move to another thread, be stored in a struct.

Measured with timeit on the first 20,000 messages of the log (code/c3_convert.py; nanoseconds per item, medians of 7):

Defaults reproduce the root's {{Benchmark|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} tab independently: there the empty PyO3 call took ns (separate run, same machine). Pure Python for comparison: sum(x*x for x in xs) costs ns per float.

Three rules fall out. Batch: one crossing costs about as much as counting a whole message, so call once per list, not once per item. Borrow: a copy costs x a view per string; take &str, &[u8] and array views unless Rust must keep the data. Convert once, at the edge: if the data goes back and forth, keep it on one side (as a Rust object behind a #[pyclass], section 7, or as a NumPy array).

5. NumPy arrays without copies (rust-numpy)

A Python list of floats is an array of pointers to separate float objects, each 24 bytes with its own refcount; converting it means visiting every object. A NumPy array is one contiguous block of raw f64 values plus a small header (shape, strides, dtype). The numpy crate (rust-numpy, 0.29.0, the release matching PyO3 0.29) lets Rust read that block in place:

[[rs:numpy]]

PyReadonlyArray1<f64> checks the dtype and takes a shared borrow of the array (rust-numpy tracks borrows so Rust cannot write to an array Python code also holds as read-only); as_slice() gives a plain &[f64] when the memory is contiguous. On a million floats: list ns per element, array ns.

Rust lost to NumPy here, and that is the lesson
np.dot(x, x) took ns per element, x faster than the Rust loop. The Rust compiler may not reorder floating-point additions (the result would change in the last bits), so .sum() runs one add at a time; NumPy calls a BLAS routine that keeps several partial sums in SIMD registers. Do not port what NumPy, PyTorch or polars already do; port the loops they cannot express.

The float32 message ('ndarray' object is not an instance of 'ndarray') is confusing: it means "not an ndarray of the dtype I asked for". A strided view (a[::2]) is refused by as_slice; either copy it with np.ascontiguousarray on the Python side or use xs.as_array(), an ndarray view that handles strides. Vec<f64> accepted an int64 array because it converts element by element, at list speed. Returning works the other way: into_pyarray hands a Vec's buffer to NumPy without copying (OWNDATA is False: the array points at Rust's allocation; its base is a small Python object (PySliceContainer) that owns the buffer and frees it when the array is collected).
