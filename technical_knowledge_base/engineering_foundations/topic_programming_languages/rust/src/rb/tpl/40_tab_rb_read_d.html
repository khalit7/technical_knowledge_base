6. Errors become exceptions; panics become PanicException

Rust has no exceptions: a function that can fail returns Result<T, E>, and ? returns early with the error ({{Part 1|#t-ra-read}}, section 9, covers both). PyO3 maps this onto Python: return PyResult<T>, and an Err(PyErr) is raised as an exception when the call returns. Many Rust errors convert by themselves: std::io::Error becomes the matching OSError subclass (FileNotFoundError, PermissionError), a failed UTF-8 decode becomes UnicodeDecodeError. For your own error kinds, declare a Python exception class from Rust:

[[rs:errors]]

map_err turns serde's error into a MalformedLine carrying serde's message; ? then raises it. A panic is different: it is Rust's reaction to a bug (an index out of bounds, an unwrap() on None), not an expected failure. PyO3 catches it at the boundary so it cannot unwind into C code, and raises pyo3_runtime.PanicException.

[[predict:code/c5_errors.py|c5_errors.txt]]

Look at the last two lines: PanicException derives from BaseException, not Exception, so except Exception: does not catch it (PyO3's source says why: "Like SystemExit, this exception is derived from BaseException so that it will typically propagate all the way through the stack and cause the Python interpreter to exit", src/panic.rs). Rust's panic handler also printed its own three lines to stderr (thread '<unnamed>' ... panicked at src/lib.rs) before Python saw the exception. Treat a PanicException in production as a bug report: fix the Rust (return a PyResult instead), do not catch it. And the FileNotFoundError message is Rust's (No such file or directory (os error 2)), not Python's usual wording.

7. Classes: #[pyclass] keeps Rust state between calls

Section 4's third rule said: when data goes back and forth, keep it on one side. A #[pyclass] is how: a Rust struct that Python sees as a class. The Python object owns the struct; methods run on it in place, so the per-user table never crosses the boundary until you ask for a result.

[[rs:class]]

#[new] is __init__ (strictly __new__), #[getter] makes a read-only property, and methods named like Python's special methods (__len__, __repr__) become them. &self methods read; &mut self methods write. Python has no borrow checker, so PyO3 enforces Rust's rule (many readers or one writer) at run time with a flag in each object.

[[predict:code/c6_class.py|c6_class.txt]]

Unlike a Python class, a #[pyclass] has no __dict__ (no new attributes), its getters are read-only, and it cannot be subclassed unless you write #[pyclass(subclass)]. Its fields cannot be Bound (no lifetimes in a pyclass): store Py<T> if it must hold Python objects. On a normal build the GIL serialises calls, so the borrow flag never trips; section 9 shows what happens on free-threaded Python.

Solves
State that lives across calls without re-converting it: a tokenizer's vocabulary, a parser's buffers, an index.
Costs
Each method call is still a crossing (about 30 to 70 ns); keep methods coarse (add_many over add).
Mistake
Returning a large Rust collection from a getter on every access: it is converted (copied) each time.
