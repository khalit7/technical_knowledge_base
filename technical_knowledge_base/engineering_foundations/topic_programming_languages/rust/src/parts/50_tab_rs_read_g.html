6. Blocking the runtime: the mistake async makes easy

A worker thread can poll only one task at a time, and it gets the thread back only at an .await. A task that calls a blocking function (std::thread::sleep, a synchronous file read, a CPU-heavy loop) holds its worker the whole time, and every other task queued on that worker waits. Alice Ryhl (a tokio maintainer) gives the rule of thumb: "no more than 10 to 100 microseconds between each .await" ({{Async: What is blocking?|https://ryhl.io/blog/async-what-is-blocking/}}). The same three jobs as the Python page (A, B and C wait 100, 200 and 300 ms), five ways:

tok/examples/a2_trace.rs (lines 16 to 41)
async fn job(name: &str, ms: u64) -> String {
    ev(name, "start", "");
    ev(name, "await", &format!("sleep({ms} ms).await"));
    tokio::time::sleep(Duration::from_millis(ms)).await; // yields to the runtime
    ev(name, "resume", "");
    ev(name, "done", "");
    name.into()
}

async fn job_blocking(name: &str, ms: u64) -> String {
    ev(name, "start", "");
    ev(name, "block", &format!("std::thread::sleep({ms} ms)"));
    std::thread::sleep(Duration::from_millis(ms)); // blocks the worker thread: nothing else runs on it
    ev(name, "done", "");
    name.into()
}

async fn job_offload(name: &str, ms: u64) -> String {
    ev(name, "start", "");
    ev(name, "await", &format!("spawn_blocking(sleep {ms} ms).await"));
    tokio::task::spawn_blocking(move || std::thread::sleep(Duration::from_millis(ms))).await.unwrap();
    ev(name, "resume", "");
    ev(name, "done", "");
    name.into()
}

Line by line: join overlaps the waits (300 ms, the longest); join_blocking (B calls std::thread::sleep) takes 500 ms, and A, whose timer fired at 100 ms, could only resume after B released the thread; join_offload moves B's blocking call to the blocking pool with spawn_blocking and is back to 300 ms. The last line is the trap: the same blocking B, spawned on a 4-worker runtime, also finishes in 300 ms, because B blocked only one worker. The bug is still there; it shows up under load, when every worker has a B. The fixes, in order of preference: use the async version of the call (tokio::time::sleep, tokio::fs, an async database driver); for blocking calls you cannot avoid, tokio::task::spawn_blocking; for CPU-heavy parallel work, a CPU thread pool such as rayon (the {{spawn_blocking docs|https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html}}: "Specialized CPU-bound executors, such as rayon, may also be a good fit"); Part 2 uses rayon from Python ({{Reading|#t-rb-read}}).

7. Send + 'static: why tokio::spawn rejects your code
