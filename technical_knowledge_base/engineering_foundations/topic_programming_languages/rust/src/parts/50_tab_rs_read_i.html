Testing

Three levels, all run by one cargo test (Part 1 covers #[test], assertions and test layout: {{Reading|#t-ra-read}}). Test strategy in general (what to test, CI) is the SWE topic's {{Testing and quality|n:3c65c17b0d0d81548848e2ebdd2f63ee}} page.

  • Unit tests of the logic, next to it in src/lib.rs, with no async and no HTTP: the token rules from the root page's spec, and malformed lines being counted rather than fatal.
  • Router tests without a network. An axum Router is a tower Service: call it with a request object and await the response, with tower::ServiceExt::oneshot. Fast (no sockets), and it exercises extractors, layers and status codes. #[tokio::test] gives each test its own runtime.
  • A real server on a real port. Bind port 0 (the OS picks a free one, so tests can run in parallel), spawn the server, talk TCP to it. Slower, but it catches what in-process tests cannot (the listener, HTTP framing).
tok/tests/service.rs (lines 13 to 26)
#[tokio::test]
async fn count_without_a_network() {
    let req = Request::post("/count")
        .header("content-type", "application/json")
        .body(Body::from(r#"{"text":"x86_64 and v2.1"}"#))
        .unwrap();
    let resp = app(cfg()).oneshot(req).await.unwrap();
    assert_eq!(resp.status(), StatusCode::OK);
    let bytes = resp.into_body().collect().await.unwrap().to_bytes();
    let body: CountResp = serde_json::from_slice(&bytes).unwrap();
    assert_eq!(body.tokens, 5); // x86, 64, and, v2, 1
}

/// A real server on port 0 (the OS picks a free port), talked to over TCP.
#[tokio::test]
async fn real_server_over_tcp() {
    let listener = tokio::net::TcpListener::bind("127.0.0.1:0").await.unwrap();
    let addr = listener.local_addr().unwrap();
    tokio::spawn(async move { axum::serve(listener, app(cfg())).await.unwrap() });

    use tokio::io::{AsyncReadExt, AsyncWriteExt};
    let mut s = tokio::net::TcpStream::connect(addr).await.unwrap();
    s.write_all(b"GET /health HTTP/1.1\r\nHost: x\r\nConnection: close\r\n\r\n").await.unwrap();
    let mut raw = String::new();
    s.read_to_string(&mut raw).await.unwrap();
    assert!(raw.starts_with("HTTP/1.1 200 OK"), "{raw}");
    assert!(raw.ends_with("\r\n\r\nok"), "{raw}");
}

Deployment: a container image

A container image is a file system plus a start command. A Python service image needs an interpreter and its packages; a Rust service image needs the binary and, at most, a C library. The standard recipe is a multi-stage build: compile in a full Rust image, then copy only the binary into a minimal one.

tok/Dockerfile
# Multi-stage build: compile in a full Rust image, ship only the binary.
# Stage 1: the builder (about 1.5 GB of compilers and headers; thrown away).
FROM rust:1.99-slim-bookworm AS build
WORKDIR /src
# Cache dependencies: build once with a dummy main so code edits do not refetch crates.
COPY Cargo.toml Cargo.lock ./
RUN mkdir -p src/bin && echo 'fn main(){}' > src/bin/tokserve.rs && echo '' > src/lib.rs \
 && cargo build --release --bin tokserve && rm -rf src
COPY src ./src
RUN touch src/lib.rs src/bin/tokserve.rs && cargo build --release --bin tokserve

# Stage 2: distroless "cc" = glibc + libgcc + CA certs, no shell, no package manager, non-root user.
FROM gcr.io/distroless/cc-debian12:nonroot
COPY --from=build /src/target/release/tokserve /tokserve
ENV TOK_ADDR=0.0.0.0:3000
EXPOSE 3000
ENTRYPOINT ["/tokserve"]

Two base images matter for the last stage. Distroless images ({{GoogleContainerTools/distroless|https://github.com/GoogleContainerTools/distroless}}) contain no shell and no package manager, so there is less to patch and less for an attacker to use; cc-debian12 adds glibc and libgcc for a normally linked Rust binary, and the :nonroot tag runs as an unprivileged user. scratch is the empty image: it works only with a fully static binary, which the musl cross-build above produces:

tok/Dockerfile.scratch
# The smallest image: a static musl binary in an empty image.
# Build the binary first (on any machine): see ../../cross.sh, or in a builder stage with
#   rustup target add x86_64-unknown-linux-musl && cargo build --release --target x86_64-unknown-linux-musl
FROM scratch
COPY tokserve /tokserve
ENV TOK_ADDR=0.0.0.0:3000
USER 65532:65532
EXPOSE 3000
ENTRYPOINT ["/tokserve"]

What else production needs, briefly: a health endpoint for the orchestrator (/health), SIGTERM handling (above), logs on stdout, configuration from the environment, resource limits (and a worker count to match the CPUs the container is given: tokserve takes --workers or TOK_WORKERS), and TLS terminated in front (a load balancer or proxy) or in-process with rustls. Load balancing and capacity are the SWE topic's {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}} page.
