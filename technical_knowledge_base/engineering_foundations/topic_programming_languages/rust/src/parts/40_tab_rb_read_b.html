2. Your first extension: PyO3 and maturin

Two tools do all the work. PyO3 is a Rust library (a crate) that wraps CPython's C API: Rust types for Python objects, conversions between the two, and macros (code generators run by the compiler, written #[...]) that turn an ordinary Rust function into a Python-callable one. maturin is a build tool: it runs cargo build to compile your crate into a shared library, then packs it into a wheel (the .whl zip file pip installs) with the right name and metadata. It is also a PEP 517 build backend, so pip install . or uv build on the project just works.

The root page's {{Toolchain atlas|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} tab has the full first run, recorded: maturin new --bindings pyo3 tokrs creates Cargo.toml, pyproject.toml, src/lib.rs and a GitHub Actions workflow; maturin develop builds and installs into the active virtual environment. This part's project grew from that skeleton. Its two configuration files:

The other four dependencies are numpy (rust-numpy, section 5), rayon (parallel loops, section 8), and serde with serde_json (typed JSON parsing, section 10).

Correction to older guides (and to the root's benchmark crate)
Older tutorials add features = ["pyo3/extension-module"] under [tool.maturin]. PyO3 now marks that feature deprecated: maturin 1.9.4 and later set the environment variable PYO3_BUILD_EXTENSION_MODULE that does the same job (stop linking to libpython) (PyO3 features guide). This project leaves it out; the root's src/bench/ext_rust/ still has it, which is harmless.

3. Functions and modules: #[pyfunction], #[pymodule]

Step 1 of the token counter: the Rosetta token loop as plain Rust, and a thin function Python can call.

ext/src/lib.rs
/// Tokens = maximal runs of ASCII letters or digits (rule 3 of PROGRAM.md).
/// Non-ASCII characters are UTF-8 bytes >= 0x80, so a byte loop gives the char answer.
fn tokens(s: &[u8]) -> u64 {
    let mut n = 0;
    let mut inside = false;
    for &b in s {
        let t = b.is_ascii_alphanumeric();
        if t && !inside {
            n += 1;
        }
        inside = t;
    }
    n
}
ext/src/lib.rs
/// Step 1: one message per call. `&str` borrows the Python string's UTF-8 bytes.
#[pyfunction]
fn count_tokens(text: &str) -> u64 {
    tokens(text.as_bytes())
}

#[pyfunction] generates the glue: a C-level function that takes Python's argument objects, converts each one to the Rust parameter type (&str here), calls your function, and converts the return value (u64) back into a Python int. The /// doc comment becomes the Python docstring. The module lists what it exports:

ext/src/lib.rs

The mod tokrs name must match the module name in pyproject.toml, because CPython looks for PyInit_tokrs when you import tokrs.

What Python sees when the types are wrong

Python has no compiler to stop count_tokens(5), so the generated glue checks every argument at run time and raises TypeError. Predict each line: which calls work, and what do the others raise?

c2_types.py
import tokrs

calls = [
    'tokrs.count_tokens(5)',
    'tokrs.count_tokens(b"raw bytes")',
    'tokrs.count_tokens(text="keyword works")',
    'tokrs.count_many(["fine", 3])',
    'tokrs.count_many(("a", "tuple"))',
    'tokrs.count_many_owned(("a", "tuple"))',
    'tokrs.count_many_owned("abc")',
    'tokrs.count_bytes("a str")',
    'tokrs.count_tokens("\\ud800 lone surrogate")',
]
for c in calls:
    try:
        r = eval(c)
        print(f"{c}\n  -> {r!r}")
    except Exception as e:
        notes = "".join(f" ({n})" for n in getattr(e, "__notes__", []))
        print(f"{c}\n  -> {type(e).__name__}: {e}{notes}")

Four lessons from the real output. (1) PyO3 adds a note naming the parameter (while processing 'text', shown by Python 3.11+ as an exception note). (2) &Bound<PyList> accepts exactly a list, so a tuple is refused, while Vec<String> accepts any sequence (a tuple worked) but deliberately refuses a str, which is also a sequence and a classic bug. (3) Inside count_many the item check runs after argument parsing, so its error has no note: say which item failed in your own messages. (4) A str holding a lone surrogate (legal in Python, not in UTF-8) cannot become &str and raises UnicodeEncodeError.

The types in those signatures

Rust typeWhat it isPython analogy
Python<'py>A zero-size token proving this thread is attached to the interpreter (holds the GIL on a normal build). You get it as a parameter or from a Bound.Being inside the interpreter at all; Python code always is
Bound<'py, T>A strong reference to a Python object of type T (PyList, PyDict, PyAny), usable only while attached. Dropping it decrements the refcount.Any ordinary variable holding an object
Py<T>The same reference without the 'py lifetime: can be stored in a struct or sent to another thread; call .bind(py) to use it.An object kept in a global or a queue
PyResult<T>Result<T, PyErr>: Err becomes a raised exception (section 6).return or raise

The 'py is a lifetime ({{Part 1|#t-ra-read}}, section 6, explains them): the compiler uses it to stop a Bound escaping the region where the interpreter is attached. You rarely write it out except in return types like Bound<'py, PyDict>.
