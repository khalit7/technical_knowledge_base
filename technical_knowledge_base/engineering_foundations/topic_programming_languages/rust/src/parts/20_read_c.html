4. Ownership and moves

First, where values live. Each function call gets a stack frame, a block of memory for its local variables, released automatically when the function returns. Data whose size is only known at run time (a growing vector, a string read from a file) goes on the heap, which someone must release explicitly. A Rust String or Vec is a small fixed-size header on the stack (three machine words: a pointer to the heap buffer, the capacity, the length; 24 bytes) plus a buffer on the heap. Python hides all of this: every object is on the heap and names are references to it.

Fig. 2 is one small program, stepped line by line; every address and number in it was printed by the program itself when it ran (rustc 1.99.0), and the counters under it keep the score: allocations, live blocks, bytes copied by moves, elements copied. Predict first: after let w = v;, which address changes, the stack slot or the heap block? Switch the figure to Python for the same steps in Python's model: names pointing at one object, and a reference count.

  1. One owner, two places. A Vec with capacity 3 holds 10, 20, 30. Its header is on the stack at 0x16da0a2a8; the elements are in one heap block at 0x102d3d4a0.
  2. Borrowing never copies. r = &v is just an 8-byte pointer to v's stack slot (the run printed 0x16da0a2a8, the same address as v).
  3. Growth moves the buffer. push(40) on a full vector allocated a new block (capacity 3 to 6) at 0x102d3d510, copied the elements and freed the old one. r pointed at the header and is not used again, so this was allowed; a reference into the buffer (like &v[0]) would now point at freed memory, which is exactly why the borrow checker refuses a reference into the buffer across a push (section 5).
  4. One writer. m = &mut v is an exclusive borrow: while m is in use nobody else may read or write v. m[0] = 11 writes into the heap block through it.
  5. A move copies 24 bytes, not the data. let w = v copies the header to w's slot (0x16da0a350); the heap block is untouched and still at 0x102d3d510. v is now unusable: any use is a compile error.
  6. Clone allocates. c = w.clone() is a deep copy with its own block (4 slots, at 0x102d3d4a0). On this run the allocator handed it the block freed at step 3. Reusing freed memory is normal, and is why a dangling pointer can read someone else's data in C++.
  7. Drop frees at a known line. drop(w) releases the second block now, at a line you can point to. No garbage collector, no reference count.
  8. The clone lives on. c is still valid and owns its own block.
  9. The closing brace. c goes out of scope at the end of main and its block is freed: not printed, because this is the drop the compiler inserts.
  1. One object, one name. v = [10, 20, 30]: the name v points at one list object on the heap (id 0x105e26140), reference count 1.
  2. A second name. r = v names the same object; the count becomes 2. Python never copies on assignment.
  3. Growth in place. v.append(40): the list grows in place (its internal pointer array may move, the object does not), and r sees the change.
  4. A change through any name. m = v; m[0] = 11: a third name; a change through any of them is visible through all. Count 3.
  5. No such thing as a move. w = v: a fourth name, and the count rises to 4; v stays usable.
  6. The only new object. c = w.copy() is the only allocation after the first (id 0x10a8842c0).
  7. del removes a name. del w removes a name, not the object: the count drops to 3 and the list lives on.
  8. Freed when the count reaches zero. Both objects are alive; each is freed when its count reaches zero (here, when the program ends).

The ownership rules ({{Rust Book 4.1|https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html}}): each value has one owner (a variable, a field, a vector slot); when the owner goes out of scope the value is dropped (its heap memory freed); assigning or passing a value moves ownership.

move.rs
fn shout(s: String) -> String {
    // takes ownership of s; returns ownership of a new String
    s.to_uppercase()
}

fn main() {
    let a = String::from("hello");
    let b = a; // move: b now owns the heap buffer
    println!("b = {b}");
    let c = b.clone(); // explicit deep copy: a second heap buffer
    let d = shout(b); // b moves into the function
    println!("c = {c}, d = {d}");
    let n = 5; // i32 is Copy: assignment copies the bits
    let m = n;
    println!("n = {n}, m = {m}"); // both still usable
}

After let b = a; the 24-byte header was copied into b and a became unusable. The heap buffer was not copied and not freed: it now has exactly one owner again. Using a afterwards is refused with E0382, "borrow of moved value: a", and the error names the cause: String does not implement the Copy trait.

The Python bridge
In Python, b = a makes two names for one object, kept alive by a reference count. Rust refuses the second name, so it never needs a count: the single owner frees the buffer at a point the compiler knows. Think of a move as handing over the only key.
  • Copy types (integers, floats, bool, char, and tuples or arrays of them) have no heap part, so assignment copies the bits and both stay usable (n and m above).
  • clone() is the explicit deep copy: a second heap buffer. It is visible in the code on purpose, so you can see every place that copies data.
  • Passing to a function moves too (shout(b)); returning moves ownership back out.

Drop: cleanup at a known moment

A type can run code when it is dropped by implementing the Drop trait, which is how files close, locks release and buffers free themselves. There is no garbage collector, so the order is fixed:

drop.rs
struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

fn consume(n: Noisy) {
    println!("consume got {}", n.0);
} // n is dropped here, at the end of the function that owns it

fn main() {
    let _a = Noisy("a");
    let b = Noisy("b");
    {
        let _c = Noisy("c");
        println!("inner scope ends");
    } // c dropped here
    consume(b); // b moved into consume; dropped inside it
    let _d = Noisy("d");
    println!("main ends");
} // locals dropped in reverse order of declaration: d, then a

Locals drop at the end of their scope in reverse order of declaration; a value moved into a function drops at the end of that function. This is C++'s RAII (resource acquisition is initialisation) made the default; Python's equivalent is with, which you have to remember to write.

SolvesUse after free and double free, with no garbage collector and no reference counts.
CostsYou must decide who owns each value; sharing needs borrowing (section 5) or explicit shared ownership (Rc, Arc: the {{lifetimes child|n:4055c17b0d0d8160aa32df9cda0aef03}}, section 2).
Common mistakeSprinkling .clone() until it compiles. Fine for small values; in a hot loop it allocates on every iteration. Borrow first.

5. Borrowing: many readers or one writer


Moving everything everywhere would be unbearable, so you lend a value instead: a reference &v borrows it without taking ownership. Two kinds:


    

  • &T, a shared reference: read only; any number at once.
    • 

  • &mut T, an exclusive (mutable) reference: may change the value; while it is in use, no other reference to that value may be.
    • 



borrow.rs
fn total(v: &[u64]) -> u64 {
    // borrows: reads, does not own
    v.iter().sum()
}

fn add_one(v: &mut Vec<u64>) {
    // borrows exclusively: may change it
    v.push(1);
}

fn main() {
    let mut v = vec![3, 4, 5];
    let a = &v; // any number of shared borrows at once
    let b = &v;
    println!("{} {}", total(a), total(b));
    add_one(&mut v); // a and b are no longer used, so this is allowed
    println!("{:?} total {}", v, total(&v));
}


$ rustc --edition 2024 borrow.rs && ./borrow
12 12
[3, 4, 5, 1] total 13


The part of the compiler that enforces this is the borrow checker. A borrow lasts from where it is created to its last use, not to the end of the block (the Book: "a reference's scope starts from where it is introduced and continues through the last time that reference is used"). That is why add_one(&mut v) is accepted above: a and b are never used again.

  1. The code and headline (error[E0502], "cannot borrow v as mutable because it is also borrowed as immutable") say which rule broke; --> gate_err.rs:4:5 is the file, line and column of the main conflict.
    2. 

  2.
