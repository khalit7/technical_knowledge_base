4. Ownership and moves

First, where values live. Each function call gets a stack frame, a block of memory for its local variables, released automatically when the function returns. Data whose size is only known at run time (a growing vector, a string read from a file) goes on the heap, which someone must release explicitly. A Rust String or Vec is a small fixed-size header on the stack (three machine words: a pointer to the heap buffer, the capacity, the length; 24 bytes) plus a buffer on the heap, as the hero at the top draws. Python hides all of this: every object is on the heap and names are references to it.

The ownership rules ({{Rust Book 4.1|https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html}}): each value has one owner (a variable, a field, a vector slot); when the owner goes out of scope the value is dropped (its heap memory freed); assigning or passing a value moves ownership.

move.rs
fn shout(s: String) -> String {
    // takes ownership of s; returns ownership of a new String
    s.to_uppercase()
}

fn main() {
    let a = String::from("hello");
    let b = a; // move: b now owns the heap buffer
    println!("b = {b}");
    let c = b.clone(); // explicit deep copy: a second heap buffer
    let d = shout(b); // b moves into the function
    println!("c = {c}, d = {d}");
    let n = 5; // i32 is Copy: assignment copies the bits
    let m = n;
    println!("n = {n}, m = {m}"); // both still usable
}
$ rustc --edition 2024 move.rs && ./move
b = hello
c = hello, d = HELLO
n = 5, m = 5

After let b = a; the 24-byte header was copied into b and a became unusable. The heap buffer was not copied and not freed: it now has exactly one owner again. Using a afterwards is refused with E0382, "borrow of moved value: a", and the error names the cause: String does not implement the Copy trait.

The Python bridge
In Python, b = a makes two names for one object, kept alive by a reference count. Rust refuses the second name, so it never needs a count: the single owner frees the buffer at a point the compiler knows. Think of a move as handing over the only key.
  • Copy types (integers, floats, bool, char, and tuples or arrays of them) have no heap part, so assignment copies the bits and both stay usable (n and m above).
  • clone() is the explicit deep copy: a second heap buffer. It is visible in the code on purpose, so you can see every place that copies data.
  • Passing to a function moves too (shout(b)); returning moves ownership back out.

Drop: cleanup at a known moment

A type can run code when it is dropped by implementing the Drop trait, which is how files close, locks release and buffers free themselves. There is no garbage collector, so the order is fixed:

drop.rs
struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

fn consume(n: Noisy) {
    println!("consume got {}", n.0);
} // n is dropped here, at the end of the function that owns it

fn main() {
    let _a = Noisy("a");
    let b = Noisy("b");
    {
        let _c = Noisy("c");
        println!("inner scope ends");
    } // c dropped here
    consume(b); // b moved into consume; dropped inside it
    let _d = Noisy("d");
    println!("main ends");
} // locals dropped in reverse order of declaration: d, then a

Locals drop at the end of their scope in reverse order of declaration; a value moved into a function drops at the end of that function. This is C++'s RAII (resource acquisition is initialisation) made the default; Python's equivalent is with, which you have to remember to write.

SolvesUse after free and double free, with no garbage collector and no reference counts.
CostsYou must decide who owns each value; sharing needs borrowing (section 5) or explicit shared ownership (Rc, Arc: the {{lifetimes child|n:4055c17b0d0d8160aa32df9cda0aef03}}, section 2).
Common mistakeSprinkling .clone() until it compiles. Fine for small values; in a hot loop it allocates on every iteration. Borrow first.

5. Borrowing: many readers or one writer

Moving everything everywhere would be unbearable, so you lend a value instead: a reference &v borrows it without taking ownership. Two kinds:

  • &T, a shared reference: read only; any number at once.
  • &mut T, an exclusive (mutable) reference: may change the value; while it is in use, no other reference to that value may be.
borrow.rs
fn total(v: &[u64]) -> u64 {
    // borrows: reads, does not own
    v.iter().sum()
}

fn add_one(v: &mut Vec<u64>) {
    // borrows exclusively: may change it
    v.push(1);
}

fn main() {
    let mut v = vec![3, 4, 5];
    let a = &v; // any number of shared borrows at once
    let b = &v;
    println!("{} {}", total(a), total(b));
    add_one(&mut v); // a and b are no longer used, so this is allowed
    println!("{:?} total {}", v, total(&v));
}
$ rustc --edition 2024 borrow.rs && ./borrow
12 12
[3, 4, 5, 1] total 13

The part of the compiler that enforces this is the borrow checker. A borrow lasts from where it is created to its last use, not to the end of the block (the Book: "a reference's scope starts from where it is introduced and continues through the last time that reference is used"). That is why add_one(&mut v) is accepted above: a and b are never used again.

The canonical error, and why it is a real bug

The old page's "gate" question: why does this fail to compile?

gate_err.rs

first points into the vector's heap buffer. push may find the buffer full, allocate a bigger one, copy the elements and free the old one (step 3 of the hero); first would then point at freed memory. In C++ the same code compiles and reads freed memory (the root page runs it: Reading section 5).

A borrow lives until its last use: the checker refuses only when a shared bar and the push overlap
