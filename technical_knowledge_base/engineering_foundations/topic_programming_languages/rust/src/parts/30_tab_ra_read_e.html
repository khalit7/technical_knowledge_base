16. Threads without data races

A data race is two threads touching the same memory at the same time, at least one of them writing, with nothing ordering them. Updates get lost or values tear. In CPython the GIL used to hide most of these; free-threaded Python 3.14 does not, and an unsynchronised counter there loses updates (measured on the {{Python page|n:3cd5c17b0d0d81b28acdea39e7a4d998}}). Rust makes data races a compile error in safe code, by applying section 5's rule across threads: shared data may be read by many threads, and changed only through a type that synchronises (a lock or an atomic).

The obvious Python translation, eight threads incrementing one counter, does not compile, and the three errors are the three problems:

race_err.rs
use std::thread;

fn main() {
    let mut counter = 0u64;
    let mut hs = vec![];
    for _ in 0..8 {
        hs.push(thread::spawn(|| for _ in 0..100_000 { counter += 1; }));
    }
    for h in hs { h.join().unwrap(); }
    println!("{counter}");
}

Two marker traits carry the rule. They are implemented automatically by the compiler for types whose parts qualify ({{std::marker::Send|https://doc.rust-lang.org/std/marker/trait.Send.html}}):

  • Send: a value of this type may be moved to another thread.
  • Sync: a &T may be shared between threads (precisely, T is Sync if &T is Send).

Rc is neither, because two threads updating its non-atomic counter at once would be a race; Arc uses atomic updates and is both. Try to send an Rc:

The working toolbox, every result exact:

threads.rs
use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::mpsc;
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // 1. spawn + join; `move` gives the thread its own copy of what it uses
    let docs = vec!["a b c", "d e", "f"];
    let handles: Vec<_> = docs.into_iter().enumerate().map(|(i, d)| {
        thread::spawn(move || (i, d.split_whitespace().count()))
    }).collect();
    let counts: Vec<_> = handles.into_iter().map(|h| h.join().unwrap()).collect();
    println!("spawned: {counts:?}");

    // 2. scoped threads may borrow local data, because they are joined before the scope ends
    let data = vec![1u64; 1_000_000];
    let (left, right) = data.split_at(data.len() / 2);
    let total = thread::scope(|s| {
        let a = s.spawn(|| left.iter().sum::<u64>());
        let b = s.spawn(|| right.iter().sum::<u64>());
        a.join().unwrap() + b.join().unwrap()
    });
    println!("scoped sum: {total}");

    // 3. shared mutable state: Arc (shared ownership across threads) + Mutex (one writer at a time)
    let counter = Arc::new(Mutex::new(0u64));
    let mut hs = vec![];
    for _ in 0..8 {
        let c = Arc::clone(&counter);
        hs.push(thread::spawn(move || for _ in 0..100_000 { *c.lock().unwrap() += 1; }));
    }
    for h in hs { h.join().unwrap(); }
    println!("mutex counter: {} (expected 800000)", *counter.lock().unwrap());

    // 4. an atomic does the same without a lock
    let hits = Arc::new(AtomicU64::new(0));
    thread::scope(|s| for _ in 0..8 { let h = &hits; s.spawn(move || for _ in 0..100_000 { h.fetch_add(1, Ordering::Relaxed); }); });
    println!("atomic counter: {}", hits.load(Ordering::Relaxed));

    // 5. channels: send values from many producers to one consumer
    let (tx, rx) = mpsc::channel();
    for id in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || tx.send(format!("worker {id} done")).unwrap());
    }
    drop(tx); // close our copy so the loop below ends when the workers finish
    let mut got: Vec<String> = rx.iter().collect();
    got.sort();
    println!("channel: {got:?}");
}

  • thread::spawn(move || ...) plus join() for owned work; thread::scope when threads should borrow local data.
  • Arc<Mutex<T>> for shared mutable state: lock() returns a guard that unlocks when dropped, and the data is reachable only through the guard, so you cannot forget the lock. Atomics (AtomicU64) for single counters and flags.
  • Channels (mpsc) to pass messages instead of sharing memory.
  • For data parallelism over a collection, the {{rayon|https://docs.rs/rayon}} crate turns iter() into par_iter(); Part 2 uses it to parallelise the token counter inside a Python extension ({{Part 2|#t-rb-read}}).
What the compiler does not prevent
Deadlocks (two threads each holding the lock the other needs), logic races (check-then-act with the lock released in between), and leaked memory are all possible in safe Rust. "Fearless" means no data races and no use after free, not no concurrency bugs.

Async, in one paragraph

Threads suit CPU work. For thousands of concurrent network calls (an LLM gateway, an agent fanning out tool calls), Rust uses async fn and .await, as Python's asyncio does, with two differences worth knowing now: a future does nothing until it is awaited or spawned (calling an async fn does not start it), and the language ships no event loop, so you choose a runtime library, almost always {{tokio|https://tokio.rs}}. {{Part 3, Services and CLIs|#t-rs-read}} teaches async from zero and builds an HTTP service with it.

17. unsafe, in one section

Some correct code cannot be proved safe by the compiler: the inside of Vec, calls into C libraries, hardware access. Inside an unsafe block you may do five extra things, the "unsafe superpowers" ({{Rust Book 20.1|https://doc.rust-lang.org/book/ch20-01-unsafe-rust.html}}): dereference a raw pointer; call an unsafe function; access or modify a mutable static; implement an unsafe trait; access fields of a union. Nothing else changes: "unsafe doesn't turn off the borrow checker or disable any of Rust's other safety checks".

unsafe_ok.rs
fn main() {
    let v = vec![10u32, 20, 30];
    let p: *const u32 = v.as_ptr(); // making a raw pointer is safe
    let second = unsafe { *p.add(1) }; // dereferencing it is not: we promise it is in bounds
    println!("second = {second}");
    // A safe API built on unsafe: split_at_mut hands out two &mut halves of one slice,
    // which the borrow checker cannot prove disjoint by itself.
    let mut a = [1, 2, 3, 4];
    let (l, r) = a.split_at_mut(2);
    l[0] += 100;
    r[0] += 100;
    println!("{a:?}");
}
$ rustc --edition 2024 unsafe_ok.rs && ./unsafe_ok
second = 20
[101, 2, 103, 4]

The pattern to aim for is the one split_at_mut shows: a small unsafe core with a stated invariant ("the two halves never overlap"), wrapped in a safe API that cannot be used to break it. Because unsafe is a keyword, every such place can be found with a text search and reviewed.

When you get it wrong: Miri

Breaking an invariant is undefined behaviour, exactly as in C++: the program may do anything, including appear to work. This program reads one element past the end of a vector, and then reads a freed vector; built in release mode, it runs and prints plausible numbers:

main.rs
// Undefined behaviour that compiles and "works": reading one element past the end
// through a raw pointer, and using a pointer after its Vec was freed.
fn main() {
    let v = vec![10u32, 20, 30];
    let p = v.as_ptr();
    let past_end = unsafe { *p.add(3) }; // out of bounds: UB
    println!("read past the end: {past_end}");
    let q = {
        let w = vec![1u32, 2, 3];
        w.as_ptr()
    }; // w freed here; q dangles
    let after_free = unsafe { *q }; // use after free: UB
    println!("read after free: {after_free}");
}
$ cargo run -q --release
read past the end: 0
read after free: 0

{{Miri|https://github.com/rust-lang/miri}} is an interpreter for Rust's intermediate representation that checks every memory access against the rules. It runs on the nightly toolchain (here rustc 1.101.0-nightly of 2026-10-04) and is much slower than native code, so you run your tests under it, not production:
