3. The runtime is a library: tokio

Python ships one event loop in the standard library; Node has one built in. Rust's standard library defines the Future trait but no runtime (the executor that polls futures, plus timers and non-blocking sockets). You add one; tokio is the de facto standard, and axum, reqwest and tonic are built on it. Forgetting it is the first error everyone meets:

#[tokio::main] rewrites main into "build a runtime, then block_on the body". tokserve.rs spells that out so the number of threads is a flag:

tok/src/bin/tokserve.rs (lines 34 to 39)
    // What #[tokio::main] writes for you, spelled out so the worker count is configurable.
    let mut rt = tokio::runtime::Builder::new_multi_thread();
    if let Some(n) = args.workers {
        rt.worker_threads(n);
    }
    rt.enable_all().build()?.block_on(serve(args))
current_threadOne thread polls every task: the asyncio and Node model. #[tokio::main(flavor = "current_thread")]. Used by the examples here so traces are easy to read.
multi_thread (default)A pool of worker threads, by default "the number of cores available to the system" ({{Builder docs|https://docs.rs/tokio/latest/tokio/runtime/struct.Builder.html}}), each with its own queue; idle workers steal tasks from busy ones. One process uses every core.
blocking poolExtra threads for code that must block (file I/O, CPU work) via spawn_blocking; up to 512 by default.

4. Concurrency: join, spawn, JoinSet, Semaphore

tokio::join!(a, b, c) polls several futures inside the current task and finishes when all are done: concurrency without new tasks. tokio::spawn(fut) hands a future to the runtime as an independent task (Python's create_task) that may run on any worker thread, in parallel with others; it returns a JoinHandle to await the result. A JoinSet owns a group of tasks (like asyncio.TaskGroup) and aborts them all if it is dropped. The Python page's fan-out benchmark, rewritten: 20 calls to a local server that answers after 100 ms (this part's own service, standing in for a model API).

tok/examples/a4_fanout.rs (lines 26 to 55)
    let t = Instant::now();
    for _ in 0..20 {
        get(addr, "/slow?ms=100".into()).await; // one after another
    }
    println!("sequential, 20 calls      {:6.3} s", t.elapsed().as_secs_f64());

    let t = Instant::now();
    let mut set = JoinSet::new(); // like asyncio.TaskGroup: owns its tasks, aborts them when dropped
    for _ in 0..20 {
        set.spawn(get(addr, "/slow?ms=100".into()));
    }
    let bodies = set.join_all().await;
    println!("JoinSet, 20 at once       {:6.3} s   {:?}", t.elapsed().as_secs_f64(), bodies[0]);

    let t = Instant::now();
    let limit = Arc::new(Semaphore::new(5)); // at most 5 in flight
    let mut set = JoinSet::new();
    for _ in 0..20 {
        let limit = limit.clone();
        set.spawn(async move {
            let _permit = limit.acquire().await.unwrap(); // released when dropped
            get(addr, "/slow?ms=100".into()).await
        });
    }
    set.join_all().await;
    println!("JoinSet, at most 5        {:6.3} s", t.elapsed().as_secs_f64());

    let t = Instant::now();
    let r = tokio::time::timeout(Duration::from_millis(250), get(addr, "/slow?ms=2000".into())).await;
    println!("timeout after             {:6.3} s   {}", t.elapsed().as_secs_f64(), if r.is_err() { "Elapsed" } else { "ok" });

Same shape, same numbers: for waiting, the language does not matter, the overlap does. 20 sequential calls cost 20 × 100 ms; concurrent ones cost one round trip; a semaphore with 5 permits gives 4 waves of 100 ms. That last pattern is the polite way to call a rate-limited model API. Rust differs where work is done between the waits: there, a multi-threaded runtime uses all cores, which one asyncio loop cannot.

5. Timeouts, select!, cancellation

Cancelling a future in Rust means dropping it: it is never polled again, so the code after its pending .await never runs, and its local variables are dropped (their Drop code runs). timeout and select! are both built on that.

tok/examples/a3_cancel.rs (lines 6 to 46)
/// Prints when it is dropped, to show exactly when a future is cancelled.
struct Guard(&'static str);
impl Drop for Guard {
    fn drop(&mut self) {
        println!("   drop: {} cleaned up", self.0);
    }
}

async fn step(name: &'static str, ms: u64) -> &'static str {
    let _g = Guard(name);
    println!("   {name}: started, waiting {ms} ms");
    sleep(Duration::from_millis(ms)).await;
    println!("   {name}: finished"); // never printed if the future is dropped first
    name
}

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let t = Instant::now();
    println!("1. timeout(250 ms) around a 2000 ms call");
    let r = timeout(Duration::from_millis(250), step("slow", 2000)).await;
    println!("   -> {r:?} after {} ms", t.elapsed().as_millis());

    println!("2. select!: first to finish wins, the other is dropped");
    let t = Instant::now();
    tokio::select! {
        w = step("fast", 100) => println!("   -> winner {w} after {} ms", t.elapsed().as_millis()),
        w = step("lazy", 300) => println!("   -> winner {w}"),
    }

    println!("3. a spawned task keeps running on its own; abort() cancels it");
    let h = tokio::spawn(step("background", 1000));
    sleep(Duration::from_millis(50)).await;
    h.abort();
    println!("   -> join: {:?}", h.await.map_err(|e| e.is_cancelled()));

    println!("4. dropping a JoinHandle does NOT cancel the task (it is detached)");
    drop(tokio::spawn(step("detached", 100)));
    sleep(Duration::from_millis(150)).await;
    println!("   -> main done");
}

   detached: started, waiting 100 ms
   detached: finished
   drop: detached cleaned up

Read the second case carefully: "lazy" started before "fast" because select! "randomly picks a branch to check first" unless you write biased; ({{select! docs|https://docs.rs/tokio/latest/tokio/macro.select.html}}); run it again and the order may differ. And the fourth: dropping a JoinHandle detaches a spawned task, it does not cancel it; only abort() (or dropping the JoinSet that owns it) does.

Python, the same timeout: cancellation is an exception raised inside the coroutine at its await, so it can run cleanup (or even catch it):

1. asyncio.timeout(0.25) around a 2000 ms call
   slow: started, waiting 2000 ms
   slow: CancelledError raised at the await
   finally: slow cleaned up
   -> TimeoutError after 252 ms

What this means in practice. In Python, cleanup goes in finally; in Rust, cleanup goes in Drop (a guard), because there is no exception to catch. A future that has done half its work when dropped (read part of a message, taken an item off a queue) loses that half: cancel safety. tokio documents which of its methods are cancel safe; inside select! loops, use those, or keep state outside the future.
