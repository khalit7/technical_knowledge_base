You have a Python program and one part of it is slow. This part shows how to move that part into Rust, so Python calls it like any other module: first one function, then a class, then threads, then a wheel anyone can pip install. The running example is the root page's count_tokens program (read a 200,000-line JSONL chat log, count word-ish tokens per user), and every step is measured.

About 40 minutes. Every code block is a file in src/rb/ of the repository and every output block is its real output, recorded on 2026-10-05 on an Apple M1 Pro (8 performance and 2 efficiency cores, macOS 27) with CPython 3.14.8, Rust 1.99.0, PyO3 0.29.3 and maturin 1.15.0 (exact versions in src/rb/versions.txt; src/rb/run_all.sh reproduces everything). Timings are medians of 7 runs with the spread beside them; the laptop was in normal use (load average 9 to 12 on 10 cores during the recorded runs, up to 26 during earlier trial runs), so read the second digit of any timing as noise. You need the Rust basics of {{Part 1|#t-ra-read}} (ownership, borrowing, Result); each Rust idea used here links back to it.

1. Is it worth it? Profile first

An extension module is a compiled shared library (a .so file on macOS and Linux, .pyd on Windows) that Python loads with an ordinary import. CPython calls a function in it named PyInit_<name>, which hands back a module object whose functions are machine code. NumPy, PyTorch and orjson are all extension modules. Writing one costs a second language, a compiler in your build, and a wheel per platform (section 12), so do it only when the numbers say so.

In Python you would
reach for cProfile or py-spy, find the hot function, and try the cheap wins first: a better algorithm, a built-in (re, collections.Counter), NumPy, or an existing library. The {{Python page|n:3cd5c17b0d0d81b28acdea39e7a4d998}} (Part 1, "Performance") walks through that order. Rust comes after those, for a hot loop that is left and that no library already does.

Here is the root program, cut into its phases and timed (medians of 5 runs; the script is code/ladder.py with --phases):

Milliseconds per phase for the whole 200,000-line log (38.8 MB). Top bar: pure Python. Second bar: the same program with only the token loop moved into Rust. The loop shrinks from ms to ms, and what remains is mostly json.loads.

This is Amdahl's law: if a fraction p of the time is sped up s times, the whole program speeds up 1 / ((1 - p) + p/s). In-process, the token loop was % of the pure-Python run (p = ). Even an infinitely fast loop leaves the other %, so the best this change alone can give is 1 / (1 - p) = x, and we measured x. To go further, the parsing has to move too (section 10).

Worth it when
a profile shows one hot path you own, it is not array arithmetic NumPy already does, it runs often (a tokenizer, a parser, a sampler, a graph walk), and you can pass it big batches.
Not worth it when
the time is in I/O or the network, a library already does it (orjson, polars, pyarrow), or the hot code calls back into Python objects on every step.
What it costs
A Rust toolchain in your build, about 16 s for a clean build here, wheels per platform, and a team that can read Rust.
