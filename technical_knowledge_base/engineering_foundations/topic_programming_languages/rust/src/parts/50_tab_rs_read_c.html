A CLI with clap

The problem it solves. A command-line tool has to read arguments, validate them, print help, report errors on stderr, write results on stdout, and return an exit code a shell script can test. Doing that by hand is tedious and always slightly wrong. clap generates all of it from a struct.

Arguments are a struct

tok/src/bin/tokcount.rs (lines 10 to 37)
/// Count word-ish tokens per user in JSONL chat logs.
#[derive(Parser)]
#[command(name = "tokcount", version)]
struct Cli {
    #[command(subcommand)]
    cmd: Cmd,
}

#[derive(Subcommand)]
enum Cmd {
    /// Count tokens per user in one or more JSONL files ("-" reads stdin)
    Count {
        /// Input files; "-" means standard input
        #[arg(required = true)]
        files: Vec<PathBuf>,
        /// How many users to list
        #[arg(short = 'n', long, default_value_t = 5, value_parser = clap::value_parser!(u16).range(1..=1000))]
        top: u16,
        /// Print JSON instead of text
        #[arg(long)]
        json: bool,
        /// Exit with code 3 if any line is malformed
        #[arg(long)]
        strict: bool,
    },
    /// Count tokens in a piece of text (an argument, or stdin when absent)
    Text { text: Option<String> },
}

Read it like a typed argparse declaration. #[derive(Parser)] is a derive macro: at compile time it writes the parsing code for this struct. Each field is an argument; its type decides parsing (Vec<PathBuf> takes one or more paths, bool is a flag, Option<String> is optional, u16 must parse as a number); the /// doc comments become the help text. An enum with #[derive(Subcommand)] gives subcommands, one variant each, like git commit and git push. Part 1 explains why enums with data are the natural shape for "one of these" ({{Reading|#t-ra-read}}).

Arguments:
  <FILES>...  Input files; "-" means standard input

Options:

Errors and exit codes

Unix convention: exit 0 for success, non-zero for failure, and clap uses 2 for usage errors (its source defines USAGE_CODE = 2: {{clap_builder util|https://github.com/clap-rs/clap/blob/master/clap_builder/src/util/mod.rs}}). Everything after parsing is ours. The pattern: main calls a run function that returns anyhow::Result, so every fallible step can use ?, and only main decides how an error looks and which code it returns.

tok/src/bin/tokcount.rs (lines 39 to 49)
fn main() -> ExitCode {
    let cli = Cli::parse(); // bad arguments: clap prints usage and exits with code 2
    match run(cli) {
        Ok(code) => code,
        Err(e) => {
            // {:#} prints the whole context chain on one line: "outer: inner: cause"
            eprintln!("error: {e:#}");
            ExitCode::from(1)
        }
    }
}
Predict, then reveal: tokcount count -n 0 chat.jsonl: which exit code, and does any of our code run?
$ tokcount count -n 0 chat.jsonl
error: invalid value '0' for '--top <TOP>': 0 is not in 1..=1000

For more information, try '--help'.
[exit 2]
Predict, then reveal: tokcount count nope.jsonl: what does the message look like, and which code?
$ tokcount count nope.jsonl
error: cannot open nope.jsonl: No such file or directory (os error 2)
[exit 1]

with_context(|| format!("cannot open {}", ...)) wrapped the OS error in a sentence, and {e:#} printed the chain on one line: "cannot open nope.jsonl: No such file or directory (os error 2)". That is anyhow: an error type for applications that carries any error plus context. Libraries define their own error enums with thiserror instead (the service's AppError below), so callers can match on them. Part 1 teaches Result and ? ({{Reading|#t-ra-read}}).

stdin, stdout, stderr, and the broken pipe

Three conventions make a tool composable with |: results go to stdout, messages and progress to stderr, and - as a file name means stdin. The count branch:

tok/src/bin/tokcount.rs (lines 65 to 91)
        Cmd::Count { files, top, json, strict } => {
            let mut tally = Tally::default();
            for path in &files {
                if path.as_os_str() == "-" {
                    feed(&mut tally, io::stdin().lock(), "stdin")?;
                } else {
                    let f = File::open(path)
                        .with_context(|| format!("cannot open {}", path.display()))?;
                    feed(&mut tally, BufReader::new(f), &path.display().to_string())?;
                }
            }
            let report = tally.report(top as usize);
            let out = if json {
                serde_json::to_string_pretty(&report)? + "\n"
            } else {
                report.to_text()
            };
            // Write through a locked handle and treat a closed pipe (`| head`) as success:
            // println! would panic with "failed printing to stdout: Broken pipe".
            let mut stdout = io::stdout().lock();
            if let Err(e) = stdout.write_all(out.as_bytes()).and_then(|_| stdout.flush()) {
                if e.kind() != io::ErrorKind::BrokenPipe {
                    return Err(e).context("writing stdout");
                }
            }
            Ok(if strict && report.malformed > 0 { ExitCode::from(3) } else { ExitCode::SUCCESS })
        }
Predict, then reveal: A program that prints 100,000 lines with println!, piped into head -1. What happens after the first line?
$ target/release/examples/b1_naive_print | head -1; echo "[left side exit ${pipestatus[1]}]"
line 1

thread 'main' (N) panicked at /rustc/b940084d7eb6a299eb4bfeb8e34901bc051e7ac4/library/std/src/io/stdio.rs:1168:9:
failed printing to stdout: Broken pipe (os error 32)
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
[left side exit 101]
[exit 0]

head exits after one line, the pipe closes, and the next write fails with EPIPE. Rust programs ignore the SIGPIPE signal that would silently kill a C program (the runtime sets it to ignored before main: {{unstable book, on-broken-pipe|https://doc.rust-lang.org/beta/unstable-book/compiler-flags/on-broken-pipe.html}}), so the error reaches println!, which panics: exit code 101 and a panic message, in every Rust CLI that prints with println! in a loop. tokcount writes through a locked stdout handle (one lock for the whole output, also faster) and treats BrokenPipe as a normal end:

$ tokcount count chat.jsonl | head -1; echo "[left side exit ${pipestatus[1]}]"
lines 2000  ok 1992  malformed 8 (first at line 53)
[left side exit 0]
[exit 0]

Progress belongs on stderr, and only when a person is watching: io::stderr().is_terminal() is false in a pipe, a cron job or a CI log, so tokcount prints its line counter only in an interactive terminal (the {{indicatif|https://docs.rs/indicatif}} crate draws real progress bars the same way).

tok/src/bin/tokcount.rs (lines 95 to 115)
/// Read lines into the tally. Progress goes to stderr, and only when stderr is a terminal,
/// so pipes and logs stay clean.
fn feed(tally: &mut Tally, mut r: impl BufRead, name: &str) -> Result<()> {
    let show = io::stderr().is_terminal();
    let mut line = String::new();
    loop {
        line.clear();
        let n = r.read_line(&mut line).with_context(|| format!("reading {name}"))?;
        if n == 0 {
            break;
        }
        tally.add_line(line.trim_end_matches(['\n', '\r']));
        if show && tally.lines % 100_000 == 0 {
            eprint!("\r{name}: {} lines", tally.lines);
        }
    }
    if show && tally.lines >= 100_000 {
        eprintln!();
    }
    Ok(())
}
Python bridge
argparse also exits 2 on usage errors. The differences: clap's checks are generated from types (a u16 field cannot receive "abc"), the help is always in sync with the code, and Python prints a traceback for an uncaught exception where tokcount prints one line. Python's print in a loop piped into head raises BrokenPipeError: the same bug, different name.
Costsclap, with serde_json, is most of the CLI's dependencies: compile time on the first build and binary size (the whole stripped tokcount is 0.93 MB). For a two-flag internal tool, std::env::args() is fine.
When notA ten-line script you run once: write it in Python. A CLI earns Rust when it is distributed, run often, or does real work per byte.
