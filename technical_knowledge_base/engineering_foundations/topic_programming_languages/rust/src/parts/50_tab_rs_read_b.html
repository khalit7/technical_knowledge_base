The three ideas to keep from this part. (1) A Rust tool or service is one compiled file: that is most of why people write them. (2) Async Rust is lazy and cooperative: a future runs only when polled, and it gives the thread back only at an .await; CPU work between awaits blocks every other request on that thread (measured below: /health p50 went from 0.44 ms to 10.7 ms). (3) The type system follows you into concurrency: tokio::spawn demands Send + 'static, so data races and dangling borrows across tasks are compile errors, not incidents.

The crates, and one Cargo.toml

A crate is a Rust package (Part 1's {{Reading|#t-ra-read}} covers cargo, modules and crates). Rust's standard library deliberately has no HTTP, no async runtime and no argument parser; the ecosystem settled on a small set of de facto standards instead. This part's whole project uses ten dependencies:

tok/Cargo.toml (lines 1 to 22)
[package]
name = "tok"
version = "0.1.0"
edition = "2024"
description = "Part 3 of the Rust page: the root's token counter as a CLI (tokcount) and an HTTP service (tokserve)"
publish = false

[dependencies]
anyhow = "1"
axum = "0.8"
clap = { version = "4", features = ["derive", "env"] }
serde = { version = "1", features = ["derive"] }
serde_json = "1"
thiserror = "2"
tokio = { version = "1", features = ["full"] }
tower-http = { version = "0.6", features = ["trace", "timeout", "limit"] }
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }

[dev-dependencies]
http-body-util = "0.1"
tower = { version = "0.5", features = ["util"] }

features = [...] switches on optional parts of a crate at compile time (clap's derive macros, tokio's full runtime); fewer features means a faster build and a smaller binary. Cargo.lock (committed next to it) pins every transitive version, like uv.lock. The project is a library plus two binaries: src/lib.rs holds the counting logic (the root page's program), src/bin/tokcount.rs is the CLI and src/bin/tokserve.rs the service. Cargo builds every file in src/bin/ as its own executable, and both link the same library, so there is one implementation and two front ends.

Python bridge
This is the shape of a Python project with a package plus two [project.scripts] entry points. The difference is what you ship: here each entry point compiles to a self-contained executable with the library inside it.

Versions resolved on 2026-10-05: tokio 1.53.2, axum 0.8.9, clap 4.6.7, serde 1.0.229, tracing 0.1.44, tower-http 0.6.11 (0.7.1 exists; this project pins 0.6). The async-std runtime you may meet in old tutorials is discontinued; its README says "use smol instead" ({{async-std|https://github.com/async-rs/async-std}}).
