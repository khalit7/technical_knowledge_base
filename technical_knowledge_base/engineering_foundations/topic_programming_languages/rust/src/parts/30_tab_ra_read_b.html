4. Ownership and moves

First, where values live. Each function call gets a stack frame, a block of memory for its local variables, released automatically when the function returns. Data whose size is only known at run time (a growing vector, a string read from a file) goes on the heap, which someone must release explicitly. A Rust String or Vec is a small fixed-size header on the stack (three machine words: a pointer to the heap buffer, the capacity, the length; 24 bytes) plus a buffer on the heap. Python hides all of this: every object is on the heap and names are references to it.

The ownership rules ({{Rust Book 4.1|https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html}}): each value has one owner (a variable, a field, a vector slot); when the owner goes out of scope the value is dropped (its heap memory freed); assigning or passing a value moves ownership.

move.rs
fn shout(s: String) -> String {
    // takes ownership of s; returns ownership of a new String
    s.to_uppercase()
}

fn main() {
    let a = String::from("hello");
    let b = a; // move: b now owns the heap buffer
    println!("b = {b}");
    let c = b.clone(); // explicit deep copy: a second heap buffer
    let d = shout(b); // b moves into the function
    println!("c = {c}, d = {d}");
    let n = 5; // i32 is Copy: assignment copies the bits
    let m = n;
    println!("n = {n}, m = {m}"); // both still usable
}
$ rustc --edition 2024 move.rs && ./move
b = hello
c = hello, d = HELLO
n = 5, m = 5

After let b = a; the 24-byte header was copied into b and a became unusable. The heap buffer was not copied and not freed: it now has exactly one owner again. Using a afterwards is refused:

The Python bridge
In Python, b = a makes two names for one object, kept alive by a reference count. Rust refuses the second name, so it never needs a count: the single owner frees the buffer at a point the compiler knows. Think of a move as handing over the only key.
  • Copy types (integers, floats, bool, char, and tuples or arrays of them) have no heap part, so assignment copies the bits and both stay usable (n and m above).
  • clone() is the explicit deep copy: a second heap buffer. It is visible in the code on purpose, so you can see every place that copies data.
  • Passing to a function moves too (shout(b)); returning moves ownership back out.

Drop: cleanup at a known moment

A type can run code when it is dropped by implementing the Drop trait, which is how files close, locks release and buffers free themselves. There is no garbage collector, so the order is fixed:

drop.rs
struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

fn consume(n: Noisy) {
    println!("consume got {}", n.0);
} // n is dropped here, at the end of the function that owns it

fn main() {
    let _a = Noisy("a");
    let b = Noisy("b");
    {
        let _c = Noisy("c");
        println!("inner scope ends");
    } // c dropped here
    consume(b); // b moved into consume; dropped inside it
    let _d = Noisy("d");
    println!("main ends");
} // locals dropped in reverse order of declaration: d, then a
Predict, then reveal: In what order are the four drop lines printed?
$ rustc --edition 2024 drop.rs && ./drop

Locals drop at the end of their scope in reverse order of declaration; a value moved into a function drops at the end of that function. This is C++'s RAII (resource acquisition is initialisation) made the default; Python's equivalent is with, which you have to remember to write.

SolvesUse after free and double free, with no garbage collector and no reference counts.
CostsYou must decide who owns each value; sharing needs borrowing (section 5) or explicit shared ownership (section 15).
Common mistakeSprinkling .clone() until it compiles. Fine for small values; in a hot loop it allocates on every iteration. Borrow first.

5. Borrowing: many readers or one writer

Moving everything everywhere would be unbearable, so you lend a value instead: a reference &v borrows it without taking ownership. Two kinds:

  • &T, a shared reference: read only; any number at once.
  • &mut T, an exclusive (mutable) reference: may change the value; while it is in use, no other reference to that value may be.
borrow.rs
fn total(v: &[u64]) -> u64 {
    // borrows: reads, does not own
    v.iter().sum()
}

fn add_one(v: &mut Vec<u64>) {
    // borrows exclusively: may change it
    v.push(1);
}

fn main() {
    let mut v = vec![3, 4, 5];
    let a = &v; // any number of shared borrows at once
    let b = &v;
    println!("{} {}", total(a), total(b));
    add_one(&mut v); // a and b are no longer used, so this is allowed
    println!("{:?} total {}", v, total(&v));
}
$ rustc --edition 2024 borrow.rs && ./borrow
12 12
[3, 4, 5, 1] total 13

The part of the compiler that enforces this is the borrow checker. A borrow lasts from where it is created to its last use, not to the end of the block (the Book: "a reference's scope starts from where it is introduced and continues through the last time that reference is used"). That is why add_one(&mut v) is accepted above: a and b are never used again.

How to read a borrow error


    

  1. The code and headline (E0502, "cannot borrow v as mutable because it is also borrowed as immutable") say which rule broke.
    2. 

  2. The labels are a story in source order: where the first borrow starts, where the conflicting use happens, and where the first borrow is later used. That third label is the key: it is the reason the first borrow is still alive.
    3. 

  3. The fix is nearly always one of four: end the first borrow earlier (move its last use up), copy or clone the small value out, restructure into "read first, then write", or give the data a different owner. help: lines often propose one; they are usually right for the code as written, and not always right for your design.
    4. 

  4. rustc --explain E0502 prints a full explanation with examples (also online in the {{error code index|https://doc.rust-lang.org/error_codes/error-index.html}}).
    5.

6. Lifetimes in plain words


A lifetime is the stretch of the program during which a reference is valid. The checker computes them itself almost everywhere. You write one, as 'a, only when a function returns a reference (or a struct holds one) and the compiler cannot tell which input it came from:

Read 'a as a name for "some region of the program". The fixed signature says: the result is valid as long as both inputs are. Lifetimes generate no code; they are a contract the checker verifies at every call.


life.rs
// 'a names "some region of the program". The signature promises: the result
// lives no longer than the shorter-lived of a and b.
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

// One input reference: the compiler fills in the lifetimes itself (elision).
fn first_word(s: &str) -> &str {
    s.split(' ').next().unwrap_or("")
}

// A struct that holds a reference must say how long it may live.
struct Token<'a> {
    text: &'a str,
}

fn main() {
    let a = String::from("tokens");
    let w;
    {
        let b = String::from("logits!");
        w = longest(&a, &b);
        println!("longest: {w}");
    }
    let t = Token { text: first_word("hello world") };
    let s: &'static str = "string literals live for the whole program";
    println!("{} | {}", t.text, s);
}


$ rustc --edition 2024 life.rs && ./life
longest: logits!
hello | string literals live for the whole program

When do you write them? The {{elision rules|https://doc.rust-lang.org/reference/lifetime-elision.html}} fill in the common cases: each input reference gets its own lifetime; if there is exactly one input lifetime, outputs get it (first_word); in a method taking &self, outputs get self's. So you write lifetimes when a function has two or more reference inputs and returns a reference, or a struct stores a reference. 'static means "valid for the whole program": string literals are &'static str because they live in the program's binary.


What no lifetime can do is make a reference to a value that is about to die, because annotations describe lifetimes and never extend them:


dangle_err.rs
fn make_greeting(name: &str) -> &str {
    let s = format!("hello {name}");
    &s
}

fn main() {
    println!("{}", make_greeting("ada"));
}

The fix is to return the owned String. That is the general rule of thumb: if "just add a lifetime" spreads 'a through many types, store an owned value instead; borrowing in structs is an optimisation for later.







7. Strings and slices: String vs &str, and UTF-8


A slice is a borrowed view into a run of elements owned by someone else: a pointer and a length. &[u64] is a slice of numbers (borrowed from a Vec, an array or part of either); &str is a slice of text. Rust has two main string types:

Both are always valid UTF-8, and lengths and indexes are in bytes. Python's str counts code points. On the same text:


strings.rs
fn count_words(text: &str) -> usize {
    // &str accepts a String (via &s) and a literal alike
    text.split_whitespace().count()
}

fn main() {
    let s = String::from("café 日本語 🦀");
    println!("len() = {} bytes", s.len());
    println!("chars = {}", s.chars().count());
    println!("bytes of 'é': {:?}", "é".as_bytes());
    println!("&s[0..3] = {:?}", &s[0..3]); // byte offsets
    println!("first char = {:?}", s.chars().next());
    println!("char_indices: {:?}", s.char_indices().map(|(i, _)| i).collect::<Vec<_>>());
    let mut owned = String::new(); // String: owned, growable, on the heap
    owned.push_str("tokens");
    owned += " and logits";
    let view: &str = &owned[0..6]; // &str: a borrowed view (pointer + length)
    println!("{owned} | {view} | words {}", count_words(&owned) + count_words("a literal is a &str"));
    println!("size_of String = {}, &str = {}", std::mem::size_of::<String>(), std::mem::size_of::<&str>());
    println!("upper: {}", s.to_uppercase());
    println!("reversed chars: {}", s.chars().rev().collect::<String>());
    let cut = &s[0..4]; // 'é' occupies bytes 3 and 4: this panics at run time
    println!("{cut}");
}
