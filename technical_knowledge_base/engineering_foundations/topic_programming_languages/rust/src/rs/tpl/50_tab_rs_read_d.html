Shipping a binary

The problem it solves. Giving a Python tool to someone means giving them a Python, a virtual environment and the right wheels. A Rust tool is one executable file with its dependencies compiled in. Three ways to get it onto a machine:

  • cargo install --path . (or cargo install <crate> from crates.io) compiles the binaries in release mode and copies them to ~/.cargo/bin: the equivalent of uv tool install or pipx, but it builds from source, so the user needs a Rust toolchain.
  • Copy the file from target/release/: works on machines with the same OS, CPU architecture and (on Linux) a compatible C library.
  • Release prebuilt binaries per platform (GitHub releases, Homebrew, a container image), built by CI or cross-compiled as below. This is how uv and ruff ship.

The useful reading: debug builds are large and slow and never for measuring (Part 1's iterator benchmark shows the speed gap: {Reading|#t-ra-read}); release is a good default; stripping and LTO are cheap wins for distributed binaries; opt-level = "z" is for when size matters more than speed (embedded, WebAssembly, a CLI downloaded millions of times).

Static binaries and cross-compilation

A dynamically linked binary loads shared libraries (the C library, at least) when it starts; a statically linked one contains everything and runs on any machine with the same OS and CPU. Rust links its own crates statically always; the question is only the C library.

  • macOS: every binary links Apple's libSystem dynamically (tokserve also links libiconv, which ships with macOS: see otool -L below), and Apple does not support anything else ("Apple does not support statically linked binaries on Mac OS X": {QA1118|https://developer.apple.com/library/archive/qa/qa1118/_index.html}). That is fine: libSystem is on every Mac.
  • Linux: the usual target links glibc dynamically, so a binary built on a new distribution can fail on an old one. The *-unknown-linux-musl targets link the musl C library statically: one file that runs on any Linux kernel of that architecture, and the input for the empty container image below.

Cross-compiling means building for a different OS or CPU than the one you are on. rustup target add downloads the standard library for the target; you also need a linker for it. For a pure-Rust crate (no C code, as here: no TLS library), the rust-lld linker that ships with rustup was enough on this Mac. The rustc docs show a cross gcc as the linker and do not promise this; crates with C dependencies need a real cross toolchain, which is what {cargo-zigbuild|https://github.com/rust-cross/cargo-zigbuild} (zig as the linker) and {cross|https://github.com/cross-rs/cross} (builds in a container) provide.
