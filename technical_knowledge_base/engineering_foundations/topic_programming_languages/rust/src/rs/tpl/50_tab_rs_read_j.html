Measured: the same service in axum and in FastAPI

The FastAPI twin (code/py/app.py) has the same routes, the same rules and returns byte-identical JSON; it uses the root page's reference token function and FastAPI's advice for blocking work (the log count runs in a worker thread). Both were driven by the same load generator (oha 1.16.0) on the same laptop, four configurations (1 or 4 async worker threads for axum, 1 or 4 uvicorn worker processes for FastAPI), three short rounds each. How to read it. For tiny requests both are fast in absolute terms, and a real service's time goes to its database or model call, not the framework: at a steady 1,000 requests per second every configuration answered /count with a median under half a millisecond. The gaps that matter are CPU work in Python (counting 391 KB costs about [[b:fastapi-1|count_log@20/s|p50_ms|.0f]] ms in Python and [[b:axum-4|count_log@20/s|p50_ms|.1f]] ms in Rust, and in one uvicorn worker the GIL lets only one count run at a time, even on worker threads) and memory per worker: Python scales across cores with processes, each holding its own interpreter and imports, where tokio scales with threads in one process. The {{Service benchmark|#t-rs-bench}} tab has every run, the spread, the open-loop latencies and the caveats; how to load-test properly (open vs closed loop, coordinated omission) is the SWE topic's {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}} page. The root page's {{Benchmark tab|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} measures the same program as a batch job.

What this does not show
The laptop was in normal use (load average 7 to 13 on 10 cores) and the load generator ran on the same machine, so absolute numbers are low and noisy (the spread is in the tab); oha with 2 threads may itself cap the axum /health runs. "1 worker" for axum still offloads /count_log to tokio's blocking pool, so it used more than one core on that load. Production Python services often move CPU work out of the request path (a queue, or a Rust extension: Part 2, {{Reading|#t-rb-read}}), which removes most of the /count_log gap. No TLS, no database, loopback networking.

Rust in ML serving

The pattern above (a fast, small HTTP front end in Rust around heavy compute) is how Hugging Face built its servers. Text Generation Inference's router is a Rust crate on axum (its router/Cargo.toml lists axum = 0.7), with the model code in Python; its README now says "text-generation-inference is now in maintenance mode" ({{TGI|https://github.com/huggingface/text-generation-inference}}). Text Embeddings Inference is mostly Rust (1.0 MB of Rust against 0.13 MB of Python by GitHub's language count, 2026-10-05: {{TEI|https://github.com/huggingface/text-embeddings-inference}}). The model-side libraries the old page listed (candle, burn, ort, mistral.rs) and serving concepts (batching, KV cache) belong to the {{inference and serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} topic; GPU kernels in Rust to the {{CUDA and GPU programming|n:3c65c17b0d0d81c39f34d5e070d783c1}} topic.
