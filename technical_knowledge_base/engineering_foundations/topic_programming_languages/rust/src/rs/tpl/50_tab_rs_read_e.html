Async Rust from zero

The problem it solves. A service spends most of its time waiting: for the network, a database, a model API. One OS thread per waiting request works up to a few thousand requests, then the memory for stacks and the cost of switching threads dominate. Async lets one thread juggle many waiting operations: each operation runs until it would wait, hands the thread back, and is resumed when its data arrives. Python's asyncio and JavaScript's event loop are the same idea; the Python page's Part 1 teaches asyncio from the event loop up ({{Python page|n:3cd5c17b0d0d81b28acdea39e7a4d998}}, tab "Event loop"). Rust's version differs in three ways, each shown below with real runs: futures are lazy, the runtime is a library you choose (and usually runs on several threads), and cancellation is dropping.

1. A future is a value, and it is lazy

An async fn does not run when you call it. It returns a future: a value that describes the work, which runs only when something polls it, normally .await.

2. What .await does: poll, Pending, wake

Every future implements one method, poll. The runtime calls it; it returns Poll::Ready(value) if done, or Poll::Pending if it has to wait, after arranging for a waker to be called when it can make progress (a socket becomes readable, a timer fires). The runtime then polls something else, and polls this future again only after its waker fires. That is the whole protocol. A hand-written future, to see it:

[[code:tok/examples/a1_poll.rs]] [[out:a1_poll]]

You will almost never write poll yourself; async fn generates it, with one state per .await point. Two consequences matter every day: code between two awaits runs without interruption (no other task can run on that thread meanwhile), and a future that is never polled again simply stops at its last await.

Pin, in one paragraph. The generated state machine can hold a reference to one of its own local variables across an await (a buffer and a slice of it). If the future were moved in memory, that reference would dangle. poll therefore takes Pin<&mut Self>: a pointer that promises the future will not move again once polled. .await, tokio::spawn and Box::pin handle it for you; you meet Pin when storing futures in structs or writing poll by hand ({{std::pin docs|https://doc.rust-lang.org/std/pin/index.html}}).
