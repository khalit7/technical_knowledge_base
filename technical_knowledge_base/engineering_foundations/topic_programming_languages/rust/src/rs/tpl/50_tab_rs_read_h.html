An HTTP service with axum

The problem it solves. Turn the token counter into something other programs call over HTTP: POST /count with {"text": "..."} returns {"tokens": n}, POST /count_log with a JSONL body returns the root program's report as JSON. axum is the tokio project's web framework: a thin, typed layer over the hyper HTTP library. If you know FastAPI, most of it maps one to one. HTTP design itself (methods, status codes, idempotency, versioning) is the SWE topic's page: {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}.

Routes and handlers

[[code:tok/src/service.rs:70-98]]

A handler is an async fn. Its parameters are extractors: types that know how to pull something out of the request. Json<CountReq> parses the body as JSON into the struct (serde checks every field and type, like a pydantic model); State<...> hands over shared state; Query<T> parses the query string; axum::body::Bytes takes the raw body. Its return type must implement IntoResponse: a String, a Json<T>, a status code, a tuple of those, or a Result of two of them. If an extractor fails, axum answers for you and the handler never runs:

[[pr:svc_missing|Send {"txt": "oops"} (a typo in the field name). Which status, and what body?]] [[pr:svc_ctype|Send valid JSON without a content-type: application/json header. Which status?]]
Python bridge
FastAPI answers the same mistake with 422 and a structured JSON detail list (recorded from the FastAPI twin in code/py/app.py: {"detail":[{"type":"missing","loc":["body","text"],"msg":"Field required",...}]}). axum's default rejection is a plain-text sentence; to get JSON errors, write your own extractor wrapper or map rejections in a layer. FastAPI's dependency injection corresponds to extractors and State; Starlette middleware corresponds to tower layers.

The #[from] tokio::task::JoinError line lets ? convert a crashed background job into a 500 automatically. A panic (a bug such as an out-of-bounds index) inside a handler does not take the server down: tokio catches it at the task boundary, that one connection is closed without a response, and other requests carry on. examples/b3_panic.rs, with curl as the client:

[[out:b3_panic]]

curl's exit 52 is "empty reply from server". To answer 500 instead, add tower-http's CatchPanicLayer; to find the bug, the panic message is on stderr with the file and line.

Shared state

Every request runs as its own task, maybe on another thread, so shared state goes behind an Arc (a thread-safe shared pointer; Part 1, {{Reading|#t-ra-read}}) and anything mutable inside it must be thread-safe: here, two atomic counters. with_state(state) gives each handler a cheap clone of the Arc. For a mutable map, use a Mutex (held briefly, never across an await) or a concurrent map; for a database pool, the pool type is already shareable. Python's equivalent, a module-level dict, is per worker process under uvicorn --workers 4, so /stats on the FastAPI twin reports only the worker that answered. tokserve's counters are process-wide because its workers are threads:

CPU work inside a handler

Counting a 391 KB log is about a millisecond of CPU; a 3.9 MB one about ten times that. Either is far above the 10 to 100 µs budget between awaits, so the handler moves it to the blocking pool (the inline mode exists only for the measurement above). Note the double ??: the first unwraps the JoinError (did the background job panic?), the second the counting's own Result.

Middleware: tower layers

A layer wraps the whole router in reusable behaviour; tower-http provides the common ones. The last .layer added is the outermost, so a request passes through tracing, then the timeout, then the body limit, then the route. Two of them in action:

[[pr:svc_timeout|GET /slow?ms=1500 with the default 1,000 ms request timeout. What comes back?]] [[pr:svc_toolarge|POST a 3.9 MB log when the limit is 1 MiB. What comes back, and does the handler run?]]

Watch out for two body limits: axum's extractors refuse bodies over 2 MB by default ({{DefaultBodyLimit|https://docs.rs/axum/latest/axum/extract/struct.DefaultBodyLimit.html}}), independently of any tower layer. This project's first benchmark of the blocking experiment was silently measuring fast 413 rejections because of it; DefaultBodyLimit::disable() plus one configured RequestBodyLimitLayer leaves a single limit to reason about.

Logs and spans: tracing

tracing records events (log lines with typed fields) inside spans (a named period of work, here one per request, opened by TraceLayer). The subscriber decides the format and filter; RUST_LOG=info,tower_http=debug asks for info everywhere and per-request lines from tower-http. Configuration and graceful shutdown

The service reads its settings with clap, with env = "TOK_ADDR" on each flag, so the same binary takes flags on a laptop and environment variables in a container (twelve-factor style):

[[out:svc_help]]

When an orchestrator stops a container it sends SIGTERM, waits a grace period, then sends SIGKILL: 10 s by default for docker stop ({{docs|https://docs.docker.com/reference/cli/docker/container/stop/}}), 30 s by default on Kubernetes ({{pod lifecycle|https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/}}). A service that dies on SIGTERM drops every request in flight. with_graceful_shutdown takes a future; when it resolves, axum stops accepting connections and waits for in-flight requests to finish:

[[code:tok/src/bin/tokserve.rs:51-75]] [[out:svc_graceful]]

The slow request that was in flight when SIGTERM arrived completed with 200; the new connection was refused; the process exited 0 after draining. In production, also put a timeout on the drain (requests longer than the grace period are killed anyway).
