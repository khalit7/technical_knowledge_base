Rust: the essentials

What every reader of the Rust pages needs first: one owner per value and borrows checked before the program runs, drawn on one Vec at its real addresses; cargo; numbers that differ from Python; modules; fifteen real borrow-checker errors to practise on; the traps that cut across the language; and the map of the four child pages. Every output and compiler error is a real run (rustc 1.99.0, CPython 3.14.8) on an Apple M1 Pro. Data as of October 2026. Reading: 26 min, plus 11 in closed details.

Every Rust value has exactly one owner, and the compiler checks every borrow of it before the program runs: nothing may use a value after its owner has freed it, or while someone else is changing it. So use after free, dangling references, iterator invalidation and data races become compile errors, with no garbage collector and no reference counts; the price is that you decide who owns what.

One Vec, at its real addresses: a borrow copies nothing, growth moves the buffer, a move copies 24 bytes, drop frees at a known line

One small program, stepped line by line. A Rust Vec is a 24-byte header on the stack (pointer, capacity, length) and a buffer on the heap. Every address and number below was printed by the program itself when it ran (rustc 1.99.0). Predict first: after let w = v;, which address changes, the stack slot or the heap block? Then step. Switch to Python for the same steps in Python's model: names pointing at one object, and a reference count.

The captions name what changes at each step, and the counters under the figure keep the score: allocations, live blocks, bytes copied by moves, elements copied.

What the run shows, in six lines
  • Borrowing never copies. r and m are 8-byte pointers to v's stack slot (the same address the program printed for v).
  • Growth moves the buffer. push on a full vector allocated a new block (capacity 3 to 6) and freed the old one. That is exactly why the borrow checker refuses a reference into the buffer across a push (section 5).
  • A move copies 24 bytes, not the data. w has a new stack address but the same heap address as v had; v is unusable afterwards.
  • Clone allocates. c got its own buffer; on this run the allocator handed it the block freed at step 3 (heap 0x102d3d4a0, the same as step 1). Reusing freed memory is normal, and is why a dangling pointer can read someone else's data in C++.
  • Drop frees at a known line. drop(w) released the second buffer immediately; c is freed at the closing brace of main.
  • In Python every step after the first only adds a name to one object (the count rises to 4); copy() is the only new allocation; del w removes a name, not the object.
The source and the two recorded runs
own_anim.rs
// Prints the real addresses behind the ownership animation: a Vec is three
// machine words on the stack (pointer, capacity, length) and a buffer on the heap.
fn show(step: &str, name: &str, v: &Vec<u32>) {
    println!(
        "{step} {name} stack={:p} heap={:p} len={} cap={} data={:?}",
        v as *const Vec<u32>, v.as_ptr(), v.len(), v.capacity(), v
    );
}

fn main() {
    println!("size_of::<Vec<u32>>() = {}", std::mem::size_of::<Vec<u32>>());
    let mut v: Vec<u32> = Vec::with_capacity(3);
    v.extend([10, 20, 30]);
    show("1", "v", &v);
    let r = &v; // a shared borrow: a pointer to v's stack slot
    println!("2 r points to {:p} (v's stack slot), r.len()={}", r as *const Vec<u32>, r.len());
    v.push(40); // r is no longer used, so v may be mutated: the buffer is full, so it grows
    show("3", "v", &v);
    let m = &mut v; // one exclusive borrow
    m[0] = 11;
    println!("4 m points to {:p}, wrote m[0]=11", m as *const Vec<u32>);
    let w = v; // move: the three words are copied to w's slot, the heap buffer is not touched
    show("5", "w", &w);
    let c = w.clone(); // clone: a new heap buffer with a copy of the elements
    show("6", "c", &c);
    drop(w); // w's buffer is freed now
    println!("7 dropped w");
    show("8", "c", &c);
}

Owner, drop
the variable (or field, or vector slot) responsible for a value; when it goes out of scope the value is dropped and its memory freed.
Move
assignment or passing hands ownership over; the old name may not be used again.
Copy, clone()
small plain values (numbers, bool) are copied bit for bit; clone() is the explicit deep copy of anything else.
Borrow: &T, &mut T
a reference that uses a value without owning it: any number of shared (read-only) borrows, or one exclusive (mutable) borrow.
Borrow checker
the part of the compiler that proves every borrow ends before its value is freed or changed by someone else.
Crate, cargo
a crate is a unit of compiled Rust (a library or a program); cargo builds, tests, lints and fetches them.

1. Rust in one screen, for a Python programmer

Rust is the language under much of the Python tooling you already use (uv, ruff, ty, pydantic-core, Hugging Face tokenizers, polars). Python gets memory safety from reference counting and a garbage collector at run time; C++ trusts you. Rust checks a set of rules at compile time and then runs with no collector at all. 2. Cargo: the one tool

Rust is compiled: rustc, the compiler, turns source files into a machine-code program before anything runs. You rarely call it yourself. Cargo is the build tool and package manager: it creates projects, downloads dependencies, calls rustc, runs tests and lints. A package of Rust code is a crate; the public registry is crates.io. Toolchains are installed and updated by rustup (here the stable 1.99.0 of 2026-10-01; a new stable ships every six weeks, RELEASES.md).

Cargo.lock pins the exact versions resolved, like uv.lock, and the version rules differ from pip's in one way that bites: for a 0.x crate the minor number is the breaking one.

Dependencies, versions, the lock file, features and build-time code
  • Cargo.toml lists dependencies with version requirements; Cargo.lock pins the exact versions resolved, like uv.lock. Commit it.
  • serde = "1.0" means "compatible with 1.0": any 1.x. For 0.x versions the minor number is the breaking one: "0.14" accepts 0.14.9 but not 0.15.0 (Cargo book, SemVer compatibility). Much of the ecosystem is at 0.x, so this matters.
  • Two incompatible versions of one crate can both end up in your program (say rand 0.8 and 0.9). That avoids dependency deadlock, at the cost of a confusing error: two types with the same name that are not the same type.
  • Features are optional parts of a crate switched on at compile time: serde = { version = "1", features = ["derive"] }. They are unified: if any crate in the build turns one on, everyone gets it.
  • Build scripts (build.rs) and procedural macros run code at build time, the same trust question as a Python package's setup code. cargo audit checks the lock file against the RustSec advisory database.

3. Variables and numbers: what differs from Python

vars.rs
fn main() {
    let x = 5; // immutable by default
    let mut y = 5; // `mut` makes it changeable
    y += 1;
    let spaces = "   "; // shadowing: a new variable with the same name...
    let spaces = spaces.len(); // ...may even have a different type
    const MAX_TOKENS: u32 = 4_096; // a compile-time constant, type required
    println!("x={x} y={y} spaces={spaces} max={MAX_TOKENS}");
    let z; // declared now, assigned once later
    if y > 5 { z = "big" } else { z = "small" }
    println!("z={z}");
}
$ rustc --edition 2024 vars.rs && ./vars
x=5 y=6 spaces=3 max=4096
z=big
  • let introduces a variable. Its type is inferred from use, like Python, but fixed at compile time: y is an i32 (the default integer type) forever.
  • Immutable by default. Change it and the compiler refuses with E0384, "cannot assign twice to immutable variable", and suggests let mut.

That error has the shape of every Rust error: a code (E0384; rustc --explain E0384 prints a page about it), the file and line, the source with labels under the relevant spans, and usually a help with the fix (+++ marks inserted text).

  • Shadowing: a second let spaces makes a new variable that hides the old one, even with a new type. Useful for "parse this string into a number and keep the name"; it is not mutation.
  • Rust is expression-based: if, match and blocks { ... } produce values. A block's value is its last expression without a semicolon, which is why functions end in sum rather than return sum;.
  • println! ends in ! because it is a macro: code that writes code at compile time. {x} in the format string is like an f-string; {:?} prints the debug form (like repr), {:#?} pretty-prints it.

Numbers: fixed widths, checked overflow

This is the documented rule (Rust Book 3.2, Integer Overflow): debug builds check and panic; release builds wrap with two's complement and "relying on integer overflow's wrapping behavior is considered an error". When overflow is possible, say what you want: checked_* (an Option), wrapping_*, saturating_* or overflowing_*. A panic is Rust's crash for bugs: it prints the message and location, unwinds the thread and exits with code 101. If the compiler can see the overflow (255 + 1 as a u8), it refuses outright: "this arithmetic operation will overflow".

The arithmetic differences that bite Python programmers:

  • Integer / truncates toward zero (-7 / 2 is -3, Python's // gives -4); div_euclid and rem_euclid give Python's answers for positive divisors.
  • as never fails: it truncates integers (300 as u8 is 44), reinterprets signs (-1 as u32 is 4294967295), and saturates float to integer (not-a-number becomes 0). Use TryFrom when a value might not fit.
  • Floats are the same IEEE 754 doubles as Python's: 0.1 + 0.2 prints the same.

4. Ownership and moves

First, where values live. Each function call gets a stack frame, a block of memory for its local variables, released automatically when the function returns. Data whose size is only known at run time (a growing vector, a string read from a file) goes on the heap, which someone must release explicitly. A Rust String or Vec is a small fixed-size header on the stack (three machine words: a pointer to the heap buffer, the capacity, the length; 24 bytes) plus a buffer on the heap, as the hero at the top draws. Python hides all of this: every object is on the heap and names are references to it.

The ownership rules (Rust Book 4.1): each value has one owner (a variable, a field, a vector slot); when the owner goes out of scope the value is dropped (its heap memory freed); assigning or passing a value moves ownership.

move.rs
fn shout(s: String) -> String {
    // takes ownership of s; returns ownership of a new String
    s.to_uppercase()
}

fn main() {
    let a = String::from("hello");
    let b = a; // move: b now owns the heap buffer
    println!("b = {b}");
    let c = b.clone(); // explicit deep copy: a second heap buffer
    let d = shout(b); // b moves into the function
    println!("c = {c}, d = {d}");
    let n = 5; // i32 is Copy: assignment copies the bits
    let m = n;
    println!("n = {n}, m = {m}"); // both still usable
}
$ rustc --edition 2024 move.rs && ./move
b = hello
c = hello, d = HELLO
n = 5, m = 5

After let b = a; the 24-byte header was copied into b and a became unusable. The heap buffer was not copied and not freed: it now has exactly one owner again. Using a afterwards is refused with E0382, "borrow of moved value: a", and the error names the cause: String does not implement the Copy trait.

The Python bridge
In Python, b = a makes two names for one object, kept alive by a reference count. Rust refuses the second name, so it never needs a count: the single owner frees the buffer at a point the compiler knows. Think of a move as handing over the only key.
  • Copy types (integers, floats, bool, char, and tuples or arrays of them) have no heap part, so assignment copies the bits and both stay usable (n and m above).
  • clone() is the explicit deep copy: a second heap buffer. It is visible in the code on purpose, so you can see every place that copies data.
  • Passing to a function moves too (shout(b)); returning moves ownership back out.

Drop: cleanup at a known moment

A type can run code when it is dropped by implementing the Drop trait, which is how files close, locks release and buffers free themselves. There is no garbage collector, so the order is fixed:

drop.rs
struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

fn consume(n: Noisy) {
    println!("consume got {}", n.0);
} // n is dropped here, at the end of the function that owns it

fn main() {
    let _a = Noisy("a");
    let b = Noisy("b");
    {
        let _c = Noisy("c");
        println!("inner scope ends");
    } // c dropped here
    consume(b); // b moved into consume; dropped inside it
    let _d = Noisy("d");
    println!("main ends");
} // locals dropped in reverse order of declaration: d, then a

Locals drop at the end of their scope in reverse order of declaration; a value moved into a function drops at the end of that function. This is C++'s RAII (resource acquisition is initialisation) made the default; Python's equivalent is with, which you have to remember to write.

SolvesUse after free and double free, with no garbage collector and no reference counts.
CostsYou must decide who owns each value; sharing needs borrowing (section 5) or explicit shared ownership (Rc, Arc: the lifetimes child, section 2).
Common mistakeSprinkling .clone() until it compiles. Fine for small values; in a hot loop it allocates on every iteration. Borrow first.

5. Borrowing: many readers or one writer

Moving everything everywhere would be unbearable, so you lend a value instead: a reference &v borrows it without taking ownership. Two kinds:

  • &T, a shared reference: read only; any number at once.
  • &mut T, an exclusive (mutable) reference: may change the value; while it is in use, no other reference to that value may be.
borrow.rs
fn total(v: &[u64]) -> u64 {
    // borrows: reads, does not own
    v.iter().sum()
}

fn add_one(v: &mut Vec<u64>) {
    // borrows exclusively: may change it
    v.push(1);
}

fn main() {
    let mut v = vec![3, 4, 5];
    let a = &v; // any number of shared borrows at once
    let b = &v;
    println!("{} {}", total(a), total(b));
    add_one(&mut v); // a and b are no longer used, so this is allowed
    println!("{:?} total {}", v, total(&v));
}
$ rustc --edition 2024 borrow.rs && ./borrow
12 12
[3, 4, 5, 1] total 13

The part of the compiler that enforces this is the borrow checker. A borrow lasts from where it is created to its last use, not to the end of the block (the Book: "a reference's scope starts from where it is introduced and continues through the last time that reference is used"). That is why add_one(&mut v) is accepted above: a and b are never used again.

    2.

6. Modules, crates and visibility


    

  • A package is what cargo new makes (one Cargo.toml); it contains a library crate (src/lib.rs), and/or one or more binary crates (src/main.rs, src/bin/*.rs). A crate is the unit the compiler builds at once.
    • 

  • A module is a namespace inside a crate: mod tokenize; in lib.rs loads src/tokenize.rs. Paths use :: (crate::tokenize::count_tokens); use imports a name, like Python's from x import y.
    • 

  • Everything is private by default, visible only inside its module and its children. pub exports it; pub(crate) exports it within the crate only. Python's leading underscore is a convention; this is enforced: calling a private tokenizer::split from outside its module is E0603, "function split is private".
    •
