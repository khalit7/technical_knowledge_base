Part 1, for Python programmers: Rust in one screen

Rust is the language under much of the Python tooling you already use (uv, ruff, ty, pydantic-core, Hugging Face tokenizers, polars). This part teaches it from zero with Python as the bridge. Every program here was compiled with rustc 1.99.0 and run on this laptop (Apple M1 Pro, macOS 27); every output, compiler error and panic you see is the real one, recorded by a script (src/ra/run_all.sh).

Rust rests on one decision: every value has exactly one owner, and the compiler proves, before the program runs, that nothing uses a value after its owner has freed it or while someone else is changing it. Python gets safety from reference counting and a garbage collector at run time; C++ trusts you. Rust checks a set of rules at compile time and then runs with no collector at all. 1. Cargo: the one tool

Rust is compiled: rustc, the compiler, turns source files into a machine-code program before anything runs. You rarely call it yourself. Cargo is the build tool and package manager: it creates projects, downloads dependencies, calls rustc, runs tests and lints. A package of Rust code is a crate; the public registry is crates.io. Toolchains are installed and updated by rustup (here the stable 1.99.0 of 2026-10-01; a new stable ships every six weeks, RELEASES.md).

Dependencies, versions, lock file

  • Cargo.toml lists dependencies with version requirements; Cargo.lock pins the exact versions resolved, like uv.lock. Commit it.
  • serde = "1.0" means "compatible with 1.0": any 1.x. For 0.x versions the minor number is the breaking one: "0.14" accepts 0.14.9 but not 0.15.0 (Cargo book, SemVer compatibility). Much of the ecosystem is at 0.x, so this matters.
  • Two incompatible versions of one crate can both end up in your program (say rand 0.8 and 0.9). That avoids dependency deadlock, at the cost of a confusing error: two types with the same name that are not the same type.
  • Features are optional parts of a crate switched on at compile time: serde = { version = "1", features = ["derive"] }. They are unified: if any crate in the build turns one on, everyone gets it.
  • Build scripts (build.rs) and procedural macros run code at build time, the same trust question as a Python package's setup code. cargo audit checks the lock file against the RustSec advisory database.

2. Variables, mutability, shadowing

vars.rs
fn main() {
    let x = 5; // immutable by default
    let mut y = 5; // `mut` makes it changeable
    y += 1;
    let spaces = "   "; // shadowing: a new variable with the same name...
    let spaces = spaces.len(); // ...may even have a different type
    const MAX_TOKENS: u32 = 4_096; // a compile-time constant, type required
    println!("x={x} y={y} spaces={spaces} max={MAX_TOKENS}");
    let z; // declared now, assigned once later
    if y > 5 { z = "big" } else { z = "small" }
    println!("z={z}");
}
$ rustc --edition 2024 vars.rs && ./vars

  • Shadowing: a second let spaces makes a new variable that hides the old one, even with a new type. Useful for "parse this string into a number and keep the name"; it is not mutation.

4. Ownership and moves

First, where values live. Each function call gets a stack frame, a block of memory for its local variables, released automatically when the function returns. Data whose size is only known at run time (a growing vector, a string read from a file) goes on the heap, which someone must release explicitly. A Rust String or Vec is a small fixed-size header on the stack (three machine words: a pointer to the heap buffer, the capacity, the length; 24 bytes) plus a buffer on the heap. Python hides all of this: every object is on the heap and names are references to it.

The ownership rules (Rust Book 4.1): each value has one owner (a variable, a field, a vector slot); when the owner goes out of scope the value is dropped (its heap memory freed); assigning or passing a value moves ownership.

move.rs
fn shout(s: String) -> String {
    // takes ownership of s; returns ownership of a new String
    s.to_uppercase()
}

fn main() {
    let a = String::from("hello");
    let b = a; // move: b now owns the heap buffer
    println!("b = {b}");
    let c = b.clone(); // explicit deep copy: a second heap buffer
    let d = shout(b); // b moves into the function
    println!("c = {c}, d = {d}");
    let n = 5; // i32 is Copy: assignment copies the bits
    let m = n;
    println!("n = {n}, m = {m}"); // both still usable
}
$ rustc --edition 2024 move.rs && ./move

The Python bridge
In Python, b = a makes two names for one object, kept alive by a reference count. Rust refuses the second name, so it never needs a count: the single owner frees the buffer at a point the compiler knows. Think of a move as handing over the only key.
  • Copy types (integers, floats, bool, char, and tuples or arrays of them) have no heap part, so assignment copies the bits and both stay usable (n and m above).
  • clone() is the explicit deep copy: a second heap buffer. It is visible in the code on purpose, so you can see every place that copies data.
  • Passing to a function moves too (shout(b)); returning moves ownership back out.

Drop: cleanup at a known moment

A type can run code when it is dropped by implementing the Drop trait, which is how files close, locks release and buffers free themselves. There is no garbage collector, so the order is fixed:

drop.rs
struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

fn consume(n: Noisy) {
    println!("consume got {}", n.0);
} // n is dropped here, at the end of the function that owns it

fn main() {
    let _a = Noisy("a");
    let b = Noisy("b");
    {
        let _c = Noisy("c");
        println!("inner scope ends");
    } // c dropped here
    consume(b); // b moved into consume; dropped inside it
    let _d = Noisy("d");
    println!("main ends");
} // locals dropped in reverse order of declaration: d, then a

5. Borrowing: many readers or one writer

Moving everything everywhere would be unbearable, so you lend a value instead: a reference &v borrows it without taking ownership. Two kinds:

  • &T, a shared reference: read only; any number at once.
  • &mut T, an exclusive (mutable) reference: may change the value; while it is in use, no other reference to that value may be.
borrow.rs
fn total(v: &[u64]) -> u64 {
    // borrows: reads, does not own
    v.iter().sum()
}

fn add_one(v: &mut Vec<u64>) {
    // borrows exclusively: may change it
    v.push(1);
}

fn main() {
    let mut v = vec![3, 4, 5];
    let a = &v; // any number of shared borrows at once
    let b = &v;
    println!("{} {}", total(a), total(b));
    add_one(&mut v); // a and b are no longer used, so this is allowed
    println!("{:?} total {}", v, total(&v));
}
$ rustc --edition 2024 borrow.rs && ./borrow
12 12
[3, 4, 5, 1] total 13

The part of the compiler that enforces this is the borrow checker. A borrow lasts from where it is created to its last use, not to the end of the block (the Book: "a reference's scope starts from where it is introduced and continues through the last time that reference is used"). That is why add_one(&mut v) is accepted above: a and b are never used again.

8. Structs, enums and match: make illegal states unrepresentable


A struct is a record with named fields, like a dataclass. 9. Option, Result and ?: errors as values


Rust has no None that can appear anywhere and no exceptions for expected failures. Two enums from the standard library carry them, written like any other enum:


    

  • Option<T> is Some(value) or None: maybe missing. dict.get, str.find and "first element" return one.
    • 

  • Result<T, E> is Ok(value) or Err(error): may fail. Parsing, I/O and network calls return one.
    • 



You cannot use the value inside without deciding what happens in the other case. The ? operator is the common decision: "if this is an Err, return it from my function now; otherwise give me the value". It is the explicit, typed version of letting an exception propagate.

// A library-style typed error (thiserror) under an application-style error (anyhow).
use anyhow::{Context, Result};
use thiserror::Error;

#[derive(Debug, Error)]
enum ParseError {
    #[error("line {line}: missing field {field}")]
    MissingField { line: usize, field: &'static str },
    #[error("line {line}: bad token count")]
    BadCount { line: usize, #[source] source: std::num::ParseIntError },
}

// typed: callers can match on the variant
fn parse_line(line: usize, s: &str) -> Result<(String, u64), ParseError> {
    let mut it = s.split(',');
    let user = it.next().filter(|u| !u.is_empty()).ok_or(ParseError::MissingField { line, field: "user" })?;
    let n = it.next().ok_or(ParseError::MissingField { line, field: "tokens" })?;
    let n = n.trim().parse().map_err(|source| ParseError::BadCount { line, source })?;
    Ok((user.to_string(), n))
}

// application: any error, plus context explaining what we were doing
fn load(path: &str) -> Result<u64> {
    let text = std::fs::read_to_string(path).with_context(|| format!("reading {path}"))?;
    let mut total = 0;
    for (i, l) in text.lines().enumerate() {
        let (_, n) = parse_line(i + 1, l).context("parsing usage file")?;
        total += n;
    }
    Ok(total)
}

fn main() {
    std::fs::write("good.csv", "ada,10\nbob,32\n").unwrap();
    std::fs::write("bad.csv", "ada,10\nbob,thirty\n").unwrap();
    for p in ["good.csv", "bad.csv", "nope.csv"] {
        match load(p) {
            Ok(t) => println!("{p}: total {t}"),
            Err(e) => println!("{p}: error: {e:#}"), // {:#} prints the whole chain
        }
    }
    match parse_line(7, ",5") {
        Err(ParseError::MissingField { field, .. }) => println!("caller matched: missing {field}"),
        other => println!("{other:?}"),
    }
}

A trait may have default methods written in terms of the others. A generic function takes a type parameter with a bound: fn total<T: Tokenizer> accepts any T that implements Tokenizer.

use std::fmt::Display;

// A trait: a named set of methods a type promises to have (like a Protocol).
trait Tokenizer {
    fn name(&self) -> String;
    fn count(&self, text: &str) -> usize;
    // a default method, written once in terms of the others
    fn report(&self, text: &str) -> String {
        format!("{} -> {} tokens", self.name(), self.count(text))
    }
}

struct Whitespace;
struct Chars { per_token: usize }

impl Tokenizer for Whitespace {
    fn name(&self) -> String { "whitespace".into() }
    fn count(&self, text: &str) -> usize { text.split_whitespace().count() }
}

impl Tokenizer for Chars {
    fn name(&self) -> String { format!("chars/{}", self.per_token) }
    fn count(&self, text: &str) -> usize { text.chars().count().div_ceil(self.per_token) }
}

// Generic: one copy of this function is compiled per concrete T (monomorphisation).
fn total<T: Tokenizer>(t: &T, docs: &[&str]) -> usize {
    docs.iter().map(|d| t.count(d)).sum()
}

// Trait object: one compiled copy; the call goes through a table of function pointers.
fn total_dyn(t: &dyn Tokenizer, docs: &[&str]) -> usize {
    docs.iter().map(|d| t.count(d)).sum()
}

// impl Trait in argument position is shorthand for a generic
fn show_all(items: &[impl Display]) -> String {
    items.iter().map(|x| x.to_string()).collect::<Vec<_>>().join(", ")
}

fn main() {
    let docs = ["the cat sat", "on the mat today"];
    println!("{}", Whitespace.report(docs[0]));
    println!("{}", Chars { per_token: 4 }.report(docs[0]));
    println!("generic: {} {}", total(&Whitespace, &docs), total(&Chars { per_token: 4 }, &docs));
    let toks: Vec<Box<dyn Tokenizer>> = vec![Box::new(Whitespace), Box::new(Chars { per_token: 3 })];
    for t in &toks {
        println!("dyn: {} = {}", t.name(), total_dyn(t.as_ref(), &docs));
    }
    println!("{}", show_all(&[1.5, 2.25]));
    println!("size_of &Whitespace = {}, &dyn Tokenizer = {}",
        std::mem::size_of::<&Whitespace>(), std::mem::size_of::<&dyn Tokenizer>());
}

11. Iterators and closures: lazy pipelines that cost nothing


An iterator in Rust is any type with a next() method returning Option<Item>, the same protocol as Python's __next__ raising StopIteration. Adapters such as map, filter, zip, enumerate, take build a lazy pipeline, like a generator expression; a consumer (collect, sum, count, fold, a for loop) runs it. A closure is an anonymous function that can capture variables from where it is written: |x| x * 2 is Python's lambda x: x * 2, but with any number of statements.


iters.rs
fn main() {
    let words = ["Rust", "is", "fast", "and", "safe", "and", "fun"];
    // An iterator chain: lazy until something consumes it (collect, sum, for).
    let long: Vec<String> = words.iter()
        .filter(|w| w.len() > 2)
        .map(|w| w.to_lowercase())
        .collect();
    println!("{long:?}");
    // Laziness, visible: nothing is printed until next() is called.
    let mut it = (1..=3).map(|x| { println!("  computing {x}"); x * 10 });
    println!("built the iterator");
    println!("first = {:?}", it.next());
    // Python's enumerate, zip, sum, any, max_by_key all exist
    for (i, w) in words.iter().enumerate().skip(5) { println!("{i} {w}"); }
    let lens: usize = words.iter().map(|w| w.len()).sum();
    let pairs: Vec<(char, usize)> = "abc".chars().zip(1..).collect();
    println!("lens {lens}, pairs {pairs:?}, any 'fun' {}", words.contains(&"fun"));
    println!("longest {:?}", words.iter().max_by_key(|w| w.len()));
    let (even, odd): (Vec<u32>, Vec<u32>) = (1..=6).partition(|n| n % 2 == 0);
    println!("even {even:?} odd {odd:?}");
    // Closures capture their environment: by reference, by mutable reference, or by value
    let limit = 4;
    let short = |w: &str| w.len() < limit; // borrows limit (Fn)
    let mut seen = 0;
    let mut count = |_w: &str| seen += 1; // mutably borrows seen (FnMut)
    for w in words { count(w); }
    let name = String::from("owner");
    let consume = move || name.len(); // moves name into the closure
    println!("short {}, seen {seen}, consume() {}", words.iter().filter(|w| short(w)).count(), consume());

    struct Countdown(u32);
    impl Iterator for Countdown {
        type Item = u32;
        fn next(&mut self) -> Option<u32> {
            if self.0 == 0 { None } else { self.0 -= 1; Some(self.0 + 1) }
        }
    }
    println!("{:?}", Countdown(3).collect::<Vec<_>>());

use std::collections::{BTreeMap, HashMap, HashSet, VecDeque};

fn main() {
    // Vec: a growable array. Capacity grows by doubling, so push is cheap on average.
    let mut v = Vec::new();
    let mut caps = vec![];
    for i in 0..20 { v.push(i); if caps.last() != Some(&v.capacity()) { caps.push(v.capacity()); } }
    println!("Vec capacities seen while pushing 20 items: {caps:?}");
    println!("v.get(99) = {:?}  (v[99] would panic)", v.get(99));

    // HashMap: the entry API does "get or insert" with one lookup
    let text = "the cat and the hat and the bat";
    let mut counts: HashMap<&str, u32> = HashMap::new();
    for w in text.split(' ') { *counts.entry(w).or_insert(0) += 1; }
    println!("HashMap iteration order: {:?}", counts.iter().collect::<Vec<_>>());
    let mut sorted: Vec<(&str, u32)> = counts.into_iter().collect();
    sorted.sort_by(|a, b| b.1.cmp(&a.1).then(a.0.cmp(b.0))); // count desc, then word asc
    println!("sorted: {sorted:?}");

    // BTreeMap: kept sorted by key, so iteration order is deterministic
    let bt: BTreeMap<&str, u32> = text.split(' ').map(|w| (w, w.len() as u32)).collect();
    println!("BTreeMap: {bt:?}");
    println!("range \"b\"..\"d\": {:?}", bt.range("b".."d").collect::<Vec<_>>());

    // HashSet: membership and set algebra
    let a: HashSet<u32> = [1, 2, 3, 4].into();
    let b: HashSet<u32> = [3, 4, 5].into();
    let mut inter: Vec<_> = a.intersection(&b).copied().collect();
    inter.sort();
    println!("intersection {inter:?}, contains 5? {}", a.contains(&5));

    // VecDeque: a ring buffer, O(1) at both ends (Python's collections.deque)
    let mut q: VecDeque<u32> = VecDeque::new();
    q.push_back(1); q.push_back(2); q.push_front(0);
    let front = q.pop_front();
    println!("deque after pop_front: {q:?}, popped {front:?}");

use std::cell::{Cell, RefCell};
use std::rc::{Rc, Weak};

// Box: put a value on the heap. Needed for recursive types, whose size would otherwise be infinite.
#[derive(Debug)]
enum Expr {
    Num(f64),
    Add(Box<Expr>, Box<Expr>),
    Mul(Box<Expr>, Box<Expr>),
}

fn eval(e: &Expr) -> f64 {
    match e {
        Expr::Num(x) => *x,
        Expr::Add(a, b) => eval(a) + eval(b),
        Expr::Mul(a, b) => eval(a) * eval(b),
    }
}

#[derive(Debug)]
struct Doc {
    name: String,
    cache_hits: Cell<u32>, // interior mutability for a Copy value
}

fn main() {
    let e = Expr::Add(Box::new(Expr::Num(2.0)), Box::new(Expr::Mul(Box::new(Expr::Num(3.0)), Box::new(Expr::Num(4.0)))));
    println!("2 + 3 * 4 = {}", eval(&e));

    // Rc: shared ownership in one thread; the last owner to go frees the value
    let shared = Rc::new(Doc { name: "system prompt".into(), cache_hits: Cell::new(0) });
    let a = Rc::clone(&shared); // copies a pointer, bumps a counter
    {
        let b = Rc::clone(&shared);
        b.cache_hits.set(b.cache_hits.get() + 1); // mutate through a shared reference
        println!("strong_count inside = {}", Rc::strong_count(&shared));
    }
    println!("strong_count after = {}, hits = {}, name = {}", Rc::strong_count(&a), a.cache_hits.get(), a.name);

    // RefCell: borrow rules checked at run time instead of compile time
    let log = Rc::new(RefCell::new(Vec::<String>::new()));
    let writer = Rc::clone(&log);
    writer.borrow_mut().push("first".into());
    writer.borrow_mut().push("second".into());
    println!("log = {:?}", log.borrow());

    // Weak: a non-owning pointer (it does not keep the value alive); used to break cycles
    let parent = Rc::new(String::from("parent"));
    let w: Weak<String> = Rc::downgrade(&parent);
    println!("weak upgrade while alive: {}", w.upgrade().is_some());
    drop(parent);
    println!("weak upgrade after drop: {}", w.upgrade().is_some());
    println!("size_of Box<Expr> = {}, Rc<Doc> = {}, Expr = {}",
        std::mem::size_of::<Box<Expr>>(), std::mem::size_of::<Rc<Doc>>(), std::mem::size_of::<Expr>());

    // The run-time check, failing: two mutable borrows at once
    let first = log.borrow_mut();
    let second = log.borrow_mut(); // panics: already mutably borrowed
    println!("{} {}", first.len(), second.len());
}

Reference cycles leak


Reference counting cannot free a cycle, in Rust as in Python (where the cycle collector cleans up afterwards; Rust has none). Leaking memory is safe in Rust's sense, so the compiler allows it:

fn main() {
    {
        let x = node("x (cycle of Rc)");
        let y = node("y (cycle of Rc)");

        println!("weak: x strong_count = {}, weak_count = {}", Rc::strong_count(&x), Rc::weak_count(&x));

16. Threads without data races


A data race is two threads touching the same memory at the same time, at least one of them writing, with nothing ordering them. Updates get lost or values tear. In CPython the GIL used to hide most of these; free-threaded Python 3.14 does not, and an unsynchronised counter there loses updates (measured on the Python page). Rust makes data races a compile error in safe code, by applying section 5's rule across threads: shared data may be read by many threads, and changed only through a type that synchronises (a lock or an atomic).

use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::mpsc;
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // 1. spawn + join; `move` gives the thread its own copy of what it uses
    let docs = vec!["a b c", "d e", "f"];
    let handles: Vec<_> = docs.into_iter().enumerate().map(|(i, d)| {
        thread::spawn(move || (i, d.split_whitespace().count()))
    }).collect();
    let counts: Vec<_> = handles.into_iter().map(|h| h.join().unwrap()).collect();
    println!("spawned: {counts:?}");

    // 2. scoped threads may borrow local data, because they are joined before the scope ends
    let data = vec![1u64; 1_000_000];
    let (left, right) = data.split_at(data.len() / 2);
    let total = thread::scope(|s| {
        let a = s.spawn(|| left.iter().sum::<u64>());
        let b = s.spawn(|| right.iter().sum::<u64>());
        a.join().unwrap() + b.join().unwrap()
    });
    println!("scoped sum: {total}");

    // 3. shared mutable state: Arc (shared ownership across threads) + Mutex (one writer at a time)
    let counter = Arc::new(Mutex::new(0u64));
    let mut hs = vec![];
    for _ in 0..8 {
        let c = Arc::clone(&counter);
        hs.push(thread::spawn(move || for _ in 0..100_000 { *c.lock().unwrap() += 1; }));
    }
    for h in hs { h.join().unwrap(); }
    println!("mutex counter: {} (expected 800000)", *counter.lock().unwrap());

    // 4. an atomic does the same without a lock
    let hits = Arc::new(AtomicU64::new(0));
    thread::scope(|s| for _ in 0..8 { let h = &hits; s.spawn(move || for _ in 0..100_000 { h.fetch_add(1, Ordering::Relaxed); }); });
    println!("atomic counter: {}", hits.load(Ordering::Relaxed));

    // 5. channels: send values from many producers to one consumer
    let (tx, rx) = mpsc::channel();
    for id in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || tx.send(format!("worker {id} done")).unwrap());
    }
    drop(tx); // close our copy so the loop below ends when the workers finish
    let mut got: Vec<String> = rx.iter().collect();
    got.sort();
    println!("channel: {got:?}");
}

17. unsafe, in one section


Some correct code cannot be proved safe by the compiler: the inside of Vec, calls into C libraries, hardware access. Inside an unsafe block you may do five extra things, the "unsafe superpowers" (Rust Book 20.1): dereference a raw pointer; call an unsafe function; access or modify a mutable static; implement an unsafe trait; access fields of a union. Nothing else changes: "unsafe doesn't turn off the borrow checker or disable any of Rust's other safety checks".


unsafe_ok.rs

19. Common mistakes, and the habit that replaces each


Cloning until it compiles.
Each clone() of a String or Vec allocates and copies. Ask first whether the callee could borrow (&str, &[T]), whether the value could move, or whether its last use could come earlier. Clone small things freely; never in a hot loop without a reason.


Rc<RefCell<T>> everywhere to recreate Python's object graph.
It compiles and then panics at run time (section 15). Give the data one owner (often a struct holding Vecs) and refer to items by index.


&String or &Vec<T> parameters.
Take &str and &[T]: they accept more callers and are what clippy suggests (section 1).


Byte indexes on text.
s.len() is bytes and &s[0..n] panics inside a character (section 7). Use chars(), char_indices(), or a byte-level algorithm on purpose (the token counter works on bytes because tokens are ASCII).


unwrap() in library code.
Return Result and use ?; reserve expect("reason") for states you can prove impossible.


Expecting dict order from HashMap.
Its order changes between runs (section 12). Sort, or use BTreeMap, or a Vec of pairs.


Timing a debug build.
cargo run is unoptimised; measure with --release. And a release build silently wraps on overflow: use checked_* where it matters (section 3).


Lifetimes in every struct.
Store owned data first; borrow in structs only when a profile says the copies matter (section 6).


Blocking inside async code.
A long computation or a blocking file read inside an async fn stalls every task on that thread; Part 3 shows spawn_blocking.

Ownership, animated: one Vec, at its real addresses


One small program, stepped line by line. A Rust Vec is a 24-byte header on the stack (pointer, capacity, length) and a buffer on the heap. Every address and number below was printed by the program itself when it ran (Reading section 4 explains the rules). Switch to Python to see the same steps with Python's model: names pointing at one object and a reference count.
















What the run shows


    

  • Borrowing never copies. r and m are 8-byte pointers to v's stack slot (the same address the program printed for v).
    • 

  • Growth moves the buffer. push on a full vector allocated a new block (capacity 3 to 6) and freed the old one. That is exactly why the borrow checker refuses a reference into the buffer across a push (Borrow-checker lab, "Push while a reference is alive").
    • 

  • A move copies 24 bytes, not the data. w has a new stack address but the same heap address as v had; v is unusable afterwards.
    • 

  • Clone allocates. c got its own buffer; on this run the allocator handed it the block freed at step 3 (heap 0x102d3d4a0, the same as step 1). Reusing freed memory is normal, and is why a dangling pointer can read someone else's data in C++.
    • 

  • Drop frees at a known line. drop(w) released the second buffer immediately; c is freed at the closing brace of main.
    • 

  • In Python every step after the first only adds a name to one object (the count rises to 4); copy() is the only new allocation; del w removes a name, not the object.
    •

own_anim.rs
// Prints the real addresses behind the ownership animation: a Vec is three
// machine words on the stack (pointer, capacity, length) and a buffer on the heap.
fn show(step: &str, name: &str, v: &Vec<u32>) {
    println!(
        "{step} {name} stack={:p} heap={:p} len={} cap={} data={:?}",
        v as *const Vec<u32>, v.as_ptr(), v.len(), v.capacity(), v
    );
}

fn main() {
    println!("size_of::<Vec<u32>>() = {}", std::mem::size_of::<Vec<u32>>());
    let mut v: Vec<u32> = Vec::with_capacity(3);
    v.extend([10, 20, 30]);
    show("1", "v", &v);
    let r = &v; // a shared borrow: a pointer to v's stack slot
    println!("2 r points to {:p} (v's stack slot), r.len()={}", r as *const Vec<u32>, r.len());
    v.push(40); // r is no longer used, so v may be mutated: the buffer is full, so it grows
    show("3", "v", &v);
    let m = &mut v; // one exclusive borrow
    m[0] = 11;
    println!("4 m points to {:p}, wrote m[0]=11", m as *const Vec<u32>);
    let w = v; // move: the three words are copied to w's slot, the heap buffer is not touched
    show("5", "w", &w);
    let c = w.clone(); // clone: a new heap buffer with a copy of the elements
    show("6", "c", &c);
    drop(w); // w's buffer is freed now
    println!("7 dropped w");
    show("8", "c", &c);
}

1. Is it worth it? Profile first


An extension module is a compiled shared library (a .so file on macOS and Linux, .pyd on Windows) that Python loads with an ordinary import. CPython calls a function in it named PyInit_<name>, which hands back a module object whose functions are machine code. NumPy, PyTorch and orjson are all extension modules. Writing one costs a second language, a compiler in your build, and a wheel per platform (section 12), so do it only when the numbers say so.


In Python you would
reach for cProfile or py-spy, find the hot function, and try the cheap wins first: a better algorithm, a built-in (re, collections.Counter), NumPy, or an existing library. The Python page (Part 1, "Performance") walks through that order. Rust comes after those, for a hot loop that is left and that no library already does.


Here is the root program, cut into its phases and timed (medians of 5 runs; the script is code/ladder.py with --phases):




Milliseconds per phase for the whole 200,000-line log (38.8 MB). Top bar: pure Python. Second bar: the same program with only the token loop moved into Rust. The loop shrinks from  ms to  ms, and what remains is mostly json.loads.


This is Amdahl's law: if a fraction p of the time is sped up s times, the whole program speeds up 1 / ((1 - p) + p/s). In-process, the token loop was % of the pure-Python run (p = ). Even an infinitely fast loop leaves the other %, so the best this change alone can give is 1 / (1 - p) = x, and we measured x. To go further, the parsing has to move too (section 10).


Worth it when
a profile shows one hot path you own, it is not array arithmetic NumPy already does, it runs often (a tokenizer, a parser, a sampler, a graph walk), and you can pass it big batches.
Not worth it when
the time is in I/O or the network, a library already does it (orjson, polars, pyarrow), or the hot code calls back into Python objects on every step.
What it costs
A Rust toolchain in your build, about 16 s for a clean build here, wheels per platform, and a team that can read Rust.

3. Functions and modules: #[pyfunction], #[pymodule]


Step 1 of the token counter: the Rosetta token loop as plain Rust, and a thin function Python can call.


ext/src/lib.rs
/// Tokens = maximal runs of ASCII letters or digits (rule 3 of PROGRAM.md).
/// Non-ASCII characters are UTF-8 bytes >= 0x80, so a byte loop gives the char answer.
fn tokens(s: &[u8]) -> u64 {
    let mut n = 0;
    let mut inside = false;
    for &b in s {
        let t = b.is_ascii_alphanumeric();
        if t && !inside {
            n += 1;
        }
        inside = t;
    }
    n
}

4. Crossing the boundary: what each conversion costs


A Python str and a Rust String are different things in memory. A Python str is an object on Python's heap with a refcount, a length and its characters in one of three fixed widths (1, 2 or 4 bytes each, whichever fits the widest character). A Rust &str is just a pointer and a length into UTF-8 bytes (Part 1, section 7: String against &str). So every argument crosses the boundary in one of two ways:


  • Borrowed (a view): Rust gets a pointer into memory Python owns. &str from a str, &[u8] from bytes, a NumPy array view. No allocation, no copy, but the view only lives for the call.
    • 

  • Owned (a copy): Rust builds its own value. String, Vec<T>, HashMap<K, V>: one allocation per string, one conversion per element. The value can then outlive the call, move to another thread, be stored in a struct.

5. NumPy arrays without copies (rust-numpy)


A Python list of floats is an array of pointers to separate float objects, each 24 bytes with its own refcount; converting it means visiting every object. A NumPy array is one contiguous block of raw f64 values plus a small header (shape, strides, dtype). The numpy crate (rust-numpy, 0.29.0, the release matching PyO3 0.29) lets Rust read that block in place:


ext/src/lib.rs
/// Sum of squares from a Python list: every float is converted into a new Vec<f64>.
#[pyfunction]

}

6. Errors become exceptions; panics become PanicException


Rust has no exceptions: a function that can fail returns Result<T, E>, and ? returns early with the error (Part 1, section 9, covers both). PyO3 maps this onto Python: return PyResult<T>, and an Err(PyErr) is raised as an exception when the call returns. Many Rust errors convert by themselves: std::io::Error becomes the matching OSError subclass (FileNotFoundError, PermissionError), a failed UTF-8 decode becomes UnicodeDecodeError. For your own error kinds, declare a Python exception class from Rust:

7. Classes: #[pyclass] keeps Rust state between calls


Section 4's third rule said: when data goes back and forth, keep it on one side. A #[pyclass] is how: a Rust struct that Python sees as a class. The Python object owns the struct; methods run on it in place, so the per-user table never crosses the boundary until you ask for a result.


ext/src/lib.rs
/// A running per-user counter that lives across calls.
#[pyclass(module = "tokrs")]
struct Counter {
    per_user: HashMap<String, u64>,
    lines: u64,
}

#[pymethods]
impl Counter {
    #[new]
    fn new() -> Self {
        Counter { per_user: HashMap::new(), lines: 0 }
    }

    /// Add one message. `&mut self`: PyO3 checks at run time that nobody else holds it.
    fn add(&mut self, user: &str, text: &str) {
        self.lines += 1;
        *self.per_user.entry(user.to_owned()).or_insert(0) += tokens(text.as_bytes());
    }

    /// The n heaviest users, ties by id (rule 5).
    #[pyo3(signature = (n=5))]
    fn top(&self, n: usize) -> Vec<(String, u64)> {
        let mut v: Vec<(String, u64)> = self.per_user.iter().map(|(u, c)| (u.clone(), *c)).collect();
        v.sort_by(|a, b| b.1.cmp(&a.1).then_with(|| a.0.cmp(&b.0)));
        v.truncate(n);
        v
    }

    #[getter]
    fn total(&self) -> u64 {
        self.per_user.values().sum()
    }

    fn __len__(&self) -> usize {
        self.per_user.len()
    }

    fn __repr__(&self) -> String {
        format!("Counter(users={}, lines={}, tokens={})", self.per_user.len(), self.lines, self.total())
    }
}


#[new] is __init__ (strictly __new__), #[getter] makes a read-only property, and methods named like Python's special methods (__len__, __repr__) become them. &self methods read; &mut self methods write. Python has no borrow checker, so PyO3 enforces Rust's rule (many readers or one writer) at run time with a flag in each object.

8. Releasing the GIL, and parallel Rust with rayon


On the normal (GIL) build of CPython, a thread must hold the global interpreter lock to touch any Python object, and only one thread holds it at a time. While your Rust function runs, the calling thread still holds it, so four Python threads calling the same Rust function take turns, exactly like four threads running Python. But a function that only touches Rust data (bytes already borrowed, a Vec, a HashMap) does not need the interpreter. py.detach(closure) releases the GIL, runs the closure, and takes it back:


ext/src/lib.rs
/// Step 4: the same work with the GIL released. `py.detach` runs the closure
/// detached from the interpreter, so other Python threads keep running.
#[pyfunction]
fn tally_bytes_detached<'py>(py: Python<'py>, data: &[u8]) -> PyResult<Report<'py>> {
    let t = py.detach(|| tally(data, 1));
    to_python(py, t)
}

Parallelism inside one call: rayon


If the caller is single-threaded, Rust can split the work itself. rayon turns an iterator into a parallel one (.into_par_iter()) and runs it on a pool of OS threads, one per core by default; reduce merges the partial tallies:


ext/src/lib.rs
/// Pure Rust, no Python objects: safe to run without the GIL and on many threads.
fn tally(data: &[u8], first_lineno: u64) -> Tally {
    let mut t = Tally::default();
    for (i, line) in data.split_inclusive(|&b| b == b'\n').enumerate() {
        t.lines += 1;
        match serde_json::from_slice::<Message>(line) {
            Ok(m) => {
                t.ok += 1;
                *t.per_user.entry(m.user).or_insert(0) += tokens(m.text.as_bytes());
            }
            Err(_) => {
                t.bad += 1;
                if t.first_bad == 0 {
                    t.first_bad = first_lineno + i as u64;
                }
            }
        }
    }
    t
}

fn merge(mut a: Tally, b: Tally) -> Tally {
    a.lines += b.lines;
    a.ok += b.ok;
    a.bad += b.bad;
    if a.first_bad == 0 {
        a.first_bad = b.first_bad;
    }
    for (u, n) in b.per_user {
        *a.per_user.entry(u).or_insert(0) += n;
    }
    a
}


ext/src/lib.rs
/// Step 5: detached and parallel. rayon splits the chunks over its thread pool.
#[pyfunction]
#[pyo3(signature = (data, threads=8))]
fn tally_bytes_parallel<'py>(py: Python<'py>, data: &[u8], threads: usize) -> PyResult<Report<'py>> {
    let t = py.detach(|| {
        chunks(data, threads)
            .into_par_iter()
            .map(|(part, first)| tally(part, first))
            .reduce(Tally::default, merge)
    });
    to_python(py, t)
}


tally takes only &[u8] and returns plain Rust data, so it is safe to run on any thread; the compiler checks that too (rayon requires Send). The split itself (chunks, in lib.rs) cuts at newlines and remembers each chunk's first line number so "first malformed line" stays exact; the pytest suite (section 11) checks the parallel result equals the serial one for 1, 2, 3, 8 and 64 chunks.


Detach when
the Rust work is long-running and touches no Python objects. Do it on free-threaded Python too: there, a thread that stays attached through long work can stall the interpreter's stop-the-world pauses (garbage collection, sys.settrace, fork) for every other thread (PyO3 free-threading guide).
Mistakes
Detaching around a tiny function (all overhead, no gain); initialising a std::sync::OnceLock or LazyLock with code that calls Python, which can deadlock against the GIL (PyO3's FAQ: use PyOnceLock); starting a rayon pool in a process that already runs one worker per core (oversubscription).

/// The thread-safe version: `frozen` means no `&mut self` ever, so PyO3 needs no
/// run-time borrow flag; the mutable state sits behind a Mutex that threads queue on.
#[pyclass(module = "tokrs", frozen)]
struct SharedCounter {
    per_user: std::sync::Mutex<HashMap<String, u64>>,
}

#[pymethods]
impl SharedCounter {
    #[new]
    fn new() -> Self {
        SharedCounter { per_user: std::sync::Mutex::new(HashMap::new()) }
    }

    fn add(&self, user: &str, text: &str) {
        let n = tokens(text.as_bytes()); // count outside the lock
        *self.per_user.lock().unwrap().entry(user.to_owned()).or_insert(0) += n;
    }

    #[getter]
    fn total(&self) -> u64 {
        self.per_user.lock().unwrap().values().sum()
    }
}


The token counting happens before lock(), so threads only queue for the short dictionary update. The generated job uploads with a long-lived PYPI_API_TOKEN secret. 15. Common mistakes


Timing a debug build
maturin develop without --release builds without optimisation. Always benchmark release builds.


One call per element
Each crossing costs about as much as counting a 125-character message (section 4). Pass the list, return a list or an array.


Porting one function inside a Python hot path
The rest of the path still runs in Python (section 1). Move the whole path, or measure what is left first.


Owned types everywhere
Vec<String>, HashMap and Vec<f64> copy; use &str, &[u8], &Bound<PyList>, NumPy views unless Rust must keep the data.


Holding the GIL through long Rust work
Other Python threads stop (section 8). Wrap pure-Rust work in py.detach.


A &mut self class shared between threads
Works on the GIL build, raises Already borrowed on 3.14t (section 9). Use frozen plus a Mutex or atomics, and run tests on 3.14t.


Catching PanicException with except Exception
It derives from BaseException. A panic is a bug: return PyResult instead.


Forgetting to restart Python after a rebuild
A process cannot unload a shared library it has loaded, so importlib.reload will not pick up the new build. Restart the interpreter or notebook kernel.


Module name mismatch
The #[pymodule] name, the library name in Cargo.toml and module-name in pyproject.toml must agree, or import fails because CPython cannot find PyInit_<name>.


Rewriting NumPy
A plain Rust loop lost to np.dot by x (section 5).


Shipping only an abi3 wheel
Free-threaded users cannot install it (section 12): add cp314t wheels, or abi3t once you can require 3.15.


No stub file
Type checkers then know nothing about your module (section 11).

/// so pipes and logs stay clean.
fn feed(tally: &mut Tally, mut r: impl BufRead, name: &str) -> Result<()> {
    let show = io::stderr().is_terminal();
    let mut line = String::new();
    loop {
        line.clear();
        let n = r.read_line(&mut line).with_context(|| format!("reading {name}"))?;
        if n == 0 {
            break;
        }
        tally.add_line(line.trim_end_matches(['\n', '\r']));
        if show && tally.lines % 100_000 == 0 {
            eprint!("\r{name}: {} lines", tally.lines);
        }
    }
    if show && tally.lines >= 100_000 {
        eprintln!();
    }
    Ok(())
}

Async Rust from zero


The problem it solves. A service spends most of its time waiting: for the network, a database, a model API. One OS thread per waiting request works up to a few thousand requests, then the memory for stacks and the cost of switching threads dominate. Async lets one thread juggle many waiting operations: each operation runs until it would wait, hands the thread back, and is resumed when its data arrives. Python's asyncio and JavaScript's event loop are the same idea; the Python page's Part 1 teaches asyncio from the event loop up (Python page, tab "Event loop"). Rust's version differs in three ways, each shown below with real runs: futures are lazy, the runtime is a library you choose (and usually runs on several threads), and cancellation is dropping.


1. A future is a value, and it is lazy


An async fn does not run when you call it. It returns a future: a value that describes the work, which runs only when something polls it, normally .await.

// A future is a value: calling an async fn runs nothing until something awaits (polls) it.
async fn hello(tag: &str) -> u32 {
    println!("   {tag}: body runs");
    42
}

    println!("3. awaited it: {v}");
    hello("b"); // never awaited: the compiler warns and the body never runs
    println!("4. end of main");
}

2. What .await does: poll, Pending, wake


Every future implements one method, poll. The runtime calls it; it returns Poll::Ready(value) if done, or Poll::Pending if it has to wait, after arranging for a waker to be called when it can make progress (a socket becomes readable, a timer fires). The runtime then polls something else, and polls this future again only after its waker fires. That is the whole protocol. A hand-written future, to see it:


tok/examples/a1_poll.rs
// What .await does underneath: the runtime calls poll() until it returns Ready.
// A hand-written future that is not ready the first two times it is polled.
use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

struct Countdown {
    left: u32,
}

impl Future for Countdown {
    type Output = &'static str;
    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output> {
        if self.left == 0 {
            println!("   poll: Ready");
            return Poll::Ready("done");
        }
        println!("   poll: Pending ({} left), asking to be woken", self.left);
        self.left -= 1;
        // A real future (a socket, a timer) hands the waker to the OS event source.
        // Here we wake ourselves at once, so the runtime polls again.
        cx.waker().wake_by_ref();
        Poll::Pending
    }
}

#[tokio::main(flavor = "current_thread")]
async fn main() {
    println!("awaiting Countdown {{ left: 2 }}");
    let r = Countdown { left: 2 }.await;
    println!("result: {r}");
}


awaiting Countdown { left: 2 }
   poll: Pending (2 left), asking to be woken
   poll: Pending (1 left), asking to be woken
   poll: Ready
result: done


You will almost never write poll yourself; async fn generates it, with one state per .await point. Two consequences matter every day: code between two awaits runs without interruption (no other task can run on that thread meanwhile), and a future that is never polled again simply stops at its last await.


Pin, in one paragraph. The generated state machine can hold a reference to one of its own local variables across an await (a buffer and a slice of it). If the future were moved in memory, that reference would dangle. poll therefore takes Pin<&mut Self>: a pointer that promises the future will not move again once polled. .await, tokio::spawn and Box::pin handle it for you; you meet Pin when storing futures in structs or writing poll by hand (std::pin docs).


3. The runtime is a library: tokio

4. Concurrency: join, spawn, JoinSet, Semaphore


tokio::join!(a, b, c) polls several futures inside the current task and finishes when all are done: concurrency without new tasks. tokio::spawn(fut) hands a future to the runtime as an independent task (Python's create_task) that may run on any worker thread, in parallel with others; it returns a JoinHandle to await the result. A JoinSet owns a group of tasks (like asyncio.TaskGroup) and aborts them all if it is dropped. The Python page's fan-out benchmark, rewritten: 20 calls to a local server that answers after 100 ms (this part's own service, standing in for a model API).

5. Timeouts, select!, cancellation


Cancelling a future in Rust means dropping it: it is never polled again, so the code after its pending .await never runs, and its local variables are dropped (their Drop code runs). timeout and select! are both built on that.

struct Guard(&'static str);
impl Drop for Guard {
    fn drop(&mut self) {
        println!("   drop: {} cleaned up", self.0);

}

6. Blocking the runtime: the mistake async makes easy


A worker thread can poll only one task at a time, and it gets the thread back only at an .await. A task that calls a blocking function (std::thread::sleep, a synchronous file read, a CPU-heavy loop) holds its worker the whole time, and every other task queued on that worker waits. Alice Ryhl (a tokio maintainer) gives the rule of thumb: "no more than 10 to 100 microseconds between each .await" (Async: What is blocking?). The same three jobs as the Python page (A, B and C wait 100, 200 and 300 ms), five ways:

async fn job(name: &str, ms: u64) -> String {
    ev(name, "start", "");
    ev(name, "await", &format!("sleep({ms} ms).await"));
    tokio::time::sleep(Duration::from_millis(ms)).await; // yields to the runtime
    ev(name, "resume", "");
    ev(name, "done", "");

}

    ev(name, "start", "");

Shared state


Every request runs as its own task, maybe on another thread, so shared state goes behind an Arc (a thread-safe shared pointer; Part 1, Reading) and anything mutable inside it must be thread-safe: here, two atomic counters. with_state(state) gives each handler a cheap clone of the Arc. When an orchestrator stops a container it sends SIGTERM, waits a grace period, then sends SIGKILL: 10 s by default for docker stop (docs), 30 s by default on Kubernetes (pod lifecycle). /// Resolves on Ctrl-C or SIGTERM (what `docker stop` and Kubernetes send).
/// After it resolves, axum stops accepting and waits for in-flight requests to finish.
async fn shutdown_signal() {
    let ctrl_c = async { tokio::signal::ctrl_c().await.expect("ctrl-c handler") };
    #[cfg(unix)]
    let term = async {
        tokio::signal::unix::signal(tokio::signal::unix::SignalKind::terminate())
            .expect("SIGTERM handler")
            .recv()
            .await;
    };
    #[cfg(not(unix))]
    let term = std::future::pending::<()>();
    tokio::select! {
        _ = ctrl_c => info!("Ctrl-C received, draining"),
        _ = term => info!("SIGTERM received, draining"),
    }
}

Deployment: a container image


A container image is a file system plus a start command. A Python service image needs an interpreter and its packages; a Rust service image needs the binary and, at most, a C library. The standard recipe is a multi-stage build: compile in a full Rust image, then copy only the binary into a minimal one.

Common mistakes


Blocking inside async code
std::thread::sleep, std::fs, a synchronous HTTP client or a long CPU loop inside an async fn stalls its worker and every task queued on it. It hides on a multi-threaded runtime until load arrives (the 300 ms line in the trace above). Use the async API, spawn_blocking, or rayon.


Forgetting that futures are lazy
Calling an async fn without .await (or spawning it) does nothing. The compiler warns ("futures do nothing unless you .await or poll them"); do not silence the warning.


Holding a lock or a non-Send value across .await
A std::sync::MutexGuard or an Rc alive at an await makes the future non-Send, and tokio::spawn refuses it. Scope the guard so it drops before the await; use Arc; reach for tokio::sync::Mutex only when the lock must be held across an await.


Assuming a dropped JoinHandle cancels the task
It detaches it; the task keeps running. Use abort(), or a JoinSet, which aborts its tasks when dropped.


Code that is not cancel safe inside select!
The losing branch is dropped mid-way. If it had read half a message or popped an item, that work is lost. Keep buffers outside the future or use methods documented as cancel safe.


println! in a CLI that may be piped
A closed pipe makes println! panic (exit 101). Write through a locked stdout and treat BrokenPipe as success.


Progress and logs on stdout
They corrupt the output for the next program in the pipe. stdout is for results; stderr for everything else; progress only when is_terminal().


Measuring a debug build
cargo run builds without optimisation. Benchmark and ship --release.


Two body limits
axum's extractors reject bodies over 2 MB regardless of your tower limit. Decide on one limit (DefaultBodyLimit) and test the 413 path.


Dying on SIGTERM
Without graceful shutdown every deploy drops in-flight requests. Wire with_graceful_shutdown to SIGTERM and Ctrl-C.


Comparing frameworks on a hello-world endpoint
Requests per second on /health say little about a service whose time goes to a database or a model. Measure your real handler, open-loop, with the latency percentiles you care about.
