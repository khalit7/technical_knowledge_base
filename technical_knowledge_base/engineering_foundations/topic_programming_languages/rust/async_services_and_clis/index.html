The idea in one sentence. A Rust future is a lazy state machine that runs only when a runtime polls it and gives its thread back only at an .await; tokio polls such tasks on a few worker threads, axum makes every request one of them, and the whole service or command-line tool ships as one compiled file.

Three ideas to keep. (1) A Rust tool or service is one compiled file: that is most of why people write them. (2) Async Rust is lazy and cooperative: CPU work between awaits blocks every other request on that thread (measured below: /health p50 went from 0.44 ms to 10.7 ms). (3) The type system follows you into concurrency: tokio::spawn demands Send + 'static, so data races and dangling borrows across tasks are compile errors, not incidents.

Async Rust from zero

A service spends most of its time waiting (network, database, model API). One OS thread per waiting request works up to a few thousand requests, then stack memory and thread switches dominate. Async lets one thread juggle many waiting operations: each runs until it would wait, hands the thread back, and is resumed when its data arrives. That is asyncio's idea too; Rust differs in three ways, each shown with a real run: futures are lazy, the runtime is a library you choose (usually on several threads), and cancellation is dropping.

1. A future is a value, and it is lazy

An async fn does not run when you call it. It returns a future that runs only when something polls it, normally .await. The program builds hello("a") and awaits it, and builds hello("b") and drops it:

The code (examples/a1_lazy.rs)

    println!("   {tag}: body runs");
    42

    println!("3. awaited it: {v}");
    hello("b"); // never awaited: the compiler warns and the body never runs
    println!("4. end of main");
}

2. What .await does: poll, Pending, wake

Every future implements one method, poll. The runtime calls it; it returns Poll::Ready(value) if done, or Poll::Pending after arranging for a waker to be called when it can make progress (a socket becomes readable, a timer fires). The runtime polls something else meanwhile and polls this future again only after its waker fires. A hand-written future that is ready on its third poll:

   poll: Pending (2 left), asking to be woken
   poll: Pending (1 left), asking to be woken
   poll: Ready
result: done
The hand-written future, and Pin in one paragraph
tok/examples/a1_poll.rs
// What .await does underneath: the runtime calls poll() until it returns Ready.
// A hand-written future that is not ready the first two times it is polled.
use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

struct Countdown {
    left: u32,
}

impl Future for Countdown {
    type Output = &'static str;
    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output> {
        if self.left == 0 {
            println!("   poll: Ready");
            return Poll::Ready("done");
        }
        println!("   poll: Pending ({} left), asking to be woken", self.left);
        self.left -= 1;
        // A real future (a socket, a timer) hands the waker to the OS event source.
        // Here we wake ourselves at once, so the runtime polls again.
        cx.waker().wake_by_ref();
        Poll::Pending
    }
}

#[tokio::main(flavor = "current_thread")]
async fn main() {
    println!("awaiting Countdown {{ left: 2 }}");
    let r = Countdown { left: 2 }.await;
    println!("result: {r}");
}

Pin. The generated state machine can hold a reference to one of its own locals across an await (a buffer and a slice of it). If the future were moved in memory, that reference would dangle. poll therefore takes Pin<&mut Self>: a pointer that promises the future will not move again once polled. .await, tokio::spawn and Box::pin handle it for you; you meet Pin when storing futures in structs or writing poll by hand (std::pin docs).

You will almost never write poll; async fn generates it, with one state per .await point. Two consequences matter every day: code between two awaits runs without interruption (no other task runs on that thread meanwhile), and a future that is never polled again simply stops at its last await.

4. Concurrency: join, spawn, JoinSet, Semaphore

tokio::join!(a, b, c) polls several futures inside the current task: concurrency without new tasks. tokio::spawn(fut) hands a future to the runtime as an independent task (Python's create_task) that may run on any worker thread, in parallel with others, and returns a JoinHandle. A JoinSet owns a group of tasks (like asyncio.TaskGroup) and aborts them all if dropped. 20 sequential calls cost 20 × 100 ms; concurrent ones cost one round trip; a semaphore with 5 permits gives 4 waves of 100 ms, the polite way to call a rate-limited model API. asyncio gives the same numbers on the same machine (the Python page's fan-out): for waiting, the language does not matter, the overlap does. Rust differs where work is done between the waits: a multi-threaded runtime uses all cores, which one asyncio loop cannot.

5. Timeouts, select!, cancellation

Cancelling a future in Rust means dropping it: it is never polled again, so the code after its pending .await never runs, and its locals are dropped (their Drop code runs). timeout and select! are both built on that. Four cases, with a guard that prints when it is dropped:

The code (examples/a3_cancel.rs)
tok/examples/a3_cancel.rs (lines 6 to 46)
/// Prints when it is dropped, to show exactly when a future is cancelled.
struct Guard(&'static str);
impl Drop for Guard {
    fn drop(&mut self) {
        println!("   drop: {} cleaned up", self.0);
    }
}

async fn step(name: &'static str, ms: u64) -> &'static str {
    let _g = Guard(name);
    println!("   {name}: started, waiting {ms} ms");
    sleep(Duration::from_millis(ms)).await;
    println!("   {name}: finished"); // never printed if the future is dropped first
    name
}

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let t = Instant::now();
    println!("1. timeout(250 ms) around a 2000 ms call");
    let r = timeout(Duration::from_millis(250), step("slow", 2000)).await;
    println!("   -> {r:?} after {} ms", t.elapsed().as_millis());

    println!("2. select!: first to finish wins, the other is dropped");
    let t = Instant::now();
    tokio::select! {
        w = step("fast", 100) => println!("   -> winner {w} after {} ms", t.elapsed().as_millis()),
        w = step("lazy", 300) => println!("   -> winner {w}"),
    }

    println!("3. a spawned task keeps running on its own; abort() cancels it");
    let h = tokio::spawn(step("background", 1000));
    sleep(Duration::from_millis(50)).await;
    h.abort();
    println!("   -> join: {:?}", h.await.map_err(|e| e.is_cancelled()));

    println!("4. dropping a JoinHandle does NOT cancel the task (it is detached)");
    drop(tokio::spawn(step("detached", 100)));
    sleep(Duration::from_millis(150)).await;
    println!("   -> main done");
}

What this means in practice. Python cancels by raising CancelledError at the await, so cleanup goes in finally; Rust has no exception to catch, so cleanup goes in Drop (a guard). A future that has done half its work when dropped (read part of a message, taken an item off a queue) loses that half: cancel safety. tokio documents which of its methods are cancel safe; inside select! loops, use those, or keep state outside the future.

Blocking the runtime: the mistake async makes easy

A worker thread polls one task at a time and gets the thread back only at an .await. A task that calls a blocking function (std::thread::sleep, a synchronous file read, a CPU-heavy loop) holds its worker the whole time, and every other task queued on that worker waits. Alice Ryhl (a tokio maintainer) gives the rule of thumb: "no more than 10 to 100 microseconds between each .await" (Async: What is blocking?).     ev(name, "start", "");
    ev(name, "await", &format!("sleep({ms} ms).await"));

    ev(name, "start", "");

/// POST /count {"text": "..."} -> {"tokens": n}
async fn count(State(st): State<Arc<AppState>>, Json(req): Json<CountReq>) -> Result<Json<CountResp>, AppError> {
    st.requests.fetch_add(1, Ordering::Relaxed);
    if req.text.is_empty() {
        return Err(AppError::Empty);
    }
    let tokens = count_tokens(&req.text);
    st.tokens_counted.fetch_add(tokens, Ordering::Relaxed);
    Ok(Json(CountResp { tokens }))
}

/// Errors a handler can return. IntoResponse turns each into a status code and a JSON body.

pub enum AppError {
    #[error("body is not valid UTF-8")]
    NotUtf8,
    #[error("text is empty")]
    Empty,
    #[error("worker failed: {0}")]
    Join(#[from] tokio::task::JoinError),
}

impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        let status = match self {
            AppError::NotUtf8 | AppError::Empty => StatusCode::BAD_REQUEST,
            AppError::Join(_) => StatusCode::INTERNAL_SERVER_ERROR,
        };
        (status, Json(serde_json::json!({ "error": self.to_string() }))).into_response()
    }
}

Shared state and CPU work

Every request is its own task, maybe on another thread, so shared state goes behind an Arc and anything mutable inside it must be thread-safe: here, two atomic counters. For a mutable map use a Mutex (held briefly, never across an await) or a concurrent map; a database pool is already shareable. Python's equivalent, a module-level dict, is per worker process under uvicorn --workers 4, so /stats on the FastAPI twin reports only the worker that answered; tokserve's counters are process-wide because its workers are threads (/stats after the requests on this page: {"requests":3,"tokens_counted":44703}).

Counting a 391 KB log is about a millisecond of CPU, a 3.9 MB one about ten times that: both far above the 10 to 100 µs budget between awaits, so the handler moves it to the blocking pool (the inline mode exists only for Experiment B above). The double ??: the first unwraps the JoinError (did the background job panic?), the second the counting's own Result.

/// POST /count_log with a JSONL body -> the root program's report as JSON.
/// Counting a large body is CPU work: with offload on it runs on the blocking pool.
async fn count_log(State(st): State<Arc<AppState>>, body: axum::body::Bytes) -> Result<Json<crate::Report>, AppError> {
    st.requests.fetch_add(1, Ordering::Relaxed);
    let work = move || -> Result<crate::Report, AppError> {
        let text = std::str::from_utf8(&body).map_err(|_| AppError::NotUtf8)?;
        let mut t = Tally::default();
        t.add_text(text);
        Ok(t.report(5))
    };
    let report = if st.cfg.offload { tokio::task::spawn_blocking(work).await?? } else { work()? };
    st.tokens_counted.fetch_add(report.tokens, Ordering::Relaxed);
    Ok(Json(report))
}

/// Resolves on Ctrl-C or SIGTERM (what `docker stop` and Kubernetes send).
/// After it resolves, axum stops accepting and waits for in-flight requests to finish.
async fn shutdown_signal() {
    let ctrl_c = async { tokio::signal::ctrl_c().await.expect("ctrl-c handler") };
    #[cfg(unix)]
    let term = async {
        tokio::signal::unix::signal(tokio::signal::unix::SignalKind::terminate())
            .expect("SIGTERM handler")
            .recv()
            .await;
    };
    #[cfg(not(unix))]
    let term = std::future::pending::<()>();
    tokio::select! {
        _ = ctrl_c => info!("Ctrl-C received, draining"),
        _ = term => info!("SIGTERM received, draining"),
    }
}

A CLI with clap

A command-line tool has to read arguments, validate them, print help, report errors on stderr, write results on stdout, and return an exit code a shell script can test. clap generates all of it from a struct. No async here: a CLI that reads files needs no runtime.

Arguments are a struct

    /// Count tokens per user in one or more JSONL files ("-" reads stdin)

        #[arg(required = true)]

        /// How many users to list

}

Read it like a typed argparse declaration. #[derive(Parser)] is a derive macro: at compile time it writes the parsing code for this struct. Each field is an argument and its type decides parsing (Vec<PathBuf> takes one or more paths, bool is a flag, Option<String> is optional, u16 must parse as a number); the /// doc comments become the help text; an enum with #[derive(Subcommand)] gives one subcommand per variant, like git commit and git push. Against argparse (which also exits 2 on usage errors): the checks are generated from types (a u16 field cannot receive "abc"), the help is always in sync with the code, and an error prints one line where Python prints a traceback.

Errors and exit codes

Unix convention: exit 0 for success, non-zero for failure, and clap uses 2 for usage errors (its source defines USAGE_CODE = 2: clap_builder util), before any of your code runs. After parsing, main calls a run function that returns anyhow::Result, so every fallible step can use ?, and only main decides how an error looks and which code it returns (main is in the closed block below).

with_context(|| format!("cannot open {}", ...)) wraps the OS error in a sentence, and {e:#} prints the chain on one line: "cannot open nope.jsonl: No such file or directory (os error 2)". That is anyhow, an error type for applications that carries any error plus context; libraries define their own error enums with thiserror instead (the service's AppError above), so callers can match on them.

/// Read lines into the tally. Progress goes to stderr, and only when stderr is a terminal,
/// so pipes and logs stay clean.
fn feed(tally: &mut Tally, mut r: impl BufRead, name: &str) -> Result<()> {
    let show = io::stderr().is_terminal();
    let mut line = String::new();
    loop {
        line.clear();
        let n = r.read_line(&mut line).with_context(|| format!("reading {name}"))?;
        if n == 0 {
            break;
        }
        tally.add_line(line.trim_end_matches(['\n', '\r']));
        if show && tally.lines % 100_000 == 0 {
            eprint!("\r{name}: {} lines", tally.lines);
        }
    }
    if show && tally.lines >= 100_000 {
        eprintln!();
    }
    Ok(())
}

Shipping a binary, and a container image


Giving a Python tool to someone means giving them a Python, a virtual environment and the right wheels. A Rust tool is one executable with its dependencies compiled in. Three ways onto a machine: cargo install --path . (or cargo install <crate> from crates.io) builds in release mode into ~/.cargo/bin, like uv tool install but from source, so the user needs a Rust toolchain; copy the file from target/release/ to a machine with the same OS, CPU architecture and (on Linux) a compatible C library; or release prebuilt binaries per platform (GitHub releases, Homebrew, a container image), built by CI or cross-compiled. That last is how uv and ruff ship.

Static binaries and cross-compilation


A dynamically linked binary loads shared libraries (the C library, at least) when it starts; a statically linked one contains everything. Rust links its own crates statically always; the question is only the C library. On macOS every binary links Apple's libSystem dynamically (tokserve also links libiconv, which ships with macOS), and Apple supports nothing else ("Apple does not support statically linked binaries on Mac OS X": QA1118); fine, libSystem is on every Mac. On Linux the usual target links glibc dynamically, so a binary built on a new distribution can fail on an old one; the *-unknown-linux-musl targets link musl statically: one file that runs on any Linux kernel of that architecture.


Cross-compiling means building for another OS or CPU. rustup target add downloads the standard library for the target; you also need a linker. For a pure-Rust crate (no C code, as here: no TLS library), the rust-lld linker that ships with rustup was enough on this Mac (the rustc docs show a cross gcc and do not promise this); crates with C dependencies need a real cross toolchain, which cargo-zigbuild (zig as the linker) and cross (builds in a container) provide. The static arm64 tokserve came out at 4582976 bytes, "statically linked".

Checklist: the mistakes this page shows, in one place
    

  • Blocking inside async code (std::thread::sleep, std::fs, a synchronous HTTP client, a long CPU loop): it hides on a multi-threaded runtime until load arrives. Use the async API, spawn_blocking, or rayon.
    • 

  • Forgetting that futures are lazy: an async fn called without .await does nothing; do not silence the "futures do nothing unless you .await or poll them" warning.
    • 

  • Holding a lock or a non-Send value across .await: scope the guard so it drops before the await; use Arc; tokio::sync::Mutex only when the lock must be held across an await.
    • 

  • Assuming a dropped JoinHandle cancels the task: it detaches it. Use abort() or a JoinSet.
    • 

  • Code that is not cancel safe inside select!: the losing branch is dropped mid-way. Keep buffers outside the future.
    • 

  • println! in a CLI that may be piped: a closed pipe makes it panic (exit 101). Write through a locked stdout and treat BrokenPipe as success.
    • 

  • Progress and logs on stdout: they corrupt the output for the next program in the pipe. Progress only when is_terminal().
    • 

  • Measuring a debug build: benchmark and ship --release.
    • 

  • Two body limits: decide on one (DefaultBodyLimit) and test the 413 path.
    • 

  • Dying on SIGTERM: wire with_graceful_shutdown to SIGTERM and Ctrl-C.
    • 

  • Comparing frameworks on a hello-world endpoint: measure your real handler, open loop, with the percentiles you care about.
