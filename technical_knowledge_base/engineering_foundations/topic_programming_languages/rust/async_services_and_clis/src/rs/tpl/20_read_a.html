The idea

The idea in one sentence. A Rust future is a lazy state machine that runs only when a runtime polls it and gives its thread back only at an .await; tokio polls such tasks on a few worker threads, axum makes every request one of them, and the whole service or command-line tool ships as one compiled file.

Fig. 1 is tokio's multi-thread runtime as its documentation describes it (the "Multi threaded runtime" section of the {{tokio runtime docs|https://docs.rs/tokio/latest/tokio/runtime/index.html}}), the runtime under this page's service, tokserve. The queue contents are illustrative; the numbers are this page's recorded runs (an Apple M1 Pro, 2026-10-05).

  1. Workers, each with its own queue. A fixed set of worker threads, by default one per core ("the number of cores available to the system"; tokserve takes --workers). The runtime "maintains one global queue, and a local queue for each worker thread"; a local queue "can fit at most 256 tasks". Each block on a tray is a task: a future handed to the runtime.
  2. A worker polls a task. A worker prefers its own local queue and takes from the global queue only when its local queue is empty, or every so often (by default the runtime "targets 10ms intervals between each check of the global queue"). Polling runs the task's code up to its next .await.
  3. Pending: the task is parked, the worker moves on. At an .await on a socket or a timer the poll returns Pending; the task leaves the worker and waits with the I/O driver and the timers, which hold its waker. The worker polls its next task at once: nothing is blocked.
  4. The driver wakes it, maybe onto another worker. The runtime checks for I/O and timer events "whenever there are no tasks ready to be scheduled, or when it has scheduled 61 tasks in a row". tokio's net feature is built on mio, an "I/O event queue backed by epoll, kqueue, and IOCP" ({{mio|https://github.com/tokio-rs/mio}}; what epoll does is the {{OS Concurrency page|n:3f05c17b0d0d8112ad1af99308fa913f}}). The waker puts the task back on a run queue, not always its old worker's: in this page's 4-worker run, task A started on thread 3 and resumed on thread 5 at 103.8 ms, because thread 3 was stuck (Fig. 2, last mode).
  5. An idle worker steals. A worker with nothing to run "will attempt to steal tasks from the local queue of another worker thread", and "stealing is done by moving half of the tasks in one local queue to another local queue". A burst of requests that lands on one worker spreads over all of them.
  6. A CPU loop holds its worker. Code with no .await (counting a large log, std::thread::sleep) keeps its worker until it ends; nothing preempts it, and the tasks queued behind it wait unless another worker steals them. With both of tokserve's 2 workers counting, /health p50 went from [[b:B|spawn_blocking|p50_ms|.2f]] ms to [[b:B|inline|p50_ms|.1f]] ms (Experiment B, measured).
  7. spawn_blocking moves it off. spawn_blocking runs the closure on the blocking pool (separate threads, 512 at most by default) while the task awaits it, so the worker goes back to polling. Because a task can move between workers at any .await, tokio::spawn demands Send + 'static.

If you know Python's asyncio ({{Python: concurrency, asyncio and the GIL|n:4055c17b0d0d81bdbee8c37d80b55a0e}}), this page only says what differs.

future
a value describing async work; nothing runs until it is polled
poll, waker
the one method a future has (Ready or Pending), and the callback that says "poll me again"
runtime
the library (tokio) that polls futures and owns timers and sockets
task
a future handed to the runtime with tokio::spawn; may run on any worker thread
blocking pool
extra threads for code that must block, via spawn_blocking
cancel safety
whether dropping a future half way loses work
extractor
an axum handler parameter that pulls typed data out of a request
layer
tower middleware wrapped around the router (timeout, body limit, tracing)
profile
a named set of compiler settings in Cargo.toml (release, size, LTO)

Three ideas to keep. (1) A Rust tool or service is one compiled file: that is most of why people write them. (2) Async Rust is lazy and cooperative: CPU work between awaits blocks every other request on that thread (measured below: /health p50 went from [[b:B|spawn_blocking|p50_ms|.2f]] ms to [[b:B|inline|p50_ms|.1f]] ms). (3) The type system follows you into concurrency: tokio::spawn demands Send + 'static, so data races and dangling borrows across tasks are compile errors, not incidents.

features = [...] switches on optional parts of a crate at compile time (clap's derive macros, tokio's full runtime); fewer features means a faster build and a smaller binary. Cargo.lock pins every transitive version, like uv.lock. Cargo builds every file in src/bin/ as its own executable, and both link the same library: one implementation, two front ends, the shape of a Python package with two [project.scripts] entry points, except each compiles to a self-contained executable.
