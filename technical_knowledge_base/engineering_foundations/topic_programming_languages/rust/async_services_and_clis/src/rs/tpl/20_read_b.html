Async Rust from zero

A service spends most of its time waiting (network, database, model API). One OS thread per waiting request works up to a few thousand requests, then stack memory and thread switches dominate. Async lets one thread juggle many waiting operations: each runs until it would wait, hands the thread back, and is resumed when its data arrives. That is asyncio's idea too; Rust differs in three ways, each shown with a real run: futures are lazy, the runtime is a library you choose (usually on several threads), and cancellation is dropping.

1. A future is a value, and it is lazy

An async fn does not run when you call it. It returns a future that runs only when something polls it, normally .await. The program builds hello("a") and awaits it, and builds hello("b") and drops it:

JavaScript does not: an async function runs its body at once, up to its first await ({{JavaScript: the event loop, promises and streams|n:4055c17b0d0d81fe857de8b34db109ea}}).

2. What .await does: poll, Pending, wake

Every future implements one method, poll. The runtime calls it; it returns Poll::Ready(value) if done, or Poll::Pending after arranging for a waker to be called when it can make progress (a socket becomes readable, a timer fires). The runtime polls something else meanwhile and polls this future again only after its waker fires. A hand-written future that is ready on its third poll:

Pin. The generated state machine can hold a reference to one of its own locals across an await (a buffer and a slice of it). If the future were moved in memory, that reference would dangle. poll therefore takes Pin<&mut Self>: a pointer that promises the future will not move again once polled. .await, tokio::spawn and Box::pin handle it for you; you meet Pin when storing futures in structs or writing poll by hand ({{std::pin docs|https://doc.rust-lang.org/std/pin/index.html}}).

You will almost never write poll; async fn generates it, with one state per .await point. Two consequences matter every day: code between two awaits runs without interruption (no other task runs on that thread meanwhile), and a future that is never polled again simply stops at its last await.

3. The runtime is a library: tokio

The standard library defines the Future trait but no runtime (the executor that polls futures, plus timers and non-blocking sockets). You add one; tokio is the de facto standard, and axum, reqwest and tonic are built on it. Forgetting it is the first error everyone meets:

#[tokio::main] rewrites main into "build a runtime, then block_on the body". tokserve.rs spells that out so the number of threads is a flag:

4. Concurrency: join, spawn, JoinSet, Semaphore

tokio::join!(a, b, c) polls several futures inside the current task: concurrency without new tasks. tokio::spawn(fut) hands a future to the runtime as an independent task (Python's create_task) that may run on any worker thread, in parallel with others, and returns a JoinHandle. A JoinSet owns a group of tasks (like asyncio.TaskGroup) and aborts them all if dropped. 20 sequential calls cost 20 × 100 ms; concurrent ones cost one round trip; a semaphore with 5 permits gives 4 waves of 100 ms, the polite way to call a rate-limited model API. asyncio gives the same numbers on the same machine (the Python page's fan-out): for waiting, the language does not matter, the overlap does. Rust differs where work is done between the waits: a multi-threaded runtime uses all cores, which one asyncio loop cannot.

5. Timeouts, select!, cancellation

Cancelling a future in Rust means dropping it: it is never polled again, so the code after its pending .await never runs, and its locals are dropped (their Drop code runs). timeout and select! are both built on that. Four cases, with a guard that prints when it is dropped:

In case 2, "lazy" started before "fast" because select! "randomly picks a branch to check first" unless you write biased; ({{select! docs|https://docs.rs/tokio/latest/tokio/macro.select.html}}). In case 4, dropping a JoinHandle detaches a spawned task, it does not cancel it; only abort() (or dropping the JoinSet that owns it) does.

What this means in practice. Python cancels by raising CancelledError at the await, so cleanup goes in finally; Rust has no exception to catch, so cleanup goes in Drop (a guard). A future that has done half its work when dropped (read part of a message, taken an item off a queue) loses that half: cancel safety. tokio documents which of its methods are cancel safe; inside select! loops, use those, or keep state outside the future.
