A CLI with clap

A command-line tool has to read arguments, validate them, print help, report errors on stderr, write results on stdout, and return an exit code a shell script can test. clap generates all of it from a struct. No async here: a CLI that reads files needs no runtime.

Arguments are a struct

[[code:tok/src/bin/tokcount.rs:10-37]]

Read it like a typed argparse declaration. #[derive(Parser)] is a derive macro: at compile time it writes the parsing code for this struct. Each field is an argument and its type decides parsing (Vec<PathBuf> takes one or more paths, bool is a flag, Option<String> is optional, u16 must parse as a number); the /// doc comments become the help text; an enum with #[derive(Subcommand)] gives one subcommand per variant, like git commit and git push. Against argparse (which also exits 2 on usage errors): the checks are generated from types (a u16 field cannot receive "abc"), the help is always in sync with the code, and an error prints one line where Python prints a traceback.

Errors and exit codes

Unix convention: exit 0 for success, non-zero for failure, and clap uses 2 for usage errors (its source defines USAGE_CODE = 2: {{clap_builder util|https://github.com/clap-rs/clap/blob/master/clap_builder/src/util/mod.rs}}), before any of your code runs. After parsing, main calls a run function that returns anyhow::Result, so every fallible step can use ?, and only main decides how an error looks and which code it returns (main is in the closed block below).

with_context(|| format!("cannot open {}", ...)) wraps the OS error in a sentence, and {e:#} prints the chain on one line: "cannot open nope.jsonl: No such file or directory (os error 2)". That is anyhow, an error type for applications that carries any error plus context; libraries define their own error enums with thiserror instead (the service's AppError above), so callers can match on them.

stdin, stdout, stderr, and the broken pipe


Three conventions make a tool composable with |: results go to stdout, messages and progress to stderr, and - as a file name means stdin. The trap is the pipe: head exits after one line, the pipe closes, and the next write fails with EPIPE. Rust programs ignore the SIGPIPE signal that would silently kill a C program (the runtime sets it to ignored before main: {{unstable book, on-broken-pipe|https://doc.rust-lang.org/beta/unstable-book/compiler-flags/on-broken-pipe.html}}), so the error reaches println!, which panics: exit 101 and a panic message, in every Rust CLI that prints with println! in a loop (Python's print raises BrokenPipeError: the same bug, different name).

[[out:cli_pipe_naive]]

tokcount writes through a locked stdout handle (one lock for the whole output, also faster) and treats BrokenPipe as a normal end; and it prints progress on stderr only when a person is watching: io::stderr().is_terminal() is false in a pipe, a cron job or a CI log (the {{indicatif|https://docs.rs/indicatif}} crate draws real progress bars the same way).
