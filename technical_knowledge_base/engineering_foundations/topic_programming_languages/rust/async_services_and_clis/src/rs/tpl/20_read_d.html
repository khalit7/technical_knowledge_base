An HTTP service with axum

The token counter as a service: POST /count with {"text": "..."} returns {"tokens": n}; POST /count_log with a JSONL body returns the root program's report as JSON. axum is the tokio project's web framework, a thin typed layer over the hyper HTTP library; most of it maps one to one onto FastAPI. What a service must do whatever its language (request lifecycle, health endpoints, config, graceful shutdown) is {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}; this section is how axum does it.

Routes, handlers, extractors

[[code:tok/src/service.rs:70-98]]

A handler is an async fn. Its parameters are extractors: Json<CountReq> parses the body into the struct (serde checks every field and type, like a pydantic model), State<...> hands over shared state, Query<T> parses the query string, axum::body::Bytes takes the raw body. The return type must implement IntoResponse: a String, a Json<T>, a status code, a tuple of those, or a Result of two of them. If an extractor fails, axum answers for you and the handler never runs:

[[pr:svc_missing|Send {"txt": "oops"} (a typo in the field name). Which status, and what body?]] [[pr:svc_ctype|Send valid JSON without a content-type: application/json header. Which status?]]

FastAPI answers the same typo with 422 and a structured JSON detail list (recorded from the FastAPI twin in code/py/app.py: {"detail":[{"type":"missing","loc":["body","text"],"msg":"Field required",...}]}); axum's default rejection is a plain-text sentence, so for JSON errors write your own extractor wrapper or map rejections in a layer. FastAPI's dependency injection corresponds to extractors and State; Starlette middleware to tower layers.

Errors, and panics

For errors the handler decides, define an enum with thiserror (so each case maps to its own status) and implement IntoResponse once; #[from] tokio::task::JoinError lets ? turn a crashed background job into a 500.

A panic (a bug such as an out-of-bounds index) inside a handler does not take the server down: tokio catches it at the task boundary, that one connection is closed without a response, and other requests carry on (examples/b3_panic.rs, curl as the client; exit 52 is "empty reply from server"). To answer 500 instead, add tower-http's CatchPanicLayer.

Shared state and CPU work

Every request is its own task, maybe on another thread, so shared state goes behind an Arc and anything mutable inside it must be thread-safe: here, two atomic counters. For a mutable map use a Mutex (held briefly, never across an await) or a concurrent map; a database pool is already shareable. Python's equivalent, a module-level dict, is per worker process under uvicorn --workers 4, so /stats on the FastAPI twin reports only the worker that answered; tokserve's counters are process-wide because its workers are threads (/stats after the requests on this page: [[g:svc_stats|(\{.*\})]]).

Counting a 391 KB log is about a millisecond of CPU, a 3.9 MB one about ten times that: both far above the 10 to 100 µs budget between awaits, so the handler moves it to the blocking pool (the inline mode exists only for Experiment B above). The double ??: the first unwraps the JoinError (did the background job panic?), the second the counting's own Result.

Middleware: tower layers

A layer wraps the whole router in reusable behaviour; tower-http provides the common ones. The last .layer added is the outermost, so a request passes through tracing, then the timeout, then the body limit, then the route.

[[pr:svc_timeout|GET /slow?ms=1500 with the default 1,000 ms request timeout. What comes back?]] [[pr:svc_toolarge|POST a 3.9 MB log when the limit is 1 MiB. What comes back, and does the handler run?]]

Watch for two body limits: axum's extractors refuse bodies over 2 MB by default ({{DefaultBodyLimit|https://docs.rs/axum/latest/axum/extract/struct.DefaultBodyLimit.html}}), independently of any tower layer. This project's first run of Experiment B was silently measuring fast 413 rejections because of it; DefaultBodyLimit::disable() plus one configured RequestBodyLimitLayer leaves a single limit to reason about.

Logs and spans: tracing

tracing records events (log lines with typed fields) inside spans (a named period of work, here one per request, opened by TraceLayer). The subscriber decides format and filter: RUST_LOG=info,tower_http=debug asks for info everywhere and per-request lines from tower-http. The same spans can be exported to OpenTelemetry; what to log and alert on is {{Observability|n:3ef5c17b0d0d811e8490c54dd42c2b9b}}.

Configuration and graceful shutdown

Settings come from clap with env = "TOK_ADDR" on each flag, so the same binary takes flags on a laptop and environment variables in a container. On shutdown an orchestrator sends SIGTERM, waits a grace period, then SIGKILL (10 s by default for docker stop: {{docs|https://docs.docker.com/reference/cli/docker/container/stop/}}; Kubernetes' 30 s and why to drain are on the backend API page). with_graceful_shutdown takes a future; when it resolves (here a select! over Ctrl-C and SIGTERM), axum stops accepting connections and waits for in-flight requests.
