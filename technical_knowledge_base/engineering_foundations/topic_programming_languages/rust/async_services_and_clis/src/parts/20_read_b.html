Async Rust from zero

A service spends most of its time waiting (network, database, model API). One OS thread per waiting request works up to a few thousand requests, then stack memory and thread switches dominate. Async lets one thread juggle many waiting operations: each runs until it would wait, hands the thread back, and is resumed when its data arrives. That is asyncio's idea too; Rust differs in three ways, each shown with a real run: futures are lazy, the runtime is a library you choose (usually on several threads), and cancellation is dropping.

1. A future is a value, and it is lazy

An async fn does not run when you call it. It returns a future that runs only when something polls it, normally .await. The program builds hello("a") and awaits it, and builds hello("b") and drops it:

The code (examples/a1_lazy.rs)
tok/examples/a1_lazy.rs
// A future is a value: calling an async fn runs nothing until something awaits (polls) it.
async fn hello(tag: &str) -> u32 {
    println!("   {tag}: body runs");
    42
}

#[tokio::main(flavor = "current_thread")]
async fn main() {
    println!("1. calling hello(\"a\")");
    let fut = hello("a"); // nothing printed: we only built a state machine
    println!("2. holding a future of {} bytes; its body has not run", std::mem::size_of_val(&fut));
    let v = fut.await; // now the runtime polls it to completion
    println!("3. awaited it: {v}");
    hello("b"); // never awaited: the compiler warns and the body never runs
    println!("4. end of main");
}

JavaScript does not: an async function runs its body at once, up to its first await ({{JavaScript: the event loop, promises and streams|n:4055c17b0d0d81fe857de8b34db109ea}}).

2. What .await does: poll, Pending, wake

Every future implements one method, poll. The runtime calls it; it returns Poll::Ready(value) if done, or Poll::Pending after arranging for a waker to be called when it can make progress (a socket becomes readable, a timer fires). The runtime polls something else meanwhile and polls this future again only after its waker fires. A hand-written future that is ready on its third poll:

awaiting Countdown { left: 2 }
   poll: Pending (2 left), asking to be woken
   poll: Pending (1 left), asking to be woken
   poll: Ready
result: done
The hand-written future, and Pin in one paragraph
tok/examples/a1_poll.rs
// What .await does underneath: the runtime calls poll() until it returns Ready.
// A hand-written future that is not ready the first two times it is polled.
use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

struct Countdown {
    left: u32,
}

impl Future for Countdown {
    type Output = &'static str;
    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output> {
        if self.left == 0 {
            println!("   poll: Ready");
            return Poll::Ready("done");
        }
        println!("   poll: Pending ({} left), asking to be woken", self.left);
        self.left -= 1;
        // A real future (a socket, a timer) hands the waker to the OS event source.
        // Here we wake ourselves at once, so the runtime polls again.
        cx.waker().wake_by_ref();
        Poll::Pending
    }
}

#[tokio::main(flavor = "current_thread")]
async fn main() {
    println!("awaiting Countdown {{ left: 2 }}");
    let r = Countdown { left: 2 }.await;
    println!("result: {r}");
}

Pin. The generated state machine can hold a reference to one of its own locals across an await (a buffer and a slice of it). If the future were moved in memory, that reference would dangle. poll therefore takes Pin<&mut Self>: a pointer that promises the future will not move again once polled. .await, tokio::spawn and Box::pin handle it for you; you meet Pin when storing futures in structs or writing poll by hand ({{std::pin docs|https://doc.rust-lang.org/std/pin/index.html}}).

You will almost never write poll; async fn generates it, with one state per .await point. Two consequences matter every day: code between two awaits runs without interruption (no other task runs on that thread meanwhile), and a future that is never polled again simply stops at its last await.

3. The runtime is a library: tokio

The standard library defines the Future trait but no runtime (the executor that polls futures, plus timers and non-blocking sockets). You add one; tokio is the de facto standard, and axum, reqwest and tonic are built on it. Forgetting it is the first error everyone meets:

4. Concurrency: join, spawn, JoinSet, Semaphore

tokio::join!(a, b, c) polls several futures inside the current task: concurrency without new tasks. tokio::spawn(fut) hands a future to the runtime as an independent task (Python's create_task) that may run on any worker thread, in parallel with others, and returns a JoinHandle. A JoinSet owns a group of tasks (like asyncio.TaskGroup) and aborts them all if dropped. Twenty calls to a local server that answers after 100 ms (this page's own service, standing in for a model API):

sequential, 20 calls       2.058 s
JoinSet, 20 at once        0.107 s   "slept 100 ms"
JoinSet, at most 5         0.415 s
timeout after              0.253 s   Elapsed
The code (examples/a4_fanout.rs)
tok/examples/a4_fanout.rs (lines 26 to 55)
    let t = Instant::now();
    for _ in 0..20 {
        get(addr, "/slow?ms=100".into()).await; // one after another
    }
    println!("sequential, 20 calls      {:6.3} s", t.elapsed().as_secs_f64());

    let t = Instant::now();
    let mut set = JoinSet::new(); // like asyncio.TaskGroup: owns its tasks, aborts them when dropped
    for _ in 0..20 {
        set.spawn(get(addr, "/slow?ms=100".into()));
    }
    let bodies = set.join_all().await;
    println!("JoinSet, 20 at once       {:6.3} s   {:?}", t.elapsed().as_secs_f64(), bodies[0]);

    let t = Instant::now();
    let limit = Arc::new(Semaphore::new(5)); // at most 5 in flight
    let mut set = JoinSet::new();
    for _ in 0..20 {
        let limit = limit.clone();
        set.spawn(async move {
            let _permit = limit.acquire().await.unwrap(); // released when dropped
            get(addr, "/slow?ms=100".into()).await
        });
    }
    set.join_all().await;
    println!("JoinSet, at most 5        {:6.3} s", t.elapsed().as_secs_f64());

    let t = Instant::now();
    let r = tokio::time::timeout(Duration::from_millis(250), get(addr, "/slow?ms=2000".into())).await;
    println!("timeout after             {:6.3} s   {}", t.elapsed().as_secs_f64(), if r.is_err() { "Elapsed" } else { "ok" });

20 sequential calls cost 20 × 100 ms; concurrent ones cost one round trip; a semaphore with 5 permits gives 4 waves of 100 ms, the polite way to call a rate-limited model API. asyncio gives the same numbers on the same machine (the Python page's fan-out): for waiting, the language does not matter, the overlap does. Rust differs where work is done between the waits: a multi-threaded runtime uses all cores, which one asyncio loop cannot.

5. Timeouts, select!, cancellation

Cancelling a future in Rust means dropping it: it is never polled again, so the code after its pending .await never runs, and its locals are dropped (their Drop code runs). timeout and select! are both built on that. Four cases, with a guard that prints when it is dropped:

The code (examples/a3_cancel.rs)
tok/examples/a3_cancel.rs (lines 6 to 46)
/// Prints when it is dropped, to show exactly when a future is cancelled.
struct Guard(&'static str);
impl Drop for Guard {
    fn drop(&mut self) {
        println!("   drop: {} cleaned up", self.0);
    }
}

async fn step(name: &'static str, ms: u64) -> &'static str {
    let _g = Guard(name);
    println!("   {name}: started, waiting {ms} ms");
    sleep(Duration::from_millis(ms)).await;
    println!("   {name}: finished"); // never printed if the future is dropped first
    name
}

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let t = Instant::now();
    println!("1. timeout(250 ms) around a 2000 ms call");
    let r = timeout(Duration::from_millis(250), step("slow", 2000)).await;
    println!("   -> {r:?} after {} ms", t.elapsed().as_millis());

    println!("2. select!: first to finish wins, the other is dropped");
    let t = Instant::now();
    tokio::select! {
        w = step("fast", 100) => println!("   -> winner {w} after {} ms", t.elapsed().as_millis()),
        w = step("lazy", 300) => println!("   -> winner {w}"),
    }

    println!("3. a spawned task keeps running on its own; abort() cancels it");
    let h = tokio::spawn(step("background", 1000));
    sleep(Duration::from_millis(50)).await;
    h.abort();
    println!("   -> join: {:?}", h.await.map_err(|e| e.is_cancelled()));

    println!("4. dropping a JoinHandle does NOT cancel the task (it is detached)");
    drop(tokio::spawn(step("detached", 100)));
    sleep(Duration::from_millis(150)).await;
    println!("   -> main done");
}

In case 2, "lazy" started before "fast" because select! "randomly picks a branch to check first" unless you write biased; ({{select! docs|https://docs.rs/tokio/latest/tokio/macro.select.html}}). In case 4, dropping a JoinHandle detaches a spawned task, it does not cancel it; only abort() (or dropping the JoinSet that owns it) does.

What this means in practice. Python cancels by raising CancelledError at the await, so cleanup goes in finally; Rust has no exception to catch, so cleanup goes in Drop (a guard). A future that has done half its work when dropped (read part of a message, taken an item off a queue) loses that half: cancel safety. tokio documents which of its methods are cancel safe; inside select! loops, use those, or keep state outside the future.
