Blocking the runtime: the mistake async makes easy

A worker thread polls one task at a time and gets the thread back only at an .await. A task that calls a blocking function (std::thread::sleep, a synchronous file read, a CPU-heavy loop) holds its worker the whole time, and every other task queued on that worker waits. Alice Ryhl (a tokio maintainer) gives the rule of thumb: "no more than 10 to 100 microseconds between each .await" ({{Async: What is blocking?|https://ryhl.io/blog/async-what-is-blocking/}}).   3. B lets go at 208.1 ms. A's timer was due at 100 ms, but nobody could poll A: it is 108 ms late.
  4. C starts; A finally finishes. At 208.1 ms C starts and suspends, and A is resumed and done.

  1. B's sleep goes to the blocking pool. At 0.0 ms all three suspend; B awaits spawn_blocking, whose closure sleeps on a pool thread, not on ours.
  2. A on time. A is done at 103.1 ms.
  3. B when the pool thread finishes. B is resumed and done at 210.1 ms.
  4. C last. C is done at 305.5 ms: total 305.5 ms, back to the longest wait.
  1. A suspends, B blocks a worker. On a 4-worker runtime the three jobs are spawned as tasks. A and B start on thread 3: A suspends, then B blocks thread 3 at 0.0 ms.
  2. C runs on another worker. C starts on thread 5 and suspends at 0.0 ms.
  3. A resumes on thread 5. A's timer fires while thread 3 is still stuck, so A is resumed on thread 5 and done at 103.8 ms. The task moved between threads, which is why spawned tasks must be Send.
  4. B releases thread 3. B finishes at 204.5 ms.
  5. C done: the trap. C finishes at 303.8 ms: total 303.8 ms, as fast as with no blocking, because B blocked only one worker. The bug is still there; it shows up under load, when every worker has a B (Fig. 3).

In short: join overlaps the waits, a blocking B holds the one thread and makes A late, spawn_blocking moves B off it, and on 4 workers the blocking B hides. async fn job(name: &str, ms: u64) -> String {
    ev(name, "start", "");
    ev(name, "await", &format!("sleep({ms} ms).await"));
    tokio::time::sleep(Duration::from_millis(ms)).await; // yields to the runtime
    ev(name, "resume", "");
    ev(name, "done", "");
    name.into()
}

async fn job_blocking(name: &str, ms: u64) -> String {
    ev(name, "start", "");
    ev(name, "block", &format!("std::thread::sleep({ms} ms)"));
    std::thread::sleep(Duration::from_millis(ms)); // blocks the worker thread: nothing else runs on it
    ev(name, "done", "");
    name.into()
}

async fn job_offload(name: &str, ms: u64) -> String {
    ev(name, "start", "");
    ev(name, "await", &format!("spawn_blocking(sleep {ms} ms).await"));
    tokio::task::spawn_blocking(move || std::thread::sleep(Duration::from_millis(ms))).await.unwrap();
    ev(name, "resume", "");
    ev(name, "done", "");
    name.into()
}

The fixes, in order of preference: use the async version of the call (tokio::time::sleep, tokio::fs, an async database driver); for blocking calls you cannot avoid, tokio::task::spawn_blocking; for CPU-heavy parallel work, a CPU thread pool such as rayon (the {{spawn_blocking docs|https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html}}: "Specialized CPU-bound executors, such as rayon, may also be a good fit"); the PyO3 page uses rayon from Python ({{Rust: speeding up Python with PyO3 and maturin|n:4055c17b0d0d81048311c87e9b76a78a}}).

Send + 'static: why tokio::spawn rejects your code

A spawned task can outlive the function that spawned it ('static: it may not borrow its locals) and can move to another worker thread at any .await (Send: everything it holds across an await must be safe to move between threads). Send and Sync themselves are taught on {{Rust: lifetimes, smart pointers, threads and unsafe|n:4055c17b0d0d8160aa32df9cda0aef03}}; here are the three errors they produce in async code, with the compiler's real messages.
