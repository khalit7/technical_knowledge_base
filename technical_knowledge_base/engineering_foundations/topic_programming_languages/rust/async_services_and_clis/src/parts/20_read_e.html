Measured: the same service in axum and in FastAPI

The FastAPI twin (code/py/app.py) has the same routes and rules and returns byte-identical JSON; it uses the root page's reference token function and FastAPI's advice for blocking work (the log count runs in a worker thread). tokserve is axum 0.8.9 on tokio 1.53.2 (release build); the twin is FastAPI 0.142.2 on uvicorn 0.54.0 with uvloop and httptools, pydantic 2.13.5, CPython 3.14.8. Same load generator (oha 1.16.0, 2 threads), same machine (Apple M1 Pro, 10 cores, in normal use), four configurations (1 or 4 async worker threads for axum, 1 or 4 uvicorn worker processes for FastAPI), three rounds of 3 s per load in alternating order.

Tiny requests: both fast; CPU work and memory: where the gap is

Predict first: on /count_log (391 KB of counting), how many times more requests per second does axum with 4 workers serve than FastAPI with 4? Then switch to "/health" and to memory.

Bars: median of three rounds; whiskers: lowest and highest round. measured; method and raw runs in src/rs/bench/.

How to read it. For tiny requests both are fast in absolute terms, and a real service's time goes to its database or model call, not the framework: at a steady 1,000 requests per second every configuration answered /count with a median under half a millisecond. The gaps that matter are CPU work in Python (counting 391 KB costs about 14 ms in Python and 1.3 ms in Rust, and in one uvicorn worker the GIL lets only one count run at a time, even on worker threads) and memory per worker: Python scales across cores with processes, each holding its own interpreter and imports, where tokio scales with threads in one process. How to load-test properly (open against closed loop, coordinated omission) is {{Capacity planning and performance|n:3ef5c17b0d0d81458291d55d7443700c}}; the root page's {{Benchmark tab|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} measures the same program as a batch job.

What this does not show (caveats)
  • Laptop in normal use: load average 7 to 13 during the runs (10 cores). The load generator shares the machine; numbers are lower and noisier than on a quiet server.
  • Closed-loop loads (32 or 8 connections, as fast as possible) measure capacity; their latency excludes queueing that a real arrival process would see. The "@1000/s" and "@20/s" loads are open loop with oha's latency correction.
  • oha with 2 threads can be the bottleneck for axum's fastest loads; the /health and /count gaps are lower bounds.
  • axum "1 worker" still runs /count_log on tokio's blocking pool, so it used more than one core there; FastAPI's count runs on a thread but the GIL serialises it within a worker.
  • Memory: resident set of the server process and its children (uvicorn's supervisor plus workers), sampled every 0.25 s.
  • Production Python services often move CPU work out of the request path (a queue, or a Rust extension: {{the PyO3 page|n:4055c17b0d0d81048311c87e9b76a78a}}), which removes most of the /count_log gap. No TLS, no database, loopback networking.
  • Every response in these runs was a 200: bench.py records each run's status codes, because a benchmark can silently measure rejections (the 2 MB body limit above).

Testing a service

Three levels, all run by one cargo test (test strategy in general is {{Testing and quality|n:3c65c17b0d0d81548848e2ebdd2f63ee}}):

  • Unit tests of the logic in src/lib.rs, with no async and no HTTP: the token rules from the root page's spec, and malformed lines being counted rather than fatal.
  • Router tests without a network. An axum Router is a tower Service: call it with a request object and await the response with tower::ServiceExt::oneshot. No sockets, and it exercises extractors, layers and status codes. #[tokio::test] gives each test its own runtime.
  • A real server on a real port. Bind port 0 (the OS picks a free one, so tests run in parallel), spawn the server, talk TCP to it: catches what in-process tests cannot (the listener, HTTP framing).

#[tokio::test]
async fn count_without_a_network() {
    let req = Request::post("/count")
        .header("content-type", "application/json")
        .body(Body::from(r#"{"text":"x86_64 and v2.1"}"#))
        .unwrap();
    let resp = app(cfg()).oneshot(req).await.unwrap();
    assert_eq!(resp.status(), StatusCode::OK);
    let bytes = resp.into_body().collect().await.unwrap().to_bytes();
    let body: CountResp = serde_json::from_slice(&bytes).unwrap();
    assert_eq!(body.tokens, 5); // x86, 64, and, v2, 1
}

/// A real server on port 0 (the OS picks a free port), talked to over TCP.
#[tokio::test]
async fn real_server_over_tcp() {
    let listener = tokio::net::TcpListener::bind("127.0.0.1:0").await.unwrap();
    let addr = listener.local_addr().unwrap();
    tokio::spawn(async move { axum::serve(listener, app(cfg())).await.unwrap() });

    use tokio::io::{AsyncReadExt, AsyncWriteExt};
    let mut s = tokio::net::TcpStream::connect(addr).await.unwrap();
    s.write_all(b"GET /health HTTP/1.1\r\nHost: x\r\nConnection: close\r\n\r\n").await.unwrap();
    let mut raw = String::new();
    s.read_to_string(&mut raw).await.unwrap();
    assert!(raw.starts_with("HTTP/1.1 200 OK"), "{raw}");
    assert!(raw.ends_with("\r\n\r\nok"), "{raw}");
}
