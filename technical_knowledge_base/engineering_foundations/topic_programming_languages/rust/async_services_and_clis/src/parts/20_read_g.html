Shipping a binary, and a container image

Giving a Python tool to someone means giving them a Python, a virtual environment and the right wheels. A Rust tool is one executable with its dependencies compiled in. Three ways onto a machine: cargo install --path . (or cargo install <crate> from crates.io) builds in release mode into ~/.cargo/bin, like uv tool install but from source, so the user needs a Rust toolchain; copy the file from target/release/ to a machine with the same OS, CPU architecture and (on Linux) a compatible C library; or release prebuilt binaries per platform (GitHub releases, Homebrew, a container image), built by CI or cross-compiled. That last is how uv and ruff ship.

[profile.release-small]
inherits = "release"

[profile.release-strip]
inherits = "release"
strip = true

Debug builds are large and slow and never for measuring or shipping (cargo run builds without optimisation); release is a good default; stripping and LTO are cheap wins for distributed binaries; opt-level = "z" is for when size matters more than speed (embedded, WebAssembly, a CLI downloaded millions of times).

Static binaries and cross-compilation

A dynamically linked binary loads shared libraries (the C library, at least) when it starts; a statically linked one contains everything. Rust links its own crates statically always; the question is only the C library. On macOS every binary links Apple's libSystem dynamically (tokserve also links libiconv, which ships with macOS), and Apple supports nothing else ("Apple does not support statically linked binaries on Mac OS X": {{QA1118|https://developer.apple.com/library/archive/qa/qa1118/_index.html}}); fine, libSystem is on every Mac. On Linux the usual target links glibc dynamically, so a binary built on a new distribution can fail on an old one; the *-unknown-linux-musl targets link musl statically: one file that runs on any Linux kernel of that architecture.

Cross-compiling means building for another OS or CPU. rustup target add downloads the standard library for the target; you also need a linker. For a pure-Rust crate (no C code, as here: no TLS library), the rust-lld linker that ships with rustup was enough on this Mac (the rustc docs show a cross gcc and do not promise this); crates with C dependencies need a real cross toolchain, which {{cargo-zigbuild|https://github.com/rust-cross/cargo-zigbuild}} (zig as the linker) and {{cross|https://github.com/cross-rs/cross}} (builds in a container) provide. The static arm64 tokserve came out at 4582976 bytes, "statically linked".

A container image

A Rust service image needs the binary and, at most, a C library: compile in a full Rust image, copy only the binary into a minimal one (a multi-stage build). For a normally linked binary, Google's distroless cc-debian12 adds glibc and libgcc and no shell or package manager (its :nonroot tag runs unprivileged: {{GoogleContainerTools/distroless|https://github.com/GoogleContainerTools/distroless}}); for the static musl build, scratch, the empty image, is enough. How images, layers and isolation work is {{Containers and isolation|n:3f05c17b0d0d8156a841e4bf28f11293}}.

The two Dockerfiles
tok/Dockerfile
# Multi-stage build: compile in a full Rust image, ship only the binary.
# Stage 1: the builder (about 1.5 GB of compilers and headers; thrown away).
FROM rust:1.99-slim-bookworm AS build
WORKDIR /src
# Cache dependencies: build once with a dummy main so code edits do not refetch crates.
COPY Cargo.toml Cargo.lock ./
RUN mkdir -p src/bin && echo 'fn main(){}' > src/bin/tokserve.rs && echo '' > src/lib.rs \
 && cargo build --release --bin tokserve && rm -rf src
COPY src ./src
RUN touch src/lib.rs src/bin/tokserve.rs && cargo build --release --bin tokserve

# Stage 2: distroless "cc" = glibc + libgcc + CA certs, no shell, no package manager, non-root user.
FROM gcr.io/distroless/cc-debian12:nonroot
COPY --from=build /src/target/release/tokserve /tokserve
ENV TOK_ADDR=0.0.0.0:3000
EXPOSE 3000
ENTRYPOINT ["/tokserve"]
tok/Dockerfile.scratch
# The smallest image: a static musl binary in an empty image.
# Build the binary first (on any machine): see ../../cross.sh, or in a builder stage with
#   rustup target add x86_64-unknown-linux-musl && cargo build --release --target x86_64-unknown-linux-musl
FROM scratch
COPY tokserve /tokserve
ENV TOK_ADDR=0.0.0.0:3000
USER 65532:65532
EXPOSE 3000
ENTRYPOINT ["/tokserve"]

What else production needs (health endpoint, SIGTERM, logs on stdout, configuration from the environment, TLS in front) is the backend API page's; the Rust-specific part is matching the worker count to the CPUs the container is given (tokserve takes --workers or TOK_WORKERS), and TLS in-process, when wanted, with rustls.
