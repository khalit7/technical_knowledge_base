2. Structs, enums and match: make illegal states unrepresentable

A struct is a record with named fields, like a dataclass. An enum in Rust is far more than Python's Enum: each variant can carry its own data, so one type says "a message is either text from a user, or a tool call with arguments, or an image of some size". This is called a sum type or tagged union. match takes it apart, and must cover every variant.

The design habit this enables matters more than the syntax. Python code often models state as one class with optional fields and a status string, and every method checks that the fields agree with the status. In Rust, give each state exactly the data it has. "Connected but no session id" or "failed with no error" then cannot be written at all:

states.rs (lines 1 to 20)
// Python habit: one class with optional fields and a status string.
// Here every state carries exactly the data that state has, so
// "connected but no socket" or "failed but no error" cannot be written.
#[derive(Debug)]
enum Conn {
    Idle,
    Connecting { attempt: u32 },
    Connected { session_id: u64 },
    Failed { error: String },
}

fn step(c: Conn) -> Conn {
    match c {
        Conn::Idle => Conn::Connecting { attempt: 1 },
        Conn::Connecting { attempt } if attempt < 3 => Conn::Connecting { attempt: attempt + 1 },
        Conn::Connecting { .. } => Conn::Connected { session_id: 42 },
        Conn::Connected { session_id } => Conn::Connected { session_id },
        Conn::Failed { error } => Conn::Failed { error },
    }
}

What an enum costs in memory

The last three lines of that run are about memory: Option<u64> needs 16 bytes, but Option<&u64> and Option<Box<u64>> fit in 8. A second program, layout.rs, prints the size and alignment of each type here and finds where each variant's data sits (the address of a field minus the address of the value), so the figure is drawn to scale, one cube per byte:

  1. A tag costs a byte, and padding. Option<u8> is 2 bytes: the u8 plus one tag byte saying Some or None. Option<u32> is 8, with the u32 at offset 4: a u32 must start at a multiple of 4, so the tag byte is followed by 3 bytes of padding.
  2. Option<u64>: 16 bytes for 8 of data. The u64 sits at offset 8 and is aligned to 8, so one tag byte costs 8 bytes in all. Every value of a u64 is a valid number, so the tag has nowhere else to go.
  3. Option<&u64>: no tag at all. 8 bytes, the same as &u64, and the same for Box. A reference is never null, so the all-zero pattern is free to mean None: the "null pointer optimisation", which the {{Option documentation|https://doc.rust-lang.org/std/option/index.html#representation}} guarantees for references, Box, function pointers and NonZero numbers. A bit pattern a type can never hold is called a niche. Safety without null costs nothing here.
  4. A String is three words. 24 bytes: a capacity, a pointer to the text on the heap, and a length. Taking a String of capacity 16 holding "timeout" apart word by word found them in that order on this build (the {{Vec documentation|https://doc.rust-lang.org/std/vec/struct.Vec.html#guarantees}} leaves the order unspecified).
  5. Conn: four variants in the same 24 bytes. An enum is as big as its largest variant, here Failed's String at offset 0. The others reuse the same bytes: Connecting's attempt and Connected's session_id both sit at offset 8; Idle has no data. size_of::<Conn>() printed 24: not one byte more than the String.
  6. The tag hides in the first word. For Failed the first word is the String's capacity (0x0000000000000010, that is 16). For the other three it held 0x8000000000000000, ...01 and ...02: 263 and up, more than isize::MAX, and a capacity can never be that large (a Vec "panics if the new capacity exceeds isize::MAX bytes", and String::as_mut_vec exposes the Vec<u8> under a String). The compiler stored the tag in that niche.
  7. Option<Conn>: still 24. There are many unused capacities, so None::<Conn> simply takes the next one, 0x8000000000000003. Wrapping an enum in Option cost nothing either.

Recorded with rustc 1.94.0 on Linux x86-64 (the rest of the page used rustc 1.99.0 on the M1 Pro; the three sizes both runs print agree). Where the compiler puts a tag is not a stable guarantee, except the null pointer case: read size_of, do not rely on the layout. The heap buffer in steps 4 to 6 is drawn smaller than scale.

// Offsets are measured with plain references (field address minus value address): no unsafe.
use std::mem::{align_of, size_of};

#[allow(dead_code)]
#[derive(Debug)]
enum Conn {
    Idle,
    Connecting { attempt: u32 },
    Connected { session_id: u64 },
    Failed { error: String },
}

fn off<T, F>(base: &T, field: &F) -> usize {
    field as *const F as usize - base as *const T as usize
}

The syntax, on a chat message

enums.rs
#[derive(Debug, Clone, PartialEq)]
struct Usage {
    user: String,
    tokens: u64,
}

// An enum's variants can carry different data: a "tagged union".
#[derive(Debug)]
enum Message {
    Text { user: String, text: String },
    ToolCall { name: String, args: Vec<String> },
    Image { width: u32, height: u32 },
    Ping,
}

impl Message {
    fn describe(&self) -> String {
        match self {
            Message::Text { user, text } if text.is_empty() => format!("{user} sent nothing"),
            Message::Text { user, text } => format!("{user}: {} chars", text.len()),
            Message::ToolCall { name, args } => format!("call {name} with {} args", args.len()),
            Message::Image { width, height } => format!("image {width}x{height}"),
            Message::Ping => "ping".to_string(),
        }
    }
}

fn main() {
    let u = Usage { user: "u0029".into(), tokens: 9491 };
    let v = Usage { tokens: 10, ..u.clone() }; // struct update syntax
    println!("{u:?}\n{v:?} equal? {}", u == v);
    let msgs = vec![
        Message::Text { user: "ada".into(), text: "hi there".into() },
        Message::Text { user: "bob".into(), text: String::new() },
        Message::ToolCall { name: "search".into(), args: vec!["rust".into()] },
        Message::Image { width: 640, height: 480 },
        Message::Ping,
    ];
    for m in &msgs {
        println!("{}", m.describe());
    }
    println!("{:#?}", msgs[2]);
    let n = 7;
    let kind = match n {
        0 => "zero",
        1..=9 => "one digit",
        _ => "more", // `_` matches anything else
    };
    println!("{n} is {kind}");
    if let Message::Image { width, .. } = &msgs[3] {
        println!("if let: width {width}");
    }
}

3. Option, Result and ?: errors as values

Rust has no None that can appear anywhere and no exceptions for expected failures. Two enums from the standard library carry them, written like any other enum:

  • Option<T> is Some(value) or None: maybe missing. dict.get, str.find and "first element" return one.
  • Result<T, E> is Ok(value) or Err(error): may fail. Parsing, I/O and network calls return one.

You cannot use the value inside without deciding what happens in the other case. The ? operator is the common decision: "if this is an Err, return it from my function now; otherwise give me the value". It is the explicit, typed version of letting an exception propagate. The recorded program on its three configurations (pick one on the figure):

  1. The call. main calls budget(&bad); bad has context = "8k".
  2. Into get_num. budget calls get_num(cfg, "context").
  3. The key is there. cfg.get("context") is Some("8k"); ok_or makes it Ok("8k"); ? unwraps it, so raw = "8k".
  4. The parse fails. "8k".parse::<u32>() returns Err(ParseIntError { kind: InvalidDigit }).
  5. The error is wrapped. map_err wraps it as Err(BadNumber { key: "context", source }). With no semicolon, that is get_num's return value.
  6. ? returns early. Back in budget, ? sees an Err and returns it from budget at once. Lines 31 and 32 never run: max_output is never read.
  7. main reports it. main's match takes the Err arm and prints error: context is not a number: invalid digit found in string (the message is ConfigError's Display).
  1. The call. main calls budget(&missing); missing has no max_output.
  2. The first number parses. get_num(cfg, "context") finds "8192" and parses it: Ok(8192), so ? gives ctx = 8192.
  3. The second call. budget calls get_num(cfg, "max_output").
  4. The key is missing. cfg.get("max_output") is None; ok_or turns it into Err(Missing("max_output")); ? returns it from get_num immediately. Lines 24 to 26 never run.
  5. ? again. In budget, ? returns the same Err; line 32 never runs.
  6. main reports it. main prints error: missing key max_output.
  1. The call. main calls budget(&good).
  2. The first number. "8192" parses: ctx = 8192.
  3. The second number. " 1024" is trimmed, then parses: out = 1024.
  4. The last line runs. Both ? found Ok, so budget reaches its last line: Ok(8192 - 1024).
  5. main prints the result. main prints ok: 7168 tokens for the prompt.
The whole program, errors.rs (the error type and main)
errors.rs
use std::collections::HashMap;
use std::fmt;
use std::num::ParseIntError;

#[derive(Debug)]
enum ConfigError {
    Missing(&'static str),
    BadNumber { key: &'static str, source: ParseIntError },
}

impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            ConfigError::Missing(k) => write!(f, "missing key {k}"),
            ConfigError::BadNumber { key, source } => write!(f, "{key} is not a number: {source}"),
        }
    }
}

impl std::error::Error for ConfigError {}

fn get_num(cfg: &HashMap<&str, &str>, key: &'static str) -> Result<u32, ConfigError> {
    let raw = cfg.get(key).ok_or(ConfigError::Missing(key))?; // Option -> Result, then ?
    raw.trim()
        .parse::<u32>()
        .map_err(|e| ConfigError::BadNumber { key, source: e })
}

fn budget(cfg: &HashMap<&str, &str>) -> Result<u32, ConfigError> {
    let ctx = get_num(cfg, "context")?; // ? returns the error to our caller
    let out = get_num(cfg, "max_output")?;
    Ok(ctx - out)
}

fn main() {
    let good = HashMap::from([("context", "8192"), ("max_output", " 1024")]);
    let bad = HashMap::from([("context", "8k"), ("max_output", "1024")]);
    let missing = HashMap::from([("context", "8192")]);
    for cfg in [&good, &bad, &missing] {
        match budget(cfg) {
            Ok(n) => println!("ok: {n} tokens for the prompt"),
            Err(e) => println!("error: {e}   (debug: {e:?})"),
        }
    }
    let first: Option<&str> = "".split_whitespace().next();
    println!("first word of \"\": {:?}, or default: {}", first, first.unwrap_or("<none>"));
    let n: Result<u8, _> = "300".parse::<u8>();
    println!("\"300\".parse::<u8>() = {n:?}");
    let x: u32 = "12".parse().unwrap(); // fine
    println!("unwrap ok: {x}");
    let y: u32 = "twelve".parse().expect("config value must be a number"); // panics
    println!("{y}");
}

thiserror and anyhow

The common split ({{thiserror|https://docs.rs/thiserror}}, {{anyhow|https://docs.rs/anyhow}}): libraries define typed error enums so callers can match on them, and thiserror writes the Display and Error code from attributes; applications mostly report errors, and anyhow::Result holds any error plus a chain of context messages. Versions used here: thiserror 2.0.21, anyhow 1.0.104.

main.rs
// A library-style typed error (thiserror) under an application-style error (anyhow).
use anyhow::{Context, Result};
use thiserror::Error;

#[derive(Debug, Error)]
enum ParseError {
    #[error("line {line}: missing field {field}")]
    MissingField { line: usize, field: &'static str },
    #[error("line {line}: bad token count")]
    BadCount { line: usize, #[source] source: std::num::ParseIntError },
}

// typed: callers can match on the variant
fn parse_line(line: usize, s: &str) -> Result<(String, u64), ParseError> {
    let mut it = s.split(',');
    let user = it.next().filter(|u| !u.is_empty()).ok_or(ParseError::MissingField { line, field: "user" })?;
    let n = it.next().ok_or(ParseError::MissingField { line, field: "tokens" })?;
    let n = n.trim().parse().map_err(|source| ParseError::BadCount { line, source })?;
    Ok((user.to_string(), n))
}

// application: any error, plus context explaining what we were doing
fn load(path: &str) -> Result<u64> {
    let text = std::fs::read_to_string(path).with_context(|| format!("reading {path}"))?;
    let mut total = 0;
    for (i, l) in text.lines().enumerate() {
        let (_, n) = parse_line(i + 1, l).context("parsing usage file")?;
        total += n;
    }
    Ok(total)
}

fn main() {
    std::fs::write("good.csv", "ada,10\nbob,32\n").unwrap();
    std::fs::write("bad.csv", "ada,10\nbob,thirty\n").unwrap();
    for p in ["good.csv", "bad.csv", "nope.csv"] {
        match load(p) {
            Ok(t) => println!("{p}: total {t}"),
            Err(e) => println!("{p}: error: {e:#}"), // {:#} prints the whole chain
        }
    }
    match parse_line(7, ",5") {
        Err(ParseError::MissingField { field, .. }) => println!("caller matched: missing {field}"),
        other => println!("{other:?}"),
    }
}

The second line is what a user wants to read: what the program was doing (parsing usage file), where (line 2), and the root cause, all from {:#} on the chain. SolvesEvery failure is visible in the signature; nothing is thrown past a caller that did not expect it.
CostsMore words than try/except at the top, and error types to design; ? keeps the middle short.
Common mistakeunwrap() everywhere in library code; or one giant error enum for a whole crate. Prefer one enum per module boundary (error design as a craft: {{Code design|n:3ef5c17b0d0d817b99a0ff9701ff30cd}}).
