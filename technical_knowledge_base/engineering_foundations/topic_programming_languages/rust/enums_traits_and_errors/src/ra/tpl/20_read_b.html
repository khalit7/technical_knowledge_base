2. Structs, enums and match: make illegal states unrepresentable

A struct is a record with named fields, like a dataclass. An enum in Rust is far more than Python's Enum: each variant can carry its own data, so one type says "a message is either text from a user, or a tool call with arguments, or an image of some size". This is called a sum type or tagged union. match takes it apart, and must cover every variant.

The design habit this enables matters more than the syntax. Python code often models state as one class with optional fields and a status string, and every method checks that the fields agree with the status. In Rust, give each state exactly the data it has. "Connected but no session id" or "failed with no error" then cannot be written at all:

What an enum costs in memory

The last three lines of that run are about memory: Option<u64> needs [[g:l_states|^size_of Option = (\d+)]] bytes, but Option<&u64> and Option<Box<u64>> fit in [[g:l_states|^size_of Option<&u64> = (\d+)]]. A second program, layout.rs, prints the size and alignment of each type here and finds where each variant's data sits (the address of a field minus the address of the value), so the figure is drawn to scale, one cube per byte:

  1. A tag costs a byte, and padding. Option<u8> is [[g:l_layout|^Option\s+size\s+(\d+)]] bytes: the u8 plus one tag byte saying Some or None. Option<u32> is [[g:l_layout|^Option\s+size\s+(\d+)]], with the u32 at offset [[g:l_layout|^Option: Some's u32 at offset (\d+)]]: a u32 must start at a multiple of 4, so the tag byte is followed by 3 bytes of padding.
  2. Option<u64>: 16 bytes for 8 of data. The u64 sits at offset [[g:l_layout|^Option: Some's u64 at offset (\d+)]] and is aligned to 8, so one tag byte costs 8 bytes in all. Every value of a u64 is a valid number, so the tag has nowhere else to go.
  3. Option<&u64>: no tag at all. [[g:l_layout|^Option<&u64>\s+size\s+(\d+)]] bytes, the same as &u64, and the same for Box. A reference is never null, so the all-zero pattern is free to mean None: the "null pointer optimisation", which the {{Option documentation|https://doc.rust-lang.org/std/option/index.html#representation}} guarantees for references, Box, function pointers and NonZero numbers. A bit pattern a type can never hold is called a niche. Safety without null costs nothing here.
  4. A String is three words. [[g:l_layout|^String\s+size\s+(\d+)]] bytes: a capacity, a pointer to the text on the heap, and a length. Taking a String of capacity 16 holding "timeout" apart word by word found them in that order on this build (the {{Vec documentation|https://doc.rust-lang.org/std/vec/struct.Vec.html#guarantees}} leaves the order unspecified).
  5. Conn: four variants in the same 24 bytes. An enum is as big as its largest variant, here Failed's String at offset [[g:l_layout|^Conn::Failed: error \(String, \d+ bytes\) at offset (\d+)]]. The others reuse the same bytes: Connecting's attempt and Connected's session_id both sit at offset [[g:l_layout|^Conn::Connected: session_id \(u64\) at offset (\d+)]]; Idle has no data. size_of::<Conn>() printed [[g:l_layout|^Conn\s+size\s+(\d+)]]: not one byte more than the String.
  6. The tag hides in the first word. For Failed the first word is the String's capacity ([[g:l_layout|^first word of Failed \{ error: "timeout" \}\s+(0x[0-9a-f]+)]], that is 16). For the other three it held [[g:l_layout|^first word of Idle\s+(0x[0-9a-f]+)]], ...01 and ...02: 263 and up, more than isize::MAX, and a capacity can never be that large (a Vec "panics if the new capacity exceeds isize::MAX bytes", and String::as_mut_vec exposes the Vec<u8> under a String). The compiler stored the tag in that niche.
  7. Option<Conn>: still 24. There are many unused capacities, so None::<Conn> simply takes the next one, [[g:l_layout|^first word of None::\s+(0x[0-9a-f]+)]]. Wrapping an enum in Option cost nothing either.

Recorded with rustc 1.94.0 on Linux x86-64 (the rest of the page used rustc 1.99.0 on the M1 Pro; the three sizes both runs print agree). Where the compiler puts a tag is not a stable guarantee, except the null pointer case: read size_of, do not rely on the layout. The heap buffer in steps 4 to 6 is drawn smaller than scale.

3. Option, Result and ?: errors as values

Rust has no None that can appear anywhere and no exceptions for expected failures. Two enums from the standard library carry them, written like any other enum:

  • Option<T> is Some(value) or None: maybe missing. dict.get, str.find and "first element" return one.
  • Result<T, E> is Ok(value) or Err(error): may fail. Parsing, I/O and network calls return one.

You cannot use the value inside without deciding what happens in the other case. The ? operator is the common decision: "if this is an Err, return it from my function now; otherwise give me the value". It is the explicit, typed version of letting an exception propagate. The recorded program on its three configurations (pick one on the figure):

  1. The call. main calls budget(&bad); bad has context = "8k".
  2. Into get_num. budget calls get_num(cfg, "context").
  3. The key is there. cfg.get("context") is Some("8k"); ok_or makes it Ok("8k"); ? unwraps it, so raw = "8k".
  4. The parse fails. "8k".parse::<u32>() returns Err(ParseIntError { kind: InvalidDigit }).
  5. The error is wrapped. map_err wraps it as Err(BadNumber { key: "context", source }). With no semicolon, that is get_num's return value.
  6. ? returns early. Back in budget, ? sees an Err and returns it from budget at once. Lines 31 and 32 never run: max_output is never read.
  7. main reports it. main's match takes the Err arm and prints [[g:l_errors|^(error: context.*?)\s+\(debug]] (the message is ConfigError's Display).
  1. The call. main calls budget(&missing); missing has no max_output.
  2. The first number parses. get_num(cfg, "context") finds "8192" and parses it: Ok(8192), so ? gives ctx = 8192.
  3. The second call. budget calls get_num(cfg, "max_output").
  4. The key is missing. cfg.get("max_output") is None; ok_or turns it into Err(Missing("max_output")); ? returns it from get_num immediately. Lines 24 to 26 never run.
  5. ? again. In budget, ? returns the same Err; line 32 never runs.
  6. main reports it. main prints [[g:l_errors|^(error: missing.*?)\s+\(debug]].
  1. The call. main calls budget(&good).
  2. The first number. "8192" parses: ctx = 8192.
  3. The second number. " 1024" is trimmed, then parses: out = 1024.
  4. The last line runs. Both ? found Ok, so budget reaches its last line: Ok(8192 - 1024).
  5. main prints the result. main prints [[g:l_errors|^(ok: .*)$]].

  • ok_or turns an Option into a Result; map_err converts one error type into another; unwrap_or supplies a default.
  • unwrap() and expect("why") say "this cannot fail; if it does, it is a bug": they panic, as the last line shows. Fine in tests and prototypes; in libraries prefer returning the error.
  • A custom error type is an enum with a Display implementation (the message) and the Error trait (ConfigError above). That is boilerplate, which is why two crates are everywhere (below).

? only works in a function that returns Result or Option, which catches people in main: E0277, "the ? operator can only be used in a function that returns Result or Option", and the compiler proposes the fix, fn main() -> Result<(), Box<dyn std::error::Error>> plus Ok(()) at the end.
