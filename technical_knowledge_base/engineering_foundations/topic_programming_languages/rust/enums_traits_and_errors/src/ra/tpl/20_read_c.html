4. Traits and generics: duck typing, checked

A trait names a set of methods a type promises to provide, like a Python Protocol, except that a type must say so explicitly (impl Tokenizer for Whitespace) and the compiler checks it before the program runs. A trait may have default methods written in terms of the others. A generic function takes a type parameter with a bound: fn total<T: Tokenizer> accepts any T that implements Tokenizer.

[[code:lang/traits.rs]] [[out:l_traits]]

There are two ways to call through a trait, and the choice is a real trade-off. The figure follows both through the compiled program:

  1. One generic, written once. mono.rs defines biggest<T: PartialOrd + Copy> once and calls it on slices of u8, i64, f64 and char.
  2. Compiled four times. The release binary's symbol table (nm, recorded below) holds four functions: biggest::<char>, <f64>, <i64> and <u8>. Each is compiled for its own type, so x > b is one machine comparison of that type: this is monomorphisation.
  3. A generic call is direct. biggest(&[1u8, 7, 3]) jumps straight to biggest::<u8>: the target is known when compiling, so it can be inlined and optimised with the caller.
  4. A trait object is a fat pointer. &Whitespace is [[g:l_traits|size_of &Whitespace = (\d+)]] bytes; &dyn Tokenizer is [[g:l_traits|&dyn Tokenizer = (\d+)]] (recorded above): one word points at the value, the second at the vtable of the value's type.
  5. One vtable per type. The compiler builds one table per type used as dyn Tokenizer: drop, size, align, then name → Chars::name, count → Chars::count, report → the default method. Every &dyn Tokenizer to a Chars shares it; Whitespace has its own.
  6. The call: a load and a jump. total_dyn is compiled once. Each t.count(d) loads the address of count from the table the second word points at, then calls it with the first word as self. The target is not known when compiling, so it cannot be inlined.
  7. The extra word is in the reference, not the value. A value is passed either by a plain reference (8 bytes, like &Whitespace: direct calls) or as &dyn Tokenizer (16 bytes: calls through the table); the value itself carries no table pointer, so you pay only where you write dyn. C++ puts its vtable pointer inside every object of a class with a virtual function instead (8 bytes grow to 16 on {{C++: classes, templates and the standard library|n:4055c17b0d0d818a9509f6035089a7e1}}, whose section 2 follows a virtual call through memory; the table and the loads are the same idea).
  8. What the table costs in a hot loop. The same closure called through a generic took [[g:t_iterbench|generic closure F: Fn\s+([0-9.]+)]] ns per element, through &dyn Fn [[g:t_iterbench|&dyn Fn closure\s+([0-9.]+)]] ns: about three times slower, because the call through the table blocks inlining (section 5 has the full measurement).

Section 5 measures what the vtable costs in a hot loop. Two real errors worth recognising. Use an operator the bound does not promise, and you get E0369, "binary operation > cannot be applied to type &T", with the help "consider restricting type parameter T with trait PartialOrd". Pass a type that does not implement the trait, and you get E0277, "the trait bound Whitespace: Tokenizer is not satisfied", pointing at the call and at the bound; Python would fail at run time, on the first call to the missing method.

The two errors in full
[[out:l_bound_err]][[out:l_notimpl_err]]
  • No inheritance. Share behaviour with default methods and generic functions, and share data by putting one struct inside another. Python programmers rarely miss class hierarchies after a week.
  • The standard traits matter: Debug, Clone, Copy, PartialEq, Eq, Hash, Ord, Default, Display, From/Into, Iterator. Most are derivable; implementing Display is Rust's __str__, Add its __add__ (Python's side of these hooks: {{Python: the data model and protocols|n:4055c17b0d0d816a8705e4d3f20b3da7}}). A missing standard trait is a common surprise, as in the prompt below: floats are not Ord.
  • The orphan rule: you may implement a trait for a type only if your crate defines the trait or the type. To add a foreign trait to a foreign type, wrap the type in a one-field struct of your own (the "newtype" pattern).

5. Iterators and closures: lazy pipelines that cost nothing

An iterator in Rust is any type with a next() method returning Option<Item>, the same protocol as Python's __next__ raising StopIteration. Adapters such as map, filter, zip, enumerate, take build a lazy pipeline, like a generator expression; a consumer (collect, sum, count, fold, a for loop) runs it. A closure is an anonymous function that can capture variables from where it is written: |x| x * 2 is Python's lambda x: x * 2, but with any number of statements.

What is new for a Python programmer is the cost, so it comes first. Rust's claim is that the iterator chain compiles to the same machine code as the hand-written loop. Why it costs nothing: one value, pulled from the end

The laziness is Python's; what makes it free is how the chain is built. lazy.rs runs the chain from iters.rs with a print inside each closure, then the same work the Python-list way, then with take(2); the figure replays its trace:

  1. Built: one small value, nothing ran. words.iter().filter(..).map(..) is a single value of [[g:l_lazy|one value of (\d+) bytes]] bytes whose type nests the stages: Map<Filter<Iter<&str>, closure>, closure> (type_name_of_val printed it). The closures are part of the type, so the compiler sees every call; no closure has run yet.
  2. collect pulls "Rust" through. collect asks Map for an item, Map asks Filter, Filter asks the slice iterator. "Rust" comes back: the filter keeps it, the map lowercases it, collect pushes "rust".
  3. "is" stops at the filter. The filter drops it and asks the slice for the next word itself; the map never sees "is".
  4. "fast", then "and". Each word goes all the way through before the next is read: the trace alternates filter, map, filter, map.
  5. "safe", "and", "fun", then the end. The slice runs out, next() returns None, and collect returns the 6 words. No list existed in between: the chain held one word at a time.
  6. The Python-list habit: filter everything first. Collecting after the filter runs it on all 7 words into a first Vec of 6.
  7. Then map, into a second Vec. The map runs 6 times over the first Vec: two full buffers, and the trace reads 7 filters, then 6 maps.
  8. take(2) stops early. With .take(2) before collect, pulling stops once "fast" is out: 3 words filtered, 2 mapped; "and", "safe", "and" and "fun" are never read.

Closures capture in the least demanding way that works, and the compiler records which in the closure's type: Fn (reads captured values: short above), FnMut (changes them: count), FnOnce (moves them out, so it can run once). move before a closure makes it take ownership of what it captures (consume), needed when the closure outlives the current function, as a thread's does ({{Rust: lifetimes, smart pointers, threads and unsafe|n:4055c17b0d0d8160aa32df9cda0aef03}}). A type with a next() method (Countdown) is Rust's generator: any struct can be an iterator.
