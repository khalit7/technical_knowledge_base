# `src/ra/`: code, recordings and generator for "Rust: enums, traits, errors and iterators"

Copied (`cp -R`) from the Rust language page's `src/ra/` (Part 1, "For Python programmers") and trimmed to the sections this page owns: strings, enums and `match`, `Option`/`Result`/`?`, traits and generics, iterators and closures, collections, testing, and nine of the twelve drill items. The language page's copy is unchanged.

Owned files in `../parts/`: `20_read_a.html` to `20_read_d.html` and `20_read_z.html` (the Reading tab, generated from `tpl/`) and `34_js_ra_data.js` (generated). Hand-written parts are listed in `../README.md`.

## Pipeline
1. `sh src/ra/run_all.sh` copies `code/` (and the topic root's `src/rosetta/data/chat.jsonl`, found by walking up to `topic_programming_languages`) to the scratch folder `pl/ra_enums/work`, compiles and runs every example there, and records each command and its combined output in `out/NAME.txt` (paths shortened). Steps: `steps/20_lang.sh` (sections 1 to 7 and the tokstat tests), `30_timing.sh` (the iterator benchmark, with the load average before and after), `40_drill.sh` (the nine prediction prompts: the Python and three Rust candidates each). Needs the toolchains in `versions.txt`; `sh src/ra/run_all.sh 30` reruns one step. Not rerun for this split: every output is the language page's recording of 2026-10-05.
1b. `sh src/ra/run_new.sh` (seconds) records the two programs added on 2026-11-07 for the 3D stages, `code/lang/layout.rs` (sizes, alignments, field offsets and each `Conn` variant's first word) and `code/lang/lazy.rs` (the chain from `iters.rs` with a print in each closure, eagerly, and with `take(2)`), into `out/l_layout.txt` and `out/l_lazy.txt`. It uses the `rustc` on PATH, not `lib.sh`'s pinned toolchain, and records `rustc --version` and `uname -sm` in the command; the recorded runs are rustc 1.94.0 on Linux x86-64.
2. `python3 src/ra/gen.py` turns `tpl/*.html` into the parts files, replacing `[[code:...]]`, `[[out:...]]`, `[[pr:...]]` (predict, then reveal), `[[g:...]]` (a value taken from an output) and `[[drill:ID]]` (a prediction prompt rendered statically, its recorded results in a closed block; notes from `content.py`), and writes `parts/34_js_ra_data.js` (the benchmark, `errors.rs` and its output for the `?` stepper, the strings run, and the layout, lazy-chain, traits and mono recordings that drive the three 3D stages). Never edit generated parts by hand.
3. `sh src/build.sh`, then `node src/check_stages.mjs` (the stages and the stepper play when scrolled into view, reach their last step with one list item per step, stop off screen, never move under reduced motion; the step lists' numbers equal the recordings), `node src/ra/check.mjs` (every control at 390 dark and 920 light with reduced motion; nothing changes without input; no errors, NaN, undefined or sideways scroll; every embedded output and data string equals its file; the stepper's last steps print the recorded lines; each prompt has exactly one candidate printing what Python prints, and it is the marked answer) and `sh html_utils/checkpage.sh <page folder>`.

Thread ids in panic messages, `HashMap` orders and timings change from run to run; the prose takes such values from the outputs through `[[g:...]]` or the JS reads them from the data. Prompt d09 needs the `HashMap` candidate's random order to differ from insertion order (6 keys, 1 chance in 720 per run); `check.mjs` fails if it ever coincides, and a rerun fixes it.
