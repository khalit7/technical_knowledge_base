2. Smart pointers and interior mutability

Single ownership and compile-time borrowing cover most code. For the rest, the standard library has types that own their contents in other ways, each with a cost:

TypeWhat it gives youCostPython analogue
Box<T>one owner, value on the heap; needed for recursive types and trait objectsone allocationevery object
Rc<T>shared ownership in one thread; freed when the last Rc goesa counter update per clone and dropreference counting
Arc<T>the same across threadsatomic counter updates (slower)reference counting in free-threaded CPython
Cell<T>, RefCell<T>interior mutability: change through a shared reference; RefCell checks the borrow rules at run timea flag check per borrow; a panic if the rules are broken(all objects are mutable)
Mutex<T>, RwLock<T>the same across threads, by lockinga lock per access; contentionthreading.Lock
Weak<T>a non-owning pointer to an Rc/Arc value; breaks cyclesupgrade() may find it goneweakref

Box, Rc and RefCell: handles on the stack, counted blocks on the heap

A recursive type needs Box, because a value that contains itself directly would have infinite size; with the Box each child is one 8-byte pointer, as the run below prints (size_of Box<Expr> = [[x:smart.box]]).

Rc: shared ownership is a counter beside the value. Cloning an Rc copies an 8-byte pointer and bumps a count; the value is freed when the count reaches 0. The stage steps through smart.rs: handles on the stack plate, the blocks they own on the heap floor, dots running along each owning pointer. The counts the program prints are marked printed; the others follow from the code. Positions and block sizes are illustrative.

  1. Box: one owner, a heap allocation. e is an Expr::Add holding two Boxes, and the Mul holds two more: a tree of heap allocations, each Box [[x:smart.box]] bytes, the Expr itself [[x:smart.expr]]. Printed: [[x:smart.eval]]. Dropping e frees the whole tree, owner by owner.
  2. Rc::new: count 1. Line [[x:smart.lines.new]]: one heap block holds the count and the Doc; shared is an [[x:smart.rc]]-byte pointer to it (Rc<Doc> = [[x:smart.rc]], printed). strong_count = 1.
  3. A clone copies the pointer: count 2. Line [[x:smart.lines.clone_a]], Rc::clone(&shared): copies the pointer and adds 1. The Doc and its String are not copied.
  4. A third handle, and a change through it. Lines [[x:smart.lines.clone_b]] and [[x:smart.lines.set]]: a third handle b; b.cache_hits.set(..) changes the shared value through Cell. Printed: strong_count inside = [[x:smart.inside]].
  5. A handle goes: count down, nothing freed. Line [[x:smart.lines.b_end]], b leaves its block: dropping an Rc subtracts 1. Printed: strong_count after = [[x:smart.after]], hits = [[x:smart.hits]]. The Doc is freed only when the last handle goes and the count reaches 0.
  6. Rc<RefCell<Vec>>: a borrow flag. Line [[x:smart.lines.log]]: log and its clone writer share one RefCell (count 2). Each borrow_mut() sets the flag to "one writer" while it lasts, and the pushes land: printed log = [[x:smart.log]].
  7. Two writers at once: a panic. Lines [[x:smart.lines.first]] and [[x:smart.lines.second]] hold two borrow_mut() at the same time. The flag already says "one writer", so the second one panics: [[x:smart.panic]], at [[x:smart.panic_at]].

The same program also shows Cell: b.cache_hits.set(...) changes the Doc through a shared Rc, which plain & would refuse. Cell does it by copying values in and out, never handing out a reference, so it needs no check at all; RefCell hands out references, so it must count them.

The panic is the price of RefCell: the same rule as compile-time borrowing, but discovered while the program runs. Rc<RefCell<T>> compiles in situations where plain references would not, and it is the most common way learners make a borrow error go away and turn it into a crash. So: Rc<RefCell<T>> compiles but can still panic because the exclusivity check moved from compile time to run time. try_borrow_mut returns an error instead of panicking ({{RefCell docs|https://doc.rust-lang.org/std/cell/struct.RefCell.html}}), for code that can recover.

Reference cycles leak

Reference counting cannot free a cycle, in Rust as in Python (where the cycle collector cleans up afterwards; Rust has none). Leaking memory is safe in Rust's sense, so the compiler allows it. The figure is leak.rs's two blocks: a pair of nodes that own each other, and the same pair with the back edge made Weak. (The {{C++ ownership page|n:4055c17b0d0d81819d74fa010e68ac2a}} replays the same cycle with shared_ptr and weak_ptr on its smart-pointer stage: Rc is shared_ptr without atomic counts, Arc with them.)

[[pr:l_leak|Which of the four nodes print "drop"?]]

Rule of thumb: ownership should form a tree. Back pointers (child to parent, node to previous) are Weak, or better, indexes into a Vec that owns all the nodes (an "arena"), which is how most Rust graph code is written. Miri (section 4) reports memory still allocated when a program ends, so it would flag this leak in a test.
