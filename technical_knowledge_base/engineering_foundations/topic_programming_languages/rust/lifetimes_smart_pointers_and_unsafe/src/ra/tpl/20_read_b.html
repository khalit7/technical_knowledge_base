1. Lifetimes: a contract the compiler checks at every call

A lifetime is the stretch of the program during which a reference is valid. The checker computes them itself almost everywhere. You write one, as 'a, only when a function returns a reference (or a struct holds one) and the compiler cannot tell which input it came from:

[[out:l_life_err]]

Read 'a as a name for "some region of the program". The fixed signature fn longest<'a>(a: &'a str, b: &'a str) -> &'a str says: the result is valid as long as both inputs are, so at each call 'a shrinks to the overlap of the two. Lifetimes generate no code; they are a contract the checker verifies at every call. The picture is that overlap, drawn for the two calls below.

The result's lifetime must fit inside both inputs': moving one use is the difference

Bars run from a value's creation to its end of scope; the blue bar is the borrow w holds, from the call to its last use. The compiler fits 'a to that bar and checks it against each input's bar.

Breaking the contract at a call site: b dies at the inner closing brace, but w, which may point into b, is used after it. The error names exactly the three points on the timeline: where b was borrowed, where it was dropped, where the borrow was used later.

When you write them: the three elision rules

The {{elision rules|https://doc.rust-lang.org/reference/lifetime-elision.html}} fill in the common cases, so most signatures carry no 'a:

RuleExampleFilled in as
1. Each input reference gets its own lifetime.fn f(a: &str, b: &str)fn f<'1, '2>(a: &'1 str, b: &'2 str)
2. Exactly one input lifetime: outputs get it.fn first_word(s: &str) -> &strthe result borrows from s
3. A method with &self: outputs get self's.fn name(&self) -> &strthe result borrows from self

So you write lifetimes when a function has two or more reference inputs and returns a reference, or a struct stores a reference (struct Token<'a> { text: &'a str } in life.rs). Rule 3 is the one that surprises: in a method it guesses self, even when the result can come from another argument.

What no lifetime can do

Annotations describe lifetimes and never extend them, so no 'a makes a reference to a value that is about to die:

Returning a reference to a local (dangle_err.rs, E0515)
[[code:lang/dangle_err.rs:1-4]] [[out:l_dangle_err]]

The fix is to return the owned String. That is the general rule of thumb: if "just add a lifetime" spreads 'a through many types, store an owned value instead; borrowing in structs is an optimisation for later.

'static: two meanings, one of which is a bound

&'static str is a reference valid for the whole program: string literals are &'static str because they live in the program's binary. T: 'static as a bound is weaker and far more common: T holds no borrow that could expire. Every owned type (String, Vec, Arc<Mutex<..>>) satisfies it, and is still freed whenever its owner drops it. This is the bound on std::thread::spawn and tokio::spawn, and the reason section 3's first error says "requires argument type to outlive 'static".

Further, for when you meet them (not demonstrated here)
  • '_, the anonymous lifetime: "the elided one", written where a type needs a lifetime parameter but you want elision, as in impl fmt::Display for Token<'_>.
  • T: 'a bounds say every reference inside T outlives 'a; they appear on structs holding generic references, and the compiler infers most of them.
  • Variance decides when a &'long T may be used where a &'short T is expected (always, for shared references) and why &mut T is stricter; the {{Rustonomicon's chapter on subtyping|https://doc.rust-lang.org/nomicon/subtyping.html}} is the reference.
  • Borrows end at their last use, not at the end of the block (non-lexical lifetimes); {{Rust: the essentials|n:3c65c17b0d0d8156bed9ead8a22f33b0}} animates this on its borrow timeline, and its Borrow-checker lab has the lifetime scenarios (returning a local reference, a missing lifetime, a borrow outliving its owner, a struct holding a reference).
