3. Threads without data races: Send and Sync

A data race is two threads touching the same memory at the same time, at least one of them writing, with nothing ordering them. Updates get lost or values tear. In CPython the GIL used to hide most of these; free-threaded Python 3.14 does not, and an unsynchronised counter there loses updates (measured on {{Python: concurrency, asyncio and the GIL|n:4055c17b0d0d81bdbee8c37d80b55a0e}}). Rust makes data races a compile error in safe code by applying the borrowing rule across threads: shared data may be read by many threads, and changed only through a type that synchronises (a lock or an atomic). What a race, a mutex and an atomic are at the OS level is taught on {{Concurrency: threads, locks, futexes, deadlock, and event-driven I/O|n:3f05c17b0d0d8112ad1af99308fa913f}}; this section is what Rust's types add.

The obvious Python translation, eight threads incrementing one counter, does not compile, and the three errors are the three problems:

race_err.rs
use std::thread;

fn main() {
    let mut counter = 0u64;
    let mut hs = vec![];
    for _ in 0..8 {
        hs.push(thread::spawn(|| for _ in 0..100_000 { counter += 1; }));
    }
    for h in hs { h.join().unwrap(); }
    println!("{counter}");
}

The two marker traits

Two marker traits carry the rule. They have no methods; the compiler implements them automatically for a type whose parts all qualify ({{std::marker::Send|https://doc.rust-lang.org/std/marker/trait.Send.html}}, {{the Rustonomicon on Send and Sync|https://doc.rust-lang.org/nomicon/send-and-sync.html}}):

  • Send: a value of this type may be moved to another thread.
  • Sync: a &T may be shared between threads (precisely, T is Sync if &T is Send).

thread::spawn requires its closure to be Send, so everything the closure captures must be. Rc is neither, because two threads updating its non-atomic counter at once would be a race; Arc uses atomic updates and is both. Moving an Rc into a thread is refused with E0277, "Rc<Vec<i32>> cannot be sent between threads safely", naming spawn's bound as the reason.

Predict before reading the columns: is Arc<RefCell<i32>> Send? Is a Mutex holding a Cell Sync?

TypeSendSyncWhy
i32, String, Vec<u8>, Box<i32>yesyesown their data; nothing shared behind them
&i32yesyesa shared reference is Send because i32 is Sync
Rc<i32>nonotwo clones in two threads would update the plain counter at once
Arc<i32>yesyesthe counter is updated atomically
Cell<i32>, RefCell<i32>yesnomay move to one thread; sharing would let two threads mutate unsynchronised
Arc<RefCell<i32>>nonoArc is only as shareable as its contents
Mutex<i32>, RwLock<i32>yesyesthe lock orders every access
Mutex<Cell<i32>>yesyesa Mutex makes a non-Sync value Sync (it needs only Send)
Arc<Mutex<Vec<u8>>>yesyesthe shared-mutable-state pattern

MutexGuard<i32>noyessome platforms require the locking thread to unlock
*const i32nonoraw pointers opt out; unsafe code must vouch with unsafe impl

The 25 "yes" cells are asserted in sendsync.rs, which compiles (all 25 "yes" claims compile); the 9 "no" cells are each refused with E0277 in sendsync_err.rs. Arc<T> is Send and Sync only when T is both; Mutex<T> is Sync when T is merely Send, which is how a lock makes unshareable data shareable. MutexGuard's reason is from its {{documentation|https://doc.rust-lang.org/std/sync/struct.MutexGuard.html}}.

A type you write gets Send and Sync for free when its fields have them. Only a type holding a raw pointer (a wrapper around a C handle, say) has to claim them by hand with unsafe impl Send for T {}, which is a promise the compiler cannot check: one of section 4's five unsafe operations.

lock() returns a guard that unlocks when dropped, and the data is reachable only through the guard, so you cannot forget the lock. What Ordering::Relaxed on the atomic means (and when you need stronger orderings) is memory order, taught on the {{OS concurrency page|n:3f05c17b0d0d8112ad1af99308fa913f}}; a counter needs only Relaxed. For data parallelism over a collection, the {{rayon|https://docs.rs/rayon}} crate turns iter() into par_iter(); {{Rust: speeding up Python with PyO3 and maturin|n:4055c17b0d0d81048311c87e9b76a78a}} uses it to parallelise the token counter inside a Python extension.

threads.rs (the five tools, with the full output)
threads.rs
use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::mpsc;
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // 1. spawn + join; `move` gives the thread its own copy of what it uses
    let docs = vec!["a b c", "d e", "f"];
    let handles: Vec<_> = docs.into_iter().enumerate().map(|(i, d)| {
        thread::spawn(move || (i, d.split_whitespace().count()))
    }).collect();
    let counts: Vec<_> = handles.into_iter().map(|h| h.join().unwrap()).collect();
    println!("spawned: {counts:?}");

    // 2. scoped threads may borrow local data, because they are joined before the scope ends
    let data = vec![1u64; 1_000_000];
    let (left, right) = data.split_at(data.len() / 2);
    let total = thread::scope(|s| {
        let a = s.spawn(|| left.iter().sum::<u64>());
        let b = s.spawn(|| right.iter().sum::<u64>());
        a.join().unwrap() + b.join().unwrap()
    });
    println!("scoped sum: {total}");

    // 3. shared mutable state: Arc (shared ownership across threads) + Mutex (one writer at a time)
    let counter = Arc::new(Mutex::new(0u64));
    let mut hs = vec![];
    for _ in 0..8 {
        let c = Arc::clone(&counter);
        hs.push(thread::spawn(move || for _ in 0..100_000 { *c.lock().unwrap() += 1; }));
    }
    for h in hs { h.join().unwrap(); }
    println!("mutex counter: {} (expected 800000)", *counter.lock().unwrap());

    // 4. an atomic does the same without a lock
    let hits = Arc::new(AtomicU64::new(0));
    thread::scope(|s| for _ in 0..8 { let h = &hits; s.spawn(move || for _ in 0..100_000 { h.fetch_add(1, Ordering::Relaxed); }); });
    println!("atomic counter: {}", hits.load(Ordering::Relaxed));

    // 5. channels: send values from many producers to one consumer
    let (tx, rx) = mpsc::channel();
    for id in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || tx.send(format!("worker {id} done")).unwrap());
    }
    drop(tx); // close our copy so the loop below ends when the workers finish
    let mut got: Vec<String> = rx.iter().collect();
    got.sort();
    println!("channel: {got:?}");
}

What the compiler does not prevent
Deadlocks (two threads each holding the lock the other needs), logic races (check-then-act with the lock released in between), and leaked memory are all possible in safe Rust. "Fearless" means no data races and no use after free, not no concurrency bugs.

Async is the other way to be concurrent: for thousands of network calls rather than CPU work, Rust uses async fn and a runtime library, almost always tokio. The same two traits decide what may cross .await points on a multi-threaded runtime (tokio::spawn needs Send + 'static); {{Rust: async with tokio, services with axum, and CLIs|n:4055c17b0d0d8148b863faa050cf5456}} owns it.
