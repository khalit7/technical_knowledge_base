Rust: lifetimes, smart pointers, threads and unsafe

How Rust's one aliasing rule is checked by lifetimes, carried across threads by Send and Sync, moved to run time by RefCell and Mutex, and left to you inside unsafe, with Miri to check it; every output recorded with rustc 1.99.0 on an Apple M1 Pro. The idea in one sentence. Rust has one rule, many readers or one writer, and no reference outlives what it points to; lifetimes let the compiler check it for references, Send and Sync carry it across threads, RefCell and Mutex move the check to run time, and inside unsafe it becomes your job, with Miri checking it in your tests.

1. Lifetimes: a contract the compiler checks at every call

A lifetime is the stretch of the program during which a reference is valid. The checker computes them itself almost everywhere. You write one, as 'a, only when a function returns a reference (or a struct holds one) and the compiler cannot tell which input it came from:

Read 'a as a name for "some region of the program". The fixed signature fn longest<'a>(a: &'a str, b: &'a str) -> &'a str says: the result is valid as long as both inputs are, so at each call 'a shrinks to the overlap of the two. Lifetimes generate no code; they are a contract the checker verifies at every call. The picture is that overlap, drawn for the two calls below.

The result's lifetime must fit inside both inputs': moving one use is the difference

Bars run from a value's creation to its end of scope; the blue bar is the borrow w holds, from the call to its last use. The compiler fits 'a to that bar and checks it against each input's bar.

Breaking the contract at a call site: b dies at the inner closing brace, but w, which may point into b, is used after it. The error names exactly the three points on the timeline: where b was borrowed, where it was dropped, where the borrow was used later.

life.rs
// 'a names "some region of the program". The signature promises: the result
// lives no longer than the shorter-lived of a and b.
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

// One input reference: the compiler fills in the lifetimes itself (elision).
fn first_word(s: &str) -> &str {
    s.split(' ').next().unwrap_or("")
}

// A struct that holds a reference must say how long it may live.
struct Token<'a> {
    text: &'a str,
}

fn main() {
    let a = String::from("tokens");
    let w;
    {
        let b = String::from("logits!");
        w = longest(&a, &b);
        println!("longest: {w}");
    }
    let t = Token { text: first_word("hello world") };
    let s: &'static str = "string literals live for the whole program";
    println!("{} | {}", t.text, s);
}

When you write them: the three elision rules

The elision rules fill in the common cases, so most signatures carry no 'a:

RuleExampleFilled in as
1. Each input reference gets its own lifetime.fn f(a: &str, b: &str)fn f<'1, '2>(a: &'1 str, b: &'2 str)
2. Exactly one input lifetime: outputs get it.fn first_word(s: &str) -> &strthe result borrows from s
3. A method with &self: outputs get self's.fn name(&self) -> &strthe result borrows from self

So you write lifetimes when a function has two or more reference inputs and returns a reference, or a struct stores a reference (struct Token<'a> { text: &'a str } in life.rs). Rule 3 is the one that surprises: in a method it guesses self, even when the result can come from another argument.

A method that returns its argument, refused under rule 3, and the fix (elide_self_err.rs, elide_self_fix.rs)

'static: two meanings, one of which is a bound

&'static str is a reference valid for the whole program: string literals are &'static str because they live in the program's binary. T: 'static as a bound is weaker and far more common: T holds no borrow that could expire. Every owned type (String, Vec, Arc<Mutex<..>>) satisfies it, and is still freed whenever its owner drops it. This is the bound on std::thread::spawn and tokio::spawn, and the reason section 3's first error says "requires argument type to outlive 'static".

Further, for when you meet them (not demonstrated here)
  • '_, the anonymous lifetime: "the elided one", written where a type needs a lifetime parameter but you want elision, as in impl fmt::Display for Token<'_>.
  • T: 'a bounds say every reference inside T outlives 'a; they appear on structs holding generic references, and the compiler infers most of them.
  • Variance decides when a &'long T may be used where a &'short T is expected (always, for shared references) and why &mut T is stricter; the Rustonomicon's chapter on subtyping is the reference.
  • Borrows end at their last use, not at the end of the block (non-lexical lifetimes); Rust: the essentials animates this on its borrow timeline, and its Borrow-checker lab has the lifetime scenarios (returning a local reference, a missing lifetime, a borrow outliving its owner, a struct holding a reference).

2. Smart pointers and interior mutability

Single ownership and compile-time borrowing cover most code. For the rest, the standard library has types that own their contents in other ways, each with a cost:

TypeWhat it gives youCostPython analogue
Box<T>one owner, value on the heap; needed for recursive types and trait objectsone allocationevery object
Rc<T>shared ownership in one thread; freed when the last Rc goesa counter update per clone and dropreference counting
Arc<T>the same across threadsatomic counter updates (slower)reference counting in free-threaded CPython
Cell<T>, RefCell<T>interior mutability: change through a shared reference; RefCell checks the borrow rules at run timea flag check per borrow; a panic if the rules are broken(all objects are mutable)
Mutex<T>, RwLock<T>the same across threads, by lockinga lock per access; contentionthreading.Lock
Weak<T>a non-owning pointer to an Rc/Arc value; breaks cyclesupgrade() may find it goneweakref

The panic is the price of RefCell: the same rule as compile-time borrowing, but discovered while the program runs. Rc<RefCell<T>> compiles in situations where plain references would not, and it is the most common way learners make a borrow error go away and turn it into a crash. So: Rc<RefCell<T>> compiles but can still panic because the exclusivity check moved from compile time to run time. try_borrow_mut returns an error instead of panicking (RefCell docs), for code that can recover.

fn eval(e: &Expr) -> f64 {
    match e {

        Expr::Add(a, b) => eval(a) + eval(b),
        Expr::Mul(a, b) => eval(a) * eval(b),

Reference cycles leak

Reference counting cannot free a cycle, in Rust as in Python (where the cycle collector cleans up afterwards; Rust has none). Leaking memory is safe in Rust's sense, so the compiler allows it.

Before and after: two nodes that own each other never reach 0; make the back edge Weak and both drop

Counts are leak.rs's printed values (cycle: x strong_count = 2; weak: x strong_count = 1, weak_count = 1); the code and the full output are below.

Predict, then reveal: Which of the four nodes print "drop"?
$ rustc --edition 2024 leak.rs && ./leak

Rule of thumb: ownership should form a tree. Back pointers (child to parent, node to previous) are Weak, or better, indexes into a Vec that owns all the nodes (an "arena"), which is how most Rust graph code is written. Miri (section 4) reports memory still allocated when a program ends, so it would flag this leak in a test.

leak.rs in full
leak.rs
use std::cell::RefCell;
use std::rc::{Rc, Weak};

struct Node {
    name: &'static str,
    next: RefCell<Option<Rc<Node>>>, // owning edge
    back: RefCell<Weak<Node>>,       // non-owning edge
}

impl Drop for Node {
    fn drop(&mut self) {
        println!("drop {}", self.name);
    }
}

fn node(name: &'static str) -> Rc<Node> {
    Rc::new(Node { name, next: RefCell::new(None), back: RefCell::new(Weak::new()) })
}

fn main() {
    {
        let x = node("x (cycle of Rc)");
        let y = node("y (cycle of Rc)");
        *x.next.borrow_mut() = Some(Rc::clone(&y)); // x -> y
        *y.next.borrow_mut() = Some(Rc::clone(&x)); // y -> x: a cycle
        println!("cycle: x strong_count = {}", Rc::strong_count(&x));
    } // our two handles go, but each node still owns the other: neither count reaches 0
    {
        let x = node("x (Weak back edge)");
        let y = node("y (Weak back edge)");
        *x.next.borrow_mut() = Some(Rc::clone(&y)); // x owns y
        *y.back.borrow_mut() = Rc::downgrade(&x); // y only points back at x
        println!("weak: x strong_count = {}, weak_count = {}", Rc::strong_count(&x), Rc::weak_count(&x));
        println!("y.back.upgrade() is {}", y.back.borrow().upgrade().map(|n| n.name).unwrap_or("gone"));
    }
    println!("end of main: the Rc cycle was never dropped (a leak, which safe Rust allows)");
}

3. Threads without data races: Send and Sync

A data race is two threads touching the same memory at the same time, at least one of them writing, with nothing ordering them. Updates get lost or values tear. In CPython the GIL used to hide most of these; free-threaded Python 3.14 does not, and an unsynchronised counter there loses updates (measured on Python: concurrency, asyncio and the GIL). Rust makes data races a compile error in safe code by applying the borrowing rule across threads: shared data may be read by many threads, and changed only through a type that synchronises (a lock or an atomic). What a race, a mutex and an atomic are at the OS level is taught on Concurrency: threads, locks, futexes, deadlock, and event-driven I/O; this section is what Rust's types add.

The obvious Python translation, eight threads incrementing one counter, does not compile, and the three errors are the three problems:

race_err.rs

        hs.push(thread::spawn(|| for _ in 0..100_000 { counter += 1; }));
    }
    for h in hs { h.join().unwrap(); }
    println!("{counter}");
}

The two marker traits

Two marker traits carry the rule. They have no methods; the compiler implements them automatically for a type whose parts all qualify (std::marker::Send, the Rustonomicon on Send and Sync):

  • Send: a value of this type may be moved to another thread.
  • Sync: a &T may be shared between threads (precisely, T is Sync if &T is Send).

thread::spawn requires its closure to be Send, so everything the closure captures must be. Rc is neither, because two threads updating its non-atomic counter at once would be a race; Arc uses atomic updates and is both. Moving an Rc into a thread is refused with E0277, "Rc<Vec<i32>> cannot be sent between threads safely", naming spawn's bound as the reason.

The 25 "yes" cells are asserted in sendsync.rs, which compiles (all 25 "yes" claims compile); the 9 "no" cells are each refused with E0277 in sendsync_err.rs. threads.rs (the five tools, with the full output)
threads.rs
use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::mpsc;
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // 1. spawn + join; `move` gives the thread its own copy of what it uses
    let docs = vec!["a b c", "d e", "f"];
    let handles: Vec<_> = docs.into_iter().enumerate().map(|(i, d)| {
        thread::spawn(move || (i, d.split_whitespace().count()))
    }).collect();
    let counts: Vec<_> = handles.into_iter().map(|h| h.join().unwrap()).collect();
    println!("spawned: {counts:?}");

    // 2. scoped threads may borrow local data, because they are joined before the scope ends
    let data = vec![1u64; 1_000_000];
    let (left, right) = data.split_at(data.len() / 2);
    let total = thread::scope(|s| {
        let a = s.spawn(|| left.iter().sum::<u64>());
        let b = s.spawn(|| right.iter().sum::<u64>());
        a.join().unwrap() + b.join().unwrap()
    });
    println!("scoped sum: {total}");

    // 3. shared mutable state: Arc (shared ownership across threads) + Mutex (one writer at a time)
    let counter = Arc::new(Mutex::new(0u64));
    let mut hs = vec![];
    for _ in 0..8 {
        let c = Arc::clone(&counter);
        hs.push(thread::spawn(move || for _ in 0..100_000 { *c.lock().unwrap() += 1; }));
    }
    for h in hs { h.join().unwrap(); }
    println!("mutex counter: {} (expected 800000)", *counter.lock().unwrap());

    // 4. an atomic does the same without a lock
    let hits = Arc::new(AtomicU64::new(0));
    thread::scope(|s| for _ in 0..8 { let h = &hits; s.spawn(move || for _ in 0..100_000 { h.fetch_add(1, Ordering::Relaxed); }); });
    println!("atomic counter: {}", hits.load(Ordering::Relaxed));

    // 5. channels: send values from many producers to one consumer
    let (tx, rx) = mpsc::channel();
    for id in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || tx.send(format!("worker {id} done")).unwrap());
    }
    drop(tx); // close our copy so the loop below ends when the workers finish
    let mut got: Vec<String> = rx.iter().collect();
    got.sort();
    println!("channel: {got:?}");
}

What the compiler does not prevent
Deadlocks (two threads each holding the lock the other needs), logic races (check-then-act with the lock released in between), and leaked memory are all possible in safe Rust. "Fearless" means no data races and no use after free, not no concurrency bugs.

Async is the other way to be concurrent: for thousands of network calls rather than CPU work, Rust uses async fn and a runtime library, almost always tokio. The same two traits decide what may cross .await points on a multi-threaded runtime (tokio::spawn needs Send + 'static); Rust: async with tokio, services with axum, and CLIs owns it.

4. unsafe, and checking it with Miri

Some correct code cannot be proved safe by the compiler: the inside of Vec, calls into C libraries, hardware access. Inside an unsafe block you may do five extra things, the "unsafe superpowers" (Rust Book 20.1): dereference a raw pointer; call an unsafe function; access or modify a mutable static; implement an unsafe trait (such as Send, section 3); access fields of a union. Nothing else changes: "unsafe doesn't turn off the borrow checker or disable any of Rust's other safety checks".

unsafe_ok.rs
fn main() {
    let v = vec![10u32, 20, 30];
    let p: *const u32 = v.as_ptr(); // making a raw pointer is safe
    let second = unsafe { *p.add(1) }; // dereferencing it is not: we promise it is in bounds
    println!("second = {second}");
    // A safe API built on unsafe: split_at_mut hands out two &mut halves of one slice,
    // which the borrow checker cannot prove disjoint by itself.
    let mut a = [1, 2, 3, 4];
    let (l, r) = a.split_at_mut(2);
    l[0] += 100;
    r[0] += 100;
    println!("{a:?}");
}
$ rustc --edition 2024 unsafe_ok.rs && ./unsafe_ok

A small unsafe core behind a safe API: split_at_mut's halves can never overlap

That is the pattern to aim for: a small unsafe core with a stated invariant ("the two halves never overlap"), wrapped in a safe API that cannot be used to break it (split_at_mut docs: it panics if mid > len). Because unsafe is a keyword, every such place can be found with a text search and reviewed.

When you get it wrong: Miri

Breaking an invariant is undefined behaviour, exactly as in C++: the program may do anything, including appear to work. This program reads one element past the end of a vector, and then reads a freed vector:

main.rs
// Undefined behaviour that compiles and "works": reading one element past the end
// through a raw pointer, and using a pointer after its Vec was freed.
fn main() {
    let v = vec![10u32, 20, 30];
    let p = v.as_ptr();
    let past_end = unsafe { *p.add(3) }; // out of bounds: UB
    println!("read past the end: {past_end}");
    let q = {
        let w = vec![1u32, 2, 3];
        w.as_ptr()
    }; // w freed here; q dangles
    let after_free = unsafe { *q }; // use after free: UB
    println!("read after free: {after_free}");
}
