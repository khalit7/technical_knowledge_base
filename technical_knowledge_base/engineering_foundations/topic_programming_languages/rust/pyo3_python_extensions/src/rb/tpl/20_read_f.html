Read it as a story. Steps 1 to 3 move only the token loop: a 3x gain. Step 1 calls Rust 199,992 times (once per message); step 2 makes one call but Vec<String> copies all 25 million characters first, so its counting phase is slower than step 1's and end to end the two are within noise; step 3 borrows &str views and barely beats step 1, because once the loop is in Rust the program is waiting on json.loads. Step 4 moves the parsing too: Python reads the file as bytes and makes one call; serde parses each line straight into a typed struct, and the program runs times faster than the Python version. Step 5 releases the GIL and splits the file over 8 rayon threads. The root's own whole-file PyO3 variant measured s (one thread) and s (4 threads), in line with steps 4 and 5.

Predict: step 5 runs on 8 threads. Why is it about 2x faster than step 4 and not 8x?

The phases (from ladder.py --phases): the Rust part fell from ms to ms (x on a busy laptop with 2 of its 10 cores slower efficiency cores). What did not shrink is everything else in the process: starting Python and importing tokrs ( ms on its own, measured with hyperfine), reading the file, building the result dict and printing.
