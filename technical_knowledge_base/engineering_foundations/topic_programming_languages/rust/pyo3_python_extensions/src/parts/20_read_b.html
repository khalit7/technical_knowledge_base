1. Is it worth it? Profile, then do the arithmetic

On import, CPython calls a function in an extension module named PyInit_<name>, which hands back a module object whose functions are machine code. Writing one costs a second language, a compiler in your build and a wheel per platform (section 12), so do it only when a profile says so. Finding the hot function and trying the cheap wins first (a better algorithm, a built-in such as re or collections.Counter, NumPy, an existing library) is {{Python: CPython internals and performance|n:4055c17b0d0d8111872ad7101b7e3c22}}; Rust comes after those, for a hot loop that is left and that no library already does.

The hero's first two bars are Amdahl's law: if a fraction p of the time is sped up s times, the whole program speeds up 1 / ((1 - p) + p/s). The token loop was % of the pure-Python run (p = ), so even an infinitely fast loop leaves the other % and the best this change alone can give is 1 / (1 - p) = x; we measured x end to end. To go further, the parsing has to move too.

Worth it when
a profile shows one hot path you own, it is not array arithmetic NumPy already does, it runs often (a tokenizer, a parser, a sampler, a graph walk), and you can pass it big batches.
Not worth it when
the time is in I/O or the network, a library already does it (orjson, polars, pyarrow), or the hot code calls back into Python objects on every step.
What it costs
A Rust toolchain in your build (about 10 s for a clean build here), wheels per platform, and a team that can read Rust.

2. Your first extension: PyO3 and maturin

PyO3's macros (code generators run by the compiler, written #[...]) turn an ordinary Rust function into a Python-callable one; maturin compiles the crate and packs the library into a wheel (the .whl zip pip installs). The root page's {{Toolchain atlas|n:3c65c17b0d0d81a2bb1ac0bc8aeb6aa9}} tab has the first run recorded: maturin new --bindings pyo3 tokrs writes Cargo.toml, pyproject.toml, src/lib.rs and a GitHub Actions workflow. This page's project, tokrs, grew from that skeleton.

The 10 s is mostly compiling PyO3, the NumPy bindings, rayon and serde once; after that an edit to lib.rs rebuilds in a few seconds. maturin develop installs the wheel as editable, so you rerun it after each Rust change and then restart the interpreter or notebook kernel: a process cannot unload a shared library it has loaded, so importlib.reload will not pick up the new build.

3. Functions and modules: #[pyfunction], #[pymodule]

Step 1 of the token counter: the root program's token loop as plain Rust, and a thin function Python can call.

ext/src/lib.rs
/// Tokens = maximal runs of ASCII letters or digits (rule 3 of PROGRAM.md).
/// Non-ASCII characters are UTF-8 bytes >= 0x80, so a byte loop gives the char answer.
fn tokens(s: &[u8]) -> u64 {
    let mut n = 0;
    let mut inside = false;
    for &b in s {
        let t = b.is_ascii_alphanumeric();
        if t && !inside {
            n += 1;
        }
        inside = t;
    }
    n
}
ext/src/lib.rs
/// Step 1: one message per call. `&str` borrows the Python string's UTF-8 bytes.
#[pyfunction]
fn count_tokens(text: &str) -> u64 {
    tokens(text.as_bytes())
}

#[pyfunction] generates the glue: a C-level function that takes Python's argument objects, converts each to the Rust parameter type (&str here), calls your function, and converts the u64 result back into a Python int. The /// doc comment becomes the docstring. The module lists what it exports:

ext/src/lib.rs
#[pymodule]
mod tokrs {
    #[pymodule_export]
    use super::{
        count_bytes, count_bytes_owned, count_many, count_many_owned, count_tokens, counts_array,
        counts_list, dict_total, dict_total_owned, first_token_len, noop, parse_line, sum_sq_array, sum_sq_list, tally_bytes,
        tally_bytes_detached, tally_bytes_parallel, tally_file, total_len, total_len_owned, SharedCounter, Counter, MalformedLine,
    };
}

The #[pymodule] name (mod tokrs), the library name in Cargo.toml and module-name in pyproject.toml must agree, because CPython looks for PyInit_tokrs when you import tokrs; a mismatch makes the import fail.

What Python sees when the types are wrong

Python has no compiler to stop count_tokens(5), so the glue checks every argument at run time and raises TypeError. Nine wrong and right calls, run for real, gave four lessons.

Predict the nine calls, then reveal the real output
c2_types.py
import tokrs

calls = [
    'tokrs.count_tokens(5)',
    'tokrs.count_tokens(b"raw bytes")',
    'tokrs.count_tokens(text="keyword works")',
    'tokrs.count_many(["fine", 3])',
    'tokrs.count_many(("a", "tuple"))',
    'tokrs.count_many_owned(("a", "tuple"))',
    'tokrs.count_many_owned("abc")',
    'tokrs.count_bytes("a str")',
    'tokrs.count_tokens("\\ud800 lone surrogate")',
]
for c in calls:
    try:
        r = eval(c)
        print(f"{c}\n  -> {r!r}")
    except Exception as e:
        notes = "".join(f" ({n})" for n in getattr(e, "__notes__", []))
        print(f"{c}\n  -> {type(e).__name__}: {e}{notes}")

(1) PyO3 adds a note naming the parameter (while processing 'text', shown by Python 3.11+ as an exception note). (2) &Bound<PyList> accepts exactly a list, so a tuple is refused, while Vec<String> accepts any sequence but deliberately refuses a str, which is also a sequence and a classic bug. (3) Inside count_many the item check runs after argument parsing, so its error has no note: say which item failed in your own messages. (4) A str holding a lone surrogate (legal in Python, not in UTF-8) cannot become &str and raises UnicodeEncodeError.

The types in those signatures

Rust typeWhat it isPython analogy
Python<'py>A zero-size token proving this thread is attached to the interpreter (holds the GIL on a normal build). You get it as a parameter or from a Bound.Being inside the interpreter at all
Bound<'py, T>A strong reference to a Python object of type T (PyList, PyDict, PyAny), usable only while attached. Dropping it decrements the refcount.Any ordinary variable holding an object
Py<T>The same reference without the 'py lifetime: can be stored in a struct or sent to another thread; call .bind(py) to use it.An object kept in a global or a queue

The 'py is a lifetime ({{Rust: lifetimes, smart pointers, threads and unsafe|n:4055c17b0d0d8160aa32df9cda0aef03}}): the compiler uses it to stop a Bound escaping the region where the interpreter is attached. You rarely write it except in return types like Bound<'py, PyDict>.
