Rust: speeding up Python with PyO3 and maturin

The slow part of a Python program moved into a Rust extension one measured step at a time: one function, conversions and NumPy, errors, classes, the GIL and threads, free-threaded Python, then stubs, tests and wheels anyone can pip install. Every output is a real run (CPython 3.14.8 and 3.14.8t, Rust 1.99.0, PyO3 0.29.3, maturin 1.15.0) on an Apple M1 Pro. A child of Rust: the essentials. Data as of October 2026. Reading: 38 min, plus 13 in closed details.

A Rust extension pays off only when the whole hot path crosses into Rust in one big call, borrowing Python's memory instead of copying it and releasing the GIL while it works; moving one function inside a Python loop leaves the program waiting on the Python that is left.

You need: ownership, borrowing and Result from Rust: the essentials; String against &str, Result and ? from Rust: enums, traits, errors and iterators; lifetimes, Mutex and Send from Rust: lifetimes, smart pointers, threads and unsafe. On the Python side, profiling and why the interpreter is slow are Python: CPython internals and performance; the GIL and the free-threaded build are Python: concurrency, asyncio and the GIL; wheel tags and publishing are Python: typing, uv, packaging and the toolchain.

1. Is it worth it? Profile, then do the arithmetic

On import, CPython calls a function in an extension module named PyInit_<name>, which hands back a module object whose functions are machine code. Writing one costs a second language, a compiler in your build and a wheel per platform (section 12), so do it only when a profile says so. Finding the hot function and trying the cheap wins first (a better algorithm, a built-in such as re or collections.Counter, NumPy, an existing library) is Python: CPython internals and performance; Rust comes after those, for a hot loop that is left and that no library already does.

The hero's first two bars are Amdahl's law: if a fraction p of the time is sped up s times, the whole program speeds up 1 / ((1 - p) + p/s). The token loop was % of the pure-Python run (p = ), so even an infinitely fast loop leaves the other % and the best this change alone can give is 1 / (1 - p) = x; we measured x end to end. To go further, the parsing has to move too.

Worth it when
a profile shows one hot path you own, it is not array arithmetic NumPy already does, it runs often (a tokenizer, a parser, a sampler, a graph walk), and you can pass it big batches.
Not worth it when
the time is in I/O or the network, a library already does it (orjson, polars, pyarrow), or the hot code calls back into Python objects on every step.
What it costs
A Rust toolchain in your build (about 10 s for a clean build here), wheels per platform, and a team that can read Rust.

2. Your first extension: PyO3 and maturin

PyO3's macros (code generators run by the compiler, written #[...]) turn an ordinary Rust function into a Python-callable one; maturin compiles the crate and packs the library into a wheel (the .whl zip pip installs). The root page's Toolchain atlas tab has the first run recorded: maturin new --bindings pyo3 tokrs writes Cargo.toml, pyproject.toml, src/lib.rs and a GitHub Actions workflow. This page's project, tokrs, grew from that skeleton.

The stage (Fig. 1) follows tokrs from its source files to import tokrs; every name and number in the steps is from the recorded build (outputs/b1_develop.txt, b3_wheel.txt, b4_wheel_files.txt).

  1. The crate. Three files: Cargo.toml (the Rust package: crate-type = ["cdylib"] and its five dependencies), pyproject.toml (names maturin as the build backend) and src/lib.rs, the code. The hand-written stub tokrs.pyi sits beside them (section 11).
  2. cargo compiles everything once. maturin runs cargo, which compiles PyO3, the NumPy bindings, rayon, serde and lib.rs in release mode: Finished `release` profile [optimized] target(s) in 9.25s on a clean build, 10.32 s for the whole command. After that an edit to lib.rs rebuilds in a few seconds.
  3. One shared library. The result is tokrs.cpython-314-darwin.so, 1,012,496 bytes of machine code. otool -L lists only libiconv and libSystem: it does not link to libpython, and finds Python's C API in the process that loads it.
  4. maturin packs a wheel. A zip of 8 files: the library, __init__.py, the stub as __init__.pyi, py.typed, and the metadata (METADATA, WHEEL, RECORD and a software bill of materials). Its name carries the tags pip matches: tokrs-0.1.0-cp314-cp314-macosx_11_0_arm64.whl (section 12).
  5. Installed into the venv. maturin develop installs that wheel into the active virtual environment as editable (Installed tokrs-0.1.0); maturin build --release writes it to dist/ instead, which is what you ship.
  6. import tokrs. CPython finds the library in site-packages/tokrs/ and calls its PyInit_tokrs, which returns a module whose functions are machine code. After each Rust change, rerun maturin develop and restart the interpreter or notebook kernel: a process cannot unload a shared library it has loaded, so importlib.reload will not pick up the new build.

3. Functions and modules: #[pyfunction], #[pymodule]

Step 1 of the token counter: the root program's token loop as plain Rust, and a thin function Python can call.

ext/src/lib.rs
/// Tokens = maximal runs of ASCII letters or digits (rule 3 of PROGRAM.md).
/// Non-ASCII characters are UTF-8 bytes >= 0x80, so a byte loop gives the char answer.
fn tokens(s: &[u8]) -> u64 {
    let mut n = 0;
    let mut inside = false;
    for &b in s {
        let t = b.is_ascii_alphanumeric();
        if t && !inside {
            n += 1;
        }
        inside = t;
    }
    n
}
ext/src/lib.rs
/// Step 1: one message per call. `&str` borrows the Python string's UTF-8 bytes.
#[pyfunction]
fn count_tokens(text: &str) -> u64 {
    tokens(text.as_bytes())
}

#[pyfunction] generates the glue: a C-level function that takes Python's argument objects, converts each to the Rust parameter type (&str here), calls your function, and converts the u64 result back into a Python int. The /// doc comment becomes the docstring. The module lists what it exports:

4. Crossing the boundary: what each conversion costs

A Python str is an object on Python's heap with a refcount, a length and its characters in one fixed width (1, 2 or 4 bytes each, whichever fits the widest character; PEP 393). A Rust &str is just a pointer and a length into UTF-8 bytes. So every argument crosses in one of two ways:

  • Borrowed (a view): Rust gets a pointer into memory Python owns: &str from a str, &[u8] from bytes, a NumPy array view. No allocation, no copy, but the view only lives for the call.
  • Owned (a copy): Rust builds its own value: String, Vec<T>, HashMap<K, V>, one allocation per string and one conversion per element. The value can then outlive the call, move to another thread, be stored in a struct.

The stage (Fig. 2) sends one call across the boundary in each of four signatures, with three illustrative items: the strings of rule 3 and three small floats. The objects follow what PyO3 0.29 and CPython 3.14 do (the UTF-8 cache is filled by PyUnicode_AsUTF8AndSize); the towers on the boundary are the measured cost per item from the table below, not the cost of these three items.

  1. Two heaps and a boundary. Python's objects sit on the left plate: a list holding three str objects ("café", "x86_64", "v2.1 C++"). Rust works on the right plate, inside the call. Crossing costs something even with nothing to convert: an empty call, noop(), took 25.9 ns.
  2. Copied: Vec<String>. count_many_owned(texts: Vec<String>): PyO3 visits each str, asks CPython for its UTF-8 bytes (ASCII text already is UTF-8; "café" is encoded once, 5 bytes, and the copy cached inside the object), allocates a Rust String and copies the bytes in: three allocations, 19 bytes. Measured: 72.7 ns per string.
  3. Borrowed: &str views. count_many(texts: &Bound<PyList>): Rust gets a pointer and a length into each string's UTF-8 bytes, inside the Python objects. No allocation, no copy: 9.4 ns per string, 8x less than the copy. The views end with the call, and the compiler will not let one escape.
  4. A list of floats: unbox every object. sum_sq_list(xs: Vec<f64>): a list of floats is an array of pointers to separate 24-byte objects (a refcount, a type pointer, the 8-byte double). PyO3 visits each object and copies its double into one new Vec: 6.70 ns per float.
  5. A NumPy array: one buffer, one pointer. sum_sq_array(xs: PyReadonlyArray1<f64>): the array is a small header plus one contiguous buffer of raw f64 values. rust-numpy checks the dtype once and as_slice() hands Rust a pointer and a length; nothing crosses per element. 0.97 ns per float, and most of that is the sum itself.
  6. The result crosses back. Rust's answer becomes new Python objects on the left: the Vec<u64> of token counts (1, 2, 3) a new list of ints (small ints come from CPython's cache, so no new int objects), the sum of squares (8.75) one new float.
  7. The copies are freed. When the call returns, Rust drops the Strings and the Vec it built for this call; the views simply end. Python's objects are untouched either way.

Three rules fall out. Batch: one crossing costs about as much as counting a whole message, so call once per list, not once per item. Borrow: a copy costs x a view per string; take &str, &[u8], &Bound<PyList> and array views unless Rust must keep the data. Convert once, at the edge: if the data goes back and forth, keep it on one side (as a Rust object behind a #[pyclass], section 7, or as a NumPy array). Copy anyway when Rust must keep the data after the call (store it in a #[pyclass], or hand it to a thread that outlives the call); views of immutable str and bytes may even be read with the GIL released, as tally_bytes_detached does (section 8).

5. NumPy arrays without copies (rust-numpy)

A Python list of floats is an array of pointers to separate float objects, each 24 bytes with its own refcount; converting it visits every object. A NumPy array is one contiguous block of raw f64 values plus a small header (shape, strides, dtype). The numpy crate (rust-numpy 0.29.0, the release matching PyO3 0.29) lets Rust read that block in place:

ext/src/lib.rs
/// Sum of squares from a Python list: every float is converted into a new Vec<f64>.
#[pyfunction]
fn sum_sq_list(xs: Vec<f64>) -> f64 {
    xs.iter().map(|x| x * x).sum()
}

/// The same from a NumPy array: a read-only view of NumPy's own buffer, zero copies.
#[pyfunction]
fn sum_sq_array(xs: PyReadonlyArray1<'_, f64>) -> PyResult<f64> {
    let s = xs.as_slice()?; // error if the array is not contiguous
    Ok(s.iter().map(|x| x * x).sum())
}

/// Returning results: a Vec<u64> becomes a Python list (one int object per element) ...
#[pyfunction]
fn counts_list(texts: &Bound<'_, PyList>) -> PyResult<Vec<u64>> {
    count_many(texts)
}

/// ... or a NumPy array that takes over the Vec's buffer without copying it.
#[pyfunction]
fn counts_array<'py>(py: Python<'py>, texts: &Bound<'py, PyList>) -> PyResult<Bound<'py, PyArray1<u64>>> {
    Ok(count_many(texts)?.into_pyarray(py))
}

/// Dicts: `HashMap<String, u64>` copies every key into a new String ...
#[pyfunction]
fn dict_total_owned(d: HashMap<String, u64>) -> u64 {
    d.values().sum()
}

/// ... while iterating the `PyDict` in place only reads the values.
#[pyfunction]
fn dict_total(d: &Bound<'_, PyDict>) -> PyResult<u64> {
    let mut s = 0;
    for (_k, v) in d.iter() {
        s += v.extract::<u64>()?;
    }
    Ok(s)
}

PyReadonlyArray1<f64> checks the dtype and takes a shared borrow of the array (rust-numpy tracks borrows so Rust cannot write to an array Python code also holds as read-only); as_slice() gives a plain &[f64] when the memory is contiguous. On a million floats: list ns per element, array ns. Returning works the other way: into_pyarray hands a Vec's buffer to NumPy without copying.

Rust lost to NumPy here, and that is the lesson
np.dot(x, x) took ns per element, x faster than the Rust loop. The Rust compiler may not reorder floating-point additions (the result would change in the last bits; Numerical computing says why), so .sum() runs one add at a time; NumPy calls a BLAS routine that keeps several partial sums in SIMD registers. Do not port what NumPy, PyTorch or polars already do; port the loops they cannot express.

6. Errors become exceptions; panics become PanicException

Return PyResult<T> and an Err(PyErr) is raised as an exception when the call returns. For your own error kinds, declare a Python exception class from Rust:

7. Classes: #[pyclass] keeps Rust state between calls

When data goes back and forth, keep it on one side. A #[pyclass] is a Rust struct that Python sees as a class: the Python object owns the struct, methods run on it in place, and the per-user table never crosses the boundary until you ask for a result.

ext/src/lib.rs
/// A running per-user counter that lives across calls.
#[pyclass(module = "tokrs")]
struct Counter {
    per_user: HashMap<String, u64>,
    lines: u64,
}

#[pymethods]
impl Counter {
    #[new]
    fn new() -> Self {
        Counter { per_user: HashMap::new(), lines: 0 }
    }

    /// Add one message. `&mut self`: PyO3 checks at run time that nobody else holds it.
    fn add(&mut self, user: &str, text: &str) {
        self.lines += 1;
        *self.per_user.entry(user.to_owned()).or_insert(0) += tokens(text.as_bytes());
    }

    /// The n heaviest users, ties by id (rule 5).
    #[pyo3(signature = (n=5))]
    fn top(&self, n: usize) -> Vec<(String, u64)> {
        let mut v: Vec<(String, u64)> = self.per_user.iter().map(|(u, c)| (u.clone(), *c)).collect();
        v.sort_by(|a, b| b.1.cmp(&a.1).then_with(|| a.0.cmp(&b.0)));
        v.truncate(n);
        v
    }

    #[getter]
    fn total(&self) -> u64 {
        self.per_user.values().sum()
    }

    fn __len__(&self) -> usize {
        self.per_user.len()
    }

    fn __repr__(&self) -> String {
        format!("Counter(users={}, lines={}, tokens={})", self.per_user.len(), self.lines, self.total())
    }
}

#[new] is __init__ (strictly __new__), #[getter] makes a read-only property, and methods named like Python's special methods (__len__, __repr__) become them. &self methods read; &mut self methods write. Python has no borrow checker, so PyO3 enforces Rust's rule (many readers or one writer) at run time with a flag in each object.

8. Releasing the GIL, and parallel Rust with rayon

On the normal build only the thread holding the GIL may touch Python objects (Python: concurrency, asyncio and the GIL owns the lock itself). While your Rust function runs, the calling thread still holds it, so four Python threads calling the same Rust function take turns. But a function that only touches Rust data (bytes already borrowed, a Vec, a HashMap) does not need the interpreter: py.detach(closure) releases the GIL, runs the closure, and takes it back.

ext/src/lib.rs
/// Step 4: the same work with the GIL released. `py.detach` runs the closure
/// detached from the interpreter, so other Python threads keep running.
#[pyfunction]
fn tally_bytes_detached<'py>(py: Python<'py>, data: &[u8]) -> PyResult<Report<'py>> {
    let t = py.detach(|| tally(data, 1));

Parallelism inside one call: rayon

If the caller is single-threaded, Rust can split the work itself. rayon turns an iterator into a parallel one (.into_par_iter()) and runs it on a pool of OS threads, one per core by default; reduce merges the partial tallies:

ext/src/lib.rs
/// Step 5: detached and parallel. rayon splits the chunks over its thread pool.
#[pyfunction]
#[pyo3(signature = (data, threads=8))]
fn tally_bytes_parallel<'py>(py: Python<'py>, data: &[u8], threads: usize) -> PyResult<Report<'py>> {
    let t = py.detach(|| {
        chunks(data, threads)
            .into_par_iter()
            .map(|(part, first)| tally(part, first))
            .reduce(Tally::default, merge)
    });
    to_python(py, t)
}

tally takes only &[u8] and returns plain Rust data, so it is safe on any thread, and the compiler checks that too (rayon requires Send). The split (chunks, in lib.rs) cuts at newlines and remembers each chunk's first line number so "first malformed line" stays exact; the pytest suite (section 11) checks the parallel result equals the serial one for 1, 2, 3, 8 and 64 chunks.

tally: the serde parse and per-user count that every thread runs
ext/src/lib.rs
/// Pure Rust, no Python objects: safe to run without the GIL and on many threads.
fn tally(data: &[u8], first_lineno: u64) -> Tally {
    let mut t = Tally::default();
    for (i, line) in data.split_inclusive(|&b| b == b'\n').enumerate() {
        t.lines += 1;
        match serde_json::from_slice::<Message>(line) {
            Ok(m) => {
                t.ok += 1;
                *t.per_user.entry(m.user).or_insert(0) += tokens(m.text.as_bytes());
            }
            Err(_) => {
                t.bad += 1;
                if t.first_bad == 0 {
                    t.first_bad = first_lineno + i as u64;
                }
            }
        }
    }
    t
}

fn merge(mut a: Tally, b: Tally) -> Tally {
    a.lines += b.lines;
    a.ok += b.ok;
    a.bad += b.bad;
    if a.first_bad == 0 {
        a.first_bad = b.first_bad;
    }
    for (u, n) in b.per_user {
        *a.per_user.entry(u).or_insert(0) += n;
    }
    a
}

the Rust work is long-running and touches no Python objects. Do it on free-threaded Python too: there, a thread that stays attached through long work can stall the interpreter's stop-the-world pauses (garbage collection, sys.settrace, fork) for every other thread (PyO3 free-threading guide).
Mistakes
Detaching around a tiny function (all overhead, no gain); initialising a std::sync::OnceLock or LazyLock with code that calls Python, which can deadlock against the GIL (PyO3's FAQ: use PyOnceLock); starting a rayon pool in a process that already runs one worker per core (oversubscription).

9. Free-threaded Python: what an extension must declare and protect

CPython 3.14 officially supports a build without the GIL, python3.14t (PEP 779); what it costs and what it breaks is Python: concurrency, asyncio and the GIL. For an extension author it changes two things.

1. A module must declare that it is safe without the GIL, or importing it turns the GIL back on for the whole process. Since PyO3 0.28 (2026-02-01) every PyO3 module declares itself safe by default; you opt out with #[pymodule(gil_used = true)] (from 0.23 to 0.27 it was the other way round). 2. Calls really do run at the same time, so state shared between threads must be protected by Rust, not by the GIL. tokrs functions that only read their arguments are fine. /// The thread-safe version: `frozen` means no `&mut self` ever, so PyO3 needs no
/// run-time borrow flag; the mutable state sits behind a Mutex that threads queue on.
#[pyclass(module = "tokrs", frozen)]
struct SharedCounter {
    per_user: std::sync::Mutex<HashMap<String, u64>>,
}

#[pymethods]
impl SharedCounter {
    #[new]
    fn new() -> Self {
        SharedCounter { per_user: std::sync::Mutex::new(HashMap::new()) }
    }

    fn add(&self, user: &str, text: &str) {
        let n = tokens(text.as_bytes()); // count outside the lock
        *self.per_user.lock().unwrap().entry(user.to_owned()).or_insert(0) += n;
    }

    #[getter]
    fn total(&self) -> u64 {
        self.per_user.lock().unwrap().values().sum()
    }
}

The token counting happens before lock(), so threads only queue for the short dictionary update. 12. Wheels: abi3, abi3t, CI and publishing

Users should never need Rust to install your package: they need a wheel built for their Python and their machine, which pip or uv picks from PyPI by the tags in its file name (Python: typing, uv, packaging and the toolchain owns wheel tags, platform tags such as manylinux, and the four packaging layers). maturin build --release wrote tokrs-0.1.0-cp314-cp314-macosx_11_0_arm64.whl: CPython 3.14's full C ABI (it loads on 3.14 only; a free-threaded build would say cp314t), macOS 11 or later on Apple silicon. Inside: the compiled library, the stub and py.typed, metadata, and a software bill of materials (sboms/, the Rust crates compiled in, written by maturin). otool -L (macOS's ldd) shows the library does not link to libpython: it finds Python's C API symbols in the process that loads it, which is what lets one wheel work with any CPython 3.14 binary.

The stage (Fig. 4) carries three wheels built from the same crate to the interpreters they were installed into, in fresh virtual environments (outputs/b3_wheel.txt and b5 to b8):

  1. A cp314 wheel: one interpreter. The wheel above is built against CPython 3.14's full C ABI, so it is for 3.14 alone; every other version, and the free-threaded 3.14t, needs a wheel of its own.
  2. An abi3 wheel: one file, three versions. Built with --features pyo3/abi3-py310, the file is tokrs-0.1.0-cp310-abi3-macosx_11_0_arm64.whl. The same file loaded on Python 3.12.15, 3.13.16 and 3.14.8, each printing loads tokrs.abi3.so -> 3.
  3. Refused by 3.14t. uv would not install it on free-threaded 3.14: "the wheel was built for the stable ABI (abi3), which requires a GIL-enabled interpreter". abi3 assumes the GIL build's object layout.
  4. An abi3t wheel: both 3.15 builds. Built with --features pyo3/abi3t-py315 against 3.15.0rc3: tokrs-0.1.0-cp315-abi3.abi3t-macosx_11_0_arm64.whl. The tag abi3.abi3t means one file for both builds, and it loaded with the GIL disabled and with it enabled.
  5. What to ship today. Until you can require 3.15: the abi3 wheel for every GIL build from 3.10 on, plus a cp314t wheel (dashed: not built here) for the free-threaded build, per platform.
