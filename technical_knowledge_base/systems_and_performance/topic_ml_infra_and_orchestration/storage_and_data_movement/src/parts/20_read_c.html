3. The other designs: where the metadata lives, and who places the bytes

Every parallel file system answers two questions differently: who owns the names (a dedicated metadata tier, or every server), and who decides where a byte goes (a layout handed out once, or a placement every server can compute). That choice decides how it behaves under a metadata storm and when a server fails.

Two families: a separate metadata tier that hands out layouts, or metadata spread over every server

Left: the client asks the metadata tier once, then reads and writes the storage servers directly; data I/O never touches the metadata tier, but every name does. Right: every server holds data and metadata, so there is no single metadata tier to size, at the price of distributed locking (GPFS's token manager, "one metanode per open file"). Tectonic and 3FS put metadata in a transactional key-value store behind stateless servers, which is how they scale the namespace.

4. Metadata: the start-up and small-file storms

The problem. Bandwidth scales with storage servers; metadata does not, or not as fast. A Lustre file system with hundreds of OSTs may have one or a handful of MDTs, and every create, open, stat and failed lookup goes to them. Amazon sells this capacity separately: an FSx for Lustre file system of 1,200 GiB includes 1,500 metadata IOPS, and each metadata IOPS serves 2 file creates, opens or closes per second, 1 delete, or 0.1 directory creates ({{FSx performance guide|https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance.html}}) vendor: 3,000 opens per second for the whole file system derived.

What import torch asks the file system

Python finds a module by trying names on every directory of sys.path in turn, so an import is mostly lookups, many of files that do not exist. Counted with strace -f -c -e trace=%file,getdents64 in a container with torch 2.14.1+cpu and Python 3.11 measured (3 runs each, identical counts): import torch makes 17,983 file-system calls, 16,196 of them stat, 1,341 opens, and 652 fail (almost all ENOENT, no such file: the misses).

The same four operations on three stores: network storage is a hundred times slower per name, and misses are worst

Each process works in its own directory: create empty files, stat them, look up names that do not exist ("miss", an S3 HEAD that returns 404), delete them, in lock step measured (medians of 3; src/runs/meta_real.py). Operations per second, all processes together, log scale.

A local file system does hundreds of thousands of operations a second, a network one a few thousand: the gap is the round trip, not the disk. The host folder shared into the VM answers stat of an existing file from its cache, as fast as local disk, but every lookup of a missing name crosses to the host: network file systems cache what exists far better than what does not. The object store pays a full HTTP request for everything, even a HEAD.

The same runs as a table, with the toy's one-server rate (reference)
Predict. 16,384 ranks (Llama 3 405B's scale) start at the same second and each runs import torch from a Python environment on the shared file system. Suppose only the 652 failed lookups per rank reach the metadata servers (everything else cached). At 3,000 metadata operations per second, how long is the start-up stall?
16,384 x 652 = 10.7 million lookups; at 3,000 a second that is 3,561 s, about an hour derived, before a single step. With all 17,983 calls reaching the server it would be 27 hours. Real metadata servers are faster than this FSx entry size and clients cache more, so the real number depends on the system, but the shape is why large clusters never run Python from the shared file system: the environment lives in the container image on each node's local disk (squashfs images through enroot and pyxis on Slurm, image layers on Kubernetes), or is unpacked to local NVMe at job start. The start-up storm: stall = ranks x calls per rank / metadata capacity

Calls per rank are measured with strace; how many of them a real client sends to the server depends on its caches, so choose the bound.

More clients, one metadata server: the rate flattens and every operation waits longer

On the toy, 16 client processes each create, stat and delete 300 files of their own through one metadata server held to half a CPU, then through two (the idea of Lustre's DNE, Distributed Namespace: names hashed over servers).

The same 14,400 operations from 16 clients: a second metadata server gives 1.6 times the rate, not 2

16 processes x 300 files x (create, stat, unlink). The bar is completed operations at the measured aggregate rate, on one clock for both modes; each client's dot is busy while it waits for its answer.

Two metadata servers served 16 clients at 2,635 operations per second against 1,603 for one measured. The server, not the clients, was the limit: at 16 and 32 clients its container used all of its half CPU while the client container used about a fifth of its two, and 32 clients got fewer operations per second than 16 and waited twice as long for each.

CPU use during the runs, and DNE on real Lustre (depth)

One MDS serves a whole Lustre file system until DNE adds more: a directory can live on another MDT (lfs mkdir -i mdt_index), or one huge directory can be spread over several with lfs mkdir -c mdt_count, "indended [sic] for specific applications where many output files are being created in one large directory (over 50k entries)".

The fixes, in the order to try them

  • Keep code and environments off shared storage: container images or a packed environment copied to local disk once per node. Symptom when you do not: jobs take minutes to reach step 1, get slower as they get bigger, and the metadata server sits at 100% while the OSTs idle.
  • Pack data into big shards: one open per shard instead of per sample. How big (a few hundred MB, so loader workers read in parallel and a job resumes from a shard) and the formats are owned by {{Storage and loading at scale|n:3f95c17b0d0d81398782efcb29d950d4}}, section 7.
  • One file per rank for checkpoints, not one per tensor: DCP writes one .distcp file per rank plus one .metadata (section 8).
  • Big output directories: spread over MDTs with a DNE striped directory, or hash into subdirectories; never ls -l or find over millions of entries on a busy file system (each entry is a stat).
  • Small files that must exist: Data on MDT, so each costs one server.
  • More metadata servers (DNE on Lustre, more metadata IOPS on FSx) when the workload truly needs them.

Measured: the same bytes as big files and as small ones

Reading training data is the easy pattern: sequential, predictable, and small next to the compute for text (the {{throughput calculator on Storage and loading|n:3f95c17b0d0d81398782efcb29d950d4}} shows Llama 3 405B needed about 11 MB/s of token ids for the whole job). What still goes wrong is about requests, not bytes. 64 MiB of the running example's token ids, stored as 16 files of 4 MiB or as 16,384 files of 4 KiB (the same bytes), on a Docker volume and on the S3 store, from one container, in the root page's Storage lab measured:

Each file costs an open, a metadata lookup and a close; each object costs an HTTP request. At 4 KiB per file those fixed costs are the whole bill, and on a parallel file system they land on the metadata servers (FSx's 2 file create/open/close operations per metadata IOPS vendor), so a thousand nodes each opening millions of tiny files saturate it long before the disks are busy, and the whole cluster slows, not only your job.

A loader that keeps the next shards in flight hides each fetch only while fetching is faster than computing; the measured run (S3 against a Docker volume, 4 MiB shards, 100 ms of compute per step) is section 10 of {{Storage and loading at scale|n:3f95c17b0d0d81398782efcb29d950d4}}.
