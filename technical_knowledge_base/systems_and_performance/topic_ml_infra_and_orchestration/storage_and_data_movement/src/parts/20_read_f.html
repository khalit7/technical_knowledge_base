8. Checkpoint formats, seen as files and byte ranges

What is in a checkpoint, measured

A checkpoint is everything needed to continue training as if nothing had happened: the weights, the optimiser's state, the step number, and anything else that carries state (random number generators, the data loader's position, the learning-rate schedule). Leave any of it out and a resumed run differs from an uninterrupted one. The running example needs only three things, because its batches depend only on (seed, step) and it uses no randomness after initialisation; this is why its resume is bit-exact.

With the contents known, the question is what the storage sees: how many files or objects, how big, and which byte ranges a reader must fetch. PyTorch Distributed Checkpoint (DCP): one file per rank, plus a map

DCP "produces multiple files per checkpoint, with at least one per rank" and "handles load-time resharding which enables saving in one cluster topology and loading into another" ({{DCP docs, 2.14|https://docs.pytorch.org/docs/stable/distributed.checkpoint.html}}). Our 4-rank save:

The .metadata file is the map: for each of the entries (102 weight tensors, 204 Adam moments, 102 step counters), the global shape, and for each of its chunks the offsets in the global tensor and the file, byte offset and length where it lives. FSDP2 shards every tensor along its first dimension, so tok.weight (65 x 512) is four chunks of 17, 17, 17 and 14 rows:

Each chunk is stored as a small torch.save record, so 384 x 512 fp32 values (786,432 bytes) take 788,009 bytes on disk. File 0 is smaller than the others because DCP's de-duplication gave the replicated entries to the ranks with less to write (the parent's lab quotes the code).

Resharding is a set of byte-range reads: the same checkpoint loaded by 4, 2 and 3 ranks

Every read DCP issued was recorded (a FileSystemReader subclass logging file, offset and length before reading) measured. Top: the four files on disk, to scale. Below: the new ranks; each step shows what one rank read from each file.

Why 3 ranks read 1.5 times the checkpoint. A new rank that owns rows 0 to 21 of a tensor saved in chunks of 17 needs part of the second chunk, and DCP's file reader fetches whole stored chunks, then copies the slice it needs:

torch/distributed/checkpoint/filesystem.py, lines 869-884, PyTorch v2.14.1
    def read_data(self, plan: LoadPlan, planner: LoadPlanner) -> Future[None]:
        # group requests by file
        per_file: dict[str, list[ReadItem]] = {}
        for read_item in plan.items:
            item_md: _StorageInfo = self.storage_data[read_item.storage_index]
            path = item_md.relative_path
            per_file.setdefault(path, []).append(read_item)

        for relative_path, reqs in per_file.items():
            new_path = self.fs.concat_path(self.path, relative_path)
            with self.fs.create_stream(new_path, "rb") as stream:
                # TODO sort by offset and cache the reading
                for req in reqs:
                    item_md = self.storage_data[req.storage_index]
                    file_slice = self._slice_file(stream, item_md)

item_md is the stored chunk's (relative_path, offset, length); _slice_file (line 860) views exactly that range, so the whole chunk is read even when the new rank needs a few rows of it. Resharding to a divisor of the old world size (4 to 2) reads each byte once; to a non-divisor (4 to 3) the overlapping chunks are read by two ranks each. On a parallel file system that is 50% more restore traffic; on an object store, 50% more GET bytes.

The burst, measured: every rank writes at once

Training is synchronous: at the checkpoint step, every rank reaches the save at the same moment, and the storage system sees all of them arrive together. Whatever the aggregate write bandwidth is, they share it. Who writes what then decides both the bytes and the time:

  • Rank 0 writes everything (train.py's way, fine for DDP, where every rank holds a full copy): one writer, one link.
  • Every rank writes everything: the forgotten if rank == 0. Same file content, written N times.
  • Consolidated (gather, then one file): with a sharded model (FSDP, ZeRO-3), the pieces are first sent to rank 0 over the network, then rank 0 writes one file. Needs the whole state in rank 0's memory.
  • Sharded (PyTorch Distributed Checkpoint, DCP): every rank writes its own piece to its own file, in parallel, plus a small .metadata file mapping pieces to tensors. No gather, no single writer.

Measured with 4 ranks in one container (2 CPUs, gloo) and the 3.2M-parameter GPT (38.6 MB of state), three repetitions each, on the slow shared folder and on a Docker volume measured:

gathering pieces to rank 0writing (and fsync)waiting for the others

What this shows, and what it cannot. Bytes on a shared pipe cost time: writing four copies took about three times as long as one. But sharding did not make the write faster here, because all four ranks share one container, one virtual disk and one file-sharing channel: there is only one pipe. On a cluster every node has its own network link to storage (a DGX B200 has two BlueField-3 storage ports at up to 400 Gb/s each, {{NVIDIA|https://docs.nvidia.com/dgx/dgxb200-user-guide/introduction-to-dgxb200.html}}), so N nodes writing their shards use N links at once, while a consolidated write squeezes the whole state through one. The root page's {{Storage lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} calculator and this page's {{Sizing calculator|#t-sdsize}} do that arithmetic. What the local run does show is the hidden cost of consolidating: on the fast volume, gathering 38.6 MB to rank 0 took longer than writing it.

safetensors: a header that maps every tensor to a byte range

The format is "8 bytes: N, an unsigned little-endian 64-bit integer, containing the size of the header", then N bytes of JSON giving each tensor's "dtype", "shape" and "data_offsets" relative to the data buffer, then the bytes; the header is capped at 100 MB ({{safetensors README|https://github.com/huggingface/safetensors}}). 9. Sizing storage for a cluster


Four separate questions; the {{Sizing calculator|#t-sdsize}} answers all four for any cluster. {{Cluster anatomy|n:3fc5c17b0d0d816a871df56477fc83b2}} covers NVIDIA's per-SU reference numbers; this is the arithmetic behind any such table.


    

  1. Write bandwidth, from the checkpoint. Size = parameters x bytes per parameter (about 14 for bf16 with fp32 Adam; MLPerf Storage v2.0's own checkpoint table gives 912 GB for 70B and 5.29 TB for 405B, 13.0 and 13.1 bytes per parameter derived, {{MLPerf Storage rules v2.0|https://github.com/mlcommons/storage/blob/v2.0/Submission_guidelines.md}}). With synchronous saves, bandwidth = size / the stall you accept. With asynchronous saves, the GPUs stop only for the copy to host memory and the storage only has to drain the checkpoint before the next one: bandwidth = size / interval.
    2. 

  2. Read bandwidth, from data and from restarts. Data: tokens per second x bytes per token, small for text. Restart: every rank reads the checkpoint at once, size / the restart time you accept, usually the larger number.
    3. 

  3. Metadata rate, from start-up and small files. Ranks x the operations each makes at start (section 4), and files per second for data in small files.
    4. 

  4. Capacity = datasets + checkpoints kept x size + scratch, and on a parallel file system bought as servers, capacity often follows from the bandwidth rather than the bytes.
    5. 



Predict. A 70B model on 1,024 GPUs checkpoints every 30 minutes (0.98 TB at 14 bytes per parameter). How much write bandwidth does storage need, synchronous with a 30 s stall against asynchronous?




0.98 TB / 30 s = 32.7 GB/s; 0.98 TB / 1,800 s = 0.54 GB/s derived: sixty times less, because asynchronous saving lets the write take the whole interval. On FSx for Lustre at 125 MB/s per TiB, 32.7 GB/s means buying 261 TiB (about $38,800 a month at $0.145 per GB-month) to store about 10 TB of checkpoints derived. Restarts are the catch: reading 0.98 TB back in 60 s still needs 16.3 GB/s, so size reads for recovery and writes for the drain.
