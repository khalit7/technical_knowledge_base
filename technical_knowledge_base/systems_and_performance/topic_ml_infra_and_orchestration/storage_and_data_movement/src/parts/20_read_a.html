The idea in one screen

A training cluster's storage is a ladder of tiers, from each node's memory and NVMe to a shared parallel file system to the object store, each slower and more durable than the one above; and nearly every storage problem in training is one of three: bytes go only as fast as the servers a file is spread over, names go only as fast as the few metadata servers, and checkpoints arrive from every rank at the same second.

The storage ladder: a checkpoint walks down it, data and restarts climb back up

Each rung is a real tier with a sourced number: a SuperPOD node must read more than 40 GB/s by itself (NVIDIA, on {{Cluster anatomy|n:3fc5c17b0d0d816a871df56477fc83b2}}); a DGX H100 keeps 8 x 3.84 TB of NVMe in RAID 0 for staging; Argonne's Polaris runs "Lustre: 100 PB @ 650GB/s"; S3 answers in "roughly 100-200 milliseconds" and costs $0.023 per GB-month against $0.145 for FSx for Lustre (AWS, us-east-1, read 2026-10-16). The three highlighted marks are the three bottlenecks: striping (section 2), metadata (section 4) and the burst (sections 8 and 9). Each hop down is asynchronous from the one before (section 7), so with asynchronous saves training stops only for the first.

Bandwidth, IOPS, latency
bytes per second for large transfers; small operations per second; how long one operation takes, which caps a client doing one thing at a time.
Metadata operation
an operation on names rather than bytes: create, open, stat (ask a file's size and times), lookup of a missing name, list, delete.
Parallel file system
POSIX storage that keeps names on a few metadata servers and spreads each file's bytes over many storage servers.
Stripe size, stripe count
bytes written to one server before moving to the next; how many servers one file is spread over.
Object store
a flat space of keys, each an immutable object written whole and read by byte range (S3, GCS, Azure Blob).
Prefix
the leading characters of a key; S3 partitions request capacity by prefix.
DCP
PyTorch Distributed Checkpoint: one file per rank plus a .metadata map, loadable into any number of ranks.
The burst
every rank writing its share of a checkpoint at the same moment.

1. The problem: one server is one pipe

What a training job asks of shared storage, and when. All four patterns hit every rank at the same moment, which is what makes training storage different from a file server's usual load.

Start-upEvery rank imports Python packages and loads its container image: tens of thousands of opens and lookups each, all ranks in the same second (17,983 file-system calls for import torch, section 4).
Reading dataA steady stream of large sequential reads, small next to compute for text and easy to prefetch.
CheckpointingEvery few minutes to hours, every rank writes its piece at once while the GPUs wait, unless the save is asynchronous: a burst of terabytes (section 9).
Restart and evaluationEvery rank reads the latest checkpoint at once, often into a different number of ranks (section 8); evaluation jobs read many checkpoints.

Why one file server is not enough. An NFS server holds both the names and the bytes, so all of the above goes through one machine's disks and one network card, while a SuperPOD node alone must pull more than 40 GB/s, already more than a good single server delivers. The parent's lab saw the same shape in miniature: the 304 MB checkpoint took 7.31 s through a host folder shared into the Docker VM (one file-sharing channel) against 387 ms on a Docker volume measured.

The two ways out. A parallel file system keeps POSIX (directories, open, seek, rename) but separates names from bytes: a few metadata servers answer "where is this file", and the bytes go straight to and from many storage servers at once. An object store gives up POSIX (no rename, no append, no partial overwrite) for a design partitioned by key, which scales to any number of clients at a fraction of the price per byte. Large clusters use both: the object store holds the data and checkpoints of record, a parallel file system or local NVMe the working copies.
