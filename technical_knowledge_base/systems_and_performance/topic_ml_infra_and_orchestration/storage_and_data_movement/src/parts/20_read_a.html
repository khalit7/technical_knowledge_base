Every node of a training cluster reads the same datasets, writes its share of every checkpoint and starts from the same code, so somewhere there is storage that all of them share. This page opens that storage up: how a parallel file system splits names from bytes and spreads each file over many servers, what an object store promises and what it does not, the caches and staging copies in between, how data and checkpoints move from one to another, how to size all of it for a cluster, and what a checkpoint looks like when you see it as files and byte ranges. 1. The problem: one server is one pipe

Four numbers describe any store. Bandwidth is bytes per second for large transfers (GB/s). IOPS (I/O operations per second) is how many small reads or writes it serves. Metadata operations per second counts the operations on names rather than bytes: create, open, stat (ask for a file's size and times), lookup of a name that does not exist, list a directory, delete. Latency is how long one operation takes, which caps what one client doing one thing at a time can get. A store can be fast on one and slow on another, and training jobs hit all four.

What a training job asks of shared storage, and when.

Start-upEvery rank imports Python packages and loads the container image: tens of thousands of opens and lookups each, all ranks at the same second (section 4 counts them: 17,983 file-system calls for import torch).
Reading dataA steady stream of large sequential reads, small next to compute for text and easy to prefetch (the parent's lab and Storage and loading at scale).
CheckpointingEvery few minutes to hours, every rank writes its piece at the same moment while the GPUs wait unless the save is asynchronous: a burst of terabytes (section 9).
Restart and evaluationEvery rank reads the latest checkpoint at once, often into a different number of ranks (section 8); evaluation jobs read many checkpoints.

Why one file server is not enough. An NFS server holds both the names and the bytes, so all of the above goes through one machine's disks and one network card. A modern GPU node can pull more than 40 GB/s by itself (NVIDIA's requirement for SuperPOD nodes, on the sibling Cluster anatomy page), which is already more than a good single server delivers. The parent's lab saw the same shape in miniature: the 304 MB checkpoint took 7.31 s through a host folder shared into the Docker VM (one file-sharing channel) against 387 ms on a Docker volume measured.

The two ways out, and the rest of the page follows them. A parallel file system keeps the POSIX interface (directories, open, seek, rename) but separates the names from the bytes: a few metadata servers answer "where is this file", and the bytes go straight to and from many storage servers at once. An object store gives up POSIX (no rename, no append, no partial overwrite) in exchange for a design that partitions everything by key, so it scales to any number of clients and costs a fraction as much per byte. Large training clusters use both: the object store holds the data and checkpoints of record, a parallel file system or local NVMe holds the working copies.
