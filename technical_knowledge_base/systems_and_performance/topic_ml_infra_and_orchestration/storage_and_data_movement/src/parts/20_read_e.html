6. Caches and tiers in between

The problem. The object store is cheap and holds everything, but answers in 100-200 ms and has no POSIX; the parallel file system is fast but costs several times as much per byte (FSx for Lustre persistent SSD at 125 MB/s per TiB: $0.145 per GB-month, against S3 Standard's $0.023, AWS us-east-1, read 2026-10-16 published). A cache or tier keeps the working set on fast media near the GPUs and the rest in the object store.

When a cache helps, in one line. It pays only for bytes read more than once. Single-pass pretraining reads each token about once, so a data cache adds nothing but a copy; multi-epoch fine-tuning, many jobs reading the same dataset, evaluation sets, model weights loaded by every serving replica, and container images are where caches earn their space. The second kind of help is latency: a cache on local NVMe answers in microseconds where the object store answers in a tenth of a second, which matters for small files and for random access.

GPUDirect Storage: removing the CPU bounce buffer (depth)

GPUDirect Storage removes a different hop: "a direct data path for direct memory access (DMA) transfers between GPU memory and storage" that "avoids a bounce buffer through the CPU"; NVIDIA's only number is that such a path "offers at least twice the peak bandwidth as compared to taking a data path through the CPU" on suitable PCIe topologies ({{GDS overview v1.19.1|https://docs.nvidia.com/gpudirect-storage/overview-guide/index.html}}) vendor. It needs supported NVMe or network storage and code written to the cuFile API; not run here.

7. Moving data: staging, checkpoint paths, other regions

Staging a dataset is a copy, and a copy's time is its size over the narrowest pipe: t = bytes / min(source read, destination write, the link between). 100 TB over one 100 Gb/s (12.5 GB/s) link takes 2.2 hours derived, and many files make it slower, because a single-threaded copy also pays a metadata round trip per file; the fix is a copy tool that parallelises both.

The tools that parallelise a copy: mpiFileUtils, s5cmd, Slurm's sbcast and burst buffers (depth)
  • mpiFileUtils (dcp, dsync): MPI-parallel copy and sync for file systems, "providing speedups of up to 20-30x"; "dsync is the recommended way to make a copy a large set of files" ({{mpiFileUtils|https://github.com/hpc/mpifileutils}}) authors.
  • s5cmd or a CRT-based S3 client for object stores: many connections, ranged parts (section 5).
  • Slurm: sbcast "is used to transmit a file to all nodes allocated to the currently active Slurm job" to local disk (good for one binary or one environment tarball; the docs warn "parallel file systems may provide better performance"), and burst-buffer plugins (datawarp, lua) that run stage-in and stage-out scripts around a job ({{burst buffers|https://slurm.schedmd.com/burst_buffer.html}}). The sibling {{Slurm|n:3c65c17b0d0d81889c32cd050bbbadd3}} page covers job prologs and epilogs.

A checkpoint's path to safety, fastest first. Each hop is asynchronous from the one before, so training stops only for the first:

  1. GPU memory to host memory: the copy that asynchronous DCP blocks on (the parent's lab: training stopped 77.9 ms per checkpoint instead of 1.81 s on its slow folder measured); torchtitan exposes it as async_mode "disabled", "async" or "async_with_pinned_mem" ({{torchtitan|https://github.com/pytorch/torchtitan}}).
  2. Host memory to local NVMe or a peer's memory: survives the process, not the node. In-memory checkpoints in other nodes' RAM recover far faster than remote storage allows: Gemini (an Amazon system, SOSP 2023, not Google's model) reports "more than 13x" faster failure recovery and that checkpointing MT-NLG's states takes "42 minutes" to remote storage at 20 Gbps ({{Gemini, SOSP 2023|https://cdn.amazon.science/29/31/6523473f48e4af52252bac56ef51/gemini-fast-failure-recovery-in-distributed-training-with-in-memory-checkpoints.pdf}}) authors. The sibling {{Fault tolerance at scale|n:3fc5c17b0d0d815786d1c1dddb311a9b}} page compares these designs.
  3. To the parallel file system: survives nodes; this is where the burst lands (section 9).
  4. To the object store: survives the cluster; retention lives here. torchtitan keeps the latest 10 by default (keep_latest_k: int = 10, interval 500 steps), so capacity is about ten checkpoints, not one. Megatron Core writes straight to object stores with --save msc://my-profile/checkpoints through NVIDIA's Multi-Storage Client ({{Megatron Core MSC|https://docs.nvidia.com/megatron-core/developer-guide/latest/user-guide/msc_integration.html}}); FSx can export to its linked bucket automatically.

Asynchronous checkpointing, measured: training stops for the copy, not for the write

An asynchronous checkpoint splits the save in two: stage the state into host memory (a PCIe copy of each rank's shard), then let training continue while a background thread writes the staged copy. The cost: a second copy of the state in host RAM, and the write must finish before the next checkpoint starts. The same 60 training steps of the 3.2M-parameter GPT (4 ranks, DCP, a checkpoint every 15 steps) without checkpoints, with dcp.save and with dcp.async_save; step times are each step's slowest rank, from the root page's Storage lab (Apple M1 Pro, Docker Desktop VM and native, shared machine) measured:

training steptraining stopped for the checkpointbackground write (drawn with the synchronous write's measured time)

Published, at scale: PyTorch and IBM report that asynchronous DCP cut the time a 7B model's training stood still per checkpoint from 148.8 s to 6.3 s on average, the 6.3 s being the copy to CPU memory published ({{PyTorch blog, November 2024|https://pytorch.org/blog/reducing-checkpointing-times/}}). Google's Gemini 1.0 report describes keeping redundant copies of model state in other hosts' memory, raising its largest job's goodput from 85% to 97% ({{Gemini 1.0 report, section 3|https://arxiv.org/abs/2312.11805}}).

The async trap we hit: give the background writer its own process group (a real hang and crash)

DCP's save runs collectives (it gathers every rank's plan and agrees the file is complete). async_save runs them in a background thread; if that thread uses the same process group as training, two threads issue collectives on one channel at once. Our first attempt (4 ranks, gloo, native) hung: every rank at 0% CPU after the first checkpoint, nothing printed for over four minutes. A rerun crashed 3 s after the checkpoint, two ranks aborting with:

gloo::EnforceNotMet: [enforce fail at .../third_party/gloo/gloo/transport/uv/pair.cc:253] op.nread == op.preamble.nbytes

The fix is one line, the one the PyTorch blog recommends: create a group once, ck_pg = dist.new_group(backend="gloo"), and pass process_group=ck_pg to async_save. All runs above use it.

One 405B checkpoint at MLPerf Storage's 5.29 TB costs about $106 to copy to another US region and about $476 to take out to the internet, and takes 423 s over a dedicated 100 Gb/s link derived. Keeping ten of them in a second region doubles their storage bill, which is why most labs replicate only selected checkpoints.
