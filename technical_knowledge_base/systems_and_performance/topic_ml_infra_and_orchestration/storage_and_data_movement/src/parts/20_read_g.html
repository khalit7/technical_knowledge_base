Common mistakes

A big shared file with the default stripe count of 1
Every writer and reader of the file lands on one OST. On the toy, four ranks writing one shared file with one stripe got 24.9 MB/s; with four stripes 97.8 measured. Check with lfs getstripe; set a directory default (lfs setstripe -c 4 -S 4M dir) before the files exist: a layout cannot change after creation without lfs migrate.
Pinning every file to one OST
lfs setstripe -i 0 copied from an example puts every new file on OST 0: four file-per-rank writers fell from 88.9 to 25.0 MB/s on the toy measured. The manual: the default start index of -1 "allows the MDS to choose the starting index. This setting is strongly recommended".
Unaligned writers sharing one stripe
Ranks writing interleaved pieces of one file fight over the OST's extent locks ("lock exchange") even when their bytes do not overlap. Align each writer to whole stripes, or write one file per rank (DCP does).
A Python environment on the shared file system
17,983 file-system calls and 652 failed lookups per rank for import torch measured, times every rank, all at once. Symptom: jobs that take minutes to reach step 1 and get slower as they get bigger, and a metadata server at 100% while the OSTs idle. Ship the environment in the container image on local disk.
A PFL file that keeps growing by appends
Appending to a file with a wide last component instantiates every component, and "an operation such as reading the file length will send a request in parallel to every OST" (FSx guide). FSx gives files opened in append mode a stripe count of 1 for that reason. On Data on MDT layouts without an end-of-file component, "writes beyond the end of the last existing component will fail with error ENODATA" (manual).
Multipart parts below the minimum
Every part but the last must be at least 5 MiB. Our store refused two 1 MiB parts at completion: measured. The failed upload then stayed open and listed (it was in list_multipart_uploads next to the abandoned one); on AWS its parts are billed until aborted. Add a lifecycle rule that aborts incomplete multipart uploads.
"Renaming" a checkpoint on an object store
There is no rename: a copy and a delete move every byte again (here 64 MiB took 0.49 s to "rename" against 0.66 s to upload measured; a server-side copy still rewrites the bytes inside the store). Upload under the final key and write a marker or .metadata last; protect the marker with If-None-Match: * (a second writer got ).
Storage that silently filled up
Overwriting the same 256 MiB key over and over on SeaweedFS ended with InternalError ... We encountered an internal error, please try again. after 16 uploads: deleted and overwritten data kept its space until a vacuum (our inference). Every store has a version of this (snapshots, object versions, Lustre OSTs that fill unevenly): watch free space per server, not just in total, and keep checkpoint retention (keep the last k) in the training code.
Resharding to a world size that does not divide the old one, and blaming the network
4 ranks to 3 read 1.50 times the checkpoint's bytes, 4 to 2 read 1.00 times measured (section 8). Plan restore bandwidth for the overlap, or restart at a divisor when you can.
Expecting a cache to speed up the first epoch
A lazy-loading cache (FSx linked to S3, Mountpoint's cache) serves the first read at the object store's speed. Preload the hot directory before the job, or accept that single-pass pretraining gains nothing from it.

Interview questions

Why can a parallel file system go faster than any one of its servers, and what stops it?
Metadata and data are split: the client fetches a file's layout from the metadata server once, then reads and writes the objects on many storage servers in parallel (RAID 0 by stripe size). It stops at the narrowest of: the stripe count (one file uses only its objects' servers), the client's network card, the servers' disks and networks, the metadata server for small files and start-ups, and lock contention when writers share stripes.
You are writing 1,024 checkpoint shards of 2 GB each to Lustre. What stripe settings?
File per rank already spreads the load if the MDS places the files round robin, so stripe count 1 (or a few) and stripe size 1 to 4 MiB; never a fixed start index. Wide striping helps when few large files must use many OSTs (a consolidated export, a dataset file read by everyone). Check the result with lfs df for balance.
What does S3 guarantee about a checkpoint, and what must your code add?
Each object appears atomically and strong read-after-write holds per key. Nothing is atomic across keys, so a multi-shard checkpoint needs a marker or metadata object written last and a reader that ignores directories without it; conditional writes (If-None-Match, If-Match) stop two writers clobbering each other; abort incomplete multipart uploads; spread keys over prefixes and retry 503 SlowDown with backoff.
Jobs take ten minutes to reach the first step on 2,000 nodes, a minute on 20. Where do you look?
A metadata storm: Python or shared libraries loaded from the shared file system, every rank doing tens of thousands of lookups at once. Confirm with strace -c on one rank and the metadata server's load; fix by shipping the environment in the image on local disk, then data in shards.
Synchronous or asynchronous checkpoints: how does the choice change the storage you buy?
Synchronous: bandwidth = checkpoint size / acceptable stall (32.7 GB/s for 0.98 TB in 30 s). Asynchronous: the GPUs stop only for the host copy, and storage needs size / interval (0.54 GB/s every 30 minutes), plus host RAM for the staged copy and a separate process group for the background collectives. Restores still need size / acceptable restart time.
Why might restoring onto 3 nodes take longer than onto 2, from the same 4-rank checkpoint?
DCP reads whole stored chunks. At a divisor each byte is read once; at a non-divisor, chunks straddle new ranks and are read twice (1.50 times the bytes measured here), on top of uneven shard sizes.
When is a cache in front of the object store worth it?
When bytes are read more than once (multi-epoch, many jobs on one dataset, eval sets, weights for many replicas, images) or when latency matters (small files, random access). Single-pass pretraining gains almost nothing; the first epoch through a lazy cache runs at object-store speed.
Design question: the storage for a 1,000-GPU training lab.

Tiers. An object store (S3 or an on-premises one) as the system of record for datasets, checkpoints kept beyond a few days, and artifacts, with lifecycle rules. A parallel file system (Lustre or FSx for Lustre, WEKA, VAST) as the working tier for checkpoints and hot datasets, linked to the object store for import and export. Local NVMe on every node for staged data, images and the first copy of each checkpoint. Home directories and code on a small NFS.

Numbers. For a 70B model on 1,024 GPUs: 0.98 TB per checkpoint; asynchronous saves every 30 minutes need about 0.5 GB/s of drain; recovery in 60 s needs about 16 GB/s of read; ten kept checkpoints are about 10 TB; data reads for text are small. So size the file system for restore reads and bursts from many jobs at once, and buy metadata capacity (more MDTs or metadata IOPS) for start-ups and small files.

Rules. DCP or equivalent with one file per rank, a marker written last, keep-last-k retention in the trainer; environments in container images; data in shards of tens to hundreds of MB; checkpoint directories with a sane default layout; per-server monitoring (OST balance, MDT load, S3 503s). Trade-offs to say out loud: managed (FSx, cost per TiB tied to throughput) against owned (capital, staff), one tier against two, and how much to replicate across regions ($0.02 per GB between AWS US regions).
