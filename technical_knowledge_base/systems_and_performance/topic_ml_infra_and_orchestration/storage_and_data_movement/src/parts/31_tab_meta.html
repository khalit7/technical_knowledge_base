Metadata storm: when names, not bytes, are the bottleneck

Two kinds of run. On tpfs, the toy parallel file system of the {{Striping lab|#t-sdstripe}}, every client process creates, stats and deletes 300 files of its own through one metadata server held to half a CPU, then through two (the DNE idea: entries hashed over servers by name). On real stores, the same operations run on a Docker volume, a host folder shared into the VM and SeaweedFS's S3 gateway measured (Apple M1 Pro, Docker Desktop VM, shared machine, 2026-10-16; medians of 3).

16 processes x 300 files x (create, stat, unlink). The bar is completed operations at the measured aggregate rate, on one clock for both modes; each client's dot is busy while it waits for its answer.

More clients, same server: throughput flattens, every operation waits longer

The evidence that the server, not the clients, is the limit: at 16 and 32 clients the metadata server's container used all of its half CPU while the client container used about a fifth of its two. Past that point more clients only queue: 32 clients got fewer operations per second than 16 and waited twice as long for each.

Log scale. "miss" is a stat of a name that does not exist (an S3 HEAD that returns 404), what Python's import does on every sys.path entry. The shared folder caches existing files' attributes (its stat is as fast as local) but not absence, so its misses cost a round trip to the host each.
