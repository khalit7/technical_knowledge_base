Striping lab: one file over many servers

Every run here used tpfs, a toy parallel file system written for this page (src/runs/tpfs.py, standard-library Python): one metadata server that hands out layouts, and four object servers that store the bytes, each in its own container (0.5 CPU, 256 MB) and each held to 25 MB/s by a token bucket standing in for its disks. The client gets a file's layout once and then talks to the object servers directly, using Lustre's RAID 0 arithmetic. The per-server limit is an input; the scaling, the hot spots and the slowdowns below are what happened measured (Apple M1 Pro, Docker Desktop VM, shared machine, 2026-10-16; medians of 3). Not modelled: locks, caches, failures.

Each square is 1 MiB (one stripe), coloured by the object server that received it, filled at the rate the real run achieved. The clock is the same for all three, so the striped runs finish early on screen exactly as they did.

Four writers at once: where the bytes land decides the speed

Four processes in one client container each write 64 MiB, in four layouts measured. Bars: aggregate MB/s (256 MiB over the time from the first start to the last finish).

The two slow rows are the same mistake in two forms: all the bytes on one server (every file pinned to OST 0 with -i 0, or one shared file left at stripe count 1). The two fast rows are equal: when every rank writes its own file and the files are spread, striping each file adds nothing. On real Lustre the shared-file row also pays for lock exchange between writers in the same stripe, which tpfs does not model, so the shared file would do worse than shown.

How the toy is built, and how to run it

docker network create sd-net
for i in 0 1 2 3; do
  docker run -d --rm --name sd-ost$i --network sd-net -v $PWD/tpfs.py:/tpfs.py:ro \
    --memory 256m --cpus 0.5 python:3.12-slim python3 /tpfs.py ost --mbps 25
done
docker run -d --rm --name sd-mds0 --network sd-net -v $PWD/tpfs.py:/tpfs.py:ro \
  --memory 256m --cpus 0.5 python:3.12-slim \
  python3 /tpfs.py mds --osts sd-ost0:9000,sd-ost1:9000,sd-ost2:9000,sd-ost3:9000
docker run -d --rm --name sd-cli --network sd-net -v $PWD/tpfs.py:/tpfs.py:ro \
  --memory 768m --cpus 2 python:3.12-slim sleep 3600
docker exec sd-cli python3 /tpfs.py bench stripe --mds sd-mds0:8000 --mib 128 --counts 1,2,4

What transfers to a real cluster: the arithmetic (one file's bandwidth is its stripe count times one server's, until the client's network card or the job's other files get in the way), the hot spot when files share a server, and the cost of small stripes. What does not: the absolute numbers (25 MB/s per server is a choice, a real OST does gigabytes), locks, and the client-side caching and RPC pipelining that make Lustre's per-request costs far lower than Python's.
