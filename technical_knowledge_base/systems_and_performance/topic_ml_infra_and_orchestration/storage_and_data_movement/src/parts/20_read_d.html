5. Object storage: what it promises, and how fast it goes

An object store keeps objects (a key, the bytes, a little metadata) in buckets. The key ckpt/step_000200/__3_0.distcp looks like a path, but there are no directories: the slashes are characters, and "listing a directory" is asking for keys that start with a prefix. The rules below are Amazon S3's, quoted from its documentation (read 2026-10-16); Google Cloud Storage and Azure Blob differ in detail, not in kind. Every behaviour marked measured ran against SeaweedFS 4.48 set up as a real distributed store (one master, three volume servers, one filer with its S3 gateway, in capped containers; src/runs/run_seaweed.sh); MinIO was the plan, but its images could no longer be pulled on 2026-10-16.

The throughput model: requests, prefixes and connections

Per request. S3 quotes "roughly 100-200 milliseconds" of latency for small objects and to the first byte of large ones, and "at least 3,500 PUT/COPY/POST/DELETE or 5,500 GET/HEAD requests per second per partitioned Amazon S3 prefix. There are no limits to the number of prefixes in a bucket." Scaling to a higher rate "happens gradually", with "503 (Slow Down)" errors meanwhile ({{S3 performance guide|https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html}}) vendor. So a checkpoint of 16,384 shards written in one second under one prefix asks for 4.7 times one prefix's write rate derived (16,384 / 3,500): spread keys over prefixes (by rank, for example) and retry with backoff.

Per connection. One connection is limited by its latency and the server's per-stream rate, so throughput comes from many at once: "You can use concurrent connections to Amazon S3 to fetch different byte ranges from within the same object", with GETs aligned to the upload's part boundaries, up to a single instance's "100 Gb/s". Fast clients exist for exactly this: s5cmd's README quotes a user benchmark in which it "can saturate a 40Gbps link (~4.3 GB/s), whereas s3cmd and aws-cli can only reach 85 MB/s and 375 MB/s" ({{s5cmd|https://github.com/peak/s5cmd}}) independent, undated.

Measured on the stand-in: eight ranged GETs at once beat one; eight parallel parts barely beat one (one 256 MiB object, medians of 3) measured:

Parallel ranged GETs helped downloads (363 to 477 MB/s); parallel parts barely helped uploads (80 to 112 MB/s) because the store, one filer on one CPU and three volume servers on half a CPU each, was already the bottleneck. That is the lesson that transfers: concurrency moves the limit from the client's round trips to the servers, and on a laptop the servers are small. On S3 the server side is effectively unbounded and the limit becomes the node's network card.

What a request costs. At S3 Standard's $0.005 per 1,000 PUTs and $0.0004 per 1,000 GETs (AWS Price List, published 2026-10-15, us-east-1) published, writing a million 4 KiB files costs $5.00 in requests and their 4.1 GB of storage $0.09 a month derived: small objects are billed by count, not size.

S3 Express One Zone, and the run that filled the store (depth)

S3 Express One Zone trades durability across zones for "consistent, single-digit millisecond data access" in one Availability Zone, up to "200,000 read TPS" and "100,000 write TPS" per directory bucket ({{AWS|https://docs.aws.amazon.com/AmazonS3/latest/userguide/directory-bucket-high-performance.html}}) vendor, at $0.11 per GB-month against $0.023: a place for hot data and fast checkpoints, not for the copy of record.
