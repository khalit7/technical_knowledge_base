5. Object storage: what it promises, and how fast it goes

An object store keeps objects (a key, the bytes, a little metadata) in buckets. The key ckpt/step_000200/__3_0.distcp looks like a path, but there are no directories: the slashes are characters, and "listing a directory" is asking for keys that start with a prefix. The rules below are Amazon S3's, quoted from its documentation (read 2026-10-16); Google Cloud Storage and Azure Blob differ in detail, not in kind. Every behaviour marked measured ran against SeaweedFS 4.48 set up as a real distributed store (one master, three volume servers, one filer with its S3 gateway, in capped containers; src/runs/run_seaweed.sh).

The semantics, and what each one means for a checkpoint writer

  • Whole objects, atomically: old or new, never partial; an upload in progress is invisible, so no half-written checkpoint is ever seen.
  • Strong read-after-write (since 2020-12-01): a restarted job sees the latest pointer as soon as the writer got its 200.
  • Nothing across keys: a checkpoint of many shards is complete only when a marker written last says so (DCP's .metadata).
  • Conditional writes (If-None-Match, If-Match, 2024): two jobs cannot claim one checkpoint directory; a "latest" pointer updates by compare-and-swap.
  • No rename: "write to .tmp, then rename" becomes "upload under the final key, marker last".
  • Multipart upload: big shards go up as parallel parts of 5 MiB to 5 GiB, each retried alone; unfinished uploads stay (and bill) until aborted.
  • Listing: at most 1,000 keys per request, so keep a small index object instead of listing 100,000 shards.

The throughput model: requests, prefixes and connections

Per request. S3 quotes "roughly 100-200 milliseconds" of latency for small objects and to the first byte of large ones, and "at least 3,500 PUT/COPY/POST/DELETE or 5,500 GET/HEAD requests per second per partitioned Amazon S3 prefix. There are no limits to the number of prefixes in a bucket." Scaling to a higher rate "happens gradually", with "503 (Slow Down)" errors meanwhile ({{S3 performance guide|https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html}}) vendor. So a checkpoint of 16,384 shards written in one second under one prefix asks for 4.7 times one prefix's write rate derived (16,384 / 3,500): spread keys over prefixes (by rank, for example) and retry with backoff.

Per connection. One connection is limited by its latency, so throughput comes from many at once: "You can use concurrent connections to Amazon S3 to fetch different byte ranges from within the same object", aligned to the upload's parts, up to a single instance's "100 Gb/s".

Fig. 2, step by step: one bucket, one client

  1. A bucket of whole objects. Keys such as ckpt/step_000200/__3_0.distcp look like paths, but the bucket is flat: listing asks for a prefix, at most 1,000 keys per request (5,000 keys took 5 requests here measured).
  2. PUT writes a whole object, atomically. Old or new, never half. No rename: a copy and a delete move every byte again (64 MiB: 0.49 s, against 0.66 s to upload measured).
  3. Multipart: parts in parallel. 8 MiB parts: 80 MB/s one at a time, 112 MB/s eight at a time measured; the stand-in store was already the limit.
  4. One GET at a time. S3 quotes 100-200 ms to the first byte; one stream of 8 MiB ranges read 363 MB/s on the stand-in measured.
  5. Eight ranged GETs at once. 477 MB/s measured. On S3 the servers are effectively unbounded, so the node's network card becomes the limit.
  6. Prefixes partition the request rate. 3,500 writes or 5,500 reads a second per prefix: spread the keys over prefixes (by rank) and retry 503 Slow Down with backoff.

What transfers from the stand-in (Fig. 2, steps 3 to 5): concurrency moves the limit from the client's round trips to the servers. Uploads barely gained because the store (one filer on one CPU, three volume servers on half a CPU each) was already the bottleneck; on S3 the server side is effectively unbounded and the node's network card becomes the limit.

What a request costs. At S3 Standard's $0.005 per 1,000 PUTs and $0.0004 per 1,000 GETs (AWS Price List, published 2026-10-15, us-east-1) published, writing a million 4 KiB files costs $5.00 in requests and their 4.1 GB of storage $0.09 a month derived: small objects are billed by count, not size.

Fast clients, S3 Express One Zone, and the run that filled the store (depth)

s5cmd's README quotes a user benchmark in which it "can saturate a 40Gbps link (~4.3 GB/s), whereas s3cmd and aws-cli can only reach 85 MB/s and 375 MB/s" ({{s5cmd|https://github.com/peak/s5cmd}}) independent, undated.

S3 Express One Zone trades durability across zones for "consistent, single-digit millisecond data access" in one Availability Zone, up to "200,000 read TPS" and "100,000 write TPS" per directory bucket ({{AWS|https://docs.aws.amazon.com/AmazonS3/latest/userguide/directory-bucket-high-performance.html}}) vendor, at $0.11 per GB-month against $0.023: a place for hot data and fast checkpoints, not for the copy of record.
