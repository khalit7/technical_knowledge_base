2. How a parallel file system works: Lustre, piece by piece

Lustre is the reference design (open source, on most of the largest supercomputers, and underneath managed services such as Amazon FSx for Lustre), so it is taught in full; section 3 shows how the others differ. Current release 2.17.0, tagged 2025-12-30 ({{lustre.org|https://www.lustre.org/}}; {{lustre-release tag 2.17.0|https://github.com/lustre/lustre-release/tree/2.17.0}}). Illustrative, built from the manual's I/O path and from nfs(5)'s close-to-open rule; drawn to scale in bytes (each square is 1 MiB), not in time. Toggle the system; the step list explains each step.

Lustre: two metadata requests in all (create and close), for any file size; NFS: one server takes the name and every byte, and close() flushes and reports write errors.

The one idea. A file's entry on the MDT holds its layout: a list of objects, each on one OST, plus the stripe size. "When a client wants to read from or write to a file, it first fetches the layout EA from the MDT object for the file. The client then uses this information to perform I/O on the file, directly interacting with the OSS nodes where the objects are stored." The metadata server is asked once per open; the bytes never pass through it.

Follow one 8 MiB write through both designs (toggle on the card):

  1. The job wants to write 8 MiB. Rank 3 is about to write its 8 MiB checkpoint shard. The file does not exist yet.
  2. open(O_CREAT) goes to the metadata server. The client's MDC sends one create request to the MDS. No data moves yet.
  3. The MDS picks four OSTs and returns the layout. It creates one object on each of OST 0 to 3, stores the layout (4 objects, 1 MiB stripes) in the file's entry on the MDT, and hands it to the client.
  4. The client computes where every MiB goes. MiB k goes to object k mod 4, at object offset (k div 4) x 1 MiB: lov_stripe_number() and lov_stripe_offset(). The MDS is not asked again.
  5. MiB 0 to 3 go to four servers at once. Each OSC talks to its own OSS, in parallel. Each OST takes the extent lock on its object for this client.
  6. MiB 4 to 7 follow. Each object now holds 2 MiB. No server saw more than a quarter of the bytes.
  7. close() tells the MDS; the size lives on the OSTs. The file's size is the sum of what its objects hold; a later stat asks the OSTs. Two metadata requests in all, for any file size.
  1. The job wants to write 8 MiB. Rank 3 is about to write its 8 MiB checkpoint shard to an NFS mount.
  2. open(O_CREAT) goes to the NFS server. The one server creates the name; it will also take every byte.
  3. MiB 0 to 3 go to the server. All through one network card and one set of disks.
  4. MiB 4 to 7 follow. 8 MiB through one machine; every other node writing now shares it.
  5. close() flushes and reports errors. Close-to-open consistency: "when the application closes the file, the NFS client writes back any pending changes" and reports write errors in close() (nfs(5)). Another node sees the data when it opens the file after this.

Striping: which server holds byte X

A concrete case first. A file with 1 MiB stripes over 4 objects: MiB 0 goes to object 0, MiB 1 to object 1, ..., MiB 4 back to object 0. So the byte at 5 MiB lands in object 1, at offset 1 MiB inside it derived. A layout is RAID 0 across its objects: "If the MDT file points to more than one object, the file data is striped across the objects using RAID 0, and each object is stored on a different OST."

Fig. 1, step by step: one file, then four, on the toy file system

  1. The parts. A client node, the metadata server with its target (names and layouts), and four object storage targets, each held to 25 MB/s: tpfs, the toy file system built for this page, using Lustre's arithmetic.
  2. Open: one request for the layout. The client asks the metadata server once for the objects, their OSTs and the stripe size (1 MiB); after that it is not asked again, and the bytes never pass through it.
  3. Stripe count 1, the default. Every 1 MiB stripe of the 128 MiB file goes to one object (on OST 0 in the run): one server works while three idle, 22.2 MB/s.
  4. Stripe count 2. Two objects (OSTs 3 and 0); stripe k goes to object k mod 2, both written at once: 44.8 MB/s.
  5. Stripe count 4: every server busy. Four objects (OSTs 1, 2, 3, 0). MiB 5 goes to object 5 mod 4 = 1 (here on OST 2), at offset 1 MiB inside it. 88.7 MB/s: linear in the stripe count.
  6. Four ranks, four files, spread. Four writers of 64 MiB each at stripe count 1, the four files on four different OSTs: 88.9 MB/s together.
  7. The same four files on one OST. lfs setstripe -i 0 copied from an example puts every file on OST 0: 25.0 MB/s, a quarter. The hot spot hurts, not the stripe count.

With stripe size S (bytes to one object before moving on) and stripe count C (how many objects), byte X of the file lands in

stripe = ⌊(X mod S·C) / S⌋    object offset = ⌊X / (S·C)⌋·S + (X mod S)
S
stripe size, default 1 MiB ("the default value for stripe_size is 1MB"; a multiple of 64 KB)
C
stripe count, default 1 ("The default value for stripe_count is 1 stripe for file"); -1 means every OST
stripe
index into the layout's object list; the MDS chose each object's OST when the file was created

What striping costs. More objects mean "more locks and extra network operations during common operations such as stat and unlink", and "when files are striped across all servers and one of the servers breaks down, a small part of each striped file is lost." "Small files do not benefit from striping." The manual's rule: "stripe over as few objects as will meet those needs and no more", bounded by "the I/O rate of the clients/jobs divided by the performance per OSS".

Four files or one shared file striped four ways: which is faster? About the same: 88.9 MB/s for four files with one stripe each, 97.8 MB/s for one file striped four ways measured, medians of 3. Striping matters when few files must use many servers; when every rank writes its own file and the files are spread, the servers are already all busy. What hurts is when they are not spread: the same four files forced onto OST 0 (lfs setstripe -i 0 copied from an example) or one shared file left at stripe count 1 ran at 25.0 and 24.9 MB/s, a quarter. The manual: the default start index of -1 "allows the MDS to choose the starting index. This setting is strongly recommended"; and with 100 clients and 100 servers, one object per file means "no contention", while 100 objects per file means "the clients all compete with one another for the attention of the servers".

Locks: why many writers in one stripe are slow

Each OST runs its own lock manager (the LDLM) for the byte ranges of its objects, and a client caches data only while it holds the lock. "When writing to a single file from multiple nodes, having more than one client writing to a stripe can lead to issues with lock exchange, where clients contend over writing to that stripe, even if their I/Os do not overlap. This can be avoided if I/O can be stripe aligned so that each stripe is accessed by only one client." The toy has no locks, so on real Lustre an N-to-1 shared checkpoint with unaligned writes does much worse than the toy shows. DCP's one file per rank sidesteps it.

Where does byte X live: Lustre's own code, and a calculator over plain and PFL layouts (depth)
lustre/lov/lov_offset.c, lines 273-288, lustre-release tag 2.17.0
/* compute which stripe number "lov_off" will be written into */
int lov_stripe_number(struct lov_stripe_md *lsm, int index, u64 lov_off)
{
	unsigned long ssize = lsm->lsm_entries[index]->lsme_stripe_size;
	u64 stripe_off;
	u64 swidth;

	swidth = stripe_width(lsm, index);

	lov_off = div64_u64_rem(lov_off, swidth, &stripe_off);

	/* Puts stripe_off/ssize result into stripe_off */
	stripe_off = div_u64(stripe_off, ssize);

	return (int) stripe_off;
}

stripe_width() (lines 20-30) returns stripe size times stripe count; index picks the layout component. lov_stripe_offset() (lines 121-152) computes the object offset, *obdoff = lov_off * ssize + stripe_off. The calculator below runs exactly this arithmetic, and so does the toy file system.

Layouts that adapt (PFL, Data on MDT) and what you type on a real client (depth)

A Progressive File Layout (PFL, since 2.10) gives one file several components by offset, so small files stay on one OST and big ones spread out without anyone choosing in advance. The manual's example on 8 OSTs: lfs setstripe -E 4M -c 1 -E 64M -c 4 -E -1 -c -1 -i 4 /mnt/testfs/create_comp: "The first component has 1 stripe and covers [0, 4M), the second component has 4 stripes and covers [4M, 64M), and the last component stripes start at OST4, cross over all available OSTs and covers [64M, EOF)." Components after the first are created only when a write reaches them. Amazon FSx for Lustre file systems created after August 25, 2023 default to lfs setstripe -E 100M -c 1 -E 10G -c 8 -E 100G -c 16 -E -1 -c 32 ({{FSx performance guide|https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance.html}}) vendor. The trap: appending to a file with a wide last component instantiates every component, and "an operation such as reading the file length will send a request in parallel to every OST" (FSx guide), so FSx gives files opened in append mode a stripe count of 1.

Data on MDT (DoM, since 2.11) puts the first part of a file on the metadata server itself, so a small file costs one server instead of two: "improves small file IO by placing small files directly on the MDT". The default maximum is 1 MB (dom_stripesize). Example: lfs setstripe -E 1M -L mdt -E -1 -S 4M -c -1 /mnt/lustre/domfile. On DoM layouts without an end-of-file component, "writes beyond the end of the last existing component will fail with error ENODATA".

The toy file system: how it is built, smaller stripes, and what transfers to a real cluster (provenance)

src/runs/tpfs.py, standard-library Python: one metadata server that hands out layouts and four object servers that store the bytes, each in its own container (0.5 CPU, 256 MB), each held to 25 MB/s by a token bucket. The client gets a file's layout once and then talks to the object servers directly, using Lustre's RAID 0 arithmetic. The per-server limit is an input; the scaling, the hot spots and the slowdowns are what happened (Apple M1 Pro, Docker Desktop VM, shared machine, 2026-10-16; medians of 3).

docker network create sd-net
for i in 0 1 2 3; do
  docker run -d --rm --name sd-ost$i --network sd-net -v $PWD/tpfs.py:/tpfs.py:ro \
    --memory 256m --cpus 0.5 python:3.12-slim python3 /tpfs.py ost --mbps 25
done
docker run -d --rm --name sd-mds0 --network sd-net -v $PWD/tpfs.py:/tpfs.py:ro \
  --memory 256m --cpus 0.5 python:3.12-slim \
  python3 /tpfs.py mds --osts sd-ost0:9000,sd-ost1:9000,sd-ost2:9000,sd-ost3:9000
docker run -d --rm --name sd-cli --network sd-net -v $PWD/tpfs.py:/tpfs.py:ro \
  --memory 768m --cpus 2 python:3.12-slim sleep 3600

What transfers to a real cluster: the arithmetic (one file's bandwidth is its stripe count times one server's, until the client's network card or the job's other files get in the way), the hot spot when files share a server, and the cost of small stripes. What does not: the absolute numbers (25 MB/s per server is a choice, a real OST does gigabytes), locks, and the client-side caching and RPC pipelining that make Lustre's per-request costs far lower than Python's.
