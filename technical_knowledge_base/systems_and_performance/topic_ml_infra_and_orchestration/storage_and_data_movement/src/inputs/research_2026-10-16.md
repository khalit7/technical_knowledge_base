## 1. Lustre

Source for 1.1 to 1.9 unless stated: Lustre Software Release 2.x Operations Manual, https://doc.lustre.org/lustre_manual.xhtml (single XHTML, downloaded whole and grepped; the manual carries no single release date on its title page; it says "This document is maintained by Whamcloud in Docbook format"). ### 1.1 Components
- MGS: "The MGS stores configuration information for all the Lustre file systems in a cluster and provides this information to other Lustre components." (Section 1.2.1) [doc]
- MDS: "The MDS makes metadata stored in one or more MDTs available to Lustre clients. Each MDS manages the names and directories in the Lustre file system(s) and provides network request handling for one or more local MDTs." (1.2.2) [doc]
- MDT: "The MDT stores metadata (such as filenames, directories, permissions and file layout) on storage attached to an MDS." (1.2.2) [doc]
- OSS: "The OSS provides file I/O service and network request handling for one or more local OSTs. Typically, an OSS serves between two and eight OSTs, up to 16 TiB each." (1.2.2) [doc]
- OST: "User file data is stored in one or more objects, each object on a separate OST in a Lustre file system." (1.2.2) [doc]
- Clients: "The client software includes a management client (MGC), a metadata client (MDC), and multiple object storage clients (OSCs), one corresponding to each OST in the file system." and "A logical object volume (LOV) aggregates the OSCs to provide transparent access across all the OSTs." (1.2.2) [doc]
- LMV: "A logical metadata volume (LMV) aggregates the MDCs to provide transparent access across all the MDTs in a similar manner as the LOV does for file access." [doc]
- LNet: "Lustre Networking (LNet) is a custom networking API that provides the communication infrastructure that handles metadata and file I/O data for the Lustre file system servers and clients." (1.2.3) [doc]
- Sizing table (Table 1.2): MDSs "1-2% of file system capacity"; OSSs "1-128 TiB per OST, 1-8 OSTs per OSS"; Clients "No local storage needed". [doc]
- Note: the manual is internally inconsistent on OST size ("up to 16 TiB each" in 1.2.2 vs "1-128 TiB per OST" in Table 1.2); both quoted verbatim.
- Concurrent access: "Several clients can write to different parts of the same file simultaneously, while, at the same time, other clients can read from the file." [doc]

### 1.2 What the MDT stores for a file; RAID 0
- "Information about where file data is located on the OST(s) is stored as an extended attribute called layout EA in an MDT object identified by the FID for the file" (1.3) [doc]
- "If the MDT file points to more than one object, the file data is striped across the objects using RAID 0, and each object is stored on a different OST." (1.3) [doc]
- I/O path: "When a client wants to read from or write to a file, it first fetches the layout EA from the MDT object for the file. The client then uses this information to perform I/O on the file, directly interacting with the OSS nodes where the objects are stored." (1.3) [doc]
- FID: "A FID is a 128-bit identifier, which contains a unique 64-bit sequence number (SEQ), a 32-bit object ID (OID), and a 32-bit version number." (1.3) [doc]
- Bandwidth rule: "The aggregate bandwidth equals the minimum of the disk bandwidth and the network bandwidth." (1.3) [doc]

### 1.3 Striping and defaults
- "One of the main factors leading to the high performance of Lustre file systems is the ability to stripe data across multiple OSTs in a round-robin fashion." (1.3.1) [doc]
- "Striping can be used to improve performance when the aggregate bandwidth to a single file exceeds the bandwidth of a single OST." (1.3.1) [doc]
- "When the chunk of data being written to a particular object exceeds the stripe_size, the next chunk of data in the file is stored on the next object." (1.3.1) [doc]
- Defaults: "The default value for stripe_count is 1 stripe for file and the default value for stripe_size is 1MB. The user may change these values on a per directory or per file basis." (1.3.1) [doc]  CONFIRMED: stripe_count 1, stripe_size 1 MB.

### 1.4 Maximum stripe count
- "Although a single file can only be striped over 2000 objects, Lustre file systems can have thousands of OSTs. ... On systems with more than 2000 OSTs, clients can do I/O using multiple files to utilize the full file system bandwidth." [doc]
- "ldiskfs filesystems without the ea_inode feature limit the maximum stripe count for a single file to 160 OSTs." [doc]
- Limits table: "A single file can have a maximum of 2000 stripes, which gives an upper single file data capacity of 31.25 PiB for 64-bit ldiskfs systems." [doc]  CONFIRMED: 2000.
- Since 2.13 ea_inode is the default: "With a ZFS-based MDT, or if the ea_inode feature is enabled for an ldiskfs-based MDT (the default since Lustre 2.13.0), a file can be striped across up to 2000 OSTs." (19.1) [doc]
- Allocation: "the MDS allocates objects to OSTs using either a round-robin algorithm or a weighted algorithm. When the amount of free space is well balanced (i.e., by default, when the free space across OSTs differs by less than 17%), the round-robin algorithm is used" (19.1) [doc]

### 1.5 lfs setstripe options
- Synopsis (19.3), verbatim: `lfs setstripe [--size|-s stripe_size] [--stripe-count|-c stripe_count] [--overstripe-count|-C stripe_count] [--index|-i start_ost] [--pool|-p pool_name] filename|dirname` [doc]
- Note: the manual's synopsis uses `-s` / `--size` for stripe size; the PFL and DoM examples use `-S 4M` (e.g. `lfs setstripe -E 1M -L mdt -E -1 -S 4M -c -1 /mnt/lustre/domfile`). Both spellings appear verbatim in the manual.
- -S / stripe_size: "The stripe_size indicates how much data to write to one OST before moving to the next OST. The default stripe_size is 1 MB. Passing a stripe_size of 0 causes the default stripe size to be used. Otherwise, the stripe_size value must be a multiple of 64 KB." [doc]
- -c / stripe_count: "The default stripe_count value is 1. Setting stripe_count to 0 causes the default stripe count to be used. Setting stripe_count to -1 means stripe over all available OSTs (full OSTs are skipped)." [doc]
- -i / start_ost: "The default value for start_ost is -1, which allows the MDS to choose the starting index. This setting is strongly recommended" [doc]
- -E / PFL: "The -E option is used to specify the end offset (in bytes or using a suffix kMGTP e.g. 256M) of each component, and it also indicates the following STRIPE_OPTIONS are for this component." and "A -1 end offset or eof indicates this is the last component extending to the end of file." (19.5.1.1) [doc]
- Directory default: "In a directory, the lfs setstripe command sets a default striping configuration for files created in the directory." (19.3.2) [doc]

### 1.6 Stripe size and stripe count guidance (shared file vs file per process)
- Rule of thumb: "A good rule of thumb is to stripe over as few objects as will meet those needs and no more." (19.2) [doc]
- Shared file use case: "Examples are a scientific application that writes to a single file from hundreds of nodes, or a binary executable that is loaded by many nodes when an application starts." ... "Striping across a larger number of OSSs should only be used when the file size is very large and/or is accessed by many nodes at a time." (19.2) [doc]
- Upper bound: "The largest useful stripe count is bounded by the I/O rate of the clients/jobs divided by the performance per OSS." (19.2) [doc]
- Lock contention on a shared file (Introduced in 2.13 paragraph): "When writing to a single file from multiple nodes, having more than one client writing to a stripe can lead to issues with lock exchange, where clients contend over writing to that stripe, even if their I/Os do not overlap. This can be avoided if I/O can be stripe aligned so that each stripe is accessed by only one client." (19.2) [doc]
- Overstriping: "Since Lustre 2.13, the 'overstriping' feature is available, allowing more than one stripe per OST. This is particularly helpful for the case where thread count exceeds OST count" (19.2) [doc]
- File per process, argument against wide striping: "Consider a cluster with 100 clients and 100 OSSs, each with one OST. If each file has exactly one object and the load is distributed evenly, there is no contention and the disks on each server can manage sequential I/O. If each file has 100 objects, then the clients all compete with one another for the attention of the servers, and the disks on each node seek in 100 different directions resulting in needless contention." (19.2) [doc]
- Overhead: "Striping results in more locks and extra network operations during common operations such as stat and unlink." [doc]
- Risk: "When files are striped across all servers and one of the servers breaks down, a small part of each striped file is lost." [doc]
- Small files: "Small files do not benefit from striping because they can be efficiently stored and accessed as a single OST object or even with Data on MDT." [doc]
- Stripe size (19.2.1): "The smallest recommended stripe size is 512 KB." ... "the Lustre file system sends 1MB chunks over the network." ... "A good stripe size for sequential I/O using high-speed networks is between 1 MB and 4 MB. In most situations, stripe sizes larger than 4 MB may result in longer lock hold times and contention during shared file access." ... "The maximum stripe size is 4 GB." ... "If the file is written in a consistent and aligned way, make the stripe size a multiple of the write() size." [doc]

### 1.7 LDLM (locks)
- "The Lustre distributed lock manager (LDLM) ensures that files are coherent between all clients and servers in the file system. The MDT LDLM manages locks on inode permissions and pathnames. Each OST has its own LDLM for locks on file stripes stored thereon, which scales the locking performance as the file system grows." (1.1 features) [doc]
- lfs ladvise (34.8): "lockahead Request an LDLM extent lock of the given mode on the given byte range" and "noexpand Disable extent lock expansion behavior for I/O to this file descriptor"; "it is used in special cases to avoid pathological results (lock exchange) from the normal LDLM locking behavior." [doc]
- UNCONFIRMED in the manual: an explicit sentence that the server grants extent locks expanded to cover the whole object by default (the "lock expansion" mechanism is only implied by "noexpand"). The lock-exchange quote above (19.2) is the clearest manual statement of shared-file write contention.

### 1.8 PFL (Progressive File Layouts, since 2.10)
- Purpose: "users do not necessarily need to know the size or concurrency of output files in advance of their creation and explicitly specify an optimal layout for each file in order to achieve good performance for both highly concurrent shared-single-large-file IO or parallel IO to many smaller per-process files." (19.5) [doc]
- Structure: "A PFL file is essentially an array of sub-layout components, with each sub-layout component being a plain layout covering different and non-overlapped extents of the file." [doc]
- Lazy instantiation: "When a file range with defined but not instantiated component is accessed, clients will send a Layout Intent RPC to the MDT, and the MDT would instantiate the objects of the components covering that range." [doc]
- Example from the manual (19.5.1.1, assumes 8 OSTs, stripe size 1MB default), verbatim:
```
$ lfs setstripe -E 4M -c 1 -E 64M -c 4 -E -1 -c -1 -i 4 \
/mnt/testfs/create_comp
```
  "The first component has 1 stripe and covers [0, 4M), the second component has 4 stripes and covers [4M, 64M), and the last component stripes start at OST4, cross over all available OSTs and covers [64M, EOF)." [doc]
- "Only the first component's OST objects of the PFL file are instantiated when the layout is being set. Other instantiation is delayed to later write/truncate operations." [doc]
- Figure 19.1 text: a 2055MB file in 3 components; "The stripe size for the first two components is 1MB, while the stripe size for the third component is 4MB." ... "The final component holds the next 1800MB spread over 32 OST objects." [doc]

### 1.10 DoM (Data on MDT, since 2.11)
- Purpose: "The Lustre Data on MDT (DoM) feature improves small file IO by placing small files directly on the MDT, and also improves large file IO by avoiding the OST being affected by small random IO that can cause device seeking and hurt the streaming IO performance." (20.1) [doc]
- "The layout of a DoM file is stored on disk as a composite layout and is a special case of Progressive File Layout (PFL)." [doc]
- Default max: "The MDT controls the default maximum DoM size on the server via the parameter dom_stripesize in the LOD device. ... The default value of the parameter is 1MB and can be changed with lctl tool." (20.2.6) [doc]  CONFIRMED 1 MB.
- Example: `lfs setstripe -E 1M -L mdt -E -1 -S 4M -c -1 /mnt/lustre/domfile` "The first component has an mdt layout and is placed on the MDT, covering [0, 1M). The second component covers [1M, EOF) and is striped over all available OSTs." [doc]
- Pitfall: "if an EOF component is not present, then writes beyond the end of the last existing component will fail with error ENODATA" [doc]

### 1.11 DNE (Distributed Namespace)
- Remote directories: "Using the DNE feature it is possible to dedicate additional MDTs to sub-directories off the file system root directory stored on MDT0000 ... using the lfs mkdir -i mdt_index command. If an MDT serving a subdirectory becomes unavailable, any subdirectories on that MDT and all directories beneath it will also become inaccessible." (5.1.1 note) [doc]
- Striped directories (2.8+): "it is possible to spread a single large directory across multiple MDTs using the DNE striped directory feature by specifying multiple stripes (or shards) at creation time using the lfs mkdir -c stripe_count command" ... "This is indended for specific applications where many output files are being created in one large directory (over 50k entries)." (spelling "indended" as in the manual) [doc]
- 13.10: "metadata requests for files in a single large striped directory are serviced by multiple MDTs" ... "Normally, all files in a directory must be created on a single MDT." Command: `lfs mkdir -c mdt_count /mount_point/new_directory` [doc]

### 1.13 Source: offset to stripe mapping (lustre-release tag 2.17.0)
File: lustre/lov/lov_offset.c at tag 2.17.0, https://raw.githubusercontent.com/lustre/lustre-release/2.17.0/lustre/lov/lov_offset.c (identical at tag v2_17_0). Read 2026-10-16. [src]

Lines 20--30, stripe width = stripe size x stripe count (DoM entry: just stripe size):
```c
u64 stripe_width(struct lov_stripe_md *lsm, unsigned int index)
{
	struct lov_stripe_md_entry *entry = lsm->lsm_entries[index];

	LASSERT(index < lsm->lsm_entry_count);

	if (lsme_is_dom(entry))
		return entry->lsme_stripe_size;

	return (u64)entry->lsme_stripe_size * entry->lsme_stripe_count;
}
```
Lines 273--288, which stripe a file offset lands in:
```c
/* compute which stripe number "lov_off" will be written into */
int lov_stripe_number(struct lov_stripe_md *lsm, int index, u64 lov_off)
{
	unsigned long ssize = lsm->lsm_entries[index]->lsme_stripe_size;
	u64 stripe_off;
	u64 swidth;

	swidth = stripe_width(lsm, index);

	lov_off = div64_u64_rem(lov_off, swidth, &stripe_off);

	/* Puts stripe_off/ssize result into stripe_off */
	stripe_off = div_u64(stripe_off, ssize);

	return (int) stripe_off;
}
```
Lines 121--152, file offset to offset inside that stripe's object (core lines):
```c
int lov_stripe_offset(struct lov_stripe_md *lsm, int index, loff_t lov_off,
		      int stripeno, loff_t *obdoff)
{
	unsigned long ssize  = lsm->lsm_entries[index]->lsme_stripe_size;
	u64 stripe_off, this_stripe, swidth;
	...
	swidth = stripe_width(lsm, index);

	lov_off = div64_u64_rem(lov_off, swidth, &stripe_off);

	this_stripe = (u64)stripeno * ssize;
	...
	*obdoff = lov_off * ssize + stripe_off;
	return ret;
}
```
In words: stripe number = (offset mod (stripe_size x stripe_count)) div stripe_size; object offset = (offset div stripe_width) x stripe_size + remainder within the stripe. The `index` argument selects the PFL component (lsm_entries[index]).

### 2.2 Original GPFS paper (design; still the clearest statement of wide striping)
Schmuck and Haskin, "GPFS: A Shared-Disk File System for Large Computing Clusters", USENIX FAST 2002, https://static.usenix.org/events/fast02/full_papers/schmuck/schmuck_html/index.html , read 2026-10-16. [indep: peer-reviewed paper by IBM Research authors, so vendor-authored]
- "All nodes in the cluster have equal access to all disks."
- "Files are striped across all disks in the file system – several thousand disks in the largest GPFS installations." (the dash is in the original)
- "Large files in GPFS are divided into equal sized blocks," and "consecutive blocks are placed on different disks in a round-robin fashion."
- 2002 block size: "To minimize seek overhead, the block size is large (typically 256k, but can be configured between 16k and 1M)." (historical; today's default is 4 MiB, see 2.1)
- "The GPFS architecture is fundamentally based on distributed locking."
- "The token manager keeps track of all lock tokens granted to all nodes in the cluster."
- "The metanode for a particular file is elected dynamically with the help of the token server."
- "each node becomes metanode for the files it uses and handles all metadata updates locally."
- Contrast with SAN file systems where "all metadata updates are still handled by a centralized metadata server."
- Takeaway for the page: GPFS has no dedicated metadata server: metadata lives on the shared disks, the token manager hands out locks, and one node per open file (the metanode) writes its inode updates. Contrast with Lustre's dedicated MDS/MDT.

## 3. WEKA, VAST, DAOS, DeepSeek 3FS, Meta Tectonic

### 3.1 DeepSeek 3FS (Fire-Flyer File System)
Sources: README https://github.com/deepseek-ai/3FS (raw main branch README.md) and docs/design_notes.md (raw main), read 2026-10-16. Repository created "2025-02-27T13:36:53Z" (GitHub API created_at; DeepSeek released it during its Open Source Week, end of February 2025; last push "2026-05-07"). All numbers are DeepSeek's own measurements on its own clusters: [vendor] in the sense of self-reported by the author, open source (MIT).
- What it is: "The Fire-Flyer File System (3FS) is a high-performance distributed file system designed to address the challenges of AI training and inference workloads. It leverages modern SSDs and RDMA networks to provide a shared storage layer that simplifies development of distributed applications."
- Disaggregated: "Combines the throughput of thousands of SSDs and the network bandwidth of hundreds of storage nodes, enabling applications to access storage resource in a locality-oblivious manner."
- CRAQ: "Implements Chain Replication with Apportioned Queries (CRAQ) for strong consistency, making application code simple and easy to reason about."
- Metadata: "Develops stateless metadata services backed by a transactional key-value store (e.g., FoundationDB)."
- Checkpointing listed as a target workload: "Supports high-throughput parallel checkpointing for large-scale training."
- Components (design notes): "The 3FS system has four components: cluster manager, metadata service, storage service and client. All components are connected in an RDMA network (InfiniBand or RoCE)."
- Chunks: "A 3FS file is split into equally sized chunks, which are replicated over multiple SSDs." and "3FS divides file data into equally sized chunks and stripes them across multiple replication chains" ... "Users can specify the chain table, chunk size, and stripe size for files on a per-directory basis."
- Client computes placement: "When an application opens a file, the client contacts the meta service to obtain the file's data layout information. Then the client can independently compute chunk IDs and chains for data operations, minimizing the involvement of the meta service in the critical path." (same idea as Lustre's layout EA)
- Production stripe: "Our production environments use a large stripe size: 200."
- CRAQ write path: "In CRAQ write requests are sent to the head target and propagated along a chain. Read requests can be sent to any of the storage target." and "CRAQ is a write-all-read-any replication protocol optimized for read-heavy workloads."
- Clients: "Two clients are developed for applications: FUSE client and native client. Most applications use FUSE client, which has a low adoption barrier. Performance-critical applications are integrated with the native client."
- FUSE limit measured: "Our benchmark results indicate that FUSE only handles approximately 400K 4KiB reads per second." and "FUSE on Linux 5.x does not support concurrent writes to the same file"
- Native client (USRBIO): "we have chosen to implement a native client within the FUSE daemon. This client offers an interface that supports asynchronous zero-copy I/O operations. File meta operations are still handled by FUSE daemon" ... "The asynchronous, zero-copy API is inspired by Linux io_uring." (Iov = shared memory region, Ior = ring buffer)
- Peak throughput, verbatim: "This cluster consists of 180 storage nodes, each equipped with 2×200Gbps InfiniBand NICs and sixteen 14TiB NVMe SSDs. Approximately 500+ client nodes were used for the read stress test, with each client node configured with 1x200Gbps InfiniBand NIC. The final aggregate read throughput reached approximately 6.6 TiB/s with background traffic from training jobs."
  - Sanity check (mine): 180 x 2 x 200 Gb/s = 72 Tb/s = 9 TB/s of storage NIC line rate; 6.6 TiB/s is about 7.3 TB/s, about 80 percent of it.
- GraySort, verbatim: "The test cluster comprised 25 storage nodes (2 NUMA domains/node, 1 storage service/NUMA, 2×400Gbps NICs/node) and 50 compute nodes (2 NUMA domains, 192 physical cores, 2.2 TiB RAM, and 1×200 Gbps NIC/node). Sorting 110.5 TiB of data across 8,192 partitions completed in 30 minutes and 14 seconds, achieving an average throughput of 3.66 TiB/min."
- KVCache, verbatim: "The top figure demonstrates the read throughput of all KVCache clients (1×400Gbps NIC/node), highlighting both peak and average values, with peak throughput reaching up to 40 GiB/s."

### 3.2 Meta Tectonic
Pan et al., "Facebook's Tectonic Filesystem: Efficiency from Exascale", USENIX FAST '21 (February 2021), https://www.usenix.org/conference/fast21/presentation/pan , PDF https://www.usenix.org/system/files/fast21-pan.pdf , read 2026-10-16. [indep: peer-reviewed; authored by Meta engineers about their own system]
- "Tectonic is Facebook's exabyte-scale distributed filesystem." (abstract)
- "The foundation of a Tectonic cluster is the Chunk Store (§3.2), a fleet of storage nodes which store and access data chunks on hard drives."
- "On top of the Chunk Store is the Metadata Store (§3.3), which consists of a scalable key-value store and stateless metadata services that construct the filesystem logic over the key-value store."
- "Tectonic delegates filesystem metadata storage to ZippyDB [6], a linearizable, fault-tolerant, sharded key-value store."
- "The Chunk Store is a flat, distributed object store for chunks, the unit of data storage in Tectonic. Chunks make up blocks, which in turn make up Tectonic files."
- "Applications interact with Tectonic through a hierarchical filesystem API with append-only semantics, similar to HDFS"
- One sentence for the page: Tectonic is a client-driven, append-only file system whose Metadata Store (stateless services over ZippyDB, hash-partitioned naming, file and block layers) maps blocks to chunks held by a flat HDD-based Chunk Store. ## 6. Checkpoint formats as storage

### 6.1 safetensors format
README, https://github.com/huggingface/safetensors (main branch), read 2026-10-16. [doc]
- Layout, verbatim:
  - "8 bytes: N, an unsigned little-endian 64-bit integer, containing the size of the header"
  - "N bytes: a JSON UTF-8 string representing the header."
  - "The header is a dict like {"TENSOR_NAME": {"dtype": "F16", "shape": [1, 16, 256], "data_offsets": [BEGIN, END]}, "NEXT_TENSOR_NAME": {...}, ...},"
  - "data_offsets point to the tensor data relative to the beginning of the byte buffer (i.e. not an absolute position in the file), with BEGIN as the starting offset and END as the one-past offset (so total tensor byte size = END - BEGIN)."
  - "A special key __metadata__ is allowed to contain free form string-to-string map."
  - "Rest of the file: byte-buffer."
  - "The byte buffer needs to be entirely indexed, and cannot contain holes."
- Header limit: "Currently, there's a limit on the size of the header of 100MB to prevent parsing extremely large JSON."
- Zero-copy claim and its caveat: the intro says "safely (as opposed to pickle) and that is still fast (zero-copy)", but the notes say "No format is really zero-copy in ML, it needs to go from disk to RAM/GPU RAM (that takes time). On CPU, if the file is already in cache, then it can truly be zero-copy, whereas on GPU there is not such disk cache, so a copy is always required" and "SafeTensors is not zero-copy for the header."
- mmap: "Loading first on CPU with memmapping with torch, and then moving all tensors to GPU seems to be faster too somehow"
- Lazy loading (relevant to sharded reads): "in distributed (multi-node or multi-gpu) settings, it's nice to be able to load only part of the tensors on the various models. For BLOOM using this format enabled to load the model on 8 GPUs from 10mn with regular PyTorch weights down to 45s." [vendor: HF's own measurement]
- Storage takeaway (mine): one small header read gives every tensor's byte range, so a reader can issue ranged GETs (S3) or pread() only for the tensors it needs.

## 7. Published numbers on storage for training at scale

### 7.1 Llama 3 (Meta), arXiv 2407.21783
"The Llama 3 Herd of Models", https://arxiv.org/html/2407.21783v3 , section 3.3.1 "Training Infrastructure", paragraph "Storage." Read 2026-10-16. [indep: paper by the operator, Meta]
- CONFIRMED verbatim: "Tectonic (Pan et al., 2021), Meta's general-purpose distributed file system, is used to build a storage fabric (Battey and Gupta, 2024) for Llama 3 pre-training. It offers 240 PB of storage out of 7,500 servers equipped with SSDs, and supports a sustainable throughput of 2 TB/s and a peak throughput of 7 TB/s. A major challenge is supporting the highly bursty checkpoint writes that saturate the storage fabric for short durations. Checkpointing saves each GPU's model state, ranging from 1 MB to 4 GB per GPU, for recovery and debugging. We aim to minimize GPU pause time during checkpointing and increase checkpoint frequency to reduce the amount of lost work after a recovery."
- Same paper, 3.3.4: "Llama 3 405B is trained on up to 16K H100 GPUs"; "During a 54-day snapshot period of pre-training, we experienced a total of 466 job interruptions. Of these, 47 were planned interruptions ... The remaining 419 were unexpected interruptions" and "we achieved higher than 90% effective training time". [indep]

### 7.2 MLPerf Storage v2.0 (checkpointing workload added)
- MLCommons announcement, https://mlcommons.org/2025/08/mlperf-storage-v2-0-results/ , "August 4, 2025", read 2026-10-16 [indep: benchmark consortium]: "Additionally, the v2.0 benchmark adds new tests that replicate real-world checkpointing for AI training systems." and "MLPerf Storage v2.0 includes >200 performance results from 26 submitting organizations." Failure framing: "if the mean time to failure for an accelerator is 50,000 hours, then a 100,000-accelerator cluster running for extended periods at full utilization will likely experience a failure every half-hour." and "A cluster with one million accelerators would expect to see a failure every three minutes."
- What it measures, from the v2.0 rules (Submission_guidelines.md at tag v2.0, https://raw.githubusercontent.com/mlcommons/storage/v2.0/Submission_guidelines.md , read 2026-10-16) [doc]:
  - Metrics: "The benchmark performance metrics for Checkpoint workloads (write/take, and read/recover) are bandwidth while writing, and bandwidth while reading, plus an additional data point which is the amount of time required, if any, between the completion of writing a checkpoint and the first point at which that checkpoint can be read from a different host node."
  - Procedure: "Write 10x checkpoints" then clear caches, then "Read 10x checkpoints"; "We enforce fsync to be applied during checkpoint writes"; "If the checkpoint size per client node is less than 3x the client node's memory capacity, then the filesystem cache needs to be cleared between the write and read phases."
  - "Checkpoint recovery is intended to mimic an environment where a failure has occurred and the data needs to be read by different hosts than wrote the data."
  - "Submitters do not need to use hardware accelerators (e.g., GPUs, TPUs, and other ASICs) when running MLPerf Storage - Checkpointing."
  - Table 2 LLM models, verbatim:

| Checkpoint size | 105 GB | 912 GB | 5.29 TB | 18 TB |

  - Modes: "default: Used for shared storage systems." and "subset: Intended for node local storage systems."

### 7.4 ByteCheckpoint (ByteDance), arXiv 2407.20143
"ByteCheckpoint: A Unified Checkpointing System for Large Foundation Model Development", https://arxiv.org/html/2407.20143 (v4, "02 Apr 2025"; "Accepted by NSDI'25"). Read 2026-10-16. [indep: peer-reviewed; authors are the operator]
- "Compared to existing open-source checkpointing systems [58, 52], ByteCheckpoint significantly reduces runtime checkpoint stalls, achieving an average reduction of 54.20×. For saving and loading times, ByteCheckpoint achieves improvements of up to 9.96× and 8.80×, respectively." (abstract; baselines are PyTorch DCP and Megatron Distributed Checkpoint)
- Scale: "This full-stack approach scales ByteCheckpoint to support the training of a 405B LFM on 8,960 GPUs while still maintaining high efficiency."
- Intro: "ByteCheckpoint achieves improvements ranging from 12.13× to 161.50× in terms of checkpoint stalls reduction, making the end-to-end checkpoint saving and loading procedures 6.05× and 3.88× faster on average, respectively."
- Storage problem: "the average end-to-end time required to save checkpoints of a GPT 175B model, trained on 4096 GPUs, to HDFS can be 200 seconds." and "massive read/write requests for checkpoint files from the training cluster to the storage systems (e.g., HDFS) can overload the master node, causing delays in file metadata operations."
- HDFS tricks: "single-file read speed has improved from 400 MB/s to 2-3 GB/s, all tested on H800 servers equipped with over 100 CPU cores, TB-level memory, and a 200Gbps NIC." and "we split the target file into several sub-files of fixed size and concurrently write them into HDFS using multi-threading." ... "single-file upload speed can reach 3 GB/s, far exceeding the average read/write throughput of a single HDFS client (under 100 MB/s [48])."
- "We have rewritten all HDFS components, including NameNode, DataNode, and SDK [15], in C++, effectively doubling performance compared to the original Java-based implementation."

### 7.5 DataStates-LLM (Argonne), arXiv 2406.10707
"DataStates-LLM: Lazy Asynchronous Checkpointing for Large Language Models", HPDC '24, arXiv submitted 2024-06-15, https://arxiv.org/abs/2406.10707 (arXiv API), read 2026-10-16. [indep]
- "we introduce a lazy asynchronous multi-level approach that takes advantage of the fact that the tensors making up the model and optimizer state shards remain immutable for extended periods of time, which makes it possible to copy their content in the background with minimal interference during the training process."
- "We evaluate our approach at scales of up to 180 GPUs ... The results show up to 48× faster checkpointing and 2.2× faster end-to-end training runtime compared with the state-of-art checkpointing approaches."
