Every node of a training cluster reads the same datasets, writes its share of every checkpoint and starts from the same code, so somewhere there is storage that all of them share. 1. The problem: one server is one pipe

Four numbers describe any store. Bandwidth is bytes per second for large transfers (GB/s). IOPS (I/O operations per second) is how many small reads or writes it serves. Metadata operations per second counts the operations on names rather than bytes: create, open, stat (ask for a file's size and times), lookup of a name that does not exist, list a directory, delete. Latency is how long one operation takes, which caps what one client doing one thing at a time can get. A store can be fast on one and slow on another, and training jobs hit all four.

What a training job asks of shared storage, and when.

Start-upEvery rank imports Python packages and loads the container image: tens of thousands of opens and lookups each, all ranks at the same second (section 4 counts them: 17,983 file-system calls for import torch).
Reading dataA steady stream of large sequential reads, small next to compute for text and easy to prefetch (the parent's lab and Storage and loading at scale).
CheckpointingEvery few minutes to hours, every rank writes its piece at the same moment while the GPUs wait unless the save is asynchronous: a burst of terabytes (section 9).
Restart and evaluationEvery rank reads the latest checkpoint at once, often into a different number of ranks (section 8); evaluation jobs read many checkpoints.

Why one file server is not enough. An NFS server holds both the names and the bytes, so all of the above goes through one machine's disks and one network card. A modern GPU node can pull more than 40 GB/s by itself (NVIDIA's requirement for SuperPOD nodes, on the sibling Cluster anatomy page), which is already more than a good single server delivers. The parent's lab saw the same shape in miniature: the 304 MB checkpoint took 7.31 s through a host folder shared into the Docker VM (one file-sharing channel) against 387 ms on a Docker volume measured.

The two ways out, and the rest of the page follows them. A parallel file system keeps the POSIX interface (directories, open, seek, rename) but separates the names from the bytes: a few metadata servers answer "where is this file", and the bytes go straight to and from many storage servers at once. An object store gives up POSIX (no rename, no append, no partial overwrite) in exchange for a design that partitions everything by key, so it scales to any number of clients and costs a fraction as much per byte. Large training clusters use both: the object store holds the data and checkpoints of record, a parallel file system or local NVMe holds the working copies.

2. How a parallel file system works: Lustre, piece by piece

Lustre is the reference design (open source, on most of the largest supercomputers, and underneath managed services such as Amazon FSx for Lustre), so it is taught in full here; section 3 shows how the others differ. Current release: 2.17.0, tagged 2025-12-30 (lustre.org; lustre-release tag 2.17.0). Quotes are from the Lustre Operations Manual unless marked.

The one idea. A file's entry on the MDT holds its layout: a list of objects, each on one OST, plus the stripe size. "When a client wants to read from or write to a file, it first fetches the layout EA from the MDT object for the file. The client then uses this information to perform I/O on the file, directly interacting with the OSS nodes where the objects are stored." The metadata server is asked once per open; the bytes never pass through it.

Striping: which server holds byte X

A layout is RAID 0 across its objects: "If the MDT file points to more than one object, the file data is striped across the objects using RAID 0, and each object is stored on a different OST." With stripe size S (bytes written to one object before moving to the next) and stripe count C (how many objects), byte offset X of the file lands in

stripe = ⌊(X mod S·C) / S⌋    object offset = ⌊X / (S·C)⌋·S + (X mod S)
S
stripe size, default 1 MiB ("the default value for stripe_size is 1MB"; must be a multiple of 64 KB)
C
stripe count, default 1 ("The default value for stripe_count is 1 stripe for file"); -1 means every OST
stripe
index into the layout's object list; the MDS chose which OST each object lives on when the file was created
lustre/lov/lov_offset.c, lines 273-288, lustre-release tag 2.17.0
/* compute which stripe number "lov_off" will be written into */
int lov_stripe_number(struct lov_stripe_md *lsm, int index, u64 lov_off)
{
	unsigned long ssize = lsm->lsm_entries[index]->lsme_stripe_size;
	u64 stripe_off;
	u64 swidth;

	swidth = stripe_width(lsm, index);

	lov_off = div64_u64_rem(lov_off, swidth, &stripe_off);

	/* Puts stripe_off/ssize result into stripe_off */
	stripe_off = div_u64(stripe_off, ssize);

	return (int) stripe_off;
}

stripe_width() (lines 20-30) returns stripe size times stripe count; index picks the layout component (below). lov_stripe_offset() (lines 121-152) computes the object offset, *obdoff = lov_off * ssize + stripe_off. The Striping lab has a calculator that runs exactly this arithmetic and our toy file system uses it too.

What it buys. "Striping can be used to improve performance when the aggregate bandwidth to a single file exceeds the bandwidth of a single OST." On our toy parallel file system (four object servers in containers, each held to 25 MB/s by a token bucket standing in for its disks; real code, not Lustre), one client wrote a 128 MiB file at 22.2 MB/s with stripe count 1, 44.8 with 2 and 88.7 with 4 measured, medians of 3: linear, because nothing else was in the way. The Striping lab animates both runs.

What it costs. More objects mean "more locks and extra network operations during common operations such as stat and unlink", and "when files are striped across all servers and one of the servers breaks down, a small part of each striped file is lost." Small files gain nothing: "Small files do not benefit from striping". The manual's rule: "stripe over as few objects as will meet those needs and no more", bounded by "the I/O rate of the clients/jobs divided by the performance per OSS".

Predict. Four ranks each write their own 64 MiB checkpoint shard to the toy file system, stripe count 1, and the MDS spreads the four files over the four servers. Then the same four shards go into one shared file striped over all four servers. Which is faster?
About the same: 88.9 MB/s for four files with one stripe each, 97.8 MB/s for one file striped four ways measured, medians of 3. Striping matters when few files must use many servers; when every rank writes its own file and the files are spread, the servers are already all busy. What hurts is when they are not spread: the same four files all forced onto OST 0 (lfs setstripe -i 0, the mistake) or one shared file with stripe count 1 ran at 25.0 and 24.9 MB/s, a quarter. The manual makes the same argument with 100 clients and 100 servers: one object per file means "no contention", while 100 objects per file means "the clients all compete with one another for the attention of the servers".

Locks: why many writers in one stripe are slow

Each OST runs its own lock manager (the LDLM) for the byte ranges of its objects, so a client caches data only while it holds the lock. "When writing to a single file from multiple nodes, having more than one client writing to a stripe can lead to issues with lock exchange, where clients contend over writing to that stripe, even if their I/Os do not overlap. This can be avoided if I/O can be stripe aligned so that each stripe is accessed by only one client." Our toy has no locks, so this cost is not modelled there; on Lustre it makes an N-to-1 shared checkpoint file with unaligned writes much worse than the toy shows. DCP's one file per rank sidesteps it.

Layouts that adapt: PFL and Data on MDT

A Progressive File Layout (PFL, since 2.10) gives one file several components by offset, so small files stay on one OST and big ones spread out without anyone choosing in advance. The manual's example on 8 OSTs: lfs setstripe -E 4M -c 1 -E 64M -c 4 -E -1 -c -1 -i 4 /mnt/testfs/create_comp: "The first component has 1 stripe and covers [0, 4M), the second component has 4 stripes and covers [4M, 64M), and the last component stripes start at OST4, cross over all available OSTs and covers [64M, EOF)." Components after the first are created only when a write reaches them. Amazon FSx for Lustre file systems created after August 25, 2023 default to lfs setstripe -E 100M -c 1 -E 10G -c 8 -E 100G -c 16 -E -1 -c 32 (FSx performance guide) vendor.

Data on MDT (DoM, since 2.11) puts the first part of a file on the metadata server itself, so a small file costs one server instead of two: "improves small file IO by placing small files directly on the MDT". The default maximum is 1 MB (dom_stripesize). Example: lfs setstripe -E 1M -L mdt -E -1 -S 4M -c -1 /mnt/lustre/domfile.

More than one metadata server: DNE

One MDS serves a whole file system until DNE (Distributed Namespace) adds more: a directory can live on another MDT (lfs mkdir -i mdt_index), or one huge directory can be spread over several with lfs mkdir -c mdt_count, "indended [sic] for specific applications where many output files are being created in one large directory (over 50k entries)". On our toy, two metadata servers instead of one served 16 clients at 2,635 operations per second against 1,603 measured: the Metadata storm tab has the full curve.

3. The other designs: where the metadata lives, and who places the bytes

Every parallel file system answers the same two questions differently: who owns the names (a dedicated metadata tier, or every server), and who decides where a byte goes (a layout handed out once, or a placement every server can compute). That choice decides how it behaves under a metadata storm and when a server fails.

Two families. Lustre and 3FS keep a separate metadata tier and hand the client a layout, so data I/O never touches it; GPFS, WEKA and VAST spread metadata over the same servers as data, so there is no single metadata bottleneck to size, at the price of distributed locking. Tectonic and 3FS both put metadata in a transactional key-value store behind stateless servers, which is how they scale the namespace. The 3FS headline matches Fire-Flyer 2's "8 TB/s" quoted on the parent page only loosely (6.6 TiB/s is 7.3 TB/s derived): the paper and the README describe different measurements.

4. Metadata: the small-file and start-up storms

The problem. Bandwidth scales with storage servers; metadata does not, or not as fast. A Lustre file system with hundreds of OSTs may have one or a handful of MDTs, and every create, open, stat and failed lookup goes to them. Small files make every byte cost a metadata operation; thousands of ranks starting at once make every rank's start-up cost thousands. Amazon sells this capacity separately: an FSx for Lustre file system of 1,200 GiB includes 1,500 metadata IOPS, and each metadata IOPS serves 2 file creates, opens or closes per second, 1 delete, or 0.1 directory creates (FSx performance guide) vendor: 3,000 opens per second for the whole file system derived.

Measured: the same four operations on four stores

16 processes, each in its own directory, create empty files, stat them, look up names that do not exist, and delete them, in lock step measured (medians of 3; src/runs/meta_real.py). Operations per second, all processes together:

Three things to read off it. A local file system does hundreds of thousands of operations a second, a network one a few thousand: the gap is the round trip, not the disk. The host folder shared into the VM answers stat of an existing file from its cache, as fast as local disk, but every lookup of a missing name crosses to the host (the "miss" column): network file systems cache what exists far better than what does not. And the object store pays a full HTTP request for everything, even a HEAD.

The start-up storm: what import torch asks the file system

Python finds a module by trying names on every directory of sys.path in turn, so an import is mostly lookups, many of them of files that do not exist. Counted with strace -f -c -e trace=%file,getdents64 in a container with torch 2.14.1+cpu and Python 3.11 measured (3 runs each, identical counts):

Predict. 16,384 ranks (Llama 3 405B's scale) start at the same second and each runs import torch from a Python environment on the shared file system. Suppose only the 652 failed lookups per rank reach the metadata servers (everything else cached). At 3,000 metadata operations per second, how long is the start-up stall?
16,384 x 652 = 10.7 million lookups; at 3,000 a second that is 3,561 s, about an hour derived, before a single step. With all 17,983 calls reaching the server it would be 27 hours. Real metadata servers are faster than this FSx entry size and clients cache more, so the real number depends on the system, but the shape is why large clusters never run Python from the shared file system: the environment lives in the container image on each node's local disk (squashfs images through enroot and pyxis on Slurm, image layers on Kubernetes), or is unpacked to local NVMe at job start. The Metadata storm tab computes this for any cluster and store.

The fixes, in the order to try them

  • Keep code and environments off shared storage: container images or a packed environment copied to local disk once per node.
  • Pack data into big shards (tens to hundreds of MB): one open per shard instead of per sample. Formats are on Storage and loading at scale.
  • One file per rank for checkpoints, not one per tensor: DCP writes one .distcp file per rank plus one .metadata (section 8).
  • Big output directories: spread over MDTs with a DNE striped directory, or hash into subdirectories; never ls -l or find over millions of entries on a busy file system (each entry is a stat).
  • Small files that must exist: Data on MDT, so each costs one server.
  • More metadata servers (DNE on Lustre, more metadata IOPS on FSx) when the workload truly needs them: on the toy, a second metadata server took 16 clients from 1,603 to 2,635 operations per second measured.

5. Object storage: what it promises, and how fast it goes

An object store keeps objects (a key, the bytes, a little metadata) in buckets. The key ckpt/step_000200/__3_0.distcp looks like a path, but there are no directories: the slashes are characters, and "listing a directory" is asking for keys that start with a prefix. The rules below are Amazon S3's, quoted from its documentation (read 2026-10-16); Google Cloud Storage and Azure Blob differ in detail, not in kind. Every behaviour marked measured was run against SeaweedFS 4.48 (the parent's S3 stand-in, MinIO's images being unavailable), set up as a real distributed store: one master, three volume servers and one filer with its S3 gateway, in capped containers (src/runs/run_seaweed.sh).

The throughput model: requests, prefixes and connections

Per request. S3 quotes "roughly 100-200 milliseconds" of latency for small objects and to the first byte of large ones, and "at least 3,500 PUT/COPY/POST/DELETE or 5,500 GET/HEAD requests per second per partitioned Amazon S3 prefix. There are no limits to the number of prefixes in a bucket." Scaling to a higher rate "happens gradually", with "503 (Slow Down)" errors meanwhile (S3 performance guide) vendor. So a checkpoint of 16,384 shards written in one second under one prefix asks for 4.7 times one prefix's write rate derived (16,384 / 3,500): spread keys over prefixes (by rank, for example) and retry with backoff.

Per connection. One connection is limited by its latency and the server's per-stream rate, so throughput comes from many at once: "You can use concurrent connections to Amazon S3 to fetch different byte ranges from within the same object", with GETs aligned to the upload's part boundaries, up to a single instance's "100 Gb/s". Fast clients exist for exactly this: s5cmd's README quotes a user benchmark in which it "can saturate a 40Gbps link (~4.3 GB/s), whereas s3cmd and aws-cli can only reach 85 MB/s and 375 MB/s" (s5cmd) independent, undated.

Measured on the stand-in, one 256 MiB object, medians of 3 measured:

Parallel ranged GETs helped downloads (363 to 477 MB/s); parallel parts barely helped uploads (80 to 112 MB/s) because the store, one filer on one CPU and three volume servers on half a CPU each, was already the bottleneck. That is the lesson that transfers: concurrency moves the limit from the client's round trips to the servers, and on a laptop the servers are small. On S3 the server side is effectively unbounded and the limit becomes the node's network card. Our first attempt at this run failed after 16 uploads of 256 MiB to the same key with InternalError ... We encountered an internal error, please try again.: overwritten and deleted data kept its space until the master vacuumed the volumes; vacuuming after each upload fixed it (our inference from the fix, not a SeaweedFS diagnosis).

What a request costs. At S3 Standard's $0.005 per 1,000 PUTs and $0.0004 per 1,000 GETs (AWS Price List, published 2026-10-15, us-east-1) published, writing a million 4 KiB files costs $5.00 in requests and their 4.1 GB of storage $0.09 a month derived: small objects are billed by count, not size. S3 Express One Zone trades durability across zones for "consistent, single-digit millisecond data access" in one Availability Zone, up to "200,000 read TPS" and "100,000 write TPS" per directory bucket (AWS) vendor, at $0.11 per GB-month against $0.023: a place for hot data and fast checkpoints, not for the copy of record.

6. Caches and tiers in between

The problem. The object store is cheap and holds everything, but answers in 100-200 ms and has no POSIX; the parallel file system is fast but costs several times as much per byte (FSx for Lustre persistent SSD at 125 MB/s per TiB: $0.145 per GB-month, against S3 Standard's $0.023, AWS us-east-1, read 2026-10-16 published). A cache or tier keeps the working set on fast media near the GPUs and the rest in the object store.

When a cache helps, in one line. It pays only for bytes read more than once. Single-pass pretraining reads each token about once, so a data cache adds nothing but a copy; multi-epoch fine-tuning, many jobs reading the same dataset, evaluation sets, model weights loaded by every serving replica, and container images are where caches earn their space. The second kind of help is latency: a cache on local NVMe answers in microseconds where the object store answers in a tenth of a second, which matters for small files and for random access.

GPUDirect Storage removes a different hop: "a direct data path for direct memory access (DMA) transfers between GPU memory and storage" that "avoids a bounce buffer through the CPU"; NVIDIA's only number is that such a path "offers at least twice the peak bandwidth as compared to taking a data path through the CPU" on suitable PCIe topologies (GDS overview v1.19.1) vendor. It needs supported NVMe or network storage and code written to the cuFile API; not run here.

7. Moving data: staging, checkpoint paths, other regions

Staging a dataset is a copy, and a copy's time is its size over the narrowest pipe: t = bytes / min(source read, destination write, the link between). 100 TB over one 100 Gb/s (12.5 GB/s) link takes 2.2 hours derived, and many files make it slower, because a single-threaded copy also pays a metadata round trip per file. The tools that parallelise both:

  • mpiFileUtils (dcp, dsync): MPI-parallel copy and sync for file systems, "providing speedups of up to 20-30x"; "dsync is the recommended way to make a copy a large set of files" (mpiFileUtils) authors.
  • s5cmd or a CRT-based S3 client for object stores: many connections, ranged parts (section 5).
  • Slurm: sbcast "is used to transmit a file to all nodes allocated to the currently active Slurm job" to local disk (good for one binary or one environment tarball; the docs warn "parallel file systems may provide better performance"), and burst-buffer plugins (datawarp, lua) that run stage-in and stage-out scripts around a job (burst buffers). The sibling Slurm page covers job prologs and epilogs.

A checkpoint's path to safety, fastest first. Each hop is asynchronous from the one before, so training stops only for the first:

  1. GPU memory to host memory: the copy that asynchronous DCP blocks on (the parent's lab: training stopped 77.9 ms per checkpoint instead of 1.81 s on its slow folder measured); torchtitan exposes it as async_mode "disabled", "async" or "async_with_pinned_mem" (torchtitan).
  2. Host memory to local NVMe or a peer's memory: survives the process, not the node. In-memory checkpoints in other nodes' RAM recover far faster than remote storage allows: Gemini reports "more than 13x" faster failure recovery and that checkpointing MT-NLG's states takes "42 minutes" to remote storage at 20 Gbps (Gemini, SOSP 2023) authors. The sibling Fault tolerance at scale page compares these designs.
  3. To the parallel file system: survives nodes; this is where the burst lands (section 9).
  4. To the object store: survives the cluster; retention lives here. torchtitan keeps the latest 10 by default (keep_latest_k: int = 10, interval 500 steps), so capacity is about ten checkpoints, not one. Megatron Core writes straight to object stores with --save msc://my-profile/checkpoints through NVIDIA's Multi-Storage Client (Megatron Core MSC); FSx can export to its linked bucket automatically.

Other regions and clouds cost money as well as time. AWS charges $0.02 per GB from us-east-1 to us-west-2, $0.01 to us-east-2, and $0.09 per GB for the first 10 TB a month out to the internet; inbound is free (AWS Price List, AWSDataTransfer, published 2026-09-16) published. One 405B checkpoint at MLPerf Storage's 5.29 TB costs about $106 to copy to another US region and about $476 to take out to the internet, and takes 423 s over a dedicated 100 Gb/s link derived. Keeping ten of them in a second region doubles their storage bill, which is why most labs replicate only selected checkpoints.

PyTorch Distributed Checkpoint (DCP): one file per rank, plus a map

Resharding is a set of byte-range reads: the same checkpoint loaded by 4, 2 and 3 ranks

Why 3 ranks read 1.5 times the checkpoint. A new rank that owns rows 0 to 21 of a tensor saved in chunks of 17 needs part of the second chunk, and DCP's file reader fetches whole stored chunks, then copies the slice it needs:

torch/distributed/checkpoint/filesystem.py, lines 869-884, PyTorch v2.14.1
    def read_data(self, plan: LoadPlan, planner: LoadPlanner) -> Future[None]:
        # group requests by file
        per_file: dict[str, list[ReadItem]] = {}
        for read_item in plan.items:
            item_md: _StorageInfo = self.storage_data[read_item.storage_index]
            path = item_md.relative_path
            per_file.setdefault(path, []).append(read_item)

        for relative_path, reqs in per_file.items():
            new_path = self.fs.concat_path(self.path, relative_path)
            with self.fs.create_stream(new_path, "rb") as stream:
                # TODO sort by offset and cache the reading
                for req in reqs:
                    item_md = self.storage_data[req.storage_index]
                    file_slice = self._slice_file(stream, item_md)

item_md is the stored chunk's (relative_path, offset, length); _slice_file (line 860) views exactly that range, so the whole chunk is read even when the new rank needs a few rows of it. Resharding to a divisor of the old world size (4 to 2) reads each byte once; to a non-divisor (4 to 3) the overlapping chunks are read by two ranks each. On a parallel file system that is 50% more restore traffic; on an object store, 50% more GET bytes.

9. Sizing storage for a cluster


Four separate questions; the Sizing calculator answers all four for any cluster. Cluster anatomy covers NVIDIA's per-SU reference numbers; this is the arithmetic behind any such table.


    

  1. Write bandwidth, from the checkpoint. Size = parameters x bytes per parameter (about 14 for bf16 with fp32 Adam; MLPerf Storage v2.0's own checkpoint table gives 912 GB for 70B and 5.29 TB for 405B, 13.0 and 13.1 bytes per parameter derived, MLPerf Storage rules v2.0). With synchronous saves, bandwidth = size / the stall you accept. With asynchronous saves, the GPUs stop only for the copy to host memory and the storage only has to drain the checkpoint before the next one: bandwidth = size / interval.
    2. 

  2. Read bandwidth, from data and from restarts. Data: tokens per second x bytes per token, small for text. Restart: every rank reads the checkpoint at once, size / the restart time you accept, usually the larger number.
    3. 

  3. Metadata rate, from start-up and small files. Ranks x the operations each makes at start (section 4), and files per second for data in small files.
    4. 

  4. Capacity = datasets + checkpoints kept x size + scratch, and on a parallel file system bought as servers, capacity often follows from the bandwidth rather than the bytes.
    5. 



Predict. A 70B model on 1,024 GPUs checkpoints every 30 minutes (0.98 TB at 14 bytes per parameter). How much write bandwidth does storage need, synchronous with a 30 s stall against asynchronous?




0.98 TB / 30 s = 32.7 GB/s; 0.98 TB / 1,800 s = 0.54 GB/s derived: sixty times less, because asynchronous saving lets the write take the whole interval. On FSx for Lustre at 125 MB/s per TiB, 32.7 GB/s means buying 261 TiB (about $38,800 a month at $0.145 per GB-month) to store about 10 TB of checkpoints derived. Restarts are the catch: reading 0.98 TB back in 60 s still needs 16.3 GB/s, so size reads for recovery and writes for the drain.

Common mistakes


A big shared file with the default stripe count of 1
Every writer and reader of the file lands on one OST. On the toy, four ranks writing one shared file with one stripe got 24.9 MB/s; with four stripes 97.8 measured. Check with lfs getstripe; set a directory default (lfs setstripe -c 4 -S 4M dir) before the files exist: a layout cannot change after creation without lfs migrate.


Pinning every file to one OST
lfs setstripe -i 0 copied from an example puts every new file on OST 0: four file-per-rank writers fell from 88.9 to 25.0 MB/s on the toy measured. The manual: the default start index of -1 "allows the MDS to choose the starting index. This setting is strongly recommended".


Unaligned writers sharing one stripe
Ranks writing interleaved pieces of one file fight over the OST's extent locks ("lock exchange") even when their bytes do not overlap. Align each writer to whole stripes, or write one file per rank (DCP does).


A Python environment on the shared file system
17,983 file-system calls and 652 failed lookups per rank for import torch measured, times every rank, all at once. Symptom: jobs that take minutes to reach step 1 and get slower as they get bigger, and a metadata server at 100% while the OSTs idle. Ship the environment in the container image on local disk.


A PFL file that keeps growing by appends
Appending to a file with a wide last component instantiates every component, and "an operation such as reading the file length will send a request in parallel to every OST" (FSx guide). FSx gives files opened in append mode a stripe count of 1 for that reason. On Data on MDT layouts without an end-of-file component, "writes beyond the end of the last existing component will fail with error ENODATA" (manual).


Multipart parts below the minimum
Every part but the last must be at least 5 MiB. Our store refused two 1 MiB parts at completion:  measured. The failed upload then stayed open and listed (it was in list_multipart_uploads next to the abandoned one); on AWS its parts are billed until aborted. Add a lifecycle rule that aborts incomplete multipart uploads.


"Renaming" a checkpoint on an object store
There is no rename: a copy and a delete move every byte again (here 64 MiB took 0.49 s to "rename" against 0.66 s to upload measured; a server-side copy still rewrites the bytes inside the store). Upload under the final key and write a marker or .metadata last; protect the marker with If-None-Match: * (a second writer got ).


Storage that silently filled up
Overwriting the same 256 MiB key over and over on SeaweedFS ended with InternalError ... We encountered an internal error, please try again. after 16 uploads: deleted and overwritten data kept its space until a vacuum (our inference). Every store has a version of this (snapshots, object versions, Lustre OSTs that fill unevenly): watch free space per server, not just in total, and keep checkpoint retention (keep the last k) in the training code.


Resharding to a world size that does not divide the old one, and blaming the network
4 ranks to 3 read 1.50 times the checkpoint's bytes, 4 to 2 read 1.00 times measured (section 8). Plan restore bandwidth for the overlap, or restart at a divisor when you can.


Expecting a cache to speed up the first epoch
A lazy-loading cache (FSx linked to S3, Mountpoint's cache) serves the first read at the object store's speed. Preload the hot directory before the job, or accept that single-pass pretraining gains nothing from it.







Interview questions


Why can a parallel file system go faster than any one of its servers, and what stops it?
Metadata and data are split: the client fetches a file's layout from the metadata server once, then reads and writes the objects on many storage servers in parallel (RAID 0 by stripe size). It stops at the narrowest of: the stripe count (one file uses only its objects' servers), the client's network card, the servers' disks and networks, the metadata server for small files and start-ups, and lock contention when writers share stripes.


You are writing 1,024 checkpoint shards of 2 GB each to Lustre. What stripe settings?
File per rank already spreads the load if the MDS places the files round robin, so stripe count 1 (or a few) and stripe size 1 to 4 MiB; never a fixed start index. Wide striping helps when few large files must use many OSTs (a consolidated export, a dataset file read by everyone). Check the result with lfs df for balance.


What does S3 guarantee about a checkpoint, and what must your code add?
Each object appears atomically and strong read-after-write holds per key. Nothing is atomic across keys, so a multi-shard checkpoint needs a marker or metadata object written last and a reader that ignores directories without it; conditional writes (If-None-Match, If-Match) stop two writers clobbering each other; abort incomplete multipart uploads; spread keys over prefixes and retry 503 SlowDown with backoff.


Jobs take ten minutes to reach the first step on 2,000 nodes, a minute on 20. Where do you look?
A metadata storm: Python or shared libraries loaded from the shared file system, every rank doing tens of thousands of lookups at once. Confirm with strace -c on one rank and the metadata server's load; fix by shipping the environment in the image on local disk, then data in shards.


Synchronous or asynchronous checkpoints: how does the choice change the storage you buy?
Synchronous: bandwidth = checkpoint size / acceptable stall (32.7 GB/s for 0.98 TB in 30 s). Asynchronous: the GPUs stop only for the host copy, and storage needs size / interval (0.54 GB/s every 30 minutes), plus host RAM for the staged copy and a separate process group for the background collectives. Restores still need size / acceptable restart time.


Why might restoring onto 3 nodes take longer than onto 2, from the same 4-rank checkpoint?
DCP reads whole stored chunks. At a divisor each byte is read once; at a non-divisor, chunks straddle new ranks and are read twice (1.50 times the bytes measured here), on top of uneven shard sizes.


When is a cache in front of the object store worth it?
When bytes are read more than once (multi-epoch, many jobs on one dataset, eval sets, weights for many replicas, images) or when latency matters (small files, random access). Single-pass pretraining gains almost nothing; the first epoch through a lazy cache runs at object-store speed.


Design question: the storage for a 1,000-GPU training lab.
Tiers. An object store (S3 or an on-premises one) as the system of record for datasets, checkpoints kept beyond a few days, and artifacts, with lifecycle rules. A parallel file system (Lustre or FSx for Lustre, WEKA, VAST) as the working tier for checkpoints and hot datasets, linked to the object store for import and export. Local NVMe on every node for staged data, images and the first copy of each checkpoint. Home directories and code on a small NFS.
Numbers. For a 70B model on 1,024 GPUs: 0.98 TB per checkpoint; asynchronous saves every 30 minutes need about 0.5 GB/s of drain; recovery in 60 s needs about 16 GB/s of read; ten kept checkpoints are about 10 TB; data reads for text are small. So size the file system for restore reads and bursts from many jobs at once, and buy metadata capacity (more MDTs or metadata IOPS) for start-ups and small files.
Rules. DCP or equivalent with one file per rank, a marker written last, keep-last-k retention in the trainer; environments in container images; data in shards of tens to hundreds of MB; checkpoint directories with a sane default layout; per-server monitoring (OST balance, MDT load, S3 503s). Trade-offs to say out loud: managed (FSx, cost per TiB tied to throughput) against owned (capital, staff), one tier against two, and how much to replicate across regions ($0.02 per GB between AWS US regions).
