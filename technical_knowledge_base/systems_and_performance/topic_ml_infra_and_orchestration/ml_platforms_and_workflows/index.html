ML platforms in one screen

A scheduler (Slurm, Kubernetes, Ray) answers one question: which machines run this job, and when? Everything a team needs around that question is the ML platform: the order in which the steps of a project run (prepare data, train, evaluate, register), a record of every run so that nobody has to remember what produced what, and a named, versioned home for the models that are good enough to use. This page builds that layer for the topic's running example and shows, with real records, what each piece is for and how it fails.

Model registry: which model is the one to use?
Named models with numbered versions and movable labels (aliases such as champion). Serving and evaluation ask for models:/mi-tiny-gpt@champion, never for a file path. MLflow Model Registry, W&B Registry, the Hugging Face Hub, cloud registries.
Experiment tracker: what ran, with what, and what came out?
One record per run: parameters, metrics over time, tags (code, data and environment hashes), artifacts. MLflow, Weights & Biases, ClearML.
Workflow engine: in what order, and what happens when a step fails?
A graph of steps with their inputs and outputs, retries, timeouts, caching and resume, schedules and triggers. Airflow, Kubeflow Pipelines, Flyte, Metaflow, Prefect, Dagster, ZenML.
Scheduler and launcher: which machines, and how do the processes start?
Slurm, Kubernetes with Kueue and JobSet, Ray; torchrun inside the job. The rest of this topic. A workflow step submits to this layer; it does not replace it.
Storage: where the bytes live
Datasets, checkpoints, model files and the tracker's own database and artifact store. Sibling page: Storage and data movement.

Four words carry the page. A run is one execution of a training program with fixed inputs. An artifact is any file or object a step produces (a data split, a checkpoint, a model). Lineage is the chain of links from an artifact back to everything that made it: code, data, parameters, environment, the run. Reproducing a run means producing the same artifact again from that chain; this page measures how exactly that works (bit for bit on the same machine, not across platforms).

1. Why a platform layer: the problem it solves

The problem. After a week of experiments a team has dozens of checkpoints, each made by some version of the code, on some version of the data, with some flags. The questions that follow are always the same: which run gave the number on the slide? Was it trained on the data before or after the dedup fix? Which file is in production, and what replaced what? A shared folder named final_v3_really_final/ answers none of them. Sculley and colleagues at Google called this hidden technical debt: ML systems pick up "data dependencies, configuration issues" and "undeclared consumers" that cost far more to maintain than the model code (Sculley et al., NIPS 2015).

The answer, in three parts. Write the steps down as a graph the machine runs (a workflow), so the order and the inputs are code, not memory. Record every run automatically (a tracker), so the record exists even when nobody thought it would matter. Give the good models names and versions (a registry), so "production" is a pointer that moves on purpose. Hashes of code, data and checkpoints tie the three together (lineage).

The cost. A tracking server and its database and artifact store to run and back up (here about 540 MB of memory at idle for the MLflow server's three processes measured), a workflow engine that is one more thing to configure (here a step hung for 6 minutes because steps have no timeout by default: section 3), and discipline: a record is only as good as what the code logs.

When it matters. A tracker and a registry pay off from the first shared project, because the cost of a lost run is paid later and by someone else. A workflow engine pays off once the same multi-step process runs often enough that doing it by hand causes mistakes: a nightly evaluation of every new checkpoint, a data pipeline that feeds training, a sweep of many runs. A single researcher's one-off pretraining run on Slurm needs the tracker, not the engine.

How to check you have it. Pick any model in use and try to answer, from records alone: the exact command, the code version, the data version, the environment, and the run's metrics. The Reproduce a run tab does exactly that for the registry of this page.

2. Workflows: the steps around training, written as a graph

The idea. A workflow (or pipeline) is a directed acyclic graph (DAG): boxes are steps (also called tasks), arrows say "this step needs that one's output". A workflow engine reads the graph, starts each step when its inputs exist, records what each step produced, and decides what to do when a step fails. The engine is an orchestrator: it decides order and records state; the actual compute runs wherever the step sends it (a local process, a Kubernetes pod, a Slurm job, a Ray task).

The running example as a workflow. Four steps and an end, in one Python file (src/lab/flow.py, Metaflow 2.19.39). Each self.x = ... inside a step becomes an artifact: Metaflow serialises it, stores it under the SHA-1 of its bytes in its datastore (content_addressed_store.py line 98), and hands it to the next step. That is how the 1.4 MB checkpoint travels from train to evaluate: through the datastore, not through a path someone has to remember.

Where the steps run. Here every step is a local process. In production the heavy step submits work to the scheduler and waits: Metaflow's @kubernetes or @batch decorators send a step to a pod or an AWS Batch job; Airflow tasks hand work to executors (Celery, Kubernetes, Edge) or operators that create pods; Kubeflow Pipelines runs every step as a container on Kubernetes; on Slurm a task can call sbatch --wait and read the job's exit code (Tool map entries; sbatch --wait). The rule of the root's Tool map holds: a workflow engine does not launch a multi-node training job itself; it asks Slurm, Kubernetes (JobSet, Kueue) or Ray to, and records the result.


Slurm already has a small workflow engine. Job arrays (one script, many indexed tasks) and dependencies (--dependency=afterok:123) chain jobs inside the scheduler with no extra service. The sibling page Slurm from zero, section 9, ran them on the topic's cluster, including the trap: a dependency on a failed job stays pending forever with DependencyNeverSatisfied. Use them for chains of cluster jobs; use a workflow engine when steps cross systems (a data warehouse, a cluster, a registry, a notification), need schedules or triggers, or need records of every step's inputs and outputs.

3. Retries, timeouts, caching and resume: what an engine does when a step fails


The problem. Steps fail: a flaky network call, a bug in the last step, a machine that disappears. Without an engine you rerun the whole script, paying again for every step that had already worked; for a pipeline whose first step is a multi-hour training job, that is the whole cost.


How it works. Because the engine stored every finished step's outputs, it can start again from the failure. Metaflow calls it resume: it "reuses results of every successful step instead of actually running them", deciding what to reuse "by the flow and step names", not by the code, and parameters cannot change on resume (Metaflow docs, debugging). Airflow reruns from a failed task when you clear it, because task-instance states live in its metadata database (Airflow docs, DAG runs); Kubeflow Pipelines and Flyte cache step outputs keyed on the step's inputs, so an unchanged step is skipped (KFP overview; Flyte's typed inputs and outputs "allow for parameterized workflows, data lineage and caching", Lyft, 2020-01-07). Retries (@retry, three times by default in Metaflow) handle transient failures; a timeout turns a hang into a failure the engine can act on; in Metaflow "by default, there is no timeout for steps" (Metaflow docs, failures).

The cost. Every step's outputs are stored (7.5 MB of datastore here for eight small runs; for real checkpoints, terabytes), and every step must be safe to run twice (idempotent): a step that appends to a table or sends an email does it again on retry. Resume also creates a lineage trap, measured here: the resumed run's start step was cloned, so its recorded code_sha (3cdcf1a9ce10) is the hash of the code before the fix, while register ran the fixed code (67873f121e99). The registry's version 1 therefore points at a code hash that never produced it end to end; the Reproduce a run tab flags it.


When it matters. Whenever an early step is expensive: training, a large data job, an evaluation over thousands of prompts. For a pipeline of cheap steps, rerunning is simpler than reasoning about what was reused.


How to check. Make the last step fail on purpose and resume: the engine's log must say it cloned the earlier steps (here: Cloning previously run task 1792142900051724/train/2), and their outputs must have the same content hashes as the original run (they do: the Lineage graph shows identical artifact hashes).


Predict: after the failure you also want to try lr 0.003 instead of 0.001. You run python flow.py resume --lr 0.003. What happens?




Resume is for continuing the same run after a failure, not for changing it. Metaflow's docs: parameter values "can't be changed on resume", and configs from the original run are used. Changing an input means a new run with its own record; that is what keeps the record honest. Caching engines (KFP, Flyte) handle this differently: a changed input changes the cache key, so the step reruns.

5. Experiment tracking: one record per run


The idea. A tracker keeps one run record per execution: the parameters it was given, metrics as step-indexed series (loss at step 10, 20, ...), tags (free-form strings: code hash, data hash, platform), artifacts (files) and system metadata it fills in itself (user name, source file, git commit when run from a repository). Runs are grouped into experiments and can be searched and compared: "every run with lr above 0.003 sorted by held-out loss" is one query.


One real run record: the champion's MLflow 3.17.1, recorded




Read back from the tracking server after the runs (src/lab/export.py). The user is mp-lab because the lab set USER before running: by default MLflow records your login name, Metaflow tags runs user:<login>, and both record source paths. Decide what your tracker may store before sharing it.


How MLflow is built. Three parts. The client (mlflow.log_metric, MlflowClient) talks REST to a tracking server, which keeps run and registry records in a backend store (a SQL database: SQLite here, PostgreSQL or MySQL in production) and files in an artifact store (S3, GCS, Azure, a local folder). Started with --artifacts-destination, the server proxies artifact uploads, so clients see mlflow-artifacts:/ URIs and need no bucket credentials. The server here was one command:


mlflow server --backend-store-uri sqlite:///mlflow.db --artifacts-destination ./artifacts \
  --host 127.0.0.1 --port 5077 --workers 1


It started three processes (the launcher, a uvicorn web app and a job runner) using about 540 MB of memory at idle, and printed Security middleware enabled with default settings (localhost-only) measured. After eight workflow runs the database held , the artifact store , and Metaflow's datastore : small, because this model is small; with real checkpoints the artifact store is the part that grows (sibling page: Storage and data movement).


The local default changed, and the old one now refuses to run. With no URI set, MLflow 3.17.1 writes to sqlite:///mlflow.db in the working directory (mlflow/store/tracking/__init__.py line 13), unless ./mlruns already holds experiments, in which case it keeps using them. The docs date the switch to MLflow 3.7.0 and say the file store "is in maintenance mode" (backend store docs). In 3.17.1 asking for a file store explicitly raises, measured here: MlflowException: The filesystem tracking backend (e.g., './mlruns') is in maintenance mode and will not receive further updates. ... set `MLFLOW_ALLOW_FILE_STORE=true` to opt out of this exception. (file_store.py line 225). Old tutorials that say "MLflow logs to ./mlruns" are out of date.


Logging from distributed training. Every rank computes the loss, but one record should hold it: log from rank 0 only (or give each rank its own run and tag it). Log the all-reduced loss, not one rank's: here the flow logged gloss, the mean over ranks, the number the topic compares across Slurm, Kubernetes and Ray. This lab logs after the fact: train.py writes one JSON line per logged step, and the workflow step uploads all 21 points in one log_batch call after torchrun exits. That keeps the training code free of tracker imports and makes the tracker optional, at the price of seeing nothing live; hosted trackers (Weights & Biases) stream metrics and system metrics (GPU utilisation, memory) during the run.


The status trap measured. Each step of this flow opened the MLflow run, logged, and closed it. The first workflow run hung inside train and was killed; its MLflow run says FINISHED, because start had closed it cleanly, and it has no metrics at all. A tracker's status is what the code told it, not what happened. Check runs by their content (does it have val_loss?), keep one run open for the whole workflow with a heartbeat, or tag the workflow's own final state.


The trackers. MLflow (Linux Foundation project led by Databricks, Apache-2.0, 3.17.1 on 2026-10-13; 3.0 in June 2025 added the LoggedModel entity, "moving beyond the traditional run-centric approach", MLflow 3 release): the open default, self-hosted on a database plus object storage. Weights & Biases (client 0.30.0; owned by CoreWeave since 2025-05-05, CoreWeave): a widely used hosted tracker for deep learning, with artifacts, a registry, sweeps and live system metrics. ClearML (2.1.12): a self-hosted suite of tracking, data versioning, pipelines and an agent that pulls queued jobs onto GPU machines.


A tracker can disappear. Neptune, a hosted tracker used for foundation-model training, agreed to be acquired by OpenAI in December 2025; its hosted app and API were turned off "On March 5, 2026, at 10 am PST", data still there was "securely and irreversibly deleted", and the transition hub offered an exporter and migration guides to MLflow, Weights & Biases, ZenML, Comet and others (Neptune transition hub, read 2026-10-16; the root's Tool map records the earlier March 4 date and its correction). Lesson: whatever tracker you use, keep an export of the records that matter (a scheduled dump of runs, metrics and registry to your own storage), and keep the training code independent of the tracker's SDK where you can, as this lab does.

6. The model registry: names, versions and aliases


The idea. A registered model is a name (mi-tiny-gpt). Each time a model is registered under it, the registry creates a version (1, 2, 3, ...), which is immutable: it points at one stored model and the run that made it. An alias is a movable label on one version ("a mutable, named reference", MLflow docs): champion for what serves, challenger for what is being tested. Consumers load models:/mi-tiny-gpt@champion; deploying a new model is moving the alias, and rolling back is moving it back. Tags on a version carry evidence (here val_loss, data_sha, code_sha, ckpt_sha, metaflow_run).


Stages are deprecated. MLflow's older fixed stages (None, Staging, Production, Archived) and transition_model_version_stage carry @deprecated(since="2.9.0") in 3.17.1 (mlflow/tracking/client.py line 4941); the REST response below still shows "current_stage": "None". Use aliases and tags.

7. Lineage and versioning: what made this model?


The idea. A model is a function of a handful of inputs: code, data, configuration (parameters, seed), environment (library versions, hardware) and, for a resumed run, a checkpoint. Lineage records an identifier for each, at the moment it is used, on the record of the run and on the model version. An identifier is only useful if it changes whenever the thing changes: a content hash (SHA-256 of the bytes) or an immutable version id, never a name like latest or a path like /data/shakespeare/.

Content addressing gives lineage for free. Metaflow stores each artifact under the hash of its bytes, so identical outputs are stored once and the same hash appears wherever the same object was used. In the Lineage graph, the resumed run's train task carries exactly the artifact hashes of the failed run's train task (it was cloned), and every run on the 90/10 split shares one train_sha. Lineage across systems is the harder part: a dataset written by a Spark job, read by a training job, evaluated by a pipeline. OpenLineage, a Linux Foundation project, defines events about "datasets, jobs, and runs" that tools emit so one graph can be assembled (openlineage.io).


The cost. Hashing a 1 MB file is free; hashing a 10 TB dataset at every run is not, so at scale the hash is taken once when a dataset version is written and the run records the version id. Every pinned input must also be kept: a hash of data that was deleted proves nothing can be rebuilt.


How to check. From a model version, walk back to every input without asking a person. The Lineage graph does this on the real records; the Reproduce a run tab then reruns the result.







8. Reproducibility: same command, same bits?


"Reproducible" means three different things, from weakest to strongest: you can re-execute the same command (you know what it was); the result is statistically equivalent (same quality within noise, what most large runs can promise); the result is bit-identical (every byte of the checkpoint the same). The running example was built to be bit-identical: no dropout, deterministic algorithms, one thread per rank, batches drawn from (seed, step) only (root page, src/data/README.md). What this means. Bit-identical reproduction held on the same machine and software, and broke across platforms with the same version number of PyTorch: the macOS and Linux builds compute some operations in a different order or with different kernels (which ones was not traced here), and once one rounding differs, training amplifies it. The drift stays tiny for this model (1.3e-5 in loss after 200 steps); on a large run that difference grows into a different trajectory that is only statistically equivalent. The root's Failure lab found the same edge inside one platform: resuming the running example from a checkpoint is bit-exact with 2 ranks but not with 4, because DDP rebuilds its gradient buckets after restart (2.4e-7 at two logged steps).


What to pin, so a rerun is at least equivalent: the code commit, the data version, the full config and seed, the container image digest (it fixes the library builds, not just their versions), the hardware type and the number of ranks; and store the checkpoint, since the cheapest exact reproduction of a trained model is to keep it.

10. Design: the platform for a 1,000-GPU training lab


The interview version: 1,000 GPUs (125 nodes of 8), about 50 researchers, a few long pretraining runs, hundreds of fine-tuning and ablation runs a week, nightly evaluation of new checkpoints. One reasonable design, with the trade-off at each choice:


    

  1. Scheduler: Slurm, or Kubernetes with Kueue and JobSet (the root page and its Scheduling lab compare them). The platform layer must work with either: every job goes through one submission wrapper.
    2. 

  2. Submission wrapper (the piece most teams underbuild): a small CLI that refuses a dirty git tree, resolves the dataset version and container image digest, creates the tracker run with those as tags, then calls sbatch or creates the JobSet. Lineage then exists for every run, not just the careful ones.
    3. 

  3. Tracker: hosted Weights & Biases (no operations, live system metrics, cost per seat, data leaves your network) or self-hosted MLflow on PostgreSQL plus object storage (you run and back it up). Either way, a nightly export of runs and the registry to your own storage: Neptune's shutdown is the reason.
    4. 

  4. Registry: the tracker's registry, with aliases per purpose (champion, eval-candidate) and version tags for evidence; checkpoints stay in object storage and the registry points at them.
    5. 

  5. Workflow engine: for the recurring pipelines only: data preparation, the nightly evaluation of every new checkpoint, registration and promotion. Airflow if a data team already runs it; Flyte or Kubeflow Pipelines on a Kubernetes estate. The training job itself stays a scheduler job that the pipeline submits and waits for.
    6. 

  6. Gate: promotion scored on a frozen evaluation set whose hash is checked, champion and challenger in the same step (section 6); a human approval for anything that serves users.
    7. 

  7. Retention: keep every registered version's checkpoint, keep the last few checkpoints of each run, delete the rest on a schedule; the tracker's records cost little and are kept.
    8. 



What breaks first, and how to check: the tracker's database under many runs logging many metrics at a high rate (load-test it with the expected points per second: for example 200 concurrent runs x 50 metrics every 10 s is 1,000 points per second derived, illustrative inputs); artifact storage filled by checkpoints nobody registered; pipelines that hang without timeouts; and lineage gaps from runs started outside the wrapper.






11. Common mistakes, with the messages they produce


Following an old tutorial that logs to ./mlruns
MLflow 3.17.1 raised on mlflow.set_tracking_uri("file:./mlruns"): MlflowException: The filesystem tracking backend (e.g., './mlruns') is in maintenance mode and will not receive further updates. Please migrate to a database backend (e.g., 'sqlite:///mlflow.db') .... Use the SQLite default locally and a server on PostgreSQL for a team; mlflow migrate-filestore moves old data (section 5).


A workflow step with no timeout that hangs
torchrun --standalone inside a Metaflow step on macOS kept printing [c10d] The IPv6 network addresses of (1.0.0.0...ip6.arpa, 55935) cannot be retrieved (gai error: 8 - nodename nor servname provided, or not known) and then The client socket has timed out after 300000ms, retrying; the step ran for 6 minutes until killed, because Metaflow steps have no timeout by default. Fixed with static rendezvous on 127.0.0.1 and @timeout(minutes=5). Put a timeout on every step that waits on something else (section 3; rendezvous itself: sibling page Launching distributed training).


Logging a PyTorch model with MLflow 3.17 as if it were MLflow 2
The default format is now pt2: If `serialization_format` is set to 'pt2', then input_example is required. Then an example of batch 1 fixes the batch size forever: AssertionError: Guard failed: idx.size()[0] == 1 on a batch of 4. Pass an example with batch 2 or more, or choose serialization_format="pickle" knowingly (section 6).


Trusting a run's status
The hung workflow's MLflow run says FINISHED and has no metrics, because the first step closed the run cleanly before the hang. Filter on content (a final metric exists) and record the workflow's own state (section 5).


Ranking runs evaluated on different data
The 80/20 run's held-out loss (2.1990) and the 90/10 runs' (2.1776) are on different text; the tracker sorts them together without complaint. Gate promotions on a frozen evaluation set and check its hash (sections 5 and 6).


Believing the code hash of a resumed run
Resume clones finished steps with their recorded artifacts, including the code hash taken in start, while the later steps run new code. Version 1 here carries code_sha 3cdcf1a9ce10 but was registered by code 67873f121e99. Record the code hash in every step, or forbid code changes between failure and resume for runs that will be registered (section 3).


Names instead of identifiers: latest, :latest, /data/current/
A pointer that moves records nothing. Record content hashes, dataset version ids and image digests; keep movable names (registry aliases) for the one place they belong, choosing what to serve (section 7).


Logging one rank's loss, or every rank into one series
Rank 0's own loss covers only its share of the batch (half of it here); every rank writing to the same metric interleaves different numbers at the same step. Log the all-reduced loss from rank 0 (section 5).


A tracker with no way out
Neptune's hosted service was switched off on 5 March 2026 and the data left in it deleted (section 5). Schedule exports of the records that matter; keep the training code free of the tracker SDK where possible.


Running the training job inside the orchestrator
An Airflow worker or a pipeline pod is not a multi-node GPU allocation: it has no gang scheduling, no topology and no node health checks. The step submits to Slurm, Kubernetes (JobSet with Kueue) or Ray and waits (section 2).


Expecting bit-identical results on another platform
Same code, seed, data and torch 2.14.1 on macOS and on Linux diverged in the last bits from step 2 and by 1.3e-5 in loss at step 200 (section 8). Pin the container image digest and the hardware, and define "reproduced" as statistically equivalent unless the setup is identical.


Using registry stages
transition_model_version_stage is deprecated since MLflow 2.9.0; the REST response still shows "current_stage": "None". Use aliases (models:/name@champion) and tags (section 6).







12. Interview questions


What is the difference between a scheduler and a workflow engine?
The scheduler decides which machines run a job and when (Slurm, Kubernetes, Ray). The workflow engine decides the order of steps, passes their outputs, retries and resumes, and records state; its heavy steps submit jobs to the scheduler. Slurm's dependencies are a tiny workflow engine inside a scheduler.


What should a run record contain so the run can be reproduced?
The code commit, dataset version or hash, the full resolved config and seed, the environment (image digest or lockfile, driver, hardware, number of ranks), metrics as step-indexed series, and the hashes of the outputs (checkpoint, model). Plus the checkpoint itself, kept.


Why aliases rather than stages, and why not a path?
A version is immutable evidence; an alias is a movable decision. Consumers load @champion; promotion and rollback are one alias move, logged, with no consumer change. Stages were a fixed set of four and are deprecated since MLflow 2.9.0; a path can be overwritten silently.


A step failed after a 3-day training step. What does the engine need to avoid rerunning training?
Stored outputs of the finished steps (a datastore or cache) and a resume or cache mechanism keyed on step identity or inputs: Metaflow resume, a cleared Airflow task, a KFP or Flyte cache hit. And the training step's output must be the checkpoint in durable storage, not a local file on a node that is gone.


Two runs differ in the 6th decimal. Is the code non-deterministic?
Not necessarily. Here the same deterministic code on two platforms with the same torch version diverged from step 2. Check the platform, image digest, number of ranks (DDP bucket rebuild made a 4-rank resume differ by 2.4e-7) and thread counts before blaming the code.


Self-hosted MLflow or hosted Weights & Biases?
W&B: no operations, rich live dashboards and system metrics, a per-seat cost, data off-site (and since May 2025 owned by CoreWeave, a GPU cloud). MLflow: free and open, you run PostgreSQL, object storage and backups, simpler UI. Choose by data policy and who will operate it; plan an export either way.


How would you make promotion safe?
Register every candidate; score candidate and current champion on one frozen evaluation set in the same job and check the set's hash; move the alias only on a margin larger than the noise; require approval for user-facing models; keep the previous champion's version for rollback.


Design: the ML platform for a 1,000-GPU lab with 50 researchers.
Scheduler (Slurm or Kubernetes with Kueue and JobSet); one submission wrapper that pins commit, data version and image digest and opens the tracker run; a tracker (hosted W&B or MLflow on PostgreSQL plus object storage) with nightly exports; the tracker's registry with aliases and evidence tags; a workflow engine only for recurring pipelines (data prep, nightly eval, promotion) that submits to the scheduler; a gated promotion on a frozen eval set; retention rules for checkpoints. Load-test the tracker at the expected metric points per second (section 10).
