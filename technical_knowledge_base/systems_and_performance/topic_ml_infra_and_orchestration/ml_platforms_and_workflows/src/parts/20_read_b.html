2. Workflows: the steps around training, written as a graph

The idea. A workflow (or pipeline) is a directed acyclic graph (DAG): boxes are steps (also called tasks), arrows say "this step needs that one's output". A workflow engine reads the graph, starts each step when its inputs exist, records what each step produced, and decides what to do when a step fails. The engine is an orchestrator: it decides order and records state; the actual compute runs wherever the step sends it (a local process, a Kubernetes pod, a Slurm job, a Ray task).

The running example as a workflow. Four steps and an end, in one Python file (src/lab/flow.py, Metaflow 2.19.39). Each self.x = ... inside a step becomes an artifact: Metaflow serialises it, stores it under the SHA-1 of its bytes in its datastore ({{content_addressed_store.py line 98|https://github.com/Netflix/metaflow/blob/2.19.39/metaflow/datastore/content_addressed_store.py}}), and hands it to the next step. That is how the 1.4 MB checkpoint travels from train to evaluate: through the datastore, not through a path someone has to remember.

Where the steps run. Here every step is a local process. In production the heavy step submits work to the scheduler and waits: Metaflow's @kubernetes or @batch decorators send a step to a pod or an AWS Batch job; Airflow tasks hand work to executors (Celery, Kubernetes, Edge) or operators that create pods; Kubeflow Pipelines runs every step as a container on Kubernetes; on Slurm a task can call sbatch --wait and read the job's exit code ({{Tool map|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} entries; {{sbatch --wait|https://slurm.schedmd.com/sbatch.html}}). The rule of the root's Tool map holds: a workflow engine does not launch a multi-node training job itself; it asks Slurm, Kubernetes (JobSet, Kueue) or Ray to, and records the result.


Slurm already has a small workflow engine. Job arrays (one script, many indexed tasks) and dependencies (--dependency=afterok:123) chain jobs inside the scheduler with no extra service. The sibling page {{Slurm from zero|n:3c65c17b0d0d81889c32cd050bbbadd3}}, section 9, ran them on the topic's cluster, including the trap: a dependency on a failed job stays pending forever with DependencyNeverSatisfied. Use them for chains of cluster jobs; use a workflow engine when steps cross systems (a data warehouse, a cluster, a registry, a notification), need schedules or triggers, or need records of every step's inputs and outputs.

3. Retries, timeouts, caching and resume: what an engine does when a step fails


The problem. Steps fail: a flaky network call, a bug in the last step, a machine that disappears. Without an engine you rerun the whole script, paying again for every step that had already worked; for a pipeline whose first step is a multi-hour training job, that is the whole cost.


How it works. Because the engine stored every finished step's outputs, it can start again from the failure. Metaflow calls it resume: it "reuses results of every successful step instead of actually running them", deciding what to reuse "by the flow and step names", not by the code, and parameters cannot change on resume ({{Metaflow docs, debugging|https://docs.metaflow.org/metaflow/debugging}}). Airflow reruns from a failed task when you clear it, because task-instance states live in its metadata database ({{Airflow docs, DAG runs|https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/dag-run.html}}); Kubeflow Pipelines and Flyte cache step outputs keyed on the step's inputs, so an unchanged step is skipped ({{KFP overview|https://www.kubeflow.org/docs/components/pipelines/overview/}}; Flyte's typed inputs and outputs "allow for parameterized workflows, data lineage and caching", {{Lyft, 2020-01-07|https://flyte.org/blog/introducing-flyte-a-cloud-native-machine-learning-and-data-processing-platform}}). Retries (@retry, three times by default in Metaflow) handle transient failures; a timeout turns a hang into a failure the engine can act on; in Metaflow "by default, there is no timeout for steps" ({{Metaflow docs, failures|https://docs.metaflow.org/scaling/failures}}).

Drawn to scale; seconds are from one shared laptop.


The cost. Every step's outputs are stored (7.5 MB of datastore here for eight small runs; for real checkpoints, terabytes), and every step must be safe to run twice (idempotent): a step that appends to a table or sends an email does it again on retry. Resume also creates a lineage trap, measured here: the resumed run's start step was cloned, so its recorded code_sha (3cdcf1a9ce10) is the hash of the code before the fix, while register ran the fixed code (67873f121e99). The registry's version 1 therefore points at a code hash that never produced it end to end; the {{Reproduce a run|#t-rep}} tab flags it.


When it matters. Whenever an early step is expensive: training, a large data job, an evaluation over thousands of prompts. For a pipeline of cheap steps, rerunning is simpler than reasoning about what was reused.


How to check. Make the last step fail on purpose and resume: the engine's log must say it cloned the earlier steps (here: Cloning previously run task 1792142900051724/train/2), and their outputs must have the same content hashes as the original run (they do: the {{Lineage graph|#t-lin}} shows identical artifact hashes).


Predict: after the failure you also want to try lr 0.003 instead of 0.001. You run python flow.py resume --lr 0.003. What happens?




Resume is for continuing the same run after a failure, not for changing it. Metaflow's docs: parameter values "can't be changed on resume", and configs from the original run are used. Changing an input means a new run with its own record; that is what keeps the record honest. Caching engines (KFP, Flyte) handle this differently: a changed input changes the cache key, so the step reruns.

Choosing, in one paragraph. If pipelines are mostly scheduled data work and you already run Airflow, use Airflow and let its training task submit to the cluster. If everything runs on Kubernetes and steps should be containers, Kubeflow Pipelines or Flyte. If the users are researchers who write Python and want the same flow on a laptop and in the cloud, Metaflow (or Prefect for general automation). If the things you care about are datasets and their freshness, Dagster.
