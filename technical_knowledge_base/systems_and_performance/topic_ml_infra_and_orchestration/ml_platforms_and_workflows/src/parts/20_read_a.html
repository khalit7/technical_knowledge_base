The idea

A scheduler decides which machines run a job; an ML platform makes every model in use the end of a recorded chain (the hashes of its code, data, config and environment, the workflow run that used them, the tracker's run record, an immutable registry version and a movable alias), so that anyone can say what made it and make it again.

Run
one execution of a training program with fixed inputs.
Artifact
any file or object a step produces: a data split, a checkpoint, a model.
Workflow (pipeline), step
a directed acyclic graph (DAG) of steps; an arrow means "needs that step's output".
Workflow engine
runs the graph, stores each step's outputs, retries, resumes; an orchestrator, not a scheduler.
Tracker, run record
a service that keeps one record per run: parameters, metrics, tags, artifacts.
Registered model, version, alias
a name; an immutable numbered entry under it; a movable label on one version.
Lineage
the chain of links from an artifact back to everything that made it.
Reproducing
producing the same artifact again from that chain (bit for bit on the same machine here, not across platforms: section 8).
Feature store
a store of model inputs computed once, read point in time correct for training and fast for serving (section 9).

1. Why a platform layer

The problem. After a week of experiments a team has dozens of checkpoints, each made by some version of the code, on some version of the data, with some flags. Which run gave the number on the slide? Was it trained before or after the dedup fix? Which file is in production? A folder named final_v3_really_final/ answers none of them. Sculley and colleagues at Google called this hidden technical debt: ML systems pick up "data dependencies, configuration issues" and "undeclared consumers" that cost far more to maintain than the model code ({{Sculley et al., NIPS 2015|https://papers.nips.cc/paper_files/paper/2015/hash/86df7dcfd896fcaf2674f757a2463eba-Abstract.html}}). The answer is the chain in the figure: steps written as a graph the machine runs, every run recorded automatically, good models given names and versions, hashes tying them together.

The cost. A tracking server with its database and artifact store to run and back up (here about 540 MB of memory at idle for the MLflow server's three processes measured), a workflow engine to configure (a step here hung for 6 minutes because steps have no timeout by default: section 3), and discipline: a record is only as good as what the code logs.

When it matters. A tracker and a registry pay off from the first shared project, because the cost of a lost run is paid later and by someone else. A workflow engine pays off once the same multi-step process runs often enough that doing it by hand causes mistakes: a nightly evaluation of every new checkpoint, a data pipeline that feeds training, a sweep of many runs. A single researcher's one-off pretraining run on Slurm needs the tracker, not the engine. How to check you have it: pick any model in use and answer, from records alone, the exact command, code version, data version, environment and metrics (section 8 does it for this page's registry).
