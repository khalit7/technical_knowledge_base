9. Feature stores, in brief

The problem. For models fed by tabular or event data (fraud, ranking, recommendations), the inputs are features computed from logs: "trips this driver made today". Training needs each feature as it was when each labelled event happened; serving needs the current value in milliseconds. Computing them twice, in two code paths, gives a model trained on one definition and served another; joining training labels to the latest value lets the future leak into training. A feature store computes each feature once and serves it two ways: "an offline store for historical feature extraction used in model training" and "an online store for serving features at low-latency in production" ({{Feast docs|https://docs.feast.dev/}}).

The point-in-time join: each training row sees only what was known at its event time illustrative values

Feature rows for driver 1001 (trips_today): 09:00 = 3, 10:00 = 5, 11:00 = 8. Time to live (TTL) 2 hours, as in Feast's example feature view.

For each entity row, Feast's get_historical_features() looks backward from that row's own timestamp, up to the TTL ("TTL is not relative to the current point in time"). By default only the event timestamp constrains the join; filter_by_created_timestamp=True also hides values backfilled or corrected later, "to keep backfilled values from leaking into training data" ({{Feast, point-in-time joins|https://docs.feast.dev/getting-started/concepts/point-in-time-joins}}).

When it matters. When the same features feed many models and serving needs them fresh: the classic case is Uber's Michelangelo, whose feature store and serving numbers are on {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}}. LLM training does not use one: its inputs are token shards, versioned as datasets (section 7). The tools: Feast (open source), the clouds' own feature stores, and Tecton, which Databricks announced it had acquired in August 2025 ({{ChannelLife, 2025-08-26|https://channellife.com.au/story/databricks-acquires-tecton-to-boost-real-time-ai-agent-data}}). How to check: rebuild one training row by hand from the raw log at its event time and compare it with what the store returned.

10. Managed platforms: SageMaker, Vertex AI and Azure ML, and what they take off your hands

A managed platform is the hero figure with the cloud running the boxes: training compute that exists only for a job, a hosted tracker, a registry, a pipeline service. What it abstracts is operations (servers, databases, upgrades, capacity); what it does not abstract is the discipline of sections 5 to 8. SageMaker training jobs against HyperPod: who owns the cluster

Training job: the job owns its machines

startdatatrainupload

One API call (CreateTrainingJob) names a container, instances and S3 input and output. The job moves through Starting, Downloading (data to the instances' volumes), Training and Uploading ("model artifacts are being uploaded to the S3 location"). You are billed from TrainingStartTime to TrainingEndTime, which "for successful jobs ... is the time after model artifacts are uploaded" ({{TrainingJob API|https://docs.aws.amazon.com/sagemaker/latest/APIReference/API_TrainingJob.html}}). Good for: many independent runs, sweeps, fine-tuning; nothing to keep alive between jobs.

HyperPod: the cluster outlives the jobs

job AfaultA resumedjob B

"A persistent cluster service" for "resilient clusters" ({{SageMaker training docs|https://docs.aws.amazon.com/sagemaker/latest/dg/how-it-works-training.html}}), orchestrated by Slurm (head, login and worker nodes; you sbatch as on any cluster) or by Amazon EKS. With node recovery set to Automatic (the default) it "reboots or replaces faulty nodes"; a job launched with srun --auto-resume=1 is restarted "from the last saved checkpoint" once the faulty nodes are replaced, after nvidia-smi, Neuron and EFA checks ({{HyperPod auto-resume|https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-resiliency-slurm-auto-resume.html}}). Good for: long pretraining runs on reserved capacity, where recovery time is what costs (sibling: {{Fault tolerance at scale|n:3fc5c17b0d0d815786d1c1dddb311a9b}}).

Strips are schematic, not to scale: a job's four stages; a cluster on which job A loses a node, the node is replaced and A resumes, then job B runs. The auto-resume script must not trust $SLURM_JOB_NODELIST, "because its value might be outdated after SageMaker HyperPod auto-resumes the job"; it recomputes the node list and MASTER_ADDR from scontrol. Auto-resume restarts the step; the checkpoint it resumes from is still yours to write.

Cost controls and automation AWS docs. A training job's StoppingCondition caps its run time ("Use this API to cap model training costs"); on a stop SageMaker sends SIGTERM and allows 120 seconds to save artifacts; managed Spot training runs on Spot instances, and warm pools keep instances between jobs ({{TrainingJob API|https://docs.aws.amazon.com/sagemaker/latest/APIReference/API_TrainingJob.html}}). A HyperPod cluster stays up between jobs, so its idle time is the cost to manage. SageMaker's managed MLflow emits events to Amazon EventBridge, including "SageMaker MLFlow Tracking Server Setting Registered Model Alias", which EventBridge routes "to consumer applications": an alias move can start a deployment without anyone polling the registry ({{SageMaker managed MLflow|https://docs.aws.amazon.com/sagemaker/latest/dg/mlflow.html}}).

Limits and details of the managed trackers (as documented 2026-10-24)
  • SageMaker MLflow tracking servers come in Small, Medium and Large, recommended for teams of up to 25, 50 and 100 users, at up to 25, 50 and 100 sustained transactions per second; "SageMaker AI MLflow has a 200 MB download size limit"; the newer serverless MLflow Apps run MLflow 3.16. Every MLflow REST call is an IAM action under the sagemaker-mlflow prefix, logged in CloudTrail.
  • Azure ML: support for MLproject files "will be fully retired in September 2026"; MLflow tracking from R and Java is limited (no model registration from R, no artifacts from Java).
  • HyperPod on Slurm gained health monitoring agents on 2025-09-11. When GRES are attached to a Slurm node, auto-resume re-queues the job and restarts it "from the beginning" instead of replacing the node in place.
  • HyperPod with EKS maps one EKS control plane to one HyperPod cluster and offers job auto-resume for Kubeflow PyTorch training ({{HyperPod overview|https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod.html}}); launched 2023-11-29 with Slurm, EKS support GA 2024-09-10 (root Tool map).
