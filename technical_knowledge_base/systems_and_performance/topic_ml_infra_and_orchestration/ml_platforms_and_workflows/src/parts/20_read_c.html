5. Experiment tracking: one record per run

The idea. A tracker keeps one run record per execution: the parameters it was given, metrics as step-indexed series (loss at step 10, 20, ...), tags (free-form strings: code hash, data hash, platform), artifacts (files) and system metadata it fills in itself (user name, source file, git commit when run from a repository). Runs are grouped into experiments and can be searched and compared: "every run with lr above 0.003 sorted by held-out loss" is one query.

How MLflow is built. Three parts. The client (mlflow.log_metric, MlflowClient) talks REST to a tracking server, which keeps run and registry records in a backend store (a SQL database: SQLite here, PostgreSQL or MySQL in production) and files in an artifact store (S3, GCS, Azure, a local folder). Started with --artifacts-destination, the server proxies artifact uploads, so clients see mlflow-artifacts:/ URIs and need no bucket credentials. The server here was one command:

mlflow server --backend-store-uri sqlite:///mlflow.db --artifacts-destination ./artifacts \
  --host 127.0.0.1 --port 5077 --workers 1

It started three processes (the launcher, a uvicorn web app and a job runner) using about 540 MB of memory at idle, and printed Security middleware enabled with default settings (localhost-only) measured. After eight workflow runs the database held , the artifact store , and Metaflow's datastore : small, because this model is small; with real checkpoints the artifact store is the part that grows (sibling page: Storage and data movement).

The local default changed, and the old one now refuses to run. With no URI set, MLflow 3.17.1 writes to sqlite:///mlflow.db in the working directory ({{mlflow/store/tracking/__init__.py line 13|https://github.com/mlflow/mlflow/blob/v3.17.1/mlflow/store/tracking/__init__.py}}), unless ./mlruns already holds experiments, in which case it keeps using them. The docs date the switch to MLflow 3.7.0 and say the file store "is in maintenance mode" ({{backend store docs|https://mlflow.org/docs/latest/self-hosting/architecture/backend-store/}}). In 3.17.1 asking for a file store explicitly raises, measured here: MlflowException: The filesystem tracking backend (e.g., './mlruns') is in maintenance mode and will not receive further updates. ... set `MLFLOW_ALLOW_FILE_STORE=true` to opt out of this exception. ({{file_store.py line 225|https://github.com/mlflow/mlflow/blob/v3.17.1/mlflow/store/tracking/file_store.py}}). Old tutorials that say "MLflow logs to ./mlruns" are out of date.

Logging from distributed training. Every rank computes the loss, but one record should hold it: log from rank 0 only (or give each rank its own run and tag it). Log the all-reduced loss, not one rank's: here the flow logged gloss, the mean over ranks, the number the topic compares across Slurm, Kubernetes and Ray. This lab logs after the fact: train.py writes one JSON line per logged step, and the workflow step uploads all 21 points in one log_batch call after torchrun exits. That keeps the training code free of tracker imports and makes the tracker optional, at the price of seeing nothing live; hosted trackers (Weights & Biases) stream metrics and system metrics (GPU utilisation, memory) during the run.

The status trap measured. Each step of this flow opened the MLflow run, logged, and closed it. The first workflow run hung inside train and was killed; its MLflow run says FINISHED, because start had closed it cleanly, and it has no metrics at all. A tracker's status is what the code told it, not what happened. Check runs by their content (does it have val_loss?), keep one run open for the whole workflow with a heartbeat, or tag the workflow's own final state.

The trackers. MLflow (Linux Foundation project led by Databricks, Apache-2.0, 3.17.1 on 2026-10-13; 3.0 in June 2025 added the LoggedModel entity, "moving beyond the traditional run-centric approach", {{MLflow 3 release|https://mlflow.org/releases/3}}): the open default, self-hosted on a database plus object storage. Weights & Biases (client 0.30.0; owned by CoreWeave since 2025-05-05, {{CoreWeave|https://www.coreweave.com/news/coreweave-completes-acquisition-of-weights-biases-2}}): a widely used hosted tracker for deep learning, with artifacts, a registry, sweeps and live system metrics. ClearML (2.1.12): a self-hosted suite of tracking, data versioning, pipelines and an agent that pulls queued jobs onto GPU machines.

A tracker can disappear. Neptune, a hosted tracker used for foundation-model training, agreed to be acquired by OpenAI in December 2025; its hosted app and API were turned off "On March 5, 2026, at 10 am PST", data still there was "securely and irreversibly deleted", and the transition hub offered an exporter and migration guides to MLflow, Weights & Biases, ZenML, Comet and others ({{Neptune transition hub|https://docs.neptune.ai/transition_hub}}, read 2026-10-16; the root's Tool map records the earlier March 4 date and its correction). Lesson: whatever tracker you use, keep an export of the records that matter (a scheduled dump of runs, metrics and registry to your own storage), and keep the training code independent of the tracker's SDK where you can, as this lab does.

6. The model registry: names, versions and aliases

The idea. A registered model is a name (mi-tiny-gpt). Each time a model is registered under it, the registry creates a version (1, 2, 3, ...), which is immutable: it points at one stored model and the run that made it. An alias is a movable label on one version ("a mutable, named reference", {{MLflow docs|https://mlflow.org/docs/latest/ml/model-registry/}}): champion for what serves, challenger for what is being tested. Consumers load models:/mi-tiny-gpt@champion; deploying a new model is moving the alias, and rolling back is moving it back. Tags on a version carry evidence (here val_loss, data_sha, code_sha, ckpt_sha, metaflow_run).

Stages are deprecated. MLflow's older fixed stages (None, Staging, Production, Archived) and transition_model_version_stage carry @deprecated(since="2.9.0") in 3.17.1 ({{mlflow/tracking/client.py line 4941|https://github.com/mlflow/mlflow/blob/v3.17.1/mlflow/tracking/client.py}}); the REST response below still shows "current_stage": "None". Use aliases and tags.
