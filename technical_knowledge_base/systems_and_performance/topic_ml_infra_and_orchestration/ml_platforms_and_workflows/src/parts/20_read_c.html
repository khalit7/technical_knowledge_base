5. Experiment tracking: one record per run

A tracker keeps one run record per execution: the parameters it was given, metrics as step-indexed series (loss at step 10, 20, ...), tags (free-form strings: code hash, data hash, platform), artifacts (files) and system metadata it fills in itself (user name, source file, git commit when run from a repository). Runs are grouped into experiments and can be searched: "every run with lr above 0.003 sorted by held-out loss" is one query.

Logging from distributed training. The status trap measured. Each step of this flow opened the MLflow run, logged, and closed it. The first workflow run hung inside train and was killed; its MLflow run says FINISHED, because start had closed it cleanly, and it has no metrics at all. A tracker's status is what the code told it, not what happened. Check runs by their content (does it have val_loss?), keep one run open for the whole workflow with a heartbeat, or tag the workflow's own final state.

A tracker can disappear. Neptune, a hosted tracker used for foundation-model training, agreed to be acquired by OpenAI in December 2025; its hosted app and API were turned off "On March 5, 2026, at 10 am PST" and data still there was "securely and irreversibly deleted" ({{Neptune transition hub|https://docs.neptune.ai/transition_hub}}, read 2026-10-16). 6. The model registry: names, versions and aliases

A registry (MLflow Model Registry, W&B Registry, the Hugging Face Hub, the clouds' registries) holds registered models. A registered model is a name (mi-tiny-gpt). Each registration creates a version (1, 2, 3, ...), immutable: it points at one stored model and the run that made it. An alias is a movable label on one version ("a mutable, named reference", {{MLflow docs|https://mlflow.org/docs/latest/ml/model-registry/}}): champion for what serves, challenger for what is being tested. Consumers load models:/mi-tiny-gpt@champion; deploying is moving the alias, rolling back is moving it back. Tags on a version carry evidence (here val_loss, data_sha, code_sha, ckpt_sha, metaflow_run).

Promotion is a gate in code. The register step registers every model as a new version, then moves champion only if the new held-out loss is strictly lower than the current champion's (simplified from flow.py, which also handles the first version, when no alias exists yet):

champ = client.get_model_version_by_alias("mi-tiny-gpt", "champion")
if val_loss < float(champ.tags["val_loss"]):
    client.set_registered_model_alias("mi-tiny-gpt", "champion", version)

The registry's one mutable thing, moving: six registrations, three alias moves replayed from the version tags

Each step registers the next version, as the register step did, and applies the gate. The replay (src/scripts/gen_data.py) matches the alias the server ended with: version 3. Versions stay; only the alias moves.

A correct gate scores champion and challenger on the same frozen evaluation set in the same step (or refuses to compare when the eval-set hash differs), moves the alias only on a margin larger than the noise, and keeps the previous champion for rollback; production evaluation gates do this (sibling topic: {{Production eval engineering|n:3c65c17b0d0d81b39ad9e96193d21adc}}).

An example of shape (2, 64) kept the batch dynamic (tested). The alternative is serialization_format="pickle", which needs the model's class importable when loading.
