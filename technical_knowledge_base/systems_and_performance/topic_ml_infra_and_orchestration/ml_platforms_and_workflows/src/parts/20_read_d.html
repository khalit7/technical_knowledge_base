7. Lineage and versioning: what made this model?

The idea. A model is a function of a handful of inputs: code, data, configuration (parameters, seed), environment (library versions, hardware) and, for a resumed run, a checkpoint. Lineage records an identifier for each, at the moment it is used, on the record of the run and on the model version. An identifier is only useful if it changes whenever the thing changes: a content hash (SHA-256 of the bytes) or an immutable version id, never a name like latest or a path like /data/shakespeare/.

Content addressing gives lineage for free. Metaflow stores each artifact under the hash of its bytes, so identical outputs are stored once and the same hash appears wherever the same object was used. In the {{Lineage graph|#t-lin}}, the resumed run's train task carries exactly the artifact hashes of the failed run's train task (it was cloned), and every run on the 90/10 split shares one train_sha. Lineage across systems is the harder part: a dataset written by a Spark job, read by a training job, evaluated by a pipeline. OpenLineage, a Linux Foundation project, defines events about "datasets, jobs, and runs" that tools emit so one graph can be assembled ({{openlineage.io|https://openlineage.io/}}).

The cost. Hashing a 1 MB file is free; hashing a 10 TB dataset at every run is not, so at scale the hash is taken once when a dataset version is written and the run records the version id. Every pinned input must also be kept: a hash of data that was deleted proves nothing can be rebuilt.

How to check. From a model version, walk back to every input without asking a person. The {{Lineage graph|#t-lin}} does this on the real records; the {{Reproduce a run|#t-rep}} tab then reruns the result.

8. Reproducibility: same command, same bits?

"Reproducible" means three different things, from weakest to strongest: you can re-execute the same command (you know what it was); the result is statistically equivalent (same quality within noise, what most large runs can promise); the result is bit-identical (every byte of the checkpoint the same). The running example was built to be bit-identical: no dropout, deterministic algorithms, one thread per rank, batches drawn from (seed, step) only (root page, src/data/README.md). What this means. Bit-identical reproduction held on the same machine and software, and broke across platforms with the same version number of PyTorch: the macOS and Linux builds compute some operations in a different order or with different kernels (which ones was not traced here), and once one rounding differs, training amplifies it. The drift stays tiny for this model (1.3e-5 in loss after 200 steps); on a large run that difference grows into a different trajectory that is only statistically equivalent. The root's Failure lab found the same edge inside one platform: resuming the running example from a checkpoint is bit-exact with 2 ranks but not with 4, because DDP rebuilds its gradient buckets after restart (2.4e-7 at two logged steps).

What to pin, so a rerun is at least equivalent: the code commit, the data version, the full config and seed, the container image digest (it fixes the library builds, not just their versions), the hardware type and the number of ranks; and store the checkpoint, since the cheapest exact reproduction of a trained model is to keep it.

10. Design: the platform for a 1,000-GPU training lab

The interview version: 1,000 GPUs (125 nodes of 8), about 50 researchers, a few long pretraining runs, hundreds of fine-tuning and ablation runs a week, nightly evaluation of new checkpoints. One reasonable design, with the trade-off at each choice:

  1. Scheduler: Slurm, or Kubernetes with Kueue and JobSet (the root page and its Scheduling lab compare them). The platform layer must work with either: every job goes through one submission wrapper.
  2. Submission wrapper (the piece most teams underbuild): a small CLI that refuses a dirty git tree, resolves the dataset version and container image digest, creates the tracker run with those as tags, then calls sbatch or creates the JobSet. Lineage then exists for every run, not just the careful ones.
  3. Tracker: hosted Weights & Biases (no operations, live system metrics, cost per seat, data leaves your network) or self-hosted MLflow on PostgreSQL plus object storage (you run and back it up). Either way, a nightly export of runs and the registry to your own storage: Neptune's shutdown is the reason.
  4. Registry: the tracker's registry, with aliases per purpose (champion, eval-candidate) and version tags for evidence; checkpoints stay in object storage and the registry points at them.
  5. Workflow engine: for the recurring pipelines only: data preparation, the nightly evaluation of every new checkpoint, registration and promotion. Airflow if a data team already runs it; Flyte or Kubeflow Pipelines on a Kubernetes estate. The training job itself stays a scheduler job that the pipeline submits and waits for.
  6. Gate: promotion scored on a frozen evaluation set whose hash is checked, champion and challenger in the same step (section 6); a human approval for anything that serves users.
  7. Retention: keep every registered version's checkpoint, keep the last few checkpoints of each run, delete the rest on a schedule; the tracker's records cost little and are kept.

What breaks first, and how to check: the tracker's database under many runs logging many metrics at a high rate (load-test it with the expected points per second: for example 200 concurrent runs x 50 metrics every 10 s is 1,000 points per second derived, illustrative inputs); artifact storage filled by checkpoints nobody registered; pipelines that hang without timeouts; and lineage gaps from runs started outside the wrapper.
