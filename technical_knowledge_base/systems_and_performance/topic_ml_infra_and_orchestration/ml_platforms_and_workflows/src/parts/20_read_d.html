7. Lineage and versioning: what made this model?

A model is a function of a handful of inputs: code, data, configuration (parameters, seed), environment (library versions, hardware) and, for a resumed run, a checkpoint. Lineage records an identifier for each, at the moment it is used, on the run record and on the model version. An identifier is only useful if it changes whenever the thing changes: a content hash (SHA-256 of the bytes) or an immutable version id, never a name like latest, :latest or a path like /data/shakespeare/. Movable names belong in one place only: the registry alias that chooses what to serve.

Content addressing gives lineage for free. Metaflow stores each artifact under the hash of its bytes, so identical outputs are stored once and the same hash appears wherever the same object was used: in the graph, the resumed run's train task carries exactly the artifact hashes of the failed run's (it was cloned), and every run on the 90/10 split shares one train_sha. Lineage across systems is the harder part: a dataset written by a Spark job, read by a training job, evaluated by a pipeline. OpenLineage, a Linux Foundation project, defines events about "datasets, jobs, and runs" that tools emit so one graph can be assembled ({{openlineage.io|https://openlineage.io/}}).

The cost. Hashing a 1 MB file is free; hashing a 10 TB dataset at every run is not, so at scale the hash is taken once when a dataset version is written and the run records the version id. Every pinned input must also be kept: a hash of data that was deleted proves nothing can be rebuilt.

8. Reproducibility: same command, same bits?

"Reproducible" means three things, from weakest to strongest: you can re-execute the same command (you know what it was); the result is statistically equivalent (same quality within noise, what most large runs can promise); the result is bit-identical (every byte of the checkpoint the same). The running example was built to be bit-identical: no dropout, deterministic algorithms, one thread per rank, batches drawn from (seed, step) only (root page, src/data/README.md).

What this means. Bit-identical reproduction held on the same machine and software, and broke across platforms with the same version number of PyTorch: the macOS and Linux builds compute some operations in a different order or with different kernels (which ones was not traced here), and once one rounding differs, training amplifies it. The drift stays tiny for this model (1.3e-5 in loss after 200 steps); on a large run it grows into a different trajectory that is only statistically equivalent. The root's Failure lab found the same edge inside one platform: resuming the running example from a checkpoint is bit-exact with 2 ranks but not with 4, because DDP rebuilds its gradient buckets after restart (2.4e-7 at two logged steps). So before blaming code for a difference in the 6th decimal, check the platform, image digest, number of ranks and thread counts.

What to pin, so a rerun is at least equivalent: the code commit, the data version, the full config and seed, the container image digest (it fixes the library builds, not just their versions), the hardware type and the number of ranks; and store the checkpoint, since the cheapest exact reproduction of a trained model is to keep it.
