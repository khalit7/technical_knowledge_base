Tasks: remote functions and futures

@ray.remote registers a function with the cluster. f.remote(x) does not run f: it sends a task description (function, arguments, resource request, by default 1 CPU) to Ray and returns an ObjectRef at once. ray.get(ref) blocks until the result exists; ray.wait(refs) returns the ones that are ready. Because .remote() returns immediately, you submit many tasks before waiting for any: that is where the parallelism comes from.

From src/scripts/ry_core.py (section tasks), run as the driver on the head:

@ray.remote
def noop():
    return socket.gethostname()

# one at a time: submit, wait, repeat (100 times)
for _ in range(100):
    ray.get(noop.remote())
# 1,000 at once: submit all, then wait for all
hosts = ray.get([noop.remote() for _ in range(1000)])

measured One tiny task round trip (submit, schedule, run, return) took about 3 ms on this laptop; 1,000 tasks submitted together cost well under 1 ms each, because Ray pipelines them across the 4 worker processes and reuses a leased worker for many tasks. The 1,000 results came from both workers (the split is in the card). The {{Ownership paper|https://www.usenix.org/conference/nsdi21/presentation/cheng}} (NSDI 2021, the design Ray implements) reports about 1 ms per task on a real cluster published: the same order.

About 1 s (two waves of 4 on 4 CPUs) against about 4 s: 4.0 s instead of 1.1 s here. In the second form each ray.get waits for its task before the next is even submitted, so the eight run one after another: the classic "ray.get in a loop" mistake.

Where ray.get sits decides whether tasks overlap measured

Each lane is one worker process (node and pid from the run); each bar is one task, placed where and when it really ran. Same eight tasks, same cluster.

Cost. A task is a scheduling decision, a message and a serialisation: milliseconds, not microseconds. Batch tiny work into fewer, larger tasks. The Ray docs' own example ({{anti-pattern: too fine-grained tasks|https://docs.ray.io/en/latest/ray-core/patterns/too-fine-grained-tasks.html}} published) runs 10,000 calls of a 10-microsecond function: about 0.17 s as plain calls, 1.6 s as one task each, 0.03 s as batches of 1,000 per task.

Check. ray status shows CPUs in use; ray timeline writes a Chrome trace with each task as a bar per worker, as drawn above. Serial bars that should overlap mean a ray.get between submissions.

Actors: a process with state

Tasks forget everything between calls; a model on a GPU, a replay buffer or a simulator must live in one process. @ray.remote on a class makes an actor class: Counter.remote() starts a dedicated worker process, runs __init__ there and returns an actor handle. Calls from one caller run one at a time in submission order (unless you ask for max_concurrency or async methods), so two calls never touch the state at once.

@ray.remote
class Counter:
    def __init__(self):
        self.n = 0
    def incr(self):
        self.n += 1
        return self.n

c = Counter.remote()                                  # a new process on some node
vals = ray.get([c.incr.remote() for _ in range(1000)])  # 1,000 calls queued, run in order

measured After creation, an actor call round trip was faster than a task's: no scheduling decision, the caller talks straight to the actor's process. The 1,000 queued calls came back in order (the counter starts above 1 because 100 single calls ran first).
