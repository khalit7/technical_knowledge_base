Tasks: remote functions and futures

The problem. You have a function and a thousand inputs, and one machine is too slow. You want the calls to run on many cores of many machines without writing sockets, queues or a scheduler.

How it works. Decorating a function with @ray.remote registers it with the cluster. f.remote(x) does not run f: it sends a task description (function, arguments, resource request, by default 1 CPU) to Ray and immediately returns an ObjectRef, a future. ray.get(ref) blocks until the result exists and returns it; ray.wait(refs) returns the ones that are ready. Because .remote() returns at once, you can submit many tasks before waiting for any: that is where the parallelism comes from.

From src/scripts/ry_core.py (section tasks), run as the driver on the head:

@ray.remote
def noop():
    return socket.gethostname()

# one at a time: submit, wait, repeat (100 times)
for _ in range(100):
    ray.get(noop.remote())
# 1,000 at once: submit all, then wait for all
hosts = ray.get([noop.remote() for _ in range(1000)])

measured One tiny task round trip (submit, schedule, run, return) took about 3 ms on this laptop; 1,000 tasks submitted together cost well under 1 ms each because Ray pipelines them across the 4 worker processes and reuses a leased worker for many tasks. The 1,000 results came from both workers (the hosts split is shown). The {{Ownership paper|https://www.usenix.org/conference/nsdi21/presentation/cheng}} (NSDI 2021, the design Ray implements) reports about 1 ms per task on a real cluster published; a laptop VM is slower but the same order.

Predict: eight tasks that each sleep 0.5 s, on a cluster with 4 free CPUs. How long does ray.get([nap.remote(i, 0.5) for i in range(8)]) take, and how long does [ray.get(nap.remote(i, 0.5)) for i in range(8)] take?
About 1 s (two waves of 4 on 4 CPUs) against about 4 s. In the second form each ray.get waits for its task before the next task is even submitted, so the eight run one after another: the classic "ray.get in a loop" mistake. What it costs. A task is a scheduling decision, a message to a worker, a serialisation of arguments and results: milliseconds, not microseconds. Tasks of a few milliseconds of work spend most of their life in overhead, so batch tiny work into fewer, larger tasks. The Ray docs' own example ({{anti-pattern: too fine-grained tasks|https://docs.ray.io/en/latest/ray-core/patterns/too-fine-grained-tasks.html}} published) runs 10,000 calls of a 10-microsecond function: about 0.17 s as plain calls, 1.6 s as one task each, 0.03 s as batches of 1,000 per task.

How to check it. ray status shows how many CPUs are in use right now; the dashboard's timeline (ray timeline writes a Chrome trace) shows each task as a bar per worker, exactly as drawn above. If the bars are serial when they should overlap, look for a ray.get between submissions.

Actors: a process with state

The problem. Tasks forget everything between calls. A model loaded on a GPU, a replay buffer, an environment simulator, a counter of tokens processed: these must live in one process and be called many times.

How it works. @ray.remote on a class makes it an actor class. Counter.remote() starts a dedicated worker process somewhere in the cluster, runs __init__ there and returns an actor handle. c.incr.remote() sends a method call to that one process; calls from one caller run one at a time in submission order (unless you ask for concurrency with max_concurrency or async methods), so the state is never touched by two calls at once.

@ray.remote
class Counter:
    def __init__(self):
        self.n = 0
    def incr(self):
        self.n += 1
        return self.n

c = Counter.remote()                                  # a new process on some node
vals = ray.get([c.incr.remote() for _ in range(1000)])  # 1,000 calls queued, run in order

measured Creating the actor (start a process, run __init__) took a fraction of a second; after that a call round trip was faster than a task's, because no scheduling decision is needed: the caller talks straight to the actor's process. 1,000 queued calls came back in order (first value, last value and the ordered check are from the run; the counter starts above 1 because 100 single calls ran first).

When it matters. Every training worker in Ray Train is an actor (RayTrainWorker in the logs), and so is every vLLM engine in an RL post-training stack. Choosing "task or actor" is choosing whether state, placement and order matter. The actor's price is that its state dies with its process, which is the fault-tolerance section's subject.
