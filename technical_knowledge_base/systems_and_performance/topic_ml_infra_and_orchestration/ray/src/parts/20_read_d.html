Processes: the GCS, raylets, workers and the driver

Four kinds of process make the cluster in the hero figure; knowing which holds what is how you read logs and failures.

GCS (head only)

The Global Control Service (older papers: Global Control Store), gcs_server: the node table, the actor table (where each actor lives, its restarts), placement groups, jobs, a key-value store. It health-checks every raylet and declares nodes dead. It does not hold objects or schedule ordinary tasks.

Raylet (every node)

A scheduler that grants worker leases for this node's resources or points the request elsewhere (spillback), the object store and object manager, and the worker pool that starts and reuses Python workers.

Workers

Python processes running tasks and actors. Each embeds a core worker library, which is where ownership lives.

Driver

Your script after ray.init(): a worker that owns everything it submits. Here and for Ray Jobs it runs on the head, so the head needs memory for it.

On the head, the dashboard outweighs the GCS measured

When it matters. The head is a single point of failure and a memory hot spot. The root's {{Failure lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} saw the head at 95% of its 1.5 GB cap during Ray Train runs, and Ray's memory monitor killed 13 non-training worker processes there. On a real cluster: no training on the head (--num-cpus 0, as here), memory for the driver, dashboard and Ray Train's controller, and GCS fault tolerance (Failures, below).

Found here: raising a container's memory cap does not raise Ray's kill threshold

Ray's memory monitor kills workers when a node's memory use passes memory_usage_threshold = 0.95 (ray_config_def.h line 79), checked every 250 ms (line 83). The threshold in bytes is computed once, when the raylet starts (src/ray/common/monitors/threshold_memory_monitor.cc line 33 stores it; line 126 compares against it). After docker update --memory 2000m on the running head, a Ray Train run still died with "Memory usage 1539858432B exceeded threshold of 1494220800B (71.2% of 2097152000B limit)": 1,494,220,800 is 95% of the old 1,500 MiB limit. Raise memory before ray start, or restart Ray after resizing. (This page then ran its head with 2,000 MB from the start, on 2026-10-16.)

Scheduling: resources, policies and placement groups

Resources are counters. A node advertises numbers (CPU, GPU, memory, any custom name such as fake_gpu); a task or actor asks for amounts (num_cpus=1, num_gpus=0.5, resources={"fake_gpu": 1}) and runs only where they are free. The numbers are for placement, not enforcement: Ray does not stop a task from using more (unlike Slurm with cgroups). On a real GPU node Ray sets CUDA_VISIBLE_DEVICES for the GPUs it assigned; for a custom resource it sets nothing.

Policies. The default hybrid policy prefers the local node until its critical resource passes scheduler_spread_threshold = 0.5 utilisation (ray_config_def.h line 252), then picks randomly among the least-loaded few (src/ray/raylet/scheduling/policy/hybrid_scheduling_policy.h lines 29 to 48: "Scheduling a task on a new node incurs a cold start penalty ... Past a certain utilization threshold, a big noisy neighbor problem occurs"). "SPREAD" spreads; NodeAffinitySchedulingStrategy(node_id, soft) pins to one node (soft: fall back if it is gone).

Placement groups reserve several bundles at once, all or nothing, so a multi-worker job never starts with half its GPUs: Ray's gang scheduling. The GCS reserves them with a two-phase commit across raylets ("The first phase of 2PC ... prepare resources", "The second phase of 2PC", src/ray/gcs/gcs_placement_group_scheduler.h lines 114 and 116). Ray Train puts its worker group in one (ScalingConfig(placement_strategy="PACK") by default).

Four bundles, two nodes of two: only the strict strategies refuse measured

Each bundle is 1 CPU + 1 fake_gpu, what one Ray Train worker asks for. Placements as recorded by the root's {{Scheduling lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} (src/sched/runs/ray/ray_pg.jsonl in the root's folder, Ray 2.59.0, 2026-10-16). PACK prefers one node but settles for two; SPREAD spreads bundles over nodes, best effort; the STRICT_ variants wait rather than settle: STRICT_PACK needs one node with 4 and STRICT_SPREAD four nodes, so both stayed PENDING (with 2 bundles each, both were created) and the autoscaler printed "Error: No available node types can fulfill resource request ... {'CPU': 4.0, 'fake_gpu': 4.0}". A second group that needed 3 of 4 GPUs waited holding nothing, then got all 3 at once 0.68 s after the first was removed.
