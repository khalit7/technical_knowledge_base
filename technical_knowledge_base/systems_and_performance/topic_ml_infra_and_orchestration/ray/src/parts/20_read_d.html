Architecture: the GCS, raylets, workers and the driver

Four kinds of process make a Ray cluster. Knowing which one holds what is how you read its logs and its failures.

GCS (head node only)

The Global Control Service (older papers: Global Control Store), process gcs_server. Holds cluster metadata: the node table, the actor table (where each actor lives, its restart count), placement groups, jobs, a key-value store. It health-checks every raylet and declares nodes dead. It does not hold objects or schedule ordinary tasks.

Raylet (every node)

The per-node daemon: a scheduler that grants worker leases for this node's resources (or points the request at another node), the object store and object manager that move objects between nodes, and the worker pool that starts and reuses Python worker processes.

Workers

Python processes that run tasks and actors. Each embeds a core worker library, which is where ownership lives: a worker that submits tasks keeps their refs, counts and lineage itself.

Driver

Your script after ray.init(): a worker that owns everything it submits. Here it runs on the head; for Ray Jobs it also runs on the head, so the head needs memory for it.

The life of one task, in the order the {{Ownership paper|https://www.usenix.org/conference/nsdi21/presentation/cheng}} and Ray's {{architecture whitepaper|https://docs.ray.io/en/latest/ray-contribute/whitepaper.html}} give it: the owner asks its local raylet for a worker lease that fits the task's resources; the raylet grants one of its own workers or replies "try node X" (spillback); the owner sends the task straight to the leased worker; the worker fetches any object arguments, runs the function and stores the result (inline back to the owner when small, in its node's store when large); the owner records the result's location and the lease is reused for the next task with the same shape or returned. The GCS is not on this path, which is why ordinary tasks keep running while the GCS is briefly slow. The {{Ownership lab|#t-own}} animates these steps.

What the head's memory is made of measured

When it matters. The head is a single point of failure and a memory hot spot. On this cluster the root's {{Failure lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} saw the head at 95% of its 1.5 GB cap during Ray Train runs, and Ray's memory monitor killed 13 non-training worker processes there. The fix on a real cluster is a head with no training on it (--num-cpus 0, as here), enough memory for the driver, the dashboard and Ray Train's controller, and GCS fault tolerance (below).

Found here: raising a container's memory cap does not raise Ray's kill threshold
Ray's memory monitor kills workers when a node's memory use passes memory_usage_threshold = 0.95 (ray_config_def.h line 79), checked every 250 ms (line 83). The threshold in bytes is computed once, when the raylet starts (src/ray/common/monitors/threshold_memory_monitor.cc line 33 stores it; line 126 compares against it). After docker update --memory 2000m on the running head, a Ray Train run still died with "Memory usage 1539858432B exceeded threshold of 1494220800B (71.2% of 2097152000B limit)": 1,494,220,800 is 95% of the old 1,500 MiB limit. Raise memory before ray start, or restart Ray after resizing. (This page then ran its Ray head with 2,000 MB from the start, 500 MB more than the shared setup, on 2026-10-16.)

Scheduling: resources, policies and placement groups

Resources are counters. A node advertises numbers: CPU, GPU, memory, and any custom name (fake_gpu here). A task or actor asks for amounts (num_cpus=1, num_gpus=0.5, resources={"fake_gpu": 1}), and Ray only runs it where the amounts are free. Ray does not stop a task from using more than it asked for: the numbers are for placement, not enforcement (unlike Slurm with cgroups). On a real GPU node Ray sets CUDA_VISIBLE_DEVICES for the GPUs it assigned; with a custom resource it sets nothing.

Policies. The default hybrid policy prefers the local node until its critical resource is past scheduler_spread_threshold = 0.5 utilisation (ray_config_def.h line 252), then picks among the least-loaded nodes, choosing randomly among the top few (src/ray/raylet/scheduling/policy/hybrid_scheduling_policy.h lines 29 to 48: "Scheduling a task on a new node incurs a cold start penalty ... Past a certain utilization threshold, a big noisy neighbor problem occurs"). "SPREAD" spreads over nodes; NodeAffinitySchedulingStrategy(node_id, soft) pins to one node (soft: fall back elsewhere if it is gone).

Placement groups reserve several bundles of resources at once, all or nothing, so a multi-worker job never starts with half its GPUs: Ray's gang scheduling. The GCS reserves them with a two-phase commit across the raylets ("The first phase of 2PC ... prepare resources", "The second phase of 2PC", src/ray/gcs/gcs_placement_group_scheduler.h lines 114 and 116). Strategies: PACK (as few nodes as possible, may spread), SPREAD, STRICT_PACK (one node or wait), STRICT_SPREAD (one bundle per node or wait). Ray Train puts its worker group in one placement group (ScalingConfig(placement_strategy="PACK") by default).

Measured in the root's Scheduling lab (not repeated here)
The {{Scheduling lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} ran every strategy on this cluster with 4 one-GPU bundles: PACK put 2 on each worker (a node only has 2), SPREAD alternated, STRICT_PACK and STRICT_SPREAD stayed PENDING forever (no node has 4; only 2 worker nodes), and the autoscaler printed "Error: No available node types can fulfill resource request ... {'CPU': 4.0, 'fake_gpu': 4.0}". A second group that needed 3 of 4 GPUs waited holding nothing, then got all 3 at once 0.68 s after the first was removed. Its recorded output is src/sched/runs/ray/ray_pg.jsonl in the root's folder.

Fault tolerance: what survives a crash

Ray separates three kinds of failure and handles each differently. Every row below was run on this cluster (ry_core.py fault and lineage); the error names and messages are Ray's own.

What failedDefault behaviour (source)What happened here

Tasks are retried up to max_retries = 3 times when the worker process or its node dies (DEFAULT_TASK_MAX_RETRIES = 3, ray_constants.py line 633; ray_option_utils.py line 182). An exception raised by your code is not retried unless you set retry_exceptions=True (line 207): Ray assumes a crash is the machine's fault and an exception is yours. Retries re-run the function, so tasks should be idempotent (safe to run twice).

Actors are not restarted by default (max_restarts = 0, line 254). With max_restarts=N Ray starts a new process and runs __init__ again: the state is gone (the counter went from 3 back to 1 here) unless the actor saved it somewhere and reloads it. Calls in flight when it died fail unless max_task_retries is set (default 0, line 255).

Objects lost with a node are rebuilt from lineage by their owner, by re-running the task that made them (the GCS log said "Attempting to recover 2 lost objects by resubmitting their tasks"), if that task is retryable. Objects whose owner died are lost for good (OwnerDiedError), and so are ray.put objects whose only copy was on the lost node.

Nodes are declared dead by the GCS after health_check_failure_threshold = 5 failed checks, sent every health_check_period_ms = 3,000 ms with a health_check_timeout_ms = 10,000 ms timeout (ray_config_def.h lines 1060 to 1064). Here the first check failed 11.7 s after the node was killed (a 10 s timeout: the container's address no longer answered) and the node was dead at 29.9 s; the root's Failure lab measured 30.0 s on its own run.

The head is the exception: without GCS fault tolerance, losing the head loses the cluster (every actor and object). With GCS fault tolerance the GCS writes its tables to an external Redis; when it restarts, raylets and workers reconnect (they wait up to gcs_rpc_server_reconnect_timeout_s = 60 s, line 549) and running tasks and actors continue ({{Ray docs: GCS fault tolerance|https://docs.ray.io/en/latest/ray-core/fault_tolerance/gcs.html}}; on KubeRay 1.3.0 and later, a gcsFaultToleranceOptions field in the RayCluster spec pointing at Redis: {{KubeRay GCS fault tolerance|https://docs.ray.io/en/latest/cluster/kubernetes/user-guides/kuberay-gcs-ft.html}}). not run here: it needs a Redis and a head restart, which teaches little on a toy cluster beyond what the docs state.

Predict: a task running on node B calls ray.put(big_array) and returns the ref to the driver. Node B dies. The array's only copy was on node C, which is healthy. Can the driver still ray.get it?
No. The owner is the worker on B that called ray.put; its reference count and location table died with it, and Ray's docs are explicit: "Currently, Ray does not support recovery from owner failure", and "Ray will clean up any remaining copies of the object's value to prevent a memory leak" ({{object fault tolerance|https://docs.ray.io/en/latest/ray-core/fault_tolerance/objects.html}}). Ray raises OwnerDiedError ("The object's owner has exited. This is the Python worker that first created the ObjectRef via .remote() or ray.put()"). It was measured here with the copy on the killed node itself (object C in the {{Ownership lab|#t-own}}). Rule: have the driver (or a long-lived actor) own anything you cannot afford to lose; return values from tasks instead of ray.put inside them.
