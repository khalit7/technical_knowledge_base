Failures: what survives a crash

Ray handles tasks, actors, objects and nodes differently. Every row below was run on this cluster (ry_core.py fault and lineage); error names and messages are Ray's own.

What failedDefault behaviour (source)What happened here
  • Tasks are retried up to max_retries = 3 times when the worker process or node dies (DEFAULT_TASK_MAX_RETRIES = 3, ray_constants.py line 633; ray_option_utils.py line 182). An exception from your code is not retried unless retry_exceptions=True (line 207): a crash is the machine's fault, an exception yours. Retries re-run the function, so tasks should be idempotent.
  • Actors are not restarted by default (max_restarts = 0, line 254). With max_restarts=N a new process runs __init__ again: the state is gone (the counter went from 3 back to 1 here). Calls in flight fail unless max_task_retries is set (default 0, line 255).
  • Objects lost with a node are rebuilt by their owner re-running the task (the GCS log said "Attempting to recover 2 lost objects by resubmitting their tasks"), if that task is retryable. Objects whose owner died are lost for good (OwnerDiedError), and so are ray.put objects whose only copy was on the lost node.
  • Nodes are declared dead by the GCS after health_check_failure_threshold = 5 failed checks, sent every health_check_period_ms = 3,000 ms with a health_check_timeout_ms = 10,000 ms timeout (ray_config_def.h lines 1060 to 1064). Here the first check failed 11.7 s after the node was killed and the node was dead at 29.9 s; the root's Failure lab measured 30.0 s on its own run.

No. The owner is the worker on B that called ray.put; its count and location table died with it. Ray's docs: "Currently, Ray does not support recovery from owner failure", and "Ray will clean up any remaining copies of the object's value to prevent a memory leak" ({{object fault tolerance|https://docs.ray.io/en/latest/ray-core/fault_tolerance/objects.html}}). The error reads "The object's owner has exited. This is the Python worker that first created the ObjectRef via .remote() or ray.put()"; measured here with the copy on the killed node itself (object C). Rule: let the driver or a long-lived actor own what you cannot lose; return values from tasks instead of ray.put inside them.

The head is the exception: without GCS fault tolerance, losing it loses the cluster. With GCS fault tolerance the GCS writes its tables to an external Redis; when it restarts, raylets and workers reconnect (they wait up to gcs_rpc_server_reconnect_timeout_s = 60 s, line 549) and running tasks and actors continue ({{Ray docs: GCS fault tolerance|https://docs.ray.io/en/latest/ray-core/fault_tolerance/gcs.html}}; on KubeRay 1.3.0 and later, a gcsFaultToleranceOptions field in the RayCluster spec: {{KubeRay GCS fault tolerance|https://docs.ray.io/en/latest/cluster/kubernetes/user-guides/kuberay-gcs-ft.html}}). not run here: it needs a Redis and a head restart, which teaches little on a toy cluster beyond what the docs state.

Ray Data: streaming blocks through the cluster

Training reads and transforms data while GPUs wait. Inside each training process, preprocessing is tied to the trainer's CPUs; all up front, it needs storage for the whole result and a long wait. A Ray Data Dataset is a lazy plan (read_* or from_items, then map_batches(fn), then a consumer such as iter_batches or a Ray Train worker). Data moves as blocks in the object store, which Ray Data "attempts to bound ... between 1 MiB and 128 MiB" ({{Ray Data internals|https://docs.ray.io/en/latest/data/data-internals.html}}; DEFAULT_TARGET_MAX_BLOCK_SIZE, python/ray/data/context.py line 76). The streaming executor runs every operator at once: each "takes in and outputs a stream of blocks", each block is one Ray task (or an actor pool for stateful work such as a model), and the first batch arrives once the first block has passed every stage.

  • Operator fusion. Consecutive map operators with compatible remote arguments become one task per block, with no store hop between them (are_remote_args_compatible, python/ray/data/_internal/logical/rules/operator_fusion.py lines 886 to 899: different num_cpus means no fusion).
  • Backpressure. "To limit object store use, Ray Data applies backpressure and stops launching tasks once enough data is buffered" (same page), so a slow consumer does not make producers fill memory.

When it matters. Heavy preprocessing, or preprocessing on a different machine type than training (CPU nodes decoding video for GPU trainers), and offline batch inference.
