The idea

Ray turns Python functions and classes into tasks and actors scheduled across a cluster; their results are immutable objects kept in each node's shared-memory store, and every object has an owner, the worker that created it, which counts its references, knows where its copies are and decides whether it can be rebuilt after a failure.

One call, y = f.remote(x), on this page's cluster: who does what

The driver (your script) asks a raylet for a worker lease (1), pushes the task straight to the leased worker (2), and the 8 MB result is stored in that node's object store (3); a reader on another node pulls a copy (4). The owner's table in the driver is the only record of y's references, copies and lineage. The GCS on the head keeps cluster metadata and health-checks nodes; it is not on the task's path. Ray Train, Data, Serve and Tune are libraries built from these pieces; the machines underneath come from Kubernetes or Slurm.

Where it sits. Slurm and Kubernetes hand out machines to jobs (the root page's {{Scheduling lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} compares them). Ray runs inside machines you already have, usually Kubernetes pods (KubeRay) or a Slurm allocation, and schedules the tasks of one program across them. It is not a rival to Slurm for "who gets the cluster"; it is the layer that makes one program distributed.

You need: DDP and torch.distributed for the Ray Train section ({{Distributed PyTorch|n:3c65c17b0d0d815e85aff8decd8f35ab}}); the root page's {{Slurm, Kubernetes and Ray comparison|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} for the cluster layer below.

New terms

  • Task: one call of a remote function; stateless, retryable.
  • Actor: an instance of a remote class; one process with state.
  • ObjectRef: a future, a handle to a result that will exist.
  • Object store: per-node shared memory holding large objects.
  • Owner: the worker that created a ref; holds its count, locations, lineage.
  • Lineage: the task that made an object, kept to re-run it.
  • Raylet: per-node daemon: scheduler, object manager, worker pool.
  • GCS: Global Control Service on the head: cluster metadata.
  • Placement group: bundles of resources reserved all or nothing.
  • Block: Ray Data's unit, a chunk of rows in the object store.

The cluster every number on this page came from measured

Ray 2.59.0 in three containers on one laptop (setup in the root's src/data/README.md). The head offers 0 CPUs, so no task runs there; each worker offers 2 CPUs, an 80 MB object store and 2 fake_gpu (a custom resource Ray counts and hands out, not a device). Memory is docker stats with the cluster idle.

How the evidence was made

All runs: Ray 2.59.0 (PyPI 2026-10-02), torch 2.14.1 CPU, 2026-10-16, scripts in src/scripts/ (ry_core.py tasks, actors, objects, spilling, failures and a node loss; ry_data.py Ray Data; ry_train.py Ray Train with its checkpoint API), raw output scrubbed in src/runs/. Timings are measured on Apple M1 Pro, Docker Desktop VM, shared machine: rough, useful for ratios and orders of magnitude, not as cluster numbers. Placements, counts, error types, messages and event orders are deterministic and transfer to a real cluster. Ray source is quoted at tag ray-2.59.0 (commit dd83c3a), file and line, located by pattern in src/scripts/ry_quotes.py; Ray Serve defaults were read from the same tag on 2026-10-24. The head was given a 2,000 MB cap, 500 MB more than the shared setup's 1,500 MB (see Processes). Process sizes are resident memory (RSS) read from /proc, which double-counts shared pages. Ray runs in Linux containers because it refuses a multi-node cluster on macOS ("Multi-node Ray clusters are not supported on Windows and OSX").
