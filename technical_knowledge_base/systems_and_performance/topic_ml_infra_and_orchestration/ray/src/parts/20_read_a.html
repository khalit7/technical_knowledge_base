Ray in one screen

Ray is a library that turns ordinary Python functions and classes into work that runs on many machines. You add @ray.remote to a function, call it with .remote(), and get back a ticket for a result that does not exist yet; Ray finds a machine with a free CPU (or GPU), runs the function there and keeps the result in shared memory on that machine until someone asks for it. Training libraries (Ray Train), data pipelines (Ray Data), hyperparameter search (Ray Tune) and most open RL post-training stacks are built on those few primitives.

Where it sits: Slurm and Kubernetes hand out machines to jobs (the root page's {{Scheduling lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} compares them). Ray runs inside machines you already have: a Ray cluster is a set of processes, usually started on Kubernetes pods (KubeRay) or inside a Slurm allocation, and Ray then schedules the tasks of one program across them. So Ray is not a rival to Slurm for "who gets the cluster"; it is the layer that makes one program distributed.

Four ideas carry the whole page. Each section below is one of them in detail.

1. Tasks

A task is one call of a remote function: stateless, runs anywhere a CPU is free, can be retried. Calling it returns at once with an ObjectRef (a future: a handle to a result that will exist).

2. Actors

An actor is an instance of a remote class: one long-lived process with state. Its method calls run one at a time, in order. A model replica, a parameter server, a rollout worker, a Ray Train worker: all actors.

3. Objects

Results and ray.put values are objects, immutable. Small ones travel inside messages; big ones live in each node's object store (shared memory), are copied to whichever node reads them, and spill to disk when the store fills.

4. Ownership

Every object has an owner: the worker that called .remote() or ray.put. The owner counts references, knows where copies live and remembers how to rebuild the object. When the owner dies, its objects are gone. This one rule explains most of Ray's failure behaviour.

The cluster this page ran on measured

The topic's lab cluster: Ray 2.59.0 in three containers on one laptop (setup in the root's src/data/README.md). The head runs the GCS, the dashboard and the driver but offers 0 CPUs, so no task runs there (this page gave it a 2,000 MB cap, 500 MB more than the shared setup's 1,500 MB: see Architecture); each worker offers 2 CPUs, an 80 MB object store and 2 fake_gpu, a custom resource Ray counts and hands out but that is not a device. Memory is what docker stats showed with the cluster idle; process sizes are resident memory (RSS) read from /proc, which double-counts shared pages. Ray runs in Linux containers because it refuses a multi-node cluster on macOS ("Multi-node Ray clusters are not supported on Windows and OSX").

How the evidence on this page was made
All runs: Ray 2.59.0 (PyPI 2026-10-02), torch 2.14.1 CPU, 2026-10-16, scripts in this page's src/scripts/ (ry_core.py tasks, actors, objects, spilling, failures and a node loss; ry_data.py Ray Data; ry_train.py Ray Train with its checkpoint API), raw output scrubbed in src/runs/. Timings are measured on Apple M1 Pro, Docker Desktop VM, shared machine: rough, useful for ratios and orders of magnitude, not as cluster numbers. Placements, counts, error types, messages and event orders are deterministic and transfer to a real cluster. Ray source is quoted at tag ray-2.59.0 (commit dd83c3a), file and line, located by pattern in src/scripts/ry_quotes.py.
