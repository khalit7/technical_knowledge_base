The idea

Ray turns Python functions and classes into tasks and actors scheduled across a cluster; their results are immutable objects kept in each node's shared-memory store, and every object has an owner, the worker that created it, which counts its references, knows where its copies are and decides whether it can be rebuilt after a failure.

Fig. 1, step by step: one call, y = f.remote(x), on the cluster every number on this page came from measured

  1. The cluster. Ray 2.59.0 in three containers on one laptop (setup in the root's src/data/README.md). The head offers 0 CPUs, so no task runs there; it holds the GCS (cluster metadata and node health checks) and your driver. Each worker, w1 and w2, offers 2 CPUs, an 80 MB object store and 2 fake_gpu (a custom resource Ray counts and hands out, not a device); every node runs a raylet. Idle memory from docker stats: head 692 MB of a 2,000 MB cap, workers 244 and 243 MB of 1,100 MB.
  2. The call returns a ref and makes an owner. Nothing runs yet: the driver (your script) creates the ObjectRef y, becomes its owner and writes its table: 1 reference, no location yet, and the lineage, the task f(x), to re-run if every copy is lost.
  3. A lease, with spillback. The owner asks its local raylet (the head's) for a worker lease that fits 1 CPU. The head offers 0 CPUs, so its raylet answers with spillback: ask w1, which has free CPUs (it knows other nodes' free resources from the cluster view the GCS keeps in sync). w1's raylet grants a lease on one of its pooled worker processes, or starts one.
  4. Push straight to the worker. The owner sends the task directly to the leased worker. The GCS is not on this path, which is why ordinary tasks keep running while it is briefly slow. If w1 has no copy of the argument x, its object manager pulls one first.
  5. The result lands in w1's store. 8 MB is over the 100 KB inline limit, so it is written to w1's object store and the worker tells the owner "y is at w1"; the lease can be reused for the next task of the same shape. A result under 100 KB would travel inside the reply and live in the owner's memory instead.
  6. A reader on w2 pulls a copy. The owner tells w2 where y is; w2's raylet pulls a copy into its own store, and that copy serves every reader on w2. Measured with a 16 MB object: the first read on w2 took 0.42 s, the second 5 ms.
  7. Freed when the count reaches 0. The driver deletes y: the owner tells both stores to free their copies and forgets the lineage.

The owner's table in the driver is the only record of y's references, copies and lineage. Message order from the {{Ownership paper|https://www.usenix.org/conference/nsdi21/presentation/cheng}} and Ray's {{architecture whitepaper|https://docs.ray.io/en/latest/ray-contribute/whitepaper.html}}; no timings are drawn per message because none were measured. Ray Train, Data, Serve and Tune are libraries built from these pieces; the machines underneath come from Kubernetes or Slurm. Positions are schematic.

Where it sits. Slurm and Kubernetes hand out machines to jobs (the root page's {{Scheduling lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} compares them). Ray runs inside machines you already have, usually Kubernetes pods (KubeRay) or a Slurm allocation, and schedules the tasks of one program across them. It is not a rival to Slurm for "who gets the cluster"; it is the layer that makes one program distributed.

You need: DDP and torch.distributed for the Ray Train section ({{Distributed PyTorch|n:3c65c17b0d0d815e85aff8decd8f35ab}}); the root page's {{Slurm, Kubernetes and Ray comparison|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} for the cluster layer below.

New terms

  • Task: one call of a remote function; stateless, retryable.
  • Actor: an instance of a remote class; one process with state.
  • ObjectRef: a future, a handle to a result that will exist.
  • Object store: per-node shared memory holding large objects.
  • Owner: the worker that created a ref; holds its count, locations, lineage.
  • Lineage: the task that made an object, kept to re-run it.
  • Raylet: per-node daemon: scheduler, object manager, worker pool.
  • GCS: Global Control Service on the head: cluster metadata.
  • Placement group: bundles of resources reserved all or nothing.
  • Block: Ray Data's unit, a chunk of rows in the object store.
How the evidence was made

All runs: Ray 2.59.0 (PyPI 2026-10-02), torch 2.14.1 CPU, 2026-10-16, scripts in src/scripts/ (ry_core.py tasks, actors, objects, spilling, failures and a node loss; ry_data.py Ray Data; ry_train.py Ray Train with its checkpoint API), raw output scrubbed in src/runs/. Timings are measured on Apple M1 Pro, Docker Desktop VM, shared machine: rough, useful for ratios and orders of magnitude, not as cluster numbers. Placements, counts, error types, messages and event orders are deterministic and transfer to a real cluster. Ray source is quoted at tag ray-2.59.0 (commit dd83c3a), file and line, located by pattern in src/scripts/ry_quotes.py; Ray Serve defaults were read from the same tag on 2026-10-24. The head was given a 2,000 MB cap, 500 MB more than the shared setup's 1,500 MB (see Processes). Process sizes are resident memory (RSS) read from /proc, which double-counts shared pages. The containers share a Docker bridge network and a volume mounted at /shared on all three. Ray runs in Linux containers because it refuses a multi-node cluster on macOS ("Multi-node Ray clusters are not supported on Windows and OSX").

Where ray.get sits decides whether tasks overlap measured

Tasks: remote functions and futures

@ray.remote registers a function with the cluster. f.remote(x) does not run f: it sends a task description (function, arguments, resource request, by default 1 CPU) to Ray and returns an ObjectRef at once. ray.get(ref) blocks until the result exists; ray.wait(refs) returns the ones that are ready. Because .remote() returns immediately, you submit many tasks before waiting for any: that is where the parallelism comes from.

From src/scripts/ry_core.py (section tasks), run as the driver on the head:

@ray.remote
def noop():
    return socket.gethostname()

# one at a time: submit, wait, repeat (100 times)
for _ in range(100):
    ray.get(noop.remote())
# 1,000 at once: submit all, then wait for all
hosts = ray.get([noop.remote() for _ in range(1000)])

measured One tiny task round trip (submit, schedule, run, return) took about 3 ms on this laptop; 1,000 tasks submitted together cost well under 1 ms each, because Ray pipelines them across the 4 worker processes and reuses a leased worker for many tasks. The 1,000 results came from both workers (the split is in the card). The {{Ownership paper|https://www.usenix.org/conference/nsdi21/presentation/cheng}} (NSDI 2021, the design Ray implements) reports about 1 ms per task on a real cluster published: the same order.

Predict: eight tasks that each sleep 0.5 s, on 4 free CPUs. How long does ray.get([nap.remote(i, 0.5) for i in range(8)]) take, and how long does [ray.get(nap.remote(i, 0.5)) for i in range(8)] take? Answer, then watch the replay.
About 1 s (two waves of 4 on 4 CPUs) against about 4 s: 4.0 s instead of 1.1 s here. In the second form each ray.get waits for its task before the next is even submitted, so the eight run one after another: the classic "ray.get in a loop" mistake.

The replay, in stretches of the recorded run

  1. Submit all eight. Every .remote() returns at once; four tasks start within 12 ms, one on each worker process (two per worker node).
  2. The first wave. Four run side by side for 0.5 s; the other four wait for a free CPU.
  3. The second wave. Each freed process takes the next task (two on w2 started 0.1 s late, at 0.61 s); ray.get returns all eight at 1.12 s: two waves of 4 on 4 CPUs.
  1. Task 0 runs alone. It runs on w1 for 0.5 s while three CPUs idle: the loop is blocked in ray.get and has not submitted task 1.
  2. Tasks 1 to 3, one at a time. Each is submitted only when the previous one returns, so they alternate between w1 and w2 and never overlap: 2.02 s so far.
  3. Tasks 4 to 7, the same. Done at 4.03 s, eight tasks times 0.5 s, on a cluster that could run four at once.

Each lane is one worker process (node and pid from the run); each bar is one task, placed where and when it really ran. Same eight tasks, same cluster.

Cost. A task is a scheduling decision, a message and a serialisation: milliseconds, not microseconds. Batch tiny work into fewer, larger tasks. The Ray docs' own example ({{anti-pattern: too fine-grained tasks|https://docs.ray.io/en/latest/ray-core/patterns/too-fine-grained-tasks.html}} published) runs 10,000 calls of a 10-microsecond function: about 0.17 s as plain calls, 1.6 s as one task each, 0.03 s as batches of 1,000 per task.

Check. ray status shows CPUs in use; ray timeline writes a Chrome trace with each task as a bar per worker, as drawn here. Serial bars that should overlap mean a ray.get between submissions.

Actors: a process with state

Tasks forget everything between calls; a model on a GPU, a replay buffer or a simulator must live in one process. @ray.remote on a class makes an actor class: Counter.remote() starts a dedicated worker process, runs __init__ there and returns an actor handle. Calls from one caller run one at a time in submission order (unless you ask for max_concurrency or async methods), so two calls never touch the state at once.

@ray.remote
class Counter:
    def __init__(self):
        self.n = 0
    def incr(self):
        self.n += 1
        return self.n

c = Counter.remote()                                  # a new process on some node
vals = ray.get([c.incr.remote() for _ in range(1000)])  # 1,000 calls queued, run in order

Fig. 2, step by step: three Counters from ry_core.py measured

  1. Counter.remote() starts a process. Ray placed a dedicated worker process for the actor on w1 in 0.16 s, ran __init__ there (n = 0) and returned a handle.
  2. Calls go straight to that process. 100 calls one at a time: a median round trip of 0.95 ms, against 2.96 ms for a task. After creation, an actor call round trip is faster than a task's: no scheduling decision, the caller talks straight to the actor's process.
  3. Queued calls run in order. 1,000 incr calls submitted at once took 0.23 s and returned 101 to 1100: the 1,000 queued calls came back in order (the counter starts above 1 because the 100 single calls ran first).
  4. The process dies, max_restarts=1. A second Counter, on w2 with n at 3, is killed. The call in flight fails with ActorUnavailableError; Ray starts a new process on w1 with a new pid, __init__ runs again, and the next call returns 1: the state is gone.
  5. The default, max_restarts=0. A third Counter, on w1, is killed and stays dead: every later call raises ActorDiedError.
