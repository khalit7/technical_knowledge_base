Ray Train: the worker group, checkpoints and failures

Distributed PyTorch needs N processes on the right machines, each told its rank, the world size and rank 0's address, a process group, and someone to restart from a checkpoint when one dies. torchrun does this per node and Slurm or Kubernetes supply machines; Ray Train does all of it inside a Ray cluster. TorchTrainer(train_loop, scaling_config=ScalingConfig(num_workers=4, ...), run_config=RunConfig(...)).fit():

  1. A controller actor (Ray Train v2, the default: RAY_TRAIN_V2_ENABLED defaults to true, python/ray/train/v2/_internal/constants.py line 149) requests a placement group of N bundles ("Requesting resources: {'CPU': 1, 'fake_gpu': 1} * 4").
  2. It starts N RayTrainWorker actors, sets MASTER_ADDR, MASTER_PORT, RANK, WORLD_SIZE, LOCAL_RANK and initialises the process group with TorchConfig(backend=...) ("Setting up process group for: env:// [rank=0, world_size=4]"). The root's Launch lab has the env dump.
  3. Every worker runs your train_loop. ray.train.report(metrics, checkpoint=Checkpoint.from_directory(d)) uploads the checkpoint to storage_path and queues a report; ray.train.get_checkpoint() returns the latest registered one after a restart.
  4. The controller polls the workers every DEFAULT_HEALTH_CHECK_INTERVAL_S = 2.0 s (line 35; controller.py line 436), collects reports and, on a failure, applies FailureConfig: a new worker group from the latest checkpoint, up to max_failures times (default 0: python/ray/air/config.py line 368), or raise.

Ray Serve: replicas are actors behind a proxy

Ray Serve runs online inference on a Ray cluster. A deployment is a class decorated with @serve.deployment; each copy of it is a replica, an actor. A controller actor ("a global actor unique to each Serve instance that manages the control plane") creates and replaces replicas; an HTTP proxy actor (by default "one HTTP proxy actor on the head node", port 8000) receives requests and routes them to replicas through a DeploymentHandle. Deployments call each other through handles, so a pipeline of models is one Python program ({{Ray Serve architecture|https://docs.ray.io/en/latest/serve/architecture.html}}).

A request queues at the proxy only when every replica is at max_ongoing_requests

from the source Defaults at tag ray-2.59.0 (python/ray/serve/_private/constants.py lines 283 and 284, python/ray/serve/config.py lines 695 and 704, read 2026-10-24): each replica takes up to max_ongoing_requests = 5 at once; with autoscaling on, the controller aims for target_ongoing_requests = 2 per replica between min_replicas and max_replicas (both 1 by default), adding replicas after upscale_delay_s = 30 s of load and removing them after downscale_delay_s = 600 s. "When replica Actors fail, the Controller Actor replaces them with new ones."

Batching and LLMs. @serve.batch gathers concurrent calls into one list (defaults max_batch_size = 10, batch_wait_timeout_s = 0.01, python/ray/serve/batching.py lines 803 and 804). For LLMs, Ray Serve LLM wraps an engine ("Engine-agnostic backends such as vLLM and SGLang") behind LLMConfig and build_openai_app, an OpenAI-compatible app, with prefill-decode disaggregation, multi-LoRA and prefix-aware routing ({{Ray Serve LLM|https://docs.ray.io/en/latest/serve/llm/index.html}}). What those mechanisms are is the serving topic's: {{vLLM|n:3c65c17b0d0d8113b976d8bcaf2c0722}} and {{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}} own batching, routing and autoscaling as ideas. not run here: a Serve app on this cluster would show actor placement already measured above; on Kubernetes it runs as a RayService.

Ray Tune, briefly

Tuner(trainable, param_space={...}, tune_config=TuneConfig(num_samples=N, scheduler=ASHAScheduler())) runs many trials, each an actor or a whole Ray Train run; a search algorithm proposes configurations (random, grid, Bayesian through Optuna and others) and a trial scheduler stops bad trials early (ASHA, successive halving) or mutates good ones (Population Based Training). Right for many small or medium trials on a shared cluster; one large pretraining run has nothing to tune in parallel ({{Ray Tune docs|https://docs.ray.io/en/latest/tune/index.html}}). not run here: a sweep would only repeat the task and actor mechanics above.

KubeRay: Ray on Kubernetes

In production a Ray cluster usually lives on Kubernetes through the KubeRay operator (v1.7.1, released 2026-09-21), which adds three custom resources:

  • RayCluster: a head pod and worker groups (pod template and replica range); with autoscaling, a Ray autoscaler sidecar asks for worker pods when tasks wait for resources and removes idle ones.
  • RayJob: a RayCluster plus an entrypoint (your driver), created for the job and deleted after. Kueue admits it as one workload, so team quotas and gang admission come from Kueue while Ray schedules inside.
  • RayService: a RayCluster running Ray Serve, with zero-downtime upgrades.

GPUs come from the Kubernetes device plugin as nvidia.com/gpu in the pod spec; Ray reads them as its GPU resource. Operators, device plugins and Kueue are taught on {{Kubernetes for ML|n:3c65c17b0d0d81cf9417de52108cfbce}}; {{KubeRay docs|https://docs.ray.io/en/latest/cluster/kubernetes/index.html}}. not run here: KubeRay plus a Ray cluster on the topic's kind cluster would add about 3 GB of containers to a laptop already near its budget; the root's Tool map lists KubeRay's status.
