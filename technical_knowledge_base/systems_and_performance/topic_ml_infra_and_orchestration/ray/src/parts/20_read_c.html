Objects and the object store

Tasks pass data to each other. Sending every result back through the submitting program would make it the bottleneck, so every node runs an object store (historically Plasma): shared memory, managed by the node's raylet, that every worker on the node can map. A result is stored where its task ran, and:

  • Small objects travel inline. A result under max_direct_call_object_size = 100 KB (src/ray/common/ray_config_def.h line 274) goes back to the owner inside the reply and never enters a store.
  • Big objects stay put until read. A reader on another node pulls a copy into its own store in 5 MB chunks (object_manager_default_chunk_size, line 432); that copy serves every reader on the node.
  • Reads are zero-copy, objects immutable. A NumPy array from the store is a read-only view of shared memory; a new value is a new object.
  • The store has a size. By default 30% of the node's memory (DEFAULT_OBJECT_STORE_MEMORY_PROPORTION, python/ray/_private/ray_constants.py line 110), capped at 200 GB (line 106); this cluster sets 80 MB per node with --object-store-memory.

The stepper: copies per node, read from ray.experimental.get_object_locations after each action measured

  1. Two tasks on w1 return a 1 KB and a 1 MB array. The 1 MB array is in w1's store, where its task ran. The 1 KB result has no store location: inline, 1,269 bytes serialised, held by the driver. Both tasks were pinned to w1 with NodeAffinitySchedulingStrategy.
  2. The driver calls ray.get on the 1 MB one. Now it has two copies, on w1 and on the head (the driver's node). The array the driver got is read-only (writeable False, owndata False), a view of shared memory: writing to it raised ValueError: assignment destination is read-only.
  3. The driver calls ray.put on a 4 MB array. ray.put stores the value in the store of the caller's node, the head, and the driver owns it.
  4. A task on w2 reads a 16 MB object made on w1. w2 had no copy, so its raylet pulled one from w1 in 5 MB chunks: 0.419 s end to end. Copies afterwards: w1 and w2.
  5. A second task on w2 reads it again. A local copy already existed: no transfer, 0.005 s.
  6. A task on w1 reads it. Local as well: 0.008 s. Copies stay on w1 and w2 until the owner frees them.

Cost. A cross-node read pays the network once per node, then is free on that node: here the first 16 MB read on the other worker took about 0.4 s and the second about 5 ms (a Docker bridge on a laptop, far below a real 100 to 400 Gb/s fabric; the ratio is the lesson). Passing a big array by value to many tasks stores a fresh copy per call; ray.put it once and pass the ref. (Both were timed; at 4 calls of 8 MB the difference was within this laptop's noise, so no number is quoted.) Check: ray memory lists every reference with its size, owner and why it is alive; --stats-only prints store usage and spill counters.

When the store fills: spilling

Past object_spilling_threshold = 0.8 of capacity (ray_config_def.h line 827), the raylet writes objects that are referenced but not in use to local disk through IO worker processes (max_io_workers = 4 per node) and restores them when read. Unreferenced objects are deleted; objects in use cannot be spilled. Only if spilling cannot keep up does a put fail with ObjectStoreFullError (spilling is on by default, automatic_object_spilling_enabled, line 804).

When it matters. Spilling turns an out-of-memory crash into slower progress: right for data pipelines, wrong for a latency-sensitive actor. Its hidden cost showed up later here: the spill and restore IO workers stayed alive (two of each, about 400 MB of resident memory on a 1.1 GB node, src/runs/debug/ps_w1_after_spill.txt), and the next Ray Train run on that node was killed by Ray's memory monitor (Mistakes). ray memory --stats-only printed "Spilled 64 MiB, 8 objects, avg write throughput 212 MiB/s" and "Restored 64 MiB, 8 objects, avg read throughput 1591 MiB/s"; spill throughput that low on a real node means a slow disk: point object_spilling_config (in ray start --system-config) at local NVMe ({{Ray docs: object spilling|https://docs.ray.io/en/latest/ray-core/objects/object-spilling.html}}).

Ownership: who is responsible for an object

Once refs are passed between tasks on many nodes, someone must know when an object can be freed, where its copies are and what to do if its node dies; a central table for every object would be a bottleneck at millions of tasks per second. Ray's answer, from the {{Ownership paper|https://www.usenix.org/conference/nsdi21/presentation/cheng}} (Wang et al., NSDI 2021): the worker that creates an ObjectRef, by .remote() or ray.put, is its owner, and keeps in its own memory the reference count (borrowers report back to it), the locations of the copies and the lineage, the task that produced it, kept while the object is referenced (lineage_pinning_enabled, line 208) up to max_lineage_bytes = 1 GB per owner (line 224). Fig. 1, at the top of the page, follows one task while the owner's table changes (steps 2, 5 and 7).

Consequences. The driver owns everything it submits. A task that calls ray.put or submits tasks inside its body owns those objects, and they die with that worker even if the data sat on a healthy node. ray.put objects have no lineage (no task made them), so they cannot be rebuilt. Small inline objects live in the owner's memory, so they survive the loss of the node that computed them. Failures, below, shows all four on a real node loss.
