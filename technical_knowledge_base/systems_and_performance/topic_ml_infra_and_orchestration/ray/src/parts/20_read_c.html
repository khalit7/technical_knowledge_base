Objects and the object store

The problem. Tasks pass data to each other: a batch of tokens, a model shard, a set of rollouts. Sending every result back through the program that submitted the task would make that program the bottleneck, and copying the same array to every reader wastes memory.

How it works. Every node runs an object store (historically called Plasma): a region of shared memory, managed by the node's raylet, that every worker process on the node can map. A task's result is stored where the task ran. Then:

  • Small objects travel inline. A result under max_direct_call_object_size = 100 KB (src/ray/common/ray_config_def.h line 274) is sent straight back to the owner inside the reply and never enters a shared store.
  • Big objects stay put until read. A reader on another node pulls a copy into its own node's store, in 5 MB chunks (object_manager_default_chunk_size, line 432); the copy then serves every reader on that node.
  • Reads are zero-copy. A NumPy array read from the store is a view of shared memory, so it is read-only: writing to it raises an error.
  • Objects are immutable. There is no update: a new value is a new object.
  • The store has a size. By default 30% of the node's memory (DEFAULT_OBJECT_STORE_MEMORY_PROPORTION, python/ray/_private/ray_constants.py line 110), capped at 200 GB (line 106); this cluster sets 80 MB per node with --object-store-memory.

What it costs. A cross-node read pays the network once per node, then is free on that node; here the first 16 MB read on the other worker took about 0.4 s and the second about 5 ms (a Docker bridge network on a laptop, so the first number is far below a real 100 to 400 Gb/s fabric; the ratio is the lesson). Passing a big array by value to many tasks makes Ray store a fresh copy for each call; ray.put it once and pass the ref. (Both forms were timed here; at 4 calls of 8 MB the difference was within this laptop's noise, so no number is quoted.)

How to check it. ray memory lists every object reference in the cluster with its size, owner and why it is still alive; ray memory --stats-only prints the store's usage and the spill counters used in the next section.

When the store fills: spilling

The problem. A pipeline produces objects faster than they are consumed, or a program keeps references to many large objects. Shared memory runs out.

How it works. When a node's store passes object_spilling_threshold = 0.8 of its capacity (ray_config_def.h line 827), the raylet writes objects that are still referenced but not in use to local disk through dedicated IO worker processes (max_io_workers = 4 per node), and reads them back (restores) when someone needs them. Objects nobody references are simply deleted; objects in use cannot be spilled. Only if spilling cannot keep up does a put fail with ObjectStoreFullError (with spilling on, the default, automatic_object_spilling_enabled, line 804).

14 objects of 8 MB into an 80 MB store, then read back measured

When it matters. Spilling turns an out-of-memory crash into slower progress, which is usually what you want for data pipelines and wrong for a latency-sensitive actor. Its hidden cost showed up later on this cluster: the spill and restore IO workers stayed alive after the test (two spill and two restore workers, about 400 MB of resident memory on a 1.1 GB node: src/runs/debug/ps_w1_after_spill.txt), and the next Ray Train run on the same node was killed by Ray's memory monitor (Mistakes below has the message).

How to check it. ray memory --stats-only after the run printed: "Spilled 64 MiB, 8 objects, avg write throughput 212 MiB/s" and "Restored 64 MiB, 8 objects, avg read throughput 1591 MiB/s". Spill throughput that low on a real node means the spill directory is on a slow disk; point it at local NVMe (object_spilling_config in ray start --system-config, {{Ray docs: object spilling|https://docs.ray.io/en/latest/ray-core/objects/object-spilling.html}}).

Ownership: who is responsible for an object

The problem. Once objects live on many nodes and refs are passed around between tasks, somebody has to know when an object can be deleted (no references left), where its copies are, and what to do if the node holding it dies. A central table for every object would be a bottleneck at millions of tasks per second.

How it works. Ray's answer, from the {{Ownership paper|https://www.usenix.org/conference/nsdi21/presentation/cheng}} (Wang et al., NSDI 2021): the worker that creates an ObjectRef, by calling .remote() or ray.put, is its owner. The owner keeps, in its own process memory:

  • the reference count: which workers hold the ref (borrowers report back to the owner), so the object is freed when the count reaches zero;
  • the locations of the object's copies;
  • the lineage: the task description that produced it, so it can be run again if every copy is lost (kept while the object is referenced, lineage_pinning_enabled, line 208, up to max_lineage_bytes = 1 GB per owner, line 224).

The consequences follow directly. The driver (your script) owns everything it submits directly. A task that calls ray.put or submits tasks inside its body owns those objects, and they die with that worker, even if the data sat on a healthy node. Objects made by ray.put have no lineage (no task made them), so they cannot be rebuilt. And small objects returned inline live in the owner's memory, so they survive the loss of the node that computed them.
