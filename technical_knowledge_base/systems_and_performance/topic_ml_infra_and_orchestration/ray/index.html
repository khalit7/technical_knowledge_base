Ray: tasks, actors, the object store and Ray Train

How Ray turns a Python program into a distributed one, and how it runs training: tasks, actors and objects, who owns what, the GCS, raylets and the object store, scheduling and placement groups, what survives a crash, Ray Data's streaming, Ray Train's worker group and checkpoints, and when Ray is the right layer. Ray in one screen

Ray is a library that turns ordinary Python functions and classes into work that runs on many machines. You add @ray.remote to a function, call it with .remote(), and get back a ticket for a result that does not exist yet; Ray finds a machine with a free CPU (or GPU), runs the function there and keeps the result in shared memory on that machine until someone asks for it. Training libraries (Ray Train), data pipelines (Ray Data), hyperparameter search (Ray Tune) and most open RL post-training stacks are built on those few primitives.

Where it sits: Slurm and Kubernetes hand out machines to jobs (the root page's Scheduling lab compares them). Ray runs inside machines you already have: a Ray cluster is a set of processes, usually started on Kubernetes pods (KubeRay) or inside a Slurm allocation, and Ray then schedules the tasks of one program across them. So Ray is not a rival to Slurm for "who gets the cluster"; it is the layer that makes one program distributed.

Four ideas carry the whole page. Each section below is one of them in detail.

1. Tasks

A task is one call of a remote function: stateless, runs anywhere a CPU is free, can be retried. Calling it returns at once with an ObjectRef (a future: a handle to a result that will exist).

2. Actors

An actor is an instance of a remote class: one long-lived process with state. Its method calls run one at a time, in order. A model replica, a parameter server, a rollout worker, a Ray Train worker: all actors.

3. Objects

Results and ray.put values are objects, immutable. Small ones travel inside messages; big ones live in each node's object store (shared memory), are copied to whichever node reads them, and spill to disk when the store fills.

4. Ownership

Every object has an owner: the worker that called .remote() or ray.put. The owner counts references, knows where copies live and remembers how to rebuild the object. When the owner dies, its objects are gone. This one rule explains most of Ray's failure behaviour.

Tasks: remote functions and futures

The problem. You have a function and a thousand inputs, and one machine is too slow. You want the calls to run on many cores of many machines without writing sockets, queues or a scheduler.

How it works. Decorating a function with @ray.remote registers it with the cluster. f.remote(x) does not run f: it sends a task description (function, arguments, resource request, by default 1 CPU) to Ray and immediately returns an ObjectRef, a future. ray.get(ref) blocks until the result exists and returns it; ray.wait(refs) returns the ones that are ready. Because .remote() returns at once, you can submit many tasks before waiting for any: that is where the parallelism comes from.

From src/scripts/ry_core.py (section tasks), run as the driver on the head:

@ray.remote
def noop():
    return socket.gethostname()

# one at a time: submit, wait, repeat (100 times)
for _ in range(100):
    ray.get(noop.remote())
# 1,000 at once: submit all, then wait for all
hosts = ray.get([noop.remote() for _ in range(1000)])

measured One tiny task round trip (submit, schedule, run, return) took about 3 ms on this laptop; 1,000 tasks submitted together cost well under 1 ms each because Ray pipelines them across the 4 worker processes and reuses a leased worker for many tasks. The 1,000 results came from both workers (the hosts split is shown). The Ownership paper (NSDI 2021, the design Ray implements) reports about 1 ms per task on a real cluster published; a laptop VM is slower but the same order.

Predict: eight tasks that each sleep 0.5 s, on a cluster with 4 free CPUs. How long does ray.get([nap.remote(i, 0.5) for i in range(8)]) take, and how long does [ray.get(nap.remote(i, 0.5)) for i in range(8)] take?
About 1 s (two waves of 4 on 4 CPUs) against about 4 s. In the second form each ray.get waits for its task before the next task is even submitted, so the eight run one after another: the classic "ray.get in a loop" mistake. What it costs. A task is a scheduling decision, a message to a worker, a serialisation of arguments and results: milliseconds, not microseconds. Tasks of a few milliseconds of work spend most of their life in overhead, so batch tiny work into fewer, larger tasks. The Ray docs' own example (anti-pattern: too fine-grained tasks published) runs 10,000 calls of a 10-microsecond function: about 0.17 s as plain calls, 1.6 s as one task each, 0.03 s as batches of 1,000 per task.

How to check it. ray status shows how many CPUs are in use right now; the dashboard's timeline (ray timeline writes a Chrome trace) shows each task as a bar per worker, exactly as drawn above. If the bars are serial when they should overlap, look for a ray.get between submissions.

Actors: a process with state

The problem. Tasks forget everything between calls. A model loaded on a GPU, a replay buffer, an environment simulator, a counter of tokens processed: these must live in one process and be called many times.

How it works. @ray.remote on a class makes it an actor class. Counter.remote() starts a dedicated worker process somewhere in the cluster, runs __init__ there and returns an actor handle. c.incr.remote() sends a method call to that one process; calls from one caller run one at a time in submission order (unless you ask for concurrency with max_concurrency or async methods), so the state is never touched by two calls at once.

@ray.remote
class Counter:
    def __init__(self):
        self.n = 0
    def incr(self):
        self.n += 1
        return self.n

c = Counter.remote()                                  # a new process on some node
vals = ray.get([c.incr.remote() for _ in range(1000)])  # 1,000 calls queued, run in order

measured Creating the actor (start a process, run __init__) took a fraction of a second; after that a call round trip was faster than a task's, because no scheduling decision is needed: the caller talks straight to the actor's process. 1,000 queued calls came back in order (first value, last value and the ordered check are from the run; the counter starts above 1 because 100 single calls ran first).

When it matters. Every training worker in Ray Train is an actor (RayTrainWorker in the logs), and so is every vLLM engine in an RL post-training stack. Choosing "task or actor" is choosing whether state, placement and order matter. The actor's price is that its state dies with its process, which is the fault-tolerance section's subject.

Objects and the object store

The problem. Tasks pass data to each other: a batch of tokens, a model shard, a set of rollouts. Sending every result back through the program that submitted the task would make that program the bottleneck, and copying the same array to every reader wastes memory.

How it works. Every node runs an object store (historically called Plasma): a region of shared memory, managed by the node's raylet, that every worker process on the node can map. A task's result is stored where the task ran. Then:

  • Small objects travel inline. A result under max_direct_call_object_size = 100 KB (src/ray/common/ray_config_def.h line 274) is sent straight back to the owner inside the reply and never enters a shared store.
  • Big objects stay put until read. A reader on another node pulls a copy into its own node's store, in 5 MB chunks (object_manager_default_chunk_size, line 432); the copy then serves every reader on that node.
  • Reads are zero-copy. A NumPy array read from the store is a view of shared memory, so it is read-only: writing to it raises an error.
  • Objects are immutable. There is no update: a new value is a new object.
  • The store has a size. By default 30% of the node's memory (DEFAULT_OBJECT_STORE_MEMORY_PROPORTION, python/ray/_private/ray_constants.py line 110), capped at 200 GB (line 106); this cluster sets 80 MB per node with --object-store-memory.

Where each object lived, read from ray.experimental.get_object_locations measured

What it costs. A cross-node read pays the network once per node, then is free on that node; here the first 16 MB read on the other worker took about 0.4 s and the second about 5 ms (a Docker bridge network on a laptop, so the first number is far below a real 100 to 400 Gb/s fabric; the ratio is the lesson). Passing a big array by value to many tasks makes Ray store a fresh copy for each call; ray.put it once and pass the ref. (Both forms were timed here; at 4 calls of 8 MB the difference was within this laptop's noise, so no number is quoted.)

How to check it. ray memory lists every object reference in the cluster with its size, owner and why it is still alive; ray memory --stats-only prints the store's usage and the spill counters used in the next section.

When the store fills: spilling

The problem. A pipeline produces objects faster than they are consumed, or a program keeps references to many large objects. Shared memory runs out.

How it works. When a node's store passes object_spilling_threshold = 0.8 of its capacity (ray_config_def.h line 827), the raylet writes objects that are still referenced but not in use to local disk through dedicated IO worker processes (max_io_workers = 4 per node), and reads them back (restores) when someone needs them. Objects nobody references are simply deleted; objects in use cannot be spilled. Only if spilling cannot keep up does a put fail with ObjectStoreFullError (with spilling on, the default, automatic_object_spilling_enabled, line 804).

14 objects of 8 MB into an 80 MB store, then read back measured

When it matters. Spilling turns an out-of-memory crash into slower progress, which is usually what you want for data pipelines and wrong for a latency-sensitive actor. Its hidden cost showed up later on this cluster: the spill and restore IO workers stayed alive after the test (two spill and two restore workers, about 400 MB of resident memory on a 1.1 GB node: src/runs/debug/ps_w1_after_spill.txt), and the next Ray Train run on the same node was killed by Ray's memory monitor (Mistakes below has the message).

How to check it. ray memory --stats-only after the run printed: "Spilled 64 MiB, 8 objects, avg write throughput 212 MiB/s" and "Restored 64 MiB, 8 objects, avg read throughput 1591 MiB/s". Spill throughput that low on a real node means the spill directory is on a slow disk; point it at local NVMe (object_spilling_config in ray start --system-config, Ray docs: object spilling).

Ownership: who is responsible for an object

The problem. Once objects live on many nodes and refs are passed around between tasks, somebody has to know when an object can be deleted (no references left), where its copies are, and what to do if the node holding it dies. A central table for every object would be a bottleneck at millions of tasks per second.

How it works. Ray's answer, from the Ownership paper (Wang et al., NSDI 2021): the worker that creates an ObjectRef, by calling .remote() or ray.put, is its owner. The owner keeps, in its own process memory:

  • the reference count: which workers hold the ref (borrowers report back to the owner), so the object is freed when the count reaches zero;
  • the locations of the object's copies;
  • the lineage: the task description that produced it, so it can be run again if every copy is lost (kept while the object is referenced, lineage_pinning_enabled, line 208, up to max_lineage_bytes = 1 GB per owner, line 224).

The consequences follow directly. The driver (your script) owns everything it submits directly. A task that calls ray.put or submits tasks inside its body owns those objects, and they die with that worker, even if the data sat on a healthy node. Objects made by ray.put have no lineage (no task made them), so they cannot be rebuilt. And small objects returned inline live in the owner's memory, so they survive the loss of the node that computed them.

Architecture: the GCS, raylets, workers and the driver

Four kinds of process make a Ray cluster. Knowing which one holds what is how you read its logs and its failures.

GCS (head node only)

The Global Control Service (older papers: Global Control Store), process gcs_server. Holds cluster metadata: the node table, the actor table (where each actor lives, its restart count), placement groups, jobs, a key-value store. It health-checks every raylet and declares nodes dead. It does not hold objects or schedule ordinary tasks.

Raylet (every node)

The per-node daemon: a scheduler that grants worker leases for this node's resources (or points the request at another node), the object store and object manager that move objects between nodes, and the worker pool that starts and reuses Python worker processes.

Workers

Python processes that run tasks and actors. Each embeds a core worker library, which is where ownership lives: a worker that submits tasks keeps their refs, counts and lineage itself.

Driver

Your script after ray.init(): a worker that owns everything it submits. Here it runs on the head; for Ray Jobs it also runs on the head, so the head needs memory for it.

The life of one task, in the order the Ownership paper and Ray's architecture whitepaper give it: the owner asks its local raylet for a worker lease that fits the task's resources; the raylet grants one of its own workers or replies "try node X" (spillback); the owner sends the task straight to the leased worker; the worker fetches any object arguments, runs the function and stores the result (inline back to the owner when small, in its node's store when large); the owner records the result's location and the lease is reused for the next task with the same shape or returned. The GCS is not on this path, which is why ordinary tasks keep running while the GCS is briefly slow. The Ownership lab animates these steps.

What the head's memory is made of measured

When it matters. The head is a single point of failure and a memory hot spot. On this cluster the root's Failure lab saw the head at 95% of its 1.5 GB cap during Ray Train runs, and Ray's memory monitor killed 13 non-training worker processes there. The fix on a real cluster is a head with no training on it (--num-cpus 0, as here), enough memory for the driver, the dashboard and Ray Train's controller, and GCS fault tolerance (below).

Found here: raising a container's memory cap does not raise Ray's kill threshold
Ray's memory monitor kills workers when a node's memory use passes memory_usage_threshold = 0.95 (ray_config_def.h line 79), checked every 250 ms (line 83). The threshold in bytes is computed once, when the raylet starts (src/ray/common/monitors/threshold_memory_monitor.cc line 33 stores it; line 126 compares against it). After docker update --memory 2000m on the running head, a Ray Train run still died with "Memory usage 1539858432B exceeded threshold of 1494220800B (71.2% of 2097152000B limit)": 1,494,220,800 is 95% of the old 1,500 MiB limit. Raise memory before ray start, or restart Ray after resizing. (This page then ran its Ray head with 2,000 MB from the start, 500 MB more than the shared setup, on 2026-10-16.)

Scheduling: resources, policies and placement groups

Resources are counters. A node advertises numbers: CPU, GPU, memory, and any custom name (fake_gpu here). A task or actor asks for amounts (num_cpus=1, num_gpus=0.5, resources={"fake_gpu": 1}), and Ray only runs it where the amounts are free. Ray does not stop a task from using more than it asked for: the numbers are for placement, not enforcement (unlike Slurm with cgroups). On a real GPU node Ray sets CUDA_VISIBLE_DEVICES for the GPUs it assigned; with a custom resource it sets nothing.

Policies. The default hybrid policy prefers the local node until its critical resource is past scheduler_spread_threshold = 0.5 utilisation (ray_config_def.h line 252), then picks among the least-loaded nodes, choosing randomly among the top few (src/ray/raylet/scheduling/policy/hybrid_scheduling_policy.h lines 29 to 48: "Scheduling a task on a new node incurs a cold start penalty ... Past a certain utilization threshold, a big noisy neighbor problem occurs"). "SPREAD" spreads over nodes; NodeAffinitySchedulingStrategy(node_id, soft) pins to one node (soft: fall back elsewhere if it is gone).

Placement groups reserve several bundles of resources at once, all or nothing, so a multi-worker job never starts with half its GPUs: Ray's gang scheduling. The GCS reserves them with a two-phase commit across the raylets ("The first phase of 2PC ... prepare resources", "The second phase of 2PC", src/ray/gcs/gcs_placement_group_scheduler.h lines 114 and 116). Strategies: PACK (as few nodes as possible, may spread), SPREAD, STRICT_PACK (one node or wait), STRICT_SPREAD (one bundle per node or wait). Ray Train puts its worker group in one placement group (ScalingConfig(placement_strategy="PACK") by default).

Measured in the root's Scheduling lab (not repeated here)
The Scheduling lab ran every strategy on this cluster with 4 one-GPU bundles: PACK put 2 on each worker (a node only has 2), SPREAD alternated, STRICT_PACK and STRICT_SPREAD stayed PENDING forever (no node has 4; only 2 worker nodes), and the autoscaler printed "Error: No available node types can fulfill resource request ... {'CPU': 4.0, 'fake_gpu': 4.0}". A second group that needed 3 of 4 GPUs waited holding nothing, then got all 3 at once 0.68 s after the first was removed. Its recorded output is src/sched/runs/ray/ray_pg.jsonl in the root's folder.

Fault tolerance: what survives a crash

Ray separates three kinds of failure and handles each differently. Every row below was run on this cluster (ry_core.py fault and lineage); the error names and messages are Ray's own.

What failedDefault behaviour (source)What happened here

Tasks are retried up to max_retries = 3 times when the worker process or its node dies (DEFAULT_TASK_MAX_RETRIES = 3, ray_constants.py line 633; ray_option_utils.py line 182). An exception raised by your code is not retried unless you set retry_exceptions=True (line 207): Ray assumes a crash is the machine's fault and an exception is yours. Retries re-run the function, so tasks should be idempotent (safe to run twice).

Actors are not restarted by default (max_restarts = 0, line 254). With max_restarts=N Ray starts a new process and runs __init__ again: the state is gone (the counter went from 3 back to 1 here) unless the actor saved it somewhere and reloads it. Calls in flight when it died fail unless max_task_retries is set (default 0, line 255).

Objects lost with a node are rebuilt from lineage by their owner, by re-running the task that made them (the GCS log said "Attempting to recover 2 lost objects by resubmitting their tasks"), if that task is retryable. Objects whose owner died are lost for good (OwnerDiedError), and so are ray.put objects whose only copy was on the lost node.

Nodes are declared dead by the GCS after health_check_failure_threshold = 5 failed checks, sent every health_check_period_ms = 3,000 ms with a health_check_timeout_ms = 10,000 ms timeout (ray_config_def.h lines 1060 to 1064). Here the first check failed 11.7 s after the node was killed (a 10 s timeout: the container's address no longer answered) and the node was dead at 29.9 s; the root's Failure lab measured 30.0 s on its own run.

The head is the exception: without GCS fault tolerance, losing the head loses the cluster (every actor and object). With GCS fault tolerance the GCS writes its tables to an external Redis; when it restarts, raylets and workers reconnect (they wait up to gcs_rpc_server_reconnect_timeout_s = 60 s, line 549) and running tasks and actors continue (Ray docs: GCS fault tolerance; on KubeRay 1.3.0 and later, a gcsFaultToleranceOptions field in the RayCluster spec pointing at Redis: KubeRay GCS fault tolerance). not run here: it needs a Redis and a head restart, which teaches little on a toy cluster beyond what the docs state.

Predict: a task running on node B calls ray.put(big_array) and returns the ref to the driver. Node B dies. The array's only copy was on node C, which is healthy. Can the driver still ray.get it?
No. The owner is the worker on B that called ray.put; its reference count and location table died with it, and Ray's docs are explicit: "Currently, Ray does not support recovery from owner failure", and "Ray will clean up any remaining copies of the object's value to prevent a memory leak" (object fault tolerance). Ray raises OwnerDiedError ("The object's owner has exited. This is the Python worker that first created the ObjectRef via .remote() or ray.put()"). It was measured here with the copy on the killed node itself (object C in the Ownership lab). Rule: have the driver (or a long-lived actor) own anything you cannot afford to lose; return values from tasks instead of ray.put inside them.

Ray Data: streaming blocks through the cluster

The problem. Training reads and transforms data (decode, tokenize, augment, pack) while GPUs wait. Doing it inside each training process ties preprocessing to the trainer's CPUs; doing it all up front needs storage for the whole result and a long wait before the first step.

How it works. A Ray Data Dataset is a lazy plan: read_* or from_items, then transformations such as map_batches(fn), then a consumer such as iter_batches or a Ray Train worker. Data moves as blocks (chunks of rows in Arrow, pandas or NumPy form) stored in the object store; Ray Data "attempts to bound block sizes between 1 MiB and 128 MiB" (Ray Data internals; DEFAULT_TARGET_MAX_BLOCK_SIZE, python/ray/data/context.py line 76). When the consumer starts pulling, the streaming executor runs every operator at once: each operator "takes in and outputs a stream of blocks", each block is processed by a Ray task (or an actor pool for stateful work such as a model), and the first batch arrives as soon as the first block has passed every stage. Two refinements:

  • Operator fusion. Consecutive map operators with compatible remote arguments are merged into one task per block, so a block goes through both functions without being written to the object store in between (are_remote_args_compatible, python/ray/data/_internal/logical/rules/operator_fusion.py lines 886 to 899: different num_cpus means no fusion).
  • Backpressure. "To limit object store use, Ray Data applies backpressure and stops launching tasks once enough data is buffered" (same docs page), so a slow consumer does not make the producers fill memory.

From src/scripts/ry_data.py: the running example's text in 24 chunks, two pretend preprocessing stages (0.3 s and 0.2 s of work per block), a pretend training loop (0.1 s per batch of 512 samples):

ds = ray.data.from_items(items, override_num_blocks=24)
ds = ds.map_batches(encode, batch_size=1)                 # characters to ids
# staged: ds = ds.materialize()   (finish stage 1 everywhere first)
ds = ds.map_batches(window, batch_size=1)                 # pipelined: num_cpus=0.5 stops fusion
for b in ds.iter_batches(batch_size=512, batch_format="numpy"):
    time.sleep(0.1)                                       # a training step

measured Same 24 blocks, same 17,424 samples in 35 batches, three plans. Fused streaming delivered the first batch soonest; staging (bulk-synchronous) delayed it until every block had passed stage 1 and finished last. Unfusing the two stages added a task and an object-store hop per block and cost time here; on a real pipeline you unfuse on purpose when the stages need different resources (CPU decode, GPU model). The Ray Data pipeline tab draws every block of all three runs on the workers' timelines.

Published claim. The Ray Data paper (Luan et al., The Streaming Batch Model for Efficient and Fault-Tolerant Heterogeneous Execution, first posted 2025-01-16; authors from UC Berkeley and Anyscale, Ray's company) reports throughput gains of "2.5-12x" on heterogeneous batch inference pipelines over batch and stream processing systems, and 31% higher training throughput for Stable Diffusion than single-node data loaders published, authors' own measurements. Not reproduced here.

When it matters. Ray Data earns its place when preprocessing is heavy or needs a different machine type than training (CPU-only nodes decoding video for GPU trainers), or for offline batch inference. For a text pretraining run whose data is already tokenized into shards, a plain loader is simpler; the data-curation topic's storage and loading page covers formats and loaders.

Ray Train: the worker group, checkpoints and failures

The problem. Distributed PyTorch needs N processes on the right machines, each told its rank, the world size and the address of rank 0, a process group initialised, and someone to notice when one dies and start again from a checkpoint. torchrun does this per node; Slurm or Kubernetes supply the machines. Ray Train does all of it inside a Ray cluster.

How it works. TorchTrainer(train_loop, scaling_config=ScalingConfig(num_workers=4, resources_per_worker=...), run_config=RunConfig(...)), then trainer.fit():

  1. A controller actor (Ray Train v2, the default since RAY_TRAIN_V2_ENABLED defaults to true, python/ray/train/v2/_internal/constants.py line 149) requests a placement group of N bundles ("Requesting resources: {'CPU': 1, 'fake_gpu': 1} * 4" in the log).
  2. It starts N RayTrainWorker actors in the bundles, picks rank 0's address, sets MASTER_ADDR, MASTER_PORT, RANK, WORLD_SIZE, LOCAL_RANK in each, and initialises the process group with TorchConfig(backend=...) ("Setting up process group for: env:// [rank=0, world_size=4]"). The Launch lab's env dump of these variables is on the root page.
  3. Every worker runs your train_loop. Inside it, ray.train.report(metrics, checkpoint=Checkpoint.from_directory(d)) uploads the checkpoint to storage_path and queues a report; ray.train.get_checkpoint() returns the latest registered one after a restart.
  4. The controller polls the workers (every DEFAULT_HEALTH_CHECK_INTERVAL_S = 2.0 s, line 35; controller.py line 436), collects reports and, when a worker has failed, applies the FailureConfig: retry by building a new worker group from the latest checkpoint, up to max_failures times (default 0: python/ray/air/config.py line 368), or raise.

From step 50, in all three runs made here, although every worker had called report for step 100 and rank 0 had written the step-100 checkpoint to storage half a second before the crash. A report reaches the controller only when the controller polls the workers, and it registers a checkpoint only once it holds that report from every worker (report_handler.py lines 40 and 63: "Wait for all workers to report training results", if not all(self._training_report_queues): return). Rank 3's step-100 report was still inside its process when it died, so step 100 was never registered: 70 steps redone instead of 20, and the step-100 files stayed in storage as an orphan directory that num_to_keep=2 did not delete (it was still there at the end of every run). Replayed step by step in the Train failure replay.

measured Three repeats of the same crash. The restarted group recomputed steps 50 to 120 and finished; its loss matched the uninterrupted running example at most logged steps and differed by one float32 rounding step (2.4e-7) at steps 70, 180 and 200, the DDP bucket-rebuild effect the root's Failure lab explains (a restarted process steps once with the initial bucket layout).

What it costs. Launch: the root's Launch lab measured a median 10.0 s from submit to first step for this job on Ray Train, against 7.5 s on Slurm and 5.8 s on Kubernetes (5 runs each, image preloaded, laptop), most of it starting worker processes and importing torch. Recovery: about 6 to 7 s from crash to the new group's first step here (process start, rendezvous, checkpoint load), plus the steps redone. Memory: the controller (about 0.21 GB) and the driver (about 0.23 GB) live on the head (setup measurements).

Measured in the root's Failure lab (not repeated here)
With train.py writing its own checkpoints (no Ray Train checkpoint API), the Failure lab ran: max_failures=0, a rank crash: fit() raised WorkerGroupError after 1.27 s; max_failures=2: a new worker group resumed from step 100 10.15 s after the crash; a killed worker node: Ray waited for 4 fake_gpu with only 2 alive and resumed only when the node came back (93.6 s), because Ray Train does not shrink the group unless you configure elastic scaling. The Launch lab found that the worker-group start timeout (60 s, RAY_TRAIN_WORKER_GROUP_START_TIMEOUT_S) is retried forever when capacity never comes.

How to check it. The driver log shows the controller's decisions ("[FailurePolicy] RETRY ... Error count: 1 (max allowed: 1)", "Started training worker group of size 4" with every rank's node and pid); the storage path shows which checkpoints exist; result.checkpoint and result.best_checkpoints are what the controller registered. If the newest checkpoint on disk is not the one get_checkpoint() returned, you are looking at this race.

Ray Tune, briefly

Ray Tune runs many training trials with different hyperparameters: Tuner(trainable, param_space={...}, tune_config=TuneConfig(num_samples=N, scheduler=ASHAScheduler())). Each trial is a Ray actor (or a whole Ray Train run); a search algorithm proposes configurations (random, grid, Bayesian through Optuna and others) and a trial scheduler stops bad trials early (ASHA, successive halving) or mutates good ones (Population Based Training). It is the right tool for many small or medium trials on a shared cluster; for one large pretraining run there is nothing to tune in parallel. Ray Tune docs. not run here: a sweep of the running example would only repeat the task and actor mechanics above, and the evaluation of hyperparameter search belongs to the training topic.

KubeRay: Ray on Kubernetes

In production a Ray cluster usually lives on Kubernetes through the KubeRay operator (v1.7.1, released 2026-09-21). It adds three custom resources:

  • RayCluster: a head pod and worker groups (each a pod template and a replica range); the operator creates the pods and, with autoscaling on, a Ray autoscaler sidecar asks for more worker pods when tasks wait for resources and removes idle ones.
  • RayJob: a RayCluster plus an entrypoint (your driver script); the cluster is created for the job and deleted after it. This is what Kueue admits as one workload, so team quotas and gang admission come from Kueue while Ray schedules inside.
  • RayService: a RayCluster running Ray Serve, with zero-downtime upgrades.

GCS fault tolerance on KubeRay needs a Redis (the gcsFaultToleranceOptions field, KubeRay 1.3.0 and later). GPUs come from the Kubernetes device plugin as nvidia.com/gpu in the pod spec; Ray reads them as its GPU resource. The sibling page "Kubernetes for ML: scheduling, device plugins, gang scheduling and operators" covers operators, device plugins and Kueue. KubeRay docs. not run here: KubeRay plus a Ray cluster on the topic's kind cluster would add about 3 GB of containers to a laptop already near its budget; the root's Tool map lists KubeRay's status.

Interview questions

Task or actor: how do you choose?
Task for stateless, retryable work that can run anywhere (map over data). Actor when state must persist between calls (a loaded model, a simulator, a buffer) or calls must be ordered. Actors hold their placement for their lifetime and lose state on restart.
What is an object's owner, and what happens when it dies?
The worker that created the ref (.remote() or ray.put). It holds the reference count, the copies' locations and the lineage. When it dies the object is lost (OwnerDiedError) even if copies exist; Ray cleans up the copies.
A node dies. Which objects come back?
Task outputs whose owner is alive and whose task is retryable: the owner re-runs the task (lineage reconstruction; measured here 31 s after the kill, most of it the 30 s needed to declare the node dead). Not: ray.put objects with no other copy, outputs of max_retries=0 tasks, objects owned by workers on the dead node. Small inline objects were never on that node.
How long until Ray notices a dead node, and what sets it?
The GCS health checks: period 3 s, timeout 10 s, 5 failures (ray_config_def.h lines 1060 to 1064). About 30 s here. A crashed worker process is noticed in under a second by its raylet.
Why is a placement group needed for distributed training?
All N workers must start together, or none: a partial group holds GPUs and waits forever (the gang problem). A placement group reserves all bundles atomically (two-phase commit in the GCS). PACK minimises nodes; STRICT_PACK insists on one node; SPREAD and STRICT_SPREAD spread for fault isolation.
How does Ray Train set up torch.distributed?
The controller creates a placement group, starts one worker actor per rank, picks rank 0's address and a free port, sets MASTER_ADDR, MASTER_PORT, RANK, WORLD_SIZE, LOCAL_RANK, and calls init_process_group with the TorchConfig backend (env://) before your loop runs. No torchrun.
A Ray Train job restarted from an older checkpoint than the newest one on disk. Why?
The controller registers a checkpoint only after collecting that report from every worker, by polling (every 2 s). A worker that dies after report but before the poll takes its report with it, so the latest checkpoint is never registered (measured: restart from 50 with 100 on disk, 3 of 3 runs). Shorter gap between checkpoints, or accept up to one interval more of lost work.
The head node keeps running out of memory. What lives there?
The GCS, the dashboard and its modules (most of the head's memory here), the autoscaler monitor, the driver, Ray Train's controller and anything scheduled on it. Give the head --num-cpus 0 so no tasks land there, enough memory for the driver and controller, and GCS fault tolerance so its loss is survivable.
Design: an RL post-training system for a 70B policy on 256 GPUs with vLLM rollouts.
Kubernetes with KubeRay (a RayJob per experiment) and Kueue for team quotas and gang admission of the whole RayCluster. Inside: one driver (single controller) running the loop; actor groups for the trainer (FSDP or Megatron workers, one placement group, STRICT_PACK per node for NVLink), vLLM engines (actors with their own placement groups), reward and reference models. Decide colocation: shared GPUs (hybrid engine, swap weights) saves GPUs, separate pools allow asynchronous rollouts. Move weights trainer to engines over NCCL, not the object store (too big); move prompts, rollouts and rewards through the object store (small). Checkpoint the trainer to object storage with DCP at an interval set by the failure rate; restart engines freely (stateless); GCS fault tolerance with Redis; watch the head's memory. Failure plan: a lost trainer node restarts the trainer group from checkpoint (Ray Train or your own), a lost engine is replaced and its prompts re-queued.
Design: a pipeline that decodes video on CPUs and embeds it on GPUs, feeding training.
Ray Data: read on CPU nodes, map_batches(decode) as CPU tasks, map_batches(Embedder, num_gpus=1, concurrency=N) as an actor pool on GPU nodes (different resources, so not fused), consumed by Ray Train workers with iter_torch_batches. Streaming keeps GPUs busy from the first blocks; backpressure bounds memory; size blocks (1 to 128 MiB) and pools so neither stage starves; spill to local NVMe.
