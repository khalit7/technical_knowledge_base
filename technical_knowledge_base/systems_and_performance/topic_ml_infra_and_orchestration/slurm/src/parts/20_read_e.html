5. Partitions, QOS and associations: who may use what

The problem. A shared cluster needs rules beyond "first come, first served": one team may not take every GPU, debug jobs must start fast, a huge job may run only at night. Slurm has three places to put rules, and a pending job's reason names the one holding it.

Partition

A named set of nodes (a queue) with its own rules: MaxTime, MaxNodes, default time, who may submit, PriorityJobFactor (a priority bonus) and PriorityTier (an order between partitions, used for preemption). Partitions may overlap: here batch, urgent and this page's sllow all cover c[1-3]. In slurm.conf.

Association

A (cluster, account, user) triple in the accounting database: alice in teama, bob in teamb. Accounts form a tree (root, teama, teamb), each with fairshare shares and optional limits such as GrpTRES=gres/gpu=64 (the whole team at once) or MaxJobs. In slurmdbd, set with sacctmgr.

QOS

"Quality of service": a named bundle of a priority, limits (MaxTRESPerUser, MaxWall, GrpTRES) and preemption rules that a job selects with --qos. Typical: debug (high priority, 1 node, 30 minutes), normal, scavenger (lowest priority, preemptible). In slurmdbd.

When several define the same limit, the first one found wins, in this order: partition QOS, job QOS, user association, account associations up the tree, root, partition ({{resource limits|https://slurm.schedmd.com/resource_limits.html}}). And none of it applies unless AccountingStorageEnforce includes limits and qos: the default is none, and this lab cluster runs with none, so for this page's runs it was switched on, with two QOS and one limit measured:

$ sacctmgr -i add qos sl-small Priority=20 MaxTRESPerUser=gres/gpu=4
$ sacctmgr -i modify user where name=alice,bob,carol set qos+=sl-high,sl-small
$ sacctmgr -i modify user where name=carol set GrpTRES=gres/gpu=2

6. The scheduler: a main loop and a backfill loop


The problem. Thousands of pending jobs, a cluster that changes every second. Testing every job against every node on every change would be too slow, and starting jobs in strict priority order wastes nodes that a big job at the head cannot use yet. Slurm runs two loops inside the controller.




The main loop (fast, strict)
Runs on every event (a job submitted or ending, a node returning) and every sched_interval (60 s by default, ). It walks the pending jobs in priority order and starts each one that fits now. On an event it tests at most default_queue_depth jobs (100 by default). And the moment one job of a partition cannot start, it starts nothing else in that partition or on its nodes in that pass: strict priority order.


The backfill loop (slower, planning)
Every bf_interval (30 s by default, 2 s here) it builds a timeline from every running job's time limit, gives each waiting job, in priority order, the earliest start where it fits (a reservation), and starts any lower-priority job that fits in a gap and ends before the reservations it would cross. Slurm's version reserves for every job it tests (conservative) and reserves whole nodes.




Source: the main loop stops a partition at its first blocked job


and on an event it tests a limited depth


That rule is where the two most common reasons come from: the first blocked job of a partition shows Resources, and every job behind it shows Priority ("a job ahead of me is waiting"). Backfill is the only way a job jumps that line, and it needs your time limit to do it. The root's {{Scheduling lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} runs the same eight-job queue under FIFO and backfill on this cluster and shows where Slurm's whole-node reservations depart from the textbook; this page does not repeat it.

On a large cluster backfill cycles take seconds; when Backfill exit shows Hit bf_max_job_test or Timeout (bf_max_time), jobs deep in the queue are never considered for backfill at all; the knobs are bf_max_job_test, bf_max_job_user (a cap per user so one user's thousand jobs do not fill the test budget), bf_continue and bf_max_time.


The idle-cluster run shows the two loops racing: job 125 was submitted at 05:42:05.390 and started by backfill 444 ms later, not by the main loop, because this cluster's sched_min_interval=500000 (0.5 s) keeps the main loop from running more than twice a second and the backfill cycle came first. Either loop may start any job; the log line says which (sched: Allocate for the main loop, sched/backfill: _start_job for backfill).
