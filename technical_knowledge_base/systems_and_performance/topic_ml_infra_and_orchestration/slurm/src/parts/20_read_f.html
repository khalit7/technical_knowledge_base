8. Preemption and requeue: taking nodes back

The cluster is full of long training jobs and an urgent job arrives (an evaluation before a deadline, a team whose guaranteed share others are using). Preemption lets the scheduler stop running jobs to make room; the same requeue machinery serves time limits.

SettingChoices
PreemptType: who may preempt whompreempt/partition_prio: a job in a partition with a strictly higher PriorityTier preempts jobs of lower tiers (this cluster: urgent tier 10 over batch tier 1). preempt/qos: each QOS lists the QOS it may preempt (sacctmgr modify qos high set preempt=scavenger). preempt/none.
PreemptMode: what happens to the victimCANCEL (killed), REQUEUE (killed and put back in the queue, needs --requeue; otherwise cancelled), SUSPEND (paused in memory; needs GANG at cluster level, and keeps GPU memory occupied, so it is rarely practical for GPU jobs), GANG (time slicing on the same resources), OFF ({{preemption docs|https://slurm.schedmd.com/preempt.html}}).
GraceTimethe victim gets SIGCONT and SIGTERM at once and SIGKILL only after GraceTime (default 0): the window to write a checkpoint.

For training the usual choice is REQUEUE with a GraceTime long enough to checkpoint, with low-priority work in a preemptible QOS or partition. The root's {{Scheduling lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} preempted bob's 12-GPU batch job with a 4-GPU urgent job on this cluster: preempted JobId=39 has been requeued to reclaim resources for JobId=40, the urgent job was allocated 0.6 s after submission, and the victim could not restart for 121 s. GPU-hours lost per preemption are the time since the last checkpoint times the GPUs, the trade-off the root's Failure lab turns into a checkpoint interval.

Checkpoint before the limit, then two minutes of dead time: job 128 measured

--time=1 --signal=B:USR1@25 --requeue: Slurm should signal the batch shell 25 s before the 60 s limit; the script traps SIGUSR1, saves, and runs scontrol requeue; the next start resumes. The signal came 12 s after the start, not 35 s; the requeued job became eligible at 05:44:53, 121 s after the requeue, and finished from its checkpoint. 16 Oct 2026, sacct -D.

Two lessons for a checkpoint budget. The signal "may be sent up to 60 seconds earlier than specified" because of how Slurm resolves events ({{sbatch --signal|https://slurm.schedmd.com/sbatch.html}}), so ask for more warning than a save takes, plus a minute. And a requeued job's begin time is pushed past the job credential's lifetime (120 s by default) plus 1 s, so the old run's credentials and I/O are gone before the new run starts: budget two minutes of dead time per requeue, for preemption and for time limits alike. SLURM_RESTART_COUNT tells the script it is a restart; the running example instead finds its latest checkpoint pointer and resumes from it. A 30-day run on a cluster whose maximum job time is 2 days is a chain of such hops (or of afterany jobs, section 9).

9. Arrays, dependencies and heterogeneous jobs: workflows inside Slurm


Real work is rarely one job: a sweep is 50 nearly identical jobs; a pipeline is "tokenise, then train, then evaluate, and clean up if training fails"; an RL setup wants a CPU-only controller beside GPU workers, started together. All three tools were run here at once:


sbatch --array=0-5%2 ...                          # 6 tasks, at most 2 running at a time
sbatch -J sl-prep ...                              # job 103
sbatch -J sl-train --dependency=afterok:103 ...     # 106: only if prep exits 0
sbatch -J sl-eval  --dependency=afterok:106 ...     # 107
sbatch -J sl-fail --wrap 'sleep 5; exit 3'         # 108: fails on purpose
sbatch -J sl-clean  --dependency=afternotok:108 ... # 109: only if 108 fails
sbatch -J sl-report --dependency=afterok:108 ...    # 110: only if 108 succeeds
sbatch -J sl-single --dependency=singleton ...      # 111 and 112: same name, one at a time
