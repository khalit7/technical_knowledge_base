Slurm in one screen

Slurm is the program that owns a cluster's machines and hands them out. You describe what your job needs (2 nodes, 4 GPUs each, 10 hours); Slurm queues the request, decides when it may run and on which nodes, starts it there, watches it, kills it at its time limit and records what it used. Most large GPU training clusters run it: the {{root page's Tool map|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} has the dated evidence of who uses what.

Four ideas carry the whole page. Read them once now; every section below is one of them in detail.

1. One controller decides

A single daemon, slurmctld, holds every job and node in memory and makes every scheduling decision. Each compute node runs slurmd, which only does what the controller says. There is no negotiation between nodes.

2. A job is an allocation

A job is a reservation of resources (nodes, CPUs, memory, GPUs) for a time limit. It gets all of them at once or stays pending, so a multi-node job never starts with half its nodes: gang scheduling comes free.

3. Steps run inside it

Inside the allocation, srun launches job steps: the processes that do the work, one per task. A job can run many steps, one after another or side by side.

4. Policy is a priority number

Who goes first is one integer per job, a weighted sum of factors (fairshare, age, size, partition, QOS). Limits (QOS, accounts, partitions) can hold a job whatever its priority, and preemption can take nodes back.

The cluster this page ran on measured

The topic's lab cluster: Slurm 24.11.5 in four containers on one laptop (setup in the root's src/data/README.md). The GPUs are fake: each node declares 4 gpu resources that Slurm counts, allocates and bills, but no real device exists, so jobs get SLURM_GPUS_ON_NODE and no CUDA_VISIBLE_DEVICES. Click a box for what it does.

The running example. One small PyTorch job is used across the whole topic: a 112,577-parameter GPT trained with DDP over gloo, 2 nodes by 2 ranks, 200 steps, checkpoint every 50. On this cluster it is submitted with sbatch train.sbatch; its global loss at step 200 is 2.2638769149780273 on Slurm, Kubernetes and Ray alike (root page, src/data/runs/), and it was again in every run of it on this page.

What "measured" means here. Every command output on this page ran on that cluster on 16 October 2026 measured on Apple M1 Pro, Docker Desktop VM, shared machine. Which job ran where, in what order, with which reason and priority is deterministic Slurm behaviour and transfers to a real cluster; seconds and milliseconds are rough. Slurm here is the Debian 13 package 24.11.5; the current upstream release is 26.05.5 (13 October 2026, {{SchedMD releases|https://github.com/SchedMD/slurm/releases}}); source is quoted at tag slurm-24-11-5-1 so it matches what ran. Slurm has been open source (GPL-2.0) since 2002; NVIDIA bought SchedMD, its developer, in December 2025 and said it stays open source ({{NVIDIA, 2025-12-15|https://blogs.nvidia.com/blog/nvidia-acquires-schedmd/}}).
