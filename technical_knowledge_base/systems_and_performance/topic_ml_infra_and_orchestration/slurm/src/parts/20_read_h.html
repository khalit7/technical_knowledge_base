12. Containers on Slurm described, not run here

The problem. A training job needs an exact software stack (CUDA, NCCL, PyTorch, your code), while the nodes have one operating system image shared by everyone. Containers package the stack; the question is how to run one on a multi-user cluster where nobody gets root.

WayHowNotes
Pyxis + enroot (NVIDIA)srun --container-image=nvcr.io#nvidia/pytorch:<tag> --container-mounts=/data:/data python train.pyPyxis is "a SPANK plugin for the Slurm Workload Manager" (SPANK: Slurm's plugin interface for job options) that adds --container-image, --container-mounts, --container-name and others to srun; enroot imports a Docker image into a squashfs file and runs it without root; pyxis requires enroot 3.1.0 or later ({{pyxis README|https://github.com/NVIDIA/pyxis}}).
Apptainer (formerly Singularity)srun apptainer exec --nv image.sif python train.pyone-file images (.sif), run as the user; --nv exposes the host's GPU devices and binds in its CUDA libraries ({{Apptainer GPU docs|https://apptainer.org/docs/user/main/gpu.html}}).
Slurm's own OCI supportsrun --container=/path/to/bundle ..., configured by oci.conf (runc, crun, ...); scrun lets rootless Docker or Podman run jobs (Slurm 23.02 and later)"The bundle must already exist on the requested path on the execution node" ({{containers docs|https://slurm.schedmd.com/containers.html}}).
plain Dockernoneeds a root daemon; the Slurm docs list the security options and networking it must give up to be used through scrun.

Why not run here. This lab cluster is itself made of containers (the nodes' image already contains the running example and torch 2.14.1), so nesting a container runtime inside would show nothing a real GPU node does; the trade-offs that matter (image pull time on thousands of nodes, squashfs caching on local NVMe, the driver binding) need real nodes.

13. Slurm on Kubernetes described, not run here

The problem. Many organisations want one pool of GPUs for both batch training (which researchers like to drive with sbatch, fairshare and backfill) and long-running services (inference, notebooks, pipelines) that Kubernetes runs well. Splitting the GPUs between two clusters leaves one idle while the other queues. Two projects run Slurm inside Kubernetes:

  • Slinky (SchedMD's own): a Kubernetes operator that "contains a Kubernetes operator to deploy and manage certain components of Slurm clusters". Workers are NodeSets, "A set of homogeneous Slurm workers (compute nodes)", run as a StatefulSet or a DaemonSet of slurmd pods, each pod's status reflecting its Slurm node state; the controller is a pod too, with high availability through a ReadWriteMany volume. Its compatibility table lists releases 1.0 to 1.3, each needing Slurm 25.11 or later ({{slurm-operator README|https://github.com/SlinkyProject/slurm-operator}}); the latest release when this page was written was v1.2.3 (30 September 2026, root page's Tool map).
  • SUNK (CoreWeave): "Each Slurm compute node is a Pod running slurmd, placed one-to-one on a Kubernetes Node"; a SUNK Pod Scheduler places Kubernetes pods "through Slurm's own scheduling logic, on the same Nodes as Slurm jobs", and a Syncer "mirrors state between Slurm nodes and their Pods in both directions" ({{SUNK docs|https://docs.coreweave.com/products/sunk}}, vendor).
  • Managed Slurm in clouds: AWS SageMaker HyperPod launched with Slurm in November 2023 (root page's Tool map).

What you get, and what it costs. Slurm's semantics stay intact (an allocation is still all-or-nothing, fairshare and backfill still decide), while Kubernetes handles node lifecycle, images, monitoring and the services next to the jobs. The cost is two control planes that must agree about every node, a slurmd per node that now lives in a pod (its cgroups, devices and network are whatever the pod is given), and failure modes from both. Choosing between Slurm, Kubernetes with Kueue, and Ray is the root page's comparison; the sibling page Kubernetes for ML (kubernetes_for_ml) covers the Kubernetes side.
