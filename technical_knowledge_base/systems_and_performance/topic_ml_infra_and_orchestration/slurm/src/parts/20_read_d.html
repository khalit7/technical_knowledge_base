5. Partitions, QOS and associations: who may use what

A shared cluster needs rules beyond first come, first served: one team may not take every GPU, debug jobs must start fast, a huge job may run only at night. Slurm has three places to put a rule, and a pending job's reason names the one holding it.

All three were accepted and will never start: 8 GPUs exceed sl-small's 4 per user, 4 GPUs exceed carol's 2, and 120 minutes exceed batch's MaxTime=60. A job that breaks a limit on its own pends forever unless its QOS has the DenyOnLimit flag (then it is refused at submission), and a job over a partition's time limit is accepted unless EnforcePartLimits is set. Carol's priority, 6500, was the highest of the three: priority and limits are separate questions. squeue --start printed N/A for job 88 but a start time for 92 and 93, so a start time is not a promise that a job can run.

When several places define the same limit, the first found wins, in this order: partition QOS, job QOS, user association, account associations up the tree, root, partition ({{resource limits|https://slurm.schedmd.com/resource_limits.html}}). And none of it applies unless AccountingStorageEnforce includes limits and qos: the default is none, as on this lab cluster, so for these runs it was set to associations,limits,qos.

Partition: a named set of nodes with MaxTime, MaxNodes, a default time, who may submit, PriorityJobFactor and PriorityTier, in slurm.conf; partitions may overlap (here batch, urgent and sllow all cover c[1-3]). Association: a (cluster, account, user) triple in slurmdbd; accounts form a tree with fairshare shares and limits such as GrpTRES=gres/gpu=64 (the whole team at once) or MaxJobs, set with sacctmgr. QOS: a named bundle of a priority, limits (MaxTRESPerUser, MaxWall, GrpTRES) and preemption rules that a job selects with --qos; typical are debug (high priority, 1 node, 30 minutes), normal and scavenger (lowest, preemptible).







6. The scheduler: a main loop and a backfill loop


Testing every job against every node on every change is too slow, and starting jobs in strict priority order wastes nodes that a big job at the head cannot use yet. So the controller runs two loops. The main loop runs on every event (a job submitted or ending, a node returning) and every sched_interval (60 s by default, ); it walks pending jobs in priority order, starts each one that fits now, tests at most default_queue_depth jobs on an event (100 by default), and the moment one job of a partition cannot start, starts nothing else in that partition or on its nodes in that pass. The backfill loop runs every bf_interval (30 s by default, 2 s here): it builds a timeline from every running job's time limit, reserves the earliest start for each waiting job in priority order, and starts a lower job that fits a gap and ends before any reservation it would cross. Slurm's version reserves for every job it tests (conservative) and reserves whole nodes.


The main loop stops at the first blocked job; backfill fills the gap it leaves

  4. Backfill fills the gap. C needs one node for 20 minutes; on c3, from minute 5 to 25, it ends before B's reservation at 40, so backfill starts it now. B is not delayed.

  5. A job that does not fit. D asks for 60 minutes; on c3 it would run past 40 and delay B, so it waits. Slurm reserves a start for every job it tests (here 70). A shorter limit is D's only way in.

That rule is where the two most common reasons come from: the first blocked job of a partition shows Resources, and every job behind it shows Priority ("a job ahead of me is waiting"). Backfill is the only way a job jumps that line, and it needs your time limit to do it: a 2-hour job asking for 24 hours fits no gap. Either loop may start any job, and the log says which (sched: Allocate for the main loop, sched/backfill: _start_job for backfill): on the idle cluster job 125 was started by backfill 444 ms after sbatch, because this cluster's sched_min_interval=500000 (0.5 s) keeps the main loop from running more than twice a second and the backfill cycle came first.


A message that misleads: "Nodes required for job are DOWN, DRAINED or reserved for jobs in higher priority partitions" measured

Job 91, in partition sllow (same nodes as batch, same tier), pended with exactly this reason although every node was up and nothing was drained. When batch's top job could not start, the main loop removed batch's nodes from the rest of that pass, so sllow saw zero usable nodes and the code fills in its generic text (the source below). On clusters with overlapping partitions this reason usually means "a higher-priority job in another partition is waiting for these nodes". Check sinfo before calling the administrators.
