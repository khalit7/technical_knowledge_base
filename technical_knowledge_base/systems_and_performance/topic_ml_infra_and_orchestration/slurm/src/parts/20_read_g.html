9. Arrays, dependencies and heterogeneous jobs: workflows inside Slurm

The problem. Real work is rarely one job: a hyperparameter sweep is 50 nearly identical jobs; a pipeline is "tokenise, then train, then evaluate, and clean up if training fails"; an RL setup wants a CPU-only controller beside GPU workers, started together. Slurm has a tool for each, and all of them were run here at once:

sbatch --array=0-5%2 ...                          # 6 tasks, at most 2 running at a time
sbatch -J sl-prep ...                              # job 103
sbatch -J sl-train --dependency=afterok:103 ...     # 106: only if prep exits 0
sbatch -J sl-eval  --dependency=afterok:106 ...     # 107
sbatch -J sl-fail --wrap 'sleep 5; exit 3'         # 108: fails on purpose
sbatch -J sl-clean  --dependency=afternotok:108 ... # 109: only if 108 fails
sbatch -J sl-report --dependency=afterok:108 ...    # 110: only if 108 succeeds
sbatch -J sl-single --dependency=singleton ...      # 111 and 112: same name, one at a time

What sacct recorded measured

Thin grey: submitted, not yet eligible (waiting on a dependency or the array limit). Bar: running, on the node shown. Every job asks for 1 fake GPU except sl-train (4). 16 Oct 2026, one-second resolution; seconds from submission.

  • Arrays. One submission, one job id (102), tasks 102_0 to 102_5, each with SLURM_ARRAY_TASK_ID set (the script uses it to pick its hyperparameters or shard). %2 throttles: tasks 2 to 5 pended with reason JobArrayTaskLimit and started in pairs as earlier ones ended. Until a task starts, the pending tasks are one record in the controller, which is why a 1,000-task array costs the scheduler far less than 1,000 jobs; the default MaxArraySize is 1001 (), so --array=0-1000 is the largest by default.
  • Dependencies. sl-train became eligible the second sl-prep ended (+10 s), sl-eval when sl-train ended. afternotok ran the cleanup because 108 exited 3. sl-report, waiting on afterok:108, can never run, and Slurm says so but leaves it in the queue: 
    
Without --kill-on-invalid-dep=yes (or the cluster-wide kill_invalid_depend) such jobs sit in the queue forever. singleton held the second sl-single until the first ended. The types: after, afterany, afterok, afternotok, aftercorr (task by task between two arrays), singleton ({{sbatch --dependency|https://slurm.schedmd.com/sbatch.html}}).

When to use what. Sweeps of small runs: an array with a throttle. A pipeline: dependencies, or an outside workflow engine (Airflow, Flyte, Metaflow submit jobs and watch them), covered by the sibling page ML platforms and workflows (ml_platforms_and_workflows). A long training run cut into time-limited pieces: one job that requeues itself (section 8) or a chain of afterany jobs that each resume from the latest checkpoint.







10. Reservations: holding nodes for a time or a team


The problem. Some capacity must be guaranteed in advance: a maintenance window when nodes will be rebooted, a week of 512 GPUs promised to one team for a big run, a demo. A reservation is a named block of nodes (or cores) for a time window, usable only by the users or accounts it names (scontrol create reservation, by an administrator).


A maintenance window, all three nodes, starting in 3 minutes, for 5 minutes, then three jobs measured:


$ scontrol create reservation ReservationName=sl_maint StartTime=now+3minutes Duration=5 \
      Nodes=ALL Flags=MAINT,IGNORE_JOBS Users=root
Reservation created: sl_maint
$ squeue                                   # 8 s later
JOBID         NAME   USER ST PRIORITY NODES CPUS NODELIST(REASON)
  118    sl-r-long  alice PD     6833     2    8 (ReqNodeNotAvail, Reserved for maintenance)   # --time=10
  120     sl-r-mid    bob PD     4000     1    4 (ReqNodeNotAvail, Reserved for maintenance)   # --time=4
  119   sl-r-short  alice  R     6500     1    4 c1                                            # --time=2
$ squeue --start
  118    sl-r-long PD  2026-10-16T05:47:57 (ReqNodeNotAvail, Reserved for maintenance)
  120     sl-r-mid PD  2026-10-16T05:47:57 (ReqNodeNotAvail, Reserved for maintenance)
$ scontrol delete ReservationName=sl_maint ; squeue     # 6 s later
  120     sl-r-mid    bob PD     4000     1    4 (Resources)
  118    sl-r-long  alice  R     6833     2    8 c[2-3]
  119   sl-r-short  alice  R     6500     1    4 c1


From src/runs/raw1/resv.txt, columns trimmed.


The 2-minute job fitted before the window and ran; the 4- and 10-minute jobs could not finish before it and were held until its end (05:47:57). This is the most common surprise before a maintenance: free nodes, a job that will not start. Ask for less time, or wait. The source sets that reason when a job's time window overlaps a MAINT reservation .


A team reservation, node c3 for alice for 10 minutes:


$ scontrol create reservation ReservationName=sl_team StartTime=now Duration=10 Nodes=c3 Users=alice
$ squeue
JOBID         NAME   USER ST PRIORITY NODES CPUS NODELIST(REASON)
  121   sl-t-bob12    bob PD     4666     3   12 (ReqNodeNotAvail, May be reserved for other job)
  122    sl-t-bob8    bob PD     4333     2    8 (Resources)
  123    sl-t-resv  alice  R     6500     1    4 c3     # --reservation=sl_team
  124   sl-t-nores  alice  R     6500     1    4 c1     # no reservation: ordinary nodes


Bob's 12-GPU job needs all three nodes and is told one may be reserved; his 8-GPU job waits for ordinary nodes (c1 is taken by alice's other job, c3 is reserved). Only a job that names the reservation can use it. Flags change the rules: FLEX lets a job use nodes inside and outside, MAINT marks the time as maintenance in accounting, IGNORE_JOBS creates it even if running jobs overlap. For a training team the useful pattern is a recurring or long reservation on a block of nodes in one network domain, so a large job never waits behind fragmentation.







11. Accounting: what ran, and what it used


The problem. After the fact you need to know what a job used (to debug it, to bill a team, to plan capacity), and the controller forgets finished jobs after MinJobAge (300 s by default, ; 600 s on this cluster). slurmdbd keeps them.


    

  • sacct: one row per job and per step, any field (AllocTRES, Elapsed, State, ExitCode, NodeList, Reason, Eligible). -X drops the steps, -D shows every requeued run, -P gives pipe-separated output for scripts. GPU-hours of a job are gres/gpu in AllocTRES times Elapsed.
    • 

  • sreport: summaries (cluster utilisation, top users) from rollups the database computes hourly. Asked for this page's last few minutes, it printed headers and no rows measured: recent jobs are in sacct but not yet in sreport.
    • 

  • sstat: live usage of a running step (CPU, memory). It needs the job accounting plugin to read real per-process numbers; in these containers without cgroups it printed nonsense (AveCPU 213503982+, no MaxRSS) for the running example, so it is not used here.
    • 

  • sacctmgr: the database's users, accounts, QOS and limits (section 5).
