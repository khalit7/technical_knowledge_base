10. Reservations: holding nodes for a time or a team

Some capacity must be guaranteed in advance: a maintenance window, a week of 512 GPUs promised to one team for a big run, a demo. A reservation is a named block of nodes (or cores) for a time window, usable only by the users or accounts it names (scontrol create reservation, by an administrator). A maintenance window on all three nodes, starting in 3 minutes for 5 minutes, then three jobs measured:

Free nodes, and a job that will not start: its time limit crosses the window

scontrol create reservation ReservationName=sl_maint StartTime=now+3minutes Duration=5 Nodes=ALL Flags=MAINT,IGNORE_JOBS Users=root, window 05:42:57 to 05:47:57; three jobs submitted at 05:39:57 (src/runs/raw1/resv.txt). Bars are each job's time limit from submission.

The 2-minute job fitted before the window and ran; the 4- and 10-minute jobs could not finish before it and pended with ReqNodeNotAvail, Reserved for maintenance, planned for 05:47:57, its end. This is the most common surprise before a maintenance: ask for less time, or wait. After scontrol delete ReservationName=sl_maint the 10-minute job started at once. The source sets that reason when a job's time window overlaps a MAINT reservation .

A team reservation, node c3 for alice for 10 minutes: alice's job naming --reservation=sl_team ran on c3, her job without it on c1; bob's 3-node job pended with ReqNodeNotAvail, May be reserved for other job and his 2-node job with Resources. Only a job that names the reservation can use it. Flags change the rules: FLEX lets a job use nodes inside and outside, MAINT marks the time as maintenance in accounting, IGNORE_JOBS creates it even if running jobs overlap. For a training team the useful pattern is a recurring or long reservation on a block of nodes in one network domain, so a large job never waits behind fragmentation.

11. Accounting: what ran, and what it used

The controller forgets finished jobs after MinJobAge (300 s by default, ; 600 s on this cluster); slurmdbd keeps them.

  • sacct: one row per job and per step, any field (AllocTRES, Elapsed, State, ExitCode, NodeList, Reason, Eligible). -X drops the steps, -D shows every requeued run, -P gives pipe-separated output. A job's GPU-hours are gres/gpu in AllocTRES times Elapsed. Cancelled pending jobs have empty AllocTRES: they never held anything.
  • sreport: summaries (cluster utilisation, top users) from rollups the database computes hourly. Asked for this page's last few minutes it printed headers and no rows measured: use sacct for recent jobs.
  • sstat: live usage of a running step. It needs the job accounting plugin to read real per-process numbers; in these containers without cgroups it printed nonsense (AveCPU 213503982+, no MaxRSS), so it is not used here.
  • sacctmgr: the database's users, accounts, QOS and limits (section 5).

12. Containers on Slurm described, not run here


A training job needs an exact stack (CUDA, NCCL, PyTorch, your code) on nodes that share one OS image, and nobody gets root. The common answer on GPU clusters is Pyxis with enroot (NVIDIA): Pyxis is "a SPANK plugin for the Slurm Workload Manager" (SPANK: Slurm's plugin interface for job options) that adds --container-image, --container-mounts and --container-name to srun, so srun --container-image=nvcr.io#nvidia/pytorch:<tag> --container-mounts=/data:/data python train.py runs every rank in the image; enroot imports a Docker image into a squashfs file and runs it without root, and pyxis requires enroot 3.1.0 or later ({{pyxis README|https://github.com/NVIDIA/pyxis}}). Not run here because this cluster is itself made of containers; what matters (image pull time on thousands of nodes, squashfs caching on local NVMe, the driver binding) needs real nodes.

Slurm on Kubernetes: Slinky and SUNK (described, not run here)


Organisations that want one GPU pool for batch training (driven with sbatch, fairshare and backfill) and long-running services that Kubernetes runs well can run Slurm inside Kubernetes rather than split the GPUs between two clusters, one idle while the other queues.


    

  • Slinky (SchedMD's own): a Kubernetes operator that "contains a Kubernetes operator to deploy and manage certain components of Slurm clusters". Workers are NodeSets, "A set of homogeneous Slurm workers (compute nodes)", run as a StatefulSet or a DaemonSet of slurmd pods, each pod's status reflecting its Slurm node state; the controller is a pod too, with high availability through a ReadWriteMany volume. Its compatibility table lists releases 1.0 to 1.3, each needing Slurm 25.11 or later ({{slurm-operator README|https://github.com/SlinkyProject/slurm-operator}}); the latest release when this page was written was v1.2.3 (30 September 2026, root's Tool map). SchedMD open-sourced it in November 2024 (Apache-2.0) and reached 1.0 in late 2025; a second Slinky project, slurm-bridge, goes the other way and lets Slurm be the scheduler for Kubernetes pods so both kinds of work share one GPU pool ({{Slinky docs|https://slurm.schedmd.com/slinky.html}}). Not run on the topic's kind cluster: it needs Slurm 25.11+ images and more memory than the topic's budget.
    • 

  • SUNK (CoreWeave): "Each Slurm compute node is a Pod running slurmd, placed one-to-one on a Kubernetes Node"; a SUNK Pod Scheduler places Kubernetes pods "through Slurm's own scheduling logic, on the same Nodes as Slurm jobs", and a Syncer "mirrors state between Slurm nodes and their Pods in both directions" ({{SUNK docs|https://docs.coreweave.com/products/sunk}}, vendor). A CoreWeave product since 2023 with no public repository: Slurm accounting in MySQL, node lifecycle tied to CoreWeave's node health checks, available only on CoreWeave Kubernetes Service.
    • 

  • Which: Slinky on any Kubernetes cluster, SUNK when renting from CoreWeave; neither if researchers are content with Kubernetes-native jobs.
    • 

  • Managed Slurm in clouds: AWS SageMaker HyperPod launched with Slurm in November 2023 (root's Tool map).
    • 



What you get, and what it costs. Slurm's semantics stay intact (all-or-nothing allocations, fairshare, backfill) while Kubernetes handles node lifecycle, images, monitoring and the services beside the jobs. The cost is two control planes that must agree about every node, a slurmd that lives in a pod (its cgroups, devices and network are whatever the pod is given), and failure modes from both. Choosing between Slurm, Kubernetes with Kueue, and Ray is the root's comparison; {{Kubernetes for ML|n:3c65c17b0d0d81cf9417de52108cfbce}} owns the Kubernetes side.
