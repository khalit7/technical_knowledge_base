1. The daemons: who does what

The problem. Hundreds or thousands of machines, many users, and one rule: no GPU may be given to two jobs at once. Slurm's answer is a single brain. Every decision is made in one process that holds the whole cluster in memory, and the machines are its hands.

Configless: one copy of the configuration

Every daemon needs slurm.conf, and on old clusters it was copied to every node, where copies drifted apart. Since Slurm 20.02 a node can fetch it: slurmd --conf-server ctl asks the controller, which serves slurm.conf, gres.conf, cgroup.conf and a few others, and slurmd caches them under SlurmdSpoolDir/conf-cache ({{configless docs|https://slurm.schedmd.com/configless_slurm.html}}). On this cluster measured:

$ ls /var/spool/slurmd/conf-cache     # on c1
cgroup.conf
gres.conf
slurm.conf

A change is then two commands on the controller: edit slurm.conf, run scontrol reconfigure. In 24.11 that restarts the controller in place; its own log says so (measured, 05:36:39 to 05:36:40 UTC): Reconfigure signal (SIGHUP) received, Saving all slurm state, slurmctld version 24.11.5 started on cluster mi, Recovered state of 3 nodes, Relinquishing control to new slurmctld process. Every experiment on this page that changed the configuration did it this way and put the original back the same way.

Declared, not detected

Slurm schedules what slurm.conf declares for a node, not what the hardware has. slurmd -C prints what the node would declare from its hardware:

$ slurmd -C                      # on c1: what the hardware says
NodeName=c1 CPUs=5 Boards=1 SocketsPerBoard=1 CoresPerSocket=5 ThreadsPerCore=1 RealMemory=9951
$ scontrol show node c1          # what Slurm uses (lines trimmed)
NodeName=c1 Arch=aarch64 CoresPerSocket=4
   CPUAlloc=0 CPUEfctv=4 CPUTot=4 CPULoad=0.45
   Gres=gpu:4
   RealMemory=4000 AllocMem=0 FreeMem=5565 Sockets=1 Boards=1
   State=IDLE ThreadsPerCore=1 TmpDisk=0 Weight=1
   CfgTRES=cpu=4,mem=4000M,billing=5,gres/gpu=4

16 Oct 2026. The container sees the whole Docker VM (5 CPUs, 9.7 GB); the configuration declares 4 CPUs and 4,000 MB per node, and Slurm hands out exactly those. billing=5 is this cluster's TRESBillingWeights: 4 GPUs at 1.0 plus 4 CPUs at 0.25.

Why it matters. Declaring less than the hardware is safe (some is left for the OS). Declaring more is not: a node that registers with fewer CPUs, less memory or less temporary disk than declared is taken out of service "to avoid scheduling jobs on them" ({{slurm.conf, node configuration|https://slurm.schedmd.com/slurm.conf.html}}; the state shows as INVAL, an invalid registration). This cluster hit it while being built: with no device files for its fake GPUs a node went INVAL with gres/gpu count reported lower than configured (0 < 4) (root page, src/data/README.md). So a typo in slurm.conf takes nodes out of service, and production sites declare a little less memory than slurmd -C reports.

Predict: the controller crashes on day 2 of a 3-day training job and is restarted an hour later. What happened to the job?
It kept training. The processes run under slurmstepd on the compute nodes and do not need the controller while they run; the controller's state (jobs, allocations) is on disk in StateSaveLocation, and on restart it logs Recovered state of N nodes and Recovered information about N jobs, as it did here at every reconfigure. What stops for that hour is everything new: submissions, starts, and steps (srun must ask the controller for each step, so a script that launches a new step every epoch would stall).
