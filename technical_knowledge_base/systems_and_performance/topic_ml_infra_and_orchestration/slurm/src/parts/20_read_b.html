1. The daemons: one brain, many hands

No GPU may be given to two jobs at once, on thousands of machines with many users. Slurm's answer is a single brain: every decision is made in one process that holds the whole cluster in memory (the hero's top box), and the machines only do what it says.

Defaults read from src/common/read_config.h at slurm-24-11-5-1: . This lab cluster sets both timeouts to 30 s so the root's Failure lab could watch a node die in seconds: there a killed node was marked DOWN and its job requeued 32.1 s after the kill.

Declared, not detected. Slurm schedules what slurm.conf declares for a node, not what the hardware has. Here each node declares 4 CPUs and 4,000 MB while slurmd -C sees 5 CPUs and 9,951 MB, and Slurm hands out exactly the declared amounts. Declaring less is safe; declaring more is not: a node that registers with fewer CPUs, memory or temporary disk than declared is taken out of service "to avoid scheduling jobs on them" (state INVAL, {{slurm.conf|https://slurm.schedmd.com/slurm.conf.html}}). This cluster hit it while being built: gres/gpu count reported lower than configured (0 < 4). So a typo in slurm.conf takes nodes out of service, and sites declare a little less memory than slurmd -C reports.

Predict: the controller crashes on day 2 of a 3-day training job and is restarted an hour later. What happened to the job?
It kept training. The processes run under slurmstepd on the compute nodes and do not need the controller while they run; the controller's state is on disk in StateSaveLocation, and on restart it logs Recovered state of N nodes and Recovered information about N jobs, as it did here at every reconfigure. What stops for that hour is everything new: submissions, starts and steps (srun asks the controller for each step, so a script that launches a new step every epoch would stall).

Configless. Every daemon needs slurm.conf; on old clusters it was copied to every node, where copies drifted apart. Since Slurm 20.02 a node can fetch it: slurmd --conf-server ctl asks the controller, which serves slurm.conf, gres.conf, cgroup.conf and a few others, cached under SlurmdSpoolDir/conf-cache ({{configless docs|https://slurm.schedmd.com/configless_slurm.html}}). On c1, ls /var/spool/slurmd/conf-cache printed cgroup.conf gres.conf slurm.conf.

A change is then: edit slurm.conf on the controller, run scontrol reconfigure. In 24.11 that restarts the controller in place; its log (05:36:39 to 05:36:40 UTC): Reconfigure signal (SIGHUP) received, Saving all slurm state, slurmctld version 24.11.5 started on cluster mi, Recovered state of 3 nodes, Relinquishing control to new slurmctld process. Running jobs are not touched. Every experiment here that changed the configuration did it this way and put the original back the same way.

Slurm's own steps are milliseconds (allocation to prolog 5 to 7 ms, prolog to batch script 11 to 12 ms, script to step launch 27 to 28 ms); the training processes began 2.2 to 2.3 s after the step launch (torchrun, imports, rendezvous) and trained for about 6.3 to 6.5 s.

Submit. sbatch sends the script and its options; the controller checks them against partitions, limits and node configurations (a request no node could ever satisfy is refused here with Requested node configuration is not available), assigns an id and an initial priority (InitPrio=4166), and stores the script: editing the file afterwards changes nothing.
    2. 

  2. Pending, with a reason, here Resources (first in line, resources busy). Backfill planned the start at 05:37:53 and logged the same plan 12 times (every 2 s, bf_interval=2): that is the blocker's time limit, not its real end. Slurm plans with limits because it cannot know runtimes.
    3. 

  3. Allocate. The blocker ended at 05:37:18.890; a job ending is an event that runs the main scheduler, which allocated c1 and c2 22 ms later, 34 s before the plan. A planned start is an upper bound that usually moves earlier.
    4. 

  4. Prolog. With PrologFlags=Alloc, slurmd runs the site's prolog as root on every node first (5 ms later here). Sites check GPU health here; a prolog that exits non-zero drains the node and requeues the job.
    5. 

  5. Batch step. The script runs on the first node (c1) as the user: step 79.batch.
    6. 

  6. Job steps. Each srun asks the controller for a step; slurmd starts a slurmstepd on each node, which starts the tasks. The one srun here started one torchrun per node: step 79.0.
    7. 

  7. Completing. When the script exits, every node kills leftovers and runs the epilog; only then are the nodes free.
    8.

The states squeue and sacct print


Main line: PENDING (PD), CONFIGURING (CF, nodes booting or a slow prolog), RUNNING (R), COMPLETING (CG, about 1 s here), COMPLETED (CD). Bad ends: FAILED (script exited non-zero; not requeued), TIMEOUT (SIGTERM at the limit, SIGKILL after KillWait), CANCELLED, NODE_FAIL (with --requeue the job is requeued instead), OUT_OF_MEMORY (needs ConstrainRAMSpace), PREEMPTED. Back to the queue or paused: REQUEUED, SUSPENDED (keeps its memory, GPU memory included). Click a state for its note.


Where the 10 seconds went. The training loop ran about 6.5 s (the ranks' own wall_s); the rest is the chain every job pays: prolog, batch shell, step request, torchrun and imports (the ranks began 2.3 s after the step launch), rendezvous, epilog. On a real cluster GPU health checks, image pulls and the rendezvous of hundreds of nodes make this chain minutes long, paid again on every restart; the root's {{Launch lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} splits it by stage.


Predict: squeue --start said job 79 would start at 05:37:53. Why did it start at 05:37:18?




The plan uses time limits; the blocker asked for 1 minute and used 25 s. _job_complete was followed 21 ms later by Running job scheduler for default depth and the allocation: the main scheduler runs on events (a job submitted or ending, a node coming back) as well as periodically. Nothing was preempted: both jobs were in partition batch, and preemption here works only across partition tiers (section 8).
