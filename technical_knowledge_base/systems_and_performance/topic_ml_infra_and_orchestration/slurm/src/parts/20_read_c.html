2. The life of a job, from the controller's own log

The problem. "My job is not running" can mean a dozen things: it is waiting its turn, waiting for nodes, waiting for a limit, its nodes are booting, its prolog is running, its first step has not launched, it finished and is cleaning up. Each is a different state in Slurm, and knowing them tells you where to look.

Job states

The states squeue and sacct print (short codes in brackets). Click one. The main line is what the running example did here; the side exits are the ways a job ends badly.

Watching it happen. The running example was submitted while another job (bob's, 12 GPUs, time limit 1 minute, sleeping 25 s) held every GPU, with the controller at debug log level and the Backfill debug flag on, a prolog and epilog that log a line on each node, and squeue polled every second measured. Raw logs (IPs scrubbed) in src/runs/raw1/. The {{Job lifecycle|#t-life}} tab replays every line on a timeline, against the same job on an idle cluster.

Read it as the job's life:

  1. Submit. sbatch sends the script and its options to the controller, which validates them against partitions, limits and node configurations (a request no node could ever satisfy is refused here, with Requested node configuration is not available), gives the job an id and an initial priority, and returns. The script is stored by the controller; editing the file afterwards changes nothing.
  2. Pending. The job waits with a reason, here Resources: it is first in line and the resources are busy. The backfill scheduler planned a start at 05:37:53, which is the blocker's time limit (started 05:36:53, limit 1 minute), not its real end: Slurm plans with limits because it cannot know runtimes.
  3. Allocate. The blocker actually ended at 05:37:18.890. Ending a job is an event that triggers the main scheduler, which allocated c1 and c2 to job 79 22 ms later, 34 s before the plan. A job's planned start is an upper bound that usually moves earlier.
  4. Prolog. With PrologFlags=Alloc, slurmd runs the site's prolog as root on every node of the allocation before anything else (5 ms later here). Sites check GPU health here; a prolog that exits non-zero drains the node and requeues the job.
  5. Batch step. The script runs on the first node of the allocation (c1) as the user. This is step 79.batch.
  6. Job steps. Each srun inside the script asks the controller for a step; slurmd on each node starts a slurmstepd, which starts the tasks. The running example's one srun started one torchrun per node: step 79.0.
  7. Completing. When the script exits, the job is COMPLETING while every node kills leftovers and runs the epilog; only then are the nodes free for the next job.
  8. Completed, and recorded. The accounting record goes to slurmdbd; sacct shows the job and each step:

Where the 10 seconds went. Of the job's 10 s of elapsed time, the training loop itself ran about 6.5 s (the ranks' own wall_s); the rest is the chain every job pays: prolog, starting the batch shell, the step request, torchrun and Python imports, rendezvous, and the epilog. On a real cluster the prolog (GPU health checks), image pulls and the rendezvous of hundreds of nodes make this chain minutes long, and it is paid again on every restart. The root's {{Launch lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} splits it by stage. measured on Apple M1 Pro, Docker Desktop VM, shared machine

Predict: squeue --start said job 79 would start at 05:37:53. Why did it start at 05:37:18?
The plan uses time limits; the blocker asked for 1 minute and used 25 s. When it ended, _job_complete was followed 21 ms later by Running job scheduler for default depth and the allocation: the main scheduler runs on events (a job submitted or ending, a node coming back) and also periodically, so it does not wait for the next backfill cycle. Nothing was preempted: both jobs were in partition batch, and preemption here works only across partition tiers (section 9).
