3. Resources: what a job asks for, and what it gets

A GPU node is not a box of GPUs: it is CPUs, memory and GPUs that must be handed out together. Slurm counts every kind of thing it hands out as a TRES (trackable resource): cpu, mem, node, gres/gpu, and billing, a weighted sum used for fairshare. The selection plugin select/cons_tres (the default) allocates individual cores, memory and GPUs, so several jobs can share a node; SelectTypeParameters says what is consumable (here CR_Core, cores only; GPU clusters use CR_Core_Memory so memory is counted too).

Which GPU is mine? On a real node gres.conf maps each GPU to its device file (Name=gpu File=/dev/nvidia[0-7], or AutoDetect=nvml), and Slurm sets CUDA_VISIBLE_DEVICES for every job and step to the GPUs it was given. Only cgroups make that a fence: with TaskPlugin=task/cgroup, ProctrackType=proctrack/cgroup and ConstrainCores, ConstrainRAMSpace, ConstrainDevices in cgroup.conf (each "no" by default, {{cgroup.conf|https://slurm.schedmd.com/cgroup.conf.html}}), the job's processes cannot see other GPUs or use other cores, and are killed past their memory (state OUT_OF_MEMORY). Without them a process can open every GPU on the node, as on this lab cluster, where cgroups are off (inside a container without systemd, slurmd 24.11 stops with fatal: systemd scope for slurmstepd could not be set). How cgroups work is owned by {{Containers and isolation|n:3f05c17b0d0d8156a841e4bf28f11293}}.

Topology. Where the nodes sit decides all-reduce speed: topology/tree (switches) and topology/block (blocks of nodes such as NVL72 racks; both in 24.11, and 25.05 added several topologies in one topology.yaml, {{topology docs|https://slurm.schedmd.com/topology.html}}) keep a job inside one switch or block, and --switches=1@01:00:00 waits up to an hour for that. The networks themselves are {{Cluster anatomy|n:3fc5c17b0d0d816a871df56477fc83b2}}'s.

4. Job steps: the processes inside an allocation

An allocation is only a reservation; srun starts the processes. Each srun in a script is one job step: it asks the controller for a slice of the allocation, slurmd on each node starts a slurmstepd, and that starts the tasks, gives each its rank and collects their exit codes. Steps run one after another (preprocess, train, evaluate) or side by side (a sweep of small runs inside one big allocation).

The trap. By default a step may use every CPU of the job on each of its nodes ("By default, all non-GRES resources on each node in the step allocation will be used", {{srun --exact|https://slurm.schedmd.com/srun.html}}), so steps meant to run side by side queue behind each other. Without --exact each step took both CPUs of its node (AllocTRES cpu=2), so the third and fourth waited 6 s (srun prints only srun: Step created for StepId=129.4 when it finally gets in); with it each took one CPU and all four ran at once. A subtlety: a job submitted with --cpus-per-task exports SLURM_CPUS_PER_TASK, and srun treats that as an explicit -c, which "implies --exact" (srun's -c entry): the same steps without --exact inside a job with --cpus-per-task=1 (job 130) ran side by side. So a step's behaviour depends on how its job was submitted: write --exact when you mean it, and -N1 for one-task steps in a multi-node job.

Overlap. Steps never share CPUs unless asked: srun --overlap --jobid=N --pty bash runs a step on resources another step holds, which is how you attach a debugger or py-spy to a running training step. For training the usual layout is one step that starts everything: one torchrun per node (the running example, section 14), or one task per GPU with ranks from SLURM_PROCID. {{Launching distributed training|n:3fc5c17b0d0d81b3a8a5c58224bff9fa}} compares the launchers, and {{Distributed PyTorch|n:3c65c17b0d0d815e85aff8decd8f35ab}} owns torchrun at the PyTorch level.
