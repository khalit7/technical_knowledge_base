The idea in one screen

Starting a distributed job is a chain of six links (scheduler, node launcher, agent rendezvous, worker start, communicator, first step), each owned by different software with its own timeout. A broken link rarely crashes: the processes that did start wait for the ones that did not until some timeout fires, so which timeout fires first decides both how long you wait and what the error says.

Rank, local rank
a process's number in the job (0 to W−1, W the world size) and on its own machine (picks the GPU).
Launcher
the program that starts the processes and tells each its numbers (srun, mpirun, torchrun, Ray Train ...).
Agent
a launcher process that stays alive on each node to watch and restart its workers; torchrun is one.
Rendezvous
how processes on different machines find each other and agree on ranks, through a store (a small key-value server).
Communicator
the object that runs collectives among the ranks, built by a backend: gloo (CPU, TCP) or NCCL (NVIDIA GPUs).
Bootstrap
NCCL's own start-up: a ring of TCP connections over which ranks swap addresses and topology.

Timeouts: torch 2.14.1 and Ray 2.59.0 source, each linked in section 7. Typical failures seen there: a node that never arrives gives a bare RendezvousTimeoutError after 602 s (c10d); a missing pod gives "1/2 clients joined" at 903 s (static); a wrong WORLD_SIZE gives "wait timeout after 120000ms"; Ray Train with too few resources retries "worker group startup timed out" every 60 s, forever.

When a job "hangs at start", the first question is always which link is it stuck in? Section 7 puts every link's clock on one axis; section 8 is how to find the one rank that is different once training has started.
