1. The launch chain in one screen

A scheduler gives your job some machines. Nothing has trained yet. One process per GPU has to start on every machine, learn who it is, find all the others and build a communicator (the object that runs collectives such as all-reduce among them). That start-up is a chain of six links, each owned by different software, each with its own way of failing and its own timeout. When a job "hangs at start", the first question is always: which link is it stuck in?

The words used below, once. A process is one running copy of your training script; the job has world size W of them, numbered by rank 0 to W−1, and numbered again 0, 1, ... on each machine by local rank (which picks the GPU). A launcher is the program that starts those processes and tells each its numbers. An agent is a launcher process that stays alive on each node to watch and restart its workers (torchrun is one). Rendezvous is the protocol by which processes on different machines discover each other. A store is the small key-value server they rendezvous through. The {{Launch lab of the parent page|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} introduces all of these with the same job; this page goes one level down into each link.

The running example is the topic's tiny GPT (112,577 parameters, TinyShakespeare, DDP over gloo, PyTorch's CPU communication library standing in for NVIDIA's NCCL), 2 nodes × 2 processes, in Linux containers on an Apple M1 Pro (Docker Desktop VM, shared machine), torch 2.14.1. Click a link of the chain for what it does, what it needs and how it breaks.

The rule that organises the rest of the page
A broken link rarely crashes. The processes that did start wait, politely, for the ones that did not, until some timeout fires; which timeout fires first decides both how long you wait and what the error says. Section 7 puts every timeout in one table; the {{Hang triage|#t-ldhang}} tab shows the real error each failure produced here.

Two patterns cover almost every real job. Scheduler starts one agent per node, the agent starts one worker per GPU (srun → torchrun, kubelet → torchrun, Trainer → torchrun, accelerate → torchrun): torchrun earns its place by doing the rendezvous between nodes and by restarting workers. The scheduler starts every rank directly (srun with one task per GPU, mpirun, Ray Train, DeepSpeed's pdsh): no agent, so your script must turn the launcher's numbers into RANK and WORLD_SIZE, and a failure is handled by the scheduler, not in place. The {{Kubernetes|n:3c65c17b0d0d81cf9417de52108cfbce}} child page measured what the first pattern does to exit codes: a rank that exits with code 13 makes torchrun exit 1 (its ChildFailedError lists "exitcode : 13"), so a Kubernetes podFailurePolicy rule on exit code 13 never matches (sibling page {{Kubernetes for ML|n:3c65c17b0d0d81cf9417de52108cfbce}}, measured on Kubernetes v1.37.0).

Predict: on two machines, accelerate launch --num_machines 2 --machine_rank 1 --main_process_ip 10.0.0.5 train.py. Which rendezvous does it use?
torchrun's static rendezvous. Accelerate 1.15.0 hands the job to torch.distributed.run; its --rdzv_backend defaults to static, and for more than one machine (without --same_network) it sets rdzv_endpoint = main_process_ip:main_process_port ({{utils/launch.py:224|L:acc_rdzv}}), port 29500 when none is given. So Accelerate jobs inherit torchrun's timeouts, including the 900 s static wait of section 7.
