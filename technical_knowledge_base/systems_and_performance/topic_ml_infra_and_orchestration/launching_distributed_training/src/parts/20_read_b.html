3. torchrun's agent: start, watch, restart

torchrun is a thin command-line wrapper around PyTorch's elastic agent (LocalElasticAgent). One agent runs per node, and its whole life is one loop ({{api.py:906-974|L:agent_failed}}):

  1. Rendezvous with the other agents (section 4), which gives this node its group rank (node rank) and the job's world size.
  2. Start the workers: --nproc-per-node child processes, each with RANK, LOCAL_RANK, WORLD_SIZE, MASTER_ADDR, MASTER_PORT, TORCHELASTIC_RESTART_COUNT and the rest ({{local_elastic_agent.py:424-441|L:agent_env}}).
  3. Watch: every --monitor-interval (0.1 s by default, {{run.py:576|L:run_monitor}}) check whether each worker is alive, exited with 0, or exited with an error. The group is HEALTHY, SUCCEEDED or FAILED.
  4. React. FAILED with restarts left: stop every local worker, go back to step 1 and count one restart. HEALTHY but the rendezvous reports nodes waiting to join: also go back to step 1, and this one is free: "membership changes do not count as retries" ({{api.py:958|L:agent_member}}). SUCCEEDED: wait at an exit barrier for the other agents, up to 300 s ({{api.py:465|L:agent_exitbarrier}}).

Three consequences follow, each seen in this page's runs. A restart restarts every process of every node, not just the one that died: the healthy ranks' collectives fail when their peer vanishes, their agents see FAILED too, and all agents re-run the rendezvous. A restart runs your script again from the top, so it continues only if the script loads its own checkpoint (the running example does). The failure costs at least one monitor interval plus a rendezvous plus a cold start: in the run below a rank exited at step 30, both agents logged FAILED within about a second, and the workers were back at step 20 (the last checkpoint) 4.3 s after the crash (measured on Apple M1 Pro, Docker Desktop VM, shared machine; the Failure lab of the parent page measured 3.4 s for the same restart on Slurm).

4. Rendezvous internals: static and dynamic


torchrun ships two rendezvous backends that behave nothing alike.


Static (the default, {{run.py:523|L:run_static}}) has no negotiation. You give every node its rank (--node-rank) and the address of node 0 (--master-addr, --master-port). Node 0's agent opens a TCPStore there; the others connect; everyone waits until all --nnodes have connected, then starts. A missing node means a wait of 900 s, because torchrun's launcher writes timeout=900 into the rendezvous configuration ({{launcher/api.py:126-130|L:launcher_cfg}}) and the static backend reads exactly that key ({{static_tcp_rendezvous.py:122|L:static_cfg}}); its own default of 600 s ({{:28|L:static_600}}) is never used from torchrun. A node that dies after the start is a job failure: the static handler cannot form a new group without it.


Dynamic (--rdzv-backend=c10d) is a small distributed state machine kept in the store. The state ({{dynamic_rendezvous.py:272|L:dyn_state}}) is: a round number; the participants of the current round; a wait list of nodes that arrived after the round closed and want the next one; a redundancy list of nodes beyond max_nodes; a deadline; a complete flag; and each node's last heartbeat. Each agent repeatedly reads the state, decides one action, and writes the new state back with a compare-and-set, retrying when someone else wrote first (the "stale state" lines in the logs). The join decision ({{_RendezvousJoinOp|L:dyn_join}}) is a short list of rules:


    

  • Round not complete and I am not in it: add myself to the participants. When the count reaches min_nodes, set a last-call deadline 30 s away ({{:743|L:dyn_lastcall}}, default {{:145|L:dyn_lastcall30}}); when it reaches max_nodes, complete at once ({{:748|L:dyn_max}}).
    • 

  • Round complete and I am not in it: join the wait list if there is room ({{:930|L:dyn_waitlist}}), else the redundancy list ({{:936|L:dyn_redund}}). Running agents notice a non-empty wait list at their next monitor tick and re-rendezvous (section 3).
    • 

  • I am a participant, the count is between min and max, and the deadline has passed: mark the round complete. Ranks are then given in the sorted order of node descriptors ({{:833|L:dyn_ranks}}), strings of the form <fqdn>_<pid>_<n> ({{:269|L:dyn_nodedesc}}): not arrival order, and since the sort is on text, pid 100 sorts before pid 11.
    • 

  • A node whose heartbeat is older than 5 s × 3 attempts ({{:1430|L:dyn_keepalive}}, {{:1435|L:dyn_keepmax}}, check {{:476|L:dyn_dead}}) is dead and removed by whoever syncs next.
    • 

  • The join deadline passed (600 s by default, {{:144|L:dyn_timeouts}}): give up with RendezvousTimeoutError. The launcher's timeout=900 is not this key: the dynamic backend reads join_timeout ({{:1385|L:dyn_gettimeout}}), so c10d jobs give up at 600 s while static ones wait 900 s (the parent's Launch lab measured 602 s and 903 s).
    • 



The {{Rendezvous lab|#t-ldrz}} replays all of it from a real run: three agents A, B, C on --nnodes=2:3; C arrives 45 s late; later C is killed. The numbers, from that run (measured, timings rough):




Predict: in that run, C was killed at 56.2 s. How long until A and B were training again at world size 2?




About 43 s, and every part is a default. The agents saw their workers fail within 1 s and went back to the rendezvous; but C was still a participant of the completed round, so A and B could only join the wait list of the next round until C was declared dead, 13 s after the kill (heartbeats every 5 s, dead after 3 missed). Then A and B formed round 2, reached min_nodes=2, and the 30 s last call ran out before the round completed: 13 + 30 = 43 s. The parent's Failure lab measured 44.0 s for the same scale-down on Slurm. Shorter last-call and keep-alive settings (--rdzv-conf last_call_timeout=...,keep_alive_interval=...) shorten it, at the price of forming smaller groups or declaring slow nodes dead.


Where the store lives. With c10d the agent whose host name matches --rdzv-endpoint hosts the store; when several agents share a machine, all try, one wins and the rest connect as clients ({{c10d_rendezvous_backend.py:154|L:c10d_twice}}). That process is a single point of failure: the parent's Failure lab killed the agent hosting the store and the whole job died with "RendezvousConnectionError: The connection to the C10d store has failed", elastic or not. On a real cluster, put the endpoint on a node that is least likely to fail, or run the store outside the job (etcd-v2 backend, or a dedicated host).







5. The store between attempts: one variable decides whether a restart works


After the agents meet, each worker needs a store too: init_process_group uses it to swap the addresses gloo or NCCL will connect to. In torch 2.14.1 the rank-0 agent starts a second TCPStore on a free port and the workers use it, kept for the life of the agent and reused by every later round ({{dynamic_rendezvous.py:1209-1217|L:dyn_bootcond}}). The worker side assumes the opposite. Its comment reads "We create a new TCPStore for every retry so no need to add prefix for each attempt" ({{rendezvous.py:205|L:rdzv_noprefix}}). So after a restart the new workers find the old workers' keys still there, including each rank's old gloo address. Setting TORCH_DISABLE_SHARE_RDZV_TCP_STORE=1 ({{:1146|L:dyn_share}}) turns the sharing off: each round's rank 0 builds a fresh store on a new port.


The parent's Failure lab found that in-job restarts on two Slurm nodes failed with the default and worked with the variable set. The animation shows why, from three recorded runs with the same crash: a probe in every worker connects to the workers' store before init_process_group and counts its keys.

Both shared runs failed, differently. In run 1 rank 1 connected at once to rank 0's old port and got "Connection refused", while rank 0 waited for a connection that could never come for 300 s, the c10d Store's default timeout ({{Store.hpp:21|L:store_300}}), not the 60 s process-group timeout the script passed (that this 300 s is the one gloo used is our reading; gloo's own source was not checked). In run 2 rank 0 was the one to read a stale address. Which rank loses the race is chance, which is why restarts with the default can look flaky rather than broken; the sibling PyTorch page's "flaky elastic restarts" on one machine are consistent with it.


The same sharing also breaks growing an elastic job
In the default-store version of the Rendezvous lab's run (labelled "store shared" there), C's arrival made the agents re-rendezvous into round 1 with C. C, new, needed MASTER_ADDR from the round's keys ({{api.py:102|L:api_masteraddr}}); A, rank 0 again, already had its store server and skipped publishing it (the condition at {{dynamic_rendezvous.py:1209|L:dyn_bootcond}}). All three agents waited on keys nobody would write, and all three failed 61.5 s later on the c10d store's 60 s read timeout: "wait timeout after 60000ms, keys: /torch.rendezvous.ld-el.1/MASTER_ADDR". With the variable set the same arrival cost 2.3 s, from the agents noticing C to the new round's workers starting. For any job with --max-restarts above 0 or an elastic node range, set TORCH_DISABLE_SHARE_RDZV_TCP_STORE=1 on torch 2.14.1 (whether this is reported upstream was not checked).
