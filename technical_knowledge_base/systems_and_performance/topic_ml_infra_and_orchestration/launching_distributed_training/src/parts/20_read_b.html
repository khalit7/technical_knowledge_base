Two patterns cover almost every real job. The scheduler starts one agent per node and the agent starts one worker per GPU (srun → torchrun, kubelet → torchrun, Trainer → torchrun, accelerate → torchrun): torchrun earns its place by doing the rendezvous between nodes and by restarting workers. The scheduler starts every rank directly (srun with one task per GPU, mpirun, Ray Train, DeepSpeed's pdsh): no agent, so your script turns the launcher's numbers into RANK and WORLD_SIZE, and a failure is handled by the scheduler, not in place.

torchrun's static rendezvous. Accelerate 1.15.0 hands the job to torch.distributed.run; its --rdzv_backend defaults to static, and for more than one machine (without --same_network) it sets rdzv_endpoint = main_process_ip:main_process_port ({{utils/launch.py:224|L:acc_rdzv}}), port 29500 when none is given. So Accelerate jobs inherit torchrun's timeouts, including the 900 s static wait of section 7.

3. torchrun's agent: start, watch, restart

torchrun is a thin command-line wrapper around PyTorch's elastic agent (LocalElasticAgent). One agent runs per node and its whole life is one loop ({{api.py:906-974|L:agent_failed}}):

The agent's loop: every failure goes back to the rendezvous, and takes every node with it

Times on the arrows are from the restart run below: a rank exits with code 13 at step 30; both agents log FAILED within about a second; the workers are back at step 20 (the last checkpoint) 4.3 s after the crash (measured on Apple M1 Pro, Docker Desktop VM, shared machine; the parent's Failure lab measured 3.4 s for the same restart on Slurm).

  1. Rendezvous with the other agents (section 4): this node gets its group rank (node rank) and the job's world size.
  2. Start the workers: --nproc-per-node child processes, each with RANK, LOCAL_RANK, WORLD_SIZE, MASTER_ADDR, MASTER_PORT, TORCHELASTIC_RESTART_COUNT and the rest ({{local_elastic_agent.py:424-441|L:agent_env}}).
  3. Watch every --monitor-interval (0.1 s by default, {{run.py:576|L:run_monitor}}): the group is HEALTHY, SUCCEEDED or FAILED.
  4. React. FAILED with restarts left: stop every local worker, go back to step 1, count one restart (--max-restarts, default 0, {{run.py:564|L:run_maxrestarts}}). HEALTHY but nodes waiting to join: also back to step 1, for free: "membership changes do not count as retries" ({{api.py:958|L:agent_member}}). SUCCEEDED: wait at an exit barrier for the other agents, up to 300 s ({{api.py:465|L:agent_exitbarrier}}).

So a restart restarts every process of every node, not just the one that died (the healthy ranks' collectives fail when their peer vanishes, their agents see FAILED too); it runs your script again from the top, so it continues only if the script loads its own checkpoint; and it costs at least a monitor interval, a rendezvous and a cold start.

4. Rendezvous: static and dynamic


Static (the default, {{run.py:523|L:run_static}}) has no negotiation. You give every node its rank (--node-rank) and node 0's address (--master-addr, --master-port); node 0's agent opens a TCPStore there, the others connect, and everyone waits until all --nnodes have connected. A missing node means a wait of 900 s: torchrun's launcher writes timeout=900 into the rendezvous configuration ({{launcher/api.py:126-130|L:launcher_cfg}}) and the static backend reads exactly that key ({{static_tcp_rendezvous.py:122|L:static_cfg}}); its own default of 600 s ({{:28|L:static_600}}) is never used from torchrun. A node that dies after the start is a job failure: the static handler cannot form a new group without it.


Dynamic (--rdzv-backend=c10d) is a small distributed state machine kept in the store ({{dynamic_rendezvous.py:272|L:dyn_state}}): a round number, the round's participants, a wait list of nodes that arrived after the round closed, a redundancy list beyond max_nodes, a deadline, a complete flag and each node's last heartbeat. Each agent reads the state, decides one action and writes it back with a compare-and-set, retrying when someone else wrote first (the "stale state" log lines). The join rules ({{_RendezvousJoinOp|L:dyn_join}}):


    

  • Round open, I am not in it: join the participants. At min_nodes, set a last-call deadline 30 s away ({{:743|L:dyn_lastcall}}, default {{:145|L:dyn_lastcall30}}); at max_nodes, complete at once ({{:748|L:dyn_max}}).
    • 

  • Round complete, I am not in it: join the wait list if there is room ({{:930|L:dyn_waitlist}}), else the redundancy list ({{:936|L:dyn_redund}}). Running agents see a non-empty wait list at their next monitor tick and re-rendezvous (section 3).
    • 

  • Participant, count between min and max, deadline passed: mark the round complete. Ranks follow the sorted order of node descriptors ({{:833|L:dyn_ranks}}), strings <fqdn>_<pid>_<n> ({{:269|L:dyn_nodedesc}}): not arrival order, and since the sort is on text, pid 100 sorts before pid 11.
    • 

  • Heartbeat older than 5 s × 3 attempts ({{:1430|L:dyn_keepalive}}, {{:1435|L:dyn_keepmax}}, check {{:476|L:dyn_dead}}): the node is dead, removed by whoever syncs next.
    • 

  • Join deadline passed (600 s by default, {{:144|L:dyn_timeouts}}): give up with RendezvousTimeoutError. The dynamic backend reads join_timeout ({{:1385|L:dyn_gettimeout}}), not the launcher's timeout=900, so c10d jobs give up at 600 s while static ones wait 900 s (the parent's Launch lab measured 602 s and 903 s).

About 43 s, and every part is a default. The agents saw their workers fail within 1 s and went back to the rendezvous; but C was still a participant of the completed round, so A and B could only join the wait list of the next round until C was declared dead, 13 s after the kill (heartbeats every 5 s, dead after 3 missed). Where the store lives. With c10d the agent whose host name matches --rdzv-endpoint hosts the store; when several agents share a machine, all try, one wins and the rest connect as clients ({{c10d_rendezvous_backend.py:154|L:c10d_twice}}). That process is a single point of failure: the parent's Failure lab killed the agent hosting the store and the whole job died with "RendezvousConnectionError: The connection to the C10d store has failed", elastic or not. 5. The store between attempts: one variable decides whether a restart works


After the agents meet, the workers need a store too: init_process_group uses it to swap the addresses gloo or NCCL will connect to. In torch 2.14.1 the rank-0 agent starts a second TCPStore on a free port for the workers, kept for the life of the agent and reused by every later round ({{dynamic_rendezvous.py:1209-1217|L:dyn_bootcond}}). The worker side assumes the opposite: "We create a new TCPStore for every retry so no need to add prefix for each attempt" ({{rendezvous.py:205|L:rdzv_noprefix}}). So after a restart the new workers find the old workers' keys still there, including each rank's old gloo address. TORCH_DISABLE_SHARE_RDZV_TCP_STORE=1 ({{:1146|L:dyn_share}}) turns the sharing off: each round's rank 0 builds a fresh store on a new port. The parent's Failure lab found that in-job restarts on two Slurm nodes failed with the default and worked with the variable set; this before/after shows why, from three recorded runs of the same crash, with a probe in every worker counting the store's keys before init_process_group.

Both shared runs failed, differently. In run 1 rank 1 connected at once to rank 0's old port and got "Connection refused", while rank 0 waited for a connection that could never come for 300 s, the c10d Store's default timeout ({{Store.hpp:21|L:store_300}}), not the 60 s process-group timeout the script passed (that this 300 s is the one gloo used is our reading; gloo's own source was not checked). In run 2 rank 0 read the stale address. Which rank loses the race is chance, which is why restarts with the default look flaky rather than broken; the sibling PyTorch page's "flaky elastic restarts" on one machine are consistent with it.
