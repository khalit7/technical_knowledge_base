--max-restarts without TORCH_DISABLE_SHARE_RDZV_TCP_STORE=1 (torch 2.14.1)
The restarted workers read the dead workers' addresses from the reused store. Gloo connectFullMesh failed with [.../gloo/transport/tcp/pair.cc:152] timed out connecting: SO_ERROR: Connection refused, remote=[<ip-1>]:3500 on one rank, a 300 s silence then Connect timeout [none] on the other. Set the variable (section 5).
An elastic range (--nnodes=2:3) with the default store: the job dies when a node joins
All agents wait 60 s, then torch.distributed.DistStoreError: wait timeout after 60000ms, keys: /torch.rendezvous.ld-el.1/MASTER_ADDR (and the rank-0 agent: .../torchelastic/role_info/0, ... /1, ... /2). Same fix.
A collective inside if rank == 0: (logging a metric, saving with a sharded state dict)
Rank 0's extra all-reduce is matched with the others' next one. Here rank 0 aborted at once: terminate called after throwing an instance of 'gloo::EnforceNotMet' what(): [enforce fail at .../pair.cc:464] op.preamble.length <= op.nbytes. 56292 vs 4. Received data size doesn't match expected size. Is there a distributed collective mismatch in your code? (exit code −6, SIGABRT), and the others reported "Connection closed by peer". With equal sizes it would not fail at all: it would silently pair the wrong collectives. Every rank must call the same collectives in the same order.
One rank all-reduces a tensor of a different shape
No error for 60 s, then on all four ranks [.../gloo/transport/tcp/unbound_buffer.cc:78] Timed out waiting 60000ms for recv operation to complete: the process-group timeout, not a diagnosis. TORCH_DISTRIBUTED_DEBUG=DETAIL names both shapes (section 8), except with DDP on torch 2.14.1.
Uneven data: one rank has one batch fewer
Rank 3 finished its loop and exited cleanly; 0.4 to 0.9 s later the others failed with Connection closed by peer [<ip-1>]:... This is typically caused by a remote worker crashing. Nothing crashed. Give every rank the same number of batches (DistributedSampler(drop_last=True)) or wrap the loop in DDP's join() context manager.
A rank stuck in its own code (a data loader, a lock, a file that never appears)
Three ranks in backward's all-reduce, one in threading.Event.wait; after the timeout, Timed out waiting 60000ms for recv operation to complete on the waiting ranks and nothing from the stuck one. Only stacks or the flight recorder name it (section 8).
MASTER_ADDR=localhost, or a short pod host name, on more than one node
Each node finds its own address, so nobody meets: a bare RendezvousTimeoutError after 601 s (c10d) or The IPv6 network addresses of (la-badaddr-node-0-0, 29500) cannot be retrieved (gai error: -2 - Name or service not known) repeated until 902 s (static), both in the parent's Launch lab.
Running NCCL in a default Docker container
64M of /dev/shm and 64 KB of lockable memory (measured above). Pass --shm-size=1g --ulimit memlock=-1 (NCCL's own recommendation) or the pod equivalents.
Interview rehearsal: seven questions with answers (optional)
What does torchrun do that srun python train.py does not?
It rendezvous between nodes (so ranks are not fixed in advance and nodes can come and go within a range), starts and watches one worker per GPU, sets the PyTorch variables, and restarts the whole group on failure up to --max-restarts. srun alone gives each task SLURM_PROCID and friends; your script maps them to RANK and WORLD_SIZE, and a failure is handled by Slurm (requeue), not in place.
Static or c10d rendezvous: when do you pick which?
Static when the scheduler already gives every node a stable index and address (JobSet's completion index and pod DNS name, Slurm's node list) and you do not need in-job restarts across nodes: no negotiation, nothing to time out except the 900 s wait. c10d when you want elastic ranges, restarts that can re-form the group, or hosts you do not know in advance; you pay a last-call wait (30 s) and depend on the store host staying up.
A 64-node job sits silent for exactly 10 minutes, then fails with an empty RendezvousTimeoutError. What happened?
The c10d join timeout (600 s) expired before all agents joined: at least one node's agent never reached the store. Look at which nodes' logs are empty (the missing ones), then why: image pull, node boot, a wrong endpoint or DNS on that node. 15 minutes and "1/64 clients joined" would point at the static backend instead.
How does NCCL find its peers, and what is the most common reason it hangs at init?
Rank 0 creates a unique id containing the address of a bootstrap socket; PyTorch passes it to every rank through the c10d store; ranks connect to that root, form a ring over TCP and exchange addresses and topology, then build rings and trees and connect lazily. The usual hang is the bootstrap or socket transport choosing an interface other nodes cannot reach (a bridge, a management NIC): set NCCL_SOCKET_IFNAME and read NCCL_DEBUG=INFO's "Bootstrap: Using" line.
All 512 ranks are stuck. How do you find the cause in five minutes?
Do not read 512 identical stacks: compare. Flight-recorder dumps (or a watchdog that writes them) give each rank's last collective sequence number; the rank with a lower number, or none, is the odd one; its py-spy or faulthandler stack names the line. If every rank is at the same collective and sequence, suspect the network or a GPU (NCCL_DEBUG, the kernel log), not your code.
Which timeouts would you set for a job whose rank 0 spends 20 minutes writing a checkpoint while the others wait?
The process-group timeout must exceed the longest gap between collectives, so more than 20 minutes (NCCL's default of 10 would kill the job; gloo's 30 would not). Better: make the save asynchronous or shard it so all ranks take part, and keep the timeout tight enough to catch real hangs.
Design: the launch layer for a 1,000-GPU lab (125 nodes of 8 GPUs). What do you standardise?
One image per release, pre-pulled or cached on every node (start-up waits for the slowest node). One launcher pattern: the scheduler (Slurm or JobSet) starts one torchrun per node with c10d rendezvous on a stable endpoint, explicit join, last-call and process-group timeouts, --max-restarts plus a checkpoint resume, and TORCH_DISABLE_SHARE_RDZV_TCP_STORE=1 while the store-sharing problem stands. A job template that fixes NCCL_SOCKET_IFNAME, NCCL_IB_HCA, NCCL_NET=IB (fail instead of falling back), shared memory and memlock, flight recorder and dump-on-timeout, and an in-process hang watchdog writing stacks to shared storage. A pre-job health check per node (GPU, NVLink, NIC, a two-node NCCL test on new nodes) so bad nodes never join a rendezvous. Hot spares registered with the scheduler, so a failed node is replaced by a requeue rather than a shrink. And dashboards for the start-up stages of section 1, because at this size start-up and restart time are a measurable share of goodput (sibling page {{Fault tolerance at scale|n:3fc5c17b0d0d815786d1c1dddb311a9b}}).
