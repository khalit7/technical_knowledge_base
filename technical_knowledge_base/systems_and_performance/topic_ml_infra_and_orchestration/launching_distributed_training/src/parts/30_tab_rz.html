Rendezvous lab: torchrun's state machine, replayed from a real run

Three torchrun agents, A, B and C, play three nodes (one container, one rank each, the running example, torch 2.14.1). A starts at 0 s, B at 3 s, C at 45 s; when the job has run 40 steps at world size 3, C and its rank are killed with SIGKILL. The same arrivals and the same kill run three ways: the dynamic (c10d) rendezvous with --nnodes=2:3 --max-restarts=3 and TORCH_DISABLE_SHARE_RDZV_TCP_STORE=1; the same with torch's default store sharing; and the static rendezvous with --nnodes=3. Every step below is a line the agents logged: torch records each rendezvous action as an event but discards it by default (the handler is a NullHandler, {{handlers.py:14|L:events_null}}), so the runs used a 20-line wrapper, src/scripts/ld_torchrun.py, that only turns that log on and then calls torchrun's own main(). Heartbeats and retries after a lost compare-and-set ("stale state") are left out. State (round, participants, wait list, deadline) is rebuilt from the events by the rules of section 4 of the Reading tab.

Green bars: training, by the world size in rank 0's log; dots: logged events (red: failures, blue: rounds completed).
Times from the agents' logs, seconds since agent A was started; measured on Apple M1 Pro, Docker Desktop VM, shared machine (rough to about a second; the defaults behind them, 30 s last call, 5 s × 3 heartbeats, 60 s store reads, are exact). Script: src/scripts/ld_rdzv.sh elastic | elastic_share | static.
Predict before you play the static mode: C is killed at 54 s. What does the static rendezvous do?
The static handler has no rounds, no wait list and here no restarts (--max-restarts default 0): A and B exited with code 1 within 1.3 s of the kill. With restarts allowed it would try to meet again at the same fixed world size of 3 and wait for C. Static is the right choice only when something above it (Slurm's requeue, a JobSet restart) replaces the node.

What to take away

  • Joining a running elastic job costs a full restart of every worker (here 2.3 s at toy scale, from noticing the new node to the rendezvous being done), and it is free in torchrun's accounting: membership changes do not use up --max-restarts.
  • Losing a node costs heartbeat expiry plus a last call (13 + 30 s here) before training resumes at the smaller size; neither shows up as an error in the logs, only as silence.
  • Node ranks follow the sorted node descriptors, not arrival order: here A, B, C happened to sort in arrival order (pids 11, 16, 31).
  • With the default shared store the grow step deadlocked and the whole job failed after the store's 60 s read timeout: the reason to set TORCH_DISABLE_SHARE_RDZV_TCP_STORE=1 on torch 2.14.1.
