8. Debugging a hang: find the one rank that is different

A hang in a collective job is almost always one rank doing something else while all the others wait for it in a collective. The waiting ranks look identical and tell you nothing; the work is finding the odd one and seeing what it is doing. Two questions sort every case: did it hang before the first step or during training? (before: a link of section 1; during: a collective mismatch, a dead or stuck rank, or the network) and are all ranks stuck in the same place? The rule behind training-time hangs (every rank calls the same collectives, in the same order, with matching sizes) and the flight recorder that checks it are owned by {{Distributed PyTorch|n:3c65c17b0d0d815e85aff8decd8f35ab}}, section 11; here are four real hangs met the way you meet them.

The running example's model, data and optimiser in its training loop with one classic distributed bug injected at step 5, 4 ranks under torchrun in one container, process-group timeout 60 s (src/scripts/ld_hang.py, ld_hang.sh). At 25 s, if the job was still alive, py-spy dump read every rank's stack from outside (the container had CAP_SYS_PTRACE, not --privileged); a watchdog thread inside each rank also wrote its own stacks and flight recorder after 20 s without a step. Pick a case, read the logs, diagnose, then reveal the stacks.

All measured on Apple M1 Pro, Docker Desktop VM, shared machine, torch 2.14.1+cpu, gloo. Times are seconds since the processes finished init_process_group; addresses scrubbed. The timeouts and messages are what matter, not the seconds.

The pattern: a collective on one rank only aborts that rank at once (gloo's size check); different shapes and a rank stuck in user code both give silence until the 60 s process-group timeout, and only stacks or the flight recorder name the odd rank (in the stuck case rank 1 issued 15 collectives and the others 16: "missing ranks: {1}"); uneven batches look like a crash ("Connection closed by peer ... typically caused by a remote worker crashing") 0.4 to 0.9 s later although the short rank exited 0. The fixes: every rank calls the same collectives; equal batches per rank (DistributedSampler(drop_last=True) or DDP's join()); a timeout on every blocking call in the data path.

An in-process watchdog is the tool that scales: when no step completes for N seconds, a daemon thread writes every thread's stack (faulthandler) and the flight recorder (torch._C._distributed_c10d._dump_fr_trace(), a pickle) to files, before any timeout kills the evidence. It needs no ptrace and runs on every rank at once, which is what a 1,000-rank job needs; it is about twenty lines of src/scripts/ld_hang.py, and on the stuck case all four ranks dumped 20.5 to 20.6 s after their last step.

TORCH_DISTRIBUTED_DEBUG=DETAIL crashed every DDP run here
With DETAIL, every rank of every hang case died with SIGSEGV (exit code −11) before the first step. Isolated: a bare all-reduce worked, a deliberate shape mismatch was caught with the full message below, but wrapping the running example's model in DDP segfaulted inside DDP's constructor (_ddp_init_helper, the call to self.logger.set_construction_data_and_log at {{distributed.py:1474|L:ddp_logger}}, located with PYTHONFAULTHANDLER=1). Same on the macOS wheel; TORCH_DISTRIBUTED_DEBUG=INFO worked. measured with torch 2.14.1 CPU builds (Linux aarch64 container and macOS arm64); CUDA builds not checked, and not checked against PyTorch's issue tracker. Use DETAIL on a small reproduction without DDP, or on another torch version.


What DETAIL says when it works: rank 0 all-reduces a tensor of shape [1], rank 1 one of shape [2] (src/scripts/ld_detail.py --what mismatch, 2 ranks). Without DETAIL the same bug waited out the 30 s timeout: "Timed out waiting 30000ms for send operation to complete".

Getting ptrace inside containers. A training container usually lacks CAP_SYS_PTRACE, and restarting it with the capability destroys the hang you wanted to see. Attach a debug sidecar that joins the stuck container's process namespace instead; on Kubernetes kubectl debug -it <pod> --target=<container> --image=... does the same with an ephemeral container (described, not run here).
