6. Building the communicator: gloo here, NCCL on GPUs

init_process_group takes the store from the rendezvous (env:// means MASTER_ADDR:MASTER_PORT), wraps it in a prefix so different groups never collide (default_pg, {{distributed_c10d.py:2551|L:pg_default}}), and asks a backend, the library that actually moves bytes, to build the communicator. The two backends start very differently.

gloo (what ran here) builds everything inside init_process_group: each rank writes its listening address under a key, reads every other rank's, and connects to all of them, a full mesh of TCP connections ({{ProcessGroupGloo.cpp:697|L:gloo_mesh}}). It is eager and fails early: a wrong address shows up as "Gloo connectFullMesh failed" before step 1. The parent's Launch lab measured this step at a median of 9 ms on Slurm with every rank already waiting.

NCCL (NVIDIA GPUs; read from source at v2.30.7-1, the version torch 2.14.1's Linux wheel pins as nvidia-nccl-cu13==2.30.7 on PyPI; not run here, nothing here has a GPU) is lazy and has its own bootstrap. In order:

  1. Nothing happens in init_process_group unless you pass device_id=, which makes PyTorch connect eagerly ({{ProcessGroupNCCL.cpp:1089|L:nccl_eager}}). By default the communicator is built at the first collective, which for DDP is the parameter broadcast inside the DDP constructor. So "hangs at init" often means "hangs in the DDP constructor".
  2. Rank 0 makes a unique id: a random 64-bit "magic" plus the address of a listening bootstrap root socket on the one interface NCCL picked for bootstrap ({{bootstrap.cc:430|L:nccl_uid}}, interface choice {{:124|L:nccl_boot_if}}). NCCL_COMM_ID=host:port replaces it with a fixed address ({{:441|L:nccl_commid}}).
  3. PyTorch hands the id to everyone through the c10d store (rank 0 sets key "0", "1", ... per communicator, {{ProcessGroupNCCL.cpp:2913|L:nccl_uid_set}}). If rank 0 died first, the others report "[r] is setting up NCCL communicator and retrieving ncclUniqueId from [0] via c10d key-value store by key '0', but store->get('0') got error: ..." ({{:2927|L:nccl_uid_err}}).
  4. Bootstrap ring (bootstrapInit, {{init.cc:1916|L:nccl_bootinit}}): every rank opens listening sockets and sends its address to the root; the root tells each rank who its next neighbour is; the ranks connect in a ring and pass everyone's addresses around it. Above 256 ranks the connections to the root are staggered at 7,000 messages per second ({{bootstrap.cc:669|L:nccl_stagger}}; documented as NCCL_UID_STAGGER_THRESHOLD and _RATE). All of this is plain TCP on the bootstrap interface, the front-end network (sibling page Cluster anatomy: "NCCL's bootstrap uses the front-end").
  5. Peer information is all-gathered over the bootstrap ring (AllGather1, {{init.cc:1034|L:nccl_allgather1}}): host hashes, GPU bus ids, which ranks share a machine.
  6. Topology: each rank reads its machine's PCI tree, NVLink and NICs into a graph ({{ncclTopoGetSystem, init.cc:1141|L:nccl_topo}}; NCCL_TOPO_DUMP_FILE writes it as XML) and searches it for rings ({{:1178|L:nccl_ring}}), trees ({{:1186|L:nccl_tree}}), CollNet and NVLS patterns; the ranks agree on one plan.
  7. Network plugin: InfiniBand or RoCE through verbs if any device is found, otherwise TCP sockets ("Using network %s", {{init.cc:486|L:nccl_net_name}}; force one with NCCL_NET, {{:2117|L:nccl_net_env}}). No RDMA device prints NET/IB : No device found. ({{net_ib/init.cc:470|L:nccl_ib_none}}) and NCCL carries on over sockets, much slower and without an error (sibling page Cluster anatomy covers the cluster side of that fallback).
  8. Connections between peers are made when a collective first needs them: NCCL_RUNTIME_CONNECT defaults to 1 ({{init.cc:61|L:nccl_runtime_connect}}). A communicator can initialise cleanly and the first all-reduce hang because a peer's data network is unreachable.

Which interface does NCCL pick?

Most "NCCL hangs at init" are the bootstrap or the socket transport choosing an interface the other nodes cannot reach. The rule, from ncclFindInterfaces ({{socket.cc:190-232|L:nccl_iface}}) and the matcher ({{os/linux.cc:379|L:nccl_os_find}}): if NCCL_SOCKET_IFNAME is set, use the interfaces it names (prefixes; ^ excludes, = means exact); otherwise try names starting with ib ({{:206|L:nccl_iface_ib}}), then an interface in the same subnet as NCCL_COMM_ID, then anything not starting with docker, lo or virbr ({{:220|L:nccl_iface_excl}}), then docker, then lo. Only interfaces that are up and running count ({{linux.cc:402|L:nccl_os_running}}), in the kernel's order; bootstrap takes the first one, the socket transport up to 16 ({{net_socket.cc:59|L:nccl_sock_ifs}}, {{socket.h:25|L:nccl_maxifs}}). Below, that rule applied by this page's script to the real interface lists of two containers on this machine. rule from source, applied here; NCCL itself not run

On the host network (how Slurm containers, pyxis/enroot and Kubernetes hostNetwork: true pods see the machine) the default rule happily takes Docker's bridges and veth pairs: harmless for bootstrap here, because eth0 comes first in the kernel's list, but the socket transport would spread traffic over interfaces no other node can reach. One explicit NCCL_SOCKET_IFNAME per cluster, put in the job template, removes the guess.
