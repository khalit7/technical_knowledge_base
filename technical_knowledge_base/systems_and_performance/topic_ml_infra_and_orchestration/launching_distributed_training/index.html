The idea in one screen

Starting a distributed job is a chain of six links (scheduler, node launcher, agent rendezvous, worker start, communicator, first step), each owned by different software with its own timeout. A broken link rarely crashes: the processes that did start wait for the ones that did not until some timeout fires, so which timeout fires first decides both how long you wait and what the error says.

Parallelism forms are on Distributed Training; this page is everything between "the scheduler gave me nodes" and "step 1 ran".

Rank, local rank
a process's number in the job (0 to W−1, W the world size) and on its own machine (picks the GPU).
Launcher
the program that starts the processes and tells each its numbers (srun, mpirun, torchrun, Ray Train ...).
Agent
a launcher process that stays alive on each node to watch and restart its workers; torchrun is one.
Rendezvous
how processes on different machines find each other and agree on ranks, through a store (a small key-value server).
Communicator
the object that runs collectives among the ranks, built by a backend: gloo (CPU, TCP) or NCCL (NVIDIA GPUs).
Bootstrap
NCCL's own start-up: a ring of TCP connections over which ranks swap addresses and topology.

Typical failures seen there: a node that never arrives gives a bare RendezvousTimeoutError after 602 s (c10d); a missing pod gives "1/2 clients joined" at 903 s (static); a wrong WORLD_SIZE gives "wait timeout after 120000ms"; Ray Train with too few resources retries "worker group startup timed out" every 60 s, forever.

When a job "hangs at start", the first question is always which link is it stuck in? Section 7 puts every link's clock on one axis; section 8 is how to find the one rank that is different once training has started.

Two patterns cover almost every real job. The scheduler starts one agent per node and the agent starts one worker per GPU (srun → torchrun, kubelet → torchrun, Trainer → torchrun, accelerate → torchrun): torchrun earns its place by doing the rendezvous between nodes and by restarting workers. The scheduler starts every rank directly (srun with one task per GPU, mpirun, Ray Train, DeepSpeed's pdsh): no agent, so your script turns the launcher's numbers into RANK and WORLD_SIZE, and a failure is handled by the scheduler, not in place.

Predict: on two machines, accelerate launch --num_machines 2 --machine_rank 1 --main_process_ip 10.0.0.5 train.py. Which rendezvous does it use?
torchrun's static rendezvous. Accelerate 1.15.0 hands the job to torch.distributed.run; its --rdzv_backend defaults to static, and for more than one machine (without --same_network) it sets rdzv_endpoint = main_process_ip:main_process_port (utils/launch.py:224), port 29500 when none is given. So Accelerate jobs inherit torchrun's timeouts, including the 900 s static wait of section 7.

3. torchrun's agent: start, watch, restart

torchrun is a thin command-line wrapper around PyTorch's elastic agent (LocalElasticAgent). One agent runs per node and its whole life is one loop (api.py:906-974):

The agent's loop: every failure goes back to the rendezvous, and takes every node with it

Times on the arrows are from the restart run below: a rank exits with code 13 at step 30; both agents log FAILED within about a second; the workers are back at step 20 (the last checkpoint) 4.3 s after the crash (measured on Apple M1 Pro, Docker Desktop VM, shared machine; the parent's Failure lab measured 3.4 s for the same restart on Slurm).

  1. Rendezvous with the other agents (section 4): this node gets its group rank (node rank) and the job's world size.
  2. Start the workers: --nproc-per-node child processes, each with RANK, LOCAL_RANK, WORLD_SIZE, MASTER_ADDR, MASTER_PORT, TORCHELASTIC_RESTART_COUNT and the rest (local_elastic_agent.py:424-441).
  3. Watch every --monitor-interval (0.1 s by default, run.py:576): the group is HEALTHY, SUCCEEDED or FAILED.
  4. React. FAILED with restarts left: stop every local worker, go back to step 1, count one restart (--max-restarts, default 0, run.py:564). HEALTHY but nodes waiting to join: also back to step 1, for free: "membership changes do not count as retries" (api.py:958). SUCCEEDED: wait at an exit barrier for the other agents, up to 300 s (api.py:465).

So a restart restarts every process of every node, not just the one that died (the healthy ranks' collectives fail when their peer vanishes, their agents see FAILED too); it runs your script again from the top, so it continues only if the script loads its own checkpoint; and it costs at least a monitor interval, a rendezvous and a cold start.

Anything above torchrun (srun's --kill-on-bad-exit, Slurm's job state, a Kubernetes podFailurePolicy) sees 1, so a podFailurePolicy rule on exit code 13 never matches (measured by the sibling page Kubernetes for ML on Kubernetes v1.37.0). 4. Rendezvous: static and dynamic


Static (the default, run.py:523) has no negotiation. You give every node its rank (--node-rank) and node 0's address (--master-addr, --master-port); node 0's agent opens a TCPStore there, the others connect, and everyone waits until all --nnodes have connected. A missing node means a wait of 900 s: torchrun's launcher writes timeout=900 into the rendezvous configuration (launcher/api.py:126-130) and the static backend reads exactly that key (static_tcp_rendezvous.py:122); its own default of 600 s (:28) is never used from torchrun. A node that dies after the start is a job failure: the static handler cannot form a new group without it.


Dynamic (--rdzv-backend=c10d) is a small distributed state machine kept in the store (dynamic_rendezvous.py:272): a round number, the round's participants, a wait list of nodes that arrived after the round closed, a redundancy list beyond max_nodes, a deadline, a complete flag and each node's last heartbeat. Each agent reads the state, decides one action and writes it back with a compare-and-set, retrying when someone else wrote first (the "stale state" log lines). The join rules (_RendezvousJoinOp):


    

  • Round open, I am not in it: join the participants. At min_nodes, set a last-call deadline 30 s away (:743, default :145); at max_nodes, complete at once (:748).
    • 

  • Round complete, I am not in it: join the wait list if there is room (:930), else the redundancy list (:936). Running agents see a non-empty wait list at their next monitor tick and re-rendezvous (section 3).
    • 

  • Participant, count between min and max, deadline passed: mark the round complete. Ranks follow the sorted order of node descriptors (:833), strings <fqdn>_<pid>_<n> (:269): not arrival order, and since the sort is on text, pid 100 sorts before pid 11.
    • 

  • Heartbeat older than 5 s × 3 attempts (:1430, :1435, check :476): the node is dead, removed by whoever syncs next.
    • 

  • Join deadline passed (600 s by default, :144): give up with RendezvousTimeoutError. The dynamic backend reads join_timeout (:1385), not the launcher's timeout=900, so c10d jobs give up at 600 s while static ones wait 900 s (the parent's Launch lab measured 602 s and 903 s).
    •

About 43 s, and every part is a default. The agents saw their workers fail within 1 s and went back to the rendezvous; but C was still a participant of the completed round, so A and B could only join the wait list of the next round until C was declared dead, 13 s after the kill (heartbeats every 5 s, dead after 3 missed). What the c10d run shows: a node joining a running job costs a full restart of every worker (2.3 s here, from the agents noticing C to round 1 done at max_nodes), free in torchrun's accounting; losing a node costs heartbeat expiry plus a last call (13 + 30 s), with no error in the logs, only silence; and the ranks followed the sorted descriptors (here A, B, C happened to sort in arrival order, pids 11, 16, 31). Where the store lives. With c10d the agent whose host name matches --rdzv-endpoint hosts the store; when several agents share a machine, all try, one wins and the rest connect as clients (c10d_rendezvous_backend.py:154). That process is a single point of failure: the parent's Failure lab killed the agent hosting the store and the whole job died with "RendezvousConnectionError: The connection to the C10d store has failed", elastic or not. Put the endpoint on the node least likely to fail, or run the store outside the job (etcd-v2 backend, or a dedicated host).







5. The store between attempts: one variable decides whether a restart works


After the agents meet, the workers need a store too: init_process_group uses it to swap the addresses gloo or NCCL will connect to. In torch 2.14.1 the rank-0 agent starts a second TCPStore on a free port for the workers, kept for the life of the agent and reused by every later round (dynamic_rendezvous.py:1209-1217). The worker side assumes the opposite: "We create a new TCPStore for every retry so no need to add prefix for each attempt" (rendezvous.py:205). So after a restart the new workers find the old workers' keys still there, including each rank's old gloo address. TORCH_DISABLE_SHARE_RDZV_TCP_STORE=1 (:1146) turns the sharing off: each round's rank 0 builds a fresh store on a new port. The parent's Failure lab found that in-job restarts on two Slurm nodes failed with the default and worked with the variable set; this before/after shows why, from three recorded runs of the same crash, with a probe in every worker counting the store's keys before init_process_group.

Both shared runs failed, differently. In run 1 rank 1 connected at once to rank 0's old port and got "Connection refused", while rank 0 waited for a connection that could never come for 300 s, the c10d Store's default timeout (Store.hpp:21), not the 60 s process-group timeout the script passed (that this 300 s is the one gloo used is our reading; gloo's own source was not checked). In run 2 rank 0 read the stale address. Which rank loses the race is chance, which is why restarts with the default look flaky rather than broken; the sibling PyTorch page's "flaky elastic restarts" on one machine are consistent with it.


The same sharing breaks growing an elastic job
In the replay's "store shared" mode (section 4), C's arrival made the agents re-rendezvous into round 1. C, new, needed MASTER_ADDR from the round's keys (api.py:102); A, rank 0 again, already had its store server and skipped publishing it (the condition at dynamic_rendezvous.py:1209). All three agents waited on keys nobody would write, and all three failed 61.5 s later on the c10d store's 60 s read timeout: "wait timeout after 60000ms, keys: /torch.rendezvous.ld-el.1/MASTER_ADDR". With the variable set the same arrival cost 2.3 s. For any job with --max-restarts above 0 or an elastic node range, set TORCH_DISABLE_SHARE_RDZV_TCP_STORE=1 on torch 2.14.1 (whether this is reported upstream was not checked).






6. Building the communicator: gloo here, NCCL on GPUs


init_process_group takes the store from the rendezvous (env:// means MASTER_ADDR:MASTER_PORT), wraps it in a prefix so different groups never collide (default_pg, distributed_c10d.py:2551), and asks a backend to build the communicator. gloo (what ran here) builds everything inside init_process_group: each rank writes its listening address under a key, reads every other rank's, and connects to all of them, a full mesh of TCP connections (ProcessGroupGloo.cpp:697). It is eager and fails early: a wrong address shows up as "Gloo connectFullMesh failed" before step 1. The parent's Launch lab measured this step at a median of 9 ms on Slurm with every rank already waiting.


NCCL is lazy and has its own bootstrap. Read from source at v2.30.7-1, the version torch 2.14.1's Linux wheel pins as nvidia-nccl-cu13==2.30.7 on PyPI; not run here, nothing here has a GPU. Step through it on the same 2 × 2 job:

  1. Nothing happens in init_process_group unless you pass device_id=, which makes PyTorch connect eagerly (ProcessGroupNCCL.cpp:1089). By default the communicator is built at the first collective, which for DDP is the parameter broadcast inside the DDP constructor. So "hangs at init" often means "hangs in the DDP constructor".

  2. Rank 0 makes a unique id: a random 64-bit "magic" plus the address of a listening bootstrap root socket on the one interface NCCL picked for bootstrap (bootstrap.cc:430, interface choice :124). NCCL_COMM_ID=host:port replaces it with a fixed address (:441).
    3. 

  3. PyTorch hands the id to everyone through the c10d store (rank 0 sets key "0", "1", ... per communicator, ProcessGroupNCCL.cpp:2913).     4. 

  4. Bootstrap ring (bootstrapInit, init.cc:1916): every rank opens listening sockets and sends its address to the root; the root tells each rank who its next neighbour is; the ranks connect in a ring and pass everyone's addresses around it. Above 256 ranks the connections to the root are staggered at 7,000 messages per second (bootstrap.cc:669; documented as NCCL_UID_STAGGER_THRESHOLD and _RATE). All of this is plain TCP on the bootstrap interface, the front-end network (sibling page Cluster anatomy: "NCCL's bootstrap uses the front-end").
    5. 

  5. Peer information is all-gathered over the bootstrap ring (AllGather1, init.cc:1034): host hashes, GPU bus ids, which ranks share a machine.
    6. 

  6. Topology: each rank reads its machine's PCI tree, NVLink and NICs into a graph (ncclTopoGetSystem, init.cc:1141; NCCL_TOPO_DUMP_FILE writes it as XML) and searches it for rings (:1178), trees (:1186), CollNet and NVLS patterns; the ranks agree on one plan.
    7. 

  7. Network plugin: InfiniBand or RoCE through verbs if any device is found, otherwise TCP sockets ("Using network %s", init.cc:486; force one with NCCL_NET, :2117). No RDMA device prints NET/IB : No device found. (net_ib/init.cc:470) and NCCL carries on over sockets, much slower and without an error (sibling page Cluster anatomy covers the cluster side of that fallback).
    8. 

  8. Connections between peers are made when a collective first needs them: NCCL_RUNTIME_CONNECT defaults to 1 (init.cc:61). A communicator can initialise cleanly and the first all-reduce hang because a peer's data network is unreachable.

Which interface does NCCL pick?


Most "NCCL hangs at init" are the bootstrap or the socket transport choosing an interface the other nodes cannot reach. The rule, from ncclFindInterfaces (socket.cc:190-232) and the matcher (os/linux.cc:379): if NCCL_SOCKET_IFNAME is set, use the interfaces it names (prefixes; ^ excludes, = means exact); otherwise try names starting with ib (:206), then an interface in the same subnet as NCCL_COMM_ID, then anything not starting with docker, lo or virbr (:220), then docker, then lo. Only interfaces that are up and running count (linux.cc:402), in the kernel's order; bootstrap takes the first one, the socket transport up to 16 (net_socket.cc:59, socket.h:25). Below, that rule applied by this page's script to the real interface lists of two containers on this machine. rule from source, applied here; NCCL itself not run












On the host network (how Slurm containers, pyxis/enroot and Kubernetes hostNetwork: true pods see the machine) the default rule happily takes Docker's bridges and veth pairs: harmless for bootstrap here, because eth0 comes first in the kernel's list, but the socket transport would spread traffic over interfaces no other node can reach. One explicit NCCL_SOCKET_IFNAME per cluster, put in the job template, removes the guess.


Two variables worth setting on purpose: NCCL_NET=IB makes a missing RDMA device an error instead of a silent fallback to sockets, and NCCL_RUNTIME_CONNECT=0 makes a network problem fail at init rather than at the first collective. PyTorch's NCCL switches (TORCH_NCCL_ASYNC_ERROR_HANDLING, which torchrun sets to 1 unless you set it, local_elastic_agent.py:439; TORCH_NCCL_DUMP_ON_TIMEOUT; TORCH_NCCL_HEARTBEAT_TIMEOUT_SEC) and the debugging variables (NCCL_DEBUG, NCCL_DEBUG_SUBSYS, NCCL_DEBUG_FILE, NCCL_IB_HCA, NCCL_IB_DISABLE, NCCL_P2P_DISABLE, NCCL_NET_GDR_LEVEL, NCCL_TOPO_DUMP_FILE) are in the parent's Launch lab; the NCCL API (ncclGetUniqueId, ncclCommInitRank, ordering rules) is on Streams, CUDA graphs and multi-GPU programming.


A job hangs at start-up or on its first big collective: the network causes, in the order to check
    

  1. Wrong interface. NCCL picked docker0, a loopback or a management NIC (the rule above): NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NET prints the choice; set NCCL_SOCKET_IFNAME, and GLOO_SOCKET_IFNAME for gloo, a separate variable that NCCL's setting does not cover (PyTorch distributed docs).
    2. 

  2. Firewall or security group. Only MASTER_PORT (29500 unless set) has a fixed number; NCCL's reference names no fixed port range for its own sockets, so opening one port between nodes is not enough. A silent hang in init_process_group is usually a dropped SYN.
    3. 

  3. MTU mismatch between nodes: the handshake and small messages pass, the first full-size packet is dropped and the first large collective hangs. Prove it with don't-fragment pings of increasing size.
    4. 

  4. Silent socket fallback. No RDMA device inside the container (or NCCL_IB_DISABLE=1 left in a template) and NCCL runs over TCP sockets: the job does not hang, it crawls; the log says "Using network Socket". NCCL_NET=IB turns it into an error.
    5. 

  5. Accept queue or file descriptors at the rendezvous rank when thousands of ranks connect at once.
    6. 

  6. Not the network at all. One straggler rank (a slow GPU, a data-loading stall) makes every other rank wait inside the collective, which looks exactly like a network hang; section 8 finds it.
    7. 

Why each happens at the TCP and IP layer (the SYN that is never answered, path MTU discovery and its black holes, the accept queue, the 16 TCP connections per peer NCCL opens when it falls back to sockets) is Networking foundations, sections 3, 8, 10 and 14.

7. Every timeout on the way, on one axis


Each link of section 1 has its own clock, set by different teams for different reasons, from 15 seconds to 30 minutes. Knowing them turns "it hung for ten minutes" into a diagnosis: the length of the silence names the link.


The silence names the link: default timeouts (bars, log scale) and when the error really appeared (dots)


Defaults from the linked source lines (torch 2.14.1, Ray 2.59.0, NCCL v2.30.7-1): c10d dead node 15 s (5 s × 3 heartbeats), last call 30 s, Ray Train worker-group start 60 s (retried forever), c10d store client read 60 s, c10d Store default 300 s, agent exit barrier 300 s, c10d join 600 s, NCCL process group 600 s, static rendezvous via torchrun 900 s, gloo and default process group 1800 s, Ray Train TorchConfig timeout_s 1800 s. Dots: measured on Apple M1 Pro, Docker Desktop VM, shared machine, on this page or its parent; deterministic up to a second or two.


The defaults are long and uneven: a c10d job with a missing node fails in 10 minutes, the same job on the static backend in 15, an NCCL collective in 10 and a gloo one in 30, and Ray Train never fails at all. Set them on purpose, each a little longer than the slowest legitimate wait at that link: --rdzv-conf join_timeout=... (image pulls and node boot), init_process_group(timeout=...) (the longest gap between collectives, often a checkpoint save or an evaluation on rank 0 alone), the scheduler's own limit above both. A shorter timeout is not free: it trades waiting for false alarms, and every false alarm is a restart (section 3) costing a rendezvous and a cold start on every node.






8. Debugging a hang: find the one rank that is different


A hang in a collective job is almost always one rank doing something else while all the others wait for it in a collective. The waiting ranks look identical and tell you nothing; the work is finding the odd one and seeing what it is doing. Two questions sort every case: did it hang before the first step or during training? (before: a link of section 1; during: a collective mismatch, a dead or stuck rank, or the network) and are all ranks stuck in the same place? The rule behind training-time hangs (every rank calls the same collectives, in the same order, with matching sizes) and the flight recorder that checks it are owned by Distributed PyTorch, section 11; here are four real hangs met the way you meet them.


The running example's model, data and optimiser in its training loop with one classic distributed bug injected at step 5, 4 ranks under torchrun in one container, process-group timeout 60 s (src/scripts/ld_hang.py, ld_hang.sh). At 25 s, if the job was still alive, py-spy dump read every rank's stack from outside (the container had CAP_SYS_PTRACE, not --privileged); a watchdog thread inside each rank also wrote its own stacks and flight recorder after 20 s without a step. Pick a case, read the logs, diagnose, then reveal the stacks.










All measured on Apple M1 Pro, Docker Desktop VM, shared machine, torch 2.14.1+cpu, gloo. Times are seconds since the processes finished init_process_group; addresses scrubbed. The timeouts and messages are what matter, not the seconds.

The pattern: a collective on one rank only aborts that rank at once (gloo's size check); different shapes and a rank stuck in user code both give silence until the 60 s process-group timeout, and only stacks or the flight recorder name the odd rank (in the stuck case rank 1 issued 15 collectives and the others 16: "missing ranks: {1}"); uneven batches look like a crash ("Connection closed by peer ... typically caused by a remote worker crashing") 0.4 to 0.9 s later although the short rank exited 0. An in-process watchdog is the tool that scales: when no step completes for N seconds, a daemon thread writes every thread's stack (faulthandler) and the flight recorder (torch._C._distributed_c10d._dump_fr_trace(), a pickle) to files, before any timeout kills the evidence. It needs no ptrace and runs on every rank at once, which is what a 1,000-rank job needs; it is about twenty lines of src/scripts/ld_hang.py, and on the stuck case all four ranks dumped 20.5 to 20.6 s after their last step.

Interview rehearsal: seven questions with answers (optional)


What does torchrun do that srun python train.py does not?
It rendezvous between nodes (so ranks are not fixed in advance and nodes can come and go within a range), starts and watches one worker per GPU, sets the PyTorch variables, and restarts the whole group on failure up to --max-restarts. srun alone gives each task SLURM_PROCID and friends; your script maps them to RANK and WORLD_SIZE, and a failure is handled by Slurm (requeue), not in place.


Static or c10d rendezvous: when do you pick which?
Static when the scheduler already gives every node a stable index and address (JobSet's completion index and pod DNS name, Slurm's node list) and you do not need in-job restarts across nodes: no negotiation, nothing to time out except the 900 s wait. c10d when you want elastic ranges, restarts that can re-form the group, or hosts you do not know in advance; you pay a last-call wait (30 s) and depend on the store host staying up.


A 64-node job sits silent for exactly 10 minutes, then fails with an empty RendezvousTimeoutError. What happened?
The c10d join timeout (600 s) expired before all agents joined: at least one node's agent never reached the store. Look at which nodes' logs are empty (the missing ones), then why: image pull, node boot, a wrong endpoint or DNS on that node. 15 minutes and "1/64 clients joined" would point at the static backend instead.


How does NCCL find its peers, and what is the most common reason it hangs at init?
Rank 0 creates a unique id containing the address of a bootstrap socket; PyTorch passes it to every rank through the c10d store; ranks connect to that root, form a ring over TCP and exchange addresses and topology, then build rings and trees and connect lazily. The usual hang is the bootstrap or socket transport choosing an interface other nodes cannot reach (a bridge, a management NIC): set NCCL_SOCKET_IFNAME and read NCCL_DEBUG=INFO's "Bootstrap: Using" line.


All 512 ranks are stuck. How do you find the cause in five minutes?
Do not read 512 identical stacks: compare. Flight-recorder dumps (or a watchdog that writes them) give each rank's last collective sequence number; the rank with a lower number, or none, is the odd one; its py-spy or faulthandler stack names the line. If every rank is at the same collective and sequence, suspect the network or a GPU (NCCL_DEBUG, the kernel log), not your code.


Which timeouts would you set for a job whose rank 0 spends 20 minutes writing a checkpoint while the others wait?
The process-group timeout must exceed the longest gap between collectives, so more than 20 minutes (NCCL's default of 10 would kill the job; gloo's 30 would not). Better: make the save asynchronous or shard it so all ranks take part, and keep the timeout tight enough to catch real hangs.


Design: the launch layer for a 1,000-GPU lab (125 nodes of 8 GPUs). What do you standardise?
One image per release, pre-pulled or cached on every node (start-up waits for the slowest node). One launcher pattern: the scheduler (Slurm or JobSet) starts one torchrun per node with c10d rendezvous on a stable endpoint, explicit join, last-call and process-group timeouts, --max-restarts plus a checkpoint resume, and TORCH_DISABLE_SHARE_RDZV_TCP_STORE=1 while the store-sharing problem stands. A job template that fixes NCCL_SOCKET_IFNAME, NCCL_IB_HCA, NCCL_NET=IB (fail instead of falling back), shared memory and memlock, flight recorder and dump-on-timeout, and an in-process hang watchdog writing stacks to shared storage. A pre-job health check per node (GPU, NVLink, NIC, a two-node NCCL test on new nodes) so bad nodes never join a rendezvous. Hot spares registered with the scheduler, so a failed node is replaced by a requeue rather than a shrink. And dashboards for the start-up stages of section 1, because at this size start-up and restart time are a measurable share of goodput (sibling page Fault tolerance at scale).
