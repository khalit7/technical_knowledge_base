The problem. Three different numbers are all called GPU utilisation: the share of GPUs allocated to jobs, the share of time any kernel ran, and the share of SMs with work. Each is an upper bound on the next, and published fleets show how far apart they sit. Before the table, guess.

5. MFU and HFU in the training loop

The problem. The only counter of useful work is the job's own: tokens processed per second, turned into FLOPs and divided by the peak. How it works: model FLOPs per step = 6 x parameters x tokens in the step (plus an attention term at long context); MFU = model FLOPs per step / (step time x GPUs x peak FLOP/s). HFU uses the FLOPs the hardware actually ran, including activation recomputation, so it rises when you recompute and is not comparable across runs. The arithmetic, its conventions and published values are on {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}; here is how to log it, done on the running example.

# in the training loop: time a step the way the hardware sees it
t0 = time.perf_counter()
loss = model(x).loss; loss.backward(); opt.step(); opt.zero_grad()
torch.cuda.synchronize()        # on a GPU: or the clock stops before the kernels finish
dt = time.perf_counter() - t0
flops = 6 * n_params * tokens_per_step          # + 12 * layers * ctx * d_model * tokens at long context
mfu = flops / (dt * world_size * PEAK_FLOPS)    # PEAK: dense BF16 datasheet value, never the sparse one
log({"step": step, "tokens_per_s": tokens_per_step / dt, "mfu": mfu})

Measured here (src/scripts/oc_mfu.py, one process, one thread, in the mi-train:1 container capped at 1 CPU, 3 runs): the "peak" is a 1,024 x 1,024 fp32 matrix multiply on that core, because a container's CPU share has no datasheet. measured on Apple M1 Pro, Docker Desktop VM, shared machine.

What transfers: the method, and the fact that the convention changes the number (here attention adds about 15% to the FLOPs at context 64). What does not: the value; a 112,577-parameter model on one CPU core says nothing about an H100. Published values for real runs: Llama 3 405B 38% to 43% BF16 MFU ({{Llama 3, sec. 3.3.2|https://arxiv.org/html/2407.21783v3}}, operator); ByteDance MegaScale 55.2% on 12,288 GPUs for a 175B model ({{MegaScale|https://arxiv.org/html/2402.15627v1}}, operator of its own system).

Four ways to log a wrong MFU
Timing without synchronising (the CPU clock stops before the GPU finishes, MFU too high). Dividing by the 2:4-sparse peak (twice the dense one, MFU half what it should be). Counting padding tokens as tokens. Averaging over a window that includes evaluation, checkpoint saves or the first step's compilation, which then hides as "low MFU" instead of showing as badput.
