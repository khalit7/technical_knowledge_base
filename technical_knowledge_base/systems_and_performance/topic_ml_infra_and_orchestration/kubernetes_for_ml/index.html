The idea in one screen

Kubernetes places one pod at a time, ranks nodes by CPU and memory and treats every pod failure on its own, so a multi-node GPU training job needs add-ons that count and attach GPUs (device plugins, DRA), admit the whole job at once (Kueue, PodGroups) and restart it as one unit (JobSet, operators, LeaderWorkerSet for serving).

One training job is a chain of objects; each controller watches one and writes the next

Read top to bottom: you write only the top object. Every box is an object stored by the API server (in etcd); every arrow is a different program that watches the box above and writes the box below; nobody calls anybody. Three surprises this page measures

(1) The default scheduler does not look at GPUs when it ranks nodes: it ranks by CPU and memory only, so it scatters small GPU jobs and can leave no node with 4 free GPUs (section 3). (2) A rank that exits with code 13 makes its pod exit with code 1, because torchrun is the container's main process, so a Job failure rule on code 13 never fires (section 2). (3) Kubernetes v1.37 ships native gang scheduling, but behind a feature gate that is off by default (section 7).

1. The control loop: who does what

Everything is an object with a spec (what you want) and a status (what is true now), stored in etcd. Only the API server talks to etcd: it validates each write, runs admission webhooks (external programs that may change or refuse an object), stores it and streams the change to everyone watching. The job controller (in kube-controller-manager) writes pods for Jobs; the scheduler writes a node name into each pod that has none; the kubelet on each node starts the pods bound to it and writes their status. Step through one job below, then switch layers: each layer you add is one more controller in the chain.

Field managers, scale limits and how to check (depth)

Every write bumps the object's resourceVersion and is attributed to a field manager (kubectl, kube-controller-manager, kubelet), which is how the animation knows who did what. In the recorded run the pod's field managers are only kube-controller-manager (it created the pod) and kubelet (status): the binding write is not recorded as a field manager. A hand-set nodeName is how DaemonSets and static pods used to work.

The cost. Every object and every watch costs API server memory. On this cluster the control plane runs in 1.6 GB, and in the parent's Scheduling lab the API server restarted once at 1.27 GB under load. Installing Kubeflow Trainer's three custom resource definitions (2.4 MB of YAML, mostly embedded JobSet and pod schemas) raised the control plane's memory from 1.04 to 1.25 GiB measured. Kubernetes v1.37 is designed for at most 5,000 nodes, 110 pods per node, 150,000 pods and 300,000 containers (Considerations for large clusters docs, read 2026-10-16); training clusters hit the node and watch limits long before the pod limit, since they run about one pod per node.

How to check. kubectl get events -n NS --sort-by=.metadata.creationTimestamp shows who did what; kubectl get pod P -o yaml --show-managed-fields shows the field managers; kubectl get --raw /metrics on the API server and the controllers' logs show the rest.

2. Pods and Jobs: a training job with no add-ons

A Job (batch/v1) creates pods until enough have succeeded (completions of them, parallelism at a time). With completionMode: Indexed each pod gets an index 0..N-1 in JOB_COMPLETION_INDEX and the hostname <job>-<index>; a headless Service (clusterIP: None, DNS records only) whose name matches the pods' subdomain makes each resolvable as <job>-<index>.<service>. That is all torchrun needs: node rank from the index, rendezvous address from pod 0's name. The running example ran this way unchanged.

When a pod fails, the job controller retries, fails the Job or ignores the failure, by these knobs:

  • backoffLimit: how many failed pods the Job tolerates (default 6); retries wait 10 s, doubling per failure, capped at 10 minutes.
  • podFailurePolicy: rules matched in order on a failed pod's exit codes or conditions, with actions FailJob, Ignore, Count (the default) and FailIndex. Not allowed with restartPolicy: OnFailure, where the kubelet restarts the container in place and the Job never sees a failed pod.
  • backoffLimitPerIndex (with maxFailedIndexes) and successPolicy: a budget per index for independent shards; success declared early, for example when the leader index succeeds.

Choosing a rule on exit code 1 is a trade-off

Code 1 is what torchrun returns for any failed worker in these runs, including ones you want retried (a lost peer, a NCCL timeout). A rule FailJob on 1 stops wasting GPUs on a deterministic bug but also gives up on transient failures. Alternatives: have the training script write the root cause somewhere a wrapper can read and exit with its own code (torchrun records it in the file named by TORCHELASTIC_ERROR_FILE when the script's entry point is decorated with @record: PyTorch elastic errors docs, the page the log itself points to); or launch one process per pod without torchrun, so the script's exit code is the container's.

Did the resumed run train the same model? Almost: after resuming from step 50 with 4 ranks, the global loss matched the uninterrupted run at most logged steps and differed by 2.4e-7 (one float32 rounding step) at steps 70, 180 and 200. This is the DDP gradient-bucket rebuild effect the root's Failure lab identified (there after a resume at step 100); the steps that differ depend on where the run resumed.

Two smaller lessons from the shard runs. With backoffLimitPerIndex: 1, the broken shard (index 2) was retried after 9.7 s and the Job failed with FailedIndexes while indexes 0, 1 and 3 completed (e4a). With successPolicy on index 0 (e4b), the Job reached SuccessCriteriaMet at 8.1 s but Complete only at 39.3 s: the two workers ran sleep as their main process, which ignores SIGTERM, so they were killed after the default 30 s grace period (exit 137). A training container whose main process ignores SIGTERM also loses the chance to write a last checkpoint on preemption.

3. The scheduler: filter, score, bind

kube-scheduler takes one unbound pod per scheduling cycle (from a queue sorted by priority, then age). Filter plugins reject nodes that cannot run it (too few free GPUs, an untolerated taint, a label or volume mismatch); Score plugins give each remaining node 0 to 100, multiplied by the plugin's weight and summed; the highest total wins (ties broken at random) and a separate binding cycle writes the Binding. For a web service "good" means spread out; for training it usually means packed, so whole nodes stay free for the next big job.

The trap. NodeResourcesFit's default scoring strategy, LeastAllocated, prefers the emptiest node but counts only the resources it lists, and the default list is CPU and memory. A GPU is used to filter but never to rank unless you list it. The alternative, MostAllocated, prefers the fullest node: bin packing.

When it matters, and the cost

It matters on a cluster that mixes 1- and 2-GPU jobs (notebooks, evaluation, small fine-tunes) with 8-GPU jobs: spreading fragments the nodes and the large jobs starve while the GPU allocation looks fine. Bin packing costs some resilience (one node failure kills more small jobs) and concentrates heat; the usual answers are separate node pools, a second scheduler profile (the scheduler config is a control-plane setting a managed cluster may not expose), or a scheduler (Volcano, KAI) or Kueue topology placement that packs by design.

4. GPUs as resources: extended resources, device plugins, the GPU Operator and DRA

Kubernetes knows CPU and memory natively. A GPU is a device on one node: the scheduler must count them, and the kubelet must give a container the right device files, driver libraries and environment for the specific GPUs it got. There are three levels of help.

Extended resources: counting only. Any resource name with a domain (nvidia.com/gpu, example.com/gpu) in a node's status.capacity. Pods request whole numbers, the scheduler subtracts, and nothing is attached to the container; it cannot be overcommitted (a limit, if given, must equal the request) (Extended resources docs). This topic's cluster has no GPUs, so its setup wrote example.com/gpu: 4 into each worker's status by hand: every GPU number on this page is that counter.

Device plugins: counting plus attaching. A device plugin is a small gRPC server, usually a DaemonSet pod on every GPU node, that calls the kubelet's Register; the kubelet then streams ListAndWatch (device IDs and health), may ask GetPreferredAllocation (so the plugin can pick GPUs that share an NVLink or PCIe switch) and calls Allocate once per container, whose answer lists device files, mounts, environment variables or CDI device names. The scheduler picks the node; the kubelet picks which GPUs.

The NVIDIA GPU Operator is how that stack usually arrives: an operator that runs as containers on each GPU node "the NVIDIA drivers (to enable CUDA), Kubernetes device plugin for GPUs, the NVIDIA Container Runtime, automatic node labelling, DCGM based monitoring and others" (NVIDIA/gpu-operator README at v26.7.2, released 2026-10-14 vendor), so GPU nodes can boot the same OS image as CPU nodes. NVIDIA's device plugin advertises nvidia.com/gpu and can split GPUs by MIG or share them by time-slicing or MPS; MIG itself is on Virtualization and the GPU driver stack, and DCGM's metrics on Observability and cost.

DRA: described devices. Dynamic Resource Allocation (resource.k8s.io/v1, GA in v1.34) replaces "a count of opaque units" with structured devices. A DRA driver publishes ResourceSlices (each device with attributes such as model, memory, NUMA node, PCIe root); an admin defines DeviceClasses (a CEL selector); a pod references a ResourceClaim asking for, say, exactly 2 devices of a class with at least 80Gi. The scheduler allocates the exact devices while it picks the node, and the kubelet then asks the node's driver to prepare them.

5. Multi-node networking: getting the RDMA NIC into the pod

A pod normally has one interface, eth0, on the cluster's pod network (made by the cluster's CNI plugin: an overlay or routed network over TCP). That is enough for DNS and torchrun's rendezvous, but NCCL's all-reduce between nodes wants the RDMA fabric (InfiniBand or RoCE, usually one 400 Gb/s card per GPU: Cluster anatomy). With no RDMA device in the container NCCL prints NET/IB : No device found. and carries on over sockets, much slower and without an error (Launching distributed training). Two things must be added to the pod: the RDMA device and a network interface on the fabric.

A training pod with two networks: the pod network for names, the RDMA fabric for NCCL

The GPUs come from the GPU device plugin (section 4); the RDMA device from a second device plugin (the RDMA shared device plugin, or the SR-IOV network device plugin, which hands each pod its own virtual function of the NIC); the second interface, net1, from Multus, a CNI "meta-plugin" that calls further CNI plugins for each network the pod's annotation k8s.v1.cni.cncf.io/networks names (a NetworkAttachmentDefinition object) (Multus CNI v4.3.1 docs). Not run here: the kind cluster has no RDMA hardware.

  • The simple way: hostNetwork: true. The pod sees every host interface, RDMA NICs included; it gives up network isolation and port separation between pods, which is acceptable on nodes that run one training pod each.
  • The managed way: the NVIDIA Network Operator (v26.7.1, 2026-10-16 vendor), the networking counterpart of the GPU Operator. Its NicClusterPolicy installs the NIC driver container, the RDMA shared device plugin or the SR-IOV network device plugin, Multus and the secondary-network CNI plugins (macvlan, host-device, IP over InfiniBand) and an IP address manager, so that "RDMA and GPUDirect RDMA workloads" run in the cluster (Mellanox/network-operator README vendor). A pod then requests, next to nvidia.com/gpu: 8, a resource such as rdma/hca_shared_devices_a: 1 (the plugin's example name) and names the secondary network in its annotation.
  • How to check: inside the pod, ibv_devices lists the RDMA devices and ip addr shows net1; with NCCL_DEBUG=INFO the log must say NET/IB, not NET/Socket; set NCCL_NET=IB to turn a silent fallback into an error.

The fabric itself (InfiniBand against RoCE, rails, GPUDirect RDMA) is on Interconnects and scaling; NCCL's variables on Launching distributed training. 6. Placement controls: affinity, taints, spread, priority and preemption

Training pods only on GPU nodes, everything else kept off them, a job's pods close together, important jobs able to take GPUs from unimportant ones: four controls do it.

  • nodeSelector and node affinity: node labels the pod requires (requiredDuringSchedulingIgnoredDuringExecution, a Filter) or prefers (preferred..., a Score). Kueue's flavors (section 8) add one for you.
  • Taints and tolerations: a node's taint repels every pod that does not tolerate it. GPU pools are usually tainted (for example nvidia.com/gpu=present:NoSchedule) so only training pods and the device plugin DaemonSet land there. NoExecute also evicts running pods; the node lifecycle controller adds node.kubernetes.io/unreachable this way when a node goes silent (the root's Failure lab measures it).
  • topologySpreadConstraints: keep the count of matching pods per topology domain (nodes sharing a label value, such as a zone or this cluster's block mi.example.com/block) within maxSkew.
  • Pod affinity and anti-affinity: place a pod near (or away from) pods with given labels in a domain. JobSet's exclusive placement (section 9) is built from these.

Priority and preemption. A PriorityClass maps a name to an integer. Higher-priority pods go first in the queue, and when nothing fits, the default PostFilter plugin looks for a node where evicting lower-priority pods makes room (preemption). The victims get the DisruptionTarget condition (reason PreemptionByScheduler), SIGTERM and their grace period; the preemptor waits with status.nominatedNodeName set. preemptionPolicy: Never keeps the queue priority but never evicts.

Cost and when it matters. The scheduler preempts pods, not jobs: evicting one pod of a 64-pod training job kills all 64 (section 2), and it will happily preempt a pod 3 minutes from a checkpoint. That is why training clusters move preemption up a level: Kueue preempts whole workloads by priority or to reclaim quota (the parent's Scheduling lab shows the reclaim), and the native PodGroup has a disruptionMode (single or all) for exactly this. A PodDisruptionBudget limits voluntary evictions (drains), but not preemption by priority beyond a best effort.

7. Gang scheduling: every pod or none

The scheduler places one pod per cycle and knows nothing of the job it belongs to. Two jobs that each need the whole cluster can each get half, and wait forever for the other half: a partial-placement deadlock. The parent's Scheduling lab produced exactly that on this cluster and fixed it with Kueue. A gang is a set of pods that must start together; gang scheduling binds all of them or none. Kubernetes v1.37 has it built in, behind a gate: a PodGroup object with gang.minCount, and a GangScheduling plugin that holds a group's pods at PreEnqueue until minCount exist and at Permit until minCount are placed. This page switched the gate on for one run, on the parent's deadlock input:

Without the gang, a0, b0 and c0 each took a worker and the other three waited: every job half placed, none able to run. With the PodGroups, a0 was held at PreEnqueue (waiting for minCount pods from a gang to appear in scheduling queue); when a1 arrived both were placed and released together (Quorum is met for a gang. Allowing other pods from a gang waiting on permit); gangs b and c were refused as a whole (minCount (2) cannot be satisfied: 1 scheduled, 0 remaining) and ran one after another as the GPUs freed up.

Which one to use. Native gangs fix the deadlock but have no notion of quota or queues: a big job still waits behind whatever arrives first, and two teams still race. Kueue gives queues and quotas and works with the default scheduler today (and its admission can lag behind real placement: an admitted workload can still find a node broken, which waitForPodsReady, default timeout 30 minutes in v0.20 per apis/config/v1beta2/defaults.go line 48, handles by evicting and requeueing it). Volcano and KAI replace the scheduler and give both, at the cost of running a second scheduler you must trust with every GPU pod.

Beyond Kueue and the native PodGroup, three batch schedulers replace kube-scheduler for GPU pods and do gangs, queues and fair share inside it: Volcano (CNCF), KAI Scheduler (NVIDIA, from Run:ai) and YuniKorn; the older coscheduling plugin is a second scheduler build with a PodGroup CRD (what OpenAI used on its 7,500-node cluster); LeaderWorkerSet gangs each serving group (section 11).

8. Kueue: quota, flavors, topology

Several teams share a fixed pool of GPUs. Each needs a guaranteed share, idle shares should be usable by others, jobs should wait in an orderly queue rather than as Pending pods, and a 16-GPU job should get 16 GPUs that are close together. Kueue is a controller plus webhooks with six kinds of object (all kueue.x-k8s.io/v1beta2; v0.20 no longer serves v1beta1):

ResourceFlavorA kind of capacity, mapped to nodes by labels (and tolerations): "H100 in block 1", "spot A100". Optional topologyName for topology-aware placement.
ClusterQueueA team's quota: for each flavor and resource a nominalQuota (plus borrowingLimit, lendingLimit), a queueing strategy, preemption rules, and the cohort it shares with.
LocalQueueA namespace's door into a ClusterQueue. Jobs say kueue.x-k8s.io/queue-name: <localqueue>.
WorkloadKueue's record of one job: its pod sets (count and requests per pod), created by Kueue's integration for Jobs, JobSets, TrainJobs, RayJobs and others. Admission is a property of the Workload.
CohortA group of ClusterQueues that lend each other unused quota; cohorts can form a tree.
TopologyAn ordered list of node labels (block, rack, host) for topology-aware scheduling.

Admission, step by step. A labelled job is made to start suspended (spec.suspend: true: no pods). Kueue's loop takes the head of each queue, assigns flavors (the flavors in order, checking the workload's total request against unused quota, borrowing and preemption), reserves the quota, runs any admission checks (for example a ProvisioningRequest that asks the cluster autoscaler for nodes first), then admits: it writes the chosen flavors into the Workload, injects the flavor's node labels as a nodeSelector and unsuspends the job. From there the normal scheduler places pods. The parent's Scheduling lab shows queueing and cohort borrowing and reclaim; here are the two things it did not run, one decision per step.

11. Serving on Kubernetes: Deployments, LeaderWorkerSet, KServe and the vLLM production stack

Serving replicas run for months, scale with traffic and are updated while serving. A model that fits on one node is an ordinary Deployment: each replica is one pod (say one vLLM server on 8 GPUs), scaled by changing replicas and rolled pod by pod. A model sharded across nodes (pipeline or tensor parallel over 2 or more nodes) breaks that: a replica is now several pods that must be created together, find a leader, fail together and be upgraded together. A Deployment would roll one shard of a replica at a time and leave half-updated groups.

The unit of scaling changes from a pod to a group

Top: a Deployment of four single-node replicas, each pod independent (one fails, one is replaced). Bottom: a LeaderWorkerSet with replicas: 2 and size: 4, eight pods in two groups, each a leader (L) and 3 workers (W); the group is what is created, scaled, restarted and rolled.

LeaderWorkerSet (LWS, kubernetes-sigs, v1.0.0 released 2026-10-16) is the API for that group. Its README: "a group of pods as a unit of replication", with one template for the leader and one for the workers, a unique index 0 to n-1 per pod, rolling update "at the group level", a scale subresource for the HPA that counts groups, opt-in topology placement of a group, gang scheduling of each group (alpha), and "all-or-nothing restart" (kubernetes-sigs/lws docs). In the API (api/leaderworkerset/v1/leaderworkerset_types.go at v1.0.0 source) size is the number of pods per group (default 1, line 403), the default restartPolicy is RecreateGroupOnPodRestart (line 408: one pod's failure recreates the whole group, the serving cousin of JobSet's restart-everything), and every container gets LWS_LEADER_ADDRESS, LWS_GROUP_SIZE and LWS_WORKER_INDEX (lines 82-90), the serving equivalent of torchrun's master address, world size and rank.

KServe (v0.21.0, 2026-09-25) is the operator one level up. Its LLMInferenceService (serving.kserve.io/v1alpha2) takes a model URI and a parallelism block; its controller writes a Deployment for a single-node model and a LeaderWorkerSet for a multi-node one, with size set from the pipeline (or data) parallel degree, restartPolicy: RecreateGroupOnPodRestart and startupPolicy: LeaderCreated (pkg/controller/v1alpha2/llmisvc/workload_multi_node.go lines 167-191 and workload_single_node.go line 118 at v0.21.0 source), plus prefill and decode workloads when the two phases are split, and routing through the Gateway API Inference Extension (a dependency in its go.mod). The classic InferenceService runs on Knative (scale to zero, canaries) or, in the lighter install, as plain Deployments.

The vLLM production stack (Helm chart vllm-stack-0.1.13, 2026-09-29) is the minimal alternative: one Helm release with three parts, "Serving engine" (vLLM Deployments), "Request router" ("based on routing keys or session IDs to maximize KV cache reuse") and an "Observability stack" (Prometheus and Grafana) (vllm-project/production-stack README docs). llm-d, which co-designs LWS according to the LWS README, is the larger option.

What this page does not teach: how the router scores replicas, how autoscaling on queue length works and how KServe hands it to KEDA are on LLM serving in production; disaggregated prefill and decode, Dynamo and llm-d as systems on Distributed and disaggregated serving; vLLM itself on its own page. Not run here: LWS and KServe need a model server and GPUs to show anything a kind cluster could.

12. Storage for training pods: volumes, claims and CSI

Checkpoints and datasets must outlive pods and be reachable from whichever node the restarted pod lands on. A pod mounts volumes. A PersistentVolumeClaim (PVC) asks for storage by size and access mode (ReadWriteOnce: one node; ReadWriteMany: many nodes; ReadOnlyMany); a StorageClass says which provisioner creates the PersistentVolume (PV) and when; a CSI driver (Container Storage Interface) is the plugin that attaches and mounts it on a node. For training the usual choices are a shared file system through CSI (Lustre, GPFS, Weka, NFS, Filestore, FSx: ReadWriteMany), object storage read by the job itself, and local NVMe for caches. kind's default StorageClass is rancher.io/local-path: a folder on one node's disk, with volumeBindingMode: WaitForFirstConsumer.

The claim stayed Pending (waiting for first consumer to be created before binding) until the writer pod was scheduled; the volume was then created on that pod's node and got a node affinity to it. A pod on any other node is unschedulable: 1 node(s) didn't match PersistentVolume's node affinity. If the checkpoint of a training job lives on such a volume, a restart after a node failure cannot run anywhere else; and if that node is gone, the checkpoint is gone too. Use node-local volumes for caches, not for state the job must resume from. Storage systems themselves are the Storage and data movement sibling's subject and the parent's Storage lab measures checkpoint writes on this cluster (the host folder these pods mount was 36 times slower than a Docker volume there).


Images are storage too: a pod on a fresh node first pulls the training image: Trainer's default torch runtime image, pytorch/pytorch:2.13.0-cuda13.0-cudnn9-runtime, is 3.04 GB compressed (Docker Hub API, read 2026-10-16), before any project code or data, which is why GPU clusters pre-pull images onto nodes, run a pull-through registry cache, or use lazy-loading snapshotters. Depth: mistakes with the messages they produce, and interview rehearsal


Ten common mistakes, each with the message it produces (diagnostic reference)


Matching a Job failure rule on the training script's exit code
Under torchrun the container exits 1 whatever the rank returned (run e2b: the rank exited 13, the rule on 13 never fired, the Job retried a deterministic crash). Match what the container really returns, or launch one process per pod. Message to look for in the pod log: exitcode  : 13 (pid: 13) under "Root Cause", next to a container exit code of 1.


Ignoring disruptions per pod in a multi-pod job
An Ignore rule on DisruptionTarget does not save the job: the peers fail a moment later with an ordinary error and are counted (run e2d2, BackoffLimitExceeded). Fail the Job on disruption and restart the group at the JobSet level (run e3b).


Expecting the default scheduler to pack GPUs
It ranks by CPU and memory only. Symptom: GPUs free in total, big job Pending with Insufficient nvidia.com/gpu on every node (here 3 Insufficient example.com/gpu). Fix: MostAllocated with the GPU resource listed, separate node pools by job size, or a packing scheduler.


Partial placement that looks healthy
Half-placed jobs show as Running pods with no progress; the scheduler reports only Insufficient for the rest, and preemption declines (Preemption is not helpful for scheduling). Use Kueue, a gang scheduler, or (when enabled) a PodGroup.


A spread constraint that counts a tainted domain
2 node(s) didn't match pod topology spread constraints with free nodes available: the default nodeTaintsPolicy: Ignore counts nodes the pod cannot use. Set Honor.


Checkpoints on a node-local volume
1 node(s) didn't match PersistentVolume's node affinity after a restart lands elsewhere; the checkpoint is also lost with the node. Use a shared file system (ReadWriteMany) or object storage for resumable state.


A main process that ignores SIGTERM
Preemption and eviction send SIGTERM, wait terminationGracePeriodSeconds (default 30 s), then SIGKILL (exit 137, run e4b). A training process should catch SIGTERM, write a checkpoint and exit; give it a grace period long enough to do so; and do not hide it behind a shell that swallows the signal (sh -c "exec torchrun ...", as this page's manifests do, keeps torchrun as PID 1).


Treating Kueue's webhook as optional
With Kueue's controller down, failed calling webhook "mpod.kb.io" ... connection refused for every pod in every namespace it watches, including system add-ons outside kube-system. Run Kueue with several replicas, watch its readiness, and know the namespaces its webhook excludes.


Assuming a removed device plugin cleans up
The node keeps the resource in capacity with allocatable 0 (measured here after deleting the plugin, until the kubelet restarted). Dashboards that sum capacity overcount GPUs; sum allocatable.


Using v1beta1 Kueue objects with Kueue v0.20
v0.20 serves only kueue.x-k8s.io/v1beta2; manifests still written for v1beta1 are rejected because the version is no longer served (Kueue CHANGELOG-0.20, "Actions required", in the topic's shared facts; not run here). Convert them before upgrading.




Interview rehearsal: eight questions with short answers (optional)


Walk me through what happens between kubectl apply of a training Job and the first training step.
The API server validates the Job, runs admission webhooks (Kueue may suspend it until quota is reserved), stores it in etcd. The job controller sees it and creates the pods; the scheduler filters and scores nodes for each and writes a Binding; the kubelet on each node pulls the image, starts the container (device plugin Allocate or DRA prepare first), and reports status. torchrun in each pod then rendezvouses through the DNS name of pod 0. Measured here: pods bound 44 ms after creation, containers started at 0.6 s, with the image preloaded.


Why does Kubernetes need add-ons for distributed training when Slurm does not?
Slurm allocates a job's nodes as one unit, so gangs, queues and fairshare are built in. Kubernetes schedules pods one at a time, has no queue beyond Pending pods, and no quota sharing between teams; Kueue (admission, quota, cohorts), JobSet (group lifecycle) and gang scheduling (PodGroup, Volcano, KAI) add what Slurm's controller does itself.


What is the difference between a device plugin and DRA?
A device plugin advertises a count of identical devices and the kubelet picks which ones at container start; DRA publishes typed devices with attributes, pods claim them with CEL selectors, and the scheduler allocates specific devices while it picks the node. DRA can express "2 GPUs with 80 GB on one NVLink island"; a device plugin needs node labels and separate resource names to approximate it.


A 64-GPU job has been Pending for an hour with 80 GPUs free. What do you check?
Whether any node or topology domain can host its pods: free GPUs may be scattered (spread scoring), on tainted or cordoned nodes, in a flavor or block the job cannot use, or behind a Kueue quota or a TAS constraint. Read the pod's FailedScheduling event and the Workload's QuotaReserved condition message; compare allocatable, not capacity.


How should a training job on a preemptible pool be configured so that preemptions are free and bugs are not?
Pods fail their Job on DisruptionTarget (podFailurePolicy FailJob), the JobSet restarts all Jobs on reason PodFailurePolicy without counting it (RestartJobSetAndIgnoreMaxRestarts), maxRestarts stays low for real crashes, the process checkpoints on SIGTERM within the grace period, and checkpoints live on shared storage. Run e3b shows the restart and resume.


Kueue or Volcano?
Kueue keeps the default scheduler and adds queueing and quota at admission; it composes with JobSet, Trainer, KubeRay and cluster autoscaling. Volcano (or KAI) replaces the scheduler and does gangs, queues and fair share inside it, which also lets it pack and place by topology pod by pod. Choose Kueue when the cluster runs many kinds of workload and you want upstream components; a full batch scheduler when the cluster is dedicated to batch GPU jobs and needs its policies.


Design question: the Kubernetes layer of a training platform for a 1,000-GPU lab (125 nodes of 8 GPUs).
Node pools by GPU type, tainted, labelled by rack and network block; NVIDIA GPU Operator for driver, device plugin (or DRA driver) and DCGM; a health-check DaemonSet that cordons failing nodes. Kueue with one ClusterQueue per team in a cohort (nominal shares, borrowing, reclaim), flavors per GPU type, topology-aware scheduling on the block and rack labels, and waitForPodsReady; priority classes for production, research and preemptible. JobSet (or TrainJob over it) as the job API, with the disruption-free restart policy and checkpoint-on-SIGTERM; checkpoints on a parallel file system through CSI, datasets streamed from object storage. A bin-packing scheduler profile for small jobs or a separate pool. Trade-offs to explain: quota by team against throughput, spreading against packing, one big cluster against several with MultiKueue, and the control-plane limits (5,000 nodes, watch load), which 125 nodes does not approach.


Why is the scheduler's tie-break random, and why does it matter for GPUs?
Among equal scores it picks by a per-node random number, so equal nodes share load. For GPU jobs under the default profile, nodes are nearly always equal (GPUs do not enter the score), so placement of small jobs is effectively random, which is what fragments the cluster.
