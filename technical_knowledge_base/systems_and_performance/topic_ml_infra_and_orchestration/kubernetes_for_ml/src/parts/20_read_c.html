2. Pods and Jobs: a training job with no add-ons

A Job (batch/v1) creates pods until enough have succeeded (completions of them, parallelism at a time). With completionMode: Indexed each pod gets an index 0..N-1 in JOB_COMPLETION_INDEX and the hostname <job>-<index>; a headless Service (clusterIP: None, DNS records only) whose name matches the pods' subdomain makes each resolvable as <job>-<index>.<service>. That is all torchrun needs: node rank from the index, rendezvous address from pod 0's name. The running example ran this way unchanged.

The manifest that ran (the Indexed Job plus its Service, with the crash knobs of the runs below)
apiVersion: v1
kind: Service
metadata: {name: km-e2c, namespace: km}
spec:
  clusterIP: None
  selector: {job-name: km-e2c}
  publishNotReadyAddresses: true      # DNS records before the pods are Ready: rendezvous happens first
---
apiVersion: batch/v1
kind: Job
metadata: {name: km-e2c, namespace: km}
spec:
  completions: 2
  parallelism: 2
  completionMode: Indexed
  backoffLimit: 2
  podFailurePolicy:
    rules:
    - action: FailJob
      onExitCodes: {containerName: trainer, operator: In, values: [1]}
  template:
    spec:
      restartPolicy: Never
      subdomain: km-e2c
      containers:
      - name: trainer
        image: mi-train:1
        imagePullPolicy: Never
        command: ["sh", "-c"]
        args:
        - >-
          exec torchrun --nnodes=2 --nproc-per-node=2 --node-rank=$JOB_COMPLETION_INDEX
          --master-addr=km-e2c-0.km-e2c --master-port=29500
          /opt/mi/train.py --ckpt-dir=/shared/ckpt/km-e2c --log-dir=/shared/logs/km-e2c --steps 200 --crash-rank 1 --crash-step 20 --no-resume
        resources:
          requests: {cpu: 500m, memory: 400Mi, example.com/gpu: "2"}
          limits: {cpu: "2", memory: 900Mi, example.com/gpu: "2"}
        volumeMounts:
        - {name: shared, mountPath: /shared}
      volumes:
      - name: shared
        hostPath: {path: /shared, type: Directory}

When a pod fails, the job controller retries, fails the Job or ignores the failure, by these knobs:

  • backoffLimit: how many failed pods the Job tolerates (default 6); retries wait 10 s, doubling per failure, capped at 10 minutes.
  • podFailurePolicy: rules matched in order on a failed pod's exit codes or conditions, with actions FailJob, Ignore, Count (the default) and FailIndex. Not allowed with restartPolicy: OnFailure, where the kubelet restarts the container in place and the Job never sees a failed pod.
  • backoffLimitPerIndex (with maxFailedIndexes) and successPolicy: a budget per index for independent shards; success declared early, for example when the leader index succeeds.

Exit code 13 never reaches KubernetesThe rank exited 13, torchrun printed exitcode : 13 (pid: 13) as the root cause, and then torchrun itself, the container's main process, exited 1. A rule onExitCodes: In [13] (run e2b) therefore never matched: the Job retried after 19.1 s and failed with BackoffLimitExceeded at 34 s, exactly like no rule at all (e2a, 34 s). The rule on code 1 (e2c) failed the Job at 11.6 s with reason PodFailurePolicy and message "Container trainer for pod km/km-e2c-0-pj2zt failed with exit code 1 matching FailJob rule at index 0". Why the agent turns every worker failure into its own 1 is {{Launching distributed training|n:3fc5c17b0d0d81b3a8a5c58224bff9fa}}, section 3.
Eviction: one failure becomes twoWith Ignore on the DisruptionTarget condition (e2d2), the evicted pod was not counted (status.failed 1, not 2), but the other pod's ranks lost their peer, its torchrun exited 1, and that failure counted: BackoffLimitExceeded with backoffLimit 0, the same outcome as with no rule (e2d1). A pod-level rule cannot say "the gang failed because one member was disrupted".

The fix for the second case lives one layer up: a JobSet (section 9) whose Job fails fast on DisruptionTarget and whose failure policy restarts all pods without spending the restart budget (e3b). The run restarted once, resumed from its step-50 checkpoint and completed; the same JobSet with a real crash (e3c) failed at 8.8 s with ReachedMaxRestarts. That is the policy a preemptible training job wants: evictions are free, bugs are not.

Predict. In run e2a (backoffLimit 2, two pods per attempt, deterministic crash), how many attempts did the Job make before failing?
Two. backoffLimit counts failed pods, not attempts. The first attempt produced two failed pods (the crashing pod and its peer), within the limit; the second made four, over it. For a multi-pod training job, set backoffLimit with the pod count in mind, or move restart decisions to JobSet, which counts restarts of the whole group.

Choosing a rule on exit code 1 is a trade-off

Code 1 is what torchrun returns for any failed worker in these runs, including ones you want retried (a lost peer, a NCCL timeout). A rule FailJob on 1 stops wasting GPUs on a deterministic bug but also gives up on transient failures. Alternatives: have the training script write the root cause somewhere a wrapper can read and exit with its own code (torchrun records it in the file named by TORCHELASTIC_ERROR_FILE when the script's entry point is decorated with @record: {{PyTorch elastic errors|https://pytorch.org/docs/stable/elastic/errors.html}} docs, the page the log itself points to); or launch one process per pod without torchrun, so the script's exit code is the container's.

Did the resumed run train the same model? Almost: after resuming from step 50 with 4 ranks, the global loss matched the uninterrupted run at most logged steps and differed by 2.4e-7 (one float32 rounding step) at steps 70, 180 and 200. This is the DDP gradient-bucket rebuild effect the root's {{Failure lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} identified (there after a resume at step 100); the steps that differ depend on where the run resumed.

Two smaller lessons from the shard runs. With backoffLimitPerIndex: 1, the broken shard (index 2) was retried after 9.7 s and the Job failed with FailedIndexes while indexes 0, 1 and 3 completed (e4a). With successPolicy on index 0 (e4b), the Job reached SuccessCriteriaMet at 8.1 s but Complete only at 39.3 s: the two workers ran sleep as their main process, which ignores SIGTERM, so they were killed after the default 30 s grace period (exit 137). A training container whose main process ignores SIGTERM also loses the chance to write a last checkpoint on preemption.

Since v1.33 a Job adds the condition SuccessCriteriaMet before Complete, and FailureTarget before Failed (both visible in every run above): the terminal condition is written only after all pods have terminated. Watch for Complete or Failed, not for the first.
