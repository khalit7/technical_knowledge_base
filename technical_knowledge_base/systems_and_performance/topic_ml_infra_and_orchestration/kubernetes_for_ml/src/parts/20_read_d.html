3. The scheduler: filter, score, bind

The problem. A pod with no node must be put on one that can run it, and among those, on a good one. "Good" for a web service means spread out; for training it usually means packed together, so that whole nodes stay free for the next big job.

How it works. kube-scheduler keeps a scheduling queue of unbound pods (sorted by priority, then age) and takes one pod per scheduling cycle. Each step of the cycle is an extension point where plugins (Go code compiled into the scheduler, configured per profile) run:

  1. PreEnqueue: may keep a pod out of the queue entirely (scheduling gates, and in v1.37 the gang plugin).
  2. PreFilter, Filter: every plugin can reject a node: not enough free GPUs (NodeResourcesFit), an untolerated taint (TaintToleration), a label mismatch (NodeAffinity), a volume on another node (VolumeBinding), a spread rule (PodTopologySpread). A node is feasible only if every Filter passes.
  3. PostFilter: runs only if no node is feasible; the default is preemption (section 5).
  4. PreScore, Score, NormalizeScore: each scoring plugin gives each feasible node 0 to 100; the scores are multiplied by the plugin's weight and summed.
  5. Reserve, Permit: the chosen node's resources are reserved in the scheduler's cache; Permit can hold the pod (the gang plugin does).
  6. PreBind, Bind: in a separate binding cycle, volumes are bound and the Binding is written, so the next pod's cycle does not wait for the API call.

The default plugins and weights are in pkg/scheduler/apis/config/v1/default_plugins.go lines 32-57 at v1.37.0 source: TaintToleration 3, NodeAffinity 2, PodTopologySpread 2, InterPodAffinity 2, NodeResourcesFit 1, NodeResourcesBalancedAllocation 1, ImageLocality 1. The cycle itself is schedulingCycle and schedulePod in pkg/scheduler/schedule_one.go (lines 169 and 572); the highest total wins, ties are broken by a random number drawn per node (framework/sorted_nodes.go lines 61-64). On clusters of 100 nodes or more the scheduler stops looking after enough feasible nodes (numFeasibleNodesToFind, lines 866-892: 50% minus 1% per 125 nodes, at least 5%, at least 100 nodes), so on a 5,000-node cluster a pod is scored against 500 of them, not the best of all.

The default scheduler does not see GPUs when it ranks nodes

NodeResourcesFit's default scoring strategy, LeastAllocated, prefers the node with the most free capacity, but it counts only the resources its strategy lists, and the default list is CPU and memory, weight 1 each (apis/config/v1/defaults.go lines 33-35). An extended resource such as a GPU is used to filter (a node with too few free GPUs is rejected) but never to rank unless you list it (noderesources/resource_allocation.go lines 176-182). The alternative strategy, MostAllocated, prefers the fullest node: bin packing.

The same six pods, default profile against a bin-packing profile measured

Pods asking for 2, 1, 1, 2 and 2 fake GPUs, then one asking for 4, created one after another on 3 workers of 4 GPUs each. Both profiles ran in one kube-scheduler (two profiles, chosen per pod with spec.schedulerName; config in src/k8s/km-sched-config.yaml), with per-plugin scores logged by --vmodule=schedule_one=10. src/recompute.py recomputes every logged score from the node states with the ported formulas: 135 of 135 match. The step-by-step cycle, every plugin and every node, is in the {{Scheduling cycle|#t-kmcyc}} tab.

What happened. Under the default profile the GPUs did not enter the score at all: every node scored 94 or 95 for NodeResourcesFit (a 100m pod on a 5-CPU node moves the score by one point), so pods went wherever CPU and memory were a hair freer, and to a random node among equals. After five pods every worker held some GPUs (4, 3 and 1 used) and the 4-GPU pod stayed Pending: 0/4 nodes are available: 1 node(s) had untolerated taint(s), 3 Insufficient example.com/gpu, with 4 GPUs free in total. Under MostAllocated with GPUs weighted 5, pods 2 and 3 joined pod 1 on one worker (scores 55 and 73 against 19), pods 4 and 5 shared the second, and the 4-GPU pod got the empty third.

When it matters, and the cost

On a cluster that runs whole-node training jobs only, spreading does not matter. On a cluster that mixes 1- and 2-GPU jobs (notebooks, evaluation, small fine-tunes) with 8-GPU jobs, spreading fragments the nodes and the large jobs starve while the GPU allocation looks fine. Bin packing costs some resilience (one node failure kills more small jobs) and concentrates heat; the usual answer is separate node pools, or a scheduler (Volcano, KAI) or Kueue's topology placement that packs by design. Because the scheduler's config is a control-plane setting, a managed cluster may not let you change it; a second scheduler profile or a second scheduler binary is the usual route.
