3. The scheduler: filter, score, bind

kube-scheduler takes one unbound pod per scheduling cycle (from a queue sorted by priority, then age). Filter plugins reject nodes that cannot run it (too few free GPUs, an untolerated taint, a label or volume mismatch); Score plugins give each remaining node 0 to 100, multiplied by the plugin's weight and summed; the highest total wins (ties broken at random) and a separate binding cycle writes the Binding. For a web service "good" means spread out; for training it usually means packed, so whole nodes stay free for the next big job.

The trap. NodeResourcesFit's default scoring strategy, LeastAllocated, prefers the emptiest node but counts only the resources it lists, and the default list is CPU and memory. A GPU is used to filter but never to rank unless you list it. The alternative, MostAllocated, prefers the fullest node: bin packing.

When it matters, and the cost

It matters on a cluster that mixes 1- and 2-GPU jobs (notebooks, evaluation, small fine-tunes) with 8-GPU jobs: spreading fragments the nodes and the large jobs starve while the GPU allocation looks fine. Bin packing costs some resilience (one node failure kills more small jobs) and concentrates heat; the usual answers are separate node pools, a second scheduler profile (the scheduler config is a control-plane setting a managed cluster may not expose), or a scheduler (Volcano, KAI) or Kueue topology placement that packs by design.

Every plugin, every node: the full scheduling cycle of each pod, on the recorded runs or your own sequence (depth)

Plugins are Go code compiled into the scheduler and configured per profile. The cycle's extension points, in order: PreEnqueue (may keep a pod out of the queue: scheduling gates, and in v1.37 the gang plugin); PreFilter, Filter (NodeResourcesFit, TaintToleration, NodeAffinity, VolumeBinding, PodTopologySpread; a node is feasible only if every Filter passes); PostFilter (only when no node is feasible; the default is preemption, section 6); PreScore, Score, NormalizeScore; Reserve, Permit (resources reserved in the scheduler's cache; Permit can hold the pod, as the gang plugin does); PreBind, Bind in the binding cycle, so the next pod's cycle does not wait for the API call. Default weights (pkg/scheduler/apis/config/v1/default_plugins.go lines 32-57 at v1.37.0 source): TaintToleration 3, NodeAffinity 2, PodTopologySpread 2, InterPodAffinity 2, NodeResourcesFit 1, NodeResourcesBalancedAllocation 1, ImageLocality 1. The default resource list is in apis/config/v1/defaults.go lines 33-35; extended resources are left out of the score in noderesources/resource_allocation.go lines 176-182.

The formulas

LeastAllocated
per resource ⌊(capacity − requested) × 100 / capacity⌋, then the weighted mean, rounded down; requested counts a container with no request as 100m CPU and 200 MiB (least_allocated.go lines 52-60, scheduler/util/pod_resources.go lines 28-31)
MostAllocated
per resource ⌊requested × 100 / capacity⌋, weighted mean (most_allocated.go lines 54-65)
BalancedAllocation
50 + ⌊(50 + swith pod − swithout) / 2⌋, s = ⌊(1 − σ) × 100⌋, σ the spread of the CPU and memory fractions (balanced_allocation.go lines 204-262)
total
3 × TaintToleration + 1 × NodeResourcesFit + 1 × BalancedAllocation + 1 × ImageLocality (+ 2 × the affinity and spread plugins, 0 here)

The cycle itself is schedulingCycle and schedulePod in pkg/scheduler/schedule_one.go (lines 169 and 572); ties are broken by a random number drawn per node (framework/sorted_nodes.go lines 61-64). On clusters of 100 nodes or more the scheduler stops looking after enough feasible nodes (numFeasibleNodesToFind, lines 866-892: 50% minus 1% per 125 nodes, at least 5%, at least 100 nodes), so on a 5,000-node cluster a pod is scored against 500 of them, not the best of all.
