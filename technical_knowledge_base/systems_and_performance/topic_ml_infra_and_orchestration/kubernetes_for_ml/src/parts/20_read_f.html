5. Placement controls: affinity, taints, spread, priority and preemption

The problem. GPU nodes are expensive and different from each other (H100 against A100, one network block against another). You want training pods only on GPU nodes, everything else kept off them, a job's pods close together, and important jobs able to take GPUs from unimportant ones.

  • nodeSelector and node affinity: the pod lists node labels it requires (requiredDuringSchedulingIgnoredDuringExecution, a Filter) or prefers (preferred..., a Score). Cloud providers label GPU nodes with the accelerator type; Kueue's flavors (section 7) work by adding a nodeSelector for you.
  • Taints and tolerations: a node's taint repels every pod that does not tolerate it. GPU node pools are usually tainted (for example nvidia.com/gpu=present:NoSchedule) so that only pods that tolerate it (training pods, the device plugin DaemonSet) land there. NoExecute also evicts running pods; the node lifecycle controller adds node.kubernetes.io/unreachable this way when a node goes silent (the root's {{Failure lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} measures it).
  • topologySpreadConstraints: keep the count of matching pods per topology domain (all nodes sharing a label value, such as a zone or this cluster's block mi.example.com/block) within maxSkew of each other.
  • Pod affinity and anti-affinity: place a pod near (or away from) pods with given labels in a domain. JobSet's exclusive placement (section 8) is built from these.

A spread rule meets a tainted node

Three 1-GPU pods with maxSkew: 1 over the two blocks (b1 = worker and worker2, b2 = worker3), while worker3 carries a taint the pods do not tolerate (say it is reserved for inference). Should b2 count as a domain the pods must spread into?

nodeTaintsPolicy Ignore (the default) against Honor, same pods measured

src/k8s/spread-pod.sh; taint km.example.com/reserved=inference:NoSchedule on worker3 during the runs, removed after.

With the default, the tainted block still counts as a domain with zero pods, so after one pod in b1 the second would make the skew 2 and is refused: two pods Pending with 2 node(s) didn't match pod topology spread constraints, 2 node(s) had untolerated taint(s). With nodeTaintsPolicy: Honor the tainted node is left out of the count and all three run in b1. The same trap exists for nodeAffinityPolicy, whose default is Honor.

Priority and preemption

A PriorityClass maps a name to an integer. Higher-priority pods go first in the scheduling queue, and when nothing fits, the default PostFilter plugin looks for a node where evicting lower-priority pods would make room (preemption). The victims get the DisruptionTarget condition (reason PreemptionByScheduler), receive SIGTERM and their grace period, and the preemptor waits with status.nominatedNodeName set until they are gone. preemptionPolicy: Never keeps the queue priority but never evicts.

Three low-priority jobs fill the cluster; two high-priority jobs arrive measured

PriorityClasses km-low (100), km-high (1000) and km-high-nopreempt (1000, preemptionPolicy Never) from src/k8s/e5-priority.yaml; every pod asks for a whole worker's 4 fake GPUs. Events in src/runs/e5a.events.txt.

Cost and when it matters. Preemption is how a shared research cluster lets production training take GPUs back, but the scheduler preempts pods, not jobs: evicting one pod of a 64-pod training job kills all 64 (section 2), and the scheduler does not know that. It will also happily preempt a pod that is 3 minutes from a checkpoint. That is why training clusters move preemption up a level: Kueue preempts whole workloads by priority or to reclaim quota (the parent's {{Scheduling lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} shows the reclaim), and the native PodGroup has a disruptionMode (single or all) for exactly this. A PodDisruptionBudget limits voluntary evictions (drains), but not preemption by priority beyond a best effort.
