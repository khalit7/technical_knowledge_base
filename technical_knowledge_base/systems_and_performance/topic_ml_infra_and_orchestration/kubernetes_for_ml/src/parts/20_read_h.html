7. Kueue in depth: quota, flavors, topology

The problem. Several teams share a fixed pool of GPUs. Each needs a guaranteed share, idle shares should be usable by others, jobs should wait in an orderly queue rather than as Pending pods, and a 16-GPU job should get 16 GPUs that are close together.

How it works. Kueue is a controller plus webhooks. Its objects (all kueue.x-k8s.io/v1beta2; v0.20 no longer serves v1beta1):

ResourceFlavorA kind of capacity, mapped to nodes by labels (and tolerations): "H100 in block 1", "spot A100". Optional topologyName for topology-aware placement.
ClusterQueueA team's quota: for each flavor and resource a nominalQuota (plus borrowingLimit, lendingLimit), a queueing strategy, preemption rules, and the cohort it shares with.
LocalQueueA namespace's door into a ClusterQueue. Jobs say kueue.x-k8s.io/queue-name: <localqueue>.
WorkloadKueue's record of one job: its pod sets (count and requests per pod), created by Kueue's integration for Jobs, JobSets, TrainJobs, RayJobs and others. Admission is a property of the Workload.
CohortA group of ClusterQueues that lend each other unused quota; cohorts can form a tree.
TopologyAn ordered list of node labels (block, rack, host) for topology-aware scheduling.

When a labelled job is created, Kueue's webhook makes it start suspended (spec.suspend: true: the job controller creates no pods). Kueue's scheduler loop takes the head of each queue, tries to assign flavors (for each resource group, the flavors in order, checking the workload's total request against unused quota, borrowing and preemption possibilities), reserves the quota, runs any admission checks (for example a ProvisioningRequest that asks the cluster autoscaler for nodes first), and then admits: it writes the chosen flavors into the Workload, injects the flavors' node labels as a nodeSelector into the pod template, and unsuspends the job. From there the normal scheduler places pods. The parent's {{Scheduling lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} quotes the loop (pkg/scheduler/scheduler.go in Kueue) and shows queueing and cohort borrowing and reclaim; here are the two things it did not run.

The rest of Kueue, briefly (described, not run here)

  • Flavor fungibility: by default the search stops at the first flavor where the workload fits or fits by borrowing (whenCanBorrow: MayStopSearch), but tries the next flavor before preempting in the current one (whenCanPreempt: TryNextFlavor) (apis/kueue/v1beta2/clusterqueue_types.go lines 526-549).
  • Preemption: withinClusterQueue (by priority inside a team), reclaimWithinCohort (take back lent quota; the parent's lab measured it), borrowWithinCohort (preempt to borrow). Kueue preempts whole workloads, which is the right unit for training.
  • Fair sharing: in the Kueue configuration, share cohort capacity by weight rather than first come; and admission fair sharing orders a queue by each LocalQueue's recent usage ({{Kueue fair sharing|https://kueue.sigs.k8s.io/docs/concepts/fair_sharing/}} docs).
  • waitForPodsReady: evict and requeue an admitted workload whose pods are not all ready within a timeout (default 30 minutes in v0.20), closing the gap between "quota reserved" and "pods really running".
  • MultiKueue: one manager cluster dispatching workloads to several worker clusters.

The cost. Kueue reasons about quota, not nodes (except with topology): with 12 GPUs of quota and 12 GPUs in the cluster, an admitted job can still be unplaceable if a node is cordoned or fragmented. Keep quotas equal to what is really schedulable, and mind the webhook: as section 6 found, while Kueue is down no pod can be created anywhere it watches.

8. JobSet in depth

The problem. One training run is often several groups of pods (a driver and workers; parameter servers; a group per data-parallel replica), each an Indexed Job, which must share a network identity, succeed or fail as a whole, and be restarted together.

How it works. A JobSet (jobset.x-k8s.io/v1alpha2, kubernetes-sigs, v0.13.0) holds a list of replicatedJobs, each a Job template and a replica count. The controller creates Jobs named <jobset>-<replicatedJob>-<index>, a headless Service named after the JobSet, and sets each pod's hostname and subdomain so it resolves as <jobset>-<replicatedJob>-<jobIndex>-<podIndex>.<jobset>; inside the running example's pods hostname -f printed km-e3a-node-0-0.km-e3a.km.svc.cluster.local measured. It labels every pod with jobset.sigs.k8s.io/jobset-name, replicatedjob-name, job-index, restart-attempt and more, which is what failure handling and Kueue key on.

  • failurePolicy: maxRestarts (restart the whole JobSet up to N times), restartStrategy (Recreate, BlockingRecreate which waits for every old pod to be gone, InPlaceRestart which restarts healthy containers in place), and ordered rules matched on the failed Job's reason (onJobFailureReasons) with actions FailJobSet, RestartJobSet, RestartJobSetAndIgnoreMaxRestarts, RestartJob, RestartJobAndIgnoreMaxRestarts (api/jobset/v1alpha2/jobset_types.go lines 464-545 at v0.13.0 source). If no rule matches, RestartJobSet applies.
  • successPolicy: operator: All or Any over targetReplicatedJobs, so the JobSet completes when the driver completes.
  • startupPolicy (InOrder) or dependsOn: start the coordinator before the workers.
  • Exclusive placement: the annotation alpha.jobset.sigs.k8s.io/exclusive-topology: <label> puts each child Job alone in one topology domain (one Job per rack, say) through pod affinity and anti-affinity (line 49).
  • Workload-aware scheduling: v0.13 can describe the JobSet to the native Workload API (spec.scheduling, behind its own feature gate and the alpha CompositePodGroup gate; not run here).

The policy that ran in section 2, the shape JobSet recommends for preemptible training:

spec:
  failurePolicy:
    maxRestarts: 0                        # a crash is not retried
    rules:
    - name: disruptedRestartFree
      action: RestartJobSetAndIgnoreMaxRestarts
      onJobFailureReasons: [PodFailurePolicy]
  replicatedJobs:
  - name: node
    template:
      spec:
        backoffLimit: 0
        podFailurePolicy:                 # an evicted or preempted pod fails its Job at once,
          rules:                          # with reason PodFailurePolicy
          - action: FailJob
            onPodConditions:
            - {type: DisruptionTarget}

Predict. In run e3b the evicted pod's Job failed with reason PodFailurePolicy. The other pod of the same Job then also exited 1 (its peer was gone). Does that second failure spend the restart budget?
No. A Job fails once; the first matching pod failure decides its reason. The JobSet sees one failed Job with reason PodFailurePolicy, matches the rule, deletes every Job and recreates them (status restarts: 1, no restartsCountTowardsMax). The order matters, though: the evicted pod reached Failed at 17.5 s and its peer at 18.2 s, so the Job's first failure was the disruption.
