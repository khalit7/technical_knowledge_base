6. Gang scheduling: every pod or none

The problem. The scheduler places one pod per cycle and knows nothing of the job it belongs to. Two jobs that each need the whole cluster can each get half, and wait forever for the other half. The parent's {{Scheduling lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} produced exactly that on this cluster (three 2-pod jobs, each pod a whole worker: three pods Running and doing nothing, three Pending) and fixed it with Kueue. A gang is a set of pods that must start together; gang scheduling binds all of them or none.

Native gang scheduling, switched on for one run

Kubernetes v1.37 has the pieces built in: a PodGroup object (scheduling.k8s.io/v1beta1) with schedulingPolicy.gang.minCount, a pod field spec.schedulingGroup.podGroupName (it replaced workloadRef in v1.36, staging/src/k8s.io/api/core/v1/types.go lines 4697-4716), and a GangScheduling plugin. To try it, this page turned on the gate in the API server (plus --runtime-config=scheduling.k8s.io/v1beta1=true) and in the scheduler, ran the parent's deadlock input again with placeholder pods, and restored both manifests (src/scripts/km_gang_reconf.sh):

The parent's deadlock input, without and with a PodGroup measured

Three jobs of two pods, each pod holding a whole worker's 4 fake GPUs (12 in all, so 1.5 jobs fit), released one second apart in the order a0, b0, c0, a1, b1, c1. Pods sleep 30 s in the gang run (600 s in the other, which was stopped after 28 s). Snapshots in src/runs/e11nogang.snap, e11gang.snap; scheduler log in e11gang.schedlog.txt.

Without the gang, a0, b0 and c0 each took a worker and the other three waited: every job half placed, none able to run. With the PodGroups, a0 was held at PreEnqueue (waiting for minCount pods from a gang to appear in scheduling queue); when a1 arrived both were placed and released together (Quorum is met for a gang. Allowing other pods from a gang waiting on permit); gangs b and c were refused as a whole (minCount (2) cannot be satisfied: 1 scheduled, 0 remaining) and ran one after another as the GPUs freed up. Two things went wrong on the way, both worth knowing

Restarting the API server restarted Kueue's controller too, and until it served again every pod creation in the cluster failed: failed calling webhook "mpod.kb.io": failed to call webhook: Post "https://kueue-webhook-service.kueue-system.svc:443/mutate--v1-pod?timeout=10s": ... connection refused. Kueue's pod webhook has failurePolicy: Fail for every namespace except kube-system and kueue-system, so Kueue is on the critical path of all pods, queued or not. And the PodGroups carry a finalizer (scheduling.k8s.io/podgroup-protection) that a kube-controller-manager controller removes; with the gate on only in the API server and scheduler, deleting them hung until the finalizer was removed by hand. Turning on a beta gate means turning it on in every component that has it.

Which one to use. Native gangs fix the deadlock but have no notion of quota or queues: a big job still waits behind whatever arrives first, and two teams still race. Kueue gives queues and quotas and works with the default scheduler today (and its admission can lag behind real placement: an admitted workload can still find a node broken, which waitForPodsReady, default timeout 30 minutes in v0.20 per apis/config/v1beta2/defaults.go line 48, handles by evicting and requeueing it). Volcano and KAI replace the scheduler and give both, at the cost of running a second scheduler you must trust with every GPU pod.
