11. Serving on Kubernetes: Deployments, LeaderWorkerSet, KServe and the vLLM production stack

Serving replicas run for months, scale with traffic and are updated while serving. A model that fits on one node is an ordinary Deployment: each replica is one pod (say one vLLM server on 8 GPUs), scaled by changing replicas and rolled pod by pod. A model sharded across nodes (pipeline or tensor parallel over 2 or more nodes) breaks that: a replica is now several pods that must be created together, find a leader, fail together and be upgraded together. A Deployment would roll one shard of a replica at a time and leave half-updated groups.

The unit of scaling changes from a pod to a group

Top: a Deployment of four single-node replicas, each pod independent (one fails, one is replaced). Bottom: a LeaderWorkerSet with replicas: 2 and size: 4, eight pods in two groups, each a leader (L) and 3 workers (W); the group is what is created, scaled, restarted and rolled.

LeaderWorkerSet (LWS, kubernetes-sigs, v1.0.0 released 2026-10-16) is the API for that group. Its README: "a group of pods as a unit of replication", with one template for the leader and one for the workers, a unique index 0 to n-1 per pod, rolling update "at the group level", a scale subresource for the HPA that counts groups, opt-in topology placement of a group, gang scheduling of each group (alpha), and "all-or-nothing restart" ({{kubernetes-sigs/lws|https://github.com/kubernetes-sigs/lws}} docs). In the API (api/leaderworkerset/v1/leaderworkerset_types.go at v1.0.0 source) size is the number of pods per group (default 1, line 403), the default restartPolicy is RecreateGroupOnPodRestart (line 408: one pod's failure recreates the whole group, the serving cousin of JobSet's restart-everything), and every container gets LWS_LEADER_ADDRESS, LWS_GROUP_SIZE and LWS_WORKER_INDEX (lines 82-90), the serving equivalent of torchrun's master address, world size and rank.

KServe (v0.21.0, 2026-09-25) is the operator one level up. Its LLMInferenceService (serving.kserve.io/v1alpha2) takes a model URI and a parallelism block; its controller writes a Deployment for a single-node model and a LeaderWorkerSet for a multi-node one, with size set from the pipeline (or data) parallel degree, restartPolicy: RecreateGroupOnPodRestart and startupPolicy: LeaderCreated (pkg/controller/v1alpha2/llmisvc/workload_multi_node.go lines 167-191 and workload_single_node.go line 118 at v0.21.0 source), plus prefill and decode workloads when the two phases are split, and routing through the Gateway API Inference Extension (a dependency in its go.mod). The classic InferenceService runs on Knative (scale to zero, canaries) or, in the lighter install, as plain Deployments.

The vLLM production stack (Helm chart vllm-stack-0.1.13, 2026-09-29) is the minimal alternative: one Helm release with three parts, "Serving engine" (vLLM Deployments), "Request router" ("based on routing keys or session IDs to maximize KV cache reuse") and an "Observability stack" (Prometheus and Grafana) ({{vllm-project/production-stack README|https://github.com/vllm-project/production-stack}} docs). llm-d, which co-designs LWS according to the LWS README, is the larger option.
