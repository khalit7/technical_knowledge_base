9. Operators: Kubeflow Trainer v2 and KubeRay

The problem. Writing the JobSet of section 8 by hand for every run means every user knows torchrun's flags, the DNS naming and the restart rules. An operator packages that knowledge: a custom resource definition (CRD, a new object kind the API server stores), a controller that reconciles it into lower-level objects, and usually webhooks that validate and default it.

Kubeflow Trainer v2. Trainer v2 (v2.0 July 2025; v2.3.0 released 2026-08-07, whose README still calls the API alpha) has two kinds of object: a TrainingRuntime or ClusterTrainingRuntime, written once by the platform team, holding a JobSet template and an ML policy (torch, torchtune, DeepSpeed, JAX, MLX and XGBoost runtimes ship in its manifests/base/runtimes), and a TrainJob, written by the user, that names a runtime and says only what differs. The controller merges the two into a JobSet. It replaced the v1 Training Operator's per-framework kinds (PyTorchJob and friends); v1 is maintained on its release-1.9 branch (v1.9.4, 2026-08-18), and Kueue's docs call its integration legacy.

apiVersion: trainer.kubeflow.org/v1alpha1
kind: TrainJob
metadata: {name: km-tj, namespace: km}
spec:
  runtimeRef: {name: torch-distributed}      # Trainer's own ClusterTrainingRuntime
  trainer:
    image: mi-train:1
    numNodes: 2
    numProcPerNode: 2
    command: ["torchrun", "/opt/mi/train.py", "--ckpt-dir=/tmp/ckpt", "--log-dir=/tmp/logs"]
    resourcesPerNode:
      requests: {cpu: 500m, memory: 400Mi, example.com/gpu: "2"}
      limits: {cpu: "2", memory: 900Mi, example.com/gpu: "2"}

The master address the controller wrote, km-tj-node-0-0.km-tj, is the same JobSet DNS rule as the hand-written run's km-e3a-node-0-0.km-e3a; the operator encodes the convention, nothing more (pkg/runtime/framework/plugins/torch/torch.go lines 147-165 at v2.3.0 source). The cost: three CRDs of 2.4 MB of YAML in the API server (the control plane grew by about 0.2 GiB here), one more controller and two more webhooks on the path of every TrainJob. Note also restartPolicy: OnFailure: the kubelet restarts a failed container in place, so the Job (and a podFailurePolicy, which then cannot be used) never sees the failure.

KubeRay (v1.7.1, 2026-09-21) is the operator for Ray: RayCluster (a head pod and worker groups, with autoscaling), RayJob (a cluster plus a submitted driver, torn down after) and RayService. Kueue can admit a RayJob or RayCluster as one workload. Ray's own scheduling (placement groups, the object store) is the {{Ray|n:3fc5c17b0d0d811cba13f3aeccf8724b}} sibling page's subject; the parent's {{Scheduling lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} measures Ray placement groups. Not run here.

When an operator is worth it. When many users submit the same shape of job (one runtime, many TrainJobs), or when the framework needs more than a Job can express (Ray's head and workers, MPI's launcher and hostfile). When a team runs one kind of job and already has a JobSet template, the operator adds an API surface to upgrade and little else.

10. Storage for training pods: volumes, claims and CSI

The problem. A container's file system disappears with it. Checkpoints and datasets must outlive pods and be reachable from whichever node the restarted pod lands on.

How it works. A pod mounts volumes. A PersistentVolumeClaim (PVC) asks for storage by size and access mode (ReadWriteOnce: one node; ReadWriteMany: many nodes; ReadOnlyMany); a StorageClass says which provisioner creates the PersistentVolume (PV) and when; a CSI driver (Container Storage Interface) is the plugin that attaches and mounts it on a node. For training the usual choices are a shared file system through CSI (Lustre, GPFS, Weka, NFS, Filestore, FSx: ReadWriteMany), object storage read by the job itself, and local NVMe for caches. kind's default StorageClass is rancher.io/local-path: a folder on one node's disk, with volumeBindingMode: WaitForFirstConsumer.

The claim stayed Pending (waiting for first consumer to be created before binding) until the writer pod was scheduled; the volume was then created on that pod's node and got a node affinity to it. A pod on any other node is unschedulable: 1 node(s) didn't match PersistentVolume's node affinity. If the checkpoint of a training job lives on such a volume, a restart after a node failure cannot run anywhere else; and if that node is gone, the checkpoint is gone too. Use node-local volumes for caches, not for state the job must resume from. Storage systems themselves are the {{Storage and data movement|n:3fc5c17b0d0d818a94ced3fc7c3331fe}} sibling's subject and the parent's {{Storage lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} measures checkpoint writes on this cluster (the host folder these pods mount was 36 times slower than a Docker volume there).


Images are storage too: a pod on a fresh node first pulls the training image: Trainer's default torch runtime image, pytorch/pytorch:2.13.0-cuda13.0-cudnn9-runtime, is 3.04 GB compressed (Docker Hub API, read 2026-10-16), before any project code or data, which is why GPU clusters pre-pull images onto nodes, run a pull-through registry cache, or use lazy-loading snapshotters.
