Kubernetes was built to keep web services running, one replica at a time. A training job is a different animal: it needs all of its machines at once, it needs GPUs that Kubernetes does not natively understand, and a single lost process stops the whole run. This page shows, on a real cluster, what Kubernetes does with such a job by default, where that goes wrong, and which pieces (device plugins, DRA, Kueue, JobSet, PodGroups, operators) fill each gap.

0. In one screen

The running example of this topic is a tiny GPT trained with DDP over 4 processes on 2 machines (the root's {{running example|n:3c65c17b0d0d81b5925bfd1d8665dd4b}}: 112,577 parameters, 200 steps, global loss 2.2638769149780273 at step 200 on every system). On Kubernetes each machine's share becomes a pod (one or more containers that are always placed together on one node), and the job becomes a stack of objects, each made by a different program. Three surprises this page measures

(1) The default scheduler does not look at GPUs when it ranks nodes: it ranks by CPU and memory only, so it scatters small GPU jobs and can leave no node with 4 free GPUs (section 3). (2) A rank that exits with code 13 makes its pod exit with code 1, because torchrun is the container's main process, so a Job failure rule on code 13 never fires (section 2). (3) Kubernetes v1.37 ships native gang scheduling, but behind a feature gate that is off by default (section 6).

1. The control loop: who does what

The problem. A cluster has many machines and many programs that must agree on what should run where, while machines fail and people submit work. Kubernetes' answer is one shared database of desired and actual state, and many small programs that each watch part of it and act.

How it works. Everything is an object (a record such as a Job or a Pod) with a spec (what you want) and a status (what is true now). Objects live in etcd, a replicated key-value store, and only one program talks to etcd: the API server, which validates every write, runs admission webhooks (external programs that may change or refuse an object), stores it, and streams changes to anyone watching. A controller is a loop that watches some kinds of object and writes others so that actual state moves toward the spec; this is called reconciling. The job controller (inside kube-controller-manager) creates pods for Jobs; the scheduler watches pods with no node and writes a node name into each; the kubelet, an agent on every node, watches pods bound to its node, starts their containers through the container runtime and writes their status back. Nobody calls anybody: each program reads and writes objects. Every write bumps the object's resourceVersion, and every write is attributed to a field manager (kubectl, kube-controller-manager, kubelet), which is how the animation below knows who did what.

The same training job at three levels, from the API server's point of view measured

Every step is one change the watcher (src/scripts/km_watch.py, a Python client watching the namespace) received, with its arrival time after the first object was created. The three runs are the running example (2 pods x 2 ranks, 200 steps) submitted as an Indexed Job plus a headless Service, as a JobSet, and as a Kubeflow Trainer TrainJob, on 16 Oct 2026. The TrainJob's own creation is not in the stream (the watcher did not watch TrainJobs); its first step is the Trainer controller writing the JobSet.

What the run shows. From kubectl create to both pods bound took 44 ms: the job controller created pod 0 after 21 ms, the scheduler bound it 13 ms later. The containers started at 0.61 s because the image was already on the nodes (a real CUDA training image, 3 GB compressed or more, is pulled first, which can take minutes and is a common reason a GPU pod sits in ContainerCreating; section 10). Training took 15 s, and the Job was marked Complete at 17.6 s. Each layer you add puts one more controller in the chain: the JobSet controller writes the Job, the Trainer controller writes the JobSet. None of them talks to the others; they only read and write objects.

Predict. Which program writes the pod's spec.nodeName, the field that says where it runs?
The scheduler. It posts a Binding to the API server (pods/binding), which sets spec.nodeName; the kubelet only reacts to it. In the recorded run the pod's field managers are only kube-controller-manager (it created the pod) and kubelet (status): the binding write is not recorded as a field manager. A pod created with nodeName already set skips the scheduler entirely, which is how DaemonSets and static pods used to work and why a hand-set nodeName ignores taints and quotas.

The cost. Every object and every watch costs API server memory. On this cluster the control plane runs in 1.6 GB, and in the parent's Scheduling lab the API server restarted once at 1.27 GB under load. Installing Kubeflow Trainer's three custom resource definitions (2.4 MB of YAML, mostly embedded JobSet and pod schemas) raised the control plane's memory from 1.04 to 1.25 GiB measured. Kubernetes v1.37 is designed for at most 5,000 nodes, 110 pods per node, 150,000 pods and 300,000 containers ({{Considerations for large clusters|https://kubernetes.io/docs/setup/best-practices/cluster-large/}} docs, read 2026-10-16); training clusters hit the node and watch limits long before the pod limit, since they run about one pod per node.

How to check it. kubectl get events -n NS --sort-by=.metadata.creationTimestamp shows who did what; kubectl get pod P -o yaml --show-managed-fields shows the field managers; kubectl get --raw /metrics on the API server and the controllers' logs show the rest.
