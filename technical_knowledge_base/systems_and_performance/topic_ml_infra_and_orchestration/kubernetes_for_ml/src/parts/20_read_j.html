9. JobSet: several Jobs with one lifecycle

A JobSet (jobset.x-k8s.io/v1alpha2, kubernetes-sigs, v0.13.0) holds a list of replicatedJobs, each a Job template and a replica count (a driver and workers; a group per data-parallel replica). The controller creates Jobs named <jobset>-<replicatedJob>-<index> and one headless Service named after the JobSet, so every pod resolves as <jobset>-<replicatedJob>-<jobIndex>-<podIndex>.<jobset>; inside the running example's pods hostname -f printed km-e3a-node-0-0.km-e3a.km.svc.cluster.local measured. Its failurePolicy decides, per failed Job, whether to fail the set or restart all of it, and whether that restart counts. The policy that ran in section 2, the shape JobSet recommends for preemptible training:

spec:
  failurePolicy:
    maxRestarts: 0                        # a crash is not retried
    rules:
    - name: disruptedRestartFree
      action: RestartJobSetAndIgnoreMaxRestarts
      onJobFailureReasons: [PodFailurePolicy]
  replicatedJobs:
  - name: node
    template:
      spec:
        backoffLimit: 0
        podFailurePolicy:                 # an evicted or preempted pod fails its Job at once,
          rules:                          # with reason PodFailurePolicy
          - action: FailJob
            onPodConditions:
            - {type: DisruptionTarget}

src/k8s/train-jobset.sh km-e3b policy (abridged). Run e3b: one eviction, restarts: 1, resumed from step 50, completed. Run e3c: a crash, jobset failed due to reaching max number of restarts (first failed job: km-e3c-node-0).

Predict. In run e3b the evicted pod's Job failed with reason PodFailurePolicy. The other pod of the same Job then also exited 1 (its peer was gone). Does that second failure spend the restart budget?
No. A Job fails once; the first matching pod failure decides its reason. The JobSet sees one failed Job with reason PodFailurePolicy, matches the rule, deletes every Job and recreates them (status restarts: 1, no restartsCountTowardsMax). The order matters, though: the evicted pod reached Failed at 17.5 s and its peer at 18.2 s, so the Job's first failure was the disruption.
Every JobSet knob: failure rules and restart strategies, success, startup order, exclusive placement, Workload API (depth)

The controller labels every pod with jobset.sigs.k8s.io/jobset-name, replicatedjob-name, job-index, restart-attempt and more, which is what failure handling and Kueue key on.

  • failurePolicy: maxRestarts (restart the whole JobSet up to N times), restartStrategy (Recreate, BlockingRecreate which waits for every old pod to be gone, InPlaceRestart which restarts healthy containers in place), and ordered rules matched on the failed Job's reason (onJobFailureReasons) with actions FailJobSet, RestartJobSet, RestartJobSetAndIgnoreMaxRestarts, RestartJob, RestartJobAndIgnoreMaxRestarts (api/jobset/v1alpha2/jobset_types.go lines 464-545 at v0.13.0 source). If no rule matches, RestartJobSet applies.
  • successPolicy: operator: All or Any over targetReplicatedJobs, so the JobSet completes when the driver completes.
  • startupPolicy (InOrder) or dependsOn: start the coordinator before the workers.
  • Exclusive placement: the annotation alpha.jobset.sigs.k8s.io/exclusive-topology: <label> puts each child Job alone in one topology domain (one Job per rack, say) through pod affinity and anti-affinity (line 49).
  • Workload-aware scheduling: v0.13 can describe the JobSet to the native Workload API (spec.scheduling, behind its own feature gate and the alpha CompositePodGroup gate; not run here).
