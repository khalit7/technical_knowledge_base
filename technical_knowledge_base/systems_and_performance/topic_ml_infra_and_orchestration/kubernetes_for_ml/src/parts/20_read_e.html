4. GPUs as resources: extended resources, device plugins, the GPU Operator and DRA

Kubernetes knows CPU and memory natively. A GPU is a device on one node: the scheduler must count them, and the kubelet must give a container the right device files, driver libraries and environment for the specific GPUs it got. There are three levels of help.

Extended resources: counting only. Any resource name with a domain (nvidia.com/gpu, example.com/gpu) in a node's status.capacity. Pods request whole numbers, the scheduler subtracts, and nothing is attached to the container; it cannot be overcommitted (a limit, if given, must equal the request) ({{Extended resources|https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#extended-resources}} docs). This topic's cluster has no GPUs, so its setup wrote example.com/gpu: 4 into each worker's status by hand: every GPU number on this page is that counter.

Device plugins: counting plus attaching. A device plugin is a small gRPC server, usually a DaemonSet pod on every GPU node, that calls the kubelet's Register; the kubelet then streams ListAndWatch (device IDs and health), may ask GetPreferredAllocation (so the plugin can pick GPUs that share an NVLink or PCIe switch) and calls Allocate once per container, whose answer lists device files, mounts, environment variables or CDI device names. The scheduler picks the node; the kubelet picks which GPUs.

The NVIDIA GPU Operator is how that stack usually arrives: an operator that runs as containers on each GPU node "the NVIDIA drivers (to enable CUDA), Kubernetes device plugin for GPUs, the NVIDIA Container Runtime, automatic node labelling, DCGM based monitoring and others" ({{NVIDIA/gpu-operator README|https://github.com/NVIDIA/gpu-operator}} at v26.7.2, released 2026-10-14 vendor), so GPU nodes can boot the same OS image as CPU nodes. NVIDIA's device plugin advertises nvidia.com/gpu and can split GPUs by MIG or share them by time-slicing or MPS; MIG itself is on {{Virtualization and the GPU driver stack|n:3f05c17b0d0d8158b029e9b2ba2e161b}}, and DCGM's metrics on {{Observability and cost|n:3c65c17b0d0d818ebf79d1af4532f3ee}}.

DRA: described devices. Dynamic Resource Allocation (resource.k8s.io/v1, GA in v1.34) replaces "a count of opaque units" with structured devices. A DRA driver publishes ResourceSlices (each device with attributes such as model, memory, NUMA node, PCIe root); an admin defines DeviceClasses (a CEL selector); a pod references a ResourceClaim asking for, say, exactly 2 devices of a class with at least 80Gi. The scheduler allocates the exact devices while it picks the node, and the kubelet then asks the node's driver to prepare them.

The same request, through a device plugin and through DRA measured

Device plugin: Kubernetes' own e2e sample plugin (test/images/sample-device-plugin, image 1.8.0) on worker3, advertising two fake devices as example.com/resource. DRA: a hand-written ResourceSlice of four fake GPUs on worker3 (two with 40Gi, two with 80Gi), a DeviceClass and a claim template asking for 2 devices with at least 80Gi; no DRA driver installed. Manifests in src/k8s/e7-device-plugin.yaml and e8-dra.yaml; outputs in src/runs/e7.steps.txt and e8.steps.txt.

What the runs show. The device plugin registered in 9 ms; a pod asking for 1 got Allocate request="container_requests:{devices_ids:\"Dev-2\"}" and saw /tmp/Dev-2 mounted. After the plugin pod was deleted, the node kept capacity 2 with allocatable 0 until the kubelet was restarted. Through DRA, the scheduler allocated gpu-2 and gpu-3 (the two 80Gi devices) and wrote them into the claim before binding; the kubelet then failed with DRA driver gpu.km.example.com is not registered. The split is visible: allocation works from the published slice alone; only preparation needs the driver.

Device pluginSimple, everywhere, what NVIDIA's stack uses today. Counts only: "2 GPUs" cannot say "on the same NVLink island" or "with 80 GB" except through node labels and separate resource names. The scheduler picks the node; the kubelet picks the GPUs.
DRATyped devices, CEL selection, sharing a claim between pods, the scheduler choosing exact devices. Needs a DRA driver on every node and v1.34 or later; allocation is more work in the scheduler for every pod with a claim.
Predict. A node's GPU device plugin crashes and restarts while a training pod is running on that node's 8 GPUs. What happens to the running pod?
Nothing happens to it. Allocate happens once, at container start; the device files are already in the container. While the plugin is gone the node's allocatable for that resource drops to 0 (as measured above), so new GPU pods cannot land there, and on re-registration the kubelet restores it from ListAndWatch. A plugin that reports a device Unhealthy also only lowers allocatable; killing the pod that uses it is someone else's job (a health checker, or the root's {{Failure lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} patterns).
The device-plugin API, NVIDIA's plugin, the DRA run in full (depth)

The plugin talks to the kubelet over a Unix socket in /var/lib/kubelet/device-plugins/. The API (staging/src/k8s.io/kubelet/pkg/apis/deviceplugin/v1beta1/api.proto at v1.37.0 source): Register line 14, ListAndWatch line 48, GetPreferredAllocation line 55, Allocate line 60. NVIDIA's plugin is deployed as a DaemonSet; its MIG strategies are none, single and mixed (the last exposing names like nvidia.com/mig-1g.10gb), and for time-slicing its README says "nothing special is done to isolate workloads" ({{NVIDIA/k8s-device-plugin|https://github.com/NVIDIA/k8s-device-plugin}} vendor, v0.20.1 released 2026-09-22). The GPU Operator also installs the container toolkit. DRA's GA: {{Kubernetes blog, 2025-09-01|https://kubernetes.io/blog/2025/09/01/kubernetes-v1-34-dra-updates/}} docs; the scheduler's DynamicResources plugin has weight 2 when the feature is on. The NVIDIA GPU DRA driver now lives at {{kubernetes-sigs/dra-driver-nvidia-gpu|https://github.com/kubernetes-sigs/dra-driver-nvidia-gpu}} (the old NVIDIA/k8s-dra-driver-gpu address redirects there; latest release v0.5.1, 2026-10-12, GitHub API; not run here); the GPU Operator README's roadmap includes managing it as one of its components.

In the device-plugin run the log read "Device Plugin registered with the Kubelet", then "ListAndWatch"; the node reported example.com/resource: 2 on its next status update, and the kubelet recorded the assignment in its checkpoint file (kubelet_internal_checkpoint: pod UID, container, device IDs). Patching the leftover capacity out of the node status did not help (the kubelet wrote it back within seconds); it went away only when the kubelet was restarted at cleanup, about 50 minutes later. The DRA failure in full: Failed to prepare dynamic resources: prepare dynamic resources: DRA driver gpu.km.example.com is not registered (pkg/kubelet/cm/dra/plugin/dra_plugin_manager.go line 280), and a second identical pod was refused at scheduling with 3 cannot allocate all claims.
