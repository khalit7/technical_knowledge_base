4. GPUs as resources: extended resources, device plugins and DRA

The problem. Kubernetes knows CPU and memory natively. A GPU is a device on one node: the scheduler must count them, and the kubelet must give a container the right device files, driver libraries and environment for the specific GPUs it got.

Extended resources: counting only. An extended resource is any resource name with a domain (nvidia.com/gpu, example.com/gpu) that appears in a node's status.capacity. Pods request it in whole numbers, the scheduler subtracts, and that is all: it cannot be overcommitted (a request, if given with a limit, must equal it), and nothing is attached to the container ({{Extended resources|https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#extended-resources}} docs). This topic's cluster has no GPUs, so its setup wrote example.com/gpu: 4 into each worker's status by hand (the root's {{running example|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} setup): every GPU number on this page is that counter. The parent's labs, and sections 2, 3 and 6 here, rely on nothing more.

Device plugins: counting plus attaching. A device plugin is a small gRPC server, usually a DaemonSet pod on every GPU node, that the kubelet talks to over a Unix socket in /var/lib/kubelet/device-plugins/. The API (staging/src/k8s.io/kubelet/pkg/apis/deviceplugin/v1beta1/api.proto at v1.37.0 source) has the plugin call Register (line 14) on the kubelet's socket, then the kubelet calls ListAndWatch (line 48, a stream of the device IDs and their health), optionally GetPreferredAllocation (line 55, so a plugin can pick GPUs that share an NVLink or PCIe switch), and Allocate (line 60) once per container, whose answer lists device files, mounts, environment variables or CDI device names to add. NVIDIA's plugin advertises nvidia.com/gpu, is deployed as a DaemonSet, and can split GPUs by MIG (strategies none, single, mixed, the last exposing names like nvidia.com/mig-1g.10gb) or share them by time-slicing ("nothing special is done to isolate workloads", in its README) or MPS ({{NVIDIA/k8s-device-plugin|https://github.com/NVIDIA/k8s-device-plugin}} vendor, v0.20.1 released 2026-09-22). In production it usually comes with the NVIDIA GPU Operator (26.7.2, 2026-10-14), which also installs the driver, the container toolkit and DCGM. MIG itself is on {{Virtualization and the GPU driver stack|n:3f05c17b0d0d8158b029e9b2ba2e161b}}.

DRA: describing devices. Dynamic Resource Allocation (resource.k8s.io/v1, GA in v1.34: {{Kubernetes blog, 2025-09-01|https://kubernetes.io/blog/2025/09/01/kubernetes-v1-34-dra-updates/}} docs) replaces "a count of opaque units" with structured devices. A DRA driver publishes ResourceSlices: the devices on a node with attributes (model, memory, NUMA node, PCIe root) and capacities. A cluster admin defines DeviceClasses (a CEL selector over those attributes). A pod references a ResourceClaim (or a template that makes one per pod) asking for, say, exactly 2 devices of a class whose memory is at least 80Gi. The scheduler allocates specific devices to the claim while it picks the node (the DynamicResources plugin, weight 2 when the feature is on), and the kubelet then calls the driver on that node (NodePrepareResources) to set them up. Allocation moves from the node to the scheduler, so the scheduler knows which devices, not just how many.

The same request, through a device plugin and through DRA measured

Device plugin: Kubernetes' own e2e sample plugin (test/images/sample-device-plugin, image 1.8.0) on worker3, advertising two fake devices as example.com/resource. DRA: a hand-written ResourceSlice of four fake GPUs on worker3 (two with 40Gi, two with 80Gi), a DeviceClass and a claim template asking for 2 devices with at least 80Gi; no DRA driver installed. Manifests in src/k8s/e7-device-plugin.yaml and e8-dra.yaml; outputs in src/runs/e7.steps.txt and e8.steps.txt.

What the runs show. The device plugin registered in 9 ms (log: "Device Plugin registered with the Kubelet", then "ListAndWatch"); the node reported example.com/resource: 2 on its next status update; a pod asking for 1 got Allocate request="container_requests:{devices_ids:\"Dev-2\"}" and saw the file /tmp/Dev-2 mounted, and the kubelet recorded the assignment in its checkpoint file (kubelet_internal_checkpoint: pod UID, container, device IDs). After the plugin pod was deleted, the node kept capacity 2 with allocatable 0; patching it out of the node status did not help (the kubelet wrote it back within seconds), and it went away only when the kubelet was restarted at cleanup, about 50 minutes later. Through DRA, the scheduler allocated gpu-2 and gpu-3 (the two 80Gi devices) and wrote them into the claim's status before binding; the kubelet then failed with Failed to prepare dynamic resources: prepare dynamic resources: DRA driver gpu.km.example.com is not registered (pkg/kubelet/cm/dra/plugin/dra_plugin_manager.go line 280), and a second identical pod was refused at scheduling with 3 cannot allocate all claims. The split is visible: allocation works from the published slice alone; only preparation needs the driver.

Device pluginSimple, everywhere, what NVIDIA's stack uses today. Counts only: "2 GPUs" cannot say "on the same NVLink island" or "with 80 GB" except through node labels and separate resource names. The scheduler picks the node; the kubelet picks the GPUs.
DRATyped devices, CEL selection, sharing a claim between pods, the scheduler choosing exact devices. Needs a DRA driver (the NVIDIA GPU DRA driver now lives at {{kubernetes-sigs/dra-driver-nvidia-gpu|https://github.com/kubernetes-sigs/dra-driver-nvidia-gpu}}, the old NVIDIA/k8s-dra-driver-gpu address redirects there; latest release v0.5.1, 2026-10-12, GitHub API; not run here) and v1.34 or later. Allocation is more work in the scheduler for every pod with a claim.
Predict. A node's GPU device plugin crashes and restarts while a training pod is running on that node's 8 GPUs. What happens to the running pod?
Nothing happens to it. Allocate happens once, at container start; the device files are already in the container. While the plugin is gone the node's allocatable for that resource drops to 0 (as measured above), so new GPU pods cannot land there, and on re-registration the kubelet restores it from ListAndWatch. A plugin that reports a device Unhealthy also only lowers allocatable; killing the pod that uses it is someone else's job (a health checker, or the root's {{Failure lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} patterns).
