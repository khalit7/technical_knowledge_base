3. Slurm, Kubernetes and Ray

Three systems hand out machines for training today, and they come from three different worlds.

  • Slurm comes from supercomputing (HPC). You ask for an allocation (whole nodes, for a time limit) with a batch script (sbatch); when it starts, srun launches your processes on every node of it. A central daemon (slurmctld) runs the queue with priorities, backfill and fairshare built in; a daemon on each node (slurmd) starts and watches the processes. An allocation is all-or-nothing, so gang scheduling comes free. Containers are an add-on (Pyxis with Enroot, or Apptainer).
  • Kubernetes comes from running web services. Everything is a container in a pod; you declare the state you want in YAML and controllers keep making it true; the kube-scheduler places pods one at a time on nodes that advertise GPUs through a device plugin (nvidia.com/gpu: 8). It filters nodes on GPUs, but its default scoring weighs only CPU and memory, so it does not pack GPUs unless you configure it to. It has no job queue, no fairshare and, by default, no gang scheduling (Kubernetes 1.37 has a native one behind the GenericWorkload feature gate, beta and off by default); for training you add Kueue (queues, team quotas, borrowing, and admitting a job only when all of it fits; its pod webhook is fail-closed, so while Kueue is down no pod can be created in the namespaces it manages), JobSet (a group of pods treated as one job, with stable DNS names for rendezvous) or Volcano, and often the Kubeflow Trainer on top.
  • Ray comes from distributed Python. It is a runtime rather than a cluster scheduler: a head node keeps cluster state (the GCS, Global Control Service), a raylet on each node schedules tasks (remote functions) and actors (remote objects with state), and a shared-memory object store moves data between them. Ray Train starts a group of worker actors and sets up PyTorch's process group for you; placement groups reserve bundles of GPUs together (PACK, SPREAD, STRICT_PACK). Ray usually runs on Kubernetes (through KubeRay) or on plain VMs, and leaves multi-team queues and quotas to the layer below (Kueue can admit Ray jobs: {{Kueue docs|https://kueue.sigs.k8s.io/docs/tasks/run/rayjobs/}}).

#!/bin/bash
# The running example on Slurm: 2 nodes x 2 ranks. One torchrun per node (srun starts them), c10d rendezvous
# on the first node of the allocation. Submit as a lab user: su alice -c "sbatch /shared/jobs/train.sbatch"
# Extra arguments go to train.py, e.g. sbatch train.sbatch --steps 400 --step-sleep-ms 50. RUN names the output dirs.
#SBATCH --job-name=mi-train
#SBATCH --nodes=2
#SBATCH --ntasks-per-node=1
#SBATCH --cpus-per-task=2
#SBATCH --gres=gpu:2
#SBATCH --time=00:10:00
#SBATCH --output=/shared/out/%x-%j.out
#SBATCH --requeue
set -euo pipefail
export MASTER_ADDR=$(scontrol show hostnames "$SLURM_JOB_NODELIST" | head -n1)
export MASTER_PORT=29500
RUN=${RUN:-slurm-$SLURM_JOB_ID}
echo "job $SLURM_JOB_ID nodes $SLURM_JOB_NODELIST master $MASTER_ADDR:$MASTER_PORT restart ${SLURM_RESTART_COUNT:-0}"
srun --kill-on-bad-exit=1 torchrun --nnodes="$SLURM_NNODES" --nproc-per-node=2 \
  --rdzv-backend=c10d --rdzv-endpoint="$MASTER_ADDR:$MASTER_PORT" --rdzv-id="$SLURM_JOB_ID" \
  /opt/mi/train.py --ckpt-dir "/shared/ckpt/$RUN" --log-dir "/shared/logs/$RUN" "$@"
job 1 nodes c[1-2] master c1:29500 restart 0

# The running example on Kubernetes: a JobSet with one replicated Job of 2 pods (Indexed), each pod one
# "node" running torchrun with 2 ranks. Kueue admits the whole JobSet at once (gang) from LocalQueue mi-lq.
# Rendezvous is static: pod index 0 hosts the c10d TCPStore; the others reach it through the headless
# Service JobSet creates (DNS name <jobset>-<replicatedJob>-<job index>-<pod index>.<jobset>).
# Submit: kubectl create -f train-jobset.yaml   (RUN names the output folders under /shared)
apiVersion: jobset.x-k8s.io/v1alpha2
kind: JobSet
metadata:
  name: mi-train
  namespace: mi
  labels:
    kueue.x-k8s.io/queue-name: mi-lq
spec:
  failurePolicy:
    maxRestarts: 0
  replicatedJobs:
  - name: node
    replicas: 1
    template:
      spec:
        parallelism: 2
        completions: 2
        completionMode: Indexed
        backoffLimit: 0
        template:
          spec:
            restartPolicy: Never
            containers:
            - name: trainer
              image: mi-train:1
              imagePullPolicy: Never
              env:
              - {name: RUN, value: ex-k8s}
              command: ["sh", "-c"]
              args:
              - >-
                exec torchrun --nnodes=2 --nproc-per-node=2 --node-rank=$JOB_COMPLETION_INDEX
                --master-addr=mi-train-node-0-0.mi-train --master-port=29500
                /opt/mi/train.py --ckpt-dir=/shared/ckpt/$RUN --log-dir=/shared/logs/$RUN
              resources:
                requests: {cpu: "1", memory: 900Mi, example.com/gpu: "2"}
                limits: {cpu: "2", memory: 900Mi, example.com/gpu: "2"}
              volumeMounts:
              - {name: shared, mountPath: /shared}
            volumes:
            - name: shared
              hostPath: {path: /shared, type: Directory}

Run with python ray_train.py on a Ray 2.59.0 cluster of three containers (head plus 2 workers). Ray Train placed 4 worker actors, set the environment itself and initialised the gloo process group (env://) before calling the training function.

The training code is identical in all three, and so is the result: the global loss agreed bit for bit at all 21 logged steps on Slurm, Kubernetes and Ray (step 200: 2.2638769149780273) measured (src/data/runs/compare.json). Only who starts the processes and how they learn each other's address changed: c1 from Slurm's node list, a pod DNS name from JobSet, an IP chosen by Ray. That difference is section 4.

Who uses what (dated evidence)

There is no census of training clusters, so the honest evidence is what operators say about their own runs. The largest labs mostly run their own schedulers or heavily extended Kubernetes; Slurm dominates supercomputers and the GPU clouds that rent clusters for training; Ray sits on top as a runtime, notably for reinforcement learning.
