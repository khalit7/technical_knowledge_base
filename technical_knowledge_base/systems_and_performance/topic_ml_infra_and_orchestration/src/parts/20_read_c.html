4. Launching a distributed job and finding peers

The problem. The scheduler hands you nodes; your training script needs one process per GPU, each knowing who it is and how to reach the others. Four numbers say who a process is: its rank (0 to W−1 across the job), the world size W (how many processes), its local rank (its index on its own node, which picks its GPU) and its node's index. A launcher starts the processes and gives them those numbers, usually as environment variables (RANK, WORLD_SIZE, LOCAL_RANK):

  • torchrun (PyTorch's launcher, also called the elastic agent) runs once per node and starts --nproc-per-node workers, restarting them if they fail.
  • Slurm: srun starts tasks on every node of the allocation and sets SLURM_PROCID, SLURM_NTASKS, SLURM_LOCALID and the node list; scripts either map those to PyTorch's names or run one torchrun per node.
  • Kubernetes: each pod of an indexed Job or JobSet gets an index and, through a headless service, a stable DNS name, so pod 0's name can serve as the meeting address.
  • Ray Train starts the worker actors and sets all of it itself.

Rendezvous is how the processes meet. Everyone is told one address, MASTER_ADDR:MASTER_PORT (usually rank 0's node); a small key-value server there, PyTorch's TCPStore (the "c10d store"), collects each rank's details, and nobody proceeds until all W have arrived. Then init_process_group builds the process group, the communicator that collectives such as all-reduce run on: gloo on CPUs (what this page's running example uses), NCCL on NVIDIA GPUs, which shares a unique id through the same store and then wires up its own rings and trees between GPUs.

Rendezvous, step by step: 2 nodes, 4 ranks

Order of events as PyTorch implements it; the timeouts are the defaults in torch 2.14.1 (30 minutes for a gloo process group, read from the installed package; 10 minutes for NCCL, {{ProcessGroupNCCL.hpp line 159|https://github.com/pytorch/pytorch/blob/v2.14.1/torch/csrc/distributed/c10d/ProcessGroupNCCL.hpp#L159}}; 600 s for torchrun's dynamic (c10d) rendezvous to complete, {{dynamic_rendezvous.py|https://github.com/pytorch/pytorch/blob/v2.14.1/torch/distributed/elastic/rendezvous/dynamic_rendezvous.py#L1405}}; 900 s for its default static rendezvous, because torchrun's launcher fills in that timeout, {{launcher/api.py lines 125-130|https://github.com/pytorch/pytorch/blob/v2.14.1/torch/distributed/launcher/api.py#L125-L130}}, overriding the static backend's own 600 s).

What it looked like when one node of the running example never arrived, in the {{Launch lab|#t-launch}}: on Slurm (c10d rendezvous) nothing was logged for ten minutes, then at 602 s a bare torch.distributed.elastic.rendezvous.api.RendezvousTimeoutError with no message; on Kubernetes (static rendezvous) at 903 s, torch.distributed.DistStoreError: Timed out after 901 seconds waiting for clients. 1/2 clients joined.; on Ray, a fifth worker that could never be placed, the job never failed at all: The worker group startup timed out after 60.0 seconds waiting for 5 workers, retried every 60 s indefinitely (13 attempts in about 12 minutes, until it was stopped by hand) measured. Those times are set by timeouts, so they repeat; every waiting process held its CPUs (and fake GPUs) the whole time.

What it costs, and why it matters. The start of a job is a chain: wait in the queue, pull the container image to every node, start the containers, rendezvous, build the communicators, load the first batch, run the first step. Repeated five times per system (2 nodes x 2 ranks, the image already on every node), the running example's median from submit to its first finished step was 7.5 s on Slurm, 5.8 s on Kubernetes and 10.0 s on Ray measured on Apple M1 Pro, Docker Desktop VM, shared machine. By stage (medians, which need not add up to the median total): Slurm 0.7 s from sbatch to the batch script, 1.3 s for torchrun to import, 1.1 s of c10d rendezvous (the dynamic backend polls once a second), 2.5 s to spawn the workers and import torch, 0.01 s for init_process_group, 2.0 s for data, model and the DDP wrapper; Kubernetes 0.9 s for Kueue admission, scheduling and container start, 1.9 s of torchrun imports, 0.03 s of static rendezvous, 1.1 s of worker start, 1.3 s of data, model and DDP; Ray 1.6 s for the driver to import Ray, then 4.4 s for Ray Train's controller, placement group and worker processes, 0.9 s until the worker actors were ready, 0.3 s for the process group and 2.0 s for data, model and DDP. Pulling the image is not in these numbers; on a real cluster a multi-gigabyte image pulled to every node is often the longest stage, which is why images are cached on nodes. At thousands of GPUs every link of that chain is paid on every restart, which is why section 5's failure arithmetic counts restart time.

How a launch goes wrong. Almost every multi-node launch failure is a hang, not a crash, because the ranks that did arrive wait politely for the ones that did not. The usual causes: a wrong MASTER_ADDR (a name that resolves differently on each node), a port blocked by a firewall, a world size that does not match the processes actually started, a rank that crashed before it reached the store, or, after start-up, one rank stuck while the others wait inside a collective. The tools: TORCH_DISTRIBUTED_DEBUG=DETAIL and NCCL_DEBUG=INFO for logs, py-spy dump on a hung process to see where it waits, and PyTorch's flight recorder, which records each rank's last collectives so you can find the rank that is out of step. One trap, measured here on CPU builds only (torch 2.14.1 in a Linux container and on macOS; CUDA builds not checked): TORCH_DISTRIBUTED_DEBUG=DETAIL with DDP crashed the process with a segmentation fault (exit code -11) inside DDP's constructor, before any training; INFO worked, and DETAIL on raw collectives did report the mismatch. If DETAIL crashes, fall back to INFO.

Predict: a 512-GPU job has printed nothing for 20 minutes after start. 511 ranks' logs end at "init_process_group". What is the most likely cause?
The 511 identical logs are the clue: they are all waiting for the 512th. Look for the missing rank (the scheduler's per-node logs, that node's container status, a crash before init), not at the 511 that are fine. Running out of memory would crash with an error, not hang at init.
