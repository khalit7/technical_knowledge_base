2. What is in a checkpoint

A checkpoint is everything needed to continue training as if nothing had happened: the weights, the optimiser's state, the step number, and anything else that carries state (random number generators, the data loader's position, the learning-rate schedule). Leave any of it out and a resumed run differs from an uninterrupted one. The running example needs only three things, because its batches depend only on (seed, step) and it uses no randomness after initialisation; this is why its resume is bit-exact.

Why optimiser state dominates. AdamW keeps two numbers per parameter, a running mean of the gradient and of its square, each in fp32: 8 bytes, on top of the 4-byte fp32 weight. Mixed-precision training adds the bf16 copy the GPU computes with:

bytes per parameter = weights + master copy + 2 moments
fp32 training (this run)
4 + 0 + 8 = 12, plus the pickle and zip overhead here: 12.31 measured
bf16 mixed precision
2 (bf16 weights) + 4 (fp32 master) + 8 = 14, the common case (the Reading tab's figure; layouts vary: some frameworks save only the fp32 master and rebuild bf16 weights, 12)
weights for inference
2 (bf16 only): a "checkpoint" exported for serving is 7 times smaller and cannot resume training

All rows derived: size = parameters x bytes per parameter; per GPU = size / GPUs (64 and 1,024 GPUs for the 8B and 70B rows are illustrative choices), assuming the optimiser state is sharded over every GPU (as with FSDP or ZeRO-3 across all data-parallel ranks). Llama 3 405B trained on up to 16,384 GPUs ({{Llama 3 §3.3|https://arxiv.org/html/2407.21783v3#S3.SS3}}); the paper says its checkpoint writes range "from 1 MB to 4 GB per GPU", and 346 MB per GPU falls inside that range: a consistency check, not a reproduction. DeepSeek-V3 has 671B parameters and trained on 2,048 H800 GPUs ({{DeepSeek-V3 report|https://arxiv.org/abs/2412.19437}}); its real per-GPU layout (expert parallelism, FP8) differs, so its row shows only the arithmetic.
