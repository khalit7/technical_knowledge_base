Storage lab: where data and checkpoints live

A training job touches storage in two very different ways. It reads its data as a steady stream, which is easy to hide behind compute. And every so often it writes a checkpoint: every rank at the same moment, while the GPUs wait. This lab measured both with the running example on this Mac; at root depth it keeps the tiers compared, the measured results in one table, and one calculator that scales the arithmetic up to real model sizes. How parallel file systems and object stores work inside, and how to size one, is the child page {{Storage and data movement|n:3fc5c17b0d0d818a94ced3fc7c3331fe}}. The question it keeps returning to: how long does training stand still to save itself, and what does it take to make that short?

In one screen
  • A checkpoint is mostly optimiser state. The running example's 1,386,049-byte file is 32.5% weights and 65.0% AdamW moments: 12.3 bytes per parameter. With mixed precision it is about 14, so a 405B model's checkpoint is about 5.7 TB derived.
  • The tier decides the time. The same 304 MB checkpoint took to a Docker volume and to a host folder shared into the VM measured: slower, the gap between local disk and a network file system in miniature. The same shared folder made the Kubernetes runs' checkpoints slower than Slurm's.
  • Shard and go asynchronous. Every rank writes its own piece (sharded), and copies it to memory first so training continues while it uploads (asynchronous). On the slow folder, async cut the time training stood still per checkpoint from to measured.
  • At scale it is bandwidth arithmetic: size / aggregate write bandwidth. A parallel file system sells bandwidth as capacity, so you size it for the checkpoint burst, not for the bytes stored.

1. The tiers, from zero

Storage is a ladder: the closer to the GPU, the faster, smaller and more fragile. Five rungs matter for training:

  • Host RAM: the node's own memory. A copy from GPU memory crosses PCIe and takes seconds; lost if the node dies.
  • Local NVMe: SSDs inside the node. Fast and private to the node; gone (or unreachable) with it.
  • Parallel file system (Lustre, IBM Storage Scale/GPFS, WEKA, VAST, Meta's Tectonic, DeepSeek's 3FS): one namespace mounted on every node, each file striped over many storage servers so thousands of clients read and write at once. Metadata (names, directories, opens) is served separately, by metadata servers.
  • NFS: one file server exporting a directory over the network. Simple; one server's link is its ceiling.
  • Object storage (S3, Google Cloud Storage, Azure Blob, on-premises S3-compatible stores): whole objects addressed by key over HTTP. Nearly limitless and cheap; each request pays tens of milliseconds; no appends or in-place edits; an object appears only when its upload completes.
