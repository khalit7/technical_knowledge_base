5. Hangs: the failure that does not crash

A frozen rank is worse than a dead one: nothing exits, no exit code reaches anybody, the GPUs of every other rank sit in an all-reduce doing nothing. To make one, we sent SIGSTOP to rank 3's process after step 120 (it stays alive and holds its sockets open) with the process-group timeout set to 30 s.

[rank0]: RuntimeError: [.../gloo/transport/tcp/unbound_buffer.cc:129] Timed out waiting 30000ms for send operation to complete [rank1]: RuntimeError: [.../gloo/transport/tcp/unbound_buffer.cc:78] Timed out waiting 30000ms for recv operation to complete ... Root Cause (first observed failure): [0]: host : c1 rank : 0 (local_rank: 0) exitcode : 1 (pid: 1972)

measured: job 51 (runs/fl-hang/job51.out, trimmed). The three healthy ranks errored 30.8 s after the freeze, and the job failed.

Predict: which rank does torchrun's "Root Cause (first observed failure)" name?
A healthy one: rank 0 on c1. "First observed failure" means the first process to exit with an error, and in a hang that is a victim that timed out first; the frozen rank never errors, it only received SIGTERM during clean-up. In a hang, read the timeout messages for which rank everyone was waiting on (the one that did not time out), and get stacks from the stuck processes (py-spy dump, the {{Launch lab's hang drills|#t-launch}}) or PyTorch's flight recorder, which in torch 2.14.1 records gloo collectives too (the {{Launch lab|#t-launch}} dumped it from a stalled rank on CPUs and found that rank one collective behind).

The timeout is a trade-off you own. Detection time equals the collective timeout. PyTorch's defaults in 2.14 are 30 minutes for gloo and 10 minutes for NCCL, so with defaults a frozen GPU costs every other GPU in the job up to 10 minutes of nothing before anyone acts. Too short, and legitimate pauses kill healthy runs: a slow checkpoint save, an evaluation on rank 0 while the others wait at a barrier, a long first compilation. Large runs therefore add their own watchdogs: Llama 3 used PyTorch's NCCL flight recorder, "a feature that captures collective metadata and stack traces into a ring buffer", and dumped it automatically "on NCCLX watchdog or heartbeat timeout" published ({{section 3.3.4|https://arxiv.org/html/2407.21783v3#S3.SS3.SSS4}}). In stock PyTorch 2.14.1 the two NCCL messages are different events: Watchdog caught collective operation timeout: ... ran for ... milliseconds before timing out. (a collective exceeded its timeout) and ProcessGroupNCCL's watchdog got stuck for ... seconds without making progress in monitoring enqueued collectives. (the watchdog thread itself hung; the heartbeat monitor waits 480 s by default), {{ProcessGroupNCCL.cpp lines 735-739 and 1954|https://github.com/pytorch/pytorch/blob/v2.14.1/torch/csrc/distributed/c10d/ProcessGroupNCCL.cpp#L1954}}.

6. Stragglers: slow is not dead

A straggler is a rank that keeps working, slowly: a GPU throttling on heat, a flapping link, a noisy neighbour. Nothing fails, so no scheduler acts, but because every step waits for every rank, the whole job runs at the straggler's pace. We made rank 3 sleep 50 ms or 200 ms after every step.

One slow rank sets the pace of all four

measured: step time per rank from logged timestamps, steps 10 to 100 (runs fl-strag0, fl-strag50, fl-strag200 on Slurm, 2 nodes x 2 ranks). The split of each step into compute and waiting is drawn from the measured totals and the probe below illustrative split.

Every rank reports the same step time (22.1, 70.5 and 221.8 ms), so a step-time log cannot tell you who is slow. Time spent inside the gradient all-reduce can. We wrapped loss.backward() (which contains DDP's all-reduce) with a timer on every rank:

measured: median backward() time per rank, steps 11 to 100 (runs fl-probe0, fl-probe50; probe in src/fail/scripts/fl_wrap.py, FL_PROBE=1).

The slow rank is the one that waits least. With rank 3 sleeping 50 ms, ranks 0 to 2 spent about 62.6 ms in backward and rank 3 only 12.2 ms: it arrives last, so it never waits. Monitoring that flags the rank with the longest collective time finds the victims, not the culprit. Fleet tools compare per-rank compute time before the collective, or collective durations from the flight recorder, across all ranks. The cost side (how much a 1% straggler costs a 16,000-GPU run) is on {{Training Infrastructure|n:3c65c17b0d0d81c9b2cac997583bf572}}.

7. Keeping bad nodes out: drain, cordon, taints, health checks

Restarting onto the same broken machine just fails again, so every system has a way to say "schedule nothing new here". On Slurm a node is drained: running jobs finish, nothing new starts. On Kubernetes it is cordoned (marked unschedulable) or tainted (a taint repels every pod that does not tolerate it; a NoExecute taint also evicts running ones). A health check is the program that decides, run before jobs, between them, or on a timer.

A health check that drains its own node. Slurm runs HealthCheckProgram on every node every HealthCheckInterval seconds, as root, and ignores its exit code: the script must drain the node itself. This one checks that the node's four (fake) GPU devices exist; a real one runs nvidia-smi or dcgmi diag, scans the kernel log for Xid errors, and checks ECC counters, NVLink and InfiniBand ports.

#!/bin/sh
NODE=$(hostname)
missing=""
for i in 0 1 2 3; do [ -e /dev/mi_gpu$i ] || missing="$missing mi_gpu$i"; done
if [ -n "$missing" ]; then
  scontrol update nodename="$NODE" state=drain reason="healthcheck: missing$missing"
  exit 1
fi
exit 0

src/fail/scripts/fl_healthcheck.sh, with HealthCheckProgram=/shared/jobs/fl/fl_healthcheck.sh, HealthCheckInterval=10, HealthCheckNodeState=ANY added to slurm.conf for the test, then removed. Moving one device file away drained the node within 1.4 to 7.3 s in four tries measured: anywhere up to one interval, depending on where in the cycle the fault lands.

The Kubernetes trap measured in section 2. A node that goes silent becomes NotReady after 50 s and gets the taint node.kubernetes.io/unreachable:NoExecute; pods tolerate it for 300 s by default, then are marked for deletion. But a pod is only gone when its kubelet confirms it, and a dead kubelet never does, so the pod stays Terminating and anything waiting for it waits forever. The fix is to tell the cluster the node is really down:

kubectl taint node mi-kind-worker2 node.kubernetes.io/out-of-service=nodeshutdown:NoExecute

measured: 2 s after this taint the stuck pod was force-deleted, the JobSet restarted on two healthy workers and the run resumed from step 100 (runs/fl-k3). Remove the taint once the node is repaired. Clusters automate this with a node-health controller rather than a person.

8. Elastic training and hot spares, measured with torchrun

Elastic training lets a job continue with fewer machines instead of stopping: torchrun --nnodes=1:2 accepts any number of nodes between 1 and 2. Each node runs an agent; the agents meet at a rendezvous (here the c10d backend: a small key-value store that one of the agents hosts) to agree who is in the job, then start the workers. When a worker fails, every agent stops its workers, meets again with whoever is still there, and restarts them all from the latest checkpoint with the new world size.

Lose one of two nodes, then add one back

measured in one container capped at 2 CPUs and 2.2 GB: two torchrun agents (A, B) of 2 ranks each, c10d rendezvous on localhost, 400 steps, checkpoints every 50; B and its ranks are killed with SIGKILL (src/fail/scripts/fl_elastic.sh, fl_spare.sh; runs el3, el4).

Where the 44 seconds go. Agent A saw its ranks fail 1.5 s after the kill. It then waited for the rendezvous to forget B, whose keep-alive stops counting after 5 s x 3 attempts, and for the last call: once the minimum number of nodes is present the rendezvous still waits 30 s for more before closing. With a spare already waiting, the job was full again at once and only paid detection and restart: 18.1 s.

Three things the runs taught.

  • The agent that hosts the store is a single point of failure. In our first attempt the killed agent happened to be the one hosting the c10d store, and the survivor died with RendezvousConnectionError: The connection to the C10d store has failed. Which agent hosts it is decided by whose host name matches the endpoint and who binds first (c10d_rendezvous_backend.py lines 145 and 165: "Process ... hosts the TCP store for the C10d rendezvous backend"). Put the endpoint on the most stable machine, or use an external etcd rendezvous.
  • Restarts reuse the rendezvous store by default, and that broke multi-node restarts here. Since PyTorch shares the rendezvous TCP store with the workers, the store server is created once and reused across rounds (dynamic_rendezvous.py lines 1209-1218; and in torch/distributed/rendezvous.py line 205 the comment "We create a new TCPStore for every retry so no need to add prefix for each attempt"). Our 2-node Slurm restarts then failed to connect; TORCH_DISABLE_SHARE_RDZV_TCP_STORE=1 (read at lines 1146 and 1194) fixed them, and the elastic runs here used it. The mechanism, isolated on the child page Launching distributed training (torch 2.14.1, gloo): the rank-0 agent keeps one workers' store for every round, while the workers' side assumes a fresh store per attempt (the rendezvous.py:205 comment above), so attempt 1 found attempt 0's keys still there, including both stale gloo address keys, and dialled dead addresses. Which rank loses is a race: in one run rank 1 got "Connection refused" and rank 0 timed out after 300 s; in the other, rank 0 was refused and rank 1 lost the store. Growing an elastic job deadlocks too: rank 0 does not republish the bootstrap info when the store already exists (dynamic_rendezvous.py line 1209), so the new node waits for MASTER_ADDR until the 60 s store timeout ("wait timeout after 60000ms, keys: .../MASTER_ADDR"). With the variable set, each attempt gets a new store on a new port, and on that page's run the restart resumed 4.3 s after the crash. Test your own restart path before relying on it.
  • Shrinking counts as a restart; growing does not. The restart counter went to 1 when B was lost and stayed at 1 when C joined: "membership changes do not count as retries" (elastic/agent/server/api.py line 958). And the shrunk run is not the same computation: the global batch stays 32 sequences, but each of 2 ranks now averages 16 rows instead of 8, so the sums happen in a different order and the loss differs in the last bits at 7 of the 15 logged steps run at world size 2 (by up to 4.8e-7) against an uninterrupted 4-rank run measured. With a batch that does not divide evenly, or a data loader that shards by rank, it would also change which data each step sees.

Most large pre-training runs do not shrink: a smaller world changes the batch per GPU, the parallelism layout and the learning-rate schedule's assumptions. They restart at full size on spare capacity instead: for Gemini Ultra, Google decided "to retain a small number of cubes per superpod to allow for hot standbys and rolling maintenance" ({{Gemini 1.0, section 3|https://arxiv.org/abs/2312.11805}}) published. The spare run above is that pattern at toy scale.
