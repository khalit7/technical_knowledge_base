5. Checkpoint-time calculator: from this laptop to 16,384 GPUs

At scale the measurement turns into arithmetic. Three numbers decide how long a checkpoint stops training: its size, the slowest pipe it must squeeze through (one node's link for a consolidated write; all the nodes' links or the storage system's aggregate bandwidth, whichever is smaller, for a sharded one), and, for asynchronous checkpointing, the copy of each GPU's shard to host memory. Defaults check: 405B at 14 bytes on 16,384 GPUs gives 5.67 TB, 346 MB per GPU (inside Llama 3's stated 1 MB to 4 GB per GPU) and 2.8 s at Tectonic's 2 TB/s sustained. Simplifications, said plainly: no metadata or file-creation cost, no gather time for the consolidated write, perfect parallelism, and a store that sustains its rated bandwidth under a burst (Meta built Tectonic's 7 TB/s peak for exactly this). 6. Reading data: big files, prefetch, and the small-files problem

Reading training data is the easy pattern: sequential, predictable, and small next to the compute for text (the {{throughput calculator on Storage and loading|n:3f95c17b0d0d81398782efcb29d950d4}} shows Llama 3 405B needed about 11 MB/s of token ids for the whole job). Two things still go wrong, and both are about requests, not bytes. Measured with 64 MiB of the running example's token ids, stored as 16 files of 4 MiB or as 16,384 files of 4 KiB (the same bytes), on a Docker volume and on the S3 store, from one container measured:

The small-files problem. Each file costs an open, a metadata lookup and a close; each object costs an HTTP request. At 4 KiB per file those fixed costs are the whole bill. On a parallel file system they land on the metadata servers, which are far fewer than the storage servers: FSx for Lustre, for example, includes 1,500 metadata IOPS at 1.2 TiB and serves 2 file create/open/close operations per metadata IOPS vendor ({{AWS|https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance.html}}), so a thousand nodes each opening millions of tiny files saturate it long before the disks are busy. The cure is the one {{Storage and loading|n:3f95c17b0d0d81398782efcb29d950d4}} teaches: pack samples into shards of tens to hundreds of megabytes. Checkpoints obey the same rule: DCP writes one file per rank, not one per tensor.

Prefetch. A loader that fetches the next shard only when it needs it adds the fetch to every step; one that keeps the next shards in flight hides it, as long as fetching is faster than computing. A loop that needs one 4 MiB shard per step and computes for 100 ms (a sleep standing in for the GPU):

7. Restoring: when a checkpoint will not load

A checkpoint is only as good as its restore, and restores fail in a few recognisable ways. Each of these is a real message from this lab (torch 2.14.1):

Resharding works. The 4-rank DCP checkpoint loaded into 2 ranks and into 3 ranks, and into a single process with no process group at all, each time tensor for tensor identical to the full state measured. DCP's .metadata records which byte ranges of which tensor live in which file, so any number of ranks can ask for the pieces they now own. A consolidated torch.save file can also be loaded anywhere, but only by first reading the whole thing into one process.

Is the resume exact? The running example resumes bit-exactly (the setup checked it: global loss at steps 150 and 200 identical to an uninterrupted run), because its checkpoint holds everything that carries state. 8. Common mistakes

Writing the checkpoint in place, or renaming without fsync
A crash mid-write leaves a half file, and the next start loads it: "PytorchStreamReader failed reading zip archive: failed finding central directory" (above). train.py writes step_N.pt.tmp, renames it, then updates latest: a reader never sees a partial file. But it does not call fsync before the rename, so after a power loss (not a process crash) the renamed file can still be empty on some file systems. Write, fsync the file, rename, fsync the directory; on macOS, F_FULLFSYNC. Object stores give atomicity for free: an object appears only when its upload completes.
Every rank saves the full state
The forgotten if rank == 0 in DDP: N copies of the same bytes, at the same moment, on the same storage. Here, 4 times the bytes took 3 times as long on a shared pipe. Use rank 0 for small DDP models, DCP for anything sharded.
Consolidating a sharded model to one file every time
Gathering the full state onto one rank needs that rank to hold all of it in memory and pushes it through one node's link. Save sharded during training; consolidate once, offline, when exporting.
Running async checkpointing on the training process group
Two threads issuing collectives on one group: a hang or a crash ("op.nread == op.preamble.nbytes" with gloo here). Give async_save its own group.
Starting the next async checkpoint before the last one finished
If the upload takes longer than the interval, checkpoints pile up in host memory. Wait on the previous future before staging the next (dist_ckpt.py does), and size the interval so the upload fits.
Trusting that a path is local
On kind, /shared looks like any directory and was 36 times slower than Slurm's volume for the same 1.39 MB file. Measure a mount with the real write (size, fsync, rename) before putting checkpoints on it.
Millions of small files on a parallel file system
Metadata servers, not disks, become the limit; the whole cluster slows down, not only your job. Shard data and keep checkpoint files per rank, not per tensor.
Keeping every checkpoint, or only the last one
Every checkpoint of a 405B run is 5.7 TB; keeping all of them is expensive. Keeping only the latest means one corrupted or bad checkpoint (a loss spike saved right before a crash) leaves nothing to fall back on. Keep the last few, plus periodic milestones, and delete the rest automatically.

9. Interview questions

How big is the checkpoint of a 70B model trained with AdamW in mixed precision, and how long does it take to write?
About 14 bytes per parameter (bf16 weights 2, fp32 master 4, two fp32 moments 8): 0.98 TB. Time = size / the slowest pipe: at 100 GB/s of aggregate storage bandwidth, about 10 s if sharded across enough nodes that their links are not the limit; through one node's 50 GB/s link (consolidated), about 20 s plus the gather.
Your 1,024-GPU job spends 8% of its time checkpointing. What do you do?
First measure where the time goes: gather, serialisation, or storage bandwidth. Then: shard (DCP) so every node writes in parallel; go asynchronous so training stops only for the GPU to host copy; check the storage system's aggregate bandwidth against size / target time and buy bandwidth if it is the limit; and choose the interval from the failure rate (the Young/Daly optimum in the {{Failure lab|#t-fail}}), not by habit.
Why can't you just checkpoint to local NVMe?
You can, and should, as a first stage: it is fast and parallel. But a checkpoint on a node that dies is gone or unreachable, and the restarted job usually lands on different nodes. So copy it onward (to the parallel file system or object storage) in the background, or replicate it to peers' memory or disks as Gemini did.
Lustre or S3 for checkpoints?
A parallel file system gives the highest burst bandwidth and POSIX semantics (rename, partial reads), but it is priced by capacity and its bandwidth comes with capacity. Object storage is cheap and scales with parallel requests, with tens of milliseconds per request and whole-object writes. Common answer: write to the parallel file system or local NVMe on the critical path, then copy to object storage for durability and retention.
A job resumed from a checkpoint and the loss jumped. What do you check?
Whether the checkpoint holds everything that carries state: optimiser moments (a fresh AdamW restarts its estimates), the learning-rate schedule's step, data loader position (the data seen again or skipped), and RNG states. Then whether the world size or parallel layout changed and the load resharded correctly; then whether you loaded the latest complete checkpoint and not a partial one.
