Launch lab: how a multi-node job starts and finds its peers

A scheduler hands your job some machines. Nothing has trained yet: one process per GPU must start on every machine, learn who it is, find all the others and build a communicator with them. This lab starts the same small training job on three real systems running on one laptop (Slurm, Kubernetes and Ray), times every stage from submit to the first training step, dumps the environment each system hands the processes, and breaks the start-up on purpose to record the real error messages and how long each one takes to appear.

What ran (16 October 2026)

The running example of this page: a tiny GPT (112,577 parameters) trained on TinyShakespeare with DDP over gloo (PyTorch's CPU communication backend, standing in for NCCL), 2 "nodes" × 2 processes = 4 ranks, the same image (torch 2.14.1+cpu) everywhere. The nodes are containers on one Docker Desktop VM (5 CPUs, 9.7 GiB) on an Apple M1 Pro shared with other jobs, so every measured time is rough: it is labelled, repeated, and shown as a median with its range. The order of events, the environment variables, the error messages and the timeouts do not depend on the machine.

1. From zero: processes, ranks and world size

Data-parallel training runs one copy of the training script per GPU. Each copy is an ordinary operating-system process. To cooperate, every process needs four numbers:

  • world size W: how many processes the job has (here 4);
  • rank: this process's number, 0 to W−1, unique across the whole job (rank 0 usually writes checkpoints and logs);
  • local rank: its number on its own machine, 0 to (processes per node)−1; on a GPU node it picks the GPU (cuda:LOCAL_RANK);
  • node rank (torchrun calls it GROUP_RANK): which machine it is on.

And one address: where to meet. That address, MASTER_ADDR:MASTER_PORT, is where a small key-value server will run so the processes can exchange what they need to connect to each other. The picture is the running example as it ran on Kubernetes:

2. The launcher's job

A launcher is whatever starts those processes and hands them their numbers. Every system has one, and they stack: the scheduler starts something on each node, which starts the training processes.

The common pattern on Slurm and Kubernetes is two layers: the scheduler starts one torchrun per node, torchrun starts one worker per GPU. torchrun earns its place by doing the rendezvous between nodes and by restarting workers; a script launched directly by srun has to map SLURM_PROCID to RANK itself (section 7 does exactly that, and gets it wrong on purpose).
