Predict: the Slurm script passes --rdzv-endpoint=c1:29500 to torchrun. Which MASTER_PORT do the training processes see?
A random port. With the dynamic (c10d) backend, port 29500 belongs to the agents' rendezvous store. After the agents meet, the agent that became node rank 0 starts a second TCPStore on a free port (port 0, so the operating system picks one) and publishes its address and port through the rendezvous store; every agent passes them to its workers as MASTER_ADDR and MASTER_PORT. On Kubernetes, with the static backend, the workers see 29500 itself, because there the agents' store is the workers' store. A firewall rule that opens only 29500 therefore breaks the Slurm-style launch and not the static one.

6. Building the process group: gloo here, NCCL on GPUs

init_process_group creates the process group: the object collectives such as all_reduce run on. It needs a store (from the rendezvous) and a backend, the library that moves the bytes:

  • gloo (what ran here): each rank opens a listening socket, writes its address into the store, reads everyone else's, and connects to every other rank (a full mesh of TCP connections). Collectives then run over those sockets on the CPU.
  • NCCL (NVIDIA GPUs; described, not run): rank 0 creates a unique id (ncclGetUniqueId, which contains the address of a bootstrap socket), PyTorch passes it to every rank through the store, and each rank calls ncclCommInitRank. NCCL then runs its own bootstrap over sockets: ranks exchange their addresses and topology, detect NVLink, PCIe and network cards (InfiniBand or RoCE through verbs, or TCP sockets), and build rings and trees for each collective. Most "NCCL hangs at init" are this bootstrap choosing a network interface the other nodes cannot reach.
