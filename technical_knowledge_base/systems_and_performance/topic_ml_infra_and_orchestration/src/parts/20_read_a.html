1. What a training cluster is

A node is one server: typically 8 GPUs, two CPUs, local NVMe disks and one network card per GPU (Meta trained Llama 3 405B on servers of eight GPUs and two CPUs, up to 16K H100s in all, {{Llama 3 §3.3.1|https://arxiv.org/html/2407.21783v3#S3.SS3.SSS1}} published). A cluster is many nodes plus four things that make them one machine:

  • Two networks for GPUs. Inside a node, GPUs talk over NVLink (the scale-up domain); between nodes, over a scale-out fabric, InfiniBand or Ethernet with RDMA (RoCE), usually one 400 Gb/s card per GPU. Per direction an H100's NVLink is about 9 times one such card (450 against 50 GB/s), which is why tensor parallelism stays inside a node and data parallelism crosses nodes ({{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}} owns these numbers).
  • A front-end network (ordinary Ethernet) for logins, the scheduler, container images, data and checkpoints, unless storage has its own fabric.
  • Shared storage that every node sees: a parallel file system or object storage (section 6).
  • Control nodes: login nodes where users submit, and the controller or head node that tracks every node and job (Slurm's slurmctld, Kubernetes' API server and scheduler, Ray's head node). What each runs, and how one job lands on the machines step by step, is {{Cluster anatomy|n:3fc5c17b0d0d816a871df56477fc83b2}}, section 3 (its job stepper).

Two units recur everywhere: the GPU-hour (cost and quota) and the rank (one process, normally one per GPU; a job on 128 nodes of 8 GPUs has 1,024 ranks).

2. How a job gets machines: one vocabulary for every scheduler

There are more jobs than GPUs, and a distributed job is useless until it holds all its GPUs at once. A scheduler (also workload manager or batch system) keeps a queue of requests (8 nodes of 8 GPUs for 12 hours) and a policy that decides which starts next and where. Every system in this topic combines the same seven ideas; section 3 shows how each expresses them.

  • FIFO with priorities. First in, first out, ordered by a priority number; one big job at the head blocks everything behind it while nodes idle (head-of-line blocking).
  • Backfill. A later, smaller job may use idle nodes if it ends before the big job could have started anyway, which the scheduler knows only from each job's time limit (Slurm's --time). EASY backfill protects only the first waiting job's reserved start; conservative backfill protects every waiting job.
  • Fairshare. Each team has a share; recent usage above it lowers the team's priority, and past usage decays (a half-life of days to weeks).
  • Preemption. A more important job evicts a running one, which is killed or requeued; cheap only if the victim checkpoints (section 5).
  • Gang scheduling. All of a job's processes start together or none do (the figure below).
  • Topology-aware placement. A job's nodes go under as few switches as possible, because collectives across distant switches are slower.
  • Quotas and borrowing. Teams own a guaranteed amount; idle quota is lent and reclaimed (by preemption) when the owner needs it.

Backfill on real Slurm. The {{Scheduling lab|#t-sched}} ran one eight-job queue on the topic's Slurm cluster with backfill off and on: the queue drained at 16:48 against 14:48, utilisation of the 8 GPUs rose from 71% to 80%, and the mean wait fell from 8:09 to 3:06 (minutes:seconds) measured. The price is honest time limits: a job that asks for three times what it needs looks too long for any gap and is never backfilled.
