Scheduling lab: how a job gets machines

A cluster is a pool of GPUs and a queue of jobs that want them. A scheduler decides which waiting job starts next and on which machines. This lab sends the same small workloads through three real schedulers running on one laptop and records what each one did, from its own logs and accounting.

Job and request

A unit of work that asks for resources: 8 GPUs on 1 node for 2 hours. It holds them from start to end, even while it does nothing with them.

Time limit

The longest a job may run (--time in Slurm). The scheduler plans with it, because it cannot know the real runtime; the job is killed when it is reached.

Queue and priority

Pending jobs in the order the scheduler will consider them. Priority is the number that sets that order: submit time, user, fairshare, partition.

Utilisation, wait, makespan

Utilisation: GPU-time used by jobs divided by GPU-time available. Wait: start minus submit. Makespan: first submit to last end.

1. FIFO and backfill, on real Slurm

The problem. Jobs ask for different amounts. Take them strictly in order (FIFO, first in first out) and a big job at the head of the queue that does not fit yet blocks every job behind it, even small ones that would fit in the GPUs sitting idle. Backfill lets a later job jump ahead into those idle GPUs if doing so does not delay the jobs ahead of it. To know that, the scheduler builds a plan of the future from every running job's time limit: when each will end at the latest, and so when each waiting job could start.

Two flavours differ in whose start is protected. EASY backfill (from the Extensible Argonne Scheduling sYstem) reserves a start time only for the first waiting job; a later job may jump ahead if it does not delay that one. Conservative backfill reserves a start for every waiting job and lets a job jump only if it delays none of them. Slurm's own header calls its plugin conservative, and the code reserves for every job it tests (below).

The experiment. An eight-job queue, run for real: 8 fake GPUs (nodes c1 and c2, 4 each), jobs A to H submitted together by one user in that order, each asking for N GPUs as N tasks of 1 GPU and 1 CPU, with a time limit of R minutes and a real runtime of R minutes minus 5 seconds (Slurm time limits are whole minutes, so one simulated time unit is one real minute). Run once with Slurm's FIFO plugin (SchedulerType=sched/builtin) and once with the cluster's normal sched/backfill; the start and end times come from sacct.

Under backfill, C, D and G started at once in that hole and H slipped in at minute 3, all finishing before B's reserved start, so B started at the same minute under both: backfill took nothing from the job it jumped.

One job did not do what the simple model says. F (2 GPUs, 7 minutes) started at ?, together with B, not at minute 2 as a pool-of-8-GPUs model predicts (the pooled simulator below is that model). The source explains it: Slurm's reservation for B blocks both nodes from minute 6 to 10, although B leaves 2 GPUs of c2 unused, so a 7-minute job starting at minute 2 would overlap the reservation on every node. A node-level simulator that copies this rule reproduces Slurm's schedule exactly. The general point: backfill packs GPUs only as finely as the scheduler's plan resolves them, and Slurm's plan resolves nodes.

The plan (node_space) is a list of time slices, each with a bitmap of available nodes; _add_reservation removes the reserved job's nodes from every slice it overlaps (line 3909: bit_and(node_space[j].avail_bitmap, res_bitmap)). So a future reservation blocks whole nodes for its window, even if the reserved job will use only some of their GPUs. The defaults the lab changed: bf_interval 30 s, bf_resolution 60 s, bf_window one day (lines 107 to 109); here 2 s, 1 s and 60 minutes.

Predict: in the backfill run, job F (2 GPUs, 7 minutes) is behind B (6 GPUs), which must wait for A. Could F start before B?
Backfill lets F jump only if it does not push back B's reserved start. B needs 6 of the 8 GPUs at the moment A ends; F may hold 2 GPUs through that moment only if 6 others will still be free. Whether Slurm agrees depends on which nodes those GPUs sit on, because its reservations block whole nodes: compare the two runs above.
A real surprise from the first attempt: idle GPUs that nothing could use

The first version of this experiment asked for GPUs with sbatch --gpus=6 --cpus-per-gpu=1. Slurm placed job B as one task per node and gave it all 8 CPUs of c1 and c2, not 6, so the 2 GPUs left free on c2 had no CPU to go with them. Job C (2 GPUs) then sat in (Resources) while sinfo showed GPUs free:

scontrol -d show job and sinfo -N -O NodeList,CPUsState,Gres,GresUsed, Slurm 24.11.5, 16 Oct 2026. Asking for tasks instead (--ntasks=6 --gpus-per-task=1 --cpus-per-task=1) gave exactly 6 CPUs, and the runs above use that form.

The lesson carries to real clusters: a GPU is schedulable only with the CPUs and memory that must come with it. A node whose CPUs or memory are fully allocated has stranded GPUs; check AllocTRES against the request, not only the GPU count.
