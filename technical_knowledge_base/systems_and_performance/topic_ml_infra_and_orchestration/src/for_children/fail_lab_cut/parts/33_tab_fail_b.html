2. Kill it: the same failures on Slurm, Kubernetes and Ray

Who can notice a failure, and how. Three layers watch a training job, each with its own clock:

  • The other ranks. They talk to the failed rank over TCP (gloo here, NCCL on GPUs). If its process died, the kernel closes its sockets and the peers get an error at once ("Connection reset by peer"). If it is alive but silent (frozen, or its machine cut off), nothing errors until the collective timeout: how long a rank waits inside an all-reduce before giving up (30 s in these runs; PyTorch's default is 30 minutes for gloo and 10 minutes for NCCL in 2.14).
  • The launcher on each machine (torchrun's agent, a Ray Train worker, the container runtime) sees its own child processes exit and their exit codes immediately.
  • The scheduler. It learns a machine is gone only when heartbeats stop: Slurm's controller waits SlurmdTimeout (30 s in this cluster, 300 s by default), Kubernetes marks a node NotReady after node-monitor-grace-period (50 s by default in v1.37), and Ray's GCS declares a node dead after its health checks fail (30 s measured).

What happens next is policy, and the three systems ship different defaults. The matrix below holds every run; click a cell to replay it step by step from its own logs.

What the twelve runs show.

  • A crash is seen in well under a second everywhere; what differs is the decision. Slurm marks the job FAILED and does nothing more: its --requeue covers node failure and preemption, not a program that exited with an error. A JobSet fails unless failurePolicy.maxRestarts is above 0, and Ray Train unless FailureConfig(max_failures) is; the running example sets both to 0 (as is common in templates), so all three systems stopped. With retries allowed, JobSet recreated every pod and resumed in 10.3 s, Ray Train started a new worker group and resumed in 10.2 s.
  • Retries inside a Slurm job are the launcher's job: torchrun --max-restarts=2. With PyTorch 2.14.1's defaults on two machines the restart failed twice in a row, in two separate jobs (Gloo connectFullMesh failed ... Connection refused): the restarted ranks dialled addresses from the previous attempt. Setting TORCH_DISABLE_SHARE_RDZV_TCP_STORE=1 gives each restart a fresh store, and the same crash then resumed in 3.4 s. The source explains the trap (below, section 8).
  • A crash that happens every time eats the retry budget: the poison-step run crashed at step 120 on all three attempts, redoing steps 100 to 120 each time, then failed. Retries cure transient faults, not bugs or a bad batch.
  • Losing a machine takes a heartbeat timeout to notice, then each system diverges. Slurm set the node DOWN after 32.1 s, requeued the job automatically, held it for about two minutes (a requeued job gets a new eligible time) and restarted it on the spare node c3: resumed after 166 s with no person involved. Ray declared the node dead after 30 s and then waited: its worker group needs four slots and only two existed, so it resumed only when the node came back. Kubernetes with a silent node was the worst case: the surviving pod failed on the gloo timeout, the JobSet asked for a restart, and the Job then waited for the pod on the dead node to finish terminating, which a frozen kubelet never confirms. The default 300 s eviction did not help; it took an operator's out-of-service taint (section 7) at 445 s.
  • Every resumed run restarted from step 100 and redid 20 steps: checkpoints every 50 steps, failure after step 120. The cost of a failure is the work since the last checkpoint plus the time to detect and restart; section 3 shows both on one picture, section 9 turns it into goodput.

4. Did the loss come back bit for bit?

A resumed run should continue the same training trajectory, not a nearby one. The running example is built for that: the batch of step s depends only on the seed and s, there is no dropout, kernels are forced deterministic, and the checkpoint holds the optimiser state. So we compared the global loss of every resumed run with the uninterrupted run at every logged step after the resume.

Resumed runs against the uninterrupted run (global loss, 4 ranks)

measured: the reference is the setup's uninterrupted run (src/data/runs/slurm). Steps 110 to 200 are compared; "1 ulp" means one float32 rounding step (2.4e-7 at a loss near 2.4).

Almost, and the "almost" is instructive. All seven resumed runs, on three schedulers, agree with each other exactly, and with the uninterrupted run at 8 of 10 logged steps including the last one; at steps 110 and 180 they differ in the last bit. A difference that is identical everywhere is not noise; it is a deterministic change in the arithmetic. We found it with three more runs in one container:

Why. DDP does not all-reduce gradients one tensor at a time: it packs them into flat buckets, and after the first iteration of every process it rebuilds the buckets in the order gradients actually became ready (PyTorch's DistributedDataParallel._pre_forward calls reducer._rebuild_buckets(), "called only once during whole training period"). A restarted process takes its first step with the initial layout, the uninterrupted run with the rebuilt one. The layout changes which slice of the flat buffer each piece of the all-reduce handles, and so the order in which the four ranks' values are added for a given gradient element our reading of the mechanism; the experiment shows the cause. Floating-point addition is not associative, so (a+b)+(c+d) and ((a+b)+c)+d can differ in the last bit; with two ranks there is only a+b = b+a, which is exact, and that is why the setup's 2-rank resume check passed. Switch the rebuild off in both runs and the 4-rank resume is exact.

Why it matters, and when it does not. A one-ulp change is far below anything that affects training. But "bit for bit" is a powerful debugging tool (a resumed run that matches proves the checkpoint holds everything), and on GPUs nondeterministic kernels and different collective algorithms usually take it away anyway. Then test resume the practical way: the loss at the first logged steps after resuming must match the original run to the precision you expect, with no jump. A jump means something was not saved: the optimiser state (a fresh AdamW takes large first steps), the learning-rate schedule step, the data loader's position (the run sees data again or skips it), or the random-number generators (dropout masks, sampling).
