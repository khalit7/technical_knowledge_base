3. The burst: every rank writes at once

Training is synchronous: at the checkpoint step, every rank reaches the save at the same moment, and the storage system sees all of them arrive together. Whatever the aggregate write bandwidth is, they share it. Who writes what then decides both the bytes and the time:

  • Rank 0 writes everything (train.py's way, fine for DDP, where every rank holds a full copy): one writer, one link.
  • Every rank writes everything: the forgotten if rank == 0. Same file content, written N times.
  • Consolidated (gather, then one file): with a sharded model (FSDP, ZeRO-3), the pieces are first sent to rank 0 over the network, then rank 0 writes one file. Needs the whole state in rank 0's memory.
  • Sharded (PyTorch Distributed Checkpoint, DCP): every rank writes its own piece to its own file, in parallel, plus a small .metadata file mapping pieces to tensors. No gather, no single writer.

Measured with 4 ranks in one container (2 CPUs, gloo) and the 3.2M-parameter GPT (38.6 MB of state), three repetitions each, on the slow shared folder and on a Docker volume measured:

What this shows, and what it cannot. Bytes on a shared pipe cost time: writing four copies took about three times as long as one. But sharding did not make the write faster here, because all four ranks share one container, one virtual disk and one file-sharing channel: there is only one pipe. On a cluster every node has its own network link to storage (a DGX B200 has two BlueField-3 storage ports at up to 400 Gb/s each, {{NVIDIA|https://docs.nvidia.com/dgx/dgxb200-user-guide/introduction-to-dgxb200.html}}), so N nodes writing their shards use N links at once, while a consolidated write squeezes the whole state through one. 4. Asynchronous checkpointing: stop for the copy, not for the write

A synchronous checkpoint stops training for the whole write. An asynchronous checkpoint splits it in two: first stage the state into host memory (from GPU memory, a PCIe copy of each rank's shard), then let training continue while a background thread writes the staged copy to storage. Training stands still only for the copy. The cost: a second copy of the state in host RAM, and the write must finish before the next checkpoint starts.

The same 60 training steps of the 3.2M-parameter GPT (4 ranks, a checkpoint every 15 steps, DCP), run three times: without checkpoints, with dcp.save, and with dcp.async_save. Step times are each step's slowest rank measured:

training steptraining stopped for the checkpointbackground write (drawn with the synchronous write's measured time)

Published, at scale: PyTorch and IBM report that asynchronous DCP cut the time a 7B model's training stood still per checkpoint from 148.8 s to 6.3 s on average, the 6.3 s being the copy to CPU memory published ({{PyTorch blog, November 2024|https://pytorch.org/blog/reducing-checkpointing-times/}}). Gemini went further and kept redundant copies of model state in other hosts' memory, raising its largest job's goodput from 85% to 97% ({{Gemini 1.0 report, section 3|https://arxiv.org/abs/2312.11805}}).

The async trap we hit: give the background writer its own process group

DCP's save runs collectives (it gathers every rank's plan and agrees the file is complete). async_save runs them in a background thread; if that thread uses the same process group as training, two threads issue collectives on one channel at once. Our first attempt (4 ranks, gloo, native) hung: every rank at 0% CPU after the first checkpoint, nothing printed for over four minutes. A rerun crashed 3 s after the checkpoint, two ranks aborting with:

gloo::EnforceNotMet: [enforce fail at .../third_party/gloo/gloo/transport/uv/pair.cc:253] op.nread == op.preamble.nbytes

The fix is one line, the one the PyTorch blog recommends: create a group once, ck_pg = dist.new_group(backend="gloo"), and pass process_group=ck_pg to async_save. All runs above use it.
