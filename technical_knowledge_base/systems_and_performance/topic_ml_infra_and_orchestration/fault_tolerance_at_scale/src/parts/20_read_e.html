6. A restart is only as good as the checkpoint it finds

Every recovery design ends the same way: some process loads some saved state and continues. Four traps found on this topic's own clusters show that "we have checkpoints" and "we can restart" are different claims, and each has a check you can run before the real run needs it.

1. The restart path itself fails

Two-node torchrun --max-restarts=2 with PyTorch 2.14.1's defaults failed to restart twice in a row on Slurm (Gloo connectFullMesh failed ... Connection refused): the restarted ranks dialled addresses from the previous attempt. TORCH_DISABLE_SHARE_RDZV_TCP_STORE=1 gives each restart a fresh store and the same crash then resumed in 3.4 s measured (root's {{Failure lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}}; the elastic runs are in section 5). Check: kill a rank in a test job and watch it come back.

2. The restart has a single point of failure

With torchrun's c10d rendezvous, one agent hosts the key-value store every agent meets at. Kill that agent's node and the survivors die too: RendezvousConnectionError: The connection to the C10d store has failed measured. Check: put the endpoint on the most stable machine, or use an external store (etcd), and kill the store's host in a test.

3. The newest checkpoint on disk is not the one restored

Ray Train 2.59.0 restored step 50 in 3 of 3 runs although rank 0 had written step 100 to storage before the crash measured (the {{Ray|n:3fc5c17b0d0d811cba13f3aeccf8724b}} child page). The controller registers a checkpoint only once it has collected that report from every worker, by polling every 2 s (report_handler.py lines 40 and 63 @ ray-2.59.0: "Wait for all workers to report training results", if not all(self._training_report_queues): return); a worker that died before the poll took its report with it. Check: restore from what the framework says is registered, treat other directories as possibly incomplete, and count the lost interval in your goodput.

4. The resumed run is not the same run

Resuming the running example with 4 ranks changed the loss in the last bit at 2 of 10 logged steps (2.4e-7), identically on Slurm, Kubernetes and Ray measured: DDP rebuilds its gradient buckets after a process's first step, so a restarted process sums in a different order. Harmless here, but it means "bit for bit" needs care, and it is why this page's replay switches the rebuild off. Check: compare the loss of the first steps after a resume with the original run; a last-bit difference is arithmetic, a jump is missing state (optimiser moments, learning-rate step, data position, random-number generators).
