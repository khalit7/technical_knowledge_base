3. Five ways to fail, and why they need different detectors

Sorting failures by cause (GPU, network, software) tells you what to fix in the fleet. Sorting them by how they look to the job tells you how to notice them, and that is what decides how much time each one costs. Five shapes cover everything in the published records.

ShapeWhat the job seesExampleWho can notice first
Fail-stop: a process diesA rank exits with an error code; its sockets close at once.An uncorrectable ECC error kills the CUDA context; a Python exception; out of memory.The launcher (exit code), and the peers ("Connection reset by peer") within a second.
A machine is lostEvery process on one host vanishes; if the host is frozen rather than off, its sockets stay open.Power supply, kernel panic, a host taken for maintenance, a NIC that drops off the bus.The peers if the sockets close; otherwise only the scheduler, when heartbeats stop.
Fail-hangEvery rank waits in a collective that never completes; nothing exits.A GPU or NVLink fault that stalls a kernel "without returning a clear error code" (Llama 3); a rank stuck in a deadlock.Only a timeout: the collective's, the NCCL watchdog's, or your own.
Fail-slowSteps take longer; nothing fails.A throttled GPU, a flapping link, a slow disk, a noisy neighbour.Nobody, unless per-rank timings are compared (section 8).
Fail-silentThe numbers are wrong; everything runs.Silent data corruption in a multiplier or a register.Nobody, unless something recomputes and compares (section 7).

Fail-stop is the easy case and the one every scheduler handles; the root's {{Failure lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} measured it on all three systems (a crashed rank was seen in about 0.15 s everywhere). The expensive failures are the ones further down the table, because their cost is mostly the time before anyone acts.

4. Detection: every layer has a clock

A failure costs at least the time until some layer notices it. Each layer of the stack watches with its own timer, and their defaults were chosen for safety, not speed: a timeout that is too short kills healthy jobs during a slow checkpoint or a long first compilation. Here is what each layer watches, its default at the versions this topic pins, and where it is set.

A hang, measured: what the logs say and what they do not

A frozen rank is worse than a dead one: nothing exits, no exit code reaches anybody, and every other rank sits in an all-reduce doing nothing. The {{root page|n:3c65c17b0d0d81b5925bfd1d8665dd4b}}'s lab made one on its Slurm cluster: SIGSTOP to rank 3's process after step 120 (it stays alive and holds its sockets open), with the process-group timeout set to 30 s measured.

[rank0]: RuntimeError: [.../gloo/transport/tcp/unbound_buffer.cc:129] Timed out waiting 30000ms for send operation to complete [rank1]: RuntimeError: [.../gloo/transport/tcp/unbound_buffer.cc:78] Timed out waiting 30000ms for recv operation to complete ... Root Cause (first observed failure): [0]: host : c1 rank : 0 (local_rank: 0) exitcode : 1 (pid: 1972)

measured: job 51 (root page, src/fail/runs/fl-hang/job51.out, trimmed). The three healthy ranks errored 30.8 s after the freeze, and the job failed.

Predict: which rank does torchrun's "Root Cause (first observed failure)" name?
A healthy one: rank 0 on c1. "First observed failure" means the first process to exit with an error, and in a hang that is a victim that timed out first; the frozen rank never errors, it only received SIGTERM during clean-up. In a hang, read the timeout messages for which rank everyone was waiting on (the one that did not time out), and get stacks from the stuck processes (py-spy dump, the {{Launch lab's hang drills|#t-launch}}) or PyTorch's flight recorder, which in torch 2.14.1 records gloo collectives too (the {{Launch lab|#t-launch}} dumped it from a stalled rank on CPUs and found that rank one collective behind).

The two NCCL messages that end a hang on GPUs are different events in PyTorch 2.14.1: Watchdog caught collective operation timeout: ... ran for ... milliseconds before timing out. means a collective exceeded its timeout; ProcessGroupNCCL's watchdog got stuck for ... seconds without making progress in monitoring enqueued collectives. means the watchdog thread itself hung and the heartbeat monitor (the 8-minute row above) ended it (ProcessGroupNCCL.cpp lines 735-739 and 1954 @ v2.14.1) source.

Health checks: catching bad machines before and between jobs

Timeouts catch a failure after it has stopped a job. Health checks try to catch the machine before it is given one. Three moments matter: before a node joins (burn-in; OpenAI's nodes join Kubernetes with a "preflight" taint that only passing GPU tests remove, per the root page), before or between jobs (Ai2's Beaker multiplies two tensors on every GPU before each workload and cordons the host on failure; Slurm's HealthCheckProgram, which must drain the node itself, measured at the end of this section), and after a failure, to decide whether the machine goes back into the pool.

"Higher numbered tests include all beneath"; active diagnostics need exclusive use of the GPUs, while DCGM's health watches (dcgmi health: PCIe, memory, InfoROM, thermal and power, NVLink, driver) are passive and run beside jobs. Not run here: there are no GPUs on this machine.

The cost structure decides where each check goes: level 1 fits before every job, level 2 between jobs or after a failure, levels 3 and 4 in burn-in or when a node keeps failing. NVIDIA's Xid catalogue pairs each driver error with an action, and the action is the useful part for automation: Xid 13 and 31 (an out-of-bounds access, a page fault: "Typically these are application-level bugs") say restart the application, not the node; Xid 48 (double-bit ECC) a GPU reset; Xid 79 ("GPU has fallen off the bus") a reboot of the machine; Xid 74 (NVLink) needs care, because "if a GPU fails, another GPU connected to it over NVLink may report an Xid 74 simply because the link went down" ({{Xid catalogue|https://docs.nvidia.com/deploy/xid-errors/analyzing-xid-catalog.html}} vendor). The hardware side of these errors is on the {{hardware reliability page|n:3f05c17b0d0d8143851cfc3ae14c3c22}}. A drain or taint after a failed check is what keeps the next restart from landing on the same bad machine, the trap OPT-175B's logbook records when its cloud replacement returned the same bad host.

Measured on the lab clusters: drain, cordon, a health check, and the Kubernetes trap

Restarting onto the same broken machine just fails again, so every system has a way to say "schedule nothing new here". On Slurm a node is drained: running jobs finish, nothing new starts. On Kubernetes it is cordoned (marked unschedulable) or tainted (a taint repels every pod that does not tolerate it; a NoExecute taint also evicts running ones). A health check that drains its own node. Slurm runs HealthCheckProgram on every node every HealthCheckInterval seconds, as root, and ignores its exit code: the script must drain the node itself. This one checks that the node's four (fake) GPU devices exist; a real one runs nvidia-smi or dcgmi diag, scans the kernel log for Xid errors, and checks ECC counters, NVLink and InfiniBand ports.

#!/bin/sh
NODE=$(hostname)
missing=""
for i in 0 1 2 3; do [ -e /dev/mi_gpu$i ] || missing="$missing mi_gpu$i"; done
if [ -n "$missing" ]; then
  scontrol update nodename="$NODE" state=drain reason="healthcheck: missing$missing"
  exit 1
fi
exit 0

src/fail/scripts/fl_healthcheck.sh, with HealthCheckProgram=/shared/jobs/fl/fl_healthcheck.sh, HealthCheckInterval=10, HealthCheckNodeState=ANY added to slurm.conf for the test, then removed. Moving one device file away drained the node within 1.4 to 7.3 s in four tries measured: anywhere up to one interval, depending on where in the cycle the fault lands.

The Kubernetes trap measured in section 2. A node that goes silent becomes NotReady after 50 s and gets the taint node.kubernetes.io/unreachable:NoExecute; pods tolerate it for 300 s by default, then are marked for deletion. But a pod is only gone when its kubelet confirms it, and a dead kubelet never does, so the pod stays Terminating and anything waiting for it waits forever. The fix is to tell the cluster the node is really down:

kubectl taint node mi-kind-worker2 node.kubernetes.io/out-of-service=nodeshutdown:NoExecute

measured: 2 s after this taint the stuck pod was force-deleted, the JobSet restarted on two healthy workers and the run resumed from step 100 (root page, src/fail/runs/fl-k3). Remove the taint once the node is repaired. Clusters automate this with a node-health controller rather than a person.
