4. Checkpointing: what each strategy stops training for

A checkpoint is the job's state saved so a restart can continue: weights, optimiser moments, the learning-rate step, the data position, the random-number generators. Its price is the pause C, the time training stands still per save, and that pause sets how often you can afford to save: the best interval grows as √(2CM) for a job MTBF M (Young; derived on the {{reliability page|n:3f05c17b0d0d8143851cfc3ae14c3c22}}, section 6). A cheaper pause means more frequent saves, so less rework per failure.

First, what a checkpoint buys. The root page's lab crashed the running example after step 120 on Slurm twice, once checkpointing every 50 steps (1.39 MB, written atomically) and once with --ckpt-every 0, and resubmitted each by hand measured. The chart opens on the end of the run: with checkpoints the second attempt starts from step 100 and redoes 20 steps; without them it climbs from step 0 again and finishes later, by a gap that grows with how long the run had gone before the crash. Four strategies: where the bytes go, and what stops

Predict before reading the steps: which strategy can still lose the newest checkpoint even though training already moved past it? Fig. 1 follows one save and one restore on four nodes (the boxes and distances are schematic); each node has GPUs holding the state, host CPU memory, and a link to shared storage. The pauses are the page's published and measured numbers, the same inputs as section 5's model.

  1. The state to save. Every GPU holds its shard of the weights and the optimiser moments; the learning-rate step, data position and random-number generators travel with them. Shared storage sits far from the nodes, across the storage fabric.
  2. Synchronous: training stops for the whole write. torch.save or dcp.save serialises every byte and sends it to storage while every GPU waits. 1.81 s per checkpoint on the root lab's slow shared folder measured; a 7B model 148.8 s on average published ({{PyTorch blog, November 2024|https://pytorch.org/blog/reducing-checkpointing-times/}}); section 5's default design assumes 5 min. Restore reads storage.
  3. Asynchronous: stop only to copy to host memory. With dcp.async_save training pauses only to copy the state to the node's own CPU memory, then resumes while serialising and writing run in the background on their own process group. 78 ms instead of 1.81 s on the same folder measured; Llama3-70B on 1,856 H200 blocked "for less than a second" (0.78 s) vendor. The checkpoint exists only when the background write ends: a failure during it falls back to the previous one.
  4. In-memory and peer: copy to your own memory and a neighbour's. Each node keeps its shard in its own CPU memory and a peer's, every step or every few (Gemini, SOSP 2023; ByteRobust). ByteRobust blocks 0.01 to 0.04 s per step; Gemini checkpoints every iteration in under 3 s authors' figures. Storage is written rarely, in the background.
  5. A node fails, and its copies go with it. Node 3's GPUs and its CPU memory are gone; the shard it held still exists in node 4's memory, and the shard node 2 had parked on node 3 is still on node 2.
  6. Restore from a peer's memory, not from storage. A hot spare takes node 3's place and reads the lost shard from node 4's memory over the network: Gemini's retrieval took under 3 s, against the 162 s section 5's model charges to read a checkpoint back from storage. Restore reads a peer's memory, not storage, so it is fast.
  7. When the copies fail together, fall back to storage. If both machines holding a shard fail at once, that shard is only on storage, and the restart pays the slow path. Gemini puts it at a 6.7% chance when 2 of 16 machines are replaced: placing the copies is the design.
  8. Just-in-time: no periodic checkpoints. When a failure is detected, the surviving data-parallel replicas save on the spot, so only one minibatch is replayed (Microsoft, EuroSys 2024). Needs a healthy replica of every shard at failure time.

Sharded checkpoints. Any of the first three strategies can be sharded: with PyTorch DCP each rank writes only its own shard, in parallel, plus one metadata file, and the checkpoint exists only when every shard and the metadata file are written, which is what DCP's final metadata write marks. Answer to the prediction: asynchronous (and sharded writes, until the metadata lands). Numbers per design, with sources, are in section 5's table; the measured asynchronous animation and the process-group trap that hung it are on {{Storage and data movement|n:3fc5c17b0d0d818a94ced3fc7c3331fe}}, section 7.

Two rules make any checkpoint safe to trust, and the running example follows both: write atomically (write to a temporary name, then rename, so a crash mid-write never leaves a half file under the real name) and move a "latest" pointer only after the file is complete, so the reader never picks a partial checkpoint. Section 6 shows what goes wrong on restore when a framework's idea of "latest" differs from what is on disk.
