4. Checkpointing: what each strategy stops training for

A checkpoint is the job's state saved so a restart can continue: weights, optimiser moments, the learning-rate step, the data position, the random-number generators. Its price is the pause C, the time training stands still per save, and that pause sets how often you can afford to save: the best interval grows as √(2CM) for a job MTBF M (Young; derived on the {{reliability page|n:3f05c17b0d0d8143851cfc3ae14c3c22}}, section 6). A cheaper pause means more frequent saves, so less rework per failure.

Synchronoustorch.save, dcp.save
Training stops for the whole write: serialise every byte and send it to storage. 1.81 s per checkpoint on the root lab's slow shared folder measured; a 7B model 148.8 s on average published ({{PyTorch blog, November 2024|https://pytorch.org/blog/reducing-checkpointing-times/}}). Restore reads storage.
Asynchronousdcp.async_save
Stops only to copy state to host memory; serialising and writing run in the background on their own process group. 78 ms instead of 1.81 s on the same folder measured; Llama3-70B on 1,856 H200 blocked "for less than a second" (0.78 s) vendor. The checkpoint exists only when the background write ends: a failure during it falls back to the previous one.
In-memory and peerGemini (SOSP 2023), ByteRobust
Copy the state to the machine's own CPU memory and a peer's, every step or every few. ByteRobust blocks 0.01 to 0.04 s per step; Gemini checkpoints every iteration in under 3 s authors' figures. Restore reads a peer's memory, not storage, so it is fast; it falls back to storage when every copy of a shard sat on machines that failed together.
Just-in-timeMicrosoft, EuroSys 2024
No periodic checkpoints: when a failure is detected, the surviving data-parallel replicas save on the spot, so only one minibatch is replayed. Needs a healthy replica of every shard at failure time.

Any of the first three can be sharded: with PyTorch DCP each rank writes only its own shard, in parallel, plus one metadata file, and the checkpoint exists only when every shard and the metadata file are written, which is what DCP's final metadata write marks. Answer to the prediction: asynchronous (and sharded writes, until the metadata lands). Numbers per design, with sources, are in section 5's table; the measured asynchronous animation and the process-group trap that hung it are on {{Storage and data movement|n:3fc5c17b0d0d818a94ced3fc7c3331fe}}, section 7.

Two rules make any checkpoint safe to trust, and the running example follows both: write atomically (write to a temporary name, then rename, so a crash mid-write never leaves a half file under the real name) and move a "latest" pointer only after the file is complete, so the reader never picks a partial checkpoint. Section 6 shows what goes wrong on restore when a framework's idea of "latest" differs from what is on disk.
