Recovery designs: where the time per failure goes, and what it does to goodput

Every recovery design is an answer to one question: which part of the time lost per failure does it remove? This tab splits that time into the same five parts for every design (detect, wait for the scheduler, get a healthy machine, start up, load the checkpoint), adds the rework since the last checkpoint, and runs the root page's goodput model for any job size.

How to read the numbers
The model is the one in the root's {{Failure lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}}, section 9: failures arrive at random with job MTBF M = 1 / (GPUs × failure rate per GPU); a checkpoint pauses training for C every τ of work; each failure costs the recovery time R plus the work since the last checkpoint; expected goodput = τ / (M eR/M (e(τ+C)/M − 1)) (Daly 2006), with τ at its optimum unless the design fixes it. For replica groups only the failed group's share of R is lost (R × (1 − kept share)), our approximation. calculation Inputs are published figures from different systems and hardware, combined per design, so each design row is illustrative as a whole even where every input is sourced: no single source reports these exact combinations. The two bottom designs are this topic's own measured runs of the tiny job, for scale. Not modelled: storage bandwidth (frequent checkpoints of a large model must fit the storage fabric), the window in which an asynchronous checkpoint is still being written (a failure then falls back to the previous one), queue time, and failures during recovery beyond the formula's own.
