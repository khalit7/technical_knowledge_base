Straggler replay: find the slow rank from per-rank timings

A straggler is a rank that keeps working, slowly. Nothing fails, so no scheduler acts; every step simply waits for it. This tab replays three real runs of the running example with stragglers planted on a schedule, and lets you try the detection rules that production systems use on the same per-rank timings, to see which rule names the culprit, how fast, and how often it accuses an innocent rank.

How the data was made measured
The running example (4 ranks, gloo, 1 thread each) run natively on the Mac by src/scripts/ft_lab.py --mode strag, 300 steps, on 2026-10-16: measured on Apple M1 Pro, natively (macOS), shared machine. A DDP communication hook records, on every rank and every step, when the rank's gradients were ready (end of its compute: forward plus backward) and when the gradient all-reduce finished (wait: the all-reduce itself plus the time spent waiting for the slowest peer). Stragglers are emulated by a sleep inside the forward pass of one rank on a schedule: rank 2 slow on every step 80 to 159 (+6 ms requested), rank 0 slow on every 25th step (+20 ms: work only rank 0 does, such as logging or evaluation), rank 3 mildly slow on every step 200 to 300 (+2 ms). macOS oversleeps, so the measured extra compute is larger than requested (about +8.3 ms and +2.6 ms). The run with no stragglers is the noise floor; the second mixed run is a repeat. Reading, section 8 shows the same effect, measured on the Slurm cluster with one constant straggler; this tab adds the split between compute and wait, a schedule, and the detectors.

What the replay shows

  • Step time cannot name the culprit. Every rank reports the same step time (the all-reduce makes them wait for each other), so a per-rank step-time log only tells you the job got slower. The "Step time" rule above flags the whole job, never a rank.
  • The slow rank waits least. Pick "Long waits in the all-reduce": it flags the three innocent ranks hundreds of times and never rank 2 or rank 3. Root-cause tools that rank collectives by duration find the victims; the simplest case in Reading, section 8 shows the same inversion on Slurm (12 ms against 63 ms).
  • Compute time, compared across ranks, names it. With a 10-step median window, "Longest compute" and the relative score both flag rank 2 at step 84, four steps after its slowness began, and rank 3's mild slowness at step 204 or 205, with no false alarm on any of the three runs; with the median they ignore rank 0's periodic spike, which is a code path, not a slow machine. Switch the statistic to the maximum and rank 0 is flagged on all twelve of its spikes: decide which of the two you want to page someone about.
  • Comparing a rank with its own past is noisier. The individual score raised 4 false alarms on the run with no straggler at the same settings, and with the maximum it raises dozens: a rank's own history includes its warm-up and the machine's other load.
  • The threshold and window are a trade-off. A 1-step window reacts at once and flags noise; a longer window is quieter and later. The relative score's default cutoff of 0.75 here is NVIDIA Resiliency Extension's; real systems also require a minimum duration before acting.
