DESIGN: checkpoint/restart via scheduler requeue; in-allocation restart (torchrun --max-restarts); NVIDIA Resiliency Extension (ft_launcher in-job restart, hot spares, in-process restart, local checkpointing). All read 2026-10-16. All are vendor documentation (the project's own docs). No performance numbers are published in these docs except the NVRx in-process restart latency table.

1) SLURM REQUEUE (docs, https://slurm.schedmd.com/sbatch.html, current at read time)
- "--requeue[=expedite] Specifies that the batch job should be eligible for requeuing. The job may be requeued explicitly by a system administrator, after node failure, or upon preemption by a higher priority job. When a job is requeued, the batch script is initiated from its beginning with the same job ID." "The JobRequeue configuration parameter controls the default behavior on the cluster."
- "--signal=[{R|B}:]<sig_num>[@sig_time] When a job is within sig_time seconds of its end time, send it the signal sig_num. Due to the resolution of event handling by Slurm, the signal may be sent up to 60 seconds earlier than specified." "By default, no signal is sent before the job's end time."
- My summary: requeue pays everything: queue wait again (Q), new allocation, container/env start, process-group init, checkpoint load, and rework since the last checkpoint.

2) TORCHRUN / TORCHELASTIC (docs https://docs.pytorch.org/docs/2.14/elastic/run.html, "Created On: May 12, 2026"; source torch/distributed/run.py and elastic/rendezvous/dynamic_rendezvous.py on main, read 2026-10-16)
- Fault tolerant example: "Fault tolerant (fixed sized number of workers, no elasticity, tolerates 3 failures)" with "--max-restarts=3 --rdzv-id=$JOB_ID --rdzv-backend=c10d --rdzv-endpoint=$HOST_NODE_ADDR". Elastic: "Elastic (min=1, max=4, tolerates up to 3 membership changes or failures)" with "--nnodes=1:4".
- Failure modes: "Worker failure: For a training job with n workers, if k<=n workers fail all workers are stopped and restarted up to max_restarts." "Agent failure: An agent failure results in a local worker group failure. It is up to the job manager to fail the entire job (gang semantics) or attempt to replace the node." "Node failure: Same as agent failure."
- Membership: "Node departure (scale-down): The agent is notified of the departure, all existing workers are stopped, a new WorkerGroup is formed, and all workers are started with a new RANK and WORLD_SIZE." Same for arrival.
- "On failures or membership changes ALL surviving workers are killed immediately. Make sure to checkpoint your progress. The frequency of checkpoints should depend on your job's tolerance for lost work." "RANK is NOT stable."
- Defaults from run.py: --max-restarts default=0; --monitor-interval default=0.1 (seconds). WorkerSpec(max_restarts=3, monitor_interval=0.1) in the agent API.
- Dynamic rendezvous default timeouts (dynamic_rendezvous.py): "join": timedelta(seconds=600), "last_call": timedelta(seconds=30), "close": timedelta(seconds=30), "heartbeat": timedelta(seconds=5).
- My summary: saves rescheduling and queue wait (stays in the allocation), but still restarts processes: CUDA context, NCCL init, checkpoint load, rework. Cannot replace a dead node unless spare nodes are already in the allocation (nnodes=min:max).

3) NVIDIA RESILIENCY EXTENSION (NVRx), docs v0.7.0, https://nvidia.github.io/nvidia-resiliency-ext/ ; repo https://github.com/NVIDIA/nvidia-resiliency-ext
Features list: "Hang detection and automatic in-job restarting; In-process restarting; Async checkpointing; Local checkpointing; Straggler (slower ranks) detection; Failure attribution; Shared utilities and distributed logging".
3a) Fault tolerance package / ft_launcher (fault_tolerance/usage_guide.html, fault_tolerance/api/config.html)
- "ft_launcher is a launcher tool included in FT, which is based on torchrun." "heartbeat is a lightweight message sent from a rank to its rank monitor that indicates that a rank is alive." "section is a user code segment with a custom name assigned." "rank monitor is a special side process started by ft_launcher that monitors its rank."
- Design: "Each rank periodically sends updates to its rank monitor (e.g., during each training and evaluation step). In case of a hang, the rank monitor detects missing updates from its rank and terminates it. If any ranks disappear, ft_launcher detects that and terminates or restarts the workload. ft_launcher instances communicate via the torchrun "rendezvous" mechanism."
- "If --max-restarts is specified, the launcher restarts failed workers." "only any-failed is supported: all workers are restarted if any worker fails (torchrun-style behavior)."
- Hang detection: "Heartbeats API ... If no heartbeat arrives in a defined time, the workload is considered hung. This API is the simplest to use but might require coarse timeouts". "Sections API ... If any section is opened for too long, the workload is considered hung ... timeouts can be defined more precisely, and hangs can be detected quicker."
- FaultToleranceConfig defaults (signature): workload_check_interval=5.0, initial_rank_heartbeat_timeout=None, rank_heartbeat_timeout=None, rank_out_of_section_timeout=None, node_health_check_interval=5.0, safety_factor=5.0, rank_termination_signal=SIGKILL, restart_check_interval=60.0, enable_nic_monitor=False, enable_nic_healthcheck=True, enable_dist_storage_healthcheck=False. "If any timeout is None, it has no effect (as if it was +INF). All timeouts can be deduced and set during runtime." "safety_factor [float] when deducing the timeouts, observed intervals are multiplied by this factor to obtain the timeouts." gpu_memory_reclaim_timeout default 50.0 s; num_warmup_iterations default 5 (excluded from step/out-of-section timeout monitoring).
- Pre-rendezvous checks: optional node health check service (nvhcd, BCM prolog/epilog checks, default args ["--no-slurm", "--group", "prolog", "epilog", "logs", "gpu"]); NIC link state check (default on); optional Lustre/NFS and path checks.
- Hot spares: "The ft_launcher supports hot spare nodes, which are standby nodes that can replace failed nodes during restart. Hot spare functionality is always enabled and works with --max-restarts." "The first min_nodes (from --nnodes) are assigned as active workers. Any additional nodes beyond min_nodes become hot spares with standby ranks". Example: "ft_launcher --nnodes=6:8 --nproc-per-node=8 --max-restarts=3 ... Nodes 0-5: Active workers (ranks 0-47); Nodes 6-7: Hot spares". Segment-aware mode --ft-segment=N for NVLink domains (DGX H200, HGX B200).
- Failure attribution: "Attribution never delays a restart."
3b) In-process restart (inprocess/usage_guide.html; inprocess/api/wrap.html)
- "Upon a fault, the wrapped function is restarted across all distributed ranks, within the same operating system process. Wrapped function restart invocation excludes distributed ranks that are terminated, missing, or deemed unhealthy."
- Requires "PyTorch v2.5.1 or higher and NCCL v2.26.2 or higher". "The PyTorch NCCL watchdog must either be disabled or configured with a timeout longer than the hard_timeout". Slurm: "Use the --kill-on-bad-exit=0 option with srun". "node failure on rank 0 causes termination of the entire job" (rank 0 hosts the TCPStore by default). "It is heavily recommended for the wrapped function to load the state affected by distributed collectives from a checkpoint on every restart".
- Timeouts: "Soft timeout is equivalent to a Python exception raised by one of the ranks, and triggers an attempt to restart the wrapped function on all healthy ranks." Hard timeout sends SIGCONT, SIGTERM then SIGKILL after termination_grace_time.
- Wrapper defaults: monitor_thread_interval=1 s, monitor_process_interval=1 s, heartbeat_interval=1 s, progress_watchdog_interval=1 s, soft_timeout=60 s, hard_timeout=90 s, heartbeat_timeout=30 s, barrier_timeout=120 s, completion_timeout=120 s, last_call_wait=1 s, termination_grace_time=5 s.
- Restart latency table (vendor, "the time elapsed between a fault occurring on any distributed rank and successfully relaunching the wrapped function across all distributed ranks"):
  torch.distributed.destroy_process_group(): ~0.5s + 0.01s * num pending NCCL kernels
  complete pending CUDA kernels: ~training iteration
  wait for concurrent faults on other ranks: last_call_wait
  execute rank_assignment: ~0.5s
  TCPStore-based barrier: 0.5s @ 16k ranks
  user initialize / finalize / health_check: N/A
  (H) detect GIL-released hang: soft_timeout + monitor_process_interval
  (H) detect GIL-holding hang: hard_timeout + monitor_process_interval + termination_grace_time
  "(H) increase restart latency only when the application hangs." Note: the table excludes checkpoint reload and rework.
- Megatron Bridge docs (https://docs.nvidia.com/nemo/megatron-bridge/latest/training/resiliency.html; the NeMo framework resiliency URL redirects there): in-process restart "avoids the overhead of launching new jobs, starting containers, and creating new CUDA contexts"; status "Experimental"; "In-process restart is not suitable for hardware-level failures such as switch failures or network partitions. For comprehensive fault tolerance, combine it with job-level fault tolerance." FT "Requires Slurm and ft_launcher (not torchrun)"; "supports both in-job restarts (within the same Slurm allocation) and new job launches on failure".
3c) Local checkpointing (checkpointing/local/usage_guide.html)
- LocalCheckpointManager saves to node-local storage with replication: "We provide the CliqueReplicationStrategy, which groups ranks into rank "cliques" where checkpoint parts are replicated. The replication_factor parameter defines the size of each group (clique), while the replication_jump parameter determines how the cliques are formed." Directory needs capacity for "at least two checkpoint parts (clean and dirty) per rank multiplied by the replication factor".
- Megatron Bridge: "Local checkpointing saves checkpoint data to node-local storage first, then replicates across a configurable number of nodes. This avoids the latency of writing to shared network storage during the critical path." Status listed as production.
- Numbers for local checkpointing speed: none found in these docs (unconfirmed).
