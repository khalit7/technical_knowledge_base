A. AUTO-RESUME + NODE RECOVERY (verbatim)
- "As of September 11, 2025, HyperPod with Slurm orchestration now supports health monitoring agents."
- "cluster admin users can select the node (instance) recovery option between Automatic (Recommended) and None at the cluster level. If set to Automatic, SageMaker HyperPod reboots or replaces faulty nodes automatically." "By default, the clusters are set up with Automatic node recovery." "Automatic node recovery runs when issues are found from health-monitoring agent, basic health checks, and deep health checks. If set to None, the health monitoring agent will label the instances when a fault is detected, but it will not automatically initiate any repair".
- "if a job fails due to a hardware failure or any transient issues in-between training, SageMaker HyperPod auto-resume starts the node replacement workflow and restarts the job after the faulty nodes are replaced." Hardware checks on job failure: nvidia-smi parsing (GPU), Neuron sysfs (Trainium), EFA connectivity tests.
- Usage: "srun --auto-resume=1 train_auto_resume.sh"; run "inside an exclusive allocation acquired either by using salloc or sbatch"; "make sure that all setup steps run in a single srun command when resuming the job".
- GRES caveat: "Unless explicitly forbidden, the HyperPod auto-resume functionality automatically re-queues any faulty job associated with the GRES-enabled nodes. This process involves stopping the job, placing it back into the job queue, and then restarting the job from the beginning."
- No timing for node replacement or resume is stated in these docs (unconfirmed).
B. DEEP HEALTH CHECKS: run "during the creation and update of HyperPod clusters" and on demand via StartClusterHealthCheck. Instance level: GPU/NVLink count; "DCGM (NVIDIA Data Center GPU Manager) diagnostics at level 4, including additional memory tests"; EFA latency/bandwidth benchmarking; hardware stress (log example: stress-ng ... --timeout 60). Cluster level: "NCCL test ... Verifies the performance of collective communication operations on multiple NVIDIA GPUs". Example failure log: "Bandwidth has less than threshold: Expected minimum threshold :80,NCCL Test output Bw: 30". Duration of deep checks: not stated (unconfirmed).
C. HEALTH MONITORING AGENT (passive, continuous): "DCGM policy violation notifications; Errors in the nvidia-smi output; Various errors in the logs generated by the Amazon Elastic Compute Cloud (EC2) platform; GPU Count validation -- if there's a mismatch between the expected number of GPUs ... then HMA reboots the node". Response: node labels (node-health-status, fault-types, fault-reasons), taint "node-health-status=Unschedulable:NoSchedule", annotation. Example detection: XidHardwareFailure, "Xid ... 71 ... NVLink: fatal error".
D. CHECKPOINTLESS TRAINING (EKS; recommended p5/p5e/p5en, p6-b200, p6e-gb200)
- Mechanism (my words): five components: rootless/TCPStore-less NCCL and Gloo initialization (ranks compute peer addresses, no rank-0 rendezvous); memory-mapped data loading cached in shared memory that survives process failure; in-process recovery of only the failed process (CUDA context kept), escalating to process-level restart (containers kept) and hot-spare swap for hardware faults; continuous peer-to-peer replication of model/optimizer shards onto peer GPUs, recovered over EFA; a training operator coordinating it, with checkpoint fallback.
- Verbatim: "Results from production-scale validation show 80-93% reduction in recovery time (from 15-30 minutes or more to under 2 minutes) and enables up to 95% training goodput on cluster sizes with thousands of AI accelerators." (source uses an en dash in "80-93%" and "15-30")
- "extensive testing across a range of cluster sizes, spanning 16 GPUs to 2,304 GPUs ... consistently reducing downtime by 80-93% compared to traditional checkpoint-based recovery."
- "we consistently observed goodput upwards of 95% across massive-scale deployments that exceeded 2,300 GPUs." "Our internal studies on 2,304 GPUs show recovery times dropped from 15-30 minutes to under 90 seconds, translating to over 80% reduction in idle GPU time per failure."
- "The latest Amazon Nova models were trained using this technology on tens of thousands of AI accelerators."
- Correctness: "at every training step verified a bit-wise match on training loss" (Llama-3 70B on 32 x ml.p5.48xlarge).
- Breakdown of a traditional restart (their stages): job restart; process and network init ("The process group initialization alone can take tens of minutes on large clusters"); checkpoint retrieval ("can take tens of minutes or longer"); data loader init ("a few minutes"); first step overhead; lost steps overhead.
- Worked cost example: "256 P5 instances, checkpointing every 20 minutes, faces two challenges when disrupted: 10 minutes of lost work plus 10 minutes for recovery. With ml.p5.24xlarge instances costing $55 per hour, each disruption costs $4,693 in compute time." (instance name as written in the post).
- Goodput used as "the percentage of time your cluster spends making forward progress on training rather than sitting idle during failures."
E. Product page: "With checkpointless training, recovery happens in minutes through peer-to-peer state transfer from healthy accelerators ... This enables over 95% training goodput on clusters with thousands of accelerators" (note: "over 95%" here vs "up to 95%" in the blog intro).

CAVEATS: all vendor internal studies; no per-stage timings published; hardware for the 2,304-GPU test not named in the text I read (P5 family implied by requirements, unconfirmed).
