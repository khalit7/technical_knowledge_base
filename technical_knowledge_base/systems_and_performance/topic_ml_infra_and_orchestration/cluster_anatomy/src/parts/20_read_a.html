A GPU training cluster is a few hundred to a few hundred thousand GPUs, packed into servers, racks and rows, joined by several networks and fed by shared storage, so that one training job can use thousands of them as if they were one machine. This page takes it apart level by level and says, at each level, what is there, how fast it talks to its neighbours, what limits it (bandwidth, ports, watts) and how you check it. Reading time about 22 minutes (words outside widgets at 200 a minute; the widgets, folded answers and outputs add about 8).

It is the cluster view. How each link works (PCIe, NVLink, InfiniBand and RoCE, fat trees, the all-reduce algorithms) is taught on {{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}}; watts, cooling and failure rates on {{Power, cooling and reliability|n:3f05c17b0d0d8143851cfc3ae14c3c22}}; the GPU itself on {{GPU architecture|n:3c65c17b0d0d810682aae39bd614ec64}}. This page uses their numbers (the same values, so the pages agree) and asks the questions they do not: what is in the box, how the boxes are grouped, which network each byte travels on, and what a scheduler and an engineer need to know about all of it.

The whole subject on one screen: the levels of one real cluster

Meta's Llama 3 cluster of 24,576 H100s ({{Llama 3 report, section 3.3.1|https://arxiv.org/html/2407.21783v3}}) published. Each row is a level: how many GPUs it holds, and the bandwidth one GPU gets to another GPU at that distance, one direction, on a log scale. Click a row for its section.

The staircase is the point: every level up multiplies the GPUs reachable and divides the bandwidth to them. Memory 3,350 GB/s, NVLink 450, the network card 50, and 7 when a whole pod crosses the 1:7 top layer at once derived (50 / 7). Where a job's traffic sits on this staircase decides how fast it runs. The {{Cluster explorer|#t-camap}} tab draws the same ladder for four designs.

Two words before anything else. A node is one server: one operating system, one set of CPUs and memory, usually 8 GPUs. A rank is one training process, normally one per GPU. The {{parent page|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} defines both and runs its running example (a 112,577-parameter GPT trained as 4 ranks on 2 "nodes") on toy clusters in containers; section 8 asks those toy nodes what they think they are, and compares the answers with a real DGX H100.

1. Inside one node: the parts list

The problem. A GPU is useless alone: something must feed it data, start its programs, connect it to other GPUs and carry its results away. A GPU server is that something, and it has many more parts than "8 GPUs" suggests. Knowing them matters because each part is a place where a job can be slow or broken: a GPU on the wrong CPU socket, a network card that is not the one next to its GPU, a disk that disappears when the node fails.

The reference node. NVIDIA's DGX H100 is the most fully documented 8-GPU server; most "HGX" servers from other builders (Meta's Grand Teton, Dell, Supermicro) use the same 8-GPU board and a similar layout. Its user guide lists ({{DGX H100 user guide|https://docs.nvidia.com/dgx/dgxh100-user-guide/introduction-to-dgxh100.html}}) vendor:

The PCIe tree and NUMA: why "which GPU" matters inside one box

PCIe is the bus every device in the server hangs from (taught on the {{interconnects page|n:3c65c17b0d0d81808563fd41fb163af0}}). In an 8-GPU server it is a tree: each CPU socket has PCIe lanes; under each socket sit PCIe switches; under each switch sit (typically) two GPUs and their two network cards, and some NVMe drives. Two consequences:

  • GPU and NIC pairs. When GPU 3 sends to another node, the fastest path is through the NIC under the same PCIe switch: the data goes GPU to switch to NIC, never touching the CPU (that is GPUDirect RDMA). Through a NIC under the other socket it would cross the link between the two CPUs. NCCL reads the tree and pairs each GPU with its nearest NIC; it names the distances PIX (same PCIe switch), PXB (several PCIe switches), PHB (through the CPU, same NUMA node) and SYS ("crossing the SMP interconnect (e.g. QPI/UPI)") ({{NCCL environment variables|https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/env.html}}) docs.
  • NUMA. With two sockets, each socket's memory is "near" to its own cores and "far" from the other's: a NUMA node (non-uniform memory access) is one socket and its memory. A rank whose process runs on socket 1 while its GPU hangs under socket 0 copies every batch across the inter-socket link. Launchers and schedulers fix this with CPU affinity: Slurm's --gpu-bind and --cpu-bind, Kubernetes' Topology Manager, or numactl in the launch script. The siblings Slurm and Kubernetes for ML cover the switches; affinity and pinning from the operating system side are on {{Scheduling and CPU time|n:3f05c17b0d0d81ed9c18cc47c6bfdf76}}.
The commonest node-level mistake
Running 8 ranks with no binding, so the operating system spreads them over both sockets as it likes. Nothing fails; input copies and the data loader get slower, by an amount that depends on the job. Check what a node's GPUs, NICs and NUMA nodes are with nvidia-smi topo -m before writing the launch script (section 9 shows how to read it).
