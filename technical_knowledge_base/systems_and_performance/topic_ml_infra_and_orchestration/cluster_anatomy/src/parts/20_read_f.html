5. Storage tiers at cluster level

Training data and checkpoints are far larger than any GPU's memory, and the storage every node can see is far slower than the storage inside one node. So a cluster has a ladder of tiers, each bigger, slower and longer-lived than the one above; the infrastructure's job is to keep the GPUs fed from the top while the truth lives at the bottom.

Fig. 4 puts the tiers on one scalable unit of NVIDIA's SuperPOD (32 nodes, two per rack) and sends a training job's data through them. Box sizes are not to scale; the numbers are the sources' own.

  1. Inside one node: three tiers. GPU memory, 8 x 80 GB = 640 GB at 3.35 TB/s per GPU; host DRAM, 2 TB, reached over PCIe 5.0 x16 at about 63 GB/s each way per GPU; local NVMe, 30.72 TB in RAID 0, whose bandwidth the guide does not give. Each is bigger and slower than the one above, and the NVMe is lost with the node.
  2. The shared file system: 32 nodes, one pipe. Each node can read faster than 40 GB/s; the standard tier gives all 32 together 40 GB/s of read. When they all read at once, each gets 40 / 32 = 1.25 GB/s derived.
  3. Object storage: where the data lives for years. Tens to hundreds of PB behind the file system. Meta's Tectonic for Llama 3 (a different cluster, drawn here for scale): 240 PB on 7,500 SSD servers, 2 TB/s sustained and 7 TB/s peak for the whole cluster.
  4. Stage once, read many times. The dataset comes down the ladder once, from the object store through the file system to each node's NVMe; every later epoch reads it locally, so the shared tiers carry the average, not every read.
  5. Checkpoint: every GPU writes at once. All ranks write together, a burst towards the file system, whose write is "at least ½ of the read performance": 20 GB/s per 32 nodes on the standard tier derived. Written straight there, the GPUs wait for the slowest pipe.
  6. Write near, drain far. The checkpoint lands first in host memory or local NVMe at node speed, training resumes, and the copy drains to the shared file system in the background.

Per node against the whole cluster. NVIDIA asks that each SuperPOD node can read faster than 40 GB/s, and sizes the shared file system at 40 GB/s of read per 32-node SU in its standard tier, 125 GB/s in the enhanced one, with write "at least ½ of the read performance" ({{SuperPOD storage guidance, Tables 5 and 6|https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-b200/latest/storage-architecture.html}}) vendor. Put together: 32 nodes each able to pull 40 GB/s could ask for 1,280 GB/s, and the standard tier gives 40, so only one node in 32 can read at its peak at a time derived. Storage is sized for the average plus bursts; the local NVMe absorbs the difference: stage the dataset once, read it many times locally.

Predict. A 4-SU SuperPOD (1,016 GPUs) writes a checkpoint of 4 GB per GPU, the top of Llama 3's "1 MB to 4 GB per GPU". With the standard tier's 80 GB/s of write, how long do the GPUs wait if nothing is asynchronous?
1,016 x 4 GB = 4.06 TB; at 80 GB/s that is 50.8 s derived (16.3 s on the enhanced tier's 250 GB/s). Every 30 minutes that is almost 3% of the run spent writing, which is why checkpoints go first to host memory or local NVMe and drain to shared storage in the background: the parent's {{Storage lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} measures async checkpointing on the running example, and {{Storage and data movement|n:3fc5c17b0d0d818a94ced3fc7c3331fe}} owns the rest: the same ladder drawn as a checkpoint walks down it (its opening figure), how striping spreads one file over many servers (section 2) and why start-up and small files storm the metadata servers (section 4). This page keeps only the tiers and their sizes.

Real examples: Llama 3's Tectonic, 240 PB on 7,500 SSD servers, 2 TB/s sustained and 7 TB/s peak; Fire-Flyer 2's 3FS, 180 storage nodes, 8 TB/s of read on the compute fabric; AI2's Jupiter on WEKA (section 8). Formats, shards and data loaders are on {{Storage and loading at scale|n:3f95c17b0d0d81398782efcb29d950d4}}; the page cache and fsync on {{Storage and file systems|n:3f05c17b0d0d8141be7acc1313570cbf}}.

6. Power and cooling: the limit that shapes the rest

Every level above is drawn around watts. Power decides how many GPUs share a rack, which decides how many share a rack switch or an NVLink domain, which decides what "packed" can mean for your job.
