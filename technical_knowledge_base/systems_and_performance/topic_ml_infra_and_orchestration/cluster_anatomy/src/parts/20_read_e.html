8. The toy cluster: what our "nodes" say they are

The parent page's labs run on a Slurm cluster of three "nodes" (c1, c2, c3), which are containers inside one Linux VM on a laptop. Asking them what they are is a cheap way to learn the questions to ask of a real node, because here every answer is visibly different. All of this is measured on 2026-10-16 with read-only commands (src/meas/probe.sh; output in src/meas/out/).

QuestionAnswer on c1Who says so

Real output, 2026-10-16. The node's declared size and its real fence differ; on a real cluster that mismatch is a bug (section 9's first check).

One network hop. A 64-byte TCP ping-pong between c1 and c2 took a median round trip of 79 µs (three runs of 2,000: µs), and 69 µs inside one container over loopback measured. A 64-byte transfer over InfiniBand on DeepSeek's cluster took 2.8 µs one way within a leaf ({{Zhao et al. 2025, Table 5|https://arxiv.org/html/2505.09343}}) authors. The toy's "network" is the Linux kernel copying between two containers' sockets: the hop costs about as much as loopback, because both are the same software path. Bulk transfer was 2.3 to 5.1 GB/s across the bridge and about 1.5 GB/s over loopback inside one 2-CPU container, which shows that CPU, not wire, limits it.

What transfers to a real cluster and what does not
Transfers: the questions (CPUs, memory, GPUs, NUMA, NICs, topology, as each layer sees them), the habit of checking the declared size against the real fence, and the fact that Slurm schedules what it is told. Does not transfer: any speed. There is no NVLink, no RDMA, no PCIe tree and no second socket here, which is why the page's bandwidth figures are published or derived, never measured.

9. Checking a real cluster

None of these could run here (no GPUs, no InfiniBand); they are what to run on the first day on a new cluster, each with what to look for. The parent's {{Failure lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} and the sibling {{Observability and cost|n:3c65c17b0d0d818ebf79d1af4532f3ee}} cover health checks that run every day.

Common mistakes

NCCL quietly uses TCP sockets instead of InfiniBand
With NCCL_DEBUG=INFO the log says NET/IB : No device found. (NCCL's src/transport/net_ib.cc line 749 at tag v2.27.7-1) and then uses NET/Socket. The job runs, much slower, with no error. Usual causes: a container started without the RDMA devices (/dev/infiniband) or the user-space RDMA libraries. Always grep the first job on a new cluster or image for the transport line.
The socket interface name is wrong on some nodes
NET/Socket : no interface found (net_socket.cc line 50, same tag) when NCCL_SOCKET_IFNAME names an interface the node does not have; common when two node types name their Ethernet ports differently. Use a prefix (NCCL_SOCKET_IFNAME=eth) or check every node type.
Scheduling what Slurm was told instead of what the node has
Slurm hands out the resources in slurm.conf; slurmd compares some of them with the hardware. On this topic's toy cluster a node declared with gpu:4 and no device files went INVAL with gres/gpu count reported lower than configured (0 < 4) measured (the parent's setup), while 4 declared CPUs on a 2-CPU cgroup passed silently (section 8). Compare scontrol show node with nvidia-smi, lscpu and the cgroup limits.
Asking the container how many CPUs it has
nproc printed 1 because of OMP_NUM_THREADS; os.cpu_count() printed the whole VM's 5; the cgroup allowed 2 measured. A data loader that starts os.cpu_count() workers in a container limited to a few CPUs oversubscribes them. Read the cgroup (cpu.max) or the scheduler's variables (SLURM_CPUS_PER_TASK).
Reading a vendor's "900 GB/s" as one direction
NVLink 4's "900 GB/s" adds both directions: 450 GB/s each way. The same for NVL72's "130 TB/s". Network cards are quoted per direction (400 Gb/s = 50 GB/s each way). Mix them and NVLink looks 18 times faster than the network instead of 9.
Sizing storage for the average, or power for the GPUs
The checkpoint burst, not the average read rate, decides how long GPUs wait (section 5: 51 s for a 4 GB-per-GPU checkpoint on 1,016 GPUs at 80 GB/s). And GPUs are only about 55% of a DGX H100's 10.2 kW (the power page), so a plan from GPU watts is short by almost half.
"Any 16 free GPUs are the same"
Only on an idle, non-oversubscribed network. Section 4: the same job is 7 times slower in its bandwidth term when spread across a 1:7 top layer that other jobs are using derived.
