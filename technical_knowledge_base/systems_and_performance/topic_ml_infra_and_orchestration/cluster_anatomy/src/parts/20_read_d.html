3. Four networks, the control nodes, and how a job lands

A cluster moves very different traffic: gradients between GPUs (huge, bursty, every step, and the step waits for them), training data and checkpoints (large), logins, job submissions and container images (small, many), and the power-cycle command for a node whose operating system is dead. On one network a checkpoint burst slows the gradients, and a broken switch takes away the only way to reach a hung node. So NVIDIA's DGX SuperPOD reference design separates them: "DGX SuperPOD configurations utilize four network fabrics" ({{SuperPOD network fabrics|https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-b200/latest/network-fabrics.html}}) vendor, plus the NVLink inside each node:

  • Compute fabric (back-end, east-west, scale-out): one 400 Gb/s port per GPU, InfiniBand or RoCE, rail-optimised. Only GPU-to-GPU traffic: the job's collectives. A container sees none of these cards unless they are passed in; how a Kubernetes pod gets its RDMA card and a fabric interface (Multus, SR-IOV) is {{Kubernetes for ML|n:3c65c17b0d0d81cf9417de52108cfbce}}, section 5.
  • Storage fabric: the two dual-port cards per node to the shared file system. NVIDIA asks that "the I/O per-node for the DGX SuperPOD must exceed 40 GBps", with the node side "slightly oversubscribed with a ratio near 4:3".
  • In-band management (the front-end): ordinary Ethernet to the login nodes, the scheduler (Slurm, Kubernetes, Run:ai in NVIDIA's list), NFS home directories and outside services such as container registries.
  • Out-of-band management (OOB): 1 GbE to "the management ports of all devices including DGX and management servers, storage, networking gear, rack PDUs": the BMCs, so a hung node can be power-cycled.

The control nodes. Besides the GPU nodes, a cluster has a few ordinary servers that run it. "The DGX SuperPOD architecture is a combination of DGX systems, InfiniBand and Ethernet networking, management nodes, and storage", with a management rack of "networking switches, management servers, storage arrays, and UFM appliances" (UFM is the InfiniBand fabric manager) ({{SuperPOD architecture|https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-b200/latest/dgx-superpod-architecture.html}}) vendor. What runs on them: login nodes, where people ssh in (through a bastion, with keys, multiplexing and tunnels: {{SSH|n:3c65c17b0d0d81f88f50e478c94ebdcd#s-cluster}}, section 13), edit, build and submit, never train; the controller or head node, which runs the scheduler and holds the state of every node and job (Slurm's slurmctld, Kubernetes' API server and scheduler, Ray's head node; the daemons are taught on {{Slurm|n:3c65c17b0d0d81889c32cd050bbbadd3}}); and service nodes for provisioning, monitoring and the fabric manager. They sit on the front-end, and the scheduler is a layer on top of the hardware: it only knows the shape it is told.

One job's life: which machines take part and which network carries each step

  1. The cluster at rest. A login node and the controller on the front-end; two GPU nodes, each with 8 GPUs on NVLink, its NICs, local NVMe and a BMC; a leaf switch of the compute fabric; the storage servers; every BMC on the out-of-band network.
  2. Submit (front-end). You ssh to a login node and run sbatch --nodes=2 --gpus-per-node=8 train.sh; the request goes to the controller, which queues it.
  3. Place (front-end). The scheduler picks two free nodes, under one leaf if it has been told the topology (section 4), and tells slurmd on each to start the job.
  4. Pull and stage (front-end, storage). Each node pulls the container image from a registry over the front-end (thousands of nodes pulling one image at once is its own storm) and stages the dataset from shared storage to local NVMe.
  5. Launch (inside each node). slurmd starts 8 ranks per node, one per GPU, each bound to the CPU socket its GPU and NIC hang under (section 1).
  6. Bootstrap (front-end). Before NCCL opens its RDMA connections, ranks exchange addresses over plain TCP on the interface NCCL_SOCKET_IFNAME selects. A job whose ranks cannot reach each other on the front-end hangs here although the compute fabric is fine ({{Launching distributed training|n:3fc5c17b0d0d81b3a8a5c58224bff9fa}} covers bootstrap in section 6 and its hangs in section 8).
  7. Train (NVLink, compute fabric). Tensor-parallel all-reduces stay inside each server on NVLink; the gradient all-reduce between the nodes goes from each GPU to its own NIC, through the leaf, over RDMA. The step waits on it.
  8. Read and checkpoint (storage). Batches come from local NVMe or the parallel file system; every so often all 16 ranks write a checkpoint at once, a burst (section 5). On Meta's clusters this rides the front-end; Fire-Flyer 2 sends it over the compute fabric on its own virtual lane.
  9. Watch and recover (front-end, out-of-band). slurmd and kubelet heartbeat to the controller, which declares a node dead when they stop (the parent's {{Failure lab|n:3c65c17b0d0d81b5925bfd1d8665dd4b}}); a hung node is power-cycled through its BMC over the out-of-band network, which works when the operating system does not.

A 16-GPU job on two 8-GPU nodes, SuperPOD layout (schematic). Press play or step. Lit: the machines and the network of each step. The commands are Slurm's; on Kubernetes the API server, the scheduler and the kubelet play the same parts.

Not everyone splits the networks the same way: Meta, DeepSeek and NVIDIA compared (under 1 min)

Meta's RoCE clusters have two: "the frontend (FE) network for tasks such as data ingestion, checkpointing, and logging", and the backend, "a specialized fabric that connects all RDMA NICs in a non-blocking architecture" ({{Meta engineering, Aug 5 2024|https://engineering.fb.com/2024/08/05/data-center-engineering/roce-network-distributed-ai-training-at-scale/}}) published: storage rides the front-end. DeepSeek's Fire-Flyer 2 goes the other way: each node has a single 200 Gb/s InfiniBand card, and its storage servers sit on the same fabric, "each storage server equipped with two IB NICs, respectively connected to different zones" ({{Fire-Flyer 2, section III|https://arxiv.org/html/2408.14158v2}}) authors, so gradients and checkpoints share one network, kept apart with InfiniBand service levels mapped to virtual lanes so that "flows in distinct lanes do not interfere with each other" (section VI-A1). Three designs, three answers: every separate network costs cables, switches and ports; merging them costs interference.
