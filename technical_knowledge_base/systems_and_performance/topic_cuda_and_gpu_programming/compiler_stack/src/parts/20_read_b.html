2. nvcc is a driver, not a compiler

A .cu file holds two programs, host code for the CPU and device code for the GPU. nvcc splits them, compiles the device code once per target you asked for, packs the results into a fat binary, embeds that in the host object as data, and hands the host code to your normal C++ compiler. nvcc --dryrun prints every command without running it.

Predict first: you compile with nvcc -arch=sm_90a. How many GPU code images end up inside the object file?

From nvcc --dryrun -O3 -arch=sm_90a -c softmax.cu, temporary paths shortened to <tmp>; file sizes from the same build with --keep. Script: src/code/nvcc_stages.sh.


The programs it ran: gcc -E preprocesses, once for the host and once per device target with a different __CUDA_ARCH__ (how one file holds code for several generations behind #if __CUDA_ARCH__ >= 900; the preprocessed device file is 1.4 MB for a 32-line kernel, almost all CUDA headers). cudafe++, NVIDIA's C++ front end, separates host from device and replaces each kernel<<<grid, block>>>(args) with a generated launch stub, a host function that packs the arguments and calls the runtime. cicc lowers device code to NVVM IR (NVIDIA's dialect of LLVM IR; {{NVVM IR specification|https://docs.nvidia.com/cuda/nvvm-ir-spec/index.html}}), optimises it with LLVM (inlining, unrolling, deciding which pointer points into which memory) and prints PTX, once per virtual target. ptxas allocates registers, schedules and emits SASS in a cubin; with -arch=sm_90a it also runs once on the generic compute_90 PTX only to check it. fatbinary packs the images. With -rdc=true (device functions called across files) nvlink joins cubins first; this build did not need it.


The answer to the prediction: -arch=sm_90a puts three images in the object, the sm_90a machine code and two PTX copies (generic compute_90 and Hopper-specific compute_90a), where -arch=sm_90 puts two. Section 5 explains why the extra copy exists and the trap it sets.
