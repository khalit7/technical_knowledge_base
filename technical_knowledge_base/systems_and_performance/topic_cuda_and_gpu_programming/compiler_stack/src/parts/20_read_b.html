2. PTX: an assembly language for a GPU that does not exist

PTX (Parallel Thread Execution) is the language cicc writes and ptxas reads. NVIDIA's manual calls it "a low-level parallel thread execution virtual machine and instruction set architecture", and its first stated goal is to "provide a stable ISA that spans multiple GPU generations" ({{PTX ISA 9.4, introduction|https://docs.nvidia.com/cuda/parallel-thread-execution/index.html}}) documented. Virtual is the key word: no chip executes PTX. It describes an idealised GPU with as many registers as you like, and every real GPU's assembler maps it onto real hardware. That is what makes PTX the portable form of a kernel: SASS for an H100 cannot run on a B200, but PTX can be compiled for either.

Five things to know when reading PTX:


    

  • Every instruction names its type: add.f32, mul.wide.s32, ld.global.f32. There is no implicit conversion; cvt does it.
    • 

  • Every memory access names its state space: .global (device memory), .shared (the block's on-chip scratchpad), .local (per-thread memory that lives in device memory: where spills go), .const, .param (kernel arguments). In SASS the same spaces become LDG, LDS, LDL, LDC.
    • 

  • Registers are virtual and almost single-assignment. This kernel declares  virtual registers; the H100 code uses 18 real ones (cuobjdump -res-usage: ). ptxas decides which values share a register.
    • 

  • Control flow is predicates plus branches: setp.ge.s32 %p1, ... writes a 1-bit predicate; @%p1 bra $L__BB0_2 branches on it. Any instruction can be predicated.
    • 

  • Special registers give a thread its coordinates: %tid.x is threadIdx.x, %ctaid.x is blockIdx.x (a CTA, cooperative thread array, is PTX's word for a thread block), %ntid.x is blockDim.x.
    • 



Versions: PTX is tied to the toolkit that wrote it


The first lines of every PTX file say which version of the language it uses and which target it is for. CUDA 13.4 writes .version 9.4. An assembler only accepts versions it knows. Triton 3.8.0 ships its own ptxas from CUDA 12.9 (recorded in the image), so feeding it the PTX above fails run here:




Edit the first line to .version 8.8 and the same old ptxas accepts the file, because this kernel uses nothing newer. Triton avoids the problem by writing .version 8.8 itself; its PTX header also shows a different author: , against cicc's "Generated by NVIDIA NVVM Compiler". This one error message is the whole story of driver JIT compatibility: the CUDA driver contains its own copy of ptxas, and it can only compile PTX whose version it knows. NVIDIA's compatibility guide puts it plainly: "Applications that compile device code to PTX will not work on older drivers" ({{CUDA minor version compatibility|https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html}}) documented. The runtime reports it as cudaErrorUnsupportedPtxVersion, whose comment in the CUDA 13.4.2 headers reads "The most common reason for this, is the PTX was generated by a compiler newer than what is supported by the CUDA driver and PTX JIT compiler."


PTX is not what runs: ptxas does a great deal


The same PTX file assembled at ptxas's four optimisation levels compiled here, sm_90a:




Instructions are the slots cuobjdump -sass lists, including the few padding NOPs at the end of the kernel.


At -O0 ptxas assembles the PTX nearly as written; from -O1 up it removes redundant work, allocates registers tightly and schedules. The SASS at -O3 has less than a third of the instructions of -O0. So a PTX listing tells you what the front end asked for (which loads, which shuffles, whether a loop was unrolled), and only SASS tells you what the GPU does. Judge registers, spills, vector widths and instruction counts from SASS and the ptxas -v report, never from PTX.
