2. nvcc is a driver, not a compiler

A .cu file holds two programs, host code for the CPU and device code for the GPU. nvcc splits them, compiles the device code once per target, packs the results into a fat binary embedded in the host object as data, and hands the host code to your C++ compiler. nvcc --dryrun prints every command without running it.

Predict first: you compile with nvcc -arch=sm_90a. How many GPU code images end up inside the object file?

Fig. 3 runs the real commands for the row softmax compiled here, CUDA 13.4.2: each program a box, each file it writes a slab (height on a log scale, sizes from the build with --keep). Blue is the host side, purple the generic compute_90 pass, teal the Hopper-specific compute_90a pass, orange SASS.

  1. The host side, split from the device side (commands 1 and 2). gcc -E preprocesses the host side (softmax.cpp4.ii, 1.23 MB; __CUDA_ARCH_LIST__=900 tells headers the targets). cudafe++, NVIDIA's C++ front end, separates host from device and replaces each kernel<<<grid, block>>>(args) with a launch stub, a host function that packs the arguments and calls the runtime: .cudafe1.cpp (1.16 MB) and .stub.c (1.6 KB).
  2. The generic pass: compute_90 to PTX (commands 3 and 4). The device side, preprocessed with __CUDA_ARCH__=900 (how one file holds code for several generations behind #if __CUDA_ARCH__ >= 900), is 1.4 MB for a 32-line kernel, almost all CUDA headers. cicc lowers it to NVVM IR (NVIDIA's dialect of LLVM IR; {{NVVM IR specification|https://docs.nvidia.com/cuda/nvvm-ir-spec/index.html}}), optimises it with LLVM (inlining, unrolling, which pointer points into which memory) and prints PTX per virtual target: compute_90.ptx, 6.1 KB.
  3. ptxas only checks the generic PTX (command 5). ptxas -arch=compute_90 writes nothing, so a Hopper-only instruction fails here (section 5's trap).
  4. The specific pass: compute_90a to PTX (commands 6 and 7). A third time, also defining __CUDA_ARCH_FEAT_SM90_ALL and __CUDA_ARCH_SPECIFIC__=900: PTX that may use wgmma and setmaxnreg, compute_90a.ptx, 6.1 KB.
  5. ptxas: PTX to SASS for sm_90a (command 8). Register allocation, scheduling, encoding: the H100's machine code in a cubin, 7.8 KB.
  6. fatbinary packs three images (commands 9 and 10). PTX compute_90, SASS sm_90a and PTX compute_90a go into softmax.fatbin (11.0 KB), written out as a C array for the host compiler (softmax.fatbin.c, 30.2 KB); rm deletes the binary form.
  7. gcc compiles the host side (command 11), stub and fat binary inside: softmax.o, 17.8 KB, the object your linker sees. With -rdc=true (device functions called across files) nvlink would join cubins first.
  1. Host side (commands 1 and 2): as with sm_90a.
  2. One device pass: compute_90 to PTX (commands 3 and 4); no architecture-specific target.
  3. ptxas: the same PTX to SASS for sm_90 (command 5).
  4. fatbinary packs two images (commands 6 and 7): SASS sm_90 and PTX compute_90.
  5. gcc compiles the host side (command 8).
