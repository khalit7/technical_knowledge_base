1. What each compiler decides on the way down

Every GPU compiler makes three kinds of decision. Fusion: which operations become one kernel, so intermediates stay in registers. Codegen: how a kernel's work is split over blocks, warps and threads, how wide each load is, which library to call instead (a matmul usually goes to cuBLAS). Assembly: which physical registers hold what and in which order instructions issue; on NVIDIA always ptxas (or tileiras), never the framework.

Fig. 2 · Seven scheduler nodes become one kernel plus a library call

Fusion, watched on the running example

Graph compilers fuse in rounds: try every pair of nodes that may share a loop, merge the legal ones, repeat until nothing changes. Inductor on softmax(x * 0.125) @ w, x 64 x 256 run here, torch 2.14.1, CPU, TORCH_LOGS=fusion. Predict: a scale, a max, a subtract, an exp, a sum and a divide make how many kernels?

  1. Seven scheduler nodes. Dynamo's three operations (multiply, softmax, matmul), decomposed and rewritten: four row reductions (op0 is every scaled value finite?, op1 and op2 two row maxima, op4 the sum of the exps), two full-size pointwise nodes (op3 subtract, scale, exp; op5 divide) and the external matmul op6. Unfused, every arrow is a tensor written to memory and read back.
  2. Round 1: seven nodes into four. The three reductions over the same rows merge; exp merges with the sum that consumes it. op3 with op5 is refused: "cannot fuse op3 with op5: intermediate nodes between node1 & node2" (the sum must finish before any divide).
  3. Round 2: four nodes into two. With the sum inside, everything that loops over rows becomes one outer loop over the 64 rows (OuterLoopFusedSchedulerNode). The matmul stays outside, an extern kernel.
  4. Round 3 finds nothing: code generation. One C++ kernel for the six nodes, cpp_fused__softmax_abs_all_amax_eq_mul_ne_sub_0, then extern_kernels.mm; the wrapper allocates the buffers. The intermediates never leave the kernel's row loop.

Nodes and log lines (under the figure) are Inductor's own (torch/_inductor/scheduler.py in 2.14.1).

The rule: a node fuses with another only when they share a loop over the same rows and nothing between them has to finish first. The extra row reductions are an algebraic rewrite: Inductor takes the maximum of the unscaled input and applies the scale after subtracting, guarded by a check that every scaled value is finite; the same rewrite appears in its GPU code for this graph on the Triton page.

Codegen: what the generated kernel decides


For a GPU Inductor writes Triton instead. For an RMSNorm forward, x * rsqrt(mean(x2) + eps) * w on 64 rows of 256 (generated without a device by the Triton page's stand-in driver), it is a triton_per_ kernel: a persistent reduction, each program keeping a whole row (r0_numel = 256) in registers, reducing it and writing the normalised row in one pass generated here, not runnable. Codegen also chose cache hints: the input row with evict_first (read once), w with evict_last (every row reuses it), which become load modifiers like those of section 4. Block sizes are left to the launcher, steered by size_hints; on a real GPU the autotuner times candidates. Below that, Triton's compiler and ptxas decide.
