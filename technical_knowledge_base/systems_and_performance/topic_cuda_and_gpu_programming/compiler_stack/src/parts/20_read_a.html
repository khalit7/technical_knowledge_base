1. What each compiler decides on the way down

Every ML compiler that targets a GPU makes the same three kinds of decision, at different levels and with different owners. Fusion: which operations become one kernel, so their intermediates stay in registers instead of going to memory. Codegen: how one kernel's work is split over blocks, warps and threads, how wide each load is, which library to call instead (a matmul usually goes to cuBLAS). Assembly: which physical registers hold what and in which order instructions issue; on NVIDIA that is always ptxas (or tileiras), never the framework. Where each road makes them:

Fusion, watched on the running example

Graph compilers fuse in rounds: try every pair of nodes that may share a loop, merge the legal ones, repeat until nothing changes. Inductor did this to softmax(x * 0.125) @ w with x of 64 x 256 run here, torch 2.14.1, CPU, TORCH_LOGS=fusion. Predict first: the softmax is a scale, a max, a subtract, an exp, a sum and a divide. How many kernels will it become? Then step through.

The seven scheduler nodes and the fusion log are Inductor's own (torch/_inductor/scheduler.py in 2.14.1).

Seven scheduler nodes became one C++ kernel, cpp_fused__softmax_abs_all_amax_eq_mul_ne_sub_0, plus extern_kernels.mm for the matmul. A node fuses with another only when they share a loop over the same rows and nothing between them has to finish first (round 1 refuses op3 with op5 because the sum, op4, sits between them; round 2 merges all six once the sum is inside). The matmul is not fused: it goes to a library. The extra row reductions are an algebraic rewrite: Inductor takes the maximum of the unscaled input and applies the scale after subtracting, guarded by a check that every scaled value is finite. The same rewrite appears in Inductor's GPU code for this graph on the Triton page.

Codegen: what the generated kernel decides


For a GPU the same Inductor writes Triton instead of C++. Generated here without a device (the Triton page's stand-in driver) for an RMSNorm forward, x * rsqrt(mean(x2) + eps) * w on 64 rows of 256, it is a triton_per_ kernel: a persistent reduction, in which each program keeps a whole row (r0_numel = 256) in registers, reduces it and writes the normalised row in one pass generated here, not runnable. Codegen also chose cache hints: the input row is loaded with evict_first (read once), w with evict_last (every row reuses it), which end up as load modifiers like those of section 4. Block sizes are left to the launcher, steered by size_hints; on a real GPU the autotuner times candidates. From here down, Triton's compiler and ptxas decide the rest.
