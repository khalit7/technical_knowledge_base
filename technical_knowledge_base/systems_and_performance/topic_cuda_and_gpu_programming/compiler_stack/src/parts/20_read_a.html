In one screen: two roads to the same machine code

An NVIDIA GPU executes only one thing: SASS, the machine code of one GPU generation. Whatever you write, CUDA C++ or a line of PyTorch, reaches the GPU after a chain of compilers has turned it into SASS. This page follows that chain on the two roads an ML engineer uses: a hand-written CUDA kernel through nvcc, and PyTorch code through torch.compile. The running examples are the parent topic's: the row softmax kernel of its {{Compiler explorer|n:3c65c17b0d0d81c39f34d5e070d783c1}} tab, and softmax(x * 0.125) @ w, the attention-shaped graph the parent page follows from PyTorch to the instructions.

What is real here, and what is not
Every listing, error message, file size and log on this page was produced by the real tools: the CUDA 13.4.2 toolkit (nvcc, ptxas, cuobjdump, nvdisasm, NVRTC, tileiras) and torch 2.14.1 with Triton 3.8.0, inside the Docker image kb-gpu-lab:1 on an Apple M1 Pro laptop. There is no NVIDIA GPU, so nothing here ran on one: compiling needs no GPU, running does. Kernels were compiled, not executed; torch.compile ran for real on the CPU, where Inductor writes C++; its GPU code (Triton) was generated without a device by the method of the {{Triton and Gluon|n:3c65c17b0d0d81729d15ed4d1a4461b3}} page. Where the page says what a GPU or driver would do, it cites NVIDIA's documentation and says "not run here". Labels: compiled here run here (CPU) documented derived.

The two roads meet at the same assembler: Triton writes PTX through LLVM and hands it to ptxas, exactly as nvcc does. Three side roads join them: NVRTC compiles CUDA C++ while your program runs (section 5), inline PTX lets C++ name one exact instruction (section 6), and the newer MLIR-based languages (Triton, the CuTe DSL, cuTile with CUDA Tile IR) build their own front ends on the same back end (section 7).

Why an ML engineer needs this
  • "no kernel image is available for execution on the device", a slow first iteration on a new GPU, or a wheel that will not load on a B300: all are questions of which images a binary carries and what the driver does with them (section 4, and the {{Will it run?|#t-run}} tab).
  • Is my kernel using tensor cores, vector loads, no spills? Only the SASS answers that; PTX can mislead, because ptxas rewrites a lot (sections 2 and 3, and the {{SASS, decoded|#t-sass}} tab).
  • The first training step takes minutes, then a shape changes and it happens again: torch.compile's compile cost, graph breaks and recompilations, and how to see each one (sections 8 and 9, and the {{Inside torch.compile|#t-tc}} tab).

1. nvcc is a driver, not a compiler

nvcc runs a sequence of other programs. A .cu file holds two programs at once: host code for the CPU and device code for the GPU. nvcc splits them, compiles the device code once per target you asked for, packs the results into a fat binary (a container holding several GPU code images), embeds that container in the host object as data, and hands the host code to your normal C++ compiler. nvcc --dryrun prints every command without running it. What each program does:


    

  • gcc -E (your host compiler as preprocessor) expands includes and macros. It runs once for the host side and once per device target, each time with a different __CUDA_ARCH__, which is how one source file can contain code for several generations behind #if __CUDA_ARCH__ >= 900. The preprocessed device file is 1.4 MB for a 32-line kernel: almost all of it is the CUDA headers.
    • 

  • cudafe++ is NVIDIA's C++ front end. It parses CUDA C++, separates host from device, and replaces each kernel<<<grid, block>>>(args) with a call to a generated launch stub, a host function that packs the arguments and calls the CUDA runtime.
    • 

  • cicc is the device compiler: it parses the preprocessed device source with its own copy of the front end, lowers it to NVVM IR (NVIDIA's dialect of LLVM IR; {{NVVM IR specification|https://docs.nvidia.com/cuda/nvvm-ir-spec/index.html}}), runs an optimiser built on LLVM (inlining, unrolling, constant folding, deciding which pointer points into which memory) and prints PTX. It runs once per virtual target.
    • 

  • ptxas is the assembler that is really a second optimising compiler: it allocates real registers, schedules instructions, and emits SASS inside a cubin (an ELF file for the GPU). With -arch=sm_90a, nvcc also runs ptxas once on the generic compute_90 PTX just to check it (step 5); no file comes out.
    • 

  • fatbinary packs the images; the host compiler then builds the host object with the fat binary inside it. With -rdc=true (separate compilation, device functions called across files) a device link step, nvlink, joins cubins first; that is the one program this build did not need.
    •
