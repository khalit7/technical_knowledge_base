8. torch.compile as one road: what reaches Inductor, and what it costs

This section follows what each stage hands to the next; how to use torch.compile well (every graph-break kind, dynamic shapes, regional compilation, export) is on {{torch.compile from the user's side|n:3c65c17b0d0d8123a232d75bd7339ecb}}.

Dynamo: a graph and the guards that keep it valid

CPython lets a library replace the function that evaluates every Python frame (PEP 523); TorchDynamo installs itself there, sees each call before CPython runs it, and reads the function's bytecode symbolically: tensor operations are recorded into an FX graph, everything else (Python arithmetic on ints, loops over lists, attribute lookups) runs at trace time and its result is baked in ({{Ansel et al., PyTorch 2, ASPLOS 2024, section 3|https://docs.pytorch.org/assets/pytorch2-2.pdf}}) documented. The graph recorded for the running example run here, torch 2.14.1, CPU:



Baking values in is safe only if the next call looks the same, so Dynamo writes guards, cheap checks run on every call before the cached code is reused: here  guard lines, chiefly each input's dtype, device, requires_grad, sizes and strides, and global state (grad mode, autocast, default dtype, thread count). A failed guard means a recompilation; Dynamo keeps every version up to torch._dynamo.config.recompile_limit = , then runs that function eagerly.


The guards, as Dynamo wrote them


Where Dynamo meets something it cannot record (a print, by default a .item(), an if on a tensor's value), it compiles the graph so far, lets CPython run that part, and resumes tracing after it: a graph break. For the compiler stack the cost is fusion: the graphs on either side are compiled separately, so nothing fuses across the break, and every call pays Python in between. fullgraph=True turns a break into an error.

Recompilations on the running example: what changed, and what it cost


The running example called four times with a different number of rows run here, CPU:






The first call compiled a graph specialised to 64 rows. The second failed the size guard, and Dynamo recompiled with the row count as a symbol (s77, valid from 2 upward) because automatic_dynamic_shapes is on by default; from then on any row count reuses that code. That is the default dynamic=None: "automatically detect if dynamism has occurred and compile a more dynamic kernel upon recompile" ({{torch.compile, PyTorch 2.14|https://docs.pytorch.org/docs/2.14/generated/torch.compile.html}}). AOTAutograd: the backward graph, and what to save


AOTAutograd runs autograd on fake tensors (shapes and dtypes, no data) to record one joint forward-and-backward graph, then "uses a min-cut algorithm to split this joint graph into separate forward and backward graphs in a way that optimizes for memory usage" ({{Ansel et al., section 3.9|https://docs.pytorch.org/assets/pytorch2-2.pdf}}). This is a compiler decision of its own, save or recompute, taken before Inductor fuses anything. On the RMSNorm of section 1 run here:

Inductor then lowers each graph to its own loop-level IR (a "define-by-run" IR whose loop bodies are Python functions; paper section 4.3), fuses as section 1 showed, and writes one kernel per fused group plus a Python wrapper that allocates buffers and launches them: "TorchInductor generates both Triton and C++ as output code" (paper section 4).


Modes, and the Inductor options each turns on




CUDA graphs record a sequence of kernel launches once and replay it with one call, removing per-launch CPU overhead; they need static shapes and addresses and keep a private memory pool. They belong to {{Streams, CUDA graphs and multi-GPU|n:3f05c17b0d0d81b19a6acab65c370b75}}, whose section 4 covers mode="reduce-overhead" (CUDAGraph Trees) and Inductor's graph partitions, on by default in PyTorch 2.14.1. Autotuning times candidate kernels on the real GPU; neither could run here.




What compiling costs, and the caches that hide it


The RMSNorm forward and backward compiled in a fresh process, three times with an empty cache directory and three times with the directory the first run filled run here, CPU, 2 threads:




Most of a cold compile is Python (Dynamo, AOTAutograd, Inductor) plus the C++ or Triton compiler; the first call compiled for 3 to 4 seconds here, against about a millisecond afterwards. A warm start skips code generation by finding the result in Inductor's on-disk caches (TORCHINDUCTOR_CACHE_DIR; the FX graph cache is on by default) and Triton's. On a real model a cold compile is minutes, which is why torch.compiler.save_cache_artifacts() and load_cache_artifacts() exist (both in torch 2.14.1): build the caches once and ship them to every node. These steady-state numbers are a tiny CPU operation and say nothing about GPU speed-ups; for those, the PyTorch 2 paper reports 2.27x for inference and 1.41x for training (geometric mean over 180+ models, A100) published.


To see every stage yourself: TORCH_LOGS takes a comma-separated list (graph_code, guards, graph_breaks, recompiles, dynamic, bytecode, aot_graphs, fusion, output_code; a + prefix such as TORCH_LOGS=+dynamo adds debug detail); for a whole run, TORCH_TRACE=<dir> plus tlparse makes an HTML report per compiled frame.
