9. torch.compile, part 2: AOTAutograd, Inductor, and what it costs

AOTAutograd: the backward pass, decided ahead of time

Dynamo captures only the forward computation. For training, AOTAutograd runs PyTorch's autograd on fake tensors (shapes and dtypes, no data) to record one joint forward-and-backward graph, then "uses a min-cut algorithm to split this joint graph into separate forward and backward graphs in a way that optimizes for memory usage", recomputing activations that are cheap to recompute instead of saving them ({{Ansel et al., section 3.9|https://docs.pytorch.org/assets/pytorch2-2.pdf}}). Inductor: loops, fusion, code


TorchInductor lowers each graph into its own loop-level form (a "define-by-run" IR whose loop bodies are Python functions; paper section 4.3), decides which operations can share one pass over memory (fusion), and writes one kernel per fused group plus a Python wrapper that allocates buffers and launches them. "TorchInductor generates both Triton and C++ as output code" (paper section 4): Triton for GPUs, C++ with OpenMP for CPUs. Matrix multiplies go to a library call unless you ask for autotuning. Read it the way you would read a hand-written softmax: one OpenMP loop over the 64 rows; inside, a vectorised pass computing the row maximum (twice: once of x * 0.125 and once of x, plus a check that every scaled value is finite), a pass computing exp and the sum, and a pass dividing. That finite-check is the algebraic rewrite the Triton page found in Inductor's GPU code for the same graph: Inductor takes the maximum of the unscaled input and applies the scale after subtracting, when it can prove that is safe.

Modes, and what each turns on




CUDA graphs record a whole sequence of kernel launches once and replay it with one call, removing per-launch CPU overhead; they need static shapes and memory addresses, and keep a private memory pool. They are the subject of the {{Streams, CUDA graphs and multi-GPU|n:3f05c17b0d0d81b19a6acab65c370b75}} page. Autotuning times candidate kernels on the real GPU; neither could run here.


What compiling costs, and the caches that hide it


The RMSNorm forward and backward compiled in a fresh process, three times with an empty cache directory and three times with the directory the first run filled run here, CPU, 2 threads:




Most of a cold compile is Python (Dynamo, AOTAutograd, Inductor) plus the C++ or Triton compiler; a warm start skips the code generation and compiler by finding the result in Inductor's on-disk caches (TORCHINDUCTOR_CACHE_DIR; the FX graph cache is on by default) and Triton's. On a real model the cold compile is minutes, which is why torch.compiler.save_cache_artifacts() and load_cache_artifacts() exist (both present in torch 2.14.1): build the caches once, ship them to every training node. The steady-state numbers in this run are a tiny CPU operation and say nothing about GPU speed-ups; for those, the PyTorch 2 paper reports 2.27x for inference and 1.41x for training (geometric mean over 180+ models, A100) published.


The logs you will actually use
TORCH_LOGS takes a comma-separated list; all of these were used on this page: graph_code (the FX graphs), guards, graph_breaks, recompiles, dynamic, bytecode, aot_graphs, fusion, output_code (every generated kernel and the wrapper). Prefix a component with + for debug detail (TORCH_LOGS=+dynamo). For a whole training run, TORCH_TRACE=<dir> plus the tlparse tool turns the same information into an HTML report per compiled frame. The {{Inside torch.compile|#t-tc}} tab holds every log on this page, per program and stage.
