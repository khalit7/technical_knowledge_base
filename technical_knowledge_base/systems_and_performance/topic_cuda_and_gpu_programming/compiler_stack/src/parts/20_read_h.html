Dynamo: a graph and the guards that keep it valid

CPython lets a library replace the function that evaluates every Python frame (PEP 523); TorchDynamo installs itself there and reads each function's bytecode symbolically: tensor operations are recorded into an FX graph, everything else (Python arithmetic on ints, loops over lists, attribute lookups) runs at trace time and its result is baked in ({{Ansel et al., PyTorch 2, ASPLOS 2024, section 3|https://docs.pytorch.org/assets/pytorch2-2.pdf}}) documented. The graph recorded for the running example run here, torch 2.14.1, CPU:



Baking values in is safe only if the next call looks the same, so Dynamo writes guards, cheap checks run before cached code is reused: here  lines, chiefly each input's dtype, device, requires_grad, sizes and strides, and global state (grad mode, autocast, default dtype, thread count). A failed guard means a recompilation; past torch._dynamo.config.recompile_limit =  versions, the function runs eagerly.


The guards, as Dynamo wrote them


Where Dynamo meets something it cannot record (a print, by default a .item(), an if on a tensor's value), it compiles the graph so far, lets CPython run that part and resumes tracing after it: a graph break. Nothing fuses across it, and every call pays Python in between; fullgraph=True turns a break into an error. Every kind of break and its fix (nine lines, twelve fixes) is section 3 of {{torch.compile from the user's side|n:3c65c17b0d0d8123a232d75bd7339ecb}}; the block below shows what Dynamo does to the bytecode.

AOTAutograd: the backward graph, and what to save


AOTAutograd runs autograd on fake tensors (shapes and dtypes, no data) to record one joint forward-and-backward graph, then "uses a min-cut algorithm to split this joint graph into separate forward and backward graphs in a way that optimizes for memory usage" ({{Ansel et al., section 3.9|https://docs.pytorch.org/assets/pytorch2-2.pdf}}): save or recompute, decided before Inductor fuses anything. Inductor then lowers each graph to its loop-level IR (a "define-by-run" IR whose loop bodies are Python functions; paper section 4.3), fuses (section 1), and writes one kernel per fused group plus a Python wrapper that allocates buffers and launches them: "TorchInductor generates both Triton and C++ as output code" (paper section 4).


Modes, and the Inductor options each turns on




CUDA graphs record a sequence of kernel launches once and replay it with one call, removing per-launch CPU overhead; they need static shapes and addresses and keep a private memory pool. They belong to {{Streams, CUDA graphs and multi-GPU|n:3f05c17b0d0d81b19a6acab65c370b75}}, whose section 4 covers mode="reduce-overhead" (CUDAGraph Trees) and Inductor's graph partitions, on by default in PyTorch 2.14.1. Autotuning times candidate kernels on the real GPU; neither could run here.




What compiling costs, and the caches that hide it


The RMSNorm forward and backward compiled in a fresh process, three times with an empty cache directory and three times warm run here, CPU, 2 threads:




A cold compile is mostly Python (Dynamo, AOTAutograd, Inductor) plus the C++ or Triton compiler: 3 to 4 seconds for the first call here, about a millisecond afterwards. A warm start finds the result in Inductor's on-disk caches (TORCHINDUCTOR_CACHE_DIR; the FX graph cache is on by default) and Triton's. On a real model a cold compile is minutes, hence torch.compiler.save_cache_artifacts() and load_cache_artifacts() (torch 2.14.1): build the caches once, ship them to every node. These CPU numbers say nothing about GPU speed-ups; the PyTorch 2 paper reports 2.27x for inference and 1.41x for training (geometric mean over 180+ models, A100) published.
