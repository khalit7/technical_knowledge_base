5. Which binary runs on which GPU

Every NVIDIA GPU has a compute capability (CC): 8.0 for the A100, 8.9 for the L4 and RTX 4090, 9.0 for the H100 and H200, 10.0 for the B200 and GB200, 10.3 for the B300 and GB300, 12.0 for the RTX 5090 ({{NVIDIA, CUDA GPU compute capability|https://developer.nvidia.com/cuda-gpus}}) documented. Compiler targets are named after it: compute_90 is a virtual architecture (PTX for CC 9.0's feature set), sm_90 a real architecture (SASS for CC 9.0 chips). CUDA 13.4's nvcc knows these real targets recorded here: . Nothing older than Turing (7.5) is left, and with no -arch nvcc builds for sm_75 ().

The rules the driver follows

  • SASS runs within one major version on equal or newer minors: "a cubin compiled for compute capability 8.6 (sm_86) runs on GPUs with CC 8.6 or 8.9, but not on CC 8.0", and GPUs "are not binary compatible between major compute capability versions" ({{CUDA Programming Guide 1.3|https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html}}).
  • PTX "can be JIT compiled at application runtime for any compute capability equal or higher to the compute capability of the PTX code" (same page). The driver does it when no compatible SASS exists and "automatically caches a copy of the generated binary code".
  • The driver must know the PTX's version (section 3). CUDA 13.x applications need driver 580 or newer; a 13.0 driver runs SASS built by CUDA 13.4 (minor version compatibility) but cannot JIT its PTX ({{CUDA compatibility guide|https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html}}).
  • If nothing fits: cudaErrorNoKernelImageForDevice, "no kernel image is available for execution on the device".

What each flag puts in the binary

-gencode arch=compute_XY,code=... is the explicit form: arch chooses the PTX to compile from, code lists what to embed (sm_XY for SASS, compute_XY for the PTX itself). -arch=sm_XY is shorthand: "nvcc --gpu-architecture=sm_100 is equivalent to nvcc --gpu-architecture=compute_100 --gpu-code=sm_100,compute_100" ({{nvcc manual|https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html#gpu-architecture-arch}}). Three kinds of target: plain, a and f

Hopper added instructions NVIDIA does not promise to keep (wgmma, setmaxnreg); Blackwell added more (tcgen05). Using them needs an architecture-specific target with an a suffix, whose code "only runs on GPUs of that specific CC and no others". CUDA 12.9 added family-specific f targets for features "supported by devices of more than one minor compute capability": sm_100f code runs on CC 10.0, 10.3 and any later 10.x ({{NVIDIA technical blog, May 1 2025|https://developer.nvidia.com/blog/nvidia-blackwell-and-nvidia-cuda-12-9-introduce-family-specific-architecture-features/}}) documented. The JIT cache, and when loading happens


Kernels load lazily by default (CUDA_MODULE_LOADING=LAZY): a kernel is loaded, and JIT-compiled if the binary has only PTX for this GPU, the first time it is used. So the first training step is slow once per machine (per cache directory, ~/.nv/ComputeCache on Linux), then fast; in a container with a fresh home directory it is slow every time, unless CUDA_CACHE_PATH points at a persistent volume. CUDA_FORCE_PTX_JIT=1 ignores every cubin: the standard test that your binary would survive a future GPU.
