8. torch.compile, part 1: Dynamo captures a graph

torch.compile(fn) returns a function that, when called, does not simply run fn. CPython lets a library replace the function that evaluates every Python frame (PEP 523, "the frame evaluation API"); TorchDynamo installs itself there, so it sees each call to fn before CPython runs it ({{Ansel et al., PyTorch 2, ASPLOS 2024, section 3|https://docs.pytorch.org/assets/pytorch2-2.pdf}}) documented. It then reads the function's bytecode (the instructions CPython would execute) symbolically: tensor operations are recorded into an FX graph, a list of PyTorch operations with their inputs; everything else (Python arithmetic on ints, loops over lists, attribute lookups) is executed at trace time and its result baked into the graph. Baking values in is only safe if the next call looks the same, so Dynamo also writes guards: cheap checks run on every call before the compiled code is reused. If every guard passes, the cached code runs. If one fails, Dynamo compiles again (a recompilation) and keeps both versions, up to a limit (torch._dynamo.config.recompile_limit =  here).


Before and after: one call with a graph break, and with fullgraph=True


When Dynamo meets something it cannot put in a graph, it does not fail by default: it compiles what it has so far, lets CPython run the unsupported part, and resumes tracing after it. That split is a graph break. The function below has one, a print. Step through what Dynamo really did run here, then switch to fullgraph=True, where the same function is an error instead.

Recompilations: what changed, and what it cost


The running example called four times with a different number of rows each time run here, CPU:






The first call compiled a graph specialised to 64 rows. The second failed the size guard; Dynamo recompiled with the row count as a symbol (s77, valid from 2 upward) because automatic_dynamic_shapes is on by default; from then on any row count reuses that code. This is the default dynamic=None, which the docs describe as "automatically detect if dynamism has occurred and compile a more dynamic kernel upon recompile" ({{torch.compile, PyTorch 2.14|https://docs.pytorch.org/docs/2.14/generated/torch.compile.html}}). Python numbers behave the same way: a float argument s was first guarded by value, then, after one change, made symbolic run here:




In training, the usual sources of recompilation are the last batch of an epoch being shorter, variable sequence lengths, a learning rate or step count passed as a Python number, and switching between train() and eval(). TORCH_LOGS=recompiles prints each one with the guard that failed, as above.
