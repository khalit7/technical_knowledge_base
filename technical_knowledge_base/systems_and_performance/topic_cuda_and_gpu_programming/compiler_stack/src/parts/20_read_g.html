7. LLVM and MLIR: how the other front ends reach PTX

PTX is text with a published specification, so any compiler can target it and leave the rest to ptxas. Most do it through LLVM, whose NVPTX back end turns LLVM IR into PTX ({{LLVM, User Guide for NVPTX|https://llvm.org/docs/NVPTXUsage.html}}): clang compiles CUDA C++ with it ({{Compiling CUDA with clang|https://llvm.org/docs/CompileCudaWithLLVM.html}}), Rust's nvptx64-nvidia-cuda target uses it ({{rustc platform support|https://doc.rust-lang.org/rustc/platform-support/nvptx64-nvidia-cuda.html}}), and so do Triton and XLA's native emitters. NVIDIA's cicc is LLVM-based too but closed. The first lines of the PTX tell them apart:

cicc (nvcc), CUDA 13.4
Triton 3.8.0 (LLVM NVPTX)


MLIR is LLVM's framework for building compilers out of dialects, small intermediate languages each at its own level of abstraction, lowered one into the next ({{mlir.llvm.org|https://mlir.llvm.org/}}). The newer front ends are built on it and differ in the level you write at: StableHLO (JAX's input to XLA), Triton's TTIR and TTGIR, the CuTe DSL of CUTLASS 4 (Python with CuTe layouts, lowered through "the CUTLASS Python compiler stack and NVIDIA CUDA toolchain", {{CuTe DSL overview|https://docs.nvidia.com/cutlass/latest/media/docs/pythonDSL/overview.html}}; it belongs to {{Libraries and tensor cores|n:3c65c17b0d0d81a7adcaebee2f44a087}}), and CUDA Tile IR. Tile IR is the newest road, so here it is end to end.


CUDA Tile IR, compiled here without a GPU


NVIDIA calls Tile IR "a portable, low-level tile virtual machine and instruction set that models the GPU as a tile-based processor" ({{CUDA Tile IR documentation|https://docs.nvidia.com/cuda/tile-ir/latest/}}), "an MLIR-based intermediate representation" released with CUDA 13.1 ({{NVIDIA/cuda-tile|https://github.com/NVIDIA/cuda-tile}}) documented. It plays PTX's role for tiles: a portable form that tileiras turns into SASS. A cuTile Python  vector add (pip package cuda-tile) was exported to Tile IR bytecode and to cubins for four targets in the CUDA 13.4.2 image compiled here:


# cuTile: one block adds one tile of 1024 numbers; no thread index anywhere
@ct.kernel
def vector_add(a, b, out):
    i = ct.bid(0)
    x = ct.load(a, index=(i,), shape=(TILE,))
    y = ct.load(b, index=(i,), shape=(TILE,))
    ct.store(out, index=(i,), tile=x + y)




The same 703-byte file became four different machine codes with no thread, warp or layout in the source: tileiras decided how many threads, how each walks the tile and how wide each load is, the promise Triton makes one level up. An incubator back end sends Triton through Tile IR ({{triton-lang/Triton-to-tile-IR|https://github.com/triton-lang/Triton-to-tile-IR}}; not part of Triton 3.8.0, per this topic's shared facts). Running these cubins needs driver r580 or later, per cuTile's README; not run here.
