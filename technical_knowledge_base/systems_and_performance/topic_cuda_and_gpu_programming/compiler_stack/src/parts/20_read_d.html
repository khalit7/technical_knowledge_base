4. Which binary runs on which GPU

Every NVIDIA GPU has a compute capability (CC), a version number for its instruction set and limits: 8.0 for the A100, 8.9 for the L4 and RTX 4090, 9.0 for the H100 and H200, 10.0 for the B200 and GB200, 10.3 for the B300 and GB300, 12.0 for the RTX 5090 ({{NVIDIA, CUDA GPU compute capability|https://developer.nvidia.com/cuda-gpus}}) documented. Compiler targets come in two kinds named after it: compute_90 is a virtual architecture (PTX written for CC 9.0's feature set) and sm_90 a real architecture (SASS for CC 9.0 chips). What each flag puts in the binary

-gencode arch=compute_XY,code=... is the explicit form: arch chooses the PTX to compile from, code lists what to embed (sm_XY for SASS, compute_XY for the PTX itself). -arch=sm_XY is shorthand; the manual: "nvcc --gpu-architecture=sm_100 is equivalent to nvcc --gpu-architecture=compute_100 --gpu-code=sm_100,compute_100" ({{nvcc manual|https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html#gpu-architecture-arch}}). Three kinds of target: plain, a and f

Hopper introduced instructions that NVIDIA does not promise to keep in later chips (wgmma, setmaxnreg); Blackwell added more (tcgen05). To use them you compile for an architecture-specific target with an a suffix, and NVIDIA's rule is strict: such code "only runs on GPUs of that specific CC and no others". CUDA 12.9 added family-specific targets with an f suffix, for features "supported by devices of more than one minor compute capability" in one major version: sm_100f code runs on CC 10.0 and 10.3 and on any later 10.x ({{NVIDIA technical blog, May 1 2025|https://developer.nvidia.com/blog/nvidia-blackwell-and-nvidia-cuda-12-9-introduce-family-specific-architecture-features/}}) documented. Because -arch=sm_90a also emits generic compute_90 PTX (section 1), a kernel that uses wgmma in inline PTX cannot be built that way: the generic pass reaches ptxas with Hopper-only instructions compiled here:

The rules the driver follows


    

  • SASS runs within one major version on equal or newer minors: "a cubin compiled for compute capability 8.6 (sm_86) runs on GPUs with CC 8.6 or 8.9, but not on CC 8.0", and GPUs "are not binary compatible between major compute capability versions" ({{CUDA Programming Guide 1.3|https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html}}). An a cubin runs on its exact CC only; an f cubin on its family.
    • 

  • PTX "can be JIT compiled at application runtime for any compute capability equal or higher to the compute capability of the PTX code" (same page). The driver does it when no compatible SASS exists, and "automatically caches a copy of the generated binary code".
    • 

  • The driver must know the PTX's version (section 2). CUDA 13.x applications need driver 580 or newer; a 13.0 driver runs SASS built by CUDA 13.4 (minor version compatibility) but cannot JIT its PTX ({{CUDA compatibility guide|https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html}}).
    • 

  • If nothing fits, the launch fails with cudaErrorNoKernelImageForDevice: "no kernel image is available for execution on the device".
    •

The JIT cache, and when loading happens




VariableWhat it does (CUDA Programming Guide, environment variables, updated Sep 10 2026)


CUDA_CACHE_PATHWhere JIT results are kept; default ~/.nv/ComputeCache on Linux.


CUDA_CACHE_MAXSIZECache size in bytes: default 1 GiB on desktops and servers (256 MiB embedded), maximum 4 GiB.


CUDA_CACHE_DISABLE=1No on-disk cache: every run JIT-compiles again.


CUDA_FORCE_PTX_JIT=1Ignore every cubin and JIT the PTX: the standard test that your binary would survive a future GPU.


CUDA_DISABLE_PTX_JIT=1Never JIT; use a compatible cubin or fail.


CUDA_MODULE_LOADINGLAZY by default: a kernel is loaded (and JIT-compiled if needed) the first time it is used, not at start-up.




Source: {{CUDA Programming Guide, environment variables|https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html}} documented. The practical consequence of lazy loading plus JIT: on a GPU your binary has only PTX for, the first call of every kernel pays a compile, and the first training step is slow once per machine (per cache directory), then fast. In a container with a fresh home directory every time, it is slow every time; mount or point CUDA_CACHE_PATH at a persistent directory.
