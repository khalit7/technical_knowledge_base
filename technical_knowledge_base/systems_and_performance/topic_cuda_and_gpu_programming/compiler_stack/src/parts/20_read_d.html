4. SASS: reading the machine code

ptxas turns PTX into SASS, the instruction set one GPU generation executes. NVIDIA does not publish its encoding; it publishes the opcodes with one-line meanings ({{CUDA Binary Utilities, instruction set reference|https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html#instruction-set-reference}}) and tools that print it: cuobjdump -sass for a binary, nvdisasm for a cubin. The parent's {{Compiler explorer|n:3c65c17b0d0d81c39f34d5e070d783c1}} tab lines SASS up against source; this section teaches the grammar of one line, then the part nobody prints.

UR4, ULDC, S2URUniform registers: one value for the whole warp, computed once on a separate datapath. The compiler moves whatever every thread would compute identically (block index, arguments, base addresses) into them.

The bits nobody prints: stall counts and scoreboards

Since Volta every SASS instruction is one 128-bit word, and part of it is not the instruction: it is control information ptxas writes to tell the warp scheduler how to run it. A GPU issues each warp's instructions in order and, unlike a CPU core, does not track register dependencies itself; ptxas, which knows each latency, writes the waits into the code. Jia et al. worked out the layout ({{Dissecting the NVIDIA Volta GPU Architecture via Microbenchmarking, section 2.1|https://arxiv.org/abs/1804.06826}}, 2018) independent reverse engineering, not documented by NVIDIA: 21 bits, from the top, of reuse flags (4), a wait mask (6), a read barrier (3), a write barrier (3), a yield bit (1) and a stall count (4).

Bits 127 down to 105 of the instruction word. RB and WB: read and write barrier (scoreboard) indices; Y: yield.

  • Stall count (0 to 15): cycles before this warp's next instruction may issue. Fixed-latency arithmetic is spaced by stall counts alone.
  • Write barrier: an instruction of variable latency (a global or shared load, a shuffle, MUFU.EX2) gets one of six scoreboards (SB0 to SB5; 7 means none), released when its result arrives. Wait mask: an instruction that needs the result waits on that scoreboard's bit. Read barrier: the same for "do not overwrite this register until the store has read it". Yield: set, prefer to keep issuing from this warp; clear, prefer to switch.

Step through a whole kernel: each instruction issues after its stall count, or first waits for the scoreboards in its mask. The six boxes are the scoreboards, with the register each guards and the instruction that set it compiled here, decoded with Jia et al.'s layout. Try: in the softmax, step from the first LDG.E (it sets a scoreboard) to the FMNMX that waits for it; in the wgmma tile, watch HGMMA and the WARPGROUP instructions.

"Issue cycles" adds the stall counts so far: the time one warp would take if no scoreboard ever made it wait and the scheduler never switched warps. A lower bound from the encoding, not a measurement.

Checked here, on real code
If the decoding is right, every register written by an instruction that sets a scoreboard must be waited for before anything reads it. src/code/sass_decode.py decodes every instruction of six kernels compiled for sm_80, sm_90a, sm_100a and sm_120 and checks exactly that: . As a control, reading the 21 bits one or two positions off finds violations. So the 2018 Volta layout still describes ptxas's output for Ampere, Hopper and both Blackwells derived.

This is what Nsight Compute's stall reasons name: "long scoreboard" is a wait on a scoreboard set by a memory operation through L1 (global, local, texture), "short scoreboard" one set by shared memory or a special function ({{Nsight Compute profiling guide, warp stall reasons|https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html}}). Reading the bits shows, without a profiler, which loads the compiler expects you to wait on and how far apart it managed to put them.
