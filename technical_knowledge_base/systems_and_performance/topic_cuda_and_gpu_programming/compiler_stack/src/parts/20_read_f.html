6. NVRTC and inline PTX: compiling at run time, naming one instruction

Sometimes a kernel does not exist until the program runs: its shapes, data types or operation are only known then. NVRTC "accepts CUDA C++ source code in character string form and creates handles that can be used to obtain the GPU executable code", with no nvcc installed ({{NVRTC 13.4 documentation|https://docs.nvidia.com/cuda/nvrtc/index.html}}) documented. Ask for --gpu-architecture=sm_90a and you get a cubin, for compute_90a PTX for the driver to finish; you load either with cuModuleLoadData or cuLibraryLoadData and launch (that part needs a GPU; not run here). PyTorch's jiterator compiles your elementwise expression through it ({{jit_utils.cpp|https://github.com/pytorch/pytorch/blob/v2.14.0/aten/src/ATen/native/cuda/jit_utils.cpp}}); CuPy's RawKernel uses it by default and caches under $HOME/.cupy/kernel_cache/ ({{CuPy RawKernel|https://docs.cupy.dev/en/stable/reference/generated/cupy.RawKernel.html}}). Triton does not: it writes PTX itself and runs the ptxas it ships.

Inline PTX


asm("instruction %0, %1;" : "=r"(out) : "r"(in)); puts one PTX instruction into CUDA C++. The constraint letter gives the register type (h .u16, r .u32, l .u64, q .u128, f .f32, d .f64; n an immediate; "=" an output); asm volatile stops the compiler deleting or moving it, a "memory" clobber stops it moving memory accesses across it ({{Inline PTX Assembly in CUDA|https://docs.nvidia.com/cuda/inline-ptx-assembly/index.html}}) documented. It is for instructions C++ has no function for (wgmma and tcgen05, why the parent's Hopper and Blackwell kernels are mostly asm), registers C++ cannot name, and forcing one variant of an instruction. Before and after: four ways to write ex


The same kernel y[i] = exp(x[i]) four ways compiled here, sm_90a; only the arithmetic between the load and the store changes (Fig. 7).


    

  1. expf(x): 8 arithmetic instructions. The accurate library function: range reduction (FFMA.SAT, FFMA.RM, the magic constants), the exponent built separately (SHF), MUFU.EX2 for the fraction, a final multiply.
    2. 

  2. __expf(x): 5. The intrinsic: multiply by log2e, then MUFU.EX2. The FSETP and the two predicated FMULs halve and square around the EX2 for inputs below 2-126, so results stay out of the denormal range; the PTX says ex2.approx.f32 without .ftz.
    3. 

  3. Inline asm ex2.approx.ftz: 2. With .ftz (flush denormals to zero) only the multiply and MUFU.EX2 are left.
    4. 

  4. expf(x) with -use_fast_math: 2. The compiler flag rewrites expf to the fast form and adds .ftz to the arithmetic: the same two instructions as the inline PTX, from unchanged source.
    5. 



The hardware has one fast exponential, MUFU.EX2 (2x on the special function unit). expf wraps it in a range reduction accurate to 2 ulp (units in the last place); __expf multiplies by log2e and calls it, with three extra instructions that keep tiny results out of the denormal range, and an error of 2 + floor(|1.173 x|) ulp ({{CUDA Programming Guide, mathematical functions|https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/mathematical-functions.html}}) documented; inline ex2.approx.ftz drops even those; -use_fast_math turns every expf in the file into the short form. FlashAttention-style kernels use the fast form and fold log2e into the softmax scale, so the multiply disappears too.
