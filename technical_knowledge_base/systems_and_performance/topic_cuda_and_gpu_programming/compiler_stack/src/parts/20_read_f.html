7. Other roads to PTX: LLVM, MLIR, Triton, CUDA Tile IR

nvcc is not the only program that writes PTX. Since PTX is text with a published specification, any compiler can target it and let ptxas (or the driver) do the rest. Most do it through LLVM, the open compiler framework whose NVPTX back end turns LLVM IR into PTX ({{LLVM, User Guide for NVPTX|https://llvm.org/docs/NVPTXUsage.html}}): clang compiles CUDA C++ with it ({{Compiling CUDA with clang|https://llvm.org/docs/CompileCudaWithLLVM.html}}), Rust has an nvptx64-nvidia-cuda target built on it ({{rustc platform support|https://doc.rust-lang.org/rustc/platform-support/nvptx64-nvidia-cuda.html}}), and Triton uses it. NVIDIA's own cicc is also LLVM-based but closed; you can tell the two apart from the first line of the PTX:

cicc (nvcc), CUDA 13.4
Triton 3.8.0 (LLVM NVPTX)


MLIR is LLVM's framework for building compilers out of dialects, small intermediate languages each at its own level of abstraction, lowered one into the next ({{mlir.llvm.org|https://mlir.llvm.org/}}). The newer GPU languages are built on it, and differ in which level you write at:

CUDA Tile IR is the newest road, so here it is, run end to end.


CUDA Tile IR, compiled here without a GPU


NVIDIA describes Tile IR as "a portable, low-level tile virtual machine and instruction set that models the GPU as a tile-based processor" ({{CUDA Tile IR documentation|https://docs.nvidia.com/cuda/tile-ir/latest/}}); the open repository calls it "an MLIR-based intermediate representation", released with CUDA 13.1 ({{NVIDIA/cuda-tile|https://github.com/NVIDIA/cuda-tile}}) documented. It plays the role PTX plays for threads: a portable form that a back-end assembler, tileiras, turns into SASS. With cuTile Python  (the pip package cuda-tile) a vector-add kernel was exported to Tile IR bytecode and to cubins for four targets inside the CUDA 13.4.2 image compiled here:


# cuTile: one block of the grid adds one tile of 1024 numbers; no thread index anywhere
@ct.kernel
def vector_add(a, b, out):
    i = ct.bid(0)
    x = ct.load(a, index=(i,), shape=(TILE,))
    y = ct.load(b, index=(i,), shape=(TILE,))
    ct.store(out, index=(i,), tile=x + y)


The Tile IR it became (-byte bytecode, printed by tileirdisasm)




The same 703-byte file became four different machine codes, with no thread, warp or layout in the source: tileiras decided how many threads, how each one walks the tile and how wide each load is. That is the same promise Triton makes one level up, and the reason NVIDIA and the Triton project are also connecting the two (an incubator back end that sends Triton through Tile IR, {{triton-lang/Triton-to-tile-IR|https://github.com/triton-lang/Triton-to-tile-IR}}; not part of Triton 3.8.0, per this topic's shared facts). Running these cubins needs a driver of r580 or later, per cuTile's README; not run here.
