3. SASS: reading the machine code

ptxas turns PTX into SASS, the instruction set one GPU generation actually executes. NVIDIA does not publish its encoding; it does publish the list of opcodes with one-line meanings ({{CUDA Binary Utilities, instruction set reference|https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html#instruction-set-reference}}), and its tools print SASS: cuobjdump -sass for a binary, nvdisasm for a cubin with more options. The parent page's {{Compiler explorer|n:3c65c17b0d0d81c39f34d5e070d783c1}} tab lines SASS up against the source; this section teaches the grammar of one line, then the part nobody prints: the scheduling bits inside each instruction.

Anatomy of one line

Pick a real instruction from the softmax kernel on sm_90a compiled here, then click any part of it.

You seeIt means
R0 to R254, RZPer-thread 32-bit registers; RZ always reads zero. R6.64 is the pair R6, R7 holding a 64-bit address.
UR4, ULDC, S2URUniform registers: one value shared by the whole warp, computed once by a separate uniform datapath. The compiler moves anything every thread would compute identically (block index, kernel arguments, base addresses) into them.
P0 to P6, PT, @!P1Predicate registers (one bit per thread); PT is always true. @!P1 STS ... runs the store only in threads where P1 is false: this is how divergence looks in SASS.
c[0x0][0x220]Constant bank 0, which holds the kernel's arguments. The softmax's third argument (ncols) is at 0x170 on sm_80, 0x220 on sm_90a and 0x390 on sm_100a and sm_120: the layout changes between generations, one more reason SASS is not portable.
desc[UR6][R6.64]A global address with a memory descriptor held in a uniform register; it appears in our sm_90a, sm_100a and sm_120 code and not in the sm_80 code, which writes [R4.64].
SR_TID.X, SR_CTAID.XSpecial registers, read with S2R (into a register) or S2UR (into a uniform register).
.reuseA hint to keep this source operand in the operand reuse cache for the next instruction (one of the control bits below).

The bits nobody prints: stall counts and scoreboards

Since Volta, every SASS instruction is one 128-bit word, and part of that word is not the instruction at all: it is control information the compiler writes to tell the warp scheduler how to run it. A GPU issues each warp's instructions in order and, unlike a CPU core, does not work out register dependencies by itself; ptxas, which knows each instruction's latency, writes the waits into the code ahead of time. Jia et al. worked out the layout by disassembling every instruction ({{Dissecting the NVIDIA Volta GPU Architecture via Microbenchmarking, section 2.1|https://arxiv.org/abs/1804.06826}}, 2018) independent reverse engineering, not documented by NVIDIA: 21 bits, from the top, of reuse flags (4), a wait-barrier mask (6), a read barrier (3), a write barrier (3), a yield bit (1) and a stall count (4).

Bits 127 down to 105 of the instruction word. RB and WB: read and write barrier (scoreboard) indices; Y: yield.

  • Stall count (0 to 15): cycles the scheduler waits before issuing this warp's next instruction. Fixed-latency arithmetic is spaced by stall counts alone.
  • Write barrier: an instruction whose latency is not fixed (a global load, a shared load, a shuffle, a special function like MUFU.EX2) is given one of six scoreboards (SB0 to SB5; 7 means none) that is released when its result arrives.
  • Wait mask: an instruction that needs that result carries the scoreboard's bit in its mask and is not issued until the scoreboard is released. Read barrier: the same idea for "do not overwrite this register until the store has read it".
  • Yield: when set, the scheduler prefers to keep issuing from this warp; when clear, it prefers to switch.
Checked here, on real code
If the decoding is right, every register written by an instruction that sets a scoreboard must be waited for before anything reads it. A script (src/code/sass_decode.py) decodes every instruction of six kernels compiled for sm_80, sm_90a, sm_100a and sm_120 and checks exactly that: . As a control, reading the 21 bits one or two positions off finds violations. So the 2018 Volta layout still describes ptxas's output for Ampere, Hopper and both Blackwells derived.

This is what Nsight Compute's stall reasons refer to: "long scoreboard" is a wait on a scoreboard set by a memory operation through L1 (global, local, texture), "short scoreboard" one set by shared memory or a special function ({{Nsight Compute profiling guide, warp stall reasons|https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html}}). Reading the bits tells you, without a profiler, which loads the compiler expects you to wait on and how far apart it managed to put them. The {{SASS, decoded|#t-sass}} tab steps through whole kernels with the six scoreboards drawn.
