3. PTX: an assembly language for a GPU that does not exist

PTX (Parallel Thread Execution) is what cicc, LLVM's NVPTX back end and Triton write, and what ptxas reads. NVIDIA calls it "a low-level parallel thread execution virtual machine and instruction set architecture", whose first goal is to "provide a stable ISA that spans multiple GPU generations" ({{PTX ISA 9.4, introduction|https://docs.nvidia.com/cuda/parallel-thread-execution/index.html}}) documented. No chip executes it: it describes an idealised GPU with as many registers as you like, and each generation's assembler maps it onto real hardware. That is why PTX is the portable form of a kernel: H100 SASS cannot run on a B200, but PTX can be compiled for either.

Below is the whole PTX cicc wrote for the row softmax (sm_90a, -O3) compiled here. Pick a feature to light up the lines that carry it.

  • Every instruction names its type (add.f32, mul.wide.s32); there is no implicit conversion, cvt does it.
  • Every memory access names its state space: .global (device memory), .shared (the block's on-chip scratchpad), .local (per-thread memory in device memory: where spills go), .const, .param (kernel arguments). In SASS they become LDG, LDS, LDL, LDC.
  • Registers are virtual and almost single-assignment. This kernel declares of them; the H100 code uses 18 real ones (cuobjdump -res-usage: ). ptxas decides which values share a register.
  • Control flow is predicates plus branches: setp.ge.s32 %p1, ... writes a 1-bit predicate, @%p1 bra $L__BB0_2 branches on it; any instruction can be predicated.
  • Special registers: %tid.x is threadIdx.x, %ctaid.x is blockIdx.x (a CTA, cooperative thread array, is PTX's word for a block), %ntid.x is blockDim.x.

PTX is tied to the toolkit that wrote it


The first lines of every PTX file give the language version: CUDA 13.4 writes .version 9.4, and an assembler accepts only versions it knows. Triton 3.8.0 ships its own ptxas from CUDA 12.9 (recorded in the image), so feeding it the PTX above fails run here:




Edit the first line to .version 8.8 and the old ptxas accepts the file, because this kernel uses nothing newer; Triton writes .version 8.8 itself (). This one error is the whole story of driver JIT compatibility: the driver contains its own ptxas and can compile only PTX whose version it knows. "Applications that compile device code to PTX will not work on older drivers" ({{CUDA minor version compatibility|https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html}}) documented; the runtime reports cudaErrorUnsupportedPtxVersion, whose comment in the CUDA 13.4.2 headers reads "The most common reason for this, is the PTX was generated by a compiler newer than what is supported by the CUDA driver and PTX JIT compiler."








PTX is not what runs: what each compiler decides on the way down


Fig. 4 follows the row softmax down the nvcc road: each plate is one form of the kernel, lit with what the compiler that wrote it decided compiled here. The cubes are registers (one cube each), the column is the SASS instruction slots cuobjdump -sass lists, including the few padding NOPs at the end.


    

  1. The source: one kernel, 32 lines. Three passes over a row (maximum, sum of exponentials, normalise), each reduction a warp shuffle plus a shared-memory step. Fusion was decided here, by hand: everything is one kernel.
    2. 

  2. cicc writes PTX: 245 lines, 230 virtual registers. 31 predicates (%p), 74 floats (%f), 89 32-bit (%r) and 36 64-bit (%rd) values, almost each written once. cicc decided inlining (the warp reductions are gone as functions), the loops (kept rolled by #pragma unroll 1, the shuffles unrolled) and which pointer points into which memory; it did not decide registers.
    3. 

  3. ptxas -O0: 792 instruction slots, 31 registers. At -O0 ptxas assembles the PTX nearly as written.
    4. 

  4. ptxas -O1 to -O3: 232 slots, 18 registers. From -O1 up (the three levels give the same counts here) it removes redundant work, allocates registers tightly and schedules: less than a third of the instructions, 18 real registers for 230 virtual ones (cuobjdump -res-usage: 18 registers, 1056 bytes of shared memory, no local memory, so no spills).
    5. 

  5. Four generations, four machine codes. The same source compiled for sm_80, sm_90a, sm_100a and sm_120 (each from its own PTX): 224, 232, 240 and 224 instruction slots, 19, 18, 18 and 17 registers, and the third argument (ncols) read from c[0x0][0x170], 0x220, 0x390 and 0x390. Same PTX semantics, different SASS: one more reason SASS is not portable.
    6. 



So a PTX listing tells you what the front end asked for (which loads, which shuffles, whether a loop was unrolled), and only SASS tells you what the GPU does: judge registers, spills, vector widths and instruction counts from SASS and the ptxas -v report, never from PTX.
