In one screen: two roads to the same machine code

An NVIDIA GPU executes only one thing: SASS, the machine code of one GPU generation. Whatever you write, CUDA C++ or a line of PyTorch, reaches the GPU after a chain of compilers has turned it into SASS. This page follows that chain on the two roads an ML engineer uses: a hand-written CUDA kernel through nvcc, and PyTorch code through torch.compile. The running examples are the parent topic's: the row softmax kernel of its Compiler explorer tab, and softmax(x * 0.125) @ w, the attention-shaped graph the parent page follows from PyTorch to the instructions.

The two roads meet at the same assembler: Triton writes PTX through LLVM and hands it to ptxas, exactly as nvcc does. 1. nvcc is a driver, not a compiler

nvcc runs a sequence of other programs. A .cu file holds two programs at once: host code for the CPU and device code for the GPU. nvcc splits them, compiles the device code once per target you asked for, packs the results into a fat binary (a container holding several GPU code images), embeds that container in the host object as data, and hands the host code to your normal C++ compiler. nvcc --dryrun prints every command without running it. What each program does:


    

  • gcc -E (your host compiler as preprocessor) expands includes and macros. It runs once for the host side and once per device target, each time with a different __CUDA_ARCH__, which is how one source file can contain code for several generations behind #if __CUDA_ARCH__ >= 900. The preprocessed device file is 1.4 MB for a 32-line kernel: almost all of it is the CUDA headers.
    • 

  • cudafe++ is NVIDIA's C++ front end. It parses CUDA C++, separates host from device, and replaces each kernel<<<grid, block>>>(args) with a call to a generated launch stub, a host function that packs the arguments and calls the CUDA runtime.
    • 

  • cicc is the device compiler: it parses the preprocessed device source with its own copy of the front end, lowers it to NVVM IR (NVIDIA's dialect of LLVM IR; NVVM IR specification), runs an optimiser built on LLVM (inlining, unrolling, constant folding, deciding which pointer points into which memory) and prints PTX. It runs once per virtual target.
    • 

  • ptxas is the assembler that is really a second optimising compiler: it allocates real registers, schedules instructions, and emits SASS inside a cubin (an ELF file for the GPU). With -arch=sm_90a, nvcc also runs ptxas once on the generic compute_90 PTX just to check it (step 5); no file comes out.
    • 

  • fatbinary packs the images; the host compiler then builds the host object with the fat binary inside it. With -rdc=true (separate compilation, device functions called across files) a device link step, nvlink, joins cubins first; that is the one program this build did not need.
    • 



The toggle shows the answer to the question above: -arch=sm_90a puts three images in the object, the sm_90a machine code and two PTX copies (generic compute_90 and Hopper-specific compute_90a), where -arch=sm_90 puts two. Section 4 explains why the extra copy exists and the trap it sets.






2. PTX: an assembly language for a GPU that does not exist


PTX (Parallel Thread Execution) is the language cicc writes and ptxas reads. NVIDIA's manual calls it "a low-level parallel thread execution virtual machine and instruction set architecture", and its first stated goal is to "provide a stable ISA that spans multiple GPU generations" (PTX ISA 9.4, introduction) documented. Virtual is the key word: no chip executes PTX. It describes an idealised GPU with as many registers as you like, and every real GPU's assembler maps it onto real hardware. That is what makes PTX the portable form of a kernel: SASS for an H100 cannot run on a B200, but PTX can be compiled for either.

Five things to know when reading PTX:


    

  • Every instruction names its type: add.f32, mul.wide.s32, ld.global.f32. There is no implicit conversion; cvt does it.
    • 

  • Every memory access names its state space: .global (device memory), .shared (the block's on-chip scratchpad), .local (per-thread memory that lives in device memory: where spills go), .const, .param (kernel arguments). In SASS the same spaces become LDG, LDS, LDL, LDC.
    • 

  • Registers are virtual and almost single-assignment. This kernel declares  virtual registers; the H100 code uses 18 real ones (cuobjdump -res-usage: ). ptxas decides which values share a register.
    • 

  • Control flow is predicates plus branches: setp.ge.s32 %p1, ... writes a 1-bit predicate; @%p1 bra $L__BB0_2 branches on it. Any instruction can be predicated.
    • 

  • Special registers give a thread its coordinates: %tid.x is threadIdx.x, %ctaid.x is blockIdx.x (a CTA, cooperative thread array, is PTX's word for a thread block), %ntid.x is blockDim.x.
    • 



Versions: PTX is tied to the toolkit that wrote it


The first lines of every PTX file say which version of the language it uses and which target it is for. CUDA 13.4 writes .version 9.4. An assembler only accepts versions it knows. PTX is not what runs: ptxas does a great deal


The same PTX file assembled at ptxas's four optimisation levels compiled here, sm_90a:




Instructions are the slots cuobjdump -sass lists, including the few padding NOPs at the end of the kernel.


At -O0 ptxas assembles the PTX nearly as written; from -O1 up it removes redundant work, allocates registers tightly and schedules. The SASS at -O3 has less than a third of the instructions of -O0. So a PTX listing tells you what the front end asked for (which loads, which shuffles, whether a loop was unrolled), and only SASS tells you what the GPU does. Judge registers, spills, vector widths and instruction counts from SASS and the ptxas -v report, never from PTX.






3. SASS: reading the machine code


ptxas turns PTX into SASS, the instruction set one GPU generation actually executes. NVIDIA does not publish its encoding; it does publish the list of opcodes with one-line meanings (CUDA Binary Utilities, instruction set reference), and its tools print SASS: cuobjdump -sass for a binary, nvdisasm for a cubin with more options. The parent page's Compiler explorer tab lines SASS up against the source; this section teaches the grammar of one line, then the part nobody prints: the scheduling bits inside each instruction.

The bits nobody prints: stall counts and scoreboards


Since Volta, every SASS instruction is one 128-bit word, and part of that word is not the instruction at all: it is control information the compiler writes to tell the warp scheduler how to run it. A GPU issues each warp's instructions in order and, unlike a CPU core, does not work out register dependencies by itself; ptxas, which knows each instruction's latency, writes the waits into the code ahead of time. Jia et al. worked out the layout by disassembling every instruction (Dissecting the NVIDIA Volta GPU Architecture via Microbenchmarking, section 2.1, 2018) independent reverse engineering, not documented by NVIDIA: 21 bits, from the top, of reuse flags (4), a wait-barrier mask (6), a read barrier (3), a write barrier (3), a yield bit (1) and a stall count (4).




Bits 127 down to 105 of the instruction word. RB and WB: read and write barrier (scoreboard) indices; Y: yield.


    

  • Stall count (0 to 15): cycles the scheduler waits before issuing this warp's next instruction. Fixed-latency arithmetic is spaced by stall counts alone.
    • 

  • Write barrier: an instruction whose latency is not fixed (a global load, a shared load, a shuffle, a special function like MUFU.EX2) is given one of six scoreboards (SB0 to SB5; 7 means none) that is released when its result arrives.
    • 

  • Wait mask: an instruction that needs that result carries the scoreboard's bit in its mask and is not issued until the scoreboard is released. Read barrier: the same idea for "do not overwrite this register until the store has read it".
    • 

  • Yield: when set, the scheduler prefers to keep issuing from this warp; when clear, it prefers to switch.
    • 



Checked here, on real code
If the decoding is right, every register written by an instruction that sets a scoreboard must be waited for before anything reads it. This is what Nsight Compute's stall reasons refer to: "long scoreboard" is a wait on a scoreboard set by a memory operation through L1 (global, local, texture), "short scoreboard" one set by shared memory or a special function (Nsight Compute profiling guide, warp stall reasons). Reading the bits tells you, without a profiler, which loads the compiler expects you to wait on and how far apart it managed to put them. 4. Which binary runs on which GPU


Every NVIDIA GPU has a compute capability (CC), a version number for its instruction set and limits: 8.0 for the A100, 8.9 for the L4 and RTX 4090, 9.0 for the H100 and H200, 10.0 for the B200 and GB200, 10.3 for the B300 and GB300, 12.0 for the RTX 5090 (NVIDIA, CUDA GPU compute capability) documented. Compiler targets come in two kinds named after it: compute_90 is a virtual architecture (PTX written for CC 9.0's feature set) and sm_90 a real architecture (SASS for CC 9.0 chips). CUDA 13.4's nvcc knows these real targets recorded here: . Nothing older than Turing (7.5) is left, and with no -arch at all nvcc builds for sm_75 ().


What each flag puts in the binary


-gencode arch=compute_XY,code=... is the explicit form: arch chooses the PTX to compile from, code lists what to embed (sm_XY for SASS, compute_XY for the PTX itself). -arch=sm_XY is shorthand; the manual: "nvcc --gpu-architecture=sm_100 is equivalent to nvcc --gpu-architecture=compute_100 --gpu-code=sm_100,compute_100" (nvcc manual). Three kinds of target: plain, a and f


Hopper introduced instructions that NVIDIA does not promise to keep in later chips (wgmma, setmaxnreg); Blackwell added more (tcgen05). To use them you compile for an architecture-specific target with an a suffix, and NVIDIA's rule is strict: such code "only runs on GPUs of that specific CC and no others". CUDA 12.9 added family-specific targets with an f suffix, for features "supported by devices of more than one minor compute capability" in one major version: sm_100f code runs on CC 10.0 and 10.3 and on any later 10.x (NVIDIA technical blog, May 1 2025) documented. Libraries such as CUTLASS guard this way.


The rules the driver follows


    

  • SASS runs within one major version on equal or newer minors: "a cubin compiled for compute capability 8.6 (sm_86) runs on GPUs with CC 8.6 or 8.9, but not on CC 8.0", and GPUs "are not binary compatible between major compute capability versions" (CUDA Programming Guide 1.3). An a cubin runs on its exact CC only; an f cubin on its family.
    • 

  • PTX "can be JIT compiled at application runtime for any compute capability equal or higher to the compute capability of the PTX code" (same page). The driver does it when no compatible SASS exists, and "automatically caches a copy of the generated binary code".
    • 

  • The driver must know the PTX's version (section 2). CUDA 13.x applications need driver 580 or newer; a 13.0 driver runs SASS built by CUDA 13.4 (minor version compatibility) but cannot JIT its PTX (CUDA compatibility guide).
    • 

  • If nothing fits, the launch fails with cudaErrorNoKernelImageForDevice: "no kernel image is available for execution on the device".
    •

5. NVRTC: compiling while the program runs


Sometimes the kernel does not exist until the program runs: its shapes, data types or the operation itself are only known then. NVRTC is NVIDIA's library for that case: "It accepts CUDA C++ source code in character string form and creates handles that can be used to obtain the GPU executable code", without spawning nvcc or needing it installed (NVRTC 13.4 documentation) documented. Ask for --gpu-architecture=sm_90a and you get a cubin; ask for compute_90a and you get PTX for the driver to finish. You then load the result with the driver API (cuModuleLoadData or cuLibraryLoadData) and launch it; that last part needs a GPU and is not run here.


Who uses it: PyTorch's jiterator (torch.cuda.jiterator) inlines your elementwise expression into a kernel template and compiles it through NVRTC (aten/src/ATen/native/cuda/jit_utils.cpp); CuPy's RawKernel uses NVRTC by default and caches binaries under $HOME/.cupy/kernel_cache/ (CuPy RawKernel). Triton does not: it writes PTX itself and runs the ptxas binary it ships.

6. Inline PTX: naming one exact instruction from C++


asm("instruction %0, %1;" : "=r"(out) : "r"(in)); puts one PTX instruction into CUDA C++. The constraint letters give the operand's register type: h .u16, r .u32, l .u64, q .u128, f .f32, d .f64; n is an immediate integer and "=" marks an output. asm volatile stops the compiler deleting or moving it, and a "memory" clobber stops it moving memory accesses across it (Inline PTX Assembly in CUDA) documented. You need it for three things: instructions CUDA C++ has no function for (wgmma and tcgen05, which is why the parent page's Hopper and Blackwell kernels are mostly asm), registers it cannot name, and forcing one variant of an instruction. The hardware has one fast exponential, MUFU.EX2 (2x on the special function unit). expf wraps it in a careful range reduction so the result is accurate to 2 ulp (units in the last place); __expf multiplies by log2e and calls it, with three extra instructions that keep tiny results out of the denormal range, and its error grows with the input: 2 + floor(|1.173 x|) ulp (CUDA Programming Guide, mathematical functions) documented; inline ex2.approx.ftz drops even those; -use_fast_math turns every expf in the file into the shortest form. FlashAttention-style kernels use the fast form on purpose and fold log2e into the softmax scale, so the multiply disappears too.






7. Other roads to PTX: LLVM, MLIR, Triton, CUDA Tile IR


nvcc is not the only program that writes PTX. Since PTX is text with a published specification, any compiler can target it and let ptxas (or the driver) do the rest. Most do it through LLVM, the open compiler framework whose NVPTX back end turns LLVM IR into PTX (LLVM, User Guide for NVPTX): clang compiles CUDA C++ with it (Compiling CUDA with clang), Rust has an nvptx64-nvidia-cuda target built on it (rustc platform support), and Triton uses it. NVIDIA's own cicc is also LLVM-based but closed; you can tell the two apart from the first line of the PTX:

NVIDIA describes Tile IR as "a portable, low-level tile virtual machine and instruction set that models the GPU as a tile-based processor" (CUDA Tile IR documentation); the open repository calls it "an MLIR-based intermediate representation", released with CUDA 13.1 (NVIDIA/cuda-tile) documented. It plays the role PTX plays for threads: a portable form that a back-end assembler, tileiras, turns into SASS. With cuTile Python  (the pip package cuda-tile) a vector-add kernel was exported to Tile IR bytecode and to cubins for four targets inside the CUDA 13.4.2 image compiled here:


# cuTile: one block of the grid adds one tile of 1024 numbers; no thread index anywhere
@ct.kernel
def vector_add(a, b, out):
    i = ct.bid(0)
    x = ct.load(a, index=(i,), shape=(TILE,))
    y = ct.load(b, index=(i,), shape=(TILE,))
    ct.store(out, index=(i,), tile=x + y)

8. torch.compile, part 1: Dynamo captures a graph


torch.compile(fn) returns a function that, when called, does not simply run fn. CPython lets a library replace the function that evaluates every Python frame (PEP 523, "the frame evaluation API"); TorchDynamo installs itself there, so it sees each call to fn before CPython runs it (Ansel et al., PyTorch 2, ASPLOS 2024, section 3) documented. It then reads the function's bytecode (the instructions CPython would execute) symbolically: tensor operations are recorded into an FX graph, a list of PyTorch operations with their inputs; everything else (Python arithmetic on ints, loops over lists, attribute lookups) is executed at trace time and its result baked into the graph. AOTAutograd: the backward pass, decided ahead of time


Dynamo captures only the forward computation. For training, AOTAutograd runs PyTorch's autograd on fake tensors (shapes and dtypes, no data) to record one joint forward-and-backward graph, then "uses a min-cut algorithm to split this joint graph into separate forward and backward graphs in a way that optimizes for memory usage", recomputing activations that are cheap to recompute instead of saving them (Ansel et al., section 3.9). Most of a cold compile is Python (Dynamo, AOTAutograd, Inductor) plus the C++ or Triton compiler; a warm start skips the code generation and compiler by finding the result in Inductor's on-disk caches (TORCHINDUCTOR_CACHE_DIR; the FX graph cache is on by default) and Triton's. 10. Mistakes, with the evidence for each


"no kernel image is available for execution on the device"
The binary has no SASS this GPU can run and no PTX the driver could compile: for example -gencode arch=compute_90,code=sm_90 (SASS only) on a B200, or a SASS-only release wheel on a GPU of a newer major version. Check with cuobjdump -lelf -lptx on the binary or library (section 4 lists what each flag embeds); fix by adding the GPU's target or a PTX image (code=[sm_90,compute_90]). The Will it run? tab reproduces the rule.


"the provided PTX was compiled with an unsupported toolchain"
cudaErrorUnsupportedPtxVersion: the binary carries only PTX for this GPU and that PTX is newer than the driver's JIT compiler (section 2 shows the same failure offline: ptxas 12.9 refusing .version 9.4). Update the driver, or ship SASS for the GPUs you run on so that no JIT is needed.


The first step is slow on every run, in containers only
The binary has only PTX for this GPU, so the driver JIT-compiles every kernel at first use, and the container starts with an empty ~/.nv/ComputeCache each time. Point CUDA_CACHE_PATH at a persistent volume, or build SASS for the GPU. For torch.compile the same applies one level up: keep TORCHINDUCTOR_CACHE_DIR and Triton's cache, or ship them with torch.compiler.save_cache_artifacts().


An H100-tuned binary on a B200 runs, but slowly
An sm_90a cubin runs only on CC 9.0, so on a B200 the driver JIT-compiles the generic compute_90 PTX that -arch=sm_90a also embedded, which by construction contains no wgmma (section 4). The kernel works with the slower generic path. Build sm_100a or sm_100f for Blackwell.


nvcc -arch=sm_90a fails on a kernel with wgmma
The generic compute_90 pass sees Hopper-only PTX. Use -gencode arch=compute_90a,code=sm_90a or guard with __CUDA_ARCH_FEAT_SM90_ALL; both compiled here (section 4).


Judging a kernel from its PTX
ptxas removes two thirds of the instructions and decides the register count (section 2: -O0 against -O3). Registers, spills, vector widths and tensor-core instructions are facts about SASS: read -Xptxas -v and cuobjdump -sass.


-use_fast_math as a speed switch
It changes every expf, division and square root in the file and flushes denormals to zero (section 6). Use the intrinsic (__expf) or inline ex2.approx exactly where the accuracy loss is acceptable, and test against a reference.


A print, a .item() or an if on a tensor inside a compiled model
Each is a graph break: two smaller graphs, no fusion across them, Python in between on every call (section 8). Find them with torch._dynamo.explain or TORCH_LOGS=graph_breaks; keep them out with fullgraph=True.


Training slows down at the end of every epoch, or every few steps
Recompilation: the last batch is shorter, sequence lengths vary, or a Python number (learning rate, step) is passed as an argument and guarded by value (section 8). TORCH_LOGS=recompiles names the failing guard. Pass changing scalars as tensors, mark dimensions dynamic (torch._dynamo.mark_dynamic), or pad to a few bucket sizes. Past recompile_limit recompilations, Dynamo stops compiling that function and runs it eagerly.


Timing torch.compile with the compile inside the measurement
The first call compiled for 3 to 4 seconds here, against about a millisecond afterwards (section 9). Warm up first, with every shape you will time; the profiling page covers honest timing.







11. Interview questions, with short answers


What is the difference between PTX and SASS, and why does NVIDIA have both?
PTX is a virtual, documented, stable instruction set for an idealised GPU with unlimited registers; SASS is the real, undocumented-encoding machine code of one generation. PTX lets old binaries run on new GPUs (the driver compiles it) and gives other compilers a stable target; SASS is what runs, so performance work reads SASS.


What does -arch=sm_90 put in the binary? And -arch=sm_90a?
sm_90 SASS plus compute_90 PTX. With sm_90a: sm_90a SASS plus two PTX images, compute_90 and compute_90a (the manual's rule, confirmed by cuobjdump here).


A cubin built for sm_80: which GPUs run it?
CC 8.0 and any 8.x with a higher minor (8.6, 8.7, 8.9); not 9.0 or later, since binaries are not compatible across major versions. With compute_80 PTX alongside, newer GPUs JIT-compile it.


What are the a and f suffixes for?
Instructions NVIDIA does not promise to keep: a code (wgmma on sm_90a, tcgen05 on sm_100a) runs only on that exact compute capability; f (CUDA 12.9+) runs on the whole major family at equal or higher minors, so one sm_100f build serves B200 and B300.


What is in the 128 bits of a Volta-or-later SASS instruction besides the instruction?
About 21 bits of scheduling control written by ptxas: a stall count, a yield bit, write and read scoreboard indices, a mask of scoreboards to wait on, and operand reuse flags (Jia et al.; checked here on four generations).


When would you use NVRTC instead of nvcc?
When the kernel is only known at run time (generated code, shapes or types as compile-time constants, user-defined operations), or when you cannot ship nvcc. It costs tens of milliseconds per compile, so cache the results.


Walk through what happens on the first call of a torch.compiled training step.
Dynamo intercepts the frame, traces bytecode into an FX graph and writes guards; AOTAutograd traces the joint forward and backward on fake tensors and partitions it (min-cut, recomputing cheap activations); Inductor lowers each graph, fuses, and writes Triton kernels plus a Python wrapper, with matmuls going to cuBLAS by default; Triton compiles each kernel to PTX and ptxas to SASS; everything is cached. Later calls only check guards.


What is a graph break and how do you find them?
A place where Dynamo cannot trace (print, .item() by default, data-dependent control flow, unsupported libraries): it compiles the graph so far, runs that part in Python, and resumes in a generated function. Find them with torch._dynamo.explain, TORCH_LOGS=graph_breaks or tlparse; forbid them with fullgraph=True.


Why might a compiled model use less activation memory than eager?
AOTAutograd's min-cut partitioner chooses what to save for backward and recomputes cheap values (here, the normalised activation of an RMSNorm) instead of saving them; fusion also removes intermediate tensors.


What do reduce-overhead and max-autotune change?
reduce-overhead turns on CUDA graphs (one replay call instead of many launches; needs static shapes and keeps a memory pool). max-autotune also turns on CUDA graphs plus autotuned Triton matmul templates and coordinate-descent tuning, at a much longer compile.
