2. Scan: running totals

The problem. An inclusive scan (prefix sum) turns x0, x1, x2, ... into x0, x0+x1, x0+x1+x2, ...; an exclusive scan shifts it by one and starts at 0. It looks sequential, every output depends on every earlier input, yet it is everywhere in model code: a mixture-of-experts layer counts how many tokens go to each expert and scans the counts to find where each expert's tokens start in a packed buffer; top-p sampling scans sorted probabilities; packing variable-length sequences scans their lengths into offsets; torch.cumsum is a scan.

Two parallel algorithms (from {{GPU Gems 3, chapter 39|https://developer.nvidia.com/gpugems/gpugems3/part-vi-gpu-computing/chapter-39-parallel-prefix-sum-scan-cuda}}, Harris, Sengupta and Owens):

Hillis and Steele

Step k: every element adds the one 2k places to its left. log2(n) steps, all elements busy, but O(n log n) additions: for n = 224, 386 million adds against 16.8 million for a loop derived, Σk<24(n − 2k).

Blelloch (work-efficient)

An up-sweep builds a tree of partial sums (a reduction), a down-sweep pushes prefixes back down: "approximately 2 × (n − 1) adds and n − 1 swaps", 33.6 million for n = 224 derived, but twice the steps.

Both are animated on the same 16 numbers in the {{Reduce and scan, animated|#t-tree}} tab. On a real GPU neither is used across the whole array. Inside a warp, a scan is five shuffles (__shfl_up_sync; Metal's simd_prefix_exclusive_sum); across a block, warps exchange totals through shared memory; across blocks comes the hard part, because block 7 needs the total of blocks 0 to 6.

Across blocks: three launches, or one pass with a look-back

Reduce, then scan (three launches): (a) each block sums its tile; (b) one block scans the tile sums into offsets; (c) each block scans its tile again and adds its offset. The input is read twice and the output written once: 3 passes over memory, against 2 for a copy. Decoupled look-back ({{Merrill and Garland, NVIDIA, 2016|https://research.nvidia.com/publication/2016-03_single-pass-parallel-prefix-scan-decoupled-look-back}}) does it in one launch: each block publishes its own total as soon as it has it, and its inclusive prefix once it knows it; a block that needs its offset looks back at its predecessors' published values, summing totals until it meets a published prefix. It "requires only ~2n data movement" and its throughput "approaches that of copy operations" published; it is how cub::DeviceScan works. It relies on earlier blocks making progress while later ones wait, a guarantee Metal does not document, so we did not run it here.

Measured on 224 floats measured on Apple M1 Pro GPU:

Hillis and Steele over the whole array, 24 launches each reading and writing everything, takes 18.81 ms; the three-launch scan 1.41 ms, 13.4 times faster and 1.41 times a plain copy (1.00 ms), close to the 3 : 2 ratio of passes that counting bytes predicts. MLX's library mx.cumsum took 7.78 ms on the same input, 5.5 times slower than our 40 lines: libraries are not always at the ceiling, and the copy time tells you when they are not. The kernel code is in the {{Kernel bench (M1)|#t-bench}} tab.

In PyTorch, a one-dimensional torch.cumsum on CUDA calls cub::inclusive_scan, and a separate inclusive_deterministic_scan for floating-point types when deterministic algorithms are requested ({{ScanUtils.cuh|https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/cuda/ScanUtils.cuh}}, read 2026-10-05): the default single-pass scan can add in an order that depends on timing, for the same reason as the atomic sum of section 1.

3. Row normalisation: softmax, LayerNorm, RMSNorm

Softmax, LayerNorm and RMSNorm all do the same thing to each row of a matrix: compute one or two statistics of the row (a reduction), then rewrite every element using them. In a transformer the rows are tokens and a row is a few thousand numbers, so the standard layout is one block per row, the row's elements spread over the block's threads, each thread keeping its share in registers between the statistics and the rewrite, so the row is read from memory once and written once. Arithmetic is a handful of operations per element; the speed is set by bytes.

Softmax: the online trick

The topic root's Kernel lab climbs the softmax ladder in seven measured rungs, from one thread per row (177 ms) to the row held on chip (3.27 ms, the speed of a copy), so it is not repeated here ({{Kernel lab|n:3c65c17b0d0d81c39f34d5e070d783c1}}, section 1). The idea to carry forward is the online softmax ({{Milakov and Gimelshein, 2018|https://arxiv.org/abs/1805.02867}}): keep a running maximum m and a running sum d of ex − m; when a larger value arrives, rescale the sum you have.

m′ = max(m, xi)    d′ = d · em − m′ + exi − m′
merge (ma, da) with (mb, db): m = max(ma, mb),   d = da ema − m + db emb − m

The second line is what makes it a parallel algorithm: any two partial results, from two lanes, two warps or two tiles, combine exactly, in any order. Every reduction on this page that is more than a sum needs such a merge.

LayerNorm: the variance is a numerical trap

LayerNorm subtracts the row's mean μ and divides by its standard deviation σ: y = (x − μ) / √(σ2 + ε) · γ + β. The tempting one-pass formula for the variance, σ2 = E[x2] − E[x]2, subtracts two large, nearly equal numbers when the mean is large compared with the spread, and float32 keeps only about 7 significant digits.

The remaining error of the good methods grows with the mean because the input itself, stored in float32, only carries about 7 digits: at mean 3,000 each value is already rounded to 0.0002.

Welford's algorithm keeps a count n, a mean and M2 (the sum of squared deviations), updating them per value; partial results merge with the pairwise formula of Chan, Golub and LeVeque ({{the parallel algorithm, summarised|https://en.wikipedia.org/wiki/Algorithms_for_calculating_variance#Parallel_algorithm}}), which has exactly the shape of the online-softmax merge:

δ = μb − μa,   n = na + nb,   μ = μa + δ nb/n,   M2 = M2a + M2b + δ2 nanb/n

When the row fits in registers, as here, two passes over registers are just as cheap and simpler; Welford matters when the row is streamed once from memory, as in a long row or a fused kernel that cannot keep it. All three kernels took 1.74 to 1.77 ms on 8,192 rows of 4,096 (154 GB/s counting one read and one write), against 1.87 ms for MLX's mx.fast.layer_norm and 9.87 ms for the same formula as seven separate MLX operations (6.79 ms under mx.compile) measured on Apple M1 Pro GPU.

RMSNorm, fused with the residual add

RMSNorm drops the mean: y = x / √(mean(x2) + ε) · γ. In a pre-norm transformer block it always follows a residual add, h = x + r, and h is needed twice: normalised for the next layer, and raw as the next residual. Separately, the add reads x and r and writes h, and the norm reads h and writes y: 5 passes over the activations. Fused, one kernel reads x and r and writes h and y: 4 passes, so at best 5 : 4 = 1.25 times faster derived. Measured: 4.03 ms for MLX's add then mx.fast.rms_norm (4.09 ms under mx.compile, which did not fuse them), 3.35 ms fused, 1.20 times measured on Apple M1 Pro GPU. Production engines ship exactly this kernel: vLLM declares fused_add_rms_norm(input, residual, weight, epsilon) next to its plain rms_norm ({{csrc/ops.h|https://github.com/vllm-project/vllm/blob/main/csrc/ops.h}}, read 2026-10-05); count passes before writing one, because the best case is set by the byte count before you start.
