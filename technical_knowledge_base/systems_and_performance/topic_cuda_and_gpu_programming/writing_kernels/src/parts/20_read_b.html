2. Reductions: many numbers into one

Sum 225 (33.5 million) floats. On a CPU it is one loop. On a GPU, thousands of threads each do a part and then combine their parts, and combining is where every difficulty lives: threads in different blocks cannot see each other's shared memory or wait for each other inside one kernel launch. The shape of the answer is a tree: in step 1, half the threads each add two numbers; in step 2, a quarter add two partial sums; after log2(256) = 8 steps one thread holds the block's total. Each block writes its total, and a second, tiny launch (or an atomic add) combines the block totals.

Mark Harris's {{Optimizing Parallel Reduction in CUDA|https://developer.download.nvidia.com/assets/cuda/files/reduction.pdf}} (NVIDIA, 2007) is the classic ladder: seven kernels for summing 4M integers on a G80, each fixing one problem, from 2.083 to 62.671 GB/s, 30.04 times faster, and 73 GB/s on 32M elements against the G80's 86.4 GB/s peak published. Its first three rungs differ only in which threads add which elements; play them on one input:

A toy GPU: warps of 4 lanes and 4 shared-memory banks (real: 32 of each), same proportions; arrows run from the value a thread reads to the one it writes. Predict before you step: R1 makes whole warps issue for one working lane (divergence: lanes of one warp taking different branches run one after the other); R2 removes the idle lanes but its worst bank conflict becomes 4-way (lanes hitting the same bank of shared memory wait in turn); R3 fixes both; the warp shuffle needs one barrier instead of four. The two scans are section 3's: Hillis-Steele does 49 additions where Blelloch does 30, in half the steps. Counts checked against src/tree_model.py.

All six on the same input, totals (table)

Additions: useful adds. Active lanes: lane-steps doing work. Idle lanes: lanes of issued warps with nothing to do. Barriers: __syncthreads() after each shared-memory step. Shared-memory transactions: per warp and per access (read source, read destination, write destination), the largest number of distinct addresses in one bank, summed; a value above the number of warp requests means bank conflicts. The reductions end with the sum, 48, in element 0; Hillis-Steele with the inclusive scan; Blelloch with the exclusive scan.

We re-ran the ladder as Metal kernels on 225 floats measured on Apple M1 Pro GPU. Harris's last rung was 30 times faster than his first; predict ours.

Only 1.6×: R1 takes 1.61 ms (83 GB/s) and R6 1.01 ms (133 GB/s), about the speed of MLX's own mx.sum (1.04 ms). Even the worst kernel reads memory at more than half the copy speed.

Median of 3 runs; the thin line spans the fastest and slowest of all 21 trials. Each time includes MLX's per-call launch-and-wait overhead, which the {{topic root|n:3c65c17b0d0d81c39f34d5e070d783c1}} measured at about 0.2 ms (its section 1), so the kernels themselves are faster than shown and the differences between them larger in proportion.

Why the ladder flattened. In 2007 the G80 had little on-chip cache and slow integer arithmetic, so the index arithmetic, idle lanes and barriers of the early rungs cost more than the memory traffic. A modern GPU has far more arithmetic per byte of bandwidth (a higher ridge point), so a reduction is limited by reading the input almost however clumsily it combines it; the remaining gap is the 8 barriers per 256 values of R1 to R3. The lesson that survives: do most of the work in registers, one value per element, and make the tree as small as possible (a grid-stride loop: a fixed grid where each thread sums many elements in a register first). That is what every production reduction does.

Harris's seven rungs by name (depth)
1 Interleaved, divergentAt step s, threads with tid % (2s) == 0 add. Most lanes of every warp sit idle while the warp still issues.
2 Strided indexThread t works on element 2st: active threads are now contiguous, but their addresses are strided, so several lanes hit the same shared-memory bank (shared memory is split into 32 banks).
3 Sequential addressingHalve the range each step: thread t adds element t + s. Contiguous threads, contiguous addresses.
4 First add during loadHalf the blocks; each thread loads two values and adds them on the way in, so no thread starts idle.
5 Last warp unrolledThe last 32 values are summed by one warp. Harris did it with "warp-synchronous" shared memory; today you use shuffles (below).
6, 7 Unrolled, many per threadTemplates remove loop overhead; then the grid-stride loop, so the tree runs once per thread block, not once per 512 elements.

Inside a warp: shuffles

A shuffle moves a register value directly from one lane of a warp to another, with no shared memory and no barrier. Five of them sum 32 values; compiled for an H100 (sm_90a) compiled, it is exactly five shuffle-and-add pairs, and the mask 0xffffffff says all 32 lanes take part:

__device__ float warp_sum(float v) {
  for (int o = 16; o > 0; o >>= 1)
    v += __shfl_down_sync(0xffffffffu, v, o);   // add the value held by lane (lane + o)
  return v;                                     // lane 0 holds the sum of all 32
}


Since Volta (2017) the lanes of a warp are not guaranteed to run in lockstep, so old "warp-synchronous" code that reads other lanes' shared-memory writes without a barrier is a bug: use the *_sync shuffles or __syncwarp().


Correction to old habits: why "warp-synchronous" code broke (depth)
Harris's rung 5 relied on the 32 lanes of a warp executing in lockstep, reading each other's shared-memory writes with no barrier. Since Volta (2017), lanes of a warp can be scheduled independently, and NVIDIA's {{Volta tuning guide|https://docs.nvidia.com/cuda/volta-tuning-guide/index.html}} says plainly: "Assumptions that code is executed in lockstep or that reads/writes from separate threads are visible across a warp without synchronization are invalid." Use the *_sync shuffles, or __syncwarp() between shared-memory steps. Old tutorials (and old kernels) still contain the volatile trick.



Combining blocks


Four ways to turn one partial per block into one number: (1) a second, small launch that reduces the partials (R1 to R6 above); (2) every block does an atomic add of its partial into one output (A1: one launch, 1.05 ms); (3) the last block to finish, detected with an atomic counter, reduces all partials; (4) a cooperative launch, where grid.sync() makes every block wait for all the others (blocks must all be resident at once, which limits the grid size). PyTorch's own reduction kernel uses the third.


What PyTorch does, and a correction to the old page (depth)
PyTorch's Reduce.cuh keeps a global buffer and a semaphore per output when a reduction spans blocks (source excerpt in src/inputs/pytorch_extracts.txt, PyTorch main at commit 8d1d972, read 2026-10-05). The old page said "in library code use CUB (cub::BlockReduce, cub::DeviceReduce), which is what PyTorch does". For sums, PyTorch does not: torch.sum on CUDA calls its own gpu_reduce_kernel ({{ReduceSumProdKernel.cu|https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/cuda/ReduceSumProdKernel.cu}}). It does use CUB for a one-dimensional cumsum (section 3). CUB is still the right thing to call in your own CUDA code: cub::BlockReduce compiles to the same five shuffles per warp ({{Compiled for NVIDIA|#t-sass}}).



The order of additions changes the answer


Floating-point addition is not associative: (a + b) + c can differ from a + (b + c) in the last bits, so different orders give different sums.


The 225 inputs are uniform in [0, 1), so the exact sum is about 16.8 million. Add them one by one into a single float32 accumulator, in order. What comes out?




The running sum reaches 224 = 16,777,216, where float32's spacing between neighbouring numbers is 2, and from then on adding any value below 1 rounds back to the same number. Result 16,777,216, off by 495 from the float64 sum 16,777,711.32. The GPU tree gives 16,777,712, off by 0.68: a tree adds numbers of similar size at every level, which is why parallel reductions are usually more accurate than the sequential loop they replace measured on Apple M1 Pro GPU.


Atomics make the order, and so the bits, change from run to run. We ran the atomic kernel A1 30 times on the same input in each of the 3 runs: it gave 7, 6, 8 distinct results (from 16,777,702 to 16,777,718), because the blocks arrive in a different order each time; the two-launch tree gave one result every time measured on Apple M1 Pro GPU. This is why torch.use_deterministic_algorithms(True) exists, why two "identical" training runs drift apart, and why a test must compare with a tolerance rather than bit for bit (section 8).







3. Scan: running totals


An inclusive scan (prefix sum) turns x0, x1, x2, ... into x0, x0+x1, x0+x1+x2, ...; an exclusive scan shifts it by one and starts at 0. Every output depends on every earlier input, yet it is everywhere in model code: a mixture-of-experts layer counts how many tokens go to each expert and scans the counts to find where each expert's tokens start in a packed buffer; top-p sampling scans sorted probabilities; packing variable-length sequences scans their lengths into offsets; torch.cumsum is a scan. Two parallel algorithms (from {{GPU Gems 3, chapter 39|https://developer.nvidia.com/gpugems/gpugems3/part-vi-gpu-computing/chapter-39-parallel-prefix-sum-scan-cuda}}, Harris, Sengupta and Owens), both in the last two modes of the widget in section 2:




Hillis and Steele
Step k: every element adds the one 2k places to its left. log2(n) steps, all elements busy, but O(n log n) additions: for n = 224, 386 million adds against 16.8 million for a loop derived, Σk<24(n − 2k). Fine inside a warp.


Blelloch (work-efficient)
An up-sweep builds a tree of partial sums (a reduction), a down-sweep pushes prefixes back down: "approximately 2 × (n − 1) adds and n − 1 swaps", 33.6 million for n = 224 derived, but twice the steps.




On a real GPU neither is used across the whole array. Inside a warp, a scan is five shuffles (__shfl_up_sync; Metal's simd_prefix_exclusive_sum); across a block, warps exchange totals through shared memory; across blocks is the hard part, because block 7 needs the total of blocks 0 to 6. Reduce, then scan takes three launches: (a) each block sums its tile; (b) one block scans the tile sums into offsets; (c) each block scans its tile again and adds its offset. The input is read twice and the output written once: 3 passes over memory, against 2 for a copy. Decoupled look-back does it in one pass (it is how cub::DeviceScan works; details below; not run here).




On 224 floats measured on Apple M1 Pro GPU, Hillis and Steele over the whole array, 24 launches each reading and writing everything, takes 18.81 ms; the three-launch scan 1.41 ms, 13.4 times faster and 1.41 times a plain copy (1.00 ms), close to the 3 : 2 ratio of passes that counting bytes predicts. MLX's library mx.cumsum took 7.78 ms on the same input, 5.5 times slower than our 40 lines (code in {{Kernel bench (M1)|#t-bench}}): libraries are not always at the ceiling, and the copy time tells you when they are not.


Decoupled look-back, and what PyTorch calls (depth)


Decoupled look-back ({{Merrill and Garland, NVIDIA, 2016|https://research.nvidia.com/publication/2016-03_single-pass-parallel-prefix-scan-decoupled-look-back}}) scans in one launch: each block publishes its own total as soon as it has it, and its inclusive prefix once it knows it; a block that needs its offset looks back at its predecessors' published values, summing totals until it meets a published prefix. It "requires only ~2n data movement" and its throughput "approaches that of copy operations" published. It relies on earlier blocks making progress while later ones wait, a guarantee Metal does not document, so we did not run it here.


In PyTorch, a one-dimensional torch.cumsum on CUDA calls cub::inclusive_scan, and a separate inclusive_deterministic_scan for floating-point types when deterministic algorithms are requested ({{ScanUtils.cuh|https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/cuda/ScanUtils.cuh}}, read 2026-10-05): the default single-pass scan can add in an order that depends on timing, for the same reason as the atomic sum of section 2.
