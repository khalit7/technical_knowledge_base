4. The matmul ladder, as the NVIDIA compiler sees it

The problem. C = AB for n × n float32 matrices does 2n3 operations on 3n2 numbers, so in principle each number loaded can be used n times. Whether a kernel gets anywhere near that is a question of reuse: how many multiply-adds each value performs while it sits in a register or in shared memory. Simon Boehm's {{worklog|https://siboehm.com/articles/22/CUDA-MMM}} (December 2022) climbs from 309 to 21,779 GFLOP/s on an RTX A6000 (1.3% to 93.7% of cuBLAS) in ten kernels published; the topic root's section 4 summarises it and its Kernel lab times the same ladder on the M1. Four things the binary says that the source does not:

  • k1 and k2 compile to the same instructions for sm_90a (185 each, 29 FFMA, 58 global loads) and sm_80 (187 each); for sm_120 the compiler happened to unroll them differently (136 and 163), with the same loads per multiply-add. Coalescing, worth 6.4 times on Boehm's A6000, is invisible in the code: it is only about which addresses the 32 lanes of a warp touch at once. You find it with a profiler's sectors-per-request metric, or by thinking about threadIdx.x (the {{memory hierarchy page|n:3c65c17b0d0d814a8edef7bd21c303d3}}, section 1).
  • The ratio that rises is FFMA per shared load: 0.7 for plain tiles, 1.6 with a column of 8 outputs per thread, 8 with an 8 × 8 block per thread, because each shared value read into a register now feeds 8 multiply-adds. Shared-memory bandwidth, not global, limits k3 and k4; registers are the next level of reuse.
  • nvcc already vectorised k5's shared loads (32 of its 64 are LDS.128) before we asked. What k6's explicit float4 code bought is fewer instructions around them (1,047 down to 731: less address arithmetic, 16 STG instead of 64) and fewer registers (158 down to 127). Here is the inner loop of each:

  • Registers decide how many blocks fit. With NVIDIA's allocation rules (registers per warp rounded up to 256, 64K per SM, as reproduced by the root's {{GPU simulator|n:3c65c17b0d0d81c39f34d5e070d783c1}}), 158 registers allow 12 warps per SM, one block of 8 warps; 127 registers allow 16 warps, two blocks derived. Beyond the CUDA-core ladder. Boehm's last rungs (autotuned tile sizes, then a warp-level tile) reach 93.7% of cuBLAS, and the final shape, block tile, then warp tile, then thread tile, is CUTLASS's. Real training matmuls replace the 8 × 8 FFMA block with tensor-core instructions (mma.sync, wgmma, tcgen05), which the {{libraries and tensor cores page|n:3c65c17b0d0d81a7adcaebee2f44a087}} compiles generation by generation, and load the next tile while computing this one ({{memory hierarchy page|n:3c65c17b0d0d814a8edef7bd21c303d3}}, section 6). The rule that does not change: count FLOPs per byte at each level of the hierarchy, and make it larger. Boehm's other observation also holds: the best tile sizes differ from GPU to GPU, which is why every serious matmul library autotunes, and each rung's fix comes from profiling the previous one, not from a recipe.







5. Fusion: keep it on chip


The idea. Two kernels in a row hand their intermediate result over through global memory: the first writes it, the second reads it back. A fused kernel does both operations while the intermediate is in registers or shared memory. Fusion pays exactly when that round trip is a large part of the time, which gives three rules: chains of memory-bound operations (elementwise, norms) fuse to nearly the cost of one; a cheap operation applied to a matmul's output while it is still in registers (an epilogue) or to its input as it is loaded (a prologue) removes one round trip of that matrix; and fusing work into a compute-bound loop can lose, because the loop was not waiting for memory in the first place. We measured all three, with real mistakes along the way.


Epilogue: matmul, bias, GELU


y = GELU(xW + b) for 4,096 tokens, 4,096 outputs, K = 1,024 or 256 inputs, float32. Unfused, the matmul writes C (64 MiB) and a second kernel reads it, adds b, applies GELU and writes y: 134 MB of extra traffic, about 0.9 ms at this GPU's copy speed derived. Our fused kernel is the Kernel lab's fastest matmul (8 × 8 matrix instructions, 64 × 64 tile per threadgroup) with the epilogue added. MLX's eager version (matmul, add and four elementwise operations for GELU, each a kernel) took 17.47 ms and 9.24 ms under mx.compile, which fuses the elementwise chain into one kernel after MLX's matmul (faster than ours). This is the baseline the old page warned about: compare a fused kernel against the compiled framework, not against eager mode, which flatters anything. On NVIDIA you rarely write this epilogue yourself: cuBLASLt takes it as a parameter (CUBLASLT_EPILOGUE_GELU_BIAS, "apply Bias and then GELU transform", plus _AUX variants that also save GELU's input for the backward pass and DGELU for the backward itself; cublasLt.h in CUDA 13.4.2, excerpt in src/inputs/), and CUTLASS composes epilogues as trees of operations on the accumulator fragments (its epilogue visitor trees), exactly what attempt 3 does by hand; in Triton you write the epilogue as ordinary code after the tl.dot loop. The opposite case, fusing two compute-bound matmuls into one kernel, rarely pays: the tensor cores are already busy, and holding both operands raises register pressure.


Prologue: RMSNorm into the next matmul


rmsnorm(x)W = diag(1/rms(x)) · x · (diag(γ)W). Fold γ into W once, offline; the matmul loads every element of each row of x anyway, so it can accumulate the row's sum of squares as the tiles go by, and scale each output row by 1/rms(x) in the epilogue. The normalised x is never written. A neat identity; did it pay measured on Apple M1 Pro GPU?

No. The separate RMSNorm kernel moves only 32 MB and costs about 0.2 ms; the fused version adds shared-memory reads of every A tile to the matmul's inner loop, which is the bottleneck, and loses more than it saves (at K = 256 too: 2.72 separate, 2.83 fused). That is the third rule: fusion that adds work to a compute-bound loop loses. Production kernels that do fuse a norm into a GEMM (for example to quantise activations to FP8 on the way in) do it where the GEMM is memory-bound, at small batch.
