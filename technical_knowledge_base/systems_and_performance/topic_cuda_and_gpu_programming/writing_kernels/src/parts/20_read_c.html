4. Row normalisation: softmax, LayerNorm, RMSNorm

Softmax, LayerNorm and RMSNorm all do the same thing to each row of a matrix: compute one or two statistics of the row (a reduction), then rewrite every element using them. In a transformer the rows are tokens and a row is a few thousand numbers, so the standard layout is one block per row, the row's elements spread over the block's threads, each thread keeping its share in registers between the statistics and the rewrite, so the row is read from memory once and written once. Arithmetic is a handful of operations per element; the speed is set by bytes.

The softmax ladder: one change matters

One threadgroup per row instead of one thread is worth 50 times; every later rung stays within 13% of a plain copy

The topic root's Kernel lab, 16,384 rows of 4,096 float32 (256 MiB in, 256 MiB out), median of 3 runs, measured on Apple M1 Pro GPU; data copied to src/inputs/root_kernel_lab_matmul.json. A plain copy of the same bytes at the lab's 164.7 GB/s takes 3.26 ms derived, 512 MiB / 164.7 GB/s.

One thread per row (S1) takes 177.14 ms: neighbouring threads read addresses a whole row (16 KB) apart. One threadgroup per row with neighbouring threads on neighbouring elements (S2) takes 3.54 ms, 50 times faster, already at 92% of copy speed. SIMD-group reductions, float4 loads, the online softmax (two passes) and the row held in registers (one pass, S6, 3.27 ms) are worth about 8% together, and the five-kernel eager version takes 13.08 ms (10.09 under mx.compile). S2 reads each row three times yet runs near copy speed, most likely because a 16 KB row is still in cache when it is re-read unconfirmed, not profiled. The idea to carry forward is the online softmax ({{Milakov and Gimelshein, 2018|https://arxiv.org/abs/1805.02867}}): keep a running maximum m and a running sum d of ex − m; when a larger value arrives, rescale the sum you have.

m′ = max(m, xi)    d′ = d · em − m′ + exi − m′
merge (ma, da) with (mb, db): m = max(ma, mb),   d = da ema − m + db emb − m

The second line makes it a parallel algorithm: any two partial results, from two lanes, two warps or two tiles, combine exactly, in any order. Every reduction on this page that is more than a sum needs such a merge, and FlashAttention (section 7) is built on this one.

LayerNorm: the variance is a numerical trap

LayerNorm subtracts the row's mean μ and divides by its standard deviation σ: y = (x − μ) / √(σ2 + ε) · γ + β. The tempting one-pass formula for the variance, σ2 = E[x2] − E[x]2, subtracts two large, nearly equal numbers when the mean is large compared with the spread, and float32 keeps only about 7 significant digits.

When the row fits in registers, as here, two passes over registers are as cheap as one and simpler.

Timings of the three LayerNorm kernels, and Welford's algorithm (depth)

All three kernels took 1.74 to 1.77 ms on 8,192 rows of 4,096 (154 GB/s counting one read and one write), against 1.87 ms for MLX's mx.fast.layer_norm and 9.87 ms for the same formula as seven separate MLX operations (6.79 ms under mx.compile) measured on Apple M1 Pro GPU.

Welford's algorithm keeps a count n, a mean and M2 (the sum of squared deviations), updating them per value; partial results merge with the pairwise formula of Chan, Golub and LeVeque ({{the parallel algorithm, summarised|https://en.wikipedia.org/wiki/Algorithms_for_calculating_variance#Parallel_algorithm}}), which has exactly the shape of the online-softmax merge:

δ = μb − μa,   n = na + nb,   μ = μa + δ nb/n,   M2 = M2a + M2b + δ2 nanb/n
μ, M2
mean and sum of squared deviations of each part; variance = M2 / n

Welford matters when the row is streamed once from memory, as in a long row or a fused kernel that cannot keep it.

RMSNorm, fused with the residual add

RMSNorm drops the mean: y = x / √(mean(x2) + ε) · γ. In a pre-norm transformer block it always follows a residual add, h = x + r, and h is needed twice: normalised for the next layer, and raw as the next residual. Count the passes before writing the kernel:

Fusing the add into the norm saves one pass over the activations: 5 become 4

So at best 5 : 4 = 1.25 times faster derived. Measured: 4.03 ms for MLX's add then mx.fast.rms_norm (4.09 ms under mx.compile, which did not fuse them), 3.35 ms fused, 1.20 times measured on Apple M1 Pro GPU. Production engines ship exactly this kernel: vLLM declares fused_add_rms_norm(input, residual, weight, epsilon) next to its plain rms_norm ({{csrc/ops.h|https://github.com/vllm-project/vllm/blob/main/csrc/ops.h}}, read 2026-10-05). The best case is set by the byte count before you start.

5. Fusion: keep it on chip

Two kernels in a row hand their intermediate result over through global memory: the first writes it, the second reads it back. A fused kernel does both while the intermediate is in registers or shared memory. Fusion pays exactly when that round trip is a large part of the time, which gives three rules: chains of memory-bound operations (elementwise, norms) fuse to nearly the cost of one (the RMSNorm above); a cheap operation applied to a matmul's output while it is still in registers (an epilogue) or to its input as it is loaded (a prologue) removes one round trip of that matrix; and fusing work into a compute-bound loop can lose, because the loop was not waiting for memory in the first place. All three measured, with real mistakes along the way.

Epilogue: matmul, bias, GELU

y = GELU(xW + b) for 4,096 tokens, 4,096 outputs, K = 1,024 or 256 inputs, float32. Unfused, the matmul writes C (64 MiB) and a second kernel reads it, adds b, applies GELU and writes y: 134 MB of extra traffic, about 0.9 ms at this GPU's copy speed derived. Our fused kernel is the Kernel lab's fastest matmul (8 × 8 matrix instructions, 64 × 64 tile per threadgroup) with the epilogue added. Three attempts, K = 1,024 measured on Apple M1 Pro GPU:

  1. Stage the whole tile in shared memory, then apply the epilogue: 13.76 ms, slower than not fusing (10.71 ms). The 16 KB staging buffer tripled the kernel's threadgroup memory (8 KB to 24 KB), so fewer threadgroups fit on each GPU core for the whole matmul, not just the epilogue: the occupancy cliff the hardware topic measured on this GPU ({{GPU architecture|n:3c65c17b0d0d810682aae39bd614ec64}}). Shared memory is not free.
  2. Apply it to the accumulator registers directly, then store as the plain matmul does. Each lane of a SIMD-group holds 2 of the 64 values of every 8 × 8 accumulator; which two is fixed by the hardware, and we read the mapping from MLX's own kernels (steel/gemm/mma.h, get_coord). With the accurate precise::tanh: 11.40 ms, still slower. In the separate kernel, GELU's arithmetic hid behind memory traffic; inside the matmul it is added to a compute-bound kernel's time (on NVIDIA the same choice is -use_fast_math or intrinsics such as __expf; check the error you accept).
  3. Same, with fast::tanh (it differs from the precise version by at most 5 × 10−7, a side experiment in src/m1/out/side_experiments.txt): 10.07 ms against 9.92 ms for the matmul alone. The epilogue now costs 0.16 ms and saves 0.64 ms against the unfused pair; at K = 256, where the matmul is shorter and the saved bytes weigh more, 3.45 becomes 2.86 ms.

MLX's eager version (matmul, add and four elementwise operations for GELU, each a kernel) took 17.47 ms and 9.24 ms under mx.compile, which fuses the elementwise chain into one kernel after MLX's matmul (faster than ours). So compare a fused kernel against the compiled framework, not against eager mode, which flatters anything: our epilogue looked 1.7× faster than eager and was 0.92× of compiled MLX.

Where epilogues live in NVIDIA's libraries, CUTLASS and Triton (depth)

On NVIDIA you rarely write this epilogue yourself: cuBLASLt takes it as a parameter (CUBLASLT_EPILOGUE_GELU_BIAS, "apply Bias and then GELU transform", plus _AUX variants that also save GELU's input for the backward pass and DGELU for the backward itself; cublasLt.h in CUDA 13.4.2, excerpt in src/inputs/), and CUTLASS composes epilogues as trees of operations on the accumulator fragments (its epilogue visitor trees), exactly what attempt 3 does by hand; in Triton you write the epilogue as ordinary code after the tl.dot loop ({{Triton and Gluon page|n:3c65c17b0d0d81729d15ed4d1a4461b3}}). Fusing two compute-bound matmuls into one kernel rarely pays: the tensor cores are already busy, and holding both operands raises register pressure.

Prologue: RMSNorm into the next matmul

rmsnorm(x)W = diag(1/rms(x)) · x · (diag(γ)W). Fold γ into W once, offline; the matmul loads every element of each row of x anyway, so it can accumulate the row's sum of squares as the tiles go by, and scale each output row by 1/rms(x) in the epilogue. The normalised x is never written. A neat identity; did it pay measured on Apple M1 Pro GPU?
