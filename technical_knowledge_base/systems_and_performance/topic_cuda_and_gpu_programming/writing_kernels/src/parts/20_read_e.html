8. Testing a kernel against a reference

A fast wrong kernel is worse than a slow right one, and GPU bugs hide: they appear at one size, one in a hundred runs, or only after a different kernel ran first. Every kernel on this page went through the same harness before it was timed: run it, compare with a float64 reference computed by NumPy, fail if the largest error exceeds a tolerance. That harness still let one bug through.

A kernel that wrote nothing passed the test
Our first standalone RMSNorm kernel computed its loop count as C / 4 / 256, which is 0 for rows of 256 floats: it wrote nothing at all. The check passed, error 4 × 10−6 (the log line is kept in src/m1/out/side_experiments.txt). The output buffer the kernel received was, most likely, memory MLX's allocator had just freed after the library's own RMSNorm of the same shape, still holding the right answer. Two cheap defences: poison the output (fill it with NaN before the kernel runs, or make sure it is fresh memory; our harness now empties MLX's buffer cache before every check) and run the reference path after, not before, the kernel under test, so it cannot leave its answer behind. The fixed kernel then passed for the right reason. The topic root's Kernel lab kept a second lesson: a barrier that was too weak (simdgroup_barrier where a threadgroup barrier was needed) gave 1 to 5 wrong rows out of 4,096 at random, and every small test passed. Test at the real size, and repeat.

Choosing the tolerance. torch.testing.assert_close passes when |actual − expected| ≤ atol + rtol · |expected|, with defaults per data type ({{_comparison.py|https://github.com/pytorch/pytorch/blob/main/torch/testing/_comparison.py}}, read 2026-10-05; table below). These are right for one rounding, not for a sum of thousands of terms, whose error grows with the length of the sum. A practical rule: compute the reference in float64, measure the error of a trusted implementation in your precision against it, and require your kernel's error to be within a small factor of that. Our matmuls in float32 erred by up to 8 × 10−6 against float64, like MLX's; the 4-bit GEMV by 9 × 10−4 against the product with the same dequantised weights, and by far more (section 6) against the unquantised weights, which is a different question (does quantisation hurt the model?) and needs a different test (evaluation).

Tools. On NVIDIA, compute-sanitizer's initcheck would have caught our RMSNorm bug, and racecheck a missing barrier (details below). Timing honestly (warm-up, medians, L2 flushing, CUDA events) is section 2 of {{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}}; the closed workbench in its section 5 shows why a reordered sum or an atomic changes the last digits and which tolerance fits each data type.

The four sanitizer tools, PyTorch's default tolerances, and inputs that break kernels (depth)

compute-sanitizer (shipped with the toolkit) has four tools, from its own help text (CUDA 13.4.2): memcheck ("Memory access checking", the default: out-of-bounds and misaligned accesses), racecheck ("Shared memory hazard checking": a missing __syncthreads()), synccheck ("Synchronization checking": a barrier only some threads reach) and initcheck ("Global memory initialization checking": reading memory nobody wrote, which would have caught our RMSNorm bug). They slow a kernel by large factors, so run them on small inputs in CI.

  • Sizes that are not a multiple of the tile (4,097 columns, 1 row, 0 rows): the bounds checks. Every kernel on this page assumes multiples of its tile; a production kernel must not.
  • Large offsets: rows with mean 3,000 (section 4), logits of 104 (softmax without the max subtraction overflows exp above about 88.7 in float32).
  • Masks: a row whose keys are all masked gives max = −∞, then exp(−∞ − (−∞)) = NaN. Decide what the kernel should return (zeros, or NaN to flag it) and test it. Our causal kernel never meets such a row because key 0 is always visible; a padding mask breaks that.
  • Real distributions: real activations have outliers (a few channels 100 times larger than the rest); random normal inputs hide quantisation and overflow problems.
  • Repeated runs: run 10 to 30 times and compare the outputs with each other, which finds races and non-deterministic atomics (section 2).

Depth: rehearsal and a path to practise

Interview questions, with short answers (optional)
Why is a reduction memory-bound, and what is its ceiling?
One add per 4-byte element is far below any GPU's ridge point; the ceiling is the time to read the input once. On the M1 the first rung read at 83 GB/s and the last at 133 GB/s, against about 143 GB/s for a plain read measured by the hardware topic's Roofline lab.
Write a warp sum. Why the mask argument?
Five __shfl_down_sync(0xffffffff, v, o) for o = 16, 8, 4, 2, 1. The mask names the lanes that participate and must all reach the call; it exists because lanes are scheduled independently since Volta.
Hillis-Steele or Blelloch?
Hillis-Steele: log n steps, O(n log n) adds, fine inside a warp. Blelloch: O(n) adds, 2 log n steps, good for large arrays in shared memory. Across the GPU, a tiled scan with decoupled look-back reads and writes each element once (CUB).
Walk a naive matmul up to a register-tiled one. What does each step buy?
Coalesce (lanes on neighbouring columns: 8 bytes asked per FMA, 5 moved instead of 33); tile into shared memory (global traffic 32 times lower, shared reads now the limit); tile into registers (each shared value feeds 8, then 64 FMAs); vectorise (fewer instructions and registers, so more blocks per SM). Then warp tiles, autotuning and tensor cores (section 1).
A 4-bit GEMV is only 2× faster than float16, not 4×. Why might that be?
Fixed launch overhead dominates small kernels (0.17 ms here), dequantisation instructions or scalar activation loads can make it instruction-bound, and scales and biases add bytes (0.5625 bytes per weight here). Measure the read of the bytes alone first.
When does fusion not help?
When the intermediate's round trip is a small share of the time (compute-bound kernels), when it raises register or shared-memory use and cuts occupancy, or when the compiler already fused it.

Correction to the old page
The old page's project ladder was written "for the dual-5090 box"; there is no NVIDIA GPU here. The same ladder, rewritten for a Mac and rented GPU hours:
  1. On the Mac: run this page's Metal kernels (src/m1/, MLX), change one thing, re-measure. Then write softmax and a sum in Triton and check them with TRITON_INTERPRET=1 ({{Triton and Gluon page|n:3c65c17b0d0d81729d15ed4d1a4461b3}}).
  2. Compile CUDA without a GPU: build the kernels in src/cuda/ with nvcc in a container, read ptxas -v and the SASS, and predict which will be fastest ({{compiler stack page|n:3f05c17b0d0d81ddbc00fac9e8a2ff89}}).
  3. Rent one H100 for a day (on-demand at about $3.99 per GPU-hour on Lambda, 2026-10-05): reproduce Boehm's ladder through kernel 6 with Nsight Compute open, then the reduction ladder; keep a table of GFLOP/s or GB/s and the profiler's bottleneck per rung.
  4. A fusion that the compiler does not do (residual + RMSNorm + FP8 quantisation, or dequantise + GEMV for a format you use), benchmarked against torch.compile.
  5. A minimal FlashAttention forward in Triton (the official fused-attention tutorial is the reference), checked against F.scaled_dot_product_attention; then a causal version that skips tiles; then a split-KV decode kernel.
