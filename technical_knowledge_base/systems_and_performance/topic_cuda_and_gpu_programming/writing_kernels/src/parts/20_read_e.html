8. Testing a kernel against a reference

A fast wrong kernel is worse than a slow right one, and GPU bugs hide: they appear at one size, one in a hundred runs, or only after a different kernel ran first. Every kernel on this page went through the same harness before it was timed: run it, compare with a float64 reference computed by NumPy, fail if the largest error exceeds a tolerance. That harness still let one bug through, and it is the most useful thing on this page to read.

A kernel that wrote nothing passed the test
Our first standalone RMSNorm kernel computed its loop count as C / 4 / 256, which is 0 for rows of 256 floats: it wrote nothing at all. The check passed, error 4 × 10−6 (the log line is kept in src/m1/out/side_experiments.txt). The output buffer the kernel received was, most likely, memory MLX's allocator had just freed after the library's own RMSNorm of the same shape, still holding the right answer. Two cheap defences: poison the output (fill it with NaN before the kernel runs, or make sure it is fresh memory; our harness now empties MLX's buffer cache before every check) and run the reference path after, not before, the kernel under test, so it cannot leave its answer behind. The fixed kernel then passed for the right reason. The topic root's Kernel lab kept a second lesson: a barrier that was too weak (simdgroup_barrier where a threadgroup barrier was needed) gave 1 to 5 wrong rows out of 4,096 at random, and every small test passed. Test at the real size, and repeat.

Choosing the tolerance

torch.testing.assert_close passes when |actual − expected| ≤ atol + rtol · |expected|, with defaults per data type ({{_comparison.py|https://github.com/pytorch/pytorch/blob/main/torch/testing/_comparison.py}}, read 2026-10-05):

dtypertolatol
float321.3e-61e-5
float161e-31e-5
bfloat160.0161e-5
float641e-71e-7

These are right for one rounding, not for a sum of thousands of terms, whose error grows with the length of the sum. A practical rule: compute the reference in float64, measure the error of a trusted implementation in your precision (the library, or PyTorch eager) against it, and require your kernel's error to be within a small factor of that. Our matmuls in float32 erred by up to 8 × 10−6 against float64, like MLX's; the 4-bit GEMV by 9 × 10−4 against the product with the same dequantised weights, and by far more (section 6) against the unquantised weights, which is a different question (does quantisation hurt the model?) and needs a different test (evaluation).

Inputs that break kernels

  • Sizes that are not a multiple of the tile (4,097 columns, 1 row, 0 rows): the bounds checks. Every kernel on this page assumes multiples of its tile; a production kernel must not.
  • Large offsets: rows with mean 3,000 (section 3), logits of 104 (softmax without the max subtraction overflows exp above about 88.7 in float32).
  • Masks: a row whose keys are all masked gives max = −∞, then exp(−∞ − (−∞)) = NaN. Decide what the kernel should return (zeros, or NaN to flag it) and test it. Our causal kernel never meets such a row because key 0 is always visible; a padding mask breaks that.
  • Real distributions: real activations have outliers (a few channels 100 times larger than the rest); random normal inputs hide quantisation and overflow problems.
  • Repeated runs: run 10 to 30 times and compare the outputs with each other, which finds races and non-deterministic atomics (section 1).

Tools

On NVIDIA, compute-sanitizer (shipped with the toolkit) has four tools, from its own help text (CUDA 13.4.2): memcheck ("Memory access checking", the default: out-of-bounds and misaligned accesses), racecheck ("Shared memory hazard checking": a missing __syncthreads()), synccheck ("Synchronization checking": a barrier only some threads reach) and initcheck ("Global memory initialization checking": reading memory nobody wrote, which would have caught our RMSNorm bug). They slow a kernel by large factors, so run them on small inputs in CI. Timing honestly (warm-up, medians, L2 flushing, CUDA events) is section 2 of {{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}}; its Numerics lab tab shows why a reordered sum or an atomic changes the last digits and which tolerance fits each data type.

Common mistakes

Comparing a fused kernel with eager PyTorch
Eager mode runs one kernel per operation; anything fused beats it. Compare with torch.compile (or mx.compile): our GELU epilogue looked 1.7× faster than eager and was 0.92× of compiled MLX (section 5).
Fusing into a compute-bound loop
Extra instructions in the inner loop of a matmul cost more than the bytes they save: RMSNorm fused into our matmul lost (section 5). Fuse into memory-bound kernels, or into the epilogue, once.
Using more shared memory "because it is free"
Shared memory and registers per block decide how many blocks fit on an SM, for the whole kernel. A 16 KB staging buffer made our fused kernel 28% slower than not fusing.
Accurate math functions in a fused epilogue
precise::tanh cost 1.3 ms inside the matmul; in the separate, memory-bound kernel its cost hid behind the memory traffic. On NVIDIA the equivalent choice is -use_fast_math or intrinsics like __expf; check the error you accept.
Warp-synchronous code without _sync
Lanes of a warp are not guaranteed to run in lockstep since Volta. Use __shfl_*_sync and __syncwarp() (section 1).
E[x²] − E[x]²
Catastrophic cancellation when the mean is large: errors of 1,653 at mean 3,000 (section 3). Use two passes over registers or Welford.
Expecting bit-identical results
Atomics and some scans change the order of additions from run to run. Test with tolerances; turn on deterministic algorithms when you must reproduce a run.
Benchmarking only powers of two
Our split-KV kernel was nearly 3 times slower at exactly 65,536 keys than at 66,048 (section 7). Sweep sizes.
Masking instead of skipping
A causal mask applied to every tile costs the same as no mask; skipping tiles above the diagonal nearly halves the work (section 7).

Interview questions, with short answers

Why is a reduction memory-bound, and what is its ceiling?
One add per 4-byte element is far below any GPU's ridge point; the ceiling is the time to read the input once. On the M1 the first rung read at 83 GB/s and the last at 133 GB/s, against about 143 GB/s for a plain read measured by the hardware topic's Roofline lab.
Write a warp sum. Why the mask argument?
Five __shfl_down_sync(0xffffffff, v, o) for o = 16, 8, 4, 2, 1. The mask names the lanes that participate and must all reach the call; it exists because lanes are scheduled independently since Volta.
How do you combine partial sums from different blocks?
A second launch, an atomic add per block (fast, non-deterministic), or the last block to finish (found with an atomic counter) reduces all partials, as PyTorch's Reduce.cuh does.
Hillis-Steele or Blelloch?
Hillis-Steele: log n steps, O(n log n) adds, fine inside a warp. Blelloch: O(n) adds, 2 log n steps, good for large arrays in shared memory. Across the GPU, a tiled scan with decoupled look-back reads and writes each element once (CUB).
What does the online softmax merge, and why does FlashAttention need it?
Two partial (max, sum) pairs: rescale each sum by emi − m and add. It lets tiles of keys be processed one at a time, and partial outputs (Flash-Decoding) be combined, without ever seeing the full row.
Why does FlashAttention-2 split Q across warps instead of K?
Split-K leaves every warp with a partial result for every row, which must be written to shared memory, synchronised and summed; split-Q gives each warp its own rows and no communication.
What limits attention on an H100 once the bytes are fixed?
The exponentials: 989 TFLOPS of FP16 matmul against 3.9 of special functions, about 50% of the matmul time at d = 128. FA-3 overlaps them with the GEMMs (warp specialisation, ping-pong).
Why is decode attention slow with plain FlashAttention, and the fix?
One query per head gives batch × heads thread blocks, a few percent of the GPU. Split the keys (Flash-Decoding), run chunks in parallel and merge with logsumexp rescaling.
A 4-bit GEMV is only 2× faster than float16, not 4×. Why might that be?
Fixed launch overhead dominates small kernels (0.17 ms here), dequantisation instructions or scalar activation loads can make it instruction-bound, and scales and biases add bytes (0.5625 bytes per weight here). Measure the read of the bytes alone first.
When does fusion not help?
When the intermediate's round trip is a small share of the time (compute-bound kernels), when it raises register or shared-memory use and cuts occupancy, or when the compiler already fused it.

Correction to the old page
The old page's project ladder was written "for the dual-5090 box"; there is no NVIDIA GPU here. The same ladder, rewritten for a Mac and rented GPU hours:
  1. On the Mac: run this page's Metal kernels (src/m1/, MLX), change one thing, re-measure. Then write softmax and a sum in Triton and check them with TRITON_INTERPRET=1 ({{Triton and Gluon page|n:3c65c17b0d0d81729d15ed4d1a4461b3}}).
  2. Compile CUDA without a GPU: build the kernels in src/cuda/ with nvcc in a container, read ptxas -v and the SASS, and predict which will be fastest ({{compiler stack page|n:3f05c17b0d0d81ddbc00fac9e8a2ff89}}).
  3. Rent one H100 for a day (on-demand at about $3.99 per GPU-hour on Lambda, 2026-10-05): reproduce Boehm's ladder through kernel 6 with Nsight Compute open, then the reduction ladder; keep a table of GFLOP/s or GB/s and the profiler's bottleneck per rung.
  4. A fusion that the compiler does not do (residual + RMSNorm + FP8 quantisation, or dequantise + GEMV for a format you use), benchmarked against torch.compile.
  5. A minimal FlashAttention forward in Triton (the official fused-attention tutorial is the reference), checked against F.scaled_dot_product_attention; then a causal version that skips tiles; then a split-KV decode kernel.
