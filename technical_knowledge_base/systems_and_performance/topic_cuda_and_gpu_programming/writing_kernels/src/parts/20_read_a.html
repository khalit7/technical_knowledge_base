Almost every GPU kernel inside a transformer is one of a handful of patterns: an elementwise map, a reduction (many numbers into one), a scan (running totals), a row normalisation (softmax, LayerNorm, RMSNorm), a tiled matrix multiply, and fusions of these, of which FlashAttention is the famous one. This page writes each of them, tests it against a float64 reference, measures it, and climbs its optimisation ladder, so that you can write the next one yourself and read the ones in FlashAttention, CUTLASS, llama.cpp or vLLM.

It assumes the vocabulary of the {{topic root|n:3c65c17b0d0d81c39f34d5e070d783c1}}: a thread runs your kernel function once; 32 threads form a warp that issues one instruction at a time; warps are grouped into a block that shares a small fast shared memory and can wait at a barrier (__syncthreads()); blocks run on SMs (streaming multiprocessors) and talk to each other only through the large slow global memory (HBM on a datacenter GPU). If any of those is shaky, the root's section 2 and the {{programming model page|n:3c65c17b0d0d8162865eec15d9dae87e}} build them up; coalescing, bank conflicts and registers are the {{memory hierarchy page|n:3c65c17b0d0d814a8edef7bd21c303d3}}'s.

What is real on this page
There is no NVIDIA GPU here. Every timing was measured on Apple M1 Pro GPU: a real SIMT GPU whose SIMD-groups of 32 threads, threadgroups and threadgroup memory are a warp, a block and shared memory under other names; the kernels are Metal, run through MLX 0.32.3, each checked against float64 before it is timed, 3 runs of 7 trials, median shown, with the machine's load average recorded for every case (other work shared the laptop; the {{Kernel bench (M1)|#t-bench}} tab shows the spread). NVIDIA behaviour comes from compiled output (CUDA 13.4.2, the same kernels in CUDA C++, built for sm_80, sm_90a and sm_120 in a container without a GPU: registers, shared memory, instruction mix) and from published papers and talks, each cited. Arithmetic on these is derived, with its formula. What transfers from the M1 is the shape of each result; the absolute speeds do not.

And one method for all of them, used in every section below:

  1. Write the reference first, in float64 NumPy or PyTorch, and a test that compares against it with a tolerance chosen for the data type (section 8).
  2. Write the obvious kernel, make it pass, and measure it against a ceiling: for a memory-bound kernel, the time a plain copy of the same bytes takes; for a compute-bound one, the peak arithmetic rate. The gap is what is left to win.
  3. Find what limits it (a profiler on NVIDIA, see the {{profiling page|n:3c65c17b0d0d813da895ffee55b0457c}}; here, counting bytes and reading the compiled instructions), remove that limit, re-test, re-measure. Stop when you reach the ceiling or the library.

1. Reductions: many numbers into one

The problem. Sum 225 (33.5 million) floats. On a CPU it is one loop. On a GPU, thousands of threads must each do a part and then combine their parts, and combining is where every difficulty lives: threads in different blocks cannot see each other's shared memory or wait for each other inside one kernel launch.

The shape of the answer. A tree: in step 1, half the threads each add two numbers; in step 2, a quarter add two partial sums; after log2(256) = 8 steps one thread holds the block's total. Each block writes its total, and a second, tiny launch (or an atomic add) combines the block totals. The {{Reduce and scan, animated|#t-tree}} tab runs the tree step by step on one input in four variants, with counters for idle lanes and bank conflicts.

Harris's ladder, and what is left of it

Mark Harris's {{Optimizing Parallel Reduction in CUDA|https://developer.download.nvidia.com/assets/cuda/files/reduction.pdf}} (NVIDIA, 2007) is the classic warm-up: seven kernels for summing 4M integers on a G80, each fixing one problem, from 2.083 to 62.671 GB/s, 30.04 times faster, and 73 GB/s on 32M elements against the G80's 86.4 GB/s peak published. The rungs are worth knowing by name because the problems are still real:

1 Interleaved, divergentAt step s, threads with tid % (2s) == 0 add. Most lanes of every warp sit idle while the warp still issues: divergence (lanes of one warp taking different branches, run one after the other).
2 Strided indexThread t works on element 2st: active threads are now contiguous, but their addresses are strided, so several lanes hit the same shared-memory bank (shared memory is split into 32 banks; lanes hitting the same bank wait in turn).
3 Sequential addressingHalve the range each step: thread t adds element t + s. Contiguous threads, contiguous addresses.
4 First add during loadHalf the blocks; each thread loads two values and adds them on the way in, so no thread starts idle.
5 Last warp unrolledThe last 32 values are summed by one warp. Harris did it with "warp-synchronous" shared memory; today you use shuffles (below).
6, 7 Unrolled, many per threadTemplates remove loop overhead; then a fixed grid where each thread sums many elements in a register first (a grid-stride loop), so the tree runs once per thread block, not once per 512 elements.

We re-ran the ladder as Metal kernels on 225 floats measured on Apple M1 Pro GPU. Before looking: Harris's last rung was 30 times faster than his first. How much faster is ours?

On the M1 Pro, R6 (grid-stride, vector loads, SIMD sums) against R1 (interleaved, divergent):
Only 1.6×: R1 takes 1.61 ms (83 GB/s) and R6 1.01 ms (133 GB/s), about the speed of MLX's own mx.sum (1.04 ms). Even the worst kernel reads memory at more than half the copy speed.

Bars: median of 3 runs; the thin line spans the fastest and slowest of all 21 trials. Each time includes MLX's per-call launch-and-wait overhead, which the {{topic root|n:3c65c17b0d0d81c39f34d5e070d783c1}} measured at about 0.2 ms (its section 1), so the kernels themselves are faster than shown and the differences between them larger in proportion.

Why the ladder flattened. In 2007 the G80 had little on-chip cache and slow integer arithmetic, so the index arithmetic, idle lanes and barriers of the early rungs cost more than the memory traffic. A modern GPU has far more arithmetic per byte of bandwidth (the ridge point of the {{hardware root|n:3c65c17b0d0d8118beeefaed56da6f8e}}), so a reduction is limited by reading the input almost however clumsily it combines it; the remaining gap is the 8 barriers per 256 values of R1 to R3. The lesson that survives is the last one: do most of the work in registers, one value per element, and make the tree as small as possible. That is what every production reduction does.

Inside a warp: shuffles

A shuffle moves a register value directly from one lane of a warp to another, with no shared memory and no barrier. Five of them sum 32 values:

__device__ float warp_sum(float v) {
  for (int o = 16; o > 0; o >>= 1)
    v += __shfl_down_sync(0xffffffffu, v, o);   // add the value held by lane (lane + o)
  return v;                                     // lane 0 holds the sum of all 32
}

Compiled for an H100 (sm_90a) compiled, it is exactly five shuffle-and-add pairs; the mask 0xffffffff says all 32 lanes take part:



Correction to old habits: "warp-synchronous" code is a bug
Harris's rung 5 relied on the 32 lanes of a warp executing in lockstep, reading each other's shared-memory writes with no barrier. Since Volta (2017), lanes of a warp can be scheduled independently, and NVIDIA's {{Volta tuning guide|https://docs.nvidia.com/cuda/volta-tuning-guide/index.html}} says plainly: "Assumptions that code is executed in lockstep or that reads/writes from separate threads are visible across a warp without synchronization are invalid." Use the *_sync shuffles, or __syncwarp() between shared-memory steps. Old tutorials (and old kernels) still contain the volatile trick.



Combining blocks: a second launch, an atomic, or one more trick


Three ways to turn one partial per block into one number: (1) a second, small launch that reduces the partials (rungs R1 to R6 above); (2) every block does an atomic add of its partial into one output (A1: one launch, 1.05 ms); (3) the last block to finish, detected with an atomic counter, reduces all partials; (4) a cooperative launch, where grid.sync() makes every block wait for all the others (blocks must all be resident at once, which limits the grid size). PyTorch's own reduction kernel uses the third: its Reduce.cuh keeps a global buffer and a semaphore per output when a reduction spans blocks (source excerpt in src/inputs/pytorch_extracts.txt, PyTorch main at commit 8d1d972, read 2026-10-05).


Correction to the old page
The old page said "in library code use CUB (cub::BlockReduce, cub::DeviceReduce), which is what PyTorch does". For sums, PyTorch does not: torch.sum on CUDA calls its own gpu_reduce_kernel ({{ReduceSumProdKernel.cu|https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/cuda/ReduceSumProdKernel.cu}}). It does use CUB for a one-dimensional cumsum (section 2). CUB is still the right thing to call in your own CUDA code: cub::BlockReduce compiles to the same five shuffles per warp ({{Compiled for NVIDIA|#t-sass}}).



The order of additions changes the answer


Floating-point addition is not associative: (a + b) + c can differ from a + (b + c) in the last bits. A reduction picks an order, and different orders give different sums. Two consequences you will meet in training code:


The 225 inputs are uniform in [0, 1), so the exact sum is about 16.8 million. Add them one by one into a single float32 accumulator, in order. What comes out?




The running sum reaches 224 = 16,777,216, where float32's spacing between neighbouring numbers is 2, and from then on adding any value below 1 rounds back to the same number. Result 16,777,216, off by 495 from the float64 sum 16,777,711.32. The GPU tree gives 16,777,712, off by 0.68: a tree adds numbers of similar size at every level, which is why parallel reductions are usually more accurate than the sequential loop they replace measured on Apple M1 Pro GPU.


Atomics make the order, and so the bits, change from run to run. We ran the atomic kernel A1 30 times on the same input in each of the 3 runs: it gave 7, 6, 8 distinct results (from 16,777,702 to 16,777,718), because the blocks arrive in a different order each time; the two-launch tree gave one result every time measured on Apple M1 Pro GPU. This is why torch.use_deterministic_algorithms(True) exists, why two "identical" training runs drift apart, and why a test must compare with a tolerance rather than bit for bit (section 8).
