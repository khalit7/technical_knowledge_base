The idea in one screen

A kernel is fast when every byte it fetches from slow memory is used as many times as possible while it sits on chip. Each optimisation step of every kernel on this page (coalescing, tiles in shared memory, tiles in registers, wider loads, fusion) either moves fewer bytes per useful operation, or stops a result from making a round trip through global memory.

many numbers into one; running totals (prefix sums).
Shuffle
a register value passed directly between lanes of a warp, no shared memory, no barrier.
Fusion, epilogue, prologue
doing two operations in one kernel; an operation applied to a matmul's output while still in registers, or to its input as it is loaded.
Online softmax
a running max and sum that rescale when a larger value arrives, so partial results merge exactly.
Split-KV (Flash-Decoding)
decode attention split over chunks of the keys, merged at the end.
What is real on this page
There is no NVIDIA GPU here. Timings are measured on Apple M1 Pro GPU, a real SIMT GPU whose SIMD-groups of 32 threads, threadgroups and threadgroup memory are a warp, a block and shared memory under other names: Metal kernels run through MLX 0.32.3, each checked against float64 before it is timed, 3 runs of 7 trials, median shown, the machine's load recorded (other work shared the laptop; the {{Kernel bench (M1)|#t-bench}} tab shows the spread). One method for all of them: write the reference first (float64 NumPy or PyTorch) and a test with a tolerance chosen for the data type (section 8); write the obvious kernel, make it pass, and measure it against a ceiling (for a memory-bound kernel, the time a plain copy of the same bytes takes; for a compute-bound one, the peak arithmetic rate): the gap is what is left to win. Then find what limits it (a profiler on NVIDIA, see the {{profiling page|n:3c65c17b0d0d813da895ffee55b0457c}}; here, counting bytes and reading the compiled instructions), remove that limit, re-test, re-measure. Stop when you reach the ceiling or the library.

1. The matmul ladder: what each rung buys

C = AB for n × n matrices does 2n3 operations on 3n2 numbers, so each number loaded could in principle be used n times. Whether a kernel gets near that is a question of reuse. Boehm's worklog (December 2022) climbs from 309 to 21,779 GFLOP/s on an RTX A6000, 1.3% to 93.7% of cuBLAS, in ten kernels published; the hero above walks his rungs with the bytes each asks for. Read it as three moves, one per level of memory:

  • Coalesce (rung 2). The code of rungs 1 and 2 differs only in which thread index walks rows, and compiles to the same instructions (185 each for sm_90a, 29 FFMA, 58 global loads; 187 each for sm_80; for sm_120 the compiler unrolled them differently, 136 and 163, with the same loads per multiply-add) compiled. Coalescing, worth 6.4 times on Boehm's A6000, is invisible in the code: it is only about which addresses the 32 lanes of a warp touch at once. You find it with a profiler's sectors-per-request metric, or by thinking about threadIdx.x (the {{memory hierarchy page|n:3c65c17b0d0d814a8edef7bd21c303d3}}, section 1).
  • Tile into shared memory, then into registers (rungs 3 to 5). The ratio that rises is FFMA per shared load: 0.7 for plain tiles, 1.6 with a column of 8 outputs per thread, 8 with an 8 × 8 block per thread, because each shared value read into a register now feeds 8 multiply-adds. Shared-memory bandwidth, not global, limits rungs 3 and 4; registers are the next level of reuse.
  • Vectorise (rung 6). nvcc already vectorised rung 5's shared loads (32 of its 64 are LDS.128) before we asked. What the explicit float4 code bought is fewer instructions around them (1,047 down to 731: less address arithmetic, 16 STG instead of 64) and fewer registers (158 down to 127).

Registers decide how many blocks fit. With NVIDIA's allocation rules (registers per warp rounded up to 256, 64K per SM, as reproduced by the root's {{GPU simulator|n:3c65c17b0d0d81c39f34d5e070d783c1}}), 158 registers allow 12 warps per SM, one block of 8 warps; 127 registers allow 16 warps, two blocks derived. Two resident blocks let one block compute while the other waits at its barrier.

Beyond the CUDA-core ladder. Boehm's last rungs (autotuned tile sizes, then a warp-level tile) reach 93.7% of cuBLAS, and the final shape, block tile, then warp tile, then thread tile, is CUTLASS's. Real training matmuls replace the 8 × 8 FFMA block with tensor-core instructions (mma.sync, wgmma, tcgen05), which the {{libraries and tensor cores page|n:3c65c17b0d0d81a7adcaebee2f44a087}} compiles generation by generation, and load the next tile while computing this one ({{memory hierarchy page|n:3c65c17b0d0d814a8edef7bd21c303d3}}, section 6). The rule that does not change: count FLOPs per byte at each level of the hierarchy, and make it larger. Boehm's other observation also holds, and the M1 shows it (the 32 × 32 tile slower than 16 × 16, 36.48 against 26.90 ms): the best tile sizes differ from GPU to GPU, which is why every serious matmul library autotunes, and each rung's fix comes from profiling the previous one, not from a recipe.
