6. Decode: a matrix times one vector, with 4-bit weights

When a model generates one token for one user, every linear layer multiplies its weight matrix by a single vector: a GEMV. Each weight is read once and used once, so the time is the bytes of the weights divided by memory bandwidth, and the only way to go faster is to read fewer bytes. That is why decode-time weights are stored in 4 bits. But the GPU cannot multiply 4-bit codes directly; they must be dequantised (code × scale + bias, per group of weights). Do it as a separate kernel and you write a full 16-bit copy of the matrix and read it back, three times the bytes you hoped to save. Do it inside the GEMV, in registers, and only the 4-bit bytes cross the memory bus.

The shape is one MLP projection of Llama 3 8B, 14,336 × 4,096, in MLX's own 4-bit format (groups of 64 weights, a float16 scale and bias per group): 117.4 MB in float16, 33.0 MB in 4 bits, 0.5625 bytes per weight, 3.56 times fewer derived, 0.5 + 4/64.

measured on Apple M1 Pro GPU. Every kernel checked against a float64 product with the same dequantised weights. The last bar only reads the 4-bit codes (a sum over them), for scale.

  • Dequantise, then GEMV: 1.84 ms, twice the float16 GEMV (1.02 ms ours, 0.94 ms MLX): the worst of both.
  • Fused, one thread per row: 2.70 ms. Neighbouring threads read addresses a whole row (2 KB) apart: rung 1 of the hero again.
  • Fused, one SIMD-group (warp) per row, lane l reading 4-byte words l, l + 32, ...: 0.46 ms, 2.2 times the float16 GEMV. A further rung with 16-byte loads did not help (0.46 ms); MLX's mx.quantized_matmul took a median 0.67 ms with a best of 0.39 ms, noisy on a shared machine.

Why 2.2 times and not 3.56? Merely reading the codes takes 0.38 ms. Fitting time = t0 + bytes / bandwidth through that point and the float16 GEMV gives 139 GB/s and a fixed 0.17 ms per call derived, the launch-and-wait overhead the root measured; it predicts 0.41 ms for the fused kernel's bytes. So the fused kernel runs at the memory system's speed; the fixed cost of a launch is what keeps a 33 MB kernel from a 3.56× win. A decode step launches hundreds of such kernels, which is why engines capture them in CUDA graphs ({{streams and graphs page|n:3f05c17b0d0d81b19a6acab65c370b75}}).

What the NVIDIA compiler makes of the unpacking, and batches beyond one token (depth)

The same kernel in CUDA (src/cuda/kernels/g_dequant_gemv.cu, compiled) shows, per 4-byte word, a LOP3 (mask) and SHF (shift) per code and an I2FP (integer to float) per code, before the FFMA. It also shows a flaw we did not see in the source: the eight float16 activations per word are fetched with eight separate 2-byte loads (LDG.E.U16). Production kernels avoid both costs: they load activations in 16-byte vectors, and convert codes to half precision with bit tricks (PRMT and LOP3 on packed pairs) instead of one conversion per code.



With a batch of b tokens each weight is used b times, and the kernel turns into a matmul whose arithmetic eventually catches up with the saved bytes. Marlin (Frantar et al., {{2024|https://arxiv.org/abs/2408.11743}}) is a 4-bit-weight, 16-bit-activation kernel designed to keep the full win as long as possible: "batchsizes up to 16-32 can be supported with close to maximum (4×) quantization speedup", and up to 2.8 times end to end inside vLLM published. The quantisation formats themselves (GPTQ, AWQ, GGUF k-quants) are the {{quantization and precision page|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}'s and the C++ page's llama.cpp part; on this toy, 4 bits moved the output by up to 8.5% of its largest value against float16 weights measured (random weights, round-to-nearest, no calibration).









7. FlashAttention, step by step


FlashAttention is sections 1, 2, 4 and 5 composed: it tiles Q, K and V, computes each tile of scores S = QKT on chip, folds it into the output with the online-softmax merge of section 4, and never writes the N × N matrices S and P to memory. The paper page {{FlashAttention|n:3c65c17b0d0d81e4a3e8e7a2c4771381}} steps through the algorithm on a real input in its Run the kernel tab and follows FA-1 to FA-4 in Then and now; the topic root's Kernel lab builds a working FlashAttention-style Metal kernel. This section is what changed in each version and why, measured where the M1 can show it.


FlashAttention-2: three changes


The FlashAttention-2 paper ({{Dao, July 2023|https://arxiv.org/abs/2307.08691}}) starts from one number: an A100 does "312 TFLOPs/s of FP16/BF16 matmul, but only 19.5 TFLOPs/s of non-matmul FP32", so every non-matmul operation (the exponentials, the rescaling, the max) costs 16 matmul FLOPs published. It reports about 2× over FA-1 and 50 to 73% of peak on A100, from three changes:


    

  1. Fewer non-matmul operations. Keep the output unnormalised and divide by the running sum once, at the end, instead of rescaling it every tile; store one number per row for the backward pass, the logsumexp L = m + log ℓ, instead of both m and ℓ. The Kernel lab's kernel already works this way.
    2. 

  2. Parallelise over the sequence, not only batch × heads. FA-1 gave each (batch, head) pair one thread block, which loops over all query blocks; with long sequences and small batches, batch × heads is smaller than the 108 SMs of an A100 and most of the GPU idles. FA-2 gives each block of queries its own thread block. The same switch on the same kernel, 4 heads, d = 64:
    3. 





Log scale. "FA-1 grid": one threadgroup per head, 4 in all, for a GPU with 16 cores; "FA-2 grid": one per 64 query rows and head, 512 at N = 8,192. Same kernel, same arithmetic, measured on Apple M1 Pro GPU.


At N = 8,192 the FA-1 grid takes 214.54 ms and the FA-2 grid 30.62 ms, 7.0 times faster (2.24 TFLOP/s): four threadgroups cannot fill sixteen cores, and even a filled core needs several threadgroups to hide memory latency.


    

  1. Split Q across warps, not K. Inside one thread block of 4 warps, FA-1 split the K and V tile between warps ("split-K"), so each warp held a partial result for every query row and "all warps need to write their intermediate results out to shared memory, synchronize, then add up"; FA-2 splits Q, each warp owns its rows outright and reads all of K and V, with "no need for communication between warps". Split-K exchanges partial results through shared memory; split-Q never does






One block: 64 query rows, a tile of 64 keys and values per loop step (head dimension 128), 4 warps. Counts are values per loop iteration from the tile shapes alone, derived: split-Q reads 4 times more K and V from shared memory (every warp needs all of it) but never exchanges partial results. Which costs more on a real GPU depends on bandwidths the model does not have; FlashAttention-2 reports that removing the exchange gave a speedup ({{FA-2, section 3.3|https://arxiv.org/abs/2307.08691}}). Checked against src/fa_model.py.


Causal masks: skip, do not mask


In a decoder, query i may only attend to keys j ≤ i. Masking sets the forbidden scores to −∞ but still computes them; tiles wholly above the diagonal can instead be skipped. FA-2 reports "around 1.7-1.8× speedup compared to attention without the causal mask" published. With 64-row query blocks and 32-key tiles the work falls to (B + 1) / 2B of the tiles for B = N / 64 query blocks, an ideal 1.98× at N = 8,192 derived. Measured: masking only 30.42 ms (the same as no mask), skipping 16.98 ms, 1.79× measured on Apple M1 Pro GPU. Not quite 2×, because the blocks near the diagonal (more work) and far from it (less) now take very different times, so the last threadgroups run alone. MLX's own causal attention took 12.66 ms. FlashAttention-3's code answers the imbalance with "longest-processing-time-first scheduling: the longest remaining tile is assigned to the first SM that's free" ({{hopper/tile_scheduler.hpp|https://github.com/Dao-AILab/flash-attention/blob/main/hopper/tile_scheduler.hpp}}, read 2026-10-05).


FlashAttention-3: the exponentials become the bottleneck


On an H100 (Hopper) the tensor cores got faster than everything around them. The FlashAttention-3 paper ({{Shah et al., July 2024|https://arxiv.org/abs/2407.08608}}) gives the H100 SXM5 "989 TFLOPS for FP16 matmul versus 3.9 TFLOPS for special functions" (the units that compute exponentials), a ratio of 254 published. Each score costs 4d matmul FLOPs (2d for QKT, 2d for PV) and one exponential, so for d = 128 the exponentials take (1 / 3.9) / (512 / 989) = 50% of the matmul time derived, the paper's "exponential can take 50% of the cycle compared to matmul". Run one after the other, the tensor cores idle a third of the time. FA-3 overlaps them with Hopper's asynchronous hardware: ping-pong between two warpgroups (one runs its softmax while the other's GEMMs use the tensor cores) and pipelining inside one warpgroup (start the next tile's QKT before this tile's softmax is done). 0.5: H100, d = 128 (FA-3). About 1.0: tensor cores twice as fast, exponentials not (the Blackwell case FA-4 describes).






A list-scheduling model, derived and checked against src/fa_model.py: each iteration is GEMM0 (S = QKT), softmax, GEMM1 (O += PV); 8 tile iterations (one warpgroup does 8, two do 4 each); GEMMs one unit each, softmax r × 2 units; one tensor-core pipe and one exponential pipe; tasks in program order. It ignores loads (TMA producers hide them in FA-3), register limits and the rescaling work, and it is greedy: at a ratio of 1.0 it does worse with both techniques than with ping-pong alone, a reminder that FA-3's instruction order is tuned by hand.


On the real H100, ping-pong and pipelining are worth about 16% over neither (570 to 661 TFLOPS, FA-3's ablation below) published. None of this can be measured on the M1, which has no asynchronous matrix units.

FA-3's measured numbers published: ping-pong takes the FP16 forward "from approximately 570 TFLOPS to 620-640 TFLOPS" (head dimension 128, sequence 8,192); the ablation gives 661 TFLOPS with everything, 582 without the pipelining, 570 without warp specialisation (sequence 8,448 in that table). Headline: FP16 up to 740 TFLOPs/s, 75% of peak; FP8 close to 1.2 PFLOPs/s.

  • FP8: block-wise scales and "incoherent processing" (multiply Q and K by a random orthogonal Hadamard-based matrix, which spreads outliers) for "2.6× lower numerical error compared to per-tensor quantization".

FlashAttention-4. On a B200 the tensor cores doubled again while "other functional units (shared memory bandwidth, exponential units) scale more slowly or remain unchanged". FlashAttention-4 ({{Zadouri et al., 2026|https://arxiv.org/abs/2603.05451}}) answers with fully asynchronous MMA pipelines and larger tiles, exponentials partly computed in software on the FMA units, "conditional softmax rescaling" (skip the rescale when the running maximum barely moves), and tensor memory plus the 2-CTA MMA mode in the backward pass; up to 1,613 TFLOPs/s on B200 in BF16 (71%), 1.3× over cuDNN 9.13 published, written in the CuTe DSL in Python. Every generation is the same algorithm re-scheduled around whichever unit became the bottleneck.


The backward pass never stored P; it recomputes it tile by tile from Q, K and the saved logsumexp L: P = exp(S − L). FA-2's algorithm first computes D = rowsum(dO ∘ O) (one number per row), then per tile: dV += PT dO; dP = dO VT; dS = P ∘ (dP − D); dQ += dS K; dK += dST Q. It is parallelised over blocks of keys ("each worker takes care of a block of columns"), so several thread blocks add into the same rows of dQ, which FA-2 does "using atomic adds", the non-determinism of section 2 again published. Recomputing S costs about one more QKT; storing P would cost N2 numbers per head.




Decode: split the keys


Generating a token has one query per head against a long cache of keys and values. A FlashAttention grid over (batch, head, query block) then has batch × heads blocks: "with a batch size of 1, FlashAttention will use less than 1% of the GPU" (published, {{Flash-Decoding, Dao, Haziza, Massa and Sizov, October 2023|https://crfm.stanford.edu/2023/10/12/flashdecoding.html}}). Flash-Decoding splits the keys into chunks, runs the online softmax on each chunk in parallel, saves each chunk's (m, ℓ, partial output), and merges them with the section-4 rescaling in a tiny second kernel; it reports up to 8× faster generation for CodeLlama-34B at 64K context. We built it: 8 heads, d = 128, float16 cache, one query measured on Apple M1 Pro GPU.


Splitting the keys helps until S = 4; at exactly 65,536 keys, S = 8 falls off a cliff


At 65,536 tokens (268 MB of K and V), one threadgroup per head takes 3.85 ms; the best split (S = 4) 1.73 ms, 2.2×, the same as MLX's own (1.73 ms). And a surprise: S = 8 took 6.05 ms, slower than no split. With 65,536 keys per head, the 8 chunks of each head start exactly 2 MiB apart; with 512 more keys (66,048) the same kernel takes 1.82 ms at S = 8 against 5.22 at 65,536, three runs each. The likely cause is that concurrent reads spaced by a power of two land on the same memory channel or bank, since memory controllers pick a channel from address bits; we did not establish the M1's mapping, so treat this as a hypothesis unconfirmed. The lesson is general: sweep the split size and the problem size, because a performance cliff can sit at the exact power of two everyone benchmarks.
