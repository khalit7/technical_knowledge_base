The idea in one screen

A kernel is fast when every byte it fetches from slow memory is used as many times as possible while it sits on chip. Each optimisation step of every kernel on this page (coalescing, tiles in shared memory, tiles in registers, wider loads, fusion) either moves fewer bytes per useful operation, or stops a result from making a round trip through global memory.

One method for all of them: write the reference first (float64 NumPy or PyTorch) and a test with a tolerance chosen for the data type (section 8); write the obvious kernel, make it pass, and measure it against a ceiling (for a memory-bound kernel, the time a plain copy of the same bytes takes; for a compute-bound one, the peak arithmetic rate): the gap is what is left to win. Then find what limits it (a profiler on NVIDIA, see the profiling page; here, counting bytes and reading the compiled instructions), remove that limit, re-test, re-measure. Stop when you reach the ceiling or the library.

1. The matmul ladder: what each rung buys

C = AB for n × n matrices does 2n3 operations on 3n2 numbers, so each number loaded could in principle be used n times. Whether a kernel gets near that is a question of reuse. Boehm's worklog (December 2022) climbs from 309 to 21,779 GFLOP/s on an RTX A6000, 1.3% to 93.7% of cuBLAS, in ten kernels published; the hero above walks his rungs with the bytes each asks for. Read it as three moves, one per level of memory:

  • Coalesce (rung 2). The code of rungs 1 and 2 differs only in which thread index walks rows, and compiles to the same instructions (185 each for sm_90a, 29 FFMA, 58 global loads; 187 each for sm_80; for sm_120 the compiler unrolled them differently, 136 and 163, with the same loads per multiply-add) compiled. Coalescing, worth 6.4 times on Boehm's A6000, is invisible in the code: it is only about which addresses the 32 lanes of a warp touch at once. You find it with a profiler's sectors-per-request metric, or by thinking about threadIdx.x (the memory hierarchy page, section 1).
  • Tile into shared memory, then into registers (rungs 3 to 5). The ratio that rises is FFMA per shared load: 0.7 for plain tiles, 1.6 with a column of 8 outputs per thread, 8 with an 8 × 8 block per thread, because each shared value read into a register now feeds 8 multiply-adds. Shared-memory bandwidth, not global, limits rungs 3 and 4; registers are the next level of reuse.
  • Vectorise (rung 6). nvcc already vectorised rung 5's shared loads (32 of its 64 are LDS.128) before we asked. What the explicit float4 code bought is fewer instructions around them (1,047 down to 731: less address arithmetic, 16 STG instead of 64) and fewer registers (158 down to 127).

Registers decide how many blocks fit. With NVIDIA's allocation rules (registers per warp rounded up to 256, 64K per SM, as reproduced by the root's GPU simulator), 158 registers allow 12 warps per SM, one block of 8 warps; 127 registers allow 16 warps, two blocks derived. Two resident blocks let one block compute while the other waits at its barrier.

Beyond the CUDA-core ladder. Boehm's last rungs (autotuned tile sizes, then a warp-level tile) reach 93.7% of cuBLAS, and the final shape, block tile, then warp tile, then thread tile, is CUTLASS's. Real training matmuls replace the 8 × 8 FFMA block with tensor-core instructions (mma.sync, wgmma, tcgen05), which the libraries and tensor cores page compiles generation by generation, and load the next tile while computing this one (memory hierarchy page, section 6). The rule that does not change: count FLOPs per byte at each level of the hierarchy, and make it larger. Boehm's other observation also holds, and the M1 shows it (the 32 × 32 tile slower than 16 × 16, 36.48 against 26.90 ms): the best tile sizes differ from GPU to GPU, which is why every serious matmul library autotunes, and each rung's fix comes from profiling the previous one, not from a recipe.

2. Reductions: many numbers into one


Sum 225 (33.5 million) floats. On a CPU it is one loop. On a GPU, thousands of threads each do a part and then combine their parts, and combining is where every difficulty lives: threads in different blocks cannot see each other's shared memory or wait for each other inside one kernel launch. The shape of the answer is a tree: in step 1, half the threads each add two numbers; in step 2, a quarter add two partial sums; after log2(256) = 8 steps one thread holds the block's total. Each block writes its total, and a second, tiny launch (or an atomic add) combines the block totals.


Mark Harris's Optimizing Parallel Reduction in CUDA (NVIDIA, 2007) is the classic ladder: seven kernels for summing 4M integers on a G80, each fixing one problem, from 2.083 to 62.671 GB/s, 30.04 times faster, and 73 GB/s on 32M elements against the G80's 86.4 GB/s peak published. Its first three rungs differ only in which threads add which elements; play them on one input:

Each time includes MLX's per-call launch-and-wait overhead, which the topic root measured at about 0.2 ms (its section 1), so the kernels themselves are faster than shown and the differences between them larger in proportion.


Why the ladder flattened. In 2007 the G80 had little on-chip cache and slow integer arithmetic, so the index arithmetic, idle lanes and barriers of the early rungs cost more than the memory traffic. A modern GPU has far more arithmetic per byte of bandwidth (a higher ridge point), so a reduction is limited by reading the input almost however clumsily it combines it; the remaining gap is the 8 barriers per 256 values of R1 to R3. The lesson that survives: do most of the work in registers, one value per element, and make the tree as small as possible (a grid-stride loop: a fixed grid where each thread sums many elements in a register first). That is what every production reduction does.


Harris's seven rungs by name (depth)




1 Interleaved, divergentAt step s, threads with tid % (2s) == 0 add. Most lanes of every warp sit idle while the warp still issues.


2 Strided indexThread t works on element 2st: active threads are now contiguous, but their addresses are strided, so several lanes hit the same shared-memory bank (shared memory is split into 32 banks).


3 Sequential addressingHalve the range each step: thread t adds element t + s. Contiguous threads, contiguous addresses.


4 First add during loadHalf the blocks; each thread loads two values and adds them on the way in, so no thread starts idle.


5 Last warp unrolledThe last 32 values are summed by one warp. Harris did it with "warp-synchronous" shared memory; today you use shuffles (below).


6, 7 Unrolled, many per threadTemplates remove loop overhead; then the grid-stride loop, so the tree runs once per thread block, not once per 512 elements.





Inside a warp: shuffles


A shuffle moves a register value directly from one lane of a warp to another, with no shared memory and no barrier. Five of them sum 32 values; compiled for an H100 (sm_90a) compiled, it is exactly five shuffle-and-add pairs, and the mask 0xffffffff says all 32 lanes take part:


__device__ float warp_sum(float v) {
  for (int o = 16; o > 0; o >>= 1)
    v += __shfl_down_sync(0xffffffffu, v, o);   // add the value held by lane (lane + o)
  return v;                                     // lane 0 holds the sum of all 32
}


Since Volta (2017) the lanes of a warp are not guaranteed to run in lockstep, so old "warp-synchronous" code that reads other lanes' shared-memory writes without a barrier is a bug: use the *_sync shuffles or __syncwarp().


Correction to old habits: why "warp-synchronous" code broke (depth)
Harris's rung 5 relied on the 32 lanes of a warp executing in lockstep, reading each other's shared-memory writes with no barrier. Since Volta (2017), lanes of a warp can be scheduled independently, and NVIDIA's Volta tuning guide says plainly: "Assumptions that code is executed in lockstep or that reads/writes from separate threads are visible across a warp without synchronization are invalid." Use the *_sync shuffles, or __syncwarp() between shared-memory steps. Old tutorials (and old kernels) still contain the volatile trick.



Combining blocks


Four ways to turn one partial per block into one number: (1) a second, small launch that reduces the partials (R1 to R6 above); (2) every block does an atomic add of its partial into one output (A1: one launch, 1.05 ms); (3) the last block to finish, detected with an atomic counter, reduces all partials; (4) a cooperative launch, where grid.sync() makes every block wait for all the others (blocks must all be resident at once, which limits the grid size). PyTorch's own reduction kernel uses the third.


What PyTorch does, and a correction to the old page (depth)
PyTorch's Reduce.cuh keeps a global buffer and a semaphore per output when a reduction spans blocks (source excerpt in src/inputs/pytorch_extracts.txt, PyTorch main at commit 8d1d972, read 2026-10-05). The old page said "in library code use CUB (cub::BlockReduce, cub::DeviceReduce), which is what PyTorch does". For sums, PyTorch does not: torch.sum on CUDA calls its own gpu_reduce_kernel (ReduceSumProdKernel.cu). It does use CUB for a one-dimensional cumsum (section 3). CUB is still the right thing to call in your own CUDA code: cub::BlockReduce compiles to the same five shuffles per warp (Compiled for NVIDIA).



The order of additions changes the answer


Floating-point addition is not associative: (a + b) + c can differ from a + (b + c) in the last bits, so different orders give different sums.


The 225 inputs are uniform in [0, 1), so the exact sum is about 16.8 million. Add them one by one into a single float32 accumulator, in order. What comes out?




The running sum reaches 224 = 16,777,216, where float32's spacing between neighbouring numbers is 2, and from then on adding any value below 1 rounds back to the same number. Result 16,777,216, off by 495 from the float64 sum 16,777,711.32. The GPU tree gives 16,777,712, off by 0.68: a tree adds numbers of similar size at every level, which is why parallel reductions are usually more accurate than the sequential loop they replace measured on Apple M1 Pro GPU.


Atomics make the order, and so the bits, change from run to run. We ran the atomic kernel A1 30 times on the same input in each of the 3 runs: it gave 7, 6, 8 distinct results (from 16,777,702 to 16,777,718), because the blocks arrive in a different order each time; the two-launch tree gave one result every time measured on Apple M1 Pro GPU. This is why torch.use_deterministic_algorithms(True) exists, why two "identical" training runs drift apart, and why a test must compare with a tolerance rather than bit for bit (section 8).







3. Scan: running totals


An inclusive scan (prefix sum) turns x0, x1, x2, ... into x0, x0+x1, x0+x1+x2, ...; an exclusive scan shifts it by one and starts at 0. Every output depends on every earlier input, yet it is everywhere in model code: a mixture-of-experts layer counts how many tokens go to each expert and scans the counts to find where each expert's tokens start in a packed buffer; top-p sampling scans sorted probabilities; packing variable-length sequences scans their lengths into offsets; torch.cumsum is a scan. Two parallel algorithms (from GPU Gems 3, chapter 39, Harris, Sengupta and Owens), both in the last two modes of the widget in section 2:




Hillis and Steele
Step k: every element adds the one 2k places to its left. log2(n) steps, all elements busy, but O(n log n) additions: for n = 224, 386 million adds against 16.8 million for a loop derived, Σk<24(n − 2k). Fine inside a warp.


Blelloch (work-efficient)
An up-sweep builds a tree of partial sums (a reduction), a down-sweep pushes prefixes back down: "approximately 2 × (n − 1) adds and n − 1 swaps", 33.6 million for n = 224 derived, but twice the steps.




On a real GPU neither is used across the whole array. Inside a warp, a scan is five shuffles (__shfl_up_sync; Metal's simd_prefix_exclusive_sum); across a block, warps exchange totals through shared memory; across blocks is the hard part, because block 7 needs the total of blocks 0 to 6. Reduce, then scan takes three launches: (a) each block sums its tile; (b) one block scans the tile sums into offsets; (c) each block scans its tile again and adds its offset. The input is read twice and the output written once: 3 passes over memory, against 2 for a copy. Decoupled look-back does it in one pass (it is how cub::DeviceScan works; details below; not run here).




On 224 floats measured on Apple M1 Pro GPU, Hillis and Steele over the whole array, 24 launches each reading and writing everything, takes 18.81 ms; the three-launch scan 1.41 ms, 13.4 times faster and 1.41 times a plain copy (1.00 ms), close to the 3 : 2 ratio of passes that counting bytes predicts. MLX's library mx.cumsum took 7.78 ms on the same input, 5.5 times slower than our 40 lines (code in Kernel bench (M1)): libraries are not always at the ceiling, and the copy time tells you when they are not.


Decoupled look-back, and what PyTorch calls (depth)


Decoupled look-back (Merrill and Garland, NVIDIA, 2016) scans in one launch: each block publishes its own total as soon as it has it, and its inclusive prefix once it knows it; a block that needs its offset looks back at its predecessors' published values, summing totals until it meets a published prefix. It "requires only ~2n data movement" and its throughput "approaches that of copy operations" published. It relies on earlier blocks making progress while later ones wait, a guarantee Metal does not document, so we did not run it here.


In PyTorch, a one-dimensional torch.cumsum on CUDA calls cub::inclusive_scan, and a separate inclusive_deterministic_scan for floating-point types when deterministic algorithms are requested (ScanUtils.cuh, read 2026-10-05): the default single-pass scan can add in an order that depends on timing, for the same reason as the atomic sum of section 2.








4. Row normalisation: softmax, LayerNorm, RMSNorm


Softmax, LayerNorm and RMSNorm all do the same thing to each row of a matrix: compute one or two statistics of the row (a reduction), then rewrite every element using them. In a transformer the rows are tokens and a row is a few thousand numbers, so the standard layout is one block per row, the row's elements spread over the block's threads, each thread keeping its share in registers between the statistics and the rewrite, so the row is read from memory once and written once. Arithmetic is a handful of operations per element; the speed is set by bytes.


The softmax ladder: one change matters


One threadgroup per row instead of one thread is worth 50 times; every later rung stays within 13% of a plain copy




The topic root's Kernel lab, 16,384 rows of 4,096 float32 (256 MiB in, 256 MiB out), median of 3 runs, measured on Apple M1 Pro GPU; data copied to src/inputs/root_kernel_lab_matmul.json. A plain copy of the same bytes at the lab's 164.7 GB/s takes 3.26 ms derived, 512 MiB / 164.7 GB/s.


One thread per row (S1) takes 177.14 ms: neighbouring threads read addresses a whole row (16 KB) apart. One threadgroup per row with neighbouring threads on neighbouring elements (S2) takes 3.54 ms, 50 times faster, already at 92% of copy speed. SIMD-group reductions, float4 loads, the online softmax (two passes) and the row held in registers (one pass, S6, 3.27 ms) are worth about 8% together, and the five-kernel eager version takes 13.08 ms (10.09 under mx.compile). S2 reads each row three times yet runs near copy speed, most likely because a 16 KB row is still in cache when it is re-read unconfirmed, not profiled. The idea to carry forward is the online softmax (Milakov and Gimelshein, 2018): keep a running maximum m and a running sum d of ex − m; when a larger value arrives, rescale the sum you have.


m′ = max(m, xi)    d′ = d · em − m′ + exi − m′


merge (ma, da) with (mb, db): m = max(ma, mb),   d = da ema − m + db emb − m


The second line makes it a parallel algorithm: any two partial results, from two lanes, two warps or two tiles, combine exactly, in any order. Every reduction on this page that is more than a sum needs such a merge, and FlashAttention (section 7) is built on this one.


LayerNorm: the variance is a numerical trap


LayerNorm subtracts the row's mean μ and divides by its standard deviation σ: y = (x − μ) / √(σ2 + ε) · γ + β. The tempting one-pass formula for the variance, σ2 = E[x2] − E[x]2, subtracts two large, nearly equal numbers when the mean is large compared with the spread, and float32 keeps only about 7 significant digits.


Rows of 4,096 float32 values with standard deviation 1 and mean 3,000. Our kernel computes the variance as E[x2] − E[x]2. How wrong is the normalised output (largest error against float64)?




Largest error 1,653. E[x2] is about 9 million, where float32's spacing is 1, so the difference that should be 1 is rounding noise, often 0 or negative (clamped to 0), and dividing by √ε instead of 1 multiplies everything by about 316. The two-pass kernel (mean first, then the mean of (x − μ)2 from the values still in registers) errs by 6.3e-04, Welford's by 6.0e-04 measured on Apple M1 Pro GPU.

Welford's algorithm keeps a count n, a mean and M2 (the sum of squared deviations), updating them per value; partial results merge with the pairwise formula of Chan, Golub and LeVeque (the parallel algorithm, summarised), which has exactly the shape of the online-softmax merge:

Welford matters when the row is streamed once from memory, as in a long row or a fused kernel that cannot keep it.




RMSNorm, fused with the residual add


RMSNorm drops the mean: y = x / √(mean(x2) + ε) · γ. In a pre-norm transformer block it always follows a residual add, h = x + r, and h is needed twice: normalised for the next layer, and raw as the next residual. Count the passes before writing the kernel:


Fusing the add into the norm saves one pass over the activations: 5 become 4


So at best 5 : 4 = 1.25 times faster derived. Measured: 4.03 ms for MLX's add then mx.fast.rms_norm (4.09 ms under mx.compile, which did not fuse them), 3.35 ms fused, 1.20 times measured on Apple M1 Pro GPU. Production engines ship exactly this kernel: vLLM declares fused_add_rms_norm(input, residual, weight, epsilon) next to its plain rms_norm (csrc/ops.h, read 2026-10-05). The best case is set by the byte count before you start.







5. Fusion: keep it on chip


Two kernels in a row hand their intermediate result over through global memory: the first writes it, the second reads it back. A fused kernel does both while the intermediate is in registers or shared memory. Fusion pays exactly when that round trip is a large part of the time, which gives three rules: chains of memory-bound operations (elementwise, norms) fuse to nearly the cost of one (the RMSNorm above); a cheap operation applied to a matmul's output while it is still in registers (an epilogue) or to its input as it is loaded (a prologue) removes one round trip of that matrix; and fusing work into a compute-bound loop can lose, because the loop was not waiting for memory in the first place. All three measured, with real mistakes along the way.


Epilogue: matmul, bias, GELU


y = GELU(xW + b) for 4,096 tokens, 4,096 outputs, K = 1,024 or 256 inputs, float32. Unfused, the matmul writes C (64 MiB) and a second kernel reads it, adds b, applies GELU and writes y: 134 MB of extra traffic, about 0.9 ms at this GPU's copy speed derived. Our fused kernel is the Kernel lab's fastest matmul (8 × 8 matrix instructions, 64 × 64 tile per threadgroup) with the epilogue added. Three attempts, K = 1,024 measured on Apple M1 Pro GPU:




    

  1. Stage the whole tile in shared memory, then apply the epilogue: 13.76 ms, slower than not fusing (10.71 ms). The 16 KB staging buffer tripled the kernel's threadgroup memory (8 KB to 24 KB), so fewer threadgroups fit on each GPU core for the whole matmul, not just the epilogue: the occupancy cliff the hardware topic measured on this GPU (GPU architecture). Shared memory is not free.
    2. 

  2. Apply it to the accumulator registers directly, then store as the plain matmul does. Each lane of a SIMD-group holds 2 of the 64 values of every 8 × 8 accumulator; which two is fixed by the hardware, and we read the mapping from MLX's own kernels (steel/gemm/mma.h, get_coord). With the accurate precise::tanh: 11.40 ms, still slower. In the separate kernel, GELU's arithmetic hid behind memory traffic; inside the matmul it is added to a compute-bound kernel's time (on NVIDIA the same choice is -use_fast_math or intrinsics such as __expf; check the error you accept).

  3. Same, with fast::tanh (it differs from the precise version by at most 5 × 10−7, a side experiment in src/m1/out/side_experiments.txt): 10.07 ms against 9.92 ms for the matmul alone. Where epilogues live in NVIDIA's libraries, CUTLASS and Triton (depth)
On NVIDIA you rarely write this epilogue yourself: cuBLASLt takes it as a parameter (CUBLASLT_EPILOGUE_GELU_BIAS, "apply Bias and then GELU transform", plus _AUX variants that also save GELU's input for the backward pass and DGELU for the backward itself; cublasLt.h in CUDA 13.4.2, excerpt in src/inputs/), and CUTLASS composes epilogues as trees of operations on the accumulator fragments (its epilogue visitor trees), exactly what attempt 3 does by hand; in Triton you write the epilogue as ordinary code after the tl.dot loop (Triton and Gluon page). Fusing two compute-bound matmuls into one kernel rarely pays: the tensor cores are already busy, and holding both operands raises register pressure.


Prologue: RMSNorm into the next matmul


rmsnorm(x)W = diag(1/rms(x)) · x · (diag(γ)W). Fold γ into W once, offline; the matmul loads every element of each row of x anyway, so it can accumulate the row's sum of squares as the tiles go by, and scale each output row by 1/rms(x) in the epilogue. The normalised x is never written. A neat identity; did it pay measured on Apple M1 Pro GPU?

6. Decode: a matrix times one vector, with 4-bit weights


When a model generates one token for one user, every linear layer multiplies its weight matrix by a single vector: a GEMV. Each weight is read once and used once, so the time is the bytes of the weights divided by memory bandwidth, and the only way to go faster is to read fewer bytes. That is why decode-time weights are stored in 4 bits. But the GPU cannot multiply 4-bit codes directly; they must be dequantised (code × scale + bias, per group of weights). Do it as a separate kernel and you write a full 16-bit copy of the matrix and read it back, three times the bytes you hoped to save. Do it inside the GEMV, in registers, and only the 4-bit bytes cross the memory bus.


The shape is one MLP projection of Llama 3 8B, 14,336 × 4,096, in MLX's own 4-bit format (groups of 64 weights, a float16 scale and bias per group): 117.4 MB in float16, 33.0 MB in 4 bits, 0.5625 bytes per weight, 3.56 times fewer derived, 0.5 + 4/64.




measured on Apple M1 Pro GPU. Every kernel checked against a float64 product with the same dequantised weights. The last bar only reads the 4-bit codes (a sum over them), for scale.


    

  • Dequantise, then GEMV: 1.84 ms, twice the float16 GEMV (1.02 ms ours, 0.94 ms MLX): the worst of both.
    • 

  • Fused, one thread per row: 2.70 ms. Neighbouring threads read addresses a whole row (2 KB) apart: rung 1 of the hero again.
    • 

  • Fused, one SIMD-group (warp) per row, lane l reading 4-byte words l, l + 32, ...: 0.46 ms, 2.2 times the float16 GEMV. A further rung with 16-byte loads did not help (0.46 ms); MLX's mx.quantized_matmul took a median 0.67 ms with a best of 0.39 ms, noisy on a shared machine.
    • 



Why 2.2 times and not 3.56? Merely reading the codes takes 0.38 ms. Fitting time = t0 + bytes / bandwidth through that point and the float16 GEMV gives 139 GB/s and a fixed 0.17 ms per call derived, the launch-and-wait overhead the root measured; it predicts 0.41 ms for the fused kernel's bytes. So the fused kernel runs at the memory system's speed; the fixed cost of a launch is what keeps a 33 MB kernel from a 3.56× win. A decode step launches hundreds of such kernels, which is why engines capture them in CUDA graphs (streams and graphs page).


What the NVIDIA compiler makes of the unpacking, and batches beyond one token (depth)


The same kernel in CUDA (src/cuda/kernels/g_dequant_gemv.cu, compiled) shows, per 4-byte word, a LOP3 (mask) and SHF (shift) per code and an I2FP (integer to float) per code, before the FFMA. It also shows a flaw we did not see in the source: the eight float16 activations per word are fetched with eight separate 2-byte loads (LDG.E.U16). Production kernels avoid both costs: they load activations in 16-byte vectors, and convert codes to half precision with bit tricks (PRMT and LOP3 on packed pairs) instead of one conversion per code.




With a batch of b tokens each weight is used b times, and the kernel turns into a matmul whose arithmetic eventually catches up with the saved bytes. Marlin (Frantar et al., 2024) is a 4-bit-weight, 16-bit-activation kernel designed to keep the full win as long as possible: "batchsizes up to 16-32 can be supported with close to maximum (4×) quantization speedup", and up to 2.8 times end to end inside vLLM published. The quantisation formats themselves (GPTQ, AWQ, GGUF k-quants) are the quantization and precision page's and the C++ page's llama.cpp part; on this toy, 4 bits moved the output by up to 8.5% of its largest value against float16 weights measured (random weights, round-to-nearest, no calibration).









7. FlashAttention, step by step


FlashAttention is sections 1, 2, 4 and 5 composed: it tiles Q, K and V, computes each tile of scores S = QKT on chip, folds it into the output with the online-softmax merge of section 4, and never writes the N × N matrices S and P to memory. The paper page FlashAttention steps through the algorithm on a real input in its Run the kernel tab and follows FA-1 to FA-4 in Then and now; the topic root's Kernel lab builds a working FlashAttention-style Metal kernel. This section is what changed in each version and why, measured where the M1 can show it.


FlashAttention-2: three changes


The FlashAttention-2 paper (Dao, July 2023) starts from one number: an A100 does "312 TFLOPs/s of FP16/BF16 matmul, but only 19.5 TFLOPs/s of non-matmul FP32", so every non-matmul operation (the exponentials, the rescaling, the max) costs 16 matmul FLOPs published. It reports about 2× over FA-1 and 50 to 73% of peak on A100, from three changes:


    

  1. Fewer non-matmul operations. Keep the output unnormalised and divide by the running sum once, at the end, instead of rescaling it every tile; store one number per row for the backward pass, the logsumexp L = m + log ℓ, instead of both m and ℓ. The Kernel lab's kernel already works this way.
    2. 

  2. Parallelise over the sequence, not only batch × heads. FA-1 gave each (batch, head) pair one thread block, which loops over all query blocks; with long sequences and small batches, batch × heads is smaller than the 108 SMs of an A100 and most of the GPU idles. FA-2 gives each block of queries its own thread block. The same switch on the same kernel, 4 heads, d = 64:
    3. 





Log scale. "FA-1 grid": one threadgroup per head, 4 in all, for a GPU with 16 cores; "FA-2 grid": one per 64 query rows and head, 512 at N = 8,192. Same kernel, same arithmetic, measured on Apple M1 Pro GPU.


At N = 8,192 the FA-1 grid takes 214.54 ms and the FA-2 grid 30.62 ms, 7.0 times faster (2.24 TFLOP/s): four threadgroups cannot fill sixteen cores, and even a filled core needs several threadgroups to hide memory latency.


    

  1. Split Q across warps, not K. Inside one thread block of 4 warps, FA-1 split the K and V tile between warps ("split-K"), so each warp held a partial result for every query row and "all warps need to write their intermediate results out to shared memory, synchronize, then add up"; FA-2 splits Q, each warp owns its rows outright and reads all of K and V, with "no need for communication between warps". Step one loop iteration both ways:

Split-K exchanges partial results through shared memory; split-Q never does






One block: 64 query rows, a tile of 64 keys and values per loop step (head dimension 128), 4 warps. Counts are values per loop iteration from the tile shapes alone, derived: split-Q reads 4 times more K and V from shared memory (every warp needs all of it) but never exchanges partial results. Which costs more on a real GPU depends on bandwidths the model does not have; FlashAttention-2 reports that removing the exchange gave a speedup (FA-2, section 3.3). Checked against src/fa_model.py.


Causal masks: skip, do not mask


In a decoder, query i may only attend to keys j ≤ i. Masking sets the forbidden scores to −∞ but still computes them; tiles wholly above the diagonal can instead be skipped. FA-2 reports "around 1.7-1.8× speedup compared to attention without the causal mask" published. With 64-row query blocks and 32-key tiles the work falls to (B + 1) / 2B of the tiles for B = N / 64 query blocks, an ideal 1.98× at N = 8,192 derived. Measured: masking only 30.42 ms (the same as no mask), skipping 16.98 ms, 1.79× measured on Apple M1 Pro GPU. Not quite 2×, because the blocks near the diagonal (more work) and far from it (less) now take very different times, so the last threadgroups run alone. MLX's own causal attention took 12.66 ms. FlashAttention-3's code answers the imbalance with "longest-processing-time-first scheduling: the longest remaining tile is assigned to the first SM that's free" (hopper/tile_scheduler.hpp, read 2026-10-05).


FlashAttention-3: the exponentials become the bottleneck


On an H100 (Hopper) the tensor cores got faster than everything around them. The FlashAttention-3 paper (Shah et al., July 2024) gives the H100 SXM5 "989 TFLOPS for FP16 matmul versus 3.9 TFLOPS for special functions" (the units that compute exponentials), a ratio of 254 published. Each score costs 4d matmul FLOPs (2d for QKT, 2d for PV) and one exponential, so for d = 128 the exponentials take (1 / 3.9) / (512 / 989) = 50% of the matmul time derived, the paper's "exponential can take 50% of the cycle compared to matmul". Run one after the other, the tensor cores idle a third of the time. FA-3 overlaps them with Hopper's asynchronous hardware: ping-pong between two warpgroups (one runs its softmax while the other's GEMMs use the tensor cores) and pipelining inside one warpgroup (start the next tile's QKT before this tile's softmax is done). Predict which keeps the tensor cores busier, then step:


Overlapping softmax with the GEMMs keeps the tensor cores busy




0.5: H100, d = 128 (FA-3). About 1.0: tensor cores twice as fast, exponentials not (the Blackwell case FA-4 describes).






A list-scheduling model, derived and checked against src/fa_model.py: each iteration is GEMM0 (S = QKT), softmax, GEMM1 (O += PV); 8 tile iterations (one warpgroup does 8, two do 4 each); GEMMs one unit each, softmax r × 2 units; one tensor-core pipe and one exponential pipe; tasks in program order. It ignores loads (TMA producers hide them in FA-3), register limits and the rescaling work, and it is greedy: at a ratio of 1.0 it does worse with both techniques than with ping-pong alone, a reminder that FA-3's instruction order is tuned by hand.


On the real H100, ping-pong and pipelining are worth about 16% over neither (570 to 661 TFLOPS, FA-3's ablation below) published. None of this can be measured on the M1, which has no asynchronous matrix units.


FA-3's measured numbers and other machinery, FlashAttention-4 on Blackwell, and the backward pass (depth)


FA-3's measured numbers published: ping-pong takes the FP16 forward "from approximately 570 TFLOPS to 620-640 TFLOPS" (head dimension 128, sequence 8,192); the ablation gives 661 TFLOPS with everything, 582 without the pipelining, 570 without warp specialisation (sequence 8,448 in that table). Headline: FP16 up to 740 TFLOPs/s, 75% of peak; FP8 close to 1.2 PFLOPs/s.


    

  • Warp specialisation: producer warps only issue TMA copies (the tensor memory accelerator, which moves whole tiles from global to shared memory by itself), consumer warpgroups (4 warps each) only compute, and setmaxnreg moves registers from producers to consumers.
    • 

  • FP8: block-wise scales and "incoherent processing" (multiply Q and K by a random orthogonal Hadamard-based matrix, which spreads outliers) for "2.6× lower numerical error compared to per-tensor quantization".
    • 



FlashAttention-4. On a B200 the tensor cores doubled again while "other functional units (shared memory bandwidth, exponential units) scale more slowly or remain unchanged". FlashAttention-4 (Zadouri et al., 2026) answers with fully asynchronous MMA pipelines and larger tiles, exponentials partly computed in software on the FMA units, "conditional softmax rescaling" (skip the rescale when the running maximum barely moves), and tensor memory plus the 2-CTA MMA mode in the backward pass; up to 1,613 TFLOPs/s on B200 in BF16 (71%), 1.3× over cuDNN 9.13 published, written in the CuTe DSL in Python. Every generation is the same algorithm re-scheduled around whichever unit became the bottleneck.


The backward pass never stored P; it recomputes it tile by tile from Q, K and the saved logsumexp L: P = exp(S − L). FA-2's algorithm first computes D = rowsum(dO ∘ O) (one number per row), then per tile: dV += PT dO; dP = dO VT; dS = P ∘ (dP − D); dQ += dS K; dK += dST Q. It is parallelised over blocks of keys ("each worker takes care of a block of columns"), so several thread blocks add into the same rows of dQ, which FA-2 does "using atomic adds", the non-determinism of section 2 again published. Recomputing S costs about one more QKT; storing P would cost N2 numbers per head.




Decode: split the keys


Generating a token has one query per head against a long cache of keys and values. A FlashAttention grid over (batch, head, query block) then has batch × heads blocks: "with a batch size of 1, FlashAttention will use less than 1% of the GPU" (published, Flash-Decoding, Dao, Haziza, Massa and Sizov, October 2023). Flash-Decoding splits the keys into chunks, runs the online softmax on each chunk in parallel, saves each chunk's (m, ℓ, partial output), and merges them with the section-4 rescaling in a tiny second kernel; it reports up to 8× faster generation for CodeLlama-34B at 64K context. We built it: 8 heads, d = 128, float16 cache, one query measured on Apple M1 Pro GPU.


Splitting the keys helps until S = 4; at exactly 65,536 keys, S = 8 falls off a cliff


At 65,536 tokens (268 MB of K and V), one threadgroup per head takes 3.85 ms; the best split (S = 4) 1.73 ms, 2.2×, the same as MLX's own (1.73 ms). And a surprise: S = 8 took 6.05 ms, slower than no split. With 65,536 keys per head, the 8 chunks of each head start exactly 2 MiB apart; with 512 more keys (66,048) the same kernel takes 1.82 ms at S = 8 against 5.22 at 65,536, three runs each. The likely cause is that concurrent reads spaced by a power of two land on the same memory channel or bank, since memory controllers pick a channel from address bits; we did not establish the M1's mapping, so treat this as a hypothesis unconfirmed. The lesson is general: sweep the split size and the problem size, because a performance cliff can sit at the exact power of two everyone benchmarks. Paged KV caches, GQA and serving-side scheduling are the inference and serving topic's.






8. Testing a kernel against a reference


A fast wrong kernel is worse than a slow right one, and GPU bugs hide: they appear at one size, one in a hundred runs, or only after a different kernel ran first. Every kernel on this page went through the same harness before it was timed: run it, compare with a float64 reference computed by NumPy, fail if the largest error exceeds a tolerance. That harness still let one bug through.


A kernel that wrote nothing passed the test
Our first standalone RMSNorm kernel computed its loop count as C / 4 / 256, which is 0 for rows of 256 floats: it wrote nothing at all. The check passed, error 4 × 10−6 (the log line is kept in src/m1/out/side_experiments.txt). The output buffer the kernel received was, most likely, memory MLX's allocator had just freed after the library's own RMSNorm of the same shape, still holding the right answer. Two cheap defences: poison the output (fill it with NaN before the kernel runs, or make sure it is fresh memory; our harness now empties MLX's buffer cache before every check) and run the reference path after, not before, the kernel under test, so it cannot leave its answer behind. The fixed kernel then passed for the right reason. The topic root's Kernel lab kept a second lesson: a barrier that was too weak (simdgroup_barrier where a threadgroup barrier was needed) gave 1 to 5 wrong rows out of 4,096 at random, and every small test passed. Test at the real size, and repeat.


Choosing the tolerance. torch.testing.assert_close passes when |actual − expected| ≤ atol + rtol · |expected|, with defaults per data type (_comparison.py, read 2026-10-05; table below). These are right for one rounding, not for a sum of thousands of terms, whose error grows with the length of the sum. A practical rule: compute the reference in float64, measure the error of a trusted implementation in your precision against it, and require your kernel's error to be within a small factor of that. Our matmuls in float32 erred by up to 8 × 10−6 against float64, like MLX's; the 4-bit GEMV by 9 × 10−4 against the product with the same dequantised weights, and by far more (section 6) against the unquantised weights, which is a different question (does quantisation hurt the model?) and needs a different test (evaluation).


Tools. On NVIDIA, compute-sanitizer's initcheck would have caught our RMSNorm bug, and racecheck a missing barrier (details below). Timing honestly (warm-up, medians, L2 flushing, CUDA events) is section 2 of Profiling, benchmarking and correctness; the closed workbench in its section 5 shows why a reordered sum or an atomic changes the last digits and which tolerance fits each data type.


The four sanitizer tools, PyTorch's default tolerances, and inputs that break kernels (depth)


compute-sanitizer (shipped with the toolkit) has four tools, from its own help text (CUDA 13.4.2): memcheck ("Memory access checking", the default: out-of-bounds and misaligned accesses), racecheck ("Shared memory hazard checking": a missing __syncthreads()), synccheck ("Synchronization checking": a barrier only some threads reach) and initcheck ("Global memory initialization checking": reading memory nobody wrote, which would have caught our RMSNorm bug). They slow a kernel by large factors, so run them on small inputs in CI.

Depth: rehearsal and a path to practise


Interview questions, with short answers (optional)


Why is a reduction memory-bound, and what is its ceiling?
One add per 4-byte element is far below any GPU's ridge point; the ceiling is the time to read the input once. On the M1 the first rung read at 83 GB/s and the last at 133 GB/s, against about 143 GB/s for a plain read measured by the hardware topic's Roofline lab.


Write a warp sum. Why the mask argument?
Five __shfl_down_sync(0xffffffff, v, o) for o = 16, 8, 4, 2, 1. The mask names the lanes that participate and must all reach the call; it exists because lanes are scheduled independently since Volta.


Hillis-Steele or Blelloch?
Hillis-Steele: log n steps, O(n log n) adds, fine inside a warp. Blelloch: O(n) adds, 2 log n steps, good for large arrays in shared memory. Across the GPU, a tiled scan with decoupled look-back reads and writes each element once (CUB).


Walk a naive matmul up to a register-tiled one. What does each step buy?
Coalesce (lanes on neighbouring columns: 8 bytes asked per FMA, 5 moved instead of 33); tile into shared memory (global traffic 32 times lower, shared reads now the limit); tile into registers (each shared value feeds 8, then 64 FMAs); vectorise (fewer instructions and registers, so more blocks per SM). Then warp tiles, autotuning and tensor cores (section 1).


A 4-bit GEMV is only 2× faster than float16, not 4×. Why might that be?
Fixed launch overhead dominates small kernels (0.17 ms here), dequantisation instructions or scalar activation loads can make it instruction-bound, and scales and biases add bytes (0.5625 bytes per weight here). Measure the read of the bytes alone first.


When does fusion not help?
When the intermediate's round trip is a small share of the time (compute-bound kernels), when it raises register or shared-memory use and cuts occupancy, or when the compiler already fused it.

Best resources




Simon Boehm, How to Optimize a CUDA Matmul Kernel for cuBLAS-like Performance 1 h 30 min
The canonical worked example, ten kernels from 1.3% to 93.7% of cuBLAS on an RTX A6000 (December 2022). Read it, then reproduce it.


salykova, Advanced Matrix Multiplication Optimization on NVIDIA GPUs 1 h 30 min
The sequel: vectorisation, double buffering and autotuning, beating cuBLAS SGEMM on an RTX 4090 by the author's account.


Mark Harris, Optimizing Parallel Reduction in CUDA 45 min
The seven-step reduction deck (2007). Read rung 5 with the Volta correction of section 2 in mind.


Programming Massively Parallel Processors, 5th edition 2 h 15 min
Hwu, Kirk and El Hajj: chapter 6 (tiled matmul), chapters 10 and 11 (reduction, scan), later chapters for patterns.


GPU Gems 3, chapter 39: Parallel Prefix Sum (Scan) with CUDA 40 min
Harris, Sengupta and Owens: Hillis-Steele, Blelloch, bank-conflict padding.


Merrill and Garland, Single-pass Parallel Prefix Scan with Decoupled Look-back 45 min
The algorithm inside CUB's DeviceScan (NVIDIA, 2016).


CCCL (CUB, Thrust, libcu++) 20 min
Block- and device-wide reduce, scan, sort and histogram you call instead of writing; source at NVIDIA/cccl.


FlashAttention-2 · FlashAttention-3 · FlashAttention-4 1 h each
Work partitioning; Hopper asynchrony and FP8; Blackwell's asymmetric scaling. Code: Dao-AILab/flash-attention.


Flash-Decoding for long-context inference 15 min
Split-KV decode explained with animations (Dao, Haziza, Massa, Sizov, 2023).


Triton tutorial: fused softmax · fused attention 30 min each
The two kernels of the path's last steps, as reference solutions.


Marlin 45 min
Frantar et al., 2024: 4-bit weight kernels that keep the speedup up to batch 16 to 32.


GPU MODE lectures 3 h for lectures 8 and 12
Lecture 8 (CUDA performance checklist), lecture 12 (FlashAttention), and guest lectures by kernel authors.


Compute Sanitizer · cuBLAS and cuBLASLt 20 min each
The four sanitizer tools of section 8; the epilogue options of section 5.
