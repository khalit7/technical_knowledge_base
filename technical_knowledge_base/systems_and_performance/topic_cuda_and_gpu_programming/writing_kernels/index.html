Writing kernels: reductions, softmax, tiled matmul, fusion, FlashAttention

The practical track of Topic: cuda-and-gpu-programming: the handful of patterns almost every kernel in a transformer is built from, each written, tested and measured, from a sum of numbers to FlashAttention. Measured on an Apple M1 Pro GPU and compiled for NVIDIA GPUs without one; every number says which. Data as of October 2026.

Almost every GPU kernel inside a transformer is one of a handful of patterns: an elementwise map, a reduction (many numbers into one), a scan (running totals), a row normalisation (softmax, LayerNorm, RMSNorm), a tiled matrix multiply, and fusions of these, of which FlashAttention is the famous one. This page writes each of them, tests it against a float64 reference, measures it, and climbs its optimisation ladder, so that you can write the next one yourself and read the ones in FlashAttention, CUTLASS, llama.cpp or vLLM.

It assumes the vocabulary of the topic root: a thread runs your kernel function once; 32 threads form a warp that issues one instruction at a time; warps are grouped into a block that shares a small fast shared memory and can wait at a barrier (__syncthreads()); blocks run on SMs (streaming multiprocessors) and talk to each other only through the large slow global memory (HBM on a datacenter GPU). If any of those is shaky, the root's section 2 and the programming model page build them up; coalescing, bank conflicts and registers are the memory hierarchy page's.

What is real on this page
There is no NVIDIA GPU here. Every timing was measured on Apple M1 Pro GPU: a real SIMT GPU whose SIMD-groups of 32 threads, threadgroups and threadgroup memory are a warp, a block and shared memory under other names; the kernels are Metal, run through MLX 0.32.3, each checked against float64 before it is timed, 3 runs of 7 trials, median shown, with the machine's load average recorded for every case (other work shared the laptop; the Kernel bench (M1) tab shows the spread). NVIDIA behaviour comes from compiled output (CUDA 13.4.2, the same kernels in CUDA C++, built for sm_80, sm_90a and sm_120 in a container without a GPU: registers, shared memory, instruction mix) and from published papers and talks, each cited. Arithmetic on these is derived, with its formula. What transfers from the M1 is the shape of each result; the absolute speeds do not.

And one method for all of them, used in every section below:

  1. Write the reference first, in float64 NumPy or PyTorch, and a test that compares against it with a tolerance chosen for the data type (section 8).
  2. Write the obvious kernel, make it pass, and measure it against a ceiling: for a memory-bound kernel, the time a plain copy of the same bytes takes; for a compute-bound one, the peak arithmetic rate. The gap is what is left to win.
  3. Find what limits it (a profiler on NVIDIA, see the profiling page; here, counting bytes and reading the compiled instructions), remove that limit, re-test, re-measure. Stop when you reach the ceiling or the library.

1. Reductions: many numbers into one

The problem. Sum 225 (33.5 million) floats. On a CPU it is one loop. On a GPU, thousands of threads must each do a part and then combine their parts, and combining is where every difficulty lives: threads in different blocks cannot see each other's shared memory or wait for each other inside one kernel launch.

The shape of the answer. A tree: in step 1, half the threads each add two numbers; in step 2, a quarter add two partial sums; after log2(256) = 8 steps one thread holds the block's total. Each block writes its total, and a second, tiny launch (or an atomic add) combines the block totals. The Reduce and scan, animated tab runs the tree step by step on one input in four variants, with counters for idle lanes and bank conflicts.

Harris's ladder, and what is left of it

Mark Harris's Optimizing Parallel Reduction in CUDA (NVIDIA, 2007) is the classic warm-up: seven kernels for summing 4M integers on a G80, each fixing one problem, from 2.083 to 62.671 GB/s, 30.04 times faster, and 73 GB/s on 32M elements against the G80's 86.4 GB/s peak published. The rungs are worth knowing by name because the problems are still real:

1 Interleaved, divergentAt step s, threads with tid % (2s) == 0 add. Most lanes of every warp sit idle while the warp still issues: divergence (lanes of one warp taking different branches, run one after the other).
2 Strided indexThread t works on element 2st: active threads are now contiguous, but their addresses are strided, so several lanes hit the same shared-memory bank (shared memory is split into 32 banks; lanes hitting the same bank wait in turn).
3 Sequential addressingHalve the range each step: thread t adds element t + s. Contiguous threads, contiguous addresses.
4 First add during loadHalf the blocks; each thread loads two values and adds them on the way in, so no thread starts idle.
5 Last warp unrolledThe last 32 values are summed by one warp. Harris did it with "warp-synchronous" shared memory; today you use shuffles (below).
6, 7 Unrolled, many per threadTemplates remove loop overhead; then a fixed grid where each thread sums many elements in a register first (a grid-stride loop), so the tree runs once per thread block, not once per 512 elements.

We re-ran the ladder as Metal kernels on 225 floats measured on Apple M1 Pro GPU. Before looking: Harris's last rung was 30 times faster than his first. How much faster is ours?

On the M1 Pro, R6 (grid-stride, vector loads, SIMD sums) against R1 (interleaved, divergent):
Only 1.6×: R1 takes 1.61 ms (83 GB/s) and R6 1.01 ms (133 GB/s), about the speed of MLX's own mx.sum (1.04 ms). Even the worst kernel reads memory at more than half the copy speed.

Bars: median of 3 runs; the thin line spans the fastest and slowest of all 21 trials. Each time includes MLX's per-call launch-and-wait overhead, which the topic root measured at about 0.2 ms (its section 1), so the kernels themselves are faster than shown and the differences between them larger in proportion.

Why the ladder flattened. In 2007 the G80 had little on-chip cache and slow integer arithmetic, so the index arithmetic, idle lanes and barriers of the early rungs cost more than the memory traffic. A modern GPU has far more arithmetic per byte of bandwidth (the ridge point of the hardware root), so a reduction is limited by reading the input almost however clumsily it combines it; the remaining gap is the 8 barriers per 256 values of R1 to R3. The lesson that survives is the last one: do most of the work in registers, one value per element, and make the tree as small as possible. That is what every production reduction does.

Inside a warp: shuffles

A shuffle moves a register value directly from one lane of a warp to another, with no shared memory and no barrier. Five of them sum 32 values:

__device__ float warp_sum(float v) {
  for (int o = 16; o > 0; o >>= 1)
    v += __shfl_down_sync(0xffffffffu, v, o);   // add the value held by lane (lane + o)
  return v;                                     // lane 0 holds the sum of all 32
}

Compiled for an H100 (sm_90a) compiled, it is exactly five shuffle-and-add pairs; the mask 0xffffffff says all 32 lanes take part:



Correction to old habits: "warp-synchronous" code is a bug
Harris's rung 5 relied on the 32 lanes of a warp executing in lockstep, reading each other's shared-memory writes with no barrier. Since Volta (2017), lanes of a warp can be scheduled independently, and NVIDIA's Volta tuning guide says plainly: "Assumptions that code is executed in lockstep or that reads/writes from separate threads are visible across a warp without synchronization are invalid." Use the *_sync shuffles, or __syncwarp() between shared-memory steps. Old tutorials (and old kernels) still contain the volatile trick.



Combining blocks: a second launch, an atomic, or one more trick


Three ways to turn one partial per block into one number: (1) a second, small launch that reduces the partials (rungs R1 to R6 above); (2) every block does an atomic add of its partial into one output (A1: one launch, 1.05 ms); (3) the last block to finish, detected with an atomic counter, reduces all partials; (4) a cooperative launch, where grid.sync() makes every block wait for all the others (blocks must all be resident at once, which limits the grid size). PyTorch's own reduction kernel uses the third: its Reduce.cuh keeps a global buffer and a semaphore per output when a reduction spans blocks (source excerpt in src/inputs/pytorch_extracts.txt, PyTorch main at commit 8d1d972, read 2026-10-05).


Correction to the old page
The old page said "in library code use CUB (cub::BlockReduce, cub::DeviceReduce), which is what PyTorch does". For sums, PyTorch does not: torch.sum on CUDA calls its own gpu_reduce_kernel (ReduceSumProdKernel.cu). It does use CUB for a one-dimensional cumsum (section 2). CUB is still the right thing to call in your own CUDA code: cub::BlockReduce compiles to the same five shuffles per warp (Compiled for NVIDIA).



The order of additions changes the answer


Floating-point addition is not associative: (a + b) + c can differ from a + (b + c) in the last bits. A reduction picks an order, and different orders give different sums. Two consequences you will meet in training code:


The 225 inputs are uniform in [0, 1), so the exact sum is about 16.8 million. Add them one by one into a single float32 accumulator, in order. What comes out?




The running sum reaches 224 = 16,777,216, where float32's spacing between neighbouring numbers is 2, and from then on adding any value below 1 rounds back to the same number. Result 16,777,216, off by 495 from the float64 sum 16,777,711.32. The GPU tree gives 16,777,712, off by 0.68: a tree adds numbers of similar size at every level, which is why parallel reductions are usually more accurate than the sequential loop they replace measured on Apple M1 Pro GPU.


Atomics make the order, and so the bits, change from run to run. We ran the atomic kernel A1 30 times on the same input in each of the 3 runs: it gave 7, 6, 8 distinct results (from 16,777,702 to 16,777,718), because the blocks arrive in a different order each time; the two-launch tree gave one result every time measured on Apple M1 Pro GPU. This is why torch.use_deterministic_algorithms(True) exists, why two "identical" training runs drift apart, and why a test must compare with a tolerance rather than bit for bit (section 8).






2. Scan: running totals


The problem. An inclusive scan (prefix sum) turns x0, x1, x2, ... into x0, x0+x1, x0+x1+x2, ...; an exclusive scan shifts it by one and starts at 0. It looks sequential, every output depends on every earlier input, yet it is everywhere in model code: a mixture-of-experts layer counts how many tokens go to each expert and scans the counts to find where each expert's tokens start in a packed buffer; top-p sampling scans sorted probabilities; packing variable-length sequences scans their lengths into offsets; torch.cumsum is a scan.


Two parallel algorithms (from GPU Gems 3, chapter 39, Harris, Sengupta and Owens):




Hillis and Steele
Step k: every element adds the one 2k places to its left. log2(n) steps, all elements busy, but O(n log n) additions: for n = 224, 386 million adds against 16.8 million for a loop derived, Σk<24(n − 2k).


Blelloch (work-efficient)
An up-sweep builds a tree of partial sums (a reduction), a down-sweep pushes prefixes back down: "approximately 2 × (n − 1) adds and n − 1 swaps", 33.6 million for n = 224 derived, but twice the steps.




Both are animated on the same 16 numbers in the Reduce and scan, animated tab. On a real GPU neither is used across the whole array. Inside a warp, a scan is five shuffles (__shfl_up_sync; Metal's simd_prefix_exclusive_sum); across a block, warps exchange totals through shared memory; across blocks comes the hard part, because block 7 needs the total of blocks 0 to 6.


Across blocks: three launches, or one pass with a look-back


Reduce, then scan (three launches): (a) each block sums its tile; (b) one block scans the tile sums into offsets; (c) each block scans its tile again and adds its offset. The input is read twice and the output written once: 3 passes over memory, against 2 for a copy. Decoupled look-back (Merrill and Garland, NVIDIA, 2016) does it in one launch: each block publishes its own total as soon as it has it, and its inclusive prefix once it knows it; a block that needs its offset looks back at its predecessors' published values, summing totals until it meets a published prefix. It "requires only ~2n data movement" and its throughput "approaches that of copy operations" published; it is how cub::DeviceScan works. It relies on earlier blocks making progress while later ones wait, a guarantee Metal does not document, so we did not run it here.


Measured on 224 floats measured on Apple M1 Pro GPU:

In PyTorch, a one-dimensional torch.cumsum on CUDA calls cub::inclusive_scan, and a separate inclusive_deterministic_scan for floating-point types when deterministic algorithms are requested (ScanUtils.cuh, read 2026-10-05): the default single-pass scan can add in an order that depends on timing, for the same reason as the atomic sum of section 1.







3. Row normalisation: softmax, LayerNorm, RMSNorm


Softmax, LayerNorm and RMSNorm all do the same thing to each row of a matrix: compute one or two statistics of the row (a reduction), then rewrite every element using them. In a transformer the rows are tokens and a row is a few thousand numbers, so the standard layout is one block per row, the row's elements spread over the block's threads, each thread keeping its share in registers between the statistics and the rewrite, so the row is read from memory once and written once. Arithmetic is a handful of operations per element; the speed is set by bytes.


Softmax: the online trick


The topic root's Kernel lab climbs the softmax ladder in seven measured rungs, from one thread per row (177 ms) to the row held on chip (3.27 ms, the speed of a copy), so it is not repeated here (Kernel lab, section 1). The idea to carry forward is the online softmax (Milakov and Gimelshein, 2018): keep a running maximum m and a running sum d of ex − m; when a larger value arrives, rescale the sum you have.


m′ = max(m, xi)    d′ = d · em − m′ + exi − m′


merge (ma, da) with (mb, db): m = max(ma, mb),   d = da ema − m + db emb − m


The second line is what makes it a parallel algorithm: any two partial results, from two lanes, two warps or two tiles, combine exactly, in any order. Every reduction on this page that is more than a sum needs such a merge.


LayerNorm: the variance is a numerical trap


LayerNorm subtracts the row's mean μ and divides by its standard deviation σ: y = (x − μ) / √(σ2 + ε) · γ + β. The tempting one-pass formula for the variance, σ2 = E[x2] − E[x]2, subtracts two large, nearly equal numbers when the mean is large compared with the spread, and float32 keeps only about 7 significant digits.


Rows of 4,096 float32 values with standard deviation 1 and mean 3,000. Our kernel computes the variance as E[x2] − E[x]2. How wrong is the normalised output (largest error against float64)?




Largest error 1,653. E[x2] is about 9 million, where float32's spacing is 1, so the difference that should be 1 is rounding noise, often 0 or negative (clamped to 0), and dividing by √ε instead of 1 multiplies everything by about 316. The two-pass kernel (mean first, then the mean of (x − μ)2 from the values still in registers) errs by 6.3e-04, Welford's by 6.0e-04 measured on Apple M1 Pro GPU.

When the row fits in registers, as here, two passes over registers are just as cheap and simpler; Welford matters when the row is streamed once from memory, as in a long row or a fused kernel that cannot keep it. All three kernels took 1.74 to 1.77 ms on 8,192 rows of 4,096 (154 GB/s counting one read and one write), against 1.87 ms for MLX's mx.fast.layer_norm and 9.87 ms for the same formula as seven separate MLX operations (6.79 ms under mx.compile) measured on Apple M1 Pro GPU.


RMSNorm, fused with the residual add


RMSNorm drops the mean: y = x / √(mean(x2) + ε) · γ. In a pre-norm transformer block it always follows a residual add, h = x + r, and h is needed twice: normalised for the next layer, and raw as the next residual. Separately, the add reads x and r and writes h, and the norm reads h and writes y: 5 passes over the activations. Fused, one kernel reads x and r and writes h and y: 4 passes, so at best 5 : 4 = 1.25 times faster derived. Measured: 4.03 ms for MLX's add then mx.fast.rms_norm (4.09 ms under mx.compile, which did not fuse them), 3.35 ms fused, 1.20 times measured on Apple M1 Pro GPU. Production engines ship exactly this kernel: vLLM declares fused_add_rms_norm(input, residual, weight, epsilon) next to its plain rms_norm (csrc/ops.h, read 2026-10-05); count passes before writing one, because the best case is set by the byte count before you start.






4. The matmul ladder, as the NVIDIA compiler sees it


The problem. C = AB for n × n float32 matrices does 2n3 operations on 3n2 numbers, so in principle each number loaded can be used n times. Whether a kernel gets anywhere near that is a question of reuse: how many multiply-adds each value performs while it sits in a register or in shared memory. 5. Fusion: keep it on chip


The idea. Two kernels in a row hand their intermediate result over through global memory: the first writes it, the second reads it back. A fused kernel does both operations while the intermediate is in registers or shared memory. Fusion pays exactly when that round trip is a large part of the time, which gives three rules: chains of memory-bound operations (elementwise, norms) fuse to nearly the cost of one; a cheap operation applied to a matmul's output while it is still in registers (an epilogue) or to its input as it is loaded (a prologue) removes one round trip of that matrix; and fusing work into a compute-bound loop can lose, because the loop was not waiting for memory in the first place. We measured all three, with real mistakes along the way.


Epilogue: matmul, bias, GELU


y = GELU(xW + b) for 4,096 tokens, 4,096 outputs, K = 1,024 or 256 inputs, float32. Unfused, the matmul writes C (64 MiB) and a second kernel reads it, adds b, applies GELU and writes y: 134 MB of extra traffic, about 0.9 ms at this GPU's copy speed derived. Our fused kernel is the Kernel lab's fastest matmul (8 × 8 matrix instructions, 64 × 64 tile per threadgroup) with the epilogue added. 6. Decode: a matrix times one vector, with 4-bit weights


The problem. When a model generates one token for one user, every linear layer multiplies its weight matrix by a single vector: a GEMV. Each weight is read once and used once (one multiply-add), so the time is the bytes of the weights divided by memory bandwidth, and the only way to go faster is to read fewer bytes. That is why decode-time weights are stored in 4 bits. But the GPU cannot multiply 4-bit codes directly; they must be dequantised (code × scale + bias, per group of weights). Do it as a separate kernel and you write a full 16-bit copy of the matrix and read it back, three times the bytes you hoped to save. Do it inside the GEMV, in registers, and only the 4-bit bytes cross the memory bus.


The shape is one MLP projection of Llama 3 8B, 14,336 × 4,096, in MLX's own 4-bit format (groups of 64 weights, a float16 scale and bias per group): 117.4 MB in float16, 33.0 MB in 4 bits, 0.5625 bytes per weight, 3.56 times fewer derived, 0.5 + 4/64.




measured on Apple M1 Pro GPU. Every kernel checked against a float64 product with the same dequantised weights. The last bar only reads the 4-bit codes (a sum over them), for scale.


    

  • Dequantise, then GEMV: 1.84 ms, twice the float16 GEMV (1.02 ms ours, 0.94 ms MLX): the worst of both.
    • 

  • Fused, one thread per row: 2.70 ms. Neighbouring threads read addresses a whole row (2 KB) apart: the uncoalesced pattern again.
    • 

  • Fused, one SIMD-group (warp) per row, lane l reading 4-byte words l, l + 32, ...: 0.46 ms, 2.2 times the float16 GEMV. A further rung with 16-byte loads did not help (0.46 ms); MLX's mx.quantized_matmul took a median 0.67 ms with a best of 0.39 ms, noisy on a shared machine.
    • 



Why 2.2 times and not 3.56? Merely reading the codes takes 0.38 ms. Fitting time = t0 + bytes / bandwidth through that point and the float16 GEMV gives 139 GB/s and a fixed 0.17 ms per call derived, the launch-and-wait overhead the root measured; it predicts 0.41 ms for the fused kernel's bytes. So the fused kernel runs at the memory system's speed; the fixed cost of a launch is what keeps a 33 MB kernel from a 3.56× win. On a GPU serving a model, a decode step launches hundreds of such kernels, which is why engines capture them in CUDA graphs (streams and graphs page).


What the NVIDIA compiler makes of the unpacking compiled: the same kernel in CUDA (src/cuda/kernels/g_dequant_gemv.cu) shows, per 4-byte word, a LOP3 (mask) and SHF (shift) per code and an I2FP (integer to float) per code, before the FFMA. It also shows a flaw we did not see in the source: the eight float16 activations per word are fetched with eight separate 2-byte loads (LDG.E.U16). Production kernels avoid both costs: they load activations in 16-byte vectors, and convert codes to half precision with bit tricks (PRMT and LOP3 on packed pairs) instead of one conversion per code.




Beyond one token. With a batch of b tokens each weight is used b times, and the kernel turns into a matmul whose arithmetic eventually catches up with the saved bytes. Marlin (Frantar et al., 2024) is a 4-bit-weight, 16-bit-activation kernel designed to keep the full win as long as possible: "batchsizes up to 16-32 can be supported with close to maximum (4×) quantization speedup", and up to 2.8 times end to end inside vLLM published. The quantisation formats themselves (GPTQ, AWQ, GGUF k-quants) are the training topic's quantization page and the C++ page's llama.cpp part; on this toy, 4 bits moved the output by up to 8.5% of its largest value against float16 weights measured (random weights, round-to-nearest, no calibration).







7. FlashAttention, step by step


FlashAttention is sections 1, 3, 4 and 5 composed: it tiles Q, K and V, computes each tile of scores S = QKT on chip, folds it into the output with the online-softmax merge of section 3, and never writes the N × N matrices S and P to memory. The paper page FlashAttention steps through the algorithm on a real input in its Run the kernel tab and follows FA-1 to FA-4 in Then and now; the topic root's Kernel lab builds a working FlashAttention-style Metal kernel. This section is about what changed in each version and why, with each change measured where the M1 can show it.


FlashAttention-2: three changes


The FlashAttention-2 paper (Dao, July 2023) starts from one number: an A100 does "312 TFLOPs/s of FP16/BF16 matmul, but only 19.5 TFLOPs/s of non-matmul FP32", so every non-matmul operation (the exponentials, the rescaling, the max) costs 16 matmul FLOPs published. It reports about 2× over FA-1 and 50 to 73% of peak on A100, from three changes:


    

  1. Fewer non-matmul operations. Keep the output unnormalised and divide by the running sum once, at the end, instead of rescaling it every tile; store one number per row for the backward pass, the logsumexp L = m + log ℓ, instead of both m and ℓ. The Kernel lab's kernel already works this way.
    2. 

  2. Parallelise over the sequence, not only batch × heads. FA-1 gave each (batch, head) pair one thread block, which loops over all query blocks; with long sequences and small batches, batch × heads is smaller than the 108 SMs of an A100 and most of the GPU idles. FA-2 gives each block of queries its own thread block. We measured exactly this switch on the same kernel, 4 heads, d = 64:
    3. 





Log scale. "FA-1 grid": one threadgroup per head, 4 in all, for a GPU with 16 cores; "FA-2 grid": one per 64 query rows and head, 512 at N = 8,192. Same kernel, same arithmetic, measured on Apple M1 Pro GPU.


At N = 8,192 the FA-1 grid takes 214.54 ms and the FA-2 grid 30.62 ms, 7.0 times faster (2.24 TFLOP/s): four threadgroups cannot fill sixteen cores, and even a filled core needs several threadgroups to hide memory latency.


    

  1. Split Q across warps, not K. Inside one thread block of 4 warps, FA-1 split the K and V tile between warps ("split-K"), so each warp held a partial result for every query row and "all warps need to write their intermediate results out to shared memory, synchronize, then add up"; FA-2 splits Q, each warp owns its rows outright and reads all of K and V, with "no need for communication between warps". The Attention schedules tab animates both on one tile and counts the shared-memory traffic.
    2. 



Causal masks: skip, do not mask


In a decoder, query i may only attend to keys j ≤ i. Masking sets the forbidden scores to −∞ but still computes them; tiles wholly above the diagonal can instead be skipped. FA-2 reports "around 1.7-1.8× speedup compared to attention without the causal mask" published. With 64-row query blocks and 32-key tiles the work falls to (B + 1) / 2B of the tiles for B = N / 64 query blocks, an ideal 1.98× at N = 8,192 derived. Measured: masking only 30.42 ms (the same as no mask), skipping 16.98 ms, 1.79× measured on Apple M1 Pro GPU. Not quite 2×, because the blocks near the diagonal (more work) and far from it (less) now take very different times, so the last threadgroups run alone. FlashAttention-3's code answers with "longest-processing-time-first scheduling: the longest remaining tile is assigned to the first SM that's free" (hopper/tile_scheduler.hpp, read 2026-10-05). MLX's own causal attention took 12.66 ms.


FlashAttention-3: the exponentials become the bottleneck


On an H100 (Hopper) the tensor cores got faster than everything around them. The FlashAttention-3 paper (Shah et al., July 2024) gives the H100 SXM5 "989 TFLOPS for FP16 matmul versus 3.9 TFLOPS for special functions" (the units that compute exponentials), a ratio of 254 published. Each score costs 4d matmul FLOPs (2d for QKT, 2d for PV) and one exponential, so for d = 128 the exponentials take (1 / 3.9) / (512 / 989) = 50% of the matmul time derived, the paper's "exponential can take 50% of the cycle compared to matmul". If they run one after the other, the tensor cores idle a third of the time. FA-3's answer is to overlap them, with Hopper's asynchronous hardware:


    

  • Warp specialisation: producer warps only issue TMA copies (the tensor memory accelerator, which moves whole tiles from global to shared memory by itself), consumer warpgroups (4 warps each) only compute, and setmaxnreg moves registers from producers to consumers.
    • 

  • Ping-pong: two consumer warpgroups take turns, one running its softmax while the other's GEMMs run on the tensor cores: "from approximately 570 TFLOPS to 620-640 TFLOPS" (head dimension 128, sequence 8,192).
    • 

  • Intra-warpgroup pipelining: within one warpgroup, start the next tile's QKT before this tile's softmax is done, at the cost of more registers. The ablation: 661 TFLOPS with everything, 582 without this pipelining, 570 without warp specialisation.
    • 

  • FP8: block-wise scales and "incoherent processing" (multiply Q and K by a random orthogonal Hadamard-based matrix, which spreads outliers) for "2.6× lower numerical error compared to per-tensor quantization". Headline: FP16 up to 740 TFLOPs/s, 75% of peak; FP8 close to 1.2 PFLOPs/s published.
    • 



The Attention schedules tab lays the three schedules out on a time line with the exponential share as a slider. None of this can be measured on the M1, which has no asynchronous matrix units.


FlashAttention-4 and Blackwell


On a B200 the tensor cores doubled again while "other functional units (shared memory bandwidth, exponential units) scale more slowly or remain unchanged". FlashAttention-4 (Zadouri et al., 2026) answers with fully asynchronous MMA pipelines and larger tiles, exponentials partly computed in software on the FMA units, "conditional softmax rescaling" (skip the rescale when the running maximum barely moves), and tensor memory plus the 2-CTA MMA mode in the backward pass; up to 1,613 TFLOPs/s on B200 in BF16 (71%), 1.3× over cuDNN 9.13 published, written in the CuTe DSL in Python. Every generation is the same algorithm re-scheduled around whichever unit became the bottleneck.


The backward pass


The backward pass never stored P; it recomputes it tile by tile from Q, K and the saved logsumexp L: P = exp(S − L). FA-2's algorithm first computes D = rowsum(dO ∘ O) (one number per row), then per tile: dV += PT dO; dP = dO VT; dS = P ∘ (dP − D); dQ += dS K; dK += dST Q. It is parallelised over blocks of keys ("each worker takes care of a block of columns"), so several thread blocks add into the same rows of dQ, which FA-2 does "using atomic adds", the non-determinism of section 1 again published. Recomputing S costs about one more QKT; storing P would cost N2 numbers per head.


Decode: split the keys


Generating a token has one query per head against a long cache of keys and values. A FlashAttention grid over (batch, head, query block) then has batch × heads blocks: "with a batch size of 1, FlashAttention will use less than 1% of the GPU" (published, Flash-Decoding, Dao, Haziza, Massa and Sizov, October 2023). Flash-Decoding splits the keys into chunks, runs the online softmax on each chunk in parallel, saves each chunk's (m, ℓ, partial output), and merges them with the section-3 rescaling in a tiny second kernel; it reports up to 8× faster generation for CodeLlama-34B at 64K context. We built it: 8 heads, d = 128, float16 cache, one query measured on Apple M1 Pro GPU.




At 65,536 tokens (268 MB of K and V), one threadgroup per head takes 3.85 ms; the best split (S = 4) 1.73 ms, 2.2×, the same as MLX's own (1.73 ms). And a surprise: S = 8 took 6.05 ms, slower than no split. With 65,536 keys per head, the 8 chunks of each head start exactly 2 MiB apart; with 512 more keys (66,048) the same kernel takes 1.82 ms at S = 8 against 5.22 at 65,536, three runs each. The likely cause is that concurrent reads spaced by a power of two land on the same memory channel or bank, since memory controllers pick a channel from address bits; we did not establish the M1's mapping, so treat this as a hypothesis unconfirmed. The lesson is general: sweep the split size and the problem size, because a performance cliff can sit at the exact power of two everyone benchmarks. Paged KV caches, GQA and serving-side scheduling are the inference and serving topic's.






8. Testing a kernel against a reference


A fast wrong kernel is worse than a slow right one, and GPU bugs hide: they appear at one size, one in a hundred runs, or only after a different kernel ran first. Every kernel on this page went through the same harness before it was timed: run it, compare with a float64 reference computed by NumPy, fail if the largest error exceeds a tolerance. That harness still let one bug through, and it is the most useful thing on this page to read.


A kernel that wrote nothing passed the test
Our first standalone RMSNorm kernel computed its loop count as C / 4 / 256, which is 0 for rows of 256 floats: it wrote nothing at all. The check passed, error 4 × 10−6 (the log line is kept in src/m1/out/side_experiments.txt). The output buffer the kernel received was, most likely, memory MLX's allocator had just freed after the library's own RMSNorm of the same shape, still holding the right answer. Two cheap defences: poison the output (fill it with NaN before the kernel runs, or make sure it is fresh memory; our harness now empties MLX's buffer cache before every check) and run the reference path after, not before, the kernel under test, so it cannot leave its answer behind. The fixed kernel then passed for the right reason. The topic root's Kernel lab kept a second lesson: a barrier that was too weak (simdgroup_barrier where a threadgroup barrier was needed) gave 1 to 5 wrong rows out of 4,096 at random, and every small test passed. Test at the real size, and repeat.


Choosing the tolerance


torch.testing.assert_close passes when |actual − expected| ≤ atol + rtol · |expected|, with defaults per data type (_comparison.py, read 2026-10-05):


dtypertolatol


float321.3e-61e-5
float161e-31e-5


bfloat160.0161e-5
float641e-71e-7


These are right for one rounding, not for a sum of thousands of terms, whose error grows with the length of the sum. A practical rule: compute the reference in float64, measure the error of a trusted implementation in your precision (the library, or PyTorch eager) against it, and require your kernel's error to be within a small factor of that. Our matmuls in float32 erred by up to 8 × 10−6 against float64, like MLX's; the 4-bit GEMV by 9 × 10−4 against the product with the same dequantised weights, and by far more (section 6) against the unquantised weights, which is a different question (does quantisation hurt the model?) and needs a different test (evaluation).


Inputs that break kernels


    

  • Sizes that are not a multiple of the tile (4,097 columns, 1 row, 0 rows): the bounds checks. Every kernel on this page assumes multiples of its tile; a production kernel must not.
    • 

  • Large offsets: rows with mean 3,000 (section 3), logits of 104 (softmax without the max subtraction overflows exp above about 88.7 in float32).
    • 

  • Masks: a row whose keys are all masked gives max = −∞, then exp(−∞ − (−∞)) = NaN. Decide what the kernel should return (zeros, or NaN to flag it) and test it. Our causal kernel never meets such a row because key 0 is always visible; a padding mask breaks that.
    • 

  • Real distributions: real activations have outliers (a few channels 100 times larger than the rest); random normal inputs hide quantisation and overflow problems.
    • 

  • Repeated runs: run 10 to 30 times and compare the outputs with each other, which finds races and non-deterministic atomics (section 1).
    • 



Tools


On NVIDIA, compute-sanitizer (shipped with the toolkit) has four tools, from its own help text (CUDA 13.4.2): memcheck ("Memory access checking", the default: out-of-bounds and misaligned accesses), racecheck ("Shared memory hazard checking": a missing __syncthreads()), synccheck ("Synchronization checking": a barrier only some threads reach) and initcheck ("Global memory initialization checking": reading memory nobody wrote, which would have caught our RMSNorm bug). They slow a kernel by large factors, so run them on small inputs in CI. Timing honestly (warm-up, medians, L2 flushing, CUDA events) is section 2 of Profiling, benchmarking and correctness; its Numerics lab tab shows why a reordered sum or an atomic changes the last digits and which tolerance fits each data type.







Common mistakes


Comparing a fused kernel with eager PyTorch
Eager mode runs one kernel per operation; anything fused beats it. Compare with torch.compile (or mx.compile): our GELU epilogue looked 1.7× faster than eager and was 0.92× of compiled MLX (section 5).


Fusing into a compute-bound loop
Extra instructions in the inner loop of a matmul cost more than the bytes they save: RMSNorm fused into our matmul lost (section 5). Fuse into memory-bound kernels, or into the epilogue, once.


Using more shared memory "because it is free"
Shared memory and registers per block decide how many blocks fit on an SM, for the whole kernel. A 16 KB staging buffer made our fused kernel 28% slower than not fusing.


Accurate math functions in a fused epilogue
precise::tanh cost 1.3 ms inside the matmul; in the separate, memory-bound kernel its cost hid behind the memory traffic. On NVIDIA the equivalent choice is -use_fast_math or intrinsics like __expf; check the error you accept.


Warp-synchronous code without _sync
Lanes of a warp are not guaranteed to run in lockstep since Volta. Use __shfl_*_sync and __syncwarp() (section 1).


E[x²] − E[x]²
Catastrophic cancellation when the mean is large: errors of 1,653 at mean 3,000 (section 3). Use two passes over registers or Welford.


Expecting bit-identical results
Atomics and some scans change the order of additions from run to run. Test with tolerances; turn on deterministic algorithms when you must reproduce a run.


Benchmarking only powers of two
Our split-KV kernel was nearly 3 times slower at exactly 65,536 keys than at 66,048 (section 7). Sweep sizes.


Masking instead of skipping
A causal mask applied to every tile costs the same as no mask; skipping tiles above the diagonal nearly halves the work (section 7).



Interview questions, with short answers


Why is a reduction memory-bound, and what is its ceiling?
One add per 4-byte element is far below any GPU's ridge point; the ceiling is the time to read the input once. On the M1 the first rung read at 83 GB/s and the last at 133 GB/s, against about 143 GB/s for a plain read measured by the hardware topic's Roofline lab.


Write a warp sum. Why the mask argument?
Five __shfl_down_sync(0xffffffff, v, o) for o = 16, 8, 4, 2, 1. The mask names the lanes that participate and must all reach the call; it exists because lanes are scheduled independently since Volta.


How do you combine partial sums from different blocks?
A second launch, an atomic add per block (fast, non-deterministic), or the last block to finish (found with an atomic counter) reduces all partials, as PyTorch's Reduce.cuh does.


Hillis-Steele or Blelloch?
Hillis-Steele: log n steps, O(n log n) adds, fine inside a warp. Blelloch: O(n) adds, 2 log n steps, good for large arrays in shared memory. Across the GPU, a tiled scan with decoupled look-back reads and writes each element once (CUB).


What does the online softmax merge, and why does FlashAttention need it?
Two partial (max, sum) pairs: rescale each sum by emi − m and add. It lets tiles of keys be processed one at a time, and partial outputs (Flash-Decoding) be combined, without ever seeing the full row.


Why does FlashAttention-2 split Q across warps instead of K?
Split-K leaves every warp with a partial result for every row, which must be written to shared memory, synchronised and summed; split-Q gives each warp its own rows and no communication.


What limits attention on an H100 once the bytes are fixed?
The exponentials: 989 TFLOPS of FP16 matmul against 3.9 of special functions, about 50% of the matmul time at d = 128. FA-3 overlaps them with the GEMMs (warp specialisation, ping-pong).


Why is decode attention slow with plain FlashAttention, and the fix?
One query per head gives batch × heads thread blocks, a few percent of the GPU. Split the keys (Flash-Decoding), run chunks in parallel and merge with logsumexp rescaling.


A 4-bit GEMV is only 2× faster than float16, not 4×. Why might that be?
Fixed launch overhead dominates small kernels (0.17 ms here), dequantisation instructions or scalar activation loads can make it instruction-bound, and scales and biases add bytes (0.5625 bytes per weight here). Measure the read of the bytes alone first.


When does fusion not help?
When the intermediate's round trip is a small share of the time (compute-bound kernels), when it raises register or shared-memory use and cuts occupancy, or when the compiler already fused it.

Attention schedules: who computes what, and when


Two pictures of how a FlashAttention kernel is organised inside one GPU core, each a before/after on the same work. Both are models: the shapes of the work are the papers', the counts are ours, labelled derived; nothing here was measured on an NVIDIA GPU.



1. Inside one thread block: split K, or split Q (FlashAttention-1 against -2)


One block holds a tile of 64 query rows and, at each step of its loop, a tile of 64 keys and values (head dimension 128), and has 4 warps. FlashAttention-1 split the keys between the warps ("split-K"); FlashAttention-2 splits the queries ("split-Q"). Play one loop iteration both ways and compare the shared-memory traffic and barriers.






Counts are values (not bytes) per loop iteration, for Br = Bc = 64, d = 128, 4 warps, from the tile shapes alone: split-Q reads 4 times more K and V from shared memory (every warp needs all of it) but never exchanges partial results; split-K must exchange row maxima and then partial outputs through shared memory, with barriers in between. Which costs more on a real GPU depends on bandwidths the model does not have; FlashAttention-2 reports that removing the exchange gave a speedup (FA-2, section 3.3).



2. On the tensor cores' time line: FlashAttention-3's overlap


Each iteration of the loop is three steps: GEMM0 (S = QKT, tensor cores), softmax (exponentials, on the much slower special-function units), GEMM1 (O += PV, tensor cores). On an H100 at head dimension 128 the softmax takes about half as long as the two GEMMs (FA-3: 989 against 3.9 TFLOPS). Run in order, the tensor cores wait during every softmax. FlashAttention-3 overlaps them two ways: ping-pong between two warpgroups, and pipelining inside one warpgroup (start the next GEMM0 during this softmax).




0.5: H100, d = 128 (FA-3). About 1.0: tensor cores twice as fast, exponentials not (the Blackwell case FA-4 describes).






A list-scheduling model: 8 tile iterations in all (one warpgroup does 8; two do 4 each), GEMM0 and GEMM1 one unit each, softmax r × 2 units, one tensor-core pipe and one exponential pipe per SM, each task starts when its inputs are ready and its pipe is free, in program order. It ignores loads (TMA producers hide them in FA-3), register limits (pipelining costs registers) and the rescaling work, and it is greedy, not optimal: at a ratio of 1.0 it does worse with both techniques than with ping-pong alone, a reminder that FA-3's order of instructions is tuned by hand. Checked against an independent Python implementation (src/fa_model.py). FlashAttention-3's measured ablation for comparison published: 570 TFLOPS without warp specialisation, 582 without the pipelining, 661 with both (H100, FP16, head dimension 128, sequence 8,448 in that table).
