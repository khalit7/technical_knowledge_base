Four questions come up every time you try to make GPU code faster, and each has its own tool. Where does the time go? (a timeline of the whole program). Why is this one kernel slow? (hardware counters for that kernel). Is my timing true? (a measuring method that survives asynchronous execution, caches, clocks and a busy machine). Is the answer still right? This page teaches all four from zero, with real tool output wherever it can be produced without an NVIDIA GPU.

Words used throughout: a kernel is one function that runs on the GPU across many threads; a launch is the CPU asking the GPU to run one; a profiler is a program that watches another program and records what it did and how long it took. The loop this page builds
Measure the whole program (timeline) → pick the biggest kernel or gap → explain it (counters, roofline) → change one thing → re-measure with an honest benchmark → check the output against a reference. Write the numbers down at every step. A speedup without the method behind it is not a result.

1. Why a stopwatch around GPU code lies

The problem. The CPU and the GPU are two workers with a queue between them. When Python runs c = a @ b on a GPU tensor, the CPU does not wait for the multiply: it writes a command into the queue (CUDA calls the queue a stream) and returns at once. The GPU picks the command up when it is free. So a clock read on the CPU before and after that line measures how long it took to queue the work, not to do it. This is called asynchronous execution, and it is the reason PyTorch on a GPU can be fast at all: the CPU runs ahead and keeps the queue full.

How to time it. Either make the CPU wait for the queue to drain before reading the clock (torch.cuda.synchronize(), and also before starting it, or earlier queued work is charged to you), or put two markers into the queue itself and ask the GPU how far apart they were: a CUDA event. Below, one 2,048 × 2,048 float32 matrix multiply is timed four ways on this laptop's GPU, drawn to scale.

Predict: four earlier multiplies are still in the queue when you start the clock, then you queue one more and synchronise. What does the clock say, roughly?
The synchronise waits for everything in the queue, including the four multiplies queued before the clock started. measured: 19.93 ms against 4.243 ms for one. The fix is a synchronize() before reading the start time too.

The PyTorch recipe on CUDA

# warm up first (section 2), then:
start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
torch.cuda.synchronize()          # nothing else in the queue
start.record()                    # a marker in the stream
y = f(x)
end.record()
torch.cuda.synchronize()          # or end.synchronize()
ms = start.elapsed_time(end)      # GPU time between the markers, in ms

NVIDIA documents event timing with "a resolution of around 0.5 microseconds" (CUDA Runtime API 13.4, cudaEventElapsedTime) docs. Events measure the stream, so they leave out the CPU's own overhead; a synchronised CPU clock includes it. Use events for "how fast is this kernel", and a synchronised clock (or a profiler timeline) when the question is "how fast is this step", because in launch-bound code the CPU is the cost. One more trap: an event pair also counts any time the GPU sat idle between the markers waiting for the CPU to queue the next kernel, so a slow Python loop inflates event times too.

Know what your timer brackets

Apple's MPS events are not CUDA events: they mark command-buffer boundaries, so they carry a fixed overhead. On this laptop, a tiny multiply of 4,096 numbers measured 0.157 ms with an event pair and 0.196 ms with a clock and a synchronise per call, but 4.96 µs per call when 200 calls were queued back to back with one synchronise at the end measured. The GPU work is a few microseconds; everything else is the measuring. On CUDA the same effect exists at a smaller scale: a kernel of a few microseconds timed alone is mostly launch and synchronisation, which is why CUDA graphs and Triton's do_bench_cudagraph exist. For tiny kernels, time many back-to-back calls and divide, and say so.

The same trap inside PyTorch code you did not write
Any operation that needs a value on the CPU forces a synchronise: loss.item(), print(tensor), tensor.cpu(), if tensor.any():, a nonzero() whose size the CPU must know. In a training loop these silently serialise the CPU and GPU, and a stopwatch then "works" by accident. The timeline in section 3 shows where they are.

2. Benchmarking honestly: warm-up, caches, spread, clocks

Even with correct synchronisation, the same kernel gives different times depending on when and how you time it. Five effects account for almost every wrong benchmark. Each is shown here with a measurement from this laptop and the rule that follows.

Warm-up: the first call pays for everything that happens once

The first time a process runs an operation, it pays one-time costs: setting up the device, compiling or loading the kernel, choosing an algorithm (cuDNN's benchmark mode tries several), growing the memory allocator. Triton kernels compile and autotune on first call, and torch.compile compiles once per new input shape. None of that is the kernel's speed.

measured on Apple M1 Pro GPU: each line is the median over 9 fresh Python processes (3 runs × 3) of the k-th call, each call synchronised; the bars show the slowest and fastest process. The first softmax took 5.78 ms (median; one process took 17.9 ms) against 0.45 ms by the 15th call; the first matmul 26.9 ms against 4.27 ms. In the profiled training step of section 3, the first step on the GPU took 905 ms and the later ones about 7 ms. Rule: run the operation until its time stops falling, and only then time it; for compiled or autotuned code, warm up every shape you will time.

Caches: timing the same small tensor in a loop measures the cache

A GPU has a large last-level cache (the L2: 40 MB on an A100 40 GB per NVIDIA's Ampere post, 50 MB on an H100 SXM per the Hopper post, 96 MB on an RTX 5090 per the RTX Blackwell whitepaper). If a benchmark reads the same 16 MB buffer a hundred times, every read after the first comes from the cache, and the "memory bandwidth" it reports is the cache's. In a real model the input was just written by another kernel or evicted by one, so the honest number is the cold one.

Predict: x.sum() over a 16 MB tensor on this laptop (its GPU's last-level cache is 24 MB), timed hot (the same tensor again and again) and cold (rotating through 512 MB of tensors). How different?
measured: hot 255 GB/s, cold 154 GB/s. At 128 MB, far beyond the cache, both are 169 GB/s. The chart below shows where the gap opens and closes.

measured on Apple M1 Pro GPU: effective bandwidth of x.sum() (bytes read divided by time), each point the median of 3 runs of 7 batches of 32 back-to-back calls with one synchronise per batch; whiskers are the 3 runs. The M1 Pro's 24 MB system-level cache is an independent measurement (metal-benchmarks). Rule: flush the cache before each timed run, or rotate through buffers larger than it, and say which.

Spread: report the median and the spread, never one number

measured on Apple M1 Pro GPU: 300 event timings of the same 1,024 × 1,024 float32 multiply in each of three runs, minutes apart, laptop 1-minute load average between 4.3 and 4.7 (other agents were running). Run medians: 0.721, 1.554, 1.209 ms: the same code, a factor of 2 apart. Within a run, the mean is pulled by a few slow outliers (run 2: mean 1.521, maximum 11.82 ms). Rules: use the median (or several quantiles) of many runs, repeat whole runs, report the spread and the machine's load, and distrust any comparison between two numbers taken at different times on a shared machine. The minimum is tempting because it is stable, but it describes a lucky run, not the typical one.

Clocks: the GPU changes speed while you measure

GPUs raise their clock when cool and idle (boost) and lower it when hot or at their power limit (throttling), so back-to-back runs can differ. Two remedies docs only, not run here: lock the clocks for the measurement (nvidia-smi -lgc <min,max> "defines closest desired locked GPU clock speed in MHz", -rgc resets; both need root; nvidia-smi docs), or record the clock and power alongside every result (nvidia-smi dmon prints "one line of monitoring data per monitoring cycle"; the third-party nvitop is a friendlier live view). A fixed power limit (nvidia-smi -pl, in watts) and a note of the cooling matter on a workstation, where fans and room temperature change sustained clocks. Nsight Compute locks clocks itself while profiling: since version 2026.1 to boost by default, before that to base (release notes). NVIDIA's own 2023 sample reports show the old default: the device reports a maximum clock of 1,650 MHz, but every kernel ran at 0.94 to 1.05 GHz read from NVIDIA's reports. So a duration from ncu is not the duration in your training run; compare ncu with ncu.

triton.testing.do_bench: the harness that does all of this

Triton's benchmark function, read in the Triton 3.8.0 source real source: it runs your function once and synchronises; times 5 runs to estimate the cost; computes how many warm-up runs fit in 25 ms and how many timed runs fit in 100 ms; runs the warm-up; then for each timed run zeroes a 256 MB buffer ("to make sure that the L2 cache doesn't contain any input data before the run") and records one event pair around your function; finally returns the mean by default, or return_mode="median", "min", "max", "all", or quantiles=[0.2, 0.5, 0.8]. Its sibling do_bench_cudagraph captures the calls in a CUDA graph to remove launch overhead.

Correction to the old page
The old page said do_bench "has flush_l2=True". It has no such argument in Triton 3.8.0: flushing is always on (the 256 MB zeroing above). It also returns the mean, not the median, unless you ask. (testing.py.)

Ported line by line to MPS (one synchronise added before each start event, because MPS refuses event pairs that land in one command buffer) measured on Apple M1 Pro GPU: a 16 MB sum gave a median of 0.36 ms with the flush and 0.25 ms without, across 3 runs; the 2,048 matmul 4.27 ms. The flush difference matches the hot and cold measurement above; the absolute sum times include MPS's per-event overhead, which CUDA events do not have.

Fair comparisons and a log

  • Check the output first (section 5): a kernel that skips work is very fast.
  • Compare against the strongest baseline: torch.compile rather than eager PyTorch, cuBLAS or cuBLASLt with the same data type, layout and fused epilogue, FlashAttention rather than a naive attention.
  • Report achieved throughput next to the limit: GB/s against the memory bandwidth for a memory-bound kernel, TFLOP/s against the peak for the data type for a compute-bound one (Performance math owns the FLOP counts). "2× faster" means little; "from 40% to 80% of peak bandwidth" can be judged.
  • Write down the environment: GPU model and count, driver, CUDA toolkit (13.4.2 is current in October 2026; the old page's "13.3 current" is out of date), PyTorch and Triton versions, clocks (locked or not), power limit, input shapes and data types, and the machine's load. Every measurement on this page records its versions and load in src/out/.

3. Where does the time go? Timelines: Nsight Systems and torch.profiler

The problem. A training step is thousands of kernels, copies and CPU functions. Before optimising any kernel you need to know which ones matter, and whether the GPU is even busy. A timeline (a trace) records every event with its start and end on one time axis, one row per CPU thread and per GPU stream. The questions it answers: is the GPU row full or full of gaps? Which kernels take most of the time? Do copies and communication overlap the compute or wait for it? Where does the CPU block?

The tools and what sits under them

CUPTI (the CUDA Profiling Tools Interface) is NVIDIA's library for collecting GPU activity (kernel start and end times, copies) and hardware counters from inside a process. Nsight Systems (nsys) records a whole-program timeline: CPU threads, CUDA API calls, kernels, memory copies, NCCL, OS calls and your own NVTX ranges (named intervals you mark in code); its kernel times come through CUPTI (Nsight Compute's Profiling Guide). torch.profiler is PyTorch's in-process profiler, built on the Kineto library ("an in-process profiling library integrated with the PyTorch Profiler", pytorch/kineto), whose CUDA backend is CUPTI (its CuptiActivityApi sources). It names every PyTorch operator, its input shapes and the kernels it launched, so it answers "which op is slow" in PyTorch's own vocabulary.

Read the two runs side by side. On the CPU, aten::mm is the biggest row: the CPU does the multiply, so its "self CPU" time is the work (498.3 µs per call). With the model on the GPU, the same operator costs 38.5 µs of CPU time per call: that is only the time to queue it. PyTorch 2.14 has no MPS profiler activity (its activities are CPU, XPU, MTIA, CUDA, HPU, PrivateUse1), so the GPU's own time is missing and the waiting shows up wherever the CPU blocked: the step's own row holds 6.76 ms of "self" time, which is the synchronise at the end of each step. This is exactly what a CUDA profile looks like if you forget ProfilerActivity.CUDA, and why the device columns (self_cuda_time_total, called device time in PyTorch 2.14's tables) are the ones to sort by on a GPU.

4. Why is this kernel slow? Nsight Compute

The problem. The timeline says one kernel takes 30% of the step. Why? Is it moving more bytes than it needs, leaving the arithmetic units idle, using too few warps, or stalling on shared memory? The GPU has thousands of hardware counters (instructions issued, bytes read from DRAM, cache hits, cycles each unit was busy), but only a few can be read in one run. Nsight Compute (ncu) solves this by replaying the kernel: it saves the memory the kernel can touch, runs the kernel, restores the memory, runs it again with different counters, and so on, then turns the counters into metrics, sections and advice.

What replay costs, from NVIDIA's own reports real tool, NVIDIA's reports

Every one of the six sample reports shipped with Nsight Compute 2026.3.1 (collected with --set full) needed 42 passes of the same kernel, and for the matrix transpose the tool saved and restored 545 MB before each pass. Between passes it flushes the caches ("Nsight Compute flushes all GPU caches by default between replay passes"), it serialises kernels that would otherwise overlap, and it locks the clocks. So a profiled run can take orders of magnitude longer, and its durations describe a cold-cache, locked-clock, serialised kernel. Use it on a handful of kernels the timeline already convicted, never on a whole training run (Profiling Guide, kernel replay and workload durations).

ncu --set full -k regex:softmax -c 1 -o sm python train.py   # first matching kernel only
ncu --import sm.ncu-rep --page details                          # the text you see in the Report reader tab
ncu --import sm.ncu-rep --page raw --csv                        # every metric, for scripts
ncu --nvtx --nvtx-include "step/" ...                           # only kernels inside an NVTX range

Flags from ncu --help (2026.3.1): -k takes an exact name or regex:; -c limits the number of profiled launches; without --set the basic set is collected (LaunchStats, Occupancy, SpeedOfLight, WorkloadDistribution: an estimated 229 metrics), while full is an estimated 9,059 metrics in 24 sections (ncu --list-sets). Compile with -lineinfo and add --import-source on to see metrics per line of your source. A Python API for reports ships in extras/python/ncu_report.py.

Read a report top-down: three real before-and-after pairs

The Speed of Light (SOL) section comes first: "for each unit, the throughput reports the achieved percentage of utilization with respect to the theoretical maximum", and the two headline numbers are the highest such percentage among the compute units (Compute (SM)) and among the memory units (Memory). Together they place the kernel: memory high, compute low is memory-bound (move fewer bytes); compute high is compute-bound (cheaper instructions, tensor cores, lower precision); both low means latency-bound (too few warps, stalls, a tail of idle SMs, or a tiny kernel). Warp stalls in one paragraph. Each SM sub-partition's scheduler can issue one instruction per cycle from any eligible warp. A warp is stalled when its next instruction cannot go: long scoreboard means it waits for data from L1, L2 or DRAM (a memory latency problem: more warps, prefetching, fewer loads); MIO throttle and short scoreboard mostly mean shared-memory or special-function pressure (the transpose with bank conflicts spent 83.8 of 158.5 cycles per instruction in MIO throttle); barrier means warps waiting at __syncthreads() for slower ones; math pipe throttle means an arithmetic pipe is saturated (often good news). Stalls only matter when no warp is eligible; with many warps, the scheduler hides them.

5. Is the answer right? References, tolerances, order and atomics

The problem. A new kernel rarely crashes when it is wrong; it returns numbers that look plausible. And a correct kernel rarely returns exactly the same bits as PyTorch, because floating-point arithmetic rounds after every operation and addition is not associative: (a + b) + c and a + (b + c) can differ in the last bits. A GPU kernel adds in whatever order its threads, tiles and atomics dictate. So "is it right?" means "does it differ from a trustworthy reference by no more than the rounding of this number format and this summation explains?".

The number formats and their default tolerances

read from PyTorch 2.14.1: torch.finfo for each type; the default rtol and atol of torch.testing.assert_close from its source (_DTYPE_PRECISIONS). TF32 keeps float32's 8-bit exponent with a 10-bit mantissa (NVIDIA Ampere post). eps is the gap between 1 and the next number: a single rounding changes a value by at most eps/2 relative. assert_close passes when |actual − expected| ≤ atol + rtol × |expected| for every element. Floating point itself, from zero, is on Numerical computing for ML.

How to compare against a reference

  1. Same inputs, more precision. Round the inputs to the kernel's input type first, then compute the reference in float64 (or float32 for a float16 kernel) from those rounded inputs. Otherwise you measure the input rounding, not the kernel.
  2. Tolerance from the output type and the problem size. A float16 output can be off by one rounding (eps/2 relative) plus the accumulated error of the sum, which grows with the reduction length K. Near zero, after cancellation, a relative tolerance is meaningless; compare the error to the scale of the terms instead (for a dot product, √Σ(aibi)²).
  3. Look at the worst element and where it is, not only a pass or fail: an error concentrated in the last tile or the last row is a bug, an error spread evenly at the rounding level is arithmetic.
Predict: a correct float16 matmul (float32 accumulation) on this laptop's GPU, 256 × 256 output, K = 4,096, compared with assert_close's float16 defaults against a float64 reference rounded to float16. How many of the 65,536 elements fail?
measured on Apple M1 Pro GPU: 23 fail at K = 4,096 and 51 at 16,384 (none at 64 and 512). The worst error is 0.16% of the scale of the terms, about what rounding the result to float16 alone explains; the failing elements are those whose result is small after cancellation, where rtol = 0.001 of a small number is tighter than the rounding. bfloat16's default rtol of 0.016 passes every element at every K. Defaults are a starting point; set the tolerance from the format and K, and say what you chose.

Accumulate in float32, even when inputs are 16-bit

computed here (NumPy, 256 random dot products per point, inputs N(0,1) rounded to float16; products are exact in float32): median error relative to √Σ(aibi)². A running sum kept in float16 or bfloat16 loses accuracy roughly in proportion to K (at K = 65,536 the bfloat16 running sum is off by 14.6% of the scale), because each small product is rounded against a large running total. Float32 accumulation keeps the error near 10−6, and a pairwise tree (how a parallel reduction adds) keeps it lower and nearly flat. This is why tensor-core matmuls on 16-bit inputs accumulate in float32, and why a reduction kernel should keep its partial sums in float32. Try other formats and lengths in the Numerics lab.

Order changes the bits: split-K, tiles and atomics

The same 1,048,576 float32 numbers summed in different orders computed here, error in units in the last place (ulps, the spacing of float32 numbers at the size of the answer, here 0.0039):

Exact answer from math.fsum. "Split-K S" cuts the sum into S chunks, sums each, then adds the S partials, which is what a matmul does when it splits the K dimension across thread blocks to use more SMs. Every choice of S gives a different, equally legitimate answer. Sorting by value (all negatives first) is the worst order: the running total grows large before the positives cancel it.

Atomics make the order change from run to run. When many threads add into one location with atomicAdd, the hardware decides the order, so the same kernel on the same input returns different bits each run. Measured on this laptop's GPU with three MLX kernels summing the same 1,048,576 float32 numbers 30 times each measured on Apple M1 Pro GPU:

Sixteen float16 numbers, one large (2,048) and fifteen near 1; every addition is rounded to float16 by the page's float16 model, which matches PyTorch's casts bit for bit on 2,055 test values (check/check_js.mjs). At 2,048 the gap between float16 numbers is 2, so adding something near 1 to a large total can round it away. "Another run" draws a new atomic order.

When you need the same bits every run

  • torch.use_deterministic_algorithms(True) makes PyTorch use deterministic implementations where they exist and raise an error where they do not (for example index_add_ and scatter_add_ on CUDA, which use atomics); it also stops Inductor from autotuning in ways that change numerics. "Deterministic operations tend to have worse performance" (PyTorch reproducibility notes; docstring of PyTorch 2.14.1).
  • torch.backends.cudnn.benchmark = False makes cuDNN choose its algorithm deterministically; torch.backends.cudnn.deterministic = True also requires that algorithm to be deterministic.
  • cuBLAS gives "the same bit-wise results at every run when executed on GPUs with the same architecture and the same number of SMs", but not with several concurrent streams sharing a handle unless you set CUBLAS_WORKSPACE_CONFIG=:4096:8 (about 24 MiB more memory) or :16:8 (cuBLAS 13.4, results reproducibility) docs. A different GPU model, SM count or library version may still change the bits: compare across machines with a tolerance, not with equality.

FP8 needs a scale, and one outlier can spoil a per-tensor scale

float8 e4m3 has only 3 mantissa bits and a range of ±448 (its smallest normal is 2−6), so values are multiplied by a scale before the cast and divided after. A million activations whose rows differ in scale, plus one outlier of 900, cast to e4m3 computed here, PyTorch 2.14.1:

The outlier fixes the per-tensor scale at 448/900, which pushes the small rows below e4m3's range: more values flush to zero than with no scale at all. One scale per row avoids it; this is why FP8 training recipes use fine-grained scales (per tile or per block, as in the MX formats), owned by the hardware formats and tensor-core pages. Note also what PyTorch's cast did with values above 448: it saturated them to 448 (even infinity), rather than producing NaN; a kernel that casts differently will not match it bit for bit.

compute-sanitizer: memory errors, races, uninitialised reads

The programming model page shows how CUDA reports errors and why a bad kernel often fails silently. compute-sanitizer runs your program with instrumented kernels and reports the first bad access with the thread, block and source line (compile with -lineinfo). A testing checklist for a new kernel

  • Sizes that are not multiples of the tile or block (1, 7, 127, 4,097), the first and last block, and one size far bigger than any test you thought of: the parent's Kernel lab records a missing barrier that passed every small test and corrupted 1 to 5 random rows per run only at 4,096 rows.
  • Non-contiguous and transposed inputs, every data type you claim to support, and inputs with large, tiny, zero, infinite and NaN values.
  • Several random seeds; the same input twice (does the output change? then something is racing or using atomics).
  • Gradients: torch.autograd.gradcheck in float64 for a custom backward.
  • compute-sanitizer (all four tools) on a small case before any benchmark.

6. The workflow, common mistakes, and interview questions

One loop, written down

  1. Timeline first (Nsight Systems or torch.profiler with CUDA activity, a few steps after warm-up, NVTX ranges on the phases). Is the GPU busy? If not, the problem is the CPU, launches, data or communication, and no kernel work will help.
  2. Rank the kernels by total GPU time (cuda_gpu_kern_sum, or key_averages() sorted by device time). Work on the top one or two.
  3. Place each on the roofline: bytes and FLOPs it must move and do (Performance math), against its measured time. Far below both limits means latency or occupancy; near one limit means that limit.
  4. Nsight Compute on that kernel, top-down: Speed of Light, then the section it points to, then source counters. Treat the rule estimates as hypotheses (section 4).
  5. Change one thing, check the output against the reference (section 5), and re-measure with the honest harness (section 2): warm, cold-cache, many runs, median and spread, same clocks.
  6. Log the change, the numbers, the environment. Simon Boehm's matmul worklog is the model: each kernel, its GFLOP/s, and what the profiler blamed.

Common mistakes

Timing an asynchronous launch with time.time()
Measures the queueing (0.18 ms against 4.15 ms in section 1). Synchronise before both clock reads, or use events.
Including the first call
Compilation, autotuning, algorithm search and allocator growth land in it (a first softmax about 13 times slower than the fifteenth call here, median of 9 processes). Warm up every shape.
A hot cache
A tensor smaller than L2 timed in a loop reports cache bandwidth (1.7× too fast at 16 MB here). Flush or rotate buffers, as do_bench does.
Reporting the minimum, or the mean of a noisy run
Report the median and the spread over several runs, and the machine's load. Three runs on this laptop disagreed by a factor of 2.
Comparing an ncu duration with a training-step time
Nsight Compute locks clocks, flushes caches and serialises kernels; its durations are for comparing kernels under the same conditions, not for predicting the step.
Profiling the whole run with Nsight Compute
Dozens of replay passes per kernel (42 for the full set in NVIDIA's samples). Filter with -k, -c and NVTX ranges.
Believing the guided analysis's estimated speedup
64.67% estimated, 0.14% measured for NVIDIA's own uncoalesced sample. Measure.
Requiring bit-equality with PyTorch
Different summation order gives different bits. Compare with a tolerance built from the format and K; require bit-equality only from the same kernel on the same GPU with deterministic settings.
A tolerance so loose it hides a bug
bfloat16's default rtol of 1.6% would hide an off-by-one tile that changes a few per cent of one row. Look at the worst element and its location, and test float32 versions of the kernel with tight tolerances.
Testing only sizes that are multiples of the tile
Boundary handling is where kernels break: test 1, 7, 127, 4,097 and a size larger than any you expect.

Interview questions

Nsight Systems or Nsight Compute first? Why?
Systems: one cheap pass shows where wall time goes (gaps, launches, copies, communication). Compute replays one kernel dozens of times to explain it; use it only on kernels the timeline convicted.
How do you time a CUDA kernel from PyTorch?
Warm up; torch.cuda.Event(enable_timing=True) pairs recorded around the call, synchronise, elapsed_time; flush L2 or rotate inputs; many runs; report the median and spread; or just triton.testing.do_bench (mean by default; ask for the median).
Speed of Light shows Compute 20%, Memory 25%. What now?
Latency-bound: neither unit is busy. Check achieved occupancy and its limiter, waves per SM (tail), warp stall reasons (long scoreboard: memory latency, not enough loads in flight), and whether the kernel is simply tiny (then fuse it or use CUDA graphs).
How do you detect shared-memory bank conflicts?
l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum against ..._wavefronts_mem_shared_op_ld.sum in Memory Workload Analysis Tables; the Source Counters section points to the line. Typical fix: pad ([32][33]) or swizzle.
Why does my fused kernel not match PyTorch exactly?
Floating-point addition is not associative and the kernel sums in a different order (tiles, split-K, warp shuffles, atomics). Compare with a tolerance built from the output format and the reduction length, against a float64 reference of the same rounded inputs.
Why accumulate in float32 with bfloat16 inputs?
bfloat16 has 8 significant bits; a running sum in it loses each small term against a large total, with error growing about linearly in K (14.6% of the scale at K = 65,536 here, against about 10−6 in float32).
Your training loss differs between two identical runs. Where do you look?
Atomics-based ops (index_add_, scatter_add_, some backward passes), cuDNN autotuning (cudnn.benchmark), split-K choices that depend on the GPU, multiple streams sharing a cuBLAS handle, data-loader order and seeds. torch.use_deterministic_algorithms(True) plus CUBLAS_WORKSPACE_CONFIG=:4096:8 narrows it.
What does compute-sanitizer's racecheck catch that tests miss?
Shared-memory hazards between threads of a block (a missing __syncthreads()), which may only corrupt results at large sizes or on another GPU.

The tooling is starting to run this loop itself

AMD's Hyperloom, released with ROCm 10.0 on August 27, 2026, is an "agentic system that automates end-to-end inference workload optimization" by profiling, analysing, planning, applying changes and validating correctness in a loop, and "AMD reports that Hyperloom cuts what used to be weeks of manual optimization work down to hours" (a vendor claim; ROCm blog). Dream-RSI (arXiv 2609.14858, September 2026) reports, among other domains, GPU kernel engineering with "competitive or improved discovery quality while substantially reducing discovery cost". Either way, an agent's reported speedup is only as good as the method in sections 2 and 5: no warm-up, a hot cache or an unchecked output make it worthless. The old page also cited a "Phi-Bench" result (Hardware and Edge category at 5.4%); it could not be found and is left out as unconfirmed.

Pick the number formats of a dot product (the inner loop of every matmul and attention score), its length and its summation order, and see how far the result lands from the exact answer and whether torch.testing.assert_close's defaults would pass it.

How it works: each trial draws two vectors of N(0, 1) numbers with a seeded generator, rounds them to the input format, forms the products (exact in double precision, then rounded to the accumulator), adds them in the chosen order rounding after every addition, and rounds the result to the output format. The error is measured against the exact dot product of the rounded inputs (computed with Shewchuk's exact summation), divided by √Σ(aibi)². "Passes" applies assert_close's default rtol and atol for the output type (float32 1.3e-6 and 1e-5, bfloat16 0.016 and 1e-5, float16 0.001 and 1e-5) against the exact result rounded once to that type. The rounding model matches PyTorch 2.14.1's casts on 2,055 test values and six whole experiments bit for bit (check/check_js.mjs against code/reference.py). Real tensor cores may compute products and partial sums with internal widths this model does not capture.
