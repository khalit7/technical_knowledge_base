A GPU number is only as good as the method behind it: time the GPU's queue, not the CPU's call; find where the time goes with a timeline before asking why one kernel is slow; and call a kernel right only when its gap from a higher-precision reference is no bigger than its number format and summation order explain.

You need launches, warps and occupancy (The CUDA programming model, which also owns the CUDA error model, CUDA_LAUNCH_BLOCKING and what a launch costs), coalescing and bank conflicts (GPU memory hierarchy), and for step 2 of the loop the roofline (Performance math, which owns FLOP counting and MFU). The parent's section 9 is this page in one screen.

  • Stream: the queue of GPU work the CPU writes into; event: a marker in that queue that the GPU timestamps.
  • Timeline (trace): every CPU call, kernel and copy on one time axis, one row per thread or stream.
  • Replay: Nsight Compute running one kernel many times, reading a different group of hardware counters each pass.
  • Speed of Light: each unit's throughput as a percentage of its peak; achieved occupancy: active warps as a share of the SM's maximum; a warp stall: the reason a warp's next instruction cannot issue.
  • ulp: the spacing between neighbouring floating-point numbers at a value; rtol, atol: the relative and absolute tolerances of a comparison.

1. Why a stopwatch around GPU code lies

The CPU and the GPU are two workers with a queue between them. c = a @ b on a GPU tensor does not wait for the multiply: the CPU writes a command into the stream and returns at once, and the GPU picks it up when it is free. This asynchronous execution is why PyTorch on a GPU is fast (the CPU runs ahead and keeps the queue full), and why a CPU clock around that line measures how long it took to queue the work. Fig. 1 times one 2,048 × 2,048 float32 multiply four ways, drawn to scale: the CPU thread in front, the GPU stream behind, a launch as dots flowing from one to the other, the host clock as green posts and events as purple flags. Pick a way:

  1. The clock starts. t0 = time.perf_counter(). The GPU is idle.
  2. The CPU queues the multiply. c = a @ b writes a command into the queue and returns after 0.18 ms; the launch flows to the GPU.
  3. The clock stops. t1 is read straight away: the clock says 0.18 ms.
  4. The GPU does the work afterwards. The multiply runs for 4.15 ms after the clock stopped. The reported time is 23 times too small.
  1. Synchronise, then start the clock. The queue is empty, so the clock measures only this call.
  2. The CPU queues the multiply. The call returns after 0.18 ms, as before.
  3. The CPU waits in synchronize(). torch.cuda.synchronize() blocks until the queue is empty, while the GPU runs the multiply.
  4. The GPU finishes; the clock stops. The clock says 4.24 ms: the multiply plus the launch and the synchronise.
  1. start.record() puts a marker in the queue. The marker is a command too: the GPU stamps the time when it reaches it.
  2. The CPU queues the multiply, then end.record(). Both calls return at once.
  3. The GPU runs the multiply between the markers. The CPU synchronises before asking for the result.
  4. elapsed_time() reads the two stamps. 4.15 ms of GPU time, without the CPU's launch overhead.
  1. Four earlier multiplies are still queued. The loop above queued them and nobody synchronised.
  2. The clock starts, one more multiply is queued. The CPU returns at once; the GPU is still busy with the earlier work.
  3. synchronize() waits for the whole queue. It cannot wait for "my" kernel only: it drains everything.
  4. The clock stops. It says 19.93 ms, about 4.8 multiplies, not one.

measured on Apple M1 Pro GPU PyTorch 2.14.1, MPS backend; each block is the median of 25 repetitions in each of 3 runs, the median of the 3 run medians shown; the runs are listed under the counters. Without a synchronise the clock read 0.18 ms against 4.15 ms of GPU time. The same queue exists on every NVIDIA GPU; only the durations differ.

Predict: four earlier multiplies are still in the queue when you start the clock, then you queue one more and synchronise. What does the clock say, roughly?
The synchronise waits for everything in the queue, including the four multiplies queued before the clock started. measured: 19.93 ms against 4.243 ms for one. The fix is a synchronize() before reading the start time too.

So there are two honest ways: make the CPU wait for the queue to drain before both clock reads (torch.cuda.synchronize()), or put two events into the stream and ask the GPU how far apart they were:

# warm up first (section 2), then:
start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
torch.cuda.synchronize()          # nothing else in the queue
start.record()                    # a marker in the stream
y = f(x)
end.record()
torch.cuda.synchronize()          # or end.synchronize()
ms = start.elapsed_time(end)      # GPU time between the markers, in ms

Event timing has "a resolution of around 0.5 microseconds" (CUDA Runtime API 13.4, cudaEventElapsedTime) docs. Events leave out the CPU's own overhead, a synchronised clock includes it: use events for "how fast is this kernel" and a synchronised clock or a timeline for "how fast is this step", because in launch-bound code the CPU is the cost. An event pair also counts any time the GPU sat idle between the markers waiting for the CPU, so a slow Python loop inflates event times too.

Know what your timer brackets. A tiny multiply of 4,096 numbers measured 0.157 ms with an event pair and 0.196 ms with a clock and a synchronise per call, but 4.96 µs per call when 200 calls were queued back to back with one synchronise at the end measured. The GPU work is a few microseconds; the rest is the measuring (Apple's MPS events mark command-buffer boundaries and carry a fixed overhead; CUDA's are lighter, but a kernel of a few microseconds timed alone is still mostly launch and synchronisation, which is why CUDA graphs and Triton's do_bench_cudagraph exist). For tiny kernels, time many back-to-back calls and divide, and say so.

The same trap inside PyTorch code you did not write
Any operation that needs a value on the CPU forces a synchronise: loss.item(), print(tensor), tensor.cpu(), if tensor.any():, a nonzero() whose size the CPU must know. In a training loop these silently serialise the CPU and GPU, and a stopwatch then "works" by accident. The timeline in section 3 shows where they are.

2. Benchmarking honestly: warm-up, caches, spread, clocks

With correct synchronisation, the same kernel still gives different times depending on when and how you time it. Four effects account for almost every wrong benchmark, each measured here, each with its rule.

Warm-up: the first call pays for everything that happens once

measured on Apple M1 Pro GPU: each line is the median over 9 fresh Python processes (3 runs × 3) of the k-th call, each call synchronised; the bars show the slowest and fastest process. The first softmax took 5.78 ms (median; one process took 17.9 ms) against 0.45 ms by the 15th call, a first softmax about 13 times slower; the first matmul 26.9 ms against 4.27 ms. In the profiled training step of section 3 the first step on the GPU took 905 ms and the later ones about 7 ms.

The first call pays one-time costs: device set-up, compiling or loading the kernel, choosing an algorithm (cuDNN's benchmark mode tries several), growing the memory allocator. Triton kernels compile and autotune on first call, and torch.compile compiles once per new input shape. Rule: run until the time stops falling, then time; for compiled or autotuned code, warm up every shape you will time.

The first call of each operation is the slow one

measured on Apple M1 Pro GPU: median of 9 fresh processes per call; bars, slowest and fastest process.

Caches: timing the same small tensor in a loop measures the cache

A GPU's last-level cache (the L2) is large: 40 MB on an A100 40 GB (NVIDIA's Ampere post), 50 MB on an H100 SXM (Hopper post), 96 MB on an RTX 5090 (RTX Blackwell whitepaper). Read the same 16 MB buffer a hundred times and every read after the first comes from it. In a real model the input was just written or evicted by another kernel, so the honest number is the cold one.

Predict: x.sum() over a 16 MB tensor on this laptop (its GPU's last-level cache is 24 MB), timed hot (the same tensor again and again) and cold (rotating through 512 MB of tensors). How different?
measured: hot 255 GB/s, cold 154 GB/s, so the hot loop reports 1.7× too fast at 16 MB here. At 128 MB, far beyond the cache, both are 169 GB/s. The chart shows where the gap opens and closes.

The M1 Pro's 24 MB system-level cache is an independent measurement (metal-benchmarks). Rule: flush the cache before each timed run, or rotate through buffers larger than it, and say which.

Spread: report the median and the spread, never one number

measured on Apple M1 Pro GPU: 300 event timings of the same 1,024 × 1,024 float32 multiply in each of three runs, minutes apart, 1-minute load average between 4.3 and 4.7 (other agents were running). Run medians 0.721, 1.554, 1.209 ms: the same code, three runs that disagreed by a factor of 2. A few slow outliers pull the mean (run 2: mean 1.521, maximum 11.82 ms).

Rule: the median (or several quantiles) of many runs, whole runs repeated, the spread and the machine's load reported; distrust any comparison of two numbers taken at different times on a shared machine. The minimum is tempting because it is stable, but it describes a lucky run, not the typical one.

Clocks: the GPU changes speed while you measure

GPUs boost their clock when cool and throttle when hot or at their power limit, so back-to-back runs differ. Either lock the clocks for the measurement (nvidia-smi -lgc <min,max> "defines closest desired locked GPU clock speed in MHz", -rgc resets; both need root) or record clock and power beside every result (nvidia-smi dmon prints "one line of monitoring data per monitoring cycle"; the third-party nvitop is a friendlier live view) (nvidia-smi docs) docs only, not run here. On a workstation a fixed power limit (nvidia-smi -pl, in watts) and a note of the cooling matter too, because fans and room temperature change sustained clocks.

Nsight Compute locks clocks itself while profiling. NVIDIA's own 2023 sample reports show it: the device's maximum clock is 1,650 MHz, but every kernel ran at 0.94 to 1.05 GHz read from NVIDIA's reports. So a duration from ncu is not the duration in your training run; compare ncu with ncu.

Correction to the old page: ncu's clock default
The old page said ncu "locks clocks to base by default during replay". That was true until Nsight Compute 2025.4; the default of --clock-control became boost in 2026.1 (release notes; ncu --help in 2026.3.1 shows (=boost)). NVIDIA's 2023 reports above ran under the old base default. To compare ncu durations with Nsight Systems, NVIDIA recommends locking clocks with nvidia-smi and passing --clock-control none.

triton.testing.do_bench: the harness that does all of this

Read in the Triton 3.8.0 source real source: it runs your function once and synchronises; times 5 runs to estimate the cost; fits as many warm-up runs as take 25 ms and as many timed runs as take 100 ms; then for each timed run zeroes a 256 MB buffer ("to make sure that the L2 cache doesn't contain any input data before the run") and records one event pair around your function. It returns the mean by default; ask for return_mode="median" (or "min", "max", "all", or quantiles=[0.2, 0.5, 0.8]). Its sibling do_bench_cudagraph captures the calls in a CUDA graph to remove launch overhead.

Correction to the old page: do_bench
The old page said do_bench "has flush_l2=True". It has no such argument in Triton 3.8.0: flushing is always on (the 256 MB zeroing). It also returns the mean, not the median, unless you ask (testing.py).
do_bench ported to MPS, and the rules for a fair comparison

Ported line by line to MPS (one synchronise added before each start event, because MPS refuses event pairs that land in one command buffer) measured on Apple M1 Pro GPU: a 16 MB sum gave a median of 0.36 ms with the flush and 0.25 ms without, across 3 runs; the 2,048 matmul 4.27 ms. The flush difference matches the hot and cold measurement above; the absolute sum times include MPS's per-event overhead, which CUDA events do not have.

  • Check the output first (section 5): a kernel that skips work is very fast.
  • Compare against the strongest baseline: torch.compile rather than eager PyTorch, cuBLAS or cuBLASLt with the same data type, layout and fused epilogue, FlashAttention rather than a naive attention.
  • Report achieved throughput next to the limit: GB/s against the memory bandwidth for a memory-bound kernel, TFLOP/s against the peak for the data type for a compute-bound one. "2× faster" means little; "from 40% to 80% of peak bandwidth" can be judged.
  • Write down the environment: GPU model and count, driver, CUDA toolkit (13.4.2 is current in October 2026; the old page's "13.3 current" is out of date), PyTorch and Triton versions, clocks (locked or not), power limit, input shapes and data types, and the machine's load. Every measurement on this page records its versions and load in src/out/.

What sits under the tools; Nsight Systems commands, capture ranges and report scripts (docs only, not run here)

Under the first two sits CUPTI (the CUDA Profiling Tools Interface), NVIDIA's library for collecting kernel start and end times, copies and counters from inside a process. Nsight Systems records CPU threads, CUDA API calls, kernels, copies, NCCL, OS calls and your own NVTX ranges (named intervals you mark in code), its kernel times through CUPTI (Nsight Compute's Profiling Guide). torch.profiler is built on Kineto ("an in-process profiling library integrated with the PyTorch Profiler", pytorch/kineto), whose CUDA backend is CUPTI (its CuptiActivityApi sources); it names every operator, its input shapes and the kernels it launched.

nsys profile -t cuda,nvtx,osrt -o step python train.py   # default -t is cuda,opengl,nvtx,osrt
nsys profile --capture-range=cudaProfilerApi ...          # record only between cudaProfilerStart/Stop
nsys stats step.nsys-rep                                  # summary tables in the terminal

In Python, mark phases so the timeline is readable: torch.cuda.nvtx.range_push("forward") ... range_pop() (or the torch.cuda.nvtx.range context manager), and limit the capture to a few steps with torch.cuda.profiler.start()/stop() plus --capture-range=cudaProfilerApi. The nsys stats report scripts include cuda_gpu_kern_sum ("a summary of CUDA kernels and their execution times"), cuda_api_sum, cuda_gpu_mem_time_sum, nvtx_sum and osrt_sum. torch.profiler, run on a real training step

A two-block MLP (LayerNorm, 512 to 2,048 to 512 with GELU, residual) plus a 1,000-way classifier, batch 256, one AdamW step, profiled with 1 step skipped, 1 warm-up step and 2 recorded; on CUDA add ProfilerActivity.CUDA run here:

from torch.profiler import profile, schedule, record_function, ProfilerActivity

The same operator, two meanings. On the CPU, aten::mm is the biggest row: the CPU does the multiply, so its "self CPU" time is the work (498.3 µs per call). With the model on the GPU, the same operator costs 38.5 µs of CPU time per call: only the time to queue it. PyTorch 2.14 has no MPS profiler activity (its activities are CPU, XPU, MTIA, CUDA, HPU, PrivateUse1), so the GPU's own time is missing and the waiting shows up wherever the CPU blocked: the step's own row holds 6.76 ms of "self" time, the synchronise at the end of each step. That is what a CUDA profile looks like if you forget ProfilerActivity.CUDA, and why on a GPU you sort by the device columns (self_cuda_time_total, called device time in PyTorch 2.14's tables).

4. Why is this kernel slow? Nsight Compute

The timeline says one kernel takes 30% of the step. Is it moving more bytes than it needs, leaving the arithmetic units idle, running too few warps, or stalling on shared memory? The GPU has thousands of hardware counters (instructions issued, bytes read from DRAM, cache hits, cycles each unit was busy), but only a few can be read in one run. Nsight Compute (ncu) therefore replays the kernel: save the memory it can touch, run it, restore the memory, run it again with other counters, and so on, then turn the counters into metrics, sections and advice.

What replay costs real tool, NVIDIA's reports: every one of the six sample reports shipped with Nsight Compute 2026.3.1 (collected with --set full) needed 42 passes of the same kernel, and for the matrix transpose the tool saved and restored 545 MB before each pass. Between passes "Nsight Compute flushes all GPU caches by default between replay passes"; it also serialises kernels that would otherwise overlap and locks the clocks. So its durations describe a cold-cache, locked-clock, serialised kernel, and it belongs on a handful of kernels the timeline already convicted, never on a whole training run (Profiling Guide, kernel replay and workload durations).

ncu --set full -k regex:softmax -c 1 -o sm python train.py   # first matching kernel only
ncu --import sm.ncu-rep --page details                          # the text in the Report reader tab
More ncu flags: sets, NVTX filters, raw CSV, source lines

Read a report top-down: three real before-and-after pairs

The Speed of Light (SOL) section comes first: "for each unit, the throughput reports the achieved percentage of utilization with respect to the theoretical maximum", and its two headline numbers are the highest such percentage among the compute units (Compute (SM)) and among the memory units (Memory). They place the kernel: memory high and compute low is memory-bound (move fewer bytes); compute high is compute-bound (cheaper instructions, tensor cores, lower precision); both low is latency-bound (too few warps, stalls, a tail of idle SMs, or a tiny kernel). Then follow the section the numbers point to. The lesson of the first pair: the rules are hypotheses
Nsight Compute's guided analysis estimated a 64.67% speedup from fixing the uncoalesced loads of addConstDouble3. Occupancy and warp stalls: where a warp's cycles go

Each SM sub-partition's scheduler can issue one instruction per cycle from any eligible warp. A warp is stalled when its next instruction cannot go, and the Warp State section splits each warp's cycles between issued instructions by reason. Stalls only cost time when no warp is eligible, so read them together with achieved occupancy (how many warps were there to hide them) and the issue rate. The same before-and-after pairs:

  • Long scoreboard: waiting for data from L1, L2 or DRAM; a memory-latency problem (more warps or loads in flight, fewer loads).
  • MIO throttle and short scoreboard: mostly shared-memory or special-function pressure (the bank-conflict pair). Tex throttle: the texture/L1 queue is full (the Sobel double kernel).
  • Barrier: warps waiting at __syncthreads() for slower ones. Math pipe throttle: an arithmetic pipe is saturated, often good news.
  • Achieved occupancy (sm__warps_active.avg.pct_of_peak_sustained_active) against the theoretical: the limiter (registers, shared memory, block size) is in the same section (occupancy rules). High occupancy with high stalls means every warp waits on the same thing; more warps will not help.
  • Memory throughput (gpu__dram_throughput.avg.pct_of_peak_sustained_elapsed, shown as "DRAM Throughput"): near its peak, the kernel is done unless it can move fewer bytes.

The scoreboards are real bits in every SASS instruction: which instruction sets one and which waits on it is decoded in section 4 of The compiler stack ("The bits nobody prints"), with its scoreboard replay.

5. Is the answer right? References, tolerances, order and atomics

A wrong kernel rarely crashes; it returns plausible numbers. And a correct kernel rarely returns exactly PyTorch's bits, because floating point rounds after every operation and addition is not associative: (a + b) + c and a + (b + c) can differ in the last bits, and a GPU kernel adds in whatever order its threads, tiles and atomics dictate. So "is it right?" means: does it differ from a trustworthy reference by no more than this format's rounding and this summation explain?

TF32 keeps float32's 8-bit exponent with a 10-bit mantissa (NVIDIA Ampere post). eps is the gap between 1 and the next number: one rounding changes a value by at most eps/2 relative. assert_close passes when |actual − expected| ≤ atol + rtol × |expected| for every element. The defaults fit one rounding, not a sum of thousands of terms. Floating point from zero is on Numerical computing for ML; the formats themselves on Quantization and Precision.

How to compare against a reference

  1. Same inputs, more precision. Round the inputs to the kernel's input type first, then compute the reference in float64 (or float32 for a float16 kernel) from those rounded inputs. Otherwise you measure the input rounding, not the kernel.
  2. Tolerance from the output type and the problem size. A float16 output can be off by one rounding (eps/2 relative) plus the accumulated error of the sum, which grows with the reduction length K. Near zero, after cancellation, a relative tolerance is meaningless; compare the error to the scale of the terms instead (for a dot product, √Σ(aibi)²).
  3. Look at the worst element and where it is, not only pass or fail: an error concentrated in the last tile or the last row is a bug; an error spread evenly at the rounding level is arithmetic.
Predict: a correct float16 matmul (float32 accumulation) on this laptop's GPU, 256 × 256 output, K = 4,096, compared with assert_close's float16 defaults against a float64 reference rounded to float16. How many of the 65,536 elements fail?
measured on Apple M1 Pro GPU: 23 fail at K = 4,096 and 51 at 16,384 (none at 64 and 512). The worst error is 0.16% of the scale of the terms, about what rounding the result to float16 alone explains; the failing elements are those whose result is small after cancellation, where rtol = 0.001 of a small number is tighter than the rounding. bfloat16's default rtol of 0.016 passes every element at every K. Defaults are a starting point; set the tolerance from the format and K, and say what you chose.

Accumulate in float32, even when inputs are 16-bit

computed here (NumPy, 256 random dot products per point, inputs N(0,1) rounded to float16; products are exact in float32): median error relative to √Σ(aibi)². A running sum kept in float16 or bfloat16 loses accuracy roughly in proportion to K: at K = 65,536 the bfloat16 running sum is off by 14.6% of the scale, because each small product is rounded against a large running total. Float32 accumulation keeps the error near 10−6, and a pairwise tree (how a parallel reduction adds) keeps it lower and nearly flat. This is why tensor-core matmuls on 16-bit inputs accumulate in float32, and why a reduction kernel keeps its partial sums in float32.

Workbench: any input, accumulator and output format, length and summation order

Pick the number formats of a dot product (the inner loop of every matmul and attention score), its length and its summation order, and see how far the result lands from the exact answer and whether torch.testing.assert_close's defaults would pass it.

How it works: each trial draws two vectors of N(0, 1) numbers with a seeded generator, rounds them to the input format, forms the products (exact in double precision, then rounded to the accumulator), adds them in the chosen order rounding after every addition, and rounds the result to the output format. The error is measured against the exact dot product of the rounded inputs (computed with Shewchuk's exact summation), divided by √Σ(aibi)². "Passes" applies assert_close's default rtol and atol for the output type (float32 1.3e-6 and 1e-5, bfloat16 0.016 and 1e-5, float16 0.001 and 1e-5) against the exact result rounded once to that type. The rounding model matches PyTorch 2.14.1's casts on 2,055 test values and six whole experiments bit for bit (check/check_js.mjs against code/reference.py). Real tensor cores may compute products and partial sums with internal widths this model does not capture.

Atomics make the order change from run to run. When many threads add into one location with atomicAdd, the hardware decides the order, so the same kernel on the same input returns different bits each run. When you need the same bits every run

  • torch.use_deterministic_algorithms(True) makes PyTorch use deterministic implementations where they exist and raise an error where they do not (for example index_add_ and scatter_add_ on CUDA, which use atomics); it also stops Inductor from autotuning in ways that change numerics. "Deterministic operations tend to have worse performance" (PyTorch reproducibility notes; docstring of PyTorch 2.14.1).
  • torch.backends.cudnn.benchmark = False makes cuDNN choose its algorithm deterministically; torch.backends.cudnn.deterministic = True also requires that algorithm to be deterministic.
  • cuBLAS gives "the same bit-wise results at every run when executed on GPUs with the same architecture and the same number of SMs", but not with several concurrent streams sharing a handle unless you set CUBLAS_WORKSPACE_CONFIG=:4096:8 (about 24 MiB more memory) or :16:8 (cuBLAS 13.4, results reproducibility) docs. A different GPU model, SM count or library version may still change the bits: compare across machines with a tolerance, not with equality; require bit-equality only from the same kernel on the same GPU with deterministic settings.

compute-sanitizer: memory errors, races, uninitialised reads

A bad kernel often fails silently (the error model is on The CUDA programming model). compute-sanitizer, shipped with the toolkit, runs your program with instrumented kernels and reports the first bad access with the thread, block and source line (compile with -lineinfo). Its four tools, quoted from compute-sanitizer --help (2026.3.0, CUDA 13.4.2) real tool, help text:

A testing checklist for a new kernel

  • Sizes that are not multiples of the tile or block (1, 7, 127, 4,097), the first and last block, and one size far bigger than any test you thought of: the parent's Kernel lab records a missing barrier that passed every small test and corrupted 1 to 5 random rows per run only at 4,096 rows.
  • Poison the output (fill it with NaN, or use fresh memory) and run the reference after the kernel under test, not before. Writing kernels, section 8, records "a kernel that wrote nothing passed the test": an RMSNorm whose loop count came out 0 wrote nothing and still passed, because its output buffer most likely still held the library's answer from the run just before.
  • Non-contiguous and transposed inputs, every data type you claim to support, and inputs with large, tiny, zero, infinite and NaN values.
  • Several random seeds; the same input twice (does the output change? then something is racing or using atomics).
  • A tolerance tight enough to see a bug: bfloat16's default rtol of 1.6% would hide an off-by-one tile that changes a few per cent of one row, so test a float32 version of the kernel with tight tolerances too.
  • Gradients: torch.autograd.gradcheck in float64 for a custom backward.
  • compute-sanitizer (all four tools) on a small case before any benchmark.
FP8 needs a scale, and one outlier can spoil a per-tensor scale (measured)

float8 e4m3 has only 3 mantissa bits and a range of ±448 (its smallest normal is 2−6), so values are multiplied by a scale before the cast and divided after. A million activations whose rows differ in scale, plus one outlier of 900, cast to e4m3 computed here, PyTorch 2.14.1:

The outlier fixes the per-tensor scale at 448/900, which pushes the small rows below e4m3's range: 12,118 non-zero values flush to zero against 6,091 with no scale at all and 11 with one scale per row. This is why FP8 recipes use fine-grained scales (per tile or per block, as in the MX formats), owned by Quantization and Precision, the hardware formats and tensor-core pages. Note also what PyTorch's cast did with values above 448: it saturated them to 448 (even infinity), rather than producing NaN; a kernel that casts differently will not match it bit for bit.

6. Depth: interview rehearsal, and agents that run this loop

Interview rehearsal: eight questions with short answers
Nsight Systems or Nsight Compute first? Why?
Systems: one cheap pass shows where wall time goes (gaps, launches, copies, communication). Compute replays one kernel dozens of times to explain it; use it only on kernels the timeline convicted.
How do you time a CUDA kernel from PyTorch?
Warm up; torch.cuda.Event(enable_timing=True) pairs recorded around the call, synchronise, elapsed_time; flush L2 or rotate inputs; many runs; report the median and spread; or just triton.testing.do_bench (mean by default; ask for the median).
Speed of Light shows Compute 20%, Memory 25%. What now?
Latency-bound: neither unit is busy. Check achieved occupancy and its limiter, waves per SM (tail), warp stall reasons (long scoreboard: memory latency, not enough loads in flight), and whether the kernel is simply tiny (then fuse it or use CUDA graphs).
How do you detect shared-memory bank conflicts?
Bank conflicts against wavefronts in Memory Workload Analysis Tables (the metric table in section 4), MIO throttle in Warp State; the Source Counters section points to the line. Typical fix: pad ([32][33]) or swizzle.
Why does my fused kernel not match PyTorch exactly?
Floating-point addition is not associative and the kernel sums in a different order (tiles, split-K, warp shuffles, atomics). Compare with a tolerance built from the output format and the reduction length, against a float64 reference of the same rounded inputs.
Why accumulate in float32 with bfloat16 inputs?
bfloat16 has 8 significant bits; a running sum in it loses each small term against a large total, with error growing about linearly in K (14.6% of the scale at K = 65,536 here, against about 10−6 in float32).
Your training loss differs between two identical runs. Where do you look?
Atomics-based ops (index_add_, scatter_add_, some backward passes), cuDNN autotuning (cudnn.benchmark), split-K choices that depend on the GPU, multiple streams sharing a cuBLAS handle, data-loader order and seeds. torch.use_deterministic_algorithms(True) plus CUBLAS_WORKSPACE_CONFIG=:4096:8 narrows it.
What does compute-sanitizer's racecheck catch that tests miss?
Shared-memory hazards between threads of a block (a missing __syncthreads()), which may only corrupt results at large sizes or on another GPU.
Agents that run this loop, and why the method still decides (dated, 2026)

AMD's Hyperloom, released with ROCm 10.0 on August 27, 2026, is an "agentic system that automates end-to-end inference workload optimization" that profiles, plans, applies changes and validates them in a loop; AMD says it cuts weeks of tuning to hours (a vendor claim; ROCm blog; the 2026-09-14 tech news issue). Dream-RSI (arXiv 2609.14858, September 2026) reports, among other domains, GPU kernel engineering with "competitive or improved discovery quality while substantially reducing discovery cost", and Φ-Bench (arXiv 2609.10226) finds Hardware and Edge the worst category for frontier models at 5.4%. An agent's reported speedup is only as good as sections 2 and 5: no warm-up, a hot cache or an unchecked output make it worthless.
