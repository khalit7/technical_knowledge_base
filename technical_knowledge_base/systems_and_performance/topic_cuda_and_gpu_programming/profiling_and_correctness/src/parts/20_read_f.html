5. Is the answer right? References, tolerances, order and atomics

The problem. A new kernel rarely crashes when it is wrong; it returns numbers that look plausible. And a correct kernel rarely returns exactly the same bits as PyTorch, because floating-point arithmetic rounds after every operation and addition is not associative: (a + b) + c and a + (b + c) can differ in the last bits. A GPU kernel adds in whatever order its threads, tiles and atomics dictate. So "is it right?" means "does it differ from a trustworthy reference by no more than the rounding of this number format and this summation explains?".

The number formats and their default tolerances

TF32 keeps float32's 8-bit exponent with a 10-bit mantissa ({{NVIDIA Ampere post|https://developer.nvidia.com/blog/nvidia-ampere-architecture-in-depth/}}). eps is the gap between 1 and the next number: a single rounding changes a value by at most eps/2 relative. assert_close passes when |actual − expected| ≤ atol + rtol × |expected| for every element. Floating point itself, from zero, is on {{Numerical computing for ML|n:3f05c17b0d0d81d6af0be4a9a2edba8d}}.

How to compare against a reference

  1. Same inputs, more precision. Round the inputs to the kernel's input type first, then compute the reference in float64 (or float32 for a float16 kernel) from those rounded inputs. Otherwise you measure the input rounding, not the kernel.
  2. Tolerance from the output type and the problem size. A float16 output can be off by one rounding (eps/2 relative) plus the accumulated error of the sum, which grows with the reduction length K. Near zero, after cancellation, a relative tolerance is meaningless; compare the error to the scale of the terms instead (for a dot product, √Σ(aibi)²).
  3. Look at the worst element and where it is, not only a pass or fail: an error concentrated in the last tile or the last row is a bug, an error spread evenly at the rounding level is arithmetic.

The worst error is 0.16% of the scale of the terms, about what rounding the result to float16 alone explains; the failing elements are those whose result is small after cancellation, where rtol = 0.001 of a small number is tighter than the rounding. bfloat16's default rtol of 0.016 passes every element at every K. Defaults are a starting point; set the tolerance from the format and K, and say what you chose.

Accumulate in float32, even when inputs are 16-bit

computed here (NumPy, 256 random dot products per point, inputs N(0,1) rounded to float16; products are exact in float32): median error relative to √Σ(aibi)². A running sum kept in float16 or bfloat16 loses accuracy roughly in proportion to K (at K = 65,536 the bfloat16 running sum is off by 14.6% of the scale), because each small product is rounded against a large running total. Float32 accumulation keeps the error near 10−6, and a pairwise tree (how a parallel reduction adds) keeps it lower and nearly flat. This is why tensor-core matmuls on 16-bit inputs accumulate in float32, and why a reduction kernel should keep its partial sums in float32. Order changes the bits: split-K, tiles and atomics

Exact answer from math.fsum. "Split-K S" cuts the sum into S chunks, sums each, then adds the S partials, which is what a matmul does when it splits the K dimension across thread blocks to use more SMs. Every choice of S gives a different, equally legitimate answer. Sorting by value (all negatives first) is the worst order: the running total grows large before the positives cancel it.

Atomics make the order change from run to run. When many threads add into one location with atomicAdd, the hardware decides the order, so the same kernel on the same input returns different bits each run. Measured on this laptop's GPU with three MLX kernels summing the same 1,048,576 float32 numbers 30 times each measured on Apple M1 Pro GPU:

Sixteen float16 numbers, one large (2,048) and fifteen near 1; every addition is rounded to float16 by the page's float16 model, which matches PyTorch's casts bit for bit on 2,055 test values (check/check_js.mjs). At 2,048 the gap between float16 numbers is 2, so adding something near 1 to a large total can round it away. "Another run" draws a new atomic order.

When you need the same bits every run

  • torch.use_deterministic_algorithms(True) makes PyTorch use deterministic implementations where they exist and raise an error where they do not (for example index_add_ and scatter_add_ on CUDA, which use atomics); it also stops Inductor from autotuning in ways that change numerics. "Deterministic operations tend to have worse performance" ({{PyTorch reproducibility notes|https://docs.pytorch.org/docs/2.14/notes/randomness.html}}; docstring of PyTorch 2.14.1).
  • torch.backends.cudnn.benchmark = False makes cuDNN choose its algorithm deterministically; torch.backends.cudnn.deterministic = True also requires that algorithm to be deterministic.
  • cuBLAS gives "the same bit-wise results at every run when executed on GPUs with the same architecture and the same number of SMs", but not with several concurrent streams sharing a handle unless you set CUBLAS_WORKSPACE_CONFIG=:4096:8 (about 24 MiB more memory) or :16:8 ({{cuBLAS 13.4, results reproducibility|https://docs.nvidia.com/cuda/cublas/index.html#results-reproducibility}}) docs. A different GPU model, SM count or library version may still change the bits: compare across machines with a tolerance, not with equality.

FP8 needs a scale, and one outlier can spoil a per-tensor scale

float8 e4m3 has only 3 mantissa bits and a range of ±448 (its smallest normal is 2−6), so values are multiplied by a scale before the cast and divided after. A million activations whose rows differ in scale, plus one outlier of 900, cast to e4m3 computed here, PyTorch 2.14.1:

The outlier fixes the per-tensor scale at 448/900, which pushes the small rows below e4m3's range: more values flush to zero than with no scale at all. One scale per row avoids it; this is why FP8 training recipes use fine-grained scales (per tile or per block, as in the MX formats), owned by the {{hardware formats|n:3c65c17b0d0d8118beeefaed56da6f8e}} and {{tensor-core|n:3c65c17b0d0d81a7adcaebee2f44a087}} pages. Note also what PyTorch's cast did with values above 448: it saturated them to 448 (even infinity), rather than producing NaN; a kernel that casts differently will not match it bit for bit.

compute-sanitizer: memory errors, races, uninitialised reads

The {{programming model|n:3c65c17b0d0d8162865eec15d9dae87e}} page shows how CUDA reports errors and why a bad kernel often fails silently. compute-sanitizer runs your program with instrumented kernels and reports the first bad access with the thread, block and source line (compile with -lineinfo). Run here without a GPU, a deliberately out-of-bounds kernel could not be checked: compute-sanitizer printed "Target application terminated before first instrumented API call" and ncu "failed to connect to the CUDA driver" (src/out/ncu/nogpu_*.txt). cuda-gdb (also in the toolkit) steps through a kernel thread by thread when the sanitizer has found the line. Expect large slowdowns under the sanitizer; run it on small inputs that still cover the edges.

A testing checklist for a new kernel

  • Sizes that are not multiples of the tile or block (1, 7, 127, 4,097), the first and last block, and one size far bigger than any test you thought of: the parent's {{Kernel lab|n:3c65c17b0d0d81c39f34d5e070d783c1}} records a missing barrier that passed every small test and corrupted 1 to 5 random rows per run only at 4,096 rows.
  • Non-contiguous and transposed inputs, every data type you claim to support, and inputs with large, tiny, zero, infinite and NaN values.
  • Several random seeds; the same input twice (does the output change? then something is racing or using atomics).
  • Gradients: torch.autograd.gradcheck in float64 for a custom backward.
  • compute-sanitizer (all four tools) on a small case before any benchmark.
