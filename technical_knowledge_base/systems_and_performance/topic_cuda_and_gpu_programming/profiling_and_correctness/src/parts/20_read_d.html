4. Why is this kernel slow? Nsight Compute

The timeline says one kernel takes 30% of the step. Is it moving more bytes than it needs, leaving the arithmetic units idle, running too few warps, or stalling on shared memory? The GPU has thousands of hardware counters (instructions issued, bytes read from DRAM, cache hits, cycles each unit was busy), but only a few can be read in one run. Nsight Compute (ncu) therefore replays the kernel: save the memory it can touch, run it, restore the memory, run it again with other counters, and so on, then turn the counters into metrics, sections and advice.

What replay costs real tool, NVIDIA's reports: every one of the six sample reports shipped with Nsight Compute 2026.3.1 (collected with --set full) needed 42 passes of the same kernel, and for the matrix transpose the tool saved and restored 545 MB before each pass. Between passes "Nsight Compute flushes all GPU caches by default between replay passes"; it also serialises kernels that would otherwise overlap and locks the clocks. So its durations describe a cold-cache, locked-clock, serialised kernel, and it belongs on a handful of kernels the timeline already convicted, never on a whole training run ({{Profiling Guide, kernel replay and workload durations|https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html}}).

Read a report top-down: three real before-and-after pairs

The Speed of Light (SOL) section comes first: "for each unit, the throughput reports the achieved percentage of utilization with respect to the theoretical maximum", and its two headline numbers are the highest such percentage among the compute units (Compute (SM)) and among the memory units (Memory). They place the kernel: memory high and compute low is memory-bound (move fewer bytes); compute high is compute-bound (cheaper instructions, tensor cores, lower precision); both low is latency-bound (too few warps, stalls, a tail of idle SMs, or a tiny kernel). The lesson of the first pair: the rules are hypotheses
Nsight Compute's guided analysis estimated a 64.67% speedup from fixing the uncoalesced loads of addConstDouble3. NVIDIA's fixed kernel took 89.86 µs before and 89.73 µs after (64.67% estimated, 0.14% measured): both kernels move the same bytes from DRAM, and DRAM was the limit, so the extra L1 sectors cost nothing. For the transpose the estimate was 87.21% and the real gain 29.7% less time. The rules point at where to look; the clock decides. This is the old page's "trust it as a hypothesis generator" confirmed with NVIDIA's own data.

Occupancy and warp stalls: where a warp's cycles go

Each SM sub-partition's scheduler can issue one instruction per cycle from any eligible warp. A warp is stalled when its next instruction cannot go, and the Warp State section splits each warp's cycles between issued instructions by reason. Stalls only cost time when no warp is eligible, so read them together with achieved occupancy (how many warps were there to hide them) and the issue rate. The same before-and-after pairs:

real tool, NVIDIA's reports: "Warp Cycles Per Issued Instruction" and the "Warp State (All Cycles)" table of each report, first 10 reasons (the rest, under half a cycle, is shown as other); occupancy from the Occupancy section. The transpose with bank conflicts spent 83.8 of 158.5 cycles per instruction in MIO throttle; padding the tile removed it. In the Sobel pair achieved occupancy fell from 95.5% to 83.8% while cycles per issued instruction fell from 280 to 11.9: occupancy is a means, not the goal.

  • Long scoreboard: waiting for data from L1, L2 or DRAM; a memory-latency problem (more warps or loads in flight, fewer loads).
  • MIO throttle and short scoreboard: mostly shared-memory or special-function pressure (the bank-conflict pair). Tex throttle: the texture/L1 queue is full (the Sobel double kernel).
  • Barrier: warps waiting at __syncthreads() for slower ones. Math pipe throttle: an arithmetic pipe is saturated, often good news.
  • Achieved occupancy (sm__warps_active.avg.pct_of_peak_sustained_active) against the theoretical: the limiter (registers, shared memory, block size) is in the same section ({{occupancy rules|n:3c65c17b0d0d8162865eec15d9dae87e}}). High occupancy with high stalls means every warp waits on the same thing; more warps will not help.
  • Memory throughput (gpu__dram_throughput.avg.pct_of_peak_sustained_elapsed, shown as "DRAM Throughput"): near its peak, the kernel is done unless it can move fewer bytes.

The scoreboards are real bits in every SASS instruction: which instruction sets one and which waits on it is decoded in section 3 of {{The compiler stack|n:3f05c17b0d0d81ddbc00fac9e8a2ff89}} ("The bits nobody prints") and its SASS, decoded tab.
