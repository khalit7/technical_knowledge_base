3. Where does the time go? Timelines: Nsight Systems and torch.profiler

The problem. A training step is thousands of kernels, copies and CPU functions. Before optimising any kernel you need to know which ones matter, and whether the GPU is even busy. A timeline (a trace) records every event with its start and end on one time axis, one row per CPU thread and per GPU stream. The questions it answers: is the GPU row full or full of gaps? Which kernels take most of the time? Do copies and communication overlap the compute or wait for it? Where does the CPU block?

The tools and what sits under them

CUPTI (the CUDA Profiling Tools Interface) is NVIDIA's library for collecting GPU activity (kernel start and end times, copies) and hardware counters from inside a process. Nsight Systems (nsys) records a whole-program timeline: CPU threads, CUDA API calls, kernels, memory copies, NCCL, OS calls and your own NVTX ranges (named intervals you mark in code); its kernel times come through CUPTI (Nsight Compute's {{Profiling Guide|https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html}}). torch.profiler is PyTorch's in-process profiler, built on the Kineto library ("an in-process profiling library integrated with the PyTorch Profiler", {{pytorch/kineto|https://github.com/pytorch/kineto}}), whose CUDA backend is CUPTI (its CuptiActivityApi sources). It names every PyTorch operator, its input shapes and the kernels it launched, so it answers "which op is slow" in PyTorch's own vocabulary.

torch.profiler, run on a real training step

A two-block MLP (LayerNorm, 512 to 2,048 to 512 with GELU, residual) plus a 1,000-way classifier, batch 256, one AdamW step, profiled with a schedule of 1 step skipped, 1 warm-up step and 2 recorded steps; the recipe for CUDA is the same with ProfilerActivity.CUDA added run here:

from torch.profiler import profile, schedule, record_function, ProfilerActivity
with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
             schedule=schedule(wait=1, warmup=1, active=2),
             on_trace_ready=lambda p: p.export_chrome_trace("trace.json"),
             record_shapes=True, with_flops=True) as prof:
    for _ in range(5):
        with record_function("forward"): loss = loss_fn(model(x), y)
        ...
        prof.step()                                  # advances the schedule
print(prof.key_averages().table(sort_by="self_cuda_time_total", row_limit=15))

Read the two runs side by side. On the CPU, aten::mm is the biggest row: the CPU does the multiply, so its "self CPU" time is the work (498.3 µs per call). With the model on the GPU, the same operator costs 38.5 µs of CPU time per call: that is only the time to queue it. PyTorch 2.14 has no MPS profiler activity (its activities are CPU, XPU, MTIA, CUDA, HPU, PrivateUse1), so the GPU's own time is missing and the waiting shows up wherever the CPU blocked: the step's own row holds 6.76 ms of "self" time, which is the synchronise at the end of each step. This is exactly what a CUDA profile looks like if you forget ProfilerActivity.CUDA, and why the device columns (self_cuda_time_total, called device time in PyTorch 2.14's tables) are the ones to sort by on a GPU.
