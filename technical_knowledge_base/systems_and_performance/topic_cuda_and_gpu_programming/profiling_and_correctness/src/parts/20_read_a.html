A GPU number is only as good as the method behind it: time the GPU's queue, not the CPU's call; find where the time goes with a timeline before asking why one kernel is slow; and call a kernel right only when its gap from a higher-precision reference is no bigger than its number format and summation order explain.

You need launches, warps and occupancy ({{The CUDA programming model|n:3c65c17b0d0d8162865eec15d9dae87e}}, which also owns the CUDA error model, CUDA_LAUNCH_BLOCKING and what a launch costs), coalescing and bank conflicts ({{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}}), and for step 2 of the loop the roofline ({{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}, which owns FLOP counting and MFU). The parent's {{section 9|n:3c65c17b0d0d81c39f34d5e070d783c1}} is this page in one screen.

  • Stream: the queue of GPU work the CPU writes into; event: a marker in that queue that the GPU timestamps.
  • Timeline (trace): every CPU call, kernel and copy on one time axis, one row per thread or stream.
  • Replay: Nsight Compute running one kernel many times, reading a different group of hardware counters each pass.
  • Speed of Light: each unit's throughput as a percentage of its peak; achieved occupancy: active warps as a share of the SM's maximum; a warp stall: the reason a warp's next instruction cannot issue.
  • ulp: the spacing between neighbouring floating-point numbers at a value; rtol, atol: the relative and absolute tolerances of a comparison.

1. Why a stopwatch around GPU code lies

The CPU and the GPU are two workers with a queue between them. c = a @ b on a GPU tensor does not wait for the multiply: the CPU writes a command into the stream and returns at once, and the GPU picks it up when it is free. This asynchronous execution is why PyTorch on a GPU is fast (the CPU runs ahead and keeps the queue full), and why a CPU clock around that line measures how long it took to queue the work. Fig. 1 times one 2,048 × 2,048 float32 multiply four ways, drawn to scale: the CPU thread in front, the GPU stream behind, a launch as dots flowing from one to the other, the host clock as green posts and events as purple flags. Pick a way:

  1. The clock starts. t0 = time.perf_counter(). The GPU is idle.
  2. The CPU queues the multiply. c = a @ b writes a command into the queue and returns after 0.18 ms; the launch flows to the GPU.
  3. The clock stops. t1 is read straight away: the clock says 0.18 ms.
  4. The GPU does the work afterwards. The multiply runs for 4.15 ms after the clock stopped. The reported time is 23 times too small.
  1. Synchronise, then start the clock. The queue is empty, so the clock measures only this call.
  2. The CPU queues the multiply. The call returns after 0.18 ms, as before.
  3. The CPU waits in synchronize(). torch.cuda.synchronize() blocks until the queue is empty, while the GPU runs the multiply.
  4. The GPU finishes; the clock stops. The clock says 4.24 ms: the multiply plus the launch and the synchronise.
  1. start.record() puts a marker in the queue. The marker is a command too: the GPU stamps the time when it reaches it.
  2. The CPU queues the multiply, then end.record(). Both calls return at once.
  3. The GPU runs the multiply between the markers. The CPU synchronises before asking for the result.
  4. elapsed_time() reads the two stamps. 4.15 ms of GPU time, without the CPU's launch overhead.
  1. Four earlier multiplies are still queued. The loop above queued them and nobody synchronised.
  2. The clock starts, one more multiply is queued. The CPU returns at once; the GPU is still busy with the earlier work.
  3. synchronize() waits for the whole queue. It cannot wait for "my" kernel only: it drains everything.
  4. The clock stops. It says 19.93 ms, about 4.8 multiplies, not one.

measured on Apple M1 Pro GPU PyTorch 2.14.1, MPS backend; each block is the median of 25 repetitions in each of 3 runs, the median of the 3 run medians shown; the runs are listed under the counters. Without a synchronise the clock read 0.18 ms against 4.15 ms of GPU time. The same queue exists on every NVIDIA GPU; only the durations differ.

Predict: four earlier multiplies are still in the queue when you start the clock, then you queue one more and synchronise. What does the clock say, roughly?
The synchronise waits for everything in the queue, including the four multiplies queued before the clock started. measured: 19.93 ms against 4.243 ms for one. The fix is a synchronize() before reading the start time too.

So there are two honest ways: make the CPU wait for the queue to drain before both clock reads (torch.cuda.synchronize()), or put two events into the stream and ask the GPU how far apart they were:

# warm up first (section 2), then:
start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
torch.cuda.synchronize()          # nothing else in the queue
start.record()                    # a marker in the stream
y = f(x)
end.record()
torch.cuda.synchronize()          # or end.synchronize()
ms = start.elapsed_time(end)      # GPU time between the markers, in ms

Event timing has "a resolution of around 0.5 microseconds" ({{CUDA Runtime API 13.4, cudaEventElapsedTime|https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__EVENT.html}}) docs. Events leave out the CPU's own overhead, a synchronised clock includes it: use events for "how fast is this kernel" and a synchronised clock or a timeline for "how fast is this step", because in launch-bound code the CPU is the cost. An event pair also counts any time the GPU sat idle between the markers waiting for the CPU, so a slow Python loop inflates event times too.

Know what your timer brackets. A tiny multiply of 4,096 numbers measured 0.157 ms with an event pair and 0.196 ms with a clock and a synchronise per call, but 4.96 µs per call when 200 calls were queued back to back with one synchronise at the end measured. The GPU work is a few microseconds; the rest is the measuring (Apple's MPS events mark command-buffer boundaries and carry a fixed overhead; CUDA's are lighter, but a kernel of a few microseconds timed alone is still mostly launch and synchronisation, which is why {{CUDA graphs|n:3f05c17b0d0d81b19a6acab65c370b75}} and Triton's do_bench_cudagraph exist). For tiny kernels, time many back-to-back calls and divide, and say so.

The same trap inside PyTorch code you did not write
Any operation that needs a value on the CPU forces a synchronise: loss.item(), print(tensor), tensor.cpu(), if tensor.any():, a nonzero() whose size the CPU must know. In a training loop these silently serialise the CPU and GPU, and a stopwatch then "works" by accident. The timeline in section 3 shows where they are.
