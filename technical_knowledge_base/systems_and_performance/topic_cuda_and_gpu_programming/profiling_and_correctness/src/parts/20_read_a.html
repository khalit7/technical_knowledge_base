Four questions come up every time you try to make GPU code faster, and each has its own tool. Where does the time go? (a timeline of the whole program). Why is this one kernel slow? (hardware counters for that kernel). Is my timing true? (a measuring method that survives asynchronous execution, caches, clocks and a busy machine). Is the answer still right? (a reference, a tolerance that fits the number format, and tools that catch memory errors and races). This page teaches all four from zero, with real tool output wherever it can be produced without an NVIDIA GPU.

Words used throughout: a kernel is one function that runs on the GPU across many threads; a launch is the CPU asking the GPU to run one; a profiler is a program that watches another program and records what it did and how long it took. The parent's {{section 9|n:3c65c17b0d0d81c39f34d5e070d783c1}} gives the short version of this page; the {{programming model|n:3c65c17b0d0d8162865eec15d9dae87e}} sibling owns launches, the CUDA error model, CUDA_LAUNCH_BLOCKING and what a launch costs; {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}} owns FLOP counting and MFU (model FLOPs utilisation); this page owns the tools and the method.

Where does the time go?Nsight Systems (nsys) for the whole program; torch.profiler for "which PyTorch op". Cheap, run first. Section 3.
Why is this kernel slow?Nsight Compute (ncu): replays one kernel many times to read hardware counters. Slow; only on kernels the timeline convicted. Section 4.
Is my timing true?CUDA events or a synchronised clock, warm-up, a cold cache, fixed clocks, many runs, median and spread, triton.testing.do_bench. Sections 1 and 2.
Is the answer right?A higher-precision reference, a tolerance per data type, awareness of summation order and atomics, compute-sanitizer. Section 5.

The loop this page builds
Measure the whole program (timeline) → pick the biggest kernel or gap → explain it (counters, roofline) → change one thing → re-measure with an honest benchmark → check the output against a reference. Write the numbers down at every step. A speedup without the method behind it is not a result.
