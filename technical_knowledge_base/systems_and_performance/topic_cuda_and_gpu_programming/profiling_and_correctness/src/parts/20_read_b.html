1. Why a stopwatch around GPU code lies

The problem. The CPU and the GPU are two workers with a queue between them. When Python runs c = a @ b on a GPU tensor, the CPU does not wait for the multiply: it writes a command into the queue (CUDA calls the queue a stream) and returns at once. The GPU picks the command up when it is free. So a clock read on the CPU before and after that line measures how long it took to queue the work, not to do it. This is called asynchronous execution, and it is the reason PyTorch on a GPU can be fast at all: the CPU runs ahead and keeps the queue full.

How to time it. Either make the CPU wait for the queue to drain before reading the clock (torch.cuda.synchronize(), and also before starting it, or earlier queued work is charged to you), or put two markers into the queue itself and ask the GPU how far apart they were: a CUDA event. Predict: four earlier multiplies are still in the queue when you start the clock, then you queue one more and synchronise. What does the clock say, roughly?
The synchronise waits for everything in the queue, including the four multiplies queued before the clock started. measured: 19.93 ms against 4.243 ms for one. The fix is a synchronize() before reading the start time too.

The PyTorch recipe on CUDA

# warm up first (section 2), then:
start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
torch.cuda.synchronize()          # nothing else in the queue
start.record()                    # a marker in the stream
y = f(x)
end.record()
torch.cuda.synchronize()          # or end.synchronize()
ms = start.elapsed_time(end)      # GPU time between the markers, in ms

NVIDIA documents event timing with "a resolution of around 0.5 microseconds" ({{CUDA Runtime API 13.4, cudaEventElapsedTime|https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__EVENT.html}}) docs. Events measure the stream, so they leave out the CPU's own overhead; a synchronised CPU clock includes it. Use events for "how fast is this kernel", and a synchronised clock (or a profiler timeline) when the question is "how fast is this step", because in launch-bound code the CPU is the cost. One more trap: an event pair also counts any time the GPU sat idle between the markers waiting for the CPU to queue the next kernel, so a slow Python loop inflates event times too.

Know what your timer brackets

Apple's MPS events are not CUDA events: they mark command-buffer boundaries, so they carry a fixed overhead. On this laptop, a tiny multiply of 4,096 numbers measured 0.157 ms with an event pair and 0.196 ms with a clock and a synchronise per call, but 4.96 µs per call when 200 calls were queued back to back with one synchronise at the end measured. The GPU work is a few microseconds; everything else is the measuring. On CUDA the same effect exists at a smaller scale: a kernel of a few microseconds timed alone is mostly launch and synchronisation, which is why {{CUDA graphs|n:3f05c17b0d0d81b19a6acab65c370b75}} and Triton's do_bench_cudagraph exist. For tiny kernels, time many back-to-back calls and divide, and say so.

The same trap inside PyTorch code you did not write
Any operation that needs a value on the CPU forces a synchronise: loss.item(), print(tensor), tensor.cpu(), if tensor.any():, a nonzero() whose size the CPU must know. In a training loop these silently serialise the CPU and GPU, and a stopwatch then "works" by accident. The timeline in section 3 shows where they are.
