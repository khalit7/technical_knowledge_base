2. Benchmarking honestly: warm-up, caches, spread, clocks

With correct synchronisation, the same kernel still gives different times depending on when and how you time it. Four effects account for almost every wrong benchmark, each measured here, each with its rule.

Warm-up: the first call pays for everything that happens once

measured on Apple M1 Pro GPU: each line is the median over 9 fresh Python processes (3 runs × 3) of the k-th call, each call synchronised; the bars show the slowest and fastest process. The first softmax took 5.78 ms (median; one process took 17.9 ms) against 0.45 ms by the 15th call, a first softmax about 13 times slower; the first matmul 26.9 ms against 4.27 ms. In the profiled training step of section 3 the first step on the GPU took 905 ms and the later ones about 7 ms.

The first call pays one-time costs: device set-up, compiling or loading the kernel, choosing an algorithm (cuDNN's benchmark mode tries several), growing the memory allocator. Triton kernels compile and autotune on first call, and torch.compile compiles once per new input shape. Rule: run until the time stops falling, then time; for compiled or autotuned code, warm up every shape you will time.

Caches: timing the same small tensor in a loop measures the cache

A GPU's last-level cache (the L2) is large: 40 MB on an A100 40 GB ({{NVIDIA's Ampere post|https://developer.nvidia.com/blog/nvidia-ampere-architecture-in-depth/}}), 50 MB on an H100 SXM ({{Hopper post|https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/}}), 96 MB on an RTX 5090 ({{RTX Blackwell whitepaper|https://images.nvidia.com/aem-dam/Solutions/geforce/blackwell/nvidia-rtx-blackwell-gpu-architecture.pdf}}). Read the same 16 MB buffer a hundred times and every read after the first comes from it. In a real model the input was just written or evicted by another kernel, so the honest number is the cold one.

Predict: x.sum() over a 16 MB tensor on this laptop (its GPU's last-level cache is 24 MB), timed hot (the same tensor again and again) and cold (rotating through 512 MB of tensors). How different?
measured: hot 255 GB/s, cold 154 GB/s, so the hot loop reports 1.7× too fast at 16 MB here. At 128 MB, far beyond the cache, both are 169 GB/s. The chart shows where the gap opens and closes.

measured on Apple M1 Pro GPU: effective bandwidth of x.sum() (bytes read divided by time), each point the median of 3 runs of 7 batches of 32 back-to-back calls with one synchronise per batch; whiskers are the 3 runs. The M1 Pro's 24 MB system-level cache is an independent measurement ({{metal-benchmarks|https://github.com/philipturner/metal-benchmarks}}). Rule: flush the cache before each timed run, or rotate through buffers larger than it, and say which.

Spread: report the median and the spread, never one number

measured on Apple M1 Pro GPU: 300 event timings of the same 1,024 × 1,024 float32 multiply in each of three runs, minutes apart, 1-minute load average between 4.3 and 4.7 (other agents were running). Run medians 0.721, 1.554, 1.209 ms: the same code, three runs that disagreed by a factor of 2. A few slow outliers pull the mean (run 2: mean 1.521, maximum 11.82 ms).

Rule: the median (or several quantiles) of many runs, whole runs repeated, the spread and the machine's load reported; distrust any comparison of two numbers taken at different times on a shared machine. The minimum is tempting because it is stable, but it describes a lucky run, not the typical one.

Clocks: the GPU changes speed while you measure

GPUs boost their clock when cool and throttle when hot or at their power limit, so back-to-back runs differ. Either lock the clocks for the measurement (nvidia-smi -lgc <min,max> "defines closest desired locked GPU clock speed in MHz", -rgc resets; both need root) or record clock and power beside every result (nvidia-smi dmon prints "one line of monitoring data per monitoring cycle"; the third-party nvitop is a friendlier live view) ({{nvidia-smi docs|https://docs.nvidia.com/deploy/nvidia-smi/index.html}}) docs only, not run here. On a workstation a fixed power limit (nvidia-smi -pl, in watts) and a note of the cooling matter too, because fans and room temperature change sustained clocks.

Nsight Compute locks clocks itself while profiling. NVIDIA's own 2023 sample reports show it: the device's maximum clock is 1,650 MHz, but every kernel ran at 0.94 to 1.05 GHz read from NVIDIA's reports. So a duration from ncu is not the duration in your training run; compare ncu with ncu.

Correction to the old page: ncu's clock default
The old page said ncu "locks clocks to base by default during replay". That was true until Nsight Compute 2025.4; the default of --clock-control became boost in 2026.1 ({{release notes|https://docs.nvidia.com/nsight-compute/ReleaseNotes/index.html}}; ncu --help in 2026.3.1 shows (=boost)). NVIDIA's 2023 reports above ran under the old base default. To compare ncu durations with Nsight Systems, NVIDIA recommends locking clocks with nvidia-smi and passing --clock-control none.

triton.testing.do_bench: the harness that does all of this

Read in the Triton 3.8.0 source real source: it runs your function once and synchronises; times 5 runs to estimate the cost; fits as many warm-up runs as take 25 ms and as many timed runs as take 100 ms; then for each timed run zeroes a 256 MB buffer ("to make sure that the L2 cache doesn't contain any input data before the run") and records one event pair around your function. It returns the mean by default; ask for return_mode="median" (or "min", "max", "all", or quantiles=[0.2, 0.5, 0.8]). Its sibling do_bench_cudagraph captures the calls in a CUDA graph to remove launch overhead.

Correction to the old page: do_bench
The old page said do_bench "has flush_l2=True". It has no such argument in Triton 3.8.0: flushing is always on (the 256 MB zeroing). It also returns the mean, not the median, unless you ask ({{testing.py|https://github.com/triton-lang/triton/blob/main/python/triton/testing.py}}).
do_bench ported to MPS, and the rules for a fair comparison

Ported line by line to MPS (one synchronise added before each start event, because MPS refuses event pairs that land in one command buffer) measured on Apple M1 Pro GPU: a 16 MB sum gave a median of 0.36 ms with the flush and 0.25 ms without, across 3 runs; the 2,048 matmul 4.27 ms. The flush difference matches the hot and cold measurement above; the absolute sum times include MPS's per-event overhead, which CUDA events do not have.

  • Check the output first (section 5): a kernel that skips work is very fast.
  • Compare against the strongest baseline: torch.compile rather than eager PyTorch, cuBLAS or cuBLASLt with the same data type, layout and fused epilogue, FlashAttention rather than a naive attention.
  • Report achieved throughput next to the limit: GB/s against the memory bandwidth for a memory-bound kernel, TFLOP/s against the peak for the data type for a compute-bound one. "2× faster" means little; "from 40% to 80% of peak bandwidth" can be judged.
  • Write down the environment: GPU model and count, driver, CUDA toolkit (13.4.2 is current in October 2026; the old page's "13.3 current" is out of date), PyTorch and Triton versions, clocks (locked or not), power limit, input shapes and data types, and the machine's load. Every measurement on this page records its versions and load in src/out/.
