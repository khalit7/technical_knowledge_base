5. Is the answer right? References, tolerances, order and atomics

A wrong kernel rarely crashes; it returns plausible numbers. And a correct kernel rarely returns exactly PyTorch's bits, because floating point rounds after every operation and addition is not associative: (a + b) + c and a + (b + c) can differ in the last bits, and a GPU kernel adds in whatever order its threads, tiles and atomics dictate. So "is it right?" means: does it differ from a trustworthy reference by no more than this format's rounding and this summation explain?

How to compare against a reference

  1. Same inputs, more precision. Round the inputs to the kernel's input type first, then compute the reference in float64 (or float32 for a float16 kernel) from those rounded inputs. Otherwise you measure the input rounding, not the kernel.
  2. Tolerance from the output type and the problem size. A float16 output can be off by one rounding (eps/2 relative) plus the accumulated error of the sum, which grows with the reduction length K. Near zero, after cancellation, a relative tolerance is meaningless; compare the error to the scale of the terms instead (for a dot product, √Σ(aibi)²).
  3. Look at the worst element and where it is, not only pass or fail: an error concentrated in the last tile or the last row is a bug; an error spread evenly at the rounding level is arithmetic.

Workbench: any input, accumulator and output format, length and summation order

Pick the number formats of a dot product (the inner loop of every matmul and attention score), its length and its summation order, and see how far the result lands from the exact answer and whether torch.testing.assert_close's defaults would pass it.

How it works: each trial draws two vectors of N(0, 1) numbers with a seeded generator, rounds them to the input format, forms the products (exact in double precision, then rounded to the accumulator), adds them in the chosen order rounding after every addition, and rounds the result to the output format. The error is measured against the exact dot product of the rounded inputs (computed with Shewchuk's exact summation), divided by √Σ(aibi)². "Passes" applies assert_close's default rtol and atol for the output type (float32 1.3e-6 and 1e-5, bfloat16 0.016 and 1e-5, float16 0.001 and 1e-5) against the exact result rounded once to that type. The rounding model matches PyTorch 2.14.1's casts on 2,055 test values and six whole experiments bit for bit (check/check_js.mjs against code/reference.py). Real tensor cores may compute products and partial sums with internal widths this model does not capture.

When you need the same bits every run

  • torch.use_deterministic_algorithms(True) makes PyTorch use deterministic implementations where they exist and raise an error where they do not (for example index_add_ and scatter_add_ on CUDA, which use atomics); it also stops Inductor from autotuning in ways that change numerics. "Deterministic operations tend to have worse performance" ({{PyTorch reproducibility notes|https://docs.pytorch.org/docs/2.14/notes/randomness.html}}; docstring of PyTorch 2.14.1).
  • torch.backends.cudnn.benchmark = False makes cuDNN choose its algorithm deterministically; torch.backends.cudnn.deterministic = True also requires that algorithm to be deterministic.
  • cuBLAS gives "the same bit-wise results at every run when executed on GPUs with the same architecture and the same number of SMs", but not with several concurrent streams sharing a handle unless you set CUBLAS_WORKSPACE_CONFIG=:4096:8 (about 24 MiB more memory) or :16:8 ({{cuBLAS 13.4, results reproducibility|https://docs.nvidia.com/cuda/cublas/index.html#results-reproducibility}}) docs. A different GPU model, SM count or library version may still change the bits: compare across machines with a tolerance, not with equality; require bit-equality only from the same kernel on the same GPU with deterministic settings.

compute-sanitizer: memory errors, races, uninitialised reads

A bad kernel often fails silently (the error model is on {{The CUDA programming model|n:3c65c17b0d0d8162865eec15d9dae87e}}). compute-sanitizer, shipped with the toolkit, runs your program with instrumented kernels and reports the first bad access with the thread, block and source line (compile with -lineinfo). A testing checklist for a new kernel

  • Sizes that are not multiples of the tile or block (1, 7, 127, 4,097), the first and last block, and one size far bigger than any test you thought of: the parent's {{Kernel lab|n:3c65c17b0d0d81c39f34d5e070d783c1}} records a missing barrier that passed every small test and corrupted 1 to 5 random rows per run only at 4,096 rows.
  • Poison the output (fill it with NaN, or use fresh memory) and run the reference after the kernel under test, not before. {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}, section 8, records "a kernel that wrote nothing passed the test": an RMSNorm whose loop count came out 0 wrote nothing and still passed, because its output buffer most likely still held the library's answer from the run just before.
  • Non-contiguous and transposed inputs, every data type you claim to support, and inputs with large, tiny, zero, infinite and NaN values.
  • Several random seeds; the same input twice (does the output change? then something is racing or using atomics).
  • A tolerance tight enough to see a bug: bfloat16's default rtol of 1.6% would hide an off-by-one tile that changes a few per cent of one row, so test a float32 version of the kernel with tight tolerances too.
  • Gradients: torch.autograd.gradcheck in float64 for a custom backward.
  • compute-sanitizer (all four tools) on a small case before any benchmark.
FP8 needs a scale, and one outlier can spoil a per-tensor scale (measured)

float8 e4m3 has only 3 mantissa bits and a range of ±448 (its smallest normal is 2−6), so values are multiplied by a scale before the cast and divided after. A million activations whose rows differ in scale, plus one outlier of 900, cast to e4m3 computed here, PyTorch 2.14.1:

The outlier fixes the per-tensor scale at 448/900, which pushes the small rows below e4m3's range: 12,118 non-zero values flush to zero against 6,091 with no scale at all and 11 with one scale per row. This is why FP8 recipes use fine-grained scales (per tile or per block, as in the MX formats), owned by {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}, the {{hardware formats|n:3c65c17b0d0d8118beeefaed56da6f8e}} and {{tensor-core|n:3c65c17b0d0d81a7adcaebee2f44a087}} pages. Note also what PyTorch's cast did with values above 448: it saturated them to 448 (even infinity), rather than producing NaN; a kernel that casts differently will not match it bit for bit.
