4. Why is this kernel slow? Nsight Compute

The problem. The timeline says one kernel takes 30% of the step. Why? Is it moving more bytes than it needs, leaving the arithmetic units idle, using too few warps, or stalling on shared memory? The GPU has thousands of hardware counters (instructions issued, bytes read from DRAM, cache hits, cycles each unit was busy), but only a few can be read in one run. Nsight Compute (ncu) solves this by replaying the kernel: it saves the memory the kernel can touch, runs the kernel, restores the memory, runs it again with different counters, and so on, then turns the counters into metrics, sections and advice.

What replay costs, from NVIDIA's own reports real tool, NVIDIA's reports

Every one of the six sample reports shipped with Nsight Compute 2026.3.1 (collected with --set full) needed 42 passes of the same kernel, and for the matrix transpose the tool saved and restored 545 MB before each pass. Between passes it flushes the caches ("Nsight Compute flushes all GPU caches by default between replay passes"), it serialises kernels that would otherwise overlap, and it locks the clocks. So a profiled run can take orders of magnitude longer, and its durations describe a cold-cache, locked-clock, serialised kernel. Use it on a handful of kernels the timeline already convicted, never on a whole training run ({{Profiling Guide, kernel replay and workload durations|https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html}}).

ncu --set full -k regex:softmax -c 1 -o sm python train.py   # first matching kernel only
ncu --import sm.ncu-rep --page details                          # the text you see in the Report reader tab
ncu --import sm.ncu-rep --page raw --csv                        # every metric, for scripts
ncu --nvtx --nvtx-include "step/" ...                           # only kernels inside an NVTX range

Flags from ncu --help (2026.3.1): -k takes an exact name or regex:; -c limits the number of profiled launches; without --set the basic set is collected (LaunchStats, Occupancy, SpeedOfLight, WorkloadDistribution: an estimated 229 metrics), while full is an estimated 9,059 metrics in 24 sections (ncu --list-sets). Compile with -lineinfo and add --import-source on to see metrics per line of your source. A Python API for reports ships in extras/python/ncu_report.py.

Read a report top-down: three real before-and-after pairs

The Speed of Light (SOL) section comes first: "for each unit, the throughput reports the achieved percentage of utilization with respect to the theoretical maximum", and the two headline numbers are the highest such percentage among the compute units (Compute (SM)) and among the memory units (Memory). Together they place the kernel: memory high, compute low is memory-bound (move fewer bytes); compute high is compute-bound (cheaper instructions, tensor cores, lower precision); both low means latency-bound (too few warps, stalls, a tail of idle SMs, or a tiny kernel). Nsight Compute's guided analysis estimated a 64.67% speedup from fixing the uncoalesced loads of addConstDouble3. For the transpose the estimate was 87.21% and the real gain 29.7% less time. The rules point at where to look; the clock decides. What are warps waiting for?Warp State Statisticssmsp__pcsamp_warps_issue_stalled_long_scoreboard, _mio_throttle, _barrier, ..."only focus on stall reasons if the schedulers fail to issue every cycle"

Warp stalls in one paragraph. Each SM sub-partition's scheduler can issue one instruction per cycle from any eligible warp. A warp is stalled when its next instruction cannot go: long scoreboard means it waits for data from L1, L2 or DRAM (a memory latency problem: more warps, prefetching, fewer loads); MIO throttle and short scoreboard mostly mean shared-memory or special-function pressure (the transpose with bank conflicts spent 83.8 of 158.5 cycles per instruction in MIO throttle); barrier means warps waiting at __syncthreads() for slower ones; math pipe throttle means an arithmetic pipe is saturated (often good news). Stalls only matter when no warp is eligible; with many warps, the scheduler hides them. The scoreboards are real bits in every SASS instruction: which instruction sets one and which waits on it is decoded in section 3 of {{The compiler stack|n:3f05c17b0d0d81ddbc00fac9e8a2ff89}} ("The bits nobody prints") and its SASS, decoded tab.

Correction to the old page
The old page said ncu "locks clocks to base by default during replay". That was true until Nsight Compute 2025.4; the default of --clock-control became boost in 2026.1 (release notes; ncu --help in 2026.3.1 shows (=boost)). NVIDIA's 2023 reports on this page ran under the old base default, at about 1 GHz on a GPU whose maximum is 1.65 GHz. To compare ncu durations with Nsight Systems, NVIDIA recommends locking clocks with nvidia-smi and passing --clock-control none.
