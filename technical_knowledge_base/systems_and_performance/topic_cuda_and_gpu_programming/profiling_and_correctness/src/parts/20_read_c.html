3. Where does the time go? Timelines: Nsight Systems and torch.profiler

A training step is thousands of kernels, copies and CPU functions. Before optimising any kernel, find out which ones matter and whether the GPU is even busy. A timeline answers that: is the GPU row full or full of gaps, which kernels take most of the time, do copies and communication overlap the compute, where does the CPU block? What sits under the tools; Nsight Systems commands, capture ranges and report scripts (docs only, not run here)

Under the first two sits CUPTI (the CUDA Profiling Tools Interface), NVIDIA's library for collecting kernel start and end times, copies and counters from inside a process. Nsight Systems records CPU threads, CUDA API calls, kernels, copies, NCCL, OS calls and your own NVTX ranges (named intervals you mark in code), its kernel times through CUPTI (Nsight Compute's {{Profiling Guide|https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html}}). torch.profiler is built on Kineto ("an in-process profiling library integrated with the PyTorch Profiler", {{pytorch/kineto|https://github.com/pytorch/kineto}}), whose CUDA backend is CUPTI (its CuptiActivityApi sources); it names every operator, its input shapes and the kernels it launched.

nsys profile -t cuda,nvtx,osrt -o step python train.py   # default -t is cuda,opengl,nvtx,osrt
nsys profile --capture-range=cudaProfilerApi ...          # record only between cudaProfilerStart/Stop
nsys stats step.nsys-rep                                  # summary tables in the terminal

In Python, mark phases so the timeline is readable: torch.cuda.nvtx.range_push("forward") ... range_pop() (or the torch.cuda.nvtx.range context manager), and limit the capture to a few steps with torch.cuda.profiler.start()/stop() plus --capture-range=cudaProfilerApi. The nsys stats report scripts include cuda_gpu_kern_sum ("a summary of CUDA kernels and their execution times"), cuda_api_sum, cuda_gpu_mem_time_sum, nvtx_sum and osrt_sum. CUDA graphs are traced as whole graphs by default ({{User Guide v2026.5|https://docs.nvidia.com/nsight-systems/UserGuide/index.html}}, {{Analysis Guide|https://docs.nvidia.com/nsight-systems/AnalysisGuide/index.html}}).

torch.profiler, run on a real training step

A two-block MLP (LayerNorm, 512 to 2,048 to 512 with GELU, residual) plus a 1,000-way classifier, batch 256, one AdamW step, profiled with 1 step skipped, 1 warm-up step and 2 recorded; on CUDA add ProfilerActivity.CUDA run here:

from torch.profiler import profile, schedule, record_function, ProfilerActivity
with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
             schedule=schedule(wait=1, warmup=1, active=2),
             on_trace_ready=lambda p: p.export_chrome_trace("trace.json"),
             record_shapes=True, with_flops=True) as prof:
    for _ in range(5):
        with record_function("forward"): loss = loss_fn(model(x), y)
        ...
        prof.step()                                  # advances the schedule
print(prof.key_averages().table(sort_by="self_cuda_time_total", row_limit=15))

The same operator, two meanings. On the CPU, aten::mm is the biggest row: the CPU does the multiply, so its "self CPU" time is the work (498.3 µs per call). With the model on the GPU, the same operator costs 38.5 µs of CPU time per call: only the time to queue it. PyTorch 2.14 has no MPS profiler activity (its activities are CPU, XPU, MTIA, CUDA, HPU, PrivateUse1), so the GPU's own time is missing and the waiting shows up wherever the CPU blocked: the step's own row holds 6.76 ms of "self" time, the synchronise at the end of each step. That is what a CUDA profile looks like if you forget ProfilerActivity.CUDA, and why on a GPU you sort by the device columns (self_cuda_time_total, called device time in PyTorch 2.14's tables).
