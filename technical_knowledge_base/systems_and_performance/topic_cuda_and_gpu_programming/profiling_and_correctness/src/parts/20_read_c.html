2. Benchmarking honestly: warm-up, caches, spread, clocks

Even with correct synchronisation, the same kernel gives different times depending on when and how you time it. Five effects account for almost every wrong benchmark. Each is shown here with a measurement from this laptop and the rule that follows.

Warm-up: the first call pays for everything that happens once

The first time a process runs an operation, it pays one-time costs: setting up the device, compiling or loading the kernel, choosing an algorithm (cuDNN's benchmark mode tries several), growing the memory allocator. Triton kernels compile and autotune on first call, and torch.compile compiles once per new input shape. None of that is the kernel's speed.

measured on Apple M1 Pro GPU: each line is the median over 9 fresh Python processes (3 runs × 3) of the k-th call, each call synchronised; the bars show the slowest and fastest process. The first softmax took 5.78 ms (median; one process took 17.9 ms) against 0.45 ms by the 15th call; the first matmul 26.9 ms against 4.27 ms. In the profiled training step of section 3, the first step on the GPU took 905 ms and the later ones about 7 ms. Rule: run the operation until its time stops falling, and only then time it; for compiled or autotuned code, warm up every shape you will time.

Caches: timing the same small tensor in a loop measures the cache

A GPU has a large last-level cache (the L2: 40 MB on an A100 40 GB per {{NVIDIA's Ampere post|https://developer.nvidia.com/blog/nvidia-ampere-architecture-in-depth/}}, 50 MB on an H100 SXM per the {{Hopper post|https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/}}, 96 MB on an RTX 5090 per the {{RTX Blackwell whitepaper|https://images.nvidia.com/aem-dam/Solutions/geforce/blackwell/nvidia-rtx-blackwell-gpu-architecture.pdf}}). If a benchmark reads the same 16 MB buffer a hundred times, every read after the first comes from the cache, and the "memory bandwidth" it reports is the cache's. In a real model the input was just written by another kernel or evicted by one, so the honest number is the cold one.

Predict: x.sum() over a 16 MB tensor on this laptop (its GPU's last-level cache is 24 MB), timed hot (the same tensor again and again) and cold (rotating through 512 MB of tensors). How different?
measured: hot 255 GB/s, cold 154 GB/s. At 128 MB, far beyond the cache, both are 169 GB/s. The chart below shows where the gap opens and closes.

measured on Apple M1 Pro GPU: effective bandwidth of x.sum() (bytes read divided by time), each point the median of 3 runs of 7 batches of 32 back-to-back calls with one synchronise per batch; whiskers are the 3 runs. The M1 Pro's 24 MB system-level cache is an independent measurement ({{metal-benchmarks|https://github.com/philipturner/metal-benchmarks}}). Rule: flush the cache before each timed run, or rotate through buffers larger than it, and say which.

Spread: report the median and the spread, never one number

measured on Apple M1 Pro GPU: 300 event timings of the same 1,024 × 1,024 float32 multiply in each of three runs, minutes apart, laptop 1-minute load average between 4.3 and 4.7 (other agents were running). Run medians: 0.721, 1.554, 1.209 ms: the same code, a factor of 2 apart. Within a run, the mean is pulled by a few slow outliers (run 2: mean 1.521, maximum 11.82 ms). Rules: use the median (or several quantiles) of many runs, repeat whole runs, report the spread and the machine's load, and distrust any comparison between two numbers taken at different times on a shared machine. The minimum is tempting because it is stable, but it describes a lucky run, not the typical one.

Clocks: the GPU changes speed while you measure

GPUs raise their clock when cool and idle (boost) and lower it when hot or at their power limit (throttling), so back-to-back runs can differ. Two remedies docs only, not run here: lock the clocks for the measurement (nvidia-smi -lgc <min,max> "defines closest desired locked GPU clock speed in MHz", -rgc resets; both need root; {{nvidia-smi docs|https://docs.nvidia.com/deploy/nvidia-smi/index.html}}), or record the clock and power alongside every result (nvidia-smi dmon prints "one line of monitoring data per monitoring cycle"; the third-party nvitop is a friendlier live view). A fixed power limit (nvidia-smi -pl, in watts) and a note of the cooling matter on a workstation, where fans and room temperature change sustained clocks. Nsight Compute locks clocks itself while profiling: since version 2026.1 to boost by default, before that to base ({{release notes|https://docs.nvidia.com/nsight-compute/ReleaseNotes/index.html}}). NVIDIA's own 2023 sample reports show the old default: the device reports a maximum clock of 1,650 MHz, but every kernel ran at 0.94 to 1.05 GHz read from NVIDIA's reports. So a duration from ncu is not the duration in your training run; compare ncu with ncu.

triton.testing.do_bench: the harness that does all of this

Triton's benchmark function, read in the Triton 3.8.0 source real source: it runs your function once and synchronises; times 5 runs to estimate the cost; computes how many warm-up runs fit in 25 ms and how many timed runs fit in 100 ms; runs the warm-up; then for each timed run zeroes a 256 MB buffer ("to make sure that the L2 cache doesn't contain any input data before the run") and records one event pair around your function; finally returns the mean by default, or return_mode="median", "min", "max", "all", or quantiles=[0.2, 0.5, 0.8]. Its sibling do_bench_cudagraph captures the calls in a CUDA graph to remove launch overhead.

Correction to the old page
The old page said do_bench "has flush_l2=True". It has no such argument in Triton 3.8.0: flushing is always on (the 256 MB zeroing above). It also returns the mean, not the median, unless you ask. ({{testing.py|https://github.com/triton-lang/triton/blob/main/python/triton/testing.py}}.)

Ported line by line to MPS (one synchronise added before each start event, because MPS refuses event pairs that land in one command buffer) measured on Apple M1 Pro GPU: a 16 MB sum gave a median of 0.36 ms with the flush and 0.25 ms without, across 3 runs; the 2,048 matmul 4.27 ms. The flush difference matches the hot and cold measurement above; the absolute sum times include MPS's per-event overhead, which CUDA events do not have.

Fair comparisons and a log

  • Check the output first (section 5): a kernel that skips work is very fast.
  • Compare against the strongest baseline: torch.compile rather than eager PyTorch, cuBLAS or cuBLASLt with the same data type, layout and fused epilogue, FlashAttention rather than a naive attention.
  • Report achieved throughput next to the limit: GB/s against the memory bandwidth for a memory-bound kernel, TFLOP/s against the peak for the data type for a compute-bound one ({{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}} owns the FLOP counts). "2× faster" means little; "from 40% to 80% of peak bandwidth" can be judged.
  • Write down the environment: GPU model and count, driver, CUDA toolkit (13.4.2 is current in October 2026; the old page's "13.3 current" is out of date), PyTorch and Triton versions, clocks (locked or not), power limit, input shapes and data types, and the machine's load. Every measurement on this page records its versions and load in src/out/.
