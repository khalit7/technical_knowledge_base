9. The same kernels from Python

You will rarely write a main(). The programming model is the same from Python; only the spelling changes. Four routes, each tried here for real in the container with the CUDA toolkit and no GPU, so each says how far it got.

Numba CUDA: Python syntax, CUDA semantics

from numba import cuda, float32
@cuda.jit
def scale(x, y, a):
    i = cuda.grid(1)                  # = blockIdx.x * blockDim.x + threadIdx.x
    if i < x.size:
        y[i] = a * x[i]
@cuda.jit
def block_sum(x, out):
    s = cuda.shared.array(256, dtype=float32)     # __shared__ float s[256]
    t = cuda.threadIdx.x
    s[t] = x[cuda.blockIdx.x * 256 + t]
    cuda.syncthreads()                            # __syncthreads()
    k = 128
    while k > 0:
        if t < k:
            s[t] += s[t + k]
        cuda.syncthreads()
        k //= 2
    if t == 0:
        out[cuda.blockIdx.x] = s[0]
scale[grid, block](x, y, 2.0)                     # the launch: [grid, block] instead of <<<>>>

Numba-CUDA is now a separate package maintained by NVIDIA ({{numba-cuda docs|https://nvidia.github.io/numba-cuda/}}). Its simulator executes kernels "one block at a time. One thread is spawned for each thread in the block, and scheduling of the execution of these threads is left up to the operating system", and it "does not implement warp-level operations" ({{simulator docs|https://nvidia.github.io/numba-cuda/user/simulator.html}}): good for checking indexing and barriers, useless for timing.

CuPy RawKernel: CUDA C++ in a string

import cupy as cp
k = cp.RawKernel(r'''
extern "C" __global__ void scale(const float* x, float* y, float a, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) y[i] = a * x[i];
}''', "scale")
k((grid,), (block,), (x, y, cp.float32(2.0), cp.int32(n)))   # grid, block, arguments

torch.utils.cpp_extension: a CUDA kernel as a PyTorch function

from torch.utils.cpp_extension import load_inline
cuda_src = r'''
#include <torch/extension.h>
__global__ void scale_kernel(const float* x, float* y, float a, int n) { ... }
torch::Tensor scale(torch::Tensor x, double a) {
  auto y = torch::empty_like(x);
  int n = x.numel(), block = 256, grid = (n + block - 1) / block;
  scale_kernel<<<grid, block>>>(x.data_ptr<float>(), y.data_ptr<float>(), (float)a, n);
  return y;
}'''
m = load_inline("pm_scale", cpp_sources="torch::Tensor scale(torch::Tensor x, double a);",
                cuda_sources=cuda_src, functions=["scale"])   # nvcc + ninja, then import

On a CUDA build of PyTorch with a GPU, load_inline writes the sources to a build directory, compiles them with nvcc and ninja, and imports the result as a Python module ({{PyTorch C++ extension docs|https://docs.pytorch.org/docs/2.14/cpp_extension.html}}). A production version also launches on PyTorch's current stream, checks devices and dtypes, and registers the function with torch.library so torch.compile can see it; that is {{pytorch-ecosystem|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}} territory.

Triton: blocks, not threads

Triton changes the model itself: you write the program of one block on whole tiles (tl.load of 1,024 elements at once), and the compiler decides threads, warps, shared memory and synchronisation. Everything on this page still happens; Triton does it for you. That is {{Triton and Gluon|n:3c65c17b0d0d81729d15ed4d1a4461b3}}, the rung the parent page's ladder puts right after calling a library.

10. The same model in Metal, on the M1

What transfers and what does not. Warp-sized SIMD groups, barriers, races, the cost of launch-and-wait, and waves on a fixed number of cores all behaved as the CUDA model predicts. Absolute numbers do not transfer: the M1 Pro has 16 cores where an H100 has 132 SMs, about 160 GB/s where an H100 has 3.35 TB/s, and its compiler and driver are Apple's, so occupancy limits, atomic throughput and launch overheads differ.
