7. The host-side memory API, the basics

The problem. A device pointer is an address in GPU memory: the CPU cannot dereference it, and a kernel cannot dereference an ordinary CPU pointer. Every byte a kernel touches must be allocated on the device and brought there. Five calls cover nearly everything; PyTorch makes the same calls for you.

Why nvidia-smi shows your memory as used. PyTorch never calls cudaFree when a tensor dies: its caching allocator keeps the block for the next tensor, because cudaMalloc and cudaFree are slow and synchronising. The PyTorch notes: unused cached memory "still appears occupied in nvidia-smi"; torch.cuda.memory_allocated() counts live tensors and memory_reserved() counts everything the allocator holds; empty_cache() returns the unused part. When a run reports out-of-memory with plenty "reserved but unallocated", the cause is fragmentation, not a leak.

Shared memory is not allocated with this API. It is declared in the kernel: __shared__ float s[256]; (static, size known at compile time; ptxas reports "1024 bytes smem" for block_sum) or extern __shared__ float s[]; with the size given as the third launch argument (dynamic). Static shared memory "remain[s] limited to 48 KB", and "an explicit opt-in is also required to enable dynamic allocations above this limit" (cudaFuncSetAttribute(kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, bytes)); "the H100 GPU enables a single thread block to address up to 227 KB of shared memory" ({{Hopper tuning guide|https://docs.nvidia.com/cuda/hopper-tuning-guide/index.html}}) vendor doc. Everything about using it well (banks, tiling) is on {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}}.

8. What a launch costs

The problem. Every kernel launch is CPU work: the runtime and driver check the configuration, copy the arguments, and write a command for the GPU into a queue. If kernels are short, the GPU finishes each one before the CPU has queued the next, and sits idle. Eager PyTorch launches at least one kernel per operation, so a model made of many small operations can be limited by launches rather than by the GPU, the regime Horace He calls overhead-bound ({{"Making Deep Learning Go Brrrr"|https://horace.io/brrr_intro.html}}).

What travels with a launch. The grid and block shapes, the shared memory size, the stream, and the arguments by value. Arguments were limited to 4,096 bytes; CUDA 12.1 raised the limit to 32,764 bytes on Volta and later ({{NVIDIA blog, Jun 5, 2023|https://developer.nvidia.com/blog/cuda-12-1-supports-large-kernel-parameters/}}) vendor doc. Checked here with a pointer plus a struct argument: 8 + 32,756 = 32,764 bytes compiles; 8 + 32,760 fails with compiled here. In SASS the arguments are read from a constant bank (the c[0x0][0x210] loads of section 1).

How long. NVIDIA's CUDA Graphs post measured a 2.9 µs kernel taking 9.6 µs per kernel when the CPU waited after each launch, 3.4 µs with CUDA Graphs ({{NVIDIA blog, 2019, V100|https://developer.nvidia.com/blog/cuda-graphs/}}) published. The asynchronous launch is what lets the CPU run ahead: queue many kernels, wait once. On the M1 Pro, through MLX, the same tiny Metal kernel (1,024 threads) measured on Apple M1 Pro GPU:

Median of 3 runs (each the median of 7 trials). Launch and wait each time: 179.5 µs per kernel (runs 192.7, 179.5, 146.5). 200 launches queued, each reading the previous one's output, then one wait: 5.8 µs per kernel, about 31 times less. Both include MLX's Python and graph bookkeeping, so they are not CUDA numbers; the ratio is the lesson.

Three consequences for training code. Never synchronise in the hot loop without need (.item(), print(loss), a .cpu() every step: each one drains the queue). Fewer, larger kernels win when kernels are small: fusion, by hand or by torch.compile ({{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}, {{The compiler stack|n:3f05c17b0d0d81ddbc00fac9e8a2ff89}}). And when the sequence of kernels repeats exactly, as in LLM decoding, record it once and replay it as a CUDA graph ({{Streams, CUDA graphs and multi-GPU programming|n:3f05c17b0d0d81b19a6acab65c370b75}}). How to check: a profiler timeline shows gaps between kernels on the GPU row; if the gaps are as long as the kernels, you are overhead-bound ({{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}}).
