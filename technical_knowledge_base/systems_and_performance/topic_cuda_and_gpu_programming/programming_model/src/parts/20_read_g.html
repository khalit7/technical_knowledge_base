5. Choosing a launch: block size, occupancy, waves

The same kernel can be launched in thousands of ways, and the launch decides how much of the GPU works. You choose the block size, the grid size and the dynamic shared memory; the compiler chooses registers per thread, which you can steer. Two consequences follow: how many blocks fit on one SM at once (occupancy), and how many rounds the grid needs to get through the SMs (waves).

Occupancy: the resource that runs out first

Occupancy is resident warps per SM divided by the most the SM can hold (64 on A100, H100 and B200; 48 on the RTX 5090). A block is placed on an SM only if all of it fits: its warps, its registers (registers per thread × threads), its shared memory and a free block slot. Why resident warps hide latency, and the per-generation limits, are on {{GPU architecture|n:3c65c17b0d0d810682aae39bd614ec64}} (sections 3 and 4).

Steering registers trades occupancy for spills. One kernel with many live values per thread (96 accumulators), compiled three ways:

__global__ void heavy_plain(...)                              // the compiler picks registers freely
__global__ void __launch_bounds__(1024) heavy_lb1024(...)     // "I will launch up to 1,024 threads per block"
__global__ void __launch_bounds__(256, 8) heavy_lb256x8(...)  // "256 threads, and I want 8 blocks per SM"

Fig. 3 fills one H100 SM with 256-thread blocks of these three kernels, compiled for sm_90a: registers per thread are the real ptxas -v counts compiled here; blocks per SM follow NVIDIA's rules from cuda_occupancy.h derived.

  1. One SM, two budgets. An H100 SM holds at most 64 warps (left) and 65,536 registers (right), allocated per warp in units of 256; each cell on the right is 1,024 registers, one warp's worth at 32 per thread. A block is placed only if all of it fits. Shared memory and the block-slot cap are budgets too; these kernels use no shared memory.
  2. heavy_plain: 128 registers, 2 blocks. A warp needs 128 × 32 = 4,096 registers, a block 32,768: two blocks fill the register file while 48 of the 64 warp slots stay empty. 16 of 64 warps, 25% occupancy, limited by registers; a third block waits.
  3. __launch_bounds__(1024): 64 registers, 4 blocks. The promise of 1,024-thread blocks makes ptxas cap the kernel at 65,536 / 1,024 = 64 registers: 4 blocks fit, 32 warps, 50%. The values that no longer fit are spilled to local memory: 2,328 bytes of spill stores.
  4. __launch_bounds__(256, 8): 32 registers, 8 blocks. 8 blocks of 256 leave 32 registers per thread: all 64 warps resident, 100%, registers and warp slots running out together. Spill stores grow to 3,004 bytes.

On A100, H100 and B200 the three kernels reach 25%, 50% and 100% occupancy, and both capped kernels spill (2,328 to 4,260 bytes of spill stores in the ptxas reports). "Spill" bytes are values that did not fit in registers and went to local memory, which lives in the GPU's main memory behind the caches ({{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}}).

__launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor) tells ptxas the launch you promise, so it caps registers to make it fit (and a launch above the promised size fails): 1,024 threads in 65,536 registers leaves 64 per thread, 8 blocks of 256 leaves 32 (-maxrregcount=N caps every kernel in the file). Occupancy goes up; so do spills. Which wins is a measurement, not a rule: for matmul and attention kernels, which reuse values held in registers, it is usually fewer warps and no spills. What a register cap does to one kernel step by step (a 128-accumulator kernel needs 160 registers on sm_90a; capped at 128 it spills 84 bytes, capped at 32 it spills 1,240) is section 4 of {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}} and its Memory instructions tab.

Two real compiler and runtime details (depth)

On sm_120 ptxas printed Value of threads per SM for entry heavy_lb256x8 is out of range. .minnctapersm will be ignored (8 × 256 = 2,048 threads, but an sm_120 SM holds 1,536) and kept 128 registers. And heavy_plain launched with 1,024 threads would need 128 × 1,024 = 131,072 registers, twice an SM's 65,536, so the launch fails with cudaErrorLaunchOutOfResources, "too many resources requested for launch", which the runtime header explains as "the kernel launch specifies too many threads for the kernel's register count".

Letting CUDA suggest a block size. cudaOccupancyMaxPotentialBlockSize(&minGrid, &block, kernel) returns the block size with the highest occupancy and the smallest grid that fills the GPU; for the simple scale kernel it answers 1,024 threads on H100 and 768 on the RTX 5090. That maximises occupancy, not speed: a starting point.

How the suggestion is computed, and how this page checks its own occupancy numbers (depth)

The API searches from the largest block size down and keeps the first that reaches the highest occupancy. NVIDIA ships the same logic as a host-only header, cuda_occupancy.h, which runs without a GPU: compiled and run here for this page's kernels on four GPUs and checked against this page's JavaScript port, the two agree on 1,155 of 1,155 values (0 mismatches) compiled and run here.

Block size in practice. Always a multiple of 32 (a partial warp wastes lanes); 128 to 256 is the usual default. Too small hits the block-slot cap: 32-thread blocks on an H100 give at most 32 blocks of one warp, 50% occupancy derived. Too large makes each block a big unit to schedule and synchronise. On the M1 Pro a memory-bound y = 2x over 64 Mi floats ran at 156.9 to 161.5 GB/s for every threadgroup size from 32 to 1,024 measured on Apple M1 Pro GPU: once enough threads are in flight, a simple kernel does not care. Kernels that use shared memory per block or synchronise inside the block do care, and are tuned by measurement (the autotuning in {{Triton and Gluon|n:3c65c17b0d0d81729d15ed4d1a4461b3}} is exactly this search).

Waves and the tail

Blocks are handed to SMs as slots free up. If a grid has B blocks and the GPU holds S SMs × k blocks per SM at once, the grid runs in ceil(B / (S·k)) waves, and the last wave may be nearly empty while it costs nearly a full wave of time. NVIDIA's own example is a matrix multiply on an A100 (108 SMs) with 256 × 128 output tiles, one tile per block, one block per SM, M = 2,304, K = 4,096 ({{NVIDIA Matrix Multiplication Background guide, "Wave quantization"|https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html}}) vendor doc. Growing N from 1,536 to 1,544 adds 0.5% more work; predict the cost before Fig. 4 steps it:

  1. N = 1,536: 108 tiles, one wave. M = 2,304 gives ceil(2,304 / 256) = 9 tile rows and N = 1,536 gives ceil(1,536 / 128) = 12 columns: 108 tiles, one block each, one per SM. Every SM runs exactly one tile; the GPU is full the whole time.
  2. N = 1,544: 117 tiles. A thirteenth column of tiles: 9 × 13 = 117. The first wave takes 108 of them; 9 wait in the queue.
  3. Wave 2: 9 busy, 99 idle. The second wave runs 9 tiles on 9 SMs while 99 sit idle, and it takes as long as the first. 0.5% more work, twice the time: SM utilisation 54.2% derived: tiles = ceil(M/256) × ceil(N/128); waves = ceil(tiles / 108); every tile assumed to take the same time. NVIDIA reports that "GFLOPS roughly halve and duration roughly doubles from N=1536 to N=1544".
  4. The running example's row sum on an H100. One 256-thread block per row: 4,096 blocks. block_sum's registers and shared memory let 8 blocks share an SM, so the 132 SMs hold 1,056 blocks at once (each box is one SM's 8); the first three waves run 3,168.
  5. The fourth wave is 87.9% full. 928 blocks are left: 4 waves in all, the last nearly full derived. Fine: the tail costs at most one wave in four, and with hundreds of thousands of small blocks it is a rounding error.

Measured on a real GPU. A compute-only Metal kernel with 1,024-thread threadgroups, each doing the same work, launched with 1 to 72 threadgroups on the M1 Pro's 16 GPU cores measured on Apple M1 Pro GPU, in the chart on the right.

When it matters. Waves matter when each block is long: matmul tiles and attention. A GEMM whose tile count is just over a multiple of the SM count wastes most of its last wave, and cuBLAS heuristics choose tile shapes (and split-K and Stream-K) partly to avoid it ({{Libraries and tensor cores|n:3c65c17b0d0d81a7adcaebee2f44a087}}). The {{Launch planner|#t-plan}} tab computes occupancy, the limiting resource and waves for this page's real kernels on four GPUs.
