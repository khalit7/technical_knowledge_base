5. Choosing a launch: block size, occupancy, waves

The problem. The same kernel can be launched in thousands of ways, and the launch decides how much of the GPU works. You choose the block size, the grid size and the dynamic shared memory; the compiler chooses registers per thread, which you can steer. Two consequences follow, both explained below: how many blocks fit on one SM at once (occupancy), and how many rounds the grid needs to get through the SMs (waves).

Occupancy, from your side of the launch

Occupancy is resident warps per SM divided by the maximum the SM can hold (64 on A100, H100 and B200; 48 on the RTX 5090). A block is placed on an SM only if all of its resources fit: its warps, its registers (registers per thread × threads), its shared memory, and a free block slot. The per-generation limits, and why occupancy hides latency, are on {{GPU architecture|n:3c65c17b0d0d810682aae39bd614ec64}} (sections 3 and 4). What matters here is which of your choices moves it. One kernel with many live values per thread (96 accumulators), compiled three ways:

__global__ void heavy_plain(...)                              // the compiler picks registers freely
__global__ void __launch_bounds__(1024) heavy_lb1024(...)     // "I will launch up to 1,024 threads per block"
__global__ void __launch_bounds__(256, 8) heavy_lb256x8(...)  // "256 threads, and I want 8 blocks per SM"

Registers and spills: ptxas -v, CUDA 13.4.2 compiled here. Occupancy at 256 threads per block: NVIDIA's rules from cuda_occupancy.h derived. "Spill" bytes are values that did not fit in registers and went to local memory, which lives in the GPU's main memory behind the caches ({{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}}).

Read the table as a trade. __launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor) tells ptxas the launch you promise, so it caps registers to make that launch fit: 1,024 threads in 65,536 registers leaves 64 per thread, and 8 blocks of 256 leaves 32. Occupancy goes up; so do spills. Which one wins is a measurement, not a rule; for matmul and attention kernels, which reuse values held in registers, the answer is usually fewer warps and no spills. Two real details: on sm_120 ptxas printed Value of threads per SM for entry heavy_lb256x8 is out of range. .minnctapersm will be ignored (8 × 256 = 2,048 threads, but an sm_120 SM holds 1,536) and kept 128 registers; and heavy_plain launched with 1,024 threads would need 128 × 1,024 = 131,072 registers, twice an SM's 65,536, so the launch fails with cudaErrorLaunchOutOfResources, "too many resources requested for launch", which the runtime header explains as "the kernel launch specifies too many threads for the kernel's register count". The command-line alternative, -maxrregcount=N, caps every kernel in the file at once.

Letting CUDA suggest a block size. cudaOccupancyMaxPotentialBlockSize(&minGrid, &block, kernel) returns the block size with the highest occupancy and the smallest grid that fills the GPU. NVIDIA ships the same logic as a host-only header, cuda_occupancy.h, so it runs without a GPU: compiled and run here for this page's kernels on four GPUs, and checked against this page's JavaScript port, the two agree on 1,155 of 1,155 values (0 mismatches) compiled and run here. Its answer for the simple scale kernel is 1,024 threads on H100 and 768 on the RTX 5090: it searches from the largest block size down and keeps the first that reaches the highest occupancy. That maximises occupancy, not speed; treat it as a starting point.

Block size in practice. Always a multiple of 32 (a partial warp wastes lanes). Too small hits the block-slot cap: 32-thread blocks on an H100 give at most 32 blocks of one warp, 50% occupancy derived. Too large makes each block a big unit to schedule and synchronise. 128 to 256 is the usual default. On the M1 Pro, a memory-bound y = 2x over 64 Mi floats ran at 156.9 to 161.5 GB/s for every threadgroup size from 32 to 1,024 measured on Apple M1 Pro GPU: once enough threads are in flight overall, a simple kernel does not care. Kernels that use shared memory per block or synchronise inside the block do care, and are tuned by measurement (the autotuning in {{Triton and Gluon|n:3c65c17b0d0d81729d15ed4d1a4461b3}} is exactly this search).

Waves and the tail

Blocks are handed to SMs as slots free up. If a grid has B blocks and the GPU holds S SMs × k blocks per SM at once, the grid runs in ceil(B / (S·k)) waves, and the last wave may be nearly empty while it costs nearly a full wave of time. NVIDIA's own example is a matrix multiply on an A100 (108 SMs) with 256 × 128 output tiles, one tile per block, one block per SM, M = 2,304, K = 4,096 ({{NVIDIA Matrix Multiplication Background guide, "Wave quantization"|https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html}}) vendor doc. When it matters for training. Waves matter when each block is long, which is the case for matmul tiles and attention: a GEMM whose tile count is just over a multiple of the SM count wastes most of its last wave, and cuBLAS heuristics choose tile shapes (and techniques such as split-K and Stream-K) partly to avoid it ({{Libraries and tensor cores|n:3c65c17b0d0d81a7adcaebee2f44a087}}). For the running example, a row sum with one 256-thread block per row has 4,096 blocks; an H100 holds 1,056 such blocks at once, so 4 waves, the last 87.9% full derived: fine. With hundreds of thousands of small blocks, the tail is a rounding error.
