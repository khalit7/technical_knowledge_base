3. Warps from the programmer's side

The hardware issues one instruction for 32 threads at a time, the warp; if a warp's threads disagree on a branch, both paths run in turn with the inactive lanes masked off (divergence: the parent's GPU simulator, section 1, steps it; {{GPU architecture|n:3c65c17b0d0d810682aae39bd614ec64}} section 5 measures its cost). What the warp lets you do: its 32 lanes can read each other's registers and vote, with no shared memory and no barrier. In a one-dimensional block a thread's lane is threadIdx.x % 32 (& 31) and its warp threadIdx.x / 32 (>> 5).

The row sum of the running example adds 4,096 numbers into one. Inside a warp, five shuffles do it: add the value 16 lanes away, then 8, 4, 2, 1, and lane 0 holds the sum of all 32. Predict how many shared-memory loads and barriers the same sum costs without shuffles, then compare:

One warp, lane i starting with the value i + 1 (sum 528) illustrative input. Shuffles: 5 SHFL, no memory, no barrier. Shared memory: 10 loads, 6 stores and 6 barriers. Instruction counts per step come from the real SASS of warp_sum (5 SHFL) and block_sum (per level: 2 LDS, 1 STS, 1 BAR) on sm_90a compiled here.

extern "C" __global__ void warp_sum(const float* x, float* out) {
  float v = x[blockIdx.x * blockDim.x + threadIdx.x];
  for (int off = 16; off > 0; off >>= 1) v += __shfl_down_sync(0xffffffffu, v, off);
  if ((threadIdx.x & 31) == 0) atomicAdd(out, v);   // one atomic per warp, not per thread
}

ptxas unrolls the loop into 5 SHFL instructions and one REDG (a reduction in global memory: the atomic add whose result nobody reads), using 12 registers and no shared memory compiled here. The cooperative-groups version, cg::reduce(tile, v, cg::plus<float>()), compiles to the same five shuffles in the butterfly (xor) pattern, after which every lane, not just lane 0, holds the sum. The other warp-level functions (votes, __reduce_add_sync, __syncwarp) are in the closed table below.

Why every warp function takes a mask and ends in _sync. Before Volta (2017) a warp had one program counter, so code could assume its 32 lanes ran in lockstep ("warp-synchronous" code). Since Volta each thread has its own program counter and lanes can be at different instructions, so warp-level code must name the lanes taking part (the mask, usually 0xffffffff) and synchronise explicitly with __syncwarp(). Old kernels (pre-2017 tutorials, some ggml or Caffe-era code) that use warp tricks without _sync are no longer guaranteed to work. Atomics are aggregated for you: for the naive if (x[i] > 0.f) atomicAdd(out, 1); ptxas already emits one atomic per warp instead of one per thread (closed block below), so write the simple atomic first, read the SASS, and measure before hand-optimising.

The compiler already aggregates your atomics. Thousands of threads hitting one address with atomicAdd(out, 1) should serialise. The real SASS ptxas emits for it on sm_90a compiled here:



VOTEU.ANY collects which lanes are active, UFLO picks the first of them, POPC counts them, and only that lane issues REDG.E.ADD with the count: one atomic per warp instead of up to 32. This is warp-aggregated atomics, the same thing the explicit __ballot_sync + __popc kernel does by hand (its SASS: one VOTE.ANY, one POPC, one REDG); __reduce_add_sync is a third spelling, a single REDUX.SUM.S32. On the M1 Pro the three versions of a 16 Mi-element count (one atomic per positive thread, one per SIMD-group after simd_sum, one per threadgroup) took 1.18, 1.08 and 1.10 ms (medians of 3 runs; runs of the first varied from 1.095 to 1.49) measured on Apple M1 Pro GPU: no reliable difference, all close to the time to read 64 MiB. Whether Apple's compiler aggregates the same way is not documented; the result is consistent with it.
