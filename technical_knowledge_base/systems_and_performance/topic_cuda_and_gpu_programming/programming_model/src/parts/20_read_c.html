1. Host and device: a complete program

The CPU (host) and the GPU (device) have separate memories and run separate code. A CUDA program is ordinary C++ for the host plus functions marked to run on the device; it allocates device memory, copies data in, launches, and copies results back. Here is the whole of it for the elementwise step, y = a * x on 1,048,576 floats, a real file compiled here with nvcc for sm_90a (H100) compiled here:

__global__ void scale(const float* x, float* y, float a, int n) {   // runs on the GPU
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) y[i] = a * x[i];
}
int main() {
  const int n = 1 << 20;                                 // 1,048,576 elements
  std::vector<float> hx(n), hy(n);                       // host arrays
  float *dx, *dy;                                        // device pointers: not usable on the CPU
  CUDA_CHECK(cudaMalloc(&dx, n * sizeof(float)));        // 1 allocate GPU memory
  CUDA_CHECK(cudaMalloc(&dy, n * sizeof(float)));
  CUDA_CHECK(cudaMemcpy(dx, hx.data(), n * sizeof(float), cudaMemcpyHostToDevice));  // 2 copy in
  int block = 256, grid = (n + block - 1) / block;       // 3 choose the launch: 4,096 blocks of 256
  scale<<<grid, block>>>(dx, dy, 2.0f, n);               // 4 launch (returns at once)
  CUDA_CHECK(cudaGetLastError());                        //   was the launch itself valid?
  CUDA_CHECK(cudaMemcpy(hy.data(), dy, n * sizeof(float), cudaMemcpyDeviceToHost));  // 5 copy out (waits)
  // 6 compare hy with 2 * hx on the CPU;  7 cudaFree(dx); cudaFree(dy);
}

The launch is asynchronous. scale<<<grid, block>>>(...), the execution configuration, starts grid blocks of block threads (4,096 × 256 = 1,048,576, one per element) and returns before the kernel runs: "Kernel launches are asynchronous with respect to the host thread" (Programming Guide, 2.1.4). The program waits at step 5, because "the cudaMemcpy API is synchronous. That is, it does not return until the copy has completed" (2.1.3.2), and a copy queued after the kernel on the same stream starts only when the kernel ends. Bar lengths are schematic, not measured: a launch is microseconds (section 8), the copies and the kernel depend on size. Hatched = the CPU is blocked waiting for the GPU illustrative timing.

Two more launch arguments are optional: bytes of dynamic shared memory per block and the stream to queue on, <<<grid, block, smemBytes, stream>>>. Three function markers: __global__ is a kernel (returns void; results go through pointers); __device__ a helper callable only from device code; __host__ __device__ compiles for both sides, the usual way to share small maths ({{CUDA Programming Guide, section 2.1|https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/intro-to-cuda-cpp.html}} vendor doc). nvcc splits the file: host code to the normal C++ compiler, device code to NVIDIA's, and the device machine code is embedded in the executable ({{The compiler stack|n:3f05c17b0d0d81ddbc00fac9e8a2ff89}}). The "thread index" costs almost nothing: in the real SASS it is two special-register reads and one multiply-add (listing below).

Predict: n = 1,000,000 and block = 256. How many threads does the launch start, and how many do no work?
grid = ceil(1,000,000 / 256) = 3,907 blocks, so 3,907 × 256 = 1,000,192 threads derived. The last 192 fail i < n and exit at once. Without that check they would read and write past the end of the arrays, and sometimes nothing visible happens, which is worse: the classic first-kernel bug (compute-sanitizer's memcheck finds it, section 6).
What the GPU actually runs: the real SASS of scale, and the run without a GPU (depth)


S2R R0, SR_TID.X and S2UR UR4, SR_CTAID.X read threadIdx.x and blockIdx.x from special registers; LDC R7, c[0x0][RZ] loads blockDim.x from the constant bank where the launch put it; IMAD is the index; ISETP and @P0 EXIT are the bounds check (threads past n simply exit); c[0x0][0x210] and up are the kernel's arguments, also delivered in the constant bank; LDG, FMUL, STG are the load, multiply and store.
