6. When things go wrong: CUDA's error model

The problem. CUDA functions return an error code (cudaError_t) instead of throwing, a kernel launch returns nothing at all, and a kernel that crashes is noticed only by some later call. Without a habit of checking, a bad launch looks like garbage output three functions later.

Three kinds of error, three places to catch them.

  1. API errors, returned by the call itself: a bad argument to cudaMemcpy, out of memory in cudaMalloc. Wrap every call in a check macro (below).
  2. Launch errors: an impossible configuration (more than 1,024 threads per block, too much shared memory: cudaErrorInvalidConfiguration; too many registers for the block: cudaErrorLaunchOutOfResources). The launch statement cannot return them, so ask right after it: cudaGetLastError(), which "returns current error state and then resets it to cudaSuccess" (cudaPeekAtLastError() returns it "without resetting it").
  3. Execution errors, raised while the kernel runs: an out-of-bounds or misaligned access, a device-side assert, a timeout. They surface at the next call that waits for the GPU (cudaDeviceSynchronize, a cudaMemcpy, or any later call), "returned by every CUDA runtime API until the error state has been cleared" ({{Programming Guide 2.1.7|https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/intro-to-cuda-cpp.html}}) vendor doc.
#define CUDA_CHECK(call) do { cudaError_t e_ = (call); if (e_ != cudaSuccess) \
  printf("%s:%d %s failed: %s (%s, code %d)\n", __FILE__, __LINE__, #call, \
         cudaGetErrorName(e_), cudaGetErrorString(e_), (int)e_); } while (0)
CUDA_CHECK(cudaGetDeviceCount(&n));
CUDA_CHECK(cudaMalloc(&d, 1024));
k<<<1, 256>>>(d);
CUDA_CHECK(cudaGetLastError());       // launch-time errors
CUDA_CHECK(cudaDeviceSynchronize());  // errors raised while the kernel ran

Sticky errors: some errors end the process's use of the GPU

For an illegal address (700) and an unspecified launch failure (719) the header says: "This leaves the process in an inconsistent state and any further CUDA work will return the same error. To continue using CUDA, the process must be terminated and relaunched." In a training job this is the familiar CUDA error: an illegal memory access was encountered that no try/except can recover from: the worker must restart, which is why elastic training restarts processes rather than retrying the step ({{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}}).


Finding the line that failed. Because errors surface late, the reported location is often wrong. Three tools fix that:


    

  • CUDA_LAUNCH_BLOCKING=1 makes every launch synchronous, so the error appears at the guilty launch. PyTorch's {{CUDA semantics notes|https://docs.pytorch.org/docs/2.14/notes/cuda.html}}: set it "to debug GPU errors or force synchronous behavior", for "more accurate" stack traces. Slow; for debugging only.
    • 

  • compute-sanitizer (default tool memcheck: "out of bounds and misaligned memory access errors"; also racecheck, initcheck for reads of uninitialised global memory, synccheck) names the kernel, thread, block and address of the first bad access ({{Compute Sanitizer docs v2026.3.0|https://docs.nvidia.com/compute-sanitizer/ComputeSanitizer/index.html}}). It runs the program much more slowly; use it on a small input.
    • 

  • A device-side assert(i < n) in the kernel stops it with error 710, whose runtime message is exactly device-side assert triggered (printed by the program above), and whose header comment reads "The device cannot be used again. All existing allocations are invalid": another sticky error. PyTorch's kernels assert on their inputs (its loss kernels check CUDA_KERNEL_ASSERT(INDEX >= 0 && INDEX < N_CLASSES) in {{Loss.cu|https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/cuda/Loss.cu}}, read 2026-10-05), which is where this message comes from in training: usually a label outside the number of classes.
    • 



When it matters for training: a crash with an illegal-address error mid-run is almost always an out-of-range index (embedding ids, labels, gather indices) or a custom kernel's bounds check. Re-run the failing step with CUDA_LAUNCH_BLOCKING=1, then under compute-sanitizer if it is your kernel.
