11. Common mistakes, a first-kernel checklist, interview questions

Common mistakes

No bounds check, or the wrong one
The grid is rounded up to whole blocks, so the last block runs past n (192 extra threads for n = 1,000,000 with 256-thread blocks). Without if (i < n) they read and write past the arrays; sometimes nothing visible happens, which is worse. compute-sanitizer's memcheck finds it.
Timing or error-checking the launch line
The launch returns before the kernel runs. A CPU timer around it measures the launch; an error check right after it sees only configuration errors. Synchronise (or use events) to time, and check after the next synchronising call for execution errors.
__syncthreads() inside a branch that not every thread takes
The barrier waits for all non-exited threads of the block; if some never arrive, the block hangs or misbehaves. Hoist it out of the branch (section 4).
Assuming warps run in lockstep
Since Volta, lanes of a warp can be at different instructions. Old warp-synchronous code that drops __syncwarp or uses the deprecated non-_sync intrinsics can break on new GPUs or new compilers.
Expecting blocks to run in some order, or to wait for each other
"No ordering guarantees are made by the scheduler" ({{Programming Guide 2.3.7|https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html}}). A block that spins waiting for a later block can deadlock if that block is never scheduled; only a cooperative launch guarantees co-residency.
Chasing 100% occupancy
Forcing registers down with __launch_bounds__ raised occupancy from 25% to 100% in section 5 and created 3 KB of spills per thread. Occupancy is a means to hide latency; measure time.
int indices on huge tensors
Past 2,147,483,647 elements a 32-bit index wraps. Attention scores for 16 × 32 × 4,096 × 4,096 are 8.6 billion elements.
Block size not a multiple of 32, or a 2D block with threadIdx.x on the wrong dimension
A 100-thread block wastes 28 lanes of its fourth warp. Making threadIdx.y walk the contiguous dimension spreads each warp's load over 32 rows (32 sectors instead of 4: the 1 × 256 case in section 2).
Treating a sticky error as recoverable
After an illegal address or a device-side assert, every later CUDA call fails; restart the process.

Checklist for a first kernel

  1. Index with blockIdx.x * blockDim.x + threadIdx.x and the ceiling-division grid; always bounds-check; 64-bit indices for very large tensors.
  2. Block size a multiple of 32, start at 128 or 256; tune by measurement.
  3. Wrap every runtime call in CUDA_CHECK; cudaGetLastError() after each launch while developing.
  4. Compile for your GPU: -arch=sm_90a for H100 features, -arch=sm_120 for an RTX 5090 (CUDA 12.8 or later), or -arch=native; current toolkit 13.4.2. Look at -Xptxas -v for registers and spills.
  5. Check results against a CPU or PyTorch reference before timing anything; run once under compute-sanitizer.

Interview questions, short answers

Why must blocks be independent?
So the hardware can run them in any order on any number of SMs: the same binary scales from a laptop GPU to a 170-SM card. Cross-block cooperation goes through atomics, a second kernel, a cooperative launch or (sm_90+) clusters.
What is a warp and why is it 32?
The 32 threads issued together by one instruction; it is the hardware's SIMD width and has been 32 on every NVIDIA GPU. Divergence, coalescing and shuffles are all defined per warp.
How do you sum 4,096 numbers in one block?
Each thread sums its share (grid-stride), each warp reduces with 5 shuffles, warp leaders write to shared memory, __syncthreads(), one warp reduces the partials. One barrier instead of eight.
How do you synchronise all blocks?
End the kernel and launch another (the usual way), or a cooperative launch with grid.sync(), whose grid must fit on the GPU at once because it is a spin barrier on a global counter.
What limits occupancy, and is higher always better?
Registers per thread, shared memory per block, threads per block and the block-slot cap, whichever runs out first. No: matmul-like kernels trade warps for registers and reuse; spills to reach high occupancy usually lose.
What does __launch_bounds__ do?
Promises a maximum block size (and optionally a minimum number of resident blocks per SM) so ptxas caps registers to make that launch fit, possibly spilling. A launch above the promised size fails.
Your kernel takes 5 µs and the step is slow. Why?
Launch overhead: the CPU cannot queue kernels fast enough and the GPU idles. Fuse kernels, avoid synchronisations, use CUDA graphs.
What is wave quantization?
A grid of B blocks runs in ceil(B / (SMs × blocks per SM)) waves; a last wave with few blocks costs nearly a full wave. NVIDIA's A100 example: 108 tiles run in one wave, 117 in two, about twice the time for 0.5% more work.
An illegal memory access error appears at a cudaMemcpy. Is the copy wrong?
Probably not: execution errors surface at the next synchronising call. Re-run with CUDA_LAUNCH_BLOCKING=1 or under compute-sanitizer to find the kernel; the process must restart.
