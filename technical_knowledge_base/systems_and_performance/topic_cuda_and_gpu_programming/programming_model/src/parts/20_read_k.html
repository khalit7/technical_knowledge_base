Depth: mistakes, a first-kernel checklist, interview rehearsal

The mistakes the sections above already show (no bounds check, __syncthreads() in a branch, lockstep warps, chasing occupancy, 32-bit indices, sticky errors) are not repeated here.

Three more mistakes (depth)

Timing or error-checking the launch line. The launch returns before the kernel runs. A CPU timer around it measures the launch; an error check right after it sees only configuration errors. Synchronise (or use events) to time, and check after the next synchronising call for execution errors.

Expecting blocks to run in some order, or to wait for each other. "No ordering guarantees are made by the scheduler" ({{Programming Guide 2.3.7|https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html}}). A block that spins waiting for a later block can deadlock if that block is never scheduled; only a cooperative launch guarantees co-residency.

Block size not a multiple of 32, or threadIdx.x on the wrong dimension. A 100-thread block wastes 28 lanes of its fourth warp. Making threadIdx.y walk the contiguous dimension spreads each warp's load over 32 rows (32 sectors instead of 4: the 1 × 256 case in section 2).

Checklist for a first kernel (depth)
  1. Index with blockIdx.x * blockDim.x + threadIdx.x and the ceiling-division grid; always bounds-check; 64-bit indices for very large tensors.
  2. Block size a multiple of 32, start at 128 or 256; tune by measurement.
  3. Wrap every runtime call in CUDA_CHECK; cudaGetLastError() after each launch while developing.
  4. Compile for your GPU: -arch=sm_90a for H100 features, -arch=sm_120 for an RTX 5090 (CUDA 12.8 or later), or -arch=native; current toolkit 13.4.2. Look at -Xptxas -v for registers and spills.
  5. Check results against a CPU or PyTorch reference before timing anything; run once under compute-sanitizer.
Interview rehearsal: four design questions (optional)

Why must blocks be independent? So the hardware can run them in any order on any number of SMs: the same binary scales from a laptop GPU to a 170-SM card. Cross-block cooperation goes through atomics, a second kernel, a cooperative launch or (sm_90+) clusters.

How do you sum 4,096 numbers in one block? Each thread sums its share (grid-stride), each warp reduces with 5 shuffles, warp leaders write to shared memory, __syncthreads(), one warp reduces the partials. One barrier instead of eight.

What limits occupancy, and is higher always better? Registers per thread, shared memory per block, threads per block and the block-slot cap, whichever runs out first. No: matmul-like kernels trade warps for registers and reuse; spills to reach high occupancy usually lose.

An illegal memory access error appears at a cudaMemcpy. Is the copy wrong? Probably not: execution errors surface at the next synchronising call. Re-run with CUDA_LAUNCH_BLOCKING=1 or under compute-sanitizer to find the kernel; the process must restart.
