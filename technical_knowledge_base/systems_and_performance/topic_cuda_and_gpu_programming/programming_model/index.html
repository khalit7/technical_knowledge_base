The idea in one screen

You write the code of one thread; a launch runs it on a grid of blocks, each block split into warps of 32 threads that issue together. Each thread computes its own index to find its data; threads cooperate only inside a warp or a block; and the GPU places as many blocks on each SM as registers and shared memory allow (occupancy), running the rest in waves.

Fig. 1 unpacks the running example's launch, scale<<<4096, 256>>> (section 1), one level per step derived:

  1. The grid: 4,096 blocks. The launch asks for a grid of 4,096 blocks of 256 threads, one thread per element (4,096 × 256 = 1,048,576). Blocks 0 to 31 are drawn. Blocks run in any order on any SM, so they never wait for each other.
  2. Block 9: 256 threads in 8 warps. One block always runs on one SM, never split. The hardware cuts it into warps by linear thread id: warp w holds threads 32w to 32w + 31, so 256 threads = 8 warps.
  3. Warp 1: 32 lanes. Threads 32 to 63 of the block issue as one: each instruction runs for all 32 lanes at once.
  4. Lane 5 is thread 37. The thread highlighted is blockIdx.x 9, threadIdx.x 37 (warp 1, lane 5), so its element is i = 9 × 256 + 37 = 2,341: the only thing that makes it different from its neighbours is that index.
  5. Each level talks its own way. Under each plate: how its threads cooperate, and where it runs. The grid: atomics, or end the kernel, spread over all SMs in waves. The block: shared memory and __syncthreads(), on one SM. The warp: shuffles, votes and __syncwarp(). The thread: only its own registers.

You need: nothing beyond C or Python and the idea of a matrix in memory. What an SM physically contains and why a GPU needs thousands of threads to hide latency are on GPU architecture (sections 2 and 3); this page is how you program it.

1. Host and device: a complete program

The CPU (host) and the GPU (device) have separate memories and run separate code. A CUDA program is ordinary C++ for the host plus functions marked to run on the device; it allocates device memory, copies data in, launches, and copies results back. Here is the whole of it for the elementwise step, y = a * x on 1,048,576 floats, a real file compiled here with nvcc for sm_90a (H100) compiled here:

__global__ void scale(const float* x, float* y, float a, int n) {   // runs on the GPU
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) y[i] = a * x[i];
}
int main() {
  const int n = 1 << 20;                                 // 1,048,576 elements
  std::vector<float> hx(n), hy(n);                       // host arrays
  float *dx, *dy;                                        // device pointers: not usable on the CPU
  CUDA_CHECK(cudaMalloc(&dx, n * sizeof(float)));        // 1 allocate GPU memory
  CUDA_CHECK(cudaMalloc(&dy, n * sizeof(float)));
  CUDA_CHECK(cudaMemcpy(dx, hx.data(), n * sizeof(float), cudaMemcpyHostToDevice));  // 2 copy in
  int block = 256, grid = (n + block - 1) / block;       // 3 choose the launch: 4,096 blocks of 256
  scale<<<grid, block>>>(dx, dy, 2.0f, n);               // 4 launch (returns at once)
  CUDA_CHECK(cudaGetLastError());                        //   was the launch itself valid?
  CUDA_CHECK(cudaMemcpy(hy.data(), dy, n * sizeof(float), cudaMemcpyDeviceToHost));  // 5 copy out (waits)
  // 6 compare hy with 2 * hx on the CPU;  7 cudaFree(dx); cudaFree(dy);
}

Bar lengths are schematic, not measured: a launch is microseconds (section 8), the copies and the kernel depend on size. Hatched = the CPU is blocked waiting for the GPU illustrative timing.

The launch is asynchronous. scale<<<grid, block>>>(...), the execution configuration, starts grid blocks of block threads (4,096 × 256 = 1,048,576, one per element) and returns before the kernel runs: "Kernel launches are asynchronous with respect to the host thread" (Programming Guide, 2.1.4). The program waits at step 5, because "the cudaMemcpy API is synchronous. That is, it does not return until the copy has completed" (2.1.3.2), and a copy queued after the kernel on the same stream starts only when the kernel ends. The stepper walks through it, both timelines at once:

  1. Start. The host arrays hx and hy (1,048,576 floats, 4 MiB each) are in CPU memory. Nothing is on the GPU yet.
  2. 1 cudaMalloc, twice. 4 MiB each in GPU memory (1,048,576 × 4 B). dx and dy are device addresses: the CPU holds them but cannot dereference them.
  3. 2 cudaMemcpy, host to device. Synchronous: the CPU waits until the 4 MiB have crossed to the GPU.
  4. 3 and 4 The launch. scale<<<4096, 256>>>: the CPU writes a launch command into the stream's queue and returns at once. Nothing has run yet.
  5. The kernel runs; the CPU runs on. 4,096 blocks spread over the SMs. Meanwhile the CPU executes the next line, cudaGetLastError(): cudaSuccess, the launch was valid. It could do any other work here.
  6. 5 cudaMemcpy, device to host. Queued behind the kernel on the same stream, so it starts only when the kernel ends; the CPU is blocked from the call until the copy is done.
  7. 6 and 7 Check and free. Compare hy with 2 × hx on the CPU, then cudaFree. The CPU waited only at the two copies; the launch itself cost microseconds (section 8).

Two more launch arguments are optional: bytes of dynamic shared memory per block and the stream to queue on, <<<grid, block, smemBytes, stream>>>. Three function markers: __global__ is a kernel (returns void; results go through pointers); __device__ a helper callable only from device code; __host__ __device__ compiles for both sides, the usual way to share small maths (CUDA Programming Guide, section 2.1 vendor doc). nvcc splits the file: host code to the normal C++ compiler, device code to NVIDIA's, and the device machine code is embedded in the executable (The compiler stack). The "thread index" costs almost nothing: in the real SASS it is two special-register reads and one multiply-add (listing below).

Three patterns cover almost every kernel


// 1 one thread per element (the host launches ceil(n / block) blocks)

if (i < n) y[i] = a * x[i];

// 2 grid-stride loop: any grid size covers any n

  y[i] = a * x[i];

// 3 a 2D grid over a matrix: x walks columns, so neighbouring threads touch neighbouring addresses
int c = blockIdx.x * blockDim.x + threadIdx.x, r = blockIdx.y * blockDim.y + threadIdx.y;
if (r < rows && c < cols) y[r * cols + c] = a * x[r * cols + c];
// host: dim3 block(32, 8); dim3 grid((cols + 31) / 32, (rows + 7) / 8);


All three are in src/cuda/kernels/p1_index.cu and compile for all four targets; on sm_90a, ptxas gives the one-per-element and 2D kernels 10 registers per thread and the grid-stride kernel 14 (it carries the loop) compiled here. For the running example, the 4,096 × 4,096 scores take pattern 3 with a 128 by 512 grid of 32 × 8 blocks, or pattern 1 on the flattened 16,777,216 elements: for an elementwise step the shape does not matter as long as consecutive threads touch consecutive addresses.


Why the grid-stride loop is worth knowing. The grid no longer depends on n: launch exactly as many blocks as fit on the GPU at once (a persistent grid) and let each thread do several elements, run one block of one thread to debug serially, and do per-thread setup once instead of once per element (Mark Harris, "CUDA Pro Tip: Write Flexible Kernels with Grid-Stride Loops", NVIDIA, 2013 published). It does not remove the tail effect of section 5: the last iteration is still uneven.


Integer overflow. int stops at 231−1 = 2,147,483,647. A tensor of 16 × 32 × 4,096 × 4,096 attention scores has 8,589,934,592 elements, so blockIdx.x * blockDim.x + threadIdx.x computed in int wraps around silently derived. Use 64-bit arithmetic ((long long)blockIdx.x * blockDim.x, or size_t) whenever an index can pass two billion.






Which threads form a warp


The hardware groups a block's threads into warps by a single linear thread id, x + y·Dx + z·Dx·Dy ("the first index x moves the fastest, followed by y and then z"), and warp w holds linear ids 32w to 32w+31, "the first warp containing thread 0" (Programming Guide 2.3.2; 3.2, Hardware Implementation). So the block's shape decides which matrix elements one warp touches together. Pick a 256-thread shape over a row-major float32 matrix in the widget on the right:


32 × 8, 16 × 16 and 8 × 32 all touch 4 sectors per warp load, every byte used; narrower than 8 columns, sectors are half empty and the same load costs 8, then 32 sectors. Why sectors are the unit, and what it costs, is the subject of GPU memory hierarchy (coalescing). The rule to keep: make threadIdx.x walk the contiguous dimension.

3. Warps from the programmer's side


The hardware issues one instruction for 32 threads at a time, the warp; if a warp's threads disagree on a branch, both paths run in turn with the inactive lanes masked off (divergence: the parent's GPU simulator, section 1, steps it; GPU architecture section 5 measures its cost). What the warp lets you do: its 32 lanes can read each other's registers and vote, with no shared memory and no barrier. In a one-dimensional block a thread's lane is threadIdx.x % 32 (& 31) and its warp threadIdx.x / 32 (>> 5).

extern "C" __global__ void warp_sum(const float* x, float* out) {
  float v = x[blockIdx.x * blockDim.x + threadIdx.x];
  for (int off = 16; off > 0; off >>= 1) v += __shfl_down_sync(0xffffffffu, v, off);
  if ((threadIdx.x & 31) == 0) atomicAdd(out, v);   // one atomic per warp, not per thread
}


ptxas unrolls the loop into 5 SHFL instructions and one REDG (a reduction in global memory: the atomic add whose result nobody reads), using 12 registers and no shared memory compiled here. The cooperative-groups version, cg::reduce(tile, v, cg::plus<float>()), compiles to the same five shuffles in the butterfly (xor) pattern, after which every lane, not just lane 0, holds the sum. The other warp-level functions (votes, __reduce_add_sync, __syncwarp) are in the closed table below.


Why every warp function takes a mask and ends in _sync. Before Volta (2017) a warp had one program counter, so code could assume its 32 lanes ran in lockstep ("warp-synchronous" code). Since Volta each thread has its own program counter and lanes can be at different instructions, so warp-level code must name the lanes taking part (the mask, usually 0xffffffff) and synchronise explicitly with __syncwarp(). Old kernels (pre-2017 tutorials, some ggml or Caffe-era code) that use warp tricks without _sync are no longer guaranteed to work. Atomics are aggregated for you: for the naive if (x[i] > 0.f) atomicAdd(out, 1); ptxas already emits one atomic per warp instead of one per thread (closed block below), so write the simple atomic first, read the SASS, and measure before hand-optimising.

4. Synchronisation, from a warp to the whole GPU

The block barrier, and what happens without it


The block-wide row sum puts each thread's value in shared memory, then halves the active threads level by level: at level k, thread t < k adds s[t + k] into s[t]. Between levels every thread must wait until all the writes of the previous level have landed; that is __syncthreads(), which makes threads "wait until all non-exited threads in the thread block simultaneously reach the same __syncthreads()" (language extensions).   7. Result: 31 (should be 80). Thread 0 writes 31. Nothing crashed; the answer is simply wrong, and with different timing it would be wrong differently.
    8. 



On real hardware. The same 256-thread tree sum over 65,536 blocks of small integers, as a Metal kernel with and without threadgroup_barrier (Metal's __syncthreads): with the barrier, 0 wrong blocks in 15 repetitions; without it, 10.4% to 80.4% of the blocks were wrong in each repetition (median 47.4%), a different set every time measured on Apple M1 Pro GPU. A race is not "usually fine": it is wrong at a rate that depends on timing, which is why it survives small tests.






The compiler makes it worse. Without a barrier, nothing tells the compiler that another thread may have changed s[t], so it may keep its own copy in a register. The real SASS shows it did: the correct block_sum reads shared memory 17 times (two loads per level, eight levels, plus the result) with 9 BAR.SYNC; the barrier-free version reads it only 9 times, because s[t] never gets re-read compiled here. The barrier is also a compiler fence: it is what makes the write of another thread visible at all.


The rules of __syncthreads()

It is "permitted in conditional code, but only if the condition evaluates uniformly across the entire thread block. Otherwise, execution may hang or produce unintended side effects" (language extensions): if (t < k) { ...; __syncthreads(); } is a bug, so put the barrier outside the if; threads that exit early are fine. Races and bad barriers are found by compute-sanitizer --tool racecheck ("shared memory data access hazards") and --tool synccheck ("invalid usages of synchronization primitives") vendor doc, v2026.3.0.


Atomics: combining without waiting


An atomic is a read-modify-write no other thread can interleave with: atomicAdd(&h[bin], 1) is correct even when thousands of threads hit the same bin. Atomics wait for no one, so they are how blocks combine results without a grid barrier: each block reduces its part with shuffles and shared memory, then issues one atomicAdd to the global total. The cost is contention: atomics to one address are processed one after another.


Contention fixes, and why float atomics are not bit-reproducible (depth)
The two fixes, both in p2_sync.cu: aggregate first (one atomic per warp, which the compiler did by itself in section 3) and privatise (a histogram in shared memory per block, ATOMS in SASS, merged into global memory once per block). Floating-point atomics add in arrival order, so a float sum by atomics can differ in the last bits from run to run; for bit-identical results reduce in a fixed order (Profiling, benchmarking and correctness covers tolerances).


Wider than a block: grid sync and clusters


A grid barrier. Cooperative groups (#include <cooperative_groups.h>) turn each scope into an object with sync(): this_thread_block(), tiled_partition<32>(block) for a warp, this_cluster(), this_grid(). grid.sync() is built from the narrower tools: every block meets at its block barrier, one thread per block adds to a counter in global memory and spins until every block has arrived. A spinning block occupies its SM, so blocks not yet scheduled could never start and the grid would hang; that is why grid.sync() needs a cooperative launch that refuses grids larger than what fits at once (here, on an H100 with 256-thread blocks: 8 blocks per SM × 132 SMs = 1,056 blocks at most derived with NVIDIA's occupancy rules). Most code takes the cheaper route: end the kernel and launch a second one.


Clusters (compute capability 9.0 and later) sit between block and grid: up to 8 blocks, portably, scheduled together on neighbouring SMs, each able to read the others' shared memory (distributed shared memory) and to meet at a hardware barrier, cluster.sync(). Hopper and Blackwell kernels use them to share tiles between SMs (TMA multicast, FlashAttention-3), which is on Libraries and tensor cores; how DSMEM is wired is on GPU architecture.

5. Choosing a launch: block size, occupancy, waves


The same kernel can be launched in thousands of ways, and the launch decides how much of the GPU works. You choose the block size, the grid size and the dynamic shared memory; the compiler chooses registers per thread, which you can steer. Two consequences follow: how many blocks fit on one SM at once (occupancy), and how many rounds the grid needs to get through the SMs (waves).






Occupancy: the resource that runs out first


Occupancy is resident warps per SM divided by the most the SM can hold (64 on A100, H100 and B200; 48 on the RTX 5090). A block is placed on an SM only if all of it fits: its warps, its registers (registers per thread × threads), its shared memory and a free block slot. Why resident warps hide latency, and the per-generation limits, are on GPU architecture (sections 3 and 4).


Steering registers trades occupancy for spills. One kernel with many live values per thread (96 accumulators), compiled three ways:

8. What a launch costs


Every launch is CPU work: the runtime and driver check the configuration, copy the arguments and write a command for the GPU into a queue. If kernels are short, the GPU finishes each one before the CPU has queued the next, and sits idle. Eager PyTorch launches at least one kernel per operation, so a model made of many small operations can be limited by launches rather than by the GPU, the regime Horace He calls overhead-bound ("Making Deep Learning Go Brrrr").


What travels with a launch, and the argument-size limit (depth)
What travels with a launch. The grid and block shapes, the shared memory size, the stream, and the arguments by value. Arguments were limited to 4,096 bytes; CUDA 12.1 raised the limit to 32,764 bytes on Volta and later (NVIDIA blog, Jun 5, 2023) vendor doc. Checked here with a pointer plus a struct argument: 8 + 32,756 = 32,764 bytes compiles; 8 + 32,760 fails with  compiled here. In SASS the arguments are read from a constant bank (the c[0x0][0x210] loads of section 1).






How long. NVIDIA's CUDA Graphs post measured a 2.9 µs kernel taking 9.6 µs per kernel when the CPU waited after each launch, 3.4 µs with CUDA Graphs (NVIDIA blog, 2019, V100) published. The asynchronous launch is what lets the CPU run ahead: queue many kernels, wait once. Three consequences for training code. Never synchronise in the hot loop without need (.item(), print(loss), a .cpu() every step: each one drains the queue). Fewer, larger kernels win when kernels are small: fusion, by hand or by torch.compile (Writing kernels, The compiler stack). And when the sequence of kernels repeats exactly, as in LLM decoding, record it once and replay it as a CUDA graph (Streams, CUDA graphs and multi-GPU programming). How to check: a profiler timeline shows gaps between kernels on the GPU row; if the gaps are as long as the kernels, you are overhead-bound (Profiling, benchmarking and correctness).

        if t < k:
            s[t] += s[t + k]
        cuda.syncthreads()
        k //= 2
    if t == 0:
        out[cuda.blockIdx.x] = s[0]
scale[grid, block](x, y, 2.0)                     # the launch: [grid, block] instead of <<<>>>




Numba-CUDA is now a separate package maintained by NVIDIA (numba-cuda docs). Its simulator executes kernels "one block at a time. One thread is spawned for each thread in the block, and scheduling of the execution of these threads is left up to the operating system", and it "does not implement warp-level operations" (simulator docs): good for checking indexing and barriers, useless for timing.

Depth: mistakes, a first-kernel checklist, interview rehearsal


The mistakes the sections above already show (no bounds check, __syncthreads() in a branch, lockstep warps, chasing occupancy, 32-bit indices, sticky errors) are not repeated here.


Three more mistakes (depth)


Timing or error-checking the launch line. The launch returns before the kernel runs. A CPU timer around it measures the launch; an error check right after it sees only configuration errors. Synchronise (or use events) to time, and check after the next synchronising call for execution errors.


Expecting blocks to run in some order, or to wait for each other. "No ordering guarantees are made by the scheduler" (Programming Guide 2.3.7). A block that spins waiting for a later block can deadlock if that block is never scheduled; only a cooperative launch guarantees co-residency.


Block size not a multiple of 32, or threadIdx.x on the wrong dimension. A 100-thread block wastes 28 lanes of its fourth warp. Making threadIdx.y walk the contiguous dimension spreads each warp's load over 32 rows (32 sectors instead of 4: the 1 × 256 case in section 2).

Interview rehearsal: four design questions (optional)


Why must blocks be independent? So the hardware can run them in any order on any number of SMs: the same binary scales from a laptop GPU to a 170-SM card. Cross-block cooperation goes through atomics, a second kernel, a cooperative launch or (sm_90+) clusters.


How do you sum 4,096 numbers in one block? Each thread sums its share (grid-stride), each warp reduces with 5 shuffles, warp leaders write to shared memory, __syncthreads(), one warp reduces the partials. One barrier instead of eight.


What limits occupancy, and is higher always better? Registers per thread, shared memory per block, threads per block and the block-slot cap, whichever runs out first. No: matmul-like kernels trade warps for registers and reuse; spills to reach high occupancy usually lose.


An illegal memory access error appears at a cudaMemcpy. Is the copy wrong? Probably not: execution errors surface at the next synchronising call. Re-run with CUDA_LAUNCH_BLOCKING=1 or under compute-sanitizer to find the kernel; the process must restart.

How the numbers are computed, and checked

Blocks per SM follow NVIDIA's cuda_occupancy.h (CUDA 13.4.2), ported line by line: registers are allocated per warp in units of 256 and split over 4 SM sub-partitions; each block uses its shared memory plus 1 KB reserved by the system, rounded up to 128 bytes, against the SM's maximum carveout; plus the warp limit, the block-slot limit and the barrier limit; per-SM limits from the CUDA Programming Guide, Tables 30 and 31. The suggested block size follows cudaOccMaxPotentialOccupancyBlockSize: from 1,024 down, the first block size reaching the highest number of resident threads. For the presets, the header itself was compiled and run without a GPU: it agrees with this page on . Waves = ceil(grid / (SMs × blocks per SM)) derived; they assume every block takes the same time. SM counts: A100 108, H100 SXM 132 (NVIDIA architecture blogs), B200 148 (independent measurement paper, arXiv 2512.02189), RTX 5090 170 (NVIDIA whitepaper).
