A GPU runs one function, the kernel, on tens of thousands of threads at once. The programming model is the contract between you and the hardware: how you launch those threads, how each one finds its piece of data, which threads may talk to each other and how they wait for each other, and what the launch costs. This page teaches that contract from zero with real CUDA code compiled by NVIDIA's own compiler, and real runs on a real GPU (an Apple M1 Pro, the only GPU available here; every number says where it comes from).

The running example. Attention scores s, a 4,096 by 4,096 float32 matrix, need two things on the way to a softmax: an elementwise step (scale every score, e = a * s: every element independent) and a reduction (the sum of each row: many elements combine into one). The elementwise step teaches launches and indexing; the reduction forces threads to cooperate, which teaches warps, shared memory, barriers and atomics. The parent page, Topic: cuda-and-gpu-programming, follows the full softmax and attention from PyTorch down to the instructions; this page owns the model underneath.

1. A complete CUDA program, line by line

The problem. The CPU (the host) and the GPU (the device) have separate memories and run separate code. A CUDA program is ordinary C++ for the host plus functions marked to run on the device, and it must move data across, start the work, wait for it and move results back. Here is the whole of it for the elementwise step, y = a * x on a million floats. It is a real file, compiled here with nvcc for sm_90a (H100) compiled here.

__global__ void scale(const float* x, float* y, float a, int n) {   // runs on the GPU
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) y[i] = a * x[i];
}
int main() {
  const int n = 1 << 20;                                 // 1,048,576 elements
  std::vector<float> hx(n), hy(n);                       // host arrays
  float *dx, *dy;                                        // device pointers: not usable on the CPU
  CUDA_CHECK(cudaMalloc(&dx, n * sizeof(float)));        // 1 allocate GPU memory
  CUDA_CHECK(cudaMalloc(&dy, n * sizeof(float)));
  CUDA_CHECK(cudaMemcpy(dx, hx.data(), n * sizeof(float), cudaMemcpyHostToDevice));  // 2 copy in
  int block = 256, grid = (n + block - 1) / block;       // 3 choose the launch: 4,096 blocks of 256
  scale<<<grid, block>>>(dx, dy, 2.0f, n);               // 4 launch (returns at once)
  CUDA_CHECK(cudaGetLastError());                        //   was the launch itself valid?
  CUDA_CHECK(cudaMemcpy(hy.data(), dy, n * sizeof(float), cudaMemcpyDeviceToHost));  // 5 copy out (waits)
  // 6 compare hy with 2 * hx on the CPU;  7 cudaFree(dx); cudaFree(dy);
}

Full source with the CUDA_CHECK macro and the CPU check: src/cuda/host/first_program.cu. Compiled with exit code 0; run in the container, which has no GPU or driver, it stopped at its first CUDA call (line 19, the first cudaMalloc) with CUDA driver version is insufficient for CUDA runtime version, exactly as the error check is meant to. Compiling needs no GPU; running does.

The three function markers. __global__ marks a kernel: it runs on the device and is launched from the host (it returns void; results go through pointers). __device__ marks a helper that runs on the device and is called only from device code. __host__ __device__ compiles a function for both sides, the usual way to share small maths (the CUDA Programming Guide, section 2.1 vendor doc). nvcc splits the file: host code goes to the normal C++ compiler, device code to NVIDIA's compiler, and the device machine code is embedded in the executable (The compiler stack has the details).

The launch. scale<<<grid, block>>>(...) is the execution configuration: grid blocks of block threads each, here 4,096 × 256 = 1,048,576 threads, one per element. Two more optional arguments follow: bytes of dynamic shared memory per block and the stream to queue on, <<<grid, block, smemBytes, stream>>>. "Kernel launches are asynchronous with respect to the host thread" (Programming Guide, 2.1.4): the call queues the work and returns. That is why step 5 is where the program waits: "The cudaMemcpy API is synchronous. That is, it does not return until the copy has completed" (2.1.3.2), and a copy queued after the kernel on the same stream starts only after the kernel ends.

What the GPU actually runs. Below is the real SASS (the GPU's machine code) ptxas produced for scale on sm_90a, the whole kernel. Read it once: it shows that the "thread index" is just two special registers and one multiply-add.



S2R R0, SR_TID.X and S2UR UR4, SR_CTAID.X read threadIdx.x and blockIdx.x from special registers; LDC R7, c[0x0][RZ] loads blockDim.x from the constant bank where the launch put it; IMAD is the index; ISETP and @P0 EXIT are the bounds check (threads past n simply exit); c[0x0][0x210] and up are the kernel's arguments, also delivered in the constant bank; LDG, FMUL, STG are the load, multiply and store. Each instruction is issued once per warp of 32 threads. compiled here


Predict: n = 1,000,000 and block = 256. How many threads does the launch start, and how many do no work?




grid = ceil(1,000,000 / 256) = 3,907 blocks, so 3,907 × 256 = 1,000,192 threads derived. The last 192 fail i < n and exit at once. Without that check they would read and write past the end of the arrays: the classic first-kernel bug (section 6).

Three patterns cover almost every kernel


// 1 one thread per element (the host launches ceil(n / block) blocks)
int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) y[i] = a * x[i];

// 2 grid-stride loop: any grid size covers any n
for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += gridDim.x * blockDim.x)
  y[i] = a * x[i];

// 3 a 2D grid over a matrix: x walks columns, so neighbouring threads touch neighbouring addresses
int c = blockIdx.x * blockDim.x + threadIdx.x, r = blockIdx.y * blockDim.y + threadIdx.y;
if (r < rows && c < cols) y[r * cols + c] = a * x[r * cols + c];
// host: dim3 block(32, 8); dim3 grid((cols + 31) / 32, (rows + 7) / 8);


All three are in src/cuda/kernels/p1_index.cu and compile for all four targets. On sm_90a, ptxas gives the one-per-element and 2D kernels 10 registers per thread and the grid-stride kernel 14 (it carries the loop) compiled here. For the running example, the 4,096 × 4,096 scores take pattern 3 with a 128 by 512 grid of 32 × 8 blocks, or pattern 1 on the flattened 16,777,216 elements: for an elementwise step the shape does not matter as long as consecutive threads touch consecutive addresses.


Why the grid-stride loop is worth knowing. The grid size no longer depends on n: you can launch exactly as many blocks as fit on the GPU at once and let each thread do several elements (a persistent grid), run with one block of one thread to debug serially, and let per-thread setup (loading a constant, computing a base pointer) happen once per thread instead of once per element. Mark Harris's "CUDA Pro Tip: Write Flexible Kernels with Grid-Stride Loops" (NVIDIA, 2013) is the classic reference published. It does not remove the tail effect of section 5: the last iteration is still uneven.


Integer overflow. int stops at 231−1 = 2,147,483,647. A tensor of 16 × 32 × 4,096 × 4,096 attention scores has 8,589,934,592 elements, so blockIdx.x * blockDim.x + threadIdx.x computed in int wraps around silently derived. Use 64-bit arithmetic ((long long)blockIdx.x * blockDim.x, or size_t) whenever an index can pass two billion.


Which threads form a warp


The hardware groups a block's threads into warps of 32 by a single linear thread id: "the first index x moves the fastest, followed by y and then z", and "each warp contains threads of consecutive, increasing thread IDs with the first warp containing thread 0" (Programming Guide 2.3.2; 3.2, Hardware Implementation). So the linear id is x + y·Dx + z·Dx·Dy, and warp w holds linear ids 32w to 32w+31. The block's shape therefore decides which matrix elements one warp touches together. Pick a 256-thread shape over a row-major float32 matrix:










Each cell is one thread of the block placed on the matrix element it handles (columns across, rows down), coloured by warp. Click a cell to see that thread's numbers. Sectors: the 32-byte pieces of memory one warp's load touches, if the rows start 32-byte aligned and are more than a block wide derived: rows touched × ceil(columns per row × 4 B / 32 B).




32 × 8, 16 × 16 and 8 × 32 all touch 4 sectors per warp load, every byte used; narrower than 8 columns, sectors are half empty and the same load costs 8, then 32 sectors. Why sectors are the unit, and what it costs, is the subject of GPU memory hierarchy (coalescing). The rule to keep: make threadIdx.x walk the contiguous dimension.

3. Warps from the programmer's side


Recap. The hardware issues one instruction for 32 threads at a time, the warp; if the threads of a warp disagree on a branch, both paths run in turn with the inactive lanes masked off (divergence). The parent page's section 2 animates this, and GPU architecture (section 5) measures its cost. This section is about what the warp lets you do: the 32 lanes of a warp can read each other's registers and vote, with no shared memory and no barrier.


In a one-dimensional block, a thread's lane (its position in the warp) is threadIdx.x % 32, written threadIdx.x & 31, and its warp is threadIdx.x / 32 (>> 5).

The row sum of the running example needs 4,096 numbers added into one. Inside a warp, five shuffles do it: add the value 16 lanes away, then 8, 4, 2, 1, and lane 0 holds the sum of all 32. Compare it with the same step done through shared memory, the way a block-wide sum must:














One warp, lane i starting with the value i + 1 (sum 528) illustrative input. Instruction counts per step come from the real SASS of warp_sum (5 SHFL) and block_sum (per level: 2 LDS, 1 STS, 1 BAR) on sm_90a compiled here.




extern "C" __global__ void warp_sum(const float* x, float* out) {
  float v = x[blockIdx.x * blockDim.x + threadIdx.x];
  for (int off = 16; off > 0; off >>= 1) v += __shfl_down_sync(0xffffffffu, v, off);
  if ((threadIdx.x & 31) == 0) atomicAdd(out, v);   // one atomic per warp, not per thread
}


ptxas unrolls the loop into 5 SHFL instructions and one REDG (a reduction in global memory, the atomic add whose result nobody reads), using 12 registers and no shared memory compiled here. The cooperative-groups version, cg::reduce(tile, v, cg::plus<float>()), compiles to the same five shuffles in the butterfly (xor) pattern, after which every lane, not just lane 0, holds the sum.


Independent thread scheduling: why the mask and __syncwarp exist


Before Volta (2017), a warp had one program counter, so code could assume the 32 lanes ran in lockstep and skip synchronisation inside a warp ("warp-synchronous" code, common in old reduction kernels with volatile shared memory). Since Volta each thread has its own program counter and "threads can now diverge and reconverge at sub-warp granularity"; NVIDIA's instruction is that "developers should explicitly synchronize such code using __syncwarp() to ensure correct behavior across all GPU generations" (Programming Guide 3.2) vendor doc. This is why every warp function since CUDA 9 takes a mask and has _sync in its name: "the legacy warp-level primitives are deprecated starting in CUDA 9.0" and "implicit warp-synchronous programming is unsafe" (Lin and Grover, "Using CUDA Warp-Level Primitives", NVIDIA, Jan 15, 2018) published. When you read old kernels (pre-2017 tutorials, some ggml or Caffe-era code) and see warp-level tricks without _sync, that is the pattern that is no longer guaranteed.


The compiler already aggregates your atomics


The naive way to count the positive scores is one atomic per thread: if (x[i] > 0.f) atomicAdd(out, 1);. Thousands of threads hitting one address should serialise. The real SASS ptxas emits for it on sm_90a shows what happens instead compiled here:




VOTEU.ANY collects which lanes are active, UFLO picks the first of them, POPC counts them, and only that one lane issues REDG.E.ADD with the count: one atomic per warp instead of up to 32. This is warp-aggregated atomics, done for you, and it is the same thing the explicit __ballot_sync + __popc kernel does by hand (its SASS: one VOTE.ANY for the ballot, one POPC, one REDG); __reduce_add_sync gives a third spelling, a single REDUX.SUM.S32. On the M1 Pro the three versions of a 16 Mi-element count (one atomic per positive thread, one per SIMD-group after simd_sum, one per threadgroup) took 1.18, 1.08 and 1.10 ms (medians of 3 runs; runs of the first varied from 1.095 to 1.49) measured on Apple M1 Pro GPU: no reliable difference, all close to the time to read 64 MiB. Whether Apple's compiler aggregates the same way is not documented; the result is consistent with it. The lesson that transfers: write the simple atomic first, read the SASS, and measure before hand-optimising.

4. Synchronisation, from a warp to the whole GPU


The problem. A row sum needs threads to combine their partial results, and a thread may only read another thread's result after it has been written. GPUs give a different tool at each scope, and each scope has a price: the wider it is, the more expensive (or the more restricted) waiting becomes. Choosing the narrowest scope that works is most of the design of a reduction, a softmax or an attention kernel.

The block barrier, and what happens without it


The block-wide row sum puts each thread's value in shared memory, then halves the active threads level by level: at level k, thread t < k adds s[t + k] into s[t]. Between levels every thread must wait until all the writes of the previous level have landed; that is __syncthreads(), which makes threads "wait until all non-exited threads in the thread block simultaneously reach the same __syncthreads()" (language extensions). Leave it out and the code still compiles, still runs, and is wrong whenever one warp falls behind another:














A toy block of 16 threads drawn as two warps of 8 so it fits (real warps have 32); warp 1's load from global memory arrives one step late, as a slow memory access would. Shared memory starts empty (drawn as · and read as 0; real uninitialised shared memory holds whatever was there before) illustrative input: 3 1 4 1 5 9 2 6 5 3 5 8 9 7 9 3, sum 80.




On real hardware. The same 256-thread tree sum over 65,536 blocks of small integers, as a Metal kernel with and without threadgroup_barrier (Metal's __syncthreads): with the barrier, 0 wrong blocks in 15 repetitions; without it, 10.4% to 80.4% of the blocks were wrong in each repetition (median 47.4%), a different set every time measured on Apple M1 Pro GPU. A race is not "usually fine": it is wrong at a rate that depends on timing, which is why it survives small tests.


The compiler makes it worse. Without a barrier, nothing tells the compiler that another thread may have changed s[t], so it may keep its own copy in a register. The real SASS shows it did: the correct block_sum reads shared memory 17 times (two loads per level, eight levels, plus the result) with 9 BAR.SYNC; the barrier-free version reads it only 9 times, because s[t] never gets re-read compiled here. The barrier is also a compiler fence: it is what makes the write of another thread visible at all.


The rules of __syncthreads()

It is "permitted in conditional code, but only if the condition evaluates uniformly across the entire thread block. Otherwise, execution may hang or produce unintended side effects" (language extensions). So if (t < k) { ...; __syncthreads(); } is a bug: put the barrier outside the if, as in the code above. Threads that exit early are fine ("non-exited threads"). To find races and bad barriers, run the program under compute-sanitizer with --tool racecheck ("shared memory data access hazards") and --tool synccheck ("invalid usages of synchronization primitives") vendor doc, v2026.3.0.


Atomics: combining without waiting


An atomic is a read-modify-write that no other thread can interleave with: atomicAdd(&h[bin], 1) is correct even when thousands of threads hit the same bin. Atomics do not wait for other threads, so they are how blocks combine results without a grid barrier: each block reduces its part with shuffles and shared memory, then issues one atomicAdd to the global total. The cost is contention: atomics to one address are processed one after another. Two standard fixes, both in p2_sync.cu: aggregate first (one atomic per warp, done automatically in the case shown in section 3), and privatise (a histogram in shared memory per block, ATOMS in SASS, merged into global memory once per block). Floating-point atomics add in whatever order the threads arrive, so a float sum by atomics can differ in the last bits from run to run; if you need bit-identical results, reduce in a fixed order (Profiling, benchmarking and correctness covers tolerances).


Wider than a block: cooperative groups, grid sync, clusters


Cooperative groups (#include <cooperative_groups.h>) turn each scope into an object with sync(), size() and thread_rank(): this_thread_block(), tiled_partition<32>(block) for a warp, this_cluster(), this_grid(). The kernel below normalises an array by its own total: phase 1 sums, a grid-wide barrier, phase 2 divides.


cg::grid_group grid = cg::this_grid();
float v = 0.f;
for (int i = grid.thread_rank(); i < n; i += grid.size()) v += x[i];
v = cg::reduce(cg::tiled_partition<32>(cg::this_thread_block()), v, cg::plus<float>());
if ((threadIdx.x & 31) == 0) atomicAdd(&partial[0], v);
grid.sync();                         // every block has added before anyone reads
float total = partial[0];
for (int i = grid.thread_rank(); i < n; i += grid.size()) x[i] /= total;


Here is how grid.sync() is implemented, from the real SASS (the relevant instructions in order) compiled here:




Every block meets at its block barrier; one thread per block issues a GPU-wide memory fence and an atomic add on a counter in global memory, then spins (LD.E.STRONG.GPU in a loop with YIELD) until the counter shows every block has arrived; then the block barrier releases the rest. A spinning block occupies its SM. If some blocks of the grid were still waiting to be scheduled, they could never start, and the resident ones would spin forever. That is why a grid barrier needs a cooperative launch (cudaLaunchCooperativeKernel) that refuses grids larger than what fits at once, failing with cudaErrorCooperativeLaunchTooLarge, which the runtime's own header defines as more blocks than "cudaOccupancyMaxActiveBlocksPerMultiprocessor ... times the number of multiprocessors" (driver_types.h, CUDA 13.4.2). For this kernel on an H100 with 256-thread blocks: 8 blocks per SM × 132 SMs = 1,056 blocks at most derived with NVIDIA's occupancy rules. In practice most code takes the cheaper route: end the kernel and launch a second one.


Clusters (compute capability 9.0 and later) sit between block and grid. __cluster_dims__(2, 1, 1) pairs blocks; cluster.map_shared_rank(s, other) returns a pointer into the partner block's shared memory (distributed shared memory), and cluster.sync() compiles to the hardware cluster barrier UCGABAR_ARV / UCGABAR_WAIT, the same on sm_90a, sm_100a and sm_120. For sm_80 the compiler refuses: __cluster_dims__ is not supported for this GPU architecture compiled here. The second cluster.sync() in p4_cluster.cu matters: a block must not exit while its partner may still read its shared memory. Clusters are how Hopper and Blackwell kernels share tiles between SMs (TMA multicast, FlashAttention-3); that use is on Libraries and tensor cores, and the hardware (how DSMEM is wired) on GPU architecture.






5. Choosing a launch: block size, occupancy, waves


The problem. The same kernel can be launched in thousands of ways, and the launch decides how much of the GPU works. You choose the block size, the grid size and the dynamic shared memory; the compiler chooses registers per thread, which you can steer. Two consequences follow, both explained below: how many blocks fit on one SM at once (occupancy), and how many rounds the grid needs to get through the SMs (waves).


Occupancy, from your side of the launch


Occupancy is resident warps per SM divided by the maximum the SM can hold (64 on A100, H100 and B200; 48 on the RTX 5090). A block is placed on an SM only if all of its resources fit: its warps, its registers (registers per thread × threads), its shared memory, and a free block slot. The per-generation limits, and why occupancy hides latency, are on GPU architecture (sections 3 and 4). What matters here is which of your choices moves it. One kernel with many live values per thread (96 accumulators), compiled three ways:


__global__ void heavy_plain(...)                              // the compiler picks registers freely
__global__ void __launch_bounds__(1024) heavy_lb1024(...)     // "I will launch up to 1,024 threads per block"
__global__ void __launch_bounds__(256, 8) heavy_lb256x8(...)  // "256 threads, and I want 8 blocks per SM"




Registers and spills: ptxas -v, CUDA 13.4.2 compiled here. Occupancy at 256 threads per block: NVIDIA's rules from cuda_occupancy.h derived. "Spill" bytes are values that did not fit in registers and went to local memory, which lives in the GPU's main memory behind the caches (GPU memory hierarchy).


Read the table as a trade. __launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor) tells ptxas the launch you promise, so it caps registers to make that launch fit: 1,024 threads in 65,536 registers leaves 64 per thread, and 8 blocks of 256 leaves 32. Occupancy goes up; so do spills. Which one wins is a measurement, not a rule; for matmul and attention kernels, which reuse values held in registers, the answer is usually fewer warps and no spills. Two real details: on sm_120 ptxas printed Value of threads per SM for entry heavy_lb256x8 is out of range. .minnctapersm will be ignored (8 × 256 = 2,048 threads, but an sm_120 SM holds 1,536) and kept 128 registers; and heavy_plain launched with 1,024 threads would need 128 × 1,024 = 131,072 registers, twice an SM's 65,536, so the launch fails with cudaErrorLaunchOutOfResources, "too many resources requested for launch", which the runtime header explains as "the kernel launch specifies too many threads for the kernel's register count". The command-line alternative, -maxrregcount=N, caps every kernel in the file at once.


Letting CUDA suggest a block size. cudaOccupancyMaxPotentialBlockSize(&minGrid, &block, kernel) returns the block size with the highest occupancy and the smallest grid that fills the GPU. NVIDIA ships the same logic as a host-only header, cuda_occupancy.h, so it runs without a GPU: compiled and run here for this page's kernels on four GPUs, and checked against this page's JavaScript port, the two agree on 1,155 of 1,155 values (0 mismatches) compiled and run here. Its answer for the simple scale kernel is 1,024 threads on H100 and 768 on the RTX 5090: it searches from the largest block size down and keeps the first that reaches the highest occupancy. That maximises occupancy, not speed; treat it as a starting point.


Block size in practice. Always a multiple of 32 (a partial warp wastes lanes). Too small hits the block-slot cap: 32-thread blocks on an H100 give at most 32 blocks of one warp, 50% occupancy derived. Too large makes each block a big unit to schedule and synchronise. 128 to 256 is the usual default. On the M1 Pro, a memory-bound y = 2x over 64 Mi floats ran at 156.9 to 161.5 GB/s for every threadgroup size from 32 to 1,024 measured on Apple M1 Pro GPU: once enough threads are in flight overall, a simple kernel does not care. Kernels that use shared memory per block or synchronise inside the block do care, and are tuned by measurement (the autotuning in Triton and Gluon is exactly this search).


Waves and the tail


Blocks are handed to SMs as slots free up. If a grid has B blocks and the GPU holds S SMs × k blocks per SM at once, the grid runs in ceil(B / (S·k)) waves, and the last wave may be nearly empty while it costs nearly a full wave of time. NVIDIA's own example is a matrix multiply on an A100 (108 SMs) with 256 × 128 output tiles, one tile per block, one block per SM, M = 2,304, K = 4,096 (NVIDIA Matrix Multiplication Background guide, "Wave quantization") vendor doc. Growing N from 1,536 to 1,544 adds 0.5% more work:














Each square is one of the 108 SMs, drawn to scale in count; time is in units of one tile's run time, assumed equal for every tile derived: tiles = ceil(M/256) × ceil(N/128); waves = ceil(tiles / 108). NVIDIA reports that "GFLOPS roughly halve and duration roughly doubles from N=1536 to N=1544".




Measured on a real GPU. A compute-only Metal kernel with 1,024-thread threadgroups, each doing the same work, launched with 1 to 72 threadgroups on the M1 Pro's 16 GPU cores measured on Apple M1 Pro GPU:




Median of 3 runs (dots: each run); time rises in steps at 17, 33, 49 and 65 threadgroups, about 1.31 ms per extra wave: 16 threadgroups of this size run at once, one per core. 17 threadgroups take as long as 32. The scattered points at the left are the first launches of runs 1 and 3, slowed by warm-up and by other jobs on the laptop.


When it matters for training. Waves matter when each block is long, which is the case for matmul tiles and attention: a GEMM whose tile count is just over a multiple of the SM count wastes most of its last wave, and cuBLAS heuristics choose tile shapes (and techniques such as split-K and Stream-K) partly to avoid it (Libraries and tensor cores). For the running example, a row sum with one 256-thread block per row has 4,096 blocks; an H100 holds 1,056 such blocks at once, so 4 waves, the last 87.9% full derived: fine. With hundreds of thousands of small blocks, the tail is a rounding error. The Launch planner tab computes occupancy, the limiting resource and waves for this page's real kernels on four GPUs.






6. When things go wrong: CUDA's error model


The problem. CUDA functions return an error code (cudaError_t) instead of throwing, a kernel launch returns nothing at all, and a kernel that crashes is noticed only by some later call. Without a habit of checking, a bad launch looks like garbage output three functions later.


Three kinds of error, three places to catch them.


    

  1. API errors, returned by the call itself: a bad argument to cudaMemcpy, out of memory in cudaMalloc. Wrap every call in a check macro (below).
    2. 

  2. Launch errors: an impossible configuration (more than 1,024 threads per block, too much shared memory: cudaErrorInvalidConfiguration; too many registers for the block: cudaErrorLaunchOutOfResources). The launch statement cannot return them, so ask right after it: cudaGetLastError(), which "returns current error state and then resets it to cudaSuccess" (cudaPeekAtLastError() returns it "without resetting it").
    3. 

  3. Execution errors, raised while the kernel runs: an out-of-bounds or misaligned access, a device-side assert, a timeout. They surface at the next call that waits for the GPU (cudaDeviceSynchronize, a cudaMemcpy, or any later call), "returned by every CUDA runtime API until the error state has been cleared" (Programming Guide 2.1.7) vendor doc.
    4. 



#define CUDA_CHECK(call) do { cudaError_t e_ = (call); if (e_ != cudaSuccess) \
  printf("%s:%d %s failed: %s (%s, code %d)\n", __FILE__, __LINE__, #call, \
         cudaGetErrorName(e_), cudaGetErrorString(e_), (int)e_); } while (0)

Sticky errors: some errors end the process's use of the GPU

For an illegal address (700) and an unspecified launch failure (719) the header says: "This leaves the process in an inconsistent state and any further CUDA work will return the same error. To continue using CUDA, the process must be terminated and relaunched." In a training job this is the familiar CUDA error: an illegal memory access was encountered that no try/except can recover from: the worker must restart, which is why elastic training restarts processes rather than retrying the step (Distributed Training).


Finding the line that failed. Because errors surface late, the reported location is often wrong. Three tools fix that:


    

  • CUDA_LAUNCH_BLOCKING=1 makes every launch synchronous, so the error appears at the guilty launch. PyTorch's CUDA semantics notes: set it "to debug GPU errors or force synchronous behavior", for "more accurate" stack traces. Slow; for debugging only.
    • 

  • compute-sanitizer (default tool memcheck: "out of bounds and misaligned memory access errors"; also racecheck, initcheck for reads of uninitialised global memory, synccheck) names the kernel, thread, block and address of the first bad access (Compute Sanitizer docs v2026.3.0). It runs the program much more slowly; use it on a small input.
    • 

  • A device-side assert(i < n) in the kernel stops it with error 710, whose runtime message is exactly device-side assert triggered (printed by the program above), and whose header comment reads "The device cannot be used again. All existing allocations are invalid": another sticky error. PyTorch's kernels assert on their inputs (its loss kernels check CUDA_KERNEL_ASSERT(INDEX >= 0 && INDEX < N_CLASSES) in Loss.cu, read 2026-10-05), which is where this message comes from in training: usually a label outside the number of classes.
    • 



When it matters for training: a crash with an illegal-address error mid-run is almost always an out-of-range index (embedding ids, labels, gather indices) or a custom kernel's bounds check. Re-run the failing step with CUDA_LAUNCH_BLOCKING=1, then under compute-sanitizer if it is your kernel.

Why nvidia-smi shows your memory as used. PyTorch never calls cudaFree when a tensor dies: its caching allocator keeps the block for the next tensor, because cudaMalloc and cudaFree are slow and synchronising. The PyTorch notes: unused cached memory "still appears occupied in nvidia-smi"; torch.cuda.memory_allocated() counts live tensors and memory_reserved() counts everything the allocator holds; empty_cache() returns the unused part. When a run reports out-of-memory with plenty "reserved but unallocated", the cause is fragmentation, not a leak.


Shared memory is not allocated with this API. It is declared in the kernel: __shared__ float s[256]; (static, size known at compile time; ptxas reports "1024 bytes smem" for block_sum) or extern __shared__ float s[]; with the size given as the third launch argument (dynamic). Static shared memory "remain[s] limited to 48 KB", and "an explicit opt-in is also required to enable dynamic allocations above this limit" (cudaFuncSetAttribute(kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, bytes)); "the H100 GPU enables a single thread block to address up to 227 KB of shared memory" (Hopper tuning guide) vendor doc. Everything about using it well (banks, tiling) is on GPU memory hierarchy.






8. What a launch costs


The problem. Every kernel launch is CPU work: the runtime and driver check the configuration, copy the arguments, and write a command for the GPU into a queue. If kernels are short, the GPU finishes each one before the CPU has queued the next, and sits idle. Eager PyTorch launches at least one kernel per operation, so a model made of many small operations can be limited by launches rather than by the GPU, the regime Horace He calls overhead-bound ("Making Deep Learning Go Brrrr").


What travels with a launch. The grid and block shapes, the shared memory size, the stream, and the arguments by value. Arguments were limited to 4,096 bytes; CUDA 12.1 raised the limit to 32,764 bytes on Volta and later (NVIDIA blog, Jun 5, 2023) vendor doc. Checked here with a pointer plus a struct argument: 8 + 32,756 = 32,764 bytes compiles; 8 + 32,760 fails with  compiled here. In SASS the arguments are read from a constant bank (the c[0x0][0x210] loads of section 1).


How long. NVIDIA's CUDA Graphs post measured a 2.9 µs kernel taking 9.6 µs per kernel when the CPU waited after each launch, 3.4 µs with CUDA Graphs (NVIDIA blog, 2019, V100) published. The asynchronous launch is what lets the CPU run ahead: queue many kernels, wait once. On the M1 Pro, through MLX, the same tiny Metal kernel (1,024 threads) measured on Apple M1 Pro GPU:




Median of 3 runs (each the median of 7 trials). Launch and wait each time: 179.5 µs per kernel (runs 192.7, 179.5, 146.5). 200 launches queued, each reading the previous one's output, then one wait: 5.8 µs per kernel, about 31 times less. Both include MLX's Python and graph bookkeeping, so they are not CUDA numbers; the ratio is the lesson.


Three consequences for training code. Never synchronise in the hot loop without need (.item(), print(loss), a .cpu() every step: each one drains the queue). Fewer, larger kernels win when kernels are small: fusion, by hand or by torch.compile (Writing kernels, The compiler stack). And when the sequence of kernels repeats exactly, as in LLM decoding, record it once and replay it as a CUDA graph (Streams, CUDA graphs and multi-GPU programming). How to check: a profiler timeline shows gaps between kernels on the GPU row; if the gaps are as long as the kernels, you are overhead-bound (Profiling, benchmarking and correctness).






9. The same kernels from Python


You will rarely write a main(). The programming model is the same from Python; only the spelling changes. Four routes, each tried here for real in the container with the CUDA toolkit and no GPU, so each says how far it got.


Numba CUDA: Python syntax, CUDA semantics


from numba import cuda, float32
@cuda.jit
def scale(x, y, a):
    i = cuda.grid(1)                  # = blockIdx.x * blockDim.x + threadIdx.x
    if i < x.size:
        y[i] = a * x[i]
@cuda.jit
def block_sum(x, out):
    s = cuda.shared.array(256, dtype=float32)     # __shared__ float s[256]
    t = cuda.threadIdx.x
    s[t] = x[cuda.blockIdx.x * 256 + t]
    cuda.syncthreads()                            # __syncthreads()
    k = 128
    while k > 0:
        if t < k:
            s[t] += s[t + k]
        cuda.syncthreads()
        k //= 2
    if t == 0:
        out[cuda.blockIdx.x] = s[0]
scale[grid, block](x, y, 2.0)                     # the launch: [grid, block] instead of <<<>>>

11. Common mistakes, a first-kernel checklist, interview questions


Common mistakes


No bounds check, or the wrong one
The grid is rounded up to whole blocks, so the last block runs past n (192 extra threads for n = 1,000,000 with 256-thread blocks). Without if (i < n) they read and write past the arrays; sometimes nothing visible happens, which is worse. compute-sanitizer's memcheck finds it.


Timing or error-checking the launch line
The launch returns before the kernel runs. A CPU timer around it measures the launch; an error check right after it sees only configuration errors. Synchronise (or use events) to time, and check after the next synchronising call for execution errors.


__syncthreads() inside a branch that not every thread takes
The barrier waits for all non-exited threads of the block; if some never arrive, the block hangs or misbehaves. Hoist it out of the branch (section 4).


Assuming warps run in lockstep
Since Volta, lanes of a warp can be at different instructions. Old warp-synchronous code that drops __syncwarp or uses the deprecated non-_sync intrinsics can break on new GPUs or new compilers.


Expecting blocks to run in some order, or to wait for each other
"No ordering guarantees are made by the scheduler" (Programming Guide 2.3.7). A block that spins waiting for a later block can deadlock if that block is never scheduled; only a cooperative launch guarantees co-residency.


Chasing 100% occupancy
Forcing registers down with __launch_bounds__ raised occupancy from 25% to 100% in section 5 and created 3 KB of spills per thread. Occupancy is a means to hide latency; measure time.


int indices on huge tensors
Past 2,147,483,647 elements a 32-bit index wraps. Attention scores for 16 × 32 × 4,096 × 4,096 are 8.6 billion elements.


Block size not a multiple of 32, or a 2D block with threadIdx.x on the wrong dimension
A 100-thread block wastes 28 lanes of its fourth warp. Making threadIdx.y walk the contiguous dimension spreads each warp's load over 32 rows (32 sectors instead of 4: the 1 × 256 case in section 2).


Treating a sticky error as recoverable
After an illegal address or a device-side assert, every later CUDA call fails; restart the process.


Checklist for a first kernel


    

  1. Index with blockIdx.x * blockDim.x + threadIdx.x and the ceiling-division grid; always bounds-check; 64-bit indices for very large tensors.
    2. 

  2. Block size a multiple of 32, start at 128 or 256; tune by measurement.
    3. 

  3. Wrap every runtime call in CUDA_CHECK; cudaGetLastError() after each launch while developing.
    4. 

  4. Compile for your GPU: -arch=sm_90a for H100 features, -arch=sm_120 for an RTX 5090 (CUDA 12.8 or later), or -arch=native; current toolkit 13.4.2. Look at -Xptxas -v for registers and spills.
    5. 

  5. Check results against a CPU or PyTorch reference before timing anything; run once under compute-sanitizer.

Interview questions, short answers


Why must blocks be independent?
So the hardware can run them in any order on any number of SMs: the same binary scales from a laptop GPU to a 170-SM card. Cross-block cooperation goes through atomics, a second kernel, a cooperative launch or (sm_90+) clusters.


What is a warp and why is it 32?
The 32 threads issued together by one instruction; it is the hardware's SIMD width and has been 32 on every NVIDIA GPU. Divergence, coalescing and shuffles are all defined per warp.


How do you sum 4,096 numbers in one block?
Each thread sums its share (grid-stride), each warp reduces with 5 shuffles, warp leaders write to shared memory, __syncthreads(), one warp reduces the partials. One barrier instead of eight.


How do you synchronise all blocks?
End the kernel and launch another (the usual way), or a cooperative launch with grid.sync(), whose grid must fit on the GPU at once because it is a spin barrier on a global counter.


What limits occupancy, and is higher always better?
Registers per thread, shared memory per block, threads per block and the block-slot cap, whichever runs out first. No: matmul-like kernels trade warps for registers and reuse; spills to reach high occupancy usually lose.


What does __launch_bounds__ do?
Promises a maximum block size (and optionally a minimum number of resident blocks per SM) so ptxas caps registers to make that launch fit, possibly spilling. A launch above the promised size fails.


Your kernel takes 5 µs and the step is slow. Why?
Launch overhead: the CPU cannot queue kernels fast enough and the GPU idles. Fuse kernels, avoid synchronisations, use CUDA graphs.


What is wave quantization?
A grid of B blocks runs in ceil(B / (SMs × blocks per SM)) waves; a last wave with few blocks costs nearly a full wave. NVIDIA's A100 example: 108 tiles run in one wave, 117 in two, about twice the time for 0.5% more work.


An illegal memory access error appears at a cudaMemcpy. Is the copy wrong?
Probably not: execution errors surface at the next synchronising call. Re-run with CUDA_LAUNCH_BLOCKING=1 or under compute-sanitizer to find the kernel; the process must restart.

How the numbers are computed, and checked

Blocks per SM follow NVIDIA's cuda_occupancy.h (CUDA 13.4.2), ported line by line: registers are allocated per warp in units of 256 and split over 4 SM sub-partitions; each block uses its shared memory plus 1 KB reserved by the system, rounded up to 128 bytes, against the SM's maximum carveout; plus the warp limit, the block-slot limit and the barrier limit; per-SM limits from the CUDA Programming Guide, Tables 30 and 31. The suggested block size follows cudaOccMaxPotentialOccupancyBlockSize: from 1,024 down, the first block size reaching the highest number of resident threads. For the presets, the header itself was compiled and run without a GPU: it agrees with this page on . Waves = ceil(grid / (SMs × blocks per SM)) derived; they assume every block takes the same time. SM counts: A100 108, H100 SXM 132 (NVIDIA architecture blogs), B200 148 (independent measurement paper, arXiv 2512.02189), RTX 5090 170 (NVIDIA whitepaper).
