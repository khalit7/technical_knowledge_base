Setup: no NVIDIA GPU, so what is real here

This page was built on an Apple M1 Pro laptop. Its GPU is a real SIMT machine with the same building blocks as an NVIDIA GPU: groups of 32 threads that execute one instruction together, groups of threads that share a small fast on-chip memory, and a big slow memory everyone can reach. So the shape of every optimisation below transfers to CUDA, and the numbers are honest measurements of that shape. The sizes do not transfer: an H100 has about 20 times the memory bandwidth and, with tensor cores, about 200 times the matrix throughput of this GPU (section 5 does the arithmetic). 1. The softmax ladder: count the bytes

Softmax turns each row of scores into probabilities: find the row's maximum m, compute ex − m for every element (subtracting m keeps the exponentials from overflowing), add them up into s, divide each by s. That is about 5 arithmetic operations per element against 8 bytes moved (read 4, write 4 in fp32): far below this GPU's ridge point of about 30 operations per byte, so softmax is memory-bound: its speed is set by bytes moved, not by arithmetic. The input here is the Roofline lab's: 16,384 rows of 4,096 fp32 values (256 MiB in, 256 MiB out).

2. The matmul ladder: count the reuse


A matrix multiply C = A B of two 2,048 × 2,048 matrices does 2 × 2,0483 = 17.2 billion floating-point operations on 48 MiB of data: about 340 operations per byte at best, far above the ridge. So matmul is compute-bound if, and only if, each value loaded is reused many times while it sits on chip. Each rung below increases that reuse. 3. Fuse softmax into the matmul


In attention, softmax is followed by a matmul: O = softmax(S) V, where S holds one score per (query, key) pair and V holds one 64-number vector per key. Done the obvious way, softmax writes its whole N × N output P to device memory and the matmul reads it back. Fusing means one kernel does both, so P lives only in fast on-chip memory, a tile at a time. There is a catch: to normalise a row you need its maximum and sum, which you only know after seeing the whole row. Two ways out: read S twice (once for the statistics, once to multiply), or use the online softmax trick: keep a running maximum and, whenever it grows, rescale everything accumulated so far.

4. Attention: naive against online softmax


Attention for one head is O = softmax(Q KT / √d) V. The naive way runs three library calls and puts N × N matrices (scores S, then probabilities P) in device memory: memory grows with the square of the sequence length. The FlashAttention way is section 3's online kernel with one more step inside the loop: compute the 64 × 32 tile of scores from a tile of Q and a tile of K on chip. Nothing of size N × N ever exists. 6. The Triton side: same math, blocks instead of threads


In Triton you write what one program does to a block of data (a whole row, a 64 × 64 tile); the compiler decides which of its threads holds which element, how wide each load is, what goes through shared memory and which tensor-core instructions to use. Each kernel below was run with TRITON_INTERPRET=1 on the CPU against PyTorch in float64, then compiled for an A100 (sm_80) and an H100 (sm_90a) without a GPU, and its resources read from the binary. For the full PTX and SASS of these kinds of kernel, line by line, see the {{Compiler explorer|#t-compile}}.
