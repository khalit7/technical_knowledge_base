9. Profiling, benchmarking honestly, and checking correctness

No NVIDIA profiler was run for this page (there is no NVIDIA GPU); this section is from NVIDIA's documentation, with the M1 measurements as worked examples of the timing rules.

Two microscopes. Nsight Systems (nsys) records a timeline of the whole program: CPU threads, CUDA API calls, kernel launches, copies, NCCL, and your own NVTX ranges. It answers "where does the wall-clock time go?": gaps between kernels (the CPU or the launches are the bottleneck), communication that fails to overlap compute, a data loader that stalls. It is cheap, so always start there. Nsight Compute (ncu) zooms into one kernel: it replays the kernel many times to read hardware counters, so it is slow and changes timing, and you point it only at kernels the timeline already convicted. It answers "why is this kernel slow?". torch.profiler sits in between ("which PyTorch op is slow"), built like both on CUPTI, NVIDIA's profiling library. compute-sanitizer checks memory errors and races; run it before trusting a new kernel.

Read Nsight Compute top-down. Its "Speed of Light" section gives compute and memory throughput as percentages of peak, which places the kernel on the roofline immediately: memory high and compute low means memory-bound (move fewer bytes, fuse); compute high means compute-bound (use tensor cores, lower precision); both low means latency-bound (too few warps, divergence, a tail of idle SMs, or the kernel is tiny). Then the question decides the metric (the Report reader tab of {{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}} walks through real Nsight Compute reports with these questions):

QuestionWhere to look
Enough parallelism?achieved occupancy; grid size against SM count ("waves")
Coalesced?sectors per request in Memory Workload Analysis (4 is ideal for 32-bit loads)
Bank conflicts?l1tex__data_bank_conflicts_pipe_lsu_mem_shared

Spills?local memory traffic; confirm with -Xptxas -v
Correction to the old page
The old page said ncu locks clocks to base by default. The current {{Nsight Compute CLI documentation|https://docs.nvidia.com/nsight-compute/NsightComputeCli/index.html}} (v2026.3.1) lists --clock-control default boost (base, force-boost and none are options), and --cache-control default all (caches flushed between replays). Check the version you run.

Benchmarking honestly

  1. Synchronise. Launches are asynchronous, so a Python timer around a launch measures the launch. Use CUDA events (start.record(); f(); end.record(); torch.cuda.synchronize()), or synchronise before reading the clock when you want launch overhead included.
  2. Warm up. First calls pay compilation, autotuning, library heuristics and cold caches. Then time many repetitions and report a median with the spread, not the minimum of one run.
  3. Mind the cache. Timing the same small tensor in a loop measures L2 (50 MB on an H100, 96 MB on an RTX 5090), not HBM. Triton's triton.testing.do_bench always clears the L2 by zeroing a 256 MB buffer before each timed run, and returns the mean by default (return_mode="median" or quantiles= for more); it has no flush_l2 argument, contrary to the old page ({{testing.py|https://github.com/triton-lang/triton/blob/main/python/triton/testing.py}}, read 2026-10-05).
  4. Fix the clocks and the load. GPUs boost and throttle; lock clocks (nvidia-smi -lgc) or say you did not. On a shared machine, record the load.
  5. Compare fairly. Against torch.compile, not eager; against cuBLAS with the right epilogue and data type. Report achieved GB/s or TFLOP/s beside the roofline limit, so a speedup can be judged.
  6. Write down the environment: GPU, driver, CUDA, PyTorch and Triton versions, clocks.
Predict: the same MLX softmax was timed three times on this laptop, each run the median of 7 trials. How far apart were the three results?
measured on Apple M1 Pro GPU 12.36, 3.23, 3.21 ms. The first run was taken with the laptop's 1-minute load average at 6.0 (other agents were measuring at the same time); a median of 7 trials inside one run did not protect it, because the whole run was disturbed. Repeating runs, reporting spread and recording load is what exposed it. Every M1 number on this page is the median of 3 runs with each run's value shown.

Correctness: against a reference, with a tolerance

A fast wrong kernel is worse than a slow right one, and the bugs are quiet. Compare every output against a reference in higher precision, with a tolerance that matches the data type (float16 has about 3 significant digits; summing in a different order changes the last ones). measured on Apple M1 Pro GPU: the fused and unfused attention of section 5 differed by at most 0.00024 in float16 at N = 4,096, inside float16 rounding; the softmax matched a NumPy float32 reference to 3.7e-09. Test sizes that are not multiples of the tile, the first and last block, and large inputs: the {{Kernel lab|#t-lab}} records a synchronisation bug in its fused kernel that passed every small test and corrupted 1 to 5 random rows per run at 4,096 rows, fixed by using a full threadgroup barrier. On NVIDIA, compute-sanitizer --tool racecheck is built for exactly this class of bug.
