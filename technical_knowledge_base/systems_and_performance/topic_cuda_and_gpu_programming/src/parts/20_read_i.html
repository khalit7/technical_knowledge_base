Wavefront sizes: {{HIP programming model|https://rocm.docs.amd.com/projects/HIP/en/latest/understand/programming_model.html}} vendor doc. Apple's SIMD-group width of 32 was read from the M1 Pro's own Metal device by the {{GPU simulator|#t-sim}}.

ROCm and HIP (AMD). HIP is AMD's CUDA-like C++ ("the Runtime API serves the same role within ROCm as the CUDA Runtime API does in NVIDIA's stack", same page); most PyTorch kernels reach AMD Instinct parts through Triton's AMD backend. The wavefront of 64 is the trap when porting: warp-sized assumptions (a 32-bit lane mask, 32-way reductions) silently break. That holds for CDNA 3 and 4 (MI300X, MI355X) as of 2026-10-05; AMD's page for the next part, the MI455X, advertises "Wave32 execution" ({{AMD Instinct MI400|https://www.amd.com/en/products/accelerators/instinct/mi400.html}}, read 2026-10-05) vendor doc, so check the target before assuming 64. ROCm 10.0 (August 27, 2026; {{AMD ROCm blog|https://rocm.blogs.amd.com/ecosystems-and-partners/rocm-x-blog/README.html}}, {{Phoronix|https://www.phoronix.com/news/AMD-ROCm-10.0}}) jumped from 7.14 and added the ROCm CLI (a tech preview for install, validation, serving and diagnostics), Hyperloom (an "agentic system that automates end-to-end inference workload optimization", which AMD says cuts weeks of tuning to hours) and AMD Skills, validated ROCm knowledge packaged as agent skills for Claude, Cursor and Codex. The old page's "3.3 times inference and 2.4 times training over ROCm 7" appears in neither source unconfirmed.

Metal, on the Mac you are reading this on. Apple's GPU is a real SIMT GPU, which is why this page could measure divergence, coalescing, bank conflicts, latency hiding, tiling and fusion on it. Two differences matter. Memory is unified: CPU and GPU share the same DRAM (about 165 GB/s measured on the M1 Pro, against 3.35 TB/s of HBM on an H100), so there are no host-to-device copies and much less bandwidth. And there is no CUDA: you write Metal Shading Language, or from Python use MLX's mx.fast.metal_kernel, which is how the {{Kernel lab|#t-lab}} and {{GPU simulator|#t-sim}} kernels were run. PyTorch's mps device runs on Metal too.

CUDA in Rust (NVIDIA, September 8, 2026, {{NVIDIA blog|https://developer.nvidia.com/blog/introducing-cuda-rust-two-tracks-for-writing-gpu-kernels/}}), two tracks that mirror the CUDA and Triton ends of this page. cuda-oxide, the thread-level track, is "a custom rustc codegen backend" that takes kernels "through Rust MIR, the community Pliron IR framework, and LLVM IR down to PTX"; a DisjointSlice type "hands each thread exclusive access to its own element and nothing else", so aliasing between threads becomes a compile error; it is early alpha, needs a pinned nightly toolchain and compute capability 8.0 or newer. cutile-rs, the tile-level track, JIT-compiles kernels "through CUDA Tile IR", runs on stable Rust 1.89+ with CUDA 13.3, is on crates.io and is "already used outside NVIDIA in HuggingFace's Grout inference engine and in mistral.rs". No performance figures are claimed for either.

A learning path from PyTorch user to kernel author

Written for this laptop plus rented GPUs; there is no NVIDIA card at home. Times are reading or working estimates.

  1. The model and the memory ladder (about 4 h): PMPP chapters 1 to 6, or the CUDA Programming Guide's programming model chapter, with this page's {{GPU simulator|#t-sim}} beside it. Then Horace He's "Brrrr" (25 min) for the three regimes.
  2. First kernels on the Mac (a weekend): vector add, softmax and a tiled matmul as Metal kernels through MLX, reproducing the {{Kernel lab|#t-lab}} ladder and predicting each step before you time it.
  3. Triton (about 3 h, then practice): official tutorials 01 (vector add), 02 (fused softmax), 03 (matmul) and 06 (fused attention), run on the CPU with TRITON_INTERPRET=1 for correctness; Sasha Rush's Triton-Puzzles for indexing fluency.
  4. Read compiler output (2 h): compile your kernels for sm_90a and sm_120 without a GPU and read the PTX, SASS and ptxas -v, as the {{Compiler explorer|#t-compile}} does.
  5. Rent a GPU for a day (an H100 at about $3.99 per GPU-hour on demand at Lambda, fetched 2026-10-05): run Boehm's worklog kernels 1 to 6 and your Triton kernels, profile them with Nsight Systems and Nsight Compute, and benchmark them honestly (section 9).
  6. A real fusion project: a fused RMSNorm with a matmul epilogue, a dequantise-and-multiply kernel, or a FlashAttention variant, in Triton first and CUDA second, against torch.compile and cuBLAS baselines, written up as a worklog.
  7. Then read production kernels: FlashAttention-2 (CUDA), FlashAttention-4 (CuTe DSL), CUTLASS examples, ggml-cuda, vLLM's attention kernels; with section 7's vocabulary they become readable.

Throughout: the GPU MODE lectures follow roughly this order, and its Discord and kernel leaderboard supply questions and graded practice problems. Resources with times are in {{Further reading|#t-more}}.

Interview questions, with short answers

What is a warp, and why does it matter for performance?
32 threads that execute one instruction at a time together. Branch divergence, memory coalescing and shuffles are all defined per warp; a warp is the unit the scheduler switches between to hide latency.
Why is softmax memory-bound and matmul compute-bound?
Softmax does a handful of operations per element read, under one per byte, far below the roughly 295 operations per byte an H100 needs to be compute-bound. An N × N matmul does 2N³ operations on 3N² values, so its intensity grows with N, provided tiling keeps the reuse on chip.
What does shared memory buy you in a matmul?
Each tile of A and B is fetched from global memory once and reused by every thread in the block, cutting global traffic by the tile width; register tiling repeats the trick one level down.
Explain FlashAttention in three sentences.
Standard attention writes the N × N score and probability matrices to HBM. FlashAttention tiles Q, K and V so each block of scores is computed and consumed on chip, using the online-softmax rescaling to combine blocks, and recomputes scores in the backward pass instead of storing them. It does the same FLOPs with far fewer HBM bytes and O(N) extra memory.
High occupancy is good, right?
Only as a means. It helps memory-bound kernels hide latency; fast matmul and attention kernels run at low occupancy on purpose because registers per thread buy reuse. Measure achieved bandwidth or FLOPs, not occupancy.
Your custom kernel is 2 times faster than PyTorch. What do you check before believing it?
Correctness against a reference at several sizes; synchronisation and warmup in the timing; L2 effects (data larger than the cache, or flushed); the baseline (compiled, right dtype and layout); clocks and load; spread over repeated runs.
What is the difference between PTX and SASS?
PTX is a stable virtual instruction set; SASS is the real machine code of one GPU generation, produced from PTX by ptxas (or by the driver at load time). You read SASS to see what really runs: vector loads, tensor-core instructions, spills.
Why does a Hopper kernel not run on an RTX 5090?
sm_120 has TMA and clusters but not wgmma, tcgen05 or TMEM; a Hopper kernel built on wgmma will not even assemble for it. Consumer Blackwell kernels look like Ampere ones (mma.sync, register accumulators) plus TMA.
Nsight Systems or Nsight Compute first?
Systems: it shows where the time goes across the whole program (gaps, overlap, launch overhead) at little cost. Then Compute on the kernels the timeline convicts, to see why each is slow.
When would you write Triton, CUDA, or neither?
Neither if torch.compile or a library already does it. Triton for a new fusion or algorithm. CUDA or CUTLASS when you need control Triton hides (warp specialisation, exotic layouts) or the last few percent on a kernel that dominates the profile.
