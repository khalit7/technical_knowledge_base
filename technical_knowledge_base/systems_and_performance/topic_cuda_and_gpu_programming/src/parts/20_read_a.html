This page follows one operation from PyTorch down to the instructions. The operation is the heart of attention: take a matrix of scores, apply softmax along each row, and multiply the result by a matrix of values. In PyTorch it is two lines, p = torch.softmax(s, dim=-1) and o = p @ v, and in a training run it executes billions of times. By the end you should be able to say what the GPU does for each line, why the obvious way is slow, how FlashAttention fixes it, and how you would write, read, compile, profile and check such a kernel yourself.

1. What happens when you call torch.softmax on a GPU tensor

Suppose s is an 8,192 by 8,192 matrix of float32 scores on the GPU (256 MiB) and you write p = torch.softmax(s, dim=-1). Four things happen, and only the last one runs on the GPU.

  1. Dispatch. Python calls into PyTorch's C++ core, where every operator is registered once and implemented per device. The registry, {{native_functions.yaml|https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/native_functions.yaml}}, says _softmax.out goes to softmax_cpu_out on CPU, softmax_mps_out on a Mac and softmax_cuda_out on an NVIDIA GPU. The dispatcher reads the tensor's device and picks the CUDA one.
  2. Choose a kernel and its shape. A kernel is a function that runs on the GPU, executed by many threads at once. PyTorch's {{SoftMax.cu|https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/cuda/SoftMax.cu}} picks among several hand-written softmax kernels by row length: rows of at most 2,048 elements (and 8 KB) go to a kernel where one warp of 32 threads owns a row; longer rows like ours get one thread block per row (8,192 blocks), with the row kept in registers when it fits. read from PyTorch main, 2026-10-05
  3. Launch. The host (CPU) code puts "run this kernel with this many blocks of this many threads, with these pointers" into a stream, a queue of GPU work, and returns immediately. Python moves on to the next line while the GPU is still working. This is why GPU code is asynchronous, and why a Python timer around a GPU call measures almost nothing (section 9).
  4. Execute. The GPU's scheduler hands blocks to its streaming multiprocessors (SMs; an H100 SXM has 132 vendor spec), and each block reads its row from memory, finds the maximum, sums the exponentials and writes the normalised row back. The CPU waits only when it needs a value (p.item(), print(p), .cpu()): that wait is a synchronisation.

Which code runs depends on the operator. torch.matmul calls NVIDIA's closed-source cuBLAS or cuBLASLt (PyTorch's {{preferred_blas_library|https://docs.pytorch.org/docs/2.14/backends.html}} switch picks between them by heuristics by default). F.scaled_dot_product_attention picks among FlashAttention, memory-efficient attention, cuDNN attention and a plain C++ "math" fallback (the {{SDPBackend|https://github.com/pytorch/pytorch/blob/main/torch/nn/attention/__init__.py}} list). Softmax uses PyTorch's own kernels. And under torch.compile, none of these hand-written kernels may run at all: the compiler, TorchInductor, "translates PyTorch programs into OpenAI's Triton for GPUs and C++/OpenMP for CPUs" ({{PyTorch 2 paper, ASPLOS 2024|https://docs.pytorch.org/assets/pytorch2-2.pdf}}), generating a new kernel that can fuse the softmax with the operations around it.

Traffic counts each full read or write of a 256 MiB matrix. Time at H100 bandwidth = bytes / 3.35 TB/s derived; the M1 Pro column uses the softmax bandwidth measured below. Whether Inductor fuses a given pair is visible in its generated code (TORCH_LOGS=output_code); a pointwise op feeding a reduction is the textbook case it fuses.

Measured on the M1 Pro GPU measured on Apple M1 Pro GPU: MLX's softmax over the same 8,192 by 8,192 float32 matrix took 3.2 ms, which is 166 GB/s if the matrix is read once and written once. That equals the M1 Pro's measured copy bandwidth (about 165 GB/s on {{Topic: hardware|n:3c65c17b0d0d8118beeefaed56da6f8e}}'s Roofline lab): softmax does a few operations per byte, so its speed is the speed of memory, and the only way to make it faster is to move fewer bytes. The first of the three runs, taken while other jobs loaded the laptop, gave 43 GB/s; section 9 returns to that.

Overhead. Each launch costs CPU time before the GPU starts. NVIDIA measured a 2.9 µs kernel taking 9.6 µs per kernel when the CPU waited after each launch, and 3.4 µs per kernel with CUDA Graphs, which record a sequence of launches once and replay it with one CPU call ({{NVIDIA blog, 2019, V100|https://developer.nvidia.com/blog/cuda-graphs/}}) published. On the M1 Pro, one tiny MLX operation launched and waited for took about 235 µs (median of 3 runs: 674, 197, 235), which includes MLX's own bookkeeping and Metal's command buffers, so it is not comparable to a bare CUDA launch. The lesson transfers: when kernels are small, the GPU idles between them, and the fix is fewer, larger kernels or graphs. Horace He's {{"Making Deep Learning Go Brrrr"|https://horace.io/brrr_intro.html}} names the three regimes every slow operation falls into: compute-bound, memory-bound or overhead-bound.
