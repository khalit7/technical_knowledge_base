The idea in one sentence. A GPU runs one function, the kernel, on tens of thousands of threads in lockstep groups of 32, and almost every kernel is limited by the bytes it moves through a ladder of memories, so GPU programming is keeping every thread busy while moving fewer bytes per useful operation; each child page of this topic is one way to do that, or to check that you did.

New terms
Kernel: a function that runs on the GPU, executed by many threads at once.
Thread, warp, block, grid: one execution; 32 that issue together; up to 1,024 on one SM; all blocks of one launch.
SM: streaming multiprocessor, the GPU's core; an H100 SXM has 132.
Stream: a queue of GPU work; a launch returns at once.
Shared memory: on-chip scratchpad one block fills and reads.
Coalesced: a warp's 32 loads served by as few 32-byte sectors as possible.
Occupancy: resident warps per SM over the maximum.
Fusion: several operations in one kernel, intermediates kept on chip.
Tensor core: a unit that multiplies small matrix tiles in one instruction.
PTX, SASS: NVIDIA's virtual instruction set; one chip's real machine code.

1. One call, from PyTorch to the GPU

Suppose s is an 8,192 by 8,192 matrix of float32 scores on the GPU (256 MiB) and you write p = torch.softmax(s, dim=-1). Four things happen, and only the last one runs on the GPU. Dispatch: the dispatcher reads the tensor's device and picks the CUDA implementation from the registry, {{native_functions.yaml|https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/native_functions.yaml}} (softmax_cuda_out, against softmax_cpu_out and softmax_mps_out). Choose a kernel: PyTorch's {{SoftMax.cu|https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/cuda/SoftMax.cu}} picks by row length; rows of at most 2,048 elements (and 8 KB) get one warp per row, longer rows like ours one thread block per row (8,192 blocks) read from PyTorch main, 2026-10-05. Launch: the CPU queues "run this kernel with this many blocks of this many threads" on a stream and returns immediately, so a Python timer around a GPU call measures almost nothing. Execute: the GPU hands blocks to its SMs; the CPU waits only when it needs a value (p.item(), .cpu()), a synchronisation. Which code runs depends on the operator: torch.matmul calls cuBLAS or cuBLASLt, F.scaled_dot_product_attention picks among FlashAttention, memory-efficient, cuDNN and a "math" fallback, and under torch.compile none of them may run, because TorchInductor "translates PyTorch programs into OpenAI's Triton for GPUs" ({{PyTorch 2 paper, ASPLOS 2024|https://docs.pytorch.org/assets/pytorch2-2.pdf}}) and fuses the softmax with its neighbours.

Measured on the M1 Pro GPU measured on Apple M1 Pro GPU: MLX's softmax over the same matrix took 3.2 ms (median of 3 runs, as every M1 number on this page), 166 GB/s counting one read and one write, which equals the M1 Pro's measured copy bandwidth (about 165 GB/s on {{Topic: hardware|n:3c65c17b0d0d8118beeefaed56da6f8e}}'s Roofline lab). Softmax does a few operations per byte, so its speed is the speed of memory and the only way to make it faster is to move fewer bytes. The first of the three runs, taken while other jobs loaded the laptop, gave 43 GB/s (12.36, 3.23, 3.21 ms; load average 6.0): a median of 7 trials inside one disturbed run did not protect it, repeating runs did. The output matched a NumPy float32 reference to 3.7e-09.

Three regimes. Horace He's {{"Making Deep Learning Go Brrrr"|https://horace.io/brrr_intro.html}} names them: memory-bound (softmax, every elementwise and normalisation kernel), compute-bound (large matmuls, once tiling keeps the reuse on chip) and overhead-bound (kernels so small that the GPU idles between launches). On overhead: NVIDIA measured a 2.9 µs kernel at 9.6 µs per kernel when the CPU waited after each launch and 3.4 µs with a CUDA graph ({{NVIDIA blog, 2019, V100|https://developer.nvidia.com/blog/cuda-graphs/}}) published; the synchronisation, not the launch, costs most of the gap. {{Streams, CUDA graphs and multi-GPU programming|n:3f05c17b0d0d81b19a6acab65c370b75}}, section 3, takes the numbers apart. On the M1 Pro, one tiny MLX operation launched and waited for took about 235 µs (runs 674, 197, 235), MLX's bookkeeping included, so not comparable to a bare CUDA launch; the lesson transfers: when kernels are small, use fewer, larger kernels or graphs.
