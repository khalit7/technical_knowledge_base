The Apple M1 Pro GPU is a real SIMT GPU of the same family of ideas: it runs threads in SIMD-groups of 32 (read from the GPU itself with threads_per_simdgroup), groups them into threadgroups that share a fast on-chip threadgroup memory, and streams from DRAM. So the same effects show up, but its sizes and rules are Apple's, mostly undocumented. Each measured card says what transfers to an NVIDIA GPU and what does not.
Words used below (open if any is new; the {{Reading tab|#t-read}} builds them up slowly)
thread
one copy of your kernel function running with its own threadIdx and its own registers.
warp
32 threads that the hardware runs together: one instruction is fetched and issued for all 32 at once. Each thread is a lane of the warp (lane 0 to 31). Apple calls it a SIMD-group.
block
a group of up to 1,024 threads (a "thread block" or CTA) that run on the same SM and can share shared memory and wait for each other at __syncthreads(). Apple: threadgroup.
SM
streaming multiprocessor, the GPU's core: an H100 SXM has 132. Each SM holds a register file, shared memory and up to 64 resident warps, split over 4 schedulers.
global memory
the GPU's DRAM (HBM on datacentre GPUs, GDDR on consumer ones): big and far, hundreds of cycles away.
shared memory
a small on-chip scratchpad per SM (up to 228 KB on H100), about 30 cycles away, that the programmer fills and reads explicitly.
register
the fastest storage, private to a thread; an SM has 65,536 32-bit registers to share among all its threads.

1. A warp runs one instruction at a time: divergence

The problem. You write a kernel as if each thread were on its own, with ordinary if statements. But the hardware fetches and issues one instruction for a whole warp of 32 threads. When the threads of one warp disagree about a branch, the warp cannot go both ways at once: in NVIDIA's words, "the warp executes each branch path taken, disabling threads that are not on that path" (CUDA Programming Guide 3.2.2.1, SIMT execution model). The disabled lanes sit idle. Different warps never slow each other this way: "branch divergence occurs only within a warp".

What transfers, what does not

  • Transfers: both GPUs run 32 lanes from one instruction stream and serialise the two sides of a branch that splits a group of 32. The measured slowdown matches the simulator's prediction for this code shape.
  • NVIDIA detail since Volta (compute capability 7.0): each thread has its own program counter ("independent thread scheduling"), so divergent paths can interleave and threads of a warp can wait on each other without deadlock. A warp still issues one path at a time, so the cost above is unchanged; what changed is that code may no longer assume the 32 lanes move in lockstep, and must use __syncwarp() or the *_sync warp intrinsics (Programming Guide 3.2.2.1.1).
  • Short branches are often compiled into predicated instructions (both sides run, each lane keeps its own result), which avoids a jump but still pays for both sides. Look for it in the {{Compiler explorer|#t-compile}}'s SASS.

When it matters for training, and how to check

Dense matmuls and elementwise kernels have no data-dependent branches, so divergence rarely matters there. It does in masked attention, variable-length (packed) sequences, mixture-of-experts routing and sampling. The fix is to make the decision per warp or per block instead of per thread. FlashAttention-2 does exactly this for the causal mask: it skips whole blocks that are fully masked, "approximately half of the blocks for large sequence length", for a 1.7 to 1.8x speedup, and applies the per-element mask only on the diagonal blocks (Dao, 2023, section 3.1.1).

Check in Nsight Compute: the Source Counters section reports branch efficiency per line; derived__avg_thread_executed (thread instructions per warp instruction) is 32 when no lane is ever idle (Nsight Compute Profiling Guide, last updated 2026-08-27).
