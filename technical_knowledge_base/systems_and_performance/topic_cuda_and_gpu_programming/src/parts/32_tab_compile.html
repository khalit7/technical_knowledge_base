Compiler explorer: what the GPU actually runs

When you call torch.matmul or launch a kernel you wrote, the GPU does not execute your C++ or Python. It executes SASS, the machine code of one specific GPU generation. This tab follows real kernels through the real NVIDIA compiler, from source to PTX (a portable assembly language) to SASS, for four generations: sm_80 (A100, Ampere), sm_90a (H100 and H200, Hopper), sm_100a (B200 and GB200, datacenter Blackwell) and sm_120 (RTX 5090, consumer Blackwell). You learn to read what the compiler tells you: how many registers each thread needs, how much shared memory a block uses, whether anything spilled, which instructions do the arithmetic, and how many threads can therefore run at once.

realWhat is real on this tab, and what is not

Every PTX listing, SASS listing, register count, spill count and error message below was produced by NVIDIA's own compiler (nvcc, in the Linux arm64 build of the CUDA toolkit, run in a Docker container on a laptop) and, for the Triton kernels, by Triton's own compiler (Triton) asked for each GPU target explicitly. No NVIDIA GPU was used: compiling needs no GPU, running does. So nothing here is a timing; real timings of the same kernels are in the {{Kernel lab|#t-lab}} (on the Apple M1 Pro's GPU). Occupancy figures are derived: computed from the compiler's resource numbers and NVIDIA's documented per-SM limits, and checked against NVIDIA's own occupancy calculator code. Scripts and every raw output are in the page's src/compile/ folder (run_all.sh reproduces them).

Five words used everywhere below

  • Kernel: a function that runs on the GPU, launched once and executed by thousands of threads at the same time, each working on its own piece of data.
  • SM (streaming multiprocessor): one of the GPU's cores in the CPU sense (an H100 SXM has 132, per NVIDIA's Hopper architecture post). Each SM holds the registers and shared memory of the threads it is running.
  • Warp: 32 threads that execute the same instruction together. One SASS instruction is issued once per warp. A block (CUDA's "thread block", Triton's "program") is a group of warps that share one SM's shared memory.
  • Register: the fastest storage, private to one thread. Shared memory: a small fast scratchpad on the SM, shared by one block. Global memory: the GPU's main memory (HBM or GDDR), large and slow by comparison.
  • Compute capability ("sm_90" means 9.0): NVIDIA's version number for a GPU generation's instruction set and limits. Code is compiled for one or more of them.

3. Before and after: naive vs tiled matmul, in the instructions


The naive matmul reads both operands of every multiply-add from global memory. The tiled version first copies a 32 by 32 tile of A and of B into shared memory, then does 32 multiply-adds per element from there. In C++ the two inner loops look almost the same. In SASS the difference is plain: count the loads that go to global memory (LDG) against the loads from shared memory (LDS) for every fused multiply-add (FFMA). The animation steps through the real inner loop the compiler produced, one instruction at a time, with running counters.




















Predict first. In the tiled kernel, how many bytes come from global memory per multiply-add, compared with the naive kernel's 8 bytes (two 4-byte floats)?



 Each thread loads one element of A and one of B per tile (8 bytes) and then does 32 multiply-adds with values from shared memory, so global traffic per multiply-add falls from 8 bytes to 8/32 = 0.25 bytes. (Caches soften the naive kernel's real traffic: neighbouring threads read the same row of A, which the L1 cache can serve. The instruction count does not lie, though: the naive loop still issues two global loads per FFMA.)



4. Before and after: one multiply-add per thread vs one tensor-core instruction


An FFMA does one multiply-add per thread, so 32 per warp instruction. A tensor core is a unit on the SM that multiplies small matrices in one instruction. Each generation made that instruction bigger and moved more of the work off the threads: the warp-level mma.sync (SASS HMMA, the form every generation since Volta has) is issued by one warp with operands in registers; Hopper's wgmma (SASS HGMMA) is issued by a warpgroup of four warps and reads its operands straight from shared memory; datacenter Blackwell's tcgen05.mma (SASS UTCHMMA and relatives) is issued by a single thread, reads shared memory and accumulates into Tensor Memory (TMEM), a separate on-chip store of 256 KB per block (512 columns x 128 lanes x 4 bytes, PTX ISA), so the accumulator no longer occupies registers at all. The chart counts multiply-adds per issued instruction, from the instruction shapes in this tab's kernels; the table under it shows which target accepted which instruction, from the real compiles.

















5. Before and after: register pressure and spills


Keeping more partial results per thread in registers means each value loaded from memory is reused more (that is how fast matmuls work: each thread owns a small tile of the output). The price is registers. A thread can use at most 255, and every register a thread uses is taken from the SM's fixed pool of 65,536, so fewer threads fit. Past the limit, the compiler spills: it parks values in local memory, which despite the name is per-thread space in global memory (behind the L1 and L2 caches), and reloads them later with STL and LDL instructions. Slide N, the number of running sums each thread keeps.

6. What compiled where: one source, four generations


PTX is portable forward: PTX written for compute_80 can be compiled for any later GPU. Machine code is not: a cubin (compiled GPU binary) runs only on GPUs of the same major version with an equal or higher minor version, so sm_80 SASS runs on an RTX 3090 (8.6) but not on an H100 (9.0) (CUDA Programming Guide 1.3.4). Since Hopper there is a third kind of target: the "a" suffix (sm_90a, sm_100a, sm_120a) unlocks architecture-specific instructions that only the exact chip runs, which is where the newest tensor-core instructions live (Programming Guide 5.1.2). 7. From the resource report to occupancy


Occupancy is how many warps an SM holds at once, as a fraction of its maximum. Warps waiting for memory are parked while others compute, so more resident warps hide more latency, up to a point. Four limits apply at once, and the smallest wins: registers (65,536 per SM, allocated per warp in chunks of 256), shared memory (per block, plus 1 KB that CUDA reserves per block, per the Ampere tuning guide), the maximum warps per SM and the maximum blocks per SM. All four come from the compiler's report and the documented per-SM limits. Change the block size and watch which limit binds.

9. Do it yourself: the commands


Everything on this tab came from a handful of commands. All of them work without a GPU.


# resource report: registers, shared memory, spills, per kernel
nvcc -arch=sm_90a -cubin -Xptxas -v -lineinfo kernel.cu
# keep every intermediate file (.ptx, .cubin, ...) next to the source
nvcc -arch=sm_90a --keep -c kernel.cu
# PTX only (the virtual ISA), with .loc source-line directives
nvcc -arch=compute_90a -ptx -lineinfo kernel.cu
# SASS, and SASS interleaved with source file and line
cuobjdump -sass kernel.cubin
nvdisasm -g -c kernel.cubin
# resource usage of every kernel already inside a binary or library
cuobjdump -res-usage my_binary
# list which SASS targets and PTX versions a binary carries
cuobjdump -lelf -lptx my_binary

# Triton: every stage of a compiled kernel (handle returned by the launch)
k = my_kernel[grid](x, y, n, BLOCK=1024)
print(k.asm["ttgir"]); print(k.asm["ptx"]); print(k.n_regs, k.n_spills)
# Triton without a GPU: run on the CPU for correctness
TRITON_INTERPRET=1 python my_kernel_test.py

# torch.compile: print the Triton kernels Inductor generated
TORCH_LOGS="output_code" python train.py


On the web, Compiler Explorer (godbolt.org) compiles CUDA C++ and shows PTX and SASS in the browser. NVRTC is the library form of the CUDA C++ compiler: a program can compile a kernel from a string at run time and get PTX or a cubin back (NVRTC User Guide).



10. Interview questions, with short answers


What is the difference between PTX and SASS?
PTX is NVIDIA's virtual instruction set: a portable assembly with unlimited virtual registers, stable across GPU generations. SASS is the real machine code of one generation, produced from PTX by ptxas (ahead of time) or by the driver (just in time). SASS is what runs, and what Nsight Compute shows you; register allocation, instruction scheduling and spilling happen only at the PTX to SASS step.
Your extension was built with -arch=sm_80. Does it run on an H100?
Yes, but not from the sm_80 machine code: cubins are compatible only within a major version. nvcc's shorthand -arch=sm_80 also embeds compute_80 PTX, and the driver compiles that PTX for 9.0 the first time it loads (slower start, then cached). It cannot use Hopper-only features such as wgmma or TMA. Built with -gencode arch=compute_80,code=sm_80 (no PTX), it fails with "no kernel image is available for execution on the device".
What does the "a" in sm_90a mean, and why does such a kernel not run on a B200?
"a" selects the architecture-specific feature set: instructions such as wgmma that exist only on that exact compute capability and are not promised to later chips. Code compiled for an "a" target runs only on that compute capability, so sm_90a code needs a 9.0 GPU. Blackwell has its own (tcgen05); a Hopper kernel must be rewritten or recompiled from a portable source, which is one reason libraries such as CUTLASS and Triton keep per-architecture code paths.
ptxas reports 128 registers per thread for a kernel launched with 256-thread blocks on an H100, no shared memory. What is its occupancy?
Each warp needs 128 x 32 = 4,096 registers; the SM has 65,536, so 16 warps fit. A block is 8 warps, so 2 blocks, 16 of the 64 warp slots: 25%. Whether 25% is too low depends on the kernel: a matmul with lots of independent work per thread can run at full speed at low occupancy; a memory-bound elementwise kernel usually cannot.
What is a register spill, how do you see one, and why does it hurt?
When a thread needs more live values than its register budget, ptxas stores some to local memory (per-thread space in global memory, cached in L1 and L2) and reloads them later. -Xptxas -v prints "bytes spill stores / spill loads"; in SASS they are STL and LDL. A few bytes that hit L1 are cheap; spills inside a hot loop add memory traffic and latency where you wanted pure arithmetic.
Why does an RTX 5090 not run a Hopper FlashAttention-3 kernel even though it is newer?
FA3 is written around Hopper's wgmma and TMA, and wgmma exists only on sm_90a. The RTX 5090 is compute capability 12.0: it has no wgmma and no tcgen05 (this tab's compiles show both rejected for sm_120), so its tensor cores are reached through warp-level mma.sync instructions. A kernel written for it uses a different instruction mix, which is why kernel libraries ship separate sm_120 code.
You see HMMA in a profiler's SASS view for a matmul on an H100. Is something wrong?
Probably, for a large matmul: HMMA is the warp-level mma.sync instruction that every generation since Volta has. On an H100 the fastest GEMMs use HGMMA (wgmma). Seeing HMMA means the kernel was compiled for a portable target (sm_80 or sm_90 without "a"), or written with WMMA or mma.sync. It still uses the tensor cores, at a lower peak in practice; the exact gap is a measurement this tab cannot make (no GPU).
