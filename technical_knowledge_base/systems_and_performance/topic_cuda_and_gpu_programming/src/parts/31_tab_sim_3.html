3. Warps in flight hide memory latency

The problem. A load from DRAM takes hundreds of cycles to come back. Microbenchmarks measured average global-memory latencies of 466 cycles on an A100, 479 on an H800 (a Hopper H100 variant) and 542 on an RTX 4090, against about 29 to 30 cycles for shared memory and 262 to 273 for the L2 cache (Luo et al., 2024, Table IV; independent measurements, not NVIDIA figures). A GPU does not hide this with big caches or out-of-order execution like a CPU. It hides it with other warps: each SM sub-partition has a warp scheduler that, every cycle, picks one warp whose next instruction is ready and issues it. Nsight Compute's words: active warps that are not stalled are eligible; the scheduler issues from one of them; "on cycles with no eligible warp, the issue slot is skipped" (Profiling Guide, Scheduler Statistics).

The model. One scheduler, W warps, each running the same loop: issue k independent loads, wait L cycles for them, then k x c instructions that use the data. The scheduler issues one instruction per cycle and keeps issuing from the same warp until it stalls, then switches to the warp that has been ready longest ("greedy then oldest"). Little's law gives the answer the simulation lands on: the scheduler is kept busy when W x k(c + 1) ≥ k(c + 1) + L, so utilisation = min(1, W·k(c+1) / (k(c+1) + L)).

Predict first. A kernel issues one DRAM load (L = 479 cycles on an H800) for every 8 other instructions. How many warps must one scheduler hold to never idle? An H100 SM holds at most 64 warps over 4 schedulers.
(9 + 479) / 9, about 55 warps per scheduler, but a scheduler can hold at most 64 / 4 = 16. Even at full occupancy it idles about 70% of the time (16 x 9 / 488 = 30% busy). Occupancy alone cannot hide DRAM latency for code like this; each warp must keep several loads in flight at once (set k to 4: 16 warps are then enough), which is what unrolled loops, vector loads and asynchronous copies (cp.async, TMA) with double buffering do.

What transfers, what does not

  • Transfers: Little's law holds for any memory system: bandwidth = bytes in flight / latency. To stream at full speed a GPU needs enough loads outstanding, from many warps or from several loads per warp.
  • Does not transfer: the numbers. An H100 needs far more bytes in flight than the M1: assuming a clock near 1.8 GHz, 479 cycles is about 270 ns, and 3.35 TB/s x 270 ns is about 0.9 MB across the chip (derived), against about 50 KB for the M1 (derived from the measurement above). That is one reason Hopper added TMA: one thread can launch a large asynchronous copy.
  • Left out of the model: arithmetic latency (a dependent instruction also waits a few cycles), dual issue, memory bandwidth limits and bank or sector effects. It isolates the one idea.

When it matters for training, and how to check

It explains why small kernels are slow: a softmax over a few rows, a decode step at batch 1, or a launch with fewer blocks than the GPU has SMs leaves schedulers idle. It is the reason behind "fuse small kernels", CUDA graphs, and split-K or persistent kernels that keep every SM busy. The {{Kernel lab|#t-lab}} shows it on real attention kernels; the softmax ladder is in {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}, section 4.

Check in Nsight Compute: Scheduler Statistics (eligible warps per cycle, and the share of cycles with no eligible warp) and Warp State Statistics, where a large "stall long scoreboard" means warps are waiting on L1TEX (global or local memory) operations (Profiling Guide).

Interview questions

A warp hits if (threadIdx.x < 16) with two branches of equal length. What does it cost?
Both branches run one after the other with half the lanes masked each time, so the branch section takes twice the issue slots at 50% lane utilisation. Branching on threadIdx.x / 32 instead costs nothing extra, because divergence only happens inside a warp.
A kernel uses 168 registers per thread on an H100. What is its occupancy with 128-thread blocks?
168 x 32 = 5,376 registers per warp (already a multiple of 256); each of the 4 sub-partitions has 16,384, so 3 warps fit per sub-partition, 12 per SM, 3 blocks: 12 / 64 = 18.75%. Capping at 128 registers gives 16 warps, 25%, at the price of spills.
Is higher occupancy always better?
No. Occupancy only matters as a way to hide latency. A kernel can hide latency with independent work inside each thread (several loads in flight, register tiles) at low occupancy, and many of the fastest GEMM and attention kernels do. Raising occupancy by capping registers can cause spills that cost more than they save.
How many bytes must be in flight to saturate an H100's HBM?
Little's law: bandwidth x latency. With about 480 cycles of DRAM latency and a clock near 1.8 GHz (an assumption), about 270 ns: 3.35 TB/s x 270 ns is about 0.9 MB in flight across 132 SMs, about 7 KB per SM. That is why streaming kernels use vector loads, unrolling and asynchronous copies.
