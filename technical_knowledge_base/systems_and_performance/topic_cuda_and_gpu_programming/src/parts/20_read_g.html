8. The compiler: CUDA C++ to PTX to SASS

Two instruction sets. PTX is NVIDIA's virtual instruction set: a readable, stable text format that does not belong to any one chip. SASS is the real machine code of one architecture, and it changes every generation. nvcc compiles the GPU part of a .cu file to PTX, then the assembler ptxas turns PTX into SASS for each target you name (-arch=sm_90a), and both are packed into a fat binary inside your executable or library. If a binary carries PTX but no SASS for the GPU it lands on, the driver compiles the PTX just in time, which is how old binaries run on new GPUs. NVRTC does the C++-to-PTX step at run time from a string, for code generated on the fly.

Here is the vector-add kernel of section 2 at both levels, sm_90a compiled here, CUDA 13.4.2:

PTX (the body)
mov.u32      %r3, %ctaid.x;    // blockIdx.x
mov.u32      %r4, %ntid.x;     // blockDim.x
mov.u32      %r5, %tid.x;      // threadIdx.x
mad.lo.s32   %r1, %r3, %r4, %r5;
setp.ge.s32  %p1, %r1, %r2;    // i >= n ?
@%p1 bra     $L__BB0_2;
...
ld.global.f32  %f1, [%rd8];
ld.global.f32  %f2, [%rd6];
add.f32        %f3, %f2, %f1;
st.global.f32  [%rd10], %f3;
SASS (what the H100 executes)
S2R    R0, SR_TID.X ;
S2UR   UR4, SR_CTAID.X ;
LDC    R9, c[0x0][RZ] ;
IMAD   R9, R9, UR4, R0 ;
ISETP.GE.AND P0, PT, R9, UR4, PT ;
@P0 EXIT ;                     // bounds check
...
LDG.E  R3, desc[UR4][R2.64] ;  // global load
LDG.E  R4, desc[UR4][R4.64] ;
FADD   R9, R4, R3 ;
STG.E  desc[UR4][R6.64], R9 ;  // global store
EXIT ;

Reading SASS is a practical skill, not a party trick: it is where you confirm that a load is vectorised (LDG.E.128), that shared memory is used (LDS, STS), that tensor cores are used (HMMA, HGMMA, UTCHMMA), and that nothing spills (STL, LDL). The compiler's resource report, nvcc -Xptxas -v, gives registers, shared memory and spill bytes per kernel; those numbers set occupancy (section 2).

Targets. Each GPU generation has a compute capability: 8.0 for A100, 9.0 for H100, 10.0 for B200, 12.0 for the RTX 5090. Build for the one you run on (-arch=sm_120, or -arch=native); sm_100 and sm_120 need CUDA 12.8 or newer ({{CUDA 12.8 release notes|https://docs.nvidia.com/cuda/archive/12.8.0/cuda-toolkit-release-notes/index.html}}: "adds compiler support for ... SM_100, SM_101, SM_120"). The current toolkit is CUDA 13.4.2 checked 2026-10-05; the old page's "13.3 latest, 13.4 in preview" is out of date.

torch.compile, all the way down

torch.compile(model) runs a different chain: TorchDynamo captures the Python as a graph; AOTAutograd derives the backward graph; TorchInductor fuses and schedules, and writes Triton source for each fused group (matmuls go to cuBLAS by default; Triton matmul templates compete with it only under mode="max-autotune"); Triton lowers its source through its own intermediate forms to LLVM and PTX; ptxas produces SASS. Everything is cached: the first call compiles, and after one change of input shape Dynamo recompiles with a symbolic size, so later shapes reuse that graph instead of compiling again. The PyTorch 2 paper reports 2.27 times inference and 1.41 times training speedup (geometric mean) on an A100 over 180+ models ({{Ansel et al., ASPLOS 2024|https://docs.pytorch.org/assets/pytorch2-2.pdf}}) published. To see what it generated: TORCH_LOGS=output_code.
