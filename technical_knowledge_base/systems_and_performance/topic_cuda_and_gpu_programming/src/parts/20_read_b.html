2. The programming model: grid, blocks, warps, threads

The problem. A GPU has tens of thousands of arithmetic lanes and wants hundreds of thousands of independent pieces of work in flight. You cannot write a hundred thousand programs, so you write one function, the kernel, and launch it on many threads; each thread works out from its own index which piece of data is its job. That is the whole idea, and CUDA's four nested words describe how the threads are grouped.

ThreadOne execution of the kernel, with its own private registers (the fastest storage there is). You launch millions.
Warp32 consecutive threads that the hardware runs together, one instruction at a time for all 32. Not part of the language, but the unit everything performs in.
BlockUp to 1,024 threads that run on one SM and stay there. They share a small fast scratchpad, shared memory, and can wait for each other with __syncthreads(). Blocks must not depend on each other: the GPU runs them in any order on any SM, which is why the same program runs on a GPU with 20 SMs or 170.
GridAll the blocks of one launch. There is no cheap way for blocks to wait for each other inside a kernel; the end of the kernel is the global barrier. Since Hopper (compute capability 9.0) an optional cluster sits between block and grid: a few blocks on neighbouring SMs that can read each other's shared memory.

Limits from the {{CUDA C++ Programming Guide, compute capabilities|https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html}} (v13.4.2) vendor spec: warp size 32; at most 1,024 threads per block; per SM at most 64 resident warps on sm_80, sm_90 and sm_100 and 48 on consumer sm_86, sm_89 and sm_120; 65,536 32-bit registers per SM, at most 255 per thread.

A first kernel

Vector addition: thread i adds element i. This is the exact source the {{Compiler explorer|#t-compile}} compiles for four GPU generations; ptxas reports it uses 12 registers per thread on sm_90a compiled here.

extern "C" __global__ void vadd(const float* a, const float* b, float* c, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;  // this thread's global index
  if (i < n)                                       // the last block may run past n
    c[i] = a[i] + b[i];                            // two loads, one add, one store
}
// host side: enough blocks of 256 threads to cover n (ceiling division)
int block = 256, grid = (n + block - 1) / block;
vadd<<<grid, block>>>(d_a, d_b, d_c, n);   // asynchronous: returns at once

__global__ marks a kernel (runs on the GPU, launched from the CPU); blockIdx, blockDim and threadIdx are built-in variables each thread reads to learn who it is. Move the sliders to see how a launch carves up the work.

SIMT: one instruction, 32 threads, and what a branch costs

NVIDIA calls the model SIMT, single instruction, multiple threads. You write scalar code for one thread; the hardware issues each instruction once for a whole warp and the 32 lanes execute it on their own data. It is SIMD (the CPU's vector instructions, Part 2 of the {{C++ page|n:3cd5c17b0d0d81ceadcee44fe9c023a0}}) without having to write the vectors. The catch is the branch. If the 32 threads of a warp disagree on an if, the warp runs both paths one after the other, with the lanes that did not take the current path switched off (masked). This is warp divergence. Since Volta (sm_70) each thread has its own program counter ("independent thread scheduling", {{Programming Guide|https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html#independent-thread-scheduling}}), which makes divergent code correct in more cases, but the two paths still take turns.

float v = x[i];
if (v > 0.f) { v = expf(v); v = v * w; v = v + b; v = sqrtf(v); }   // path A: 4 steps
else         { v = 0.01f * v; v = v * w; v = v - b; v = fabsf(v); } // path B: 4 steps
y[i] = v;

Each row is one instruction issued for the warp; each square is a lane, coloured when the lane does useful work and grey when masked. illustrative instruction count: one row per source line

Predict: on the M1 Pro GPU, a kernel with two equally heavy branches is run once with every 32-thread group agreeing, once with alternate lanes taking alternate branches. How much slower is the divergent run?
measured on Apple M1 Pro GPU 1.86 times (2.82 ms against 1.52 ms, median of 3 runs, in the {{GPU simulator|#t-sim}}). Both paths are executed, so the cost is the sum of the two paths instead of one; with two equal paths, close to 2. It is not 32: the lanes are masked, not serialised one by one. Apple's SIMD-groups are 32 wide like NVIDIA's warps, so this transfers directly; the cost on NVIDIA is the same in kind.

When it matters for training: rarely in matmuls and normalisations, whose threads all do the same thing; often in code with data-dependent branches (masking, sparse or ragged inputs, MoE routing, sampling). A branch that is the same for a whole warp (if (blockIdx.x == 0), or a bounds check that only fails in the last warp) costs nothing. How to check: Nsight Compute reports average active threads per instruction (32 means no divergence; section 9).

Latency hiding: why a GPU wants so many threads

A read from GPU memory takes hundreds of clock cycles. A CPU core hides that with large caches and by guessing ahead; a GPU hides it by switching warps. Every resident warp keeps its registers on the SM permanently, so when one warp waits for memory the scheduler issues an instruction from another, at no cost. The more warps are ready, the more of the waiting is covered. measured on Apple M1 Pro GPU in the {{GPU simulator|#t-sim}}: streaming the same array with 256 threads in flight reached 11 GB/s; with 8,192 or more, 138 to 151 GB/s, the memory's limit. "Not enough parallelism" is a first-order failure: a kernel launched with fewer blocks than the GPU has SMs leaves most of the chip idle.

Occupancy is the number of warps resident on an SM divided by the maximum (64 on an H100). It is limited by whichever resource runs out first: registers per thread, shared memory per block, threads per block, or the cap on blocks per SM. It is a means, not a goal: memory-bound kernels want it high, while fast matmul and attention kernels deliberately run at low occupancy because more registers per thread buy more data reuse than more warps buy latency hiding. The {{Compiler explorer|#t-compile}} turns real ptxas register reports into occupancy with a calculator that agrees with NVIDIA's own cuda_occupancy.h on all 1,988 tested cases.

Streams, briefly: work in one stream runs in order; work in different streams may overlap (a copy with a kernel, or NCCL's communication with backward compute, which is how data-parallel training hides its all-reduce). Events order streams against each other and time the GPU from the GPU's side.
