3. Threads, warps, blocks: the model every child assumes

The problem. A GPU has tens of thousands of arithmetic lanes and wants hundreds of thousands of independent pieces of work in flight. So you write one function, the kernel, and launch it on many threads; each thread works out from its own index which piece of data is its job. Four nested words describe how the threads are grouped:

ThreadOne execution of the kernel, with its own private registers (the fastest storage there is). You launch millions.
Warp32 consecutive threads that the hardware runs together, one instruction at a time for all 32. Not part of the language, but the unit everything performs in.
BlockUp to 1,024 threads that run on one SM and stay there. They share shared memory and can wait for each other with __syncthreads(). Blocks must not depend on each other: the GPU runs them in any order on any SM, which is why the same program runs on a GPU with 20 SMs or 170.
GridAll the blocks of one launch; the end of the kernel is the only cheap global barrier. Since Hopper (compute capability 9.0) an optional cluster sits between block and grid: a few blocks on neighbouring SMs that can read each other's shared memory.

SIMT (single instruction, multiple threads): you write scalar code for one thread, the hardware issues each instruction once for a whole warp. It is SIMD without writing the vectors, and its catch is the branch: if the 32 threads of a warp disagree on an if, the warp runs both paths one after the other with the other lanes masked (warp divergence). On the M1 Pro, two equally heavy branches split inside every warp ran 1.86 times slower (2.82 against 1.52 ms) measured on Apple M1 Pro GPU: the sum of the two paths, not 32 times, because lanes are masked, not serialised one by one. A branch that is the same for a whole warp costs nothing.

Latency hiding. A read from GPU memory takes hundreds of cycles. A GPU hides it by switching warps: every resident warp keeps its registers on the SM, so when one waits the scheduler issues from another at no cost. Occupancy, resident warps over the maximum (64 per SM on an H100), is limited by whichever runs out first: registers per thread, shared memory per block, threads per block or the cap on blocks. A kernel launched with fewer blocks than the GPU has SMs leaves most of the chip idle. The {{GPU simulator|#t-sim}} steps all three (divergence; occupancy, whose calculator agrees with NVIDIA's own cuda_occupancy.h on all 1,988 tested cases; and latency hiding) with the M1 Pro measurements beside each.
