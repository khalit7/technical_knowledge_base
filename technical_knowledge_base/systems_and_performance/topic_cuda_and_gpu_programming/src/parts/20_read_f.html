6. Triton: blocks, not threads

The idea. In CUDA you write what one thread does and arrange the cooperation yourself: which thread loads what, when to synchronise, how to lay out shared memory. In Triton (OpenAI's Python language for kernels, {{Tillet, Kung and Cox, MAPL 2019|https://www.eecs.harvard.edu/~htk/publication/2019-mapl-tillet-kung-cox.pdf}}) you write what one program instance does to whole blocks of values, roughly what one CUDA thread block does, and the compiler decides how threads, warps, shared memory, vector loads and synchronisation implement it. Here is the same row softmax both ways, as compiled in the {{Compiler explorer|#t-compile}}:

CUDA C++: 29 lines without comments; three passes, warp shuffles and a shared-memory step written by hand (core loop shown)
for (int j = threadIdx.x; j < ncols; j += 256)
  m = fmaxf(m, xr[j]);                      // pass 1: max
m = warp_max(m); if (lane == 0) red[warp] = m;
__syncthreads();
m = (lane < 8) ? red[lane] : -INFINITY;
m = warp_max(m); __syncthreads();
for (int j = threadIdx.x; j < ncols; j += 256)
  s += __expf(xr[j] - m);                   // pass 2: sum
// ... same two-level reduction for s ...
for (int j = threadIdx.x; j < ncols; j += 256)
  yr[j] = __expf(xr[j] - m) * inv;          // pass 3
Triton: 9 lines; the whole row is one block of values
@triton.jit
def softmax(x_ptr, y_ptr, ncols, stride, BLOCK: tl.constexpr):
    row = tl.program_id(0)          # one program per row
    offs = tl.arange(0, BLOCK)
    mask = offs < ncols
    x = tl.load(x_ptr + row * stride + offs,
                mask=mask, other=-float("inf"))
    x = x - tl.max(x, axis=0)       # reduction: compiler's job
    e = tl.exp(x)
    tl.store(y_ptr + row * stride + offs,
             e / tl.sum(e, axis=0), mask=mask)

The translations to remember: tl.program_id replaces blockIdx; tl.arange plus pointer arithmetic plus mask= replace per-thread indexing and bounds checks; tl.load and tl.store move whole blocks (contiguous offsets make them coalesced for free; whether each thread also gets 16-byte vector loads depends on what the compiler can prove: with aligned pointers but a length n that is not a multiple of 16, the same vector add compiles to scalar loads, 16 LDG.E per thread instead of 4 LDG.E.128 compiled here, shown stage by stage in the Compiler stages tab of {{Triton and Gluon|n:3c65c17b0d0d81729d15ed4d1a4461b3}}); tl.max and tl.sum emit the shuffles you wrote by hand; tl.dot is a block matrix multiply that the compiler maps to tensor cores; @triton.autotune searches block sizes, num_warps and num_stages (how many tiles to prefetch) per shape. compiled here: one Triton matmul source compiled without a GPU picks a different tensor-core instruction for each target, HMMA on sm_80 and sm_120, HGMMA (wgmma) on sm_90a and UTCHMMA (tcgen05) on sm_100a; a float32 tl.dot defaults to TF32 tensor cores; a tutorial-style matmul copies tiles with cp.async, not TMA.

What you give up: warp-level control, explicit shared-memory layouts, hand-scheduled asynchronous copies and power-of-two block shapes only. When to use which: torch.compile first (it already writes Triton for you); hand-written Triton for an algorithm the compiler cannot express or schedule well (attention variants, quantised or mixed-format matmuls, fused MoE routing); CUDA C++ or CUTLASS for the last stretch of performance or features Triton does not expose. The often-quoted "within 0 to 20% of expert CUDA in a tenth of the code" is a rule of thumb from the old page unconfirmed as a general figure; the line counts above are one data point.

Gluon, in the Triton repository since 2025, is the escape hatch: "a GPU programming language based on the same compiler stack as Triton. But unlike Triton, Gluon is a lower-level language that gives the user more control and responsibility" ({{Gluon tutorial 01|https://github.com/triton-lang/triton/blob/main/python/tutorials/gluon/01-intro.py}}). Its tutorials cover exactly what Triton hides: layouts, async copies, TMA, wgmma, tcgen05 and tensor memory, warp specialisation and multi-CTA clusters.

Version: Triton 3.8.0 (GitHub release, August 28, 2026; installs from PyPI) checked 2026-10-05. The old page's "3.7 is current" is out of date.

Go deeper: {{Triton and Gluon|n:3c65c17b0d0d81729d15ed4d1a4461b3}} goes from vector add to FlashAttention, then num_warps, num_stages, autotuning, the compiler stage by stage, layouts and Gluon; the {{Kernel lab|#t-lab}} runs Triton kernels for real on the CPU with TRITON_INTERPRET=1 and checks them against PyTorch; the {{Compiler explorer|#t-compile}}, section 8, shows the PTX and SASS Triton generates per target.

Tensor cores, from the programmer's side

A tensor core is a unit that multiplies small matrix tiles in one instruction (what it is physically is on {{Topic: hardware|n:3c65c17b0d0d8118beeefaed56da6f8e}}). You reach it, from most to least abstract, through cuBLAS or cuDNN, Triton's tl.dot, CUTLASS/CuTe, or PTX instructions directly. The instruction changed shape every generation, and that is what makes kernel code generation-specific:

GenerationMatrix instruction (PTX, then SASS)Who issues it, where operands liveData movement that feeds it
Ampere sm_80; also consumer sm_86, sm_89, sm_120mma.sync → HMMA (FP8 tensor cores arrived with Ada, sm_89: an FP8 mma.sync needs sm_89 or later, and is a native QMMA on sm_120)One warp; operands and accumulators in registerscp.async: global to shared without passing through registers

Shapes and TMEM size: {{PTX ISA 9.4|https://docs.nvidia.com/cuda/parallel-thread-execution/index.html}} vendor spec. Which instruction assembles where: compiled here with CUDA 13.4.2.

Real compiles, no GPU compiled here: wgmma assembles only for sm_90a (ptxas: "Instruction 'wgmma.fence' not supported on .target 'sm_100a'"); tcgen05 only for sm_100a; TMA and clusters compile for sm_90a, sm_100a and sm_120. So the old page's claim stands: an RTX 5090 (sm_120) has TMA and clusters but no wgmma, tcgen05 or TMEM, and Hopper tutorials do not run on it as written. A surprise: an FP8 mma.sync is a native QMMA on sm_120 but is emulated on sm_90a and sm_100a (converted to FP16 and run as two HMMA), because those chips expect FP8 through wgmma and tcgen05. The a suffix (sm_90a, sm_100a) marks architecture-specific features that do not carry forward to the next generation.

Why it matters for reading kernels: a modern Hopper or Blackwell kernel is warp-specialised: some warps only issue TMA copies (producers), others only issue matrix instructions (consumers), linked by barriers in shared memory, with several tiles in flight. FlashAttention-3 and modern CUTLASS mainloops look like this. Once you can name TMA, wgmma/tcgen05, the barrier and the pipeline depth, such a kernel becomes readable.
