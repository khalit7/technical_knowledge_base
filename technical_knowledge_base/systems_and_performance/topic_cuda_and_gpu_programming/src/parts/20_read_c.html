3. The memory hierarchy, as the programmer sees it

The problem. An H100 SXM can do 989.5 trillion BF16 floating-point operations per second on its tensor cores (dense) but fetch only 3.35 TB per second from its memory vendor spec, so it can do about 295 operations for every byte it reads derived: 989.5e12 / 3.35e12. A float32 softmax does about five operations per element, which is under one per byte moved derived: 5 / 8 bytes read and written. Almost every kernel would starve if each operand came from main memory, so the chip has a ladder of smaller, faster memories, and much of kernel writing is deciding which rung each piece of data lives on.

Coalescing: 32 addresses become memory transactions

When a warp executes a load, its 32 addresses are gathered into as few 32-byte sectors as possible ({{CUDA Best Practices Guide, coalesced access|https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#coalesced-access-to-global-memory}}). If thread k reads float k, the warp needs 128 contiguous bytes, four sectors, and every byte fetched is used: the access is coalesced. If thread k reads float 32k, every thread's 4 bytes sit in a different sector and the warp moves 1,024 bytes to use 128. The rule that follows: make threadIdx.x walk along the contiguous dimension of the array (for a row-major matrix, along a row).

Predict: on the M1 Pro, reading with a stride of 32 floats instead of 1 (same number of floats) is how much slower?
measured on Apple M1 Pro GPU 6.0 times (129 GB/s of useful data at stride 1 against 22 GB/s at stride 32). Less than 32 times because caches catch some of the wasted bytes and the GPU has more requests in flight; a random gather fell to 1.5 GB/s. The NVIDIA arithmetic says 8 times as many sectors per warp at stride 32 as at stride 1.

The same effect inside a real kernel: in the {{Kernel lab|#t-lab}}, a naive 2,048 matmul whose threads walk down columns took 229 ms on the M1 Pro; swapping which index follows the thread index (nothing else) brought it to 47.5 ms, 4.8 times faster measured on Apple M1 Pro GPU.

Shared memory: a scratchpad you fill yourself

Shared memory is on-chip SRAM inside the SM, visible to all threads of one block. The pattern is always the same: threads cooperatively copy a tile from global memory into a __shared__ array (each thread one or a few elements, coalesced), wait at __syncthreads(), then all read the tile many times at on-chip speed. It is divided into 32 banks of 4 bytes; if two threads of a warp hit different addresses in the same bank, their accesses take turns (a bank conflict). The classic case is reading a column of a float tile[32][32]: all 32 threads land in the same bank. The classic fix is one padding column, tile[32][33]. measured on Apple M1 Pro GPU: threadgroup-memory reads with a lane stride of 32 ran at 113 billion reads per second against 318 at stride 1 and 394 at stride 33, the same signature (Apple does not document its banks; the {{GPU simulator|#t-sim}} shows the measurement and NVIDIA's rule side by side).

Here is the reason shared memory exists, on the operation every model spends most of its time in. One block computes a tile of C = A × B. Without shared memory, every thread fetches its own row of A and column of B from global memory, so each element is fetched once per thread that needs it. With shared memory, the block fetches each element once per tile and every thread reuses it.

One block of 4 × 4 threads computes a 4 × 4 tile of C with K = 8, in two phases of 4. The number in each cell of A and B is how many times it has been fetched from global memory so far. illustrative sizes

The saving is a factor of the tile width T: global loads per block fall from 2T²K to 2TK derived. measured on Apple M1 Pro GPU: a 2,048 float32 matmul ran at 353 GFLOP/s without tiles and 677 GFLOP/s with 8 × 8 threadgroup tiles, but only 478 with 32 × 32 tiles: a bigger tile needs more threads and memory per block, fewer blocks fit at once, and latency hiding suffers. Bigger is not automatically better, which is why tile sizes are tuned per GPU (section 4).

Registers and spills

Registers are the fastest storage and the scarcest: 65,536 per SM shared by every resident thread. A kernel that needs more than 255 per thread, or more than the compiler is allowed to use, spills: values go to "local memory", which despite the name lives in global memory behind the caches. compiled here: in the {{Compiler explorer|#t-compile}}'s register-pressure ladder, the largest kernel hits the 255-register ceiling and ptxas -v reports 1760 bytes spill stores, 1184 bytes spill loads on sm_90a. Spills are invisible in the source; check them in the compiler's report or Nsight Compute.
