4. The memory ladder: why bytes decide

The problem. An H100 SXM can do 989.5 trillion BF16 operations per second on its tensor cores (dense) but fetch only 3.35 TB per second from its memory vendor spec: about 295 operations for every byte it reads derived: 989.5e12 / 3.35e12. A float32 softmax does about five operations per element, under one per byte moved derived: 5 / 8 bytes read and written. Almost every kernel would starve if each operand came from main memory, so the chip has a ladder of smaller, faster memories: registers (one thread, about one cycle), shared memory and L1 (one block or SM, tens of cycles), L2 (the whole GPU, 50 MB on an H100) and HBM (every tensor, hundreds of cycles away). Much of kernel writing is deciding which rung each piece of data lives on.

Three rules follow, each owned and drawn by {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}}: make neighbouring threads touch neighbouring addresses, because a warp's 32 loads are served in 32-byte sectors (coalescing, its section 1); stage a tile in shared memory once and let every thread of the block reuse it, so global loads fall by the tile width (tiling, section 3); and lay the tile out so a warp's reads hit 32 different banks (banks and swizzles, section 4). Registers are the scarcest rung: a kernel that needs more than 255 per thread spills to "local memory", which lives in DRAM behind the caches; the {{Compiler explorer|#t-compile}}'s register-pressure ladder ends in 1760 bytes spill stores, 1184 bytes spill loads on sm_90a compiled here.

5. Fusion: the running example, unfused and fused

When several operations run as separate kernels, each writes its result to HBM and the next reads it back. Fusion runs them in one kernel so the intermediate stays in registers or shared memory. Attention is the example that changed the field: S = QKT, P = softmax(S), O = PV, where the two N × N matrices dwarf the inputs (with head size d = 128, S is N / 128 times the size of Q). FlashAttention ({{Dao et al., 2022|https://arxiv.org/abs/2205.14135}}) never forms them in memory: it streams blocks of K and V past a block of Q on chip and folds each block of scores into the output with the online softmax, a running maximum and sum that rescale when a larger value arrives ({{Milakov and Gimelshein, 2018|https://arxiv.org/abs/1805.02867}}). Predict how the bytes of the two versions grow as you double N, then step.

The N × N matrices are almost all the traffic, and fusion removes them

Bars in HBM are drawn to scale in bytes (BF16, 2 bytes). Traffic counts each tensor read or written once per kernel; the fused count is the ideal (in FlashAttention each block of Q re-reads K and V, which for one head is a few MB and is mostly served from the 50 MB L2). Times at H100 SXM rates: memory = bytes / 3.35 TB/s, compute = 4N²d × heads / 989.5 TFLOP/s derived; the slower of the two bounds the kernel.

Measured on the M1 Pro GPU measured on Apple M1 Pro GPU: 8 heads, d = 64, float16, three separately evaluated steps (so S and P really go to memory) against MLX's fused scaled_dot_product_attention; outputs agree to within 0.00024 at N = 4,096, inside float16 rounding.

NUnfused, msFused, msSpeedupruns (unfused / fused)

The {{Kernel lab|#t-lab}} built both steps as its own Metal kernels: softmax then a matmul at N = 8,192, unfused 7.00 ms with 520 MiB in memory, fused with the online softmax 4.38 ms with 260 MiB; whole attention, 53.5 ms and 1,056 MiB against 30.2 ms and 32 MiB.

Why only about 1.3 to 1.4 times here, when the bytes fall by far more? On this laptop the unfused version is roughly balanced: at N = 4,096 it moves 1.09 GB, 6.6 ms at 165 GB/s, against 6.9 ms of arithmetic at the M1 Pro's 5 TFLOP/s derived. Its ridge point (peak operations per byte of bandwidth) is about 30; an H100's is about 295, so the same unfused attention there spends 4.8 times longer moving bytes than computing (the default above), and fusion pays far more. What transfers: the byte arithmetic, and the memory column (at long context the unfused version does not fit). What does not: the size of the win, which grows with the chip's ratio of compute to bandwidth, and that ratio has grown every generation.
