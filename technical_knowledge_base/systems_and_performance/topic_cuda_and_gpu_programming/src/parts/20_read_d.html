4. Writing kernels: the optimisation ladders for softmax and matmul

Kernel optimisation is a ladder: write the obvious version, find out what limits it, remove that limit, and repeat until the limit is the hardware's. Two ladders teach almost everything, one memory-bound and one compute-bound.

Softmax: count the passes over memory

Softmax of a row is exp(x - max) / sum(exp(x - max)); subtracting the maximum keeps exp from overflowing (why, in floating point: {{Numerical computing for ML|n:3f05c17b0d0d81d6af0be4a9a2edba8d}}). Arithmetic is trivial, so time is set by how many times the matrix crosses the memory bus. Each rung removes passes:

RungWhat changesPassesH100, 8,192² fp32

One pass = one full read or write of the 256 MiB matrix; time = passes × 268 MB / 3.35 TB/s derived, at full bandwidth. The composed version counts PyTorch ops in eager mode (max, subtract, exp, sum, divide), each a kernel.

The rung that matters most is the third, the online softmax of {{Milakov and Gimelshein (NVIDIA, 2018)|https://arxiv.org/abs/1805.02867}}: keep a running maximum m and a running sum d, and when a new element raises the maximum, rescale the sum you already have.

m′ = max(m, xi)    d′ = d · em − m′ + exi − m′
m
largest element seen so far (start at minus infinity)
d
sum of ex − m over the elements seen so far (start at 0)

One pass yields both statistics, and the same rescaling lets you combine partial results computed by different threads or different tiles in any order. That property is the load-bearing idea inside FlashAttention (section 5). measured on Apple M1 Pro GPU: MLX's softmax ran at 166 GB/s counted as two passes, the speed of a plain copy, so it is on the top rung. A row reduction itself (the max, the sum) is done inside a warp with shuffles, instructions that pass a register value directly between lanes: five steps of __shfl_down_sync (offsets 16, 8, 4, 2, 1) sum 32 values with no shared memory; then one value per warp goes through shared memory to finish the block. In production code you call CUB's BlockReduce instead of writing it.

The ladder, measured measured on Apple M1 Pro GPU: the {{Kernel lab|#t-lab}} climbed it with Metal kernels on a 16,384 × 4,096 float32 matrix (median of 3 runs). One thread per row, so neighbouring threads read addresses a whole row apart, took 177 ms; one threadgroup per row with coalesced reads, 3.54 ms; the later rungs (SIMD-group reductions, float4 loads, online softmax, row in registers) shave the rest, because once access is coalesced the kernel is already near the memory's speed. Composed from five eager MLX operations, the same softmax took 13.1 ms, 4.0 times the single kernel kept on chip: the passes table above, measured.

Matmul: the bottleneck moves

Simon Boehm's {{worklog|https://siboehm.com/articles/22/CUDA-MMM}} (December 2022) is the standard curriculum: ten float32 kernels for a 4,092 × 4,092 matmul on an RTX A6000, each fixing what the profiler blamed on the previous one published.

GFLOP/s as published; percentages of cuBLAS as published (kernels 7 and 8, two bank-conflict experiments, are not in his summary table and are left out here too).

  • Coalescing (1 to 2, 6.4 times): swap which index follows threadIdx.x so a warp's loads are contiguous (section 3).
  • Shared-memory tiles (2 to 3): each block stages tiles of A and B on chip and reuses them. Now global bandwidth is no longer the limit; shared-memory bandwidth and instruction issue are.
  • Thread tiles in registers (3 to 5, 5.4 times): each thread computes a small block of C (8 × 8 outputs) in registers, reading each shared value into a register once and using it eight times. This is the same reuse idea one level further down the hierarchy.
  • Vectorised loads, autotuning, warp tiles (5 to 10): 128-bit loads, tile sizes searched per GPU, and a warp-level tile that matches how tensor cores are fed. The final shape, block tile, then warp tile, then thread tile, is exactly how CUTLASS is organised (section 7).

The same ladder on the M1 Pro measured on Apple M1 Pro GPU, 2,048 float32, from the {{Kernel lab|#t-lab}}: the order of the rungs and the size of the first jumps transfer; the last rung uses Apple's 8 × 8 matrix instructions, the M1's nearest thing to tensor cores.

Correction to the old page
The old child page quoted 81% of cuBLAS for kernel 6 and 94% for kernel 9; the worklog's table says 78.4% and 84.8%; 93.7% is kernel 10 (warp tiling).

All of these are CUDA-core kernels doing ordinary float32 multiply-adds. Real training matmuls run on tensor cores in BF16 or FP8, which on an H100 offer about 15 times the dense FLOP rate of its float32 units (989.5 against 67 TFLOP/s vendor spec); the same tiling ladder applies, with tensor-core instructions at the bottom and asynchronous copies feeding the tiles (section 7).

Go deeper: the {{Kernel lab|#t-lab}} runs these kernels for real, Triton versions checked on the CPU and Metal versions timed on the M1 Pro's GPU; the {{Compiler explorer|#t-compile}} shows what the naive and tiled matmul and the warp-shuffle reduction compile to.
