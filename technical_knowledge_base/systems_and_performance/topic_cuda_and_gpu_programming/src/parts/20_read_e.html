5. Fusion and FlashAttention: why bytes moved decide

The idea. When several operations run as separate kernels, each one writes its result to HBM and the next reads it back. Fusion runs them in one kernel so the intermediate stays in registers or shared memory and never touches HBM. For memory-bound operations (anything elementwise, normalisations, softmax) this is nearly the whole game: k fused memory-bound operations cost close to one. The softmax-then-matmul pair at the heart of attention is the example that changed the field.

Standard attention computes S = QKT (an N × N matrix of scores for a sequence of N tokens), P = softmax(S) and O = PV, and the two N × N matrices are far larger than the inputs: with head size d = 128, S is N / 128 times the size of Q. FlashAttention ({{Dao et al., 2022|https://arxiv.org/abs/2205.14135}}) never forms them in memory. It loads a block of Q rows on chip, streams blocks of K and V past it, computes each block of scores on chip, and folds it into the output with the online-softmax rescaling of section 4. The paper proves it needs Θ(N²d² / M) HBM accesses for on-chip memory of size M, against Θ(N d + N²) for standard attention, and reported 15% end-to-end speedup on BERT-large, 3 times on GPT-2 at 1K tokens and 2.4 times on Long Range Arena published.

Bars in HBM are drawn to scale in bytes (BF16, 2 bytes). Traffic counts each tensor read or written once per kernel; the fused count is the ideal (in FlashAttention each block of Q re-reads K and V, which for one head is a few MB and is mostly served from the 50 MB L2). Times at H100 SXM rates: memory = bytes / 3.35 TB/s, compute = 4N²d × heads / 989.5 TFLOP/s derived; the slower of the two bounds the kernel.

Measured on the M1 Pro GPU measured on Apple M1 Pro GPU: 8 heads, d = 64, float16. Three separately evaluated steps (scores, softmax, P V, so S and P really go to memory) against MLX's fused scaled_dot_product_attention; outputs agree to within 0.00024 at N = 4,096.

NUnfused, msFused, msSpeedupruns (unfused / fused)

The {{Kernel lab|#t-lab}} built both steps itself as Metal kernels measured on Apple M1 Pro GPU. Softmax followed by a matmul at N = 8,192: unfused 7.00 ms with 520 MiB in memory, fused with the online softmax 4.38 ms with 260 MiB. Whole attention at N = 8,192: S and P in memory 53.5 ms and 1,056 MiB, its FlashAttention-style kernel 30.2 ms and 32 MiB. The memory column is the part that transfers unchanged: at long context the unfused version simply does not fit.

Why only about 1.3 to 1.4 times here, when the byte count falls by far more? Because on this laptop the unfused version is roughly balanced: at N = 4,096 it moves 1.09 GB, 6.6 ms at 165 GB/s, against 6.9 ms of arithmetic at the M1 Pro's 5 TFLOP/s derived. Its ridge point (peak operations per byte of bandwidth) is about 30; an H100's is about 295, so the same unfused attention there spends 4.8 times longer moving bytes than computing (the default above), and fusion pays far more. What transfers: the byte arithmetic. What does not: the size of the win, which grows with the chip's ratio of compute to bandwidth, and that ratio has grown every generation.

The lineage is the same three ideas (tile, online softmax, recompute in the backward pass instead of storing P) re-expressed for each generation's data-movement hardware: FlashAttention-2 (better work partitioning; Ampere, Ada, Hopper), FlashAttention-3 (Hopper: wgmma, TMA, FP8), and FlashAttention-4, "written in CuTeDSL and optimized for Hopper and Blackwell GPUs" ({{flash-attention README|https://github.com/Dao-AILab/flash-attention}}, read 2026-10-05). On recent PyTorch, F.scaled_dot_product_attention picks one of these backends for you (section 1).

When fusion does not help: fusing two compute-bound matmuls rarely pays (the tensor cores are already busy and register pressure rises); and torch.compile already fuses elementwise chains and matmul epilogues, so measure against a compiled baseline, not eager. The far end of fusion is the megakernel: a whole decode step in one persistent kernel, attacking launch and scheduling overhead rather than bytes. Cohere's (September 8, 2026) reports 292 tokens per second at batch size 1 for a 30B mixture-of-experts model with 3.3B active parameters on a single H100, 62% of speed-of-light and 1.58 times vLLM, holding to 256K context ({{Cohere blog|https://cohere.com/blog/megakernels}}) published, vendor's own measurement.
