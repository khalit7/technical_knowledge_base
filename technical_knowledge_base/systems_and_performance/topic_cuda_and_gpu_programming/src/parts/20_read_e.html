8. Compile, profile, check: how you know what ran

Two instruction sets. PTX is NVIDIA's virtual instruction set, stable text that belongs to no chip; SASS is one architecture's machine code and changes every generation. nvcc compiles a .cu file's GPU part to PTX, ptxas turns PTX into SASS for each target named (-arch=sm_90a), and both go into a fat binary; a binary with PTX but no SASS for the GPU it lands on is compiled by the driver just in time, which is how old binaries run on new GPUs. Each generation has a compute capability (8.0 for A100, 9.0 for H100, 10.0 for B200, 12.0 for the RTX 5090); build for the one you run on (-arch=sm_120 or -arch=native), and note that sm_100 and sm_120 need CUDA 12.8 or newer ({{CUDA 12.8 release notes|https://docs.nvidia.com/cuda/archive/12.8.0/cuda-toolkit-release-notes/index.html}}). nvcc -Xptxas -v reports registers, shared memory and spill bytes per kernel: the numbers that set occupancy. Reading SASS is where you confirm that a load is vectorised (LDG.E.128), shared memory is used (LDS), tensor cores are used (HMMA, HGMMA, UTCHMMA) and nothing spills (STL, LDL). The vector-add kernel compiles to 12 registers per thread on sm_90a compiled here; its PTX and SASS line by line open the {{Compiler explorer|#t-compile}}.

Speed of Light places a kernel at once: memory high and compute low means memory-bound (move fewer bytes, fuse); compute high means compute-bound (tensor cores, lower precision); both low means latency-bound (too few warps, divergence, a tail of idle SMs, or a tiny kernel). Then time honestly: synchronise (a launch returns at once), warm up, mind the L2, report a median with its spread over repeated runs, and compare against torch.compile and cuBLAS, not eager. And check the answer against a higher-precision reference with a tolerance for the data type, at sizes that are not multiples of the tile: the {{Kernel lab|#t-lab}} records a synchronisation bug in its fused kernel that passed every small test and corrupted 1 to 5 random rows per run at 4,096 rows, fixed with a full threadgroup barrier; on NVIDIA, compute-sanitizer --tool racecheck is built for this class of bug.

Corrections to the old page (profiling)
The old page said ncu locks clocks to base by default. The {{Nsight Compute CLI documentation|https://docs.nvidia.com/nsight-compute/NsightComputeCli/index.html}} (v2026.3.1) lists --clock-control default boost (base, force-boost and none are options) and --cache-control default all (caches flushed between replays): check the version you run. Triton's do_bench has no flush_l2 argument; it always clears the L2 by zeroing a 256 MB buffer before each timed run ({{testing.py|https://github.com/triton-lang/triton/blob/main/python/triton/testing.py}}, read 2026-10-05).

AMD. HIP is AMD's CUDA-like C++ ("the Runtime API serves the same role within ROCm as the CUDA Runtime API does in NVIDIA's stack"); most PyTorch kernels reach Instinct parts through Triton's AMD backend. The wavefront of 64 is the porting trap: warp-sized assumptions (a 32-bit lane mask, 32-way reductions) silently break, so check the target before assuming 32 or 64. Apple. The M1 Pro is a real SIMT GPU, which is why this page could measure divergence, latency hiding and fusion on it. Its memory is unified: CPU and GPU share one DRAM (about 165 GB/s measured, against 3.35 TB/s of HBM on an H100), so there are no host-to-device copies and much less bandwidth; kernels are Metal Shading Language, or from Python MLX's mx.fast.metal_kernel, which is how this page's labs ran them; PyTorch's mps device runs on Metal too.
