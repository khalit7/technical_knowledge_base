8. Layouts: the idea Triton hides and Gluon exposes


Every block in TTGIR carries a layout: the rule that says which register of which thread of which warp holds each element. The vector add of section 1 had the simplest, #ttg.blocked<{sizePerThread = [4], threadsPerWarp = [32], warpsPerCTA = [4], order = [0]}>. For 2D blocks the four fields read like this (from Gluon's {{layouts tutorial|https://github.com/triton-lang/triton/blob/v3.8.0/python/tutorials/gluon/02-layouts.py}}): each thread owns a sizePerThread sub-tile; threads tile it threadsPerWarp times; warps tile that warpsPerCTA times; order says which dimension is filled first ([1, 0]: along rows, as row-major). If the tensor is larger than the resulting block, each thread gets more registers; if it is smaller, elements are duplicated across threads (broadcast).




One rule for every layout. Triton converts every layout to a linear layout: a list of bases, one per bit of the register, lane and warp index. The element a (warp, lane, register) holds is the XOR of the bases whose bits are set. For sizePerThread=[2,4], threadsPerWarp=[16,2], warpsPerCTA=[2,2], order=[1,0] on a 64 x 16 tensor, Triton itself prints compiled here, via Gluon's to_linear_layout:


Register bits 0 and 1 step along the row ([0,1], [0,2]), register bit 2 one row down ([1,0]); lane bit 0 jumps 4 columns, lane bits 1 to 4 go down the rows; the warps tile the rest. The {{Layout explorer|#t-lay}} draws any blocked layout from its four fields with this rule; its JavaScript matches Triton's printed bases on all 8 layouts tried, including broadcast ones, and reproduces the tutorial's printed table (first row ).


Broadcast, concretely. The same layout on a 32 x 8 tensor (smaller than its 64 x 16 block) prints warp bases [[0,0],[0,0]]: all four warps hold the same data, so element (0, 0) lives in threads 0, 32, 64 and 96. Four times the registers for the same tensor, which is why a block shape that is too small for num_warps wastes the GPU.




The other layouts you will meet in TTGIR (all visible in the {{Compiler stages|#t-ir}} tab):




slice#ttg.slice<{dim = 1, parent = #blocked}>: a 1D block derived from a 2D layout by dropping a dimension, e.g. the row offsets offs_am before [:, None].


nvidia_mma, amd_mfmaThe accumulator layout the tensor-core instruction dictates: versionMajor = 2, instrShape = [16, 8] for mma.sync; versionMajor = 3, [16, 128, 16] for wgmma; amd_mfma with instrShape = [32, 32, 8] on gfx942.


dot_opThe layout an operand of tl.dot must be in when it comes from registers (mma.sync, MFMA): which thread feeds which part of the instruction.


sharedswizzled_shared<{vec = 8, perPhase = 2, maxPhase = 4}> for tiles read with ldmatrix; nvmma_shared<{swizzlingByteWidth = 128}> for tiles read by wgmma, tcgen05 or written by TMA. Both XOR-swizzle addresses so 32 lanes hit 32 different banks ({{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}}).


tensor_memory_encodingBlackwell only: #ttng.tensor_memory_encoding<blockM = 128, blockN = 128>, the accumulator living in TMEM.


convert_layoutNot a layout but the cost of two: moving a block from one layout to another means threads exchanging data, through shared memory or shuffles. The remove-layout-conversions pass exists to delete as many as possible; one left in a hot loop is a classic hidden cost.
