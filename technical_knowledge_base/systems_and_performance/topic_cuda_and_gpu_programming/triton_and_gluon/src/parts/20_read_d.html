8. Layouts: the idea Triton hides and Gluon exposes


Every block in TTGIR carries a layout. The vector add of section 1 had the simplest, #ttg.blocked<{sizePerThread = [4], threadsPerWarp = [32], warpsPerCTA = [4], order = [0]}>. For 2D blocks the four fields read like this (Gluon's {{layouts tutorial|https://github.com/triton-lang/triton/blob/v3.8.0/python/tutorials/gluon/02-layouts.py}}): each thread owns a sizePerThread sub-tile; threads tile it threadsPerWarp times; warps tile that warpsPerCTA times; order says which dimension is filled first ([1, 0]: along rows, as row-major). A tensor larger than the resulting block gives each thread more registers; a smaller one is duplicated across threads (broadcast). Change one field at a time and watch who owns what:




Which thread holds which element: four fields decide, and a tensor smaller than the block is held several times























Each cell is one tensor element, coloured by warp, labelled T(thread):register when there is room; outlined cells belong to the highlighted thread; a number in the corner counts broadcast copies. The bases are built the way Triton converts a blocked layout to a linear layout (below): register bits for sizePerThread, then lane bits, then warp bits, each in order, then extra register bits for repeats; a basis that falls outside the tensor becomes [0, 0], which is broadcast. Checked against Triton 3.8.0's own to_linear_layout output for the 8 presets marked "Triton printed" (src/out/gluon.json), and against the table printed in Gluon tutorial 02.






One rule for every layout. Triton converts every layout to a linear layout: a list of bases, one per bit of the register, lane and warp index. The element a (warp, lane, register) holds is the XOR of the bases whose bits are set. That is why block dimensions must be powers of two: every layout is a product of power-of-two factors, so it can be written as bases over index bits. For sizePerThread=[2,4], threadsPerWarp=[16,2], warpsPerCTA=[2,2], order=[1,0] on a 64 x 16 tensor, Triton itself prints compiled here, via Gluon's to_linear_layout:


Register bits 0 and 1 step along the row ([0,1], [0,2]), register bit 2 one row down ([1,0]); lane bit 0 jumps 4 columns, lane bits 1 to 4 go down the rows; the warps tile the rest. The explorer above uses this rule; its JavaScript matches Triton's printed bases on all 8 layouts tried, including broadcast ones, and reproduces the tutorial's printed table (first row ).


Broadcast, concretely. The same layout on a 32 x 8 tensor (smaller than its 64 x 16 block) prints warp bases [[0,0],[0,0]]: all four warps hold the same data, so element (0, 0) lives in threads 0, 32, 64 and 96. Four times the registers for the same tensor, which is why a block shape too small for num_warps wastes the GPU.




Moving a block between layouts costs. A convert_layout means threads exchanging data through shared memory or shuffles; the remove-layout-conversions pass exists to delete as many as possible, and one left in a hot loop is a classic hidden cost.
