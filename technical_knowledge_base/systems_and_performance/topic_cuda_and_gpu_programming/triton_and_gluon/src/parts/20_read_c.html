4. Attention: FlashAttention forward in about 35 lines

The problem. Attention computes softmax(QKT x scale) V. Done naively it writes an N x N score matrix to memory per head, which at N = 8,192 is 64 M numbers read and written several times. FlashAttention never stores it: one program takes BM query rows, streams K and V through in tiles of BN rows, and keeps a running maximum, a running sum and a running output that it rescales as the maximum grows (the online softmax). 5. num_warps and num_stages: the two knobs on every launch


Every launch takes two compilation options besides your constexpr values; triton.Config defaults them to num_warps=4 and num_stages=3 checked here.


num_warps is how many warps (groups of 32 threads) one program gets, so how finely the block is divided. More warps means fewer elements, and fewer registers, per thread; fewer warps means more work per thread and more programs fitting on an SM. It also decides which instructions are possible: Hopper's wgmma is issued by a warpgroup of 4 warps, so with 1 or 2 warps the compiler falls back to the older mma.sync. num_stages is how deep the software pipeline is: while the tensor cores multiply tile k, the copies for the next tiles are already in flight, each into its own shared-memory buffer. The rule, matching every compiled point exactly: one stage's buffer holds one tile of A and one of B, (BM x BK + BK x BN) x 2 bytes = 32 KB here. When the MMA reads its operands straight from shared memory (wgmma, tcgen05) the compiler allocates num_stages buffers; when mma.sync first copies operands into registers, it allocates num_stages - 1 (at least 1); Blackwell adds 8 or 16 bytes of barriers derived from the compiled sizes. Check it in the IR: the matmul's TTGIR on sm_90a allocates memdesc<4x128x32xf16> for A at num_stages=4, sm_80 allocates 3x128x32 ({{Compiler stages|#t-ir}}).


Why you care. Shared memory per program decides how many programs fit on one SM (with registers), and past the GPU's per-block limit the kernel compiles fine and then refuses to launch: Triton checks metadata.shared against the device when it loads the binary and raises OutOfResources ({{compiler.py|https://github.com/triton-lang/triton/blob/v3.8.0/python/triton/compiler/compiler.py}}). A configuration tuned on an H100 with 6 stages (192 KB) cannot run on an RTX 5090 at all. The {{Config explorer|#t-cfg}} tab shows registers, shared memory, spills and blocks per SM for every configuration of tutorial 03 on each GPU.


Tensor descriptors (TMA) and warp specialisation, from Triton


Two newer features change what the compiler emits. A tensor descriptor (tl.make_tensor_descriptor, then desc.load([row, col])) describes a whole 2D tile, so on Hopper and Blackwell the copy is done by the TMA (Tensor Memory Accelerator), a copy engine that moves a tile with one instruction instead of every thread computing addresses. tl.range(..., warp_specialize=True) asks the compiler to split the loop between warps with different jobs, producers that copy and consumers that multiply. 6. Autotuning: let the GPU pick the tile


The problem. The best BM, BN, BK, num_warps and num_stages depend on the GPU, the shapes and the data type, and the compiler cannot predict them. Triton's answer is to try several and keep the fastest:

    configs=[triton.Config({"BM": 128, "BN": 256, "BK": 64, "GROUP_M": 8}, num_stages=3, num_warps=8),
             triton.Config({"BM": 64,  "BN": 256, "BK": 32, "GROUP_M": 8}, num_stages=4, num_warps=4),

How it works ({{runtime/autotuner.py|https://github.com/triton-lang/triton/blob/v3.8.0/python/triton/runtime/autotuner.py}}, read for this page): at a call, the tuner builds a key from the values of the key arguments plus the dtype of every tensor argument. On a new key it compiles every configuration and times each with triton.testing.do_bench (by default about 25 ms of warm-up and 100 ms of timed runs per configuration, clearing the L2 cache before each timed run), then stores the winner in memory; later calls with that key go straight to it. A configuration that fails to compile or does not fit (OutOfResources) is timed as infinitely slow and skipped. The grid is a function of the chosen meta-parameters, hence the lambda META.




Prune before timingprune_configs_by={"early_config_prune": f, "perf_model": m, "top_k": k}: drop configurations by rule or by a cost model before any run.


Kernels that write their inputsEvery configuration runs on the same tensors, so an in-place or accumulating kernel corrupts them: list them in reset_to_zero or restore_value.

Keep results across runscache_results=True or TRITON_CACHE_AUTOTUNING=1 writes the timings to Triton's cache directory.




What it costs
Tuning happens at the first call of every new key: N configurations x (compile + about 125 ms of timing). Tutorial 03's 16 configurations are therefore a few seconds per new (M, N, K, dtypes) derived not timed here. A key that changes on every call (a sequence length in inference, say) re-tunes forever: bucket it (round to a power of two in the wrapper) or leave it out of key. In distributed training, ranks can pick different winners from timing noise; that is harmless for speed, but the numbers can then differ slightly between ranks when configurations sum in different orders (our reasoning, not measured).


The tutorial's 16 configurations on four GPUs. On each of sm_80, sm_90a, sm_100a and sm_120,  of the 16 fit the per-block shared-memory limit; the others compile and are then skipped at launch. Which ones, and what each costs in registers and occupancy, is in the {{Config explorer|#t-cfg}}.
