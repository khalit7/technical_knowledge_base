4. Attention: FlashAttention forward in about 35 lines

Attention computes softmax(QKT x scale) V. Done naively it writes an N x N score matrix to memory per head, which at N = 8,192 is 64 M numbers read and written several times. FlashAttention never stores it: one program takes BM query rows, streams K and V through in tiles of BN rows, and keeps a running maximum, sum and output that it rescales as the maximum grows (the online softmax; derived, in CUDA C++, with FlashAttention 1 to 3 on {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}; the paper on the {{FlashAttention paper page|n:3c65c17b0d0d81e4a3e8e7a2c4771381}}; animated in the parent's {{Kernel lab|n:3c65c17b0d0d81c39f34d5e070d783c1}}). 5. num_warps and num_stages: the two knobs on every launch


Every launch takes two compilation options besides your constexpr values; triton.Config defaults them to num_warps=4 and num_stages=3 checked here.


num_warps is how many warps one program gets. More warps means fewer elements, and fewer registers, per thread; fewer means more work per thread and more programs per SM. It also decides which instructions are possible: Hopper's wgmma is issued by a warpgroup of 4 warps, so with 1 or 2 warps the compiler falls back to the older mma.sync. The same 128 x 128 x 64 FP16 matmul at five warp counts compiled here:




num_stages is the depth of the software pipeline: while the tensor cores multiply tile k, the copies for the next tiles are already in flight, each into its own shared-memory buffer (the {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}} page animates a 1-to-4-stage pipeline). Predict: does each extra stage add a fixed amount of shared memory, and is it the same on every GPU? Sweeping it on the same matmul compiled here:


Each stage adds one 32 KB buffer, and past a GPU's limit the kernel cannot launch


Shared memory per program against num_stages, 128 x 128 x 64 FP16 tiles, 4 warps. Dashed lines: the largest block each GPU accepts (99 KB on sm_120, 163 KB on sm_80, 227 KB on sm_90a and sm_100a; CUDA Programming Guide v13.4.2 Tables 30 and 31).


The rule, matching every compiled point exactly: one stage's buffer holds one tile of A and one of B, (BM x BK + BK x BN) x 2 bytes = 32 KB here. When the MMA reads its operands straight from shared memory (wgmma, tcgen05) the compiler allocates num_stages buffers; when mma.sync first copies operands into registers, num_stages - 1 (at least 1); Blackwell adds 8 or 16 bytes of barriers derived from the compiled sizes. In the IR: the matmul's TTGIR on sm_90a allocates memdesc<4x128x32xf16> for A at num_stages=4, sm_80 allocates 3x128x32 ({{Compiler stages|#t-ir}}).


Why you care. Shared memory per program, with registers, decides how many programs fit on one SM, and past the GPU's per-block limit the kernel compiles fine and then refuses to launch: Triton checks metadata.shared against the device when it loads the binary and raises OutOfResources ({{compiler.py|https://github.com/triton-lang/triton/blob/v3.8.0/python/triton/compiler/compiler.py}}). A configuration tuned on an H100 with 6 stages (192 KB) cannot run on an RTX 5090 at all. The {{Config explorer|#t-cfg}} tab gives registers, shared memory, spills and blocks per SM for every configuration of tutorial 03 on each GPU, and predicts shared memory for any tile.


Tensor descriptors (TMA) and warp specialisation


A tensor descriptor (tl.make_tensor_descriptor, then desc.load([row, col])) describes a whole 2D tile, so on Hopper and Blackwell the copy is done by the TMA (Tensor Memory Accelerator), a copy engine that moves a tile with one instruction instead of every thread computing addresses. tl.range(..., warp_specialize=True) asks the compiler to split the loop between warps with different jobs: producers that copy, consumers that multiply. What the tuner does at a call, from {{runtime/autotuner.py|https://github.com/triton-lang/triton/blob/v3.8.0/python/triton/runtime/autotuner.py}} (read for this page), stepped through with tutorial 03's 16 real configurations compiled for sm_90a:




One new key costs every configuration a compile and a timing; the next call with that key costs nothing










Configurations, registers and shared memory are tutorial 03's, compiled here for sm_90a (FP16); the 227 KB per-block limit is the CUDA Programming Guide's. On each of sm_80, sm_90a, sm_100a and sm_120,  of the 16 fit their GPU's limit. In words: the key is the values of the key arguments plus the dtype of every tensor argument; each configuration is timed with triton.testing.do_bench (by default about 25 ms of warm-up and 100 ms of timed runs, clearing the L2 cache before each timed run); one that fails to compile or does not fit is timed as infinitely slow; the winner is stored in memory under the key. Timings are the tuner's defaults, not measured: which configuration wins needs a GPU not run here.




What it costs
Tuning happens at the first call of every new key: N configurations x (compile + about 125 ms of timing). Tutorial 03's 16 configurations are therefore a few seconds per new (M, N, K, dtypes) derived not timed here. A key that changes on every call (a sequence length in inference, say) re-tunes forever: bucket it (round to a power of two in the wrapper) or leave it out of key. In distributed training, ranks can pick different winners from timing noise; that is harmless for speed, but results can then differ slightly between ranks when configurations sum in different orders (our reasoning, not measured).
