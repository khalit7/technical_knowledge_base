12. Mistakes, each with its evidence

Every item below was either reproduced on this page or read in Triton's source; the tag says which.

Assuming the tensor's length does not change the code compiled here
A length that is not a multiple of 16 removes the divisibility hint on n, and the mask can then cut a run of 4, so a perfectly aligned vector add drops from 16-byte to 4-byte loads (section 1: ). Pad allocations to a multiple of 16 when you can, or give the ragged tail its own small launch.
Passing sliced or offset tensors compiled here
x[1:] starts 4 bytes into the allocation: the pointer is no longer divisible by 16, the hint is gone and so are the vector loads (the no-hint build in section 1). Strides that are not multiples of 16 do the same to 2D tiles.
A block size that is not a power of two interpreter
tl.arange(0, 1000) is rejected: block dimensions must be powers of two. Round up with triton.next_power_of_2 and mask.
A block smaller than the data, silently interpreter
Nothing checks that BLOCK covers the row. Section 2's softmax with BLOCK 512 on 1,000 columns ran and was wrong by 0.9. Assert it in the Python wrapper, and always compare with a PyTorch reference (tolerances per data type, and why the last digits move, are in the Numerics lab tab of {{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}}).
Too many elements per thread: spills compiled here
Each thread holds BLOCK / (32 x num_warps) elements per block. Past a couple of hundred floats the compiler spills (section 2's grid; section 5's 1- and 2-warp matmuls spilled kilobytes per thread). Raise num_warps or shrink the block.
A configuration that compiles but cannot launch compiled here
Shared memory is checked only when the binary is loaded on a device. 5 of tutorial 03's 16 configurations exceed each GPU's per-block limit; on an RTX 5090 (99 KB) 5 stages of 128 x 128 x 64 FP16 tiles (128 KB) do not fit. Autotune skips them silently; a fixed configuration copied from an H100 kernel raises OutOfResources.
Fewer than 4 warps on Hopper or Blackwell compiled here
With 1 or 2 warps the compiler cannot form a warpgroup and falls back from wgmma or tcgen05 to mma.sync (section 5's table), and the 128 x 128 accumulator no longer fits in registers.
Expecting FP32 from an FP32 tl.dot source
The default is TF32 on NVIDIA (section 3). If you compare with torch.matmul in FP32, pass input_precision="ieee" or loosen the tolerance knowingly.
32-bit offsets on huge tensors derived
tl.program_id is a 32-bit integer and so is pid * BLOCK; past 231 = 2,147,483,648 elements (8 GiB of FP32) offsets wrap around. Integer arguments of 231 or more are passed as i64 (section 1), but offsets you compute from program_id are not: cast with tl.program_id(0).to(tl.int64) for tensors that large.
An autotune key that never repeats, or a kernel that writes its inputs source
Every new key value re-runs every configuration (section 6), and every configuration runs on the same tensors: bucket the key, and list in-place or accumulated outputs in reset_to_zero or restore_value.
Timing the first call source
The first call compiles (and autotunes); later calls with a new specialisation key compile again. Time with triton.testing.do_bench after a warm-up, which also clears the L2 cache between runs (it zeroes a 256 MB buffer before each one and returns the mean by default); the rest of honest timing is section 2 of {{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}}. Small kernels are often dominated by launch overhead instead, which CUDA graphs remove ({{Streams, CUDA graphs and multi-GPU|n:3f05c17b0d0d81b19a6acab65c370b75}}).
Trusting the interpreter for more than the maths source
TRITON_INTERPRET=1 runs programs one after another in NumPy. It finds indexing, masking and numerical mistakes; it cannot show a race between programs, an atomic ordering problem, a layout conversion, a spill or a compiler bug. Compile for the real target too, as this page does.

13. Interview questions, with short answers

What is a Triton program, and how does it relate to CUDA?
One instance of the kernel working on blocks of values; it becomes one CUDA thread block of num_warps x 32 threads. You index blocks with program_id; the compiler maps elements to threads through a layout.
Why do block sizes have to be powers of two?
tl.arange requires it, and every layout is built from power-of-two factors (elements per thread x threads per warp x warps), which is what lets the compiler describe any layout as bases over the bits of the register, lane and warp index.
What do num_warps and num_stages do?
num_warps: threads per program, hence elements and registers per thread, and whether warpgroup instructions are possible. num_stages: software-pipeline depth, one shared-memory buffer per stage (minus one on the mma.sync path), so it trades shared memory, and occupancy, for latency hiding.
How does Triton get vectorised, coalesced loads?
An axis analysis works out how many consecutive offsets are contiguous and how aligned they are, using the 16-byte divisibility hints Triton attaches to arguments at launch; the coalesce pass then gives each thread runs of up to 16 bytes. Lose a hint (odd offset, odd length) and the loads narrow.
My Triton FP32 matmul disagrees with torch.matmul in the fourth digit. Why?
tl.dot uses TF32 by default for FP32 inputs on NVIDIA; PyTorch's FP32 matmul does not unless allowed. Set input_precision="ieee" to compare like with like.
Why does grouped program ordering speed up a matmul?
Programs running at the same time share L2; grouping tile rows makes them share tiles of both A and B. For 9 x 9 tiles the first 9 programs need 54 tiles grouped against 90 row-major (tutorial 03).
What does the Triton compiler do between your Python and PTX?
Python to TTIR (tensor ops, no threads), TTGIR (layouts, shared memory, the MMA instruction, software pipelining, about 70 passes), LLVM IR (per-thread code), then PTX and ptxas to SASS, or AMDGCN on AMD.
When would you write Gluon or CUDA instead of Triton?
When a profile shows the kernel is far from the hardware limit and the cause is something Triton decides for you: the layout, the shared-memory plan, the pipelining or warp roles, Blackwell's tensor memory or cluster features. Gluon keeps Triton's front end and lets you choose those; CUDA C++ or CuTe DSL give you everything else.
How does torch.compile use Triton?
Inductor fuses pointwise and reduction operations into Triton kernels it writes (named triton_poi_, triton_per_, triton_red_) and launches from a generated Python wrapper; matmuls go to cuBLAS unless max-autotune lets it time its Triton templates against it. Custom kernels join the graph through torch.library.triton_op.
How does @triton.autotune decide?
On the first call with a new key (the key arguments' values plus tensor dtypes) it compiles and times every configuration with do_bench, keeps the fastest, and treats configurations that fail to compile or do not fit as infinitely slow.
