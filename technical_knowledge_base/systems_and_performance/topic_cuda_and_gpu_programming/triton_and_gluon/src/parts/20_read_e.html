9. torch.compile writes Triton for you

torch.compile captures your PyTorch code as a graph and hands it to Inductor, its code generator, which groups operations that can share one pass over memory and writes a Triton kernel for each group. Without a GPU, Inductor's CUDA path cannot run, but it can be told to emit Triton for CPU tensors (torch._inductor.config.cpu_backend = "triton"); Triton's wheel has no CPU back end, so these kernels are written but cannot execute. The code below is real Inductor output from PyTorch 2.14.1 generated here (src/code/inductor_tg.py); on a CUDA device the same graph gives kernels of the same form with GPU-specific block sizes and heuristics. The whole torch.compile stack (Dynamo, AOTAutograd, Inductor) is the subject of {{The compiler stack|n:3f05c17b0d0d81ddbc00fac9e8a2ff89}}.

gelu(x) * sigmoid(x) + 1 on a 64 x 256 tensor: three PyTorch operations, one kernel


Reading generated code. The name says what it is: triton_poi_ is a pointwise kernel, triton_per_ a persistent reduction (the whole reduced dimension in one block, like section 2's softmax), triton_red_ a looped reduction; then fused_ and the ATen operations inside. xnumel = 16384 is baked in because shapes were static. XBLOCK is left as a constexpr that Inductor's own launcher tunes from size_hints (the decorator lines above the kernel, cut here). tmp0 to tmp11 are the fused operations in order: the exact GELU through erf, then the sigmoid, the product and the +1, with one load and one store.


The attention-like graph softmax(x * 0.125) @ w became one Triton kernel for the scaled softmax and a call to extern_kernels.mm for the matmul:




The softmax kernel Inductor wrote (64 lines, shown in full)
Note what it did with the 0.125: it computes the row maximum of the unscaled input and applies the scale after subtracting, guarded by a check that every scaled value is finite (the abs, eq, ne, any in the code and in the kernel's name), falling back to the plain formula otherwise. That is an algebraic rewrite you would not think to write by hand, read directly from the generated code.




Matmuls go to a library by defaultInductor considers its Triton matmul templates (mm_template, persistent and TMA variants in torch/_inductor/kernel/mm.py) only under mode="max-autotune" or max_autotune_gemm ({{use_triton_template in _inductor/utils.py|https://github.com/pytorch/pytorch/blob/v2.14.0/torch/_inductor/utils.py}}), where it times them against cuBLAS.


See what it wroteTORCH_LOGS="output_code" prints every generated kernel and the Python wrapper that launches them; the files also sit in Inductor's cache directory.


Your Triton kernel inside a compiled graph@torch.library.triton_op plus torch.library.wrap_triton(kernel)[grid](...) registers a hand-written Triton kernel as an operator that torch.compile can see through instead of breaking the graph (both present in PyTorch 2.14).









10. Gluon: the same compiler, your layouts


"Gluon is a GPU programming language based on the same compiler stack as Triton. But unlike Triton, Gluon is a lower-level language that gives the user more control and responsibility when implementing kernels" ({{Gluon tutorial 01, v3.8.0|https://github.com/triton-lang/triton/blob/v3.8.0/python/tutorials/gluon/01-intro.py}}). The tutorial's reason: Triton's compiler "can be beaten by hand-tuned low-level code. When this happens, there is little the user can do", because layouts, memory allocation, data movement and asynchrony are hidden. Gluon exposes them. It lives in triton.experimental.gluon (experimental, by its import path), uses the same @jit-style decorator, launch syntax and @triton.autotune, and ships 14 tutorials in 3.8.0: intro, layouts, async copy, TMA, wgmma, tcgen05, persistence, warp specialisation, TMA gather and scatter, tcgen05 copy, scaled tcgen05 MMA, cluster launch control, an im2col convolution and multi-CTA kernels.




Vector add in Gluon: the layout is now yours


What changed from section 1. One line: gl.BlockedLayout([4], [32], [num_warps], [0]), exactly the layout Triton's coalesce pass chose by itself, now written by hand and attached to gl.arange; every tensor derived from it inherits it. Compiled for sm_90a compiled here, the Gluon kernel's stages are : there is no TTIR, because a Gluon program is TTGIR (layouts included) from the start, and none of Triton's layout passes need to guess.


What else is exposed (module contents checked here): shared memory you allocate (gl.allocate_shared_memory) with layouts you choose (NVMMASharedLayout, SwizzledSharedLayout, PaddedSharedLayout); for Hopper tma, mbarrier, warpgroup_mma; for Blackwell also allocate_tensor_memory, tcgen05_mma, tcgen05_commit, cluster launch control (clc); gl.warp_specialize to give warps different functions; AMD modules for CDNA3, CDNA4, CDNA5 and RDNA3/4; and a new rubin module in 3.8.0.

The instruction widths match the tutorial's table (32, 64, then 128 bits from R = 4 on, with R = 8 and 16 issuing their 128-bit loads in pairs and fours at 16-byte offsets). The lesson of the tutorial, and the reason Gluon exists: the layout changed throughput by about 5% at XBLOCK 2,048 and by 20% at XBLOCK 1,024 (R = 16) in their runs, the widest loads were not the fastest, and only a profiler could say why; their best was R = 1 with XBLOCK 8,192 (6.606 TB/s).


Who uses it
SGLang's MLA decode path for AMD imports triton.experimental.gluon and AMD's aiter mla_gluon kernel when Triton is 3.7 or newer ({{aiter_mla_gluon.py|https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/layers/attention/aiter_mla_gluon.py}}). 11. Beyond NVIDIA, and Triton's neighbours


AMD. The standard Triton wheel contains an AMD back end and the LLVM it needs, so the page's kernels compile for gfx942 (MI300X) and gfx950 (MI355X) on this laptop compiled here. What differs: a wavefront is 64 lanes, not 32 (the vector add's layout became threadsPerWarp = [64]); shared memory is called LDS; tensor cores are MFMA instructions (v_mfma_f32_32x32x8_f16 on gfx942, the doubled-K v_mfma_f32_32x32x16_f16 on gfx950; section 3's table); registers are VGPRs (and AGPRs for accumulators). Tutorial 03 ships a separate AMD configuration list (8 warps, 2 stages, matrix_instr_nonkdim = 16), a reminder that tuned configurations do not transfer between vendors. The ROCm stack itself, including the old page's ROCm 10.0 claims, is on the parent page, section 10. Intel GPUs are served by a separate repository, {{intel-xpu-backend-for-triton|https://github.com/intel/intel-xpu-backend-for-triton}} ("OpenAI Triton backend for Intel GPUs"), not by the standard wheel used here not compiled here.


Correction to the old page: the CUDA Tile IR back end
The old page said "NVIDIA contributed a CUDA Tile IR backend so Triton picks up new Blackwell-generation tensor-core features without source changes." What exists is an incubator repository in the triton-lang organisation, {{Triton-to-tile-IR|https://github.com/triton-lang/Triton-to-tile-IR}} (created December 2025, last commit September 23, 2026): a separate build of Triton 3.7 enabled with ENABLE_TILE=1, validated on B200 with CUDA 13.4, with documented gaps (poor small-GEMM performance, the tensor-of-pointers load and store style "exhibits poor performance", num_warps accepted but not obeyed; a new occupancy hint). It is not part of the Triton 3.8.0 release used on this page.




cuTile (NVIDIA)NVIDIA's own tile-level language on CUDA Tile IR: {{cutile-python|https://github.com/NVIDIA/cutile-python}}, and cutile-rs for Rust (on the parent page, section 10); Julia has cuTile.jl. Same idea as Triton: you write tiles, the compiler maps them.


Helion (PyTorch)A higher-level kernel language from the PyTorch team that compiles to Triton and autotunes over "hundreds of potential Triton implementations" in about 10 minutes, by its README (v1.4.0, July 29, 2026; {{pytorch/helion|https://github.com/pytorch/helion}}).


CuTe DSL (NVIDIA)The Python face of CUTLASS 4: explicit layouts and instructions, closer to Gluon than to Triton. On {{Libraries and tensor cores|n:3c65c17b0d0d81a7adcaebee2f44a087}}.
