9. torch.compile writes Triton for you

torch.compile captures your PyTorch code as a graph and hands it to Inductor, its code generator, which groups operations that can share one pass over memory and writes a Triton kernel for each group. The code below is real Inductor output from PyTorch 2.14.1 generated here (src/code/inductor_tg.py): without a GPU, Inductor can be told to emit Triton for CPU tensors (torch._inductor.config.cpu_backend = "triton"), and Triton's wheel has no CPU back end, so these kernels are written but cannot execute. On a CUDA device the same graph gives kernels of the same form with GPU-specific block sizes. The whole stack (Dynamo, AOTAutograd, Inductor) is {{The compiler stack|n:3f05c17b0d0d81ddbc00fac9e8a2ff89}}'s subject.

gelu(x) * sigmoid(x) + 1 on a 64 x 256 tensor: three PyTorch operations, one kernel


Reading generated code. The name says what it is: triton_poi_ is a pointwise kernel, triton_per_ a persistent reduction (the whole reduced dimension in one block, like section 2's softmax), triton_red_ a looped reduction; then fused_ and the ATen operations inside. xnumel = 16384 is baked in because shapes were static. XBLOCK is a constexpr that Inductor's own launcher tunes from size_hints (the decorator lines, cut here). tmp0 to tmp11 are the fused operations in order: the exact GELU through erf, the sigmoid, the product and the +1, with one load and one store.


The attention-like graph softmax(x * 0.125) @ w became one Triton kernel for the scaled softmax and a call to extern_kernels.mm for the matmul:




The softmax kernel Inductor wrote (64 lines, shown in full)
What it did with the 0.125: it computes the row maximum of the unscaled input and applies the scale after subtracting, guarded by a check that every scaled value is finite (the abs, eq, ne, any in the code and in the kernel's name), falling back to the plain formula otherwise. An algebraic rewrite you would not think to write by hand, read directly from the generated code.


Matmuls go to a library by default. Inductor considers its Triton matmul templates (mm_template, persistent and TMA variants in torch/_inductor/kernel/mm.py) only under mode="max-autotune" or max_autotune_gemm ({{use_triton_template in _inductor/utils.py|https://github.com/pytorch/pytorch/blob/v2.14.0/torch/_inductor/utils.py}}), where it times them against cuBLAS.


Seeing what Inductor wrote, and putting your own kernel in a compiled graph (depth)
TORCH_LOGS="output_code" prints every generated kernel and the Python wrapper that launches them (the files also sit in Inductor's cache directory). A hand-written kernel joins a compiled graph through @torch.library.triton_op plus torch.library.wrap_triton(kernel)[grid](...), which registers it as an operator torch.compile can see through instead of breaking the graph (both present in PyTorch 2.14).







10. Gluon: the same compiler, your layouts


"Gluon is a GPU programming language based on the same compiler stack as Triton. But unlike Triton, Gluon is a lower-level language that gives the user more control and responsibility when implementing kernels" ({{Gluon tutorial 01, v3.8.0|https://github.com/triton-lang/triton/blob/v3.8.0/python/tutorials/gluon/01-intro.py}}). The reason given: Triton's compiler "can be beaten by hand-tuned low-level code. When this happens, there is little the user can do", because layouts, memory allocation, data movement and asynchrony are hidden. Gluon exposes them. It lives in triton.experimental.gluon (experimental, by its import path) and uses the same @jit-style decorator, launch syntax and @triton.autotune.




Vector add in Gluon: the layout is now yours


What changed from section 1. One line: gl.BlockedLayout([4], [32], [num_warps], [0]), exactly the layout Triton's coalesce pass chose by itself, now written by hand and attached to gl.arange; every tensor derived from it inherits it. Compiled for sm_90a compiled here, the Gluon kernel's stages are : no TTIR, because a Gluon program is TTGIR, layouts included, from the start, and none of Triton's layout passes need to guess.






Tutorial 02's experiment, recompiled


Gluon tutorial 02 copies memory with the layout BlockedLayout([R], [32], [4], [0]) for R = 1 to 16, reports the throughput on a GB200, and explains the differences by the load instructions. We cannot time it, but we can compile the same kernel for sm_100a and count those instructions. Predict first: do the widest loads copy fastest?




Throughput published in the tutorial for GB200, XBLOCK 2,048, 4 warps, about 8 GB copied not run here. Instructions compiled here: per thread, from the SASS. The widths match the tutorial's table (32, 64, then 128 bits from R = 4 on, with R = 8 and 16 issuing their 128-bit loads in pairs and fours at 16-byte offsets). The lesson, and the reason Gluon exists: the layout changed throughput by about 5% at XBLOCK 2,048 and by 20% at XBLOCK 1,024 (R = 16) in their runs, the widest loads were not the fastest, and only a profiler could say why; their best was R = 1 with XBLOCK 8,192 (6.606 TB/s).


What else Gluon exposes, its tutorials, and who uses it (depth)
What else is yours (module contents checked here): shared memory you allocate (gl.allocate_shared_memory) with layouts you choose (NVMMASharedLayout, SwizzledSharedLayout, PaddedSharedLayout); for Hopper tma, mbarrier, warpgroup_mma; for Blackwell also allocate_tensor_memory, tcgen05_mma, tcgen05_commit and cluster launch control (clc); gl.warp_specialize to give warps different functions; AMD modules for CDNA3, CDNA4, CDNA5 and RDNA3/4; and a new rubin module in 3.8.0.
Triton 3.8.0 ships 14 Gluon tutorials: intro, layouts, async copy, TMA, wgmma, tcgen05, persistence, warp specialisation, TMA gather and scatter, tcgen05 copy, scaled tcgen05 MMA, cluster launch control, an im2col convolution and multi-CTA kernels.


SGLang's MLA decode path for AMD imports triton.experimental.gluon and AMD's aiter mla_gluon kernel when Triton is 3.7 or newer ({{aiter_mla_gluon.py|https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/layers/attention/aiter_mla_gluon.py}}). Triton 3.8.0 also reworked an experimental Triton-to-Gluon translator ({{release notes|https://github.com/triton-lang/triton/releases/tag/v3.8.0}}). The old page's "OpenAI publicly runs Triton/Gluon on both NVIDIA and AMD" is unconfirmed: what is public is OpenAI's gpt-oss reference implementation using Triton (its MoE kernel from Triton's triton_kernels; {{gpt-oss README|https://github.com/openai/gpt-oss}}).







11. Which tool: torch.compile, Triton, Gluon or CUDA


Each step down hands you more of the decisions in the hero figure, and more of the work.




torch.compileYou write PyTorch. Inductor fuses operations and writes Triton for you; matmuls go to a library. Start here. Section 9


TritonYou write one program over blocks; the compiler picks layouts, vector widths, shared memory, pipelining and the tensor-core instruction. For what torch.compile cannot express: attention variants, quantised or mixed-format matmuls, fused MoE routing, fused losses. Sections 1 to 8


GluonSame compiler and launch, but you choose the layouts, shared memory, asynchronous copies, barriers and warp roles. Section 10


CUDA C++, CUTLASS, CuTe DSLYou write what each thread does: explicit warp roles, swizzles, clusters, persistent scheduling, any device API, C++ deployment without Python. {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}, {{Libraries and tensor cores|n:3c65c17b0d0d81a7adcaebee2f44a087}}




When Triton is enough, and when it is not. Write no kernel until a profile shows a gap; prototype in Triton; go lower only for the kernels that dominate the profile. Go to Gluon or CUDA when the kernel is far from the hardware limit and the cause is something Triton decides for you: the layout, the shared-memory plan, the pipelining or warp roles, Blackwell's tensor memory or cluster features. Gluon keeps Triton's front end and lets you choose those; CUDA C++ or the CuTe DSL give you everything else. The old page's "a competent Triton kernel lands within 0 to 20% of expert CUDA in about a tenth of the lines" is a rule of thumb with no source we could find unconfirmed.


Beyond NVIDIA


AMD. The standard Triton wheel contains an AMD back end and the LLVM it needs, so the page's kernels compile for gfx942 (MI300X) and gfx950 (MI355X) compiled here. What differs: a wavefront is 64 lanes, not 32 (the vector add's layout became threadsPerWarp = [64]); shared memory is called LDS; tensor cores are MFMA instructions (v_mfma_f32_32x32x8_f16 on gfx942, the doubled-K v_mfma_f32_32x32x16_f16 on gfx950; section 3's table); registers are VGPRs (and AGPRs for accumulators). Tutorial 03 ships a separate AMD configuration list (8 warps, 2 stages, matrix_instr_nonkdim = 16): tuned configurations do not transfer between vendors.


Correction to the old page: the CUDA Tile IR back end
The old page said "NVIDIA contributed a CUDA Tile IR backend so Triton picks up new Blackwell-generation tensor-core features without source changes." What exists is an incubator repository in the triton-lang organisation, {{Triton-to-tile-IR|https://github.com/triton-lang/Triton-to-tile-IR}} (created December 2025, last commit September 23, 2026): a separate build of Triton 3.7 enabled with ENABLE_TILE=1, validated on B200 with CUDA 13.4, with documented gaps (poor small-GEMM performance, the tensor-of-pointers load and store style "exhibits poor performance", num_warps accepted but not obeyed; a new occupancy hint). It is not part of the Triton 3.8.0 release used on this page.


Triton's neighbours, and where Triton is used (depth)


ROCm and IntelThe ROCm stack, including the old page's ROCm 10.0 claims, is on the parent page, section 10. Intel GPUs are served by a separate repository, {{intel-xpu-backend-for-triton|https://github.com/intel/intel-xpu-backend-for-triton}} ("OpenAI Triton backend for Intel GPUs"), not by the standard wheel not compiled here.


cuTile (NVIDIA)NVIDIA's own tile-level language on CUDA Tile IR: {{cutile-python|https://github.com/NVIDIA/cutile-python}}, and cutile-rs for Rust (on the parent page, section 10); Julia has cuTile.jl. Same idea as Triton: you write tiles, the compiler maps them.


Helion (PyTorch)A higher-level kernel language from the PyTorch team that compiles to Triton and autotunes over "hundreds of potential Triton implementations" in about 10 minutes, by its README (v1.4.0, July 29, 2026; {{pytorch/helion|https://github.com/pytorch/helion}}).


CuTe DSL (NVIDIA)The Python face of CUTLASS 4: explicit layouts and instructions, closer to Gluon than to Triton. On {{Libraries and tensor cores|n:3c65c17b0d0d81a7adcaebee2f44a087}}.
