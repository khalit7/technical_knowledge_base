Triton is a Python language for writing GPU kernels in which you describe what one program does to whole blocks of numbers, and a compiler decides how the threads, registers, shared memory and tensor cores of a particular GPU carry it out. It is what torch.compile writes for you, what many open training and inference kernels are written in ({{Liger Kernel|https://github.com/linkedin/Liger-Kernel}}, Unsloth, parts of vLLM and SGLang; section 11), and the shortest road from "I use PyTorch" to "I wrote a fused kernel". Gluon is a lower-level language on the same compiler for the cases where Triton's choices leave speed behind.

This page assumes you have read the parent's {{Triton section|n:3c65c17b0d0d81c39f34d5e070d783c1}} (section 6 of its Reading tab) or nothing at all: every term is explained at first use. 1. Blocks, not threads: vector add from zero

The problem. A GPU runs thousands of threads at once. In CUDA C++ you write the code of one thread and arrange how threads cooperate. That is a lot of bookkeeping before any maths happens, and most of it (vector widths, shared memory, which instruction feeds the tensor cores) changes from one GPU generation to the next.

Triton's answer ({{Tillet, Kung and Cox, MAPL 2019|https://www.eecs.harvard.edu/~htk/publication/2019-mapl-tillet-kung-cox.pdf}}): you write one program that works on a block (a small array, every dimension a power of two) and launch a grid of copies of it. Each copy asks tl.program_id(0) which block it owns. One program becomes one CUDA thread block (a CTA) of num_warps x 32 threads; which of those threads holds which element is the compiler's business.

The kernel (src/code/kernels_tg.py)


Launching it from PyTorch
n = 1000
a, b = torch.randn(n), torch.randn(n)
c = torch.empty(n)
grid = (triton.cdiv(n, 256),)   # 4 programs
vadd[grid](a, b, c, n, BLOCK=256)
# tensors arrive as pointers to their first element


Line by line: offs is a block of 256 indices, so a_ptr + offs is a block of 256 addresses and tl.load reads all of them. The vector has 1,000 elements and the grid covers 1,024, so the last program's mask switches off 24 lanes: masked lanes neither read nor write. interpreter exact match with a + b ().




What happens at the first call. Triton looks at the arguments, builds a specialisation key and compiles (or fetches from its cache, by default ~/.triton/cache, set by TRITON_CACHE_DIR; {{knobs.py|https://github.com/triton-lang/triton/blob/v3.8.0/python/triton/knobs.py}}). The key includes every tl.constexpr value (here BLOCK), each argument's type, whether each pointer and integer is divisible by 16 (it then carries a tt.divisibility = 16 hint; {{backends/compiler.py|https://github.com/triton-lang/triton/blob/v3.8.0/python/triton/backends/compiler.py}}), and two special cases checked here: an integer equal to 1 becomes a compile-time constant, and an integer of 231 or more becomes i64 instead of i32 checked here with triton.runtime.jit.mangle_type. A new key means a new compilation, which costs time at the first call of every new shape class (section 12).

Why this matters for you. A 128-bit load moves 4 floats per instruction instead of 1, so the hinted build issues a quarter of the load instructions:  compiled here. The surprise is the middle case: with aligned pointers but n = 1,000, the layout still gives each thread runs of 4, yet the loads are scalar, because the mask offs < n could now end in the middle of a run and the compiler cannot prove a whole run is in or out. The length of your tensor changed the machine code. Both versions read the same bytes, and on a memory-bound kernel the GPU's memory system can often hide the difference; the {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}} page measured 4-, 8- and 16-byte accesses on the M1 Pro at about the same bandwidth. Where it does matter is instruction issue on wide kernels, and in everything downstream that the compiler can only do when it knows alignment (asynchronous 16-byte copies into shared memory, for one). Triton takes these hints from the arguments automatically; you lose them when you pass a sliced tensor with an odd offset or a stride that is not a multiple of 16.
