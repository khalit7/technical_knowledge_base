In Triton you write what one program does to whole blocks of numbers; the compiler decides, separately for each GPU, which thread holds which element, how wide each load is, what goes into shared memory, how deep the copy pipeline runs and which tensor-core instruction does the multiply. Gluon is the same compiler with those decisions handed back to you.

One source, decided per GPU: what you write, what the compiler chooses, what each GPU runs

Every instruction listed is real compiler output compiled here: the same 128 x 128 x 32 FP16 tl.dot became mma.sync on sm_80 and sm_120, wgmma on sm_90a, tcgen05.mma on sm_100a and MFMA on gfx942 and gfx950 (section 3). The middle column is the compiler's pipeline (section 7); the highlighted TTGIR box holds the decisions this page is about. Gluon programs start at TTGIR, the level where those decisions are written down (section 10).

one instance of the kernel; it owns one block of the data and becomes one CUDA thread block (CTA) of num_warps x 32 threads.

Grid
the number of programs launched; each asks tl.program_id which one it is.

1. Blocks, not threads: vector add

In CUDA C++ you write the code of one thread and arrange how threads cooperate, and much of that bookkeeping (vector widths, shared memory, which instruction feeds the tensor cores) changes with each GPU generation. Triton's answer ({{Tillet, Kung and Cox, MAPL 2019|https://www.eecs.harvard.edu/~htk/publication/2019-mapl-tillet-kung-cox.pdf}}): write one program over a block, launch a grid of copies, and let each ask tl.program_id(0) which block it owns.

The kernel (src/code/kernels_tg.py)


Launching it from PyTorch
n = 1000
a, b = torch.randn(n), torch.randn(n)
c = torch.empty(n)
grid = (triton.cdiv(n, 256),)   # 4 programs
vadd[grid](a, b, c, n, BLOCK=256)
# tensors arrive as pointers to their first element


offs is a block of 256 indices, so a_ptr + offs is a block of 256 addresses and tl.load reads all of them. The grid covers 1,024 elements for a vector of 1,000, so the last program's mask switches off 24 lanes: masked lanes neither read nor write. interpreter exact match with a + b ().




The first call compiles. Triton builds a specialisation key from the arguments and compiles, or fetches the binary from its cache. The key holds every tl.constexpr value (here BLOCK), each argument's type, and whether each pointer and integer is divisible by 16, in which case it carries a tt.divisibility = 16 hint ({{backends/compiler.py|https://github.com/triton-lang/triton/blob/v3.8.0/python/triton/backends/compiler.py}}). A new key means a new compilation (section 12).


Two special cases in the key, and where the cache lives (depth)
An integer argument equal to 1 becomes a compile-time constant, and an integer of 231 or more becomes i64 instead of i32 checked here with triton.runtime.jit.mangle_type. Compiled kernels are cached in ~/.triton/cache by default, set by TRITON_CACHE_DIR ({{knobs.py|https://github.com/triton-lang/triton/blob/v3.8.0/python/triton/knobs.py}}).

Real compiled output: layouts copied from the IR before and after each pass (src/out/passes.json), instruction counts from the SASS of each build (src/out/compile.json). One program's 1,024 elements as 8 rows of 128, coloured by warp; thread 0's elements outlined.




What it means. A 128-bit load moves 4 floats per instruction, so the hinted build issues a quarter of the load instructions:  compiled here. The surprise is the middle case: the layout still gives each thread runs of 4, yet the loads are scalar, because the mask offs < n could now end inside a run and the compiler cannot prove a whole run is in or out. The length of your tensor changed the machine code. The compiler learns how many offsets are contiguous and aligned from an axis analysis that starts from these hints. On a memory-bound kernel the memory system often hides the difference (the {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}} page measured 4-, 8- and 16-byte accesses on the M1 Pro at about the same bandwidth); it matters for instruction issue on wide kernels, and for what the compiler can only do with known alignment, such as 16-byte asynchronous copies into shared memory. You lose the hints by passing a sliced tensor at an odd offset or a stride that is not a multiple of 16.
