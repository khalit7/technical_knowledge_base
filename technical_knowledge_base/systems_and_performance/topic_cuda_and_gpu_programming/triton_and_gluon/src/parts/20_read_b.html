2. Softmax: a reduction in one line, and where blocks stop fitting

Row softmax needs two reductions per row (the maximum, then the sum of exponentials). In CUDA C++ a reduction is per-thread sums, warp shuffles and a shared-memory barrier ({{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}} builds it); in Triton it is tl.max(x, axis=0).

One program per row; the whole row is one block


BLOCK is the next power of two at or above the row length, so a row of 1,000 uses a block of 1,024; the 24 extra lanes load -inf (the other= value), which leaves the maximum alone and adds exp(-inf) = 0 to the sum. The row is read once and written once: the "fused softmax" of {{Triton tutorial 02|https://github.com/triton-lang/triton/blob/v3.8.0/python/tutorials/02-fused-softmax.py}}, which counts 5MN + 2M reads and 3MN + 2M writes for the unfused PyTorch version against MN and MN here (the parent's {{Kernel lab|n:3c65c17b0d0d81c39f34d5e070d783c1}} measured the same idea on the M1 Pro GPU). interpreter 37 rows of 1,000:  against torch.softmax.

The textbook two-level reduction: 5 butterfly shuffle steps across a warp's 32 lanes, then the 4 warps' partials meet in shared memory behind a barrier and finish in 2 more, twice (max and sum): 2 x (5 + 2) = 14 derived. tl.exp became MUFU.EX2, the hardware 2x unit, after a multiply by log2 e.




Predict: a row of 1,000 columns, but someone passes BLOCK=512. What happens?




Runs without complaint and is wrong:  interpreter. Columns 512 to 999 are never read, so each row is normalised over its first half only. Nothing in Triton checks that your block covers your data: that is what the mask and a test against a reference are for.




Where a block stops fitting: the register cliff


A block lives in registers, at most 255 per thread. Each thread holds BLOCK / (32 x num_warps) elements, so a long row in few warps runs out and the compiler spills to local memory (off-chip, private to the thread). Predict where the cliff is for 4 warps, then read the grid.



At 32,768 columns with 4 warps each thread would hold 256 floats: the compiler gives each thread a 2,728-byte stack frame instead (and the register count falls to 32, because the values now live in memory). With 8 warps each thread holds 128 and they fit in 170 registers. The cliff is not one number: at 65,536 columns even 16 warps (128 per thread again) spilled, so read the compiler's report. The fix is more warps per program, which is why {{tutorial 02|https://github.com/triton-lang/triton/blob/v3.8.0/python/tutorials/02-fused-softmax.py}} uses 8 warps, reads the compiled kernel's register count (kernel.n_regs) and launches only as many persistent programs as fit on the GPU at once, each looping over many rows. Rows too long for any block need the online softmax, which reads the row in chunks ({{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}).


Too many elements per thread, and the row moves from registers to a stack in memory

Why the order of programs matters: grouped ordering


Programs that run at the same time share the GPU's L2 cache, so tiles one has loaded are cheap for the others. Launched row by row, the first 9 programs share one row of A but need 9 different columns of B; launched in groups of GROUP_M rows, they share both.

The issuer differs: every warp issues mma.sync (A100, RTX 5090); a warpgroup of 4 warps issues wgmma, reading A and B from shared memory; one thread issues tcgen05.mma for the whole CTA, accumulating in tensor memory (TMEM); AMD's MFMA runs per 64-lane wavefront. The instructions and TMEM are on {{Libraries and tensor cores|n:3c65c17b0d0d81a7adcaebee2f44a087}}; the parent's {{Compiler explorer|n:3c65c17b0d0d81c39f34d5e070d783c1}} found the same choices for its plainer matmul.


An FP32 tl.dot is not FP32 by default
For FP32 inputs on NVIDIA, tl.dot defaults to input_precision="tf32": inputs rounded to TF32 (10 mantissa bits). Pass input_precision="ieee" for true FP32 or "tf32x3" for a three-pass TF32 split that recovers most of the accuracy; on AMD the default is "ieee" except CDNA3, which also offers TF32 ({{tl.dot docstring, language/core.py|https://github.com/triton-lang/triton/blob/v3.8.0/python/triton/language/core.py}}). TRITON_F32_DEFAULT changes the default for a whole process. PyTorch's FP32 matmul on Ampere and later is not TF32 unless you allow it, so a Triton kernel and torch.matmul can disagree in the third or fourth digit for this reason alone.
