2. Softmax: a reduction in one line, and where blocks stop fitting

The problem. Row softmax needs two reductions per row (the maximum, then the sum of exponentials) before it can write anything. In CUDA C++ a reduction is a small project: each thread reduces its share, warps combine with shuffles, warps combine through shared memory with a barrier ({{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}} builds it step by step). In Triton it is tl.max(x, axis=0).

One program per row; the whole row is one block


How it works. BLOCK is the next power of two at or above the row length, so a row of 1,000 uses a block of 1,024; the 24 extra lanes load -inf (the other= value), which leaves the maximum alone and adds exp(-inf) = 0 to the sum. The row is read once and written once: this is the "fused softmax" of {{Triton tutorial 02|https://github.com/triton-lang/triton/blob/v3.8.0/python/tutorials/02-fused-softmax.py}}, which counts 5MN + 2M reads and 3MN + 2M writes for the unfused PyTorch version against MN and MN here. The parent's {{Kernel lab|n:3c65c17b0d0d81c39f34d5e070d783c1}} tab measured the same idea on the M1 Pro GPU. interpreter 37 rows of 1,000:  against torch.softmax.


What tl.max became on sm_90a compiled here: . That is the textbook two-level reduction: 5 butterfly shuffle steps across the 32 lanes of a warp (log2 32 = 5), then the 4 warps' partial results meet in shared memory behind a barrier and finish in 2 more steps (log2 4 = 2), twice (max and sum): 2 x (5 + 2) = 14 derived. tl.exp became MUFU.EX2, the hardware 2x unit, after a multiply by log2 e.




Predict: a row of 1,000 columns, but someone passes BLOCK=512. What happens?




Runs without complaint and is wrong:  interpreter. Columns 512 to 999 are never read, so each row is normalised over its first half only. Nothing in Triton checks that your block covers your data: that is what the mask and a test against a reference are for.


Where a block stops fitting: the register cliff


A block lives in registers, the fastest storage, private to each thread, at most 255 per thread. Each thread holds BLOCK / (32 x num_warps) elements, so a long row in few warps runs out of registers and the compiler spills to local memory (slow, off-chip memory private to the thread; the {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}} page explains spills). Each cell: registers per thread, and the stack frame in bytes per thread when there is one (stack holds spilled values). Elements per thread shown in grey. From cuobjdump -res-usage on each compiled kernel.


Reading it. At 32,768 columns with 4 warps each thread would hold 256 floats: instead of registers the compiler gives each thread a 2,728-byte stack frame in local memory (and the register count falls to 32, because the values now live in memory). With 8 warps each thread holds 128 and they fit in 170 registers. The cliff is not one number: at 65,536 columns even 16 warps (128 per thread again) spilled. Read the compiler's report rather than guess. The fix is more warps per program, which is why {{tutorial 02|https://github.com/triton-lang/triton/blob/v3.8.0/python/tutorials/02-fused-softmax.py}} launches its softmax with 8 warps, asks the compiled kernel for its register count (kernel.n_regs) and launches only as many persistent programs as fit on the GPU at once, each looping over many rows. Rows too long for any block need a different algorithm: the online softmax, which reads the row in chunks ({{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}} and the parent's Kernel lab).







3. Matmul: tiles, tl.dot, and the order of programs


The idea. Each program computes one tile of C, a BM x BN block. It walks along K in steps of BK, loading a BM x BK tile of A and a BK x BN tile of B and multiplying them into an accumulator kept in registers in FP32. tl.dot is the block multiply; the compiler turns it into tensor-core instructions. This is {{tutorial 03|https://github.com/triton-lang/triton/blob/v3.8.0/python/tutorials/03-matrix-multiplication.py}} almost line for line.




Details worth knowing: % M on the row offsets wraps edge tiles back into the matrix so loads stay in bounds (the extra rows are computed and then dropped by the store mask); the K tail is masked with other=0.0 so it adds nothing; anything you want to do to C before it is written (bias, activation, a cast to FP16) goes after the loop while the accumulator is still FP32 and on chip, which is called an epilogue and is free fusion. interpreter 200 x 150 x 130 (no size a multiple of its tile): .


Why the order of programs matters: grouped ordering


Programs that run at the same time share the GPU's L2 cache. If they need the same tiles of A and B, the second one finds them in L2 instead of memory. Launching tiles row by row makes the first 9 programs share one row of A but need 9 different columns of B; launching them in groups of GROUP_M rows makes them share both. The warp-level mma.sync (A100, RTX 5090) is issued by every warp; Hopper's wgmma by a warpgroup (4 warps together) reading A and B straight from shared memory; Blackwell's tcgen05.mma by one thread for the whole CTA, accumulating in tensor memory (TMEM, a 256 KB per-SM store next to the tensor cores; note the LDTM/STTM instructions that move the accumulator in and out); AMD's MFMA per 64-lane wavefront. An FP32 tl.dot is not FP32 by default
For FP32 inputs on NVIDIA, tl.dot defaults to input_precision="tf32": inputs rounded to TF32 (10 mantissa bits) on the tensor cores. Pass input_precision="ieee" for true FP32 or "tf32x3" for a three-pass TF32 split that recovers most of the accuracy; on AMD the default is "ieee" except CDNA3, which also offers TF32 ({{tl.dot docstring, language/core.py|https://github.com/triton-lang/triton/blob/v3.8.0/python/triton/language/core.py}}). TRITON_F32_DEFAULT changes the default for a whole process. PyTorch's own default for FP32 matmuls on Ampere and later is not TF32 unless you allow it, so a Triton kernel and torch.matmul can disagree in the third or fourth digit for this reason alone.
