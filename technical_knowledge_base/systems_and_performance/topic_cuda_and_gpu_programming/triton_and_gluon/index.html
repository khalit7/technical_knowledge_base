In Triton you write what one program does to whole blocks of numbers; the compiler decides, separately for each GPU, which thread holds which element, how wide each load is, what goes into shared memory, how deep the copy pipeline runs and which tensor-core instruction does the multiply. Gluon is the same compiler with those decisions handed back to you.

Fig. 1, step by step: one matmul program, and what the compiler decides for it

  1. The grid: one program per tile of C. A 1,152 x 1,152 x 1,152 FP16 matmul illustrative size with 128 x 128 tiles of C is a grid of 9 x 9 = 81 programs. Each asks tl.program_id(0) which tile it owns; you never write a thread index.
  2. Program 40 owns one tile. Tile (4, 4) of C: 128 x 128 outputs, accumulated in FP32 in the program's registers. Everything this program computes, it computes for that tile only.
  3. The K loop: a tile of A and a tile of B per step. Row 4 of A and column 4 of B are cut into BK = 32 slices: 36 steps, each loading a 128 x 32 tile of A and a 32 x 128 tile of B and calling acc += tl.dot(a, b). Your code ends here: whole blocks, no threads.
  4. Inside the program, the compiler decides. Compiled for sm_90a (H100) with 4 warps and num_stages=4 compiled here: 4 shared-memory buffers for A and 4 for B, 64 KB in all; an accumulator layout (#mma, warpsPerCTA = [4, 1]) that gives each warp 16-row strips of the tile; and wgmma m64n128k16, 4 instructions per K step, 200 registers per thread.
  5. Same source, six instructions. The same 128 x 128 x 32 FP16 tl.dot became mma.sync on sm_80 and sm_120, wgmma on sm_90a, tcgen05.mma on sm_100a and MFMA on gfx942 and gfx950 compiled here. Per K step the whole program issues 256 on sm_80, 4 on sm_90a, 2 on sm_100a, 256 on sm_120, 64 on gfx942 and 32 on gfx950: the larger the instruction, the fewer it takes (section 3). The pipeline that makes these choices is section 7; Gluon programs start at TTGIR, the level where the decisions are written down (section 10).

1. Blocks, not threads: vector add

In CUDA C++ you write the code of one thread and arrange how threads cooperate, and much of that bookkeeping (vector widths, shared memory, which instruction feeds the tensor cores) changes with each GPU generation. Triton's answer (Tillet, Kung and Cox, MAPL 2019): write one program over a block, launch a grid of copies, and let each ask tl.program_id(0) which block it owns.

The kernel (src/code/kernels_tg.py)


Launching it from PyTorch
n = 1000
a, b = torch.randn(n), torch.randn(n)
c = torch.empty(n)
grid = (triton.cdiv(n, 256),)   # 4 programs
vadd[grid](a, b, c, n, BLOCK=256)
# tensors arrive as pointers to their first element


offs is a block of 256 indices, so a_ptr + offs is a block of 256 addresses and tl.load reads all of them. The grid covers 1,024 elements for a vector of 1,000, so the last program's mask switches off 24 lanes: masked lanes neither read nor write. interpreter exact match with a + b ().




The first call compiles. Triton builds a specialisation key from the arguments and compiles, or fetches the binary from its cache. The key holds every tl.constexpr value (here BLOCK), each argument's type, and whether each pointer and integer is divisible by 16, in which case it carries a tt.divisibility = 16 hint (backends/compiler.py). A new key means a new compilation (section 12).


Two special cases in the key, and where the cache lives (depth)
An integer argument equal to 1 becomes a compile-time constant, and an integer of 231 or more becomes i64 instead of i32 checked here with triton.runtime.jit.mangle_type. Compiled kernels are cached in ~/.triton/cache by default, set by TRITON_CACHE_DIR (knobs.py).

The surprise is the middle case: the layout still gives each thread runs of 4, yet the loads are scalar, because the mask offs < n could now end inside a run and the compiler cannot prove a whole run is in or out. The length of your tensor changed the machine code. The compiler learns how many offsets are contiguous and aligned from an axis analysis that starts from these hints. On a memory-bound kernel the memory system often hides the difference (the GPU memory hierarchy page measured 4-, 8- and 16-byte accesses on the M1 Pro at about the same bandwidth); it matters for instruction issue on wide kernels, and for what the compiler can only do with known alignment, such as 16-byte asynchronous copies into shared memory. You lose the hints by passing a sliced tensor at an odd offset or a stride that is not a multiple of 16.

2. Softmax: a reduction in one line, and where blocks stop fitting


Row softmax needs two reductions per row (the maximum, then the sum of exponentials) before it writes anything. In CUDA C++ a reduction is a small project of per-thread sums, warp shuffles and a shared-memory barrier (Writing kernels builds it); in Triton it is tl.max(x, axis=0), and the compiler writes the rest.




One program per row; the whole row is one block


BLOCK is the next power of two at or above the row length, so a row of 1,000 uses a block of 1,024; the 24 extra lanes load -inf (the other= value), which leaves the maximum alone and adds exp(-inf) = 0 to the sum. The row is read once and written once: the "fused softmax" of Triton tutorial 02, which counts 5MN + 2M reads and 3MN + 2M writes for the unfused PyTorch version against MN and MN here (the parent's Kernel lab measured the same idea on the M1 Pro GPU). interpreter 37 rows of 1,000:  against torch.softmax.


What tl.max became on sm_90a compiled here: . The textbook two-level reduction: 5 butterfly shuffle steps across a warp's 32 lanes (log2 32 = 5), then the 4 warps' partial results meet in shared memory behind a barrier and finish in 2 more steps (log2 4 = 2), twice (max and sum): 2 x (5 + 2) = 14 derived. tl.exp became MUFU.EX2, the hardware 2x unit, after a multiply by log2 e.




Predict: a row of 1,000 columns, but someone passes BLOCK=512. What happens?




Runs without complaint and is wrong:  interpreter. Columns 512 to 999 are never read, so each row is normalised over its first half only. Nothing in Triton checks that your block covers your data: that is what the mask and a test against a reference are for.




Where a block stops fitting: the register cliff


A block lives in registers, at most 255 per thread. Each thread holds BLOCK / (32 x num_warps) elements, so a long row in few warps runs out and the compiler spills to local memory (slow, off-chip, private to the thread). Predict where the cliff is for 4 warps, then read the grid on the right.



At 32,768 columns with 4 warps each thread would hold 256 floats: the compiler gives each thread a 2,728-byte stack frame instead (and the register count falls to 32, because the values now live in memory). With 8 warps each thread holds 128 and they fit in 170 registers. The cliff is not one number: at 65,536 columns even 16 warps (128 per thread again) spilled, so read the compiler's report rather than guess. The fix is more warps per program, which is why tutorial 02 uses 8 warps, reads the compiled kernel's register count (kernel.n_regs) and launches only as many persistent programs as fit on the GPU at once, each looping over many rows. Rows too long for any block need the online softmax, which reads the row in chunks (Writing kernels).


Too many elements per thread, and the row moves from registers to a stack in memory

3. Matmul: tiles, tl.dot, and the order of programs


Each program computes one tile of C, a BM x BN block. It walks along K in steps of BK, loading a BM x BK tile of A and a BK x BN tile of B and multiplying them into an FP32 accumulator in registers. tl.dot is the block multiply; the compiler turns it into tensor-core instructions. This is tutorial 03 almost line for line.




% M on the row offsets wraps edge tiles back into the matrix so loads stay in bounds (the extra rows are computed, then dropped by the store mask); the K tail is masked with other=0.0 so it adds nothing. Anything done to C before it is written (bias, activation, a cast to FP16) goes after the loop while the accumulator is still FP32 and on chip: the epilogue, free fusion. interpreter 200 x 150 x 130 (no size a multiple of its tile): .

Why the order of programs matters: grouped ordering


Programs that run at the same time share the GPU's L2 cache, so tiles one has loaded are cheap for the others. Launched row by row, the first 9 programs share one row of A but need 9 different columns of B; launched in groups of GROUP_M rows, they share both. The toggle on the right switches between the two orders; the steps play the launch in stretches.

One tl.dot, six instructions


The same source (128 x 128 x 32 tiles, FP16 inputs, 4 warps, num_stages=4) compiled for six targets compiled here: a different tensor-core instruction for each, fed a different way.




"Per K step" is derived: 128 x 128 x 32 multiply-adds divided by the instruction's shape. "In the listing" is the static count in the compiled code, which includes the copies of the loop body the pipeliner makes for its prologue and epilogue. Warp-level mma.sync (A100, RTX 5090) is issued by every warp; Hopper's wgmma by a warpgroup (4 warps together) reading A and B straight from shared memory; Blackwell's tcgen05.mma by one thread for the whole CTA, accumulating in tensor memory (TMEM, a 256 KB per-SM store beside the tensor cores; the LDTM/STTM instructions move the accumulator in and out); AMD's MFMA per 64-lane wavefront. The instructions themselves are on Libraries and tensor cores; the parent's Compiler explorer found the same choices for its plainer matmul.


An FP32 tl.dot is not FP32 by default
For FP32 inputs on NVIDIA, tl.dot defaults to input_precision="tf32": inputs rounded to TF32 (10 mantissa bits) on the tensor cores. Pass input_precision="ieee" for true FP32 or "tf32x3" for a three-pass TF32 split that recovers most of the accuracy; on AMD the default is "ieee" except CDNA3, which also offers TF32 (tl.dot docstring, language/core.py). TRITON_F32_DEFAULT changes the default for a whole process. PyTorch's own FP32 matmul on Ampere and later is not TF32 unless you allow it, so a Triton kernel and torch.matmul can disagree in the third or fourth digit for this reason alone.






4. Attention: FlashAttention forward in about 35 lines


Attention computes softmax(QKT x scale) V. Done naively it writes an N x N score matrix to memory per head, which at N = 8,192 is 64 M numbers read and written several times. FlashAttention never stores it: one program takes BM query rows, streams K and V through in tiles of BN rows, and keeps a running maximum, sum and output that it rescales as the maximum grows (the online softmax; derived, in CUDA C++, with FlashAttention 1 to 3 on Writing kernels; the paper on the FlashAttention paper page; animated in the parent's Kernel lab). 5. num_warps and num_stages: the two knobs on every launch


Every launch takes two compilation options besides your constexpr values; triton.Config defaults them to num_warps=4 and num_stages=3 checked here.


num_warps is how many warps one program gets. More warps means fewer elements, and fewer registers, per thread; fewer means more work per thread and more programs per SM. It also decides which instructions are possible: Hopper's wgmma is issued by a warpgroup of 4 warps, so with 1 or 2 warps the compiler falls back to the older mma.sync. The same 128 x 128 x 64 FP16 matmul at five warp counts compiled here:






num_stages is the depth of the software pipeline: while the tensor cores multiply tile k, the copies for the next tiles are already in flight, each into its own shared-memory buffer (the GPU memory hierarchy page animates a 1-to-4-stage pipeline). Predict: does each extra stage add a fixed amount of shared memory, and is it the same on every GPU? Sweeping it on the same matmul compiled here gives the chart on the right.



The rule, matching every compiled point exactly: one stage's buffer holds one tile of A and one of B, (BM x BK + BK x BN) x 2 bytes = 32 KB here. When the MMA reads its operands straight from shared memory (wgmma, tcgen05) the compiler allocates num_stages buffers; when mma.sync first copies operands into registers, num_stages - 1 (at least 1); Blackwell adds 8 or 16 bytes of barriers derived from the compiled sizes. In the IR: the matmul's TTGIR on sm_90a allocates memdesc<4x128x32xf16> for A at num_stages=4, sm_80 allocates 3x128x32 (Compiler stages).


Why you care. Shared memory per program, with registers, decides how many programs fit on one SM, and past the GPU's per-block limit the kernel compiles fine and then refuses to launch: Triton checks metadata.shared against the device when it loads the binary and raises OutOfResources (compiler.py). A configuration tuned on an H100 with 6 stages (192 KB) cannot run on an RTX 5090 at all. The Config explorer tab gives registers, shared memory, spills and blocks per SM for every configuration of tutorial 03 on each GPU, and predicts shared memory for any tile.

Tensor descriptors (TMA) and warp specialisation


A tensor descriptor (tl.make_tensor_descriptor, then desc.load([row, col])) describes a whole 2D tile, so on Hopper and Blackwell the copy is done by the TMA (Tensor Memory Accelerator), a copy engine that moves a tile with one instruction instead of every thread computing addresses. tl.range(..., warp_specialize=True) asks the compiler to split the loop between warps with different jobs: producers that copy, consumers that multiply. 6. Autotuning: let the GPU pick the tile


The best BM, BN, BK, num_warps and num_stages depend on the GPU, the shapes and the data type, and the compiler cannot predict them. So Triton tries several and keeps the fastest:

The grid is a function of the chosen meta-parameters, hence the lambda META. What the tuner does at a call, from runtime/autotuner.py (read for this page), stepped through in Fig. 2 with tutorial 03's 16 real configurations compiled for sm_90a: each slab is one configuration, its footprint the BM x BN tile of C it computes, its height the shared memory it asks for.


One new key costs every configuration a compile and a timing; the next call with that key costs nothing


    

  1. A call arrives with a key the tuner has not seen. The key is the values of the key arguments (M, N, K) plus the dtype of every tensor argument. Nothing is stored for this one, so the tuner must choose among the 16 configurations, drawn here by tile size.
    2. 

  2. Every configuration is compiled. Each is a different set of constexpr values, so a different specialisation and a different binary (section 1). Compiled for sm_90a, registers run from 64 to 254 per thread and shared memory from 24 KB to 320 KB compiled here.
    3. 

  3. 5 configurations cannot launch on this GPU. Their shared memory is over the 227 KB per-block limit (the glass plane). They compiled fine; loading them raises OutOfResources, and the tuner times such a configuration (or one that fails to compile) as infinitely slow and skips it, silently.
    4. 

  4. The 11 that fit are timed. Each runs under triton.testing.do_bench: by default about 25 ms of warm-up and 100 ms of timed runs, clearing the L2 cache before each timed run, on the same tensors (so a kernel that writes its inputs needs reset_to_zero or restore_value). 11 x 125 ms is about 1.4 s derived.
    5. 

  5. The fastest is kept, in memory, under the key. Which one wins depends on the shapes and needs a GPU not run here, so the figure leaves the winner blank. The launch grid is then computed from the winner's BM and BN (the lambda META).
    6. 

  6. The next call with the same key costs nothing. A dictionary lookup: no compile, no timing, straight to the stored winner.
    7. 

  7. A call with a new key starts again from step 2. Every distinct (M, N, K, dtypes) pays the compiles and the timing again: two keys mean 32 compiles, 10 skipped, 22 timed, about 2.8 s of timing derived. A key that changes on every call, such as a sequence length, re-tunes forever: bucket it or leave it out of key.

What it costs
Tuning happens at the first call of every new key: N configurations x (compile + about 125 ms of timing). Tutorial 03's 16 configurations are therefore a few seconds per new (M, N, K, dtypes) derived not timed here. A key that changes on every call (a sequence length in inference, say) re-tunes forever: bucket it (round to a power of two in the wrapper) or leave it out of key. In distributed training, ranks can pick different winners from timing noise; that is harmless for speed, but results can then differ slightly between ranks when configurations sum in different orders (our reasoning, not measured).

8. Layouts: the idea Triton hides and Gluon exposes




Every block in TTGIR carries a layout. The vector add of section 1 had the simplest, #ttg.blocked<{sizePerThread = [4], threadsPerWarp = [32], warpsPerCTA = [4], order = [0]}>. For 2D blocks the four fields read like this (Gluon's layouts tutorial): each thread owns a sizePerThread sub-tile; threads tile it threadsPerWarp times; warps tile that warpsPerCTA times; order says which dimension is filled first ([1, 0]: along rows, as row-major). A tensor larger than the resulting block gives each thread more registers; a smaller one is duplicated across threads (broadcast). Change one field at a time in the explorer on the right and watch who owns what.


One rule for every layout. Triton converts every layout to a linear layout: a list of bases, one per bit of the register, lane and warp index. The element a (warp, lane, register) holds is the XOR of the bases whose bits are set. That is why block dimensions must be powers of two: every layout is a product of power-of-two factors, so it can be written as bases over index bits. For sizePerThread=[2,4], threadsPerWarp=[16,2], warpsPerCTA=[2,2], order=[1,0] on a 64 x 16 tensor, Triton itself prints compiled here, via Gluon's to_linear_layout:


Register bits 0 and 1 step along the row ([0,1], [0,2]), register bit 2 one row down ([1,0]); lane bit 0 jumps 4 columns, lane bits 1 to 4 go down the rows; the warps tile the rest. The explorer uses this rule; its JavaScript matches Triton's printed bases on all 8 layouts tried, including broadcast ones, and reproduces the tutorial's printed table (first row ).


Broadcast, concretely. The same layout on a 32 x 8 tensor (smaller than its 64 x 16 block) prints warp bases [[0,0],[0,0]]: all four warps hold the same data, so element (0, 0) lives in threads 0, 32, 64 and 96. Four times the registers for the same tensor, which is why a block shape too small for num_warps wastes the GPU.


Moving a block between layouts costs. A convert_layout means threads exchanging data through shared memory or shuffles; the remove-layout-conversions pass exists to delete as many as possible, and one left in a hot loop is a classic hidden cost.




Which thread holds which element: four fields decide, and a tensor smaller than the block is held several times























Each cell is one tensor element, coloured by warp, labelled T(thread):register when there is room; outlined cells belong to the highlighted thread; a number in the corner counts broadcast copies. The bases are built the way Triton converts a blocked layout to a linear layout (below): register bits for sizePerThread, then lane bits, then warp bits, each in order, then extra register bits for repeats; a basis that falls outside the tensor becomes [0, 0], which is broadcast. Checked against Triton 3.8.0's own to_linear_layout output for the 8 presets marked "Triton printed" (src/out/gluon.json), and against the table printed in Gluon tutorial 02.




The other layouts you will meet in TTGIR (reference; all visible in the Compiler stages tab)


slice#ttg.slice<{dim = 1, parent = #blocked}>: a 1D block derived from a 2D layout by dropping a dimension, e.g. the row offsets offs_am before [:, None].


nvidia_mma, amd_mfmaThe accumulator layout the tensor-core instruction dictates: versionMajor = 2, instrShape = [16, 8] for mma.sync; versionMajor = 3, [16, 128, 16] for wgmma; amd_mfma with instrShape = [32, 32, 8] on gfx942.


dot_opThe layout an operand of tl.dot must be in when it comes from registers (mma.sync, MFMA): which thread feeds which part of the instruction.


sharedswizzled_shared<{vec = 8, perPhase = 2, maxPhase = 4}> for tiles read with ldmatrix; nvmma_shared<{swizzlingByteWidth = 128}> for tiles read by wgmma, tcgen05 or written by TMA. Both XOR-swizzle addresses so 32 lanes hit 32 different banks (GPU memory hierarchy).


tensor_memory_encodingBlackwell only: #ttng.tensor_memory_encoding<blockM = 128, blockN = 128>, the accumulator living in TMEM.








9. torch.compile writes Triton for you


torch.compile captures your PyTorch code as a graph and hands it to Inductor, its code generator, which groups operations that can share one pass over memory and writes a Triton kernel for each group. The code below is real Inductor output from PyTorch 2.14.1 generated here (src/code/inductor_tg.py): without a GPU, Inductor can be told to emit Triton for CPU tensors (torch._inductor.config.cpu_backend = "triton"), and Triton's wheel has no CPU back end, so these kernels are written but cannot execute. On a CUDA device the same graph gives kernels of the same form with GPU-specific block sizes. The whole stack (Dynamo, AOTAutograd, Inductor) is The compiler stack's subject.




gelu(x) * sigmoid(x) + 1 on a 64 x 256 tensor: three PyTorch operations, one kernel


Reading generated code. The name says what it is: triton_poi_ is a pointwise kernel, triton_per_ a persistent reduction (the whole reduced dimension in one block, like section 2's softmax), triton_red_ a looped reduction; then fused_ and the ATen operations inside. xnumel = 16384 is baked in because shapes were static. What it did with the 0.125: it computes the row maximum of the unscaled input and applies the scale after subtracting, guarded by a check that every scaled value is finite (the abs, eq, ne, any in the code and in the kernel's name), falling back to the plain formula otherwise. 10. Gluon: the same compiler, your layouts


"Gluon is a GPU programming language based on the same compiler stack as Triton. But unlike Triton, Gluon is a lower-level language that gives the user more control and responsibility when implementing kernels" (Gluon tutorial 01, v3.8.0). The reason given: Triton's compiler "can be beaten by hand-tuned low-level code. When this happens, there is little the user can do", because layouts, memory allocation, data movement and asynchrony are hidden. Gluon exposes them. It lives in triton.experimental.gluon (experimental, by its import path) and uses the same @jit-style decorator, launch syntax and @triton.autotune.




Vector add in Gluon: the layout is now yours


What changed from section 1. One line: gl.BlockedLayout([4], [32], [num_warps], [0]), exactly the layout Triton's coalesce pass chose by itself, now written by hand and attached to gl.arange; every tensor derived from it inherits it. Compiled for sm_90a compiled here, the Gluon kernel's stages are : no TTIR, because a Gluon program is TTGIR, layouts included, from the start, and none of Triton's layout passes need to guess. 11. Which tool: torch.compile, Triton, Gluon or CUDA


Each step down hands you more of the decisions in the hero figure, and more of the work.




torch.compileYou write PyTorch. Inductor fuses operations and writes Triton for you; matmuls go to a library. Start here. Section 9


TritonYou write one program over blocks; the compiler picks layouts, vector widths, shared memory, pipelining and the tensor-core instruction. For what torch.compile cannot express: attention variants, quantised or mixed-format matmuls, fused MoE routing, fused losses. Sections 1 to 8


GluonSame compiler and launch, but you choose the layouts, shared memory, asynchronous copies, barriers and warp roles. Section 10


CUDA C++, CUTLASS, CuTe DSLYou write what each thread does: explicit warp roles, swizzles, clusters, persistent scheduling, any device API, C++ deployment without Python. Writing kernels, Libraries and tensor cores




When Triton is enough, and when it is not. Write no kernel until a profile shows a gap; prototype in Triton; go lower only for the kernels that dominate the profile. Go to Gluon or CUDA when the kernel is far from the hardware limit and the cause is something Triton decides for you: the layout, the shared-memory plan, the pipelining or warp roles, Blackwell's tensor memory or cluster features. Gluon keeps Triton's front end and lets you choose those; CUDA C++ or the CuTe DSL give you everything else. The old page's "a competent Triton kernel lands within 0 to 20% of expert CUDA in about a tenth of the lines" is a rule of thumb with no source we could find unconfirmed.


Beyond NVIDIA


AMD. The standard Triton wheel contains an AMD back end and the LLVM it needs, so the page's kernels compile for gfx942 (MI300X) and gfx950 (MI355X) compiled here. What differs: a wavefront is 64 lanes, not 32 (the vector add's layout became threadsPerWarp = [64]); shared memory is called LDS; tensor cores are MFMA instructions (v_mfma_f32_32x32x8_f16 on gfx942, the doubled-K v_mfma_f32_32x32x16_f16 on gfx950; section 3's table); registers are VGPRs (and AGPRs for accumulators). Tutorial 03 ships a separate AMD configuration list (8 warps, 2 stages, matrix_instr_nonkdim = 16): tuned configurations do not transfer between vendors.


Correction to the old page: the CUDA Tile IR back end
The old page said "NVIDIA contributed a CUDA Tile IR backend so Triton picks up new Blackwell-generation tensor-core features without source changes." 12. Mistakes, each with its evidence


Closed by default: most are the sections above seen from the failure side. Each was reproduced on this page or read in Triton's source; the tag says which.


Assuming the tensor's length does not change the code compiled here
A length that is not a multiple of 16 removes the divisibility hint on n, and the mask can then cut a run of 4, so a perfectly aligned vector add drops from 16-byte to 4-byte loads (section 1: ). Pad allocations to a multiple of 16 when you can, or give the ragged tail its own small launch.


Passing sliced or offset tensors compiled here
x[1:] starts 4 bytes into the allocation: the pointer is no longer divisible by 16, the hint is gone and so are the vector loads (the no-hint build in section 1). Strides that are not multiples of 16 do the same to 2D tiles.


A block size that is not a power of two interpreter
tl.arange(0, 1000) is rejected: block dimensions must be powers of two. Round up with triton.next_power_of_2 and mask.


A block smaller than the data, silently interpreter
Nothing checks that BLOCK covers the row. Section 2's softmax with BLOCK 512 on 1,000 columns ran and was wrong by 0.9. Assert it in the Python wrapper, and always compare with a PyTorch reference (tolerances per data type, and why the last digits move, are in section 5 of Profiling, benchmarking and correctness, with its closed dot-product workbench).


Too many elements per thread: spills compiled here
Each thread holds BLOCK / (32 x num_warps) elements per block. Past a couple of hundred floats the compiler spills (section 2's grid; section 5's 1- and 2-warp matmuls spilled kilobytes per thread). Raise num_warps or shrink the block.


A configuration that compiles but cannot launch compiled here
Shared memory is checked only when the binary is loaded on a device. 5 of tutorial 03's 16 configurations exceed each GPU's per-block limit; on an RTX 5090 (99 KB) 5 stages of 128 x 128 x 64 FP16 tiles (128 KB) do not fit. Autotune skips them silently; a fixed configuration copied from an H100 kernel raises OutOfResources.


Fewer than 4 warps on Hopper or Blackwell compiled here
With 1 or 2 warps the compiler cannot form a warpgroup and falls back from wgmma or tcgen05 to mma.sync (section 5's table), and the 128 x 128 accumulator no longer fits in registers.


Expecting FP32 from an FP32 tl.dot source
The default is TF32 on NVIDIA (section 3). If you compare with torch.matmul in FP32, pass input_precision="ieee" or loosen the tolerance knowingly.


32-bit offsets on huge tensors derived
tl.program_id is a 32-bit integer and so is pid * BLOCK; past 231 = 2,147,483,648 elements (8 GiB of FP32) offsets wrap around. Integer arguments of 231 or more are passed as i64 (section 1), but offsets you compute from program_id are not: cast with tl.program_id(0).to(tl.int64) for tensors that large.


An autotune key that never repeats, or a kernel that writes its inputs source
Every new key value re-runs every configuration (section 6), and every configuration runs on the same tensors: bucket the key, and list in-place or accumulated outputs in reset_to_zero or restore_value.


Timing the first call source
The first call compiles (and autotunes); later calls with a new specialisation key compile again. Time with triton.testing.do_bench after a warm-up, which also clears the L2 cache between runs (it zeroes a 256 MB buffer before each one and returns the mean by default); the rest of honest timing is section 2 of Profiling, benchmarking and correctness. Small kernels are often dominated by launch overhead instead, which CUDA graphs remove (Streams, CUDA graphs and multi-GPU).


Trusting the interpreter for more than the maths source
TRITON_INTERPRET=1 runs programs one after another in NumPy. It finds indexing, masking and numerical mistakes; it cannot show a race between programs, an atomic ordering problem, a layout conversion, a spill or a compiler bug. Compile for the real target too, as this page does.
