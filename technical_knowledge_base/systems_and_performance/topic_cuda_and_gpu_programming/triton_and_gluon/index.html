Triton is a Python language for writing GPU kernels in which you describe what one program does to whole blocks of numbers, and a compiler decides how the threads, registers, shared memory and tensor cores of a particular GPU carry it out. It is what torch.compile writes for you, what many open training and inference kernels are written in (Liger Kernel, Unsloth, parts of vLLM and SGLang; section 11), and the shortest road from "I use PyTorch" to "I wrote a fused kernel". Gluon is a lower-level language on the same compiler for the cases where Triton's choices leave speed behind.

This page assumes you have read the parent's Triton section (section 6 of its Reading tab) or nothing at all: every term is explained at first use. It owns Triton itself and what its compiler does. The CUDA C++ versions of the same kernels are on Writing kernels; threads, warps and occupancy are on The CUDA programming model; coalescing, shared memory and spills on GPU memory hierarchy.

1. Blocks, not threads: vector add from zero

The problem. A GPU runs thousands of threads at once. In CUDA C++ you write the code of one thread and arrange how threads cooperate. That is a lot of bookkeeping before any maths happens, and most of it (vector widths, shared memory, which instruction feeds the tensor cores) changes from one GPU generation to the next.

Triton's answer (Tillet, Kung and Cox, MAPL 2019): you write one program that works on a block (a small array, every dimension a power of two) and launch a grid of copies of it. Each copy asks tl.program_id(0) which block it owns. One program becomes one CUDA thread block (a CTA) of num_warps x 32 threads; which of those threads holds which element is the compiler's business.

The kernel (src/code/kernels_tg.py)


Launching it from PyTorch
n = 1000
a, b = torch.randn(n), torch.randn(n)
c = torch.empty(n)
grid = (triton.cdiv(n, 256),)   # 4 programs
vadd[grid](a, b, c, n, BLOCK=256)
# tensors arrive as pointers to their first element


Line by line: offs is a block of 256 indices, so a_ptr + offs is a block of 256 addresses and tl.load reads all of them. The vector has 1,000 elements and the grid covers 1,024, so the last program's mask switches off 24 lanes: masked lanes neither read nor write. interpreter exact match with a + b ().




What happens at the first call. Triton looks at the arguments, builds a specialisation key and compiles (or fetches from its cache, by default ~/.triton/cache, set by TRITON_CACHE_DIR; knobs.py). The key includes every tl.constexpr value (here BLOCK), each argument's type, whether each pointer and integer is divisible by 16 (it then carries a tt.divisibility = 16 hint; backends/compiler.py), and two special cases checked here: an integer equal to 1 becomes a compile-time constant, and an integer of 231 or more becomes i64 instead of i32 checked here with triton.runtime.jit.mangle_type. A new key means a new compilation, which costs time at the first call of every new shape class (section 12).

Why this matters for you. A 128-bit load moves 4 floats per instruction instead of 1, so the hinted build issues a quarter of the load instructions:  compiled here. The surprise is the middle case: with aligned pointers but n = 1,000, the layout still gives each thread runs of 4, yet the loads are scalar, because the mask offs < n could now end in the middle of a run and the compiler cannot prove a whole run is in or out. The length of your tensor changed the machine code. Both versions read the same bytes, and on a memory-bound kernel the GPU's memory system can often hide the difference; the GPU memory hierarchy page measured 4-, 8- and 16-byte accesses on the M1 Pro at about the same bandwidth. Where it does matter is instruction issue on wide kernels, and in everything downstream that the compiler can only do when it knows alignment (asynchronous 16-byte copies into shared memory, for one). Triton takes these hints from the arguments automatically; you lose them when you pass a sliced tensor with an odd offset or a stride that is not a multiple of 16.

2. Softmax: a reduction in one line, and where blocks stop fitting


The problem. Row softmax needs two reductions per row (the maximum, then the sum of exponentials) before it can write anything. In CUDA C++ a reduction is a small project: each thread reduces its share, warps combine with shuffles, warps combine through shared memory with a barrier (Writing kernels builds it step by step). In Triton it is tl.max(x, axis=0).




One program per row; the whole row is one block


How it works. BLOCK is the next power of two at or above the row length, so a row of 1,000 uses a block of 1,024; the 24 extra lanes load -inf (the other= value), which leaves the maximum alone and adds exp(-inf) = 0 to the sum. The row is read once and written once: this is the "fused softmax" of Triton tutorial 02, which counts 5MN + 2M reads and 3MN + 2M writes for the unfused PyTorch version against MN and MN here. The parent's Kernel lab tab measured the same idea on the M1 Pro GPU. interpreter 37 rows of 1,000:  against torch.softmax.


What tl.max became on sm_90a compiled here: . That is the textbook two-level reduction: 5 butterfly shuffle steps across the 32 lanes of a warp (log2 32 = 5), then the 4 warps' partial results meet in shared memory behind a barrier and finish in 2 more steps (log2 4 = 2), twice (max and sum): 2 x (5 + 2) = 14 derived. tl.exp became MUFU.EX2, the hardware 2x unit, after a multiply by log2 e.




Predict: a row of 1,000 columns, but someone passes BLOCK=512. What happens?




Runs without complaint and is wrong:  interpreter. Columns 512 to 999 are never read, so each row is normalised over its first half only. Nothing in Triton checks that your block covers your data: that is what the mask and a test against a reference are for.


Where a block stops fitting: the register cliff


A block lives in registers, the fastest storage, private to each thread, at most 255 per thread. Each thread holds BLOCK / (32 x num_warps) elements, so a long row in few warps runs out of registers and the compiler spills to local memory (slow, off-chip memory private to the thread; the GPU memory hierarchy page explains spills). The same softmax compiled for sm_90a at seven block sizes and four warp counts compiled here:




Each cell: registers per thread, and the stack frame in bytes per thread when there is one (stack holds spilled values). Elements per thread shown in grey. From cuobjdump -res-usage on each compiled kernel.


Reading it. At 32,768 columns with 4 warps each thread would hold 256 floats: instead of registers the compiler gives each thread a 2,728-byte stack frame in local memory (and the register count falls to 32, because the values now live in memory). With 8 warps each thread holds 128 and they fit in 170 registers. The cliff is not one number: at 65,536 columns even 16 warps (128 per thread again) spilled. Read the compiler's report rather than guess. The fix is more warps per program, which is why tutorial 02 launches its softmax with 8 warps, asks the compiled kernel for its register count (kernel.n_regs) and launches only as many persistent programs as fit on the GPU at once, each looping over many rows. Rows too long for any block need a different algorithm: the online softmax, which reads the row in chunks (Writing kernels and the parent's Kernel lab).







3. Matmul: tiles, tl.dot, and the order of programs


The idea. Each program computes one tile of C, a BM x BN block. It walks along K in steps of BK, loading a BM x BK tile of A and a BK x BN tile of B and multiplying them into an accumulator kept in registers in FP32. tl.dot is the block multiply; the compiler turns it into tensor-core instructions. This is tutorial 03 almost line for line.




Details worth knowing: % M on the row offsets wraps edge tiles back into the matrix so loads stay in bounds (the extra rows are computed and then dropped by the store mask); the K tail is masked with other=0.0 so it adds nothing; anything you want to do to C before it is written (bias, activation, a cast to FP16) goes after the loop while the accumulator is still FP32 and on chip, which is called an epilogue and is free fusion. interpreter 200 x 150 x 130 (no size a multiple of its tile): .


Why the order of programs matters: grouped ordering


Programs that run at the same time share the GPU's L2 cache. If they need the same tiles of A and B, the second one finds them in L2 instead of memory. Launching tiles row by row makes the first 9 programs share one row of A but need 9 different columns of B; launching them in groups of GROUP_M rows makes them share both. Same input, both orders:














A, B and C each 9 x 9 tiles. The counter is the number of distinct A and B tiles the programs launched so far need (each needs 9 of A and 9 of B). Defaults reproduce tutorial 03's "90 blocks" against "54 blocks" for the first 9 output tiles, by construction (the same count, computed in src/code/recompute.py). The tutorial reports "more than 10%" on some hardware, "220 to 245 TFLOPS on A100" published not run here.




One tl.dot, six instructions


The same source (128 x 128 x 32 tiles, FP16 inputs, 4 warps, num_stages=4) compiled for six targets compiled here. The compiler picked a different tensor-core instruction for each, and a different way of feeding it:




"Per K step" is derived: 128 x 128 x 32 multiply-adds divided by the instruction's shape. "In the listing" is the static count in the compiled code, which includes copies of the loop body the pipeliner makes for its prologue and epilogue. The warp-level mma.sync (A100, RTX 5090) is issued by every warp; Hopper's wgmma by a warpgroup (4 warps together) reading A and B straight from shared memory; Blackwell's tcgen05.mma by one thread for the whole CTA, accumulating in tensor memory (TMEM, a 256 KB per-SM store next to the tensor cores; note the LDTM/STTM instructions that move the accumulator in and out); AMD's MFMA per 64-lane wavefront. Instruction depth lives on Libraries and tensor cores. The parent's Compiler explorer found the same choices for its plainer matmul.


An FP32 tl.dot is not FP32 by default
For FP32 inputs on NVIDIA, tl.dot defaults to input_precision="tf32": inputs rounded to TF32 (10 mantissa bits) on the tensor cores. Pass input_precision="ieee" for true FP32 or "tf32x3" for a three-pass TF32 split that recovers most of the accuracy; on AMD the default is "ieee" except CDNA3, which also offers TF32 (tl.dot docstring, language/core.py). TRITON_F32_DEFAULT changes the default for a whole process. PyTorch's own default for FP32 matmuls on Ampere and later is not TF32 unless you allow it, so a Triton kernel and torch.matmul can disagree in the third or fourth digit for this reason alone.






4. Attention: FlashAttention forward in about 35 lines


The problem. Attention computes softmax(QKT x scale) V. Done naively it writes an N x N score matrix to memory per head, which at N = 8,192 is 64 M numbers read and written several times. FlashAttention never stores it: one program takes BM query rows, streams K and V through in tiles of BN rows, and keeps a running maximum, a running sum and a running output that it rescales as the maximum grows (the online softmax). The derivation, the CUDA C++ version and FlashAttention 1, 2 and 3 are on Writing kernels, the original paper on the FlashAttention paper page; the parent's Kernel lab animates the online softmax and measured it on the M1 Pro GPU. With BM = BN, a causal program visits (nb + 1) / 2nb of the tiles a full one does,  derived. interpreter 2 heads x 200 x 64, FP16 inputs against PyTorch's attention in FP32: .

5. num_warps and num_stages: the two knobs on every launch


Every launch takes two compilation options besides your constexpr values; triton.Config defaults them to num_warps=4 and num_stages=3 checked here.


num_warps is how many warps (groups of 32 threads) one program gets, so how finely the block is divided. More warps means fewer elements, and fewer registers, per thread; fewer warps means more work per thread and more programs fitting on an SM. It also decides which instructions are possible: Hopper's wgmma is issued by a warpgroup of 4 warps, so with 1 or 2 warps the compiler falls back to the older mma.sync. The same 128 x 128 x 64 FP16 matmul at five warp counts compiled here:




num_stages is how deep the software pipeline is: while the tensor cores multiply tile k, the copies for the next tiles are already in flight, each into its own shared-memory buffer. The GPU memory hierarchy page animates a 1-to-4-stage pipeline; here is what the Triton compiler allocates for it. Sweeping num_stages on the same matmul gives an exact rule compiled here:




Shared memory per program against num_stages, 128 x 128 x 64 FP16 tiles, 4 warps. Dashed lines: the largest block each GPU accepts (99 KB on sm_120, 163 KB on sm_80, 227 KB on sm_90a and sm_100a; CUDA Programming Guide v13.4.2 Tables 30 and 31).


The rule, matching every compiled point exactly: one stage's buffer holds one tile of A and one of B, (BM x BK + BK x BN) x 2 bytes = 32 KB here. When the MMA reads its operands straight from shared memory (wgmma, tcgen05) the compiler allocates num_stages buffers; when mma.sync first copies operands into registers, it allocates num_stages - 1 (at least 1); Blackwell adds 8 or 16 bytes of barriers derived from the compiled sizes. Check it in the IR: the matmul's TTGIR on sm_90a allocates memdesc<4x128x32xf16> for A at num_stages=4, sm_80 allocates 3x128x32 (Compiler stages).


Why you care. Shared memory per program decides how many programs fit on one SM (with registers), and past the GPU's per-block limit the kernel compiles fine and then refuses to launch: Triton checks metadata.shared against the device when it loads the binary and raises OutOfResources (compiler.py). A configuration tuned on an H100 with 6 stages (192 KB) cannot run on an RTX 5090 at all. The Config explorer tab shows registers, shared memory, spills and blocks per SM for every configuration of tutorial 03 on each GPU.


Tensor descriptors (TMA) and warp specialisation, from Triton


Two newer features change what the compiler emits. A tensor descriptor (tl.make_tensor_descriptor, then desc.load([row, col])) describes a whole 2D tile, so on Hopper and Blackwell the copy is done by the TMA (Tensor Memory Accelerator), a copy engine that moves a tile with one instruction instead of every thread computing addresses. tl.range(..., warp_specialize=True) asks the compiler to split the loop between warps with different jobs, producers that copy and consumers that multiply. 6. Autotuning: let the GPU pick the tile


The problem. The best BM, BN, BK, num_warps and num_stages depend on the GPU, the shapes and the data type, and the compiler cannot predict them. Triton's answer is to try several and keep the fastest:


@triton.autotune(
    configs=[triton.Config({"BM": 128, "BN": 256, "BK": 64, "GROUP_M": 8}, num_stages=3, num_warps=8),
             triton.Config({"BM": 64,  "BN": 256, "BK": 32, "GROUP_M": 8}, num_stages=4, num_warps=4),
             # ... 14 more in tutorial 03
    ],
    key=["M", "N", "K"],          # re-tune when these change
)
@triton.jit
def matmul(a_ptr, b_ptr, c_ptr, M, N, K, ..., BM: tl.constexpr, BN: tl.constexpr, BK: tl.constexpr, GROUP_M: tl.constexpr):
    ...
matmul[lambda META: (triton.cdiv(M, META["BM"]) * triton.cdiv(N, META["BN"]),)](a, b, c, M, N, K, ...)


How it works (runtime/autotuner.py, read for this page): at a call, the tuner builds a key from the values of the key arguments plus the dtype of every tensor argument. On a new key it compiles every configuration and times each with triton.testing.do_bench (by default about 25 ms of warm-up and 100 ms of timed runs per configuration, clearing the L2 cache before each timed run), then stores the winner in memory; later calls with that key go straight to it. A configuration that fails to compile or does not fit (OutOfResources) is timed as infinitely slow and skipped. The grid is a function of the chosen meta-parameters, hence the lambda META.




Prune before timingprune_configs_by={"early_config_prune": f, "perf_model": m, "top_k": k}: drop configurations by rule or by a cost model before any run.


Kernels that write their inputsEvery configuration runs on the same tensors, so an in-place or accumulating kernel corrupts them: list them in reset_to_zero or restore_value.


See the choiceTRITON_PRINT_AUTOTUNING=1 prints the winner and timings; 3.8.0 added a listener that reports them programmatically (release notes).


Keep results across runscache_results=True or TRITON_CACHE_AUTOTUNING=1 writes the timings to Triton's cache directory.




What it costs
Tuning happens at the first call of every new key: N configurations x (compile + about 125 ms of timing). Tutorial 03's 16 configurations are therefore a few seconds per new (M, N, K, dtypes) derived not timed here. A key that changes on every call (a sequence length in inference, say) re-tunes forever: bucket it (round to a power of two in the wrapper) or leave it out of key. In distributed training, ranks can pick different winners from timing noise; that is harmless for speed, but the numbers can then differ slightly between ranks when configurations sum in different orders (our reasoning, not measured).


The tutorial's 16 configurations on four GPUs. On each of sm_80, sm_90a, sm_100a and sm_120,  of the 16 fit the per-block shared-memory limit; the others compile and are then skipped at launch. Which ones, and what each costs in registers and occupancy, is in the Config explorer.

8. Layouts: the idea Triton hides and Gluon exposes


Every block in TTGIR carries a layout: the rule that says which register of which thread of which warp holds each element. The vector add of section 1 had the simplest, #ttg.blocked<{sizePerThread = [4], threadsPerWarp = [32], warpsPerCTA = [4], order = [0]}>. For 2D blocks the four fields read like this (from Gluon's layouts tutorial): each thread owns a sizePerThread sub-tile; threads tile it threadsPerWarp times; warps tile that warpsPerCTA times; order says which dimension is filled first ([1, 0]: along rows, as row-major). If the tensor is larger than the resulting block, each thread gets more registers; if it is smaller, elements are duplicated across threads (broadcast).




One rule for every layout. Triton converts every layout to a linear layout: a list of bases, one per bit of the register, lane and warp index. The element a (warp, lane, register) holds is the XOR of the bases whose bits are set. For sizePerThread=[2,4], threadsPerWarp=[16,2], warpsPerCTA=[2,2], order=[1,0] on a 64 x 16 tensor, Triton itself prints compiled here, via Gluon's to_linear_layout:


Register bits 0 and 1 step along the row ([0,1], [0,2]), register bit 2 one row down ([1,0]); lane bit 0 jumps 4 columns, lane bits 1 to 4 go down the rows; the warps tile the rest. The Layout explorer draws any blocked layout from its four fields with this rule; its JavaScript matches Triton's printed bases on all 8 layouts tried, including broadcast ones, and reproduces the tutorial's printed table (first row ).


Broadcast, concretely. The same layout on a 32 x 8 tensor (smaller than its 64 x 16 block) prints warp bases [[0,0],[0,0]]: all four warps hold the same data, so element (0, 0) lives in threads 0, 32, 64 and 96. Four times the registers for the same tensor, which is why a block shape that is too small for num_warps wastes the GPU.




The other layouts you will meet in TTGIR (all visible in the Compiler stages tab):




slice#ttg.slice<{dim = 1, parent = #blocked}>: a 1D block derived from a 2D layout by dropping a dimension, e.g. the row offsets offs_am before [:, None].


nvidia_mma, amd_mfmaThe accumulator layout the tensor-core instruction dictates: versionMajor = 2, instrShape = [16, 8] for mma.sync; versionMajor = 3, [16, 128, 16] for wgmma; amd_mfma with instrShape = [32, 32, 8] on gfx942.


dot_opThe layout an operand of tl.dot must be in when it comes from registers (mma.sync, MFMA): which thread feeds which part of the instruction.

convert_layoutNot a layout but the cost of two: moving a block from one layout to another means threads exchanging data, through shared memory or shuffles. The remove-layout-conversions pass exists to delete as many as possible; one left in a hot loop is a classic hidden cost.








9. torch.compile writes Triton for you


torch.compile captures your PyTorch code as a graph and hands it to Inductor, its code generator, which groups operations that can share one pass over memory and writes a Triton kernel for each group. Without a GPU, Inductor's CUDA path cannot run, but it can be told to emit Triton for CPU tensors (torch._inductor.config.cpu_backend = "triton"); Triton's wheel has no CPU back end, so these kernels are written but cannot execute. The code below is real Inductor output from PyTorch 2.14.1 generated here (src/code/inductor_tg.py); on a CUDA device the same graph gives kernels of the same form with GPU-specific block sizes and heuristics. The whole torch.compile stack (Dynamo, AOTAutograd, Inductor) is the subject of The compiler stack.




gelu(x) * sigmoid(x) + 1 on a 64 x 256 tensor: three PyTorch operations, one kernel


Reading generated code. The name says what it is: triton_poi_ is a pointwise kernel, triton_per_ a persistent reduction (the whole reduced dimension in one block, like section 2's softmax), triton_red_ a looped reduction; then fused_ and the ATen operations inside. xnumel = 16384 is baked in because shapes were static. XBLOCK is left as a constexpr that Inductor's own launcher tunes from size_hints (the decorator lines above the kernel, cut here). tmp0 to tmp11 are the fused operations in order: the exact GELU through erf, then the sigmoid, the product and the +1, with one load and one store.

10. Gluon: the same compiler, your layouts


"Gluon is a GPU programming language based on the same compiler stack as Triton. But unlike Triton, Gluon is a lower-level language that gives the user more control and responsibility when implementing kernels" (Gluon tutorial 01, v3.8.0). The tutorial's reason: Triton's compiler "can be beaten by hand-tuned low-level code. When this happens, there is little the user can do", because layouts, memory allocation, data movement and asynchrony are hidden. Gluon exposes them. It lives in triton.experimental.gluon (experimental, by its import path), uses the same @jit-style decorator, launch syntax and @triton.autotune, and ships 14 tutorials in 3.8.0: intro, layouts, async copy, TMA, wgmma, tcgen05, persistence, warp specialisation, TMA gather and scatter, tcgen05 copy, scaled tcgen05 MMA, cluster launch control, an im2col convolution and multi-CTA kernels.




Vector add in Gluon: the layout is now yours


What changed from section 1. One line: gl.BlockedLayout([4], [32], [num_warps], [0]), exactly the layout Triton's coalesce pass chose by itself, now written by hand and attached to gl.arange; every tensor derived from it inherits it. Compiled for sm_90a compiled here, the Gluon kernel's stages are : there is no TTIR, because a Gluon program is TTGIR (layouts included) from the start, and none of Triton's layout passes need to guess.


What else is exposed (module contents checked here): shared memory you allocate (gl.allocate_shared_memory) with layouts you choose (NVMMASharedLayout, SwizzledSharedLayout, PaddedSharedLayout); for Hopper tma, mbarrier, warpgroup_mma; for Blackwell also allocate_tensor_memory, tcgen05_mma, tcgen05_commit, cluster launch control (clc); gl.warp_specialize to give warps different functions; AMD modules for CDNA3, CDNA4, CDNA5 and RDNA3/4; and a new rubin module in 3.8.0.

11. Beyond NVIDIA, and Triton's neighbours


AMD. The standard Triton wheel contains an AMD back end and the LLVM it needs, so the page's kernels compile for gfx942 (MI300X) and gfx950 (MI355X) on this laptop compiled here. What differs: a wavefront is 64 lanes, not 32 (the vector add's layout became threadsPerWarp = [64]); shared memory is called LDS; tensor cores are MFMA instructions (v_mfma_f32_32x32x8_f16 on gfx942, the doubled-K v_mfma_f32_32x32x16_f16 on gfx950; section 3's table); registers are VGPRs (and AGPRs for accumulators). Tutorial 03 ships a separate AMD configuration list (8 warps, 2 stages, matrix_instr_nonkdim = 16), a reminder that tuned configurations do not transfer between vendors. The ROCm stack itself, including the old page's ROCm 10.0 claims, is on the parent page, section 10. Intel GPUs are served by a separate repository, intel-xpu-backend-for-triton ("OpenAI Triton backend for Intel GPUs"), not by the standard wheel used here not compiled here.


Correction to the old page: the CUDA Tile IR back end
The old page said "NVIDIA contributed a CUDA Tile IR backend so Triton picks up new Blackwell-generation tensor-core features without source changes." What exists is an incubator repository in the triton-lang organisation, Triton-to-tile-IR (created December 2025, last commit September 23, 2026): a separate build of Triton 3.7 enabled with ENABLE_TILE=1, validated on B200 with CUDA 13.4, with documented gaps (poor small-GEMM performance, the tensor-of-pointers load and store style "exhibits poor performance", num_warps accepted but not obeyed; a new occupancy hint). It is not part of the Triton 3.8.0 release used on this page.




cuTile (NVIDIA)NVIDIA's own tile-level language on CUDA Tile IR: cutile-python, and cutile-rs for Rust (on the parent page, section 10); Julia has cuTile.jl. Same idea as Triton: you write tiles, the compiler maps them.


Helion (PyTorch)A higher-level kernel language from the PyTorch team that compiles to Triton and autotunes over "hundreds of potential Triton implementations" in about 10 minutes, by its README (v1.4.0, July 29, 2026; pytorch/helion).


CuTe DSL (NVIDIA)The Python face of CUTLASS 4: explicit layouts and instructions, closer to Gluon than to Triton. On Libraries and tensor cores.


Where Triton is usedLiger Kernel ("Efficient Triton Kernels for LLM Training"), Unsloth, vLLM's Triton attention back end and fused MoE kernels, SGLang, gpt-oss's reference implementation, and every torch.compile user. The GPU MODE lectures and kernel leaderboard are the community around it.








12. Mistakes, each with its evidence


Every item below was either reproduced on this page or read in Triton's source; the tag says which.


Assuming the tensor's length does not change the code compiled here
A length that is not a multiple of 16 removes the divisibility hint on n, and the mask can then cut a run of 4, so a perfectly aligned vector add drops from 16-byte to 4-byte loads (section 1: ). Pad allocations to a multiple of 16 when you can, or give the ragged tail its own small launch.


Passing sliced or offset tensors compiled here
x[1:] starts 4 bytes into the allocation: the pointer is no longer divisible by 16, the hint is gone and so are the vector loads (the no-hint build in section 1). Strides that are not multiples of 16 do the same to 2D tiles.


A block size that is not a power of two interpreter
tl.arange(0, 1000) is rejected: block dimensions must be powers of two. Round up with triton.next_power_of_2 and mask.


A block smaller than the data, silently interpreter
Nothing checks that BLOCK covers the row. Section 2's softmax with BLOCK 512 on 1,000 columns ran and was wrong by 0.9. Assert it in the Python wrapper, and always compare with a PyTorch reference (the Profiling, benchmarking and correctness page covers tolerances).


Too many elements per thread: spills compiled here
Each thread holds BLOCK / (32 x num_warps) elements per block. Past a couple of hundred floats the compiler spills (section 2's grid; section 5's 1- and 2-warp matmuls spilled kilobytes per thread). Raise num_warps or shrink the block.


A configuration that compiles but cannot launch compiled here
Shared memory is checked only when the binary is loaded on a device. 5 of tutorial 03's 16 configurations exceed each GPU's per-block limit; on an RTX 5090 (99 KB) 5 stages of 128 x 128 x 64 FP16 tiles (128 KB) do not fit. Autotune skips them silently; a fixed configuration copied from an H100 kernel raises OutOfResources.


Fewer than 4 warps on Hopper or Blackwell compiled here
With 1 or 2 warps the compiler cannot form a warpgroup and falls back from wgmma or tcgen05 to mma.sync (section 5's table), and the 128 x 128 accumulator no longer fits in registers.


Expecting FP32 from an FP32 tl.dot source
The default is TF32 on NVIDIA (section 3). If you compare with torch.matmul in FP32, pass input_precision="ieee" or loosen the tolerance knowingly.


32-bit offsets on huge tensors derived
tl.program_id is a 32-bit integer and so is pid * BLOCK; past 231 = 2,147,483,648 elements (8 GiB of FP32) offsets wrap around. Integer arguments of 231 or more are passed as i64 (section 1), but offsets you compute from program_id are not: cast with tl.program_id(0).to(tl.int64) for tensors that large.


An autotune key that never repeats, or a kernel that writes its inputs source
Every new key value re-runs every configuration (section 6), and every configuration runs on the same tensors: bucket the key, and list in-place or accumulated outputs in reset_to_zero or restore_value.


Timing the first call source
The first call compiles (and autotunes); later calls with a new specialisation key compile again. Time with triton.testing.do_bench after a warm-up, which also clears the L2 cache between runs. Small kernels are often dominated by launch overhead instead, which CUDA graphs remove (Streams, CUDA graphs and multi-GPU).


Trusting the interpreter for more than the maths source
TRITON_INTERPRET=1 runs programs one after another in NumPy. It finds indexing, masking and numerical mistakes; it cannot show a race between programs, an atomic ordering problem, a layout conversion, a spill or a compiler bug. Compile for the real target too, as this page does.







13. Interview questions, with short answers


What is a Triton program, and how does it relate to CUDA?
One instance of the kernel working on blocks of values; it becomes one CUDA thread block of num_warps x 32 threads. You index blocks with program_id; the compiler maps elements to threads through a layout.


Why do block sizes have to be powers of two?
tl.arange requires it, and every layout is built from power-of-two factors (elements per thread x threads per warp x warps), which is what lets the compiler describe any layout as bases over the bits of the register, lane and warp index.


What do num_warps and num_stages do?
num_warps: threads per program, hence elements and registers per thread, and whether warpgroup instructions are possible. num_stages: software-pipeline depth, one shared-memory buffer per stage (minus one on the mma.sync path), so it trades shared memory, and occupancy, for latency hiding.


How does Triton get vectorised, coalesced loads?
An axis analysis works out how many consecutive offsets are contiguous and how aligned they are, using the 16-byte divisibility hints Triton attaches to arguments at launch; the coalesce pass then gives each thread runs of up to 16 bytes. Lose a hint (odd offset, odd length) and the loads narrow.


My Triton FP32 matmul disagrees with torch.matmul in the fourth digit. Why?
tl.dot uses TF32 by default for FP32 inputs on NVIDIA; PyTorch's FP32 matmul does not unless allowed. Set input_precision="ieee" to compare like with like.


Why does grouped program ordering speed up a matmul?
Programs running at the same time share L2; grouping tile rows makes them share tiles of both A and B. For 9 x 9 tiles the first 9 programs need 54 tiles grouped against 90 row-major (tutorial 03).


What does the Triton compiler do between your Python and PTX?
Python to TTIR (tensor ops, no threads), TTGIR (layouts, shared memory, the MMA instruction, software pipelining, about 70 passes), LLVM IR (per-thread code), then PTX and ptxas to SASS, or AMDGCN on AMD.


When would you write Gluon or CUDA instead of Triton?
When a profile shows the kernel is far from the hardware limit and the cause is something Triton decides for you: the layout, the shared-memory plan, the pipelining or warp roles, Blackwell's tensor memory or cluster features. Gluon keeps Triton's front end and lets you choose those; CUDA C++ or CuTe DSL give you everything else.


How does torch.compile use Triton?
Inductor fuses pointwise and reduction operations into Triton kernels it writes (named triton_poi_, triton_per_, triton_red_) and launches from a generated Python wrapper; matmuls go to cuBLAS unless max-autotune lets it time its Triton templates against it. Custom kernels join the graph through torch.library.triton_op.


How does @triton.autotune decide?
On the first call with a new key (the key arguments' values plus tensor dtypes) it compiles and times every configuration with do_bench, keeps the fastest, and treats configurations that fail to compile or do not fit as infinitely slow.


Not run here: nothing on this page ran on an NVIDIA or AMD GPU, so it has no Triton timings of its own. For timings of the same ideas, the parent's Kernel lab measured Metal kernels on the M1 Pro GPU; for how to time Triton kernels honestly on a real GPU, Profiling, benchmarking and correctness.
