The core idea. Almost every FLOP of a training run is a matrix multiply (a GEMM, general matrix multiply: D = αAB + βC), and a fast GEMM is one generation's tensor-core instruction kept busy by tiles staged on chip, an asynchronous copy pipeline, a schedule matched to the SM count and a fused epilogue; cuBLAS and cuDNN ship thousands of such kernels prebuilt, and CUTLASS gives you the parts when none of them fits.

One PyTorch call goes down four layers, and only the bottom one changes with every GPU generation

The running example followed down: torch._addmm_activation(b, x, w.t(), use_gelu=True) hands the GELU to cuBLASLt (CUBLASLT_EPILOGUE_GELU_BIAS), whose heuristic picks, on an H100, a kernel named like sm90_xmma_gemm_bf16bf16_bf16f32_f32_tn_n_tilesize128x128x64_..._5x_cublas (decoded in section 2), which issues HGMMA.64x128x16.F32.BF16; on Ampere it would be HMMA.16816.F32.BF16, on a B200 UTCHMMA into tensor memory, on an RTX 5090 HMMA again. The numbers in brackets are this page's sections.

The running example

Y = GELU(X·W + b) in BF16 with FP32 accumulation, X = 8,192 tokens × 4,096 features, W = 4,096 × 14,336: the shape of the MLP up-projection of a Llama-3-8B-sized layer ({{config.json|https://huggingface.co/meta-llama/Llama-3.1-8B/blob/main/config.json}}: hidden_size 4096, intermediate_size 14336). One forward call is 2 · 8,192 · 14,336 · 4,096 = 962.1 GFLOP derived. Llama itself uses SwiGLU, not GELU; we use GELU because cuBLASLt can apply it inside the GEMM, and SwiGLU is exactly the kind of fusion that pushes people to write their own kernel (section 9).

New terms

tensor core, MMA
the unit that computes D = A·B + C on a small tile in one instruction (matrix multiply-accumulate)
fragment
the scattered piece of an MMA tile that one thread holds in its registers, in a pattern fixed by the hardware
warpgroup
four consecutive warps (128 threads) that issue one Hopper wgmma together
TMEM
tensor memory: datacenter Blackwell's 256 KB per SM that holds MMA accumulators instead of registers
TMA
Tensor Memory Accelerator: one thread starts a copy of a whole tile into shared memory
epilogue
what a GEMM kernel does to an output tile after the K loop, before it leaves the chip (bias, activation, scaling)
wave quantization
the idle SMs of a last wave when the tile count is just above a multiple of the SM count
CuTe layout
a shape and a stride: a function from coordinates to offsets, CUTLASS's notation for every arrangement of data and threads
