3. Tiles, waves, split-K and Stream-K: cutting one GEMM into work for the SMs

A GEMM kernel gives each thread block (each CTA, cooperative thread array) one output tile of BM × BN elements; the block loops over K in slices of BK, each slice being one MAC-loop iteration (multiply-accumulate). With T tiles and P SMs, the tiles run in waves of P (the basics of waves and occupancy are on {{The CUDA programming model|n:3c65c17b0d0d8162865eec15d9dae87e}}). When T is a little over a multiple of P, the last wave is mostly empty: wave quantization.

NVIDIA's own example, reproduced: on an A100 (108 SMs) with 256 × 128 tiles, M = 2,304 and N = 1,536 make 9 × 12 = 108 tiles, exactly one wave; N = 1,544 makes 9 × 13 = 117 tiles, two waves, and NVIDIA's guide reports the GFLOPS "roughly halve" ({{Matrix Multiplication Background guide|https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html}}) vendor. The tile counts follow from the formula by construction derived; the halving is NVIDIA's measurement, not ours.

The running example with 128 × 256 tiles: 64 × 56 = 3,584 tiles, which is 27.15 waves on an H100 (132 SMs, last wave 15% full, 97.0% of the time useful), 24.22 on a B200 (148 SMs) and 21.08 on an RTX 5090 (170 SMs) derived. Big training GEMMs barely notice; small ones do: decode with a small batch, the per-expert GEMMs of a mixture-of-experts layer, and the backward weight-gradient GEMMs of a thin layer.

Predict: M = N = 1,024, K = 16,384 on an H100 with 128 × 256 tiles. What fraction of the 132 SMs has work?
8 × 4 = 32 tiles for 132 SMs: 24% busy, and each busy SM runs a long K loop of 256 iterations. Splitting K four ways gives 128 work units (97% of the SMs), at the cost of combining partial sums. Try it in the {{GEMM scheduler|#t-sched}} tab.

Three ways to hand out the work

  • Data-parallel (the default): one CTA per output tile, the whole K loop inside it. No extra traffic; suffers from quantization.
  • Split-K: cut K into s pieces; s CTAs compute partial sums of the same tile into a workspace, and a reduction (a separate splitKreduce_kernel in cuBLAS, or atomics, or a "serial" in-kernel fix-up) adds them. More work units, but s partial tiles of FP32 written and read. This is why cuBLAS wants workspace.
  • Stream-K (Osama, Merrill, Cecka, Garland and Owens, January 2023): instead of tiles, divide the total MAC-loop iterations evenly among the SMs; an SM may finish one tile's K loop half-way and start the next, and tiles split between SMs are fixed up through a small workspace. The paper reports "a peak speedup of up to 14× and 6.7×" and more consistent performance "across 32,824 GEMM problem geometries than ... CUTLASS and cuBLAS", "from a single tile size configuration per floating-point precision" ({{arXiv 2301.03598|https://arxiv.org/abs/2301.03598}}) paper. In practice it is used as a hybrid: whole tiles data-parallel for the full waves, Stream-K for the remainder.

Same bits only on the same GPU. Split-K and Stream-K change the order in which partial sums are added, and the heuristic picks the schedule from the GPU it sees. So cuBLAS promises bitwise-identical results from run to run only for one toolkit version on GPUs with the same architecture and the same number of SMs (cuBLAS documentation, CUDA 13.4, "Results reproducibility") vendor. An H100 PCIe (114 SMs) and an H100 SXM (132 SMs), or a MIG slice and a whole GPU, may legitimately disagree in the last bits; why that is harmless, and how to test with a tolerance instead, is in {{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}}, section 5.

Persistent kernels make these schedules possible: instead of launching one CTA per tile, launch about one CTA per SM (or per cluster) and let each loop over work units handed out by a tile scheduler. That also lets a CTA start loading the next tile while its epilogue stores the last one. CUTLASS 4.8.0 ships the schedulers as headers you can read: sm90_tile_scheduler_stream_k.hpp and sm100_tile_scheduler_stream_k.hpp in include/cutlass/gemm/kernel/, and example 74_blackwell_gemm_streamk vendor.

Go deeper: the {{GEMM scheduler|#t-sched}} tab lays one GEMM onto the SMs of five GPUs under the three schedules and animates the timeline, with the work, waves and extra traffic of each.

4. cuDNN: a graph in, an engine out

cuDNN started as a list of functions (one call per convolution algorithm). Since version 8 its main interface is a graph API: you describe a small computation graph (tensors with shapes, strides and types; operations such as matmul, pointwise, reduction, normalisation, convolution, scaled dot-product attention), and cuDNN looks for an engine that can run the whole graph as one fused kernel or a few. Some engines are prebuilt ("Pre-Compiled Single Operation Engines"); others are "runtime fusion engines that generate the kernel (or kernels) at runtime based on the graph pattern" ({{cuDNN Graph API|https://docs.nvidia.com/deeplearning/cudnn/frontend/latest/developer/graph-api.html}}) vendor. The workflow, from the cuDNN frontend's Python API (version 1.30.0 with cuDNN 9.27.0.42, installed in the image; method names read from the module) compiled here:

g = cudnn.pygraph(...)                # describe the computation
o, stats = g.sdpa(q, k, v, ...)         # or g.matmul, g.pointwise, g.rmsnorm, g.conv_fprop ...
g.validate(); g.build_operation_graph()
g.create_execution_plans([cudnn.heur_mode.A, cudnn.heur_mode.FALLBACK])   # heuristics rank engine configs
g.check_support(); g.build_plans()      # runtime-fusion engines compile here
g.execute(variant_pack, workspace, handle)

The heuristic modes the module exposes are A, B, FALLBACK and OPENSOURCE; creating a handle without a GPU fails with "cudnnHandle Create failed cudaGetDeviceCount(&count) != cudaSuccess" not run here. The pattern is the same as cuBLASLt (describe, ask a heuristic, run a plan), with the extra step that a plan may be compiled when you build it, so the first call of a new shape can be slow; frameworks cache plans by shape.

cuDNN as PyTorch's attention

F.scaled_dot_product_attention has four CUDA backends: FlashAttention, memory-efficient attention, the math fallback and cuDNN. In PyTorch 2.14.1 the default order is flash, efficient, math, cuDNN, but on compute capability 9.x and 10.x (H100, B200, B300) with cuDNN newer than 9.15.0 the order is reset to cuDNN first, then flash, efficient, math; the environment variable TORCH_CUDNN_SDPA_DEPRIORITIZED=1 undoes it. cuDNN's attention then accepts head dimensions up to 256 on those GPUs (newer than cuDNN 9.22) in multiples of 8 ({{sdp_utils.cpp|https://github.com/pytorch/pytorch/blob/v2.14.1/aten/src/ATen/native/transformers/cuda/sdp_utils.cpp}}, {{Context.h|https://github.com/pytorch/pytorch/blob/v2.14.1/aten/src/ATen/Context.h}}) vendor. An RTX 5090 (compute capability 12.0) is not in that list, so it keeps the flash-first order. To see which backend ran, look for the kernel name in a trace, or force one with torch.nn.attention.sdpa_kernel([SDPBackend.CUDNN_ATTENTION]) and compare. How FlashAttention itself works is on {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}.

Corrected from the old page: it said cuDNN is the "backend of F.scaled_dot_product_attention on Hopper/Blackwell". That holds for datacenter Hopper and Blackwell in PyTorch 2.14.1 under the version condition above; consumer Blackwell (sm_120) and Ampere still try FlashAttention first.
