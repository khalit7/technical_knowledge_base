6. TMA, barriers and warp specialisation: keeping the tensor cores fed

An Ampere kernel moves its tiles with cp.async: every thread computes addresses and issues 16-byte copies, 2,048 of them per K slice for our 128 × 128 tile (the instruction itself, and why it bypasses registers, is on {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}}, section 6). Hopper's Tensor Memory Accelerator (TMA) replaces that with one instruction from one thread: "copy this box of this tensor into shared memory", described by a tensor map, and the bytes that land are counted on an mbarrier (a shared-memory barrier that also counts bytes).

A CUtensorMap is a 128-byte opaque object (sizeof 128, alignment 128, printed by our program) holding the tensor's base address, sizes and strides (up to five dimensions), the box to copy, the swizzle mode, the L2 promotion and the out-of-bounds fill. It is built on the host by the driver function cuTensorMapEncodeTiled and passed to the kernel as a const __grid_constant__ parameter. Out-of-bounds elements of a box are filled with "zero or a special NaN constant" (the oobFill argument, documented in CUDA 13.4.2's cuda.h) vendor, which is why TMA kernels need no edge masking for ragged M, N or K.

A pipeline of stages, and who works on it

Shared memory is cut into stages, each holding one K slice of A and B. With 128 × 256 tiles and 64-wide K slices in BF16, a stage is (128 + 256) × 64 × 2 bytes = 48 KB, so an H100 block (227 KB) fits 4 stages and an RTX 5090 block (99 KB) only 2 derived (limits from the CUDA Programming Guide; on the RTX the epilogue's shared memory has to fit too, so real kernels there use smaller tiles). Each stage has two barriers: full (the TMA bytes have landed) and empty (the MMAs that read it are done). The producer waits on empty and issues TMA; the consumers wait on full, issue MMAs and arrive on empty. With 3 or 4 stages, three or four loads are in flight while the tensor cores work (Fig. 3's Hopper mode plays one round).

Fig. 3 follows one thread block computing one 128 × 128 output tile in BF16 with FP32 accumulation, one 64-wide K slice at a time, as an Ampere, a Hopper and a datacenter Blackwell kernel would issue it: global memory on the left, the shared-memory stages as glass plates (each with its full and empty barrier), the tensor core, registers and, on Blackwell, tensor memory; the warps below, lit when they work. Play one generation, then predict the counters of the next before you switch. The counters are per K slice and follow from the instruction shapes derived; they reproduce by construction the counts compiled for Triton's 128 × 128 × 32 tile in the CUDA root (64 HMMA per warp on sm_80, 4 HGMMA on sm_90a).

  1. The tile. One CTA of 128 threads (4 warps) owns a 128 × 128 FP32 accumulator tile; each warp holds a 64 × 64 quarter of it in registers. K is consumed 64 at a time, through 3 stages.
  2. Copy the next slice: cp.async. Every thread issues 16-byte global-to-shared copies for the slice after this one: (128 × 64 + 128 × 64) BF16 = 32 KB = 2048 copies, 16 per thread (LDGSTS): the swarm of small dots.
  3. Wait, then __syncthreads(). cp.async.wait_group and a block barrier make the current slice visible to all warps.
  4. ldmatrix into fragments. Each warp loads its A and B fragments from shared memory with ldmatrix.x4 (LDSM), already in the lane pattern mma.sync wants: 128 per CTA.
  5. mma.sync, 512 times. m16n8k16 instructions: (128/16) × (128/8) × (64/16) = 512 per CTA, 128 per warp, each reading and writing register fragments.
  6. Next slice. The copies issued in step 2 have been landing meanwhile; with 3 stages, two slices are always in flight. For K = 4,096 this repeats 64 times.
  7. Epilogue. Each thread converts its 128 accumulator registers and stores them (directly, or through shared memory for coalescing).
  1. The tile. Three warpgroups (384 threads): one producer that only copies, two consumers that each own a 64 × 128 half of the accumulator, 64 registers per thread. Four stages.
  2. TMA: one thread, two instructions. A single producer thread issues two cp.async.bulk.tensor loads (the A slice and the B slice) from tensor maps; the stage's mbarrier expects 32 KB: two large dots instead of a swarm.
  3. Consumers wait on "full". The consumers spin on the stage barrier until its transaction count reaches zero: all bytes have landed, swizzled.
  4. wgmma, 8 times, asynchronously. Each consumer warpgroup issues m64n128k16 four times (64/16), A and B read from shared memory by descriptor: 8 per CTA. The threads do not wait for them.
  5. Release the stage. wgmma.wait_group, then the consumers arrive on the stage's "empty" barrier; the producer, already waiting, refills it.
  6. Four stages in flight. The producer runs up to 4 stages ahead; setmaxnreg gave it 40 registers and the consumers 232.
  7. Epilogue. The consumers write their accumulators to shared memory (stmatrix), then one TMA store sends the tile to global memory.
  1. The tile. The accumulator lives in tensor memory: 128 lanes × 128 columns of FP32 = 64 KB of the SM's 256 KB. No thread holds it in registers.
  2. TMA, as on Hopper. One thread of the TMA warp issues two tensor loads into a stage and arms its barrier.
  3. One thread issues tcgen05.mma, 4 times. 128 × 128 × 16 per instruction, (64/16) = 4 per slice, operands read from shared memory by descriptor, results accumulated in TMEM.
  4. tcgen05.commit frees the stage. The commit arrives on the stage's barrier when those MMAs finish; the TMA warp refills it. No warp ever waited on the math.
  5. Next slices. 64 slices for K = 4,096, four stages deep; still one issuing thread.
  6. The epilogue reads TMEM. The 4 epilogue warps copy the accumulator out with tcgen05.ld (LDTM), 32 TMEM lanes per warp.
  7. Store, while the next tile starts. Registers to shared memory, then a TMA store; meanwhile the MMA warp can already accumulate the next tile into another 128 TMEM columns.

MMA instructions per K slice fall from 512 to 8 to 4, the threads that issue them from 128 to one warpgroup per half-tile to a single thread, and the accumulator registers per thread from 128 to 64 to none; each step frees threads, on Hopper for the producer and the epilogue, on Blackwell for whole epilogue warps that run while the next tile's MMAs proceed.

Warp specialisation: registers follow the work

Once copies are one instruction, the warps that issue them need almost no registers, while the MMA warps need many for accumulators. Hopper's setmaxnreg moves registers between warpgroups at run time. In CUTLASS's Hopper example 48, compiled for sm_90a, the producer warpgroup drops to 40 registers and the two consumer warpgroups rise to 232 compiled here; the budget closes exactly: 128 threads × 40 + 256 × 232 = 64,512 of the SM's 65,536 registers derived.

Example 48's SASS (the warp-specialised structure, instruction by instruction)

CUTLASS's own Hopper example 48 is a TF32 GEMM with a 128 × 128 × 32 tile and a 4 × 2 cluster; it launches with 168 registers, the cap for 384 threads. Compiled for sm_90a its SASS shows the whole structure compiled here: the producer warpgroup executes USETMAXREG.DEALLOC.CTAPOOL 0x28 (down to 40 registers), the consumer warpgroups USETMAXREG.TRY_ALLOC.CTAPOOL 0xe8 (up to 232), with 8 HGMMA.64x128x8.F32.TF32 instructions, UTMALDG for the loads and 51 barrier operations.

CUTLASS calls the two arrangements of consumers KernelTmaWarpSpecializedCooperative (both consumer warpgroups on one tile) and ...Pingpong (they alternate tiles, so one runs its epilogue while the other runs MMAs). FlashAttention-3 is built the same way ({{arXiv 2407.08608|https://arxiv.org/abs/2407.08608}}) and reaches up to 740 TFLOPS in FP16 on an H100, 75% of peak (the hardware side: {{GPU architecture|n:3c65c17b0d0d810682aae39bd614ec64}}, section 8); its algorithm is on {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}.

7. CUTLASS and CuTe: the open-source way to build these kernels

CUTLASS is NVIDIA's open-source, header-only C++ template library for GEMM, convolution and attention; version 4.8.0 (changelog dated 2026-09-17, published on GitHub on September 22, {{releases|https://github.com/NVIDIA/cutlass/releases}}) vendor, with the Python CuTe DSL as nvidia-cutlass-dsl 4.8.0. Where cuBLAS gives you a fixed menu, CUTLASS gives you the parts: you choose types, layouts, tile and cluster shapes, the kernel schedule and the epilogue, and the compiler builds that one kernel. This is how the custom GEMMs of the last few years were made: grouped GEMMs for mixture-of-experts, GEMMs with dequantisation in the mainloop, block-scaled FP8 and FP4, FlashAttention-3.

Three layers: a collective mainloop (the K loop: TMA, barriers, MMAs), a collective epilogue (what happens to the tile afterwards; CUTLASS's epilogue visitor tree lets you compose bias, activations, scaling, reductions and extra outputs as a tree of nodes, in include/cutlass/epilogue/fusion/sm90_visitor_*.hpp and the sm100 and sm120 equivalents), and a kernel with its tile scheduler (section 3). The builders choose the tensor-core instruction, the swizzled shared-memory layouts and the stage count from the architecture tag.

CuTe: layouts from zero

Underneath CUTLASS 3 and 4 is CuTe, a small algebra that describes every arrangement of data and threads in one notation. A layout is a shape and a stride: (4,8):(1,4) is a 4 × 8 array where moving one step down a column adds 1 to the offset and one step along a row adds 4 (column-major); (4,8):(8,1) is the row-major version; (4,8):(1,5) pads each column by one element, the classic way to dodge shared-memory bank conflicts. A layout is a function from coordinates (or a single index, counted with the leftmost mode fastest) to an offset, and shapes can nest: ((2,2),(2,4)):((1,8),(2,16)) is still 4 × 8, but each mode is itself two modes, which is how a tile of tiles is written.

Four operations do almost all the work, and the page's JavaScript implements them following include/cute/layout.hpp; every case below was checked against CuTe's own printed result, compiled and run in the image (21 cases, 6,326 values, 0 differences) compiled here:

  • Composition A ∘ B: use B to choose coordinates, A to turn them into offsets. (6,2):(8,2) ∘ (4,3):(3,1) = ((2,2),3):((24,2),8), the example in CuTe's documentation.
  • Logical divide by a tiler: split a layout into (tile, rest). An 8 × 8 column-major matrix divided by 2 × 4 tiles is ((2,4),(4,2)):((1,2),(8,32)); zipped_divide regroups the same thing as ((inside a tile), (which tile)), which is how a kernel picks its CTA's tile: local_tile.
  • Complement (the layout that fills the holes) and products (blocked_product, raked_product: repeat a layout over a grid, to lay threads or values over a tile); examples in the closed block below and the Layout lab.
Complement and products, by example

complement((2,2):(1,6), 24) = (3,2):(2,12): the offsets 0 to 23 that (2,2):(1,6) misses, as a layout. blocked_product repeats a layout so each copy stays contiguous (a block of values per thread); raked_product interleaves the copies (values of one thread spread across the tile). Both are presets in the {{Layout lab|#t-layout}}, checked against CuTe.

Same 4 × 8 shape, four strides: the stride alone decides where each element lives

Two more ideas complete the picture. A swizzle Sw<B,M,S> XORs B bits of an offset into B lower bits: CUTLASS's 128-byte Hopper shared-memory atom for 16-bit types is Sw<3,4,3> o (8,64):(64,1) on byte addresses, which XORs a row's 16-byte chunk index with the row number modulo 8, so eight rows read in the same column land in eight different 16-byte bank groups (the bank arithmetic is on {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}}). Switch the swizzle on the right and watch the outlined column.

Without a swizzle, column 0 of eight rows hits one bank group eight times; Sw<3,3,3> spreads it over all eight

Eight rows of 64 BF16 values (128 bytes each) in shared memory. Each cell is a 16-byte chunk, coloured by the group of four 4-byte banks it lands in; reading one column of chunks down the eight rows (what an MMA operand load does) is conflict-free only if the eight colours differ. CuTe's Sw<3,3,3> is in 16-bit elements; on byte addresses it is Sw<3,4,3>, CUTLASS's 128-byte atom.

A thread-value (TV) layout maps (thread, value) to a position in a tile: the mma.sync fragment map in section 5 is CuTe's ((4,8),(2,2)):((32,1),(16,8)). With these, a CUTLASS kernel reads as: local_tile the global tensors to this CTA's tile, partition it across threads with a tiled copy and a tiled MMA (make_tiled_mma, partition_A), then copy and gemm on the pieces.

CuTe DSL writes the same thing in Python, compiled just in time; FlashAttention-4 and many of CUTLASS's newest examples are written in it. Installed here without a GPU, it printed the same layouts as the C++ (((2,2),3):((24,2),8) for the composition above) compiled here.
