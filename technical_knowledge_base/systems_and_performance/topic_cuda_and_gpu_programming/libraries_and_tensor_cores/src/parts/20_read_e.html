6. TMA, barriers and warp specialisation: keeping the tensor cores fed

An Ampere kernel moves its tiles with cp.async: every thread computes addresses and issues 16-byte copies, 2,048 of them per K slice for our 128 × 128 tile (the instruction itself, and why it bypasses registers, is on {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}}, section 6). Hopper's Tensor Memory Accelerator (TMA) replaces that with one instruction from one thread: "copy this box of this tensor into shared memory", described by a tensor map.

The descriptor, built on the host

A CUtensorMap is a 128-byte opaque object (sizeof 128, alignment 128, printed by our program) holding the tensor's base address, sizes and strides (up to five dimensions), the box to copy, the swizzle mode, the L2 promotion and the out-of-bounds fill. It is built by the driver function cuTensorMapEncodeTiled and passed to the kernel as a const __grid_constant__ parameter. Our program encodes a 64 × 64 BF16 box of an 8,192 × 4,096 matrix with CU_TENSOR_MAP_SWIZZLE_128B; it compiles compiled here, and run against the toolkit's driver stub every driver call returns 34, CUDA_ERROR_STUB_LIBRARY not run here. Out-of-bounds elements of a box are filled with "zero or a special NaN constant" (the oobFill argument, documented in CUDA 13.4.2's cuda.h) vendor, which is why TMA kernels need no edge masking for ragged M, N or K. Error 34 is CUDA_ERROR_STUB_LIBRARY in the same header.

A pipeline of stages

Shared memory is cut into stages, each holding one K slice of A and B. With 128 × 256 tiles and 64-wide K slices in BF16, a stage is (128 + 256) × 64 × 2 bytes = 48 KB, so an H100 block (227 KB) fits 4 stages and an RTX 5090 block (99 KB) only 2 derived (limits from the CUDA Programming Guide; on the RTX the epilogue's shared memory has to fit too, so real kernels there use smaller tiles). Each stage has two barriers: full (the TMA bytes have landed) and empty (the MMAs that read it are done). The producer waits on empty and issues TMA; the consumers wait on full, issue MMAs and arrive on empty. With 3 or 4 stages, three or four loads are in flight while the tensor cores work.

Warp specialisation and the register hand-off

Once copies are one instruction, the warps that issue them need almost no registers, while the MMA warps need many for accumulators. Hopper's setmaxnreg moves registers between warpgroups at run time. CUTLASS's own Hopper example 48 (a TF32 GEMM, 128 × 128 × 32 tile, a 4 × 2 cluster; 168 registers at launch, the cap for 384 threads), compiled for sm_90a, shows the whole structure in its SASS compiled here: the producer warpgroup executes USETMAXREG.DEALLOC.CTAPOOL 0x28 (down to 40 registers), the consumer warpgroups USETMAXREG.TRY_ALLOC.CTAPOOL 0xe8 (up to 232), with 8 HGMMA.64x128x8.F32.TF32 instructions, UTMALDG for the loads and 51 barrier operations. The budget closes exactly: 128 threads × 40 + 256 × 232 = 64,512 of the SM's 65,536 registers derived. CUTLASS calls the two arrangements of consumers KernelTmaWarpSpecializedCooperative (both consumer warpgroups on one tile) and ...Pingpong (they alternate tiles, so one runs its epilogue while the other runs MMAs). FlashAttention-3 is built the same way ({{arXiv 2407.08608|https://arxiv.org/abs/2407.08608}}); its algorithm is on {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}.

7. CUTLASS and CuTe: the open-source way to build these kernels

CUTLASS is NVIDIA's open-source, header-only C++ template library for GEMM, convolution and attention; version 4.8.0 is dated 2026-09-17 in its changelog and was published on GitHub on September 22 ({{releases|https://github.com/NVIDIA/cutlass/releases}}) vendor, with the Python CuTe DSL on PyPI as nvidia-cutlass-dsl 4.8.0. Where cuBLAS gives you a fixed menu, CUTLASS gives you the parts: you choose types, layouts, tile and cluster shapes, the kernel schedule and the epilogue, and the compiler builds that one kernel. This is how the custom GEMMs of the last few years were made: grouped GEMMs for mixture-of-experts, GEMMs with dequantisation in the mainloop, block-scaled FP8 and FP4, FlashAttention-3.

Three layers: a collective mainloop (the K loop: TMA, barriers, MMAs), a collective epilogue (what happens to the tile afterwards; CUTLASS's epilogue visitor tree lets you compose bias, activations, scaling, reductions and extra outputs as a tree of nodes, in include/cutlass/epilogue/fusion/sm90_visitor_*.hpp and the sm100 and sm120 equivalents), and a kernel with its tile scheduler (section 3). The builders choose the tensor-core instruction, the swizzled shared-memory layouts and the stage count from the architecture tag. CuTe: layouts from zero

Underneath CUTLASS 3 and 4 is CuTe, a small algebra that describes every arrangement of data and threads in one notation. A layout is a shape and a stride: (4,8):(1,4) is a 4 × 8 array where moving one step down a column adds 1 to the offset and one step along a row adds 4 (column-major); (4,8):(8,1) is the row-major version; (4,8):(1,5) pads each column by one element, the classic way to dodge shared-memory bank conflicts. A layout is a function from coordinates (or a single index, counted with the leftmost mode fastest) to an offset, and shapes can nest: ((2,2),(2,4)):((1,8),(2,16)) is still 4 × 8, but each mode is itself two modes, which is how a tile of tiles is written.

Four operations do almost all the work, and the page's JavaScript implements them following include/cute/layout.hpp; every case below was checked against CuTe's own printed result, compiled and run in the image (21 cases, 6,326 values, 0 differences) compiled here:

  • Composition A ∘ B: use B to choose coordinates, A to turn them into offsets. (6,2):(8,2) ∘ (4,3):(3,1) = ((2,2),3):((24,2),8), the example in CuTe's documentation.
  • Complement: the layout that fills the holes. complement((2,2):(1,6), 24) = (3,2):(2,12).
  • Logical divide by a tiler: split a layout into (tile, rest). An 8 × 8 column-major matrix divided by 2 × 4 tiles is ((2,4),(4,2)):((1,2),(8,32)); zipped_divide regroups the same thing as ((inside a tile), (which tile)), which is how a kernel picks its CTA's tile: local_tile.
  • Products (blocked_product, raked_product): repeat a layout over a grid, used to lay threads or values over a tile.

Two more ideas complete the picture. A swizzle Sw<B,M,S> XORs B bits of an offset into B lower bits: CUTLASS's 128-byte Hopper shared-memory atom for 16-bit types is Sw<3,4,3> o (8,64):(64,1) on byte addresses, which XORs a row's 16-byte chunk index with the row number modulo 8, so eight rows read in the same column land in eight different 16-byte bank groups (the bank arithmetic is on {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}}). A thread-value (TV) layout maps (thread, value) to a position in a tile: the mma.sync fragment map in section 5 is CuTe's ((4,8),(2,2)):((32,1),(16,8)). With these, a CUTLASS kernel reads as: local_tile the global tensors to this CTA's tile, partition it across threads with a tiled copy and a tiled MMA (make_tiled_mma, partition_A), then copy and gemm on the pieces.

CuTe DSL writes the same thing in Python. Installed in the image without a GPU, it printed the same layouts as the C++ (((2,2),3):((24,2),8) for the composition above) and compiled a small kernel to PTX for sm_90a and a cubin, through its own bundled NVVM ("release 13.4, V13.4.59") compiled here; running it needs a GPU not run here. FlashAttention-4 and many of CUTLASS's newest examples are written in it.
