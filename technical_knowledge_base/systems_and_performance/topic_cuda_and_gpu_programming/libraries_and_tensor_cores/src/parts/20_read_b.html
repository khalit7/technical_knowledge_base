1. Use a library first, and know what it is doing for you

A GEMM that runs near the tensor cores' peak is not one clever loop: it is the six ingredients of the hero working together (tiles staged in swizzled shared memory, the generation's tensor-core instruction, an asynchronous copy pipeline, warp roles, a schedule fitted to the SM count, a fused epilogue), each taught in the section named in the hero.

How far does hand-writing get you? Simon Boehm's worklog builds an FP32 matmul in ten steps on an RTX A6000 and ends at 21,779.3 GFLOP/s against cuBLAS's 23,249.6: 93.7%, without tensor cores at all ({{How to Optimize a CUDA Matmul Kernel|https://siboehm.com/articles/22/CUDA-MMM}}, December 2022) independent; on the M1 the CUDA root's Kernel lab reaches 3,371 GFLOP/s against the library's 4,048 (runs of {{Topic: cuda-and-gpu-programming|n:3c65c17b0d0d81c39f34d5e070d783c1}}'s Kernel lab, taught in {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}, section 1) measured on M1 Pro. With tensor cores the gap is wider, because the instruction, the pipeline and the warp roles change every generation. The hand-written ladder, step by step, is on {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}; this page is about the libraries at the top of it and the instructions at the bottom.

2. cuBLAS and cuBLASLt: the call, the heuristic, the epilogue

The classic API, and the column-major trap

cuBLAS follows Fortran BLAS: matrices are column-major (consecutive elements go down a column). PyTorch tensors are row-major. A row-major M × K matrix has exactly the bytes of a column-major K × M matrix, its transpose, so libraries compute YT = WT XT and never copy anything: the classic call is cublasGemmEx(handle, opA, opB, m, n, k, α, A, typeA, lda, B, typeB, ldb, β, C, typeC, ldc, computeType, algo) with A = W, B = X and m = 14,336, n = 8,192. Getting lda or an op flag wrong is the most common first cuBLAS bug: the call succeeds and computes the wrong product, so check against torch.matmul on small sizes first. The tn/nt letters in kernel names below are these op flags.

cuBLASLt: descriptors, a ranked list, and a workspace

cuBLASLt (the "lightweight" API) splits the call into objects: a matmul descriptor (compute type, transposes, epilogue, scale pointers), a layout per matrix (type, rows, columns, leading dimension, batch), and a preference (how much scratch workspace memory you allow). cublasLtMatmulAlgoGetHeuristic then returns a ranked list of algorithms for exactly this problem on exactly this GPU, and cublasLtMatmul runs the one you pass. Workspace matters: some algorithms (split-K, section 3) need scratch memory, and the heuristic only offers those that fit the workspace you declared. Too little workspace silently removes the faster choices.

Epilogues: fusion you get for free


An epilogue is what the kernel does to an output tile after the K loop and before the tile leaves the chip. cuBLASLt's menu, read from cublasLt.h in CUDA 13.4.2 vendor:

What it is worth. Unfused, the running example writes Y (BF16), reads it for the bias, writes it, reads it for GELU: 4 × 2 bytes × 8,192 × 14,336 = 0.94 GB of extra traffic. On an H100 that is about 0.28 ms at 3.35 TB/s, against about 1.34 ms for the GEMM itself at the ~720 TFLOP/s that SemiAnalysis measured for BF16 GEMMs ({{SemiAnalysis, Dec 2024|https://semianalysis.com/2024/12/22/mi300x-vs-h100-vs-h200-benchmark-part-1-training/}}) derived: about 21% on top, gone when the epilogue is fused. When PyTorch takes the cuBLASLt path (PyTorch 2.14.1 source)


torch.mm and matmul go to classic cuBLAS by default on NVIDIA GPUs (blasDefaultBackend() returns Cublas except on AMD Instinct; torch.backends.cuda.preferred_blas_library("cublaslt") switches); addmm, which is what F.linear with a bias calls, takes the cuBLASLt path with the bias in the epilogue when the bias is 1-D and contiguous, the output 2-D and contiguous, β = 1, the type FP32, FP16, BF16 or FP64, and neither matrix dimension is 1 (isInputCompliesAddmmCudaLt in {{aten/src/ATen/native/cuda/Blas.cpp|https://github.com/pytorch/pytorch/blob/v2.14.1/aten/src/ATen/native/cuda/Blas.cpp}}) vendor; DISABLE_ADDMM_CUDA_LT=1 turns it off. The GELU epilogue is reached through torch._addmm_activation(..., use_gelu=True), which compilers emit; an eager F.gelu after F.linear is a separate kernel.




Inside the box: what cuBLAS ships


cuBLAS has no GEMM "algorithm" in the textbook sense: it ships prebuilt kernels, one per combination of data types, transposes, tile shape, cluster shape, epilogue and K-splitting strategy, compiled separately for each GPU architecture, and the heuristic picks one at run time. Kernel text sections per architecture target in libcublasLt, as cuobjdump -ltext lists them; the hatched part has names replaced by an opaque hash (for example _ZN4xmma-33604). Hopper's tensor-core GEMMs sit in the "sm_90a" build because wgmma only exists there (section 5); the SASS scan of every listed kernel finds HGMMA in 1,540 Hopper kernels.


Hopper's GEMM kernels keep readable names, and the names are a specification. Of the 2,920 sm90_xmma_gemm_* kernels, 744 write an auxiliary output, 420 apply a GELU derivative and 1,041 are split-K variants: each epilogue and each splitting strategy is a separately compiled kernel. Reading of the name: ours, from the patterns across all 2,920 names; NVIDIA does not document it unconfirmed. The tile-size field is unambiguous: the most common tiles are 64 × 64 × 64, then 128 × 128, 64 × 128, 128 × 64 (× 64), with the largest 128 × 256 and 256 × 128.


How to see which kernel ran: the kernel name appears in an Nsight Systems timeline or a torch.profiler trace (the method is on {{Profiling and correctness|n:3c65c17b0d0d813da895ffee55b0457c}}). If a GEMM in your trace is named ..._splitK... or comes with a separate splitKreduce_kernel (402 of those per architecture in this build), the heuristic split K; if a bias add and a GELU follow every GEMM as separate kernels, the epilogue was not fused.


What the Blackwell builds contain (CUTLASS 3.x names, FP64 emulation, PTX for the RTX 50 series)


Scanning the SASS of every listed kernel (the {{Instruction atlas|#t-atlas}} tab has the table) finds tcgen05 instructions in only 8 kernels of the sm_100 build: integer MMAs (UTCIMMA) in kernels named cublasLt_fused_imma_dgemm_*, which by their name emulate FP64 GEMMs with INT8 arithmetic. The Blackwell tensor-core GEMMs are in the file only as names: 5,015 distinct strings in CUTLASS 3.x's naming scheme (4,679 for sm100, 240 for sm103, 96 for sm120), such as

Consumer Blackwell is different again: its listed SASS has FP8 QMMA in 375 kernels but HMMA in only 20, and the library also carries 5,588 PTX kernels for sm_120 containing 14,544 mma.sync instructions (and no wgmma or tcgen05), which the CUDA driver just-in-time compiles to SASS on an RTX 50-series GPU before first use and keeps in its compute cache (standard handling of PTX without matching SASS; the mechanism is on {{The compiler stack|n:3f05c17b0d0d81ddbc00fac9e8a2ff89}}) compiled here. Expect a one-time compilation cost the first time after a driver or library change.
