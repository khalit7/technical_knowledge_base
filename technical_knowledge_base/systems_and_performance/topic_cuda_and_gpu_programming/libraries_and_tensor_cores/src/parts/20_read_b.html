1. Use a library first, and know what it is doing for you

A GEMM that runs near the tensor cores' peak is not one clever loop. It is six things working together, and every later section of this page is one of them:

  1. Tiles on chip: each thread block computes one output tile (say 128 × 256) and stages slices of A and B in shared memory, laid out (swizzled) so reads hit different banks (section 7; the bank rules are on {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}}).
  2. The right tensor-core instruction for the generation, with operands arranged in exactly the register or shared-memory layout it expects (section 5).
  3. An asynchronous pipeline: copies for the next K slice are in flight while the tensor cores chew on this one (cp.async on Ampere, TMA on Hopper and Blackwell; section 6).
  4. Warp roles on Hopper and Blackwell: a producer warp only issues copies, consumer warps only issue MMAs, and registers are moved from one to the other (section 6).
  5. A tile shape and schedule that fit this problem shape to this GPU's SM count, so the last wave is not mostly idle (section 3).
  6. An epilogue: bias, activation, scaling and conversion done while the tile is still on chip, instead of writing it out and reading it back (sections 2 and 7).

How far does hand-writing get you? Simon Boehm's worklog builds an FP32 matmul in ten steps on an RTX A6000 and ends at 21,779.3 GFLOP/s against cuBLAS's 23,249.6: 93.7%, without tensor cores at all ({{How to Optimize a CUDA Matmul Kernel|https://siboehm.com/articles/22/CUDA-MMM}}, December 2022) independent. The CUDA root's Kernel lab reproduces the same climb on the M1: the best hand-written Metal kernel reached 3,371 GFLOP/s against MLX's library matmul at 4,048 ({{Topic: cuda-and-gpu-programming|n:3c65c17b0d0d81c39f34d5e070d783c1}}, Kernel lab tab) measured on M1 Pro. With tensor cores the gap is wider, because ingredients 2 to 4 change every generation. The full hand-written ladder, step by step, is on {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}; this page is about the libraries at the top of it and the instructions at the bottom.

2. cuBLAS and cuBLASLt: the call, the heuristic, the epilogue

The classic API, and the column-major trap

cuBLAS follows Fortran BLAS: matrices are column-major (consecutive elements go down a column). PyTorch tensors are row-major. A row-major M × K matrix has exactly the bytes of a column-major K × M matrix, its transpose, so libraries compute YT = WT XT and never copy anything: the classic call is cublasGemmEx(handle, opA, opB, m, n, k, α, A, typeA, lda, B, typeB, ldb, β, C, typeC, ldc, computeType, algo) with A = W, B = X and m = 14,336, n = 8,192. Getting lda or an op flag wrong is the most common first cuBLAS bug: the call succeeds and computes the wrong product. The tn/nt letters in kernel names below are these op flags.

cuBLASLt: descriptors, a ranked list, and a workspace

cuBLASLt (the "lightweight" API) splits the call into objects: a matmul descriptor (compute type, transposes, epilogue, scale pointers), a layout per matrix (type, rows, columns, leading dimension, batch), and a preference (how much scratch workspace memory you allow). cublasLtMatmulAlgoGetHeuristic then returns a ranked list of algorithms for exactly this problem on exactly this GPU, and cublasLtMatmul runs the one you pass. Our program for the running example (src/cuda/host/lt_gelu_bias.cu, 50 lines) compiles against cuBLASLt 13.8 in the image compiled here; run without a GPU it stops at the first call that needs the driver:



Workspace matters: some algorithms (split-K, section 3) need scratch memory, and the heuristic only offers those that fit the workspace you declared. PyTorch 2.14.1 gives cuBLAS a default workspace of 32 MiB on compute capability 9.x to 12.x (Hopper and Blackwell) and about 8 MiB on older GPUs, overridable with CUBLAS_WORKSPACE_CONFIG, and sizes cuBLASLt's with CUBLASLT_WORKSPACE_SIZE ({{CublasHandlePool.cpp|https://github.com/pytorch/pytorch/blob/v2.14.1/aten/src/ATen/cuda/CublasHandlePool.cpp}}) vendor. Too little workspace silently removes the faster choices.


Epilogues: fusion you get for free


An epilogue is what the kernel does to an output tile after the K loop and before the tile leaves the chip. cuBLASLt's menu, read from cublasLt.h in CUDA 13.4.2 vendor:

When PyTorch uses it, from the PyTorch 2.14.1 source vendor: torch.mm and matmul go to classic cuBLAS by default on NVIDIA GPUs (blasDefaultBackend() returns Cublas except on AMD Instinct; torch.backends.cuda.preferred_blas_library("cublaslt") switches); addmm, which is what F.linear with a bias calls, takes the cuBLASLt path with the bias in the epilogue when the bias is 1-D and contiguous, the output 2-D and contiguous, β = 1, the type FP32, FP16, BF16 or FP64, and neither matrix dimension is 1 (isInputCompliesAddmmCudaLt in {{aten/src/ATen/native/cuda/Blas.cpp|https://github.com/pytorch/pytorch/blob/v2.14.1/aten/src/ATen/native/cuda/Blas.cpp}}); DISABLE_ADDMM_CUDA_LT=1 turns it off. The GELU epilogue is reached through torch._addmm_activation(..., use_gelu=True), which compilers emit; an eager F.gelu after F.linear is a separate kernel.


What it is worth. Unfused, the running example writes Y (BF16), reads it for the bias, writes it, reads it for GELU: 4 × 2 bytes × 8,192 × 14,336 = 0.94 GB of extra traffic. On an H100 that is about 0.28 ms at 3.35 TB/s, against about 1.34 ms for the GEMM itself at the ~720 TFLOP/s that SemiAnalysis measured for BF16 GEMMs ({{SemiAnalysis, Dec 2024|https://semianalysis.com/2024/12/22/mi300x-vs-h100-vs-h200-benchmark-part-1-training/}}) derived: about 21% on top, gone when the epilogue is fused. We cannot time that on an NVIDIA GPU here; the M1 shows the same effect with MLX, whose addmm also puts the bias inside the GEMM:




4,096 × 4,096 output, FP16, median of 3 runs (spread in the tooltip), load average 9.7 to 10.2 measured on M1 Pro. "Eager" evaluates the GEMM, the bias add and GELU as separate steps, and eager GELU is itself about eight elementwise kernels; "fused bias+GELU" is mx.compile (the GEMM, then one fused elementwise kernel); "bias in GEMM" is mx.addmm followed by a compiled GELU. Largest error against an FP32 reference: 0.003.


The lesson in the chart: the extra kernels cost a roughly fixed amount (they move the M × N output), so fusion matters most when K is small and the GEMM itself is short: at K = 256 the eager version is 3.7× the GEMM, at K = 4,096 it is 1.19×.


Inside the box: what cuBLAS ships


cuBLAS has no GEMM "algorithm" in the textbook sense: it ships prebuilt kernels, one per combination of data types, transposes, tile shape, cluster shape, epilogue and K-splitting strategy, compiled separately for each GPU architecture, and the heuristic picks one at run time. A surprise on Blackwell. Scanning the SASS of every listed kernel (the {{Instruction atlas|#t-atlas}} tab has the table) finds HGMMA in 1,540 Hopper kernels, but tcgen05 instructions in only 8 kernels of the sm_100 build: integer MMAs (UTCIMMA) in kernels named cublasLt_fused_imma_dgemm_*, which by their name emulate FP64 GEMMs with INT8 arithmetic. The Blackwell tensor-core GEMMs are in the file only as names: 5,015 distinct strings in CUTLASS 3.x's naming scheme (4,679 for sm100, 240 for sm103, 96 for sm120), such as




which reads as a block-scaled NVFP4 GEMM (E2M1 values, UE4M3 scales every 16 elements: vs16), a 256 × 128 tile on two SMs (2sm), a bias-then-GELU epilogue in BF16, and a Stream-K schedule (section 3). Of the sm100 names, 2,201 are Stream-K variants, 1,508 use the two-SM MMA and 1,936 carry a GELU epilogue compiled here. So on Blackwell cuBLAS ships CUTLASS-generated kernels, stored in a form cuobjdump does not list; how they are stored and loaded we could not determine unconfirmed. Consumer Blackwell is different again: its listed SASS has FP8 QMMA in 375 kernels but HMMA in only 20, and the library also carries 5,588 PTX kernels for sm_120 containing 14,544 mma.sync instructions (and no wgmma or tcgen05), which the CUDA driver just-in-time compiles to SASS on an RTX 50-series GPU before first use and keeps in its compute cache (standard handling of PTX without matching SASS; the mechanism is on {{The compiler stack|n:3f05c17b0d0d81ddbc00fac9e8a2ff89}}) compiled here. Expect a one-time compilation cost the first time after a driver or library change.


Hopper's GEMM kernels keep readable names, and the names are a specification. Of the 2,920 sm90_xmma_gemm_* kernels, 744 write an auxiliary output, 420 apply a GELU derivative and 1,041 are split-K variants: each epilogue and each splitting strategy is a separately compiled kernel. How to see which kernel ran: the kernel name appears in an Nsight Systems timeline or a torch.profiler trace (the method is on {{Profiling and correctness|n:3c65c17b0d0d813da895ffee55b0457c}}). If a GEMM in your trace is named ..._splitK... or comes with a separate splitKreduce_kernel (402 of those per architecture in this build), the heuristic split K; if a bias add and a GELU follow every GEMM as separate kernels, the epilogue was not fused.
