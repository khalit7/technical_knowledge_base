5. Tensor cores from the programmer's side: one instruction per generation

A tensor core computes D = A·B + C on a small tile in one instruction. What it is physically, and how many FLOPs per clock each generation does, is on {{GPU architecture|n:3c65c17b0d0d810682aae39bd614ec64}}. What changes for the programmer is three questions: who issues the instruction (one warp, four warps, one thread), where the operands live (registers, shared memory, tensor memory), and how the next operands arrive. Every generation answered them differently, which is why a Hopper kernel does not run on a Blackwell chip and why libraries ship a build per architecture.

mma.sync: one warp, everything in registers (Ampere onward)

mma.sync.aligned.m16n8k16.row.col.f32.bf16.bf16.f32 multiplies a 16 × 16 tile of A by a 16 × 8 tile of B into a 16 × 8 FP32 tile, as one instruction for the whole warp. No thread holds a row or a column: the 32 lanes each hold a scattered fragment: 4 registers of A (8 BF16 values), 2 of B (4 values) and 4 of C (4 floats), in a pattern fixed by the hardware. Click a lane to see which elements of C it owns (the map is computed by this page's CuTe algebra from CuTe's own SM80_16x8x16_F32F16F16F32_TN layout, ((4,8),(2,2)):((32,1),(16,8)), and checked value by value against CuTe's output compiled here):

So data cannot simply be copied from shared memory into registers row by row; it has to land in this pattern. ldmatrix does exactly that: each lane supplies the address of one 16-byte row, and the warp receives four 8 × 8 tiles already distributed as mma fragments (.trans transposes on the way). It compiles to LDSM.16.M88.4 and LDSM.16.MT88.4 on every target; the reverse, stmatrix (STSM.16.M88.4), used by epilogues, exists from sm_90 on compiled here.

FP4 rows need the a target, sm_120a (section 8). Hopper and datacenter Blackwell still run mma.sync, but it is not their fast path: Luo et al. measured mma at 62.9% of Hopper's tensor-core peak on average against 96.4% for wgmma FP16 (729.3 of 756.5 TFLOP/s on an H800 PCIe) ({{arXiv 2402.13499|https://arxiv.org/html/2402.13499v1}}) independent. And FP8 mma.sync is not even native there: ptxas unpacks the FP8 values to FP16 (F2FP.F16.E4M3.UNPACK_B, 12 of them) and issues two FP16 HMMAs.

And wmma? CUDA C++'s portable warp-matrix API (nvcuda::wmma::fragment, mma_sync on 16 × 16 × 16 tiles) compiles to the very same HMMA.16816.F32 on sm_80, sm_90a, sm_100a and sm_120 (the CUDA root's Compiler explorer, kernel k6) compiled here. The old page called it "portable but slow, ignore"; more precisely it is limited: its fragment layout is opaque, so you cannot load fragments with ldmatrix patterns or address individual accumulators, and it has no route to wgmma or tcgen05. Libraries use mma.sync and newer instructions directly.

Two corrections to the old page

FP8 did not "arrive" with Hopper's wgmma: the FP8 mma.sync needs sm_89 (ptxas on sm_80: "Feature 'mma with FP8 floating point type' requires .target sm_89 or higher"), so Ada (RTX 4090, L40S) has FP8 tensor cores too, and Hopper added the warpgroup FP8 path. And "5th generation tensor core" does not mean tcgen05: NVIDIA's RTX Blackwell whitepaper also calls the RTX 5090's tensor cores "5th Gen" (Appendix A), yet sm_120 rejects every tcgen05 instruction. Marketing generations, compute capabilities and instruction sets are three different numberings.

wgmma: four warps, operands from shared memory, asynchronous (Hopper only)

Hopper added the warpgroup: four consecutive warps (128 threads) issue one wgmma.mma_async together, for a 64 × N × 16 tile (N from 8 to 256 in steps of 8; K is 32 for FP8). B, and usually A, are not in registers at all: each is described by a 64-bit matrix descriptor (shared-memory start address, two strides, a swizzle mode) and the tensor core reads shared memory itself. The instruction is asynchronous: threads continue while it runs, and the code brackets it with wgmma.fence, wgmma.commit_group and wgmma.wait_group N (wait until at most N groups are outstanding), so the next tile's MMAs can be issued before the previous ones finish. The accumulators are still registers: a 64 × 256 FP32 tile spread over 128 threads is 128 registers per thread, and ptxas reports 154 registers per thread for our one-instruction m64n256k16 kernel (and 90 for m64n128k16) compiled here. In SASS it is HGMMA.64x128x16.F32 (FP8: QGMMA.64x128x32.F32.E4M3.E4M3), and for any other target ptxas refuses it: Instruction 'wgmma.fence' not supported on .target 'sm_100a'.

tcgen05: one thread, accumulators in tensor memory (datacenter Blackwell)

Blackwell's fifth-generation tensor core moved the accumulator out of the register file into tensor memory (TMEM): 512 columns × 128 lanes of 32-bit cells per SM, 256 KB, the same size as the register file ({{PTX ISA 9.4|https://docs.nvidia.com/cuda/parallel-thread-execution/index.html}}) vendor. A kernel allocates TMEM columns (a power of two, at least 32), and a single thread issues tcgen05.mma for a tile of up to 128 × 256 × 16 with operands read from shared memory through descriptors. Completion is signalled on a shared-memory barrier by tcgen05.commit, and the epilogue copies results from TMEM to registers with tcgen05.ld. The register file is free for the epilogue and for addressing: each of our tcgen05 kernels (one 128-row MMA whose accumulator stays in TMEM until an 8-column tcgen05.ld) uses 16 registers per thread, against 90 for the m64n128 wgmma one, whose 64 accumulators per thread must live in registers. With cta_group::2, one instruction spans the two SMs of a cluster pair, each holding half of the tile. What each piece compiles to compiled here:

Consumer Blackwell (RTX 5090, DGX Spark): back to mma.sync, plus FP4

The RTX 5090 (compute capability 12.0) and the GB10 in DGX Spark (12.1) ({{CUDA GPUs list|https://developer.nvidia.com/cuda-gpus}}) vendor share the Blackwell name with the B200 but not its tensor-core programming model. Compiled for sm_120 and sm_120a compiled here: no wgmma, no tcgen05, no TMEM; mma.sync as on Ampere, with native FP8 (QMMA.16832.F32.E4M3.E4M3) and, on sm_120a only, FP4 (QMMA.16832.F32.E2M1.E2M1) and block-scaled FP4 (OMMA.SF.16864.F32.E2M1.E2M1.E8, which also assembles for sm_121a); TMA and clusters, yes; the register hand-off setmaxnreg only with the a suffix. TMA multicast assembles on sm_120 but ptxas warns it "should be used on .target 'sm_90a/sm_100a/...' instead of .target 'sm_120' as this feature is expected to have substantially reduced performance", and the SASS contains no multicast copy, only a call through a function pointer (CALL.ABS.NOINC) where sm_90a has UTMALDG.2D.MULTICAST. So the old page's claim stands, now with compiler evidence: kernels for the 5090 look like Ampere and Ada kernels (register accumulators, ldmatrix, mma.sync) fed by TMA, and Hopper tutorials built on wgmma do not run on it.

The suffixes: sm_90a, sm_100f, sm_120

From compute capability 9.0 on, features that may not survive into the next generation are only available when compiling for an architecture-specific target with an a suffix, and such code "can only be run on the exact compute capability it was compiled for". From 10.0 on, a family-specific f target covers several: compute_100f runs on 10.0, 10.3 and 10.7, compute_120f on 12.0 and 12.1 ({{CUDA Programming Guide, compute capabilities|https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html}}) vendor. The compiler shows what that means compiled here: tcgen05 compiles for sm_100f, but the NVFP4 form with scale_vec::4X does not ("Feature '.scale_vec::4X' not supported on .target 'sm_100f'") while sm_100a and sm_103a accept it, as different SASS (UTCOMMA.4X against UTCOMMA.BLOCK16): a family target gets only what every member shares. Plain sm_120 rejects setmaxnreg and the FP4 mma kinds that sm_120a accepts. This is why every architecture-specific library build is separate, and why code compiled only for sm_90a (with no portable PTX alongside) will not run on a B200.

The same tile on three generations

One thread block computing one 128 × 128 output tile in BF16 with FP32 accumulation, one 64-wide K slice at a time, as an Ampere, a Hopper and a datacenter Blackwell kernel would issue it. The counters are per K slice and follow from the instruction shapes derived; they reproduce by construction the counts compiled for Triton's 128 × 128 × 32 tile in the CUDA root (64 HMMA per warp on sm_80, 4 HGMMA on sm_90a).

Read across the three: the MMA instructions per K slice fall from 512 to 8 to 4, the threads that must cooperate to issue them from 128 to 128 per warpgroup to 1, and the registers holding the accumulator from 128 per thread to 64 to none. Each step frees the SM's threads for something else: on Hopper for the producer and the epilogue, on Blackwell for whole epilogue warps running while the next tile's MMAs proceed.
