In one screen

Almost every FLOP of a training run is a matrix multiply (a GEMM, general matrix multiply: D = αAB + βC), and almost every GEMM you run is a kernel somebody else wrote: a library. This page is about those libraries and the hardware instructions they are built on, so that you can tell which one ran, why it was fast or slow, and when it is worth writing your own.

The running example

Y = GELU(X·W + b) in BF16 with FP32 accumulation, X = 8,192 tokens × 4,096 features, W = 4,096 × 14,336: the shape of the MLP up-projection of a Llama-3-8B-sized layer (config.json: hidden_size 4096, intermediate_size 14336). One forward call is 2 · 8,192 · 14,336 · 4,096 = 962.1 GFLOP derived. Llama itself uses SwiGLU, not GELU; we use GELU because cuBLASLt can apply it inside the GEMM, and SwiGLU is exactly the kind of fusion that pushes people to write their own kernel (section 9).

1. Use a library first, and know what it is doing for you

A GEMM that runs near the tensor cores' peak is not one clever loop. It is six things working together, and every later section of this page is one of them:

  1. Tiles on chip: each thread block computes one output tile (say 128 × 256) and stages slices of A and B in shared memory, laid out (swizzled) so reads hit different banks (section 7; the bank rules are on GPU memory hierarchy).
  2. The right tensor-core instruction for the generation, with operands arranged in exactly the register or shared-memory layout it expects (section 5).
  3. An asynchronous pipeline: copies for the next K slice are in flight while the tensor cores chew on this one (cp.async on Ampere, TMA on Hopper and Blackwell; section 6).
  4. Warp roles on Hopper and Blackwell: a producer warp only issues copies, consumer warps only issue MMAs, and registers are moved from one to the other (section 6).
  5. A tile shape and schedule that fit this problem shape to this GPU's SM count, so the last wave is not mostly idle (section 3).
  6. An epilogue: bias, activation, scaling and conversion done while the tile is still on chip, instead of writing it out and reading it back (sections 2 and 7).

How far does hand-writing get you? Simon Boehm's worklog builds an FP32 matmul in ten steps on an RTX A6000 and ends at 21,779.3 GFLOP/s against cuBLAS's 23,249.6: 93.7%, without tensor cores at all (How to Optimize a CUDA Matmul Kernel, December 2022) independent. The CUDA root's Kernel lab reproduces the same climb on the M1: the best hand-written Metal kernel reached 3,371 GFLOP/s against MLX's library matmul at 4,048 (Topic: cuda-and-gpu-programming, Kernel lab tab) measured on M1 Pro. With tensor cores the gap is wider, because ingredients 2 to 4 change every generation. The full hand-written ladder, step by step, is on Writing kernels; this page is about the libraries at the top of it and the instructions at the bottom.

2. cuBLAS and cuBLASLt: the call, the heuristic, the epilogue

The classic API, and the column-major trap

cuBLAS follows Fortran BLAS: matrices are column-major (consecutive elements go down a column). PyTorch tensors are row-major. A row-major M × K matrix has exactly the bytes of a column-major K × M matrix, its transpose, so libraries compute YT = WT XT and never copy anything: the classic call is cublasGemmEx(handle, opA, opB, m, n, k, α, A, typeA, lda, B, typeB, ldb, β, C, typeC, ldc, computeType, algo) with A = W, B = X and m = 14,336, n = 8,192. Getting lda or an op flag wrong is the most common first cuBLAS bug: the call succeeds and computes the wrong product. The tn/nt letters in kernel names below are these op flags.

cuBLASLt: descriptors, a ranked list, and a workspace

cuBLASLt (the "lightweight" API) splits the call into objects: a matmul descriptor (compute type, transposes, epilogue, scale pointers), a layout per matrix (type, rows, columns, leading dimension, batch), and a preference (how much scratch workspace memory you allow). cublasLtMatmulAlgoGetHeuristic then returns a ranked list of algorithms for exactly this problem on exactly this GPU, and cublasLtMatmul runs the one you pass. Our program for the running example (src/cuda/host/lt_gelu_bias.cu, 50 lines) compiles against cuBLASLt 13.8 in the image compiled here; run without a GPU it stops at the first call that needs the driver:



Workspace matters: some algorithms (split-K, section 3) need scratch memory, and the heuristic only offers those that fit the workspace you declared. PyTorch 2.14.1 gives cuBLAS a default workspace of 32 MiB on compute capability 9.x to 12.x (Hopper and Blackwell) and about 8 MiB on older GPUs, overridable with CUBLAS_WORKSPACE_CONFIG, and sizes cuBLASLt's with CUBLASLT_WORKSPACE_SIZE (CublasHandlePool.cpp) vendor. Too little workspace silently removes the faster choices.

What it is worth. Unfused, the running example writes Y (BF16), reads it for the bias, writes it, reads it for GELU: 4 × 2 bytes × 8,192 × 14,336 = 0.94 GB of extra traffic. On an H100 that is about 0.28 ms at 3.35 TB/s, against about 1.34 ms for the GEMM itself at the ~720 TFLOP/s that SemiAnalysis measured for BF16 GEMMs (SemiAnalysis, Dec 2024) derived: about 21% on top, gone when the epilogue is fused. We cannot time that on an NVIDIA GPU here; the M1 shows the same effect with MLX, whose addmm also puts the bias inside the GEMM:

The lesson in the chart: the extra kernels cost a roughly fixed amount (they move the M × N output), so fusion matters most when K is small and the GEMM itself is short: at K = 256 the eager version is 3.7× the GEMM, at K = 4,096 it is 1.19×.

3. Tiles, waves, split-K and Stream-K: cutting one GEMM into work for the SMs


A GEMM kernel gives each thread block (each CTA, cooperative thread array) one output tile of BM × BN elements; the block loops over K in slices of BK, each slice being one MAC-loop iteration (multiply-accumulate). With T tiles and P SMs, the tiles run in waves of P (the basics of waves and occupancy are on The CUDA programming model). When T is a little over a multiple of P, the last wave is mostly empty: wave quantization.


NVIDIA's own example, reproduced: on an A100 (108 SMs) with 256 × 128 tiles, M = 2,304 and N = 1,536 make 9 × 12 = 108 tiles, exactly one wave; N = 1,544 makes 9 × 13 = 117 tiles, two waves, and NVIDIA's guide reports the GFLOPS "roughly halve" (Matrix Multiplication Background guide) vendor. The tile counts follow from the formula by construction derived; the halving is NVIDIA's measurement, not ours.


The running example with 128 × 256 tiles: 64 × 56 = 3,584 tiles, which is 27.15 waves on an H100 (132 SMs, last wave 15% full, 97.0% of the time useful), 24.22 on a B200 (148 SMs) and 21.08 on an RTX 5090 (170 SMs) derived. Big training GEMMs barely notice; small ones do: decode with a small batch, the per-expert GEMMs of a mixture-of-experts layer, and the backward weight-gradient GEMMs of a thin layer.


Predict: M = N = 1,024, K = 16,384 on an H100 with 128 × 256 tiles. What fraction of the 132 SMs has work?




8 × 4 = 32 tiles for 132 SMs: 24% busy, and each busy SM runs a long K loop of 256 iterations. Splitting K four ways gives 128 work units (97% of the SMs), at the cost of combining partial sums. Try it in the GEMM scheduler tab.


Three ways to hand out the work


    

  • Data-parallel (the default): one CTA per output tile, the whole K loop inside it. No extra traffic; suffers from quantization.
    • 

  • Split-K: cut K into s pieces; s CTAs compute partial sums of the same tile into a workspace, and a reduction (a separate splitKreduce_kernel in cuBLAS, or atomics, or a "serial" in-kernel fix-up) adds them. More work units, but s partial tiles of FP32 written and read. This is why cuBLAS wants workspace.
    • 

  • Stream-K (Osama, Merrill, Cecka, Garland and Owens, January 2023): instead of tiles, divide the total MAC-loop iterations evenly among the SMs; an SM may finish one tile's K loop half-way and start the next, and tiles split between SMs are fixed up through a small workspace. The paper reports "a peak speedup of up to 14× and 6.7×" and more consistent performance "across 32,824 GEMM problem geometries than ... CUTLASS and cuBLAS", "from a single tile size configuration per floating-point precision" (arXiv 2301.03598) paper. In practice it is used as a hybrid: whole tiles data-parallel for the full waves, Stream-K for the remainder.
    • 



Persistent kernels make these schedules possible: instead of launching one CTA per tile, launch about one CTA per SM (or per cluster) and let each loop over work units handed out by a tile scheduler. That also lets a CTA start loading the next tile while its epilogue stores the last one. CUTLASS 4.8.0 ships the schedulers as headers you can read: sm90_tile_scheduler_stream_k.hpp and sm100_tile_scheduler_stream_k.hpp in include/cutlass/gemm/kernel/, and example 74_blackwell_gemm_streamk vendor.


Go deeper: the GEMM scheduler tab lays one GEMM onto the SMs of five GPUs under the three schedules and animates the timeline, with the work, waves and extra traffic of each.






4. cuDNN: a graph in, an engine out


cuDNN started as a list of functions (one call per convolution algorithm). Since version 8 its main interface is a graph API: you describe a small computation graph (tensors with shapes, strides and types; operations such as matmul, pointwise, reduction, normalisation, convolution, scaled dot-product attention), and cuDNN looks for an engine that can run the whole graph as one fused kernel or a few. Some engines are prebuilt ("Pre-Compiled Single Operation Engines"); others are "runtime fusion engines that generate the kernel (or kernels) at runtime based on the graph pattern" (cuDNN Graph API) vendor. The workflow, from the cuDNN frontend's Python API (version 1.30.0 with cuDNN 9.27.0.42, installed in the image; method names read from the module) compiled here:


g = cudnn.pygraph(...)                # describe the computation
o, stats = g.sdpa(q, k, v, ...)         # or g.matmul, g.pointwise, g.rmsnorm, g.conv_fprop ...
g.validate(); g.build_operation_graph()
g.create_execution_plans([cudnn.heur_mode.A, cudnn.heur_mode.FALLBACK])   # heuristics rank engine configs
g.check_support(); g.build_plans()      # runtime-fusion engines compile here
g.execute(variant_pack, workspace, handle)


The heuristic modes the module exposes are A, B, FALLBACK and OPENSOURCE; creating a handle without a GPU fails with "cudnnHandle Create failed cudaGetDeviceCount(&count) != cudaSuccess" not run here. The pattern is the same as cuBLASLt (describe, ask a heuristic, run a plan), with the extra step that a plan may be compiled when you build it, so the first call of a new shape can be slow; frameworks cache plans by shape.


cuDNN as PyTorch's attention


F.scaled_dot_product_attention has four CUDA backends: FlashAttention, memory-efficient attention, the math fallback and cuDNN. In PyTorch 2.14.1 the default order is flash, efficient, math, cuDNN, but on compute capability 9.x and 10.x (H100, B200, B300) with cuDNN newer than 9.15.0 the order is reset to cuDNN first, then flash, efficient, math; the environment variable TORCH_CUDNN_SDPA_DEPRIORITIZED=1 undoes it. cuDNN's attention then accepts head dimensions up to 256 on those GPUs (newer than cuDNN 9.22) in multiples of 8 (sdp_utils.cpp, Context.h) vendor. An RTX 5090 (compute capability 12.0) is not in that list, so it keeps the flash-first order. To see which backend ran, look for the kernel name in a trace, or force one with torch.nn.attention.sdpa_kernel([SDPBackend.CUDNN_ATTENTION]) and compare. How FlashAttention itself works is on Writing kernels.


Corrected from the old page: it said cuDNN is the "backend of F.scaled_dot_product_attention on Hopper/Blackwell". That holds for datacenter Hopper and Blackwell in PyTorch 2.14.1 under the version condition above; consumer Blackwell (sm_120) and Ampere still try FlashAttention first.






5. Tensor cores from the programmer's side: one instruction per generation


A tensor core computes D = A·B + C on a small tile in one instruction. What it is physically, and how many FLOPs per clock each generation does, is on GPU architecture. What changes for the programmer is three questions: who issues the instruction (one warp, four warps, one thread), where the operands live (registers, shared memory, tensor memory), and how the next operands arrive. Every generation answered them differently, which is why a Hopper kernel does not run on a Blackwell chip and why libraries ship a build per architecture.


mma.sync: one warp, everything in registers (Ampere onward)


mma.sync.aligned.m16n8k16.row.col.f32.bf16.bf16.f32 multiplies a 16 × 16 tile of A by a 16 × 8 tile of B into a 16 × 8 FP32 tile, as one instruction for the whole warp. No thread holds a row or a column: the 32 lanes each hold a scattered fragment: 4 registers of A (8 BF16 values), 2 of B (4 values) and 4 of C (4 floats), in a pattern fixed by the hardware. Click a lane to see which elements of C it owns (the map is computed by this page's CuTe algebra from CuTe's own SM80_16x8x16_F32F16F16F32_TN layout, ((4,8),(2,2)):((32,1),(16,8)), and checked value by value against CuTe's output compiled here):








So data cannot simply be copied from shared memory into registers row by row; it has to land in this pattern. ldmatrix does exactly that: each lane supplies the address of one 16-byte row, and the warp receives four 8 × 8 tiles already distributed as mma fragments (.trans transposes on the way). It compiles to LDSM.16.M88.4 and LDSM.16.MT88.4 on every target; the reverse, stmatrix (STSM.16.M88.4), used by epilogues, exists from sm_90 on compiled here.

And wmma? The old page called it "portable but slow, ignore"; more precisely it is limited: its fragment layout is opaque, so you cannot load fragments with ldmatrix patterns or address individual accumulators, and it has no route to wgmma or tcgen05. Libraries use mma.sync and newer instructions directly.


Two corrections to the old page
FP8 did not "arrive" with Hopper's wgmma: the FP8 mma.sync needs sm_89 (ptxas on sm_80: "Feature 'mma with FP8 floating point type' requires .target sm_89 or higher"), so Ada (RTX 4090, L40S) has FP8 tensor cores too, and Hopper added the warpgroup FP8 path. Marketing generations, compute capabilities and instruction sets are three different numberings.


wgmma: four warps, operands from shared memory, asynchronous (Hopper only)


Hopper added the warpgroup: four consecutive warps (128 threads) issue one wgmma.mma_async together, for a 64 × N × 16 tile (N from 8 to 256 in steps of 8; K is 32 for FP8). B, and usually A, are not in registers at all: each is described by a 64-bit matrix descriptor (shared-memory start address, two strides, a swizzle mode) and the tensor core reads shared memory itself. The instruction is asynchronous: threads continue while it runs, and the code brackets it with wgmma.fence, wgmma.commit_group and wgmma.wait_group N (wait until at most N groups are outstanding), so the next tile's MMAs can be issued before the previous ones finish. The accumulators are still registers: a 64 × 256 FP32 tile spread over 128 threads is 128 registers per thread, and ptxas reports 154 registers per thread for our one-instruction m64n256k16 kernel (and 90 for m64n128k16) compiled here. In SASS it is HGMMA.64x128x16.F32 (FP8: QGMMA.64x128x32.F32.E4M3.E4M3), and for any other target ptxas refuses it: Instruction 'wgmma.fence' not supported on .target 'sm_100a'.


tcgen05: one thread, accumulators in tensor memory (datacenter Blackwell)


Blackwell's fifth-generation tensor core moved the accumulator out of the register file into tensor memory (TMEM): 512 columns × 128 lanes of 32-bit cells per SM, 256 KB, the same size as the register file (PTX ISA 9.4) vendor. A kernel allocates TMEM columns (a power of two, at least 32), and a single thread issues tcgen05.mma for a tile of up to 128 × 256 × 16 with operands read from shared memory through descriptors. Completion is signalled on a shared-memory barrier by tcgen05.commit, and the epilogue copies results from TMEM to registers with tcgen05.ld. The register file is free for the epilogue and for addressing: each of our tcgen05 kernels (one 128-row MMA whose accumulator stays in TMEM until an 8-column tcgen05.ld) uses 16 registers per thread, against 90 for the m64n128 wgmma one, whose 64 accumulators per thread must live in registers. Consumer Blackwell (RTX 5090, DGX Spark): back to mma.sync, plus FP4


The RTX 5090 (compute capability 12.0) and the GB10 in DGX Spark (12.1) (CUDA GPUs list) vendor share the Blackwell name with the B200 but not its tensor-core programming model. Compiled for sm_120 and sm_120a compiled here: no wgmma, no tcgen05, no TMEM; mma.sync as on Ampere, with native FP8 (QMMA.16832.F32.E4M3.E4M3) and, on sm_120a only, FP4 (QMMA.16832.F32.E2M1.E2M1) and block-scaled FP4 (OMMA.SF.16864.F32.E2M1.E2M1.E8, which also assembles for sm_121a); TMA and clusters, yes; the register hand-off setmaxnreg only with the a suffix. TMA multicast assembles on sm_120 but ptxas warns it "should be used on .target 'sm_90a/sm_100a/...' instead of .target 'sm_120' as this feature is expected to have substantially reduced performance", and the SASS contains no multicast copy, only a call through a function pointer (CALL.ABS.NOINC) where sm_90a has UTMALDG.2D.MULTICAST. So the old page's claim stands, now with compiler evidence: kernels for the 5090 look like Ampere and Ada kernels (register accumulators, ldmatrix, mma.sync) fed by TMA, and Hopper tutorials built on wgmma do not run on it.


The suffixes: sm_90a, sm_100f, sm_120


From compute capability 9.0 on, features that may not survive into the next generation are only available when compiling for an architecture-specific target with an a suffix, and such code "can only be run on the exact compute capability it was compiled for". From 10.0 on, a family-specific f target covers several: compute_100f runs on 10.0, 10.3 and 10.7, compute_120f on 12.0 and 12.1 (CUDA Programming Guide, compute capabilities) vendor. The compiler shows what that means compiled here: tcgen05 compiles for sm_100f, but the NVFP4 form with scale_vec::4X does not ("Feature '.scale_vec::4X' not supported on .target 'sm_100f'") while sm_100a and sm_103a accept it, as different SASS (UTCOMMA.4X against UTCOMMA.BLOCK16): a family target gets only what every member shares. Plain sm_120 rejects setmaxnreg and the FP4 mma kinds that sm_120a accepts. This is why every architecture-specific library build is separate, and why code compiled only for sm_90a (with no portable PTX alongside) will not run on a B200.

6. TMA, barriers and warp specialisation: keeping the tensor cores fed


An Ampere kernel moves its tiles with cp.async: every thread computes addresses and issues 16-byte copies, 2,048 of them per K slice for our 128 × 128 tile (the instruction itself, and why it bypasses registers, is on GPU memory hierarchy, section 6). Hopper's Tensor Memory Accelerator (TMA) replaces that with one instruction from one thread: "copy this box of this tensor into shared memory", described by a tensor map.


The descriptor, built on the host


A CUtensorMap is a 128-byte opaque object (sizeof 128, alignment 128, printed by our program) holding the tensor's base address, sizes and strides (up to five dimensions), the box to copy, the swizzle mode, the L2 promotion and the out-of-bounds fill. It is built by the driver function cuTensorMapEncodeTiled and passed to the kernel as a const __grid_constant__ parameter. Our program encodes a 64 × 64 BF16 box of an 8,192 × 4,096 matrix with CU_TENSOR_MAP_SWIZZLE_128B; it compiles compiled here, and run against the toolkit's driver stub every driver call returns 34, CUDA_ERROR_STUB_LIBRARY not run here. Out-of-bounds elements of a box are filled with "zero or a special NaN constant" (the oobFill argument, documented in CUDA 13.4.2's cuda.h) vendor, which is why TMA kernels need no edge masking for ragged M, N or K. Error 34 is CUDA_ERROR_STUB_LIBRARY in the same header.

A pipeline of stages


Shared memory is cut into stages, each holding one K slice of A and B. With 128 × 256 tiles and 64-wide K slices in BF16, a stage is (128 + 256) × 64 × 2 bytes = 48 KB, so an H100 block (227 KB) fits 4 stages and an RTX 5090 block (99 KB) only 2 derived (limits from the CUDA Programming Guide; on the RTX the epilogue's shared memory has to fit too, so real kernels there use smaller tiles). Each stage has two barriers: full (the TMA bytes have landed) and empty (the MMAs that read it are done). The producer waits on empty and issues TMA; the consumers wait on full, issue MMAs and arrive on empty. With 3 or 4 stages, three or four loads are in flight while the tensor cores work.


Warp specialisation and the register hand-off


Once copies are one instruction, the warps that issue them need almost no registers, while the MMA warps need many for accumulators. Hopper's setmaxnreg moves registers between warpgroups at run time. CUTLASS's own Hopper example 48 (a TF32 GEMM, 128 × 128 × 32 tile, a 4 × 2 cluster; 168 registers at launch, the cap for 384 threads), compiled for sm_90a, shows the whole structure in its SASS compiled here: the producer warpgroup executes USETMAXREG.DEALLOC.CTAPOOL 0x28 (down to 40 registers), the consumer warpgroups USETMAXREG.TRY_ALLOC.CTAPOOL 0xe8 (up to 232), with 8 HGMMA.64x128x8.F32.TF32 instructions, UTMALDG for the loads and 51 barrier operations. The budget closes exactly: 128 threads × 40 + 256 × 232 = 64,512 of the SM's 65,536 registers derived. CUTLASS calls the two arrangements of consumers KernelTmaWarpSpecializedCooperative (both consumer warpgroups on one tile) and ...Pingpong (they alternate tiles, so one runs its epilogue while the other runs MMAs). FlashAttention-3 is built the same way (arXiv 2407.08608); its algorithm is on Writing kernels.






7. CUTLASS and CuTe: the open-source way to build these kernels


CUTLASS is NVIDIA's open-source, header-only C++ template library for GEMM, convolution and attention; version 4.8.0 is dated 2026-09-17 in its changelog and was published on GitHub on September 22 (releases) vendor, with the Python CuTe DSL on PyPI as nvidia-cutlass-dsl 4.8.0. Where cuBLAS gives you a fixed menu, CUTLASS gives you the parts: you choose types, layouts, tile and cluster shapes, the kernel schedule and the epilogue, and the compiler builds that one kernel. This is how the custom GEMMs of the last few years were made: grouped GEMMs for mixture-of-experts, GEMMs with dequantisation in the mainloop, block-scaled FP8 and FP4, FlashAttention-3.


A CUTLASS 3 and 4 GEMM, assembled


// from examples/48_hopper_warp_specialized_gemm (CUTLASS 4.8.0), abridged
using TileShape    = Shape<_128,_128,_32>;   // one CTA's output tile, and the K slice
using ClusterShape = Shape<_4,_2,_1>;        // CTAs that share tiles by TMA multicast
using CollectiveMainloop = typename cutlass::gemm::collective::CollectiveBuilder<
    cutlass::arch::Sm90, cutlass::arch::OpClassTensorOp,
    ElementA, LayoutA, AlignmentA, ElementB, LayoutB, AlignmentB, ElementAccumulator,
    TileShape, ClusterShape,
    StageCountAutoCarveout<sizeof(CollectiveEpilogue::SharedStorage)>, // as many stages as fit
    KernelScheduleAuto>::CollectiveOp;        // picks a warp-specialised schedule
using GemmKernel = cutlass::gemm::kernel::GemmUniversal<Shape<int,int,int>, CollectiveMainloop, CollectiveEpilogue>;
using Gemm = cutlass::gemm::device::GemmUniversalAdapter<GemmKernel>;   // the host-side handle


Three layers: a collective mainloop (the K loop: TMA, barriers, MMAs), a collective epilogue (what happens to the tile afterwards; CUTLASS's epilogue visitor tree lets you compose bias, activations, scaling, reductions and extra outputs as a tree of nodes, in include/cutlass/epilogue/fusion/sm90_visitor_*.hpp and the sm100 and sm120 equivalents), and a kernel with its tile scheduler (section 3). The builders choose the tensor-core instruction, the swizzled shared-memory layouts and the stage count from the architecture tag. CuTe: layouts from zero


Underneath CUTLASS 3 and 4 is CuTe, a small algebra that describes every arrangement of data and threads in one notation. A layout is a shape and a stride: (4,8):(1,4) is a 4 × 8 array where moving one step down a column adds 1 to the offset and one step along a row adds 4 (column-major); (4,8):(8,1) is the row-major version; (4,8):(1,5) pads each column by one element, the classic way to dodge shared-memory bank conflicts. A layout is a function from coordinates (or a single index, counted with the leftmost mode fastest) to an offset, and shapes can nest: ((2,2),(2,4)):((1,8),(2,16)) is still 4 × 8, but each mode is itself two modes, which is how a tile of tiles is written.






Four operations do almost all the work, and the page's JavaScript implements them following include/cute/layout.hpp; every case below was checked against CuTe's own printed result, compiled and run in the image (21 cases, 6,326 values, 0 differences) compiled here:


    

  • Composition A ∘ B: use B to choose coordinates, A to turn them into offsets. (6,2):(8,2) ∘ (4,3):(3,1) = ((2,2),3):((24,2),8), the example in CuTe's documentation.
    • 

  • Complement: the layout that fills the holes. complement((2,2):(1,6), 24) = (3,2):(2,12).
    • 

  • Logical divide by a tiler: split a layout into (tile, rest). An 8 × 8 column-major matrix divided by 2 × 4 tiles is ((2,4),(4,2)):((1,2),(8,32)); zipped_divide regroups the same thing as ((inside a tile), (which tile)), which is how a kernel picks its CTA's tile: local_tile.
    • 

  • Products (blocked_product, raked_product): repeat a layout over a grid, used to lay threads or values over a tile.
    • 



Two more ideas complete the picture. A swizzle Sw<B,M,S> XORs B bits of an offset into B lower bits: CUTLASS's 128-byte Hopper shared-memory atom for 16-bit types is Sw<3,4,3> o (8,64):(64,1) on byte addresses, which XORs a row's 16-byte chunk index with the row number modulo 8, so eight rows read in the same column land in eight different 16-byte bank groups (the bank arithmetic is on GPU memory hierarchy). A thread-value (TV) layout maps (thread, value) to a position in a tile: the mma.sync fragment map in section 5 is CuTe's ((4,8),(2,2)):((32,1),(16,8)). With these, a CUTLASS kernel reads as: local_tile the global tensors to this CTA's tile, partition it across threads with a tiled copy and a tiled MMA (make_tiled_mma, partition_A), then copy and gemm on the pieces.


CuTe DSL writes the same thing in Python. Installed in the image without a GPU, it printed the same layouts as the C++ (((2,2),3):((24,2),8) for the composition above) and compiled a small kernel to PTX for sm_90a and a cubin, through its own bundled NVVM ("release 13.4, V13.4.59") compiled here; running it needs a GPU not run here. FlashAttention-4 and many of CUTLASS's newest examples are written in it.

Why the block recipe exists: DeepSeek-V3 trained in FP8 on H800s with activations scaled per 1 × 128 tile ("per token per 128 channels") and weights per 128 × 128 block, and found that "the accumulation precision of FP8 GEMM on NVIDIA H800 GPUs is limited to retaining around 14 bits"; with K = 4,096 that gave "a maximum relative error of nearly 2%" in their test. Their fix: every NC = 128 elements of K, copy the tensor-core partial sums to FP32 registers and accumulate there ("promotion to CUDA Cores") (DeepSeek-V3 report, section 3.3) independent. That is a mainloop change no library offered at the time, which is why it was a custom kernel (DeepGEMM) before it was a cuBLAS scale mode; the report itself is summarised on the DeepSeek-V3 paper page. Blackwell's block-scaled instructions move the per-block scaling into the tensor core itself.

Common mistakes


Treating column-major cuBLAS like row-major PyTorch
The call succeeds and computes the wrong thing (or the transpose). Compute YT = WTXT by swapping the operands, as in section 2; check against torch.matmul on small sizes first.


Shapes that defeat the heuristic
Dimensions not divisible by 8 (16 bytes of FP16/BF16) block the vectorised and TMA paths; a tile count just past a multiple of the SM count wastes a wave. Pad vocabulary and hidden sizes to multiples of 64 or 128; compare against a padded shape before blaming the library. On the M1, MLX's library GEMM loses 4.9% when N goes from 4,096 to 4,095 (median of 3 runs) measured on M1 Pro; the effect on NVIDIA GPUs, where alignment decides whether TMA and 16-byte vector paths are usable, is not measured here not run here. A decode-shaped GEMM (M = 8 rows) is a different problem altogether: it reads the 32 MiB weight matrix for almost no arithmetic, and the M1 library call streamed it at only 67.5 GB/s against the 146 to 163 GB/s that plain copies reach on the same GPU (GPU memory hierarchy).


Expecting a Hopper kernel to run on an RTX 5090 or a B200
wgmma code compiled for sm_90a runs only on compute capability 9.0. Check what a wheel contains with cuobjdump -lelf before renting a GPU for it.


Starving cuBLASLt of workspace
A small workspace removes split-K and some Stream-K algorithms from the heuristic's list without any error. When comparing libraries, give each the same workspace.


Timing the first call
cuDNN runtime-fusion plans and Triton or CuTe DSL kernels compile on first use; cuBLAS loads modules lazily. Warm up, then time (the method is on Profiling and correctness).


Trusting FP8 accumulation over a long K
Section 8: tensor-core FP8 accumulation on Hopper keeps about 14 bits; use libraries that promote partial sums to FP32 or test your kernel's error against an FP32 reference at the real K.

Interview questions, with short answers


Why can't you just write a fast GEMM in CUDA in an afternoon?
Peak needs on-chip tiling with swizzled layouts, the generation's tensor-core instruction with its operand layouts, an asynchronous multi-stage pipeline, warp specialisation on Hopper/Blackwell, a schedule matched to the SM count, and a fused epilogue. Each changes per generation; cuBLAS ships 52,148 kernels in its Lt library alone.


What is the difference between cuBLAS and cuBLASLt?
Same kernels; Lt exposes descriptors, a ranked heuristic list, a workspace, epilogues (bias, ReLU, GELU and their gradients) and FP8/FP4 scale modes. PyTorch uses classic cuBLAS for mm by default and Lt for addmm with a 1-D bias and for scaled matmuls.


mma.sync vs wgmma vs tcgen05?
One warp, operands and accumulators in registers (Ampere on); four warps, async, operands from shared memory by descriptor, accumulators in registers (Hopper only); one thread, async, operands from shared memory, accumulators in tensor memory, optionally across two SMs (datacenter Blackwell). The RTX 5090 uses the first.


What does TMA buy over cp.async?
One instruction from one thread moves a whole multi-dimensional tile with hardware address generation, swizzling, out-of-bounds fill and byte-counted completion on an mbarrier, optionally multicast to a cluster; the other warps are free for math.


What is wave quantization and what fixes it?
Tiles run in waves of one per SM; a tile count just above a multiple of the SM count leaves the last wave mostly idle (108 vs 117 tiles on an A100 halves throughput in NVIDIA's example). Fixes: a different tile shape, split-K, Stream-K, or padding the problem.


What is a CuTe layout?
A shape and a stride, a function from coordinates to offsets with the leftmost mode fastest; composition, complement, divide and product build tiles, thread mappings, swizzled shared memory and instruction fragments from it.


Why did DeepSeek-V3 need a custom FP8 GEMM?
Per-128-element block scaling and FP32 promotion of tensor-core partial sums every 128 elements of K, because Hopper's FP8 accumulation keeps about 14 bits. That changes the mainloop, which no library exposed then.
