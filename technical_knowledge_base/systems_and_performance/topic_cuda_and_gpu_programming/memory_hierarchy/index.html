A kernel is fast when the bytes it needs are already close to the arithmetic. This page is the programmer's view of where bytes live on an NVIDIA GPU and how your code decides it: which instruction a line of CUDA becomes, how many bytes the hardware really moves for it, and which mistakes make it move more. Everything marked compiled here is real output of NVIDIA's CUDA 13.4.2 compiler (no GPU is needed to compile); everything marked measured on Apple M1 Pro GPU was run on this laptop, whose GPU is also a SIMT machine with 32-wide SIMD-groups and a programmer-managed on-chip memory, so the shapes transfer even where the numbers do not.

The parent Topic: cuda-and-gpu-programming gives the intuition in its section 3 (the ladder, coalescing, banks, tiling, one spill) and its GPU simulator tab has the stride, bank-conflict, transpose, occupancy and tiling simulators; this page does not redo them. What the memory physically is (SRAM against DRAM, HBM stacks, the M1's measured cache ladder) belongs to Memory technology; the SM's insides to GPU architecture.

Three questions for every array in a kernel
Where does it live (which row of the table)? How many times is each byte read (once: stream it; many times: stage it on chip)? In what order do neighbouring threads touch it (neighbours on neighbouring addresses, or not)? Every section below is one of these questions answered for one space.

1. Global loads: what one warp's load really fetches

The problem. A thread asks for 4 bytes, but DRAM and the caches do not deal in 4 bytes. NVIDIA's rule: "Global memory is accessed via 32-byte memory transactions", and the warp "coalesces the memory requests from all the threads in that warp into the number of memory transactions necessary" (Programming Guide 2.3.4.1). A 32-byte piece is a sector; four sectors make a 128-byte cache line. So the cost of a load is not how many bytes the threads want but how many distinct sectors their 32 addresses fall in. 32 lanes reading 32 consecutive floats: 128 bytes, four sectors, nothing wasted. 32 lanes each 32 bytes or more apart: 32 sectors, 1,024 bytes moved for 128 used.

The parent's GPU simulator sweeps the stride. Three other ways to waste sectors come up in real ML code and are animated here on one warp: a struct field (array of structs), a misaligned start, and narrow loads.

One warp, drawn to scale: each small box is 4 bytes, each outlined group of eight is one 32-byte sector, each row is 128 bytes. A sector turns shaded when the warp fetches it; blue words are wanted by some lane, orange ones by the lanes of the current step, grey ones fetched but unused. derived from the 32-byte rule above; the same counts come out of the Access lab, which lets you type any pattern.

Predict: particles stored as a struct of eight floats (32 bytes each). A kernel reads only p[i].x. How many sectors does one warp fetch, and what fraction of the fetched bytes is used?
32 sectors, 1,024 bytes fetched for 128 used. Each lane's 4 bytes sit in its own 32-byte struct, so every lane needs its own sector. Store each field as its own array (struct of arrays) and the same warp needs 4 sectors.

What the M1 says

measured on Apple M1 Pro GPU: 16M particles of 32 bytes (512 MB), median of 3 runs of 7 trials, load average 9.2 to 9.8 while other agents worked; each bar gives the median and, in brackets, the fastest and slowest run. Reading one field from the structs took 3.66 ms, the same as reading all eight fields (3.66 ms): the GPU fetched every byte of every struct either way. The same field kept in its own array took 1.03 ms, 3.6 times faster. The ratio of bytes moved (512 MB read + 64 MB written against 64 + 64 MB) is 4.5; the gap is the smaller transfer's fixed costs. derived: 3.66 / 1.03 and 576 / 128.

Misalignment and vector width

Misaligned. If a warp's 128 contiguous bytes start in the middle of a sector, they span five sectors instead of four. NVIDIA's Best Practices Guide measured exactly this on a V100: "we would expect approximately 4/5th of the memory throughput", but got about 9/10 "because adjacent warps reuse the cache lines their neighbors fetched" (Best Practices Guide 10.2.1.3) vendor measurement. The parent's simulator found no measurable penalty for an offset of one float on the M1. Allocation keeps you aligned by default: "Memory allocated through the CUDA Runtime API, such as via cudaMalloc(), is guaranteed to be aligned to at least 256 bytes" (same guide). The misalignment comes from you: a tensor view with a storage offset (x[:, 1:]), a block size that is not a multiple of 32, a packed header in front of the data.

Width. A thread can load 4, 8 or 16 bytes in one instruction. compiled here for sm_90a, the same copy written with float, float2 and float4 becomes:



Same bytes, a quarter of the load instructions, and each instruction keeps four times as many bytes in flight. NVIDIA's advice: vectorised loads "reduce the total number of instructions, reduces latency, and improves bandwidth utilization", but "These instructions require aligned data" and "using vectorized loads increases register pressure and reduces overall parallelism" (CUDA Pro Tip: vectorized memory access, updated Aug 4, 2025). Note the .CONSTANT: the pointers were const __restrict__, section 2 explains it.




measured on Apple M1 Pro GPU: a 256 MB copy ran at about the same speed with 4-, 8- and 16-byte accesses (the bars above; spread across runs 145 to 169 GB/s). With 64 million threads in flight there is enough memory parallelism either way, so on a plain copy the M1 is limited by DRAM, not by instructions. Width pays off when a kernel has few threads per byte or many other instructions competing for issue slots: the case in matmul and attention kernels, which is why they load 16 bytes at a time (and why section 6's asynchronous copy is 16 bytes wide).


When it matters for training, and how to check


  • Layouts. A fused QKV projection stored as [tokens, 3, heads, dim] and read one head at a time; channels-last against channels-first; a transposed weight read along the wrong axis. If the innermost index your threads walk is not the innermost dimension in memory, you pay the stride.

  • Views. Slicing makes a tensor non-contiguous or misaligned; PyTorch's elementwise kernels check alignment before using vector loads (can_vectorize_up_to in ATen's MemoryAccess.cuh) and fall back to narrow loads; .contiguous() costs one copy and can make every later kernel faster.

  • Check: in Nsight Compute's Memory Workload Analysis, sectors per request for global loads (ideal: 4 for a full warp of 32-bit loads, 16 for 128-bit loads, by the rule above) and the "uncoalesced global accesses" advice; details on Profiling, benchmarking and correctness.






2. The caches, and the few ways to steer them


The problem. You do not allocate cache; the hardware decides what stays. But two caches sit between your loads and DRAM, they behave differently, and the compiler gives you a handful of hints. Knowing them explains suffixes you will see in every disassembly and one class of bug.




L1 (per SM)shares its SRAM with shared memory (section 3); caches global and local loads for that SM only. Not kept coherent with other SMs: "multiple L1 caches are not coherent for global data" (PTX ISA 9.4, cache operators).


L2 (whole GPU)every DRAM access goes through it, so it is where all SMs agree: "Global data is coherent at the L2 level" (same table). 40 MB on A100, 50 MB on H100 SXM, 96 MB on RTX 5090 vendor spec.


Read-only patha load the compiler may serve from the non-coherent texture/L1 path because nothing writes the data during the kernel. You ask for it with const T* __restrict__ or __ldg().




The read-only path. "Accesses to __global__ function const pointers marked with __restrict__ are compiled as read-only cache loads, similar to the PTX ld.global.nc or __ldg()" (C++ language extensions). compiled here: a plain const float* load becomes LDG.E; the same load with __restrict__, or written __ldg(p), becomes LDG.E.CONSTANT. The promise behind __restrict__ is that no other pointer in the kernel touches that memory. If you lie (an in-place kernel whose input and output alias), the compiler may reorder or cache, and the result is silently wrong.


Cache operators. Every load and store can carry a hint. The intrinsics map to PTX operators, and the table shows what CUDA 13.4.2 turned each into on three generations compiled here. The meanings are quoted from the PTX ISA; the reading of the SASS suffixes (EF for evict-first, STRONG.GPU for "performed at the L2, the GPU's point of coherence") is an inference from the names and the PTX definitions, since NVIDIA does not document SASS.




In practice: __ldcs/__stcs (evict-first) suit data read or written exactly once, such as a large activation streamed through an elementwise kernel, so it does not push out data that will be reused; __ldcg skips L1, useful when another block may have just written the data; .lu exists mainly for restoring spills. They are hints: "Cache operators on load or store instructions are treated as performance hints only" (PTX ISA). Most ML kernels never use them; you will meet them in hand-tuned kernels (FlashAttention, vLLM, ggml-cuda) and in Triton's eviction_policy argument to tl.load.


Keeping a buffer in L2 on purpose


Since compute capability 8.0 you can reserve part of L2 for one address range: "A portion of the L2 cache can be set aside to be used for persisting data accesses to global memory" (Programming Guide 4.14, L2 cache control). Two calls, from that page:


size_t size = min(int(prop.l2CacheSize * 0.75), prop.persistingL2CacheMaxSize);
cudaDeviceSetLimit(cudaLimitPersistingL2CacheSize, size);   // set aside up to 3/4 of L2
stream_attribute.accessPolicyWindow.base_ptr  = ptr;           // the hot buffer
stream_attribute.accessPolicyWindow.num_bytes = num_bytes;
stream_attribute.accessPolicyWindow.hitRatio  = 0.6;           // fraction of accesses marked persisting
stream_attribute.accessPolicyWindow.hitProp   = cudaAccessPropertyPersisting;
stream_attribute.accessPolicyWindow.missProp  = cudaAccessPropertyStreaming;
cudaStreamSetAttribute(stream, cudaStreamAttributeAccessPolicyWindow, &stream_attribute);


It is disabled under MIG, and fixed at server start under MPS (same page). It helps when a few tens of MB are read by many consecutive kernels in one stream while other data streams past; it cannot help data larger than the set-aside. not run here: no NVIDIA GPU.


The free way to use L2: order the work. Blocks that run at the same time share L2. A tiled matmul that launches its output tiles row by row reads each B column panel once per row of tiles; launching them in groups of rows ("grouped" or "swizzled" block order) lets concurrently running blocks reuse the same A and B panels from L2. Triton's matmul tutorial shows the reordering as "L2 cache optimizations"; Writing kernels builds it.


How fast each cache rung is on this laptop's GPU (about 1,239 GB/s for working sets up to 128 KB, 579 at 1 MB, 318 at 32 MB, 127.5 at 1 GB) is measured on Memory technology, section 3.







3. Shared memory in practice: declaring it, sizing it, wide accesses, swizzles


The problem it solves (the parent's section 3 has the full motivation): data that many threads of a block read many times should be fetched from DRAM once and then read from on-chip SRAM. Shared memory is that SRAM, managed by your code.

compiled here: static arrays show up in the compiler's report (32 × 33 × 4 = 4,224 bytes; the swizzle saves the padding column); dynamic shared memory is invisible at compile time, so the occupancy calculator must be told the launch size.


Sizes and the opt-in. Per SM: 164 KB on A100 (compute capability 8.0), 228 KB on H100 and B200 (9.0, 10.0), 100 KB on RTX 3090, 4090 and 5090 (8.6, 8.9, 12.0); one block may use 1 KB less, which CUDA reserves per block (compute capabilities). But "Kernels relying on shared memory allocations over 48 KB per block are architecture-specific. As such they must use dynamic shared memory rather than statically-sized arrays and require an explicit opt-in" (Programming Guide 3.2, L1/shared balance):


cudaFuncSetAttribute(kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, 200 * 1024);
cudaFuncSetAttribute(kernel, cudaFuncAttributePreferredSharedMemoryCarveout, cudaSharedmemCarveoutMaxShared);
kernel<<<grid, block, 200 * 1024>>>(...);


The carveout splits the SM's SRAM between L1 and shared memory, and only some splits exist: "for devices of compute capability 12.0, which have a maximum shared memory capacity of 100KB, setting the carveout to 50% will result in 64KB of shared memory, not 50KB, because devices of compute capability 12.0 support shared memory sizes of 0, 8, 16, 32, 64, and 100" (same page). Whatever shared memory takes, L1 loses. In Triton you never write these calls; a block size and num_stages that need too much raise OutOfResources for shared memory at compile time (triton/runtime/errors.py).


More shared memory is not free. What a block takes is reserved for the whole kernel, so it sets how many blocks share an SM. Writing kernels, section 5, measured it on the M1 Pro measured on Apple M1 Pro GPU: a 16 KB staging tile added to a fused matmul epilogue tripled the kernel's threadgroup memory (8 KB to 24 KB), fewer threadgroups fit on each GPU core, and the fused kernel ran slower than not fusing at all.


Banks with wide accesses


The rule (32 banks, "successive 32-bit words map to successive banks", "Each bank has a bandwidth of 32 bits per clock cycle") and the classic 32 × 32 transpose are in the parent's GPU simulator. Real kernels load 8 or 16 bytes per lane, and the rule then gives a floor, not a conflict-free promise: a warp asking for 32 × 16 = 512 bytes needs at least 512 / 128 = 4 passes, since 32 banks deliver 128 bytes per pass. The cost is the number of passes the busiest bank needs. NVIDIA's own example: with 16-byte (int4) elements "each set of eight threads loads a row", and a column-wise store "must be serialized, resulting in eight store transactions, giving an eight-way bank conflict" (Programming Guide 4.12, asynchronous copies, TMA swizzle). The current guide does not spell out how 8-byte accesses are split; the Access lab counts passes from the 32-bit rule alone and says so.


Predict: each lane reads one float4 (16 bytes) from shared memory, lanes 128 bytes apart (lane l reads element 8l). How many passes against the ideal 4?




Lane l's 16 bytes are words 32l to 32l + 3, which are banks 0 to 3 for every lane. Banks 0 to 3 each serve 32 different words: 32 passes, 8 times the ideal. A stride of 9 elements (144 bytes) spreads them out again.




measured on Apple M1 Pro GPU: bytes per second read from threadgroup memory (Apple's shared memory) by 131,072 threads, 16 KB per threadgroup, median of 3 runs. With 16-byte elements: 1,893 GB/s at a lane stride of 1 element, 1,049 at 4, 565 at 8, and 1,905 at 9, the signature of 4-byte banks that the rule predicts (Apple documents neither its bank count nor width; this is inference from the measurement). Wide reads also moved more bytes per second than 4-byte reads (1,108 GB/s at stride 1, noisy under load), so on chip as well as off chip, fewer and wider accesses win.


Swizzles: the libraries' answer


Padding ([32][33]) breaks the alignment that 16-byte and TMA copies need and wastes memory, so libraries permute instead: element (r, c) is stored at column c XOR f(r), which keeps every row and every column on distinct banks. Hopper's TMA engine writes tiles already swizzled: "the TMA engine can be instructed to 'swizzle' the data before storing it in shared memory", and with CU_TENSOR_MAP_SWIZZLE_128B "each matrix element is from a different bank for both the rows and columns" (same page). The Access lab shows plain, padded and XOR layouts side by side; CUTLASS's layout algebra that generalises this is on Libraries and tensor cores.


Beyond one block. On Hopper and later, blocks of a cluster can read each other's shared memory (distributed shared memory, about 180 cycles in Luo et al.'s H800 measurements against 29 for local shared memory independent); the hardware side is on GPU architecture, section 8, the launch side on The CUDA programming model.






4. Registers, spills, and arrays that fall into local memory


The problem. Registers are the only storage the arithmetic units read directly, and they are rationed: 65,536 32-bit registers per SM on every current NVIDIA GPU, shared by all resident threads, at most 255 per thread. A thread that keeps more values alive than it has registers must park some in memory. Fast kernels (register-tiled matmul, FlashAttention) deliberately keep large pieces of the output in registers, so they live right at this edge.


Reading the compiler's report

    • 

  • stack frame: bytes per thread of local memory for any reason: spills, or an array the compiler could not keep in registers.

The kernel keeps 128 running sums per thread (the shape of a register-tiled matmul's accumulator). Compiled with no cap, ptxas uses  registers and spills nothing. Then the same file under -maxrregcount from 32 to 255:








Two lessons. Below what the kernel needs, every register removed becomes spill traffic: at a cap of 32 each thread writes and rereads over a kilobyte per pass through the loop body's live values. Above it, ptxas does not stop at what it needs: on sm_90a it used every register it was allowed (192, 224, 255), presumably to schedule loads earlier, and each extra register lowers how many warps fit. The documented version of this behaviour is for launch bounds: "If both minBlocksPerMultiprocessor and maxThreadsPerBlock are specified, the compiler may increase register usage up to L in order to reduce the number of instructions and better hide the latency" (C++ language extensions, launch bounds); the same happening under -maxrregcount is observed here, not documented. Prefer __launch_bounds__(maxThreadsPerBlock, minBlocksPerSM) per kernel over a per-file -maxrregcount (both named in the Best Practices Guide, register pressure), and measure: a few spilled bytes that hit L1 can cost less than the occupancy they buy back.


Local memory without any register pressure


The surprise for most people: an array can land in local memory while the kernel uses only a few registers. The guide lists what the compiler puts there: "Arrays for which it cannot determine that they are indexed with constant quantities, Large structures or arrays that would consume too much register space, Any variable if the kernel uses more registers than available" (Programming Guide 2.3.3.4, local memory). Registers have no addresses, so h[b] with b known only at run time needs memory. Two versions of a per-thread 16-bin histogram, compiled here for sm_90a:




Run-time index: h[bins[k * 4096 + t] & 15] += 1.f;



Constant indices only: for (j = 0; j < 16; ++j) h[j] += (b == j) ? 1.f : 0.f;





The first uses ; the four STL.128 zero the 64-byte array in local memory and every update is an LDL and an STL. The second does 16 compare-and-adds per update but keeps all 16 bins in registers (). Local memory is laid out so that "consecutive 32-bit words are accessed by consecutive thread IDs. Accesses are therefore fully coalesced as long as all threads in a warp access the same relative address" (same section); here every lane picks its own bin, so the accesses scatter too.




measured on Apple M1 Pro GPU: the same two kernels in Metal, 262,144 threads × 1,024 updates each: 7.08 ms with the run-time index against 4.49 ms with constant indices, 1.58 times slower despite doing a sixteenth of the arithmetic. Apple's compiler faces the same problem (registers are not addressable) and makes the same choice.


Predict: ptxas reports "64 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads, Used 22 registers". What is in the 64 bytes?




Zero spill bytes, yet a stack frame: an array the compiler could not promote to registers, here 16 floats = 64 bytes. Fix it by making every index a compile-time constant (unrolled loops, selects), or move the array to shared memory if lanes need different entries.


What you cannot control: register bank conflicts inside the SM. "The compiler and hardware thread scheduler will schedule instructions as optimally as possible to avoid register memory bank conflicts. An application has no direct control over these bank conflicts. In particular, there is no register-related reason to pack data into vector data types such as float4" (Best Practices Guide 10.2.7).







5. Constant memory and kernel parameters


What it is. "There is a total of 64 KB constant memory on a device. The constant memory space is cached ... Accesses to different addresses by threads within a warp are serialized, thus the cost scales linearly with the number of unique addresses read by all threads within a warp ... If all threads of a warp access the same location, then constant memory can be as fast as a register access" (Best Practices Guide 10.2.6). So it suits values every lane reads at once: a scale, a bias, filter taps, a small lookup indexed by loop counter, not by lane. You use it more than you think, because every kernel argument lives there.


compiled here, sm_90a, from a __constant__ float c_tab[1024] and a kernel taking a small struct by value:




How to read it (bank numbers inferred from consistent use across these kernels, since SASS is undocumented): bank c[0x0] holds the launch's parameters and built-ins (c[0x0][0x0] is the block size, read for blockDim.x); bank c[0x3] holds the module's __constant__ data. With an index known at compile time, the value goes into a uniform register (ULDC, one copy for the whole warp) and straight into the FFMA. With an index known only at run time, it takes an LDC, which is where the per-address serialisation applies if lanes disagree. On sm_80 the compiler even used a parameter directly as an FFMA operand ().


Texture memory is the other read-only cached path: "optimized for 2D spatial locality" with hardware filtering and boundary handling (Best Practices Guide 10.2.5). It matters for image resampling; ML kernels almost never use it, and const __restrict__ loads already use the same cache.


A constant-address-space experiment on the M1 was tried and dropped: MLX passes buffers to custom kernels in Metal's device address space, and a program-scope constant table is a different mechanism, so the comparison did not isolate the NVIDIA behaviour described here.






6. Asynchronous copies: loading the next tile while computing this one


The problem. A tiled kernel loops: load a tile of A and B into shared memory, wait, compute on it, wait, load the next. Written plainly, every load goes global memory to a register, then register to shared memory, and the SM sits idle for a full memory latency (about 479 cycles on an H800, from the parent's table) at the start of every tile. Two costs: idle time, and registers held just to carry data in transit.


How it works. Since Ampere (compute capability 8.0) one instruction copies global to shared memory directly, without a register in between, and the thread does not wait for it: "This not only reduces register usage by copying the data directly to shared memory, but also ensures all loads from global memory are in-flight" (Programming Guide 4.12.1, LDGSTS). With two or more shared-memory buffers (stages), the copy for tile t + 1 runs while the math on tile t proceeds. compiled here for sm_90a, the same tile loop written both ways:




Synchronous: s[tid] = a[t * 256 + tid];



Two stages: __pipeline_memcpy_async, __pipeline_commit, __pipeline_wait_prior(1)





On the left, the compiler already unrolled the loop and issued four 16-byte loads ahead, each parked in four registers until its STS.128: it hides latency by spending registers. On the right, LDGSTS writes shared memory directly; LDGDEPBAR closes a group of copies (the commit) and DEPBAR.LE SB0, 0x1 waits until at most one group is still in flight (the wait_prior(1)). The .BYPASS matches the guide: "copying 16-bytes enables the L1 BYPASS mode, in which case the L1 is not polluted" (same section). The copies are per thread, so a __syncthreads() is still needed before other threads read the tile.














One block's loop over 8 tiles. Top row: copies in flight (each lasts one memory latency); bottom row: the SM computing. A copy can start only when its buffer is free (the tile that last used it has been computed); a tile can be computed only when its copy has landed. illustrative: 479 cycles per copy (H800 global latency, Luo et al.) and 200 cycles of math per tile, chosen to show the effect; it ignores bandwidth limits and the other blocks on the SM, which also hide latency. The cost. Each stage is another tile of shared memory, so stages trade against block size and occupancy (section 3's limits): this is exactly Triton's num_stages, and Triton 3.8.0 compiles a plain matmul's tile loads to LDGSTS on sm_80 (the parent's Compiler explorer). Hopper's TMA goes one step further: one thread issues a copy of a whole multi-dimensional tile (up to 5 dimensions), completion is signalled on a shared-memory barrier, and the tile can land swizzled (section 3). The TMA programming model and the warp-specialised producer/consumer kernels built on it are on Libraries and tensor cores; a full pipelined matmul on Writing kernels; the copy engines inside the SM on GPU architecture, section 8.







7. Host memory: pinned, mapped and managed


The problem. Training data and checkpoints start in host RAM; a GPU's copy engines move them over PCIe or NVLink-C2C by DMA, and DMA needs physical pages that will not move. Ordinary malloc memory can be swapped or relocated by the OS, so it cannot be the DMA target. How CUDA bridges that decides whether your input pipeline overlaps with compute.




Pageable (default)"When CUDA sends pageable data from CPU to GPU, it must first create a page-locked copy of that data before making the transfer" (PyTorch, non_blocking and pin_memory, Apr 1, 2026): an extra CPU memcpy, and the call cannot run in the background.


Pinned (page-locked)cudaMallocHost / cudaHostAlloc, or cudaHostRegister on existing memory. "Page-locked host memory is required for asynchronous copies between the CPU and GPU" and "also improves performance of synchronous copies" (Programming Guide 2.6.3).


Mapped (zero copy)pinned memory the GPU reads directly over the interconnect, uncached on the GPU. "On integrated GPUs ... mapped pinned memory is always a performance gain ... On discrete GPUs, mapped pinned memory is advantageous only in certain cases" (Best Practices Guide 10.1.3).


Managed (unified)cudaMallocManaged: one pointer for both sides; pages migrate on first touch. Prefetch with cudaMemPrefetchAsync and give hints with cudaMemAdvise, or it is slow; the driver's fault path is on Virtualization and the GPU driver stack, section 11.




How fast. The Best Practices Guide's own example is dated: "On PCIe x16 Gen3 cards, for example, pinned memory can attain roughly 12 GB/s transfer rates" vendor figure; today's links are faster (PCIe Gen5 x16 and NVLink-C2C on Interconnects and scaling), but the rule is the same. And pinning has a price: "Pinned memory should not be overused ... the pinning of system memory is a heavyweight operation" (same guide); pinned pages count against the locked-memory limit (Virtual memory, section 9). not run here: this laptop has no discrete GPU.

  • Pinning by hand on the critical path does not help: "Using tensor.pin_memory().to(device, non_blocking=True) can be up to twice as slow as a straightforward tensor.to(device)" (PyTorch tutorial above), because the pin is itself a copy.
    • 

  • The other direction is a correctness trap: after cuda_tensor.to("cpu", non_blocking=True) "there is no guarantee that the data read on GPU is valid without explicit synchronization" (same tutorial; it means the CPU-side data); synchronise (or wait on an event) before reading it.
    • 



Device allocation is not free either. "Device memory allocation and de-allocation via cudaMalloc() and cudaFree() are expensive operations. It is recommended to use cudaMallocAsync() and cudaFreeAsync() which are stream ordered pool allocators" (Best Practices Guide 10.3). PyTorch goes further with its own caching allocator, which is why nvidia-smi shows memory "used" after tensors are freed; it is simulated from its source on Memory allocators, section 9.


The Apple contrast. On this laptop there is no host-device copy to make: "Apple silicon has a unified memory architecture. The CPU and GPU have direct access to the same memory pool" (MLX, unified memory). That is the integrated case of the zero-copy rule above, and why every M1 number on this page measures the GPU's own memory system with no PCIe in the way. Grace Hopper and Grace Blackwell get part of the way on NVIDIA with a coherent CPU-GPU link (Memory technology, section 7).






8. Your kernel on a roofline: from bytes and FLOPs to a verdict


The problem. After all the rules above you still need one number: is this kernel close to what the GPU can do, and which limit is it against? The roofline answers it (the model itself, ridge points per chip and MFU are on Topic: hardware and Performance math); here is the programmer's recipe for one kernel.


    

  1. Count the bytes the kernel must move if every input is read once and every output written once (not what it actually moves: that is what you are judging).
    2. 

  2. Count the FLOPs (an FMA is 2).
    3. 

  3. Time it honestly (warm-up, many repetitions, synchronise: Profiling, benchmarking and correctness).
    4. 

  4. Divide: achieved bandwidth = bytes / time, achieved FLOP/s = FLOPs / time, arithmetic intensity = FLOPs / bytes.
    5. 

  5. Compare with the roof at that intensity: min(peak FLOP/s, intensity × peak bandwidth). Near the slanted part: memory-bound, so move fewer bytes (fuse, use smaller types). Near the flat part: compute-bound, so use tensor cores or do less math. Far below both: neither; the access pattern or latency hiding is broken, and sections 1 to 6 are where to look.
    6. 



To see a real roof rather than a datasheet one, this page measured it: a kernel that reads one float4 per thread, does F steps of 8 independent FMAs, and writes one float, for F from 1 to 1,024, so its intensity runs from 1.35 to 820 FLOP per byte.




measured on Apple M1 Pro GPU: dots are the sweep (median of 3 runs; whiskers span the runs), dashed lines are the roofs it implies: 156 GB/s (median bandwidth of the sweep's points up to F = 16) and 4,992 GFLOP/s (its best point), a ridge at 32 FLOP per byte derived: 4,992 / 156.3. Both agree with the independent measurements in Topic: hardware (about 5.0 TFLOP/s FMA, 143 to 165 GB/s streaming) and sit at 94% of the 5,308 GFLOP/s that 16 cores × 128 ALUs × 2 × 1.296 GHz gives (metal-benchmarks). The single coloured points are kernels from the parent's Kernel lab placed by the recipe above, with their minimum bytes.




The two softmaxes do the same math on the same data; the eager one sits at a quarter of the bandwidth roof because, counted against the minimum bytes, it moves the tensor several times (five kernels, each a full pass). The naive matmul has an intensity of 341 FLOP per byte, ten times the ridge, yet runs at a fraction of the compute roof: by the recipe it is "far below both", and indeed its threads re-read A and B from memory for every output (no tiles, section 3 of the parent). Tiles and registers (the 4 × 4 per thread kernel) and then the matrix instructions in MLX's library close the gap.

9. Common mistakes, how to check, interview questions




BeliefWhat is trueSection



"Local memory is fast, it is local."It lives in device DRAM; "local" is the scope. It is cached, but a spill or a run-time-indexed array costs real memory traffic.4


"Reading one field of a struct reads 4 bytes."The warp fetches whole 32-byte sectors: one field of a 32-byte struct costs as much as the whole struct (measured: same time).1


"More registers per thread is always faster."Each register costs resident warps; ptxas will use whatever cap you allow. Measure both sides of the spill/occupancy trade.4


"Padding is the way to fix bank conflicts."It works for 4-byte accesses, but breaks the alignment 16-byte and TMA copies need; libraries swizzle.3


"A bank conflict-free layout for floats stays conflict-free for float4."Wide accesses need several passes anyway and a different stride condition; count passes for the width you load.3


"__restrict__ is just documentation."It changes the load to the read-only path (LDG.E.CONSTANT); if the pointers alias, results can be wrong.2


"__constant__ is a fast table for any lookup."Only when the lanes of a warp read the same address; different addresses are served one at a time.5


"pin_memory() before every .to(device) speeds things up."Pinning is a copy; done on the critical path it can be up to twice as slow. Let the DataLoader pin in the background.7


"A kernel at 15% of peak FLOP/s is badly written."Only if it is compute-bound. Place it on the roofline first: a softmax at the bandwidth roof is done.8


"cudaMalloc in the loop is fine."Allocation is expensive and can synchronise; use pools (cudaMallocAsync) or a caching allocator.7

  • nvcc -Xptxas -v (or cuobjdump --dump-resource-usage): registers, stack frame, spill bytes, static shared memory per kernel. In Triton, kernel.n_regs and kernel.n_spills on the compiled kernel, or the parent's Compiler explorer.
    • 

  • cuobjdump -sass: LDL/STL mean local memory; LDG.E.128 means vectorised; LDGSTS means asynchronous copy; .CONSTANT means the read-only path. This page's Memory instructions tab has every example.

  • Nsight Compute: Memory Workload Analysis (sectors per request, shared-memory wavefronts against ideal, L1/L2 hit rates), Speed of Light (fraction of peak memory and compute: the roofline position). From NVIDIA's docs; not run here.
    • 

  • Back-of-envelope first: bytes and FLOPs by hand, then section 8's recipe.

Interview questions, with short answers


What does "coalesced" mean, precisely?
The 32 addresses of one warp's load fall in as few 32-byte sectors as possible, so the bytes fetched equal the bytes used. Consecutive lanes on consecutive 4-byte words: 4 sectors for 128 bytes. It is about sectors, not about order: any permutation within the same sectors is equally good.


A kernel reads a [N, 3] float array of xyz points, one point per thread. What is wrong and how do you fix it?
Each lane reads 12 bytes at a 12-byte stride: three narrow loads per lane, misaligned for vector loads, each field read strided. Store x, y, z as separate arrays (struct of arrays), or pad to float4 and load 16 bytes per lane.


ptxas says "0 bytes spill stores" but "64 bytes stack frame". What is going on?
A local array indexed with a value known only at run time; registers cannot be indexed, so it lives in local memory. Make the indices compile-time constants (unroll, select) or use shared memory.


Why would capping registers make a kernel faster, and why might it make it slower?
Faster: fewer registers per thread fits more warps per SM, which hides memory latency. Slower: values that no longer fit spill to local memory, adding loads and stores. Which wins depends on whether the kernel was latency-bound; measure.


Shared memory tile float[32][32] read by columns: what happens, and give two fixes.
All 32 lanes hit the same bank: a 32-way conflict, 32 passes. Pad to [32][33] (row r starts in bank r), or swizzle the column index with XOR of the row (no wasted memory, keeps alignment).


What does cp.async (LDGSTS) buy over a normal load followed by a shared-memory store?
The data goes global to shared without occupying registers, the thread continues immediately, and with several shared buffers the next tile's copy overlaps this tile's math. The price is shared memory per stage.


When is __constant__ memory the right choice?
Small read-only data that all lanes of a warp read at the same address at the same time (a scale, coefficients indexed by loop counter). Lanes reading different entries are serialised by the number of distinct addresses.


Why does pinned memory matter for a training input pipeline?
Copies from pageable memory are staged through a pinned buffer by the driver and cannot run asynchronously; with pinned batches (DataLoader pin_memory=True) and non_blocking=True, the host-to-device copy overlaps the previous step's compute.


Your layernorm kernel runs at 85% of DRAM bandwidth. Should you optimise it further?
Not its inner loop: it is memory-bound and near the roof. Only moving fewer bytes helps: fuse it with the neighbouring op (residual add, the next matmul's prologue) or use a smaller dtype.
