GPU memory hierarchy: coalescing, shared memory, bank conflicts, registers and spills

GPU memory as the CUDA programmer sees it: sectors and coalescing, the caches, tiling and banks, registers and spills, constant memory, asynchronous copies and host memory, from real CUDA 13.4.2 compiler output and measurements on an Apple M1 Pro GPU (no NVIDIA GPU used). The core idea. A kernel is fast when the bytes it needs are already close to the arithmetic: fetch each byte from DRAM once, in whole 32-byte sectors, and reuse it from shared memory and registers as many times as the math needs.

Every byte comes up the same ladder; your code decides how often it climbs

Fig. 1 draws the rungs a CUDA programmer touches on an H100 SXM as plates, each as wide as the logarithm of its capacity: from 80 GB at the bottom to a few hundred KB per SM at the top. Step through it:

  1. DRAM (HBM3): 80 GB at 3.35 TB/s. Global memory (LDG, STG), local memory (LDL, STL) and constant memory (LDC) all live here, 478.8 cycles away. "Local" memory (spills) sits in DRAM with global memory: the name is its scope, not its place.
  2. L2: 50 MB for the whole GPU. Every DRAM access passes through it, 263.0 cycles away; it is where all SMs see the same data.
  3. Shared memory and L1: one SRAM pool per SM. Up to 228 KB per SM; shared memory (LDS, STS) at 29.0 cycles, L1 (caching LDG) at 40.7. LDGSTS and TMA fill shared memory straight from global memory.
  4. Registers: one thread's own. 65,536 x 32-bit per SM, up to 255 per thread, read by the ALUs directly. Per SM the register file (256 KB) is as large as the shared memory.
  5. The climb. Pinned host RAM reaches HBM only through the copy engines (cudaMemcpyAsync, DMA over PCIe or NVLink-C2C), copies rather than loads. A fast kernel brings each byte up from HBM once and reuses it many times at the top (the dot density here is illustrative).

Sizes for an H100 SXM (compute capability 9.0) from the CUDA Programming Guide, compute capabilities and NVIDIA's H100 page vendor spec; 256 KB = 65,536 × 4 bytes derived; load latencies in cycles measured on an H800 by Luo et al. Three questions for every array in a kernel
Where does it live (which rung)? How many times is each byte read (once: stream it; many times: stage it on chip)? In what order do neighbouring threads touch it (neighbours on neighbouring addresses, or not)? Sections 1 to 8 answer them for one space each; section 9 turns them into a verdict on one kernel.

1. Global loads: what one warp's load really fetches

A thread asks for 4 bytes, but DRAM and the caches do not deal in 4 bytes. NVIDIA's rule: "Global memory is accessed via 32-byte memory transactions", and the warp "coalesces the memory requests from all the threads in that warp into the number of memory transactions necessary" (Programming Guide 2.3.4.1). So the cost of a load is the number of distinct sectors its 32 addresses fall in. Fig. 2 puts one warp over 1 KB of DRAM: the fetched sectors rise and turn blue, the bytes some lane wanted inside them orange, the rest grey; the counts come from the page's sector model derived from the 32-byte rule.

  1. One warp, one load. 32 lanes each ask for 4 bytes; memory answers in 32-byte sectors, four to a 128-byte line.
  2. Coalesced: lane l reads float l. 32 lanes reading 32 consecutive floats: 128 bytes in 4 sectors, moved 128 B for 128 used, nothing wasted. Order within the sectors does not matter: any permutation of the same addresses costs the same.
  3. One field of a 32-byte struct, p[i].x. Each lane's 4 bytes sit in its own struct, so in its own sector: 32 sectors, 1,024 B moved for 128 used (12.5%). Stored as a struct of arrays, the same field needs 4 sectors again.
  4. Misaligned by 4 bytes. The same 128 contiguous bytes, starting mid-sector, span 5 sectors: 160 B moved for 128.
  5. 16 bytes per lane (float4). 512 B in 16 sectors, all of them used, in one instruction where 4-byte loads would need four.
  6. A random gather. Lanes scattered over a large array almost never share a sector: 32 sectors, 1,024 B for 128 (the addresses drawn are illustrative). On the M1 Pro a random gather fell to 1.5 GB/s, against 129 GB/s at stride 1.

The rule that follows: make threadIdx.x walk along the contiguous dimension of the array (for a row-major matrix, along a row).

2. The caches, and the few ways to steer them


You do not allocate cache; the hardware decides what stays. But two caches sit between your loads and DRAM, they behave differently, and the compiler gives you a few hints.




L1 (per SM)shares its SRAM with shared memory (section 3); caches global and local loads for that SM only. Not kept coherent with other SMs: "multiple L1 caches are not coherent for global data" (PTX ISA 9.4, cache operators).


L2 (whole GPU)every DRAM access goes through it, so it is where all SMs agree: "Global data is coherent at the L2 level" (same table). 40 MB on A100, 50 MB on H100 SXM, 96 MB on RTX 5090 vendor spec.


Read-only patha load the compiler may serve from the non-coherent texture/L1 path because nothing writes the data during the kernel. You ask for it with const T* __restrict__ or __ldg().




The read-only path. "Accesses to __global__ function const pointers marked with __restrict__ are compiled as read-only cache loads, similar to the PTX ld.global.nc or __ldg()" (C++ language extensions). compiled here: a plain const float* load becomes LDG.E; with __restrict__, or written __ldg(p), it becomes LDG.E.CONSTANT. The promise behind __restrict__ is that no other pointer in the kernel touches that memory. If you lie (an in-place kernel whose input and output alias), the result can be silently wrong.


Cache operators are per-instruction hints: __ldcs/__stcs (evict-first) for data read or written exactly once, such as an activation streamed through an elementwise kernel, so it does not push out data that will be reused; __ldcg skips L1, useful when another block may have just written the data. "Cache operators on load or store instructions are treated as performance hints only" (PTX ISA). Most ML kernels never use them; you meet them in hand-tuned kernels (FlashAttention, vLLM, ggml-cuda) and in Triton's eviction_policy argument to tl.load.

The free way to use L2: order the work


Blocks that run at the same time share L2. A tiled matmul that launches its output tiles row by row reads every B column panel for each row of tiles; launching them in groups of rows ("grouped" or "swizzled" block order) lets concurrently running blocks reuse the same A and B panels from L2. Triton's matmul tutorial counts it for 9 × 9 blocks: row-major "we need to load 90 blocks into SRAM to compute the first 9 output blocks", grouped "we only need to load 54 blocks".


Switch the order on the right: the same nine output tiles of C need 90 blocks loaded in row-major order and 54 in groups of three rows.






Same nine output tiles, two launch orders: 90 against 54 blocks loaded








The first nine output tiles of C (dark) need the A row panels to their left and the B column panels above them (shaded); each panel is nine blocks. Row-major: 1 A panel + 9 B panels = 9 + 81 = 90 blocks. Grouped: 3 + 3 panels = 27 + 27 = 54 derived, as Triton's tutorial states. Writing kernels builds the grouped launch.








Keeping a buffer in L2 on purpose (persisting accesses, compute capability 8.0 and later)


"A portion of the L2 cache can be set aside to be used for persisting data accesses to global memory" (Programming Guide 4.14, L2 cache control). Two calls, from that page:


size_t size = min(int(prop.l2CacheSize * 0.75), prop.persistingL2CacheMaxSize);
cudaDeviceSetLimit(cudaLimitPersistingL2CacheSize, size);   // set aside up to 3/4 of L2

stream_attribute.accessPolicyWindow.num_bytes = num_bytes;
stream_attribute.accessPolicyWindow.hitRatio  = 0.6;           // fraction of accesses marked persisting
stream_attribute.accessPolicyWindow.hitProp   = cudaAccessPropertyPersisting;
stream_attribute.accessPolicyWindow.missProp  = cudaAccessPropertyStreaming;
cudaStreamSetAttribute(stream, cudaStreamAttributeAccessPolicyWindow, &stream_attribute);


It is disabled under MIG, and fixed at server start under MPS (same page). It helps when a few tens of MB are read by many consecutive kernels in one stream while other data streams past; it cannot help data larger than the set-aside. not run here: no NVIDIA GPU.

3. Tiling: fetch once, reuse from shared memory


Shared memory is on-chip SRAM inside the SM, visible to all threads of one block and managed by your code. The pattern is always the same: threads cooperatively copy a tile from global memory into a __shared__ array (each thread one or a few elements, coalesced), wait at __syncthreads(), then all read the tile many times at on-chip speed. On a matmul tile of C = A × B: without shared memory every thread fetches its own row of A and column of B, so each element is fetched once per thread that needs it; with shared memory the block fetches each element once per tile.


Fig. 3 runs it on one block of 4 × 4 threads computing a 4 × 4 tile of C with K = 8, in two phases of 4 illustrative sizes (moved here from the parent page, whose section 4 now links to this page). kernel<<<grid, block, 200 * 1024>>>(...);


The carveout splits the SM's SRAM between L1 and shared memory: whatever shared memory takes, L1 loses. In Triton you never write these calls; a block size and num_stages that need too much raise OutOfResources for shared memory at compile time (triton/runtime/errors.py). And what a block takes is reserved for the whole kernel, so it sets how many blocks share an SM: Writing kernels, section 5, measured a 16 KB staging tile that tripled a fused matmul's threadgroup memory (8 KB to 24 KB) and made the fused kernel slower than not fusing measured on Apple M1 Pro GPU.


Only some carveouts exist (the compute capability 12.0 example)


"for devices of compute capability 12.0, which have a maximum shared memory capacity of 100KB, setting the carveout to 50% will result in 64KB of shared memory, not 50KB, because devices of compute capability 12.0 support shared memory sizes of 0, 8, 16, 32, 64, and 100" (Programming Guide 3.2).











4. Banks: when a tile read takes turns


Shared memory is divided into 32 banks: "successive 32-bit words map to successive banks", and "Each bank has a bandwidth of 32 bits per clock cycle" (Programming Guide 2.3.4.2). Lanes reading different words of the same bank take turns (a bank conflict); lanes reading the same word get it broadcast. The classic case is a transpose: reading a column of float tile[32][32] puts all 32 lanes in one bank, 32 passes. Fig. 4 shows six accesses of one warp; each cube is a word a bank must deliver, stacked by pass, the counts from the page's bank model derived:



    

  1. A row read: lane l reads word l. 32 consecutive words land on 32 different banks: 1 pass, the ideal.
    2. 

  2. A column of float tile[32][32]. The classic transpose: every row is 32 words long, so column c is in bank c in every row, and all 32 lanes queue on one bank: 32 passes.
    3. 

  3. Padded to [32][33]. One unused word per row makes row r start in bank r, so the column spreads over all 32 banks: 1 pass again.
    4. 

  4. XOR swizzle: element (r, c) stored at column c ^ r. Every row and every column on distinct banks, with no padding: 1 pass.
    5. 

  5. 16-byte elements (float4), lanes 128 bytes apart. Lane l's 16 bytes are words 32l to 32l + 3, banks 0 to 3 for every lane: 32 passes where 4 would do.
    6. 

  6. The same at a stride of 9 elements (144 bytes). The lanes spread over all 32 banks: 4 passes, the ideal.
    7. 









Try any layout or stride


measured on Apple M1 Pro GPU (the parent topic's simulator runs): threadgroup-memory reads with a lane stride of 32 ran at 113 billion reads per second against 318 at stride 1 and 394 at stride 33, the same signature (Apple does not document its banks).


Any stride, in one rule (4-byte words)
Word w lives in bank w mod 32, so a warp reading with a lane stride of s words has a conflict of degree gcd(s, 32): a stride of 2 puts lanes l and l + 16 in one bank (a 2-way conflict, two passes), a stride of 3 or any odd stride is free, a stride of 32 is the worst (the Programming Guide draws both cases in its Figure 15) derived. A conflict only costs time when shared memory is the bottleneck: in the parent topic's 32 × 32 transpose on the M1 Pro, DRAM was the limit and padding changed nothing measurable measured on Apple M1 Pro GPU.


Wide accesses. Real kernels load 8 or 16 bytes per lane, and then the rule gives a floor, not a conflict-free promise: a warp asking for 32 × 16 = 512 bytes needs at least 512 / 128 = 4 passes, since 32 banks deliver 128 bytes per pass. The cost is the passes of the busiest bank. NVIDIA's own example: with 16-byte (int4) elements "each set of eight threads loads a row", and a column-wise store "must be serialized, resulting in eight store transactions, giving an eight-way bank conflict" (Programming Guide 4.12, TMA swizzle). The current guide does not spell out how 8-byte accesses are split.




measured on Apple M1 Pro GPU: bytes per second read from threadgroup memory by 131,072 threads, 16 KB per threadgroup, median of 3 runs. With 16-byte elements: 1,893 GB/s at a lane stride of 1 element, 1,049 at 4, 565 at 8, and 1,905 at 9, the signature of 4-byte banks the rule predicts (inference: Apple documents neither bank count nor width). Wide reads also moved more bytes per second than 4-byte reads (1,108 GB/s at stride 1, noisy under load): on chip as off chip, fewer and wider accesses win.

Swizzles: the libraries' answer. Padding breaks the alignment that 16-byte and TMA copies need and wastes memory, so libraries permute instead: element (r, c) is stored at column c XOR f(r), which keeps every row and every column on distinct banks (the XOR layout above). Hopper's TMA engine writes tiles already swizzled: "the TMA engine can be instructed to 'swizzle' the data before storing it in shared memory", and with CU_TENSOR_MAP_SWIZZLE_128B "each matrix element is from a different bank for both the rows and columns" (same page). CUTLASS's layout algebra that generalises this is on Libraries and tensor cores.


Beyond one block: distributed shared memory (Hopper clusters)


On Hopper and later, blocks of a cluster can read each other's shared memory (distributed shared memory, about 180 cycles in Luo et al.'s H800 measurements against 29 for local shared memory independent); the hardware side is on GPU architecture, section 8, the launch side on The CUDA programming model.









5. Registers, spills, and arrays that fall into local memory


Registers are the only storage the arithmetic units read directly, and they are rationed: 65,536 32-bit registers per SM on every current NVIDIA GPU, shared by all resident threads, at most 255 per thread. A thread that keeps more values alive than it has registers spills some to local memory. Fast kernels (register-tiled matmul, FlashAttention) keep large pieces of the output in registers on purpose, so they live right at this edge.

Two lessons. Below what the kernel needs, every register removed becomes spill traffic: at a cap of 32 each thread writes and rereads over a kilobyte. Above it, ptxas does not stop at what it needs: on sm_90a it used every register it was allowed (192, 224, 255), presumably to schedule loads earlier, and each extra register lowers how many warps fit. Is "uses every register it is allowed" documented? (only for launch bounds)


NVIDIA documents it for launch bounds: "If both minBlocksPerMultiprocessor and maxThreadsPerBlock are specified, the compiler may increase register usage up to L in order to reduce the number of instructions and better hide the latency" (C++ language extensions, launch bounds); the same happening under -maxrregcount is observed here, not documented.

Local memory without any register pressure


An array can land in local memory while the kernel uses only a few registers. The compiler puts there "Arrays for which it cannot determine that they are indexed with constant quantities, Large structures or arrays that would consume too much register space, Any variable if the kernel uses more registers than available" (Programming Guide 2.3.3.4, local memory). Registers have no addresses, so h[b] with b known only at run time needs memory. Two versions of a per-thread 16-bin histogram, compiled here for sm_90a (right):


The first uses ; the four STL.128 zero the 64-byte array in local memory and every update is an LDL and an STL. The second does 16 compare-and-adds per update but keeps all 16 bins in registers (). Local memory is interleaved so that "consecutive 32-bit words are accessed by consecutive thread IDs. Accesses are therefore fully coalesced as long as all threads in a warp access the same relative address" (same section); here every lane picks its own bin, so the accesses scatter too.


measured on Apple M1 Pro GPU: the same two kernels in Metal, 262,144 threads × 1,024 updates each: 7.08 ms with the run-time index against 4.49 ms with constant indices, 1.58 times slower despite a sixteenth of the arithmetic. Apple's compiler faces the same problem (registers are not addressable) and makes the same choice.


Predict: ptxas reports "64 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads, Used 22 registers". What is in the 64 bytes?




Zero spill bytes, yet a stack frame: an array the compiler could not promote to registers, here 16 floats = 64 bytes. Fix it by making every index a compile-time constant (unrolled loops, selects), or move the array to shared memory if lanes need different entries.


What you cannot control: register bank conflicts


"The compiler and hardware thread scheduler will schedule instructions as optimally as possible to avoid register memory bank conflicts. An application has no direct control over these bank conflicts. In particular, there is no register-related reason to pack data into vector data types such as float4" (Best Practices Guide 10.2.7).








Run-time index: h[bins[k * 4096 + t] & 15] += 1.f;



Constant indices only: for (j = 0; j < 16; ++j) h[j] += (b == j) ? 1.f : 0.f;










6. Constant memory and kernel parameters


"There is a total of 64 KB constant memory on a device. The constant memory space is cached ... Accesses to different addresses by threads within a warp are serialized, thus the cost scales linearly with the number of unique addresses read by all threads within a warp ... If all threads of a warp access the same location, then constant memory can be as fast as a register access" (Best Practices Guide 10.2.6). So it suits values every lane reads at once (a scale, a bias, filter taps, a lookup indexed by loop counter, not by lane), and you use it more than you think, because every kernel argument lives there. In the SASS, a constant indexed at compile time goes into a uniform register (ULDC, one copy for the whole warp) and straight into the FFMA; an index known only at run time takes an LDC, where the per-address serialisation applies if lanes disagree.

Texture memory is the other read-only cached path: "optimized for 2D spatial locality" with hardware filtering and boundary handling (Best Practices Guide 10.2.5). It matters for image resampling; ML kernels almost never use it, and const __restrict__ loads already use the same cache.

7. Asynchronous copies: loading the next tile while computing this one


Section 3's tile loop, written plainly, sends every load global memory to a register, then register to shared memory, and the SM sits idle for a full memory latency (about 479 cycles on an H800) at the start of every tile: idle time, plus registers held just to carry data in transit. Since Ampere (compute capability 8.0) one instruction copies global to shared memory directly, without a register in between, and the thread does not wait for it: "This not only reduces register usage by copying the data directly to shared memory, but also ensures all loads from global memory are in-flight" (Programming Guide 4.12.1, LDGSTS). With two or more shared-memory buffers (stages), the copy for tile t + 1 runs while the math on tile t proceeds. Fig. 5 runs one block's loop over 8 tiles through the page's pipeline model illustrative: 479 cycles per copy (the H800 global latency, Luo et al.) and 200 cycles of math per tile.


    

  1. Synchronous, one buffer. Copy through a register, wait, compute, repeat: 8 tiles take 5,432 cycles, the SM busy 29% of them.
    2. 

  2. LDGSTS: straight into shared memory. No register in between. With one buffer that saves registers, not time: the next copy still waits for the buffer to be free.
    3. 

  3. Two stages. While the SM computes on one buffer, the next tile streams into the other: 2,916 cycles, busy 55%.
    4. 

  4. Three stages. Two copies in flight during each tile's math: 2,237 cycles, busy 72%.
    5. 

  5. Four stages. 2,079 cycles, busy 77%: the floor, one latency plus all the math (479 + 8 × 200 = 2,079 cycles). Every stage is another tile of shared memory.
    6. 









compiled here for sm_90a, the same tile loop written both ways (right):


On the left the compiler unrolled the loop and issued four 16-byte loads ahead, each parked in four registers until its STS.128: it hides latency by spending registers. On the right LDGSTS writes shared memory directly; LDGDEPBAR closes a group of copies (the commit) and DEPBAR.LE SB0, 0x1 waits until at most one group is still in flight (the wait_prior(1)). The .BYPASS matches the guide: "copying 16-bytes enables the L1 BYPASS mode, in which case the L1 is not polluted". The copies are per thread, so a __syncthreads() is still needed before other threads read the tile.






Synchronous: s[tid] = a[t * 256 + tid];



Two stages: __pipeline_memcpy_async, __pipeline_commit, __pipeline_wait_prior(1)









The cost. Each stage is another tile of shared memory, so stages trade against block size and occupancy (section 3): this is exactly Triton's num_stages, and Triton 3.8.0 compiles a plain matmul's tile loads to LDGSTS on sm_80 (the parent's Compiler explorer). Hopper's TMA goes further: one thread issues a copy of a whole multi-dimensional tile (up to 5 dimensions), completion is signalled on a shared-memory barrier, and the tile can land swizzled (section 4). The TMA programming model and the warp-specialised producer/consumer kernels built on it are on Libraries and tensor cores; a full pipelined matmul on Writing kernels; the copy engines inside the SM on GPU architecture, section 8.

A copy can start only when its buffer is free (the tile that last used it has been computed); a tile can be computed only when its copy has landed. illustrative: 479 cycles per copy (H800 global latency, Luo et al.) and 200 cycles of math per tile; it ignores bandwidth limits and the other blocks on the SM, which also hide latency. 8. Host memory: pinned, mapped and managed


Training data and checkpoints start in host RAM; a GPU's copy engines move them over PCIe or NVLink-C2C by DMA, and DMA needs physical pages that will not move. Ordinary malloc memory can be swapped or relocated by the OS, so it cannot be the DMA target. How CUDA bridges that decides whether your input pipeline overlaps with compute.




Pageable (default)"When CUDA sends pageable data from CPU to GPU, it must first create a page-locked copy of that data before making the transfer" (PyTorch, non_blocking and pin_memory, Apr 1, 2026): an extra CPU memcpy, and the call cannot run in the background.


Pinned (page-locked)cudaMallocHost / cudaHostAlloc, or cudaHostRegister on existing memory. "Page-locked host memory is required for asynchronous copies between the CPU and GPU" and "also improves performance of synchronous copies" (Programming Guide 2.6.3).


Mapped (zero copy)pinned memory the GPU reads directly over the interconnect, uncached on the GPU. "On integrated GPUs ... mapped pinned memory is always a performance gain ... On discrete GPUs, mapped pinned memory is advantageous only in certain cases" (Best Practices Guide 10.1.3).


Managed (unified)cudaMallocManaged: one pointer for both sides; pages migrate on first touch. Prefetch with cudaMemPrefetchAsync and give hints with cudaMemAdvise, or it is slow; the driver's fault path is on Virtualization and the GPU driver stack, section 11.




In PyTorch.


    

  • DataLoader(..., pin_memory=True) pins each batch in a background thread; then batch.to("cuda", non_blocking=True) returns at once and the copy overlaps with the previous step's compute (stream ordering keeps it safe for kernels that use the batch; overlap itself is on Streams, CUDA graphs and multi-GPU programming).
    • 

  • Pinning by hand on the critical path does not help: "Using tensor.pin_memory().to(device, non_blocking=True) can be up to twice as slow as a straightforward tensor.to(device)" (PyTorch tutorial above), because the pin is itself a copy.
    • 

  • The other direction is a correctness trap: after cuda_tensor.to("cpu", non_blocking=True) "there is no guarantee that the data read on GPU is valid without explicit synchronization" (same tutorial; it means the CPU-side data); synchronise (or wait on an event) before reading it.
    • 



Transfer rates, the price of pinning, device allocation, and the Apple contrast


The Best Practices Guide's own example is dated: "On PCIe x16 Gen3 cards, for example, pinned memory can attain roughly 12 GB/s transfer rates" vendor figure; today's links are faster (PCIe Gen5 x16 and NVLink-C2C on Interconnects and scaling), but the rule is the same. Pinning has a price: "Pinned memory should not be overused ... the pinning of system memory is a heavyweight operation" (same guide); pinned pages count against the locked-memory limit (Virtual memory, section 9). not run here: this laptop has no discrete GPU.


Device allocation is not free either. "Device memory allocation and de-allocation via cudaMalloc() and cudaFree() are expensive operations. It is recommended to use cudaMallocAsync() and cudaFreeAsync() which are stream ordered pool allocators" (Best Practices Guide 10.3). PyTorch goes further with its own caching allocator, which is why nvidia-smi shows memory "used" after tensors are freed; it is simulated from its source on Memory allocators, section 9.


The Apple contrast. On this laptop there is no host-device copy to make: "Apple silicon has a unified memory architecture. The CPU and GPU have direct access to the same memory pool" (MLX, unified memory). That is the integrated case of the zero-copy rule above, and why every M1 number on this page measures the GPU's own memory system with no PCIe in the way. Grace Hopper and Grace Blackwell get part of the way on NVIDIA with a coherent CPU-GPU link (Memory technology, section 7).








9. Judge one kernel: is it the memory?


After the rules above you still need a verdict on one kernel: is it close to what the GPU can do, and against which limit? The roofline gives it (the model, ridge points per chip and MFU are on Performance math and the Topic: hardware Roofline lab). The programmer's recipe:


    

  1. Count the bytes the kernel must move if every input is read once and every output written once (not what it actually moves: that is what you are judging), and the FLOPs (an FMA is 2).
    2. 

  2. Time it honestly (warm-up, many repetitions, synchronise: Profiling, benchmarking and correctness), then divide: achieved bandwidth = bytes / time, achieved FLOP/s = FLOPs / time, arithmetic intensity = FLOPs / bytes.
    3. 

  3. Compare with the roof at that intensity, min(peak FLOP/s, intensity × peak bandwidth). Near the slanted part: memory-bound, so move fewer bytes (fuse, use smaller types); a softmax at the bandwidth roof is done, even at 15% of peak FLOP/s. Near the flat part: compute-bound, so use tensor cores or do less math. Far below both: the access pattern or latency hiding is broken, and sections 1 to 7 are where to look.
    4. 



The parent's kernels on this laptop show all three verdicts: the eager softmax (five kernels, each a full pass) sits at a quarter of the bandwidth roof that the fused one reaches on the same data; the naive matmul has an intensity of 341 FLOP per byte, ten times the ridge, yet runs at a fraction of the compute roof, because its threads re-read A and B from memory for every output (no tiles, section 3). Interview rehearsal (nine questions with short answers)


What does "coalesced" mean, precisely?
The 32 addresses of one warp's load fall in as few 32-byte sectors as possible, so the bytes fetched equal the bytes used. Consecutive lanes on consecutive 4-byte words: 4 sectors for 128 bytes. It is about sectors, not about order: any permutation within the same sectors is equally good.


A kernel reads a [N, 3] float array of xyz points, one point per thread. What is wrong and how do you fix it?
Each lane reads 12 bytes at a 12-byte stride: three narrow loads per lane, misaligned for vector loads, each field read strided. Store x, y, z as separate arrays (struct of arrays), or pad to float4 and load 16 bytes per lane.


ptxas says "0 bytes spill stores" but "64 bytes stack frame". What is going on?
A local array indexed with a value known only at run time; registers cannot be indexed, so it lives in local memory. Make the indices compile-time constants (unroll, select) or use shared memory.


Why would capping registers make a kernel faster, and why might it make it slower?
Faster: fewer registers per thread fits more warps per SM, which hides memory latency. Slower: values that no longer fit spill to local memory, adding loads and stores. Which wins depends on whether the kernel was latency-bound; measure.


Shared memory tile float[32][32] read by columns: what happens, and give two fixes.
All 32 lanes hit the same bank: a 32-way conflict, 32 passes. Pad to [32][33] (row r starts in bank r), or swizzle the column index with XOR of the row (no wasted memory, keeps alignment).


What does cp.async (LDGSTS) buy over a normal load followed by a shared-memory store?
The data goes global to shared without occupying registers, the thread continues immediately, and with several shared buffers the next tile's copy overlaps this tile's math. The price is shared memory per stage.


When is __constant__ memory the right choice?
Small read-only data that all lanes of a warp read at the same address at the same time (a scale, coefficients indexed by loop counter). Lanes reading different entries are serialised by the number of distinct addresses.


Why does pinned memory matter for a training input pipeline?
Copies from pageable memory are staged through a pinned buffer by the driver and cannot run asynchronously; with pinned batches (DataLoader pin_memory=True) and non_blocking=True, the host-to-device copy overlaps the previous step's compute.


Your layernorm kernel runs at 85% of DRAM bandwidth. Should you optimise it further?
Not its inner loop: it is memory-bound and near the roof. Only moving fewer bytes helps: fuse it with the neighbouring op (residual add, the next matmul's prologue) or use a smaller dtype.
