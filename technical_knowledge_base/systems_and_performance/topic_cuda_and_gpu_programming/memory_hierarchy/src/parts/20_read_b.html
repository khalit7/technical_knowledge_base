2. The caches, and the few ways to steer them

The problem. You do not allocate cache; the hardware decides what stays. But two caches sit between your loads and DRAM, they behave differently, and the compiler gives you a handful of hints. Knowing them explains suffixes you will see in every disassembly and one class of bug.

L1 (per SM)shares its SRAM with shared memory (section 3); caches global and local loads for that SM only. Not kept coherent with other SMs: "multiple L1 caches are not coherent for global data" ({{PTX ISA 9.4, cache operators|https://docs.nvidia.com/cuda/parallel-thread-execution/index.html}}).
L2 (whole GPU)every DRAM access goes through it, so it is where all SMs agree: "Global data is coherent at the L2 level" (same table). 40 MB on A100, 50 MB on H100 SXM, 96 MB on RTX 5090 vendor spec.
Read-only patha load the compiler may serve from the non-coherent texture/L1 path because nothing writes the data during the kernel. You ask for it with const T* __restrict__ or __ldg().

The read-only path. "Accesses to __global__ function const pointers marked with __restrict__ are compiled as read-only cache loads, similar to the PTX ld.global.nc or __ldg()" ({{C++ language extensions|https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html}}). compiled here: a plain const float* load becomes LDG.E; the same load with __restrict__, or written __ldg(p), becomes LDG.E.CONSTANT. The promise behind __restrict__ is that no other pointer in the kernel touches that memory. If you lie (an in-place kernel whose input and output alias), the compiler may reorder or cache, and the result is silently wrong.

Cache operators. Every load and store can carry a hint. The intrinsics map to PTX operators, and the table shows what CUDA 13.4.2 turned each into on three generations compiled here. The meanings are quoted from the PTX ISA; the reading of the SASS suffixes (EF for evict-first, STRONG.GPU for "performed at the L2, the GPU's point of coherence") is an inference from the names and the PTX definitions, since NVIDIA does not document SASS.

In practice: __ldcs/__stcs (evict-first) suit data read or written exactly once, such as a large activation streamed through an elementwise kernel, so it does not push out data that will be reused; __ldcg skips L1, useful when another block may have just written the data; .lu exists mainly for restoring spills. They are hints: "Cache operators on load or store instructions are treated as performance hints only" (PTX ISA). Most ML kernels never use them; you will meet them in hand-tuned kernels (FlashAttention, vLLM, ggml-cuda) and in Triton's eviction_policy argument to tl.load.

Keeping a buffer in L2 on purpose

Since compute capability 8.0 you can reserve part of L2 for one address range: "A portion of the L2 cache can be set aside to be used for persisting data accesses to global memory" ({{Programming Guide 4.14, L2 cache control|https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/l2-cache-control.html}}). Two calls, from that page:

size_t size = min(int(prop.l2CacheSize * 0.75), prop.persistingL2CacheMaxSize);
cudaDeviceSetLimit(cudaLimitPersistingL2CacheSize, size);   // set aside up to 3/4 of L2
stream_attribute.accessPolicyWindow.base_ptr  = ptr;           // the hot buffer
stream_attribute.accessPolicyWindow.num_bytes = num_bytes;
stream_attribute.accessPolicyWindow.hitRatio  = 0.6;           // fraction of accesses marked persisting
stream_attribute.accessPolicyWindow.hitProp   = cudaAccessPropertyPersisting;
stream_attribute.accessPolicyWindow.missProp  = cudaAccessPropertyStreaming;
cudaStreamSetAttribute(stream, cudaStreamAttributeAccessPolicyWindow, &stream_attribute);

It is disabled under MIG, and fixed at server start under MPS (same page). It helps when a few tens of MB are read by many consecutive kernels in one stream while other data streams past; it cannot help data larger than the set-aside. not run here: no NVIDIA GPU.

The free way to use L2: order the work. Blocks that run at the same time share L2. A tiled matmul that launches its output tiles row by row reads each B column panel once per row of tiles; launching them in groups of rows ("grouped" or "swizzled" block order) lets concurrently running blocks reuse the same A and B panels from L2. {{Triton's matmul tutorial|https://triton-lang.org/main/getting-started/tutorials/03-matrix-multiplication.html}} shows the reordering as "L2 cache optimizations"; {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}} builds it.

How fast each cache rung is on this laptop's GPU (about 1,239 GB/s for working sets up to 128 KB, 579 at 1 MB, 318 at 32 MB, 127.5 at 1 GB) is measured on {{Memory technology|n:3f05c17b0d0d818ab063e327e3d7009f}}, section 3.

3. Shared memory in practice: declaring it, sizing it, wide accesses, swizzles

The problem it solves (the parent's section 3 has the full motivation): data that many threads of a block read many times should be fetched from DRAM once and then read from on-chip SRAM. Shared memory is that SRAM, managed by your code.

Three ways to declare it, as the compiler sees them

KernelDeclarationptxas -v (sm_90a)
padded transpose tile__shared__ float t[32][33];
swizzled transpose tile__shared__ float t[32][32]; indexed t[y][x ^ y]
dynamicextern __shared__ float4 s[]; sized by the third launch parameter <<<grid, block, bytes>>>

compiled here: static arrays show up in the compiler's report (32 × 33 × 4 = 4,224 bytes; the swizzle saves the padding column); dynamic shared memory is invisible at compile time, so the occupancy calculator must be told the launch size.

Sizes and the opt-in. Per SM: 164 KB on A100 (compute capability 8.0), 228 KB on H100 and B200 (9.0, 10.0), 100 KB on RTX 3090, 4090 and 5090 (8.6, 8.9, 12.0); one block may use 1 KB less, which CUDA reserves per block ({{compute capabilities|https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html}}). But "Kernels relying on shared memory allocations over 48 KB per block are architecture-specific. As such they must use dynamic shared memory rather than statically-sized arrays and require an explicit opt-in" ({{Programming Guide 3.2, L1/shared balance|https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html}}):

cudaFuncSetAttribute(kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, 200 * 1024);
cudaFuncSetAttribute(kernel, cudaFuncAttributePreferredSharedMemoryCarveout, cudaSharedmemCarveoutMaxShared);
kernel<<<grid, block, 200 * 1024>>>(...);

The carveout splits the SM's SRAM between L1 and shared memory, and only some splits exist: "for devices of compute capability 12.0, which have a maximum shared memory capacity of 100KB, setting the carveout to 50% will result in 64KB of shared memory, not 50KB, because devices of compute capability 12.0 support shared memory sizes of 0, 8, 16, 32, 64, and 100" (same page). Whatever shared memory takes, L1 loses. In Triton you never write these calls; a block size and num_stages that need too much raise OutOfResources for shared memory at compile time ({{triton/runtime/errors.py|https://github.com/triton-lang/triton/blob/main/python/triton/runtime/errors.py}}).

More shared memory is not free. What a block takes is reserved for the whole kernel, so it sets how many blocks share an SM. {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}, section 5, measured it on the M1 Pro measured on Apple M1 Pro GPU: a 16 KB staging tile added to a fused matmul epilogue tripled the kernel's threadgroup memory (8 KB to 24 KB), fewer threadgroups fit on each GPU core, and the fused kernel ran slower than not fusing at all.

Banks with wide accesses

The rule (32 banks, "successive 32-bit words map to successive banks", "Each bank has a bandwidth of 32 bits per clock cycle") and the classic 32 × 32 transpose are in the parent's {{GPU simulator|n:3c65c17b0d0d81c39f34d5e070d783c1}}. Real kernels load 8 or 16 bytes per lane, and the rule then gives a floor, not a conflict-free promise: a warp asking for 32 × 16 = 512 bytes needs at least 512 / 128 = 4 passes, since 32 banks deliver 128 bytes per pass. The cost is the number of passes the busiest bank needs. NVIDIA's own example: with 16-byte (int4) elements "each set of eight threads loads a row", and a column-wise store "must be serialized, resulting in eight store transactions, giving an eight-way bank conflict" ({{Programming Guide 4.12, asynchronous copies, TMA swizzle|https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/async-copies.html}}). The current guide does not spell out how 8-byte accesses are split; the {{Access lab|#t-acc}} counts passes from the 32-bit rule alone and says so.

Predict: each lane reads one float4 (16 bytes) from shared memory, lanes 128 bytes apart (lane l reads element 8l). How many passes against the ideal 4?
Lane l's 16 bytes are words 32l to 32l + 3, which are banks 0 to 3 for every lane. Banks 0 to 3 each serve 32 different words: 32 passes, 8 times the ideal. A stride of 9 elements (144 bytes) spreads them out again.

measured on Apple M1 Pro GPU: bytes per second read from threadgroup memory (Apple's shared memory) by 131,072 threads, 16 KB per threadgroup, median of 3 runs. With 16-byte elements: 1,893 GB/s at a lane stride of 1 element, 1,049 at 4, 565 at 8, and 1,905 at 9, the signature of 4-byte banks that the rule predicts (Apple documents neither its bank count nor width; this is inference from the measurement). Wide reads also moved more bytes per second than 4-byte reads (1,108 GB/s at stride 1, noisy under load), so on chip as well as off chip, fewer and wider accesses win.

Swizzles: the libraries' answer

Padding ([32][33]) breaks the alignment that 16-byte and TMA copies need and wastes memory, so libraries permute instead: element (r, c) is stored at column c XOR f(r), which keeps every row and every column on distinct banks. Hopper's TMA engine writes tiles already swizzled: "the TMA engine can be instructed to 'swizzle' the data before storing it in shared memory", and with CU_TENSOR_MAP_SWIZZLE_128B "each matrix element is from a different bank for both the rows and columns" (same page). The {{Access lab|#t-acc}} shows plain, padded and XOR layouts side by side; CUTLASS's layout algebra that generalises this is on {{Libraries and tensor cores|n:3c65c17b0d0d81a7adcaebee2f44a087}}.

Beyond one block. On Hopper and later, blocks of a cluster can read each other's shared memory (distributed shared memory, about 180 cycles in Luo et al.'s H800 measurements against 29 for local shared memory independent); the hardware side is on {{GPU architecture|n:3c65c17b0d0d810682aae39bd614ec64}}, section 8, the launch side on {{The CUDA programming model|n:3c65c17b0d0d8162865eec15d9dae87e}}.
