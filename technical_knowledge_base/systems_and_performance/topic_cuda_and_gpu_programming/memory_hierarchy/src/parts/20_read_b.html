1. Global loads: what one warp's load really fetches

A thread asks for 4 bytes, but DRAM and the caches do not deal in 4 bytes. NVIDIA's rule: "Global memory is accessed via 32-byte memory transactions", and the warp "coalesces the memory requests from all the threads in that warp into the number of memory transactions necessary" ({{Programming Guide 2.3.4.1|https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html}}). So the cost of a load is the number of distinct sectors its 32 addresses fall in. 32 lanes reading 32 consecutive floats: 128 bytes, four sectors, nothing wasted. 32 lanes each 32 bytes or more apart: 32 sectors, 1,024 bytes moved for 128 used. The rule that follows: make threadIdx.x walk along the contiguous dimension of the array (for a row-major matrix, along a row). Order within the sectors does not matter: any permutation of the same addresses costs the same.

Type any pattern: the sectors one warp fetches

measured on Apple M1 Pro GPU (bars, the parent's {{GPU simulator|n:3c65c17b0d0d81c39f34d5e070d783c1}} runs, 4M floats, median of 3 runs): useful bandwidth by float stride, the current stride highlighted. Stride 32 is 6.0 times slower than stride 1, less than the 8 times as many sectors the NVIDIA rule gives, because caches catch some wasted bytes and many requests are in flight; a random gather fell to 1.5 GB/s. Apple does not document its transaction size: the shape transfers, not the knee. The models are checked against a Python reference on 1,000 patterns (src/check/check_js.mjs).

In a real kernel: in the parent's {{Kernel lab|n:3c65c17b0d0d81c39f34d5e070d783c1}}, a naive 2,048 matmul whose threads walked down columns took 229.2 ms on the M1 Pro; swapping which index follows the thread index, nothing else, brought it to 47.5 ms measured on Apple M1 Pro GPU.

Predict: particles stored as a struct of eight floats (32 bytes each). A kernel reads only p[i].x. How many sectors does one warp fetch, and what fraction of the fetched bytes is used?
32 sectors, 1,024 bytes fetched for 128 used. Each lane's 4 bytes sit in its own 32-byte struct, so every lane needs its own sector. Store each field as its own array (struct of arrays) and the same warp needs 4 sectors.

measured on Apple M1 Pro GPU: 16M particles of 32 bytes (512 MB), median of 3 runs of 7 trials (brackets: fastest and slowest run; load average 9.2 to 9.8 while other agents worked). One field from the structs took 3.66 ms, the same as all eight fields (3.66 ms): the GPU fetched every byte either way. The field in its own array took 1.03 ms, 3.6 times faster; the ratio of bytes moved (512 MB read + 64 MB written against 64 + 64 MB) is 4.5, the gap being the smaller transfer's fixed costs derived: 3.66 / 1.03 and 576 / 128.

Misaligned. 128 contiguous bytes that start mid-sector span five sectors (the second toggle above). "Memory allocated through the CUDA Runtime API, such as via cudaMalloc(), is guaranteed to be aligned to at least 256 bytes" ({{Best Practices Guide 10.2.1.3|https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html}}), so misalignment comes from you: a view with a storage offset (x[:, 1:]), a block size not a multiple of 32, a packed header before the data.

Measured: what misalignment costs in practice (less than the sector count says)

NVIDIA measured this on a V100: "we would expect approximately 4/5th of the memory throughput", but got about 9/10 "because adjacent warps reuse the cache lines their neighbors fetched" (same guide) vendor measurement. The parent's simulator found no measurable penalty for a one-float offset on the M1.

Same bytes, a quarter of the load instructions, four times the bytes in flight per instruction. NVIDIA: vectorised loads "reduce the total number of instructions, reduces latency, and improves bandwidth utilization", but "These instructions require aligned data" and "using vectorized loads increases register pressure and reduces overall parallelism" ({{CUDA Pro Tip: vectorized memory access|https://developer.nvidia.com/blog/cuda-pro-tip-increase-performance-with-vectorized-memory-access/}}, updated Aug 4, 2025). The .CONSTANT suffix comes from const __restrict__ (section 2).


Measured: load width on a plain copy (M1 Pro, why width did not matter there)




measured on Apple M1 Pro GPU: a 256 MB copy ran at about the same speed with 4-, 8- and 16-byte accesses (spread across runs 145 to 169 GB/s). With 64 million threads in flight there is enough memory parallelism either way, so a plain copy is limited by DRAM, not instructions. Width pays off when a kernel has few threads per byte or many other instructions competing for issue slots: the case in matmul and attention kernels, which is why they load 16 bytes at a time (and why section 7's asynchronous copy is 16 bytes wide).




When it matters for training, and how to check


  • Layouts. A fused QKV projection stored as [tokens, 3, heads, dim] and read one head at a time; channels-last against channels-first; a transposed weight read along the wrong axis. If the innermost index your threads walk is not the innermost dimension in memory, you pay the stride.
    • 

  • Views. Slicing makes a tensor non-contiguous or misaligned; PyTorch's elementwise kernels check alignment before using vector loads (can_vectorize_up_to in {{ATen's MemoryAccess.cuh|https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/cuda/MemoryAccess.cuh}}) and fall back to narrow loads; .contiguous() costs one copy and can make every later kernel faster.
    •
