4. Registers, spills, and arrays that fall into local memory

The problem. Registers are the only storage the arithmetic units read directly, and they are rationed: 65,536 32-bit registers per SM on every current NVIDIA GPU, shared by all resident threads, at most 255 per thread. A thread that keeps more values alive than it has registers must park some in memory. Fast kernels (register-tiled matmul, FlashAttention) deliberately keep large pieces of the output in registers, so they live right at this edge.

The kernel keeps 128 running sums per thread (the shape of a register-tiled matmul's accumulator). Compiled with no cap, ptxas uses  registers and spills nothing. Then the same file under -maxrregcount from 32 to 255:








Two lessons. Below what the kernel needs, every register removed becomes spill traffic: at a cap of 32 each thread writes and rereads over a kilobyte per pass through the loop body's live values. Above it, ptxas does not stop at what it needs: on sm_90a it used every register it was allowed (192, 224, 255), presumably to schedule loads earlier, and each extra register lowers how many warps fit. The documented version of this behaviour is for launch bounds: "If both minBlocksPerMultiprocessor and maxThreadsPerBlock are specified, the compiler may increase register usage up to L in order to reduce the number of instructions and better hide the latency" ({{C++ language extensions, launch bounds|https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html}}); the same happening under -maxrregcount is observed here, not documented. Prefer __launch_bounds__(maxThreadsPerBlock, minBlocksPerSM) per kernel over a per-file -maxrregcount (both named in the {{Best Practices Guide, register pressure|https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html}}), and measure: a few spilled bytes that hit L1 can cost less than the occupancy they buy back.


Local memory without any register pressure


The surprise for most people: an array can land in local memory while the kernel uses only a few registers. The guide lists what the compiler puts there: "Arrays for which it cannot determine that they are indexed with constant quantities, Large structures or arrays that would consume too much register space, Any variable if the kernel uses more registers than available" ({{Programming Guide 2.3.3.4, local memory|https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html}}). Registers have no addresses, so h[b] with b known only at run time needs memory. Two versions of a per-thread 16-bin histogram, compiled here for sm_90a:




Run-time index: h[bins[k * 4096 + t] & 15] += 1.f;



Constant indices only: for (j = 0; j < 16; ++j) h[j] += (b == j) ? 1.f : 0.f;





The first uses ; the four STL.128 zero the 64-byte array in local memory and every update is an LDL and an STL. The second does 16 compare-and-adds per update but keeps all 16 bins in registers (). Local memory is laid out so that "consecutive 32-bit words are accessed by consecutive thread IDs. Accesses are therefore fully coalesced as long as all threads in a warp access the same relative address" (same section); here every lane picks its own bin, so the accesses scatter too.




measured on Apple M1 Pro GPU: the same two kernels in Metal, 262,144 threads × 1,024 updates each: 7.08 ms with the run-time index against 4.49 ms with constant indices, 1.58 times slower despite doing a sixteenth of the arithmetic. Apple's compiler faces the same problem (registers are not addressable) and makes the same choice.


Predict: ptxas reports "64 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads, Used 22 registers". What is in the 64 bytes?




Zero spill bytes, yet a stack frame: an array the compiler could not promote to registers, here 16 floats = 64 bytes. Fix it by making every index a compile-time constant (unrolled loops, selects), or move the array to shared memory if lanes need different entries.


What you cannot control: register bank conflicts inside the SM. "The compiler and hardware thread scheduler will schedule instructions as optimally as possible to avoid register memory bank conflicts. An application has no direct control over these bank conflicts. In particular, there is no register-related reason to pack data into vector data types such as float4" ({{Best Practices Guide 10.2.7|https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html}}).







5. Constant memory and kernel parameters


What it is. "There is a total of 64 KB constant memory on a device. The constant memory space is cached ... Accesses to different addresses by threads within a warp are serialized, thus the cost scales linearly with the number of unique addresses read by all threads within a warp ... If all threads of a warp access the same location, then constant memory can be as fast as a register access" ({{Best Practices Guide 10.2.6|https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html}}). So it suits values every lane reads at once: a scale, a bias, filter taps, a small lookup indexed by loop counter, not by lane. You use it more than you think, because every kernel argument lives there.

How to read it (bank numbers inferred from consistent use across these kernels, since SASS is undocumented): bank c[0x0] holds the launch's parameters and built-ins (c[0x0][0x0] is the block size, read for blockDim.x); bank c[0x3] holds the module's __constant__ data. With an index known at compile time, the value goes into a uniform register (ULDC, one copy for the whole warp) and straight into the FFMA. With an index known only at run time, it takes an LDC, which is where the per-address serialisation applies if lanes disagree. On sm_80 the compiler even used a parameter directly as an FFMA operand ().


Texture memory is the other read-only cached path: "optimized for 2D spatial locality" with hardware filtering and boundary handling ({{Best Practices Guide 10.2.5|https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html}}). It matters for image resampling; ML kernels almost never use it, and const __restrict__ loads already use the same cache.


A constant-address-space experiment on the M1 was tried and dropped: MLX passes buffers to custom kernels in Metal's device address space, and a program-scope constant table is a different mechanism, so the comparison did not isolate the NVIDIA behaviour described here.
