A kernel is fast when the bytes it needs are already close to the arithmetic. This page is the programmer's view of where bytes live on an NVIDIA GPU and how your code decides it: which instruction a line of CUDA becomes, how many bytes the hardware really moves for it, and which mistakes make it move more. Everything marked compiled here is real output of NVIDIA's CUDA 13.4.2 compiler (no GPU is needed to compile); everything marked measured on Apple M1 Pro GPU was run on this laptop, whose GPU is also a SIMT machine with 32-wide SIMD-groups and a programmer-managed on-chip memory, so the shapes transfer even where the numbers do not.

Three questions for every array in a kernel
Where does it live (which row of the table)? How many times is each byte read (once: stream it; many times: stage it on chip)? In what order do neighbouring threads touch it (neighbours on neighbouring addresses, or not)? Every section below is one of these questions answered for one space.

1. Global loads: what one warp's load really fetches

The problem. A thread asks for 4 bytes, but DRAM and the caches do not deal in 4 bytes. NVIDIA's rule: "Global memory is accessed via 32-byte memory transactions", and the warp "coalesces the memory requests from all the threads in that warp into the number of memory transactions necessary" ({{Programming Guide 2.3.4.1|https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html}}). A 32-byte piece is a sector; four sectors make a 128-byte cache line. So the cost of a load is not how many bytes the threads want but how many distinct sectors their 32 addresses fall in. 32 lanes reading 32 consecutive floats: 128 bytes, four sectors, nothing wasted. 32 lanes each 32 bytes or more apart: 32 sectors, 1,024 bytes moved for 128 used.

The parent's {{GPU simulator|n:3c65c17b0d0d81c39f34d5e070d783c1}} sweeps the stride. Three other ways to waste sectors come up in real ML code and are animated here on one warp: a struct field (array of structs), a misaligned start, and narrow loads.

One warp, drawn to scale: each small box is 4 bytes, each outlined group of eight is one 32-byte sector, each row is 128 bytes. A sector turns shaded when the warp fetches it; blue words are wanted by some lane, orange ones by the lanes of the current step, grey ones fetched but unused. derived from the 32-byte rule above; the same counts come out of the {{Access lab|#t-acc}}, which lets you type any pattern.

Predict: particles stored as a struct of eight floats (32 bytes each). A kernel reads only p[i].x. How many sectors does one warp fetch, and what fraction of the fetched bytes is used?
32 sectors, 1,024 bytes fetched for 128 used. Each lane's 4 bytes sit in its own 32-byte struct, so every lane needs its own sector. Store each field as its own array (struct of arrays) and the same warp needs 4 sectors.

What the M1 says

measured on Apple M1 Pro GPU: 16M particles of 32 bytes (512 MB), median of 3 runs of 7 trials, load average 9.2 to 9.8 while other agents worked; each bar gives the median and, in brackets, the fastest and slowest run. Reading one field from the structs took 3.66 ms, the same as reading all eight fields (3.66 ms): the GPU fetched every byte of every struct either way. The same field kept in its own array took 1.03 ms, 3.6 times faster. The ratio of bytes moved (512 MB read + 64 MB written against 64 + 64 MB) is 4.5; the gap is the smaller transfer's fixed costs. derived: 3.66 / 1.03 and 576 / 128.

Misalignment and vector width

Misaligned. If a warp's 128 contiguous bytes start in the middle of a sector, they span five sectors instead of four. NVIDIA's Best Practices Guide measured exactly this on a V100: "we would expect approximately 4/5th of the memory throughput", but got about 9/10 "because adjacent warps reuse the cache lines their neighbors fetched" ({{Best Practices Guide 10.2.1.3|https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html}}) vendor measurement. The parent's simulator found no measurable penalty for an offset of one float on the M1. Allocation keeps you aligned by default: "Memory allocated through the CUDA Runtime API, such as via cudaMalloc(), is guaranteed to be aligned to at least 256 bytes" (same guide). The misalignment comes from you: a tensor view with a storage offset (x[:, 1:]), a block size that is not a multiple of 32, a packed header in front of the data.

Width. A thread can load 4, 8 or 16 bytes in one instruction. compiled here for sm_90a, the same copy written with float, float2 and float4 becomes:



Same bytes, a quarter of the load instructions, and each instruction keeps four times as many bytes in flight. NVIDIA's advice: vectorised loads "reduce the total number of instructions, reduces latency, and improves bandwidth utilization", but "These instructions require aligned data" and "using vectorized loads increases register pressure and reduces overall parallelism" ({{CUDA Pro Tip: vectorized memory access|https://developer.nvidia.com/blog/cuda-pro-tip-increase-performance-with-vectorized-memory-access/}}, updated Aug 4, 2025). Note the .CONSTANT: the pointers were const __restrict__, section 2 explains it.




measured on Apple M1 Pro GPU: a 256 MB copy ran at about the same speed with 4-, 8- and 16-byte accesses (the bars above; spread across runs 145 to 169 GB/s). With 64 million threads in flight there is enough memory parallelism either way, so on a plain copy the M1 is limited by DRAM, not by instructions. Width pays off when a kernel has few threads per byte or many other instructions competing for issue slots: the case in matmul and attention kernels, which is why they load 16 bytes at a time (and why section 6's asynchronous copy is 16 bytes wide).


When it matters for training, and how to check


  • Layouts. A fused QKV projection stored as [tokens, 3, heads, dim] and read one head at a time; channels-last against channels-first; a transposed weight read along the wrong axis. If the innermost index your threads walk is not the innermost dimension in memory, you pay the stride.
    • 

  • Views. Slicing makes a tensor non-contiguous or misaligned; PyTorch's elementwise kernels check alignment before using vector loads (can_vectorize_up_to in {{ATen's MemoryAccess.cuh|https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/cuda/MemoryAccess.cuh}}) and fall back to narrow loads; .contiguous() costs one copy and can make every later kernel faster.
    • 

  • Check: in Nsight Compute's Memory Workload Analysis, sectors per request for global loads (ideal: 4 for a full warp of 32-bit loads, 16 for 128-bit loads, by the rule above) and the "uncoalesced global accesses" advice; details on {{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}}.
