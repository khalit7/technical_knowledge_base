3. Tiling: fetch once, reuse from shared memory

Shared memory is on-chip SRAM inside the SM, visible to all threads of one block and managed by your code. The pattern is always the same: threads cooperatively copy a tile from global memory into a __shared__ array (each thread one or a few elements, coalesced), wait at __syncthreads(), then all read the tile many times at on-chip speed. On a matmul tile of C = A × B: without shared memory every thread fetches its own row of A and column of B, so each element is fetched once per thread that needs it; with shared memory the block fetches each element once per tile.

One block of 4 × 4 threads computes a 4 × 4 tile of C with K = 8, in two phases of 4. The number in each cell of A and B is how many times it has been fetched from global memory so far. illustrative sizes; moved here from the parent page, whose section 4 now links to this page.

The saving is a factor of the tile width T: global loads per block fall from 2T²K to 2TK derived. measured on Apple M1 Pro GPU (the parent topic's simulator runs): a 2,048 float32 matmul ran at 353 GFLOP/s without tiles and 677 with 8 × 8 threadgroup tiles, but only 478 with 32 × 32: a bigger tile needs more threads and memory per block, fewer blocks fit at once, and latency hiding suffers. Tile sizes are tuned per GPU; the full matmul ladder (register tiles, vector loads, matrix instructions) is on {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}.

Declaring it and sizing it

A static __shared__ array shows up in the compiler's report; extern __shared__ is sized by the third launch parameter and is invisible at compile time, so the occupancy calculator must be told the launch size.

Three declarations as ptxas sees them (compiled here, sm_90a)
KernelDeclarationptxas -v (sm_90a)
padded transpose tile__shared__ float t[32][33];
swizzled transpose tile__shared__ float t[32][32]; indexed t[y][x ^ y]
dynamicextern __shared__ float4 s[]; sized by the third launch parameter <<<grid, block, bytes>>>

compiled here: static arrays show up in the compiler's report (32 × 33 × 4 = 4,224 bytes; the swizzle saves the padding column); dynamic shared memory is invisible at compile time, so the occupancy calculator must be told the launch size.

Per SM: 164 KB on A100 (compute capability 8.0), 228 KB on H100 and B200 (9.0, 10.0), 100 KB on RTX 3090, 4090 and 5090 (8.6, 8.9, 12.0); one block may use 1 KB less, which CUDA reserves per block ({{compute capabilities|https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html}}). But "Kernels relying on shared memory allocations over 48 KB per block are architecture-specific. As such they must use dynamic shared memory rather than statically-sized arrays and require an explicit opt-in" ({{Programming Guide 3.2, L1/shared balance|https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html}}):

cudaFuncSetAttribute(kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, 200 * 1024);
cudaFuncSetAttribute(kernel, cudaFuncAttributePreferredSharedMemoryCarveout, cudaSharedmemCarveoutMaxShared);
kernel<<<grid, block, 200 * 1024>>>(...);

The carveout splits the SM's SRAM between L1 and shared memory: whatever shared memory takes, L1 loses. In Triton you never write these calls; a block size and num_stages that need too much raise OutOfResources for shared memory at compile time ({{triton/runtime/errors.py|https://github.com/triton-lang/triton/blob/main/python/triton/runtime/errors.py}}). And what a block takes is reserved for the whole kernel, so it sets how many blocks share an SM: {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}, section 5, measured a 16 KB staging tile that tripled a fused matmul's threadgroup memory (8 KB to 24 KB) and made the fused kernel slower than not fusing measured on Apple M1 Pro GPU.

Only some carveouts exist (the compute capability 12.0 example)

"for devices of compute capability 12.0, which have a maximum shared memory capacity of 100KB, setting the carveout to 50% will result in 64KB of shared memory, not 50KB, because devices of compute capability 12.0 support shared memory sizes of 0, 8, 16, 32, 64, and 100" ({{Programming Guide 3.2|https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html}}).

4. Banks: when a tile read takes turns

Shared memory is divided into 32 banks: "successive 32-bit words map to successive banks", and "Each bank has a bandwidth of 32 bits per clock cycle" ({{Programming Guide 2.3.4.2|https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html}}). Lanes reading different words of the same bank take turns (a bank conflict); lanes reading the same word get it broadcast. The classic case is a transpose: reading a column of float tile[32][32] puts all 32 lanes in one bank, 32 passes. Predict what one padding column, [32][33], does, then switch the layout.

For 8- and 16-byte elements the pass count is the floor that the 32-bit rule implies; the lab does not model how the hardware splits 8-byte accesses, only the bank load. derived, checked against the Python reference.

measured on Apple M1 Pro GPU (the parent topic's simulator runs): threadgroup-memory reads with a lane stride of 32 ran at 113 billion reads per second against 318 at stride 1 and 394 at stride 33, the same signature (Apple does not document its banks).

Any stride, in one rule (4-byte words)

Word w lives in bank w mod 32, so a warp reading with a lane stride of s words has a conflict of degree gcd(s, 32): a stride of 2 puts lanes l and l + 16 in one bank (a 2-way conflict, two passes), a stride of 3 or any odd stride is free, a stride of 32 is the worst (the Programming Guide draws both cases in its Figure 15) derived. A conflict only costs time when shared memory is the bottleneck: in the parent topic's 32 × 32 transpose on the M1 Pro, DRAM was the limit and padding changed nothing measurable measured on Apple M1 Pro GPU.

Wide accesses. Real kernels load 8 or 16 bytes per lane, and then the rule gives a floor, not a conflict-free promise: a warp asking for 32 × 16 = 512 bytes needs at least 512 / 128 = 4 passes, since 32 banks deliver 128 bytes per pass. The cost is the passes of the busiest bank. NVIDIA's own example: with 16-byte (int4) elements "each set of eight threads loads a row", and a column-wise store "must be serialized, resulting in eight store transactions, giving an eight-way bank conflict" ({{Programming Guide 4.12, TMA swizzle|https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/async-copies.html}}). The current guide does not spell out how 8-byte accesses are split.

Predict: each lane reads one float4 (16 bytes), lanes 128 bytes apart (lane l reads element 8l). How many passes against the ideal 4?
Lane l's 16 bytes are words 32l to 32l + 3, which are banks 0 to 3 for every lane. Banks 0 to 3 each serve 32 different words: 32 passes, 8 times the ideal. A stride of 9 elements (144 bytes) spreads them out again; set the widget to "element l × s", 16 bytes, s = 8 and 9.

measured on Apple M1 Pro GPU: bytes per second read from threadgroup memory by 131,072 threads, 16 KB per threadgroup, median of 3 runs. With 16-byte elements: 1,893 GB/s at a lane stride of 1 element, 1,049 at 4, 565 at 8, and 1,905 at 9, the signature of 4-byte banks the rule predicts (inference: Apple documents neither bank count nor width). Wide reads also moved more bytes per second than 4-byte reads (1,108 GB/s at stride 1, noisy under load): on chip as off chip, fewer and wider accesses win.

Swizzles: the libraries' answer. Padding breaks the alignment that 16-byte and TMA copies need and wastes memory, so libraries permute instead: element (r, c) is stored at column c XOR f(r), which keeps every row and every column on distinct banks (the XOR layout above). Hopper's TMA engine writes tiles already swizzled: "the TMA engine can be instructed to 'swizzle' the data before storing it in shared memory", and with CU_TENSOR_MAP_SWIZZLE_128B "each matrix element is from a different bank for both the rows and columns" (same page). CUTLASS's layout algebra that generalises this is on {{Libraries and tensor cores|n:3c65c17b0d0d81a7adcaebee2f44a087}}.

Beyond one block: distributed shared memory (Hopper clusters)

On Hopper and later, blocks of a cluster can read each other's shared memory (distributed shared memory, about 180 cycles in Luo et al.'s H800 measurements against 29 for local shared memory independent); the hardware side is on {{GPU architecture|n:3c65c17b0d0d810682aae39bd614ec64}}, section 8, the launch side on {{The CUDA programming model|n:3c65c17b0d0d8162865eec15d9dae87e}}.
