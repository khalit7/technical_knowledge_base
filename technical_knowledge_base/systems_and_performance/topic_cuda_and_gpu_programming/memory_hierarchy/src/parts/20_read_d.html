6. Asynchronous copies: loading the next tile while computing this one

The problem. A tiled kernel loops: load a tile of A and B into shared memory, wait, compute on it, wait, load the next. Written plainly, every load goes global memory to a register, then register to shared memory, and the SM sits idle for a full memory latency (about 479 cycles on an H800, from the parent's table) at the start of every tile. Two costs: idle time, and registers held just to carry data in transit.

How it works. Since Ampere (compute capability 8.0) one instruction copies global to shared memory directly, without a register in between, and the thread does not wait for it: "This not only reduces register usage by copying the data directly to shared memory, but also ensures all loads from global memory are in-flight" ({{Programming Guide 4.12.1, LDGSTS|https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/async-copies.html}}). With two or more shared-memory buffers (stages), the copy for tile t + 1 runs while the math on tile t proceeds. compiled here for sm_90a, the same tile loop written both ways:

Synchronous: s[tid] = a[t * 256 + tid]; 


Two stages: __pipeline_memcpy_async, __pipeline_commit, __pipeline_wait_prior(1)





On the left, the compiler already unrolled the loop and issued four 16-byte loads ahead, each parked in four registers until its STS.128: it hides latency by spending registers. On the right, LDGSTS writes shared memory directly; LDGDEPBAR closes a group of copies (the commit) and DEPBAR.LE SB0, 0x1 waits until at most one group is still in flight (the wait_prior(1)). The .BYPASS matches the guide: "copying 16-bytes enables the L1 BYPASS mode, in which case the L1 is not polluted" (same section). The copies are per thread, so a __syncthreads() is still needed before other threads read the tile.














One block's loop over 8 tiles. Top row: copies in flight (each lasts one memory latency); bottom row: the SM computing. A copy can start only when its buffer is free (the tile that last used it has been computed); a tile can be computed only when its copy has landed. illustrative: 479 cycles per copy (H800 global latency, Luo et al.) and 200 cycles of math per tile, chosen to show the effect; it ignores bandwidth limits and the other blocks on the SM, which also hide latency. The schedule is checked against a Python reference (src/code/reference.py).




The cost. Each stage is another tile of shared memory, so stages trade against block size and occupancy (section 3's limits): this is exactly Triton's num_stages, and Triton 3.8.0 compiles a plain matmul's tile loads to LDGSTS on sm_80 (the parent's {{Compiler explorer|n:3c65c17b0d0d81c39f34d5e070d783c1}}). Hopper's TMA goes one step further: one thread issues a copy of a whole multi-dimensional tile (up to 5 dimensions), completion is signalled on a shared-memory barrier, and the tile can land swizzled (section 3). The TMA programming model and the warp-specialised producer/consumer kernels built on it are on {{Libraries and tensor cores|n:3c65c17b0d0d81a7adcaebee2f44a087}}; a full pipelined matmul on {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}; the copy engines inside the SM on {{GPU architecture|n:3c65c17b0d0d810682aae39bd614ec64}}, section 8.







7. Host memory: pinned, mapped and managed


The problem. Training data and checkpoints start in host RAM; a GPU's copy engines move them over PCIe or NVLink-C2C by DMA, and DMA needs physical pages that will not move. Ordinary malloc memory can be swapped or relocated by the OS, so it cannot be the DMA target. How CUDA bridges that decides whether your input pipeline overlaps with compute.




Pageable (default)"When CUDA sends pageable data from CPU to GPU, it must first create a page-locked copy of that data before making the transfer" ({{PyTorch, non_blocking and pin_memory|https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html}}, Apr 1, 2026): an extra CPU memcpy, and the call cannot run in the background.


Pinned (page-locked)cudaMallocHost / cudaHostAlloc, or cudaHostRegister on existing memory. "Page-locked host memory is required for asynchronous copies between the CPU and GPU" and "also improves performance of synchronous copies" ({{Programming Guide 2.6.3|https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/understanding-memory.html}}).


Mapped (zero copy)pinned memory the GPU reads directly over the interconnect, uncached on the GPU. "On integrated GPUs ... mapped pinned memory is always a performance gain ... On discrete GPUs, mapped pinned memory is advantageous only in certain cases" ({{Best Practices Guide 10.1.3|https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html}}).


Managed (unified)cudaMallocManaged: one pointer for both sides; pages migrate on first touch. Prefetch with cudaMemPrefetchAsync and give hints with cudaMemAdvise, or it is slow; the driver's fault path is on {{Virtualization and the GPU driver stack|n:3f05c17b0d0d8158b029e9b2ba2e161b}}, section 11.




How fast. The Best Practices Guide's own example is dated: "On PCIe x16 Gen3 cards, for example, pinned memory can attain roughly 12 GB/s transfer rates" vendor figure; today's links are faster (PCIe Gen5 x16 and NVLink-C2C on {{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}}), but the rule is the same. And pinning has a price: "Pinned memory should not be overused ... the pinning of system memory is a heavyweight operation" (same guide); pinned pages count against the locked-memory limit ({{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}}, section 9). not run here: this laptop has no discrete GPU.


In PyTorch


    

  • DataLoader(..., pin_memory=True) pins each batch in a background thread; then batch.to("cuda", non_blocking=True) returns at once and the copy overlaps with the previous step's compute (stream ordering keeps it safe for kernels that use the batch; overlap itself is on {{Streams, CUDA graphs and multi-GPU programming|n:3f05c17b0d0d81b19a6acab65c370b75}}).
    • 

  • Pinning by hand on the critical path does not help: "Using tensor.pin_memory().to(device, non_blocking=True) can be up to twice as slow as a straightforward tensor.to(device)" (PyTorch tutorial above), because the pin is itself a copy.
    • 

  • The other direction is a correctness trap: after cuda_tensor.to("cpu", non_blocking=True) "there is no guarantee that the data read on GPU is valid without explicit synchronization" (same tutorial; it means the CPU-side data); synchronise (or wait on an event) before reading it.
    • 



Device allocation is not free either. "Device memory allocation and de-allocation via cudaMalloc() and cudaFree() are expensive operations. It is recommended to use cudaMallocAsync() and cudaFreeAsync() which are stream ordered pool allocators" ({{Best Practices Guide 10.3|https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html}}). PyTorch goes further with its own caching allocator, which is why nvidia-smi shows memory "used" after tensors are freed; it is simulated from its source on {{Memory allocators|n:3f05c17b0d0d81209ae9d856695dc958}}, section 9.


The Apple contrast. On this laptop there is no host-device copy to make: "Apple silicon has a unified memory architecture. The CPU and GPU have direct access to the same memory pool" ({{MLX, unified memory|https://ml-explore.github.io/mlx/build/html/usage/unified_memory.html}}). That is the integrated case of the zero-copy rule above, and why every M1 number on this page measures the GPU's own memory system with no PCIe in the way.
