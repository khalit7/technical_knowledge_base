A GPU is fast only while it has work. Between the kernels this topic teaches you to write, a training step leaves the GPU idle in three ways: it waits for the CPU to launch the next kernel, it waits for a copy over PCIe, and it waits for other GPUs to exchange gradients. This page is about the tools that remove those waits: streams (run things side by side), CUDA graphs (launch many kernels with one call) and NCCL on its own stream (communicate while computing).

Where this sits. The CUDA programming model taught what one launch is and what it costs, and left streams, events, pinned-memory pipelines and NCCL streams to this page; GPU memory hierarchy has pinned, mapped and managed memory. Below the API, Virtualization and the GPU driver stack follows a launch down to the doorbell write, and the wires (PCIe, NVLink, InfiniBand) and NCCL's algorithms are on Interconnects and scaling. This page is the programmer's side.

The one picture to keep
A step's time is the sum of the parts that do not overlap. Overlap hides the smaller of two things under the larger; it never makes the larger one shorter, and the two often slow each other down a little (both use the GPU's SMs and memory). Section 6's measurement shows both effects on real DDP.

1. Streams and events, from zero

The problem. A launch only queues work (programming model, section 8). Something must say what order the queued work runs in, and which pieces are independent enough to run at the same time. That something is the stream.

A stream is a queue of GPU operations: kernel launches, copies, memsets, waits. NVIDIA's guide: "the order of execution of operations in a stream is the same as the order in which those operations were enqueued", and operations in different streams have no order between them unless you add one (Programming Guide 2.5) vendor doc. Every launch names its stream as the fourth launch argument, k<<<grid, block, smem, stream>>>; every async copy takes one as its last argument. "Different streams may overlap" means the hardware is allowed to run them together, not that it will: a kernel that fills every SM leaves no room for another.

An event is a marker you record into a stream. It completes when everything queued before it in that stream has completed. Three uses:

  • Order two streams: cudaEventRecord(e, s1); cudaStreamWaitEvent(s2, e) makes everything queued on s2 afterwards wait for s1's work up to e, without stopping the CPU.
  • Time the GPU: two events and cudaEventElapsedTime give milliseconds between them as the GPU saw them (honest timing is on Profiling, benchmarking and correctness). An event created with cudaEventDisableTiming is cheaper and is the right kind for pure ordering.
  • Wait on the CPU for one point only: cudaEventSynchronize(e), instead of draining everything.

Host waits, from narrowest to widest: cudaEventSynchronize (one point), cudaStreamSynchronize (one stream), cudaDeviceSynchronize (everything on the GPU); cudaStreamQuery and cudaEventQuery only ask. Some calls wait without saying so: cudaMemcpy is synchronous, cudaFree synchronises the device (programming model, section 7), and in PyTorch .item(), .cpu(), print(t) and a boolean test of a GPU tensor all wait. A callback can be queued too: cudaLaunchHostFunc(stream, fn, data) runs fn on a CPU thread when the stream reaches it, and such functions "may not call any CUDA APIs" (guide 2.5.4).

The default stream trap

A launch without a stream argument goes to stream 0, the default stream, and there are two kinds. The legacy default stream (nvcc's default) is shared by every host thread and is a blocking stream: work launched into it "will wait for all other blocking streams to complete before it can execute", and the other blocking streams wait for it (guide 2.5.6.1). Streams made with cudaStreamCreate are blocking; cudaStreamCreateWithFlags(&s, cudaStreamNonBlocking) makes one that ignores stream 0. The per-thread default stream (nvcc --default-stream per-thread, or CUDA_API_PER_THREAD_DEFAULT_STREAM before including the headers) gives "each host thread its own independent default stream which will not synchronize with other streams" (guide 2.5.6.2) vendor doc.

// s5_default_stream.cu (compiled here): A on s1, B on stream 0, C on s2, then a copy on stream 0
cudaStreamCreate(&s1); cudaStreamCreate(&s2);   // blocking streams (the default flag)
k<<<1, 256, 0, s1>>>(d);          // A
k<<<1, 256>>>(d + 256);           // B: default stream
k<<<1, 256, 0, s2>>>(d + 512);    // C
cudaMemcpyAsync(d, d + 512, 1024, cudaMemcpyDeviceToDevice);   // default stream again

PyTorch's version. PyTorch never uses the legacy stream for its own work by accident: every operation goes to the current stream of its device, which starts as the default stream and is changed with a context manager:

s = torch.cuda.Stream()
s.wait_stream(torch.cuda.current_stream())   # s must see x fully written
with torch.cuda.stream(s):
    y = f(x)                                   # queued on s
torch.cuda.current_stream().wait_stream(s)   # before anyone on the main stream reads y
y.record_stream(torch.cuda.current_stream())  # or the allocator may hand y's memory out early

The last line is the subtle one. PyTorch's caching allocator records which stream a block was allocated on and reuses freed blocks in that stream's order; a tensor used on a second stream can be freed and reused while the second stream still reads it. The PyTorch notes say it plainly: even when "no other uses of A" exist, "it is still necessary to synchronize" (CUDA semantics, 2.14) vendor doc. torch.cuda.Event(enable_timing=True) wraps the CUDA event.

What "may overlap" depends on

SMs. Two kernels run side by side only if the first leaves SMs (or room on them) free. Concurrency pays when kernels are small, a few blocks each; a big GEMM takes the whole GPU and the second kernel simply starts on SMs as they free up. Work queues. The GPU takes work from a limited number of hardware queues. CUDA_DEVICE_MAX_CONNECTIONS sets how many: "1 to 32 connections, default is 8"; with more streams than queues, independent streams can share a queue and serialise through "false dependencies" (Programming Guide 3.1 and 5.2) vendor doc. Megatron-LM uses the opposite effect on purpose: it sets the variable to 1 so that launch order becomes execution order, and comments in its tensor-parallel layers say "we rely on CUDA_DEVICE_MAX_CONNECTIONS=1 to ensure that the all-reduce is scheduled before the weight gradient computation" (Megatron-LM layers.py, main, Sep 30 2026) source. One queue means the communication kernel is guaranteed to start first and then runs under the GEMM.

Priorities. cudaStreamCreateWithPriority gives a stream a priority; "lower numbers correspond to higher priorities", and cudaDeviceGetStreamPriorityRange returns the range for the device (guide 2.5.9.1) vendor doc. Waiting blocks of a high-priority stream get SMs first, which is how communication kernels are kept from queueing behind a long compute kernel; PyTorch exposes it as torch.cuda.Stream(priority=-1) and, for NCCL, TORCH_NCCL_HIGH_PRIORITY (PyTorch NCCL environment variables).

The measurement above is a contrast, not a CUDA number: Metal has command queues instead of streams, and on this M1 Pro, eight independent one-threadgroup kernels on eight separate queues took as long as eight in one queue, while the same eight in one encoder marked "concurrent" ran together. Separate queues allowed overlap but did not produce it here. The lesson transfers: never assume overlap, look for it on a timeline.

2. Copies: pinned memory and copy/compute overlap

The problem. Host memory is far away. A PCIe 5.0 x16 link moves about 63 GB/s each way (the figure Interconnects and scaling uses), while an H100 SXM reads its own HBM at 3.35 TB/s vendor spec, about 53 times faster derived: 3,350 / 63. A kernel that waits for its input to cross PCIe runs at PCIe speed. The fix is to move data while the GPU computes on something else.

Pinned memory first. The GPU's copy engines move data by DMA: they read physical pages directly, so those pages must not move or be swapped out while the copy runs. Ordinary (pageable) memory can be, so the driver first copies it into a pinned staging buffer, and the copy is not truly asynchronous. NVIDIA: "In order for memory copies involving CPU memory to be carried out asynchronously, the host buffers must be pinned and page-locked" (guide 2.5.2.3) vendor doc. Allocate pinned memory with cudaMallocHost (PyTorch: pin_memory=True in the DataLoader, or t.pin_memory()); do not pin everything, because pinned pages are taken away from the OS.

Copy engines. Copies are done by separate hardware units, not by the SMs, so a copy and a kernel can run at the same time; with two copy engines a host-to-device and a device-to-host copy can also overlap each other. cudaGetDeviceProperties reports how many as asyncEngineCount. With one engine, the two directions take turns.

The chunked pipeline

Cut the data into chunks and give each chunk its own sequence (copy in, kernel, copy out) on one of a few streams. While chunk 2 is copied in, chunk 1's kernel runs and chunk 0 is copied out. The program, compiled here compiled here:

// s1_pipeline.cu: 256 MiB in 8 chunks on 3 non-blocking streams (error checks shortened)
cudaMallocHost(&h_in, N * sizeof(float));                 // pinned
for (int k = 0; k < NS; ++k)
  cudaStreamCreateWithPriority(&s[k], cudaStreamNonBlocking, k == 0 ? hi : lo);
for (int c = 0; c < CHUNKS; ++c) {
  cudaStream_t st = s[c % NS];  size_t off = (size_t)c * C;
  cudaMemcpyAsync(d_in + off, h_in + off, C * 4, cudaMemcpyHostToDevice, st);
  scale<<<(C + 255) / 256, 256, 0, st>>>(d_out + off, d_in + off, C, 2.0f);
  cudaMemcpyAsync(h_out + off, d_out + off, C * 4, cudaMemcpyDeviceToHost, st);
}
// s[0] waits on an event from each other stream, records t1, then: cudaEventSynchronize(t1)

Model derived: 256 MiB at 63 GB/s each way = 4.26 ms per direction; the kernel reads and writes 256 MiB at 3.35 TB/s = 0.16 ms. Serial: 8.68 ms. Eight chunks with two engines: 4.81 ms; with one engine: 8.54 ms. Launch and per-copy latencies are ignored. Not run here: no GPU.

Read the chart before the numbers. The kernel was never the problem; the copies were. Pipelining hides the kernel under the copies (a saving of 0.16 ms) and, with two engines, the copy out under the copy in, which is where the factor of nearly two comes from. Overlap hides the smaller thing under the larger one. If the copies dominate, the real fixes are to copy less (keep data on the GPU, compress it, use lower precision) or to use a faster link.

In PyTorch, and when it matters for training

loader = DataLoader(ds, batch_size=16, pin_memory=True, num_workers=4)
for x, y in loader:
    x = x.to("cuda", non_blocking=True)   # returns at once; ordered before the forward on the stream
    y = y.to("cuda", non_blocking=True)
    loss = model(x, y)

Host-to-device with non_blocking=True is safe because later kernels on the same stream wait for the copy. The other direction is not: "attempting cuda_tensor.to("cpu", non_blocking=True).mean() will result in erroneous outputs", since the CPU reads the buffer before the copy lands; synchronise first. Calling .pin_memory() on a tensor just to copy it once is usually slower than a plain copy: the tutorial measured 0.4364 ms against 0.3704 ms (Moens, "A guide on good usage of non_blocking and pin_memory()", PyTorch tutorials, updated Apr 1 2026) published. Pinning pays when the buffer is reused, which is what the DataLoader's pinned buffers do.

For LLM pretraining the input copy is tiny. 16 sequences of 1,024 tokens as int64 ids, inputs plus targets, are 262,144 bytes, about 0.004 ms over PCIe derived, against tens of milliseconds of compute. Copy/compute overlap matters when the bytes are large next to the work: activations or optimizer state offloaded to the CPU (torch.autograd.graph.save_on_cpu(pin_memory=True), FSDP's CPU offload), inference that streams weights or KV cache from host memory, and image or video pipelines that decode on the CPU. In each case the same rule decides: if copying a layer's bytes takes longer than computing that layer, overlap cannot hide it.

3. Launch overhead and CUDA graphs

The problem. Every launch costs CPU time in the runtime and driver. When kernels are long, the CPU queues them far ahead and the cost is hidden. When kernels are short, as in LLM decoding (one token at a time, every matmul small) or a model built from many small operations, the GPU finishes each kernel before the CPU has queued the next one and sits idle between them. The CUDA programming model measured the M1 version of this; here is NVIDIA's.

NVIDIA's measurement (Alan Gray, "Getting Started with CUDA Graphs", NVIDIA blog, Sep 5 2019, V100) published: 20 kernels per step, 1,000 steps, each kernel 2.9 µs of GPU work. Synchronising after every launch: 9.6 µs per kernel. Launching the 20 back to back on a stream and synchronising once per step: 3.8 µs. The same 20 as one CUDA graph: 3.4 µs. Creating and instantiating the graph took "around 400µs", once.

Those four numbers fit a simple model derived: with a stream the GPU waits for the CPU, so a launch costs the CPU about 3.8 µs; a synchronisation adds about 2.9 µs of wait and wake-up (9.6 − 3.8 − 2.9); inside a graph the GPU still leaves about 0.5 µs between nodes (3.4 − 2.9). To scale. Per-kernel values fitted to NVIDIA's four published V100 figures derived; the shape, not the exact microseconds, carries over to newer GPUs and drivers.

The same experiment on the M1 Pro's GPU measured on Apple M1 Pro GPU. Metal has no streams or graphs, but it has the same three choices: one command buffer per kernel and wait (like launch-and-sync), one command buffer per kernel committed back to back (like a stream), and N dispatches recorded once into an indirect command buffer and replayed with one call (the nearest thing Metal has to a CUDA graph). 200 dependent kernels of 1,024 threads, Python driving Metal through PyObjC, all four giving the same result (101.002):

Median of 3 runs, each the median of 7 trials; load average 10.6 to 11.3 (the laptop was shared). Launch and wait: 179.9 µs per kernel (runs 179.9, 188.7, 174.2). Queued: 21.9. One command buffer: 5.3, of which the GPU's own clock counts 1.92, and encoding cost the CPU 453.5 µs for all 200 (2.27 µs each, mostly Python). Replay: 3.3 µs per kernel with 21.7 µs of CPU for the whole sequence; recording it once took 853 µs. PyTorch on MPS, 200 dependent x * a + b: 226.2 µs per iteration synchronising each time, 12.3 once (PyTorch 2.14.1).

The same three lessons as NVIDIA's numbers, measured: waiting after each launch is the disaster (8.2× slower than queueing here); queueing still pays a CPU cost per kernel; recording once and replaying removes the per-kernel CPU cost and leaves the GPU's own time. What does not transfer: Metal command buffers are not CUDA launches, Python adds its own cost, and the absolute microseconds belong to this machine.

What a CUDA graph is

"A graph is a series of operations such as kernel launches, data movement, etc., connected by dependencies", used in three stages: definition, instantiation (which "takes a snapshot of the graph template, validates it, and performs much of the setup and initialization of work with the aim of minimizing what needs to be done at launch") and execution, launching the executable graph into a stream like any other work, as often as you like (Programming Guide 4.2, CUDA Graphs, v13.4.2) vendor doc. A node can be a kernel, a copy, a memset, a host function, a child graph, an event record or wait, an allocation or free, or a conditional; CUDA 13.4.2's header lists read here.

There are two ways to define one. Stream capture records what you would have launched anyway; the explicit API (cudaGraphAddNode) builds nodes and edges by hand. Capture is what libraries use:

// s2_graph.cu, part 1 (compiled here)
cudaStreamBeginCapture(s, cudaStreamCaptureModeGlobal);
for (int k = 0; k < 20; ++k) axpb<<<n / 256, 256, 0, s>>>(d, n, 1.0001f, 0.5f);   // recorded, not run
cudaStreamEndCapture(s, &g);
cudaGraphInstantiate(&ge, g, 0);                       // once: the expensive step
for (int it = 0; it < 1000; ++it) cudaGraphLaunch(ge, s);   // one call per 20 kernels

What a graph freezes. Everything about each node: which kernel, the grid, and the argument values, including every pointer. A replay reads and writes the same addresses with the same shapes. Changing data means writing new values into the same buffers; changing a scalar argument means updating the graph. Updating is cheaper than re-instantiating: capture again with the same structure and call cudaGraphExecUpdate(ge, g2, &info), or set one node's parameters with cudaGraphExecKernelNodeSetParams. Node parameters "such as kernel parameters and memory addresses" may change; "major changes to graph structure (such as topology or node types) require re-instantiation" (guide 4.2). The header's failure codes say what can go wrong: .

What breaks capture. Anything that needs the GPU to have actually run: "It is invalid to synchronize or query the execution status of a stream which is being captured"; synchronous calls such as cudaMemcpy are invalid; while any stream is capturing, using the legacy default stream from a blocking stream is invalid; and "when an invalid operation is attempted during stream capture, any associated capture graphs are invalidated" (guide 4.2). The capture mode decides how strict this is across threads: (PyTorch's capture_error_mode, default "global"). Other streams join a capture by waiting on an event recorded in a capturing stream, which is how multi-stream work, NCCL included, ends up in one graph.

Control flow on the GPU: conditional nodes

A graph replays a fixed sequence, so a loop whose trip count depends on data (iterate until converged, decode until end-of-sequence) used to mean returning to the CPU. Conditional nodes keep the decision on the GPU: an IF node runs its body once if a condition value is non-zero (with an optional ELSE body), a WHILE node repeats its body while it is non-zero, and a SWITCH node runs body n. IF and WHILE arrived in CUDA 12.4, ELSE and SWITCH in 12.8 (NVIDIA blog, May 10 2024, updated Feb 3 2025) published. A kernel in the graph sets the condition:

// s2_graph.cu, part 3: a WHILE loop that lives on the GPU
__global__ void halve_and_test(float* x, cudaGraphConditionalHandle h) {
  x[0] *= 0.5f;
  cudaGraphSetConditional(h, x[0] > 1.0f ? 1u : 0u);    // 0 ends the loop
}
cudaGraphConditionalHandleCreate(&h, w, 1, cudaGraphCondAssignDefault);
cp.type = cudaGraphNodeTypeConditional; cp.conditional.handle = h;
cp.conditional.type = cudaGraphCondTypeWhile; cp.conditional.size = 1;
cudaGraphAddNode(&cn, w, nullptr, nullptr, 0, &cp);
cudaStreamBeginCaptureToGraph(s, cp.conditional.phGraph_out[0], nullptr, nullptr, 0, cudaStreamCaptureModeGlobal);
halve_and_test<<<1, 1, 0, s>>>(d, h);                    // captured into the loop body
cudaStreamEndCapture(s, nullptr);

What cudaGraphSetConditional compiles to on sm_90a compiled here: the kernel loads a function address from constant bank 4, which the driver fills, and calls it (CALL.ABS.NOINC); the sm_100a build does the same. The condition is set by a driver routine running on the GPU, not by a special instruction.



Other graph features worth knowing. Graphs can allocate and free memory as nodes (cudaGraphInstantiateFlagAutoFreeOnLaunch); a graph instantiated with cudaGraphInstantiateFlagDeviceLaunch can be launched from a kernel ("fire and forget", "tail" or "sibling" launch, guide 4.2); cudaGraphUpload moves the setup out of the first launch (NVIDIA's post saw the first launch "around 33% slower"); and cudaGraphDebugDotPrint writes the graph as a DOT file to look at.


Predict: instantiating costs 400 µs once and saves 0.4 µs per kernel against a stream (NVIDIA's numbers). After how many kernel launches does the graph pay for itself?




400 / (3.8 − 3.4) = 1,000 kernels derived, 50 steps of 20. Training and serving replay the same graph millions of times, so it pays; a graph re-captured every step because shapes keep changing never does. That is the whole design problem of section 4.






4. CUDA graphs in PyTorch, torch.compile and inference engines


By hand: torch.cuda.graph. PyTorch wraps capture in a context manager. The rules follow from what a graph freezes (section 3): inputs and outputs live at fixed addresses, so you copy new data into static tensors; no CPU-GPU synchronisation inside (no .item()); no data-dependent Python control flow; and warm-up must run first, on a side stream, so that lazy initialisation (cuBLAS handles, autotuning, allocator growth) happens outside the capture (CUDA semantics, CUDA Graphs, 2.14) vendor doc.


static_x = torch.randn(B, D, device="cuda")
s = torch.cuda.Stream(); s.wait_stream(torch.cuda.current_stream())
with torch.cuda.stream(s):                       # warm-up on a side stream
    for _ in range(3):
        static_y = model(static_x)
torch.cuda.current_stream().wait_stream(s)
g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):                        # capture: kernels recorded, memory from a private pool
    static_y = model(static_x)
for x in batches:
    static_x.copy_(x)                            # new data, same address
    g.replay()                                   # one call for every kernel in the model
    out = static_y.clone()                       # the next replay overwrites static_y


Memory allocated during capture comes from a pool private to the graph, kept for its whole life; graphs can share a pool (pool=, torch.cuda.graph_pool_handle()). torch.cuda.make_graphed_callables captures a module's forward and backward together, with num_warmup_iters = 3 by default; its docstring adds that DDP "needs 11 iterations for warm up" read here: PyTorch 2.14.1 source. With DDP and NCCL inside a graph, the PyTorch notes require async error handling off (NCCL_ASYNC_ERROR_HANDLING=0, now spelled TORCH_NCCL_ASYNC_ERROR_HANDLING) and at least 11 DDP-enabled warm-up iterations before capturing the backward.


Automatic: torch.compile(mode="reduce-overhead") and CUDAGraph Trees


torch.compile has four modes, "default", "reduce-overhead", "max-autotune" and "max-autotune-no-cudagraphs"; "reduce-overhead" "reduces the overhead of python with CUDA graphs, useful for small batches", at "the cost of more memory usage" (docstring, PyTorch 2.14.1). The graphs are managed by CUDAGraph Trees, whose design note in torch/_inductor/cudagraph_trees.py explains the name: graphs recorded across graph breaks share one memory pool, and "we support arbitrary trees of CUDA graph operations, not just sequences", using only the memory of the largest path read here. When not to bother
A training step for a large model spends tens of milliseconds per kernel sequence on big matmuls; launch overhead is a rounding error there and graphs mainly cost memory and constraints. Graphs earn their keep where kernels are small: decoding, small-batch inference, small models, and the many tiny kernels of optimizers and norms. Check first: if the profiler's GPU row has no gaps, graphs will not help.


Inference engines


Decoding is the textbook case: one token per step, every kernel small, the same sequence of kernels every step. Engines therefore capture one graph per batch size from a list of capture sizes and pad each real batch up to the nearest one. vLLM's design doc lists five modes (NONE, PIECEWISE, FULL, FULL_DECODE_ONLY, FULL_AND_PIECEWISE) and defaults to FULL_AND_PIECEWISE with piecewise compilation: full graphs for uniform decode batches and piecewise graphs otherwise, where piecewise means capturing everything except operations graphs cannot handle, "mainly attention", whose shapes change with every request (vLLM docs, CUDA graphs design, Sep 26 2026) published. The same trade-off as graph_partition: graph what is static, run the dynamic part eagerly between graphs.

5. Several GPUs from one process: devices, peer access, IPC


Selecting a device. The runtime has a "current device" per host thread; cudaSetDevice(d) switches it, and allocations, streams and launches made afterwards belong to device d. A stream belongs to one device; an event can be waited on by a stream of another device, which is how work on two GPUs is ordered. In PyTorch: torch.cuda.set_device(d), with torch.cuda.device(d), or explicit device="cuda:1".


One address space. On 64-bit systems the host and all GPUs share one virtual address space (unified virtual addressing), so a pointer says which device it belongs to and cudaMemcpyAsync(..., cudaMemcpyDefault, s) can copy between any two. Peer access goes further: after cudaDeviceEnablePeerAccess, a kernel on GPU 0 can dereference a pointer into GPU 1's memory, and the loads and stores travel over NVLink or PCIe with no copy.


// s3_peer.cu (compiled here)
cudaDeviceCanAccessPeer(&can01, 0, 1);           // is there a path GPU 0 can use?
cudaSetDevice(1); cudaMalloc(&b, n * 4);
cudaSetDevice(0); cudaMalloc(&a, n * 4);
if (can01) {
  cudaDeviceEnablePeerAccess(1, 0);               // GPU 0 may now dereference GPU 1 pointers
  add_remote<<<n / 256, 256>>>(a, b, n);          // b is read across the link
} else {
  cudaMemcpyPeerAsync(tmp, 0, b, 1, n * 4, 0);    // copy first, then compute locally
  add_remote<<<n / 256, 256>>>(a, tmp, n);
}
cudaIpcGetMemHandle(&hnd, a);                     // let another process map this allocation


Whether peer access exists depends on the wiring: GPUs on one NVLink/NVSwitch fabric, or under one PCIe switch on a platform that allows it. nvidia-smi topo -m prints the matrix (NV#, PIX, PXB, PHB, SYS), and consumer cards from the RTX 4090 on have no NVLink at all. The wires, their speeds and the switch layouts are Interconnects and scaling's subject; the programmer's question is only "can this pointer be read from there, and how fast".


Across processes. PyTorch training uses one process per GPU (torchrun), so peer memory crosses process boundaries: cudaIpcGetMemHandle turns an allocation into a small handle that another process opens with cudaIpcOpenMemHandle (newer code uses the driver's virtual memory API and exports a file descriptor). NCCL and symmetric memory (section 8) do exactly this under the hood to read each other's buffers.


One process, many GPUs, or one process per GPU?
One process per GPU is the PyTorch default and avoids Python's single interpreter becoming the launch bottleneck for eight GPUs. One process driving several GPUs is fine in C++ (and is what ncclCommInitAll and section 6's program do), but NCCL warns that "using multiple GPUs per process with CUDA graph capture may result in deadlocks" (NCCL user guide, CUDA graphs) vendor doc.






6. NCCL as an API, and how training hides communication


The problem. Data-parallel training runs the same model on every GPU with different data, then averages the gradients so every copy takes the same step. That average is an all-reduce, and for a model of N parameters it moves about 2N values per GPU per step. On a fast fabric it is cheap; across nodes it can cost as much as the backward pass. The idea of this section: start each piece of the all-reduce the moment its gradients exist, while backward is still computing the rest. Which collectives each parallelism needs is on Distributed Training; how NCCL schedules bytes over rings and trees, and what the network sustains, is on Interconnects and scaling (its Collective simulator tab animates rings and trees). Here: what the programmer calls and what runs where.


The API in five calls


    

  1. One id for the group. Rank 0 calls ncclGetUniqueId, and the id is "broadcast to all participating threads and processes using any CPU communication system" (in PyTorch, the TCP store set up by init_process_group).
    2. 

  2. A communicator per GPU. ncclCommInitRank(&comm, nranks, id, rank) on each, ranks 0 to n − 1; ncclCommInitAll when one process owns all the GPUs; ncclCommSplit to carve sub-groups (tensor-parallel and data-parallel groups) (NCCL user guide, communicators).
    3. 

  3. Collectives on a stream. ncclAllReduce(sendbuff, recvbuff, count, ncclBfloat16, ncclSum, comm, stream). "The NCCL call returns when the operation has been effectively enqueued to the given stream"; it runs asynchronously, and you wait with stream semantics, events or cudaStreamSynchronize (NCCL user guide, CUDA stream semantics) vendor doc.
    4. 

  4. Groups. Calls between ncclGroupStart() and ncclGroupEnd() are "fused into a single NCCL operation"; one thread driving several GPUs must group, and grouping many small collectives saves launches. ncclGroupEnd "only guarantees that the operations are enqueued on the streams, not that the operation is effectively done" (nccl.h).
    5. 

  5. Tear down with ncclCommDestroy, or ncclCommAbort when a peer is gone (section 7).
    6. 



NCCL 2.31.2's header, as shipped in the CUDA 13.4.2 image, exports  read here. Beyond the classic collectives it now has one-sided calls (ncclPutSignal, ncclSignal, ncclWaitSignal) on registered memory windows, which are section 8's territory.


Two rules that cause most NCCL bugs
Same calls, same order, on every rank. A collective completes only when every rank has joined it; if rank 3 skips an all-reduce (an if on local data, an unused parameter, an exception caught on one rank), everyone else waits forever. With several communicators per GPU, "users must ensure the order of host-side launches matches for all devices"; before NCCL 2.26 that meant serialising all of them, and 2.26 added NCCL_LAUNCH_ORDER_IMPLICIT to follow host issue order (communicators page). NCCL collectives are kernels. They run on SMs, as thread blocks (CTAs), next to your kernels, and they need the other ranks' matching kernels to be running too.


Communication costs SMs. Because a collective is a kernel, it competes with compute. NCCL's communicator config, fields read from nccl.h (), lets you bound it: minCTAs "up to 32. The default value is 1", maxCTAs default 32; CTAPolicy NCCL_CTA_POLICY_EFFICIENCY uses the "minimal number of CTAs to achieve the decent performance", recommended for compute/communication overlap, and NCCL_CTA_POLICY_ZERO uses "zero CTA whenever it can" (NCCL API types, flags, NCCL 2.32.3 docs) vendor doc. DeepSeek-V3's training gave communication 20 of the H800's 132 SMs and called that a cost: it "relies on expensive SMs ... which will limit the computational throughput" (DeepSeek-V3 report) published.


The DDP pattern, by hand


The program below does what PyTorch's DistributedDataParallel does: a compute stream runs backward, which fills gradient buckets from the last layer to the first; an event marks each bucket ready; a second, communication stream waits for that event only and all-reduces the bucket; the optimizer waits for the communication stream at the end compiled here (with -lnccl; the run prints NCCL's version code 23102, then stops at the first CUDA call).


// s4_nccl_overlap.cu (abridged; error checks removed)
ncclCommInitAll(comm.data(), nd, devs.data());
for (int b = B - 1; b >= 0; --b) {                       // backward: last layers first
  for (int d = 0; d < nd; ++d) {
    cudaSetDevice(d);
    fake_backward<<<n / 256, 256, 0, compute[d]>>>(grad[d] + b * n, n, 1.0f + d);
    cudaEventRecord(ready, compute[d]);
    cudaStreamWaitEvent(comms[d], ready, 0);              // wait for this bucket only
  }
  ncclGroupStart();
  for (int d = 0; d < nd; ++d)
    ncclAllReduce(grad[d] + b * n, grad[d] + b * n, n, ncclFloat, ncclAvg, comm[d], comms[d]);
  ncclGroupEnd();                                         // queued; backward keeps going
}
// each compute stream waits on an event from its comm stream, then the optimizer step


What PyTorch adds. DDP registers a hook on every parameter's gradient and launches a bucket's all-reduce when the bucket's last gradient arrives. Buckets follow the reverse order of model.parameters(), are rebuilt after the first iteration in the order gradients actually arrived, and default to 25 MiB, with a smaller first bucket of 1 MiB so the first all-reduce starts early (_DEFAULT_BUCKET_CAP_MB = 25, _DEFAULT_FIRST_BUCKET_BYTES = 1,048,576, PyTorch 2.14.1 source) read here. The NCCL calls run on a stream owned by the process group, ordered after the gradient kernels by events. dist.all_reduce(t, async_op=True) returns a work handle whose wait() makes the current stream wait without blocking the CPU. no_sync() skips the all-reduce during gradient accumulation; comm hooks (register_comm_hook) can compress buckets to BF16.

Attention-score FLOPs and NCCL latency are left out.










To scale. Lanes are streams on one GPU; every GPU runs the same timeline. The Step timeline tab lets you change every input.


What the model says. Without overlap the step is 42.8 ms, of which 10.7 ms is all-reduce with the SMs idle. With overlap it is 36.5 ms, 15% less, and 4.4 ms of communication is still exposed. The reason is the last bucket: GPT-2 ties its token embedding to the output layer, and that 38.6 M-parameter matrix's gradient is complete only when backward reaches the embedding lookup at the very end, so the final bucket (97.7 MiB of 237.4) cannot start until backward is over. The copy lane is honest too: the batch is a hairline, because token ids are tiny (section 2).


Measured: DDP's buckets on real processes


The mechanism can be run without GPUs. Two CPU processes, real DistributedDataParallel with the Gloo backend instead of NCCL, a 12-layer MLP of width 1,024 (6 buckets of 8.01 MiB with bucket_cap_mb=8), two threads per process, PyTorch 2.14.1. A comm hook timestamps each bucket when DDP hands it over and when its all-reduce completes; a hook on the first layer's weight marks the end of backward's compute. "No overlap" is the same model under no_sync() followed by the same buckets all-reduced one by one measured on CPU:




One representative step of each mode (the median step of run 2). Medians over 3 runs of 5 steps: backward plus communication 64.6 ms overlapped against 96.1 ms serial (33% less); per-run 64.6, 61.5, 66.3 and 92.6, 96.1, 105.7 ms; load average 5 to 7.


Two things show. The overlap is real: buckets leave during backward, and only about 7.0 ms of communication remains after the compute ends, against 45.9 ms when nothing overlaps. And overlap is not free: backward's compute itself took 15% longer (57.6 against 50.2 ms) because the all-reduce threads compete for the same cores. On a GPU the competitors are SMs and memory bandwidth instead of CPU cores, the reason for NCCL's CTA limits above. PyTorch's profiler sees the same thing: in a traced step, Gloo all-reduces run on their own threads while AddmmBackward0 runs on the autograd thread:




torch.profiler, CPU activities, rank 0 of a 2-process DDP step after 3 warm-up steps; events named autograd::engine::evaluate_function: AddmmBackward0 and gloo:all_reduce measured on CPU.


What does not transfer: Gloo on loopback is not NCCL on NVLink, CPU threads are not SMs, and the times are milliseconds on a laptop. What does: the bucket order, the hand-over during backward, the exposed tail, and the slowdown from sharing hardware.


FSDP: the same idea in both directions


Fully sharded data parallelism stores each parameter in pieces, so it must all-gather a layer's parameters before using them, forward and backward, and reduce-scatter its gradients afterwards. Overlap again decides the cost. FSDP2's docs: "In forward, all-gathers run on a separate CUDA stream, so the next module's all-gather can overlap with the current module's forward compute"; "in backward, FSDP2 additionally prefetches the next module's all-gather explicitly and runs reduce-scatters on a separate CUDA stream"; set_modules_to_forward_prefetch issues all-gathers earlier when CPU overhead eats the natural lead; reshard_after_forward defaults to true for non-root modules (free after forward, gather again in backward) and false for the root (fully_shard docs, 2.14) vendor doc. Prefetching one layer ahead costs one extra layer of unsharded parameters in memory: overlap is bought with memory.


Tensor parallelism is the hard case. Its all-reduces sit between two matmuls that need the result, so there is nothing independent to hide them under, unless the matmul is cut into pieces that start as their slice of data arrives (Megatron's ordering trick in section 1, async TP in section 8). That is why tensor parallelism stays inside the fastest domain (Interconnects and scaling works the numbers).






7. When it hangs: NCCL errors, timeouts and debugging


Why hangs, not crashes. A collective waits for every rank. If one rank never arrives, because it crashed, took a different branch, ran out of memory or is stuck on I/O, the others do not fail: their NCCL kernels spin on the GPU waiting for data that never comes, and the CPU blocks at the next synchronisation. A 1,000-GPU job then stops with 999 healthy-looking processes. Debugging a hang is mostly finding the rank, and the call, that differs.

8. Beyond collectives: symmetric memory, NVSHMEM and kernels that communicate


The problem. A collective is a separate kernel launched from the CPU, with a fixed shape, between compute kernels. Two things it cannot do well: overlap with the inside of a matmul (tensor parallelism, section 6), and move small, data-dependent messages (sending each token to the GPU that holds its expert in a mixture-of-experts layer). Both want the compute kernel itself to read or write another GPU's memory.


Symmetric memory is the enabling idea: every rank allocates the same buffer, at the same offset in a shared heap, so "this buffer on rank j" can be computed from a local pointer, and a kernel can load or store it over NVLink (peer access, section 5) or put it across the network. Two lineages:


    

  • NVSHMEM: "a parallel programming interface based on OpenSHMEM" that creates "a global address space for data that spans the memory of multiple GPUs", with "a low-overhead, in-kernel communication API for use by GPU threads" (one-sided put, get, atomics and signals) alongside operations on CUDA streams; version 3.8 is current and supports CUDA 13.4 (NVIDIA NVSHMEM page) vendor doc. It is the classic way to write kernels that communicate across nodes.
    • 

  • NCCL's own device API. Recent NCCL registers symmetric memory windows (ncclCommWindowRegister, flag NCCL_WIN_COLL_SYMMETRIC) and ships a device-side header; in NCCL 2.31.2 it is nccl_device.h, with parts named  read here. LSA (load/store accessible) covers peers reachable by plain loads and stores; GIN (GPU-initiated networking) covers peers across the network.
    • 



In PyTorch, torch.distributed._symmetric_memory: symm_mem.empty(size, device=...) allocates, symm_mem.rendezvous(tensor, group) exchanges handles (both "must be called in the same order on all ranks in the group"), with backends for CUDA peer memory within a node, NVSHMEM across nodes, and NCCL symmetric kernels (NCCL 2.27 or newer); each buffer comes with "signal pads" for synchronisation; uses named are async tensor parallelism and MoE token dispatch (all_to_all_vdev_2d) (PyTorch symmetric memory docs, 2.14) vendor doc. Async TP splits a tensor-parallel matmul so that each slice of the all-gather feeds a slice of the matmul as it arrives, which is the way around section 6's "nothing to hide it under".


A current example, checked
DeepSeek's DeepEP, the expert-parallel all-to-all library, was the best-known NVSHMEM user. Its README now says V2 moved to "the lightweight NCCL Gin backend" and V2.5 removed "V1, including its APIs, NVSHMEM backend ... NVSHMEM is no longer a dependency"; it also notes "EP dispatch and combine require GPU SMs" (DeepEP README, Sep 30 2026) source. Older write-ups that describe DeepEP as built on NVSHMEM describe V1.


For the reader who will write kernels: this is where the line between "kernel" and "communication" disappears. The tools are the same as everywhere on this page (streams, events, signals, keeping SMs busy), applied inside one kernel instead of between kernels.






Common mistakes, a checklist, interview questions


Timing GPU work with a CPU clock and no synchronisation
The clock measures how long it took to queue the work. Use CUDA events, or synchronise before reading the clock (section 1; methodology on Profiling, benchmarking and correctness).


A hidden synchronisation in the training loop
loss.item() every step, print(tensor), if (x > 0).any():, a .cpu() for logging, torch.cuda.empty_cache(): each drains the queue so the CPU can no longer run ahead. Log every N steps, or copy to pinned memory with a non-blocking copy and read it a step later.


Expecting two streams to overlap because they are two streams
The legacy default stream serialises blocking streams; big kernels leave no SMs; few hardware queues create false dependencies; the M1 measurement in section 1 overlapped nothing across queues. Check on a timeline.


Using a tensor on a side stream without wait_stream and record_stream
Either a race (reading before the producer finished) or a use-after-free through the caching allocator. Both give wrong numbers, not errors.


non_blocking=True on a device-to-host copy, then reading the result
The CPU reads the buffer before the copy lands. Synchronise (an event) before use.


Capturing a CUDA graph and then feeding it new tensors
A replay reads the addresses captured, not your new tensor. Copy new data into the static input; clone outputs you keep. Shape changes need a new graph.


A rank-dependent branch around a collective
The classic hang (section 7). Every rank must make the same collective calls in the same order with the same sizes.


Expecting overlap to remove communication cost
It hides the communication that is smaller than the compute running beside it, minus the slowdown from sharing SMs. The last bucket is always exposed; tensor-parallel all-reduces are on the critical path.


How to check, in order


    

  1. Profile one step with Nsight Systems or torch.profiler and look at the GPU rows: gaps between kernels (launch-bound or a sync), copies not under kernels (no overlap), NCCL kernels after backward ends (exposed communication).
    2. 

  2. Gaps with tiny kernels: remove syncs, fuse, then CUDA graphs (mode="reduce-overhead"), and confirm the gaps close.
    3. 

  3. Exposed all-reduce: check bucket sizes and order, look for a huge last bucket (tied embeddings), consider gradient accumulation (fewer all-reduces per sample) or a faster group layout.
    4. 

  4. Hangs: the checklist in section 7.
    5. 



Interview questions


What is a CUDA stream, and what does an event add?
A FIFO queue of GPU operations: in order within a stream, unordered across streams. An event is a marker in a stream that other streams can wait on (ordering without blocking the CPU) and that can time GPU work.


Why might two kernels on two streams still run one after the other?
The legacy default stream between them; the first kernel occupies every SM; false dependencies through a limited number of hardware queues (CUDA_DEVICE_MAX_CONNECTIONS); an implicit synchronisation such as cudaMalloc or a pageable copy.


Why does an async copy need pinned memory?
The copy engine reads physical pages by DMA. Pageable pages could move, so the driver stages them through a pinned buffer and the copy cannot overlap freely.


What does a CUDA graph save, and what does it cost?
It replaces per-kernel CPU launch work with one launch of a pre-validated graph, and lets the GPU run nodes with smaller gaps. It costs an instantiation (hundreds of microseconds), fixed addresses and shapes, no host syncs inside, and memory held by the graph's pool.


How does DDP overlap communication with backward?
Gradient hooks fill buckets in reverse parameter order; when a bucket is full its all-reduce is launched on NCCL's stream while autograd keeps computing earlier layers; the optimizer waits for all of them. Default buckets 25 MiB, first bucket 1 MiB.


Why can't tensor-parallel all-reduces be hidden the same way?
The next matmul needs their result, so no independent work exists to overlap them with, unless the matmul is split and pipelined with the communication (async TP, symmetric memory).


A 512-GPU job hangs at step 40,000. What do you do?
Find the rank and call that differ: the flight-recorder dumps on watchdog timeout, py-spy on each rank, the kernel log for a dead GPU or node; check the last collective's sequence number across ranks; restart from the checkpoint without the bad node.


Why do NCCL collectives slow down your compute kernels?
They are kernels too: they take SMs (CTAs) and memory bandwidth while they run. NCCL lets you cap CTAs (maxCTAs, NCCL_CTA_POLICY_EFFICIENCY); DeepSeek-V3 reserved 20 of 132 SMs for communication.

The formulas


    

  • Parameters: GPT-2 layout, vocabulary 50,257, context 1,024; per block 12d² + 13d (layer norms, attention, MLP with 4d); an untied output layer adds 50,257d.
    • 

  • Forward = 2N × tokens / (989.5 TFLOP/s × MFU), H100 SXM dense BF16 (vendor spec); backward = 2 × forward, split across layers in proportion to their matmul parameters; attention-score FLOPs ignored.
    • 

  • Gradient readiness: output layer first, then blocks from last to first; with tied weights the embedding's gradient is complete only at the end of backward.
    • 

  • Buckets: DDP's rule, reverse parameter order, close a bucket once it reaches the cap; BF16 gradients (2 bytes); first bucket 1 MiB (or the cap if smaller).
    • 

  • All-reduce of B bytes on n GPUs = B × 2(n − 1)/n / busbw + latency, one bucket at a time on the NCCL stream. Busbw presets: 92% of 50 GB/s (InfiniBand, the acceptance target quoted on Interconnects and scaling), 365.6 GB/s (8× H200 ring, nccl-tests at 8 GiB, measured by Bekman), 92% of 12.5 GB/s = 11.5 (100 Gb/s Ethernet, same efficiency assumed). The NVLink preset assumes all the GPUs share one NVLink domain (8 on an HGX board).
    • 

  • Optimizer = 32 bytes per parameter at 3.35 TB/s. Batch = tokens × 8 bytes × 2 (ids and targets) at 63 GB/s.
    • 

  • Slowdown: backward stretched by this percentage when overlapped, standing in for NCCL's use of SMs and memory bandwidth; the CPU measurement on the Reading tab found 15% with Gloo threads.
