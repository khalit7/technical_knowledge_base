# Streams, CUDA graphs and multi-GPU programming: sources, scripts, outputs

- `build.sh`: assembles `../index.html` from `parts/` (`01_head.html`, `02_split.html` (the split layout, a skill template), `10_header.html`, Reading `20_read_a.html` to `20_read_j.html`; JS `21` the skill template `RD`, `22` data generated by `recompute.py`, `23` static charts and text from data (and `window.SGPIPE`, the chunked-pipeline schedule with each event's chunk), `24` the training-step model and the static two-mode step chart, `25_js_s3.js` the skill template renderer v2, `25_js_sg_launch.js` the launch model, `26` the step calculator (closed block in section 6), `27` the static figures (hero, event ordering, peer access, a hang, async TP), `40` to `42` the three 3D scenes; `39_tab_more.html` Further reading; every JS part in its own script, `99_js_tabs.js` (template, storage key `cuda-sg-tab`) last).
- `run_all.sh`: reproduces everything. Needs Docker with kb-gpu-lab:1 (Dockerfile in `../../src/compile/image/`), `TORCHPY` (a Python with torch 2.14.1) and `METALPY` (a Python with pyobjc-framework-Metal 12.x), both outside the repo.
- `cuda/kernels/s1..s5`: copy/compute pipeline with pinned memory, streams, priorities and events; CUDA graphs (capture, instantiate, replay, `cudaGraphExecUpdate`, a conditional WHILE node with `cudaGraphSetConditional`); peer access and IPC; the DDP pattern by hand with NCCL on a second stream; legacy against per-thread default stream. `cuda/compile_all.sh` runs inside the container; `cuda/out/`: build and run logs (each run stops with error 35, no driver), ptxas reports and SASS of the graph kernels for sm_90a and sm_100a, PTX, the runtime symbols each default-stream mode calls, header excerpts (graph node types, conditional types, capture modes, update results, NCCL API and config fields), and which `NCCL_*` variables the library contains.
- `torch/ddp_overlap.py` (+ `run3.sh`): real DDP on 2 CPU processes with Gloo, comm-hook timestamps per bucket, overlap against `no_sync()` plus serial all-reduces, 3 runs. `torch/ddp_profile.py`: torch.profiler events of one DDP step. `torch/mps_launch.py`: eager PyTorch on MPS, sync each against sync once. `torch/extract_source.py`: DDP bucket defaults, Inductor CUDA-graph knobs and skip reasons, `make_graphed_callables` defaults, read from the installed PyTorch 2.14.1. Outputs in `torch/out/`.
- `m1/metal_launch.py`: 200 dependent kernels on the M1 Pro GPU four ways (wait each, queued, one command buffer, indirect command buffer replay); `m1/metal_concurrency.py`: 8 one-threadgroup kernels on one queue, eight queues, one concurrent encoder; `m1/run3.sh` runs both and the MPS script 3 times. Outputs in `m1/out/`.
- `inputs/`: excerpts kept as evidence (Megatron-LM's CUDA_DEVICE_MAX_CONNECTIONS comments, DeepEP's README on dropping NVSHMEM, DeepSeek-V3's 20-of-132-SMs sentences).
- `recompute.py`: parses every raw output, medians, the launch model fitted to NVIDIA's 2019 figures, the copy-pipeline model and the training-step model; writes `out/data.json` and `parts/22_js_sg_data.js` (window.SG). `fill_sgv.py` writes data values into every `data-sgv` element of the Reading parts; `check_embed.py` verifies the page embeds exactly `out/data.json`, the 79 tagged values match, and nothing private leaks. `check/check_page.mjs`: puppeteer, every control (closed blocks opened) at 390 px dark and 920 px light, every stage plays once scrolled into view (inverted 2026-11-12), the page's step model against the Python one, the launch model against NVIDIA's figures, stage end states. `check/check_stages.mjs` (run as `node src/check_stages.mjs` from the page folder, about 3.5 minutes): see the 2026-11-06 rollout below. `check_embed.py` also looks up the login and host names at run time and fails if either appears anywhere in the page folder. `ledger.json`: the knowledge ledger (`python3 html_utils/ledger.py check`).
- `viz_ideas.md`: visuals built and rejected. `coverage.json`: the root's and siblings' claims this page had to reconcile (no old page existed).

Shape: `.claude/skills/explainer-page/page-kinds/topic-child.md`. Departures: no `live.md` (a new page, no old Notion text).

**Stages and their data.** `40_js_sc_pipe.js` (Fig. 1): host memory, one glass lane per stream, the GPU with a copy engine per direction, device memory and the SMs; a chunk is a tile in its stream's colour that slides along its lane (in-track in front, out-track behind) while a copy engine moves it, with dots flowing the way the bytes go, and feeds the SMs while its kernel runs. Schedules: one stream (in order), three streams with two engines, and one engine, from `window.SGPIPE` (the chart's own event schedule, now tagged with each event's chunk); the numbers are `SG.pipe`. `41_js_sc_launch.js` (Fig. 2): the CPU thread and the GPU stream as glass lanes on one time axis for all three modes, launches as dots from CPU to GPU, the time axis zooming to its first 26 µs in the close steps; graph mode adds the captured graph as a glass plate of 20 nodes, instantiated, then launched with one flow. Times are `SGL.model` (fitted to NVIDIA's four V100 numbers). `42_js_sc_ring.js` (Fig. 3): 8 of the 64 GPUs on a ring, each with its seven gradient buckets as columns (height in MiB), filling yellow during backward, orange while all-reduced (dots round the ring, more for a bigger bucket), green when done; GPUs blue while they compute. Times and sizes are `SGM.step` (equal to `SG.step`). Figs. 1 and 3 play each step's time window to scale with their own clock (3.6 and 3.8 s), so the overlap can be watched; reduced motion shows each step's end state.

**Motion.** The two `RD.anim` animations are gone: the launch animation (21 steps, one per kernel, a long replay) became Fig. 2; the training-step animation (11 steps) became Fig. 3 for the mechanism plus a static chart of both modes to scale. Their script-drawn captions moved into the step lists. The default-stream, async-TP and pipeline widgets are reader-driven and never autoplay.
