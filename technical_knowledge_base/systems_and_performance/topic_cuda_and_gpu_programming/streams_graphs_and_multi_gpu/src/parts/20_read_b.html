1. Streams and events, from zero

The problem. A launch only queues work ({{programming model|n:3c65c17b0d0d8162865eec15d9dae87e}}, section 8). Something must say what order the queued work runs in, and which pieces are independent enough to run at the same time. That something is the stream.

A stream is a queue of GPU operations: kernel launches, copies, memsets, waits. NVIDIA's guide: "the order of execution of operations in a stream is the same as the order in which those operations were enqueued", and operations in different streams have no order between them unless you add one ({{Programming Guide 2.5|https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html}}) vendor doc. Every launch names its stream as the fourth launch argument, k<<<grid, block, smem, stream>>>; every async copy takes one as its last argument. "Different streams may overlap" means the hardware is allowed to run them together, not that it will: a kernel that fills every SM leaves no room for another.

An event is a marker you record into a stream. It completes when everything queued before it in that stream has completed. Three uses:

  • Order two streams: cudaEventRecord(e, s1); cudaStreamWaitEvent(s2, e) makes everything queued on s2 afterwards wait for s1's work up to e, without stopping the CPU.
  • Time the GPU: two events and cudaEventElapsedTime give milliseconds between them as the GPU saw them (honest timing is on {{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}}). An event created with cudaEventDisableTiming is cheaper and is the right kind for pure ordering.
  • Wait on the CPU for one point only: cudaEventSynchronize(e), instead of draining everything.

Host waits, from narrowest to widest: cudaEventSynchronize (one point), cudaStreamSynchronize (one stream), cudaDeviceSynchronize (everything on the GPU); cudaStreamQuery and cudaEventQuery only ask. Some calls wait without saying so: cudaMemcpy is synchronous, cudaFree synchronises the device ({{programming model|n:3c65c17b0d0d8162865eec15d9dae87e}}, section 7), and in PyTorch .item(), .cpu(), print(t) and a boolean test of a GPU tensor all wait. A callback can be queued too: cudaLaunchHostFunc(stream, fn, data) runs fn on a CPU thread when the stream reaches it, and such functions "may not call any CUDA APIs" (guide 2.5.4).

The default stream trap

A launch without a stream argument goes to stream 0, the default stream, and there are two kinds. The legacy default stream (nvcc's default) is shared by every host thread and is a blocking stream: work launched into it "will wait for all other blocking streams to complete before it can execute", and the other blocking streams wait for it (guide 2.5.6.1). Streams made with cudaStreamCreate are blocking; cudaStreamCreateWithFlags(&s, cudaStreamNonBlocking) makes one that ignores stream 0. The per-thread default stream (nvcc --default-stream per-thread, or CUDA_API_PER_THREAD_DEFAULT_STREAM before including the headers) gives "each host thread its own independent default stream which will not synchronize with other streams" (guide 2.5.6.2) vendor doc.

// s5_default_stream.cu (compiled here): A on s1, B on stream 0, C on s2, then a copy on stream 0
cudaStreamCreate(&s1); cudaStreamCreate(&s2);   // blocking streams (the default flag)
k<<<1, 256, 0, s1>>>(d);          // A
k<<<1, 256>>>(d + 256);           // B: default stream
k<<<1, 256, 0, s2>>>(d + 512);    // C
cudaMemcpyAsync(d, d + 512, 1024, cudaMemcpyDeviceToDevice);   // default stream again
Predict: with nvcc's default settings, can kernel C run at the same time as kernel A?
B waits for A (A is on a blocking stream), and C, queued after B, waits for B. The three run one after another although they share nothing. Compiled with --default-stream per-thread, B goes to this thread's own stream and A, B and C may all overlap. The chart below draws both.

Note also what the run printed without a driver: nothing, with exit code 0 (run_exit=0), because this program checks no return codes; the four programs that do check stop at their first call.

PyTorch's version. PyTorch never uses the legacy stream for its own work by accident: every operation goes to the current stream of its device, which starts as the default stream and is changed with a context manager:

s = torch.cuda.Stream()
s.wait_stream(torch.cuda.current_stream())   # s must see x fully written
with torch.cuda.stream(s):
    y = f(x)                                   # queued on s
torch.cuda.current_stream().wait_stream(s)   # before anyone on the main stream reads y
y.record_stream(torch.cuda.current_stream())  # or the allocator may hand y's memory out early

The last line is the subtle one. PyTorch's caching allocator records which stream a block was allocated on and reuses freed blocks in that stream's order; a tensor used on a second stream can be freed and reused while the second stream still reads it. The PyTorch notes say it plainly: even when "no other uses of A" exist, "it is still necessary to synchronize" ({{CUDA semantics, 2.14|https://docs.pytorch.org/docs/2.14/notes/cuda.html}}) vendor doc. torch.cuda.Event(enable_timing=True) wraps the CUDA event.

What "may overlap" depends on

SMs. Two kernels run side by side only if the first leaves SMs (or room on them) free. Concurrency pays when kernels are small, a few blocks each; a big GEMM takes the whole GPU and the second kernel simply starts on SMs as they free up. Work queues. The GPU takes work from a limited number of hardware queues. CUDA_DEVICE_MAX_CONNECTIONS sets how many: "1 to 32 connections, default is 8"; with more streams than queues, independent streams can share a queue and serialise through "false dependencies" ({{Programming Guide 3.1 and 5.2|https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html}}) vendor doc. Megatron-LM uses the opposite effect on purpose: it sets the variable to 1 so that launch order becomes execution order, and comments in its tensor-parallel layers say "we rely on CUDA_DEVICE_MAX_CONNECTIONS=1 to ensure that the all-reduce is scheduled before the weight gradient computation" ({{Megatron-LM layers.py, main, Sep 30 2026|https://github.com/NVIDIA/Megatron-LM/blob/main/megatron/core/tensor_parallel/layers.py}}) source. One queue means the communication kernel is guaranteed to start first and then runs under the GEMM.

Priorities. cudaStreamCreateWithPriority gives a stream a priority; "lower numbers correspond to higher priorities", and cudaDeviceGetStreamPriorityRange returns the range for the device (guide 2.5.9.1) vendor doc. Waiting blocks of a high-priority stream get SMs first, which is how communication kernels are kept from queueing behind a long compute kernel; PyTorch exposes it as torch.cuda.Stream(priority=-1) and, for NCCL, TORCH_NCCL_HIGH_PRIORITY ({{PyTorch NCCL environment variables|https://docs.pytorch.org/docs/2.14/torch_nccl_environment_variables.html}}).

The measurement above is a contrast, not a CUDA number: Metal has command queues instead of streams, and on this M1 Pro, eight independent one-threadgroup kernels on eight separate queues took as long as eight in one queue, while the same eight in one encoder marked "concurrent" ran together. Separate queues allowed overlap but did not produce it here. The lesson transfers: never assume overlap, look for it on a timeline.
