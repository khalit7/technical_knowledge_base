1. Streams and events

A launch only queues work ({{programming model|n:3c65c17b0d0d8162865eec15d9dae87e}}, section 8). A stream says in what order queued work runs: "the order of execution of operations in a stream is the same as the order in which those operations were enqueued", and operations in different streams have no order between them unless you add one ({{Programming Guide 2.5|https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html}}) vendor doc. Every launch names its stream as the fourth launch argument, k<<<grid, block, smem, stream>>>; every async copy takes one as its last argument. "Different streams may overlap" means the hardware is allowed to run them together, not that it will: a kernel that fills every SM leaves no room for another.

An event is a marker recorded into a stream; it completes when everything queued before it there has completed. cudaEventRecord(e, s1); cudaStreamWaitEvent(s2, e) makes everything queued on s2 afterwards wait for s1's work up to e, without stopping the CPU. Two events and cudaEventElapsedTime time the GPU (honest timing is on {{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}}); an event made with cudaEventDisableTiming is cheaper and is the right kind for pure ordering.

An event orders two streams; the CPU never waits

s1 produces x and records event e; s2 runs its own work, then its consume(x) waits on e only. The CPU queued all four calls in microseconds and moved on. Durations illustrative.

Hidden waits. Some calls stop the CPU without saying so: cudaMemcpy is synchronous, cudaFree synchronises the device ({{programming model|n:3c65c17b0d0d8162865eec15d9dae87e}}, section 7), and in PyTorch .item(), .cpu(), print(t) and a boolean test of a GPU tensor all wait. One of these per training step is enough to stop the CPU running ahead; log every N steps, or copy to pinned memory with a non-blocking copy and read it a step later.

The default stream trap

A launch without a stream argument goes to stream 0, and there are two kinds. The legacy default stream (nvcc's default) is shared by every host thread and is blocking: work launched into it "will wait for all other blocking streams to complete before it can execute", and the other blocking streams wait for it (guide 2.5.6.1). Streams made with cudaStreamCreate are blocking; cudaStreamCreateWithFlags(&s, cudaStreamNonBlocking) makes one that ignores stream 0. The per-thread default stream (nvcc --default-stream per-thread, or CUDA_API_PER_THREAD_DEFAULT_STREAM before including the headers) gives "each host thread its own independent default stream which will not synchronize with other streams" (guide 2.5.6.2) vendor doc.

// s5_default_stream.cu (compiled here): A on s1, B on stream 0, C on s2, then a copy on stream 0
cudaStreamCreate(&s1); cudaStreamCreate(&s2);   // blocking streams (the default flag)
k<<<1, 256, 0, s1>>>(d);          // A
k<<<1, 256>>>(d + 256);           // B: default stream
k<<<1, 256, 0, s2>>>(d + 512);    // C
cudaMemcpyAsync(d, d + 512, 1024, cudaMemcpyDeviceToDevice);   // default stream again

B waits for A (A is on a blocking stream), and C, queued after B, waits for B. The three run one after another although they share nothing. Compiled with --default-stream per-thread, B goes to this thread's own stream and A, B and C may all overlap.

One flag turns three serial kernels into three concurrent ones

How to tell which one a binary uses: the flag changes which runtime functions the code calls. The program above compiled both ways compiled here: legacy calls cudaMemcpyAsync, per-thread calls cudaMemcpyAsync_ptsz (the "per-thread stream" entry point). Without a driver this program printed nothing and exited with run_exit=0, because it checks no return codes; the four programs that do check stop at their first call.

PyTorch's streams, and the allocator trap

Every PyTorch operation goes to the current stream of its device, changed with a context manager:

s = torch.cuda.Stream()
s.wait_stream(torch.cuda.current_stream())   # s must see x fully written
with torch.cuda.stream(s):
    y = f(x)                                   # queued on s
torch.cuda.current_stream().wait_stream(s)   # before anyone on the main stream reads y
y.record_stream(torch.cuda.current_stream())  # or the allocator may hand y's memory out early

The last line is the subtle one. The caching allocator reuses a freed block in the order of the stream it was allocated on; a tensor used on a second stream can be freed and reused while that stream still reads it. Even when "no other uses of A" exist, "it is still necessary to synchronize" ({{CUDA semantics, 2.14|https://docs.pytorch.org/docs/2.14/notes/cuda.html}}) vendor doc. Forgetting wait_stream or record_stream gives a race or a use-after-free: wrong numbers, not errors. torch.cuda.Event(enable_timing=True) wraps the CUDA event.

What "may overlap" depends on

Overlap needs free SMs (concurrency pays when kernels are small, a few blocks each; a big GEMM takes the whole GPU) and free hardware queues (with more streams than queues, independent streams serialise through "false dependencies"); stream priorities let communication kernels take SMs first. The details are in the closed block below.

Separate queues allowed overlap but did not produce it

A contrast, not a CUDA number: Metal has command queues instead of streams, and on this M1 Pro eight independent one-threadgroup kernels on eight queues took as long as eight in one queue, while the same eight in one encoder marked "concurrent" ran together. Never assume overlap; look for it on a timeline.

Depth: hardware queues, priorities, host waits, callbacks, and Megatron's one-queue trick

Free SMs: concurrency pays when kernels are small, a few blocks each; a big GEMM takes the whole GPU and the next kernel starts on SMs as they free up. Hardware queues: CUDA_DEVICE_MAX_CONNECTIONS sets how many, "1 to 32 connections, default is 8"; with more streams than queues, independent streams can serialise through "false dependencies" ({{Programming Guide 3.1 and 5.2|https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html}}) vendor doc. Priorities: cudaStreamCreateWithPriority, where "lower numbers correspond to higher priorities" (guide 2.5.9.1); waiting blocks of a high-priority stream get SMs first, which keeps communication kernels from queueing behind a long compute kernel (torch.cuda.Stream(priority=-1), and TORCH_NCCL_HIGH_PRIORITY for NCCL, {{PyTorch NCCL environment variables|https://docs.pytorch.org/docs/2.14/torch_nccl_environment_variables.html}}).

Host waits, narrowest to widest: cudaEventSynchronize (one point), cudaStreamSynchronize (one stream), cudaDeviceSynchronize (everything); cudaStreamQuery and cudaEventQuery only ask. A callback can be queued too: cudaLaunchHostFunc(stream, fn, data) runs fn on a CPU thread when the stream reaches it, and such functions "may not call any CUDA APIs" (guide 2.5.4).

Megatron-LM uses false dependencies on purpose. It sets CUDA_DEVICE_MAX_CONNECTIONS to 1 so launch order becomes execution order; its tensor-parallel layers say "we rely on CUDA_DEVICE_MAX_CONNECTIONS=1 to ensure that the all-reduce is scheduled before the weight gradient computation" ({{Megatron-LM layers.py, main, Sep 30 2026|https://github.com/NVIDIA/Megatron-LM/blob/main/megatron/core/tensor_parallel/layers.py}}) source. One queue guarantees the communication kernel starts first; it then runs under the GEMM.
