5. Several GPUs from one process: devices, peer access, IPC

Selecting a device. The runtime has a "current device" per host thread; cudaSetDevice(d) switches it, and allocations, streams and launches made afterwards belong to device d. A stream belongs to one device; an event can be waited on by a stream of another device, which is how work on two GPUs is ordered. In PyTorch: torch.cuda.set_device(d), with torch.cuda.device(d), or explicit device="cuda:1".

One address space. On 64-bit systems the host and all GPUs share one virtual address space (unified virtual addressing), so a pointer says which device it belongs to and cudaMemcpyAsync(..., cudaMemcpyDefault, s) can copy between any two. Peer access goes further: after cudaDeviceEnablePeerAccess, a kernel on GPU 0 can dereference a pointer into GPU 1's memory, and the loads and stores travel over NVLink or PCIe with no copy.

// s3_peer.cu (compiled here)
cudaDeviceCanAccessPeer(&can01, 0, 1);           // is there a path GPU 0 can use?
cudaSetDevice(1); cudaMalloc(&b, n * 4);
cudaSetDevice(0); cudaMalloc(&a, n * 4);
if (can01) {
  cudaDeviceEnablePeerAccess(1, 0);               // GPU 0 may now dereference GPU 1 pointers
  add_remote<<<n / 256, 256>>>(a, b, n);          // b is read across the link
} else {
  cudaMemcpyPeerAsync(tmp, 0, b, 1, n * 4, 0);    // copy first, then compute locally
  add_remote<<<n / 256, 256>>>(a, tmp, n);
}
cudaIpcGetMemHandle(&hnd, a);                     // let another process map this allocation

Whether peer access exists depends on the wiring: GPUs on one NVLink/NVSwitch fabric, or under one PCIe switch on a platform that allows it. nvidia-smi topo -m prints the matrix (NV#, PIX, PXB, PHB, SYS), and consumer cards from the RTX 4090 on have no NVLink at all. The wires, their speeds and the switch layouts are {{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}}'s subject; the programmer's question is only "can this pointer be read from there, and how fast".

Across processes. PyTorch training uses one process per GPU (torchrun), so peer memory crosses process boundaries: cudaIpcGetMemHandle turns an allocation into a small handle that another process opens with cudaIpcOpenMemHandle (newer code uses the driver's virtual memory API and exports a file descriptor). NCCL and symmetric memory (section 8) do exactly this under the hood to read each other's buffers.

One process, many GPUs, or one process per GPU?
One process per GPU is the PyTorch default and avoids Python's single interpreter becoming the launch bottleneck for eight GPUs. One process driving several GPUs is fine in C++ (and is what ncclCommInitAll and section 6's program do), but NCCL warns that "using multiple GPUs per process with CUDA graph capture may result in deadlocks" ({{NCCL user guide, CUDA graphs|https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/cudagraph.html}}) vendor doc.
