4. CUDA graphs in PyTorch, torch.compile and inference engines

By hand: torch.cuda.graph. PyTorch wraps capture in a context manager. The rules follow from what a graph freezes (section 3): inputs and outputs live at fixed addresses, so you copy new data into static tensors; no CPU-GPU synchronisation inside (no .item()); no data-dependent Python control flow; and warm-up must run first, on a side stream, so that lazy initialisation (cuBLAS handles, autotuning, allocator growth) happens outside the capture ({{CUDA semantics, CUDA Graphs, 2.14|https://docs.pytorch.org/docs/2.14/notes/cuda.html}}) vendor doc.

static_x = torch.randn(B, D, device="cuda")
s = torch.cuda.Stream(); s.wait_stream(torch.cuda.current_stream())
with torch.cuda.stream(s):                       # warm-up on a side stream
    for _ in range(3):
        static_y = model(static_x)
torch.cuda.current_stream().wait_stream(s)
g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):                        # capture: kernels recorded, memory from a private pool
    static_y = model(static_x)
for x in batches:
    static_x.copy_(x)                            # new data, same address
    g.replay()                                   # one call for every kernel in the model
    out = static_y.clone()                       # the next replay overwrites static_y

Memory allocated during capture comes from a pool private to the graph, kept for its whole life; graphs can share a pool (pool=, torch.cuda.graph_pool_handle()). torch.cuda.make_graphed_callables captures a module's forward and backward together, with num_warmup_iters = 3 by default; its docstring adds that DDP "needs 11 iterations for warm up" read here: PyTorch 2.14.1 source. With DDP and NCCL inside a graph, the PyTorch notes require async error handling off (NCCL_ASYNC_ERROR_HANDLING=0, now spelled TORCH_NCCL_ASYNC_ERROR_HANDLING) and at least 11 DDP-enabled warm-up iterations before capturing the backward.

Automatic: torch.compile(mode="reduce-overhead") and CUDAGraph Trees

torch.compile has four modes, "default", "reduce-overhead", "max-autotune" and "max-autotune-no-cudagraphs"; "reduce-overhead" "reduces the overhead of python with CUDA graphs, useful for small batches", at "the cost of more memory usage" (docstring, PyTorch 2.14.1). The graphs are managed by CUDAGraph Trees, whose design note in torch/_inductor/cudagraph_trees.py explains the name: graphs recorded across graph breaks share one memory pool, and "we support arbitrary trees of CUDA graph operations, not just sequences", using only the memory of the largest path read here. What a user meets in practice:

  • Warm-up, record, replay. The first calls run eagerly, the next records, later calls replay. Outputs live in the shared pool, so an output kept from one iteration can be overwritten by the next replay; PyTorch raises an error when you read such a stale output, and the fix is to .clone() it.
  • One graph per shape. cudagraph_skip_dynamic_graphs is false by default, so each new input shape records a new graph, and Inductor warns when the count passes cudagraph_dynamic_shape_warn_limit = 8. Pad batch sizes to a few buckets.
  • Skips, with a reason. Inductor declines to graph a region and logs "skipping cudagraphs due to ..." for, among others: . TORCH_LOGS=perf_hints shows them.
  • Partitions instead of all or nothing. graph_partition is true by default in 2.14.1: Inductor splits a compiled graph around the parts that cannot be graphed and graphs the rest.
When not to bother
A training step for a large model spends tens of milliseconds per kernel sequence on big matmuls; launch overhead is a rounding error there and graphs mainly cost memory and constraints. Graphs earn their keep where kernels are small: decoding, small-batch inference, small models, and the many tiny kernels of optimizers and norms. Check first: if the profiler's GPU row has no gaps, graphs will not help.

Inference engines

Decoding is the textbook case: one token per step, every kernel small, the same sequence of kernels every step. Engines therefore capture one graph per batch size from a list of capture sizes and pad each real batch up to the nearest one. vLLM's design doc lists five modes (NONE, PIECEWISE, FULL, FULL_DECODE_ONLY, FULL_AND_PIECEWISE) and defaults to FULL_AND_PIECEWISE with piecewise compilation: full graphs for uniform decode batches and piecewise graphs otherwise, where piecewise means capturing everything except operations graphs cannot handle, "mainly attention", whose shapes change with every request ({{vLLM docs, CUDA graphs design, Sep 26 2026|https://docs.vllm.ai/en/latest/design/cuda_graphs.html}}) published. The same trade-off as graph_partition: graph what is static, run the dynamic part eagerly between graphs.
