Common mistakes, a checklist, interview questions

Timing GPU work with a CPU clock and no synchronisation
The clock measures how long it took to queue the work. Use CUDA events, or synchronise before reading the clock (section 1; methodology on {{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}}).
A hidden synchronisation in the training loop
loss.item() every step, print(tensor), if (x > 0).any():, a .cpu() for logging, torch.cuda.empty_cache(): each drains the queue so the CPU can no longer run ahead. Log every N steps, or copy to pinned memory with a non-blocking copy and read it a step later.
Expecting two streams to overlap because they are two streams
The legacy default stream serialises blocking streams; big kernels leave no SMs; few hardware queues create false dependencies; the M1 measurement in section 1 overlapped nothing across queues. Check on a timeline.
Using a tensor on a side stream without wait_stream and record_stream
Either a race (reading before the producer finished) or a use-after-free through the caching allocator. Both give wrong numbers, not errors.
non_blocking=True on a device-to-host copy, then reading the result
The CPU reads the buffer before the copy lands. Synchronise (an event) before use.
Capturing a CUDA graph and then feeding it new tensors
A replay reads the addresses captured, not your new tensor. Copy new data into the static input; clone outputs you keep. Shape changes need a new graph.
A rank-dependent branch around a collective
The classic hang (section 7). Every rank must make the same collective calls in the same order with the same sizes.
Expecting overlap to remove communication cost
It hides the communication that is smaller than the compute running beside it, minus the slowdown from sharing SMs. The last bucket is always exposed; tensor-parallel all-reduces are on the critical path.

How to check, in order

  1. Profile one step with Nsight Systems or torch.profiler and look at the GPU rows: gaps between kernels (launch-bound or a sync), copies not under kernels (no overlap), NCCL kernels after backward ends (exposed communication).
  2. Gaps with tiny kernels: remove syncs, fuse, then CUDA graphs (mode="reduce-overhead"), and confirm the gaps close.
  3. Exposed all-reduce: check bucket sizes and order, look for a huge last bucket (tied embeddings), consider gradient accumulation (fewer all-reduces per sample) or a faster group layout.
  4. Hangs: the checklist in section 7.

Interview questions

What is a CUDA stream, and what does an event add?
A FIFO queue of GPU operations: in order within a stream, unordered across streams. An event is a marker in a stream that other streams can wait on (ordering without blocking the CPU) and that can time GPU work.
Why might two kernels on two streams still run one after the other?
The legacy default stream between them; the first kernel occupies every SM; false dependencies through a limited number of hardware queues (CUDA_DEVICE_MAX_CONNECTIONS); an implicit synchronisation such as cudaMalloc or a pageable copy.
Why does an async copy need pinned memory?
The copy engine reads physical pages by DMA. Pageable pages could move, so the driver stages them through a pinned buffer and the copy cannot overlap freely.
What does a CUDA graph save, and what does it cost?
It replaces per-kernel CPU launch work with one launch of a pre-validated graph, and lets the GPU run nodes with smaller gaps. It costs an instantiation (hundreds of microseconds), fixed addresses and shapes, no host syncs inside, and memory held by the graph's pool.
How does DDP overlap communication with backward?
Gradient hooks fill buckets in reverse parameter order; when a bucket is full its all-reduce is launched on NCCL's stream while autograd keeps computing earlier layers; the optimizer waits for all of them. Default buckets 25 MiB, first bucket 1 MiB.
Why can't tensor-parallel all-reduces be hidden the same way?
The next matmul needs their result, so no independent work exists to overlap them with, unless the matmul is split and pipelined with the communication (async TP, symmetric memory).
A 512-GPU job hangs at step 40,000. What do you do?
Find the rank and call that differ: the flight-recorder dumps on watchdog timeout, py-spy on each rank, the kernel log for a dead GPU or node; check the last collective's sequence number across ranks; restart from the checkpoint without the bad node.
Why do NCCL collectives slow down your compute kernels?
They are kernels too: they take SMs (CTAs) and memory bandwidth while they run. NCCL lets you cap CTAs (maxCTAs, NCCL_CTA_POLICY_EFFICIENCY); DeepSeek-V3 reserved 20 of 132 SMs for communication.
