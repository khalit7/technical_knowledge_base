3. Launch overhead and CUDA graphs

Every launch costs CPU time in the runtime and driver. When kernels are long the CPU queues them far ahead and the cost is hidden; when they are short, as in LLM decoding (one token at a time, every matmul small) or a model built from many small operations, the GPU finishes each kernel before the CPU has queued the next and sits idle between them.

NVIDIA's measurement ({{Alan Gray, "Getting Started with CUDA Graphs", NVIDIA blog, Sep 5 2019, V100|https://developer.nvidia.com/blog/cuda-graphs/}}) published: 20 kernels per step, 1,000 steps, each kernel 2.9 µs of GPU work. Synchronising after every launch: 9.6 µs per kernel. Launching the 20 back to back on a stream and synchronising once per step: 3.8 µs. The same 20 as one CUDA graph: 3.4 µs. Creating and instantiating the graph took "around 400µs", once.

Fig. 2 draws those 20 kernels to scale, on the same time axis for all three ways: the CPU thread in front, the GPU stream behind, each launch as dots flowing from one to the other. Pick a way to launch them:

  1. The CPU launches kernel 1. The runtime and the driver spend about 3.8 µs of CPU time queueing it; the GPU has nothing to do yet.
  2. The kernel runs; the CPU waits. The GPU runs it in 2.9 µs while the CPU sits in a synchronise; waking the CPU up costs about 2.9 µs more, and the GPU is idle again meanwhile.
  3. The same, twenty times. Launch, run, wait, wake: 192 µs for 20 kernels of 2.9 µs.
  4. The GPU worked 30% of the time. 9.6 µs per kernel, as NVIDIA measured: most of every kernel's slot is CPU launch and wake-up.
  1. The CPU launches back to back. No synchronise between kernels: kernel 2's launch starts as soon as kernel 1's returns, and kernel 1 runs on the GPU meanwhile.
  2. Each launch takes longer than each kernel. 3.8 µs to launch, 2.9 µs to run: the GPU finishes every kernel before the next arrives and waits about 0.9 µs each time. The queue never fills: the step is launch-bound.
  3. 3.8 µs per kernel. 76 µs for the 20 and one synchronise at the end, 2.5 times faster than waiting each time; the CPU, not the GPU, sets the pace.
  1. Capture: the 20 launches become nodes. Between cudaStreamBeginCapture and cudaStreamEndCapture, launches on the stream are recorded into a graph (the glass plate), not run. Nothing reaches the GPU.
  2. Instantiate once. cudaGraphInstantiate validates the graph and prepares every launch ahead of time: about 400 µs for these 20 kernels on V100, paid once before the loop (not on this axis).
  3. One call launches all 20. cudaGraphLaunch(ge, s) costs the CPU about one launch (3.8 µs, the model's assumption) and hands the whole graph to the stream.
  4. The GPU runs the nodes back to back. About 0.5 µs between nodes, 71.3 µs for this first replay. The CPU is free after a few microseconds and here only waits in the final synchronise (grey); in a loop it queues the next replay instead, so in steady state a replay costs 68 µs.
  5. 3.4 µs per kernel. Against 3.8 on a stream and 9.6 launching and waiting; in steady state the GPU is busy 85% of the time. Same kernels, grids and pointers on every replay: that is what a graph freezes.

Fig. 2 is to scale. NVIDIA's four numbers fit a simple model derived: with a stream the GPU waits for the CPU, so a launch costs the CPU about 3.8 µs; a synchronisation adds about 2.9 µs of wait and wake-up (9.6 − 3.8 − 2.9); inside a graph the GPU still leaves about 0.5 µs between nodes (3.4 − 2.9). The shape, not the exact microseconds, carries over to newer GPUs and drivers.

The same experiment on the M1 Pro's GPU measured on Apple M1 Pro GPU. Metal has no streams or graphs but the same three choices: one command buffer per kernel and wait (launch-and-sync), command buffers committed back to back (a stream), and dispatches recorded once into an indirect command buffer and replayed with one call (the nearest thing to a CUDA graph). 200 dependent kernels of 1,024 threads, all four ways giving the same result (101.002):

Measured: waiting after each launch is the disaster; replay leaves only the GPU's time

Per kernel, log scale. Waiting each time was 8.2× slower than queueing. What does not transfer: Metal command buffers are not CUDA launches, Python adds its own cost, and the absolute microseconds belong to this machine.

Depth: the M1 measurement in full

Median of 3 runs, each the median of 7 trials; load average 10.6 to 11.3 (the laptop was shared). Launch and wait: 179.9 µs per kernel (runs 179.9, 188.7, 174.2). Queued: 21.9. One command buffer: 5.3, of which the GPU's own clock counts 1.92, and encoding cost the CPU 453.5 µs for all 200 (2.27 µs each, mostly Python). Replay: 3.3 µs per kernel with 21.7 µs of CPU for the whole sequence; recording it once took 853 µs. PyTorch on MPS, 200 dependent x * a + b: 226.2 µs per iteration synchronising each time, 12.3 once (PyTorch 2.14.1).

What a CUDA graph is

"A graph is a series of operations such as kernel launches, data movement, etc., connected by dependencies", used in three stages: definition, instantiation (which "takes a snapshot of the graph template, validates it, and performs much of the setup and initialization of work with the aim of minimizing what needs to be done at launch") and execution, launching the executable graph into a stream as often as you like ({{Programming Guide 4.2, CUDA Graphs, v13.4.2|https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html}}) vendor doc. Fig. 2's graph mode shows the three stages.

Graphs are defined by stream capture, which records what you would have launched anyway and is what libraries use, or by the explicit API (cudaGraphAddNode):

// s2_graph.cu, part 1 (compiled here)
cudaStreamBeginCapture(s, cudaStreamCaptureModeGlobal);
for (int k = 0; k < 20; ++k) axpb<<<n / 256, 256, 0, s>>>(d, n, 1.0001f, 0.5f);   // recorded, not run
cudaStreamEndCapture(s, &g);
cudaGraphInstantiate(&ge, g, 0);                       // once: the expensive step
for (int it = 0; it < 1000; ++it) cudaGraphLaunch(ge, s);   // one call per 20 kernels

What a graph freezes. Every node's kernel, grid and argument values, including every pointer: a replay reads and writes the same addresses with the same shapes. New data means writing new values into the same buffers; a new scalar argument means an update. Updating is cheaper than re-instantiating: capture again with the same structure and call cudaGraphExecUpdate(ge, g2, &info), or set one node with cudaGraphExecKernelNodeSetParams. Parameters "such as kernel parameters and memory addresses" may change; "major changes to graph structure (such as topology or node types) require re-instantiation" (guide 4.2).

What breaks capture. Anything that needs the GPU to have actually run: "It is invalid to synchronize or query the execution status of a stream which is being captured", synchronous calls such as cudaMemcpy are invalid, and so is touching the legacy default stream; "when an invalid operation is attempted during stream capture, any associated capture graphs are invalidated" (guide 4.2). Other streams join a capture by waiting on an event recorded in a capturing stream, which is how multi-stream work, NCCL included, ends up in one graph.

Predict: instantiating costs 400 µs once and saves 0.4 µs per kernel against a stream (NVIDIA's numbers). After how many kernel launches does the graph pay for itself?
400 / (3.8 − 3.4) = 1,000 kernels derived, 50 steps of 20. Training and serving replay the same graph millions of times, so it pays; a graph re-captured every step because shapes keep changing never does. That is the whole design problem of section 4.

Depth: conditional nodes (loops on the GPU), their SASS, and other graph features

Control flow on the GPU: conditional nodes

A graph replays a fixed sequence, so a loop whose trip count depends on data (iterate until converged, decode until end-of-sequence) used to mean returning to the CPU. Conditional nodes keep the decision on the GPU: an IF node runs its body once if a condition value is non-zero (with an optional ELSE body), a WHILE node repeats its body while it is non-zero, and a SWITCH node runs body n. IF and WHILE arrived in CUDA 12.4, ELSE and SWITCH in 12.8 ({{NVIDIA blog, May 10 2024, updated Feb 3 2025|https://developer.nvidia.com/blog/dynamic-control-flow-in-cuda-graphs-with-conditional-nodes/}}) published. A kernel in the graph sets the condition:

// s2_graph.cu, part 3: a WHILE loop that lives on the GPU
__global__ void halve_and_test(float* x, cudaGraphConditionalHandle h) {
  x[0] *= 0.5f;
  cudaGraphSetConditional(h, x[0] > 1.0f ? 1u : 0u);    // 0 ends the loop
}
cudaGraphConditionalHandleCreate(&h, w, 1, cudaGraphCondAssignDefault);
cp.type = cudaGraphNodeTypeConditional; cp.conditional.handle = h;
cp.conditional.type = cudaGraphCondTypeWhile; cp.conditional.size = 1;
cudaGraphAddNode(&cn, w, nullptr, nullptr, 0, &cp);
cudaStreamBeginCaptureToGraph(s, cp.conditional.phGraph_out[0], nullptr, nullptr, 0, cudaStreamCaptureModeGlobal);
halve_and_test<<<1, 1, 0, s>>>(d, h);                    // captured into the loop body
cudaStreamEndCapture(s, nullptr);

What cudaGraphSetConditional compiles to on sm_90a compiled here: the kernel loads a function address from constant bank 4, which the driver fills, and calls it (CALL.ABS.NOINC); the sm_100a build does the same. The condition is set by a driver routine running on the GPU, not by a special instruction.



Other graph features worth knowing. Graphs can allocate and free memory as nodes (cudaGraphInstantiateFlagAutoFreeOnLaunch); a graph instantiated with cudaGraphInstantiateFlagDeviceLaunch can be launched from a kernel ("fire and forget", "tail" or "sibling" launch, guide 4.2); cudaGraphUpload moves the setup out of the first launch (NVIDIA's post saw the first launch "around 33% slower"); and cudaGraphDebugDotPrint writes the graph as a DOT file to look at.
