7. When it hangs: NCCL errors, timeouts and debugging

Why hangs, not crashes. A collective waits for every rank. If one rank never arrives, because it crashed, took a different branch, ran out of memory or is stuck on I/O, the others do not fail: their NCCL kernels spin on the GPU waiting for data that never comes, and the CPU blocks at the next synchronisation. A 1,000-GPU job then stops with 999 healthy-looking processes. Debugging a hang is mostly finding the rank, and the call, that differs.

The usual causes

What PyTorch gives you

ProcessGroupNCCL runs a watchdog thread that checks every outstanding collective against the timeout passed to init_process_group(timeout=...). The behaviour is set by environment variables documented for PyTorch 2.14 ({{PyTorch NCCL environment variables|https://docs.pytorch.org/docs/2.14/torch_nccl_environment_variables.html}}) vendor doc:

  • TORCH_NCCL_ASYNC_ERROR_HANDLING (default 3): what the watchdog does when a collective fails or times out (tear down the communicator and the process, so the job fails instead of hanging).
  • TORCH_NCCL_BLOCKING_WAIT: makes wait() block the CPU, so the timeout raises in your own code.
  • TORCH_NCCL_TRACE_BUFFER_SIZE: the size of the flight recorder, a ring buffer of the last collectives on each rank (which call, sizes, state); TORCH_NCCL_DUMP_ON_TIMEOUT writes it out when the watchdog fires, and comparing the dumps across ranks shows who is behind. TORCH_NCCL_DESYNC_DEBUG tries to name the rank that caused a desync.
  • TORCH_NCCL_ENABLE_MONITORING and TORCH_NCCL_HEARTBEAT_TIMEOUT_SEC: a second thread that kills the process if the watchdog itself is stuck; TORCH_NCCL_NAN_CHECK checks inputs for not-a-number values.

The older names without TORCH_ (NCCL_BLOCKING_WAIT, NCCL_ASYNC_ERROR_HANDLING) were always PyTorch's, not NCCL's: neither string is in the NCCL 2.31.2 library, while every NCCL_* variable named on this page is checked here with strings libnccl.so.

What NCCL gives you

  • NCCL_DEBUG=INFO (with NCCL_DEBUG_SUBSYS to filter): the version, the transport for each peer (NVLink, P2P, shared memory, IB, sockets), rings and trees. A job that fell back to TCP sockets is visible in the first lines.
  • NCCL_P2P_DISABLE, NCCL_SHM_DISABLE, NCCL_IB_DISABLE: switch transports off one at a time to isolate a broken one; NCCL_ALGO and NCCL_PROTO force an algorithm or protocol (for experiments, not production).
  • ncclCommGetAsyncError and ncclCommAbort: a non-blocking communicator (blocking = 0 in its config) reports errors asynchronously, and abort unblocks the kernels so the process can exit or recover; NCCL 2.31.2 also has ncclCommRevoke, ncclCommShrink and ncclCommGrow for removing and adding ranks without restarting everything.
A first-response checklist
1. Which ranks are stuck, and in which call? (py-spy dump on every rank, or the flight recorder.) 2. Do all ranks agree on the last collective's sequence number and size? 3. Did one rank die first (OOM, a hardware error in the kernel log)? 4. Is the transport the expected one (NCCL_DEBUG=INFO)? 5. Does a tiny all-reduce test across the same nodes pass (nccl-tests)?
