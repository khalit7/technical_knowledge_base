8. Beyond collectives: symmetric memory, NVSHMEM and kernels that communicate

The problem. A collective is a separate kernel launched from the CPU, with a fixed shape, between compute kernels. Two things it cannot do well: overlap with the inside of a matmul (tensor parallelism, section 6), and move small, data-dependent messages (sending each token to the GPU that holds its expert in a mixture-of-experts layer). Both want the compute kernel itself to read or write another GPU's memory.

Symmetric memory is the enabling idea: every rank allocates the same buffer, at the same offset in a shared heap, so "this buffer on rank j" can be computed from a local pointer, and a kernel can load or store it over NVLink (peer access, section 5) or put it across the network. Two lineages:

  • NVSHMEM: "a parallel programming interface based on OpenSHMEM" that creates "a global address space for data that spans the memory of multiple GPUs", with "a low-overhead, in-kernel communication API for use by GPU threads" (one-sided put, get, atomics and signals) alongside operations on CUDA streams; version 3.8 is current and supports CUDA 13.4 ({{NVIDIA NVSHMEM page|https://developer.nvidia.com/nvshmem}}) vendor doc. It is the classic way to write kernels that communicate across nodes.
  • NCCL's own device API. Recent NCCL registers symmetric memory windows (ncclCommWindowRegister, flag NCCL_WIN_COLL_SYMMETRIC) and ships a device-side header; in NCCL 2.31.2 it is nccl_device.h, with parts named read here. LSA (load/store accessible) covers peers reachable by plain loads and stores; GIN (GPU-initiated networking) covers peers across the network.

In PyTorch, torch.distributed._symmetric_memory: symm_mem.empty(size, device=...) allocates, symm_mem.rendezvous(tensor, group) exchanges handles (both "must be called in the same order on all ranks in the group"), with backends for CUDA peer memory within a node, NVSHMEM across nodes, and NCCL symmetric kernels (NCCL 2.27 or newer); each buffer comes with "signal pads" for synchronisation; uses named are async tensor parallelism and MoE token dispatch (all_to_all_vdev_2d) ({{PyTorch symmetric memory docs, 2.14|https://docs.pytorch.org/docs/2.14/symmetric_memory.html}}) vendor doc. Async TP splits a tensor-parallel matmul so that each slice of the all-gather feeds a slice of the matmul as it arrives, which is the way around section 6's "nothing to hide it under".

A current example, checked
DeepSeek's DeepEP, the expert-parallel all-to-all library, was the best-known NVSHMEM user. Its README now says V2 moved to "the lightweight NCCL Gin backend" and V2.5 removed "V1, including its APIs, NVSHMEM backend ... NVSHMEM is no longer a dependency"; it also notes "EP dispatch and combine require GPU SMs" ({{DeepEP README, Sep 30 2026|https://github.com/deepseek-ai/DeepEP}}) source. Older write-ups that describe DeepEP as built on NVSHMEM describe V1.

For the reader who will write kernels: this is where the line between "kernel" and "communication" disappears. The tools are the same as everywhere on this page (streams, events, signals, keeping SMs busy), applied inside one kernel instead of between kernels.
