2. Copies: pinned memory, the chunked pipeline, managed memory

Host memory is far away. A PCIe 5.0 x16 link moves about 63 GB/s each way (the figure {{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}} uses), while an H100 SXM reads its own HBM at 3.35 TB/s vendor spec, about 53 times faster derived: 3,350 / 63. A kernel that waits for its input to cross PCIe runs at PCIe speed, so the data must move while the GPU computes on something else.

Pinned memory first. The copy engines move data by DMA, reading physical pages directly, so those pages must not move while the copy runs. Pageable memory can, so the driver stages it through a pinned buffer and the copy is not truly asynchronous: "In order for memory copies involving CPU memory to be carried out asynchronously, the host buffers must be pinned and page-locked" (guide 2.5.2.3) vendor doc. Allocate it with cudaMallocHost (PyTorch: pin_memory=True in the DataLoader, or t.pin_memory()), and do not pin everything: pinned pages are taken from the OS. Copy engines are separate from the SMs, so a copy and a kernel run at the same time; with two engines (asyncEngineCount in cudaGetDeviceProperties) a host-to-device and a device-to-host copy also overlap each other, and with one the two directions take turns.

The chunked pipeline

Cut the data into chunks and give each chunk its own copy in, kernel, copy out on one of a few streams: while chunk 2 is copied in, chunk 1's kernel runs and chunk 0 is copied out.

Predict: 256 MiB in, a kernel, 256 MiB out. Cutting it into 8 chunks on 3 streams makes it how much faster?
The kernel takes 0.16 ms against 4.26 ms for each copy direction, so hiding it saves almost nothing; the gain comes from running the copy out under the copy in, which needs two copy engines. Fig. 1 plays it; the chart below lets you change the chunks and the engines.

Fig. 1 runs that job: 256 MiB in, a kernel, 256 MiB out, as 8 chunks of 32 MiB. Each chunk is a tile coloured by its stream and each stream is a lane between host memory and the GPU; a tile slides along its lane while a copy engine moves it, dots flowing the way the bytes go, and sits on the SMs while its kernel runs. Time is drawn to scale within each step (the clock above the GPU).

  1. The parts. On the left, the pinned host buffer cut into 8 chunks; on the right, the GPU: a copy engine for each direction at its edge, device memory and the SMs behind them. First every chunk is queued on one stream.
  2. Everything on one stream: 8.68 ms. Inside one stream every operation waits for the one before, so chunk 0 is copied in (0.53 ms at 63 GB/s), computed and copied out before chunk 1 starts. One unit works while two wait: 4.26 + 0.16 + 4.26 ms in series.
  3. Three streams: a kernel runs while the next chunk copies in. Chunk c now goes on stream c mod 3, and each chunk's copy in, kernel and copy out are queued on its own stream, and different streams may overlap. Chunk 0's kernel (0.02 ms) runs the moment it lands, while the copy engine is already moving chunk 1.
  4. Steady state, both copy engines busy: 4.81 ms. The in-engine never stops; the out-engine follows one chunk behind, copying a chunk out while later ones come in. The job ends one chunk-copy after the last input lands, 1.80 times faster than in series.
  5. One copy engine: 8.52 ms. A GPU with one engine (asyncEngineCount = 1) takes copies in and out in turns. The engine never idles, so the job lasts exactly as long as its copies, 8.52 ms: the kernels are hidden, and that is all that is saved against the serial 8.68.
  6. The kernel was never the problem. The SMs were busy 0.16 ms of the 4.81 (3%). Overlap hid the kernel and ran the two copy directions together; it cannot make a copy shorter.

Try any chunk count

The chart is the same model for 1 to 16 chunks, with one or two copy engines. More chunks shrink the first copy in and the last copy out that nothing can hide, so the curve flattens towards the time of one direction's copies; with one engine it never falls much below the serial time.

Overlap hides the smaller thing under the larger one. When copies dominate, the fixes are to copy less (keep data on the GPU, compress, use lower precision) or a faster link.

In PyTorch, and when it matters for training

loader = DataLoader(ds, batch_size=16, pin_memory=True, num_workers=4)
for x, y in loader:
    x = x.to("cuda", non_blocking=True)   # returns at once; ordered before the forward on the stream
    y = y.to("cuda", non_blocking=True)
    loss = model(x, y)

Host-to-device with non_blocking=True is safe because later kernels on the same stream wait for the copy. The other direction is not: "attempting cuda_tensor.to("cpu", non_blocking=True).mean() will result in erroneous outputs", since the CPU reads the buffer before the copy lands; record an event and wait on it first.

For LLM pretraining the input copy is tiny. 16 sequences of 1,024 tokens as int64 ids, inputs plus targets, are 262,144 bytes, about 0.004 ms over PCIe derived, against tens of milliseconds of compute. Copy/compute overlap matters when the bytes are large next to the work: activations or optimizer state offloaded to the CPU (torch.autograd.graph.save_on_cpu(pin_memory=True), FSDP's CPU offload), inference that streams weights or KV cache from host memory, and image or video pipelines that decode on the CPU. The same rule decides each: if copying a layer's bytes takes longer than computing that layer, overlap cannot hide it.

Managed (unified) memory: the copy you do not write

cudaMallocManaged returns one pointer valid on the host and every GPU, and "per default cudaMallocManaged migrates based on a fault-and-migrate mechanism": the first GPU touch of a host-resident page faults and moves it, inside your kernel's time ({{Programming Guide 4.1, Unified Memory, v13.4.2|https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/unified-memory.html}}) vendor doc. The cure is the pipeline above: cudaMemPrefetchAsync(ptr, bytes, location, flags, stream) "is an asynchronous stream-ordered API" whose migration "does not begin until all prior operations in the stream have completed" (guide 4.1.4.1), so prefetching chunk k+1 overlaps chunk k's kernel like a copy. Managed memory buys convenience, not speed; unprefetched, its faults show up as gaps on the timeline.

Depth: cudaMemAdvise hints

cudaMemAdvise adds hints: SetReadMostly (data "mostly going to be read from and only occasionally written to", so it can be replicated), SetPreferredLocation (encourages a location but "does not guarantee it"), SetAccessedBy (map it for a device without migrating) (guide 4.1.4.2).

Depth: the pipeline program, and why pinning a tensor to copy it once is slower

The program behind the chart, compiled here compiled here:

// s1_pipeline.cu: 256 MiB in 8 chunks on 3 non-blocking streams (error checks shortened)
cudaMallocHost(&h_in, N * sizeof(float));                 // pinned
for (int k = 0; k < NS; ++k)
  cudaStreamCreateWithPriority(&s[k], cudaStreamNonBlocking, k == 0 ? hi : lo);
for (int c = 0; c < CHUNKS; ++c) {
  cudaStream_t st = s[c % NS];  size_t off = (size_t)c * C;
  cudaMemcpyAsync(d_in + off, h_in + off, C * 4, cudaMemcpyHostToDevice, st);
  scale<<<(C + 255) / 256, 256, 0, st>>>(d_out + off, d_in + off, C, 2.0f);
  cudaMemcpyAsync(h_out + off, d_out + off, C * 4, cudaMemcpyDeviceToHost, st);
}
// s[0] waits on an event from each other stream, records t1, then: cudaEventSynchronize(t1)

Calling .pin_memory() on a tensor to copy it once is usually slower than a plain copy: the tutorial measured 0.4364 ms against 0.3704 ms ({{Moens, "A guide on good usage of non_blocking and pin_memory()", PyTorch tutorials, updated Apr 1 2026|https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html}}) published. Pinning pays when the buffer is reused, which is what the DataLoader's pinned buffers do.
