2. Copies: pinned memory and copy/compute overlap

The problem. Host memory is far away. A PCIe 5.0 x16 link moves about 63 GB/s each way (the figure {{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}} uses), while an H100 SXM reads its own HBM at 3.35 TB/s vendor spec, about 53 times faster derived: 3,350 / 63. A kernel that waits for its input to cross PCIe runs at PCIe speed. The fix is to move data while the GPU computes on something else.

Pinned memory first. The GPU's copy engines move data by DMA: they read physical pages directly, so those pages must not move or be swapped out while the copy runs. Ordinary (pageable) memory can be, so the driver first copies it into a pinned staging buffer, and the copy is not truly asynchronous. NVIDIA: "In order for memory copies involving CPU memory to be carried out asynchronously, the host buffers must be pinned and page-locked" (guide 2.5.2.3) vendor doc. Allocate pinned memory with cudaMallocHost (PyTorch: pin_memory=True in the DataLoader, or t.pin_memory()); do not pin everything, because pinned pages are taken away from the OS.

Copy engines. Copies are done by separate hardware units, not by the SMs, so a copy and a kernel can run at the same time; with two copy engines a host-to-device and a device-to-host copy can also overlap each other. cudaGetDeviceProperties reports how many as asyncEngineCount. With one engine, the two directions take turns.

The chunked pipeline

Cut the data into chunks and give each chunk its own sequence (copy in, kernel, copy out) on one of a few streams. While chunk 2 is copied in, chunk 1's kernel runs and chunk 0 is copied out. The program, compiled here compiled here:

// s1_pipeline.cu: 256 MiB in 8 chunks on 3 non-blocking streams (error checks shortened)
cudaMallocHost(&h_in, N * sizeof(float));                 // pinned
for (int k = 0; k < NS; ++k)
  cudaStreamCreateWithPriority(&s[k], cudaStreamNonBlocking, k == 0 ? hi : lo);
for (int c = 0; c < CHUNKS; ++c) {
  cudaStream_t st = s[c % NS];  size_t off = (size_t)c * C;
  cudaMemcpyAsync(d_in + off, h_in + off, C * 4, cudaMemcpyHostToDevice, st);
  scale<<<(C + 255) / 256, 256, 0, st>>>(d_out + off, d_in + off, C, 2.0f);
  cudaMemcpyAsync(h_out + off, d_out + off, C * 4, cudaMemcpyDeviceToHost, st);
}
// s[0] waits on an event from each other stream, records t1, then: cudaEventSynchronize(t1)

Model derived: 256 MiB at 63 GB/s each way = 4.26 ms per direction; the kernel reads and writes 256 MiB at 3.35 TB/s = 0.16 ms. Serial: 8.68 ms. Eight chunks with two engines: 4.81 ms; with one engine: 8.54 ms. Launch and per-copy latencies are ignored. Not run here: no GPU.

Read the chart before the numbers. The kernel was never the problem; the copies were. Pipelining hides the kernel under the copies (a saving of 0.16 ms) and, with two engines, the copy out under the copy in, which is where the factor of nearly two comes from. Overlap hides the smaller thing under the larger one. If the copies dominate, the real fixes are to copy less (keep data on the GPU, compress it, use lower precision) or to use a faster link.

In PyTorch, and when it matters for training

loader = DataLoader(ds, batch_size=16, pin_memory=True, num_workers=4)
for x, y in loader:
    x = x.to("cuda", non_blocking=True)   # returns at once; ordered before the forward on the stream
    y = y.to("cuda", non_blocking=True)
    loss = model(x, y)

Host-to-device with non_blocking=True is safe because later kernels on the same stream wait for the copy. The other direction is not: "attempting cuda_tensor.to("cpu", non_blocking=True).mean() will result in erroneous outputs", since the CPU reads the buffer before the copy lands; synchronise first. Calling .pin_memory() on a tensor just to copy it once is usually slower than a plain copy: the tutorial measured 0.4364 ms against 0.3704 ms ({{Moens, "A guide on good usage of non_blocking and pin_memory()", PyTorch tutorials, updated Apr 1 2026|https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html}}) published. Pinning pays when the buffer is reused, which is what the DataLoader's pinned buffers do.

For LLM pretraining the input copy is tiny. 16 sequences of 1,024 tokens as int64 ids, inputs plus targets, are 262,144 bytes, about 0.004 ms over PCIe derived, against tens of milliseconds of compute. Copy/compute overlap matters when the bytes are large next to the work: activations or optimizer state offloaded to the CPU (torch.autograd.graph.save_on_cpu(pin_memory=True), FSDP's CPU offload), inference that streams weights or KV cache from host memory, and image or video pipelines that decode on the CPU. In each case the same rule decides: if copying a layer's bytes takes longer than computing that layer, overlap cannot hide it.
