6. NCCL as an API, and how training hides communication

Data-parallel training averages gradients across GPUs every step with an all-reduce, which for a model of N parameters moves about 2N values per GPU. Across nodes it can cost as much as the backward pass. The idea of this section: start each piece of the all-reduce the moment its gradients exist, while backward is still computing the rest. Which collectives each parallelism needs is on {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}}; how NCCL schedules bytes over rings and trees is on {{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}} (its Collective simulator tab animates them). Here: what the programmer calls and what runs where.

The API in five calls

  1. One id for the group. Rank 0 calls ncclGetUniqueId, and the id is "broadcast to all participating threads and processes using any CPU communication system" (in PyTorch, the TCP store set up by init_process_group).
  2. A communicator per GPU. ncclCommInitRank(&comm, nranks, id, rank) on each, ranks 0 to n − 1; ncclCommInitAll when one process owns all the GPUs; ncclCommSplit to carve sub-groups (tensor-parallel and data-parallel groups) ({{NCCL user guide, communicators|https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/communicators.html}}).
  3. Collectives on a stream. ncclAllReduce(sendbuff, recvbuff, count, ncclBfloat16, ncclSum, comm, stream). "The NCCL call returns when the operation has been effectively enqueued to the given stream"; it runs asynchronously, and you wait with stream semantics, events or cudaStreamSynchronize ({{NCCL user guide, CUDA stream semantics|https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/streams.html}}) vendor doc.
  4. Groups. Calls between ncclGroupStart() and ncclGroupEnd() are "fused into a single NCCL operation"; one thread driving several GPUs must group, and grouping many small collectives saves launches. ncclGroupEnd "only guarantees that the operations are enqueued on the streams, not that the operation is effectively done" (nccl.h).
  5. Tear down with ncclCommDestroy, or ncclCommAbort when a peer is gone (section 7).
Two rules that cause most NCCL bugs
Same calls, same order, on every rank. A collective completes only when every rank has joined it; if rank 3 skips an all-reduce (an if on local data, an unused parameter, an exception caught on one rank), everyone else waits forever. NCCL collectives are kernels. They run on SMs, as thread blocks (CTAs), next to your kernels, and they need the other ranks' matching kernels to be running too.

Communication costs SMs. Because a collective is a kernel, it competes with compute for SMs and memory bandwidth. NCCL lets you bound it per communicator (maxCTAs, or CTAPolicy NCCL_CTA_POLICY_EFFICIENCY, the "minimal number of CTAs to achieve the decent performance", recommended for overlap). DeepSeek-V3's training gave communication 20 of the H800's 132 SMs and called that a cost: it "relies on expensive SMs ... which will limit the computational throughput" ({{DeepSeek-V3 report|https://arxiv.org/abs/2412.19437}}) published.

Depth: the NCCL 2.31.2 API surface, CTA controls, launch order across communicators

NCCL 2.31.2's header, as shipped in the CUDA 13.4.2 image, exports read here. Beyond the classic collectives it now has one-sided calls (ncclPutSignal, ncclSignal, ncclWaitSignal) on registered memory windows, which are section 8's territory.

With several communicators per GPU, "users must ensure the order of host-side launches matches for all devices"; before NCCL 2.26 that meant serialising all of them, and 2.26 added NCCL_LAUNCH_ORDER_IMPLICIT to follow host issue order (communicators page).

NCCL's communicator config, fields read from nccl.h (), lets you bound it: minCTAs "up to 32. The default value is 1", maxCTAs default 32; CTAPolicy NCCL_CTA_POLICY_EFFICIENCY uses the "minimal number of CTAs to achieve the decent performance", recommended for compute/communication overlap, and NCCL_CTA_POLICY_ZERO uses "zero CTA whenever it can" ({{NCCL API types|https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/api/types.html}}, {{flags|https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/api/flags.html}}, NCCL 2.32.3 docs) vendor doc. DeepSeek-V3's training gave communication 20 of the H800's 132 SMs and called that a cost: it "relies on expensive SMs ... which will limit the computational throughput" ({{DeepSeek-V3 report|https://arxiv.org/abs/2412.19437}}) published.

What PyTorch adds. DDP registers a hook on every parameter's gradient and launches a bucket's all-reduce when the bucket's last gradient arrives. Buckets follow the reverse order of model.parameters(), are rebuilt after the first iteration in the order gradients actually arrived, and default to 25 MiB, with a smaller first bucket of 1 MiB so the first all-reduce starts early (_DEFAULT_BUCKET_CAP_MB = 25, _DEFAULT_FIRST_BUCKET_BYTES = 1,048,576, PyTorch 2.14.1 source) read here. The NCCL calls run on a stream owned by the process group, ordered after the gradient kernels by events. dist.all_reduce(t, async_op=True) returns a work handle whose wait() makes the current stream wait without blocking the CPU. no_sync() skips the all-reduce during gradient accumulation; comm hooks (register_comm_hook) can compress buckets to BF16.

Overlap hides every bucket but the last

To scale. Lanes are streams on one GPU; every GPU runs the same timeline. The calculator below this section's measurement lets you change every input.

What the model says. Without overlap the step is 42.8 ms, of which 10.7 ms is all-reduce with the SMs idle. With overlap it is 36.5 ms, 15% less, and 4.4 ms of communication is still exposed. The reason is the last bucket: GPT-2 ties its token embedding to the output layer, and that 38.6 M-parameter matrix's gradient is complete only when backward reaches the embedding lookup at the very end, so the final bucket (97.7 MiB of 237.4) cannot start until backward is over. The copy lane is honest too: the batch is a hairline, because token ids are tiny (section 2).

Measured: DDP's buckets on real processes

The mechanism runs without GPUs: real DistributedDataParallel on two CPU processes with Gloo instead of NCCL, a 12-layer MLP of width 1,024 in 6 buckets of 8.01 MiB (bucket_cap_mb=8), PyTorch 2.14.1. A comm hook timestamps each bucket; "no overlap" is no_sync() followed by the same buckets all-reduced one by one measured on CPU:

Measured: buckets leave during backward, and backward itself slows down

One representative step of each mode (the median step of run 2). Medians over 3 runs of 5 steps: backward plus communication 64.6 ms overlapped against 96.1 ms serial (33% less); per-run 64.6, 61.5, 66.3 and 92.6, 96.1, 105.7 ms; load average 5 to 7.

Two things show. The overlap is real: buckets leave during backward, and only about 7.0 ms of communication remains after the compute ends, against 45.9 ms when nothing overlaps. And overlap is not free: backward's compute itself took 15% longer (57.6 against 50.2 ms) because the all-reduce threads compete for the same cores. On a GPU the competitors are SMs and memory bandwidth instead of CPU cores, the reason for NCCL's CTA limits above. What does not transfer: Gloo on loopback is not NCCL on NVLink, CPU threads are not SMs, and the times are milliseconds on a laptop. What does: the bucket order, the hand-over during backward, the exposed tail, and the slowdown from sharing hardware.

The DDP pattern, by hand

The program below does what PyTorch's DistributedDataParallel does: a compute stream runs backward, which fills gradient buckets from the last layer to the first; an event marks each bucket ready; a second, communication stream waits for that event only and all-reduces the bucket; the optimizer waits for the communication stream at the end compiled here (with -lnccl; the run prints NCCL's version code 23102, then stops at the first CUDA call).

// s4_nccl_overlap.cu (abridged; error checks removed)
ncclCommInitAll(comm.data(), nd, devs.data());
for (int b = B - 1; b >= 0; --b) {                       // backward: last layers first
  for (int d = 0; d < nd; ++d) {
    cudaSetDevice(d);
    fake_backward<<<n / 256, 256, 0, compute[d]>>>(grad[d] + b * n, n, 1.0f + d);
    cudaEventRecord(ready, compute[d]);
    cudaStreamWaitEvent(comms[d], ready, 0);              // wait for this bucket only
  }
  ncclGroupStart();
  for (int d = 0; d < nd; ++d)
    ncclAllReduce(grad[d] + b * n, grad[d] + b * n, n, ncclFloat, ncclAvg, comm[d], comms[d]);
  ncclGroupEnd();                                         // queued; backward keeps going
}
// each compute stream waits on an event from its comm stream, then the optimizer step

The formulas

  • Parameters: GPT-2 layout, vocabulary 50,257, context 1,024; per block 12d² + 13d (layer norms, attention, MLP with 4d); an untied output layer adds 50,257d.
  • Forward = 2N × tokens / (989.5 TFLOP/s × MFU), H100 SXM dense BF16 (vendor spec); backward = 2 × forward, split across layers in proportion to their matmul parameters; attention-score FLOPs ignored.
  • Gradient readiness: output layer first, then blocks from last to first; with tied weights the embedding's gradient is complete only at the end of backward.
  • Buckets: DDP's rule, reverse parameter order, close a bucket once it reaches the cap; BF16 gradients (2 bytes); first bucket 1 MiB (or the cap if smaller).
  • All-reduce of B bytes on n GPUs = B × 2(n − 1)/n / busbw + latency, one bucket at a time on the NCCL stream. Busbw presets: 92% of 50 GB/s (InfiniBand, the acceptance target quoted on Interconnects and scaling), 365.6 GB/s (8× H200 ring, nccl-tests at 8 GiB, measured by Bekman), 92% of 12.5 GB/s = 11.5 (100 Gb/s Ethernet, same efficiency assumed). The NVLink preset assumes all the GPUs share one NVLink domain (8 on an HGX board).
  • Optimizer = 32 bytes per parameter at 3.35 TB/s. Batch = tokens × 8 bytes × 2 (ids and targets) at 63 GB/s.
  • Slowdown: backward stretched by this percentage when overlapped, standing in for NCCL's use of SMs and memory bandwidth; the CPU measurement above found 15% with Gloo threads.

FSDP: the same idea in both directions

Fully sharded data parallelism must all-gather a layer's parameters before using them, forward and backward, and reduce-scatter its gradients afterwards; overlap again decides the cost. FSDP2: "In forward, all-gathers run on a separate CUDA stream, so the next module's all-gather can overlap with the current module's forward compute"; "in backward, FSDP2 additionally prefetches the next module's all-gather explicitly and runs reduce-scatters on a separate CUDA stream" ({{fully_shard docs, 2.14|https://docs.pytorch.org/docs/2.14/distributed.fsdp.fully_shard.html}}) vendor doc. Prefetching one layer ahead holds one extra layer of unsharded parameters: overlap is bought with memory.

Depth: FSDP2's prefetch and reshard knobs

set_modules_to_forward_prefetch issues all-gathers earlier when CPU overhead eats the natural lead; reshard_after_forward defaults to true for non-root modules (free after forward, gather again in backward) and false for the root (fully_shard docs, 2.14).

Tensor parallelism is the hard case. Its all-reduces sit between two matmuls that need the result, so there is nothing independent to hide them under, unless the matmul is cut into pieces that start as their slice of data arrives (Megatron's ordering trick in section 1, async TP in section 8). That is why tensor parallelism stays inside the fastest domain ({{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}} works the numbers).
