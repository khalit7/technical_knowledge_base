1. What happens when you call torch.softmax on a GPU tensor

Suppose s is an 8,192 by 8,192 matrix of float32 scores on the GPU (256 MiB) and you write p = torch.softmax(s, dim=-1). Four things happen, and only the last one runs on the GPU.

  1. Dispatch. Python calls into PyTorch's C++ core, where every operator is registered once and implemented per device. The registry, native_functions.yaml, says _softmax.out goes to softmax_cpu_out on CPU, softmax_mps_out on a Mac and softmax_cuda_out on an NVIDIA GPU. The dispatcher reads the tensor's device and picks the CUDA one.
  2. Choose a kernel and its shape. A kernel is a function that runs on the GPU, executed by many threads at once. PyTorch's SoftMax.cu picks among several hand-written softmax kernels by row length: rows of at most 2,048 elements (and 8 KB) go to a kernel where one warp of 32 threads owns a row; longer rows like ours get one thread block per row (8,192 blocks), with the row kept in registers when it fits. read from PyTorch main, 2026-10-05
  3. Launch. The host (CPU) code puts "run this kernel with this many blocks of this many threads, with these pointers" into a stream, a queue of GPU work, and returns immediately. Python moves on to the next line while the GPU is still working. This is why GPU code is asynchronous, and why a Python timer around a GPU call measures almost nothing (section 9).
  4. Execute. The GPU's scheduler hands blocks to its streaming multiprocessors (SMs; an H100 SXM has 132 vendor spec), and each block reads its row from memory, finds the maximum, sums the exponentials and writes the normalised row back. The CPU waits only when it needs a value (p.item(), print(p), .cpu()): that wait is a synchronisation.

Which code runs depends on the operator. torch.matmul calls NVIDIA's closed-source cuBLAS or cuBLASLt (PyTorch's preferred_blas_library switch picks between them by heuristics by default). F.scaled_dot_product_attention picks among FlashAttention, memory-efficient attention, cuDNN attention and a plain C++ "math" fallback (the SDPBackend list). Softmax uses PyTorch's own kernels. And under torch.compile, none of these hand-written kernels may run at all: the compiler, TorchInductor, "translates PyTorch programs into OpenAI's Triton for GPUs and C++/OpenMP for CPUs" (PyTorch 2 paper, ASPLOS 2024), generating a new kernel that can fuse the softmax with the operations around it.

Overhead. Each launch costs CPU time before the GPU starts. NVIDIA measured a 2.9 µs kernel taking 9.6 µs per kernel when the CPU waited after each launch, and 3.4 µs per kernel with CUDA Graphs, which record a sequence of launches once and replay it with one CPU call (NVIDIA blog, 2019, V100) published. On the M1 Pro, one tiny MLX operation launched and waited for took about 235 µs (median of 3 runs: 674, 197, 235), which includes MLX's own bookkeeping and Metal's command buffers, so it is not comparable to a bare CUDA launch. The lesson transfers: when kernels are small, the GPU idles between them, and the fix is fewer, larger kernels or graphs. Horace He's "Making Deep Learning Go Brrrr" names the three regimes every slow operation falls into: compute-bound, memory-bound or overhead-bound.

2. The programming model: grid, blocks, warps, threads

The problem. A GPU has tens of thousands of arithmetic lanes and wants hundreds of thousands of independent pieces of work in flight. You cannot write a hundred thousand programs, so you write one function, the kernel, and launch it on many threads; each thread works out from its own index which piece of data is its job. That is the whole idea, and CUDA's four nested words describe how the threads are grouped.

ThreadOne execution of the kernel, with its own private registers (the fastest storage there is). You launch millions.
Warp32 consecutive threads that the hardware runs together, one instruction at a time for all 32. Not part of the language, but the unit everything performs in.
BlockUp to 1,024 threads that run on one SM and stay there. They share a small fast scratchpad, shared memory, and can wait for each other with __syncthreads(). Blocks must not depend on each other: the GPU runs them in any order on any SM, which is why the same program runs on a GPU with 20 SMs or 170.
GridAll the blocks of one launch. There is no cheap way for blocks to wait for each other inside a kernel; the end of the kernel is the global barrier. Since Hopper (compute capability 9.0) an optional cluster sits between block and grid: a few blocks on neighbouring SMs that can read each other's shared memory.

Limits from the CUDA C++ Programming Guide, compute capabilities (v13.4.2) vendor spec: warp size 32; at most 1,024 threads per block; per SM at most 64 resident warps on sm_80, sm_90 and sm_100 and 48 on consumer sm_86, sm_89 and sm_120; 65,536 32-bit registers per SM, at most 255 per thread.

A first kernel

Vector addition: thread i adds element i. This is the exact source the Compiler explorer compiles for four GPU generations; ptxas reports it uses 12 registers per thread on sm_90a compiled here.

extern "C" __global__ void vadd(const float* a, const float* b, float* c, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;  // this thread's global index
  if (i < n)                                       // the last block may run past n
    c[i] = a[i] + b[i];                            // two loads, one add, one store
}
// host side: enough blocks of 256 threads to cover n (ceiling division)
int block = 256, grid = (n + block - 1) / block;
vadd<<<grid, block>>>(d_a, d_b, d_c, n);   // asynchronous: returns at once

__global__ marks a kernel (runs on the GPU, launched from the CPU); blockIdx, blockDim and threadIdx are built-in variables each thread reads to learn who it is. Move the sliders to see how a launch carves up the work.

SIMT: one instruction, 32 threads, and what a branch costs

NVIDIA calls the model SIMT, single instruction, multiple threads. You write scalar code for one thread; the hardware issues each instruction once for a whole warp and the 32 lanes execute it on their own data. It is SIMD (the CPU's vector instructions, Part 2 of the C++ page) without having to write the vectors. The catch is the branch. If the 32 threads of a warp disagree on an if, the warp runs both paths one after the other, with the lanes that did not take the current path switched off (masked). This is warp divergence. Since Volta (sm_70) each thread has its own program counter ("independent thread scheduling", Programming Guide), which makes divergent code correct in more cases, but the two paths still take turns.

float v = x[i];
if (v > 0.f) { v = expf(v); v = v * w; v = v + b; v = sqrtf(v); }   // path A: 4 steps
else         { v = 0.01f * v; v = v * w; v = v - b; v = fabsf(v); } // path B: 4 steps
y[i] = v;

Predict: on the M1 Pro GPU, a kernel with two equally heavy branches is run once with every 32-thread group agreeing, once with alternate lanes taking alternate branches. How much slower is the divergent run?
measured on Apple M1 Pro GPU 1.86 times (2.82 ms against 1.52 ms, median of 3 runs, in the GPU simulator). Both paths are executed, so the cost is the sum of the two paths instead of one; with two equal paths, close to 2. It is not 32: the lanes are masked, not serialised one by one. Apple's SIMD-groups are 32 wide like NVIDIA's warps, so this transfers directly; the cost on NVIDIA is the same in kind.

When it matters for training: rarely in matmuls and normalisations, whose threads all do the same thing; often in code with data-dependent branches (masking, sparse or ragged inputs, MoE routing, sampling). A branch that is the same for a whole warp (if (blockIdx.x == 0), or a bounds check that only fails in the last warp) costs nothing. How to check: Nsight Compute reports average active threads per instruction (32 means no divergence; section 9).

Latency hiding: why a GPU wants so many threads

A read from GPU memory takes hundreds of clock cycles. A CPU core hides that with large caches and by guessing ahead; a GPU hides it by switching warps. Every resident warp keeps its registers on the SM permanently, so when one warp waits for memory the scheduler issues an instruction from another, at no cost. The more warps are ready, the more of the waiting is covered. measured on Apple M1 Pro GPU in the GPU simulator: streaming the same array with 256 threads in flight reached 11 GB/s; with 8,192 or more, 138 to 151 GB/s, the memory's limit. "Not enough parallelism" is a first-order failure: a kernel launched with fewer blocks than the GPU has SMs leaves most of the chip idle.

Occupancy is the number of warps resident on an SM divided by the maximum (64 on an H100). It is limited by whichever resource runs out first: registers per thread, shared memory per block, threads per block, or the cap on blocks per SM. It is a means, not a goal: memory-bound kernels want it high, while fast matmul and attention kernels deliberately run at low occupancy because more registers per thread buy more data reuse than more warps buy latency hiding. The Compiler explorer turns real ptxas register reports into occupancy with a calculator that agrees with NVIDIA's own cuda_occupancy.h on all 1,988 tested cases.

Streams, briefly: work in one stream runs in order; work in different streams may overlap (a copy with a kernel, or NCCL's communication with backward compute, which is how data-parallel training hides its all-reduce). Events order streams against each other and time the GPU from the GPU's side.

3. The memory hierarchy, as the programmer sees it

The problem. An H100 SXM can do 989.5 trillion BF16 floating-point operations per second on its tensor cores (dense) but fetch only 3.35 TB per second from its memory vendor spec, so it can do about 295 operations for every byte it reads derived: 989.5e12 / 3.35e12. A float32 softmax does about five operations per element, which is under one per byte moved derived: 5 / 8 bytes read and written. Almost every kernel would starve if each operand came from main memory, so the chip has a ladder of smaller, faster memories, and much of kernel writing is deciding which rung each piece of data lives on.

Coalescing: 32 addresses become memory transactions

When a warp executes a load, its 32 addresses are gathered into as few 32-byte sectors as possible (CUDA Best Practices Guide, coalesced access). If thread k reads float k, the warp needs 128 contiguous bytes, four sectors, and every byte fetched is used: the access is coalesced. If thread k reads float 32k, every thread's 4 bytes sit in a different sector and the warp moves 1,024 bytes to use 128. The rule that follows: make threadIdx.x walk along the contiguous dimension of the array (for a row-major matrix, along a row).

The same effect inside a real kernel: in the Kernel lab, a naive 2,048 matmul whose threads walk down columns took 229 ms on the M1 Pro; swapping which index follows the thread index (nothing else) brought it to 47.5 ms, 4.8 times faster measured on Apple M1 Pro GPU.

Shared memory: a scratchpad you fill yourself

Shared memory is on-chip SRAM inside the SM, visible to all threads of one block. The pattern is always the same: threads cooperatively copy a tile from global memory into a __shared__ array (each thread one or a few elements, coalesced), wait at __syncthreads(), then all read the tile many times at on-chip speed. It is divided into 32 banks of 4 bytes; if two threads of a warp hit different addresses in the same bank, their accesses take turns (a bank conflict). The classic case is reading a column of a float tile[32][32]: all 32 threads land in the same bank. The classic fix is one padding column, tile[32][33]. measured on Apple M1 Pro GPU: threadgroup-memory reads with a lane stride of 32 ran at 113 billion reads per second against 318 at stride 1 and 394 at stride 33, the same signature (Apple does not document its banks; the GPU simulator shows the measurement and NVIDIA's rule side by side).

Here is the reason shared memory exists, on the operation every model spends most of its time in. One block computes a tile of C = A × B. Without shared memory, every thread fetches its own row of A and column of B from global memory, so each element is fetched once per thread that needs it. With shared memory, the block fetches each element once per tile and every thread reuses it.

One block of 4 × 4 threads computes a 4 × 4 tile of C with K = 8, in two phases of 4. The number in each cell of A and B is how many times it has been fetched from global memory so far. illustrative sizes

The saving is a factor of the tile width T: global loads per block fall from 2T²K to 2TK derived. measured on Apple M1 Pro GPU: a 2,048 float32 matmul ran at 353 GFLOP/s without tiles and 677 GFLOP/s with 8 × 8 threadgroup tiles, but only 478 with 32 × 32 tiles: a bigger tile needs more threads and memory per block, fewer blocks fit at once, and latency hiding suffers. Bigger is not automatically better, which is why tile sizes are tuned per GPU (section 4).

Registers and spills

Registers are the fastest storage and the scarcest: 65,536 per SM shared by every resident thread. A kernel that needs more than 255 per thread, or more than the compiler is allowed to use, spills: values go to "local memory", which despite the name lives in global memory behind the caches. compiled here: in the Compiler explorer's register-pressure ladder, the largest kernel hits the 255-register ceiling and ptxas -v reports 1760 bytes spill stores, 1184 bytes spill loads on sm_90a. Spills are invisible in the source; check them in the compiler's report or Nsight Compute.

4. Writing kernels: the optimisation ladders for softmax and matmul

Kernel optimisation is a ladder: write the obvious version, find out what limits it, remove that limit, and repeat until the limit is the hardware's. Two ladders teach almost everything, one memory-bound and one compute-bound.

Softmax: count the passes over memory

Softmax of a row is exp(x - max) / sum(exp(x - max)); subtracting the maximum keeps exp from overflowing (why, in floating point: Numerical computing for ML). Arithmetic is trivial, so time is set by how many times the matrix crosses the memory bus. Each rung removes passes:

The rung that matters most is the third, the online softmax of Milakov and Gimelshein (NVIDIA, 2018): keep a running maximum m and a running sum d, and when a new element raises the maximum, rescale the sum you already have.

That property is the load-bearing idea inside FlashAttention (section 5). measured on Apple M1 Pro GPU: MLX's softmax ran at 166 GB/s counted as two passes, the speed of a plain copy, so it is on the top rung. A row reduction itself (the max, the sum) is done inside a warp with shuffles, instructions that pass a register value directly between lanes: five steps of __shfl_down_sync (offsets 16, 8, 4, 2, 1) sum 32 values with no shared memory; then one value per warp goes through shared memory to finish the block. In production code you call CUB's BlockReduce instead of writing it.

5. Fusion and FlashAttention: why bytes moved decide

The idea. When several operations run as separate kernels, each one writes its result to HBM and the next reads it back. Fusion runs them in one kernel so the intermediate stays in registers or shared memory and never touches HBM. For memory-bound operations (anything elementwise, normalisations, softmax) this is nearly the whole game: k fused memory-bound operations cost close to one. The softmax-then-matmul pair at the heart of attention is the example that changed the field.

Standard attention computes S = QKT (an N × N matrix of scores for a sequence of N tokens), P = softmax(S) and O = PV, and the two N × N matrices are far larger than the inputs: with head size d = 128, S is N / 128 times the size of Q. FlashAttention (Dao et al., 2022) never forms them in memory. It loads a block of Q rows on chip, streams blocks of K and V past it, computes each block of scores on chip, and folds it into the output with the online-softmax rescaling of section 4. The paper proves it needs Θ(N²d² / M) HBM accesses for on-chip memory of size M, against Θ(N d + N²) for standard attention, and reported 15% end-to-end speedup on BERT-large, 3 times on GPT-2 at 1K tokens and 2.4 times on Long Range Arena published.

Bars in HBM are drawn to scale in bytes (BF16, 2 bytes). Traffic counts each tensor read or written once per kernel; the fused count is the ideal (in FlashAttention each block of Q re-reads K and V, which for one head is a few MB and is mostly served from the 50 MB L2). Times at H100 SXM rates: memory = bytes / 3.35 TB/s, compute = 4N²d × heads / 989.5 TFLOP/s derived; the slower of the two bounds the kernel.

Why only about 1.3 to 1.4 times here, when the byte count falls by far more? Because on this laptop the unfused version is roughly balanced: at N = 4,096 it moves 1.09 GB, 6.6 ms at 165 GB/s, against 6.9 ms of arithmetic at the M1 Pro's 5 TFLOP/s derived. Its ridge point (peak operations per byte of bandwidth) is about 30; an H100's is about 295, so the same unfused attention there spends 4.8 times longer moving bytes than computing (the default above), and fusion pays far more. What transfers: the byte arithmetic. What does not: the size of the win, which grows with the chip's ratio of compute to bandwidth, and that ratio has grown every generation.

The lineage is the same three ideas (tile, online softmax, recompute in the backward pass instead of storing P) re-expressed for each generation's data-movement hardware: FlashAttention-2 (better work partitioning; Ampere, Ada, Hopper), FlashAttention-3 (Hopper: wgmma, TMA, FP8), and FlashAttention-4, "written in CuTeDSL and optimized for Hopper and Blackwell GPUs" (flash-attention README, read 2026-10-05). On recent PyTorch, F.scaled_dot_product_attention picks one of these backends for you (section 1).

When fusion does not help: fusing two compute-bound matmuls rarely pays (the tensor cores are already busy and register pressure rises); and torch.compile already fuses elementwise chains and matmul epilogues, so measure against a compiled baseline, not eager. The far end of fusion is the megakernel: a whole decode step in one persistent kernel, attacking launch and scheduling overhead rather than bytes. Cohere's (September 8, 2026) reports 292 tokens per second at batch size 1 for a 30B mixture-of-experts model with 3.3B active parameters on a single H100, 62% of speed-of-light and 1.58 times vLLM, holding to 256K context (Cohere blog) published, vendor's own measurement.

6. Triton: blocks, not threads

The idea. In CUDA you write what one thread does and arrange the cooperation yourself: which thread loads what, when to synchronise, how to lay out shared memory. In Triton (OpenAI's Python language for kernels, Tillet, Kung and Cox, MAPL 2019) you write what one program instance does to whole blocks of values, roughly what one CUDA thread block does, and the compiler decides how threads, warps, shared memory, vector loads and synchronisation implement it. def softmax(x_ptr, y_ptr, ncols, stride, BLOCK: tl.constexpr):

The translations to remember: tl.program_id replaces blockIdx; tl.arange plus pointer arithmetic plus mask= replace per-thread indexing and bounds checks; tl.load and tl.store move whole blocks (contiguous offsets make them coalesced for free); tl.max and tl.sum emit the shuffles you wrote by hand; tl.dot is a block matrix multiply that the compiler maps to tensor cores; @triton.autotune searches block sizes, num_warps and num_stages (how many tiles to prefetch) per shape. compiled here: one Triton matmul source compiled without a GPU picks a different tensor-core instruction for each target, HMMA on sm_80 and sm_120, HGMMA (wgmma) on sm_90a and UTCHMMA (tcgen05) on sm_100a; a float32 tl.dot defaults to TF32 tensor cores; a tutorial-style matmul copies tiles with cp.async, not TMA.

What you give up: warp-level control, explicit shared-memory layouts, hand-scheduled asynchronous copies and power-of-two block shapes only. When to use which: torch.compile first (it already writes Triton for you); hand-written Triton for an algorithm the compiler cannot express or schedule well (attention variants, quantised or mixed-format matmuls, fused MoE routing); CUDA C++ or CUTLASS for the last stretch of performance or features Triton does not expose. 8. The compiler: CUDA C++ to PTX to SASS

Two instruction sets. PTX is NVIDIA's virtual instruction set: a readable, stable text format that does not belong to any one chip. SASS is the real machine code of one architecture, and it changes every generation. nvcc compiles the GPU part of a .cu file to PTX, then the assembler ptxas turns PTX into SASS for each target you name (-arch=sm_90a), and both are packed into a fat binary inside your executable or library. If a binary carries PTX but no SASS for the GPU it lands on, the driver compiles the PTX just in time, which is how old binaries run on new GPUs. NVRTC does the C++-to-PTX step at run time from a string, for code generated on the fly.

Reading SASS is a practical skill, not a party trick: it is where you confirm that a load is vectorised (LDG.E.128), that shared memory is used (LDS, STS), that tensor cores are used (HMMA, HGMMA, UTCHMMA), and that nothing spills (STL, LDL). The compiler's resource report, nvcc -Xptxas -v, gives registers, shared memory and spill bytes per kernel; those numbers set occupancy (section 2).

Targets. Each GPU generation has a compute capability: 8.0 for A100, 9.0 for H100, 10.0 for B200, 12.0 for the RTX 5090. Build for the one you run on (-arch=sm_120, or -arch=native); sm_100 and sm_120 need CUDA 12.8 or newer (CUDA 12.8 release notes: "adds compiler support for ... SM_100, SM_101, SM_120"). The current toolkit is CUDA 13.4.2 checked 2026-10-05; the old page's "13.3 latest, 13.4 in preview" is out of date.

torch.compile, all the way down

torch.compile(model) runs a different chain: TorchDynamo captures the Python as a graph; AOTAutograd derives the backward graph; TorchInductor fuses and schedules, and writes Triton source for each fused group (matmuls go to cuBLAS or to Triton templates, chosen by autotuning); Triton lowers its source through its own intermediate forms to LLVM and PTX; ptxas produces SASS. Everything is cached, so only the first call per shape pays. The PyTorch 2 paper reports 2.27 times inference and 1.41 times training speedup (geometric mean) on an A100 over 180+ models (Ansel et al., ASPLOS 2024) published. 9. Profiling, benchmarking honestly, and checking correctness

No NVIDIA profiler was run for this page (there is no NVIDIA GPU); this section is from NVIDIA's documentation, with the M1 measurements as worked examples of the timing rules.

Two microscopes. Nsight Systems (nsys) records a timeline of the whole program: CPU threads, CUDA API calls, kernel launches, copies, NCCL, and your own NVTX ranges. It answers "where does the wall-clock time go?": gaps between kernels (the CPU or the launches are the bottleneck), communication that fails to overlap compute, a data loader that stalls. It is cheap, so always start there. Nsight Compute (ncu) zooms into one kernel: it replays the kernel many times to read hardware counters, so it is slow and changes timing, and you point it only at kernels the timeline already convicted. It answers "why is this kernel slow?". torch.profiler sits in between ("which PyTorch op is slow"), built like both on CUPTI, NVIDIA's profiling library. compute-sanitizer checks memory errors and races; run it before trusting a new kernel.

Read Nsight Compute top-down. Its "Speed of Light" section gives compute and memory throughput as percentages of peak, which places the kernel on the roofline immediately: memory high and compute low means memory-bound (move fewer bytes, fuse); compute high means compute-bound (use tensor cores, lower precision); both low means latency-bound (too few warps, divergence, a tail of idle SMs, or the kernel is tiny). Correction to the old page
The old page said ncu locks clocks to base by default. The current Nsight Compute CLI documentation (v2026.3.1) lists --clock-control default boost (base, force-boost and none are options), and --cache-control default all (caches flushed between replays). Check the version you run.

Benchmarking honestly

  1. Synchronise. Launches are asynchronous, so a Python timer around a launch measures the launch. Use CUDA events (start.record(); f(); end.record(); torch.cuda.synchronize()), or synchronise before reading the clock when you want launch overhead included.
  2. Warm up. First calls pay compilation, autotuning, library heuristics and cold caches. Then time many repetitions and report a median with the spread, not the minimum of one run.
  3. Mind the cache. Timing the same small tensor in a loop measures L2 (50 MB on an H100, 96 MB on an RTX 5090), not HBM. Triton's triton.testing.do_bench clears the L2 before each timed run and returns the mean by default (return_mode="median" or quantiles= for more); it has no flush_l2 argument, contrary to the old page (testing.py, read 2026-10-05).
  4. Fix the clocks and the load. GPUs boost and throttle; lock clocks (nvidia-smi -lgc) or say you did not. On a shared machine, record the load.
  5. Compare fairly. Against torch.compile, not eager; against cuBLAS with the right epilogue and data type. Report achieved GB/s or TFLOP/s beside the roofline limit, so a speedup can be judged.
  6. Write down the environment: GPU, driver, CUDA, PyTorch and Triton versions, clocks.

Interview questions, with short answers

What is a warp, and why does it matter for performance?
32 threads that execute one instruction at a time together. Branch divergence, memory coalescing and shuffles are all defined per warp; a warp is the unit the scheduler switches between to hide latency.
Why is softmax memory-bound and matmul compute-bound?
Softmax does a handful of operations per element read, under one per byte, far below the roughly 295 operations per byte an H100 needs to be compute-bound. An N × N matmul does 2N³ operations on 3N² values, so its intensity grows with N, provided tiling keeps the reuse on chip.
What does shared memory buy you in a matmul?
Each tile of A and B is fetched from global memory once and reused by every thread in the block, cutting global traffic by the tile width; register tiling repeats the trick one level down.
Explain FlashAttention in three sentences.
Standard attention writes the N × N score and probability matrices to HBM. FlashAttention tiles Q, K and V so each block of scores is computed and consumed on chip, using the online-softmax rescaling to combine blocks, and recomputes scores in the backward pass instead of storing them. It does the same FLOPs with far fewer HBM bytes and O(N) extra memory.
High occupancy is good, right?
Only as a means. It helps memory-bound kernels hide latency; fast matmul and attention kernels run at low occupancy on purpose because registers per thread buy reuse. Measure achieved bandwidth or FLOPs, not occupancy.
Your custom kernel is 2 times faster than PyTorch. What do you check before believing it?
Correctness against a reference at several sizes; synchronisation and warmup in the timing; L2 effects (data larger than the cache, or flushed); the baseline (compiled, right dtype and layout); clocks and load; spread over repeated runs.
What is the difference between PTX and SASS?
PTX is a stable virtual instruction set; SASS is the real machine code of one GPU generation, produced from PTX by ptxas (or by the driver at load time). You read SASS to see what really runs: vector loads, tensor-core instructions, spills.
Why does a Hopper kernel not run on an RTX 5090?
sm_120 has TMA and clusters but not wgmma, tcgen05 or TMEM; a Hopper kernel built on wgmma will not even assemble for it. Consumer Blackwell kernels look like Ampere ones (mma.sync, register accumulators) plus TMA.
Nsight Systems or Nsight Compute first?
Systems: it shows where the time goes across the whole program (gaps, overlap, launch overhead) at little cost. Then Compute on the kernels the timeline convicts, to see why each is slow.
When would you write Triton, CUDA, or neither?
Neither if torch.compile or a library already does it. Triton for a new fusion or algorithm. CUDA or CUTLASS when you need control Triton hides (warp specialisation, exotic layouts) or the last few percent on a kernel that dominates the profile.

1. A warp runs one instruction at a time: divergence

The problem. You write a kernel as if each thread were on its own, with ordinary if statements. But the hardware fetches and issues one instruction for a whole warp of 32 threads. When the threads of one warp disagree about a branch, the warp cannot go both ways at once: in NVIDIA's words, "the warp executes each branch path taken, disabling threads that are not on that path" (CUDA Programming Guide 3.2.2.1, SIMT execution model). The disabled lanes sit idle. Different warps never slow each other this way: "branch divergence occurs only within a warp".

  • Transfers: both GPUs run 32 lanes from one instruction stream and serialise the two sides of a branch that splits a group of 32. The measured slowdown matches the simulator's prediction for this code shape.
  • NVIDIA detail since Volta (compute capability 7.0): each thread has its own program counter ("independent thread scheduling"), so divergent paths can interleave and threads of a warp can wait on each other without deadlock. A warp still issues one path at a time, so the cost above is unchanged; what changed is that code may no longer assume the 32 lanes move in lockstep, and must use __syncwarp() or the *_sync warp intrinsics (Programming Guide 3.2.2.1.1).
  • Short branches are often compiled into predicated instructions (both sides run, each lane keeps its own result), which avoids a jump but still pays for both sides. Look for it in the Compiler explorer's SASS.

When it matters for training, and how to check

Dense matmuls and elementwise kernels have no data-dependent branches, so divergence rarely matters there. It does in masked attention, variable-length (packed) sequences, mixture-of-experts routing and sampling. The fix is to make the decision per warp or per block instead of per thread. FlashAttention-2 does exactly this for the causal mask: it skips whole blocks that are fully masked, "approximately half of the blocks for large sequence length", for a 1.7 to 1.8x speedup, and applies the per-element mask only on the diagonal blocks (Dao, 2023, section 3.1.1).

Check in Nsight Compute: the Source Counters section reports branch efficiency per line; derived__avg_thread_executed (thread instructions per warp instruction) is 32 when no lane is ever idle (Nsight Compute Profiling Guide, last updated 2026-08-27).

2. Thirty-two addresses become memory traffic: coalescing

The problem. When a warp executes a load, its 32 lanes each ask for one address. Memory is not delivered address by address: "global memory is accessed via 32-byte memory transactions", and the warp combines (coalesces) its 32 requests into as few 32-byte pieces, called sectors, as it can (Programming Guide 2.3.4.1). Four sectors make a 128-byte cache line. If neighbouring lanes read neighbouring 4-byte words, 32 lanes need 128 bytes, exactly 4 sectors: 100% of what moves is used. If they read words 32 bytes or more apart, every lane needs its own sector: 1,024 bytes move to deliver 128, which the guide calls "12.5%" utilisation.

A coloured word was requested by a lane (hover or tap for its lane number); every sector that holds at least one requested word is shaded and moves in full. Only lines the warp touches are drawn.

What transfers, what does not

  • Transfers: neighbouring threads should touch neighbouring addresses. On both GPUs a stride costs bandwidth and a random gather is the worst case.
  • Does not transfer: the exact curve. NVIDIA documents 32-byte sectors, so the simulator's efficiency stops falling at a stride of 32 bytes (8 floats): beyond that each lane already has its own sector. When it matters for training, and how to check

Every elementwise, normalisation, activation, optimizer and softmax kernel is limited by memory bandwidth, so wasted sectors are wasted time. It shows up as layout: a transposed or sliced tensor whose last dimension is not contiguous (PyTorch's .is_contiguous() is False and a kernel may copy it first), channels-first against channels-last convolutions, or a hand-written kernel whose thread index walks the slow dimension.

The simulator's "sectors" card is that number for one request.

3. Shared memory has 32 banks: bank conflicts

The problem. Shared memory is fast because it is split into 32 independent banks that work in parallel: "successive 32-bit words map to successive banks", and "each bank has a bandwidth of 32 bits per clock cycle" (Programming Guide 2.3.4.2). Word w lives in bank w mod 32. If the 32 lanes of a warp hit 32 different banks, the access takes one pass. If several lanes want different words in the same bank, that bank serves them one after another: an n-way bank conflict takes n passes (Nsight Compute calls each pass a wavefront). Lanes that want the same word share one read, a broadcast, at no cost.

The classic case is the transposed read in section 2: a float tile[32][32] read down a column. Row r starts at word 32r, so element (r, 0) is in bank 32r mod 32 = 0 for every r: all 32 lanes queue on bank 0. The guide's fix is one spare column, float tile[32][33]: row r now starts at word 33r, bank r, and the column spreads over all 32 banks (2.3.4.2.2). Libraries prefer a swizzle: store element (r, c) at column c XOR r, which spreads a column over the banks without wasting memory or breaking the alignment that vector and TMA loads need; Hopper's TMA can write tiles into shared memory already swizzled ("Swizzling can be used to avoid shared memory bank conflicts", Programming Guide, asynchronous copies).

Right: the 32 banks; each box is one distinct word some lane asked for, labelled with the lane. Each step is one wavefront: every bank serves the box at the bottom of its stack.

Predict first. A warp reads float words with a stride of 2 (lane l reads word 2l). Conflict or not? And with a stride of 3?
Stride 2: lanes l and l + 16 land in the same bank (2l and 2l + 32), a 2-way conflict, two wavefronts. Stride 3: 3 shares no factor with 32, so the 32 lanes hit 32 different banks, no conflict. Both are the guide's Figure 15. In general a stride s gives a conflict of degree gcd(s, 32): any odd stride is free, a stride of 32 is the worst.

  • Transfers: the M1's threadgroup memory slows down for exactly the strides that are bad on NVIDIA (16, 32 and 64 words) and is fast for 33, which is what a banked memory with 32 four-byte banks would do. Apple does not document its bank count, so this is an inference from the measurement, not a specification.
  • Transfers too: a bank conflict only costs time when shared memory is the bottleneck. In the transpose of section 2 the M1 was limited by DRAM, and padding changed nothing measurable.
  • NVIDIA detail the simulator leaves out: 64-bit and 128-bit accesses are split into several passes by design, so their rules differ from the 32-bit picture here; the simulator models 32-bit words only.

When it matters for training, and how to check

Every fast matmul and attention kernel stages tiles in shared memory and reads them in a different order than it wrote them (rows in, columns out, or the fragment layouts tensor cores want). That is why CUTLASS, Triton and FlashAttention all choose swizzled shared-memory layouts; Triton picks one for you, which is part of why a Triton matmul is fast without you thinking about banks.

Check in Nsight Compute: l1tex__data_bank_conflicts_pipe_lsu counts conflicts, and the Memory Workload Analysis table shows shared-memory wavefronts against the ideal (Profiling Guide).

4. How many warps fit on an SM: occupancy

The problem. An SM runs many warps at once so that while some wait for memory, others compute (section 5 shows why that matters). How many fit is decided when the block is placed: every warp gets its registers and every block its shared memory for its whole life, out of fixed per-SM budgets. Occupancy is the number of resident warps divided by the maximum the SM can hold. Four limits apply, and the smallest wins:

  • Registers: 65,536 32-bit registers per SM on every current GPU; a warp needs registers per thread x 32, rounded up to a multiple of 256, taken from one of the SM's 4 sub-partitions.
  • Shared memory: per block, plus 1 KB the system reserves per block, rounded up to 128 bytes, out of 100 to 228 KB per SM depending on the GPU.
  • Warp slots: 48 or 64 warps per SM.
  • Block slots: 16, 24 or 32 blocks per SM (and on some GPUs, barriers per block slot).

Per-SM limits: CUDA Programming Guide, Compute Capabilities, Tables 30 and 31 (last updated 2026-09-10). Allocation rules: NVIDIA's occupancy calculator header cuda_occupancy.h, CUDA 13.4.2, which this calculator ports line by line.

5. Warps in flight hide memory latency

The problem. A load from DRAM takes hundreds of cycles to come back. Microbenchmarks measured average global-memory latencies of 466 cycles on an A100, 479 on an H800 (a Hopper H100 variant) and 542 on an RTX 4090, against about 29 to 30 cycles for shared memory and 262 to 273 for the L2 cache (Luo et al., 2024, Table IV; independent measurements, not NVIDIA figures). A GPU does not hide this with big caches or out-of-order execution like a CPU. It hides it with other warps: each SM sub-partition has a warp scheduler that, every cycle, picks one warp whose next instruction is ready and issues it. Nsight Compute's words: active warps that are not stalled are eligible; the scheduler issues from one of them; "on cycles with no eligible warp, the issue slot is skipped" (Profiling Guide, Scheduler Statistics).

The model. One scheduler, W warps, each running the same loop: issue k independent loads, wait L cycles for them, then k x c instructions that use the data. The scheduler issues one instruction per cycle and keeps issuing from the same warp until it stalls, then switches to the warp that has been ready longest ("greedy then oldest"). Little's law gives the answer the simulation lands on: the scheduler is kept busy when W x k(c + 1) ≥ k(c + 1) + L, so utilisation = min(1, W·k(c+1) / (k(c+1) + L)).

What transfers, what does not

  • Does not transfer: the numbers.   • Left out of the model: arithmetic latency (a dependent instruction also waits a few cycles), dual issue, memory bandwidth limits and bank or sector effects. It isolates the one idea.

When it matters for training, and how to check

It explains why small kernels are slow: a softmax over a few rows, a decode step at batch 1, or a launch with fewer blocks than the GPU has SMs leaves schedulers idle. It is the reason behind "fuse small kernels", CUDA graphs, and split-K or persistent kernels that keep every SM busy. The Kernel lab shows it on real softmax and attention kernels.

6. Tiles turn a memory-bound matmul into a compute-bound one

The problem. A naive matmul has each thread compute one output C[i][j] by reading a whole row of A and column of B from global memory: 2 loads per multiply-add, 8 bytes for 2 floating-point operations in fp32, an arithmetic intensity of 0.25 FLOP per byte if nothing were cached. Every modern GPU can do far more arithmetic per byte than that, so the naive kernel waits on memory. The fix is reuse: a block computes a BM x BN tile of C; at each step it loads a BM x BK slice of A and a BK x BN slice of B into shared memory once, and every thread reuses those values from there. Each element of A is now loaded once per BN columns of output instead of once per column.

Interview questions

A warp hits if (threadIdx.x < 16) with two branches of equal length. What does it cost?
Both branches run one after the other with half the lanes masked each time, so the branch section takes twice the issue slots at 50% lane utilisation. Branching on threadIdx.x / 32 instead costs nothing extra, because divergence only happens inside a warp.
What does "coalesced" mean, and what is the worst case?
The 32 addresses of a warp's load are served by as few 32-byte sectors as possible; 32 consecutive floats need 4 sectors (100% used). The worst case is lanes 32 bytes or more apart: 32 sectors, 1,024 bytes moved for 128 used, 12.5%. Nsight Compute reports it as Sectors/Req.
Why does float tile[32][33] make a transpose faster than tile[32][32]?
Shared memory has 32 banks of 4-byte words. In a 32-wide tile every element of a column is in the same bank, a 32-way conflict on the column read. One padding word shifts each row by one bank, so a column spans all 32 banks. Libraries use an XOR swizzle for the same effect without wasting memory.
A kernel uses 168 registers per thread on an H100. What is its occupancy with 128-thread blocks?
168 x 32 = 5,376 registers per warp (already a multiple of 256); each of the 4 sub-partitions has 16,384, so 3 warps fit per sub-partition, 12 per SM, 3 blocks: 12 / 64 = 18.75%. Capping at 128 registers gives 16 warps, 25%, at the price of spills.
Is higher occupancy always better?
No. Occupancy only matters as a way to hide latency. A kernel can hide latency with independent work inside each thread (several loads in flight, register tiles) at low occupancy, and many of the fastest GEMM and attention kernels do. Raising occupancy by capping registers can cause spills that cost more than they save.
How many bytes must be in flight to saturate an H100's HBM?
Little's law: bandwidth x latency. With about 480 cycles of DRAM latency and a clock near 1.8 GHz (an assumption), about 270 ns: 3.35 TB/s x 270 ns is about 0.9 MB in flight across 132 SMs, about 7 KB per SM. That is why streaming kernels use vector loads, unrolling and asynchronous copies.
What arithmetic intensity does a T x T tiled fp32 matmul reach, and what tile does an H100 need?
T / 4 FLOP per byte (T / 2 in bf16). The H100 SXM's ridge is 67 / 3.35 = 20 FLOP per byte on its fp32 cores and 989.5 / 3.35 = 295 for dense bf16 tensor cores, so bf16 needs tiles of a few hundred, which is why real kernels use 128 x 256 style block tiles plus register tiling, and still rely on L2 to share tiles between blocks.

Five words used everywhere below

  • Kernel: a function that runs on the GPU, launched once and executed by thousands of threads at the same time, each working on its own piece of data.
  • SM (streaming multiprocessor): one of the GPU's cores in the CPU sense (an H100 SXM has 132, per NVIDIA's Hopper architecture post). Each SM holds the registers and shared memory of the threads it is running.

10. Interview questions, with short answers


What is the difference between PTX and SASS?
PTX is NVIDIA's virtual instruction set: a portable assembly with unlimited virtual registers, stable across GPU generations. SASS is the real machine code of one generation, produced from PTX by ptxas (ahead of time) or by the driver (just in time). SASS is what runs, and what Nsight Compute shows you; register allocation, instruction scheduling and spilling happen only at the PTX to SASS step.
Your extension was built with -arch=sm_80. Does it run on an H100?
Yes, but not from the sm_80 machine code: cubins are compatible only within a major version. nvcc's shorthand -arch=sm_80 also embeds compute_80 PTX, and the driver compiles that PTX for 9.0 the first time it loads (slower start, then cached). It cannot use Hopper-only features such as wgmma or TMA. Built with -gencode arch=compute_80,code=sm_80 (no PTX), it fails with "no kernel image is available for execution on the device".
What does the "a" in sm_90a mean, and why does such a kernel not run on a B200?
"a" selects the architecture-specific feature set: instructions such as wgmma that exist only on that exact compute capability and are not promised to later chips. Code compiled for an "a" target runs only on that compute capability, so sm_90a code needs a 9.0 GPU. Blackwell has its own (tcgen05); a Hopper kernel must be rewritten or recompiled from a portable source, which is one reason libraries such as CUTLASS and Triton keep per-architecture code paths.
ptxas reports 128 registers per thread for a kernel launched with 256-thread blocks on an H100, no shared memory. What is its occupancy?
Each warp needs 128 x 32 = 4,096 registers; the SM has 65,536, so 16 warps fit. A block is 8 warps, so 2 blocks, 16 of the 64 warp slots: 25%. Whether 25% is too low depends on the kernel: a matmul with lots of independent work per thread can run at full speed at low occupancy; a memory-bound elementwise kernel usually cannot.
What is a register spill, how do you see one, and why does it hurt?
When a thread needs more live values than its register budget, ptxas stores some to local memory (per-thread space in global memory, cached in L1 and L2) and reloads them later. -Xptxas -v prints "bytes spill stores / spill loads"; in SASS they are STL and LDL. A few bytes that hit L1 are cheap; spills inside a hot loop add memory traffic and latency where you wanted pure arithmetic.
Why does an RTX 5090 not run a Hopper FlashAttention-3 kernel even though it is newer?
FA3 is written around Hopper's wgmma and TMA, and wgmma exists only on sm_90a. The RTX 5090 is compute capability 12.0: it has no wgmma and no tcgen05 (this tab's compiles show both rejected for sm_120), so its tensor cores are reached through warp-level mma.sync instructions. A kernel written for it uses a different instruction mix, which is why kernel libraries ship separate sm_120 code.
You see HMMA in a profiler's SASS view for a matmul on an H100. Is something wrong?
Probably, for a large matmul: HMMA is the warp-level mma.sync instruction that every generation since Volta has. On an H100 the fastest GEMMs use HGMMA (wgmma). Seeing HMMA means the kernel was compiled for a portable target (sm_80 or sm_90 without "a"), or written with WMMA or mma.sync. It still uses the tensor cores, at a lower peak in practice; the exact gap is a measurement this tab cannot make (no GPU).

1. The softmax ladder: count the bytes


Softmax turns each row of scores into probabilities: find the row's maximum m, compute ex − m for every element (subtracting m keeps the exponentials from overflowing), add them up into s, divide each by s. That is about 5 arithmetic operations per element against 8 bytes moved (read 4, write 4 in fp32): far below this GPU's ridge point of about 30 operations per byte, so softmax is memory-bound: its speed is set by bytes moved, not by arithmetic. 3. Fuse softmax into the matmul


In attention, softmax is followed by a matmul: O = softmax(S) V, where S holds one score per (query, key) pair and V holds one 64-number vector per key. Done the obvious way, softmax writes its whole N × N output P to device memory and the matmul reads it back. Fusing means one kernel does both, so P lives only in fast on-chip memory, a tile at a time. There is a catch: to normalise a row you need its maximum and sum, which you only know after seeing the whole row. Two ways out: read S twice (once for the statistics, once to multiply), or use the online softmax trick: keep a running maximum and, whenever it grows, rescale everything accumulated so far.
