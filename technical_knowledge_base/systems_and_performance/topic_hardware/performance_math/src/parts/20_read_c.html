2. Arithmetic intensity and the roofline: compute-bound or memory-bound

The same weight, two ways. The 4,096 × 4,096 BF16 query weight is 33.6 MB. Used by one token (decoding at batch 1) it does 33.6 MFLOP for 33.6 MB moved, about 1 FLOP per byte: an H100 finishes the arithmetic in 0.034 µs and then waits 10.0 µs for the bytes. Used by 8,192 tokens (a training sequence or a long prompt) it does 275 GFLOP for 167.8 MB moved, 1,638 FLOPs per byte: 277.8 µs of arithmetic against 50.1 µs of reading. Same weight, same chip; the first is limited by memory, the second by arithmetic.

A weight matrix needs about 345 tokens per read before an H100 stops waiting on memory

Predict, then drag: how many tokens must share one read of this weight before the H100 reaches its peak? 10, 100, 1,000?

One 4,096 × 4,096 BF16 matmul: FLOPs 2mkn, bytes 2(mk + kn + mn) for reading both inputs and writing the output. Roofs: H100 SXM, 989.5 TFLOP/s dense BF16 and 3.35 TB/s (vendor), ridge 295 FLOPs per byte; Apple M1 Pro, 5.06 TFLOP/s and 165 GB/s measured in the parent's {{Roofline lab|n:3c65c17b0d0d8118beeefaed56da6f8e}}, ridge 31. The fixed point is a BF16 elementwise add (1 FLOP per 6 bytes) derived. A roofline is a ceiling: real kernels sit below it (section 5).

Three consequences run through the rest of the page. Decode at small batch sits near 1 FLOP per byte, so its speed is bytes over bandwidth (section 6), and batching is how serving climbs the slope. Training and prefill run thousands of tokens per weight read, so they are compute-bound and their time is FLOPs over peak (sections 4 and 7). Elementwise operators (norms, activations, residual adds, casts) do about one FLOP per several bytes whatever the batch, so they are always memory-bound: on an H100 a BF16 add reaches 0.56 TFLOP/s, and the only cure is to fuse it into a neighbouring kernel (section 5). The parent's Roofline lab measures these ceilings on a real GPU; the CUDA and serving pages apply the model to kernels and to batching.

3. Memory: what one training step holds

The model state. Mixed-precision training with Adam keeps, for every parameter, the BF16 weight used in the matmuls (2 bytes), its BF16 gradient (2), and the optimizer's state in FP32: a master copy of the weight (4, because tiny updates vanish when added in BF16) and Adam's two moments m and v (4 + 4). That is 2 + 2 + 12 = 16 bytes per parameter, the ZeRO paper's 2Ψ + 2Ψ + KΨ with K = 12 ({{ZeRO, section 3 "Where did all the memory go?"|https://arxiv.org/abs/1910.02054}}; {{paper page|n:3c65c17b0d0d81879a7ed90bca007699}}): 128.5 GB for Llama 3.1 8B. That does not fit one 80 GB H100, nor two 32 GB RTX 5090s; sharded over an 8-GPU server (ZeRO stage 3, FSDP) the 128.5 GB is 16.1 GB per GPU. 70B's 1.13 TB does not fit an 8-GPU H100 server (640 GB) even sharded: it needs more servers or the optimizer offloaded to CPU memory.

Activations. Every backward rule needs something from the forward pass (a linear layer's weight gradient needs its input, SiLU needs its input, softmax its output), so those tensors stay alive from the moment they are made until backward uses them; they grow with tokens per GPU. Counting every tensor autograd saves in the real model gives 49 bytes per token per hidden unit per layer: 52.7 GB for the 32 layers at 8,192 tokens and micro-batch 1, plus 4.47 GB for the output, because the loss needs the logits in FP32 (128,256 × 4 bytes per token, more than two whole layers). Total 57.1 GB, against the 36.5 GB that the GPT-3 count (34sbh) predicts counted. With plain ("eager") attention each layer also keeps its scores, 32 heads × 8,192 × 8,192 in FP32 and again in BF16: 13.0 GB per layer, 473 GB in all. With full recomputation only each layer's 2h input is kept: 6.6 GB, most of it the logits.

Correction to the old page, and to the parent's calculator
The old notes wrote activations as "sbh × L × c (batch s × seq b ...)": in Korthikanti et al. s is the sequence length and b the micro-batch, and the per-layer constant is 34 + 5as/h (about 34 with FlashAttention, 2 with full recomputation). The parent calculator's "store all, FlashAttention" option used 34sbh, about 1.4 times low for Llama-style models in the Transformers code (49h counted) and without the FP32 logits; since 2026-10-24 it uses this page's count.

Real runs choose per layer. Megatron's selective recomputation recomputes only the attention-score part, cheap in FLOPs and expensive in memory ({{Korthikanti et al., section 5|https://arxiv.org/abs/2205.05198}}); with FlashAttention there is nothing quadratic left, so the choice is between keeping the 49h and recomputing layers. Tensor parallelism with sequence parallelism divides the per-layer figure by the TP degree. How checkpointing and sharding work is {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}}'s subject; activation memory for any model, length and choice is the {{FLOP and memory ledger|#t-ledger}} tab.

Three differences from GPT-3's 34 explain the 49:

  • SwiGLU. Llama's MLP has three matrices and an intermediate width of 14,336 = 3.5h, and four 3.5h-wide tensors are saved (gate output, up output, SiLU output, their product): 28h against GPT's 18h.
  • RMSNorm in FP32. The reference code upcasts to FP32 before normalising, so each norm saves a 4h FP32 copy plus 2h BF16 copies: 16h for two norms against 4h. A fused norm kernel saves only its input and the per-token scale.
  • Grouped-query attention saves K and V at 8 heads instead of 32 (0.5h each), and there is no dropout.

Fused RMSNorm and SwiGLU kernels bring the real figure down; the counted number is for the reference code.
