1. FLOPs: where 6ND comes from, and when it is wrong

The problem. To know how long training takes you need the number of floating-point operations (FLOPs: one add or one multiply each). Counting them operator by operator is tedious; one rule gets within a few percent for most runs, and you need to know when it does not.

A matrix multiply. Multiplying an (m × k) matrix by a (k × n) matrix makes m × n outputs, each a sum of k products: k multiplies and k adds, so 2mkn FLOPs. In a transformer almost all the work is of this kind: tokens (m) times a weight matrix (k × n).

forward ≈ 2N per token    backward ≈ 4N per token    training C ≈ 6 N D
N
parameters that take part in a matrix multiply
D
training tokens
4N
the backward pass multiplies twice for every forward multiply: once for the gradient of the input (to keep backpropagating), once for the gradient of the weight

Each weight meets each token once going forward (2 FLOPs) and twice going back (4). The math topic's Matrix calculus and backprop page derives the factor 2 and measures it on a small model (exactly 2.00 for the matrix products). The rule is Kaplan et al.'s (Scaling Laws, section 2.1), and PaLM's Appendix B made it the basis of MFU (PaLM).

Training FLOPs per token by part, against 6N (dashed). The bars are PyTorch's count on the real model at each sequence length. The FLOP and memory ledger tab draws it for any length and for 70B and 405B.

Four things move it away from 6N:

  • The input embedding is not a multiply. It looks a row up. Its 525M parameters are 6.5% of N, so 6N over-counts by that much at short sequences. The output head is a multiply and counts.
  • Attention over the context. Each token's query meets every earlier key: forward 4 × T × h FLOPs per layer, growing with the sequence while 6N does not. At 2,048 tokens the two effects nearly cancel (+1.3% over 6N); at 8,192 attention adds 24.7%, at 32,768 118%, at 131,072 it is five times 6N.
  • Causal masking. A causal kernel skips blocks above the diagonal, about half the score square. Counting full squares (PaLM's 12LHQT, PyTorch's counter) gives the upper figure; the work done is nearer half the attention term. At 8,192 tokens the attention term is 26.7% of 6N counted in full, 14.3% of the matmul-only 6N counted causally: both conventions are in use, so say which you mean.
  • FlashAttention's backward recomputes the scores instead of reading them back, so its attention backward is 2.5 times its forward, not 2 times (counted: 10.74 against 4.29 GFLOP per token).
Conventions differ, even on the parent page
The parent's calculator adds attention as PaLM's 12LHQT in full (15% for 70B at 8,192); its Reading tab quotes 14% for 8B at 8,192, which is the causal half over matmul-only 6N. Both are right under their own convention. Counted in full with FlashAttention's backward, the whole step is 24.7% above 6N for 8B and 16.3% for 70B.

Mixture of experts. Each token passes through only k of E experts, so FLOPs follow the active parameters and memory follows the total: DeepSeek-V3 is 671.0B total and 37.55B active, 17.9 times fewer FLOPs per token than a dense model of the same size (parameter counts recounted from its config by the parent's calculator). The router's own FLOPs are tiny; the cost moves to the network (section 8).

2. Memory for the model: bytes per parameter

The problem. Before activations or batch size enter, the model itself must fit. How much memory one parameter costs depends on what training keeps for it.

How it works. Mixed-precision training with the Adam optimizer keeps, for every parameter: the BF16 weight used in the matmuls (2 bytes), its BF16 gradient (2), and the optimizer's state in FP32: a master copy of the weight (4, because tiny updates vanish when added in BF16) and Adam's two running moments m and v (4 + 4). That is 2 + 2 + 12 = 16 bytes per parameter, the count the ZeRO paper writes as 2Ψ + 2Ψ + KΨ with K = 12 (ZeRO, section 3 "Where did all the memory go?"; paper page).

3. Activations: what the backward pass keeps

The problem. The model state is fixed; activations grow with tokens per GPU, and at long sequences they dominate. Every backward rule needs something from the forward pass (a linear layer's weight gradient needs its input; SiLU needs its input; softmax needs its output), so those tensors stay alive from the moment they are made until the backward pass uses them.

The GPT-3 count: 34 bytes per token per hidden unit

Korthikanti et al. listed what one GPT-style layer stores, in bytes, for sequence length s, micro-batch b, hidden size h and a attention heads, in 16-bit precision (Reducing Activation Recomputation, section 4.1):

The 5as/h term is the attention score matrix: quadratic in the sequence. For GPT-3 at 2,048 tokens it is 80, more than the 34 for everything else (the paper's own example). FlashAttention never stores the score matrix (it recomputes it in the backward pass), which removes that term.

Correction to the old page
The old notes wrote activations as "sbh × L × c (batch s × seq b ...)". In Korthikanti et al. s is the sequence length and b the micro-batch; the per-layer constant is 34 + 5as/h, or about 34 with FlashAttention, and 2 per layer with full recomputation (the layer input only).

Llama 3.1 8B, counted: 49 bytes per token per hidden unit

Bytes per token in units of h = 4,096 (BF16 is 2 bytes per number, so "2h" is one hidden-sized vector). The source line is where the tensor was saved in Transformers' modeling_llama.py; attention uses PyTorch's flash kernels and saves what the flash-attn library saves (q, k, v at their own 8 KV heads, the output and the log-sum-exp) counted.

Three differences from GPT-3's 34 explain the 49:

  • SwiGLU. Llama's MLP has three matrices and an intermediate width of 14,336 = 3.5h, and four 3.5h-wide tensors are saved (gate output, up output, SiLU output, their product): 28h against GPT's 18h.
  • RMSNorm in FP32. The reference code upcasts to FP32 before normalising, so each norm saves a 4h FP32 copy plus 2h BF16 copies: 16h for two norms against 4h. A fused norm kernel saves only its input and the per-token scale.
  • Grouped-query attention saves K and V at 8 heads instead of 32 (0.5h each), and there is no dropout.

For the whole model at 8,192 tokens and micro-batch 1 that is 52.7 GB for the 32 layers plus 4.47 GB for the output: the loss needs the logits in FP32, 128,256 × 4 bytes per token, more than two whole layers. Total 57.1 GB, against the 36.5 GB that the GPT-3 count (34sbh) predicts. With plain ("eager") attention each layer also keeps its scores, 32 heads × 8,192 × 8,192 in FP32 and again in BF16: 13.0 GB per layer, 473 GB in all. With full recomputation only each layer's 2h input is kept: 6.6 GB, most of it the logits.

4. Recomputation, and why the hardware does more FLOPs than the model needs

The problem. Section 3 showed recomputation turning 73 GB into 23 GB. The price is arithmetic: the forward pass runs again during backward. How much again, and how should utilisation count it?

The textbook answer is 8N. Recompute every layer's forward (2N) on top of 6N: 8/6 = 1.33 times the work. The counted answer for Llama 3.1 8B at 8,192 tokens is smaller: 1.24 times counted. Three reasons:

  • The output head is not recomputed (only the transformer layers are checkpointed).
  • PyTorch's non-reentrant checkpoint stops recomputing as soon as every saved tensor exists again. The last matmul of each layer (the MLP's down projection) produces nothing that the backward pass needs, so it is not rerun ("Non-reentrant checkpoint stops recomputation as soon as all needed intermediate activations have been recomputed", PyTorch 2.14 docs): the recompute is 118.7 TFLOP, not the layers' full 149.5 TFLOP forward (30.8 TFLOP of down projections skipped).
  • Attention's backward already costs more than twice its forward with FlashAttention, so the recompute is a smaller share of the total.
MFU counts model FLOPs     HFU counts hardware FLOPs

Korthikanti et al. define them this way: "model FLOPs are hardware and implementation independent and only depend on the underlying model", while "if an implementation requires activation recomputation ... the hardware FLOPs are going to be larger" (section 6.3). HFU flatters: a run that recomputes everything can show high HFU while training no faster. Compare runs by MFU.

Turning Llama 3's MFU back into a step time

Table 4's first row: 8,192 GPUs, data parallel 64, batch 32 sequences of 8,192 tokens per data-parallel group, so 64 × 32 × 8,192 = 16,777,216 tokens per step. At 430 TFLOP/s per GPU and 6N FLOPs per token, one step takes 16.78e6 × 6 × 405.85e9 / (8,192 × 430e12) = 11.6 s; counting attention in full (8.3% more FLOPs), 12.6 s. Meta does not say which FLOP count its 430 uses, so the step time is known only to within that 8%. Per GPU that is 177 tokens per second. derived

Where the other 55 to 60% goes

  • Matmuls below peak. Even a large BF16 GEMM reaches about 720 of the H100's 989.5 TFLOP/s in SemiAnalysis's independent measurement (73%) (SemiAnalysis, Dec 2024). That ceiling is reached before anything else goes wrong.
  • Memory-bound operators (norms, activations, residual adds, the loss): no matmul, so no MFU, and on an H100 each byte costs as much time as 295 FLOPs (section 6 counts them).
  • Communication that does not overlap (section 8), pipeline bubbles (idle stages at the start and end of each step), stragglers, data loading.
  • Failures and restarts, which MFU measured in steady state leaves out: compare Llama 3.1 8B's card, 1.46M H100-hours for about 15T tokens, an implied 13.9% if every hour were training.

6. Measuring MFU yourself, and predicting it operator by operator

The problem. A published MFU is someone else's run. To check your own you need a clean timing, the FLOP count from section 1, and the right peak; to know what to fix you need to know where the time goes. Both were done here on a real GPU: this laptop's Apple M1 Pro.

How to measure

  1. Warm up (the first iterations compile kernels and fill allocator caches), then time many steps.
  2. Synchronise before reading the clock: GPU calls return before the work finishes (torch.cuda.synchronize(), here torch.mps.synchronize()).
  3. Take the median, repeat the whole run, and report the spread and what else was running.
  4. MFU = model FLOPs of the step / time / dense peak. Get the FLOPs from torch.utils.flop_counter.FlopCounterMode or from section 1's formulas; they agree.

Peak 5.06 TFLOP/s (FP16 fused multiply-add) and bandwidth 165 GB/s are the parent's Roofline lab measurements on this GPU. Each run is the median of 8 timed steps after 3 warm-up steps; 3 runs, 20 s apart, with the 1-minute load average of the shared machine recorded. At 2,048 tokens the first run hit memory swapping (41.7 s) and is excluded by taking the median of the three runs. Script: src/code/m1_step.py.

72 to 75% MFU on one GPU. With large matrices, no communication and no tensor cores (the M1's FP16 runs at the same rate as FP32 through ordinary ALUs, so its ridge point is only about 31 FLOPs per byte), almost every operator is compute-bound and the GPU runs near its own matmul speed. That is the first lesson: a single GPU on big matmuls reaches high MFU; the losses in section 5 come from elsewhere.

Predicting the step from its operators

The same step was run once more with a TorchDispatchMode recording every operator PyTorch launched (447 per step, 315 of which compute or move data): its FLOPs and the bytes it reads and writes. Each operator gets a roofline time, max(FLOPs / peak, bytes / bandwidth), and the step's prediction is the sum. The measurement takes 14 to 22% longer than the prediction: the overhead of launching each kernel and of matmuls that do not quite reach the FMA peak.

The same operators on an H100: why fusion matters more on faster chips

That projection is a roofline estimate, not a run. It is why the operator count matters for training performance: torch.compile and hand-written fused kernels (FlashAttention, fused norms, fused cross-entropy) exist to remove exactly this traffic, and it matters wherever the ridge is high: 295 FLOPs per byte for an H100 at BF16, twice that at FP8. Writing such kernels is the Topic: cuda-and-gpu-programming root's subject.

7. Serving: prefill, decode, and tokens per second

The problem. A served request has two phases with opposite limits. Prefill runs the whole prompt through the model at once; decode then produces one token per step, and each step must read every weight it uses plus the conversation's KV cache (the keys and values of every earlier token, which attention needs). The first is limited by arithmetic, the second by memory bandwidth.

The lesson in the table: batching is the whole economics of serving. Each step reads the weights once whatever the batch, so 64 users share the 16 GB read and cost 21 times less per token, at the price of each user waiting 3 times longer per token. The cache does not share: at long contexts each conversation's KV reads dominate and batching stops helping, the reason grouped-query attention, latent attention and FP8 caches exist. The physical side of the KV cache (sizes for 13 real configs, paging) is the sibling Memory technology page; the step at batch 1 and 64 is animated in the parent's Performance calculator.

Long prompts. Llama 3.1 70B with a 32,768-token prompt on 8 H100s at 50% of peak: 1.52 s before the first token, and attention is 23% of those FLOPs (causal count). Prefill time grows faster than linearly with the prompt.

Mixture of experts. At batch 1 a decode step reads only the routed experts: DeepSeek-V3 in FP8 reads 37.6 GB of its 671 GB. But 64 tokens with 8 of 256 experts each touch about 222 experts per layer (uniform routing, 256 × (1 − (1 − 8/256)64)), so the step reads 585 GB: an MoE's bandwidth advantage disappears at the batch sizes that make serving cheap, while its FLOP advantage stays derived.

The MoE row is an upper bound: tokens whose experts sit on the same GPU do not move, and DeepSeek-V3 limits each token to 4 nodes.

The pattern decides placement. Data-parallel traffic is per step and overlaps with backward, so it can cross the slower network between servers. Tensor-parallel traffic is per layer and blocks compute, so it stays inside the NVLink domain; expert parallelism's all-to-all is per layer too. The parent calculator's "Why tensor parallelism stays inside the NVLink domain" chart puts numbers on it; the sibling Interconnects and scaling page covers the links and collectives, and Distributed Training the layouts.

10. Common mistakes, drills and interview questions

Common mistakes

Dividing by the sparse peak
Datasheets print 2:4 structured-sparsity figures, twice the dense ones (H100 BF16: 1,979 sparse, 989.5 dense). Training never uses them; MFU against a sparse peak is half what it should be. The parent's Chip atlas marks which is which.
Reporting HFU as MFU
Counting recomputed FLOPs raises utilisation without making training faster (PaLM: 46.2% MFU, 57.8% HFU). Model FLOPs are fixed by the model; compare runs on those.
Using 6N at long context
At 32,768 tokens the attention core more than doubles the per-token cost of Llama 3.1 8B (105 against 48 GFLOP, full-square count). State the convention (full or causal) whenever you add it.
Counting the input embedding as compute
It is a lookup: 6.5% of Llama 3.1 8B's parameters do no FLOPs. Labs differ on whether "N" includes it (gpt-oss-120b's card leaves it out of the active count).
Forgetting the logits
With a 128K vocabulary the FP32 logits kept for the loss cost 4.47 GB per 8,192-token sequence: more than two layers of activations. Chunked or fused cross-entropy kernels exist for this reason.
Using GPT-3's 34sbh for a Llama model
SwiGLU and FP32 norms make it 49 in the reference code (counted). Formulas carry their architecture's assumptions.
Reading GPU-hours as efficiency
A model card's GPU-hours include restarts and experiments; Llama 3.1 8B's imply 13.9% MFU, against 38 to 43% measured in-run for the 405B.
Mixing total and active parameters
For a mixture of experts, FLOPs follow active parameters, memory follows total, and decode bandwidth follows how many experts the batch touches (section 7).
Leaving out goodput and price terms
A cost estimate without failures, restarts and the price's date and terms is a lower bound. Say which.

Drills

Commit to an answer, then reveal. Every answer is computed from the sections above; the parent's Performance calculator has ten more.

1. One training step of Llama 3.1 8B on one 8,192-token sequence. How many FLOPs, counting attention?
6N × 8,192 = 395 TFLOP; counted, 492 TFLOP (60.06 GFLOP per token × 8,192). At 40% MFU on one H100 that is 1.24 s.
2. With FlashAttention and no recomputation, how much activation memory does that step keep?
49 bytes × 4,096 × 8,192 tokens per layer = 1.65 GB, × 32 layers = 52.7 GB, plus 4.47 GB of FP32 logits: 57.1 GB. 470 GB is the same step with plain attention.
3. Why can plain (non-flash) attention not train this model at 8,192 tokens on an H100?
32 heads × 8,192 × 8,192 scores, kept in FP32 (softmax output) and BF16 (for the next matmul): 6 bytes each, 12.9 GB per layer, 13.0 GB counted with the repeated K and V. The FLOPs are the same as with FlashAttention's forward.
4. Full activation checkpointing in PyTorch: by how much does the hardware's work exceed the model's?
Counted 1.24 times, not 8/6 = 1.33: the head is not checkpointed, FlashAttention's backward is already 2.5 times its forward, and the non-reentrant checkpoint skips each layer's final down projection.
5. Llama 3 405B ran at 430 TFLOP/s per GPU on 8,192 H100s with 16.8M tokens per step. How long was a step?
16,777,216 × 6 × 405.85e9 / (8,192 × 430e12) = 11.6 s (12.6 s if Meta's FLOP count includes attention). 177 tokens per second per GPU.
6. How many H100s pretrain Llama 3.1 8B on 15T tokens in 30 days at 40% MFU and 90% goodput?
7.2e23 / (989.5e12 × 0.4) / 3,600 = 507K GPU-hours; / 0.9 / 720 hours = 783 GPUs, about $2.25M at $3.99 per hour.
7. Serving Llama 3.1 8B on one H100 at 4,096 tokens of context: how much cheaper per token is batch 64 than batch 1, at the ceilings?
$5.49 against $0.26 per million tokens: 21 times, not 64, because each of the 64 conversations still reads its own 0.54 GB cache every step.
8. DeepSeek-V3 in FP8 decoding a batch of 64: what share of its 671 GB of weights does one step read?
64 tokens touch about 222 of 256 experts per layer: 585 GB, 87% of the weights, against 37.6 GB (5.6%) at batch 1.

Interview questions, short answers

Derive 6ND.
A matmul of (m × k) by (k × n) is 2mkn FLOPs; each weight meets each token once forward (2 FLOPs) and twice backward (gradient of the input and of the weight, 4): 6 per parameter per token. It omits attention over the context and counts the embedding lookup it should not.
What are MFU and HFU, and which do you report?
Achieved model FLOPs per second over the dense peak; HFU adds recomputed FLOPs. Report MFU, state the peak's precision and whether attention is counted.
Your 8B run reaches 25% MFU on 64 H100s. Where do you look?
Single-GPU MFU first (matmul efficiency, memory-bound ops, fusion); then communication that does not overlap (FSDP across servers, TP outside NVLink); then data loading and stragglers. Each has a number from this page to compare with the profiler.
How do you estimate time per output token for a model you are serving?
Bytes per step over bandwidth: weights used plus the KV caches of the batch, divided by the HBM bandwidth (times an efficiency). Compute-bound only at large batch and short context.
Why can recomputation make training faster?
It frees activation memory, which allows a larger micro-batch or less model parallelism; PaLM chose it "because this results in higher training throughput at larger batch sizes".
