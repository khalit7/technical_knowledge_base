Performance calculator

Before you rent a single GPU, five lines of arithmetic tell you whether a model fits, how long a run takes, what it costs, how fast a deployment can answer, and how much of the time goes to the network. This tab does that arithmetic with every input visible, checks it against figures labs have published, and ends with interview-style drills.

What this tab is, and what it is not
Everything here is computed: formulas applied to vendor peak specifications (dated, sourced in the {{Chip atlas|#t-chips}}) and to real model shapes read from each model's config.json on Hugging Face. Nothing was run on an NVIDIA, AMD or Google chip. A computed number is a ceiling (the best the hardware allows) or an estimate at an efficiency you choose; real systems land below it, and the {{Roofline lab|#t-roof}} measures by how much on a real GPU. The formulas are checked against a Python reference on 507 values (all match), and the defaults are checked against published figures in the checks table.

The terms, in one screen

Parameters N, tokens D

N is the number of learned numbers in the model (8.03 billion for Llama 3.1 8B). D is how many tokens (word pieces) it trains on. For a mixture-of-experts (MoE) model, only some experts run per token: the active parameters set the compute, the total set the memory.

FLOPs and 6ND

A FLOP is one floating-point add or multiply. Each weight does one multiply and one add per token going forward (2 FLOPs) and about twice that going backward (4), so training costs about 6 N D FLOPs and generating one token about 2 N.

Peak, MFU

A chip's peak is its datasheet FLOP/s at a given precision (dense, no sparsity). MFU, model FLOPs utilisation, is the useful FLOPs a run actually achieved divided by that peak. 35 to 45% is good for large dense training.

Memory capacity, bandwidth

Capacity (GB) decides what fits on the chip; bandwidth (TB/s) decides how fast it can be read. An H100 SXM has 80 GB of HBM (stacked memory next to the chip) read at 3.35 TB/s.

KV cache, prefill, decode

While generating, a model keeps every past token's attention keys and values: the KV cache. Prefill processes the whole prompt at once (lots of maths per byte); decode then makes one token per step, rereading all weights and the cache each time (little maths per byte).

All-reduce, NVLink, InfiniBand

An all-reduce sums a tensor across GPUs so each ends with the total (how gradients are averaged). Inside a server GPUs talk over NVLink (450 GB/s each way per H100); between servers over InfiniBand or Ethernet NICs, typically 400 Gb/s = 50 GB/s per GPU.

When 6ND is wrong
  • Long sequences: attention's score and value matmuls add 12 L H Q T FLOPs per token (PaLM's Appendix B: L layers, H heads, Q head size, T sequence length). Tick the box: it adds 1.1% for PaLM at 2,048 tokens, 15% for Llama 3.1 70B at 8,192 and 61% at 32,768 (the formula counts the full score square; causal kernels skip about half of it, a convention to state).
  • Mixture of experts: use the active parameters for FLOPs and the total for memory (DeepSeek-V3: 37.6B and 671B).
  • Recompute: full activation checkpointing runs the forward pass twice, so the hardware does 8ND while the model still only "needs" 6ND. MFU counts 6ND; hardware FLOPs utilisation (HFU) counts 8ND and looks better (PaLM: 46.2% MFU, 57.8% HFU).
  • LoRA and QLoRA: the frozen base gets no weight gradients, so about 4ND (forward 2, backward through activations 2).
  • Embeddings: the input embedding is a table lookup, not a matmul. Labs differ on whether N includes it (gpt-oss-120b's 5.13B active excludes it; our recount gives 5.71B with it).
Go deeper: how the layout (TP, PP, data and expert parallelism) is chosen at real scale is the {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}} page's Layout calculator; training time for a model size and token budget from scaling laws is the training topic's {{Scaling calculator|n:3c65c17b0d0d81b6876ee72b7056793b}}.

Inference: memory, speed, and where decode stops being memory-bound

Serving has two phases. Prefill runs the prompt through the model in one big batch of tokens: compute-bound, so its time is FLOPs over peak. Decode then makes one token per sequence per step, and every step must read all the weights it uses plus every sequence's KV cache from memory: at small batch it is memory-bound, so its time is bytes over bandwidth.

Why the batch is your arithmetic intensity
At batch 1 each weight read from memory is used for one multiply-add: 2 FLOPs per 2 bytes in BF16, 1 FLOP per byte. An H100 can do 295 FLOPs in the time it reads one byte (989.5 TFLOP/s over 3.35 TB/s), so its tensor cores sit idle over 99% of the time. Batch B reuses each weight B times, so with a short context decode becomes compute-bound only near B = 295 (the chart shows the exact crossover). The KV cache does not share: each sequence reads its own, so at long context the cache, not the weights, dominates, and adding sequences never makes decode compute-bound. That is why grouped-query attention (fewer KV heads), DeepSeek's latent attention (MLA) and FP8 KV caches exist.
Go deeper: batching schedulers, paged KV caches and speculative decoding are the {{inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} topic; low-bit formats are the {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}} page.

Communication: the same bytes over NVLink and over the network

A ring all-reduce over n GPUs sends each GPU's data around the ring twice (once to sum, once to share the sum), so each GPU moves 2(n−1)/n times the tensor and the time is set by the slowest link: t = 2(n−1)/n × S / B, the bus-bandwidth model of {{NCCL's tests|https://github.com/NVIDIA/nccl-tests/blob/master/doc/PERFORMANCE.md}}. Reduce-scatter and all-gather each move (n−1)/n.

Why tensor parallelism stays inside the NVLink domain

Data parallelism exchanges gradients once per step. Tensor parallelism (Megatron-style: each layer's matrices split across GPUs) must all-reduce the layer's activations four times per layer per micro-batch (twice forward, twice backward), on the critical path. Its traffic per token is about 16 h bytes per layer against about 6 × 12h²/TP FLOPs of compute, so the ratio does not depend on batch: only a fast link keeps it small.
