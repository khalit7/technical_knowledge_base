2. Inside a GPU: SMs, warps, tensor cores, registers, caches

The problem. The step must keep tens of thousands of arithmetic lanes fed every cycle while memory takes hundreds of cycles to answer. The GPU's whole layout follows from that. The H100 is the reference here because most published training numbers were measured on it; Blackwell's changes come after.

SMThe building block. H100 SXM enables 132 of the 144 on its die (the spare ones absorb manufacturing defects). Each SM has 4 sub-partitions, each with a warp scheduler, 32 fp32 lanes, a 64 KB slice of the register file and one tensor core.
Warp32 threads that share one instruction pointer: the scheduler issues one instruction for all 32 at once (SIMT, single instruction, multiple threads). If threads in a warp take different branches, the two paths run one after the other.
Register file256 KB per SM, 64K 32-bit registers, the largest and fastest memory on the chip: 33.8 MB across 132 SMs derived. Every resident thread keeps its registers there, which is what makes switching warps free.
Shared memory and L1256 KB per SM, of which up to 228 KB can be shared memory: a scratchpad the program fills by hand so a block of threads can reuse a tile of data. Matmul and attention kernels live or die by it.
L2 cache50 MB shared by all SMs, between the SMs and HBM.
HBM80 GB in 5 stacks of stacked DRAM beside the die, 3.35 TB/s (section 3).

How latency is hidden. An SM keeps up to 64 warps (2,048 threads) resident at once, all with their registers in place. Every cycle, each sub-partition's scheduler picks a warp whose next instruction has its inputs ready and issues it. A load from HBM takes hundreds of cycles; while one warp waits, others compute. So a GPU needs far more threads in flight than it has lanes. The fraction of the 64 warp slots actually filled is called occupancy; it falls when each thread needs many registers or a block needs much shared memory, because those are shared by everyone resident. The CPU hides the same latency with caches and speculation; the GPU hides it with parallel work, which only exists if the batch is big enough.

Tensor cores, generation by generation. A tensor core takes small tiles of two matrices and returns their product added to an accumulator, in one instruction issued for a whole warp (or group of warps). Each generation made the tiles larger and the formats smaller:

When it matters for training. Peak FLOPS are tensor-core FLOPS. A step reaches them only when its matmuls are large enough to fill all 132 SMs with tiles, when the data arrives in shared memory in time (TMA, deep pipelines), and when the shapes suit the tensor cores (dimensions that are multiples of 8 or 16 are the usual advice in NVIDIA's {{matrix multiplication performance guide|https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html}}). Everything that is not a matmul (normalisation, softmax, activation functions, the optimizer update) runs on the ordinary lanes, a sixteenth of the tensor-core rate in fp32, and is usually limited by memory anyway (section 5).

How to check. nvidia-smi "utilization" only says that some kernel was running, not how much of the chip it used. The profiler's tensor-pipe utilisation and achieved occupancy per kernel are the real numbers ({{Topic: cuda-and-gpu-programming|n:3c65c17b0d0d81c39f34d5e070d783c1}} covers Nsight).
