1. Why GPUs: throughput against latency

The problem. Almost all of the step's 2.5 × 1016 FLOPs are matrix multiplications: every layer multiplies a block of activations (tokens by 4,096) by a weight matrix. A matrix multiply has three properties that decide what hardware should run it. It is huge (billions of independent multiply-adds), regular (the same operation on every element, no branches that depend on the data) and predictable (you know every address you will touch before you start). A fused multiply-add (FMA), a × b + c in one instruction, is the unit of work; one FMA counts as 2 FLOPs.

A CPU core is built for the opposite case: one stream of instructions full of branches and pointer chasing, which must finish as soon as possible. Most of its transistors go to guessing (branch prediction, speculative and out-of-order execution) and to big caches that hide memory latency, so a single thread runs fast. Its arithmetic is a small part: an M1 Pro performance core has 4 floating-point units, each working on 4 fp32 numbers at once (a 128-bit SIMD register), so 16 FMAs per cycle, 32 FLOPs per cycle, about 102 GFLOP/s at 3.2 GHz. The {{C++ page|n:3cd5c17b0d0d81ceadcee44fe9c023a0}} measured 97.5 GFLOP/s on this laptop measured here.

A GPU core drops the guessing. It runs thousands of threads in groups that execute the same instruction together, and spends its transistors on arithmetic lanes and registers. When one group waits for memory, the core simply switches to another group that is ready, so it hides latency with parallel work rather than with caches and prediction. One M1 Pro GPU core has 128 fp32 lanes at 1.296 GHz ({{metal-benchmarks|https://github.com/philipturner/metal-benchmarks}} independent); NVIDIA calls its equivalent a streaming multiprocessor (SM), and an H100 SM also has 128 fp32 lanes ({{NVIDIA Hopper in depth|https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/}} vendor spec) plus four tensor cores: units that do a whole small matrix multiply per instruction instead of one FMA per lane (section 2).

Each square is a 4 × 4 block of the 64 × 64 output; a block turns solid when its 1,024 FMAs are done. Cycles are FMAs per cycle from the specs; times divide by each engine's clock. The H100 clock, 1.83 GHz, is derived from its 989.5 TFLOPS dense BF16 figure: 989.5 × 1012 / (132 SMs × 4,096 FLOPs per cycle). The tensor-core rate per SM is the A100 SM's 1,024 dense FP16 FMAs per clock ({{A100 whitepaper|https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/nvidia-ampere-architecture-whitepaper.pdf}}) doubled for Hopper, which agrees with {{How To Scale Your Model's GPU chapter|https://jax-ml.github.io/scaling-book/gpus/}} (1,024 bf16 FLOPs per cycle per tensor core). The M1 rows also show the measured rate: 97.5 GFLOP/s per CPU core and 5.01 TFLOP/s / 16 = 313 GFLOP/s per GPU core measured here.

What it shows. One GPU core does 8 times the work per cycle of a CPU core; at its lower clock it still finishes this tile about 3 times sooner. The tensor cores do 16 times the work per cycle of the same SM's ordinary lanes. On the whole M1 Pro chip, with the same memory and the same power budget, the 8 CPU threads peaked at 562 GFLOP/s and the 16 GPU cores at 5,008 GFLOP/s measured here, a factor of 8.9. An H100 has 132 SMs with tensor cores: 989.5 TFLOPS dense BF16, about 200 times this laptop's GPU.

The cost
A GPU thread is slow and a GPU is bad at anything sequential or branchy. The CPU does not go away in training: it runs Python, launches every kernel, decodes and shuffles data, and drives the network. A data loader that cannot keep up, or a training loop that launches thousands of tiny kernels, leaves the GPU idle no matter how fast it is (section 10's symptom table).

The third answer, the TPU. Google's TPU keeps neither many threads nor big caches. Its core is a systolic array: a grid of multiply-accumulate cells (128 × 128 from v2 to v5, 256 × 256 on v6e, per {{How To Scale Your Model|https://jax-ml.github.io/scaling-book/tpus/}}; the first TPU, v1, already used one 256 × 256 array for 92 int8 TOPS, per {{Jouppi et al. 2020|https://doi.org/10.1145/3360307}}) where the weights are loaded once and stay put while activations flow through from one side and partial sums flow out the other, cell to neighbouring cell, like blood pumped through a heart. Each operand is read from memory once and used hundreds of times without touching a register file, which is where a GPU spends much of its energy. The price is flexibility: a TPU is programmed through a compiler (XLA) that schedules everything ahead of time, and anything that is not a big dense matrix multiply runs on a much slower vector unit.

Predict: an M1 Pro GPU core runs at 1.296 GHz, a CPU performance core at 3.2 GHz. Per second, how much more fp32 FMA work does one GPU core do than one CPU core?
About 3 times: 128 lanes × 1.296 GHz against 16 lanes × 3.2 GHz is 166 against 51 billion FMAs per second (3.2×). Measured: 313 against 97.5 GFLOP/s (3.2×). Width beats clock; the GPU then multiplies it by having many cores.
