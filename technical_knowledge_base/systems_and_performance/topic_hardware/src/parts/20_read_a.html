1. Why GPUs: three ways to do a matrix multiply

Almost all of the step's FLOPs are matrix multiplications: huge, regular (no data-dependent branches) and predictable (every address known in advance). A fused multiply-add (FMA) is the unit of work, 2 FLOPs. Three designs answer that workload differently:

EngineWhere its transistors goHow it hides memory latencyFMAs per cycle per core
CPU coreGuessing: branch prediction, out-of-order execution, big cachesCaches and speculation, for one fast thread16 (M1 Pro performance core: 4 units × 4 fp32 lanes)
GPU core (NVIDIA: SM)Arithmetic lanes and registers for thousands of threadsSwitches to another group of threads that is ready128 fp32 lanes (M1 Pro GPU core, H100 SM)
Tensor core (inside the SM)A small matrix multiply per instruction instead of one FMA per laneAs the SM16 times the SM's own lanes (H100)
Systolic array (TPU and most other accelerators)A grid of multiply-accumulate cells; weights stay put while activations flow cell to cellNone needed: a compiler schedules every transfer ahead of time128 × 128 cells (TPU v2 to v5), 256 × 256 (v6e)

M1 Pro CPU: about 102 GFLOP/s at 3.2 GHz, measured 97.5 GFLOP/s in {{C++: the machine underneath, section 9|n:4055c17b0d0d811fa947ee576a97a516#cb-s9}} measured here; GPU core 128 lanes at 1.296 GHz ({{metal-benchmarks|https://github.com/philipturner/metal-benchmarks}} independent); H100 SM 128 fp32 lanes and four tensor cores ({{NVIDIA Hopper in depth|https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/}} vendor spec); array sizes from {{How To Scale Your Model|https://jax-ml.github.io/scaling-book/tpus/}}.

Width beats clock: the same tile on four engines, one time axis

Each square is a 4 × 4 block of the output. The H100 clock, 1.83 GHz, is derived from 989.5 TFLOPS dense BF16 / (132 SMs × 4,096 FLOPs per cycle), where 4,096 is the A100 SM's 1,024 dense FP16 FMAs per clock ({{A100 whitepaper|https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/nvidia-ampere-architecture-whitepaper.pdf}}) doubled for Hopper, as {{How To Scale Your Model|https://jax-ml.github.io/scaling-book/gpus/}} also gives; measured per-core rates 97.5 GFLOP/s (CPU) and 5.01 TFLOP/s / 16 = 313 GFLOP/s (GPU) measured here. On the whole M1 Pro the 16 GPU cores at 5,008 GFLOP/s beat the 8 CPU threads by a factor of 8.9.

Predict before it plays: the GPU core runs at 1.296 GHz, the CPU core at 3.2 GHz. Which finishes the same tile first, and by how much? The same 64 × 64 × 64 piece of a matrix multiply (262,144 FMAs) is given to four engines on one time axis; the buttons on the figure pick two of them.

  1. t = 0: the same tile everywhere. Every engine starts the same tile: 4,096 outputs, each a dot product of length 64, so 262,144 FMAs. Time runs at the same rate for all of them.
  2. 70 ns: the H100 SM's tensor cores finish. 128 cycles at 1.83 GHz. Tensor cores do a small matrix multiply per instruction, so one SM finishes 2,048 FMAs per cycle. This is where the 989.5 TFLOPS of an H100 come from; its ordinary lanes alone give 67 TFLOPS of FP32.
  3. 1,119 ns: the same SM's CUDA cores finish. 2,048 cycles. Same SM, ordinary lanes: 128 FMAs per cycle, 16 times fewer than its tensor cores. A matmul that does not use tensor cores (fp32 without TF32, an odd shape, a hand-written loop) leaves most of the chip idle.
  4. 1,580 ns: one M1 Pro GPU core finishes. 2,048 cycles at 1.296 GHz. 128 lanes, 8 times the CPU core per cycle; at less than half the clock it still finishes about 3 times sooner. Measured: 313 GFLOP/s per core against 97.5 for the CPU core.
  5. 5,120 ns: the CPU core finishes. 16,384 cycles at 3.2 GHz: 16 FMAs per cycle (4 units × 4 lanes). Its transistors went to running one thread fast, not to arithmetic width. Measured 97.5 GFLOP/s, 95% of its 102.4 peak.
  1. t = 0: one CPU core against one GPU core. Both on the M1 Pro, both given the 262,144 FMAs of the tile; the GPU core's clock is less than half the CPU core's.
  2. 1,580 ns: the GPU core finishes. 128 lanes do 128 FMAs per cycle, 8 times the CPU core, so 2,048 cycles at 1.296 GHz are enough.
  3. 5,120 ns: the CPU core finishes. 16 FMAs per cycle need 16,384 cycles, about 3 times longer even at 3.2 GHz: width beats clock.
  1. t = 0: one H100 SM, two ways. The same SM's ordinary fp32 lanes (CUDA cores) against its four tensor cores, at the same 1.83 GHz clock.
  2. 70 ns: the tensor cores finish. 2,048 FMAs per cycle: 128 cycles.
  3. 1,119 ns: the CUDA cores finish. 128 FMAs per cycle, 16 times fewer: 2,048 cycles. Peak FLOPS are tensor-core FLOPS.

The costs. A GPU thread is slow and a GPU is bad at anything sequential or branchy, so the CPU stays: it runs Python, launches every kernel and feeds the data (the symptom table in section 10). A systolic array reads each operand from memory once and reuses it hundreds of times without a register file, which saves energy, but anything that is not a large dense matmul runs on a much slower vector unit, and the program goes through a compiler (XLA).
