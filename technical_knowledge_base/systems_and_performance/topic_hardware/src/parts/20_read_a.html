1. Why GPUs: three ways to do a matrix multiply

Almost all of the step's FLOPs are matrix multiplications: huge, regular (no data-dependent branches) and predictable (every address known in advance). A fused multiply-add (FMA) is the unit of work, 2 FLOPs. Three designs answer that workload differently:

EngineWhere its transistors goHow it hides memory latencyFMAs per cycle per core
CPU coreGuessing: branch prediction, out-of-order execution, big cachesCaches and speculation, for one fast thread16 (M1 Pro performance core: 4 units × 4 fp32 lanes)
GPU core (NVIDIA: SM)Arithmetic lanes and registers for thousands of threadsSwitches to another group of threads that is ready128 fp32 lanes (M1 Pro GPU core, H100 SM)
Tensor core (inside the SM)A small matrix multiply per instruction instead of one FMA per laneAs the SM16 times the SM's own lanes (H100)
Systolic array (TPU and most other accelerators)A grid of multiply-accumulate cells; weights stay put while activations flow cell to cellNone needed: a compiler schedules every transfer ahead of time128 × 128 cells (TPU v2 to v5), 256 × 256 (v6e)

M1 Pro CPU: about 102 GFLOP/s at 3.2 GHz, measured 97.5 GFLOP/s on the {{C++ page|n:3cd5c17b0d0d81ceadcee44fe9c023a0}} measured here; GPU core 128 lanes at 1.296 GHz ({{metal-benchmarks|https://github.com/philipturner/metal-benchmarks}} independent); H100 SM 128 fp32 lanes and four tensor cores ({{NVIDIA Hopper in depth|https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/}} vendor spec); array sizes from {{How To Scale Your Model|https://jax-ml.github.io/scaling-book/tpus/}}.

Predict before you press play: the GPU core runs at 1.296 GHz, the CPU core at 3.2 GHz. Which finishes the same tile first, and by how much? The same 64 × 64 × 64 piece of a matrix multiply (262,144 FMAs) is given to four engines on one time axis.

Width beats clock: one GPU core does 8 times the work per cycle of a CPU core and still finishes this tile about 3 times sooner; the tensor cores do 16 times the work per cycle of the same SM's lanes. Each square is a 4 × 4 block of the output. The H100 clock, 1.83 GHz, is derived from 989.5 TFLOPS dense BF16 / (132 SMs × 4,096 FLOPs per cycle), where 4,096 is the A100 SM's 1,024 dense FP16 FMAs per clock ({{A100 whitepaper|https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/nvidia-ampere-architecture-whitepaper.pdf}}) doubled for Hopper, as {{How To Scale Your Model|https://jax-ml.github.io/scaling-book/gpus/}} also gives; measured per-core rates 97.5 GFLOP/s (CPU) and 5.01 TFLOP/s / 16 = 313 GFLOP/s (GPU) measured here. On the whole M1 Pro the 16 GPU cores at 5,008 GFLOP/s beat the 8 CPU threads by a factor of 8.9.

The costs. A GPU thread is slow and a GPU is bad at anything sequential or branchy, so the CPU stays: it runs Python, launches every kernel and feeds the data (the symptom table in section 10). A systolic array reads each operand from memory once and reuses it hundreds of times without a register file, which saves energy, but anything that is not a large dense matmul runs on a much slower vector unit, and the program goes through a compiler (XLA).
