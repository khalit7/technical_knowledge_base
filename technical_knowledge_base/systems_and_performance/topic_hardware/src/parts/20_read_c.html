3. Memory: capacity against bandwidth

The problem. The step's state is 128.5 GB, and every layer's weights, activations and gradients must travel from memory to the SMs and back, several times per step. Memory has two numbers and they pull against each other: capacity (how much fits) and bandwidth (how many bytes per second reach the chip). Fast memory is small and expensive per byte; big memory is slow.

Two kinds of cell. SRAM stores a bit in a few transistors on the processor die itself: registers, shared memory, caches. It answers in a few cycles but takes a lot of area, so an H100 has about 120 MB of it in total (registers, L1 and L2 from section 2). DRAM stores a bit as charge in one transistor and a capacitor, on separate chips: dense and cheap, but every access crosses wires off the die. All the gigabytes are DRAM; the differences between GPUs come from how the DRAM is packaged.

HBM (high-bandwidth memory)DRAM dies stacked on top of each other beside the GPU die on a silicon interposer: a very wide, modestly clocked bus (1,024 bits per stack for HBM3 and HBM3e, 2,048 for HBM4). H100 SXM: 80 GB in 5 HBM3 stacks, 3.35 TB/s. B200: 180 to 192 GB of HBM3e, 8 TB/s.
GDDR7Separate chips soldered around the GPU on the board: a narrower bus clocked very fast. RTX 5090: a 512-bit bus at 28 Gbps per pin, 1.79 TB/s, 32 GB.
LPDDR5Low-power DRAM in the same package as the processor, shared by CPU and GPU. Apple M1 Pro (this laptop): 16 GB here, 200 GB/s published, 165 GB/s measured.
On-chip SRAM onlyNo DRAM for the model at all: the weights are spread over the SRAM of many chips. Groq 3 LPX rack announced: 256 chips, 128 GB of SRAM and 40 PB/s per rack.

B200 capacity is 180 GB per GPU in DGX and HGX B200 and 186 to 192 GB in other listings; the {{Chip atlas|#t-chips}} keeps each SKU apart.

Why decode waits on bytes

Generating one token at batch 1 multiplies a single activation vector by every weight matrix. Each 2-byte bf16 weight is fetched from memory to be used in exactly one FMA (2 FLOPs): 1 FLOP per byte. An H100 can do 295 FLOPs in the time it fetches one byte (section 5), so the tensor cores sit idle 99.7% of the time and the time per token is simply bytes of weights / bandwidth. The same token on the four memories, drawn on one time axis:

Llama 3.1 8B in bf16: 16.06 GB of weights read once per token, 33 blocks (32 layers and the output head), batch 1, short context so the KV cache is negligible. Time = bytes / bandwidth derived, a ceiling on tokens per second; real servers land below it (kernel overheads, the KV cache, other work). The laptop's 16 GB could not actually hold these weights beside the OS; its row is what the measured bandwidth implies.

Measured on this laptop. The {{Roofline lab|#t-roof}} timed one 8,192 × 8,192 fp16 linear layer (134 MB of weights) on the M1 Pro GPU: 0.80 ms at batch 1, reading weights at 168 GB/s, the memory's full speed; at batch 64, 64 times the arithmetic took only 3.52 ms, because the same bytes now feed 64 FMAs each measured here. Batching is how servers turn a bandwidth-bound decode into compute-bound work, and it is why a training step, with half a million tokens per batch, is compute-bound. For this 8B model in BF16 on an H100 the {{Performance calculator|#t-calc}} finds decode turns compute-bound only around batch 308 at short context, and that at 4,096 tokens of context batch 64 gives 21 times the throughput of batch 1, not 64, because every sequence's KV cache must still be read.

Full-memory reads per second

Bandwidth divided by capacity: how many times per second a chip can read its whole memory. A model that fills the memory cannot decode faster than this many tokens per second at batch 1, whatever the FLOPS.

The KV cache is the other bytes. During generation every past token's attention keys and values are kept and read again for each new token. For this model: 2 (keys and values) × 32 layers × 8 KV heads × 128 dimensions × 2 bytes = 128 KiB per token, so one 8,192-token sequence holds 1.07 GB derived, read in full for every token it generates. At long context or high batch the cache, not the weights, fills memory; that is why grouped-query attention (8 KV heads instead of 32) exists and why serving quantises the cache.

The cost
HBM gives bandwidth and fairly large capacity but needs stacked dies and an interposer beside the GPU, which makes it the expensive part of a datacenter accelerator; GDDR is cheaper but tops out at 32 GB on a consumer card; SRAM-only designs need hundreds of chips to hold one model. No memory gives both capacity and bandwidth cheaply.

When it matters for training. Capacity decides how the step must be split: 128.5 GB of state does not fit on one 80 GB H100, so it is sharded across GPUs (ZeRO or FSDP, on {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}}), or activations are recomputed instead of stored. Bandwidth decides the speed of everything that is not a big matmul: normalisation, activation functions, softmax, and the optimizer update, which reads and writes every byte of state once per step. How to check: torch.cuda.max_memory_allocated() for capacity; for bandwidth, a kernel's achieved bytes per second in the profiler against the chip's figure.
