3. Memory: capacity against bandwidth

Memory has two numbers that pull against each other: capacity (what fits) and bandwidth (bytes per second to the chip). SRAM sits on the processor die (registers, shared memory, caches: about 120 MB on an H100), answers in a few cycles and costs area; DRAM holds the gigabytes on separate dies, and accelerators differ mainly in how it is packaged:

Why bandwidth bounds decode. Generating one token at batch 1 reads every weight once to do one FMA with it, so time per token ≈ bytes of weights / bandwidth: Llama 3.1 8B's 16.06 GB at 3.35 TB/s is 4.8 ms, so at most about 209 tokens per second on an H100, while its tensor cores sit idle 99.7% of the time derived. Measured on this laptop's GPU, one 8,192 × 8,192 fp16 linear layer (134 MB of weights) took 0.80 ms at batch 1, reading weights at 168 GB/s, the memory's full speed, and 64 times the arithmetic at batch 64 took only 3.52 ms measured here: batching is how serving turns bandwidth-bound decode into compute-bound work (for this 8B model on an H100 the {{Performance calculator|#t-calc}} puts the crossover around batch 308 at short context). What it decides for training. Capacity decides how the step is split: 128.5 GB of state does not fit one 80 GB H100, so it is sharded (ZeRO, FSDP on {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}}) or activations are recomputed. Bandwidth sets the speed of everything that is not a big matmul, including the optimizer update, which reads and writes every byte of state once per step. Serving adds the KV cache, 128 KiB per token for this model, whose sizing is {{Long context|n:3fd5c17b0d0d81059ee1ce20c0326dc5}}'s.
