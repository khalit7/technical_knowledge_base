The model is Llama 3.1 8B, an ordinary dense transformer with 8,030,261,248 parameters (32 layers, hidden size 4,096, 8 key-value heads, vocabulary 128,256; counted from its config.json, an open mirror of Meta's gated repository). One step processes a batch of 64 sequences of 8,192 tokens, 524,288 tokens in all illustrative batch, the same step the Performance calculator animates. Before any chip is named, ask what that step needs. There are only three things.

Arithmetic
2.53 × 1016 FLOPs

6 × parameters × tokens: each weight does one multiply and one add per token going forward, and about twice that going backward (the 6ND rule; section 5 says when it is wrong).

Bytes in memory
128.5 GB of state

16 bytes per parameter for mixed-precision Adam (bf16 weights and gradients, fp32 master copy and two Adam moments), before activations; about 165 GB with them (the Performance calculator's count). One H100 holds 80 GB.

Bytes on the wire
16.06 GB of gradients

If the step is split across GPUs, every GPU must end up with the sum of everyone's bf16 gradients, every step (section 6).

Every piece of hardware on this page exists to serve one of those three columns: arithmetic units for the first, memory for the second, links between chips for the third. How fast a step runs is set by whichever of the three is slowest, and the art is to arrange the work so that it is the arithmetic. 1. Why GPUs: throughput against latency

The problem. Almost all of the step's 2.5 × 1016 FLOPs are matrix multiplications: every layer multiplies a block of activations (tokens by 4,096) by a weight matrix. A matrix multiply has three properties that decide what hardware should run it. It is huge (billions of independent multiply-adds), regular (the same operation on every element, no branches that depend on the data) and predictable (you know every address you will touch before you start). A fused multiply-add (FMA), a × b + c in one instruction, is the unit of work; one FMA counts as 2 FLOPs.

A CPU core is built for the opposite case: one stream of instructions full of branches and pointer chasing, which must finish as soon as possible. Most of its transistors go to guessing (branch prediction, speculative and out-of-order execution) and to big caches that hide memory latency, so a single thread runs fast. Its arithmetic is a small part: an M1 Pro performance core has 4 floating-point units, each working on 4 fp32 numbers at once (a 128-bit SIMD register), so 16 FMAs per cycle, 32 FLOPs per cycle, about 102 GFLOP/s at 3.2 GHz. The C++ page measured 97.5 GFLOP/s on this laptop measured here.

A GPU core drops the guessing. It runs thousands of threads in groups that execute the same instruction together, and spends its transistors on arithmetic lanes and registers. When one group waits for memory, the core simply switches to another group that is ready, so it hides latency with parallel work rather than with caches and prediction. One M1 Pro GPU core has 128 fp32 lanes at 1.296 GHz (metal-benchmarks independent); NVIDIA calls its equivalent a streaming multiprocessor (SM), and an H100 SM also has 128 fp32 lanes (NVIDIA Hopper in depth vendor spec) plus four tensor cores: units that do a whole small matrix multiply per instruction instead of one FMA per lane (section 2).

Each square is a 4 × 4 block of the 64 × 64 output; a block turns solid when its 1,024 FMAs are done. Cycles are FMAs per cycle from the specs; times divide by each engine's clock. The H100 clock, 1.83 GHz, is derived from its 989.5 TFLOPS dense BF16 figure: 989.5 × 1012 / (132 SMs × 4,096 FLOPs per cycle). The tensor-core rate per SM is the A100 SM's 1,024 dense FP16 FMAs per clock (A100 whitepaper) doubled for Hopper, which agrees with How To Scale Your Model's GPU chapter (1,024 bf16 FLOPs per cycle per tensor core). What it shows. One GPU core does 8 times the work per cycle of a CPU core; at its lower clock it still finishes this tile about 3 times sooner. The tensor cores do 16 times the work per cycle of the same SM's ordinary lanes. On the whole M1 Pro chip, with the same memory and the same power budget, the 8 CPU threads peaked at 562 GFLOP/s and the 16 GPU cores at 5,008 GFLOP/s measured here, a factor of 8.9. An H100 has 132 SMs with tensor cores: 989.5 TFLOPS dense BF16, about 200 times this laptop's GPU.

The cost
A GPU thread is slow and a GPU is bad at anything sequential or branchy. The CPU does not go away in training: it runs Python, launches every kernel, decodes and shuffles data, and drives the network. A data loader that cannot keep up, or a training loop that launches thousands of tiny kernels, leaves the GPU idle no matter how fast it is (section 10's symptom table).

The third answer, the TPU. Google's TPU keeps neither many threads nor big caches. Its core is a systolic array: a grid of multiply-accumulate cells (128 × 128 on most generations, 256 × 256 on v6e, per How To Scale Your Model) where the weights are loaded once and stay put while activations flow through from one side and partial sums flow out the other, cell to neighbouring cell, like blood pumped through a heart. Each operand is read from memory once and used hundreds of times without touching a register file, which is where a GPU spends much of its energy. The price is flexibility: a TPU is programmed through a compiler (XLA) that schedules everything ahead of time, and anything that is not a big dense matrix multiply runs on a much slower vector unit.

Predict: an M1 Pro GPU core runs at 1.296 GHz, a CPU performance core at 3.2 GHz. Per second, how much more fp32 FMA work does one GPU core do than one CPU core?
About 3 times: 128 lanes × 1.296 GHz against 16 lanes × 3.2 GHz is 166 against 51 billion FMAs per second (3.2×). Measured: 313 against 97.5 GFLOP/s (3.2×). Width beats clock; the GPU then multiplies it by having many cores.

2. Inside a GPU: SMs, warps, tensor cores, registers, caches

The problem. The step must keep tens of thousands of arithmetic lanes fed every cycle while memory takes hundreds of cycles to answer. The GPU's whole layout follows from that. The H100 is the reference here because most published training numbers were measured on it; Blackwell's changes come after.

SMThe building block. H100 SXM enables 132 of the 144 on its die (the spare ones absorb manufacturing defects). Each SM has 4 sub-partitions, each with a warp scheduler, 32 fp32 lanes, a 64 KB slice of the register file and one tensor core.
Warp32 threads that share one instruction pointer: the scheduler issues one instruction for all 32 at once (SIMT, single instruction, multiple threads). If threads in a warp take different branches, the two paths run one after the other.
Register file256 KB per SM, 64K 32-bit registers, the largest and fastest memory on the chip: 33.8 MB across 132 SMs derived. Every resident thread keeps its registers there, which is what makes switching warps free.
Shared memory and L1256 KB per SM, of which up to 228 KB can be shared memory: a scratchpad the program fills by hand so a block of threads can reuse a tile of data. Matmul and attention kernels live or die by it.
L2 cache50 MB shared by all SMs, between the SMs and HBM.
HBM80 GB in 5 stacks of stacked DRAM beside the die, 3.35 TB/s (section 3).

Sources: NVIDIA Hopper in depth (SM counts, 128 fp32 lanes and 4 tensor cores per SM, 256 KB L1, 50 MB L2), Hopper tuning guide (64 resident warps per SM, 64K registers, 228 KB shared memory), How To Scale Your Model, GPUs (sub-partitions), H100 product page (80 GB, 3.35 TB/s). vendor spec

How latency is hidden. An SM keeps up to 64 warps (2,048 threads) resident at once, all with their registers in place. Every cycle, each sub-partition's scheduler picks a warp whose next instruction has its inputs ready and issues it. A load from HBM takes hundreds of cycles; while one warp waits, others compute. So a GPU needs far more threads in flight than it has lanes. The fraction of the 64 warp slots actually filled is called occupancy; it falls when each thread needs many registers or a block needs much shared memory, because those are shared by everyone resident. The CPU hides the same latency with caches and speculation; the GPU hides it with parallel work, which only exists if the batch is big enough.

Tensor cores, generation by generation. A tensor core takes small tiles of two matrices and returns their product added to an accumulator, in one instruction issued for a whole warp (or group of warps). Each generation made the tiles larger and the formats smaller:

When it matters for training. Peak FLOPS are tensor-core FLOPS. A step reaches them only when its matmuls are large enough to fill all 132 SMs with tiles, when the data arrives in shared memory in time (TMA, deep pipelines), and when the shapes suit the tensor cores (dimensions that are multiples of 8 or 16 are the usual advice in NVIDIA's matrix multiplication performance guide). Everything that is not a matmul (normalisation, softmax, activation functions, the optimizer update) runs on the ordinary lanes, a sixteenth of the tensor-core rate in fp32, and is usually limited by memory anyway (section 5).

How to check. nvidia-smi "utilization" only says that some kernel was running, not how much of the chip it used. The profiler's tensor-pipe utilisation and achieved occupancy per kernel are the real numbers (Topic: cuda-and-gpu-programming covers Nsight).

3. Memory: capacity against bandwidth

The problem. The step's state is 128.5 GB, and every layer's weights, activations and gradients must travel from memory to the SMs and back, several times per step. Memory has two numbers and they pull against each other: capacity (how much fits) and bandwidth (how many bytes per second reach the chip). Fast memory is small and expensive per byte; big memory is slow.

Two kinds of cell. SRAM stores a bit in a few transistors on the processor die itself: registers, shared memory, caches. It answers in a few cycles but takes a lot of area, so an H100 has about 120 MB of it in total (registers, L1 and L2 from section 2). DRAM stores a bit as charge in one transistor and a capacitor, on separate chips: dense and cheap, but every access crosses wires off the die. All the gigabytes are DRAM; the differences between GPUs come from how the DRAM is packaged.

HBM (high-bandwidth memory)DRAM dies stacked on top of each other beside the GPU die on a silicon interposer: a very wide, modestly clocked bus (1,024 bits per stack for HBM3 and HBM3e, 2,048 for HBM4). H100 SXM: 80 GB in 5 HBM3 stacks, 3.35 TB/s. B200: 180 to 192 GB of HBM3e, 8 TB/s.
GDDR7Separate chips soldered around the GPU on the board: a narrower bus clocked very fast. RTX 5090: a 512-bit bus at 28 Gbps per pin, 1.79 TB/s, 32 GB.
LPDDR5Low-power DRAM in the same package as the processor, shared by CPU and GPU. Apple M1 Pro (this laptop): 16 GB here, 200 GB/s published, 165 GB/s measured.
On-chip SRAM onlyNo DRAM for the model at all: the weights are spread over the SRAM of many chips. Groq 3 LPX rack announced: 256 chips, 128 GB of SRAM and 40 PB/s per rack.

Sources: per-stack interface widths and rates from Rambus on HBM (HBM3 819 GB/s, HBM3e 1,229 GB/s, HBM4 2,048 GB/s per stack); H100, DGX B200, RTX Blackwell whitepaper (512 bits × 28 Gbps / 8 = 1,792 GB/s), Apple M1 Pro, Groq vendor spec; the 165 GB/s stream copy is from the Roofline lab measured here. B200 capacity is 180 GB per GPU in DGX and HGX B200 and 186 to 192 GB in other listings; the Chip atlas keeps each SKU apart.

Why decode waits on bytes

Generating one token at batch 1 multiplies a single activation vector by every weight matrix. Each 2-byte bf16 weight is fetched from memory to be used in exactly one FMA (2 FLOPs): 1 FLOP per byte. An H100 can do 295 FLOPs in the time it fetches one byte (section 5), so the tensor cores sit idle 99.7% of the time and the time per token is simply bytes of weights / bandwidth. Llama 3.1 8B in bf16: 16.06 GB of weights read once per token, 33 blocks (32 layers and the output head), batch 1, short context so the KV cache is negligible. Time = bytes / bandwidth derived, a ceiling on tokens per second; real servers land below it (kernel overheads, the KV cache, other work). The laptop's 16 GB could not actually hold these weights beside the OS; its row is what the measured bandwidth implies.

Measured on this laptop. The Roofline lab timed one 8,192 × 8,192 fp16 linear layer (134 MB of weights) on the M1 Pro GPU: 0.80 ms at batch 1, reading weights at 168 GB/s, the memory's full speed; at batch 64, 64 times the arithmetic took only 3.52 ms, because the same bytes now feed 64 FMAs each measured here. Batching is how servers turn a bandwidth-bound decode into compute-bound work, and it is why a training step, with half a million tokens per batch, is compute-bound. For this 8B model in BF16 on an H100 the Performance calculator finds decode turns compute-bound only around batch 308 at short context, and that at 4,096 tokens of context batch 64 gives 21 times the throughput of batch 1, not 64, because every sequence's KV cache must still be read.

Full-memory reads per second

Bandwidth divided by capacity: how many times per second a chip can read its whole memory. A model that fills the memory cannot decode faster than this many tokens per second at batch 1, whatever the FLOPS.

The KV cache is the other bytes. During generation every past token's attention keys and values are kept and read again for each new token. For this model: 2 (keys and values) × 32 layers × 8 KV heads × 128 dimensions × 2 bytes = 128 KiB per token, so one 8,192-token sequence holds 1.07 GB derived, read in full for every token it generates. At long context or high batch the cache, not the weights, fills memory; that is why grouped-query attention (8 KV heads instead of 32) exists and why serving quantises the cache.

The cost
HBM gives bandwidth and fairly large capacity but needs stacked dies and an interposer beside the GPU, which makes it the expensive part of a datacenter accelerator; GDDR is cheaper but tops out at 32 GB on a consumer card; SRAM-only designs need hundreds of chips to hold one model. No memory gives both capacity and bandwidth cheaply.

When it matters for training. Capacity decides how the step must be split: 128.5 GB of state does not fit on one 80 GB H100, so it is sharded across GPUs (ZeRO or FSDP, on Distributed Training), or activations are recomputed instead of stored. Bandwidth decides the speed of everything that is not a big matmul: normalisation, activation functions, softmax, and the optimizer update, which reads and writes every byte of state once per step. How to check: torch.cuda.max_memory_allocated() for capacity; for bandwidth, a kernel's achieved bytes per second in the profiler against the chip's figure.

4. Numbers: formats and what the silicon accelerates

The problem. Every byte saved per number is saved three times: in memory capacity, in bandwidth, and (when the tensor cores support the format) in arithmetic, because a multiplier for 8-bit numbers is much smaller than one for 16-bit numbers, so more of them fit in the same area. Halving the bits roughly doubles the peak FLOPS. The catch is accuracy: fewer bits mean less range (how large and small a number can be) and less precision (how finely values are spaced).

FormatBits: sign, exponent, mantissaWhere it is used in training
FP321, 8, 23Master weights and optimizer states; accumulators inside the tensor cores
TF321, 8, 10NVIDIA's tensor-core mode for fp32 inputs (Ampere on): fp32 range, BF16-like precision, stored as 32 bits
BF161, 8, 7The default for weights, activations and gradients: fp32's range, so no loss scaling needed
FP161, 5, 10More precision, much less range; needs loss scaling to keep small gradients from flushing to zero
FP8 (E4M3, E5M2)1, 4, 3 and 1, 5, 2Matmul inputs in FP8 training (Hopper on), with a scale per tensor or per block
FP6 (E3M2, E2M3), FP4 (E2M1)6 and 4 bitsMostly inference and quantised weights (Blackwell, MI355X); FP4 training is research

Block scaling. An 8-, 6- or 4-bit number cannot cover the spread of values in a whole tensor, so the newest formats give each small block of values its own scale factor. The OCP MX formats (MXFP8, MXFP6, MXFP4, MXINT8) share one 8-bit power-of-two scale (E8M0) per block of 32 values (OCP MX spec v1.0, Sep 2023). NVIDIA's NVFP4 uses blocks of 16 with an FP8 (E4M3) scale, plus one FP32 scale per tensor (NVIDIA, Jun 24 2025). The scales cost bits: MXFP4 stores 4 + 8/32 = 4.25 bits per value, NVFP4 4 + 8/16 = 4.5 derived. Blackwell's tensor cores apply the scales in hardware, inside the multiply.

What it shows. A chip only gets faster at a format it has silicon for: the A100 has no FP8 path, the H100 no FP4, TPU v6e lists no FP8 figure, and on those chips the smaller format saves memory but not arithmetic. Within a chip each halving doubles the peak (H100: 989.5 BF16, 1,979 FP8; B200: 2,250, 4,500, 9,000). And consumer cards are half-rate where training lives: the RTX 5090 does 419 TFLOPS of FP16 with FP16 accumulation but 209.5 with the FP32 accumulation that training needs (RTX Blackwell whitepaper, Appendix A).

The cost
Lower precision is not free accuracy-wise: FP8 training needs careful scaling (per tensor or per block) and keeps the master weights, the optimizer and the accumulation in higher precision. Published large runs show both choices: Llama 3 405B reported its throughput in BF16 (Llama 3, Table 4), DeepSeek-V3 trained with an FP8 mixed-precision framework (DeepSeek-V3 report).

How to check. The format of a matmul is decided by its input dtypes (torch.autocast, or the FP8 recipe of a library such as Transformer Engine); a run that is unexpectedly slow on a new GPU is often doing its matmuls in a format the tensor cores do not accelerate, or in fp32.

5. The roofline and MFU: which column limits you

The problem. Sections 1 to 3 gave each chip two speeds: how fast it computes and how fast it reads memory. A given operation needs a certain number of FLOPs per byte it moves; that number decides which of the two speeds it runs at. This is the most useful single idea on the page.

time ≈ max( FLOPs / peak FLOP/s , bytes / bandwidth )
AI
Arithmetic intensity: FLOPs performed per byte moved to or from memory, a property of the operation and its shapes
ridge
peak FLOP/s divided by bandwidth: the intensity at which the two terms are equal. Below it the operation is memory-bound, above it compute-bound

Plotting attainable FLOP/s against intensity gives a sloped line (bandwidth) that meets a flat line (peak) at the ridge: the roofline. Ridge points, dense, in FLOPs per byte derived:

Peaks and bandwidths as in sections 3 and 4 (A100 SXM 80 GB: 312 TFLOPS BF16, 2,039 GB/s, NVIDIA A100). The M1 Pro point uses the measured fp16 peak (5.06 TFLOP/s) and stream copy (165 GB/s) from the Roofline lab.

Where real operations land. Multiplying activations of shape (tokens × 4,096) by a 4,096 × 4,096 bf16 weight does 2 × tokens × 4,0962 FLOPs and moves the 32 MB weight once, plus the activations. When the number of tokens is small next to 4,096, the intensity is about equal to the number of tokens. So the batch is the intensity: decode at batch 1 sits at 1 FLOP per byte, a training step with 8,192 tokens per sequence sits in the thousands, far right of every ridge. Elementwise operations (adding a residual, an activation function, a normalisation) do a few FLOPs per element they read and write: below 1, memory-bound on every chip ever made; that is why they are fused into neighbouring kernels (torch.compile, FlashAttention). A third regime exists: overhead-bound, when the GPU waits on Python and kernel launches and neither term explains the time.

Correction to the old page
The old notes said the ridge "rises every generation". At BF16 it doubled from A100 (153) to H100 (295) and then fell slightly on B200 (281), because Blackwell grew bandwidth (3.35 to 8 TB/s) as fast as BF16 FLOPS. It keeps rising only if you move to the new formats: B200 at FP8 is 562.5, at FP4 1,125. Running in lower precision makes an operation more compute-hungry relative to its bytes, which is why low precision and big batches go together.

The Roofline lab measured this on the M1 Pro GPU: peak FMA 5.01 TFLOP/s (fp32) and 5.06 (fp16, the same ALUs: no tensor cores), copy bandwidth 165 GB/s, ridge 30.7; an 8,192 × 8,192 fp16 linear layer at batch 1 ran at 168 GB/s (memory-bound, on the roof) and at batch 64 reached 2.4 TFLOP/s; a naive, a tiled and the library matmul reached 351, 640 and 4,070 GFLOP/s at the same intensity measured here. That last row is the gap the roofline cannot see: a kernel can sit far under the roof because it is badly written. Pick any chip, precision and shape there.

Model FLOPs utilisation is the fraction of the hardware's peak that does useful model arithmetic. Counting recomputed FLOPs too gives hardware FLOPs utilisation (HFU), which flatters. Llama 3 405B on 16,384 H100s reported 400 TFLOP/s per GPU and 41% MFU; 400 / 989.5 = 40.4% recomputed, consistent with the printed figure after rounding. On 8,192 GPUs it reported 43%, and 38% at 131,072-token sequences (Llama 3, Table 4). Around 40% is what a very well tuned dense run at scale reaches; the rest goes to communication that does not overlap, memory-bound operations, pipeline bubbles and failures.

Our step. At 40% MFU, the step's 2.53 × 1016 FLOPs take 64 s of arithmetic on one H100, 8.0 s on 8 and 1.0 s on 64 derived. The Performance calculator adds memory traffic and communication: 8.7 s on 8 GPUs, 1.17 s on 64 with hybrid sharding (34% MFU), 1.95 s with flat FSDP across all 64 (20%). The difference is the network (section 6).

6. Joining chips: why the network picks your parallelism

The problem. The step's state (128.5 GB) does not fit one GPU and its arithmetic would take 64 s on one, so it is split across many. Whatever way it is split, the GPUs must exchange data: at least the gradients, 16.06 GB per step. The links between chips are a hierarchy, each level roughly an order of magnitude slower than the one above, and which kind of parallelism you can afford depends on which level its traffic crosses.

Memory: one chipHBM3 / HBM3e: 3.35 / 8 TB/s.
Scale-up: one server or rackNVLink 4 (H100) / NVLink 5 (Blackwell) through NVSwitch chips: 450 / 900 GB/s per GPU each way. 8 GPUs in an HGX server; 72 in a GB200 or GB300 NVL72 rack.
Host link: one serverPCIe 5.0 x16, about 64 GB/s each way: CPU to GPU, NIC to GPU, and between consumer cards.
Scale-out: thousands of serversInfiniBand NDR (400 Gb/s) or RoCE Ethernet, one NIC per GPU: 50 GB/s each way; XDR is 800 Gb/s.

Vendor figures are usually both directions added: NVLink 4 is "900 GB/s total" (Hopper in depth), NVLink 5 "1.8 TB/s" per GPU and 130 TB/s across an NVL72 (Blackwell); halved here to one direction. InfiniBand: Quantum-X800 (800 Gb/s ports); an AWS p5 server has 3,200 Gb/s of network for 8 H100s, 400 Gb/s per GPU (AWS p5). PCIe 5.0 runs 32 GT/s per lane, about 63 GB/s per direction on 16 lanes after encoding derived. vendor spec

The two kinds of fabric. Scale-up links (NVLink with NVSwitch, AMD Infinity Fabric, Google's ICI) join a small group of chips so closely that they can read each other's memory at hundreds of GB/s; the group is called the NVLink domain. Scale-out links (InfiniBand, or RoCE: RDMA over Ethernet) join servers through network switches; slower, but they reach tens of thousands of GPUs. Both use RDMA: the network card writes straight into another machine's GPU memory without either CPU copying it. InfiniBand has lossless, credit-based flow control built in; RoCE needs lossless Ethernet configured (PFC, ECN) and is cheaper and multi-vendor; Llama 3 trained on RoCE at 400 Gb/s per GPU, in a three-layer network of 24K GPUs (Llama 3 report).

The same all-reduce, inside and outside the NVLink domain

An all-reduce leaves every GPU with the sum of everyone's data: data-parallel training does one on the gradients every step. The usual ring algorithm splits the data into N chunks and passes them around a ring of the N GPUs: N−1 steps where chunks are added (a reduce-scatter), then N−1 steps where the finished sums are passed on (an all-gather). Each GPU sends 2(N−1)/N times the data, whatever N is, so the time is that volume divided by one link's bandwidth.

The 8B's bf16 gradients, 16.06 GB, all-reduced over 8 H100s: 2 × 7/8 × 16.06 GB = 28.1 GB sent per GPU, at 450 GB/s (NVLink 4, one direction) or 50 GB/s (one 400 Gb/s NIC per GPU) derived, ignoring latency and assuming the link is the only limit. Real collectives reach somewhat less; NCCL picks rings, trees or in-switch reduction (SHARP) by size and topology.

Why the network picks your parallelism. With 8 GPUs at 40% MFU the step's arithmetic takes 8.0 s, so even the InfiniBand all-reduce (0.56 s) is small, and it can overlap with the backward pass: data parallelism tolerates the slow network. Tensor parallelism is different. It splits each layer's matrices across GPUs, so the GPUs must all-reduce activations twice per layer going forward and twice going back. That traffic sits on the critical path between layers, and it scales with the activations, not the parameters. The Performance calculator works it for Llama 3.1 70B with 8-way tensor parallelism at 8,192 tokens: the all-reduces cost 16% of the layer's compute time over NVLink, but 141% over a 400 Gb/s NIC, so the GPUs would spend more time waiting than computing. So: tensor (and expert) parallelism stays inside the NVLink domain; pipeline and data parallelism cross servers.

Two real runs that show the rule
  • Llama 3 405B used tensor parallelism of 8, exactly one 8-GPU server, in every configuration, with pipeline (16), context and data parallelism across servers (Llama 3, Table 4).
  • DeepSeek-V3 trained on 2,048 H800s with NVLink at 160 GB/s and InfiniBand at 50 GB/s (as the report gives them), and avoided "costly Tensor Parallelism" entirely, using 16-way pipeline, 64-way expert parallelism across 8 nodes and ZeRO-1 data parallelism; its all-to-all kernels needed only 20 SMs to saturate both links (DeepSeek-V3 report).

Racks and TPU pods. The NVL72 rack exists to make the NVLink domain 72 GPUs instead of 8, so tensor and expert parallelism (and giant mixture-of-experts models) can span a rack. Google's TPUs take another route: each chip links directly to its neighbours over ICI in a 2D or 3D torus (a grid whose edges wrap around), with no switches between chips, and optical circuit switches (mirrors that redirect light) reconfigure how 64-chip cubes connect; in TPU v4 they were under 5% of system cost and 3% of its power (TPU v4 paper). An Ironwood pod joins 9,216 chips, each with 1.2 TB/s of ICI (both directions) (Google, Apr 2025). A torus is excellent for ring collectives between neighbours and slower for arbitrary point-to-point traffic, which is why TPU programs are written as shardings over a device mesh.

Predict: two RTX 5090s in one workstation have no NVLink, only PCIe 5.0 (about 64 GB/s each way). How long does the ring all-reduce of the 8B's 16.06 GB of gradients take between them?
With N = 2 each GPU sends 2 × 1/2 × 16.06 = 16.06 GB; at 64 GB/s that is 251 ms derived. Workable for data parallelism with a long step; tensor parallelism across PCIe pays the same price on every layer, which is why it rarely helps on consumer pairs. (The 5090 also cannot hold this model's 128.5 GB of training state: 32 GB each.)

8. Power, cooling, reliability

Watts per chip keep rising. A100 400 W, H100 700 W, Blackwell up to 1,200 W and Blackwell Ultra 1,400 W per GPU (NVIDIA, Aug 22 2025), MI355X 1,400 W, and AMD's announced MI455X up to 2,500 W. Megawatts per cluster. A full 9,216-chip Ironwood pod spans "nearly 10 MW" (same Google post). Reliability is a hardware number too. 9. Choosing and costing hardware for a job

Five lines of arithmetic before you rent anything, each from a section above:

  1. Memory (section 3): bytes of state (16 per parameter for mixed-precision Adam, 2 per parameter for bf16 inference, plus activations or KV cache). Does it fit one GPU, one server, or does it need sharding?
  2. Compute (section 5): 6 × parameters × tokens, divided by chips × dense peak × an assumed MFU (30 to 40% for a tuned dense run) gives the wall-clock time.
  3. Roofline (section 5): is the batch per GPU large enough to be compute-bound? Decode at small batch is bandwidth-bound: tokens per second ≈ bandwidth / bytes per token.
  4. Communication (section 6): bytes per step for each kind of parallelism against the link it crosses. Tensor and expert parallelism must fit inside the NVLink domain.
  5. Cost: chip-hours × price, with the price's date and terms.

10. Interview questions, a symptom table, and what the child pages will cover

Interview questions, short answers

Why is LLM decode memory-bound and training compute-bound?
Arithmetic intensity is about the number of tokens that share each weight read. Decode at batch 1 uses each 2-byte weight for one FMA, about 1 FLOP per byte, far below an H100's ridge of 295; a training step has thousands of tokens per weight read, far above it (section 5).
Estimate the batch-1 decode speed of an 8B bf16 model on one H100.
16 GB of weights per token at 3.35 TB/s: 4.8 ms, so at most about 209 tokens per second, before the KV cache and overheads (section 3).
How much memory does full fine-tuning of a 7 to 8B model need?
About 16 bytes per parameter for mixed-precision Adam (bf16 weights and gradients, fp32 master weights and two moments), so about 128 GB for 8B, plus activations: more than one 80 GB GPU, so shard (ZeRO, FSDP) or use LoRA.
What is MFU and what is a good value?
Useful model FLOPs per second (6N × tokens per second) over the chips' dense peak. About 40% is very good for a large dense run at scale (Llama 3 405B: 38 to 43%); under 20% points to a bottleneck. HFU also counts recomputation and is higher.
Why does tensor parallelism stay inside a node?
It all-reduces activations twice per layer forward and twice backward, on the critical path. For a 70B model with 8-way tensor parallelism that costs 16% of the compute time over NVLink and 141% over a 400 Gb/s NIC (section 6, from the Performance calculator).
What does a ring all-reduce cost?
Each GPU sends 2(N−1)/N times the data (a reduce-scatter then an all-gather), so time ≈ 2S / link bandwidth for large N, independent of N apart from latency.
What did Hopper and Blackwell add to the tensor core, physically?
Hopper: FP8, a per-SM copy engine for tiles (TMA), warpgroup-wide asynchronous matrix multiplies, clusters of SMs sharing shared memory. Blackwell: FP6, FP4 and block-scaled formats, 256 KB of tensor memory per SM for accumulators, two dies acting as one GPU.
GPU or TPU: what is the real difference?
Thousands of threads hiding latency with parallelism and caches, programmable at the kernel level, against large systolic arrays scheduled by a compiler with software-managed on-chip memory and switchless torus pods. Per-chip peaks are now comparable; the differences are flexibility, ecosystem, pod scale and price.
Why do vendors quote sparse FLOPS, and what should you use?
2:4 structured sparsity doubles the tensor-core rate if half of every four weights are zero. Dense training and most inference do not use it, so compare dense figures on both sides.
An H100 run is slow on B200s. What do you check first?
Whether the software uses the new hardware: kernels built for the new architecture, the matmul formats (FP8, FP4 paths), larger batches to stay above a ridge that did not move at BF16, and whether communication, not compute, became the limit.

Four questions to ask of any spec sheet

  2. Which number format, and which accumulator? A chip does 2x the operations per second in FP8 as in BF16 and often 2x again in FP4. GeForce cards also halve their BF16 rate when the running sum is kept in FP32, which is what training does. Compare at the same format.

Words used here. FLOPS: floating-point operations per second (one multiply-add counts as two). TFLOPS = 1012, PFLOPS = 1015. HBM (high-bandwidth memory): DRAM stacked next to the chip, wide and fast; GDDR: the cheaper memory on gaming cards; SRAM: memory on the chip itself, fastest and smallest. Bandwidth: bytes per second between memory and chip. Interview questions

Why can two chips with the same TFLOPS train at very different speeds?
Because a training step is not one big matmul. Attention, normalisation, optimizer updates and every elementwise op are limited by memory bandwidth; the gradient all-reduce is limited by the link between chips. H100 and H200 have identical compute, yet H200's 43% more bandwidth and 76% more memory make it faster on anything memory-bound and let it fit larger batches. Ask for bandwidth, memory and link bandwidth, not only FLOPS.
What does "1,979 TFLOPS BF16" on the H100 page mean, and what will you get?
It is the 2:4 structured-sparsity figure. Dense BF16 peak is 989.5. SemiAnalysis measured about 720 TFLOP/s on large BF16 GEMMs (73% of dense peak), and a whole training step reaches less, because attention, normalisation and communication run below the matmul rate. The share of dense peak a whole step achieves is MFU (model FLOPs utilisation); the Roofline lab measures it on a real GPU and the Performance calculator uses it.
Why do NVL72 racks matter for training and inference?
Because they make 72 GPUs one scale-up domain: every GPU reaches every other at 1.8 TB/s (900 GB/s each way) through NVLink switches. Tensor and expert parallelism, which exchange activations several times per layer, need that bandwidth; on an 8-GPU server they must stop at 8 GPUs, and anything larger crosses the scale-out network at 400 Gb/s (DGX B200) or 800 Gb/s (DGX B300) per GPU, that is 50 to 100 GB/s each way: 9 to 18 times slower. The TPU answer is the same idea at pod scale: 9,216 TPU7x chips on one ICI network.
Which chip would you pick to serve a 70B model at low latency, and why not the one with the most FLOPS?
Decoding at small batch reads every weight once per token, so time per token is about weight bytes divided by bandwidth: 70 GB in FP8 on one H200 (4.8 TB/s) is at least about 15 ms per token, on one B200 (8 TB/s) about 9 ms. FLOPS barely matter at batch 1; bandwidth and capacity (the weights plus the KV cache must fit) decide. SRAM-only designs (Groq, Cerebras) attack exactly this, at the cost of spreading a large model over many chips.
A vendor quotes FP4 PFLOPS. When does that number apply to you?
Only when your matmuls run in FP4 with block scaling (NVFP4 or MXFP4), which today means mostly inference of quantized models and some experimental training recipes. BF16 training uses the BF16 rate, which grew far less (B200 to B300: no change in BF16, 1.5x in FP4). Read the BF16 and FP8 rows for training.

    The terms, in one screen

    Parameters N, tokens D

    N is the number of learned numbers in the model (8.03 billion for Llama 3.1 8B). D is how many tokens (word pieces) it trains on. For a mixture-of-experts (MoE) model, only some experts run per token: the active parameters set the compute, the total set the memory.

    FLOPs and 6ND

    A FLOP is one floating-point add or multiply. Each weight does one multiply and one add per token going forward (2 FLOPs) and about twice that going backward (4), so training costs about 6 N D FLOPs and generating one token about 2 N.

    Peak, MFU

    A chip's peak is its datasheet FLOP/s at a given precision (dense, no sparsity). MFU, model FLOPs utilisation, is the useful FLOPs a run actually achieved divided by that peak. 35 to 45% is good for large dense training.

    Memory capacity, bandwidth

    Capacity (GB) decides what fits on the chip; bandwidth (TB/s) decides how fast it can be read. An H100 SXM has 80 GB of HBM (stacked memory next to the chip) read at 3.35 TB/s.

    KV cache, prefill, decode

    While generating, a model keeps every past token's attention keys and values: the KV cache. Prefill processes the whole prompt at once (lots of maths per byte); decode then makes one token per step, rereading all weights and the cache each time (little maths per byte).

    All-reduce, NVLink, InfiniBand

    An all-reduce sums a tensor across GPUs so each ends with the total (how gradients are averaged). Inside a server GPUs talk over NVLink (450 GB/s each way per H100); between servers over InfiniBand or Ethernet NICs, typically 400 Gb/s = 50 GB/s per GPU.

    Inference: memory, speed, and where decode stops being memory-bound

    Serving has two phases. Prefill runs the prompt through the model in one big batch of tokens: compute-bound, so its time is FLOPs over peak. Decode then makes one token per sequence per step, and every step must read all the weights it uses plus every sequence's KV cache from memory: at small batch it is memory-bound, so its time is bytes over bandwidth.

    Why the batch is your arithmetic intensity
    At batch 1 each weight read from memory is used for one multiply-add: 2 FLOPs per 2 bytes in BF16, 1 FLOP per byte. An H100 can do 295 FLOPs in the time it reads one byte (989.5 TFLOP/s over 3.35 TB/s), so its tensor cores sit idle over 99% of the time. Batch B reuses each weight B times, so with a short context decode becomes compute-bound only near B = 295 (the chart shows the exact crossover). The KV cache does not share: each sequence reads its own, so at long context the cache, not the weights, dominates, and adding sequences never makes decode compute-bound. That is why grouped-query attention (fewer KV heads), DeepSeek's latent attention (MLA) and FP8 KV caches exist.
    Go deeper: batching schedulers, paged KV caches and speculative decoding are the inference-and-serving topic; low-bit formats are the Quantization and Precision page.

    Communication: the same bytes over NVLink and over the network

    A ring all-reduce over n GPUs sends each GPU's data around the ring twice (once to sum, once to share the sum), so each GPU moves 2(n−1)/n times the tensor and the time is set by the slowest link: t = 2(n−1)/n × S / B, the bus-bandwidth model of NCCL's tests. Reduce-scatter and all-gather each move (n−1)/n.

    Why tensor parallelism stays inside the NVLink domain

    Data parallelism exchanges gradients once per step. Tensor parallelism (Megatron-style: each layer's matrices split across GPUs) must all-reduce the layer's activations four times per layer per micro-batch (twice forward, twice backward), on the critical path. Its traffic per token is about 16 h bytes per layer against about 6 × 12h²/TP FLOPs of compute, so the ratio does not depend on batch: only a fast link keeps it small.

    Roofline lab

    Every kernel a GPU runs is limited by one of two things: how fast the chip can do arithmetic, or how fast it can bring the numbers in from memory. The roofline is a one-line picture that tells you which, before you profile anything. This tab measures a real roofline on a real GPU (the 16-core GPU of an Apple M1 Pro laptop, the only GPU available here), places real measured kernels on it, then places the same operations on the published rooflines of datacenter chips.

    What was measured and what was not
    Every green dot and every number marked measured was run on the Apple M1 Pro GPU on through MLX (three full runs of seven timed trials each; laptop shared with other jobs, load average ). Nothing was run on an NVIDIA, AMD or Google chip: their roofs are vendor specifications, dated and linked, and ops are placed on them by computed arithmetic intensity. Vendor peaks are ceilings nobody reaches; the M1 Pro section shows by how much a real chip falls short of its own.

    The idea in one picture

    Three terms, then one formula.

    • FLOP: one floating-point add or multiply. A fused multiply-add (FMA, a*b+c in one instruction) counts as 2. FLOP/s is how many per second; the chip's peak is its maximum, set by the number of arithmetic units times the clock.
    • Memory bandwidth: bytes per second the chip can move between its main memory (HBM on datacenter GPUs, GDDR on gaming cards, LPDDR on the M1) and its compute units.
    • Arithmetic intensity (AI): FLOPs an operation does per byte it moves to and from main memory. Adding two vectors does 1 FLOP per 12 bytes (read 4, read 4, write 4 in fp32): AI = 0.083. Multiplying two big matrices reuses every number loaded hundreds of times: AI in the hundreds.
    attainable FLOP/s = min( peak FLOP/s , AI × bandwidth )
    AI
    FLOPs ÷ bytes moved (a property of the operation and its shape, not of the chip)
    ridge
    peak ÷ bandwidth: the AI where the two limits meet. Left of it a kernel is memory-bound (faster memory helps, more FLOPs do not); right of it, compute-bound.

    The running example on this tab is one linear layer, y = x WT, with an 8192 × 8192 weight in fp16 (128 MB; Llama 3 70B has a model dimension of 8192 (Llama 3 paper, Table 3), so their query and output projections have this shape). At batch 1 (one token being generated, as in LLM decoding) every weight is read once and used for one multiply-add: 2 FLOPs per 2 bytes, AI ≈ 1. At batch 64 each weight read is used 64 times: AI ≈ 63. Same weight, same code, a different side of the ridge.

    Rule of thumb this tab keeps confirming
    For a linear layer with fp16 or bf16 weights and a batch much smaller than the layer's width, AI ≈ batch size (tokens processed together). So a layer becomes compute-bound when the batch passes the chip's ridge: about tokens on the M1 Pro GPU, on an H100 in BF16. Decoding one sequence at a time is therefore memory-bound on every chip below.

    How the M1 Pro roof was measured

    A roofline has two lines, and each is measured with a kernel that does nothing else. Peak compute: every GPU thread runs 16 independent chains of FMAs on numbers held in registers, so no memory is touched; independent chains matter because one FMA has to wait a few cycles for the previous result in its own chain. Bandwidth: copy a 512 MB array (far larger than any cache) as 4-wide vectors, one per thread. Both are custom Metal kernels written through MLX's mx.fast.metal_kernel; the scripts are in the repository (src/roof/, run_all.sh).

    A lesson the first attempt taught
    The first peak kernel wrote the 16 FMAs once inside a loop and reached only . Writing the same 16 FMAs eight times per loop trip (the same work, one eighth of the loop bookkeeping) reached . Every trip round a loop costs a counter increment, a compare and a branch, and on this GPU that overhead was large enough to cut throughput by more than half. CUDA programmers meet the same thing as #pragma unroll; it is one reason a "peak" number from a microbenchmark is only as good as the microbenchmark.

    Two more things the numbers show. fp16 runs at the same rate as fp32 here: the M1 has no separate matrix units, so both use the same arithmetic units (on an H100, BF16 on tensor cores is times its plain FP32 rate). And the measured bandwidth is of Apple's 200 GB/s: a datasheet bandwidth is the memory interface's theoretical rate, and real kernels typically get 80 to 90 percent of it. The batch-1 matrix-vector product below read its weights at , a little above the copy kernel, which is why a measured roof is a lower bound on the true one.

    MFU: measured FLOPs over peak

    Model FLOPs Utilization (MFU) is the roofline turned into one training number: the FLOPs your model mathematically needs per second, divided by the hardware's peak.

    MFU = (FLOPs per token × tokens per second) ÷ (peak FLOP/s × number of chips)
    FLOPs per token
    for training a dense transformer, about 6 × parameters (2 for the forward pass, 4 for the backward), ignoring attention's own FLOPs
    peak
    the vendor's dense figure for the precision used (BF16 for most training runs today)

    On the M1 Pro, MLX's fp16 4096 × 4096 matmul alone achieves of the measured peak and of the theoretical 5,308 GFLOP/s (16 cores × 128 arithmetic units × 2 × 1.296 GHz, an independent derivation by Philip Turner's metal-benchmarks; Apple publishes no TFLOPS figure). Which denominator you choose changes the MFU by several points, so always say which one. A whole training step is far below a single matmul, because it also runs memory-bound kernels (normalisation, activations, softmax, optimizer), waits on communication between GPUs, and sometimes recomputes activations.     What transfers from the M1 Pro to an NVIDIA GPU, and what does not

    Transfers

    The roofline itself and how to measure it; AI as a property of the operation and its shape; decode being memory-bound and big matmuls compute-bound; tiling into fast on-chip memory (threadgroup memory here, shared memory on NVIDIA); loop overhead and independent instruction chains; a library kernel beating a hand-written one by an order of magnitude; SIMD groups of 32 threads (NVIDIA calls them warps).

    Does not transfer

    The numbers. No tensor cores here, so fp16 = fp32 rate (on an H100 BF16 is about 15 times FP32); a ridge of about FLOP/byte against about 295 on an H100 BF16, so the same batch crosses at a different place; LPDDR5 unified memory shared with the CPU instead of HBM; different cache sizes; no NVLink or any link between GPUs.     Interview questions

    What is arithmetic intensity, and why does it decide whether a kernel is memory-bound?
    FLOPs per byte moved to and from main memory. The chip can do peak FLOP/s or move bandwidth bytes/s; a kernel needs FLOPs ÷ peak seconds of compute and bytes ÷ bandwidth of memory traffic, and the larger one wins. They are equal at AI = peak ÷ bandwidth, the ridge.
    Why is LLM decoding slow per token, and why does batching help?
    Each new token reads every weight once for one multiply-add: AI ≈ 1, deep in the memory-bound region, so time per step ≈ weight bytes ÷ bandwidth. Batching B sequences reuses each weight read B times, so throughput grows almost linearly with B until AI ≈ B reaches the ridge (about 300 on H100 BF16). Measured here: batch 64 took times as long as batch 1 for 64 times the tokens.
    How do you compute MFU, and what is a good number?
    6 × parameters × tokens per second ÷ (peak dense FLOP/s × chips), stating the precision and which peak. Llama 3 405B published 38 to 43 percent on H100s in BF16. Hardware FLOPs utilization (HFU) also counts FLOPs spent recomputing activations, so it is higher than MFU for the same run (PaLM, Appendix B defines both).
    Your training run gets 20% MFU. Where do you look first?
    The profile's time split: memory-bound kernels that could be fused (normalisation, activations, attention without a fused kernel), communication not overlapped with compute, small per-GPU batches making matmuls memory-bound, pipeline bubbles, data loading stalls. The roofline tells you which kernels are below their ceiling, and by how much.
    Why can a GeForce card look close to a datacenter GPU on paper and still train much slower?
    Check which tensor figure is quoted. An RTX 5090's 419 TFLOPS FP16 is with FP16 accumulate; with the FP32 accumulate training uses it is 209.5, against 989.5 on an H100. It also has 1.8 TB/s against 3.35, 32 GB of memory and no NVLink.
    Does FP8 make a memory-bound kernel faster?
    Yes, but because it halves the bytes, not because of the higher peak: a memory-bound kernel's time is bytes ÷ bandwidth. For a compute-bound one the doubled peak is what helps, and the ridge doubles too, so smaller batches may fall back into the memory-bound region.
