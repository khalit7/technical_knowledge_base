1. In one screen

A GPU is a few hundred identical processors, called streaming multiprocessors (SMs), sharing one large cache and one memory. Each SM runs thousands of threads at once in groups of 32 called warps, and hides the slowness of memory by always having another warp ready to run. Since the Volta generation, two before the A100, each SM also carries tensor cores, small units that multiply whole tiles of matrices in one instruction; they hold almost all of the chip's arithmetic. Every generation since the A100 has done three things: made the tensor cores faster and added smaller number formats, added hardware that moves data to them without spending threads (asynchronous copies, then TMA, then tensor memory), and grown the chip past what one die can hold.

The parent page, Topic: hardware, gives the intuition in its section 2 and compares every accelerator in its Chip atlas tab. This page is the depth on NVIDIA's GPU itself: how each piece works, what it costs, and how you can see it. How you program these pieces (CUDA, Triton, the mma, wgmma and tcgen05 instructions) lives on Topic: cuda-and-gpu-programming; this page links its simulator and compiler output rather than repeating them.

The running example. The training step on the parent page (Llama 3.1 8B) is almost all matrix multiplies. A matmul kernel cuts each output matrix into tiles and gives each tile to one SM. We follow one such tile: a 128 × 128 block of the output, built from a 128 × 64 slice of one input and a 64 × 128 slice of the other, which is 1,048,576 multiply-adds (FMAs) derived: 128 × 128 × 64. Where that tile's numbers come from, where they wait, which unit multiplies them and how each generation changed that, is this page.

2. The SM from zero: what is inside, and why

The problem. Our tile needs a million multiply-adds, and its inputs live in memory that answers in hundreds of cycles. A CPU core spends its area on making one thread fast (big caches, branch prediction, out-of-order execution). An SM spends its area on arithmetic lanes and on storage for many threads, so that the arithmetic never waits. Everything inside it follows from that choice.

How it is laid out. An SM is split into four identical sub-partitions (quadrants). Each has its own warp scheduler, which picks one warp each cycle and issues that warp's next instruction to 32 lanes at once; its own slice of the register file (16K 32-bit registers, 64 KB); its own arithmetic lanes ("CUDA cores": 32 fp32 lanes on Hopper, 16 on the A100); and its own tensor core. The four quadrants share one block of fast on-chip SRAM that is split, at kernel launch, between an L1 cache (filled automatically) and shared memory (filled by the program), plus load/store units and, from Hopper on, a copy engine called the TMA (section 8). Blackwell datacenter parts add a fifth store, tensor memory (TMEM), 256 KB per SM that only the tensor cores use.

Try: switch A100 to H100: the lanes per quadrant double (16 to 32) and the shared store grows from 192 to 256 KB; switch to B200 / B300: the tensor memory appears beside the shared store; switch to RTX 5090: the same quadrants with half the shared store and no TMEM. Drawn to the counts, not to silicon area.

Sources: A100 in depth (64 fp32 lanes, 4 tensor cores, 192 KB L1/shared, 256 KB registers per SM), Hopper in depth (128 fp32 lanes, 256 KB L1/shared, 256 KB registers), Inside Blackwell Ultra (128 CUDA cores, 4 tensor cores, 256 KB TMEM per SM), RTX Blackwell whitepaper (256 KB registers, 128 KB L1/shared per SM), CUDA Programming Guide, compute capabilities v13.4.2 (warps, blocks, shared memory per SM, 255 registers per thread), How To Scale Your Model, GPUs (four sub-partitions, 16K registers and one tensor core each). vendor spec

Why the register file is the largest memory in the SM. 256 KB of registers per SM is more than the 228 KB of shared memory an H100 kernel can use. Across 132 SMs that is 33.0 MiB of registers derived: 132 × 256 KiB, two thirds of the size of the 50 MB L2 cache. The reason: every warp that lives on the SM keeps all of its registers there all the time, so that switching from a stalled warp to a ready one costs nothing (no state is saved or restored, unlike a CPU context switch). That free switch is the whole latency-hiding trick of section 3, and the size of the register file is what pays for it.

What it means for our tile. The tile's running sums are 128 × 128 fp32 numbers, 64 KB: a quarter of the SM's entire register file, held for the whole time the tile is computed. On Ampere and Hopper they really do live in registers (128 per thread for a 128-thread block). Blackwell's tensor memory exists to take them out (section 8).

3. Hiding latency: why a GPU needs thousands of threads

The problem. A load from HBM takes about 466 cycles on an A100 and 479 on a Hopper (H800), measured by Luo et al. 2024, Table IV independent. A scheduler that issues one instruction per cycle would sit idle for all of them if the warp it was running were the only one.

How it works. Each quadrant's scheduler holds up to 16 resident warps on A100, H100 and B200 (64 per SM, 48 on the RTX 5090's SM). Every cycle it looks for a warp whose next instruction has its inputs ready and issues it; a warp waiting for memory is simply skipped. Nothing is saved or restored (section 2). So the question is never "how fast is one warp" but "is there always some warp ready". The animation runs one quadrant's scheduler on a simple program: each warp loads a value, then does arithmetic that needs it.

Illustrative program: each warp issues its load(s), waits for all of them, then issues 8 arithmetic instructions per load; one issue per cycle; load latency 466 cycles (A100, Luo et al. Table IV). Scheduler policy: greedy then oldest (keep the current warp until it stalls, then the lowest-numbered ready warp), a policy from the research literature; NVIDIA does not publish its own. Utilisation counted from cycle 1,000 on, after the start-up. Python reference: src/recompute.py (hide_sim), which the page's numbers match.

What it shows. With 2 warps the scheduler issues in 3.6% of cycles. With all 16 warp slots filled it still issues in only about 34%: the maximum number of warps is not enough when each warp has only a few instructions of work per load. The formula is the fraction of time any warp has work: utilisation ≈ W × (instructions per load round) / (instructions + latency) = 16 × 9 / 474 ≈ 30% derived (the simulation's window, cycles 1,000 to 2,000, happens to catch a little more). The fix is the third mode: the same 16 warps, but each issues 4 independent loads before it needs any of them, and the scheduler is busy 100% of the time. That is memory-level parallelism inside each thread: unrolled loops, wide vector loads (16 bytes per thread instead of 4), and, from Ampere on, copy hardware that fetches the next tile while the current one is computed (section 8).

How many bytes must be in flight: Little's law

Queueing theory gives the rule in one line: requests in flight = throughput × latency (Little's law). To stream memory at full bandwidth, the chip must always have bandwidth × latency bytes requested and not yet returned.

At 4 bytes per thread, 1,731 loads must be in flight on every SM at once, close to the 2,048 threads an SM can hold at all; at 16 bytes per thread (one float4), 433. That is why fast kernels load 16 bytes per thread, keep several loads outstanding, and on Hopper and Blackwell hand bulk copies to the TMA, which keeps whole tiles in flight without using threads.

Measured on the M1 Pro GPU. A coalesced read of 256 MB reaches only 1.27 GB/s with 32 threads (one SIMD-group, Apple's name for a warp) and 148 GB/s with thousands, 117 times more, from parallelism alone; the curve flattens near 8,192 threads, 512 per core. A pointer chase, where each thread's next address depends on its last load, goes from 2.0 million to 406 million loads per second as threads are added, 202 times. Predict first. An H100 has 132 SMs with up to 2,048 threads each. If every thread could keep only one 4-byte load in flight, what fraction of the 3.35 TB/s could the chip reach?
270,336 threads × 4 bytes = 1.08 MB in flight, against the 0.91 MB needed, so in principle about all of it, but only if every thread slot on every SM is filled and nothing else limits occupancy (section 4). Any kernel that uses many registers or much shared memory falls below that, which is why real kernels load 16 bytes per thread and keep several loads in flight instead of relying on thread count. derived

4. Occupancy: what limits how many warps fit

The problem. Section 3 needs many warps resident. But every resident warp holds its registers and its block's shared memory for its whole life, and the SM has a fixed amount of each. Occupancy is the number of resident warps divided by the maximum (64 on A100, H100 and B200).

How it works. Four limits, and the smallest wins: warp slots, block slots, registers (64K per SM, given to each warp in units of 256 and split across the four quadrants) and shared memory (each block's request plus 1 KB that CUDA reserves). On an H100: registers allow 3 blocks, shared memory 3, so 12 warps of 64, an occupancy of 19% derived with the cuda_occupancy.h rules. That is normal and fine for a tensor-core kernel: it hides latency with copies in flight (section 8), not with warps. A simple elementwise kernel (256 threads, 32 registers, no shared memory) reaches 100%.

A common mistake
"Higher occupancy is always better." It only helps when latency is hidden by switching warps. The fastest matmul and attention kernels deliberately run few warps with many registers each, and hide latency with asynchronous copies and deep pipelines; forcing occupancy up (by capping registers) makes them spill to memory and slower.

Measured on the M1 Pro GPU. The same 256 MB read as in section 3, with enough threads to fill the GPU, but each 64-thread group reserving more and more threadgroup memory (Apple's shared memory). Up to 4 KB per group the bandwidth stays near 140 GB/s; at 20 KB it falls to 95 GB/s and from 24 KB to 66 GB/s, because fewer groups fit on a core at once. 5. Divergence: what SIMT costs

The problem. A warp's 32 threads share one instruction stream (SIMT, single instruction, multiple threads). If an if sends some threads one way and some the other, the hardware cannot run both paths at once on the same lanes.

How it works. The warp runs each path in turn with the threads that did not take it switched off, then the paths rejoin. The cost is therefore the sum of the paths taken by any thread in the warp, not a fixed "halving": two paths of equal length cost 2 times, 32 different paths cost 32 times. Divergence between warps costs nothing, because each warp has its own instruction stream.

Every thread runs one of K different FMA loops of equal length (65,536 threads, 8,192 iterations of 8 FMAs). Divergent: the loop is chosen by the thread's lane within its 32-wide SIMD-group. Uniform: chosen by SIMD-group, so all 32 lanes agree. Median of 3 runs of 5 timings each; system load average (the laptop was shared). Apple M1 Pro GPU, MLX . measured here

What it shows. Divergent: 2 paths take 1.95 times as long, 32 paths 38.6 times (a little over 32, likely because 32 loop bodies no longer fit the instruction cache; not verified). Uniform: 1.14 times at 32 paths, essentially free. The M1's SIMD-group is 32 wide like an NVIDIA warp, so the lesson transfers directly.

When it matters for training. Rarely in matmuls (every thread does the same thing), more in kernels with data-dependent work per thread: masks in attention, ragged sequence lengths, sampling, MoE routing. The fix is to assign work so that whole warps take the same path (sort or bucket by length, process a row per warp).

6. The memory ladder inside the chip

The problem. Our tile's 32 KB of inputs (a 128 × 64 and a 64 × 128 slice of BF16, 2 bytes per number) are used 128 times each. Fetching them from HBM every time would need 128 times the bytes; keeping them close to the tensor cores turns a memory-bound tile into a compute-bound one. What it shows. Shared memory answers in about 29 cycles on all three GPUs; L2 in about 260 to 270, nine times longer; HBM in 470 to 540, almost twice L2 again. A likely reason, not measured by the paper: L2 is one structure shared by every SM on a die of about 800 mm², so a request may cross the chip and back. Luo et al. also measured H800's L2 throughput at 4,472 bytes per clock, 2.2 times the A100's, and about 3.27 TB/s for DSMEM traffic between SMs of a 2-SM cluster, falling to 2.65 TB/s with 4.

Measured on the M1 Pro GPU. Two things the ladder decides for training. First, the L2 sizes matter more than they look: 40 MB (A100), 50 MB (H100) and 96 MB (RTX 5090) are large enough to hold a whole layer's activations for small batches, so a kernel that re-reads data soon after it was written may never touch HBM. Second, the split between L1 and shared memory is chosen per kernel: matmul and attention kernels take nearly all of it as shared memory, because they know exactly which tile they will reuse; elementwise kernels leave it as cache.

7. Tensor cores, generation by generation

The problem. Ordinary lanes do one multiply-add per thread per instruction. An H100 SM has 128 of them, so our tile's million FMAs would take 8,192 cycles of perfect issue. Matrix multiplication has far more structure than that: every number of A meets a whole row of B. A tensor core exploits it.

How it works. A tensor core is a small fixed-function array that takes a tile of A, a tile of B and an accumulator tile, and returns A·B + C in one instruction for a whole warp (or more). On the A100 each of the 4 tensor cores per SM does 256 FP16 multiply-adds per clock, 1,024 per SM, sixteen times the A100 SM's 64 FP32 lanes (A100 in depth). The H100's do twice that per SM on the same types and four times with FP8 (Hopper in depth), so 2,048 FP16 FMAs per SM per clock; that rate reproduces the H100's 989.5 TFLOPS at a 1.83 GHz clock 989.5e12 / (132 × 2,048 × 2), a clock NVIDIA's blog leaves "not finalized". NVIDIA publishes no per-SM rate for Blackwell; Rubin "doubles the Tensor Core throughput per clock by doubling the amount of data it can process along the K dimension" (Inside Rubin).

The bigger change over the generations is not the rate but who issues the multiply, where its operands come from, and where its results go. The animation follows our tile through the three instruction families.

What it shows. Ampere needs 512 warp instructions and every operand passes through registers; Hopper needs 8 warpgroup instructions reading straight from shared memory, but its accumulators still fill a quarter of the register file; Blackwell needs 4 instructions, issued by a single thread, and the accumulators leave the register file for tensor memory. Each step frees the threads for something else: computing addresses, the epilogue of the previous tile, softmax in attention.

Independent evidence that the instruction family matters. On an H800, Luo et al. found that the Ampere-style mma instructions reach on average only 62.9% of the tensor cores' peak, while wgmma reaches 729.3 of 756.5 TFLOPS (96.4%) in FP16 (Luo et al. 2024, Table VIII) independent. So a kernel written for the A100 runs on an H100 but leaves a third of its tensor-core peak unused.

8. Feeding the tensor cores: async copy, TMA, clusters, tensor memory

The problem. Each generation doubled the tensor cores' appetite, but the threads that had to fetch their data stayed the same. On an A100 a thread copies 16 bytes per instruction, so filling our tile's 32 KB of inputs takes 2,048 copy instructions plus the address arithmetic for each 32,768 / 16, every k-step, competing for the same issue slots as the math. The hardware added since then moves that work off the threads.

Ampere: asynchronous copy

A copy from global memory straight into shared memory that skips the registers and does not stall the thread that issued it ("eliminating the need for intermediate register file usage", A100 in depth). Threads still issue one per 16 bytes, but can issue the next tile's copies and then compute on the current one: double buffering.

Hopper: TMA

A copy engine in each SM. One thread hands it a descriptor (base address, shape and strides of a 1D to 5D tensor, the box to fetch) and the TMA moves the whole tile between global and shared memory, address arithmetic included (Hopper in depth). Our tile's inputs: 2 instructions instead of 2,048. Completion is tracked by an asynchronous transaction barrier that counts arriving bytes.

Hopper: clusters and DSMEM

A cluster is a group of up to 16 thread blocks that "run concurrently across SMs within a GPC" (Hopper in depth); each can read and write the others' shared memory (distributed shared memory), about 7 times faster than exchanging through global memory per NVIDIA, 180 cycles and up to 3.27 TB/s per Luo et al. One TMA load can also be multicast to several SMs of the cluster that need the same tile (.multicast::cluster in the PTX ISA).

Blackwell: tensor memory

256 KB per SM, organised as 128 lanes × 512 columns of 32-bit cells, allocated by columns and read only by the tensor cores and by explicit copies to registers (PTX ISA, tcgen05). Our tile's FP32 accumulators take 128 of the 512 columns, so two tiles can be accumulating while a third is being written out. Rubin widens it: CUTLASS 4.8.0's changelog (September 2026) says Rubin extends "TMEM size from 512 COL to 576 COL", with shared memory allocations up to 328 KB vendor; how kernels use tensor memory is in Libraries and tensor cores, section 5.

What this changed in kernels. Once copies and multiplies are both asynchronous, the fastest kernels split warps by role: one producer warp issues TMA copies into a ring of shared-memory buffers, consumer warps issue the matrix multiplies and the epilogue, and barriers pass buffers between them. FlashAttention-3 names this warp specialisation and the overlap of TMA and tensor cores as two of its three techniques, reaching up to 740 TFLOPS in FP16 on an H100 (75% of peak). Reading CUTLASS or FlashAttention code for Hopper or Blackwell means reading this pipeline.

The RTX 5090 is in between
Its sm_120 target compiles TMA copies and clusters (the CUDA topic's compiles) but has no wgmma, no tcgen05 and no tensor memory, so its kernels look like Ampere's mma.sync kernels fed by Hopper's copy engine.

9. The whole chip: GPCs, L2, memory, dies

How SMs are grouped. Two SMs form a TPC (texture processing cluster); TPCs form a GPC (graphics processing cluster), the unit that also bounds a thread-block cluster. The full GA100 has 8 GPCs of 8 TPCs (128 SMs); the A100 enables 108. The full GH100 has 8 GPCs of 9 TPCs (144 SMs); the H100 SXM enables 132. The RTX 5090's GB202 has 12 GPCs (192 SMs) and enables 170 in 11 GPCs. Shipping fewer SMs than the die has lets a die with a few defective SMs still be sold; NVIDIA's documents give the counts, not the yields.

L2 and memory. Memory controllers sit at the die edge, each driving one channel: on the A100 and H100, 10 of the die's 12 512-bit controllers are enabled, feeding 5 of its 6 HBM stack sites; the RTX 5090 has sixteen 32-bit GDDR7 controllers (a 512-bit bus). The L2 is split into partitions near the controllers (two on the A100, "divided into two partitions to enable higher bandwidth and lower latency"; four on the B200 per Jarmusch and Chandrasekaran).

Two dies as one GPU. A die cannot be larger than the area a lithography scanner exposes at once (the reticle); the A100 (826 mm²) and H100 (814 mm²) are near it. Blackwell's answer is two "reticle-sized" dies, 208 billion transistors in total, joined by a 10 TB/s link (NV-HBI) and presented to software as one GPU with one memory space. Blackwell Ultra keeps the two-die design with 160 SMs in 8 GPCs and eight 12-high HBM3e stacks on 16 512-bit controllers; Rubin is again two dies, 336 billion transistors and 224 SMs (Inside Blackwell Ultra, Inside Rubin).

What to notice.

  • The halving ladder held for three generations: TF32 at half of BF16, FP8 at twice, FP4 at four times (B200). Blackwell Ultra broke it on purpose: FP4 at 6 times BF16, paid for by cutting FP64 from 37 to 1.25 TFLOPS and INT8 to 187.5 TOPS per GPU.
  • Rubin breaks it again: BF16 rises 1.78 times over the B200 but FP8 3.9 times, so FP8 is 4.4 times BF16. On Rubin, training in FP8 rather than BF16 is worth more than on any earlier part.
  • Consumer parts halve the training format: the RTX 5090's BF16 with FP32 accumulation is 209.5 TFLOPS, half its 419 with FP16 accumulation; the same was true of the 4090. Training accumulates in FP32, so the lower number is the one to compare.
  • No datapath, no speed-up: FP8 on an A100 or FP4 on an H100 runs as a wider format after conversion (the CUDA topic's compile shows FP8 mma.sync becoming two FP16 multiplies on sm_90a).

The ridge moves with the format, not the generation. A kernel is compute-bound only above peak / bandwidth FLOPs per byte. At BF16 that is 153 on the A100, 295 on the H100, 281 on the B200 and 182 on Rubin, whose HBM4 grew faster than its BF16 math; at FP8 it is 591, 563 and 795 dense peak / bandwidth. The parent page's Roofline lab tab explains the ridge with measured kernels.

Go deeper (optional). How the bits encode a number and where each format overflows: Numerical computing for ML. Block scaling (MX, NVFP4) and what it costs in bits: the parent page's section 4. Training and serving in these formats: Quantization and Precision.

11. Consumer against datacenter: RTX 5090, H100, B200

The RTX 5090 has more SMs than an H100 and the same instruction set generation as the B200. What separates them is everything around the SM.

Sources: RTX Blackwell whitepaper Appendix A; H100 page; HGX page and DGX B200 (180 GB, 8 TB/s per GPU); B200 power from Inside Blackwell Ultra Table 2 ("up to 1,200 W", SKU not stated); per-SM limits from the CUDA Programming Guide; RTX 5090 price NVIDIA newsroom, Jan 6 2025. vendor spec

Reading the table. For one-GPU, memory-bound inference of a model that fits in 32 GB, a 5090 is about half an H100 (bandwidth 0.53 times), and FP4 helps it further. For training it is much further behind: BF16 with FP32 accumulation is 0.21 times an H100's, 32 GB holds model and optimizer state for only about 2 billion parameters at 16 bytes each, there is no NVLink, so two cards talk over PCIe 5.0 at 64 GB/s each way, about 7 times less than an H100's 450 GB/s NVLink per direction, and its kernels cannot use wgmma or tcgen05. It is a good target for learning kernels at sm_120 and for FP8/FP4 inference; it is not a small H100.

Corrections to the old page
The old table gave the 5090's dense FP4 as about 838 TFLOPS; the whitepaper's dense figure is 1,676 (838 is not in it). The old "PCIe ~28 times less than one H100's NVLink" compared one direction of PCIe with NVLink's two-direction total and still came out wrong: 64 against 900 is 14 times, 64 against 450 per direction is 7 times. The parent page's coverage notes record both.

The pattern to remember
Math got cheaper faster than data movement in every generation. So each generation added hardware to move data (async copy, TMA, DSMEM, TMEM, bigger L2, faster HBM) and the code that runs fastest is the code that overlaps moving with computing. A kernel written for the previous generation usually runs, but does not use what is new.

13. Checking your GPU, common mistakes, interview questions

Checking what you are running on not run here: no NVIDIA GPU

  • torch.cuda.get_device_capability() gives the compute capability (8, 0) A100, (9, 0) H100, (10, 0) B200, (12, 0) RTX 5090: it decides which instructions a kernel can use. torch.cuda.get_device_properties(0) gives the SM count and memory.
  • nvidia-smi -q lists clocks, power limit and memory; a power or clock cap lowers every peak on this page proportionally.
  • A kernel's registers, shared memory and spills: compile with -Xptxas -v, or read them per kernel in Nsight Compute, which also reports achieved occupancy and tensor-pipe utilisation (see the CUDA topic).

Common mistakes

Quoting sparse FLOPS as the chip's speed
Vendor tables print the 2:4 structured-sparsity figure first (H100 BF16 "1,979"); dense training gets half (989.5). Compare dense with dense.
"Divergence halves throughput"
The paths taken within a warp run one after the other, so the cost is the sum of the paths: 2 equal paths cost 1.95 times, 32 paths 38.6 times on the M1 measurement in section 5. Divergence between warps is free.
Chasing 100% occupancy
The fastest tensor-core kernels run at low occupancy with many registers per thread and hide latency with asynchronous copies (section 4).
"An H100 is just a faster A100"
Ampere-style mma code reaches about 63% of Hopper's tensor peak; wgmma reaches 96% (Luo et al.). Blackwell kernels need tcgen05 and TMEM. Use libraries and compilers built for the target (sm_90a, sm_100a).
"B200" is one number
HGX B200 is 2,250 BF16 TFLOPS dense; the B200 inside a GB200 rack is 2,500; Blackwell Ultra 2,250 BF16 but 15 PF FP4. Name the SKU.
Comparing a consumer card's FP16-accumulate rate with a datacenter BF16 rate
The RTX 5090's 419 TFLOPS is FP16 with FP16 accumulation; training uses FP32 accumulation, 209.5.

Interview questions, short answers

What is an SM, and what is inside it?
The GPU's repeated processor: four quadrants, each with a warp scheduler, 64 KB of registers, 32 FP32 lanes (Hopper) and a tensor core; shared L1/shared memory (256 KB on H100); on Blackwell also 256 KB of tensor memory. H100 SXM has 132.
How does a GPU hide memory latency?
By keeping many warps resident with their registers in place and issuing from whichever is ready; plus memory-level parallelism per thread and asynchronous copies. Little's law: bytes in flight = bandwidth × latency, about 0.9 MB for an H100.
What limits occupancy?
Warp slots, block slots, registers (64K per SM) and shared memory per SM; the smallest wins. Low occupancy is fine if latency is hidden another way.
What did Hopper add for matmuls, and why?
FP8, wgmma (warpgroup MMA from shared memory, asynchronous), TMA (descriptor-driven tile copies) and clusters with distributed shared memory: the tensor cores had outgrown what threads could feed.
What is TMEM and why does it exist?
256 KB per SM on Blackwell datacenter GPUs, 128 lanes by 512 columns, holding tensor-core accumulators. It frees the register file (a 128 × 128 FP32 accumulator is a quarter of it) for the epilogue and other work.
Why is the B200 two dies?
One die is limited by the reticle; two reticle-sized dies joined at 10 TB/s give 208 billion transistors presented as one GPU.
RTX 5090 or H100 for training a 7B model?
H100: 80 GB against 32 GB (full fine-tuning needs about 16 bytes per parameter), 4.7 times the BF16 rate with FP32 accumulation, NVLink, wgmma. The 5090 is for inference and kernel development.
Why did the BF16 ridge point fall on Rubin?
HBM4 bandwidth (22 TB/s) grew faster than BF16 math (4 PF): 182 FLOPs per byte against the H100's 295. At FP8 it rose to 795.

M1 GPU lab: four NVIDIA microbenchmarks, run on an Apple GPU

No NVIDIA GPU was available for this page, so the microbenchmarks that papers such as Luo et al. run to dissect NVIDIA GPUs were run on the Apple M1 Pro's 16-core GPU instead. It is a real SIMT GPU: SIMD-groups of 32 threads (Apple's warps), threadgroups (blocks), threadgroup memory (shared memory). What transfers to NVIDIA is the shape of each result and the mechanism behind it; the numbers do not, and each chart says which is which. measured here

1. The latency ladder: one thread chasing pointers

One thread follows a random cyclic chain through a buffer, one hop per 128-byte line, so every load depends on the last and nothing can overlap. Time per hop against buffer size shows each level of the memory system as a step. Launch overhead is cancelled by timing two chain lengths and taking the difference.

Transfers: the staircase (each level a plateau, a jump where the working set stops fitting), and the method; it is how Table IV of Luo et al. was measured.
Does not transfer: the sizes and the nanoseconds. Apple does not publish its GPU cache sizes (the steps here are inferred), and the last step includes address-translation misses of a 256 MB random walk.

2. Latency hiding: throughput against threads in flight

Left: a coalesced read of 256 MB (each thread loops over the buffer in 16-byte loads). Right: the pointer chase of chart 1 in a 256 MB chain, with every thread starting at a different place. Both grow with threads until the memory system saturates: Little's law, throughput = requests in flight / latency.

Transfers: a single warp reaches about 1% of the bandwidth; saturating memory needs thousands of threads or, per thread, several wide loads in flight. On an H100 the same rule asks for about 0.9 MB in flight (Reading, section 3).
Does not transfer: where the curve flattens (here about 512 threads per core) and the plateau (148 GB/s here, 3.35 TB/s nominal on an H100).

3. Occupancy: reserving shared memory evicts warps

The coalesced read again, with 65,536 threads in 64-thread groups, but each group reserves X KB of threadgroup memory it does not need. Fewer groups fit on a core, fewer loads are in flight, bandwidth falls in steps.

Transfers: the mechanism. On an H100, a block's shared memory (plus 1 KB) divided into 228 KB sets how many blocks fit, exactly as the steps here show (Reading, section 4).
Does not transfer: the per-core budget. The steps fall where 64 KB per core would put them (3 groups at 20 KB, 2 from 24 KB), but Apple does not publish the figure.

4. Divergence

Shown with its bars in Reading, section 5 (go there): K different loops chosen by lane (divergent) cost about K times; chosen by SIMD-group (uniform) cost nothing. Same kernel, same work per thread.

Method: src/m1/gpu_micro.py, custom Metal kernels through mx.fast.metal_kernel; three full runs 20 s apart (src/run_all.sh); each point is the median of the three runs' medians of 5 timings, whiskers the lowest and highest run median. Every chase result is checked against the chain computed in NumPy, every read against a float64 sum. The laptop was shared with other work: load average during the runs is given above. Raw outputs: src/m1/out/.
