Filling every warp slot is not enough; loads in flight per warp are what keep the scheduler busy

3. Hiding latency: why a GPU needs thousands of threads

The problem. A load from HBM takes about 466 cycles on an A100 and 479 on a Hopper (H800), measured by {{Luo et al. 2024|https://arxiv.org/html/2402.13499v1}}, Table IV independent.

How it works. Each quadrant's scheduler holds up to 16 resident warps on A100, H100 and B200 (64 per SM; 48 per SM on the RTX 5090). Every cycle it issues from any warp whose next instruction has its inputs ready; a warp waiting on memory is simply skipped, at no cost (section 2). So the question is "is some warp always ready". The timeline on the right is one quadrant running three programs; predict before it plays: with all 16 slots full, how busy is the scheduler?

2 warps, one load each

  1. Cycles 0 to 100: two loads, then nothing. Each warp issues its load (cycles 0 and 1) and then needs the data, 466 cycles away. The scheduler has nothing else to issue: 98 of the first 100 cycles are empty.
  2. Cycle 466: the data returns. Each warp issues its 8 arithmetic instructions and its next load, 18 busy cycles in all, then both wait again: 20 instructions by cycle 500.
  3. Cycle 1,000: the steady state. The same 18 busy cycles come back every 474; from here on the page counts utilisation, after start-up.
  4. Cycle 2,000: 74 instructions. Almost every cycle was wasted.
  1. Cycles 0 to 100: sixteen loads, then nothing. Every warp slot is full. Each warp issues its load in the first 16 cycles, then all 16 wait.
  2. Cycles 466 to 610: one burst. The loads return one per cycle; each warp has only 8 arithmetic instructions before its next load, so the 16 warps fill 144 cycles and are all waiting again: 150 instructions by cycle 600.
  3. Cycle 1,000: the steady state. Bursts of 144 busy cycles alternate with 330 idle ones; 220 instructions so far.
  4. Cycle 2,000: 560 instructions. About a third of the issue slots, with every warp slot full.
  1. Cycles 0 to 100: 64 loads in flight. The same 16 warps, but each issues 4 independent loads back to back before it needs any of them: 64 loads in the first 64 cycles.
  2. Cycles 469 to 700: the gaps close. Each warp whose data has returned has 32 arithmetic instructions; while it computes, the next warps' loads come back: 295 instructions by cycle 700.
  3. Cycle 1,000: the steady state. The scheduler has issued every cycle since cycle 469; 595 instructions so far.
  4. Cycle 2,000: 1,595 instructions. Every issue slot used, by the same 16 warps.

What it shows. With 2 warps the scheduler issues in 3.6% of cycles; with all 16 slots filled, still only about 34%, because each warp has only a few instructions of work per load. The bound is the fraction of time any warp has work: utilisation ≈ W × (instructions per load round) / (instructions + latency) = 16 × 9 / 474 ≈ 30% derived. The third mode keeps the same 16 warps but lets each issue 4 independent loads before it needs any, and the scheduler is busy 100% of the time: memory-level parallelism inside each thread (unrolled loops, 16-byte loads, and from Ampere on copy hardware, section 8).

How many bytes must be in flight: Little's law, requests in flight = throughput × latency

bytes in flight = bandwidth × latency
M1 Pro
148 GB/s (best coalesced read measured here) × 485 ns (pointer chase into DRAM, measured here) = 70 KiB in flight, about 4.4 KiB per GPU core measured here derived
H100 SXM
3.35 TB/s (vendor) × 273 ns (H800's 478.8 cycles at 1.755 GHz, Luo et al., as a stand-in) = 0.91 MB in flight, about 6,900 bytes per SM derived

At 4 bytes per thread that is 1,731 loads in flight on every SM at once, close to the 2,048 threads an SM can hold at all; at 16 bytes per thread (one float4), 433. Hence 16-byte loads, several outstanding per thread, and on Hopper and Blackwell the TMA, which keeps whole tiles in flight without threads.

Predict first. An H100 has 132 SMs with up to 2,048 threads each. If every thread could keep only one 4-byte load in flight, what fraction of the 3.35 TB/s could the chip reach?
270,336 threads × 4 bytes = 1.08 MB in flight, against the 0.91 MB needed, so in principle about all of it, but only if every thread slot on every SM is filled and nothing else limits occupancy (section 4). Kernels heavy in registers or shared memory fall below that, so real kernels rely on wide loads, not thread count. derived
How the M1 measurements were made (method, versions, machine load)

No NVIDIA GPU was available, so the microbenchmarks that papers such as Luo et al. run to dissect NVIDIA GPUs were run on the Apple M1 Pro's 16-core GPU. It is a real SIMT GPU: SIMD-groups of 32 threads (Apple's warps), threadgroups (blocks), threadgroup memory (shared memory). What transfers is the shape of each result and the mechanism; the numbers do not, and each chart says which is which.

Method: src/m1/gpu_micro.py, custom Metal kernels through mx.fast.metal_kernel; three full runs 20 s apart (src/run_all.sh); each point is the median of the three runs' medians of 5 timings, whiskers the lowest and highest run median. Every chase result is checked against the chain computed in NumPy, every read against a float64 sum. The laptop was shared with other work. Raw outputs: src/m1/out/.
