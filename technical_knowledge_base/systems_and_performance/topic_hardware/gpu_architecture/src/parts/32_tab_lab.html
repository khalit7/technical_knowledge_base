M1 GPU lab: four NVIDIA microbenchmarks, run on an Apple GPU

No NVIDIA GPU was available for this page, so the microbenchmarks that papers such as {{Luo et al.|https://arxiv.org/html/2402.13499v1}} run to dissect NVIDIA GPUs were run on the Apple M1 Pro's 16-core GPU instead. It is a real SIMT GPU: SIMD-groups of 32 threads (Apple's warps), threadgroups (blocks), threadgroup memory (shared memory). What transfers to NVIDIA is the shape of each result and the mechanism behind it; the numbers do not, and each chart says which is which. measured here

1. The latency ladder: one thread chasing pointers

One thread follows a random cyclic chain through a buffer, one hop per 128-byte line, so every load depends on the last and nothing can overlap. Time per hop against buffer size shows each level of the memory system as a step. Launch overhead is cancelled by timing two chain lengths and taking the difference.

Transfers: the staircase (each level a plateau, a jump where the working set stops fitting), and the method; it is how Table IV of Luo et al. was measured.
Does not transfer: the sizes and the nanoseconds. Apple does not publish its GPU cache sizes (the steps here are inferred), and the last step includes address-translation misses of a 256 MB random walk.

2. Latency hiding: throughput against threads in flight

Left: a coalesced read of 256 MB (each thread loops over the buffer in 16-byte loads). Right: the pointer chase of chart 1 in a 256 MB chain, with every thread starting at a different place. Both grow with threads until the memory system saturates: Little's law, throughput = requests in flight / latency.

Transfers: a single warp reaches about 1% of the bandwidth; saturating memory needs thousands of threads or, per thread, several wide loads in flight. On an H100 the same rule asks for about 0.9 MB in flight (Reading, section 3).
Does not transfer: where the curve flattens (here about 512 threads per core) and the plateau (148 GB/s here, 3.35 TB/s nominal on an H100).

3. Occupancy: reserving shared memory evicts warps

The coalesced read again, with 65,536 threads in 64-thread groups, but each group reserves X KB of threadgroup memory it does not need. Fewer groups fit on a core, fewer loads are in flight, bandwidth falls in steps.

Transfers: the mechanism. On an H100, a block's shared memory (plus 1 KB) divided into 228 KB sets how many blocks fit, exactly as the steps here show (Reading, section 4).
Does not transfer: the per-core budget. The steps fall where 64 KB per core would put them (3 groups at 20 KB, 2 from 24 KB), but Apple does not publish the figure.

4. Divergence

Shown with its bars in Reading, section 5 ({{go there|#t-read}}): K different loops chosen by lane (divergent) cost about K times; chosen by SIMD-group (uniform) cost nothing. Same kernel, same work per thread.

Method: src/m1/gpu_micro.py, custom Metal kernels through mx.fast.metal_kernel; three full runs 20 s apart (src/run_all.sh); each point is the median of the three runs' medians of 5 timings, whiskers the lowest and highest run median. Every chase result is checked against the chain computed in NumPy, every read against a float64 sum. The laptop was shared with other work: load average during the runs is given above. Raw outputs: src/m1/out/.
