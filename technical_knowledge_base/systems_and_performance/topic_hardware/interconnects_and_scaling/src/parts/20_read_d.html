7. Collectives on the wire: algorithms and what they cost

The problem. Training code calls a handful of collectives, operations every GPU in a group joins: all-reduce (everyone ends with the sum), reduce-scatter (everyone ends with the sum of one slice), all-gather (everyone ends with every slice), all-to-all (everyone sends a different piece to everyone). {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}} explains which parallelism calls which. A library (NCCL on NVIDIA, RCCL on AMD) turns each call into a schedule of point-to-point messages, and the schedule decides how many latencies and how many bytes the operation pays.

Four ways to all-reduce. With n GPUs, a buffer of S bytes, and every GPU able to send and receive one message per step:

Formulas: {{Thakur, Rabenseifner and Gropp, 2005|https://journals.sagepub.com/doi/10.1177/1094342005051521}} for recursive doubling and halving-doubling; the ring line is their ring reduce-scatter plus ring all-gather, composed here derived. Their γ term for the additions is dropped: on GPUs the adds are far cheaper than the transfers. The in-switch line is idealised (the switch adds as fast as data arrives). NCCL's other main algorithm is a pipelined double binary tree: "full bandwidth and a logarithmic latency", "up to 180x improvement at 24k GPUs" over rings in latency ({{NCCL 2.4 blog, 2019|https://developer.nvidia.com/blog/massively-scale-deep-learning-training-nccl-2-4/}}).

Try: at 16.06 GB, ring and halving-doubling send the same 28.1 GB per GPU and tie; recursive doubling sends 48.2 GB; in-switch sends 16.06 GB and finishes in about 57% of the ring's time. Then pick 8 KB: now the step count is everything, and recursive doubling's 3 steps beat the ring's 14.

Two bandwidths in every benchmark. NVIDIA's nccl-tests, the standard benchmark, prints two: algbw = S / t, and busbw = algbw × 2(n−1)/n for all-reduce ((n−1)/n for all-gather, reduce-scatter and all-to-all), defined so that it can be compared "with the hardware peak bandwidth, independently of the number of ranks used" ({{nccl-tests PERFORMANCE.md|https://github.com/NVIDIA/nccl-tests/blob/master/doc/PERFORMANCE.md}}). For a ring, busbw is the bandwidth on each wire. In-switch and hierarchical algorithms break that meaning; NCCL's author: "with SHARP enabled ... BusBW may not represent any 'Bus' bandwidth" ({{nccl-tests issue 153|https://github.com/NVIDIA/nccl-tests/issues/153}}). So a busbw above the link's rate is not a measurement error: it is NVLS or a hierarchy at work.

Published measurements against the model

Model: ring busbw equals the link's bandwidth each way; in-switch busbw = 1.75 × link (S/β time, rescaled by 2(n−1)/n); across servers a two-level model (ring inside over NVLink, each GPU's 1/8 share all-reduced over its own NIC, the slower phase setting the time) derived. Measurements: {{Bekman, ML Engineering, network benchmarks|https://github.com/stas00/ml-engineering/blob/master/network/benchmarks/README.md}} independent; {{AWS awsome-distributed-training|https://github.com/aws-samples/awsome-distributed-training/tree/main/micro-benchmarks/nccl-tests}} sample outputs vendor. Together AI's acceptance target for H100 InfiniBand clusters is "around 92% of the theoretical maximum of the fabric: so around 370 GB/s on a 400GB/s fabric" ({{Together AI, Aug 2024|https://www.together.ai/blog/a-practitioners-guide-to-testing-and-running-large-gpu-clusters-for-training-generative-ai-models}}).

What the table says. Rings reach 76 to 81% of NVLink's per-direction rate, and two-level all-reduces across servers 73 to 101% of the model. In-switch reduction is real but well short of the ideal: 1.29 times the ring on H200 and 1.23 times on B200, not the 1.75 times that halving the bytes would give, because the switch's adders and protocol overheads, not the wires, become the limit. The 2 × p5 case reaches 101% of a model that assumes a ring inside each server, which fits NCCL using NVLS there (the README does not say).

How NCCL picks. NCCL chooses algorithm (ring, tree, NVLS, CollNet, PAT) and protocol by message size and topology from a cost model. The protocols trade latency against bandwidth: LL sends 4 bytes of data with a 4-byte flag (about 1 µs per hop, 25 to 50% of peak bandwidth), LL128 120 bytes of data with an 8-byte flag (about 2 µs, about 95%), Simple large chunks with memory fences (about 6 µs, near peak) ({{Hu et al., Demystifying NCCL, Table I|https://arxiv.org/abs/2507.04786}}) independent. NVIDIA's tuning post prints a real choice on 4 servers, 32 GPUs: tree with LL up to 96 KiB, tree with LL128 up to 12 MiB, ring with LL128 up to 96 MiB, ring with Simple above ({{NVIDIA, Jul 2025|https://developer.nvidia.com/blog/understanding-nccl-tuning-to-accelerate-gpu-to-gpu-communication/}}). The lesson is the alpha-beta one: logarithmic-latency schemes for small messages, bandwidth-optimal ones for large.

Measured here: latency against bandwidth on one laptop

No GPU cluster was available, so the two algorithms were written in PyTorch (send and receive only, so the schedule is exactly the one in the table) and run as 2, 4 and 8 processes on this laptop, talking through the Gloo library over loopback TCP. The "links" are slow (about 80 µs per message) and share one memory system, but the alpha-beta logic is the same, and every result was checked against the exact sum.

What the measurement shows. At small sizes the ring takes as long as recursive doubling with 8 ranks; the model's step count predicts 14/3 = 4.67. The predicted crossover, where the ring's fewer bytes start to beat recursive doubling's fewer steps, is , and the measured crossover falls between the 1 MiB and 4 MiB sizes for 4 and 8 ranks. Two departures teach as much as the agreement. The per-step latency grows with the number of ranks (), because the processes compete for cores. And the bandwidth per rank falls as ranks are added () while the total stays near : all the "links" share one memory system, exactly like GPUs whose NICs share an oversubscribed switch. The model assumes independent links; a real fabric only gives you that if it was built with full bisection.

Corrections to the old page's sanity numbers
The old page put the 16 GB all-reduce at "~2 x 16/50 = 0.64 s" over 400G InfiniBand and "~70 ms" over NVLink 4. 2S/β is the large-n limit; for 8 GPUs the ring factor is 2 × 7/8 = 1.75, giving 0.56 s and 62 ms () derived. It also said SHARP "roughly halv[es] traffic": the bytes per GPU do fall from 2(n−1)/n · S to S, but measured speed-ups are 1.23 to 1.29 times inside a server (table above).
