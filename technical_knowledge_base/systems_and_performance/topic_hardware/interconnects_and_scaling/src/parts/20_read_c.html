3. NVLink and NVSwitch: the scale-up domain

Tensor parallelism exchanges activations several times per layer, so GPUs splitting one model need bandwidth near their memory's, far beyond PCIe. NVLink is NVIDIA's GPU-to-GPU link: many lanes of fast serial wires, grouped into links. Since the A100 the links go not to other GPUs but to NVSwitch chips, so any GPU can send to any other at its full NVLink bandwidth, all at once. The GPUs joined this way are the NVLink domain (or scale-up domain); inside it GPUs can load and store each other's memory, like one bigger GPU with slower remote memory.

A switch gives every pair the whole port; a mesh gives each pair one link

GPU 0 sending to GPU 3 highlighted. NVIDIA: without NVSwitch each of 8 GPUs "must split the same 900 GB/s connectivity into seven dedicated 128 GB/s point-to-point connections", while through NVSwitch any pair gets the full 900 ({{NVIDIA, Aug 2024|https://developer.nvidia.com/blog/nvidia-nvlink-and-nvidia-nvswitch-supercharge-large-language-model-inference/}}). MI300X: 7 Infinity Fabric links of 128 GB/s (both directions) join each GPU directly to the other 7 ({{MI300X data sheet|https://www.amd.com/content/dam/amd/en/documents/instinct-tech-docs/data-sheets/amd-instinct-mi300x-data-sheet.pdf}}). A mesh is cheaper and has no switch hop, but collectives must use all 7 links at once to see the 448 GB/s total. The NVL72 rack. GB200 NVL72 puts 72 Blackwell GPUs (and 36 Grace CPUs) in one NVLink domain. Nine switch trays, each with two NVLink switch chips of 72 ports, connect all 18 links of every GPU: "Each NVLink switch tray delivers 144 NVLink ports at 100 GB so the nine switches fully connect each of the 18 NVLink ports on every one of the 72 Blackwell GPUs", through "a copper cable cartridge" rather than optics; 72 × 1.8 TB/s gives the 130 TB/s headline ({{GB200 NVL72 blog|https://developer.nvidia.com/blog/nvidia-gb200-nvl72-delivers-trillion-parameter-llm-training-and-real-time-inference/}}, {{DGX GB200 user guide|https://docs.nvidia.com/dgx/dgxgb200-user-guide/hardware.html}}). Tensor or expert parallelism of up to 72 instead of 8 now runs at NVLink speed.

In-switch reduction (NVLink SHARP). Third-generation NVSwitch (Hopper) and later can add numbers inside the switch: GPUs send their data in, the switch sums it and multicasts the result back. NVIDIA: "In-fabric multicast and reductions provide up to 2x throughput gain while significantly reducing latency for small block size collectives" ({{Hopper in depth|https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/}}). NCCL calls the algorithm NVLS (since version 2.17, {{NCCL environment variables|https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/env.html}}). Section 7 shows why the gain is close to 2 in bytes and why measurements give less.

Other scale-up fabrics: NVLink-C2C, UALink (under 1 min)

Google's TPUs join chips directly in a torus over ICI, without switches (section 6). NVLink-C2C joins a Grace CPU to its GPUs at 900 GB/s ({{GB200 NVL72 blog|https://developer.nvidia.com/blog/nvidia-gb200-nvl72-delivers-trillion-parameter-llm-training-and-real-time-inference/}}). UALink is an open scale-up standard: its 1.0 specification defines 200 Gb/s lanes, 800 Gb/s per four-lane station and "up to 1024 endpoints" with load/store semantics ({{UALink Consortium, May 2025|https://ualinkconsortium.org/blog/ualink-200g-1-0-specification-overview-802/}}); AMD's Helios rack carries it over Ethernet (parent page, Chip atlas).

4. Leaving the server: RDMA, InfiniBand and RoCE

Past the NVLink domain, GPUs in different servers talk through NICs. The ordinary way, a program calling the operating system's TCP stack, copies every byte through kernel memory, takes interrupts and backs off on loss; at 400 Gb/s per GPU that costs CPU time and microseconds the GPUs spend idle ({{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}} explains TCP, and its section 14 why clusters avoid it for heavy traffic). Remote direct memory access (RDMA) moves the whole transport into the NIC. Step through it against the TCP path:

RDMA takes the CPU and the kernel off the data path: the NIC reads one GPU's memory and writes another's

  1. TCP, for contrast. Bytes are copied from GPU memory to a host buffer, through the kernel's socket buffers to the NIC, and the same in reverse on the receiver: CPU copies and interrupts on both sides.
  2. Register memory. The program tells the NIC which buffer it may touch (on a GPU server, a buffer in GPU memory); the NIC pins it and gets a key. With GPUDirect RDMA the NIC reaches GPU memory across PCIe without the CPU copying it.
  3. Create a queue pair. Each connection is a pair of queues (send and receive) that live in the NIC; a reliable connection keeps ordering and retransmission in hardware.
  4. Post work. The program writes a small descriptor ("write these bytes into the remote buffer at this address with this key") into the queue and rings a doorbell. No system call, no copy.
  5. The NICs move the data. A one-sided RDMA write lands in the remote buffer without the remote CPU doing anything; completion shows up in a completion queue, which the GPU or CPU polls.

The same RDMA operations run on three kinds of fabric: InfiniBand, RoCE (RDMA over Converged Ethernet: the InfiniBand transport inside UDP packets, port 4791, on ordinary routed Ethernet) and AWS's EFA (its own SRD protocol); each is described in the closed block below, and how NCCL picks between them, or falls back to TCP sockets, is on {{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}}, section 14. What separates InfiniBand from RoCE is how each avoids dropping packets, because RDMA's hardware transport recovers from a lost packet slowly. Meta trained Llama 3 405B over RoCE at 400 Gb/s per GPU (closed block below).

The three RDMA fabrics in one paragraph (under 1 min)

InfiniBand is a separate network built for RDMA, with its own adapters and switches ({{InfiniBand Trade Association|https://www.infinibandta.org/}}). RoCEv2 carries the same RDMA operations in UDP datagrams to port 4791 over ordinary routed Ethernet and IP (IANA registered 4791/udp to the InfiniBand Trade Association in 2014, {{IANA port registry|https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml?search=4791}}); the UDP header is only an envelope, and reliability lives in the RDMA transport and the fabric. AWS EFA is an OS-bypass interface whose transport is the Scalable Reliable Datagram (SRD) protocol, with built-in congestion control, reached through Libfabric, which ML applications use through NCCL and NIXL ({{EFA documentation|https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html}}).

InfiniBand never sends without buffer space; RoCE pauses the sender once a buffer fills

InfiniBand: credits

"Each receiving end of a link supplies credits to the sending device ... Data is not transmitted unless the receiver advertises credits indicating receive buffer space is available" ({{Mellanox, Introduction to InfiniBand|https://network.nvidia.com/pdf/whitepapers/IB_Intro_WP_190.pdf}}). So the fabric never drops for lack of buffer. Current NVIDIA switches add adaptive routing and in-network reduction (SHARP). vendor

RoCE: lossless Ethernet by configuration

Ethernet drops packets when buffers fill; RoCE needs Priority Flow Control (PFC), pause frames sent hop by hop, plus ECN marking and a congestion-control algorithm, usually DCQCN. The Ultra Ethernet Consortium names the costs: DCQCN "requires careful manual tuning", a lost packet triggers "Go-Back-N" retransmission, and PFC backpressure "can produce 'congestion trees' and head-of-line blocking" ({{UEC overview, 2023|https://ultraethernet.org/wp-content/uploads/sites/20/2023/10/23.07.12-UEC-1.0-Overview-FINAL-WITH-LOGO.pdf}}). In exchange it is multi-vendor and runs on the Ethernet a data centre already has.

In-network reduction (SHARP). NVIDIA's InfiniBand switches can do the additions of an all-reduce themselves (SHARPv3 on Quantum-2, SHARP v4 on Quantum-X800), so data "traversing the network" shrinks as it climbs a reduction tree ({{NVIDIA SHARP docs|https://networking-docs.nvidia.com/sharpum/300/introduction}}). SemiAnalysis measured the effect: without SHARP the all-reduce slows as GPUs are added, "In contrast, with SHARP, the speed/completion time stays the same. We have results for up to 1,024 H100s" ({{SemiAnalysis, Dec 2024|https://semianalysis.com/2024/12/22/mi300x-vs-h100-vs-h200-benchmark-part-1-training/}}) independent.

RoCE at scale: Meta's Llama 3 cluster without DCQCN (under 1 min)

RoCE at scale, in a real run. Meta trained Llama 3 405B over RoCE at 400 Gb/s per GPU (smaller models on InfiniBand). "LLM training produces fat network flows that are hard to balance across all available network paths using traditional methods such as Equal-Cost Multi-Path (ECMP) routing", so "our collective library creates 16 network flows between two GPUs, instead of just one" and an enhanced ECMP hashes on more header fields; with that balancing and "Deep-buffer switches in the spine", they ran "without traditional congestion control methods such as ... (DCQCN)" ({{Llama 3 report, section 3.3.1|https://arxiv.org/html/2407.21783v3}}). ECMP sends every packet of one flow down one path to keep order, so a few huge flows collide on some links while others sit idle; more flows per connection spread them.

Where Ethernet is going. The Ultra Ethernet Consortium released its Specification 1.0 on June 11, 2025 ({{UEC press release|https://ultraethernet.org/ultra-ethernet-consortium-uec-launches-specification-1-0-transforming-ethernet-for-ai-and-hpc-at-scale/}}). AWS's SRD already sprays and tolerates reordering (its user guide: "built-in OS-bypass and congestion control through the Scalable Reliable Datagram (SRD) protocol", {{EFA|https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html}}).
