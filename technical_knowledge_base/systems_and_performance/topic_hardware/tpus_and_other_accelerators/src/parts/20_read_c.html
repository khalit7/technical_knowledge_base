1. Systolic arrays from zero

The problem. Take the running example: the gate projection of one Llama 3.1 8B layer for one 8,192-token sequence, an 8,192 × 4,096 matrix of activations X times a 4,096 × 14,336 weight matrix W. That is 2 × 8,192 × 4,096 × 14,336 = 9.62 × 1011 FLOPs derived, but only 34 million activations and 59 million weights. Every weight is used 8,192 times (once per token) and every activation 14,336 times (once per output column). The arithmetic is cheap; what costs energy and time is fetching the operands each time they are used.

How cheap? Mark Horowitz's table of rough energy costs at 45 nm ({{Horowitz, ISSCC 2014|https://gwern.net/doc/cs/hardware/2014-horowitz-2.pdf}}, Figure 1.1.9; old process, so read the ratios, not the absolute numbers): a 16-bit floating-point multiply costs 1.1 pJ and a 32-bit add 0.9 pJ, so one bf16 multiply with an fp32 accumulate is about 2 pJ derived. A register-file access costs about 6 pJ, a 64-bit read from an 8 KB SRAM 10 pJ, from a 1 MB SRAM 100 pJ, and from DRAM 1.3 to 2.6 nJ. A programmable core also pays about 70 pJ per instruction for fetching and decoding it. So a machine that fetches both operands from a register file for every multiply-add spends most of its energy on the fetches. The question for an accelerator designer is: how many times is each number fetched from storage, per multiply-add?

How a systolic array answers it. A systolic array is a grid of identical multiply-accumulate cells, each wired only to its neighbours. In the weight-stationary layout the TPU uses, each cell is loaded with one weight, which then stays put. A row of activations enters from the left edge and moves one cell to the right per clock cycle; at each cell it is multiplied by that cell's weight, and the product is added to a partial sum that moves one cell down per cycle. A finished dot product leaves the bottom of each column. Because row k must meet the partial sum coming from row k − 1, each row of input starts one cycle later than the row above (the skew), so the work moves through the grid as a diagonal wave. The name comes from the heart: data is pumped through in rhythm. The TPU v1 paper says it directly: "As reading a large SRAM uses much more power than arithmetic, the matrix unit uses systolic execution to save energy by reducing reads and writes of the Unified Buffer ... data flows in from the left, and the weights are loaded from the top. A given 256-element multiply-accumulate operation moves through the matrix as a diagonal wavefront" ({{Jouppi et al. 2017, section 2|https://arxiv.org/abs/1704.04760}}).

What it shows. On this tiny problem the array is slower: 15 cycles against 8, because the wave needs time to fill the array and drain out of it, and two thirds of the cell-cycles are idle. But it read storage 36 times against 160. The fill and drain cost a fixed number of cycles per tile, and the reads saved grow with the matrix, so the trade only pays at scale, which is exactly where matrix multiplies in training live.

cycles per tile = M + K + N − 2    (after its K × N weights are loaded)
M
rows of X streamed through (tokens in the batch)
K, N
the weight tile's rows and columns, at most the array's side

A big matrix multiply is cut into tiles the size of the array. While one tile streams, the next tile's weights shift in behind it (double buffering), so in steady state each tile costs max(M, R) cycles on an R × R array, and the fill and drain are paid once. For the running example on a 128 × 128 array that is 32 × 112 = 3,584 tiles, each streaming 8,192 rows; reads per multiply-add fall to 1/128 + 1/8,192 = 0.0079 (each activation read once per 128 output columns, each weight once), about 250 times fewer than the scalar lanes' 2 derived.

The cost: the array only likes big, aligned matrices
  • Padding. A dimension that is not a multiple of the array's side wastes a whole tile. K = N = 130 on a 128 × 128 array needs 4 tiles for the work of about 1.03: 26% utilisation. How To Scale Your Model's rule: weight matrices "need to be padded to at least size 128 (256 on TPU v6e) in both dimensions to fill up the MXU" ({{scaling book, TPUs|https://jax-ml.github.io/scaling-book/tpus/}}).
  • Small batches. With fewer rows of X than the array's side, the array waits for the next tile's weights to shift in: 8 tokens per chip on a 128-wide array reach at most 8/128 = 6% of peak in this model, before HBM bandwidth (which limits decode anyway, see the root's {{memory section|n:3c65c17b0d0d8118beeefaed56da6f8e}}) is even counted.
  • Bigger is not always better. Google measured that four 128 × 128 arrays reached 37% to 48% utilisation on its production models, 1.6 times one 256 × 256 array (22% to 30%) in about the same area, because many real matrices are smaller than 256 ({{Jouppi et al., CACM July 2020|https://doi.org/10.1145/3360307}}). TPU v6e moved to 256 × 256 anyway, betting that today's matrices are big enough.
  • Everything else. Softmax, normalisation, activation functions and anything with data-dependent control flow run on a much smaller vector unit beside the array (section 2).

Is a GPU tensor core a systolic array? It solves the same problem at a smaller scale: one tensor-core instruction multiplies a small matrix tile (for example m16n8k16, a 16 × 16 by 16 × 8 product, in the {{PTX ISA|https://docs.nvidia.com/cuda/parallel-thread-execution/index.html}}) with operands fetched once into registers, so it also divides fetches per multiply-add by the tile size. NVIDIA does not publish the circuit inside a tensor core, so whether it is "systolic" is not stated; what matters is the reuse factor, which is the tile size. The instructions and tile shapes (mma, wgmma, tcgen05) belong to {{Topic: cuda-and-gpu-programming|n:3c65c17b0d0d81c39f34d5e070d783c1}}; the tensor core generations to the sibling {{GPU architecture|n:3c65c17b0d0d810682aae39bd614ec64}} page. AWS Trainium's tensor engine (section 6) is a 128 × 128 systolic array too, and Groq's 320 × 320 matrix arrays (section 7) attack the same problem.
