5. AMD Instinct: a GPU built from chiplets, with more memory

The bet. AMD builds the same kind of machine as NVIDIA (a GPU: many cores, thousands of threads, caches) and competes on memory per GPU and on price, while its software, ROCm, catches up with CUDA. The design is the interesting part, because it shows how a big chip is made from small ones.

MI300X, die by die. Instead of one huge die, the package stacks 8 compute dies (XCDs, TSMC 5 nm) on top of 4 I/O dies (TSMC 6 nm), surrounded by 8 HBM3 stacks. Each XCD has 40 compute units (CUs, AMD's SM) of which 38 are switched on, "with 2 disabled for yield management", so 8 × 38 = 304; each XCD has its own 4 MB L2 cache. The I/O dies hold a 256 MB "Infinity Cache" in front of memory (17.2 TB/s peak) and the HBM controllers, two stacks per I/O die, 24 GB per stack, so 192 GB at 5.3 TB/s. Each CU does 2,048 dense bf16 FLOPs per clock in its matrix cores, so 304 × 2,048 × 2.1 GHz = 1,307.4 TFLOPS, exactly AMD's figure ({{AMD CDNA 3 white paper|https://www.amd.com/content/dam/amd/en/documents/instinct-tech-docs/white-papers/amd-cdna-3-white-paper.pdf}}) derived, reproduces.

What chiplets buy and cost. Small dies yield better (a defect kills one small die, not a giant one; the two spare CUs per XCD absorb more) and let each part use the process that suits it. The cost is distance: the XCDs' L2 caches are only "coherent within an XCD", so data shared across the chip goes through the Infinity Cache, and MI300X can even be split into "up to eight partitions, one per XCD". NVIDIA's Blackwell made the same move with two dies (sibling {{GPU architecture|n:3c65c17b0d0d810682aae39bd614ec64}} page).

MI355X (CDNA 4). 8 XCDs on 3 nm with 32 of 36 CUs on (256 CUs), only 2 I/O dies, 8 stacks of 12-high HBM3E (288 GB, 8 TB/s), 4,096 bf16 FLOPs per CU per clock at 2.4 GHz (256 × 4,096 × 2.4 GHz = 2,516.6 TFLOPS, AMD's figure) plus MXFP6 and MXFP4 at 16,384. Local shared memory (LDS, AMD's name for shared memory) grew from 64 KB to 160 KB per CU, and TF32 left the hardware: it is "supported through software emulation utilizing the BF16 datatype" ({{AMD CDNA 4 white paper|https://www.amd.com/content/dam/amd/en/documents/instinct-tech-docs/white-papers/amd-cdna-4-architecture-whitepaper.pdf}}).

Eight GPUs without a switch. An NVIDIA HGX server joins its 8 GPUs through NVSwitch chips, so any GPU can send to any other at full NVLink speed. AMD's 8-GPU board instead gives every GPU 7 Infinity Fabric links, one straight to each other GPU, "to form a fully connected 8-GPU system": 7 × 128 GB/s = 896 GB/s aggregate on MI300X (64 GB/s each way per link), 7 × 153.6 = 1,075.2 GB/s on MI355X. A collective that uses all 7 links at once (an all-reduce, an all-to-all) sees the aggregate; a copy between two GPUs sees one link, a seventh of it. The scale-up domain stops at 8; AMD's answer for 72 is the announced Helios rack (72 MI455X joined by UALink over Ethernet, 3.6 TB/s per GPU; AMD calls it "a reference design, not a product for sale", {{AMD MI400|https://www.amd.com/en/products/accelerators/instinct/mi400.html}}) announced.

The trap when porting kernels: 64-thread wavefronts
AMD's equivalent of a warp, the wavefront, is 64 threads on CDNA 3 and 4 (MI300X, MI355X), not 32 ({{ROCm hardware specifications|https://rocm.docs.amd.com/en/latest/reference/gpu-arch-specs.html}}). Code that assumes 32 (a 32-bit lane mask, a 32-way shuffle reduction, a block of 32 threads per warp) silently computes the wrong thing or wastes half the machine. AMD's MI455X page advertises "Wave32 execution" for its next architecture, so the answer is changing by generation announced.

What it means for your training code. Mostly nothing, by design: "PyTorch for HIP intentionally reuses the existing torch.cuda interfaces", so .to('cuda'), torch.cuda.synchronize() and the rest run unchanged on a ROCm build (check torch.version.hip) ({{PyTorch HIP notes|https://docs.pytorch.org/docs/2.14/notes/hip.html}}); collectives go through RCCL, AMD's NCCL; Triton supports "AMD GPUs (ROCm 6.2+)" ({{Triton README|https://github.com/triton-lang/triton}}); CUDA C++ is translated by HIPIFY. The cost is everything below the framework: custom CUDA kernels, libraries that ship only CUDA builds, and tuning. An independent test in December 2024 found BF16 matmuls on MI300X reaching about 620 of its 1,307 peak TFLOPS against about 720 of 989.5 on H100, and wrote that "MI300X performance is held back by AMD software" ({{SemiAnalysis, Dec 22 2024|https://newsletter.semianalysis.com/p/mi300x-vs-h100-vs-h200-benchmark-part-1-training}}); ROCm has had two major versions since, so re-measure before you decide.

Go deeper (optional). ROCm, HIP and the current ROCm 10 release from the programmer's side: section 10, "Other stacks", of {{Topic: cuda-and-gpu-programming|n:3c65c17b0d0d81c39f34d5e070d783c1}}. Every AMD part's peaks, memory and price beside NVIDIA's: the root's "Chip atlas" tab.

6. AWS Trainium: systolic arrays you can program, on AWS only

The bet. Vertical integration: AWS designs the chip (through its Annapurna Labs team), the links, the SDK and the data centre, and rents it below the price of GPUs with NVIDIA's margin. You can only get it as an AWS instance.

Inside a NeuronCore. A Trainium2 chip has 8 NeuronCores; each is "a fully-independent heterogenous compute unit" with four engines and its own scratchpad ({{NeuronCore-v3|https://awsdocs-neuron.readthedocs-hosted.com/en/latest/about-neuron/arch/neuron-hardware/neuron-core-v3.html}}):

Tensor engineA systolic array: "a grid of 128x128 processing elements" at 2.4 GHz. You load a stationary tile, then stream a moving tile across it ("LoadStationary", "MultiplyMoving"): the same weight-stationary idea as section 1. 79 bf16 TFLOPS per core; for fp8 each cell does two multiplies, which looks like a 256 × 128 array.
Vector engineOperations where each output depends on many inputs (layer norm, pooling).
Scalar engineElementwise work: activations, exponentials.
GpSimd engine"Eight fully-programmable 512-bit wide vector processors" that run C code for custom operators.
SBUF and PSUM28 MiB of software-managed SRAM per core, laid out as 128 partitions (one per row of the array), plus a 2 MiB buffer for partial sums. Like a TPU, no cache: the compiler or your kernel moves data.

Sources: {{Trainium2 architecture guide for NKI|https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/guides/architecture/trainium2_arch.html}}; {{Trainium2|https://awsdocs-neuron.readthedocs-hosted.com/en/latest/about-neuron/arch/neuron-hardware/trainium2.html}} and {{Trainium3|https://awsdocs-neuron.readthedocs-hosted.com/en/latest/about-neuron/arch/neuron-hardware/trainium3.html}} pages, all fetched 2026-10-05.

Check the peak. 128 × 128 cells × 2 FLOPs × 2.4 GHz = 78.6 TFLOPS per core, matching the docs' 79; × 8 cores = 629 TFLOPS, but the chip page says 667 derived. The 6% gap is not explained in the docs (perhaps a different clock); the page shows it rather than hiding it.

Chips into machines. A Trn2 instance has 16 Trainium2 chips "connected using a 4x4, 2D Torus topology" over NeuronLink (1,024 GB/s per chip inside the instance), and a Trn2 UltraServer joins 4 instances, 64 chips, with chips at the same position linked in rings (256 GB/s more per chip): a small TPU-like torus ({{Trn2 architecture|https://awsdocs-neuron.readthedocs-hosted.com/en/latest/about-neuron/arch/neuron-hardware/trn2-arch.html}}). Trainium3 changes course: its UltraServers (64 or 144 chips) use switches, "replacing the previous 2D-torus architecture" with all-to-all connectivity ({{Trn3 architecture|https://awsdocs-neuron.readthedocs-hosted.com/en/latest/about-neuron/arch/neuron-hardware/trn3-arch.html}}). The docs give three different per-chip link figures for Trainium3 (2.56 TB/s, 2,048 GiB/s, and 704 GB/s from the listed PCIe links), so no single number is quoted here. At scale: Project Rainier, "nearly half a million Trainium2 chips" across several US data centres, built for Anthropic ({{Amazon, Oct 29 2025|https://www.aboutamazon.com/news/aws/aws-project-rainier-ai-trainium-chips-compute-cluster}}).

What it means for your training code. Three ways in, in flux. The newest is TorchNeuron, a native PyTorch device: "Change .to('cuda') to .to('neuron')" and compile with torch.compile(backend="neuron"), with FSDP, DTensor, DDP and tensor parallelism; the docs call it "recommended" on one page and "only available as part of a closed Beta program" on another ({{PyTorch on Neuron|https://awsdocs-neuron.readthedocs-hosted.com/en/latest/frameworks/torch/index.html}}). The older torch-neuronx path is built on PyTorch/XLA (lazy tensors, whole graphs compiled ahead of time, so static shapes matter, as on a TPU) and JAX runs through a plugin in beta. Custom kernels are written in NKI, a Python kernel language "similar to numpy and Triton" whose tiles are bounded by the hardware: the first dimension is the partition dimension (at most 128), and a matmul's stationary tile is at most 128 × 128 and its moving tile 128 × 512 ({{NKI|https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/get-started/about/index.html}}). Anthropic says it writes "low-level kernels that allow us to directly interface with the Trainium silicon" ({{Anthropic, Nov 22 2024|https://www.anthropic.com/news/anthropic-amazon-trainium}}). Inferentia is the inference-only sibling on the same SDK.
