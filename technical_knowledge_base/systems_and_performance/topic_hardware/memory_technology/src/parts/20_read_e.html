5. Capacity against bandwidth: why you rarely get both

The problem. Bandwidth comes from many short wires; capacity comes from many dies. Both compete for the same scarce thing, the space next to the processor. An HBM stack holds at most 16 dies (64 GB at the standard die size), and each stack needs its own wide interface along the edge of the GPU die and the interposer, so only so many stacks fit. Going further from the die (board, CPU socket, another node, an SSD) buys capacity cheaply but the wires get longer, fewer and slower.

The result is a ladder. Each rung below is a published figure (or measured here), drawn on a logarithmic scale: every grid step is 10×.

Two readings. First, from HBM down to the host link the bandwidth drops about 26× on an H100 (3,350 against 128 GB/s, and that 128 is both directions together), so anything that crosses PCIe once per step must be small or overlapped with compute (section 7). Second, the network to another node (50 GB/s for a 400 Gb/s NIC) is slower again: a model sharded across nodes pays for it on every step, which is why parallelism is chosen around the network (sibling {{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}}).

Unified memory blurs one rung
Apple's M1 Pro has one pool of LPDDR5 shared by CPU and GPU: no copy, no PCIe, but only 200 GB/s. NVIDIA's GH200 joins a Grace CPU and a Hopper GPU with a 900 GB/s coherent NVLink-C2C link, "7X faster than PCIe Gen5", sharing one page table for up to 624 GB of CPU and GPU memory ({{NVIDIA GH200|https://www.nvidia.com/en-us/data-center/grace-hopper-superchip/}}). Coherent does not mean equally fast: the GPU still reads its own HBM much faster than the CPU's LPDDR5X.

6. What lives in memory: weights, training state, the KV cache

Weights and training state. Serving needs the weights: 2 bytes per parameter in BF16, 1 in FP8, about 0.5 in 4-bit formats (plus their scales). Training with mixed-precision Adam needs about 16 bytes per parameter (BF16 weights and gradients, FP32 master weights and two FP32 moments) plus activations: 128.5 GB of state for Llama 3.1 8B, more than one 80 GB H100 holds. The parent's {{Performance calculator|n:3c65c17b0d0d8118beeefaed56da6f8e}} computes these for any model and recipe; {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}} derives them. This section is about the one item whose size depends on the conversation, not the model.

The KV cache. When a transformer generates token t, each attention layer compares its query with the keys of all earlier tokens and mixes their values. Recomputing every earlier key and value at every step would repeat the whole prefix, so they are kept in memory: the KV cache. Its size is fixed by the attention layout in config.json:

KV bytes per token = 2 × layers × KV heads × head dimension × bytes per value
2
one key and one value vector
KV heads
32 for Llama 2 7B (one per query head, "MHA"); 8 for Llama 3.1 8B (grouped-query attention, "GQA": 4 query heads share each KV head)

Llama 3.1 8B: 2 × 32 × 8 × 128 × 2 bytes = 128 KiB per token; a 32,768-token conversation holds 4.29 GB, a quarter of the weights; 4 such conversations hold more than the weights. Llama 2 7B, with 32 KV heads, needs 512 KiB per token: 17.18 GB at the same 32K context derived from config.json.

Architectures since 2023 attack this number in four ways, each a different trade:

Fewer KV heads (GQA, MQA)Share each key/value head among several query heads: 8 KV heads in Llama 3.1, 4 in Qwen3 235B, 1 in multi-query attention. 4× to 32× less cache than MHA.
Compress the cache (MLA)DeepSeek's multi-head latent attention caches one 512-value latent plus a 64-value RoPE key per layer instead of full keys and values: (dc + dhR) × layers ({{DeepSeek-V2, Table 1|https://arxiv.org/html/2405.04434v5}}). DeepSeek-V3: 68.6 KiB per token for a 671B model. Animated on the {{DeepSeek page|n:3c65c17b0d0d81a2ae7ec6796947a235}}.
Forget old tokens (sliding windows)Some layers attend only to the last W tokens and keep only those: every layer of Mistral 7B v0.1 (W = 4,096), five of every six layers of Gemma 3 (W = 1,024), half the layers of gpt-oss (W = 128). The cache of those layers stops growing.
Replace attention (linear and state-space layers)Qwen3-Next uses Gated DeltaNet in three of every four layers: a fixed-size state per sequence instead of a growing cache. Only 12 of its 48 layers keep a KV cache: 24 KiB per token.

Quantising the cache. Storing keys and values in FP8 halves the cache; vLLM's cache_dtype option does it ({{vLLM cache config|https://github.com/vllm-project/vllm/blob/74c5cbcd7b6fa07fa5568ba7f7dfbfedc502964e/vllm/config/cache.py}}). Quality effects are on {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}.

Allocating the cache. A server does not know how long each answer will be. Reserving the maximum length per request wasted most of the memory: in the systems measured by the PagedAttention paper only 20.4% to 38.2% of KV memory held actual tokens. vLLM stores the cache in fixed blocks (default 16 tokens) allocated on demand, limiting waste to one partly filled block per request, and improved throughput 2 to 4× ({{Kwon et al. 2023|https://arxiv.org/abs/2309.06180}}). The same idea as virtual memory pages ({{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}}). By default vLLM claims 92% of GPU memory for weights, activations and these blocks (gpu_memory_utilization = 0.92 in the source above). The before/after animation of contiguous against paged allocation is on the {{PagedAttention paper page|n:3c65c17b0d0d81bf8b90ca93fee19f5f}} (tab "Simulate the KV cache").

Decode is bound by these bytes

A decode step reads every weight once (shared by the batch) and every sequence's KV cache once (not shared). On the M1 Pro GPU one attention step over a 128K-token GQA cache (8 KV heads of 128, 512 MiB in FP16) took 4.11 ms; a straight line through the GQA points from 64 MiB up gives 141 GB/s plus a fixed 0.30 ms per call, the memory's sequential speed plus launch overhead measured here. The same 64K context with 32 KV heads (MHA) holds 4× the bytes and took 5.9× as long (13.0 against 2.2 ms): MLX's kernel streams the MHA layout at only about 81 GB/s. With 1 KV head (MQA) the cache is 8× smaller than GQA's, yet the step still took 3.66 ms at 128K: the bytes are no longer the limit, the kernel's arithmetic is. Bytes set a floor; the kernel decides how close you get (all three curves are in the {{Memory lab|#t-lab}}).

The cost
Every trick that shrinks the cache gives something up: fewer KV heads or a compressed latent change the model and must be trained in; windows forget; FP8 adds rounding error; paging adds an indirection to every attention read (block tables). None of them shrink the weights.

When it matters. For training, the KV cache does not exist (attention over a whole sequence is computed at once), but RL post-training generates rollouts, so it is back. For serving, KV memory decides the batch, and the batch decides the cost per token. How to check: vLLM logs the number of KV blocks it could allocate at start-up; torch.cuda.max_memory_allocated() for your own loop.
