6. Decode is bound by the bytes it reads

A decode step reads every weight once (shared by the whole batch) and every sequence's KV cache once (not shared), and does about 2 FLOPs per weight per sequence. At small batch the arithmetic is idle and

time per step ≥ (weight bytes + Σsequences KV-cache bytes) / bandwidth

Llama 3.1 8B on an H100: 16.06 GB / 3.35 TB/s = 4.8 ms, at most 209 steps per second at batch 1 derived. Batching shares the weight read, so tokens per second grow with the batch until the KV reads or the arithmetic take over (the parent's Performance calculator finds that point for any model).

What else is in memory. Serving needs the weights: 2 bytes per parameter in BF16, 1 in FP8, about 0.5 in 4-bit formats (plus their scales). Training with mixed-precision Adam needs about 16 bytes per parameter (BF16 weights and gradients, FP32 master weights and two FP32 moments) plus activations: 128.5 GB of state for Llama 3.1 8B, more than one 80 GB H100 holds ({{Performance calculator|n:3c65c17b0d0d8118beeefaed56da6f8e}}; derivation in {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}). The KV cache keeps every earlier token's attention keys and values so they are not recomputed; Llama 3.1 8B (8 KV heads) keeps 128 KiB per token, so a 32,768-token conversation holds 4.29 GB, a quarter of the weights, and 4 such conversations hold more than the weights derived from config.json. Sizing it for any model and context, and the designs that shrink it (fewer KV heads, latents, windows, recurrent layers), are owned by {{Long context|n:3fd5c17b0d0d81059ee1ce20c0326dc5#t-kv}} and {{Attention variants|n:3fd5c17b0d0d8120859ecc2d0236e846}}. Each way of shrinking it costs something: fewer KV heads or a latent must be trained in, windows forget, FP8 adds rounding error, paging adds a block-table indirection to every read; none of them shrinks the weights. Storing keys and values in FP8 halves the cache (vLLM's cache_dtype, {{vLLM cache config|https://github.com/vllm-project/vllm/blob/74c5cbcd7b6fa07fa5568ba7f7dfbfedc502964e/vllm/config/cache.py}}); quality effects are on {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}.

Measured: one attention step against the cache. MLX's fused attention for one new token in one layer (a whole model repeats it per layer; 32 query heads of 128, FP16) against 1K to 128K cached tokens with 32 KV heads (MHA, like Llama 2), 8 (GQA, like Llama 3.1 8B) or 1 (MQA). Predict before switching views: if bytes decide, the three lines should collapse onto one when plotted against cache bytes.

Time follows cache bytes: GQA on the line, MHA slower per byte, MQA arithmetic-bound

One step over a 128K-token GQA cache (512 MiB in FP16) took 4.11 ms; a straight line through the GQA points from 64 MiB up gives 141 GB/s plus a fixed 0.30 ms per call, the memory's sequential speed plus launch overhead measured here. The same 64K context with 32 KV heads holds 4× the bytes and took 5.9× as long (13.0 against 2.2 ms): MLX's kernel streams the MHA layout at only about 81 GB/s. With 1 KV head the cache is 8× smaller than GQA's, yet the step still took 3.66 ms at 128K: the bytes are no longer the limit, the kernel's arithmetic is. Bytes set a floor; the kernel decides how close you get.

Allocating the cache. A server does not know how long each answer will be. Reserving the maximum length per request wasted most of the memory: in the systems measured by the PagedAttention paper only 20.4% to 38.2% of KV memory held actual tokens. vLLM stores the cache in fixed blocks (default 16 tokens) allocated on demand, limiting waste to one partly filled block per request, and improved throughput 2 to 4× ({{Kwon et al. 2023|https://arxiv.org/abs/2309.06180}}), the idea of virtual memory pages ({{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}}). A 16-token block holds, per layer and KV head, 16 × 128 × 2 bytes = 4 KiB of keys: big enough to read at near-sequential speed by section 2's measurement. By default vLLM claims 92% of GPU memory for weights, activations and these blocks (gpu_memory_utilization = 0.92 in the source above). The animation of contiguous against paged allocation is on the {{PagedAttention paper page|n:3c65c17b0d0d81bf8b90ca93fee19f5f}}.

When it matters. Training has no KV cache (attention over a whole sequence is computed at once), but RL post-training generates rollouts, so it is back. In serving, KV memory decides the batch, and the batch decides the cost per token; HBM capacity per GPU is why a 288 GB part can be worth more than a 180 GB one with the same 8 TB/s (B300 against B200). Check: vLLM logs the number of KV blocks it could allocate at start-up; torch.cuda.max_memory_allocated() for your own loop; bytes per step / step time against the datasheet bandwidth.
