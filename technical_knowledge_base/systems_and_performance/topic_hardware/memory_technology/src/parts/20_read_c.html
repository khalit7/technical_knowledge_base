2. A DRAM cell, a row, a bank: why order matters and bandwidth costs power

The cell. DRAM (dynamic random-access memory) stores one bit as charge on a microscopic capacitor, reached through one transistor ({{Wikipedia, DRAM|https://en.wikipedia.org/wiki/Dynamic_random-access_memory}}): dense and cheap. The charge leaks, so every row must be refreshed (read and rewritten) within a fixed interval, 64 ms for DDR2 and half that above 85 °C case temperature ({{Wikipedia, Memory refresh|https://en.wikipedia.org/wiki/Memory_refresh}}).

The array. An activate connects a whole row of capacitors to sense amplifiers, which amplify the tiny voltages to full 0s and 1s and hold them: the row buffer (reading drains the capacitors, so the amplifiers write the values back while the row is open). A read then picks a few columns and sends them out in a burst. Opening another row first needs a precharge to close this one. A chip has several independent banks, each with its own row buffer, so one bank can activate while another sends data. In HBM2 a row is 1 KB ({{O'Connor et al., MICRO 2017|https://research.nvidia.com/publication/2017-10_fine-grained-dram-energy-efficient-dram-extreme-bandwidth-systems}}). So the cost of a read depends on what was read before it. The same 16 reads of 64 bytes, in three orders (pick one above the timeline):

The same 16 reads, step by step

  1. Sequential: one row. Sixteen reads of 64 bytes, 1 KB in all, every one from the same 1 KB row of one bank.
  2. Read 1: open the row. The bank is idle: activate the row (14 ns), read the column (14 ns), send the burst (2 ns). Data is out at 30 ns.
  3. Read 2: a row hit. The row is already in the row buffer: only a column read and a burst, pipelined behind the first. Done at 32 ns.
  4. Reads 3 to 8. Every read hits the open row, so the bursts follow one another on the bus every 2 ns: 44 ns.
  5. Reads 9 to 16. Done after 60 ns: one activate, 1 KB opened for 1 KB used, 17.07 GB/s from this one bank and bus.
  1. Random: one bank. The same sixteen reads, now to 16 different rows of one bank.
  2. Read 1: open a row. As before: activate, column read, burst. Data is out at 30 ns.
  3. Read 2: a row miss. Another row is open: precharge it (14 ns), activate the new row (14 ns), then read (14 ns) and send the burst. Done at 74 ns, 44 ns for one read.
  4. Reads 3 to 8. Every read pays precharge and activate again, and nothing overlaps: 338 ns.
  5. Reads 9 to 16. Done after 690 ns: 16 activates opened 16 KB of rows to use 1 KB, 1.48 GB/s, eleven times slower than sequential.
  1. Random: 16 banks. The same sixteen rows, now spread over 16 banks, one read each.
  2. Read 1: open a row. Activate, column read, burst: 30 ns.
  3. Read 2: another bank. Bank 1 is idle, so its activate starts 4 ns after the first (the gap between activates to different banks), overlapping read 1. Done at 34 ns.
  4. Reads 3 to 8. An activate every 4 ns, each in its own bank; only the data bus is shared: 58 ns.
  5. Reads 9 to 16. Done after 90 ns: still 16 KB of rows opened (the energy is spent), but the time is hidden, 11.38 GB/s, two thirds of sequential.

Random reads into one bank pay precharge plus activate every time and open 16 KB of rows to use 1 KB. Spreading them over many banks hides most of that, which is why memory controllers interleave consecutive addresses across banks and channels, and why a GPU wants many independent requests in flight.

Timings are illustrative DDR-class values (activate to read 14 ns, read to data 14 ns, precharge 14 ns, 2 ns per 64-byte burst, 4 ns between activates to different banks), not those of a specific part; the 1 KB row is HBM2's. illustrative The order of the three results does not depend on the exact values: 60 ns, 690 ns and 90 ns here, checked against a Python reference (code/build_data.py).

Measured on this laptop: 512 MB of the M1 Pro GPU's memory read in random blocks. Blocks of 16 bytes delivered 5.5 GB/s of useful data, 128-byte blocks 40.7 GB/s, 4 KB blocks 142.9 GB/s, close to the sequential rate measured here.

The GPU fetches whole cache lines, so a 16-byte read costs as much as a 128-byte one. That is the hardware fact behind coalescing (how a kernel arranges its loads to use whole lines: {{GPU memory hierarchy|n:3c65c17b0d0d814a8edef7bd21c303d3}}, section 1) and behind serving engines storing the KV cache in blocks of many tokens (section 6).

Below one 128-byte line, a smaller read costs the same time: useful bandwidth falls in proportion

Why bandwidth costs power

Mark Horowitz's widely used 45 nm energy table, as reprinted by {{Han et al. (2015), Figure 1|https://arxiv.org/abs/1506.02626}}: reading 32 bits from off-chip DRAM costs 640 pJ, a 32-bit float multiply 3.7 pJ, 173 times more (right).

The arithmetic is cheap; the wire is not. In stacked HBM2 a bit cost about 3.92 pJ: 1.21 pJ to activate rows, 2.24 pJ to move the bits across the DRAM die and down the through-silicon vias, about 0.3 pJ for the short interposer wires, the rest error correction; off-board GDDR5 cost about 14.0 pJ per bit ({{O'Connor et al. 2017|https://research.nvidia.com/publication/2017-10_fine-grained-dram-energy-efficient-dram-extreme-bandwidth-systems}}, Figure 1 and section 2) published measurement model. At 3.92 pJ per bit an H100 reading at its full 3.35 TB/s would spend 3.35 × 1012 × 8 × 3.92 pJ = 105 W on memory alone, and Rubin's 22 TB/s would spend 690 W derived, illustrative, so HBM3 and HBM4 must cost less per bit than HBM2 for Rubin to exist (SK hynix claims more than 40% better power efficiency for HBM4, section 8). One token of Llama 3.1 8B at batch 1 reads 16.06 GB of weights: about 0.50 J per token just to move them, divided over the batch when batching derived, illustrative.

Each activate opens a 1 KB row even if 32 bytes are wanted, and O'Connor et al. note most GPU workloads use only a small fraction of each activated row, which is why activation energy is a large share. Element-wise kernels (normalisation, activations, optimizer updates) stream every byte once and run at the sequential bandwidth; gathers (embedding lookups, MoE routing, paged KV reads) run at the rate their block size allows. Check: Nsight Compute's DRAM throughput against the device peak, and sectors per request (many 32-byte sectors per request means scattered access).
