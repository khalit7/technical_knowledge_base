The KV cache of thirteen released models, computed from their config.json files, and what it does to a GPU's memory. Every model's cache follows one rule: keys and values per token per layer, times the layers that keep them, times the tokens they keep. derived from config.json

1. One conversation grows (before/after on the same input)

The same conversation, from 1K to 128K tokens, on one model at a time, drawn to scale inside one GPU's memory with the model's weights. Switch the architecture and replay: the conversation is the same; only how the model stores it changes.

One GPU's memory to scale; the weights are bytes as released (a model larger than the GPU overflows the bar: it needs several GPUs). KV in BF16. Decode time per token at batch 1 = (weights + this conversation's cache) / bandwidth, a ceiling that ignores everything else derived.

2. KV cache against context, all thirteen

One sequence, BF16 cache, log scales. Lines that bend flat are windows filling (Mistral at 4,096 tokens) or layers whose cache stops growing (Gemma 3's local layers at 1,024; gpt-oss's at 128); Qwen3-Next starts above zero because of its fixed linear-attention state (assumed 2 bytes per value).

3. How many conversations fit

Assumptions, all ceilings: memory = GPUs × capacity × the fraction the server may use (vLLM's default gpu_memory_utilization is 0.92), minus the weights, split evenly; activations and the CUDA context are not modelled beyond that fraction. A decode step reads every weight byte once and every sequence's cache once, at the GPUs' combined bandwidth; real servers land below it, and a mixture-of-experts model reads fewer weight bytes at small batch (the parent's {{Performance calculator|n:3c65c17b0d0d8118beeefaed56da6f8e}} models expert routing and tensor-parallel communication; this tab does not).
