In JAX you write the step for one device and give a few arrays a layout over a named grid of devices; someone then lays out every other array (the compiler's propagation, the type system, or you inside shard_map), and the communication is whatever those layouts force. Communication is a consequence of layout, so you read it off the compiled program, never off the Python.

Three annotations in, one program per device out, with the collectives the layouts force

1. You annotate a few arrays
mesh = jax.make_mesh((2, 4), ('data', 'model'))
w = jax.device_put(w, NamedSharding(mesh, P('data', 'model')))
x = jax.device_put(x, NamedSharding(mesh, P('data', None)))
loss, grads = jax.jit(step)(w, x)

The running example's fc1 weight w [128, 512] and a batch x [32, 128], on 8 devices arranged as a (data 2, model 4) mesh. Nothing else in step mentions devices.

2. Each device holds one block

w as P('data', 'model'): rows split by data, columns by model; each device holds (64, 128), as jax.debug.visualize_array_sharding printed here. x is split by rows only, so the 4 devices of a data row hold the same 16 rows.

You know how PyTorch spreads a model over GPUs: you pick a wrapper (DDP, FSDP2, a tensor-parallel plan) or a DTensor placement, and it owns the communication. JAX works the other way round: change one PartitionSpec and a different set of collectives appears in the compiled program, while the Python code does not change.

You need {{JAX core|n:3c65c17b0d0d81b7a0d1faba6cef5561}} (jit, tracing, vmap), the parallelism forms from {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}} (this page shows only JAX's API and behaviour for each), and HLO dumps from {{XLA and compilation|n:3fa5c17b0d0d8135adcedefac9e1bb48}}.

measured means run here on an Apple M1 Pro CPU with 8 simulated devices (XLA_FLAGS=--xla_force_host_platform_device_count=8, jax 0.11.2): the compiled programs, the collectives and their sizes, the memory figures and the losses are real and deterministic; speeds are not (a "collective" between simulated devices is a memory copy). TPU numbers are published by Google; arithmetic on them is derived.

New terms

Mesh
a grid of devices with named axes, such as (data 2, model 4).
PartitionSpec, P
for each dimension of an array, the mesh axes that split it; None means not split.
NamedSharding
a mesh plus a PartitionSpec: what device_put and jit take.
Collective
a step in which devices exchange data: all-gather, all-reduce, reduce-scatter, all-to-all, collective-permute.
Sharding propagation
the compiler pass that gives unannotated arrays a layout: GSPMD (2021) or its successor Shardy, the default.
SPMD partitioner
the XLA pass that rewrites the program for one device and inserts the collectives.
Axis type
Auto, Explicit or Manual: who decides layouts along a mesh axis.
shard_map
per-device code over a mesh, in which you call the collectives yourself.
Multi-controller
one Python process per host, all running the same program.
ICI, DCN
the chip-to-chip links inside a TPU slice; the data-centre network between slices ({{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}}).
