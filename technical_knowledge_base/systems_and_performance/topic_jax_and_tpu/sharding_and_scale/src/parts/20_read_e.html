What each row teaches

  • Data parallel: one all-reduce of exactly the gradient bytes (101,670,916 for 25.4M float32 parameters plus 4 bytes for the loss). XLA's CPU AllReduceCombiner merged every gradient into one collective. Each device still holds all parameters and Adam state: 305 MB of 305 MB.
  • FSDP: weights split 8 ways, so parameters plus Adam state per device fall from 305 MB to 38 MB. The all-gathers carry the weights once (101.7 MB), not twice: XLA kept the gathered weights alive from the forward pass to the backward pass instead of gathering again. That is the textbook "ZeRO-3 without re-gather" point, chosen by the compiler; it costs activation-like memory (temp 412 MB per device against 311 MB for data parallel).
  • HSDP (2 replicas x FSDP over 4): the all-gathers stay inside groups of 4, and the gradient is reduced in the group then all-reduced across the 2 replicas on a quarter of the bytes. That is the layout for a multi-slice job: FSDP inside the fast ICI domain, data parallel across the slow data-centre network.
  • Tensor parallel: activations, not weights, cross the wire: 2 all-reduces of a [batch, sequence, d_model] activation per layer forward, and here 4 backward. On TPU or GPU it would be 2: XLA's AllReduceReassociate pass, which merges the q, k and v input-gradient all-reduces into one, runs in the GPU pipeline and not the CPU one (). Bytes grow with batch and sequence, not with parameters: 227 MB at 25.4M parameters against 102 MB for data parallel.
  • Tensor parallel over 8 with only 4 heads (the running example): 1.33 times the predicted bytes, because 4 heads cannot be split 8 ways and the compiler has to reshuffle the attention. The scaled model, with 8 heads, matches the prediction to 7 significant digits. Keep the tensor-parallel degree a divisor of the number of heads (of KV heads, with grouped-query attention).
  • FSDP x tensor parallel: the most memory-efficient here and the one that drew XLA's warning, pasted from the compile: . The partitioner could not move an activation from one layout to the other directly, so it replicated it and re-split it. A warning like this is a performance bug report; the fix is a with_sharding_constraint that names the layout you want at that point.
The PyTorch FSDP2 counterpart of XLA's keep-the-gathered-weights choice (20 s)

PyTorch FSDP2 makes the same choice explicit: fully_shard(reshard_after_forward=None), the default in torch 2.14.1, re-gathers in backward for every module except the root ("set to True for non-root modules and False for root modules", torch/distributed/fsdp/_fully_shard/_fully_shard.py:189).

7. Context parallelism: ring attention against all-gather

The problem. At long context the activations of one sequence no longer fit on one device, and splitting the batch does not help when the batch is one sequence. Context parallelism splits the sequence itself: device d holds tokens dT/N to (d+1)T/N − 1 of every sequence. Everything except attention is per-token and needs no communication. Attention needs every query to meet every earlier key. The three traffic patterns and the causal load balancing are {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}}'s section 8; here, what JAX compiles for each.

Three ways, run here. The running example's block-0 attention (q, k and v [32, 4 heads, 128 tokens, 32], real weights, causal) with the 128 tokens split 16 per device over 8 devices (src/runs/ss_cp.py):

  • Let propagation do it: annotate q, k, v as sequence-split and jit ordinary attention. The compiler all-gathers K and V.
  • All-gather by hand in shard_map: gather K and V, attend your own queries with the causal mask shifted by your offset. This is the variant Llama 3 used ({{Llama 3 paper, arXiv 2407.21783, section 3.3.2|https://arxiv.org/abs/2407.21783}}) and MaxText's default (context_parallel_strategy: "all_gather", ).
  • Ring attention ({{Liu, Zaharia and Abbeel 2023, arXiv 2310.01889|https://arxiv.org/abs/2310.01889}}): pass K/V blocks round the ring with ppermute, N steps, accumulating an online softmax (running max, denominator and numerator), so no device ever holds all keys or a full score matrix.

What the numbers say. All three give the one-device result (largest difference 7.5e-8 for the ring; gradients within 2.9e-6 for all three). Per device the ring sends exactly what a ring all-gather of K and V would (7 blocks of each: 3,670,016 bytes, against the all-gather's 4,194,304-byte output of which 7/8 arrives from other devices). The gain is memory: at 8,192 tokens the compiled temp memory is 123 MB per device for the ring against 273 MB for the all-gather version, because nobody holds all keys and values. The cost is N sequential steps, each needing its transfer to overlap with compute. The schedule also shows the known flaw of a plain causal ring: device 0 has work in 1 of 8 steps and device 7 in all 8. Load-balanced orderings (each device holds a chunk from the start and one from the end of the sequence) fix that; MaxText's context_parallel_load_balance: true is the default (). Not run here: the load-balanced ordering, and DeepSpeed-Ulysses, which uses all-to-all to swap the sequence split for a head split ({{arXiv 2309.14509|https://arxiv.org/abs/2309.14509}}; MaxText's "ulysses" option).


Megatron's sequence parallelism is a different thing (30 s)
Megatron's sequence parallelism ({{Korthikanti et al. 2022, arXiv 2205.05198|https://arxiv.org/abs/2205.05198}}) is a different thing despite the name: inside a tensor-parallel group it splits the LayerNorm and dropout activations along the sequence, turning each all-reduce into a reduce-scatter plus an all-gather of the same total size. On CPU the reduce-scatter cannot be formed (no ReduceScatterCreator in the pipeline), so it is not shown separately here.
