Explicit mode on the whole running example

The problem it solves. In Auto mode a bad layout costs you nothing at trace time and a lot at run time: the compiler quietly inserts whatever collective makes the program correct. Explicit mode moves the decision to trace time. Each operation has a rule mapping input shardings to an output sharding; when the rule cannot decide, or would need communication you did not ask for, tracing stops with a ShardingTypeError. The JAX guide states the intent: the rules "prefer to error and require annotation rather than falling back to arbitrarily chosen defaults", to "get important parallelism decisions in your face, rather than hide them" ({{JAX docs, Distributed arrays and automatic parallelization|https://docs.jax.dev/en/latest/parallel.html}}, read 2026-10-15).

What it costs, measured. The running example's loss and gradient, traced on an Explicit mesh exactly as written for Auto mode, then with the smallest change each error asks for. Step through the attempts for each layout; every message is pasted from the run (src/runs/ss_explicit.py, the forward is model_jax.apply written out with hooks).

Layout

Three lessons from the ladder. First, even plain data parallelism needs one annotation: the embedding lookup tok_emb[idx] is a gather whose output layout JAX will not guess, so you write tok_emb.at[idx].get(out_sharding=P('data', None, None)) (). Second, FSDP in Explicit mode is literally written out: jax.reshard(w, P()) before each use is the all-gather, and the gradient comes back with the weight's own sharding (float32[128@data,512]), because the transpose of a reshard is a reshard. Third, Megatron's row-parallel matmul is the textbook ambiguous case: both operands are split along the summed dimension, so the result is a partial sum on every device, and you must say whether you want it summed and where (jnp.einsum(..., out_sharding=P('data', None, None)), ). After the fixes, data parallel compiles to the same single all-reduce of 3,305,476 bytes as the root lab's Auto-mode layout, tensor parallel to 17 all-reduces (loss and gradient only, no optimizer here), and every loss is within 4.8e-7 of one device.

JAX also has unreduced types, where "the logical value equals the distributed sum of the physical shards' values along that axis", for delaying a reduction (shown as f32[8,16]{U:X} in the guide). Not run here: the guide marks the details as still to come.

What each row teaches

  • Data parallel: one all-reduce of exactly the gradient bytes (101,670,916 for 25.4M float32 parameters plus 4 bytes for the loss). XLA's CPU AllReduceCombiner merged every gradient into one collective. Each device still holds all parameters and Adam state: 305 MB of 305 MB.
  • FSDP: weights split 8 ways, so parameters plus Adam state per device fall from 305 MB to 38 MB. The all-gathers carry the weights once (101.7 MB), not twice: XLA kept the gathered weights alive from the forward pass to the backward pass instead of gathering again. That is the textbook "ZeRO-3 without re-gather" point, chosen by the compiler; it costs activation-like memory (temp 412 MB per device against 311 MB for data parallel). PyTorch FSDP2 makes the same choice explicit: fully_shard(reshard_after_forward=None), the default in torch 2.14.1, re-gathers in backward for every module except the root ("set to True for non-root modules and False for root modules", torch/distributed/fsdp/_fully_shard/_fully_shard.py:189).
  • HSDP (2 replicas x FSDP over 4): the all-gathers stay inside groups of 4, and the gradient is reduced in the group then all-reduced across the 2 replicas on a quarter of the bytes. That is the layout for a multi-slice job: FSDP inside the fast ICI domain, data parallel across the slow data-centre network.
  • Tensor parallel: activations, not weights, cross the wire: 2 all-reduces of a [batch, sequence, d_model] activation per layer forward, and here 4 backward. On TPU or GPU it would be 2: XLA's AllReduceReassociate pass, which merges the q, k and v input-gradient all-reduces into one, runs in the GPU pipeline and not the CPU one (). Bytes grow with batch and sequence, not with parameters: 227 MB at 25.4M parameters against 102 MB for data parallel.
  • Tensor parallel over 8 with only 4 heads (the running example): 1.33 times the predicted bytes, because 4 heads cannot be split 8 ways and the compiler has to reshuffle the attention. The scaled model, with 8 heads, matches the prediction to 7 significant digits. Keep the tensor-parallel degree a divisor of the number of heads (of KV heads, with grouped-query attention).
  • FSDP x tensor parallel: the most memory-efficient here and the one that drew XLA's warning, pasted from the compile: . The partitioner could not move an activation from one layout to the other directly, so it replicated it and re-split it. A warning like this is a performance bug report; the fix is a with_sharding_constraint that names the layout you want at that point.
