1. Mesh, PartitionSpec and jit with shardings

The objects. jax.make_mesh((2, 4), ('data', 'model')) () arranges the 8 devices as a 2 × 4 grid with named axes. A PartitionSpec says, for each dimension of an array, which mesh axes split it; a mesh axis the spec does not name holds copies. A NamedSharding(mesh, spec) joins the two. Take the running example's first MLP weight, fc1, [128, 512] in float32 (262,144 bytes), and change only its spec:

Spec

The rule (derived from the definition, and matching what visualize_array_sharding printed for P('data', 'model'): (64, 128) per device): the size each device holds along dimension i is sizei divided by the product of the sizes of the mesh axes named for i; every element is held by as many devices as the product of the axes named nowhere. A tuple such as ('data', 'model') splits one dimension over both axes, data major. An axis may appear only once per spec: P('data', 'data') is refused because the spec "has duplicate entries" ().

Where shardings enter a program. jax.device_put(x, NamedSharding(mesh, spec)) places an array. jax.jit(f, in_shardings=..., out_shardings=...) fixes the layout of a function's inputs and outputs (the multi-host run in section 12 uses in_shardings=(rep, rep, xs, xs)); without them, jit takes the layouts its arguments already have. Inside, jax.lax.with_sharding_constraint(y, spec) () pins one intermediate. Every other array is left to whoever decides layouts along each mesh axis (section 2). JAX turns a NamedSharding into GSPMD's or Shardy's own notation (, ) when it hands the program to XLA.

2. Who decides the layout: Auto, Explicit, Manual

The problem. A train step creates hundreds of intermediate arrays (activations, gradients, optimizer updates). You annotate a handful: the parameters, the batch. Every other array needs a sharding too (which device holds which piece), and every place where an operation needs its inputs laid out differently from how they are is a collective. Something has to fill in the rest.

How JAX answers. Each named axis of a Mesh has an axis type (jax.sharding.AxisType), and the type says who decides along that axis (the hero's third panel):

Two defaults matter and changed recently. jax.make_mesh creates Explicit axes unless told otherwise (), so code from older tutorials fails at its first ambiguous op; pass axis_types=(AxisType.Auto,) * n to keep Auto behaviour. The jax.sharding.Mesh constructor still defaults to Auto, and the propagator behind Auto axes is Shardy, chosen by the flag jax_use_shardy_partitioner, default True (). The modes mix: jax.sharding.auto_axes and explicit_axes switch some axes inside one function (), and shard_map makes the axes it maps Manual inside its body while the rest of the program stays as it was.


When to use which
Auto when you trust a few annotations plus constraints (what MaxText does by default: shard_mode: "auto" # can be either auto or explicit, ). Explicit when you want every layout decision visible and checked, and accept writing out_sharding= in the places JAX asks. Manual for patterns no propagator invents: ring attention, pipelines, custom MoE dispatch, overlapping a collective with compute.
