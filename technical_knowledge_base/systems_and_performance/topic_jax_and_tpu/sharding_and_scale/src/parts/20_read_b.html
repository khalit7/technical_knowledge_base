Who decides the layout: Auto, Explicit, Manual

The problem. A train step creates hundreds of intermediate arrays (activations, gradients, optimizer updates). You annotate a handful: the parameters, the batch. Every other array needs a sharding too (which device holds which piece), and every place where an operation needs its inputs laid out differently from how they are is a collective, a step in which devices exchange data. Something has to fill in the rest.

How JAX answers. Each named axis of a Mesh has an axis type (jax.sharding.AxisType), and the type says who decides along that axis:

Two defaults matter and changed recently. jax.make_mesh creates Explicit axes unless told otherwise (), while the jax.sharding.Mesh constructor still defaults to Auto; and the propagator behind Auto axes is Shardy, chosen by the flag jax_use_shardy_partitioner, default True (). The root page's lab shows the first default in action; this page shows what each mode costs on the running example (Explicit mode) and what the propagator does (Propagation). The modes mix: jax.sharding.auto_axes and explicit_axes switch some axes inside one function (), and shard_map makes the axes it maps Manual inside its body while the rest of the program stays as it was.


When to use which. Auto when you trust a few annotations plus constraints (what MaxText does by default: shard_mode: "auto" # can be either auto or explicit, ). Explicit when you want every layout decision visible and checked, and accept writing out_sharding= in the places JAX asks. Manual for patterns no propagator invents: ring attention, pipelines, custom MoE dispatch, overlapping a collective with compute.







How sharding propagation decides


The problem. Assigning a layout to every array so that total communication is smallest is a search over an exponential space; production compilers do not solve it. Both of XLA's propagators are heuristics that spread your annotations through the program and never invent a new split you did not ask for. Knowing their rules is how you predict where they will go wrong.


GSPMD (2021): priorities and iterations


The design is in {{Xu et al., GSPMD, arXiv 2105.04663, section 3.5|https://arxiv.org/abs/2105.04663}} (v2, December 2021). Its rules, in order of importance:


    

  1. Preserved dimensions pass through. "XLA operators typically preserve some dimensions from inputs to outputs. We simply propagate sharding of such a dimension from inputs to outputs, and vice versa." A batch split on the input therefore reaches every activation.
    2. 

  2. Compatible shardings merge. A matmul's output takes its row split from one operand and its column split from the other when they use different mesh axes (the paper's Figure 3: AyB times BCx gives AyCx).
    3. 

  3. Iterate to a fixed point, refining only. The pass runs "in multiple iterations, and alternates between forward propagation (input to output) and backward propagation (output to input)"; it "changes the sharding on a tensor only when it finds a more fine-grained sharding", which guarantees it stops.
    4. 

  4. Priorities break ties. "Elementwise operators are assigned the highest priority to propagate through in both directions ... Operators like Dot, which add or remove dimensions are assigned lower priority", and a broadcast propagates backward before forward. Without priorities, the visiting order decides and "may result in mismatched sharding specifications around an elementwise operator" (Figure 4).
    5. 



The paper is explicit about the limit: "We decided to keep the sharding propagation simple, so it does not try to create new sharding patterns on dimensions. The propagation result may not always be optimal", and the remedy it gives is the one you will use: "the user can explicitly annotate the output to precisely control the sharding decision."


Shardy: axes, factors and a hierarchy


Shardy is the MLIR-based successor that JAX switched to by default in 0.7.0 ("JAX is migrating from GSPMD to Shardy by default"). The {{Shardy propagation doc|https://openxla.org/shardy/propagation}} and {{sharding representation doc|https://openxla.org/shardy/sharding_representation}} (both read 2026-10-15) describe three differences:


    

  • Axis-based, not device-list-based. A sharding names mesh axes per dimension, like a PartitionSpec; GSPMD's HloSharding is a tile assignment over a device list. A dimension can be open (?: "open for propagation to further shard it along additional axes") or closed.
    • 

  • One rule per operation, in factors. Each op gets an einsum-like sharding rule, a matmul being (i, k), (k, j) -> (i, j); reshapes use compound factors such as ((ij), k). "Shardy propagates sharding axes along factors instead of dimensions": project the operands' shardings onto factors, merge, project back.
    • 

  • An explicit hierarchy of strategies, "interpreted as nested for loops": user priorities ({"x"}p1), then operation priorities ("pass-through" ops such as elementwise and reshape first, dot and reduce later, the same idea as GSPMD's), then aggressive propagation (resolves conflicts), then basic propagation ("propagates axes that are compatible between all operands and results", no conflict resolution). Loops, conditionals and shard_map regions are crossed through "data flow edges".
    • 



Both propagators hand their result to the same SPMD partitioner, which rewrites the program per device and inserts the collectives: XLA's CPU pipeline adds either sdy::ShardyXLA () or ShardingPropagation (), then StatefulRngSpmdPartitioner. Turning Shardy off in jax 0.11.2 still works and prints a warning, pasted from the run: GSPMD sharding propagation is going to be deprecated and not supported in the future. Please consider migrating to Shardy (https://openxla.org/shardy). For reference, Shardy is already the default partitioner in JAX.


Reading what the propagator chose


Dump the program right after propagation with XLA_FLAGS="--xla_dump_to=DIR --xla_dump_hlo_pass_re=shardy-xla|sharding-propagation". The same tensor (the running example's q = x @ wq under Megatron tensor parallelism on a (data 2, model 4) mesh) in the two notations, pasted from the dumps:


# Shardy: per dimension, the mesh axes that split it
dot(...), sharding={mesh['data'=2,'model'=4], [{'data'}, {}, {'model'}]}
# GSPMD: a tile grid [2,1,4] over devices 0..7 in order (iota)
dot(...), sharding={devices=[2,1,4]<=[8]}


Both say P('data', None, 'model'). A GSPMD sharding with last_tile_dim_replicate adds a final grid dimension of copies (devices=[2,1,1,4]<=[8] last_tile_dim_replicate is P('data', None, None) replicated over the 4 model devices). The {{Propagation explorer|#t-prop}} converts every operation of one block to the P(...) form for both propagators.

The lesson is not that one propagator is better: on the unconstrained FSDP layout GSPMD was the better one. It is that a layout that depends on propagation for the activations is fragile. The root lab's FSDP layout with one with_sharding_constraint on the residual stream per block compiles to the same collectives under both (78 all-gathers and 70 all-reduces each). Constrain activations at block boundaries, as MaxText does through its logical axis rules.
