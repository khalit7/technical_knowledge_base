Two Python processes, four devices each, one global mesh of eight: the running example's data-parallel train step run the multi-host way on one machine, and compared with the same step in one process.

On a TPU slice bigger than one host, every host runs the same script. To try that without a slice, src/runs/ss_multi.py starts two processes on this machine, each with 4 simulated CPU devices (--xla_force_host_platform_device_count=4), and connects them with jax.distributed.initialize over localhost; collectives between the processes go over gloo, JAX's default for CPU. Each process loads only its half of every batch. measured jax 0.11.2.

The two errors you will meet




On a real slice


    

  • Launching. The same script is started on every host of the slice (on Cloud TPU, one command over all workers; under GKE or Slurm, one pod or task per host). jax.distributed.initialize() then needs no arguments: the JAX guide lists Slurm, Kubernetes and Cloud TPU as environments where they "are automatically populated". Not run here.
    • 

  • Data. Each host reads only its shard of the data. The data loader's job is to give host h the rows that its devices hold under the batch sharding; make_array_from_process_local_data assembles the global array without communication. Deterministic, checkpointable per-host loading with grain is on the {{training stack|n:3c65c17b0d0d817ea0ace9a2ca8677ec}} page.
    • 

  • Checkpoints and logging. Orbax writes and restores sharded arrays from every host (training stack page). Logging only from jax.process_index() == 0 is fine; putting a device_put or a jitted call under that condition is not: the guide warns it "would lead to a deadlock as only process 0 initiates the collective communication".
    • 

  • Across slices. Multislice jobs add the data-centre network between slices; MaxText's dcn_*_parallelism settings put data parallelism there (Reading tab, {{Choosing a mesh|#t-read}}).
