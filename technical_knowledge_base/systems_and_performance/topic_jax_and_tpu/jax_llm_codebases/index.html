JAX LLM codebases: MaxText, Tunix, levanter

What MaxText, Tunix and Levanter each optimise for, how a config becomes a sharding and a compiled train step, and which to start from; read at pinned commits and run on the topic's running example (Apple M1 Pro CPU). Data as of October 2026. Reading: 27 min, plus 8 in closed details.

A production JAX LLM codebase is the same five boxes as your own training loop (configuration, model, sharding, train step, data and checkpoints) with one difference that reshapes all of them: the model never names a device, so a config decides the shapes, the sharding and the remat policy, and one jitted pure step turns them into a single XLA program. The codebases differ in which box they invest in: MaxText in config and sharding for scale on TPU, Tunix in the train step for post-training, Levanter in named axes and reproducible data.

Same five boxes, different investments: the highlighted cell is what each codebase is built for

The running example is the topic's 826,368-parameter character model (268 lines: model_jax.py plus common.py); MaxText holds the same boxes in 213,293 lines of Python. Reading a large codebase is finding these five boxes and the one or two ideas it adds to each. The Codebase map tab has every part of the three repositories with its size and the symbols worth reading at their lines.

You need: tracing and jax.jit (JAX core), meshes and PartitionSpec (Sharding and scale), Flax NNX split and merge, optax and Orbax (The JAX training stack). New terms:

Logical axis names: one name per dimension of a weight or activation (embed, mlp, heads), never a device.
Logical axis rules: an ordered table in the config mapping each name to mesh axes; the first free rule wins.
scan_layers: run one traced layer over weights stacked on a layers axis.
remat_policy: which named intermediates the backward pass keeps instead of recomputing.
role_to_mesh: Tunix's map from an RL role (actor, reference, rollout) to a device mesh.
Named axis (Haliax): an array dimension addressed by name in every operation, not by position.

1. MaxText's config is the program's input

One codebase trains a 0.6B Qwen on 8 chips and a 671B DeepSeek on thousands. PyTorch codebases carry the choices in argument parsers (Megatron's arguments.py, hundreds of flags) or TOML job files (torchtitan); MaxText reads a layered YAML into a validated object, and the model and train step read that object while they are traced, so every value is baked into the compiled program. pyconfig.initialize () builds it in this order, later layers winning:

  1. configs/base.yml: 1,669 lines, 828 top-level keys, every default with a comment.
  2. configs/models/<model_name>.yml (86 model files): shapes, activations, tokenizer, sometimes extra sharding rules.
  3. Command-line key=value pairs and Python keyword arguments.
  4. Environment variables named M_<KEY> ().

A pydantic class with 907 fields, MaxTextConfig (), then validates and derives what the code reads: emb_dim from base_emb_dim, global_batch_size_to_train_on from per_device_batch_size times the device count. Logical axis rules are merged by hand (): a model file's rule replaces every base rule with the same name. Degrees set to -1, such as ici_fsdp_parallelism, are resolved only when the mesh is built.

Ten real parses: pick an override set and see what the code will read measured

Each is a real call of pyconfig.initialize then maxtext_utils.get_mesh_from_config at main 1a95d1e5 on 8 simulated CPU devices (runs/lc_cfg.py, out/cfg.json), about 0.1 to 3 s each.

What it catches, and what it does not. A typo fails at start-up (remat_polcy=full raises ValueError: 'remat_polcy' not in 'emb_dim', 'mlp_dim', ... and lists every valid key); a valid key with a surprising default does not. Three to know before copying MaxText's numbers elsewhere: learning_rate: 3.e-5 (a fine-tuning value), adam_b2: 0.95 (optax and PyTorch default to 0.999), and adamw_mask: [], which decays every parameter including biases, norm scales and embeddings (section 4 measures what that costs). To check a run, diff resolved configs, not command lines: log_config (true by default, ) logs every resolved key, and cfg.get_keys() returns them. The Config explorer tab has 81 flags with line, default, comment and value per model file.

2. The model, with the running example inside it

Transformer () is a Flax NNX module (MaxText "migrated to Flax NNX from Linen" in June 2026, ) owning the token embedding and an NNXDecoder (layers/nnx_decoders.py, 2,943 lines). Which layer it runs is a config value, decoder_block, one of 25 DecoderBlockType values () each mapped to a class: DecoderBlockType.GPT3: [gpt3.Gpt3DecoderLayer] (). The layers run inside jax.lax.scan over stacked weights, each wrapped in jax.checkpoint with the configured remat policy (; section 5). Attention is also chosen at trace time, by attention= and the hardware.

Shapes and transforms are those runs/lc_fwd.py applied; every final shape matched the one MaxText created (the script asserts it). One cell is 8 × 8 numbers for matrices, one number for the scale.

  • Layout. PyTorch stores a linear weight [out, in]; MaxText's DenseGeneral [in, out...] with the output split into named axes ([embed, heads, kv]).
  • Stacking. With scan_layers=true each per-layer weight gains a layers axis at param_scan_axis = 1 (): four [128, 128] query weights become one [128, 4, 4, 32] array. This is why checkpoint converters exist.
  • An offset scale. Gpt3LayerNorm initialises its scale to zeros () and multiplies by scale + 1 (). Copy PyTorch's weight unchanged and every LayerNorm doubles its output, silently. Weight decay also pulls this scale toward 1, not 0.
  • The activation. mlp_activations=[gelu] resolves to getattr(jax.nn, "gelu") (), the tanh approximation; the running example uses exact erf GELU, and no MaxText flag spells it. Against exact GELU the logits differ by up to ; with a tanh-GELU twin the gap falls to , float32 rounding.

3. How a config becomes a sharding: logical axis names and rules

In Megatron-LM tensor parallelism lives in the model: a ColumnParallelLinear knows it is split and calls the all-reduce, so changing the parallelism means changing model code. MaxText's model never names a device. Every parameter is created with one logical axis name per dimension: Llama 2's MLP input kernel is ("embed", "layers", "mlp"), the query kernel ("embed_attn", "layers", "q_heads", "kv"); activations get names through maybe_shard_with_logical, which becomes with_sharding_constraint. Three config entries then decide where everything lives:

  • The mesh: 12 named axes (), diloco, data, stage, fsdp, fsdp_transpose, context, context_usp_ulysses, context_autoregressive, tensor, tensor_sequence, expert, autoregressive, sized by ici_*_parallelism (inside a slice) and dcn_*_parallelism (across slices); most are 1.
  • The 80 logical axis rules (), applied by logical_to_spec (): "A dimension takes the first matching rule whose mesh axes no other dimension uses yet" ().
  • Size-1 axes are dropped, which is why long rule lists collapse to a short PartitionSpec. Flax Linen's logical_to_mesh_axes does the same; what a PartitionSpec does and which collectives the compiler inserts is on Sharding and scale.

One weight walks the rule table: a rule whose mesh axis is taken is skipped, so changing one degree re-shards the model without touching it

Rule order explains a puzzle in the YAML: embed has two rules, one with fsdp_transpose and one without (). mlp's rule comes first () and takes fsdp_transpose; the first embed rule collides and is skipped, the second applies. One table serves every weight, and two-dimensional FSDP falls out of rule order.

When it fails. The running example's vocabulary of 65 cannot be split four ways. Under ici_tensor_parallelism=4 MaxText still builds the abstract model, with P('tensor', 'fsdp') and P('fsdp', 'tensor') on the embedding and output kernel, and asking for their per-device shape raises IndivisibleError: ... implies that array axis 1 is partitioned 4 times, but the dimension size is 65. base.yml's comment on vocab_size says "powers of 2 for sharding"; real vocabularies are padded to a multiple of 128 or more (which also suits the MXU).

How to check. Print the shardings of the abstract model before compiling anything (debug_sharding=true makes setup_train_loop call print_shardings_params); at start-up assert_params_sufficiently_sharded allows sharding_tolerance (2% by default) of parameters unsharded. Pipeline parallelism uses the stage axis; its bubble formula is in base.yml () and measured on Sharding and scale.

4. The train step: one pure function, compiled once

A PyTorch step mutates objects (loss.backward() fills .grad, optimizer.step() updates in place). MaxText's train_step () is a pure function from (state, batch) to (new state, metrics):

  1. nnx.merge(model, state) () rebuilds the TrainStateNNX module (model plus nnx.Optimizer) inside the trace from a static graph definition and a pytree of arrays (the split/merge pattern of the training stack).
  2. jax.value_and_grad(diff_wrapper, argnums=(0, 1), has_aux=True) () differentiates loss_fn () over the trainable nnx.Param leaves: forward, cross-entropy over non-padding tokens, auxiliary losses (MoE load balance, z-loss, multi-token prediction) when configured.
  3. Gradients are cast to grad_dtype, clipped by global norm () and applied by state.apply_gradients(grads) (), the optax chain.
  4. Metrics (loss, raw and clipped gradient norm, parameter norm) come back as arrays, so logging never forces a device-to-host copy inside the step.

jit_train_step () wraps it in jax.jit with in_shardings and out_shardings from the logical rules and donate_argnums = 0 (): the old state's buffers become the new state's, which keeps peak memory at one copy of parameters and optimizer state; the donated input arrays are invalid after the call.

5. Scan over layers, and what remat keeps

With scan_layers: true () the decoder traces one layer inside jax.lax.scan over stacked weights, so the program and the compile time stop growing with depth (PyTorch eager has no counterpart; under torch.compile the closest is compiling one block and reusing it; scan against a Python loop is measured on JAX core; nnx.scan is on the training stack). Each scanned layer is wrapped in jax.checkpoint(layer_fn, policy=policy) with the policy named by remat_policy (, default full) through get_remat_policy (): full keeps only each layer's input and recomputes the rest in the backward pass; the others keep tensors the layers name with checkpoint_name (query_proj, key_proj, value_proj, out_proj, mlpwi, mlpwo, context; e.g. ). minimal () keeps every projection output; the *_offloaded policies move them to host memory. PyTorch's counterpart is torch.utils.checkpoint with a selective policy.

Predict: for the running example's step compiled by MaxText, which policy needs the most temporary memory, and which does the most FLOPs?
minimal keeps the most (149.7 MB of XLA temporaries against 100.1 MB for full) and full recomputes the most (28.90 GFLOP against 24.61 GFLOP, layers unrolled).

What it shows. For a given scan setting every policy gives bit-identical losses: remat changes what is stored, never the result. minimal stores 50% more than full and saves 15% of the FLOPs (4.29 GFLOP of recomputed forward). save_out_proj came out below full (87.4 MB against 100.1 MB): XLA's buffer assignment on CPU is not monotone in what the policy saves, so measure rather than assume. Scan: 8,166 lines of optimised HLO against 22,270 unrolled, for only four layers. On TPU the ordering transfers and the sizes do not (bfloat16 activations, thousands of tokens, HBM per chip): pick the policy that fits HBM with the fewest recomputed FLOPs, the arithmetic TPU programming and performance does for real chips.

Two details of the remat runs, and MaxText's checkpoints

The unrolled rows start from different random weights (first-step loss 4.5451 against 4.5840 scanned): with the same seed, creating four layers one by one does not draw the same numbers as one stacked array. Converting a checkpoint between layouts is stacking or unstacking the same numbers. minimal_with_context equals minimal here because the gpt3 block names no context tensor.

Checkpoints. MaxText writes them with Orbax's v1 API (from orbax.checkpoint import v1 as ocp, ; ocp.training.Checkpointer, ), asynchronously by default (), every 10,000 steps (), and resumes automatically: "If there is already a checkpoint for this run_name, we load the latest entire checkpoint" (). Not run here (every run sets enable_checkpointing=false); the training stack runs Orbax itself.

6. How MaxText counts MFU, and what its published table used

Model FLOPs utilisation (MFU) is the model's FLOPs per step divided by step time and peak FLOP/s (Performance math derives it). MaxText's count, calculate_tflops_training_per_device (), takes every weight matmul at 2 FLOPs per multiply-add, times 3 for forward plus backward ("multiply by 3 to account for 1 forward pass + 2 backward passes", ), plus attention's score and value products, halved for the causal mask since July 2025 (causal_attention_flops = noncausal_attention_flops / 2, ; the docs, ). It counts the output projection, not the embedding lookup, and never recomputation, so heavier remat lowers MFU without changing the count. On the running example's step: 21.14 GFLOP (19.53 in weight matmuls, 1.61 in attention), against 23.69 from XLA's cost analysis (the JAX core page's measurement), which counts unmasked attention, elementwise work and softmax. MFU uses the analytic count on purpose: it does not depend on the implementation.

7. Tunix: a thin trainer and RL placement by mesh

Tunix ("Tune-in-JAX", ) is Google's post-training library on Flax NNX: SFT with full weights or LoRA, DPO and ORPO, PPO, GRPO and its variants (GSPO-token, DAPO, Dr.GRPO), multi-turn agentic RL and distillation, with vLLM's TPU backend or SGLang-JAX for generation. MaxText's post-training is Tunix underneath: its SFT, DPO and RL entry points import tunix.sft.peft_trainer, tunix.sft.dpo.dpo_trainer and tunix.rl.grpo.grpo_learner (, , ). The algorithms are taught on Alignment: SFT, RLHF, DPO family, RLVR and RL for LLMs; this section is about the code.

The trainer is twenty lines measured. PeftTrainer._train_step () is the whole algorithm, wrapped in nnx.jit(train_step, donate_argnames=("optimizer",)) (); the rest of the 882-line file is data iteration, metrics, profiling and checkpoints:

inputs = self.gen_model_input_fn(inputs)
grad_fn = nnx.value_and_grad(self.loss_fn,
    argnums=nnx.DiffState(0, nnx.LoRAParam) if self._lora_enabled else 0, has_aux=self._has_aux)
out, grads = grad_fn(model, **inputs)
grad_norm = optax.global_norm(grads)
optimizer.update(model, grads)

LoRA is not a separate code path: if the model carries nnx.LoRAParam variables, the optimizer is built with wrt=nnx.LoRAParam () and only they get gradients. Gradient accumulation is optax.MultiSteps around your optimizer (). So Tunix trains the running example as it is: runs/lc_tunix.py gave PeftTrainer the root's NNX model, optax chain and loss (with_loss_fn, with_gen_model_input_fn), and 100 steps matched the root's own NNX run to in loss. Its default loss () normalises by target tokens plus 1e-8 (), so an all-padding batch gives zero loss instead of NaN.

RL: models by role, each on a mesh. RL for an LLM needs up to five models: the actor being trained, a frozen reference for the KL penalty, a rollout engine that generates, a reward model and, for PPO, a critic. Tunix's Role enum names them (), and ClusterConfig.role_to_mesh is "Key config for colocated vs disaggregated setup" (). Same mesh for actor and rollout: they share one copy of the weights (), and with LoRA the reference shares the actor's frozen backbone too (). Different meshes: every step ends with sync_weights () pushing the actor's parameters to the rollout engine, which is "vanilla", "vllm" or "sglang_jax" ().

One GRPO step: colocated roles take turns on one mesh; disaggregated roles overlap but move weights every step

Placement

Colocated is simpler and moves no weights, but training and generation take turns on the same chips; disaggregated lets a generation-optimised engine (vLLM's TPU backend) run on its own slice, at the cost of a weight transfer every step. 8. Levanter in Marin: named axes and bitwise reproducibility

Levanter is Stanford CRFM's trainer, "built with JAX, Equinox, and Haliax", designed to be "legible, scalable, and reproducible": "Levanter is bitwise deterministic, meaning that the same configuration will always produce the same results, even in the face of preemption and resumption" (). It now lives in the Marin monorepo (lib/levanter).

Where Levanter lives now, and what Marin is

The standalone repository says "Levanter has been merged into Marin as of November 2025" (, frozen at 982cef7f); development continues in the Marin monorepo under lib/levanter (255 Python files, 87,114 lines at 1290cfb5), on PyPI as marin-levanter development builds (0.2.180.dev38754195437, uploaded 2026-10-15), requiring jax>=0.9.2,<0.12 (). Marin is an open research programme that logs every experiment; its README lists a scaling suite trained on Google's TPU Research Cloud and, as current work, a 500B+ parameter mixture-of-experts model. Its newer grug/ package (28 files) holds array-first building blocks for model templates; it was not read in depth here.

Named tensors. Haliax arrays carry a name per dimension and every operation names the axes it touches. Levanter's GPT-2 attention splits its fused projection with q, k, v = qkv_out.unbind("qkv") () and renames the keys' sequence axis, k.rename({"position": "key_position"}) (), because a product of two arrays that both have position would contract or broadcast the wrong one. In PyTorch you track this in comments next to transpose(1, 2); its experimental named tensors are little used. Modules are Equinox modules (plain pytrees), not Flax. The running example's attention, with named axes:

# runs/lc_haliax.py (abridged): block 0's attention of the running example, with named axes
Batch, Pos, KPos = Axis("batch", 32), Axis("position", 128), Axis("key_position", 128)
Embed, Heads, HeadSize = Axis("embed", 128), Axis("heads", 4), Axis("head_size", 32)
q = hax.dot(hn, W("wq"), axis=Embed) + Bv("wq")                        # [batch, position, heads, head_size]
k = (hax.dot(hn, W("wk"), axis=Embed) + Bv("wk")).rename({"position": "key_position"})
scores = hax.dot(q, k, axis=HeadSize) / math.sqrt(32)                  # no transpose to remember
probs = hax.nn.softmax(hax.where(causal, scores, -jnp.inf), axis=KPos)
ctx = hax.dot(probs, v, axis=KPos)
out = hax.dot(ctx, wo, axis=(Heads, HeadSize)) + bo

Sharding by name. Levanter has no separate logical vocabulary: a dictionary maps the model's own axis names to mesh axes (, , ). Mesh axes data (absorbs all devices), replica and model (1 each), replica_dcn across slices; mlp and heads map to model; for parameters only, embed maps to data, which is FSDP. Parameters and activations get separate mappings (parameter_axis_mapping, compute_axis_mapping), and the trainer reshards the new state with the parameter mapping after every update ().

WeightLevanter (default mapping, mesh data × model)MaxText (base rules, mesh fsdp × tensor)

Same idea, different spelling: FSDP on the embedding dimension, tensor parallelism on mlp and heads. Levanter specs from Haliax's pspec_for_axis with the default mapping (runs/lc_haliax.py); MaxText specs from runs/lc_shard.py on the running example's gpt3 config under fsdp 2 × tensor 4, without the stacked layers dimension.

Reproducibility. Bitwise determinism needs three things, all visible in the code: explicit PRNG keys (JAX has no global random state), a data loader that can jump to batch n without replaying the stream (Levanter writes a preprocessed cache with random access and shuffles with a pseudo-random permutation, ), and checkpoints that hold the step and the keys. The README's caveat: training "can even be resumed on a different number of hosts, though this breaks reproducibility for now". The TPU claim was not tested here; the CPU side was: the running example's reruns are deterministic, and the training stack shows a restored Orbax checkpoint continuing bit for bit on the same mesh, and drifting by about 3e-6 within 40 steps when restored into freshly annotated shardings.

Serving. Training codebases decode, but serving at scale is a separate engine. vLLM on TPU (tpu-inference 0.31.0, 2026-10-06, with vllm 0.31.0) is the default: vLLM's scheduler and paged KV cache with a TPU backend that, in vLLM's words, unifies "JAX and PyTorch under a single lowering path" (vLLM blog, 2025-10-16). JetStream, Google's earlier engine for MaxText models, announced it would archive on 2026-02-01 with its functions moved to tpu-inference; on 2026-10-15 GitHub still showed it unarchived, and MaxText still contains its engine (inference/maxengine/; decoupled mode stubs it out). Do not start new work on it.

The real errors you will meet, and the fix for each

Overriding a model file's key on the command line

ValueError: Keys ['base_emb_dim'] are overridden by both model config and CLI/kwargs with different values.This is not allowed, unless setting `override_model_config=True`.

Drop model_name and set every shape key yourself, or pass override_model_config=True knowingly.

Parallelism degrees that do not multiply to the device count

Parsing succeeds; the error comes when the mesh is built. Leave exactly one ICI degree at -1 and let it absorb the rest.


A dimension the mesh cannot divide
IndivisibleError: ... spec=P('fsdp', 'tensor') ... implies that array axis 1 is partitioned 4 times, but the dimension size is 65
Pad the vocabulary (and head counts) to multiples of the axis sizes you will use; 128 or 256 for the vocabulary.


Installing MaxText main with the Tunix release
ImportError: cannot import name 'diffusion' from 'tunix.sft' (unknown location)
Install both from MaxText's requirement files.


Leaving adamw_mask empty with RMSNorm-style scales
Biases, norm scales and embeddings get weight decay. For the gpt3 block the scale is an offset, so decay pulls it toward 1; for scales stored directly (RMSNorm models) it pulls them toward 0. Set the mask explicitly.


Reading FLOPs from cost_analysis() of a scanned program
XLA counts the loop body once: 7.40 GFLOP for the scanned step against 28.90 GFLOP unrolled, same computation.




Design question: GRPO fine-tuning of an 8B dense model on one v5p-64 slice. What do you build?
MaxText's model with Tunix's GRPO learner (what MaxText's RL entry point does), versions pinned together. Trainer: FSDP over the slice's ICI, bfloat16 activations, float32 master weights, remat_policy chosen by compiling a step and reading memory. Rollout: vLLM TPU; start colocated on the full slice (simplest, no weight sync), move to a split (for example 48 chips training, 16 generating) if generation dominates step time. Consider LoRA to cut memory and weight-sync volume. Checkpoint asynchronously with the data iterator state. Validate with a tiny config on CPU first (this page's method), then a short run measured against MFU with a stated FLOP count.


Design question: two teams report 45% and 40% MFU for the same run. How?
Different FLOP counts. MaxText halved attention FLOPs for causal masking in July 2025; its own table's Llama 3.1 8B row is 45.46% under the old count and 40.41% under the new one. Also check whether recomputation or the embedding is counted, and the peak FLOP/s used.


Design question: what breaks bitwise reproducibility when resuming?
A data loader that cannot seek (or reshuffles), PRNG keys not saved, a different number of hosts or a different mesh (reductions in a different order; Levanter's README says so), restoring into different shardings (the training stack page measured a 3e-6 drift), and nondeterministic kernels.


Design question: Levanter's named axes against MaxText's logical rules?
Levanter: the model's own axis names, mapped by a dictionary, separately for parameters and compute; operations name their axes, so shape bugs fail at trace time. MaxText: positional arrays with logical names attached, an ordered rule list with fallbacks (the two embed rules), more machinery for many parallelism kinds. Same compiler underneath.
