Common mistakes, with the real errors

Overriding a model file's key on the command line
ValueError: Keys ['base_emb_dim'] are overridden by both model config and CLI/kwargs with different values.This is not allowed, unless setting `override_model_config=True`.
Either drop model_name and set every shape key yourself, or pass override_model_config=True knowingly.
A typo in a key
ValueError: 'remat_polcy' not in 'emb_dim', 'mlp_dim', 'moe_mlp_dim', ... (every valid key)
Good: MaxText checks names. It cannot check that a valid key does what you think.
Parallelism degrees that do not multiply to the device count
Parsing succeeds; the error comes when the mesh is built. Leave exactly one ICI degree at -1 and let it absorb the rest.


A dimension that the mesh cannot divide
IndivisibleError: ... spec=P('fsdp', 'tensor') ... implies that array axis 1 is partitioned 4 times, but the dimension size is 65
Pad the vocabulary (and head counts) to multiples of the axis sizes you will use; 128 or 256 for the vocabulary also suits the MXU.


Copying LayerNorm weights into MaxText's gpt3 block unchanged
Its scale is stored as an offset from 1 (scale + 1); the PyTorch weight must be reduced by 1, or every norm doubles its output. Nothing errors; the loss is just wrong. Check by logits on a fixed batch.


Assuming "gelu" means the same thing everywhere
PyTorch's default is exact (erf); jax.nn.gelu defaults to the tanh approximation, and MaxText's mlp_activations=[gelu] inherits it. Logits differed by 7.0e-5 on the running example; enough to fail a tight equivalence test, small for training.


Comparing loss curves one step out of phase
MaxText's warmup starts at learning rate 0, so its first step is a no-op. Against a schedule that starts at lr/50 the curves differed by up to 0.088 here, all of it early.


Leaving adamw_mask empty
Biases, norm scales and embeddings get weight decay. For the gpt3 block the norm scale is an offset, so decay pulls the effective scale toward 1; for RMSNorm-style scales stored directly it pulls them toward 0. Set the mask explicitly.


Quoting an MFU without its FLOP count
MaxText's own table matches its pre-July-2025 (non-causal) count; the current count gives Llama 3.1 8B 40.41% instead of 45.46%. Ask which formula and which version.


Reading FLOPs from cost_analysis() of a scanned program
XLA counts a loop body once: 7.40 GFLOP for the scanned step against 28.90 GFLOP unrolled, same computation. Compare compiled FLOPs only between programs with the same loop structure.


Installing MaxText main with the Tunix release
ImportError: cannot import name 'diffusion' from 'tunix.sft' (unknown location)
MaxText's post-training pins Tunix to a GitHub commit. Install both from MaxText's requirement files.


Expecting a remat policy that saves more to always use more memory
save_out_proj used less temporary memory than full in the compiled CPU program here. Compile and read memory_analysis() for your shapes and backend.







Interview questions


How does MaxText change the parallelism of a model without editing the model?
Every weight and activation carries logical axis names; a config table of rules maps names to mesh axes, first free rule wins, size-1 axes dropped; the mesh sizes come from ICI and DCN degrees. jit compiles with those shardings and GSPMD/Shardy inserts the collectives. Changing ici_tensor_parallelism changes the specs, not the code.


Why scan over layers, and what does it cost?
One traced layer: compile time and program size independent of depth (8,166 against 22,270 HLO lines for just four layers here). Costs: weights stacked on a layer axis (checkpoint layout changes, converters needed), every layer must be identical in structure, and XLA cannot specialise per layer.


remat_policy full against minimal?
full keeps only each layer's input and recomputes the forward in the backward: least memory, most FLOPs. minimal keeps the projection outputs: about 50% more temporaries and 15% fewer FLOPs on the running example's step. Pick the cheapest policy that fits HBM; MFU does not count recompute, so heavier remat lowers MFU.


Two teams report 45% and 40% MFU for the same run. How?
Different FLOP counts. MaxText halved attention FLOPs for causal masking in July 2025; its own table's Llama 3.1 8B row is 45.46% under the old count and 40.41% under the new one. Also check whether recomputation or the embedding is counted, and the peak FLOP/s used.


You ported a model to MaxText. How do you show it is right?
Same weights, same batch: logits within float32 rounding (7.7e-7 here) at highest precision; then loss; then a few hundred steps against your own loop with every hyperparameter matched, explaining every residual (here: activation approximation, warmup phase, decay mask). Only then train for real.


Colocated or disaggregated RL on TPUs?
Colocated: actor and rollout share weights on one mesh, no transfer, but training and generation take turns. Disaggregated: generation on a serving engine (vLLM TPU) on its own slice, overlap possible, but weights move every step (Tunix's sync_weights). LoRA shrinks the transfer to the adapters and lets the reference share the frozen backbone.


Design: GRPO fine-tuning of an 8B dense model on one v5p-64 slice. What do you build?
MaxText's model with Tunix's GRPO learner (what MaxText's RL entry point does), versions pinned together. Trainer: FSDP over the slice's ICI, bfloat16 activations, float32 master weights, remat_policy chosen by compiling a step and reading memory. Rollout: vLLM TPU; start colocated on the full slice (simplest, no weight sync), move to a split (for example 48 chips training, 16 generating) if generation dominates step time. Consider LoRA to cut memory and weight-sync volume. Checkpoint asynchronously with the data iterator state. Validate with a tiny config on CPU first (this page's method), then a short run measured against MFU computed with a stated FLOP count.


Levanter's named axes against MaxText's logical rules?
Levanter: the model's own axis names, mapped by a dictionary, separately for parameters and compute; operations name their axes, so shape bugs fail at trace time. MaxText: positional arrays with logical names attached, an ordered rule list with fallbacks (the two embed rules), more machinery for many parallelism kinds. Same compiler underneath.


What does donate_argnums do in MaxText's train step?
Lets XLA reuse the input state's buffers for the output state, so parameters and optimizer state exist once in memory instead of twice during the step. The donated input arrays become invalid after the call.


What breaks bitwise reproducibility when resuming?
A data loader that cannot seek (or reshuffles), PRNG keys not saved, a different number of hosts or a different mesh (reductions in a different order; Levanter's README says so), restoring into different shardings (the training stack page measured a 3e-6 drift), and nondeterministic kernels.
