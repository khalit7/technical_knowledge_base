8. Levanter in Marin: named axes and bitwise reproducibility

Levanter is Stanford CRFM's trainer, "built with JAX, Equinox, and Haliax", designed to be "legible, scalable, and reproducible": "Levanter is bitwise deterministic, meaning that the same configuration will always produce the same results, even in the face of preemption and resumption" (). It now lives in the Marin monorepo (lib/levanter).

Where Levanter lives now, and what Marin is

The standalone repository says "Levanter has been merged into Marin as of November 2025" (, frozen at 982cef7f); development continues in the Marin monorepo under lib/levanter (255 Python files, 87,114 lines at 1290cfb5), on PyPI as marin-levanter development builds (0.2.180.dev38754195437, uploaded 2026-10-15), requiring jax>=0.9.2,<0.12 (). Marin is an open research programme that logs every experiment; its README lists a scaling suite trained on Google's TPU Research Cloud and, as current work, a 500B+ parameter mixture-of-experts model. Its newer grug/ package (28 files) holds array-first building blocks for model templates; it was not read in depth here.

Named tensors. Haliax arrays carry a name per dimension and every operation names the axes it touches. Levanter's GPT-2 attention splits its fused projection with q, k, v = qkv_out.unbind("qkv") () and renames the keys' sequence axis, k.rename({"position": "key_position"}) (), because a product of two arrays that both have position would contract or broadcast the wrong one. In PyTorch you track this in comments next to transpose(1, 2); its experimental named tensors are little used. Modules are Equinox modules (plain pytrees), not Flax. The running example's attention, with named axes:

# runs/lc_haliax.py (abridged): block 0's attention of the running example, with named axes
Batch, Pos, KPos = Axis("batch", 32), Axis("position", 128), Axis("key_position", 128)
Embed, Heads, HeadSize = Axis("embed", 128), Axis("heads", 4), Axis("head_size", 32)
q = hax.dot(hn, W("wq"), axis=Embed) + Bv("wq")                        # [batch, position, heads, head_size]
k = (hax.dot(hn, W("wk"), axis=Embed) + Bv("wk")).rename({"position": "key_position"})
scores = hax.dot(q, k, axis=HeadSize) / math.sqrt(32)                  # no transpose to remember
probs = hax.nn.softmax(hax.where(causal, scores, -jnp.inf), axis=KPos)
ctx = hax.dot(probs, v, axis=KPos)
out = hax.dot(ctx, wo, axis=(Heads, HeadSize)) + bo

Sharding by name. Levanter has no separate logical vocabulary: a dictionary maps the model's own axis names to mesh axes (, , ). Mesh axes data (absorbs all devices), replica and model (1 each), replica_dcn across slices; mlp and heads map to model; for parameters only, embed maps to data, which is FSDP. Parameters and activations get separate mappings (parameter_axis_mapping, compute_axis_mapping), and the trainer reshards the new state with the parameter mapping after every update ().

WeightLevanter (default mapping, mesh data × model)MaxText (base rules, mesh fsdp × tensor)

Same idea, different spelling: FSDP on the embedding dimension, tensor parallelism on mlp and heads. Levanter specs from Haliax's pspec_for_axis with the default mapping (runs/lc_haliax.py); MaxText specs from runs/lc_shard.py on the running example's gpt3 config under fsdp 2 × tensor 4, without the stacked layers dimension.

Reproducibility. Bitwise determinism needs three things, all visible in the code: explicit PRNG keys (JAX has no global random state), a data loader that can jump to batch n without replaying the stream (Levanter writes a preprocessed cache with random access and shuffles with a pseudo-random permutation, ), and checkpoints that hold the step and the keys. The README's caveat: training "can even be resumed on a different number of hosts, though this breaks reproducibility for now". The TPU claim was not tested here; the CPU side was: the running example's reruns are deterministic, and {{the training stack|n:3c65c17b0d0d817ea0ace9a2ca8677ec}} shows a restored Orbax checkpoint continuing bit for bit on the same mesh, and drifting by about 3e-6 within 40 steps when restored into freshly annotated shardings.

The lineage, on the root's {{Tool map|n:3c65c17b0d0d81ecbc04eea6aa45ea1a}}: T5X and Pax (with Saxml) gave way to MaxText in Google's practice, EasyLM to mesh-based trainers, Levanter to Marin.

Serving. Training codebases decode, but serving at scale is a separate engine. vLLM on TPU (tpu-inference 0.31.0, 2026-10-06, with vllm 0.31.0) is the default: vLLM's scheduler and paged KV cache with a TPU backend that, in vLLM's words, unifies "JAX and PyTorch under a single lowering path" (vLLM blog, 2025-10-16). MaxText ships an adapter (integration/vllm/, inference/vllm_decode.py) and its post-training pins a tpu-inference commit for RL rollouts (); the engine is taught on {{vLLM: inside the default engine|n:3c65c17b0d0d8113b976d8bcaf2c0722}}. SGLang-JAX (0.1.0rc0, 2026-08-29) is a JAX-native engine from the SGLang team, separate from SGLang's PyTorch code; Tunix can use it for rollouts ({{SGLang|n:3c65c17b0d0d81e691e4ce9f9b5d1fad}} has the radix cache). JetStream, Google's earlier engine for MaxText models, announced it would archive on 2026-02-01 with its functions moved to tpu-inference; on 2026-10-15 GitHub still showed it unarchived, and MaxText still contains its engine (inference/maxengine/; decoupled mode stubs it out). Do not start new work on it.
