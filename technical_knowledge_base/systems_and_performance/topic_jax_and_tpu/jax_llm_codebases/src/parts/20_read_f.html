Tunix: post-training on Flax NNX

What it is. Tunix ("Tune-in-JAX", ) is Google's post-training library: supervised fine-tuning with full weights or LoRA, DPO and ORPO, PPO, GRPO and its variants (GSPO-token, DAPO, Dr.GRPO), multi-turn agentic RL and distillation, on Flax NNX models, with vLLM's TPU backend or SGLang-JAX for generation. MaxText's post-training is Tunix underneath: its SFT, DPO and RL entry points import tunix.sft.peft_trainer, tunix.sft.dpo.dpo_trainer and tunix.rl.grpo.grpo_learner (, , ). The PyTorch counterparts are Hugging Face's Trainer and TRL for SFT and DPO, and verl or OpenRLHF for RL. What the algorithms do is taught on {{Alignment: SFT, RLHF, DPO family, RLVR|n:3c65c17b0d0d81d5bed7e608d4061c7a}} and {{RL for LLMs|n:3c65c17b0d0d818c9bcff7177325fe56}}; this section is about the code.

The trainer is twenty lines measured

PeftTrainer._train_step () is the whole algorithm:

inputs = self.gen_model_input_fn(inputs)
grad_fn = nnx.value_and_grad(self.loss_fn,
    argnums=nnx.DiffState(0, nnx.LoRAParam) if self._lora_enabled else 0, has_aux=self._has_aux)
out, grads = grad_fn(model, **inputs)
grad_norm = optax.global_norm(grads)
optimizer.update(model, grads)

wrapped in nnx.jit(train_step, donate_argnames=("optimizer",)) (). Everything else in the 882-line file is data iteration, metrics, profiling and checkpoints. LoRA is not a separate code path: if the model carries nnx.LoRAParam variables, the optimizer is built with wrt=nnx.LoRAParam () and gradients are taken only for them. Gradient accumulation is optax.MultiSteps around your optimizer ().

So Tunix can train the running example as it is. runs/lc_tunix.py gives PeftTrainer the root's Flax NNX model, its optax chain and its loss (with_loss_fn, with_gen_model_input_fn), and feeds the running example's batches: 100 steps of Tunix's trainer match the root's own 100-step NNX run to in loss. The same computation, in a different wrapper.

# runs/lc_tunix.py (abridged)
trainer = peft_trainer.PeftTrainer(model, tx, peft_trainer.TrainingConfig(eval_every_n_steps=10**9, max_steps=100))
trainer = trainer.with_loss_fn(loss_fn).with_gen_model_input_fn(lambda b: {"x": b["x"], "y": b["y"]})

RL: models by role, each on a mesh

RL for an LLM needs up to five models: the policy being trained (actor), a frozen reference for the KL penalty, a rollout engine that generates, a reward model, and for PPO a critic. Tunix's Role enum names them (), and ClusterConfig.role_to_mesh is "Key config for colocated vs disaggregated setup" (): give actor and rollout the same mesh and they share one copy of the weights (); with LoRA, the reference shares the actor's frozen backbone too (), because the base weights are the reference. Give them different meshes and every training step ends with sync_weights () pushing the actor's parameters to the rollout engine. The rollout engine is "vanilla", "vllm" or "sglang_jax" ().

When it matters. Colocated is simpler and needs no weight transfer but makes training and generation take turns on the same chips; disaggregated lets a generation-optimised engine (vLLM's TPU backend) run on its own slice while the trainer runs on another, at the cost of moving the weights every step. PyTorch's verl makes the same choice ("hybrid engine" against separate placement).

Version skew, measured. MaxText's post-training does not use the Tunix release: src/dependencies/extra_deps/post_train_github_deps.txt pins google-tunix @ https://github.com/google/tunix/archive/c2ee3bd8...zip (). With the PyPI release v0.1.7 installed, MaxText main's SFT entry point fails at import: ImportError: cannot import name 'diffusion' from 'tunix.sft'. Its DPO entry point imports fine. Install the two from the same moment, or from MaxText's own requirement files.
