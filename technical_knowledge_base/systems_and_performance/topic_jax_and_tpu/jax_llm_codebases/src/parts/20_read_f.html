7. Tunix: a thin trainer and RL placement by mesh

Tunix ("Tune-in-JAX", ) is Google's post-training library on Flax NNX: SFT with full weights or LoRA, DPO and ORPO, PPO, GRPO and its variants (GSPO-token, DAPO, Dr.GRPO), multi-turn agentic RL and distillation, with vLLM's TPU backend or SGLang-JAX for generation. MaxText's post-training is Tunix underneath: its SFT, DPO and RL entry points import tunix.sft.peft_trainer, tunix.sft.dpo.dpo_trainer and tunix.rl.grpo.grpo_learner (, , ). The algorithms are taught on {{Alignment: SFT, RLHF, DPO family, RLVR|n:3c65c17b0d0d81d5bed7e608d4061c7a}} and {{RL for LLMs|n:3c65c17b0d0d818c9bcff7177325fe56}}; this section is about the code.

The trainer is twenty lines measured. PeftTrainer._train_step () is the whole algorithm, wrapped in nnx.jit(train_step, donate_argnames=("optimizer",)) (); the rest of the 882-line file is data iteration, metrics, profiling and checkpoints:

inputs = self.gen_model_input_fn(inputs)
grad_fn = nnx.value_and_grad(self.loss_fn,
    argnums=nnx.DiffState(0, nnx.LoRAParam) if self._lora_enabled else 0, has_aux=self._has_aux)
out, grads = grad_fn(model, **inputs)
grad_norm = optax.global_norm(grads)
optimizer.update(model, grads)

LoRA is not a separate code path: if the model carries nnx.LoRAParam variables, the optimizer is built with wrt=nnx.LoRAParam () and only they get gradients. Gradient accumulation is optax.MultiSteps around your optimizer (). So Tunix trains the running example as it is: runs/lc_tunix.py gave PeftTrainer the root's NNX model, optax chain and loss (with_loss_fn, with_gen_model_input_fn), and 100 steps matched the root's own NNX run to in loss. Its default loss () normalises by target tokens plus 1e-8 (), so an all-padding batch gives zero loss instead of NaN.

Each run: 100 more batches (500 to 599), optax.adamw(1e-3, b1=0.9, b2=0.95, weight_decay=0), constant rate, one seed, nothing tuned; validation on the root's 8 fixed batches. A toy: it shows the mechanics and parameter counts; that LoRA beats full fine-tuning here says more about an untuned rate on fresh Adam state than about LoRA. {{PEFT|n:3c65c17b0d0d81eba08eef56b3e3b4eb}} and the {{LoRA paper page|n:3c65c17b0d0d81018f15edd19fa5c28a}} have the real comparisons.

RL: models by role, each on a mesh. RL for an LLM needs up to five models: the actor being trained, a frozen reference for the KL penalty, a rollout engine that generates, a reward model and, for PPO, a critic. Tunix's Role enum names them (), and ClusterConfig.role_to_mesh is "Key config for colocated vs disaggregated setup" (). Same mesh for actor and rollout: they share one copy of the weights (), and with LoRA the reference shares the actor's frozen backbone too (). Different meshes: every step ends with sync_weights () pushing the actor's parameters to the rollout engine, which is "vanilla", "vllm" or "sglang_jax" ().

One GRPO step: colocated roles take turns on one mesh; disaggregated roles overlap but move weights every step

Placement

Read from grpo_learner.py and rl_cluster.py at v0.1.7 (_generate_and_compute_advantage, : generate , reference log-probabilities , advantages ; defaults num_generations = 2, beta = 0.04, epsilon = 0.2, ). Not run here: Tunix's samplers need a model with a key-value cache interface and a tokenizer, which the running example lacks; an illustrative sequence, not a timing.

Colocated is simpler and moves no weights, but training and generation take turns on the same chips; disaggregated lets a generation-optimised engine (vLLM's TPU backend) run on its own slice, at the cost of a weight transfer every step. PyTorch's verl makes the same choice ("hybrid engine" against separate placement).

Version skew, measured. MaxText's post-training does not use the Tunix release: src/dependencies/extra_deps/post_train_github_deps.txt pins google-tunix @ https://github.com/google/tunix/archive/c2ee3bd8...zip (). With PyPI v0.1.7 installed, MaxText main's SFT entry point fails at import, ImportError: cannot import name 'diffusion' from 'tunix.sft'; its DPO entry point imports fine. Install both from MaxText's own requirement files.
