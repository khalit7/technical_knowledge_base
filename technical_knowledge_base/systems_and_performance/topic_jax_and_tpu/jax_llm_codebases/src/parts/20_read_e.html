4. The train step: one pure function, compiled once

A PyTorch step mutates objects (loss.backward() fills .grad, optimizer.step() updates in place). MaxText's train_step () is a pure function from (state, batch) to (new state, metrics):

  1. nnx.merge(model, state) () rebuilds the TrainStateNNX module (model plus nnx.Optimizer) inside the trace from a static graph definition and a pytree of arrays (the split/merge pattern of {{the training stack|n:3c65c17b0d0d817ea0ace9a2ca8677ec}}).
  2. jax.value_and_grad(diff_wrapper, argnums=(0, 1), has_aux=True) () differentiates loss_fn () over the trainable nnx.Param leaves: forward, cross-entropy over non-padding tokens, auxiliary losses (MoE load balance, z-loss, multi-token prediction) when configured.
  3. Gradients are cast to grad_dtype, clipped by global norm () and applied by state.apply_gradients(grads) (), the optax chain.
  4. Metrics (loss, raw and clipped gradient norm, parameter norm) come back as arrays, so logging never forces a device-to-host copy inside the step.

jit_train_step () wraps it in jax.jit with in_shardings and out_shardings from the logical rules and donate_argnums = 0 (): the old state's buffers become the new state's, which keeps peak memory at one copy of parameters and optimizer state; the donated input arrays are invalid after the call.

5. Scan over layers, and what remat keeps

With scan_layers: true () the decoder traces one layer inside jax.lax.scan over stacked weights, so the program and the compile time stop growing with depth (PyTorch eager has no counterpart; under torch.compile the closest is compiling one block and reusing it; scan against a Python loop is measured on {{JAX core|n:3c65c17b0d0d81b7a0d1faba6cef5561}}; nnx.scan is on {{the training stack|n:3c65c17b0d0d817ea0ace9a2ca8677ec}}). Each scanned layer is wrapped in jax.checkpoint(layer_fn, policy=policy) with the policy named by remat_policy (, default full) through get_remat_policy (): full keeps only each layer's input and recomputes the rest in the backward pass; the others keep tensors the layers name with checkpoint_name (query_proj, key_proj, value_proj, out_proj, mlpwi, mlpwo, context; e.g. ). minimal () keeps every projection output; the *_offloaded policies move them to host memory. PyTorch's counterpart is torch.utils.checkpoint with a selective policy.

Predict: for the running example's step compiled by MaxText, which policy needs the most temporary memory, and which does the most FLOPs?
minimal keeps the most (149.7 MB of XLA temporaries against 100.1 MB for full) and full recomputes the most (28.90 GFLOP against 24.61 GFLOP, layers unrolled).

6. How MaxText counts MFU, and what its published table used

Model FLOPs utilisation (MFU) is the model's FLOPs per step divided by step time and peak FLOP/s ({{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}} derives it). MaxText's count, calculate_tflops_training_per_device (), takes every weight matmul at 2 FLOPs per multiply-add, times 3 for forward plus backward ("multiply by 3 to account for 1 forward pass + 2 backward passes", ), plus attention's score and value products, halved for the causal mask since July 2025 (causal_attention_flops = noncausal_attention_flops / 2, ; the docs, ). It counts the output projection, not the embedding lookup, and never recomputation, so heavier remat lowers MFU without changing the count. On the running example's step: 21.14 GFLOP (19.53 in weight matmuls, 1.61 in attention), against 23.69 from XLA's cost analysis (the {{JAX core|n:3c65c17b0d0d81b7a0d1faba6cef5561}} page's measurement), which counts unmasked attention, elementwise work and softmax. MFU uses the analytic count on purpose: it does not depend on the implementation.
