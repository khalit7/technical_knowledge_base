5. Pallas from zero

XLA writes nearly every kernel of a JAX program, and fuses elementwise work into its matmuls well (the {{Compiler lab|#t-xla}} shows it). It cannot invent an algorithm, though: it will not turn attention into flash attention (never writing the T × T score matrix to HBM), route tokens to experts with ragged matmuls, or overlap a matmul with a collective by hand. For those you write a kernel, and on JAX that means Pallas. Five ideas are all of it:

  • Kernel: a Python function over refs, mutable views of buffers in VMEM (or SMEM). You read with x_ref[...] and write with o_ref[...] = ; inside, ordinary jnp code runs on the tile.
  • Grid: a tuple of loop bounds. The kernel body runs once per grid point; pl.program_id(axis) says which. On a TPU the points run in order, as nested loops (Pallas's TPU docs: "sequentially, in lexicographic order"), unlike a GPU, where Triton's program instances run in parallel.
  • BlockSpec(block_shape, index_map): for each input and output, the tile size and a function from grid point to block index (which tile). Pallas turns this into the HBM to VMEM copies, double-buffered so the next tile arrives while this one is used, and skips a copy when consecutive grid points ask for the same tile.
  • Dimension semantics: "parallel" (order does not matter, so the axis may be split across a megacore's two cores) or "arbitrary" (must run in order, as an accumulation must). The default is all arbitrary (lowering.py:778).
  • Backends: on TPU the kernel lowers to Mosaic, an MLIR dialect that libtpu compiles; on GPU to Triton or to Mosaic GPU; anywhere, interpret=True runs it as ordinary JAX (section 6 shows what that does and does not tell you).

What the numbers say. The matmul agrees with XLA to float32 rounding (2.5e-7 on outputs up to 0.26); fed bf16 inputs, as an MXU would be, it is off from the float32 answer by 7.1e-4, and matches XLA's own bf16 matmul to 1.2e-7, so the error is bf16's, not the kernel's. Flash attention agrees with the model's attention to 8.9e-8 while computing only 384 of its 512 blocks (for each head, the block where the first 64 queries meet the last 64 keys is entirely masked by causality, and the pl.when skips it), and never stores the 8.4 MB score matrix. Interpret mode is 10 times slower than XLA on the matmul and 70 times on attention: it is a correctness tool. What it builds explains why: the jitted interpreted matmul lowers to 147 lines of StableHLO with one while loop over the 32 grid points, 3 dynamic_slice and 3 dynamic_update_slice, where a @ b lowers to 6.


What each interpret mode catches


Pallas has two interpreters. interpret=True is the plain one (hlo_interpreter.py). Passing interpret=pltpu.InterpretParams(...) selects the TPU interpreter, which simulates the TPU's DMAs, semaphores and cores, checks every block index, and can run a race detector. The second bug is the dangerous one: the plain interpreter drops compiler_params (hlo_interpreter.py:329), so it never sees the wrong semantics, and on a single-core chip the real compiler would run the axis in order anyway. On a megacore chip the two cores would race on the same output tile. The TPU interpreter shuffles parallel axes on purpose to expose this: here it ran k = 1 before k = 0 for the first output tile, so the zeroing step erased a partial sum. The third bug is silent in plain interpret mode because its dynamic_slice clamps an out-of-range start (XLA's rule) and quietly re-reads the last tile.

7. Block sizes: VMEM against HBM traffic


The block shape is the one decision that matters in a Pallas matmul. Small blocks re-read A and B many times from HBM; large blocks need more VMEM (and, beyond what fits, the kernel fails to compile). The pattern: with bk the full K, A is read once, and B once per row of blocks; HBM traffic falls towards the minimum as bm grows, while VMEM grows linearly. For the 7B-class matmul, 128-cubed blocks move 19.6 times the minimum traffic, whose arithmetic intensity is then far below any ridge point; 512 × 5,504 × 256 blocks move 3.2 times the minimum in 27 MiB of VMEM, too much for v4's 16 MiB per core. Autotuning a kernel is searching this table with real timings.
