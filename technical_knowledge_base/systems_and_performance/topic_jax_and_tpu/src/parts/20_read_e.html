5. Sharding and scale

In PyTorch you choose a parallelism implementation (DDP, FSDP2, tensor-parallel layers) and it owns the communication. In JAX you write the single-device step once, say how arrays are laid out over devices, and the compiler does the rest. Three objects carry the description: a Mesh (devices as a named grid, such as 8 devices as ('data', 'model') of 2 × 4), a PartitionSpec P(...) (for each array dimension, the mesh axis that splits it, or None), and a NamedSharding (the two together, attached with jax.device_put, to a jitted function's inputs and outputs, or to intermediates with with_sharding_constraint).

The compiler's partitioner then propagates shardings to every other array and, wherever an operation needs data laid out differently, inserts a collective: all-gather (everyone gets the whole array), reduce-scatter (sum, each keeps a slice), all-reduce (sum, everyone gets the result), all-to-all, or permute. The design is GSPMD ({{Xu et al. 2021|https://arxiv.org/abs/2105.04663}}); since JAX 0.7.0 (2025-07-22) the propagation is done by its successor Shardy, which "will be the only partitioner in JAX" ({{JAX Shardy migration guide|https://docs.jax.dev/en/latest/shardy_jax_migration.html}}). How it was counted, and three things the counts show

Collectives counted in compile().as_text() of the whole step (forward, backward, clipping, AdamW, donated state), 20 steps each, Auto mesh axes, jax 0.11.2 (src/shard/out/rd_collectives.json). Bytes are the sizes of the arrays the collectives carry, not link traffic. Data parallel compiles to a single all-reduce: XLA combined every gradient into one. FSDP shows all-reduces where a reduce-scatter is expected: XLA's CPU pipeline reduces then slices, while its GPU pipeline has the pass that turns that into a reduce-scatter (Sharding lab, XLA source). Tensor parallel's 18 all-reduces include 8 in the forward pass, two per block.

Who decides, and when you want control. On Auto mesh axes the compiler chooses everything you did not annotate. On Explicit axes a sharding is part of the array's type (jax.typeof(x)) and ambiguous cases are errors at trace time; in JAX 0.11.2 jax.make_mesh makes Explicit axes by default, while the Mesh constructor still defaults to Auto, so pass axis_types=(AxisType.Auto,) * 2 to get the behaviour older tutorials assume. jax.shard_map runs a function per device on its local shard with collectives you write (psum, all_gather, ppermute): the rank-view program a torch.distributed user knows. Old code you will meet: pmap (in maintenance mode since 0.8.0), pjit (merged into jit), xmap (deleted in 0.4.31) ({{JAX changelog|https://docs.jax.dev/en/latest/changelog.html}}). Across many hosts the same script runs on every host and one jitted program spans the slice (not run here: one host).

Why sharding is not optional: replicated training state outgrows any chip; FSDP divides it by the device count

Training state = 16 bytes per parameter (bf16 weights and gradients, fp32 master weights and two Adam moments; the accounting of the {{ZeRO paper|n:3c65c17b0d0d81879a7ed90bca007699}}), activations excluded. derived 16 × parameters ÷ devices for FSDP, 16 × parameters for data parallel; HBM capacities vendor (section 6), all in GB of 109 bytes (v5p's 95 GiB is 102 GB, Ironwood's 192 GiB is 206 GB).

Details the child pages carry with their runs

An x @ W whose contracted dimension is sharded raises a ShardingTypeError under Explicit axes until you say how the output is sharded; jax.set_mesh(mesh) sets the mesh it uses. MaxText still defaults to automatic mode (shard_mode: "auto"). shard_map left jax.experimental in JAX 0.8.0 (2025-10-15); pmap is now reimplemented over jit and shard_map. Many hosts: jax.distributed.initialize() connects them, jax.process_index() is the rank, and each host feeds its part of the batch with jax.make_array_from_process_local_data; collectives ride the ICI links.
