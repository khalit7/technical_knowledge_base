5. Sharding and scale

In PyTorch you choose a parallelism implementation (wrap the model in DDP or FSDP, swap in tensor-parallel layers) and it owns the communication. In JAX you write the single-device step once, describe how arrays are laid out over devices, and the compiler works out the rest. Three objects carry the description:

  • Mesh: the devices arranged as a named grid, for example 8 devices as jax.make_mesh((2, 4), ('data', 'model')). The axis names are your vocabulary from then on.
  • PartitionSpec (P): for each dimension of an array, which mesh axis splits it, or None for "replicated along this dimension". P('data', None) on a [batch, features] array splits the batch over the 2 devices of the data axis.
  • NamedSharding = mesh + spec, attached to arrays with jax.device_put, to a jitted function's inputs and outputs, and to intermediates with jax.lax.with_sharding_constraint.

Then the compiler's partitioner propagates shardings from the annotated arrays to every other array in the program and, wherever an operation needs data laid out differently from how it is, inserts a collective: an all-gather (every device gets the whole array), a reduce-scatter (sum, then each device keeps a slice), an all-reduce (sum, everyone gets the whole result), an all-to-all, or a permute. The design comes from GSPMD ({{Xu et al. 2021|https://arxiv.org/abs/2105.04663}}), the name you will see everywhere; since JAX 0.7.0 (2025-07-22) the propagation is done by default by its successor Shardy, which "will be the only partitioner in JAX" once the migration ends ({{JAX Shardy migration guide|https://docs.jax.dev/en/latest/shardy_jax_migration.html}}). When you want control. jax.shard_map runs a function per device on its local shard, and you write the collectives yourself (jax.lax.psum, all_gather, psum_scatter, ppermute): the rank-view program a torch.distributed user knows, used for custom communication, overlap tricks and wrapping kernels. It left jax.experimental in JAX 0.8.0 (2025-10-15). Between the two sits the newer explicit sharding mode, where shardings are part of an array's type (visible in jax.typeof(x)) and checked while tracing; jax.set_mesh(mesh) sets the mesh it uses. History you will meet in old code: pmap (one device axis; since 0.8.0 reimplemented over jit and shard_map and "in maintenance mode"), pjit (merged into jit), xmap (deleted in 0.4.31) ({{JAX changelog|https://docs.jax.dev/en/latest/changelog.html}}).

Many hosts. A TPU slice larger than one host runs the same script on every host (usually 4 chips each). jax.distributed.initialize() connects them; jax.devices() then lists every chip in the slice and jax.process_index() is the rank; each host feeds only its part of the batch (jax.make_array_from_process_local_data), and one jitted program spans the slice, its collectives riding the ICI links. Not run here: this machine is one host.

Why sharding is not optional: training-state memory per device

Training state = 16 bytes per parameter (bf16 weights and gradients, fp32 master weights and two Adam moments; the accounting of the {{ZeRO paper|n:3c65c17b0d0d81879a7ed90bca007699}}), activations excluded. derived 16 × parameters ÷ devices for FSDP, 16 × parameters for data parallel; HBM capacities vendor (section 6), all in GB of 109 bytes (v5p's 95 GiB is 102 GB, Ironwood's 192 GiB is 206 GB).
