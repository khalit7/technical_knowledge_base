What the six runs teach

    Sequence and context parallelism, briefly. Sequence parallelism (Megatron's sense) splits the activations that tensor parallelism leaves replicated (LayerNorm, dropout) along the sequence, turning each TP all-reduce into a reduce-scatter plus an all-gather; context parallelism splits the whole sequence over devices so that very long contexts fit, and must then bring every query together with every key. The "Sequence sharded" row does the second by annotation only: the compiler's answer is to all-gather K and V in every layer, which works but sends the full K and V to everyone. Ring attention instead passes K/V blocks round the ring with ppermute while computing, overlapping the transfer with the math; that is hand-written with shard_map, not something propagation invents. Not run here.

    5. shard_map: writing the per-device program yourself

    When propagation is not enough. You may need a communication pattern the compiler will not invent (ring attention, overlapping a collective with compute, a custom MoE dispatch), or simply want certainty. jax.shard_map(f, mesh=..., in_specs=..., out_specs=...) runs f once per device on that device's shard (shapes inside are the per-device shapes) and you write the collectives yourself: psum, all_gather, psum_scatter, all_to_all, ppermute, with jax.lax.axis_index(name) as the rank. Inside, the mesh axes are Manual: the partitioner leaves that region alone. This is the rank-view program a torch.distributed user already knows; the difference is that it is still traced and compiled as one program, so it composes with jit, grad and vmap. It left jax.experimental in JAX 0.8.0 (2025-10-15); jax.experimental.shard_map still imports in 0.11.2 with a DeprecationWarning.

    A ring all-reduce written by hand, the exact code that ran (from src/shard/sh_collectives.py):

    def ring_allreduce(b):                       # b: this device's block [1, N*k]; chunks of k
    me = jax.lax.axis_index("i")
    chunks = b.reshape(N, -1)                # N chunks
    right = [(j, (j + 1) % N) for j in range(N)]
    # phase 1, reduce-scatter: at step s, send chunk (me - s) mod N to the right; add what arrives to chunk (me - s - 1)
    acc = chunks
    for s in range(N - 1):
        send = acc[(me - s) % N]
        recv = jax.lax.ppermute(send, "i", perm=right)
        acc = acc.at[(me - s - 1) % N].add(recv)
    # now chunk (me + 1) mod N holds the full sum on this device
    # phase 2, all-gather: pass the finished chunks round the ring
    for s in range(N - 1):
        send = acc[(me + 1 - s) % N]
        recv = jax.lax.ppermute(send, "i", perm=right)
        acc = acc.at[(me - s) % N].set(recv)
    return acc.reshape(1, -1)

f_ring = jax.jit(jax.shard_map(ring_allreduce, mesh=mesh, in_specs=P("i", None), out_specs=P("i", None)))

    Two errors you will meet, both pasted from runs here.

    • Input laid out differently from in_specs.
    • Claiming an output is replicated when JAX cannot prove it. out_specs=P(None, None) says "every device holds the same value". After all_gather that is true, but JAX types the result as still varying over the axis, and refuses: Either declare out_specs=P('i', None) (what the table in section 3 did: the global result is then 8 stacked copies) or pass check_vma=False if you are sure.

    6. Many hosts, and the APIs you will see in old code

    Multi-host (not run here: this machine is one host). A TPU slice bigger than one host (typically 4 chips per host) runs the same Python script on every host. jax.distributed.initialize() connects them (on Cloud TPU it finds the coordinator by itself); then jax.devices() lists every chip in the slice, jax.local_devices() only this host's, and jax.process_index() / jax.process_count() play the role of rank and world size. A sharded array is now a global array whose shards live on several hosts; each host can only touch its own (x.addressable_shards), so data loading builds the global batch from per-host pieces with jax.make_array_from_process_local_data. The jitted program is still one program over all devices; its collectives ride ICI inside a slice and the data-centre network between slices. PyTorch's equivalent is torchrun + init_process_group, with one process per GPU rather than one per host.

    History. pmap (one mapped axis, one device per element) is "in maintenance mode" since JAX 0.8.0 and, since 0.10.0, implemented on top of jit(shard_map); it still runs in 0.11.2 (). pjit was merged into jit (jax.experimental.pjit.pjit deprecated in 0.8.0); xmap was deleted in 0.4.31; with mesh: is deprecated in favour of jax.set_mesh (0.10.1); PmapSharding and device_put_sharded/replicated were removed in 0.10.0 ({{JAX changelog|https://docs.jax.dev/en/latest/changelog.html}}). New code: jax.jit with shardings, plus jax.shard_map where needed.

    8. Common mistakes and interview questions

    Annotating only the weights and trusting propagation
    The "FSDP, weights annotated only" row: the compiler followed the weights' split into the activations and then all-gathered whole-batch activations: 8 copies of the MLP hidden layer [32, 128, 512] (8 MiB each) and 16 of [32, 128, 128] (2 MiB each), about 32 times the all-gather bytes of the fixed version. One with_sharding_constraint on the residual stream per block fixed it. Constrain activations at block boundaries, as MaxText does with logical axis rules.
    Assuming make_mesh gives an Auto mesh
    In jax 0.11.2 it gives Explicit axes: shard_map then refuses mismatched inputs, and a matmul with both contracting dimensions sharded is a type error. Pass axis_types explicitly so the code says which mode it relies on.
    Reading the collectives off the code instead of the compiled HLO
    The code has none; the HLO has them all, and they depend on the backend's passes (on CPU no reduce-scatter is formed from all-reduce + slice). Search compile().as_text(), and profile on the real hardware before drawing conclusions about cost.
    Expecting bit-identical losses across layouts
    Sharding changes the order of additions (each device sums its part, then the parts are added), so float32 results differ in the last bits: here by at most over the steps, the same size as float32 rounding of a loss near 4. A gap far larger than that is a bug.
    Switching partitioner and expecting the same program
    Same annotations, different propagators: the older GSPMD propagator produced for the tensor-parallel layout where Shardy produced 18 all-reduces, but did better than Shardy on the unconstrained FSDP case. Neither is uniformly better; constraints make the result robust to both.

    Interview questions

    You annotate x as P('data', None) and W as P(None, 'model'). What does y = x @ W cost in communication?
    Nothing: each device multiplies its rows of x by its columns of W and the result is P('data', 'model'). Communication appears only if you then ask for another layout (P('data', None) costs an all-gather over 'model').
    FSDP versus data parallel: how much more traffic?
    Data parallel all-reduces the gradients: 2(n−1)/n × P bytes per device. FSDP all-gathers the weights in the forward pass, again in the backward pass if they were freed, and reduce-scatters the gradients: (n−1)/n × P each, so 1.5× data parallel with re-gathering, 1× without. In exchange each device holds 1/n of weights, gradients and optimizer state.
    Megatron tensor parallelism: where are the all-reduces, and why does the MLP need only one?
    Split the first MLP matrix by columns and the second by rows: GELU is elementwise, so each device keeps its slice of the hidden layer and the only communication is one all-reduce of the [batch, seq, d_model] output (forward), and one of the input gradient (backward). Attention likewise: heads split, one all-reduce after the output projection. Measured here: 8 forward all-reduces for 4 blocks.
    Your sharded step is slower than expected. What do you check?
    The compiled HLO for collectives you did not plan (an all-gather of activations, an all-to-all), their sizes and replica groups; whether propagation changed after a code edit (compare HLO between versions); memory_analysis() for unexpected replication; a profile to see whether collectives overlap with compute; and that the mesh axis carrying the most traffic maps onto the fastest links (ICI within a slice).
