What is real here and what is not
The 8 devices are simulated on one Apple M1 Pro CPU (XLA_FLAGS=--xla_force_host_platform_device_count=8, jax 0.11.2). The compiled HLO, the collectives XLA inserted, the per-device shapes, memory_analysis() and the losses are real and deterministic. Speeds are not: a "collective" between simulated devices is a memory copy, nothing like ICI or NVLink, so no timing on this tab says anything about a TPU. One more difference matters and is shown below: XLA's CPU pipeline lacks two collective optimisations that the GPU pipeline runs, so a few results differ from what a GPU or TPU compile would give.

1. Devices, the mesh and a PartitionSpec

Something must say which device holds which piece of every array. In PyTorch that is the wrapper you choose (DDP, FSDP2, tensor-parallel layers) or a DTensor's placements; in JAX it is three small objects. A Mesh: jax.make_mesh((2, 4), ('data', 'model')) puts the 8 devices in 2 rows and 4 columns (PyTorch: init_device_mesh("cuda", (2, 4), mesh_dim_names=("dp", "tp"))). A PartitionSpec: on a [128, 512] weight, P(None, 'model') splits the 512 columns in 4 and copies the result along data (PyTorch: placements [Replicate(), Shard(1)], one per mesh dimension instead of one per array dimension). A NamedSharding(mesh, spec), attached with jax.device_put: the array stays one logical array whose shards live on different devices.

The picture is on {{Sharding and scale|n:3c65c17b0d0d8125b084e6720cc66b3d}}, section 1 ("One weight, six PartitionSpecs": which block of the running example's [128, 512] weight each of the 8 devices holds, with jax.debug.visualize_array_sharding's own output). This lab uses those objects from section 2 on.

Two kinds of mesh axis, and a default that changed. A mesh axis has a type. On an Auto axis the compiler is free to choose shardings for everything you did not annotate (section 2). On an Explicit axis the sharding is part of the array's type, visible in jax.typeof(x) and checked while tracing; ambiguous cases are errors instead of compiler choices. In jax 0.11.2 jax.make_mesh creates Explicit axes unless told otherwise, while the jax.sharding.Mesh constructor still defaults to Auto (run here: ; source in section 7). The JAX changelog announced the switch in 0.8.1 ("Default axis_types of jax.make_mesh will change in JAX v0.9.0"), and the {{JAX sharding guide|https://docs.jax.dev/en/latest/parallel.html}} now says "By default, all mesh axis types are AxisType.Explicit". Older tutorials that call make_mesh and then rely on the compiler choosing were written for Auto: pass axis_types=(AxisType.Auto,) * 2 to get that behaviour. Every compile on this tab says which it used.
