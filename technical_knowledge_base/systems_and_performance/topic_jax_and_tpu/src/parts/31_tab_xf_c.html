4. Pure functions: side effects run once, at trace time

A pure function computes its outputs from its inputs only and changes nothing outside itself. JAX needs purity because of section 1: the Python body runs only while tracing, and later calls run the compiled program, which contains array operations and nothing else. Anything Python does on the side (print, append to a list, increment a counter, read the clock, draw a NumPy random number) happens once, at trace time, or is frozen into the program as a constant. PyTorch has no such rule, because eager mode runs your Python every step.

One jitted function, three calls (real run)

log, count = [], [0]

@jax.jit
def f_side(x):
    count[0] += 1                 # Python side effect
    log.append(x)                 # keeps a reference to a tracer
    jax.debug.print("debug.print sees x[0] = {v}", v=x[0])
    return x * 2

for i in range(3):
    f_side(jnp.full(4, float(i)))

5. Arrays are immutable


A JAX array never changes after it is created; operations return new arrays. This is what makes purity cheap to check, and the compiler gets the in-place update back where it is safe (inside jit, and across steps with buffer donation, measured in the {{Compiler lab|#t-xla}}). The indexed-update API is x.at[index].set / add / multiply / min / max / get.






Two behaviours that differ from PyTorch:


    

  • Repeated indices accumulate in JAX. x.at[[0, 0, 0]].add(1.0) adds 3 to x[0] (scatter-add). PyTorch's t[[0, 0, 0]] += 1 adds only 1, because it gathers, adds, then writes back; index_put_(..., accumulate=True) is the accumulating form.
    • 

  • Out-of-bounds indices do not raise in JAX. On a 5-element array, x[10] returned  (clamped to the last element), x[-10] returned  (clamped to the first), and x.at[10].set(99.0) silently did nothing. 6. Randomness is a value: keys instead of a global generator


The problem. torch.manual_seed(0) seeds a hidden global generator whose state advances on every call. A pure function cannot use hidden state, and a traced function would freeze it (section 4). So JAX makes the generator state an explicit array, a key, that you pass in like any other argument.




How to use keys. Never use a key twice. key, sub = jax.random.split(key) makes new independent keys (keep one to split again, use the other); jax.random.fold_in(key, step) derives a key from an integer such as the step number, handy inside a training loop. Flax's nnx.Rngs does the splitting inside modules. In this run fold_in(key, i) and split(key)[i] drew the same numbers for i = 0 and 1 (), an observation about jax 's default implementation, not a documented guarantee: do not rely on it.


Key reuse is the classic bug. Two dropout masks drawn with the same key at keep probability 0.9 agreed on  of 4,096 positions: they are the same mask. Masks drawn from a key and a split key agreed on , close to 0.9 × 0.9 + 0.1 × 0.1 = 82% for independent masks. Nothing errors; your two layers just drop the same units. (JAX has a checker, jax_debug_key_reuse, visible in the EvalTrace source in section 10.)


Same key, same numbers, on any number of devices. On 8 simulated CPU devices, jax.random.normal(key, (8, 4096)) computed inside jit with its output sharded by rows over 8 devices, and over a 2 × 4 mesh, matched the single-device result exactly (maximum difference ). jax_threefry_partitionable is on by default in this version (); its help text in the pinned source (jax/_src/config.py:1402) says that without it, jax.random "may result in extraneous communication and/or redundant distributed computation". Turning it off gave the same values across shardings here too, but different numbers from the default (largest difference ): the setting changes the stream, so switching it changes your initialisation.
