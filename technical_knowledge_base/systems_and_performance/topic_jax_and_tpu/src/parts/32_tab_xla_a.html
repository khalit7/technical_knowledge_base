In PyTorch terms
PyTorch eager runs one kernel per operation, the moment Python reaches it. jax.jit instead runs your Python once with placeholder values to record the whole function as a program, hands that program to a compiler (XLA), and from then on runs the compiled program. The nearest PyTorch analogue is torch.compile; section 9 compares them on the same model.

1. One train step, five forms

Between your Python and the processor there are five forms of the same program. Each has a name you will meet in error messages and docs, and each can be printed:

  • jaxpr (JAX expression): JAX's own program, a flat list of equations, each one primitive (an operation JAX knows how to differentiate, batch and lower, such as dot_general, add, reduce_sum) applied to typed variables. Produced by tracing: running your function with tracers, stand-in values that carry only a shape and dtype and record every operation applied to them.
  • StableHLO: the jaxpr lowered to a versioned, portable operation set written in MLIR (a compiler-infrastructure format). It is the hand-off point between front ends (JAX, PyTorch/XLA, TorchTPU, TorchNeuron) and compilers.
  • HLO (High Level Operations): XLA's internal form, the same program before any optimisation.
  • Optimised HLO: after XLA's passes (section 3) have simplified, fused and laid out the program. Each top-level instruction left is roughly one kernel, one piece of code launched on the device.
  • Executable: machine code for the backend (LLVM-generated code for this CPU; GPU and TPU code elsewhere).

2. Fusion: the same 29 equations, before and after XLA


The problem. Run the MLP sub-block eagerly and every equation is its own kernel: it reads its inputs from memory and writes its output back, even when the next equation immediately reads that output again. On accelerators, memory traffic, not arithmetic, is usually the bottleneck for this kind of elementwise work. Fusion merges a chain of operations into one kernel so intermediate values stay in registers or on-chip memory.


















Real data: the 29 equations of the block's jaxpr, and the 4 kernels of its optimised HLO. Each equation is placed in the kernel that computes it, matched by the operation name and source line XLA keeps in its metadata (src/xla/fusion_demo.py). "Bytes moved" before fusion is derived: every equation reads its inputs and writes its output once (); after fusion it is XLA's own cost_analysis()["bytes accessed"] (). What transfers to GPU and TPU, and what does not
The idea transfers: elementwise chains, broadcasts and the reductions of LayerNorm fuse on every backend, and duplicated work is removed. The exact kernels do not: on this CPU, XLA hands matmuls to the YNNPACK library and fuses LayerNorm into the matmul's input ("library fusion"); on a GPU, XLA calls libraries such as cuBLAS, which "often preclude complex fusion opportunities", or, "for more advanced fusions which include matrix multiplication or softmax", generates the kernel with Triton (OpenXLA, XLA:GPU architecture, read 2026-10-15); on a TPU, matmuls run on the MXU in code XLA generates itself (the {{TPU and Pallas lab|#t-tpu}}). Not run here (no GPU or TPU); the counts are XLA:CPU's.

3. The passes


XLA optimises by running passes, each a rewrite of the whole HLO program: algebraic simplification, common-subexpression elimination (the largest single drop in this step: the gradient norm is computed twice, once inside clip_by_global_norm and once for logging), dead-code elimination, layout assignment, fusion (the cliff, section 2), then copy insertion and buffer assignment (section 4). XLA_FLAGS=--xla_dump_to=DIR --xla_dump_hlo_pass_re=.* writes the program after every pass that changed it.
