8. Debugging a program you never see run

Inside jit, your Python ran once, during tracing; what runs later is XLA's program. So the PyTorch habits (a print, a breakpoint, checking a tensor for NaNs after each line) need JAX equivalents, each of which puts something into the compiled program:

print against jax.debug.print



Python's print fired once, while tracing, and shows a tracer; jax.debug.print became part of the program and fires on every call with the real value.


checkify: errors from inside the program


Accelerators cannot raise an exception mid-kernel, so a check becomes an error value returned next to the output, which you inspect on the host.




jax_debug_nans: find the operation that made the NaNs




When a jitted function returns NaNs, JAX reruns it de-optimised, operation by operation, and raises at the first one that produced it. Slow; turn it on to hunt, off to train.


What each costs in the compiled program




debug.print adds a call back into Python (a host round trip that also orders the program); checkify adds the checks and the error plumbing but stays on the device. All examples ran here with JAX ; outputs as printed (src/xla/debug_tools.py).

Common mistakes


Timing the first call
The first call traces, lowers and compiles (section 7). Time steady state after a warm-up call, and call jax.block_until_ready(out) before stopping the clock: JAX dispatches asynchronously, so without it you time the dispatch, not the work.


Not donating the training state
Two copies of parameters and optimiser state at the end of every step (section 4). jax.jit(step, donate_argnums=(0, 1)); with Flax NNX, nnx.jit(donate_argnames=("model", "optimizer")), since nnx.jit donates nothing by default.


Reading FLOPs from cost_analysis on a scanned model
The loop body is counted once (section 6). Multiply by the number of layers, or compute FLOPs from the model's shapes.


Expecting the persistent cache to help small programs
With the default 1-second threshold, quick compiles are never written (section 7). Lower jax_persistent_cache_min_compile_time_secs when iterating on small models.


Remat everywhere
Recomputing every block costs FLOPs on every layer, but the last block saves nothing (section 5). Start from the memory you need to free and pick the cheapest policy that frees it.


Leaving debugging on
jax.debug.print adds a host callback to every step; jax_debug_nans checks every output and reruns de-optimised on a hit. Both belong in a debugging run, not a training run.



Interview questions


What happens between jax.jit(f)(x) and the result?
Look up the cache by the signature (shapes, dtypes, shardings, static values). On a miss: trace f with abstract tracers into a jaxpr, lower each primitive to StableHLO, hand the module to XLA, which optimises (simplification, CSE, layout assignment, fusion, buffer assignment) and generates code; cache the executable. Then dispatch it asynchronously and return arrays whose values arrive later.


Why is a JAX train step often fast without custom kernels?
The whole step, forward, backward and optimiser, is one program, so XLA can fuse across operations that eager execution runs separately: elementwise chains, LayerNorm's reductions, matmul epilogues. Fusion cuts memory traffic, the usual bottleneck (here  less on one MLP block). What it cannot do (new algorithms like flash attention) is what Pallas is for.


Your model OOMs on a TPU. What do you check, in order?
memory_analysis() of the compiled step before running anything: are the state arguments donated (alias equal to the state size)? Is temp dominated by activations? Then remat (a policy, and which layers), smaller micro-batches with gradient accumulation, sharding the state (FSDP), and offloading saved activations or optimiser state to host memory.


Scan or a Python loop over layers?
Scan: compile time and program size stay flat as depth grows, and the per-layer weights become one stacked array, which suits sharding and remat per layer. A Python loop: XLA sees across layer boundaries and compile time grows with depth. Production JAX LLM code scans by default.


How does jit differ from torch.compile?
jit traces with abstract values and produces one whole program or an error; torch.compile reads bytecode, captures what it can and falls back to Python at graph breaks, guarded by runtime checks that trigger recompiles. JAX demands purity up front and gets whole-program compilation; PyTorch keeps eager semantics and compiles opportunistically.
