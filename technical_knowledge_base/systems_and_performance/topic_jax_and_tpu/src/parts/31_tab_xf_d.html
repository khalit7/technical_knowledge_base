7. Pytrees: the model's parameters as one nested value

The problem. Transformations take and return arrays, but a model has dozens of parameters. PyTorch keeps them as attributes of nn.Module objects and gives you model.parameters() and state_dict() to walk them. JAX instead accepts any nesting of containers, a pytree, and flattens it to a list of leaves (the arrays) plus a tree definition (the structure) whenever a transformation needs to. jit, grad, vmap, optax and orbax all speak pytrees, so parameters, gradients, optimiser states and checkpoints share one shape.

Explore the running example's parameter pytree

The plain-JAX model's parameters: nested dicts and a list. Click a node; leaves show their path (jax.tree_util.keystr), shape, position in jax.tree.leaves order, and the PyTorch name the setup maps them to.

What counts as a leaf. Lists, tuples, dicts, None and classes registered with JAX are containers; everything else is a leaf, including Python floats and strings. An unregistered class is a single opaque leaf, so transformations cannot see the arrays inside it. Flattening this object (real output):

obj = {"tuple": (1.0, 2.0), "none": None, "str": "adam", "opaque": Opaque(),   # plain class holding an array

       "list": [jnp.ones(3)], "empty": {}}
jax.tree_util.tree_flatten_with_path(obj)

8. grad and value_and_grad against loss.backward()


The difference in one line. PyTorch differentiates the computation that just ran: loss.backward() walks the graph autograd recorded during the forward pass and adds gradients into each parameter's .grad. JAX differentiates a function: jax.grad(loss_fn) returns a new function that, given parameters, returns a gradient pytree shaped like them. There is no .grad attribute, no zero_grad() and no requires_grad; you choose what to differentiate with argnums.


loss, grads = jax.jit(jax.value_and_grad(loss_fn))(params, x, y)   # JAX: one pure call
# PyTorch on the same weights and batch:
loss_t = loss_fn_torch(model, x, y); loss_t.backward()            # fills p.grad for every parameter

Why the key biases stand out. Their true gradient is exactly zero: adding the same vector to every key adds the same number to every score in a row, and softmax ignores a constant added to a whole row. Both frameworks compute float noise around zero (about 2e-11 here), so their relative difference is meaningless and is left out of the "worst relative" figure. The setup's equivalence check explains why that noise still moves those biases during AdamW training (Reading, section 0 and the {{Training lab|#t-train}}).
