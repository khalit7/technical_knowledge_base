6. Checkpoints with orbax: stop, restore, continue bit for bit

The problem. A long run is preempted; you need its weights, its optimiser state and its place in the data, written without stalling training, and restorable even onto a different number of devices. PyTorch's torch.save(model.state_dict()) writes one file from one process; torch.distributed.checkpoint (DCP) is the sharded, multi-process path ({{Distributed PyTorch|n:3c65c17b0d0d815e85aff8decd8f35ab}} covers it).

How it works. orbax saves any pytree. A CheckpointManager numbers checkpoints by step, keeps the last few and writes asynchronously: save() copies the arrays off the device and returns, and a background thread writes them while training continues. Arrays are stored in a TensorStore format (OCDBT, one key-value database per process), and each process writes only the shards it holds. Restoring takes a target with shapes, dtypes and shardings, so a checkpoint saved on one layout can be loaded onto another. Source at orbax v0.12.7: enable_async_checkpointing: bool = True is the default ({{checkpoint_manager.py:394|https://github.com/google/orbax/blob/a2a87a55da9caa8a76770f5e0fa544b0b5aff421/checkpoint/orbax/checkpoint/checkpoint_manager.py#L394}}); save at line 1334, restore at 1671, wait_until_finished at 2054.

One run stopped at step and resumed in a new process, against one that never stopped

Three separate Python processes (src/train/ckpt_resume.py): one trains steps without stopping; one trains steps, saves {params, opt_state} and the grain data iterator in one orbax checkpoint and exits; a third restores both and trains the rest. The final parameters and Adam moments ( arrays) are compared with np.array_equal. measured

Sharded save, different layout on restore

On 8 simulated CPU devices (a 2 x 4 mesh, the {{Sharding lab|#t-shard}} explains meshes), the running example's weights were placed with the two-dimensional ones split over both mesh axes: blocks[0].mlp.fc1.w, global shape [128, 512], becomes shards of under P('data', 'model'). orbax saved them and restored them twice: onto an 8-way split of the other axis (P(None, 'x'), shards ) and onto a single device. Every one of the arrays came back equal both times measured (src/train/ckpt_sharded.py). The arrays and the collectives on simulated devices are real; the write speeds are not those of a pod.

7. Data with grain: a loader whose position is part of the checkpoint

The problem. Resuming the weights is not enough: if the data loader restarts its epoch, the model sees some batches twice and others never, and the resumed run is no longer the run you planned. A PyTorch DataLoader does not save its position by default (the separate torchdata package adds a {{StatefulDataLoader|https://meta-pytorch.org/data/beta/torchdata.stateful_dataloader.html}} ("a drop in replacement for torch.utils.data.DataLoader that implements state_dict and load_state_dict methods, enabling mid-epoch checkpointing") for this).

How it works. grain builds a pipeline from a random-access source (anything with __len__ and __getitem__) and transformations that are pure functions of the record index and a seed: shuffling is a fixed permutation, not a buffer. So the whole state of an iterator is a small record (MapDataset.shuffle maps each position to a shuffled index with index_shuffle: {{dataset.py:649|https://github.com/google/grain/blob/d2568262e43ef1e43a7400e59caba2b2f3e1c35f/grain/_src/python/dataset/dataset.py#L649}}, {{shuffle.py:68|https://github.com/google/grain/blob/d2568262e43ef1e43a7400e59caba2b2f3e1c35f/grain/_src/python/dataset/transformations/shuffle.py#L68}}, grain v0.2.18), here {"next_index": 100}, which orbax saves next to the weights. Multi-process loading (grain.DataLoader with workers, or mp_prefetch) keeps the same determinism.
