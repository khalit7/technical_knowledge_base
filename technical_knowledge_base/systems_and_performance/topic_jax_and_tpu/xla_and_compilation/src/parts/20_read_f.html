5. Layouts and tiling

The idea. An array's layout is the order in which its dimensions sit in memory, written minor-to-major: f32[4096,128]{1,0} means dimension 1 changes fastest (row-major, PyTorch's contiguous); {0,1} would be column-major. In PyTorch a transpose is a free view with new strides and the kernel that reads it copes. XLA instead gives every array one layout, chosen by the layout-assignment pass so that matmuls and reductions read memory in the order they want, and then each transpose either disappears into the instruction that reads it or becomes a real copy.

Three transposes and reshapes, compiled measured here

Entry computations of the optimised HLO, metadata removed (src/lab/buffer_lab.py). A transpose alone is a physical copy (transpose_copy_fusion). Fed into a matmul it vanishes: transpose-folding rewrites the dot to contract over dimension 0 instead, because, in its header's words, the dot "is implemented by a GEMM kernel that can transpose its inputs". A reshape that does not change memory order becomes a bitcast, a free reinterpretation, inside the fusion.

In the train step, layout assignment added copies, and reshape-decomposer ("Postcondition: All reshapes are turned into bitcasts") turned reshapes into bitcasts or a bitcast plus copy (see the {{Pass diff viewer|#t-xppass}}).

Tiling, on TPU. A TPU layout also cuts the array into fixed tiles, because, in XLA's words, "XLA TPU uses a variety of tile-based formats due to the two-dimensional nature of its vector registers". The docs write F32[3,5]{1,0:T(2,2)} for a 3 x 5 array in 2 x 2 tiles, padded to whole tiles, and state that bf16 on TPU uses (8,128)(2,1): tiles of 8 x 128 elements, with pairs of rows interleaved inside (docs/tiled_layout.md at the pinned commit) Google docs. The cost is padding: derived the running example's output head in bf16, [128, 65] with 65 as the minor dimension, would be padded to [128, 128], 1.97 times its bytes, while the embedding table [65, 128] pads only its 65 rows to 72 (1.11 times). That is the arithmetic behind "choose dimensions that are multiples of 128", taught with the MXU on {{TPU programming and performance|n:3c65c17b0d0d8129b0a5fd82e44ecf6e}}. not run here

6. Buffer assignment: every byte planned before the step runs

The problem. PyTorch allocates as it goes, from a caching allocator, and you learn the peak afterwards (torch.cuda.max_memory_allocated()). XLA plans memory ahead: after the passes it fixes an order of execution (the schedule), gives every value a live range (from the instruction that defines it to the last one that reads it), and packs values whose ranges do not overlap into the same bytes. The result is the buffer assignment; compiled.memory_analysis() summarises it, and the dump writes it out in full.

The reconstructed peak is MB against the MB XLA reports at position (a % difference from values that share an allocation). Phase bands come from the operation names: jvp is the forward pass, transpose(jvp) the backward pass, the rest the optimiser and gradient norms.

The shape is the one every training step has: the forward pass piles up activations the backward pass will need, the peak sits at the turn, and the backward pass frees them as it consumes them. XLA attributes the bytes live at the peak to the JAX operation that produced them measured here:

What is in the plan. allocations: are parameters that may also hold an output (the donated parameters and optimiser state, reused for the new ones), are thread-local scalars inside loops and reduction bodies, and one preallocated temporary buffer of MB holds every intermediate at its planned offset. One quirk to know: on CPU, memory_analysis().peak_memory_in_bytes leaves the temporaries out; add temp_size_in_bytes or read total_allocation_bytes.

Aliasing and in-place updates

Donation (jax.jit(step, donate_argnums=(0, 1)), taught in the root's Compiler lab) lets an output reuse an input's buffer. Without it, XLA must keep the input intact, and a pass makes sure it does. An old note on this knowledge base said that under jit "XLA turns these [x.at[i].set(v)] into true in-place updates, so no copy cost in practice". Checked on a MiB array measured here:

So the update is in place only when the array is donated or is an intermediate inside the jitted function. Updating a non-donated argument copies the whole array first, because copy-insertion must keep "Entry parameter[s] ... live out of the entry computation" in their own allocation (copy_insertion.h:41) read in source. In a training loop that updates a large state each step, that is a full copy per step: donate.

7. Rematerialisation: yours and the compiler's

Two different mechanisms share the name. jax.checkpoint (alias jax.remat) is yours: at trace time you say which values the backward pass may keep and which it must recompute, with policies such as dots_saveable; the root's Compiler lab measures the policies on this model. The second is XLA's HloRematerialization pass, which runs after scheduling and recomputes values only when the planned peak exceeds the device's memory limit.

Where it runs. In the GPU pipeline (gpu_compiler.cc:3378); it is absent from the CPU pipeline, which is why no dump on this page shows it read in source. Its header names two algorithms, kAlwaysRemat ("Rematerializes anything it can at any point the HLO is above the memory limit. Default rematerialization algorithm.") and kPeakPriority ("Prioritize rematerializing the highest peak ... Much slower than the default algorithm"), and three strategies a mode can enable: recompute, compress (keep a value in a more compact shape that the backend supplies through a CompactShapeFunction) and host offload (move it to host memory and back) (hlo_rematerialization.h:78-96). The TPU compiler's equivalent is inside libtpu and cannot be read.

When it matters. A model that barely does not fit on a GPU may not fail: XLA recomputes until it fits, and the step gets slower without an error. Two checks catch it: compiled.memory_analysis() against the device's memory, and a dump filtered to the pass (--xla_dump_hlo_pass_re=rematerialization). The fix you control is the explicit one: choose what jax.checkpoint saves, so the compiler has nothing left to guess. One detail ties the two together: jax.checkpoint lowers its recomputation behind an optimization_barrier so that XLA's CSE (section 3) cannot merge the recomputed values back into the forward pass and undo the saving (ad_checkpoint.py:867 at jax-v0.11.2, quoted in the root's lab).
