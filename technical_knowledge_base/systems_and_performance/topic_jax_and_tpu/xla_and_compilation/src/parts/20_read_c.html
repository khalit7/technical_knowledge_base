1. Lowering: from jaxpr to StableHLO

The problem. Tracing (taught on {{JAX core|n:3c65c17b0d0d81b7a0d1faba6cef5561}}) leaves a jaxpr: a flat list of equations, each one primitive (an operation JAX knows how to differentiate, batch and lower, such as dot_general, mul, reduce_sum) applied to typed variables. A compiler cannot read jaxprs. Lowering translates every equation into operations of a compiler language, one rule per primitive, much as a PyTorch backend gives each ATen operator a kernel.

The target, StableHLO. StableHLO is an MLIR dialect: MLIR is a framework for building compiler languages, and a dialect is one such language with its own operations and types. StableHLO's operations (stablehlo.dot_general, stablehlo.reduce, stablehlo.broadcast_in_dim, ...) are fixed and versioned, so that a program written today can be read by a compiler built later: its compatibility document promises "5 years of backward compatibility" and "2 years of forward compatibility" for portable artifacts (openxla/stablehlo compatibility.md, read 2026-10-15) Google docs. Next to it sits CHLO ("client HLO"), a small set of convenience operations (chlo.erfc, chlo.square) that are broken into StableHLO before XLA proper sees them. PyTorch/XLA produces the same StableHLO from PyTorch programs, which is why the format is the meeting point between front ends and compilers.

How it works, in the source

One jit call becomes one MLIR module. The walk, at jax-v0.11.2 read in source:

A lowering rule is a Python function that receives the equation's operands as MLIR values and emits operations. Most elementwise primitives share one rule, _nary_lower_hlo, which first makes every operand the full output shape with explicit broadcasts and then emits the single StableHLO operation: exp's whole registration is one line. Some rules are written in JAX itself (mlir.lower_fun traces a JAX function and lowers that), which is how a primitive such as integer_pow becomes a few multiplies. A rule can also be registered per platform; dot_general registers one for each platform, which shows up in section 9 when one exported program serves CPU, CUDA and TPU at once.

The broadcasts cost nothing at run time: fusion folds them into the kernel that reads them.

2. PJRT: the plug between JAX and a device


The problem. JAX should not need to know how to compile for, allocate on, or launch work on each kind of hardware, and a hardware vendor should not need to change JAX to support a new chip. PJRT is the interface in between: a C API that a device plugin implements (create a client, list devices, compile a StableHLO module into an executable, allocate and copy buffers, execute). A jax.Array holds one buffer per device, allocated through PJRT (wrapped by IFRT, a layer above PJRT; jaxlib's own start-up log line reads PjRt-IFRT device count: total=1, addressable=1). The PyTorch analogue is the dispatcher plus a device backend; PyTorch/XLA goes through PJRT as well.


How it works. The API is versioned in xla/pjrt/c/pjrt_c_api.h: PJRT_API_MAJOR 0, incremented "when an ABI-incompatible change is made", and PJRT_API_MINOR  at the pinned commit, incremented for compatible additions read in source. JAX finds plugins at start-up: any installed module under the jax_plugins namespace, or any package advertising a jax_plugins entry point (discover_pjrt_plugins, xla_bridge.py:434), each registered with register_plugin (:584). The CPU client is built into jaxlib; NVIDIA GPUs come from the jax-cuda12-plugin or jax-cuda13-plugin wheels and TPUs from libtpu.

When it matters. Three times in practice. Installing GPU or TPU support means installing the right plugin version for your jaxlib. Anything outside JAX that can load a PJRT plugin (a C++ server, another framework) can compile and run the StableHLO that JAX produces, which is the basis of jax.export (section 9). And the asynchronous behaviour you see in JAX (a call returns before the work is done; block_until_ready waits) is PJRT's execute returning futures.
