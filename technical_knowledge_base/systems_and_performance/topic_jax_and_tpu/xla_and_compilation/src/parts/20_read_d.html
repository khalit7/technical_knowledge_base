3. XLA's HLO and its pass pipeline

HLO (High Level Operations) is XLA's own program form. A module holds computations; the ENTRY computation is the program, and the others are called from it (fusion bodies, loop bodies, the two-argument functions that tell a reduction how to combine values). Each line is one instruction. One line of the optimised attention block, taken apart:

%dot.4 = f32[4096,128]{1,0} dot(%param_0, %param_1), lhs_contracting_dims={1}, rhs_contracting_dims={0}
 name     shape (dtype[dims])  opcode   operands          attributes: which dimensions are summed over
                       {1,0} = layout: dimension 1 is fastest-varying in memory (row-major)

The shape [4096,128] is the batch of 32 x 128 characters flattened by a pass called dot_decomposer, which puts every matmul into one canonical form. On a TPU the same line would carry a tiled layout such as {1,0:T(8,128)(2,1)} and possibly a memory space S(1), which XLA's docs gloss as "this array lives in VMEM (on a TPU)" (docs/shapes.md) Google docs; section 5 explains tiles.

Passes. XLA optimises by running passes: each one reads the whole module and rewrites it (simplify algebra, remove duplicates, choose layouts, fuse, insert copies). Passes are grouped into pipelines; a pipeline wrapped in HloPassFix repeats until nothing changes, which is why the dumps below show algsimp, dce and reshape-mover six times in a row. Each backend assembles its own pipeline in its compiler: cpu_compiler.cc has AddPass calls naming pass classes; gpu_compiler.cc with its fusion pipeline has , naming ; classes appear in both read in source. The TPU pipeline lives in the closed libtpu and cannot be read. PyTorch's nearest counterpart is the chain AOTAutograd plus Inductor: decompositions, functionalisation, pattern passes, then the scheduler that fuses.

How to watch them. XLA_FLAGS="--xla_dump_to=DIR --xla_dump_hlo_pass_re=.*" writes the module after every pass that changed it. Which single pass removes the most instructions from the train step before fusion?
cse, from to instructions. The step computes the global gradient norm twice (once inside clip_by_global_norm, once for logging), one square, sum and add per parameter array each time, and broadcasts the same scalars into each of the 69 optimiser updates. Tracing records all of it; CSE keeps one copy. Its header: "Identical constants and identical instructions with the same operands are commoned" (hlo_cse.h:32).
