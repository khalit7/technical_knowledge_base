8. The caches: paying for compilation once

In memory. A jitted function keeps a cache keyed on everything that can change the program: the function object itself, the abstract signature of its arguments (shapes, dtypes, weak types, the pytree structure), the values of static arguments, and the tracing context (configuration that affects tracing, such as jax_default_matmul_precision). A hit skips tracing, lowering and compiling; a miss does all three. In every scenario of the {{Recompile detective|#t-xprec}}, counted through jax.monitoring, the three counts move together measured here. This cache dies with the process. f._cache_size() reports how many entries a jitted function holds.

On disk. The persistent compilation cache stores executables between processes:

jax.config.update("jax_compilation_cache_dir", "/path/to/cache")
jax.config.update("jax_persistent_cache_min_compile_time_secs", 0.0)  # default 1.0: faster compiles are not written

Hits, misses, files and changed ingredients are deterministic; CPU seconds for the compile call are rough. One entry is KB; a hit costs s of CPU against s for a compile.

When it matters. On a TPU pod every host compiles the same program at start-up, for minutes on large models; the JAX docs recommend a cache "in a shared file system (eg: NFS) or remote storage" for multi-node jobs, and describe a Cloud Storage bucket for it. The same docs carry a warning worth repeating: "The compilation cache is considered trusted. ... Sharing a compilation cache is equivalent to allowing anyone who can write to the cache directory to run code on your machine" (docs/persistent_compilation_cache.md) Google docs. 9. Ahead of time: stages, serialized executables and jax.export

Stages. jax.jit(f) hides four stages that you can call one at a time: .trace(*args) gives a Traced (the jaxpr), .lower() a Lowered (StableHLO), .compile() a Compiled (an executable you call directly). Arguments can be real arrays or jax.ShapeDtypeStruct placeholders, so a program can be compiled before any data exists. A Compiled object never retraces: called with a different shape it refuses measured here:



Serialized executables. jax.experimental.serialize_executable.serialize(compiled) turns the compiled CPU executable of the forward pass into  KB of bytes; in a fresh process deserialize_and_load brings it back in  s of CPU, and it returns the same logits (difference 0.0) measured here. The bytes are machine code for this backend and this jaxlib: a cache you manage yourself, not a format to ship.


jax.export: the format to ship. jax.export.export(jax.jit(f), platforms=...)(*args) returns an Exported: the StableHLO module plus everything needed to call it later (input and output types, shardings, the platforms, a calling convention version that fixes how arguments are passed;  here, the current one). .serialize() gives bytes; jax.export.deserialize(...).call(...) compiles and runs them, in another process or years later. 10. Recompiles: causes, evidence and the fix


The problem. Anything in the cache key from section 8 that changes between calls costs a full trace, lower and compile: for the train step, seconds; for a large model on TPU, minutes. Usually nothing fails, the step just gets slow. JAX can explain every miss: with jax.config.update("jax_explain_cache_misses", True) each one logs a warning that names the argument and what changed. The {{Recompile detective|#t-xprec}} runs eleven scenarios with their real explanations; the common causes:


    

  • Shapes that vary: the last, smaller batch of an epoch; variable sequence lengths. "different input types: * at x, now f32[31,128] and before f32[32,128]".
    • 

  • Weak types: a Python 2.0 is weakly typed, a np.float32(2.0) is not; the explanation reads "now f32[]{weak_type=False} and before f32[]{weak_type=True}".
    • 

  • Static arguments: every new value of a static_argnums argument is a new program (JAX's explanation here is only "cache miss explanation unavailable").
    • 

  • A new function object: jax.jit(lambda ...) created inside a loop never hits ("never seen function ... maybe the function is being re-defined repeatedly"). Wrapping the same named function again is fine.
    • 

  • Configuration: changing jax_default_matmul_precision between calls: "Tracing context doesn't match".
    • 

  • And its opposite: a Python global read inside the function is baked in at trace time; changing it later neither recompiles nor takes effect.
    • 





A recompilation storm, and the same loop with buckets


A decoding-style loop calls a jitted attention-like function on a prefix that grows from 1 to 64 positions. Exact shapes compile once per length; padding each length up to a multiple of 16 (and masking) needs four programs. Same inputs, same outputs; compile counts are deterministic, seconds are measured here (the second of three repeats is drawn; compile time in the counters is the median of the three).














At scale. In a long training or serving job, count compilations instead of reading logs. jax.monitoring.register_event_duration_secs_listener receives an event for every trace (/jax/core/compile/jaxpr_trace_duration), lowering and backend compile (/jax/core/compile/backend_compile_duration), the same hooks the detective uses; export them to your metrics system and alert when the count grows after warm-up. jax_log_compiles prints one line per stage:




The fixes, in the order to try them: make the shapes static (pad and mask to a few buckets, drop or pad the last batch); keep Python scalars out of the signature or make their types consistent; hoist jax.jit out of loops and keep one jitted function per role; pass configuration as static arguments deliberately, not by accident; and warm up every bucket before timing. When shapes must vary at run time and padding wastes too much, export with symbolic shapes (section 9) or let the serving framework bucket for you.
