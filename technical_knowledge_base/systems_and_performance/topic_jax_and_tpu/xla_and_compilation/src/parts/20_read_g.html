7. Rematerialisation: yours and the compiler's

Two different mechanisms share the name, and they differ in who decides and what failure looks like:

jax.checkpoint (alias jax.remat)XLA's HloRematerialization pass
Who decidesyou, at trace time, with a policy such as dots_saveable (measured on this model in the root's Compiler lab)the compiler, after scheduling
When it actsalways: what is not saved is recomputed in the backward passonly when the planned peak exceeds the device's memory limit
Whereevery backendthe GPU pipeline (gpu_compiler.cc:3378); absent from the CPU pipeline, so no dump here shows it; the TPU equivalent is inside libtpu read in source
What you seea known slowdown you chosea model that barely does not fit may not fail: the step just gets slower, with no error

How to check. compiled.memory_analysis() against the device's memory, and a dump filtered to the pass (--xla_dump_hlo_pass_re=rematerialization). The fix you control is the explicit one: choose what jax.checkpoint saves, so the compiler has nothing left to guess. The two meet at one point: jax.checkpoint lowers its recomputation behind an optimization_barrier so that XLA's CSE (section 3) cannot merge the recomputed values back into the forward pass and undo the saving (ad_checkpoint.py:867 at jax-v0.11.2, quoted in the root's lab).

The pass's algorithms and strategies

Its header names two algorithms, kAlwaysRemat ("Rematerializes anything it can at any point the HLO is above the memory limit. Default rematerialization algorithm.") and kPeakPriority ("Prioritize rematerializing the highest peak ... Much slower than the default algorithm"), and three strategies a mode can enable: recompute, compress (keep a value in a more compact shape that the backend supplies through a CompactShapeFunction) and host offload (move it to host memory and back) (hlo_rematerialization.h:78-96) read in source.

8. The caches: paying for compilation once

Two caches in front of the compiler: a call misses only if its key is new to both

The in-memory key as the recompile scenarios exercise it (section 10); the persistent key's eight ingredients from cache_key.py at jax-v0.11.2 read in source. The 1 s threshold is jax_persistent_cache_min_compile_time_secs's default.

In memory. A jitted function keeps a cache keyed on everything that can change the program: the function object itself, the abstract signature of its arguments (shapes, dtypes, weak types, the pytree structure), the values of static arguments, and the tracing context (configuration that affects tracing, such as jax_default_matmul_precision). A hit skips tracing, lowering and compiling; a miss does all three, and in every scenario of the {{Recompile detective|#t-xprec}}, counted through jax.monitoring, the three counts move together measured here. This cache dies with the process; f._cache_size() reports how many entries a jitted function holds.

On disk. The persistent compilation cache stores executables between processes:

jax.config.update("jax_compilation_cache_dir", "/path/to/cache")
jax.config.update("jax_persistent_cache_min_compile_time_secs", 0.0)  # default 1.0: faster compiles are not written

Its key is a SHA-256 over eight ingredients, hashed in order in cache_key.py (the entries list at line ): . The XLA flags are hashed after removing flags that cannot change the program, among them --xla_dump_to and --xla_force_host_platform_device_count. So upgrading jaxlib or the device plugin, adding a flag, or any code change that alters the module (donation included) misses. JAX logs each ingredient's hash at debug level, which tells which one changed between two runs:

Hits, misses, files and changed ingredients are deterministic; CPU seconds are rough. One entry is KB; a hit costs s of CPU against s for a compile.

When it matters. On a TPU pod every host compiles the same program at start-up, for minutes on large models; the JAX docs recommend a cache "in a shared file system (eg: NFS) or remote storage" for multi-node jobs, and describe a Cloud Storage bucket for it. The same docs warn: "The compilation cache is considered trusted. ... Sharing a compilation cache is equivalent to allowing anyone who can write to the cache directory to run code on your machine" (docs/persistent_compilation_cache.md) Google docs. Keep it per user, or read-only for everyone but a trusted job.

10. Recompiles: causes, evidence and the fix


Anything in the in-memory cache key (section 8) that changes between calls costs a full trace, lower and compile: for the train step, seconds; for a large model on TPU, minutes. Usually nothing fails; the step just gets slow. JAX can explain every miss: with jax.config.update("jax_explain_cache_misses", True) each one logs a warning that names the argument and what changed. The common causes, with JAX's own words from the {{Recompile detective|#t-xprec}} (eleven scenarios):


    

  • Shapes that vary: the last, smaller batch of an epoch; variable sequence lengths. "different input types: * at x, now f32[31,128] and before f32[32,128]".
    • 

  • Weak types: a Python 2.0 is weakly typed, a np.float32(2.0) is not: "now f32[]{weak_type=False} and before f32[]{weak_type=True}".
    • 

  • Static arguments: every new value of a static_argnums argument is a new program (JAX's explanation here is only "cache miss explanation unavailable"), and the value must be hashable (a list raises; pass a tuple).
    • 

  • A new function object: jax.jit(lambda ...) created inside a loop never hits ("never seen function ... maybe the function is being re-defined repeatedly"): 3 calls, 3 compilations. Wrapping the same named function again is fine.
    • 

  • Configuration: changing jax_default_matmul_precision between calls: "Tracing context doesn't match".
    • 

  • And its opposite: a Python global read inside the function is baked in at trace time; changing it later neither recompiles nor takes effect (the detective prints [2. 2.] twice). Pass it as an argument.
    • 





A recompilation storm: 64 compilations for 64 prefix lengths, 4 with buckets


A decoding-style loop calls a jitted attention-like function on a prefix that grows from 1 to 64 positions. Exact shapes compile once per length; padding each length up to a multiple of 16 (and masking) needs four programs. Same inputs, same outputs; compile counts are deterministic, seconds are measured here (the second of three repeats is drawn; compile time in the counters is the median of the three).














At scale, count compilations instead of reading logs. jax.monitoring.register_event_duration_secs_listener receives an event for every trace (/jax/core/compile/jaxpr_trace_duration), lowering and backend compile (/jax/core/compile/backend_compile_duration), the same hooks the detective uses; export them to your metrics system and alert when the count grows after warm-up. jax_log_compiles prints one line per stage (sample below).

The fixes, in the order to try them: make the shapes static (pad and mask to a few buckets, drop or pad the last batch); keep Python scalars out of the signature or make their types consistent; hoist jax.jit out of loops and keep one jitted function per role; pass configuration as static arguments deliberately, not by accident; and warm up every bucket before timing. When shapes must vary at run time and padding wastes too much, export with symbolic shapes (section 9) or let the serving framework bucket for you.
