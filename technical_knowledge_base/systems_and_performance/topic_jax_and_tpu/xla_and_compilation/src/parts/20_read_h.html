Taking a profile. Wrap a few steps after warm-up:

with jax.profiler.trace("/tmp/prof"):
    for i in range(5):
        with jax.profiler.StepTraceAnnotation("train", step_num=i):
            state = step(*state)
            jax.block_until_ready(state)   # without it the trace shows dispatch, not work

and open the folder in XProf (pip install xprof; the tool behind TensorBoard's Profile tab), which the JAX docs describe as "a great way to acquire and visualize performance traces and profiles of your program, including activity on GPU and TPU" (docs/profiling.md) Google docs, or in Perfetto. The files carry the machine's host name: scrub before sharing.

"On this CPU" is what xprof 2.23.2's own converter returned for the running example's trace measured here. The device-side tables are empty on a CPU: their columns (the header of hlo_stats includes "HBM BW (GiB/s)", "Bound by" and "TPU core type") are filled from device events that a CPU run does not record. not run here: their TPU and GPU content.

What the trace says about the running example. One step is about ms of wall time on this loaded machine; of the kernels' thread time, the backward pass takes about %, the forward % and the optimiser and gradient norms % measured here. Matmuls and the projections around them (the linear function) dominate. On a TPU the same table would be read against the roofline: is each fusion limited by FLOPs or by HBM bandwidth, which {{TPU programming and performance|n:3c65c17b0d0d8129b0a5fd82e44ecf6e}} teaches. Every kernel of one step, joined to its phase and model function, is in the {{Profile reader|#t-xpprof}}.

How to read a trace you did not expect. Gaps on the device row with a busy Python row mean the host cannot feed the device (dispatch, data loading, a host sync such as float(loss) every step). One kernel far longer than its neighbours: find it by name in the optimised HLO (fusion names are stable within one compile) and look at what was fused into it. Many tiny kernels: fusion broke (section 4). Time inside jit calls that should be cached: a recompile (section 10). The PyTorch profiler and Nsight equivalents are on {{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}}.

12. XLA flags that matter, and their risks

XLA reads XLA_FLAGS once, when the backend starts: "Set XLA_FLAGS before importing Jax or other relevant libraries. Changing XLA_FLAGS after backend initialization will have no effect" (docs/xla_flags.md) Google docs. Every flag is a field of DebugOptions, defined with its default and help text in xla/debug_options_flags.cc read in source:

Five CPU settings on the train step measured here, each in a fresh process; losses are the first five steps from the same initial state:

CPU seconds on a shared machine (1-minute load printed per row): read ratios, not values. --xla_backend_optimization_level=0 roughly halves compile time and more than doubles step time; numbers stay identical, and the optimised HLO is the same ( kernels, fusions, checked with the flag on): the level steers the backend's code generation, not the HLO passes. Fast math changed nothing measurable on this program.

On TPU, flags go in LIBTPU_INIT_ARGS and are read by the closed compiler. MaxText keeps a library of them: a scoped VMEM limit of 98304 KiB for dense models, flags that fuse and overlap collectives with compute, and data-parallel overlap (benchmarks/xla_flags_library.py at the pinned commit) read in source not run here.

Risks
Flags are debug options, not an API: names change between releases and help text goes stale (the YNNPACK flag's help contradicts its default, section 4). Some change numbers (fast math, disabling passes). Disabling a pass can make compilation fail or the program slow in ways that only show at scale. Every flag that is not on JAX's exclusion list is part of the persistent cache key (section 8), so a new flag recompiles everything. Keep production flags in one place, record them with each run, and re-measure after every JAX upgrade.

13. Against torch.compile, Inductor and Triton

The concepts line up (section 0's table); the behaviour differs in five places.

  • Failure mode. Dynamo splits the graph at what it cannot trace and runs that part in Python; JAX raises. One program or an error, never a silent fallback (the root's lab shows both on the same branch).
  • Dynamic shapes. torch.compile marks a dimension dynamic after it changes and compiles one program for a range of sizes; JAX keeps every shape static under jit and offers symbolic shapes only through jax.export (section 9). In JAX, padding to buckets is your job.
  • Where the decisions live. Inductor is Python and emits Triton or C++ you can read; XLA's passes are C++, readable for CPU and GPU, closed for TPU. XLA:GPU itself generates Triton for some fusions (GemmFusion, SoftmaxRewriterTriton), so Triton is an implementation detail of both stacks; a hand-written {{Triton|n:3c65c17b0d0d81729d15ed4d1a4461b3}} kernel's JAX counterpart is a {{Pallas|n:3fa5c17b0d0d817699fcf65d085402e7}} kernel.
  • Memory. XLA plans every byte before running and reports it (memory_analysis, section 6); PyTorch allocates at run time and reports afterwards.
  • Scope. jit compiles the whole train step, optimiser included, as one program; torch.compile is often applied to the model only, with the optimiser step outside or compiled separately.
