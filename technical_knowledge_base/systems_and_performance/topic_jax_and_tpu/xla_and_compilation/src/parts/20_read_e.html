4. Fusion: how XLA decides, and why it stops

The problem. Run a chain of elementwise operations one kernel at a time and every intermediate result is written to memory and read straight back. For this kind of work memory traffic, not arithmetic, is the cost. Fusion compiles a group of operations into one kernel so intermediates stay in registers or on-chip memory. The root's Compiler lab shows the result on one MLP block; this section shows the decisions.

How it works: producer into consumer

XLA's basic fusion pass (InstructionFusion, which the CPU subclasses as CpuInstructionFusion) walks the program from its outputs back to its inputs. For each instruction (the consumer) it looks at each operand (the producer) and asks one question, ShouldFuse(consumer, operand_index). A yes pulls the producer's computation inside the consumer's fusion. If the producer has other users, it now runs twice, once inside the fusion and once for the others: XLA accepts that duplication only for cheap operations, decided by a fixed list in InstructionFusion::IsExpensive (instruction_fusion.cc:80): add, multiply, select, broadcast, transpose are cheap; exp, dot, convolution, collectives and custom calls are expensive read in source.

Two programs on a 256 x 512 array: e = jnp.exp(x) then (e + 1).sum(-1) and (e * 2).max(-1); the same with e = x * 2. Which compiles to fewer kernels?
The multiply: kernels against , and half the bytes moved () measured here. x * 2 is cheap, so it is duplicated into both reductions and never stored; exp is on the expensive list, so it runs once as its own kernel and both reductions read its 512 KiB result back from memory. Recomputation is the price of fusion, and XLA only pays it when it is cheap.

Fusion kinds

Every fusion instruction carries a kind, defined in hlo_instruction.h:301 read in source:

  • kLoop: "we emit code that generates one element of the root at a time": one loop over the output, computing every fused operation per element. Elementwise chains, broadcasts, and on CPU even reductions end up here.
  • kInput: "the primary node is the root of the fused instruction", a kernel built around a reduction (or transpose, concatenate, scatter) with its inputs fused in. XLA:GPU's PriorityFusion assigns it to exactly those four emitter kinds, Triton, cuDNN and sort fusions getting kCustom (priority_fusion.cc:1351-1367); this CPU program has none.
  • kOutput: "the primary node is not the root", and one operand buffer must be able to alias the output: work fused after an operation such as a matmul (an epilogue). The CPU code chooses it only when CanBeOutputFused holds; none appear here.
  • kCustom: "backend-specific fusions that don't fit into the above patterns": here, the YNNPACK library fusions; on GPU, Triton and cuDNN fusions.

The header's own comment adds "TODO(b/79869434): This categorization scheme is not great": the kinds are hints for code generation, and each backend uses them differently. The train step's fusions are kLoop and kCustom measured here.

A library inside the CPU compiler
XLA:CPU at this commit hands matmuls and many reductions to the YNNPACK library: its debug-option defaults add three library fusion types, INDIVIDUAL_DOT, INDIVIDUAL_CONVOLUTION and REDUCE (debug_options_flags.cc:272), while the help text of the flag that controls them still says "The default list is currently empty" (:1660). The code wins: the kCustom fusions named ynn_fusion in every dump here are those. On GPU the counterpart is cuBLAS or Triton for matmuls; on TPU, XLA's own code for the MXU.

What XLA refuses, and why

The strings are XLA's own (FusionDecision::Forbid("...")), with instruction names replaced by X. The same pair can be considered several times, so the counts are decisions, not pairs. "operand can not be duplicated" and "expensive producer would be duplicated" are the duplication rule above; "Too many reductions inside single fusion" is a CPU limit of five reductions per fusion, there "to avoid excessive compilation times" (cpu_instruction_fusion.cc:482); "Fusion is not profitable" refuses an expensive producer whose consumer reads each element more than once (a broadcast does); "Producer is not loop-fusible" covers library fusions, sorts, custom calls and loops.

The same softmax, three ways

One jax.nn.softmax(x, axis=-1) on a 256 x 512 array, compiled three ways on this CPU measured here: XLA's default; with the YNNPACK library fusions switched off (--xla_cpu_experimental_ynn_fusion_type=-individual_dot,-individual_convolution,-reduce); with the fusion pass switched off (--xla_disable_hlo_passes=fusion). Each box is one kernel, with the operations inside it; the bar under it marks a trip to memory. Bytes moved is XLA's cost_analysis().

Two things show. With the library off, XLA's own tree_reduction_rewriter splits each reduction into a reduce-window over chunks and then a smaller reduction, a pass whose header explains it as increasing "precision for the reduction operation by applying the reduce-window first" (pairwise-style summation, smaller rounding error). And with the fusion pass off the CPU still wraps each remaining operation in a one-operation kLoop fusion (FusionWrapper, "so that the fusion emitter can kick in"), which is why "no fusion" still prints fusions.

On GPU and TPU

XLA:GPU replaces the fixed rules with PriorityFusion (fusion_pipeline.cc:79), which estimates each candidate's run time with a cost model of the device and fuses the most profitable first, followed by MultiOutputFusion (:89), which lets one kernel produce several outputs (for example two reductions that read the same input, done in one pass over it). Matmuls go to cuBLAS through GemmRewriter or become Triton kernels through GemmFusion (gpu_compiler.cc:2132), and SoftmaxRewriterTriton (:2172) turns softmax-like patterns into Triton kernels read in source. On the CPU multi-output fusion exists (CpuMultiOutputFusion) but is only added when a backend option asks for it (cpu_compiler.cc:1098). The TPU's fusion rules are inside libtpu. What transfers from this CPU: the rules' logic (cheap producers duplicate, expensive ones materialise, loops and custom calls are walls) and the byte accounting. What does not: the exact kernels, and the library split.
