4. Fusion: how XLA decides, and why it stops

Run a chain of elementwise operations one kernel at a time and every intermediate result is written to memory and read straight back; for this kind of work memory traffic, not arithmetic, is the cost. Fusion compiles a group of operations into one kernel so intermediates stay in registers or on-chip memory. The root's Compiler lab shows the result on one MLP block; this section shows the decisions.

The rule: pull producers into consumers, duplicate only what is cheap

XLA's basic fusion pass (InstructionFusion, which the CPU subclasses as CpuInstructionFusion) walks the program from its outputs back to its inputs. For each instruction (the consumer) and each of its operands (the producer) it asks one question, ShouldFuse(consumer, operand_index); a yes pulls the producer's computation inside the consumer's kernel. If the producer has other users it now runs twice, once inside the fusion and once for the others, and XLA accepts that only for cheap operations, decided by a fixed list in InstructionFusion::IsExpensive (instruction_fusion.cc:80): add, multiply, select, broadcast, transpose are cheap; exp, dot, convolution, collectives and custom calls are expensive read in source.

Fusion kinds

Every fusion carries a kind, a hint for code generation that each backend uses differently: kLoop (one loop over the output's elements: elementwise chains, broadcasts, on CPU even reductions), kInput (built around a reduction, transpose, concatenate or scatter), kOutput (work fused after an operation such as a matmul) and kCustom (backend-specific: here the YNNPACK library; on GPU, Triton and cuDNN). The train step's fusions are kLoop and kCustom measured here.

The four kinds in the header's own words, and who assigns kInput on GPU

Every fusion instruction carries a kind, defined in hlo_instruction.h:301 read in source:

  • kLoop: "we emit code that generates one element of the root at a time": one loop over the output. Elementwise chains, broadcasts, and on CPU even reductions.
  • kInput: "the primary node is the root of the fused instruction": a kernel built around a reduction (or transpose, concatenate, scatter) with its inputs fused in. XLA:GPU's PriorityFusion assigns it to exactly those four emitter kinds, with Triton, cuDNN and sort fusions getting kCustom (priority_fusion.cc:1351-1367); this CPU program has none.
  • kOutput: "the primary node is not the root", and one operand buffer must be able to alias the output: work fused after an operation such as a matmul (an epilogue). The CPU chooses it only when CanBeOutputFused holds; none appear here.
  • kCustom: "backend-specific fusions that don't fit into the above patterns": here the YNNPACK library fusions; on GPU, Triton and cuDNN fusions.

The header's own comment adds "TODO(b/79869434): This categorization scheme is not great": the kinds are hints for code generation, used differently by each backend.

A library inside the CPU compiler
XLA:CPU at this commit hands matmuls and many reductions to the YNNPACK library: its debug-option defaults add three library fusion types, INDIVIDUAL_DOT, INDIVIDUAL_CONVOLUTION and REDUCE (debug_options_flags.cc:272), while the help text of the flag that controls them still says "The default list is currently empty" (:1660). The code wins: the kCustom fusions named ynn_fusion in every dump here are those. On GPU the counterpart is cuBLAS or Triton for matmuls; on TPU, XLA's own code for the MXU.

What XLA refuses, and why

XLA logs every decision at verbose level (TF_CPP_MIN_LOG_LEVEL=0 TF_CPP_VMODULE=cpu_instruction_fusion=2,instruction_fusion=3). Counted over the whole train step measured here:

XLA's own strings (FusionDecision::Forbid("...")), instruction names replaced by X; counts are decisions, not pairs. "operand can not be duplicated" and "expensive producer would be duplicated" are the duplication rule above; "Too many reductions inside single fusion" is a CPU limit of five, "to avoid excessive compilation times" (cpu_instruction_fusion.cc:482); "Fusion is not profitable" refuses an expensive producer whose consumer reads each element more than once (a broadcast does); "Producer is not loop-fusible" covers library fusions, sorts, custom calls and loops. Each box is one kernel with the operations inside it; the bar under it marks a trip to memory. Bytes moved is XLA's cost_analysis().

Two things show. With the library off, XLA's own tree_reduction_rewriter splits each reduction into a reduce-window over chunks and then a smaller reduction, a pass whose header explains it as increasing "precision for the reduction operation by applying the reduce-window first" (pairwise-style summation, smaller rounding error). And with the fusion pass off, the CPU still wraps each remaining operation in a one-operation kLoop fusion (FusionWrapper, "so that the fusion emitter can kick in"), which is why "no fusion" still prints fusions.

On GPU and TPU

XLA:GPU replaces the fixed rules with PriorityFusion (fusion_pipeline.cc:79), which estimates each candidate's run time with a cost model of the device and fuses the most profitable first, followed by MultiOutputFusion (:89), which lets one kernel produce several outputs (two reductions that read the same input, done in one pass over it). Matmuls go to cuBLAS through GemmRewriter or become Triton kernels through GemmFusion (gpu_compiler.cc:2132), and SoftmaxRewriterTriton (:2172) turns softmax-like patterns into Triton kernels read in source. On the CPU multi-output fusion exists (CpuMultiOutputFusion) but is added only when a backend option asks for it (cpu_compiler.cc:1098). The TPU's fusion rules are inside libtpu. What transfers from this CPU: the rules' logic (cheap producers duplicate, expensive ones materialise, loops and custom calls are walls) and the byte accounting. What does not: the exact kernels, and the library split. When no compiler will fuse what you need (attention's online softmax), you write the kernel: {{Pallas kernels|n:3fa5c17b0d0d817699fcf65d085402e7}} in JAX, {{Triton|n:3c65c17b0d0d81729d15ed4d1a4461b3}} in PyTorch.
