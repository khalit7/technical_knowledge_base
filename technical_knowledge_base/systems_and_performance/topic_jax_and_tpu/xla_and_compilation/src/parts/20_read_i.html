Common mistakes, with the evidence

Every error message below is real output from src/lab/ on JAX , paths removed.

A list (or dict) as a static argument
Static arguments are cache-key entries, so they must be hashable: . Pass a tuple.
Calling a Compiled object with a new shape
AOT-compiled code never retraces: . Compile one per shape bucket, or call the jit function instead.
Running a TPU-only export on another platform
. Export for every platform you will run on (platforms=("cpu", "cuda", "tpu")); the module grows only where lowering rules differ.
Serializing an export without flatbuffers
ImportError: Please install 'flatbuffers' in order to use Exported serialization. It is not a dependency of jax 0.11.2; install it next to JAX.
Setting XLA_FLAGS inside a script after JAX started
No error and no effect: the flags are read when the backend initialises (section 12). Set them in the shell, or in os.environ before import jax.
jax.jit(lambda ...) inside a loop
A new function object per iteration: every call traces and compiles (3 calls, 3 compilations in the detective). Define the function once, outside the loop.
Reading a Python global inside a jitted function
Its value at trace time is baked in as a constant. Change the global later and the function keeps returning the old answer, with no recompile and no warning ([2. 2.] twice in the detective). Pass it as an argument.
Expecting x.at[i].set(v) to be free on an argument
Without donation XLA copies the whole array first (section 6). Donate the state, or update values created inside the function.
Leaving jax.debug.print in the training step
It compiles to a host callback, a custom call that splits fusion: the three-operation chain that is 1 kernel without it is 3 kernels with it, plus a round trip to Python each step (Fusion explorer, "jax.debug.print in the middle").
Trusting peak_memory_in_bytes on CPU
On this backend it leaves out the temporaries; use temp_size_in_bytes plus arguments and outputs minus aliases, or total_allocation_bytes (section 6).
Sharing a writable compilation cache
The cache holds executables that JAX loads and runs; whoever can write to it can run code in your process (the JAX docs' own warning, section 8). Keep it per user or read-only for others.
Diagnosing a slow step by reading the Python
The Python ran once, at trace time. Read what the compiler made of it: the explanation of cache misses, the dumped HLO before and after (count fusions and copies), memory_analysis(), and a profile, in that order.

Interview questions, with short answers

Walk through what happens on the first call of jax.jit(f)(x), down to machine code.
The cache is looked up by the function, the abstract signature (shapes, dtypes, weak types, pytree structure), static values and the tracing context. On a miss: trace f with abstract tracers into a jaxpr; lower each equation by its primitive's rule into one StableHLO module (mlir.lower_jaxpr_to_module); hand it through PJRT to the backend compiler; XLA runs its pass pipeline (simplification to a fixed point, CSE, layout assignment, library rewrites, fusion, copy insertion), schedules, assigns buffers, and generates code (LLVM on CPU, PTX on NVIDIA, libtpu on TPU); store the executable (and optionally write it to the persistent cache). Then execution is dispatched asynchronously.
What is StableHLO for, if XLA has HLO?
A versioned, portable boundary between front ends (JAX, PyTorch/XLA) and compilers, with compatibility guarantees (5 years backward, 2 forward for portable artifacts). HLO is XLA's internal form and can change at any commit. jax.export ships StableHLO for that reason.
Why does XLA not fuse everything into one kernel?
Fusing a producer with several users duplicates its work, which XLA accepts only for cheap operations; matmuls and (on this CPU) many reductions go to libraries; loops, sorts, custom calls and host callbacks are walls; and backends cap fusion size (five reductions per fusion on CPU, concatenations of more than eight operands) to keep compile time and code quality reasonable. On GPU a cost model decides which fusions pay.
kLoop, kInput, kOutput, kCustom?
Hints for code generation: kLoop computes one output element at a time; kInput is built around a reduction (or transpose, scatter, concatenate) with its inputs fused in; kOutput fuses work after an operation such as a matmul into its output; kCustom is backend-specific (library, Triton, cuDNN). XLA's own header calls the scheme "not great".
Your train step got 30% slower after a refactor. How do you find out why?
First, recompiles: turn on jax_explain_cache_misses and count compilations after warm-up. Second, the program: dump the optimised HLO before and after, compare fusion counts, copies and transposes (a layout change can add copies), and check donation still aliases (alias_size_in_bytes). Third, memory: memory_analysis() before and after (a bigger plan can trigger XLA rematerialisation on GPU). Fourth, a profile: which kernels grew, and whether the device now waits on the host.
What is in the persistent compilation cache key, and why did my cache miss after an upgrade?
A hash of the canonicalised module, the jaxlib version, the backend version, the XLA flags (minus dump and similar flags), the compile options, the accelerator configuration, the compression algorithm and a custom hook. Upgrading jaxlib or the device plugin, or adding a flag, changes the key; so does a code change that alters the module, including donation.
jax.export or a serialized executable?
A serialized executable is machine code for one backend and one jaxlib: fast to load, useless elsewhere. An export is StableHLO with a calling convention: compiled where it runs, portable across platforms named at export time, and guaranteed to load on JAX up to 6 months newer (3 weeks older); it can carry symbolic shapes and its own VJP.
How does XLA's rematerialisation differ from jax.checkpoint?
jax.checkpoint is a decision you make at trace time about what the backward pass keeps. HloRematerialization is a compiler pass (in the GPU pipeline, absent on CPU) that recomputes values after scheduling only when the planned peak exceeds the device memory limit; it can also compress or offload. Relying on it means a silent slowdown instead of an out-of-memory error.
Why is a transpose sometimes free and sometimes a full copy?
Every XLA array has one layout. A transpose feeding a matmul is folded into the dot's dimension numbers; a reshape that keeps memory order is a bitcast; a transpose whose result must exist in the new order (stored, or read by an elementwise kernel) becomes a copy. Layout assignment chooses where those copies go.
Design: serve a JAX model on TPU for requests of any length up to 8,192 tokens, with predictable latency.
Fix a small set of shape buckets (for example powers of two in length, and a few batch sizes), pad and mask into them, and AOT-compile every bucket at start-up with jax.ShapeDtypeStruct placeholders so no request ever compiles; count compilations through jax.monitoring and alert on any after warm-up. Share a read-only persistent cache among replicas built by a trusted job, keyed by the exact jaxlib and libtpu versions. The trade-off is padding waste against the number of programs: with power-of-two buckets the expected waste is up to half of each request's length in the worst case, so add intermediate buckets where traffic concentrates. If the model must also run elsewhere, ship it as a multi-platform jax.export. Measure with a profile per bucket: decode steps are memory-bound, so small batches waste the MXU and the batch buckets matter as much as the length buckets.
