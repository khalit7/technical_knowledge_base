The idea in one screen

jax.jit hands XLA the whole train step as one program, so the compiler decides everything before the first step runs: which operations share a kernel, where every array sits in memory, and which compiled executable a later call reuses. Almost every JAX performance surprise (a slow first call, a step that keeps recompiling, a copy you did not ask for, memory that does not fit) is one of those decisions, and every one of them can be read in what XLA dumps.

One train step on its way down: six forms, one plug, and the levers you hold

Left: the running example's whole train step (forward, backward, AdamW) at each stage: 3,411 jaxpr equations, 5,318 StableHLO operations, 4,932 HLO instructions, then 817 kernels (783 fusions, 33 matmuls, 1 copy) and a planned peak of 374.4 MB measured here. Right: the levers this page explains, each beside the stage it acts on. A hit in the in-memory cache skips every stage above the executable; a hit on disk skips only XLA's compile (section 8).

You need: tracing and what a jaxpr is (JAX core), and the root's Compiler lab (five forms, fusion of one MLP block, donation, remat policies), which this page goes deeper than. Elsewhere: the sharding passes and collectives on Sharding and scale, the TPU's memory hierarchy on TPU programming and performance, hand-written kernels on Pallas kernels.

1. Lowering: from jaxpr to StableHLO

Tracing leaves a jaxpr: a flat list of equations, each one primitive (an operation JAX knows how to differentiate, batch and lower, such as dot_general, mul, reduce_sum) applied to typed variables. A compiler cannot read jaxprs. Lowering translates every equation into compiler operations, one rule per primitive, much as a PyTorch backend gives each ATen operator a kernel. One jit call becomes one MLIR module. Here is one sub-block of the running example in all four forms:

One attention sub-block, four forms: 61 equations grow to 90 operations and 133 instructions, then XLA's passes leave 13 kernels

Block 0's x + attention(layer_norm(x)), forward only, on the running example's shapes measured here. Switch forms; the text is the real output with paths removed (optimised HLO also without its metadata).



import jax
tr = jax.jit(attn_block).trace(p0, x)   # p0: block 0's parameters, x: float32[32, 128, 128]
print(tr.jaxpr)                          # jaxpr
lo = tr.lower()
print(lo.as_text())                      # StableHLO (an MLIR module)
print(lo.as_text(dialect="hlo"))         # XLA HLO before any pass
print(lo.compile().as_text())            # optimised HLO, after XLA's passes


From src/lab/lowering.py. In the jaxpr, t = div s 128.0 is followed by the same subtraction sub q t recorded twice (as u and as z), because LayerNorm's Python computes x - mu twice. Tracing records exactly what Python did; removing the duplicate is the compiler's job (common-subexpression elimination, section 3).




The target, StableHLO, is an MLIR dialect (MLIR is a framework for building compiler languages; a dialect is one of them) whose operations (stablehlo.dot_general, stablehlo.reduce, stablehlo.broadcast_in_dim, ...) are fixed and versioned: its compatibility document promises "5 years of backward compatibility" and "2 years of forward compatibility" for portable artifacts (openxla/stablehlo compatibility.md, read 2026-10-15) Google docs. That makes it the meeting point between front ends and compilers (PyTorch/XLA emits the same StableHLO) and the format jax.export ships (section 9). Beside it, CHLO ("client HLO") adds convenience operations (chlo.erfc, chlo.square) that are broken into StableHLO before XLA proper sees them.


A lowering rule is a Python function that receives the operands as MLIR values and emits operations. Most elementwise primitives share one rule, _nary_lower_hlo, which first broadcasts every operand to the output shape and then emits the single operation (exp's whole registration is one line). Some rules are JAX code traced again (mlir.lower_fun, which is how integer_pow becomes a few multiplies), and a rule can be registered per platform: dot_general registers one for each, which section 9 meets when one export serves CPU, CUDA and TPU.


Counting by the name JAX writes into every operation's location (jit(train_step)/jvp(...)/mul): the train step's jaxpr has  mul equations. How many StableHLO operations do they lower to?




, of which  are broadcast_in_dim measured here. A jaxpr may multiply an array by a scalar (mul bc 0.5); StableHLO requires both operands to have the same shape, so the rule broadcasts the scalar first. The broadcasts cost nothing at run time: fusion folds them into the kernel that reads them.

2. PJRT: the plug between JAX and a device


JAX should not need to know how to compile for, allocate on or launch work on each kind of hardware, and a vendor should not need to change JAX to support a new chip. PJRT is the C API in between, which each device plugin implements: create a client, list devices, compile a StableHLO module into an executable, allocate and copy buffers, execute. A jax.Array holds one buffer per device, allocated through PJRT (wrapped by IFRT, a layer above it; jaxlib's start-up log line reads PjRt-IFRT device count: total=1, addressable=1). The PyTorch analogue is the dispatcher plus a device backend; PyTorch/XLA goes through PJRT as well.


One API, one plugin per kind of device; only the CPU client exists on this machine




Structure from xla/pjrt/c/pjrt_c_api.h and xla_bridge.py at the pinned versions read in source; the highlighted client is the only one that started here measured here.


When it matters. Installing GPU or TPU support means installing the plugin that matches your jaxlib (the jax-cuda12-plugin or jax-cuda13-plugin wheels, or libtpu). Anything that can load a PJRT plugin (a C++ server, another framework) can compile and run the StableHLO that JAX produces, which is the basis of jax.export. And JAX's asynchronous dispatch (a call returns before the work is done; block_until_ready waits) is PJRT's execute returning futures.


Versioning, plugin discovery, and what this machine reports


The API is versioned in xla/pjrt/c/pjrt_c_api.h: PJRT_API_MAJOR 0, incremented "when an ABI-incompatible change is made", and PJRT_API_MINOR  at the pinned commit, incremented for compatible additions read in source. JAX finds plugins at start-up: any installed module under the jax_plugins namespace, or any package advertising a jax_plugins entry point (discover_pjrt_plugins, xla_bridge.py:434), each registered with register_plugin (:584). The CPU client is built into jaxlib.

3. XLA's HLO and its pass pipeline


HLO (High Level Operations) is XLA's own program form. A module holds computations: the ENTRY computation is the program, and the others are called from it (fusion bodies, loop bodies, the two-argument functions that tell a reduction how to combine values). Each line is one instruction. One line of the optimised attention block, taken apart:


%dot.4 = f32[4096,128]{1,0} dot(%param_0, %param_1), lhs_contracting_dims={1}, rhs_contracting_dims={0}
 name     shape (dtype[dims])  opcode   operands          attributes: which dimensions are summed over
                       {1,0} = layout: dimension 1 is fastest-varying in memory (row-major)


The shape [4096,128] is the batch of 32 x 128 characters flattened by a pass called dot_decomposer, which puts every matmul into one canonical form. On a TPU the same line would carry a tiled layout such as {1,0:T(8,128)(2,1)} and possibly a memory space S(1), which XLA's docs gloss as "this array lives in VMEM (on a TPU)" (docs/shapes.md) Google docs; section 5 explains tiles.


Passes. XLA optimises by running passes: each reads the whole module and rewrites it (simplify algebra, remove duplicates, choose layouts, fuse, insert copies). Passes are grouped into pipelines; a pipeline wrapped in HloPassFix repeats until nothing changes, which is why the dumps show algsimp, dce and reshape-mover six times in a row. Each backend assembles its own pipeline: cpu_compiler.cc has  AddPass calls naming  pass classes, gpu_compiler.cc with its fusion pipeline  naming , and  classes appear in both read in source. The TPU pipeline lives in the closed libtpu.


How to watch them. 4. Fusion: how XLA decides, and why it stops


Run a chain of elementwise operations one kernel at a time and every intermediate result is written to memory and read straight back; for this kind of work memory traffic, not arithmetic, is the cost. Fusion compiles a group of operations into one kernel so intermediates stay in registers or on-chip memory. The root's Compiler lab shows the result on one MLP block; this section shows the decisions.



The rule: pull producers into consumers, duplicate only what is cheap


XLA's basic fusion pass (InstructionFusion, which the CPU subclasses as CpuInstructionFusion) walks the program from its outputs back to its inputs. For each instruction (the consumer) and each of its operands (the producer) it asks one question, ShouldFuse(consumer, operand_index); a yes pulls the producer's computation inside the consumer's kernel. If the producer has other users it now runs twice, once inside the fusion and once for the others, and XLA accepts that only for cheap operations, decided by a fixed list in InstructionFusion::IsExpensive (instruction_fusion.cc:80): add, multiply, select, broadcast, transpose are cheap; exp, dot, convolution, collectives and custom calls are expensive read in source.

Fusion kinds


Every fusion carries a kind, a hint for code generation that each backend uses differently: kLoop (one loop over the output's elements: elementwise chains, broadcasts, on CPU even reductions), kInput (built around a reduction, transpose, concatenate or scatter), kOutput (work fused after an operation such as a matmul) and kCustom (backend-specific: here the YNNPACK library; on GPU, Triton and cuDNN). The train step's  fusions are  kLoop and  kCustom measured here.

On GPU and TPU


XLA:GPU replaces the fixed rules with PriorityFusion (fusion_pipeline.cc:79), which estimates each candidate's run time with a cost model of the device and fuses the most profitable first, followed by MultiOutputFusion (:89), which lets one kernel produce several outputs (two reductions that read the same input, done in one pass over it). 5. Layouts and tiling


An array's layout is the order in which its dimensions sit in memory, written minor-to-major: f32[4096,128]{1,0} means dimension 1 changes fastest (row-major, PyTorch's contiguous); {0,1} would be column-major. In PyTorch a transpose is a free view with new strides and the kernel that reads it copes. XLA instead gives every array one layout, chosen by the layout-assignment pass so that matmuls and reductions read memory in the order they want; each transpose then either disappears into the instruction that reads it or becomes a real copy.


Three transposes and reshapes, compiled: a copy, nothing, and a free bitcast measured here




Entry computations of the optimised HLO, metadata removed (src/lab/buffer_lab.py). A transpose alone is a physical copy (transpose_copy_fusion). Fed into a matmul it vanishes: transpose-folding rewrites the dot to contract over dimension 0 instead, because, in its header's words, the dot "is implemented by a GEMM kernel that can transpose its inputs". A reshape that does not change memory order becomes a bitcast, a free reinterpretation, inside the fusion.


In the train step, layout assignment added  copies, and reshape-decomposer ("Postcondition: All reshapes are turned into bitcasts") turned  reshapes into bitcasts or a bitcast plus copy (see the Pass diff viewer).


Tiling, on TPU. A TPU layout also cuts the array into fixed tiles because, in XLA's words, "XLA TPU uses a variety of tile-based formats due to the two-dimensional nature of its vector registers". The docs write F32[3,5]{1,0:T(2,2)} for a 3 x 5 array in 2 x 2 tiles, padded to whole tiles, and state that bf16 on TPU uses (8,128)(2,1): tiles of 8 x 128 elements, with pairs of rows interleaved inside (docs/tiled_layout.md at the pinned commit) Google docs. The cost is padding.


Padding to whole 8 x 128 tiles: a minor dimension just past a multiple of 128 nearly doubles the bytes

6. Buffer assignment: every byte planned before the step runs


PyTorch allocates as it goes, from a caching allocator, and you learn the peak afterwards (torch.cuda.max_memory_allocated()). XLA plans memory ahead: after the passes it fixes an order of execution (the schedule), gives every value a live range (from the instruction that defines it to the last one that reads it), and packs values whose ranges do not overlap into the same bytes. The result is the buffer assignment; compiled.memory_analysis() summarises it, and the dump writes it out in full.




Bytes live at each point of the train step's schedule: the peak sits where forward turns into backward










Reconstructed from XLA's own dump measured here: the schedule ( positions) and every value's live range from *-live-range.txt, sizes from *-buffer-assignment.txt. Phase bands come from the operation names: jvp is the forward pass, transpose(jvp) the backward pass, the rest the optimiser and gradient norms.




The forward pass piles up activations the backward pass will need, the peak sits at the turn, and the backward pass frees them as it consumes them. XLA attributes the bytes live at the peak to the JAX operation that produced them measured here:

Aliasing and in-place updates


Donation (jax.jit(step, donate_argnums=(0, 1)), shown in the root's Compiler lab) lets an output reuse an input's buffer. Without it XLA must keep the input intact, and a pass makes sure it does. Checked on a  MiB array with x.at[i].set(v) measured here:




Correction
An old note on this knowledge base said that under jit "XLA turns these [x.at[i].set(v)] into true in-place updates, so no copy cost in practice". The update is in place only when the array is donated or is an intermediate inside the jitted function. Updating a non-donated argument copies the whole array first, because copy-insertion must keep "Entry parameter[s] ... live out of the entry computation" in their own allocation (copy_insertion.h:41) read in source. 7. Rematerialisation: yours and the compiler's


Two different mechanisms share the name, and they differ in who decides and what failure looks like:


jax.checkpoint (alias jax.remat)XLA's HloRematerialization pass


Who decidesyou, at trace time, with a policy such as dots_saveable (measured on this model in the root's Compiler lab)the compiler, after scheduling


When it actsalways: what is not saved is recomputed in the backward passonly when the planned peak exceeds the device's memory limit


Whereevery backendthe GPU pipeline (gpu_compiler.cc:3378); absent from the CPU pipeline, so no dump here shows it; the TPU equivalent is inside libtpu read in source


What you seea known slowdown you chosea model that barely does not fit may not fail: the step just gets slower, with no error




How to check. compiled.memory_analysis() against the device's memory, and a dump filtered to the pass (--xla_dump_hlo_pass_re=rematerialization). The fix you control is the explicit one: choose what jax.checkpoint saves, so the compiler has nothing left to guess. The two meet at one point: jax.checkpoint lowers its recomputation behind an optimization_barrier so that XLA's CSE (section 3) cannot merge the recomputed values back into the forward pass and undo the saving (ad_checkpoint.py:867 at jax-v0.11.2, quoted in the root's lab).


The pass's algorithms and strategies


Its header names two algorithms, kAlwaysRemat ("Rematerializes anything it can at any point the HLO is above the memory limit. Default rematerialization algorithm.") and kPeakPriority ("Prioritize rematerializing the highest peak ... Much slower than the default algorithm"), and three strategies a mode can enable: recompute, compress (keep a value in a more compact shape that the backend supplies through a CompactShapeFunction) and host offload (move it to host memory and back) (hlo_rematerialization.h:78-96) read in source.







8. The caches: paying for compilation once


Two caches in front of the compiler: a call misses only if its key is new to both




The in-memory key as the recompile scenarios exercise it (section 10); the persistent key's eight ingredients from cache_key.py at jax-v0.11.2 read in source. The 1 s threshold is jax_persistent_cache_min_compile_time_secs's default.


In memory. A jitted function keeps a cache keyed on everything that can change the program: the function object itself, the abstract signature of its arguments (shapes, dtypes, weak types, the pytree structure), the values of static arguments, and the tracing context (configuration that affects tracing, such as jax_default_matmul_precision). A hit skips tracing, lowering and compiling; a miss does all three, and in every scenario of the Recompile detective, counted through jax.monitoring, the three counts move together measured here. This cache dies with the process; f._cache_size() reports how many entries a jitted function holds.


On disk. The persistent compilation cache stores executables between processes:

Its key is a SHA-256 over eight ingredients, hashed in order in cache_key.py (the entries list at line ): . The XLA flags are hashed after removing flags that cannot change the program, among them --xla_dump_to and --xla_force_host_platform_device_count. So upgrading jaxlib or the device plugin, adding a flag, or any code change that alters the module (donation included) misses. Hits, misses, files and changed ingredients are deterministic; CPU seconds are rough. One entry is  KB; a hit costs  s of CPU against  s for a compile.


When it matters. On a TPU pod every host compiles the same program at start-up, for minutes on large models; the JAX docs recommend a cache "in a shared file system (eg: NFS) or remote storage" for multi-node jobs, and describe a Cloud Storage bucket for it. The same docs warn: "The compilation cache is considered trusted. ... Sharing a compilation cache is equivalent to allowing anyone who can write to the cache directory to run code on your machine" (docs/persistent_compilation_cache.md) Google docs. Keep it per user, or read-only for everyone but a trusted job.







9. Ahead of time: stages, serialized executables and jax.export


Stages. jax.jit(f) hides stages you can call one at a time: .trace(*args) gives a Traced (the jaxpr), .lower() a Lowered (StableHLO), .compile() a Compiled (an executable you call directly). Arguments can be real arrays or jax.ShapeDtypeStruct placeholders, so a program can be compiled before any data exists. A Compiled object never retraces; called with a different shape it refuses (compile one per shape bucket, or call the jit function instead) measured here:




Serialized executables. jax.experimental.serialize_executable.serialize(compiled) turns the compiled CPU executable of the forward pass into  KB; in a fresh process deserialize_and_load brings it back in  s of CPU and it returns the same logits (difference 0.0) measured here. The bytes are machine code for this backend and this jaxlib: a cache you manage yourself, not a format to ship.


jax.export: the format to ship. jax.export.export(jax.jit(f), platforms=...)(*args) returns an Exported: the StableHLO module plus everything needed to call it later (input and output types, shardings, the platforms, and a calling convention version that fixes how arguments are passed;  here, the current one). .serialize() gives bytes; jax.export.deserialize(...).call(...) compiles and runs them, in another process or years later. 10. Recompiles: causes, evidence and the fix


Anything in the in-memory cache key (section 8) that changes between calls costs a full trace, lower and compile: for the train step, seconds; for a large model on TPU, minutes. Usually nothing fails; the step just gets slow. JAX can explain every miss: with jax.config.update("jax_explain_cache_misses", True) each one logs a warning that names the argument and what changed. The common causes, with JAX's own words from the Recompile detective (eleven scenarios):


    

  • Shapes that vary: the last, smaller batch of an epoch; variable sequence lengths. "different input types: * at x, now f32[31,128] and before f32[32,128]".
    • 

  • Weak types: a Python 2.0 is weakly typed, a np.float32(2.0) is not: "now f32[]{weak_type=False} and before f32[]{weak_type=True}".
    • 

  • Static arguments: every new value of a static_argnums argument is a new program (JAX's explanation here is only "cache miss explanation unavailable"), and the value must be hashable (a list raises; pass a tuple).
    • 

  • A new function object: jax.jit(lambda ...) created inside a loop never hits ("never seen function ... maybe the function is being re-defined repeatedly"): 3 calls, 3 compilations. Wrapping the same named function again is fine.
    • 

  • Configuration: changing jax_default_matmul_precision between calls: "Tracing context doesn't match".
    • 

  • And its opposite: a Python global read inside the function is baked in at trace time; changing it later neither recompiles nor takes effect (the detective prints [2. 2.] twice). Pass it as an argument.
    • 





A recompilation storm: 64 compilations for 64 prefix lengths, 4 with buckets


A decoding-style loop calls a jitted attention-like function on a prefix that grows from 1 to 64 positions. Exact shapes compile once per length; padding each length up to a multiple of 16 (and masking) needs four programs. Same inputs, same outputs; compile counts are deterministic, seconds are measured here (the second of three repeats is drawn; compile time in the counters is the median of the three).














At scale, count compilations instead of reading logs. jax.monitoring.register_event_duration_secs_listener receives an event for every trace (/jax/core/compile/jaxpr_trace_duration), lowering and backend compile (/jax/core/compile/backend_compile_duration), the same hooks the detective uses; export them to your metrics system and alert when the count grows after warm-up. jax_log_compiles prints one line per stage (sample below).


What jax_log_compiles printed for the storm's first calls


The fixes, in the order to try them: make the shapes static (pad and mask to a few buckets, drop or pad the last batch); keep Python scalars out of the signature or make their types consistent; hoist jax.jit out of loops and keep one jitted function per role; pass configuration as static arguments deliberately, not by accident; and warm up every bucket before timing. When shapes must vary at run time and padding wastes too much, export with symbolic shapes (section 9) or let the serving framework bucket for you.

12. XLA flags that matter, and their risks


XLA reads XLA_FLAGS once, when the backend starts: "Set XLA_FLAGS before importing Jax or other relevant libraries. Changing XLA_FLAGS after backend initialization will have no effect" (docs/xla_flags.md) Google docs; set inside a running script, they fail silently, so set them in the shell or in os.environ before import jax. Every flag is a field of DebugOptions, defined with its default and help text in xla/debug_options_flags.cc read in source (the flags this page uses, with their help text, are in the closed block below). Five CPU settings on the train step measured here, each in a fresh process; losses are the first five steps from the same initial state:




CPU seconds on a shared machine (1-minute load printed per row): read ratios, not values. --xla_backend_optimization_level=0 roughly halves compile time and more than doubles step time; numbers stay identical, and the optimised HLO is the same ( kernels,  fusions, checked with the flag on): the level steers the backend's code generation, not the HLO passes. Fast math changed nothing measurable on this program.


On TPU, flags go in LIBTPU_INIT_ARGS and are read by the closed compiler. MaxText keeps a library of them: a scoped VMEM limit of 98304 KiB for dense models, flags that fuse and overlap collectives with compute, and data-parallel overlap (benchmarks/xla_flags_library.py at the pinned commit) read in source not run here.


Risks
Flags are debug options, not an API: names change between releases and help text goes stale (the YNNPACK flag's help contradicts its default, section 4). Some change numbers (fast math, disabling passes). Disabling a pass can make compilation fail or the program slow in ways that only show at scale. Every flag that is not on JAX's exclusion list is part of the persistent cache key (section 8), so a new flag recompiles everything. Keep production flags in one place, record them with each run, and re-measure after every JAX upgrade.

Interview rehearsal: two questions that add a design angle (optional)


Why does XLA not fuse everything into one kernel? Fusing a producer with several users duplicates its work, which XLA accepts only for cheap operations; matmuls and (on this CPU) many reductions go to libraries; loops, sorts, custom calls and host callbacks are walls; and backends cap fusion size (five reductions per fusion on CPU, concatenations of more than eight operands) to keep compile time and code quality reasonable. On GPU a cost model decides which fusions pay.


Design: serve a JAX model on TPU for requests of any length up to 8,192 tokens, with predictable latency. Fix a small set of shape buckets (for example powers of two in length, and a few batch sizes), pad and mask into them, and AOT-compile every bucket at start-up with jax.ShapeDtypeStruct placeholders so no request ever compiles; count compilations through jax.monitoring and alert on any after warm-up. Share a read-only persistent cache among replicas built by a trusted job, keyed by the exact jaxlib and libtpu versions. The trade-off is padding waste against the number of programs: with power-of-two buckets the expected waste is up to half of each request's length in the worst case, so add intermediate buckets where traffic concentrates. If the model must also run elsewhere, ship it as a multi-platform jax.export. Measure with a profile per bucket: decode steps are memory-bound, so small batches waste the MXU and the batch buckets matter as much as the length buckets.
