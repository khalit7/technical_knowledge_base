1. Why write a kernel at all, and when not to

The problem. In PyTorch you reach for a custom CUDA or Triton kernel when the framework's kernels move too much memory. In JAX the compiler, XLA, already writes most kernels for you and fuses chains of elementwise work into one pass (how it decides, and the softmax compiled three ways, are on {{XLA and compilation, section 4|n:3fa5c17b0d0d8135adcedefac9e1bb48}}). What a compiler cannot do is change the algorithm. Four kinds of work need one:

  • Store less than the maths suggests. Attention written as softmax(q kT) v materialises a T × T score matrix in memory (HBM, the chip's large and slow memory). Flash attention computes the same result one tile at a time and never stores it. For the running example's layer 0 that matrix is 8.4 MB of float32 (32 sequences × 4 heads × 128 × 128), and the backward of the plain version keeps the probabilities of the same size as a residual; the flash backward keeps one number per row instead, 66 KB measured here. For a 7B-class model at 8,192 tokens with 32 heads, the scores are 32 × 8,1922 × 2 bytes = 4.3 GB per sequence per layer in bf16 derived.
  • Data-dependent tiles. Serving keeps the KV cache in fixed-size pages scattered through memory; mixture-of-experts sends a different number of tokens to each expert. The tile a step needs depends on a table that only exists at run time (section 7).
  • Skip work that is known to be zero. Causal or block-sparse attention masks whole tiles; a kernel can skip computing them and even skip copying them (sections 5 and 7).
  • Overlap communication with compute by hand, for example a matmul that pulls the next shard from a neighbouring chip while multiplying the current one (Pallas TPU kernels can copy between chips with pltpu.make_async_remote_copy; not run here: it needs several chips).

When not to. Google's own Pallas TPU matmul guide measured, on a TPU v5e, a plain Pallas matmul against jnp.matmul (XLA). The best Pallas block size reached the compiler; small blocks were 15 times worse. Published outputs committed with the guide at jax-v0.11.2 Google, published:

Share of v5e bf16 peak reached by a square bf16 matmul (N × N × N)

Source: docs/pallas/tpu/matmul.ipynb cell outputs at jax-v0.11.2 (the guide states "This notebook was run on a TPU v5e chip"; run date not stated). Utilisation = 2N3 / time / 197 TFLOP/s, as the guide computes it. Blocks are (bm, bk, bn).

The same guide's sparse chapter, on the same kind of chip, is the counter-example: a block-sparse × dense matmul (16,384 square, blocks of 512) took 8.136 ms against 46.953 ms for the dense XLA reference Google, published, because the kernel never touches the zero blocks. That is the general rule: a kernel wins by doing less, not by doing the same thing better than the compiler.

Predict: for which of these would you expect a hand-written Pallas kernel to beat XLA on a TPU by a wide margin?
Attention with a block-sparse mask: the kernel skips whole tiles of work and memory traffic that XLA's dense attention must do. The matmul is XLA's best case (the guide's 92.3% against 91.5%). LayerNorm and bias-plus-GELU are memory-bound elementwise chains that XLA already fuses into one pass; a kernel can at most match it (section 3 shows the kernels anyway, because they teach the mechanics).

2. The programming model, precisely

Backends. The same pallas_call lowers per platform: on TPU to a tpu_custom_call holding a Mosaic module (an MLIR dialect that libtpu compiles); on cuda and rocm to Triton unless you pass Mosaic GPU's compiler parameters (pallas_call.py:922: with no compiler_params it constructs Triton's). What the two lowerings show is the core difference between the backends. In Mosaic the refs arrive as memref<512x128xf32, #tpu.memory_space<vmem>>: the copy from HBM already happened, decided by the BlockSpec, and the body is vector.load, two vector.multi_reductions and a tpu.vector_store. In Triton the refs arrive as raw pointers (!tt.ptr<f32>), and the lowering builds a 16 × 128 tensor of addresses (tt.make_range, tt.addptr) before tt.load: the BlockSpec became pointer arithmetic, which is what a Triton programmer writes by hand. Triton functions and their tuning are on {{Triton and Gluon|n:3c65c17b0d0d81729d15ed4d1a4461b3}}.


Transformations. A pallas_call sits inside jax.jit like any primitive. jax.vmap of it adds a leading grid axis (the design note's rule, docs/pallas/design/design.md:542): the softmax kernel vmapped over 4 score matrices of 1,024 rows became one call with grid (4, 2) and matched to 1.5e-8 measured here (jax's own GPU LayerNorm is written this way, one row per program, then vmapped). jax.grad needs a custom_vjp (section 4). Inside shard_map a kernel sees each device's shard; the sharding pages own that.
