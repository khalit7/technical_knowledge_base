1. When a kernel wins, and when it cannot

In PyTorch you reach for a Triton or CUDA kernel when the framework's kernels move too much memory. In JAX the compiler, XLA, already writes most kernels and fuses chains of elementwise work into one pass ({{XLA and compilation, section 4|n:3fa5c17b0d0d8135adcedefac9e1bb48}}). What a compiler cannot do is change the algorithm. Four kinds of work need one:

  • Store less than the maths suggests. softmax(q kT) v materialises a T × T score matrix in HBM, the chip's large and slow memory; flash attention computes the same result tile by tile and never stores it. For the running example's layer 0 that matrix is 8.4 MB of float32 (32 sequences × 4 heads × 128 × 128), and the plain backward keeps probabilities of the same size; the flash backward keeps one number per row, 66 KB measured here. For a 7B-class model at 8,192 tokens with 32 heads, the scores are 32 × 8,1922 × 2 bytes = 4.3 GB per sequence per layer in bf16 derived.
  • Data-dependent tiles. Serving keeps the KV cache in pages scattered through memory; mixture-of-experts sends a different number of tokens to each expert. The tile a step needs depends on a table that exists only at run time (section 7).
  • Skip work known to be zero. Causal or block-sparse masks empty whole tiles; a kernel skips computing them and even copying them (sections 2 and 5).
  • Overlap communication with compute by hand, for example a matmul that pulls the next shard from a neighbouring chip while multiplying the current one (pltpu.make_async_remote_copy; not run here: it needs several chips).

When not to. Google's Pallas TPU matmul guide measured a plain Pallas matmul against jnp.matmul (XLA) on a TPU v5e: the best block size only reached the compiler, and small blocks were 15 times worse Google, published:

Utilisation = 2N3 / time / 197 TFLOP/s, as the guide computes it. Blocks are (bm, bk, bn); at 8,192 the guide's best is 91.5% against XLA's 92.3%, and 128-cubed blocks reach 6.1%.

The same guide's sparse chapter is the counter-example: a block-sparse × dense matmul (16,384 square, blocks of 512) took 8.136 ms against 46.953 ms for the dense XLA reference Google, published, because the kernel never touches the zero blocks. A kernel wins by doing less, not by doing the same thing better than the compiler.

Predict: for which of these would you expect a hand-written Pallas kernel to beat XLA on a TPU by a wide margin?
Attention with a block-sparse mask: the kernel skips whole tiles of work and memory traffic that XLA's dense attention must do. The matmul is XLA's best case (92.3% against 91.5%). LayerNorm and bias-plus-GELU are memory-bound elementwise chains that XLA already fuses into one pass; a kernel can at most match it (section 3 shows them anyway, because they teach the mechanics).

2. The model: one call, a grid and BlockSpecs

Everything is one call, pl.pallas_call(kernel, out_shape, *, grid, in_specs, out_specs, scratch_shapes, input_output_aliases, compiler_params, interpret, ...) (pallas_call.py:1091 at jax-v0.11.2 read in source), which returns a function you call on arrays inside jax.jit. The bias + GELU kernel of the hero, in full:

pl.pallas_call(bias_gelu_kernel,
    out_shape=jax.ShapeDtypeStruct((4096, 512), x.dtype),
    grid=(8,),                                              # 8 steps of 512 rows
    in_specs=[pl.BlockSpec((512, 512), lambda i: (i, 0)),   # x: block (i, 0) at step i
              pl.BlockSpec((1, 512),   lambda i: (0, 0))],  # b: the same block every step
    out_specs=pl.BlockSpec((512, 512), lambda i: (i, 0)),
    compiler_params=pltpu.CompilerParams(dimension_semantics=("parallel",)))(x, b)
Condensed from src/runs/pk_kernels.py (the bias_gelu section, shown in full in section 3), with the running example's shapes filled in.

The one rule that explains every copy. Before each step Pallas evaluates every index map; it copies an input block only when its block index differs from the one the previous step used, and writes an output block back when its index changes (or at the end). An index map returns block coordinates, not element offsets. So x and o move 8 times and b once. Step any kernel on this page through its grid:

Try: Bias + GELU to the last step (x 8 copies, b 1, o 8). Then Flash fwd with "Before: naive index map" against "After: clamped": the same 16 steps and the same 10 computed tiles, but K and V are copied 16 times against 9 (section 5). LayerNorm bwd: dscale and dbias are copied once and written back once, the reason its axis must be "arbitrary" (section 4). Paged decode: the page index jumps around the pool (section 7).
How the lab is drawn and where its numbers come from

The index maps are the kernels' own, evaluated in src/runs/pk_grid.py; the body conditions are their pl.when tests. Each operand is drawn to its own scale (the arrays range from 8 × 32 to 16,384 × 128), with its block grid; an operand that is a single tall column of more than 8 blocks is drawn wrapped, its blocks numbered in order; three-dimensional operands are drawn as the two dimensions a block covers (flash: one head; paged: the pool as 40 pages of 16 tokens). Bytes count bf16 for activations and weights and float32 for statistics and fp32 outputs, the dtypes a TPU kernel would use. "Minimum" is every element read or written once. The recorded orders come from pltpu.InterpretParams(grid_point_recorder=...) on the real kernels; with "parallel" axes the interpreter shuffles them on purpose, even on one core, and a copy count in that order is computed here from the recorded order, per core.

Transformations. A pallas_call sits inside jax.jit like any primitive. jax.vmap of it adds a leading grid axis (docs/pallas/design/design.md:542): the softmax kernel vmapped over 4 score matrices of 1,024 rows became one call with grid (4, 2) and matched to 1.5e-8 measured here (jax's own GPU LayerNorm is written this way, one row per program, then vmapped). jax.grad needs a custom_vjp (section 4).
