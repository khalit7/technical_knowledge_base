3. Row kernels: elementwise, softmax, cross-entropy

The simplest useful kernels cut an array into bands of rows and process each band alone: a one-dimensional grid, one BlockSpec per operand, the axis "parallel". Three of them, each on a real tensor of the running example, code exactly as it ran (src/runs/pk_kernels.py):





Bias + GELU on layer 0's MLP pre-activation (layer 0 MLP pre-activation x W1 [4,096 x 512] and bias b1 [512]) matches jax.nn.gelu(x + b, approximate=False) to 7.5e-8 and the model's own hidden activations to the same measured here. The bias is the trivial window of the hero: the TPU lowering marks it #tpu.pipeline_mode<synchronous>, single-buffered ("Force single-buffering pipelining for trivial windowing in VMEM", mosaic/lowering.py:1220), a trivial window being a block equal to the whole array with an index map of zeros. jax.lax.erf lowers to Mosaic's math.erf, so the exact GELU the model uses costs nothing extra; the tanh approximation (JAX's default) would differ by 1.9e-4 here, a porting trap.


Fused softmax on the scaled, causally masked attention scores of all 128 heads (layer 0 attention scores, scaled and causally masked, all 128 heads [16,384 x 128]): whole rows fit in a 512 × 128 block, so the max, the exponentials and the sum stay in VMEM and each element is read once and written once. Error 6.0e-8, row sums within 2.4e-7 of 1. 49.6% of the entries are -inf and come out as exact zeros, which works only because every row keeps its diagonal: a row with every entry masked computes -inf - (-inf) and returns NaN (tried here: that row came out all NaN, yes, the other 511 rows untouched; decoding at length 0 is the usual way to hit it). That is why the flash and paged kernels skip empty tiles with pl.when.


Fused cross-entropy on the whole model's logits at initialisation (logits of the whole model at initialisation, batch 0 [4,096 x 65], with the targets): each row's loss is its logsumexp minus the target's logit, picked with broadcasted_iota and a compare instead of a gather; the softmax is never stored. Mean 4.21168, identical to the model's loss_fn (difference 0), close to ln 65 = 4.174 as an untrained model should be. The 512 × 65 block is legal only because 65 is the whole row (the root lab showed the (8, 128) rule rejecting a 100-row block). Legal is not free: VMEM is laid out in rows of 128 lanes, so each 65-wide row occupies 128 lanes and 49% of the vector work and memory is padding derived. The production flash attention kernel pays the same on purpose: it stores its running max and sum 128 lanes wide, one value repeated (flash_attention.py:675; why, in the depth block at the end).


Precision: bf16 inputs, and an output dtype that rounds the accumulator


With bf16 inputs the softmax kernel (which upcasts to float32 inside) is off the float32 answer by 2.0e-3; XLA's jax.nn.softmax on the same bf16 input by 3.6e-3 measured here: inside a kernel the precision of the arithmetic is yours to choose.


The old version of this page showed a matmul kernel with out_shape in the input dtype and x_ref[...] @ y_ref[...]. It is correct, but with bf16 inputs the result is stored in bf16: off the float32 answer by 9.0e-4 against 7.1e-4 with a float32 output (preferred_element_type=jnp.float32), measured here. 4. LayerNorm, forward and backward, joined by custom_vjp


The problem. A pallas_call is opaque to reverse-mode autodiff. Measured here: jax.grad through the softmax kernel fails with ValueError: Linearization failed to produce known values for all output primals. This is typically caused by attempting to differentiate a function uses an operation that does not support reverse-mode autodiff., and through the flash kernel (scratch buffers, pl.when) with a bare AssertionError; forward mode (jax.jvp) of the softmax kernel works. The Pallas design note explains why: transposing a kernel turns parallel reads into overlapping writes ("slow when done atomically"), and it names jax.custom_vjp "a viable escape hatch" (docs/pallas/design/design.md:553). So every training kernel is a pair, forward and backward, joined by jax.custom_vjp ({{JAX core, section 6|n:3c65c17b0d0d81b7a0d1faba6cef5561}}); PyTorch's counterpart is a torch.autograd.Function.


The code: forward kernel, backward kernel and the custom_vjp that joins them, as they ran


src/runs/pk_kernels.py, the layer_norm section, as it ran.


How it works. The forward normalises a band of 256 rows and also writes two numbers per row, the mean and 1/√(var + ε). The backward recomputes x̂ = (x − μ) · rstd from them instead of storing x̂, so the saved state is x plus 2,130,432 bytes in all for this input, of which only 32 KB are statistics. The backward has two kinds of output: dx is per row, like the forward; dscale and dbias are sums over all 4,096 rows, so their BlockSpec maps every step to the same (1, 128) block, which stays in VMEM: the kernel zeroes it at step 0, adds each band's contribution, and Pallas writes it back once at the end (step "LayerNorm bwd" in section 2's lab).


Evidence. On layer 0's input with the trained LayerNorm (scale between 0.935 and 1.037 after the 500-step run), the forward matches the model's layer_norm to 2.4e-7, and the gradients agree with jax.vjp of it to a relative 1.1e-7 (dx), 1.7e-7 (dscale) and 1.0e-7 (dbias) measured here: float32 rounding.


The accumulation forces "arbitrary", and the plain interpreter will not tell you


Mark the backward's row axis "parallel" and a megacore chip may split the rows between its two cores, each accumulating into its own copy of the shared block. The plain interpreter ignores dimension semantics and returns the right answer (error 3.1e-5 on values up to 176, rounding). The TPU interpreter with two simulated cores, three seeds:  measured here. With "arbitrary" the same two-core run is right again (3.1e-5).


On a GPU the decomposition changes. GPU programs run at the same time, so they cannot accumulate into one block. The Triton-style LayerNorm that ships with jax (deprecated in favour of tokamax, section 10) computes dscale and dbias in a second kernel, layer_norm_backward_kernel_dw_db (ops/gpu/layer_norm.py:192), one program per block of columns looping over all rows with masked loads. Same maths, a different decomposition, forced by the grid semantics.
