5. Flash attention: the forward with its residual, and the backward

The root's lab ran the causal flash attention forward and showed it matching the model. A training kernel needs three more things: the forward must save something for the backward, the backward must exist, and the two must be joined by custom_vjp. All three are below, checked against plain attention and against the two production kernels that ship with jax, on the same tensors (layer 0 q, k, v of all 32 sequences x 4 heads [128 x 128 x 32]; upstream gradient N(0, 1), key 1).

mnew = max(m, rowmax Sj), α = em − mnew, l ← α l + rowsum eSj − mnew, acc ← α acc + eSj − mnew Vj
Sj

m, l, acc

α
rescales everything accumulated so far when the row max grows; the output is acc / l after the last block, and the saved residual is the logsumexp L = m + log l

The {{Flash tiles|#t-pktile}} tab replays this loop on one query block of a trained layer, step by step, against the naive softmax and against the same loop with α left out. The paper itself, with an HBM against on-chip animation of both loop orders on random input, is the {{FlashAttention paper page|n:3c65c17b0d0d81e4a3e8e7a2c4771381}}; the GPU schedules (FlashAttention-2's split of queries across warps, atomics in its backward, Flash-Decoding) are on {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}}. The forward here is the root's kernel plus one output, lse; with it the output matches the root kernel exactly (difference 0) and the logsumexp matches jax.nn.logsumexp of the scores to 9.5e-7.

The backward, from the softmax derivative. With P = eS − L recomputed tile by tile from the saved L, and D = rowsum(dO ∘ O) computed once outside the kernels:

dV = PT dO, dP = dO VT, dS = P ∘ (dP − D), dK = dST Q / √dh, dQ = dS K / √dh
D
rowsum(dO ∘ O): the term the softmax Jacobian subtracts; the production kernel calls it di
∘
elementwise product

dK and dV sum over query blocks; dQ sums over key blocks. A grid step may only accumulate into an output block it owns, so the backward is two kernels: the first walks one key block past every query block (grid: head, key block, query block), the second one query block past every key block. The production TPU kernel splits it the same way, _flash_attention_dkv_kernel then _flash_attention_dq_kernel (flash_attention.py:796 and :1146). Both recompute P, the price of not storing it: about one extra QKT matmul per kernel.

Skipping, and not even copying. With causal masking the tiles above the diagonal are all -inf. The kernels skip their arithmetic with pl.when, but a BlockSpec would still copy K and V for them. The forward's K and V index map therefore re-uses the last block the query block needs, min(j, last); an unchanged block index means no copy. 6. Pipelining: what a BlockSpec does for you, written by hand


The problem. A TensorCore computes only on data in VMEM; the arrays live in HBM. Copying a tile in, computing, and copying the result out, one after the other, leaves the matrix unit idle during every copy. Every BlockSpec kernel on this page is pipelined automatically: while step s computes, Pallas's generated code is already copying the blocks step s+1 needs into a second buffer (double buffering), and writes each output block back once it is final. The default is two buffers per operand ("The default buffer count is 2 for all inputs and outputs", the Pallas TPU pipelining guide, docs/pallas/tpu/pipelining.md:140).

The two cases show the two regimes. The running example's matmul moves more bytes than it computes, so even perfectly overlapped it takes as long as its copies (9.05 µs against 8.96 µs of copies); the 7B-class matmul with 512 × 1,024 × 1,024 blocks computes longer than it copies, and overlap hides almost every copy (73.7 µs against 119.2 serial for the first 12 steps). Overlap can only bring the time down to the larger of the two lanes; block sizes decide which lane that is (section 11).

The pallas_call lowering accepts one or two buffers only ("Only single (1) and double (2) buffering are supported", mosaic/lowering.py:1277); deeper buffering and lookahead prefetch are emit_pipeline features. One buffer saves VMEM and gives up the overlap: use it for blocks that never change. VMEM is calculated: buffers × block bytes.


The bug the TPU interpreter exists for
Move the .wait() to after the matmul that uses the slot. In the plain interpreter a DMA completes the moment it starts, so the result is still exact (error 0). On a TPU the matmul would read a half-copied buffer. The TPU interpreter executes DMAs only when the kernel waits on their semaphore (dma_execution_mode="on_wait", the default, interpret/params.py:178) and fills fresh buffers with NaN, so 1,024 of the 4,096 output rows came out NaN measured here.
