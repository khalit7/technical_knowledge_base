The idea in one screen

Pallas is JAX's kernel language: you write one Python function that works on tiles in VMEM, the TPU core's fast on-chip memory, and a grid (a loop) plus one BlockSpec per array decide which tile of each array is copied in at every step, with the copies overlapped behind the compute. You write one only when the win comes from doing less than the compiler (XLA) can derive: not storing an intermediate, choosing tiles from data, or skipping known-zero work.

One grid step: the BlockSpec has copied block i into VMEM, block i+1 is already on its way, the bias was copied once

The bias + GELU kernel of section 3 on the running example's MLP pre-activation x [4,096 × 512]: grid=(8,), one 512-row band per step. x and o move band by band (8 copies in, 8 write-backs); the bias's index map always returns block (0, 0), so it is copied once and given a single buffer. On a TPU core the 8 steps run one after another; on a GPU they would be 8 parallel programs. Section 2 steps through this and nine other grids.

You need: jax.jit and jax.custom_vjp ({{JAX core|n:3c65c17b0d0d81b7a0d1faba6cef5561}}, section 6 for custom rules); what VMEM, HBM and the MXU are and how big they are per generation ({{TPU programming and performance|n:3c65c17b0d0d8129b0a5fd82e44ecf6e}}); the five ideas of Pallas, its tiled matmul and the (8, 128) block rule, from the root's {{TPU and Pallas lab|n:3c65c17b0d0d81ecbc04eea6aa45ea1a}}. Ref
a mutable view of one tile in fast memory; the kernel reads x_ref[...] and writes o_ref[...] = ....
Grid
the loop nest the kernel body runs in; sequential on one TPU core, parallel programs on a GPU.
BlockSpec
for one array: the tile shape and an index map from grid indices to the tile's block index.
VMEM, SMEM, HBM
the core's vector memory (tiles), its small scalar memory (indices), and the chip's large slow memory (whole arrays).
Mosaic
the compiler that turns a Pallas kernel into TPU code; on GPUs Pallas lowers to Triton or Mosaic GPU.
Dimension semantics
"parallel" or "arbitrary" per grid axis: whether the axis may be split between cores.
Scalar prefetch
small integer arrays copied to SMEM before the grid starts, so index maps can choose tiles from data.
Interpret mode
running the kernel as ordinary JAX on a CPU (interpret=True), or under the TPU interpreter, which simulates copies and cores.
The four things to take away
  • Write a kernel only for what XLA cannot derive: an algorithm that changes what is stored (flash attention never writes the T × T scores), data-dependent tiles (paged and ragged attention, mixture-of-experts), or block sparsity. For a matmul, Google's own guide shows the best Pallas kernel only matching XLA (section 1).
  • The grid is a sequential loop on a TPU, so a block that several steps share stays in VMEM and can accumulate (sections 4 and 8). On a GPU the same grid is parallel programs, which is why the GPU kernels split such reductions into a second kernel.
  • Gradients are yours to write: jax.grad of a pallas_call fails; wrap forward and backward kernels in jax.custom_vjp (sections 4 and 5).
  • Interpret mode proves correctness, not speed or legality: test with the TPU interpreter and lower for TPU on your laptop before paying for a chip (section 9).
