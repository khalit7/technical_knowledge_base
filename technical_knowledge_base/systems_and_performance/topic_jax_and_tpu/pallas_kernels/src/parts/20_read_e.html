7. Scalar prefetch: tiles chosen by data

The problem. An index map is a traced function of the grid indices, run before each step to decide which block to copy. Serving needs more: each sequence's KV cache lives in fixed-size pages scattered through a shared pool, and which physical page holds tokens 32 to 47 of sequence 3 is in a page table known only at run time (why pages: the {{PagedAttention paper page|n:3c65c17b0d0d81bf8b90ca93fee19f5f}}). Scalar prefetch solves it: pltpu.PrefetchScalarGridSpec(num_scalar_prefetch=n, ...) (mosaic/core.py:390) copies the first n arguments, small integer arrays, into SMEM before the grid starts and passes them to every index map and to the kernel (as SMEM refs, :407). The BlockSpec still does the copy, so section 6's pipelining still applies. In vLLM's CUDA paged attention the block table is just a kernel argument each thread block reads; in Triton you load the entry and compute the pointer.

The whole trick is the index map, which now also receives the prefetched arrays (from the kernel's code, below):

def page_map(page):
    def f(s, p, table_ref, lens_ref):                            # index maps also receive the prefetched scalars
        last = (lens_ref[s] - 1) // page                         # last page that holds a token
        return (table_ref[s, jnp.minimum(p, last)], 0, 0)        # physical page; clamped, so no copy past the end
    return f
The code: paged decode attention with scalar prefetch, as it ran
src/runs/pk_kernels.py, the paged_decode section: grid (sequence, logical page); the K and V index maps return the table entry for min(page, last page); the kernel masks the tail of the last page and runs the online softmax across pages.


The test. Eight (sequence, head) pairs of the running example decode one token each: query = the q row at position n − 1, keys and values 0 to n − 1, with lengths 37, 128, 64, 90, 1, 17, 113, 70. Their K and V are cut into pages of 16 tokens and scattered over a pool of 40 pages (3 unused) in a shuffled order. Causal attention's row n − 1 sees exactly keys 0 to n − 1, so the kernel's output must equal the model's own attention output at that row: it does, to 3.7e-8, in both interpreters measured here.


The page table sends each logical page to a scattered physical page




Rows: the 8 sequences (n = length); columns: logical pages 0 to 7; each cell is the physical page in the pool (a dash: unused slot). Hover or tap a cell to see its page in the pool. Lengths and the shuffle are those of src/runs/pk_run.py (NumPy seed 0).


The index map also clamps the page index to the sequence's last page, so the steps past the end, which do no work, copy nothing new: 43 K-page copies without the clamp, 37 with it, exactly the 37 pages that hold tokens (step "Paged decode" in section 2's lab).


Stale table entries
Unused table slots must still hold a valid page index. With 9,999 in them and no clamp, the plain interpreter silently clamps the out-of-range block (error 3.7e-8: the step's arithmetic is skipped anyway); the TPU interpreter refuses: Out-of-bounds block index (9999, 0, 0) for input "k_ref" in iteration (0, 3) on device 0 (core 0): reading [(9999, slice(0, 16, 1), slice(0, 32, 1))] but input has shape (40, 16, 32). On a chip that copy would read outside the pool. With −1 in the slots neither interpreter raised measured here, so do not rely on the interpreter for negative indices: fill unused slots with a valid index and clamp in the index map.


What the lowering looks like, and who uses scalar prefetch in production


Lowered for TPU, the table and lengths become memref<8x8xi32, #tpu.memory_space<smem>> and memref<8xi32, ...smem> arguments and the function is tagged scalar_prefetch = 2 : i64; the index maps become transform_ functions that read SMEM with memref.load.


In production (all at jax-v0.11.2, section 10): paged attention passes lengths and page indices this way (paged_attention_kernel.py:640). The megablox grouped matmul for mixture-of-experts prefetches group metadata, which group and which row tile each step works on (gmm.py:530, built by make_group_metadata:79); run here on the running example's MLP rows split into four "experts" of 1000, 0, 2600, 496 rows, one of them empty, it matched per-group matmuls to 2.7e-7. Splash attention precomputes, for every (head, query block, key block), the next key block worth fetching, data_next, and keeps it "in TPU scalar-memory", a "scarse resource" its comment says, shrinking the dtype to int8 or int16 where it can (splash_attention_mask_info.py:32).









8. Dimension semantics, megacore and the order of the grid


Each grid axis is "parallel" (any order is fine, so the axis may be split between cores) or "arbitrary" (must run in order, as an accumulation must). With no dimension_semantics, every axis is arbitrary (mosaic/lowering.py:778). The split matters on megacore chips, v4 and v5p, where two TensorCores appear as one JAX device and share HBM but each has its own VMEM; "Only parallel dimensions can be partitioned over cores" (the Pallas TPU design notes, docs/pallas/tpu/details.rst:180). On TPU7x each core is its own device (the root's TPU lab, from tpu_info.py), and splitting work between them is sharding's job, not the grid's.


The rule: an axis may be "parallel" only if no output block is visited by two different indices along it ("parallel, unless the output window does not vary"). The matmul's K axis, the flash kernels' inner key or query loop, and the LayerNorm backward's row axis (because of dscale) all revisit an output block, so they are "arbitrary"; everything else on this page is "parallel". The root's lab showed a matmul whose K axis was marked parallel going wrong by 0.17 under two simulated cores; section 4 showed the same for an accumulation across rows. Both are invisible to interpret=True.
