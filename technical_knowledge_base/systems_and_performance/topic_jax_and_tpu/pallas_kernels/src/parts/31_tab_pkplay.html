Kernel playground

Every kernel on this page, with its code as it ran, what was measured about it here, what the TPU lowering produced, and a calculator for the one decision you would tune on a chip: the block size, and whether its buffers fit in VMEM.

Try: Flash attention forward at 128 × 128 blocks on v4: the logical bytes fit easily, but the head dimension of 32 is padded to 128 lanes and every one-number-per-row statistic to 128 more, so the padded footprint is about seven times the logical one. Then cross-entropy: the labels block, one int32 per row, takes as much VMEM as the 65-wide logits. Then the root's matmul at 1,024 × 128 × 512 blocks.

Measured values: src/runs/out/kernels.json (interpret mode on Apple M1 Pro CPU, jax 0.11.2). Lowering: jax.export(..., platforms=["tpu"]) for a TPU v5e on this CPU, op counts read from the printed Mosaic module (not compiled). The calculator is arithmetic, not a measurement: buffers × block bytes, two buffers per pipelined operand, one for a block that never moves (the lowering's single-buffering rule), plus scratch; "padded" rounds every block's last two dimensions up to (8, 128) as VMEM tiles do. VMEM per TensorCore by generation is read from jax/_src/tpu_info.py at jax-v0.11.2 (as the root's TPU lab reads it). The compiler also applies a lower default limit per kernel, raised with vmem_limit_bytes and the --xla_tpu_scoped_vmem_limit_kib flag; its default value is not stated in the source read here, so it is not drawn.
