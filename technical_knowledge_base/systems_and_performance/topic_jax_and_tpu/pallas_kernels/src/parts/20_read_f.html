What to copy into your own kernels, from reading them: keep every block size in one frozen dataclass, forward and backward, so they can be swept; save the logsumexp, not the probabilities; clamp index maps for skipped tiles; precompute masks and metadata on the host and pass them by scalar prefetch; write the reference implementation beside the kernel (both flash kernels ship one: mha_reference); and pass every scale explicitly.

11. Choosing block sizes

The cost model. For a matmul tiled (bm, bk, bn), the Pallas TPU guide counts HBM traffic as (m k n / bn + k n m / bm + m n) × bytes per element: A is re-read once per column of blocks, B once per row of blocks (docs/pallas/tpu/matmul.md:341). Its advice: "to be compute bound, make the blocks as big as possible", limited by VMEM and by pipeline bubbles (with few grid steps, the first copy and last write-back are not hidden); and in practice "sweep over a large set of candidate block sizes, profile the kernel, and pick the best one". The root's lab tabulates that traffic for the running example and a 7B-class matmul; the {{Kernel playground|#t-pkplay}} adds the VMEM each of this page's kernels needs at each block size, against each generation's VMEM.

What production does. Three strategies, from the source:

  • One default for everything: the flash attention kernel's 128 everywhere, with its TODO.
  • A checked-in table: ragged paged attention looks its block sizes up in TUNED_BLOCK_SIZES (tuned_block_sizes.py:37), 668 entries for "TPU v5" and 668 for "TPU v6", keyed by dtypes, heads per block, head dimension, page size, batched tokens and maximum model length, each giving (KV pages per block, queries per block). The two generations share every key but disagree on 237 of them: tuned values do not transfer between chips.
  • Search at run time: tokamax's ops declare a search space and tokamax.autotune measures it, for example ragged_dot's row tiles from 128 to 1,024 ("we found that there is no need on current TPU generations to search for larger tiles for m", ops/ragged_dot/pallas_mosaic_tpu.py:453). Its README warns that "autotuning is fundamentally non-deterministic" and that different configs "can lead to different numerics": serialise the result and reuse it.

The tuned table, one slice: best (KV pages per block, queries per block)
