Five rungs, each catching a different class of bug. Every kernel on this page climbed the first four on a laptop:

Tolerances. Compare with numpy.testing.assert_allclose against the jnp reference, with tolerances set by dtype, not by hope. On this page float32 kernels land at a relative 1e-7 (rounding), a long float32 sum such as dscale over 4,096 rows at a few e-5 absolute on values near 176, and bf16 inputs at a few e-3. A kernel 1e-4 off in float32 has a bug.

What interpret mode cannot tell you. It runs the kernel body as ordinary XLA:CPU code inside a loop over the grid, so it knows nothing about the MXU, VMEM capacity, DMA bandwidth or how Mosaic will schedule the code. What transfers to a TPU is correctness, legality of the block shapes, VMEM arithmetic and copy counts; speed has to be measured on the chip, with the profiler, against the XLA version you are trying to beat. The flash kernel took 150 ms in interpret mode against 2.0 ms for XLA's attention on this CPU, a ratio that says nothing about a TPU.

10. Reading production kernels

Before writing a kernel, look for one. Two places ship them: jax.experimental.pallas.ops inside jax (TPU: flash, splash, paged and ragged paged attention, the megablox grouped matmul; GPU: Triton-backed ops being deprecated, and Mosaic GPU matmuls), and tokamax, OpenXLA's separate kernel library with one API per op and several implementations chosen per device (0.0.16 on PyPI, uploaded 2026-10-09; its README says it "is still heavily under development"). Three were run here on this page's tensors: jax's TPU flash attention (output 6.0e-8, gradients within 4.8e-7), megablox gmm and the GPU mha (output 8.9e-8).

What to copy into your own kernels, from reading them: keep every block size in one frozen dataclass, forward and backward, so they can be swept; save the logsumexp, not the probabilities; clamp index maps for skipped tiles; precompute masks and metadata on the host and pass them by scalar prefetch; write the reference implementation beside the kernel (both flash kernels ship one: mha_reference); and pass every scale explicitly.

11. Choosing block sizes

The cost model. For a matmul tiled (bm, bk, bn), the Pallas TPU guide counts HBM traffic as (m k n / bn + k n m / bm + m n) × bytes per element: A is re-read once per column of blocks, B once per row of blocks (docs/pallas/tpu/matmul.md:341). Its advice: "to be compute bound, make the blocks as big as possible", limited by VMEM and by pipeline bubbles (with few grid steps, the first copy and last write-back are not hidden); and in practice "sweep over a large set of candidate block sizes, profile the kernel, and pick the best one". The root's lab tabulates that traffic for the running example and a 7B-class matmul; the {{Kernel playground|#t-pkplay}} tab adds the VMEM each of this page's kernels needs at each block size, logical and padded to (8, 128) tiles, against each generation's VMEM (flash attention at 128 × 128 blocks needs about seven times its logical bytes once its 32-wide head dimension and its one-number-per-row statistics are padded to 128 lanes).

What production does. Three strategies, from the source:

  • One default for everything: the flash attention kernel's 128 everywhere, with its TODO.
  • A checked-in table: ragged paged attention looks its block sizes up in TUNED_BLOCK_SIZES (tuned_block_sizes.py:37), 668 entries for "TPU v5" and 668 for "TPU v6", keyed by dtypes, heads per block, head dimension, page size, batched tokens and maximum model length, each giving (KV pages per block, queries per block). The two generations share every key but disagree on 237 of them: tuned values do not transfer between chips.
  • Search at run time: tokamax's ops declare a search space and tokamax.autotune measures it, for example ragged_dot's row tiles from 128 to 1,024 ("we found that there is no need on current TPU generations to search for larger tiles for m", ops/ragged_dot/pallas_mosaic_tpu.py:453). Its README warns that "autotuning is fundamentally non-deterministic" and that different configs "can lead to different numerics": serialise the result and reuse it.

The same keys, tuned on v5 and on v6, often pick different blocks
