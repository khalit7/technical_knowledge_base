JAX is a Python library from Google that looks like NumPy but treats your functions as things to transform: it can turn a function into its gradient (grad), into a batched version of itself (vmap), or into one compiled program for a CPU, GPU or TPU (jit), and these compose. A TPU (Tensor Processing Unit) is Google's own accelerator chip, and JAX is the main way to program it. This page teaches both from zero for someone who knows PyTorch well, mapping every idea to its PyTorch counterpart. Reading time about 25 minutes (measured from the words outside widgets at 200 a minute; the folded answers and code add about 9).

1. Why JAX exists, and who uses it

The problem. PyTorch runs your Python line by line: each operation is sent to the device the moment Python reaches it (eager execution, also called define-by-run), and autograd records a tape of what ran so loss.backward() can replay it backwards. That is wonderful for debugging and costs two things at scale: Python is on the critical path of every operation, and no one ever sees the whole program at once, so no one can optimise across it or decide, for the whole step, how to split it over thousands of chips.

JAX takes the opposite bet. You write ordinary NumPy-style Python, but the function is first run once with placeholder values that carry only a shape and a type, which records what it does as a small program. That program can then be transformed (differentiated, batched, split across devices) and compiled as a whole by XLA (Accelerated Linear Algebra, Google's compiler for array programs, which started inside TensorFlow). JAX's own description: "a Python library for accelerator-oriented array computation and program transformation" (JAX README). An early version was described at SysML 2018 (Frostig, Johnson and Leary, "Compiling machine learning programs via high-level tracing").

The price is a discipline: functions must be pure (their result depends only on their arguments, and they change nothing outside themselves), because anything that happens outside the arguments is either invisible to the recording or frozen into it. Parameters, optimiser state and random-number state stop being hidden inside objects and become values you pass in and get back. Section 2 shows why, and what goes wrong when you forget.

Who uses it. Google DeepMind trains Gemini with it: "We trained Gemini models using TPUv5e and TPUv4", where "the 'single controller' programming model of Jax and Pathways allows a single Python process to orchestrate the entire training run" (Gemini 1 report, section 3, vendor). Apple's foundation models "are pre-trained on v4 and v5p Cloud TPU clusters with the AXLearn framework", a JAX library: the server model on 8,192 TPUv4 chips and the on-device model on one slice of 2,048 TPUv5p chips (Apple AFM report, section 3.3). xAI released Grok-1 (314B parameters) with "JAX example code" (grok-1 repository). Outside the large labs PyTorch dominates: on the Hugging Face Hub, 255,916 models are tagged PyTorch and 12,404 JAX, about 21 to 1 measured 2026-10-15 from the Hub's library filter (a weak signal: the tag follows the weight files uploaded, and models trained in JAX are often uploaded as PyTorch weights).

The one-sentence version
JAX trades PyTorch's "run each line now" for "record the whole function, then transform and compile it", which costs you purity and buys you whole-program compilation, composable transformations and sharding by annotation. TPUs were designed around that compiled model, so JAX is their native language.

2. The functional model and the transformations

Arrays. jax.numpy (imported as jnp) mirrors NumPy, and a JAX array lives on a device like a CUDA tensor. One difference shows up on day one: arrays are immutable. x[0] = 1.0 raises an error; you write x = x.at[0].set(1.0), which returns a new array (inside jit the compiler turns it back into an in-place write when the old array is not needed).

Tracing. When a transformation meets your function, JAX calls it once with tracers: stand-ins that carry an abstract value (a shape and a dtype such as f32[8,128], no numbers) and record every operation applied to them. The record is a jaxpr (JAX expression): a small, typed, side-effect-free program of primitives (the elementary operations, such as dot_general, add, tanh). Here is a real one, for a two-line function of the running example's size:

import jax, jax.numpy as jnp

def mlp(w1, w2, x):          # x: [tokens, d_model]
    h = jax.nn.gelu(x @ w1)  # [tokens, 4 * d_model]
    return h @ w2

w1, w2 = jnp.ones((128, 512)), jnp.ones((512, 128))
x = jnp.ones((8, 128))

Read it as a program: a, b, c are the inputs with their abstract values, each line is one primitive with its output type, and nothing in it is Python any more. It also shows a porting trap: the GELU became tanh and a cube, because jax.nn.gelu defaults to the tanh approximation (approximate=True), while PyTorch's nn.GELU defaults to the exact form (approximate='none'), both checked in the installed versions.

Every transformation is an interpreter over such programs. That one idea explains the rest:

  • jax.jit(f) compiles the jaxpr with XLA and caches the executable under the call's signature: argument shapes and dtypes, plus any argument marked static (static_argnums), whose Python value is baked into the program. A new signature means a new trace and a new compile. Shapes are always static: no array may have a shape that depends on data, so variable lengths are padded and masked. PyTorch counterpart: torch.compile, but all or nothing.
  • jax.grad(f) and jax.value_and_grad(f) return a new function that computes the gradient of a scalar f with respect to its first argument (argnums picks others; has_aux=True lets f also return metrics). The gradient has exactly the structure of the parameters. No .grad attributes, no zero_grad(): a gradient is a fresh value each call. Counterpart: loss.backward(), but as a function. jax.lax.stop_gradient is detach().
  • jax.vmap(f) turns a function written for one example into one for a batch, by rewriting each primitive into its batched form; in_axes says which arguments carry the batch. Per-example gradients are vmap(grad(loss), in_axes=(None, 0)). Counterpart: torch.func.vmap, which ports the idea.

Control flow. A Python if on a traced value cannot be decided while tracing (the tracer has no value), so JAX raises an error; a Python loop is unrolled into the trace, one copy per iteration. Inside compiled code you use structured control flow: jax.lax.cond (both branches compiled), jnp.where (both computed, then selected), jax.lax.scan (a compiled loop with a carried state: how layers, RNNs and decode loops are written, and much faster to compile than an unrolled loop), jax.lax.fori_loop and jax.lax.while_loop (dynamic trip count; not reverse-differentiable).

Randomness is a value. PyTorch's torch.manual_seed(0) seeds a hidden global generator that changes on every call. In JAX a key is an array: key = jax.random.key(0); key, sub = jax.random.split(key); jax.random.normal(sub, shape). The same key always gives the same numbers, so you split a fresh subkey for every use and pass keys through your step like any other state. Flax's nnx.Rngs does the splitting inside models.

Pytrees. A pytree is any nesting of lists, tuples, dicts (and registered classes such as Flax modules) with arrays at the leaves. Parameters, gradients and optimiser states are all pytrees of the same shape, and jax.tree.map(lambda p, g: p - lr * g, params, grads) is a complete SGD step. One concept replaces model.parameters(), state_dict() and parameter groups.

3. What the compiler does

After tracing, a jitted function passes through four forms before it runs, and you can print each one:

  1. jaxpr: JAX's own program (jax.make_jaxpr(f)(x)).
  2. StableHLO: the jaxpr lowered into a versioned, portable operation set written in MLIR, Google's compiler-infrastructure format; this is the hand-off point between frameworks and compilers (PyTorch/XLA emits it too). jax.jit(f).lower(x).as_text().
  3. Optimised HLO: XLA's internal form (HLO, high-level operations) after its passes run. jax.jit(f).lower(x).compile().as_text().
  4. Machine code for the backend: LLVM for CPUs, GPU kernels (some generated through Triton), or the TPU backend.

The passes that matter to you:

  • Fusion: a chain of elementwise operations (and often the reduction after it) becomes one kernel, so intermediates stay in registers or on-chip memory instead of making a round trip to HBM each. This is why a JAX train step is usually fast without hand-written kernels: the whole step, backward pass and optimiser included, is one program the compiler can fuse across.
  • Layout assignment (which dimension is stored contiguously, and padding to the hardware's tile sizes), algebraic simplification, and buffer assignment, which decides which arrays can share memory. Its results are reported by compiled.memory_analysis(); compiled.cost_analysis() estimates FLOPs and bytes.
  • Donation: jax.jit(step, donate_argnums=0) promises that the old parameters and optimiser state will not be used again, so the new ones can be written into the same buffers. Without it the step briefly holds two copies of everything it returns.
  • Rematerialisation: jax.checkpoint (alias jax.remat) marks a function whose activations are recomputed in the backward pass instead of stored, trading compute for memory; policies choose what to keep. PyTorch counterpart: activation checkpointing.

The running example's train step through the pipeline

Compile time is real time. The first call of a large step can take seconds to minutes; the compiled program is cached in memory for the process, and a persistent compilation cache (jax.config.update("jax_compilation_cache_dir", ...)) keeps it across runs. Long Python loops inside a jitted function multiply compile time, which is the main reason layers are stacked and run with lax.scan.

Against torch.compile. TorchDynamo reads Python bytecode as it runs, captures what it can into graphs, and at anything it cannot handle inserts a graph break: that part runs eagerly and the program still works. TorchInductor then generates kernels (Triton on GPU) for each graph. JAX never reads your Python: tracing only sees operations on tracers, so Python control flow is either resolved during tracing or is an error. The result is one graph or none, with no silent fallback. Graph breaks, guards and recompiles on the PyTorch side are taught on torch.compile from the user's side.

4. The training stack

JAX itself has no layers, optimisers or checkpoints. Four libraries supply them, each a separate install, and together they are what Google calls the JAX AI stack (docs.jaxstack.ai). Versions are the latest on PyPI on 2026-10-15.

Mixed precision. The common recipe is the same as in PyTorch, written explicitly: float32 master parameters and optimiser state, a bf16 copy for the forward and backward matmuls, float32 for reductions such as softmax and the loss. On TPUs bf16 is native and no loss scaling is needed.

A whole train step, in the running example's JAX twin:

import jax, optax
from flax import nnx
import common as C, model_nnx as M                # the running example (src/data)

model = M.make_model(C.CFG)                       # built eagerly, like an nn.Module
optimizer = M.make_optimizer(model, C.CFG)        # nnx.Optimizer(model, optax chain, wrt=nnx.Param)

@nnx.jit                                          # one compiled program: forward, backward, update
def train_step(model, optimizer, x, y):
    def loss_fn(model):
        logits = model(x)                         # [B, T, vocab]
        return optax.softmax_cross_entropy_with_integer_labels(logits, y).mean()
    loss, grads = nnx.value_and_grad(loss_fn)(model)   # grads mirror the parameters
    optimizer.update(model, grads)                # zero_grad + backward + step, in one call
    return loss

params = nnx.state(model, nnx.Param)
print("parameters:", sum(p.size for p in jax.tree.leaves(params)))
for step in range(3):
    x, y = C.batch(step)                          # int32 [32, 128]: the batches PyTorch reads too
    print(step, x.shape, float(train_step(model, optimizer, x, y)))

5. Sharding and scale

In PyTorch you choose a parallelism implementation (wrap the model in DDP or FSDP, swap in tensor-parallel layers) and it owns the communication. In JAX you write the single-device step once, describe how arrays are laid out over devices, and the compiler works out the rest. Three objects carry the description:

  • Mesh: the devices arranged as a named grid, for example 8 devices as jax.make_mesh((2, 4), ('data', 'model')). The axis names are your vocabulary from then on.
  • PartitionSpec (P): for each dimension of an array, which mesh axis splits it, or None for "replicated along this dimension". P('data', None) on a [batch, features] array splits the batch over the 2 devices of the data axis.
  • NamedSharding = mesh + spec, attached to arrays with jax.device_put, to a jitted function's inputs and outputs, and to intermediates with jax.lax.with_sharding_constraint.

Then the compiler's partitioner propagates shardings from the annotated arrays to every other array in the program and, wherever an operation needs data laid out differently from how it is, inserts a collective: an all-gather (every device gets the whole array), a reduce-scatter (sum, then each device keeps a slice), an all-reduce (sum, everyone gets the whole result), an all-to-all, or a permute. The design comes from GSPMD (Xu et al. 2021), the name you will see everywhere; since JAX 0.7.0 (2025-07-22) the propagation is done by default by its successor Shardy, which "will be the only partitioner in JAX" once the migration ends (JAX Shardy migration guide). The idea is unchanged. The parallelism strategies you know are then just different specs on the same function:

When you want control. jax.shard_map runs a function per device on its local shard, and you write the collectives yourself (jax.lax.psum, all_gather, psum_scatter, ppermute): the rank-view program a torch.distributed user knows, used for custom communication, overlap tricks and wrapping kernels. It left jax.experimental in JAX 0.8.0 (2025-10-15). Between the two sits the newer explicit sharding mode, where shardings are part of an array's type (visible in jax.typeof(x)) and checked while tracing; jax.set_mesh(mesh) sets the mesh it uses. History you will meet in old code: pmap (one device axis; since 0.8.0 reimplemented over jit and shard_map and "in maintenance mode"), pjit (merged into jit), xmap (deleted in 0.4.31) (JAX changelog).

Many hosts. A TPU slice larger than one host runs the same script on every host (usually 4 chips each). jax.distributed.initialize() connects them; jax.devices() then lists every chip in the slice and jax.process_index() is the rank; each host feeds only its part of the batch (jax.make_array_from_process_local_data), and one jitted program spans the slice, its collectives riding the ICI links. Not run here: this machine is one host.

Why sharding is not optional: training-state memory per device

Training state = 16 bytes per parameter (bf16 weights and gradients, fp32 master weights and two Adam moments; the accounting of the ZeRO paper), activations excluded. derived 16 × parameters ÷ devices for FSDP, 16 × parameters for data parallel; HBM capacities vendor (section 6), all in GB of 109 bytes (v5p's 95 GiB is 102 GB, Ironwood's 192 GiB is 206 GB).

6. TPUs from the programmer's side, and Pallas

A GPU is about a hundred small processors (streaming multiprocessors) running thousands of threads; you think in threads, warps and blocks. A TPU chip has one or two big TensorCores and no threads at all: think "one wide core with a matrix engine and explicitly managed memory", scheduled almost entirely by the XLA compiler. What a JAX programmer needs from the hardware, each term once:

  • MXU (matrix multiply unit): a systolic array of 128 × 128 multiply-accumulate cells (256 × 256 on v6e) that weights are loaded into and activations pulse through; bf16 inputs, fp32 accumulation. Peak speed only on large matmuls whose dimensions are multiples of the array size: a dimension of 130 on a 128-wide array needs two passes for the work of about one.
  • VPU (vector unit): everything elementwise (activations, normalisation, softmax), much slower than the MXU.
  • VMEM: a software-managed on-chip scratchpad that tiles of data are staged into from HBM; there is no hardware cache doing it for you. HBM (high-bandwidth memory) is the chip's main memory.
  • ICI (inter-chip interconnect): direct links from each chip to its neighbours, forming a 2D torus (v5e, v6e) or a 3D torus (v4, v5p, Ironwood); in 3D pods optical circuit switches join cubes of 64 chips and route around failures. A pod is the largest set of chips joined this way; a slice is the part of one you rent.

The roofline in one line. A matmul of a batch of B tokens against a D × F weight matrix does 2BDF FLOPs and moves about 2DF bytes of bf16 weights, so when B is much smaller than D and F its arithmetic intensity (FLOPs per byte) is about B. Training with thousands of tokens per chip clears every ridge above; decoding one token at a time for 8 users does not.

Predict: a 7B model decodes for a batch of 8 users on one v6e chip. What fraction of the chip's bf16 peak can its weight matmuls reach at best?
About 8 ÷ 560 = 1.4% derived. Each weight byte read from HBM is used for only about 8 multiply-adds, and v6e needs about 560 per byte to keep its matrix units busy. That is why inference batches requests, and why the same chip can look superb in training and poor in small-batch decoding. The TPU and Pallas lab places the running example's own matmuls on this roofline.

Pallas. XLA writes almost every kernel for you, and for most training that is enough. When it is not (attention variants, mixture-of-experts routing, quantised or ragged matmuls), Pallas is JAX's kernel language, the counterpart of Triton: you write a Python function over refs (buffers in fast on-chip memory), launch it on a grid, and give each input a BlockSpec saying which tile of the big array each grid step loads. It lowers through Mosaic on TPU and through Triton or Mosaic GPU on GPU (Pallas docs). Its interpret=True mode runs a kernel on the CPU, which checks indexing and correctness but says nothing about speed: TODO (TPU and Pallas lab): the kernels written here, and how closely they match jnp.

9. Choosing

Choose JAX when

  • you will train on TPUs (it is their native language, and the price per chip-hour is the reason to be there);
  • you want one program that a compiler shards across hundreds of chips, with sharding kept out of the model code (MaxText's logical axes);
  • your research composes transformations: per-example gradients, Hessian-vector products, ensembles by vmap over stacked parameters;
  • bit-reproducible runs matter (explicit keys, levanter's preemption-proof determinism).

Stay with PyTorch when

  • you train and serve on NVIDIA GPUs and need the newest kernels the week they appear;
  • you start from Hugging Face checkpoints and PyTorch-first tools (vLLM, SGLang, TRL);
  • your team debugs by stepping through eager code, and the model changes shape a lot (variable-length everything);
  • the codebase already exists: port only when moving to TPUs, and then consider PyTorch/XLA or torchax before rewriting.

A practical path (the old page's, kept because it works): develop and test on CPU, where JAX traces identically; check sharding on simulated CPU devices as this page does; smoke-test on a free single TPU chip; train on a slice; profile before buying more. Free TPU options are described in Further reading.

Common mistakes

Each is something a PyTorch habit does in JAX. The error messages are the real ones, from running each snippet with JAX on this machine (src/read/run_examples.py).

Python if on a traced value

The tracer has no value, so Python cannot decide the branch. Use jax.lax.cond or jnp.where, or mark the argument static if it really is a configuration value.

import jax, jax.numpy as jnp

@jax.jit
def relu_or_not(x):
    if x.sum() > 0:          # a Python bool of a traced value
        return x
    return -x

The error occurred while tracing the function relu_or_not at <snippet>:3 for jit. This concrete value was not available in Python because it depends on the value of the argument x.

A shape that depends on the data

Every array shape must be known while tracing. Keep the shape fixed and mask: jnp.where(x > 0, x, 0), or jnp.nonzero(x, size=k) with a fixed maximum.

import jax, jax.numpy as jnp

@jax.jit
def positives(x):
    return x[x > 0]          # how many? depends on the data

positives(jnp.array([1.0, -2.0, 3.0]))

Assigning into an array

JAX arrays are immutable. .at[i].set(v) (also .add, .multiply, .min, .max) returns a new array; under jit it becomes an in-place write when the old array is dead.

import jax.numpy as jnp
x = jnp.zeros(3)
try:
    x[0] = 1.0
except TypeError as e:
    print("TypeError:", e)
x = x.at[0].set(1.0)         # a new array
print(x)

Side effects that run once (print, appending to a list, a global counter)

The list grew once, during tracing, and holds a tracer. Return values instead of appending; for logging at run time use jax.debug.print or jax.debug.callback.

import jax, jax.numpy as jnp
seen = []

@jax.jit
def f(x):
    seen.append(x)           # runs while tracing only
    return x + 1

for _ in range(3):
    f(jnp.ones(2))
print(len(seen), seen[0])

A global read inside jit is frozen

The global was read while tracing and baked into the compiled program as a constant. Pass anything that changes as an argument.

import jax, jax.numpy as jnp
scale = 2.0

@jax.jit
def f(x):
    return x * scale         # read once, while tracing

print(f(jnp.ones(2)))
scale = 10.0
print(f(jnp.ones(2)))        # same shape: cached, still 2.0

[2. 2.]

Reusing a random key

import jax

a = jax.random.normal(key, (3,))
b = jax.random.normal(key, (3,))      # same key: same numbers
key, sub = jax.random.split(key)
c = jax.random.normal(sub, (3,))      # fresh subkey: new numbers
print(a); print(b); print(c)

Out-of-bounds indexing does not raise

Under JAX, out-of-bounds reads are clamped and out-of-bounds writes are dropped, with no error, because accelerators cannot raise mid-kernel. Check indices yourself, or use jax.experimental.checkify.

import jax, jax.numpy as jnp
x = jnp.arange(5.0)
print(x[10])                          # no error: clamped to the last element
print(x.at[10].set(99.0))             # no error: the write is dropped

Timing dispatch instead of compute, or including the compile
JAX returns from a call as soon as the work is queued (asynchronous dispatch, like CUDA). Time with out.block_until_ready() and leave out the first call, which includes tracing and compiling. The reverse mistake is a host sync every step: float(loss), loss.item(), printing or converting to NumPy forces Python to wait for the device and stalls the queue; log every N steps.
Not donating the training state
Without donate_argnums (or nnx.jit, which handles it for modules), the step's outputs need fresh buffers while the inputs are still alive: briefly two copies of parameters and optimiser state, which runs out of memory at exactly the scale you care about. TODO (Compiler lab): the running example's memory_analysis with and without donation.
Expecting float32 matmuls on a TPU
On TPU the default precision of a float32 matmul uses bfloat16 passes on the MXU, so results differ from a float32 GPU or CPU run in the third or fourth digit. Ask for more with precision=jax.lax.Precision.HIGHEST or jax.default_matmul_precision("float32") when comparing against PyTorch (JAX docs, default_matmul_precision).

Interview questions

Short answers; open each after answering it yourself. The design questions have no single right answer: say the constraint that decides it.

What does jax.jit do on the first call, and on the second?
First call: run the Python function once with tracers (shape and dtype only), record a jaxpr, lower it to StableHLO, compile it with XLA for this device, cache the executable under the signature (shapes, dtypes, static arguments, shardings), then run it. Second call with the same signature: look up the cache and run; Python inside the function does not run at all. A new shape, dtype or static value starts again from tracing.
How does JAX compute gradients without a tape?
It differentiates the recorded program, not a run. grad traces the function into a jaxpr, builds its forward-mode linearisation (JVP), and transposes the linear part to get the reverse-mode (VJP) program; that new program is then compiled like any other. The backward pass is therefore code the compiler can fuse and shard, not a replay of a log.
Why must functions be pure, concretely?
Because the function body runs only while tracing. A print, a list append or a global counter happens once, at trace time, and never again on cached calls; a global read is frozen into the compiled program as a constant. Anything that should change between calls must come in as an argument and go out as a result.
In JAX, what changes in the code to go from data parallel to FSDP to tensor parallel?
Only the partition specs. Data parallel: batch P('data'), weights replicated, so XLA all-reduces the gradients. FSDP (ZeRO-3 style): weights also sharded on the 'data' axis, so XLA all-gathers each weight before use and reduce-scatters its gradient. Tensor parallel: the MLP's first weight split by columns and the second by rows on a 'model' axis, so one all-reduce per block. The model code does not change; the compiled program and its collectives do.
Design: shard a 70B dense model for training on a v5p pod. What mesh, and why?
Start from memory, then communication. Memory: bf16 parameters about 140 GB and fp32 Adam moments about 560 GB, plus about 10.5 TB of activation checkpoints at a batch of 1,024 sequences of 4,096 tokens (two per layer), about 11.2 TB in all against about 96 GB of HBM per chip (the scaling book's round figure; Google lists 95 GiB): about 117 chips is the floor by memory, so memory is not what decides it on a pod. Communication decides it: the batch of 1,024 sequences limits pure data parallelism to 1,024 chips, and pure FSDP over the whole pod leaves too few tokens per chip to hide its all-gathers. The scaling book's answer is mixed FSDP and tensor parallelism, about 2,048-way FSDP by 4-way tensor parallel on 8,192 of the 8,960 chips, at an assumed 40% MFU about 44 days for 15T tokens (How to Scale Your Model, part 6, Google DeepMind, 2025-02-04; its takeaway also lists 1,024-way data, 2-way sequence and 4-way tensor parallel, so the exact split varies). Map the tensor-parallel axis onto the fastest, shortest ICI dimension, keep the FSDP axis on the rest, and leave pipeline parallelism out unless the slice is split across pods (then add a data-parallel axis over the data-centre network).
Debug: your JAX train step is 3x slower than expected. What do you check, in order?
  1. Are you timing correctly? Exclude the first call (compilation) and call block_until_ready(); JAX dispatches asynchronously.
  2. Recompiles: set jax_log_compiles (or jax_explain_cache_misses); varying shapes or a Python value passed as static recompiles every step.
  3. Host syncs: float(loss), .item(), printing or NumPy conversion every step stalls the pipeline; log every N steps.
  4. Input pipeline: is the device waiting on data? The profiler shows idle gaps between steps.
  5. Surprise communication: read the compiled HLO (jit(f).lower(...).compile().as_text()) for unexpected all-gathers or all-reduces; a missing sharding constraint can replicate a large array.
  6. Shapes and precision: dimensions not multiples of 128 waste the MXU; fp32 where bf16 was intended halves throughput or worse.
  7. Memory pressure: no buffer donation, or rematerialisation recomputing too much.
  8. Then profile with jax.profiler (XProf trace viewer) rather than guessing.
Why do TPUs (and GPUs) want large batches?
A weight matmul's arithmetic intensity is about the number of tokens per chip, and the chip needs about 166 (v5p) to 560 (v6e) FLOPs per byte of HBM traffic to keep its matrix units busy (section 6). Below that it waits on memory; communication sets a similar floor for sharded training.
When would you write a Pallas kernel instead of trusting XLA?
When the profile shows a memory-bound sequence XLA does not fuse well or a structure it cannot express efficiently: attention variants (flash or splash attention), ragged or block-sparse matmuls, quantised matmuls, MoE routing. Not by default: the kernel must define its own gradient and is tied to one backend's tiling rules.
pmap, shard_map, and jit with shardings: which, today?
jit with shardings (GSPMD) by default; jax.shard_map when you need per-device code and explicit collectives; never new pmap: since JAX 0.8.0 (2025-10-15) it is implemented over jit and shard_map and "in maintenance mode", and 0.10.0 (2026-04-16) removed the old implementation. pjit is deprecated in favour of jit; xmap was deleted in 0.4.31 (JAX changelog).
You port a PyTorch model to JAX and the losses differ. What do you check?
The defaults first, because they differ silently (read from the installed versions, src/read/check_defaults.py): LayerNorm epsilon is 1e-6 in Flax NNX and 1e-5 in PyTorch; jax.nn.gelu uses the tanh approximation by default, nn.GELU the exact form; optax's adamw defaults to weight decay 0.0001, PyTorch's AdamW to 0.01; nnx.Linear initialises its kernel with LeCun normal (truncated, fan-in) and PyTorch's Linear with Kaiming uniform; and the kernel is stored [in, out], the transpose of PyTorch's weight, so copied weights must be transposed. Set every one explicitly and copy the weights, and the running example's twins agree to about 10-6 in loss (section 0). Then: matmul precision (on TPU the default precision for fp32 matmuls uses bf16 passes), reduction order, and dropout keys.

Interview questions

"Should a new JAX project use Flax Linen, Flax NNX, Equinox or Haiku?"

Flax NNX by default: it is what the Flax team points new users to, and MaxText and Tunix build on it; its stateful modules read like PyTorch. Equinox if you want models to be plain pytrees (common in scientific ML). Linen only to maintain existing code (it is not deprecated, but no longer the recommendation). Haiku is in maintenance mode by DeepMind's own notice since July 2023.

"A tutorial uses jax.pmap. What do you tell the team?"

pmap has been in maintenance mode since JAX 0.8.0 (October 2025) and since 0.10.0 it is a wrapper over jit(shard_map). Write new code with jax.jit plus NamedSharding (let the compiler place collectives) or jax.shard_map when you want per-device code; the migration guide has drop-in replacements.

"Our team is PyTorch-only. Can we use TPUs?"

Today: serving yes (vLLM TPU runs unchanged PyTorch model code through torchax); training through torchax or the old PyTorch/XLA, which Google says TorchTPU will replace. TorchTPU (native PyTorch device, torch.compile with XLA) was announced in April 2026 but was not public on 15 October 2026. The honest answer is "yes for serving, possible but bumpy for training, wait for TorchTPU or port the training code to JAX".

"Which open codebase would you read to learn how LLMs are sharded on TPU pods?"

MaxText: it is Google's maintained reference, expresses every parallelism as a mesh axis, and has MLPerf-tagged configurations. Marin's Levanter is the best non-Google alternative (named tensors, reproducible). T5X, Pax and EasyLM teach the pjit era but are quiet and use deprecated APIs.

"How do you judge whether a library is alive?"

Look for the owner's notice first (README banners: Haiku, JetStream, XPK, Levanter), then the archived flag, then the date of the last release, and only then commits, reading what they are: T5X, Pax and jmp had commits in 2026 that were automated lint changes. A dependency with one maintainer (Equinox, EasyDeL) is alive but carries bus-factor risk.
