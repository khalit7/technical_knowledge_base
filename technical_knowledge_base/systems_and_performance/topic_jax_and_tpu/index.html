The core idea
JAX runs your Python function once on placeholders to record it as a whole program, then transforms that program (differentiate, batch, split across devices) and hands it to the XLA compiler in one piece; TPUs were designed around exactly that compiled model, and the price is that your functions must be pure.

1. Why JAX exists, and who uses it

PyTorch runs your Python line by line (eager execution): each operation goes to the device when Python reaches it, and autograd records a tape for loss.backward(). That is wonderful for debugging and costs two things at scale: Python is on the critical path of every operation, and no one ever sees the whole program, so no one can optimise across it or decide, for the whole step, how to split it over thousands of chips. JAX takes the opposite bet: record the function first, then transform it and compile it as a whole with XLA (Accelerated Linear Algebra, Google's compiler for array programs, which started inside TensorFlow). In its own words, "a Python library for accelerator-oriented array computation and program transformation" (JAX README); an early version was described at SysML 2018 (Frostig, Johnson and Leary, "Compiling machine learning programs via high-level tracing"). The price is purity: parameters, optimiser state and random-number state stop hiding inside objects and become values you pass in and get back.

Who uses it. Google DeepMind trains Gemini with it: "We trained Gemini models using TPUv5e and TPUv4", where "the 'single controller' programming model of Jax and Pathways allows a single Python process to orchestrate the entire training run" (Gemini 1 report, section 3, vendor). Apple's foundation models "are pre-trained on v4 and v5p Cloud TPU clusters with the AXLearn framework", a JAX library: the server model on 8,192 TPUv4 chips and the on-device model on one slice of 2,048 TPUv5p chips (Apple AFM report, section 3.3). xAI released Grok-1 (314B parameters) with "JAX example code" (grok-1 repository). Outside the large labs PyTorch dominates: on the Hugging Face Hub, 255,916 models are tagged PyTorch and 12,404 JAX, about 21 to 1 measured 2026-10-15 from the Hub's library filter (a weak signal: the tag follows the weight files uploaded, and models trained in JAX are often uploaded as PyTorch weights).

2. The functional model and the transformations

Tracing. When a transformation meets your function, JAX calls it once with tracers: stand-ins that carry an abstract value (shape and dtype, no numbers) and record every array operation into a jaxpr, a small typed program of primitives. Python itself (loops, helper functions, arithmetic on shapes) runs to completion and leaves no trace. Every transformation is then an interpreter over that program, which explains the rest:

  • jax.jit(f) compiles the jaxpr with XLA and caches the executable under the call's signature: argument shapes and dtypes, plus any argument marked static, whose Python value is baked in. A new signature means a new trace and a new compile; shapes are always static, so variable lengths are padded and masked. PyTorch: torch.compile, but all or nothing.
  • jax.grad(f), jax.value_and_grad(f) return a function computing the gradient of a scalar f, with exactly the structure of the parameters: no .grad attributes, no zero_grad(). PyTorch: loss.backward(), but as a function; jax.lax.stop_gradient is detach().
  • jax.vmap(f) turns a function for one example into one for a batch by rewriting each primitive into its batched form. Per-example gradients are vmap(grad(loss), in_axes=(None, 0)). PyTorch: torch.func.vmap, which ports the idea.

The discipline follows from tracing. Arrays are immutable (x = x.at[0].set(1.0) returns a new array; under jit it becomes an in-place write). A Python if on a traced value is an error and a Python loop is unrolled, so compiled code uses jax.lax.cond, jnp.where, jax.lax.scan and while_loop. Randomness is a value: a key (jax.random.key(0)) is split into a fresh subkey for every use, and the same key always gives the same numbers. And a pytree (nested lists, tuples, dicts and registered classes with arrays at the leaves) holds parameters, gradients and optimiser state alike: jax.tree.map(lambda p, g: p - lr * g, params, grads) is a complete SGD step, replacing model.parameters(), state_dict() and parameter groups.

3. What the compiler does

A jitted function passes through four forms, each printable: the jaxpr (jax.make_jaxpr(f)(x)); StableHLO, a versioned, portable operation set in MLIR and the hand-off point between frameworks and compilers (PyTorch's TPU and Trainium backends emit it too; jax.jit(f).lower(x).as_text()); optimised HLO after XLA's passes (.compile().as_text()); and machine code (LLVM for CPUs, GPU kernels, some through Triton, or the TPU backend).

The running example's train step through the pipeline: thousands of operations become about 800 kernels

The passes that matter to you, each defined once:

  • Fusion: a chain of elementwise operations (often with the reduction after it) becomes one kernel, so intermediates never make a round trip to HBM. The whole step, backward and optimiser included, is one program to fuse across, which is why a JAX step is usually fast without hand-written kernels.
  • Layout assignment (which dimension is contiguous, padding to the hardware's tiles), algebraic simplification, and buffer assignment, which lets arrays with non-overlapping lifetimes share memory; compiled.memory_analysis() reports its result before anything runs.
  • Donation: jax.jit(step, donate_argnums=0) promises the old parameters and optimiser state are dead, so the new ones reuse their buffers instead of a second copy existing. Flax's nnx.jit donates nothing unless asked.
  • Rematerialisation: jax.checkpoint (alias jax.remat) recomputes activations in the backward pass instead of storing them; policies choose what to keep. PyTorch: activation checkpointing.

Compile time is real time. A large step's first call can take seconds to minutes; the executable is cached in memory, and a persistent compilation cache (jax.config.update("jax_compilation_cache_dir", ...)) keeps it across runs. Long Python loops multiply compile time, which is why layers are stacked and run with lax.scan.

Against torch.compile. TorchDynamo reads Python bytecode, captures what it can, and at anything it cannot handle inserts a graph break that runs eagerly. JAX never reads your Python: Python control flow is resolved while tracing or is an error. One graph or none, no silent fallback (torch.compile from the user's side owns the PyTorch side).

5. Sharding and scale

In PyTorch you choose a parallelism implementation (DDP, FSDP2, tensor-parallel layers) and it owns the communication. In JAX you write the single-device step once, say how arrays are laid out over devices, and the compiler does the rest. Three objects carry the description: a Mesh (devices as a named grid, such as 8 devices as ('data', 'model') of 2 × 4), a PartitionSpec P(...) (for each array dimension, the mesh axis that splits it, or None), and a NamedSharding (the two together, attached with jax.device_put, to a jitted function's inputs and outputs, or to intermediates with with_sharding_constraint).

The compiler's partitioner then propagates shardings to every other array and, wherever an operation needs data laid out differently, inserts a collective: all-gather (everyone gets the whole array), reduce-scatter (sum, each keeps a slice), all-reduce (sum, everyone gets the result), all-to-all, or permute. The design is GSPMD (Xu et al. 2021); since JAX 0.7.0 (2025-07-22) the propagation is done by its successor Shardy, which "will be the only partitioner in JAX" (JAX Shardy migration guide). How it was counted, and three things the counts show

Collectives counted in compile().as_text() of the whole step (forward, backward, clipping, AdamW, donated state), 20 steps each, Auto mesh axes, jax 0.11.2 (src/shard/out/rd_collectives.json). Who decides, and when you want control. On Auto mesh axes the compiler chooses everything you did not annotate. On Explicit axes a sharding is part of the array's type (jax.typeof(x)) and ambiguous cases are errors at trace time; in JAX 0.11.2 jax.make_mesh makes Explicit axes by default, while the Mesh constructor still defaults to Auto, so pass axis_types=(AxisType.Auto,) * 2 to get the behaviour older tutorials assume. jax.shard_map runs a function per device on its local shard with collectives you write (psum, all_gather, ppermute): the rank-view program a torch.distributed user knows. Old code you will meet: pmap (in maintenance mode since 0.8.0), pjit (merged into jit), xmap (deleted in 0.4.31) (JAX changelog). Across many hosts the same script runs on every host and one jitted program spans the slice (not run here: one host).

Why sharding is not optional: replicated training state outgrows any chip; FSDP divides it by the device count

6. TPUs from the programmer's side, and Pallas

A GPU is about a hundred small processors running thousands of threads. A TPU chip has one or two big TensorCores and no threads: think "one wide core with a matrix engine and explicitly managed memory", scheduled almost entirely by XLA. The parts a JAX programmer meets:

  • MXU: a systolic array of 128 × 128 multiply-accumulate cells (256 × 256 on v6e and TPU7x), bf16 in, fp32 accumulation; peak only when matmul dimensions are multiples of its size. VPU: the slower vector unit for everything elementwise.
  • VMEM: a software-managed on-chip scratchpad that tiles are copied into from HBM, the chip's main memory; no hardware cache does it for you.
  • ICI: direct chip-to-chip links forming a 2D torus (v5e, v6e) or a 3D torus (v4, v5p, Ironwood). A pod is the largest set joined this way, a slice the part you rent; Multislice joins slices over the slower data-centre network. v5p's pod is 8,960 chips, but the largest slice Cloud schedules is 6,144 (16 × 16 × 24), and Multislice reaches 18,432 (vendor, Cloud TPU v5p page, last updated 2026-10-13).
  • A JAX device is not always a chip: on v4 and v5p the two TensorCores are fused into one device ("megacore"); on TPU7x each core is a device, so a 4-chip Ironwood host shows 8 (jax/_src/tpu_info.py at jax-v0.11.2).

Two notes on the figures

Ironwood's ridge uses its bf16 peak. v5e's bandwidth is ambiguous: Cloud's page says "800 GiBps" (859 GB/s, ridge 229), the scaling book and JAX's own tpu_info.py 819 GB/s, used here. The specifications come from the Cloud TPU documentation and Google's posts; the hardware page also records where they disagree.

The roofline in one line. A matmul of B tokens against a D × F weight does 2BDF FLOPs and moves about 2DF bytes of bf16 weights, so when B is much smaller than D and F its arithmetic intensity is about B FLOPs per byte. Training with thousands of tokens per chip clears every ridge above; decoding one token at a time for 8 users does not.

Predict: a 7B model decodes for a batch of 8 users on one v6e chip. What fraction of the chip's bf16 peak can its weight matmuls reach at best?
About 8 ÷ 560 = 1.4% derived. Each weight byte read from HBM is used for only about 8 multiply-adds, and v6e needs about 560 per byte to keep its matrix units busy. That is why inference batches requests, and why the same chip can look superb in training and poor in small-batch decoding. Pallas. XLA writes almost every kernel, and for most training that is enough. When it is not (attention variants, mixture-of-experts routing, quantised or ragged matmuls), Pallas is JAX's kernel language, the counterpart of Triton: a Python function over refs (buffers in on-chip memory), launched on a grid, with a BlockSpec per input saying which tile each grid step loads. It lowers through Mosaic on TPU and through Triton or Mosaic GPU on GPU (Pallas docs); interpret=True runs a kernel on the CPU, checking indexing and correctness but not speed.

9. Choosing

Choose JAX when

  • you will train on TPUs and want the most mature path (XLA and the TPU grew up with it; TorchTPU is the newer route);
  • you want one program that a compiler shards across hundreds of chips, with sharding kept out of the model code (MaxText's logical axes);
  • your research composes transformations: per-example gradients, Hessian-vector products, ensembles by vmap over stacked parameters;
  • bit-reproducible runs matter (explicit keys, levanter's preemption-proof determinism).

Stay with PyTorch when

  • you train and serve on NVIDIA GPUs and need the newest kernels the week they appear;
  • you start from Hugging Face checkpoints and PyTorch-first tools (vLLM, SGLang, TRL);
  • your team debugs by stepping through eager code, and the model changes shape a lot (variable-length everything);
  • the codebase already exists: even on TPUs, try TorchTPU before rewriting in JAX.

A practical path (the old page's, kept because it works): develop and test on CPU, where JAX traces identically; check sharding on simulated CPU devices as this page does; smoke-test on a free single TPU chip; train on a slice; profile before buying more. Free TPU options are described in Further reading.

Timing dispatch instead of compute, or including the compile
JAX returns from a call as soon as the work is queued (asynchronous dispatch, like CUDA). Time with out.block_until_ready() and leave out the first call, which includes tracing and compiling. The reverse mistake is a host sync every step: float(loss), loss.item(), printing or converting to NumPy forces Python to wait for the device and stalls the queue; log every N steps.
Not donating the training state
Without donate_argnums, the step's outputs need fresh buffers while the inputs are still alive: briefly two copies of parameters and optimiser state. nnx.jit does not donate by default (flax 0.12.10, nnx/transforms/compilation.py:317-318: "If neither donate_argnums nor donate_argnames is provided, no arguments are donated"); write @nnx.jit(donate_argnames=("model", "optimizer")). On the running example the Compiler lab measured, from memory_analysis: 385.8 MB in all without donation, 376.6 MB with it, the difference being the 9.9 MB of parameters and Adam state that the outputs now reuse ("alias") measured. Here activations (366 MB of temporaries) dwarf the state, so donation saves 2.4%; for a 70B model the state is about 1.1 TB (section 5) and the second copy is what runs out of memory.
Expecting float32 matmuls on a TPU
On TPU the default precision of a float32 matmul uses bfloat16 passes on the MXU, so results differ from a float32 GPU or CPU run in the third or fourth digit. Ask for more with precision=jax.lax.Precision.HIGHEST or jax.default_matmul_precision("float32") when comparing against PyTorch (JAX docs, default_matmul_precision).

Interview questions

Answer each yourself first; the design questions have no single right answer, so say the constraint that decides it.

What does jax.jit do on the first call, and on the second?
First call: run the Python function once with tracers (shape and dtype only), record a jaxpr, lower it to StableHLO, compile it with XLA for this device, cache the executable under the signature (shapes, dtypes, static arguments, shardings), then run it. Second call with the same signature: look up the cache and run; Python inside the function does not run at all. A new shape, dtype or static value starts again from tracing.
How does JAX compute gradients without a tape?
It differentiates the recorded program, not a run. grad traces the function into a jaxpr, builds its forward-mode linearisation (JVP), and transposes the linear part to get the reverse-mode (VJP) program; that new program is then compiled like any other. The backward pass is therefore code the compiler can fuse and shard, not a replay of a log.
Why must functions be pure, concretely?
Because the function body runs only while tracing. A print, a list append or a global counter happens once, at trace time, and never again on cached calls; a global read is frozen into the compiled program as a constant. Anything that should change between calls must come in as an argument and go out as a result.
In JAX, what changes in the code to go from data parallel to FSDP to tensor parallel?
Only the partition specs. Data parallel: batch P('data'), weights replicated, so XLA all-reduces the gradients. FSDP (ZeRO-3 style): weights also sharded on the 'data' axis, so XLA all-gathers each weight before use and reduce-scatters its gradient (on CPU, XLA does the last as an all-reduce and a slice). Tensor parallel: the first weight of the attention and of the MLP split by columns and the second by rows on a 'model' axis, so two all-reduces per block in the forward pass (8 for the running example's 4 blocks, measured in section 5). The model code does not change; the compiled program and its collectives do.
Design: shard a 70B dense model for training on a v5p pod. What mesh, and why?
Start from memory, then communication. Memory: bf16 parameters about 140 GB and fp32 Adam moments about 560 GB, plus about 10.5 TB of activation checkpoints at a batch of 1,024 sequences of 4,096 tokens (two per layer), about 11.2 TB in all against about 96 GB of HBM per chip (the scaling book's round figure; Google lists 95 GiB): about 117 chips is the floor by memory, so memory is not what decides it on a pod. Communication decides it: the batch of 1,024 sequences limits pure data parallelism to 1,024 chips, and pure FSDP over the whole pod leaves too few tokens per chip to hide its all-gathers. The scaling book's answer is mixed FSDP and tensor parallelism, about 2,048-way FSDP by 4-way tensor parallel on 8,192 of the pod's 8,960 chips, at an assumed 40% MFU about 44 days for 15T tokens (How to Scale Your Model, part 6, Google DeepMind, 2025-02-04; its takeaway also lists 1,024-way data, 2-way sequence and 4-way tensor parallel, so the exact split varies). A caveat: 8,192 chips is more than one v5p slice, since the largest Cloud schedules is 6,144 chips (16 × 16 × 24; the 16 × 20 × 28 pod is not one schedulable slice), so in practice that run is two or more slices joined by Multislice over the data-centre network, with a data-parallel axis across slices. Map the tensor-parallel axis onto the fastest, shortest ICI dimension, keep the FSDP axis on the rest, and put only the data-parallel axis across slices, on the slower data-centre network (MaxText's dcn_data_parallelism setting), and leave pipeline parallelism out unless that network becomes the bottleneck.
Debug: your JAX train step is 3x slower than expected. What do you check, in order?
  1. Are you timing correctly? Exclude the first call (compilation) and call block_until_ready(); JAX dispatches asynchronously.
  2. Recompiles: set jax_log_compiles (or jax_explain_cache_misses); varying shapes or a Python value passed as static recompiles every step.
  3. Host syncs: float(loss), .item(), printing or NumPy conversion every step stalls the pipeline; log every N steps.
  4. Input pipeline: is the device waiting on data? The profiler shows idle gaps between steps.
  5. Surprise communication: read the compiled HLO (jit(f).lower(...).compile().as_text()) for unexpected all-gathers or all-reduces; a missing sharding constraint can replicate a large array.
  6. Shapes and precision: dimensions not multiples of 128 waste the MXU; fp32 where bf16 was intended halves throughput or worse.
  7. Memory pressure: no buffer donation, or rematerialisation recomputing too much.
  8. Then profile with jax.profiler (XProf trace viewer) rather than guessing.
Why do TPUs (and GPUs) want large batches?
A weight matmul's arithmetic intensity is about the number of tokens per chip, and the chip needs about 166 (v5p) to 560 (v6e) FLOPs per byte of HBM traffic to keep its matrix units busy (section 6). Below that it waits on memory; communication sets a similar floor for sharded training.
When would you write a Pallas kernel instead of trusting XLA?
When the profile shows a memory-bound sequence XLA does not fuse well or a structure it cannot express efficiently: attention variants (flash or splash attention), ragged or block-sparse matmuls, quantised matmuls, MoE routing. Not by default: the kernel must define its own gradient and is tied to one backend's tiling rules.
pmap, shard_map, and jit with shardings: which, today?
jit with shardings (GSPMD) by default; jax.shard_map when you need per-device code and explicit collectives; never new pmap: since JAX 0.8.0 (2025-10-15) it is implemented over jit and shard_map and "in maintenance mode", and 0.10.0 (2026-04-16) removed the old implementation. pjit is deprecated in favour of jit; xmap was deleted in 0.4.31 (JAX changelog).
You port a PyTorch model to JAX and the losses differ. What do you check?
The defaults first, because they differ silently (read from the installed versions, src/read/check_defaults.py): LayerNorm epsilon is 1e-6 in Flax NNX and 1e-5 in PyTorch, and NNX's LayerNorm also defaults to use_fast_variance=True (variance as E[x2] − E[x]2, harmless on this model, lossy when the mean is large against the spread; child page PyTorch to JAX); jax.nn.gelu uses the tanh approximation by default, nn.GELU the exact form; optax's adamw defaults to weight decay 0.0001, PyTorch's AdamW to 0.01; nnx.Linear initialises its kernel with LeCun normal (truncated, fan-in) and PyTorch's Linear with Kaiming uniform; and the kernel is stored [in, out], the transpose of PyTorch's weight, so copied weights must be transposed. Set every one explicitly and copy the weights, and the running example's twins stay within 3 × 10-5 in loss over 500 steps and 10-3 over 4,000 (sections 0 and 8); what remains is summation order, compounding slowly. Then: matmul precision (on TPU the default precision for fp32 matmuls uses bf16 passes), reduction order, and dropout keys.

The one idea
A JAX transformation (jit, grad, vmap) does not run your Python on numbers. It runs it once on tracers, stand-ins that carry only a shape and a dtype, records every elementary operation into a small typed program called a jaxpr, and then interprets that program: compile it (jit), differentiate it (grad), or batch it (vmap). Everything else in this lab, the purity rules, the recompiles, the errors, follows from that.

1. Tracing: the same function before and after

The problem it solves. PyTorch in eager mode runs each operation the moment Python reaches it, so the framework never sees your program as a whole and cannot optimise across operations (torch.compile exists to recover that view). JAX takes the opposite route: before doing anything, it captures the whole function as data.

How it works. When jax.jit(f) (or jax.make_jaxpr(f)) is called, JAX replaces each array argument by a tracer whose abstract value is a ShapedArray: shape and dtype, no numbers (printed f32[32,128,128]). Your Python then runs normally, but every jnp or lax call on a tracer is intercepted and appended to the jaxpr as one primitive (an elementary operation such as dot_general, add, exp) with its output's abstract value. Python itself (the variables, the helper functions, the for over q, k and v, the arithmetic on shapes) runs to completion and leaves no trace: only the array operations remain.

2. Static and dynamic values; Python control flow against lax

The rule. While tracing, a value is either static (known to Python now: shapes, dtypes, Python numbers, arguments marked static_argnums) or dynamic (a tracer: known only when the compiled program runs). Python may branch and loop on static values freely; the branch taken is simply baked into the program. It cannot branch on a dynamic value, because there is no value yet. The real errors, from this run:

5. Arrays are immutable


A JAX array never changes after it is created; operations return new arrays. This is what makes purity cheap to check, and the compiler gets the in-place update back where it is safe (inside jit, and across steps with buffer donation, measured in the Compiler lab). 7. Pytrees: the model's parameters as one nested value


The problem. Transformations take and return arrays, but a model has dozens of parameters. PyTorch keeps them as attributes of nn.Module objects and gives you model.parameters() and state_dict() to walk them. JAX instead accepts any nesting of containers, a pytree, and flattens it to a list of leaves (the arrays) plus a tree definition (the structure) whenever a transformation needs to. jit, grad, vmap, optax and orbax all speak pytrees, so parameters, gradients, optimiser states and checkpoints share one shape.

The difference in one line. PyTorch differentiates the computation that just ran: loss.backward() walks the graph autograd recorded during the forward pass and adds gradients into each parameter's .grad. 9. vmap: write it for one example, run it on a batch


The problem. Many computations are easiest to write for one example: one sequence's loss, one query against one key, one sample's gradient. Batching them by hand means adding a leading dimension everywhere and getting every transpose right; a Python loop over examples is slow. jax.vmap(f, in_axes=...) does the rewrite for you: it traces f with batch tracers that remember which dimension is the batch, and replaces each primitive with its batched form through that primitive's batching rule. No loop survives into the program. in_axes gives the batched dimension of each argument (None for an argument shared by the whole batch); out_axes places it in the output.

10. Inside: every transformation is an interpreter


JAX's core is small. Each transformation is a trace object (an interpreter) with one method that matters, process_primitive. Every jnp or lax call ends in Primitive.bind, which hands the operation to whichever trace is current. Transformations nest by stacking traces: under jit(vmap(grad(f))), grad's trace handles an operation first and calls the operation again on its parent (vmap's), which calls it on jit's, which records it. 2. Fusion: the same 29 equations, before and after XLA


The problem. Run the MLP sub-block eagerly and every equation is its own kernel: it reads its inputs from memory and writes its output back, even when the next equation immediately reads that output again. On accelerators, memory traffic, not arithmetic, is usually the bottleneck for this kind of elementwise work. Fusion merges a chain of operations into one kernel so intermediate values stay in registers or on-chip memory.

What transfers to GPU and TPU, and what does not
The idea transfers: elementwise chains, broadcasts and the reductions of LayerNorm fuse on every backend, and duplicated work is removed. The exact kernels do not: on this CPU, XLA hands matmuls to the YNNPACK library and fuses LayerNorm into the matmul's input ("library fusion"); on a GPU, XLA calls libraries such as cuBLAS, which "often preclude complex fusion opportunities", or, "for more advanced fusions which include matrix multiplication or softmax", generates the kernel with Triton (OpenXLA, XLA:GPU architecture, read 2026-10-15); on a TPU, matmuls run on the MXU in code XLA generates itself (the TPU and Pallas lab). 4. Memory: buffer assignment and donation


After fusion, XLA's buffer assignment gives every value in the program a place in memory, letting values whose lifetimes do not overlap share the same bytes. compiled.memory_analysis() reports the result before anything runs: arguments (what you pass in), outputs, temp (everything in between, mostly the activations the backward pass needs) and alias (outputs written into input buffers). PyTorch has no ahead-of-time equivalent; you learn its peak from torch.cuda.max_memory_allocated() after running.


Donation. A train step takes the parameters and optimiser state and returns new ones of exactly the same shapes. Without help, XLA must keep the inputs intact (you might use them again), so the outputs need fresh buffers: two copies of the training state exist at once. jax.jit(step, donate_argnums=(0, 1)) is a promise that you will not touch arguments 0 and 1 again, so XLA may write the outputs into their buffers. The running example's make_train_step donates both.


On the running example, memory_analysis() gives 385.8 MB in all without donation and 376.6 MB with it, because the outputs now reuse ("alias") the 9.9 MB of parameters and Adam state, while the activations (366 MB of temporaries) dwarf the state. 5. Rematerialisation: memory against recompute


The problem. The backward pass needs the forward pass's intermediate values (the attention scores, the GELU inputs, ...). Keeping them all is the "temp" bar above, and it grows with batch, sequence length and depth. Rematerialisation (jax.checkpoint, alias jax.remat; PyTorch's torch.utils.checkpoint) keeps less and recomputes the rest during the backward pass. A policy says what to keep:


    

  • nothing_saveable: keep only the wrapped function's inputs; recompute everything (the default for jax.checkpoint).
    • 

  • dots_saveable: keep every matmul output, recompute the cheap elementwise work around them.
    • 

  • dots_with_no_batch_dims_saveable: keep matmuls against weights, but not the batched ones (attention's q @ k and p @ v, whose outputs are the large B x H x T x T tensors).
    • 



Production code names its policies by what they keep: MaxText's default is remat_policy: 'full' (recompute everything), with a ladder of options from 'minimal' to 'full' that its config describes as a "trade-off between speed (fastest to slowest) and HBM usage (highest to lowest)", including variants that offload saved tensors to host memory (configs/base.yml:489-492).

Common mistakes


Timing the first call
The first call traces, lowers and compiles (section 7). Time steady state after a warm-up call, and call jax.block_until_ready(out) before stopping the clock: JAX dispatches asynchronously, so without it you time the dispatch, not the work.


Not donating the training state
Two copies of parameters and optimiser state at the end of every step (section 4). jax.jit(step, donate_argnums=(0, 1)); with Flax NNX, nnx.jit(donate_argnames=("model", "optimizer")), since nnx.jit donates nothing by default.


Reading FLOPs from cost_analysis on a scanned model
The loop body is counted once (section 6). Multiply by the number of layers, or compute FLOPs from the model's shapes.


Expecting the persistent cache to help small programs
With the default 1-second threshold, quick compiles are never written (section 7). Lower jax_persistent_cache_min_compile_time_secs when iterating on small models.


Remat everywhere
Recomputing every block costs FLOPs on every layer, but the last block saves nothing (section 5). Start from the memory you need to free and pick the cheapest policy that frees it.


Leaving debugging on
jax.debug.print adds a host callback to every step; jax_debug_nans checks every output and reruns de-optimised on a hit. Both belong in a debugging run, not a training run.



Interview questions


What happens between jax.jit(f)(x) and the result?
Look up the cache by the signature (shapes, dtypes, shardings, static values). On a miss: trace f with abstract tracers into a jaxpr, lower each primitive to StableHLO, hand the module to XLA, which optimises (simplification, CSE, layout assignment, fusion, buffer assignment) and generates code; cache the executable. Then dispatch it asynchronously and return arrays whose values arrive later.


Why is a JAX train step often fast without custom kernels?
The whole step, forward, backward and optimiser, is one program, so XLA can fuse across operations that eager execution runs separately: elementwise chains, LayerNorm's reductions, matmul epilogues. Fusion cuts memory traffic, the usual bottleneck (here  less on one MLP block). What it cannot do (new algorithms like flash attention) is what Pallas is for.


Your model OOMs on a TPU. What do you check, in order?
memory_analysis() of the compiled step before running anything: are the state arguments donated (alias equal to the state size)? Is temp dominated by activations? Then remat (a policy, and which layers), smaller micro-batches with gradient accumulation, sharding the state (FSDP), and offloading saved activations or optimiser state to host memory.


Scan or a Python loop over layers?
Scan: compile time and program size stay flat as depth grows, and the per-layer weights become one stacked array, which suits sharding and remat per layer. A Python loop: XLA sees across layer boundaries and compile time grows with depth. Production JAX LLM code scans by default.


How does jit differ from torch.compile?
jit traces with abstract values and produces one whole program or an error; torch.compile reads bytecode, captures what it can and falls back to Python at graph breaks, guarded by runtime checks that trigger recompiles. JAX demands purity up front and gets whole-program compilation; PyTorch keeps eager semantics and compiles opportunistically.

2. optax: an optimiser is a pair of pure functions


The problem. torch.optim.AdamW is an object that holds the moment estimates and writes into the parameters in step(); parameter groups carry per-group settings such as "no weight decay on biases", and a separate scheduler object changes the learning rate. Under jit nothing may be mutated, so optax splits the optimiser into data and functions.


How it works. An optax GradientTransformation is two pure functions: init(params) returns the optimiser state (a pytree, for Adam the step count and the two moment trees), and update(grads, state, params) returns (updates, new_state). You add the updates yourself with optax.apply_updates(params, updates), a plain sum. Bigger optimisers are optax.chain(...) of small transformations, and that is literally how optax.adamw is written: chain(scale_by_adam(b1, b2, eps), add_decayed_weights(weight_decay, mask), scale_by_learning_rate(learning_rate)) (alias.py:724-727 at optax v0.2.8). A mask (a pytree of booleans, or a function returning one) replaces parameter groups, and a learning-rate schedule is just a function of the step count.

6. Checkpoints with orbax: stop, restore, continue bit for bit


The problem. A long run is preempted; you need its weights, its optimiser state and its place in the data, written without stalling training, and restorable even onto a different number of devices. PyTorch's torch.save(model.state_dict()) writes one file from one process; torch.distributed.checkpoint (DCP) is the sharded, multi-process path (Distributed PyTorch covers it).

Restoring takes a target with shapes, dtypes and shardings, so a checkpoint saved on one layout can be loaded onto another. 7. Data with grain: a loader whose position is part of the checkpoint


The problem. Resuming the weights is not enough: if the data loader restarts its epoch, the model sees some batches twice and others never, and the resumed run is no longer the run you planned. A PyTorch DataLoader does not save its position by default (the separate torchdata package adds a StatefulDataLoader ("a drop in replacement for torch.utils.data.DataLoader that implements state_dict and load_state_dict methods, enabling mid-epoch checkpointing") for this).


How it works. grain builds a pipeline from a random-access source (anything with __len__ and __getitem__) and transformations that are pure functions of the record index and a seed: shuffling is a fixed permutation, not a buffer. So the whole state of an iterator is a small record (MapDataset.shuffle maps each position to a shuffled index with index_shuffle: dataset.py:649, shuffle.py:68, grain v0.2.18), here {"next_index": 100}, which orbax saves next to the weights. Multi-process loading (grain.DataLoader with workers, or mp_prefetch) repeats the same stream on a rerun with the same worker count, but changing the worker count keeps it only if the batches are formed before the work is shared out: MapDataset.batch before to_iter_dataset gave the same batches with 0, 2 and 4 workers, while batching after to_iter_dataset, a filter before mp_prefetch, or a Batch operation in grain.DataLoader lets each worker batch its own share, so the batches depend on the worker count. Iterator state does not transfer across worker counts either: a 2-worker state loaded into a 0-worker pipeline fails with KeyError: 'next_index' (grain 0.2.18, measured on the child page The JAX training stack).

8. Mixed precision: bfloat16 compute, float32 master weights


The problem. Matmuls in 16-bit floats run faster and halve activation memory, and TPUs and recent GPUs are built for bfloat16 (8 exponent bits like float32, so the same range, but only 8 significant bits instead of 24). The catch is the update: a weight near 1.0 can only take bfloat16 values 2-7 = 0.0078 apart, so an Adam step of about the learning rate (1e-3) rounds away to nothing.


How it works. Keep a float32 master copy of the weights and the optimiser state; cast a bfloat16 copy for the forward and backward pass; the gradient of a cast is a cast back, so the gradients reach the optimiser in float32. PyTorch does this with torch.autocast; in JAX it is written out, usually as a policy naming three dtypes (params, compute, output). DeepMind's jmp library is the reference implementation of such policies; it has had no release since 0.0.4 (2023-01-30, see the Tool map) and the libraries carry the policy themselves: NNX layers take dtype (compute) and param_dtype arguments, and MaxText's default config has dtype: "bfloat16" with weight_dtype: "float32" (base.yml:128, 202, main on 2026-10-15). Loss scaling is only needed for float16, whose range is narrow; bfloat16 does not need it.

9. Common mistakes, and questions to answer


Copying weights without the transpose
PyTorch's Linear.weight is [out, in]; Flax's kernel is [in, out]. Non-square matrices fail loudly, square ones load silently wrong: 16 of the running example's 25 weight matrices are 128 x 128. Check logits against PyTorch on one batch before training (section 4).


Trusting the defaults
LayerNorm epsilon (1e-5 against 1e-6) and variance formula (Flax's use_fast_variance=True computes E[x2] − E[x]2; harmless on this model, so the twins leave it on), GELU (exact against tanh), initialisers (kaiming-uniform against lecun-normal), AdamW weight decay (0.01 against 1e-4) and its scope (groups against mask) all differ. Write every one of them explicitly on both sides.


Expecting bit-identical curves across frameworks
Different kernels sum in different orders; expect agreement to float32 rounding for the first few hundred steps and a slow drift after (section 5). Compare logits and gradients on one batch for correctness, and loss curves for agreement within noise.


Saving the weights but not the optimiser or the data position
AdamW's two moment trees are twice the size of the weights and the run is not resumable without them; without the data iterator the resumed run reads different batches. Save all three in one orbax checkpoint (section 6).


bfloat16 weights without a master copy
Updates smaller than half the bfloat16 spacing vanish; LayerNorm scales near 1.0 freeze first (section 8).


Wrapping a JAX-transformed function in an Equinox module
The first version of frameworks.py called eqx.filter_jit(jax.vmap(model)); Equinox warned that the callable returned by jax.vmap is not a pytree, so the model's arrays become constants baked into the compiled program and would get no gradient. Questions


How is an optax optimiser different from a torch.optim one?
It holds no state and changes nothing: init builds the state pytree, update returns updates and a new state, and you apply them. That makes it composable (chain), jittable and shardable like any pytree; parameter groups become masks and schedulers become functions of the step.


What does nnx.jit do that jax.jit does not?
It accepts modules and optimisers as arguments: it splits them into graphdef and state, passes only the state through jax.jit (the graphdef is static, part of the cache key), merges inside, and writes any changed state back into your Python objects after the call.


Your JAX port's loss is 0.02 higher than PyTorch's after 300 steps. Where do you look?
First logits at initialisation on one batch with copied weights: a difference above about 1e-5 means the forward differs (transposes, epsilon, GELU, masks). If those match, compare one optimiser step on the same gradients (decay scope, betas, schedule offset). Section 4 shows which mistake gives which signature.


How do you make a preempted JAX run resume exactly?
Checkpoint parameters, optimiser state, the step, the RNG key and the data iterator state together (orbax plus grain), restore into the same shapes and shardings, keep the data order a function of the seed and the step, and resume with the same number of data workers (grain's iterator state does not transfer across worker counts; section 7). Here that gives a bit-identical continuation.


Why bfloat16 rather than float16 for training?
Same exponent range as float32, so no overflow and no loss scaling; fewer mantissa bits, which a float32 master copy absorbs. TPUs' matrix units take bfloat16 natively.

1. Devices, the mesh and a PartitionSpec


Something must say which device holds which piece of every array. In PyTorch that is the wrapper you choose (DDP, FSDP2, tensor-parallel layers) or a DTensor's placements; in JAX it is three small objects. 2. Propagation: annotate a few arrays, the compiler does the rest


How it works. You write the single-device program and annotate some arrays: the inputs (by passing sharded arrays, or in_shardings to jax.jit), the outputs (out_shardings), and if you need to, a few intermediates with jax.lax.with_sharding_constraint(x, sharding). The compiler then does two jobs. Sharding propagation gives every other array a sharding, by pushing the known ones through each operation (a matmul whose input rows are split on data produces output rows split on data). The SPMD partitioner then rewrites the program into the one program every device runs on its own shard (SPMD: single program, multiple data), and wherever an operation needs data laid out differently from how it is, inserts a collective: an operation in which a group of devices exchange data. The design is GSPMD (Xu et al. 2021); since JAX 0.7.0 the propagation step is done by default by its successor Shardy, and both hand over to the same partitioner (XLA's source shows the switch, section 7). PyTorch has no counterpart for whole programs: DTensor decides operator by operator at run time, and torch.compile does not re-plan the communication.


The cost. You do not see the communication in your code. It appears only in the compiled program, so checking it is part of the job: jax.jit(f).lower(*args).compile().as_text() and search for all-reduce, all-gather, reduce-scatter, all-to-all, collective-permute. That is exactly how every number on this tab was obtained.

    5. shard_map: writing the per-device program yourself
    

    When propagation is not enough. You may need a communication pattern the compiler will not invent (ring attention, overlapping a collective with compute, a custom MoE dispatch), or simply want certainty. jax.shard_map(f, mesh=..., in_specs=..., out_specs=...) runs f once per device on that device's shard (shapes inside are the per-device shapes) and you write the collectives yourself: psum, all_gather, psum_scatter, all_to_all, ppermute, with jax.lax.axis_index(name) as the rank. Inside, the mesh axes are Manual: the partitioner leaves that region alone. This is the rank-view program a torch.distributed user already knows; the difference is that it is still traced and compiled as one program, so it composes with jit, grad and vmap. It left jax.experimental in JAX 0.8.0 (2025-10-15); jax.experimental.shard_map still imports in 0.11.2 with a DeprecationWarning.
    

    A ring all-reduce written by hand, the exact code that ran (from src/shard/sh_collectives.py):
    

    def ring_allreduce(b):                       # b: this device's block [1, N*k]; chunks of k
    me = jax.lax.axis_index("i")
    chunks = b.reshape(N, -1)                # N chunks
    right = [(j, (j + 1) % N) for j in range(N)]
    # phase 1, reduce-scatter: at step s, send chunk (me - s) mod N to the right; add what arrives to chunk (me - s - 1)
    acc = chunks
    for s in range(N - 1):
        send = acc[(me - s) % N]
        recv = jax.lax.ppermute(send, "i", perm=right)
        acc = acc.at[(me - s - 1) % N].add(recv)
    # now chunk (me + 1) mod N holds the full sum on this device
    # phase 2, all-gather: pass the finished chunks round the ring
    for s in range(N - 1):
        send = acc[(me + 1 - s) % N]
        recv = jax.lax.ppermute(send, "i", perm=right)
        acc = acc.at[(me - s) % N].set(recv)
    return acc.reshape(1, -1)

f_ring = jax.jit(jax.shard_map(ring_allreduce, mesh=mesh, in_specs=P("i", None), out_specs=P("i", None)))

    6. Many hosts, and the APIs you will see in old code
    

    Multi-host (not run here: this machine is one host). A TPU slice bigger than one host (typically 4 chips per host) runs the same Python script on every host. jax.distributed.initialize() connects them (on Cloud TPU it finds the coordinator by itself); then jax.devices() lists every chip in the slice, jax.local_devices() only this host's, and jax.process_index() / jax.process_count() play the role of rank and world size. PyTorch's equivalent is torchrun + init_process_group, with one process per GPU rather than one per host.

    8. Common mistakes and interview questions
    

    Annotating only the weights and trusting propagation
    The "FSDP, weights annotated only" row: the compiler followed the weights' split into the activations and then all-gathered whole-batch activations: 8 copies of the MLP hidden layer [32, 128, 512] (8 MiB each) and 16 of [32, 128, 128] (2 MiB each), about 32 times the all-gather bytes of the fixed version. One with_sharding_constraint on the residual stream per block fixed it. Constrain activations at block boundaries, as MaxText does with logical axis rules.
    

    Assuming make_mesh gives an Auto mesh
    In jax 0.11.2 it gives Explicit axes: shard_map then refuses mismatched inputs, and a matmul with both contracting dimensions sharded is a type error. Pass axis_types explicitly so the code says which mode it relies on.
    

    Reading the collectives off the code instead of the compiled HLO
    The code has none; the HLO has them all, and they depend on the backend's passes (on CPU no reduce-scatter is formed from all-reduce + slice). Search compile().as_text(), and profile on the real hardware before drawing conclusions about cost.
    

    Expecting bit-identical losses across layouts
    Sharding changes the order of additions (each device sums its part, then the parts are added), so float32 results differ in the last bits: here by at most  over the steps, the same size as float32 rounding of a loss near 4. A gap far larger than that is a bug.
    

    Switching partitioner and expecting the same program
    Same annotations, different propagators: the older GSPMD propagator produced  for the tensor-parallel layout where Shardy produced 18 all-reduces, but did better than Shardy on the unconstrained FSDP case. Where GSPMD's extra tensor-parallel collectives come from, located by the source line each carries in the HLO (child page Sharding and scale): 84 of its all-gathers sit in the optimiser, 28 each in optax's Adam moment updates (_tree_math.py:398 and :433) and in apply_updates (update.py:42), because GSPMD split the small replicated parameters (biases and LayerNorm parameters) over the model axis, idle for them, and gathers them back every step; 29 more are in LayerNorm (model_jax.py:45–47), which it split on the feature dimension. Shardy inserts none of these. Neither is uniformly better; constraints make the result robust to both.
    

    Interview questions
    

    You annotate x as P('data', None) and W as P(None, 'model'). What does y = x @ W cost in communication?
    Nothing: each device multiplies its rows of x by its columns of W and the result is P('data', 'model'). Communication appears only if you then ask for another layout (P('data', None) costs an all-gather over 'model').
    

    FSDP versus data parallel: how much more traffic?
    Data parallel all-reduces the gradients: 2(n−1)/n × P bytes per device. FSDP all-gathers the weights in the forward pass, again in the backward pass if they were freed, and reduce-scatters the gradients: (n−1)/n × P each, so 1.5× data parallel with re-gathering, 1× without. In exchange each device holds 1/n of weights, gradients and optimizer state.
    

    Megatron tensor parallelism: where are the all-reduces, and why does the MLP need only one?
    Split the first MLP matrix by columns and the second by rows: GELU is elementwise, so each device keeps its slice of the hidden layer and the only communication is one all-reduce of the [batch, seq, d_model] output (forward), and one of the input gradient (backward). Attention likewise: heads split, one all-reduce after the output projection. Measured here: 8 forward all-reduces for 4 blocks.
    

    Your sharded step is slower than expected. What do you check?
    The compiled HLO for collectives you did not plan (an all-gather of activations, an all-to-all), their sizes and replica groups; whether propagation changed after a code edit (compare HLO between versions); memory_analysis() for unexpected replication; a profile to see whether collectives overlap with compute; and that the mesh axis carrying the most traffic maps onto the fastest links (ICI within a slice).

    1. A TensorCore, as JAX sees it
    

    The Reading tab defined the parts (MXU, VPU, VMEM, HBM, ICI) and gave each generation's peak and ridge point. Here is the one level down that a JAX or Pallas programmer touches. A TensorCore is one sequential processor with no threads: a scalar unit runs the control flow and computes addresses (from its own small SMEM), and issues wide vector instructions; the VPU works on vector registers of 8 × 128 32-bit values (128 lanes, 8 sublanes); the MXUs multiply; DMA engines copy tiles between HBM and VMEM in the background while the core computes. In PyTorch-on-GPU terms: VMEM plays the role of shared memory, but it is tens of megabytes rather than a few hundred kilobytes, and nothing caches HBM for you, so the compiler (or your Pallas kernel) decides every copy.

      Predict: a kernel's working set is 40 MiB of tiles. On which generations does it fit in one core's VMEM?
      

      

      v5e and v6e have 128 MiB per core; v5p and TPU7x have 64 MiB, v4 16 MiB (tpu_info.py). And the compiler applies a default per-kernel ("scoped") VMEM limit; a kernel that needs more asks with vmem_limit_bytes (section 7).
      

      


      

      2. The MXU, and why shapes should be multiples of 128
      

      An MXU is a systolic array: a square of multiply-accumulate cells holding one tile of the weight matrix, through which rows of activations pulse, each cell multiplying, adding and passing its result to the next cell, so each number read from VMEM is used 128 (or 256) times. It holds a whole k × n tile at a time, of side 128 (v4, v5e, v5p) or 256 (v6e, TPU7x), and the scaling book's rule follows: "Weight matrices need to be padded to at least size 128 (256 on TPU v6e) in both dimensions to fill up the MXU." A weight of 65 columns occupies a 128-wide tile and leaves the rest of the cells multiplying zeros. The cycle-by-cycle picture of the array is on the Hardware topic's TPU page; here is what it means for the shapes in your model.
      

      The tile-by-tile picture is on TPU programming and performance, section 4 ("a last dimension of 65 is stored as 128", and a matmul on the MXU with the padding drawn). Utilisation below is calculated for every distinct matmul shape in the running example's training step (the 99 dot_general equations of jax.make_jaxpr(jax.value_and_grad(loss_fn)), 33 of them in the forward pass): useful multiply-adds ÷ multiply-adds the padded tiles issue, an upper bound.
      

      Two lessons from the running example. Its output head (D = 128 to a vocabulary of 65) fills 51% of a 128-wide MXU and 13% of a 256-wide one; its attention, with a head dimension of 32, fills 25% and 6%.       4. The mesh meets the torus
      

      The Sharding lab built meshes on 8 simulated devices, where every device is as close as every other. On a real slice the chips sit on a torus (section 1's table), and two neighbours along one ICI link are much cheaper to talk to than two chips five hops apart. So the question a JAX programmer faces is: when I write jax.make_mesh((16, 16), ("data", "model")), which physical chips form each "model" group? JAX answers it in mesh_utils.create_device_mesh, which jax.make_mesh calls. That function only reads each device's coordinates, so it runs on this CPU against mock TPU devices built the way JAX's own tests build them.

      5. Pallas from zero
      

      XLA writes nearly every kernel of a JAX program, and fuses elementwise work into its matmuls well (the Compiler lab shows it). It cannot invent an algorithm, though: it will not turn attention into flash attention (never writing the T × T score matrix to HBM), route tokens to experts with ragged matmuls, or overlap a matmul with a collective by hand. For those you write a kernel, and on JAX that means Pallas. Five ideas are all of it:
      

        

      • Kernel: a Python function over refs, mutable views of buffers in VMEM (or SMEM). You read with x_ref[...] and write with o_ref[...] = ; inside, ordinary jnp code runs on the tile.
        • 

      • Grid: a tuple of loop bounds. The kernel body runs once per grid point; pl.program_id(axis) says which. On a TPU the points run in order, as nested loops (Pallas's TPU docs: "sequentially, in lexicographic order"), unlike a GPU, where Triton's program instances run in parallel.
        • 

      • BlockSpec(block_shape, index_map): for each input and output, the tile size and a function from grid point to block index (which tile). Pallas turns this into the HBM to VMEM copies, double-buffered so the next tile arrives while this one is used, and skips a copy when consecutive grid points ask for the same tile.
        • 

      • Dimension semantics: "parallel" (order does not matter, so the axis may be split across a megacore's two cores) or "arbitrary" (must run in order, as an accumulation must). The default is all arbitrary (lowering.py:778).
        • 

      • Backends: on TPU the kernel lowers to Mosaic, an MLIR dialect that libtpu compiles; on GPU to Triton or to Mosaic GPU; anywhere, interpret=True runs it as ordinary JAX (section 6 shows what that does and does not tell you).
        •

      11. Common mistakes and interview questions
      

      Head dimensions or vocabularies that are not multiples of 128
      Each MXU pass is a full 128 × 128 (or 256 × 256) tile; a head dimension of 32 uses a quarter of it on v5e and a sixteenth on v6e (section 2). Pad vocabularies to a multiple of 128; choose head dimensions of 128.
      

      Expecting small-batch decoding to use the chip
      A 7B-class model decoding one sequence reaches 0.2 to 0.6% of bf16 peak on any generation (section 3): every weight byte is read for one multiply-add. Batch requests until the token count approaches the ridge point.
      

      Mesh axes in the wrong order
      create_device_mesh gives the most physical axes to the last logical axis. Put tensor parallelism last; a mesh written ("model", "data") gives the chatty axis the worst placement.
      

      Forgetting to zero an accumulator, or zeroing it on the wrong grid step
      Pallas outputs start uninitialised; both interpreters fill them with NaN, which is how the bug shows (section 6). Initialise under pl.when(pl.program_id(k_axis) == 0).
      

      Marking a reduction axis "parallel"
      The plain interpreter ignores dimension semantics and gives the right answer; the TPU interpreter, with two cores, gave an error of 0.17 (section 6). Only axes whose output tiles differ may be parallel; Pallas's rule of thumb is "parallel, unless the output window does not vary".
      

      Leaving every axis "arbitrary" on v4 or v5p
      The default semantics are all arbitrary, so a megacore chip runs the kernel on one of its two cores. Mark independent output axes parallel.
      

      Trusting interpret mode for shapes and speed
      It accepted a 100-row block the TPU compiler rejects, and it clamps out-of-range tiles silently. Lower for "tpu" with jax.export, and use InterpretParams() for index checks.
      


      Interview questions
      

      Why do TPUs want shapes in multiples of 128, and what changed with v6e?
      The MXU is a 128 × 128 systolic array (256 × 256 on v6e and TPU7x) holding one weight tile; any dimension is padded up to a whole tile, and the VPU's registers are 8 × 128, so the last two dimensions of arrays and Pallas blocks want multiples of 8 and 128. On v6e the tile is 256, so a model of 128-wide matrices uses a quarter of each pass.
      

      Your 7B model decodes at 60 tokens per second on one v5e. Is something wrong?
      No: that is the memory bound. 13.5 GB of bf16 weights at 819 GB/s is 16 ms per step, 62 tokens per second for a batch of one. Raise the batch (throughput grows almost linearly until about 240 tokens per step, the ridge), quantise the weights, or shard the weights over more chips.
      

      On a 4 × 4 × 4 v5p slice, how would you lay out FSDP 16 and tensor parallelism 4, and why?
      jax.make_mesh((16, 4), ("fsdp", "model")): the model axis, which communicates every layer, gets one whole physical axis with wraparound (neighbours 1 hop apart); FSDP, which gathers weights once per layer and can overlap with compute, gets the other two (y and z), so its all-gathers use two axes of bandwidth. (8, 8) is not placeable without splitting axes.
      

      What does a BlockSpec do that a Triton kernel does by hand?
      It states which tile each grid point needs; Pallas then generates the HBM to VMEM DMAs, double-buffers them so loads overlap compute, and skips copies of a tile that did not change. In Triton you compute pointers and masks and the hardware cache and the compiler's pipelining do the rest.
      

      How do you develop a TPU kernel without a TPU?
      Write it with a jnp reference; run it with interpret=True for correctness, then with interpret=pltpu.InterpretParams(detect_races=True, num_cores_or_threads=2) for index, ordering and race bugs; lower it with jax.export(..., platforms=["tpu"]) to catch tiling errors; then measure on a real chip. All four steps but the last ran on this page.
      

      When is an all-reduce over ICI latency-bound?
      When the bytes per hop are small: the scaling book puts the per-hop floor at about 1 µs, so on v5e (4.5e10 B/s one way) anything under about 45 kB per hop is latency-bound. The running example's 3.3 MB of float32 gradients over 16 chips is not: all-reduced over a 16-chip v5e axis with wraparound it takes about 73 µs, about a sixth of the step's matmul bound (section 3).

      Interview questions
      

      "Should a new JAX project use Flax Linen, Flax NNX, Equinox or Haiku?"
      Flax NNX by default: it is what the Flax team points new users to, and MaxText and Tunix build on it; its stateful modules read like PyTorch. Equinox if you want models to be plain pytrees (common in scientific ML). Linen only to maintain existing code (it is not deprecated, but no longer the recommendation). Haiku is in maintenance mode by DeepMind's own notice since July 2023.
      

      "A tutorial uses jax.pmap. What do you tell the team?"
      pmap has been in maintenance mode since JAX 0.8.0 (October 2025) and since 0.10.0 it is a wrapper over jit(shard_map). Write new code with jax.jit plus NamedSharding (let the compiler place collectives) or jax.shard_map when you want per-device code; the migration guide has drop-in replacements.
      

      "Our team is PyTorch-only. Can we use TPUs?"
      Yes. TorchTPU (a native PyTorch device, torch.compile lowered to XLA) was announced in April 2026 and open-sourced on 20 October 2026; vLLM and SGLang TPU engines are built on it, and TorchTitan trains on it. It is new (one process per chip, about 450 ATen ops, collectives compiled one by one unless marked safe), so expect gaps a mature JAX stack does not have. The honest answer is "yes for serving and training through TorchTPU; port to JAX when you want the most mature TPU path".
      

      "Which open codebase would you read to learn how LLMs are sharded on TPU pods?"
      MaxText: it is Google's maintained reference, expresses every parallelism as a mesh axis, and has MLPerf-tagged configurations. Marin's Levanter is the best non-Google alternative (named tensors, reproducible). T5X, Pax and EasyLM teach the pjit era but are quiet and use deprecated APIs.
      

      "How do you judge whether a library is alive?"
      Look for the owner's notice first (README banners: Haiku, JetStream, XPK, Levanter), then the archived flag, then the date of the last release, and only then commits, reading what they are: T5X, Pax and jmp had commits in 2026 that were automated lint changes. A dependency with one maintainer (Equinox, EasyDeL) is alive but carries bus-factor risk.
