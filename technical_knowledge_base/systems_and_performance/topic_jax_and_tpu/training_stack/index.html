The JAX training stack: Flax NNX, optax, orbax and grain

How the four libraries around JAX turn a model into a training run that compiles once and resumes as the same run, measured on the parent topic's tiny character LM (Apple M1 Pro CPU). Data as of October 2026. Reading: 29 min, plus 20 in closed details.
The idea1 NNX state2 NNX transforms3 Linen, Equinox4 optax5 orbax6 grain7 float168 Metrics9 Full scriptChecklists

A JAX training run is one compiled, pure step function applied to a pytree of state; Flax NNX turns your model object into that pytree, optax is a pair of pure functions over it, orbax writes it to disk, and grain makes the data position a few integers inside it. So the run you resume is the same run only when every piece of state that decides the next step (parameters, optimiser moments and step count, random streams, data position) went into the checkpoint.

One training step: everything that decides step t + 1 is state you can name, save and restore

The graphdef (the model's structure) is the only part not saved: it is rebuilt from your code and keys the compile cache, so the same structure reuses one compiled step. Section numbers on the figure point to where each box is explained; every number on this page was measured on the running example below.

You need: jax.jit, jax.grad, pytrees and PRNG keys (JAX core), and a PyTorch training loop, which the table below maps onto this stack. New terms:

Variable: a typed box holding one array of an NNX module (nnx.Param, nnx.RngKey, ...).
graphdef: the module's structure with no arrays; static and hashable.
filter: a rule selecting Variables by type or path (nnx.Param, ...).
GradientTransformation: optax's (init, update) pair of pure functions.
CheckpointManager: orbax's object that saves, keeps and restores numbered steps.
MapDataset: grain's random-access dataset, record i computed from i and a seed.

1. Flax NNX: where the state lives

jax.jit, jax.grad and jax.vmap transform pure functions of pytrees (nested lists, tuples and dicts whose leaves are arrays). A PyTorch-style model is an object that owns its weights and changes them in place. Flax NNX keeps the object, so model code reads like PyTorch, and converts it to a pytree at every transformation boundary.

Variables: typed boxes for every array

Every array an NNX module owns sits in an nnx.Variable, and the subclass says what kind of state it is. PyTorch has two kinds (parameters the optimiser sees, buffers it does not); NNX has as many as you like, and every API that moves state takes a filter over them.

split: one object becomes a graphdef and states

graphdef, state = nnx.split(model) walks the object graph. The graphdef records every node (module, list, Variable) and every non-array attribute; the state is a pytree of the arrays, keyed by path. nnx.merge(graphdef, state) builds an equivalent object; nnx.update(model, state) writes arrays back into an existing one. With filters, nnx.split(model, f1, f2, ...) returns one state per filter: a filter is a Variable type, a path predicate (nnx.PathContains("kernel")), a combination (nnx.All, nnx.Any, nnx.Not), or ... for "everything else". It is how you say "differentiate the Params only", "decay only the kernels", "vectorise the stacked layers, broadcast the rest".

Randomness is state: nnx.Rngs


PyTorch draws dropout masks from a global generator that advances by itself. JAX has no global generator: a random function takes a key and returns the same numbers for the same key. NNX stores a key and a counter per stream (params, dropout, ...) inside the model; each draw folds the counter into the key and increments it. Measured on the running example with dropout measured:




The third row is a real bug pattern: split once, call a pure jax.jit function with the state and never return the new state. The counter advances inside the trace, the advanced value is dropped, and every step gets the same dropout mask, with no error. nnx.jit avoids it by writing the updated state back into your object; with raw jax.jit return nnx.state(model) and use it next time. model.eval() sets deterministic=True on every Dropout (and use_running_average on BatchNorm), like PyTorch's.

Shared modules: graph mode and tree mode


The running example with its output head tied to the token embedding holds one Embed referenced twice. A pytree cannot express sharing: each leaf appears once. Graph mode tracks object identity, stores the shared array once and restores the sharing on merge; tree mode treats modules as plain pytrees and refuses duplicates ("Duplicate Param"). In flax 0.12.10 graph mode is  by default and graph updates  (, ); every API takes graph=. On the tied model graph mode splits into  leaves and  parameters (the untied count minus the 128 x 65 head) measured.


The defaults are planned to change
Flax's design note FLIP 5310 plans to make tree mode the default; shared modules and nnx.grad's Params-only default then go away. Code that ties weights by sharing a module, or relies on that default, should pin nnx.set_graph_mode(True) or use nnx.compat.*. Not yet the default at 0.12.10 measured.


FLIP 5310 in its own words, and the tree-mode error on the tied model
"Tree Mode NNX" (dated Mar 4, 2026, in the pinned clone) says: "The goal will be to have the default value for nnx_graph_mode and nnx_graph_updates to be set to False" (). Under tree mode, shared references, prefix filters (StateAxes, DiffState, StateSharding) and structure changes inside transforms go away, and nnx.grad returns gradients of the input's own type ().
Pin graph mode, or tie by computing the head from the embedding's array instead of sharing the module.






2. NNX transformations: jit, grad, the optimiser, scan, sharding


nnx.jit: what retraces, what is written back


nnx.jit(f) is jax.jit with a wrapper: it splits every module argument into graphdef and state, passes the graphdefs as static (hashed into the cache key) and the states as traced arrays, merges them back into objects inside, and after the call copies changed Variables back into your objects. So a Python side effect runs only while tracing, and a change to the module's structure retraces. The running example with a custom StepCount Variable incremented on every call measured:


@nnx.jit
def step_count(m, x):
    TR["n"] += 1                   # Python side effect: runs only when tracing
    return m(x).mean()




From src/runs/ts_nnx.py (E5). "Traces" counts how many times Python ran the body; "StepCount" is the Variable incremented inside the compiled program and written back. Setting h to the value it already had did not retrace (the graphdef compares equal); one added Param took the trace count from 1 to 2, a new batch shape to 3.


In a training loop the danger is code that adds, removes or re-creates a submodule or a Python attribute every step: each step then compiles from scratch. Keep per-step values in Variables or pass them as arguments. The root's Compiler lab tab measures what a recompile costs; XLA and compilation shows how to find the cause at scale. Source: .



nnx.grad and nnx.Optimizer


nnx.grad(loss_fn)(model, x, y) differentiates with respect to the model's nnx.Param leaves only, because its default argnums is nnx.DiffState(0, nnx.Param): on the counter model the gradient was a State of 69 Param leaves, without the StepCount measured. A narrower filter differentiates a subset: nnx.DiffState(0, nnx.All(nnx.Param, nnx.PathContains("attn"))) gave 32 leaves (the 4 x 8 attention weights and biases). The PyTorch counterpart is requires_grad_(False) on everything else, but nothing is mutated and the choice is per call (source ; tree mode will change this default, section 1).


nnx.Optimizer(model, tx, wrt=nnx.Param) runs tx.init on the filtered state and stores the result as Variables, so the optimiser passes through nnx.jit and into a checkpoint like a model; opt.update(model, grads) calls tx.update and writes the new parameters into the model. Since Flax 0.11 it holds no reference to the model (which is why update takes it) and wrt is required. For the AdamW chain its state has 141 leaves and 1,652,739 numbers measured: two moment trees of 826,368 each plus step counters.

Scan over layers: one traced block instead of four


A Python for loop over layers is unrolled when traced: 4 blocks give 4 copies of the block in the jaxpr, 48 give 48, and compile time grows with depth. Create the blocks with nnx.vmap over a split of the Rngs, so every parameter gets a leading layer axis (a [128, 512] kernel becomes [4, 128, 512]); run them with nnx.scan, which lowers to one lax.scan whose body is traced once. This is the NNX spelling of MaxText's scan_layers and of Linen's nn.scan.


@nnx.split_rngs(splits=cfg["n_layers"])
@nnx.vmap(in_axes=(0,), out_axes=0)
def make_blocks(r):
    return MN.Block(cfg, rngs=r)          # the running example's Block, unchanged
self.blocks = make_blocks(rngs)          # every Param now has a leading axis of 4

@nnx.scan(in_axes=(nnx.Carry, 0), out_axes=nnx.Carry)
def body(x, blk):
    return blk(x)
x = body(x, self.blocks)

Sharding annotations on parameters


NNX attaches a layout to each parameter at creation: wrap an initialiser with nnx.with_partitioning(init, ("embed", "mlp")), where the names are logical axes of the weight, and map logical names to mesh axes once with nnx.logical_axis_rules. Under jax.set_mesh(mesh) the parameter is born sharded ("eager sharding", on by default in 0.12.10: ). The optimiser's moment trees inherit each parameter's sharding, so optimiser memory is split exactly like the weights; the compiler inserts the collectives (12 all-reduces in one training step of the layout below) measured. Choosing the mesh and the rules for a real model is Sharding and scale's subject; MaxText's rules are on JAX LLM codebases, section 3.

Two habits carry over. In Linen code look for init/apply, the collection names, mutable= and rngs= at every call site: the train step carries params, batch_stats and the optimiser state as three separate trees (often bundled in flax.training.train_state.TrainState). In Equinox code the model is itself the pytree, so look for the eqx.filter_* transforms. nnx.bridge.ToNNX and ToLinen wrap one in the other, which is how a codebase migrates one module at a time (Flax's bridge guide; source ).


Linen in detail, with the errors you meet (measured)



A Linen module is a frozen dataclass of hyperparameters. variables = model.init(rngs, x) runs it once to create every array, grouped into collections; model.apply(variables, x) runs it as a pure function. A block with Dense, BatchNorm, Dropout and sow (a test module in src/runs/ts_linen_eqx.py):


class LBlock(nn.Module):
    d_ff: int = 512
    @nn.compact
    def __call__(self, x, train: bool):
        h = nn.Dense(self.d_ff)(x)                 # input width read from x at init time
        h = nn.BatchNorm(use_running_average=not train, momentum=0.9)(h)
        h = nn.gelu(h, approximate=False)
        self.sow("intermediates", "hidden_mean", h.mean())
        h = nn.Dropout(0.1, deterministic=not train)(h)
        return nn.Dense(x.shape[-1])(h)

4. optax, transformation by transformation


An optax GradientTransformation is a named tuple of two pure functions: init(params) -> state and update(grads, state, params) -> (updates, new_state) (). optax.chain(t1, t2, ...) feeds each one's output into the next and keeps a tuple of their states (). Every optimiser you know is a chain: optax.adamw is scale_by_adam, then add_decayed_weights, then scale_by_learning_rate (). Because the state is just more arrays, it is jitted, sharded and checkpointed like the model. The algorithms themselves (why Adam, AdamW, Lion, Muon, which schedule) are Optimisers and learning-rate schedulers's; this section is how optax builds and runs them.



One real step through the running example's chain


The running example uses chain(clip_by_global_norm(1.0), adamw(lr_schedule, b1=0.9, b2=0.95, eps=1e-8, weight_decay=0.1, mask=decay_mask)). A script recomputes every stage by hand on the real gradients of the first 12 steps and checks it against tx.update: the largest difference was 7.3e-11 measured, float rounding in the bias correction. The four things PyTorch does by mutation, done as transformations


    

  • Changing a hyperparameter mid-run: inject_hyperparams. An optax optimiser closes over its hyperparameters, so they are constants in the compiled step; optax.inject_hyperparams(optax.adamw)(learning_rate=1e-3, ...) moves them into the state as traced arrays you can overwrite (). Changing it four times traced the step once; rebuilding optax.adamw(lr) with a new Python float traced it once per value measured. A schedule needs neither: it is evaluated inside the step from the step count.
    • 

  • Parameter groups: masks and optax.partition. A mask (a pytree of booleans, or a function returning one) switches one transformation per leaf (adamw(mask=...) decays only masked leaves); optax.partition sends each leaf to a different optimiser by label (; optax.multi_transform is now its backwards-compatible alias, ). Freezing with set_to_zero() also saves memory: it keeps no moments.
    • 

  • Gradient accumulation: optax.MultiSteps(tx, every_k_schedule=4). For three calls it adds the gradient to an accumulator and returns zero updates; on the fourth it passes the mean to tx (). Cost: one more parameter-sized accumulator. Trap: the step count and every schedule now advance once per four calls, so count real updates (state.gradient_step).
    • 

  • Skipping bad steps: optax.apply_if_finite(tx, max_consecutive_errors=3). If any gradient is NaN or infinite it returns zero updates and leaves the inner state untouched (); after max_consecutive_errors bad steps in a row it applies the update anyway, so persistent NaNs still surface. It is the JAX counterpart of the skip that PyTorch's GradScaler performs on overflow.
    •

Lion and Muon in optax


Both are in optax (Lion in core, Muon in optax.contrib, where optax keeps newer optimisers alongside schedule-free, Prodigy and SOAP-style ones); how they work is on the optimisers page. One optax-specific trap matters in practice:


optax's Muon applies to every 2-D parameter by default
By default optax.contrib.muon labels every two-dimensional leaf "muon" and everything else "adam" (). In the running example that includes the token and position embeddings and the output head, which Muon's authors keep on AdamW. Pass muon_weight_dimension_numbers returning None for them.


Lion and Muon measured here: Lion's sign step, Muon's Newton-Schulz on a real gradient, and 300 steps with four optimisers


Lion (Chen et al., 2023) keeps one moment and steps by its sign: every coordinate moves by exactly the learning rate. On one step at lr 1e-4, 99.92% of the updates had magnitude 1e-4 and the rest were exact zeros (zero gradients) measured. Its state is one tree (826,369 numbers, half of AdamW's), its default weight decay is 1e-3 (), and its authors recommend a learning rate 3 to 10 times smaller and decay 3 to 10 times larger than AdamW's (arXiv 2302.06675, section 5).


Muon (Jordan, 2024) applies momentum, then replaces each weight matrix's update by an approximately orthogonal one (the same singular vectors, singular values pushed towards 1) through five iterations of a quintic Newton-Schulz map with optax's coefficients (3.4445, −4.7750, 2.0315) (, ). On the running example's real first-layer MLP gradient ([128, 512]) the singular values spanned a ratio of 1.2e8; after normalisation and five iterations 122 of the 128 ended between 0.5 and 1.20, close to the 0.5 to 1.5 band the optax docstring describes, while the smallest stayed near zero (5.7e-6): a direction with essentially no gradient is not amplified in five iterations.

5. orbax: checkpoints that resume the same run


A run is preempted at step 80. To continue the same run, not a similar one, you need everything that decides step 81: the parameters, the optimiser's moments and step count (the schedule reads it), the random streams (dropout) and the data loader's position. PyTorch scatters these across model.state_dict(), optimizer.state_dict(), scheduler.state_dict(), the global RNG states and a loader with no state; in JAX all of them are pytrees, and orbax saves pytrees.

Reading the signatures. Restoring everything gives an identical run, every array bit for bit. A fresh data iterator re-reads batches 0, 1, 2, so the very first resumed loss is off (by 0.015). The step count is in the optimiser state here (opt.step), so the schedule followed it.



How a CheckpointManager save works


    

  • Items. One checkpoint holds named items, each with a handler: ocp.args.Composite(model=StandardSave(nnx.state(model)), opt=StandardSave(nnx.state(opt, nnx.Not(nnx.Param))), data=grain.checkpoint.CheckpointSave(it), meta=JsonSave({...})), each a directory under <dir>/<step>/.
    • 

  • Async. enable_async_checkpointing defaults to True (): save() copies the arrays to host memory and returns while a background thread writes (call 0.14 s, write done at 0.36 s here, rough). Call wait_until_finished() before exiting; orbax ignores unfinished checkpoints (finished ones carry commit_success.txt files).
    • 

  • Sharded. Arrays go to TensorStore in OCDBT format, one key-value store per process (ocdbt.process_0/), each process writing only the shards it owns: no gather to rank 0, unlike a naive torch.save; the PyTorch counterpart is torch.distributed.checkpoint.
    • 

  • Restore into a target. You pass a pytree with the shapes, dtypes and shardings you want (a freshly built model's state, or an abstract one from nnx.eval_shape) and orbax reads each shard into place; the layout on disk does not constrain the layout you restore to.
    • 

  • Which checkpoints to keep. In orbax-checkpoint 0.12.7, max_to_keep, keep_period and best_fn are documented as "deprecated, do not use. use preservation_policy instead" (). The replacements compose: save_decision_policy=FixedIntervalPolicy(100) and preservation_policy=AnyPreservationPolicy([LatestN(1), BestN(get_metric_fn=..., reverse=True, n=2)]). BestN sorts by the metric and keeps the last n (), so for a loss you need reverse=True, or it keeps the two worst (the old best_mode="min" was translated to exactly that: ).
    • 



Found here: the policy API alone does not save the metrics
In orbax-checkpoint 0.12.7 a CheckpointManager writes the metrics you pass to save() only when best_fn is set (the _track_best check at ). With preservation_policy=...BestN(...) and no best_fn, ranking works inside one process, but after a restart the old checkpoints have no metrics, BestN keeps checkpoints without metrics by default, and they are never deleted. With section 9's script, the uninterrupted run kept steps 300, 400; the preempted and restarted run kept 100, 200, 300, 400 measured. Emergency checkpointing and orbax's new API (read, not run)
On a large TPU job the cost of a checkpoint is the write to remote storage (Cloud Storage), so you checkpoint rarely and lose up to an interval of work on each failure. orbax's experimental.emergency.CheckpointManager keeps two tiers: frequent local checkpoints to fast local storage (RAM disk) on each host (default save_interval_steps 10: ) and rare persistent ones to remote storage (default 1000: ); after a failure, a slice that still holds a complete local checkpoint broadcasts it to the replaced hosts, and the persistent tier is the fallback (docstring at ). The module is marked "experimental; do not use without specific approval" (). Not run here: it needs several hosts and slices. orbax also ships a new API, orbax.checkpoint.experimental.v1 (), still under experimental at 0.12.7; the code on this page uses the stable CheckpointManager, as Tunix does. MaxText has moved to the v1 API (ocp.training.Checkpointer, on JAX LLM codebases, section 5).






6. grain: a data pipeline that is a function of the index


For a resumed run to be the same run, the loader must produce the same batches in the same order and be able to jump to the middle of an epoch; on many hosts, each host must read a disjoint part of the data, deterministically. PyTorch's DataLoader gets order from a sampler in the main process, randomness inside __getitem__ from per-worker generators, and has no position to save.


How grain works. A MapDataset is random-access: ds[i] computes record i from a source (anything with __len__ and __getitem__, such as an ArrayRecord file or a numpy array) and a chain of transformations. shuffle(seed) is a fixed permutation of indices (); random_map(f, seed) hands f a numpy generator seeded from the seed and the record's index (); repeat() reseeds every random transformation per epoch, so each epoch is shuffled differently but deterministically (). to_iter_dataset() turns it into an iterator, read by 16 threads by default (), and mp_prefetch adds worker processes. Because record i depends only on (i, seed, epoch), the iterator's whole state is a few integers. The older grain.DataLoader(data_source, sampler, operations, worker_count) API does the same with an IndexSampler.


On the running example's 7,781 windows measured (src/runs/ts_grain.py): record 100,000 of shuffle(0).repeat() (epoch 12) is window 3986, computed with no iteration, and a random crop drawn in random_map was identical for 192 records with 0 and 4 worker processes. The same crop drawn with torch.randint in a PyTorch __getitem__ agreed between 0 and 2 workers for only 12.5% of 128 records (chance is 1 in 8), because torch seeds each worker differently (src/runs/ts_torch_loader.py, torch 2.14.1).



Where you batch decides whether the worker count matters


mp_prefetch gives each worker process a slice of the MapDataset's elements and interleaves their outputs; anything after to_iter_dataset() runs inside each worker on its own slice. The same pipeline written four ways:

7. float16 and loss scaling


On TPU use bfloat16: it has float32's 8 exponent bits, so its range is float32's and it needs no loss scaling (the root's Training lab measured bf16 compute with a float32 master copy ending within 0.001 of float32). float16 (5 exponent bits, smallest normal 6.10e-5, largest 65,504) is still what many GPU recipes use, and gradients are small: the running example's float32 gradients at initialisation have a median magnitude of 1.1e-3, and many land among float16's subnormals. Loss scaling multiplies the loss by S before the backward pass and divides the gradients by S in float32 before the optimiser; dynamic loss scaling starts S high, halves it and skips the step whenever a gradient is not finite, and doubles it after a run of good steps. In JAX the reference implementation is jmp's DynamicLossScale (last released 2023), a small pytree carried through the jitted step; PyTorch's torch.amp.GradScaler is the same algorithm. Formats, subnormals and a loss-scale slider are taught on Numerical computing for ML (section 9); mixed precision across frameworks on Quantization and Precision.


Measured here measured: at S = 1 the median relative error of float16 gradients was about ten times that at S = 256; at S = 224 almost every gradient overflowed. Over 200 steps with float32 master weights, a static scale of 212 stayed on top of float32 (validation loss 2.36050 against 2.36054); no scaling wandered off the float32 trajectory (2.3319: not worse here, a different run); the dynamic scale started at 215, skipped the overflowing steps 111 and 144, halving each time, and ended at 213.

@jax.jit
def step(p, s, ls, x, y):
    def f(pc):
        logits = MJ.apply(jax.tree.map(lambda a: a.astype(jnp.float16), pc), x, CFG).astype(jnp.float32)
        return ls.scale(optax.softmax_cross_entropy_with_integer_labels(logits, y).mean())
    l, g = jax.value_and_grad(f)(p)          # float32 master weights; float16 inside
    g = ls.unscale(g)
    finite = jmp.all_finite(g)
    u, s2 = tx.update(g, s, p)
    p, s = jmp.select_tree(finite, (optax.apply_updates(p, u), s2), (p, s))   # skip the step on overflow
    return p, s, ls.adjust(finite), ls.unscale(l), finite

8. Evaluation loops and metrics


loss.item() every step forces the host to wait for the device, serialising a pipeline that JAX runs asynchronously (dispatch returns before the device finishes). So accumulate metrics on the device, inside the compiled step, and read them every N steps. nnx.MultiMetric(loss=nnx.metrics.Average("loss"), accuracy=nnx.metrics.Accuracy()) is a module whose state is running sums in Variables; metrics.update(loss=..., logits=..., labels=...) inside an nnx.jit step adds to them on device; metrics.compute() and reset() on the host every N steps are the only syncs (source ; also Welford for mean and variance). An evaluation loop is the same with a second MultiMetric and an eval_step that does not touch the optimiser; call model.eval() first if the model has dropout or BatchNorm. clu (Google's CommonLoopUtils), which older Flax code uses for metrics and periodic actions, last released 0.0.12 on 2024-04-10 (PyPI, read 2026-10-15) published; for NNX code nnx.metrics is enough.

Checklists and provenance


Pre-flight checklist: the mistakes that give a different run with no error
    

  • State and RNG. A pure jax.jit step that does not return nnx.state(model) reuses the same dropout mask every step (section 1). Filters must end with ... on a model with any non-Param state. A module shared twice is a "Duplicate Param" in tree mode.
    • 

  • Recompiles. Adding an attribute, rebuilding a submodule or flipping a Python flag stored on the module changes the graphdef and recompiles (section 2); so does rebuilding the optimiser with a new Python learning rate (one compile per value, section 4).
    • 

  • Linen and Equinox. Every training apply needs mutable=["batch_stats"] and rngs={"dropout": key}, and you merge the returned updates; plain jax.jit on an Equinox model holding a function fails: use eqx.filter_jit (section 3).
    • 

  • optax. Under MultiSteps a schedule written for 10,000 updates and a loop of 10,000 micro-batches with k = 4 reaches only a quarter of the schedule. optax.contrib.muon orthogonalises embeddings and the head unless told not to (section 4).
    • 

  • orbax. Save model state (with RNG), optimiser state and the data iterator in one checkpoint; parameters alone silently restart warmup, zero the moments, re-read the first batches and repeat the masks. BestN for a loss needs reverse=True; with 0.12.7 set best_fn too or metrics are not persisted; call wait_until_finished() before exiting. Expect bitwise resumes only into the saved shardings (section 5).
    • 

  • grain. Batch in the MapDataset before to_iter_dataset(), keep filters after mp_prefetch, and resume with the same worker count (section 6).
    • 

  • Sharding. With eager sharding (default in 0.12) an annotated model needs a mesh in scope: "An auto mesh context or metadata is required if creating a variable with annotation out_sharding=..." (section 2).
    • 

  • Metrics. No loss.item() per step; accumulate with nnx.metrics and read every N steps (section 8).

Interview rehearsal: two questions that combine the sections


Why does NNX store RNG keys in the model, and what breaks if you forget them in a checkpoint?
JAX has no global generator; a key plus a counter per stream makes randomness explicit state that transforms can carry and checkpoints can save. Without it a resumed run repeats the dropout masks of the first steps: a different run, silently.


Your resumed run's loss differs from the original from the first step. What do you check?
If the first resumed loss differs, the forward pass saw different inputs or weights: the data iterator position, or the RNG streams. If the first loss matches and then drifts: the optimiser state (moments, step count, schedule). If it matches for many steps then drifts very slowly: a different compiled program changing reduction order: another mesh, or the same mesh with the state restored into its annotated shardings rather than the ones the compiler had given it (section 5).


Design: design the checkpointing for a 2-week run of a 70B model on a TPU pod that is preempted a few times a day.
Save one checkpoint item for model state, one for optimiser state, one for each host's data iterator and a JSON item for the step and config; async, sharded, each host writing its own shards (orbax OCDBT). Two tiers: local checkpoints every few minutes of work to host RAM disk, replicated across slices so a replaced slice can be refilled, and persistent ones to Cloud Storage every hour or so (orbax's emergency manager is built for this, still experimental); keep the latest plus a few by evaluation loss, and some at fixed periods for analysis. Make data order a function of (seed, step) and keep the worker count fixed. Measure: time the save call blocks the step, write bandwidth, restore time, and test a real kill and resume in staging, comparing losses for 100 steps. Restoring onto a different slice shape works (restore into the new shardings) but will not be bitwise.
