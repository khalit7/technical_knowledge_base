5. orbax: checkpoints that resume the same run

The problem. A run is preempted at step 80. To continue the same run, not a similar one, you need everything that decides step 81: the parameters, the optimiser's moments and step count (the schedule reads it), the random streams (dropout), and the data loader's position. PyTorch scatters these across model.state_dict(), optimizer.state_dict(), scheduler.state_dict(), the global RNG states and a loader that has no state; JAX puts all of them in pytrees, and orbax saves pytrees.

How a CheckpointManager save works

  • Items. One checkpoint holds named items, each with a handler: ocp.args.Composite(model=StandardSave(nnx.state(model)), opt=StandardSave(nnx.state(opt, nnx.Not(nnx.Param))), data=grain.checkpoint.CheckpointSave(it), meta=JsonSave({...})). Each item is a directory under <dir>/<step>/.
  • Async. enable_async_checkpointing defaults to True (): save() copies the arrays to host memory and returns while a background thread writes. Measured on the running example with dropout: the call returned after s and the write finished at s measured (rough timing). wait_until_finished() before exiting, or the last checkpoint is incomplete; orbax marks a finished checkpoint (here with commit_success.txt files) and ignores unfinished ones.
  • Sharded. Arrays go to TensorStore in OCDBT format, one key-value store per process (ocdbt.process_0/), each process writing only the shards it owns. No gather to rank 0, unlike a naive torch.save; the PyTorch counterpart is torch.distributed.checkpoint.
  • Restore into a target. You pass a pytree with the shapes, dtypes and shardings you want (a freshly built model's state, or an abstract one from nnx.eval_shape) and orbax reads each shard into place. The layout on disk does not constrain the layout you restore to (measured below).
  • Which checkpoints to keep. In orbax-checkpoint 0.12.7, max_to_keep, keep_period and best_fn on CheckpointManagerOptions are documented as "deprecated, do not use. use preservation_policy instead" (). The replacements compose: save_decision_policy=FixedIntervalPolicy(100) and preservation_policy=AnyPreservationPolicy([LatestN(1), BestN(get_metric_fn=..., reverse=True, n=2)]). Watch the direction: BestN sorts by the metric and keeps the last n (), so for a loss, where smaller is better, you need reverse=True (the old best_mode="min" was translated to exactly that: ).
Found here: the policy API alone does not save the metrics
In orbax-checkpoint 0.12.7 a CheckpointManager writes the metrics you pass to save() only when best_fn is set (the _track_best check at ). With preservation_policy=...BestN(...) and no best_fn, ranking works inside one process, but after a restart the old checkpoints have no metrics, BestN keeps checkpoints without metrics by default, and they are never deleted. Measured with section 9's script: the uninterrupted run kept steps ; the preempted and restarted run kept measured. Setting the deprecated best_fn and best_mode="min" as well makes the metrics persist (section 9 runs that way).

Reading the table. Restoring everything gives an identical run: every array equal bit for bit, every loss equal. Each omission produces a different run with no error, each with its own signature: a fresh data iterator re-reads batches 0, 1, 2 (the first resumed loss is already off by ); a fresh optimiser gives the same first loss (the forward pass does not read it) but restarts warmup and zeroes the moments, so the curve then drifts; fresh RNG streams repeat the dropout masks of steps 0 onward, a tiny first difference () that compounds. "Parameters only", which is what torch.save(model.state_dict()) keeps, combines all three. The step count is in the optimiser state here (opt.step), so the schedule followed it.

Predict. You restore parameters and optimiser state but build a new grain iterator. Is the resumed loss at step 80 equal to the uninterrupted run's?
No: the new iterator starts at batch 0, so step 80 trains on the batch that step 0 saw. The forward pass at step 80 already sees different data; the loss is off by .

Restoring onto a different mesh

On 8 simulated devices the running example, sharded on a (data 2, model 4) mesh with the annotations of section 2, trained 20 steps and was saved; it was then restored five ways (four layouts, and the same mesh again with the shardings the state had when saved) and trained to step 40 (src/runs/ts_ckpt_mesh.py) measured:

Restore is exact on every layout: the arrays that come back are bit-identical to the ones saved, whatever the new sharding. Continuing is bit-identical only in the last row, and the reason is a finding worth knowing. The model's annotations replicate the biases (spec P()), but after one jitted training step of the parameter and optimiser leaves came back with a different sharding chosen by the compiler (the fc1 bias, for example, went from P() to P('model',)) measured. A freshly built model on the same mesh has the annotated shardings, so its first step is a different compiled program, which sums partial results in a different order: the run drifts from step 21 by float rounding (up to by step 40). Restoring into the shardings the state actually had when it was saved (the last row: targets built from the saved arrays' shardings) gives the same program and a bit-identical continuation. The same 20 steps run three times on one mesh were identical every time (src/runs/ts_mesh_det.py), so nothing here is nondeterminism. Two lessons: pin the state's shardings in the train step (out_shardings or jax.lax.with_sharding_constraint on the new state) so they never drift, and when the mesh really changes, compare losses, not bits.

Emergency checkpointing (read, not run)

On a large TPU job the cost of a checkpoint is the write to remote storage (Cloud Storage), so you checkpoint rarely and lose up to an interval of work on each failure. orbax's experimental.emergency.CheckpointManager keeps two tiers: frequent local checkpoints to fast local storage (RAM disk) on each host (default save_interval_steps 10: ) and rare persistent ones to remote storage (default 1000: ); after a failure, a slice that still holds a complete local checkpoint broadcasts it to the replaced hosts, and the persistent tier is the fallback (docstring at ). The module is marked "experimental; do not use without specific approval" (). Not run here: it needs several hosts and slices. orbax also ships a new API, orbax.checkpoint.experimental.v1 (), still under experimental at 0.12.7; the code on this page uses the stable CheckpointManager that MaxText and Tunix use.
