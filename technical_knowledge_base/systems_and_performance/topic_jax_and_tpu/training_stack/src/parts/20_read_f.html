5. orbax: checkpoints that resume the same run

A run is preempted at step 80. To continue the same run, not a similar one, you need everything that decides step 81: the parameters, the optimiser's moments and step count (the schedule reads it), the random streams (dropout) and the data loader's position. PyTorch scatters these across model.state_dict(), optimizer.state_dict(), scheduler.state_dict(), the global RNG states and a loader with no state; in JAX all of them are pytrees, and orbax saves pytrees.

Reading the signatures. Restoring everything gives an identical run, every array bit for bit. A fresh data iterator re-reads batches 0, 1, 2, so the very first resumed loss is off (by 0.015). A fresh optimiser gives the same first loss (the forward pass does not read it) but restarts warmup and zeroes the moments, so the curve then drifts. Fresh RNG streams repeat the dropout masks of steps 0 onward: a tiny first difference (1.9e-4) that compounds. "Params only", what torch.save(model.state_dict()) keeps, combines all three. The step count is in the optimiser state here (opt.step), so the schedule followed it.

How a CheckpointManager save works

  • Items. One checkpoint holds named items, each with a handler: ocp.args.Composite(model=StandardSave(nnx.state(model)), opt=StandardSave(nnx.state(opt, nnx.Not(nnx.Param))), data=grain.checkpoint.CheckpointSave(it), meta=JsonSave({...})), each a directory under <dir>/<step>/.
  • Async. enable_async_checkpointing defaults to True (): save() copies the arrays to host memory and returns while a background thread writes (call 0.14 s, write done at 0.36 s here, rough). Call wait_until_finished() before exiting; orbax ignores unfinished checkpoints (finished ones carry commit_success.txt files).
  • Sharded. Arrays go to TensorStore in OCDBT format, one key-value store per process (ocdbt.process_0/), each process writing only the shards it owns: no gather to rank 0, unlike a naive torch.save; the PyTorch counterpart is torch.distributed.checkpoint.
  • Restore into a target. You pass a pytree with the shapes, dtypes and shardings you want (a freshly built model's state, or an abstract one from nnx.eval_shape) and orbax reads each shard into place; the layout on disk does not constrain the layout you restore to.
  • Which checkpoints to keep. In orbax-checkpoint 0.12.7, max_to_keep, keep_period and best_fn are documented as "deprecated, do not use. use preservation_policy instead" (). The replacements compose: save_decision_policy=FixedIntervalPolicy(100) and preservation_policy=AnyPreservationPolicy([LatestN(1), BestN(get_metric_fn=..., reverse=True, n=2)]). BestN sorts by the metric and keeps the last n (), so for a loss you need reverse=True, or it keeps the two worst (the old best_mode="min" was translated to exactly that: ).
Found here: the policy API alone does not save the metrics
In orbax-checkpoint 0.12.7 a CheckpointManager writes the metrics you pass to save() only when best_fn is set (the _track_best check at ). With preservation_policy=...BestN(...) and no best_fn, ranking works inside one process, but after a restart the old checkpoints have no metrics, BestN keeps checkpoints without metrics by default, and they are never deleted. With section 9's script, the uninterrupted run kept steps 300, 400; the preempted and restarted run kept 100, 200, 300, 400 measured. Setting the deprecated best_fn and best_mode="min" as well makes the metrics persist (section 9 runs that way).

Restoring onto a different mesh

Saved sharded on a (data 2, model 4) mesh of 8 simulated devices at step 20 and restored onto four layouts, restore was exact on every layout, but continuing was bit-identical only when restored into the shardings the state had when saved; otherwise, even on the same mesh, the run drifted by float rounding (up to 3.4e-6 in a parameter by step 40) measured. The cause: after one jitted step the compiler had re-sharded 81 of the 210 parameter and optimiser leaves, so a freshly built model compiles a different step that sums in a different order. Pin the state's shardings in the train step (out_shardings or jax.lax.with_sharding_constraint), and when the mesh really changes, compare losses, not bits.

The five restores, layout by layout, and why this is not nondeterminism

The running example was restored onto the same mesh, (8 x 1), (1 x 8) and one device, plus the same mesh into the saved shardings, and trained to step 40 (src/runs/ts_ckpt_mesh.py). Emergency checkpointing and orbax's new API (read, not run)

On a large TPU job the cost of a checkpoint is the write to remote storage (Cloud Storage), so you checkpoint rarely and lose up to an interval of work on each failure. orbax's experimental.emergency.CheckpointManager keeps two tiers: frequent local checkpoints to fast local storage (RAM disk) on each host (default save_interval_steps 10: ) and rare persistent ones to remote storage (default 1000: ); after a failure, a slice that still holds a complete local checkpoint broadcasts it to the replaced hosts, and the persistent tier is the fallback (docstring at ). The module is marked "experimental; do not use without specific approval" (). Not run here: it needs several hosts and slices. orbax also ships a new API, orbax.checkpoint.experimental.v1 (), still under experimental at 0.12.7; the code on this page uses the stable CheckpointManager, as Tunix does.
