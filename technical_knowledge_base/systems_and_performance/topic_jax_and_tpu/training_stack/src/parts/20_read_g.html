6. grain: a data pipeline that is a function of the index

For a resumed run to be the same run, the loader must produce the same batches in the same order and be able to jump to the middle of an epoch; on many hosts, each host must read a disjoint part of the data, deterministically. PyTorch's DataLoader gets order from a sampler in the main process, randomness inside __getitem__ from per-worker generators, and has no position to save.

How grain works. A MapDataset is random-access: ds[i] computes record i from a source (anything with __len__ and __getitem__, such as an ArrayRecord file or a numpy array) and a chain of transformations. shuffle(seed) is a fixed permutation of indices (); random_map(f, seed) hands f a numpy generator seeded from the seed and the record's index (); repeat() reseeds every random transformation per epoch, so each epoch is shuffled differently but deterministically (). to_iter_dataset() turns it into an iterator, read by 16 threads by default (), and mp_prefetch adds worker processes. Because record i depends only on (i, seed, epoch), the iterator's whole state is a few integers. The older grain.DataLoader(data_source, sampler, operations, worker_count) API does the same with an IndexSampler.

On the running example's 7,781 windows measured (src/runs/ts_grain.py): record 100,000 of shuffle(0).repeat() (epoch 12) is window 3986, computed with no iteration, and a random crop drawn in random_map was identical for 192 records with 0 and 4 worker processes. The same crop drawn with torch.randint in a PyTorch __getitem__ agreed between 0 and 2 workers for only 12.5% of 128 records (chance is 1 in 8), because torch seeds each worker differently (src/runs/ts_torch_loader.py, torch 2.14.1).

Batching in the MapDataset makes each element a whole batch, so workers share out batches and the stream does not depend on the worker count. Batching after to_iter_dataset() but before mp_prefetch makes each worker batch its own slice: batch 0 becomes records 0, 2, 4, ... of the shuffled order with 2 workers. A filter (many-to-one) before mp_prefetch also changes the stream, as grain's docstring warns (). The output stays deterministic for a fixed worker count (the DataLoader run with 2 workers repeated exactly); what is lost is elasticity: change the worker count between save and resume and you get a different run.

Checkpointing the iterator, and many hosts

With 2 worker processes the iterator state records per-worker positions; a fresh 2-worker iterator given the state after 7 batches produced the same next 3 batches, but loading it into a 0-worker pipeline raised KeyError: 'next_index' measured. So resume with the same worker count. orbax writes the state through grain.checkpoint.CheckpointSave/CheckpointRestore as a small JSON item per process. On a multi-host slice each host reads its own shard: IndexSampler(shard_options=ShardOptions(shard_index=k, shard_count=2)) gave two simulated hosts 3,888 records each, disjoint, together 7,776 of 7,781 (the remainder dropped so shards are equal) measured. In real use grain.sharding.ShardByJaxProcess() fills in jax.process_index() and jax.process_count(), and jax.make_array_from_process_local_data assembles the global batch ({{Sharding and scale|n:3c65c17b0d0d8125b084e6720cc66b3d}}); with the dataset API, ds[k::n] slices the same way.

Threads, processes and speed; grain against the alternatives


Two kinds of slow transformation behave differently. With a 2 ms per-record map (rough timings, load average about 40): a map that waits (sleep, like reading a file) ran at  batches per second (115) with no worker processes, against the 15.6 a serial loop would allow (1 / (32 x 2 ms) derived), because the default 16 read threads overlap the waits; a map that computes in Python (a busy loop holding the GIL) ran at , the serial rate, since threads cannot run Python in parallel. Worker processes are the fix for the second kind; on this heavily loaded shared machine their speed-up was not measurable reliably ( and  batches per second with 2 and 4 workers), so no claim is made about it. On a TPU host: profile the input pipeline (xprof's input pipeline analyser) and add workers until the device never waits.
