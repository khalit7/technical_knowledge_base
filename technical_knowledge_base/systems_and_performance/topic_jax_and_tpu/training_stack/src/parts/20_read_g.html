6. grain: a data pipeline that is a function of the index

The problem. For a resumed run to be the same run, the loader must produce the same batches in the same order, and be able to jump to the middle of an epoch. For a multi-host run, each host must read a disjoint part of the data, deterministically. PyTorch's DataLoader gets order from a sampler in the main process, randomness inside __getitem__ from per-worker generators, and has no position to save.

How grain works. A MapDataset is random-access: ds[i] computes record i from a source (anything with __len__ and __getitem__, such as an ArrayRecord file or a numpy array) and a chain of transformations. shuffle(seed) is a fixed permutation of indices (); random_map(f, seed) hands f a numpy generator seeded from the seed and the record's index (); repeat() reseeds every random transformation per epoch, so each epoch is shuffled differently but deterministically (). to_iter_dataset() turns it into an iterator, read by 16 threads by default (), and mp_prefetch adds worker processes. Because record i depends only on (i, seed, epoch), the iterator's state is a few integers. The older grain.DataLoader(data_source, sampler, operations, worker_count) API does the same with an IndexSampler.

Where you batch decides whether the worker count matters

mp_prefetch gives each worker process a slice of the MapDataset's elements and interleaves their outputs; anything after to_iter_dataset() runs inside each worker on its own slice. So the same pipeline written four ways behaved differently with 0, 2 and 4 workers measured:

Batching in the MapDataset makes each element a whole batch, so workers share out batches and the stream does not depend on the worker count. Batching after to_iter_dataset() but before mp_prefetch makes each worker batch its own slice: batch 0 becomes records 0, 2, 4, ... of the shuffled order with 2 workers. A filter (a many-to-one transformation) before mp_prefetch also changes the stream, which grain's docstring warns about (). The output stays deterministic for a fixed worker count (grain's docstring says so, and the DataLoader run with 2 workers repeated exactly, ); it is elasticity that is lost: change the worker count between save and resume and you get a different run. Threads, processes and speed


Two kinds of slow transformation behave differently. Measured with a 2 ms per-record map (rough timings, load average about 40): a map that waits (sleep, like reading a file) ran at  batches per second with no worker processes, against the 15.6 a serial loop would allow (1 / (32 x 2 ms) derived), because the default 16 read threads overlap the waits; a map that computes in Python (a busy loop holding the GIL) ran at , the serial rate, since threads cannot run Python in parallel. Worker processes are the fix for the second kind; on this heavily loaded shared machine their speed-up was not measurable reliably ( and  batches per second with 2 and 4 workers), so no claim is made about it here. On a TPU host the rule is the usual one: profile the input pipeline (xprof's input pipeline analyser) and add workers until the device never waits.


grain versus the alternatives
A Python generator over a numpy memmap (the root's running example) is fine when the data fits on one host and you never resume mid-epoch. tf.data is what older JAX code (T5X, big_vision) uses. PyTorch's DataLoader works from JAX too (convert batches with np.asarray); torchdata's StatefulDataLoader adds state_dict for mid-epoch resume (not run here). MaxText's default dataset_type is synthetic, with grain, Hugging Face and tfds options (root's Tool map).
