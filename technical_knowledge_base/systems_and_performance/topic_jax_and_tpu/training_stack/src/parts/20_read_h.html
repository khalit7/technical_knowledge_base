7. float16 and loss scaling

On TPU use bfloat16: it has float32's 8 exponent bits, so its range is float32's and it needs no loss scaling (the root's Training lab measured bf16 compute with a float32 master copy ending within 0.001 of float32). float16 (5 exponent bits, smallest normal 6.10e-5, largest 65,504) is still what many GPU recipes use, and gradients are small: the running example's float32 gradients at initialisation have a median magnitude of 1.1e-3, and many land among float16's subnormals. Loss scaling multiplies the loss by S before the backward pass and divides the gradients by S in float32 before the optimiser; dynamic loss scaling starts S high, halves it and skips the step whenever a gradient is not finite, and doubles it after a run of good steps. In JAX the reference implementation is jmp's DynamicLossScale (last released 2023), a small pytree carried through the jitted step; PyTorch's torch.amp.GradScaler is the same algorithm. Formats, subnormals and a loss-scale slider are taught on {{Numerical computing for ML|n:3f05c17b0d0d81d6af0be4a9a2edba8d}} (section 11); mixed precision across frameworks on {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}.

Measured here measured: at S = 1 the median relative error of float16 gradients was about ten times that at S = 256; at S = 224 almost every gradient overflowed. Over 200 steps with float32 master weights, a static scale of 212 stayed on top of float32 (validation loss 2.36050 against 2.36054); no scaling wandered off the float32 trajectory (2.3319: not worse here, a different run); the dynamic scale started at 215, skipped the overflowing steps 111 and 144, halving each time, and ended at 213.

ls = jmp.DynamicLossScale(jnp.asarray(2.0 ** 15, jnp.float32))
@jax.jit
def step(p, s, ls, x, y):
    def f(pc):
        logits = MJ.apply(jax.tree.map(lambda a: a.astype(jnp.float16), pc), x, CFG).astype(jnp.float32)
        return ls.scale(optax.softmax_cross_entropy_with_integer_labels(logits, y).mean())
    l, g = jax.value_and_grad(f)(p)          # float32 master weights; float16 inside
    g = ls.unscale(g)
    finite = jmp.all_finite(g)
    u, s2 = tx.update(g, s, p)
    p, s = jmp.select_tree(finite, (optax.apply_updates(p, u), s2), (p, s))   # skip the step on overflow
    return p, s, ls.adjust(finite), ls.unscale(l), finite

On a CPU float16 is emulated, so no speed is reported. jmp doubles the scale again only after 2,000 good steps by default. A tiny model at initialisation has large gradients; deep models late in training have far smaller ones, which is where unscaled float16 loses updates outright.

8. Evaluation loops and metrics

loss.item() every step forces the host to wait for the device, serialising a pipeline that JAX runs asynchronously (dispatch returns before the device finishes). So accumulate metrics on the device, inside the compiled step, and read them every N steps. nnx.MultiMetric(loss=nnx.metrics.Average("loss"), accuracy=nnx.metrics.Accuracy()) is a module whose state is running sums in Variables; metrics.update(loss=..., logits=..., labels=...) inside an nnx.jit step adds to them on device; metrics.compute() and reset() on the host every N steps are the only syncs (source ; also Welford for mean and variance). An evaluation loop is the same with a second MultiMetric and an eval_step that does not touch the optimiser; call model.eval() first if the model has dropout or BatchNorm. clu (Google's CommonLoopUtils), which older Flax code uses for metrics and periodic actions, last released 0.0.12 on 2024-04-10 (PyPI, read 2026-10-15) published; for NNX code nnx.metrics is enough.

It ran three times in separate processes measured: A trained 400 steps; B ran the same command and was stopped after step 250, the way a preemption would stop it; C ran the same command again, found the step-200 checkpoint and continued.
