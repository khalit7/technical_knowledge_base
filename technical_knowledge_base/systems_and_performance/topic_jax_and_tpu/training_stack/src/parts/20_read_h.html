7. float16 and loss scaling

The root's Training lab measured bfloat16: compute in bf16 with a float32 master copy ends within 0.001 of float32, and bf16 weights without a master copy freeze LayerNorm scales. bfloat16 has float32's 8 exponent bits, so its range is the same and it needs no loss scaling; that is why TPUs use it. float16 (5 exponent bits) is still what many GPU recipes use, and its smallest normal number is (subnormals go down to , with fewer and fewer significant bits), its largest . Gradients are small numbers: the running example's float32 gradients at initialisation have a median magnitude of .

Loss scaling multiplies the loss by S before the backward pass, so every gradient is S times larger while it is in float16, and divides by S in float32 before the optimiser. Measured on one batch at the initial weights, gradients computed through a float16 copy of the model measured:

At S = 1 few gradients become exactly zero, but many land among float16's subnormals and lose precision: the median relative error is about ten times that at S = 256. bfloat16 at S = 1 has a larger median error still (8 significant bits against float16's 11) but loses nothing to range; its handful of zeros are sums that cancel, not underflow. Too large a scale overflows: at 224 almost every gradient became infinite. Dynamic loss scaling searches for the largest safe S: start high, halve S and skip the step whenever a gradient is not finite, double it after a run of good steps. jmp's DynamicLossScale (the reference implementation, last released 2023) does this as a small pytree you carry through the jitted step; PyTorch's torch.amp.GradScaler is the same algorithm.

ls = jmp.DynamicLossScale(jnp.asarray(2.0 ** 15, jnp.float32))
@jax.jit
def step(p, s, ls, x, y):
    def f(pc):
        logits = MJ.apply(jax.tree.map(lambda a: a.astype(jnp.float16), pc), x, CFG).astype(jnp.float32)
        return ls.scale(optax.softmax_cross_entropy_with_integer_labels(logits, y).mean())
    l, g = jax.value_and_grad(f)(p)          # float32 master weights; float16 inside
    g = ls.unscale(g)
    finite = jmp.all_finite(g)
    u, s2 = tx.update(g, s, p)
    p, s = jmp.select_tree(finite, (optax.apply_updates(p, u), s2), (p, s))   # skip the step on overflow
    return p, s, ls.adjust(finite), ls.unscale(l), finite

8. Evaluation loops and metrics

The problem. loss.item() every step is harmless in eager PyTorch on CPU but on an accelerator it forces the host to wait for the device, serialising a pipeline that JAX runs asynchronously (dispatch returns before the device finishes). The fix is to accumulate metrics on the device, inside the compiled step, and read them every N steps.

nnx.MultiMetric(loss=nnx.metrics.Average("loss"), accuracy=nnx.metrics.Accuracy()) is a module whose state is running sums in Variables; metrics.update(loss=..., logits=..., labels=...) inside an nnx.jit step adds to them on device; metrics.compute() and reset() on the host every N steps are the only syncs (source ; also Welford for mean and variance). An evaluation loop is the same with a second MultiMetric and an eval_step that does not touch the optimiser; call model.eval() first if the model has dropout or BatchNorm. clu (Google's CommonLoopUtils), which older Flax code uses for metrics and periodic actions, last released 0.0.12 on 2024-04-10 (PyPI, read 2026-10-15) published; for NNX code nnx.metrics is enough.
