2. NNX transformations: jit, grad, the optimiser, scan, sharding

nnx.jit: what retraces, what is written back

nnx.jit(f) is jax.jit with a wrapper: before the call it splits every module argument into graphdef and state, passes the graphdefs as static (hashed into the cache key) and the states as traced arrays; inside, it merges them back into objects; after the call it copies changed Variables back into your objects. So two things hold that a PyTorch user does not expect: a Python side effect in the function runs only while tracing, and a change to the module's structure retraces. The running example with a custom StepCount Variable incremented on every call measured:

@nnx.jit
def step_count(m, x):
    TR["n"] += 1                   # Python side effect: runs only when tracing
    return m(x).mean()

From src/runs/ts_nnx.py (E5). "Traces" counts how many times Python ran the function body; "calls" is the Variable incremented inside the compiled program and written back.

Setting h to the value it already had does not retrace: the graphdef compares equal. Adding an attribute does, and so does a new input shape, exactly as with jax.jit. In a training loop the danger is code that adds, removes or re-creates a submodule or a Python attribute every step: each step then compiles from scratch. The root's {{Compiler lab|n:3c65c17b0d0d81ecbc04eea6aa45ea1a}} tab measures what a recompile costs; {{XLA and compilation|n:3fa5c17b0d0d8135adcedefac9e1bb48}} shows how to find the cause at scale. nnx.grad: gradients with respect to Params only

nnx.grad(loss_fn)(model, x, y) differentiates with respect to the model's nnx.Param leaves and nothing else, because its default argnums is nnx.DiffState(0, nnx.Param). On the counter model measured: the gradient is an nnx. with leaves, all of type ; the StepCount is not in it. To differentiate a subset, pass a narrower filter: argnums=nnx.DiffState(0, nnx.All(nnx.Param, nnx.PathContains("attn"))) gives leaves (the 4 x 8 attention weights and biases). The PyTorch counterpart is requires_grad_(False) on everything else, but here nothing is mutated and the choice is per call. The key-projection bias gradient is at most against for the query kernel: zero in exact arithmetic, because a constant added to every key shifts each softmax row by a constant (the root's Training lab explains the consequences for Adam). nnx.Optimizer: the optimiser as a module

nnx.Optimizer(model, tx, wrt=nnx.Param) runs tx.init on the filtered state and stores the result as Variables, so the optimiser can be passed through nnx.jit and checkpointed like a model; opt.update(model, grads) calls tx.update, adds the updates and writes them into the model. It no longer holds a reference to the model (since Flax 0.11), which is why update takes it. Scan over layers: one traced block instead of four

The problem. A Python for loop over layers is unrolled when traced: 4 blocks give 4 copies of the block in the jaxpr, 48 give 48, and compile time grows with depth. How it works. Create the blocks with nnx.vmap over a split of the Rngs, so every parameter gets a leading layer axis (a [128, 512] kernel becomes [4, 128, 512]); run them with nnx.scan, which lowers to one lax.scan whose body is traced once. This is the NNX spelling of MaxText's scan_layers and of Linen's nn.scan.

@nnx.split_rngs(splits=cfg["n_layers"])
@nnx.vmap(in_axes=(0,), out_axes=0)
def make_blocks(r):
    return MN.Block(cfg, rngs=r)          # the running example's Block, unchanged
self.blocks = make_blocks(rngs)          # every Param now has a leading axis of 4

@nnx.scan(in_axes=(nnx.Carry, 0), out_axes=nnx.Carry)
def body(x, blk):
    return blk(x)
x = body(x, self.blocks)

What the numbers say. The scanned program's jaxpr stays at top-level equations and its optimised HLO at lines whatever the depth, while the unrolled one grows linearly ( equations at 4 layers, at 16). The scanned and unrolled models give the same logits to (float rounding: XLA fuses the two programs differently). On this CPU at 4 to 16 layers the scanned program compiled more slowly, not faster: the loop machinery has a fixed cost, and these blocks are tiny. The saving is in growth: at 4 to 16 layers the unrolled compile time rose from s to s while the scanned one stayed near to s; at the 32 to 128 layers of real LLMs the unrolled program is what dominates compile time (not run here: the measured trend is the evidence, the extrapolation is not). The cost of scanning: every layer must have identical structure, per-layer Python logic is gone, and XLA cannot fuse across layer boundaries. Pair it with nnx.remat to choose which activations each layer saves.

Sharding annotations on parameters

To train on many devices each parameter needs a layout. NNX attaches it at creation: wrap an initialiser with nnx.with_partitioning(init, ("embed", "mlp")), where the names are logical axes of the weight, and map logical names to mesh axes once with nnx.logical_axis_rules. Under jax.set_mesh(mesh) the parameter is born sharded ("eager sharding", on by default in 0.12.10: ).
