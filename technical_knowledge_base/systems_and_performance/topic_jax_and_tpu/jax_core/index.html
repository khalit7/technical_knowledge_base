The whole of JAX in four sentences
A jax.Array is an immutable, typed, device-resident buffer. A transformation calls your Python function on tracers, stand-ins that carry an abstract value (shape and dtype); every array operation lands on a primitive, and the primitive asks the current trace (an interpreter) what to do with it. One interpreter records a jaxpr (jit), one computes derivatives (grad, jvp), one adds a batch dimension (vmap), and they stack. Everything else on this page (dtypes, control flow, custom rules, pytrees, keys) is a consequence of that design.

1. Arrays: what a jax.Array is, where it lives, and what dtype it really has

The problem. A PyTorch tensor is a mutable buffer on one device, and most of its behaviour (dtype rules, synchronisation) is inherited from CUDA and NumPy habits. JAX arrays look the same from Python but differ in four ways that bite when porting: they can span several devices, they remember whether you placed them on purpose, operations on them return before the work is done, and their dtype rules are JAX's own, not NumPy's.

What the object is

Every array you touch is a jaxlib._jax.ArrayImpl, a C++ object behind the public type jax.Array (isinstance(x, jax.Array) is ). For x = jnp.arange(6.0).reshape(2, 3) this run printed:

x.shape, x.dtype(2, 3), static: known without computing anything; they make up the abstract value
jax.typeof(x)the abstract value tracing works with (section 2)
x.devices()a set: a sharded array lives on many
x.shardinghow the logical array maps to device buffers (Sharding and scale owns this)
x.committedplaced on purpose, or left to JAX (next paragraph)
x.weak_typewhether the dtype is "weak" (below)

It is immutable: x[0] = 1 raises and x.at[0].set(1) returns a new array; the root's Transforms lab (section 5) shows the indexed-update API and why out-of-bounds indices clamp instead of raising.

Committed and uncommitted: who chose the device

An array is committed when you placed it explicitly (jax.device_put(x, device) or a sharding), and uncommitted when JAX chose the default device for you (jnp.ones, jnp.asarray(numpy_array), jax.device_put(x) with no device). The rule: an operation on uncommitted arrays may move them to wherever the committed operands are; an operation mixing arrays committed to different devices is an error, because JAX will not silently copy what you placed on purpose. measured here with 8 simulated CPU devices (run_array8.py):

a0 = jax.device_put(x, devs[0])   # committed to cpu:0
a3 = jax.device_put(x, devs[3])   # committed to cpu:3
u  = jnp.ones(4)                  # uncommitted, on cpu:0
u + a3     # -> lands on cpu:3, committed: u followed a3
a0 + a3    # -> error below


Fix: move one side explicitly, jax.device_put(a0, devs[3]) + a3. PyTorch counterpart: RuntimeError: Expected all tensors to be on the same device fires for any mix of devices; JAX is more permissive for arrays you never placed, and exactly as strict for those you did. Inside jit the same check gives the same message with the argument names.



Async dispatch: the call returns before the work is done


How it works. Calling a jitted function enqueues the compiled program on the device and returns an array whose buffer is not filled yet; Python runs ahead. Anything that needs the actual numbers in Python waits: x.block_until_ready(), float(x), x.item(), print(x), np.asarray(x), jax.device_get(x), or a Python if on a value. measured here for tanh(a @ b) with two float32 1024 x 1024 matrices, jitted, median of 7 calls:

Problem, cost, when it matters, how to check

Cost: none at run time; the cost is bugs. When it matters: mixed-precision models (strong constants upcasting bf16), integer ids and counters (int32 overflow), cross-device code (committed arrays), benchmarks and training loops (hidden syncs). How to check: jax.typeof(x) prints dtype, weak flag and sharding; x.committed, x.devices(); jax.config.update("jax_numpy_dtype_promotion", "strict") makes any operation between arrays of two different strong dtypes an error (weak scalars still promote); the profiler's trace shows device idle gaps from host syncs (the XLA and compilation child page reads profiles).






2. Tracing in depth: abstract values, traces and how transformations nest


The problem. One Python function has to become several different programs: a compiled one (jit), one that also computes derivatives (grad), one that works on a batch (vmap), and any composition of these. PyTorch's eager mode cannot do this, because it only ever sees one operation at a time on real numbers. JAX instead runs your Python on tracers and lets an interpreter decide what each operation means.



Abstract values


An abstract value (an "aval") describes a set of possible arrays: everything about an array except its numbers. For arrays it is a ShapedArray, and its fields are exactly what a compiled program may depend on. source




Shape, dtype and weak type you met in section 1; sharding is the logical layout over a mesh, manual_axis_type records, inside shard_map, over which mesh axes a value varies or is still unreduced (a sum not yet taken), memory_space and layout describe where and how the buffer sits. jax.typeof(x) gives the aval of anything (measured here):




A typed PRNG key is an array whose dtype is a key type (key<fry>), section 9. The shapes are static: they are part of the aval, so they are known while tracing, which is why x.shape[0] is a plain Python int inside a jitted function and why no shape may depend on data.



Traces and tracers


A trace is an interpreter. It has one method that matters, process_primitive(primitive, tracers, params), which says what applying a primitive means in that interpretation. A tracer is a value that belongs to a trace; it has an aval and whatever the interpreter needs (a JVP tracer carries a primal and a tangent, a batch tracer carries a value and the index of its batch dimension). source the interface:

Cost, and how to check


Cost. Tracing is Python: every primitive goes through bind and one process_primitive per trace level, so tracing time grows with (number of primitive calls) x (number of nested transformations). It is paid once per cache miss, which is why it hurts only when something retraces (the root's Transforms lab counts retraces; its section 2 measures trace time against model depth) and why large models scan over layers (section 4). How to check: jax.make_jaxpr(f)(*args) shows the program; print(jax.typeof(x)) or print(x) inside f shows the tracer (once, at trace time); jax.config.update("jax_check_tracer_leaks", True) finds tracers that escaped (slow, debugging only).







3. Jaxprs: the program every transformation reads and writes


The problem. A transformation needs the computation as data it can inspect and rewrite. The jaxpr is that data: small (a few dozen primitives cover most models), typed (every variable has an aval), and pure (no Python, no side effects except declared effects). PyTorch counterpart: an FX graph or the aten graph that torch.export produces.


Anatomy


A printed jaxpr reads { lambda constvars ; invars . let equations in (outvars) }. Each equation is outvars = primitive[params] invars. Hover or tap the legend to find each part in a real jaxpr (the function cf of the Jaxpr explorer):

Two changes in recent versions, read in the pinned source source. First, a closed jaxpr is now just a jaxpr: the class that used to pair a jaxpr with its constant values was merged into Jaxpr, which now carries its consts.




Second, how closed-over constants are handled is changing. 5. Autodiff from zero: JVP, VJP, linearize and transpose


The idea. Near a point x, a differentiable function f from n numbers to m numbers behaves like a linear map: its Jacobian J, an m x n matrix. Autodiff never builds J. It offers two ways to apply it:




Forward mode: JVP
jax.jvp(f, (x,), (v,)) returns f(x) and J v: push a direction v (a "tangent") from the inputs to the outputs, alongside the ordinary computation. One pass gives one column of information about J. PyTorch: torch.func.jvp; dual numbers.


Reverse mode: VJP
y, f_vjp = jax.vjp(f, x), then f_vjp(u) returns uT J: pull a weighting u of the outputs (a "cotangent") back to the inputs. For a scalar loss, u = 1 gives the gradient. PyTorch: loss.backward(), torch.func.vjp.




What each costs, and why training uses reverse mode


One JVP and one VJP each cost a small constant times one forward pass. A full Jacobian therefore costs n JVPs (one per input) or m VJPs (one per output): forward mode wins when there are few inputs, reverse mode when there are few outputs. measured here with XLA's own FLOP count (deterministic) for Jacobians of the running example's MLP restricted to k inputs and m outputs of one token:

The pattern is exact: jacfwd's cost grows with k only, jacrev's with m only, and they cross on the diagonal. A training loss has 826,368 inputs and 1 output, so reverse mode costs one VJP. measured here on one training batch: forward pass  GFLOP, value_and_grad  GFLOP ( times the forward), one JVP in one direction  GFLOP.   1. Linearize: run the forward computation once with a LinearizeTrace. For each primitive it computes the primal value now and records the tangent computation (which is linear) into a separate jaxpr. Values the linear program needs from the forward pass, such as an activation to multiply by, become that jaxpr's constants: the residuals.
    2. 

  2. Transpose: run the linear jaxpr backwards, replacing every linear primitive by its transpose: a matmul by x becomes a matmul by xT, a broadcast becomes a sum, a sum becomes a broadcast, an addition sends its cotangent to both inputs.
    3.

6. Custom derivative rules: custom_jvp and custom_vjp


The problem. Autodiff differentiates the program you wrote, not the function you meant. A formula that is correct in exact arithmetic can have a derivative program that overflows, divides by zero or multiplies infinity by zero, and some programs (a while_loop solver) cannot be reverse-differentiated at all. PyTorch's answer is torch.autograd.Function with a hand-written backward; JAX has two decorators.




jax.custom_jvp
You write the JVP rule (primal out, tangent out). JAX linearizes and transposes it for reverse mode, so the function works under jvp, grad, vmap and jit alike. The default choice. The rule must be linear in the tangents.


jax.custom_vjp
You write a forward that returns residuals and a backward that maps output cotangents to input cotangents, like PyTorch's forward/backward. Use it when the backward pass should be a different computation (implicit differentiation, saving memory, clipping). It does not support forward mode.




A softplus that overflows


log(1 + exp(x)) is softplus written naively. measured here in float32: its value becomes inf and its gradient NaN from x =  on (the sweep steps by 1; exp overflows float32 above ln(3.4e38) = ), because the derivative program computes exp(x) / (1 + exp(x)) = inf / inf. A custom_jvp rule that returns t * sigmoid(x) fixes the gradient (1.0 at x = 100) but not the value, which is still inf: a rule changes the derivative program only. A rewrite that never overflows, max(x, 0) + log1p(exp(-|x|)), fixes both and needs no rule, but has its own trap: at x = 0 its gradient is  (true value 0.5), because the derivatives of max and |x| at their kinks follow conventions. jax.nn.softplus is right everywhere (it is built on logaddexp). A norm at zero, and the jnp.where trap


The gradient of sqrt(s) is 0.5 / sqrt(s): infinite at s = 0, and the chain rule multiplies it by 2x = 0, giving NaN. Interview questions


How does jax.grad work, and how is it different from loss.backward()?
grad wraps the function; calling it runs the function once under a linearize interpreter, which computes primal values and records the tangent (linear) program with residuals, then transposes that program to get the backward pass, and returns gradients shaped like the parameters. PyTorch records a tape during an ordinary forward pass and accumulates into .grad. Same math (one forward plus a backward of about twice the cost: measured 2.88 x forward FLOPs); JAX's version is a pure function that composes with jit and vmap and needs no zero_grad.


What is a tracer, and what does it know?
A stand-in value owned by one trace (interpreter). It carries an abstract value (shape, dtype, weak type, sharding) and whatever its interpreter needs: a jaxpr variable (jit), a primal and a tangent (jvp), a value and a batch axis (vmap). Under jit it has no numbers, so Python control flow on it fails; under grad alone the primal is concrete.


When do you use jacfwd and when jacrev? How do you get Hessian information cheaply?
jacfwd costs one JVP per input, jacrev one VJP per output: forward for tall Jacobians (few inputs), reverse for wide ones (few outputs, such as losses). Measured: jacfwd FLOPs grew with inputs only, jacrev with outputs only. Hessians: jacfwd(jacrev(f)); but for curvature-times-vector use a Hessian-vector product, jvp(grad(f)), about twice the cost of a gradient (measured 1.7x) and no n x n matrix.


Why can't you take the gradient of a while_loop, and what do you do instead?
Reverse mode replays the loop backwards and must store per-iteration residuals, so it needs a trip count known at trace time; while_loop's transpose rule is an error by design. Use scan (or fori_loop with static bounds) to a fixed maximum with masking, or differentiate the result implicitly with custom_vjp (for fixed points and solvers), which also keeps memory constant.


What happens to lax.cond under vmap?
If the predicate is not batched, it stays a cond. If it is, the batching rule converts it to a select: both branches run for every example and the results are selected, so the expensive branch is always paid (measured several hundred times slower for a heavy branch). A vmapped while_loop with a batched predicate runs until every example is done.


custom_jvp or custom_vjp?
custom_jvp by default: you write the forward-mode rule, JAX transposes it for reverse mode, and everything composes (jvp, grad, vmap, Hessians). custom_vjp when the backward must be a different computation: implicit differentiation, memory savings, gradient clipping or straight-through estimators; it gives up forward mode.


What is a weak type, and why does JAX have them?
A dtype flagged "defer to the other operand", given to Python scalars and arrays made from them. It keeps bf16_array * 2.0 in bfloat16 instead of upcasting; promotion follows a lattice in which weak types sit low. NumPy 2 adopted similar rules (NEP 50), but differences remain (JAX wraps int8 + 1000, NumPy raises).


Why does JAX use a counter-based PRNG?
Random bits are a keyed hash of an index, so any element can be computed independently: reproducible across shardings and devices, parallel without communication, and splittable without shared state. With partitionable Threefry (default since 0.5.0), element i depends only on the key and i, so a sharded array of random numbers needs no collectives.


Design: per-example gradient clipping (DP-SGD) for a 1B-parameter model on a TPU pod. How do you write it in JAX, and what limits it?
The algorithm (Abadi et al. 2016): per-example gradients, clip each to norm C, sum, add noise. In JAX it is vmap(grad(loss), in_axes=(None, 0, 0)) over the batch, norms by jax.tree.map, a jnp.minimum(1, C / norm) scale, sum, noise from a key folded with the step. The limit is memory: B per-example gradients of 1B parameters is B x 4 GB in float32, so process the batch in micro-batches with lax.scan or lax.map over chunks, accumulating clipped sums (constant memory, B/chunk sequential steps), shard the batch axis over the data mesh axis, and donate the accumulators. Trade-off: chunk size against memory and step time. To avoid materialising per-example gradients at all, "ghost clipping" computes per-example norms from activations and output gradients (Li et al. 2021), at the cost of custom per-layer code.


Design: a new operation needs a fast kernel and a gradient. Which extension point?
Ladder from cheapest: compose existing jnp/lax ops and let XLA fuse; custom_jvp or custom_vjp for a different derivative; Pallas for a custom kernel (TPU or GPU), wrapped in custom_vjp for its backward; jax.ffi for existing C++ or CUDA code; pure_callback for host Python (slow, no device code); a new primitive only when the operation must be a first-class node that transformations and the compiler see (new collective, new layout semantics), because you then owe abstract eval, lowering per platform, JVP, transpose and batching rules.

  • "grad is source-to-source, not tape-based": it is trace-based: JAX never reads your source; it transforms the traced program (linearize, then transpose). The residuals it keeps play the role of a tape (section 5).
    • 

  • key = jax.random.key(0)  # PRNGKey; an array: key() returns a typed key (key<fry>[]), not a PRNGKey; PRNGKey() returns the raw uint32[2] form (section 9).
    • 

  • "Out-of-bounds indexing does not raise under jit": it does not raise outside jit either (the root's Transforms lab measured eager clamping).
    • 

  • "On TPU, matmuls may use bf16 accumulation semantics": the DEFAULT precision computes float32 matmuls in bfloat16 (inputs rounded; HIGH and HIGHEST use 3 and 6 bfloat16 passes), per lax.Precision's docstring; it is about input precision and passes, not accumulation (section 1).
    • 

  • "jax.numpy ... weak typing rules that differ subtly from NumPy": NumPy 2 adopted weak Python scalars (NEP 50); the remaining differences are measured in section 1's table.
    • 

  • "cond: both branches compiled": true, and only one runs, except under vmap with a batched predicate, where both run (section 4).
    • 

  • The scaling book's chapter 10 was described as "how a PyTorch person should read JAX code": its title is "Programming TPUs in JAX" and it is about parallelism (sharding, shard_map), so it moved to the sharding links. "JAX tutorials" now redirects to "JAX 101".
