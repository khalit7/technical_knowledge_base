1. Arrays: what a jax.Array is, where it lives, and what dtype it really has

The problem. A PyTorch tensor is a mutable buffer on one device, and most of its behaviour (dtype rules, synchronisation) is inherited from CUDA and NumPy habits. JAX arrays look the same from Python but differ in four ways that bite when porting: they can span several devices, they remember whether you placed them on purpose, operations on them return before the work is done, and their dtype rules are JAX's own, not NumPy's.

What the object is

Every array you touch is a jaxlib._jax.ArrayImpl, a C++ object behind the public type jax.Array (isinstance(x, jax.Array) is ). For x = jnp.arange(6.0).reshape(2, 3) this run printed:

x.shape, x.dtype(2, 3), static: known without computing anything; they make up the abstract value
jax.typeof(x)the abstract value tracing works with (section 2)
x.devices()a set: a sharded array lives on many
x.shardinghow the logical array maps to device buffers ({{Sharding and scale|n:3c65c17b0d0d8125b084e6720cc66b3d}} owns this)
x.committedplaced on purpose, or left to JAX (next paragraph)
x.weak_typewhether the dtype is "weak" (below)

It is immutable: x[0] = 1 raises and x.at[0].set(1) returns a new array; the root's {{Transforms lab|n:3c65c17b0d0d81ecbc04eea6aa45ea1a}} (section 5) shows the indexed-update API and why out-of-bounds indices clamp instead of raising.

Committed and uncommitted: who chose the device

An array is committed when you placed it explicitly (jax.device_put(x, device) or a sharding), and uncommitted when JAX chose the default device for you (jnp.ones, jnp.asarray(numpy_array), jax.device_put(x) with no device). The rule: an operation on uncommitted arrays may move them to wherever the committed operands are; an operation mixing arrays committed to different devices is an error, because JAX will not silently copy what you placed on purpose. measured here with 8 simulated CPU devices (run_array8.py):

a0 = jax.device_put(x, devs[0])   # committed to cpu:0
a3 = jax.device_put(x, devs[3])   # committed to cpu:3
u  = jnp.ones(4)                  # uncommitted, on cpu:0
u + a3     # -> lands on cpu:3, committed: u followed a3
a0 + a3    # -> error below


Fix: move one side explicitly, jax.device_put(a0, devs[3]) + a3. PyTorch counterpart: RuntimeError: Expected all tensors to be on the same device fires for any mix of devices; JAX is more permissive for arrays you never placed, and exactly as strict for those you did. Inside jit the same check gives the same message with the argument names.



Async dispatch: the call returns before the work is done


How it works. Calling a jitted function enqueues the compiled program on the device and returns an array whose buffer is not filled yet; Python runs ahead. Anything that needs the actual numbers in Python waits: x.block_until_ready(), float(x), x.item(), print(x), np.asarray(x), jax.device_get(x), or a Python if on a value. measured here for tanh(a @ b) with two float32 1024 x 1024 matrices, jitted, median of 7 calls:

On a GPU or TPU the same thing happens, which is why a benchmark without block_until_ready() measures dispatch, and why one stray float(loss) per step serialises Python with the device. PyTorch counterpart: CUDA kernels are asynchronous too and loss.item() is the same hidden sync; on CPU, PyTorch is synchronous and JAX is not. Weak types: why bf16_array * 2.0 stays bfloat16


The problem. In NumPy 1, float32_array * 2.0 could upcast to float64 because the Python float was treated as float64. For bfloat16 models that would be a disaster: every x * 0.5 would double memory. JAX gives Python scalars a weak type: a dtype marked "defer to the other operand". jax.typeof(2.0) prints ; the tilde is the weak flag, and jax.typeof(jnp.float32(2.0)) prints  (strong).

How it works. JAX defines promotion on a lattice: each type points to the types just above it, and two types promote to their lowest common upper bound. Weak int and weak float sit low in the lattice, so they join any array type without raising it. source:

Problem, cost, when it matters, how to check

Cost: none at run time; the cost is bugs. When it matters: mixed-precision models (strong constants upcasting bf16), integer ids and counters (int32 overflow), cross-device code (committed arrays), benchmarks and training loops (hidden syncs). How to check: jax.typeof(x) prints dtype, weak flag and sharding; x.committed, x.devices(); jax.config.update("jax_numpy_dtype_promotion", "strict") makes any operation between arrays of two different strong dtypes an error (weak scalars still promote); the profiler's trace shows device idle gaps from host syncs (the {{XLA and compilation|n:3fa5c17b0d0d8135adcedefac9e1bb48}} child page reads profiles).
