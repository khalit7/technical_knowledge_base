1. Arrays: immutable, asynchronous, and typed by JAX's own rules

A JAX array looks like a tensor from Python but differs in four ways that bite when porting: it can span several devices, it remembers whether you placed it on purpose, operations on it return before the work is done, and its dtype rules are JAX's own, not NumPy's.

Every array is a jaxlib._jax.ArrayImpl, a C++ object behind the public type jax.Array (isinstance(x, jax.Array) is ). For x = jnp.arange(6.0).reshape(2, 3) this run printed:

x.shape, x.dtype(2, 3), static: known without computing anything; they make up the abstract value
jax.typeof(x)the abstract value tracing works with (section 2)
x.devices(), x.sharding; a set, because a sharded array lives on many devices ({{Sharding and scale|n:3c65c17b0d0d8125b084e6720cc66b3d}} owns sharding)
x.committed, x.weak_type, placed on purpose or left to JAX (closed block below); whether the dtype is "weak" (below)

It is immutable: x[0] = 1 raises and x.at[0].set(1) returns a new array; inside jit the compiler turns that back into an in-place update where it is safe. Two differences from PyTorch: repeated indices accumulate (x.at[[0, 0, 0]].add(1.0) adds 3), and out-of-bounds indices clamp on reads and are dropped on writes instead of raising, in eager mode and under jit alike (the root's Transforms lab, section 5, measured both).

Async dispatch: the call returns before the work is done

Calling a jitted function enqueues the compiled program and returns an array whose buffer is not filled yet; Python runs ahead until something needs the numbers. measured here for tanh(a @ b) with two float32 1024 x 1024 matrices, median of 7 calls: the call returned after ms, the result was ready after ms, and is_ready() right after the call was in 5 of 5 calls. Apple M1 Pro (CPU), shared machine: only the ratio matters.

Anything that needs the numbers in Python waits: x.block_until_ready(), float(x), x.item(), print(x), np.asarray(x), jax.device_get(x), or a Python if on a value. So a benchmark without block_until_ready() measures dispatch, and one stray float(loss) per step serialises Python with the device. PyTorch counterpart: CUDA kernels are asynchronous too and loss.item() is the same hidden sync; on CPU PyTorch is synchronous and JAX is not ({{Asynchronous dispatch|https://docs.jax.dev/en/latest/async_dispatch.html}}).

Weak types: why bf16_array * 2.0 stays bfloat16

In NumPy 1, float32_array * 2.0 could upcast to float64 because the Python float counted as float64; in a bfloat16 model every x * 0.5 would then double memory. JAX gives Python scalars a weak type, a dtype marked "defer to the other operand": jax.typeof(2.0) prints (the tilde is the weak flag) and jax.typeof(jnp.float32(2.0)) prints (strong). Promotion is defined on a lattice: two types promote to their lowest common upper bound, and weak int and weak float sit low, so they join any array type without raising it ({{JEP 9407, type promotion semantics|https://docs.jax.dev/en/latest/jep/9407-type-promotion.html}}).

Predict: x is a bfloat16 array. What dtype is x * jnp.float32(2.0)?
float32 ( in this run), while x * 2.0 stayed . A NumPy scalar np.float32(2.0) is strongly typed too (), but jnp.array(2.0) keeps the weak flag of the Python float it came from (). A constant built with an explicit dtype in a bf16 model silently upcasts the whole expression.

Real results of x + y in both libraries in this environment (NumPy ). NumPy 2 adopted weak Python scalars too (NEP 50), so the two agree more often than they used to. Two weak-type results worth knowing measured here: int8_array + 1000 gives in JAX (1000 is cast to int8 and wraps) while NumPy 2 refuses (); uint8_array + (-1) gives in JAX. JAX never raises on a value it would have to inspect, because under jit there is no value to inspect.

How to check: jax.typeof(x) prints dtype, weak flag and sharding; jax.config.update("jax_numpy_dtype_promotion", "strict") makes any operation between two different strong dtypes an error (weak scalars still promote); the profiler's trace shows device idle gaps from host syncs (the {{XLA and compilation|n:3fa5c17b0d0d8135adcedefac9e1bb48}} page reads profiles).

Committed and uncommitted arrays: who chose the device

An array is committed when you placed it explicitly (jax.device_put(x, device) or a sharding), and uncommitted when JAX chose the default device (jnp.ones, jnp.asarray(numpy_array), jax.device_put(x) with no device). An operation on uncommitted arrays may move them to wherever the committed operands are; mixing arrays committed to different devices is an error, because JAX will not silently copy what you placed on purpose. measured here with 8 simulated CPU devices (run_array8.py):

a0 = jax.device_put(x, devs[0])   # committed to cpu:0
a3 = jax.device_put(x, devs[3])   # committed to cpu:3
u  = jnp.ones(4)                  # uncommitted, on cpu:0
u + a3     # -> lands on cpu:3, committed: u followed a3
a0 + a3    # -> error below


Fix: move one side explicitly, jax.device_put(a0, devs[3]) + a3. PyTorch's Expected all tensors to be on the same device fires for any mix; JAX is more permissive for arrays you never placed and exactly as strict for those you did. Inside jit the same check gives the same message with the argument names.
