9. Pytrees: leaves, a structure, and static data in the jit key

A pytree is any nested container of arrays (dicts, lists, tuples, registered classes). Every transformation flattens its arguments into leaves (the arrays it traces) and a treedef (the structure, including each node's auxiliary data, the static part), and the treedef is part of the jit cache key (section 3). The root's Transforms lab, section 7, explores the running example's parameter tree; this section is about your own classes.

What a transformation sees of a registered class: arrays become leaves and are traced; everything else rides in the treedef, is compared by value and is baked into the program.

A node type needs two functions, flatten (object to children plus aux data) and unflatten (back). Three ways to get them measured here (run_pytree.py):

10. Random keys: a counter-based hash instead of a global generator


torch.manual_seed(0) seeds a hidden global generator whose state advances on every call. A pure function cannot use hidden state, and a traced function would freeze it (section 3). So JAX makes the generator state an explicit value, a key, passed in like any argument. The rules: never use a key twice; key, sub = jax.random.split(key) makes new independent keys (keep one to split again); jax.random.fold_in(key, step) derives a key from an integer such as the step number. The classic bug is silent: measured by the root's Transforms lab, two dropout masks drawn with the same key at keep probability 0.9 agreed on 100% of 4,096 positions (they are the same mask), while masks from split keys agreed on 81.8%, close to 0.9 x 0.9 + 0.1 x 0.1 = 82% for independent masks.

Why JAX's keys work under jit, vmap and sharding: the default generator, Threefry-2x32 ({{Salmon et al. (2011), Parallel random numbers: as easy as 1, 2, 3|http://www.thesalmons.org/john/random123/papers/random123sc11.pdf}}), computes random bits as a keyed hash of a counter, built from 32-bit additions, rotations and XORs.


Typed keys. measured here: jax.random.key(0) is a scalar array of a key dtype; the older jax.random.PRNGKey(0) is a plain uint32 array of two words. They give the same stream (), but typed keys are the recommended form ({{JEP 9263|https://docs.jax.dev/en/latest/jep/9263-typed-keys.html}}): arithmetic on a key is a bug, a batch of keys has the batch shape and nothing else, and the implementation travels with the dtype.

11. Writing a new primitive, one rule at a time


Almost never needed: custom_jvp or custom_vjp (section 7) cover new derivatives, jax.pure_callback calls host Python, jax.ffi calls compiled C++ or CUDA through XLA's foreign function interface, and {{Pallas|n:3fa5c17b0d0d817699fcf65d085402e7}} writes kernels. A primitive is what those are built from, and writing one shows what every transformation needs. The example is multiply_add(x, y, z) = x * y + z from JAX's own {{primitives guide|https://docs.jax.dev/en/latest/601/jax-primitives.html}}, written against the public extension modules of jax 0.11.2:


Each rule unlocks a transformation (real results after each step)










The rules, in the order they unlock things: impl (eager evaluation), abstract evaluation (shapes and dtypes: tracing, so make_jaxpr), lowering (StableHLO: jit), JVP (forward mode), transpose (reverse mode, because grad is linearize then transpose), batching (vmap). Each failure is the message JAX printed (run_prim.py).




Each rule is a dictionary entry keyed by the primitive: ad.primitive_jvps, ad.primitive_transposes, batching.primitive_batchers, and the lowering registry (this process:  platform-independent lowerings, plus  CPU-,  CUDA- and  TPU-specific ones). The finished primitive's gradient program shows the transpose rule at work: the backward pass is itself a multiply_add. Its jit lowers to two StableHLO ops, stablehlo.multiply and stablehlo.add, because the lowering rule traced the impl (mlir.lower_fun); a real primitive (a new matmul variant, a collective) would emit its own ops or a custom call.
