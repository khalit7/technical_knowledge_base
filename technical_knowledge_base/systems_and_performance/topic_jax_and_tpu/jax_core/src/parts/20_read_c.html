2. Tracing in depth: abstract values, traces and how transformations nest

The problem. One Python function has to become several different programs: a compiled one (jit), one that also computes derivatives (grad), one that works on a batch (vmap), and any composition of these. PyTorch's eager mode cannot do this, because it only ever sees one operation at a time on real numbers. JAX instead runs your Python on tracers and lets an interpreter decide what each operation means.

Abstract values

An abstract value (an "aval") describes a set of possible arrays: everything about an array except its numbers. For arrays it is a ShapedArray, and its fields are exactly what a compiled program may depend on. source

Shape, dtype and weak type you met in section 1; sharding is the logical layout over a mesh, manual_axis_type records, inside shard_map, over which mesh axes a value varies or is still unreduced (a sum not yet taken), memory_space and layout describe where and how the buffer sits. jax.typeof(x) gives the aval of anything (measured here):

A typed PRNG key is an array whose dtype is a key type (key<fry>), section 9. The shapes are static: they are part of the aval, so they are known while tracing, which is why x.shape[0] is a plain Python int inside a jitted function and why no shape may depend on data.

Traces and tracers

A trace is an interpreter. It has one method that matters, process_primitive(primitive, tracers, params), which says what applying a primitive means in that interpretation. A tracer is a value that belongs to a trace; it has an aval and whatever the interpreter needs (a JVP tracer carries a primal and a tangent, a batch tracer carries a value and the index of its batch dimension). source the interface:

How one call finds its interpreter

Every jnp or lax function ends in Primitive.bind, which looks up the current trace and hands it the operation. source

The current trace lives in a thread-local context, not in the data: source

Each transforming trace keeps a parent_trace. When it handles a primitive it computes what it needs and binds the resulting operations on its parent, with the parent set as current. So under jit(vmap(jvp(f))), a sin in f goes to the JVP trace, which asks its parent (the batch trace) for sin, cos and mul, which asks its parent (the jaxpr trace) for batched versions, which records them. Before December 2024 this dispatch was decided by levels: every trace had a level on a global stack ("main traces"), every tracer remembered its level, and bind picked the highest level among its arguments. JAX 0.4.36 (2024-12-05) replaced it: source the CHANGELOG says the release "lands 'stackless' ... trace dispatch purely a function of context rather than a function of both context and data. This let us delete a lot of machinery for managing data-dependent tracing: levels, sublevels, post_process_call, new_base_main, custom_bind". The original {{Autodidax|https://docs.jax.dev/en/latest/autodidax.html}} still builds the level stack (its MainTrace(level, ...)); {{Autodidax2, part 1|https://docs.jax.dev/en/latest/autodidax2_part1.html}} rebuilds the current, context-based design. What each function sees under nested transformations


Inside f, the argument is a tracer of the innermost transformation, and its primal or value is a tracer of the next one out, down to a real array or a jaxpr variable. measured here by walking that chain inside f(x) = sin(x).sum() for an x of shape (2, 3):

Cost, and how to check


Cost. Tracing is Python: every primitive goes through bind and one process_primitive per trace level, so tracing time grows with (number of primitive calls) x (number of nested transformations). It is paid once per cache miss, which is why it hurts only when something retraces (the root's {{Transforms lab|n:3c65c17b0d0d81ecbc04eea6aa45ea1a}} counts retraces; its section 2 measures trace time against model depth) and why large models scan over layers (section 4). How to check: jax.make_jaxpr(f)(*args) shows the program; print(jax.typeof(x)) or print(x) inside f shows the tracer (once, at trace time); jax.config.update("jax_check_tracer_leaks", True) finds tracers that escaped (slow, debugging only).







3. Jaxprs: the program every transformation reads and writes


The problem. A transformation needs the computation as data it can inspect and rewrite. The jaxpr is that data: small (a few dozen primitives cover most models), typed (every variable has an aval), and pure (no Python, no side effects except declared effects). PyTorch counterpart: an FX graph or the aten graph that torch.export produces.


Anatomy


A printed jaxpr reads { lambda constvars ; invars . let equations in (outvars) }. Each equation is outvars = primitive[params] invars. Hover or tap the legend to find each part in a real jaxpr (the function cf of the Jaxpr explorer):

  • invars and outvars: one variable per array leaf of the inputs and outputs (a pytree of four weights becomes four invars).
    • 

  • constvars (before the semicolon): arrays the function closed over. Here the NumPy array big_np became a constvar; a scalar like 3.0 became a literal, written into the equation with its type (3.0:f32[]).
    • 

  • equations: a primitive, its inputs, its outputs with avals, and params: static, hashable values such as axes=(0,) or dimension_numbers for a matmul.
    • 

  • sub-jaxprs as params: higher-order primitives carry whole programs. cond has branches (listed false first: index 0), scan a jaxpr for the body, while a cond_jaxpr and a body_jaxpr, a nested jax.jit a primitive named jit with its own jaxpr (older printouts call it pjit), custom_jvp_call a call_jaxpr plus the rule, jax.checkpoint a remat2.
    • 

  • effects: jax.debug.print becomes a debug_print equation with no outputs and a declared effect, so dead-code elimination cannot remove it.
    • 

  • _: an output nobody reads (a "drop var").

Two changes in recent versions, read in the pinned source source. First, a closed jaxpr is now just a jaxpr: the class that used to pair a jaxpr with its constant values was merged into Jaxpr, which now carries its consts.




Second, how closed-over constants are handled is changing. JAX's internals note ({{Handling of closed-over constants|https://docs.jax.dev/en/latest/internals/constants.html}}, dated "As of April 2026") says that today large closed-over arrays become constvars and are embedded in the compiled program, which can bloat HLO, slow compilation through constant folding and lose a constant's sharding; a future default (opt-in now with JAX_USE_SIMPLIFIED_JAXPR_CONSTANTS=True) keeps them as literals and passes them to the compiled program as extra arguments. measured here: in this run, closing over a NumPy array and a jax.Array gave  constvars:






jnp.full((16,), 142.0) did not become a constant: it was staged as a broadcast_in_dim equation, because it is a JAX operation. Rule of thumb: build constants with jnp inside the function, or pass big arrays as arguments; setting JAX_CAPTURED_CONSTANTS_WARN_BYTES logs every captured constant above a size.
