4. Jaxprs: the program every transformation reads and writes

A transformation needs the computation as data it can inspect and rewrite. The jaxpr is that data: small (a few dozen primitives cover most models), typed (every variable has an aval) and pure (no Python, no side effects except declared effects). PyTorch counterpart: an FX graph, or the aten graph torch.export produces. A printed jaxpr reads { lambda constvars ; invars . let equations in (outvars) }, each equation outvars = primitive[params] invars. Hover or tap the legend to find each part in a real one:

Printed by jax.make_jaxpr(cf, static_argnums=1)(jnp.ones(16), 4) in run_trace.py; the function cf and five more programs are in the Jaxpr explorer, where every equation links to its Python line and its data flow.
  • invars and outvars: one variable per array leaf of the inputs and outputs (a pytree of four weights becomes four invars).
  • constvars (before the semicolon): arrays the function closed over. Here the NumPy array big_np became a constvar; a scalar like 3.0 became a literal, written into the equation with its type (3.0:f32[]).
  • params: static, hashable values such as axes=(0,) or a matmul's dimension_numbers. Higher-order primitives carry whole programs as params: cond has branches (false first: index 0), scan a body jaxpr, while a cond_jaxpr and a body_jaxpr, a nested jax.jit a primitive named jit (older printouts: pjit), custom_jvp_call a call_jaxpr plus the rule, jax.checkpoint a remat2.
  • effects: jax.debug.print becomes a debug_print equation with no outputs and a declared effect, so dead-code elimination cannot remove it; _ is an output nobody reads (a "drop var").

What XLA does with the jaxpr after lowering is the {{XLA and compilation|n:3fa5c17b0d0d8135adcedefac9e1bb48}} page. JAX's own reference: {{Understanding jaxprs|https://docs.jax.dev/en/latest/601/jaxpr.html}}.

Closed-over constants: today's behaviour, the planned change, and a closed jaxpr is now just a jaxpr

JAX's internals note ({{Handling of closed-over constants|https://docs.jax.dev/en/latest/internals/constants.html}}, dated "As of April 2026") says that today large closed-over arrays become constvars and are embedded in the compiled program, which can bloat HLO, slow compilation through constant folding and lose a constant's sharding; a future default (opt-in now with JAX_USE_SIMPLIFIED_JAXPR_CONSTANTS=True) keeps them as literals and passes them to the compiled program as extra arguments. measured here: closing over a NumPy array and a jax.Array gave constvars:

Only the loop whose trip count is unknown until run time fails, and only in reverse mode: reverse mode replays the loop backwards, so it must know how many iterations to store. while's transpose rule is an error by design. fori_loop is not a primitive of its own: it becomes a scan when both bounds are concrete at trace time (so it is reverse-differentiable) and a while when either is traced. Control flow under vmap: per-example predicates run every branch


A batching rule must produce one program for the whole batch. If a cond's predicate is the same for every example, the batched program is still a cond. If it differs per example, there is no single branch to take, so the rule runs both branches for everyone and selects.

associative_scan: a loop as a tree, and why it lost on this CPU


A linear recurrence h_t = a_t * h_(t-1) + b_t can be computed by combining steps pairwise, because composing two such steps gives another of the same form. lax.associative_scan does that in about log2(n) rounds instead of n sequential steps, at the price of more total work. measured here on float32 (n, 256), same answers to :




On this CPU the sequential scan wins at every length; the tree version only pays where many cores or a wide accelerator can run a round in parallel, which is why it appears in linear-RNN and state-space layers trained on GPUs and TPUs. Not run here on such hardware. JAX's docs: {{Control flow and logical operators with JIT|https://docs.jax.dev/en/latest/control-flow.html}}.
