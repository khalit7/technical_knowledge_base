Depth: mistakes worth knowing, two design questions, and what changed from the old page

Each mistake ran in this page's scripts (src/runs/); the others sit in the sections above, beside the mechanism that causes them, and the basic ones (tracer leaks, Python if under jit, side effects) in section 3.

Integer overflow and division by zero with no error
int8_array + 1000 gave ; jnp.array(7) // 0 gave ; int32 max + 1 gave . Compiled code cannot raise on values; check ranges yourself or use jax.experimental.checkify.
Reverse-mode gradient through a while_loop or a fori_loop with traced bounds
Fix: scan or fori_loop with Python-int bounds; or a custom_vjp that differentiates the solution (section 7).


NaN gradients from jnp.where, sqrt or a norm at zero
Gradient of where(x > 0, sqrt(x), 0) at x = -1 and 0: NaN in JAX and PyTorch alike ( in PyTorch). jnp.linalg.norm at the zero vector: . Fix: the double where, or a custom_jvp (section 7). Find the first NaN with jax.config.update("jax_debug_nans", True).


Passing an unregistered class to jit or grad
Register it (register_dataclass, register_pytree_node) or use Flax or Equinox modules.


Flipping jax_threefry_partitionable in an existing codebase
The two settings give different streams (root Transforms lab: largest difference 5.8 in its test), so every initialisation and dropout mask changes. Pin it in configs that must reproduce old runs.


Interview rehearsal: two design questions


Design: per-example gradient clipping (DP-SGD) for a 1B-parameter model on a TPU pod. How do you write it in JAX, and what limits it?
The algorithm ({{Abadi et al. 2016|https://arxiv.org/abs/1607.00133}}): per-example gradients, clip each to norm C, sum, add noise. In JAX it is vmap(grad(loss), in_axes=(None, 0, 0)) over the batch, norms by jax.tree.map, a jnp.minimum(1, C / norm) scale, sum, noise from a key folded with the step. The limit is memory: B per-example gradients of 1B parameters is B x 4 GB in float32, so process the batch in micro-batches with lax.scan or lax.map over chunks, accumulating clipped sums (constant memory, B/chunk sequential steps), shard the batch axis over the data mesh axis, and donate the accumulators. Trade-off: chunk size against memory and step time. To avoid materialising per-example gradients at all, "ghost clipping" computes per-example norms from activations and output gradients ({{Li et al. 2021|https://arxiv.org/abs/2110.05679}}), at the cost of custom per-layer code.


Design: a new operation needs a fast kernel and a gradient. Which extension point?
Ladder from cheapest: compose existing jnp/lax ops and let XLA fuse; custom_jvp or custom_vjp for a different derivative; Pallas for a custom kernel (TPU or GPU), wrapped in custom_vjp for its backward; jax.ffi for existing C++ or CUDA code; pure_callback for host Python (slow, no device code); a new primitive only when the operation must be a first-class node that transformations and the compiler see (new collective, new layout semantics), because you then owe abstract eval, lowering per platform, JVP, transpose and batching rules.




What changed from the old Notion page "JAX core: the functional model"


This page reuses the Notion page "JAX core: the functional model" (saved verbatim in src/live.md). Its claims were treated as unverified notes; each was checked against the pinned source or a run. The corrections, also in src/coverage.md:


    

  • "Minimum Python 3.11" for JAX 0.11.2: wrong; 0.11.0 dropped 3.11, the minimum is 3.12 (root FACTS, PyPI).
    • 

  • "Each transformation works by tracing ... into a jaxpr and then rewriting or compiling it": only jit (and make_jaxpr) stage a whole jaxpr first. grad and vmap interpret primitives as Python runs (section 2); grad stages only the linear tangent program, to transpose it.
    • 

  • "JAX runs your Python function once with abstract tracer values (shape and dtype, no data)": true under jit; under grad alone the tracer holds the real primal value (section 2's chain table).
    • 

  • "Python scalars used in control flow ... are compile-time constants": only if marked static. A Python scalar passed as an argument to a jitted function is traced, with a weak type (section 1); only Python values the function closes over, or static arguments, are baked in.
    • 

  • "jit compiles one executable per distinct (shape, dtype, static-arg) signature": incomplete. The key also includes weak type, sharding, pytree structure with its aux data and the function object (section 3).
    • 

  • "grad is source-to-source, not tape-based": it is trace-based: JAX never reads your source; it transforms the traced program (linearize, then transpose). The residuals it keeps play the role of a tape (section 6).
    • 

  • key = jax.random.key(0)  # PRNGKey; an array: key() returns a typed key (key<fry>[]), not a PRNGKey; PRNGKey() returns the raw uint32[2] form (section 10).
    • 

  • "Out-of-bounds indexing does not raise under jit": it does not raise outside jit either (the root's Transforms lab measured eager clamping).
    • 

  • "On TPU, matmuls may use bf16 accumulation semantics": the DEFAULT precision computes float32 matmuls in bfloat16 (inputs rounded; HIGH and HIGHEST use 3 and 6 bfloat16 passes), per lax.Precision's docstring; it is about input precision and passes, not accumulation (section 1).
    • 

  • "jax.numpy ... weak typing rules that differ subtly from NumPy": NumPy 2 adopted weak Python scalars (NEP 50); the remaining differences are measured in section 1's table.
    • 

  • "cond: both branches compiled": true, and only one runs, except under vmap with a batched predicate, where both run (section 5).
    • 

  • The scaling book's chapter 10 was described as "how a PyTorch person should read JAX code": its title is "Programming TPUs in JAX" and it is about parallelism (sharding, shard_map), so it moved to the sharding links. "JAX tutorials" now redirects to "JAX 101".
    • 

  • Reading times were re-estimated from the pages' word counts on 2026-10-15 (Further reading).
    •
