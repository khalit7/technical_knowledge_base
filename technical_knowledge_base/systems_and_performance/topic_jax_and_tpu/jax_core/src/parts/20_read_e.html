6. Custom derivative rules: custom_jvp and custom_vjp

The problem. Autodiff differentiates the program you wrote, not the function you meant. A formula that is correct in exact arithmetic can have a derivative program that overflows, divides by zero or multiplies infinity by zero, and some programs (a while_loop solver) cannot be reverse-differentiated at all. PyTorch's answer is torch.autograd.Function with a hand-written backward; JAX has two decorators.

jax.custom_jvp

You write the JVP rule (primal out, tangent out). JAX linearizes and transposes it for reverse mode, so the function works under jvp, grad, vmap and jit alike. The default choice. The rule must be linear in the tangents.

jax.custom_vjp

You write a forward that returns residuals and a backward that maps output cotangents to input cotangents, like PyTorch's forward/backward. Use it when the backward pass should be a different computation (implicit differentiation, saving memory, clipping). It does not support forward mode.

A softplus that overflows

log(1 + exp(x)) is softplus written naively. measured here in float32: its value becomes inf and its gradient NaN from x = on (the sweep steps by 1; exp overflows float32 above ln(3.4e38) = ), because the derivative program computes exp(x) / (1 + exp(x)) = inf / inf. A custom_jvp rule that returns t * sigmoid(x) fixes the gradient (1.0 at x = 100) but not the value, which is still inf: a rule changes the derivative program only. A rewrite that never overflows, max(x, 0) + log1p(exp(-|x|)), fixes both and needs no rule, but has its own trap: at x = 0 its gradient is (true value 0.5), because the derivatives of max and |x| at their kinks follow conventions. jax.nn.softplus is right everywhere (it is built on logaddexp). A norm at zero, and the jnp.where trap


The gradient of sqrt(s) is 0.5 / sqrt(s): infinite at s = 0, and the chain rule multiplies it by 2x = 0, giving NaN. So sqrt(sum(x**2)) has a NaN gradient at the zero vector, and so does jnp.linalg.norm in jax 0.11.2 (). A custom_jvp rule that returns the subgradient 0 at the origin fixes it (), and so does the "double where" rewrite.


The double where exists because of a trap that catches everyone. jnp.where(x > 0, jnp.sqrt(x), 0.0) has the right value everywhere and a NaN gradient for every x <= 0: both branches are computed, the untaken branch's derivative is NaN or inf, and the where multiplies it by zero, which leaves NaN. A fixed point: when the backward pass should be a different computation


Some layers are defined by an equation, not a fixed sequence of steps: z = tanh(W z + x), solved by iterating until it stops changing (deep equilibrium models, implicit layers, many solvers). Problem, cost, when it matters, how to check
Cost: usually none beyond the batched primitives; batching rules add broadcasts or moves of the batch axis, and control flow with per-example predicates runs every branch (section 4). When it matters: per-example gradients (root Transforms lab, section 9), ensembles, attention over heads, anything written for one example. How to check: jax.make_jaxpr(jax.vmap(f)) should show batched primitives and no per-example loop; look for select_n where you expected a cond.
