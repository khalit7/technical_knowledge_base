8. Profiling on a TPU: predict each fusion, then find the ones that miss

Wrap a few steps in with jax.profiler.trace("/tmp/prof"): (or jax.profiler.start_trace / stop_trace), call jax.block_until_ready on the result so the work lands inside the window, and open the directory with XProf (pip install xprof, the successor of the TensorBoard profile plugin). It is the counterpart of torch.profiler plus Nsight Systems, with one difference that changes how you read it: there are no kernel launches, only the compiled XLA program, so every row of the timeline is an HLO operation, usually a fusion (one matmul plus the elementwise work XLA fused around it).

The habit. The scaling book reads a real trace this way: an MLP up-projection, bf16[8, 1024, 8192] by bf16[8192, 16384] sharded 4-way data parallel and 2-way model parallel on 8 TPU v2 cores, "should" take 2 x 32 x 1024 x 8192 x 32768 ÷ (23e12 x 8) = 95.6 ms "which is pretty much exactly how long it takes (96ms)" published. Predict each big fusion's time from its shapes with the roofline of section 3, then look for the ones that miss: those are memory-bound, padded, or waiting.

9. MFU and cost per token: ask how attention was counted

The definition. Model FLOPs utilisation is the FLOPs the model needs per step divided by step time x peak FLOP/s; equivalently, measured tokens per second over the tokens per second peak would allow (MaxText's docs/reference/performance_metrics.md; the general treatment is on {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}). "Model" FLOPs means what the architecture needs, not what the program executes: rematerialisation adds hardware FLOPs (28% on the running example) but no model FLOPs, so it lowers MFU.

How MaxText counts. calculate_tflops_training_per_device (src/maxtext/utils/maxtext_utils.py:1152) sums 2 x m x k x n for every weight matmul, triples it for forward plus backward, and adds attention as 4 x sequence2 x heads x head size per layer and sequence, tripled, then halved for causal masking (causal_attention_flops = noncausal_attention_flops / 2, line 1217). The halving arrived with MaxText pull request 1988; its tiering page warns that "Some older TFLOPS/s results are impacted by an updated calculation for causal attention" published.

What we found. We ported that function line by line, fed it each model's MaxText config, and multiplied by the published tokens per second per chip. Six of the eight published MFUs come back within a quarter of a point only when attention is counted the old, non-causal way; counted causally, as the current code does, every one is lower, by 0.8 to 5.1 points calculated from published numbers:

The published MFU matches the old, non-causal count, not the current one

Published MFU and approximate tokens/s per device from MaxText's docs/reference/models/tiering.md at 1a95d1e5 (undated; read 2026-10-15). Peaks 918 TFLOP/s (v6e) and 459 (v5p). The two that do not reproduce: Llama 2 70B on v5p (67.0% non-causal against 65.4% published; its tokens/s is "approx") and Llama 3.1 405B on v6e (35.2% against 38.55%: unexplained).

The gap grows with sequence length: at 8,192 tokens, Llama 3.1 8B's attention is 13% of its FLOPs counted causally and 22% non-causally, so the same run reads as 40.4% or 45.5%. When you compare an MFU across codebases, or against a GPU number, ask for the FLOP formula and which peak it divided by (dense bf16, not sparse or fp8), or compare tokens per second per chip on the same model and sequence length.
