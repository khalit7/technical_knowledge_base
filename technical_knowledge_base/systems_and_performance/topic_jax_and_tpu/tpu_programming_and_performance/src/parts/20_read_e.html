6. Memory planning: what fits, and what rematerialisation buys

The problem. A chip's HBM is all the memory a JAX program has (16 GB on v5e), and XLA plans every byte of the step when it compiles. In PyTorch you discover the peak while running; in JAX you can ask before running (jax.jit(step).lower(...).compile().memory_analysis()), and a step that does not fit fails at compile or load time, not halfway through an epoch.

The training state. With float32 weights and Adam, each parameter costs 4 bytes of weight, 4 of gradient and 8 of the two moments: 16 bytes (MaxText's defaults are weight_dtype: "float32" with dtype: "bfloat16" activations, the root's Training lab). Activations and rematerialisation. The backward pass needs values from the forward pass (the residuals: layer inputs, attention probabilities, MLP pre-activations). jax.checkpoint (alias jax.remat) with a policy decides which to keep and which to recompute; it is PyTorch's torch.utils.checkpoint, but selective by operation type or by name. What transfers to TPU: the residual counts and bytes and the extra FLOPs (properties of the program); what does not: the temporary bytes, which are XLA:CPU's buffer plan.

Read the table as a menu. Saving nothing (full rematerialisation) shrinks the residuals 17-fold for 28% more FLOPs, close to one extra forward pass of the blocks. Saving only matmul outputs (dots_saveable) costs 5% more FLOPs and keeps 36% of the bytes: the cheap-to-recompute elementwise values are dropped, the expensive matmul results kept. dots_with_no_batch_dims_saveable also drops the attention matmuls (they have a batch dimension), keeping the weight matmuls only. MaxText offers the same trade with named tensors: remat_policy chooses among 'minimal_with_context', 'minimal', 'save_dot_with_context_except_mlp', 'save_dot_except_mlpwi', 'save_dot_except_mlp', 'save_qkv_proj', 'qkv_proj_offloaded', 'custom', 'minimal_offloaded', 'save_out_proj' and 'full', "a trade-off between speed (fastest to slowest) and HBM usage (highest to lowest)" (configs/base.yml:489; default 'full', line 492), each built from jax.checkpoint_policies.save_only_these_names in layers/nnx_decoders.py:1383.

The TPU-specific option: offload to the host. A policy can also move a residual to the host's memory over PCIe and bring it back for the backward pass: save_and_offload_only_these_names(..., offload_src="device", offload_dst="pinned_host") (jax/_src/ad_checkpoint.py:165; MaxText's 'custom' policy, nnx_decoders.py:1480). MaxText's Gold Llama 3.1 8B recipe on v6e offloads the decoder layer inputs and the q, k, v and output projections (benchmarks/maxtext_trillium_model_configs.py:716), with XLA flags that overlap the transfers with compute. The budget is PCIe: 3.2e10 B/s per v6e chip (scaling book), so a step can offload only what that bandwidth moves while the chip computes.

7. Slices, pods, multislice, and the mesh on the torus

The vocabulary. A host is one CPU machine with 4 chips (v4, v5p, TPU7x) or 8 (v5e, v6e), running one JAX process. A slice is a set of chips joined by ICI, named by its topology: 4x4x8 is 128 chips in a 3D block. A cube is a 4x4x4 block of 64 chips; v4, v5p and TPU7x build big slices from cubes joined by optical switches, which also provide the wraparound links that make a torus. A pod is everything one ICI fabric can join: 256 chips for v5e and v6e, 4,096 for v4, 8,960 for v5p, 9,216 for TPU7x. Multislice runs one job over several slices, which talk over DCN.

Names count different things. Cloud's v4 page names slices by TensorCores: "v4-8" is 4 chips. Its v5p table has a Cores column at twice the chips (so the conventional v5p-128 is 64 chips). The v5e, v6e and TPU7x pages list topologies and chip counts. Read the topology string, not the number published.

Wraparound and twists. On v5p "All 4x4x4 and larger slices (one cube) have full 3D torus connectivity", smaller ones do not; on v5e and v6e an axis wraps only at its full length of 16 (scaling book). Some 3D shapes can be ordered as a twisted torus: "a 4x4x8 twisted topology provides a 70% theoretical increase in bisection bandwidth" (Cloud v5p page), supported on v4 and v5p where each side is the smallest or twice it.

The largest v5p slice is not the pod (a cross-check)
The scaling book writes the v5p pod as a 16x20x28 "superpod" of 8,960 chips, and Cloud agrees on 8,960 chips (140 cubes). But Cloud's v5p page also says "The largest job that can be scheduled is a 96 cube (6144 chip) job", topology 16x16x24, and "You can scale up to 18432 chips using Multislice". So 16x20x28 is the size of the fabric, not a slice you can request; a plan that needs all 8,960 chips in one slice is two or more slices over DCN. (The {{Sharding and scale|n:3c65c17b0d0d8125b084e6720cc66b3d}} page's mesh designer uses 16x20x28 as the scaling book's example; JAX's placement accepts that shape on mock devices, as it accepts any shape.)

Multislice: only the cheapest traffic crosses DCN. DCN gives a v5p chip 6.25e9 B/s (Cloud's 50 Gbps); ICI gives it six links of 9e10 B/s each way (scaling book), 86 times more in one direction. So a multislice job puts data parallelism across slices (one gradient reduction per step) and everything else inside: MaxText's defaults are dcn_data_parallelism: -1, "recommended DCN axis to be auto-sharded" (configs/base.yml:817), ici_fsdp_parallelism: -1 (line 831) and dcn_tensor_parallelism: 1 # never recommended (line 824).
