The idea in one screen

A TPU is a few large matrix units fed from HBM through a compiler-managed scratch memory, with no kernels and no caches, so a JAX program is fast on it when its shapes keep those units fed: enough tokens per chip to pass the ridge point, dimensions in whole 128 (or 256) tiles, bf16 operands, a memory plan that fits HBM, and a mesh laid on whole torus axes.

One TPU chip as your program meets it: every byte goes HBM, then VMEM, then the MXUs

TensorCore
one sequential processor; a chip has one or two. XLA compiles your whole jitted step into one program for it.
MXU
matrix unit: a 128 x 128 (or 256 x 256) systolic array doing every matmul, bf16 in, float32 accumulate.
VPU
vector unit for everything else, on 8 x 128 registers (8 sublanes x 128 lanes) of float32.
VMEM
on-core scratch memory filled by DMA from HBM; nothing caches HBM for you.
ICI, DCN
chip-to-chip links inside a slice (a 2D or 3D torus); the data-centre network between slices.
Slice, pod
chips joined by ICI and named by topology (4x4x8); the most chips one ICI fabric can join.
Ridge point
peak FLOP/s ÷ HBM bytes/s: the FLOPs per byte an operation needs to stop waiting on memory.
What is real on this page
No TPU was used. published: Google's Cloud TPU pages (last updated 2026-10-13), jax/_src/tpu_info.py at jax-v0.11.2, MaxText's docs at commit 1a95d1e5, and the {{scaling book|https://jax-ml.github.io/scaling-book/}} (Google DeepMind, chapters dated 2025-02-04), all read 2026-10-15. measured here on an Apple M1 Pro CPU with jax 0.11.2: the running example's residuals and FLOPs under each rematerialisation policy, matmul precision emulated pass by pass on its trained weights, JAX's own device placement on mock slices. calculated: roofline arithmetic, what an operation would need at best on a TPU, never what it would get. The running example is the root page's tiny character-level transformer (826,368 parameters, 4 layers, width 128, batch 32 x 128 characters; {{Topic: jax-and-tpu|n:3c65c17b0d0d81ecbc04eea6aa45ea1a}}).
