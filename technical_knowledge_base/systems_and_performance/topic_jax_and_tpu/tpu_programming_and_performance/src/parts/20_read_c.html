3. Rooflines: the batch you need, per generation

Concrete first. Llama 2 7B's MLP up-projection multiplies a [B, 4,096] activation by a [4,096, 11,008] weight. In decode, B is the number of users generating at once; in training it is the tokens on one chip. The weight is 90 MB in bf16 whatever B is, so at B = 1 the MXUs do one multiply-add per weight read and wait on HBM; at B = 4,096 the same bytes feed 4,096 times the work. The rule. The arithmetic intensity of an operation is its FLOPs divided by the bytes it moves between HBM and the chip. Below the chip's ridge point an operation is memory-bound (time = bytes ÷ bandwidth); above it, compute-bound (time = FLOPs ÷ peak). For [B, D] x [D, F] in bf16 the FLOPs are 2BDF and the bytes 2(BD + DF + BF), so when B is much smaller than D and F the intensity is about B. Hence the scaling book's rule: a bf16 matmul is compute-bound only when the number of tokens it processes per chip exceeds the ridge point, 1.97e14 ÷ 8.2e11 = 240 on v5e (its figure; our table uses Cloud's 819 GB/s and gets 240.5). Store the weights in int8 but compute in bf16 and the weight bytes halve, so the threshold halves to 120 (also the scaling book's figure).

Predict: Llama 2 7B serving 64 users at once on a v6e. Are its weight matmuls compute-bound or memory-bound?
Memory-bound. Each decode step processes 64 tokens per weight read, an intensity of about 64, and v6e's ridge is 560: the MXUs could do nine times more. The context length changes the attention part (always memory-bound in decode), not the weight matmuls. To use a v6e's MXUs on decode you need more than 560 sequences per chip, or int8 weights (280), or several chips' worth of users per copy of the weights.

Attention is the exception

The two attention matmuls have no weights to reuse. In training or prefill, the scores QKT for one head and one sequence of S tokens multiply [S, dh] by [dh, S]: 2S2dh FLOPs over 2(2Sdh + S2) bytes if the S x S score matrix goes to HBM. At S = 4,096 and head size 128 that is an intensity of 120, below every generation's ridge calculated. Hence a fused attention kernel (flash or splash attention, a Pallas kernel on TPU): the scores stay in VMEM, the S2 term leaves the byte count, and the intensity climbs to about S. In decode each new token reads the whole key-value cache to do two FLOPs per cached number, an intensity near 1 (the scaling book: "we're basically always memory bandwidth-bound during attention"). Grouped-query attention helps by exactly the group size, because several query heads share one cached key and value. The scaling book turns this into a lower bound on a decode step:

Tstep = B · KV(T) ÷ Whbm + max(2 · B · P ÷ C, P · bw ÷ Whbm)
B
sequences generating at once
KV(T)
key-value cache bytes per sequence at context T: 2 x layers x KV heads x head size x bytes. Llama 2 7B (32 KV heads, bf16): 524,288 bytes, half a MiB, per token
P, bw
weights read by the matmuls and bytes per weight
C, Whbm
peak FLOP/s and HBM bandwidth of all the chips serving the model

For Llama 2 7B on one v5e at context 2,048 it gives 17.4 ms per step at batch 1 (57 tokens per second), 100 ms at batch 64 and 331 ms at batch 240 (725 tokens per second) calculated; at batch 240 the caches alone would need 240 x 2,048 x 0.5 MiB = 240 GiB, fifteen v5e chips' worth. The {{Roofline lab|#t-roof}} runs this model for any generation, batch, context, dtype and chip count.

The same rule between chips: how wide a matmul must be before splitting it pays (depth)

Shard a matmul's contracting dimension D over two chips and each must send its partial [B, F] result to the other: 2BF bytes over one ICI link against BDF FLOPs. The step stays compute-bound only if D/2 exceeds peak ÷ link bandwidth, D > 8,755 on v5e (the scaling book's number, from 4.5e10 B/s one way) calculated. It is 12,222 on v4, 10,200 on v5p, 20,400 on v6e and 51,267 on TPU7x (links of 4.5e10 or 9e10 B/s one way): the faster the chip, the wider the model must be before splitting a matmul between chips pays.
