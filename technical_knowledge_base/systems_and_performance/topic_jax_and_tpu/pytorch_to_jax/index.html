The core idea
PyTorch keeps four kinds of state hidden inside objects (the weights in modules, the gradients in .grad, the optimiser's moments in the optimiser, the random generator's position in a global), and JAX makes each of them an argument and a return value of one pure, compiled training step. A port is that rewrite plus a test: about twenty defaults differ between the libraries without a warning, so a port is correct only when one fixed batch gives PyTorch's logits, loss, gradients and first optimiser step.
The same training step, two homes for its state. Left, PyTorch: the step changes four kinds of state in place (dashed arrows). Right, JAX: params, opt_state and the random key go in and new ones come out; the gradients are a value inside the step, never stored. Colours are the same state on both sides. Section 1 steps through the real code of both twins line by line.

You need: PyTorch at the level of writing a training loop, and the running example of Topic: jax-and-tpu (a 4-layer character transformer, 826,368 parameters; written three times, in PyTorch, Flax NNX and plain JAX; section 1 steps through two of them side by side). Why JAX insists on pure functions (tracing, the jit cache, pytrees, random keys) is taught on JAX core; how .grad accumulates and what autograd records is on Tensors, the dispatcher and autograd. This page uses those ideas and owns only the translation.

1. Four differences, on one training step

Both panes are the root's real files, cut to the lines that matter: src/data/model_torch.py and model_jax.py (plain JAX plus optax, state passed explicitly). Step through: each step lights the lines of one difference on both sides.

Highlighted lines differ between the twins; every other line is the same arithmetic. Press play or step to take the four kinds of state, then compilation, one at a time.
Weights: a module owns them; a function receives them. nn.Linear creates and keeps its weight inside the object; in JAX init_params returns a dict (a pytree) and every layer is a function of p, so the weights are an argument of train_step and come back out of it. The weight is stored [in, out] (x @ p["w"]), the transpose of PyTorch's [out, in]: section 3. Flax NNX keeps PyTorch's object style (class Block(nnx.Module)), and nnx.jit splits it into the same pytree at the boundary.
Randomness: a global generator against explicit keys. torch.manual_seed sets a hidden generator that advances by itself on every draw. A JAX key is a value: drawing twice with the same key gives the same numbers, so init_params splits it into one key per tensor. This model has no dropout, so its step takes no key; with dropout the key becomes one more argument, split or folded with the step number each step (section 2, Dropout).
Gradients: accumulated into .grad against returned. loss.backward() adds into each parameter's .grad, which is why the step starts with zero_grad. jax.value_and_grad returns the gradients as a pytree shaped like params; nothing is stored, so there is nothing to zero, and gradient accumulation is an explicit sum.
Optimiser state: inside the optimiser against passed through. opt.step() updates Adam's moments in place and sched.step() advances a hidden counter. tx.update(grads, opt_state, params) returns new updates and a new opt_state; the schedule is a function of the update count. Parameter groups become a mask pytree (mask=decay_mask), and clipping becomes a link in the chain, before adamw: the order matters (section 2).
Eager against traced. PyTorch runs each line as it is called and loss.item() returns a number. jax.jit runs the Python once per input shape to record a program, then reruns only that program: a Python if on an array value or a print inside the step sees a tracer, not a number (JAX core, sections 2 and 3). donate_argnums=(0, 1) lets XLA reuse the old params and opt_state buffers, which is safe only because the caller never touches them again. float(loss) blocks until the device finishes: log every N steps.

Predict: you flip the mask convention in a JAX port, so each position attends only to positions after it, with -inf fill. What happens at step 0?
NaN, at step 0: the last position has no later position, its row is all -inf, and softmax of that is 0/0. With Flax's finfo.min fill instead there is no NaN: the row averages every value, the model learns to read the future, training loss falls to 0.024 on validation with its own mask, and with the correct causal mask the same weights score 6.83. The NaN is the lucky outcome.

Dropout: compare distributions, not values

Dropout masks come from each framework's own generator, so twins with dropout can never agree bit for bit: test the port with dropout off (as the running example is), then turn it on and compare statistics. Predict before reading the chart: a JAX port reuses one key for every step's dropout mask (PyTorch's generator advances by itself; a JAX key does not). Will the loss curve show it? The run adds dropout 0.1 to both residual branches and trains 300 steps: PyTorch, JAX with a fresh key per step (fold_in(key, step)), JAX with the same key every step, and the no-dropout anchor.

The reused key is invisible in the loss: check that the masks change between steps.

3. Converting the weights, both ways

A PyTorch checkpoint is a flat dictionary of names (blocks.0.attn.wq.weight) to tensors; an NNX model's state is a nested tree of paths (blocks/0/attn/wq/kernel) to arrays, with every Linear weight transposed. Watch what the transpose does to a real corner of one weight, then the same animation on GPT-2's checkpoint, where nothing should move.

Each element keeps its value; only its position changes, and a square matrix loaded without the transpose raises nothing. Values are the real top-left corner (6 rows by 8 columns as stored) of blocks.0.attn.wq.weight after 500 training steps, and of GPT-2's h.0.attn.c_proj.weight; colour by value (blue negative, orange positive).

The fix is a rule, not a hand copy. Write the conversion as a rule on the path, apply it to every leaf, and let shape checks fail loudly. Here the whole rule is a four-entry table: kernel becomes weight and is transposed; bias, scale (to weight) and embedding (to weight) are copied. The file in between is safetensors: a JSON header (names, dtypes, shapes, byte offsets) followed by raw bytes, with no pickle and so no code executed on load.

def torch_name(path):                  # ('blocks', 0, 'attn', 'wq', 'kernel') -> ('blocks.0.attn.wq.weight', True)
    *mods, leaf = [str(p) for p in path]
    tname, transpose = {"kernel": ("weight", True), "bias": ("bias", False),
                        "scale": ("weight", False), "embedding": ("weight", False)}[leaf]
    return ".".join(mods + [tname]), transpose

flat_in = safetensors.flax.load_file("tinylm_torch.safetensors")      # {name: jax.Array}
state = nnx.state(model, nnx.Param)
leaves = []
for path, var in nnx.to_flat_state(state):
    name, tr = torch_name(path)
    w = flat_in[name].T if tr else flat_in[name]
    assert w.shape == var[...].shape, (name, w.shape, var[...].shape)  # the check a hand copy forgets
    leaves.append((path, var.replace(w)))
nnx.update(model, nnx.from_flat_state(leaves))
From src/runs/pj_convert.py, run on the running example's 500-step weights.

How to check, all three passed here: every name used exactly once (unused PyTorch keys: 0), logits within float32 noise of the source, and the reverse trip back to PyTorch loading with strict=True and comparing bit for bit (true: a transpose is exact, so anything but bitwise equality is a bug). Cost: nothing measurable at this size (the file is 3,311,552 bytes for 3,305,472 bytes of float32 weights; the header is 6,072 bytes). At 70B parameters the same loop needs the model sharded while it loads; Tunix and MaxText do exactly this with a regex table (section 6).

The conversion errors you will meet (real messages)
  • save_file on a transposed view: ValueError: You are trying to save a non contiguous tensor: `w` which is not allowed. It either means you are trying to save tensors which are reference of each other in which case it's recommended to save only the full tensors, and reslice at load time, or simply call `.contiguous()` on your tensor to pack it before saving. Fix: .contiguous().
  • bfloat16 through numpy: TypeError: Got unsupported ScalarType BFloat16. numpy has no bfloat16; go through safetensors' flax loader (dtype bfloat16, bit-equal: true), DLPack (true), or .view(torch.int16) then .view(jnp.bfloat16) (true).
  • Assigning a [512, 128] PyTorch weight into a [128, 512] kernel: ValueError: Incompatible types for broadcasting: input type=float32[512,128] and requested type=float32[128,512]
  • The same wrong shape through nnx.update: no error at update time; the error only comes at the first call, TypeError: dot_general requires contracting dimensions to have the same shape, got (128,) and (512,).. Hence the explicit assert above.
  • A missing key in PyTorch: strict=True raises RuntimeError: Error(s) in loading state_dict for TinyLM: Missing key(s) in state_dict: "ln_f.bias".; strict=False only returns _IncompatibleKeys(missing_keys=['ln_f.bias'], unexpected_keys=[]), which most code ignores.

4. The equivalence test: is the gap rounding or a bug?

Two correct ports never agree exactly: matrix multiplies and reductions add the same numbers in a different order in each library, and float32 addition is not associative, so every operation can differ in its last bit. The test separates that noise from a real difference and finds where the difference first appears. The ladder: fix one batch and one set of weights, then compare five things in order, each a superset of the one before: logits (the forward pass), loss (the reduction), gradients (the backward pass), parameters after one optimiser step (the optimiser and its defaults) and training curves (everything, over time). The first rung that fails names the part that is wrong: forward bugs fail at the first rung; optimiser bugs pass three rungs and fail at the fourth or fifth. Pick a port and step up the ladder.

Every number is a real measurement from src/runs/pj_hunt.py against the PyTorch twin, same weights, same batch 0. Pass thresholds (this page's choice, 4 to 45 times the correct port's own float32 differences): logits 1e-5, loss 1e-5, gradients 1e-5, one step 1e-6, curves 1e-4 over 300 steps. Gradients exclude the key biases (the key-bias puzzle, closed block at the end of this section).
Predict: a port sums the per-character losses instead of averaging them, so every gradient is 4,096 times larger. The run clips gradients to norm 1 and uses AdamW. What happens to training?
It trains, differently: validation 2.2746 against 2.2635, curves apart from step 33. Adam alone would barely notice the scale (it divides by the running root-mean-square of the gradient), but clipping happens first: with gradients 4,096 times larger, every step is clipped to norm 1, while the correct run is clipped only when its norm exceeds 1. The fourth rung (one step) does not catch it, because Adam's first update is the learning rate times the sign of the gradient, whatever the gradient's size (for gradients well above Adam's eps of 1e-8).

Tolerances depend on the dtype

"Close enough" is a multiple of the dtype's machine epsilon (the gap between 1 and the next float) times the size of the numbers compared, times a factor for how many operations accumulate. The epsilons: float64 2.2e-16, float32 1.2e-7, float16 9.8e-4, bfloat16 0.0078.

Why a correct port still drifts in float64: Adam multiplies tiny gradient differences by lr / eps = 2,000
The key-bias puzzle: why every comparison skips the key projections' biases

Adding the same vector b to every key adds the same number q.b to every score in a query's row, and softmax ignores a constant added to a whole row, so the true gradient of a key bias is exactly zero. Computed, it is float noise: 2.2e-11 (PyTorch) and 2.5e-11 (JAX) in float32, and 3.1e-20 and 4.1e-20 in float64. The two frameworks' noise is unrelated, so their key biases take unrelated paths; the root's run measured them as the largest weight difference at 500 steps, with no effect on outputs (the root's Topic: jax-and-tpu, Training lab, section 5).

A refinement of the usual story ("Adam turns the noise into full-size steps"). With eps = 1e-8 and gradients near 1e-11, Adam's update is about lr x g / eps: around 2e-6 per step at the full learning rate of 1e-3, some five hundred times smaller than a normal step of about lr. What makes key biases drift is that nothing pulls them back (no gradient restores them, and they are not decayed), so the two frameworks' unrelated noise accumulates. Measured: after one step the key biases differ by 8.1e-9, other weights by 2.1e-7; after 100 steps the key biases differ by 7.2e-5 while every other weight still agrees to 3.6e-7. By 4,000 steps the ordinary weights have drifted further than the key biases anyway (the root's twin_long.json).

5. Training both, and judging the drift

The root's Training lab trained the PyTorch, plain-JAX and NNX twins for 4,000 steps on identical batches; cited, not rerun. The curves agree to 1e-5 until step 312 and to 1e-4 until step 1446, and never differ by 1e-3 (largest 9.5e-4). The gap grows steadily, window by window:

How to judge it. Drift that grows smoothly from float noise and stays orders of magnitude below the run-to-run variation of a different seed is not a bug; training is a chaotic iteration that amplifies last-bit differences. Drift that appears at step 0, or jumps at a step, is. Plain JAX and NNX lower to nearly the same XLA program and stay within 2.7e-5 of each other over the whole run, an order of magnitude closer than PyTorch and JAX: the size of the drift tracks how different the two programs are, which is what rounding predicts.

Step times of the three twins, and what transfers

Measured on Apple M1 Pro (CPU), shared machine: median step time 0.164 s (PyTorch), 0.193 s (plain JAX), 0.225 s (NNX). Not a framework comparison: a tiny model on a loaded CPU, where each framework calls a different matmul library. What transfers to TPU and GPU is the method and the drift's shape; not the step times, and not the bit patterns (a TPU's default matmul precision is bfloat16, section 2).

6. Porting a Hugging Face model: GPT-2 by hand

Why by hand. The old easy path, FlaxGPT2LMHeadModel.from_pretrained, is closing: Hugging Face's transformers v5 announcement (1 December 2025) says they are "sunsetting our Flax/TensorFlow support in favor of focusing on PyTorch as the sole backend", while "working with partners in the Jax ecosystem", naming MaxText (Hugging Face blog). Measured here: transformers 5.19.0 exports 0 names starting with "Flax". The checkpoints remain (the GPT-2 repository still carries a flax_model.msgpack), and safetensors files load into JAX directly, so a port today is: read the safetensors, write the forward pass, check it against transformers' PyTorch model.

GPT-2 small, from openai-community/gpt2 at revision 607a30d7 (124,439,808 parameters in 160 tensors, of which 12 are causal-mask buffers, not weights), ported in about 25 lines of plain JAX (src/runs/pj_gpt2.py). Three facts of this checkpoint decide the port, and each contradicts a habit from the running example:

  • No transpose. GPT-2's projections are Hugging Face's Conv1D, whose weight is stored [in, out], already JAX's layout (excerpt in the closed block below). Transposing "because PyTorch is [out, in]" breaks it.
  • Tanh GELU. The config says "activation_function": "gelu_new", the tanh approximation: here jax.nn.gelu's default is the right one.
  • Tied head. There is no lm_head.weight in the file: the output projection is the token embedding transposed (x @ wte.T). transformers' model shares the tensor (tied: true).
Prompt "The quick brown fox", greedy decoding of 20 tokens, float32, both on Apple M1 Pro (CPU). The JAX port runs eagerly without a KV cache (29.5 s against transformers' 2.2 s): fine for a check, not for serving.
Greedy text is a weak test
The exact-GELU mistake moves the logits by 0.075 and still produces identical greedy text; the epsilon mistake likewise. Only the transpose mistake shows in text ("The quick brown fox. the the the the the the the the the the the the the the the the the the the"). Compare logits with a tolerance; read text only as a smoke test.
Where the real ports live: Tunix and MaxText converters, and the source excerpts

At scale nobody writes a forward pass per checkpoint by hand without a table. Tunix (v0.1.7) loads Hugging Face safetensors into NNX models with a regex from each PyTorch name to a JAX path plus a permutation and reshape (excerpt below); MaxText converts both ways with checkpoint_conversion/to_maxtext.py and to_huggingface.py (MaxText at 1a95d1e5). Both are the same idea as section 3's four-entry rule, grown to whole model families; JAX LLM codebases reads them in depth.

Saving the transformers model back with safetensors' plain save_file fails on the tie: RuntimeError: Some tensors share memory, this will lead to duplicate memory on disk and potential differences when loading them again: [{'transformer.wte.weight', 'lm_head.weight'}]. A potential way to correctly save your model is to use `save_model`.

7. Interop: using PyTorch code from JAX without porting it

Sometimes only one piece needs to be in the other framework: a JAX loss inside a PyTorch training loop, a PyTorch model evaluated inside a JAX pipeline, or a PyTorch codebase that must run on TPUs. Four tools, all tried here on the running example (measurements in the closed block below):

ToolWhat it doesUse it when
DLPack (jax.dlpack.from_dlpack, torch.from_dlpack)hands a buffer from one framework to the other without copying; an in-place op on one side changes the othermoving activations or batches between frameworks on one device; copy (.clone()) if either side may mutate
A jax2torch bridge (a torch.autograd.Function calling a jitted JAX function)forward runs JAX, backward returns JAX's gradients to autograda JAX-only component (a loss, a sampler, a kernel) inside a PyTorch loop
torchax (google/torchax)runs PyTorch modules with JAX arrays underneath; torchax.extract_jax(module) returns the weights as a pytree and the forward as a pure JAX functiontrying a PyTorch model on TPU, or under jit, grad and sharding, before deciding to port; pin the torch version it was tested with

How to check an interop boundary. The same ladder: the bridge's loss and gradients against the native ones. Two costs: every crossing is a host-side Python call (no fusion across the boundary), and under jax.jit a PyTorch call needs jax.pure_callback, which XLA cannot optimise or differentiate unless you supply the rule.

8. The porting checklist, and when not to port

The whole page as the order to work in. Each item names the failure it prevents and where it was measured.

  1. Decide whether to port at all (table below): try torchax or PyTorch/XLA first if the goal is one TPU run.
  2. Translate state, not syntax: weights, gradients, optimiser state and keys become arguments and return values of one jitted step (section 1).
  3. Write every default explicitly on both sides: norm epsilon and variance, GELU form, initialisers, mask convention and fill, loss reduction and ignored labels, weight decay and its mask, clip position, schedule count, matmul precision (section 2).
  4. Convert weights by a rule on the path, with a shape assert per tensor, every name used once, and a bitwise round trip (section 3).
  5. Climb the ladder on one batch with dropout off: logits, loss, gradients, one step, curves; stop at the first failing rung (section 4).
  6. Repeat in float64 when a gap is near the thresholds: rounding shrinks by about nine orders of magnitude, a bug does not (section 4).
  7. Judge curves against seed-to-seed variation, not against zero; turn dropout on last and compare statistics (sections 2 and 5).
  8. Only then change precision or sharding, each as its own comparison, with precision=HIGHEST for the equivalence run on a TPU (section 2, hardware numerics).

When not to port. A port costs the translation, the equivalence test and, from then on, two code bases (or one you know less well). It pays when the target gives something the source cannot. Judgement, labelled as such:

Rung thresholds as in the Reading tab, section 4: logits, loss and gradients 1e-5, one step 1e-6, curve 1e-4. A dash means the rung could not be computed (the loss was already NaN). What the runs say
  • Forward-pass differences show at step 0. The epsilon, GELU, bfloat16 and mask switches all fail the logits rung; one batch of logits from copied weights catches every one of them before any training.
  • Optimiser differences pass three rungs. Weight decay, b2, clip position and the schedule's off-by-one leave logits and gradients identical and only appear at the one-step rung or in the curves.
  • Two differences are harmless. PyTorch's clipping formula and Flax's fast variance stay within the correct port's own noise for all 300 steps; the ladder passes them, which is the point of having thresholds.
  • A wrong mask can look like success. Without the causal mask the training loss collapses (the model reads the answer), validation with a proper mask is 5.79 against 2.26.
