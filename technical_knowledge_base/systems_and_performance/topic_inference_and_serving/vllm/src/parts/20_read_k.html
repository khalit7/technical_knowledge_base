Interview rehearsal: three questions that need the whole page (optional)
Walk me through what happens inside vLLM between an HTTP request arriving and the first token streaming back.
API server: route, sampling params, tokenize (InputProcessor), register a detokenizer and an output queue, send an EngineCoreRequest over ZeroMQ. Engine core: an input thread queues it; the busy loop adds it to the waiting queue (hashing its full blocks); schedule() admits it if its whole prompt fits, allocating blocks after a prefix-cache lookup, and gives it budget; the executor runs the forward pass and samples; update_from_output appends the token; an output thread sends it back. API server: detokenize, check stop strings, put into the request's queue, write a server-sent event. TTFT is queue time plus the prefill steps plus these hops.
Your p99 inter-token latency spikes whenever long prompts arrive. Which knobs?
Lower max_num_batched_tokens (smaller prefill chunks per step, so decode steps stay short), or set long_prefill_token_threshold; at the cost of slower TTFT for the long prompts. If it is a separate population, disaggregate prefill and decode ({{distributed page|n:3c65c17b0d0d8170bd7cdf47af0ec07b}}). Measure with vllm:inter_token_latency_seconds and the chunk sweep of section 5.
Throughput is flat but the waiting queue grows and KV usage is near 100%. What is the limit and what do you change?
Memory, not compute: requests cannot be admitted because their prompts do not fit. Options: raise gpu_memory_utilization if there is headroom, an FP8 KV cache (half the bytes per token), lower max_model_len to stop huge requests, more replicas, or a model with a smaller cache (GQA, MLA). Raising max_num_seqs does nothing here.
