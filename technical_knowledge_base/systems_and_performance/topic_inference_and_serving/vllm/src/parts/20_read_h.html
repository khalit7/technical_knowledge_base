7. Upgrades: what a new release changes under you

vLLM ships a minor release about every two weeks, each with several hundred commits. Most lines of a release note are model and kernel work; what an operator must read are the changed defaults and the breaking changes, because a deployment that never set a flag silently inherits the new value. The code walked through on this page is the v0.31.0 tag; what changed in the releases around it is in the closed table below.

Correction to the old page
The old page said v0.28.0 doubled max_num_batched_tokens from 8,192 to 16,384 for "any deployment that never set it". The release note says so in one line, but the change itself ({{PR #51726|https://github.com/vllm-project/vllm/pull/51726}}, merged 2026-08-11) only adds a new tier: the API server on GPUs with at least 160 GiB of memory now gets 16,384. An H100 or H200 server still defaults to 8,192, and the offline LLM class already used 16,384 there ({{arg_utils.py L2858 to L2887|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/engine/arg_utils.py#L2858}}). Section 5 has the full table.

An upgrade checklist that follows from the code

  1. Diff the resolved configuration, not the flags. vLLM logs its final VllmConfig at start-up; save it for the old and new versions and compare max_num_batched_tokens, max_num_seqs, the cache size in tokens and the CUDA graph sizes.
  2. Check which model runner you got. Grep for "Model Runner V2 does not yet support" (section 4).
  3. Check the removed flags and environment variables in your launch scripts; an unknown CLI flag stops the server, while a removed VLLM_ environment variable only logs "Unknown vLLM environment variable detected" ({{platforms/interface.py L1344|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/platforms/interface.py#L1344}}) and its setting is lost (--fail-on-environ-validation, off by default, turns that into an error: {{arg_utils.py L836|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/engine/arg_utils.py#L836}}).
  4. Replay real traffic with the same load generator at the same arrival rate and compare TTFT and ITL percentiles and preemptions (section 6), not one throughput number.
  5. Re-check prefix-cache behaviour when hashes change: v0.29.0 changed the seed default and v0.31.0 changed the extra keys, so caches shared across machines (LMCache, Mooncake, llm-d) must run the same version on every node.
  6. Check what the server now exposes and accepts. v0.32.0 serves a new endpoint by default and stops sending permissive CORS headers, so review the network policy in front of the server and add --allowed-origins for browser clients; clients that parse Responses reasoning events or count on max_tokens being reserved from the context need retesting.
