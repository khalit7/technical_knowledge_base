5. The knobs that matter

Dozens of flags exist; a handful decide how a deployment behaves, and each trades one thing for another. Defaults are read at v0.31.0; "how to check" names the metric of section 6; the {{Knob lab|#t-knob}} turns the first three on a live server.

Knob (default)What it controlsRaise it andHow to check
max_num_batched_tokens
(per hardware, below)		The per-step token budget: how many prompt tokens a step may prefill on top of the decodes.Prompts finish prefill in fewer steps (better TTFT, more throughput from big matrix multiplies), but every step that carries a big chunk is long, so users already streaming see a stall (worse ITL tail).ITL p99 against TTFT; Knob lab section 2
max_num_seqs
(1,024 / 256 / 128 per CPU worker)		The most requests in the running list.More users share each step (throughput up) until the step lengthens or the cache runs out; each user's TPOT rises.num_requests_running at the cap with a growing waiting queue; Knob lab section 1
gpu_memory_utilization
(0.92, {{cache.py L103|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/cache.py#L103}})		Share of the whole GPU vLLM may use; the KV cache gets what is left after weights, activations and CUDA graphs.A bigger cache (more concurrent users, fewer preemptions), less headroom for anything else on the GPU.The start-up line with the cache size in tokens; kv_cache_usage_perc, num_preemptions
enable_prefix_caching
(on, {{L142|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/cache.py#L142}})		Hashing and reusing full blocks across requests (section 3).Off: saves the hashing on unique prompts; loses every shared-prefix hit.prefix_cache_hits / prefix_cache_queries
enable_chunked_prefill
(on, {{scheduler.py L135|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/scheduler.py#L135}})		Whether a prompt may be split across steps.Off: a long prompt waits for a step with room for all of it and then stalls everyone for that step.ITL p99
long_prefill_token_threshold
(0, off)		A per-request cap on prefill tokens per step, so one long prompt cannot take the whole budget.Fairer budget among several prefills; each long prompt takes more steps.TTFT by prompt length
max_model_len
(the model's)		The longest request accepted; at start-up the cache must hold at least one such request.Lower it to start on a smaller GPU or to refuse giant prompts that would block admission.The "maximum concurrency" start-up line
kv_cache_dtype
(auto = model dtype)		Bytes per cached number; fp8 halves them against 16-bit.Twice the tokens in the same memory; a small accuracy risk (the parent page's {{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} measured 8-bit and 4-bit caches in llama.cpp).Cache size in tokens; quality on your eval
block_size
(16 on GPU, {{L71|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/cache.py#L71}}; 128 on CPU)		Tokens per block: the unit of allocation and of prefix-cache matching.Less metadata and fewer table entries; coarser sharing (a prefix is reused only in whole blocks) and more waste in each request's last block.Hit rate against block size
performance_mode
(balanced)		"throughput" doubles the default batch tokens and sequences ({{arg_utils.py L3064|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/engine/arg_utils.py#L3064}}) and, per its docstring, uses larger CUDA graphs and throughput-oriented kernels ({{vllm.py L448|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/vllm.py#L448}}); "interactivity" captures graphs for every batch size up to 32.One switch for the throughput-or-latency trade when you have not tuned the two knobs above.Both latency percentiles and throughput
-O level
(-O2)		torch.compile and CUDA graph mode (section 4).-O0 starts fastest and runs slowest; use it to iterate, never to benchmark.Start-up time; batch-1 decode speed

The per-hardware budget is chosen in get_batch_defaults ({{arg_utils.py L2829 to L2920|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/engine/arg_utils.py#L2829}}) from the device's memory, and differs between the HTTP server and the offline LLM class, because an offline batch job wants throughput and a server wants smooth streams:

Devicemax_num_batched_tokens, server / offlinemax_num_seqs, server / offline
GPU with at least 160 GiB (B200, B300, MI300X)16,384 / 16,3841,024 / 1,024
GPU with at least 70 GiB, not an A100 (H100, H200)8,192 / 16,3841,024 / 1,024
Other GPUs (A100, L40S, RTX 5090 and smaller)2,048 / 8,192256 / 256
CPU backend, per worker2,048 / 4,096128 / 256

TPUs have their own smaller values in the same function. Set both knobs explicitly in production: a default that depends on which GPU the scheduler landed on is a benchmark you cannot reproduce.

Predict: the CPU server here was given a 2 GiB KV cache (VLLM_CPU_KVCACHE_SPACE=2) for Qwen3-0.6B in float32 (229,376 bytes per token) with the CPU's 128-token blocks. How many tokens can it hold?
9,344: 2,147,483,648 / (128 × 229,376) = 73.1, so 73 whole blocks of 128 tokens. That is the number the parent page's {{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} read from vLLM's start-up log, and it is why 16 users with 413-token prompts and 128-token answers (16 × 541 = 8,656 tokens) already pushed it to 100% and into preemption there.
