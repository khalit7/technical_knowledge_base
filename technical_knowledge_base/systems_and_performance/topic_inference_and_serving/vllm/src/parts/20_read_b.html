1. One request, through vLLM's code

The problem. A GPU must never wait for Python. Tokenizing a prompt, turning token ids back into text, parsing JSON and writing HTTP responses are CPU work; if the loop that feeds the GPU also did them, the GPU would sit idle between steps. vLLM's answer since its V1 rewrite ({{V1 announcement, 2025-01-27|https://blog.vllm.ai/2025/01/27/v1-alpha-release.html}}) is to split the work across processes:

API server processHTTP (FastAPI), chat template, tokenizer, detokenizer, stop strings, streaming. One by default; --api-server-count adds more.
Engine core processThe busy loop: scheduler, KV cache manager, and the executor that drives the GPU workers. One per data-parallel rank.
GPU workerLoads weights, prepares inputs, runs the forward pass and the sampler. With one GPU it lives inside the engine core process (executor "uni", {{parallel.py L1033|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/parallel.py#L1033}}); with tensor parallelism, one process per GPU.
Between themZeroMQ sockets carrying msgpack-encoded requests one way and outputs the other; inside the engine core, two I/O threads and two Python queues.

Three consequences follow, and each is a classic production surprise.

  • Tokenizing and detokenizing happen in the API server, not on the GPU's critical path, so at high request rates the API server's single Python process can saturate before the GPU does; the {{architecture overview|https://github.com/vllm-project/vllm/blob/v0.31.0/docs/design/arch_overview.md}} sizes CPU cores for this, and --api-server-count scales it out.
  • The scheduler sees token ids, never text. Stop strings are checked in the API server after detokenizing ({{output_processor.py L720|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/output_processor.py#L720}}), which then aborts the request in the engine; stop token ids and max_tokens are checked in the engine itself.
  • Each step returns outputs for every running request at once, and the API server fans them out to one queue per request (RequestOutputCollector). One slow client does not slow the loop.
Predict: vllm serve <model> -tp 4 on one server with four GPUs. How many vLLM processes run?
Six. One API server, one engine core, and one worker process per GPU, because with more than one GPU the executor becomes "mp" (multiprocessing). The {{architecture overview|https://github.com/vllm-project/vllm/blob/v0.31.0/docs/design/arch_overview.md}} gives the general count: A API servers + DP engine cores + N workers (+1 coordinator when DP > 1); -tp 2 -dp 4 on eight GPUs makes 17. With one GPU it is two processes, the worker living inside the engine core. The CPU backend is the exception: it always uses the multiprocessing executor because OpenMP threads must be set up in their own process ({{cpu.py L317 to L324|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/platforms/cpu.py#L317}}), so the CPU container here showed three vLLM processes measured here:

The same three steps without and with asynchronous scheduling

illustrative durations (CPU work 3 ms, GPU work 10 ms per step) to show the mechanism; the mechanism itself is the source's: with async scheduling the engine core keeps a batch queue of 2 ({{vllm.py L592|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/vllm.py#L592}}) and step_with_batch_queue schedules step N+1 before step N's result is back ({{core.py L670|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/core.py#L670}}). The CPU platform turns it off ({{cpu.py L314|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/platforms/cpu.py#L314}}), so the stepper's trace is synchronous.

What async scheduling costs. The scheduler decides step N+1 before it knows step N's token, so a request that will finish at step N is scheduled once more; the running loop skips a request whose in-flight tokens already reach max_tokens ({{scheduler.py L635|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L635}}), and outputs that arrive for a request preempted in between are marked stale ({{scheduler.py L1563|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L1563}}). When it matters: small models and small batches, where the GPU step is a few milliseconds and the CPU work is the same order. How to check: a profile with gaps between GPU kernels at batch 1 means the CPU is the bottleneck.
