1. One request, through vLLM's code

One streamed request crosses two processes and back: follow it function by function

source: vLLM v0.31.0, every line number linked in the caption. The token chip shows what travels at each step: text, token ids, a scheduler decision, a sampled token id, text again.

The problem. A GPU must never wait for Python. Tokenizing, detokenizing, parsing JSON and writing HTTP are CPU work; if the loop that feeds the GPU did them, the GPU would idle between steps. So since the V1 rewrite the work is split across processes: one API server (FastAPI, chat template, tokenizer, detokenizer, stop strings, streaming; --api-server-count adds more), one engine core per data-parallel rank (the busy loop, with two I/O threads and two Python queues so socket work never blocks it), and the GPU worker, which lives inside the engine core with one GPU (executor "uni", {{parallel.py L1033|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/parallel.py#L1033}}) and is one process per GPU with tensor parallelism. ZeroMQ sockets carry msgpack-encoded requests one way and outputs the other.

The animation, step by step: one streamed request, function by function

  1. The client sends one request. A JSON body with the prompt and stream: true. FastAPI routes it to {{create_completion (api_router.py L47)|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/entrypoints/openai/completion/api_router.py#L47}}.
  2. The serving layer builds sampling parameters. OpenAIServingCompletion.create_completion ({{serving.py L109|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/entrypoints/openai/completion/serving.py#L109}}) turns the request into SamplingParams and calls engine_client.generate() ({{L203|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/entrypoints/openai/completion/serving.py#L203}}), an async generator.
  3. Tokenize, in the API server. AsyncLLM.add_request runs the InputProcessor ({{async_llm.py L449|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/async_llm.py#L449}}): chat template and tokenizer, on this process's CPU. It also creates the request's own output queue, a RequestOutputCollector ({{L495|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/async_llm.py#L495}}).
  4. Register, then send to the engine. The OutputProcessor gets an incremental detokenizer for this request ({{L547|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/async_llm.py#L547}}); then {{add_request_async (L550)|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/async_llm.py#L550}} sends an EngineCoreRequest, msgpack over a ZeroMQ socket ({{core_client.py L1259|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/core_client.py#L1259}}).
  5. Engine core: an I/O thread receives it. A dedicated input thread decodes the message and puts it on a Python queue ({{core.py L1754|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/core.py#L1754}}), so socket work never blocks the loop.
  6. The busy loop picks it up. Each loop iteration first drains the input queue ({{_process_input_queue, L1496|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/core.py#L1496}}), so new requests join between steps; Scheduler.add_request ({{scheduler.py L2557|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L2557}}) appends it to the waiting queue and its full blocks are hashed for the prefix cache.
  7. schedule(): who runs, how many tokens. The scheduler fills a token budget: running requests first, then waiting ones, allocating KV blocks for each ({{scheduler.py L562|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L562}}). Our request is admitted and gets its prompt (or a chunk of it). Section 2 opens this function.
  8. The model runs. execute_model ({{core.py L641|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/core.py#L641}}) goes through the executor to the worker's model runner: build input ids, positions and block tables, run the forward pass ({{model_runner.py L1676|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/worker/gpu/model_runner.py#L1676}}), then sample one token per request ({{L2050|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/worker/gpu/model_runner.py#L2050}}).
  9. update_from_output(): append, check, free. The sampled id is appended to the request; EOS, stop token ids and max_tokens are checked here; a finished request's blocks go back to the pool ({{scheduler.py L1967|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L1967}}).
  10. Outputs leave the engine. The step's outputs for every running request go on the output queue ({{L1526|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/core.py#L1526}}); an output thread sends them over ZeroMQ ({{L1856|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/core.py#L1856}}). The loop is already scheduling the next step.
  11. Detokenize, check stop strings. The API server's output_handler task ({{async_llm.py L813|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/async_llm.py#L813}}) hands them to process_outputs ({{output_processor.py L646|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/output_processor.py#L646}}): incremental detokenizing and stop-string checks ({{L720|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/output_processor.py#L720}}), then a put into this request's collector ({{L745|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/output_processor.py#L745}}).
  12. Stream it out, and repeat. generate() yields from that collector ({{L735|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/async_llm.py#L735}}); the serving layer writes one server-sent event. Steps 7 to 12 repeat once per output token until the request finishes.

Three consequences, each a classic production surprise:

  • Tokenizing and detokenizing happen in the API server, not on the GPU's critical path, so at high request rates that single Python process can saturate before the GPU does; the {{architecture overview|https://github.com/vllm-project/vllm/blob/v0.31.0/docs/design/arch_overview.md}} sizes CPU cores for this, and --api-server-count scales it out.
  • The scheduler sees token ids, never text. Stop strings are checked in the API server after detokenizing ({{output_processor.py L720|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/output_processor.py#L720}}), which then aborts the request in the engine; stop token ids and max_tokens are checked in the engine itself.
  • Each step returns outputs for every running request at once, and the API server fans them out to one queue per request (RequestOutputCollector), so one slow client does not slow the loop.
Predict: vllm serve <model> -tp 4 on one server with four GPUs. How many vLLM processes run?
Six. One API server, one engine core, and one worker process per GPU, because with more than one GPU the executor becomes "mp" (multiprocessing). The {{architecture overview|https://github.com/vllm-project/vllm/blob/v0.31.0/docs/design/arch_overview.md}} gives the general count: A API servers + DP engine cores + N workers (+1 coordinator when DP > 1); -tp 2 -dp 4 on eight GPUs makes 17. With one GPU it is two processes, the worker living inside the engine core. The CPU backend is the exception: it always uses the multiprocessing executor because OpenMP threads must be set up in their own process ({{cpu.py L317 to L324|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/platforms/cpu.py#L317}}), so the CPU container here showed three vLLM processes measured here:

Async scheduling hides the CPU's work behind the GPU's: the same three steps, before and after

illustrative durations (CPU work 3 ms, GPU work 10 ms per step) to show the mechanism; the mechanism itself is the source's: with async scheduling the engine core keeps a batch queue of 2 ({{vllm.py L592|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/vllm.py#L592}}) and step_with_batch_queue schedules step N+1 before step N's result is back ({{core.py L670|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/engine/core.py#L670}}). The CPU platform turns it off ({{cpu.py L314|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/platforms/cpu.py#L314}}), so the recorded runs in section 3 are synchronous.

Async scheduling. The CPU work of a step (scheduling, then applying the sampled tokens) can run while the GPU computes the previous step, as long as the scheduler does not need that step's tokens first.

The animation, step by step

  1. Step 1. The engine core schedules (3 ms), then waits while the GPU runs the forward pass (10 ms); only then can it apply the sampled tokens (1 ms). The GPU is idle while the CPU decides.
  2. Step 2. The next schedule() cannot start before step 1's tokens are applied, so the GPU idles another 4 ms between forward passes.
  3. Step 3. The same gap again: every step costs the CPU's time plus the GPU's, 14 ms.
  4. Step 4. Four steps take 56 ms, and the GPU is busy 71% of the time.
  1. Step 1. With a batch queue of 2, the engine core schedules step 1 (3 ms), launches it, and schedules step 2 while forward pass 1 runs.
  2. Step 2. Forward pass 2 starts the moment pass 1 ends; step 1's tokens are applied while the GPU is already busy, and step 3 is scheduled in its shadow.
  3. Step 3. As long as the CPU work (4 ms) is shorter than the forward pass (10 ms), each step costs only the forward pass.
  4. Step 4. Four steps take 44 ms instead of 56, and the GPU is busy 91% of the time; only the first schedule and the last update stay exposed.

What async scheduling costs. Step N+1 is decided before step N's token is known, so a request that will finish at step N is scheduled once more; the running loop skips a request whose in-flight tokens already reach max_tokens ({{scheduler.py L635|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L635}}), and outputs that arrive for a request preempted in between are marked stale ({{scheduler.py L1563|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L1563}}). It matters for small models and small batches, where a GPU step is a few milliseconds and the CPU work is the same order; a profile with gaps between GPU kernels at batch 1 means the CPU is the bottleneck.
