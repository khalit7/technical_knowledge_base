vLLM is the open-source serving engine most deployments start from: give it a model and it serves an OpenAI-compatible HTTP API, batching many users onto the same GPUs. The parent page, {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}, explains what every engine must do (prefill and decode, the KV cache, continuous batching, chunked prefill, prefix caching). This page opens vLLM itself, at the release tagged v0.31.0 (2026-10-05, commit db9527a4), so that you can read its code, predict what it will do with your traffic, tune it and change it.

It began as the PagedAttention paper's engine in the Sky Computing Lab at UC Berkeley ({{README|https://github.com/vllm-project/vllm/blob/v0.31.0/README.md}}), became a PyTorch Foundation hosted project on 2025-05-07 ({{PyTorch Foundation|https://pytorch.org/blog/pytorch-foundation-welcomes-vllm/}}), and is also the generation engine inside RL post-training stacks: TRL's GRPO and online DPO trainers generate with vLLM 0.21.0 to 0.31.0 ({{TRL docs|https://github.com/huggingface/trl/blob/main/docs/source/vllm_integration.md}}), and verl lists vLLM, SGLang and Transformers for rollouts ({{verl README|https://github.com/volcengine/verl}}).

The whole engine in five sentences
  1. Two processes, two queues. An API server process tokenizes, detokenizes and speaks HTTP; an engine core process runs a busy loop; they exchange messages over ZeroMQ sockets (section 1).
  2. One loop, three calls. Every iteration of the engine core calls schedule(), then the model, then update_from_output() (v1/engine/core.py L630).
  3. No phases, only a token budget. The scheduler gives each request some number of tokens to compute this step so that its computed count catches up with its length; prefill, chunked prefill, decode and speculative tokens are all the same thing to it (section 2).
  4. Memory is a pool of 16-token blocks. A block pool hands out blocks from the head of a free queue, takes them back in an order that makes the tail least recently used, and names every full block by a hash of its tokens and its parent's hash, which is the whole prefix cache (section 3).
  5. The GPU side is a model runner per GPU. Since v0.29.0 the default is Model Runner V2, rewritten for asynchronous scheduling (section 4).

The running example is the parent page's chat assistant, shrunk to what this laptop can run: Qwen3-0.6B answering customers of a bicycle shop, every request starting with the same system prompt. Two kinds of evidence appear, and every number says which:

  • measured here: vLLM's own CPU image vllm/vllm-openai-cpu:v0.31.0-arm64 in Docker on an Apple M1 Pro (5 CPUs and 9.7 GiB for Docker's virtual machine, 4 CPUs for the stepper's recordings; float32 weights). Its Python files for the scheduler, the KV cache manager, the block pool, the engine core, the async front end and the metrics are byte-identical to the v0.31.0 tag (eight files, MD5 compared, src/inputs/image_vs_tag_md5.txt), so the scheduling and caching decisions are exactly what a GPU server makes; only the speed is not. The {{Scheduler stepper|#t-step}} records that real scheduler while the real engine serves the real model, step by step.
  • source: lines read in the v0.31.0 tree, written file Lnnn and linked to GitHub at that tag; release notes and docs as published, dated.
