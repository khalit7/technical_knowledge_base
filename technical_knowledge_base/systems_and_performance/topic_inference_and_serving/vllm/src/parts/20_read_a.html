The idea in one screen

vLLM is one loop in its own process: every step it calls schedule(), runs the model once, and calls update_from_output(). The scheduler gives each request a share of a per-step token budget and the blocks to hold it from a pool of fixed-size KV blocks; almost every production knob changes the budget, the pool, or how fast the model step runs.

One loop between the API server and the GPU, and where each knob acts

  1. Two processes, two queues. The API server speaks HTTP, tokenizes and detokenizes; the engine core runs a busy loop; they exchange msgpack messages over ZeroMQ (section 1).
  2. One loop, three calls. schedule(), the model, update_from_output() (v1/engine/core.py L630).
  3. No phases, only a token budget. Prefill, chunked prefill, decode and speculative tokens are all "give this request some tokens this step" (section 2).
  4. Memory is a pool of 16-token blocks (on GPU): a free queue whose order is the eviction policy, and a map from block hash to block that is the whole prefix cache (section 3).
  5. The GPU side is a model runner per GPU, Model Runner V2 by default since v0.29.0 (section 4).

Knob names in accent sit where they act; section 5 gives each one's default and trade. source: vLLM v0.31.0.

You need: continuous batching, paged attention and prefix caching as ideas, with their papers: {{Batching, KV cache and scheduling in depth|n:3c65c17b0d0d819db53bd2c48909e5b2}} owns them, and this page shows only how vLLM's code implements them. How many bytes one token's cache takes for a given model: {{Long context|n:3fd5c17b0d0d81059ee1ce20c0326dc5#t-kv}} (KV-cache calculator). Prefill, decode, TTFT and ITL: the root, {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}.

Engine core
the process that runs the busy loop: scheduler, KV cache manager, and (with one GPU) the worker.
Token budget
max_num_batched_tokens: the most tokens one step may compute, across all requests.
Block pool, free queue
every KV block's metadata, and the list of blocks nobody is using, in the order they will be handed out.
Block hash
a hash of a full block's tokens and its parent block's hash: the prefix cache's key.
Model runner, persistent batch
the per-GPU object that turns the scheduler's decision into tensors, keeping them allocated across steps.
MRV2
Model Runner V2, the rewritten runner, default since v0.29.0.

How the evidence was made, and running the CPU image yourself (provenance)

measured here: vLLM's own CPU image vllm/vllm-openai-cpu:v0.31.0-arm64 in Docker on an Apple M1 Pro (5 CPUs and 9.7 GiB for Docker's virtual machine, 4 CPUs for the stepper's recordings; float32 weights). Its Python files for the scheduler, the KV cache manager, the block pool, the engine core, the async front end and the metrics are byte-identical to the v0.31.0 tag (eight files, MD5 compared, src/inputs/image_vs_tag_md5.txt), so the scheduling and caching decisions are exactly what a GPU server makes; only the speed is not.

Not run here: CUDA graphs, torch.compile on GPU, tensor parallelism, FlashAttention kernels, and Model Runner V2 itself (the CPU backend still uses the V1 model runner, section 4). Each is described from source and docs, and labelled.

Running the CPU image yourself: four traps the sibling pages hit. In Docker it needs --shm-size (it wants about 160 MiB of shared memory, more than Docker's 64 MiB default) and a --gpu-memory-utilization below the memory actually free, because by default it reserves 0.92 of the virtual machine's RAM ({{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}, which ran it for start-up and multi-LoRA tests). Tensor or pipeline parallelism above 1 needs VLLM_CPU_OMP_THREADS_BIND set by hand, since the automatic binding asserts one NUMA node per worker and refuses two workers on a one-node machine; and VLLM_ENABLE_V1_MULTIPROCESSING=0 (engine in the calling process) is not supported by the CPU backend's OpenMP thread setup (vllm/platforms/cpu.py L317 to L324 at v0.31.0). {{Distributed and disaggregated serving|n:3c65c17b0d0d8170bd7cdf47af0ec07b}} (section 4, closed block "Measured here") ran TP 2 and PP 2 on this image.

Where vLLM comes from (context)

It began as the PagedAttention paper's engine in the Sky Computing Lab at UC Berkeley ({{README|https://github.com/vllm-project/vllm/blob/v0.31.0/README.md}}), became a PyTorch Foundation hosted project on 2025-05-07 ({{PyTorch Foundation|https://pytorch.org/blog/pytorch-foundation-welcomes-vllm/}}), and is also the generation engine inside RL post-training stacks: TRL's GRPO and online DPO trainers generate with vLLM 0.21.0 to 0.31.0 ({{TRL docs|https://github.com/huggingface/trl/blob/main/docs/source/vllm_integration.md}}), and verl lists vLLM, SGLang and Transformers for rollouts ({{verl README|https://github.com/volcengine/verl}}). The V1 rewrite that gave it the process split of section 1 was announced on 2025-01-27 ({{V1 announcement|https://blog.vllm.ai/2025/01/27/v1-alpha-release.html}}).
