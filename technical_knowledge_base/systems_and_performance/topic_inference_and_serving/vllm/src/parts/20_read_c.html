2. The scheduler loop

The problem. Every step, choose which requests run and how many of their tokens, without running out of KV blocks and without letting one long prompt freeze everyone else's stream. vLLM's answer is one function, Scheduler.schedule() ({{scheduler.py L562|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L562}}), whose first comment states the design:

# There's no "decoding phase" nor "prefill phase" in the scheduler. # Each request just has the num_computed_tokens and num_tokens_with_spec. # At each step, the scheduler tries to assign tokens to the requests # so that each request's num_computed_tokens can catch up its # num_tokens_with_spec. This is general enough to cover chunked prefills, # prefix caching, speculative decoding, and the "jump decoding" optimization. (L564 to L573, abridged)

So a request is two numbers: how many of its tokens exist (prompt plus output so far, plus draft tokens when speculating) and how many already have their keys and values in the cache. A new request has 2,000 tokens and 0 computed: it needs 2,000. A decoding request has 2,301 tokens and 2,300 computed: it needs 1. A prefix-cache hit simply starts a request with some tokens already computed. The scheduler hands out a per-step token budget (max_num_batched_tokens, section 5) to close those gaps.

Fig. 2, step by step: one call of schedule() and the model step after it, in the order the code runs

Step 4 of the recorded run with prefix caching off (section 3): the real engine's token counts and block numbers, a 64-token budget, 32-token blocks, 29 usable blocks. measured here

  1. Two numbers per request. A has computed 105 of its 106 tokens (it is decoding: it needs 1); B 87 of its 111-token prompt (it needs 24); C has just arrived with 104 tokens and none computed. The scheduler closes those gaps within the budget.
  2. Loop 1, running requests first. In order of admission ({{L630|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L630}}): tokens wanted, capped by what is left of the budget ({{L681|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L681}}), then allocate_slots for the blocks those tokens need. A gets 1 token, B 24 and block 8 for its last ones: 25 of 64 used. If the pool is empty, preempt and retry (below).
  3. Loop 2, waiting requests. Only if nothing was preempted this step ({{L873|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L873}}), and while fewer than max_num_seqs run ({{L893|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L893}}; 4 here): look up the prefix cache, cut the prompt to what the budget allows, allocate. C's whole prompt (4 blocks) fits in the 21 free blocks, so it is admitted with the 39 tokens left and blocks 9 and 10. The first request that does not fit stops the loop ({{L1223|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L1223}}): first come, first served, including the head-of-line blocking that implies.
  4. One flat batch. The model runner (section 4) lays the 64 tokens out in one row, A's 1, B's 24 and C's 39, each with its position and its request's block table, so attention reads and writes the right blocks: no padding, no separate prefill and decode passes.
  5. One forward pass. All 64 tokens go through Qwen3-0.6B's 28 layers together, and each token's keys and values are written into its own request's blocks: A's block 4, B's blocks 7 and 8, C's blocks 9 and 10.
  6. After the model runs. update_from_output ({{L1967|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L1967}}) appends each sampled token, checks EOS, stop ids and max_tokens, and frees the blocks of finished requests. A and B each gain one token (B's prompt is now complete, so this is its first output token); C's chunk ends mid-prompt, so it gets none and finishes its prompt over the next two steps (62, then 3 tokens).

Preemption. Under FCFS the victim is self.running[-1], the most recently admitted request ({{L771|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L771}}); under the priority policy, the lowest priority, latest arrival (stepped through against this same code on the {{Batching, KV cache and scheduling|n:3c65c17b0d0d819db53bd2c48909e5b2}} page, section 6). Its blocks are freed, its computed count reset to 0, and it goes to the front of the waiting queue ({{L1538 to L1580|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L1538}}). There is no swap to CPU memory in this engine: preemption is recompute. (CPU offload exists, but as a KV connector tier, not as the preemption path.)

Two admission rules that surprise people. First, a waiting request is admitted only when its whole prompt fits in free blocks, not just the first chunk: scheduler_reserve_full_isl defaults to True ({{config/scheduler.py L191|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/scheduler.py#L191}}) and is passed as full_sequence_must_fit ({{L1218|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L1218}}; checked in {{kv_cache_manager.py L519|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/kv_cache_manager.py#L519}}). The parent page's {{Serving simulator|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} found this when its scheduler was checked against this very code: it had to change to match, and then agreed with vLLM on all 10 traces, 2,535 steps and 39 preemptions. Second, chunking is on by default ({{config/scheduler.py L135|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/scheduler.py#L135}}); with it off, a prompt longer than the remaining budget waits for a step with room ({{L1115|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L1115}}).

Predict: the budget is 64 tokens, two requests are decoding, and a new 150-token prompt is waiting with plenty of free blocks. How many of its tokens are computed this step?
62. Running requests are served first: the two decodes take 1 token each, leaving 62 of the 64; the new request is admitted (its whole prompt fits in free blocks) and gets a 62-token chunk, then the rest in later steps. The recorded run at the end of section 3 shows exactly this on the real engine with a 64-token budget.
Predict: the pool is full and the running list, in admission order, is [A, B, C]. A needs one more block to decode. What does the scheduler do?
It preempts C (self.running.pop(), L803), frees its blocks, resets its computed tokens to 0 and puts it at the front of the waiting queue; A then gets its block. C will be prefilled again later: with prefix caching on, its freed full blocks keep their hashes, so much of that recompute is a cache hit if nobody has evicted them in between. No new request is admitted in a step that preempted.
Predict: a 4,000-token prompt arrives; 150 blocks of 16 tokens are free (2,400 tokens); the budget is 2,048 and chunked prefill is on. Is its first chunk scheduled?
No. The whole sequence must fit before admission (full_sequence_must_fit), so it waits until 250 blocks are free. Before this rule an engine could admit many long prompts on their first chunks and then preempt them all.
What v0.31.0 added to the scheduler (release detail)

From the {{release notes|https://github.com/vllm-project/vllm/releases/tag/v0.31.0}}: requests that already hold KV blocks wait in their own queue and are tried first ({{L887|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L887}}); --max-num-active-seqs caps running requests separately from max_num_seqs; and long_prefill_token_threshold, off by default, no longer chunks a request that is alone ({{L611 to L626|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L611}}).

What it costs, when it matters, how to check
Cost: a preemption throws away all of a request's computed tokens; head-of-line blocking can hold short requests behind a long one that does not fit. When it matters: when the KV cache is near full, with long prompts, and under bursts. How to check: vllm:num_preemptions rising, vllm:num_requests_waiting growing while vllm:kv_cache_usage_perc sits near 1, and vllm:request_queue_time_seconds (section 6).
