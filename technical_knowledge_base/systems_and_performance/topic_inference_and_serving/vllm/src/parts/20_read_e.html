4. The model runner, and Model Runner V2

The problem. The scheduler's decision is a small dictionary ({request: tokens this step}, plus new block ids). The GPU needs dense tensors: one flat list of input token ids for all requests, their positions, where each request's tokens start, every request's block table, and per-request sampling settings. Building those in Python from scratch every step would cost more than the forward pass of a small model, so the model runner, one per GPU, keeps a persistent batch: tensors that stay allocated across steps and change only where a request joined or left.

Each step the runner (1) applies the scheduler's diff (new requests, finished ones, new blocks), (2) gathers the step's inputs and attention metadata, (3) runs the model, replaying a captured CUDA graph when the batch shape allows, (4) computes logits for the last position of each request, and (5) samples. Then the sampled ids go back to update_from_output.

Why a second model runner

The V1 runner's persistent batch used its state tensors directly as model inputs, so a request finishing in the middle forced rows to be reordered, and it kept a duplicate copy of each request's state; asynchronous scheduling was retrofitted onto it. Model Runner V2 (MRV2) was rewritten "from first principles" ({{design doc|https://github.com/vllm-project/vllm/blob/v0.31.0/docs/design/model_runner_v2.md}}):

Model Runner V1Model Runner V2
Persistent stateState tensors are the inputs; rows reordered when requests join or leaveEach request owns a fixed row (up to max_num_reqs, 1,024 on most platforms) until it finishes or is preempted; inputs are gathered from those rows on the GPU each step
Async schedulingRetrofitted, with an async barrier around CPU buffersDesigned in: no CPU synchronization in the step; CPU writes go to unpinned buffers copied through a temporary pinned one
Block tablesCopied from CPUStagedWriteTensor: diffs staged on CPU, one kernel applies them
Input preparation and samplingPython and PyTorchTriton kernels for input ids, positions and sequence lengths; a Triton Gumbel-max sampler; top-k logprobs without a full-vocabulary softmax
CUDA graphsImplicit, mixed into dummy_runAn explicit CUDAGraphManager; several draft-model steps captured in one graph

Every row from the design document at v0.31.0, the authors' description; not run here.

Which runner you get. MRV2 has been the default for every model since v0.29.0 (2026-09-09, {{release notes|https://github.com/vllm-project/vllm/releases/tag/v0.29.0}}), with V1 deprecated and its removal targeted for v0.32. At v0.31.0 the choice is a property, use_v2_model_runner ({{vllm.py L701 to L761|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/vllm.py#L701}}): VLLM_USE_V2_MODEL_RUNNER forces either way; otherwise V2, unless Triton is missing or the configuration uses something V2 does not support yet, listed in {{L3051 to L3103|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/vllm.py#L3051}}: stock torch.compile mode, sequence parallelism with TP > 1, pipeline parallelism under the external launcher, the speculative methods ngram, ngram_gpu, suffix, medusa, mlp_speculator and custom_class, parallel drafting for EAGLE, dual-batch overlap's unsupported cases, elastic expert parallelism, and Mamba cache mode "all". Then vLLM logs "Model Runner V2 does not yet support ..." and falls back. On ROCm, a few architectures default to V1 for speed. The CPU backend used on this page runs CPUModelRunner, a subclass of the V1 GPU runner ({{cpu_model_runner.py L23|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/worker/cpu_model_runner.py#L23}}): nothing here measures MRV2.

Predict: you upgrade a deployment that uses n-gram speculative decoding from v0.28 to v0.31. Which model runner does it run?
V1. "ngram" is on the unsupported list, so the property returns False and logs "Model Runner V2 does not yet support speculative method 'ngram'; using the V1 model runner instead." Benchmarks of V2 do not describe this deployment, and when V1 is removed (targeted for v0.32) the configuration must change or the feature must land in V2 first. Grep your logs for that line before upgrading.

CUDA graphs and torch.compile, by link

At batch 1 a decode step launches hundreds of small kernels, and the launch overhead can rival the work (the parent page's "third regime"). vLLM captures CUDA graphs for a fixed set of batch sizes and replays them. The default, FULL_AND_PIECEWISE, captures a full graph for pure decode batches and piecewise graphs (attention left outside) for prefill and mixed batches ({{compilation.py L606|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/compilation.py#L606}}); the optimization levels -O0 to -O3 trade start-up time for this (-O2 is the default: torch.compile plus FULL_AND_PIECEWISE; -O0 no compilation and no graphs, {{optimization_levels.md|https://github.com/vllm-project/vllm/blob/v0.31.0/docs/design/optimization_levels.md}}). Capture costs start-up time and memory: v0.30.0 cut capture from 12 s to 2 s and engine start from 28.9 s to 8.2 s on an H200 by freezing the garbage collector during capture ({{release notes|https://github.com/vllm-project/vllm/releases/tag/v0.30.0}}, the project's measurement).
