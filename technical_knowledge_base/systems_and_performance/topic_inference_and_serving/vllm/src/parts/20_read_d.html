3. The KV cache manager: blocks, a free queue, and hashes

The problem. Every token of every running request keeps a key and a value vector in every layer (114,688 bytes per token for Qwen3-0.6B in 16-bit, 229,376 in float32: 2 × 28 layers × 8 KV heads × 128 dims × bytes; the formula and its check against llama.cpp are on the parent page). That memory must be handed out as requests grow, taken back when they finish, and, if another request starts with the same tokens, found again instead of recomputed. Three small classes do it, and the {{PagedAttention paper page|n:3c65c17b0d0d81bf8b90ca93fee19f5f}} explains why the memory is paged at all.

KVCacheBlock{{kv_cache_utils.py L176|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/kv_cache_utils.py#L176}}: a block id, a reference count (how many running requests use it), the block's hash once it is full and cached, and two pointers for the free list. Metadata only: the tensors live on the GPU, indexed by block id.
FreeKVCacheBlockQueue{{L246|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/kv_cache_utils.py#L246}}: a doubly linked list threaded through the blocks themselves, with fake head and tail, so a block can be removed from the middle in O(1) when a request hits it in the cache. The head is the next block to hand out; the tail is the last to be evicted.
BlockPool{{block_pool.py L136|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/block_pool.py#L136}}: all blocks, the free queue, and a map from block hash to block. Block 0 is a reserved null block ({{L187|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/block_pool.py#L187}}), so a pool of N blocks holds N − 1 usable ones.
KVCacheManager{{kv_cache_manager.py L131|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/kv_cache_manager.py#L131}}: the scheduler's interface: get_computed_blocks (prefix lookup), allocate_slots, free; one block table per request.

Four operations, and the order that makes a cache out of a free list

OperationWhat it doesSource
allocatePop blocks from the head of the free queue. If a popped block still carries a hash, it is a cached block being evicted: its hash is removed from the map first. This is the only place eviction happens.{{block_pool.py L669|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/block_pool.py#L669}}
cacheWhen a block fills up, during prefill or decode, give it its hash and enter it in the map. Only full blocks are ever cached.{{L226|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/block_pool.py#L226}}
freeA finished or preempted request returns its blocks tail first ({{kv_cache_manager.py L616|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/kv_cache_manager.py#L616}}). Each block's count drops; at zero, a block without a hash goes to the front (reused first), a block with a hash to the back (kept as long as possible).{{block_pool.py L777|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/block_pool.py#L777}}
touchA cache hit: increment the count and, if the block was free (count 0), unlink it from the free queue so nobody can evict it while it is in use.{{L755|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/block_pool.py#L755}}

Put together: the free queue is a list of blocks nobody is using, ordered so that partial and unhashed blocks go first, then cached blocks from least to most recently freed, and within one request from its last block to its first. Evicting from the head is therefore least recently used eviction, and a request's tail goes before its prefix, because a prefix is more likely to be shared. No timestamps, no heap: the order of the list is the policy.

Predict, from vLLM's own unit test: a pool of 11 blocks (block 0 is the null block) is fresh. Request 0 takes blocks 1 to 6 (87 tokens: five full blocks, one partial); request 1 takes 7, 8, 9. Request 0 finishes. What is the free queue, head first?
6, 10, 5, 4, 3, 2, 1, asserted in {{test_prefix_caching.py, test_evict|https://github.com/vllm-project/vllm/blob/v0.31.0/tests/v1/core/test_prefix_caching.py#L2739}}. Block 6 is partial, so it has no hash and is put in front of the never-used block 10 (reused first, while its memory is warm); blocks 5 to 1 are full and cached, appended tail first, so block 1, the start of the prompt, is the last to be evicted. When request 1 also finishes the queue becomes 6, 10, 5, 4, 3, 2, 1, 9, 8, 7.

Prefix caching is a hash chain

A block's hash is sha256(pickle((parent_hash, tuple(block_tokens), extra_keys))) ({{hash_block_tokens, L684|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/kv_cache_utils.py#L684}}; {{hashing.py L26|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/utils/hashing.py#L26}}), where the first block's parent is a fixed seed hash ("vllm-none-hash", {{L122|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/kv_cache_utils.py#L122}}). Because each hash includes its parent's, equal hashes at block k mean equal tokens in blocks 0 to k: one dictionary lookup per block finds the longest cached prefix, with no tree to walk. SGLang keeps the same information as a radix tree matched token by token; the {{SGLang page|n:3c65c17b0d0d81e691e4ce9f9b5d1fad}}'s Radix lab runs both on the same traces, and the {{Batching, KV cache and scheduling|n:3c65c17b0d0d819db53bd2c48909e5b2}} page's Eviction lab compares LRU with other eviction policies. The extra keys carry what tokens alone do not say: LoRA adapter, image or audio content, prompt embeddings, and an optional per-request cache_salt on the first block, which isolates tenants because every later hash inherits it ({{L614|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/kv_cache_utils.py#L614}}). The seed has been deterministic by default since v0.29.0, so hashes agree across processes and machines (needed by distributed KV caches), and v0.31.0 tagged the extra keys by source so a LoRA name and a salt can no longer collide ({{release notes|https://github.com/vllm-project/vllm/releases/tag/v0.31.0}}).

Real block hashes from the recorded engine: where two requests' chains meet and part

measured here: the first 4 bytes of each block hash as vLLM v0.31.0 computed it while serving Qwen3-0.6B ({{Scheduler stepper|#t-step}}, prefix caching on). Each cell is one block with its text (32 tokens per block here: the CPU attention backend needs a multiple of 32, while GPUs default to 16); blue cells hold a hash both requests have, which is what get_computed_blocks reuses. The last partial block never has a hash.

Two details that change numbers. A full-prompt hit still recomputes the last block: the lookup is capped at num_tokens − 1 tokens because the model must produce logits for the last prompt token ({{kv_cache_manager.py L289 to L295|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/kv_cache_manager.py#L289}}), and the cap rounds down to a block boundary. And vllm:kv_cache_usage_perc is 1 − free blocks / usable blocks ({{block_pool.py L880|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/block_pool.py#L880}}): cached blocks that nobody is using count as free, so a server can show low usage while holding a large warm cache, and 100% means every block belongs to a running request.

What it costs, when it matters, how to check
Cost: hashing every full block with SHA-256 over pickled tuples, on the engine core's CPU (--prefix-caching-hash-algo xxhash is faster but not collision resistant, and then uses a random seed per process unless PYTHONHASHSEED is set, {{L160|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/kv_cache_utils.py#L160}}). When it matters: shared system prompts, multi-turn chat, agents and few-shot templates; for unique prompts it is pure overhead, and it is on by default. How to check: vllm:prefix_cache_hits / vllm:prefix_cache_queries is the hit rate in tokens; the {{Knob lab|#t-knob}} reads both from a live server, and the parent page's {{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} tab measured the time to first token with caching on and off.
