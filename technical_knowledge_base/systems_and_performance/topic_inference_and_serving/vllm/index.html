vLLM: inside the default engine

How vLLM v0.31.0 turns an HTTP request into tokens, read from its source with file and line: the processes and queues, the scheduler loop, the KV cache manager and its prefix cache, Model Runner V2, the knobs that matter and the metrics that show them, recent releases, and a first patch with its tests. Its real scheduler is recorded step by step serving Qwen3-0.6B on CPU. Data as of October 2026.

vLLM is the open-source serving engine most deployments start from: give it a model and it serves an OpenAI-compatible HTTP API, batching many users onto the same GPUs. The parent page, Topic: inference-and-serving, explains what every engine must do (prefill and decode, the KV cache, continuous batching, chunked prefill, prefix caching). This page opens vLLM itself, at the release tagged v0.31.0 (2026-10-05, commit db9527a4), so that you can read its code, predict what it will do with your traffic, tune it and change it.

It began as the PagedAttention paper's engine in the Sky Computing Lab at UC Berkeley (README), became a PyTorch Foundation hosted project on 2025-05-07 (PyTorch Foundation), and is also the generation engine inside RL post-training stacks: TRL's GRPO and online DPO trainers generate with vLLM 0.21.0 to 0.31.0 (TRL docs), and verl lists vLLM, SGLang and Transformers for rollouts (verl README).

The whole engine in five sentences
  1. Two processes, two queues. An API server process tokenizes, detokenizes and speaks HTTP; an engine core process runs a busy loop; they exchange messages over ZeroMQ sockets (section 1).
  2. One loop, three calls. Every iteration of the engine core calls schedule(), then the model, then update_from_output() (v1/engine/core.py L630).
  3. No phases, only a token budget. The scheduler gives each request some number of tokens to compute this step so that its computed count catches up with its length; prefill, chunked prefill, decode and speculative tokens are all the same thing to it (section 2).
  4. Memory is a pool of 16-token blocks. A block pool hands out blocks from the head of a free queue, takes them back in an order that makes the tail least recently used, and names every full block by a hash of its tokens and its parent's hash, which is the whole prefix cache (section 3).
  5. The GPU side is a model runner per GPU. Since v0.29.0 the default is Model Runner V2, rewritten for asynchronous scheduling (section 4).

The running example is the parent page's chat assistant, shrunk to what this laptop can run: Qwen3-0.6B answering customers of a bicycle shop, every request starting with the same system prompt. Two kinds of evidence appear, and every number says which:

1. One request, through vLLM's code

The problem. A GPU must never wait for Python. Tokenizing a prompt, turning token ids back into text, parsing JSON and writing HTTP responses are CPU work; if the loop that feeds the GPU also did them, the GPU would sit idle between steps. vLLM's answer since its V1 rewrite (V1 announcement, 2025-01-27) is to split the work across processes:

API server processHTTP (FastAPI), chat template, tokenizer, detokenizer, stop strings, streaming. One by default; --api-server-count adds more.
Engine core processThe busy loop: scheduler, KV cache manager, and the executor that drives the GPU workers. One per data-parallel rank.
GPU workerLoads weights, prepares inputs, runs the forward pass and the sampler. With one GPU it lives inside the engine core process (executor "uni", parallel.py L1033); with tensor parallelism, one process per GPU.
Between themZeroMQ sockets carrying msgpack-encoded requests one way and outputs the other; inside the engine core, two I/O threads and two Python queues.

Follow one streamed completion through the code. Every box is a function you can open at the tag; the step list is the order the code runs.

source: vLLM v0.31.0, every line number linked in the caption. The token chip shows what travels at each step: text, token ids, a scheduler decision, a sampled token id, text again.

Three consequences follow, and each is a classic production surprise.

  • Tokenizing and detokenizing happen in the API server, not on the GPU's critical path, so at high request rates the API server's single Python process can saturate before the GPU does; the architecture overview sizes CPU cores for this, and --api-server-count scales it out.
  • The scheduler sees token ids, never text. Stop strings are checked in the API server after detokenizing (output_processor.py L720), which then aborts the request in the engine; stop token ids and max_tokens are checked in the engine itself.
  • Each step returns outputs for every running request at once, and the API server fans them out to one queue per request (RequestOutputCollector). One slow client does not slow the loop.
Predict: vllm serve <model> -tp 4 on one server with four GPUs. How many vLLM processes run?
Six. One API server, one engine core, and one worker process per GPU, because with more than one GPU the executor becomes "mp" (multiprocessing). The architecture overview gives the general count: A API servers + DP engine cores + N workers (+1 coordinator when DP > 1); -tp 2 -dp 4 on eight GPUs makes 17. With one GPU it is two processes, the worker living inside the engine core. The CPU backend is the exception: it always uses the multiprocessing executor because OpenMP threads must be set up in their own process (cpu.py L317 to L324), so the CPU container here showed three vLLM processes measured here:

The same three steps without and with asynchronous scheduling

illustrative durations (CPU work 3 ms, GPU work 10 ms per step) to show the mechanism; the mechanism itself is the source's: with async scheduling the engine core keeps a batch queue of 2 (vllm.py L592) and step_with_batch_queue schedules step N+1 before step N's result is back (core.py L670). The CPU platform turns it off (cpu.py L314), so the stepper's trace is synchronous.

What async scheduling costs. The scheduler decides step N+1 before it knows step N's token, so a request that will finish at step N is scheduled once more; the running loop skips a request whose in-flight tokens already reach max_tokens (scheduler.py L635), and outputs that arrive for a request preempted in between are marked stale (scheduler.py L1563). When it matters: small models and small batches, where the GPU step is a few milliseconds and the CPU work is the same order. How to check: a profile with gaps between GPU kernels at batch 1 means the CPU is the bottleneck.

2. The scheduler loop

The problem. Every step, the engine must choose which requests run and how many of their tokens, without running out of KV cache memory and without letting one long prompt freeze everyone else's stream. vLLM's scheduler is one function, Scheduler.schedule() (scheduler.py L562), and its first comment states the design:

# There's no "decoding phase" nor "prefill phase" in the scheduler. # Each request just has the num_computed_tokens and num_tokens_with_spec. # At each step, the scheduler tries to assign tokens to the requests # so that each request's num_computed_tokens can catch up its # num_tokens_with_spec. This is general enough to cover chunked prefills, # prefix caching, speculative decoding, and the "jump decoding" optimization. (L564 to L573, abridged)

So a request is two numbers: how many of its tokens exist (prompt plus output so far, plus draft tokens when speculating) and how many already have their keys and values in the cache. A new request has 2,000 tokens and 0 computed: it needs 2,000. A decoding request has 2,301 tokens and 2,300 computed: it needs 1. A prefix-cache hit simply starts a request with some tokens already computed. The scheduler hands out a per-step token budget (max_num_batched_tokens, section 5) to close those gaps.

Loop 1, running requests

In order of admission (L630): tokens wanted, capped by what is left of the budget (L681), then allocate_slots for the blocks those tokens need. If the pool is empty, preempt and retry.

Preemption

Under FCFS the victim is self.running[-1], the most recently admitted request (L771); under the priority policy, the lowest priority, latest arrival (stepped through against this same code on the Batching, KV cache and scheduling page's Scheduling lab). Its blocks are freed, its computed count reset to 0, and it goes to the front of the waiting queue (L1538 to L1580). There is no swap to CPU memory in this engine: preemption is recompute.

Loop 2, waiting requests

Only if nothing was preempted this step (L873), and while fewer than max_num_seqs run (L893): look up the prefix cache, cut the prompt to what the budget allows, allocate. The first request that does not fit stops the loop (L1223): first come, first served, including the head-of-line blocking that implies.

After the model runs

update_from_output (L1967) appends each sampled token, checks EOS, stop ids and max_tokens, and frees the blocks of finished requests.

Two admission rules that surprise people. First, a waiting request is admitted only when its whole prompt fits in free blocks, not just the first chunk: scheduler_reserve_full_isl defaults to True (config/scheduler.py L191) and is passed as full_sequence_must_fit (L1218; checked in kv_cache_manager.py L519). The parent page's Serving simulator found this when its scheduler was checked against this very code: it had to change to match, and then agreed with vLLM on all 10 traces, 2,535 steps and 39 preemptions. Second, chunking is on by default (config/scheduler.py L135); with it off, a prompt longer than the remaining budget waits for a step with room (L1115).

New in v0.31.0 (release notes): requests that already hold KV blocks wait in their own queue and are tried first (L887); --max-num-active-seqs caps running requests separately from max_num_seqs; and long_prefill_token_threshold, off by default, no longer chunks a request that is alone (L611 to L626).

Predict: the budget is 64 tokens, two requests are decoding, and a new 150-token prompt is waiting with plenty of free blocks. How many of its tokens are computed this step?
62. Running requests are served first: the two decodes take 1 token each, leaving 62 of the 64; the new request is admitted (its whole prompt fits in free blocks) and gets a 62-token chunk, then the rest in later steps. The Scheduler stepper shows exactly this on the real engine with a 64-token budget.
Predict: the pool is full and the running list, in admission order, is [A, B, C]. A needs one more block to decode. What does the scheduler do?
It preempts C (self.running.pop(), L803), frees its blocks, resets its computed tokens to 0 and puts it at the front of the waiting queue; A then gets its block. C will be prefilled again later: with prefix caching on, its freed full blocks keep their hashes, so much of that recompute is a cache hit if nobody has evicted them in between. No new request is admitted in a step that preempted.
Predict: a 4,000-token prompt arrives; 150 blocks of 16 tokens are free (2,400 tokens); the budget is 2,048 and chunked prefill is on. Is its first chunk scheduled?
No. The whole sequence must fit before admission (full_sequence_must_fit), so it waits until 250 blocks are free. Before this rule an engine could admit many long prompts on their first chunks and then preempt them all.
What it costs, when it matters, how to check
Cost: a preemption throws away all of a request's computed tokens; head-of-line blocking can hold short requests behind a long one that does not fit. When it matters: when the KV cache is near full, with long prompts, and under bursts. How to check: vllm:num_preemptions rising, vllm:num_requests_waiting growing while vllm:kv_cache_usage_perc sits near 1, and vllm:request_queue_time_seconds (section 6). Step through the real thing in the Scheduler stepper.

3. The KV cache manager: blocks, a free queue, and hashes

The problem. Every token of every running request keeps a key and a value vector in every layer (114,688 bytes per token for Qwen3-0.6B in 16-bit, 229,376 in float32: 2 × 28 layers × 8 KV heads × 128 dims × bytes; the formula and its check against llama.cpp are on the parent page). That memory must be handed out as requests grow, taken back when they finish, and, if another request starts with the same tokens, found again instead of recomputed. Three small classes do it, and the PagedAttention paper page explains why the memory is paged at all.

KVCacheBlockkv_cache_utils.py L176: a block id, a reference count (how many running requests use it), the block's hash once it is full and cached, and two pointers for the free list. Metadata only: the tensors live on the GPU, indexed by block id.
FreeKVCacheBlockQueueL246: a doubly linked list threaded through the blocks themselves, with fake head and tail, so a block can be removed from the middle in O(1) when a request hits it in the cache. The head is the next block to hand out; the tail is the last to be evicted.
BlockPoolblock_pool.py L136: all blocks, the free queue, and a map from block hash to block. Block 0 is a reserved null block (L187), so a pool of N blocks holds N − 1 usable ones.
KVCacheManagerkv_cache_manager.py L131: the scheduler's interface: get_computed_blocks (prefix lookup), allocate_slots, free; one block table per request.

Four operations, and the order that makes a cache out of a free list

OperationWhat it doesSource
allocatePop blocks from the head of the free queue. If a popped block still carries a hash, it is a cached block being evicted: its hash is removed from the map first. This is the only place eviction happens.block_pool.py L669
cacheWhen a block fills up, during prefill or decode, give it its hash and enter it in the map. Only full blocks are ever cached.L226
freeA finished or preempted request returns its blocks tail first (kv_cache_manager.py L616). Each block's count drops; at zero, a block without a hash goes to the front (reused first), a block with a hash to the back (kept as long as possible).block_pool.py L777
touchA cache hit: increment the count and, if the block was free (count 0), unlink it from the free queue so nobody can evict it while it is in use.L755

Put together: the free queue is a list of blocks nobody is using, ordered so that partial and unhashed blocks go first, then cached blocks from least to most recently freed, and within one request from its last block to its first. Evicting from the head is therefore least recently used eviction, and a request's tail goes before its prefix, because a prefix is more likely to be shared. No timestamps, no heap: the order of the list is the policy.

Predict, from vLLM's own unit test: a pool of 11 blocks (block 0 is the null block) is fresh. Request 0 takes blocks 1 to 6 (87 tokens: five full blocks, one partial); request 1 takes 7, 8, 9. Request 0 finishes. What is the free queue, head first?
6, 10, 5, 4, 3, 2, 1, asserted in test_prefix_caching.py, test_evict. Block 6 is partial, so it has no hash and is put in front of the never-used block 10 (reused first, while its memory is warm); blocks 5 to 1 are full and cached, appended tail first, so block 1, the start of the prompt, is the last to be evicted. When request 1 also finishes the queue becomes 6, 10, 5, 4, 3, 2, 1, 9, 8, 7.

Prefix caching is a hash chain

A block's hash is sha256(pickle((parent_hash, tuple(block_tokens), extra_keys))) (hash_block_tokens, L684; hashing.py L26), where the first block's parent is a fixed seed hash ("vllm-none-hash", L122). Because each hash includes its parent's, equal hashes at block k mean equal tokens in blocks 0 to k: one dictionary lookup per block finds the longest cached prefix, with no tree to walk. SGLang keeps the same information as a radix tree matched token by token; the SGLang page's Radix lab runs both on the same traces, and the Batching, KV cache and scheduling page's Eviction lab compares LRU with other eviction policies. The extra keys carry what tokens alone do not say: LoRA adapter, image or audio content, prompt embeddings, and an optional per-request cache_salt on the first block, which isolates tenants because every later hash inherits it (L614). The seed has been deterministic by default since v0.29.0, so hashes agree across processes and machines (needed by distributed KV caches), and v0.31.0 tagged the extra keys by source so a LoRA name and a salt can no longer collide (release notes).

Real block hashes from the recorded engine: where two requests' chains meet and part

measured here: the first 4 bytes of each block hash as vLLM v0.31.0 computed it while serving Qwen3-0.6B (Scheduler stepper, prefix caching on). Each cell is one block with its text (32 tokens per block here: the CPU attention backend needs a multiple of 32, while GPUs default to 16); blue cells hold a hash both requests have, which is what get_computed_blocks reuses. The last partial block never has a hash.

Two details that change numbers. A full-prompt hit still recomputes the last block: the lookup is capped at num_tokens − 1 tokens because the model must produce logits for the last prompt token (kv_cache_manager.py L289 to L295), and the cap rounds down to a block boundary. And vllm:kv_cache_usage_perc is 1 − free blocks / usable blocks (block_pool.py L880): cached blocks that nobody is using count as free, so a server can show low usage while holding a large warm cache, and 100% means every block belongs to a running request.

What it costs, when it matters, how to check
Cost: hashing every full block with SHA-256 over pickled tuples, on the engine core's CPU (--prefix-caching-hash-algo xxhash is faster but not collision resistant, and then uses a random seed per process unless PYTHONHASHSEED is set, L160). When it matters: shared system prompts, multi-turn chat, agents and few-shot templates; for unique prompts it is pure overhead, and it is on by default. How to check: vllm:prefix_cache_hits / vllm:prefix_cache_queries is the hit rate in tokens; the Knob lab reads both from a live server, and the parent page's Engine bench tab measured the time to first token with caching on and off.

4. The model runner, and Model Runner V2

The problem. The scheduler's decision is a small dictionary ({request: tokens this step}, plus new block ids). The GPU needs dense tensors: one flat list of input token ids for all requests, their positions, where each request's tokens start, every request's block table, and per-request sampling settings. Building those in Python from scratch every step would cost more than the forward pass of a small model, so the model runner, one per GPU, keeps a persistent batch: tensors that stay allocated across steps and change only where a request joined or left.

Each step the runner (1) applies the scheduler's diff (new requests, finished ones, new blocks), (2) gathers the step's inputs and attention metadata, (3) runs the model, replaying a captured CUDA graph when the batch shape allows, (4) computes logits for the last position of each request, and (5) samples. Then the sampled ids go back to update_from_output.

Why a second model runner

The V1 runner's persistent batch used its state tensors directly as model inputs, so a request finishing in the middle forced rows to be reordered, and it kept a duplicate copy of each request's state; asynchronous scheduling was retrofitted onto it. Model Runner V2 (MRV2) was rewritten "from first principles" (design doc):

Model Runner V1Model Runner V2
Persistent stateState tensors are the inputs; rows reordered when requests join or leaveEach request owns a fixed row (up to max_num_reqs, 1,024 on most platforms) until it finishes or is preempted; inputs are gathered from those rows on the GPU each step
Async schedulingRetrofitted, with an async barrier around CPU buffersDesigned in: no CPU synchronization in the step; CPU writes go to unpinned buffers copied through a temporary pinned one
Block tablesCopied from CPUStagedWriteTensor: diffs staged on CPU, one kernel applies them

Every row from the design document at v0.31.0, the authors' description; not run here.

Which runner you get. MRV2 has been the default for every model since v0.29.0 (2026-09-09, release notes), with V1 deprecated and its removal targeted for v0.32. At v0.31.0 the choice is a property, use_v2_model_runner (vllm.py L701 to L761): VLLM_USE_V2_MODEL_RUNNER forces either way; otherwise V2, unless Triton is missing or the configuration uses something V2 does not support yet, listed in L3051 to L3103: stock torch.compile mode, sequence parallelism with TP > 1, pipeline parallelism under the external launcher, the speculative methods ngram, ngram_gpu, suffix, medusa, mlp_speculator and custom_class, parallel drafting for EAGLE, dual-batch overlap's unsupported cases, elastic expert parallelism, and Mamba cache mode "all". Then vLLM logs "Model Runner V2 does not yet support ..." and falls back. On ROCm, a few architectures default to V1 for speed. The CPU backend used on this page runs CPUModelRunner, a subclass of the V1 GPU runner (cpu_model_runner.py L23): nothing here measures MRV2.

Predict: you upgrade a deployment that uses n-gram speculative decoding from v0.28 to v0.31. Which model runner does it run?
V1. "ngram" is on the unsupported list, so the property returns False and logs "Model Runner V2 does not yet support speculative method 'ngram'; using the V1 model runner instead." Benchmarks of V2 do not describe this deployment, and when V1 is removed (targeted for v0.32) the configuration must change or the feature must land in V2 first. Grep your logs for that line before upgrading.

CUDA graphs and torch.compile, by link

At batch 1 a decode step launches hundreds of small kernels, and the launch overhead can rival the work (the parent page's "third regime"). vLLM captures CUDA graphs for a fixed set of batch sizes and replays them. The default, FULL_AND_PIECEWISE, captures a full graph for pure decode batches and piecewise graphs (attention left outside) for prefill and mixed batches (compilation.py L606); the optimization levels -O0 to -O3 trade start-up time for this (-O2 is the default: torch.compile plus FULL_AND_PIECEWISE; -O0 no compilation and no graphs, optimization_levels.md). Capture costs start-up time and memory: v0.30.0 cut capture from 12 s to 2 s and engine start from 28.9 s to 8.2 s on an H200 by freezing the garbage collector during capture (release notes, the project's measurement). How graphs work and what breaks them: Streams, CUDA graphs and multi-GPU. What torch.compile and Inductor do to the model: Compiler stack. The attention kernels themselves (FlashAttention, split-KV decode): Writing kernels.

6. Reading the metrics

vLLM's API server exports Prometheus metrics at /metrics, defined in one class, PrometheusStatLogger (loggers.py L509 onward). Their values come from two places, and knowing which tells you how fresh they are: gauges and counters about the scheduler (running, waiting, KV usage, prefix-cache queries and hits) arrive with every step's outputs as a SchedulerStats object built in the engine core (scheduler.py L2859); per-request histograms (TTFT, ITL, queue time, prefill and decode time) are computed in the API server from timestamps the engine attaches to each request's events. The Knob lab lists every metric the live server exported, with values before and after a run.

Gaps worth knowing. No exported metric counts how many cached blocks are evicted to make room (only residency histograms, which need --kv-cache-metrics sampling) or how much work preemption threw away. Section 8 adds the first one, as a worked example of a contribution.

The old page said v0.28.0 doubled max_num_batched_tokens from 8,192 to 16,384 for "any deployment that never set it". An upgrade checklist that follows from the code

  1. Diff the resolved configuration, not the flags. vLLM logs its final VllmConfig at start-up; save it for the old and new versions and compare max_num_batched_tokens, max_num_seqs, the cache size in tokens and the CUDA graph sizes.
  2. Check which model runner you got. Grep for "Model Runner V2 does not yet support" (section 4).
  3. Check the removed flags and environment variables in your launch scripts; an unknown CLI flag stops the server, while a removed VLLM_ environment variable only logs "Unknown vLLM environment variable detected" (platforms/interface.py L1344) and its setting is lost (--fail-on-environ-validation, off by default, turns that into an error: arg_utils.py L836).
  4. Replay real traffic with the same load generator at the same arrival rate and compare TTFT and ITL percentiles and preemptions (section 6), not one throughput number.
  5. Re-check prefix-cache behaviour when hashes change: v0.29.0 changed the seed default and v0.31.0 changed the extra keys, so caches shared across machines (LMCache, Mooncake, llm-d) must run the same version on every node.

The old page also listed model-specific kernel speedups from v0.28.0 and v0.29.0 (Kimi-K3, DeepSeek V4, Hy4-preview); they are verified in the release notes but belong to the models' own pages. Its "about 3x throughput" for decode context parallelism on long-context agentic workloads was not found in the release notes and is left out (unconfirmed).

8. Contributing: a first patch, with its tests

The fastest way to own an engine is to change it. Section 6 found a gap: the server says how often the prefix cache hits, but not how often it has to throw cached blocks away to make room, which is the number that says "this cache is too small for this traffic". Here is the patch that adds it, the test that proves it, and the metric live in a server.

1. Count it where it happens

In BlockPool.get_new_blocks, the only place a cached block is evicted, increment a counter when _maybe_evict_cached_block returns True; add take_num_evicted_cached_blocks() to read and reset it.

2. Carry it with the step's stats

A new field evicted_blocks on PrefixCacheStats, filled in KVCacheManager.make_prefix_cache_stats(), so it travels to the API server inside each step's SchedulerStats like the hit counts.

3. Export it

A Prometheus counter vllm:prefix_cache_evicted_blocks registered next to prefix_cache_hits in PrometheusStatLogger and incremented in record().

4. Test it

A unit test built on the same fixture as test_evict: free a request with five cached blocks, allocate eight new ones, expect exactly three evictions (the five never-hashed free blocks go first), then zero after the reset.

The tests, run in vLLM's own CPU image measured here, 2026-10-08: the image's installed package with the four patched files mounted over it, and the clone's tests/ directory (which contains the new test) in both runs: test_prefix_caching.py, test_scheduler.py and metrics/test_stats.py.

How to get a change merged

From the contributing guide at v0.31.0, checked against the old page's notes:

  • Set-up for Python-only work: VLLM_USE_PRECOMPILED=1 uv pip install -e . reuses the released compiled kernels, so editing the scheduler needs no CUDA build; kernel work needs PyTorch first and --no-build-isolation. Tests are plain pytest; lint with pre-commit.
  • Every commit needs a DCO Signed-off-by: line; PR titles start with tags such as [Bugfix][Scheduler].
  • AI-assisted contributions must be disclosed in the PR and marked with commit trailers (for example Co-authored-by: Claude); "pure agent" PRs and one-line busywork PRs are not accepted; the human submitter must have reviewed every line and run the tests.
  • Large changes (over 500 lines, excluding kernels, data, config and tests) need an RFC issue first, or the PR gets rfc-required.
  • Review: a reviewer is assigned and gives status updates every 2 to 3 days; ping after 7 days without review.
  • Where to start: issues labelled "good first issue"; the scheduler and KV cache code in vllm/v1/core/ is readable and well tested, as this section shows; new model support follows the existing files under vllm/model_executor/models/.

Common mistakes

MistakeWhat is actually true, and where
"vLLM has a prefill phase and a decode phase."The scheduler has neither; it closes the gap between computed and existing tokens for each request under one budget (scheduler.py L564). Mixed steps are the normal case.
"Preempted requests are swapped to CPU memory."In this engine preemption is recompute: blocks freed, computed count reset to 0, request to the front of the waiting queue (L1538 to L1580). Its cached full blocks may still be hit when it returns. CPU offload exists, but as a KV connector tier, not as the preemption path.
"KV cache usage 30% means 70% of the cache is empty."Cached blocks that no running request holds count as free (block_pool.py L880). Usage is the share referenced by running requests; the warm cache is invisible in this metric.
"Chunked prefill means a long prompt is admitted chunk by chunk as memory frees up."Admission needs the whole prompt to fit (scheduler_reserve_full_isl); chunking only spreads its compute over steps.
"A full prefix-cache hit costs no prefill."The last block is always recomputed to get the first token's logits (kv_cache_manager.py L289), and only full blocks are ever cached.
"max_num_batched_tokens is 16,384 since v0.28."Only for the API server on GPUs with at least 160 GiB; H100 and H200 servers default to 8,192, other GPUs 2,048, the CPU backend 2,048 per worker (arg_utils.py L2858 to L2917).
"V2 benchmarks describe my deployment."Unsupported features silently fall back to Model Runner V1 with one warning line (vllm.py L752).
"gpu_memory_utilization is how much of the cache to use."It is the fraction of the whole GPU memory vLLM may take for weights, activations, CUDA graphs and the cache together; the cache gets what is left after profiling (default 0.92, cache.py L103). Two vLLM servers on one GPU need fractions that sum below 1.

Interview questions

Walk me through what happens inside vLLM between an HTTP request arriving and the first token streaming back.
API server: route, sampling params, tokenize (InputProcessor), register a detokenizer and an output queue, send an EngineCoreRequest over ZeroMQ. Engine core: an input thread queues it; the busy loop adds it to the waiting queue (hashing its full blocks); schedule() admits it if its whole prompt fits, allocating blocks after a prefix-cache lookup, and gives it budget; the executor runs the forward pass and samples; update_from_output appends the token; an output thread sends it back. API server: detokenize, check stop strings, put into the request's queue, write a server-sent event. TTFT is queue time plus the prefill steps plus these hops.
Why does vLLM split the API server and the engine core into separate processes?
Python's GIL: tokenizing, detokenizing and HTTP are CPU work that would stall the loop that keeps the GPU fed. Separate processes overlap them with GPU steps; the cost is serialization over ZeroMQ, and at high request rates you add API server processes.
How does vLLM decide which request to preempt, and what does preemption cost?
FCFS: the last request in the running list, the most recently admitted; priority policy: the lowest priority, latest arrival. It costs all of that request's computed tokens (recompute), unless its freed full blocks are still in the prefix cache when it is readmitted; no new requests are admitted in that step.
How is the prefix cache implemented, and why a hash chain rather than a radix tree?
Each full block is named by a hash of its parent's hash, its tokens and extra keys (LoRA, multimodal, salt); a dictionary maps hash to block. Equal hash at block k implies equal prefix up to k, so lookup is one dictionary probe per block, block-granular, with no tree to maintain. Eviction is the free queue's order: unused cached blocks wait at the tail, least recently freed first at the head. SGLang's radix tree matches at token granularity and supports cache-aware scheduling (SGLang page).
Your p99 inter-token latency spikes whenever long prompts arrive. Which knobs?
Lower max_num_batched_tokens (smaller prefill chunks per step, so decode steps stay short), or set long_prefill_token_threshold; at the cost of slower TTFT for the long prompts. If it is a separate population, disaggregate prefill and decode (distributed page). Measure with vllm:inter_token_latency_seconds and the Knob lab's chunk sweep.
Throughput is flat but the waiting queue grows and KV usage is near 100%. What is the limit and what do you change?
Memory, not compute: requests cannot be admitted because their prompts do not fit. Options: raise gpu_memory_utilization if there is headroom, an FP8 KV cache (half the bytes per token), lower max_model_len to stop huge requests, more replicas, or a model with a smaller cache (GQA, MLA). Raising max_num_seqs does nothing here.
What is Model Runner V2 and when do you not get it?
The rewritten per-GPU runner (default since v0.29.0): persistent per-request rows with GPU-side gathering, async-first, Triton input preparation and sampling, explicit CUDA graph management. You get V1 when a feature it does not support is configured (n-gram, suffix or Medusa speculation, sequence parallelism with TP, elastic EP and others), on some ROCm models, without Triton, and on the CPU backend.
How would you add a new metric to vLLM?
Count it where the event happens (engine core), carry it in the per-step stats object (SchedulerStats or PrefixCacheStats), register a Prometheus counter in PrometheusStatLogger and increment it in record(), and add a unit test. Section 8 does exactly this for prefix-cache evictions.
