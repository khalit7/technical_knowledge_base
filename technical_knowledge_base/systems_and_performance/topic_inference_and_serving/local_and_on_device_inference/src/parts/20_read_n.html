Depth: common mistakes and interview rehearsal

Common mistakes, each with the section that shows it (depth)
  • Judging a quant by its name. Q4_K_M is a recipe, and on small models the embeddings dominate: on Qwen3-1.7B "Q2_K" averages bits per weight, and the Qwen3-0.6B Q4_K_M file , while Q4_K itself is 4.5. Compare files by size and a measured KLD (section 4).
  • Ranking quants by perplexity alone. Perplexity on one text moves by luck and can even improve after quantisation; KLD against the full-precision model, and its 99th percentile, show the drift users feel (section 5).
  • Downloading a low-bit GGUF made without an importance matrix. At 3 bits and below it is the difference between usable and broken: Q2_K's KLD on Qwen3-1.7B was without one and with one, same size.
  • Requantising a quantised file. Q8_0 to Q4_K_M stacks two roundings. Quantise from the BF16 or F32 original (section 3).
  • "Converting to F16 GGUF is lossless." From a BF16 checkpoint it changed values of Qwen3-0.6B. Use --outtype bf16 (or f32) for a lossless master.
  • Trusting a GGUF's chat template because the file is self-contained. It is whatever the uploader wrote: the Unsloth file in the store has a rewritten template and one fewer stop id than the original repo.
  • Reading GGUF shapes like PyTorch shapes. GGUF lists dimensions fastest-first: [1024, 151936] is PyTorch's [151936, 1024].
  • "weights_only=True makes torch.load safe." It was bypassed before PyTorch 2.6 (CVE-2025-32434), and it is still an allowlist inside a pickle interpreter. Prefer safetensors; keep PyTorch current.
  • Expecting a 4-bit file to stream 4 times faster than F16. On a GPU with little arithmetic unpacking costs time: Q4_K_M streamed times faster than F16 on this laptop, not 3.2 times (section 1).
  • Forgetting the KV cache when sizing. A full 40,960-token context of Qwen3-4B needs 6.0 GB of F16 cache, more than twice its Q4_K_M weights (section 2).
  • Leaving Ollama at its default context. Under 24 GiB of VRAM it uses 4,096 tokens; a longer prompt is cut without an error. Set num_ctx or OLLAMA_CONTEXT_LENGTH (section 8).
  • Splitting a model across two GPUs and expecting it to be faster. The default layer split adds memory, not single-user speed. For one user use tensor split; for throughput, one replica per card (section 9).
  • Turning on --cache-reuse or --context-shift without knowing they are approximate. Both reuse keys and values computed with different preceding text (section 6).
  • Running mlx_lm.server for a team. Its own docs say not for production, and it ran out of Metal memory under load here (section 7).
  • Measuring load time with a warm cache and calling it cold start. The second load reads from RAM; cold loads are disk-bound (section 3).
  • Exporting an LLM to ONNX and expecting a chat server. A plain export has no KV cache, sampling or batching (section 3).
  • Shipping a TensorRT plan as "the model". It is tied to the GPU type and TensorRT version; ship safetensors and build plans in CI.
  • Believing a headline tokens-per-second figure. Ask for the batch size, context length, hardware, quantisation and who measured it; vendor "up to" numbers and model-card tables differed by about 10% for Bonsai (section 10).
Interview rehearsal (optional)

A 70B model on two 24 GB GPUs: how do you run it, and how fast? At about 4.8 bits it is about 43 GB: it fits across 48 GB with a little room for the cache. Layer split: one user gets about one card's bandwidth, a ceiling of about 1,000 / 43 = 23 tokens per second on 4090s, less in practice. Tensor split adds speed at the cost of PCIe traffic (no P2P on GeForce). Or drop to 3 bits with an imatrix and accept the quality cost.

An RTX 5090 on a 3.8 GB model: the speed limit? 1,792 / 3.83 = 468 tokens per second; measured 300.

A model's file is 20% bigger than parameters × 2 bytes. Where would you look? Duplicated tied tensors (Qwen3-0.6B's lm_head), F32 tensors, or extra heads; list the header and compare byte ranges.

Two Q4 formats both cost 4.5 bits per weight. What can still differ? Group size, whether there is an offset, scale precision, and where scales live in the file (GGUF interleaves them per block; MLX keeps separate tensors), which affects quality and kernel design.

Why does Apple silicon run large models that a gaming GPU cannot? Unified memory: up to 512 GB the GPU can address, against 32 GB on an RTX 5090; but bandwidth is lower (200 to 1,200 GB/s against 1,792) and prompt reading much slower. Big models fit; they stream more slowly and read prompts much more slowly.

Why don't vLLM and SGLang serve ONNX, and is a TensorRT engine portable? Their speed comes from a paged KV cache, custom attention kernels and per-step scheduling, which a static graph does not express. A TensorRT engine is portable by default only to the same GPU type and TensorRT version; hardware and version compatibility modes (since 8.6) widen that at some cost.

Is a 1.58-bit model just a 16-bit model rounded hard? No: rounding a normally trained model to 2 bits or below breaks it (Q1_0 perplexity here); ternary models are trained or retrained for it and need kernels that store and unpack them (TQ1_0/TQ2_0, bitnet.cpp).
