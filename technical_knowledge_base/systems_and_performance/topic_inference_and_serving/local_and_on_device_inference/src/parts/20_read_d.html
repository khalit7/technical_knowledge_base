3. The file: what a model format holds, and what reading it costs

A model format is the agreement on how a model's named arrays, and the facts needed to use them, are written to disk. vLLM gets a folder of safetensors shards plus a config.json; a laptop gets one GGUF file or an MLX folder. Keep three layers apart:

1. Container

How bytes are laid out: where each tensor starts, what metadata travels with it, and whether reading the file can run code. safetensors, GGUF, pickle, ONNX's protobuf, flatbuffers.

2. Number encoding

How each number is stored: BF16, FP8, or a quantisation scheme such as GGUF's Q4_K or MLX's 4-bit affine groups (section 4). The container says which; the scheme says how to decode it.

3. Compiled artifact

A build output tied to one runtime and one kind of hardware: a TensorRT engine, a Core ML compiled model. Not something to distribute; something to rebuild.

GGUF fuses layers 1 and 2; safetensors owns only layer 1; a TensorRT engine is layer 3. Every claim below is read from real Qwen3-0.6B files; the {{File explorer|#t-bytes}} tab walks three of them field by field.

What a file has to hold

Five kinds of thing travel with a model; a format either carries each one or leaves it to a sibling file:

TensorsEach a name (model.layers.0.self_attn.k_proj.weight), a dtype (BF16: two bytes), a shape ([1024, 1024]) and raw bytes.
ConfigLayers, heads, hidden size, RoPE base, norm epsilon. Qwen3-1.7B's is a 726-byte JSON file.
TokenizerThe vocabulary (151,936 tokens for Qwen3), merge rules, special-token ids.
Chat templateThe Jinja program that turns messages into the token sequence the model was trained on.
Generation defaultsRecommended sampling (Qwen3: temperature 0.6, top-k 20, top-p 0.95) and the ids that end a turn.

Bytes on disk: order and size (depth)

A tensor on disk is its numbers in a row, row-major (last index fastest) and little-endian, plus its shape: bytes = (product of the shape) × (bytes per element), so k_proj.weight, BF16, [1024, 1024] is 2,097,152 bytes, exactly the gap between its two offsets in the real file.

dtypes. A float is a sign bit, an exponent (range) and a mantissa (precision). BF16 keeps F32's 8 exponent bits and cuts the mantissa to 7; F16 has 10 mantissa bits but only 5 exponent bits, so very small and very large numbers do not fit. Try a value:

Predict: the converter stores Qwen3's RMSNorm weights (1-D vectors) as F32 even when you ask for BF16. Does that lose anything?
No. F32 has the same 8 exponent bits and a longer mantissa, so every BF16 value widens exactly; the comparison found all 113 F32 tensors identical to the BF16 originals. The converter keeps 1-D tensors and norms in F32 because "most of the codebase that takes in 1D tensors or norms only handles F32 tensors" (conversion/base.py L1047, b11146); they hold 65,536 of the 751.6 million values (under 0.01%).

Pickle: a checkpoint that is a program

Pickle (what torch.save writes; every pytorch_model.bin) is a program for a small stack machine, and loading runs it: its GLOBAL opcode imports any function and REDUCE calls it. What pickle is, in Python's own words, and the checkpoint disassembled (depth)

For years torch.save wrote Python's pickle format, and Hugging Face files named pytorch_model.bin are exactly that. A pickle is not data but a program for a small stack machine, and loading it runs the program. The machine reads one-byte opcodes; most push values, and two are the point: GLOBAL imports any module.name, and REDUCE pops a callable and an argument tuple and calls it. That is how a tensor is rebuilt (call torch._utils._rebuild_tensor_v2) and equally how a file can call os.system. Python's documentation: "The pickle module is not secure. Only unpickle data you trust. It is possible to construct malicious pickle data which will execute arbitrary code during unpickling" ({{pickle docs|https://docs.python.org/3/library/pickle.html}}).

Since PyTorch 1.6 a .pt or .bin file is a zip ({{torch.save docs|https://pytorch.org/docs/stable/generated/torch.save.html}}): a small data.pkl program plus one raw file per storage. What happened when they were loaded (depth)

Loading them run here: plain pickle.loads of the malicious bytes (in a child process) printed LOADING THIS FILE RAN print(): it could have been any function and returned normally; nothing looked wrong. torch.load with its default weights_only=True refused it before any call (the message is in the closed block below).

The rule
Treat a pickle checkpoint from anyone you do not trust as an executable. Prefer the safetensors files in the same repo; if only a .bin exists, convert it inside a throwaway sandbox (a container with no credentials and no network), never on your workstation. weights_only=True was itself bypassed before PyTorch 2.6 (below).
The refusal message, the mitigation that failed, the ones that hold, and real attacks (depth)
  • weights_only=True swaps the pickle machine for a restricted one that allows only an allowlist of globals (tensor rebuild functions, plain containers). PyTorch 2.6 made it the default on 2025-01-29, calling it a backward-compatibility-breaking change ({{PyTorch 2.6 blog|https://pytorch.org/blog/pytorch2-6/}}).
  • It was bypassed. {{CVE-2025-32434|https://github.com/advisories/GHSA-53q9-r3pm-6pq6}} (published 2025-04-17/18, CVSS v4 9.3, critical): remote code execution through torch.load even with weights_only=True, in every PyTorch before 2.6.0. For years the recommended safe path was not safe.
  • Libraries now refuse. transformers 4.52.0 (2025-05-20) added check_torch_load_is_safe(): on PyTorch older than 2.6 it raises instead of loading a .bin, adding "This version restriction does not apply when loading files with safetensors" ({{source|https://github.com/huggingface/transformers/blob/main/src/transformers/utils/import_utils.py}}).
  • Real attacks exist. JFrog found "around 100" malicious models on the Hugging Face Hub, one opening a reverse shell (2024-02-27, {{JFrog|https://jfrog.com/blog/data-scientists-targeted-by-malicious-hugging-face-ml-models-with-silent-backdoor/}}). ReversingLabs' "nullifAI" (2025-02-06) found two models whose pickles were packed with 7z and deliberately broken after the payload, so the Hub's Picklescan missed them ({{ReversingLabs|https://www.reversinglabs.com/blog/rl-identifies-malware-ml-model-hosted-on-hugging-face}}). The Hub lists each pickle's imports without executing it and says this "is not 100% foolproof" ({{Hub docs|https://huggingface.co/docs/hub/security-pickle}}).
  • Not only PyTorch. Keras models could carry code in Lambda layers ({{CVE-2024-3660|https://nvd.nist.gov/vuln/detail/CVE-2024-3660}}, fixed in Keras 2.13 with safe_mode), and {{CVE-2025-1550|https://nvd.nist.gov/vuln/detail/CVE-2025-1550}} ran code through load_model even with safe_mode=True (fixed in Keras 3.9.0).
