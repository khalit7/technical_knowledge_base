The idea in one screen

On a machine you own, one user's speed is memory bandwidth divided by the bytes each token reads, and what fits is weights plus KV cache inside the memory the GPU may use. So local inference is choosing a file (its format and its quantisation type) small enough to fit and cheap enough to read, and an engine that reads it well.

One model on this laptop: the same 2.49 GB file decides both what fits and how fast it can stream

Qwen3-4B at Q4_K_M (with an importance matrix) on an Apple M1 Pro with 16 GB. Top: memory, to scale. The GPU may use (measured: Metal's recommended working set); the weights take 2.49 GB, and a full 40,960-token context adds 6.04 GB of F16 KV cache (147,456 bytes per token, derived from the config). Below: the bytes each generated token must read. With a short prompt that is the weights alone, so the ceiling is 200 GB/s / 2.49 GB = 80 tokens per second (measured: 43.2, because unpacking 4-bit blocks costs this GPU arithmetic, section 1); with the context full it is 2.49 + 6.04 = 8.53 GB, a ceiling of 23.

You need: prefill, decode and the KV cache from the parent, {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} (its section 2 explains why decode is memory-bound). Number formats and the general methods (GPTQ, AWQ, quantisation-aware training) are owned by {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}; which small model to choose is {{Distillation and small language models|n:3c65c17b0d0d81efa2a8c3b3b623eb09}} ("What makes a good small model"). This page owns running models locally: the engines, the file formats, the quantised types in practice, and memory budgets on laptops, GPUs and phones.

Prefill, decode
reading the whole prompt in one pass; then producing one token per pass. TTFT is the wait before the first token; tokens per second is the speed after it.
GGUF
llama.cpp's one-file format: weights in its own quantised types, plus tokenizer, chat template and architecture numbers.
safetensors
a header plus raw tensor bytes, no code; the Hugging Face standard, and the container MLX uses.
Quant type, recipe
Q4_K is a type (how one block of weights is stored); Q4_K_M is a recipe that mixes types across tensors.
Bits per weight (bpw)
file bits divided by weights, scales included: what sets size and decode speed.
Importance matrix (imatrix)
per-column activation statistics from a calibration text, used to choose scales that protect the weights that matter.
KL divergence (KLD)
how far a quantised model's next-token distribution moved from the original's; 0 means identical.
Slot
one conversation in llama-server, with its share of the KV cache.
Memory-map (mmap)
make a file appear as memory without reading it; pages load on first touch.
