6. MLX and mlx-lm on Apple silicon

MLX is Apple's array framework for its own chips (open source, from Apple's machine learning research team): NumPy-like arrays, automatic differentiation, and two design choices that matter for inference. Arrays live in unified memory, so the CPU and GPU use the same bytes without copies; and evaluation is lazy: operations build a graph that runs only when a result is needed, which lets MLX fuse work and skip what is never used. mlx-lm is the language-model package on top: generation, a server, conversion and quantization from Hugging Face checkpoints, and LoRA fine-tuning. Versions here: MLX 0.32.3, mlx-lm 0.32.0 (1 October 2026, {{PyPI|https://pypi.org/project/mlx-lm/}}).

Why it exists next to llama.cpp. llama.cpp is a C++ engine for every platform; MLX is a framework, written for Apple's GPU, that researchers can read and change in Python (a model in mlx-lm is a short Python file). New architectures often appear in mlx-lm within days, and Ollama, LM Studio and Perplexity's Lily all build on MLX for Macs (section 7).

MLX's quantization: a scale and a bias per group

MLX's default affine quantization stores, per group of 64 consecutive weights, a 16-bit scale and a 16-bit bias, and each weight as a 4-bit code: w ≈ scale × q + bias. That is 4 + 32/64 = 4.5 bits per weight, the same as Q4_0 or Q4_K, with an offset like Q4_1. Other modes: mxfp4 (groups of 32 sharing an 8-bit power-of-two scale: 4.25 bits), nvfp4 (groups of 16 with an FP8 scale) and mxfp8 (MLX v0.32.3 mx.quantize, {{ops.cpp|https://github.com/ml-explore/mlx/blob/v0.32.3/python/src/ops.cpp}}); group size 32 or 128 and 2 to 8 bits; and mixed recipes (--quant-predicate mixed_3_6: 3 bits for most layers, 6 for sensitive ones; mlx_lm/convert.py L20 to L80). mlx-lm also ships calibrated methods (awq, gptq, dwq distilled quantization), not measured here.

mlx_lm.server: good for one person

The server batches: up to 32 requests decode together and 8 prompts are read together (--decode-concurrency, --prompt-concurrency, server.py L1876 to L1887), since v0.28.4 (December 2025). A quantized KV cache (--kv-bits) turns batching off, and so does a draft model (L365). Its own documentation says it is "not recommended for production" ({{SERVER.md|https://github.com/ml-explore/mlx-lm/blob/v0.32.0/mlx_lm/SERVER.md}}). The parent's {{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} found why: past about 2 requests per second on Qwen3-0.6B its memory grew to 12 GB and Metal ran out of memory, killing the generation thread. SGLang's MLX backend fared worse on this machine (wrong text from cache hits, crashes on eviction: the {{SGLang sibling|n:3c65c17b0d0d81e691e4ce9f9b5d1fad}}). For more than a few users on a Mac, llama-server is the steadier server.

Beyond one Mac, and other engines on MLX

  • Several Macs. mx.distributed splits a model over Macs (tensor or pipeline parallel, --pipeline in mlx-lm). From macOS 26.2, RDMA over Thunderbolt 5 lets Macs exchange data directly; MLX's JACCL back end uses it with "communication latency an order of magnitude lower than the ring backend" ({{MLX distributed docs|https://ml-explore.github.io/mlx/build/html/usage/distributed.html}}). docs
  • Lily (Perplexity, open source, 2 September 2026): a Rust and Metal server for one model, Qwen3.6-35B-A3B, on M5-class chips, loading MLX's 4-bit checkpoints. Its own report against mlx-lm on an M5 Max: decode 1.31 times faster at 256 tokens of context and 1.24 at 131K; prefill 1.13 times at 256 tokens but 0.80 (slower) at 131K ({{pplx-garden performance doc|https://github.com/perplexityai/pplx-garden/blob/main/lily/docs/2026-09-02-performance-mlx-0.32.2.md}}). vendor A specialised engine buys speed for one model on one chip.
  • Ollama on MLX: its blog reported Qwen3.5-35B-A3B in NVFP4 on MLX against Q4_K_M on llama.cpp at 1,810 against 1,154 tokens per second of prefill and 112 against 58 of decode, using the M5's GPU neural accelerators ({{Ollama blog, 30 March 2026|https://ollama.com/blog/mlx}}). vendor, one model, one chip, two different quantizations.
