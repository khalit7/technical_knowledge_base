What llama-server serves (depth)

llama-server is llama.cpp's HTTP server: one process, one model (or many in router mode), an OpenAI-compatible API (/v1/chat/completions, /v1/completions, embeddings, reranking), an Anthropic-compatible /v1/messages ({{PR #17570|https://github.com/ggml-org/llama.cpp/pull/17570}}, November 2025), its own /completion, and a web UI. Everything below was read in the source at build 11146 and run on this laptop with Qwen3-1.7B Q4_K_M; the {{C++ page|n:3cd5c17b0d0d81ceadcee44fe9c023a0}} (Part 3) walks the code itself.

Slots: how one server serves several people

A slot is one conversation in progress: its tokens, its sampling settings and its share of the KV cache. -np N sets the number of slots, and every step all busy slots go through the model together (continuous batching: a slot joins or leaves the batch at any step, as in the parent's section 5); a request that finds every slot busy waits. -c is the total KV cache in tokens: with the default split KV each slot gets -c / N; with a unified KV (-kvu) all slots draw from one pool, so one long conversation can use most of it. Defaults at b11146: -np "auto" means 4 slots with a unified cache (tools/server/server.cpp L156 to L160). Measured here:

Which slot a request gets, and the prompt cache tier (depth)

Which slot a request gets (get_available_slot, server-context.cpp L1547 to L1655): among idle slots, the one whose cached tokens share the longest common prefix with the new prompt, if that prefix is more than 10% of the prompt (--slot-prompt-similarity, default 0.1); otherwise the least recently used. So a returning conversation lands on the slot that still holds its history and skips most of its prefill. A slot about to be overwritten is first saved to a host-memory prompt cache (--cache-ram, 8,192 MiB by default); the {{batching sibling|n:3c65c17b0d0d819db53bd2c48909e5b2}} measured that tier (113 to 421 ms to restore a 5,010-token prompt against 5.63 s to recompute it).

Two ways the cache is reused, and one way it is stretched

Prompt caching (cache_prompt, on by default): a new request keeps the cached tokens it shares as a prefix with the slot's previous prompt and computes only the rest (L3216 to L3225), like vLLM's prefix cache, per slot. But once one early token differs (an edited message, a tool result inserted in the middle, a document removed) everything after it is recomputed, even text still there. Cache reuse (--cache-reuse N, off by default) goes further: after the common prefix it scans the old cache for runs of at least N tokens that match the new prompt and moves them instead of recomputing them (L3226 to L3290), possible because a cached key can be re-rotated to a new position (RoPE positions are a rotation). It is approximate: the moved keys and values were computed attending to the old preceding text.

Context shift: how it works (depth)

Context shift (--context-shift, off by default at b11146) handles a conversation that outgrows its slot. Off: generation stops when the slot is full, and a longer prompt is refused ("exceeds the available context size", L3195 to L3215). On: when the slot fills, the server keeps the first n_keep tokens, discards half of the rest and shifts the remainder back (L2909 to L2970), so generation goes on while forgetting the middle. Fine for endless chat; wrong for anything that must see its whole input, and, like cache reuse, wrong for an evaluation that must match a fresh run.

Router mode: several models behind one port

Started without -m and with --models-dir, llama-server becomes a router: it lists the GGUF files, starts one child llama-server per model on demand, forwards each request by its "model" field, and at --models-max unloads the least recently used (router mode {{PR #17470|https://github.com/ggml-org/llama.cpp/pull/17470}}, December 2025; LRU scheduling {{PR #26572|https://github.com/ggml-org/llama.cpp/pull/26572}}, August 2026).
