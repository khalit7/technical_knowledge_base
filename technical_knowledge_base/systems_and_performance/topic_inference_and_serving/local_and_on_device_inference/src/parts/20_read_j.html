A 5090 reads memory nine times faster than this laptop (1,792 against 200 GB/s) but holds 32 GB against a Mac's up to 512 GB. That is the whole trade between the two kinds of local machine: a GPU streams a model that fits much faster; a big Mac fits a model that a GPU cannot hold. At 300.4 tokens per second the 3.56 GiB (3.83 GB) file is read at 1.15 TB/s, 64% of the 5090's peak; this laptop reaches of its peak at best, on Qwen3-1.7B in F16 (section 1). Prompt reading barely moves between the two cards (14,970 against 14,771): it is bound by arithmetic, not bandwidth, and the scoreboard does not say which kernels each run used.

Two cards: what a second GPU buys

Two 5090s give 64 GB. How the model is split decides whether they also give speed. With layer split (llama.cpp's default, -sm layer: the first half of the layers on one card, the second half on the other) a token passes through card 1 then card 2, each reading its half: the memory adds up, the bandwidth for one user does not, because the cards take turns. With tensor split (tensor parallelism: every matrix cut in two, both cards read their halves at the same time, then exchange partial results over PCIe) one user's token is read at up to twice the bandwidth, minus the exchange. The {{Distributed and disaggregated serving|n:3c65c17b0d0d8170bd7cdf47af0ec07b}} sibling explains these splits from zero; here is what is published for consumer cards:

  • Layer split, one user. Ollama on two 5090s: Llama 3.3 70B at 4 bits, 26.85 tokens per second; DeepSeek-R1 70B 27.03; Qwen2.5 72B 24.15 (hosting vendor's measurement, {{DatabaseMart|https://databasemart.com/blog/ollama-gpu-benchmark-rtx5090-2}}, Ollama 0.6.5). The bandwidth rule for a 70B model at about 4.8 bits (about 43 GB, one card's bandwidth): 1,792 / 43 = 42 tokens per second ceiling, so 27 is 64% of it, the same efficiency as one card.
  • Tensor split in llama.cpp (-sm tensor, experimental, merged 9 April 2026): on two RTX 4090s, Llama 8B F16 generation went from 60.28 to 96.63 tokens per second (1.60 times) while prompt reading fell to 0.76 times; four 4090s took Llama 70B Q4_K_M from 21.25 to 48.31. Marked "not yet production ready" at merge, CUDA only for the fast path, needs flash attention (maintainer's numbers, {{PR #19378|https://github.com/ggml-org/llama.cpp/pull/19378}}).
  • Many users, vLLM. One 5090 serving Qwen3-Coder-30B-A3B (AWQ 4-bit) to 400 concurrent requests: 4,570 output tokens per second in total; two 5090s serving Llama 3.3 70B AWQ with pipeline parallelism: 1,230 (independent, {{CloudRift, 9 October 2025|https://www.cloudrift.ai/blog/benchmarking-rtx-gpus-for-llm-inference}}). No published dual-5090 tensor-parallel curve against concurrency was found.
GeForce cards cannot talk to each other directly

NVIDIA does not support peer-to-peer (P2P) transfers between GeForce cards: "RTX 50-series are Geforce GPU series, and p2p is not supported" ({{NVIDIA developer forum, 13 March 2025|https://forums.developer.nvidia.com/t/p2p-issue-using-two-rtx-5090-gpus/326776/8}}). Tensor parallelism therefore exchanges data through host memory. vLLM v0.31.0 detects this, disables its custom all-reduce ("your platform lacks GPU P2P capability or P2P test failed") and falls back to NCCL ({{custom_all_reduce.py|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/distributed/device_communicators/custom_all_reduce.py}}). Community-patched kernel modules re-enable P2P ({{tinygrad|https://github.com/tinygrad/open-gpu-kernel-modules}}, for the 4090; {{aikitoria's fork|https://github.com/aikitoria/open-gpu-kernel-modules}}, for the 30, 40 and 50 series): unsupported, at your own risk. On desktop CPUs two cards also share the CPU's lanes: a Ryzen 9 9950X has 24 usable PCIe 5.0 lanes and a Core Ultra 9 285K allows "2x8+2x4", so two GPUs run at x8 each, about 32 GB/s per direction ({{AMD|https://www.amd.com/en/products/processors/desktops/ryzen/9000-series/amd-ryzen-9-9950x.html}}, {{Intel|https://www.intel.com/content/www/us/en/products/sku/241060/intel-core-ultra-9-processor-285k-36m-cache-up-to-5-70-ghz/specifications.html}}).

A setup for your dual RTX 5090 box

Not run here; each step is sourced, the choices are reasoned from sections 1 to 7. Use the {{Fit and speed|#t-fit}} tab with "2 × RTX 5090" to check any model before downloading it.

  1. Linux driver and CUDA. Blackwell runs only on NVIDIA's open kernel modules on Linux ("Blackwell and later are only supported by the open kernel modules", {{driver README 595.84|https://download.nvidia.com/XFree86/Linux-x86_64/595.84/README/kernel_open.html}}); the first Linux driver for the 5090 was 570.86.16 (30 January 2025), so use a current branch. CUDA 12.8 is the first toolkit that targets SM_120 and needs driver 570.26 or later ({{CUDA 12.8 release notes|https://docs.nvidia.com/cuda/archive/12.8.0/cuda-toolkit-release-notes/index.html}}); PyTorch 2.7 (23 April 2025) was the first release with CUDA 12.8 wheels ({{PyTorch blog|https://pytorch.org/blog/pytorch-2-7/}}).
  2. Interactive use, one person: llama.cpp (llama-server) with GGUF. A model up to about 28 GB at your chosen quant: put it on one card (CUDA_VISIBLE_DEVICES=0, {{build.md|https://github.com/ggml-org/llama.cpp/blob/b11541/docs/build.md}}) and keep the second card for a second model (a draft model, an embedding model, or another chat model through router mode, section 5). Between 28 and about 58 GB: both cards with the default layer split, which fits but does not speed up one user; try -sm tensor for speed, knowing it is experimental. Prefer an imatrix K-quant or IQ4_XS at 4 to 5 bits (section 4) and a q8_0 KV cache for long contexts (the {{batching sibling|n:3c65c17b0d0d819db53bd2c48909e5b2}} measured q8_0 at no perplexity cost on Qwen3-1.7B).
  3. Several users or parallel agents: vLLM. When requests arrive together, batching is what matters (the parent's section 3) and vLLM's scheduler beats llama-server's slots. A model that fits one card: run two independent replicas, one per GPU, behind a router ({{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}): no PCIe exchange, twice the throughput. A model that needs both cards: --tensor-parallel-size 2 (or pipeline parallelism, which CloudRift used) with an NVFP4 or AWQ checkpoint; vLLM v0.30.0 made NVFP4 with 4-bit activations the default on SM120 ({{vLLM releases|https://github.com/vllm-project/vllm/releases}}). Expect the exchange over PCIe without P2P to cost more than on a datacenter node; measure it.
  4. Power. Two cards at 575 W each plus the CPU is a lot for one desktop. nvidia-smi -pl <watts> caps a card's power (root, not persistent across reboots, {{nvidia-smi docs|https://docs.nvidia.com/deploy/nvidia-smi/index.html}}); decode is bandwidth-bound, so a moderate cap usually costs generation speed less than it costs prompt reading. That last point is reasoning from section 1, not a measurement: check it on the box with llama-bench.
  5. What fits, roughly (computed in the Fit and speed tab from the models' configs and the bits per weight measured in section 4): 8B to 14B dense models at 8 bits on one card; 32B dense at Q4_K_M on one card with room for context; 70B dense at about 4.8 bits across both; gpt-oss-120b as released (MXFP4 experts, the rest BF16: about 65 GB) does not fit in 64 GB, but a mixture of experts tolerates keeping some experts in system RAM: --n-cpu-moe N keeps the experts of the first N layers on the CPU, which costs speed only for those layers.
