safetensors: remove the program

safetensors removes the program: 8 bytes giving the header length, a JSON header (each tensor's dtype, shape and byte offsets), then the raw bytes back to back. Nothing in it can name a function, and each tensor is a slice of the file at a known place. It cannot say "this tensor is that one", so tied weights are stored twice: Qwen3-0.6B's lm_head duplicates its embedding, of the file.

The layout, field by field (depth)

A safetensors file is three things in a row, and nothing in it can name a function ({{format spec|https://github.com/safetensors/safetensors}}):

  1. 8 bytes: an unsigned 64-bit little-endian integer N, the length of the header.
  2. N bytes of JSON: for every tensor its dtype, shape and data_offsets [begin, end) from the start of the data buffer, plus an optional __metadata__ map of strings to strings ("Arbitrary JSON is not allowed").
  3. The data buffer: every tensor's raw bytes, back to back. The spec forbids holes and overlaps, which also rules out "polyglot" files hiding a second payload.

The first bytes of the real Qwen3-0.6B model.safetensors ( bytes): the first 8, read little-endian, give the header length, and the JSON starts right after.

The header measured, and what each tool does with the duplicate (depth)

The header is bytes describing tensors, of the file. A reader parses that JSON, and then each tensor is a slice of the file at a known place: no parsing, no conversion.

What it cannot say: tied weights are stored twice. Qwen3-0.6B's config says tie_word_embeddings: true (the input embedding and the output layer, lm_head, are one matrix), but safetensors cannot express an alias, so the released file stores both; the two byte ranges hash the same, measured here: bytes (, of the file) are a duplicate. Qwen3-1.7B does the same in its second shard (its index has 311 entries and the second shard holds exactly one tensor, lm_head.weight); Qwen3-4B's checkpoint does not. Downstream tools disagree: MLX's converter honours the tie and keeps one copy ( tensors; Qwen3-1.7B is 3.44 GB in MLX bf16 against 4.06 GB as F16 GGUF), while llama.cpp's converter keeps both, as token_embd and output, which inflates small models' bits per weight (section 4).

Header limits, padding, shards, and the project's status (depth)

The Rust reference implementation refuses headers over 100 MB (MAX_HEADER_SIZE = 100_000_000, {{tensor.rs L10|https://github.com/safetensors/safetensors/blob/main/safetensors/src/tensor.rs}}), so a hostile file cannot make you allocate gigabytes of JSON, and its writer pads the header with spaces to a multiple of 8 bytes so the buffer starts 8-byte aligned (the Qwen file's header ends in one space). MLX's writer does not pad: the MLX file's header is bytes, 4 more than a multiple of 8, which the format allows.

Shards. Big checkpoints are split into model-00001-of-00002.safetensors and so on, with model.safetensors.index.json mapping every tensor name to its shard. transformers chooses the split when saving: max_shard_size defaulted to "5GB" in v4 and "50GB" from v5.0.0 (2026-01-26). The Hub recommends files under 200 GB and enforces 500 GB per file ({{Hub storage limits|https://huggingface.co/docs/hub/storage-limits}}).

Status, October 2026. A Trail of Bits audit commissioned by Hugging Face with EleutherAI and Stability AI found "no critical security flaw leading to arbitrary code execution" (2023-05-23, {{HF blog|https://huggingface.co/blog/safetensors-security-audit}}). safetensors became a PyTorch Foundation project on 2026-04-08 ({{announcement|https://www.linuxfoundation.org/press/pytorch-foundation-announces-safetensors-as-newest-contributed-project-to-secure-ai-model-execution}}) and moved to the github.com/safetensors organisation; the latest release is v0.8.0 (2026-06-09). Its dtypes run from F64 down to F8 (E4M3, E5M2, E8M0) and F4/F6 for microscaling formats.

GGUF: one file, everything in it

GGUF goes the other way: one file holding tensors, tokenizer, chat template and architecture numbers as typed metadata, every tensor aligned so the file can be mapped and used in place. Each tensor carries its own type, so "Q4_K_M" is a mix of types (section 4).

The layout, field by field (depth)

GGUF goes the other way: tensors, tokenizer, chat template and architecture numbers travel together, the last three as typed key/value metadata ({{gguf.md|https://github.com/ggml-org/ggml/blob/master/docs/gguf.md}}; llama.cpp's header sums it up in 30 lines, {{gguf.h L1-L30|https://github.com/ggml-org/llama.cpp/blob/b11146/ggml/include/gguf.h}}):

  1. Magic GGUF (bytes 47 47 55 46), version (u32, now 3), tensor count and key/value count (64-bit each).
  2. Key/value pairs: a key string (a u64 length, then the bytes), a value type (one of 13: integers, floats, bool, string, array), the value. Keys are namespaced: general.architecture, qwen3.attention.head_count, tokenizer.ggml.tokens.
  3. Tensor infos: each tensor's name, number of dimensions, dimensions, type, and offset into the data section.
  4. Padding to general.alignment (32 when absent), then the data section; every offset is a multiple of the alignment, so the file can be mapped and each tensor used in place.

Reading GGUF shapes (depth)

One trap: GGUF stores dimensions fastest-first, the reverse of PyTorch: the embedding safetensors lists as [151936, 1024] appears as [1024, 151936]. Same bytes, same order, opposite way of writing the shape. Each tensor carries its own type, so one file mixes several; "Q4_K_M" is a recipe, taken apart in section 4.

Self-contained, but check what it contains. One file cannot drift out of sync, so ollama run works from it alone; but it holds only what its maker put in. The Qwen3-0.6B GGUF in the shared store, made by Unsloth, against one converted here from the same Qwen release (checked here): its chat template was rewritten (4,905 characters against the original 4,168), it carries no sampling defaults, it has one end-of-turn id where the repo has two, and it dropped the separate output layer.

Splitting a GGUF, where the format came from, and its costs (depth)

Splitting. Files over a hosting limit are split with llama-gguf-split into name-00001-of-00003.gguf and so on. The 397 MB file split at 150 MB here: the first shard carries all 28 metadata keys plus three split.* keys and 28 tensors; the others only the split.* keys and their tensors (179 and 103). Pointing llama.cpp at the first shard loads all three, with no index file, and --merge gave back all 310 tensors byte-identical (the merged file is 96 bytes larger: the split keys stay). Run here.

  • History. GGUF replaced llama.cpp's earlier files (GGML, then GGMF with a version, then GGJT with aligned tensors for mmap), whose hyperparameters were an untyped positional list, so each new architecture broke old loaders. GGUF's typed, named metadata fixed that; it landed with {{PR #2398|https://github.com/ggml-org/llama.cpp/pull/2398}} on 2023-08-21; version 3 added big-endian files. The ggml.ai team joined Hugging Face on 2026-02-20 ({{announcement|https://github.com/ggml-org/llama.cpp/discussions/19759}}), the projects staying community-run.
  • New architectures wait for the converter. Every family needs its own code in llama.cpp's converter (in b11146 a package of per-family modules) and its own graph in llama.cpp, so a new model can take days to months to get a working GGUF.
  • No code, but not no risk. A parser reading lengths from a hostile file is attack surface: Databricks reported heap overflows in gguf_init_from_file (CVE-2024-25664 to 25668, 2024-03-22, {{Databricks|https://www.databricks.com/blog/ggml-gguf-file-format-vulnerabilities}}) and Cisco Talos others (CVE-2024-21836 and three more). Today's parser rejects strings over 1 GiB and arrays over 230 elements ({{gguf.cpp L19-L20|https://github.com/ggml-org/llama.cpp/blob/b11146/ggml/src/gguf.cpp}}). And the embedded chat template is a program: llama-cpp-python rendered it with an unsandboxed Jinja2 until 0.2.72 ({{CVE-2024-34359|https://github.com/abetlen/llama-cpp-python/security/advisories/GHSA-56xg-wfcc-g829}}, CVSS 9.6, 2024-05-10).

MLX: safetensors with packed groups

An MLX model is safetensors plus a quantization block in config.json; each quantised layer becomes three tensors: packed 4-bit codes, and a BF16 scale and bias per group of 64 weights.

The config and the three tensors of one layer (depth)

An MLX model is a Hugging Face-style folder whose weights are safetensors and whose config.json says how they are quantised; mlx_lm convert -q wrote "quantization": { "group_size": 64, "bits": 4, "mode": "affine" } into Qwen3-0.6B's config (and mirrored it as quantization_config). What MLX adds is a layout: each quantised linear layer becomes three tensors, weight with the 4-bit codes packed eight to a 32-bit word (lowest bits first), and scales and biases with one BF16 scale s and offset b per group of 64 weights, each weight being s·q + b ({{mx.quantize|https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.quantize.html}}). So the 4-bit file has tensors where the BF16 one has 310; layer 0's key projection (1,024 × 1,024) becomes k_proj.weight U32 [1024, 128], k_proj.scales and k_proj.biases BF16 [1024, 16].

The same 256 weights, 144 bytes either way: GGUF keeps a block together, MLX spreads it over three tensors

Both cost 4.5 bits per weight; the difference is where the scales live, which shapes the kernels. Loading needs no copy to a GPU (unified memory); MLX does not use the Neural Engine ({{mlx issue #18|https://github.com/ml-explore/mlx/issues/18}}, since 2023). Its other modes and its quality against GGUF: section 7.

One MLX group decoded by hand, and conversion runs (depth)

The first MLX group decoded by hand (first word 06 b5 ae cb = 3,417,224,454, codes 6, 0, 5, 11, 14, 10, 11, 12) equals mx.dequantize exactly run here, mlx 0.32.3. Two runs of mlx_lm convert took 2.3 and 1.7 s and gave the same SHA-256 as the store's copy made two days earlier.

ONNX: the model as a graph

ONNX stores the computation as well as the weights: a graph of operators pinned to an opset, so it runs on CPUs, GPUs and NPU SDKs years later. Qwen3-0.6B exported here became operators and no KV cache, so generating needs a cache-aware export and a loop (ONNX Runtime GenAI). It suits encoders, classic ML and NPUs, not datacenter LLM engines.

The export measured, and why LLM engines skip ONNX (depth)

ONNX stores the computation too: a graph of operators, weights as initializers, and an opset version that pins every operator's meaning ("When the inventory of a given operator set changes ... its version MUST increase", {{Versioning.md|https://github.com/onnx/onnx/blob/main/docs/Versioning.md}}), so a graph exported today runs on a runtime written years later, on CPU, GPU or an NPU vendor's SDK. Protobuf messages cannot exceed 2 GB, so larger models keep weights in an external data file ({{ExternalData.md|https://github.com/onnx/onnx/blob/main/docs/ExternalData.md}}). There is no "attention" operator and no KV cache: attention became MatMul, Softmax (, one per layer), Transpose and Reshape, and the graph recomputes the whole sequence on every call. To generate you need a cache-aware export and a loop, such as {{ONNX Runtime GenAI|https://github.com/microsoft/onnxruntime-genai}} ("implements the generative AI loop for ONNX models" including "KV cache management"; v0.17, 2026-09-28; behind Foundry Local, Windows ML and the VS Code AI Toolkit). So ONNX suits encoders (embeddings, rerankers), classic ML, NPUs and Intel hardware; datacenter LLM engines do not use it, because their speed lives in a paged KV cache, custom attention kernels and per-step scheduling, which a fixed graph cannot express ({{vLLM: inside the default engine|n:3c65c17b0d0d8113b976d8bcaf2c0722}}).

The Hugging Face repo, quantised checkpoints and remote code

Almost every format is made from a Hugging Face repo. Quantised checkpoints for vLLM and SGLang stay safetensors (compressed-tensors), and trust_remote_code=True runs the repo's own Python: pickle's risk by another door.

Quantised checkpoints and remote code (depth)

Almost every format above is made from a Hugging Face model repo, and knowing its files is what lets you debug "the model loads but answers badly". Quantised checkpoints stay in safetensors: FP8, INT4 or NVFP4 checkpoints served by vLLM and SGLang are usually compressed-tensors, which "extends the safetensors format": packed weights and scales are ordinary tensors, and config.json carries "quant_method": "compressed-tensors" with a format such as pack-quantized or nvfp4-pack-quantized ({{repo|https://github.com/vllm-project/compressed-tensors}}, 0.19.0, 2026-09-21), written by llm-compressor. That is how the parent's FP8 Llama 3.1 70B arrives at vLLM. Remote code: a repo can ship Python modeling files, which transformers runs only with trust_remote_code=True: pickle's risk by a different door; read the code or pin a revision you have read.

Conversions: which ones keep every number

Every arrow between formats is a repack (same numbers, new layout) or a requantisation (new numbers):

Lossless: pickle to safetensors, BF16 safetensors to BF16 GGUF or F32 ONNX. Lossy: BF16 to F16 (a little) and any quantisation, so always quantise from the full-precision original, never from a quantised file.

The rules, with the runs behind them (depth)
  • Lossless: pickle to safetensors; safetensors BF16 to GGUF BF16 (all 751.6 million values identical) or F32; safetensors to ONNX in F32. Not lossless: BF16 to F16, by a little (above).
  • Lossy by design: any quantisation (llama-quantize, mlx_lm convert -q, llm-compressor, a TensorRT build with FP8 or INT4). Always quantise from the full-precision original, never from an already quantised file: errors compound. Dequantising a GGUF gives a rounded shadow of the model, so if you need a GGUF and an FP8 checkpoint, make both from the safetensors original.
  • Lossy in a second sense: exports drop what is not numbers. The ONNX export carries no tokenizer, template or sampling defaults; a third-party GGUF may carry a different template.
  • Reproducible: the GGUF converter, llama-quantize and mlx_lm convert all gave byte-identical files on re-runs here, so a SHA-256 is a fair check that a file is what you think.

Loading: mapping, not reading

safetensors and GGUF tensors sit at known offsets, so a loader memory-maps the file (nothing is read until touched) instead of running a pickle program and copying every storage. Same Qwen3-0.6B weights, warm cache, measured here:

What mapping does (depth)

To memory-map a file is to make it appear as memory without reading it: nothing is copied until a byte is touched, then the OS brings in that 16 KiB page (on Apple silicon) from its page cache, the RAM it keeps recently read files in. Because safetensors and GGUF tensors sit at known offsets in their final layout, a loader can hand out slices of the mapping; a pickle must run its program first and, by default, copy every storage. The same Qwen3-0.6B weights loaded both ways, each in a fresh process, times, files already in the page cache (measured on Apple M1 Pro, PyTorch 2.14.1, safetensors 0.8.0):

safetensors returns in milliseconds because it maps; a pickle copies first

Bars: median seconds to return (whiskers: min to max). Right: extra resident memory over a baseline process. "Touch" reads one value in every page of every tensor, so all 1.5 GB is really brought in.

llama.cpp maps GGUF by default; mapping matters most when the file is not yet in RAM or only part of the model is needed, and a cold load is disk-bound.

The numbers, and llama-server mapped against read (depth)

Plain torch.load took and MiB of new memory before anything was usable; safetensors.torch.load_file returned in with MiB, and touching every page then took in total. llama.cpp maps GGUF files by default (--load-mode auto: "mmap, unless a device does not support it"). llama-server on Qwen3-4B Q4_K_M (2.5 GB), four starts each way, warm page cache, measured:

Mapping saved about a third of a second and 0.6 GiB here (medians). The bigger wins come when the file is not yet in RAM, when several processes share one mapping, or when only part of the model is needed (a pipeline stage, a tensor-parallel rank). With a cold cache all of this is disk-bound: about 3.2 GB/s on this laptop's SSD ({{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}, which owns cold starts and autoscaling).

torch.load with mmap, the page cache, and published loading numbers (depth)

torch.load(mmap=True) closes most of the gap (, then touched) but still runs the pickle program. llama.cpp refuses to map a GGUF whose data section is not aligned. A second start is quicker because the file is still in the page cache (the router run in section 6 shows it).

The safetensors README credits the format with loading BLOOM on 8 GPUs "from 10mn with regular PyTorch weights down to 45s" vendor. fastsafetensors (IBM Research, {{arXiv 2505.23072|https://arxiv.org/abs/2505.23072}}) copies groups of tensors straight into GPU memory, with GPUDirect Storage where available, and reports 4.8x to 7.5x faster loads and 26.4 GB/s for Llama-70B on four GPUs authors; vLLM and SGLang accept --load-format fastsafetensors. On a datacenter GPU the weights must still be copied from host memory into HBM, which is what these attack.

Compiled artifacts: TensorRT engines, and TensorRT-LLM's move away from them (depth)

Not run here (no NVIDIA GPU). NVIDIA's builder profiles kernels on the actual GPU, fuses layers, picks memory layouts and serializes the result with the weights into a plan (.plan or .engine): "By default, TensorRT engines are compatible only with the version of TensorRT used to build them" and "only compatible with the type of device where they were built" ({{Engine compatibility|https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html}}). Since TensorRT 8.6 two opt-ins loosen that: hardware compatibility (one plan for Ampere and newer, at some speed cost) and version compatibility (later releases of the same major version). Version-compatible plans embed runtime code, so deserialize only plans you trust. Treat plans as a cache keyed on (model, GPU, TensorRT version, shape profiles), built in CI, never as the model you publish.

Since v1.0.0 (2025-09-24) TensorRT-LLM's PyTorch backend is "the default experience": point it at safetensors and it uses NVIDIA's kernels without a build artifact. The old trtllm-build engine path is still in the latest stable release, v1.2.1 (2026-04-20), but was removed on main on 2026-07-14 and is gone from the 1.3 release candidates ({{releases|https://github.com/NVIDIA/TensorRT-LLM/releases}}). How it serves is on {{Distributed and disaggregated serving|n:3c65c17b0d0d8170bd7cdf47af0ec07b}}. Other compiled and serialised formats: the PT2 archive that torch.export.save and AOTInductor packaging write (a zip with the exported program as JSON and each weight as raw bytes, not pickle, {{spec|https://docs.pytorch.org/docs/main/user_guide/torch_compiler/export/pt2_archive.html}}; introduced in PyTorch 2.6), and TF SavedModel (a directory of a protobuf graph, variables and assets) beside Keras .keras (a zip of config.json, metadata.json and model.weights.h5, {{guide|https://keras.io/guides/serialization_and_saving/}}; Keras 3.15.1), for existing TensorFlow stacks. The on-device formats are in section 11.
