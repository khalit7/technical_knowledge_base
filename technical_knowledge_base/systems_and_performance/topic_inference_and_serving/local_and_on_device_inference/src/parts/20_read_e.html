3. Quantization from zero: what a GGUF type name means

The problem. Sections 1 and 2 say the same thing twice: fewer bytes per weight means more model in the same memory and more tokens per second. A trained model stores each weight as a 16-bit float (BF16 or F16). Quantization stores it in fewer bits, as a small integer code plus some shared numbers to turn codes back into values. The cost is error: the stored value is no longer exactly the trained one. The parent's {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}} page owns the general theory (number formats, quantization-aware training, GPTQ and AWQ); this section covers the family local engines use, llama.cpp's GGUF types, and section 4 measures them.

The idea: a scale per small block

Take 32 consecutive weights of one row. Find a scale d so that the codes cover the block's range, store d once (16 bits), and store each weight as the integer q nearest to w / d. Reading back, the kernel computes d × q as it multiplies (it dequantizes on the fly; the weights stay compressed in memory). The scale is per block because weights vary: one scale for a whole matrix would waste the codes on a few outliers. The cost of the scale is spread over the block: 16 bits over 32 weights is 0.5 bit per weight, so a 4-bit type with a 16-bit scale per 32 weights is 4.5 bits per weight (bpw), the number that sets file size and decode speed.

The stored scales and codes are decoded from the files' bytes; the reconstructed values are what llama.cpp's own dequantizer (gguf-py) returns.

Names like Q4_K_M are recipes, not types

A GGUF file mixes types. llama-quantize applies a recipe per tensor: the type in the name for most tensors, more bits where errors hurt most. For Q4_K_M ("medium"), the value projection (attn_v) and the second feed-forward matrix (ffn_down) get Q6_K in the first eighth of the layers, the last eighth and every third layer between (the use_more_bits rule, src/llama-quant.cpp L434 to L436, L556 to L557, L612 to L617), and the output layer gets Q6_K. _S and _L variants shift that balance: Q4_K_S is mostly Q4_K but not uniformly (attn_v in the first 4 layers and ffn_down in the first eighth go to Q5_K, the output layer to Q6_K), and the only _L type in llama.cpp is Q3_K_L; Hub uploads that keep the embedding and output at Q8_0 under an "_L" name are their makers' recipes, not llama.cpp types (same file and lines; the {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}} page corrected an old claim that Q4_K_S "is uniformly Q4_K"). So a "4-bit" Q4_K_M file is about bits per weight on average on Qwen3-1.7B, measured from the file below. Bigger model files on Hugging Face often add a maker's own mix (Unsloth's "dynamic" quants, for example); the name then tells you only the base type.

Importance matrices (imatrix): spend the error where it matters least

Plain quantization picks each block's scale to minimise the error on the weights themselves. But a weight that multiplies a large activation matters more than one that multiplies a small one. An importance matrix records, for each input column of each matrix, the average squared activation seen while running the model over a calibration text. llama-quantize --imatrix then chooses scales (and lattice points) that minimise the error weighted by that importance ({{PR #4861|https://github.com/ggml-org/llama.cpp/pull/4861}}, January 2024). It costs one pass of the full-precision model over the calibration text (here 128 chunks of 512 tokens of bartowski's {{calibration_datav3|https://gist.github.com/bartowski1182/eb213dccb3571f863da82e99418f81e8}}, about 2 minutes for Qwen3-1.7B on this laptop) and nothing at run time: the file is the same size. The lowest types refuse to run without one: IQ1_S, IQ1_M, the IQ2 types and IQ3_XXS, plus Q2_K inside a Q2_K_S file (tensor_requires_imatrix, src/llama-quant.cpp L822 to L840). A caveat: the calibration text shapes what is protected, so a code-heavy calibration helps code, and an imatrix built from English prose alone can score well on English perplexity while code, other languages and long-context use quietly degrade (practitioner guidance, no single source: evaluate on your own tasks); the text used here was checked to share no 60-character passage with the WikiText-2 test text used to score the files.

Predict: you quantize the same model to Q4_K_M twice, once without an imatrix and once with one. How do the two files compare?
Same size and speed, better quality. The importance matrix changes which codes and scales are chosen, not how many bits are stored. On Qwen3-1.7B it cut Q4_K_M's KL divergence from to (section 4).
Cost, when it matters, how to check

Cost. Error (section 4 measures it) and, for i-quants and K-quants on some hardware, extra arithmetic per weight read. When it matters: always locally; in a datacenter the same trade appears as FP8 and NVFP4 checkpoints. How to check: llama-quantize --dry-run model-f16.gguf Q4_K_M prints every tensor's type and the final size without writing the file; the file's tensor list (gguf-py's gguf-dump) shows the mix you downloaded.
