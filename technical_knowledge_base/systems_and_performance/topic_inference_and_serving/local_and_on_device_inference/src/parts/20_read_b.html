1. One user's speed is set by memory bandwidth

To generate one token, the model multiplies the newest token's vector by every weight matrix: each weight is read from memory once and used for one multiply and one add. With one user that is 2 operations per weight read, so the arithmetic units wait for memory almost all the time (the parent's section 2 explains this from zero; {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}} counts it).

So the bandwidth rule is a ceiling, reached by formats that are cheap to unpack and approached less closely by complex ones on a small GPU. On a GPU with far more arithmetic per byte (an RTX 5090 has about 40 times this laptop's FP16 throughput for 9 times its bandwidth) small formats come much closer: 64% of peak for Q4_0 on the published scoreboard (section 9). The rule still decides the big choices: a model twice as large streams about half as fast, and a machine with twice the bandwidth about twice as fast.

The context adds bytes too

Each token also reads the KV cache of every earlier token: at 16,000 tokens Qwen3-1.7B reads GB of cache against GB of Q4_K_M weights, so long contexts stream slower.

The KV cache read, counted (depth)

Each new token also reads the KV cache of every earlier token. Qwen3-1.7B keeps 114,688 bytes per token (2 for K and V × 28 layers × 8 KV heads × 128 dimensions × 2 bytes), so at 16,000 tokens a token reads GB of cache besides GB of Q4_K_M weights: the cache is the larger read. The parent's {{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} measured the effect on Qwen3-0.6B: 198 tokens per second with an empty context, 56 at 16K. Long-context local work is slower than a short chat on the same model, and a q8_0 KV cache helps speed as well as memory.

Reading the prompt is the laptop's weak point

Prefill is arithmetic-bound, and it is the laptop's weak point: a 30,000-token history costs about seconds before the first token on Qwen3-1.7B at Q4_K_M, where a datacenter GPU takes a fraction of a second.

Prefill measured on this laptop (depth)

Prefill reads the weights once for all the prompt's tokens, hundreds of operations per byte, so it is limited by arithmetic. Measured here: Qwen3-1.7B F16 reads a 512-token prompt at tokens per second, times faster per token than generating, about TFLOP/s of useful arithmetic against a peak of about 5.3 ({{Topic: hardware|n:3c65c17b0d0d8118beeefaed56da6f8e}}). A 30,000-token agent history still costs seconds before the first token on Qwen3-1.7B at Q4_K_M (longer in practice, since attention grows with the prompt); a datacenter GPU does it in a fraction of a second. On a Mac, prompt length is what you feel.

What transfers. The rule is the same everywhere: one user's decode speed is bandwidth over bytes, and the parent's {{Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} uses exactly this step model for an H200. What does not transfer: the arithmetic shortfall on small formats (a GPU with tensor cores unpacks 4-bit blocks with time to spare), and the slow prefill (an H200's 1,979 FP8 TFLOP/s, the parent's figure, is about 370 times this GPU's 5.3). A datacenter never runs one user: batching shares each read of the weights across many users, the point of the parent page. How to check on your machine: llama-bench -m model.gguf -p 512 -n 128, then divide file size by the tg time per token.
