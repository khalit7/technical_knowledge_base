4. Quantisation from zero: what a GGUF type name means

Sections 1 and 2 say the same thing twice: fewer bytes per weight means more model in the same memory and more tokens per second. A trained model stores each weight as a 16-bit float; quantisation stores it as a small integer code plus a few shared numbers that turn codes back into values, at the cost of error. The general theory (number formats, quantisation-aware training, GPTQ and AWQ) is owned by {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}; this section is the family local engines use, llama.cpp's GGUF types, and section 5 measures them.

The idea: a scale per small block

Take 32 consecutive weights of one row. Find a scale d so the codes cover the block's range, store d once (16 bits), and store each weight as the integer q nearest to w / d. The kernel computes d × q as it multiplies (it dequantises on the fly; the weights stay compressed in memory). The scale is per block because one scale for a whole matrix would waste the codes on a few outliers. Its cost is spread over the block: 16 bits over 32 weights is 0.5 bit per weight, so a 4-bit type with a 16-bit scale per 32 weights is 4.5 bits per weight.

Names like Q4_K_M are recipes, not types

A GGUF file mixes types: llama-quantize applies a recipe per tensor, the type in the name for most and more bits where errors hurt most. For Q4_K_M ("medium"), the value projection (attn_v) and the second feed-forward matrix (ffn_down) get Q6_K in the first eighth of the layers, the last eighth and every third layer between (the use_more_bits rule, src/llama-quant.cpp L434 to L436, L556 to L557, L612 to L617), and the output layer gets Q6_K. In the Qwen3-0.6B Q4_K_M file read in section 3, 168 tensors are Q4_K, 29 are Q6_K (the embedding, and attn_v and ffn_down in 14 of the 28 layers) and 113 small vectors stay F32: bits per weight averaged over every value, not 4.

Why small models average more bits (depth)

On small models the label misleads further. Qwen3-1.7B's checkpoint stores its tied embedding twice (section 3), and llama.cpp keeps both copies as token_embd and output: 30.6% of the file's 2.03 billion values, which the quantiser keeps at higher precision. So on this model Q4_K_M averages bits per weight, Q2_K and IQ1_M (tensor mix of the Q4_K_M file made here: ). On a 70B model the embedding and output are about 3% of the weights, and the averages sit close to the names. Compare files by size, not by label.

_S and _L variants, and makers' own recipes (depth)

_S and _L shift the balance: Q4_K_S is mostly Q4_K but not uniformly (attn_v in the first 4 layers and ffn_down in the first eighth go to Q5_K, the output layer to Q6_K), and the only _L type in llama.cpp is Q3_K_L; Hub uploads that keep the embedding and output at Q8_0 under an "_L" name are their makers' recipes, not llama.cpp types (same file and lines; the {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}} page corrected an old claim that Q4_K_S "is uniformly Q4_K"). Bigger files on Hugging Face often carry a maker's own mix (Unsloth's "dynamic" quants, for example); the name then tells you only the base type. Never requantise a quantised file (Q8_0 to Q4_K_M stacks two roundings); always start from BF16 or F32.

Importance matrices: spend the error where it matters least

Plain quantisation picks each block's scale to minimise the error on the weights themselves, but a weight that multiplies a large activation matters more than one that multiplies a small one. An importance matrix records, for each input column of each matrix, the average squared activation over a calibration text; llama-quantize --imatrix then chooses scales (and lattice points) that minimise the error weighted by it ({{PR #4861|https://github.com/ggml-org/llama.cpp/pull/4861}}, January 2024). It costs one pass of the full-precision model over the calibration text (here 128 chunks of 512 tokens of bartowski's {{calibration_datav3|https://gist.github.com/bartowski1182/eb213dccb3571f863da82e99418f81e8}}, about 2 minutes for Qwen3-1.7B on this laptop) and nothing at run time. The lowest types refuse to run without one: IQ1_S, IQ1_M, the IQ2 types and IQ3_XXS, plus Q2_K inside a Q2_K_S file (tensor_requires_imatrix, src/llama-quant.cpp L822 to L840).

Predict: you quantise the same model to Q4_K_M twice, once without an imatrix and once with one. How do the two files compare?
Same size and speed, better quality: the importance matrix changes which codes and scales are chosen, not how many bits are stored. On Qwen3-1.7B it cut Q4_K_M's KL divergence from to (section 5).
A caveat on calibration text (depth)

A caveat: the calibration text shapes what is protected, so a code-heavy calibration helps code, and an imatrix built from English prose alone can score well on English perplexity while code, other languages and long-context use quietly degrade (practitioner guidance, no single source: evaluate on your own tasks). The text used here was checked to share no 60-character passage with the WikiText-2 test text used to score the files.
