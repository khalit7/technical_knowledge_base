1. One user's speed is set by memory bandwidth

The problem. To generate one token, the model multiplies the newest token's vector by every weight matrix it has. Each weight is read from memory once and used for one multiply and one add. With one user there is one token per step, so a step does 2 operations per weight read: the arithmetic units wait for memory almost all the time (the parent's section 1 explains this from zero; {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}} counts it). So:

tokens per second ≤ bandwidth / bytes read per token
bandwidth
how many bytes per second the memory holding the weights delivers (Apple: 200 GB/s for this M1 Pro)
bytes read per token
the weights the token passes through (all of them for a dense model, only the routed experts for a mixture of experts) plus the KV cache read so far

For Qwen3-1.7B in F16, the weights are GB, so the ceiling on this laptop is 200 / = tokens per second. Measured here: , which means memory was read at GB/s, of Apple's figure. Quantization (section 3) shrinks the bytes and should raise the ceiling in proportion:

The 4-bit file is not limited by memory any more: unpacking each 4-bit code with its 6-bit sub-block scale and minimum costs arithmetic, and this laptop's GPU (about 5 TFLOP/s, no matrix units) runs out of arithmetic first. Simpler blocks unpack faster: Q4_0, the same size class, reached . The {{Quant ladder|#t-quant}} tab plots every file against the bandwidth line.

So the bandwidth rule is a ceiling, reached by formats that are cheap to unpack and approached less closely by complex ones on a small GPU. On a GPU with far more arithmetic per byte (an RTX 5090 has about 40 times this laptop's FP16 throughput for 9 times its bandwidth) small formats come much closer to the line: 64% of peak for Q4_0 on the published scoreboard (section 8). The rule still decides the big choices: a model twice as large streams about half as fast on the same machine, and a machine with twice the bandwidth streams about twice as fast.

The context adds bytes too

Each new token also reads the KV cache of every earlier token. Qwen3-1.7B keeps 114,688 bytes per token (2 for K and V × 28 layers × 8 KV heads × 128 dimensions × 2 bytes), so at 16,000 tokens of context a token reads GB of cache besides its GB of Q4_K_M weights: the cache read is the larger part. The parent's {{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} measured this on Qwen3-0.6B: generation fell from 198 to 56 tokens per second between an empty context and 16K. Long-context local work (agents with big histories, whole documents) is slower than a short chat on the same model, and a quantized KV cache (q8_0) helps speed as well as memory.

Reading the prompt is a different problem

Prefill reads the weights once for all the prompt's tokens, so it does hundreds of operations per byte and is limited by arithmetic. Measured here: Qwen3-1.7B F16 reads a 512-token prompt at tokens per second, about TFLOP/s of useful arithmetic (2 operations × 1.41 billion multiplied weights per token: the embedding table is looked up, not multiplied, and llama-bench computes the output layer only for the last token, src/llama-batch.cpp L121 to L125), against a peak of about 5.3 for this GPU ({{Topic: hardware|n:3c65c17b0d0d8118beeefaed56da6f8e}}). That is times faster per token than generating. But it is the laptop's weak point: a 30,000-token agent history or document costs seconds before the first token on Qwen3-1.7B at Q4_K_M, at the measured rate (and longer in practice, since attention grows with the prompt). A datacenter GPU does the same in a fraction of a second. On a Mac, prompt length is what you feel.

CPU or GPU on the same chip

On Apple silicon the CPU and GPU share the same memory, so they see the same 200 GB/s in principle; in practice the CPU cores cannot pull that much. What transfers to datacenter GPUs, and what does not

The rule is the same everywhere: one user's decode speed is bandwidth over bytes, and the parent's {{Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} uses exactly this step model for an H200. What does not transfer: the arithmetic shortfall on small formats (a GPU with tensor cores unpacks 4-bit blocks with time to spare), and the slow prefill (an H200's 1,979 FP8 TFLOP/s, the parent's figure, is about 370 times this GPU's 5.3). And a datacenter never runs one user: batching shares each read of the weights across many users, which is the whole point of the parent page. How to check it on your machine: llama-bench -m model.gguf -p 512 -n 128, then divide file size by the tg time per token.
