2. Will it fit? Weights, cache and buffers

The model must sit in memory the GPU reads fast: its own VRAM on a graphics card (32 GB on an RTX 5090), or on a Mac the unified memory the CPU and GPU share, of which macOS lets the GPU use only part. Three things need room:

memory ≈ weights + KV cache + buffers
weights
parameters × bits per weight / 8 (Qwen3-4B at Q4_K_M: 4.02 billion × bits measured, about 2.5 GB)
KV cache
bytes per token × context × slots, where bytes per token = 2 × layers × KV heads × head size × bytes per value
buffers
scratch for one step's activations, a few hundred MB for small models (llama.cpp prints its compute buffer at start)

The cache can outweigh the model (Fig. 1): Qwen3-4B keeps 2 × 36 × 8 × 128 × 2 = 147,456 bytes per token in F16, so its full 40,960-token context costs 6.0 GB, more than twice the 2.5 GB of Q4_K_M weights. Long contexts are paid in memory first and speed second. Two remedies: a quantised cache (-ctk q8_0 -ctv q8_0 halves it; the {{batching sibling|n:3c65c17b0d0d819db53bd2c48909e5b2}} measured no perplexity change at q8_0 on Qwen3-1.7B), and a context no longer than you need.

macOS lets the GPU use of this laptop's 16 GB (measured), and llama-server's --fit shrinks unset settings until the plan fits.

Fig. 4, two kinds of local machine: where the bytes live decides what fits and how fast it streams

  1. A Mac: one pool for both. On this M1 Pro the CPU and the GPU read the same 16 GB at 200 GB/s. The file is loaded once and the GPU reads it where it lies: Fig. 1's 2.49 GB of weights and 6.04 GB of cache sit inside its share.
  2. A PC: two memories and a link. An RTX 5090 carries its own 32 GB of GDDR7 at 1,792 GB/s (section 9); the CPU has system RAM; between them runs PCIe (5.0 on this card; at x8, as when a desktop holds two cards, about 32 GB/s each way).
  3. Loading crosses the link once. The file comes from disk into system RAM and is copied over PCIe into the card's memory. Nothing crosses the link again while tokens are generated.
  4. Then every token reads the card's memory. The same 2.49 GB file streams at up to 1,792 GB/s: a ceiling of 1,792 / 2.49 = 719 tokens per second (derived; the published scoreboard reaches 64% of the 5090's peak, section 9) against 80 on the laptop.
  5. Too big for the card. A 70B model at about 4.8 bits is about 43 GB (section 9): 32 GB fit on the card and the remaining 11 GB of layers stay in system RAM, where the CPU runs them at system RAM's tens of GB/s (partial offload, -ngl, below). Those layers set the pace.
  6. The trade. A GPU streams a model that fits about nine times faster than this laptop (1,792 against 200 GB/s); a Mac's single pool, up to 512 GB, fits a model that no single card can hold.

Why a Mac has one pool

On Apple silicon the memory is not on the motherboard: it sits in the chip's own package, beside the processor. Apple describes "a unified memory architecture that brings together high-bandwidth, low-latency memory into a single pool within a custom package" ({{Apple, M1 announcement, 10 November 2020|https://www.apple.com/newsroom/2020/11/apple-unleashes-m1/}}). The CPU and the GPU are two clients of those same chips, so a model is never copied to the GPU; the price is that the pool's size is fixed when the machine is bought (16 GB on this laptop, up to 512 GB on the largest Macs).

When it does not fit

  • Partial offload. -ngl N puts only N layers on the GPU; the rest run on the CPU at the CPU's bandwidth. On a PC that is system RAM at tens of GB/s, many times below a GPU's; on a Mac the CPU shares the memory but pulls less of it ( against tokens per second, section 1).
  • Mixture-of-experts models read only a few experts per token, so keeping the experts in system RAM (--n-cpu-moe N or --cpu-moe) and attention and shared layers on the GPU costs less than offloading a dense model of the same size.
  • Memory-mapped files. llama.cpp maps the GGUF file (section 3), so a model larger than RAM still loads and its pages are read from disk as needed: a loading trick, not a way to run fast.
