The idea in one screen

On a machine you own, one user's speed is memory bandwidth divided by the bytes each token reads, and what fits is weights plus KV cache inside the memory the GPU may use. So local inference is choosing a file (its format and its quantisation type) small enough to fit and cheap enough to read, and an engine that reads it well.

1. One user's speed is set by memory bandwidth

To generate one token, the model multiplies the newest token's vector by every weight matrix: each weight is read from memory once and used for one multiply and one add. With one user that is 2 operations per weight read, so the arithmetic units wait for memory almost all the time (the parent's section 2 explains this from zero; Performance math counts it).

tokens per second ≤ bandwidth / bytes read per token
bandwidth
bytes per second the memory holding the weights delivers (200 GB/s for this M1 Pro, Apple's figure)
bytes read per token
the weights the token passes through (all of them for a dense model, only the routed experts for a mixture of experts) plus the KV cache read so far

Qwen3-1.7B in F16 is 4.06 GB, so the ceiling here is 200 / 4.06 = 49 tokens per second. Measured here: 45.9, memory read at 187 GB/s, 93% of Apple's figure. Quantisation (section 4) shrinks the bytes and should raise the ceiling in proportion:

Predict: Q8_0 is 1.9 times smaller than F16 and Q4_K_M (with an importance matrix) 3.2 times smaller. How much faster do they generate on this laptop?
Measured: Q8_0 generates at 79.3 tokens per second (1.73 times F16), reading memory at 171 GB/s; Q4_K_M at 101.4 (2.21 times), only 130 GB/s. The 4-bit file is no longer limited by memory: unpacking each 4-bit code with its 6-bit sub-block scale and minimum costs arithmetic, and this laptop's GPU (about 5 TFLOP/s, no matrix units) runs out of arithmetic first. Simpler blocks unpack faster: Q4_0, the same size class, reached 123.3. The chart below plots every file.

Files sit on or below the bandwidth line: the small, complex ones fall furthest below it

Every GGUF file of Qwen3-1.7B and Qwen3-4B made here, and MLX's Qwen3-1.7B files, against the GB read per token. Measured here with llama-bench -p 512 -n 128 -r 5 -fa 1 (Metal), fastest of up to three passes.

So the bandwidth rule is a ceiling, reached by formats that are cheap to unpack and approached less closely by complex ones on a small GPU. On a GPU with far more arithmetic per byte (an RTX 5090 has about 40 times this laptop's FP16 throughput for 9 times its bandwidth) small formats come much closer: 64% of peak for Q4_0 on the published scoreboard (section 9). The rule still decides the big choices: a model twice as large streams about half as fast, and a machine with twice the bandwidth about twice as fast. It is also why mixtures of experts with few active parameters suit laptops: Recursive's Flint, a coding model of 40B parameters with about 2.5B active per token (Apache 2.0), ships in NVFP4 and is claimed at more than 125 tokens per second on an M4 Pro MacBook Pro, averaged over a 128k-token session (Recursive, vendor). All 40B must fit in memory (section 2), but each token reads only the active few.

The context adds bytes too

Each token also reads the KV cache of every earlier token: at 16,000 tokens Qwen3-1.7B reads 1.84 GB of cache against 1.28 GB of Q4_K_M weights, so long contexts stream slower.

The KV cache read, counted (depth)

Each new token also reads the KV cache of every earlier token. Qwen3-1.7B keeps 114,688 bytes per token (2 for K and V × 28 layers × 8 KV heads × 128 dimensions × 2 bytes), so at 16,000 tokens a token reads 1.84 GB of cache besides 1.28 GB of Q4_K_M weights: the cache is the larger read. The parent's Engine bench measured the effect on Qwen3-0.6B: 198 tokens per second with an empty context, 56 at 16K. Long-context local work is slower than a short chat on the same model, and a q8_0 KV cache helps speed as well as memory.

Reading the prompt is the laptop's weak point

Prefill is arithmetic-bound, and it is the laptop's weak point: a 30,000-token history costs about 25 seconds before the first token on Qwen3-1.7B at Q4_K_M, where a datacenter GPU takes a fraction of a second.

The prefill FLOP count. 2 operations × 1.41 billion multiplied weights per token: the embedding table is looked up, not multiplied, and llama-bench computes the output layer only for the last token (src/llama-batch.cpp L121 to L125).

2. Will it fit? Weights, cache and buffers

The model must sit in memory the GPU reads fast: its own VRAM on a graphics card (32 GB on an RTX 5090), or on a Mac the unified memory the CPU and GPU share, of which macOS lets the GPU use only part. Three things need room:

memory ≈ weights + KV cache + buffers
weights
parameters × bits per weight / 8 (Qwen3-4B at Q4_K_M: 4.02 billion × 4.95 bits measured, about 2.5 GB)
KV cache
bytes per token × context × slots, where bytes per token = 2 × layers × KV heads × head size × bytes per value
buffers
scratch for one step's activations, a few hundred MB for small models (llama.cpp prints its compute buffer at start)

The cache can outweigh the model (the hero above): Qwen3-4B keeps 2 × 36 × 8 × 128 × 2 = 147,456 bytes per token in F16, so its full 40,960-token context costs 6.0 GB, more than twice the 2.5 GB of Q4_K_M weights. Long contexts are paid in memory first and speed second. Two remedies: a quantised cache (-ctk q8_0 -ctv q8_0 halves it; the batching sibling measured no perplexity change at q8_0 on Qwen3-1.7B), and a context no longer than you need.

macOS lets the GPU use 12.7 GB of this laptop's 16 GB (measured), and llama-server's --fit shrinks unset settings until the plan fits.

The Mac working set and llama-server's defaults (depth)

How much a Mac lets the GPU use. Metal reports a "recommended maximum working set", and llama.cpp sizes its plans to it (ggml-metal-device.m L1276, L1350). Measured here: 12.7 GB of 16 GB (74%). What llama-server does by default at b11146: -c 0 asks for the model's trained context, and --fit (on) shrinks unset settings until the plan fits with a 1,024 MiB margin (common/fit.h). Measured here, Qwen3-1.7B Q4_K_M with no options: ready in 5.6 s with 4 slots sharing one unified KV cache of 87,552 tokens (10.0 GB in F16), each slot capped at the model's trained 40,960 tokens. --fit started from 4 × 40,960 = 163,840 tokens (the trained context for every slot) and cut it to what fits the GPU's working set less its margin (common/fit.cpp L267 to L272, L393 to L430). A bare start on a small model claims most of the GPU's memory for cache; on a shared machine set -c yourself.

The Fit and speed tab does this arithmetic for any model and machine before you download anything (a Mac, a DGX Spark, one or two RTX 5090s).

When it does not fit

  • Partial offload. -ngl N puts only N layers on the GPU; the rest run on the CPU at the CPU's bandwidth. On a PC that is system RAM at tens of GB/s, many times below a GPU's; on a Mac the CPU shares the memory but pulls less of it (45.4 against 89.7 tokens per second, section 1).
  • Mixture-of-experts models read only a few experts per token, so keeping the experts in system RAM (--n-cpu-moe N or --cpu-moe) and attention and shared layers on the GPU costs less than offloading a dense model of the same size.
  • Memory-mapped files. llama.cpp maps the GGUF file (section 3), so a model larger than RAM still loads and its pages are read from disk as needed: a loading trick, not a way to run fast.

3. The file: what a model format holds, and what reading it costs

A model format is the agreement on how a model's named arrays, and the facts needed to use them, are written to disk. vLLM gets a folder of safetensors shards plus a config.json; a laptop gets one GGUF file or an MLX folder. Keep three layers apart:

1. Container

How bytes are laid out: where each tensor starts, what metadata travels with it, and whether reading the file can run code. safetensors, GGUF, pickle, ONNX's protobuf, flatbuffers.

2. Number encoding

How each number is stored: BF16, FP8, or a quantisation scheme such as GGUF's Q4_K or MLX's 4-bit affine groups (section 4). The container says which; the scheme says how to decode it.

3. Compiled artifact

A build output tied to one runtime and one kind of hardware: a TensorRT engine, a Core ML compiled model. Not something to distribute; something to rebuild.

GGUF fuses layers 1 and 2; safetensors owns only layer 1; a TensorRT engine is layer 3. Every claim below is read from real Qwen3-0.6B files; the File explorer tab walks three of them field by field.

Bytes on disk: order and size (depth)

A tensor on disk is its numbers in a row, row-major (last index fastest) and little-endian, plus its shape: bytes = (product of the shape) × (bytes per element), so k_proj.weight, BF16, [1024, 1024] is 2,097,152 bytes, exactly the gap between its two offsets in the real file.

dtypes. A float is a sign bit, an exponent (range) and a mantissa (precision). BF16 keeps F32's 8 exponent bits and cuts the mantissa to 7; F16 has 10 mantissa bits but only 5 exponent bits, so very small and very large numbers do not fit. Try a value:

What pickle is, in Python's own words, and the checkpoint disassembled (depth)

For years torch.save wrote Python's pickle format, and Hugging Face files named pytorch_model.bin are exactly that. A pickle is not data but a program for a small stack machine, and loading it runs the program. The machine reads one-byte opcodes; most push values, and two are the point: GLOBAL imports any module.name, and REDUCE pops a callable and an argument tuple and calls it. That is how a tensor is rebuilt (call torch._utils._rebuild_tensor_v2) and equally how a file can call os.system. Python's documentation: "The pickle module is not secure. Only unpickle data you trust. It is possible to construct malicious pickle data which will execute arbitrary code during unpickling" (pickle docs).

Since PyTorch 1.6 a .pt or .bin file is a zip (torch.save docs): a small data.pkl program plus one raw file per storage. What happened when they were loaded (depth)

Loading them run here: plain pickle.loads of the malicious bytes (in a child process) printed LOADING THIS FILE RAN print(): it could have been any function and returned normally; nothing looked wrong. torch.load with its default weights_only=True refused it before any call (the message is in the closed block below).

The rule
Treat a pickle checkpoint from anyone you do not trust as an executable. Prefer the safetensors files in the same repo; if only a .bin exists, convert it inside a throwaway sandbox (a container with no credentials and no network), never on your workstation. weights_only=True was itself bypassed before PyTorch 2.6 (below).
The refusal message, the mitigation that failed, the ones that hold, and real attacks (depth)
  • weights_only=True swaps the pickle machine for a restricted one that allows only an allowlist of globals (tensor rebuild functions, plain containers). PyTorch 2.6 made it the default on 2025-01-29, calling it a backward-compatibility-breaking change (PyTorch 2.6 blog).
  • It was bypassed. CVE-2025-32434 (published 2025-04-17/18, CVSS v4 9.3, critical): remote code execution through torch.load even with weights_only=True, in every PyTorch before 2.6.0. For years the recommended safe path was not safe.
  • Libraries now refuse. transformers 4.52.0 (2025-05-20) added check_torch_load_is_safe(): on PyTorch older than 2.6 it raises instead of loading a .bin, adding "This version restriction does not apply when loading files with safetensors" (source).
  • Real attacks exist. JFrog found "around 100" malicious models on the Hugging Face Hub, one opening a reverse shell (2024-02-27, JFrog). ReversingLabs' "nullifAI" (2025-02-06) found two models whose pickles were packed with 7z and deliberately broken after the payload, so the Hub's Picklescan missed them (ReversingLabs). The Hub lists each pickle's imports without executing it and says this "is not 100% foolproof" (Hub docs).
  • Not only PyTorch. Keras models could carry code in Lambda layers (CVE-2024-3660, fixed in Keras 2.13 with safe_mode), and CVE-2025-1550 ran code through load_model even with safe_mode=True (fixed in Keras 3.9.0).

safetensors: remove the program

safetensors removes the program: 8 bytes giving the header length, a JSON header (each tensor's dtype, shape and byte offsets), then the raw bytes back to back. Nothing in it can name a function, and each tensor is a slice of the file at a known place. It cannot say "this tensor is that one", so tied weights are stored twice: Qwen3-0.6B's lm_head duplicates its embedding, 20.7% of the file.

The layout, field by field (depth)

A safetensors file is three things in a row, and nothing in it can name a function (format spec):

  1. 8 bytes: an unsigned 64-bit little-endian integer N, the length of the header.
  2. N bytes of JSON: for every tensor its dtype, shape and data_offsets [begin, end) from the start of the data buffer, plus an optional __metadata__ map of strings to strings ("Arbitrary JSON is not allowed").
  3. The data buffer: every tensor's raw bytes, back to back. The spec forbids holes and overlaps, which also rules out "polyglot" files hiding a second payload.

The first bytes of the real Qwen3-0.6B model.safetensors (1,503,300,328 bytes): the first 8, read little-endian, give the header length, and the JSON starts right after.

The header measured, and what each tool does with the duplicate (depth)

The header is 35,552 bytes describing 311 tensors, 0.0024% of the file. A reader parses that JSON, and then each tensor is a slice of the file at a known place: no parsing, no conversion.

What it cannot say: tied weights are stored twice. Qwen3-0.6B's config says tie_word_embeddings: true (the input embedding and the output layer, lm_head, are one matrix), but safetensors cannot express an alias, so the released file stores both; the two byte ranges hash the same, measured here: 311,164,928 bytes (311.2 MB, 20.7% of the file) are a duplicate. Qwen3-1.7B does the same in its second shard (its index has 311 entries and the second shard holds exactly one tensor, lm_head.weight); Qwen3-4B's checkpoint does not. Downstream tools disagree: MLX's converter honours the tie and keeps one copy (310 tensors; Qwen3-1.7B is 3.44 GB in MLX bf16 against 4.06 GB as F16 GGUF), while llama.cpp's converter keeps both, as token_embd and output, which inflates small models' bits per weight (section 4).

Header limits, padding, shards, and the project's status (depth)

The Rust reference implementation refuses headers over 100 MB (MAX_HEADER_SIZE = 100_000_000, tensor.rs L10), so a hostile file cannot make you allocate gigabytes of JSON, and its writer pads the header with spaces to a multiple of 8 bytes so the buffer starts 8-byte aligned (the Qwen file's header ends in one space). MLX's writer does not pad: the MLX file's header is 78,252 bytes, 4 more than a multiple of 8, which the format allows.

Shards. Big checkpoints are split into model-00001-of-00002.safetensors and so on, with model.safetensors.index.json mapping every tensor name to its shard. transformers chooses the split when saving: max_shard_size defaulted to "5GB" in v4 and "50GB" from v5.0.0 (2026-01-26). The Hub recommends files under 200 GB and enforces 500 GB per file (Hub storage limits).

Status, October 2026. A Trail of Bits audit commissioned by Hugging Face with EleutherAI and Stability AI found "no critical security flaw leading to arbitrary code execution" (2023-05-23, HF blog). safetensors became a PyTorch Foundation project on 2026-04-08 (announcement) and moved to the github.com/safetensors organisation; the latest release is v0.8.0 (2026-06-09). Its dtypes run from F64 down to F8 (E4M3, E5M2, E8M0) and F4/F6 for microscaling formats.

GGUF: one file, everything in it

GGUF goes the other way: one file holding tensors, tokenizer, chat template and architecture numbers as typed metadata, every tensor aligned so the file can be mapped and used in place. Each tensor carries its own type, so "Q4_K_M" is a mix of types (section 4).

The layout, field by field (depth)

GGUF goes the other way: tensors, tokenizer, chat template and architecture numbers travel together, the last three as typed key/value metadata (gguf.md; llama.cpp's header sums it up in 30 lines, gguf.h L1-L30):

  1. Magic GGUF (bytes 47 47 55 46), version (u32, now 3), tensor count and key/value count (64-bit each).
  2. Key/value pairs: a key string (a u64 length, then the bytes), a value type (one of 13: integers, floats, bool, string, array), the value. Keys are namespaced: general.architecture, qwen3.attention.head_count, tokenizer.ggml.tokens.
  3. Tensor infos: each tensor's name, number of dimensions, dimensions, type, and offset into the data section.
  4. Padding to general.alignment (32 when absent), then the data section; every offset is a multiple of the alignment, so the file can be mapped and each tensor used in place.

MLX: safetensors with packed groups

An MLX model is safetensors plus a quantization block in config.json; each quantised layer becomes three tensors: packed 4-bit codes, and a BF16 scale and bias per group of 64 weights.

The config and the three tensors of one layer (depth)

An MLX model is a Hugging Face-style folder whose weights are safetensors and whose config.json says how they are quantised; mlx_lm convert -q wrote "quantization": { "group_size": 64, "bits": 4, "mode": "affine" } into Qwen3-0.6B's config (and mirrored it as quantization_config). What MLX adds is a layout: each quantised linear layer becomes three tensors, weight with the 4-bit codes packed eight to a 32-bit word (lowest bits first), and scales and biases with one BF16 scale s and offset b per group of 64 weights, each weight being s·q + b (mx.quantize). So the 4-bit file has 704 tensors where the BF16 one has 310; layer 0's key projection (1,024 × 1,024) becomes k_proj.weight U32 [1024, 128], k_proj.scales and k_proj.biases BF16 [1024, 16].

The same 256 weights, 144 bytes either way: GGUF keeps a block together, MLX spreads it over three tensors

Both cost 4.5 bits per weight; the difference is where the scales live, which shapes the kernels. Loading needs no copy to a GPU (unified memory); MLX does not use the Neural Engine (mlx issue #18, since 2023). Its other modes and its quality against GGUF: section 7.

The rules, with the runs behind them (depth)

  • Reproducible: the GGUF converter, llama-quantize and mlx_lm convert all gave byte-identical files on re-runs here, so a SHA-256 is a fair check that a file is what you think.

What mapping does (depth)

To memory-map a file is to make it appear as memory without reading it: nothing is copied until a byte is touched, then the OS brings in that 16 KiB page (on Apple silicon) from its page cache, the RAM it keeps recently read files in. Because safetensors and GGUF tensors sit at known offsets in their final layout, a loader can hand out slices of the mapping; a pickle must run its program first and, by default, copy every storage. 4. Quantisation from zero: what a GGUF type name means

Sections 1 and 2 say the same thing twice: fewer bytes per weight means more model in the same memory and more tokens per second. A trained model stores each weight as a 16-bit float; quantisation stores it as a small integer code plus a few shared numbers that turn codes back into values, at the cost of error. The general theory (number formats, quantisation-aware training, GPTQ and AWQ) is owned by Quantization and Precision; this section is the family local engines use, llama.cpp's GGUF types, and section 5 measures them.

The idea: a scale per small block

Take 32 consecutive weights of one row. Find a scale d so the codes cover the block's range, store d once (16 bits), and store each weight as the integer q nearest to w / d. The kernel computes d × q as it multiplies (it dequantises on the fly; the weights stay compressed in memory). The scale is per block because one scale for a whole matrix would waste the codes on a few outliers. Its cost is spread over the block: 16 bits over 32 weights is 0.5 bit per weight, so a 4-bit type with a 16-bit scale per 32 weights is 4.5 bits per weight.

Names like Q4_K_M are recipes, not types

A GGUF file mixes types: llama-quantize applies a recipe per tensor, the type in the name for most and more bits where errors hurt most. For Q4_K_M ("medium"), the value projection (attn_v) and the second feed-forward matrix (ffn_down) get Q6_K in the first eighth of the layers, the last eighth and every third layer between (the use_more_bits rule, src/llama-quant.cpp L434 to L436, L556 to L557, L612 to L617), and the output layer gets Q6_K. In the Qwen3-0.6B Q4_K_M file read in section 3, 168 tensors are Q4_K, 29 are Q6_K (the embedding, and attn_v and ffn_down in 14 of the 28 layers) and 113 small vectors stay F32: 5.24 bits per weight averaged over every value, not 4.

Why small models average more bits (depth)

On small models the label misleads further. Qwen3-1.7B's checkpoint stores its tied embedding twice (section 3), and llama.cpp keeps both copies as token_embd and output: 30.6% of the file's 2.03 billion values, which the quantiser keeps at higher precision. So on this model Q4_K_M averages 5.03 bits per weight, Q2_K 3.44 and IQ1_M 2.52 (tensor mix of the Q4_K_M file made here: Q4_K: 169 tensors, 75% of weights; Q6_K: 29 tensors, 25% of weights; F32: 113 tensors, 0% of weights). On a 70B model the embedding and output are about 3% of the weights, and the averages sit close to the names. Compare files by size, not by label.

_S and _L variants, and makers' own recipes (depth)

_S and _L shift the balance: Q4_K_S is mostly Q4_K but not uniformly (attn_v in the first 4 layers and ffn_down in the first eighth go to Q5_K, the output layer to Q6_K), and the only _L type in llama.cpp is Q3_K_L; Hub uploads that keep the embedding and output at Q8_0 under an "_L" name are their makers' recipes, not llama.cpp types (same file and lines; the Quantization and Precision page corrected an old claim that Q4_K_S "is uniformly Q4_K"). Bigger files on Hugging Face often carry a maker's own mix (Unsloth's "dynamic" quants, for example); the name then tells you only the base type. Never requantise a quantised file (Q8_0 to Q4_K_M stacks two roundings); always start from BF16 or F32.

Importance matrices: spend the error where it matters least

Plain quantisation picks each block's scale to minimise the error on the weights themselves, but a weight that multiplies a large activation matters more than one that multiplies a small one. An importance matrix records, for each input column of each matrix, the average squared activation over a calibration text; llama-quantize --imatrix then chooses scales (and lattice points) that minimise the error weighted by it (PR #4861, January 2024). It costs one pass of the full-precision model over the calibration text (here 128 chunks of 512 tokens of bartowski's calibration_datav3, about 2 minutes for Qwen3-1.7B on this laptop) and nothing at run time. The lowest types refuse to run without one: IQ1_S, IQ1_M, the IQ2 types and IQ3_XXS, plus Q2_K inside a Q2_K_S file (tensor_requires_imatrix, src/llama-quant.cpp L822 to L840).

Predict: you quantise the same model to Q4_K_M twice, once without an imatrix and once with one. How do the two files compare?
Same size and speed, better quality: the importance matrix changes which codes and scales are chosen, not how many bits are stored. On Qwen3-1.7B it cut Q4_K_M's KL divergence from 0.114 to 0.0603 (section 5).
A caveat on calibration text (depth)

A caveat: the calibration text shapes what is protected, so a code-heavy calibration helps code, and an imatrix built from English prose alone can score well on English perplexity while code, other languages and long-context use quietly degrade (practitioner guidance, no single source: evaluate on your own tasks). The text used here was checked to share no 60-character passage with the WikiText-2 test text used to score the files.

6. llama-server in depth

llama-server is llama.cpp's HTTP server (OpenAI- and Anthropic-compatible), read at build 11146 and run here on Qwen3-1.7B Q4_K_M.

What llama-server serves (depth)

llama-server is llama.cpp's HTTP server: one process, one model (or many in router mode), an OpenAI-compatible API (/v1/chat/completions, /v1/completions, embeddings, reranking), an Anthropic-compatible /v1/messages (PR #17570, November 2025), its own /completion, and a web UI. Everything below was read in the source at build 11146 and run on this laptop with Qwen3-1.7B Q4_K_M; the C++ page (Part 3) walks the code itself.

Slots: how one server serves several people

A slot is one conversation in progress: its tokens, its sampling settings and its share of the KV cache. -np N sets the number of slots, and every step all busy slots go through the model together (continuous batching: a slot joins or leaves the batch at any step, as in the parent's section 5); a request that finds every slot busy waits. -c is the total KV cache in tokens: with the default split KV each slot gets -c / N; with a unified KV (-kvu) all slots draw from one pool, so one long conversation can use most of it. Defaults at b11146: -np "auto" means 4 slots with a unified cache (tools/server/server.cpp L156 to L160). Measured here: with 4 slots and 8,192 tokens of cache, a 2,925-token prompt was refused by the split cache (2,048 per slot) and served by the unified one.

A request goes to the idle slot that already holds the longest shared prefix, so a returning conversation skips most of its prefill.

Which slot a request gets, and the prompt cache tier (depth)

Which slot a request gets (get_available_slot, server-context.cpp L1547 to L1655): among idle slots, the one whose cached tokens share the longest common prefix with the new prompt, if that prefix is more than 10% of the prompt (--slot-prompt-similarity, default 0.1); otherwise the least recently used. So a returning conversation lands on the slot that still holds its history and skips most of its prefill. A slot about to be overwritten is first saved to a host-memory prompt cache (--cache-ram, 8,192 MiB by default); the batching sibling measured that tier (113 to 421 ms to restore a 5,010-token prompt against 5.63 s to recompute it).

Two ways the cache is reused, and one way it is stretched

Prompt caching (cache_prompt, on by default): a new request keeps the cached tokens it shares as a prefix with the slot's previous prompt and computes only the rest (L3216 to L3225), like vLLM's prefix cache, per slot. But once one early token differs (an edited message, a tool result inserted in the middle, a document removed) everything after it is recomputed, even text still there. Cache reuse (--cache-reuse N, off by default) goes further: after the common prefix it scans the old cache for runs of at least N tokens that match the new prompt and moves them instead of recomputing them (L3226 to L3290), possible because a cached key can be re-rotated to a new position (RoPE positions are a rotation). It is approximate: the moved keys and values were computed attending to the old preceding text.

Context shift: how it works (depth)

Context shift (--context-shift, off by default at b11146) handles a conversation that outgrows its slot. Off: generation stops when the slot is full, and a longer prompt is refused ("exceeds the available context size", L3195 to L3215). On: when the slot fills, the server keeps the first n_keep tokens, discards half of the rest and shifts the remainder back (L2909 to L2970), so generation goes on while forgetting the middle. Fine for endless chat; wrong for anything that must see its whole input, and, like cache reuse, wrong for an evaluation that must match a fresh run.

Started without -m and with --models-dir, llama-server becomes a router: it lists the GGUF files, starts one child llama-server per model on demand, forwards each request by its "model" field, and at --models-max unloads the least recently used (router mode PR #17470, December 2025; LRU scheduling PR #26572, August 2026). 7. MLX and mlx-lm on Apple silicon

MLX is Apple's array framework (unified memory, lazy evaluation) and mlx-lm its language-model package; new architectures often reach it within days, and Ollama, LM Studio and Lily build on it for Macs.

What MLX is, and why it exists beside llama.cpp (depth)

MLX is Apple's open-source array framework for its own chips: NumPy-like arrays and automatic differentiation, with two design choices that matter for inference. Arrays live in unified memory, so CPU and GPU use the same bytes without copies; and evaluation is lazy: operations build a graph that runs only when a result is needed, which lets MLX fuse work and skip what is never used. mlx-lm is the language-model package on top: generation, a server, conversion and quantisation from Hugging Face checkpoints, and LoRA fine-tuning (MLX 0.32.3, mlx-lm 0.32.0 of 1 October 2026, PyPI). It exists beside llama.cpp because it is a framework researchers can read and change in Python (a model is a short Python file), so new architectures often appear in mlx-lm within days, and Ollama, LM Studio and Perplexity's Lily build on it for Macs.

Its quantisation is the per-group scale and bias laid out in section 3: by default 4-bit codes with a 16-bit scale and bias per 64 weights, w ≈ scale × q + bias, 4 + 32/64 = 4.5 bits per weight, the size of Q4_0 or Q4_K with an offset like Q4_1; group size, bit width and FP4 or FP8 modes are options (closed block below).

MLX's other quantisation modes (reference)

Other modes: mxfp4 (groups of 32 sharing an 8-bit power-of-two scale: 4.25 bits, since v0.29.0, 2025-08-29), nvfp4 (groups of 16 with an FP8 scale) and mxfp8 (both since v0.29.4, 2025-11-11; ops.cpp); affine allows 2 to 8 bits (and 1) with groups of 32, 64 or 128, and mixed recipes (--quant-predicate mixed_3_6: 3 bits for most layers, 6 for sensitive ones; mlx_lm/convert.py L20 to L80). mlx-lm also ships calibrated methods (awq, gptq, dwq distilled quantisation), not measured here.

Two cards: what a second GPU buys

Two 5090s give 64 GB. The default layer split adds memory but not single-user speed (the cards take turns); tensor split reads both halves at once and exchanges over PCIe; for throughput, run one replica per card.

Layer split against tensor split (depth)

Two 5090s give 64 GB; how the model is split decides whether they also give speed. With layer split (llama.cpp's default, -sm layer: the first half of the layers on one card, the second half on the other) a token passes through card 1 then card 2: the memory adds up, the bandwidth for one user does not, because the cards take turns. With tensor split (every matrix cut in two, both cards read their halves at once and exchange partial results over PCIe) one user's token is read at up to twice the bandwidth, minus the exchange; Distributed and disaggregated serving explains these splits from zero. For throughput with a model that fits one card, run one replica per card.

GeForce cards cannot talk to each other directly

NVIDIA does not support peer-to-peer (P2P) transfers between GeForce cards: "RTX 50-series are Geforce GPU series, and p2p is not supported" (NVIDIA developer forum, 13 March 2025). Tensor parallelism therefore exchanges data through host memory: vLLM v0.31.0 detects this, disables its custom all-reduce ("your platform lacks GPU P2P capability or P2P test failed") and falls back to NCCL (custom_all_reduce.py).

10. Very low bits: ternary and 1-bit models

Ternary weights (−1, 0, +1) need log23 ≈ 1.585 bits each, but rounding a normally trained model that far breaks it: Qwen3-1.7B at IQ1_M reached perplexity 89.01 against 15.34 (measured here). Such models must be trained ternary and stored in formats built for it.

What rounding does, measured (depth)

If weights could be only −1, 0 or +1 (ternary), each would need log23 each would need log23 = 1.58 bitsasymp; 1.585 bits, a 70B model would fit in about 14 GB, and multiplication would become addition and subtraction. You cannot get there by rounding a normally trained model. Measured here on Qwen3-1.7B: at IQ2_M with an importance matrix (3.24 bits per weight) perplexity rose from 15.34 to 21.57; at IQ1_M (2.52 bits) to 89.01; llama.cpp's binary Q1_0 type (one scale per 128 weights and a sign bit each, 1.125 bits; the file averages 1.96 bits with its embeddings kept at higher precision) gave 393,471, no longer a language model. Bigger models fall less far (llama-quantize's help gives +3.5 perplexity at Q2_K for Llama-3-8B, against +172.81 here), but no normally trained model survives 1 or 2 bits. The working route is to train the model ternary from the start, or retrain it heavily, and store it in a format built for it.

Packing is a format question. GGUF's TQ1_0 packs mostly five ternary weights per byte (35 = 243 fits in 256) plus an F16 scale per 256 weights, 1.6875 bits per weight; TQ2_0 spends 2.0625 (2 bits each, faster to unpack). BITCOS notes that ternary models are up to 51.5% zeros, so storing a bitmap of the non-zero weights plus their signs costs 2 − z bits (z the zero share), down to 1.485. Same model, different bytes.

Reading "N-bit model at M tokens per second" claims

Ask four questions: was the model trained or retrained for that precision (if not, expect the cliff above); which benchmark gives the "98%" and against which baseline; what batch size, context and hardware produced the speed (decode at batch 1 on short context is the flattering case, section 1); and does stock software run it. The 1.58-bit idea is sound; the products are young.

11. Phones, the browser, and on-device formats

A phone is the same problem with a smaller budget: a few GB of memory shared with everything else, less bandwidth than a laptop (Apple publishes 120 GB/s for the base M4 chip and no iPhone figures), a battery and a thermal limit, and usually an NPU (a neural processing unit: fixed-function matrix hardware that runs integer and low-precision maths efficiently, if the model was compiled for it). Depth: common mistakes and interview rehearsal

Common mistakes, each with the section that shows it (depth)
  • Judging a quant by its name. Q4_K_M is a recipe, and on small models the embeddings dominate: on Qwen3-1.7B "Q2_K" averages 3.44 bits per weight, and the Qwen3-0.6B Q4_K_M file 5.24, while Q4_K itself is 4.5. Compare files by size and a measured KLD (section 4).
  • Ranking quants by perplexity alone. Perplexity on one text moves by luck and can even improve after quantisation; KLD against the full-precision model, and its 99th percentile, show the drift users feel (section 5).
  • Downloading a low-bit GGUF made without an importance matrix. At 3 bits and below it is the difference between usable and broken: Q2_K's KLD on Qwen3-1.7B was 2.702 without one and 0.547 with one, same size.
  • Requantising a quantised file. Q8_0 to Q4_K_M stacks two roundings. Quantise from the BF16 or F32 original (section 3).
  • "Converting to F16 GGUF is lossless." From a BF16 checkpoint it changed 120,378 values of Qwen3-0.6B. Use --outtype bf16 (or f32) for a lossless master.
  • Trusting a GGUF's chat template because the file is self-contained. It is whatever the uploader wrote: the Unsloth file in the store has a rewritten template and one fewer stop id than the original repo.
  • Reading GGUF shapes like PyTorch shapes. GGUF lists dimensions fastest-first: [1024, 151936] is PyTorch's [151936, 1024].
  • "weights_only=True makes torch.load safe." It was bypassed before PyTorch 2.6 (CVE-2025-32434), and it is still an allowlist inside a pickle interpreter. Prefer safetensors; keep PyTorch current.
  • Expecting a 4-bit file to stream 4 times faster than F16. On a GPU with little arithmetic unpacking costs time: Q4_K_M streamed 2.21 times faster than F16 on this laptop, not 3.2 times (section 1).
  • Forgetting the KV cache when sizing. A full 40,960-token context of Qwen3-4B needs 6.0 GB of F16 cache, more than twice its Q4_K_M weights (section 2).
  • Leaving Ollama at its default context. Under 24 GiB of VRAM it uses 4,096 tokens; a longer prompt is cut without an error. Set num_ctx or OLLAMA_CONTEXT_LENGTH (section 8).
  • Splitting a model across two GPUs and expecting it to be faster. The default layer split adds memory, not single-user speed. For one user use tensor split; for throughput, one replica per card (section 9).
  • Turning on --cache-reuse or --context-shift without knowing they are approximate. Both reuse keys and values computed with different preceding text (section 6).
  • Running mlx_lm.server for a team. Its own docs say not for production, and it ran out of Metal memory under load here (section 7).
  • Measuring load time with a warm cache and calling it cold start. The second load reads from RAM; cold loads are disk-bound (section 3).
  • Exporting an LLM to ONNX and expecting a chat server. A plain export has no KV cache, sampling or batching (section 3).
  • Shipping a TensorRT plan as "the model". It is tied to the GPU type and TensorRT version; ship safetensors and build plans in CI.
  • Believing a headline tokens-per-second figure. Ask for the batch size, context length, hardware, quantisation and who measured it; vendor "up to" numbers and model-card tables differed by about 10% for Bonsai (section 10).
Interview rehearsal (optional)

A 70B model on two 24 GB GPUs: how do you run it, and how fast? At about 4.8 bits it is about 43 GB: it fits across 48 GB with a little room for the cache. Layer split: one user gets about one card's bandwidth, a ceiling of about 1,000 / 43 = 23 tokens per second on 4090s, less in practice. Tensor split adds speed at the cost of PCIe traffic (no P2P on GeForce). Or drop to 3 bits with an imatrix and accept the quality cost.

An RTX 5090 on a 3.8 GB model: the speed limit? 1,792 / 3.83 = 468 tokens per second; measured 300.

A model's file is 20% bigger than parameters × 2 bytes. Where would you look? Duplicated tied tensors (Qwen3-0.6B's lm_head), F32 tensors, or extra heads; list the header and compare byte ranges.

Two Q4 formats both cost 4.5 bits per weight. What can still differ? Group size, whether there is an offset, scale precision, and where scales live in the file (GGUF interleaves them per block; MLX keeps separate tensors), which affects quality and kernel design.

Why does Apple silicon run large models that a gaming GPU cannot? Unified memory: up to 512 GB the GPU can address, against 32 GB on an RTX 5090; but bandwidth is lower (200 to 1,200 GB/s against 1,792) and prompt reading much slower. Big models fit; they stream more slowly and read prompts much more slowly.

Why don't vLLM and SGLang serve ONNX, and is a TensorRT engine portable? Their speed comes from a paged KV cache, custom attention kernels and per-step scheduling, which a static graph does not express. A TensorRT engine is portable by default only to the same GPU type and TensorRT version; hardware and version compatibility modes (since 8.6) widen that at some cost.

Is a 1.58-bit model just a 16-bit model rounded hard? No: rounding a normally trained model to 2 bits or below breaks it (Q1_0 perplexity 393,471 here); ternary models are trained or retrained for it and need kernels that store and unpack them (TQ1_0/TQ2_0, bitnet.cpp).
