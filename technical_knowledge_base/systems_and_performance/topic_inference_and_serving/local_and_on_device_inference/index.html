Local inference means running a language model on a machine you own (a laptop, a desktop with one or two gaming GPUs, a phone) for yourself or a handful of people. The datacenter pages ask how to serve thousands of users per GPU at the lowest cost. Here the questions flip: does the model fit in my memory, how fast does it stream for me, how much quality did shrinking it cost, and which program should run it?

The parent page, Topic: inference-and-serving, explains prefill, decode and the KV cache from zero; this page uses those words. In one line each: prefill reads the whole prompt in one pass; decode then produces one token per pass; the KV cache holds the keys and values every earlier token produced, so decode does not recompute them; TTFT (time to first token) is how long you wait before text appears, and tokens per second (or its inverse, TPOT, time per output token) is how fast it streams after that.

1. How fast it streams
bytes per token / bandwidth

With one user, every token reads all the weights once. Speed is set by memory bandwidth, not by arithmetic (section 1).

2. Whether it fits
weights + KV cache + buffers

The weights must sit in memory the GPU can read fast: VRAM on a graphics card, unified memory on a Mac (section 2).

3. What shrinking costs
quantization

Storing weights in 4 bits instead of 16 makes the model 3 to 4 times smaller, faster (by less than that on a small GPU, section 1), and a little worse. How much worse is measurable (sections 3 and 4).

4. Which program
llama.cpp, MLX, Ollama, LM Studio

All four sit on two engines: ggml (llama.cpp) and MLX. The wrappers add model management and hide knobs (sections 5 to 7).

1. One user's speed is set by memory bandwidth

The problem. To generate one token, the model multiplies the newest token's vector by every weight matrix it has. Each weight is read from memory once and used for one multiply and one add. With one user there is one token per step, so a step does 2 operations per weight read: the arithmetic units wait for memory almost all the time (the parent's section 1 explains this from zero; Performance math counts it). So:

tokens per second ≤ bandwidth / bytes read per token
bandwidth
how many bytes per second the memory holding the weights delivers (Apple: 200 GB/s for this M1 Pro)
bytes read per token
the weights the token passes through (all of them for a dense model, only the routed experts for a mixture of experts) plus the KV cache read so far

For Qwen3-1.7B in F16, the weights are GB, so the ceiling on this laptop is 200 / = tokens per second. Measured here: , which means memory was read at GB/s, of Apple's figure. Quantization (section 3) shrinks the bytes and should raise the ceiling in proportion:

The 4-bit file is not limited by memory any more: unpacking each 4-bit code with its 6-bit sub-block scale and minimum costs arithmetic, and this laptop's GPU (about 5 TFLOP/s, no matrix units) runs out of arithmetic first. So the bandwidth rule is a ceiling, reached by formats that are cheap to unpack and approached less closely by complex ones on a small GPU. On a GPU with far more arithmetic per byte (an RTX 5090 has about 40 times this laptop's FP16 throughput for 9 times its bandwidth) small formats come much closer to the line: 64% of peak for Q4_0 on the published scoreboard (section 8). The rule still decides the big choices: a model twice as large streams about half as fast on the same machine, and a machine with twice the bandwidth streams about twice as fast.

The context adds bytes too

Each new token also reads the KV cache of every earlier token. Qwen3-1.7B keeps 114,688 bytes per token (2 for K and V × 28 layers × 8 KV heads × 128 dimensions × 2 bytes), so at 16,000 tokens of context a token reads GB of cache besides its GB of Q4_K_M weights: the cache read is the larger part. The parent's Engine bench measured this on Qwen3-0.6B: generation fell from 198 to 56 tokens per second between an empty context and 16K. Long-context local work (agents with big histories, whole documents) is slower than a short chat on the same model, and a quantized KV cache (q8_0) helps speed as well as memory.

Reading the prompt is a different problem

Prefill reads the weights once for all the prompt's tokens, so it does hundreds of operations per byte and is limited by arithmetic. Measured here: Qwen3-1.7B F16 reads a 512-token prompt at tokens per second, about TFLOP/s of useful arithmetic (2 operations × 1.41 billion multiplied weights per token: the embedding table is looked up, not multiplied, and llama-bench computes the output layer only for the last token, src/llama-batch.cpp L121 to L125), against a peak of about 5.3 for this GPU (Topic: hardware). That is times faster per token than generating. But it is the laptop's weak point: a 30,000-token agent history or document costs seconds before the first token on Qwen3-1.7B at Q4_K_M, at the measured rate (and longer in practice, since attention grows with the prompt). A datacenter GPU does the same in a fraction of a second. On a Mac, prompt length is what you feel.

CPU or GPU on the same chip

On Apple silicon the CPU and GPU share the same memory, so they see the same 200 GB/s in principle; in practice the CPU cores cannot pull that much. What transfers to datacenter GPUs, and what does not

The rule is the same everywhere: one user's decode speed is bandwidth over bytes, and the parent's Capacity planner uses exactly this step model for an H200. What does not transfer: the arithmetic shortfall on small formats (a GPU with tensor cores unpacks 4-bit blocks with time to spare), and the slow prefill (an H200's 1,979 FP8 TFLOP/s, the parent's figure, is about 370 times this GPU's 5.3). And a datacenter never runs one user: batching shares each read of the weights across many users, which is the whole point of the parent page. How to check it on your machine: llama-bench -m model.gguf -p 512 -n 128, then divide file size by the tg time per token.

2. Will it fit? Weights, cache and buffers

The problem. The model must sit in memory the GPU reads fast. On a graphics card that is its own VRAM (32 GB on an RTX 5090); on a Mac it is the unified memory the CPU and GPU share, but macOS lets the GPU use only part of it. Three things need room:

memory ≈ weights + KV cache + buffers
weights
parameters × bits per weight / 8 (Qwen3-4B at Q4_K_M: 4.02 billion parameters × bits measured, about 2.5 GB)
KV cache
bytes per token × context × slots: 2 × layers × KV heads × head size × bytes per value
buffers
scratch memory for one step's activations, a few hundred MB for small models (llama.cpp prints its compute buffer at start)

The cache can outweigh the model. Qwen3-4B keeps 2 × 36 layers × 8 KV heads × 128 × 2 bytes = 147,456 bytes per token in F16. Its trained context is 40,960 tokens: a full context costs 6.0 GB of cache, more than twice the 2.5 GB of Q4_K_M weights. Long contexts are paid in memory first and speed second (section 1). Two remedies: a quantized cache (-ctk q8_0 -ctv q8_0 halves it; the batching sibling measured no perplexity change at q8_0 on Qwen3-1.7B), and a context no longer than you need.

When it does not fit

  • Partial offload. -ngl N puts only N layers on the GPU; the rest run on the CPU from system RAM. It runs, at the speed of the slowest part: on a PC the CPU's RAM bandwidth (tens of GB/s on a desktop) is many times below a GPU's, so each CPU layer costs far more than a GPU layer. On a Mac the CPU shares the same memory, but its cores pull less of it (section 1 measured the CPU at tokens per second against the GPU's ).
  • Mixture-of-experts models read only a few experts per token, so keeping the experts in system RAM (--n-cpu-moe N or --cpu-moe) and the attention and shared layers on the GPU costs less than offloading a dense model of the same size.
  • Memory-mapped files. llama.cpp maps the GGUF file into memory (mmap) instead of reading it, so a model that does not fit in RAM still loads, and its pages are read from disk as needed: a loading trick, not a way to run fast. A second start of the same model is quicker because the file is still in the operating system's page cache (the router run in section 5 shows the effect).
How to check

Start the server and read its first lines: llama.cpp prints the model buffer, KV buffer and compute buffer sizes per device and the context it chose. On a Mac, Activity Monitor's memory pressure shows when the system starts swapping. The Fit and speed tab does this arithmetic for any model and machine before you download anything.

3. Quantization from zero: what a GGUF type name means

The problem. Sections 1 and 2 say the same thing twice: fewer bytes per weight means more model in the same memory and more tokens per second. A trained model stores each weight as a 16-bit float (BF16 or F16). Quantization stores it in fewer bits, as a small integer code plus some shared numbers to turn codes back into values. The cost is error: the stored value is no longer exactly the trained one. The parent's Quantization and Precision page owns the general theory (number formats, quantization-aware training, GPTQ and AWQ); this section covers the family local engines use, llama.cpp's GGUF types, and section 4 measures them.

The idea: a scale per small block

Take 32 consecutive weights of one row. Find a scale d so that the codes cover the block's range, store d once (16 bits), and store each weight as the integer q nearest to w / d. Reading back, the kernel computes d × q as it multiplies (it dequantizes on the fly; the weights stay compressed in memory). The scale is per block because weights vary: one scale for a whole matrix would waste the codes on a few outliers. The cost of the scale is spread over the block: 16 bits over 32 weights is 0.5 bit per weight, so a 4-bit type with a 16-bit scale per 32 weights is 4.5 bits per weight (bpw), the number that sets file size and decode speed.

Names like Q4_K_M are recipes, not types

A GGUF file mixes types. llama-quantize applies a recipe per tensor: the type in the name for most tensors, more bits where errors hurt most. For Q4_K_M ("medium"), the value projection (attn_v) and the second feed-forward matrix (ffn_down) get Q6_K in the first eighth of the layers, the last eighth and every third layer between (the use_more_bits rule, src/llama-quant.cpp L434 to L436, L556 to L557, L612 to L617), and the output layer gets Q6_K. _S and _L variants shift that balance. Importance matrices (imatrix): spend the error where it matters least

Plain quantization picks each block's scale to minimise the error on the weights themselves. But a weight that multiplies a large activation matters more than one that multiplies a small one. An importance matrix records, for each input column of each matrix, the average squared activation seen while running the model over a calibration text. llama-quantize --imatrix then chooses scales (and lattice points) that minimise the error weighted by that importance (PR #4861, January 2024). It costs one pass of the full-precision model over the calibration text (here 128 chunks of 512 tokens of bartowski's calibration_datav3, about 2 minutes for Qwen3-1.7B on this laptop) and nothing at run time: the file is the same size. The lowest types refuse to run without one: IQ1_S, IQ1_M, the IQ2 types and IQ3_XXS, plus Q2_K inside a Q2_K_S file (tensor_requires_imatrix, src/llama-quant.cpp L822 to L840). A caveat: the calibration text shapes what is protected, so a code-heavy calibration helps code; the text used here was checked to share no 60-character passage with the WikiText-2 test text used to score the files.

How quality was measured. 5. llama-server in depth

llama-server is llama.cpp's HTTP server: one process, one model (or many in router mode), an OpenAI-compatible API (/v1/chat/completions, /v1/completions, embeddings, reranking), an Anthropic-compatible /v1/messages (PR #17570, November 2025), its own /completion, and a web UI. Everything below was read in the source at build 11146 and run on this laptop with Qwen3-1.7B Q4_K_M. The C++ page (Part 3) walks the code itself; this section is about running it.

Slots: how one server serves several people

A slot is one conversation in progress: its tokens, its sampling settings and its share of the KV cache. -np N sets the number of slots; every step, all busy slots go through the model together (continuous batching, on by default: a slot joins or leaves the batch at any step, as in the parent's section 3). A request that finds every slot busy waits. The context -c is the total KV cache in tokens: with the default split KV each slot gets -c / N; with a unified KV (-kvu) all slots draw from one pool, so one long conversation can use most of it. Defaults at b11146: -np is "auto", which means 4 slots with a unified KV cache (tools/server/server.cpp L156 to L160); -c 0 takes the model's trained context, and --fit (on) then shrinks unset settings until the model and cache fit the device with a 1,024 MiB margin (common/fit.h).

Which slot a request gets (get_available_slot, server-context.cpp L1547 to L1655): among idle slots, the one whose cached tokens share the longest common prefix with the new prompt, if that prefix is more than 10% of the prompt (--slot-prompt-similarity, default 0.1); otherwise the least recently used idle slot. So a returning conversation lands back on the slot that still holds its history and skips most of its prefill. When a slot is about to be overwritten, its cache is first saved to a host-memory prompt cache (--cache-ram, 8,192 MiB by default) so it can be restored later; the batching sibling measured that tier (113 to 421 ms to restore a 5,010-token prompt against 5.63 s to recompute it).

Two ways the cache is reused, and one way it is stretched

Prompt caching (cache_prompt, on by default): a new request in a slot keeps the cached tokens it shares as a prefix with the slot's previous prompt and computes only the rest (L3216 to L3225). This is the same idea as vLLM's prefix cache, per slot. But the moment one early token differs (an edited message, a tool result inserted in the middle, a document removed) everything after it is recomputed, even text that is still there.

Cache reuse (--cache-reuse N, off by default) goes further: after the common prefix, it scans the old cache for runs of at least N tokens that match the new prompt and moves them to their new positions instead of recomputing them (L3226 to L3290). Moving is possible because llama.cpp can re-rotate cached keys to a new position (RoPE positions are a rotation, so shifting a key is one more rotation). It is approximate: the moved keys and values were computed while attending to the old preceding text, not the new one. The animation runs the same edit both ways.

Context shift (--context-shift, off by default at b11146) handles a conversation that outgrows its slot. Off: generation stops when the slot is full, and a prompt longer than the slot is refused ("exceeds the available context size", L3195 to L3215). On: when the slot fills, the server keeps the first n_keep tokens, discards half of the rest and shifts the remainder back (L2909 to L2970), so generation can go on forever while forgetting the middle. Useful for endless chat; wrong for anything that must see its whole input.

6. MLX and mlx-lm on Apple silicon

MLX is Apple's array framework for its own chips (open source, from Apple's machine learning research team): NumPy-like arrays, automatic differentiation, and two design choices that matter for inference. Arrays live in unified memory, so the CPU and GPU use the same bytes without copies; and evaluation is lazy: operations build a graph that runs only when a result is needed, which lets MLX fuse work and skip what is never used. mlx-lm is the language-model package on top: generation, a server, conversion and quantization from Hugging Face checkpoints, and LoRA fine-tuning. Versions here: MLX 0.32.3, mlx-lm 0.32.0 (1 October 2026, PyPI).

Why it exists next to llama.cpp. llama.cpp is a C++ engine for every platform; MLX is a framework, written for Apple's GPU, that researchers can read and change in Python (a model in mlx-lm is a short Python file). New architectures often appear in mlx-lm within days, and Ollama, LM Studio and Perplexity's Lily all build on MLX for Macs (section 7).

MLX's quantization: a scale and a bias per group

MLX's default affine quantization stores, per group of 64 consecutive weights, a 16-bit scale and a 16-bit bias, and each weight as a 4-bit code: w ≈ scale × q + bias. That is 4 + 32/64 = 4.5 bits per weight, the same as Q4_0 or Q4_K, with an offset like Q4_1. Other modes: mxfp4 (groups of 32 sharing an 8-bit power-of-two scale: 4.25 bits), nvfp4 (groups of 16 with an FP8 scale) and mxfp8 (MLX v0.32.3 mx.quantize, ops.cpp); group size 32 or 128 and 2 to 8 bits; and mixed recipes (--quant-predicate mixed_3_6: 3 bits for most layers, 6 for sensitive ones; mlx_lm/convert.py L20 to L80). mlx-lm also ships calibrated methods (awq, gptq, dwq distilled quantization), not measured here.

7. Ollama and LM Studio: what the wrappers add

The problem they solve. llama-server is one process for one model, started with flags you have to know. Most people want to type a model name and chat, have several models available, and not think about which GGUF file, context length or GPU layers. Ollama and LM Studio do that: they manage downloads, start and stop engines on demand, and pick defaults. The cost is that the defaults are theirs.

Two cards: what a second GPU buys

Two 5090s give 64 GB. How the model is split decides whether they also give speed. With layer split (llama.cpp's default, -sm layer: the first half of the layers on one card, the second half on the other) a token passes through card 1 then card 2, each reading its half: the memory adds up, the bandwidth for one user does not, because the cards take turns. With tensor split (tensor parallelism: every matrix cut in two, both cards read their halves at the same time, then exchange partial results over PCIe) one user's token is read at up to twice the bandwidth, minus the exchange. The Distributed and disaggregated serving sibling explains these splits from zero; here is what is published for consumer cards:

  • Layer split, one user. Ollama on two 5090s: Llama 3.3 70B at 4 bits, 26.85 tokens per second; DeepSeek-R1 70B 27.03; Qwen2.5 72B 24.15 (hosting vendor's measurement, DatabaseMart, Ollama 0.6.5). The bandwidth rule for a 70B model at about 4.8 bits (about 43 GB, one card's bandwidth): 1,792 / 43 = 42 tokens per second ceiling, so 27 is 64% of it, the same efficiency as one card.
  • Tensor split in llama.cpp (-sm tensor, experimental, merged 9 April 2026): on two RTX 4090s, Llama 8B F16 generation went from 60.28 to 96.63 tokens per second (1.60 times) while prompt reading fell to 0.76 times; four 4090s took Llama 70B Q4_K_M from 21.25 to 48.31. Marked "not yet production ready" at merge, CUDA only for the fast path, needs flash attention (maintainer's numbers, PR #19378).
  • Many users, vLLM. One 5090 serving Qwen3-Coder-30B-A3B (AWQ 4-bit) to 400 concurrent requests: 4,570 output tokens per second in total; two 5090s serving Llama 3.3 70B AWQ with pipeline parallelism: 1,230 (independent, CloudRift, 9 October 2025). GeForce cards cannot talk to each other directly

NVIDIA does not support peer-to-peer (P2P) transfers between GeForce cards: "RTX 50-series are Geforce GPU series, and p2p is not supported" (NVIDIA developer forum, 13 March 2025). Tensor parallelism therefore exchanges data through host memory. vLLM v0.31.0 detects this, disables its custom all-reduce ("your platform lacks GPU P2P capability or P2P test failed") and falls back to NCCL (custom_all_reduce.py). Community-patched kernel modules re-enable P2P (tinygrad, for the 4090; aikitoria's fork, for the 30, 40 and 50 series): unsupported, at your own risk. On desktop CPUs two cards also share the CPU's lanes: a Ryzen 9 9950X has 24 usable PCIe 5.0 lanes and a Core Ultra 9 285K allows "2x8+2x4", so two GPUs run at x8 each, about 32 GB/s per direction (AMD, Intel).

9. Very low bits: ternary and 1-bit models

The idea. If a model's weights could be only −1, 0 or +1 (ternary), each weight would need log23 = 1.58 bits, a 70B model would fit in about 14 GB, and multiplication would become addition and subtraction. The catch is that you cannot get there by rounding a normally trained model: section 4 shows what that does even at 2 bits. The working route is to train the model ternary (or nearly so) from the start, or to retrain it heavily, so it learns weights that survive.

Common mistakes

Judging a quant by its name
Q4_K_M is a recipe, not a type, and on small models the embeddings dominate: on Qwen3-1.7B "Q2_K" averages bits per weight. Compare files by size and by a measured KLD, not by the label (section 3).
Ranking quants by perplexity alone
Perplexity on one text moves by luck and can even improve after quantization. KL divergence against the full-precision model, and its 99th percentile, show the drift that users feel (section 4).
Downloading a low-bit GGUF made without an importance matrix
At 3 bits and below it is the difference between usable and broken: Q2_K's KLD on Qwen3-1.7B was without one and with one, same size.
Expecting a 4-bit file to stream 4 times faster than F16
On a GPU with little arithmetic (any Mac here) unpacking costs time: Q4_K_M streamed times faster than F16 on this laptop, not 3.2 times. Check with llama-bench (section 1).
Forgetting the KV cache when sizing
A full 40,960-token context of Qwen3-4B needs 6.0 GB of F16 cache, more than twice its Q4_K_M weights. Size for the context you need, and use a q8_0 cache (section 2).
Leaving Ollama at its default context
Under 24 GiB of VRAM Ollama uses 4,096 tokens; a longer prompt is cut without an error. Set num_ctx or OLLAMA_CONTEXT_LENGTH (section 7).
Splitting a model across two GPUs and expecting it to be faster
The default layer split adds memory, not single-user speed: the cards take turns. For speed with one user use tensor split (experimental in llama.cpp, standard in vLLM); for throughput run one replica per card (section 8).
Turning on --cache-reuse or --context-shift without knowing they are approximate
Both reuse keys and values computed with different preceding text. Fine for chat, wrong for an evaluation or anything that must match a fresh run (section 5).
Running mlx_lm.server for a team
It batches, but its own docs say it is not for production, and it ran out of Metal memory under load on this laptop. Use llama-server, or vLLM on a GPU box (section 6).
Believing a headline tokens-per-second figure
Ask for the batch size, context length, hardware, quantization and who measured it. Vendor "up to" numbers and model-card tables can differ by 10% for the same model (Bonsai, section 9).

Interview questions

Why is single-user generation memory-bound, and what is its speed limit?
Each token passes every weight once and does two operations per weight read, far below any GPU's operations-per-byte ratio. So tokens per second ≤ bandwidth / bytes read per token (weights plus KV cache). An RTX 5090 (1,792 GB/s) on a 3.8 GB model: under 470 tokens per second; measured 300.
What does Q4_K_M mean?
K-quant, 4-bit base type: 256-weight super-blocks of 8 sub-blocks, each sub-block with a 6-bit scale and minimum, one 16-bit scale for those per super-block (4.5 bits per weight); "M" is the recipe that keeps attn_v and ffn_down in Q6_K for some layers and the output layer in Q6_K. About 4.8 to 5 bits per weight on average, depending on the model.
What is an importance matrix and why does it help?
Per input column of each matrix, the mean squared activation over a calibration text. Quantizing to minimise error weighted by it protects the weights that multiply large activations. Same file size, much lower KL divergence, especially at 2 to 3 bits.
How would you measure the quality loss of a quantized model?
KL divergence of its next-token distribution from the full-precision model's on held-out text (mean and high percentiles), same-top-token rate, then task benchmarks for the use case. Perplexity alone is noisy. Keep the calibration text apart from the evaluation text.
A 70B model on two 24 GB GPUs: how do you run it, and how fast?
At about 4.8 bits it is about 43 GB: it fits across 48 GB with a little room for the cache. Layer split: one user gets about one card's bandwidth, ceiling about 1,000 / 43 = 23 tokens per second on 4090s, less in practice. Tensor split adds speed at the cost of PCIe traffic (no P2P on GeForce). Or drop to 3 bits with an imatrix and accept the quality cost.
Why does Apple silicon run large models that a gaming GPU cannot?
Unified memory: up to 512 GB the GPU can address, against 32 GB of VRAM on an RTX 5090. But bandwidth is lower (200 to 1,200 GB/s against 1,792), and prompt processing much slower (far less matrix arithmetic). Big models fit; they stream more slowly and read prompts much more slowly.
What does llama-server's slot do, and how does it pick one?
A slot is one conversation's state and KV share; all busy slots decode together each step (continuous batching). A request goes to the idle slot with the longest common prefix if it covers more than 10% of the prompt, else the least recently used; old slot caches are saved to a host-memory prompt cache.
Prefix caching against --cache-reuse?
Prefix caching keeps the cached tokens that match from the start, exactly. Cache reuse also moves matching chunks after the first difference to their new positions (re-rotating their keys), so an edited conversation skips most of its prefill, at the cost of approximation: those keys and values saw different earlier text.
Ollama, llama.cpp, MLX, vLLM: when each?
Ollama or LM Studio for convenience; llama-server for control, metrics and the newest features; MLX on a Mac for speed on supported models and for working in Python; vLLM once several users or agents run concurrently on a GPU box.
Is a 1.58-bit model just a 16-bit model rounded hard?
No. Rounding a normally trained model to 2 bits or below breaks it (measured: Q1_0 perplexity ). Ternary models are trained or retrained for ternary weights, and need kernels that store and unpack them (TQ1_0/TQ2_0, bitnet.cpp).

Measured here, Apple M1 Pro, ; the load average during each run is in the table.

Three quality measures. Perplexity (PPL) is exp of the average negative log-probability the model gives the true next token: lower is better, but quantization noise can lower it by luck on one text. KL divergence (KLD) compares the whole next-token distribution of the quantized model with the F16 model's, token by token: it is 0 only if they agree exactly, and it is what llama.cpp's own tool reports for comparing a quantized file with its source (llama-perplexity --kl-divergence). Same top token is how often both models' most likely next token is the same: what greedy decoding would see.

Fit and speed: will a model fit, and how fast will it stream?

The arithmetic of sections 1 and 2, for any model and machine. Memory = weights + KV cache + a margin; generation speed ≈ efficiency × bandwidth / bytes read per token. Model shapes come from the released config.json files through the parent's Capacity planner model (the same functions, imported unchanged); bits per weight are the averages measured in the Quant ladder tab (embeddings and the quantizer's mix included); bandwidths are the makers' figures. Derived: an estimate, checked against this laptop's measurements where they exist.

Does the rule match what was measured here?

Not modelled: prompt reading time on machines without a calibration point, speculative decoding, the extra memory a long prompt's processing buffers need, and partial offload to the CPU (section 2). The usable share of a Mac's memory is what Metal reports as its recommended working set; it was measured only on this 16 GB laptop, and the same share is assumed for other Macs.
