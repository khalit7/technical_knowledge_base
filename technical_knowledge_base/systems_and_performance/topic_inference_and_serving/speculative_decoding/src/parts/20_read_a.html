In one screen

A large model generating text spends most of each step reading its weights, not doing arithmetic. Speculative decoding lets a cheap drafter guess the next few tokens and has the large target model check all the guesses in one forward pass, keeping the ones it agrees with. A probabilistic acceptance rule makes the result exactly what the target alone would have produced, only sooner.

Why it can work

On this laptop one Qwen3-4B forward pass over 5 tokens took times as long as a pass over 1 token, not 5 times measured here. Checking guesses is cheap while the chip waits on memory.

Why it is exact

Accept a guessed token x with probability min(1, p(x)/q(x)); on rejection, draw from what the target wanted and the draft under-proposed. Tested here on real models with 20,000 samples per rule: the exact rules pass, a one-line bug fails by a chi-square of .

What it gives

Tokens per target pass = (1 − αk+1)/(1 − α), with α the chance a guess is accepted and k guesses per step. Published: 2 to 3x at batch 1 with a good drafter on datacenter chips (authors' and vendors' numbers).

When it stops paying

As the batch grows a step becomes compute-bound and every extra checked token costs real time. Measured on a real server here: Engines now switch it down or off by batch size.

Running example: the parent page's chat assistant, here a Qwen3-4B (or 1.7B) target with a Qwen3-0.6B draft from the same family, so they share a tokenizer, on an Apple M1 Pro (16-core GPU, 16 GB) with llama.cpp and MLX. Every result run here is marked measured here and says what transfers to datacenter GPUs; published results are marked by who measured them. 1. Why decode leaves the chip idle

The problem. A language model produces one token per forward pass, and each pass depends on the token before it. During decode (generating the answer) each pass processes one new token per user, yet it has to read every weight of the model from memory. Qwen3-4B at 4-bit (Q4_K_M) is a GB file: every token of the answer reads those bytes once. On the M1 Pro that pass took ms, about tokens per second measured here.

How much arithmetic is that? About 2 operations per weight per token (one multiply, one add), so roughly 8 billion operations per token for a 4B model. At tokens per second that is under 0.4 trillion operations per second, on a GPU that did trillion per second while processing a 512-token prompt (the same weights, read once, used for 512 tokens). The arithmetic units are mostly idle; the step waits for memory. This is the memory-bound regime, worked out with a roofline on {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}.

Predict: one Qwen3-4B pass over 5 tokens (positions processed in parallel, as when checking 4 guesses plus one) versus a pass over 1 token, on the M1 Pro GPU. How much longer?

Time of one forward pass against the number of tokens in it

What this means. If the pass time stayed flat as tokens were added, checking guesses would be free. On a datacenter GPU it nearly is: in the derived H100 curve a pass stays within 10% of the one-token time up to about tokens, because the H100 does about 590 FP8 operations per byte it reads (1,979 TFLOP/s over 3.35 TB/s) and a few extra tokens use a sliver of that. On the laptop the measured curve is a staircase instead: 2 tokens cost x one token, 5 tokens x, yet 16 to 32 tokens cost only times. The steps are kernels, not physics. llama.cpp's Metal backend multiplies a quantized weight matrix by 1 token with a matrix-vector kernel; it has a small-batch kernel for 2 to 8 tokens, but for the Q4_K and Q6_K formats in this file only from 4 tokens; and above 8 tokens it switches to a matrix-matrix kernel ({{ggml-metal-ops.cpp L2442 to L2470|https://github.com/ggml-org/llama.cpp/blob/b11146/ggml/src/ggml-metal/ggml-metal-ops.cpp#L2442}}, {{ggml-metal-common.cpp L28 to L35|https://github.com/ggml-org/llama.cpp/blob/b11146/ggml/src/ggml-metal/ggml-metal-common.cpp#L28}}). The same measurement on Qwen3-1.7B at Q8_0, which does get the small-batch kernel from 2 tokens, gives x for 5 tokens (toggle above).

What transfers from the laptop
The shape transfers: a pass over a few tokens costs much less than that many passes, because the weights are read once. Where it bends does not, and it depends on hardware, weight format and kernels as much as on the model. The M1 Pro's GPU does about 5 trillion operations per second on this workload against roughly 150 GB/s of effective bandwidth (the parent's {{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}), about 35 operations per byte, so it runs out of idle arithmetic within tens of tokens even with ideal kernels; an H100 after a hundred or more. Before trusting any speed-up, measure t(k + 1)/t(1) on your own engine and weights.
