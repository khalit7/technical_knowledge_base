The idea in one screen

While decode is memory-bound, a forward pass over a few tokens costs little more than over one, so a cheap drafter guesses the next k tokens and the large target model checks them all in one pass; an acceptance rule keeps exactly what the target would have sampled, so the output is unchanged and only the time per token falls, until the batch is large enough that checking stops being free.

Four tokens: four target passes, or one cheap draft and one target pass

Green: a guess the target kept; orange: the first guess it rejected, replaced by the target's own token, which every step adds. Here 3 of 4 guesses survive, so one target pass yields 4 tokens.

Target, drafter
the model whose output we want, and the cheap proposer of guesses (a small model, extra heads, or a lookup).
Draft length k
guesses per step (Leviathan et al. call it γ).
Acceptance α
the probability that one guess is kept; with the exact rule α = Σ min(p, q).
Acceptance length
tokens produced per target pass, between 1 and k + 1; engines report it.
Bonus token
the extra token the target adds when every guess survives.
Residual
max(0, p − q): what the target wanted and the draft under-proposed; rejections draw from it.

one draft pass as a fraction of one target pass.
Crossover
the batch size above which speculation makes throughput worse.

1. Why checking guesses is nearly free: decode leaves the chip idle

A language model produces one token per forward pass, and each pass depends on the token before it. During decode each pass processes one new token per user, yet it reads every weight from memory. Qwen3-4B at 4-bit (Q4_K_M) is a GB file: every token of the answer reads those bytes once. On the M1 Pro that pass took ms, about tokens per second measured here.

At about 2 operations per weight per token, that is roughly 8 billion operations per token, so under 0.4 trillion per second, on a GPU that did trillion per second while processing a 512-token prompt (the same weights, read once, used for 512 tokens). The arithmetic units are mostly idle; the step waits for memory: the memory-bound regime. A pass over k + 1 tokens reads the same weights once, so checking k guesses should cost little extra.

Predict: one Qwen3-4B pass over 5 tokens (4 guesses plus one) against a pass over 1 token, on the M1 Pro GPU. How much longer?

A pass over a few tokens costs far less than that many passes; where it bends depends on the chip

On a datacenter GPU checking is nearly free: in the derived H100 curve a pass stays within 10% of the one-token time up to about tokens (a 5-token check costs x a 1-token pass, Llama 3.1 8B FP8), because the H100 does about 590 FP8 operations per byte it reads (1,979 TFLOP/s over 3.35 TB/s) and a few extra tokens use a sliver of that. On the laptop the measured curve is a staircase: 2 tokens cost x one token, 5 tokens x, yet 16 to 32 tokens only times. The steps are kernels, not physics (closed block below); Qwen3-1.7B at Q8_0, which gets the small-batch kernel from 2 tokens, costs x for 5 tokens (toggle above).

What transfers from the laptop
The shape transfers: a pass over a few tokens costs much less than that many passes, because the weights are read once. Where it bends does not; it depends on hardware, weight format and kernels as much as on the model. The M1 Pro's GPU does about 5 trillion operations per second on this workload against roughly 150 GB/s of effective bandwidth (the parent's {{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}), about 35 operations per byte, so it runs out of idle arithmetic within tens of tokens even with ideal kernels; an H100 after a hundred or more. Before trusting any speed-up, measure t(k + 1)/t(1) on your own engine and weights.
Why the laptop curve is a staircase (llama.cpp's Metal kernels)

llama.cpp's Metal backend multiplies a quantized weight matrix by 1 token with a matrix-vector kernel; it has a small-batch kernel for 2 to 8 tokens, but for the Q4_K and Q6_K formats in this file only from 4 tokens; and above 8 tokens it switches to a matrix-matrix kernel ({{ggml-metal-ops.cpp L2442 to L2470|https://github.com/ggml-org/llama.cpp/blob/b11146/ggml/src/ggml-metal/ggml-metal-ops.cpp#L2442}}, {{ggml-metal-common.cpp L28 to L35|https://github.com/ggml-org/llama.cpp/blob/b11146/ggml/src/ggml-metal/ggml-metal-common.cpp#L28}}). So 2 and 3 tokens are handled almost one at a time, which is why 2 tokens cost 1.74x and not about 1x.
