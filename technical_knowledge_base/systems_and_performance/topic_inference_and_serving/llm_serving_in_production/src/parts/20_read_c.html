2. Routing: which replica gets the request

For ordinary web servers any replica will do, so the classic routers are round robin (1, 2, 3, 1, 2, 3, ...) and least loaded (fewest requests in flight). An LLM replica is not interchangeable: it keeps a prefix cache of prompts it has already processed, and a request whose beginning is cached there skips that part of its prefill. A chat resends its whole history every turn, an agent its tools and growing context every step; send turn 2 to a different replica from turn 1 and the whole history is computed again.

Round robin, least loadedSpread the load evenly; ignore the cache. Least loaded reacts to slow requests; round robin does not.
Hash on the prefixHash the first N tokens (or a session key) to a replica with consistent or rendezvous hashing: the same prefix always lands on the same replica, and adding a replica moves only a share of the keys. No state, no load awareness.
Cache-aware (SGLang Model Gateway)Keep an approximate radix tree of what was sent where; follow the longest match if it covers more than cache_threshold (0.3) of the prompt, else go to the least loaded; switch to least loaded when the busiest replica has more than 64 requests and 1.5 times the idlest.
Weighted scorers (llm-d)Score every replica on several signals (prefix-cache match, queue depth, KV usage, LoRA affinity), each from 0 to 1 times a weight, and pick the highest total ({{llm-d scheduler|https://llm-d.ai/docs/dev/architecture/core/router/epp/scheduling}}). Red Hat's documented example weighs the prefix scorer 3 and the queue scorer 2 ({{OpenShift AI 3.5 docs|https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.5/html/deploy_models_using_distributed_inference_with_llm-d/configuring-llm-scheduler}}).

What it shows. Round robin computed 13,000 prompt tokens in every run, exactly the parent's figure. The parent's prefix-aware figure (7,800) does not reproduce: its toy charges a load penalty for every request already sent, but real routers see only requests in flight, and requests arriving one at a time leave none. So least loaded, SGLang's rules, the weighted scorer and the hash all sent all eight to replica 1, and what that saved depended on memory: with a 256 MiB host cache (about one 2,300-token conversation at 112 KiB per token) 9,701 tokens were computed, with 1.5 GiB 5,804. When requests overlap, load becomes visible (third scenario, two bursts of four): the hash and SGLang's rules still sent all eight to replica 1, computing the fewest tokens (6,804) at a mean TTFT of 3.2 to 3.5 s; the weighted scorer's queue term spread them 3, 2, 3 and computed 10,103 with the lowest mean TTFT, 1.73 to 1.74 s; round robin and least loaded computed 14,000. The three replicas share one GPU, so spreading helps less than it would on three.

A real multi-turn trace

Mooncake, Kimi's serving system, released its production request traces with a hash per 512-token block, so prefix sharing between requests is exact while the text stays private ({{FAST'25 release|https://github.com/kvcache-ai/Mooncake/tree/main/FAST25-release}}). This page keeps every turn of one conversation in twelve from the first 30 minutes, scales each block to 16 tokens and plays it 20 times faster: 541 requests from 304 conversations at about 3.1 per second. One replica with unlimited cache would find 40.6% of prompt tokens cached (the {{batching page|n:3c65c17b0d0d819db53bd2c48909e5b2}} found 36.6% on the whole trace); each replica here holds much less, so routing decides what is reused.

Predict: which policy gives the lowest median and p90 time to first token on this trace?
The weighted cache-plus-queue score: median 0.23 to 0.25 s and p90 1.09 to 1.18 s in all three repeats, against 0.34 to 0.39 s and 2.28 to 2.51 s for round robin. It reuses about as much cache as hashing and SGLang's rules and also steers away from a busy replica. At the p99 the repeats overlap (weighted 2.3 to 2.7 s, least loaded 2.6 to 2.9 s, cache-aware 2.4 to 4.2 s): three runs cannot rank them there.

Following the prefix and watching the queue moves the whole TTFT curve left

Share of the 541 requests whose TTFT was at most x (log scale), first repeat of each policy; the thick line is the weighted cache-plus-queue score. measured on Apple M1 Pro

Following the prefix nearly doubles the reuse: hashing the first two blocks (system prompt plus the start of the conversation), SGLang's rules and the weighted score found 17 to 19% of prompt tokens cached, round robin and least loaded 11 to 12%, and the replicas computed about 7% fewer prompt tokens. A bad key is worse than no routing: hashing only the first block, which every request shares (the system prompt), sent all 541 requests to one replica, found 9.9% cached and gave a median TTFT of 7.7 s. SGLang's imbalance rule never fired: no replica ever had more than 10 requests in flight against its threshold of 64, so the router followed the cache whenever the match exceeded 0.3 of the prompt (301 of 541 decisions in the first run) and otherwise picked the least loaded; on a small deployment its load protection is off unless you lower the thresholds. All policies delivered the same output tokens per second, because the arrival schedule is fixed; the difference is the work done and the wait.

What it costs, when it matters, how to check

Cost: a router that follows the cache concentrates traffic, so it needs a load signal or a bound; it also needs state (a tree per replica, or the engines' cache events, as llm-d's precise prefix scorer and Dynamo's KV-aware router read), and an approximate tree drifts from what the replica really kept. Stickiness concentrates harm as well as load: in Anthropic's August 2025 incident "some users were affected more severely, as our routing is 'sticky'", because a user routed to a misconfigured server kept going back to it ({{Anthropic postmortem, 17 Sep 2025|https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues}}). When it matters: requests sharing long prefixes (multi-turn chat, agents, a long system prompt or document) over more than one replica. How to check: each replica's prefix hit rate and prompt tokens computed, from its own counters, against what one replica with infinite cache would get on the same traffic; the busiest replica's share of the work; TTFT percentiles at the client.

Depth: other routers you will meet, and published gains

The vLLM production stack router (Helm chart vllm-stack-0.1.13, 29 Sep 2026) offers roundrobin, session, prefixaware, kvaware, loadaware and others; its load-aware rule is "score(i) = matched_tokens(i) / prompt_tokens - beta * relative_load(i)", so "a warm-but-saturated instance can lose to a cold-but-idle one", the same trade the weighted scorer made above ({{routing_logic.py at vllm-stack-0.1.13|https://github.com/vllm-project/production-stack/blob/vllm-stack-0.1.13/src/vllm_router/routers/routing_logic.py}}). Kubernetes' Gateway API Inference Extension (v1.6.2) replaces a plain Service with an InferencePool, "an extensible request scheduling algorithm that is kv-cache and request cost aware", whose endpoint picker now lives in llm-d ({{README at v1.6.2|https://github.com/kubernetes-sigs/gateway-api-inference-extension/blob/v1.6.2/README.md}}). project docs The simplest form is a sticky session: Character.AI routes every message of one dialogue to the same server so its cached KV state is reused between turns, and reports a 95% cache hit rate ({{Character.AI, 20 Jun 2024|https://research.character.ai/optimizing-inference/}}; a case file on {{Topic: swe-and-system-design|n:3c65c17b0d0d81048ae0dd14ac399b4d}}).

Published gains are larger than the ones measured here and come from the projects themselves: llm-d reports 3 times the output throughput and half the TTFT of round robin for Llama 3.1 70B on four MI300X; Dynamo's KV-aware router, twice as fast a TTFT on Baseten's deployment (both quoted on the parent page). project measurements
