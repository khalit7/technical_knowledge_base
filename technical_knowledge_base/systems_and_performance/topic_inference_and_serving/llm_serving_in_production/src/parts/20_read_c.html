2. Autoscaling: what to scale on

The problem. Traffic to a chat assistant is not flat: it follows the working day, and a launch or an agent fleet can triple it in minutes. A fixed pool sized for the peak wastes GPUs most of the day; one sized for the average misses its latency target at the peak. An autoscaler adds replicas when load rises and removes them when it falls. It is a control loop: read a metric, compare it with a target, change the replica count, wait, repeat.

How it works. Kubernetes' Horizontal Pod Autoscaler (HPA), which most LLM deployments use directly or through KEDA, runs every 15 seconds and computes desired = ceil(current × metric / target); it ignores ratios within 10% of 1, adds at most 100% or 4 pods per 15 seconds, and only scales down to the highest recommendation of the last 300 seconds, so a brief lull does not remove capacity that is needed again a minute later ({{HPA docs|https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/}}). Everything interesting is in the choice of metric.

GPU utilizationThe default instinct, and wrong for LLMs. NVIDIA's counter is the share of time at least one kernel was running ({{NVML|https://docs.nvidia.com/deploy/nvml-api/api/structnvmlUtilization__t.html}}). With continuous batching some request is almost always decoding, so it reads near 100% at a fraction of capacity.
Queue depthRequests waiting for a slot, per replica. It moves exactly when users start waiting, and is zero when there is headroom. vLLM exports it as vllm:num_requests_waiting, llama-server as llamacpp:requests_deferred.
KV cache usageThe share of KV memory in use: the resource that runs out first in decode. It saturates at 100%, so it says "full" but not "how far over".
A latency SLOScale when the p90 TTFT approaches its target. It measures what users feel, but it reacts after they have felt it, and percentiles need enough requests per window to be stable.
Predict: one replica of the running example runs at 10% of the load it can carry. What does the GPU utilization gauge read?
About 96% derived. A request occupies the GPU for its whole life, prefill plus 300 decode steps: 0.42 + 300 × 0.0468 = 14.5 s. At 10% of the 2.2 requests per second a replica completes, 0.22 requests arrive per second, so on average 0.22 × 14.5 = 3.2 requests are in flight; with random (Poisson) arrivals the chance that none is running is e−3.2 = 4%. The gauge reads 96% while the replica could take ten times the load. An HPA with a 70% utilization target therefore scales to its maximum and stays there: in the {{Autoscaling lab|#t-scale}} it holds 16 replicas through the whole half hour, costing 7.66 replica-hours against 4.27 for a queue-depth autoscaler on the same traffic.

The cost of reacting: the queue builds while replicas boot. A scale-up decision only helps after the new replica's cold start (next section). In the lab's default comparison, traffic triples for ten minutes; with a 44.5-second start the queue-depth autoscaler lets the p99 TTFT reach 29.8 s, and 89.5% of requests meet the 1.05 s TTFT target. The same autoscaler with a 6-second start keeps 96.1% within it. That is the whole case for fast starts: the faster a replica starts, the less spare capacity you must keep idle in reserve.

What it costs, when it matters, how to check

Cost: spare replicas (headroom) or SLO misses during every ramp; flapping if the scale-down window is short (the lab's fourth comparison). When it matters: whenever traffic varies by more than a replica or two, and most when cold starts are long. How to check: replay a real day of arrivals against the autoscaler's rules before trusting it, and plot replicas, queue depth and p90 TTFT on one time axis. Scaling to zero needs an external trigger (KEDA, Knative or a gateway that holds the first request), because a pool with no replicas reports no metrics at all.

Go deeper: the {{Autoscaling lab|#t-scale}} runs any two autoscalers on the same spike; the parent's {{Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} sizes the pool for a steady rate.

3. Cold starts: what a new replica does before its first token

The problem. A cold start is everything between "start a replica" and "it serves requests". It sets how fast an autoscaler can react, how long a crashed replica is missing, and whether scaling to zero is tolerable. For the running example the weights alone are 72.66 GB.

1. Machine
seconds to minutes

A GPU node is provisioned (if none is free), the driver loads, the container image (often 10 GB or more) is pulled.

2. Weights
bytes / bandwidth

Read from local NVMe, network storage or a model hub into host memory and onto the GPU; 72.66 GB at an assumed 2 GB/s is 36 s, from remote storage minutes.

3. Engine init
seconds

Profile memory to size the KV cache, compile (torch.compile), capture CUDA graphs for each batch size, warm up.

4. Ready
health check passes

Only now does the router send traffic; the first requests may still pay for lazy initialization.

Measured here: llama-server, three model sizes, cold and warm. "Ready" is from starting the process to its health check answering; "cold" means none of the file was in the operating system's page cache (each run reads a fresh APFS clone of the GGUF, which shares the disk blocks but not the cached pages), "warm" means the file had just been read. Medians of 3 runs each, machine load average about 3 to 5. measured on Apple M1 Pro

Two things transfer to datacenter GPUs. First, the weights term is bytes over bandwidth: the cold runs take longer than the warm ones by 0.77 s for the 4B file's 2.50 GB, an effective 3.2 GB/s from this laptop's SSD derived: extra time against file size, close for all three sizes. At that rate the running example's 72.66 GB would take 23 s, before any engine work. Second, the first token after "ready" is fast here (64 ms for the 4B model) because llama-server does its warm-up before it reports healthy; engines that capture graphs or compile lazily pay on the first requests instead. What does not transfer: llama.cpp maps the file and has no CUDA graphs or torch.compile, so its engine initialization is a fraction of a second; a GPU engine adds memory profiling, graph capture for each batch size and compilation.

Measured here: vLLM v0.31.0 on the CPU, in Docker (Qwen3-0.6B in float32, the model folder mounted from the Mac into the Docker Desktop VM; 2 starts). From docker run to a healthy server took 78 and 80 s, and the engine's own log shows where: 36.2 and 37.3 s loading a 1.40 GiB checkpoint, because the file came through Docker's file-sharing layer (the log names it: FUSE.GRPCFUSE) at about 40 MB/s, against 3.2 GB/s from the same SSD for llama-server above; 0.69 and 0.45 s to profile memory, allocate 6,016 and 5,760 tokens of KV cache (it sizes the cache from the memory free at start) and warm up (no CUDA graphs on the CPU backend); the rest is the container, Python imports and the API server. measured on Apple M1 Pro The lesson transfers exactly: where the weights come from can dominate a cold start, and the engine's log tells you which phase to fix.

Published start-up times project measurements: vLLM v0.30.0 cut CUDA graph capture from 12 s to 2 s and engine initialization from 28.9 s to 8.2 s on an H200 (model not stated), and added a per-GPU daemon that keeps post-quantized weights in GPU memory across engine restarts, launched with vllm preload in v0.31.0 ({{v0.30.0|https://github.com/vllm-project/vllm/releases/tag/v0.30.0}}, {{v0.31.0|https://github.com/vllm-project/vllm/releases/tag/v0.31.0}} release notes). SGLang v0.5.18 stages checkpoint pages from storage while CUDA graphs capture: Qwen3-32B on an H100 starts 2.38 times faster than the plain default (35.6 s against 84.8 s) but only 8.6 to 11.7% faster than serial loading with prefetch, so most of the gain is the prefetch; it is opt-in with --startup-weight-load-mode overlap ({{v0.5.18|https://github.com/sgl-project/sglang/releases/tag/v0.5.18}}). ServerlessLLM reports 10 to 200 times lower latency than state-of-the-art serverless systems, from loading-optimised checkpoints in a multi-tier store, live migration of running inferences, and placing models on servers that already hold their checkpoint ({{Fu et al. 2024|https://arxiv.org/abs/2401.14351}}) authors' measurement.

Mitigations, in the order they usually pay

Keep weights close: local NVMe or host memory rather than a hub or object store (the bandwidth term above). Keep the engine alive: sleep mode or a weight daemon instead of a new process. Keep warm spare replicas sized to the cold start: the {{Autoscaling lab|#t-scale}} shows the queue that builds while replicas boot. Scale ahead of known peaks on a schedule. Measure each phase from the engine's log on your own hardware; the previous section's autoscaling numbers depend on it. When one replica spans several GPUs or nodes, start-up also includes setting up the parallel groups and their links: see {{Distributed and disaggregated serving|n:3c65c17b0d0d8170bd7cdf47af0ec07b}}.
