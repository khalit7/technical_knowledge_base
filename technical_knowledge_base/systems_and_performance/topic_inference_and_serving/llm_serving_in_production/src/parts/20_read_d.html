3. Autoscaling: what to scale on

Traffic follows the working day, and a launch or an agent fleet can triple it in minutes. A pool sized for the peak wastes GPUs most of the day (section 1); one sized for the average misses its SLO at the peak. An autoscaler is a control loop: read a metric, compare it with a target, change the replica count, wait, repeat. Kubernetes' Horizontal Pod Autoscaler (HPA), which most LLM deployments use directly or through KEDA, runs every 15 seconds and computes desired = ceil(current × metric / target); it ignores ratios within 10% of 1, adds at most 100% or 4 pods per 15 seconds, and only scales down to the highest recommendation of the last 300 seconds ({{HPA docs|https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/}}). Everything interesting is in the choice of metric.

GPU utilizationThe default instinct, and wrong for LLMs. NVIDIA's counter is the share of time at least one kernel was running ({{NVML|https://docs.nvidia.com/deploy/nvml-api/api/structnvmlUtilization__t.html}}). With continuous batching some request is almost always decoding, so it reads near 100% at a fraction of capacity.
Queue depthRequests waiting for a slot, per replica. It moves exactly when users start waiting, and is zero when there is headroom. vLLM exports it as vllm:num_requests_waiting, llama-server as llamacpp:requests_deferred.
KV cache usageThe share of KV memory in use: the resource that runs out first in decode. It saturates at 100%, so it says "full" but not "how far over".
A latency SLOScale when the p90 TTFT approaches its target. It measures what users feel, but reacts after they have felt it, and percentiles need enough requests per window to be stable.
Predict: one replica of the running example runs at 10% of the load it can carry. What does the GPU utilization gauge read?
About 96% derived. A request occupies the GPU for its whole life, prefill plus 300 decode steps: 0.42 + 300 × 0.0468 = 14.5 s. At 10% of the 2.2 requests per second a replica completes, 0.22 requests arrive per second, so on average 0.22 × 14.5 = 3.2 requests are in flight; with random (Poisson) arrivals the chance that none is running is e−3.2 = 4%. The gauge reads 96% while the replica could take ten times the load, so an HPA with a 70% utilization target scales to its maximum and stays there: in the comparison below it holds 16 replicas through the whole half hour, 7.66 replica-hours against 4.27 for a queue-depth autoscaler on the same traffic.

The cost of reacting. A scale-up decision helps only after the new replica's cold start (section 4). With a 44.5-second start the queue-depth autoscaler lets the p99 TTFT reach 29.8 s during the spike, and 89.5% of requests meet the 1.05 s target; the same autoscaler with a 6-second start keeps 96.1% within it. The faster a replica starts, the less headroom (capacity kept above demand) you must pay for: if a replica takes 3 minutes to start and traffic can grow 20% in 3 minutes, keep about 20% spare at all times. A short scale-down window flaps (the fourth comparison).

Three more signals that fail. CPU utilization barely moves, because a GPU server's CPU mostly tokenizes and schedules ("For inference workloads running on GPUs, we don't recommend CPU and memory utilization as the only indicators", Google's GKE guide); on ordinary servers it can even run backwards, as in Slack's January 2021 outage, where threads waiting on a congested network used less CPU and the autoscaler removed servers during the overload (a case file on {{Topic: swe-and-system-design|n:3c65c17b0d0d81048ae0dd14ac399b4d}}). GPU memory is worse: engines reserve almost all of it at start, so it "only works for scaling up, and won't scale down when traffic decreases" ({{GKE, Best practices for autoscaling LLM inference workloads with GPUs|https://cloud.google.com/kubernetes-engine/docs/best-practices/machine-learning/inference/autoscaling}}, updated 2026-10-02). Requests per second ignores size: "A single request with a 32K-token prompt consumes orders of magnitude more compute than a short one" ({{Dynamo Planner overview, v1.5.0|https://github.com/ai-dynamo/dynamo/blob/v1.5.0/docs/fern/pages/developer-guide/knowledge-base/modular-components/planner/overview.md}}), so when replies grow during a spike the queue builds anyway. vendor guidance

One operational trap: metric names change between engine versions (vLLM renamed gpu_cache_usage_perc to kv_cache_usage_perc in 0.9.2), and an autoscaler querying a removed name reads zero and silently stops scaling. Scaling to zero needs an external trigger (KEDA, Knative or a gateway that holds the first request), because a pool with no replicas reports no metrics at all, and the first user after a quiet period waits the whole cold start: fine for an internal tool, wrong for a chat product.

Depth: what the guides recommend, with real thresholds

GKE: queue size "directly correlates to request latency" and is "largely workload-agnostic", so "use the growth point as a signal to initiate scale-up", starting with a threshold "between 3-5" waiting requests per replica; batch size (vllm:num_requests_running) reacts sooner for tighter latency but depends on request sizes. llm-d's KEDA blueprint scales each prefill or decode role on waiting requests (threshold 20) and KV cache use (0.95) ({{llm-d-autoscaling at 3c06c88|https://github.com/llm-d/llm-d-autoscaling/blob/3c06c8814bcde4f7da0c7b4fadeed015e135a9de/README.md}}). KServe (v0.21.0) hands autoscaling to KEDA; its documented example puts autoscalerClass: "keda" on an InferenceService and scales a vLLM server between 1 and 5 replicas on the Prometheus query vllm:num_requests_running with a target of 2, so "if our LLM receives 6 concurrent requests with our target of 2 requests per pod, the system will scale to 3 replicas" ({{KServe docs, LLM autoscaling with KEDA|https://kserve.github.io/website/docs/model-serving/generative-inference/autoscaling}}); the vLLM production stack's tutorial does the same on vllm:num_requests_waiting with a threshold of 5 ({{tutorial 20, at 014d070|https://github.com/vllm-project/production-stack/blob/014d070e6f7611978d321bdb05cbe9a934b614e7/tutorials/20-keda-autoscaling.md}}). KEDA polls every 30 s, and its 300 s cooldownPeriod applies only to scaling to zero ({{KEDA 2.21 ScaledObject spec|https://keda.sh/docs/2.21/reference/scaledobject-spec/}}). NVIDIA's Dynamo planner can "Target specific TTFT/ITL SLA values" and runs a predictive loop (default every 180 s) for the daily curve under a reactive one (every 5 s) for surprises. project docs

Depth: spot (preemptible) capacity

Spot GPUs are cheaper and can be taken back with little warning: two minutes on AWS ({{EC2 Spot interruption notices|https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-instance-termination-notices.html}}), 0 seconds by default or 120 seconds if configured on Google Cloud, which advertises "up to 91% discounts" ({{GCP Spot VMs|https://cloud.google.com/compute/docs/instances/spot}}), "up to 30 seconds" on Azure ({{Azure Spot VMs|https://learn.microsoft.com/en-us/azure/virtual-machines/spot-vms}}). Two minutes is less than most cold starts, so spot suits batch work first; for live serving, research systems mix spot across regions with on-demand fallback: SkyServe "reduces cost by 43% on average" against on-demand replicas ({{SkyServe, EuroSys 2025|https://arxiv.org/abs/2411.01438}}), and SpotServe reports "saving 54% monetary cost compared with only using on-demand instances" ({{SpotServe, ASPLOS 2024|https://arxiv.org/abs/2311.15566}}). authors' measurements

How to check

Replay a real day of arrivals against the autoscaler's rules before trusting it, and plot replicas, queue depth and p90 TTFT on one time axis, as above.
