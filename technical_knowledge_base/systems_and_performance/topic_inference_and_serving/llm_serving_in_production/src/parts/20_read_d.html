4. Multi-LoRA: many fine-tunes on one set of weights

The problem. A LoRA adapter fine-tunes a model by adding a small low-rank update to some weight matrices: instead of changing a d × d matrix W, it learns B (d × r) and A (r × d) with rank r of 8 to 64 and computes x W + x AT BT scaled ({{LoRA paper page|n:3c65c17b0d0d81018f15edd19fa5c28a}}). An adapter is tiny next to the model (rank 16 on the attention projections of Qwen3-0.6B is 4.6 million parameters, 9.2 MB in FP16, against 0.6 billion in the base ({{model card|https://huggingface.co/Qwen/Qwen3-0.6B}})), so a provider can offer one per customer or per task. Serving a separate copy of the model for each would waste almost all the memory. The goal is one copy of the base weights, many adapters, and requests for different adapters in the same batch, because batching is where serving efficiency comes from.

How it works. The base model's matrix multiply is shared by the whole batch; only the small A and B products differ per request. Punica's kernel gathers each request's adapter and computes all the small products in one launch, and reported 12 times the throughput of serving systems of the time when serving many LoRA models, adding 2 ms per token ({{Chen et al. 2023|https://arxiv.org/abs/2310.18547}}) authors' measurement. S-LoRA keeps all adapters in host memory, moves the active ones to the GPU on demand, and pages adapter weights and KV cache from one memory pool, serving thousands of adapters on one GPU with up to 4 times the throughput of HuggingFace PEFT and vLLM's then naive LoRA support ({{Sheng et al. 2023|https://arxiv.org/abs/2311.03285}}) authors' measurement. vLLM now batches mixed adapters with its own kernels: --enable-lora, --max-loras (adapters on the GPU at once) and --max-lora-rank, with more kept in CPU memory; llm-d has a LoRA-affinity scorer that routes a request to a replica that already holds its adapter.

Measured here: llama-server with eight adapters. Eight rank-16 adapters made for this page (random weights, seeds 1 to 8, converted with llama.cpp's convert_lora_to_gguf.py: for measuring cost only, they do not improve the model), loaded with --lora-init-without-apply into one llama-server with 8 slots; 8 concurrent users each send 3 requests of 64 output tokens, and each request names its adapter. Two repeats. measured on Apple M1 Pro

With every request on the same adapter, the server keeps 352 and 353 tokens/s, close to the 378 to 384 of the same server with no adapters loaded. As soon as two different adapters are in flight it falls to 109 to 127, and with four or eight to 83 to 90, no better than a single user alone (88 to 100). The reason is one line of the server: a batch may only contain slots whose adapter sets are equal (can_batch_with, {{server-context.cpp L449-L455|https://github.com/ggml-org/llama.cpp/blob/b11146/tools/server/server-context.cpp#L449}}), because it applies one set of adapters to the whole context per step (common_set_adapter_lora, L2855). Different adapters take turns, and the batch that makes serving efficient disappears. That is the problem Punica and S-LoRA solved.

A trap found on the way

A request that lists no adapter does not get the base model: llama-server then applies every loaded adapter at its load-time scale (launch_slot_with_task, L1708 to L1723, uses the server's default list). Here that meant all eight random adapters at once: garbage text and 206 and 217 tokens/s. Listing one adapter at scale 0 switches all of them off (365 and 382 tokens/s). Name the adapters explicitly in every request, or start the server without --lora for base traffic.

The same test on vLLM v0.31.0 (CPU backend in Docker, Qwen3-0.6B float32, --enable-lora --max-loras 4 --max-lora-rank 16, the same eight adapters in PEFT format, 8 users, 2 requests each): with the adapter path active, throughput is 21.1 and 24.6 tokens/s for one adapter and 20.1 and 24.1 for four different ones in the same batches, so mixing adapters costs nothing extra; eight different adapters, more than --max-loras allows on the device at once, fell to 15.8 and 17.2 as adapters were swapped in and out. Without any adapter the same server gave 55.1 and 58.6 (two repeats each, machine load average 5 to 9): on this CPU backend the LoRA path itself is expensive, which says nothing about GPUs, where Punica-style kernels add little. measured on Apple M1 Pro vLLM counts requests per adapter in vllm:lora_requests_info ({{loggers.py L993|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/metrics/loggers.py#L993}}). How vLLM's knobs and metrics behave on a live server is on {{vLLM: inside the default engine|n:3c65c17b0d0d8113b976d8bcaf2c0722}}.

5. Structured output under load

The problem. Tool calls and machine-read answers must be valid JSON matching a schema. Constrained decoding makes invalid output impossible: the schema is compiled into a grammar, and at every step the engine masks out every token that would break it before sampling. How it works inside an engine (XGrammar, the token mask, the jump-forward SGLang removed) is on the {{SGLang page|n:3c65c17b0d0d81e691e4ce9f9b5d1fad}}. The serving question is what it costs per token, and whether the cost grows with load.

Measured here: llama-server with a JSON schema. The same server without adapters; each request asks Qwen3-0.6B (thinking off) to invent a person as a JSON object with four keys, with and without response_format set to that schema; 1 user sending 5 requests, then 4 users sending 5 each; two repeats. measured on Apple M1 Pro

Two results. Cost per token: within the noise here: median time per output token with the schema was 7.8 and 10.1 ms against 7.5 and 8.3 ms without it for one user, and 17.4 and 19.7 ms against 19.1 and 18.4 ms for four. The grammar check runs on the CPU per sampled token; for a small vocabulary walk like this one it is cheap next to a decode step, and the {{SGLang page|n:3c65c17b0d0d81e691e4ce9f9b5d1fad}}'s measurement on its MLX backend (13.4 against 4.9 ms per token) shows it is not always so. Validity: the schema matters more than the speed: without it every answer (0 of 50) came wrapped in a Markdown code fence and failed a strict parse, though all parsed once the fence was stripped; with it, 50 of 50 were bare, valid objects with exactly the four keys.

On vLLM v0.31.0 (CPU, 4 users, structured-output backend auto, the default, which picks a grammar library per request: {{structured_outputs.py L21|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/structured_outputs.py#L21}}) the cost was inconclusive: 136 and 112 against 114 and 112 ms per output token in the two repeats, and again every unconstrained answer was fenced (0 of 24 strictly valid) while all 24 constrained answers were valid. measured on Apple M1 Pro

What it costs, when it matters, how to check

Cost: grammar compilation once per new schema (cached after), a vocabulary-wide mask per step, and possible quality loss where the mask overrides the model's choice. When it matters: tool calls, extraction, anything a program reads; reasoning models are usually left unconstrained while thinking. How to check: parse every response in production (count failures), and compare time per output token with and without the schema at the same output length and concurrency, as here.
