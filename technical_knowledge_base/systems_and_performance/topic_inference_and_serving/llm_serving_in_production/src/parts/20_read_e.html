4. Cold starts: what a new replica does before its first token

A cold start sets how fast an autoscaler can react, how long a crashed replica is missing, and whether scaling to zero is tolerable. For the running example the weights alone are 72.66 GB. Four phases, each with its own fix:

1. Machine
seconds to minutes

A GPU node is provisioned (if none is free), the driver loads, the container image (often 10 GB or more) is pulled.

2. Weights
bytes / bandwidth

Read from local NVMe, network storage or a model hub into host memory and onto the GPU; 72.66 GB at an assumed 2 GB/s is 36 s, from remote storage minutes.

3. Engine init
seconds

Profile memory to size the KV cache, compile (torch.compile), capture CUDA graphs for each batch size, warm up.

4. Ready
health check passes

Only now does the router send traffic; the first requests may still pay for lazy initialization.

Where a cold start goes depends on where the weights come from

Seconds from start to healthy, split by phase, on one axis. Measured: vLLM v0.31.0 on the M1 Pro's CPU in Docker, phases read from the engine's log (run 1 of 2). Published: NVIDIA's Run:ai Model Streamer test (Llama 3 8B, 15 GB, on an A10G, read from S3). Derived: the running example on one H200, 72.66 GB at an assumed 2 GB/s plus vLLM's engine initialization on an H200 as its release notes give it, before and after v0.30.0. measured vendor derived

The weights term is bytes over bandwidth. llama-server on the M1 Pro, three model sizes, cold (a fresh APFS clone of the file, so none of it in the page cache) and warm (just read); medians of 3 runs, machine load average 3 to 5. measured on Apple M1 Pro

Cold runs take longer than warm ones by 0.77 s for the 4B file's 2.50 GB, an effective 3.2 GB/s from this laptop's SSD derived: extra time against file size, close for all three sizes. At that rate the running example's 72.66 GB would take 23 s before any engine work. The vLLM container, reading a 1.40 GiB checkpoint through Docker's file-sharing layer (the log names it: FUSE.GRPCFUSE) at about 40 MB/s, spent 36.2 and 37.3 s on weights of its 78 and 80 s start: where the weights come from can dominate, and the engine's log tells you which phase to fix. Its own initialization took 0.69 and 0.45 s (profile memory, allocate 6,016 and 5,760 tokens of KV cache, sized from the memory free at start; no CUDA graphs on the CPU backend). What does not transfer: llama.cpp maps the file and has no CUDA graphs or torch.compile, and it warms up before it reports healthy (first token after "ready" 64 ms for the 4B model); a GPU engine adds memory profiling, graph capture for each batch size and compilation, as the NVIDIA bar shows.

Mitigations, in the order they usually pay

Keep weights close: local NVMe or host memory rather than a hub or object store. Keep the engine alive: sleep mode or a weight daemon instead of a new process. Keep warm spare replicas sized to the cold start (section 3 shows the queue that builds while replicas boot). Scale ahead of known peaks on a schedule. Measure each phase from the engine's log on your own hardware. When one replica spans several GPUs or nodes, start-up also includes setting up the parallel groups: see {{Distributed and disaggregated serving|n:3c65c17b0d0d8170bd7cdf47af0ec07b}}.

Depth: published start-up times and fixes for each phase

Engines project measurements: vLLM v0.30.0 cut CUDA graph capture from 12 s to 2 s and engine initialization from 28.9 s to 8.2 s on an H200 (model not stated), and added a per-GPU daemon that keeps post-quantized weights in GPU memory across engine restarts, launched with vllm preload in v0.31.0 ({{v0.30.0|https://github.com/vllm-project/vllm/releases/tag/v0.30.0}}, {{v0.31.0|https://github.com/vllm-project/vllm/releases/tag/v0.31.0}} release notes). SGLang v0.5.18 stages checkpoint pages from storage while CUDA graphs capture: Qwen3-32B on an H100 starts 2.38 times faster than the plain default (35.6 s against 84.8 s) but only 8.6 to 11.7% faster than serial loading with prefetch, so most of the gain is the prefetch; it is opt-in with --startup-weight-load-mode overlap ({{v0.5.18|https://github.com/sgl-project/sglang/releases/tag/v0.5.18}}). ServerlessLLM reports 10 to 200 times lower latency than state-of-the-art serverless systems, from loading-optimised checkpoints in a multi-tier store, live migration of running inferences, and placing models on servers that already hold their checkpoint ({{Fu et al. 2024|https://arxiv.org/abs/2401.14351}}) authors' measurement.

Each phase vendor measurements. Machine: "Spinning up a GPU worker takes minutes, not seconds" (Dynamo docs), so keep spare nodes or predict demand. Image: 24 s to 1.5 s with GKE image streaming, on Google's sample web app ({{GKE image streaming|https://cloud.google.com/kubernetes-engine/docs/how-to/image-streaming}}). Weights: Llama 3 8B (15 GB) on an A10G loaded in 47.99 s with the standard Hugging Face loader and 4.88 s from S3 with the Run:ai Model Streamer (vllm serve --load-format runai_streamer), yet the server took 23.18 s to be ready, the rest being allocator setup, CUDA graph capture and compilation ({{NVIDIA, 16 Sep 2025|https://developer.nvidia.com/blog/reducing-cold-start-latency-for-llm-inference-with-nvidia-runai-model-streamer/}}). Engine: vLLM's sleep mode "Offloads model weights to CPU RAM and discards KV cache", and waking is "18-200x faster than full reload" ({{vLLM blog, 26 Oct 2025|https://vllm.ai/blog/2025-10-26-sleep-mode}}); GPU memory snapshots took a small vLLM model's start from 45 s to 5 s on Modal ({{Modal, 30 Jul 2025|https://modal.com/blog/gpu-mem-snapshots}}).
