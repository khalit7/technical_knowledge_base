Common mistakes

Round-robin load balancing in front of engines that cache prefixes
Each replica ends up prefilling every conversation's history again; the hit rate falls toward what one replica's share of the traffic can reuse. Route on the prefix (section 1), and measure the hit rate per replica from the engine's own counters.
Hashing on the first few tokens
If every request starts with the same system prompt, a hash of the first block sends all of them to one replica (section 1, the hash-on-first-block run). Hash on a key that differs per conversation, or use a cache-aware router that also weighs load.
Autoscaling on GPU utilization
The gauge reads the share of time any kernel ran, which is near 100% with continuous batching at a fraction of capacity (section 2). Scale on queue depth, KV usage or a latency SLO.
Ignoring cold-start time when sizing headroom
A scale-up decision helps only after the new replica has loaded its weights, profiled memory and captured its graphs. Measure the start-up on your hardware (section 3) and keep enough spare capacity to cover the ramp in that time.
Mixing many LoRA adapters on an engine that cannot batch them
llama-server puts only requests with identical adapters in one batch, so different adapters take turns (section 4). Use an engine with multi-adapter kernels (vLLM, SGLang, LoRAX-style servers) or group traffic by adapter.
Loading LoRA adapters into llama-server and sending requests that name none
Such a request gets every loaded adapter at its load-time scale, not the base model (section 4: all eight test adapters at once, garbage text at about half the speed). List the adapters in every request, with scale 0 for base traffic, or serve base traffic from a server started without --lora.
Benchmarking with a closed loop and calling the result a latency
A closed-loop generator stops sending while the server stalls, so the stall barely shows in its percentiles (section 7). Use open-loop arrivals at a stated rate, or correct for the intended send times.
Running vllm bench serve with its default request rate
The default is infinite: every request is sent at time 0, which measures a burst, not a service. Set --request-rate (Poisson by default) or --max-concurrency, and sweep.
Quoting a p99 from a histogram as if it were exact
histogram_quantile interpolates inside a bucket; between vLLM's 1 s and 2.5 s buckets a p99 can be anywhere in that range (section 6). Keep raw samples when the exact percentile matters, or choose buckets around your SLO.
Measuring TTFT only inside the server
The engine's clock starts when it receives the request; time in the gateway, router and network is outside it. Measure at the client as well.

Interview questions

Design the serving layer for a chat product on 20 GPU replicas. How do you route?
A router that keeps each conversation on the replica that holds its prefix (consistent hashing on a conversation key, or a cache-aware router that tracks prefixes per replica) and falls back to the least-loaded replica when the preferred one is overloaded. Measure the prefix hit rate per replica and the TTFT tail; watch for hot spots on popular shared prefixes.
Why not autoscale an LLM server on GPU utilization? What instead?
The utilization counter is the share of time any kernel ran; continuous batching keeps it near 100% at low load. Scale on waiting requests, KV cache usage or the TTFT SLO, and size headroom for the cold start.
A new replica takes 90 seconds to start. What do you do?
Break it down (node, image pull, weight load, engine initialization, graph capture), then attack the largest part: weights cached on local NVMe or kept in host memory, a loading-optimised format, overlapped loading, captured graphs reused, a warm pool or sleep mode instead of new replicas, and scaling ahead of known peaks.
You must serve 500 customer fine-tunes of one 8B model. How?
LoRA adapters on shared base weights: an engine that batches different adapters in one pass (Punica/S-LoRA-style kernels in vLLM or SGLang), a limit on adapters resident on the GPU with the rest in host memory, an LRU between them, and routing that prefers replicas where the adapter is already loaded (llm-d has a LoRA-affinity scorer).
Structured output (JSON schema) slows a service down. Where does the time go?
Compiling the grammar for a new schema, computing a mask over the whole vocabulary every step, and on some engines losing the overlap between CPU and GPU work. Cache compiled grammars, use an engine with a fast backend (XGrammar), and measure time per output token with and without the schema at the same output length.
Your benchmark says p99 TTFT is 300 ms but users complain. What could be wrong?
A closed-loop generator (coordinated omission), warm caches from repeated prompts, fixed short prompts, no queueing because the rate was low, or TTFT measured inside the engine and not at the client. Re-run with open-loop arrivals from real traffic, real lengths and a cold cache.
What does prefix-aware routing cost?
Load imbalance: the replica holding a popular prefix attracts its traffic. Routers bound it with load thresholds (SGLang's gateway: switch to least-loaded when the busiest has more than 64 requests and 1.5 times the idlest, by its command-line defaults) or by weighing a load score against the cache score (llm-d).
How would you alert on latency for an LLM API?
Two SLOs, TTFT and TPOT, each with an error budget, and multiwindow burn-rate alerts (page at 14.4 times the budget rate over both an hour and 5 minutes). Not on averages, and not on GPU utilization.
