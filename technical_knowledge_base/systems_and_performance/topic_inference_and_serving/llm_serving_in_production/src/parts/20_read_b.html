1. Routing: which replica gets the request

The problem. One engine on one GPU (or one group of GPUs) is a replica. To serve more users you run several, and something in front, the router (or load balancer), picks a replica for every request. For ordinary web servers any replica will do, so the classic choices are round robin (1, 2, 3, 1, 2, 3, ...) and least loaded (the replica with the fewest requests in flight). An LLM replica is not interchangeable: each keeps a prefix cache, the keys and values of prompts it has already processed, and a request whose beginning is cached there skips that part of its prefill. A chat conversation resends its whole history every turn, an agent resends its tools and its growing context every step. Send turn 2 to a different replica from turn 1 and the whole history is computed again.

Four ways to route. The parent page's section 9 gives the picture; the {{SGLang page|n:3c65c17b0d0d81e691e4ce9f9b5d1fad}} reads the cache-aware router's code. In short:

Round robin, least loadedSpread the load evenly; ignore the cache. Least loaded reacts to slow requests; round robin does not.
Hash on the prefixHash the first N tokens (or a session key) and map it to a replica with consistent or rendezvous hashing, so the same prefix always lands on the same replica, and adding a replica moves only a share of the keys. No state, no load awareness.
Cache-aware (SGLang Model Gateway)Keep an approximate radix tree of what was sent where; follow the longest match if it covers more than cache_threshold (0.3) of the prompt, else go to the least loaded; switch to least loaded when the busiest replica has more than 64 requests and 1.5 times the idlest.
Weighted scorers (llm-d)Score every replica on several signals (prefix-cache match, queue depth, KV usage, LoRA affinity), each from 0 to 1 times a weight, and pick the highest total ({{llm-d scheduler|https://llm-d.ai/docs/dev/architecture/core/router/epp/scheduling}}). Red Hat's documented example weighs the prefix scorer 3 and the queue scorer 2 ({{OpenShift AI 3.5 docs|https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.5/html/deploy_models_using_distributed_inference_with_llm-d/configuring-llm-scheduler}}).

The experiment. Three replicas of llama-server (Qwen3-0.6B, Q4_K_M) run on the M1 Pro, each with 2 slots of 2,048 tokens and a host prompt cache (--cache-ram) that keeps recent prompts' KV in memory. A router written for this page (src/exp/route_client.py, standard-library Python) implements the policies above: the cache-aware one follows SGLang v0.5.21's select_worker with its command-line defaults (0.3, 64, 1.5), on token blocks instead of characters; the weighted one uses a prefix-match score and a queue score with weights 3 and 2. Requests carry their prompts as token ids, and llama-server returns, for each one, how many prompt tokens it found cached and how many it computed. So every hit rate below is the engine's own count, and the replicas' Prometheus counters (llamacpp:prompt_tokens_total) agree with it to the token. measured on Apple M1 Pro

Eight requests, three replicas: what the replicas actually cached

The parent's scenario exactly: system prompt 1,000 tokens, first turns 2,000 tokens, second turns 2,500 tokens plus the generated answer; every policy repeated 3 times on fresh replicas (identical routing and token counts each time; TTFTs vary by a few hundredths of a second).

What the real replicas say about the parent's toy. Round robin computed 13,000 prompt tokens in every run, exactly the parent's figure: confirmed. The prefix-aware figure is not. The toy charges 1,000 tokens of "load" per request already sent to a replica, which spreads the eight requests and lands on 7,800. Real routers see only requests in flight, so when requests arrive one at a time there is never any load to see: least loaded (ties to the first replica), the SGLang rules, the weighted scorer and the hash all sent all eight requests to replica 1. What that saves then depends on how much one replica can keep. With a 256 MiB host prompt cache, which holds the KV of about one 2,300-token conversation (112 KiB per token for Qwen3-0.6B), the second turns of A, B and C found only the system prompt and 9,701 tokens were computed. With 1.5 GiB, every second turn found its whole first turn and answer: 5,804, less than the toy's 7,800 because nothing is spread. Prefix-aware routing only pays when the replica it chooses still has the prefix, and memory, not the routing rule, decided that here.

When requests overlap, load becomes visible. In the third scenario the four first turns arrive together and so do the four second turns. Round robin and least loaded both computed 14,000 tokens: the four first turns start before anything is cached, and most second turns land away from their first turn. The hash and SGLang's cache-aware rules still sent all eight to replica 1 (the imbalance rule never fires with a gap of a few requests): the fewest tokens, 6,804, but every request queued on one replica, a mean TTFT of 3.2 to 3.5 s. The weighted scorer, whose queue term pushes back as soon as a replica is busy, spread them (3, 2, 3) and computed 10,103 with the lowest mean TTFT, 1.73 to 1.74 s. That is the parent's picture of a trade between cache and load, reached by a different rule. Two repeats gave identical token counts. TTFT here includes the prefill of up to four 2,000-token prompts sharing one GPU; the three replicas share the M1's GPU, so spreading helps less than it would on three GPUs.

A real multi-turn trace

Eight requests show the mechanism; a trace shows the trade. Mooncake, Kimi's serving system, released the request traces of its production service with a hash per 512-token block, so prefix sharing between requests is exact while the text stays private ({{FAST'25 release|https://github.com/kvcache-ai/Mooncake/tree/main/FAST25-release}}). From the conversation trace this page keeps every turn of one conversation in twelve that began in the first 30 minutes, scales each block to 16 tokens, and plays it 20 times faster: 541 requests from 304 conversations at about 3.1 per second. On one replica with unlimited cache, 40.6% of all prompt tokens would be found cached (the {{batching page|n:3c65c17b0d0d819db53bd2c48909e5b2}} found 36.6% on the whole trace). Each replica here holds much less, so routing decides what is reused.

Predict: which policy gives the lowest median and p90 time to first token on this trace?
The weighted cache-plus-queue score: median 0.23 to 0.25 s and p90 1.09 to 1.18 s in all three repeats, against 0.34 to 0.39 s and 2.28 to 2.51 s for round robin. It reuses about as much cache as hashing and SGLang's rules and also steers away from a busy replica. At the p99 the repeats overlap (weighted 2.3 to 2.7 s, least loaded 2.6 to 2.9 s, cache-aware 2.4 to 4.2 s): three runs cannot rank them there.

What the table shows. Following the prefix nearly doubles the reuse: hashing the first two blocks (system prompt plus the start of the conversation, so one conversation always lands on one replica), SGLang's rules and the weighted score all found 17 to 19% of prompt tokens cached, round robin and least loaded 11 to 12%, and the replicas computed about 7% fewer prompt tokens. The absolute numbers are small because each replica keeps little (two 2,048-token slots and 256 MiB, about 2,300 tokens of host cache) against what one replica with an unlimited cache would reuse, 40.6%; the {{Router lab|#t-route}} simulates more memory and more replicas. A bad key is worse than no routing: hashing only the first block, which every request shares (the system prompt), sent all 541 requests to one replica, found 9.9% cached and gave a median TTFT of 7.7 s. SGLang's imbalance rule never fired: with its default thresholds the busiest replica must have more than 64 requests in flight and 1.5 times the idlest; here no replica ever had more than 10 in flight, so the router followed the cache whenever the match exceeded 0.3 of the prompt (301 of 541 decisions in the first run) and otherwise picked the least loaded. On a small deployment its load protection is effectively off unless you lower the thresholds. All policies delivered the same output tokens per second, because the arrival schedule is fixed; the difference is in the work done and in the wait.

What it costs, when it matters, how to check

Cost: a router that follows the cache concentrates traffic, so it needs a load signal or a bound; it also needs state (a tree per replica, or the engines' cache events, as llm-d's precise prefix scorer and Dynamo's KV-aware router read), and an approximate tree drifts from what the replica really kept. When it matters: when requests share long prefixes (multi-turn chat, agents, a long system prompt or document) and replicas are more than one; least when prompts are unique. How to check: each replica's prefix hit rate and prompt tokens computed, from its own counters, against the hit rate one replica with infinite cache would get on the same traffic; the busiest replica's share of the work; and TTFT percentiles at the client.

Other routers you will meet. The vLLM production stack router (Helm chart vllm-stack-0.1.13, 29 Sep 2026) offers roundrobin, session, prefixaware, kvaware, loadaware and others; its load-aware rule is "score(i) = matched_tokens(i) / prompt_tokens - beta * relative_load(i)", so "a warm-but-saturated instance can lose to a cold-but-idle one", the same trade the weighted scorer made above ({{routing_logic.py at vllm-stack-0.1.13|https://github.com/vllm-project/production-stack/blob/vllm-stack-0.1.13/src/vllm_router/routers/routing_logic.py}}). Kubernetes' Gateway API Inference Extension (v1.6.2) replaces a plain Service with an InferencePool, "an extensible request scheduling algorithm that is kv-cache and request cost aware", whose endpoint picker now lives in llm-d ({{README at v1.6.2|https://github.com/kubernetes-sigs/gateway-api-inference-extension/blob/v1.6.2/README.md}}). project docs The simplest form is a sticky session: Character.AI routes every message of one dialogue to the same server so its cached KV state is reused between turns, and reports a 95% cache hit rate ({{Character.AI, 20 Jun 2024|https://research.character.ai/optimizing-inference/}}; a case file on {{Topic: swe-and-system-design|n:3c65c17b0d0d81048ae0dd14ac399b4d}}). Stickiness concentrates harm as well as load: in Anthropic's August 2025 incident, "some users were affected more severely, as our routing is 'sticky'", because a user routed to a misconfigured server kept going back to it ({{Anthropic postmortem, 17 Sep 2025|https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues}}). Where this layer sits in a whole LLM service, with tenancy and degradation ladders around it, is {{ML system design|n:3c65c17b0d0d8117b057dc2586836ec8}}.

Published gains are larger than the ones measured here and come from the projects themselves: llm-d reports 3 times the output throughput and half the TTFT of round robin for Llama 3.1 70B on four MI300X; Dynamo's KV-aware router, twice as fast a TTFT on Baseten's deployment (both quoted on the parent page).
