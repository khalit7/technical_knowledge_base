0. In one screen

A serving engine on one GPU is the unit the parent page taught. This page is about what happens when one unit is not enough: the model does not fit, the users do not fit, one GPU is too slow for the latency target, or prefill and decode keep getting in each other's way. There are five ways to spread the work, each costs something different on the wire, and above them sits a serving layer (NVIDIA Dynamo, llm-d, KServe, Ray Serve) that decides which GPU gets which request.

The question this page keeps returning to: for each way of splitting, what crosses between GPUs for every token, how long does that take on the link it uses, and what does the split buy in latency, users and cost? The running example is the parent page's chat assistant: Llama 3.1 70B with FP8 weights and a BF16 KV cache on H200s (141 GB each), 2,000-token prompts and 300-token answers, targets of 2 s to the first token and 50 ms per output token. Every derived number comes from the parent's Capacity planner model (run by src/recompute.py), so it can be checked there.

1. Why one GPU stops being enough

Four different pressures push a deployment past one GPU, and they have different fixes. Mixing them up is the most common planning mistake.

The weights do not fitLlama 3.1 405B in FP8 is about 405 GB; an H200 has 141 GB. Some split of the weights is required: tensor or pipeline parallelism, or experts spread over GPUs.
The cache for enough users does not fitEvery running conversation keeps its KV cache in GPU memory (320 KiB per token for this model). Whatever the weights leave over decides how many users run at once.
One GPU is too slow for the latency targetDecode reads every weight once per step, so one token can never come faster than weight bytes divided by memory bandwidth: 72.7 GB / 4.8 TB/s = 15 ms on an H200. A tighter target needs the weights spread over more GPUs' bandwidth.
One GPU is too slow for the trafficThe model fits and is fast enough, there is just more traffic than one GPU serves. Copies (replicas) are the answer.

In the running example the weights fit: 72.7 GB of FP8 weights (embeddings kept in BF16, as released FP8 checkpoints do) on one H200, leaving room for the cache of conversations of the average length. Split the same model over two GPUs with tensor parallelism and the pair holds : twice the GPUs, times the conversations, because the weights are paid once across the pair while all the memory they freed goes to cache Capacity planner memory model: 92% of 141 GB usable, activations and 1.5 GB overhead reserved. That is the first lesson of the page: splitting a model is often about cache, not about weights.

Predict: Llama 3.1 70B on one H200 makes one user's token in about 21.6 ms. Split over eight H200s with tensor parallelism, how long does one token take?
About ms, 3.6 times faster, not 8. The weight reading does shrink eightfold (19.1 ms to 2.4 ms), but the 2.5 ms of fixed work per step (scheduling, sampling, kernel launches) does not shrink at all, and every layer now ends with two all-reduces across the eight GPUs, about 1.1 ms in all. 2. Replicas: copies that never talk

Data parallelism in serving means running several complete copies of the engine (replicas) and sending each request to one of them. Nothing crosses between copies while they work, so capacity grows exactly with the number of copies, and so does cost. One request is served by one copy, so a replica never makes any single user faster.

The problem it solves: traffic. How it works: a load balancer in front picks a replica per request. Cost: each copy needs the whole model and its own cache, and the cache is not shared: a conversation that moves to another replica loses its cached prefix and pays its prefill again. That is why the router matters more for LLMs than for ordinary web servers: round robin scatters conversations, prefix-aware routing (send the request where its prefix is cached) keeps them together. Routing policies, autoscaling and cold starts are on LLM serving in production (link); Dynamo's and llm-d's routers are in section 8.

When it matters: always, as the outer layer. Real deployments are replicas of something: of one GPU (an 8B model), of a TP 8 server (a 70B model), or of a whole prefill/decode group. How to check: per-replica request rates and KV cache usage should be even; a hot replica means the router is not balancing (vLLM exports vllm:kv_cache_usage_perc and vllm:num_requests_waiting per engine; what each metric means is on vLLM: inside the default engine).

A special case worth knowing: data-parallel attention. In a mixture-of-experts deployment (section 5) the attention layers are often run as replicas, each GPU attending over its own users with its own cache, while the experts are spread across all GPUs. vLLM does this with --data-parallel-size together with --enable-expert-parallel (vLLM v0.31.0 config/parallel.py L134, L172: "MoE layers will be sharded according to the product of the tensor, prefill-context, and data parallel sizes").

3. Tensor parallelism: every GPU holds a slice of every layer

The problem: one GPU reads the weights too slowly for the latency target, or holds too little cache. The idea (Megatron-LM, 2019; paper page): cut each weight matrix across GPUs so each GPU does a slice of every matrix multiplication. In attention the query, key and value projections are split by heads, so each GPU computes its own heads with its own share of the KV cache; the output projection is split by rows, so each GPU ends with a partial sum of the layer's output. The MLP works the same way: the first matrix split by columns, the second by rows. Two partial sums per layer have to be added up across all GPUs before the next layer can start: two all-reduces per layer, every step.

bytes each GPU sends per all-reduce (ring) = 2 (t − 1) / t × hidden size × 2 bytes × tokens in the step

Running example: hidden size 8,192, so one token's activation is 16 KiB. At TP 8 each GPU sends per all-reduce, and a token needs 2 × 80 = 160 of them: per token per GPU. derived

At batch 1 those messages are tiny and the cost is latency, not bandwidth: each all-reduce is a round of synchronisation that takes microseconds however few bytes it carries. The planner charges about 6.7 µs per small all-reduce (two NVLink hops of 3.33 µs, from DeepSeek's ISCA 2025 paper, Table 5), so 160 of them cost about 1.1 ms per token, a sixth of the whole step at TP 8. At 64 users the bytes start to count too. The animation draws one decode step to scale under each split, for one user and for 64.

What to take from it. With one user, TP 8 makes the token times faster; replicas and pipeline stages make it no faster at all. With 64 users the picture changes: eight replicas give each user a GPU-eighth of the traffic but each copy still reads all 72.7 GB per step for only 8 users, while TP 8 reads each weight once for all 64; at equal users, TP 8 delivers tokens per second against for the replicas. The replicas win back when traffic is high enough to fill each copy's batch: that is the throughput-against-latency trade of the parent page's Capacity planner, which searches it for you (try TP 1 against TP 2 there).

Why tensor parallelism stays inside one server

Every all-reduce sits between two matrix multiplications that need its result, so it cannot be hidden behind other work, and its cost does not shrink with batch size relative to the compute. It needs the fastest link there is: NVLink gives an H100 900 GB/s counting both directions, 450 GB/s each way (NVIDIA, vendor spec); a 400 Gb/s network card moves 50 GB/s each way, nine times less, with several microseconds more latency per message. Interconnects and scaling (section 9) works the ratio out for this model and finds tensor parallelism over a network card would leave the GPUs waiting most of the time. Hence the rule every engine's documentation repeats: tensor parallelism within the NVLink domain (8 GPUs in an HGX server, 72 in a GB200 NVL72 rack), pipeline or expert parallelism across it.

Two limits that are easy to miss. The KV cache is split by heads, and Llama 3.1 70B has 8 key/value heads: at TP 8 each GPU owns one, and beyond 8 the heads must be copied, so the cache stops shrinking. And the engine needs the head counts to divide evenly by the TP degree (vLLM refuses to start otherwise: "Total number of attention heads ... must be divisible by tensor parallel size", config/model.py L1504-1509).

How to check it: vLLM --tensor-parallel-size 8; SGLang --tp-size 8; TensorRT-LLM tensor_parallel_size. Measure time per output token at batch 1 against TP 1; if it improves much less than the planner predicts, profile the all-reduces (NCCL logs which link it used: Interconnects and scaling, section 10) and check that CUDA graphs are on, since launch overhead grows with every extra collective.

4. Pipeline parallelism: every GPU holds a run of whole layers

The problem: the model does not fit in one server, and the link between servers is too slow for tensor parallelism. The idea: cut the model by depth. With 8 stages, GPU 0 holds layers 1 to 10, GPU 1 layers 11 to 20, and so on; each stage also holds the KV cache of its own layers. A token's hidden state, 16 KiB for this model, is the only thing that crosses a boundary, once per stage: any network can carry that.

The cost: a single request walks the stages one after another, so it gets no faster: in the animation above, pipeline parallel 8 takes the same time per token as one GPU, and each GPU is idle seven eighths of the time (the pipeline bubble). The bubble fills only when several batches are in flight at once, one per stage: engines keep as many micro-batches running as there are stages (vLLM v0.31.0: "PP requires PP-size concurrent batches to fill the pipeline", config/vllm.py L592-602). With 64 users in eight micro-batches every stage is busy, and throughput matches eight replicas, but each user still waits for the whole pipeline every token.

When it matters: across servers. vLLM's guidance is explicit: "Set tensor_parallel_size to the number of GPUs per node and pipeline_parallel_size to the number of nodes", for example TP 8 and PP 2 on two 8-GPU servers; and pipeline parallelism without tensor parallelism when a model must be split unevenly or the GPUs have no NVLink, such as L40S (vLLM v0.31.0 docs, Parallelism and Scaling). Llama 3.1 405B in BF16 (810 GB) on H100s (640 GB per server) is the textbook case.

How to check it: --pipeline-parallel-size in vLLM, --pp-size in SGLang. Watch per-stage utilisation: an idle stage means too few requests in flight, or uneven stages (a stage holding the embedding or the output layer does more work).

5. Expert parallelism: the experts spread over many GPUs

A mixture-of-experts (MoE) model replaces each layer's MLP with many smaller MLPs, the experts, and a small router that sends each token to a few of them. DeepSeek-V3 (and R1) has 256 routed experts per MoE layer, picks 8 per token, and has 58 MoE layers: 671 billion parameters in all, 37.6 billion used per token as the hardware root's calculator counts them from the config.json (DeepSeek rounds to 671B and 37B). Most of the weights are experts, and any one token touches a few percent of them.

The idea: give each GPU a few experts and send every token to the GPUs that hold its experts. The attention layers usually run data-parallel (section 2), each GPU attending over its own users. Every MoE layer then needs two all-to-alls: dispatch (each token's hidden state to its 8 experts' GPUs) and combine (the 8 results back).

bytes per token per MoE layer = k × hidden × (1 byte FP8 dispatch + 2 bytes BF16 combine)

DeepSeek-V3: 8 × 7,168 × 3 = per token per layer; over 58 MoE layers, per token, about twice what tensor parallelism moves for the dense 70B model. FP8 dispatch and BF16 combine are what DeepSeek uses (inference system overview). derived

Unlike tensor parallelism, the traffic is per token routed, and much of it can be overlapped: while one micro-batch's tokens are in flight, another micro-batch computes (DeepSeek's "dual-batch overlap"). That is why expert parallelism can cross servers where tensor parallelism cannot, and why there are special communication libraries for it. DeepEP, DeepSeek's, had "normal" kernels for prefill (large batches, bandwidth-bound) and "low-latency" kernels for decode (pure RDMA); on H800s with 400 Gb/s cards its v1 README reported dispatch of 128 tokens in 77 µs at EP 8 and 194 µs at EP 256 (DeepEP v1.2.1 README, 2025-09-16, vendor; the current README is a rewrite, "V2.5", without these tables). vLLM exposes the same split as --all2all-backend deepep_high_throughput or deepep_low_latency (config/parallel.py L44-56).

The catch: the busiest GPU sets the pace

The router decides where tokens go, not the scheduler, and some experts are far more popular than others. Every GPU must finish its experts before the combine, so a step lasts as long as the most loaded GPU. Measured on a real MoE here (IBM's Granite 3.1 1B-A400M, 32 experts, 8 per token, on WikiText-2): The Expert balancer tab shows every layer.

Redundant experts are the fix DeepSeek published: copy the hottest experts onto extra slots and pack the copies so every GPU carries about the same load. Their EPLB (Expert Parallelism Load Balancer) does it greedily from recent load statistics: replicate whichever expert has the highest load per copy until the slots run out, then fill GPUs heaviest-first. A hierarchical variant first balances groups of experts across servers (for prefill), a global one ignores groups (for decode). The DeepSeek page steps through the README's worked example; the Expert balancer runs the unchanged code on the measured routing. vLLM turns it on with --enable-eplb.

What a production deployment looks like

DeepSeek's own V3/R1 service, as of February 2025 vendor: prefill units of 4 servers (32 H800s, expert parallelism 32, each GPU holding 9 routed experts and 1 shared expert, with 32 redundant experts) and decode units of 18 servers (144 GPUs, expert parallelism 144, 2 routed experts and 1 shared expert per GPU), so prefill and decode are also disaggregated (section 6). They reported about 73.7k input tokens per second per server during prefill and 14.8k output tokens per second per server during decode, and a 545% theoretical cost-profit margin at R1 prices that their actual revenue did not reach (inference system overview, 2025-03-01). The open re-creations of this layout (SGLang on 96 H100s, llm-d's wide-EP path, TensorRT-LLM's wide-EP on GB200 NVL72) are on SGLang and in section 8. TensorRT-LLM's team adds a caution worth repeating: "if the MoE GroupGEMM computation is not the bottleneck, then large-scale EP may not help much" (wide-EP blog, part 1, vendor).

6. Splitting prefill from decode

The problem. The two phases of a request want different things. Prefill computes the whole prompt at once and is limited by compute; decode makes one token per user per step and is limited by memory bandwidth (the parent page, section 1). In one engine they share every step, so a long prompt arriving makes every running user wait: the parent's section 4 showed it, and Batching, KV cache and scheduling in depth (section 5) measured it on llama-server, where a 2,048-token chunk budget let one prompt freeze running streams for 2.66 s. Chunked prefill cuts the prompt into pieces and so trades long stalls for many shorter ones; it cannot remove them.

The idea of disaggregated serving: run prefill on some GPUs and decode on others. A request is prefilled on a prefill engine, which produces the first token and the request's whole KV cache; the cache is copied to a decode engine, which produces every later token. Decode engines never see a prompt, so their users never stall; each pool gets its own parallelism and batch size. The same two H200s, both ways:

Read the counters together. Disaggregation removes the pause, and the new user even gets the first token sooner (no decode work rides in the prefill step), but the decode GPU now carries 64 users, so everyone's normal time per token rises from to ms, and the prefill GPU sits idle between prompts. Whether that trade wins depends on the traffic and the targets: section 7.

What moving the cache costs

The KV cache of one request is (prompt tokens) × (KV bytes per token). For the running example that is 2,000 × 320 KiB = MiB, which takes ms over one 400 Gb/s network card at full speed, about 3% of the ms the prefill itself takes. Engines also send the cache layer by layer while prefill is still running, so most of the transfer hides behind compute. Try other models and links:

How the cache moves. Every engine has a pluggable transport. vLLM v0.31.0 registers 17 KV connectors, among them NixlConnector (NVIDIA's NIXL library over RDMA or NVLink), MooncakeConnector, LMCacheConnectorV1, OffloadingConnector and ExampleConnector, which writes the cache to shared files (kv_connector/factory.py L153-246); its documentation still labels the feature experimental. SGLang v0.5.21 offers six transfer backends with Mooncake the default and NIXL the other common one (arg_groups/choices.py L120-127); TensorRT-LLM's current documentation sends the cache over NIXL. NIXL (NVIDIA Inference Xfer Library) abstracts "various types of memory (e.g., CPU and GPU) and storage (e.g., file, block and object store)" behind one point-to-point API, with UCX, GPUDirect Storage, Mooncake, libfabric and object-store plug-ins; it runs on Linux only (README, v1.5.0, 2026-09-30).

Ratio. How many prefill GPUs per decode GPU? TensorRT-LLM's guide states the rule: choose the ratio so that "aggregated throughput of context servers matches the aggregated throughput of generation servers" (disaggregated serving blog). The right ratio moves with prompt and answer lengths, which is why Dynamo and llm-d add planners that resize the two pools as traffic changes (section 8).

7. When disaggregation pays

Measure goodput, not throughput. DistServe's measure: the highest request rate at which a target share of requests (90% here) meets both the time-to-first-token and the time-per-output-token targets, per GPU (Batching, KV cache and scheduling in depth, section 7, owns the definition and its scheduling side). Throughput that breaks the targets is not useful. The DistServe paper's own worked example shows why splitting can win on this measure (Zhong et al. 2024, section 1, a 13B model on A100s, the authors' figures):

Colocated

The win comes from removing interference, so it is largest exactly when interference hurts most: strict per-token targets and long prompts. With loose targets, colocated engines with chunked prefill use every GPU for prompts and every GPU for decoding, and nothing is stranded in an idle pool.

8. The serving layer: Dynamo, llm-d, TensorRT-LLM, Triton, KServe, Ray Serve

An engine (vLLM, SGLang, TensorRT-LLM) runs a model on a fixed set of GPUs. Once there are many engines, something has to choose which engine gets each request, move caches between them, start and stop them, and hide all of it behind one API. That is the serving layer. The products below sit at different heights in that stack, and their names are confusing, so first the map. Announced at GTC on 2025-03-18 (first release v0.1.0 the same day), 1.0 on 2026-03-13, v1.5.1 on 2026-10-07 (releases). The README calls it "the orchestration layer above inference engines": "it doesn't replace SGLang, TensorRT-LLM, or vLLM, it turns them into a coordinated multi-node inference system", "Built in Rust for performance, Python for extensibility" (README). Its parts:

RouterPicks the worker with the lowest cost: prompt blocks it would still have to compute (minus the blocks already cached on that worker, counting GPU, host and disk hits) scaled by a weight, plus the decode blocks it already carries. Optional softmax sampling instead of always the minimum.

The router's cost, quoted from the routing concepts doc (main, 2026-10-09): cost = prefill_load_scale × max(0, active_prefill_blocks + incoming_prompt_blocks − overlap_credit_blocks) + active_decode_blocks + incoming_active_blocks, plus an optional per-request term whose weight defaults to 0. Prefix-aware and load-aware routing in one number: a worker that already caches most of the prompt wins unless it is much busier.

NVIDIA's claims, all vendor and with their conditions. At launch: "increased the number of requests served by up to 30x" for DeepSeek-R1 on GB200 NVL72 with disaggregation (TensorRT-LLM, FP4, 32K in and 8K out, a figure labelled "Projected performance subject to change"), and "more than doubled the throughput" for Llama 70B on Hopper (vLLM, FP8, 3K in and 50 out; TP8 DP2 aggregated against prefill TP2 DP4 plus decode TP8) (GTC 2025 blog). The current README adds "7x higher throughput per GPU" for DeepSeek R1 on GB200 NVL72 with Dynamo against B200 without, citing SemiAnalysis InferenceX: a comparison across two different systems, so it measures the rack as much as the software.

llm-d

Launched in May 2025 by Red Hat, Google Cloud, IBM Research, CoreWeave and NVIDIA; accepted as a CNCF Sandbox project, announced 2026-03-24 (CNCF blog); v0.10.0 on 2026-09-29. Where Dynamo is engine-agnostic and NVIDIA-led, llm-d is Kubernetes-first and built around vLLM. Its documentation is a set of "well-lit paths", tested recipes: an optimised baseline, routing by predicted latency, precise prefix-cache-aware routing, a tiered prefix cache, prefill/decode disaggregation, wide expert parallelism for MoE models, flow control and fairness, autoscaling, and more (well-lit paths).

Its router is a Kubernetes building block worth knowing by name. The Gateway API Inference Extension (GAIE, a Kubernetes SIG project, v1.6.2 on 2026-09-17) defines an InferencePool resource and lets any Envoy-based gateway ask an Endpoint Picker (EPP) which pod should take each request. llm-d's EPP, now called the llm-d Router (v0.11.0, 2026-09-27), filters pods, gives each a score between 0 and 1 from weighted scorers (prefix-cache match length, queue depth, KV-cache utilisation, running requests, token load, predicted latency, LoRA affinity) and picks the highest sum (llm-d-router). Partner results in the README, all measured by the companies on their own deployments: 3 times the output throughput and 2 times faster TTFT from prefix-cache-aware routing over round robin (Llama 3.1 70B on 4 MI300X), up to 70% more tokens per second from disaggregation (gpt-oss on B200), and "10-30% throughput improvement with disaggregated serving on identical infrastructure" (Oracle, MI300X) vendor.

TensorRT-LLM

NVIDIA's own engine, for NVIDIA GPUs only. Until 2025 it compiled each model into a TensorRT "engine" ahead of time, per GPU type and shape limits; release 1.0 (2025-09-24) made "the PyTorch-based architecture ... stable and the default experience" (v1.0.0 notes), so models are Python code and need no compile step. It does continuous batching under the name in-flight batching ("also known as continuous batching or iteration-level batching"), paged KV, FP8 and NVFP4, speculative decoding, wide expert parallelism, and disaggregated serving with trtllm-serve disaggregated. Its disaggregation blog, all on GB200 vendor: DeepSeek R1 at 4,400 in and 1,200 out gained 1.4 to 1.8 times, 1.6 to 2.5 times with multi-token prediction, "especially at lower concurrency levels"; Qwen 3 at 8,192 in and 1,024 out 1.7 to 6.11 times; the gains are largest "for workloads with long input sequences and moderate output lengths where interference is most severe" (blog). MLPerf's NVIDIA submissions run on it (the parent's Capacity planner uses HPE's 8×H200 TensorRT-LLM run).

Triton Inference Server, and the three Tritons

Three unrelated things share the name: Triton Inference Server, NVIDIA's general model server (this section); OpenAI's Triton, a Python language for writing GPU kernels (Triton and Gluon); and the moon. NVIDIA renamed the server: "As of March 18, 2025, NVIDIA Triton Inference Server is now part of the NVIDIA Dynamo Platform and has been renamed to NVIDIA Dynamo Triton" (NVIDIA blog note); the product page says "Dynamo-Triton, formerly NVIDIA Triton Inference Server" and presents Dynamo as a separate product for LLMs. GitHub still calls it Triton Inference Server; v2.73.0 matches the 26.09 NGC container (2026-09-30), a monthly cadence.

It serves any model from many frameworks behind one endpoint: back ends for TensorRT, ONNX Runtime, PyTorch, TensorFlow, OpenVINO, Python, DALI, FIL (tree models), TensorRT-LLM and vLLM; ensembles and Python business-logic scripts chain models server-side (tokenize, embed, rerank, classify); a model repository with versions and hot reload; Prometheus metrics; Model Analyzer to search configurations. Its dynamic batcher is the classic one: it holds requests for up to max_queue_delay_microseconds hoping to fill a batch, then sends the batch as is, and that batch runs to completion (batcher.md). That is request-level batching, the static batching the parent page warns against for LLMs: dynamic batching is not continuous batching. For LLMs Triton hands the batching to its TensorRT-LLM back end's in-flight batcher, or to vLLM. Use it when one serving substrate must carry a mixed zoo (recommenders, vision, tree models, embedders and the odd LLM); for a pure LLM API it adds little over the engines' own servers.

KServe and Ray Serve

KServe is Kubernetes' general model-serving project (CNCF incubating, announced 2025-11-11; v0.21.0 on 2026-09-25). For LLMs it adds an LLMInferenceService resource (serving.kserve.io/v1alpha2) that "provides the integration with llm-d to support disaggregated serving, pre-fix caching, intelligent scheduling, variant autoscaling" (CNCF post); its samples set data, expert and tensor parallelism in the spec and pass NixlConnector to vLLM. Ray Serve LLM runs vLLM engines on a Ray cluster from Python: "tensor, pipeline, expert, and data parallel attention", prefill/decode disaggregation since Ray 2.47 (2025-06-12) with NIXL or LMCache connectors, and prefix-aware and KV-aware routers (Ray docs). vLLM itself is a common engine under both, and also uses Ray for multi-node runs.

9. Choosing a layout, and checking it

A procedure that works for most deployments, in order:

  1. Fit. Weights plus a useful cache on one GPU? If not, tensor parallelism inside the server up to the number of KV heads (and the NVLink domain); past one server, add pipeline stages (dense models) or expert parallelism (MoE models).
  2. Latency floor. The fastest one token can be is weight bytes per GPU divided by its memory bandwidth, plus fixed per-step work. If the per-token target is below that, raise tensor parallelism; replicas cannot help.
  3. Cache. Count the conversations that fit (the parent's Capacity planner does it). If too few, a higher TP degree often beats more replicas because the weights are paid once (section 1).
  4. Traffic. Replicate the unit until the traffic fits, with a prefix-aware router if prompts repeat.
  5. Interference. Only now consider disaggregation: long prompts, a strict time-per-token target, and enough traffic to keep a separate prefill pool busy. Simulate or measure before committing (section 7).

Common mistakes

Expecting N GPUs of tensor parallelism to make a token N times faster
Fixed per-step work and the all-reduces do not shrink: the running example goes 3.6 times faster on 8 GPUs (section 1). Measure at batch 1 before promising a latency.
Using pipeline parallelism to cut latency
A request still visits every stage in turn. Pipeline stages add capacity across slow links, never speed for one user.
Running tensor parallelism across servers over the network
The all-reduces cannot overlap with compute and the link is nine or more times slower than NVLink each way: keep TP inside the NVLink domain and put PP or EP across it.
Replicas behind round robin for a chat product
Each replica has its own cache, so round robin scatters every conversation and pays its prefix again. Route by prefix (or by session) and watch the hit rate.
Calling an MoE deployment balanced because the average load is even
The step waits for the busiest GPU in each batch, and small batches are far less even than the day's totals (Expert balancer). Judge balance per batch, on traffic the balancer did not see.
Disaggregating because the papers report big gains
The gains are for strict per-token targets, long prompts and well-matched pools. With loose targets colocated engines with chunked prefill often serve more (section 7; vLLM's own docs: "Disaggregated prefill DOES NOT improve throughput").
Fixing the prefill-to-decode ratio once
The right ratio moves with prompt and answer lengths. A ratio sized for chat strands GPUs when traffic turns to long documents; that is what Dynamo's planner and llm-d's autoscaling are for.
Treating Triton's dynamic batching as continuous batching
The dynamic batcher groups whole requests and runs each batch to completion. For LLMs the TensorRT-LLM or vLLM back end does the in-flight batching.
Reading a vendor's "30x" as a software speed-up
Dynamo's launch figure compared different parallel layouts on a GB200 NVL72 rack and was labelled projected; the README's "7x" compares GB200 NVL72 with Dynamo against B200 without. Ask what changed besides the software.

Interview questions, with short answers

Tensor or pipeline parallelism for serving a 70B model on one 8-GPU server?
Tensor parallelism: it lowers time per token (each GPU reads an eighth of the weights) and frees memory for cache, and NVLink carries its two all-reduces per layer. Pipeline parallelism would add capacity but no speed for any user. Go past 8 only with stages or experts across servers.
Why does tensor parallelism stay inside one server?
Each layer ends in all-reduces whose result the next matrix multiplication needs, so they cannot be overlapped, and their share of the step does not shrink with batch size. Between servers a 400 Gb/s card is 50 GB/s each way against 450 GB/s for NVLink, with more latency per message.
How big is one request's KV cache for Llama 3.1 70B with a 2,000-token prompt, and how long does it take to move?
80 layers × 8 KV heads × 128 dimensions × 2 (K and V) × 2 bytes = 320 KiB per token, so 625 MiB; about 13 ms at 50 GB/s (a 400 Gb/s card), about 1.5 ms over NVLink. Prefill of that prompt takes about 420 ms on an H200, so the transfer is a few percent, and engines overlap it layer by layer.
Can you run Llama 3.1 70B at TP 16?
Only by copying KV heads: it has 8, so beyond TP 8 each head lives on two GPUs, the cache stops shrinking, and the all-reduces now cross servers. Use TP 8 with PP 2 or two replicas instead.
What is expert parallelism, and what limits it?
The experts of an MoE model are spread over GPUs; each MoE layer sends every token to its experts' GPUs and back (two all-to-alls). It is limited by the network (about 10 MB per token per pass for DeepSeek-V3) and by load imbalance: the busiest GPU sets the step time. Overlap two micro-batches to hide the traffic and replicate hot experts (EPLB) to balance load.
When does disaggregating prefill and decode pay off?
When the per-token target is strict, prompts are long relative to answers, and traffic is steady enough to size both pools. With a loose per-token target, colocated engines with chunked prefill use every GPU for prefill and usually serve more. Measure goodput, not throughput.
Define goodput.
DistServe: the highest request rate a deployment serves while a target share of requests (say 90%) meets both the time-to-first-token and the time-per-output-token targets, usually per GPU.
Triton's dynamic batching versus vLLM's continuous batching?
Dynamic batching waits briefly to group whole requests, then runs the batch to completion; continuous (in-flight) batching changes the batch every step, adding and removing sequences as they start and finish. For LLMs only the second keeps the GPU full.
Why can two GPUs with tensor parallelism hold more than twice the conversations of one?
The weights are paid once across the pair, so all the memory they freed goes to cache: for the running example 141 conversations on one H200 and 480 on two (planner model).
Design: serve DeepSeek-R1 to a chat product. Sketch the layout.
FP8 weights about 671 GB: one 8-GPU H200 server holds them. Attention data-parallel, experts spread with expert parallelism (EP 8 in a server, wider across servers with RDMA and overlap), redundant experts from EPLB, MLA keeps the cache at about 69 KiB per token. Separate prefill and decode pools if the per-token target is tight, sized by rate matching; a KV-aware router (Dynamo or llm-d) in front; autoscale the pools on queue depth and SLO attainment. Check per-batch expert balance and all-to-all time before scaling out.

What transfers to datacenter GPUs, and what does not

  • Transfers: the shape of each cost. A layer split pays per crossing, so it hurts generation (a crossing per token) far more than prompts (a crossing per batch); a tensor split pays inside every layer, so a slow link ruins it; the cache file is exactly tokens × KV bytes per token; a decode server that receives a cache recomputes nothing; two processes on one GPU still compete for it.
  • Does not transfer: the magnitudes. Loopback TCP between two Metal processes has far more per-message overhead than NVLink (a few microseconds per small all-reduce) and far less bandwidth than RDMA between servers; here both "devices" are the same GPU, so no split can be faster than one process; vLLM's CPU back end shares 4 cores among its workers. The datacenter numbers on the Reading tab come from the planner and published measurements, not from these runs.
