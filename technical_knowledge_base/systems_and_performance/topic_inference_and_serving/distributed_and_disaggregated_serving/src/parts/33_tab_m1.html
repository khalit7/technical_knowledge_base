No NVIDIA GPU here, so the splits of the Reading tab were run at laptop scale: one Apple M1 Pro (16 GB unified memory, one GPU) and the 5 CPUs Docker Desktop gives vLLM's CPU image. Two processes on one machine share one GPU and talk over loopback TCP or shared memory, which is slower in latency than NVLink and in a different league for bandwidth, so the numbers show how each mechanism behaves, not how fast a datacenter runs it. Every run was repeated; the spread is shown; the machine was shared with other agents, so load averages are recorded.

1. One model, two processes: split by layers or by tensors (llama.cpp RPC)

llama.cpp build 11146 (commit 7fe450e19) compiled here with its RPC back end. A second process, ggml-rpc-server, exposes the same Metal GPU over TCP on localhost; llama-bench then splits the model half and half between its own Metal device and the remote one: -sm layer (pipeline: each device holds half the layers, one hidden state crosses per token) or -sm tensor (each device holds half of every weight matrix; experimental). Prompt processing of 512 tokens (pp512) and generation of 64 (tg64), tokens per second.

2. vLLM's CPU engine with tensor and pipeline parallelism

vLLM v0.31.0 CPU image (arm64), Qwen3-0.6B in float32, cores 0 to 3 of the Docker VM for the container (one worker bound to all four, or two workers bound to two each with VLLM_CPU_OMP_THREADS_BIND: vLLM’s automatic binding wants one NUMA node per worker and refused to start two workers on this one-node VM), the parent's bench load generator (closed loop, 300-word prompts, 64 output tokens): 1 user, then 8 users. TP 2 runs two worker processes, each with half of every layer, joined by vLLM's CPU communicator; PP 2 gives each worker half the layers.

3. Handing a KV cache from a prefill server to a decode server

Two llama-server processes (Homebrew build 11146, Metal), Qwen3-1.7B Q8_0 with an F16 cache, prompt cache off. Server P computes a prompt and saves slot 0's cache to a file (POST /slots/0?action=save); server D loads the file into its slot 0 (action=restore) and answers 64 tokens reusing it; then D forgets the cache and computes the same prompt itself, for comparison. This is disaggregation through shared storage, the same idea as vLLM's ExampleConnector, with a disk instead of a network.

4. Does a separate prefill process protect a decode stream on the same GPU?

A stream of 300 tokens runs on server D. After 60 tokens, a 3,000-word prompt arrives, either at D itself (colocated, its second slot) or at server P (another process on the same GPU). Every token's arrival time is recorded; the chart shows the gaps between consecutive tokens (the final end-of-stream message left out).

What transfers to datacenter GPUs, and what does not

  • Transfers: the shape of each cost. A layer split pays per crossing, so it hurts generation (a crossing per token) far more than prompts (a crossing per batch); a tensor split pays inside every layer, so a slow link ruins it; the cache file is exactly tokens × KV bytes per token; a decode server that receives a cache recomputes nothing; two processes on one GPU still compete for it.
  • Does not transfer: the magnitudes. Loopback TCP between two Metal processes has far more per-message overhead than NVLink (a few microseconds per small all-reduce) and far less bandwidth than RDMA between servers; here both "devices" are the same GPU, so no split can be faster than one process; vLLM's CPU back end shares 4 cores among its workers. The datacenter numbers on the Reading tab come from the planner and published measurements, not from these runs.
