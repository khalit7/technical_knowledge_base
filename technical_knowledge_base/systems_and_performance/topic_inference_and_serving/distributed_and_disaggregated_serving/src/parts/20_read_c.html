3. Tensor parallelism: every GPU holds a slice of every layer

The problem: one GPU reads the weights too slowly for the latency target, or holds too little cache. The idea (Megatron-LM, 2019; {{paper page|n:3c65c17b0d0d8133ae92fbe90a1f308e}}): cut each weight matrix across GPUs so each GPU does a slice of every matrix multiplication. In attention the query, key and value projections are split by heads, so each GPU computes its own heads with its own share of the KV cache; the output projection is split by rows, so each GPU ends with a partial sum of the layer's output. The MLP works the same way: the first matrix split by columns, the second by rows. Two partial sums per layer have to be added up across all GPUs before the next layer can start: two all-reduces per layer, every step.

bytes each GPU sends per all-reduce (ring) = 2 (t − 1) / t × hidden size × 2 bytes × tokens in the step

Running example: hidden size 8,192, so one token's activation is 16 KiB. At TP 8 each GPU sends per all-reduce, and a token needs 2 × 80 = 160 of them: per token per GPU. derived

At batch 1 those messages are tiny and the cost is latency, not bandwidth: each all-reduce is a round of synchronisation that takes microseconds however few bytes it carries. The planner charges about 6.7 µs per small all-reduce (two NVLink hops of 3.33 µs, from {{DeepSeek's ISCA 2025 paper, Table 5|https://arxiv.org/html/2505.09343}}), so 160 of them cost about 1.1 ms per token, a sixth of the whole step at TP 8. What to take from it. With one user, TP 8 makes the token times faster; replicas and pipeline stages make it no faster at all. With 64 users the picture changes: eight replicas give each user a GPU-eighth of the traffic but each copy still reads all 72.7 GB per step for only 8 users, while TP 8 reads each weight once for all 64; at equal users, TP 8 delivers tokens per second against for the replicas. The replicas win back when traffic is high enough to fill each copy's batch: that is the throughput-against-latency trade of the parent page's {{Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}, which searches it for you (try TP 1 against TP 2 there).

Why tensor parallelism stays inside one server

Every all-reduce sits between two matrix multiplications that need its result, so it cannot be hidden behind other work, and its cost does not shrink with batch size relative to the compute. It needs the fastest link there is: NVLink gives an H100 900 GB/s counting both directions, 450 GB/s each way ({{NVIDIA|https://www.nvidia.com/en-us/data-center/nvlink/}}, vendor spec); a 400 Gb/s network card moves 50 GB/s each way, nine times less, with several microseconds more latency per message. {{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}} (section 9) works the ratio out for this model and finds tensor parallelism over a network card would leave the GPUs waiting most of the time. Hence the rule every engine's documentation repeats: tensor parallelism within the NVLink domain (8 GPUs in an HGX server, 72 in a GB200 NVL72 rack), pipeline or expert parallelism across it.

Two limits that are easy to miss. The KV cache is split by heads, and Llama 3.1 70B has 8 key/value heads: at TP 8 each GPU owns one, and beyond 8 the heads must be copied, so the cache stops shrinking. And the engine needs the head counts to divide evenly by the TP degree (vLLM refuses to start otherwise: "Total number of attention heads ... must be divisible by tensor parallel size", {{config/model.py L1504-1509|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/model.py}}).

How to check it: vLLM --tensor-parallel-size 8; SGLang --tp-size 8; TensorRT-LLM tensor_parallel_size. Measure time per output token at batch 1 against TP 1; if it improves much less than the planner predicts, profile the all-reduces (NCCL logs which link it used: {{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}}, section 10) and check that CUDA graphs are on, since launch overhead grows with every extra collective.
