3. Tensor parallelism at serve time: latency, inside one server

Tensor parallelism cuts every weight matrix across GPUs (Megatron-LM's split, column then row, heads divided among GPUs; the form is on {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}} and the {{Megatron-LM paper page|n:3c65c17b0d0d8133ae92fbe90a1f308e}}). At serve time three things differ from training. There are no gradients, so the only traffic is two all-reduces per layer, every decode step. Each GPU keeps the KV cache of its own heads, so the cache per GPU shrinks too. And the step is tiny: at batch 1 the messages carry a few kilobytes, so the cost is synchronisation latency, not bandwidth.

bytes each GPU sends per all-reduce (ring) = 2 (t − 1) / t × hidden size × 2 bytes × tokens in the step

Running example: hidden size 8,192, so one token's activation is 16 KiB. At TP 8 each GPU sends per all-reduce, and a token needs 2 × 80 = 160 of them: per token per GPU. The planner charges about 6.7 µs per small all-reduce (two NVLink hops of 3.33 µs, from {{DeepSeek's ISCA 2025 paper, Table 5|https://arxiv.org/html/2505.09343}}), so 160 of them cost about 1.1 ms per token, a sixth of the whole step at TP 8. derived

Fig. 3a draws the 80 layers as eight glass slabs of ten and one server's eight H200s; step times from the planner, derived.

  1. One GPU holds everything. All 80 layers sit on one H200: 72.7 GB of weights read once per step, one user's token in 21.6 ms, and the other seven GPUs idle.
  2. Cut every layer eight ways. Each GPU now holds one eighth of every layer, 9.1 GB, and the KV cache of one of the model's 8 key/value heads.
  3. Two all-reduces per layer. Each layer ends with the GPUs summing their partial results: 28 KiB sent per GPU per all-reduce, 160 per token, 4.59 MB in all, about 1.1 ms of waiting.
  4. Faster, but not eight times. One token now takes 6.0 ms: the weight reading shrank from 19.1 ms to 2.4 ms, the 2.5 ms of fixed work per step did not, and the all-reduces added 1.1 ms.
  5. Only inside the NVLink domain. NVLink moves 450 GB/s each way per GPU; a 400 Gb/s card between servers moves 50 GB/s, nine times less, and every one of the 160 all-reduces per token would wait on it.

Why it stays inside one server. Every all-reduce sits between two matrix multiplications that need its result, so it cannot hide behind other work. NVLink gives an H100 900 GB/s counting both directions, 450 GB/s each way ({{NVIDIA|https://www.nvidia.com/en-us/data-center/nvlink/}}, vendor spec); a 400 Gb/s network card moves 50 GB/s each way, nine times less, with several microseconds more latency per message; {{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}} (section 9) works the ratio out for this model. Hence the rule every engine's documentation repeats: tensor parallelism within the NVLink domain (8 GPUs in an HGX server, 72 in a GB200 NVL72 rack), pipeline or expert parallelism across it.

Two serve-time limits. The KV cache is split by heads, and Llama 3.1 70B has 8 key/value heads: at TP 8 each GPU owns one, and beyond 8 the heads must be copied, so the cache stops shrinking (TP 16 would also push the all-reduces across servers: use TP 8 with PP 2, or two replicas). And the head counts must divide evenly by the TP degree (vLLM refuses to start otherwise: "Total number of attention heads ... must be divisible by tensor parallel size", {{config/model.py L1504-1509|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/model.py}}).

How to check it: vLLM --tensor-parallel-size 8; SGLang --tp-size 8; TensorRT-LLM tensor_parallel_size. Measure time per output token at batch 1 against TP 1; if it improves much less than the planner predicts, profile the all-reduces (NCCL logs which link it used: {{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}}, section 10) and check that CUDA graphs are on, since launch overhead grows with every extra collective.

4. Pipeline parallelism at serve time: capacity, across servers

Pipeline parallelism cuts the model by depth: with 8 stages, GPU 0 holds layers 1 to 10, GPU 1 layers 11 to 20, and so on, each stage with the KV cache of its own layers. A token's hidden state, 16 KiB for this model, is the only thing that crosses a boundary: any network can carry that. At serve time there is no backward pass and no 1F1B schedule to design; what remains is that a single request walks the stages one after another, so it gets no faster: pipeline parallel 8 takes the same time per token as one GPU (Fig. 3b, step 2, and Fig. 4), and each GPU is idle seven eighths of the time (the pipeline bubble). The bubble fills only when several batches are in flight at once, one per stage (vLLM v0.31.0: "PP requires PP-size concurrent batches to fill the pipeline", {{config/vllm.py L592-602|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/vllm.py}}). With 64 users in eight micro-batches every stage is busy and throughput matches eight replicas, but each user still waits for the whole pipeline every token.

  1. Cut by depth. GPU 0 holds layers 1 to 10, GPU 1 layers 11 to 20, and so on: 9.1 GB of weights each, and the KV cache of its own layers.
  2. One user walks the stages. The token's 16 KiB hidden state crosses each boundary in turn: one token takes 21.4 ms, as on one GPU, and each GPU works one eighth of the time.
  3. Fill the pipeline. With 64 users in eight micro-batches, one per stage, every stage is busy: 2,796 tokens per second, the same as eight replicas, but each user still waits for all eight stages, 22.9 ms per token.
  4. Across servers. Tensor parallel 8 inside each server and pipeline parallel 2 between two servers: only the 16 KiB hidden state per token crosses the network, which is how Llama 3.1 405B in BF16 (810 GB) runs on two 8-GPU H100 servers.

When it matters: across servers. vLLM's guidance: "Set tensor_parallel_size to the number of GPUs per node and pipeline_parallel_size to the number of nodes", for example TP 8 and PP 2 on two 8-GPU servers; and pipeline parallelism without tensor parallelism when a model must be split unevenly or the GPUs have no NVLink, such as L40S ({{vLLM v0.31.0 docs, Parallelism and Scaling|https://github.com/vllm-project/vllm/blob/v0.31.0/docs/serving/parallelism_scaling.md}}). Llama 3.1 405B in BF16 (810 GB) on H100s (640 GB per server) is the textbook case.

How to check it: --pipeline-parallel-size in vLLM, --pp-size in SGLang. Watch per-stage utilisation: an idle stage means too few requests in flight, or uneven stages (a stage holding the embedding or the output layer does more work).

One decode step, four layouts

Predict first: which of the four layouts makes one user's token fastest, and which serves 64 users best?

  1. One GPU, one user. The whole 72.7 GB of weights is read once per step: 21.6 ms per token. The other seven GPUs wait.
  2. Eight replicas, one user. The user lands on one copy, which works exactly like the single GPU: 21.6 ms. Copies add capacity, never speed for one request.
  3. Tensor parallel 8, one user. Each GPU reads 9.1 GB, so the reading shrinks eightfold, but each of the 80 layers ends in all-reduces (1.08 ms in all): 6.0 ms per token.
  4. Pipeline parallel 8, one user. The token walks the stages one after another: 21.4 ms, as on one GPU, each GPU busy one eighth of the time.
  5. Eight replicas, 64 users. Each copy serves 8 users and still reads all 72.7 GB every step: 22.9 ms per step, 2,796 tokens per second on the eight GPUs.
  6. Tensor parallel 8, 64 users. Each weight is read once for all 64 users: 8.1 ms per step, 7,949 tokens per second.
  7. Pipeline parallel 8, 64 users. Eight micro-batches of 8 users keep every stage busy: 22.9 ms per token for each user and 2,796 tokens per second, the same as the replicas; only one 16 KiB hidden state per token crosses each boundary.

With one user, TP 8 makes the token times faster; replicas and pipeline stages make it no faster at all. With 64 users the picture changes: eight replicas give each copy 8 users but each copy still reads all 72.7 GB per step, while TP 8 reads each weight once for all 64; at equal users, TP 8 delivers tokens per second against for the replicas. The replicas win back when traffic is high enough to fill each copy's batch: the throughput-against-latency trade the parent's {{Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} searches for you (try TP 1 against TP 2 there).

What transfers to datacenter GPUs, and what does not

  • Transfers: the shape of each cost. A layer split pays per crossing, so it hurts generation (a crossing per token) far more than prompts (a crossing per batch); a tensor split pays inside every layer, so a slow link ruins it; the cache file is exactly tokens × KV bytes per token; a decode server that receives a cache recomputes nothing; two processes on one GPU still compete for it.
  • Does not transfer: the magnitudes. Loopback TCP between two Metal processes has far more per-message overhead than NVLink (a few microseconds per small all-reduce) and far less bandwidth than RDMA between servers; here both "devices" are the same GPU, so no split can be faster than one process; vLLM's CPU back end shares 4 cores among its workers. The datacenter numbers on this page come from the planner and published measurements, not from these runs.
