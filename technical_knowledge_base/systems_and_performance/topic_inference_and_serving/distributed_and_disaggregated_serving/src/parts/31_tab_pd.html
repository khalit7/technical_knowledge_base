This tab answers with the root page's {{Serving simulator|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} on the running example, for every split from 1 prefill + 7 decode to 7 + 1, three workloads, twelve pairs of latency targets and two link speeds.

What is simulated, and what is not

The model is Llama 3.1 70B with FP8 weights and a BF16 KV cache on H200s, one engine per GPU (no tensor parallelism): the root's running example. Weights and the KV pool per GPU come from the {{Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}'s memory model (); every step's duration is the simulator's roofline, with compute and memory efficiencies and per-step overheads fitted on NVIDIA's published NIM measurements of Llama 3.1 8B on an H100 (vendor figures) and applied to the H200's peak and bandwidth. Scheduling (continuous batching, paged blocks, chunked prefill with an 8,192-token budget, recompute preemption) is the simulator's, which matched vLLM v0.31.0's own scheduler step for step on the traces the root compared. Requests arrive as a Poisson process; requests per run, the first 10% left out as warm-up.

Disaggregated mode: a request goes round robin to a prefill engine, which computes its prompt; the whole cache then travels to a decode engine (round robin) as one transfer of (prompt tokens × 320 KiB) at the link's full speed, and the decode engine produces every output token after the first. Not modelled: sending the cache layer by layer while prefill runs (real systems hide most of the transfer this way), link contention, routing by load, and the decode engine's prefix cache. This mode has not been checked against a real disaggregated engine. simulated
