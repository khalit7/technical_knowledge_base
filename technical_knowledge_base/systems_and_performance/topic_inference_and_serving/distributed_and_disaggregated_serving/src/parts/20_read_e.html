6. Splitting prefill from decode

The problem. Prefill computes the whole prompt at once and is limited by compute; decode makes one token per user per step and is limited by memory bandwidth. In one engine they share every step, so a long prompt arriving makes every running user wait: {{Batching, KV cache and scheduling in depth|n:3c65c17b0d0d819db53bd2c48909e5b2}} (section 5) measured one prompt freezing running streams for 2.66 s on llama-server with a 2,048-token chunk budget. Chunked prefill cuts the prompt into pieces and so trades long stalls for many shorter ones; it cannot remove them.

The idea of disaggregated serving: a request is prefilled on a prefill engine, which produces the first token and the request's whole KV cache; the cache is copied to a decode engine, which produces every later token. Decode engines never see a prompt, so their users never stall, and each pool gets its own parallelism and batch size. Predict before you step through it: when the prompt arrives, who pays, and what does the split cost instead?

Read the counters together. Disaggregation removes the pause, and the new user even gets the first token sooner (no decode work rides in the prefill step), but the decode GPU now carries 64 users, so everyone's normal time per token rises from to ms, and the prefill GPU sits idle between prompts. Whether that trade wins depends on the traffic and the targets: section 7.

What moving the cache costs

The KV cache of one request is (prompt tokens) × (KV bytes per token; the sizing for any model is {{Long context|n:3fd5c17b0d0d81059ee1ce20c0326dc5#t-kv}}'s calculator). For the running example that is 2,000 × 320 KiB = MiB, which takes ms over one 400 Gb/s network card at full speed (about 1.5 ms over NVLink), about 3% of the ms the prefill itself takes. Engines also send the cache layer by layer while prefill is still running, so most of the transfer hides behind compute. Move the prompt length: the transfer grows with the prompt like the prefill does, so its share stays small; on a slow link it does not.

How the cache moves. Every engine has a pluggable transport. vLLM v0.31.0 registers 17 KV connectors, among them NixlConnector (NVIDIA's NIXL library over RDMA or NVLink), MooncakeConnector, LMCacheConnectorV1, OffloadingConnector and ExampleConnector, which writes the cache to shared files ({{kv_connector/factory.py L153-246|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/distributed/kv_transfer/kv_connector/factory.py}}); its documentation still labels the feature experimental. SGLang v0.5.21 offers six transfer backends with Mooncake the default and NIXL the other common one ({{arg_groups/choices.py L120-127|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/arg_groups/choices.py}}); TensorRT-LLM's current documentation sends the cache over NIXL. NIXL (NVIDIA Inference Xfer Library) abstracts "various types of memory (e.g., CPU and GPU) and storage (e.g., file, block and object store)" behind one point-to-point API, with UCX, GPUDirect Storage, Mooncake, libfabric and object-store plug-ins; it runs on Linux only ({{README|https://github.com/ai-dynamo/nixl}}, v1.5.0, 2026-09-30).

Ratio. How many prefill GPUs per decode GPU? TensorRT-LLM's guide states the rule: choose the ratio so that "aggregated throughput of context servers matches the aggregated throughput of generation servers" ({{disaggregated serving blog|https://nvidia.github.io/TensorRT-LLM/blogs/tech_blog/blog5_Disaggregated_Serving_in_TensorRT-LLM.html}}). The right ratio moves with prompt and answer lengths; a ratio sized for chat strands GPUs when traffic turns to long documents, which is why Dynamo and llm-d add planners that resize the two pools as traffic changes (section 8).
