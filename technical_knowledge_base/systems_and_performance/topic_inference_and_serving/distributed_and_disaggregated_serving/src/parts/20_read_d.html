4. Pipeline parallelism: every GPU holds a run of whole layers

The problem: the model does not fit in one server, and the link between servers is too slow for tensor parallelism. The idea: cut the model by depth. With 8 stages, GPU 0 holds layers 1 to 10, GPU 1 layers 11 to 20, and so on; each stage also holds the KV cache of its own layers. A token's hidden state, 16 KiB for this model, is the only thing that crosses a boundary, once per stage: any network can carry that.

The cost: a single request walks the stages one after another, so it gets no faster: in the animation above, pipeline parallel 8 takes the same time per token as one GPU, and each GPU is idle seven eighths of the time (the pipeline bubble). The bubble fills only when several batches are in flight at once, one per stage: engines keep as many micro-batches running as there are stages (vLLM v0.31.0: "PP requires PP-size concurrent batches to fill the pipeline", {{config/vllm.py L592-602|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/vllm.py}}). With 64 users in eight micro-batches every stage is busy, and throughput matches eight replicas, but each user still waits for the whole pipeline every token.

When it matters: across servers. vLLM's guidance is explicit: "Set tensor_parallel_size to the number of GPUs per node and pipeline_parallel_size to the number of nodes", for example TP 8 and PP 2 on two 8-GPU servers; and pipeline parallelism without tensor parallelism when a model must be split unevenly or the GPUs have no NVLink, such as L40S ({{vLLM v0.31.0 docs, Parallelism and Scaling|https://github.com/vllm-project/vllm/blob/v0.31.0/docs/serving/parallelism_scaling.md}}). Llama 3.1 405B in BF16 (810 GB) on H100s (640 GB per server) is the textbook case.

How to check it: --pipeline-parallel-size in vLLM, --pp-size in SGLang. Watch per-stage utilisation: an idle stage means too few requests in flight, or uneven stages (a stage holding the embedding or the output layer does more work).

5. Expert parallelism: the experts spread over many GPUs

A mixture-of-experts (MoE) model replaces each layer's MLP with many smaller MLPs, the experts, and a small router that sends each token to a few of them. DeepSeek-V3 (and R1) has 256 routed experts per MoE layer, picks 8 per token, and has 58 MoE layers: 671 billion parameters in all, 37.6 billion used per token as the hardware root's calculator counts them from the {{config.json|https://huggingface.co/deepseek-ai/DeepSeek-V3/blob/main/config.json}} (DeepSeek rounds to 671B and 37B). Most of the weights are experts, and any one token touches a few percent of them.

The idea: give each GPU a few experts and send every token to the GPUs that hold its experts. The attention layers usually run data-parallel (section 2), each GPU attending over its own users. Every MoE layer then needs two all-to-alls: dispatch (each token's hidden state to its 8 experts' GPUs) and combine (the 8 results back).

bytes per token per MoE layer = k × hidden × (1 byte FP8 dispatch + 2 bytes BF16 combine)

DeepSeek-V3: 8 × 7,168 × 3 = per token per layer; over 58 MoE layers, per token, about twice what tensor parallelism moves for the dense 70B model. FP8 dispatch and BF16 combine are what DeepSeek uses ({{inference system overview|https://github.com/deepseek-ai/open-infra-index/blob/main/202502OpenSourceWeek/day_6_one_more_thing_deepseekV3R1_inference_system_overview.md}}). derived

Unlike tensor parallelism, the traffic is per token routed, and much of it can be overlapped: while one micro-batch's tokens are in flight, another micro-batch computes (DeepSeek's "dual-batch overlap"). That is why expert parallelism can cross servers where tensor parallelism cannot, and why there are special communication libraries for it. DeepEP, DeepSeek's, had "normal" kernels for prefill (large batches, bandwidth-bound) and "low-latency" kernels for decode (pure RDMA); on H800s with 400 Gb/s cards its v1 README reported dispatch of 128 tokens in 77 µs at EP 8 and 194 µs at EP 256 ({{DeepEP v1.2.1 README|https://github.com/deepseek-ai/DeepEP/blob/v1.2.1/README.md}}, 2025-09-16, vendor; the current README is a rewrite, "V2.5", without these tables). vLLM exposes the same split as --all2all-backend deepep_high_throughput or deepep_low_latency ({{config/parallel.py L44-56|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/parallel.py}}).

The catch: the busiest GPU sets the pace

The router decides where tokens go, not the scheduler, and some experts are far more popular than others. Every GPU must finish its experts before the combine, so a step lasts as long as the most loaded GPU. Measured on a real MoE here (IBM's Granite 3.1 1B-A400M, 32 experts, 8 per token, on WikiText-2): The {{Expert balancer|#t-ep}} tab shows every layer.

Redundant experts are the fix DeepSeek published: copy the hottest experts onto extra slots and pack the copies so every GPU carries about the same load. Their {{EPLB|https://github.com/deepseek-ai/EPLB}} (Expert Parallelism Load Balancer) does it greedily from recent load statistics: replicate whichever expert has the highest load per copy until the slots run out, then fill GPUs heaviest-first. A hierarchical variant first balances groups of experts across servers (for prefill), a global one ignores groups (for decode). The {{DeepSeek page|n:3c65c17b0d0d81a2ae7ec6796947a235}} steps through the README's worked example; the {{Expert balancer|#t-ep}} runs the unchanged code on the measured routing. vLLM turns it on with --enable-eplb.

What a production deployment looks like

DeepSeek's own V3/R1 service, as of February 2025 vendor: prefill units of 4 servers (32 H800s, expert parallelism 32, each GPU holding 9 routed experts and 1 shared expert, with 32 redundant experts) and decode units of 18 servers (144 GPUs, expert parallelism 144, 2 routed experts and 1 shared expert per GPU), so prefill and decode are also disaggregated (section 6). They reported about 73.7k input tokens per second per server during prefill and 14.8k output tokens per second per server during decode, and a 545% theoretical cost-profit margin at R1 prices that their actual revenue did not reach ({{inference system overview|https://github.com/deepseek-ai/open-infra-index/blob/main/202502OpenSourceWeek/day_6_one_more_thing_deepseekV3R1_inference_system_overview.md}}, 2025-03-01). The open re-creations of this layout (SGLang on 96 H100s, llm-d's wide-EP path, TensorRT-LLM's wide-EP on GB200 NVL72) are on {{SGLang|n:3c65c17b0d0d81e691e4ce9f9b5d1fad}} and in section 8. TensorRT-LLM's team adds a caution worth repeating: "if the MoE GroupGEMM computation is not the bottleneck, then large-scale EP may not help much" ({{wide-EP blog, part 1|https://github.com/NVIDIA/TensorRT-LLM/blob/main/docs/source/blogs/tech_blog/blog04_Scaling_Expert_Parallelism_in_TensorRT-LLM.md}}, vendor).
