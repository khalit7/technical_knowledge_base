9. Choosing a layout, and checking it

A procedure that works for most deployments, in order:

  1. Fit. Weights plus a useful cache on one GPU? If not, tensor parallelism inside the server up to the number of KV heads (and the NVLink domain); past one server, add pipeline stages (dense models) or expert parallelism (MoE models).
  2. Latency floor. The fastest one token can be is weight bytes per GPU divided by its memory bandwidth, plus fixed per-step work. If the per-token target is below that, raise tensor parallelism; replicas cannot help.
  3. Cache. Count the conversations that fit (the parent's {{Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} does it). If too few, a higher TP degree often beats more replicas because the weights are paid once (section 1).
  4. Traffic. Replicate the unit until the traffic fits, with a prefix-aware router if prompts repeat.
  5. Interference. Only now consider disaggregation: long prompts, a strict time-per-token target, and enough traffic to keep a separate prefill pool busy. Simulate or measure before committing (section 7).

Depth

Mistakes that look reasonable (four)
  • Calling an MoE deployment balanced because the average load is even. The step waits for the busiest GPU in each batch, and small batches are far less even than the day's totals (section 5). Judge balance per batch, on traffic the balancer did not see.
  • Disaggregating because the papers report big gains. The gains are for strict per-token targets, long prompts and well-matched pools; with loose targets colocated engines with chunked prefill often serve more (section 7).
  • Treating Triton's dynamic batching as continuous batching. The dynamic batcher groups whole requests and runs each batch to completion. For LLMs the TensorRT-LLM or vLLM back end does the in-flight batching.
  • Reading a vendor's "30x" as a software speed-up. Dynamo's launch figure compared different parallel layouts on a GB200 NVL72 rack and was labelled projected; the README's "7x" compares GB200 NVL72 with Dynamo against B200 without.
A design question: serve DeepSeek-R1 to a chat product (rehearsal)

FP8 weights about 671 GB: one 8-GPU H200 server holds them. Attention data-parallel, experts spread with expert parallelism (EP 8 in a server, wider across servers with RDMA and overlap), redundant experts from EPLB, MLA keeps the cache at about 69 KiB per token. Separate prefill and decode pools if the per-token target is tight, sized by rate matching; a KV-aware router (Dynamo or llm-d) in front; autoscale the pools on queue depth and SLO attainment. Check per-batch expert balance and all-to-all time before scaling out.

Corrections to the old version of this page (five)

The old page ("NVIDIA Triton Inference Server, TensorRT-LLM, and Dynamo", saved verbatim in the parent's src/read/old/) was checked claim by claim; the full list is in this page's src/coverage.md. The ones that change what you would say:

  • Dynamo's "up to 30x more requests/GPU": NVIDIA's wording is "increased the number of requests served by up to 30x", for DeepSeek-R1 on GB200 NVL72 with FP4 and 32K-in, 8K-out requests, and the figure is labelled "Projected performance subject to change". The "~2x for Llama-70B on Hopper" is "more than doubled the throughput" with vLLM, FP8, 3K in and 50 out.
  • Triton branding: not a lean but a rename, dated: Triton Inference Server "has been renamed to NVIDIA Dynamo Triton" as of 2025-03-18; GitHub still uses the old name.
  • TensorRT-LLM "1.x, 2025-2026, PyTorch runtime as the default": confirmed and dated: default from v1.0.0 (2025-09-24; first in v1.0.0rc0, 2025-06-25). The latest stable is v1.2.1 (2026-04-20). "Runtime-reconfigurable xPyD" could not be confirmed in the current documentation and is left out.
  • llm-d "CNCF/Red Hat/Google-led": launched by Red Hat, Google Cloud, IBM Research, CoreWeave and NVIDIA (May 2025), CNCF Sandbox announced 2026-03-24. Its scheduler is now the llm-d Router, which took over the endpoint picker code from the Gateway API Inference Extension.
  • "AMD maintains a ROCm port" of Triton: not confirmed in the Triton repositories read; left out.
