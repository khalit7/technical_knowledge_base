1. Why one GPU stops being enough

Four different pressures push a deployment past one GPU, and they have different fixes. Mixing them up is the most common planning mistake.

The weights do not fitLlama 3.1 405B in FP8 is about 405 GB; an H200 has 141 GB. Some split of the weights is required: tensor or pipeline parallelism, or experts spread over GPUs.
The cache for enough users does not fitEvery running conversation keeps its KV cache in GPU memory (320 KiB per token for this model). Whatever the weights leave over decides how many users run at once.
One GPU is too slow for the latency targetDecode reads every weight once per step, so one token can never come faster than weight bytes divided by memory bandwidth: 72.7 GB / 4.8 TB/s = 15 ms on an H200. A tighter target needs the weights spread over more GPUs' bandwidth.
One GPU is too slow for the trafficThe model fits and is fast enough, there is just more traffic than one GPU serves. Copies (replicas) are the answer.

In the running example the weights fit: 72.7 GB of FP8 weights (embeddings kept in BF16, as released FP8 checkpoints do) on one H200, leaving room for the cache of conversations of the average length. Split the same model over two GPUs with tensor parallelism and the pair holds : twice the GPUs, times the conversations, because the weights are paid once across the pair while all the memory they freed goes to cache.

Splitting a model is often about cache, not weights

2. Replicas, and routing for the cache

Data parallelism in serving means running several complete copies of the engine (replicas) and sending each request to one of them. Nothing crosses between copies, so capacity grows exactly with the number of copies, and so does cost; one request is served by one copy, so a replica never makes any single user faster. Real deployments are replicas of something: of one GPU (an 8B model), of a TP 8 server (a 70B model), or of a whole prefill/decode group.

What changes at serve time is the cache. Each replica keeps its own prefix cache, so a conversation that lands on another replica loses its cached prefix and pays its prefill again: round robin scatters conversations, prefix-aware routing sends a request where its prefix is cached. {{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}} (section 2) steps round robin against prefix-aware routing through eight requests on three real replicas. The question a router then has to answer is how much cache is worth how much load. NVIDIA Dynamo's router answers with one number per worker ({{routing concepts doc|https://github.com/ai-dynamo/dynamo/blob/main/docs/fern/pages/developer-guide/knowledge-base/modular-components/router/routing-concepts.md}}, main, 2026-10-09): prompt blocks the worker would still have to compute, scaled by a weight, plus the decode blocks it already carries, and the lowest cost wins.

Predict: worker A already holds 112 of the prompt's 125 blocks; worker B holds none and carries 100 decode blocks. How many decode blocks can A carry before the router sends the request to B?
About 212. With the weight at 1, each cached block is worth exactly one block of load: A wins while 13 + its load < 125 + 100. A larger weight on prefill makes cached blocks worth more.

A cached prefix is traded block for block against load

One incoming request with a 2,000-token prompt, 125 blocks of 16 tokens; A caches 112 of them (an earlier turn of the same conversation), B and C none; B and C carry 100 and 200 decode blocks; no prefill in progress; weight 1. All loads illustrative; the formula is Dynamo's.

cost = prefill_load_scale × max(0, active_prefill_blocks + incoming_prompt_blocks − overlap_credit_blocks) + active_decode_blocks + incoming_active_blocks

Quoted from Dynamo's routing doc, plus an optional per-request term whose weight defaults to 0. The overlap credit counts cached blocks on GPU, host and disk; optional softmax sampling replaces always taking the minimum. llm-d's router does the same job with weighted scorers (section 8). Routing policies in general, autoscaling and cold starts are on {{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}.

How to check: per-replica request rates and KV cache usage should be even, and the prefix hit rate high for chat; a hot replica means the router is not balancing (vLLM exports vllm:kv_cache_usage_perc and vllm:num_requests_waiting per engine; what each metric means is on {{vLLM: inside the default engine|n:3c65c17b0d0d8113b976d8bcaf2c0722}}).

A special case: data-parallel attention. In a mixture-of-experts deployment (section 5) the attention layers often run as replicas, each GPU attending over its own users with its own cache, while the experts are spread across all GPUs. vLLM does this with --data-parallel-size together with --enable-expert-parallel ({{vLLM v0.31.0 config/parallel.py L134, L172|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/parallel.py}}: "MoE layers will be sharded according to the product of the tensor, prefill-context, and data parallel sizes").
