8. The serving layer: Dynamo, llm-d, TensorRT-LLM, Triton, KServe, Ray Serve

An engine (vLLM, SGLang, TensorRT-LLM) runs a model on a fixed set of GPUs. Once there are many engines, something has to choose which engine gets each request, move caches between them, start and stop them, and hide all of it behind one API: the serving layer. The products sit at different heights in that stack, and their names are confusing, so first the map. Nothing in this section was run here: it is read from documentation and source, with dates.

Who does what above the engines

Filled: the project does it itself. Ring: through another component it drives (an engine, or llm-d under KServe). Blank: not covered on this page. From each project's documentation, read 2026-10-09 and 2026-10-10.

What each one adds

  • Dynamo: the engine-agnostic, NVIDIA-led layer: a Rust front end, the KV-aware router of section 2, a planner that resizes the prefill and decode pools to meet latency targets, a KV block manager that offloads cache to host memory, disk and object storage, NIXL for transfers, and Grove for gang scheduling a prefill/decode group on Kubernetes.
  • llm-d: Kubernetes-first and built on vLLM; tested recipes ("well-lit paths"); its router is an Endpoint Picker for the Gateway API Inference Extension that scores pods on prefix-cache match, queue depth, KV usage and predicted latency.
  • TensorRT-LLM: NVIDIA's engine, PyTorch-based by default since 1.0; continuous batching under the name in-flight batching; disaggregation with trtllm-serve disaggregated.
  • Triton Inference Server (renamed Dynamo-Triton; not OpenAI's Triton kernel language): a general server for a zoo of frameworks. Its dynamic batcher groups whole requests and runs each batch to completion: dynamic batching is not continuous batching, so for LLMs it hands batching to its TensorRT-LLM or vLLM back end.
  • KServe drives llm-d through an LLMInferenceService resource on Kubernetes; Ray Serve LLM runs vLLM engines on a Ray cluster with prefill/decode disaggregation and prefix-aware routers.
Each project in detail: parts, versions, history, quotes (reference)

NVIDIA Dynamo

Announced at GTC on 2025-03-18 (first release v0.1.0 the same day), 1.0 on 2026-03-13, v1.5.1 on 2026-10-07 ({{releases|https://github.com/ai-dynamo/dynamo/releases}}). The README calls it "the orchestration layer above inference engines": "it doesn't replace SGLang, TensorRT-LLM, or vLLM, it turns them into a coordinated multi-node inference system", "Built in Rust for performance, Python for extensibility" ({{README|https://github.com/ai-dynamo/dynamo}}). Its parts:

Front endAn OpenAI-compatible HTTP server (Rust) that tokenizes and forwards; on Kubernetes the Gateway API Inference Extension can call Dynamo's endpoint picker instead.
RouterPicks the worker with the lowest cost: prompt blocks still to compute (cached blocks on GPU, host and disk credited) plus decode blocks carried; the formula and a worked example are in section 2.
Planner"Autoscaler that adjusts prefill and decode replicas using engine performance models and traffic prediction to meet TTFT and ITL SLAs."
KV Block ManagerOffloads cache blocks GPU (G1) to pinned host memory (G2) to disk (G3) to S3-compatible object storage (G4); the tiers themselves are taught on {{Batching, KV cache and scheduling|n:3c65c17b0d0d819db53bd2c48909e5b2}}, section 4.
NIXLThe transfer library of section 6, for cache moves between workers and tiers.
GroveA Kubernetes operator for "topology-aware gang scheduling (NVL72)": start a prefill/decode group together, on GPUs close to each other.

llm-d

Launched in May 2025 by Red Hat, Google Cloud, IBM Research, CoreWeave and NVIDIA; accepted as a CNCF Sandbox project, announced 2026-03-24 ({{CNCF blog|https://www.cncf.io/blog/2026/03/24/welcome-llm-d-to-the-cncf-evolving-kubernetes-into-sota-ai-infrastructure/}}); v0.10.0 on 2026-09-29. Where Dynamo is engine-agnostic and NVIDIA-led, llm-d is Kubernetes-first and built around vLLM. Its documentation is a set of "well-lit paths", tested recipes: an optimised baseline, routing by predicted latency, precise prefix-cache-aware routing, a tiered prefix cache, prefill/decode disaggregation, wide expert parallelism for MoE models, flow control and fairness, autoscaling, and more ({{well-lit paths|https://llm-d.ai/docs/well-lit-paths}}).

Its router is a Kubernetes building block worth knowing by name. The Gateway API Inference Extension (GAIE, a Kubernetes SIG project, v1.6.2 on 2026-09-17) defines an InferencePool resource and lets any Envoy-based gateway ask an Endpoint Picker (EPP) which pod should take each request. llm-d's EPP, now called the llm-d Router (v0.11.0, 2026-09-27), filters pods, gives each a score between 0 and 1 from weighted scorers (prefix-cache match length, queue depth, KV-cache utilisation, running requests, token load, predicted latency, LoRA affinity) and picks the highest sum ({{llm-d-router|https://github.com/llm-d/llm-d-router}}).

TensorRT-LLM

NVIDIA's own engine, for NVIDIA GPUs only. Until 2025 it compiled each model into a TensorRT "engine" ahead of time, per GPU type and shape limits; release 1.0 (2025-09-24) made "the PyTorch-based architecture ... stable and the default experience" ({{v1.0.0 notes|https://github.com/NVIDIA/TensorRT-LLM/releases/tag/v1.0.0}}), so models are Python code and need no compile step. It does continuous batching under the name in-flight batching ("also known as continuous batching or iteration-level batching"), paged KV, FP8 and NVFP4, speculative decoding, wide expert parallelism, and disaggregated serving with trtllm-serve disaggregated; its gains from disaggregation are largest "for workloads with long input sequences and moderate output lengths where interference is most severe" ({{blog|https://nvidia.github.io/TensorRT-LLM/blogs/tech_blog/blog5_Disaggregated_Serving_in_TensorRT-LLM.html}}). MLPerf's NVIDIA submissions run on it (the parent's {{Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} uses HPE's 8×H200 TensorRT-LLM run).

Triton Inference Server, and the three Tritons

Three unrelated things share the name: Triton Inference Server, NVIDIA's general model server (this section); OpenAI's Triton, a Python language for writing GPU kernels ({{Triton and Gluon|n:3c65c17b0d0d81729d15ed4d1a4461b3}}); and the moon. NVIDIA renamed the server: "As of March 18, 2025, NVIDIA Triton Inference Server is now part of the NVIDIA Dynamo Platform and has been renamed to NVIDIA Dynamo Triton" ({{NVIDIA blog note|https://developer.nvidia.com/blog/optimize-ai-inference-performance-with-nvidia-full-stack-solutions/}}); the product page says "Dynamo-Triton, formerly NVIDIA Triton Inference Server" and presents Dynamo as a separate product for LLMs. GitHub still calls it Triton Inference Server; v2.73.0 matches the 26.09 NGC container (2026-09-30), a monthly cadence.

It serves any model from many frameworks behind one endpoint: back ends for TensorRT, ONNX Runtime, PyTorch, TensorFlow, OpenVINO, Python, DALI, FIL (tree models), TensorRT-LLM and vLLM; ensembles and Python business-logic scripts chain models server-side (tokenize, embed, rerank, classify); a model repository with versions and hot reload; Prometheus metrics; Model Analyzer to search configurations. Its dynamic batcher is the classic one: it holds requests for up to max_queue_delay_microseconds hoping to fill a batch, then sends the batch as is, and that batch runs to completion ({{batcher.md|https://github.com/triton-inference-server/server/blob/main/docs/user_guide/batcher.md}}). That is request-level batching, the static batching the parent page warns against for LLMs: dynamic batching is not continuous batching. For LLMs Triton hands the batching to its TensorRT-LLM back end's in-flight batcher, or to vLLM. Use it when one serving substrate must carry a mixed zoo (recommenders, vision, tree models, embedders and the odd LLM); for a pure LLM API it adds little over the engines' own servers.

KServe and Ray Serve

KServe is Kubernetes' general model-serving project (CNCF incubating, announced 2025-11-11; v0.21.0 on 2026-09-25). For LLMs it adds an LLMInferenceService resource (serving.kserve.io/v1alpha2) that "provides the integration with llm-d to support disaggregated serving, pre-fix caching, intelligent scheduling, variant autoscaling" ({{CNCF post|https://www.cncf.io/blog/2025/11/11/kserve-becomes-a-cncf-incubating-project/}}); its samples set data, expert and tensor parallelism in the spec and pass NixlConnector to vLLM. Ray Serve LLM runs vLLM engines on a Ray cluster from Python: "tensor, pipeline, expert, and data parallel attention", prefill/decode disaggregation since Ray 2.47 (2025-06-12) with NIXL or LMCache connectors, and prefix-aware and KV-aware routers ({{Ray docs|https://docs.ray.io/en/latest/serve/llm/index.html}}). vLLM itself is a common engine under both, and also uses Ray for multi-node runs.

Vendor and partner claims, with their conditions (provenance)

Dynamo. At launch: "increased the number of requests served by up to 30x" for DeepSeek-R1 on GB200 NVL72 with disaggregation (TensorRT-LLM, FP4, 32K in and 8K out, a figure labelled "Projected performance subject to change"), and "more than doubled the throughput" for Llama 70B on Hopper (vLLM, FP8, 3K in and 50 out; TP8 DP2 aggregated against prefill TP2 DP4 plus decode TP8) ({{GTC 2025 blog|https://developer.nvidia.com/blog/introducing-nvidia-dynamo-a-low-latency-distributed-inference-framework-for-scaling-reasoning-ai-models/}}). The current README adds "7x higher throughput per GPU" for DeepSeek R1 on GB200 NVL72 with Dynamo against B200 without, citing SemiAnalysis InferenceX: a comparison across two different systems, so it measures the rack as much as the software. Ask what changed besides the software before reading any of these as a software speed-up. vendor

llm-d. Partner results in the README, all measured by the companies on their own deployments: 3 times the output throughput and 2 times faster TTFT from prefix-cache-aware routing over round robin (Llama 3.1 70B on 4 MI300X), up to 70% more tokens per second from disaggregation (gpt-oss on B200), and "10-30% throughput improvement with disaggregated serving on identical infrastructure" (Oracle, MI300X). vendor

TensorRT-LLM. Its disaggregation blog, all on GB200: DeepSeek R1 at 4,400 in and 1,200 out gained 1.4 to 1.8 times, 1.6 to 2.5 times with multi-token prediction, "especially at lower concurrency levels"; Qwen 3 at 8,192 in and 1,024 out 1.7 to 6.11 times. vendor
