The idea in one screen

Serving one model on many GPUs is a choice of what crosses between GPUs, and how often: nothing (replicas), two all-reduces per layer for every token (tensor parallel), one hidden state per stage (pipeline parallel), every token to its experts and back (expert parallel), or the whole KV cache once per request (prefill/decode split). The link each one can afford decides where it may run, and above the engines a serving layer (Dynamo, llm-d) decides which GPU gets which request.

Five ways to spread serving: what crosses, how often, and over which link

Running example unless marked: Llama 3.1 70B, FP8 weights, BF16 cache, H200s, 8 GPUs per split (4 drawn). Per token at TP 8 each GPU sends 4.59 MB over 160 all-reduces; a pipeline boundary carries one 16 KiB hidden state; DeepSeek-V3's expert parallelism moves 9.98 MB per token over 58 MoE layers; a 2,000-token prompt's cache is 625 MiB, sent once. derived, formulas in sections 3 to 6.

Replica
a complete copy of the engine; a request is served by one copy.
All-reduce
every GPU ends with the sum of everyone's partial result; tensor parallelism needs two per layer.
Pipeline bubble
stages idle because too few batches are in flight to keep each one busy.
All-to-all
each GPU sends a different piece to every other GPU: dispatch (tokens to experts) and combine (results back).
Redundant expert
an extra copy of a popular expert on another GPU, placed by a balancer such as DeepSeek's EPLB.
Disaggregated serving
prefill on some GPUs, decode on others, the KV cache copied between them.
KV connector
the engine plug-in that sends or receives a request's cache (NIXL, Mooncake, LMCache, a file).
Goodput
the highest request rate at which a target share of requests meets both latency targets.
Serving layer
the software above many engines that routes requests, moves caches and sizes the pools.

The running example is the parent page's chat assistant: Llama 3.1 70B with FP8 weights and a BF16 KV cache on H200s (141 GB each), 2,000-token prompts and 300-token answers, targets of 2 s to the first token and 50 ms per output token.
