0. In one screen

A serving engine on one GPU is the unit the parent page taught. This page is about what happens when one unit is not enough: the model does not fit, the users do not fit, one GPU is too slow for the latency target, or prefill and decode keep getting in each other's way. There are five ways to spread the work, each costs something different on the wire, and above them sits a serving layer (NVIDIA Dynamo, llm-d, KServe, Ray Serve) that decides which GPU gets which request.

The question this page keeps returning to: for each way of splitting, what crosses between GPUs for every token, how long does that take on the link it uses, and what does the split buy in latency, users and cost? The running example is the parent page's chat assistant: Llama 3.1 70B with FP8 weights and a BF16 KV cache on H200s (141 GB each), 2,000-token prompts and 300-token answers, targets of 2 s to the first token and 50 ms per output token. Every derived number comes from the parent's {{Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} model (run by src/recompute.py), so it can be checked there.
