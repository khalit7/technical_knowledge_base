What a model file has to hold, taught from zero and read byte by byte from real Qwen3 files: why pickle checkpoints run code, how safetensors and GGUF lay out the same weights, MLX's packed 4-bit groups, what ONNX turns a decoder into, compiled engines and on-device formats, the Hugging Face repo layout, and which conversions keep every number. A trained model is a few hundred named arrays of numbers plus the facts needed to use them. A model format is the agreement on how those arrays and facts are written to disk. This page reads real files byte by byte (the Qwen3 models measured across this topic), so every claim below can be checked against bytes you can see in the File explorer tab.

The running example is the one from the parent page, Topic: inference-and-serving: a chat assistant serving many users. In the datacenter its model (the parent's planner uses Llama 3.1 70B in FP8 on H200) arrives at vLLM as a folder of safetensors shards plus a config.json. On a laptop, the same kind of model arrives as one GGUF file for llama.cpp or an MLX folder. Same idea, three ways of writing it down. Qwen3-0.6B is the specimen: small enough to convert many times, built exactly like its bigger siblings.

In one screen

Most confusion about formats comes from mixing up three separate layers. Keep them apart and almost every question answers itself:

1. Container

How bytes are laid out: where each tensor starts, what metadata travels with it, and whether reading the file can run code. safetensors, GGUF, pickle, ONNX's protobuf, flatbuffers.

2. Number encoding

How each number is stored: BF16, FP8, or a quantization scheme such as GGUF's Q4_K or MLX's 4-bit affine groups. The container says which; the scheme says how to decode it.

3. Compiled artifact

A build output tied to one runtime and one kind of hardware: a TensorRT engine, a Core ML compiled model. Not something to distribute; something to rebuild.

GGUF is unusual because it fuses layers 1 and 2 (its quantization types are defined inside the format). safetensors deliberately owns only layer 1. A TensorRT engine is layer 3 and is not really a model format at all. The table is the whole page in one view; each row has a section below.

1. What a model file has to hold

The problem. Training leaves the model in GPU memory as Python objects. To ship it, every one of its arrays has to become bytes on disk, and someone else's program has to turn those bytes back into exactly the same arrays, and know what to do with them. Writing objects to bytes is serialization; reading them back is deserialization.

What has to travel. Five kinds of thing, and a format either carries each one or leaves it to a sibling file:

TensorsEvery weight array. For each: a name (model.layers.0.self_attn.k_proj.weight), a dtype (how one number is stored, such as BF16, two bytes), a shape ([1024, 1024]), and the raw bytes.
ConfigThe architecture numbers that turn arrays into a network: layers, heads, hidden size, RoPE base, norm epsilon. Qwen3-1.7B's is a 726-byte JSON file.
TokenizerThe vocabulary (151,936 tokens for Qwen3), the merge rules, special-token ids. Without it the model's input and output ids mean nothing.
Chat templateThe Jinja program that turns a list of messages into the exact token sequence the model was trained on (<|im_start|>user ...).
Generation defaultsSampling settings the authors recommend (Qwen3: temperature 0.6, top-k 20, top-p 0.95) and which ids end a turn.

Here is a real Hugging Face model folder, Qwen3-1.7B, drawn to scale by bytes. The weights are almost everything; the small files decide whether those bytes mean anything. Tap a segment.

A tensor on disk is just numbers in a row

A file never stores a "matrix". It stores the numbers one after another and remembers the shape. The order is row-major (the last index changes fastest, as in C and PyTorch) and every multi-byte number is little-endian (lowest byte first), the byte order of every x86 and Arm chip you will meet. So a tensor's size is simply: number of elements times bytes per element.

bytes = (product of the shape) × (bytes per element)
example
k_proj.weight, BF16, shape [1024, 1024]: 1,048,576 × 2 = 2,097,152 bytes, exactly the gap between its two offsets in the real file (section 3).

dtypes from zero: what one number costs

A floating-point number is a sign bit, an exponent (how big: the range) and a mantissa (how precise: the significant digits). Formats differ only in how many bits each part gets. BF16 (brain float) keeps F32's 8 exponent bits and cuts the mantissa to 7, so it covers the same range with less precision; F16 (half) has more precision (10 bits) but only 5 exponent bits, so very small and very large numbers do not fit. The quantization types and the maths behind them are owned by Quantization and Precision; here we only need what they cost on disk.

The converter keeps 1-D tensors and norms in F32 because, in its own words, "most of the codebase that takes in 1D tensors or norms only handles F32 tensors" (conversion/base.py L1047, b11146); they hold 65,536 of the 751.6 million values (under 0.01%).

2. Pickle: a checkpoint that is a program

The problem. For years the default way to save a PyTorch model was torch.save, which writes Python's pickle format, and the Hugging Face files named pytorch_model.bin are exactly that. Pickle can save any Python object, which sounds like a feature until you see how: a pickle is not data, it is a program for a small stack machine, and loading it runs the program.

How it works. The pickle machine reads one-byte opcodes. Most push values (a string, an integer) onto a stack. Two are the point: GLOBAL imports any module.name and pushes it, and REDUCE pops a callable and an argument tuple and calls it. That is how a tensor is rebuilt (call torch._utils._rebuild_tensor_v2 with the storage and shape) and equally how a file can call os.system. Python's own documentation says it plainly: "The pickle module is not secure. Only unpickle data you trust. It is possible to construct malicious pickle data which will execute arbitrary code during unpickling" (pickle docs).

Since PyTorch 1.6 a .pt or .bin file is a zip archive (torch.save docs): a small data.pkl program plus one raw file per storage. We saved a two-tensor checkpoint and disassembled its program with pickletools (never loading it) run here, PyTorch 2.14.1: bytes, opcodes, of which imports and calls. The mitigation that failed, and the ones that hold

  • weights_only=True swaps the pickle machine for a restricted one that only allows an allowlist of globals (tensor rebuild functions, plain containers). PyTorch 2.6 made it the default on 2025-01-29, calling it a backward-compatibility-breaking change (PyTorch 2.6 blog).
  • It was bypassed. CVE-2025-32434 (published 2025-04-17/18, CVSS v4 9.3, critical): remote code execution through torch.load even with weights_only=True, in every PyTorch before 2.6.0. So for years the recommended safe path was not safe.
  • Libraries now refuse. transformers 4.52.0 (2025-05-20) added check_torch_load_is_safe(): on PyTorch older than 2.6 it raises instead of loading a .bin, and its message adds "This version restriction does not apply when loading files with safetensors" (source).
  • Real attacks exist. JFrog found "around 100" malicious models on the Hugging Face Hub, one opening a reverse shell (2024-02-27, JFrog). ReversingLabs' "nullifAI" (2025-02-06) found two models whose pickles were packed with 7z and deliberately broken after the payload, so the Hub's Picklescan missed them (ReversingLabs). The Hub lists each pickle's imports without executing it and says this "is not 100% foolproof" (Hub docs).
  • Not only PyTorch. Keras models could carry code in Lambda layers (CVE-2024-3660, fixed in Keras 2.13 with safe_mode), and CVE-2025-1550 ran code through load_model even with safe_mode=True (fixed in Keras 3.9.0).
The rule
Treat a pickle checkpoint from anyone you do not trust as an executable. Prefer the safetensors files in the same repo; if only a .bin exists, convert it inside a throwaway sandbox (a container with no credentials and no network), never on your workstation.

3. safetensors, byte by byte

The idea. Remove the program. A safetensors file is three things in a row, and nothing in it can name a function (format spec):

  1. 8 bytes: an unsigned 64-bit little-endian integer N, the length of the header.
  2. N bytes of JSON: for every tensor its dtype, shape and data_offsets [begin, end), counted from the start of the data buffer, plus an optional __metadata__ map of strings to strings ("Arbitrary JSON is not allowed").
  3. The data buffer: every tensor's raw bytes, back to back, little-endian, row-major. The spec forbids holes and overlaps, which also rules out "polyglot" files that hide a second payload.

Here are the first bytes of the real Qwen3-0.6B model.safetensors ( bytes). The first 8 bytes, read little-endian, give the header length; the JSON starts right after:

The header is bytes describing tensors, of the file. A reader parses that JSON, and then each tensor is a slice of the file at a known place: no parsing, no conversion. The Rust reference implementation refuses headers over 100 MB (MAX_HEADER_SIZE = 100_000_000, tensor.rs L10) so a hostile file cannot make you allocate gigabytes of JSON, and its writer pads the header with spaces to a multiple of 8 bytes, so the buffer starts 8-byte aligned (the Qwen file's header ends in one space). MLX's own writer does not pad: the MLX file's header is bytes, 4 more than a multiple of 8, which the format allows. Step through all three files field by field in the File explorer.

Status, October 2026
A Trail of Bits audit commissioned by Hugging Face with EleutherAI and Stability AI found "no critical security flaw leading to arbitrary code execution" (2023-05-23, HF blog). safetensors became a PyTorch Foundation project on 2026-04-08 (announcement) and moved to the github.com/safetensors organisation; the latest release is v0.8.0 (2026-06-09). Its dtype list now runs from F64 down to F8 (E4M3, E5M2, E8M0) and F4/F6 for microscaling formats.

What it cannot say: tied weights are stored twice

Qwen3-0.6B's config says tie_word_embeddings: true: the input embedding and the output layer (lm_head) are one shared matrix in the model. safetensors has no way to say "this tensor is that one" (an alias), so the released file stores both, and we checked that the two byte ranges hash the same measured here: bytes (, of the file) are a duplicate. Qwen3-1.7B does the same in its second shard; Qwen3-4B's checkpoint does not. Downstream tools disagree on what to do: MLX's converter honours the tie and keeps one copy ( tensors), llama.cpp's converter keeps both (section 4). The quality cost of that on GGUF quant types is on Local and on-device inference.

Shards and the index

Big checkpoints are split into shards, model-00001-of-00002.safetensors and so on, with model.safetensors.index.json mapping every tensor name to its shard. Qwen3-1.7B's index has 311 entries; the second shard holds exactly one tensor, the duplicate lm_head.weight. transformers chooses the split when saving: max_shard_size defaulted to "5GB" in v4 and "50GB" from v5.0.0 (2026-01-26). The Hub recommends files under 200 GB and enforces 500 GB per file (Hub storage limits).

Why it is fast: mapping, not reading

To memory-map (mmap) a file is to ask the operating system to make the file appear as memory without reading it. Nothing is copied until a byte is touched; then the OS brings in that 16 KiB page (on Apple silicon) from its page cache, the RAM it uses to keep recently read files. Because safetensors tensors sit at known offsets in their final layout, a loader can hand out slices of the mapping directly. A pickle checkpoint must run its program first and, by default, copy every storage into fresh memory.

Reading it. Plain torch.load took and MiB of new memory before you could use anything. safetensors.torch.load_file returned in with MiB, because it maps the file and the tensors are views; touching every page then took in total. torch.load(mmap=True) closes most of the gap for the zip format (, then touched), but still runs the pickle program. With a cold cache all of these become disk-bound: the production child measured this laptop's SSD at about 3.2 GB/s for cold starts (LLM serving in production).

Published numbers, not run here. The safetensors README credits the format with loading BLOOM on 8 GPUs "from 10mn with regular PyTorch weights down to 45s" vendor. fastsafetensors (IBM Research, arXiv 2505.23072) copies groups of tensors straight into GPU memory, with GPUDirect Storage where available, and reports 4.8x to 7.5x faster loads and 26.4 GB/s for Llama-70B on four GPUs authors; vLLM and SGLang accept --load-format fastsafetensors.

4. GGUF, byte by byte

The idea. GGUF goes the other way from safetensors: one file, everything in it. Tensors, tokenizer, chat template and architecture numbers travel together, the last three as typed key/value metadata. llama.cpp, Ollama and LM Studio read it; the specification is short (gguf.md) and llama.cpp's header file sums it up in 30 lines (gguf.h L1-L30):

  1. Magic GGUF (bytes 47 47 55 46), version (u32, now 3), tensor count and key/value count (64-bit each).
  2. Key/value pairs: a key string (a u64 length, then the bytes), a value type (one of 13: integers, floats, bool, string, array), the value. Keys are namespaced: general.architecture, qwen3.attention.head_count, tokenizer.ggml.tokens.
  3. Tensor infos: for each tensor its name, number of dimensions, the dimensions, its type, and its offset into the data section.
  4. Padding with zero bytes up to general.alignment (32 when absent), then the data section; every tensor's offset is a multiple of the alignment, so the file can be mapped and each tensor used in place.

Here is the real Qwen3-0.6B Q4_K_M file ( bytes) drawn to scale, then its header zoomed. Everything before the data is bytes ( of the file), and of that is the tokenizer: 151,936 token strings, their types and 151,387 merge rules. The other facts and all tensor infos fit in the rest.

Tap a segment.

One trap when reading GGUF. Dimensions are stored fastest-first, the reverse of PyTorch: the embedding that safetensors lists as [151936, 1024] appears in GGUF as [1024, 151936]. Same bytes, same row-major order, opposite way of writing the shape.

Each tensor carries its own type: Q4_K_M is a recipe

Because the type is per tensor, one file mixes several. "Q4_K_M" is a recipe chosen by llama-quantize, not one type: in this file 168 tensors are Q4_K, 29 are Q6_K (the embedding, and the value projection and FFN down projection in 14 of the 28 layers) and 113 small vectors stay F32. Averaged over every value it is bits per weight, not 4.

What each type does to quality, measured on Qwen3-1.7B and 4B with perplexity and KL divergence, is the Quant ladder tab of Local and on-device inference, which also shows one 32-weight block in five formats. This page only needs the file layout of a block. A Q4_K super-block holds 256 weights in 144 bytes (ggml-common.h L325-L338): two F16 numbers d and dmin, 12 bytes packing eight 6-bit scales and eight 6-bit minimums (one pair per 32 weights), and 128 bytes of 4-bit codes. Each weight is d · scalej · q − dmin · minj. Here is the first block of layer 0's key projection, decoded by hand from the file and checked against gguf-py's decoder run here:

Splitting a GGUF

Files over a hosting limit are split with llama-gguf-split into name-00001-of-00003.gguf and so on. We split the 397 MB file at 150 MB run here: the first shard carries all 28 metadata keys plus three split.* keys and 28 tensors; the others carry only the split.* keys and their tensors (179 and 103). Pointing llama.cpp at the first shard loads all three, with no index file, and --merge gave back all 310 tensors byte-identical (the merged file is 96 bytes larger: the split keys stay).

Where it came from, and its costs

  • History. GGUF replaced llama.cpp's earlier files (GGML, then GGMF with a version, then GGJT with aligned tensors for mmap), whose hyperparameters were an untyped positional list, so each new architecture broke old loaders. GGUF's typed, named metadata fixed that; it landed in llama.cpp with PR #2398 on 2023-08-21; version 3 added big-endian files. The library keeps the name ggml, and the ggml.ai team joined Hugging Face on 2026-02-20 (announcement), with the projects staying community-run.
  • New architectures wait for the converter. Every family needs its own code in llama.cpp's converter (in b11146 a package of per-family modules) and its own graph in llama.cpp, so a new model can take days to months to get a working GGUF.
  • No code, but not no risk. GGUF has no opcodes, yet a parser reading lengths from a hostile file is attack surface: Databricks reported heap overflows in gguf_init_from_file (CVE-2024-25664 to 25668, 2024-03-22, Databricks) and Cisco Talos reported others (CVE-2024-21836 and three more). Today's parser rejects strings over 1 GiB and arrays over 230 elements (gguf.cpp L19-L20). And the embedded chat template is a program: llama-cpp-python rendered it with an unsandboxed Jinja2 until 0.2.72 (CVE-2024-34359, CVSS 9.6, 2024-05-10).
  • Packing can change without the model changing. Ternary models (weights in {−1, 0, +1}) need log23 ≈ 1.585 bits each. GGUF's TQ1_0 packs mostly five weights per byte (35 = 243 fits in 256) plus an F16 scale per 256 weights, 1.6875 bits per weight, and TQ2_0 spends 2.0625 (PR #8151, 2024-09-06). BITCOS (arXiv 2609.16338, Intel, 2026-09-14) notes that five-trit packing "rounds up to 1.625 bits per weight" with power-of-two groups and that zeros reach up to 51.5% of weights in the 29 models it studied; storing a presence bitmap and the signs costs 2 − z bits (z the zero share), beats five-trit packing on 26 of 29 models, reaches 1.485 bits, and speeds decoding up to 1.18x on CPU and 1.27x on Intel Xe2 GPUs authors' claims, not run here. Same model, different bytes: that is the layer a format owns.

5. MLX: safetensors with packed groups

The idea. MLX, Apple's array framework, did not invent a container: an MLX model is a Hugging Face-style folder whose weights are safetensors and whose config.json says how they are quantized. What it adds is a layout for quantized weights. mlx_lm convert -q wrote this into our Qwen3-0.6B config (and mirrored it as quantization_config for Hugging Face tools):

"quantization": { "group_size": 64, "bits": 4, "mode": "affine" }

How it works. Each quantized linear layer becomes three tensors: weight holds the 4-bit codes packed eight to a 32-bit word (lowest bits first), and scales and biases hold one BF16 scale s and one offset b for every group of 64 weights; each weight is s·q + b (mx.quantize). That is why the 4-bit file has tensors where the BF16 one has 310. For layer 0's key projection (1,024 × 1,024 weights):

Tensordtypeshapewhy
k_proj.weightU32[1024, 128]1,024 inputs × 4 bits / 32 bits per word
k_proj.scalesBF16[1024, 16]1,024 / 64 groups per row
k_proj.biasesBF16[1024, 16]one offset per group

Below, the same 256 weights (the start of that row) as one GGUF Q4_K super-block and as four MLX groups, drawn byte for byte. Both cost exactly 144 bytes, 4.5 bits per weight; the difference is the layout. GGUF keeps the scales next to their codes inside one block; MLX keeps codes, scales and biases in three separate tensors, so the bytes of one group live in three places in the file.

We decoded the first MLX group by hand (first word 06 b5 ae cb = 3,417,224,454 → codes 6, 0, 5, 11, 14, 10, 11, 12) and the result equals mx.dequantize exactly run here, mlx 0.32.3. MLX also has non-affine modes: mxfp4 since v0.29.0 (2025-08-29) and mxfp8 and nvfp4 since v0.29.4 (2025-11-11); affine allows 2 to 8 bits (and 1) with groups of 32, 64 or 128.

Cost and speed. The conversion is cheap and repeatable: two runs of mlx_lm convert took 2.3 and 1.7 s and produced the same SHA-256 as the copy made for the shared store two days earlier. Loading needs no copy to a GPU, because Apple silicon's GPU reads the same unified memory. MLX does not use the Neural Engine; its maintainers have said so since 2023 (mlx issue #18). How fast and how accurate MLX's types are against GGUF's on the same model is measured on Local and on-device inference.

6. ONNX: the model as a graph

The idea. Every format so far stores only weights; the code that uses them lives in the engine. ONNX (Open Neural Network Exchange) stores the computation too: a graph of operators (MatMul, Softmax, ...) wired by named tensors, the weights as initializers, and an opset version that pins the exact meaning of every operator: "When the inventory of a given operator set changes ... its version MUST increase" (Versioning.md). A graph exported today therefore runs on a runtime written years later, on CPU, GPU, or an NPU vendor's SDK. The file is a protobuf message, and protobuf messages cannot exceed 2 GB, so larger models keep their weights in an external data file referenced by path, offset and length (ExternalData.md).

What a decoder becomes run here: PyTorch 2.14.1 exporter (dynamo, the default since 2.9), onnx 1.23.2, ONNX Runtime 1.31.0. We exported Qwen3-0.6B's forward pass (token ids in, logits out, batch and sequence length left dynamic) and opened the result:

Reading it. There is no "attention" or "RMSNorm" operator: attention became MatMul, Softmax (, one per layer), Transpose and Reshape; each RMSNorm became Pow, ReduceMean, Sqrt and Reciprocal (113 of each: 4 norms in each of 28 layers, counting the per-head query and key norms, plus the final one) with an Add and Muls around them. And there is no KV cache: this graph recomputes the whole sequence on every call. To generate text you export a variant whose inputs and outputs include each layer's past keys and values, and run the loop, sampling and cache yourself, or use ONNX Runtime GenAI, which "implements the generative AI loop for ONNX models" including "KV cache management" and powers Foundry Local, Windows ML and the VS Code AI Toolkit (v0.17, 2026-09-28). One pitfall we hit: with an example batch of 1, torch.export fixed the batch dimension at 1; export with a batch of 2.

Where it fits. ONNX is the right answer for encoders (embeddings, rerankers), classic ML, and NPUs or Intel hardware whose toolchains ingest it. Datacenter LLM engines (vLLM, SGLang, TensorRT-LLM) do not use it: their speed lives in a paged KV cache, custom attention kernels and a scheduler that changes the batch every step, none of which is a fixed graph (see vLLM: inside the default engine). The current onnx release is 1.23.2 (2026-10-06), defining opset 28; PyTorch 2.14's exporter wrote opset 20 by default.

7. Compiled artifacts and on-device formats

None of these were run here (no NVIDIA GPU, no phone toolchain); every fact is from the project's documentation or release notes, dated.

TensorRT engines are build outputs. NVIDIA's builder profiles kernels on the actual GPU, fuses layers, picks memory layouts and serializes the result with the weights into a plan (.plan or .engine). The documentation is direct: "By default, TensorRT engines are compatible only with the version of TensorRT used to build them" and "only compatible with the type of device where they were built" (Engine compatibility). Since TensorRT 8.6 two opt-ins loosen that: hardware compatibility (one plan for Ampere and newer, at some speed cost) and version compatibility (later releases of the same major version). Version-compatible plans embed runtime code, so deserialize only plans you trust. Treat plans as a cache keyed on (model, GPU, TensorRT version, shape profiles), built in CI, never as the model you publish.

TensorRT-LLM moved away from them. Since v1.0.0 (2025-09-24) its PyTorch backend is "the default experience": point it at safetensors and it uses NVIDIA's kernels without a build artifact. The old trtllm-build engine path is still in the latest stable release, v1.2.1 (2026-04-20), but was removed on main on 2026-07-14 and is gone from the 1.3 release candidates (releases). How it serves is on Distributed and disaggregated serving.

8. The Hugging Face repo: the source of truth

Almost every format above is made from one place: a Hugging Face model repo. Knowing its files is what lets you debug "the model loads but answers badly". The real Qwen3-1.7B repo (section 1's bar) holds:

Quantized checkpoints stay in safetensors. FP8, INT4 or NVFP4 checkpoints served by vLLM and SGLang are usually compressed-tensors, which "extends the safetensors format": the packed weights and their scales are ordinary tensors, and config.json carries "quant_method": "compressed-tensors" with a format such as pack-quantized or nvfp4-pack-quantized (repo, 0.19.0, 2026-09-21). It is written by llm-compressor. That is how the parent's FP8 Llama 3.1 70B arrives at vLLM. The methods (GPTQ, AWQ, FP8, NVFP4) are on Quantization and Precision.

Remote code. A repo can also ship Python modeling files. transformers runs them only when you pass trust_remote_code=True, which is pickle's risk again by a different door: read the code first or pin a revision you have read.

9. Conversions: which ones keep every number

Every arrow between formats is either a repack (same numbers, new layout) or a requantization (new numbers). The Conversion map tab draws them all, with the runs made here. The rules that matter more than the arrows:

  • Lossless: pickle to safetensors; safetensors BF16 to GGUF BF16 (we checked all 751.6 million values: identical) or F32; safetensors to ONNX in F32. Not lossless: BF16 to F16, by a little (section 1).
  • Lossy by design: any quantization (llama-quantize, mlx_lm convert -q, llm-compressor, a TensorRT build with FP8 or INT4). Always quantize from the full-precision original, never from an already quantized file: errors compound.
  • One-way in practice: dequantizing a GGUF gives a rounded shadow of the model, not the model. If you need a GGUF and an FP8 checkpoint, make both from the safetensors original.
  • Lossy in a second sense: exports drop things that are not numbers. Our ONNX export carries no tokenizer, template or sampling defaults; a third-party GGUF may carry a different template (section 4).
  • Reproducible: the GGUF converter, llama-quantize and mlx_lm convert all gave byte-identical files on re-runs here, so a SHA-256 is a fair way to check that a file is what you think it is.
# safetensors to GGUF to a quant type (llama.cpp b11146), as run here python convert_hf_to_gguf.py Qwen3-0.6B/ --outtype bf16 --outfile q06-bf16.gguf # 11 to 17 s, 1,509,347,136 bytes llama-quantize q06-bf16.gguf q06-Q4_K_M.gguf Q4_K_M # 4.7 to 6.1 s # safetensors to MLX 4-bit python -m mlx_lm convert --hf-path Qwen3-0.6B --mlx-path q06-mlx4 -q --q-bits 4 --q-group-size 64 # about 2 s

10. Loading: what the format buys at start-up

For a server, the format matters most at cold start: the seconds between "launch" and "ready" that decide how fast you can scale out (autoscaling is on LLM serving in production). Mapping instead of copying is the main lever. llama.cpp maps GGUF files by default (--load-mode auto: "mmap, unless a device does not support it"; the loader refuses to map a file whose data section is not aligned). We started llama-server on Qwen3-4B Q4_K_M (2.5 GB) four times each way measured on Apple M1 Pro, warm page cache:

Mapping saved about a third of a second and 0.6 GiB here; the bigger wins come when the file is not yet in RAM, when several processes share one mapped file, or when only part of the model is needed (a pipeline stage, a tensor-parallel rank, a draft model). On a datacenter GPU the weights must still be copied from host memory into HBM, which is what fastsafetensors and GPUDirect Storage attack (section 3).

Common mistakes

"weights_only=True makes torch.load safe."
It was bypassed before PyTorch 2.6 (CVE-2025-32434). Even now it is an allowlist inside a pickle interpreter. Prefer safetensors; keep PyTorch current.
"Converting to F16 GGUF is lossless."
From a BF16 checkpoint it changed values of Qwen3-0.6B. Use --outtype bf16 (or f32) for a lossless master.
"A GGUF is self-contained, so its chat template is the model's."
It is whatever the uploader wrote. The Unsloth file in our store has a rewritten template and one fewer stop id than the original repo.
"Q4_K_M means 4 bits per weight."
It is a recipe of types: the Qwen3-0.6B file averages bits per weight, and Q4_K itself is 4.5.
Requantizing a quantized file.
Q8_0 to Q4_K_M stacks two roundings. Quantize from the BF16 or F32 original.
Reading GGUF shapes like PyTorch shapes.
GGUF lists dimensions fastest-first: [1024, 151936] is PyTorch's [151936, 1024].
Shipping a TensorRT plan as "the model".
It is tied to the GPU type and TensorRT version it was built with. Ship safetensors; build plans in CI.
Measuring load time with a warm cache and calling it cold start.
The second load reads from RAM. Our load numbers are warm and say so; cold numbers are disk-bound.
Exporting an LLM to ONNX and expecting a chat server.
A plain export has no KV cache, sampling or batching; you need a cache-aware export and a loop such as ONNX Runtime GenAI.

Interview questions

Why is loading a pickle checkpoint dangerous, in one sentence?
A pickle is a program whose GLOBAL and REDUCE opcodes import and call any function, and loading runs it.
Describe the safetensors layout.
An 8-byte little-endian header length, a JSON header (dtype, shape, data offsets per tensor, string metadata), then one contiguous buffer; tensors can be mapped and sliced in place.
What does GGUF carry that safetensors does not?
Tokenizer, chat template, architecture numbers and its own quantization types, as typed metadata in the same file.
Why does memory-mapping speed up loading?
Nothing is copied or parsed up front; pages come in on first touch, can be shared between processes, and only the parts a process uses are read.
Two Q4 formats both cost 4.5 bits per weight. What can still differ?
Group size, whether there is an offset, scale precision, and where scales live in the file (GGUF interleaves them per block; MLX keeps separate tensors), which affects quality and kernel design.
Why don't vLLM and SGLang serve ONNX?
Their performance comes from a paged KV cache, custom attention kernels and per-step scheduling, which a static graph does not express.
A model's file is 20% bigger than params × 2 bytes. Where would you look?
Duplicated tied tensors (Qwen3-0.6B's lm_head), F32 tensors, or extra heads; list the header and compare byte ranges.
Is a TensorRT engine portable?
By default only to the same GPU type and TensorRT version; hardware and version compatibility modes (since 8.6) widen that at some cost.
