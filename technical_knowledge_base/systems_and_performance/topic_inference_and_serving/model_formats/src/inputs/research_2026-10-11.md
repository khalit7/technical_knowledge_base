# Model file formats: fact check (checked 2026-10-11)

## 1. GGUF spec
Source: https://github.com/ggml-org/ggml/blob/master/docs/gguf.md (living doc, fetched 2026-10-11).
- Verified. Magic: "Must be `GGUF` at the byte level: `0x47` `0x47` `0x55` `0x46`" (uint32, reads as 0x46554747 little-endian). Version: "Must be `3` for version described in this spec, which introduces big-endian support." Changelog: v1 initial; v2 changed most counts "from `uint32` to `uint64`"; v3 adds big-endian support.
- Header: uint32 magic, uint32 version, uint64 tensor_count, uint64 metadata_kv_count, then the KV pairs. Key: GGUF string, ASCII, lower_snake_case dotted, at most 65535 bytes.
- Metadata value type enum (uint32): 0 UINT8, 1 INT8, 2 UINT16, 3 INT16, 4 UINT32, 5 INT32, 6 FLOAT32, 7 BOOL, 8 STRING, 9 ARRAY, 10 UINT64, 11 INT64, 12 FLOAT64. Array = element type (uint32) + uint64 count ("Number of elements, not bytes") + values; arrays may nest.
- String: uint64 len (bytes) + UTF-8 bytes, "non-null-terminated".
- Tensor info: name (GGUF string, at most 64 bytes), uint32 n_dimensions ("Currently at most 4"), uint64 dimensions[n], ggml_type type (uint32 enum), uint64 offset: "relative to `tensor_data`, not to the start of the file"; must be a multiple of ALIGNMENT. Padding after the tensor infos to ALIGNMENT, then tensor_data.
- general.alignment: uint32, "must be a multiple of 8 ... If the alignment is **not** specified, assume it is `32`." Padding bytes are 0x00.
- Endianness: "Models are little-endian by default. They can also come in big-endian ... At the time of writing, there is no way to determine if a model is big-endian ... If no additional information is provided, assume the model is little-endian."
- Predecessors: "successor file format to GGML, GGMF and GGJT". GGML unversioned, no alignment; GGMF = GGML plus versioning (one version); GGJT aligns tensors for mmap (v1--v3). Key change vs GGJT: typed key-value metadata instead of "a list of untyped values".
- ggml_type ids in the spec now run to 39 (MXFP4); TQ1_0 = 34, TQ2_0 = 35; Q4_0_4_4/4_8/8_8 (31--33) and IQ4_NL_x_x (36--38) are removed from GGUF files.
- Landing in llama.cpp: PR #2398 "GGUF", opened 2023-07-26, merged 2023-08-21 (https://github.com/ggml-org/llama.cpp/pull/2398, GitHub API).

## 2. safetensors
Sources: README https://github.com/safetensors/safetensors (repo moved from huggingface/safetensors to the safetensors org); Rust source safetensors/src/tensor.rs (main, fetched 2026-10-11).
- Verified format: "8 bytes: `N`, an unsigned little-endian 64-bit integer, containing the size of the header"; then N bytes of UTF-8 JSON that "MUST begin with a `{`" and "MAY be trailing padded with whitespace (0x20)"; then the byte buffer. "`data_offsets` point to the tensor data relative to the beginning of the byte buffer (i.e. not an absolute position in the file)", [BEGIN, END) with END one-past. "`__metadata__` ... free form string-to-string map. Arbitrary JSON is not allowed". Byte buffer must be fully indexed, no holes ("prevents the creation of polyglot files"); little-endian; row-major; duplicate keys disallowed.
- Header limit verified: tensor.rs line 10 `const MAX_HEADER_SIZE: usize = 100_000_000;` (100 MB decimal); README: "a limit on the size of the header of 100MB to prevent parsing extremely large JSON."
- Padding rule: the Rust writer pads the header with spaces to a multiple of 8 bytes (tensor.rs ~line 253: "// Force alignment to 8 bytes." `next_multiple_of(N_LEN)` with N_LEN = 8), so the data buffer starts 8-byte aligned. This is the reference writer's behaviour; the spec only says MAY pad.
- Dtypes (enum Dtype in tensor.rs): BOOL, F4 (MXFP4), F6_E2M3, F6_E3M2, U8, I8, F8_E5M2, F8_E4M3, F8_E8M0, F8_E4M3FNUZ, F8_E5M2FNUZ, I16, U16, F16, BF16, I32, U32, F32, C64, F64, I64, U64.
- Latest release: v0.8.0, 2026-06-09 (GitHub and PyPI); v0.9.0-rc.1 pre-release 2026-09-23.
- Audit: verified. Hugging Face "in close collaboration with EleutherAI and Stability AI, has ordered an external security audit"; done by Trail of Bits; blog 2023-05-23 (https://huggingface.co/blog/safetensors-security-audit). "No critical security flaw leading to arbitrary code execution was found." Report PDF dated 2023 (Trail of Bits file name 2023-03).
- BLOOM claim: verified, it is in the safetensors README "Benefits / Lazy loading": "For BLOOM using this format enabled to load the model on 8 GPUs from 10mn with regular PyTorch weights down to 45s."
- PyTorch Foundation: verified. Announced 2026-04-08 at PyTorch Conference EU, Paris: "Safetensors has joined the Foundation as its newest foundation-hosted project" (https://www.linuxfoundation.org/press/pytorch-foundation-announces-safetensors-as-newest-contributed-project-to-secure-ai-model-execution). The GitHub repo now lives at github.com/safetensors/safetensors.

## 4. Pickle and malicious Hub models
- Verified. Python docs (Doc/library/pickle.rst, https://docs.python.org/3/library/pickle.html): "The `pickle` module **is not secure**. Only unpickle data you trust. It is possible to construct malicious pickle data which will **execute arbitrary code during unpickling**."
- Verified opcodes (Lib/pickletools.py): GLOBAL (code 'c', protocol 0): "Push a global object (module.attr) on the stack" via `find_class(module, name)`, two newline-terminated strings follow. STACK_GLOBAL (code '\x93', protocol 4): same, module and name taken from the stack. REDUCE (code 'R', protocol 0): "Push an object built from a callable and an argument tuple", stack after `callable(*pytuple)`. Hugging Face's summary (https://huggingface.co/docs/hub/security-pickle): "The instructions that pose a threat are `STACK_GLOBAL`, `GLOBAL` and `REDUCE`."
- Verified. JFrog, 2024-02-27: "Our analysis has pinpointed around 100 instances of such models to date"; PyTorch models most common, then TensorFlow Keras; one payload gave a reverse shell. https://jfrog.com/blog/data-scientists-targeted-by-malicious-hugging-face-ml-models-with-silent-backdoor/
- Verified. ReversingLabs "nullifAI", 2025-02-06: two models (glockr1/ballr7 and who-r-u0000/0000...), PyTorch files compressed with 7z instead of ZIP, pickle "broken" after the payload; Picklescan did not flag them; reverse shell to a hard-coded IP. Reported 2025-01-20; Hugging Face removed them in "less than 24 hours" and updated Picklescan for broken pickles. https://www.reversinglabs.com/blog/rl-identifies-malware-ml-model-hosted-on-hugging-face
- Verified. Hub scanning: every pushed file gets ClamAV and a "Pickle Import scan" that lists imports (read with `pickletools.genops`, no execution) and highlights suspicious ones; "this is not 100% foolproof". https://huggingface.co/docs/hub/security-pickle (undated living doc).

- Verified. torch.onnx.export signature: `dynamo: bool = False` in v2.8.0, `dynamo: bool = True` in v2.9.0 (torch/onnx/__init__.py). So the torch.export-based exporter has been the default since PyTorch 2.9 (PyPI 2025-10-15).

"ONNX Runtime GenAI powers Foundry Local, Windows ML, and the Visual Studio Code AI Toolkit." Copilot+ not named in the README (unconfirmed). ## 6. TensorRT engines and TensorRT-LLM
- Verified (TensorRT docs, Engine Compatibility, latest = 11.x, https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html): "By default, TensorRT engines are compatible only with the version of TensorRT used to build them." and "By default, TensorRT engines are only compatible with the type of device where they were built." Version-compatible plans embed a copy of the lean runtime (unless EXCLUDE_LEAN_RUNTIME) and contain executable code, so deserialize only trusted plans. Serialized engines are also not portable across operating systems (support matrix).
- Hardware compatibility: `kAMPERE_PLUS` builds for "all NVIDIA Ampere architecture and newer architectures" (compute capability 8.0+), may cost throughput or latency; newer level `kSAME_COMPUTE_CAPABILITY` targets GPUs with the build device's compute capability (can beat AMPERE_PLUS, allows FP8 and FP4). Not on DriveOS or JetPack. Both hardware compatibility and version compatibility were introduced in TensorRT 8.6 (8.6 release notes, https://docs.nvidia.com/deeplearning/tensorrt/archives/tensorrt-861/release-notes/index.html); version compatibility works within a major version (e.g. built on 11.0, runs on later 11.x), and the current page's example says TensorRT 10 engines work with TensorRT 11 when enabled. Latest TensorRT on PyPI: 11.4.0 (2026-10-08).
- Verified. TensorRT-LLM v1.0.0 released 2025-09-24: "the PyTorch-based architecture is now stable and the default experience"; "BREAKING CHANGE Promote PyTorch to be the default LLM backend". https://github.com/NVIDIA/TensorRT-LLM/releases/tag/v1.0.0
- Correction/update on trtllm-build: deprecation warnings added to TRT-backend entry points 2026-03-31 (#11723); the legacy TensorRT engine backend's Python modules were removed 2026-07-14 (commit 7e833f7, "BREAKING: Remove python modules and tests for legacy TensorRT backend (#15918)"). tensorrt_llm/commands/build.py (trtllm-build) exists in v1.0.0 and v1.2.1 (latest stable, 2026-04-20) but is gone in v1.3.0rc29 (2026-09-29) and main. So: still in the latest stable release, removed in the 1.3 line.

## 8. Core ML
- Verified (coremltools guide "Convert models to ML programs", https://apple.github.io/coremltools/docs-guides/source/convert-to-ml-program.html): ML program is "an evolution of the neural network model type"; "An ML program decouples the weights from the program architecture, so it cannot be saved as an `.mlmodel` file." So ML programs are .mlpackage only (a directory bundle: model spec plus a weights folder); the older neural network type can be .mlmodel or .mlpackage. ML programs need iOS 15 / macOS 12+.
- Verified (Apple docs, MLModel.compileModel(at:), https://developer.apple.com/documentation/coreml/mlmodel/compilemodel(at:)): compiles a model file on device into a compiled `.mlmodelc` directory, which `MLModel(contentsOf:)` loads; Xcode does this at build time for bundled models.
- Latest coremltools: 9.0, 2025-11-10 (GitHub and PyPI; a 9.1.dev1 pre-release exists on PyPI, no 9.1 final yet).
- ANE: Core ML is the only public, supported API that schedules work on the Neural Engine (Apple exposes no public ANE programming API; reverse-engineered private-API projects exist but are unofficial). MLX does not use the ANE: MLX issue #18 "ANE support" (closed 2023-12-08), maintainer: "at the moment we don't have plans to support ANE in MLX given it is a closed source API"; reiterated 2025-05-03 "No plan for that at the moment." https://github.com/ml-explore/mlx/issues/18. Nuance: on M5, MLX uses the GPU's per-core "Neural Accelerators" (matrix units inside the GPU, not the ANE): Apple ML Research, "Exploring LLMs with MLX and the Neural Accelerators in the M5 GPU" (about 2025-11-19/20), https://machinelearning.apple.com/research/exploring-llms-mlx-m5.

## 11. MLX quantization
- Verified (mx.quantize docstring, python/src/ops.cpp on main; mlx latest v0.32.3, 2026-09-29; docs https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.quantize.html): `quantize(w, group_size=None, bits=None, mode='affine', *, global_scale=None)`, returns (w_q, scales, biases); biases only for affine. Modes table (default marked *): affine group 32, 64*, 128; bits 1, 2, 3, 4*, 5, 6, 8; scale same dtype as input; bias yes. mxfp4 group 32, 4 bits, e8m0 scale, no bias. mxfp8 group 32, 8 bits, e8m0. nvfp4 group 16, 4 bits, e4m3 scale (optional float32 global_scale). Affine: s = (max - min)/(2^b - 1), q = round((w - min)/s); stores s as scales and min (beta) as biases; packed low-to-high into uint32 (8 x 4-bit per word).
- Version history (checked ops.cpp at tags): mxfp4 first in v0.29.0 (2025-08-29); mxfp8 and nvfp4 first in v0.29.4 (2025-11-11), present in v0.30.0 (2025-11-19). Correction if the page says they all arrived together.
- Verified (mlx-lm mlx_lm/utils.py `quantize_model`, main; mlx-lm 0.32.0, PyPI 2026-10-01): writes `config["quantization"] = {"group_size": g, "bits": b, "mode": m}` and mirrors it to `config["quantization_config"]` ("support hf model tree"); mixed-precision recipes add per-layer entries keyed by module path inside "quantization". Loader treats missing "mode" as "affine". mlx-lm also maps compressed-tensors formats (nvfp4/mxfp4) on load.

## 13. fastsafetensors
- Verified. arXiv 2505.23072 "Speeding up Model Loading with fastsafetensors" (Yoshimura, Chiba, Sethi, Waddington, Sundararaman; IBM Research; v1 2025-05-29; IEEE CLOUD 2025). Abstract: copies groups of tensors straight to device memory and instantiates them there instead of deserializing each in host memory, enabling parallel copies and peer-to-peer DMA; "performance improvements of 4.8x to 7.5x in loading models" such as Llama 7B, 13B, 70B, Falcon 40B, Bloom 176B.
- Repo README (github.com/foundation-model-stack/fastsafetensors): "reached 26.4 GB/s NVMe read throughput for Llama-70B on four GPUs with GDS" (GPUDirect Storage via cuFile; a `nogds` fallback exists); vLLM startup "12.39s to 4.74s" for Llama-2-13B on 4x L40S, "16.04s to 6.88s" on 1x A100. vLLM and SGLang take `--load-format fastsafetensors`. Latest 0.4.0 (PyPI 2026-09-07).

## 15. GGUF ternary types TQ1_0 / TQ2_0, and BITCOS wording
- Verified (llama.cpp ggml/src/ggml-common.h, master, 2026-10-11), super-block QK_K = 256:
  - TQ1_0, comment "// 1.6875 bpw": qs[(QK_K - 4*QK_K/64)/5] = 48 bytes, "5 elements per byte (3^5 = 243 < 256)" (240 weights); qh[QK_K/64] = 4 bytes, "4 elements per byte" (16 weights); one fp16 scale d (2 bytes). 54 bytes / 256 = 1.6875 bpw.
  - TQ2_0, comment "// 2.0625 bpw": qs[QK_K/4] = 64 bytes "2 bits per element" + fp16 d = 66 bytes / 256 = 2.0625 bpw.
  - GGUF type ids: TQ1_0 = 34, TQ2_0 = 35 (gguf.md).
- Added by llama.cpp PR #8151 "ggml-quants : ternary packing for TriLMs and BitNet b1.58" (author compilade), merged 2024-09-06. https://github.com/ggml-org/llama.cpp/pull/8151
- BITCOS paper: "Breaking the 1.58-bit Barrier for Ternary LLMs", Georganas, Heinecke, Dubey (Intel), arXiv 2609.16338v1, 2026-09-14. Exact abstract wording: "The prevailing deployment format packs five ternary weights into one byte (five-trit packing), and due to the power-of-two group sizes used in practice this rounds up to $1.625$ bits per weight." Baseline "log2 3 ~ 1.585 bits per weight". BITCOS costs "2 - z bits per weight" (z = zero density); zeros up to 51.5% of weights across 29 models; beats five-trit packing in 26 of 29; best 1.485 bpw; kernel gain up to 1.28x; decode up to 1.18x CPU, 1.27x GPU. Note for the page: pure five-trit packing is 8/5 = 1.6 bpw; 1.625 is the paper's figure after power-of-two grouping (e.g. 256 weights need 52 bytes); llama.cpp's TQ1_0 adds an fp16 scale per 256 and lands at 1.6875. The paper does not state "1.6".

## 16. Parser and template attack surface
- Verified with correction. ## 17. compressed-tensors
- Verified. README (https://github.com/vllm-project/compressed-tensors; repo moved from neuralmagic): "extends the safetensors format, providing a versatile and efficient way to store and manage compressed tensor data", covering GPTQ, AWQ, SmoothQuant, SparseGPT across INT8, FP8, NVFP4, MXFP4, MXFP8; works with llm-compressor, vLLM, SGLang. ## 18. PT2 archive and torch.save zip format
- Verified. PT2 Archive Spec (https://docs.pytorch.org/docs/main/user_guide/torch_compiler/export/pt2_archive.html): the format produced by `torch.export.save` and AOTInductor `aoti_compile_and_package`; "The archive is a zipfile, and can be manipulated using standard zipfile APIs." Layout: `archive_format` ("pt2"), `.data/version`, `models/<name>.json` (serialized ExportedProgram), `data/weights/` (one raw-bytes file per tensor, mapped by `<name>_weights_config.json`), `data/constants/`, `data/aotinductor/` (compiled artifacts), `extra/`. Weights are raw blobs, not pickle (sample inputs use torch.save). Introduced as "a new package format, PT2 archive" in PyTorch 2.6 (blog 2025-01-29).
- Verified. torch/serialization.py: v1.5.0 `_use_new_zipfile_serialization=False`; v1.6.0 `=True`; main docstring: "The 1.6 release of PyTorch switched `torch.save` to use a new zip file-based format." (The zip holds data.pkl plus one file per storage; still pickle.)
