A trained model is a few hundred named arrays of numbers plus the facts needed to use them. A model format is the agreement on how those arrays and facts are written to disk. This page reads real files byte by byte (the Qwen3 models measured across this topic), so every claim below can be checked against bytes you can see in the {{File explorer|#t-bytes}} tab.

The running example is the one from the parent page, {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}: a chat assistant serving many users. In the datacenter its model (the parent's planner uses Llama 3.1 70B in FP8 on H200) arrives at vLLM as a folder of safetensors shards plus a config.json. On a laptop, the same kind of model arrives as one GGUF file for llama.cpp or an MLX folder. Same idea, three ways of writing it down. Qwen3-0.6B is the specimen: small enough to convert many times, built exactly like its bigger siblings.

Most confusion about formats comes from mixing up three separate layers. Keep them apart and almost every question answers itself:

1. Container

How bytes are laid out: where each tensor starts, what metadata travels with it, and whether reading the file can run code. safetensors, GGUF, pickle, ONNX's protobuf, flatbuffers.

2. Number encoding

How each number is stored: BF16, FP8, or a quantization scheme such as GGUF's Q4_K or MLX's 4-bit affine groups. The container says which; the scheme says how to decode it.

3. Compiled artifact

A build output tied to one runtime and one kind of hardware: a TensorRT engine, a Core ML compiled model. Not something to distribute; something to rebuild.

GGUF is unusual because it fuses layers 1 and 2 (its quantization types are defined inside the format). safetensors deliberately owns only layer 1. A TensorRT engine is layer 3 and is not really a model format at all. The table is the whole page in one view; each row has a section below.
