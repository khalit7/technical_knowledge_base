5. MLX: safetensors with packed groups

The idea. MLX, Apple's array framework, did not invent a container: an MLX model is a Hugging Face-style folder whose weights are safetensors and whose config.json says how they are quantized. What it adds is a layout for quantized weights. mlx_lm convert -q wrote this into our Qwen3-0.6B config (and mirrored it as quantization_config for Hugging Face tools):

"quantization": { "group_size": 64, "bits": 4, "mode": "affine" }

How it works. Each quantized linear layer becomes three tensors: weight holds the 4-bit codes packed eight to a 32-bit word (lowest bits first), and scales and biases hold one BF16 scale s and one offset b for every group of 64 weights; each weight is s·q + b ({{mx.quantize|https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.quantize.html}}). That is why the 4-bit file has tensors where the BF16 one has 310. For layer 0's key projection (1,024 × 1,024 weights):

Tensordtypeshapewhy

k_proj.scalesBF16[1024, 16]1,024 / 64 groups per row

Below, the same 256 weights (the start of that row) as one GGUF Q4_K super-block and as four MLX groups, drawn byte for byte. Both cost exactly 144 bytes, 4.5 bits per weight; the difference is the layout. GGUF keeps the scales next to their codes inside one block; MLX keeps codes, scales and biases in three separate tensors, so the bytes of one group live in three places in the file.

We decoded the first MLX group by hand (first word 06 b5 ae cb = 3,417,224,454 → codes 6, 0, 5, 11, 14, 10, 11, 12) and the result equals mx.dequantize exactly run here, mlx 0.32.3. MLX also has non-affine modes: mxfp4 since v0.29.0 (2025-08-29) and mxfp8 and nvfp4 since v0.29.4 (2025-11-11); affine allows 2 to 8 bits (and 1) with groups of 32, 64 or 128.

Cost and speed. The conversion is cheap and repeatable: two runs of mlx_lm convert took 2.3 and 1.7 s and produced the same SHA-256 as the copy made for the shared store two days earlier. Loading needs no copy to a GPU, because Apple silicon's GPU reads the same unified memory. MLX does not use the Neural Engine; its maintainers have said so since 2023 ({{mlx issue #18|https://github.com/ml-explore/mlx/issues/18}}). How fast and how accurate MLX's types are against GGUF's on the same model is measured on {{Local and on-device inference|n:3c65c17b0d0d81f7a144fe25d799e811}}.

6. ONNX: the model as a graph

The idea. Every format so far stores only weights; the code that uses them lives in the engine. ONNX (Open Neural Network Exchange) stores the computation too: a graph of operators (MatMul, Softmax, ...) wired by named tensors, the weights as initializers, and an opset version that pins the exact meaning of every operator: "When the inventory of a given operator set changes ... its version MUST increase" ({{Versioning.md|https://github.com/onnx/onnx/blob/main/docs/Versioning.md}}). A graph exported today therefore runs on a runtime written years later, on CPU, GPU, or an NPU vendor's SDK. The file is a protobuf message, and protobuf messages cannot exceed 2 GB, so larger models keep their weights in an external data file referenced by path, offset and length ({{ExternalData.md|https://github.com/onnx/onnx/blob/main/docs/ExternalData.md}}).

What a decoder becomes run here: PyTorch 2.14.1 exporter (dynamo, the default since 2.9), onnx 1.23.2, ONNX Runtime 1.31.0. We exported Qwen3-0.6B's forward pass (token ids in, logits out, batch and sequence length left dynamic) and opened the result:

Reading it. There is no "attention" or "RMSNorm" operator: attention became MatMul, Softmax (, one per layer), Transpose and Reshape; each RMSNorm became Pow, ReduceMean, Sqrt and Reciprocal (113 of each: 4 norms in each of 28 layers, counting the per-head query and key norms, plus the final one) with an Add and Muls around them. And there is no KV cache: this graph recomputes the whole sequence on every call. To generate text you export a variant whose inputs and outputs include each layer's past keys and values, and run the loop, sampling and cache yourself, or use {{ONNX Runtime GenAI|https://github.com/microsoft/onnxruntime-genai}}, which "implements the generative AI loop for ONNX models" including "KV cache management" and powers Foundry Local, Windows ML and the VS Code AI Toolkit (v0.17, 2026-09-28). One pitfall we hit: with an example batch of 1, torch.export fixed the batch dimension at 1; export with a batch of 2.

Where it fits. ONNX is the right answer for encoders (embeddings, rerankers), classic ML, and NPUs or Intel hardware whose toolchains ingest it. Datacenter LLM engines (vLLM, SGLang, TensorRT-LLM) do not use it: their speed lives in a paged KV cache, custom attention kernels and a scheduler that changes the batch every step, none of which is a fixed graph (see {{vLLM: inside the default engine|n:3c65c17b0d0d8113b976d8bcaf2c0722}}). The current onnx release is 1.23.2 (2026-10-06), defining opset 28; PyTorch 2.14's exporter wrote opset 20 by default.
