3. safetensors, byte by byte

The idea. Remove the program. A safetensors file is three things in a row, and nothing in it can name a function ({{format spec|https://github.com/safetensors/safetensors}}):

  1. 8 bytes: an unsigned 64-bit little-endian integer N, the length of the header.
  2. N bytes of JSON: for every tensor its dtype, shape and data_offsets [begin, end), counted from the start of the data buffer, plus an optional __metadata__ map of strings to strings ("Arbitrary JSON is not allowed").
  3. The data buffer: every tensor's raw bytes, back to back, little-endian, row-major. The spec forbids holes and overlaps, which also rules out "polyglot" files that hide a second payload.

The header is bytes describing tensors, of the file. A reader parses that JSON, and then each tensor is a slice of the file at a known place: no parsing, no conversion. The Rust reference implementation refuses headers over 100 MB (MAX_HEADER_SIZE = 100_000_000, {{tensor.rs L10|https://github.com/safetensors/safetensors/blob/main/safetensors/src/tensor.rs}}) so a hostile file cannot make you allocate gigabytes of JSON, and its writer pads the header with spaces to a multiple of 8 bytes, so the buffer starts 8-byte aligned (the Qwen file's header ends in one space). MLX's own writer does not pad: the MLX file's header is bytes, 4 more than a multiple of 8, which the format allows. Step through all three files field by field in the {{File explorer|#t-bytes}}.

Status, October 2026
A Trail of Bits audit commissioned by Hugging Face with EleutherAI and Stability AI found "no critical security flaw leading to arbitrary code execution" (2023-05-23, {{HF blog|https://huggingface.co/blog/safetensors-security-audit}}). safetensors became a PyTorch Foundation project on 2026-04-08 ({{announcement|https://www.linuxfoundation.org/press/pytorch-foundation-announces-safetensors-as-newest-contributed-project-to-secure-ai-model-execution}}) and moved to the github.com/safetensors organisation; the latest release is v0.8.0 (2026-06-09). Its dtype list now runs from F64 down to F8 (E4M3, E5M2, E8M0) and F4/F6 for microscaling formats.

What it cannot say: tied weights are stored twice

Qwen3-0.6B's config says tie_word_embeddings: true: the input embedding and the output layer (lm_head) are one shared matrix in the model. safetensors has no way to say "this tensor is that one" (an alias), so the released file stores both, and we checked that the two byte ranges hash the same measured here: bytes (, of the file) are a duplicate. Qwen3-1.7B does the same in its second shard; Qwen3-4B's checkpoint does not. Downstream tools disagree on what to do: MLX's converter honours the tie and keeps one copy ( tensors), llama.cpp's converter keeps both (section 4). The quality cost of that on GGUF quant types is on {{Local and on-device inference|n:3c65c17b0d0d81f7a144fe25d799e811}}.

Shards and the index

Big checkpoints are split into shards, model-00001-of-00002.safetensors and so on, with model.safetensors.index.json mapping every tensor name to its shard. Qwen3-1.7B's index has 311 entries; the second shard holds exactly one tensor, the duplicate lm_head.weight. transformers chooses the split when saving: max_shard_size defaulted to "5GB" in v4 and "50GB" from v5.0.0 (2026-01-26). The Hub recommends files under 200 GB and enforces 500 GB per file ({{Hub storage limits|https://huggingface.co/docs/hub/storage-limits}}).

Why it is fast: mapping, not reading

To memory-map (mmap) a file is to ask the operating system to make the file appear as memory without reading it. Nothing is copied until a byte is touched; then the OS brings in that 16 KiB page (on Apple silicon) from its page cache, the RAM it uses to keep recently read files. Because safetensors tensors sit at known offsets in their final layout, a loader can hand out slices of the mapping directly. A pickle checkpoint must run its program first and, by default, copy every storage into fresh memory.

Reading it. Plain torch.load took and MiB of new memory before you could use anything. safetensors.torch.load_file returned in with MiB, because it maps the file and the tensors are views; touching every page then took in total. torch.load(mmap=True) closes most of the gap for the zip format (, then touched), but still runs the pickle program. With a cold cache all of these become disk-bound: the production child measured this laptop's SSD at about 3.2 GB/s for cold starts ({{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}).
