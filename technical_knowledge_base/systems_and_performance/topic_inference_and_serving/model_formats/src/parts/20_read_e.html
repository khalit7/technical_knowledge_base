4. GGUF, byte by byte

The idea. GGUF goes the other way from safetensors: one file, everything in it. Tensors, tokenizer, chat template and architecture numbers travel together, the last three as typed key/value metadata. llama.cpp, Ollama and LM Studio read it; the specification is short ({{gguf.md|https://github.com/ggml-org/ggml/blob/master/docs/gguf.md}}) and llama.cpp's header file sums it up in 30 lines ({{gguf.h L1-L30|https://github.com/ggml-org/llama.cpp/blob/b11146/ggml/include/gguf.h}}):

  1. Magic GGUF (bytes 47 47 55 46), version (u32, now 3), tensor count and key/value count (64-bit each).
  2. Key/value pairs: a key string (a u64 length, then the bytes), a value type (one of 13: integers, floats, bool, string, array), the value. Keys are namespaced: general.architecture, qwen3.attention.head_count, tokenizer.ggml.tokens.
  3. Tensor infos: for each tensor its name, number of dimensions, the dimensions, its type, and its offset into the data section.
  4. Padding with zero bytes up to general.alignment (32 when absent), then the data section; every tensor's offset is a multiple of the alignment, so the file can be mapped and each tensor used in place.

Tap a segment.

One trap when reading GGUF. Dimensions are stored fastest-first, the reverse of PyTorch: the embedding that safetensors lists as [151936, 1024] appears in GGUF as [1024, 151936]. Same bytes, same row-major order, opposite way of writing the shape.

Each tensor carries its own type: Q4_K_M is a recipe

Because the type is per tensor, one file mixes several. "Q4_K_M" is a recipe chosen by llama-quantize, not one type: in this file 168 tensors are Q4_K, 29 are Q6_K (the embedding, and the value projection and FFN down projection in 14 of the 28 layers) and 113 small vectors stay F32. Averaged over every value it is bits per weight, not 4.

What each type does to quality, measured on Qwen3-1.7B and 4B with perplexity and KL divergence, is the {{Quant ladder|n:3c65c17b0d0d81f7a144fe25d799e811}} tab of Local and on-device inference, which also shows one 32-weight block in five formats. This page only needs the file layout of a block. A Q4_K super-block holds 256 weights in 144 bytes ({{ggml-common.h L325-L338|https://github.com/ggml-org/llama.cpp/blob/b11146/ggml/src/ggml-common.h}}): two F16 numbers d and dmin, 12 bytes packing eight 6-bit scales and eight 6-bit minimums (one pair per 32 weights), and 128 bytes of 4-bit codes. Self-contained, but check what it contains

The case for GGUF is that nothing can drift: no separate tokenizer, config or template to fall out of sync, so ollama run works from one file. That holds only for what the person who made the file put in it. We compared the GGUF in the shared store (made by Unsloth from Qwen3-0.6B) with one we converted ourselves from the same Qwen release checked here:

Both run: when output.weight is missing, llama.cpp's Qwen3 loader reuses the embedding ({{qwen3.cpp L22-L25|https://github.com/ggml-org/llama.cpp/blob/b11146/src/models/qwen3.cpp}}). But they are not the same artifact, and a template rewritten by a third party is exactly the drift GGUF was supposed to remove. Check the template and the stop ids of any GGUF you deploy (llama-server prints the template at start; gguf-py's gguf-dump lists every key). The converter writes the BF16 file deterministically: two runs gave the same SHA-256, and so did llama-quantize re-run on the store's BF16 file (details in the {{Conversion map|#t-conv}}).

Splitting a GGUF

Files over a hosting limit are split with llama-gguf-split into name-00001-of-00003.gguf and so on. We split the 397 MB file at 150 MB run here: the first shard carries all 28 metadata keys plus three split.* keys and 28 tensors; the others carry only the split.* keys and their tensors (179 and 103). Pointing llama.cpp at the first shard loads all three, with no index file, and --merge gave back all 310 tensors byte-identical (the merged file is 96 bytes larger: the split keys stay).

Where it came from, and its costs

  • History. GGUF replaced llama.cpp's earlier files (GGML, then GGMF with a version, then GGJT with aligned tensors for mmap), whose hyperparameters were an untyped positional list, so each new architecture broke old loaders. GGUF's typed, named metadata fixed that; it landed in llama.cpp with {{PR #2398|https://github.com/ggml-org/llama.cpp/pull/2398}} on 2023-08-21; version 3 added big-endian files. The library keeps the name ggml, and the ggml.ai team joined Hugging Face on 2026-02-20 ({{announcement|https://github.com/ggml-org/llama.cpp/discussions/19759}}), with the projects staying community-run.
  • New architectures wait for the converter. Every family needs its own code in llama.cpp's converter (in b11146 a package of per-family modules) and its own graph in llama.cpp, so a new model can take days to months to get a working GGUF.
  • No code, but not no risk. GGUF has no opcodes, yet a parser reading lengths from a hostile file is attack surface: Databricks reported heap overflows in gguf_init_from_file (CVE-2024-25664 to 25668, 2024-03-22, {{Databricks|https://www.databricks.com/blog/ggml-gguf-file-format-vulnerabilities}}) and Cisco Talos reported others (CVE-2024-21836 and three more). Today's parser rejects strings over 1 GiB and arrays over 230 elements ({{gguf.cpp L19-L20|https://github.com/ggml-org/llama.cpp/blob/b11146/ggml/src/gguf.cpp}}). And the embedded chat template is a program: llama-cpp-python rendered it with an unsandboxed Jinja2 until 0.2.72 ({{CVE-2024-34359|https://github.com/abetlen/llama-cpp-python/security/advisories/GHSA-56xg-wfcc-g829}}, CVSS 9.6, 2024-05-10).
  • Packing can change without the model changing. Ternary models (weights in {−1, 0, +1}) need log23 ≈ 1.585 bits each. GGUF's TQ1_0 packs mostly five weights per byte (35 = 243 fits in 256) plus an F16 scale per 256 weights, 1.6875 bits per weight, and TQ2_0 spends 2.0625 ({{PR #8151|https://github.com/ggml-org/llama.cpp/pull/8151}}, 2024-09-06). BITCOS ({{arXiv 2609.16338|https://arxiv.org/abs/2609.16338}}, Intel, 2026-09-14) notes that five-trit packing "rounds up to 1.625 bits per weight" with power-of-two groups and that zeros reach up to 51.5% of weights in the 29 models it studied; storing a presence bitmap and the signs costs 2 − z bits (z the zero share), beats five-trit packing on 26 of 29 models, reaches 1.485 bits, and speeds decoding up to 1.18x on CPU and 1.27x on Intel Xe2 GPUs authors' claims, not run here. Same model, different bytes: that is the layer a format owns.
