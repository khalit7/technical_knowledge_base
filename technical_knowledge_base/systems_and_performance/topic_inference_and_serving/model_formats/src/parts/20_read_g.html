7. Compiled artifacts and on-device formats

None of these were run here (no NVIDIA GPU, no phone toolchain); every fact is from the project's documentation or release notes, dated.

TensorRT engines are build outputs. NVIDIA's builder profiles kernels on the actual GPU, fuses layers, picks memory layouts and serializes the result with the weights into a plan (.plan or .engine). The documentation is direct: "By default, TensorRT engines are compatible only with the version of TensorRT used to build them" and "only compatible with the type of device where they were built" ({{Engine compatibility|https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html}}). Since TensorRT 8.6 two opt-ins loosen that: hardware compatibility (one plan for Ampere and newer, at some speed cost) and version compatibility (later releases of the same major version). Version-compatible plans embed runtime code, so deserialize only plans you trust. Treat plans as a cache keyed on (model, GPU, TensorRT version, shape profiles), built in CI, never as the model you publish.

TensorRT-LLM moved away from them. Since v1.0.0 (2025-09-24) its PyTorch backend is "the default experience": point it at safetensors and it uses NVIDIA's kernels without a build artifact. The old trtllm-build engine path is still in the latest stable release, v1.2.1 (2026-04-20), but was removed on main on 2026-07-14 and is gone from the 1.3 release candidates ({{releases|https://github.com/NVIDIA/TensorRT-LLM/releases}}). How it serves is on {{Distributed and disaggregated serving|n:3c65c17b0d0d8170bd7cdf47af0ec07b}}.

8. The Hugging Face repo: the source of truth

Almost every format above is made from one place: a Hugging Face model repo. Knowing its files is what lets you debug "the model loads but answers badly". The real Qwen3-1.7B repo (section 1's bar) holds:

FileWhat it decides
model-0000N-of-0000M.safetensorsThe weights, sharded (section 3).
model.safetensors.index.jsonweight_map: tensor name to shard, plus total_size (4,063,479,808 bytes here).
config.jsonArchitecture (architectures: Qwen3ForCausalLM, layers, heads, tie_word_embeddings, torch_dtype) and, for quantized checkpoints, quantization_config.
generation_config.jsonRecommended sampling and the end-of-turn ids (Qwen3: two).
tokenizer.json, vocab.json, merges.txt, tokenizer_config.jsonThe tokenizer; tokenizer_config.json also held the chat template in older repos.
chat_template.jinjaThe template as its own file, the newer layout: mlx-lm wrote one into our MLX folder.

Quantized checkpoints stay in safetensors. FP8, INT4 or NVFP4 checkpoints served by vLLM and SGLang are usually compressed-tensors, which "extends the safetensors format": the packed weights and their scales are ordinary tensors, and config.json carries "quant_method": "compressed-tensors" with a format such as pack-quantized or nvfp4-pack-quantized ({{repo|https://github.com/vllm-project/compressed-tensors}}, 0.19.0, 2026-09-21). It is written by llm-compressor. That is how the parent's FP8 Llama 3.1 70B arrives at vLLM. The methods (GPTQ, AWQ, FP8, NVFP4) are on {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}.

Remote code. A repo can also ship Python modeling files. transformers runs them only when you pass trust_remote_code=True, which is pickle's risk again by a different door: read the code first or pin a revision you have read.
