Reading the log. Each decode batch prints a line such as #running-req: 233, #token: 370959, token usage: 0.82, gen throughput (token/s): 4594.01, #queue-req: 317 (the docs' example on an H100-class GPU). Token usage above 0.9 with a queue means the pool is the limit; a queue of 0 in an offline job means the client is not sending fast enough (the docs suggest 100 to 2,000 waiting for offline throughput); frequent retraction means the scheduler admitted more than fit. 8. The router: keeping a conversation where its cache is

The problem. With several replicas of a model (data parallelism), each has its own radix tree. A round-robin load balancer sends a conversation's next turn to a replica that has never seen it, so the cache hit rate falls toward one over the number of replicas. Sending every request to the replica with its prefix concentrates popular prefixes on one replica. The router has to trade cache affinity against load.

How SGLang's router decides ({{cache_aware.rs, select_worker L387|https://github.com/sgl-project/sglang/blob/v0.5.21/sgl-model-gateway/src/policies/cache_aware.rs#L387}}). The router (now the SGLang Model Gateway, written in Rust) keeps an approximate radix tree per worker of the request texts it has sent there, in characters rather than tokens so it never tokenizes, and never asks the workers what they actually hold. For each request:

  1. If the load is imbalanced (the busiest worker has more than balance_abs_threshold requests more than the idlest and more than balance_rel_threshold times as many), send it to the least loaded worker.
  2. Otherwise find the worker whose tree matches the longest prefix of the text. If the matched share exceeds cache_threshold, send it there.
  3. Otherwise send it to the least loaded worker (the file's header comment says "smallest tree size"; the code picks the least loaded, ties broken at random).
  4. Insert the text into the chosen worker's tree; trees are trimmed least recently used on a timer.

The command-line defaults are a 0.3 cache threshold, 64 requests absolute and 1.5 times relative imbalance, eviction every 120 s and up to 226 tree nodes ({{main.rs L150-170|https://github.com/sgl-project/sglang/blob/v0.5.21/sgl-model-gateway/src/main.rs#L150}}); the Rust struct's own Default (0.5, 32, 1.1, 30 s, 10,000) and the Python launcher (eviction 60 s) disagree with them, so check which entry point you use. The v0.4 post reported 1.9 times the throughput and a hit rate of 75% against 20% with 8 replicas on a workload of long shared-prefix groups ({{LMSYS, 2024-12-04|https://lmsys.org/blog/2024-12-04-sglang-v0-4/}}) vendor, one workload. The other policies are round_robin, random, power_of_two (pick the less loaded of two random workers), prefix_hash, consistent_hashing and bucket ({{policies/|https://github.com/sgl-project/sglang/tree/v0.5.21/sgl-model-gateway/src/policies}}).

A router in front of real replicas, measured on this machine against round robin and least-loaded, is on {{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}; the routing picture is on the root's Reading tab, section 9. The gateway also does prefill/decode routing, retries, circuit breakers, rate limits and tokenization in Rust ({{README|https://github.com/sgl-project/sglang/tree/v0.5.21/sgl-model-gateway}}).

9. Large scale: DeepSeek on 96 GPUs and on a rack

SGLang's large-scale recipes target mixture-of-experts models such as DeepSeek-V3/R1 (671 billion parameters, 37 billion active per token, 256 routed experts per layer, multi-head latent attention with one compressed KV vector per token). Serving them well needs four ideas, each explained in depth on {{Distributed and disaggregated serving|n:3c65c17b0d0d8170bd7cdf47af0ec07b}}:

DP attentionWith MLA there is a single KV head, so splitting attention across GPUs by heads (tensor parallelism) would copy the whole KV cache to every GPU. SGLang instead runs attention data-parallel, each GPU holding different requests' KV, and gathers only around the expert layers; v0.4 reported 1.9 times decode throughput from it vendor.
Expert parallelism (EP) with DeepEPEach GPU holds a slice of the experts; every token is sent to the GPUs holding its chosen experts and back (all-to-all), with DeepEP's normal mode for prefill and low-latency mode for decode (--moe-a2a-backend deepep, {{EP docs|https://docs.sglang.io/docs/advanced_features/expert_parallelism}}).
EPLBSome experts are far more popular; DeepSeek's expert-parallel load balancer replicates hot experts into redundant slots (256 plus 32 = 288), which also allows 12 or 72 GPUs instead of powers of two.
Two-batch overlapSplit the batch in two so one half's all-to-all runs while the other half computes; on GB200 NVL72's faster links SGLang moved to finer single-batch overlap.
Prefill/decode disaggregationPrefill and decode run on different GPU pools and the KV cache moves between them over RDMA with Mooncake or NIXL ({{PD docs|https://docs.sglang.io/docs/advanced_features/pd_disaggregation}}); v0.5.21 lets an instance switch role without a restart ({{#28403|https://github.com/sgl-project/sglang/pull/28403}}).
