SGLang keeps the KV cache of every finished request in a radix tree of token runs, so a later request that begins with the same tokens skips recomputing them; its scheduler, router and structured-output path are built around reusing that tree.

Where each idea acts: one request through an SGLang deployment

Three processes per server talk over ZeroMQ sockets so that tokenizing, scheduling and detokenizing never block one another: the HTTP server with the TokenizerManager (OpenAI-compatible or native /generate; chat template, token ids), the Scheduler, one per GPU rank, which owns the waiting queue, the radix tree and the KV pool and runs the model ({{scheduler.py|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/scheduler.py}}), and the DetokenizerManager, which turns new ids into text and streams it ({{detokenizer_manager.py|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/detokenizer_manager.py}}). The tree lives on the CPU and maps runs of token ids to slot numbers in the GPU's KV pool; the KV itself never moves. Everything this page says about caching and ordering happens inside the Scheduler. Section numbers in the figure point to where each part is explained.

You need: prefill, decode and the KV cache (the keys and values every layer computed for every earlier token) from the parent {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}; continuous batching, paged attention and prefix caching as ideas (keeping the KV after a request ends so the next request with the same beginning reuses it) from {{Batching, KV cache and scheduling in depth|n:3c65c17b0d0d819db53bd2c48909e5b2}}. The other engine, read the same way, is {{vLLM: inside the default engine|n:3c65c17b0d0d8113b976d8bcaf2c0722}}.

Radix tree
a prefix tree whose edges carry whole runs of tokens; a node exists only where two cached sequences part (section 2).
Lock reference
a count of running requests using a node; a locked node cannot be evicted.
Schedule policy
the order of the waiting queue: fcfs (default), or cache-aware lpm (longest prefix match) and dfs-weight (section 4).
Overlap scheduler
the loop that prepares step k plus 1 on the CPU while the GPU runs step k (section 5).
Retraction
SGLang's word for preemption: a running request is pushed back to the queue and recomputed later (section 7).
HiCache
the radix tree extended over host memory and storage (section 7).
The short answer
On the same requests the radix tree and vLLM's hash blocks reuse almost exactly the same tokens (within 0.8 points, section 3). SGLang's edge, where it has one, comes from what sits around the cache: queue ordering when the cache is scarce, the router, structured-output plumbing and the large-scale MoE recipes; and both engines move fast enough that any benchmark older than a few months says little about today.

How this page knows: the evidence behind it (provenance)

Everything is read from source at SGLang v0.5.21 (tag commit e00930c5) and vLLM v0.31.0, with file and line beside each claim. Three kinds of evidence are added to the published record, each labelled where it appears: the engines' own prefix-cache classes replayed on the same request traces (section 3); SGLang's own scheduling-policy code ordering real queues (section 4); and SGLang v0.5.21 built from source and run on an Apple M1 Pro through its MLX backend (sections 3 to 6 and 11), which also surfaced bugs on Apple silicon: the release would not start, its cache returned another request's text, and eviction, chunked prefill and cache flushes crashed it. The independent comparison of the two engines is SemiAnalysis InferenceX (section 10). The small open model measured here is Qwen3-0.6B (28 layers, 8 KV heads of 128 dimensions, so 114,688 bytes of KV per token at 16-bit precision, as the root's {{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} tab measured); the running example is the root's chat assistant.
