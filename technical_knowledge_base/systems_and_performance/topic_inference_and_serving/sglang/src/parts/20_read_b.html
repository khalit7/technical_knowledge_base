1. Where it came from, and the frontend language

The problem it started from. In late 2023 most engines threw a request's KV cache away the moment the request finished, yet real traffic repeats itself: every chat turn resends the whole conversation, few-shot prompts resend the same examples, an agent resends its growing history on every step, and a self-consistency run asks the same question several times. The SGLang paper ({{Zheng et al., arXiv 2312.07104|https://arxiv.org/abs/2312.07104}}, December 2023, NeurIPS 2024, from the LMSYS group behind Vicuna and Chatbot Arena) proposed two things: a runtime that keeps every request's KV cache in a radix tree so that calls share whatever prefix they have in common (RadixAttention), and a small Python language for programs that make many model calls. The authors report up to 6.4 times the throughput of the systems they compared against authors' measurement.

The frontend language (python/sglang/lang, still shipped) writes a multi-call program as a function over a prompt state s: gen generates into a named variable, select picks among fixed choices by their likelihood, and fork copies the state into parallel branches. Adapted from the frontend docs (not run here):

@sgl.function
def tips(s):
    s += "Here are two tips for staying healthy: 1. Balanced Diet. 2. Regular Exercise.\n\n"
    forks = s.fork(2)                       # two branches share everything above
    for i, f in enumerate(forks):
        f += f"Now, expand tip {i+1} into a paragraph:\n"
        f += sgl.gen("detail", max_tokens=256, stop="\n\n")
    s += "Tip 1:" + forks[0]["detail"] + "\nTip 2:" + forks[1]["detail"] + "\n"
    s += "Overall, " + sgl.select("verdict", choices=["diet", "exercise"]) + " matters more."

In the tree, the shared opening becomes one node with two children, one per branch, and the final call reuses everything before it: the program's structure is exactly the prefix sharing the runtime exploits. Most deployments today send plain requests to the OpenAI-compatible server instead, and the tree finds the same sharing without being told, so the rest of this page is about the runtime.

Read the early speedups with their baseline
The launch blog's "up to 5x faster" ({{LMSYS, 2024-01-17|https://lmsys.org/blog/2024-01-17-sglang/}}) compared against Guidance and vLLM v0.2.5, which kept no KV cache across requests at all. vLLM added automatic prefix caching in v0.4.0 on 2024-03-30, off by default at first ({{release notes|https://github.com/vllm-project/vllm/releases/tag/v0.4.0}}), and its V1 engine turns it on by default. So the 2024 gap was mostly "cache across requests or not", which no longer separates the two engines (section 3 measures what is left).

2. The radix tree, from zero

The problem. A prefix cache must answer one question fast, millions of times: of the tokens this new request starts with, how many have I already computed, and where is their KV? A dictionary from whole prompts finds only exact repeats. A trie (prefix tree) finds the longest shared beginning by walking one token per level, but a 2,000-token system prompt would be 2,000 nodes deep. A radix tree is a trie whose edges carry whole runs of tokens: the 2,000-token system prompt is one node and each conversation that continues it is one more.

What each node holds ({{TreeNode, radix_cache.py L249|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L249}}): its run of token ids (the key), the indices of the KV slots holding those tokens' keys and values in the GPU pool (the value), its children (indexed by first token), a lock reference count and a last-access time for eviction. The tree only maps token runs to slot numbers, which is why it can live on the CPU.

Eight requests through a radix tree, then through hash blocks: the tree shares partial blocks and evicts whole leaves

Eight requests from a toy bank assistant, one word per token, pool of 40 slots (10 blocks of 4; vLLM uses 16, 4 keeps the picture readable). Watch three differences: the tree shares the tail of a partially filled block and the hash table cannot; the tree evicts whole leaves while blocks go one at a time; the bookkeeping is a handful of nodes against a row per block. Both modes run the page's port of the two caches (src/iso/ref.py), which reproduces SGLang's and vLLM's own classes request by request (section 3).

The five operations, each with its line in v0.5.21's radix_cache.py; step through the animation above to see each one happen:

match

Walk from the root along the child whose first token matches, comparing token by token ({{L639|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L639}}). The hit is capped at the prompt length minus one, so at least one token is computed to produce the first output ({{schedule_batch.py L1702|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/schedule_batch.py#L1702}}).

split

If the walk stops inside a node's run, the node is cut in two so the shared part becomes its own node ({{L665|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L665}}); only the slot list is sliced, nothing moves on the GPU.

insert

A finished request's prompt and output (all but the last token, whose KV was never computed) go in; the part already present is reused and the duplicate slots freed ({{L698|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L698}}). The leaf is split at the prompt boundary so the output can be evicted before the prompt.

lock

A running request increments the lock count of every node on its path ({{L583|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L583}}); a prefix in use never disappears under it.

evict

When the pool is full, pop the least recently used unlocked leaf, free its slots, and push its parent if it has just become a childless unlocked leaf ({{L553|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L553}}). Branches are eaten from the tips inward, so the shared trunk survives longest.

Cost, when it matters, how to check
  • Cost: CPU work proportional to the matched length, one node per branch point, and no GPU memory beyond KV that would otherwise sit in free slots (eviction gives them back on demand).
  • When: any traffic with repeated beginnings (chat history, shared system prompts, few-shot examples, retrieval over the same documents, agents). On unrelated one-shot prompts it does nothing and costs little (no measurable overhead without hits, {{launch blog|https://lmsys.org/blog/2024-01-17-sglang/}}).
  • Check: meta_info.cached_tokens in every native response, #cached-token in the prefill log line, the hit counters with --enable-metrics; compare with --disable-radix-cache.
