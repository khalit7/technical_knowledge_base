1. What SGLang is, and where it came from

The problem it started from. In late 2023 most engines threw a request's KV cache away the moment the request finished. Yet real traffic repeats itself: every chat turn resends the whole conversation, every few-shot prompt resends the same examples, an agent resends its growing history on every step, and a self-consistency run asks the same question several times. The SGLang paper ({{Zheng et al., arXiv 2312.07104|https://arxiv.org/abs/2312.07104}}, December 2023, NeurIPS 2024, from the LMSYS group behind Vicuna and Chatbot Arena) proposed two things: a small Python language for programs that make many model calls (gen, select, fork), and a runtime that keeps every request's KV cache in a radix tree so those calls share whatever prefix they have in common (RadixAttention). The authors report up to 6.4 times the throughput of the systems they compared against authors' measurement.

Read the early speedups with their baseline
The launch blog's "up to 5x faster" ({{LMSYS, 2024-01-17|https://lmsys.org/blog/2024-01-17-sglang/}}) compared against Guidance and vLLM v0.2.5, which kept no KV cache across requests at all. vLLM added automatic prefix caching in v0.4.0 on 2024-03-30, off by default at first ({{release notes|https://github.com/vllm-project/vllm/releases/tag/v0.4.0}}), and its V1 engine turns it on by default. So the 2024 gap was mostly "cache across requests or not", which no longer separates the two engines (section 3 measures what is left).

What it is now. The frontend language still ships (python/sglang/lang), but most deployments use the OpenAI-compatible server, so this page is about the runtime. Releases came every few weeks: v0.4 (December 2024) added the overlap scheduler, the cache-aware router and XGrammar ({{LMSYS, 2024-12-04|https://lmsys.org/blog/2024-12-04-sglang-v0-4/}}); 2025 brought prefill/decode disaggregation and large-scale expert parallelism for DeepSeek (section 9); 2026 added TPUs through SGLang-Jax and Apple silicon through MLX. The release read here, v0.5.21, was published on 2026-10-02 with 779 pull requests from 227 contributors, and makes a Rust implementation of the prefix-cache tree the default ({{release notes|https://github.com/sgl-project/sglang/releases/tag/v0.5.21}}; tag commit e00930c5). The project is hosted by the non-profit LMSYS and its README lists xAI, NVIDIA, AMD, LinkedIn, Cursor and the large clouds among adopters, "on over 400,000 GPUs" ({{README|https://github.com/sgl-project/sglang/tree/v0.5.21#adoption-and-sponsorship}}) project's own claim.

How a request flows. Like vLLM, SGLang splits the work across processes that talk over ZeroMQ sockets, so that tokenizing, scheduling and detokenizing never block one another:

1. HTTP server + TokenizerManagerReceives the request (OpenAI-compatible or native /generate), applies the chat template, tokenizes, forwards the token ids.
2. Scheduler (one per GPU rank)Owns the waiting queue, the radix tree and the KV pool; matches prefixes, picks the next batch, runs the model worker, frees and caches KV when requests finish ({{scheduler.py|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/scheduler.py}}).
3. DetokenizerManagerTurns new token ids back into text incrementally and streams it out ({{detokenizer_manager.py|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/detokenizer_manager.py}}).

On the M1 run here these were three Python processes, the scheduler holding the model through the MLX backend. Everything this page says about caching and ordering happens inside process 2.

2. The radix tree, from zero

The problem. A prefix cache must answer one question fast, millions of times: of the tokens this new request starts with, how many have I already computed, and where is their KV? A plain dictionary from whole prompts to KV only finds exact repeats. A trie (prefix tree) finds the longest shared beginning by walking one token per level, but a 2,000-token system prompt would be 2,000 nodes deep. A radix tree is a trie whose edges carry whole runs of tokens: a node is created only where two cached sequences part ways, so the 2,000-token system prompt is one node and each conversation that continues it is one more.

What each node holds ({{TreeNode, radix_cache.py L249|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L249}}): its run of token ids (the key), the indices of the KV slots where those tokens' keys and values live in the GPU pool (the value), its children (indexed by their first token), a lock reference count (how many running requests are using this node right now) and a last-access time for eviction. The KV itself never moves; the tree only maps token runs to slot numbers, which is why the SGLang authors keep it on the CPU.

The five operations, each with the line in v0.5.21's radix_cache.py that does it:

match

Walk from the root, following the child whose first token matches, comparing the run token by token ({{L639|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L639}}). The hit is capped at the prompt length minus one, so at least one token is computed to produce the first output ({{schedule_batch.py L1702|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/schedule_batch.py#L1702}}).

split

If the walk stops in the middle of a node's run, that node is cut in two so the shared part becomes its own node ({{L665|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L665}}). Nothing is copied on the GPU; only the slot list is sliced.

insert

When a request finishes, its prompt and output (all but the last token, whose KV was never computed) are inserted; the part already in the tree is reused and the duplicate slots freed ({{L698|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L698}}). The leaf is then split at the prompt boundary so the output can be evicted before the prompt.

lock

A running request increments the lock count of every node on its path ({{L583|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L583}}); a locked node cannot be evicted, so a prefix in use never disappears under a request.

evict

When the pool is full, pop the least recently used unlocked leaf, free its slots, and if its parent has just become a childless unlocked leaf, push the parent too ({{L553|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L553}}). Eviction eats branches from the tips inward, so the shared trunk survives longest.

What it costs, when it matters, how to check
  • Cost: CPU work per request proportional to the matched length (a token-by-token comparison along the path), plus one node object per branch point. No GPU memory beyond the KV the cache keeps instead of freeing; that KV only uses slots that would otherwise sit empty, because eviction gives them back on demand.
  • When it matters: any traffic with repeated beginnings: chat history, shared system prompts, few-shot examples, retrieval over the same documents, agents. On one-shot unrelated prompts it does nothing and costs little (the authors report no measurable overhead without hits, {{launch blog|https://lmsys.org/blog/2024-01-17-sglang/}}).
  • How to check: every response from SGLang's native API carries meta_info.cached_tokens; the server log prints #cached-token per prefill batch; with --enable-metrics the Prometheus endpoint exposes the cache hit counters. Compare against a run with --disable-radix-cache.
