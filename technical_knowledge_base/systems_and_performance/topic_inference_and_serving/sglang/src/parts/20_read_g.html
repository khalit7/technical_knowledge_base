11. Running SGLang on a Mac, and what broke

Since 2026 SGLang runs natively on Apple silicon: with SGLANG_USE_MLX=1 the scheduler, radix cache and API are SGLang's own, and the forward pass runs in Apple's MLX ({{Apple Metal docs|https://docs.sglang.io/docs/hardware-platforms/apple_metal}}). That is what made the measurements on this page possible on a laptop. It is installed from source (no macOS wheel on PyPI: the v0.5.21 wheels are Linux only) with the srt_mps extra, which brings PyTorch 2.13.0, MLX and XGrammar 0.2.7. Several problems surfaced, and the way they were found is the useful part:

1. It did not start

v0.5.21 stopped at start-up with AttributeError: 'MlxModelRunnerStub' object has no attribute 'kv_cache_configurator'. A refactor of the token-capacity code had not been carried to the Apple path; the fix ({{PR #41314|https://github.com/sgl-project/sglang/pull/41314}}, merged 2026-09-30) landed one day after the release's tag commit. Applying its seven-line property let the server start.

2. It answered the wrong question

With the cache on, send A, then an unrelated B, then A again, all greedy: the second A came back as unrelated text ("a) the number of employees in the company...") with 25 of its 26 prompt tokens reported cached. Disabling the radix cache made it go away, which pointed at the cache. This is open issue {{#42415|https://github.com/sgl-project/sglang/issues/42415}} (reported on v0.5.20); the open pull request {{#42542|https://github.com/sgl-project/sglang/pull/42542}} traces it to chained decode steps writing a finished request's KV into slots the tree still points at. With that patch applied the repeat answered A again, every time.

3. Not a bug: cached and uncached answers differ

Even patched, the cached A diverged from the uncached A after eight tokens ("is used to store" against "represents the hierarchical"). MLX-LM alone, with no SGLang, does the same when the prompt is computed in two pieces instead of one: the top two candidates were within 0.125 of each other in logit at that step, and computing in a different order rounds differently. Prefix caching is exact in arithmetic, not in floating point.

4. Crashes

The server died with [METAL] Command buffer execution failed: Insufficient Memory, with gigabytes free, in several situations: every time the radix cache had to evict (a 3,000-token pool and 840-token prompts one at a time, with and without the patch of item 2); every time a prefill batch mixed a chunked prompt (512-token chunks) with other requests; on a burst of requests sent after /flush_cache (seen in two runs, not isolated further); and in every run of the overlap experiment (32 requests of 128 tokens in and out, one after another), with the overlap loop on or off. The dfs-weight queue runs crashed too. Open pull requests on the Apple backend touch neighbouring code (per-request buffers released late, {{#39251|https://github.com/sgl-project/sglang/pull/39251}}; retracted requests' state, {{#38179|https://github.com/sgl-project/sglang/pull/38179}}; no device-memory figure on Apple, {{#39675|https://github.com/sgl-project/sglang/issues/39675}}); none was confirmed as the cause here. The runs on this page avoid all three: a pool large enough never to evict, chunks of 4,096 and no flushes. The backend also gives each running request its own 4,096-token KV buffer per layer (448 MiB for this model), so at most 8 ran at once.

The habit this teaches
Before trusting a cache, run the same greedy request with it on and off, and an unrelated request in between. Identical text is not guaranteed (item 3), but a different topic is a bug (item 2). All measurements on this page were taken with both fixes applied and the crashes avoided; the commands, patches and raw results are on the {{SGLang on the M1|#t-sgm1}} tab.

Common mistakes

"SGLang schedules by longest prefix by default."
Not since v0.4.4 (March 2025): the default is fcfs. Cache-aware ordering is opt-in, and lpm turns itself off whenever more than 128 requests wait.
"The radix tree gets more cache hits than vLLM's blocks."
On the same requests and pool they reused the same share of tokens within a point; with a tight pool the blocks can win because they evict one block at a time (section 3). The engines differ in ordering, routing and recipes, not in what the cache structure can find.
"SGLang decodes forced JSON strings in one jump."
Jump-forward decoding was removed in v0.4.4 (PR #4032). Constrained decoding today is per-token masking by XGrammar.
Quoting launch-blog speedups as today's gap.
The 5 times of January 2024 was against a vLLM without any cross-request cache. Compare current builds, on your model, on your hardware, at your latency target.
Measuring prefix caching with identical repeated prompts.
That measures the best case. Real hit rates depend on whether the working set of live prefixes fits the pool: the agent trace went from about 70% to 97% between 24,000 and 48,000 slots. Size the pool from the number of live conversations times their history.
Expecting bit-identical output with and without the cache.
Different computation order rounds differently; at a near-tie greedy decoding flips. Test for the right topic, not for identical bytes.
Reading a vendor "25x" as a hardware ratio.
It was measured at one per-user speed (50 tokens/s) where the older GPU is weakest; the same post says the unconstrained gap is much smaller.

Interview questions

Why a radix tree rather than a trie or a hash map for prefix caching?
A hash map of whole prompts finds only exact repeats; a trie finds longest prefixes but has one node per token; a radix tree compresses runs into single edges, so nodes exist only where cached sequences diverge, and a lookup walks one path comparing tokens.
How does SGLang avoid evicting KV that a running request needs?
Lock references: a request increments a counter on every node of its matched path; eviction only takes unlocked leaves, and a parent becomes a candidate only once all its children are gone.
Why is a prefix match capped at the prompt length minus one?
The last prompt token's forward pass produces the logits for the first output token, so it must be computed even when its KV is cached. Both SGLang and vLLM cap the hit there.
When does cache-aware scheduling help, and what does it cost?
When the queue is deep and the cache cannot hold all hot prefixes: ordering by longest match (or depth-first through the tree) uses a prefix before it is evicted. It costs a match per waiting request per pass and can starve requests with unshared prompts; SGLang disables lpm above 128 waiting requests.
What does the overlap scheduler overlap, and what is its catch?
The CPU's scheduling and result processing for neighbouring steps with the GPU's forward pass, using placeholders for tokens not yet produced. Catch: anything that needs the previous token on the CPU (some grammar paths, custom logit processors) forces a sync.
Design a router for 8 replicas of a chat model with long system prompts.
Route by prefix affinity (approximate per-replica trees or consistent hashing of the prefix) but fall back to least-loaded when the load is imbalanced beyond a threshold; measure hit rate, TTFT percentiles and per-replica load. SGLang's gateway does exactly this with a 0.3 match threshold and 64/1.5 imbalance thresholds by default.
Why does DeepSeek serving use data-parallel attention with expert parallelism?
MLA has one compressed KV per token, so tensor-parallel attention would replicate the cache on every GPU; data-parallel attention keeps each request's cache on one GPU, and expert parallelism spreads the experts, with all-to-all exchanges around each MoE layer.
How would you check that prefix caching is working on a production server?
Per-request cached-token counts or the hit-rate metric, TTFT split by hit and miss, and a greedy A/B/A correctness test with the cache on and off.
