3. Radix tree or hash blocks: does the data structure matter?

The old claim, still repeated in comparisons, is that SGLang's tree "wins on shared-prefix traffic" against vLLM's block cache. Both structures answer the same question, so the claim can be tested directly: replay the same requests through both caches with the same pool size and count the reused tokens. That is what was done here, with the engines' own code rather than a re-implementation:

  • SGLang: its default UnifiedRadixCache (Python tree core, a real token allocator and a tiny KV pool on the CPU, set up as in SGLang's own unit tests) and its older RadixCache, both from v0.5.21.
  • vLLM: its own v1 Scheduler and KVCacheManager from v0.31.0, with a fake model runner, exactly as the root's {{Serving simulator|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} tab checked its own engine.
  • Traces: three from the root simulator's generator (a chat assistant with three 600-token system prompts and four turns per conversation; a coding agent with one 2,000-token system prompt and ten growing turns; unrelated one-shot prompts) and one of 160 short questions about eight 800-token documents. Requests run one at a time, so only the cache differs.

Across 4 traces and 6 pool sizes, the three real classes and the page's small port (src/iso/ref.py) agreed on every one of the ... requests replayed, so the {{Radix lab|#t-sgtree}} can run the comparison live at any pool size. The result:

Within one percent when the pool is roomy. With room for everything, the tree reuses ... of the chat trace's prompt tokens and the blocks ...; on the agent trace ... against ...; on unrelated prompts both reuse nothing. The tree's small lead is the tail of the last, partially filled block of each shared prefix, which a hash of full blocks cannot match (up to 15 tokens a request with 16-token blocks).

When the pool is tight, the blocks can win. With 6,000 slots on the document trace the blocks reuse ... and the tree .... The reason is eviction granularity: vLLM frees a request's blocks tail first and evicts them one block at a time, so a document can lose its last blocks and keep its first ones, and the next question about it still reuses a prefix. The tree evicts whole leaf nodes: once a document's questions are gone, the 800-token document node is itself a leaf, and it goes all at once.

Bookkeeping differs a lot more than hits. At the end of the unbounded chat replay the tree holds ... nodes where vLLM holds ... cached blocks, each with its hash. A tree lookup compares tokens along one path; a block lookup hashes every full block of the prompt (vLLM uses SHA-256 by default, {{cache.py L144|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/cache.py#L144}}). Both are cheap next to a forward pass, and SGLang moved its tree to Rust in v0.5.21 precisely to keep that CPU work small.

Predict: in the agent trace each turn resends the whole conversation (2,000-token system prompt plus every earlier turn). The pool grows from 24,000 to 48,000 token slots. What happens to the share of prompt tokens reused?
It jumps from about 70% to 97%. The agent's conversations interleave in time, and each one's history (thousands of tokens) has to survive until its next turn arrives 15 seconds later. At 24,000 slots the least recently used histories are evicted before they come back; at 48,000 they all fit. Hit rate is a cliff, not a slope, in the working-set size: the capacity planning question is whether the live histories fit, which the {{Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} tab can size in GB.

So what does differ between the engines?
Not how many tokens the cache can reuse, but what the engine does with it: whether the scheduler orders the queue to reuse it before it is evicted (section 4), whether the router keeps a conversation on the replica that holds it (section 8), how big the pages are (SGLang's page size 1 matches to the token; most fast attention kernels want 16 or more, and SGLang uses 64 or 128 with some of them, {{overrides.py L1068|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/arg_groups/overrides.py#L1068}}), and how the cache spills to host memory and disk (HiCache, section 7; vLLM's offload connectors, {{Batching, KV cache and scheduling in depth|n:3c65c17b0d0d819db53bd2c48909e5b2}}).
