3. Radix tree or hash blocks: does the data structure matter?

A claim still repeated in comparisons is that SGLang's tree "wins on shared-prefix traffic" against vLLM's block cache. Both structures answer the same question, so it can be tested directly: replay the same requests through both caches with the same pool and count the reused prompt tokens. That was done here with the engines' own classes, SGLang v0.5.21's UnifiedRadixCache and RadixCache and vLLM v0.31.0's Scheduler and KVCacheManager, on four traces at six pool sizes: 4,800 requests through each class, 72 replays, every one identical request by request to the page's small port (src/iso/ref.py), which is what runs below.

With room for everything they are within one point: the tree reuses 87.6% of the chat trace's prompt tokens and the blocks 86.8%; on the coding-agent trace 97.2% against 97.0%; on unrelated prompts both reuse nothing. The tree's small lead is the tail of the last, partially filled block of each shared prefix, which a hash of full blocks cannot match (up to 15 tokens a request with 16-token blocks). When the pool is tight the blocks can win: with 6,000 slots on the document trace the blocks reuse 69.7% and the tree 65.4%, because vLLM evicts one block at a time, tail first, so a document can lose its last blocks and keep its first; the tree evicts whole leaves, and once a document's questions are gone the 800-token document node is itself a leaf and goes all at once.

Predict, then drag: in the coding-agent trace each turn resends the whole conversation (2,000-token system prompt plus every earlier turn). The pool grows from 24,000 to 48,000 token slots. What happens to the share of prompt tokens reused?
It jumps from about 70% to 97%. The agent's conversations interleave in time, and each one's history (thousands of tokens) has to survive until its next turn arrives 15 seconds later. At 24,000 slots the least recently used histories are evicted before they come back; at 48,000 they all fit. Hit rate is a cliff, not a slope, in the working-set size: the capacity question is whether the live histories fit, which the root's {{Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} tab sizes in GB.

Bookkeeping differs far more than hits. At the end of the unbounded chat replay the tree holds 483 nodes where vLLM holds 3,641 cached blocks, each with its hash. A tree lookup compares tokens along one path; a block lookup hashes every full block of the prompt (SHA-256 by default, {{cache.py L144|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/cache.py#L144}}). Both are cheap next to a forward pass, and SGLang moved its tree to Rust in v0.5.21 to keep that CPU work small.

So what does differ between the engines?
Not how many tokens the cache can reuse, but what the engine does with it: whether the scheduler orders the queue to reuse it before it is evicted (section 4), whether the router keeps a conversation on the replica that holds it (section 8), how big the pages are (SGLang's page size 1 matches to the token; most fast attention kernels want 16 or more, and SGLang uses 64 or 128 with some of them, {{overrides.py L1068|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/arg_groups/overrides.py#L1068}}), and how the cache spills to host memory and disk (HiCache, section 7; vLLM's offload connectors, {{Batching, KV cache and scheduling in depth|n:3c65c17b0d0d819db53bd2c48909e5b2}}).

How the replays were run, and what the port leaves out (method)
  • SGLang: its default UnifiedRadixCache (Python tree core, a real token allocator and a tiny KV pool on the CPU, set up as in SGLang's own unit tests) and its older RadixCache, both from v0.5.21. v0.5.21 makes a Rust tree core the default; the Python core was run here (the Rust extension was not built), and SGLang runs the same unit suite against both (test/registered/unit/mem_cache/test_rust_unified_radix_cache_unittest.py).
  • vLLM: its own v1 Scheduler and KVCacheManager from v0.31.0, with a fake model runner, exactly as the root's {{Serving simulator|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} tab checked its own engine.
  • Traces: chat (seed 7; 90% of conversations under one of 3 system prompts of 600 tokens), agent (seed 11; turns 15 s apart, up to about 4,800 tokens of history per request), documents (seed 5; questions and answers of 20 to 80 tokens), unrelated (seed 3; 100 to 800 tokens).
  • The port: match the prompt (capped at its length minus one), lock the matched path, evict least recently used leaves or blocks until the request's new KV fits, insert prompt and output (minus the last token), unlock. Not modelled: concurrency (several running requests locking more of the tree), HiCache or vLLM's offload tiers, page sizes other than 1 and 16, sliding-window or hybrid models.
On the real engine: a four-turn chat with the radix cache on and off (measured on the M1)

Eight four-turn conversations at once under one 600-token system prompt, on SGLang v0.5.21 on the M1 (section 11); each turn adds 60 to 120 tokens of user text and 64 tokens of answer and resends the whole history; KV pool 24,000 tokens. By the fourth turn (about 1,166 prompt tokens, 1,002 of them cached) the mean time to first token was 2.32 s with the radix cache and 4.81 s with --disable-radix-cache, 2.1 times faster; on the first turn, where only the system prompt can be shared, 2.32 s against 2.73 s. But decoding was slower with the cache on (208 against 86 ms per output token), so the whole job took longer (59.9 s against 38.8 s): the Apple backend copies KV between its pool and per-request buffers when the cache is on, a cost a GPU engine with paged attention does not pay (cause not isolated). measured on Apple M1 Pro
