5. The overlap scheduler: hiding the CPU behind the GPU

The problem. Every decode step has CPU work around the GPU work: pick the batch, allocate KV slots, match prefixes, build the input tensors, then, after the forward pass, read the sampled tokens back, check stop conditions, free finished requests and insert them into the tree. In a plain loop the GPU waits while the CPU does all of this. On a large model the forward pass is long and the CPU share small; on a small model, or with many GPUs splitting each step so each one's share of the forward is short, the CPU share can be large. The SGLang v0.4 post says an unoptimized engine "can spend as much as half of its time on CPU overhead" ({{LMSYS, 2024-12-04|https://lmsys.org/blog/2024-12-04-sglang-v0-4/}}) project's claim.

How it works. The overlap loop ({{event_loop_overlap, scheduler.py L1941|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/scheduler.py#L1941}}) launches batch k on the GPU without waiting for it, then processes the results of batch k minus 1 and schedules batch k plus 1 while the GPU is busy. The catch is that batch k plus 1 needs the tokens batch k has not produced yet; SGLang passes them as placeholders that the GPU fills in when it gets there (the FutureMap, {{overlap_utils.py L248|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/overlap_utils.py#L248}}). The plain loop is still there ({{event_loop_normal, L1906|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/scheduler.py#L1906}}) behind --disable-overlap-schedule. The idea is NanoFlow's, as the v0.4 post credits; vLLM's asynchronous scheduling does the same job.

What it costs, when it matters, how to check
  • Cost: complexity, one extra step of latency in noticing that a request finished (its slot frees one step late), and a sync point wherever the CPU must see a token before building the next step: on the Apple backend a batch with a grammar or a custom logit processor cannot be chained ({{scheduler_mixin.py|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/hardware_backend/mlx/scheduler_mixin.py}}); on GPUs SGLang syncs for grammars only with some speculative-decoding algorithms ({{L2015|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/scheduler.py#L2015}}).
  • When it matters: small models, low batch sizes, many GPUs per model, fast GPUs: whenever a forward pass is a few milliseconds. The v0.4 post measured 1.1 times its previous version and says the gain is largest "on small models and large tensor parallelism sizes" vendor.
  • How to check: a profiler timeline (Nsight Systems on NVIDIA) shows gaps between kernels in the plain loop and none with overlap; without one, compare decode throughput at concurrency 1 with and without --disable-overlap-schedule, as done here.

6. Structured output: grammars, masks and the jump-forward that was removed

The problem. A tool call or an API response must be valid JSON matching a schema. Asking nicely fails some of the time; constrained decoding makes failure impossible by setting the probability of every token that would break the grammar to zero before sampling. The grammar (a JSON schema, a regular expression or an EBNF grammar) is compiled into an automaton; at every step the engine computes a token mask over the whole vocabulary (151,936 tokens for Qwen3) and applies it to the logits.

How SGLang does it now. The default backend is XGrammar ({{serving_hook.py L219|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/arg_groups/serving_hook.py#L219}}), with llguidance and outlines selectable by --grammar-backend. XGrammar splits the vocabulary into tokens whose validity is known from the grammar position alone (checked ahead of time) and the few that need the parser's stack at run time, and overlaps the mask computation with the GPU's forward pass; its paper reports up to 100 times faster than earlier engines ({{Dong et al., arXiv 2411.15100|https://arxiv.org/abs/2411.15100}}) authors' measurement. A request asks for it with json_schema, regex or ebnf in its sampling parameters, or the OpenAI response_format.

The compressed FSM, and what became of it. In February 2024 SGLang introduced jump-forward decoding: where the grammar allows only one continuation (the key {"name": " in a schema, say), append that whole string in one prefill step instead of decoding it token by token, with the radix tree keeping the KV; the post reported up to 2 times lower latency and 2.5 times higher throughput than Outlines with vLLM ({{LMSYS, 2024-02-05|https://lmsys.org/blog/2024-02-05-compressed-fsm/}}) vendor. It was removed in v0.4.4 "to simplify the code maintenance" ({{PR #4032, merged 2025-03-03|https://github.com/sgl-project/sglang/pull/4032}}). In v0.5.21 the backends still define try_jump_forward ({{xgrammar_backend.py L167|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/constrained/xgrammar_backend.py#L167}}) but nothing in the scheduler calls it, so no current SGLang release jump-forwards.

What it costs, when it matters, how to check
  • Cost: compiling the grammar (cached per schema, so the first request with a new schema pays it), a vocabulary-sized mask per step, and on some paths the loss of CPU/GPU overlap. A constrained answer is also not the answer the model wanted: masking forces a different token where the model's choice was invalid, which can lower quality; reasoning models are usually left unconstrained while they think ({{structured outputs for reasoning models|https://docs.sglang.io/docs/advanced_features/structured_outputs_for_reasoning_models}}).
  • When it matters: tool calling and any machine-read output. The serving-time trade-offs (overhead under load, measured with llama.cpp grammars) are on {{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}.
  • How to check: parse every response (here every constrained one parsed, see the M1 tab), and compare time per output token with and without the schema at the same output length.
