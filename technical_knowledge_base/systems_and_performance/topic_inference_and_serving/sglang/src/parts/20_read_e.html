5. The overlap scheduler: hiding the CPU behind the GPU

The problem. Every decode step has CPU work around the GPU work: pick the batch, allocate KV slots, match prefixes, build the input tensors, then read the sampled tokens back, check stop conditions, free finished requests and insert them into the tree. In a plain loop the GPU waits through all of it. With a small model, or many GPUs splitting each step so each one's forward is short, the CPU share can be large: the SGLang v0.4 post says an unoptimized engine "can spend as much as half of its time on CPU overhead" ({{LMSYS, 2024-12-04|https://lmsys.org/blog/2024-12-04-sglang-v0-4/}}) project's claim.

How it works. The overlap loop ({{event_loop_overlap, scheduler.py L1941|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/scheduler.py#L1941}}) launches batch k on the GPU without waiting, then processes the results of batch k minus 1 and schedules batch k plus 1 while the GPU is busy. Batch k plus 1 needs tokens batch k has not produced yet, so they are passed as placeholders the GPU fills in when it gets there (the FutureMap, {{overlap_utils.py L248|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/overlap_utils.py#L248}}). The plain loop remains ({{event_loop_normal, L1906|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/scheduler.py#L1906}}) behind --disable-overlap-schedule. The idea is NanoFlow's, as the v0.4 post credits; vLLM's asynchronous scheduling does the same job.

Five decode steps: the plain loop leaves the GPU idle during CPU work; the overlap loop fills those gaps

Illustrative durations: 5 ms of GPU work and 1.5 ms of CPU work per step. Steady state: GPU plus CPU per step in the plain loop, the larger of the two with overlap.

Cost, when it matters, how to check
  • Cost: complexity, a finished request noticed one step late (its slot frees one step later), and a sync wherever the CPU must see a token before building the next step: on the Apple backend a batch with a grammar or a custom logit processor cannot be chained ({{scheduler_mixin.py|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/hardware_backend/mlx/scheduler_mixin.py}}); on GPUs SGLang syncs for grammars only with some speculative-decoding algorithms ({{L2015|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/scheduler.py#L2015}}).
  • When: small models, low batch sizes, many GPUs per model, fast GPUs: whenever a forward pass takes a few milliseconds. The v0.4 post measured 1.1 times its previous version and says the gain is largest "on small models and large tensor parallelism sizes" vendor.
  • Check: a profiler timeline (Nsight Systems on NVIDIA) shows gaps between kernels in the plain loop and none with overlap; or compare decode throughput at concurrency 1 with and without --disable-overlap-schedule.
Why there is no measurement from the M1 here (a failed experiment)

Not measured: with the overlap loop on and off, a sequence of 32 requests of 128 tokens in and out at concurrency 1, 4 and 8 crashed the server every time (6 configurations, each retried once on a fresh server). With the overlap on, the Metal out-of-memory error inside the chained-decode path; with it off, an error in the overlap bookkeeping (overlap_utils.py, stash). A short decode (32 tokens) had worked in the first smoke tests; 128-token outputs in sequence did not. The 1.1 times above is the project's own figure.

6. Structured output: where the grammar sits, and the jump-forward that was removed

Constrained decoding sets the probability of every token that would break a grammar (a JSON schema, a regular expression, an EBNF grammar) to zero before sampling, using a token mask over the whole vocabulary (151,936 tokens for Qwen3). How the masks are built, and how XGrammar's context-independent tokens make them cheap, is taught on {{Sampling and decoding|n:3c65c17b0d0d8115bafcda29a2c7086e}}; this section is how SGLang wires it in.

A constrained request in SGLang: the grammar is compiled once per schema, then masks every step

Measured on the M1 with Qwen3-0.6B: first request with a new schema 957 ms to first token (compilation included); 13.4 ms against 4.9 ms per output token with and without the schema measured on Apple M1 Pro, where the grammar also stops decode steps being chained (section 5), which is much of that per-token cost here.

The default backend is XGrammar ({{serving_hook.py L219|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/arg_groups/serving_hook.py#L219}}), with llguidance and outlines selectable by --grammar-backend; its mask is computed on the CPU, overlapped with the GPU's forward pass, and its paper reports up to 100 times faster than earlier engines ({{Dong et al., arXiv 2411.15100|https://arxiv.org/abs/2411.15100}}) authors' measurement. A request asks for it with json_schema, regex or ebnf in its sampling parameters, or the OpenAI response_format. On the M1, 24 of 24 answers with a JSON schema parsed as JSON against 0 of 24 without it (unconstrained, the model wraps its JSON in a Markdown code fence).

The compressed FSM, and what became of it. In February 2024 SGLang introduced jump-forward decoding: where the grammar allows only one continuation (the key {"name": " in a schema, say), append that whole string in one prefill step instead of decoding it token by token, with the radix tree keeping the KV; the post reported up to 2 times lower latency and 2.5 times higher throughput than Outlines with vLLM ({{LMSYS, 2024-02-05|https://lmsys.org/blog/2024-02-05-compressed-fsm/}}) vendor. It was removed in v0.4.4 "to simplify the code maintenance" ({{PR #4032, merged 2025-03-03|https://github.com/sgl-project/sglang/pull/4032}}). In v0.5.21 the backends still define try_jump_forward ({{xgrammar_backend.py L167|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/constrained/xgrammar_backend.py#L167}}) but nothing in the scheduler calls it, so no current SGLang release jump-forwards: forced strings are decoded one masked token at a time.

Cost, when it matters, how to check
  • Cost: compiling the grammar (cached per schema), a vocabulary-sized mask per step, and on some paths the loss of CPU/GPU overlap. A constrained answer is also not the answer the model wanted: masking forces a different token where the model's choice was invalid, which can lower quality; reasoning models are usually left unconstrained while they think ({{structured outputs for reasoning models|https://docs.sglang.io/docs/advanced_features/structured_outputs_for_reasoning_models}}).
  • When: tool calling and any machine-read output. The serving-time trade-offs (overhead under load, measured with llama.cpp grammars) are on {{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}.
  • Check: parse every response, and compare time per output token with and without the schema at the same output length.
The JSON-schema run on the M1, with one answer each way (measured on the M1)

Twelve chat requests asking for an invented person, with and without a JSON schema (name, city, age, up to four skills) through the default XGrammar backend; two passes each. Grammars apply on the Apple backend only with --mlx-enable-sampling: without the flag the same requests were decoded greedily without a mask, the grammar rejected the first token (a code fence) and every request ended after 2 tokens with invalid output (0 valid of 24). One server run with another job on the machine (load average 13.7), so read the ratio, not the absolute times.
