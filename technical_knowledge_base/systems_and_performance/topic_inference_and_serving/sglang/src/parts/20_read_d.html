4. Cache-aware scheduling: the order of the queue

The problem. When many requests wait at once and the KV pool cannot hold every shared prefix, the order in which the scheduler admits them decides whether a prefix is reused or evicted before its siblings arrive. Picture 160 questions about eight long documents, sent at once in a shuffled order, with a pool that holds about three documents. First come, first served visits the documents at random: a document is computed, evicted to make room for the next one, and computed again a few requests later.

How SGLang orders the queue. Before every prefill batch the scheduler matches each waiting request against the tree and sorts the queue by a schedule policy ({{calc_priority, schedule_policy.py L260|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/schedule_policy.py#L260}}):

fcfs (the default)

Arrival order. The default since v0.4.4 (2025-03-13); v0.3 to v0.4.3 defaulted to lpm ({{server_args.py at v0.4.3|https://github.com/sgl-project/sglang/blob/v0.4.3/python/sglang/srt/server_args.py}} and {{at v0.4.4|https://github.com/sgl-project/sglang/blob/v0.4.4/python/sglang/srt/server_args.py}}). The release notes we read do not give the reason unconfirmed.

lpm: longest prefix match

Requests with the longest cached prefix go first, so what is cached is used before it can be evicted ({{L477|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/schedule_policy.py#L477}}). The docs suggest it "if the workload has many shared prefixes" and warn of more scheduling overhead ({{hyperparameter tuning|https://docs.sglang.io/docs/advanced_features/hyperparameter_tuning}}).

in-batch prefix caching (inside lpm)

If several waiting requests share 32 or more tokens that are not yet cached, only the first is admitted now; the rest move to the back and hit the cache once it is computed ({{L373|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/schedule_policy.py#L373}}, thresholds 32 and 32 at {{L100|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/schedule_policy.py#L100}}). Without it, ten questions about an uncached document in one batch would each compute the document.

dfs-weight

Walk the tree depth first, heaviest subtree (most waiting requests) first, and admit in that order ({{base_prefix_cache.py L325|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/base_prefix_cache.py#L325}}). The SGLang paper proves that for a fixed batch, visiting the tree depth first gives the optimal hit rate when the cache holds at least the longest request, and that longest-prefix-first is equivalent (Theorem 3.1, {{arXiv 2312.07104|https://arxiv.org/abs/2312.07104}}).

the 128 cliff

With more than 128 requests waiting, lpm (and hrrn) silently fall back to arrival order to save the sorting cost ({{_determine_active_policy, L331|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/schedule_policy.py#L331}}). dfs-weight has no such cut-off.

Predict: you enable --schedule-policy lpm on a busy server where 300 requests are usually waiting. How much does the queue order change?
Not at all. With more than 128 requests waiting, _determine_active_policy returns FCFS for lpm, so the sort is skipped entirely, and it comes back only when the queue drains. On a server that is always deep in backlog, lpm does nothing; dfs-weight has no cut-off but costs a tree walk per scheduling pass. The real fix for a permanent backlog is more capacity or a router that keeps related requests together (section 8).
What it costs, when it matters, how to check
  • Cost: one prefix match per waiting request per scheduling pass, plus the sort; and fairness: a request whose prefix nobody shares can wait behind a stream of cache hits. The paper names this starvation risk and leaves fairness to future work; SGLang now offers hrrn (highest response ratio next, aging by processed tokens, {{L496|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/managers/schedule_policy.py#L496}}) and priority scheduling.
  • When it matters: offline batch jobs and bursts (evaluations, synthetic data, RL rollouts with many samples per prompt, retrieval over a shared corpus) where the queue is deep and the cache smaller than the set of hot prefixes. At steady low load the queue is nearly empty and every policy is FCFS.
  • How to check: the prefill log line's #cached-token against #new-token, the per-request cached_tokens, and the total time of a fixed batch, with each policy in turn.
