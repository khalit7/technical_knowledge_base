SGLang is an open-source serving engine for language models: software that takes requests over HTTP, batches them onto GPUs and streams tokens back, like vLLM. Its organising idea is to keep the KV cache of every finished request in a radix tree, so that any later request starting with the same tokens (a system prompt, a document, the earlier turns of a chat, an agent's growing history) skips recomputing them. Around that tree it builds a scheduler that can order requests to hit the cache, a scheduler loop that hides its own CPU work behind the GPU, constrained decoding for JSON and grammars, a router that sends each request to the replica most likely to hold its prefix, and recipes for serving DeepSeek-sized mixture-of-experts models on hundreds of GPUs.

This page assumes the parent Topic: inference-and-serving: what prefill and decode are, what the KV cache is (the keys and values every layer computed for every earlier token, kept so that each new token attends to them without recomputing them), and what prefix caching is (keeping that cache after a request ends so the next request with the same beginning reuses it). The running example is the root's chat assistant, and the small open model measured here is Qwen3-0.6B (28 layers, 8 KV heads of 128 dimensions, so 114,688 bytes of KV per token at 16-bit precision, as the Engine bench tab measured).

The short answer
On the same requests the radix tree and vLLM's hash blocks reuse almost exactly the same tokens (section 3). SGLang's edge, where it has one, comes from what sits around the cache: queue ordering when the cache is scarce, the router, structured-output plumbing and the large-scale MoE recipes; and both engines move fast enough that any benchmark older than a few months says little about today.

1. What SGLang is, and where it came from

The problem it started from. In late 2023 most engines threw a request's KV cache away the moment the request finished. Yet real traffic repeats itself: every chat turn resends the whole conversation, every few-shot prompt resends the same examples, an agent resends its growing history on every step, and a self-consistency run asks the same question several times. The SGLang paper (Zheng et al., arXiv 2312.07104, December 2023, NeurIPS 2024, from the LMSYS group behind Vicuna and Chatbot Arena) proposed two things: a small Python language for programs that make many model calls (gen, select, fork), and a runtime that keeps every request's KV cache in a radix tree so those calls share whatever prefix they have in common (RadixAttention). The authors report up to 6.4 times the throughput of the systems they compared against authors' measurement.

Read the early speedups with their baseline
The launch blog's "up to 5x faster" (LMSYS, 2024-01-17) compared against Guidance and vLLM v0.2.5, which kept no KV cache across requests at all. vLLM added automatic prefix caching in v0.4.0 on 2024-03-30, off by default at first (release notes), and its V1 engine turns it on by default. So the 2024 gap was mostly "cache across requests or not", which no longer separates the two engines (section 3 measures what is left).

What it is now. The frontend language still ships (python/sglang/lang), but most deployments use the OpenAI-compatible server, so this page is about the runtime. Releases came every few weeks: v0.4 (December 2024) added the overlap scheduler, the cache-aware router and XGrammar (LMSYS, 2024-12-04); 2025 brought prefill/decode disaggregation and large-scale expert parallelism for DeepSeek (section 9); 2026 added TPUs through SGLang-Jax and Apple silicon through MLX. The release read here, v0.5.21, was published on 2026-10-02 with 779 pull requests from 227 contributors, and makes a Rust implementation of the prefix-cache tree the default (release notes; tag commit e00930c5). The project is hosted by the non-profit LMSYS and its README lists xAI, NVIDIA, AMD, LinkedIn, Cursor and the large clouds among adopters, "on over 400,000 GPUs" (README) project's own claim.

How a request flows. Like vLLM, SGLang splits the work across processes that talk over ZeroMQ sockets, so that tokenizing, scheduling and detokenizing never block one another:

1. HTTP server + TokenizerManagerReceives the request (OpenAI-compatible or native /generate), applies the chat template, tokenizes, forwards the token ids.
2. Scheduler (one per GPU rank)Owns the waiting queue, the radix tree and the KV pool; matches prefixes, picks the next batch, runs the model worker, frees and caches KV when requests finish (scheduler.py).
3. DetokenizerManagerTurns new token ids back into text incrementally and streams it out (detokenizer_manager.py).

On the M1 run here these were three Python processes, the scheduler holding the model through the MLX backend. Everything this page says about caching and ordering happens inside process 2.

2. The radix tree, from zero

The problem. A prefix cache must answer one question fast, millions of times: of the tokens this new request starts with, how many have I already computed, and where is their KV? A plain dictionary from whole prompts to KV only finds exact repeats. A trie (prefix tree) finds the longest shared beginning by walking one token per level, but a 2,000-token system prompt would be 2,000 nodes deep. A radix tree is a trie whose edges carry whole runs of tokens: a node is created only where two cached sequences part ways, so the 2,000-token system prompt is one node and each conversation that continues it is one more.

What each node holds (TreeNode, radix_cache.py L249): its run of token ids (the key), the indices of the KV slots where those tokens' keys and values live in the GPU pool (the value), its children (indexed by their first token), a lock reference count (how many running requests are using this node right now) and a last-access time for eviction. The KV itself never moves; the tree only maps token runs to slot numbers, which is why the SGLang authors keep it on the CPU.

The five operations, each with the line in v0.5.21's radix_cache.py that does it:

match

Walk from the root, following the child whose first token matches, comparing the run token by token (L639). The hit is capped at the prompt length minus one, so at least one token is computed to produce the first output (schedule_batch.py L1702).

split

If the walk stops in the middle of a node's run, that node is cut in two so the shared part becomes its own node (L665). Nothing is copied on the GPU; only the slot list is sliced.

insert

When a request finishes, its prompt and output (all but the last token, whose KV was never computed) are inserted; the part already in the tree is reused and the duplicate slots freed (L698). The leaf is then split at the prompt boundary so the output can be evicted before the prompt.

lock

A running request increments the lock count of every node on its path (L583); a locked node cannot be evicted, so a prefix in use never disappears under a request.

evict

When the pool is full, pop the least recently used unlocked leaf, free its slots, and if its parent has just become a childless unlocked leaf, push the parent too (L553). Eviction eats branches from the tips inward, so the shared trunk survives longest.

The same requests then go through vLLM's way of doing it: hash every full block of 4 tokens (vLLM uses 16; 4 keeps the picture readable) and look the hashes up. Watch three differences: the tree shares the tail of a partially filled block and the hash table cannot; the tree evicts whole leaves while the blocks are evicted one at a time; and the bookkeeping is a handful of nodes against a row per block.

What it costs, when it matters, how to check
  • Cost: CPU work per request proportional to the matched length (a token-by-token comparison along the path), plus one node object per branch point. No GPU memory beyond the KV the cache keeps instead of freeing; that KV only uses slots that would otherwise sit empty, because eviction gives them back on demand.
  • When it matters: any traffic with repeated beginnings: chat history, shared system prompts, few-shot examples, retrieval over the same documents, agents. On one-shot unrelated prompts it does nothing and costs little (the authors report no measurable overhead without hits, launch blog).
  • How to check: every response from SGLang's native API carries meta_info.cached_tokens; the server log prints #cached-token per prefill batch; with --enable-metrics the Prometheus endpoint exposes the cache hit counters. Compare against a run with --disable-radix-cache.

3. Radix tree or hash blocks: does the data structure matter?

The old claim, still repeated in comparisons, is that SGLang's tree "wins on shared-prefix traffic" against vLLM's block cache. Both structures answer the same question, so the claim can be tested directly: replay the same requests through both caches with the same pool size and count the reused tokens. That is what was done here, with the engines' own code rather than a re-implementation:

  • SGLang: its default UnifiedRadixCache (Python tree core, a real token allocator and a tiny KV pool on the CPU, set up as in SGLang's own unit tests) and its older RadixCache, both from v0.5.21.
  • vLLM: its own v1 Scheduler and KVCacheManager from v0.31.0, with a fake model runner, exactly as the root's Serving simulator tab checked its own engine.
  • Traces: three from the root simulator's generator (a chat assistant with three 600-token system prompts and four turns per conversation; a coding agent with one 2,000-token system prompt and ten growing turns; unrelated one-shot prompts) and one of 160 short questions about eight 800-token documents. Requests run one at a time, so only the cache differs.

When the pool is tight, the blocks can win. With 6,000 slots on the document trace the blocks reuse ... and the tree .... The reason is eviction granularity: vLLM frees a request's blocks tail first and evicts them one block at a time, so a document can lose its last blocks and keep its first ones, and the next question about it still reuses a prefix. The tree evicts whole leaf nodes: once a document's questions are gone, the 800-token document node is itself a leaf, and it goes all at once.

Bookkeeping differs a lot more than hits. At the end of the unbounded chat replay the tree holds ... nodes where vLLM holds ... cached blocks, each with its hash. A tree lookup compares tokens along one path; a block lookup hashes every full block of the prompt (vLLM uses SHA-256 by default, cache.py L144). Both are cheap next to a forward pass, and SGLang moved its tree to Rust in v0.5.21 precisely to keep that CPU work small.

Predict: in the agent trace each turn resends the whole conversation (2,000-token system prompt plus every earlier turn). The pool grows from 24,000 to 48,000 token slots. What happens to the share of prompt tokens reused?
It jumps from about 70% to 97%. The agent's conversations interleave in time, and each one's history (thousands of tokens) has to survive until its next turn arrives 15 seconds later. At 24,000 slots the least recently used histories are evicted before they come back; at 48,000 they all fit. Hit rate is a cliff, not a slope, in the working-set size: the capacity planning question is whether the live histories fit, which the Capacity planner tab can size in GB.

So what does differ between the engines?
Not how many tokens the cache can reuse, but what the engine does with it: whether the scheduler orders the queue to reuse it before it is evicted (section 4), whether the router keeps a conversation on the replica that holds it (section 8), how big the pages are (SGLang's page size 1 matches to the token; most fast attention kernels want 16 or more, and SGLang uses 64 or 128 with some of them, overrides.py L1068), and how the cache spills to host memory and disk (HiCache, section 7; vLLM's offload connectors, Batching, KV cache and scheduling in depth).

4. Cache-aware scheduling: the order of the queue

The problem. When many requests wait at once and the KV pool cannot hold every shared prefix, the order in which the scheduler admits them decides whether a prefix is reused or evicted before its siblings arrive. Picture 160 questions about eight long documents, sent at once in a shuffled order, with a pool that holds about three documents. First come, first served visits the documents at random: a document is computed, evicted to make room for the next one, and computed again a few requests later.

How SGLang orders the queue. Before every prefill batch the scheduler matches each waiting request against the tree and sorts the queue by a schedule policy (calc_priority, schedule_policy.py L260):

fcfs (the default)

Arrival order. The default since v0.4.4 (2025-03-13); v0.3 to v0.4.3 defaulted to lpm (server_args.py at v0.4.3 and at v0.4.4). The release notes we read do not give the reason unconfirmed.

lpm: longest prefix match

Requests with the longest cached prefix go first, so what is cached is used before it can be evicted (L477). The docs suggest it "if the workload has many shared prefixes" and warn of more scheduling overhead (hyperparameter tuning).

in-batch prefix caching (inside lpm)

If several waiting requests share 32 or more tokens that are not yet cached, only the first is admitted now; the rest move to the back and hit the cache once it is computed (L373, thresholds 32 and 32 at L100). Without it, ten questions about an uncached document in one batch would each compute the document.

dfs-weight

Walk the tree depth first, heaviest subtree (most waiting requests) first, and admit in that order (base_prefix_cache.py L325). The SGLang paper proves that for a fixed batch, visiting the tree depth first gives the optimal hit rate when the cache holds at least the longest request, and that longest-prefix-first is equivalent (Theorem 3.1, arXiv 2312.07104).

the 128 cliff

With more than 128 requests waiting, lpm (and hrrn) silently fall back to arrival order to save the sorting cost (_determine_active_policy, L331). dfs-weight has no such cut-off.

Predict: you enable --schedule-policy lpm on a busy server where 300 requests are usually waiting. How much does the queue order change?
Not at all. With more than 128 requests waiting, _determine_active_policy returns FCFS for lpm, so the sort is skipped entirely, and it comes back only when the queue drains. On a server that is always deep in backlog, lpm does nothing; dfs-weight has no cut-off but costs a tree walk per scheduling pass. The real fix for a permanent backlog is more capacity or a router that keeps related requests together (section 8).
What it costs, when it matters, how to check
  • Cost: one prefix match per waiting request per scheduling pass, plus the sort; and fairness: a request whose prefix nobody shares can wait behind a stream of cache hits. The paper names this starvation risk and leaves fairness to future work; SGLang now offers hrrn (highest response ratio next, aging by processed tokens, L496) and priority scheduling.
  • When it matters: offline batch jobs and bursts (evaluations, synthetic data, RL rollouts with many samples per prompt, retrieval over a shared corpus) where the queue is deep and the cache smaller than the set of hot prefixes. At steady low load the queue is nearly empty and every policy is FCFS.
  • How to check: the prefill log line's #cached-token against #new-token, the per-request cached_tokens, and the total time of a fixed batch, with each policy in turn.

5. The overlap scheduler: hiding the CPU behind the GPU

The problem. Every decode step has CPU work around the GPU work: pick the batch, allocate KV slots, match prefixes, build the input tensors, then, after the forward pass, read the sampled tokens back, check stop conditions, free finished requests and insert them into the tree. In a plain loop the GPU waits while the CPU does all of this. On a large model the forward pass is long and the CPU share small; on a small model, or with many GPUs splitting each step so each one's share of the forward is short, the CPU share can be large. The SGLang v0.4 post says an unoptimized engine "can spend as much as half of its time on CPU overhead" (LMSYS, 2024-12-04) project's claim.

How it works. The overlap loop (event_loop_overlap, scheduler.py L1941) launches batch k on the GPU without waiting for it, then processes the results of batch k minus 1 and schedules batch k plus 1 while the GPU is busy. The catch is that batch k plus 1 needs the tokens batch k has not produced yet; SGLang passes them as placeholders that the GPU fills in when it gets there (the FutureMap, overlap_utils.py L248). The plain loop is still there (event_loop_normal, L1906) behind --disable-overlap-schedule. The idea is NanoFlow's, as the v0.4 post credits; vLLM's asynchronous scheduling does the same job.

What it costs, when it matters, how to check
  • Cost: complexity, one extra step of latency in noticing that a request finished (its slot frees one step late), and a sync point wherever the CPU must see a token before building the next step: on the Apple backend a batch with a grammar or a custom logit processor cannot be chained (scheduler_mixin.py); on GPUs SGLang syncs for grammars only with some speculative-decoding algorithms (L2015).
  • When it matters: small models, low batch sizes, many GPUs per model, fast GPUs: whenever a forward pass is a few milliseconds. The v0.4 post measured 1.1 times its previous version and says the gain is largest "on small models and large tensor parallelism sizes" vendor.
  • How to check: a profiler timeline (Nsight Systems on NVIDIA) shows gaps between kernels in the plain loop and none with overlap; without one, compare decode throughput at concurrency 1 with and without --disable-overlap-schedule, as done here.

6. Structured output: grammars, masks and the jump-forward that was removed

The problem. A tool call or an API response must be valid JSON matching a schema. Asking nicely fails some of the time; constrained decoding makes failure impossible by setting the probability of every token that would break the grammar to zero before sampling. The grammar (a JSON schema, a regular expression or an EBNF grammar) is compiled into an automaton; at every step the engine computes a token mask over the whole vocabulary (151,936 tokens for Qwen3) and applies it to the logits.

How SGLang does it now. The default backend is XGrammar (serving_hook.py L219), with llguidance and outlines selectable by --grammar-backend. XGrammar splits the vocabulary into tokens whose validity is known from the grammar position alone (checked ahead of time) and the few that need the parser's stack at run time, and overlaps the mask computation with the GPU's forward pass; its paper reports up to 100 times faster than earlier engines (Dong et al., arXiv 2411.15100) authors' measurement. A request asks for it with json_schema, regex or ebnf in its sampling parameters, or the OpenAI response_format.

The compressed FSM, and what became of it. In February 2024 SGLang introduced jump-forward decoding: where the grammar allows only one continuation (the key {"name": " in a schema, say), append that whole string in one prefill step instead of decoding it token by token, with the radix tree keeping the KV; the post reported up to 2 times lower latency and 2.5 times higher throughput than Outlines with vLLM (LMSYS, 2024-02-05) vendor. It was removed in v0.4.4 "to simplify the code maintenance" (PR #4032, merged 2025-03-03). In v0.5.21 the backends still define try_jump_forward (xgrammar_backend.py L167) but nothing in the scheduler calls it, so no current SGLang release jump-forwards.

What it costs, when it matters, how to check
  • Cost: compiling the grammar (cached per schema, so the first request with a new schema pays it), a vocabulary-sized mask per step, and on some paths the loss of CPU/GPU overlap. A constrained answer is also not the answer the model wanted: masking forces a different token where the model's choice was invalid, which can lower quality; reasoning models are usually left unconstrained while they think (structured outputs for reasoning models).
  • When it matters: tool calling and any machine-read output. The serving-time trade-offs (overhead under load, measured with llama.cpp grammars) are on LLM serving in production.
  • How to check: parse every response (here every constrained one parsed, see the M1 tab), and compare time per output token with and without the schema at the same output length.

8. The router: keeping a conversation where its cache is

The problem. With several replicas of a model (data parallelism), each has its own radix tree. A round-robin load balancer sends a conversation's next turn to a replica that has never seen it, so the cache hit rate falls toward one over the number of replicas. Sending every request to the replica with its prefix concentrates popular prefixes on one replica. The router has to trade cache affinity against load.

How SGLang's router decides (cache_aware.rs, select_worker L387). The router (now the SGLang Model Gateway, written in Rust) keeps an approximate radix tree per worker of the request texts it has sent there, in characters rather than tokens so it never tokenizes, and never asks the workers what they actually hold. For each request:

  1. If the load is imbalanced (the busiest worker has more than balance_abs_threshold requests more than the idlest and more than balance_rel_threshold times as many), send it to the least loaded worker.
  2. Otherwise find the worker whose tree matches the longest prefix of the text. If the matched share exceeds cache_threshold, send it there.
  3. Otherwise send it to the least loaded worker (the file's header comment says "smallest tree size"; the code picks the least loaded, ties broken at random).
  4. Insert the text into the chosen worker's tree; trees are trimmed least recently used on a timer.

The command-line defaults are a 0.3 cache threshold, 64 requests absolute and 1.5 times relative imbalance, eviction every 120 s and up to 226 tree nodes (main.rs L150-170); the Rust struct's own Default (0.5, 32, 1.1, 30 s, 10,000) and the Python launcher (eviction 60 s) disagree with them, so check which entry point you use. The v0.4 post reported 1.9 times the throughput and a hit rate of 75% against 20% with 8 replicas on a workload of long shared-prefix groups (LMSYS, 2024-12-04) vendor, one workload. The other policies are round_robin, random, power_of_two (pick the less loaded of two random workers), prefix_hash, consistent_hashing and bucket (policies/).

A router in front of real replicas, measured on this machine against round robin and least-loaded, is on LLM serving in production; the routing picture is on the root's Reading tab, section 9. The gateway also does prefill/decode routing, retries, circuit breakers, rate limits and tokenization in Rust (README).

9. Large scale: DeepSeek on 96 GPUs and on a rack

SGLang's large-scale recipes target mixture-of-experts models such as DeepSeek-V3/R1 (671 billion parameters, 37 billion active per token, 256 routed experts per layer, multi-head latent attention with one compressed KV vector per token). Serving them well needs four ideas, each explained in depth on Distributed and disaggregated serving:

DP attentionWith MLA there is a single KV head, so splitting attention across GPUs by heads (tensor parallelism) would copy the whole KV cache to every GPU. SGLang instead runs attention data-parallel, each GPU holding different requests' KV, and gathers only around the expert layers; v0.4 reported 1.9 times decode throughput from it vendor.
Expert parallelism (EP) with DeepEPEach GPU holds a slice of the experts; every token is sent to the GPUs holding its chosen experts and back (all-to-all), with DeepEP's normal mode for prefill and low-latency mode for decode (--moe-a2a-backend deepep, EP docs).
EPLBSome experts are far more popular; DeepSeek's expert-parallel load balancer replicates hot experts into redundant slots (256 plus 32 = 288), which also allows 12 or 72 GPUs instead of powers of two.
Two-batch overlapSplit the batch in two so one half's all-to-all runs while the other half computes; on GB200 NVL72's faster links SGLang moved to finer single-batch overlap.
Prefill/decode disaggregationPrefill and decode run on different GPU pools and the KV cache moves between them over RDMA with Mooncake or NIXL (PD docs); v0.5.21 lets an instance switch role without a restart (#28403).

11. Running SGLang on a Mac, and what broke

Since 2026 SGLang runs natively on Apple silicon: with SGLANG_USE_MLX=1 the scheduler, radix cache and API are SGLang's own, and the forward pass runs in Apple's MLX (Apple Metal docs). That is what made the measurements on this page possible on a laptop. It is installed from source (no macOS wheel on PyPI: the v0.5.21 wheels are Linux only) with the srt_mps extra, which brings PyTorch 2.13.0, MLX and XGrammar 0.2.7. Several problems surfaced, and the way they were found is the useful part:

1. It did not start

v0.5.21 stopped at start-up with AttributeError: 'MlxModelRunnerStub' object has no attribute 'kv_cache_configurator'. A refactor of the token-capacity code had not been carried to the Apple path; the fix (PR #41314, merged 2026-09-30) landed one day after the release's tag commit. Applying its seven-line property let the server start.

2. It answered the wrong question

With the cache on, send A, then an unrelated B, then A again, all greedy: the second A came back as unrelated text ("a) the number of employees in the company...") with 25 of its 26 prompt tokens reported cached. Disabling the radix cache made it go away, which pointed at the cache. This is open issue #42415 (reported on v0.5.20); the open pull request #42542 traces it to chained decode steps writing a finished request's KV into slots the tree still points at. With that patch applied the repeat answered A again, every time.

3. Not a bug: cached and uncached answers differ

Even patched, the cached A diverged from the uncached A after eight tokens ("is used to store" against "represents the hierarchical"). MLX-LM alone, with no SGLang, does the same when the prompt is computed in two pieces instead of one: the top two candidates were within 0.125 of each other in logit at that step, and computing in a different order rounds differently. Prefix caching is exact in arithmetic, not in floating point.

4. Crashes

The server died with [METAL] Command buffer execution failed: Insufficient Memory, with gigabytes free, in several situations: every time the radix cache had to evict (a 3,000-token pool and 840-token prompts one at a time, with and without the patch of item 2); every time a prefill batch mixed a chunked prompt (512-token chunks) with other requests; on a burst of requests sent after /flush_cache (seen in two runs, not isolated further); and in every run of the overlap experiment (32 requests of 128 tokens in and out, one after another), with the overlap loop on or off. The dfs-weight queue runs crashed too. Open pull requests on the Apple backend touch neighbouring code (per-request buffers released late, #39251; retracted requests' state, #38179; no device-memory figure on Apple, #39675); none was confirmed as the cause here. The runs on this page avoid all three: a pool large enough never to evict, chunks of 4,096 and no flushes. The backend also gives each running request its own 4,096-token KV buffer per layer (448 MiB for this model), so at most 8 ran at once.

The habit this teaches
Before trusting a cache, run the same greedy request with it on and off, and an unrelated request in between. Identical text is not guaranteed (item 3), but a different topic is a bug (item 2). All measurements on this page were taken with both fixes applied and the crashes avoided; the commands, patches and raw results are on the SGLang on the M1 tab.

Common mistakes

"SGLang schedules by longest prefix by default."
Not since v0.4.4 (March 2025): the default is fcfs. Cache-aware ordering is opt-in, and lpm turns itself off whenever more than 128 requests wait.
"The radix tree gets more cache hits than vLLM's blocks."
On the same requests and pool they reused the same share of tokens within a point; with a tight pool the blocks can win because they evict one block at a time (section 3). The engines differ in ordering, routing and recipes, not in what the cache structure can find.
"SGLang decodes forced JSON strings in one jump."
Jump-forward decoding was removed in v0.4.4 (PR #4032). Constrained decoding today is per-token masking by XGrammar.
Quoting launch-blog speedups as today's gap.
The 5 times of January 2024 was against a vLLM without any cross-request cache. Compare current builds, on your model, on your hardware, at your latency target.
Measuring prefix caching with identical repeated prompts.
That measures the best case. Real hit rates depend on whether the working set of live prefixes fits the pool: the agent trace went from about 70% to 97% between 24,000 and 48,000 slots. Size the pool from the number of live conversations times their history.
Expecting bit-identical output with and without the cache.
Different computation order rounds differently; at a near-tie greedy decoding flips. Test for the right topic, not for identical bytes.
Reading a vendor "25x" as a hardware ratio.
It was measured at one per-user speed (50 tokens/s) where the older GPU is weakest; the same post says the unconstrained gap is much smaller.

Interview questions

Why a radix tree rather than a trie or a hash map for prefix caching?
A hash map of whole prompts finds only exact repeats; a trie finds longest prefixes but has one node per token; a radix tree compresses runs into single edges, so nodes exist only where cached sequences diverge, and a lookup walks one path comparing tokens.
How does SGLang avoid evicting KV that a running request needs?
Lock references: a request increments a counter on every node of its matched path; eviction only takes unlocked leaves, and a parent becomes a candidate only once all its children are gone.
Why is a prefix match capped at the prompt length minus one?
The last prompt token's forward pass produces the logits for the first output token, so it must be computed even when its KV is cached. Both SGLang and vLLM cap the hit there.
When does cache-aware scheduling help, and what does it cost?
When the queue is deep and the cache cannot hold all hot prefixes: ordering by longest match (or depth-first through the tree) uses a prefix before it is evicted. It costs a match per waiting request per pass and can starve requests with unshared prompts; SGLang disables lpm above 128 waiting requests.
What does the overlap scheduler overlap, and what is its catch?
The CPU's scheduling and result processing for neighbouring steps with the GPU's forward pass, using placeholders for tokens not yet produced. Catch: anything that needs the previous token on the CPU (some grammar paths, custom logit processors) forces a sync.
Design a router for 8 replicas of a chat model with long system prompts.
Route by prefix affinity (approximate per-replica trees or consistent hashing of the prefix) but fall back to least-loaded when the load is imbalanced beyond a threshold; measure hit rate, TTFT percentiles and per-replica load. SGLang's gateway does exactly this with a 0.3 match threshold and 64/1.5 imbalance thresholds by default.
Why does DeepSeek serving use data-parallel attention with expert parallelism?
MLA has one compressed KV per token, so tensor-parallel attention would replicate the cache on every GPU; data-parallel attention keeps each request's cache on one GPU, and expert parallelism spreads the experts, with all-to-all exchanges around each MoE layer.
How would you check that prefix caching is working on a production server?
Per-request cached-token counts or the hit-rate metric, TTFT split by hit and miss, and a greedy A/B/A correctness test with the cache on and off.

What the port does, and what it leaves out
Requests run one at a time, so the comparison isolates the cache: match the prompt (capped at its length minus one), lock the matched path, evict least recently used leaves or blocks until the request's new KV fits, insert prompt and output (minus the last token, whose KV is never computed), unlock. Not modelled: concurrency (several running requests locking more of the tree), HiCache or vLLM's offload tiers, page sizes other than 1 and 16, sliding-window or hybrid models. SGLang v0.5.21 makes a Rust tree core the default; the Python core was run here (the Rust extension was not built), and SGLang runs the same unit suite against both (test/registered/unit/mem_cache/test_rust_unified_radix_cache_unittest.py).

The model, and how it was checked
A round: match every waiting question against the tree; order the queue by the policy; admit questions in that order while each one's new tokens plus its output fit in the free and evictable pool and the round's prefill stays under 16,384 tokens, stopping at the first that does not fit; run the admitted ones to completion and insert them. Real SGLang admits continuously, reserves output space by an estimate scaled by --schedule-conservativeness, and overlaps prefill with running decodes, so the numbers here are the policy's effect in isolation, not a throughput prediction. What transfers to a datacenter GPU

  • Transfers: which tokens are cached and reused (the scheduler and tree are the same code), the ordering effects of the queue policies, the correctness test, the fact that a grammar adds per-step CPU work.
  • Does not transfer: the absolute times. A 0.6B model on a laptop GPU makes the forward pass short and the Python scheduler's share large, so CPU-side effects (overlap, grammar masks) look bigger here than on an H100 serving a 70B model; prefill costs far more per token here than on a GPU, so cache hits save more seconds here. The MLX backend also lacks paged attention: it copies a cached prefix out of the pool into a per-request cache (model_runner.py).

What this comparison can and cannot say
  • Different builds and dates. The vLLM runs used v0.25.0 to v0.25.1 or nightly images from July to September 2026; the SGLang runs used nightly images from late June and July 2026 (shown per row). Both engines have released several versions since (vLLM v0.31.0, SGLang v0.5.21).
