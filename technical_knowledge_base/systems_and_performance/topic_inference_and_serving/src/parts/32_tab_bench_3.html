Batching: one read of the weights, many users served

Because decode is limited by reading the weights, decoding several sequences in the same step costs little more than decoding one: the weights are read once and applied to every sequence in the batch. Total throughput rises with batch size; each user's own speed falls a little. This is why serving engines batch, and why a server that is idle most of the time wastes most of what the hardware can do.

Predict: one sequence decodes at about 190 tokens/s. With 8 sequences in the same batch, what is the total?
Measured tokens/s with 8 sequences: about 2x, not 8x. On this small model and this GPU every extra sequence makes the step noticeably slower (a step with 2 tokens already costs x a step with 1, measured in the speculative decoding section), so the gain is far from linear; it keeps growing to x at 64 sequences. On a large model on a datacenter GPU the first steps are closer to free (see What transfers).

The throughput-latency curve, and where it bends

A real server has requests arriving at random times. This tab's load generator (src/bench/scripts/loadgen.py, standard library only) sends streamed completion requests in two ways. Closed loop: a fixed number of users, each sending a new request as soon as the last one finishes. Open loop: requests arrive as a Poisson process (independent random arrivals at a set average rate, fixed seed), which is how MLPerf's Server scenario and most production traffic behave. Every request has a 400-word prompt (about 410 tokens, with a unique tag so no prompt is cached) and asks for exactly 128 tokens.

Goodput under an SLO

A service level objective (SLO) sets the latency each request must meet, for example "first token within 1 s and at most 50 ms between tokens". Goodput counts only the requests that met it. Move the limits and watch which load level gives the most useful work: past the bend, raw throughput stays flat but goodput collapses.
