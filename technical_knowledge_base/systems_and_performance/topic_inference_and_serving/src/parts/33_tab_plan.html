Capacity planner

How many GPUs a model needs to serve a given traffic within a latency promise, what that costs per million tokens, and whether an API would be cheaper. You choose the model, the precision, the GPU, how the model is split across GPUs, the traffic and the latency targets; the planner works out the memory each GPU spends, how many conversations fit at once, how long each engine step takes, the most traffic one copy of the model can carry inside the targets, and the bill. The formulas are the hardware root's {{Performance calculator|n:3c65c17b0d0d8118beeefaed56da6f8e}} (FLOPs and bytes per step, KV cache per token, the same functions) and they extend the {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}} page's serving frontier with queueing, latency targets and prices. Every result is an estimate from a stated model whose two engine constants are fitted to published MLPerf runs; the residuals are shown below, not hidden.

Try: start from the running example (a chat assistant on Llama 3.1 70B), then open the worked examples: each one sets every control and says what to notice and how the planner compares with what was published.

How close is the model? Calibration against published runs

The planner has two engine constants that no datasheet gives: the share of peak compute the engine reaches, and a fixed overhead per step (scheduling, sampling, kernel launches). They are fitted to MLPerf Inference v5.1 runs of Llama 3.1 8B whose full settings are public (vendor submissions, reviewed by MLCommons): the compute share so the offline ceiling equals the Offline result, the overhead so the simulated mean TPOT at the Server run's arrival rate equals the measured one. Everything else in the table is not fitted and tests the model: the Server throughput inside 2 s and 100 ms, the measured TTFT, another submitter's run, and each GPU's constants applied to the others. A third constant, the share of memory bandwidth reached (80%), is an assumption.

How noisy is the simulation?

Latencies come from simulating 3,000 requests with one fixed random seed (the same arrivals at every rate, so curves are smooth). Near the knee a different seed gives a different answer, which is a real property of a loaded server, not only of the simulation: a burst lengthens steps, longer steps let more sequences pile up, and the queue takes a while to drain. The model, every formula and assumption
KV pool per GPU = memory × utilisation − weights per GPU − activations − other
weights per GPU
weights / (TP × PP); with expert parallelism, all non-expert weights plus experts / GPUs. FP8 and INT4 keep the embedding and LM head at 16 bits, as released checkpoints do: this reproduces the 9.08 GB of RedHatAI's Llama-3.1-8B-Instruct-FP8 (1.05B BF16 plus 6.98B FP8 parameters, Hugging Face API) derived
activations
tokens per step × 2 bytes × (2h + 2 × FFN width / TP) + sampled positions × vocabulary × 4 bytes / TP: an estimate of the peak vLLM measures in its profiling run estimate
sequences that fit
(pool − shared prefix, stored once) / (KV per token per GPU × held tokens), held = uncached prompt + half the output, rounded up to 16-token blocks (vLLM's default block). KV per token per GPU: GQA heads split over TP but never below one head per GPU; DeepSeek's MLA latent is the same on every TP rank; PP splits layers
step = PP × [ max( bytes / (bandwidth × ηm), FLOPs / (peak × ηc) ) + communication ] + overhead + B × per-sequence cost
bytes
weights read once per micro-batch (for MoE, only the experts the step's tokens touch, uniform routing: the parent's formula) + every decoding sequence's cache at its mean context
FLOPs
2 × active parameters per token + attention: the parent's decode and prefill counts
communication
TP: two all-reduces per layer, ring time 2(n−1)/n × bytes / link + latency (two NVLink hops of 3.33 µs, doubled on PCIe assumption); EP: dispatch (FP8) and combine (BF16) all-to-all per MoE layer
per-sequence cost
an extra fixed time per decoding sequence per step; zero for the GPU engines (their fits do not need it), fitted for llama.cpp on the M1 Pro, whose batched decode costs far more per sequence than the bytes it reads
peak
dense FP8 peak for FP8 weights on chips that have it, otherwise dense BF16 (weight-only INT4 and MXFP4 compute in 16 bits)
offline ceiling: T = step(B = λ × O × T, c = λ × Pu × T)
B, c
sequences decoding at once (Little's law) and prompt tokens per step, at arrival rate λ per copy, when every step carries the prompts that arrived during the previous one (the fluid limit)
ceiling
the highest λ with a solution that keeps B within the cache and B + c within the token budget: the most one copy can do with no latency target (MLPerf's Offline scenario)
latencies: simulate the scheduler, step by step
arrivals
Poisson, 3,000 requests, one fixed seed (MLPerf's Server scenario also uses Poisson arrivals); the first 15% are warm-up and not counted
each step
every running sequence decodes one token; the budget left goes to waiting prompts first come first served, in chunks (chunked prefill); a new sequence starts only while the cache has room; the step lasts step(B, c) from the formula above
TTFT, TPOT
first token at the end of the step that finishes the prompt; TPOT = (finish − first token) / (O − 1), averaged over requests; the targets are p99 TTFT and mean TPOT
inside targets
bisection on λ between 0 and the offline ceiling; a run whose waiting queue keeps growing counts as a miss
$ per hour = GPUs × price;   $ per M output = $ per hour × (1 − fprefill) / output tokens per hour × 106
GPUs
ceil(peak traffic / highest rate per copy inside both targets) × GPUs per copy
fprefill
the prefill share of step time at the operating point (one convention for splitting a shared bill; the blended price per token does not depend on it)
tokens per hour
at the average traffic: a fleet sized for the peak is paid for all day

Not modelled: speculative decoding, varying prompt and output lengths (fixed here; real spread lengthens the TTFT tail, as the MLPerf check shows), preemption churn, prefill/decode disaggregation, CPU offload of the cache, request routing across copies (assumed perfect), and cold starts.
