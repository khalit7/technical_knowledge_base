0. The map

The idea in one sentence. Every decode step reads all the model's weights to produce one token per user, so serving is the craft of putting as many users as possible on each read of the weights, while their KV caches fit in the memory left over and each user's latency stays inside its promise.

The running example. A chat assistant built on Llama 3.1 70B (70.6 billion parameters, 80 layers; {{config.json|https://huggingface.co/unsloth/Meta-Llama-3.1-70B/blob/main/config.json}}, an open mirror of Meta's gated repository), stored in FP8 (one byte per weight) on NVIDIA H200 GPUs (141 GB of memory at 4.8 TB/s, {{NVIDIA|https://www.nvidia.com/en-us/data-center/h200/}}). Every request carries a 2,000-token prompt whose first 1,000 tokens are the same system prompt, and gets a 300-token answer. It is the deployment the {{Capacity planner|#t-plan}} opens with, so every number here can be checked there, and the children reuse it. A token is the unit the model reads and writes, about three quarters of an English word on average.

Fig. 1 is the page: one request's path through a serving fleet, each part lit where it acts, with the child page that owns it.

  1. The map: one request, one fleet. Users and agents send prompts and get a stream of tokens back. A router picks one of several replicas (copies of the model); inside the replica a serving engine (vLLM, SGLang, TensorRT-LLM, llama.cpp, MLX: the same five parts, built differently, compared in section 7) turns the prompt into tokens on one GPU or many; a laptop beside them runs the same loop for one user. Drawn: three H200 replicas and one laptop illustrative layout; the numbers are the running example's. Each step lights one part and links the child page whose own figure teaches it.
  2. Router: send the request to its cache. Pick a replica for each request: round-robin ignores the cache, while a prefix-aware router sends a returning conversation back to the replica that holds its prefix, weighed against load; an autoscaler adds replicas when queues grow, before users wait. On eight real requests over three replicas, round-robin computed 13,000 prompt tokens and the prefix-following rules as few as 5,804 (section 10). Owner: {{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}, whose {{Fig. 2|n:3f35c17b0d0d818aa406da1f7a784c62#stg-rt}} steps those requests (sections 2 to 4); {{Distributed and disaggregated serving|n:3c65c17b0d0d8170bd7cdf47af0ec07b}}'s {{Fig. 2|n:3c65c17b0d0d8170bd7cdf47af0ec07b#stg-rt}} scores workers by cache against load, and its section 8 covers the serving layers above engines (Dynamo, llm-d).
  3. Scheduler and KV cache manager: who runs this step, and where their memory goes. On one H200 the 72.66 GB of FP8 weights land first; about 54 GB is left for the KV cache, cut into blocks, room for 141 conversations (bars to scale). Every step the scheduler builds the batch: who decodes, which prompt chunks join, who waits or is preempted; the cache manager hands out blocks, keeps shared prefixes and offloads cold ones. Owner: {{Batching, KV cache and scheduling|n:3c65c17b0d0d819db53bd2c48909e5b2}}, whose {{Fig. 1|n:3c65c17b0d0d819db53bd2c48909e5b2#stg-hero}} builds one engine step and {{Fig. 3|n:3c65c17b0d0d819db53bd2c48909e5b2#stg-pool}} lays block tables over one pool; the real code is {{vLLM|n:3c65c17b0d0d8113b976d8bcaf2c0722}}'s {{Fig. 2|n:3c65c17b0d0d8113b976d8bcaf2c0722#stg-step}} (one engine step, recorded) and {{SGLang|n:3c65c17b0d0d81e691e4ce9f9b5d1fad}}'s {{Fig. 2|n:3c65c17b0d0d81e691e4ce9f9b5d1fad#stg-tree}} (a radix tree). Sections 4 and 5.
  4. Model runner, prefill: the whole prompt in one pass. All 2,000 prompt tokens go through the 80 layers together (drawn as 8 glass plates of 10 layers) and write their keys and values into the pool, 625 MiB. One read of the weights serves 2,000 tokens, 3,956 operations per byte, so the arithmetic sets the pace (compute-bound): 0.42 s, the time to first token. This page owns it: sections 1 and 2, Figs. 2 and 3.
  5. Model runner, decode: one token per user per step. Each step feeds only the newest token of every running request; the weights are read once for all of them, plus each request's own cache (bandwidth-bound). Alone: 21.6 ms a step, 46 tokens a second, 2 operations per byte; 141 users on the same read get 2,982 tokens a second between them (section 5). One engine step with prefill chunks and decodes mixed is {{Batching|n:3c65c17b0d0d819db53bd2c48909e5b2}}'s {{Fig. 1|n:3c65c17b0d0d819db53bd2c48909e5b2#stg-hero}}; eight requests in four seats, static against continuous batching, its {{Fig. 2|n:3c65c17b0d0d819db53bd2c48909e5b2#stg-cb}}.
  6. Sampler: 128,256 scores become one token. The last layer gives a score for every token in Llama 3.1's vocabulary; temperature, top-p, penalties and grammar masks pick one, which is streamed to the user and fed back as the next step's input. Owner: {{Sampling and decoding|n:3c65c17b0d0d8115bafcda29a2c7086e}}, whose {{Fig. 1|n:3c65c17b0d0d8115bafcda29a2c7086e#stg-hero}} runs one real distribution through the decoder and {{Fig. 3|n:3c65c17b0d0d8115bafcda29a2c7086e#stg-mask}} draws a grammar mask.
  7. Drafter (optional): several tokens per read. Decode leaves the arithmetic idle, so a cheap draft guesses k tokens and the model checks them all in one pass, keeping the run it agrees with; the output stays exactly the model's. It pays while checking k tokens costs little more than one: on the laptop a Qwen3-4B pass over 4 tokens cost 2.2 times a pass over 1 measured here (section 8). Owner: {{Speculative decoding|n:3f35c17b0d0d81e086fde85940ebac1c}}, whose {{Fig. 1|n:3f35c17b0d0d81e086fde85940ebac1c#stg-hero}} runs one round on real tokens and {{Fig. 3|n:3f35c17b0d0d81e086fde85940ebac1c#stg-xo}} shows the gain fade as the batch grows.
  8. One GPU or many: replicas, slices and two pools. One copy serves 2.11 requests a second inside the running example's promises, so 20 at peak need 10 H200s (section 6). When one GPU's memory or speed is not enough, the model is sliced (tensor, pipeline or expert parallelism), or prefill and decode move to separate pools and the finished cache crosses between them: 625 MiB for a 2,000-token prompt, about 13 ms over a 400 Gb/s link (section 9). Owner: {{Distributed and disaggregated serving|n:3c65c17b0d0d8170bd7cdf47af0ec07b}}, whose {{Fig. 1|n:3c65c17b0d0d8170bd7cdf47af0ec07b#stg-hero}} draws five ways to spread serving and {{Fig. 6|n:3c65c17b0d0d8170bd7cdf47af0ec07b#stg-pd}} colocated against disaggregated; the pool following the traffic is {{Production|n:3f35c17b0d0d818aa406da1f7a784c62}}'s {{Fig. 3|n:3f35c17b0d0d818aa406da1f7a784c62#stg-as}}.
  9. A laptop: the same loop for one user. On a machine you own there is usually one user, so decode speed is memory bandwidth over the bytes read per token: Qwen3-0.6B at Q4_K_M generates 196 tokens a second on this M1 Pro measured here. The weights arrive as a file in some format and precision. Owner: {{Local and on-device inference|n:3c65c17b0d0d81f7a144fe25d799e811}}, whose {{Fig. 1|n:3c65c17b0d0d81f7a144fe25d799e811#stg-hero}} puts one model in this laptop's memory and {{Fig. 3|n:3c65c17b0d0d81f7a144fe25d799e811#stg-bw}} sets bytes per token against tokens per second (files and GGUF types: sections 3 to 5); number formats: {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}.

A map, not a mechanism: each step lights the part one child page owns and links that child's own figure. Judged on: time to first token, time per output token, goodput under a latency promise, and dollars per million tokens ({{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}, section 1). This page's {{Capacity planner|#t-plan}} computes all four for any model and GPU; its {{Serving simulator|#t-sim}} runs the engine box; its {{Engine bench|#t-bench}} measured real engines. Counts drawn (three replicas, eight layer plates, the blocks, the users) are illustrative; the bar heights in step 3 are the page's numbers to scale.

New terms
Prefill: the prompt in one pass; writes the KV cache, yields the first token.
Decode: one pass per further token, reading the weights and the cache.
KV cache: the keys and values every past token keeps in every layer.
TTFT, TPOT: time to first token; time per output token after it.
Continuous batching: re-forming the batch every step.
Paged cache: the cache in fixed-size blocks found through a block table.
Prefix caching: keeping a prompt's cache for the next request that starts the same way.
Goodput: the load served while the latency promise holds.
Replica: one copy of the model behind a router.
