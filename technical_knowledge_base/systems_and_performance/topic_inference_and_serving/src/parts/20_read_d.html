4. Memory: the KV cache decides how many users fit

Every token of every active conversation keeps one key and one value vector in every layer:

KV bytes per token = 2 × layers × KV heads × head size × bytes per number
2
one key and one value
KV heads
with grouped-query attention (GQA) several query heads share one, which is why Llama 3.1 70B has 64 query heads but only 8 KV heads
bytes
2 for FP16/BF16, 1 for an FP8 cache

For Llama 3.1 70B that is 2 × 80 × 8 × 128 × 2 = 327,680 bytes, 320 KiB per token, so one 2,300-token conversation holds 719 MiB 2,300 × 320 KiB. The formula matches a real engine: for Qwen3-0.6B it gives 114,688 bytes, exactly what llama.cpp allocated measured here (448 MiB at 4,096 tokens, {{Engine bench|#t-bench}}). On one H200 with FP8 weights, vLLM's default 92% of 141 GB leaves about 54 GB for the cache after weights and activations: room for 141 conversations of the running example, with the shared system prompt stored once {{Capacity planner|#t-plan}}, section 1. The 142nd user waits, and since more users per step means more throughput (section 5), the cache size is the throughput ceiling. Model design moves it most: GQA cut Llama's cache 8 times against full multi-head attention, and DeepSeek's latent attention stores one 576-number vector per layer. The cache of any model at any context, against the weights, is on {{Long context|n:3fd5c17b0d0d81059ee1ce20c0326dc5#t-kv}}'s KV calculator; the attention designs behind it on {{Attention variants|n:3fd5c17b0d0d8120859ecc2d0236e846}}.

How engines make the most of it, each owned by {{Batching, KV cache and scheduling in depth|n:3c65c17b0d0d819db53bd2c48909e5b2}}:

Paging (section 2)PagedAttention cuts the cache into fixed blocks (16 tokens by default in vLLM) found through a per-request block table, so waste falls to one partly filled block per request ({{PagedAttention paper page|n:3c65c17b0d0d81bf8b90ca93fee19f5f}}).
Prefix caching (section 3)Blocks are named by a hash of their tokens and their predecessor's hash (vLLM) or kept in a radix tree (SGLang), so a request that starts like an earlier one skips that prefill.
Offload (section 4)Cold blocks move to CPU memory or SSD and come back on a hit (LMCache, Mooncake's store, llm-d's tiered cache).
When the pool is full (section 6)Evict unused cached blocks first, then stop admitting, then preempt a running request and recompute or swap it back.
Fewer bytes (section 8)An 8-bit cache halves the bytes (llama.cpp: 60,928 bytes per token against 114,688); dropping tokens only saves memory when whole blocks are freed, the realisable saving that page measures.

The cache as physical memory is on {{Memory technology|n:3f05c17b0d0d818ab063e327e3d7009f}}; measured cache size against context in the {{Engine bench|#t-bench}}, section "KV cache memory against context".

5. Batching and scheduling: one read of the weights, many users

A decode step reads 72.66 GB of weights to produce one token for one user. Let many users' next tokens ride on the same read: the weights are read once per step whatever the batch, and each extra user adds only its own cache bytes and a little arithmetic. On the H200 model, one user alone gets 46 tokens per second; 141 users together get 2,982, each at 21, and 64 users give 42 times the tokens of one for 1.54 times the step time {{Capacity planner|#t-plan}}. On the laptop measured here each extra sequence cost about 1.2 ms per step on top of the weight read, so 64 sequences gave 7 times the throughput of one measured here ({{Engine bench|#t-bench}}, "Batching"). More throughput for the owner against slower tokens for each user is the central dial of serving; past the knee, more users add latency without adding throughput.

Continuous batching (Orca, {{Yu et al., OSDI 2022|https://www.usenix.org/conference/osdi22/presentation/yu}}: 36.9 times FasterTransformer's throughput at the same latency on GPT-3 175B, their measurement) re-forms the batch every step, so a finished request leaves and a waiting one joins at once; static batching ran until the longest answer ended, and dynamic batching (wait to fill, then run as a unit) suits one-pass models such as classifiers and embedders, not generation. Every engine here batches continuously by default. The before and after on the same requests is drawn on {{Batching, KV cache and scheduling in depth|n:3c65c17b0d0d819db53bd2c48909e5b2}}, section 1, with paging's in its section 2.

6. Latency promises and the bill

A service level objective (SLO) is the latency promise, written on a percentile: "99% of requests see their first token within 2 seconds" is a p99 TTFT target. Percentiles matter because a user who sends twenty messages meets the slow tail. One request measured here shows why: under 16 concurrent users on llama-server (Qwen3-0.6B, a 412-token prompt, 128 tokens out) it saw a TTFT of 0.96 s and a mean TPOT of 43.9 ms, yet a median gap of 31.4 ms and a longest gap of 803 ms, a step where another user's prompt was being read measured here ({{Engine bench|#t-bench}}, "One request alone, and the same request under load"). MLPerf's targets for Llama 3.1 8B are p99 TTFT 2 s and p99 TPOT 100 ms, and 0.5 s and 30 ms in its interactive scenario ({{MLPerf inference rules|https://github.com/mlcommons/inference_policies/blob/master/inference_rules.adoc}}). Goodput (DistServe's term) is the highest request rate at which the target share of requests meets the SLOs: throughput that breaks the promise is not worth having.

GPUs = ⌈ peak requests/s ÷ requests/s one copy serves within the SLO ⌉ × GPUs per copy
$ per million tokens = $ per GPU-hour × GPUs ÷ (millions of tokens per hour at average traffic)

For the running example the {{Capacity planner|#t-plan}} finds that one H200 serves 2.11 requests per second within p99 TTFT 2 s and TPOT 50 ms (at that load TTFT p99 1.05 s, TPOT 46.8 ms), so 20 at peak need 10 H200s: $44.70 an hour at $4.47 per H200-hour, $0.54 per million tokens at half the peak on average, against $33.12 an hour for the same traffic at $0.40 per million from the cheapest API listed on 2026-10-08 planner, worked example "Chat assistant". For this workload the API is cheaper. The 50 ms TPOT target, not memory, sets the number of copies: relaxing it to 100 ms cuts the fleet from 10 GPUs to 8 ($35.76 an hour). Utilisation, not peak speed, decides self-host against API: one H200 at full batch makes 10.7 million output tokens an hour, $0.42 per million, but only if it is full every hour. Self-hosting wins with high and steady use, reserved or cheaper GPUs, heavy prefix reuse, a model no provider hosts, or data that cannot leave your network; add the engineers' time. How these definitions are measured, the cost slider and the break-even point are on {{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}, section 1; laptop numbers do not transfer to these dollars, only ratios and the shapes of the curves do (the {{Engine bench|#t-bench}}'s "What transfers").
