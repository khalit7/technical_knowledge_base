3. Batching: one read of the weights, many users served

The problem. A decode step reads 72.66 GB of weights to produce one token for one user, and the arithmetic units sit idle. The idea: let many users' next tokens ride on the same read. The weights are read once per step whatever the batch; each extra user adds only the bytes of its own cache and a little arithmetic. So the step barely slows while the tokens per step multiply:

measured here: llama-batched-bench, Qwen3-0.6B Q4_K_M on the M1 Pro GPU ({{Engine bench|#t-bench}}, section "Batching"). Here each extra sequence costs about 1.2 ms per step on top of the weight read, so 64 sequences give 7 times the throughput of one, not 64; on the H200 model, 64 users give 42 times.

Throughput climbs almost linearly while the step is dominated by the weight read, then bends as each user's cache read and arithmetic add up; each user's own speed falls as the step lengthens. That trade, more throughput for the owner against slower tokens for each user, is the central dial of serving. Baseten's framing is the test for any change: batch size, quantization level or speculation settings move a deployment along the latency-throughput frontier, while better kernels, cache management or architecture push the frontier outward ({{Baseten, 2026-09-02|https://www.baseten.co/blog/the-efficient-frontier-of-llm-inference/}}). Only the second is a free win.

Static, dynamic and continuous batching

StaticRun a batch until its longest answer ends; early finishers leave empty seats, new arrivals wait.
DynamicWait up to a time limit to fill a batch, then run it as a unit: right for one-pass models (classifiers, embeddings), not for generation.
ContinuousRe-form the batch every step: finished requests leave, waiting ones join at once. Also called iteration-level scheduling or in-flight batching.

Continuous batching was introduced by Orca ({{Yu et al., OSDI 2022|https://www.usenix.org/conference/osdi22/presentation/yu}}): the scheduler runs the model for one iteration at a time, and "selective batching" batches the matrix multiplications over all tokens of all requests while attention runs per request, since each request has its own cache. The authors reported 36.9 times the throughput of NVIDIA FasterTransformer at the same latency on GPT-3 175B (their measurement). It is why serving got so much cheaper in 2022 to 2023, and every engine on this page now does it by default (llama-server's "continuous batching on", TensorRT-LLM's "in-flight batching", vLLM's and SGLang's schedulers). The {{Serving simulator|#t-sim}} animates the same 20 requests under static and continuous batching in its section 1.

Predict: static batching versus continuous batching on chat traffic whose answers range from 10 to 1,000 tokens. Which suffers most under static batching?
Both. A static batch runs as long as its longest answer, so a 10-token answer holds its seat for 1,000 steps (throughput lost), and a request that arrives just after the batch starts waits for all of it before its first token (TTFT lost). A larger batch makes both worse: more seats empty, longer waits. Try it in the {{Serving simulator|#t-sim}}'s lab.
What it costs, when it matters, how to check
  • Cost: every extra user lengthens every step a little (higher TPOT for all) and holds cache memory; past the knee, adding users adds latency without adding throughput.
  • When it matters: always for a shared server; not for a single local user, where batch size is one and only fewer bytes per token help.
  • How to check: sweep concurrency and plot throughput against TPOT and TTFT; the operating point is just before the knee. The {{Engine bench|#t-bench}} measured that curve on real engines (section "The throughput-latency curve").
