One request alone, and the same request under load

Two numbers describe how a streamed answer feels. TTFT (time to first token) is how long you stare at an empty box: the server has to queue the request, read the whole prompt (prefill) and produce the first token. TPOT (time per output token, also called inter-token latency) is the gap between the tokens that follow, one per decode step. What changes under load: the first token waits behind other prompts being read (TTFT s against s), and each later token waits for a decode step that now carries 16 sequences and, every few steps, someone else's prompt (median gap ms against ms, with spikes up to ms when a new prompt joins the batch).

Prefill and decode are two different workloads

Prefill pushes the whole prompt through the model in one pass: hundreds of tokens share each read of the weights, so the GPU's arithmetic units are the limit (compute-bound). Decode produces one token per pass: every weight is read from memory to do a little arithmetic for a single token, so memory bandwidth is the limit (memory-bound). Prompt processing speed against prompt length

llama-bench, Qwen3-0.6B, F16 and Q4_K_M, 3 repetitions per point (bars show min to max). Short prompts are too small to keep the GPU busy; past about 256 tokens the speed falls again because attention over the prompt grows with the square of its length. F16 prefills faster than Q4_K_M: 4-bit weights must be unpacked before the matrix multiply, and prefill is limited by arithmetic, not by bytes.

At short context the fixed cost dominates: a 0.6B model is too small to saturate memory bandwidth one token at a time. At 16K context the KV cache read dominates and the bandwidth model explains the slowdown. Flash attention matters most at long context, where it avoids writing and re-reading the attention scores.
