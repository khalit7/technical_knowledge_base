Engines side by side, same workload

The same closed-loop workload (410-token prompts, 128 output tokens) against three engines. llama.cpp and MLX run Qwen3-0.6B on the GPU at about 4.5 to 5 bits per weight; vLLM runs it on 4 CPU cores in 32-bit floats, so compare its shape with the others, not its speed.

Median over seeds; each cell's range in brackets. Throughput is output tokens per second over the whole run.

What each engine did that a benchmark sheet would not tell you

  • llama.cpp (llama-server): continuous batching across slots, and a new prompt is processed in the same step as other users' decode tokens, which is why their token gaps spike when someone joins (the animation above). Prompt caching is on by default and keeps up to 8 GiB of old prompts in host memory. Speculative decoding needs --spec-type draft-simple as well as -md: with only -md the draft model was loaded and never used (default spec type none in 0.5.0).
  • MLX (mlx_lm.server): batches continuously (up to 32 decoding and 8 prefilling requests by default), but it is a Python HTTP server that says it is not meant for production. Under overload (Poisson arrivals at 3 requests/s and above, past its capacity of about 1.5 to 2) its memory footprint grew to 12 GB within minutes, the machine began swapping, and its generation thread died with a Metal out-of-memory error, in both attempts. With 16 simultaneous connections a few were reset (the listen queue holds 5); the load generator retried them and counted the wait.
  • vLLM on CPU: the official arm64 CPU image (v0.31.0) started and served correctly, but bfloat16 matrix multiplies fell back to a slow path on this CPU (no BF16 instructions on the M1), so it ran in float32. With 2 GiB reserved for KV (VLLM_CPU_KVCACHE_SPACE=2) it reported room for tokens (4-byte KV: bytes per token). With 16 users of about 540 tokens each that pool ran out: the engine's log showed KV usage up to % with requests waiting, its metrics counted preemptions (a running request evicted and later recomputed), and throughput fell from tokens/s at 8 users to at 16. That is the KV cache acting as the scarce resource, measured. Its scheduler, block manager and prefix cache are the same code as on a GPU; only the kernels differ.
  • SGLang: not run here. Its CPU backend is "enabled and optimized on the CPUs equipped with Intel AMX instructions" (SGLang docs, CPU servers, v0.5.21) and its prebuilt CPU images (tags ending in -xeon) are x86-64 only (Docker Hub, checked ); an arm64 Dockerfile exists that builds from source, which was not attempted on this shared laptop. TensorRT-LLM needs an NVIDIA GPU.

Every run, with its exact command

Model paths are written as <models>/. Load is the one-minute load average of the 10-core machine at the start (and end) of the run. Raw results, the load generator and the scripts are in src/bench/.

How the measurements were made, and their limits
  • Repeats and spread. llama-bench repeats each test 5 times (3 for sweeps) and reports mean and standard deviation; MLX trials are 3 to 5; load tests use 2 to 3 seeds. Charts show the spread as a bar from minimum to maximum.
  • Machine load. The laptop ran other jobs at the same time (other agents, a browser, an IDE). The one-minute load average at the start of runs ranged from to ; the GPU had no other measured user while a run held the bench lock, but GPU use by other processes cannot be ruled out.
  • Load generator. Python standard library, one thread per in-flight request, streaming SSE; TTFT is measured from sending the request to the first text chunk; TPOT is (last token time minus first token time) divided by (tokens minus 1). Prompts are random common English words plus a unique tag; every request asks for 128 tokens at temperature 0 (llama.cpp and vLLM with ignore_eos; MLX has no such option but produced all 128 tokens in every run).
  • Small quality checks. Perplexity on about 15,000 tokens and KL divergence on about 5,000 are enough to rank quantizations of one model, not to compare models.
  • Not a GPU benchmark. Absolute numbers describe one laptop. MLPerf Inference and the engines' own published numbers, labelled vendor or independent, are on the {{Capacity planner|#t-plan}} tab.
