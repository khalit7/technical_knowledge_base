KV cache memory against context

For every token in every sequence, each layer keeps that token's key and value vectors (the KV cache) so later tokens can attend to it without recomputing it. Its size per token is fixed by the model's shape: 2 (K and V) × layers × KV heads × head size × bytes per number. For Qwen3-0.6B (28 layers, 8 KV heads of 128 numbers, from its config.json) at 16 bits that is bytes, which llama.cpp's allocation matches exactly. The {{Memory technology|n:3f05c17b0d0d818ab063e327e3d7009f}} page covers where these bytes live physically.

Dots: the KV buffer llama-server allocated at start-up (Qwen3-0.6B, one sequence, context 4,096, 16,384 and 40,960, KV types f16, q8_0, q4_0). Lines: the formula. q8_0 stores 8.5 bits per number and q4_0 4.5 (a 16-bit scale per block of 32), hence 0.53x and 0.28x of f16. The sliders turn bytes into the number of sequences that fit, which is what limits a server's batch size: memory, not compute, usually caps concurrency.

Quantization: speed and quality

Quantization stores weights in fewer bits (8, or about 5 on average for Q4_K_M, instead of 16). Decode reads every weight once per token, so fewer bytes means faster decode; prefill is limited by arithmetic, so it gains little or even loses to the unpacking work. Quality falls as bits fall, and falls faster on small models. The {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}} page owns the formats and the maths; here are the measured trade-offs.

Speculative decoding: a draft model guesses, the big model checks

Decode wastes most of the hardware on one token per step. Speculative decoding lets a small draft model guess the next k tokens cheaply, then the big target model checks all k in one batched step and keeps the longest correct prefix plus one token of its own. The output is exactly what the target alone would produce (at temperature 0, the same text); only the speed changes. It pays when checking k tokens costs about the same as producing one, and when the draft guesses well.

Prefix caching: a shared system prompt is read once

Chat assistants send the same long system prompt with every request, and multi-turn conversations resend the whole history. If the server keeps the KV cache of a prompt it has already read, a new request that starts with the same tokens skips straight to the part that differs. llama-server keeps each slot's last prompt (and, by default, up to 8 GiB of older prompts in host memory); vLLM and SGLang keep cached blocks in a hash table or a radix tree (see the {{Reading|#t-read}} tab).
