1. One request: prefill, then decode

A language model returns a probability for every token in its vocabulary (128,256 for Llama 3.1) being the next one. To answer, the server calls it, picks one token (the sampler, {{Sampling and decoding|n:3c65c17b0d0d8115bafcda29a2c7086e}}), appends it and calls it again: autoregressive decoding, one token at a time, each depending on the last. Prefill reads all 2,000 prompt tokens through all 80 layers in one pass and stores every token's key and value vectors (the KV cache); decode then feeds only the newest token, which attends to the cache and adds its own entry. Before prefill the server wraps the messages in the model's chat template and splits them into token ids on the CPU, and the request may queue for a seat in the batch and memory for its cache (section 5). 2. Why decode is slow: three regimes

A GPU has two budgets: arithmetic per second and bytes read from memory per second. One H200 does 1,979 trillion FP8 operations per second but reads only 4.8 TB/s, so it can do 412 operations in the time it reads one byte 1,979 / 4.8. Work below that ratio (its arithmetic intensity) is memory-bound; above it, compute-bound (the roofline: {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}). Each weight does one multiply and one add per token. A decode step has one token per user, so the chip reads all 72.66 GB of weights for 2 operations per byte: the arithmetic idles more than 99% of the time and the step lasts as long as the read, 21.6 ms. Prefill shares one read among 2,000 tokens, 3,956 operations per byte: compute-bound, 423.5 ms, about 0.2 ms per token, a hundred times cheaper per token than decoding.

Predict: a new GPU has twice the H200's arithmetic speed and the same memory bandwidth. How much faster does one user's answer stream on it?
Hardly at all. The 21.6 ms decode step is 19.1 ms of reading weights and cache (73.4 GB at 0.8 of 4.8 TB/s) plus 2.5 ms of fixed overhead; the arithmetic takes about 0.2 ms and was already hidden behind the read. Prefill, which is compute-bound, would get almost twice as fast, so time to first token improves while streaming speed does not. This is why inference chips are judged on bandwidth and memory size at least as much as on FLOP/s.

The split shows on any hardware: on the laptop measured here, Qwen3-0.6B reads a 512-token prompt at 3,240 tokens per second and generates at 196, 17 times slower measured here ({{Engine bench|#t-bench}}). The ratio is larger on a datacenter GPU because arithmetic has grown faster than bandwidth: the M1 Pro does about 30 operations per byte read (5.0 TFLOP/s over 165 GB/s, measured on Topic: hardware), the H200 412.

Name the regime before choosing a fix. The third is easy to miss: on the laptop the fixed cost was 2.18 ms of a 5 ms Qwen3-0.6B step measured here, and the planner charges 2.5 ms per H200 step; fewer bytes do not help there. To check where you are, measure prompt-processing and generation speed separately (llama-bench reports pp and tg; vLLM's benchmark reports TTFT and TPOT); if single-stream tokens per second times bytes read per token is close to the memory bandwidth, decode is at its roofline (on this M1 Pro, rated 200 GB/s, plain decode of Qwen3-1.7B in F16 reached 187 GB/s, {{Local and on-device inference|n:3c65c17b0d0d81f7a144fe25d799e811}}, section 1) and only fewer bytes or more users per read will help.

Megakernels and on-chip memory: published batch-1 figures (vendor, dated)
Cohere reports 292 tokens per second at batch 1 on an H100 with a whole decode step fused into one kernel, 62% of the hardware's speed-of-light limit and 1.58 times vLLM ({{Cohere, 2026-09-08|https://cohere.com/blog/megakernels}}); Inferact's TPU v7 megakernels 1.4 to 2 times a GB200 baseline at batch 1 to 8 ({{Inferact, 2026-09-23|https://inferact.ai/blog/tpu-megakernels}}). The hardware answer keeps the weights in on-chip SRAM: Cerebras serves Qwen3.8-27B at about 1,800 tokens per second for one stream ({{AlphaSignal, 2026-09-11|https://alphasignal.ai/news/cerebras-runs-alibaba-s-qwen-3-8-27b-at-1-850-tokens-per-second}}). The Engine bench's 147 GB/s is a different number from the 187 above: a line fitted to a 0.6B model as its context grows.
