1. One request, from zero

What the model computes. A language model is a function: give it a sequence of tokens and it returns a probability for every token in its vocabulary (128,256 of them for Llama 3.1) being the next one. To write an answer, the server calls it, picks one token from those probabilities (greedy, temperature, top-p: {{Sampling and Decoding|n:3c65c17b0d0d8115bafcda29a2c7086e}}), appends it, and calls it again. Generating one token at a time, each depending on the last, is called autoregressive decoding, and it is the root of every problem on this page.

The steps a server runs, in the order the animation above showed them:

  1. Tokenize. The messages are wrapped in the model's chat template and split into token ids, on the CPU.
  2. Queue. It waits for a place in the next batch and memory for its cache (sections 3 and 4).
  3. Prefill (also called prompt processing). All 2,000 prompt tokens go through all 80 layers in one pass. Inside each layer's attention, every token produces a key and a value vector (what later tokens look up, and what they read when they find it). These are kept: that store is the KV cache. Prefill ends with the probabilities for the first answer token.
  4. Decode, once per answer token. Only the newest token goes through the model. It attends to every cached key and value, adds its own, and produces the next probabilities. Without the cache, every step would recompute all earlier tokens; with it, each step does the work of one token, but must read the whole cache.
  5. Detokenize and stream. Each token is turned back into text and sent at once, usually as server-sent events ({{Streaming and real-time|n:3c65c17b0d0d812daa9fdb38719fc82b}}). The request ends at an end-of-sequence token or the max_tokens limit, and its cache is freed.

Why decode is slow: the weights are read for one token

A GPU has two budgets: how many arithmetic operations it can do per second (FLOP/s) and how many bytes it can read from its memory per second. One H200 does 1,979 trillion FP8 operations per second but reads only 4.8 TB/s, so it can do 412 operations in the time it reads one byte 1,979 / 4.8. A piece of work is memory-bound when it does fewer operations per byte read than that (its arithmetic intensity is below the chip's ridge point) and compute-bound when it does more (the roofline model: {{Topic: hardware|n:3c65c17b0d0d8118beeefaed56da6f8e}}; the counting: {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}).

Each weight is used for one multiply and one add per token. In a decode step there is one token, so the chip reads all 72.66 GB of weights to do 2 operations per byte: the arithmetic units are idle more than 99% of the time and the step lasts as long as the read, 21.6 ms. In prefill, 2,000 tokens share one read of the weights, which gives 3,956 operations per byte: compute-bound, 423.5 ms for all 2,000 tokens, about 0.2 ms per token, a hundred times cheaper per token than decoding. The same split shows up on any hardware. On the laptop measured here, Qwen3-0.6B reads a 512-token prompt at 3,240 tokens per second and generates at 196, 17 times slower, with the same weights on the same chip measured here ({{Engine bench|#t-bench}}). The ratio is larger on a datacenter GPU because its arithmetic has grown faster than its bandwidth: the M1 Pro does about 30 operations per byte read (5.0 TFLOP/s over 165 GB/s, measured on Topic: hardware), the H200 412.

Predict: a new GPU has twice the H200's arithmetic speed and the same memory bandwidth. How much faster does one user's answer stream on it (the running example)?
Hardly at all. The 21.6 ms decode step is 19.1 ms of reading weights and cache (73.4 GB at 0.8 of 4.8 TB/s) plus 2.5 ms of fixed overhead; the arithmetic takes about 0.2 ms of it and was already hidden behind the read. The prefill, which is compute-bound, would get almost twice as fast, so time to first token improves while streaming speed does not. This is why inference chips are judged on bandwidth and memory size at least as much as on FLOP/s.

A third regime: one user, small steps, overhead

So a request is stuck in one of three places, and naming which comes before choosing a fix: prefill is compute-bound, decode is bandwidth-bound, and decode at batch size 1 on a small or fast model is often bound by neither, but by the fixed cost of launching hundreds of kernels and scheduling each step. On the laptop measured here that fixed cost was 2.18 ms of a 5 ms Qwen3-0.6B step measured here; the planner charges 2.5 ms per H200 step. Fewer bytes do not help there; fewer launches do. A decode megakernel fuses the whole step into one kernel: Cohere reports 292 tokens per second at batch 1 on an H100, 62% of the hardware's speed-of-light limit and 1.58 times vLLM ({{Cohere, 2026-09-08|https://cohere.com/blog/megakernels}}, vendor), and Inferact's TPU v7 megakernels 1.4 to 2 times a GB200 baseline at batch 1 to 8 ({{Inferact, 2026-09-23|https://inferact.ai/blog/tpu-megakernels}}, vendor). The hardware answer keeps the weights in on-chip SRAM: Cerebras serves Qwen3.8-27B at about 1,800 tokens per second for one stream ({{AlphaSignal, 2026-09-11|https://alphasignal.ai/news/cerebras-runs-alibaba-s-qwen-3-8-27b-at-1-850-tokens-per-second}}, vendor figure).

What it costs, when it matters, how to check
  • Cost: a decode step costs a full read of the weights plus the cache, whatever the batch; prefill costs arithmetic in proportion to prompt length (plus attention, which grows with the square of it).
  • When it matters: long prompts and short answers (retrieval, classification, summarization) are prefill-heavy and compute-bound; chat and reasoning with long answers are decode-heavy and memory-bound. The two phases want different hardware and different tuning (section 7 splits them onto different GPUs).
  • How to check: measure prompt-processing and generation speed separately (llama-bench reports pp and tg; vLLM's benchmark reports TTFT and TPOT). If single-stream tokens per second times bytes read per token is close to the memory bandwidth, decode is at its roofline and only fewer bytes (quantization, section 6) or more users per read (batching, section 3) will help.
