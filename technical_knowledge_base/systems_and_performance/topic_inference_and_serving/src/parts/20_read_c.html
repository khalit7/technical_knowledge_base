2. The KV cache: the resource that runs out

How big it is. Every token of every active conversation keeps one key and one value vector in every layer. Per token:

KV bytes per token = 2 × layers × KV heads × head size × bytes per number
2
one key and one value
KV heads
the number of key/value heads; with grouped-query attention (GQA) several query heads share one, which is why Llama 3.1 70B has 64 query heads but only 8 KV heads
bytes
2 for FP16/BF16, 1 for an FP8 cache

For Llama 3.1 70B that is 2 × 80 × 8 × 128 × 2 = 327,680 bytes, 320 KiB per token, so one 2,300-token conversation of the running example holds 719 MiB 2,300 × 320 KiB. The formula is checked against a real engine: for Qwen3-0.6B it gives 114,688 bytes, exactly what llama.cpp allocated measured here (448 MiB at 4,096 tokens, {{Engine bench|#t-bench}}).

Why it limits concurrency. GPU memory holds the weights, a working area for activations, and the cache. On one H200 with FP8 weights, vLLM's default 92% of 141 GB leaves about 54 GB for the cache after 72.66 GB of weights and activations, room for 141 conversations of the running example (with the shared system prompt stored once) {{Capacity planner|#t-plan}}, section 1. The 142nd user waits. Section 3 shows that more users per step means more throughput, so the cache size is, quite directly, the throughput ceiling. Model design moves it a lot: GQA cut Llama's cache 8 times against full multi-head attention, and DeepSeek's multi-head latent attention (MLA) stores one compressed 576-number vector per layer, so the 671B DeepSeek-V3 needs less per token than the 8B Llama:

Paging: allocate the cache in blocks, not slabs

Nobody knows in advance how long an answer will be. Early servers reserved one contiguous slab per request sized for its maximum length, so most of it sat empty, and gaps between slabs of different sizes could not be used. Kwon et al. measured that in such systems only 20.4% to 38.2% of the KV memory held actual tokens ({{PagedAttention, Fig. 2|https://arxiv.org/abs/2309.06180}}). PagedAttention borrows virtual memory from operating systems: the cache is cut into fixed-size blocks (16 tokens by default in vLLM v0.31.0, {{config/cache.py|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/cache.py}}), each request has a block table mapping its token positions to blocks anywhere in memory, and a block is taken only when the previous one is full. Waste falls to at most one partly filled block per request; the authors report 2 to 4 times the throughput of FasterTransformer and Orca at the same latency (their measurement, 2023). Every major engine now pages its cache. The {{Serving simulator|#t-sim}} animates contiguous against paged allocation on the same 20 requests (its section 1); the {{PagedAttention paper page|n:3c65c17b0d0d81bf8b90ca93fee19f5f}} has the details.

Prefix caching: never compute the same prompt twice

Every request of the running example starts with the same 1,000-token system prompt, and every turn of a conversation resends the whole history. Their keys and values are identical each time, so an engine can keep them and skip that part of the prefill. vLLM names each full block by a hash of its tokens and of the previous block's hash ({{hash_block_tokens, kv_cache_utils.py line 684|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/kv_cache_utils.py#L684}}), so equal hashes mean an equal prefix up to that block; prefix caching is on by default (cache.py line 142). Blocks shared by several requests carry a reference count; when no request uses a cached block it stays in memory and is evicted least recently used only when space is needed. SGLang keeps the same information as a radix tree of token sequences (RadixAttention, {{Zheng et al. 2023|https://arxiv.org/abs/2312.07104}}) and evicts leaves no running request holds ({{radix_cache.py line 553|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L553}}). llama.cpp's server keeps each slot's last prompt and, by default, up to 8 GiB of older prompts in host memory.

Measured here, a 1,500-word shared prefix cut llama.cpp's time to first token from 1,426 ms to 77 ms (19 times) on Qwen3-1.7B, and vLLM's CPU backend went from about 6.7 s to under 1 s measured here ({{Engine bench|#t-bench}}, section "Prefix caching").

When the pool is full, the engine first evicts cached blocks nobody is using, then stops admitting requests, then preempts a running one (section 4). Three ways to fit more: store the cache in FP8 (half the bytes; llama.cpp's 8-bit cache measured 60,928 bytes per token against 114,688), offload cold blocks to CPU memory or SSD and bring them back on a hit (LMCache, Mooncake's store, llm-d's tiered cache), or pick a model with a smaller cache (GQA, MLA, sliding windows).
