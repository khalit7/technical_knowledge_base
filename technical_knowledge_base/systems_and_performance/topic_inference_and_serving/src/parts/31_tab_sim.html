Serving simulator

A serving engine is a loop. Every iteration (a step) it picks which requests run, how many of their tokens to compute, and where their KV cache lives; the GPU then runs one forward pass over that batch. This tab is that loop, written out so you can switch each mechanism off and watch what it was for, on the same requests.

What is real here: the scheduling decisions in the continuous-batching, paged mode are the same as vLLM v0.31.0's own scheduler, step for step, on every trace we compared (checked below). The time each step takes comes from a roofline model (the larger of compute time and memory time, plus overheads) whose four efficiency numbers were fitted to NVIDIA's published NIM measurements for Llama 3.1 8B on one H100, then checked on rows of that table not used in the fit. The M1 Pro preset is calibrated on llama.cpp runs made on this machine. Everything else (static batching, contiguous allocation, swap, disaggregation) follows the published designs and is labelled illustrative where no engine was checked.

Words used on this tab
Prefill: processing the whole prompt in one pass, which writes its KV cache and yields the first output token. Decode: one pass per further output token. TTFT (time to first token): arrival to first token. TPOT (time per output token) and ITL (inter-token latency): the gap between later tokens, averaged per request or per gap. Goodput: requests per second that meet both latency targets (an SLO, service-level objective). Block: a fixed-size page of KV cache (16 tokens by default in vLLM). Preemption: evicting a running request's KV cache to make room, then recomputing it (or copying it back) later.

Why the shapes differ. Static batching (FasterTransformer-era servers, a plain generate() loop) takes a batch, pads every prompt to the longest, and decodes until the longest answer ends: finished rows sit idle and new requests wait for the whole batch. Continuous batching (Orca's iteration-level scheduling, {{Yu et al., OSDI 2022|https://www.usenix.org/conference/osdi22/presentation/yu}}) re-forms the batch every step, so a finished request leaves and a waiting one joins at once. Contiguous memory reserves prompt plus max_tokens for each request up front in one piece; most of the reservation is never used, and the gaps left between pieces may be too small for the next request. Paged memory (PagedAttention, {{Kwon et al., SOSP 2023|n:3c65c17b0d0d81bf8b90ca93fee19f5f}}) hands out 16-token blocks as tokens are produced, so the only waste is the unfilled tail of each request's last block.

3. A long prompt arrives while others are talking: chunked prefill

Eight users are mid-answer, each getting a token every few milliseconds. Then one user pastes a 12,000-token document. Without chunking, the engine computes that whole prompt in one step and the eight answers freeze until it is done. With chunked prefill (Sarathi-Serve, {{Agrawal et al., OSDI 2024|https://arxiv.org/abs/2403.02310}}; on by default in vLLM v1), the prompt is cut into pieces that fit the per-step token budget and each piece rides along with the eight decodes.

4. Where it bends: latency against load

Raise the arrival rate and throughput climbs, then flattens; latency stays flat, then shoots up. The knee is where the engine runs out of room: a step can carry more decodes almost for free while it is memory-bound (weights are read once per step whatever the batch), but once the KV cache or the compute is full, extra requests can only wait. 5. Is the simulator right? Three checks

Check 1: the scheduler is vLLM's. We ran vLLM's real Scheduler and KVCacheManager (v0.31.0, commit db9527a, Python only, no GPU: a stand-in model runner returns one token per finished prefill or decode) on the traces below, and compared every step with this page's simulator: which requests run, how many tokens each computes, which are preempted. Two details had to match vLLM exactly for that: a new request is admitted only if its whole prompt fits in free blocks (scheduler_reserve_full_isl, default on), and freed blocks without cached content go to the front of the free queue while cached ones go to the back, so prefix-cache entries are evicted least recently used first (block_pool.py, free_blocks). checked against the engine's code

Check 2: the step time on an H100. NVIDIA publishes TTFT, inter-token latency and throughput for Llama 3.1 8B Instruct on one H100 in FP8 at five prompt and answer lengths and eight concurrency levels (NIM 1.8.0, measured with genai-perf in closed loop: each of C clients sends its next request when the last one ends) vendor. 6. The step-time model, and what it leaves out

tstep = t0 + s · B + max( F / (ec · peak) , bytes / (em · bandwidth) )
F
2 × (parameters without the output layer) × tokens in the step, plus 2 × output-layer parameters per sequence (logits only for each sequence's last position), plus attention 4 × layers × query heads × head size × context, summed over new tokens
bytes
all weights once per step, plus each scheduled sequence's KV cache (read, and the new tokens written)
B
sequences in the step; t0 and s are fixed costs per step and per sequence (launches, sampling, scheduling, streaming)
ec, em
fitted efficiencies: the share of peak compute and of peak bandwidth the engine reaches

The same roofline as the {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}} page's serving planner (bytes over bandwidth against FLOPs over peak, the larger wins), applied to each mixed step instead of a pure decode batch, and with overheads that this page fits instead of assuming. Peaks come from the vendors (H100 SXM: 989.5 TFLOP/s BF16 and 1,979 FP8 dense, 3.35 TB/s; M1 Pro: 5.3 TFLOP/s by Philip Turner's count, 200 GB/s).

Not modelled
CUDA graphs and their batch-size buckets (steps padded to the next captured size); the CPU side running ahead of the GPU (vLLM v0.31.0 turns on async scheduling by default, which prepares the next step while the GPU runs the current one; the harness above used the synchronous Scheduler, and the time model has no CPU-GPU overlap); tokenization and network time except one fixed client latency in the H100 fit; tensor and pipeline parallelism (each GPU here is a whole replica); speculative decoding; sampling cost differences; KV-cache quantization accuracy; attention kernels that are not bandwidth-bound at long context. Static batching, contiguous allocation, swap and disaggregation follow their papers' designs and were not checked against a running engine illustrative.
What carries over from these numbers, and what does not
Carries over: the shapes. Decode steps cost about the same for 1 or 50 sequences until compute or KV reads catch up; static batching wastes the gap between the shortest and longest answer; contiguous reservation strands most of the cache; prefix caching removes the shared part of the prefill; chunking caps the stall a long prompt causes; latency turns up sharply once the cache is full. Does not carry over: absolute milliseconds, which depend on kernels, CUDA graphs, the engine version and the GPU; the M1 numbers in particular describe llama.cpp on a laptop GPU with 200 GB/s, about 1/17 of an H100's bandwidth.
