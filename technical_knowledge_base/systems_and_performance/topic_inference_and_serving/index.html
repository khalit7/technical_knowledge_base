Inference is running a trained model to get an answer. Serving is doing that for many people at once, over a network, fast enough that nobody waits too long, and cheaply enough to pay for. Training builds the model once; serving runs it millions of times, so for most deployed models serving is where the hardware bill goes. This page teaches it from zero by following one chat request through a serving engine, then a thousand of them.

The running example. A chat assistant built on Llama 3.1 70B (70.6 billion parameters, 80 layers; config.json, an open mirror of Meta's gated repository), stored in FP8 (one byte per weight) on NVIDIA H200 GPUs (141 GB of memory at 4.8 TB/s, NVIDIA). Every request carries a 2,000-token prompt whose first 1,000 tokens are the same system prompt, and gets a 300-token answer. It is the same deployment the Capacity planner opens with, so every number here can be checked there. A token is the unit the model reads and writes, a word or a piece of one (about three quarters of an English word on average).

1. One request, from zero

What the model computes. A language model is a function: give it a sequence of tokens and it returns a probability for every token in its vocabulary (128,256 of them for Llama 3.1) being the next one. To write an answer, the server calls it, picks one token from those probabilities (greedy, temperature, top-p: Sampling and Decoding), appends it, and calls it again. Generating one token at a time, each depending on the last, is called autoregressive decoding, and it is the root of every problem on this page.

The steps a server runs, in the order the animation above showed them:

  1. Tokenize. The chat messages are wrapped in the model's chat template (special tokens marking system, user and assistant turns) and split into token ids. This runs on the CPU and takes microseconds to milliseconds.
  2. Queue. The request waits until the engine has room for it: a place in the next batch and memory for its cache (sections 3 and 4).
  3. Prefill (also called prompt processing). All 2,000 prompt tokens go through all 80 layers in one pass. Inside each layer's attention, every token produces a key and a value vector (what later tokens look up, and what they read when they find it). These are kept: that store is the KV cache. Prefill ends with the probabilities for the first answer token.
  4. Decode, once per answer token. Only the newest token goes through the model. Its query is compared with every cached key, it reads the cached values, adds its own key and value to the cache, and produces the next probabilities. Without the cache, every step would recompute all earlier tokens; with it, each step does the work of one token, but must read the whole cache.
  5. Detokenize and stream. Each token is turned back into text (carefully: one character can span two tokens) and sent as soon as it exists, usually as server-sent events (Streaming and real-time). The request ends at an end-of-sequence token or the max_tokens limit, and its cache is freed.

Why decode is slow: the weights are read for one token

A GPU has two budgets: how many arithmetic operations it can do per second (FLOP/s) and how many bytes it can read from its memory per second. One H200 does 1,979 trillion FP8 operations per second but reads only 4.8 TB/s, so it can do 412 operations in the time it reads one byte 1,979 / 4.8. A piece of work is memory-bound when it does fewer operations per byte read than that (its arithmetic intensity is below the chip's ridge point) and compute-bound when it does more (the roofline model: Topic: hardware; the counting: Performance math).

Each weight is used for one multiply and one add per token. In a decode step there is one token, so the chip reads all 72.66 GB of weights to do 2 operations per byte: the arithmetic units are idle more than 99% of the time and the step lasts as long as the read, 21.6 ms. In prefill, 2,000 tokens share one read of the weights, which gives 3,956 operations per byte: compute-bound, 423.5 ms for all 2,000 tokens, about 0.2 ms per token, a hundred times cheaper per token than decoding. Predict: a new GPU has twice the H200's arithmetic speed and the same memory bandwidth. How much faster does one user's answer stream on it (the running example)?
Hardly at all. The 21.6 ms decode step is 19.1 ms of reading weights and cache (73.4 GB at 0.8 of 4.8 TB/s) plus 2.5 ms of fixed overhead; the arithmetic takes about 0.2 ms of it and was already hidden behind the read. The prefill, which is compute-bound, would get almost twice as fast, so time to first token improves while streaming speed does not. This is why inference chips are judged on bandwidth and memory size at least as much as on FLOP/s.
What it costs, when it matters, how to check
  • Cost: a decode step costs a full read of the weights plus the cache, whatever the batch; prefill costs arithmetic in proportion to prompt length (plus attention, which grows with the square of it).
  • When it matters: long prompts and short answers (retrieval, classification, summarization) are prefill-heavy and compute-bound; chat and reasoning with long answers are decode-heavy and memory-bound. The two phases want different hardware and different tuning (section 7 splits them onto different GPUs).
  • How to check: measure prompt-processing and generation speed separately (llama-bench reports pp and tg; vLLM's benchmark reports TTFT and TPOT). If single-stream tokens per second times bytes read per token is close to the memory bandwidth, decode is at its roofline and only fewer bytes (quantization, section 6) or more users per read (batching, section 3) will help.

2. The KV cache: the resource that runs out

How big it is. Every token of every active conversation keeps one key and one value vector in every layer. Per token:

KV bytes per token = 2 × layers × KV heads × head size × bytes per number
2
one key and one value
KV heads
the number of key/value heads; with grouped-query attention (GQA) several query heads share one, which is why Llama 3.1 70B has 64 query heads but only 8 KV heads
bytes
2 for FP16/BF16, 1 for an FP8 cache

For Llama 3.1 70B that is 2 × 80 × 8 × 128 × 2 = 327,680 bytes, 320 KiB per token, so one 2,300-token conversation of the running example holds 719 MiB 2,300 × 320 KiB. The formula is checked against a real engine: for Qwen3-0.6B it gives 114,688 bytes, exactly what llama.cpp allocated measured here (448 MiB at 4,096 tokens, Engine bench).

Why it limits concurrency. GPU memory holds the weights, a working area for activations, and the cache. On one H200 with FP8 weights, vLLM's default 92% of 141 GB leaves about 54 GB for the cache after 72.66 GB of weights and activations, room for 141 conversations of the running example (with the shared system prompt stored once) Capacity planner, section 1. The 142nd user waits. Section 3 shows that more users per step means more throughput, so the cache size is, quite directly, the throughput ceiling. Model design moves it a lot: GQA cut Llama's cache 8 times against full multi-head attention, and DeepSeek's multi-head latent attention (MLA) stores one compressed 576-number vector per layer, so the 671B DeepSeek-V3 needs less per token than the 8B Llama:

Paging: allocate the cache in blocks, not slabs

Nobody knows in advance how long an answer will be. Early servers reserved one contiguous slab per request sized for its maximum length, so most of it sat empty, and gaps between slabs of different sizes could not be used. Kwon et al. measured that in such systems only 20.4% to 38.2% of the KV memory held actual tokens (PagedAttention, Fig. 2). PagedAttention borrows virtual memory from operating systems: the cache is cut into fixed-size blocks (16 tokens by default in vLLM v0.31.0, config/cache.py), each request has a block table mapping its token positions to blocks anywhere in memory, and a block is taken only when the previous one is full. Waste falls to at most one partly filled block per request; the authors report 2 to 4 times the throughput of FasterTransformer and Orca at the same latency (their measurement, 2023). Every major engine now pages its cache. The Serving simulator animates contiguous against paged allocation on the same 20 requests (its section 1); the PagedAttention paper page has the details.

Prefix caching: never compute the same prompt twice

Every request of the running example starts with the same 1,000-token system prompt, and every turn of a conversation resends the whole history. Their keys and values are identical each time, so an engine can keep them and skip that part of the prefill. vLLM names each full block by a hash of its tokens and of the previous block's hash (hash_block_tokens, kv_cache_utils.py line 684), so equal hashes mean an equal prefix up to that block; prefix caching is on by default (cache.py line 142). Blocks shared by several requests carry a reference count; when no request uses a cached block it stays in memory and is evicted least recently used only when space is needed. SGLang keeps the same information as a radix tree of token sequences (RadixAttention, Zheng et al. 2023) and evicts leaves no running request holds (radix_cache.py line 553). llama.cpp's server keeps each slot's last prompt and, by default, up to 8 GiB of older prompts in host memory.

When the pool is full, the engine first evicts cached blocks nobody is using, then stops admitting requests, then preempts a running one (section 4). Three ways to fit more: store the cache in FP8 (half the bytes; llama.cpp's 8-bit cache measured 60,928 bytes per token against 114,688), offload cold blocks to CPU memory or SSD and bring them back on a hit (LMCache, Mooncake's store, llm-d's tiered cache), or pick a model with a smaller cache (GQA, MLA, sliding windows).

3. Batching: one read of the weights, many users served

The problem. A decode step reads 72.66 GB of weights to produce one token for one user, and the arithmetic units sit idle. The idea: let many users' next tokens ride on the same read. The weights are read once per step whatever the batch; each extra user adds only the bytes of its own cache and a little arithmetic. So the step barely slows while the tokens per step multiply:

measured here: llama-batched-bench, Qwen3-0.6B Q4_K_M on the M1 Pro GPU (Engine bench, section "Batching"). Here each extra sequence costs about 1.2 ms per step on top of the weight read, so 64 sequences give 7 times the throughput of one, not 64; on the H200 model, 64 users give 42 times.

Throughput climbs almost linearly while the step is dominated by the weight read, then bends as each user's cache read and arithmetic add up; each user's own speed falls as the step lengthens. That trade, more throughput for the owner against slower tokens for each user, is the central dial of serving.

Static, dynamic and continuous batching

StaticCollect a batch, run it until its longest answer finishes, then start the next. Users whose answers end early leave empty seats; new arrivals wait for the whole batch.
DynamicWait up to a time limit to fill a batch, then run it as a unit. Right for models that answer in one pass (classifiers, embeddings; NVIDIA Triton's dynamic batcher); for generation it keeps the static problem.
ContinuousDecide the batch again at every step. A finished request leaves immediately and a waiting one joins at the next step. Also called iteration-level scheduling or in-flight batching.

Continuous batching was introduced by Orca (Yu et al., OSDI 2022): the scheduler runs the model for one iteration at a time, and "selective batching" batches the matrix multiplications over all tokens of all requests while attention runs per request, since each request has its own cache. The authors reported 36.9 times the throughput of NVIDIA FasterTransformer at the same latency on GPT-3 175B (their measurement). It is why serving got so much cheaper in 2022 to 2023, and every engine on this page now does it by default (llama-server's "continuous batching on", TensorRT-LLM's "in-flight batching", vLLM's and SGLang's schedulers). The Serving simulator animates the same 20 requests under static and continuous batching in its section 1.

Predict: static batching versus continuous batching on chat traffic whose answers range from 10 to 1,000 tokens. Which suffers most under static batching?
Both. A static batch runs as long as its longest answer, so a 10-token answer holds its seat for 1,000 steps (throughput lost), and a request that arrives just after the batch starts waits for all of it before its first token (TTFT lost). A larger batch makes both worse: more seats empty, longer waits. Try it in the Serving simulator's lab.
What it costs, when it matters, how to check
  • Cost: every extra user lengthens every step a little (higher TPOT for all) and holds cache memory; past the knee, adding users adds latency without adding throughput.
  • When it matters: always for a shared server; not for a single local user, where batch size is one and only fewer bytes per token help.
  • How to check: sweep concurrency and plot throughput against TPOT and TTFT; the operating point is just before the knee. The Engine bench measured that curve on real engines (section "The throughput-latency curve").

4. Scheduling and SLOs: who goes next, and how fast is fast enough

A service level objective (SLO) is the latency promise a service tries to keep, usually written on a percentile: "99% of requests see their first token within 2 seconds" is a p99 TTFT target. Percentiles matter because a user who sends twenty messages will meet the slow tail; a mean hides it. The numbers worth knowing, all computed from the timestamps of each streamed token:

One real request shows why the definitions matter. Under 16 concurrent users on llama-server (Qwen3-0.6B, a 412-token prompt, 128 tokens out), it saw a TTFT of 0.96 s and a mean TPOT of 43.9 ms, yet its median gap was 31.4 ms and its longest 803 ms measured here (Engine bench, "One request alone, and the same request under load"). The mean is not the typical gap and not the worst one: the long gaps are steps where other users' prompts were being read. MLPerf's targets for Llama 3.1 8B are p99 TTFT 2 s and p99 TPOT 100 ms, and 0.5 s and 30 ms in its interactive scenario (MLPerf inference rules).

What the scheduler decides, every step

The scheduler builds each step's batch: which running requests decode, which waiting prompts start, and what to do when memory runs out. Four mechanisms, each a fix for a specific failure:

Admission and orderFirst come, first served by default (vLLM's policy "fcfs", config/scheduler.py line 160; "priority" is the alternative). vLLM admits a waiting request only when its whole prompt fits in free blocks; TensorRT-LLM's default (GUARANTEED_NO_EVICT) admits one only if its maximum length fits, so it never has to evict but runs fewer at once.
Chunked prefillA long prompt read in one step makes that step long, and every user's stream stalls (the 803 ms gap above). Cap the tokens per step and cut prompts into chunks; decodes go first and chunks fill the rest of the budget.
PreemptionAnswers grow, so a cache that fit at admission can run out. The engine evicts a running request: recompute (drop its cache, prefill it again later) or swap (copy its cache to CPU memory and back). vLLM v1 only recomputes, taking the most recently admitted request and putting it first in the queue.
Priorities and fairnessInteractive before batch jobs, short before long, one tenant not starving another. vLLM's priority policy, SGLang's longest-prefix-match policy, which runs first the requests with the most cached tokens (schedule_policy.py line 223), and admission limits per tenant in a gateway in front.

Chunked prefill comes from Sarathi (Agrawal et al. 2023) and Sarathi-Serve (OSDI 2024), whose authors report 2.6 times the serving capacity of vLLM at the time for Mistral-7B on one A100 under tail-latency targets. vLLM v0.31.0 turns it on by default (config/scheduler.py line 135) with a budget of 8,192 tokens per step for its API server on H100-class GPUs; TensorRT-LLM v1.2.1 leaves it off by default (llm_args.py line 2006). The budget is the dial: smaller chunks keep streams smooth but take more steps to finish a prompt (higher TTFT). The Serving simulator shows the stall and the fix on the same requests (section 3). Preemption, measured: vLLM's CPU backend with a 9,344-token cache reached 100% cache use and 8 preemptions at 16 users, and its output throughput fell from 26.5 to 15.6 tokens per second between 8 and 16 users measured here: work thrown away and redone.

How to check
  • Engines export these as Prometheus metrics (vLLM's /metrics: running and waiting requests, KV cache usage, preemptions, TTFT and ITL histograms). Waiting requests growing while cache usage sits near 100% means memory, not compute, is the limit.
  • Report percentiles (p50, p90, p99) of TTFT and ITL, never only means, and goodput at a stated SLO.

6. Making each token cheaper

Since decode is limited by bytes read, there are two ways to make a token cheaper: read fewer bytes per token (quantization), or get more than one token per read (speculative decoding). Kernels and graphs remove the overheads around both.

Quantization for serving: fewer bytes per weight

Quantization stores numbers in fewer bits (the formats and the maths are on Quantization and Precision). For serving, what matters is which numbers and what the hardware does with them:

Weight-only (INT4, INT8)Weights stored in 4 or 8 bits with a scale per small group, turned back into 16 bits inside the matrix kernel (AWQ, GPTQ, llama.cpp's GGUF k-quants). Decode reads 2 to 4 times fewer bytes, so it speeds up; prefill does the same 16-bit arithmetic plus unpacking, so it does not.
Weights and activations (FP8, FP4)Both sides of the matrix multiply in 8 bits (or 4 on Blackwell's NVFP4 and MXFP4), on tensor cores that run them twice (or four times) as fast as BF16. Faster decode and faster prefill; needs Hopper, Blackwell or MI300-class hardware.
KV cache (FP8, INT8, INT4)Halves (or quarters) the cache: more users per GPU and less to read at long context. Quality cost depends on the model; check it.

Measured here on Qwen3-0.6B (llama.cpp, M1 Pro GPU): generation went from 113 tokens per second at F16 to 140 at Q8_0 and 196 at Q4_K_M, while prompt processing fell from 3,618 to 3,240 at Q4_K_M; perplexity on WikiText-2 went from 20.88 (F16) to 20.86 (Q8_0) and 22.59 (Q4_K_M), and the most likely next token stayed the same as F16's 97.8% of the time at Q8_0 but 83.0% at Q4_K_M measured here (Engine bench, "Quantization: speed and quality"). Eight bits is close to free; four bits is a real trade, larger on small models like this one. AWQ (Lin et al. 2023) and GPTQ (Frantar et al. 2022) are the two common recipes for 4-bit weights.

Speculative decoding: guess several tokens, check them in one pass

A decode step at small batch leaves the arithmetic idle, so checking 5 tokens costs about the same as producing 1 (it is a tiny prefill). Speculative decoding uses that: a cheap draft proposes the next k tokens, the big target model scores all of them in one pass, keeps the longest run it agrees with, and adds one token of its own. A modified rejection-sampling rule keeps the output distribution exactly the target's (Leviathan et al. 2023, Chen et al. 2023). With acceptance rate a per token, each target pass yields (1 − ak+1) / (1 − a) tokens on average: 2.77 at a = 0.7 and k = 4.

The draft can be a small model of the same family, extra prediction heads on the target (Medusa: 2.2 to 3.6 times faster in its authors' tests, Cai et al. 2024), a light layer that predicts the target's own features (EAGLE: 2.7 to 3.5 times lower latency on LLaMA2-Chat 70B, Li et al. 2024), the model's own multi-token prediction heads (DeepSeek-V3), or no model at all: n-gram or prompt lookup, which copies a continuation that already appears in the prompt and works well for code edits and retrieval answers. vLLM v0.31.0 offers all of these (config/speculative.py).

It is not always faster, and not always byte-identical
It pays only when checking k tokens costs little more than producing one, and when the draft guesses well. At large batch the GPU is no longer idle, so verification is not free and the gain shrinks. On this laptop a Qwen3-4B pass over 4 tokens cost 2.2 times a pass over 1, so a 0.6B draft made llama.cpp slower on free text and at best 1.32 times faster on a highly predictable list prompt; MLX was slower at every k measured here. The output distribution is the target's in exact arithmetic, but in floating point a batched check can round a near-tie differently from one-at-a-time decoding: at k = 6, MLX's greedy output differed from its own baseline on two prompts (Engine bench, "Speculative decoding"). Test acceptance rate and speed on your own traffic and batch size.

Kernels and graphs: removing the overhead around the bytes

Three pieces of engineering every serious engine uses, each owned by another page: FlashAttention computes attention in on-chip memory without writing the full score matrix (paper page; split-KV decode kernels on Writing kernels); paged attention kernels read keys and values through the block table; CUDA graphs record a decode step's hundreds of small kernel launches once and replay them, removing launch overhead that otherwise dominates small batches (Streams, CUDA graphs and multi-GPU; compilers on Compiler stack).

7. More than one GPU

8. Three workloads that change the rules

Long context

The cache grows with every token: 128K tokens of Llama 3.1 70B are 40 GiB 131,072 × 320 KiB, four fifths of the roughly 54 GB an H200 has left for the cache after FP8 weights (section 2), for one conversation. Every decode step reads all of it, so tokens slow down as the context grows: measured here, Qwen3-0.6B went from 198 tokens per second with an empty context to 56 at 16,384 tokens, because the cache read became larger than the weight read measured here. Prefill attention grows with the square of the prompt, so a long prompt can hold a GPU for seconds. The levers: chunked prefill (so a long prompt does not stall everyone), an FP8 cache, offloading cold blocks, splitting one sequence across GPUs (context parallelism, ring attention), and models built for it (sliding-window layers as in gpt-oss, MLA as in DeepSeek). How well models actually use long contexts is on Long-context and multimodal benchmarks.

Structured output

To guarantee valid JSON (or any grammar), the engine masks the vocabulary at every step: tokens that would break the grammar get probability zero before sampling. The cost is computing that mask, on the CPU, every step for every constrained request, which once slowed decoding noticeably. XGrammar precomputes the mask for tokens whose validity does not depend on the parser's stack and reports up to 100 times faster mask generation than earlier engines and near-zero end-to-end overhead (Dong et al. 2024, the authors); vLLM uses xgrammar or guidance as back ends. A constraint can also push the model away from what it would have written, so check quality, not only validity.

Many fine-tuned variants: multi-LoRA

A LoRA adapter is a small low-rank change to a base model's weights, a few megabytes against the base's gigabytes. Serving a hundred customers' adapters as a hundred models would need a hundred copies; instead one base model serves them all in one batch, each request applying its own adapter through a batched kernel, with adapters paged in from CPU memory as needed. Punica reported 12 times the throughput of serving systems of the time with 2 ms added per token (Chen et al. 2023); S-LoRA, thousands of adapters on one GPU (Sheng et al. 2023); both the authors' measurements. vLLM, SGLang and TensorRT-LLM support it; a router that sends each adapter's traffic to the replicas that already hold it avoids reloading (llm-d's cache-aware LoRA routing).

9. Running it in production

Routing: send a conversation back to its cache

With several replicas, something in front must pick one for each request. A web load balancer's round-robin spreads the load evenly but ignores the cache: the second turn of a conversation lands on a replica that never saw the first, and its whole history is prefilled again. Prefix-aware routing (also called cache-aware or KV-aware) sends a request to the replica most likely to hold its prefix, weighed against how busy each replica is.

Autoscaling and cold starts

Scale on what the users feel and what runs out: queue length, KV cache usage, TTFT. Not on GPU utilization, which reads near 100% during memory-bound decode whether the server is comfortable or drowning. Adding a replica is slow: the weights must be fetched and loaded (72.66 GB for the running example, about 36 s at an assumed 2 GB/s from a local NVMe disk 72.66 GB / 2 GB/s, minutes from remote storage), then the engine profiles memory and captures CUDA graphs. Keep a minimum of warm replicas, cache weights on local disk, and scale ahead of known peaks. ServerlessLLM reports 10 to 200 times lower start-up latency from loading-optimised checkpoints on local storage (Fu et al. 2024, the authors).

Observability and benchmarking honestly

Watch per replica: running and waiting requests, KV cache usage, preemptions, prefix cache hit rate, TTFT and ITL histograms, tokens in and out. Most engines publish these at /metrics for Prometheus. When you benchmark, a number is only meaningful with its conditions:

  • Open-loop arrivals (Poisson, as MLPerf's Server scenario) for a service; a closed loop (N users who each wait for their answer) hides overload, because the users slow down with the server.
  • Real length distributions, not one fixed prompt and output length; state whether end-of-sequence was ignored to force lengths.
  • Prefix cache state: repeated identical prompts measure the cache, not the model.
  • Percentiles and goodput at a stated SLO, across a sweep of load to find the knee; warm-up excluded; several runs with their spread; exact versions, flags and hardware. The Engine bench records every run with its command line and the machine's load, because this laptop was shared.

Common mistakes

"It does 3,000 tokens per second."
Per user or for the whole server? Input, output or both? At what latency? The running example does 46 tokens per second for one user alone and 2,982 for the GPU at 141 users, with each of them then at 21. A throughput figure without its concurrency and its TPOT is not a capacity.
Sizing by the weights alone
"70B in BF16 fits on two H100s" is true and useless: what is left holds the cache of 2 conversations (section 7). Size by weights plus cache for the concurrency you need, plus activations and the engine's reserve.
Reading GPU utilization as load
nvidia-smi's utilization says a kernel was running, not how much of the chip it used; memory-bound decode shows near 100% while the arithmetic units idle. Watch queue length, KV cache usage, TTFT and ITL.
Means instead of percentiles
The measured request of section 4 had a mean TPOT of 43.9 ms and an 803 ms stall. Users notice the stalls. Report p50, p90 and p99 of TTFT and ITL, and goodput at a stated SLO.
Benchmarking with a closed loop, fixed lengths and a warm cache
N users who each wait for their answer slow down with the server and hide overload; identical prompts measure the prefix cache. Use open-loop (Poisson) arrivals at several rates, real length distributions, and say what was cached.
Comparing engines at their defaults
Defaults differ: llama-server picks 4 slots on its own, mlx_lm.server decodes 32 at once, vLLM's token budget per step depends on the GPU, TensorRT-LLM admits only what is guaranteed to fit. Set the same batch limits, cache size and precision before comparing.
"Speculative decoding is a free 2 to 3 times"
The published speed-ups are at batch 1 on GPUs where checking k tokens is nearly free. At large batch, or where verification costs more (2.2 times for 4 tokens on the laptop measured here), it can slow decoding down; and floating-point outputs can differ from plain decoding.
"4-bit is free" and "4-bit is faster"
Weight-only 4-bit speeds up decode (fewer bytes) but not prefill (same arithmetic, plus unpacking: 3,240 against 3,618 tokens per second measured here), and costs quality that grows as models shrink (perplexity 20.88 to 22.59 on Qwen3-0.6B). Measure on your task.
Round-robin in front of prefix caching
With N replicas, a returning conversation lands on a replica without its cache (N − 1) / N of the time, and its history is prefilled again. Route by prefix.

Interview questions, with short answers

Why is decode memory-bound and prefill compute-bound?
Each weight does 2 operations per token. Decode processes one token per sequence per step, so it reads every weight for about 2 operations per byte (in FP8); an H200 can do 412 operations per byte read. Prefill processes thousands of prompt tokens per read of the weights, far above 412. Batching moves decode up the same axis.
How much KV cache do 100 users at 4K context need on Llama 3.1 70B?
2 × 80 layers × 8 KV heads × 128 × 2 bytes = 320 KiB per token; × 4,096 × 100 = 125 GiB in BF16, more than one H200 has left after the weights; FP8 halves it. Then say what you would do: FP8 cache, TP 2, or fewer users per GPU.
What did continuous batching fix, and what did PagedAttention fix?
Continuous batching (Orca) re-forms the batch every step, so finished requests leave and new ones join at once, instead of waiting for the slowest answer. PagedAttention (vLLM) allocates the cache in small blocks through a block table instead of one slab per request for its maximum length, so far more requests fit, which is where the throughput comes from; it also makes prefix sharing natural.
TTFT is fine at low load but its p99 explodes at peak. Why, and what do you do?
Queueing: requests wait for cache room or for prefill budget. Check waiting requests, KV usage and preemptions. Fixes: more replicas or bigger cache (FP8 KV, TP), chunked prefill with a sensible token budget, prefix caching and prefix-aware routing, admission control that rejects early instead of timing out late.
TPOT is spiky. Why?
Steps that also carry someone's prefill. Chunked prefill caps it; disaggregating prefill and decode removes it.
When would you split prefill and decode onto different GPUs?
At scale, with strict TPOT targets and long prompts, when the two phases want different parallelism or hardware. The price is moving the cache (625 MiB per 2,000-token prompt of a 70B model) and running two pools. On a few GPUs, chunked prefill first.
When does speculative decoding not help?
At large batch (the GPU is no longer idle, so verification costs real time), with a poor draft (low acceptance), or where a k-token pass costs much more than a 1-token pass. Measure acceptance and speed at your batch size.

By prefix: hash the conversation's prefix (or ask the replicas what they hold) and send it where its cache lives, unless that replica is overloaded. Round-robin forces re-prefill.

Compute dollars per million tokens at your average utilization, not at peak throughput. APIs win at low or bursty volume; self-hosting at high steady volume, with heavy prefix reuse, custom models or data that cannot leave. Add the engineers' time.

A serving engine is a loop. Why the shapes differ. Static batching (FasterTransformer-era servers, a plain generate() loop) takes a batch, pads every prompt to the longest, and decodes until the longest answer ends: finished rows sit idle and new requests wait for the whole batch. Continuous batching (Orca's iteration-level scheduling, Yu et al., OSDI 2022) re-forms the batch every step, so a finished request leaves and a waiting one joins at once. Contiguous memory reserves prompt plus max_tokens for each request up front in one piece; most of the reservation is never used, and the gaps left between pieces may be too small for the next request. Paged memory (PagedAttention, Kwon et al., SOSP 2023) hands out 16-token blocks as tokens are produced, so the only waste is the unfilled tail of each request's last block.

3. A long prompt arrives while others are talking: chunked prefill

Eight users are mid-answer, each getting a token every few milliseconds. Then one user pastes a 12,000-token document. Peaks come from the vendors (H100 SXM: 989.5 TFLOP/s BF16 and 1,979 FP8 dense, 3.35 TB/s; M1 Pro: 5.3 TFLOP/s by Philip Turner's count, 200 GB/s).

Not modelled
CUDA graphs and their batch-size buckets (steps padded to the next captured size); the CPU side running ahead of the GPU (vLLM v0.31.0 turns on async scheduling by default, which prepares the next step while the GPU runs the current one; the harness above used the synchronous Scheduler, and the time model has no CPU-GPU overlap); tokenization and network time except one fixed client latency in the H100 fit; tensor and pipeline parallelism (each GPU here is a whole replica); speculative decoding; sampling cost differences; KV-cache quantization accuracy; attention kernels that are not bandwidth-bound at long context. Static batching, contiguous allocation, swap and disaggregation follow their papers' designs and were not checked against a running engine illustrative.
What carries over from these numbers, and what does not
Carries over: the shapes. Decode steps cost about the same for 1 or 50 sequences until compute or KV reads catch up; static batching wastes the gap between the shortest and longest answer; contiguous reservation strands most of the cache; prefix caching removes the shared part of the prefill; chunking caps the stall a long prompt causes; latency turns up sharply once the cache is full. Does not carry over: absolute milliseconds, which depend on kernels, CUDA graphs, the engine version and the GPU; the M1 numbers in particular describe llama.cpp on a laptop GPU with 200 GB/s, about 1/17 of an H100's bandwidth.

Prefill and decode are two different workloads

Prefill pushes the whole prompt through the model in one pass: hundreds of tokens share each read of the weights, so the GPU's arithmetic units are the limit (compute-bound). Decode produces one token per pass: every weight is read from memory to do a little arithmetic for a single token, so memory bandwidth is the limit (memory-bound). Batching: one read of the weights, many users served

Because decode is limited by reading the weights, decoding several sequences in the same step costs little more than decoding one: the weights are read once and applied to every sequence in the batch. Total throughput rises with batch size; each user's own speed falls a little. This is why serving engines batch, and why a server that is idle most of the time wastes most of what the hardware can do.

The throughput-latency curve, and where it bends

A real server has requests arriving at random times. This tab's load generator (src/bench/scripts/loadgen.py, standard library only) sends streamed completion requests in two ways. Closed loop: a fixed number of users, each sending a new request as soon as the last one finishes. Open loop: requests arrive as a Poisson process (independent random arrivals at a set average rate, fixed seed), which is how MLPerf's Server scenario and most production traffic behave. Every request has a 400-word prompt (about 410 tokens, with a unique tag so no prompt is cached) and asks for exactly 128 tokens.

Goodput under an SLO

A service level objective (SLO) sets the latency each request must meet, for example "first token within 1 s and at most 50 ms between tokens". Goodput counts only the requests that met it. Move the limits and watch which load level gives the most useful work: past the bend, raw throughput stays flat but goodput collapses.

KV cache memory against context

For every token in every sequence, each layer keeps that token's key and value vectors (the KV cache) so later tokens can attend to it without recomputing it. Its size per token is fixed by the model's shape: 2 (K and V) × layers × KV heads × head size × bytes per number. For Qwen3-0.6B (28 layers, 8 KV heads of 128 numbers, from its config.json) at 16 bits that is bytes, which llama.cpp's allocation matches exactly. The Memory technology page covers where these bytes live physically.

Dots: the KV buffer llama-server allocated at start-up (Qwen3-0.6B, one sequence, context 4,096, 16,384 and 40,960, KV types f16, q8_0, q4_0). Lines: the formula. q8_0 stores 8.5 bits per number and q4_0 4.5 (a 16-bit scale per block of 32), hence 0.53x and 0.28x of f16. The sliders turn bytes into the number of sequences that fit, which is what limits a server's batch size: memory, not compute, usually caps concurrency.

Quantization: speed and quality

Quantization stores weights in fewer bits (8, or about 5 on average for Q4_K_M, instead of 16). Decode reads every weight once per token, so fewer bytes means faster decode; prefill is limited by arithmetic, so it gains little or even loses to the unpacking work. Quality falls as bits fall, and falls faster on small models. The Quantization and Precision page owns the formats and the maths; here are the measured trade-offs.

Speculative decoding: a draft model guesses, the big model checks

Decode wastes most of the hardware on one token per step. Speculative decoding lets a small draft model guess the next k tokens cheaply, then the big target model checks all k in one batched step and keeps the longest correct prefix plus one token of its own. In exact arithmetic the output follows exactly the target's own distribution (at temperature 0, the same text); in real floating point a batched check can round differently, so text can occasionally differ (MLX did at k = 6, below). Mainly the speed changes. It pays when checking k tokens costs about the same as producing one, and when the draft guesses well.

Prefix caching: a shared system prompt is read once

Chat assistants send the same long system prompt with every request, and multi-turn conversations resend the whole history. If the server keeps the KV cache of a prompt it has already read, a new request that starts with the same tokens skips straight to the part that differs. llama-server keeps each slot's last prompt (and, by default, up to 8 GiB of older prompts in host memory); vLLM and SGLang keep cached blocks in a hash table or a radix tree (see the Reading tab).

What each engine did that a benchmark sheet would not tell you

  • llama.cpp (llama-server): continuous batching across slots, and a new prompt is processed in the same step as other users' decode tokens, which is why their token gaps spike when someone joins (the animation above). Prompt caching is on by default and keeps up to 8 GiB of old prompts in host memory. Speculative decoding needs --spec-type draft-simple as well as -md: with only -md the draft model was loaded and never used (default spec type none in 0.5.0).
  • MLX (mlx_lm.server): batches continuously (up to 32 decoding and 8 prefilling requests by default), but it is a Python HTTP server that says it is not meant for production. Under overload (Poisson arrivals at 3 requests/s and above, past its capacity of about 1.5 to 2) its memory footprint grew to 12 GB within minutes, the machine began swapping, and its generation thread died with a Metal out-of-memory error, in both attempts. With 16 simultaneous connections a few were reset (the listen queue holds 5); the load generator retried them and counted the wait.
  • vLLM on CPU: the official arm64 CPU image (v0.31.0) started and served correctly, but bfloat16 matrix multiplies fell back to a slow path on this CPU (no BF16 instructions on the M1), so it ran in float32. With 2 GiB reserved for KV (VLLM_CPU_KVCACHE_SPACE=2) it reported room for tokens (4-byte KV: bytes per token). With 16 users of about 540 tokens each that pool ran out: the engine's log showed KV usage up to % with requests waiting, its metrics counted preemptions (a running request evicted and later recomputed), and throughput fell from tokens/s at 8 users to at 16. That is the KV cache acting as the scarce resource, measured. Its scheduler, block manager and prefix cache are the same code as on a GPU; only the kernels differ.
  • SGLang: not run here. Its CPU backend is "enabled and optimized on the CPUs equipped with Intel AMX instructions" (SGLang docs, CPU servers, v0.5.21) and its prebuilt CPU images (tags ending in -xeon) are x86-64 only (Docker Hub, checked ); an arm64 Dockerfile exists that builds from source, which was not attempted on this shared laptop.
