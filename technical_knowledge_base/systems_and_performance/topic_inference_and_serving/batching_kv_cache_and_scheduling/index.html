A serving engine is a loop. Every few milliseconds it takes one step (also called an iteration): it decides which requests run, how many of their tokens it computes, and where their KV cache lives, then runs the model once over that batch. Everything on this page is a rule for one of those three decisions, and each rule exists because a simpler one broke.

The parent page, Topic: inference-and-serving, gives the intuition for each mechanism in a few paragraphs. This page goes one level down: what the papers measured, what the engines' code actually does (read at pinned versions: vLLM v0.31.0, SGLang v0.5.21, llama.cpp build 11146), what it costs, and how to check it on your own server. Words used throughout: prefill is the pass that reads a request's whole prompt and writes its keys and values; decode is one pass per further output token; the KV cache is those stored keys and values, one pair per token per layer; TTFT (time to first token) and TPOT or ITL (time per output token, inter-token latency) are the two latencies a user feels.

Which requests
batching, admission, order

Continuous batching re-forms the batch every step (section 1). Admission asks whether the KV cache has room; the order of the waiting queue is a policy: first come first served, priority, fairness, shortest first (section 7).

How many tokens
the token budget

A step carries at most a fixed number of new tokens. Decodes take one each; a long prompt is cut into chunks that fill the rest (chunked prefill, section 5).

Where the KV lives
blocks, tiers, eviction

The cache is cut into fixed blocks (paging, section 2), shared across requests that start the same way (prefix caching, section 3), spilled to slower memory (offload, section 4), taken back from a running request when it runs out (preemption, section 6), or thinned (compression, section 8).

The running example is the parent page's chat assistant: Llama 3.1 70B with FP8 weights on NVIDIA H200 GPUs, prompts of 2,000 tokens of which 1,000 are a shared system prompt, answers of 300 tokens. Its cache costs 320 KiB per token (2 × 80 layers × 8 KV heads × 128 dimensions × 2 bytes), so one 2,300-token conversation holds 719 MiB and one H200 has room for about 141 of them (Capacity planner tab of the parent, section 1). The measured examples are small Qwen3 models (0.6B and 1.7B) run on the Apple M1 Pro laptop this page was built on, the same models the parent's Engine bench tab measured.

1. Continuous batching: one step, any mix of requests

The problem. Before 2022, servers batched whole requests: take B requests, run them together until the longest answer ends, then take the next B. Finished requests leave empty seats and new arrivals wait for the whole batch (the parent's Serving simulator tab animates this in its section 1). The fix has two halves, both from one paper, Orca (Yu et al., OSDI 2022):

  • Iteration-level scheduling: the scheduler hands the engine one iteration (one step) at a time and gets control back after each, so a finished request can leave and a new one can join between any two steps.
  • Selective batching: the trick that makes any mix of requests runnable as one step. Most of a transformer layer (the matrix multiplications, normalisation, activation) does not care which request a token belongs to, so all tokens of all requests are stacked into one tall matrix of shape [total tokens, hidden size]. Only attention needs to know: each token may look only at its own request's earlier tokens. Orca splits the stack per request for attention and merges it back.

Orca's own example is four requests in four different states: x1 and x2 are decoding (one new token each, at different positions), x3 arrives with a 2-token prompt and x4 with a 3-token prompt. In a system that batches tensors of shape [batch, length, hidden], these four cannot share a step: the two prompts have different lengths, the two decodes sit at different positions, and prompts and decodes take different numbers of tokens (Orca, section 3, "C2"). What engines do now. The split and merge became one kernel. vLLM's FlashAttention backend takes the flattened tokens plus, for each request, where its queries start (query_start_loc), its total length (seq_lens) and its block table, and calls a variable-length attention kernel once for the whole step (vllm/v1/attention/backends/flash_attn.py, FlashAttentionMetadata L520 and flash_attn_varlen_func L1566). That is why prefill chunks and decodes can sit in the same step (section 5), and why the scheduler talks about tokens, not sequences.

The two caps on a step

Every engine bounds a step two ways. In vLLM they are max_num_batched_tokens, the token budget (new tokens computed per step, prefill and decode together), and max_num_seqs, the most requests in one step. In v0.31.0 the API server picks them from the GPU's memory: 8,192 tokens and 1,024 sequences on H100 and H200, 16,384 and 1,024 at 160 GiB or more (B200, MI300X), 2,048 and 256 on smaller GPUs such as an A100, L40S or RTX 5090 (engine/arg_utils.py get_batch_defaults, L2858). llama-server's equivalent of the budget is -b (default 2,048) and of the sequence cap the number of slots -np. SGLang sets its prefill chunk from GPU memory: 2,048 tokens under 20 GB, 4,096 under 80 GB, 8,192 for H100 and H200, 16,384 above 160 GB (arg_groups/memory_hook.py, handle_gpu_memory_settings L47).

Predict: a decode step for 64 users on the running example (Llama 3.1 70B FP8 on one H200). Roughly how much longer is it than a step for one user?
About 1.5 times. The step reads 72.66 GB of weights whatever the batch; each extra user adds only its own cache reads and a little arithmetic. The parent's planner gives 21.6 ms for one user and about 33 ms for 64 (46 against 1,930 output tokens per second, the parent's section 3), so 64 users cost 1.54 times the time (33.2 ms = 64 / 1,930) for 42 times the tokens. Measured here on a laptop GPU the same curve is flatter: llama-batched-bench with Qwen3-0.6B gave 188 tokens per second for one sequence and 1,320 for 64 (7 times), because each extra sequence costs about 1.2 ms of fixed work per step on this machine (Engine bench tab, "Batching").
Cost, when it matters, how to check

Cost. A step lasts as long as its slowest part, so whatever joins a step slows every user in it: a long prompt most of all (section 5). Each request also holds cache memory for as long as it runs, so more concurrency means more memory (section 2). When it matters: any server with more than one user at a time. How to check: sweep concurrency and plot output throughput against TPOT; vLLM's vllm:num_requests_running and vllm:num_requests_waiting gauges show whether the batch is full and requests queue.

One more thing Orca did, and the reason for the next section: to be sure a request could never run out of room mid-answer, its scheduler reserved max_tokens cache slots for every request at admission (Orca Algorithm 1, lines 23 to 26). Most of those slots were never used.

2. Paging: where the memory went, and how blocks got it back

The problem. Kwon et al. measured systems that store each request's cache in one contiguous region, sized when the request is admitted, and found that only 20.4% to 38.2% of the cache memory held actual tokens (PagedAttention, SOSP 2023, Fig. 2). They named three kinds of waste (same paper, Fig. 3):

  • Reservation: slots kept for tokens the request will generate later. They will be used, but nobody else can use them meanwhile.
  • Internal fragmentation: slots reserved that will never be used, because the answer ends before the reservation does.
  • External fragmentation: gaps between reservations, too small for the next request (the memory allocator's leftovers).

How paging works. PagedAttention borrows virtual memory from operating systems. The cache is a pool of fixed-size blocks (16 tokens in vLLM by default, vllm/config/cache.py L71); each request has a block table mapping its token positions to blocks anywhere in the pool; a new block is taken only when the last one fills. Reservation and external fragmentation disappear (all blocks are the same size and none is held in advance) and internal fragmentation shrinks to the unfilled tail of each request's last block: on average half a block, 8 tokens. The cost is an indirection inside the attention kernel, which reads keys and values through the table instead of from one contiguous array. Kwon et al. report 2 to 4 times the throughput of FasterTransformer and their Orca at the same latency (their measurement, 2023), and their vLLM held 96.3% token states in the same experiment.

Two lessons from the two charts. First, the waste is mostly reservation for answers that never come: these traces have long prompts (12,035 tokens on average in the conversation trace) and short answers (343), so even an oracle wastes little, while reserving 16,384 output tokens leaves under half the memory holding tokens. Short prompts with a large max_tokens, as in PagedAttention's experiment, are the worst case. Second, block size barely matters for waste until blocks get large: at 16 tokens the last-block waste is 0.06% here; at 2,048 tokens it is 7%.

Choosing a block size

Smaller blocks waste less but make the block table longer and each memory read smaller; larger blocks read more efficiently but waste more and share less, since a prefix can only be shared in whole blocks. Kwon et al. found 16 to 128 tokens best on ShareGPT and 16 or 32 on Alpaca's short sequences, and chose 16 as vLLM's default (PagedAttention section 7.2). Small blocks also made their swap path slow, because each block became a separate small PCIe copy (section 6). llama.cpp keeps per-token cells in one buffer shared by all slots, and Mooncake hashes its prefixes in 512-token blocks, which is why the traces below come in 512-token units.

Sharing inside one request

Blocks also make sharing cheap. When one request asks for several samples (parallel sampling, n > 1) or runs beam search, the sequences share their prompt's blocks; a block is copied only when a sequence writes into a shared one (copy-on-write, counted with a reference count per block). The authors measured memory savings of 6.1% to 9.8% for parallel sampling and 37.6% to 55.2% for beam search on Alpaca, and 16.2% to 30.5% and 44.3% to 66.3% on ShareGPT (PagedAttention section 6.3, their measurement). The same reference counts are what makes sharing across requests possible: prefix caching, next.

3. Prefix caching and eviction: which blocks to keep

The problem. Requests repeat themselves. Every turn of a chat resends the whole history; every call of an agent resends its tool definitions and instructions; every request of the running example starts with the same 1,000-token system prompt. Their keys and values are identical each time, so recomputing them wastes prefill. The parent measured a 1,500-word shared prefix cutting llama.cpp's TTFT from 1,426 ms to 77 ms on Qwen3-1.7B (Engine bench, "Prefix caching", measured here).

How a block is recognised

  • A name for each full block. vLLM hashes each full block from its parent block's hash, its own token ids and any extra keys (a LoRA adapter id, image hashes) (hash_block_tokens, kv_cache_utils.py L684; SHA-256 by default, cache.py L144). Because the parent's hash is inside, equal hashes mean an equal prefix all the way back to token 0. A half-filled last block has no hash and is never shared.
  • A hit is a prefix. The lookup walks the new request's block hashes from the start and stops at the first miss, and it stops one token short of the prompt, because the last token must be computed to produce logits (kv_cache_manager.py L295). A cached block after a missing one is useless for that request.
  • Cached is not the same as used. Each block has a reference count of running requests. When a request finishes, its blocks drop to zero references but keep their hashes: they stay in the cache, free to be taken, until a new allocation needs the space. Prefix caching is on by default (cache.py L142).
  • The free queue is the eviction order. Blocks nobody uses sit in one queue; new allocations take from the front. A finished request's blocks are returned in reverse order, tail first, blocks without a hash to the front (reused at once) and cached ones to the back (single_type_kv_cache_manager.py L588, block_pool.py free_blocks L777). The result is least-recently-used eviction in which, among blocks of the same age, a prefix's tail goes before its head.

SGLang keeps the same information as a radix tree of token sequences (RadixAttention, Zheng et al. 2023; the SGLang page reads it in depth) and evicts only leaves that no running request holds (radix_cache.py evict L553). Its eviction order is a choice: --radix-eviction-policy takes lru (the default), lfu, slru, priority or tlru (arg_groups/fields/memory.py, choices.py L184).

Why the tail must go first

A chain of blocks is only useful from its start. Evict a prefix's first block and every later block of that prefix becomes an orphan: still in memory, never hit again, until it too is evicted. Plain LRU orders blocks by last use, and all blocks of one request are used at the same moment, so the tie-break decides. vLLM's reverse-order free and SGLang's leaves-only rule both make the tail go first. Which policy, on a whole day's traffic

Moonshot AI released three one-hour request traces from Kimi with every request's 512-token block hashes (Mooncake FAST'25 traces): conversation (12,031 requests, 12,035 input tokens on average), tool and agent (23,608 requests, 8,596) and a synthetic one built from public datasets (3,993 requests, 15,325). Replaying them through six policies at fifteen cache sizes gives three findings (all in the Eviction lab, trace, computed here):

  • Capacity dominates. On the conversation trace, LRU hits 4.5% of blocks with 1,024 blocks (0.5 million tokens), 18.2% with 8,192 (4.2 million) and 33.5% with 32,768, against 36.6% for an unlimited cache. The best possible policy (Belady, which needs the future) already reaches the full 36.6% at 8,192 blocks: the gap is real, but no deployable policy here closes much of it.
  • Recency beats frequency on conversations. At 8,192 blocks LFU keeps 11.9% against LRU's 18.2%: chats come back while they are fresh, and old popular blocks crowd them out. On agent traffic, where a few tool prompts are reused all hour, LFU edges ahead at small sizes (18.5% against 17.3% at 16 blocks) and loses at middle sizes (39.3% against 44.0% at 8,192). ARC, an adaptive mix of the two and one of vLLM's host-memory policies, tracks LRU within a few points.
  • The tie-break matters only when the cache is tiny. Head-first LRU orphans blocks and loses a fifth of the hits at 16 blocks on agent traffic (14.0% against 17.3%); from 256 blocks up the gap is under one point on every trace (at most 0.7, synthetic trace at 4,096 blocks).

Cost, when it matters, how to check

Cost: hashing every full block (cheap), and nothing else while memory is spare: cached blocks only occupy space nobody needs yet. When it matters: multi-turn chat, agents, shared system prompts, few-shot templates, retrieval over the same documents. How to check: the hit rate is vllm:prefix_cache_hits over vllm:prefix_cache_queries, both counted in tokens (loggers.py L600 and L611); with --kv-cache-metrics (off by default, config/observability.py L60) vLLM also samples vllm:kv_block_reuse_gap_seconds and vllm:kv_block_idle_before_evict_seconds: if blocks are evicted after being idle for less time than typical reuse gaps, the cache is too small for your traffic. SGLang's newest option, tail-optimized LRU, evicts the parts of conversations that cannot affect tail TTFT first; its authors report up to 27.5% lower P90 TTFT than LRU on WildChat conversations (Tail-Optimized Caching, arXiv 2510.15152, authors' measurement, not run here).

4. Offload tiers: a bigger, slower cache behind the GPU

The problem. The GPU holds very few reusable prefixes. In the running example one H200 has about 54 GB for its cache, 164,800 tokens at 320 KiB each: about 320 of Mooncake's 512-token blocks. On the conversation trace, an LRU cache of 256 blocks hits 4.2% of blocks; an unlimited one would hit 36.6%. The data that could be reused does not fit, and the cheapest place to put it is the server's own DRAM (often 1 to 2 TB per 8-GPU server), then local SSDs, then other servers' memory over the network.

Reload or recompute?

A tier is worth having when reading a block back is faster than recomputing it. Recomputing costs a prefill; reloading costs the block's bytes divided by the link's bandwidth. Per token:

reload / recompute = (KV bytes per token / link bandwidth) ÷ (prefill time per token)

Reload a cached prefix, or compute it again?

For every model here the link wins by a wide margin over PCIe and the network, and even an SSD read beats recomputing on a datacenter GPU. Recompute only competes where prefill is very fast relative to the cache's size: small models, or links shared by many GPUs at once. Two things the formula leaves out push the same way: prefill attention grows with the square of the prefix, so long prefixes favour reloading more, and engines overlap loading with other requests' compute (CachedAttention loads layer by layer while earlier layers run; its authors report up to 87% lower TTFT for multi-turn conversations, Gao et al., USENIX ATC 2024, their measurement).

5. Chunked prefill: the token budget as a latency dial

The problem. Continuous batching lets a new prompt join a step that is also decoding other users. If the whole prompt joins at once, that step lasts as long as the prompt's prefill, and every user mid-answer sees their stream freeze: a generation stall (the term is from Sarathi-Serve, Agrawal et al., OSDI 2024). The parent's Engine bench saw one: a gap of 803 ms in a stream whose median gap was 31.4 ms.

How it works. Cap the new tokens per step (the token budget of section 1), schedule the decodes first, and let a waiting prompt fill what is left, one chunk per step, until its prompt is done. Sarathi introduced chunked prefills with "decode-maximal batching" (Agrawal et al. 2023); Sarathi-Serve made them stall-free and reports 2.6 times the serving capacity of vLLM at the time for Mistral-7B on one A100, 3.7 times for Yi-34B on two A100s and 5.6 times for Falcon-180B with pipeline parallelism, under tail-latency targets (authors' measurement). The engines:

  • vLLM v0.31.0: on by default (config/scheduler.py L135); the scheduler walks the running requests first (their decodes, and the unfinished chunks of prompts already started), then admits waiting requests while budget remains (scheduler.py, schedule()).
  • llama-server: each step first adds every generating slot's sampled token, then pending prompt tokens until the batch holds -b tokens (server-context.cpp, update_slots L3100 to L3115 and L3524). So -b is its chunk size, decode-first, the same design.
  • SGLang v0.5.21: --chunked-prefill-size, set from GPU memory when not given (8,192 on H100 and H200, section 1); -1 turns it off.
  • TensorRT-LLM v1.2.1: enable_chunked_prefill is False by default (llm_args.py L2006).

The trade. A smaller budget means shorter stalls, but the long prompt needs more steps, each paying fixed costs and re-reading the weights, so its TTFT rises a little and total throughput falls a little. It was measured here on a real engine: four users decoding on llama-server while a fifth sends a 6,011-token prompt, at six budgets.

Stall against TTFT, one point per token budget

Measured here (Qwen3-1.7B, llama-server, three runs per budget): with a budget of 128 tokens per step the four decoding users never waited more than 242 ms, but the 6,008-token prompt took 9.55 s to its first token; at 512 tokens, 762 ms and 7.57 s; at 2,048, 2.66 s and 7.17 s; at 8,192, where the whole prompt fits in one step, the four users froze for 7.26 s and the prompt took 7.28 s. Alone, the same four streams had gaps of 26 ms (median) and 33 ms (p99). The three runs of each budget agreed within 2.5% on TTFT and 4% on the longest gap, although other work kept the machine's load average between 17 and 151. The simulator, given only its M1 Pro preset and Qwen3-1.7B's shape, comes within 4% to 11% of both numbers for budgets of 512 and above, and is 20% to 24% low at 128, where per-step costs it underestimates dominate. One more lesson from the same runs: at budgets of 2,048 and 8,192 the p99 of all gaps was 37 ms, because the stall is one gap among two thousand. Only the maximum shows it.

Predict: on the simulated H100, halving the budget from 2,048 to 1,024 tokens per step. What happens to the long prompt's TTFT?
About 2%: 0.431 s to 0.439 s, while the longest gap the eight decoding users see halves, from 79 ms to 42 ms (derived, the parent's simulator with the H100 preset fitted to NVIDIA's published measurements). Each chunk is still large enough to keep the GPU busy, so cutting it costs little; the cost grows below about 512 tokens (0.471 s at 512, 0.880 s at 128), where each step's fixed costs and weight reads dominate.

Choosing the budget

Pick the largest budget whose stall your inter-token latency target tolerates. Under steady traffic, with 20 chat requests per second and 2 long-document requests per second on the simulated H100, the p99 inter-token gap goes from 13 ms at a 512-token budget to 45 ms at 2,048 and 267 ms at 16,384, while p99 TTFT goes from 1.46 s to 1.07 s to 0.95 s and throughput does not move (Scheduling lab, section 1). vLLM's 8,192 default on an H100 is tuned for throughput; an interactive service with a 50 ms TPOT target wants about 2,048 on this model.

Cost, when it matters, how to check

Cost: slightly longer TTFT for long prompts and slightly lower peak throughput at small budgets. When it matters: any mix of long prompts (documents, retrieval, agents with big tool outputs) and streaming users. How to check: look at the maximum and p99 inter-token latency, not the mean (vllm:inter_token_latency_seconds is a histogram), during periods when long prompts arrive.

6. Preemption: taking memory back from a running request

The problem. Nobody knows an answer's length in advance. vLLM admits a request when its prompt fits in free blocks (it reserves nothing for the answer, section 2), so at some step a running request needs one more block and there is none. The engine must take memory from someone: preemption. There are three answers to "who" and two to "what happens to their cache".

Recompute or swap

Swapping copies the victim's blocks to host memory and back: 2 × KV bytes / link bandwidth per token. Recomputing runs its prefill again: about 0.21 ms per token for the running example. With 320 KiB per token over PCIe Gen5 at 64 GB/s each way, a swap costs about 10 µs per token, twenty times cheaper in time (the section 4 calculator, doubled). So why did vLLM keep only recompute?

  • The measured difference was small. Kwon et al. found swapping slow with small blocks (many tiny PCIe copies), recomputing constant, and the two "comparable end-to-end" for blocks of 16 to 64 tokens; "recomputation overhead is never higher than 20% of swapping's latency" (PagedAttention section 7.3, their measurement on A100s).
  • Recompute uses idle arithmetic. Decode steps are memory-bound; a recomputed prefix rides in the token budget like any prompt chunk (section 5).
  • Swap is machinery: a host block allocator, copies on the critical path, and memory bounded by the GPU cache size.
  • The offload tier does it anyway. With --kv-offloading-size set, the OffloadingConnector writes blocks to host memory as they are computed and flushes the pending writes of a preempted request (offloading/scheduler.py L1787); when the request is scheduled again its prefix is found in host memory and loaded rather than recomputed. Recompute-only preemption plus a CPU tier behaves like a write-through swap. (Read in source, not run here.)

On the simulated H100 with a deliberately small cache (2,000 blocks of 16 tokens, Llama 3.1 8B in BF16, 6 requests per second), recompute and swap at 25 GB/s differ by 3% in throughput (2,364 against 2,430 tokens per second) with the same 146 preemptions; a slow 6 GB/s link makes swap the worse one (2,287). The bigger effect is admission: reserving every request's maximum length, TensorRT-LLM's default rule, removes all preemptions but serves 1,785 tokens per second with a p99 TTFT of 31.25 s, against 12.61 s for optimistic admission (Scheduling lab, section 4, derived). Measured here, vLLM's CPU backend with a 9,344-token cache reached 100% cache use and 8 preemptions at 16 users, and its output fell from 26.5 to 15.6 tokens per second between 8 and 16 users (Engine bench): preemption is the symptom of admitting more than fits.

Cost, when it matters, how to check

Cost: the victim's work is thrown away (recompute) or copied twice (swap), and the victim's latency jumps. When it matters: long answers, large max_tokens, high concurrency on a small cache. How to check: vllm:num_preemptions (loggers.py L677) rising while vllm:kv_cache_usage_perc sits at 1.0. The fixes, in order: a smaller max_num_seqs, a lower max_tokens, a quantized cache (FP8 halves it), more GPUs.

7. Priority, fairness and SLOs: who goes next

The problem. When the server is full, the order of the waiting queue decides who waits. First come, first served (FCFS, every engine's default) is fair per request, not per user: one client that sends a flood of requests puts everyone else behind it (head-of-line blocking), and one very long job can hold up many short ones. Three families of answers, from simplest to subtlest:

Priority classes

Each request carries a number; the scheduler serves the best number first. In vLLM v0.31.0 (--scheduling-policy priority, field priority on the request), lower values go first, ties by arrival time and then by request id (vllm/v1/request.py Request.__lt__); when memory runs out, the victim is the running request with the largest priority value, then the latest arrival (scheduler.py L764). A waiting high-priority request does not evict running ones to get in: it waits for space. SGLang (--enable-priority-scheduling, off by default) serves higher values first by default and lets an arriving request preempt running ones whose priority is at least 10 worse (--priority-scheduling-preemption-threshold, arg_groups/fields/schedule.py). Checked here: the parent's simulator, extended with vLLM's priority rules, made the same decisions as vLLM's own Scheduler class at every step of eight two-client traces (four with priorities, four first come first served; 2,256 steps, 79 preemptions); matching it needed one detail, that vLLM breaks priority-and-arrival ties by comparing request ids as strings, so request "10" goes before request "2" (Scheduling lab, section 5).

Fairness between clients: the Virtual Token Counter

Priorities need someone to assign them and can starve the low class. Sheng et al. define fair service for LLMs by counting tokens, with output tokens weighted more because they cost more (w_p = 1 per prompt token, w_q = 2 per output token, following OpenAI's prices at the time) and propose the Virtual Token Counter (VTC): keep one counter per client; when there is room, admit the earliest request of the client with the smallest counter; add wp × prompt tokens when a request is admitted and wq per generated token; when a client (re)joins the queue, lift its counter to the smallest counter among waiting clients, so idle time cannot be banked. They prove that two clients who both have work waiting never differ in service by more than 2 × max(wp × longest prompt, wq × largest batch of output tokens) (Fairness in Serving Large Language Models, OSDI 2024, Algorithm 2 and Theorem 4.4). The usual alternative, a requests-per-minute limit per client, wastes capacity when other clients are idle.

Shortest job first

Serving short jobs first minimises mean waiting time, a classic result; the catch is that an answer's length is unknown until it ends. Systems approximate it by predicting lengths: learning to rank them (its authors report 2.8 times lower latency for chatbot serving, Fu et al. 2024) or a multi-level feedback queue that demotes long-running jobs (FastServe, Wu et al. 2023). The simulator with perfect knowledge (an oracle) shows what is at stake: below capacity nothing changes, because no queue forms; at 46 requests per second, beyond the server's capacity, mean TTFT falls from 2.25 s to 1.47 s, but p99 TTFT rises from 5.1 s to 26.8 s, and the longest answers' p99 latency from 15.7 s to 36.9 s (Scheduling lab, section 3, derived). Shortest-first trades the tail for the mean.

SLOs and goodput

Every policy above is a guess at what users want. An SLO (service level objective) states it: for example p99 TTFT under 2 s and TPOT under 100 ms, MLPerf's targets for Llama 3.1 8B. DistServe defines goodput as "the maximum request rate that can be served adhering to the SLO attainment goal (say, 90%) for each GPU provisioned" (DistServe, section 1); simulators, the parent's included, often report the simpler per-second count of requests that met both targets. SLO-aware schedulers order and admit requests by deadline, and under overload reject early rather than serve everyone late: Mooncake's scheduler predicts load and rejects requests it cannot serve in time (Mooncake). SGLang also ships cache-aware orders: --schedule-policy takes fcfs (the default), lpm (longest cached prefix first), dfs-weight, lof, random, priority, routing-key, hrrn and shortest-prefill-first (arg_groups/fields/schedule.py); the SGLang page measures why ordering by cache hits matters.

Cost, when it matters, how to check

Cost: any reordering makes someone wait longer; strict priority and shortest-first can starve. When it matters: only when a queue forms, that is near or beyond capacity, and with several tenants or very mixed request sizes. How to check: TTFT percentiles per tenant and per priority class (tag requests and split your metrics), and vllm:request_queue_time_seconds for time spent waiting.

8. KV compression: algorithmic against realisable savings

The problem. Long contexts fill the cache no matter how well it is paged, cached and offloaded. The remaining option is to store less per token or fewer tokens. Four families, from safest to riskiest:

  • A model with a smaller cache. Grouped-query attention, multi-head latent attention, sliding-window layers: chosen at training time (the parent's section 2).
  • Fewer bytes per entry: KV quantization. vLLM and SGLang offer an FP8 cache; llama.cpp offers q8_0 (8.5 bits per number) and q4_0 (4.5) for keys and values, 0.53 and 0.28 of the F16 size (the parent's Engine bench measured the bytes). Measured here on Qwen3-1.7B (Q8_0 weights, WikiText-2 test, 2,048-token windows, 30 of them): perplexity 15.18 with an F16 cache, 15.18 with q8_0, and 19.42 with q4_0, 28% worse. An 8-bit cache was free on this model; a 4-bit one was not.
  • Fewer entries: eviction. Prefill the prompt, score every cached token by an importance signal, keep the best: StreamingLLM keeps the first few tokens, which soak up attention ("attention sinks"), plus a recent window (Xiao et al. 2023); H2O keeps tokens with the most accumulated attention (Zhang et al. 2023); SnapKV scores tokens by the attention they get from an "observation window" at the end of the prompt, per head (Li et al. 2024, whose authors report 3.6 times faster generation and 8.2 times better memory efficiency at 16K tokens); KVzip scores by how well the model can reconstruct the context and reports 3 to 4 times smaller caches (Kim et al. 2025); Expected Attention estimates future queries' attention and ships KVPress, a library of more than 20 methods (Devoto et al. 2025). All authors' claims, not run here.
  • Fewer tokens: compress the input before the decoder. A small encoder turns the context into fewer latent vectors; the cache layout stays standard (Latent Context Language Models).

Two questions to ask of any eviction paper

Is the saving realisable? An eviction method that prefills the whole prompt first never lowers the peak: the full cache existed. And a paged engine stores all heads of all layers for 16 tokens in one block, so it can free a block only when every head of every layer has dropped all 16 of its tokens. A method that keeps different tokens per head, as SnapKV and H2O do, shows that quality survives a smaller cache (the algorithmic saving) without letting the engine reclaim the memory (the realisable saving) unless the cache layout changes. A selection shared by all heads and layers can be compacted into fewer blocks.

Does it beat the cheap control? Keep the prompt and evict uniformly at random: on reasoning traces, Random Attention matched the strongest learned policy on four models and six tasks, at 32% to 43% higher throughput in vLLM (arXiv 2609.03430, authors' measurement; their explanation is that reasoning traces repeat what they still need). Random eviction draws no score, so it costs nothing to compute.

Both questions, measured

Measured here on Qwen3-0.6B (PyTorch on the CPU; the KV compression experiment tab has every number). Task A hides one "secret code" line among 60 (about 800 tokens) and asks for it; with the full cache the model answers 98.3% of 60 questions.   • Random eviction must keep the first tokens. Uniform random choice over all positions sends perplexity from 17.04 to 927 on average at 25% kept, because it can drop the first token, the attention sink; the one seed that kept it scored 23. Keeping the first 4 tokens and choosing the rest at random gives 23.71. The cheap control has to be done right.
  • On text continuation, random is a respectable control but loses. At 25% kept: H2O 18.08, SnapKV 19.83, random per head 22.16, random shared 23.71. At 10%: 19.97, 22.97, 26.84 and 27.80.
  • On retrieval, random fails outright. At 25% kept, random with sinks answers 5.6% of questions, random per head 13.9%, keeping the most recent tokens 26.7%, H2O 26.7%, SnapKV per head 63.3%, and SnapKV with one selection shared by all heads and layers 91.7%. Retrieval needs one specific line, which only a score informed by the question keeps. The Random Attention result is about reasoning traces, which repeat themselves; it does not transfer to finding one fact.
  • The realisable saving. Per-head selections (SnapKV, H2O, random per head) left no 16-token block free: 0% of the memory comes back in a paged engine without a per-head layout. Shared random selection freed 1.3% of blocks in place at 25% kept (kept tokens are scattered over almost every block), although compaction could reclaim all 75%. The shared SnapKV selection, the best on retrieval here, also kept its tokens in clusters: 51% of blocks freeable in place, 75% with compaction.

What transfers: the ranking of methods and the two questions. What does not: a 0.6B model on 800 to 1,024-token contexts is not a 70B model on 100K tokens, and eviction matters most where contexts are long. Treat these as a demonstration of the method of checking, not as the verdict on any paper.

Common mistakes

"Prefix caching is on, so repeated prompts are free."
Only whole blocks of an exact prefix hit, and the last prompt token is always recomputed (section 3). One changing token near the start (a timestamp or a request id in the system prompt) makes every later block a miss. Put what changes at the end, and check vllm:prefix_cache_hits rather than assuming.
"More concurrent sequences, more throughput."
Only while the cache has room. Past that point the engine preempts and recomputes: vLLM's CPU backend went from 26.5 to 15.6 output tokens per second between 8 and 16 users once its cache filled (the parent's Engine bench, measured). Watch vllm:num_preemptions before raising max_num_seqs.
"Chunked prefill makes prefill faster."
It makes it slightly slower. It caps how long any one step can last, so decoding users never stall for a whole long prompt; the long prompt pays with a little more TTFT (section 5).
"The mean inter-token latency shows stalls."
A one-second stall in a 500-token answer moves the mean by 2 ms, and a rare one hides even from the p99: measured here at a budget of 8,192, the p99 gap was 37 ms while the longest was 7.26 s (section 5). Look at the maximum gap while long prompts arrive.
"Frequently used blocks should be kept longest (LFU)."
On Kimi's conversation trace LFU keeps 11.9% of blocks against LRU's 18.2% at 8,192 blocks: conversations return while they are fresh, and blocks that were popular an hour ago crowd them out (section 3).
"A cached block is a hit."
Only if every block before it in the prompt is cached too. A cache that evicts a prefix's head keeps its tail as orphans that can never be used (section 3).
"Swapping is obviously better than recomputing, PCIe is fast."
Per token it is cheaper in time, but measured end to end the two were comparable for normal block sizes, and recompute needs no host block manager (section 6). vLLM v1 keeps only recompute; its host-memory offload tier gives a write-through copy anyway.
"The paper says 8 times less KV memory, so 8 times more users."
Ask whether the saving is realisable: eviction after a full prefill does not lower peak memory, and selections that differ per head or per layer free no blocks in a paged engine (section 8 measures it). Then run the cheap control: uniform random eviction that keeps the first tokens.
"Fairness means per-client rate limits."
Rate limits cap a client even when the server is idle. A fair scheduler (VTC) shares capacity only when there is contention (section 7).

Interview questions, with short answers

Why does continuous batching need special attention kernels?
Each request in a step has its own length and its own cache, so attention cannot use one rectangular tensor. Engines flatten all new tokens into one matrix for the linear layers and run a variable-length attention kernel that takes each request's query offsets, sequence length and block table (vLLM's FlashAttention backend).
What did PagedAttention fix, and what does it cost?
Reservation, internal and external fragmentation of contiguous per-request caches (20.4% to 38.2% of memory held tokens in the authors' baselines). Fixed-size blocks with a block table leave at most one partly filled block per request. Cost: an indirection in the attention kernel and a block size to choose (16 by default).
How does vLLM know two requests share a prefix?
Each full block is named by a hash of its parent block's hash, its token ids and extra keys (LoRA, images); equal hashes mean equal prefixes back to token 0. The lookup stops at the first miss and one token short of the prompt.
Which blocks should a prefix cache evict first, and why the tail?
The least recently used, and among blocks of the same request the tail first, because a block is useless once any block before it is gone. Measured on production traces, capacity matters far more than the policy; LRU beats LFU on conversations.
When is loading KV from host memory better than recomputing it?
When KV bytes per token divided by link bandwidth is below prefill time per token. For Llama 3.1 70B, 320 KiB over 64 GB/s is about 5 µs against about 210 µs of prefill on an H200: almost always for large models.
How do you choose max_num_batched_tokens?
It is the chunk size: the largest value whose worst step still meets your inter-token latency target when a long prompt arrives. Larger budgets raise throughput and lower long-prompt TTFT slightly; smaller ones cap stalls.
Your cache fills mid-answer. What does each engine do?
vLLM preempts the newest request (or the worst priority) and recomputes it later; SGLang retracts the request with the fewest output tokens; TensorRT-LLM by default never admits more than fits with every request's maximum length; llama-server fails the active requests.
How would you make a multi-tenant LLM API fair?
Count service in weighted tokens (input and output weighted differently), keep a counter per tenant, always admit from the tenant with the smallest counter, and lift a returning tenant's counter so idle time is not banked: the Virtual Token Counter, with a proven bound on the service gap between backlogged tenants.
Why can shortest-job-first make things worse?
It only matters when a queue forms, and then it lowers mean latency by pushing long jobs back: in the simulator at 46 requests per second, mean TTFT fell from 2.25 s to 1.47 s while p99 TTFT rose from 5.1 s to 26.8 s.
What is goodput, and why use it instead of throughput?
The request rate a deployment sustains while meeting its latency targets (DistServe: at a given SLO attainment, such as 90% of requests). Throughput that breaks the SLO is not useful capacity.
A paper claims 8 times smaller KV cache from eviction. What do you check?
Whether the saving is realisable (eviction after full prefill, per-head selections in a paged engine), what task it was scored on (retrieval punishes eviction far more than perplexity), and whether it beats uniform random eviction that keeps the first tokens.

5. What the replay leaves out

  • Time and concurrency. Requests are replayed one after another, as Mooncake's own analysis does ("we consider only the sequence of requests"): blocks of running requests are not pinned, prefill time is not modelled, and nothing is evicted mid-request by other requests.
  • Generated tokens. The traces hash prompts only, so blocks written during decoding are never cached here; a real engine caches them too, which helps multi-turn chat (the next turn's prompt contains the last answer).
  • One cache. One pool, as if every request reached the same replica. Several replicas each with their own cache need routing that sends a conversation back to its cache (LLM serving in production).
  • Block size. 512-token blocks, as hashed in the traces, against vLLM's 16: finer blocks can match partial prefixes the traces cannot show.

6. What the simulator leaves out

  • Everything the parent's simulator leaves out: CUDA graph padding, the CPU running ahead of the GPU (vLLM's asynchronous scheduling), tokenization and network time, tensor parallelism, speculative decoding.
  • VTC and SJF are the papers' algorithms on vLLM's step structure, not code from a released engine; the priority policy is vLLM's and is checked against it.
  • Swap is modelled as a blocking copy at the link's full bandwidth, with no per-block overhead: the PagedAttention authors measured small blocks transferring far below that (section 6 of the Reading tab).

KV compression papers drop most of a prompt's cache entries and report that quality survives. Two questions decide whether that helps a server: does a clever importance score beat dropping entries at random, and can a paged engine actually reclaim the memory? This tab answers both on a real model, run here.

The experiment
measured here: Qwen/Qwen3-0.6B (safetensors @ c1899de2, BF16 weights run in float32), PyTorch 2.14.1 and transformers 5.19.0 on the M1 Pro's CPU with 2 threads, eager attention so the attention weights can be read, greedy decoding; script src/kvc/kvc.py. 2. What a paged engine could free

"Selection" says whether every layer and head keeps the same positions. A paged engine stores all heads of all layers of 16 tokens in one block (vLLM), so a block is free only when no layer and no head keeps any of its 16 tokens: the "freeable in place" column. A uniform selection can also be compacted (the kept tokens rewritten into fewer blocks; their positions are already baked into the keys by RoPE), which realises the full saving; a per-head or per-layer selection cannot without a per-head cache layout. Eviction after a full prefill never lowers the peak: the whole prompt's cache existed first.

4. Reading the result, and what does not transfer

  • Sinks first. Dropping the first tokens wrecks the model (perplexity in the hundreds), which is why every sensible policy keeps them and why a fair random control must too.
  • The task decides the winner. On continuation, heavy hitters (H2O) lose least; on retrieval, a question-aware score (SnapKV) is the only thing that works, and the shared version beats the per-head one here. Random with sinks is a fair floor on continuation and useless on retrieval.
  • Realisable is a separate axis. The per-head methods that score well on continuation free nothing in a paged engine; the shared selection frees memory but scores worse on continuation. A paper's memory figure must say which kind it is.
  • Not transferable: absolute numbers (tiny model, short contexts, CPU), anything about speed (not measured: eager attention on a CPU), and long-context behaviour, where eviction matters most. For long-context benchmarks see Long-context and multimodal benchmarks.
