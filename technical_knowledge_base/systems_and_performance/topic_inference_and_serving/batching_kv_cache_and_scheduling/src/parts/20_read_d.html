3. Prefix caching and eviction: which blocks to keep

The problem. Requests repeat themselves. Every turn of a chat resends the whole history; every call of an agent resends its tool definitions and instructions; every request of the running example starts with the same 1,000-token system prompt. Their keys and values are identical each time, so recomputing them wastes prefill. The parent measured a 1,500-word shared prefix cutting llama.cpp's TTFT from 1,426 ms to 77 ms on Qwen3-1.7B ({{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}, "Prefix caching", measured here).

How a block is recognised

  • A name for each full block. vLLM hashes each full block from its parent block's hash, its own token ids and any extra keys (a LoRA adapter id, image hashes) ({{hash_block_tokens, kv_cache_utils.py L684|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/kv_cache_utils.py#L684}}; SHA-256 by default, {{cache.py L144|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/cache.py#L144}}). Because the parent's hash is inside, equal hashes mean an equal prefix all the way back to token 0. A half-filled last block has no hash and is never shared.
  • A hit is a prefix. The lookup walks the new request's block hashes from the start and stops at the first miss, and it stops one token short of the prompt, because the last token must be computed to produce logits ({{kv_cache_manager.py L295|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/kv_cache_manager.py#L295}}). A cached block after a missing one is useless for that request.
  • Cached is not the same as used. Each block has a reference count of running requests. When a request finishes, its blocks drop to zero references but keep their hashes: they stay in the cache, free to be taken, until a new allocation needs the space. Prefix caching is on by default ({{cache.py L142|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/cache.py#L142}}).
  • The free queue is the eviction order. Blocks nobody uses sit in one queue; new allocations take from the front. A finished request's blocks are returned in reverse order, tail first, blocks without a hash to the front (reused at once) and cached ones to the back ({{single_type_kv_cache_manager.py L588|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/single_type_kv_cache_manager.py#L588}}, {{block_pool.py free_blocks L777|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/block_pool.py#L777}}). The result is least-recently-used eviction in which, among blocks of the same age, a prefix's tail goes before its head.

SGLang keeps the same information as a radix tree of token sequences (RadixAttention, {{Zheng et al. 2023|https://arxiv.org/abs/2312.07104}}; the {{SGLang page|n:3c65c17b0d0d81e691e4ce9f9b5d1fad}} reads it in depth) and evicts only leaves that no running request holds ({{radix_cache.py evict L553|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L553}}). Its eviction order is a choice: --radix-eviction-policy takes lru (the default), lfu, slru, priority or tlru ({{arg_groups/fields/memory.py|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/arg_groups/fields/memory.py}}, {{choices.py L184|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/arg_groups/choices.py#L184}}).

Why the tail must go first

A chain of blocks is only useful from its start. Evict a prefix's first block and every later block of that prefix becomes an orphan: still in memory, never hit again, until it too is evicted. Plain LRU orders blocks by last use, and all blocks of one request are used at the same moment, so the tie-break decides. vLLM's reverse-order free and SGLang's leaves-only rule both make the tail go first. Which policy, on a whole day's traffic

Moonshot AI released three one-hour request traces from Kimi with every request's 512-token block hashes ({{Mooncake FAST'25 traces|https://github.com/kvcache-ai/Mooncake/tree/main/FAST25-release}}): conversation (12,031 requests, 12,035 input tokens on average), tool and agent (23,608 requests, 8,596) and a synthetic one built from public datasets (3,993 requests, 15,325). Replaying them through six policies at fifteen cache sizes gives three findings (all in the {{Eviction lab|#t-ev}}, trace, computed here):

  • Capacity dominates. On the conversation trace, LRU hits 4.5% of blocks with 1,024 blocks (0.5 million tokens), 18.2% with 8,192 (4.2 million) and 33.5% with 32,768, against 36.6% for an unlimited cache. The best possible policy (Belady, which needs the future) already reaches the full 36.6% at 8,192 blocks: the gap is real, but no deployable policy here closes much of it.
  • Recency beats frequency on conversations. At 8,192 blocks LFU keeps 11.9% against LRU's 18.2%: chats come back while they are fresh, and old popular blocks crowd them out. On agent traffic, where a few tool prompts are reused all hour, LFU edges ahead at small sizes (18.5% against 17.3% at 16 blocks) and loses at middle sizes (39.3% against 44.0% at 8,192). ARC, an adaptive mix of the two and one of vLLM's host-memory policies, tracks LRU within a few points.
  • The tie-break matters only when the cache is tiny. Head-first LRU orphans blocks and loses a fifth of the hits at 16 blocks on agent traffic (14.0% against 17.3%); from 256 blocks up the gap is under one point on every trace (at most 0.7, synthetic trace at 4,096 blocks).
Predict: the Mooncake report's own table says increasing a global cache from 1,000 to 50,000 blocks raises the hit rate from 30% to 50% under LRU. On the trace file they released, does the replay here find the same?
Same shape, a few points higher: 34.1% at 1,000 blocks, 46.1% at 10,000, 55.1% at 50,000 and 55.3% unlimited, against the table's 30%, 40%, 50% and 51% ({{Mooncake arXiv report, Table 1|https://arxiv.org/abs/2407.00079}}). LRU also beats LFU at middle sizes in both. It does not reproduce exactly: the report says the trace averages 7,590 input tokens, while the released file averages 8,590, so the table may come from a different cut of the data. The FAST'25 paper's Fig. 9 labels (local cache of 3 million tokens as a share of the unlimited hit rate) reproduce closely: 73.7% for tool and agent against 75%, 48.4% for synthetic against 48%, 44.6% for all three merged against 46%, and 37.1% for conversation against 41%.
Cost, when it matters, how to check

Cost: hashing every full block (cheap), and nothing else while memory is spare: cached blocks only occupy space nobody needs yet. When it matters: multi-turn chat, agents, shared system prompts, few-shot templates, retrieval over the same documents. How to check: the hit rate is vllm:prefix_cache_hits over vllm:prefix_cache_queries, both counted in tokens ({{loggers.py L600 and L611|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/metrics/loggers.py#L600}}); with --kv-cache-metrics (off by default, {{config/observability.py L60|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/observability.py#L60}}) vLLM also samples vllm:kv_block_reuse_gap_seconds and vllm:kv_block_idle_before_evict_seconds: if blocks are evicted after being idle for less time than typical reuse gaps, the cache is too small for your traffic. SGLang's newest option, tail-optimized LRU, evicts the parts of conversations that cannot affect tail TTFT first; its authors report up to 27.5% lower P90 TTFT than LRU on WildChat conversations ({{Tail-Optimized Caching, arXiv 2510.15152|https://arxiv.org/abs/2510.15152}}, authors' measurement, not run here).
