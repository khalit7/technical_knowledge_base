3. Prefix caching and eviction: which blocks to keep

Requests repeat themselves. Every chat turn resends the whole history, every agent call resends its tool definitions, every request of the running example starts with the same 1,000-token system prompt. Their keys and values are identical each time, so recomputing them wastes prefill: the parent measured a 1,500-word shared prefix cutting llama.cpp's TTFT from 1,426 ms to 77 ms on Qwen3-1.7B ({{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}, "Prefix caching", measured here). Four rules make a block reusable in vLLM:

  • A name for each full block. Each full block is hashed from its parent block's hash, its own token ids and any extra keys (a LoRA adapter id, image hashes); SHA-256 by default. Because the parent's hash is inside, equal hashes mean an equal prefix all the way back to token 0. A half-filled last block has no hash and is never shared.
  • A hit is a prefix. The lookup walks the new request's block hashes from the start, stops at the first miss, and stops one token short of the prompt, because the last token must be computed to produce logits. So one changing token near the start (a timestamp or a request id in the system prompt) makes every later block a miss: put what changes at the end.
  • Cached is not used. Each block counts the running requests that hold it. A finished request's blocks drop to zero references but keep their hashes: they stay cached, free to be taken, until an allocation needs the space. Prefix caching is on by default.
  • The free queue is the eviction order. Unused blocks sit in one queue and new allocations take from the front. A finished request's blocks are returned in reverse order, tail first: blocks without a hash to the front (reused at once), cached ones to the back. The result is least-recently-used (LRU) eviction in which, among blocks of the same age, a prefix's tail goes before its head.

SGLang keeps the same information as a radix tree of token sequences (RadixAttention, {{Zheng et al. 2023|https://arxiv.org/abs/2312.07104}}; the {{SGLang page|n:3c65c17b0d0d81e691e4ce9f9b5d1fad}} reads it in depth) and evicts only leaves that no running request holds, which also sends the tail first.

Why the tail must go first

A chain of blocks is only useful from its start. Evict a prefix's first block and every later block of it becomes an orphan: still in memory, never hit again. All blocks of one request were used at the same moment, so plain LRU's tie-break decides. Step through what the other tie-break does on 16 consecutive requests from Kimi's production agent traffic.

Which policy, on a whole hour of traffic

Moonshot AI released three one-hour request traces from Kimi with every request's 512-token block hashes ({{Mooncake FAST'25 traces|https://github.com/kvcache-ai/Mooncake/tree/main/FAST25-release}}): conversation (12,031 requests, 12,035 input tokens on average), tool and agent (23,608 requests, 8,596) and a synthetic one built from public datasets (3,993 requests, 15,325). Capacity matters far more than the policy: hit rate against cache size, six policies

  • Capacity dominates. On the conversation trace, LRU hits 4.5% of blocks with 1,024 blocks (0.5 million tokens), 18.2% with 8,192 (4.2 million) and 33.5% with 32,768, against 36.6% for an unlimited cache. Belady, the best possible policy (it needs the future), already reaches the full 36.6% at 8,192 blocks: the gap is real, but no deployable policy here closes much of it.
  • Recency beats frequency on conversations. At 8,192 blocks LFU keeps 11.9% against LRU's 18.2%: chats come back while they are fresh, and blocks that were popular an hour ago crowd them out. On agent traffic, where a few tool prompts are reused all hour, LFU edges ahead at small sizes (18.5% against 17.3% at 16 blocks) and loses at middle sizes (39.3% against 44.0% at 8,192). ARC, an adaptive mix of the two and one of vLLM's host-memory policies, tracks LRU within a few points.
  • The tie-break matters only when the cache is tiny. Head-first LRU loses a fifth of the hits at 16 blocks on agent traffic (14.0% against 17.3%); from 256 blocks up the gap is under one point on every trace (at most 0.7, synthetic trace at 4,096 blocks).

Same shape, a few points higher: 34.1% at 1,000 blocks, 46.1% at 10,000, 55.1% at 50,000 and 55.3% unlimited, against the table's 30%, 40%, 50% and 51% ({{Mooncake arXiv report, Table 1|https://arxiv.org/abs/2407.00079}}). Check: the hit rate is vllm:prefix_cache_hits over vllm:prefix_cache_queries, both in tokens; with --kv-cache-metrics on, vLLM also samples how long blocks sat idle before eviction against typical reuse gaps (section 9). Prefix caching costs only hashing while memory is spare: cached blocks occupy space nobody needs yet.

The traces and the published numbers they reproduce, and vLLM's own block pool as referee

The data: for every request its arrival time, input and output lengths, and the hash of each 512-token block of its prompt, remapped so that equal hashes mean equal prefixes; no text (files fetched 2026-10-08). Conversation and tool-and-agent are each "sampled from one hour of online request data"; synthetic is built from public datasets with Poisson arrivals.

Is the replay right? vLLM v0.31.0's real KVCacheManager (commit db9527a, Python only, no model) was fed the first 3,000 requests of two traces, with prompt token ids synthesised from the block hashes (equal hashes, equal tokens) and a block size of 512: prefix lookup, allocation, free, at three cache sizes. A re-implementation of vLLM's rules (only full blocks cached, the lookup stops one token short of the prompt, tail-first free order) gave the same hit count every time; this replay's LRU, which also caches each prompt's partial last block, lands within 1.7%.

What the replay leaves out. Time and concurrency: requests are replayed one after another, as Mooncake's own analysis does ("we consider only the sequence of requests"), so blocks of running requests are not pinned and nothing is evicted mid-request. Generated tokens: the traces hash prompts only, so blocks written during decoding are never cached here; a real engine caches them too, which helps multi-turn chat. One cache: one pool, as if every request reached the same replica; several replicas need routing that sends a conversation back to its cache ({{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}). Block size: 512-token blocks, as hashed in the traces, against vLLM's 16.

SGLang v0.5.21 evicts leaves no running request holds ({{radix_cache.py evict L553|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/mem_cache/radix_cache.py#L553}}); --radix-eviction-policy takes lru (the default), lfu, slru, priority or tlru ({{arg_groups/fields/memory.py|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/arg_groups/fields/memory.py}}, {{choices.py L184|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/arg_groups/choices.py#L184}}). Its newest, tail-optimized LRU, evicts first the parts of conversations that cannot affect tail TTFT; its authors report up to 27.5% lower P90 TTFT than LRU on WildChat conversations ({{Tail-Optimized Caching, arXiv 2510.15152|https://arxiv.org/abs/2510.15152}}, not run here).

A model that edits an early part of its own context loses the cache for everything after the edit. Context Language Models, which rewrite their context as a file, are served with a co-designed Suffix Cache Reuse that the authors report cuts server-side compute by 35% against standard SGLang at matched performance ({{Shao et al., arXiv 2609.37725|https://arxiv.org/abs/2609.37725}}; the abstract does not describe the mechanism).
