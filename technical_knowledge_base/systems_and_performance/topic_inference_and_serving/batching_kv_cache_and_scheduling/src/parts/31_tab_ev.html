Which blocks should a prefix cache keep? This tab replays three hours of real requests from Kimi, Moonshot AI's chat service, through six eviction policies at fifteen cache sizes, then through a GPU tier with a host-memory tier behind it. Every number here is computed by src/evict/evict.py; the replay rules match vLLM's own block pool exactly (section 4).

4. Is the replay right? vLLM's own block pool on the same requests

vLLM v0.31.0's real KVCacheManager (commit db9527a, Python only, no model) was fed the first 3,000 requests of two traces, with prompt token ids synthesised from the block hashes (equal hashes, equal tokens) and a block size of 512: prefix lookup, allocation, free, at three cache sizes. A re-implementation of vLLM's rules (only full blocks cached, the lookup stops one token short of the prompt, tail-first free order) gave the same hit count every time; the lab's LRU, which also caches each prompt's partial last block, lands within 1.7%.

5. What the replay leaves out

  • Time and concurrency. Requests are replayed one after another, as Mooncake's own analysis does ("we consider only the sequence of requests"): blocks of running requests are not pinned, prefill time is not modelled, and nothing is evicted mid-request by other requests.
  • Generated tokens. The traces hash prompts only, so blocks written during decoding are never cached here; a real engine caches them too, which helps multi-turn chat (the next turn's prompt contains the last answer).
  • One cache. One pool, as if every request reached the same replica. Several replicas each with their own cache need routing that sends a conversation back to its cache ({{LLM serving in production|n:3f35c17b0d0d818aa406da1f7a784c62}}).
  • Block size. 512-token blocks, as hashed in the traces, against vLLM's 16: finer blocks can match partial prefixes the traces cannot show.
