2. Paging: where the memory went, and how blocks got it back

The problem. Kwon et al. measured systems that store each request's cache in one contiguous region, sized when the request is admitted, and found that only 20.4% to 38.2% of the cache memory held actual tokens ({{PagedAttention, SOSP 2023, Fig. 2|https://arxiv.org/abs/2309.06180}}). They named three kinds of waste ({{same paper, Fig. 3|https://arxiv.org/abs/2309.06180}}):

  • Reservation: slots kept for tokens the request will generate later. They will be used, but nobody else can use them meanwhile.
  • Internal fragmentation: slots reserved that will never be used, because the answer ends before the reservation does.
  • External fragmentation: gaps between reservations, too small for the next request (the memory allocator's leftovers).

How paging works. PagedAttention borrows virtual memory from operating systems. The cache is a pool of fixed-size blocks (16 tokens in vLLM by default, {{vllm/config/cache.py L71|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/cache.py#L71}}); each request has a block table mapping its token positions to blocks anywhere in the pool; a new block is taken only when the last one fills. Reservation and external fragmentation disappear (all blocks are the same size and none is held in advance) and internal fragmentation shrinks to the unfilled tail of each request's last block: on average half a block, 8 tokens. The cost is an indirection inside the attention kernel, which reads keys and values through the table instead of from one contiguous array. Kwon et al. report 2 to 4 times the throughput of FasterTransformer and their Orca at the same latency (their measurement, 2023), and their vLLM held 96.3% token states in the same experiment.

How much contiguous allocation wastes depends on the traffic, so here it is on real traffic: the prompt and answer lengths of Kimi's production traces (section 3 introduces them), time-averaged over each request's answer.

Two lessons from the two charts. First, the waste is mostly reservation for answers that never come: these traces have long prompts (12,035 tokens on average in the conversation trace) and short answers (343), so even an oracle wastes little, while reserving 16,384 output tokens leaves under half the memory holding tokens. Short prompts with a large max_tokens, as in PagedAttention's experiment, are the worst case. Second, block size barely matters for waste until blocks get large: at 16 tokens the last-block waste is 0.06% here; at 2,048 tokens it is 7%.

Choosing a block size

Smaller blocks waste less but make the block table longer and each memory read smaller; larger blocks read more efficiently but waste more and share less, since a prefix can only be shared in whole blocks. Kwon et al. found 16 to 128 tokens best on ShareGPT and 16 or 32 on Alpaca's short sequences, and chose 16 as vLLM's default ({{PagedAttention section 7.2|https://arxiv.org/abs/2309.06180}}). Small blocks also made their swap path slow, because each block became a separate small PCIe copy (section 6). llama.cpp keeps per-token cells in one buffer shared by all slots, and Mooncake hashes its prefixes in 512-token blocks, which is why the traces below come in 512-token units.

Sharing inside one request

Blocks also make sharing cheap. When one request asks for several samples (parallel sampling, n > 1) or runs beam search, the sequences share their prompt's blocks; a block is copied only when a sequence writes into a shared one (copy-on-write, counted with a reference count per block). The authors measured memory savings of 6.1% to 9.8% for parallel sampling and 37.6% to 55.2% for beam search on Alpaca, and 16.2% to 30.5% and 44.3% to 66.3% on ShareGPT ({{PagedAttention section 6.3|https://arxiv.org/abs/2309.06180}}, their measurement). The same reference counts are what makes sharing across requests possible: prefix caching, next.

Cost, when it matters, how to check

Cost: the block-table indirection in the attention kernel, and kernels that must handle scattered blocks (the {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}} page covers paged attention kernels). When it matters: always on a shared server; it decides how many requests fit. How to check: vLLM exports vllm:kv_cache_usage_perc ({{vllm/v1/metrics/loggers.py L577|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/metrics/loggers.py#L577}}); compare it with the tokens your running requests actually hold.
