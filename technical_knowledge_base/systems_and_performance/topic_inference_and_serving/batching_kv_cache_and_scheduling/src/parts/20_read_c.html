2. Paging: where the memory went, and how blocks got it back

Kwon et al. found that systems storing each request's cache in one contiguous region, sized at admission, had only 20.4% to 38.2% of cache memory holding tokens ({{PagedAttention, SOSP 2023, Fig. 2|https://arxiv.org/abs/2309.06180}}). The rest was three kinds of waste ({{same paper, Fig. 3|https://arxiv.org/abs/2309.06180}}): reservation, slots kept for tokens not yet written; internal fragmentation, reserved slots never used because the answer ended early; external fragmentation, gaps between reservations too small for the next request. Predict: of 48 slots, how many hold tokens once two requests are admitted with max_tokens 16?

  1. Three requests, 48 free slots. A (5-token prompt), B (7) and C (6); each may write max_tokens = 16 more, so a contiguous scheme reserves prompt + 16 slots in one piece.
  2. A and B reserve 21 and 23 slots. Prompts fill 12; 32 are held for answers that may never come (reservation); 4 remain.
  3. C must wait. It needs 22 contiguous slots; memory holding 12 tokens turns it away.
  4. Three decode steps: A ends. A stopped at 8 of its 21 slots: 13 reserved for nothing (internal fragmentation, red). B holds 10 of 23.
  5. A is released, C still waits. 25 slots are free, but in pieces of 21 and 4 (external fragmentation).
  6. B ends after 9 answer tokens. 7 of its 23 slots were never used; only now does C start, five steps late. At the peak, 18 tokens filled 44 slots taken: 41%.
  1. 12 blocks of 4 slots. Nothing is reserved: a request takes a block only when its last one is full.
  2. A and B take 2 blocks each. A fills blocks 0 and 1, B blocks 2 and 3: 16 slots taken, 12 hold tokens.
  3. C is admitted at once. Blocks 4 and 5: three requests run where contiguous ran two.
  4. Three decode steps: A ends. B and C took blocks 6 and 7; the only waste is each unfilled last block: 5 slots.
  5. A's blocks return to the free list. Their contents stay until the next owner overwrites them. With prefix caching they stay cached until needed (section 3).
  6. B and C end. B's table is 2, 3, 6, 8, scattered; the attention kernel follows it. At the peak, 27 tokens filled 32 slots taken: 84%.

How paging works. PagedAttention borrows virtual memory from operating systems: the cache is a pool of fixed-size blocks (16 tokens in vLLM by default, {{vllm/config/cache.py L71|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/cache.py#L71}}), and each request's block table maps its positions to blocks anywhere in the pool. Reservation and external fragmentation disappear; internal fragmentation shrinks to each request's last block, on average half a block, 8 tokens. The cost is an indirection: the attention kernel reads keys and values through the table. Freed blocks are not cleared, which is standard and saves time: the next owner overwrites them. So the block tables are the only isolation between users, and a request that attends over blocks it never wrote answers from other users' keys and values. That happened in production in 2026 on a disaggregated SGLang deployment, where a refused request still reached decode ({{Cloudflare's KV cache exposure|n:4255c17b0d0d81daaaedd7f7c98e621f}}; the handoff side is on {{Distributed and disaggregated serving|n:3c65c17b0d0d8170bd7cdf47af0ec07b}}, section 6).

Sharing. Several samples of one request (n > 1) or beam search share their prompt's blocks, copied only when a sequence writes into a shared one (copy-on-write, with a reference count per block). The same counts allow sharing across requests: prefix caching (section 3).

Fig. 3 is a 40-block pool of 16-token blocks in this page's simulator, which follows vLLM's block pool rules: four requests whose prompts start with the same 32-token system prompt (lengths illustrative, every allocation and hit simulated).

  1. One request, one block table. R1's 62-token prompt (32 system-prompt tokens plus 30 of its own) takes 4 blocks, 0 to 3; only the last is partly filled (14 of 16 slots).
  2. A second request finds the system prompt cached. R2's lookup finds blocks 0 and 1 already hashed, so its table points at them (2 holders each) and only its own 50 tokens take new blocks, 5 to 8. R1 has taken block 4 for its answer.
  3. Shared prefix blocks are counted once. R3 hits blocks 0 and 1 too: 96 system-prompt tokens in three tables, 2 blocks in memory. Its own 20 tokens take blocks 9 and 10.
  4. Answers grow one block at a time, anywhere. R1's table is now 0, 1, 2, 3, 4, 11, 14; R2's ends in 12, R3's in 13: the blocks interleave and the kernel follows each table.
  5. A finished request's blocks stay cached. R1 ends; its full blocks 2, 3, 4 and 11 keep their hashes, cached and free (grey) until needed; its partly filled last block had no hash and is free outright. Blocks 0 and 1 drop to 2 holders.
  6. The next turn reuses the whole history. R4 is R1's next turn, 118 in all: the lookup finds 0 and 1 (shared) and 2, 3, 4, 11 (R1's history), 96 tokens not recomputed; only 22 tokens are computed, into blocks 18 and 19.

Kwon et al. report 2 to 4 times the throughput of FasterTransformer and their Orca at the same latency (their measurement, 2023); their vLLM held 96.3% token states in the same experiment, against 20.4% to 38.2% for the contiguous schemes.

Choosing a block size, copy-on-write savings, and where the kernels and the hardware are covered

Block size. Smaller blocks waste less but make the block table longer and each memory read smaller; larger blocks read more efficiently but waste more and share less, since a prefix can only be shared in whole blocks. Kwon et al. found 16 to 128 tokens best on ShareGPT and 16 or 32 on Alpaca's short sequences, and chose 16 as vLLM's default ({{PagedAttention section 7.2|https://arxiv.org/abs/2309.06180}}). Small blocks also made their swap path slow, because each block became a separate small PCIe copy (section 6). llama.cpp keeps per-token cells in one buffer shared by all slots, and Mooncake hashes its prefixes in 512-token blocks, which is why the traces below come in 512-token units.

Copy-on-write savings (authors' measurement): 6.1% to 9.8% of memory for parallel sampling and 37.6% to 55.2% for beam search on Alpaca, 16.2% to 30.5% and 44.3% to 66.3% on ShareGPT ({{PagedAttention section 6.3|https://arxiv.org/abs/2309.06180}}).
