2. Paging: where the memory went, and how blocks got it back

Kwon et al. measured systems that store each request's cache in one contiguous region, sized at admission, and found that only 20.4% to 38.2% of the cache memory held actual tokens ({{PagedAttention, SOSP 2023, Fig. 2|https://arxiv.org/abs/2309.06180}}). The rest was three kinds of waste ({{same paper, Fig. 3|https://arxiv.org/abs/2309.06180}}): reservation, slots kept for tokens the request will write later; internal fragmentation, reserved slots never used because the answer ended early; and external fragmentation, gaps between reservations too small for the next request. Predict before you step: of 48 slots, how many will hold tokens once two requests are admitted with max_tokens 16?

  1. Three requests, 48 free slots. A (5-token prompt), B (7) and C (6) will arrive. Each may write up to max_tokens = 16 more tokens, so a contiguous scheme reserves prompt + 16 slots in one piece.
  2. A and B reserve 21 and 23 slots. Their prompts fill 12 slots; the other 32 are held for answers that may never come (reservation). 4 slots remain.
  3. C arrives and must wait. C needs 22 contiguous slots and only 4 are free. Memory holding 12 tokens turns a request away.
  4. Three decode steps: A ends. A wrote its 3 answer tokens and stopped at 8 of its 21 slots: 13 were reserved for nothing (internal fragmentation, red). B holds 10 of 23.
  5. A is released, C still waits. 25 slots are free, but in two pieces of 21 and 4, and C needs 22 in one piece (external fragmentation).
  6. B ends after 9 answer tokens. B used 16 of its 23 slots; 7 were never used. Only now can C start, five steps late. At the peak, 18 tokens filled 44 slots taken: 41%.
  1. Three requests, 12 blocks of 4 slots. The same requests. Nothing is reserved for answers: a request takes a block only when its last block is full.
  2. A and B take 2 blocks each. A's 5 prompt tokens fill blocks 0 and 1 (one slot of the second), B's 7 fill blocks 2 and 3. 16 slots taken, 12 hold tokens.
  3. C arrives and is admitted at once. C's 6 tokens take blocks 4 and 5. Three requests run where the contiguous scheme ran two.
  4. Three decode steps: A ends. A filled its second block; B and C each needed a third and took blocks 6 and 7 from the free list. The only waste is each request's unfilled last block: 5 slots.
  5. A's blocks go back to the free list. Blocks 0 and 1 are free again; with prefix caching they stay cached until the space is needed (section 3).
  6. B and C end. B needed a fourth block and took block 8: its block table is 2, 3, 6, 8, scattered, and the attention kernel follows it. At the peak, 27 tokens filled 32 slots taken: 84%.

How paging works. PagedAttention borrows virtual memory from operating systems. The cache is a pool of fixed-size blocks (16 tokens in vLLM by default, {{vllm/config/cache.py L71|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/cache.py#L71}}); each request has a block table mapping its token positions to blocks anywhere in the pool, and takes a new block only when its last one fills. Reservation and external fragmentation disappear, and internal fragmentation shrinks to the unfilled tail of each request's last block: on average half a block, 8 tokens. The cost is an indirection inside the attention kernel, which reads keys and values through the table instead of from one contiguous array.

Sharing. Blocks also make sharing cheap. When one request asks for several samples (n > 1) or runs beam search, the sequences share their prompt's blocks, and a block is copied only when a sequence writes into a shared one (copy-on-write, counted with a reference count per block). The same reference counts make sharing across requests possible: prefix caching, the next section, and the last steps of Fig. 3.

Fig. 3 is a 40-block pool of 16-token blocks in this page's simulator, which follows vLLM's block pool rules: four requests whose prompts start with the same 32-token system prompt (lengths illustrative, every allocation and hit simulated).

  1. One request, one block table. R1's 62-token prompt (the 32-token system prompt plus 30 of its own) takes 4 blocks from the free queue; its block table lists them, 0 to 3, and only the last is partly filled (14 of 16 slots).
  2. A second request finds the system prompt cached. R2 starts with the same 32 tokens: the lookup finds blocks 0 and 1 already hashed, so its table points at them (each block now counts 2 holders) and only its own 50 tokens take new blocks, 5 to 8. R1 has meanwhile taken block 4 for its answer.
  3. Shared prefix blocks are counted once. R3 hits blocks 0 and 1 too: three requests, 96 system-prompt tokens in their tables, 2 blocks in memory, each counting 3 holders. Its own 20 tokens take blocks 9 and 10.
  4. Answers grow one block at a time, anywhere. Each request takes a new block only when its last one fills, from wherever the free queue points: R1's table is now 0, 1, 2, 3, 4, 11, 14; R2's ends in 12, R3's in 13. The blocks interleave and the attention kernel follows each table; the only waste is each request's partly filled last block.
  5. A finished request's blocks stay cached. R1 ends. Its own full blocks 2, 3, 4 and 11 keep their hashes and sit in the free queue, cached and free (grey) until the space is needed; its partly filled last block had no hash and is free outright. Blocks 0 and 1 drop to 2 holders.
  6. The next turn reuses the whole history. R4 is R1's next turn: R1's prompt and answer plus 16 new tokens, 118 in all. The lookup finds 6 blocks, 0 and 1 (still shared) and 2, 3, 4, 11 (R1's history): 96 tokens not recomputed. Only 22 tokens are computed, into blocks 18 and 19.

Choosing a block size, copy-on-write savings, and where the kernels and the hardware are covered

Block size. Smaller blocks waste less but make the block table longer and each memory read smaller; larger blocks read more efficiently but waste more and share less, since a prefix can only be shared in whole blocks. Kwon et al. found 16 to 128 tokens best on ShareGPT and 16 or 32 on Alpaca's short sequences, and chose 16 as vLLM's default ({{PagedAttention section 7.2|https://arxiv.org/abs/2309.06180}}). Small blocks also made their swap path slow, because each block became a separate small PCIe copy (section 6). llama.cpp keeps per-token cells in one buffer shared by all slots, and Mooncake hashes its prefixes in 512-token blocks, which is why the traces below come in 512-token units.

Copy-on-write savings (authors' measurement): 6.1% to 9.8% of memory for parallel sampling and 37.6% to 55.2% for beam search on Alpaca, 16.2% to 30.5% and 44.3% to 66.3% on ShareGPT ({{PagedAttention section 6.3|https://arxiv.org/abs/2309.06180}}).
