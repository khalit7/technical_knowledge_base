7. Priority, fairness and SLOs: who goes next

The problem. When the server is full, the order of the waiting queue decides who waits. First come, first served (FCFS, every engine's default) is fair per request, not per user: one client that sends a flood of requests puts everyone else behind it (head-of-line blocking), and one very long job can hold up many short ones. Three families of answers, from simplest to subtlest:

Priority classes

Each request carries a number; the scheduler serves the best number first. In vLLM v0.31.0 (--scheduling-policy priority, field priority on the request), lower values go first, ties by arrival time and then by request id ({{vllm/v1/request.py Request.__lt__|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/request.py}}); when memory runs out, the victim is the running request with the largest priority value, then the latest arrival ({{scheduler.py L764|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/core/sched/scheduler.py#L764}}). A waiting high-priority request does not evict running ones to get in: it waits for space. SGLang (--enable-priority-scheduling, off by default) serves higher values first by default and lets an arriving request preempt running ones whose priority is at least 10 worse (--priority-scheduling-preemption-threshold, {{arg_groups/fields/schedule.py|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/arg_groups/fields/schedule.py}}). Checked here: the parent's simulator, extended with vLLM's priority rules, made the same decisions as vLLM's own Scheduler class at every step of eight two-client traces (four with priorities, four first come first served; 2,256 steps, 79 preemptions); matching it needed one detail, that vLLM breaks priority-and-arrival ties by comparing request ids as strings, so request "10" goes before request "2" ({{Scheduling lab|#t-sch}}, section 5).

Fairness between clients: the Virtual Token Counter

Priorities need someone to assign them and can starve the low class. Sheng et al. define fair service for LLMs by counting tokens, with output tokens weighted more because they cost more (w_p = 1 per prompt token, w_q = 2 per output token, following OpenAI's prices at the time) and propose the Virtual Token Counter (VTC): keep one counter per client; when there is room, admit the earliest request of the client with the smallest counter; add wp × prompt tokens when a request is admitted and wq per generated token; when a client (re)joins the queue, lift its counter to the smallest counter among waiting clients, so idle time cannot be banked. They prove that two clients who both have work waiting never differ in service by more than 2 × max(wp × longest prompt, wq × largest batch of output tokens) ({{Fairness in Serving Large Language Models, OSDI 2024|https://arxiv.org/abs/2401.00588}}, Algorithm 2 and Theorem 4.4). The usual alternative, a requests-per-minute limit per client, wastes capacity when other clients are idle.

Shortest job first

Serving short jobs first minimises mean waiting time, a classic result; the catch is that an answer's length is unknown until it ends. Systems approximate it by predicting lengths: learning to rank them (its authors report 2.8 times lower latency for chatbot serving, {{Fu et al. 2024|https://arxiv.org/abs/2408.15792}}) or a multi-level feedback queue that demotes long-running jobs (FastServe, {{Wu et al. 2023|https://arxiv.org/abs/2305.05920}}). The simulator with perfect knowledge (an oracle) shows what is at stake: below capacity nothing changes, because no queue forms; at 46 requests per second, beyond the server's capacity, mean TTFT falls from 2.25 s to 1.47 s, but p99 TTFT rises from 5.1 s to 26.8 s, and the longest answers' p99 latency from 15.7 s to 36.9 s ({{Scheduling lab|#t-sch}}, section 3, derived). Shortest-first trades the tail for the mean.

SLOs and goodput

Every policy above is a guess at what users want. An SLO (service level objective) states it: for example p99 TTFT under 2 s and TPOT under 100 ms, MLPerf's targets for Llama 3.1 8B. DistServe defines goodput as "the maximum request rate that can be served adhering to the SLO attainment goal (say, 90%) for each GPU provisioned" ({{DistServe, section 1|https://arxiv.org/abs/2401.09670}}); simulators, the parent's included, often report the simpler per-second count of requests that met both targets. SLO-aware schedulers order and admit requests by deadline, and under overload reject early rather than serve everyone late: Mooncake's scheduler predicts load and rejects requests it cannot serve in time ({{Mooncake|https://arxiv.org/abs/2407.00079}}). SGLang also ships cache-aware orders: --schedule-policy takes fcfs (the default), lpm (longest cached prefix first), dfs-weight, lof, random, priority, routing-key, hrrn and shortest-prefill-first ({{arg_groups/fields/schedule.py|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/arg_groups/fields/schedule.py}}); the {{SGLang page|n:3c65c17b0d0d81e691e4ce9f9b5d1fad}} measures why ordering by cache hits matters.

Cost, when it matters, how to check

Cost: any reordering makes someone wait longer; strict priority and shortest-first can starve. When it matters: only when a queue forms, that is near or beyond capacity, and with several tenants or very mixed request sizes. How to check: TTFT percentiles per tenant and per priority class (tag requests and split your metrics), and vllm:request_queue_time_seconds for time spent waiting.
