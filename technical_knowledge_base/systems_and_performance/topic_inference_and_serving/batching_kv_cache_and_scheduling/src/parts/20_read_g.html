6. Preemption: taking memory back from a running request

The problem. Nobody knows an answer's length in advance. vLLM admits a request when its prompt fits in free blocks (it reserves nothing for the answer, section 2), so at some step a running request needs one more block and there is none. The engine must take memory from someone: preemption. There are three answers to "who" and two to "what happens to their cache".

Recompute or swap

Swapping copies the victim's blocks to host memory and back: 2 × KV bytes / link bandwidth per token. Recomputing runs its prefill again: about 0.21 ms per token for the running example. With 320 KiB per token over PCIe Gen5 at 64 GB/s each way, a swap costs about 10 µs per token, twenty times cheaper in time (the section 4 calculator, doubled). So why did vLLM keep only recompute?

  • The measured difference was small. Kwon et al. found swapping slow with small blocks (many tiny PCIe copies), recomputing constant, and the two "comparable end-to-end" for blocks of 16 to 64 tokens; "recomputation overhead is never higher than 20% of swapping's latency" ({{PagedAttention section 7.3|https://arxiv.org/abs/2309.06180}}, their measurement on A100s).
  • Recompute uses idle arithmetic. Decode steps are memory-bound; a recomputed prefix rides in the token budget like any prompt chunk (section 5).
  • Swap is machinery: a host block allocator, copies on the critical path, and memory bounded by the GPU cache size.
  • The offload tier does it anyway. With --kv-offloading-size set, the OffloadingConnector writes blocks to host memory as they are computed and flushes the pending writes of a preempted request ({{offloading/scheduler.py L1787|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py#L1787}}); when the request is scheduled again its prefix is found in host memory and loaded rather than recomputed. Recompute-only preemption plus a CPU tier behaves like a write-through swap. (Read in source, not run here.)

On the simulated H100 with a deliberately small cache (2,000 blocks of 16 tokens, Llama 3.1 8B in BF16, 6 requests per second), recompute and swap at 25 GB/s differ by 3% in throughput (2,364 against 2,430 tokens per second) with the same 146 preemptions; a slow 6 GB/s link makes swap the worse one (2,287). The bigger effect is admission: reserving every request's maximum length, TensorRT-LLM's default rule, removes all preemptions but serves 1,785 tokens per second with a p99 TTFT of 31.25 s, against 12.61 s for optimistic admission ({{Scheduling lab|#t-sch}}, section 4, derived). Measured here, vLLM's CPU backend with a 9,344-token cache reached 100% cache use and 8 preemptions at 16 users, and its output fell from 26.5 to 15.6 tokens per second between 8 and 16 users ({{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}): preemption is the symptom of admitting more than fits.

Cost, when it matters, how to check

Cost: the victim's work is thrown away (recompute) or copied twice (swap), and the victim's latency jumps. When it matters: long answers, large max_tokens, high concurrency on a small cache. How to check: vllm:num_preemptions ({{loggers.py L677|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/metrics/loggers.py#L677}}) rising while vllm:kv_cache_usage_perc sits at 1.0. The fixes, in order: a smaller max_num_seqs, a lower max_tokens, a quantized cache (FP8 halves it), more GPUs.
