KV compression papers drop most of a prompt's cache entries and report that quality survives. Two questions decide whether that helps a server: does a clever importance score beat dropping entries at random, and can a paged engine actually reclaim the memory? This tab answers both on a real model, run here.

The experiment
measured here: Qwen/Qwen3-0.6B (safetensors @ c1899de2, BF16 weights run in float32), PyTorch 2.14.1 and transformers 5.19.0 on the M1 Pro's CPU with 2 threads, eager attention so the attention weights can be read, greedy decoding; script src/kvc/kvc.py. Protocol, identical for every policy: prefill the prompt except its last token with the full cache, keep a share of the "compressible" positions (Task A: the 60 lines of context, about 800 tokens; Task B: the first 992 of 1,024 context tokens), always keep the rest (the question; the last 32 tokens), then continue. Task A: 60 lists of "The secret code of the <noun> is <4 digits>." and a question about one line; correct if the first four digits generated match. Task B: 24 windows of WikiText-2 test; perplexity of the next 128 tokens. Random policies were run with three seeds (mean shown, range in brackets). Policies: random over all positions; the first 4 tokens plus random (shared, or per layer and head); the first 4 plus the most recent (StreamingLLM); accumulated attention per head (H2O); attention from the observation window per head, max-pooled over 7 positions (SnapKV); the same score summed over all heads and layers, one shared selection. Wall time 27 min for Task A, 6 min for Task B.

2. What a paged engine could free

"Selection" says whether every layer and head keeps the same positions. A paged engine stores all heads of all layers of 16 tokens in one block (vLLM), so a block is free only when no layer and no head keeps any of its 16 tokens: the "freeable in place" column. A uniform selection can also be compacted (the kept tokens rewritten into fewer blocks; their positions are already baked into the keys by RoPE), which realises the full saving; a per-head or per-layer selection cannot without a per-head cache layout. Eviction after a full prefill never lowers the peak: the whole prompt's cache existed first.

4. Reading the result, and what does not transfer

  • Sinks first. Dropping the first tokens wrecks the model (perplexity in the hundreds), which is why every sensible policy keeps them and why a fair random control must too.
  • The task decides the winner. On continuation, heavy hitters (H2O) lose least; on retrieval, a question-aware score (SnapKV) is the only thing that works, and the shared version beats the per-head one here. Random with sinks is a fair floor on continuation and useless on retrieval.
  • Realisable is a separate axis. The per-head methods that score well on continuation free nothing in a paged engine; the shared selection frees memory but scores worse on continuation. A paper's memory figure must say which kind it is.
  • Not transferable: absolute numbers (tiny model, short contexts, CPU), anything about speed (not measured: eager attention on a CPU), and long-context behaviour, where eviction matters most.
