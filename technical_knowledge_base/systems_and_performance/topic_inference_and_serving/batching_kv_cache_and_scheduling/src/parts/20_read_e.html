4. Offload tiers: a bigger, slower cache behind the GPU

The problem. The GPU holds very few reusable prefixes. In the running example one H200 has about 54 GB for its cache, 164,800 tokens at 320 KiB each: about 320 of Mooncake's 512-token blocks. On the conversation trace, an LRU cache of 256 blocks hits 4.2% of blocks; an unlimited one would hit 36.6%. The data that could be reused does not fit, and the cheapest place to put it is the server's own DRAM (often 1 to 2 TB per 8-GPU server), then local SSDs, then other servers' memory over the network.

Reload or recompute?

A tier is worth having when reading a block back is faster than recomputing it. Recomputing costs a prefill; reloading costs the block's bytes divided by the link's bandwidth. Per token:

reload / recompute = (KV bytes per token / link bandwidth) ÷ (prefill time per token)
KV bytes
320 KiB for Llama 3.1 70B in BF16 cache (section 0)
link
host memory over PCIe Gen5 x16: 64 GB/s each way (PCIe 5.0 x16 is 128 GB/s counting both directions, as AMD's MI300X data sheet does; {{Topic: hardware|n:3c65c17b0d0d8118beeefaed56da6f8e}}); GH200's NVLink-C2C: 900 GB/s ({{NVIDIA|https://www.nvidia.com/en-us/data-center/grace-hopper-superchip/}}); one 400 Gb/s network card: 50 GB/s
prefill
0.21 ms per token for the running example alone on an H200 (2,000 tokens in 423.5 ms, the parent's planner)

Reload a cached prefix, or compute it again?

For every model here the link wins by a wide margin over PCIe and the network, and even an SSD read beats recomputing on a datacenter GPU. Recompute only competes where prefill is very fast relative to the cache's size: small models, or links shared by many GPUs at once. Two things the formula leaves out push the same way: prefill attention grows with the square of the prefix, so long prefixes favour reloading more, and engines overlap loading with other requests' compute (CachedAttention loads layer by layer while earlier layers run; its authors report up to 87% lower TTFT for multi-turn conversations, {{Gao et al., USENIX ATC 2024|https://arxiv.org/abs/2403.19708}}, their measurement).

How much a host-memory tier adds, on real traffic

The {{Eviction lab|#t-ev}} replays the Mooncake traces through a GPU tier with LRU in front of a host tier with LRU: a block evicted from the GPU moves to host memory; a host hit is copied back. For the running example's sizes (256 blocks on the GPU, 43 GB; 4,096 in host memory, 687 GB at 160 MiB per block): trace

  • Conversation: 4.2% of blocks hit on the GPU, plus 5.1% from host memory. A pooled tier of 65,536 blocks (about 11 TB, many servers' DRAM, as Mooncake's store pools it) adds 31.8%, reaching 36.0% of the 36.6% possible.
  • Tool and agent: 33.2% on the GPU (a few tool prompts are reused all the time), plus 4.5% from host memory.
  • Synthetic (public datasets, long documents): 2.4% on the GPU, plus 22.8% from host memory.

Mooncake's authors reached the same conclusion from the same traces: a local cache of 3 million tokens per node gets under half of the possible hit rate on most workloads, while 50 million tokens, pooled from at least 20 nodes' DRAM, gets nearly all of it ({{Mooncake, FAST 2025, section 5.3.1|https://github.com/kvcache-ai/Mooncake/blob/main/FAST25-release/Mooncake-FAST25.pdf}}).

Where one conversation's cache comes back from, measured on llama-server

Measured here with one slot (Qwen3-1.7B, a 5,010-token conversation whose cache is 575 MB): computing it from scratch took 5.63 s to the first token; while the slot still held it, 23 ms. After another conversation had taken the slot, bringing it back from the host prompt cache took 113 to 421 ms over three runs, a time that includes saving the other conversation's 575 MB and loading this one's; with the prompt cache turned off (--cache-ram 0) it was recomputed in 5.64 s. Saving the slot to a file took 0.54 to 0.67 s and restoring it 75 to 79 ms, after which the first token came in 27 to 35 ms; that read was probably served from the operating system's file cache, since the file had just been written. The M1's memory is shared by CPU and GPU, so "host" here is another region of the same DRAM and the copy costs memory bandwidth, not PCIe. Reloading was 13 to 50 times faster than recomputing, as the calculator above predicts for a small model on a slow GPU.

Cost, when it matters, how to check

Cost: host memory, PCIe or network bandwidth that other traffic also wants, a second eviction policy, and the write traffic of storing blocks that may never be read. When it matters: multi-turn and agent traffic whose reuse distance exceeds GPU capacity: the trace replays above show it is most of the reuse on conversations. How to check: vLLM counts connector hits as vllm:external_prefix_cache_hits and vllm:external_prefix_cache_queries ({{loggers.py L636|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/metrics/loggers.py#L636}}); compare TTFT on host hits with TTFT on misses.
