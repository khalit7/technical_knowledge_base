1. Continuous batching: one step, any mix of requests

The problem. Before 2022, servers batched whole requests: take B requests, run them together until the longest answer ends, then take the next B. Finished requests leave empty seats and new arrivals wait for the whole batch (the parent's {{Serving simulator|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} tab animates this in its section 1). The fix has two halves, both from one paper, Orca ({{Yu et al., OSDI 2022|https://www.usenix.org/conference/osdi22/presentation/yu}}):

  • Iteration-level scheduling: the scheduler hands the engine one iteration (one step) at a time and gets control back after each, so a finished request can leave and a new one can join between any two steps.
  • Selective batching: the trick that makes any mix of requests runnable as one step. Most of a transformer layer (the matrix multiplications, normalisation, activation) does not care which request a token belongs to, so all tokens of all requests are stacked into one tall matrix of shape [total tokens, hidden size]. Only attention needs to know: each token may look only at its own request's earlier tokens. Orca splits the stack per request for attention and merges it back.

Orca's own example is four requests in four different states: x1 and x2 are decoding (one new token each, at different positions), x3 arrives with a 2-token prompt and x4 with a 3-token prompt. In a system that batches tensors of shape [batch, length, hidden], these four cannot share a step: the two prompts have different lengths, the two decodes sit at different positions, and prompts and decodes take different numbers of tokens ({{Orca, section 3, "C2"|https://www.usenix.org/system/files/osdi22-yu.pdf}}). "Weight reads" counts how many times the layer's weights stream from memory for this step: the dominant cost of a decode step (the parent's section 1).

What engines do now. The split and merge became one kernel. vLLM's FlashAttention backend takes the flattened tokens plus, for each request, where its queries start (query_start_loc), its total length (seq_lens) and its block table, and calls a variable-length attention kernel once for the whole step ({{vllm/v1/attention/backends/flash_attn.py, FlashAttentionMetadata L520 and flash_attn_varlen_func L1566|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/attention/backends/flash_attn.py#L520}}). That is why prefill chunks and decodes can sit in the same step (section 5), and why the scheduler talks about tokens, not sequences.

The two caps on a step

Every engine bounds a step two ways. In vLLM they are max_num_batched_tokens, the token budget (new tokens computed per step, prefill and decode together), and max_num_seqs, the most requests in one step. In v0.31.0 the API server picks them from the GPU's memory: 8,192 tokens and 1,024 sequences on H100 and H200, 16,384 and 1,024 at 160 GiB or more (B200, MI300X), 2,048 and 256 on smaller GPUs such as an A100, L40S or RTX 5090 ({{engine/arg_utils.py get_batch_defaults, L2858|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/engine/arg_utils.py#L2858}}). llama-server's equivalent of the budget is -b (default 2,048) and of the sequence cap the number of slots -np. SGLang sets its prefill chunk from GPU memory: 2,048 tokens under 20 GB, 4,096 under 80 GB, 8,192 for H100 and H200, 16,384 above 160 GB ({{arg_groups/memory_hook.py, handle_gpu_memory_settings L47|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/arg_groups/memory_hook.py#L47}}).

Predict: a decode step for 64 users on the running example (Llama 3.1 70B FP8 on one H200). Roughly how much longer is it than a step for one user?
About 1.5 times. The step reads 72.66 GB of weights whatever the batch; each extra user adds only its own cache reads and a little arithmetic. The parent's planner gives 21.6 ms for one user and about 33 ms for 64 (46 against 1,930 output tokens per second, {{the parent's section 3|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}), so 64 users cost 1.54 times the time (33.2 ms = 64 / 1,930) for 42 times the tokens. Measured here on a laptop GPU the same curve is flatter: llama-batched-bench with Qwen3-0.6B gave 188 tokens per second for one sequence and 1,320 for 64 (7 times), because each extra sequence costs about 1.2 ms of fixed work per step on this machine ({{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} tab, "Batching").
Cost, when it matters, how to check

Cost. A step lasts as long as its slowest part, so whatever joins a step slows every user in it: a long prompt most of all (section 5). Each request also holds cache memory for as long as it runs, so more concurrency means more memory (section 2). When it matters: any server with more than one user at a time. How to check: sweep concurrency and plot output throughput against TPOT; vLLM's vllm:num_requests_running and vllm:num_requests_waiting gauges show whether the batch is full and requests queue.

One more thing Orca did, and the reason for the next section: to be sure a request could never run out of room mid-answer, its scheduler reserved max_tokens cache slots for every request at admission ({{Orca Algorithm 1, lines 23 to 26|https://www.usenix.org/system/files/osdi22-yu.pdf}}). Most of those slots were never used.
