1. Continuous batching: one step, any mix of requests

Before 2022, servers batched whole requests: take B requests, run them together until the longest answer ends, then take the next B. Finished requests left empty seats and new arrivals waited for the whole batch. Orca ({{Yu et al., OSDI 2022|https://www.usenix.org/conference/osdi22/presentation/yu}}) fixed both with two ideas. The first is iteration-level scheduling: the scheduler hands the engine one step at a time and gets control back after each, so a finished request leaves and a new one joins between any two steps. Fig. 2 runs the same eight requests both ways on four seats in this page's simulator (Llama 3.1 8B FP8 on the calibrated H100 preset; the request lengths are illustrative, every time is simulated).

  1. Eight requests, four seats. Eight requests are queued at once with answers of 60 to 360 tokens; at most four run together (max_num_seqs 4 for the picture). Time runs left to right on one scale for both rows.
  2. Static batching: the batch runs as long as its longest answer. R1 to R4 start together; their prompts are padded to the longest (560 tokens), so the first step takes 33.6 ms, then every step 4.69 ms makes one token per request. R2's 360 tokens set the batch's length: 1.72 s.
  3. Finished requests leave their seats empty. R3 is done at 0.31 s, R1 at 0.59 s, R4 at 1.16 s, but their seats stay held until the whole batch ends (red): 43% of the seat time the first batch holds is idle.
  4. The next batch waits for the whole first one. R5 to R8 start only at 1.72 s; everything is done at 3.16 s, 475 tokens per second, with seats busy 57% of the time.
  5. Continuous batching: a seat is refilled at the next step. The same requests, scheduled one step at a time: when R3 leaves at 0.30 s, R5 takes its seat in the very next step; R6, R7 and R8 follow the same way.
  6. Same work, finished sooner. Everything is done at 1.85 s, 1.30 s sooner: 811 tokens per second against 475, mean completion 1.27 s against 1.77 s, seats busy 96% of the time against 57%.

Seven new tokens, one weight read instead of four: selective batching against tensor batching (Orca's Figure 5 example)

xij is the j-th token of request i; shaded tokens are prompt tokens, plain ones were generated earlier. One square is one token row of hidden size H. "Weight reads" counts how many times the layer's weights stream from memory for this step: the dominant cost of a decode step.

The second idea is selective batching: stack every new token of every request into one matrix of shape [total tokens, hidden size] for the layers that do not care which request a token belongs to (the matrix multiplications, normalisation, activation), and split per request only for attention, where each token may look only at its own request's earlier tokens.

Orca's own example: x1 and x2 are decoding (one new token each, at positions 4 and 2), x3 arrives with a 2-token prompt and x4 with a 3-token prompt. A system that batches [batch, length, hidden] tensors cannot put them in one step ({{Orca, section 3, "C2"|https://www.usenix.org/system/files/osdi22-yu.pdf}}). Step through the same four requests both ways.

  1. The request pool. Four requests in four states. x1 and x2 each need one new token computed (x14, x22) on top of what is cached; x3 and x4 have just arrived with 2- and 3-token prompts. Seven token rows need computing in this step.
  2. Stack every new token. Selective batching stacks the seven rows into one matrix of shape [7, H], with no padding and no batch dimension. Non-attention layers do not care which request a row belongs to.
  3. QKV projection: one read of the weights. The query, key and value projections run once on all seven rows. The weights stream from memory once for the whole step; that is the saving batching is for.
  4. Split for attention. Attention is the only place requests must stay apart: each request's rows attend to its own keys and values, the cached ones (x11 to x13 for x1, x21 for x2) plus those just computed. Orca ran one attention call per request; vLLM now does all four in one variable-length kernel call.
  5. Merge back. The four attention outputs are stacked into [7, H] again.
  6. Output projection and MLP: one more read. The rest of the layer runs on all seven rows at once, again one read of each weight matrix. (Every layer of the model repeats steps 3 to 6.)
  7. Sample one token per request. Only each request's last row produces a token: x15, x23, x33 and x44. x3 and x4 got their first token in the same step that x1 and x2 continued: none of them waited for the others.
  1. The request pool. The same four requests. A system that batches [batch, length, hidden] tensors needs every request in a batch to have the same number of new tokens at the same position.
  2. Group by shape. x3 and x4 have different prompt lengths (2 and 3), x1 and x2 decode at different positions (4 and 2), and prompts and decodes differ in length. No two of them match, so the step falls apart into four separate runs (Orca, section 3, the three cases of challenge C2). Padding to [4, 3, H] would add 5 empty rows and still mix positions.
  3. Run x1 alone. One token row through the whole layer: the weights stream from memory for a single token.
  4. Run x2 alone. Another full read of the weights for one row.
  5. Run x3 alone. A third read, for two rows.
  6. Run x4 alone. A fourth read, for three rows.
  7. Same four tokens, four times the weight traffic. The outputs are the same x15, x23, x33 and x44, after four reads of the weights instead of one. In practice such systems did not even try: they waited until a whole batch finished (static batching).

In today's engines the split and merge are one kernel call: vLLM flattens the step's tokens and passes, per request, where its queries start, its total length and its block table to a variable-length attention kernel. That is why prefill chunks and decodes can share a step (section 5), and why schedulers count tokens, not sequences. Every engine caps a step two ways: the token budget (new tokens per step, prefill and decode together) and the most sequences per step: in vLLM max_num_batched_tokens, 8,192 on an H100 or H200, and max_num_seqs, 1,024.

Predict: a decode step for 64 users on the running example (Llama 3.1 70B FP8 on one H200). Roughly how much longer is it than a step for one user?
About 1.5 times. The step reads 72.66 GB of weights whatever the batch; each extra user adds only its own cache reads and a little arithmetic. The parent's planner gives 21.6 ms for one user and about 33 ms for 64 (46 against 1,930 output tokens per second, {{the parent's Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13#t-plan}}), so 64 users cost 1.54 times the time (33.2 ms = 64 / 1,930) for 42 times the tokens. Measured here on a laptop GPU the same curve is flatter: llama-batched-bench with Qwen3-0.6B gave 188 tokens per second for one sequence and 1,320 for 64 (7 times), because each extra sequence costs about 1.2 ms of fixed work per step on this machine ({{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} tab, "Batching").

Cost and check. A step lasts as long as its slowest part, so whatever joins it slows every user in it, a long prompt most of all (section 5); and every running request holds cache memory, so concurrency is bounded by memory (section 2). Sweep concurrency and plot output throughput against TPOT; vLLM's vllm:num_requests_running and vllm:num_requests_waiting show whether the batch is full and requests queue. One more thing Orca did leads to the next section: so that no request could run out of room mid-answer, it reserved max_tokens cache slots for every request at admission ({{Orca Algorithm 1, lines 23 to 26|https://www.usenix.org/system/files/osdi22-yu.pdf}}). Most were never used.

The kernel and the step caps in source: vLLM, llama-server, SGLang

vLLM's FlashAttention backend takes the flattened tokens plus, for each request, query_start_loc, seq_lens and its block table, and calls a variable-length attention kernel once for the whole step ({{vllm/v1/attention/backends/flash_attn.py, FlashAttentionMetadata L520 and flash_attn_varlen_func L1566|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/attention/backends/flash_attn.py#L520}}).

In v0.31.0 the API server picks the two caps from the GPU's memory: 8,192 tokens and 1,024 sequences on H100 and H200, 16,384 and 1,024 at 160 GiB or more (B200, MI300X), 2,048 and 256 on smaller GPUs such as an A100, L40S or RTX 5090 ({{engine/arg_utils.py get_batch_defaults, L2858|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/engine/arg_utils.py#L2858}}). llama-server's equivalent of the budget is -b (default 2,048) and of the sequence cap the number of slots -np. SGLang sets its prefill chunk from GPU memory: 2,048 tokens under 20 GB, 4,096 under 80 GB, 8,192 for H100 and H200, 16,384 above 160 GB ({{arg_groups/memory_hook.py, handle_gpu_memory_settings L47|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/arg_groups/memory_hook.py#L47}}).
