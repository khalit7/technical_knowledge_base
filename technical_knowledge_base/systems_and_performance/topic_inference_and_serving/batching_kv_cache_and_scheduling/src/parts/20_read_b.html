1. Continuous batching: one step, any mix of requests

Before 2022, servers batched whole requests: run B requests together until the longest answer ends, then take the next B. Orca ({{Yu et al., OSDI 2022|https://www.usenix.org/conference/osdi22/presentation/yu}}) fixed the empty seats and the waiting with two ideas. The first is iteration-level scheduling: the scheduler hands the engine one step at a time and gets control back after each, so requests leave and join between any two steps. Fig. 2 runs eight requests both ways on four seats in this page's simulator (Llama 3.1 8B FP8, calibrated H100 preset; lengths illustrative, times simulated).

  1. Eight requests, four seats. All queued at once, answers of 60 to 360 tokens, at most four running (max_num_seqs 4); one time scale for both rows.
  2. Static: the batch lasts as long as its longest answer. R1 to R4 are padded to the longest (560 tokens) prompt: the first step takes 33.6 ms, then each 4.69 ms step makes one token per request; R2's 360 tokens make it 1.72 s.
  3. Finished requests leave seats empty. R3 is done at 0.31 s, R1 at 0.59 s, R4 at 1.16 s, but their seats stay held (red): 43% of the first batch's seat time is idle.
  4. The next batch waits. R5 to R8 start only at 1.72 s; all done at 3.16 s, 475 tokens per second, seats busy 57%.
  5. Continuous: a seat is refilled at the next step. When R3 leaves at 0.30 s, R5 takes its seat in the very next step; R6 to R8 likewise.
  6. Same work, finished sooner. All done at 1.85 s, 1.30 s sooner: 811 tokens per second against 475, mean completion 1.27 s against 1.77 s, seats busy 96% of the time against 57%.

Seven new tokens, one weight read instead of four: selective batching against tensor batching (Orca's Figure 5 example)

xij is the j-th token of request i; shaded tokens are prompt tokens, plain ones were generated earlier. One square is one token row of hidden size H. "Weight reads" counts how many times the layer's weights stream from memory for this step: the dominant cost of a decode step.

The second idea is selective batching: stack every new token of every request into one [total tokens, hidden size] matrix for the layers that ignore which request a token belongs to (matrix multiplications, normalisation, activation), and split per request only for attention. Orca's example: x1 and x2 decode (one new token each, at positions 4 and 2), x3 and x4 arrive with 2- and 3-token prompts; a system batching [batch, length, hidden] tensors cannot put them in one step ({{Orca, section 3, "C2"|https://www.usenix.org/system/files/osdi22-yu.pdf}}).

  1. The request pool. x1 and x2 need one new token each (x14, x22) on top of their cache; x3 and x4 bring 2- and 3-token prompts: seven token rows to compute.
  2. Stack every new token. One [7, H] matrix, no padding, no batch dimension.
  3. QKV projection: one read of the weights. The projections run once on all seven rows, so the weights stream from memory once for the step: the saving batching is for.
  4. Split for attention. Each request's rows attend only to its own keys and values, cached (x11 to x13 for x1, x21 for x2) and new. Orca ran one attention call per request; vLLM does all four in one variable-length kernel call.
  5. Merge back. The four outputs are stacked into [7, H] again.
  6. Output projection and MLP: one more read. Again one read of each weight matrix for all seven rows. (Every layer repeats steps 3 to 6.)
  7. Sample one token per request. Each request's last row gives x15, x23, x33 and x44: x3 and x4 got their first token in the step that x1 and x2 continued, nobody waited.
  1. The request pool. A tensor batch needs equal new-token counts at equal positions.
  2. Group by shape. No two match (Orca's three cases of challenge C2); padding to [4, 3, H] adds 5 empty rows and still mixes positions.
  3. Run x1 alone: a weight read for one row.
  4. Run x2 alone: a second read.
  5. Run x3 alone: a third, two rows.
  6. Run x4 alone: a fourth, three rows.
  7. Four times the weight traffic. In practice such systems waited for whole batches (static batching).

Because split and merge are one variable-length kernel call (closed block), prefill chunks and decodes can share a step (section 5) and schedulers count tokens, not sequences. Every engine caps a step two ways: the token budget (new tokens per step, prefill and decode together) and the most sequences per step; in vLLM max_num_batched_tokens, 8,192 on an H100 or H200, and max_num_seqs, 1,024.

Predict: a decode step for 64 users on the running example (Llama 3.1 70B FP8 on one H200). Roughly how much longer is it than a step for one user?
About 1.5 times. The step reads 72.66 GB of weights whatever the batch; each extra user adds only its own cache reads and a little arithmetic. The parent's planner gives 21.6 ms for one user and about 33 ms for 64 (46 against 1,930 output tokens per second, {{the parent's Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13#t-plan}}): 1.54 times the time (33.2 ms = 64 / 1,930) for 42 times the tokens. Measured here on a laptop GPU the curve is flatter: llama-batched-bench with Qwen3-0.6B gave 188 tokens per second for one sequence and 1,320 for 64 (7 times), since each extra sequence costs about 1.2 ms of fixed work per step ({{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} tab, "Batching").

Cost and check. Whatever joins a step slows every user in it, a long prompt most of all (section 5), and every running request holds cache memory, so memory bounds concurrency (section 2). Sweep concurrency and plot output throughput against TPOT; vllm:num_requests_running and vllm:num_requests_waiting show whether the batch is full and requests queue. Orca also reserved max_tokens cache slots per request at admission, so none could run out mid-answer ({{Orca Algorithm 1, lines 23 to 26|https://www.usenix.org/system/files/osdi22-yu.pdf}}); most were never used, which is where section 2 starts.

The kernel and the step caps in source: vLLM, llama-server, SGLang

vLLM's FlashAttention backend takes the flattened tokens plus, for each request, query_start_loc, seq_lens and its block table, and calls a variable-length attention kernel once for the whole step ({{vllm/v1/attention/backends/flash_attn.py, FlashAttentionMetadata L520 and flash_attn_varlen_func L1566|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/attention/backends/flash_attn.py#L520}}).

In v0.31.0 the API server picks the two caps from the GPU's memory: 8,192 tokens and 1,024 sequences on H100 and H200, 16,384 and 1,024 at 160 GiB or more (B200, MI300X), 2,048 and 256 on smaller GPUs such as an A100, L40S or RTX 5090 ({{engine/arg_utils.py get_batch_defaults, L2858|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/engine/arg_utils.py#L2858}}). llama-server's equivalent of the budget is -b (default 2,048) and of the sequence cap the number of slots -np. SGLang sets its prefill chunk from GPU memory: 2,048 tokens under 20 GB, 4,096 under 80 GB, 8,192 for H100 and H200, 16,384 above 160 GB ({{arg_groups/memory_hook.py, handle_gpu_memory_settings L47|https://github.com/sgl-project/sglang/blob/v0.5.21/python/sglang/srt/arg_groups/memory_hook.py#L47}}).
