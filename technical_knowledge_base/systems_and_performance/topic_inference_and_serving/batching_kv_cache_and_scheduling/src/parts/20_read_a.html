The idea in one sentenceA serving engine is a loop that takes one step every few milliseconds, and at each step decides which requests run, how many of their tokens it computes and where their KV cache lives; continuous batching, paging, prefix caching, offload, chunked prefill, preemption and queue policies are each a rule for one of those three decisions, and each replaced a simpler rule that wasted memory or made users wait.

One step of the running example: a token budget filled from many requests, a cache made of shared blocks

Step t on one H200 serving the running example (below). Top, to scale: the step may compute at most 8,192 new tokens. The 64 requests already answering add 1 decode token each; R7, a new chat turn whose 1,000-token system prompt is already cached, adds its other 1,000 prompt tokens; R8, a 40,000-token document, adds a 7,128-token chunk and will finish its prompt over the next steps; R9 waits because the budget is full. Bottom, schematic (one square stands for many blocks): the KV cache is a pool of 16-token blocks; each request's block table lists its blocks wherever they lie; the system prompt's blocks are stored once and shared by every request; blocks of finished requests stay cached until the space is needed; a host-memory tier catches what the GPU evicts. Step (iteration): one forward pass of the model over every token the scheduler picked.
Prefill / decode: reading a prompt and writing its keys and values / one pass per further output token.
TTFT / TPOT (ITL): time to first token / time per output token (inter-token latency), the two latencies a user feels.
Token budget: the most new tokens one step may compute (vLLM's max_num_batched_tokens).
Block, block table: a fixed slice of cache (16 tokens in vLLM) / a request's list of its blocks.
Prefix hit: a prompt's leading blocks found already cached, so not recomputed.
Preemption: taking cache memory back from a running request.
Goodput: the request rate served while meeting the latency targets.

The running example is the parent page's chat assistant: Llama 3.1 70B with FP8 weights on NVIDIA H200 GPUs, prompts of 2,000 tokens of which 1,000 are a shared system prompt, answers of 300 tokens. Its cache costs 320 KiB per token (2 × 80 layers × 8 KV heads × 128 dimensions × 2 bytes), so one 2,300-token conversation holds 719 MiB and one H200 has room for about 141 of them ({{Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} tab of the parent). The measured examples are small Qwen3 models (0.6B and 1.7B) on the Apple M1 Pro laptop this page was built on, the models the parent's {{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} tab measured. Engine behaviour is read in source at pinned versions: vLLM v0.31.0, SGLang v0.5.21, llama.cpp build 11146.
