A serving engine is a loop. Every few milliseconds it takes one step (also called an iteration): it decides which requests run, how many of their tokens it computes, and where their KV cache lives, then runs the model once over that batch. Everything on this page is a rule for one of those three decisions, and each rule exists because a simpler one broke.

The parent page, {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}, gives the intuition for each mechanism in a few paragraphs. This page goes one level down: what the papers measured, what the engines' code actually does (read at pinned versions: vLLM v0.31.0, SGLang v0.5.21, llama.cpp build 11146), what it costs, and how to check it on your own server. Words used throughout: prefill is the pass that reads a request's whole prompt and writes its keys and values; decode is one pass per further output token; the KV cache is those stored keys and values, one pair per token per layer; TTFT (time to first token) and TPOT or ITL (time per output token, inter-token latency) are the two latencies a user feels.

Which requests
batching, admission, order

Continuous batching re-forms the batch every step (section 1). Admission asks whether the KV cache has room; the order of the waiting queue is a policy: first come first served, priority, fairness, shortest first (section 7).

How many tokens
the token budget

A step carries at most a fixed number of new tokens. Decodes take one each; a long prompt is cut into chunks that fill the rest (chunked prefill, section 5).

Where the KV lives
blocks, tiers, eviction

The cache is cut into fixed blocks (paging, section 2), shared across requests that start the same way (prefix caching, section 3), spilled to slower memory (offload, section 4), taken back from a running request when it runs out (preemption, section 6), or thinned (compression, section 8).

The running example is the parent page's chat assistant: Llama 3.1 70B with FP8 weights on NVIDIA H200 GPUs, prompts of 2,000 tokens of which 1,000 are a shared system prompt, answers of 300 tokens. Its cache costs 320 KiB per token (2 × 80 layers × 8 KV heads × 128 dimensions × 2 bytes), so one 2,300-token conversation holds 719 MiB and one H200 has room for about 141 of them ({{Capacity planner|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} tab of the parent, section 1). The measured examples are small Qwen3 models (0.6B and 1.7B) run on the Apple M1 Pro laptop this page was built on, the same models the parent's {{Engine bench|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} tab measured.
