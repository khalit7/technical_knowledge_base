0. In one screen: what happens when you write torch.mm(x, w)

PyTorch looks like a NumPy that can also compute gradients. Underneath, every line goes through three machines that this page takes apart one at a time. A tensor is a small description (shape, strides, offset, dtype, device) laid over a flat block of memory. The dispatcher is a table lookup that decides, for each call, which pieces of PyTorch get to act on it: mixed precision, gradient recording, view tracking, Python hooks, and finally the kernel that does the arithmetic. Autograd is the part that, while the forward runs, builds a graph of what happened, and then runs that graph backwards to produce gradients.

1. The tensor
header + storage

x is 8 × 256 float32: 8,192 bytes of storage, strides (256, 1). A transpose writes a new header, never moves a byte.

2. The key set
keys of x and w, plus thread state

Every CPU tensor carries CPU, ADInplaceOrView, AutogradCPU, AutocastCPU; the thread switches some on or off.

3. Walk down the keys
Autocast, Autograd, ADInplaceOrView, CPU

Each kernel does its one job and calls the operator again below itself. Autograd records MmBackward0 and keeps x and w for later.

4. Backward
the engine runs the graph

loss.backward() runs each node once its inputs are ready; AccumulateGrad writes w.grad.

1. Tensors: a header over a block of bytes

1.1 Storage, sizes, strides, offset

The problem. Deep learning code reshapes, slices, transposes and splits arrays constantly: attention alone turns one (8, 64, 768) block into q, k and v, each split into 4 heads. If each of those operations copied the data, a forward pass would spend most of its time and memory moving bytes.

How it works. A storage is one flat, untyped block of bytes on one device. A tensor is a header that says how to read it: sizes (the shape), strides (how many elements to skip in storage to move one step along each dimension), a storage offset (where element [0, 0, ...] sits) and a dtype (how many bytes per element and how to read them). The address of any element is a dot product:

address(i, j, …) = offset + i·stride0 + j·stride1 + …
address
position in the storage, in elements (multiply by the element size for bytes)
strided
elements skipped per step along dimension d; 0 means "repeat the same element"

A view is a new header on the same storage. Measured on x = torch.arange(12.).view(3, 4), where every value equals its storage index, so the values printed prove the addresses:

Three rows deserve a second look. x[0:1].expand(3, 4) has stride 0 along rows: three rows, one row of memory (this is how broadcasting avoids copies). x.unfold(1, 2, 1) makes overlapping windows, so some cells are read twice. x.detach() shares the storage but is not a "view" in autograd's sense (_base is None), which matters in section 3.

1.2 Contiguous, view against reshape, and when a copy happens

A tensor is contiguous when reading it in order walks the storage in order with no gaps: strides equal the row-major ones for its shape ((4, 1) for (3, 4)). Most kernels are fastest on contiguous input and some require it. The rules you need:

  • view never copies; it fails if no strides can describe the new shape over the old layout: x.t().view(12) raised
  • reshape returns a view when it can and copies when it cannot: x.reshape(12) shared storage, x.t().reshape(12) did not.
  • .contiguous() copies only when needed. flip, advanced indexing (x[[0, 2]]) and boolean masks always copy (there are no negative strides: ).

1.3 Memory formats: channels_last

For images, a (N, C, H, W) tensor stored row-major keeps each channel's whole image together (NCHW). Convolution kernels on GPUs with tensor cores, and oneDNN on CPUs, prefer the channels of one pixel together (NHWC). PyTorch keeps the logical shape (N, C, H, W) and changes only the strides: that is channels_last, a memory format.

So is_contiguous() answers "row-major?" and says no, while is_contiguous(memory_format=torch.channels_last) says yes. Element-wise ops and convolutions keep the format (measured above); view on it fails like on any non-contiguous tensor. A tensor with C = 1 or H = W = 1 is both at once, which is why format checks are ambiguous on such shapes.

1.4 dtypes and type promotion

A dtype fixes the bytes per element and how to read them: float32 (4 bytes), bfloat16 and float16 (2), int64 (8), bool (1). When an operation mixes dtypes, PyTorch picks the result dtype with type promotion: within the same category (bool < integer < floating < complex) the wider type wins, and when neither type can hold the other, a third one is chosen. 1.5 Devices, copies between them, and pinned memory

A storage lives on one device (cpu, mps, cuda:0), and an operation needs all its tensors on the same device. .to(device) is a copy (an aten::_to_copy call; a no-op if already there). On a GPU that copy crosses a bus, and copying from ordinary ("pageable") host memory makes the driver stage it through a pinned buffer first. Pinned (page-locked) host memory can be read by the GPU's copy engine directly, which is what lets .to("cuda", non_blocking=True) overlap the copy with compute. On this Mac, torch.randn(1024).pin_memory() worked and reported is_pinned() == True, but a DataLoader(pin_memory=True) warned and returned unpinned batches measured on Apple M1 Pro. The overlap itself is a CUDA matter: not run here (no NVIDIA GPU); see Streams, CUDA graphs and multi-GPU.

2. The dispatcher: one table lookup per call

The problem. One operator, say matrix multiply, has to do different things depending on context: cast to bfloat16 under mixed precision, record a graph node when gradients are needed, run on a CPU, an Apple GPU or a CUDA GPU, call back into Python when a tensor subclass or a tracing tool wants to see it, or only compute output shapes when the compiler is tracing. Writing all of that into every one of thousands of kernels is impossible to maintain. PyTorch separates the concerns and lets a table decide which ones apply to each call.

2.1 Operators and their schemas

An operator is a named function in the aten namespace (ATen is PyTorch's C++ tensor library) with a schema: its signature, including which arguments it writes to and which outputs alias an input. The schemas are declared in native_functions.yaml, which at v2.14.1 has - func: entries; the installed wheel registers operators in the aten namespace (more than the YAML entries, because out-variants and functional variants are generated). 2.2 Dispatch keys and their order

A dispatch key names one concern. Keys come in two parts: a functionality (Dense, Autograd, Autocast, Python, ...) and, for some functionalities, a backend bit (CPU, MPS, CUDA, ...). AutogradCPU is the Autograd functionality with the CPU bit. The functionality order is the priority: when several keys apply, the one with the highest number runs first. 2.6 Autocast: mixed precision as a dispatch key

How it works. torch.autocast(device, dtype) removes that device's Autocast key from the excluded set. From then on, every operator reaches the Autocast key first, and for most of them the slot is a fallthrough. Operators on the lower_precision_fp list (matrix multiplies, convolutions, attention, linear) get a kernel that casts their floating-point inputs to the autocast dtype; operators on the fp32 list (losses, norms, reductions that lose accuracy) cast to float32. Weights stay float32: the casts are new tensors each time.

2.7 Functionalization: removing mutation for compilers

The problem. Compilers and graph exporters want pure functions: no in-place writes, no aliasing, so they can reorder and fuse freely. Python code is full of add_, views and x[...] = y. Functionalization is a dispatch key (Functionalize, with a real kernel for aten operators and a boxed fallback for the rest) that wraps tensors and replays every mutation as an out-of-place op, regenerating views from their base. torch.compile's AOTAutograd stage uses it. 3. Autograd: a graph recorded in forward, run by an engine in backward

The problem. Training needs the gradient of one number (the loss) with respect to millions of parameters. The chain rule gives it, if you know every operation that produced the loss and kept what each needs to differentiate. Autograd records exactly that while forward runs (reverse-mode automatic differentiation), so the backward pass costs about as much as a couple of forwards, whatever the number of parameters.

3.1 The graph: nodes, edges, saved tensors

When the autograd kernel of an operator runs with grad mode on and an input that requires grad, it creates a Node (the object you see as y.grad_fn, such as AddmmBackward0) and points the output at it. A node holds three things: edges to the nodes that produced its inputs (next_functions), the saved tensors its formula in derivatives.yaml needs, and a sequence number, a per-thread counter taken at creation. Leaves that require grad (parameters, here also the input x) end in an AccumulateGrad node, whose job is to add the arriving gradient into .grad.

3.2 The engine: dependencies, a ready queue, and one thread per device

Calling loss.backward() hands the graph to the engine (C++, torch/csrc/autograd/engine.cpp). It first counts, for every node reachable from the loss, how many edges point into it (its dependencies). Then it repeatedly takes a node from a ready queue, runs it, adds the gradients it produces into the input buffers of the next nodes, decrements their counts, and pushes each node whose count reaches zero. The ready queue is a priority queue: among ready nodes, the one with the highest sequence number (the one created last in forward) runs first, and AccumulateGrad nodes take the largest possible number so they run as soon as they are ready, freeing the gradient buffer early.

Checked against the record: re-running that rule on the recorded graph (dependencies from the edges, a max-heap on sequence number) reproduces the order the engine actually ran the nodes, recorded with node pre-hooks, in all three variants (plain, checkpointed, with saved-tensor hooks) on the CPU and both variants on MPS measured on Apple M1 Pro. One detail the source leaves open: ties between AccumulateGrad nodes (all at the same maximal number) are broken by the heap; in this record the first pushed always ran first. The Autograd engine tab steps through it node by node with the queue and the counts visible.

    3.4 Version counters and "modified by an inplace operation"

    The problem. A node saved a tensor in forward; if your code then overwrites that tensor in place before backward, the saved value is wrong, and the gradient with it. Copying every saved tensor would cost memory, so PyTorch detects instead. Every in-place write bumps the tensor's version counter (the ADInplaceOrView kernel does it, below the copy itself); a saved tensor remembers the version it had when saved; unpacking it in backward compares the two.

    The Version-counter lab runs fourteen snippets. The summary:

    Two ways to get a wrong gradient with no error, both measured
    Writing through .data (the write is invisible: fresh counter) and installing saved-tensor hooks whose pack keeps a reference (the version check is skipped whenever hooks are installed: line 165 above). In the sigmoid case the correct gradient is ; through .data backward returned . Use .detach(), which shares the counter and gets caught.

    3.5 retain_graph, create_graph and double backward

    Backward frees each node's saved tensors as soon as the node has run, which is why backward's memory falls as it goes. A second backward() through the same graph therefore fails: With retain_graph=True the saved tensors stay, and since gradients accumulate, two backwards on (w**2).sum() at w = [1, 2, 3] gave then .

    create_graph=True goes further: backward itself is recorded, so the gradient is a tensor with its own grad_fn and can be differentiated again. For y = ∑x3 at x = [1, 2, 3]: first gradient (grad_fn MulBackward0, requires grad), second = 6x. Without it the gradient does not require grad and differentiating it fails with the familiar "does not require grad" error. This is how gradient penalties (WGAN-GP, input-gradient regularizers) and Hessian-vector products work. The cost is real: on a small MLP, forward plus one gradient took aten calls; forward, gradient with create_graph, the penalty and its backward took measured, aten calls counted by a dispatch mode.

    3.6 Writing your own backward: torch.autograd.Function

    When you want a different gradient than the one autograd would derive (a numerically safer formula, a fused kernel, a straight-through estimator), subclass torch.autograd.Function. The current style keeps forward free of the context and saves in a separate setup_context, which is what lets the function work with torch.func transforms:

    class MyGelu(torch.autograd.Function): @staticmethod def forward(x): # no ctx here return 0.5 * x * (1 + torch.tanh(0.7978845608 * (x + 0.044715 * x ** 3))) @staticmethod def setup_context(ctx, inputs, output): (x,) = inputs ctx.save_for_backward(x) # goes through SavedVariable: version-checked @staticmethod def backward(ctx, g): (x,) = ctx.saved_tensors u = 0.7978845608 * (x + 0.044715 * x ** 3) t = torch.tanh(u) du = 0.7978845608 * (1 + 3 * 0.044715 * x ** 2) return g * (0.5 * (1 + t) + 0.5 * x * (1 - t ** 2) * du) x = torch.randn(6, dtype=torch.float64, requires_grad=True) torch.autograd.gradcheck(MyGelu.apply, (x,)) # finite differences in float64 torch.autograd.gradgradcheck(MyGelu.apply, (x,)) # its backward is differentiable too

    gradcheck compares your backward with finite differences, column by column of the Jacobian; use float64, or rounding drowns the comparison. A backward that forgets the second term of the product rule fails at once: gradgradcheck does the same for the backward's own gradient. If your backward is written with operations autograd cannot differentiate (an external kernel), decorate it with @once_differentiable: then its output does not require grad and asking for a second derivative fails loudly () instead of silently returning a wrong one. Other context methods: ctx.needs_input_grad (skip work for inputs that need no gradient), ctx.mark_dirty (the forward wrote an input in place), ctx.mark_non_differentiable (integer outputs such as indices). For an operator that must also survive torch.compile and export as a single node, prefer torch.library.custom_op with register_autograd (Extending PyTorch).

    3.7 Anomaly mode: finding the op that made a NaN

    A NaN in a gradient usually comes from one backward formula hitting a singular point. The classic: sqrt at 0 has an infinite derivative, and multiplying by a zero gradient gives 0 × ∞ = NaN.     3.8 Turning gradients off: no_grad, set_grad_enabled, inference_mode

    So: no_grad and set_grad_enabled(False) are the same switch (the second takes a bool, handy for set_grad_enabled(is_train)); enable_grad turns it back on inside; inference_mode also removes the autograd and view-tracking keys (2.3) and produces inference tensors that can never enter autograd later. Use inference_mode for serving and for evaluation whose outputs you never train on; no_grad for anything inside a training loop (EMA updates, metrics on tensors you may reuse).

    3.9 Saved-tensor hooks and activation checkpointing

    The problem. The saved tensors of 3.1 are the activation memory that limits batch size and sequence length. Two tools trade something else for it.

    Saved-tensor hooks (torch.autograd.graph.saved_tensors_hooks(pack, unpack)) intercept every tensor a node saves: pack may return anything (a CPU copy, a compressed version, a file name), and unpack must give the tensor back in backward. torch.autograd.graph.save_on_cpu() is the built-in pair that copies saved tensors to host memory. Activation checkpointing (torch.utils.checkpoint.checkpoint(fn, x, use_reentrant=False)) saves only the region's input and reruns the region during backward when a node first asks for a tensor it did not keep.         Common mistakes

        Assuming .view() after a transpose or permute will work
        It fails whenever the strides cannot describe the new shape; .reshape() works and may copy. Both are measured in 1.2.
        Writing in place into something backward needs
        nn.ReLU(inplace=True) after a sigmoid, x += ... on a saved activation, an optimizer step or EMA update between forward and backward. The version check catches it: "modified by an inplace operation" (3.4).
        Using .data to "get around" autograd
        The write is invisible to the version counter and the gradient comes out wrong without any error (measured in 3.4). Use .detach() or torch.no_grad().
        Thinking no_grad stops version counting, or that it removes keys
        It only tells the autograd kernel not to record; in-place writes still bump counters (1.6) and the autograd key still runs (2.3).
        Returning a tensor made under inference_mode into training code
        "Inference tensors cannot be saved for backward" as soon as an op needs to save it; clone it first or use no_grad (3.8).
        Calling checkpoint without use_reentrant
        At 2.14.1 it still means the reentrant variant: no gradient when no input requires grad, no torch.autograd.grad, full recompute (3.9).
        Ignoring load_state_dict(strict=False)'s return value
        Missing keys keep their random initialization silently (4.2).
        Forgetting tied weights when saving, loading or materializing
        safetensors refuses shared tensors, two values loaded under the two names means the last wins, and to_empty unties them (4.1, 2.8).
        Accumulating gradients without dividing the loss
        The gradient comes out exactly the number of micro-batches times too large (4.4).
        Clipping before unscaling with a GradScaler
        You clip the scaled gradient (65,536 times too large at the default scale) and the threshold means nothing. Call scaler.unscale_(opt) first.
        Assuming torch.manual_seed seeds everything
        It does not seed Python's random or NumPy in the main process (measured in 4.6); DataLoader workers seed all three for you.
        Expecting autocast to make the model bfloat16
        Only the listed ops run in the lower dtype; norms, adds and the loss stay float32, and the weights are re-cast every forward (2.6).
        A custom op without an autograd registration
        The autograd fallback lets backward run with only a warning, and the gradient is wrong (2.4).

        Interview questions, with short answers

        What is the difference between a tensor and a storage? When do two tensors share memory?
        The storage is the bytes on a device; the tensor is sizes, strides, offset and dtype over it. Views (slicing, transpose, view, expand, split) share storage; compare untyped_storage().data_ptr(). flip, advanced indexing and contiguous() on a non-contiguous tensor copy.
        Why can expand make a 1,000 × 1,000 tensor from 1,000 numbers?
        Stride 0 on the expanded dimension: every row reads the same memory. Writing into it in place is an error for that reason.
        Walk through what happens in torch.mm(x, w) with w requiring grad, under autocast.
        Key set = keys of x and w, plus the thread's included set, minus excluded. AutocastCPU runs first (autocast removed its exclusion) and casts both to bf16, then calls mm again with Autocast excluded; AutogradCPU records MmBackward0 saving both inputs and redispatches below autograd; ADInplaceOrView is a fallthrough for mm; the CPU kernel computes. Measured: 2 _to_copy calls and a bf16 mm (Dispatcher walker).
        What do CompositeImplicitAutograd and CompositeExplicitAutograd mean?
        Implicit: the op is written in other ops and gets its gradient from them (no derivative formula, no backend kernel), so it decomposes before autograd records. Explicit: one implementation for all backends, but it needs its own derivative. A backend may override either (MPS registers its own linear).
        no_grad versus inference_mode, mechanically?
        no_grad flips the grad-mode flag; the autograd kernel still runs and records nothing. inference_mode also excludes every autograd key, stops including ADInplaceOrView, and creates inference tensors without version counters, which can never be saved for backward.
        How does the autograd engine decide the order of backward?
        Count dependencies; run ready nodes from a priority queue keyed on sequence number (latest-created first), AccumulateGrad first of all; CPU work on the calling thread, one worker thread per GPU device. Re-running that rule reproduced the recorded order here.
        How does PyTorch detect "modified by an inplace operation"?
        A version counter per storage, shared by views, bumped by every in-place op (ADInplaceOrView kernels); saved tensors record the version at save time and compare at unpack. It is skipped for .data writes and when saved-tensor hooks are installed.
        What does create_graph=True cost and when do you need it?
        It records backward as a graph so you can differentiate the gradient (penalties, Hessian-vector products, meta-learning). It keeps more saved tensors and more ops: 15 against 50 aten calls on a small MLP here.
        Reentrant or non-reentrant checkpointing?
        Non-reentrant: works when inputs do not require grad, works with autograd.grad and keyword args, stops recomputing early (12 of 16 matmuls here). Reentrant is the old default, still the fallback at 2.14.1 if you pass nothing.
        Why does only float16 need a GradScaler?
        float16 has 5 exponent bits: gradients below about 6e-8 vanish (1,636 of 3.19 million here) and the maximum is 65,504. bfloat16 has float32's 8 exponent bits, so its range is the same as float32's.
        Your parameter count from the state_dict is higher than from parameters(). Why?
        Tied (shared) parameters appear once per name in the state_dict: 3,197,952 against 3,186,944 elements here.
        How would you see every operator a model calls, and what can fool you?
        A TorchDispatchMode logging func. What it sees depends on grad mode: in training F.linear arrives decomposed (t + addmm), under inference_mode as linear. The profiler sees still more (calls inside kernels).

        Each node runs once all edges into it have delivered a gradient (its count reaches 0).         The mechanism in four lines
        Every storage-sharing family of tensors has one version counter. Every in-place op bumps it (the ADInplaceOrView kernel, even under no_grad). A node that saves a tensor records the counter's value. When backward unpacks the tensor, a different value raises the error, unless saved-tensor hooks are installed, in which case nothing is checked.
