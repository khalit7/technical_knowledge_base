The idea in one screen

Every PyTorch call reads tensors that are headers over a flat block of bytes, is routed by the dispatcher down a stack of kernels chosen by dispatch keys (autocast, autograd, view tracking, then the device kernel), and one of those kernels, autograd's, records a node that loss.backward() later runs in reverse.

Fig. 1 follows one call through all three; each machine has its own section and figure below.

  1. The tensor x is a header over storage. x is 8 × 256 float32: 8,192 bytes of storage read through strides (256, 1), offset 0. A transpose would write a new header and move no byte.
  2. The call meets the keys; autocast is skipped. torch.mm(x, w) with w requiring grad: every CPU tensor carries the keys CPU, ADInplaceOrView, AutogradCPU, AutocastCPU, but the thread excludes Autocast unless you enter torch.autocast, so the call starts one key lower.
  3. AutogradCPU records a node. The autograd kernel records MmBackward0, which keeps x and w because the gradient formula needs both, and redispatches below itself.
  4. ADInplaceOrView: a fallthrough. mm neither views nor writes in place, so its slot at this key is a fallthrough and the call drops straight through.
  5. The CPU kernel does the arithmetic. Only now is anything computed: y = x @ w, written to a new storage. y's grad_fn points at the node.
  6. Backward runs the node. loss.backward() reaches MmBackward0, which uses the saved x for w's gradient, and AccumulateGrad writes w.grad.

Keys and slots read from the installed wheel (torch._C._dispatch_keys, _dispatch_dump_table("aten::mm"); sections 2.1 to 2.3); the storage is drawn as 8 rows of 256 floats.

You need: PyTorch as a user (you train models with it). The root, Topic: pytorch-ecosystem, is the map; its Inside one step tab records one whole training step of the running example op by op (923 calls). This page explains why each call took the route it did, from the C++ that decides it. The running example is the topic's tiny GPT: 4 blocks, d_model 256, a 43-character vocabulary, 3,186,944 parameters, batch 8 × 64, the output layer tied to the input embedding.

1. A tensor is a header over bytes

Take x = torch.arange(12.).view(3, 4). Its storage is 12 floats (48 bytes), and every value equals its own storage index, so the values printed prove the addresses. A view reads in place: it is a new header (shape, strides, offset) over the same storage, and reading element [i, j] means reading storage[offset + i·stride0 + j·stride1].

Predict before Fig. 2 plays: as you read x.t() row by row, how many times does the read position jump backwards in storage?

  1. One storage: 12 floats. torch.arange(12.) fills 48 bytes on one device. It has no shape of its own; everything else is a header over it.
  2. x = a header, shape (3, 4), strides (4, 1), offset 0. Moving one row skips 4 floats, one column 1 float, so row 0 reads storage 0, 1, 2, 3 and row 1 starts at 4.
  3. A slice moves the offset. x[1:, 1:3] has shape (2, 2), strides (4, 1) and offset 5: it reads 5, 6, 9, 10 from the same storage, and nothing is copied.
  4. x.t(): a new header, the same bytes. Shape (4, 3) and strides (1, 4) over the same 12 floats: row 0 of the transpose reads storage 0, 4, 8. Nothing moves.
  5. Read in order, x.t() jumps back three times. Row by row it reads 0, 4, 8, 1, 5, 9, 2, 6, 10, 3, 7, 11: consecutive elements sit 4 apart, and after each row the position jumps back (red). No single stride describes that walk, which is why view(12) cannot.
  6. .contiguous() writes a new storage in reading order. x.t().contiguous() copies the 12 floats in the order they are read (48 bytes) into storage of its own, strides (3, 1), sharing nothing with x.
  7. A stride of 0 repeats memory. x[0:1].expand(3, 4) has strides (0, 1): three rows over one row of storage, each of cells 0 to 3 read three times, which is how broadcasting avoids copies.

Every shape, stride, offset and address in Fig. 2 is what torch 2.14.1 reported for that tensor (src/exp/tensors.py); the copy has strides (3, 1) and shares no storage with x.

A tensor is contiguous when reading it in order walks the storage in order with no gaps: strides equal the row-major ones for its shape ((4, 1) for (3, 4)). Most kernels are fastest on contiguous input and some require it. Three rules follow from the formula:

  • view never copies, so it fails when no strides can describe the new shape over the old layout: x.t().view(12) raised "view size is not compatible with input tensor's size and stride (at least one dimension spans across two contiguous subspaces). Use .reshape(...) instead."
  • reshape returns a view when it can and copies when it cannot: x.reshape(12) shared storage, x.t().reshape(12) did not. .contiguous() copies only when needed; flip, advanced indexing (x[[0, 2]]) and boolean masks always copy, because there are no negative strides ("as_strided: Negative strides are not supported at the moment, got strides: [-4, 1]").
  • A stride of 0 repeats memory (step 7), so writing into an expanded tensor in place is an error ("more than one element of the written-to tensor refers to a single memory location"). x.unfold(1, 2, 1) makes overlapping windows, so some cells are read twice.

On the running example this is why attention costs no copies. q, k and v are three views of one (8, 64, 768) qkv output at storage offsets 0, 256 and 512, all with strides (49152, 768, 1); splitting heads with view and transpose gives strides (49152, 64, 768, 1): zero bytes copied. On the CPU the attention kernel then writes its (8, 4, 64, 64) output with strides (16384, 64, 256, 1), already in (batch, position, head, dim) order, so the model's .transpose(1, 2).contiguous() finds a contiguous tensor and copies nothing measured on Apple M1 Pro, CPU. On MPS the same line copies 524,288 bytes per layer (the root's Inside one step tab, section 1). Every expression on four bases, with every address, is in the Stride explorer tab.

The header carries more than layout: requires_grad, is_leaf (made by you, not by a recorded op), grad_fn (the node that made it), _base (the tensor it views) and the version counter, shared by every view of one storage. Section 3.3 shows why autograd needs the counter.

Memory formats: channels_last is a stride order, not a shape (depth)

For images, a (N, C, H, W) tensor stored row-major keeps each channel's whole image together (NCHW). Convolution kernels on GPUs with tensor cores, and oneDNN on CPUs, prefer the channels of one pixel together (NHWC). PyTorch keeps the logical shape (N, C, H, W) and changes only the strides: that is channels_last, a memory format.

So is_contiguous() answers "row-major?" and says no, while is_contiguous(memory_format=torch.channels_last) says yes. Element-wise ops and convolutions keep the format (measured above); view on it fails like on any non-contiguous tensor. A tensor with C = 1 or H = W = 1 is both at once, which is why format checks are ambiguous on such shapes. Does it pay on a CPU? A 3 × 3 convolution, 64 to 64 channels, on (8, 64, 56, 56) took 4.669 ms in NCHW against 4.199 ms in channels_last measured on Apple M1 Pro, CPU, 4 threads, median of 3 × torch.utils.benchmark (trials 4.644, 4.669, 4.703 and 4.116, 4.392, 4.199). On NVIDIA GPUs the gain with tensor-core convolutions is the documented reason for the format; not run here.

dtypes and type promotion: the wider type does not always win (depth, with a drill)

A dtype fixes the bytes per element and how to read them: float32 (4 bytes), bfloat16 and float16 (2), int64 (8), bool (1). When an operation mixes dtypes, PyTorch picks the result with type promotion: within the same category (bool < integer < floating < complex) the wider type wins, and when neither type can hold the other, a third one is chosen. The grid is torch.promote_types(row, column) read from the installed wheel; outlined cells are neither input (bfloat16 with float16 gives float32; uint8 with int8 gives int16):

Two exceptions catch everyone, both measured below: a Python scalar or a 0-dim tensor does not raise precision within its category (float16 tensor + float64 0-dim tensor stays float16), but it does move you to a higher category (an int64 tensor + 2.5 becomes float32, the default dtype). And an in-place op cannot change the dtype of its destination.

Devices, copies between them, and pinned memory (depth)

A storage lives on one device (cpu, mps, cuda:0), and an operation needs all its tensors on the same device. .to(device) is a copy (an aten::_to_copy call; a no-op if already there). On a GPU that copy crosses a bus, and copying from ordinary ("pageable") host memory makes the driver stage it through a pinned buffer first. Pinned (page-locked) host memory can be read by the GPU's copy engine directly, which is what lets .to("cuda", non_blocking=True) overlap the copy with compute. On this Mac, torch.randn(1024).pin_memory() worked and reported is_pinned() == True, but a DataLoader(pin_memory=True) warned and returned unpinned batches measured on Apple M1 Pro. The overlap itself is a CUDA matter: not run here (no NVIDIA GPU); see Streams, CUDA graphs and multi-GPU.

2. The dispatcher: a walk down a stack of keys

One operator, say mm, has to do different things by context: cast to bfloat16 under mixed precision, record a graph node when gradients are needed, run on a CPU, an Apple GPU or a CUDA GPU, call back into Python for a tensor subclass or a tracing tool, or only compute output shapes while a compiler traces. Instead of writing all of that into every one of thousands of kernels, PyTorch gives each concern its own kernel under its own dispatch key, and per call a table lookup decides which of them run, in priority order. Each kernel does its one job and calls the operator again with its own key masked off (it redispatches), so the call walks down the stack.

2.1 The keys, in priority order

A key has two parts: a functionality (Dense, Autograd, Autocast, Python, ...) and, for some functionalities, a backend bit (CPU, MPS, CUDA, ...). AutogradCPU is the Autograd functionality with the CPU bit. The functionality order is the priority.

Higher number runs first: autocast, then autograd, then view bookkeeping, then Python, then the arithmetic

2.2 The key set of one call: tensors, plus the thread, minus the thread

Every tensor carries a key set: a plain CPU float tensor has CPU, ADInplaceOrView, AutogradCPU, AutocastCPU; an inference tensor only CPU, AutocastCPU; a FakeTensor adds Python and PythonTLSSnapshot. The thread carries two more sets, an included and an excluded set, changed by context managers. For each call:

keys = (∪ keys of the tensor arguments ∪ included) − excluded − fallthroughs

and the kernel of the highest key left runs. Two defaults explain a lot: ADInplaceOrView is in every thread's included set, and every Autocast key sits in the excluded set until you enter torch.autocast. So a plain tensor carries AutocastCPU, but the thread hides it. Watch it on a real call in Fig. 3.

A tensor that does not require grad takes exactly this route.
  2. Under no_grad: the same three. Under no_grad the autograd kernel still runs: grad mode is only a flag it reads before deciding not to record, and no key changes.
  3. Under inference_mode: autograd is skipped. The autograd keys are excluded, so that kernel never runs (two kernels). The op still visits ADInplaceOrView because the tensor was made outside the mode and keeps its own keys.
  4. Under autocast: a cast at the top. AutocastCPU leaves the excluded set, so its kernel runs first, receives float32, casts and calls the op again with AutocastCPU excluded: the input arrives as bfloat16 everywhere below. Four kernels; the result is bfloat16.
  5. Inside a TorchDispatchMode: the Python key. The mode puts Python into the key set; that key sits below autograd and ADInplaceOrView, so a mode sees calls after autograd has recorded them. Four kernels.
  6. A meta tensor: the Meta kernel. torch.empty(4, device='meta') carries Meta keys, so the Meta kernel runs instead of the CPU one and computes the output's shape only. A meta tensor carries AutogradMeta; the boxed autograd fallback ran there, invisible to this log.
  7. An inference tensor outside the mode: two kernels. A tensor made under inference_mode carries only CPU, AutocastCPU, so even in normal mode autograd is not in the key set; ADInplaceOrView still runs because it is in every thread's included set.

2.3 Behind each key, a table slot

Each operator keeps a dispatch table: one slot per key. A slot is filled by, in order: a kernel registered for exactly that key; else a kernel for an alias key that covers it (CompositeExplicitAutograd, one implementation for all backends; CompositeImplicitAutograd, a decomposition into other operators that also serves as its own autograd, the "math kernel"); else a backend fallback registered for every operator at that key; and a fallthrough means "skip this key". A fallback is boxed: the arguments arrive as a generic stack of values, which is what lets one function serve every operator. Counted over every operator in the wheel:

2.4 Autocast is just a key

torch.autocast(device, dtype) removes that device's Autocast key from the excluded set; nothing else. From then on every operator reaches the Autocast key first, and for most the slot is a fallthrough. Operators on the lower_precision_fp list (matrix multiplies, convolutions, attention, linear) get a kernel that casts their floating-point inputs to the autocast dtype; operators on the fp32 list (losses, norms, reductions that lose accuracy) cast to float32. Weights stay float32: the casts are new tensors on every forward. On the running example, one forward under bfloat16 autocast on the CPU made 180 aten calls against 137 without, 43 of them _to_copy casts; all 9 layer norms ran in float32, and the loss was 3.801377 against 3.801371 in float32 measured on Apple M1 Pro, CPU. Autocast does not make "the model" bf16; it makes chosen ops bf16. Step 4 of Fig. 3 shows the cast happen at the top of the stack.

2.5 Keys that rewrite or skip the arithmetic: functionalisation, meta and fake tensors

Three more keys explain how compilers see your code without running it. Functionalize (a real kernel for 1,333 aten operators, a boxed fallback for the rest) wraps tensors and replays every in-place write as an out-of-place op, regenerating views from their base, so a traced graph has no mutation; torch.compile's AOTAutograd stage uses it (torch.compile from the user's side owns the compiler). A meta tensor has sizes, strides and a dtype but no storage; its Meta kernels only compute output metadata: built under with torch.device("meta"), the running example has 3,186,944 parameters, allocates nothing, and a forward returns logits of shape (8, 64, 43). A FakeTensor is the same idea with a device attached, a tensor subclass that dispatches at the Python key; under FakeTensorMode the running example ran forward and backward with no arithmetic, giving a blocks.0.mlp.fc.weight.grad of shape (1024, 256). torch.compile traces your model this way.

2.6 What dispatch costs, and how to look

Each call pays for the key computation, each kernel it walks through and the Python binding before any arithmetic. For a one-element add, where the arithmetic is nothing, that is the whole time: 0.622 µs on a plain tensor, 1.06 µs when it records a node, 4.818 µs through a Python TorchDispatchMode measured on Apple M1 Pro, CPU, median of 3. A real matmul in the running example takes tens to hundreds of microseconds, so this matters only for many tiny ops: the reason torch.compile and CUDA graphs exist. To see every aten call of a program, a TorchDispatchMode whose __torch_dispatch__ logs func sees everything below autograd (that is how the root counted 923 calls in one step). What it sees depends on grad mode: in training F.linear reaches it as t plus addmm (decomposed at the autograd key); under inference_mode as linear (autograd skipped, so the decomposition happens below the mode).

3. Autograd: a graph recorded in forward, run backwards by the engine

Training needs the gradient of one number (the loss) with respect to millions of parameters. The chain rule gives it if you know every operation that produced the loss and kept what each needs to differentiate. Autograd records exactly that while forward runs (reverse-mode automatic differentiation), so backward costs about as much as a couple of forwards, whatever the number of parameters. Take one block of the running example, applied to the embedding output as a leaf x, with loss = mean(block(x)2), on the CPU: forward creates 33 operator nodes and 13 AccumulateGrad nodes (12 parameters and x), 46 in all, which keep 8.93 MB of activations between them; backward runs all 46 and makes 75 aten calls recorded with node pre-hooks and a dispatch mode.

  1. Forward, first half: the graph grows as the code runs. Each operation with an input that requires grad creates one node, in sequence-number order: ln1 (sequence number 0), the qkv matrix multiply (3), the split into q, k and v and their head views (5 to 11, side by side), attention (12). Each leaf that requires grad gets an AccumulateGrad node (green, in front). Saved activations stack up on the nodes that keep them.
  2. Forward, second half: 46 nodes, 8.93 MB held. The output projection, the residual add, ln2, the MLP's two matrix multiplies with GELU between them, and the loss: 33 operator nodes and 13 AccumulateGrad nodes (12 parameters and x), keeping 8.93 MB of activations between them.
  3. What one node holds. Close on attention's node (sequence number 12): edges to the three nodes that made q, k and v (next_functions), and its saved tensors, q, k and v as one shared (8, 64, 768) storage of 1,572,864 bytes plus its output and log-sum-exp.
  4. Backward starts at the loss. The engine runs the root, then always the ready node with the highest sequence number: through the residual to the MLP output's AddmmBackward0, then at once the AccumulateGrad of mlp.proj.bias and of its weight. Gradients flow along the edges; each node frees its saved tensors as it runs.
  5. Through the MLP and ln2. GELU's 2,097,152-byte input and the MLP's saved inputs go as their nodes run, and each parameter's .grad is written the moment its gradient is complete.
  6. Through attention. Attention's node runs and frees q, k and v; the gradient splits into three branches that meet again at SplitBackward0, then the qkv matrix multiply.
  7. To the leaves. ln1 and finally x's AccumulateGrad: all 46 nodes have run, in the order the ready-queue rule of 3.2 predicts, with 75 aten calls, and no saved activation is held.

3.1 What a node holds

When the autograd kernel of an operator runs with grad mode on and an input that requires grad, it creates a Node (what you see as y.grad_fn, such as AddmmBackward0) and points the output at it. A node holds edges to the nodes that produced its inputs (next_functions), the saved tensors its gradient formula needs, and a sequence number, a per-thread counter taken at creation. The formula comes from derivatives.yaml: mm's needs both self and mat2, so its node saves both; gelu's needs its input. Leaves that require grad end in an AccumulateGrad node, whose job is to add the arriving gradient into .grad. The expensive saved tensors are activations, not weights: attention saves q, k and v as one shared (8, 64, 768) storage plus its output and log-sum-exp; each matrix multiply saves its input. That is the memory checkpointing gives back (3.6).

3.2 The engine's rule: dependencies and a ready queue

Calling loss.backward() hands the graph to the engine (C++, torch/csrc/autograd/engine.cpp). It counts, for every node reachable from the loss, how many edges point into it (its dependencies). Then it repeatedly takes a node from a ready queue, runs it, adds the gradients it produces into the next nodes' input buffers, decrements their counts, and pushes each node whose count reaches zero. The queue is a priority queue: the ready node with the highest sequence number (created last in forward) runs first, and AccumulateGrad nodes take the largest possible number, so a parameter's .grad is written the moment its gradient is complete and the buffer can be freed. Checked against the record: re-running that rule on the recorded graph (dependencies from the edges, a max-heap on sequence number) reproduces the order the engine actually ran the 46 nodes, in all three CPU variants and both MPS variants measured on Apple M1 Pro. Ties between AccumulateGrad nodes (all at the same maximal number) are broken by the heap; in this record the first pushed always ran first.

Predict: which node does the engine run right after the first AddmmBackward0 (the MLP output projection)? Then step the engine explorer below to check.
AccumulateGrad for mlp.proj.bias: once AddmmBackward0 runs, three nodes become ready (the bias's AccumulateGrad, the weight's TBackward0, and the GELU path's ViewBackward0); AccumulateGrad has the largest sequence number, so it goes first. In the record the next two nodes to run are that AccumulateGrad and then TBackward0, then the weight's AccumulateGrad, and only then the GELU path.

Threads. CPU work runs on the thread that called backward(); each non-CPU device gets one long-lived worker thread with its own queue. Measured: a tensor hook fired on the calling thread for a CPU backward and on a different thread for an MPS backward. So a Python hook or a custom backward for a GPU tensor runs on the engine's device thread, not yours; PyTorch carries the thread-local dispatch and grad-mode state into it (each graph task stores the caller's at::ThreadLocalState, graph_task.h L125), but Python threading.local values you set yourself are not there.

3.3 Version counters: how autograd notices you overwrote what it saved

A node saved a tensor in forward; if your code overwrites that tensor in place before backward, the saved value is wrong and so is the gradient. Copying every saved tensor would cost memory, so PyTorch detects instead: every in-place write bumps the storage's version counter (the ADInplaceOrView kernel does it, below the copy itself); a saved tensor remembers the version it had when saved; unpacking it in backward compares the two.

The counter is counting, not recording: a write under no_grad still bumped it, while a write through .data did not (.data hands you a tensor with a fresh counter). Inference tensors have none: reading _version raised "Inference tensors do not track version counter." 3.4 Your own backward: torch.autograd.Function

When you want a different gradient than the one autograd would derive (a numerically safer formula, a fused kernel, a straight-through estimator), subclass torch.autograd.Function. It plugs into the same graph: apply runs your forward with recording off, your setup_context saves what backward needs through the same version-checked saved-tensor path, and one node of your class stands for the whole forward.

A custom Function is one node: forward is not recorded inside, backward is yours

For MyGelu below, the output's grad_fn was MyGeluBackward measured. The engine treats it like any other node: it runs when its dependencies are met, and what backward returns is sent along its edges.

class MyGelu(torch.autograd.Function): @staticmethod def forward(x): # no ctx here return 0.5 * x * (1 + torch.tanh(0.7978845608 * (x + 0.044715 * x ** 3))) @staticmethod def setup_context(ctx, inputs, output): (x,) = inputs ctx.save_for_backward(x) # goes through SavedVariable: version-checked @staticmethod def backward(ctx, g): (x,) = ctx.saved_tensors u = 0.7978845608 * (x + 0.044715 * x ** 3) t = torch.tanh(u) du = 0.7978845608 * (1 + 3 * 0.044715 * x ** 2) return g * (0.5 * (1 + t) + 0.5 * x * (1 - t ** 2) * du) x = torch.randn(6, dtype=torch.float64, requires_grad=True) torch.autograd.gradcheck(MyGelu.apply, (x,)) # finite differences in float64 torch.autograd.gradgradcheck(MyGelu.apply, (x,)) # its backward is differentiable too

Keeping forward free of the context and saving in setup_context is what lets the function work with torch.func transforms. gradcheck compares your backward with finite differences, column by column of the Jacobian; use float64, or rounding drowns the comparison. A backward that forgets the second term of the product rule fails at once: "Jacobian mismatch for output 0 with respect to input 0". gradgradcheck does the same for the backward's own gradient. If your backward uses operations autograd cannot differentiate (an external kernel), decorate it with @once_differentiable: then asking for a second derivative fails loudly ("element 0 of tensors does not require grad and does not have a grad_fn") instead of silently returning a wrong one. Other context methods: ctx.needs_input_grad (skip work for inputs that need no gradient), ctx.mark_dirty (the forward wrote an input in place), ctx.mark_non_differentiable (integer outputs such as indices). For an operator that must also survive torch.compile and export as a single node, use torch.library.custom_op with register_autograd (Extending PyTorch).

3.5 Turning gradients off

no_grad and set_grad_enabled(False) are the same switch: the grad-mode flag the autograd kernel reads (section 2.2). No key changes, outputs get no grad_fn, and they can still be used in training later. inference_mode also excludes the autograd and view-tracking keys and produces inference tensors, which have no version counter and can never be saved for backward: using one in training later raised "Inference tensors cannot be saved for backward." Use inference_mode for serving and for evaluation whose outputs you never train on; no_grad inside a training loop (EMA updates, metrics on tensors you may reuse).

3.6 Trading the saved memory: saved-tensor hooks and checkpointing

The saved tensors are the activation memory that limits batch size and sequence length. Saved-tensor hooks (torch.autograd.graph.saved_tensors_hooks(pack, unpack)) intercept every tensor a node saves: pack may return anything (a CPU copy, a compressed version, a file name) and unpack must give the tensor back in backward; torch.autograd.graph.save_on_cpu() is the built-in pair. Activation checkpointing (torch.utils.checkpoint.checkpoint(fn, x, use_reentrant=False)) saves only the region's input and reruns the region during backward when a node first asks for a tensor it did not keep. The "MPS: saved tensors to host" variant moved 25 tensors, 13,119,488 B, to host memory in forward and back in backward, leaving 524,544 B on the device after forward instead of 8,921,344 B; but a forward and backward of the whole model took 72.98 ms against 12.02 ms plain measured on Apple M1 Pro, MPS, median of 3 × 10. On this Mac's unified memory the round trip saves the allocator's bytes but not physical memory; on a CUDA GPU the copies can overlap compute with pinned memory and streams.

Checkpointing cut what forward leaves behind tenfold and paid for it in backward calls

Full running example on the CPU, live storages tracked with a dispatch mode (src/exp/autograd_lab.py); gradients identical to plain (max difference 0) in every variant. Non-reentrant recomputes 12 of the 16 block matrix multiplies (it stops early: the last projection's output is never needed); reentrant reruns all 16. Time per forward and backward: plain 17.47 ms, non-reentrant 25.18 ms, reentrant 23.41 ms (median of 3 × 10, CPU 4 threads; why non-reentrant was not faster despite 4 fewer matmuls was not investigated).

Two checkpoint variants, and a default that still has not changed. The original reentrant variant (use_reentrant=True) runs the region under no_grad and, in backward, reruns it inside a nested call to the engine. The non-reentrant variant (use_reentrant=False) is built on saved-tensor hooks: forward packs placeholders, and the first unpack in backward triggers the rerun, which can stop as soon as everything needed is rebuilt. Reentrant breaks in two measured ways: when no input requires grad (a frozen embedding before it) the output does not require grad and the region's weights get no gradient ("None of the inputs have requires_grad=True. Gradients will be None"); and with torch.autograd.grad it raises "When use_reentrant=True, torch.utils.checkpoint is incompatible with .grad() or passing an `inputs` parameter to .backward()". Non-reentrant handles both.

Correction to a common claim
The warning and the docstring say that from PyTorch 2.9 calling checkpoint without use_reentrant "will raise an exception". At 2.14.1 it still warns and falls back to use_reentrant=True (checkpoint.py line 645, and measured: the unspecified run behaved exactly like the reentrant one, 431 backward calls and 16 recomputed matmuls). Always pass use_reentrant=False.

Hooks: five places to step in, in the order they fired (depth)

One backward of the block with one hook of each kind registered, in the order they fired:

  1. tensor hook: block output y
  2. node pre-hook: AddBackward0 (y's grad_fn)
  3. node hook: AddBackward0 (y's grad_fn)
  4. module pre-hook: mlp (grad of its output arrives)
  5. tensor hook: mlp.fc.weight (gradient before accumulation)
  6. post-accumulate-grad hook: mlp.fc.weight (.grad is set)
  7. module hook: mlp (grad of its input computed)
  8. post-accumulate-grad hook: attn.qkv.weight
  9. tensor hook: input x

The kinds: a tensor hook (t.register_hook(fn)) sees, and may replace, the gradient flowing into that tensor; node pre-hooks and hooks (grad_fn.register_prehook, register_hook) run around one node; module backward hooks (register_full_backward_pre_hook, register_full_backward_hook) see the gradients of a module's outputs and inputs; a post-accumulate-grad hook (p.register_post_accumulate_grad_hook(fn)) runs after p.grad has been written, the place to step an optimiser per parameter during backward so gradients can be freed early. A hook that returns a value replaces the gradient: w.register_hook(lambda g: g.clamp(-1, 1)); (w ** 3).sum().backward() gave w.grad = [1, 1, 1] instead of [3, 12, 27] (measured).

retain_graph, create_graph and double backward (depth)

Backward frees each node's saved tensors as soon as the node has run, which is why backward's memory falls as it goes (Fig. 4, and the curve in the engine explorer in 3.2). A second backward() through the same graph therefore fails: "Trying to backward through the graph a second time (or directly access saved tensors after they have already been freed)." With retain_graph=True the saved tensors stay, and since gradients accumulate, two backwards on (w**2).sum() at w = [1, 2, 3] gave [2, 4, 6] then [4, 8, 12].

create_graph=True goes further: backward itself is recorded, so the gradient is a tensor with its own grad_fn and can be differentiated again. For y = ∑x3 at x = [1, 2, 3]: first gradient [3, 12, 27] (grad_fn MulBackward0, requires grad), second [6, 12, 18] = 6x. Without it the gradient does not require grad and differentiating it fails with "element 0 of tensors does not require grad". This is how gradient penalties (WGAN-GP, input-gradient regularisers) and Hessian-vector products work. The cost is real: on a small MLP, forward plus one gradient took 15 aten calls; forward, gradient with create_graph, the penalty and its backward took 50 measured, aten calls counted by a dispatch mode.

Anomaly mode: finding the op that made a NaN (depth)

A NaN in a gradient usually comes from one backward formula hitting a singular point. The classic: sqrt at 0 has an infinite derivative, and multiplying by a zero gradient gives 0 × ∞ = NaN. Without help, backward just returns x.grad = [nan, 0.5] with no error. Inside torch.autograd.detect_anomaly() the engine checks every node's output and raises "Function 'SqrtBackward0' returned nan values in its 0th output.", after printing a warning "Error detected in SqrtBackward0. Traceback of forward call that caused the error:" with the Python stack of the forward line that created the node. It records a stack trace for every node in forward and checks every output in backward, so it is a debugging tool, not a default: one forward and backward of the running example took 42.43 ms with it against 17.47 ms without measured on Apple M1 Pro, CPU, 4 threads, median of 3 × 10.

4. Modules and the loop sit on top

nn.Module adds bookkeeping, not a new machine: a parameter is a leaf tensor with requires_grad=True (an AccumulateGrad node waits for it), a state_dict is names over storages, and a module's backward hooks are autograd hooks on its outputs (section 3's hooks block). A tied weight is one storage under two names (section 1), so when you load an untied checkpoint (a model trained without tying) into a tied architecture, both names copy into that one storage and the later one silently wins. The modules, saving and loading, the training loop (accumulation, clipping, the GradScaler), determinism and DataLoader seeding, all measured on this running example, are taught on Making training fast: Reading section 7 for the loop and the module, section 6 for the GradScaler, section 4's closed block for workers and seeds.

Common mistakes, each with the section that shows it (8)
  • Assuming .view() after a transpose or permute will work. It fails whenever the strides cannot describe the new shape; .reshape() works and may copy (1).
  • Writing in place into something backward needs: nn.ReLU(inplace=True) after a sigmoid, x += ... on a saved activation, an optimiser step or EMA update between forward and backward. The version check catches it: "modified by an inplace operation" (3.3).
  • Using .data to "get around" autograd. The write is invisible to the version counter and the gradient comes out wrong without any error (3.3). Use .detach() or torch.no_grad().
  • Thinking no_grad stops version counting, or that it removes keys. It only tells the autograd kernel not to record; in-place writes still bump counters and the autograd key still runs (2.2, 3.3).
  • Returning a tensor made under inference_mode into training code. "Inference tensors cannot be saved for backward" as soon as an op needs to save it; clone it first or use no_grad (3.5).
  • Calling checkpoint without use_reentrant. At 2.14.1 it still means the reentrant variant: no gradient when no input requires grad, no torch.autograd.grad, full recompute (3.6).
  • Expecting autocast to make the model bfloat16. Only the listed ops run in the lower dtype; norms, adds and the loss stay float32, and the weights are re-cast every forward (2.4).
  • A custom op without an autograd registration. The autograd fallback lets backward run with only a warning, and the gradient is wrong (2.3).
Interview rehearsal: ten questions with short answers (optional)
What is the difference between a tensor and a storage? When do two tensors share memory?
The storage is the bytes on a device; the tensor is sizes, strides, offset and dtype over it. Views (slicing, transpose, view, expand, split) share storage; compare untyped_storage().data_ptr(). flip, advanced indexing and contiguous() on a non-contiguous tensor copy.
Why can expand make a 1,000 × 1,000 tensor from 1,000 numbers?
Stride 0 on the expanded dimension: every row reads the same memory. Writing into it in place is an error for that reason.
Walk through what happens in torch.mm(x, w) with w requiring grad, under autocast.
Key set = keys of x and w, plus the thread's included set, minus excluded. AutocastCPU runs first (autocast removed its exclusion) and casts both to bf16, then calls mm again with Autocast excluded; AutogradCPU records MmBackward0 saving both inputs and redispatches below autograd; ADInplaceOrView is a fallthrough for mm; the CPU kernel computes. Measured: 2 _to_copy calls and a bf16 mm (section 2.6's aten-call explorer).
What do CompositeImplicitAutograd and CompositeExplicitAutograd mean?
Implicit: the op is written in other ops and gets its gradient from them (no derivative formula, no backend kernel), so it decomposes before autograd records. Explicit: one implementation for all backends, but it needs its own derivative. A backend may override either (MPS registers its own linear).
no_grad versus inference_mode, mechanically?
no_grad flips the grad-mode flag; the autograd kernel still runs and records nothing. inference_mode also excludes every autograd key, stops including ADInplaceOrView, and creates inference tensors without version counters, which can never be saved for backward.
How does the autograd engine decide the order of backward?
Count dependencies; run ready nodes from a priority queue keyed on sequence number (latest-created first), AccumulateGrad first of all; CPU work on the calling thread, one worker thread per GPU device. Re-running that rule reproduced the recorded order here.
How does PyTorch detect "modified by an inplace operation"?
A version counter per storage, shared by views, bumped by every in-place op (ADInplaceOrView kernels); saved tensors record the version at save time and compare at unpack. It is skipped for .data writes and when saved-tensor hooks are installed.
What does create_graph=True cost and when do you need it?
It records backward as a graph so you can differentiate the gradient (penalties, Hessian-vector products, meta-learning). It keeps more saved tensors and more ops: 15 against 50 aten calls on a small MLP here.
Reentrant or non-reentrant checkpointing?
Non-reentrant: works when inputs do not require grad, works with autograd.grad and keyword args, stops recomputing early (12 of 16 matmuls here). Reentrant is the old default, still the fallback at 2.14.1 if you pass nothing.
How would you see every operator a model calls, and what can fool you?
A TorchDispatchMode logging func. What it sees depends on grad mode: in training F.linear arrives decomposed (t + addmm), under inference_mode as linear. The profiler sees still more (calls inside kernels).
