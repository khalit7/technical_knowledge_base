Autograd engine

One backward pass of one block of the running example (block 0, input the embedding output of batch 0 as a leaf x, loss = mean(block(x)2)), node by node, exactly in the order the engine ran it. The graph, the sequence numbers, the saved tensors and the order were recorded with node pre-hooks; the ready queue and the dependency counts beside it are the engine's rule re-run on that graph, which reproduces the recorded order in every variant (src/exp/autograd_graph.py). Same input and weights in every variant; the gradients agree with the plain run to the bit (max difference 0).

"Saved bytes still held" counts the unique activation storages saved by nodes that have not run yet (weights excluded, they stay in memory anyway): derived from the recorded graph, assuming a node's saved tensors are freed when it runs (the engine releases them unless retain_graph=True). For the checkpointed variant nothing is held until the first node that unpacks a saved tensor, where the block is rerun (the red calls); from there on the count is the same derivation. The bytes "after forward" are measured: live storages on the CPU, torch.mps.current_allocated_memory() on MPS.

Read it like the engine
Each node runs once all edges into it have delivered a gradient (its count reaches 0). Among ready nodes, the one created last in forward goes first, and AccumulateGrad goes before everything, so a parameter's .grad is written the moment its gradient is complete. On MPS the same rule runs on the engine's MPS worker thread, not on the thread that called backward (measured).
