The idea in one screen

Every PyTorch call reads tensors that are headers over a flat block of bytes, is routed by the dispatcher down a stack of kernels chosen by dispatch keys (autocast, autograd, view tracking, then the device kernel), and one of those kernels, autograd's, records a node that loss.backward() later runs in reverse.

One call, three machines: torch.mm(x, w) with w requiring grad

Left: x is 8 × 256 float32, 8,192 bytes of storage read through strides (256, 1); a transpose would write a new header and move no byte. Middle: every CPU tensor carries the keys CPU, ADInplaceOrView, AutogradCPU, AutocastCPU; the thread excludes Autocast unless you enter torch.autocast, and mm's slot at ADInplaceOrView is a fallthrough. Right: the autograd kernel records MmBackward0, which keeps x and w because the gradient formula needs both; backward runs it and AccumulateGrad writes w.grad. Keys and slots read from the installed wheel (sections 2.1 to 2.3).

You need: PyTorch as a user (you train models with it). The root, {{Topic: pytorch-ecosystem|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}}, is the map; its {{Inside one step|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}} tab records one whole training step of the running example op by op (923 calls). This page explains why each call took the route it did, from the C++ that decides it. The running example is the topic's tiny GPT: 4 blocks, d_model 256, a 43-character vocabulary, 3,186,944 parameters, batch 8 × 64, the output layer tied to the input embedding.

1. A tensor is a header over bytes

Take x = torch.arange(12.).view(3, 4). Its storage is 12 floats (48 bytes), and every value equals its own storage index, so the values printed prove the addresses. The header says shape (3, 4), strides (4, 1), offset 0. x.t() writes a new header, shape (4, 3) and strides (1, 4), over the same 12 floats: nothing moves. Reading element [i, j] means reading storage[offset + i·stride0 + j·stride1]:

A view reads in place; .contiguous() writes a new storage in reading order

Predict before you step: as you read x.t() row by row, how many times does the read position jump backwards in storage?

Every address is what torch 2.14.1 reported for this tensor (src/exp/tensors.py); the copy has strides (3, 1) and shares no storage with x.

address(i, j, …) = offset + i·stride0 + j·stride1 + …
address
position in the storage, in elements (multiply by the element size for bytes)
strided
elements skipped per step along dimension d; 0 means "repeat the same element"

A tensor is contiguous when reading it in order walks the storage in order with no gaps: strides equal the row-major ones for its shape ((4, 1) for (3, 4)). Most kernels are fastest on contiguous input and some require it. Three rules follow from the formula:

  • view never copies, so it fails when no strides can describe the new shape over the old layout: x.t().view(12) raised "view size is not compatible with input tensor's size and stride (at least one dimension spans across two contiguous subspaces). Use .reshape(...) instead."
  • reshape returns a view when it can and copies when it cannot: x.reshape(12) shared storage, x.t().reshape(12) did not. .contiguous() copies only when needed; flip, advanced indexing (x[[0, 2]]) and boolean masks always copy, because there are no negative strides ("as_strided: Negative strides are not supported at the moment, got strides: [-4, 1]").
  • A stride of 0 repeats memory: x[0:1].expand(3, 4) is three rows over one row of storage, which is how broadcasting avoids copies; writing into it in place is an error ("more than one element of the written-to tensor refers to a single memory location"). x.unfold(1, 2, 1) makes overlapping windows, so some cells are read twice.

On the running example this is why attention costs no copies. q, k and v are three views of one (8, 64, 768) qkv output at storage offsets 0, 256 and 512, all with strides (49152, 768, 1); splitting heads with view and transpose gives strides (49152, 64, 768, 1): zero bytes copied. On the CPU the attention kernel then writes its (8, 4, 64, 64) output with strides (16384, 64, 256, 1), already in (batch, position, head, dim) order, so the model's .transpose(1, 2).contiguous() finds a contiguous tensor and copies nothing measured on Apple M1 Pro, CPU. On MPS the same line copies 524,288 bytes per layer (the root's {{Inside one step|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}} tab, section 1). Every expression on four bases, with every address, is in the {{Stride explorer|#t-tda-str}} tab.

The header carries more than layout: requires_grad, is_leaf (made by you, not by a recorded op), grad_fn (the node that made it), _base (the tensor it views) and the version counter, shared by every view of one storage. Section 3.3 shows why autograd needs the counter.

Memory formats: channels_last is a stride order, not a shape (depth)

For images, a (N, C, H, W) tensor stored row-major keeps each channel's whole image together (NCHW). Convolution kernels on GPUs with tensor cores, and oneDNN on CPUs, prefer the channels of one pixel together (NHWC). PyTorch keeps the logical shape (N, C, H, W) and changes only the strides: that is channels_last, a memory format.

So is_contiguous() answers "row-major?" and says no, while is_contiguous(memory_format=torch.channels_last) says yes. Element-wise ops and convolutions keep the format (measured above); view on it fails like on any non-contiguous tensor. A tensor with C = 1 or H = W = 1 is both at once, which is why format checks are ambiguous on such shapes. Does it pay on a CPU? A 3 × 3 convolution, 64 to 64 channels, on (8, 64, 56, 56) took 4.669 ms in NCHW against 4.199 ms in channels_last measured on Apple M1 Pro, CPU, 4 threads, median of 3 × torch.utils.benchmark (trials 4.644, 4.669, 4.703 and 4.116, 4.392, 4.199). On NVIDIA GPUs the gain with tensor-core convolutions is the documented reason for the format; not run here.

dtypes and type promotion: the wider type does not always win (depth, with a drill)

A dtype fixes the bytes per element and how to read them: float32 (4 bytes), bfloat16 and float16 (2), int64 (8), bool (1). When an operation mixes dtypes, PyTorch picks the result with type promotion: within the same category (bool < integer < floating < complex) the wider type wins, and when neither type can hold the other, a third one is chosen. The grid is torch.promote_types(row, column) read from the installed wheel; outlined cells are neither input (bfloat16 with float16 gives float32; uint8 with int8 gives int16):

Two exceptions catch everyone, both measured below: a Python scalar or a 0-dim tensor does not raise precision within its category (float16 tensor + float64 0-dim tensor stays float16), but it does move you to a higher category (an int64 tensor + 2.5 becomes float32, the default dtype). And an in-place op cannot change the dtype of its destination.

Predict: torch.tensor([1, 2], dtype=torch.uint8) + 300. What comes out?
uint8 [45, 46] (measured): the Python int does not widen a uint8 tensor (same category), and 301 and 302 wrap modulo 256. Integer overflow in PyTorch is silent. Cast first if the range matters.

Range limits from torch.finfo in the wheel; smallest subnormals are 2−24, 2−133, 2−149 and 2−1074. bfloat16 keeps float32's range with 8 bits of precision (eps 0.0078125); float16 has more precision but overflows above 65,504, which is why only float16 training needs a gradient scaler (section 4). Devices, copies between them, and pinned memory (depth)

A storage lives on one device (cpu, mps, cuda:0), and an operation needs all its tensors on the same device. .to(device) is a copy (an aten::_to_copy call; a no-op if already there). On a GPU that copy crosses a bus, and copying from ordinary ("pageable") host memory makes the driver stage it through a pinned buffer first. Pinned (page-locked) host memory can be read by the GPU's copy engine directly, which is what lets .to("cuda", non_blocking=True) overlap the copy with compute. On this Mac, torch.randn(1024).pin_memory() worked and reported is_pinned() == True, but a DataLoader(pin_memory=True) warned and returned unpinned batches measured on Apple M1 Pro. The overlap itself is a CUDA matter: not run here (no NVIDIA GPU); see {{Streams, CUDA graphs and multi-GPU|n:3f05c17b0d0d81b19a6acab65c370b75}}.
