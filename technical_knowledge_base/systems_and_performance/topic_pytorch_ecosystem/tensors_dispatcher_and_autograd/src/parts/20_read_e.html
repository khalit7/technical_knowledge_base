4. Modules and the loop sit on top

nn.Module adds bookkeeping, not a new machine: a parameter is a leaf tensor with requires_grad=True (an AccumulateGrad node waits for it), and a state_dict is names over storages. The consequences follow from sections 1 and 3. A tied weight is one Parameter under two names, so parameters() counts 52 tensors and the state_dict 53 (3,197,952 elements against 3,186,944); safetensors refuses to save the shared storage, two different values loaded under the two names leave the later one, and to_empty unties them (2.5). In the loop, gradients accumulate into .grad across backwards, so micro-batch losses must be divided; a GradScaler's scaled gradients must be unscaled before clipping. The measured details are below, for when you save, load or write a loop.

What a Module registers, and the tied weight one level deeper (measured)

An nn.Module is a Python object whose attribute assignments are intercepted: assigning an nn.Parameter registers a parameter (a leaf tensor with requires_grad=True that optimisers will update), assigning a module registers a sub-module, and register_buffer registers a buffer (state that is saved but not trained, such as running statistics; persistent=False keeps it out of the state_dict). Everything else (parameters(), .to(), state_dict(), train()/eval()) walks that tree. On the running example:

head.weight is tok.weight: one Parameter reachable under two names. parameters() de-duplicates by object, the state_dict does not, so every tool that walks names sees two tensors sharing one storage. Measured consequences:

safetensors: "Some tensors share memory, this will lead to duplicate memory on disk and potential differences when loading them again"; save_model writes 52 tensors and drops tok.weight, and load_model restores the tie.

12,791,808 derived: the state_dict has 53 entries totalling 3,197,952 elements, because the tied tok.weight and head.weight (43 × 256 = 11,008 elements) appear under both names. They are one storage, so the real memory is 12,747,776 bytes; code that sums a state_dict overcounts.
Loading: strict, missing and unexpected keys (measured)

load_state_dict matches by name. With the default strict=True, a renamed key (here blocks.0.ln1.weight saved as blocks.0.ln_1.weight) raised:

With strict=False nothing is raised and the call returns ; the missing parameter silently keeps its initial value. Check the return value, always. A shape mismatch is an error even with strict=False: "size mismatch for blocks.0.mlp.fc.weight: copying a param with shape torch.Size([512, 256]) from checkpoint, the shape in current model is torch.Size([1024, 256])."

Predict: you load a state_dict whose tok.weight is all 1.0 and whose head.weight is all 2.0 into the tied model. What is model.tok.weight[0, 0] afterwards?
2.0 (measured). Both names copy into the same storage, in state_dict order, and head.weight comes after tok.weight, so the last one wins and no warning is given. This happens when you load an untied checkpoint (a model trained without tying) into a tied architecture.
Forward hooks (measured)

register_forward_pre_hook sees a module's inputs before forward, register_forward_hook its inputs and output after; both may replace them. They are the standard way to read activations without editing the model: one hook per block of the running example, one batch, collected the output standard deviation per block, 0.0495, 0.0659, 0.0799 and 0.0924 measured, the residual stream growing block by block as expected at initialisation. Backward hooks on modules are in section 3's hooks block.

The loop, line by line, with a float16 drill (measured)
model.train() opt = torch.optim.AdamW(groups, lr=6e-4, betas=(0.9, 0.95), weight_decay=0.1, fused=True) scaler = torch.amp.GradScaler("cuda", enabled=(amp_dtype == torch.float16)) # only float16 needs it for step in range(steps): for micro in range(accum): # gradient accumulation x, y = get_batch(cfg, step * accum + micro, device) # batch k is the same on every run with torch.autocast(device_type, dtype=amp_dtype): # bf16 or fp16 for chosen ops _, loss = model(x, y) scaler.scale(loss / accum).backward() # .grad adds up across micro-batches scaler.unscale_(opt) # clip the true gradient, not the scaled one total_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0) scaler.step(opt) # skipped if any gradient is inf or NaN scaler.update() opt.zero_grad(set_to_none=True) # free the gradients

Each line, with what was measured on the running example:

    Measured: four micro-batches of 2 with each loss divided by 4 gave the same gradient as one batch of 8 (norm 11.1032); without the division the norm was 44.41, exactly 4.00 times too large. clip_grad_norm_ returned the norm before clipping (11.1032 at step 0). zero_grad freed 12,747,776 bytes of gradients.

    Predict: of the running example's 3,186,944 gradient values at step 0, how many would be flushed to zero if stored in float16 without a scaler?
    1,636 (measured on the fp32 gradients of step 0) are below 2−24, float16's smallest subnormal, so they would round to 0 or to that one value; 436,592 are below the smallest normal 2−14 and lose precision. Multiplied by 65,536 those counts fall to 58 and 1,031, while the largest gradient becomes 33,812, still under float16's maximum of 65,504. bfloat16 has float32's exponent range, so none of this happens and no scaler is needed.
    Determinism and seeds (measured)

    In short: CPU with a fixed thread count was bit-for-bit repeatable; 1 against 4 threads differed in the last bits (max parameter difference 1.46e-06); MPS was not bit-repeatable even with use_deterministic_algorithms(True), which raised nothing.

    DataLoader workers, seeds and pin_memory (measured)

    In short: workers on macOS start with spawn; each worker seeds torch, random and NumPy; in the main process torch.manual_seed does not seed Python's random or NumPy.

    Common mistakes, each with the section that shows it (13)
    • Assuming .view() after a transpose or permute will work. It fails whenever the strides cannot describe the new shape; .reshape() works and may copy (1).
    • Writing in place into something backward needs: nn.ReLU(inplace=True) after a sigmoid, x += ... on a saved activation, an optimiser step or EMA update between forward and backward. The version check catches it: "modified by an inplace operation" (3.3).
    • Using .data to "get around" autograd. The write is invisible to the version counter and the gradient comes out wrong without any error (3.3). Use .detach() or torch.no_grad().
    • Thinking no_grad stops version counting, or that it removes keys. It only tells the autograd kernel not to record; in-place writes still bump counters and the autograd key still runs (2.2, 3.3).
    • Returning a tensor made under inference_mode into training code. "Inference tensors cannot be saved for backward" as soon as an op needs to save it; clone it first or use no_grad (3.5).
    • Calling checkpoint without use_reentrant. At 2.14.1 it still means the reentrant variant: no gradient when no input requires grad, no torch.autograd.grad, full recompute (3.6).
    • Ignoring load_state_dict(strict=False)'s return value. Missing keys keep their random initialisation silently (4).
    • Forgetting tied weights when saving, loading or materialising. safetensors refuses shared tensors, two values loaded under the two names means the last wins, and to_empty unties them (4, 2.5).
    • Accumulating gradients without dividing the loss. The gradient comes out exactly the number of micro-batches times too large (4).
    • Clipping before unscaling with a GradScaler. You clip the scaled gradient (65,536 times too large at the default scale) and the threshold means nothing. Call scaler.unscale_(opt) first.
    • Assuming torch.manual_seed seeds everything. It does not seed Python's random or NumPy in the main process (4); DataLoader workers seed all three for you.
    • Expecting autocast to make the model bfloat16. Only the listed ops run in the lower dtype; norms, adds and the loss stay float32, and the weights are re-cast every forward (2.4).
    • A custom op without an autograd registration. The autograd fallback lets backward run with only a warning, and the gradient is wrong (2.3).
    Interview rehearsal: twelve questions with short answers (optional)
    What is the difference between a tensor and a storage? When do two tensors share memory?
    The storage is the bytes on a device; the tensor is sizes, strides, offset and dtype over it. Views (slicing, transpose, view, expand, split) share storage; compare untyped_storage().data_ptr(). flip, advanced indexing and contiguous() on a non-contiguous tensor copy.
    Why can expand make a 1,000 × 1,000 tensor from 1,000 numbers?
    Stride 0 on the expanded dimension: every row reads the same memory. Writing into it in place is an error for that reason.
    Walk through what happens in torch.mm(x, w) with w requiring grad, under autocast.
    Key set = keys of x and w, plus the thread's included set, minus excluded. AutocastCPU runs first (autocast removed its exclusion) and casts both to bf16, then calls mm again with Autocast excluded; AutogradCPU records MmBackward0 saving both inputs and redispatches below autograd; ADInplaceOrView is a fallthrough for mm; the CPU kernel computes. Measured: 2 _to_copy calls and a bf16 mm (section 2.6's aten-call explorer).
    What do CompositeImplicitAutograd and CompositeExplicitAutograd mean?
    Implicit: the op is written in other ops and gets its gradient from them (no derivative formula, no backend kernel), so it decomposes before autograd records. Explicit: one implementation for all backends, but it needs its own derivative. A backend may override either (MPS registers its own linear).
    no_grad versus inference_mode, mechanically?
    no_grad flips the grad-mode flag; the autograd kernel still runs and records nothing. inference_mode also excludes every autograd key, stops including ADInplaceOrView, and creates inference tensors without version counters, which can never be saved for backward.
    How does the autograd engine decide the order of backward?
    Count dependencies; run ready nodes from a priority queue keyed on sequence number (latest-created first), AccumulateGrad first of all; CPU work on the calling thread, one worker thread per GPU device. Re-running that rule reproduced the recorded order here.
    How does PyTorch detect "modified by an inplace operation"?
    A version counter per storage, shared by views, bumped by every in-place op (ADInplaceOrView kernels); saved tensors record the version at save time and compare at unpack. It is skipped for .data writes and when saved-tensor hooks are installed.
    What does create_graph=True cost and when do you need it?
    It records backward as a graph so you can differentiate the gradient (penalties, Hessian-vector products, meta-learning). It keeps more saved tensors and more ops: 15 against 50 aten calls on a small MLP here.
    Reentrant or non-reentrant checkpointing?
    Non-reentrant: works when inputs do not require grad, works with autograd.grad and keyword args, stops recomputing early (12 of 16 matmuls here). Reentrant is the old default, still the fallback at 2.14.1 if you pass nothing.
    Why does only float16 need a GradScaler?
    float16 has 5 exponent bits: gradients below about 6e-8 vanish (1,636 of 3.19 million here) and the maximum is 65,504. bfloat16 has float32's 8 exponent bits, so its range is the same as float32's.
    Your parameter count from the state_dict is higher than from parameters(). Why?
    Tied (shared) parameters appear once per name in the state_dict: 3,197,952 against 3,186,944 elements here.
    How would you see every operator a model calls, and what can fool you?
    A TorchDispatchMode logging func. What it sees depends on grad mode: in training F.linear arrives decomposed (t + addmm), under inference_mode as linear. The profiler sees still more (calls inside kernels).
