2. The dispatcher: a walk down a stack of keys

One operator, say mm, has to do different things by context: cast to bfloat16 under mixed precision, record a graph node when gradients are needed, run on a CPU, an Apple GPU or a CUDA GPU, call back into Python for a tensor subclass or a tracing tool, or only compute output shapes while a compiler traces. Instead of writing all of that into every one of thousands of kernels, PyTorch gives each concern its own kernel under its own dispatch key, and per call a table lookup decides which of them run, in priority order. Each kernel does its one job and calls the operator again with its own key masked off (it redispatches), so the call walks down the stack.

A key has two parts: a functionality (Dense, Autograd, Autocast, Python, ...) and, for some functionalities, a backend bit (CPU, MPS, CUDA, ...). AutogradCPU is the Autograd functionality with the CPU bit. The functionality order is the priority.

2.2 The key set of one call: tensors, plus the thread, minus the thread

Every tensor carries a key set: a plain CPU float tensor has CPU, ADInplaceOrView, AutogradCPU, AutocastCPU; an inference tensor only CPU, AutocastCPU; a FakeTensor adds Python and PythonTLSSnapshot. The thread carries two more sets, an included and an excluded set, changed by context managers. For each call:

keys = (∪ keys of the tensor arguments ∪ included) − excluded − fallthroughs

and the kernel of the highest key left runs. Two defaults explain a lot: ADInplaceOrView is in every thread's included set, and every Autocast key sits in the excluded set until you enter torch.autocast. So a plain tensor carries AutocastCPU, but the thread hides it. Watch it on a real call:

Four lessons in it. Under no_grad the autograd kernel still runs: grad mode is only a flag it reads before deciding not to record, and no key changes. Under inference_mode the autograd keys are excluded, so that kernel is skipped entirely (the custom op still visits ADInplaceOrView because the tensor was made outside the mode and keeps its own keys). Under autocast the input arrives as float32 at AutocastCPU and as bfloat16 everywhere below. And a TorchDispatchMode's Python key sits below autograd and ADInplaceOrView, so a mode sees calls after autograd has recorded them.

2.3 Behind each key, a table slot

Each operator keeps a dispatch table: one slot per key. A slot is filled by, in order: a kernel registered for exactly that key; else a kernel for an alias key that covers it (CompositeExplicitAutograd, one implementation for all backends; CompositeImplicitAutograd, a decomposition into other operators that also serves as its own autograd, the "math kernel"); else a backend fallback registered for every operator at that key; and a fallthrough means "skip this key". A fallback is boxed: the arguments arrive as a generic stack of values, which is what lets one function serve every operator. Counted over every operator in the wheel:

At the autograd keys the boxed fallback handles operators with no derivative registered, and that bites your own operators. A custom op tda2::noautograd with only a CPU kernel, called on a tensor that requires grad, returned a tensor with grad_fn MulBackward0 and backward ran, with only a warning: "tda2::noautograd: an autograd kernel was not registered to the Autograd key(s) but we are trying to backprop through it. This may lead to silently incorrect behavior." (fallback mode "warn"). The gradient is silently not what the op computes. 2.4 Autocast is just a key

torch.autocast(device, dtype) removes that device's Autocast key from the excluded set; nothing else. From then on every operator reaches the Autocast key first, and for most the slot is a fallthrough. Operators on the lower_precision_fp list (matrix multiplies, convolutions, attention, linear) get a kernel that casts their floating-point inputs to the autocast dtype; operators on the fp32 list (losses, norms, reductions that lose accuracy) cast to float32. Weights stay float32: the casts are new tensors on every forward. On the running example, one forward under bfloat16 autocast on the CPU made 180 aten calls against 137 without, 43 of them _to_copy casts; all 9 layer norms ran in float32, and the loss was 3.801377 against 3.801371 in float32 measured on Apple M1 Pro, CPU. Autocast does not make "the model" bf16; it makes chosen ops bf16. Pick "under autocast" in the walker above to see the cast happen at the top of the stack.

2.5 Keys that rewrite or skip the arithmetic: functionalisation, meta and fake tensors

Three more keys explain how compilers see your code without running it. Functionalize (a real kernel for 1,333 aten operators, a boxed fallback for the rest) wraps tensors and replays every in-place write as an out-of-place op, regenerating views from their base, so a traced graph has no mutation; torch.compile's AOTAutograd stage uses it ({{torch.compile from the user's side|n:3c65c17b0d0d8123a232d75bd7339ecb}} owns the compiler). A meta tensor has sizes, strides and a dtype but no storage; its Meta kernels only compute output metadata: built under with torch.device("meta"), the running example has 3,186,944 parameters, allocates nothing, and a forward returns logits of shape (8, 64, 43). A FakeTensor is the same idea with a device attached, a tensor subclass that dispatches at the Python key; under FakeTensorMode the running example ran forward and backward with no arithmetic, giving a blocks.0.mlp.fc.weight.grad of shape (1024, 256). torch.compile traces your model this way.

On meta, loss.item() fails: "Tensor.item() cannot be called on meta tensors". Building on meta is how you make a model too big for one machine and then materialise it shard by shard (to_empty plus your own initialisation).

2.6 What dispatch costs, and how to look

Each call pays for the key computation, each kernel it walks through and the Python binding before any arithmetic. For a one-element add, where the arithmetic is nothing, that is the whole time: 0.622 µs on a plain tensor, 1.06 µs when it records a node, 4.818 µs through a Python TorchDispatchMode measured on Apple M1 Pro, CPU, median of 3. A real matmul in the running example takes tens to hundreds of microseconds, so this matters only for many tiny ops: the reason torch.compile and CUDA graphs exist. To see every aten call of a program, a TorchDispatchMode whose __torch_dispatch__ logs func sees everything below autograd (that is how the root counted 923 calls in one step). What it sees depends on grad mode: in training F.linear reaches it as t plus addmm (decomposed at the autograd key); under inference_mode as linear (autograd skipped, so the decomposition happens below the mode).
