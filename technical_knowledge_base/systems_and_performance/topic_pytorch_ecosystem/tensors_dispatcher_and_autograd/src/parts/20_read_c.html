2. The dispatcher: one table lookup per call

The problem. One operator, say matrix multiply, has to do different things depending on context: cast to bfloat16 under mixed precision, record a graph node when gradients are needed, run on a CPU, an Apple GPU or a CUDA GPU, call back into Python when a tensor subclass or a tracing tool wants to see it, or only compute output shapes when the compiler is tracing. Writing all of that into every one of thousands of kernels is impossible to maintain. PyTorch separates the concerns and lets a table decide which ones apply to each call.

2.1 Operators and their schemas

An operator is a named function in the aten namespace (ATen is PyTorch's C++ tensor library) with a schema: its signature, including which arguments it writes to and which outputs alias an input. The schemas are declared in native_functions.yaml, which at v2.14.1 has - func: entries; the installed wheel registers operators in the aten namespace (more than the YAML entries, because out-variants and functional variants are generated). 2.2 Dispatch keys and their order

A dispatch key names one concern. Keys come in two parts: a functionality (Dense, Autograd, Autocast, Python, ...) and, for some functionalities, a backend bit (CPU, MPS, CUDA, ...). AutogradCPU is the Autograd functionality with the CPU bit. The functionality order is the priority: when several keys apply, the one with the highest number runs first. 2.3 The key set of one call: tensors, plus the thread, minus the thread

Every tensor carries a key set. The keys depend on what the tensor is, measured on real tensors:

The thread carries two more sets, an included set and an excluded set, changed by context managers. For each call the dispatcher computes

keys = (∪ keys of the tensor arguments ∪ included) − excluded − fallthroughs

and runs the kernel of the highest-priority key left. Two defaults explain a lot (quoted below): ADInplaceOrView is in the included set of every thread, and every Autocast key is in the excluded set until you enter torch.autocast. So a plain tensor carries AutocastCPU, but it is excluded until autocast removes the exclusion. Measured: the effective set for a plain CPU tensor in each context.

2.4 The dispatch table, and what "math kernel" and "fallthrough" mean

Each operator keeps a dispatch table: one slot per runtime key. A slot is filled by, in order: a kernel registered for exactly that key; else a kernel registered for an alias key that covers it (CompositeExplicitAutograd, one implementation for all backends; CompositeImplicitAutograd, a decomposition into other operators that also serves as its own autograd, shown as "math kernel"); else a backend fallback registered for every operator at that key; and a fallthrough means "skip this key". So: about a quarter of all operators decompose (739 math kernels at the CPU key, linear into t and addmm among them); ADInplaceOrView has a real kernel only for views and in-place ops and is a fallthrough for the rest; autocast touches only the operators on its list; and the Python key is a single boxed fallback that serves every operator. Boxed means the arguments arrive as a generic stack of values, which is what lets one function handle every operator.
