8. Memory: what fills it during one step

Five things live in memory during training (float32, AdamW, P parameters): parameters, 4 bytes × P, always; gradients, 4 bytes × P, built layer by layer in backward, freed by zero_grad(set_to_none=True); optimizer state, 8 bytes × P from the first step(); activations, saved by forward for backward, scaling with batch × sequence length; and short-lived temporaries. The fixed cost is 16 bytes per parameter (4 + 4 + 8); mixed-precision training with float32 master weights also comes to 16, split differently (2 + 2 + 12 in the ZeRO paper's accounting; {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}} owns that arithmetic and how sharding divides it).

9. Activation checkpointing as a lever, full and selective

Activation checkpointing keeps only each block's input in forward and reruns the block's forward in backward to rebuild what it needs: memory down, compute up by about one extra forward of the checkpointed part. Use checkpoint(block, x, use_reentrant=False); how it hooks autograd's saved tensors is on {{Tensors, the dispatcher and autograd|n:3f85c17b0d0d81138595c1c6cd52f795}}, the trade at cluster scale on {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}}. Selective activation checkpointing (SAC) lets a policy, called for every ATen op in the region, save some outputs anyway; the usual one saves matmul outputs (expensive to recompute) and recomputes element-wise ops ({{PyTorch blog, 2025|https://pytorch.org/blog/activation-checkpointing-techniques/}}; prototype since 2.5). The six CheckpointPolicy values at 2.14.1: MUST_SAVE, PREFER_SAVE, MUST_RECOMPUTE, PREFER_RECOMPUTE, MUST_CPU_OFFLOAD, PREFER_CPU_OFFLOAD read from the installed wheel.

from functools import partial from torch.utils.checkpoint import checkpoint, create_selective_checkpoint_contexts, CheckpointPolicy aten = torch.ops.aten SAVE = {aten.mm.default, aten.addmm.default, aten.bmm.default, aten._scaled_dot_product_flash_attention_for_cpu.default} # the CPU attention kernel; on CUDA name the flash/efficient ops def policy(ctx, op, *args, **kwargs): return CheckpointPolicy.MUST_SAVE if op in SAVE else CheckpointPolicy.PREFER_RECOMPUTE x = checkpoint(block, x, use_reentrant=False, context_fn=partial(create_selective_checkpoint_contexts, policy))

Full checkpointing cut the peak from 867.4 MB to 485.3 MB (44% less): forward now saves only each block's input, 42.3 MB instead of 546.4 MB. The price: backward runs 1,087 ATen calls instead of 567 (each block's forward again), and the step went from 389 ms to 475 ms on the CPU (+22%) and from 150 ms to 189 ms on MPS. SAC saving matmuls landed in between (724.6 MB, 411 ms on CPU); SAC saving only attention matched full checkpointing's peak (485.3 MB). Saving the matmuls saved little because here most activation bytes are matmul outputs (the MLP's 4d-wide fc and GELU outputs, the 3d-wide qkv projection); SAC pays off when expensive ops have small outputs, or when only some layers save. A policy must name the ops that actually run, and names differ by device (_scaled_dot_product_flash_attention_for_cpu on CPU, _scaled_dot_product_flash_attention or _efficient_attention on CUDA).

The numbers

Eager saves 546.4 MB; compiled at budget 1.0 546.8 MB, at 0.5 273.0 MB, at 0.2 109.1 MB, and at 0.0 nothing beyond the inputs (0.0 MB); eager checkpointing of every block keeps the block inputs, 42.3 MB. The loss is the same in all (3.81230, freshly initialised model on batch 1).

Under torch.compile the partitioner already decides what to save ({{torch.compile from the user's side|n:3c65c17b0d0d8123a232d75bd7339ecb}} owns it); torch._functorch.config.activation_memory_budget, default 1.0, makes it a memory target: in between it "solves a 0-1 knapsack to find the minimum recompute necessary to stay below the activation memory budget" (torch/_functorch/config.py L190 to 202 at 2.14.1). Budget 1.0 saves what eager saves: by default the partitioner optimises runtime, not memory. The PyTorch blog's example spells it torch._dynamo.config.activation_memory_budget; at 2.14.1 it lives in torch._functorch.config checked on the installed wheel.

When: activations dominate the peak and you would otherwise shrink the batch; not when weights and optimizer state dominate (shard those: FSDP2, the root's {{Distributed lab|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}}). Check: peak and step time before and after, and the same loss on the same batch.

10. The logits problem and fused linear cross-entropy

The logits, one score per vocabulary entry per position, are batch × sequence × V. With a real tokeniser (GPT-2's has 50,257 entries; the running example has 43 characters) the logits, their softmax and their gradient are the largest tensors of the step. To see it, the larger variant was given V = 50,257 (the batches still use only 43 characters, which changes no shapes and therefore no bytes): one logits tensor is 8 × 256 × 50,257 × 4 bytes = 411.7 MB.

A fused linear cross-entropy processes the positions in chunks: for each chunk it computes that chunk's logits, the loss and the gradient pieces, then frees them, so the full logits tensor never exists. The same idea is behind {{Liger Kernel|https://github.com/linkedin/Liger-Kernel}}'s fused linear cross-entropy and Apple's {{Cut Cross-Entropy|https://arxiv.org/abs/2411.09009}} (2024); PyTorch 2.13 added it to core as nn.LinearCrossEntropyLoss and F.linear_cross_entropy ({{2.13 release notes|https://github.com/pytorch/pytorch/releases/tag/v2.13.0}}, "up to 4x lower peak memory", release-note figure).

The default does not chunk
At 2.14.1, F.linear_cross_entropy(x, W, y) with the default options=None runs the reference path, which materialises all logits like the unfused code. The chunked path needs options=LinearCrossEntropyOptions() (from torch.nn.modules.linear_cross_entropy_options; its docstring: "Pass options=None to use the reference path; pass an instance of this class to opt in"). Measured below: the default saves exactly nothing.
from torch.nn.modules.linear_cross_entropy_options import LinearCrossEntropyOptions h = model.ln_f(hidden) # (B*T, d): stop before the head loss = F.linear_cross_entropy(h.view(-1, d), model.head.weight, y.view(-1), options=LinearCrossEntropyOptions()) # without options: no chunking
With a 50,257-entry vocabulary the chunked loss nearly halves the peak; the default call changes nothing

measured on Apple M1 Pro, the same loss in every run (8.9544 for all four).

Measured on Apple M1 Pro: how

measured on Apple M1 Pro, CPU, float32, PyTorch 2.14.1, deterministic (CPU memory profiler, src/exp/mem_step.py); the same loss in every run (8.9544 for all four). Step time, median of 3 trials of 5 steps: unfused 827 ms, chunked 1398 ms on CPU; 491 ms and 900 ms on MPS (load average 3.5; bench lock).

The unfused step peaks at 2394.2 MB; at that moment the backward temporaries alone hold 823.4 MB, the softmax's gradient and the logits' gradient, two tensors of 411.7 MB each. The chunked loss brings the peak to 1278.8 MB (1.87 times lower), and its saved activations from 957.8 MB to 541.9 MB, about what the 43-character model saves (546.4 MB): the vocabulary no longer costs activation memory. The default call (2394.2 MB) is byte for byte the unfused peak. Against the release notes' "up to 4x", this whole step (weights, AdamW state, block activations included) gains 1.87 times, and pays in time: +69% on the CPU, +84% on MPS. The docstring's rule: chunking "is a win when num_batches >= in_features and num_classes > in_features; below that, the reference path is cheaper". Logits scale with tokens × V, not width, so a small model with a big tokenizer is hit hardest. Check: the peak with and without, and the loss to rounding.
