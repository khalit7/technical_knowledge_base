12. torchao: fewer bits for weights, activations and gradients

Fewer bits mean less memory, less data moved and, with matching hardware, faster matmuls. torchao (pip install torchao, 0.18.0 here, released 2026-08-03) is PyTorch's library for that, for inference and training; the formats themselves (int8, int4, float8 E4M3 and E5M2, the MX block formats) belong to {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}. quantize_(model, config) walks the model and replaces each nn.Linear's weight with a tensor subclass (a Python class that wraps the low-bit data and its scales and intercepts every op on it; built as on {{Extending PyTorch|n:3f85c17b0d0d8158a7addcd3d601d72a}}). The module code is unchanged: when F.linear reaches the subclass it dispatches to a quantized kernel or dequantizes, and because it is a subclass it composes with torch.compile, FSDP2 and DTensor.

int8 cuts the weights four times at no loss; "int4" on the CPU is stored in bytes and comes out larger than int8

measured on Apple M1 Pro, CPU: the larger variant after 150 training steps, every Linear except the tied head quantized.

Measured on Apple M1 Pro: how

measured on Apple M1 Pro, CPU, torchao 0.18.0, PyTorch 2.14.1 (src/exp/torchao_lab.py): the larger variant after 150 training steps, every Linear except the tied head quantized. "Linear bytes": every inner tensor of the 32 block weights plus the head's float32 weight (data, scales, zero points). Loss on 8 fixed batches of the same text (the model has no held-out data: it is a toy). Logit difference against the float32 model on one batch.

Int8 weight-only cut the Linear weights from 100.8 MB to 25.4 MB (3.96 times smaller: 1 byte per weight plus one float32 scale per row) and moved the loss by 0.00002. Int4WeightOnlyConfig failed with "ImportError: Requires mslk >= 1.0.0" (it needs a separate kernel package), and the CPU-capable IntxWeightOnlyConfig(int4) stores each 4-bit value in a full byte (IntxUnpackedToInt8Tensor) plus a scale per group of 32, so it is larger than int8 (29.2 MB). "int4" names the value grid, not the storage: check bytes, do not assume them. float8 weight-only runs on the CPU; dynamic float8 activations do not.

A quantization config is only as fast as the kernel it reaches: one 4096 × 4096 Linear, one token against 2,048
Measured on Apple M1 Pro: how

A one-token matmul is memory-bound, so fewer bytes per weight should mean less time. Yet int8 weight-only took 3.16 ms and int4 (Intx) 5.99 ms against float32's 2.18 ms at M = 1: in eager mode the int8 weight is converted to float32 on every call, then multiplied with an ordinary torch.mm (torchao 0.18.0, int8_tensor.py L337 to 354). Dynamic int8 activations with int8 weights multiply int8 by int8 (int_scaled_matmul, L315): 0.40 ms for one token (5.4 times faster than float32) but 250 ms for 2,048 tokens against 37.0 ms (float32 BLAS is far better tuned here). On GPUs the weight-only paths have dedicated kernels, not represented here. The rule: weight-only for memory-bound work (small-batch decoding), quantized activations for compute-bound work (large batches, prefill, training).

float8 training (torchao.float8.convert_to_float8_training(model)) swaps each Linear for a Float8Linear that casts inputs, weights and output gradients to float8 with a scale per tensor (or row), runs the matmul on float8 tensor cores and keeps master weights in higher precision: up to 1.5 times the throughput at 512 GPUs on a 405B model vendor, torchao README ({{torchao|https://github.com/pytorch/ao}}). It needs compute capability 8.9 or newer (Ada, Hopper, Blackwell) or AMD MI300 ("requires CUDA compute capability ≥8.9 or MI300+ or XPU", reproduced as the error here). Float8LinearConfig(emulate=True) runs the same casts and scales with a float32 matmul: the numerics, not the speed.

Emulated float8 tracks float32 except for one spike: 60 training steps, same seed, same batches

measured on Apple M1 Pro, CPU, torchao 0.18.0, the running example; the head (256 × 43) stays in float32 because float8 matmuls need both dimensions divisible by 16 (src/exp/torchao_lab.py). The two runs end at 2.183 (float32) and 2.194 (float8), within the step-to-step noise, except for one spike at step 11 (5.39 against 2.90) that the next step recovers from. A spike like that, from a tensor whose scale is set by one large value, is what scaling recipes (per-row scales, MX blocks) and loss-spike monitoring exist for; this run did not investigate its cause.

Quantizing after training (PTQ) rounds weights the model never saw rounded. Quantization-aware training (QAT) fine-tunes with fake quantization: forward rounds weights to the target grid and back to float, backward treats the rounding as identity, so the weights learn to sit where rounding hurts least. In torchao: quantize_(m, QATConfig(base_config, step="prepare")), train, then quantize_(m, QATConfig(base_config, step="convert")). Run here on the running example: fake quantization reproduced the converted model's loss exactly (0.35054 both), which is the whole point; on a model this small int4 costs almost nothing, so QAT had nothing to recover.

QAT against PTQ, MX formats and the other torchao pieces (measured and reference)

QAT run. CPU, IntxWeightOnlyConfig(int4, group 32) as the base config: 300 float32 steps, then 100 more steps either in float32 followed by quantization (PTQ) or with fake-quantized weights (QAT) followed by conversion. QAT ended slightly worse than PTQ here; its value shows on large models where PTQ loses accuracy.

MX formats (MXFP8, MXFP4; and NVIDIA's NVFP4) put one shared scale on every block of 32 (MX) or 16 (NVFP4) values, so outliers cost less precision than with one scale per tensor. In torchao 0.18.0 they live in torchao.prototype.mx_formats (MXDynamicActivationMXWeightConfig, NVFP4DynamicActivationNVFP4WeightConfig; listed from the installed package) and target Blackwell's block-scaled tensor cores. Not run here: no Blackwell GPU, and no CPU emulation was attempted.

Other pieces: torchao.optim.AdamW8bit and AdamW4bit (optimizer state in 8 or 4 bits: the 8 bytes per parameter of section 8 shrink to about 2 or 1), CPUOffloadOptimizer (state and the step on the CPU), sparsify_ for 2:4 sparsity on GPUs that accelerate it. All present in 0.18.0 checked; not run here.
