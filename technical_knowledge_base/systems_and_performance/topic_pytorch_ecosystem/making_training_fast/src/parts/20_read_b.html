3. The worked hunt: one slow step, fixed one bottleneck at a time

The job. The larger variant trained through a DataLoader, written the way a first version usually is:

loader = DataLoader(dataset, batch_size=8) # num_workers=0: batches built in the main process model = make_model(GPTConfig(..., attn="manual")) # attention written out: softmax(QK^T / sqrt(d)) V opt = torch.optim.AdamW(params, lr=6e-4) # default implementation: for-loop on CPU and MPS for x, y in loader: _, loss = model(x.to(dev), y.to(dev)) # float32 everywhere loss.backward(); opt.step(); opt.zero_grad(set_to_none=True) print(loss.item()) # waits for the device every step

The dataset spends 2 ms of Python work per sample before returning a window of text illustrative cost: a stand-in for decoding and tokenising raw data, set by hand so that data loading is visible. Everything else is the real model.

Step two: apply one fix at a time, keep it only if it beats the spread

Fig. 2 builds the step time fix by fix: each block is the median of three runs of 20 steps, compared with the block it was built on; a fix that is slower beyond the spread of both steps aside (to the back) and is reverted, and the next fix is built on the last kept block.

  1. Baseline: 162.3 ms. Everything as first written (range 161.5 to 164.8 ms over the three runs).
  2. + DataLoader workers: 146.4 ms, kept. 15.9 ms faster, beyond the spread of both: two worker processes build batches in the background, so the 16 ms of Python work per batch overlaps the step.
  3. + fused AdamW: 139.0 ms, kept. 7.3 ms faster: one fused kernel updates all 100 parameter tensors instead of several small ops per tensor.
  4. + SDPA: 143.0 ms, kept anyway. 4.0 ms slower: on MPS with gradients SDPA runs the same math path as the written-out attention (section 11), so there is nothing to gain. It stays because it is the right default wherever a fused kernel exists (CPU here, CUDA); a strict hunt on this machine alone would revert it.
  5. + no per-step sync: 143.0 ms, no measurable change. Without .item() every step the CPU can queue the next step while the GPU works; here the GPU is the bottleneck, so overlap buys little.
  6. + bfloat16 autocast: 208.0 ms, reverted. 65.1 ms slower: on hardware without native bfloat16 arithmetic the conversions cost more than they save (section 6). The block steps aside; the next fix is built on step 5.
  7. + torch.compile: 133.6 ms, kept. 9.3 ms faster than step 5: Inductor fuses the element-wise ops (LayerNorm, GELU, residual adds, masking) into generated Metal kernels, so fewer launches and fewer round trips to memory.
  8. + compile and bfloat16: 196.2 ms, reverted. The bfloat16 cost dominates again. Final: torch.compile and everything before it except bfloat16, 133.6 ms.
  1. Baseline: 429.4 ms. Everything as first written (range 427.7 to 430.3 ms).
  2. + DataLoader workers: 414.9 ms, kept. 14.5 ms faster: the loading overlaps the step.
  3. + fused AdamW: 395.0 ms, kept. 19.9 ms faster.
  4. + SDPA: 362.3 ms, kept. 32.7 ms faster, the biggest gain on this device: on the CPU SDPA runs a flash-style kernel instead of materialising the 256 × 256 scores per head.
  5. + no per-step sync: 373.8 ms, no measurable change. On the CPU .item() costs nothing (no device to wait for); its range overlaps step 4's, so the difference is noise.
  6. + bfloat16 autocast: 43.7 s, reverted. About 117 times slower: this CPU has no bfloat16 instructions (section 6). The block is drawn cut off at the top.
  7. + torch.compile: 371.7 ms, no measurable change. The step is dominated by matmuls, which compiled code still hands to the same BLAS library. Final: SDPA and the fixes before it, 362.3 ms.

In sum: on MPS 162 ms became 134 ms (1.21 times faster), and the biggest gain was the least glamorous, DataLoader workers (15.9 ms); on the CPU 429 ms became 362 ms (1.19 times), led by the attention kernel. bfloat16 autocast lost on both (on the CPU 43.7 seconds per step, 2 runs of 3 steps). On an NVIDIA GPU the ranking would likely change; the method would not.

measured on Apple M1 Pro, PyTorch 2.14.1; per stage the median of 3 runs of 20 steps after 8 warm-up steps, timed with a synchronize at both ends; bench lock, load average quoted in the recorded inputs (src/exp/hunt.py). The same step traced, before and after

Two real torch.profiler traces of one MPS step: as first written, and with the fixes the hunt kept. Lanes are threads: the main thread runs the record_function ranges, a second lane is autograd's device thread running backward.

  1. Before: data, 17.5 ms. With num_workers=0 the main thread builds the batch itself: the Dataset's Python work runs right here, and nothing else happens.
  2. Forward 5.0 ms, backward 10.3 ms. The CPU walks the model's Python code and only queues one kernel after another; autograd runs backward on its own device thread (the second lane, 9.4 ms busy).
  3. Optimizer, 11.8 ms. The for-loop AdamW: several small ops per tensor (addcmul_ and addcdiv_ 100 calls each), every one a launch.
  4. .item(), 117.6 ms: 72.4% of the step. .item() copies one number to Python, so it must wait until every queued GPU kernel has finished: this bar is the GPU's backlog showing up on the CPU (aten::_local_scalar_dense).
  5. After: the wait has moved into data. With workers, fused AdamW, SDPA, no per-step sync and torch.compile, forward takes 3.2 ms, backward 5.0 and the optimizer 0.8; the CPU runs ahead until the next thing that needs the GPU, copying the next batch (aten::copy_, 123.7 ms of a 124.1 ms data range).
  6. On one clock: 162.3 ms against 133.0 ms. The step is GPU-bound either way. What shrank is the GPU work and the serial loading in front of it; the gap between the two ends is what the fixes saved.

The wait moves; it does not vanish. On MPS the CPU only enqueues work, so the GPU's timeline is not in this trace (Fig. 3 marks its lane as not recorded; on CUDA ProfilerActivity.CUDA adds it, on MPS it goes to Instruments via torch.mps.profiler.profile()). The 117.6 ms in .item() is every queued kernel finishing; after the hunt the same wait sits in the next batch's copy.

Where the time went: ATen ops by self time, before and after (table)

How close to the hardware's limit? Model FLOPs utilisation (MFU) = model FLOPs per step / step time / peak. One step needs 6 × 25,373,184 parameters × 2,048 tokens = 311.8 GFLOP plus 12 × L × T × d per token for attention (12 × 8 × 256 × 512 × 2,048 = 25.8 GFLOP): 337.6 GFLOP derived. With this GPU's measured float32 matmul rate as the peak (4,087.5 GFLOP/s, section 6; Apple publishes none), MFU = 337.6 / 0.162 / 4,087.5 = 51% as first written and 62% after the hunt; on the CPU (1,854.3 GFLOP/s) 42% and 50% derived, src/derive_mfu.py. The fixes removed overhead around the matmuls; what remains is matmuls. Peaks of real GPUs and MFU of published runs: {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}.

The method, which is the point
  1. Time the whole step honestly, then split it: phases with a synchronize, and a trace.
  2. Fix the biggest piece with the cheapest change that targets it.
  3. Measure again with the spread; keep the change only if it beats the noise, even if "everyone uses it".
  4. Check the loss is unchanged on the same batches (it was, to the printed digits, for every float32 stage here).
  5. Repeat until what remains is matmuls on a busy device, which MFU measures.
