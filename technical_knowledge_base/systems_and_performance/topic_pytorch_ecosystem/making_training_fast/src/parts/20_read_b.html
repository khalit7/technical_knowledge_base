3. The worked hunt: one slow step, fixed one bottleneck at a time

The job. The larger variant trained through a DataLoader, written the way a first version usually is:

loader = DataLoader(dataset, batch_size=8) # num_workers=0: batches built in the main process model = make_model(GPTConfig(..., attn="manual")) # attention written out: softmax(QK^T / sqrt(d)) V opt = torch.optim.AdamW(params, lr=6e-4) # default implementation: for-loop on CPU and MPS for x, y in loader: _, loss = model(x.to(dev), y.to(dev)) # float32 everywhere loss.backward(); opt.step(); opt.zero_grad(set_to_none=True) print(loss.item()) # waits for the device every step

The dataset spends 2 ms of Python work per sample before returning a window of text illustrative cost: a stand-in for decoding and tokenising raw data, set by hand so that data loading is visible. Everything else is the real model.

Measured on Apple M1 Pro: how

On MPS the step went from 162 ms to 134 ms (1.21 times faster; final configuration: torch.compile and everything before it except bfloat16); on the CPU from 429 ms to 362 ms (1.19 times; final: SDPA and the fixes before it). On MPS the biggest gain was the least glamorous: DataLoader workers (15.9 ms), then torch.compile (9.3 ms), then the fused optimizer (7.3 ms). On the CPU the attention kernel mattered (32.7 ms) and compile did not (372 ms against 374 ms). bfloat16 autocast lost on both: 208 ms against 143 ms on MPS, 43.7 seconds per step on the CPU (2 runs of 3 steps) against 374 ms (section 6). On an NVIDIA GPU the ranking would likely change; the method would not.

Measured on Apple M1 Pro: how

The wait moves; it does not vanish. On MPS the CPU only enqueues work, so the GPU's timeline is not in this trace (on CUDA ProfilerActivity.CUDA adds it; on MPS it goes to Instruments via torch.mps.profiler.profile()). "Before", the CPU waits 117.6 ms in .item() (aten::_local_scalar_dense, 72.4% of the traced step): every queued kernel finishing. "After", the CPU runs ahead until the next thing that needs the GPU, copying the next batch (aten::copy_, 123.7 ms). The step is GPU-bound either way; what shrank is the GPU work and the serial loading in front of it.

Where the time went: ATen ops by self time, before and after (table)

How close to the hardware's limit? Model FLOPs utilisation (MFU) = model FLOPs per step / step time / peak. One step needs 6 × 25,373,184 parameters × 2,048 tokens = 311.8 GFLOP plus 12 × L × T × d per token for attention (12 × 8 × 256 × 512 × 2,048 = 25.8 GFLOP): 337.6 GFLOP derived. With this GPU's measured float32 matmul rate as the peak (4,087.5 GFLOP/s, section 6; Apple publishes none), MFU = 337.6 / 0.162 / 4,087.5 = 51% as first written and 62% after the hunt; on the CPU (1,854.3 GFLOP/s) 42% and 50% derived, src/derive_mfu.py. The fixes removed overhead around the matmuls; what remains is matmuls. Peaks of real GPUs and MFU of published runs: {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}.

The method, which is the point
  1. Time the whole step honestly, then split it: phases with a synchronize, and a trace.
  2. Fix the biggest piece with the cheapest change that targets it.
  3. Measure again with the spread; keep the change only if it beats the noise, even if "everyone uses it".
  4. Check the loss is unchanged on the same batches (it was, to the printed digits, for every float32 stage here).
  5. Repeat until what remains is matmuls on a busy device, which MFU measures.
