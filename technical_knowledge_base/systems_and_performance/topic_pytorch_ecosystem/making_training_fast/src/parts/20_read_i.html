8. Activation checkpointing, full and selective

The problem. Section 7's activations are the part that grows with batch and sequence length. Activation checkpointing (also called rematerialisation) keeps only each block's input during forward and runs the block's forward a second time during backward to rebuild what it needs. Memory goes down; compute goes up by roughly one extra forward of the checkpointed part.

How it works in PyTorch. torch.utils.checkpoint.checkpoint(block, x, use_reentrant=False). The non-reentrant version (the one to use; the root's {{Inside one step|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}} tab measured it) hooks into autograd's saved-tensor mechanism: during forward it saves nothing inside the block, and when backward first asks for a saved tensor, it reruns the block's forward. It also stops the recomputation early, as soon as it has rebuilt the last tensor backward needs (torch/utils/checkpoint.py at 2.14.1).

Selective activation checkpointing (SAC) keeps the checkpoint region but lets a policy decide, op by op, what to save anyway. The policy is a function called for every ATen op inside the region; it returns one of six CheckpointPolicy values at 2.14.1: MUST_SAVE, PREFER_SAVE, MUST_RECOMPUTE, PREFER_RECOMPUTE, MUST_CPU_OFFLOAD, PREFER_CPU_OFFLOAD read from the installed wheel (the last two move the saved tensor to host memory instead of dropping it). The usual policy saves matmul outputs, which are expensive to recompute, and recomputes cheap element-wise ops ({{PyTorch blog, 2025|https://pytorch.org/blog/activation-checkpointing-techniques/}}; SAC shipped as a prototype in 2.5):

from functools import partial from torch.utils.checkpoint import checkpoint, create_selective_checkpoint_contexts, CheckpointPolicy aten = torch.ops.aten SAVE = {aten.mm.default, aten.addmm.default, aten.bmm.default, aten._scaled_dot_product_flash_attention_for_cpu.default} # the CPU attention kernel; on CUDA name the flash/efficient ops def policy(ctx, op, *args, **kwargs): return CheckpointPolicy.MUST_SAVE if op in SAVE else CheckpointPolicy.PREFER_RECOMPUTE x = checkpoint(block, x, use_reentrant=False, context_fn=partial(create_selective_checkpoint_contexts, policy))

Why "save the matmuls" saved so little here
In this model most activation bytes are matmul outputs: the MLP's 4d-wide hidden layer (fc output, then GELU output) and the 3d-wide qkv projection. A policy that saves every matmul keeps most of what plain training keeps. Saving only the attention output and recomputing everything else gives full checkpointing's peak. SAC pays off when the expensive ops have small outputs and the cheap ops have big ones, or when you save some layers' matmuls and not others; measure with your model, do not assume.

The compile-only shortcut. Under torch.compile, AOTAutograd's partitioner already decides what to save and what to recompute (the {{torch.compile child|n:3c65c17b0d0d8123a232d75bd7339ecb}} owns it). One knob turns that decision into a memory target: torch._functorch.config.activation_memory_budget, default 1.0 (the runtime-optimised choice); 0.0 means as little as checkpointing the whole compiled region; in between, it "solves a 0-1 knapsack to find the minimum recompute necessary to stay below the activation memory budget" (torch/_functorch/config.py L190 to 202 at 2.14.1). The PyTorch blog's example spells it torch._dynamo.config.activation_memory_budget; at 2.14.1 the setting lives in torch._functorch.config checked on the installed wheel.

When it matters. When activations dominate the peak (long sequences, big micro-batches) and you would otherwise shrink the batch. When it does not: when weights and optimizer state dominate (shard those instead: FSDP2 in the {{Distributed lab|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}}), or when you are compute-bound and memory is not the limit. How to check it: peak memory before and after (section 7's tools), step time before and after, and the loss on the same batch, which must not change.
