0. In one screen

A training job is slow or out of memory for one main reason at a time. Find it by measuring, fix that one thing, measure again. This page does that on the topic's running example (a small GPT, see the root page) and on a larger variant of it, on an Apple M1 Pro's CPU and GPU, and says for every result what carries over to NVIDIA GPUs.

Three ideas the rest of the page keeps using
  • A GPU runs behind the CPU. PyTorch queues work and returns; the CPU only waits when it needs a result (.item(), printing, copying to the CPU). Timings and traces must account for that.
  • Count bytes and launches, not just FLOPs. Element-wise ops move memory and cost a launch each; matmuls do arithmetic. Most fixes either remove launches (fusing) or remove bytes (fewer saved activations, fewer bits).
  • Peak memory is a moment. It is what is alive at one instant: usually the start of backward, sometimes its end. Fixes that do not touch what is alive at that instant do not lower the peak.

Labels used throughout: measured on this machine with PyTorch 2.14.1 (scripts in this page's src/exp/), vendor for a figure published by the people who built the thing, derived for arithmetic on other numbers, illustrative for an input chosen by hand. Timed runs held a lock so no other job of this knowledge base ran at the same time; the load average is quoted next to them.

1. Measuring honestly: what a timing can and cannot tell you

The problem. Every fix on this page is judged by a number, and a careless number points at the wrong fix. Three things make naive timings lie.

Asynchronous devicesOn a GPU (CUDA or Apple's MPS), a PyTorch call only queues a kernel and returns. Timing the call times the queuing. You must wait for the device to finish (torch.cuda.synchronize(), torch.mps.synchronize()) before reading the clock.
Warm-upThe first calls pay one-off costs: memory allocation into the caching allocator, kernel selection, compilation for torch.compile, lazy initialisation. Run a few untimed steps first.
NoiseOther processes, thermal limits and frequency scaling move every number. Repeat, report the median and the spread, and record the machine's load.

The same matrix multiply, timed three ways on MPS

torch.utils.benchmark.Timer does the bookkeeping: it warms up, chooses how many runs fit in a time budget, sets the thread count, and reports the median and interquartile range (IQR, the spread of the middle half of the runs). At 2.14.1 its default clock calls torch.accelerator.synchronize() before every reading whenever an accelerator is present, CUDA or MPS alike (torch/utils/benchmark/utils/timer.py L15 to 18). This page's scripts also synchronised inside the timed statement, which is redundant but harmless:

import torch.utils.benchmark as tb def call(): a @ b; torch.mps.synchronize() # redundant at 2.14.1: Timer's clock synchronises the accelerator m = tb.Timer(stmt="call()", globals={"call": call}).blocked_autorange(min_run_time=1.0) print(m.median, m.iqr, len(m.times))

Whole training steps are timed the simple way: warm up, synchronise, start the clock, run N steps, synchronise, stop, divide; repeat the whole thing three times and take the median. Every timed result on this page was taken that way or with Timer, while holding a lock so that no other job of this knowledge base ran at the same time, with the load average recorded next to it.

What carries over to NVIDIA GPUs, and what does not
The method carries over exactly, and so do byte counts, op counts, which ops exist and which fixes apply. The times do not: an M1 Pro's CPU and GPU have their own balance of compute, memory bandwidth and launch cost, so a fix that wins 20% here can win 2% or 2 times on an H100. This page says, for each result, which way it is likely to move on a data-centre GPU and why; the honest-timing details for CUDA (CUDA events, cudaDeviceSynchronize, Nsight) are on Profiling, benchmarking and correctness.

2. torch.profiler from zero

The problem. A step time says how slow; it does not say where. torch.profiler records every operator PyTorch runs (with start and end time, thread, input shapes if asked, the Python stack if asked, memory allocated if asked) and, on CUDA, every GPU kernel and memory copy. Its output is a trace: a timeline you can open in a viewer.

from torch.profiler import profile, schedule, record_function, ProfilerActivity with profile(activities=[ProfilerActivity.CPU], # add ProfilerActivity.CUDA on NVIDIA GPUs schedule=schedule(wait=4, warmup=2, active=2), # skip 4 steps, warm the profiler 2, record 2 record_shapes=True, # input shapes per op (for "which matmul?") on_trace_ready=lambda p: p.export_chrome_trace("trace.json")) as prof: for step in range(8): with record_function("data"): x, y = next(it) with record_function("forward"): _, loss = model(x, y) with record_function("backward"): loss.backward() with record_function("optimizer"): opt.step(); opt.zero_grad(set_to_none=True) prof.step() # tells the schedule a step ended print(prof.key_averages().table(sort_by="self_cpu_time_total", row_limit=10))
  • schedule(wait, warmup, active, repeat): profiling every step of a long run would be slow and huge. The schedule skips wait steps, runs the profiler without keeping results for warmup steps (its own start-up cost lands there), then records active steps; repeat cycles it. prof.step() at the end of each step drives it. Signature at 2.14.1: schedule(*, wait, warmup, active, repeat=0, skip_first=0, skip_first_wait=0) read from the installed wheel.
  • record_function("name"): a labelled range in the trace. Cheap; leave a few in your training loop for good.
  • key_averages(): the same events summed by name. Total time includes children (aten::linear includes its aten::addmm); self time excludes them. Sort by self time to find the ops doing the work.
  • with_stack=True links each op to the Python line that called it (larger traces); profile_memory=True records allocations (section 7). On CUDA with compiled code, TORCHINDUCTOR_UNIQUE_KERNEL_NAMES=1 gives generated kernels readable names.
  • Viewers: Perfetto or chrome://tracing open the exported JSON; tensorboard_trace_handler(dir) writes files for TensorBoard; for many ranks at once, Holistic Trace Analysis summarises idle time, communication overlap and stragglers across ranks.

What to look for in a trace. On a GPU, the device lane should be busy end to end. Gaps on it mean the GPU waited for something: the data loader (gaps before forward), the CPU launching many tiny kernels (launch-bound: fix with fusion, torch.compile, CUDA graphs, fused optimizers), or a synchronisation such as .item(), .cpu() or print(loss) (a device-to-host copy). In multi-GPU traces, communication kernels that do not overlap compute. On a CPU, the bars are the work, so look for the widest ones.

3. The worked hunt: one slow step, fixed one bottleneck at a time

The job. The running example's larger variant (8 blocks, d 512, 8 heads, context 256, batch 8: 25.4M parameters) trained through a DataLoader, written the way a first version usually is:

loader = DataLoader(dataset, batch_size=8) # num_workers=0: batches built in the main process model = make_model(GPTConfig(..., attn="manual")) # attention written out: softmax(QK^T / sqrt(d)) V opt = torch.optim.AdamW(params, lr=6e-4) # default implementation: for-loop on CPU and MPS for x, y in loader: _, loss = model(x.to(dev), y.to(dev)) # float32 everywhere loss.backward(); opt.step(); opt.zero_grad(set_to_none=True) print(loss.item()) # waits for the device every step

The dataset spends 2 ms of Python work per sample before returning a window of text illustrative cost: a stand-in for decoding and tokenising raw data, set by hand so that data loading is visible. Everything else is the real model.

Step one: where does the baseline step go? (per-phase time, synchronised after each phase)

Predict before reading on: on the Apple GPU (MPS), which change will speed this step up the most?

Step two: apply one fix at a time, keep it only if it helps (median step time)

The method, which is the point
  1. Time the whole step honestly (section 1), then split it: per-phase timings with a synchronize, and a trace (section 2).
  2. Fix the biggest piece with the cheapest change that targets it.
  3. Measure again, with the spread. Keep the change only if the gain is larger than the noise; revert it otherwise, even if "everyone uses it".
  4. Check the loss is unchanged on the same batches (it was, to the printed digits, for every float32 stage here).
  5. Repeat until the remaining time is the work itself: matmuls on a busy device.

4. Data loading: keep the next batch ready

The problem. If the training loop asks for a batch and the batch is not ready, everything waits. With DataLoader(num_workers=0) (the default) the main process reads, decodes and collates every sample itself, between steps, so loading time adds straight onto step time.

How it works. num_workers=n starts n worker processes that each build whole batches in the background; prefetch_factor (default 2 when workers are used) is how many batches each worker keeps ready ahead; persistent_workers=True keeps them alive between epochs instead of paying their start-up each epoch. pin_memory=True puts batches in page-locked host memory so a CUDA copy can run asynchronously with x.to("cuda", non_blocking=True); it is a CUDA mechanism (signature at 2.14.1 includes pin_memory_device and in_order, read from the installed wheel), and on an Apple chip the CPU and GPU share one memory, so it was not measured here.

A loop that needs 20 ms per step, fed by a loader whose batches cost 16 ms to build

When it matters. Whenever building a batch takes a noticeable share of the step: decoding images or audio, tokenising on the fly, reading from network storage, heavy augmentation. Pre-tokenised data in memory-mapped arrays (as LLM pre-training usually uses) barely needs workers. How to check it: in a trace, the data range (or gaps on the GPU before forward); or time next(iter(loader)) on its own. Workers are separate processes: each holds its own copy of the Dataset object, so keep it small, and on macOS and Windows they start with spawn, so the Dataset must be importable and picklable.

5. The optimizer step: one kernel or hundreds

The problem. AdamW's update is a handful of element-wise operations per parameter tensor. Written as a Python loop over tensors (the for-loop implementation), that is several separate operator calls for each of the model's tensors (100 tensors in the larger variant, 52 in the small one), each with Python and dispatcher overhead and, on a GPU, a separate kernel launch.

How it works. Two faster implementations exist. foreach uses torch._foreach_* operators that take a whole list of tensors per call (a few launches per step instead of several per tensor). fused does the whole update for all parameters in one kernel per device and dtype group. Select with torch.optim.AdamW(..., foreach=True) or fused=True. At 2.14.1 the default is foreach on CUDA-like devices and the for-loop on CPU and MPS; fused is never the default though it runs on CPU, MPS and CUDA (torch/utils/_foreach_utils.py L8 to 23, per the root's Inside one step measurements).

One AdamW step, three implementations

When it matters. Many parameter tensors, small model, or a fast device where the arithmetic is cheap and launches dominate. Cost: foreach and fused keep temporary lists or buffers; fused needs every parameter on a supported device and dtype. Check: the optimizer range in a trace, or time opt.step() on its own as above.

6. Mixed precision: fewer bits per number

The problem. float32 uses 4 bytes per number; bfloat16 and float16 use 2. Half the bytes means half the memory traffic, and on GPUs with tensor cores the 16-bit matmuls also run several times faster. Automatic mixed precision (AMP) gets most of that without rewriting the model: inside torch.autocast(device_type, dtype=torch.bfloat16), ops on autocast's lists (matmuls, linear layers, attention) run in 16 bits, precision-sensitive ops (softmax, normalisation, losses) stay in float32, and the parameters themselves stay float32.

  • bfloat16 keeps float32's exponent range (8 exponent bits) with fewer mantissa bits: no overflow, so no loss scaling needed. The usual choice on recent GPUs.
  • float16 has more mantissa but a narrow range: small gradients underflow to zero, so it needs torch.amp.GradScaler, which multiplies the loss by a large factor before backward, divides gradients before the step, and skips steps whose gradients overflowed.
scaler = torch.amp.GradScaler("cuda") # only for float16 with torch.autocast("cuda", dtype=torch.float16): _, loss = model(x, y) scaler.scale(loss).backward(); scaler.step(opt); scaler.update(); opt.zero_grad(set_to_none=True)

What bfloat16 did on this machine

This is the result that does not transfer
Data-centre NVIDIA GPUs since the A100 have bfloat16 tensor cores; there, bfloat16 matmuls run many times faster than float32 ones and AMP is close to free speed. This M1 Pro's CPU reports no bfloat16 instructions (sysctl hw.optional.arm.FEAT_BF16 = 0, while FEAT_FP16 = 1) read on this machine, so bfloat16 math on it is converted and pays for the conversion; the measured MPS slowdown points the same way for its GPU (not checked against Apple documentation). The lesson that does transfer: check that the hardware has native support for the dtype before expecting a speedup, and measure.

7. Memory: what fills it during one step

The problem. A job that runs out of memory stops; a job that barely fits runs with a small batch and wastes the hardware. Before cutting memory you need to know what holds it and when, because the peak is a moment, not a total.

Five things live in memory during training (sizes for float32 and AdamW, with P parameters):

Parameters4 bytes × P. Alive the whole time.
Gradients4 bytes × P. Created during backward, layer by layer; freed by zero_grad(set_to_none=True).
Optimizer stateAdamW keeps two running averages per parameter: 8 bytes × P. Created at the first step(), alive from then on.
ActivationsTensors the forward pass saves for backward (section 3 of the root). They grow through forward and shrink through backward. They scale with batch × sequence length.
TemporariesShort-lived: a matmul's output before the next op consumes it, gradients of activations flowing back through backward.

So the fixed cost is 16 bytes per parameter (4 + 4 + 8). Mixed-precision training with float32 master weights also comes to 16 bytes, split differently (2 + 2 + 12 in the ZeRO paper's accounting; Distributed Training owns that arithmetic and how sharding divides it). The variable cost is the activations, and the peak usually lands at the start of backward, when every activation is still saved and the first gradients start to appear.

8. Activation checkpointing, full and selective

The problem. Section 7's activations are the part that grows with batch and sequence length. Activation checkpointing (also called rematerialisation) keeps only each block's input during forward and runs the block's forward a second time during backward to rebuild what it needs. Memory goes down; compute goes up by roughly one extra forward of the checkpointed part.

How it works in PyTorch. torch.utils.checkpoint.checkpoint(block, x, use_reentrant=False). The non-reentrant version (the one to use; the root's Inside one step tab measured it) hooks into autograd's saved-tensor mechanism: during forward it saves nothing inside the block, and when backward first asks for a saved tensor, it reruns the block's forward. It also stops the recomputation early, as soon as it has rebuilt the last tensor backward needs (torch/utils/checkpoint.py at 2.14.1).

Selective activation checkpointing (SAC) keeps the checkpoint region but lets a policy decide, op by op, what to save anyway. The policy is a function called for every ATen op inside the region; it returns one of six CheckpointPolicy values at 2.14.1: MUST_SAVE, PREFER_SAVE, MUST_RECOMPUTE, PREFER_RECOMPUTE, MUST_CPU_OFFLOAD, PREFER_CPU_OFFLOAD read from the installed wheel (the last two move the saved tensor to host memory instead of dropping it). The usual policy saves matmul outputs, which are expensive to recompute, and recomputes cheap element-wise ops (PyTorch blog, 2025; SAC shipped as a prototype in 2.5):

from functools import partial from torch.utils.checkpoint import checkpoint, create_selective_checkpoint_contexts, CheckpointPolicy aten = torch.ops.aten SAVE = {aten.mm.default, aten.addmm.default, aten.bmm.default, aten._scaled_dot_product_flash_attention_for_cpu.default} # the CPU attention kernel; on CUDA name the flash/efficient ops def policy(ctx, op, *args, **kwargs): return CheckpointPolicy.MUST_SAVE if op in SAVE else CheckpointPolicy.PREFER_RECOMPUTE x = checkpoint(block, x, use_reentrant=False, context_fn=partial(create_selective_checkpoint_contexts, policy))

Why "save the matmuls" saved so little here
In this model most activation bytes are matmul outputs: the MLP's 4d-wide hidden layer (fc output, then GELU output) and the 3d-wide qkv projection. A policy that saves every matmul keeps most of what plain training keeps. Saving only the attention output and recomputing everything else gives full checkpointing's peak. SAC pays off when the expensive ops have small outputs and the cheap ops have big ones, or when you save some layers' matmuls and not others; measure with your model, do not assume.

The compile-only shortcut. Under torch.compile, AOTAutograd's partitioner already decides what to save and what to recompute (the torch.compile child owns it). One knob turns that decision into a memory target: torch._functorch.config.activation_memory_budget, default 1.0 (the runtime-optimised choice); 0.0 means as little as checkpointing the whole compiled region; in between, it "solves a 0-1 knapsack to find the minimum recompute necessary to stay below the activation memory budget" (torch/_functorch/config.py L190 to 202 at 2.14.1). The PyTorch blog's example spells it torch._dynamo.config.activation_memory_budget; at 2.14.1 the setting lives in torch._functorch.config checked on the installed wheel.

When it matters. When activations dominate the peak (long sequences, big micro-batches) and you would otherwise shrink the batch. When it does not: when weights and optimizer state dominate (shard those instead: FSDP2 in the Distributed lab), or when you are compute-bound and memory is not the limit. How to check it: peak memory before and after (section 7's tools), step time before and after, and the loss on the same batch, which must not change.

9. The logits problem and fused linear cross-entropy

The problem. A language model's last layer turns each position's hidden vector (d numbers) into one score per vocabulary entry (V numbers): the logits, a tensor of batch × sequence × V. The running example's vocabulary is 43 characters, so its logits are tiny. Real tokenisers have tens of thousands of entries (GPT-2's has 50,257), and then the logits, their softmax and their gradient become the largest tensors of the whole step.

To see it, the larger variant was given GPT-2's vocabulary size (V = 50,257; the batches still use only our 43 characters, which changes no shapes and therefore no bytes). One logits tensor is then 8 × 256 × 50,257 × 4 bytes = 411.7 MB.

How fusing fixes it. Instead of computing all logits and then the loss, a fused linear cross-entropy processes the positions in chunks: for each chunk it computes that chunk's logits, the loss and the gradient pieces, then frees them. The full logits tensor never exists. The same idea is behind Liger Kernel's fused linear cross-entropy and Apple's Cut Cross-Entropy (2024); PyTorch 2.13 added it to core as nn.LinearCrossEntropyLoss and F.linear_cross_entropy (2.13 release notes, "up to 4x lower peak memory", release-note figure).

The default does not chunk
At 2.14.1, F.linear_cross_entropy(x, W, y) with the default options=None runs the reference path, which materialises all logits like the unfused code. The chunked path needs options=LinearCrossEntropyOptions() (from torch.nn.modules.linear_cross_entropy_options; its docstring: "Pass options=None to use the reference path; pass an instance of this class to opt in"). Measured below: the default saves exactly nothing.
from torch.nn.modules.linear_cross_entropy_options import LinearCrossEntropyOptions h = model.ln_f(hidden) # (B*T, d): stop before the head loss = F.linear_cross_entropy(h.view(-1, d), model.head.weight, y.view(-1), options=LinearCrossEntropyOptions()) # without options: no chunking

When it matters. Large vocabularies with long sequences: the logits scale with tokens per step × V, independent of model width, so a small model with a big tokenizer is hit hardest. The options docstring adds its own rule: chunking "is a win when num_batches >= in_features and num_classes > in_features; below that, the reference path is cheaper". With 43 classes the running example is far below that. How to check it: the peak (section 7) with and without; the loss must match to rounding.

10. Attention: SDPA backends, FlexAttention, variable length

The problem. Attention compares every position with every earlier one. Written out (the running example's attn="manual"), it builds a sequence × sequence matrix of scores per head, softmaxes it, and keeps it for backward. That matrix grows with the square of the sequence length: double the context, four times the memory. The fix, from FlashAttention, is to compute attention in tiles and keep only the output plus one number per row (the log of the softmax's sum, logsumexp), recomputing the tiles in backward. Memory becomes linear in sequence length; Writing kernels owns how the kernel does it.

FlexAttention: attention variants as two small functions

Fixed backends cover causal and full attention. Everything else (sliding windows, several documents packed into one sequence, a prefix that sees itself both ways, relative position biases, soft-capping) used to mean a custom kernel or the slow math path. FlexAttention (torch.nn.attention.flex_attention, prototype in 2.5) takes two Python functions instead:

  • score_mod(score, b, h, q_idx, kv_idx) changes one score: add a bias, cap it.
  • mask_mod(b, h, q_idx, kv_idx) says whether query q_idx may see key kv_idx. create_block_mask evaluates it once per tile of 128 × 128 (the default block size, flex_attention.py L444) and stores, per row of tiles, which tiles are fully allowed, partly allowed (the kernel applies the mask inside) or empty (the kernel skips them). That BlockMask is where the speed comes from: empty tiles cost nothing.
from torch.nn.attention.flex_attention import flex_attention, create_block_mask doc = document_id_per_position # (T,) int tensor, 0,0,0,1,1,2,... def doc_causal(b, h, q, k): return (doc[q] == doc[k]) & (q >= k) bm = create_block_mask(doc_causal, None, None, T, T) # once per shape; reuse it flex = torch.compile(flex_attention) # eager mode materialises the full score matrix out = flex(q, k, v, block_mask=bm)

What FlexAttention does not do on this Mac at 2.14.1
  • No backward on CPU or MPS. _validate_device raises "FlexAttention does not support backward on CPU" (and on MPS) when an input requires grad (flex_attention.py L2204 to 2219) reproduced. So it cannot train the running example here; on CUDA it can.
  • No compiled kernel on a Mac CPU. Inductor's CPU FlexAttention template requires AVX2 and refuses sys.platform == "darwin" (torch/_inductor/kernel/flex/flex_cpu.py L31 to 40); compiling fails with "torch.compile on current platform is not supported for CPU" reproduced. Eager mode works and is exact, but materialises the scores.
  • MPS compiles it (Inductor generates a Metal kernel; supported since 2.13 per the 2.13 release notes), inference only.

Published speed on GPUs: 90% of FlashAttention-2 in forward and 85% in backward on the authors' benchmarks vendor, PyTorch team, 2024 (FlexAttention blog). The Attention lab tab draws each mask tile by tile and puts the measured times and errors side by side.

Variable-length attention

Packing several sequences into one row avoids padding; the mask then has to stop sequences seeing each other. Two ways: a document mask in FlexAttention (above), or torch.nn.attention.varlen.varlen_attn(q, k, v, cu_seq_q, cu_seq_k, max_q, max_k) (added in 2.10), which takes all sequences concatenated as (total tokens, heads, head size) plus cumulative lengths, like flash_attn_varlen_func. At 2.14.1 it calls aten._flash_attention_forward or cuDNN, both CUDA kernels (torch/nn/attention/varlen.py L54, L139).

11. torchao: fewer bits for weights, activations and gradients

The problem. Every number in the running example is a 32-bit float. Fewer bits means less memory, less data moved and, on hardware with matching instructions, faster matmuls. torchao (pip install torchao, 0.18.0 here, released 2026-08-03) is PyTorch's library for that, for inference and for training. The formats themselves (int8, int4, float8 E4M3 and E5M2, the MX block formats) belong to Quantization and Precision; this section is about the PyTorch side: what torchao does to a model, what ran on this machine, and what needs which GPU.

How it works. quantize_(model, config) walks the model and replaces each nn.Linear's weight with a tensor subclass (a Python class that wraps the low-bit data and its scales and intercepts every op on it; the Extending PyTorch child shows how subclasses are built). The module code is unchanged; when F.linear reaches the subclass, it dispatches to a quantized kernel or dequantizes. Because it is a subclass, it composes with torch.compile, FSDP2 and DTensor.

Low-precision training: float8 and MX

float8 training (torchao.float8.convert_to_float8_training(model)) swaps each Linear for a Float8Linear that casts its inputs, weights and output gradients to float8 with a scale per tensor (or per row), runs the matmul in float8 on the tensor cores and keeps the master weights in higher precision. Published: up to 1.5 times the throughput at 512 GPUs on a 405B model vendor, torchao README (torchao). It needs float8 tensor cores: compute capability 8.9 or newer (Ada, Hopper, Blackwell), or AMD MI300; torchao's dynamic float8 inference config asserts exactly that ("requires CUDA compute capability ≥8.9 or MI300+ or XPU", reproduced as the error on this CPU).

What can run here is the numerics: Float8LinearConfig(emulate=True) performs the same casts and scales and emulates the float8 matmul in float32. It shows whether float8 rounding hurts this model, nothing about speed.

60 training steps of the running example: float32 against emulated float8 (same seed, same batches)

measured on Apple M1 Pro, CPU, torchao 0.18.0; the head (256 × 43) stays in float32 because float8 matmuls need both dimensions divisible by 16 (src/exp/torchao_lab.py).

MX formats (MXFP8, MXFP4; and NVIDIA's NVFP4) put one shared scale on every block of 32 (MX) or 16 (NVFP4) values, so outliers cost less precision than with one scale per tensor. In torchao 0.18.0 they live in torchao.prototype.mx_formats (MXDynamicActivationMXWeightConfig, NVFP4DynamicActivationNVFP4WeightConfig; listed from the installed package) and target Blackwell's block-scaled tensor cores. Not run here: no Blackwell GPU, and no CPU emulation was attempted.

Quantization-aware training (QAT)

The idea. Quantizing after training rounds weights the model never saw rounded. QAT fine-tunes with fake quantization: the forward pass rounds weights to the target grid (then back to float), the backward pass treats the rounding as identity, so the weights learn to sit where rounding hurts least. In torchao: quantize_(m, QATConfig(base_config, step="prepare")), train, then quantize_(m, QATConfig(base_config, step="convert")).

Other torchao pieces, by name

torchao.optim.AdamW8bit and AdamW4bit (optimizer state in 8 or 4 bits: the 8 bytes per parameter of section 7 shrink to about 2 or 1), CPUOffloadOptimizer (state and the step on the CPU), sparsify_ for 2:4 sparsity on GPUs that accelerate it. All present in 0.18.0 checked; not run here.

Common mistakes

Timing GPU code without a synchronize
You time the queuing, not the work (section 1 measured the gap). Synchronize before reading the clock, or use torch.utils.benchmark.Timer, which does it for you at 2.14.1.
Reading the big .item() bar as the problem
On a GPU, the bar where the CPU waits is where queued work surfaces. Removing the .item() moves the wait elsewhere unless the GPU had idle time to overlap. Look at the device lane, or time phases with a synchronize after each.
Applying the standard checklist without measuring
bfloat16 autocast and torch.compile made this machine slower (section 3). Each fix is a hypothesis; keep it only if the measured gain beats the noise.
Calling F.linear_cross_entropy without options
At 2.14.1 the default is the reference path and saves no memory (section 9). Pass options=LinearCrossEntropyOptions().
Expecting sdpa_kernel([FLASH_ATTENTION]) to force a kernel everywhere
On MPS at 2.14.1 the context manager is ignored: the math path always runs (section 10). On CPU and CUDA it restricts the choice and raises if nothing qualifies.
Calling flex_attention without torch.compile
Eager FlexAttention materialises the whole score matrix (it warns). Compile it, and build the BlockMask once per shape, not every step. On CPU and MPS it is inference-only at 2.14.1.
Assuming "int4" means 4 bits in memory
IntxWeightOnlyConfig(int4) stored a byte per value plus group scales and came out larger than int8 (section 11). Check the bytes.
Adding up 16 bytes per parameter and all activations as "the peak"
Gradients grow while activations shrink; they are rarely all alive together. The peak is the larger of two moments (the Memory budget tab), and the sum overestimates it.
A selective-checkpointing policy that names the wrong ops
Op names differ by device (_scaled_dot_product_flash_attention_for_cpu on CPU, _scaled_dot_product_flash_attention or _efficient_attention on CUDA). A policy that names none of the ops that actually run saves nothing and silently behaves like full checkpointing.
Leaving the profiler on for the whole run
Use schedule(wait, warmup, active) so it records a few steps; with with_stack=True and profile_memory=True traces get large and steps slow.

Interview questions, with short answers

Your training step got slower after you added torch.cuda.synchronize() for timing. Why, and is the number wrong?
It removed CPU and GPU overlap, so the step is a little slower; the number is now honest about one step's latency. For throughput, time many steps between two synchronizes.
How do you tell a data-loading bottleneck from a compute one?
In the trace: gaps on the GPU before forward and long time inside the DataLoader's __next__. Or time next(iter(loader)) alone against the step. Fix with workers, prefetching, pre-processing offline.
Where is peak memory usually reached in a training step, and what lowers it?
At the start of backward (all activations saved, first gradients appearing). Checkpointing, smaller micro-batch, shorter sequence, fused losses, flash attention. If the peak is at the end of backward, it is gradients and optimizer state: shard them (FSDP2) or use a lighter optimizer.
Full checkpointing against selective checkpointing?
Full keeps only block inputs and recomputes the block's forward (about one extra forward). SAC saves chosen ops (typically matmuls) and recomputes the rest: less recompute, less saving. Which wins depends on where the bytes are: here the matmul outputs were most of the bytes.
Why does a large vocabulary blow up memory, and what fixes it?
Logits are batch × sequence × vocabulary floats, plus their softmax and gradient. A fused linear cross-entropy computes them in chunks and never holds them all (nn.LinearCrossEntropyLoss, PyTorch 2.13+).
What does SDPA do when you pass an arbitrary attn_mask on CUDA?
The flash backend only supports is_causal, so it falls to memory-efficient attention (supports additive masks) or math. FlexAttention covers structured masks without a dense mask tensor.
What is a BlockMask and why does it matter?
A tile-level summary of a mask_mod: per row of tiles, which tiles are fully allowed, partly allowed, or empty. The kernel skips empty tiles entirely, so sparse patterns (sliding window, documents) cost less than causal.
Weight-only int8 against dynamic int8 activations: when each?
Weight-only when memory-bound (small batch decoding: each weight is read once per token). Quantized activations when compute-bound (large batches, prefill, training), where int8 or float8 matmuls are faster than float ones.
Why does float8 training need special hardware, and what does torchao do?
Speed needs float8 tensor cores (compute capability 8.9 or newer). torchao's Float8Linear casts inputs, weights and gradients to float8 with per-tensor or per-row scales and keeps master weights in high precision; on other hardware it can only emulate.
for-loop, foreach, fused optimizers?
Several ops per tensor; a few multi-tensor ops per step; one kernel for all. Fused is fastest where supported; foreach is the CUDA default at 2.14.1.

How to read a trace like this

  • Top lane, labelled ranges. The step was wrapped in torch.profiler.record_function("data"), "forward", "backward", "optimizer" and "log loss (.item)". Your own labels are the fastest way to map a trace onto your code.
  • Bars below a label are the ATen operators the Python code called, nested: aten::linear contains aten::addmm, and so on. A bar's self time is its length minus its children.
  • On MPS (and CUDA) the CPU only enqueues work. The forward bars are short because the CPU hands kernels to the GPU and moves on; the GPU's own timeline is not in this trace (on CUDA, ProfilerActivity.CUDA adds it as a separate lane; on MPS the GPU side goes to Instruments through torch.mps.profiler.profile()). The long bar under .item() is not the cost of .item(): it is the CPU waiting for all the queued GPU work to finish.
  • On the CPU the bars are the work itself, so their lengths add up to the step.
  • A second lane appears when autograd's engine runs backward on its own thread for a device (MPS here; CUDA likewise).

What this calculator leaves out
