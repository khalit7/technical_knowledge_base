The idea

A training step is slow or out of memory for one main reason at a time: measure where its time and its peak memory go, fix the biggest piece with the lever aimed at it, and measure again.

One step of the larger variant on the Apple GPU, as first written: every lever on this page aims at one part of these two bars

The job is the topic's running example (a small GPT, see the root page) and its larger variant (8 blocks, d 512, 8 heads, context 256, batch 8: 25.4M parameters), measured on an Apple M1 Pro's CPU and GPU. Every result says what carries over to NVIDIA GPUs.

Three ideas the rest of the page keeps using
  • A GPU runs behind the CPU. PyTorch queues work and returns; the CPU only waits when it needs a result (.item(), printing, copying to the CPU). Timings and traces must account for that.
  • Count bytes and launches, not just FLOPs. Element-wise ops move memory and cost a launch each; matmuls do arithmetic. Most fixes either remove launches (fusing) or remove bytes (fewer saved activations, fewer bits).
  • Peak memory is a moment. It is what is alive at one instant: usually the start of backward, sometimes its end. Fixes that do not touch what is alive at that instant do not lower the peak.
The answers in one screen (measured)
  • How long does a step take? A 2,048-square matmul on MPS read 0.35 ms without a synchronize and 4.25 ms with torch.utils.benchmark.Timer (section 1).
  • Where does the time go? On MPS the CPU spent most of the step waiting in .item() for the GPU (sections 2, 3).
  • Which fix helps? 162 ms → 134 ms on MPS, 429 ms → 362 ms on CPU, one change at a time, measured with its spread; bfloat16 and torch.compile are not automatic wins (sections 3 to 6).
  • What holds memory at the peak? Larger variant: peak 867.4 MB, of which 537.7 MB saved activations, 304.5 MB weights and AdamW state (section 8).
  • How to trade compute for memory? Checkpointing every block: peak 485.3 MB (44% lower), step +22% on CPU (section 9).
  • A big vocabulary? Vocabulary 50,257: peak 2394.2 MB → 1278.8 MB with the chunked loss; the default call saves nothing (section 10).
  • Which attention kernel runs? CPU: a flash-style kernel, 4.3 MB kept at 2,048 positions against 138.4 MB written out; MPS: always the math path; FlexAttention inference-only here (section 11).
  • Fewer bits? int8 weight-only: Linear weights 100.8 MB → 25.4 MB; float8 training and MX need GPUs not present here (section 12).

1. Measuring honestly

Every fix is judged by a number, and three things make a naive timing lie. Asynchronous devices: on a GPU (CUDA or Apple's MPS) a PyTorch call only queues a kernel and returns, so you must wait for the device (torch.cuda.synchronize(), torch.mps.synchronize()) before reading the clock. Warm-up: the first calls pay one-off costs (memory allocation into the caching allocator, kernel selection, compilation for torch.compile, lazy initialisation); run a few untimed steps first. Noise: other processes, thermal limits and frequency scaling move every number; repeat, report the median and the spread, and record the machine's load.

Without a synchronize the clock times the queuing: the same matrix multiply on MPS, timed three ways

torch.utils.benchmark.Timer does the bookkeeping: it warms up, chooses how many runs fit in a time budget, sets the thread count, and reports the median and interquartile range (IQR, the spread of the middle half of the runs). At 2.14.1 its default clock calls torch.accelerator.synchronize() before every reading whenever an accelerator is present, CUDA or MPS alike (torch/utils/benchmark/utils/timer.py L15 to 18), so the synchronize inside this page's timed statement is redundant but harmless:

import torch.utils.benchmark as tb def call(): a @ b; torch.mps.synchronize() # redundant at 2.14.1: Timer's clock synchronises the accelerator m = tb.Timer(stmt="call()", globals={"call": call}).blocked_autorange(min_run_time=1.0) print(m.median, m.iqr, len(m.times))

Whole training steps: warm up, synchronise, time N steps, synchronise, divide; median of three. What carries over to NVIDIA GPUs: the method, byte and op counts, which fixes apply; not the times (a fix that wins 20% here can win 2% or 2 times on an H100). 2. torch.profiler

A step time says how slow, not where. torch.profiler records every operator PyTorch runs (start, end, thread; input shapes, Python stack and memory if asked) and, on CUDA, every GPU kernel and copy. Its output is a trace, a timeline you open in Perfetto or chrome://tracing.

from torch.profiler import profile, schedule, record_function, ProfilerActivity with profile(activities=[ProfilerActivity.CPU], # add ProfilerActivity.CUDA on NVIDIA GPUs schedule=schedule(wait=4, warmup=2, active=2), # skip 4 steps, warm the profiler 2, record 2 record_shapes=True, # input shapes per op (for "which matmul?") on_trace_ready=lambda p: p.export_chrome_trace("trace.json")) as prof: for step in range(8): with record_function("data"): x, y = next(it) with record_function("forward"): _, loss = model(x, y) with record_function("backward"): loss.backward() with record_function("optimizer"): opt.step(); opt.zero_grad(set_to_none=True) prof.step() # tells the schedule a step ended print(prof.key_averages().table(sort_by="self_cpu_time_total", row_limit=10))

The schedule records a few steps instead of the whole run; record_function ranges are cheap labels worth leaving in a loop for good; key_averages() sums events by name, where total time includes children (aten::linear includes its aten::addmm) and self time excludes them: sort by self time to find the ops doing the work.

What to look for. On a GPU the device lane should be busy end to end. A gap means the GPU waited: for the data loader (gaps before forward), for a CPU launching many tiny kernels (launch-bound), or for a synchronisation such as .item(), .cpu() or print(loss). In multi-GPU traces: communication that does not overlap compute. On a CPU the bars are the work. Launch-bound fixes: fusion (torch.compile), fused optimizers (section 5) and CUDA graphs, one recorded sequence of launches replayed with one call; torch.compile(mode="reduce-overhead") "reduces the overhead of python with CUDA graphs, useful for small batches", at the cost of memory, CUDA only (torch.compile from the user's side; mechanism: Streams, CUDA graphs and multi-GPU). Not measured here: this Mac has no equivalent.

Profiler options in detail (reference)
  • schedule(wait, warmup, active, repeat) skips wait steps, runs the profiler without keeping results for warmup steps (its own start-up cost lands there), then records active steps; repeat cycles it; prof.step() at the end of each step drives it. Signature at 2.14.1: schedule(*, wait, warmup, active, repeat=0, skip_first=0, skip_first_wait=0) read from the installed wheel.
  • with_stack=True links each op to the Python line that called it (larger traces); profile_memory=True records allocations (section 8). On CUDA with compiled code, TORCHINDUCTOR_UNIQUE_KERNEL_NAMES=1 gives generated kernels readable names.
  • Viewers: tensorboard_trace_handler(dir) writes files for TensorBoard; for many ranks at once, Holistic Trace Analysis summarises idle time, communication overlap and stragglers across ranks.
  • Leave it off for the whole run. With with_stack=True and profile_memory=True traces get large and steps slow; the schedule is what keeps it to a few steps.

3. The worked hunt: one slow step, fixed one bottleneck at a time

The job. The larger variant trained through a DataLoader, written the way a first version usually is:

loader = DataLoader(dataset, batch_size=8) # num_workers=0: batches built in the main process model = make_model(GPTConfig(..., attn="manual")) # attention written out: softmax(QK^T / sqrt(d)) V opt = torch.optim.AdamW(params, lr=6e-4) # default implementation: for-loop on CPU and MPS for x, y in loader: _, loss = model(x.to(dev), y.to(dev)) # float32 everywhere loss.backward(); opt.step(); opt.zero_grad(set_to_none=True) print(loss.item()) # waits for the device every step

The dataset spends 2 ms of Python work per sample before returning a window of text illustrative cost: a stand-in for decoding and tokenising raw data, set by hand so that data loading is visible. Everything else is the real model.

Where the time went: ATen ops by self time, before and after (table)

How close to the hardware's limit? Model FLOPs utilisation (MFU) = model FLOPs per step / step time / peak. One step needs 6 × 25,373,184 parameters × 2,048 tokens = 311.8 GFLOP plus 12 × L × T × d per token for attention (12 × 8 × 256 × 512 × 2,048 = 25.8 GFLOP): 337.6 GFLOP derived. With this GPU's measured float32 matmul rate as the peak (4,087.5 GFLOP/s, section 6; Apple publishes none), MFU = 337.6 / 0.162 / 4,087.5 = 51% as first written and 62% after the hunt; on the CPU (1,854.3 GFLOP/s) 42% and 50% derived, src/derive_mfu.py. The fixes removed overhead around the matmuls; what remains is matmuls. Peaks of real GPUs and MFU of published runs: Performance math.

The method, which is the point
  1. Time the whole step honestly, then split it: phases with a synchronize, and a trace.
  2. Fix the biggest piece with the cheapest change that targets it.
  3. Measure again with the spread; keep the change only if it beats the noise, even if "everyone uses it".
  4. Check the loss is unchanged on the same batches (it was, to the printed digits, for every float32 stage here).
  5. Repeat until what remains is matmuls on a busy device, which MFU measures.

4. Data loading: keep the next batch ready

With DataLoader(num_workers=0) (the default) the main process reads, decodes and collates every sample itself, between steps, so loading time adds straight onto step time. num_workers=n starts n worker processes that build whole batches in the background; prefetch_factor (default 2 when workers are used) is how many batches each keeps ready; persistent_workers=True keeps them alive between epochs instead of paying their start-up each epoch.

One worker hides the loading: a loop that needs 20 ms per step, fed by batches that cost 16 ms to build
Measured on Apple M1 Pro: how

Without workers, every step waited 16.1 ms for its batch (8 samples × 2 ms) and took 44.5 ms. One worker builds the next batch while the step runs, and the wait fell to 0.22 ms; with two the step took 27.6 ms, within a millisecond or two of the loop with free data (27.1 ms). More workers or a deeper prefetch changed nothing here, because one worker already kept up; they help when loading is slower than the step, or uneven.

When it matters: decoding images or audio, tokenising on the fly, network storage, heavy augmentation; pre-tokenised data in memory-mapped arrays (as LLM pre-training usually uses) barely needs workers. Check: the data range in a trace (or gaps on the GPU before forward), or time next(iter(loader)) alone. On CUDA add pin_memory=True (page-locked host memory) so x.to("cuda", non_blocking=True) copies asynchronously.

Workers, seeds and pin_memory, measured (absorbed from Tensors, the dispatcher and autograd)

Workers are separate processes: each holds its own copy of the Dataset, so keep it small; on macOS and Windows they start with spawn, so the Dataset must be importable and picklable. On an Apple chip CPU and GPU share one memory, so pin_memory was not measured here (signature at 2.14.1 includes pin_memory_device and in_order, read from the installed wheel).

In short: workers on macOS start with spawn; each worker seeds torch, random and NumPy; in the main process torch.manual_seed does not seed Python's random or NumPy. pin_memory=True on MPS warned "'pin_memory' argument is set as true but not supported on MPS now, device pinned memory won't be used." Defaults worth knowing at 2.14.1: prefetch_factor 2 batches per worker when num_workers > 0 (dataloader.py L293), workers restarted every epoch unless persistent_workers=True.

5. The optimizer step: one kernel or hundreds

AdamW's update is a few element-wise ops per parameter tensor. The for-loop implementation calls them for each tensor in turn (100 tensors in the larger variant, 52 in the small one), each call with Python and dispatcher overhead and, on a GPU, a launch. foreach uses torch._foreach_* operators that take a whole list of tensors per call; fused does the whole update for all parameters in one kernel per device and dtype group (torch.optim.AdamW(..., foreach=True) or fused=True). At 2.14.1 the default is foreach on CUDA-like devices and the for-loop on CPU and MPS; fused is never the default though it runs on CPU, MPS and CUDA (torch/utils/_foreach_utils.py L8 to 23, per the root's Inside one step measurements).

Fused AdamW is three times faster than the default; foreach barely helps (opt.step() alone)
Measured on Apple M1 Pro: how

Larger variant: fused 9.17 ms against 28.5 ms for the for-loop on the CPU (3.1 times), 7.67 ms against 25.0 ms on MPS (3.3 times); foreach within a few percent of the for-loop (26.7 and 24.5 ms), because each foreach op still makes a full pass over every tensor, while fused makes one pass for the whole update. It matters most with many small tensors, or a fast device where launches dominate. On CUDA foreach is already the default; fused is the switch to try (it needs every parameter on a supported device and dtype). What AdamW computes: Optimisers.

6. Mixed precision in practice: autocast and the GradScaler

bfloat16 and float16 use 2 bytes per number against float32's 4: half the memory traffic and, on GPUs with tensor cores, much faster matmuls. Automatic mixed precision (AMP): inside torch.autocast(device_type, dtype=torch.bfloat16), ops on autocast's lists (matmuls, linear layers, attention) run in 16 bits, precision-sensitive ops (softmax, normalisation, losses) stay in float32, and the parameters stay float32. On the CPU the running example's step under bfloat16 autocast produced bfloat16 logits, a float32 loss and float32 gradients on float32 parameters measured: autocast changes the compute, not the weights or the optimizer. The formats themselves belong to Quantization and Precision.

bfloat16 keeps float32's 8 exponent bits: no overflow or underflow beyond float32's, so no loss scaling; the usual choice on recent GPUs. float16 has 5 exponent bits: below 2−14 it loses precision and below 2−24 it cannot represent a value at all, so small gradients vanish. torch.amp.GradScaler multiplies the loss by a scale (default 216 = 65,536) before backward, so every gradient is 65,536 times larger while in float16, then divides it out before the step; if any gradient overflowed to inf or NaN it skips the step and halves the scale, and every 2,000 clean steps it doubles it (defaults init_scale=2.0**16, growth_factor=2.0, backoff_factor=0.5, growth_interval=2000, grad_scaler.py L126 to 129 at v2.14.1).

7. The loop the levers plug into

Every lever changes one line of the same loop, whose own rules decide whether a fix is correct. nn.Module adds bookkeeping, not a new machine: assigning an nn.Parameter to a module attribute registers a parameter (a leaf tensor with requires_grad=True that optimisers update), assigning a module registers a sub-module, and register_buffer registers a buffer (saved, not trained; persistent=False keeps it out of the state_dict). parameters(), .to(), state_dict() and train()/eval() walk that tree, and a state_dict is names over storages.

A tied weight is one Parameter under two names: parameters() counts it once, the state_dict twice

The running example ties its output head to its token embedding (head.weight is tok.weight). parameters() de-duplicates by object, the state_dict does not, so parameters() counts 52 tensors and the state_dict 53 (3,197,952 elements against 3,186,944) measured. Consequences: safetensors refuses to save the shared storage, two different values loaded under the two names leave the later one, and to_empty unties them (details below).

One optimizer step with accumulation, float16 and clipping, line by line (step through it)

measured on the running example, CPU, PyTorch 2.14.1 (recorded by the sibling Tensors, the dispatcher and autograd, its exp/module_loop.py): four micro-batches of 2 with each loss divided by 4 gave the same gradient as one batch of 8 (norm 11.1032); without the division the norm was 44.41, exactly 4.00 times too large. clip_grad_norm_ returned the norm before clipping (11.1032 at step 0). zero_grad freed 12,747,776 bytes of gradients.

Three rules follow. Gradients accumulate into .grad across backwards, so micro-batch losses must be divided by their number; this is also a memory lever, because activations scale with the micro-batch while the gradient is that of the whole batch (section 8). A GradScaler's gradients must be unscaled before clipping, or you clip a gradient 65,536 times too large and the threshold means nothing. Log the norm clip_grad_norm_ returns: it is the cheapest training-health signal you have.

Determinism. Seed with torch.manual_seed and make the data order a function of the step, as get_batch(cfg, step) does (it made the first three losses identical across a plain loop and three frameworks on the root's Ecosystem map tab). In short: CPU with a fixed thread count was bit-for-bit repeatable; 1 against 4 threads differed in the last bits (max parameter difference 1.46e-06); MPS was not bit-repeatable even with use_deterministic_algorithms(True), which raised nothing measured.

8. Memory: what fills it during one step

Five things live in memory during training (float32, AdamW, P parameters): parameters, 4 bytes × P, always; gradients, 4 bytes × P, built layer by layer in backward, freed by zero_grad(set_to_none=True); optimizer state, 8 bytes × P from the first step(); activations, saved by forward for backward, scaling with batch × sequence length; and short-lived temporaries. The fixed cost is 16 bytes per parameter (4 + 4 + 8); mixed-precision training with float32 master weights also comes to 16, split differently (2 + 2 + 12 in the ZeRO paper's accounting; Distributed Training owns that arithmetic and how sharding divides it).

Before the forward pass, 304.5 MB is already in use: parameters (101.5 MB = 25,373,184 × 4 bytes) and AdamW state (203.0 MB). Gradients reach their full 101.5 MB only at the end of backward, by which time most activations are gone, so the textbook sum "16 bytes per parameter plus activations" (943.6 MB) overstates this peak. Switch to Checkpoint every block: the activations nearly vanish and the peak moves to the end of backward (485.3 MB), where full gradients and the last block's rebuilt activations coexist. The Memory budget tab turns this into a calculator with both moments.

9. Activation checkpointing as a lever, full and selective

Activation checkpointing keeps only each block's input in forward and reruns the block's forward in backward to rebuild what it needs: memory down, compute up by about one extra forward of the checkpointed part. Use checkpoint(block, x, use_reentrant=False); how it hooks autograd's saved tensors is on Tensors, the dispatcher and autograd, the trade at cluster scale on Distributed Training. Selective activation checkpointing (SAC) lets a policy, called for every ATen op in the region, save some outputs anyway; the usual one saves matmul outputs (expensive to recompute) and recomputes element-wise ops (PyTorch blog, 2025; prototype since 2.5). The six CheckpointPolicy values at 2.14.1: MUST_SAVE, PREFER_SAVE, MUST_RECOMPUTE, PREFER_RECOMPUTE, MUST_CPU_OFFLOAD, PREFER_CPU_OFFLOAD read from the installed wheel.

from functools import partial from torch.utils.checkpoint import checkpoint, create_selective_checkpoint_contexts, CheckpointPolicy aten = torch.ops.aten SAVE = {aten.mm.default, aten.addmm.default, aten.bmm.default, aten._scaled_dot_product_flash_attention_for_cpu.default} # the CPU attention kernel; on CUDA name the flash/efficient ops def policy(ctx, op, *args, **kwargs): return CheckpointPolicy.MUST_SAVE if op in SAVE else CheckpointPolicy.PREFER_RECOMPUTE x = checkpoint(block, x, use_reentrant=False, context_fn=partial(create_selective_checkpoint_contexts, policy))
Checkpointing every block cuts the peak by 44% for 22% more step time; saving the matmuls saves little

measured on Apple M1 Pro, float32, the same batch and the same loss (3.39147) in all four.

Full checkpointing cut the peak from 867.4 MB to 485.3 MB (44% less): forward now saves only each block's input, 42.3 MB instead of 546.4 MB. The price: backward runs 1,087 ATen calls instead of 567 (each block's forward again), and the step went from 389 ms to 475 ms on the CPU (+22%) and from 150 ms to 189 ms on MPS. Saving the matmuls saved little because here most activation bytes are matmul outputs (the MLP's 4d-wide fc and GELU outputs, the 3d-wide qkv projection); SAC pays off when expensive ops have small outputs, or when only some layers save. A policy must name the ops that actually run, and names differ by device (_scaled_dot_product_flash_attention_for_cpu on CPU, _scaled_dot_product_flash_attention or _efficient_attention on CUDA).

torch.compile's memory budget: one knob from "save what eager saves" (1.0) to "recompute everything" (0.0)

measured on the larger variant, CPU, deterministic (src/exp/budget.py): activation bytes saved for backward; at 0.0 backward recomputes the whole forward.

The numbers

Eager saves 546.4 MB; compiled at budget 1.0 546.8 MB, at 0.5 273.0 MB, at 0.2 109.1 MB, and at 0.0 nothing beyond the inputs (0.0 MB); eager checkpointing of every block keeps the block inputs, 42.3 MB. The loss is the same in all (3.81230, freshly initialised model on batch 1).

Under torch.compile the partitioner already decides what to save (torch.compile from the user's side owns it); torch._functorch.config.activation_memory_budget, default 1.0, makes it a memory target: in between it "solves a 0-1 knapsack to find the minimum recompute necessary to stay below the activation memory budget" (torch/_functorch/config.py L190 to 202 at 2.14.1). Budget 1.0 saves what eager saves: by default the partitioner optimises runtime, not memory. The PyTorch blog's example spells it torch._dynamo.config.activation_memory_budget; at 2.14.1 it lives in torch._functorch.config checked on the installed wheel.

When: activations dominate the peak and you would otherwise shrink the batch; not when weights and optimizer state dominate (shard those: FSDP2, the root's Distributed lab). Check: peak and step time before and after, and the same loss on the same batch.

10. The logits problem and fused linear cross-entropy

The logits, one score per vocabulary entry per position, are batch × sequence × V. With a real tokeniser (GPT-2's has 50,257 entries; the running example has 43 characters) the logits, their softmax and their gradient are the largest tensors of the step. To see it, the larger variant was given V = 50,257 (the batches still use only 43 characters, which changes no shapes and therefore no bytes): one logits tensor is 8 × 256 × 50,257 × 4 bytes = 411.7 MB.

A fused linear cross-entropy processes the positions in chunks: for each chunk it computes that chunk's logits, the loss and the gradient pieces, then frees them, so the full logits tensor never exists. The same idea is behind Liger Kernel's fused linear cross-entropy and Apple's Cut Cross-Entropy (2024); PyTorch 2.13 added it to core as nn.LinearCrossEntropyLoss and F.linear_cross_entropy (2.13 release notes, "up to 4x lower peak memory", release-note figure).

The default does not chunk
At 2.14.1, F.linear_cross_entropy(x, W, y) with the default options=None runs the reference path, which materialises all logits like the unfused code. The chunked path needs options=LinearCrossEntropyOptions() (from torch.nn.modules.linear_cross_entropy_options; its docstring: "Pass options=None to use the reference path; pass an instance of this class to opt in"). Measured below: the default saves exactly nothing.
from torch.nn.modules.linear_cross_entropy_options import LinearCrossEntropyOptions h = model.ln_f(hidden) # (B*T, d): stop before the head loss = F.linear_cross_entropy(h.view(-1, d), model.head.weight, y.view(-1), options=LinearCrossEntropyOptions()) # without options: no chunking
With a 50,257-entry vocabulary the chunked loss nearly halves the peak; the default call changes nothing

measured on Apple M1 Pro, the same loss in every run (8.9544 for all four).

Measured on Apple M1 Pro: how

measured on Apple M1 Pro, CPU, float32, PyTorch 2.14.1, deterministic (CPU memory profiler, src/exp/mem_step.py); the same loss in every run (8.9544 for all four). The unfused step peaks at 2394.2 MB; at that moment the backward temporaries alone hold 823.4 MB, the softmax's gradient and the logits' gradient, two tensors of 411.7 MB each. The default call (2394.2 MB) is byte for byte the unfused peak. Against the release notes' "up to 4x", this whole step (weights, AdamW state, block activations included) gains 1.87 times, and pays in time: +69% on the CPU, +84% on MPS. The docstring's rule: chunking "is a win when num_batches >= in_features and num_classes > in_features; below that, the reference path is cheaper". Logits scale with tokens × V, not width, so a small model with a big tokenizer is hit hardest. Check: the peak with and without, and the loss to rounding.

11. Attention kernels: SDPA backends, FlexAttention, variable length

Written out (the running example's attn="manual"), attention builds a sequence × sequence matrix of scores per head, softmaxes it and keeps it for backward: double the context, four times the memory. The fix, from FlashAttention, computes attention in tiles and keeps only the output plus one number per row (the log of the softmax's sum, logsumexp), recomputing the tiles in backward, so memory becomes linear in sequence length (Writing kernels owns how the kernel does it; the attention designs themselves are on Attention variants).

A fused kernel keeps 32 times less for backward at 2,048 positions, and the gap grows with T² (one attention call, 8 heads of 64)

measured on Apple M1 Pro, float32, PyTorch 2.14.1, deterministic: unique storages passed to autograd's saved-tensor hooks, q, k and v excluded (src/exp/attn_backends.py).

On the CPU, SDPA ran the flash-style CPU kernel and kept the output and one logsumexp per row and head: 4.3 MB at 2,048 positions, growing linearly (0.5 MB at 256). Written out, the same attention kept the 8 × T × T softmax: 138.4 MB at 2,048, 32 times more. On MPS, SDPA with gradients takes the math path and keeps the T × T matrix too (142.6 MB): there is no memory-efficient attention for training on Apple GPUs in PyTorch 2.14.1.

SDPA: one function, several kernels. F.scaled_dot_product_attention (SDPA) checks the inputs against each backend's constraints in a fixed priority order and runs the first that qualifies. CUDA tries flash, efficient, math, cuDNN (cuDNN first on Hopper and Blackwell with recent cuDNN), and an arbitrary attn_mask or a float32 input rules flash out; the CPU tries a flash-style kernel, then math; MPS always runs math. Measured here: on the CPU the flash kernel took every case except dropout; on MPS forcing a backend changes nothing; bfloat16 is less exact (largest error 8.1e-3 against 8.4e-7 for float32). Check which ran: profile one call and read the op name (aten::_scaled_dot_product_flash_attention, ..._efficient_attention, ..._cudnn_attention, ..._attention_math), or force one with sdpa_kernel([SDPBackend.FLASH_ATTENTION]), which raises instead of falling back silently.

12. torchao: fewer bits for weights, activations and gradients

Fewer bits mean less memory, less data moved and, with matching hardware, faster matmuls. torchao (pip install torchao, 0.18.0 here, released 2026-08-03) is PyTorch's library for that, for inference and training; the formats themselves (int8, int4, float8 E4M3 and E5M2, the MX block formats) belong to Quantization and Precision. quantize_(model, config) walks the model and replaces each nn.Linear's weight with a tensor subclass (a Python class that wraps the low-bit data and its scales and intercepts every op on it; built as on Extending PyTorch). The module code is unchanged: when F.linear reaches the subclass it dispatches to a quantized kernel or dequantizes, and because it is a subclass it composes with torch.compile, FSDP2 and DTensor.

int8 cuts the weights four times at no loss; "int4" on the CPU is stored in bytes and comes out larger than int8

measured on Apple M1 Pro, CPU: the larger variant after 150 training steps, every Linear except the tied head quantized.

Measured on Apple M1 Pro: how

measured on Apple M1 Pro, CPU, torchao 0.18.0, PyTorch 2.14.1 (src/exp/torchao_lab.py): the larger variant after 150 training steps, every Linear except the tied head quantized. "Linear bytes": every inner tensor of the 32 block weights plus the head's float32 weight (data, scales, zero points). Loss on 8 fixed batches of the same text (the model has no held-out data: it is a toy). Logit difference against the float32 model on one batch.

Int8 weight-only cut the Linear weights from 100.8 MB to 25.4 MB (3.96 times smaller: 1 byte per weight plus one float32 scale per row) and moved the loss by 0.00002. Int4WeightOnlyConfig failed with "ImportError: Requires mslk >= 1.0.0" (it needs a separate kernel package), and the CPU-capable IntxWeightOnlyConfig(int4) stores each 4-bit value in a full byte (IntxUnpackedToInt8Tensor) plus a scale per group of 32, so it is larger than int8 (29.2 MB). "int4" names the value grid, not the storage: check bytes, do not assume them. float8 weight-only runs on the CPU; dynamic float8 activations do not.

A quantization config is only as fast as the kernel it reaches: one 4096 × 4096 Linear, one token against 2,048
Measured on Apple M1 Pro: how

A one-token matmul is memory-bound, so fewer bytes per weight should mean less time. Yet int8 weight-only took 3.16 ms and int4 (Intx) 5.99 ms against float32's 2.18 ms at M = 1: in eager mode the int8 weight is converted to float32 on every call, then multiplied with an ordinary torch.mm (torchao 0.18.0, int8_tensor.py L337 to 354). Dynamic int8 activations with int8 weights multiply int8 by int8 (int_scaled_matmul, L315): 0.40 ms for one token (5.4 times faster than float32) but 250 ms for 2,048 tokens against 37.0 ms (float32 BLAS is far better tuned here). On GPUs the weight-only paths have dedicated kernels, not represented here. The rule: weight-only for memory-bound work (small-batch decoding), quantized activations for compute-bound work (large batches, prefill, training).

float8 training (torchao.float8.convert_to_float8_training(model)) swaps each Linear for a Float8Linear that casts inputs, weights and output gradients to float8 with a scale per tensor (or row), runs the matmul on float8 tensor cores and keeps master weights in higher precision: up to 1.5 times the throughput at 512 GPUs on a 405B model vendor, torchao README (torchao). It needs compute capability 8.9 or newer (Ada, Hopper, Blackwell) or AMD MI300 ("requires CUDA compute capability ≥8.9 or MI300+ or XPU", reproduced as the error here). Float8LinearConfig(emulate=True) runs the same casts and scales with a float32 matmul: the numerics, not the speed.

Emulated float8 tracks float32 except for one spike: 60 training steps, same seed, same batches

measured on Apple M1 Pro, CPU, torchao 0.18.0, the running example; the head (256 × 43) stays in float32 because float8 matmuls need both dimensions divisible by 16 (src/exp/torchao_lab.py). Quantizing after training (PTQ) rounds weights the model never saw rounded. Quantization-aware training (QAT) fine-tunes with fake quantization: forward rounds weights to the target grid and back to float, backward treats the rounding as identity, so the weights learn to sit where rounding hurts least. In torchao: quantize_(m, QATConfig(base_config, step="prepare")), train, then quantize_(m, QATConfig(base_config, step="convert")). Run here on the running example: fake quantization reproduced the converted model's loss exactly (0.35054 both), which is the whole point; on a model this small int4 costs almost nothing, so QAT had nothing to recover.

Common mistakes, each with the section that shows it (14)
  • Timing GPU code without a synchronize: you time the queuing, not the work; use torch.utils.benchmark.Timer, which synchronises for you at 2.14.1 (1).
  • Reading the big .item() bar as the problem: it is where queued work surfaces; removing the .item() moves the wait elsewhere unless the GPU had idle time to overlap. Look at the device lane, or time phases with a synchronize after each (3).
  • Applying the standard checklist without measuring: bfloat16 autocast and torch.compile made this machine slower; each fix is a hypothesis (3).
  • Accumulating gradients without dividing the loss: the gradient comes out exactly the number of micro-batches times too large (7).
  • Clipping before unscaling with a GradScaler: you clip the scaled gradient (65,536 times too large at the default scale) and the threshold means nothing (7).
  • Assuming torch.manual_seed seeds everything: it does not seed Python's random or NumPy in the main process; DataLoader workers seed all three for you (4, 7).
  • Ignoring load_state_dict(strict=False)'s return value: missing keys keep their random initialisation silently; and tied weights break safetensors, loading and to_empty (7).
  • Adding up 16 bytes per parameter and all activations as "the peak": gradients grow while activations shrink, so the peak is the larger of two moments and the sum overestimates it (8).
  • A selective-checkpointing policy that names the wrong ops: it saves nothing and silently behaves like full checkpointing (9).
  • Calling F.linear_cross_entropy without options: the reference path saves no memory at 2.14.1 (10).
  • Expecting sdpa_kernel([FLASH_ATTENTION]) to force a kernel everywhere: on MPS it is ignored; on CPU and CUDA it restricts the choice and raises if nothing qualifies (11).
  • Calling flex_attention without torch.compile, or building the BlockMask every step: eager materialises the whole score matrix; build the mask once per shape (11).
  • Assuming "int4" means 4 bits in memory: IntxWeightOnlyConfig(int4) stored a byte per value and came out larger than int8 (12).
  • Leaving the profiler on for the whole run: use a schedule (2).
Interview rehearsal: thirteen questions with short answers (optional)
Your training step got slower after you added torch.cuda.synchronize() for timing. Why, and is the number wrong?
It removed CPU and GPU overlap, so the step is a little slower; the number is now honest about one step's latency. For throughput, time many steps between two synchronizes.
How do you tell a data-loading bottleneck from a compute one?
In the trace: gaps on the GPU before forward and long time inside the DataLoader's __next__. Or time next(iter(loader)) alone against the step. Fix with workers, prefetching, pre-processing offline.
Your MFU is 30%. Where do you look?
The trace's device lane for gaps (data, launches, synchronisations), then the share of non-matmul kernels. Gaps are fixed by workers, fusion, CUDA graphs and removing per-step syncs; a matmul share that is already high means the remaining lever is precision (bfloat16 or float8 tensor cores) or larger matmuls.
Where is peak memory usually reached in a training step, and what lowers it?
At the start of backward (all activations saved, first gradients appearing). Checkpointing, smaller micro-batch, shorter sequence, fused losses, flash attention. If the peak is at the end of backward, it is gradients and optimizer state: shard them (FSDP2) or use a lighter optimizer.
Full checkpointing against selective checkpointing?
Full keeps only block inputs and recomputes the block's forward (about one extra forward). SAC saves chosen ops (typically matmuls) and recomputes the rest: less recompute, less saving. Which wins depends on where the bytes are: here the matmul outputs were most of the bytes.
Why does a large vocabulary blow up memory, and what fixes it?
Logits are batch × sequence × vocabulary floats, plus their softmax and gradient. A fused linear cross-entropy computes them in chunks and never holds them all (nn.LinearCrossEntropyLoss, PyTorch 2.13+).
Why does only float16 need a GradScaler?
float16 has 5 exponent bits: gradients below about 6e-8 vanish (1,636 of 3.19 million here) and the maximum is 65,504. bfloat16 has float32's 8 exponent bits, so its range is the same as float32's.
Your parameter count from the state_dict is higher than from parameters(). Why?
Tied (shared) parameters appear once per name in the state_dict: 3,197,952 against 3,186,944 elements here.
What does SDPA do when you pass an arbitrary attn_mask on CUDA?
The flash backend only supports is_causal, so it falls to memory-efficient attention (supports additive masks) or math. FlexAttention covers structured masks without a dense mask tensor.
What is a BlockMask and why does it matter?
A tile-level summary of a mask_mod: per row of tiles, which tiles are fully allowed, partly allowed, or empty. The kernel skips empty tiles entirely, so sparse patterns (sliding window, documents) cost less than causal.
Weight-only int8 against dynamic int8 activations: when each?
Weight-only when memory-bound (small batch decoding: each weight is read once per token). Quantized activations when compute-bound (large batches, prefill, training), where int8 or float8 matmuls are faster than float ones.
Why does float8 training need special hardware, and what does torchao do?
Speed needs float8 tensor cores (compute capability 8.9 or newer). torchao's Float8Linear casts inputs, weights and gradients to float8 with per-tensor or per-row scales and keeps master weights in high precision; on other hardware it can only emulate.
for-loop, foreach, fused optimizers?
Several ops per tensor; a few multi-tensor ops per step; one kernel for all. Fused is fastest where supported; foreach is the CUDA default at 2.14.1.

What this calculator leaves out

  • The CUDA caching allocator's overhead and fragmentation (reserved above allocated): see Memory allocators. Measure reserved memory on the real device (torch.cuda.memory_reserved()).
  • CUDA context and library workspaces (cuBLAS, cuDNN, NCCL buffers), which take memory before the first tensor.
  • Sharding across GPUs (FSDP2 divides parameters, gradients and optimizer state by the number of ranks): Distributed Training owns that arithmetic.
  • Mixed precision: autocast keeps float32 parameters and adds bfloat16 copies of activations; this calculator counts float32 everywhere, as measured.
