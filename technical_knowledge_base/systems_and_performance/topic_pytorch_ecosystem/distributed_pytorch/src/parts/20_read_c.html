3. DDP from the inside: the reducer, unused parameters, accumulation, hooks

DDP (DistributedDataParallel) keeps a full model on every rank and averages gradients during backward. The lab tab (sections 3, 5, 6) shows its buckets on the running example: a single bucket in step 0, then a layout rebuilt in the order gradients actually arrived (1,051,648 and 11,696,128 bytes), each bucket's all-reduce launched while backward continues. The piece of C++ that does this is the reducer (torch/csrc/distributed/c10d/reducer.cpp): one autograd hook per parameter marks it ready; when every parameter of a bucket is ready, the bucket's tensor goes to a communication hook (by default an all-reduce) whose future is awaited at the end of backward. Four switches change that machinery, each measured here on 2 processes.

Unused parameters: find_unused_parameters and static_graph

The reducer waits for every parameter of a bucket. A parameter that forward did not use never gets a gradient, so its bucket never completes. To show it, the running example was wrapped with one extra Linear that forward skips:

Measured, 2 CPU processes, gloo. The 216-byte all-reduce is the used-parameter bitmap: 54 parameters × 4 bytes, so every rank learns which parameters some rank used. find_unused_parameters=True also turns off the single-bucket first step (the size caps apply from step 0) and walks the autograd graph from the outputs every step to find the unused ones; the extra cost is that traversal plus the bitmap. static_graph=True promises the same parameters are used every step: DDP learns the set in the first iteration, then rebuilds buckets after step 1 (the two broadcasts in step 2). When a parameter is used on one rank only, every rank still ends with the same averaged gradient for it (checked on both ranks: neither left it empty).

Gradient accumulation: no_sync

With 4 micro-batches per optimizer step, an all-reduce after each micro-batch wastes three of them: only the sum matters. with ddp.no_sync(): lets backward accumulate locally without communicating.

for i, (x, y) in enumerate(micro_batches):         # 4 per optimizer step
    ctx = ddp.no_sync() if i < 3 else contextlib.nullcontext()
    with ctx:
        _, loss = ddp(x, y)
        (loss / 4).backward()                        # the last backward all-reduces the sum
opt.step(); opt.zero_grad(set_to_none=True)

Uneven inputs: Join

If rank 0 has 5 batches and rank 1 has 3, rank 0's fourth backward waits for a partner that has left the loop. Recorded: without help, both ranks failed with gloo's receive timeout after seconds (the script's 10 s timeout). The Join context manager (torch.distributed.algorithms.join) fixes it: each iteration starts with a 4-byte all-reduce counting the ranks still training, and a rank that has run out "shadows" the others' all-reduces with zeros until all are done. Communication hooks

ddp.register_comm_hook(state, hook) replaces the all-reduce of each bucket with any function that returns a future of the reduced bucket. PyTorch ships three families in torch.distributed.algorithms.ddp_comm_hooks: plain all-reduce (allreduce_hook, which divides by the world size then all-reduces, default_hooks.py L18), compression to 16 bits (fp16_compress_hook: cast, divide, all-reduce, cast back), and PowerSGD (Vogels et al. 2019, arXiv 1905.13727), which replaces each gradient matrix M (n × m) by a rank-r product P QT found with one step of power iteration and all-reduces only P (n × r) and Q (m × r), keeping the error it made as error feedback to add to the next step's gradient. Three things that broke, and why they matter beyond this laptop
  • bf16_compress_hook refuses gloo: Use fp16 compression on CPU, bf16 on NCCL.
  • batched_powerSGD_hook is broken at 2.14.1 on any backend. It ran the two plain warm-up steps, then failed at its first compressed step with a bare AssertionError: it passes a 2-D matrix to _orthogonalize, which asserts a 3-D batch (L24-26, called from L808).
  • PowerSGD on 4 gloo processes crashed the job (gloo EnforceNotMet ... op.nread == op.preamble.nbytes: a message of the wrong size arrived), for ranks 1 and 4, while rank 16 and rank 4 without error feedback finished. Logging every all-reduce the hook issues showed why: two thirds are issued from future callbacks on another thread, not the main thread, and at step 16 the ranks issued them in different orders: Collectives must be issued in the same order on every rank (the rule of section 11); a hook that issues them from callbacks can break it whenever timing differs. On 2 processes it did not happen in 180 steps. Not checked on NCCL.

Two neighbours. gradient_as_bucket_view=True makes each .grad a view into its bucket instead of a copy (the lab tab, section 3, measured it on this model: no change in peak, because the peak comes at the start of backward). Under torch.compile, DDP splits the compiled graph at bucket boundaries so the all-reduces still overlap (DDPOptimizer: 2, 4 and 13 graphs for 25, 4 and 1 MB buckets on the running example), measured on the {{torch.compile|n:3c65c17b0d0d8123a232d75bd7339ecb}} child.
