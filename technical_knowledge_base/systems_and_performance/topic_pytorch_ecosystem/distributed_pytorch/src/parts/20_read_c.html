3. DDP: buckets that all-reduce while backward runs

DDP (DistributedDataParallel) keeps a full model on every rank and averages gradients during backward. The C++ reducer (torch/csrc/distributed/c10d/reducer.cpp) puts one autograd hook on each parameter. Gradients are grouped into buckets; when every gradient of a bucket is ready, the bucket goes to a communication hook (by default an all-reduce) and backward carries on. In the first step all gradients share one bucket; after it, DDP rebuilds the buckets in the order the gradients actually arrived, the first one closing at about 1 MiB and the rest at 25 MiB (bucket_cap_mb), so the first bucket fills early in backward.

Three switches change that machinery, each measured here on 2 processes.

Unused parameters. The reducer waits for every parameter of a bucket; one that forward did not use never gets a gradient, so its bucket never completes and DDP raises at the next step. find_unused_parameters=True walks the autograd graph from the outputs every step and all-reduces a used-parameter bitmap (216 bytes here: 54 parameters × 4 bytes); static_graph=True promises the same set every step, learns it once and rebuilds buckets after step 1.

Gradient accumulation. With 4 micro-batches per optimizer step, only the sum matters, so all-reducing after each wastes three. with ddp.no_sync(): lets backward accumulate locally:

for i, (x, y) in enumerate(micro_batches):         # 4 per optimizer step
    ctx = ddp.no_sync() if i < 3 else contextlib.nullcontext()
    with ctx:
        _, loss = ddp(x, y)
        (loss / 4).backward()                        # the last backward all-reduces the sum
opt.step(); opt.zero_grad(set_to_none=True)

Communication hooks. ddp.register_comm_hook(state, hook) replaces each bucket's all-reduce with any function returning a future of the reduced bucket. PyTorch ships plain all-reduce, compression to 16 bits (fp16_compress_hook: 6,373,888 bytes per step instead of 12,747,776, gradient error 2.8e-4) and PowerSGD (Vogels et al. 2019, arXiv 1905.13727), which replaces each gradient matrix by a rank-r product P QT and all-reduces only P and Q (327,344 bytes at rank 4, 39 times fewer), keeping what it dropped as error feedback for the next step. Fewer bytes is not a faster step on NVLink, where 12.75 MB is cheap and PowerSGD's extra matrix work may cost more than it saves; the paper reports its gains on slower networks.

Three hooks that broke, and why they matter beyond this laptop
  • bf16_compress_hook refuses gloo: Use fp16 compression on CPU, bf16 on NCCL.
  • batched_powerSGD_hook is broken at 2.14.1 on any backend. It ran the two plain warm-up steps, then failed at its first compressed step with a bare AssertionError: it passes a 2-D matrix to _orthogonalize, which asserts a 3-D batch (L24-26, called from L808).
  • PowerSGD on 4 gloo processes crashed the job (gloo EnforceNotMet ... op.nread == op.preamble.nbytes: a message of the wrong size arrived), for ranks 1 and 4, while rank 16 and rank 4 without error feedback finished. Logging every all-reduce the hook issues showed why: two thirds are issued from future callbacks on another thread, not the main thread, and at step 16 the ranks issued them in different orders: Collectives must be issued in the same order on every rank (the rule of section 11); a hook that issues them from callbacks can break it whenever timing differs. On 2 processes it did not happen in 180 steps. Not checked on NCCL.

What transfers to GPUs: the bytes and the errors, exactly (they depend on shapes and arithmetic, not the backend), except that NCCL also accepts the bf16 hook. What does not: whether fewer bytes means a faster step.

The 216-byte all-reduce is the used-parameter bitmap, so every rank learns which parameters some rank used. find_unused_parameters=True also turns off the single-bucket first step (the size caps apply from step 0); its extra cost is the graph traversal plus the bitmap, so leaving it on "to be safe" costs every step. static_graph=True's two broadcasts in step 2 are the bucket rebuild: 3 collectives per step with find_unused_parameters; 2, 1, then 4 in the first three steps with static_graph. When a parameter is used on one rank only, every rank still ends with the same averaged gradient for it (checked on both ranks: neither left it empty).

Uneven inputs: Join. If rank 0 has 5 batches and rank 1 has 3, rank 0's fourth backward waits for a partner that has left the loop. Recorded: without help, both ranks failed with gloo's receive timeout after seconds (the script's 10 s timeout). The Join context manager (torch.distributed.algorithms.join) fixes it: each iteration starts with a 4-byte all-reduce counting the ranks still training, and a rank that has run out "shadows" the others' all-reduces with zeros until all are done.
