5. DTensor and DeviceMesh: placements, and how an operation picks its output's

A DTensor (torch.distributed.tensor) is one logical tensor spread over a DeviceMesh, with one placement per mesh dimension: Shard(d) (split along tensor dimension d), Replicate() (every rank has all of it) or Partial() (every rank has a full-shape tensor and the true value is their sum). FSDP2, tensor parallel and DCP are all built on it.

A matrix product of two shards is a pending sum, free; a nonlinearity on that sum forces an all-reduce first

Right: A split by columns times B split by rows leaves each rank a full-shape partial product (S(1) x S(0) → P, no communication); relu of a sum is not the sum of relus, so DTensor all-reduces to Replicate before applying it. Measured, 2 CPU processes; collectives as CommDebugMode counted them; every result checked against plain tensors.

How it decides. DTensor is a tensor subclass (built as the {{Extending PyTorch|n:3f85c17b0d0d8158a7addcd3d601d72a}} child describes, with a C++ fast path). For every ATen operation it asks the sharding propagator: given the inputs' placements, which output placement can be computed locally, and if none, which inputs must be redistributed first? Each operation registers a strategy, a list of (output placements, required input placements) pairs; DTensor picks the cheapest, runs any redistribution (a collective), then runs the plain operation on the local pieces. Four rules fall out of 28 recorded cases, and they are most of tensor parallelism:

  • Linear operations commute with the sum, so a Partial passes through them free: S(1) x S(0) → P; Partial + Partial and 2 × Partial stay Partial.
  • Nonlinear ones do not. relu(Partial) forced an all-reduce first. This is why Megatron's MLP puts the GeLU between a column split and a row split.
  • Operations that need a whole row need it gathered. Softmax and LayerNorm along a sharded dimension all-gathered it (output Replicate); along an unsharded dimension they ran locally. Sequence parallelism (section 6) uses exactly this: LayerNorm is per token, so splitting the sequence is free.
  • A row-sharded embedding table gives a new kind of placement, MaskPartial: each rank looks up the ids it owns, writes zeros elsewhere, and the sum is pending. That is vocabulary-parallel embedding.

Moving between placements is redistribute, one collective per change (Shard to Replicate is an all-gather, Partial to Replicate an all-reduce, Partial to Shard a reduce-scatter); the parent lab's {{redistribution explorer|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}} (Distributed lab tab, section 7) has every pair. Wrapping existing tensors is DTensor.from_local(t, mesh, [Shard(0)]), which declares that the ranks' local tensors together form one DTensor and moves no data; to_local() returns the local piece without copying.

from_local, recorded: Two traps: with uneven pieces, the global shape must be given (shape= and stride=), and the pieces must follow torch.chunk's split (3 rows over 2 ranks is 2 and 1, recorded ). A first attempt here declared pieces of 3 and 1 rows with shape=(4, 2); full_tensor() then all-gathered pieces of the wrong size and gloo aborted both processes.

A custom operator needs a strategy. An operator DTensor does not know raises at once. Recorded for a small torch.library op dpt::rowscale(x, s) = x * s[:, None]: Registering a strategy fixes it:

from torch.distributed.tensor.experimental import register_sharding

@register_sharding(torch.ops.dpt.rowscale.default)
def rowscale_strategy(x, s):
    # (output placements, input placements) pairs DTensor may choose from
    return [([Shard(0)], [Shard(0), Shard(0)]),       # rows split: each rank scales its own rows
            ([Replicate()], [Replicate(), Replicate()]),
            ([Shard(1)], [Shard(1), Replicate()])]     # columns split: needs all of s

The fourth line asked for x by columns and s by rows; no strategy matches, so DTensor redistributed s to Replicate with one all-gather and picked the third strategy. Measured, 2 CPU processes.
