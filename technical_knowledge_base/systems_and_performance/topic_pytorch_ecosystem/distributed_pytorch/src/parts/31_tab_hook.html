Comm-hook bytes lab

The running example trained for 30 steps under DDP with each communication hook PyTorch ships, from the same weights on the same batches: what each sends per step, how far its averaged gradient is from the exact average, and where the loss ends up. Then the arithmetic that predicts PowerSGD's bytes for any rank.

How it was recorded: src/exp/ddp_more.py hooks, one clean torchrun launch per hook (run_hooks.sh), CPU processes on gloo, torch 2.14.1, Apple M1 Pro. Bytes are the flight recorder's input bytes of every collective of the step's backward. The "exact" gradient is each step's local gradients (computed under no_sync) all-reduced on a separate process group, so the error isolates the hook. PowerSGD uses start_powerSGD_iter=2, so steps 0 and 1 are plain all-reduces. The Reading tab's section 3 explains each hook. Measured, deterministic (no timing).

PowerSGD views each gradient as a matrix n × m and sends P (n × r) and Q (m × r) instead, but only when that saves at least a factor min_compression_rate (default 2): (n + m) r × 2 < n m. One-dimensional gradients (biases, LayerNorm) and matrices that fail the test go uncompressed (powerSGD_hook.py L79-104). For the running example's 52 parameter tensors:

What transfers to GPUs: the bytes and the errors, exactly (they depend on shapes and arithmetic, not the backend), except that NCCL also accepts the bf16 hook. What does not: whether fewer bytes means a faster step. On NVLink an all-reduce of 12.75 MB is cheap and PowerSGD's extra matrix multiplies and orthogonalisation may cost more than they save; the PowerSGD paper reports its gains on slower networks (Vogels et al. 2019, independent of this page).
