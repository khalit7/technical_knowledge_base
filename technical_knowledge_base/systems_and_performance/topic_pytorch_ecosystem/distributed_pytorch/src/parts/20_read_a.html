0. In one screen

Distributed PyTorch runs the same Python script in several processes, one per device, and lets them cooperate only through collectives (operations every process in a group calls together, such as summing a tensor across all of them). Everything on this page is a way of deciding what each process holds and which collectives it calls: copy the model and split the data (DDP), split the model's state too (FSDP2), split the matrices (tensor parallel), split the sequence (sequence and context parallel), split the layers (pipelining), and save it all without ever gathering it in one place (DCP).

The parent page's {{Distributed lab|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}} tab already follows one training step of the running example (the topic's 3,186,944-parameter character GPT: 4 blocks, dmodel 256, batch 8 × 64 tokens, AdamW) through DDP, FSDP2, TP, a 2-stage pipeline, DCP and three hangs, and animates DDP against FSDP2. This page goes one level down into each API, on the same model, with new runs: 50 recordings on 2, 4 and 8 CPU processes. The theory (why ZeRO saves memory, the parallelism maths, which split to use at what scale) belongs to {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}}; NCCL itself to {{Streams, CUDA graphs and multi-GPU|n:3f05c17b0d0d81b19a6acab65c370b75}}. This page is what PyTorch's APIs actually do, and how to check it.

1. Processes, process groups and the store (c10d)

The problem. Eight Python processes start on eight GPUs. Before any tensor moves, each must learn who it is, find the others, and agree on a channel. c10d ("collective communication", PyTorch's distributed core) does this in three layers: a store (a small key-value server everyone can reach), a process group (a set of ranks plus a backend), and a backend (the library that moves bytes: NCCL between NVIDIA GPUs, gloo on CPUs).

What torchrun hands each process

Subgroups and meshes

A collective can run on any subset of ranks: dist.new_group([0, 1]) makes a group of two. A DeviceMesh builds them for you: init_device_mesh("cpu", (2, 2), mesh_dim_names=("dp", "tp")) lays ranks 0 to 3 out as [[0, 1], [2, 3]] and creates one group per row (the "tp" groups {0, 1} and {2, 3}) and one per column (the "dp" groups {0, 2} and {1, 3}). Recorded: rank 1 sits at coordinate (0, 1), its tp group is [0, 1] and its dp group [1, 3]. Neighbouring ranks share a row, which is why torchtitan puts tensor parallelism on the innermost (last) mesh dimension: neighbouring ranks share a server and its fast links (section 10). The {{Mesh explorer|#t-dpt-mesh}} tab shows every group of every layout run here.

Elastic restarts

When one process dies, the others block in their next collective. torchrun --max-restarts N turns that into a restart: its agent kills the survivors, runs the rendezvous again and starts every worker from the top of the script, with TORCHELASTIC_RESTART_COUNT incremented. Nothing is kept in memory, so the script must resume from its own checkpoint. Run here with rank 1 crashing at step 3:

An honest caveat: restarts on this machine were flaky
The 20-second timeout is the script's own (init_process_group(timeout=...)); the cause was not isolated (gloo over the loopback interface on macOS). torchrun's restart budget is what absorbed it, which is the general lesson: give --max-restarts some slack and make resuming cheap. For failures that should not restart the whole job, torchft keeps healthy replicas training ({{Ecosystem map|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}} tab has its status).
