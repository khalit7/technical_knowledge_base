4. FSDP2 in depth: policies, HSDP, prefetching, accumulation, state dicts

FSDP2 (torch.distributed.fsdp.fully_shard) is PyTorch's ZeRO stage 3: each rank keeps 1/n of every parameter, gradient and optimizer state, gathers a unit's full weights just before using them and reduce-scatters the gradients. The lab tab (sections 4 to 6) records it on the running example: fully_shard on each block, then on the whole model; 14 collectives per step; the root unit not resharded after forward. What fully_shard does to a module is concrete: every parameter becomes a DTensor (section 5) with placement Shard(0), the module's class is swapped for a new subclass that also inherits FSDPModule (checked here: GPT becomes FSDPGPT, whose bases are FSDPModule then GPT; each Block becomes FSDPBlock), so model.unshard(), reshard(), set_requires_gradient_sync() exist; and forward pre/post hooks plus autograd hooks schedule the gathers and reductions. How those hooks sit on the tensor subclass machinery is on the {{Extending PyTorch|n:3f85c17b0d0d8158a7addcd3d601d72a}} child. This section measures the knobs, on 2 and 4 processes.

MixedPrecisionPolicy: what travels in which dtype

Measured, 2 CPU processes, step 1. param_dtype=bfloat16 casts each gathered weight, so the all-gathers carry half the bytes and forward and backward compute in bfloat16; the sharded master weights and AdamW stay float32 (persistent state is the same in all three rows). reduce_dtype sets the gradient reduction. torchtitan's default is exactly the middle row: bfloat16 parameters, float32 reductions (torchtitan 0.3.0 config/configs.py L85 and L93). On this M1 Pro CPU, bfloat16 matrix multiplication has no hardware support (FACTS fst: 2.1 GFLOP/s), so these rows are for bytes and dtypes, not speed.

reshard_after_forward as an integer

After a block's forward, FSDP2 can free the gathered weights (True, gather again in backward), keep them (False, no second gather, more memory), or, given an integer k, keep them sharded over k ranks only. On 4 processes with reshard_after_forward=2, FSDP2 built a second mesh : forward all-gathers run over all 4 ranks (789,760 bytes in per block), backward all-gathers only within the pair (1,579,520 bytes in, from the pair's half). The step's peak above persistent state rose from 43.9 MB to 48.6 MB. The point on GPUs: make the pair the 8 GPUs of one server, so the backward gather never crosses the slower network.

HSDP: shard inside a group, replicate across groups

Pass a 2-D mesh, fully_shard(m, mesh=init_device_mesh("cpu", (2, 2), mesh_dim_names=("replicate", "shard"))), and every parameter is placed (Replicate(), Shard(0)): sharded over the 2 ranks of its row, copied in the other row. Per step on 4 processes: all-gathers and gradient reductions within the shard group, plus one all-reduce per unit across the replicate group, 19 collectives in all against FSDP's 14, for half the sharding (6,374,400 bytes of weights per rank against 3,187,200). Losses were identical to FSDP2 and DDP on 4 processes (3.801371, 3.171438, 3.121909). The {{Mesh explorer|#t-dpt-mesh}} lets you click any rank of any layout and see its groups, shards and collectives.

Prefetching: issuing the next gather early

By default FSDP2 prefetches implicitly: while block i runs forward it has already issued block i + 1's all-gather; in backward, the next block's. block.set_modules_to_forward_prefetch([...]) and set_modules_to_backward_prefetch([...]) name the modules explicitly, here two ahead. Gradient accumulation without reducing every micro-batch

model.set_requires_gradient_sync(False) is FSDP2's no_sync. Over 4 micro-batches on 2 processes: The all-gathers do not go away, because each micro-batch's forward and backward needs full weights again; set_reshard_after_backward(False) keeps them gathered between micro-batches at the cost of memory (not run here).

CPU offload, state dicts, and an unsharded surprise

  • offload_policy=CPUOffloadPolicy() ran here (losses , the same as plain FSDP2), but means nothing on a CPU: on a GPU it keeps the sharded parameters, gradients and optimizer state in host memory and runs the optimizer step on the CPU. Not measured on a GPU.
  • Sharded state dicts cost nothing. model.state_dict() issued ; get_model_state_dict(model, options=StateDictOptions(full_state_dict=True, cpu_offload=True)) issued all-gathers to build full tensors. Save with DCP (section 9) and you never pay the second.
  • After a forward without backward, the root's parameters are plain tensors. The root unit is not resharded after forward (it is needed first in backward), so its parameters are swapped for the unsharded full tensors until backward or reshard(). Recorded in the DCP run: were not DTensors after an evaluation forward. Code that inspects parameters after an eval forward sees full shapes on the root and shards on the blocks.
