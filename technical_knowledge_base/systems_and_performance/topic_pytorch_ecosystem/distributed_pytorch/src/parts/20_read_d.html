4. FSDP2: fully_shard, one unit gathered at a time

FSDP2 (torch.distributed.fsdp.fully_shard) is PyTorch's ZeRO stage 3 (the form is on {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}}, section 4): each rank keeps 1/n of every parameter, gradient and optimizer state, gathers a unit's full weights just before using them and reduce-scatters its gradients. You call fully_shard on each block, then on the whole model; each call makes one unit. What it does to a module is concrete:

  • every parameter becomes a DTensor (section 5) with placement Shard(0): on 4 ranks block 0's mlp.fc.weight [1024, 256] is [256, 256] per rank;
  • the module's class is swapped for a subclass that also inherits FSDPModule (checked: GPT becomes FSDPGPT, bases FSDPModule then GPT; each Block becomes FSDPBlock), so model.unshard(), reshard() and set_requires_gradient_sync() exist;
  • forward pre/post hooks and autograd hooks schedule the gathers and reductions (how they sit on the tensor-subclass machinery: {{Extending PyTorch|n:3f85c17b0d0d8158a7addcd3d601d72a}}).

One step on 4 ranks: 9 all-gathers bring each unit in, 5 reductions send its gradients out

Rank 0's step in issue order. The root unit (embeddings, final LayerNorm, the tied head) is gathered once and kept through backward, because backward needs it first; each block is gathered for its forward, freed, gathered again for its backward, and its gradients reduced: 1 + 4 + 4 = 9 all-gathers (28,160 bytes in for the root, 789,760 per block) and 4 + 1 = 5 reductions (3,159,040 bytes per block, 112,640 for the root; on gloo each is an all-reduce of the full gradient, section 2). The parent's {{Distributed lab|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}} tab animates this step against DDP's. Measured, 4 CPU processes, step 1.

Prefetching: issue the next gather early

By default FSDP2 prefetches implicitly: while block i runs forward it has already issued block i + 1's all-gather; in backward, the next block's. block.set_modules_to_forward_prefetch([...]) and set_modules_to_backward_prefetch([...]) name the modules explicitly, here two ahead.

Explicit prefetch issues gathers earlier, and holds more gathered weights at once

Measured, 2 CPU processes, step 2: bars are each block's forward and backward on rank 0, diamonds the all-gathers and gradient reductions as issued. Gloo on one thread does not overlap communication with compute the way NCCL streams do, so read the order, not the gaps.

MixedPrecisionPolicy: what travels in which dtype

Measured, 2 CPU processes, step 1. param_dtype=bfloat16 casts each gathered weight, so the all-gathers carry half the bytes and forward and backward compute in bfloat16; the sharded master weights and AdamW stay float32 (persistent state is the same in all three rows). reduce_dtype sets the gradient reduction. torchtitan's default is exactly the middle row: bfloat16 parameters, float32 reductions (torchtitan 0.3.0 config/configs.py L85 and L93). On this M1 Pro CPU, bfloat16 matrix multiplication has no hardware support (FACTS fst: 2.1 GFLOP/s), so these rows are for bytes and dtypes, not speed.

HSDP: shard inside a group, replicate across groups

Pass a 2-D mesh, fully_shard(m, mesh=init_device_mesh("cpu", (2, 2), mesh_dim_names=("replicate", "shard"))), and every parameter is placed (Replicate(), Shard(0)): sharded over the 2 ranks of its row, copied in the other row. Per step on 4 processes: all-gathers and gradient reductions within the shard group, plus one all-reduce per unit across the replicate group, 19 collectives in all against FSDP's 14, for half the sharding (6,374,400 bytes of weights per rank against 3,187,200). Losses were identical to FSDP2 and DDP on 4 processes (3.801371, 3.171438, 3.121909). Pick it when one node's worth of shards holds the model: the per-layer all-gathers stay on the node's fast links and only one gradient all-reduce per unit crosses the network. The {{Mesh explorer|#t-dpt-mesh}} shows every rank's groups, shards and collectives.

Gradient accumulation. model.set_requires_gradient_sync(False) is FSDP2's no_sync: over 4 micro-batches it removed reductions only (20 to 5); each micro-batch still gathered the weights (36 all-gathers either way), because its forward and backward need them.

Depth: reshard_after_forward as an integer, accumulation, offload, state dicts, an unsharded root, FSDP1 against FSDP2 (4 min)

reshard_after_forward as an integer. After a block's forward, FSDP2 can free the gathered weights (True, gather again in backward), keep them (False, no second gather, more memory), or, given an integer k, keep them sharded over k ranks only. On 4 processes with reshard_after_forward=2, FSDP2 built a second mesh : forward all-gathers run over all 4 ranks (789,760 bytes in per block), backward all-gathers only within the pair (1,579,520 bytes in, from the pair's half). The step's peak above persistent state rose from 43.9 MB to 48.6 MB. On GPUs, make the pair the 8 GPUs of one server, so the backward gather never crosses the slower network.

Accumulation, measured (4 micro-batches, 2 processes): set_reshard_after_backward(False) keeps weights gathered between micro-batches at the cost of memory (not run here).

  • offload_policy=CPUOffloadPolicy() ran here (losses , the same as plain FSDP2), but means nothing on a CPU: on a GPU it keeps the sharded parameters, gradients and optimizer state in host memory and runs the optimizer step on the CPU. Not measured on a GPU.
  • Sharded state dicts cost nothing. model.state_dict() issued ; get_model_state_dict(model, options=StateDictOptions(full_state_dict=True, cpu_offload=True)) issued all-gathers to build full tensors. Save with DCP (section 9) and you never pay the second.
  • After a forward without backward, the root's parameters are plain tensors. The root unit is not resharded after forward, so its parameters are swapped for the unsharded full tensors until backward or reshard(). Recorded in the DCP run: were not DTensors after an evaluation forward. Call model.reshard() after evaluation if code downstream expects shards.
