9. Distributed checkpoints (DCP): every rank writes its own shards

DCP (torch.distributed.checkpoint) has every rank write its own shards plus one .metadata file mapping every piece of every tensor to its offsets, so a checkpoint loads into any other layout and nothing is ever gathered on one rank. dcp.save(state, checkpoint_id=dir) and dcp.load(state, checkpoint_id=dir) take the state dict of DTensors that FSDP2 and TP already hold; the parent lab saved from 4 FSDP2 ranks and loaded into 2 and into 1.

10. Composing PP, FSDP and TP the torchtitan way

Real jobs combine several of these on one mesh. torchtitan (PyTorch's reference trainer; release 0.3.0 read here) does it in a fixed order, and the order is the lesson:

  1. Mesh, with tensor parallel innermost: dimensions ["pp", "dp_replicate", "fsdp", "tp"] unflattened from one world mesh (distributed/parallel_dims.py, build_mesh). Ranks next to each other share a server, so the chattiest axis (TP: collectives in every layer) gets the fastest links and the quietest (PP: point-to-point once per micro-batch) spans servers.
  2. Pipeline split first: the model (built on the meta device, no memory) is cut into stage modules, and everything below is applied to each stage (distributed/pipeline_parallel.py pipeline_llm, L65-125).
  3. Per stage: context parallel, then TP, then activation checkpointing, then torch.compile per block, then FSDP2 last (models/llama3/parallelize.py L42-94). FSDP2 goes last because it shards whatever DTensors TP produced along one more mesh dimension; compile goes before it so each block compiles once.
  4. Then weights are materialised and initialised on each rank (to_empty, init_weights), and the schedule (1F1B by default, config/configs.py L210) drives training.

Each layer of the recipe cuts the same weight again: TP's half, then FSDP's half of that

Block 0's mlp.fc.weight on rank 0 of the 8-process run (pp 2 × dp 2 × tp 2), drawn to scale: [1024, 256] in the model, [512, 256] after ColwiseParallel, [256, 256] after fully_shard. Its placements on the (dp, tp) mesh were : sharded on dimension 0 by TP and again, "strided", by FSDP (_StridedShard), so that each rank's rows are the right ones of TP's shard. Measured, 8 CPU processes, gloo.

Run here on 8 processes with the running example in that order: two stages of 2 blocks, TP on each block (the 16-all-reduce plan of section 6), fully_shard over the dp axis, Schedule1F1B with 4 micro-batches, and one all-reduce over the pp axis for the tied embedding and head, which now live on different stages. Each rank held about 1.6 MB of the 12.75 MB of weights, and every rank's gradients matched one process on the same 16 sequences to 1.8e-7. The dp reductions happen once per step, not per micro-batch: the pipeline asks FSDP2 to reduce only after the last micro-batch. The {{Mesh explorer|#t-dpt-mesh}} has this layout rank by rank.
